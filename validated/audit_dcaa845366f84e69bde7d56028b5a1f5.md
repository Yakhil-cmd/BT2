### Title
Webhook signature is verified against `repository.owner.login`, but events are applied to the repository named in `repository.full_name` — cross-organization webhook forgery in a multi-org Shipit install - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App / `webhook_secret` to check the HMAC signature against using the untrusted, unverified field `repository.owner.login` (or `organization.login`) taken straight from the raw JSON body. [1](#0-0)  Once the signature check passes, every event handler determines *which* `Repository`/`Stack` to mutate using a **different** field of the same untrusted body: `payload.dig('repository', 'full_name')`. [2](#0-1)  Nothing checks that `repository.owner.login` (the value used to select the verification key) and the owner embedded in `repository.full_name` (the value used to select the object being written) refer to the same organization. In a multi-tenant `secrets.github` configuration, where each organization has its own independently-generated `webhook_secret`, [3](#0-2)  this lets a party who legitimately controls one onboarded organization's GitHub App (and therefore knows that org's `webhook_secret`) forge and self-sign a payload that is verified as "from OrgA" but whose `repository.full_name` points at a completely different organization/repository (`OrgB/...`) also tracked by the same Shipit instance.

### Finding Description
The binding that should hold is:
`organization whose signature was verified == organization that owns the repository being mutated`

Before the fix: `verify_signature` computes `repository_owner = params.dig('repository','owner','login') || params.dig('organization','login')` and fetches `Shipit.github(organization: repository_owner)` to verify the signature. [4](#0-3)  Every concrete handler (`PushHandler`, `StatusHandler` via `Commit.where(sha:)`, `PullRequest::*Handler`, etc.) then acts on data keyed by `payload['repository']['full_name']`, resolved through `Repository.from_github_repo_name` in the shared `Handler` base class. [2](#0-1)  `repository.owner.login` and `repository.full_name` are two independently attacker-controlled strings inside the same unsigned-at-parse-time JSON body — the HMAC covers the raw bytes as a whole, but the controller never re-derives the "owner" used for verification from the same `full_name` it later trusts for routing, nor does it reject payloads where they disagree.

Concretely, `PushHandler` uses `params.after`/`params.ref` plus the resolved `stacks` (found via `full_name`) to enqueue `GithubSyncJob` for that stack with an attacker-chosen `expected_head_sha`. [5](#0-4)  An attacker who administers OrgA's real GitHub App installed on this Shipit instance can sign an arbitrary payload with OrgA's secret (`repository.owner.login: "OrgA"`), while setting `repository.full_name: "OrgB/victim-repo"`. `verify_signature` verifies successfully against OrgA's `webhook_secret`, and `PushHandler` then walks the actual OrgB-owned `Stack` and pushes it into `sync_github` for a branch/sha the attacker chose — none of which came from GitHub for OrgB at all.

This is worse for `StatusHandler`, which doesn't even consult `repository.full_name`; it resolves target commits purely by `Commit.where(sha: params.sha)`, [6](#0-5)  so any organization validly onboarded to the Shipit instance can post a forged `success`/`failure` status for a commit sha belonging to any other tracked stack (trivial to align when the same commit/tree is shared across mirrored/forked repos tracked under different orgs in the same instance), which can feed directly into `MergeRequest#all_status_checks_passed?`/`any_status_checks_missing?` used by the automated merge queue. [7](#0-6) 

### Impact Explanation
This crosses a documented, multi-tenant trust boundary: one organization's GitHub App credentials should only be able to affect that organization's own stacks. Because the code authenticates against one payload field and acts against a different, unrelated payload field, an org-scoped webhook secret can be leveraged to inject fabricated push/status events for another organization's stacks in the same Shipit deployment — potentially forcing spurious syncs, spoofing CI status used for automerge, or corrupting deployment state for a repository the attacker does not own. This matches the High-severity class of "escalation into cross-tenant authorization" / "unauthorized deploy or merge" called out in the rules.

### Likelihood Explanation
Exploitation requires the attacker to control (or have compromised) at least one legitimate organization's GitHub App/webhook secret that is configured in the same shared Shipit installation (multi-org configuration as documented in `docs/setup.md`). This is a realistic scenario for shared/internal Shipit deployments serving multiple teams or business units, each with their own onboarded GitHub org, since Shipit explicitly supports and documents this multi-org model. [3](#0-2)  No GitHub write access to the victim org, no Shipit session, and no `ApiClient` token are needed — only the ability to send an HTTP POST to `/github/webhooks` (or equivalent mounted webhook route) with a payload signed using the attacker's own legitimately-known secret.

### Recommendation
In `WebhooksController#verify_signature` (and/or in `Shipit::Webhooks::Handlers::Handler`), require that the organization used to select/verify the webhook signature is the same organization embedded in `repository.full_name` (and `organization.login` when present) before dispatching to a handler; reject the request (422) on any mismatch. Additionally, scope `StatusHandler#process` (and any other handler that looks up records purely by content hash, e.g. `Commit.where(sha:)`) to the resolved `Repository`/`Stack` derived from the verified organization, rather than matching commits globally by sha across all tenants.

### Proof of Concept
1. Shipit is configured with `secrets.github` containing two orgs, `OrgA` and `OrgB`, each with its own `webhook_secret` (per `docs/setup.md`'s "Using Multiple Github Applications" section).
2. Attacker legitimately owns/administers `OrgA`'s GitHub App and therefore knows `OrgA`'s `webhook_secret`.
3. Attacker crafts a JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "deadbeefdeadbeefdeadbeefdeadbeefdeadbeef",
  "repository": {
    "full_name": "OrgB/victim-repo",
    "owner": { "login": "OrgA" }
  }
}
```
4. Attacker computes `X-Hub-Signature: sha1=HMAC(OrgA_webhook_secret, body)` and sends `POST /github/webhooks` with header `X-Github-Event: push`.
5. `WebhooksController#verify_signature` resolves `repository_owner = "OrgA"`, fetches OrgA's `GitHubApp`, and the signature check succeeds (attacker computed it with the correct, known secret). [4](#0-3) 
6. `PushHandler#process` resolves stacks via `payload['repository']['full_name'] = "OrgB/victim-repo"`, unrelated to the verified `OrgA`, and enqueues `GithubSyncJob` with the attacker-chosen `expected_head_sha` against OrgB's real stack. [5](#0-4)  The org whose credentials were checked never matches the org whose stack was mutated.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping
      head(:ok) if event == 'ping'
    end

    def event
      request.headers.fetch('X-Github-Event')
    end

    def repository_owner
      # Fallback to the organization sub-object if repository isn't included in the payload

    end
