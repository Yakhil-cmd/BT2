### Title
Submodule credential leakage due to host-only (path-insensitive) git credential matching - (File: main.go)

### Summary
`git-sync` stores repository credentials via Git's credential store using `git credential approve` with the full `--repo` URL, then relies on Git's own credential lookup (`git credential fill`) to supply those credentials for every subsequent git network operation, including submodule fetches triggered during `configureWorktree`. Git's credential matching by default operates on **scheme + host (+port)**, not on the full path, unless `credential.useHttpPath` is explicitly enabled. `git-sync` never sets `credential.useHttpPath`, so any submodule URL that shares the same host as the main `--repo` — but points to a different, attacker-controlled path — will transparently receive the same stored username/password. Since submodule URLs come from `.gitmodules` inside the synced repository content itself, an attacker who can influence a commit that git-sync fetches (a malicious PR merge, a compromised branch, or any attacker-controlled ref reachable by git-sync) can redirect the credentialed request to an endpoint they control on the same host, exfiltrating the stored username/password.

### Finding Description
This is the git-sync analog of the RubiconRouter bug class: an intermediary/proxy identity (here, Git's credential store keyed loosely by host) is trusted by a downstream operation (submodule fetch) without verifying it actually belongs to the entity that was granted the credential (the specific `--repo` path).

- `refreshCreds` in `main.go` calls `git.StoreCredentials(ctx, cred.URL, cred.Username, password)` for each `--credential` entry and for `--askpass-url` results, using `git credential approve` [1](#0-0) [2](#0-1) .
- `StoreCredentials` writes `url=<v>\nusername=<v>\npassword=<v>\n` to `git credential approve`, which stores the credential in Git's credential cache/store keyed by the URL's scheme/host (and path only if `useHttpPath` is set) [3](#0-2) .
- Nowhere does the codebase set `http.<url>.useHttpPath` or otherwise scope stored credentials to the exact repo path; the only git-config knobs exposed are the generic `--git-config`/`--git-config-add` flags, which are user-supplied and off by default.
- During `configureWorktree`, when submodules are enabled, `git-sync` runs `submodule update --init` (optionally `--recursive`) directly against the checked-out worktree content [4](#0-3) . The submodule URLs are read from `.gitmodules`, which is part of the synced repository content — i.e., attacker-influenced if the attacker can land a commit/ref that git-sync will sync.
- Because Git's credential helper resolves credentials by host by default, a `.gitmodules` entry pointing to `https://<same-host>/attacker/evil-repo` will cause Git to present the main repo's stored username/password to that attacker-controlled path during the submodule fetch.

The e2e test `e2e::submodule_sync_over_http_different_passwords` demonstrates that git-sync intentionally stores distinct per-URL credentials to support multiple submodule hosts [5](#0-4) , confirming that path-based credential separation is not otherwise enforced by git-sync itself — it depends entirely on Git's default (host-only) matching behavior, which is insufficient to segregate multiple repos/paths on the same host.

### Impact Explanation
An attacker who can get a commit synced by git-sync (e.g., merge/push access to a branch/ref git-sync tracks, or control of a fork merged upstream) can add or modify a submodule entry to point at a same-host path they control. When git-sync's next sync runs `git submodule update --init`, Git will automatically attach the previously-approved username/password (or askpass-url-provided credentials) to the HTTP request against the attacker's URL, disclosing the operator's git credentials to the attacker. This satisfies the "credential or token disclosure" impact class.

### Likelihood Explanation
Requires: (1) `--credential`, `--askpass-url`, or `--username`/password-based auth in use (common for private repos), (2) submodules enabled (`--submodules`, default `recursive`), and (3) an attacker-influenced commit reaching git-sync's synced ref, and (4) a same-host path the attacker can point to (e.g., another namespace/repo on the same self-hosted Git server, or an attacker-controlled path under the same domain). This is a realistic scenario for self-hosted GitLab/Gitea/Bitbucket-style multi-tenant hosts where different users/orgs share a host but have differing trust levels, which is exactly the kind of setup git-sync's multi-credential (`--credential`) feature is designed to support.

### Recommendation
- Have `git-sync` explicitly set `credential.useHttpPath=true` (or configure the credential store per exact URL including path) when storing/approving credentials, so Git's credential matching honors the full path and does not leak credentials across different paths on the same host.
- Additionally/alternatively, restrict submodule fetches to an explicit allowlist of URLs/hosts configured by the operator (matching the `--credential` URL list), rejecting any submodule URL not present in that allowlist.

### Proof of Concept
1. Operator configures git-sync with `--repo=https://git.example.com/org/main-repo`, `--username=svc`, `--password-file=/creds/pass`, and `--submodules=recursive`.
2. `refreshCreds`/`StoreCredentials` runs `git credential approve` with `url=https://git.example.com/org/main-repo` and the service credentials [3](#0-2) .
3. An attacker with push/merge access to `main-repo` (or a merged PR) adds a `.gitmodules` entry: `url = https://git.example.com/attacker/evil-repo`.
4. On the next sync, `configureWorktree` runs `git submodule update --init --recursive` [4](#0-3) .
5. Because `credential.useHttpPath` is not set, Git's credential helper matches by host only (`git.example.com`) and attaches `svc`'s username/password to the request for `evil-repo`, which the attacker's server-side controls/logs, disclosing the credential.

// StoreCredentials stores a username and password for later use.
func (git *repoSync) StoreCredentials(ctx context.Context, url, username, password string) error {
	git.log.V(1).Info("storing git credential", "url", redactURL(url))
	git.log.V(9).Info("md5 of credential", "url", url, "username", md5sum(username), "password", md5sum(password))

	creds := fmt.Sprintf("url=%v\nusername=%v\npassword=%v\n", url, username, password)
	_, _, err := git.RunWithStdin(ctx, "", creds, "credential", "approve")
	if err != nil {
		return fmt.Errorf("can't configure git credentials: %w", err)
	}

	return nil
}
