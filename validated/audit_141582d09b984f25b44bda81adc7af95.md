### Title
Command injection via crafted hook script filename in `test-hook.sh` non-executable fallback - ([File: plugins/plugin-dev/skills/hook-development/scripts/test-hook.sh])

### Summary
`test-hook.sh` builds an inner shell command string by directly interpolating the unsanitized `$HOOK_SCRIPT` filename into a `bash -c "..."` argument. Because filenames can legally contain shell metacharacters (backticks, `$()`, `;`, `|`), an attacker who checks a non-executable file with such a crafted name into a plugin/hook directory can achieve arbitrary command execution when a developer (or an agent following the documented `hook-development` skill workflow) runs `test-hook.sh` against that file.

### Finding Description
`HOOK_SCRIPT="$1"` at line 135 stores the raw filename argument. Since the file is checked into the repo and is non-executable (the normal state of a freshly committed script before `chmod +x`), the executable check at lines 144-147 fires and rewrites `HOOK_SCRIPT="bash $HOOK_SCRIPT"`, concatenating the attacker-controlled filename literally, backticks and all: [1](#0-0) 

That value is later spliced, unquoted, into a string passed to a fresh `bash -c` invocation:
`output=$(timeout "$TIMEOUT" bash -c "cat '$TEST_INPUT' | $HOOK_SCRIPT" 2>&1)` [2](#0-1) 

The double quotes only protect the string during construction in the *outer* shell; once handed to the *inner* `bash -c`, any backticks, `$()`, `;`, `|`, etc. that are part of the filename are re-parsed and executed as shell syntax by that inner shell. A file literally named, e.g., `` `touch /tmp/pwned`.sh `` passes the `[ -f "$HOOK_SCRIPT" ]` existence check at line 139 (Linux filenames may contain backticks), then produces the line `cat 'test-input.json' | bash \`touch /tmp/pwned\`.sh`, which the inner bash parses as command substitution, executing `touch /tmp/pwned` before the pipeline even runs.

Nothing in the script sanitizes the filename for shell metacharacters, quotes it for safe reuse in `bash -c`, or uses an array/exec form instead of string interpolation.

### Impact Explanation
Arbitrary command execution on the machine of whoever (developer or an agent autonomously following the `hook-development` skill's documented workflow step "Test hooks with `scripts/test-hook.sh` before deployment") runs this script against a maliciously named file supplied via a plugin/hook repository or PR. This matches an unauthorized command execution / workspace compromise impact — the victim's shell runs attacker-chosen commands with the victim's own privileges, which can lead to secret disclosure, file mutation, or further compromise of the developer's environment.

### Likelihood Explanation
Preconditions: attacker must be able to get a maliciously-named, non-executable file into a repository/plugin directory that the victim (human or agent) later tests with `test-hook.sh <that-file> <input.json>`, which is an explicitly documented step in `SKILL.md`'s Implementation Workflow. Checking in a file with backticks/`$()` in its name is trivial on typical Unix filesystems and requires no special privileges — an ordinary contributor/PR author can do it. The bug is deterministically triggered whenever the crafted file is non-executable (the default state for checked-in scripts), which is exactly the fallback path in question.

### Recommendation
Never interpolate a filename into a string executed via `bash -c`. Instead:
- Invoke the hook directly via `"$HOOK_SCRIPT"` (or `bash "$HOOK_SCRIPT"`) as an argv element, e.g. `timeout "$TIMEOUT" bash -c 'cat "$1" | "${@:2}"' _ "$TEST_INPUT" bash "$HOOK_SCRIPT"`, or better, avoid the extra `bash -c` layer entirely and run `cat "$TEST_INPUT" | timeout "$TIMEOUT" bash "$HOOK_SCRIPT"` with `$HOOK_SCRIPT` always passed as a properly quoted argument, not string-concatenated.
- Reject/validate filenames containing shell metacharacters before use, as defense in depth.

### Proof of Concept
Integration test plan:
1. Create a non-executable file named `` `touch /tmp/hookpoc`.sh `` (or `$(touch /tmp/hookpoc).sh`) with arbitrary shell content, e.g. `#!/bin/bash\nexit 0`.
2. Create a minimal valid JSON test input file `input.json` containing `{}`.
3. Run: `bash plugins/plugin-dev/skills/hook-development/scripts/test-hook.sh '`touch /tmp/hookpoc`.sh' input.json`.
4. Assert that `/tmp/hookpoc` exists after execution, proving the `touch` command embedded in the filename executed via the inner `bash -c` regardless of the intended hook logic — demonstrating command injection through the unsanitized `HOOK_SCRIPT` interpolation at line 190, reached deterministically through the non-executable fallback at lines 144-147.
