## Finding

### Title
Stack-scoped API client token authorizes reads of any stack via CCMenu endpoint - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`ApiClient` records can be scoped to a single stack via the `stack_id` column, and every other API endpoint enforces that scope by resolving the target stack through `BaseController#stacks`/`#stack`, which filters `Stack.where(id: current_api_client.stack_id)` when the client is stack-scoped. `Api::CCMenuController` overrides `#stack` to bypass that filter entirely, so a token that is only authorized for one stack can be used to read the CI/build status of any stack in the installation.

### Finding Description
`Shipit::Api::BaseController` defines the scoping contract that all API endpoints are expected to rely on: [1](#0-0) 

Any `ApiClient` with a non-nil `stack_id` is meant to be restricted to that one stack — this is exactly what `Api::StacksController` relies on and what is tested ("an api client scoped to a stack will only see that one stack").

`Api::CCMenuController`, however, redefines `stack` to resolve directly from `Stack.from_param!(params[:stack_id])` instead of going through the scoped `stacks`/`stack` helper from `BaseController`: [2](#0-1) 

`require_permission :read, :stack` only checks that the `"read:stack"` string is present in `ApiClient#permissions` — it does not verify which stack the permission applies to: [3](#0-2) 

Because `CCMenuController#stack` never consults `current_api_client.stack_id`, any authenticated `ApiClient` holding the generic `read:stack` permission — including one deliberately scoped to only stack A via its `stack_id` — can pass a different `stack_id` in the URL and receive the CCMenu XML (build/deploy status) for stack B, C, etc. This breaks the binding: "the stack a token authorizes" (`ApiClient#stack_id`) vs. "the stack the request actually touches" (`params[:stack_id]` in `CCMenuController#stack`).

### Impact Explanation
This crosses the authorization boundary intended by per-stack `ApiClient` scoping, giving an unprivileged (but token-holding) actor unauthenticated-relative read access to stack/deploy state (last deploy status, activity, lock status) for stacks they were never granted access to. This matches the in-scope High-severity bucket for "unauthenticated read of stack state ... or deploy output" achieved via an authorization-scope escalation rather than a legitimate grant.

### Likelihood Explanation
Any environment that creates stack-scoped `ApiClient`s (a supported, documented feature exposed through the admin UI/`ApiClientsController`) and exposes a CCMenu URL/token is affected. Exploitation requires only knowledge of another stack's `to_param`/slug, which is generally public/discoverable information within a Shipit instance, and a single GET request — no privileged access or additional credentials beyond the possessed token are needed.

### Recommendation
Have `Api::CCMenuController#stack` reuse the scoped resolution from `BaseController` (i.e., `stacks.from_param!(params[:stack_id])`) instead of `Stack.from_param!`, so that stack-scoped `ApiClient` tokens cannot be used to read state of stacks outside their granted scope.

### Proof of Concept
1. As an admin, create an `ApiClient` scoped to Stack A only: `ApiClient.create!(creator: admin, name: 'A-only', stack: stack_a, permissions: ['read:stack'])`.
2. Using that client's `authentication_token`, request `GET /api/stacks/:stack_b_id/ccmenu.xml?token=<token>` where `stack_b_id` refers to Stack B (a different stack the client is not scoped to).
3. Observe the CCMenu XML response contains Stack B's `lastBuildStatus`/activity, even though the token was only meant to authorize reads on Stack A, because `Api::CCMenuController#stack` resolves `Stack.from_param!(params[:stack_id])` directly rather than through the scoped `stacks` collection used everywhere else in the API. Contrast with `Api::StacksController#index`, which correctly restricts results for the same stack-scoped client (see `test/controllers/api/stacks_controller_test.rb` test "an api client scoped to a stack will only see that one stack"). # frozen_string_literal: true

```ruby
module Shipit
  module Api
    class CCMenuController < BaseController
      require_permission :read, :stack

      class NoDeploy
        def id
          0
        end

        def ended_at
          Time.now.utc
        end

        def running?
          false
        end
      end

      def show
        latest_deploy = stack.deploys_and_rollbacks.last || NoDeploy.new
        render('shipit/ccmenu/project', formats: [:xml], locals: { stack:, deploy: latest_deploy })
      end

      private

      def stack
        @stack ||= Stack.from_param!(params[:stack_id])
      end

      def authenticate_api_client
        @current_api_client = ApiClient.authenticate(params[:token])
        super unless @current_api_client
      end
    end
  end
end
```
