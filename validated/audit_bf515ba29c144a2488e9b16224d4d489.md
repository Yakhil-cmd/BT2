### Title
Webhook signature is bound to the payload's organization, but handlers write to repositories/commits identified by unverified fields, enabling cross-tenant forgery of pushes, check-runs and CI statuses - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects the GitHub App/secret to validate the HMAC signature using the organization derived from `repository.owner.login` (or `organization.login`), but the event handlers that mutate state (`PushHandler`, `CheckSuiteHandler`, and especially `StatusHandler`) look up the target repository/commit using different, uncorrelated payload fields (`repository.full_name`, or a bare commit `sha` with no repository scoping at all). In Shipit's multi-organization mode, each tenant organization has its own independent `webhook_secret`. An attacker who legitimately controls one tenant's GitHub App webhook secret can therefore forge a validly-signed request for "their" organization while making the payload's repository/commit fields point at a *different* tenant's stack, causing Shipit to act on data the signer never had rights over.

### Finding Description
`verify_signature` computes trust based solely on the org name extracted from the payload: [1](#0-0) [2](#0-1) 

This binds the request only to *an* organization's secret matching `repository.owner.login`/`organization.login`. Shipit explicitly supports multiple independently-configured organizations, each with its own `webhook_secret`: [3](#0-2) [4](#0-3) 

Once the signature check passes for "OrgA," the entire raw JSON `params` (not just the parts covering OrgA) is dispatched unchanged to handlers:

```ruby
Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }
``` [5](#0-4) 

Handlers resolve their target repository from `repository.full_name`, a field completely independent of the `repository.owner.login`/`organization.login` value that determined which secret verified the signature: [6](#0-5) [7](#0-6) [8](#0-7) 

`StatusHandler` is worse: it does not scope by repository at all, resolving purely by commit `sha` across the entire Shipit instance: [9](#0-8) 

The equality that should hold but does not: `organization authenticated by verify_signature (repository.owner.login) == organization that owns the repository/commit acted upon by the handler`. Nothing enforces this equality; the two lookups are performed on different, attacker-influenced fields of the same JSON body, and the signature only proves that *some* field of the body (the whole raw body) was signed by *a* known org's secret - it does not prove the semantic consistency between `repository.owner.login` and `repository.full_name`/`sha`.

### Impact Explanation
In a multi-org deployment, an attacker who administers/controls the GitHub App webhook secret for one weakly-trusted tenant organization (unprivileged with respect to any other tenant or to Shipit itself) can send a single validly-signed POST to `/webhooks` where:
- `push` event: `repository.owner.login` = "OrgA" (their own org, used to pick and satisfy the secret check) but `repository.full_name` = "OrgB/production-repo" (a repository/stack belonging to a different tenant). This triggers `stack.sync_github(expected_head_sha: params.after)` on OrgB's stack with an attacker-chosen `after` SHA, corrupting/desynchronizing another tenant's deploy history tracking.
- `status` event: since `StatusHandler` has zero repository scoping, the attacker can forge a CI status (`state`, `context`, `description`, `target_url`) for *any* commit SHA tracked anywhere in the Shipit instance, including commits belonging to other tenants. Commit statuses gate the merge queue and deploy readiness checks, so this can flip a blocking/failing status to `success`, directly enabling an unauthorized merge or deploy decision downstream - the exact "unauthorized deploy/merge" impact class called out in scope.
- `check_suite` event: similarly triggers `RefreshCheckRunsJob`/`schedule_refresh_check_runs!` against another tenant's commits.

This is a cross-tenant authentication/authorization boundary break: the HMAC only proves possession of one organization's secret, yet the write target is chosen by an unrelated, unverified field.

### Likelihood Explanation
Requires the attacker to control (or know) the `webhook_secret` for at least one organization configured in the multi-org Shipit deployment - a routine, low-privilege position for anyone who administers a GitHub App/organization onboarded onto a shared Shipit instance, and requires no Shipit session, API token, or GitHub write access to the victim organization/repository at all. Constructing the forged JSON body and HMAC is trivial once the secret is known.

### Recommendation
After verifying the signature, re-derive the handler's repository/commit scoping strictly from the same organization value (`repository_owner`) used to select the signing secret, and reject the webhook if `repository.full_name`'s owner segment (or the commit's associated repository owner, for `status`) does not match `repository_owner`. For `StatusHandler` specifically, scope the `Commit.where(sha: params.sha)` lookup to repositories belonging to the verified organization before creating a status.

### Proof of Concept
1. Deploy Shipit configured with two tenant organizations, `OrgA` and `OrgB`, each with a distinct `webhook_secret` (as supported by `Shipit.github_app_config`), each with tracked stacks.
2. As an attacker who only knows/controls `OrgA`'s `webhook_secret` (e.g., they administer OrgA's GitHub App), craft a JSON body:
   ```json
   {
     "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/production-repo" },
     "ref": "refs/heads/master",
     "after": "<attacker-chosen sha>"
   }
   ```
3. Compute `X-Hub-Signature` as `sha1=` + `HMAC-SHA1(OrgA_webhook_secret, body)`.
4. POST to `/webhooks` with header `X-Github-Event: push`.
5. `verify_signature` resolves `repository_owner` = "OrgA", fetches OrgA's `GitHubApp`, and the HMAC validates successfully (`app/controllers/shipit/webhooks_controller.rb:24-30`).
6. `PushHandler#stacks` resolves the target via `repository.full_name` = "OrgB/production-repo" (`app/models/shipit/webhooks/handlers/handler.rb:32-38`) and calls `stack.sync_github(expected_head_sha: params.after)` on OrgB's stack - a stack the attacker has no legitimate signing authority over.
7. For an even simpler demonstration, send a `status` event signed with OrgA's secret referencing any known commit `sha` belonging to OrgB; `StatusHandler#process` creates the forged status unconditionally (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`), with no repository check whatsoever.
