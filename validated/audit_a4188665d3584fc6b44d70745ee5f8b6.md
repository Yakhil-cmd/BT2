### Title
Cross-organization webhook forgery escalates into `Shipit.github_teams` authorization - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`WebhooksController` selects which GitHub App/webhook secret to verify a webhook signature against using the organization named inside the *unverified* JSON body, but the handler that actually mutates state (`MembershipHandler`) trusts a different field of that same body (a numeric `team.id`) without checking that it belongs to the signing organization. An operator of any organization onboarded into a multi-tenant Shipit instance can therefore forge a `membership` webhook, sign it with their own legitimately-known webhook secret, and add an arbitrary GitHub login to a `Team` that belongs to a different organization — including a team listed in `Shipit.github_teams`, which gates authenticated access to the whole instance.

### Finding Description
`WebhooksController#verify_signature` picks the GitHub App config to verify against based on a field taken directly from the untrusted payload: [1](#0-0) [2](#0-1) 

For `membership` events there is no `repository` key, so `repository_owner` falls back to `params.dig('organization', 'login')`. Signature verification therefore only proves "this payload was signed by *some* organization's configured webhook secret" — it proves nothing about the `team.id` or `member.login` fields also contained in the same payload.

`MembershipHandler#process` then trusts `team.id` (a raw GitHub numeric database ID) to look up or create a `Team`, and unconditionally adds the named member to it: [3](#0-2) 

`find_or_create_by!(github_id: params.team.id)` only sets `organization` when the `Team` row does **not** already exist; if the team already exists (e.g. it was previously synced because it belongs to a legitimate, different organization tracked by the same Shipit instance), the `organization` field is left untouched, and `team.add_member(member)` still executes for the login supplied in the forged payload.

`Shipit.github(organization:)` selects a distinct `GithubApp`/secret per organization key in `secrets.github`, confirming Shipit supports multiple organizations, each presumably administering their own GitHub App/webhook secret: [4](#0-3) [5](#0-4) 

Membership in a `Team` listed in `Shipit.github_teams` is exactly what grants authenticated access to the application: [6](#0-5) 

The binding that should hold — `signing_organization(payload) == owning_organization(team.id)` — is never checked; only the raw `team.id` numeric value is trusted, decoupled from the organization whose secret validated the request.

### Impact Explanation
An attacker who legitimately administers their own organization's GitHub App in a multi-org Shipit deployment (an "unprivileged attacker" relative to any *other* org's data) knows their own `webhook_secret`. Using it, they can forge a `membership` webhook naming their own org (so signature verification passes) but referencing the numeric `team.id` of a different organization's team that is configured in `Shipit.github_teams`. This adds any GitHub login of the attacker's choosing to that team in Shipit's database, without any real GitHub team membership. Since `User#authorized?` checks Shipit `Team` membership, not live GitHub state at request time (aside from OAuth login), the attacker's chosen account becomes authorized in the target instance — enabling deploys, rollbacks, locks, and merges on stacks/repositories they had no legitimate access to. This matches the listed High-impact category "escalation into `Shipit.github_teams` authorization," and can cascade into an unauthorized deploy/merge (Critical).

### Likelihood Explanation
Exploitation requires only: (1) being an administrator of any one organization already configured in the target Shipit instance (a normal, unprivileged-relative-to-others tenant), and (2) knowing or guessing a numeric GitHub `team.id` belonging to another tracked organization (team IDs are small sequential integers and are frequently observable via the GitHub API, public webhook payload examples, or prior legitimate webhook deliveries already stored in Shipit's `Hook`/`Delivery` records). No GitHub App private key, Shipit session, or `ApiClient` token is needed — only an HTTP POST with a correctly-HMAC-signed body using the attacker's own known secret. This is realistic in any deployment that onboards more than one organization.

### Recommendation
In `MembershipHandler` (and any other handler that derives authorization-relevant identifiers from webhook payload fields not covered by the signing key selection), verify that the `organization.login` used to select/verify the webhook signature matches the organization that actually owns the `team.id`/`repository` being mutated — e.g., re-fetch or cross-check the team's organization before calling `team.add_member`, and reject the event if it doesn't match `repository_owner`/the verified signing organization. More generally, `WebhooksController#verify_signature` should bind the field used to pick the verification secret to the same field(s) later used for authorization-sensitive writes, rather than allowing them to diverge.

### Proof of Concept
1. Attacker administers "attacker-org", legitimately configured in Shipit as `secrets.github['attacker-org']` with a known `webhook_secret`.
2. Attacker discovers (via GitHub API, prior webhook deliveries, or brute-force of small sequential IDs) the numeric `github_id` of a `Team` belonging to "victim-org" that is listed in `Shipit.github_teams`.
3. Attacker builds the payload:
```json
{
  "action": "added",
  "team": {"id": 4242, "name": "victim-team", "slug": "victim-team", "url": "https://api.github.com/teams/4242"},
  "organization": {"login": "attacker-org"},
  "member": {"login": "attacker-controlled-account"}
}
```
4. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(attacker-org_webhook_secret, body)` and POSTs it to the Shipit webhooks endpoint with header `X-Github-Event: membership`.
5. `WebhooksController#verify_signature` calls `Shipit.github(organization: 'attacker-org')`, which succeeds because the payload really was signed with attacker-org's own secret.
6. `MembershipHandler#process` runs `Team.find_or_create_by!(github_id: 4242)`, finds the pre-existing "victim-team" `Team` row (owned by victim-org), and calls `team.add_member(User.find_or_create_by_login!('attacker-controlled-account'))`.
7. `attacker-controlled-account` is now a member of victim-org's authorized team in Shipit's database. When that GitHub account subsequently completes normal OAuth login, `User#authorized?` returns `true`, granting full access to victim-org's stacks.

```ruby
          team = find_or_create_team!
          member = User.find_or_create_by_login!(params.member.login)

          case params.action
          when 'added'
            team.add_member(member)
          when 'removed'
            team.members.delete(member)
          else
            raise ArgumentError, "Don't know how to perform action: `#{action.inspect}`"
          end
        end

          Team.find_or_create_by!(github_id: params.team.id) do |team|

            team.organization = params.organization.login
          end
        end
```

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
