Based on the analysis, I found a concrete cross-repository write binding break in the webhooks controller.

### Title
Webhook signature verified against the payload's organization but commit-status writes are applied to any repository named in the same unverified payload - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` picks the GitHub App/secret to validate the HMAC signature against using the organization named inside the still-unverified JSON body (`repository.owner.login`), then, once "verified", dispatches the *entire* raw body to event handlers that independently re-derive the target repository from another field of that same body (`repository.full_name`), with no requirement that the two agree.

### Finding Description
`verify_signature` computes `repository_owner` from the request body itself (`params.dig('repository', 'owner', 'login')`) and uses it to select which configured GitHub App's `webhook_secret` to check the `X-Hub-Signature` against: [1](#0-0) [2](#0-1) 

In the multi-org configuration (`config/secrets.yml` with per-organization `app_id`/`installation_id`/`webhook_secret`), each org has its own independent secret: [3](#0-2) [4](#0-3) 

Once the signature check passes for `repository_owner`, the whole raw body is handed to handlers, e.g. `StatusHandler`, which locates target `Commit` rows purely by `sha` (with no repository/owner scoping at all) and writes a new `Status` from other attacker-controlled fields (`state`, `description`, `target_url`, `context`, `created_at`): [5](#0-4) 

Other handlers (e.g. `PullRequest::OpenedHandler`, `ClosedHandler`, `AssignedHandler`) do scope to a repository, but that repository is derived from `params.repository.full_name` — a field entirely independent of `repository_owner`, which is what the signature actually authenticated: [6](#0-5) [7](#0-6) 

The binding that should hold is: `organization whose secret validated the signature == organization that owns the repository being mutated`. Nothing in the controller or handlers enforces `repository.owner.login == repository.full_name.split('/').first`, or that `repository.full_name`'s owner is the same organization as `repository_owner`. An attacker who legitimately controls (or can trigger) valid webhook deliveries from Organization A — for which they know/can compute a valid signature (e.g., they are able to trigger their own repo's webhook in an org that shares the Shipit instance) — can craft a `status` (or `pull_request`) payload whose `repository.owner.login` is Org A (so the signature check passes with Org A's secret) but whose `repository.full_name` names a completely different, unrelated Org B repository tracked by the same Shipit instance.

### Impact Explanation
For the `status` event this is especially severe because `StatusHandler` doesn't even use `repository.full_name` — it matches purely on commit `sha` across the whole database, so any organization able to pass its own signature check can forge CI status ("success"/"failure") for any commit sha it knows about in any stack of the entire Shipit instance. Forged "success" statuses feed directly into `MergeRequest#reject_unless_mergeable!`/`all_status_checks_passed?` (via `StatusChecker`) which gates the merge queue, and into `Stack#deployment_checks_passed?`/CI-required-status logic that gates deploys: [8](#0-7) 

This allows an attacker who only has legitimate access to one organization on a shared multi-org Shipit instance to inject fake CI-passing statuses for a different organization's commits, bypassing required CI checks and enabling an unauthorized merge or deploy of that other repository — a cross-repository write / unauthorized-ship class impact.

### Likelihood Explanation
This requires a multi-organization Shipit deployment (documented as an explicitly supported configuration) where the attacker controls, or can cause, GitHub webhook deliveries from one of the configured organizations (e.g. they are an authorized GitHub App/repo admin in Org A but have no access to Org B). No `ApiClient` token, session, or GitHub write access to the target repository is needed — only the ability to produce one valid signature for the org whose secret they can compute, plus knowledge of a target commit sha (visible via the target's public GitHub page or PR).

### Recommendation
After signature verification, re-verify that every repository-scoped field referenced by a handler (`repository.full_name`, and any commit lookups) actually belongs to the same organization whose secret validated the signature — e.g., reject the webhook if `repository.full_name.split('/').first != repository_owner`, and scope `StatusHandler`'s `Commit` lookup by `stack.repository.owner` matching the verified organization instead of a bare, cross-tenant `Commit.where(sha:)`.

### Proof of Concept
1. Configure Shipit with two organizations, `org-a` and `org-b`, each with its own `webhook_secret` (per `docs/setup.md` multi-org setup).
2. As someone with the ability to trigger/replay webhook deliveries for `org-a` (e.g., an org-a app admin, or by knowing `org-a`'s `webhook_secret`), craft a `status` event body:
   ```json
   { "sha": "<sha-of-a-commit-in-org-b-repo>", "state": "success", "context": "ci/required",
     "repository": { "owner": { "login": "org-a" }, "full_name": "org-b/private-repo" } }
   ```
3. Sign the raw body with `org-a`'s `webhook_secret` and send it as `X-Hub-Signature`, `X-Github-Event: status`.
4. `verify_signature` resolves `repository_owner` = `"org-a"`, fetches `Shipit.github(organization: "org-a")`, and the signature validates successfully because it was computed with that org's real secret.
5. `StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`) matches `Commit.where(sha: params.sha)` with no organization scoping and creates a `success` `Status` on the `org-b` commit, which can satisfy `ci.require` checks and unblock merges/deploys for `org-b`'s stack despite the attacker never being authenticated for `org-b`.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
module Shipit
  module Webhooks

          accepts :context, String
          accepts :created_at, String

          accepts :branches, Array do
            requires :name, String
          end
        end

        def process
          Commit.where(sha: params.sha).each do |commit|
            commit.create_status_from_github!(params)
          end
        end
      end
```
