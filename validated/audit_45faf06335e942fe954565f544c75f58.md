### Title
Webhook signature verification keys on `repository.owner.login` while all handlers act on `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App/HMAC secret to validate an inbound webhook against using `repository.owner.login` (or `organization.login`), but every `Handler` subclass resolves the target `Repository`/`Stack` using a *different* field, `repository.full_name` [1](#0-0) [2](#0-1) [3](#0-2) . Because the HMAC only proves "this body was signed with the secret belonging to whichever org `repository.owner.login` names", and does not enforce that `repository.owner.login` and the owner segment of `repository.full_name` are the same string, an attacker who legitimately controls a GitHub organization/repository connected to this Shipit instance (and thus knows or can trigger genuine signed webhooks for *that* org) can craft a payload where `repository.owner.login` is their own org but `repository.full_name` names an entirely different, victim-owned repository tracked by Shipit.

### Finding Description
The trust binding that should hold is:
`organization whose secret authenticated the request == organization that owns the repository the handler mutates`

Before the attacker's request: a webhook for org A is HMAC-signed with A's `webhook_secret`, and `repository.full_name` in a legitimate GitHub payload always equals `A/<repo>`, so the binding holds implicitly because GitHub itself keeps the fields consistent.

`verify_signature` fetches the app config via `Shipit.github(organization: repository_owner)` and checks the signature against that org's `webhook_secret` [1](#0-0) . `repository_owner` is read straight from the JSON body: `params.dig('repository', 'owner', 'login')` [2](#0-1) .

Once verification passes, `WebhooksController#create` dispatches the *entire* parsed body to the registered handler(s) [4](#0-3) . Every handler resolves which `Stack`s to act on via `Handler#stacks`/`#repository_name`, which reads `payload.dig('repository', 'full_name')` and looks it up with `Repository.from_github_repo_name` [3](#0-2) [5](#0-4) . Nothing re-checks that `full_name`'s owner segment matches `repository.owner.login` used for signing.

Since the raw body is HMAC-signed as a whole, the attacker must be able to produce a valid signature — but they can do that for *any* body as long as they know the `webhook_secret` of the org named in `repository.owner.login`. An attacker who is an admin of their own GitHub org/repo that is connected to this Shipit instance knows (or can obtain, e.g. by re-configuring the webhook to a URL they control and reading the header) a valid `webhook_secret` for their own org. They can then submit a POST to `/webhooks` with:
- `repository.owner.login = "attacker-org"` (so `verify_signature` picks and validates against `attacker-org`'s secret, which they control)
- `repository.full_name = "victim-org/victim-repo"` (so the handler acts on the victim's tracked `Stack`)

After the attack: the request passes signature verification (bound to `attacker-org`) yet mutates state belonging to `victim-org/victim-repo`, i.e. the org that authenticated is not the repository that is written — precisely the class of binding violation the report highlights (interface/identity mismatch between what's checked and what's acted upon).

### Impact Explanation
This crosses a repository boundary without any GitHub-side authorization for the victim repo. Concretely:
- `PushHandler#process` finds the victim `Stack`s by `branch` and calls `stack.sync_github(expected_head_sha: params.after)` [6](#0-5) , letting the attacker force a resync against an arbitrary SHA on someone else's stack.
- `StatusHandler#process` looks up existing `Commit` rows by `sha` and calls `commit.create_status_from_github!(params)` with attacker-supplied `state`/`context`/`description` [7](#0-6) . Since deploys gate on required CI statuses (`ci.require` in `shipit.yml`), an attacker can forge a "success" status for a commit on the victim's tracked stack, potentially enabling an unauthorized deploy/merge decision that depends on that status, without ever touching the victim's real CI or repo.

This matches the required "cross-repository writes / unauthorized deploy" impact bar, because the write (Commit status, sync trigger) lands on a `Stack`/`Repository` the attacker was never authorized against, using credentials only valid for their own org.

### Likelihood Explanation
Requires the attacker to control at least one GitHub organization/repository that is itself connected to the same Shipit instance (has its own `webhook_secret` configured under `Shipit.github(organization: ...)`), which is a real but non-trivial precondition — it needs multi-tenant/multi-org configuration of the Shipit instance and the attacker being a legitimate (if low-privilege) tenant. Given that precondition, forging the payload is straightforward: no GitHub API access, no session, no `ApiClient` token is needed — only an HTTP POST to `/webhooks` with a body whose HMAC matches the attacker's own known secret.

### Recommendation
In `WebhooksController#verify_signature` (or in `Handler`), verify that `repository.owner.login`/`organization.login` used to select the signing secret matches the owner segment actually used to resolve the `Repository`/`Stack` (`repository.full_name`), and reject the webhook if they diverge.

### Proof of Concept
1. Attacker administers `attacker-org` on GitHub, connected to the shared Shipit instance, and knows `attacker-org`'s `webhook_secret` (e.g., because they configured it themselves via the GitHub App settings they control).
2. Attacker computes `signature = HMAC-SHA1(attacker_org_webhook_secret, body)` for a `push` event body where:
   ```json
   { "ref": "refs/heads/main", "after": "<attacker-chosen sha>",
     "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" } }
   ```
3. POST to `/webhooks` with `X-Github-Event: push` and `X-Hub-Signature: sha1=<signature>`.
4. `verify_signature` resolves `Shipit.github(organization: "attacker-org")` and successfully verifies the signature against the attacker's own secret [1](#0-0) .
5. `PushHandler` resolves stacks via `repository.full_name = "victim-org/victim-repo"` [3](#0-2)  and triggers `sync_github` on the victim's `Stack`, entirely outside of GitHub's authorization for that repo.
