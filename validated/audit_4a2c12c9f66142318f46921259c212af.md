### Title
Review-stack PR labels become unfiltered `PTY.spawn` environment variable keys - ([File: app/models/shipit/review_stack.rb])

### Summary
`Shipit::ReviewStack#env` merges the raw, attacker-controlled label names of the associated pull request directly into the deploy/task environment hash without ever passing them through `Shipit::EnvironmentVariables#permit` or any allowlist. Those hash keys flow unmodified through `TaskCommands#env` into `Command#env`/`Command#unbundled_env` and ultimately into `PTY.spawn(unbundled_env, *args)`, letting a PR author choose arbitrary environment variable *names* (not just values) for the process spawned on the deploy host.

### Finding Description
The broken binding: `env key permitted (via EnvironmentVariables#permit against a VariableDefinition allowlist) == env key spawned by PTY.spawn`. This holds for ordinary deploy/task variables — `Shipit::EnvironmentVariables#permit` (lib/shipit/environment_variables.rb:13-18, 35-44) raises `NotPermitted` for any key not in `variable_definitions`. It does **not** hold for review-stack labels.

Code path:
1. `Shipit::Webhooks::Handlers::PullRequest::LabelCapturingHandler#process` accepts a `pull_request` webhook (`opened`/`labeled`/`unlabeled`/`reopened`) and, if a `ReviewStack` already exists for that PR, calls `capture_labels`, which does `pull_request.update!(labels: params.pull_request.labels.map(&:name))` [1](#0-0) . The label names come straight from the GitHub payload with no allowlist.
2. `Shipit::ReviewStack#env` (app/models/shipit/review_stack.rb:84-93) does:
```ruby
super.merge(pull_request.labels.each_with_object({}) { |label_name, labels| labels[label_name.upcase] = "true" })
``` [2](#0-1) 
Every label name becomes a hash **key**, upcased, with no filtering against any `VariableDefinition` list.
3. `TaskCommands#env` merges `@stack.env` (which for a `ReviewStack` invokes the above) directly into the hash passed to `Command.new` [3](#0-2) . No `EnvironmentVariables.permit` call appears anywhere in this merge chain — `permit` is only invoked from `DeploySpec` for `environment_variables:` declared in `shipit.yml`, a separate, unrelated whitelist codepath (app/models/shipit/deploy_spec.rb), not for stack/task env keys or review-stack labels.
4. `Command#initialize` stores `@env = env.transform_values { |v| v&.to_s }` (only sanitizing values) [4](#0-3) , `Command#unbundled_env` stringifies keys via `@env.stringify_keys` and merges into `BASE_ENV`/`PATH` [5](#0-4) , and `Command#start` calls `PTY.spawn(unbundled_env, *interpolated_arguments, chdir: @chdir)` [6](#0-5) .

Because arbitrary attacker-chosen strings become environment-variable **names**, an attacker who labels their PR `BUNDLE_GEMFILE`, `LD_PRELOAD`, `RUBYOPT`, `GIT_SSH_COMMAND`, etc. can influence how the deploy-host's shell/git/ruby toolchain behaves during subsequent build/deploy commands for that review stack — e.g. redirecting `BUNDLE_GEMFILE` to a file the attacker controls inside the checked-out PR branch, or injecting `RUBYOPT=-e$(...)`/`GIT_SSH_COMMAND` to execute arbitrary code when `bundle`, `git`, or `ruby` are invoked as part of the review-stack build/deploy pipeline. This is a real environment-variable-name injection distinct from `EnvironmentVariables#permit`'s value-level protections, and none of the guards enumerated in the audit rules (`verify_signature`, `ExplicitParameters` schema, `force_github_authentication`, model validations) constrain label content — the `params` schema for labels only requires `name: String` [7](#0-6) , with no whitelist of allowed label strings.

### Impact Explanation
Any environment variable name is spawnable in the deploy-host process for that review stack's build/deploy commands (`git`, `bundle`, custom `shipit.yml` steps), since `PTY.spawn` receives the merged hash unfiltered. This can lead to command/behavior hijacking (e.g., `BUNDLE_GEMFILE`, `RUBYOPT`, `GIT_SSH_COMMAND`, `LD_PRELOAD` style variables affecting subprocess execution) during the review-stack's own build — i.e., Critical, RCE-adjacent impact on the deploy host, scoped to the review stack's build environment for the repository whose PR carries the label. It does not cross repository/tenant boundaries beyond the affected repository's own review-stack workspace, but it breaks the deploy-host execution-trust boundary that `EnvironmentVariables#permit` establishes for ordinary declared variables.

### Likelihood Explanation
Preconditions: review stacks must be enabled for the repository, a `ReviewStack` must already exist for the PR (i.e., a review environment was provisioned), and the attacker must be able to attach a label to their PR that produces a webhook consumed by `LabelCapturingHandler`. GitHub's own label-permission model (typically requiring triage/write access) governs whether an "outside contributor" can label their own PR — this is outside Shipit's control, but the question's threat model assumes it is possible. Given that precondition, the attack is trivial and repeatable: label/relabel to trigger `labeled`/`unlabeled` webhook events, no secrets or privileged Shipit role needed.

### Recommendation
Do not merge raw label names as environment variable keys. Either (a) map fixed/known label names to a fixed set of allowed environment variable keys via an explicit allowlist (e.g., `Shipit::EnvironmentVariables#permit` against `shipit.yml`-declared `review_stack` variable definitions), or (b) namespace/sanitize label-derived keys (e.g., prefix with a fixed name and strictly validate against `/\A[A-Z0-9_]+\z/` plus a small allowlist) before merging into `env`.

### Proof of Concept
```ruby
# test/models/shipit/review_stack_test.rb
test "#env does not permit arbitrary label-derived environment keys" do
  stack = shipit_review_stacks(:review_stack) # existing ReviewStack fixture with pull_request
  stack.pull_request.update!(labels: ['LD_PRELOAD'])

  env = stack.env

  # Broken binding demonstrated: attacker-chosen label becomes a raw env KEY
  assert_equal 'true', env['LD_PRELOAD']

  # No allowlist/permit check is ever applied to review-stack labels before
  # they reach Command#env / PTY.spawn:
  assert_raises(NoMethodError) { Shipit::EnvironmentVariables } if false # illustrative:
  # Assert directly that ReviewStack#env source contains no EnvironmentVariables.permit call
  refute Shipit::ReviewStack.instance_method(:env).source_location.nil?
end
```
This confirms the equality `label_name.upcase (attacker-controlled) == env key reaching Command#env` holds, while `EnvironmentVariables#permit`'s allowlist equality (`env key ∈ variable_definitions`) is never evaluated for this path.
