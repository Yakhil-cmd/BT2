### Title
ERC721 `transferFrom` used instead of `safeTransferFrom` in `handleERC721Transfer` permanently locks bridged NFTs in non-receiver contracts — (`contracts/service_chain/bridge/BridgeTransferERC721.sol`)

### Summary
`BridgeTransferERC721.handleERC721Transfer` uses `IERC721.transferFrom` to release NFTs to the destination recipient. Unlike `safeTransferFrom`, `transferFrom` does not invoke `onERC721Received` on the recipient. When the recipient is a contract that does not implement `IERC721Receiver`, the transfer succeeds without reverting, the NFT is permanently locked in that contract, and the bridge handle-nonce is consumed — making the loss irrecoverable.

### Finding Description
In `BridgeTransferERC721.handleERC721Transfer`, the bridge first commits all state changes (sets the handled request tx hash, updates the handle nonce, emits `HandleValueTransfer`) and then calls:

```solidity
// contracts/service_chain/bridge/BridgeTransferERC721.sol, line 69
IERC721(_tokenAddress).transferFrom(address(this), _to, _tokenId);
```

The OpenZeppelin `ERC721.transferFrom` implementation (used by all registered tokens) does **not** check whether `_to` is a contract capable of receiving ERC721 tokens:

```solidity
// contracts/libs/openzeppelin-contracts-v2/contracts/token/ERC721/ERC721.sol, lines 142-147
function transferFrom(address from, address to, uint256 tokenId) public {
    require(_isApprovedOrOwner(msg.sender, tokenId), "...");
    _transferFrom(from, to, tokenId);
}
```

`safeTransferFrom`, by contrast, calls `_checkOnERC721Received` and reverts if the recipient contract does not return the `IERC721Receiver` magic value. Because `transferFrom` is used, the call succeeds even when `_to` is a contract without `onERC721Received`, the NFT ownership is transferred to that contract, and the NFT becomes permanently inaccessible. The bridge has already incremented `lowerHandleNonce` and emitted the event, so there is no retry or recovery mechanism.

The same pattern appears in the deposit path:

```solidity
// contracts/service_chain/bridge/BridgeTransferERC721.sol, line 129
IERC721(_tokenAddress).transferFrom(msg.sender, address(this), _tokenId);
```

Here the bridge itself is the recipient and it does implement `onERC721Received`, so this direction is safe in practice — but it is still inconsistent with the ERC721 best practice of always using `safeTransferFrom`.

### Impact Explanation
When `handleERC721Transfer` is executed with a contract address as `_to` that does not implement `IERC721Receiver` (e.g., a multisig wallet, a DAO treasury, a DeFi protocol contract, or any arbitrary smart contract), the bridged NFT is permanently locked in that contract. The bridge handle-nonce is consumed and the `HandleValueTransfer` event is emitted, so the bridge considers the transfer complete. There is no on-chain mechanism to recover the NFT or re-execute the transfer to a different address. The bridged asset is effectively burned.

### Likelihood Explanation
Any user who initiates `requestERC721Transfer` on the source chain and specifies a contract address as `_to` that does not implement `IERC721Receiver` will trigger this condition. This is a realistic scenario: users commonly specify multisig wallets (Gnosis Safe), DAO contracts, or other smart contracts as recipients. The bridge operators faithfully relay the user-specified `_to` address to `handleERC721Transfer` with no validation. No special privileges are required — any unprivileged user can trigger the loss.

### Recommendation
Replace `transferFrom` with `safeTransferFrom` in `handleERC721Transfer`:

```solidity
// Before
IERC721(_tokenAddress).transferFrom(address(this), _to, _tokenId);

// After
IERC721(_tokenAddress).safeTransferFrom(address(this), _to, _tokenId);
```

This causes the call to revert if `_to` is a contract that cannot handle ERC721 tokens, preventing the bridge from consuming the handle-nonce and permanently losing the NFT. The bridge operator layer (`node/sc/bridge_manager.go`) already handles transaction errors and can retry or escalate accordingly.

### Proof of Concept

1. User on source chain calls `requestERC721Transfer(tokenAddr, contractWithNoReceiver, tokenId, "")` where `contractWithNoReceiver` is a deployed contract that does not implement `IERC721Receiver`.
2. Bridge operators observe the `RequestValueTransferEncoded` event and call `handleERC721Transfer` on the destination bridge with `_to = contractWithNoReceiver`.
3. Inside `handleERC721Transfer`:
   - Line 49: `_setHandledRequestTxHash(_requestTxHash)` — state committed.
   - Line 52: `_updateHandleNonce(_requestedNonce)` — nonce consumed.
   - Lines 54–64: `HandleValueTransfer` event emitted — bridge considers transfer done.
   - Line 69: `IERC721(_tokenAddress).transferFrom(address(this), contractWithNoReceiver, tokenId)` — succeeds without revert; NFT ownership transferred to `contractWithNoReceiver`.
4. `contractWithNoReceiver` holds the NFT but has no function to transfer it out. The NFT is permanently locked.
5. The bridge has no mechanism to re-execute the transfer or recover the NFT. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3)
