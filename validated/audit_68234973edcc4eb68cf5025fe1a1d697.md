### Title
Tokens sent directly to the `LiquidityPool` contract are permanently frozen — the pool has no recovery path for balance above its `cash` book - ([File: contracts/pool/src/lib.rs])

### Summary
The pool credits supply, repay, and recapitalize on the controller's word and tracks reserves in a `cash` bookkeeping variable. Any token balance above the per-market `cash` totals — a direct `token::transfer` to the pool address — belongs to no book and no entrypoint can move it: every mutating function is `#[only_owner]` (the controller), and neither the pool nor the controller exposes a sweep/rescue function. Stray tokens are unrecoverable even by governance, short of a contract upgrade.

### Finding Description
The pool's trust model states that "`supply`, `repay` and `recapitalize` all credit `cash` on the controller's word, without verifying the transfer" and that "the only reconciliation against a real `token.balance()` is in `flash_loan`, which checks it three times with strict equality" [1](#0-0) . Invariants confirm reserves are a pure book value: "Reserve checks use tracked market cash; token donations alone do not increase it" [2](#0-1) . A test pins the behavior: minting 1,000,000 extra units directly to the pool leaves `reserves` unchanged [3](#0-2) , and the money-flow audit test confirms a donation "belongs to no market's cash book" while remaining in pool custody [4](#0-3) .

Unlike the Nouns `Stream` — which at least had `rescueERC20` for non-payment tokens — the pool's full external surface is owner-only (`create_market`, `supply`, `borrow`, `withdraw`, `repay`, `net_settle`, `seize_positions`, `claim_revenue`, `recapitalize`, `flash_loan`, `create_strategy`, `update_indexes`, `update_params`, `upgrade`), and every outbound leg transfers only amounts booked against `cash` [5](#0-4) . The controller likewise refunds "only positive callback deltas of refund-listed tokens … Neither category sweeps prior balances" [6](#0-5) , so the controller cannot serve as a rescue path for pool-held tokens either. The pool's owner is the deployed controller with "no transfer, accept, or renounce on the ABI" [7](#0-6) , so there is no `sweep_balance`-style escape hatch anywhere in the custody chain — in contrast to the swap aggregator, which does expose `sweep_balance` for balances above its `ReservedTotal` [8](#0-7) .

This also has a non-self-inflicted variant the docs already acknowledge: Aquarius LP rewards accrue to the pool as holder and "any caller can push accrued rewards into the pool address as an unbooked donation," which then sit in custody permanently [9](#0-8) .

### Impact Explanation
Any tokens transferred directly to the pool — by accident, by a third party, or pushed by a venue reward claim — are permanently frozen. They inflate physical custody but can never be withdrawn, since every outbound transfer is bounded by the `cash`/`require_reserves` book and no entrypoint pays out unbooked balance. This is the same permanent-freeze impact class as the reference finding, and applies to every token in every hub sharing the pool's custody.

### Likelihood Explanation
Medium-low per incident but continuous exposure: any user error sending a listed token to the pool address, any venue pushing holder rewards (Aquarius reward claims need no pool authorization), or any airdrop to the pool address produces permanently stranded funds. It requires no privileged action and cannot be undone once executed.

### Recommendation
Add an owner-authorized skim, e.g. `fn skim(env, hub_asset, recipient)` on the pool that transfers `token.balance(pool) - total_booked_cash_for_asset` (summed across hubs sharing the token), callable by the owner — mirroring `sweep_balance`'s "balance minus reserved" pattern in the swap aggregator. Alternatively, route one through the controller so governance can recover stranded funds without a Wasm upgrade.

### Proof of Concept
1. `token.transfer(user, pool_addr, amount)` on any listed asset.
2. `get_reserves(hub_asset)` unchanged; `token.balance(pool) == cash_total + amount`.
3. No combination of `supply`, `withdraw`, `claim_revenue`, `recapitalize`, or `flash_loan` can emit the excess `amount` — all payouts are book-bounded and all pool entrypoints are `#[only_owner]` with no skim. The tokens are frozen permanently.

    /// Transfers each token's balance above its reserved fee total to `recipient`. Owner only.
    #[only_owner]
    fn sweep_balance(env: Env, recipient: Address, tokens: Vec<Address>) {
        renew_instance(&env);
        let router = env.current_contract_address();
        let n = tokens.len();
        for i in 0..n {
            // `i < n == tokens.len()`, so the index is in range by construction.
            let token = tokens.get_unchecked(i);
            let client = token::Client::new(&env, &token);
            let balance = client.balance(&router);
            let reserved = storage::reserved_fee_balance(&env, &token);
            if balance > reserved {
                client.transfer(&router, &recipient, &(balance - reserved));
            }
        }
    }
