### Title
CCMenuController#stack bypasses the ApiClient stack scope, allowing an out-of-scope stack's build status to be read - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Api::CCMenuController#stack` resolves `params[:stack_id]` via `Stack.from_param!`, which is unscoped, instead of the inherited `stacks.from_param!` pattern used by every other `BaseController` subclass, which scopes lookups to `current_api_client.stack_id`. This lets an `ApiClient` that is scoped to one stack (with only `read:stack` permission) fetch build status (`lastBuildStatus`, `lastBuildLabel`, `webUrl`, etc.) for any other stack in the system, because `require_permission!` only checks the literal `read:stack` string, never which stack.

### Finding Description
The intended binding is: for any `BaseController` action gated by `require_permission :operation, :stack`, the resolved `stack` must satisfy `stack ∈ stacks` where `stacks = current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all` [1](#0-0) . `require_permission!` itself only calls `current_api_client.check_permissions!(operation, scope)`, which checks the string `"#{operation}:#{scope}"` against the client's `permissions` array and is entirely independent of any specific record id [2](#0-1) [3](#0-2) .

Every other `BaseController` subclass correctly resolves `stack`/`task` through the scoped `stacks` relation (base `stack` method, or `stack.tasks`, `Hook.where(stack_id:)`, etc.) [4](#0-3) [5](#0-4) [6](#0-5) [7](#0-6) .

`CCMenuController`, however, overrides `stack` to use `Stack.from_param!(params[:stack_id])` directly — the unscoped `Stack` model, not the scoped `stacks` helper: [8](#0-7) 

`CCMenuController` requires only `read:stack` (`require_permission :read, :stack`) [9](#0-8) , and its `#show` action renders the stack's latest deploy status using this unscoped `stack` [10](#0-9) .

Exploit flow: attacker holds a valid `ApiClient` token whose `stack_id` is set to stack A and whose `permissions` includes `read:stack` (a legitimately provisioned client, e.g. for CI status polling of their own stack). `require_permission!` passes because the literal string `read:stack` is present in `permissions`, regardless of `stack_id`. The attacker then requests `GET /api/stacks/:stack_id/cc_menu.xml` with `stack_id` set to an arbitrary other stack B's param. `CCMenuController#stack` calls `Stack.from_param!(params[:stack_id])`, which resolves stack B without any scope check, and the action renders stack B's `lastBuildStatus`, `lastBuildLabel`, `webUrl`, lock state, etc. — data belonging to a repository/stack the attacker's client was never granted access to. The existing test suite even documents the `authenticate!` helper attaches a stack-scoped client (`here_come_the_walrus`) and asserts scoping behavior for `StacksController#index`, but there is no equivalent assertion for `CCMenuController`, confirming the scoping guard is present elsewhere but missing here.

### Impact Explanation
This is a scope-check bypass: an authenticated but stack-scoped `ApiClient` can read build/deploy status metadata (`lastBuildStatus`, `lastBuildLabel`, `webUrl`, lock state) belonging to any stack in the Shipit instance, not just the one it is authorized for. This matches the "High - unauthenticated [here, out-of-scope] read of stack state" category: it is a cross-tenant information disclosure — a client provisioned for repository/stack A learns build health and repo/branch/environment metadata about stack B belonging to a different repository or team. It is repeatable for any stack id and does not require privileged credentials beyond the attacker's own already-issued scoped API client token. It does not by itself achieve RCE, secret exfiltration, or an unauthorized deploy/lock/rollback (the CCMenu endpoint is read-only and does not expose `GITHUB_TOKEN`, `github_access_token`, or trigger any mutating action), so it does not reach the Critical bar described in the question, but it is a genuine, reachable violation of the exact binding the question describes.

### Likelihood Explanation
Preconditions: the attacker must already possess one legitimately-issued, stack-scoped `ApiClient` token with `read:stack` permission (a fairly common provisioning pattern for CI dashboards). No GitHub secrets, session, or operator privileges are required — only knowledge of another stack's `to_param` (typically `owner/repo/environment`, often guessable or discoverable via other read endpoints). Cost is a single HTTP GET with a different `stack_id` path parameter. Fully repeatable against arbitrary stacks.

### Recommendation
Change `Api::CCMenuController#stack` to reuse the scoped resolver from `BaseController` instead of overriding it with an unscoped lookup, e.g. remove the override so it inherits `stacks.from_param!(params[:stack_id])`, or explicitly define it as `stacks.from_param!(params[:stack_id])` to enforce `current_api_client.stack_id` scoping consistently with every other controller.

### Proof of Concept
Minitest plan (`test/controllers/api/ccmenu_controller_test.rb`):
1. Create two stacks, A and B, in different repositories.
2. Create an `ApiClient` scoped to stack A (`stack_id: stack_a.id`) with `permissions: ['read:stack']`.
3. Authenticate as that client and `GET :show, params: { stack_id: stack_b.to_param }`.
4. Assert the binding both sides:
   - Expected (per intended scope binding): `stack_b ∈ stacks_scoped_to(client)` should be `false` since `Stack.where(id: client.stack_id)` excludes stack B.
   - Actual (observed): response is `200 OK` and the XML payload's `name`/`lastBuildStatus` corresponds to stack B, proving `CCMenuController#show` served data for a stack outside the client's `stacks` scope.
5. Additionally assert that `Api::CCMenuController.new.send(:stack)` (or a static/reflective check across all `BaseController` subclasses) shows `CCMenuController#stack` is defined using `Stack.from_param!` rather than `stacks.from_param!`, distinguishing it from `BaseController#stack` and confirming it is the sole exception.
