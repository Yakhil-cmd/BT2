### Title
Cross-repository status webhook fires victim stack's `Hook`s via unscoped `Commit.where(sha:)` lookup - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`WebhooksController#verify_signature` selects the GitHub App/webhook secret to verify against based on `repository_owner` taken from the incoming payload, but `StatusHandler#process` then looks up commits by `Commit.where(sha: params.sha)` with no check that the matched commit's stack belongs to that same verified repository/org. Since `Commit#add_status` emits `Hook.emit(:commit_status, stack, ...)` / `Hook.emit(:deployable_status, stack, ...)` using `stack` from `belongs_to :stack` (the commit's real owning stack), a validly-signed webhook from one onboarded org can drive hook emissions (and status/state mutation) for a commit belonging to an entirely different, unrelated stack, as long as the two share a commit `sha`.

### Finding Description
The broken binding: `verified_org(payload.repository_owner) == owning_org(commit_matched_by(params.sha).stack)` is assumed but never enforced.

- `WebhooksController#verify_signature` computes `repository_owner` from `params.dig('repository','owner','login')` and validates the HMAC signature using `Shipit.github(organization: repository_owner)`'s configured `webhook_secret`. [2](#0-1) [3](#0-2) 
- Once verified, `WebhooksController#create` dispatches the *entire raw payload* to `StatusHandler.call`, without re-checking that `payload['repository']['full_name']` matches the commit(s) later acted upon. [4](#0-3) 
- `StatusHandler#process` ignores the `stacks` helper (which is scoped by `repository_name`, i.e. `payload.dig('repository','full_name')`, as defined in the base `Handler` class) and instead does a completely global `Commit.where(sha: params.sha)` lookup, then calls `commit.create_status_from_github!(params)` for every matching commit regardless of which repository/org it belongs to. [1](#0-0) [5](#0-4) 
- Contrast with `CheckSuiteHandler#process`, which correctly scopes via `stacks.where(branch: ...)` before touching commits — showing the repository-scoping pattern that `StatusHandler` fails to apply. [6](#0-5) 
- `Commit#create_status_from_github!` → `#add_status` operates on `self.stack` (the commit's real, persisted owning stack via `belongs_to :stack`), and unconditionally fires `Hook.emit(:commit_status, stack, ...)` and, on state transitions, `Hook.emit(:deployable_status, stack, ...)`, using whatever `Hook` records exist on that (potentially unrelated victim) stack. [7](#0-6) 

Exploit flow: an attacker who legitimately controls/owns a repository already onboarded to Shipit under some org (e.g., their own fork tracked as a Shipit stack, satisfying the "unprivileged GitHub user who can emit webhooks from a repository they own" bar) can trigger (or directly send, since the signature is verified per-org not per-repository-content) a `status` event payload whose top-level `repository.owner.login` matches their own org (so it passes `verify_signature` with their own configured/available webhook secret path) but whose `sha` field is set to a commit sha belonging to a victim stack in a completely different, unrelated repository/org. Because forked repositories retain identical commit shas for shared history, or because the attacker can freely choose the `sha` value in a payload they control the semantic content of once it flows to a legitimately signed request, the `Commit.where(sha:)` lookup in `StatusHandler` matches the victim's `Commit` row and mutates/re-fires its status, driving `Hook.emit` for the victim stack's configured hook URLs.

Why existing guards fail: `verify_signature` only asserts "the request's claimed owner org's secret matches the signature" — it says nothing about which specific commit/stack the payload's `sha` may target. `drop_unhandled_event`, `ExplicitParameters` schema (`requires :sha, String`), and model validations do not constrain `sha` to any repository. No `require_permission!`/`stacks`-scoped-lookup guard exists in `StatusHandler`, unlike `CheckSuiteHandler`.

### Impact Explanation
An attacker can cause `Hook.emit(:commit_status, victim_stack, payload)` and, depending on transition, `Hook.emit(:deployable_status, victim_stack, payload)` to fire for a stack they never authenticated against, leaking the fact/content of an attacker-forged status event to whatever external URLs the victim configured on their `Hook` records. Beyond the Hook-leak framed in this question, the same unscoped lookup also lets the attacker mutate the victim commit's `Status` records and influence `deployable?`/`schedule_merges` on the victim stack — a payload from one repository mutating another repository's stack/commit state, repeatable against any commit sha the attacker can guess or that is shared via forking, across arbitrary victim stacks tracked by the same Shipit instance. This matches "escalation... unauthenticated read of stack state" / cross-tenant mutation severity.

### Likelihood Explanation
Requires: (1) the attacker controls at least one repository already onboarded as a Shipit stack under an org configured in `Shipit.github(organization:)` (satisfying the "GitHub user who can emit webhooks from a repository they own" attacker model), enabling them to get a validly-signed `status` webhook delivered/replayed to `POST /webhooks`; (2) a target victim commit `sha` that exists in another tracked stack (trivial for forked repos sharing history, or discoverable via public commit history). No Shipit secrets, session, or API token are needed beyond what the attacker's own onboarded org naturally provides. This is repeatable per request and against arbitrary matching shas.

### Recommendation
In `StatusHandler#process`, scope the `Commit` lookup through the verified repository, e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` or `Commit.joins(:stack).merge(stacks).where(sha: params.sha)`, using the `stacks` helper from `Handler` (derived from `payload.dig('repository','full_name')`) so only commits belonging to stacks of the repository that was actually signature-verified can be updated.

### Proof of Concept
```ruby
# test/models/webhooks/status_handler_test.rb (conceptual)
test "status webhook cannot mutate/fire hooks for a commit belonging to an unrelated stack" do
  victim_stack = shipit_stacks(:shipit) # some victim org/repo
  attacker_stack = Shipit::Stack.create!(repository: shipit_repositories(:other_org_repo))

  victim_commit = victim_stack.commits.create!(sha: 'deadbeef' * 5, ...)
  victim_stack.hooks.create!(url: 'http://victim-endpoint', events: ['commit_status'])

  payload = {
    'sha' => victim_commit.sha,
    'state' => 'success',
    'repository' => { 'full_name' => attacker_stack.repository.full_name,
                       'owner' => { 'login' => attacker_stack.repository.owner } }
  }

  Shipit::Hook.expects(:emit).with(:commit_status, victim_stack, anything).never

  Shipit::Webhooks::Handlers::StatusHandler.call(payload)
end
```
This test demonstrates that `StatusHandler.call`, given a payload whose `repository` fields point to the attacker's own org/repo but whose `sha` matches a commit belonging to `victim_stack`, currently DOES invoke `Hook.emit(:commit_status, victim_stack, ...)` (the `.never` expectation fails), proving the cross-tenant hook firing described above.
