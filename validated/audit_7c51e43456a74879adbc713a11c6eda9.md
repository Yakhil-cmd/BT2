### Title
Webhook signature validated against `repository.owner.login` while handlers act on the unrelated `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App / HMAC secret used to authenticate an incoming webhook based on `repository.owner.login` (or the fallback `organization.login`), but every event handler subsequently resolves the actual `Repository`/`Stack` to mutate using the sibling field `repository.full_name` from the *same* JSON body. Nothing enforces that `full_name` is prefixed by `owner.login`. Because the two fields are read from attacker-controlled JSON rather than derived from one verified value, a party that legitimately controls the webhook secret for **one** organization configured in `Shipit.github` can forge a signed payload whose `owner.login` matches their own org (so signature verification passes) while `full_name` points at a completely different, unrelated repository/stack tracked by the same Shipit instance.

### Finding Description
`verify_signature` computes the trust anchor for the request from a payload field: [1](#0-0) [2](#0-1) 

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

The HMAC (`verify_webhook_signature`) only proves that *some* org's secret produced a valid signature over the raw body; it says nothing about which repository the body's other fields legitimately reference: [3](#0-2) 

Every handler that acts on the payload, however, resolves the target `Repository`/`Stack` from a *different* field in the same JSON object: [4](#0-3) 

```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
```

`PushHandler` (and the pull-request handlers) use this to locate and mutate stacks belonging to *any* repository tracked by the Shipit instance, regardless of which org's secret validated the request: [5](#0-4) [6](#0-5) [7](#0-6) 

The equality that should hold but does not is:

`repository.owner.login (used to select the verifying secret) == owner(repository.full_name) (used to select the acted-upon Repository/Stack)`

Because both values are pulled independently from attacker-supplied JSON and GitHub's own delivery mechanism is what normally keeps them consistent, an attacker who controls the webhook secret for their *own* configured organization (a legitimate, unprivileged tenant in a multi-org `Shipit.github` deployment, cf. `config/secrets.development.shopify.yml`) can post directly to `/webhooks` with a self-signed body claiming `owner.login: "their-org"` but `full_name: "victim-org/victim-repo"`.

### Impact Explanation
This crosses the "organization authenticated vs. repository that is written" boundary called out in scope. Concretely, with a validly self-signed payload an attacker in org A can:
- Force a `push` event to trigger `stack.sync_github` for any tracked stack belonging to org B, regardless of org A's own permissions.
- Drive pull-request handlers (`OpenedHandler`, `ClosedHandler`, `LabeledHandler`/`UnlabeledHandler`, `ReopenedHandler`) to archive, unarchive, or provision review stacks belonging to org B's repositories by supplying a `repository.full_name` for a victim repo alongside a self-signed `owner.login` for org A.
- Archiving/unarchiving/provisioning a review stack can enqueue provisioning, which ultimately schedules deploy-class tasks — i.e., the webhook endpoint can be used to remotely trigger unauthorized state changes/deploys on stacks the caller does not own, satisfying the "unauthorized deploy" criterion for this engine's threat model.

This is High severity: it lets one authenticated-but-unprivileged tenant escalate control over another tenant's stacks purely by exploiting the mismatch between the field used for signature-org selection and the field used for target-repository resolution — no GitHub write access, session, or `ApiClient` token to the victim's stack is required.

### Likelihood Explanation
Likelihood is Low-to-Medium: it requires the attacker to already possess a legitimate `webhook_secret` for at least one organization configured on the same multi-tenant Shipit instance (`Shipit.github(organization: ...)` implies multiple orgs can share one deployment, as shown by `config/secrets.development.shopify.yml`). This is realistic for SaaS/multi-tenant deployments of Shipit where each org's operator provisions their own GitHub App and therefore knows their own webhook secret, but is not exploitable by a fully external, uncredentialed attacker against a single-org Shipit install.

### Recommendation
- Do not use `repository.owner.login` merely as a lookup key with no further binding; after signature verification, cross-check that the `repository.full_name` referenced by the handler is actually owned by (has an owner prefix matching) the organization/app whose secret validated the signature.
- Alternatively, resolve the target `Repository` first, look up that repository's own organization/webhook configuration, and verify the signature specifically against that organization's secret — making the verification and the action operate on the same authenticated identity instead of two independently-controlled JSON fields.
- Reject webhooks where `repository.full_name`'s owner segment does not match `repository.owner.login`/`organization.login`.

### Proof of Concept
1. Shipit is configured with two organizations, `attacker-org` and `victim-org`, each with its own GitHub App and `webhook_secret` (per `config/secrets.development.shopify.yml`), both tracking stacks in the same Shipit instance.
2. The operator of `attacker-org` (who legitimately knows their own `webhook_secret` because they created their GitHub App) crafts a JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "deadbeef",
  "repository": {
    "full_name": "victim-org/victim-repo",
    "owner": { "login": "attacker-org" }
  }
}
```
3. They compute `X-Hub-Signature: sha1=<hmac-sha1(attacker-org secret, body)>` and POST it to `/webhooks` with `X-Github-Event: push`.
4. `verify_signature` calls `Shipit.github(organization: "attacker-org")` (from `repository.owner.login`), verifies successfully against the attacker's own secret.
5. `PushHandler#process` resolves `Repository.from_github_repo_name("victim-org/victim-repo")` and calls `stack.sync_github(expected_head_sha: "deadbeef")` on a stack the attacker does not own/control, despite the request only ever proving knowledge of `attacker-org`'s secret.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
