Found it: `Api::CcmenuController` overrides `stack` to bypass the scoping entirely.

The critical binding: `Api::BaseController#stack` scopes lookups through `stacks` (`current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all`), enforcing that a stack-scoped `ApiClient` (`stack_id` set, e.g. via `CCMenuUrlController#client`, created with only `read:stack` permission scoped to one stack) can only reach the one stack it was authorized for.

But `Api::CCMenuController` (`app/controllers/shipit/api/ccmenu_controller.rb:29-31`) redefines `stack` as `@stack ||= Stack.from_param!(params[:stack_id])` — bypassing `stacks` (and thus the `current_api_client.stack_id` restriction) entirely: [1](#0-0) [2](#0-1) 

### Title
Stack-scoped API token authorizes one stack but the CCMenu endpoint fetches any stack — (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Api::CcmenuController` authenticates with a token exactly like other API endpoints, but instead of resolving the target `Stack` through the `stacks` scope that enforces `current_api_client.stack_id`, it resolves the stack directly from the URL param via `Stack.from_param!(params[:stack_id])`. This breaks the equality that should hold between "the stack a token is authorized for" and "the stack the token can read," letting a stack-scoped, read-only CCMenu token read the build status of *any* stack, not just the one it was issued for.

### Finding Description
`ApiClient` supports being scoped to a single stack: `belongs_to :stack, optional: true` [3](#0-2) . This scoping is enforced centrally in `Api::BaseController#stacks`/`#stack`:
```ruby
def stacks
  @stacks ||= current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all
end

def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
``` [2](#0-1) 

Every other API controller (`DeploysController`, etc.) relies on this inherited `stack` method, so the token's `stack_id` binding is the equality that grants access: `token.stack_id == accessed_stack.id` (or the token is unscoped).

`Api::CcmenuController`, however, overrides `stack` locally:
```ruby
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end
``` [4](#0-3) 

This override completely discards the `stacks` scoping helper, so `current_api_client.stack_id` is never consulted when resolving `stack` — the `require_permission :read, :stack` check only verifies the client *has* the `read:stack` permission string, not that it's scoped to the requested stack [5](#0-4) . The route is `/stacks/*stack_id/ccmenu` [6](#0-5) , so `stack_id` is fully attacker-controlled.

This class of token is routinely created and handed out by the app itself: `CCMenuUrlController#client` creates a stack-scoped, `read:stack`-only `ApiClient` and embeds its `authentication_token` in a URL shown to any user with read access to that one stack [7](#0-6) . That URL/token is meant to be shared with third-party CI dashboard tools (CCMenu clients) for exactly one stack.

### Impact Explanation
An attacker who obtains a legitimately-issued, single-stack CCMenu token (e.g., a teammate pastes it into a public CI dashboard config, or it leaks via referrer/logs — a realistic exposure path for tokens embedded in unauthenticated GET query strings) can use it to read build/deploy status (`lastBuildStatus`, `activity`, `webUrl`, etc.) of *every* stack in the Shipit instance, including private/production stacks the token was never meant to access. This is an unauthenticated-read escalation beyond the token's authorized scope — the token authorizes read access to stack A, but it is usable against stack B, C, … reachable via `Stack.from_param!`.

### Likelihood Explanation
High likelihood: exploitation requires no privileges beyond possessing any valid CCMenu token (which the application itself is designed to hand out broadly and embed in plain URLs, per `CCMenuUrlController`). The bypass requires only changing the `stack_id` segment of the URL; `Stack.from_param!` does not re-check `current_api_client.stack_id`.

### Recommendation
Remove the local `stack` override in `Api::CcmenuController` and let it inherit `Api::BaseController#stack`, so the `stacks` scope (which enforces `current_api_client.stack_id`) is applied consistently. If the override exists to support the `token` query-param auth path, apply the scoping check separately, e.g.:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```

### Proof of Concept
1. As a user with access only to `stack-a`, visit its CI dashboard page to have Shipit auto-provision a CCMenu token: `GET /ccmenu/stack-a` → returns `ccmenu_url` containing `?token=<TOKEN_A>`, backed by an `ApiClient` with `stack_id = stack-a.id` and `permissions = ['read:stack']` [8](#0-7) .
2. Obtain `TOKEN_A` (it is designed to be embedded in a plaintext URL for third-party CCMenu clients, so leakage via shared dashboards/logs is expected).
3. Request a different, unauthorized stack's CCMenu feed using `TOKEN_A`:
   `GET /api/stacks/some-other-org/private-app/production/ccmenu?token=<TOKEN_A>`
4. `Api::CcmenuController#authenticate_api_client` authenticates `TOKEN_A` successfully (it's a valid, unrevoked token) [9](#0-8) . `require_permission :read, :stack` passes because `TOKEN_A` does have `read:stack` in its `permissions` list [10](#0-9) . `stack` resolves via the overridden method directly to `private-app/production`, bypassing the `stack_id` scoping check that would apply on every other API endpoint [11](#0-10) .
5. The response renders `private-app/production`'s build status/activity/last build label — data the token was never authorized to read.
