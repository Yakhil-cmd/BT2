### Title
Webhook signature is verified against the organization in `repository.owner.login`, but events are applied to the repository named in `repository.full_name` - allowing a trusted organization's webhook secret to forge events against any other org's stacks - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to verify the HMAC signature against using `repository_owner`, which is read from `params.dig('repository', 'owner', 'login')` (falling back to `params.dig('organization', 'login')`). Once the signature check passes, the entire raw JSON payload is forwarded unchanged to the registered `Shipit::Webhooks::Handlers` (`create` action calls `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`). Those handlers, however, resolve the *actual* repository/stack to mutate using a different field of the same payload: `payload.dig('repository', 'full_name')` (`Shipit::Webhooks::Handlers::Handler#repository_name`, used by `PushHandler`, `CheckSuiteHandler`, and others via `Repository.from_github_repo_name`).

Nothing ties `repository.owner.login` to `repository.full_name` before the trusted action is taken. The two values are independently attacker-controlled fields inside a single JSON body that only needs to carry a valid signature for whichever organization `repository.owner.login` names.

### Finding Description
- Signature verification binding: `verify_signature` in `app/controllers/shipit/webhooks_controller.rb` (lines 24-49) computes `repository_owner` from the payload and does `github_app = Shipit.github(organization: repository_owner)` then `github_app.verify_webhook_signature(...)`. This determines *whose secret* authorizes the request.
- Action-target binding: `Shipit::Webhooks::Handlers::Handler#repository_name` (`app/models/shipit/webhooks/handlers/handler.rb`, lines 36-38) does `payload.dig('repository', 'full_name')`, and `#stacks` resolves `Repository.from_github_repo_name(repository_name)&.stacks`. `PushHandler#process` (`app/models/shipit/webhooks/handlers/push_handler.rb`) calls `stack.sync_github(...)` on every matching stack; `CheckSuiteHandler#process` schedules check-run refreshes on the stacks it finds.
- These two lookups are logically supposed to represent "the same repository," but the controller never enforces that `repository.owner.login == repository.full_name.split('/').first`. Shipit is explicitly designed to support multiple organizations configured under `github:` in `secrets.yml` (see `test/dummy/config/secrets_double_github_app.yml`, `config/secrets.development.shopify.yml`), each with its own independent `webhook_secret`.
- Consequence: anyone who legitimately knows/controls one configured organization's `webhook_secret` (e.g., an org admin who set up their own GitHub App installation pointed at this shared Shipit instance) can craft a payload where `repository.owner.login` (or `organization.login`) names *their own* org (to pass signature verification) while `repository.full_name` names a *different, victim* organization's repository that is also registered in this Shipit instance. The signature check passes using the attacker's own org's secret, but the handler acts on the victim org's stack.

This breaks the required invariant "the organization that authenticated == the repository that is written," which is exactly the class of bug described in the source report (an entity used for authorization diverging from the entity actually acted upon).

### Impact Explanation
This allows cross-repository/cross-organization writes from a party who is authorized for only one org: an attacker can forge `push` events to make Shipit believe arbitrary commits/SHAs were pushed to a victim stack's tracked branch (`PushHandler` → `stack.sync_github(expected_head_sha: ...)`), and forge `check_suite` events to mark CI as complete for arbitrary commits (`CheckSuiteHandler`). On stacks with `continuous_deployment` enabled and CI requirements satisfied via forged/spoofed status/check-suite events, this chain can lead to an unauthorized deploy being triggered for a repository the attacker does not control - matching the "Critical: cross-repository writes / unauthorized deploy" impact bucket.

### Likelihood Explanation
Requires the attacker to be a legitimate, trusted operator of at least one organization configured in the same multi-tenant Shipit deployment (so they know that org's `webhook_secret`), which is the same "unprivileged relative to the victim, privileged only for their own domain" model used in the source report (an allowed user acting outside their authorized scope). No `ApiClient` token, GitHub App private key, or session compromise is required - only crafting a raw HTTP POST to `/webhooks` with a valid HMAC computed from their own org's secret over a payload that names a foreign repository.

### Recommendation
In `WebhooksController#verify_signature`, and/or in `Shipit::Webhooks::Handlers::Handler`, cross-validate that the organization used to select the verifying secret (`repository.owner.login` / `organization.login`) matches the owner segment of `repository.full_name` before dispatching to handlers. Reject (422) any payload where these two do not agree.

### Proof of Concept
1. Configure two organizations in `secrets.yml` under `github:`, e.g. `AttackerOrg` (attacker knows `webhook_secret`) and `VictimOrg` (has a tracked stack/repository in this Shipit instance).
2. Attacker crafts a JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha-already-existing-on-victim-remote-or-crafted>",
  "repository": {
    "owner": { "login": "AttackerOrg" },
    "full_name": "VictimOrg/victim-repo"
  }
}
```
3. Compute `X-Hub-Signature: sha1=<hmac-sha1(AttackerOrg_webhook_secret, body)>`.
4. `POST /webhooks` with header `X-Github-Event: push`.
5. `WebhooksController#verify_signature` resolves `repository_owner => "AttackerOrg"`, verifies signature successfully with `AttackerOrg`'s secret.
6. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("VictimOrg/victim-repo")` and calls `sync_github` on `VictimOrg`'s stack, using attacker-supplied `after` SHA - a cross-organization write the attacker was never authorized to perform.     def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e

        'Webhook from unknown organization',

        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
    end
  end
end

        params do
          requires :check_suite do

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
