### Title
Supply-position map TTL expiry makes all supply-reading account operations trap with an uncatchable `Error(Storage, MissingValue)` - ([File: contracts/controller/src/storage/account.rs])

### Summary
The NULL-pointer-dereference class maps onto Soroban as a missing/archived storage read that traps instead of returning `None`. The controller's `get_account_borrow_only` loads `AccountMeta` and `BorrowPositions` — renewing their user TTL via `get_user` — but deliberately skips `SupplyPositions`. `write_side_map` also explicitly never renews TTL on position-map writes ("position-map writes do not", line 2). So an account that only ever exercises the borrow-only path (`repay`) keeps its meta and debt alive while its `SupplyPositions` persistent entry lapses past `TTL_BUMP_USER`. From then on, every supply-reading entrypoint (`withdraw`, `borrow`, `liquidate`, `supply`, `update_account_threshold`, `multiply`, `flash_position`) traps with a host-level `Error(Storage, MissingValue)` — not a contract error — on `get_supply_positions` until someone submits a `restore_footprint` transaction for that key.

### Finding Description
- `get_account_borrow_only` intentionally leaves `supply_positions` as `Map::new`, so the `ControllerKey::SupplyPositions(account_id)` entry is never touched — and `get_user` only renews keys it actually reads (`contracts/controller/src/storage/protocol.rs:190-196`).
- `repay` is routed through this borrow-only load, so repeated repays renew `AccountMeta`, `BorrowPositions`, and `Delegates` but not `SupplyPositions`.
- `set_supply_positions`/`write_side_map` (lines 75-105) write with a plain `persistent.set` and no `extend_ttl`, so even genuine supply writes only reset the TTL from creation, never bump it.
- Once the supply map expires, `get_supply_positions` at line 63-68 calls `get_user` → `persistent().get` on the expired key. Soroban raises `Error(Storage, MissingValue)`, which is a host trap: it cannot be caught by `panic_with_error`/`assert_with_error` handling and reverts the entire transaction — the contract-side equivalent of the kernel's NULL deref panic. The error is also not one of the contract's typed errors, so `try_get_account`'s `Option` plumbing never gets a chance to return `None`.
- `renew_user_account`/`renew_account` cannot fix it either: it iterates the four keys and calls `renew_user_key` → `persistent().extend_ttl`, which itself panics on an expired entry before `has` filtering can help (and `has`/`extend_ttl` on expired persistent data also traps in Soroban).

### Impact Explanation
Temporary freezing of user funds and of liquidation capacity. All collateral-management operations on the affected account trap until a third party (or the owner) restores the `SupplyPositions` footprint with `restore_footprint`. For an unhealthy account this also blocks `liquidate` during the freeze window, letting bad debt accrue interest. Fits the "temporary freezing of funds" impact class; analogous to the CVE in that a state reachable through normal, unprivileged calls leads to a crash on access rather than a graceful error.

### Likelihood Explanation
Requires the supply map to go a full `TTL_BUMP_USER` window without a single supply-reading operation while borrow-only operations (`repay`) continue. Repay requires owner/delegate auth, so the pattern is realistic for a borrower steadily paying down debt without ever withdrawing, re-borrowing, or being liquidated — e.g., a leveraged `Multiply`/`Short` account serviced only by repays. On-chain this is a plausible multi-week liveness lapse rather than an exotic edge case, which keeps it at Medium rather than High: the freeze is self-healing once any keeper or user restores the archived entry, and no funds are stolen.

### Recommendation
Either renew `SupplyPositions` in `get_account_borrow_only` (cheap `persistent.has` + `renew_user_key`, same loop as `renew_user_account` at lines 259-272), or call `renew_user_account` from the `repay` entrypoint so all four per-account keys stay in lockstep. Alternatively, make `write_side_map` renew TTL on writes like `set_user` does.

### Proof of Concept
1. Open an account with collateral and debt via `supply` + `borrow` (or `multiply`/`flash_position`).
2. For longer than `TTL_THRESHOLD_USER`/`TTL_BUMP_USER` ledgers, call only `repay` (which loads via `get_account_borrow_only`) — meta and borrow entries renew, `SupplyPositions(id)` does not.
3. Call `withdraw` (or `borrow`, or have a third party call `liquidate`). `try_get_account` → `get_supply_positions` → `persistent().get(SupplyPositions(id))` traps with `Error(Storage, MissingValue)`; the transaction reverts and the position is frozen.
4. Recovery requires a `restore_footprint`/`restore` transaction on that key before any account operation succeeds.

Note: this assessment relies on the standard Soroban semantics that reads and `extend_ttl` on expired persistent entries raise a host `MissingValue` trap rather than returning `None`; if the deployment ledger version instead treats expired reads as absent, the trap path degrades to positions silently appearing empty, which is a different (also bad) outcome.
