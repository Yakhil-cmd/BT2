### Title
Unchecked interest-accrual arithmetic overflow permanently freezes oversized markets - (File: common/src/rates/index.rs)

### Summary
Interest accrual calculates total debt and supplied value as `scaled_shares * index` before applying the configured index ceiling. For a sufficiently large market, this intermediate value can exceed `i128` and panic with `MathOverflow`, after which every pool operation that loads the market repeats the same failing accrual. [1](#0-0) [2](#0-1) 

### Finding Description
All market mutations load a synced cache, meaning `interest::global_sync` executes before supply, borrow, withdrawal, repayment, liquidation, seizure, or explicit index updates. [3](#0-2)  `accrue_chunk` updates both indexes and protocol revenue through `accrue_step`, while `global_sync` only marks the market accrued after every chunk succeeds. [4](#0-3) [2](#0-1) 

Inside `calculate_supplier_rewards`, `borrowed.mul(old_borrow_index)` and `borrowed.mul(new_borrow_index)` are evaluated before their difference is taken. [1](#0-0)  The configured borrow-index ceiling only bounds `old_index.mul(interest_factor)`; it does not prevent `borrowed * index` from exceeding the representable value domain when `borrowed` is large. [5](#0-4)  `update_supply_index` similarly evaluates `supplied * old_index` before deriving the next supply index. [6](#0-5) 

An unprivileged user can create the prerequisite state through the controller’s normal `supply` and `borrow` flows: supply the target asset to create pool liquidity, supply collateral in another listed market, and borrow a large fraction of the target market. [7](#0-6)  Once later accrual pushes either valuation product past `i128::MAX`, the panic occurs before `mark_accrued`, so the stale timestamp causes the same overflowing calculation on every subsequent invocation. [4](#0-3) 

### Impact Explanation
The affected market can become permanently unusable: withdrawals, repayments, liquidations, bad-debt processing, recapitalization, and index updates all begin by loading an interest-synced market and therefore fail before reaching their own accounting logic. [3](#0-2) [8](#0-7) [9](#0-8)  This permanently freezes suppliers’ pool claims and prevents borrowers from repaying unless privileged intervention deploys corrected code. [10](#0-9) 

The repository contains a regression demonstrating this exact cliff: an 18-decimal market supplied with a one-billion-token principal and borrowed at 98% utilization eventually fails `update_indexes` with `MathOverflow`, and subsequent withdrawal and repayment attempts fail with the same error. [11](#0-10) 

### Likelihood Explanation
The issue is exploitable without privileged access whenever a listed market’s caps, liquidity, and collateral markets permit a sufficiently large scaled-debt or scaled-supply total to accrue toward the value-domain boundary. [12](#0-11)  The required market size is extreme and depends on an admitted high-decimal asset and sustained debt accrual, so this is less likely than an ordinary liquidation flaw, but the protocol explicitly allows scaled amounts whose future indexed values are not guaranteed to fit. [12](#0-11)  The result is a permanent loss of market availability rather than a transient rejected transaction, making the finding Medium severity. [13](#0-12) 

### Recommendation
Enforce an invariant that stored scaled totals can always be multiplied by the maximum supported index without overflowing, rather than relying only on initial token-domain caps. In particular, bound `supplied` and `borrowed` to approximately `i128::MAX / MAX_INDEX_MULTIPLIER`, apply the bound when minting supply shares, debt shares, and protocol-revenue shares, and derive `MAX_INDEX_MULTIPLIER` from `MAX_SUPPLY_INDEX_RAY / RAY` and `MAX_BORROW_INDEX_RAY / RAY`. [14](#0-13) [15](#0-14) 

Additionally, make accrual fail safely by computing old and new totals with explicitly widened arithmetic or by capping the index before evaluating unrepresentable totals; the ceiling should account for the current `borrowed` and `supplied` totals instead of only capping `old_index * interest_factor`. [5](#0-4) [16](#0-15) 

### Proof of Concept
1. In a market using an admitted 18-decimal asset, call controller `supply` with enough units to create approximately one billion whole tokens of liquidity.
2. Supply sufficient collateral in another listed market and call controller `borrow` for approximately 98% of the target asset’s liquidity.
3. Allow high-utilization interest to accrue and call controller `update_indexes` for the target `hub_asset`.
4. Accrual reaches `calculate_supplier_rewards`, where `borrowed.mul(new_borrow_index)` exceeds the value domain before the borrow-index ceiling can bound the result; the transaction panics with `MathOverflow`. [1](#0-0) 
5. Because `last_timestamp` is not marked accrued before all chunks complete, later calls repeat the same overflowing step, causing `update_indexes`, `withdraw`, and `repay` to keep failing. [4](#0-3) [13](#0-12)

/// Applies `interest_factor` to `old_index` to produce the new borrow index,
/// capped at `MAX_BORROW_INDEX_RAY`.
pub fn update_borrow_index(env: &Env, old_index: Ray, interest_factor: Ray) -> Ray {
    let new_index = old_index.mul(env, interest_factor);
    if new_index.raw() > MAX_BORROW_INDEX_RAY {
        return Ray::from(MAX_BORROW_INDEX_RAY);
    }
    new_index
}

/// Grows `old_index` by distributing `rewards_increase` over the total value
/// currently supplied (`supplied * old_index`). The division rounds down.
///
/// Returns `old_index` unchanged if `supplied` or `rewards_increase` is zero,
/// or if the total supplied value is zero. Clamps the result between
/// `old_index` (itself capped at `MAX_SUPPLY_INDEX_RAY`) and
/// `MAX_SUPPLY_INDEX_RAY`, so the returned index never decreases and never
/// exceeds the cap.
pub fn update_supply_index(env: &Env, supplied: Ray, old_index: Ray, rewards_increase: Ray) -> Ray {
    if supplied == Ray::ZERO || rewards_increase == Ray::ZERO {
        return old_index;
    }

    let total_supplied_value = supplied.mul(env, old_index);

    if total_supplied_value == Ray::ZERO {
        return old_index;
    }

    let new_value = total_supplied_value.checked_add(env, rewards_increase);
    let grown = fp_core::mul_div_floor_saturating(env, new_value.raw(), RAY, supplied.raw());

    let bounded_old = old_index.raw().min(MAX_SUPPLY_INDEX_RAY);
    Ray::from(grown.min(MAX_SUPPLY_INDEX_RAY).max(bounded_old))
}

    params: &MarketParams,

    new_borrow_index: Ray,

/// Converts a Ray-denominated `fee` into scaled supply-index shares
/// (`fee / supply_index`), floor-rounded and saturating on overflow. Caps the
/// result so that adding it to `supplied` cannot overflow `i128::MAX`.
pub fn protocol_fee_shares(env: &Env, fee: Ray, supply_index: Ray, supplied: Ray) -> Ray {
    let raw = fp_core::mul_div_floor_saturating(env, fee.raw(), RAY, supply_index.raw());

    let headroom = i128::MAX.saturating_sub(supplied.raw());
    Ray::from(raw.min(headroom))
}

pub(crate) fn global_sync(env: &Env, cache: &mut Cache) {
    if !cache.needs_accrual() {
        return;

    while let Some(nonzero) = NonZeroU64::new(remaining) {

        remaining = remaining.saturating_sub(chunk);

values and market totals must independently fit the RAY domain; valid caps and
bounded indexes do not guarantee that future accrual fits. Value overflow can
occur before the index ceiling and block repayment/withdrawal because those
operations accrue first. At the borrow-index ceiling, further accrual produces

//! [`super::fp`]: overflow-safe `x * y / d` with half-up, floor and ceiling
//! rounding, plus rescaling between decimal precisions.

//! Every multiply-divide first attempts the whole computation in `i128` and
//! only widens the operands to `I256` when the intermediate product does not
