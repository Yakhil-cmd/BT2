### Title
Webhook signature is verified against the payload's `repository.owner.login`, but the actual mutated resource is selected from the unrelated `repository.full_name` field, letting one onboarded organization's webhook secret authorize actions against another organization's stack - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/webhook secret to validate the `X-Hub-Signature` against using `repository_owner`, read from `params.dig('repository', 'owner', 'login')`. Once the signature check passes, the handler layer (`Shipit::Webhooks::Handlers::Handler#stacks`/`#repository_name`) resolves which `Repository`/`Stack` to act on using a *different* JSON field, `payload.dig('repository', 'full_name')`. Nothing enforces that these two fields refer to the same repository/organization, so a webhook that is validly signed for organization A can carry a `repository.full_name` pointing at organization B's repository, letting the sync/push machinery act on a stack the sender has no relationship to.

### Finding Description
The equality that should hold is:

`organization whose secret authenticated the request == organization that owns the repository being written to`

but the engine actually enforces:

`organization used to pick the HMAC secret (repository.owner.login) != organization/repo used to look up the Stack (repository.full_name)`

Concretely:
- `verify_signature` picks the app config via `Shipit.github(organization: repository_owner)` and calls `verify_webhook_signature(signature, raw_post)`, where `repository_owner` comes from `repository.owner.login` (or `organization.login`). [1](#0-0) 
- The signature is a valid HMAC over the raw body for whichever organization's secret matches - it says nothing about what `repository.full_name` is allowed to contain inside that same signed body.
- `PushHandler#process` resolves the stacks to mutate purely from `repository_name`, i.e. `payload.dig('repository', 'full_name')`, via the base `Handler#stacks`/`#repository_name` methods, then calls `stack.sync_github(expected_head_sha: params.after)` for every matching, non-archived stack on the branch. [2](#0-1) [3](#0-2) 

Shipit explicitly supports multiple GitHub organizations sharing one instance, each with its own `webhook_secret` under `config/secrets.yml`'s `github` map. [4](#0-3) 

Because the signature-selection field (`repository.owner.login`) and the resource-selection field (`repository.full_name`) are independent strings inside the attacker-fully-controlled JSON body, an entity that legitimately knows the webhook secret for Org A (e.g. because they administer the GitHub App installation for Org A and can view/rotate its webhook secret) can forge a `push` payload where:
- `repository.owner.login` = `"OrgA"` (so the correct secret is selected and HMAC verification succeeds)
- `repository.full_name` = `"OrgB/victim-repo"` (so the handler looks up and mutates Org B's `Stack`)

This breaks the deployment-trust binding described in the rules: "an organization that authenticated versus the repository that is written."

### Impact Explanation
Any stack belonging to `OrgB/victim-repo` (an organization the attacker has no GitHub relationship with, and for which Shipit never validated a signature) will have `stack.sync_github(expected_head_sha: <attacker-chosen sha>)` invoked. On a stack with `continuous_deployment: true`, forcing a sync can trigger the stack's deploy pipeline immediately (e.g. through `Stack.schedule_continuous_delivery`/`sync_github`-driven flows), effectively letting an outsider to Org B trigger an unscheduled/forced deploy path on Org B's stack, purely by controlling only a webhook secret that was legitimately issued to Org A. This is an unauthorized-action-on-another-repository impact that maps to the "unauthorized deploy" category, since none of Shipit's authorization/signature machinery for Org B's app was ever consulted.

### Likelihood Explanation
The prerequisite is possession of a valid `webhook_secret` for *any one* of the GitHub organizations configured in the shared Shipit instance's `config/secrets.yml`. In a single-organization deployment this analog collapses (there is only one secret, and it necessarily corresponds to the owner of every repository Shipit tracks). But in the officially documented multi-organization configuration, each org's administrators independently know/manage their own app's webhook secret, and the engine does nothing to bind that secret to the `full_name` in the payload. This is a design gap that manifests specifically because the same raw-body signature is checked using an org-selection field distinct from the resource-selection field used later - no code change in the host application ("mounting the engine as documented") is needed to expose it; it exists purely in `app/controllers/shipit/webhooks_controller.rb` and `app/models/shipit/webhooks/handlers/handler.rb`.

### Recommendation
After the signature is verified, additionally verify that `repository.full_name`'s owner segment matches the `repository_owner`/organization whose secret was used to authenticate the webhook (or, more robustly, look up the `Repository`/`Stack` scoped to that verified organization instead of trusting `full_name` independently). Reject the webhook if the two disagree.

### Proof of Concept
1. Configure Shipit (per `docs/setup.md`) with two organizations, `OrgA` and `OrgB`, each with its own GitHub App and `webhook_secret` in `config/secrets.yml`.
2. As an administrator of `OrgA`'s GitHub App installation, obtain `OrgA`'s `webhook_secret`.
3. Craft a `push` JSON payload:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker chosen sha that exists on OrgB/victim-repo>",
  "repository": {
    "owner": { "login": "OrgA" },
    "full_name": "OrgB/victim-repo"
  }
}
```
4. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(OrgA_webhook_secret, raw_body)>` and POST to `/webhooks` with `X-Github-Event: push`.
5. `WebhooksController#verify_signature` selects `Shipit.github(organization: "OrgA")` (from `repository.owner.login`) and successfully verifies the signature. [5](#0-4) 
6. `PushHandler#process` resolves `stacks` from `repository.full_name` = `"OrgB/victim-repo"`, finds the matching, non-archived `main`-branch stack belonging to `OrgB`, and invokes `stack.sync_github(expected_head_sha: <attacker-chosen sha>)`, despite the request never having been authenticated against `OrgB`'s webhook secret. [6](#0-5) [7](#0-6)

```ruby
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
```

```ruby
# frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
    end
  end
end
```
