### Title
Repository-unscoped `Commit.where(sha:)` lookup in `StatusHandler#process` lets a status webhook from any authenticated repository mutate commit status/deployability of an unrelated stack sharing the same SHA - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits by bare SHA across the entire `commits` table with no repository/stack scoping, unlike every other handler in this codebase which resolves handled stacks through `Repository.from_github_repo_name(repository_name)`. Any `status` event that authenticates for one repository (`repository.owner.login`) can therefore flip the CI status, and consequently `deployable?`/`blocked?`, of a `Commit` row belonging to a completely different stack, as long as both stacks happen to contain a commit row with the same SHA.

### Finding Description
The broken binding is: **the repository that authenticated the webhook (verified via `Shipit.github(organization: repository_owner)` in `WebhooksController#verify_signature`) MUST equal the repository/stack whose data is mutated by `handler.call(params)`.** For `StatusHandler` this equality does not hold.

Base class `Handler` (`app/models/shipit/webhooks/handlers/handler.rb`) defines a `stacks` helper that scopes to the caller's own repository: [1](#0-0) 
Most handlers (`pull_request/*_handler.rb` etc.) use this `stacks` scope. `StatusHandler`, however, bypasses it entirely: [2](#0-1) 

`Commit.where(sha: params.sha)` queries the global `commits` table with no `stack_id`/repository filter, so if any other stack (the "victim" stack) has a `Commit` row with the identical SHA — e.g., because it shares git history with the attacker's own repository (a fork, a common upstream, a cherry-picked/rebased commit, or simply a PR commit that also exists upstream before merge) — `commit.create_status_from_github!(params)` is invoked on that victim's `Commit`, writing a `Status` row to it: [3](#0-2) 

That write flows through `add_status`, which recomputes `status`, emits hooks, and — critically — calls `stack.schedule_merges` when the status becomes pending or successful, and affects `blocked?`/`deployable?` for any commit that references it via `blocking_statuses`: [4](#0-3) [5](#0-4) 

The attacker's exact request: an unprivileged GitHub user who owns/controls a repository with a valid GitHub App installation (satisfying `verify_webhook_signature` for *their own* `repository_owner`) sends a `status` webhook with `context: ci/kubernetes`, `state: failure`, and `sha` equal to a SHA that is also recorded as a `Commit` in the victim stack (`merge_queue_enabled: true`, requiring `ci/kubernetes`). `WebhooksController#verify_signature` only checks that the signature matches the GitHub App registered for `repository_owner` taken from the *attacker's own* payload — it never checks that the SHA/commit being modified actually belongs to that repository: [6](#0-5) 

Because `StatusHandler` does not use the `stacks`/`repository_name` scoping that every other handler relies on, the signature check's per-repository guarantee is silently discarded for this handler, and the `failure` status is applied to the victim's `Commit` regardless of which repository actually owns it. This directly marks the victim's commit as blocking/undeployable (or, with matching status polarity, unblocks/advances the merge queue via `schedule_merges`), affecting deploy/merge decisions for a stack the attacker never authenticated against.

### Impact Explanation
A record (`Status`) is written against a `Commit` belonging to a repository/stack that did not authenticate the request, directly changing `deployable?`/`blocked?` and triggering `stack.schedule_merges` for the merge queue. This is a payload for one repository mutating another's stack/commit state, matching the Critical category ("a payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy, rollback or merge"). It is repeatable against any victim stack whose commit history shares a SHA with a repository the attacker controls (forks, shared upstream commits, or commits from open PRs that exist in both trees before merge).

### Likelihood Explanation
Preconditions: victim stack has `merge_queue_enabled: true` and requires `ci/kubernetes`; attacker must control a GitHub repository with a legitimate app installation (any public GitHub user can create one) and must be able to produce/reference a commit SHA that is also present as a `Commit` row in the victim stack — realistically achievable via a fork sharing history with the upstream, or by referencing the SHA of an open pull request commit that Shipit has already ingested into the victim stack's `commits` table (Shipit records PR head commits before merge). No Shipit session, API token, or GitHub secret is required beyond the attacker's own repository's legitimate signature, which they can generate themselves. This makes the attack feasible and repeatable.

### Recommendation
Scope `StatusHandler#process` to the authenticating repository, mirroring other handlers: resolve the caller's stacks via `stacks` (i.e., `Repository.from_github_repo_name(repository_name)`), and restrict the `Commit` lookup to `Commit.where(sha: params.sha, stack_id: stacks.select(:id))` (or iterate `stacks.flat_map { |s| s.commits.where(sha: params.sha) }`) instead of the unscoped `Commit.where(sha: params.sha)`.

### Proof of Concept
minitest plan (no live GitHub, per rules):
1. Create two stacks `stack_a` (attacker-controlled repo, e.g. `attacker/repo`) and `stack_b` (victim, `merge_queue_enabled: true`, `Shipit.stack.something` configured to require `ci/kubernetes`).
2. Create `Commit` rows with the **same** `sha` value in both `stack_a` and `stack_b` (simulating shared git history).
3. Assert baseline binding: `stack_b_commit.blocked?` / `stack_b_commit.deployable?` reflects no `ci/kubernetes` status yet (e.g. `stack_b_commit.status.pending?` is true, `deployable?` is `false` due to pending or as configured).
4. Build a payload: `{ 'sha' => shared_sha, 'state' => 'failure', 'context' => 'ci/kubernetes', 'repository' => { 'full_name' => 'attacker/repo', 'owner' => { 'login' => 'attacker' } } }`.
5. Call `Shipit::Webhooks::Handlers::StatusHandler.call(payload)` directly (bypassing only the outer signature check, which is orthogonal to this bug since it only validates the attacker's own repo).
6. Assert `stack_b_commit.reload.status.failure?` is now `true` and `stack_b_commit.blocked?`/`deployable?` changed, while `stack_a_commit`'s equivalent state also updated — proving the write happened on `stack_b` despite the payload's `repository.full_name` being `attacker/repo`, i.e. the equality "authenticated repository == mutated stack" is violated.
7. Additionally assert `stack_b.reload` triggers `schedule_merges`/merge-queue-relevant callback (e.g. via mocking `Stack#schedule_merges` and asserting it was called for `stack_b` off of an `attacker/repo`-signed payload).

    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
