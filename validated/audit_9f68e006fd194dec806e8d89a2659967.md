### Title
Naive substring-based `---` delimiter split lets an embedded `---` inside a frontmatter value silently strip subsequent fields (including `action: block`) into the message body, downgrading a deny rule to a warn/no-op rule - (File: `plugins/hookify/core/config_loader.py`)

### Summary
`extract_frontmatter` locates the YAML frontmatter block using a raw string `content.split('---', 2)` instead of matching `---` only when it appears alone on its own line. If any frontmatter value (e.g. a `pattern` used to match dangerous commands) itself contains the literal substring `---`, that occurrence is misidentified as the closing delimiter, truncating the parsed frontmatter and pushing everything after it — including a subsequent `action: block` line — into the plain-text `message` body instead of the parsed dict. `Rule.from_dict` then falls back to the default `action = "warn"` [1](#0-0) , silently converting an intended blocking/deny rule into a non-blocking warn rule.

### Finding Description
`extract_frontmatter` splits the whole file content on the literal three-character sequence `---` with `maxsplit=2`: [2](#0-1) 

This is not YAML-delimiter-line-aware — it does not require `---` to appear alone on its own line (the standard YAML frontmatter convention, and what a real YAML parser or a `re.match(r'^---\s*$', line)` check would enforce). If a rule's own YAML content contains an embedded `---` substring inside a value — e.g. a `pattern` field designed to match a dangerous command flag or separator such as `pattern: "rm -rf --- force"` — that embedded occurrence is consumed as the *second* split token (the "closing" frontmatter delimiter) before the real closing `---` line is reached.

As a result:
- `parts[1]` (treated as `frontmatter_text`) is truncated mid-value, before later fields such as `action: block` are ever parsed.
- `parts[2]` (treated as `message`) now contains the rest of the intended frontmatter, including `action: block`, misinterpreted as literal markdown message text rather than YAML.

When `Rule.from_dict` builds the `Rule`, `frontmatter.get('action', 'warn')` finds no `action` key (since it was shifted into the message body) and defaults to `"warn"` [3](#0-2) . Downstream, `RuleEngine.evaluate_rules` only treats a rule as blocking when `rule.action == 'block'`; anything else falls into `warning_rules`, which only annotates a `systemMessage` and allows the tool call to proceed [4](#0-3) . Thus a rule author's (or an automated `/hookify`-generated) deny rule for a dangerous `Bash`/`Edit`/`Stop` action is silently converted into a rule that merely warns, and the dangerous tool call is executed. No further validation exists in `load_rule_file` to detect this corruption — it treats the truncated frontmatter as valid as long as it is non-empty [5](#0-4) .

### Impact Explanation
This breaks the stated invariant that "a deny rule must never be parsed into a non-blocking configuration." A `.claude/hookify.*.local.md` rule intended to hard-block a dangerous `Bash`, `Edit`, or `Stop` action (e.g., blocking `rm -rf`, blocking edits to secrets, blocking risky stop reasons) can be silently reduced to advisory-only if its own matching pattern happens to contain `---`, or if such content is crafted/suggested via the `/hookify` flow. Since `hookify` hooks (`pretooluse.py`, `posttooluse.py`, `stop.py`) are the only enforcement mechanism gating those tool calls in this plugin, the practical effect is a security-control bypass: dangerous commands proceed with only a warning message instead of being denied.

### Likelihood Explanation
The trigger condition is simple and only requires the rule's own frontmatter content to contain the three-character substring `---` anywhere before the intended closing delimiter — this can happen incidentally (patterns targeting flags like `--force`, `---`, YAML block scalars, or markdown horizontal rules used as example text) or be deliberately engineered by whoever authors/generates the `.claude/hookify.*.local.md` file (including content produced through the `/hookify` command flow, e.g. from pasted/suggested rule text). No privileged access is needed beyond the ability to place or edit a `hookify.*.local.md` file, which is exactly the file `/hookify` is designed to create/edit.

### Recommendation
Replace the substring-based split with a line-anchored delimiter check, e.g. only treat a line as a frontmatter delimiter when `re.match(r'^---\s*$', line)` on its own line, similar to how standard front-matter/YAML parsers (and most static site generators) delimit blocks. Additionally, after parsing, validate that `action` (and other critical fields) is explicitly present when expected, and fail closed (reject the rule file, or default unspecified/ambiguous `action` values to `block` rather than `warn`) rather than silently defaulting to the least restrictive behavior when frontmatter parsing is ambiguous or fails to find expected keys.

### Proof of Concept
Unit test to add to a test suite for `config_loader.py`:

```python
def test_embedded_triple_dash_downgrades_block_rule():
    content = '''---
name: block-rm
enabled: true
event: bash
tool_matcher: Bash
conditions:
  - field: command
    operator: regex_match
    pattern: "rm -rf --- force"
action: block
---

This command is forbidden.
'''
    frontmatter, message = extract_frontmatter(content)
    rule = Rule.from_dict(frontmatter, message)

    # Invariant: an author-specified "action: block" line in the file
    # must never be parsed as a non-blocking rule.
    assert rule.action == "block", (
        f"Expected block rule but got action={rule.action!r}; "
        f"'action: block' was corrupted into message body: {message!r}"
    )
```

Expected/actual: the assertion fails — `rule.action` resolves to `"warn"` (the default), while `message` will contain the literal text `force"\naction: block\n---\n\nThis command is forbidden.`, proving that the `action: block` directive was misparsed into the message body rather than the frontmatter dict. This can be confirmed end-to-end by placing the crafted file at `.claude/hookify.bash.local.md` in a cloned repo, invoking `plugins/hookify/hooks/pretooluse.py` with a `Bash` `tool_input.command` of `rm -rf / --- force`, and observing that the hook returns a `systemMessage`-only warning response (`RuleEngine.evaluate_rules` warning branch) instead of `hookSpecificOutput.permissionDecision == "deny"`.

def load_rule_file(file_path: str) -> Optional[Rule]:
    """Load a single rule file.

    Returns:
        Rule object or None if file is invalid.
    """
    try:
        with open(file_path, 'r') as f:
            content = f.read()

        frontmatter, message = extract_frontmatter(content)

        if not frontmatter:
            print(f"Warning: {file_path} missing YAML frontmatter (must start with ---)", file=sys.stderr)
            return None

        rule = Rule.from_dict(frontmatter, message)
        return rule
