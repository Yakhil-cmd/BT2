### Title
Unprivileged dust top-up force-restamps a victim's cached risk parameters, blocking borrow/withdraw and potentially enabling liquidation — (File: contracts/controller/src/positions/supply.rs)

### Summary
The MySQL/InnoDB CVE is a low-privilege, network-reachable denial of service. The analog in XOXNO Lending: any unprivileged address can call `controller::supply` with a dust amount on a hub asset a victim account already holds. Per INV-AUTH-03 a third-party top-up cannot open a new slot, but it is allowed to grow an existing supply leg — and that path restamps the position's cached `loan_to_value` to the *currently listed* config, bypassing the health-factor floor that protects the equivalent `update_account_threshold` maintenance path. The test `poc_third_party_top_up_force_restamps_ltv` demonstrates the primitive end-to-end: after a governance listing change lowers `loan_to_value`/`liquidation_threshold`, a 1-unit third-party `supply` restamps the victim's LTV, and the victim's subsequent `borrow` reverts with `InsufficientCollateral`. [1](#0-0) 

### Finding Description
`supply(caller, account_id, spoke_id, assets)` accepts a caller that is neither owner nor delegate when every `HubAssetKey` in `assets` is already a supply position of `account_id` (README: "a third-party `supply` may only top up hub assets the account already holds"). The deposit writes fresh risk parameters from the current spoke listing into the account's cached position snapshot (`loan_to_value`, and per the position struct the same record carries `liquidation_threshold`, `liquidation_bonus`, `liquidation_fees`). [2](#0-1) [3](#0-2) 

This skips the guard on the designated maintenance path: `update_account_threshold(caller, has_risks, account_ids)` reverts the whole batch unless each account clears a post-update health-factor floor (~1.05), specifically so cached risk parameters cannot be used to push an account into liquidation. [4](#0-3) [5](#0-4) 

The dust top-up therefore reaches the same restamp with no solvency check, for the cost of one token base unit.

### Impact Explanation
- **Denial of service (the CVE class):** after any listing change that lowers LTV, an attacker dusts the victim's existing leg, restamps it, and the victim's `borrow` reverts (`InsufficientCollateral` in the PoC). The same cache feeds `withdraw`'s post-operation solvency check, so exits that were previously safe can also revert — temporary freezing of funds until governance parameters move back or the victim repays. [6](#0-5) 
- **Escalation to liquidation:** the position record restamped here also stores `liquidation_threshold`, which `calculate_account_risk_totals` reads to compute the health factor. If the restamp lowers a cached LT (e.g., a listing edit reduced the threshold while the victim's snapshot still held the old, higher value), a single dust top-up can push `HF < 1` without the `update_account_threshold` HF floor ever running, exposing the account to a pro-rata seizure at bonus — theft of the liquidation bonus from the user. [7](#0-6) 

I could not fully verify whether the top-up restamp writes `liquidation_threshold` in addition to `loan_to_value` (the test asserts only the LTV leg); if it does not, the confirmed impact is the DoS leg only. Either way the accepted-impact bar (temporary freezing of funds) is met.

### Likelihood Explanation
Medium. Requirements: (a) governance edits a listing so listed LTV/LT differ from values already cached on victim positions — a normal operation since `update_account_threshold` exists precisely to converge stale snapshots; (b) the victim already holds a supply position in that hub asset, which is true for any supplier. The attack costs one base unit of the asset per leg and requires no privileges, no oracle manipulation, and no flash path. The HF-floor check on `update_account_threshold` shows the designers considered forced restamping dangerous; the supply path is an unguarded equivalent.

### Recommendation
On the third-party top-up branch of `supply` (caller is neither owner nor active delegate), either preserve the position's existing cached risk parameters instead of restamping, or apply the same post-update health-factor floor used by `update_account_threshold` in `contracts/controller/src/risk/params.rs`. Reuse `FreezePolicy`/risk-validation helpers already applied to owner deposits so the permissionless top-up cannot tighten a victim's risk snapshot.

### Proof of Concept
Modeled on `poc_third_party_top_up_force_restamps_ltv`:

```text
1. Victim supplies USDC (LTV 8000 / LT 8500 listed); snapshot caches those values.
2. Governance lists USDC at LTV 5000 / LT 5500 (or any lower set).
3. Attacker calls controller::supply { caller: attacker, account_id: victim,
   spoke_id, assets: [(HubAssetKey{hub_id, USDC}, 1)] }.
   -> Allowed (existing leg); victim's cached LTV restamps to 5000.
4. victim.borrow(... ) that was valid at the old snapshot now reverts
   InsufficientCollateral; withdraw legs that breach the new LTV-weighted
   solvency likewise revert.
5. If liquidation_threshold is restamped as well and drops the account's
   weighted threshold below debt, is_liquidatable(victim) becomes true and any
   liquidator seizes collateral pro-rata at bonus via
   liquidate(liquidator, victim, payments, SeizeMode::Transfer) — with no
   HF-floor check having ever run on the restamp.
```

Reference: `tests/test-harness/tests/controller/security_audit.rs` `poc_third_party_top_up_force_restamps_ltv` (steps 1–4 confirmed by the test; step 5 depends on whether `liquidation_threshold` is included in the same restamp, which I could not confirm from the indexed source).

```rust
#[test]
fn poc_third_party_top_up_force_restamps_ltv() {
    let mut t = LendingTest::new().standard_two_asset_dust_disabled();

    t.supply(ALICE, "USDC", 10_000.0);
    let id = t.resolve_account_id(ALICE);

    t.edit_asset_config("USDC", |c| {
        c.loan_to_value = 5_000;
        c.liquidation_threshold = 5_500;
    });

    t.try_supply_to_account(BOB, ALICE, "USDC", 1.0)
        .expect("third-party top-up of existing leg allowed");
    let (ltv, _) = supply_ltv_and_lt(&t, id, "USDC");
    assert_eq!(
        ltv, 5_000,
        "H-RISK-03: third-party top-up force-restamps LTV"
    );

    let blocked = t.try_borrow(ALICE, "ETH", 3.5);
    assert_contract_error(blocked, errors::INSUFFICIENT_COLLATERAL);

    t.borrow(ALICE, "ETH", 2.0);
    t.assert_healthy(ALICE);
}
```
