**Analysis:** The Fiat-Shamir transcript in `compute_r_powers_for_verify_kzg_proof_batch` [1](#0-0)  hashes the domain separator, degree, count `n`, and then *every* commitment, `z`, `y`, and proof for all `n` entries into a single SHA256 digest before deriving `r` via `hash_to_bls_field`, and only afterward computes `r_powers_out` with `compute_powers`. This means `r` is a function of the entire batch — including item 1's forged commitment/proof — so the attacker cannot choose item 1's bytes after learning `r`; any change to any byte in the batch (including a "fixed" forged proof) changes `r` deterministically via the pre-image-resistant hash.

All inputs are validated before entering the transcript: `bytes_to_kzg_commitment` and `bytes_to_kzg_proof` perform subgroup/curve validation (`validate_kzg_g1`) and `bytes_to_bls_field` enforces canonical field elements, all called in `verify_blob_kzg_proof_batch` prior to `verify_kzg_proof_batch` [2](#0-1) . The final check is a single pairing equation combining all `n` entries weighted by `r^i`, requiring the discrete-log/pairing assumption to break for any forged item to slip through undetected [3](#0-2) .

This is the standard, sound batch-KZG-with-random-linear-combination construction: since `r` is derived from a hash of the *entire* batch (all commitments, z's, y's, proofs) before the pairing check is performed, and the pairing check is a single combined equation, there is no window in which an attacker learns `r` and then retroactively forges proof/commitment data to pass. No code path allows computing `r` first and then supplying attacker-chosen proofs afterward — the hash and the verification happen atomically within `verify_kzg_proof_batch` using the same in-memory arrays. The `n==0` and `n==1` short-circuits [4](#0-3)  don't affect this since the 2-item scenario goes through the general batch path.
