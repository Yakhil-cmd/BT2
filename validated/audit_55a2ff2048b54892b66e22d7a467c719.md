Based on my investigation, I found a genuinely analogous precision-loss pattern in the TPS fee accounting logic that is directly reachable by an unprivileged unit poster and enforced deterministically at unit-validation time by every node.

### Title
Precision loss in TPS fee balance accounting (`tps_fees_balance / share`) allows the last recipient in a multi-author unit to be systematically underpaid / systematically evade the minimum fee floor - ([File: storage.js, validation.js])

### Summary
`updateTpsFees` in `storage.js` truncates each recipient's earned share of the tps-fee surplus/deficit with `Math.floor(total_tps_fees_delta * share / 100)` and stores it per address in `tps_fees_balances`. Later, `getPaidTpsFee` and `validateTpsFee` recover an "effective" full-unit fee for that recipient by doing the **inverse operation independently**: `tps_fees_balance / share` — instead of re-deriving it consistently from the same rounding basis used at write time. Because the write path truncates towards zero for each recipient separately (rather than as one atomic computation later divided back out), and the read path performs an un-cancelled division, the recovered `tps_fee` can silently drift below the true value, in the same way `WIchiFarm`'s `enIchi`/`stIchi` drift apart because they are computed by two independent multiply-then-divide operations rather than as one cancelling expression.

### Finding Description
In `storage.js`, `updateTpsFees` computes, for each recipient address of a unit's earned-headers-commission split: [1](#0-0) 
`total_tps_fees_delta * share / 100` is floored per-address, so any fractional remainder for that address's share is discarded and never carried anywhere (unlike an accumulator pattern that would track leftover remainders). Each address's `tps_fees_balance` therefore represents `floor(delta * share/100)` summed over mci's — a value that is *not* the exact `share` fraction of the true delta.

Later, both `getPaidTpsFee` (used by `parent_composer.js` to filter candidate parents for tps-fee sufficiency) and `validateTpsFee` (used by every node to accept/reject a newly posted unit) recover the "reconstructed" full unit-equivalent fee by doing the reverse division: [2](#0-1) [3](#0-2) 

Because `share` for multi-author units is only a fraction like `p/100` (not necessarily a divisor of 100 that keeps things integral), `tps_fees_balance / share` does not invert `floor(total_tps_fees_delta * share/100)` exactly — it introduces a rounding error whose magnitude scales with `1/share`. For an address with a small `share` (e.g., 1%), each unit of truncation at write-time (`floor` can discard up to `0.99` of a fee unit) is amplified by `100x` on the read side (`/0.01`), producing potentially large swings in the reconstructed `tps_fee` estimate used to decide whether the unit satisfies the tps-fee minimum.

This mirrors exactly the `WIchiFarm` bug class: instead of tracking one canonical, cancelling quantity, the protocol independently rounds/truncates a per-share value on write and un-rounds it on read, and the two operations do not invert each other.

### Impact Explanation
`validateTpsFee` is run by every full node for every unit created after `constants.v4UpgradeMci`, and it directly gates whether a posted unit is accepted into the DAG: [4](#0-3) 
A multi-authored unit (author addresses acting as tps-fee recipients with unequal, especially small, `earned_headers_commission_share` splits) can exploit the truncation asymmetry to make the reconstructed `tps_fee` for a small-share address appear inflated or deflated relative to the true value, potentially allowing units that underpay the true required tps fee to pass validation (or conversely causing correctly-paying units to be wrongly rejected as underpaying, a network-availability/fairness problem). This is a core-protocol economic-accounting flaw reachable purely by constructing a unit with an `earned_headers_commission_recipients` split, not requiring any privileged access.

### Likelihood Explanation
Any user composing a multi-authored unit chooses the `earned_headers_commission_share` split (validated only to sum to 100, per `validateHeadersCommissionRecipients` in `validation.js`), so an attacker fully controls the `share` values feeding this arithmetic. Since the amplification factor is `1/share`, an attacker who intentionally uses very small shares (e.g., 1%) for some addresses can maximize the reconstruction error deterministically and repeatedly, making exploitation straightforward and repeatable across many units over time to accumulate drift in `tps_fees_balances`.

### Recommendation
Avoid reconstructing a full-unit-equivalent fee via `balance / share`. Instead:
- Store and compare tps-fee sufficiency using the same rounding basis on both write and read (e.g., always compare `tps_fees_balance` against `floor(required_fee * share / 100)`, never re-inflate by dividing).
- Or track exact fractional remainders (numerator/denominator, similar to `divCeil`-style bookkeeping) instead of flooring silently, ensuring the sum of per-address floors plus tracked remainder equals the original total delta, and use ceiling rather than floor consistently to bias in favor of the protocol/network rather than the unit author when comparing against the minimum acceptable fee.

### Proof of Concept
1. Construct a 2-author unit with `earned_headers_commission_recipients` split as `{addrA: 99, addrB: 1}`.
2. Over several mci's, `updateTpsFees` accumulates `floor(total_tps_fees_delta * 1/100)` into `addrB`'s `tps_fees_balances`, discarding up to `0.99` of a fee unit each time it truncates — this remainder is never recovered anywhere [1](#0-0) .
3. When composing/validating a new unit, `tps_fees_balance / share` for `addrB` divides the already-truncated balance by `0.01`, amplifying the missing fractional remainder by 100x when compared against `min_tps_fee` [5](#0-4) .
4. By choosing the split to maximize this amplification, an attacker can cause the computed `tps_fee` to diverge meaningfully from the true value used to decide if the unit is validly paying its required tps fee, without any special privileges beyond posting a normal multi-authored unit.
