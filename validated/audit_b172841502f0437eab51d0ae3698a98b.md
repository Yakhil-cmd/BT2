### Title
Cross-repository status forgery via SHA-scoped (not repository-scoped) webhook status handler - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`Shipit::Webhooks::StatusHandler` applies a signed GitHub `status` webhook event to **every** `Commit` row in the database whose `sha` matches the payload, regardless of which repository/organization the webhook was authenticated for. The webhook signature only proves the payload originated from the GitHub App/organization tied to `repository.owner.login`, but the handler never re-checks that the target commit actually belongs to a stack under that same repository/organization.

### Finding Description
`WebhooksController#verify_signature` resolves the signing secret using the org named in the unvalidated JSON body and verifies the HMAC of the whole raw payload against that org's `webhook_secret`: [1](#0-0) [1](#0-0) 

That only proves "this payload was signed by the GitHub App configured for organization X" — it says nothing about which specific repository's commit the payload is entitled to affect. The `status` handler then does: [2](#0-1) 

`Commit.where(sha: params.sha)` is a **global, unscoped** query across all stacks/repositories tracked by the Shipit instance, and `commit.create_status_from_github!(params)` writes the forwarded state/description/context directly into that commit's status history: [3](#0-2) 

By contrast, every other handler in the codebase scopes commits/pull-requests to the specific `repository.full_name` from the payload via `Handler#stacks`: [4](#0-3) 

`StatusHandler` skips this scoping entirely. Because git commit SHAs are content-addressed and identical between a fork and its upstream (or between any two repos that share history — e.g. a mirrored/forked repository also onboarded as a separate Shipit stack), an attacker who administers a webhook on **any** repository the Shipit instance is configured to trust (i.e., can get GitHub to deliver — or, since the secret is the shared org-level value, can self-construct — a validly-signed `status` event for their own, less-privileged repo) can supply a `sha` that also exists as a commit in a different, more sensitive stack, and inject an arbitrary CI `state`/`description`/`context` for that unrelated stack's commit.

This breaks the binding: **organization/repository the webhook signature authenticates == repository whose commit status is written**. The signature authenticates "org A said this", but the write lands on any commit anywhere in the instance whose SHA happens to match, including stacks belonging to org B.

### Impact Explanation
Commit status directly gates deployability and continuous delivery: `Commit#deployable?` requires `success?` (derived from `statuses`) and continuous deployment is scheduled off status changes: [5](#0-4) [6](#0-5) 

Forging a `success` status on a shared commit in a stack the attacker does not control can make an otherwise CI-blocked commit appear deployable and, on stacks with `continuous_deployment: true`, trigger an actual deploy of that commit — an unauthorized deploy driven entirely by a signature-valid webhook the attacker was only entitled to send for a different (their own) repository.

### Likelihood Explanation
Requires: (a) the attacker to already have the ability to get a validly-signed `status` webhook delivered to the Shipit endpoint for some org/repo they legitimately administer (a normal, low-privilege capability — anyone who can configure a GitHub webhook on any repo already onboarded into Shipit), and (b) a colliding SHA between their repo and a victim stack, which is common for forks, mirrors, or monorepos split into multiple Shipit stacks that share commit history. No GitHub App private key, `ApiClient` token, or Shipit session is needed — only the ability to trigger one legitimately-signed webhook.

### Recommendation
Scope `StatusHandler#process` (and any other handler that queries `Commit`/`Stack` by content rather than by `repository.full_name`) to `stacks` derived from the authenticated `repository.full_name`, e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` instead of the global `Commit.where(sha: params.sha)`, matching the pattern already used by `Handler#stacks`.

### Proof of Concept
1. Attacker administers `attacker-org/forked-repo` (a fork of `victim-org/upstream-repo`), both tracked as separate Shipit stacks, and configures/triggers a legitimate `status` webhook on `attacker-org/forked-repo` (signed with `attacker-org`'s configured `webhook_secret`, which `verify_signature` accepts because `repository.owner.login == "attacker-org"`).
2. The webhook payload sets `sha` to a commit shared between the fork and upstream (present in both histories) and `state: "success"`, `context: "ci/required-check"`.
3. `StatusHandler#process` runs `Commit.where(sha: params.sha)` and finds the matching commit row belonging to `victim-org/upstream-repo`'s stack, then calls `commit.create_status_from_github!(params)`.
4. The victim stack's commit now shows a forged successful status; if `continuous_deployment` is enabled or a human relies on the (forged) green check to trigger deploy, an unauthorized deploy of that commit can occur — despite the webhook signature only ever having authenticated `attacker-org`.
