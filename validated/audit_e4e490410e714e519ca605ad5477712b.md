### Title
Silent Overwrite of CLStakingInfo for Consolidated Validators Causes Incorrect KAIA Reward Distribution — (`kaiax/staking/staking_info.go`)

### Summary

When multiple NodeIds share the same `RewardAddr` in the AddressBook (a supported and documented feature called "consolidation"), and more than one of those NodeIds has a `CLStakingInfo` registered in the CLRegistry, `consolidateNodes()` silently overwrites the first `CLStakingInfo` with the last one processed. The overwritten CL pool receives zero reward, and the total excess stake used in reward calculation is underestimated, corrupting every staker's proportional share for that block.

### Finding Description

`StakingInfo.consolidateNodes()` in `kaiax/staking/staking_info.go` merges AddressBook entries that share the same `RewardAddr` into a single `consolidatedNode`. After building the node map it iterates over `CLStakingInfos` and attaches each entry to the consolidated node whose `RewardAddr` corresponds to the `CLNodeId`:

```go
for _, clsi := range si.CLStakingInfos {
    if r, ok := nToR[clsi.CLNodeId]; ok {
        // One CLStakingInfo per validator is guaranteed by CLRegistry.
        cmap[r].CLStakingInfo = clsi   // ← plain assignment, not accumulation
    }
}
``` [1](#0-0) 

The comment asserts "One CLStakingInfo per validator is guaranteed by CLRegistry." The CLRegistry enforces uniqueness **per NodeId**, not per `RewardAddr`. When two NodeIds (`N1`, `N3`) share the same `RewardAddr` (`R1`) — a configuration explicitly supported and tested by the codebase — and both NodeIds independently register a `CLStakingInfo` in the CLRegistry, the loop processes `{CLNodeId: N1, ...}` first and then `{CLNodeId: N3, ...}`. The second assignment `cmap[R1].CLStakingInfo = clsi_N3` silently discards `clsi_N1`.

The test suite acknowledges this exact scenario but incorrectly dismisses it:

```go
// CL1 will be ignored when being consolidated since it has duplicate CL (not feasible in real)
``` [2](#0-1) 

The scenario **is** feasible: the CLRegistry enforces one entry per `CLNodeId`, not per `RewardAddr`. A validator legitimately operating two staking contracts (`N1`, `N3`) under one reward address can register CL pools for both.

### Impact Explanation

`assignStakingRewards()` in `kaiax/reward/impl/getter.go` calls `ConsolidatedNodes()` and computes `cnTotalStakingAmount` as `cn.StakingAmount + cn.CLStakingInfo.CLStakingAmount`:

```go
cnTotalStakingAmount := cn.StakingAmount
if isPrague && cn.CLStakingInfo != nil {
    cnTotalStakingAmount += cn.CLStakingInfo.CLStakingAmount
}
totalExcessInt += cnTotalStakingAmount - minStake
``` [3](#0-2) 

Because only `clsi_N3` survives, `clStakingAmount_N1` is excluded from `totalExcessInt`. This produces two concrete errors every block:

1. **`clPool1` (N1's CL pool) receives zero KAIA reward** — it is not referenced in `alloc` at all.
2. **`totalExcess` is underestimated** — every other staker's proportional share is inflated by the missing `clStakingAmount_N1`, so the remainder sent to the proposer is also wrong.

The reward is distributed via `FinalizeState()` which calls `state.AddBalance()` for each entry in `spec.Rewards`:

```go
for addr, amount := range spec.Rewards {
    state.AddBalance(addr, amount)
}
``` [4](#0-3) 

`clPool1` never appears in `spec.Rewards`, so its KAIA reward is permanently lost — not redistributed, not burnt, simply absent from the block's reward accounting.

### Likelihood Explanation

The trigger requires a validator to:
1. Register two or more NodeIds (`N1`, `N3`) under the same `RewardAddr` in the AddressBook — a documented and tested feature.
2. Register a `CLStakingInfo` for each of those NodeIds in the CLRegistry.

Both steps are permissioned (controlled by the validator itself), so no external attacker is needed. Any validator operating multiple staking contracts under one reward address who also participates in consensus liquidity will hit this silently. The likelihood is low in absolute terms but non-zero and grows as consensus liquidity adoption increases post-Prague hardfork.

### Recommendation

Replace the plain assignment with accumulation. Since a consolidated node may have multiple CL pools, `CLStakingInfo` should be changed to a slice, or the amounts should be summed and a representative pool address chosen. At minimum, add a duplicate-detection guard:

```go
for _, clsi := range si.CLStakingInfos {
    if r, ok := nToR[clsi.CLNodeId]; ok {
        if cmap[r].CLStakingInfo != nil {
            // Accumulate CLStakingAmount; decide on pool address policy
            cmap[r].CLStakingInfo.CLStakingAmount += clsi.CLStakingAmount
        } else {
            cmap[r].CLStakingInfo = clsi
        }
    }
}
```

Alternatively, enforce at the `parsePermissionlessCallResult` / `parseCallResult` layer that no two entries in `CLStakingInfos` resolve to the same consolidated `RewardAddr`, and return an error if they do.

### Proof of Concept

The existing test case in `kaiax/staking/staking_info_test.go` already demonstrates the overwrite:

```
NodeIds     = [N1, N2, N3, N4]
RewardAddrs = [R1, R2, R1, R2]   // N1 and N3 share R1
CLStakingInfos = [
  {CLNodeId: N1, CLPoolAddr: clPool1, CLStakingAmount: 1_000_000},
  {CLNodeId: N3, CLPoolAddr: clPool2, CLStakingAmount: 3_000_000},
]

After consolidateNodes():
  consolidatedNode for R1 = {NodeIds:[N1,N3], StakingAmount:A1+A3,
                              CLStakingInfo: {N3, clPool2, 3_000_000}}
  // clPool1 and its 1_000_000 are silently dropped
``` [5](#0-4) 

In `assignStakingRewards`, `totalExcessInt` is computed using only `3_000_000` instead of `4_000_000`. The reward split via `cn.Split(reward)` sends a portion to `clPool2` only. `clPool1` receives `0` KAIA. The `FinalizeState` call at the end of every block finalizes this incorrect distribution into the chain state. [6](#0-5) [7](#0-6)
