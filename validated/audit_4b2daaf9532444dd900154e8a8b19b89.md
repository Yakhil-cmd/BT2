### Title
Unsanitized HTML Injection in Arbiter Contract Fields (`title`, `text`, `my_party_name`, `peer_party_name`, `my_contact_info`) - (File: wallet.js)

### Summary
The CVE analog is Cacti's failure to sanitize the `group_prefix` field before storing/rendering it, allowing an authenticated but low-privileged user to inject arbitrary HTML that is later rendered in another user's browser. `ocore` has the same root-cause pattern in the arbiter-contract message handlers in `wallet.js`: free-text fields supplied by a remote *contract counterparty* device (`body.title`, `body.text`, `body.my_party_name`, `body.peer_party_name`, `body.my_contact_info`) are validated only for type/non-emptiness/length, never for HTML/script content, then persisted verbatim and later re-transmitted/rendered to the peer's and cosigners' wallet UI.

### Finding Description
`ocore` already recognizes this exact bug class and mitigates it in two other places:
- `device.js` `handlePairingMessage()` strips angle brackets from the attacker-controlled `device_name` before storing it: `body.device_name.replace(/<[^>]*>?/g, '')` [1](#0-0) 
- `wallet_defined_by_keys.js` `handleOfferToCreateNewWallet()` strips `<`/`>` from `wallet_name` and each `cosigner.name` before storing/using them: `body.wallet_name.replace(/[<>]/g, '')` / `cosigner.name.replace(/[<>]/g, '')` [2](#0-1) 

These two sanitizers establish that free-text values coming from a remote peer and destined to be shown in the wallet UI must be scrubbed of HTML tags in `ocore` before persistence, since `ocore` has no other output-encoding layer.

The `arbiter_contract_offer` handler in `wallet.js` breaks this pattern: it validates only that `title`, `text`, `my_pairing_code` are non-empty strings, that `my_contact_info`/`my_party_name`/`peer_party_name` are strings-or-falsy, and that the SHA hash of the whole object matches — there is no `<`/`>`/HTML stripping anywhere: [3](#0-2) 

The unsanitized body is then persisted verbatim through `arbiter_contract.store()`: [4](#0-3) 

and the `title`/`text`/`my_party_name`/`peer_party_name`/contact-info columns are plain `TEXT`/`VARCHAR` with no escaping applied anywhere in the ocore layer: [5](#0-4) 

The same unsanitized fields are re-emitted to cosigners (`arbiter_contract_shared`), copied into `peer_party_name`/`my_party_name` swaps, and surfaced via `eventBus.emit("arbiter_contract_offer", ...)`, which the wallet UI (GUI wallet / Obyte wallet apps that consume `ocore`) uses to render the contract to the user, exactly like Cacti rendered the unsanitized `group_prefix` to an admin.

### Impact Explanation
Because `ocore` performs no output encoding of its own and relies on inline sanitization to remove `<`/`>` for any field known to reach the UI, the missing sanitization on arbiter-contract fields lets a malicious contract counterparty (an untrusted device merely paired for contract negotiation — no special privilege required) store arbitrary HTML/script payloads (`title`, `text`, `my_party_name`, `peer_party_name`, `my_contact_info`) that get displayed to the victim's wallet UI and forwarded to the victim's cosigners as well (`arbiter_contract_shared`, `arbiter_contract_update`). This can lead to UI spoofing of contract terms/amount/party names to trick the victim into signing or paying against a different agreement than displayed, or, if the wallet UI's HTML renderer executes injected markup/script, to a stored XSS-class compromise of the wallet session (persistent HTML/script injection consistent with the CVE-2021-3816 impact class), enabling social-engineering-driven fund loss in a private, address-defined multi-sig/arbitration payment flow.

### Likelihood Explanation
Likelihood is high: any device that a user has merely paired with (a normal, low-friction pairing flow) can send an `arbiter_contract_offer` message with attacker-controlled `title`/`text`/party-name fields; no additional trust, keys, or privileges are required beyond the pairing relationship, which is the same posture assumed for private-payment counterparties.

### Recommendation
Apply the same sanitization already used elsewhere in the codebase (`replace(/<[^>]*>?/g, '')` or an equivalent HTML-escaping function) to `body.title`, `body.text`, `body.my_party_name`, `body.peer_party_name`, and `body.my_contact_info`/`body.peer_contact_info` in the `arbiter_contract_offer`, `arbiter_contract_shared`, `arbiter_contract_response`, and `arbiter_contract_update` handlers in `wallet.js` before they are persisted via `arbiter_contract.store()`/`setField()`, mirroring the pattern in `device.js`'s `handlePairingMessage()` and `wallet_defined_by_keys.js`'s `handleOfferToCreateNewWallet()`.

### Proof of Concept
1. Device B pairs with device A (normal pairing flow).
2. Device B sends a `arbiter_contract_offer` message to A with `title: "Contract"`, `text: "<img src=x onerror=alert(document.cookie)>"`, `my_party_name: "<script>...</script>"`, satisfying all of the checks in [6](#0-5)  (valid addresses, matching hash, valid date format, non-empty strings).
3. `ocore` stores the payload unmodified via `arbiter_contract.store()` [4](#0-3)  and emits `arbiter_contract_offer` for the UI to render.
4. When device A's wallet UI displays the pending contract (title/text/party names), the injected HTML/script executes or spoofs the displayed contract terms, and if A accepts and forwards `arbiter_contract_shared` to a cosigner device, the same payload propagates to the cosigner's UI as well.
