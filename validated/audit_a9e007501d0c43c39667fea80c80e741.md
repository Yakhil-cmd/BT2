### Title
AA response engine silently under-funds a capped-asset payment when required issuance exceeds the asset's cap, producing an invalid unit and freezing the AA response - (File: `aa_composer.js`)

### Summary
`aa_composer.js`'s `issueAsset()` helper, invoked from `completePaymentPayload()` while an AA composes its response unit, issues the *entire* asset cap instead of only the amount still missing to cover the payment. If the cap is smaller than the shortfall, the function reports success (no error) even though the resulting inputs still don't cover the outputs, and the caller proceeds to finalize/send the unit without re-checking sufficiency — mirroring the reported bug class where a helper returns/"succeeds" without conveying the real amount actually obtained, and the caller blindly trusts it for a downstream transfer.

### Finding Description
When an AA needs to pay out more of a self-issuable, capped asset than it currently holds, `completePaymentPayload()` falls back to `issueAsset()`: [1](#0-0) 

`issue_amount` is set to `objAsset.cap` unconditionally when the asset has a cap — not to `target_amount - total_amount` (the actual amount still required), which is only used for uncapped assets. `addIssueInput()` then adds `issue_amount` to `total_amount` and only emits a change output `if (change_amount > 0)`; if `change_amount` (`total_amount - target_amount`) is negative — i.e., the cap wasn't enough to cover the outstanding payment — no error is raised, and `cb2()` is invoked signaling "done" with no error.

The caller only checks for an explicit `err` from `issueAsset`: [2](#0-1) 

Since no `err` is produced in the cap-insufficient case, `sortOutputsAndReturn()` is called and the payment message is finalized with `sum(outputs) > sum(inputs)` for that asset — an unbalanced, invalid payment payload. There is no re-check of `bFound`/sufficiency after `issueAsset()` completes.

This differs from the pre-flight balance check performed earlier in `handleTrigger`, which only verifies that the AA is allowed to issue the asset (i.e., is the definer), not that the cap actually suffices to cover the deficit: [3](#0-2) 

That check passes as long as the AA is the asset definer, regardless of whether `cap` is large enough — so the flaw in `issueAsset()` is fully reachable.

### Impact Explanation
An unbalanced payment (outputs exceeding inputs) violates the fundamental invariant enforced by `validation.js`'s input/output balance checks for non-issue payments. Because the composing node itself validates units it builds before broadcasting, this scenario results in the AA response either:
- failing unit validation/composition unexpectedly (an unhandled condition not funneled through the graceful `bounce()` path used elsewhere in this same function), or
- if somehow accepted locally, producing a unit that would be rejected by every other node on the network as invalid.

Either way, the AA becomes unable to correctly process this trigger (and potentially any trigger that hits the same code path for the same capped asset), which is a fund-freezing/denial-of-service condition on the AA — reachable by any ordinary trigger sender, not requiring any special privilege, and is exactly the kind of "AA fund loss or freezing" impact in scope.

### Likelihood Explanation
This is triggered purely by ordinary AA logic: an AA whose oscript defines/uses a capped asset (`cap` property) and whose payment logic can, under some trigger inputs, need to issue more of that asset than the cap allows in a single issuance event. Any user who can send a trigger causing the AA's internal balance math to require more than the cap in one issuance event can hit this path — no privileged access, malicious peer, or network-level manipulation is required, satisfying the "unprivileged AA trigger sender" reachability requirement.

### Recommendation
In `issueAsset()` (aa_composer.js), after computing `issue_amount` for capped assets, verify that `total_amount` (after adding `issue_amount`) actually reaches `target_amount`. If it doesn't, treat this as a `"not enough funds"` error identical to the uncapped path, so the caller's existing `if (err) { ... bounce(...) }` logic correctly rejects the trigger instead of proceeding to build an unbalanced, invalid unit:

```js
function addIssueInput(serial_number){
    var input = { type: "issue", amount: issue_amount, serial_number: serial_number };
    payload.inputs.unshift(input);
    total_amount += issue_amount;
    var change_amount = total_amount - target_amount;
    if (change_amount < 0)
        return cb2("not enough funds even after issuing the capped asset");
    if (change_amount > 0)
        payload.outputs.push({ address: address, amount: change_amount });
    cb2();
}
```

### Proof of Concept
1. Deploy an AA whose definition issues a custom asset with a `cap` (e.g., `cap: 1000`) where the AA is the definer/issuer.
2. Craft AA logic so that, depending on trigger data, the AA must pay out more than `1000` units of that asset in a single response (e.g., `payment` message with `outputs` summing to `1500`, while the AA's current balance in that asset is `0` and the asset has never been issued).
3. Send a trigger unit that causes this code path: the pre-check in `handleTrigger` (lines 977-1002) passes because the AA is the definer, so it proceeds to `sendUnit()` → `completePaymentPayload()` → `issueAsset()`.
4. `issue_amount` is set to `1000` (the cap), `total_amount` becomes `1000`, `target_amount` is `1500`, so `change_amount = -500`; no error is raised, and the malformed unit (with outputs of 1500 but inputs of only 1000 in that asset) proceeds toward finalization instead of being bounced — leaving the AA in a state where this trigger's response cannot be validly completed.

Note: I was not able to fully trace, within the remaining exploration budget, the exact downstream error-handling path once the unbalanced payload reaches unit validation/writer logic (i.e., whether it surfaces as an uncaught exception, a rejected joint, or a stuck AA response state) — this would benefit from direct testing/tracing in a live/dev environment to confirm the precise failure mode and whether it is a one-off bounce or a persistent freeze for subsequent triggers exercising the same asset/cap.
