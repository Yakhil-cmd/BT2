### Title
`isContractAddr` Uses `extcodesize` Allowing Quorum Bypass in Treasury Rebalance Approval — (`contracts/testing/system_contracts/TreasuryRebalance.sol`, `contracts/testing/system_contracts/TreasuryRebalanceV2.sol`)

---

### Summary

Both `TreasuryRebalance.sol` (KIP-103) and `TreasuryRebalanceV2.sol` (KIP-160) use `extcodesize` to distinguish EOA from contract addresses in their approval and quorum-verification logic. A registered multi-sig contract that selfdestructs after a single admin approves will be reclassified as an EOA at quorum-check time, causing `checkRetiredsApproved()` / `checkZeroedsApproved()` to accept one approval instead of the required quorum. The core's `RebalanceTreasury()` then executes the rebalance — zeroing the registered address's KAIA balance and distributing it to allocated addresses — without the required number of approvals.

---

### Finding Description

`isContractAddr` in both contracts is implemented identically:

```solidity
function isContractAddr(address _addr) public view returns (bool) {
    uint256 size;
    assembly { size := extcodesize(_addr) }
    return size > 0;
}
``` [1](#0-0) [2](#0-1) 

This result drives two separate code paths in `approve()`:

```solidity
bool isContract = isContractAddr(_retiredAddress);
if (!isContract) {
    require(msg.sender == _retiredAddress, "retiredAddress is not the msg.sender");
    _updateApprover(_retiredAddress, msg.sender);
} else {
    (address[] memory adminList, ) = _getState(_retiredAddress);
    require(adminList.length != 0, "admin list cannot be empty");
    require(_validateAdmin(msg.sender, adminList), "msg.sender is not the admin");
    _updateApprover(_retiredAddress, msg.sender);
}
``` [3](#0-2) [4](#0-3) 

And the same `isContractAddr` call is repeated inside `checkRetiredsApproved()` / `checkZeroedsApproved()`:

```solidity
bool isContract = isContractAddr(retired.retired);
if (isContract) {
    // quorum check: validApprovals >= req
} else {
    require(retired.approvers.length == 1, "EOA should approve");
}
``` [5](#0-4) [6](#0-5) 

Because `extcodesize` returns 0 for a selfdestructed contract, the two calls to `isContractAddr` — one at approval time and one at quorum-verification time — can return different values for the same address. An address that was a contract when `approve()` was called can appear as an EOA when `checkRetiredsApproved()` / `checkZeroedsApproved()` is called.

The quorum-verification result is consumed directly by `finalizeApproval()`, and the core's `RebalanceTreasury()` re-runs `CheckZeroedsApproved` as Validation 3 before executing state changes:

```go
if err = caller.CheckZeroedsApproved(nil); err != nil {
    return result, err
}
// Execution 1) Clear all balances of zeroeds
for addr := range result.Before.Zeroed {
    state.SetBalance(addr, big.NewInt(0))
    ...
}
// Execution 2) Distribute KAIA to all allocateds
for addr, balance := range result.After.Allocated {
    state.SetBalance(addr, balance)
}
``` [7](#0-6) 

---

### Impact Explanation

A registered multi-sig treasury contract (e.g., requiring 3-of-5 admin approvals) can have its quorum requirement silently bypassed. The consequence is that `RebalanceTreasury()` executes with only 1 approval, zeroing the contract's KAIA balance and distributing it to the allocated addresses. This is an unauthorized KAIA transfer / burn affecting system-managed treasury funds.

---

### Likelihood Explanation

The trigger requires a single admin of the registered multi-sig contract to:
1. Call `approve()` while the contract has code (satisfying the contract-path admin check).
2. Cause the contract to `selfdestruct` before `checkRetiredsApproved()` / `checkZeroedsApproved()` is evaluated.

Pre-Cancun (KIP-103 era, mainnet block < 147,534,000): `selfdestruct` fully removes code in any transaction, making this straightforward.

Post-Cancun (KIP-160 era): EIP-6780 (`enable6780`) restricts `selfdestruct` to only remove code when called in the same transaction as contract creation. [8](#0-7) 

However, a CREATE2-deployed contract that selfdestructs in its constructor has `extcodesize == 0` from the moment of deployment, so the `approve()` call already takes the EOA path — meaning the attacker would need `msg.sender == retiredAddress`, which is impossible for a CREATE2 address. The more realistic post-Cancun vector requires the contract to be deployed, registered, approved (1 admin), and then selfdestructed within the same transaction as creation — a tighter but not impossible constraint using a factory pattern.

The overall likelihood is **medium**: it requires a semi-trusted insider (one admin of the registered multi-sig) and is easier pre-Cancun.

---

### Recommendation

Remove the `isContractAddr` distinction entirely from the approval and quorum-verification logic. Instead, record at registration time whether the address is a contract (or require explicit declaration), and use that immutable flag for all subsequent checks. Alternatively, store the quorum requirement at registration time rather than re-querying the (potentially destroyed) contract at verification time.

---

contract AttackerMultiSig {

        admins = _admins;

        return (admins, 3); // quorum = 3

//    → CheckZeroedsApproved passes (same bypass)

//    → allocated addresses receive funds

```go
func RebalanceTreasury(state *state.StateDB, chain backends.BlockChainForCaller, header *types.Header) (*rebalanceResult, error) {
	var (
		err    error
		caller RebalanceCaller

		result   = newRebalanceReceipt()
		isKIP160 = chain.Config().IsKIP160ForkBlock(header.Number)
		isKIP103 = chain.Config().IsKIP103ForkBlock(header.Number)
	)

	if isKIP160 {
		caller, err = rebalance.NewTreasuryRebalanceV2Caller(chain.Config().Kip160ContractAddress, backends.NewBlockchainContractBackend(chain, nil, nil))
	} else if isKIP103 {
		caller, err = NewKip103ContractCaller(state, chain, header)
	} else {
		return nil, errors.New("rebalancing shouldn't be executed unless the block number is kip103 or kip160 hard fork")
	}
	if err != nil {
		return nil, err
	}

	// Retrieve 1) Get Zeroed
	if err = result.fillZeroed(caller, state); err != nil {
		return result, err
	}

	// Retrieve 2) Get Allocated
	if err = result.fillAllocated(caller, state); err != nil {
		return result, err
	}

	// Validation 1) Check the target block number
	if blockNum, err := caller.RebalanceBlockNumber(nil); err != nil || blockNum.Cmp(header.Number) != 0 {
		return result, ErrRebalanceIncorrectBlock
	}

	// Validation 2) Check whether status is approved. It should be 2 meaning approved
	if status, err := caller.Status(nil); err != nil || status != 2 {
		return result, ErrRebalanceBadStatus
	}

	// Validation 3) Check approvals from zeroeds
	if err = caller.CheckZeroedsApproved(nil); err != nil {
		return result, err
	}

	// Validation 4) Check the total balance of zeroeds are bigger than the distributing amount
	totalZeroedAmount := result.totalZeroedBalance()
	totalAllocatedAmount := result.totalAllocatedBalance()
	if isKIP103 && totalZeroedAmount.Cmp(totalAllocatedAmount) < 0 {
		return result, ErrRebalanceNotEnoughBalance
	}

	// Execution 1) Clear all balances of zeroeds
	for addr := range result.Before.Zeroed {
		state.SetBalance(addr, big.NewInt(0))
		result.After.Zeroed[addr] = big.NewInt(0)
	}
	// Execution 2) Distribute KAIA to all allocateds
	for addr, balance := range result.After.Allocated {
		// if an allocated has KAIA before the allocation, it will be burnt
		currentBalance := state.GetBalance(addr)
		result.Burnt.Add(result.Burnt, currentBalance)

		state.SetBalance(addr, balance)
	}

	// Fill the remaining fields of the result
	remainder := new(big.Int).Sub(totalZeroedAmount, totalAllocatedAmount)
	result.Burnt.Add(result.Burnt, remainder)
	result.Success = true
	return result, nil
```
