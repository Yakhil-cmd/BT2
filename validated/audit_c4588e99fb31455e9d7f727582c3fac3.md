### Title
Address hash (`chash160`) truncates RIPEMD-160 output to 128 bits, weakening address-definition collision resistance - (File: `chash.js`)

### Summary
`ocore`'s payment/AA/device address scheme derives every address from the hash of its definition using `getChash160()`. Instead of using the full 160-bit RIPEMD-160 digest, the implementation discards the first 4 bytes of the digest and embeds a checksum computed over the remaining 16 bytes, so the actual security-relevant entropy backing every address is only 128 bits, not 160. This mirrors the externally reported bug class: using only part of a cryptographic hash as a unique identifier significantly reduces the cost of a birthday-collision attack against that identifier.

### Finding Description
`getChash()` computes the RIPEMD-160 digest of the definition's source string and then explicitly drops 4 bytes before using the result: [1](#0-0) 

```
var hash = crypto.createHash((chash_length === 160) ? "ripemd160" : "sha256").update(data, "utf8").digest();
var truncated_hash = (chash_length === 160) ? hash.slice(4) : hash; // drop first 4 bytes if 160
var checksum = getChecksum(truncated_hash);
```

The 4-byte checksum is deterministically derived from `truncated_hash` via `getChecksum()`: [2](#0-1) 

so it carries no independent entropy — colliding on the 16-byte `truncated_hash` alone is sufficient to produce an identical encoded `chash160` (address), because the checksum will match automatically. The remaining 4 bytes of the original 160-bit digest are discarded entirely and never influence the output.

This `getChash160` primitive is the address-derivation function used throughout the codebase to turn an address *definition* (an oscript authentication policy) into the 32-character address string: [3](#0-2) 

It is the function used to validate that a unit author's/definition matches the claimed address, both for freshly-introduced definitions and for shared/multi-sig addresses: [4](#0-3) [5](#0-4) 

and to derive definition-based device addresses: [6](#0-5) 

Because only 128 bits of the digest determine the address, an attacker only needs to find two different oscript *definitions* whose 128-bit truncated RIPEMD-160 digests collide — a standard birthday attack requiring on the order of 2^64 hash evaluations, dramatically cheaper than attacking a full 160-bit (or 256-bit) hash. As in the referenced report's PoC methodology, the attacker can hold one definition fixed as "legitimate" (e.g., a normal `sig` definition controlled by the victim/attacker to bootstrap trust) and vary an unused/free field in a second, "malicious" definition (e.g., extra bytes in a padding field of a `["and", [...]]`/`["r of set"]`-style definition, or a benign extra clause) until its truncated hash matches the first one's.

### Impact Explanation
If a collision is found between a benign definition D1 and an attacker-crafted definition D2 with a materially different authorization policy (e.g., D2 adds the attacker as a co-signer, lowers a multi-sig threshold, or grants the attacker unilateral spending rights) such that `getChash160(D1) === getChash160(D2)`, the attacker can:
- Post a unit that first establishes address `A = getChash160(D1)` with the innocuous definition D1 (as normally happens on first use), and later present D2 as the "definition" for the same address `A` in a subsequent unit or in `wallet_defined_by_addresses.js`'s shared-address flow. Since `validation.js`'s `validateDefinition()` only checks that `getChash160(definition) === definition_chash`, a colliding D2 passes this check just as well as D1 would.
- This enables unauthorized spending from address `A` (funds theft) if D2 grants the attacker signing rights, or a permanent freeze/DoS of the address's funds if D2 is unsatisfiable, or governance hijack of a shared address analogous to the "hosts"/threshold manipulation described in the source report.

This satisfies the "concrete unauthorized spending / AA fund loss or freezing" bar, reachable by any unprivileged party who can construct and register/post an address definition.

### Likelihood Explanation
A 2^64-effort birthday search is impractical for casual attackers but is within reach of a well-resourced adversary (similar cost class to large-scale ASIC/GPU hashing operations), and RIPEMD-160 has no known way to accelerate this beyond generic birthday-attack bounds. Given the potentially high value of a shared/multi-sig or contract-controlled address, this places the risk at Medium, consistent with the judged severity of the analogous PartyDAO finding, which used comparable (15–16 byte / 120–128-bit) truncation and per-unit cost estimates.

### Recommendation
Do not discard any bytes of the underlying digest before deriving the address. If a checksum must be embedded for typo-detection (as `chash.js` already does), compute it over the full 160-bit RIPEMD-160 digest instead of a 128-bit truncation of it, and/or extend the addressing scheme to use a full 256-bit hash algorithm to bring the collision-resistance margin in line with modern standards, as PartyDAO did by widening `distributionHash15`/`governanceOptsHash` to the full 32-byte `keccak256` output.

### Proof of Concept
1. Fix a benign definition `D1 = ["sig", {"pubkey": P}]` used to legitimately fund address `A = getChash160(D1)` (as in `object_hash.js` `getChash160`).
2. Construct a family of malicious definitions `D2_i = ["and", [["sig", {"pubkey": P}], ["sig", {"pubkey": Q_i}]]]` (or any structurally different definition) by varying `Q_i` (e.g., grinding an attacker-controlled second-signer pubkey or an unused padding field), each hashed with the same `getChash160()`.
3. Run the birthday search: hash ~2^64 candidate `D1`-variants and `D2`-variants (per the report's own cost methodology, scaled to `truncated_hash` = 16 bytes) until a pair collides in the resulting `chash160` string.
4. Once a colliding `D2` is found, submit a unit (or shared-address handshake per `wallet_defined_by_addresses.js` `handleNewSharedAddress`) presenting `D2` as the definition for address `A`; `validation.js`'s `getChash160(D2) === definition_chash` check passes, letting the attacker's co-signer clause take effect on the already-funded address `A`.
