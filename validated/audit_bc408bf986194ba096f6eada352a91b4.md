## Analysis

The AntSword bug class is: a **regex/pattern-based sanitizer (`noxss()`) that strips a specific dangerous marker/format-code from untrusted text using a single, literal-anchored pattern**, which is bypassable by nesting a decoy occurrence of the pattern so that, after the single-pass removal, the surrounding fragments recombine into a fresh, fully-formed malicious marker that the client-side renderer then interprets specially — leading to unintended, attacker-controlled rich-content execution.

`ocore` has a structurally identical sanitizer in `wallet.js`'s handling of `text` messages received from any paired/correspondent device: [1](#0-0) 

```js
case "text":
    message_counter++;
    if (!ValidationUtils.isNonemptyString(body))
        return callbacks.ifError("text body must be string");
    body = body
        .replace(/\(prosaic-contract:.+?\)/g, '')
        .replace(/\(arbiter-contract-offer:.+?\)/g, '')
        .replace(/\(arbiter-contract-event:.+?\)/g, '')
        .replace(/\(arbiter-dispute:.+?\)/g, '');
    // the wallet should have an event handler that displays the text to the user
    eventBus.emit("text", from_address, body, message_counter);
```

This filter exists specifically because the wallet client (GUI) treats these `(marker:base64)` sequences embedded in chat text as *rich, structured UI elements* — the wallet only ever legitimately synthesizes such a marker after cryptographically validating a real `prosaic_contract_offer`/`arbiter_contract_offer`/response message and re-injecting it into the chat stream as plain "text" for rendering: [2](#0-1) 

The stripping regexes use a **literal prefix + non-greedy `.+?` up to the first `)`** — the exact pattern class vulnerable to nested-decoy reconstruction. An attacker (any correspondent device that has paired with the victim — an allowed actor per scope) can send a `text` message body such as:

```
(pro(prosaic-contract:X)saic-contract:<attacker_base64_payload>)
```

Single-pass, left-to-right regex matching finds the *first* literal `(prosaic-contract:` at offset 4, and `.+?` lazily matches up to the *nearest* `)` (`X)`), so only `"(prosaic-contract:X)"` is removed. Concatenating what remains — `"(pro"` + `"saic-contract:<attacker_base64_payload>)"` — reconstructs exactly `"(prosaic-contract:<attacker_base64_payload>)"`, a brand-new, fully-formed marker that survives the filter untouched and is then emitted via `eventBus.emit("text", ...)` to the wallet UI for rich rendering, exactly as if it had passed through the legitimate, validated `prosaic_contract_offer`/`arbiter_contract_offer` handlers (which independently enforce hash/address/date checks): [3](#0-2) [4](#0-3) 

Because the forged marker never passed through those validated code paths, its embedded JSON (title, amount, asset, addresses, arbiter, pairing codes) is entirely attacker-controlled and displayed to the victim as if it were a genuine, mutually-agreed contract/dispute offer from a trusted correspondent — a "1-click" social-engineering vector structurally identical to AntSword's incomplete `noxss()` → format-code injection chain, reachable purely by a paired device sending an ordinary chat message.

### Title
Incomplete sanitization of embedded contract markers in wallet "text" messages allows forged contract/dispute UI injection - (File: wallet.js)

### Summary
`handleMessageFromHub`'s `"text"` case sanitizes chat bodies with four literal-anchored, non-greedy regexes intended to strip `(prosaic-contract:...)`, `(arbiter-contract-offer:...)`, `(arbiter-contract-event:...)`, and `(arbiter-dispute:...)` markers that the wallet UI treats as rich, actionable contract/dispute cards. The single-pass `String.replace` sanitization can be bypassed by nesting a decoy marker so the surrounding leftover fragments recombine into a new, complete marker after removal.

### Finding Description
`wallet.js` (lines 101-113) applies `.replace(/\(prosaic-contract:.+?\)/g,'')` and three sibling regexes to any `text` message received from a paired correspondent device before re-emitting it via `eventBus.emit("text", ...)` for display. These markers are the same format the wallet itself generates only after validating a real contract-protocol message (lines 455-481, 617-654), so any correspondent able to make such a marker survive the filter can impersonate the legitimate contract-offer/response pipeline purely through a `text` chat message. Because each regex is anchored to a literal keyword and uses a non-greedy quantifier bounded by the *first* subsequent `)`, a crafted input containing a nested decoy occurrence of the same keyword is only partially stripped in a single pass; the untouched prefix/suffix around the removed decoy re-forms a brand-new, fully-formed marker with attacker-chosen base64 payload (e.g. `"(pro(prosaic-contract:X)saic-contract:<payload>)"` → after filtering → `"(prosaic-contract:<payload>)"`).

### Impact Explanation
The reconstructed marker is delivered to the wallet's `text` UI handler unmodified, which decodes/parses it the same way it parses legitimately-issued contract offers, rendering an attacker-controlled contract/dispute card (fake counterparty terms, amount, asset, addresses, arbiter) that never passed the real validation performed in the dedicated `prosaic_contract_offer`/`arbiter_contract_offer` handlers. A victim who trusts the sender and interacts with the forged card (accepts/signs/pays) can be induced into authorizing a real, attacker-defined payment or shared-address signing flow, causing unauthorized spending or fund loss — the wallet/contract message-handling equivalent of AntSword's incomplete-sanitization → forged-content → 1-click impact chain.

### Likelihood Explanation
Any device that has paired with the victim (a standard, low-privilege relationship) can trigger this by sending one crafted `text` message; no cryptographic material or special trust is required beyond an existing pairing, and the bypass construction is deterministic and easy to reproduce.

### Recommendation
Replace the single-pass literal/non-greedy stripping with a sanitizer that loops until no further matches are found (or use a non-regex tokenizer), and/or reject any `text` body that still contains the literal substrings `(prosaic-contract:`, `(arbiter-contract-offer:`, `(arbiter-contract-event:`, `(arbiter-dispute:` after sanitization, throwing an error instead of silently forwarding partially-cleaned content.

### Proof of Concept
1. Device B pairs with victim device A (normal pairing flow).
2. Device B sends subject `"text"` with body:
   `"(pro(prosaic-contract:X)saic-contract:" + Buffer.from(JSON.stringify({title:"Fake", text:"...", peer_address:"<attacker_addr>", my_address:"<victim_addr>", amount: 999999, ...}), 'utf8').toString('base64') + ")"`
3. `wallet.js` line 106 removes only `"(prosaic-contract:X)"`, leaving the surrounding text concatenated into `"(prosaic-contract:<payload>)"`.
4. `eventBus.emit("text", from_address, body, message_counter)` delivers the forged marker to the wallet UI, which renders it as a genuine incoming contract offer despite never being processed by `prosaic_contract_offer`'s validation logic [5](#0-4) .
