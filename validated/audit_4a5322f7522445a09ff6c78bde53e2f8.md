### Title
Webhook signature is verified against a GitHub organization derived from attacker-controlled JSON, while the repository actually acted upon is taken from a different, unvalidated field of the same payload - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` picks the GitHub App/`webhook_secret` to validate a webhook against based on `repository_owner`, a value read straight out of the JSON body (`repository.owner.login`, falling back to `organization.login`). The handlers that actually act on the payload (`PushHandler`, `PullRequest::*Handler`, etc.) resolve the target `Repository`/`Stack` from a **different** field of the same body, `repository.full_name`, via `Handler#repository_name`. Nothing enforces that the organization used to select the verification secret and the organization embedded in `repository.full_name` are the same organization.

### Finding Description
`verify_signature` computes the org to authenticate against purely from payload content: [1](#0-0) [2](#0-1) 

`Shipit.github(organization: repository_owner)` loads the `GitHubApp` (and its `webhook_secret`) configured for that org, and `verify_webhook_signature` HMACs the *entire* raw body against that secret: [3](#0-2) 

Once the signature check passes, `create` dispatches the parsed body to handlers unchanged: [4](#0-3) 

Every handler resolves the `Repository`/`Stack` it will mutate from `repository.full_name`, a sibling field of `repository.owner.login` inside the same body, with no cross-check against the value used for signature selection: [5](#0-4) [6](#0-5) 

This is the structural analog of the reported bug class: a verification step keys off one field/condition (here, "which org's secret to check"), while the consequential action is driven by a different, independently-controlled field ("which repository/stack to mutate") that the check never constrains. In the original report, a failed `minValue`/`maxValue` check silently let an empty constraint be written for the wrong parameter type; here, a valid signature computed against org A's secret silently authorizes an action against any repository name embedded in the same JSON, including one belonging to org B — because HMAC verification only proves the bytes weren't altered in transit, not that the fields inside are mutually consistent with the org that produced the secret.

Concretely: anyone who legitimately administers a Shipit-connected GitHub App/org (and therefore knows or can trigger deliveries signed with that org's `webhook_secret`) can craft a POST to `/webhooks` where:
- `repository.owner.login` (and/or `organization.login`) = their own org (so `verify_signature` selects their own, correctly-configured `webhook_secret` and the HMAC passes), while
- `repository.full_name` = `"other-org/other-repo"` — a stack belonging to a completely different organization they have no GitHub-side access to.

`PushHandler` will then locate that other org's `Repository`/`Stack` via `Repository.from_github_repo_name(repository_name)` and enqueue `GithubSyncJob`, causing Shipit to fetch commits and advance stack state for a repository outside the attacker's authorized organization: [7](#0-6) [8](#0-7) 

Other handlers exhibit the same pattern and amplify the impact: `PullRequest::ClosedHandler`/`ReopenedHandler`/`LabeledHandler`/`UnlabeledHandler` resolve `repository` the same way and then call `stack.archive!` / `stack.unarchive!` on review stacks belonging to the spoofed repository: [9](#0-8) [10](#0-9) 

### Impact Explanation
This breaks the binding "organization whose secret authenticated the request == organization whose repository is written," matching the report's finding class where a check's failure/scope mismatch results in the wrong entity being modified. An attacker who is a legitimate admin of one Shipit-connected GitHub organization (an unprivileged party with respect to every *other* org tracked by the same Shipit instance) can forge webhook bodies that:
- Force `GithubSyncJob` to run against an unrelated organization's stack (state mutation / resource-abuse against a repository they don't control), and
- Archive/unarchive review stacks, or otherwise flip control-flow booleans (`respond_to_pull_request_closed?`, `unarchive?`, label-driven provisioning logic) for repositories owned by other organizations.

This is a cross-organization / cross-repository write achieved purely by crafting payload fields the signature check never binds together, landing in the "cross-repository writes" Critical impact bucket defined by the rules.

### Likelihood Explanation
Likelihood depends on a Shipit deployment configuring more than one GitHub organization (the multi-org `github_app_config`/`TOP_LEVEL_GH_KEYS` schema in `lib/shipit.rb`, lines 170–200) with `Shipit.github(organization:)` selecting per-org secrets — this is a supported, documented configuration path, not an edge case requiring the host app to deviate from documented mounting. Any org admin already holding a legitimate `webhook_secret` for their own org (no additional privilege, no Shipit session, no `ApiClient` token) can exploit this by POSTing directly to the public `/webhooks` endpoint.

### Recommendation
`verify_signature` should not be the only binding between "which org's secret validated this request" and "which repository the handlers mutate." After computing `repository_owner` and verifying the signature, the controller (or `Handler#repository_name`/`stacks`) should additionally assert that the resolved `Repository`'s owner/org matches `repository_owner` (or, more robustly, that `repository.full_name`'s owner segment equals `repository.owner.login`), rejecting (422) the request otherwise — mirroring the report's recommendation to make the mismatched-check case a hard failure rather than a silent pass-through to downstream logic.

### Proof of Concept
1. Attacker legitimately administers `attacker-org`, which is configured in Shipit's multi-org GitHub App secrets with its own `webhook_secret` (`S`).
2. Victim Shipit instance also tracks `victim-org/victim-repo` under a different `webhook_secret`.
3. Attacker crafts a `push` event body:
   ```json
   {
     "ref": "refs/heads/master",
     "after": "<attacker-chosen sha, or reuse a known victim sha>",
     "repository": {
       "owner": { "login": "attacker-org" },
       "full_name": "victim-org/victim-repo"
     }
   }
   ```
4. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(S, raw_body)` using their own known `webhook_secret` for `attacker-org`, and sends it to `POST /webhooks` with `X-Github-Event: push`.
5. `verify_signature` calls `Shipit.github(organization: "attacker-org")`, whose `webhook_secret` matches, so the HMAC check passes (`app/controllers/shipit/webhooks_controller.rb:24-30`, `lib/shipit/github_app.rb:76-83`).
6. `PushHandler#process` resolves the stack via `Repository.from_github_repo_name("victim-org/victim-repo")` (`app/models/shipit/webhooks/handlers/handler.rb:32-38`, `push_handler.rb:12-17`) and enqueues `GithubSyncJob` for the victim's stack — an action the attacker was never authorized to trigger via GitHub.

Note: I was unable to execute this end-to-end (no test harness invoked in this session); the analysis is based on directly reading `webhooks_controller.rb`, `github_app.rb`, `handler.rb`, `push_handler.rb`, the `pull_request/*` handlers, and `lib/shipit.rb`'s multi-org `github`/`github_app_config` methods, all of which are in-scope engine files.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
    def perform(params)
      @stack = Stack.find(params[:stack_id])
      expected_head_sha = params[:expected_head_sha]
      retry_count = params[:retry_count] || 0
      head_before_sync = spec_cache_target
      appended_commits = []

      handle_github_errors do
        new_commits, shared_parent = fetch_missing_commits { stack.github_commits }

        # Retry on Github eventual consistency: webhook indicated new commits but we found none
        if expected_head_sha && new_commits.empty? && !commit_exists?(expected_head_sha) &&
           retry_count < MAX_RETRY_ATTEMPTS
          GithubSyncJob.set(wait: RETRY_DELAY * retry_count).perform_later(params.merge(retry_count: retry_count + 1))
          return
        end

        stack.transaction do
          shared_parent&.detach_children!
          appended_commits = new_commits.map do |gh_commit|
            append_commit(gh_commit)
          end
          stack.lock_reverted_commits! if appended_commits.any?(&:revert?)
        end
      end
      sync_changed_nothing = appended_commits.empty? &&
                             spec_cache_target == head_before_sync &&
                             stack.cached_deploy_spec.present?
      return if sync_changed_nothing && !params[:force_spec_cache]

      CacheDeploySpecJob.perform_later(stack)
    end
```
