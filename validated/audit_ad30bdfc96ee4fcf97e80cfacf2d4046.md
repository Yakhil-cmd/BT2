### Title
Attacker-controlled swap route injects unauthorized sub-invocations into the caller's signed auth tree, letting a rogue hop drain the caller's wallet — (File: contracts/controller/src/strategies/swap.rs)

### Summary
The OS-command-injection class (untrusted data executed as instructions in a privileged context) maps onto XOXNO Lending's strategy swaps: the `swap` payload is caller-supplied instruction data, and the route names arbitrary pool/token contract addresses that execute under the swapper's authorization. Neither the controller nor the router maintains an allowlist of hop contracts, so a maliciously crafted route can invoke attacker-deployed code that issues `token.transfer(caller, attacker, amount)` — a call that attaches to the caller's own authorization entry in simulation and executes on-chain once the caller signs the recorded tree. The harness test `rogue_hop_pool_transfer_joins_caller_auth_tree.rs` demonstrates the full wallet drain.

### Finding Description
Account strategies (`swap_collateral`, `swap_debt`, `repay_debt_with_collateral`, `multiply`, `flash_position`) accept an attacker-influenced `StrategySwap` XDR and forward it to the configured router via `swap_tokens` in `contracts/controller/src/strategies/swap.rs:13-55`. The controller's only guard is an exact input-transfer authorization (`authorize_transfer_as_current`, line 34) plus measured input/output deltas; it places no constraint on *what code* the payload names. The router's `run` (`contracts/swap-aggregator/src/execute/mod.rs:51-119`) decodes the instruction stream and dispatches hops to payload-supplied `pool` addresses (e.g., `invoke_contract(&ctx.hop.pool, "swap_exact_amount_in", ...)` in `venues/comet.rs:30-34`), with no venue/pool allowlist — the whitelist in `storage::load_whitelist` only selects fee placement. Because the hop runs inside the caller's `require_auth` root, any `require_auth` call the rogue hop makes on *the caller's* address is recorded as a sub-invocation of the caller's tree and is authorized when the caller signs it. This is the injection: untrusted route bytes smuggle attacker-authored invocations into the victim's authorization context — the exact structural analog of injecting shell metacharacters into a command string.

### Impact Explanation
Theft of user funds, unbounded by the swap amount. The test at `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs:194-269` shows a rogue hop pool transferring the victim's entire balance (77,770 units) of an *unlisted* wallet token to the attacker, while the swap itself settles "fairly" (correct output, correct collateral credit) so every protocol-side check — `RouterOverspend`, `NoSwapOutput`, min-out, final account risk — passes. The routed principal, the payload `min_out`, and the health-factor gates impose no bound on the loss, which equals whatever the victim's wallet holds and signs for.

### Likelihood Explanation
Reachable by any unprivileged address through all route-taking entrypoints and through direct `router.execute_strategy` calls. Exploitation requires the victim to submit an attacker-crafted route and sign the resulting authorization tree — analogous to the UI:R requirement of the reference CVE. Wallets/clients that render or auto-sign the simulation-produced tree without decoding hops expose users directly; the protocol's own threat model (`docs/explanation/threat-model.md:154-165`) acknowledges this path and shifts the burden to client-side route decoding rather than enforcing anything on-chain. Because the honest flow produces exactly one child entry (the input transfer), enforcing a "no extra children" rule on-chain is feasible, which makes the absence of an allowlist a genuine contract-level gap rather than a purely client-side concern.

### Recommendation
Enforce venue integrity on-chain instead of relying on clients to decode routes:
- Maintain a governance-managed allowlist of hop pool/venue contract addresses in the router (or controller) and reject hops whose `pool`/`token_in`/`token_out` are not listed, mirroring the existing Blend-pool approval list (INV-STRAT-03).
- Alternatively, have the router verify after the hop that it made no calls requiring the `sender`'s authorization beyond the single inbound `transfer` (e.g., constrain venue calls to invoker-auth-only paths, as `comet.rs` already does for the router's own approvals).
- At minimum, document and enforce a strict expected auth-tree shape in any reference client/SDK shipped with the protocol.

### Proof of Concept
1. Attacker deploys a "pool" contract whose `swap()` calls `token::Client::new(&env, &any_token).transfer(&victim, &attacker, &victim_balance)` — see `RogueHopPool` in `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs:62-71`.
2. Attacker hands the victim a route XDR whose hop names the rogue pool and a fair `min_out` (the router double at lines 39-47 mirrors what a real fair-paying route looks like).
3. Victim calls `controller.swap_collateral(...)` with that `swap` payload. `swap_tokens` authorizes only the input transfer and measures deltas, so nothing rejects the route.
4. During `router.execute_strategy`, `invoke_contract` enters the rogue pool; its `transfer(victim → attacker)` hits `from.require_auth()` on the victim and is recorded as a child of the victim's `swap_collateral` authorization entry (asserted at lines 206-222).
5. Simulation returns the poisoned tree; the victim signs it. On submission the host authorizes the embedded transfer: the victim's wallet balance of the unrelated token goes to 0 and the attacker receives it — `assert_eq!(s.wallet(&s.alice), 0)` / `assert_eq!(s.wallet(&s.attacker), WALLET_BALANCE)` at lines 224-225 and 267-268 — while the victim still receives the fair swap output and a healthy position, so no protocol gate ever fires.

Caveat: I could not fully read `venues/dispatch_hop` and the remaining venue modules in this session, but the harness test and threat-model text independently confirm that payload-named addresses are invoked with no allowlist.
