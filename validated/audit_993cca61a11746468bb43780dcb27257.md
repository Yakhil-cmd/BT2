### Title
Webhook signature is verified against the payload's claimed organization, but writes are performed against an unrelated repository/commit - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the HMAC secret to validate a webhook against using `repository.owner.login` (or `organization.login`) taken from the untrusted JSON body, then hands the *entire* raw payload to event handlers that act on a completely different field — `repository.full_name` for `PushHandler`, and no repository scoping at all for `StatusHandler`. An attacker who legitimately controls a GitHub App/webhook secret for their own organization can therefore forge a signed webhook whose "authenticating" field points at their own org while its "acted upon" fields point at another organization's stack or any commit SHA in the database, breaking the binding `organization that authenticated == repository/commit that is written`.

### Finding Description
`verify_signature` picks the GitHub App configuration (and thus the webhook secret) solely from the payload's `repository.owner.login`/`organization.login`: [1](#0-0) 

For multi-org configurations, `Shipit.github(organization:)` resolves the app config keyed strictly by that same attacker-controlled field: [2](#0-1) 

(In single-org configurations it is even weaker: `github_default_organization` is `nil`, so `Shipit.github` ignores the `organization` parameter entirely and always returns the one global config — meaning the signature only proves "signed with the single configured secret," never proving anything about which repository/org the event concerns.)

Once the signature check passes, `create` dispatches the *raw, unmodified* payload to handlers: [3](#0-2) 

`PushHandler` resolves the target stacks using `repository.full_name`, a field never checked by `verify_signature`: [4](#0-3) [5](#0-4) 

`StatusHandler` is worse: it doesn't scope by repository at all, matching purely on `sha` across the entire `Commit` table, i.e. across every stack/repository hosted by the Shipit instance: [6](#0-5) 

So the field that is cryptographically bound (`repository.owner.login`) and the field(s) that are actually acted upon (`repository.full_name`, `sha`) are independent, attacker-controlled JSON keys in the same request body.

### Impact Explanation
Any party who legitimately operates a GitHub App/webhook secret for one organization onboarded to a shared Shipit instance can forge signed webhook deliveries that:
- Trigger `stack.sync_github` (`GithubSyncJob`) for stacks belonging to a different organization's repository by setting `repository.owner.login` to their own org (to pass signature check) while setting `repository.full_name` to the victim repository, and
- Inject/forge `Commit::Status` records for arbitrary commit SHAs belonging to any stack in the instance via `StatusHandler`, since it performs no repository check whatsoever.

Because Shipit's deploy gating (`Stack`/`Commit` status/check checks) is used to decide whether a commit is deployable, forging a passing status for a victim commit can influence deploy decisions for a repository the attacker does not own — a cross-repository/cross-organization write achieved purely by presenting a signature that is valid only for the attacker's own organization.

### Likelihood Explanation
This requires no privileged Shipit account, API token, or `webhook_secret` for the *victim* organization — only a signature that is valid for *any* organization already configured/onboarded on the shared Shipit instance (the attacker's own, or the single global secret in single-org deployments). This is a realistic and low-cost multi-tenant scenario: Shipit is commonly deployed as a shared instance serving multiple GitHub orgs/repos, and each org's webhook secret is intentionally accessible to that org's own GitHub App administrators.

### Recommendation
Bind the signature-verification identity to the exact same field used for write authorization. Concretely, after selecting the app config, re-validate that `repository.full_name`'s owner segment matches the `repository_owner` used to select the webhook secret, and reject the request otherwise. Additionally, `StatusHandler` (and any handler acting on cross-cutting resources like `Commit`) must scope lookups through `stacks`/`Repository.from_github_repo_name(repository_name)` rather than querying `Commit` globally by `sha`.

### Proof of Concept
1. Attacker operates a GitHub App installed on organization `attacker-org`, with known `webhook_secret_attacker`, in a Shipit instance that also serves `victim-org/victim-repo`.
2. Attacker crafts a `push` (or `status`) webhook body:
   ```json
   {
     "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" },
     "ref": "refs/heads/main",
     "after": "<victim commit sha>"
   }
   ```
3. Attacker computes `X-Hub-Signature: sha1=HMAC(webhook_secret_attacker, raw_body)` — this passes `verify_signature` because `repository_owner` resolves to `attacker-org`.
4. `PushHandler#process` resolves `stacks` via `repository.full_name = "victim-org/victim-repo"` (see `Handler#repository_name`) and calls `stack.sync_github(expected_head_sha: ...)` on the victim's stack, or a forged `status` event marks an arbitrary SHA (via `StatusHandler`, unscoped by repo) with `state: "success"`, both without ever holding credentials for `victim-org`.

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping
      head(:ok) if event == 'ping'
    end

    def event
      request.headers.fetch('X-Github-Event')
    end

    def repository_owner
      # Fallback to the organization sub-object if repository isn't included in the payload
      params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
    end
```

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
