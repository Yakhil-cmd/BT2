### Title
`provision?` operator‑precedence bug lets a PR label bypass `review_stacks_enabled`, forcing unauthorized `ReviewStack` provisioning - ([File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb])

### Summary
`OpenedHandler#provision?` intends `review_stacks_enabled` to gate *all* provisioning behaviors, but Ruby operator precedence only ANDs it with the `allow_all` branch. An unprivileged PR author who labels their own pull request with the repository's configured `provisioning_label_name` can trigger `ReviewStack` creation even when `review_stacks_enabled` is `false`, as long as `provisioning_behavior` is `allow_with_label` (or `prevent_with_label`, by simply not applying the label).

### Finding Description
The broken binding, stated as an equality the code assumes but does not enforce:
`provision? == (repository.review_stacks_enabled && (allow_all? || allow_with_label?&&label || prevent_with_label?&&!label))`

The actual code is: [1](#0-0) 

Due to `&&` binding tighter than `||`, this parses as:
`(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label) || (prevent_with_label? && !has_label)`

`review_stacks_enabled` is only ANDed with the first disjunct. When `provisioning_behavior` is `allow_with_label` (or `prevent_with_label`), the result of `provision?` is fully independent of `review_stacks_enabled`.

Path: `OpenedHandler#process` → `respond_to_pull_request_opened?` → `provision?` → `ReviewStackAdapter#find_or_create!`, gated only by `params.action == "opened"` and the buggy `provision?`. There is no additional check on `review_stacks_enabled` elsewhere in this path. `repository` is resolved purely from `params.repository.full_name` in the webhook payload sent by GitHub for the PR event [2](#0-1) , and `pull_request_has_provisioning_label?` reads label names straight from the attacker-controlled `pull_request.labels` array in the payload [3](#0-2) .

Exploit: attacker opens a PR on a repository they control (or fork of a tracked repo), applies a label whose name equals the target repository's `provisioning_label_name` (visible in the public repo settings UI or guessable, e.g. commonly `"deploy"`, `"review"`, etc.), and sends (or lets GitHub send) the `pull_request` `opened` webhook. Even if the maintainer set `review_stacks_enabled: false` intending to disable review-stack provisioning while leaving `provisioning_behavior` as `allow_with_label` from a prior configuration, the label alone provisions a `ReviewStack`.

Existing guards do not catch this: signature verification (`verify_signature`) only proves the webhook came from GitHub for that repository — it does not validate the business-logic condition `review_stacks_enabled`. `ExplicitParameters` only validates payload shape, not authorization semantics. There is no separate check enforcing `review_stacks_enabled` before calling `ReviewStackAdapter#find_or_create!`. This is confirmed by the test suite: `test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb`'s `"creates stacks for repos that allow_with_label when label is present"` test never sets `review_stacks_enabled: false`, and no test in this file exercises `allow_with_label` (or `prevent_with_label`) together with `review_stacks_enabled: false` — i.e., the precedence bug is untested and unguarded [4](#0-3) .

### Impact Explanation
A `ReviewStack` is created for a repository whose operator explicitly disabled review-stack provisioning (`review_stacks_enabled: false`), based solely on an attacker-controlled label on their own PR. Review-stack creation drives the downstream provisioning task pipeline (deploy/provision commands executed via `Command`/`PTY.spawn` against the configured deploy spec), so this results in unauthorized deploy/provisioning execution against the host — a write for a repository whose current authorization state (`review_stacks_enabled == false`) explicitly forbids it. This is repeatable on every "opened" PR event and applies to any tracked repository configured with `provisioning_behavior: allow_with_label` (or `prevent_with_label`) regardless of the `review_stacks_enabled` toggle, i.e., across any tenant repository using non-`allow_all` behaviors. This matches the Critical category: an unauthorized deploy/provisioning action performed for a repository that did not authorize it.

### Likelihood Explanation
Preconditions: the target repository must have `provisioning_behavior` set to `allow_with_label` or `prevent_with_label` with `review_stacks_enabled` set to `false` (a plausible, even likely, misconfiguration state — e.g., an operator toggling `review_stacks_enabled` off temporarily without also resetting `provisioning_behavior`). The attacker only needs the ability to open a PR and set a label with a specific name in their own fork/branch, both of which are ordinary unprivileged GitHub actions requiring no Shipit credentials. Discovering `provisioning_label_name` requires no more than reading the repository's Shipit settings page or trial-and-error with common label names. The attack is trivially repeatable at zero cost per attempt.

### Recommendation
Fix operator grouping in `provision?` so `review_stacks_enabled` gates every behavior branch, e.g.:
```ruby
def provision?
  repository.review_stacks_enabled && (
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
  )
end
```

### Proof of Concept
In `test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb`, add:
```ruby
test "does not create stacks for allow_with_label repos when review_stacks_enabled is false" do
  repository = shipit_repositories(:shipit)
  repository.update!(
    review_stacks_enabled: false,
    provisioning_behavior: :allow_with_label,
    provisioning_label_name: "deploy-me"
  )
  payload = payload_parsed(:pull_request_opened)
  payload["pull_request"]["labels"] << { "name" => "deploy-me" }

  assert_no_difference -> { Shipit::Stack.count } do
    OpenedHandler.new(payload).process
  end
end
```
Before the fix: `Shipit::Stack.count` increases by 1 (assertion fails), proving `provision?` returns `true` even though `repository.review_stacks_enabled == false`, i.e. the equality `provision? == (review_stacks_enabled && behavior_matches)` is broken. After applying the recommended fix, the test passes (no stack created), restoring the intended binding.
