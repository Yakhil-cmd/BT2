### Title
Unscoped `Commit.where(sha:)` lookup in `StatusHandler#process` lets a status delivered for one repository mutate CI state on any other stack that happens to share the same commit SHA - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` resolves the target `Commit` records purely by bare SHA, with no scoping to the repository/stack that GitHub actually authenticated the webhook for. Because `Shipit::WebhooksController#verify_signature` verifies signatures per-organization (not per-repository), any webhook legitimately delivered for one repository under a trusted organization can write a `Status` (e.g. `context: "ci/smoke"`) onto a `Commit` belonging to a completely different stack, provided the two repositories happen to share that SHA (e.g. one is a fork/mirror of the other within the same org). If the victim stack has `merge_queue_enabled: true` and requires `ci/smoke`, this write can flip `MergeRequest#all_status_checks_passed?`/`any_status_checks_failed?`, causing `ProcessMergeRequestsJob` to call `MergeRequest#merge!` on the victim stack.

### Finding Description
The broken invariant, stated as an equality that should hold and does not:
`Status.create(context: "ci/smoke").stack_id == authenticated_repository.stack_id` — this is false in general.

Trace:
- `Shipit::WebhooksController#verify_signature` scopes trust to `Shipit.github(organization: repository_owner)` where `repository_owner = params.dig('repository','owner','login')` [1](#0-0) [2](#0-1) . This authenticates that the payload came from *some* repository owned by that GitHub organization/app installation — it does not bind the payload to the specific repository named in it, nor to any particular Shipit `Stack`.
- Once verified, `WebhooksController#create` just dispatches `params` to the registered handler for the event, with no repository/stack filtering [3](#0-2) .
- `Webhooks.for_event('status')` routes to `Handlers::StatusHandler` [4](#0-3) .
- `StatusHandler#process` does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` — a **global** lookup by bare SHA across every stack in the database, with no `repository`/`stack` filter at all [5](#0-4) .
- `Commit#create_status_from_github!` creates a `Status` row tied to that commit's own `stack_id` [6](#0-5) , and `Status#after_create`/`after_commit` callbacks immediately enable CI on the stack and schedule continuous delivery / broadcast the update [7](#0-6) .
- If that stack's `merge_queue_enabled` is true, `MergeRequest.schedule_merges` / `ProcessMergeRequestsJob#perform` re-evaluates pending merge requests, calling `merge_request.all_status_checks_passed?` (built from `StatusChecker` over `head.statuses_and_check_runs`) and, if green, `merge_request.merge!`, which calls `stack.github_api.merge_pull_request` [8](#0-7) [9](#0-8) [10](#0-9) .

Exploit flow: an attacker with ordinary write access to some repository `B` that shares GitHub App/webhook-secret scope with the victim's organization (e.g. an in-org fork/mirror of the victim's repo `A`, sharing git history/SHAs) posts (or has GitHub deliver) a `status` event for repo `B` with `context: "ci/smoke"`, `state: "success"`, and a `sha` that is also present in the victim stack `A`'s commit history (inherited via the fork). The webhook passes `verify_signature` because it is a genuine, correctly-signed event for organization-owned repo `B`. `StatusHandler#process` then finds and updates the `Commit` row belonging to stack `A` as well (since `Commit.where(sha:)` is unscoped), flipping CI green on stack `A`'s head and triggering `merge!`.

Existing guards do not stop this: `verify_signature` only proves "some repo in this org sent this", not "this repo owns this commit"; there is no `ExplicitParameters` repository check in `StatusHandler`'s `params do ... end` block [11](#0-10) ; and no model-level constraint ties a `Status`'s creation to the repository that authenticated the request.

### Impact Explanation
A payload authenticated for repository `B` writes a `Status` (and therefore green/red CI state) onto a `Commit` owned by stack `A`, a different tenant's stack, satisfying the "payload for one repository mutating another's stack/commit" Critical category. With `merge_queue_enabled: true` on the victim stack, this can directly trigger `MergeRequest#merge!`, i.e. an unauthorized merge on GitHub performed with the Shipit-held credentials for stack `A`'s repository — a real, repeatable, unauthorized merge/ship action. The blast radius is any pair of stacks/repositories in the same Shipit deployment whose commit histories overlap (forks, mirrors, template repos, monorepo splits) under the same GitHub org/app-installation trust boundary that `verify_signature` uses.

### Likelihood Explanation
Preconditions: (1) two repositories under the same trusted org/app-installation share at least one commit SHA (a very common situation for forks/mirrors/template repos), (2) the victim stack has `merge_queue_enabled: true` and requires the spoofed context, (3) the attacker has ordinary, unprivileged write/collaborator access to the non-victim repository (sufficient to have GitHub emit a real `status` event, e.g. via a CI integration or the commit-status API scoped to that repo). No Shipit secrets, sessions, or API tokens are needed — the attacker only needs GitHub to deliver one authentic webhook for a repo they already have legitimate access to. This is realistic and repeatable for any shared-history repo pair.

### Recommendation
Scope `StatusHandler#process` (and the analogous check-run/push handlers if similarly unscoped) to the repository named in the payload, not just the SHA — e.g. resolve `Repository` from `params.dig('repository', 'full_name')`/owner+name, then `Commit.joins(:stack).where(sha: params.sha, stacks: { repository_id: repository.id })`, and reject/no-op if the payload's repository does not match. Additionally consider making `verify_signature` bind to the specific repository (not just organization) where the app's installation model supports per-repository secrets.

### Proof of Concept
minitest plan (`test/models/webhooks/handlers/status_handler_test.rb` or similar, not authored here per scope rules but described):
1. Create `stack_a` (victim) with `merge_queue_enabled: true`, `cached_deploy_spec` requiring `ci/smoke`; create `commit_a` on `stack_a` with `sha: "deadbeef..."`; create a pending `MergeRequest` whose `head` is `commit_a`.
2. Create `stack_b` (attacker-controlled, different repository) and a `commit_b` on `stack_b` with the **same** `sha: "deadbeef..."` (simulating shared git history).
3. Build a `status` payload: `{ sha: "deadbeef...", state: "success", context: "ci/smoke" }` with `repository.owner.login` matching `stack_b`'s org (verified via stubbed `verify_signature`).
4. Call `Shipit::Webhooks::Handlers::StatusHandler.call(payload)` (or POST through the controller with signature stubbed true).
5. Assert both `commit_a.statuses.last.context == "ci/smoke"` and `commit_a.statuses.last.state == "success"` were created even though the payload's `repository` was `stack_b`'s, i.e. `commit_a.stack_id != stack_b.id` yet the status was written — proving the equality `Status.stack_id == authenticated_repository.stack_id` fails.
6. Assert `ProcessMergeRequestsJob` is enqueued for `stack_a` (via `commit.schedule_continuous_delivery`/hooks) and, with `merge_request.reload.all_status_checks_passed?` stubbed/true, that `merge_request.merge!` is invoked (or `stack_a.github_api` receives `merge_pull_request`), demonstrating the unauthorized merge trigger on the victim stack.

    def perform(stack)
      merge_requests = stack.merge_requests.to_be_merged.to_a
      merge_requests.each do |merge_request|
        merge_request.refresh!
        merge_request.reject_unless_mergeable!
        merge_request.cancel! if merge_request.closed?
        merge_request.revalidate! if merge_request.need_revalidation?
      end

      return false unless stack.allows_merges?

      merge_requests.select(&:pending?).each do |merge_request|
        merge_request.refresh!
        next unless merge_request.all_status_checks_passed?

        begin
          merge_request.merge!
        rescue MergeRequest::NotReady
          ProcessMergeRequestsJob.set(wait: 10.seconds).perform_later(stack)
          return false
        end
      end

    def merge!
      raise InvalidTransition unless pending?

      raise NotReady if not_mergeable_yet?

      stack.github_api.merge_pull_request(
        stack.github_repo_name,
        number,
        merge_message,
        sha: head.sha,
        commit_message: 'Merged by Shipit',
        merge_method: stack.merge_method
      )
      begin
        if stack.github_api.pull_requests(stack.github_repo_name, base: branch).empty?
          stack.github_api.delete_branch(stack.github_repo_name, branch)
        end
      rescue Octokit::UnprocessableEntity
        # branch was already deleted somehow
      end
      complete!
      true
    rescue Octokit::MethodNotAllowed # merge conflict
      reject!('merge_conflict')
      false
    rescue Octokit::Conflict # shas didn't match, PR was updated.
      raise NotReady
    end
