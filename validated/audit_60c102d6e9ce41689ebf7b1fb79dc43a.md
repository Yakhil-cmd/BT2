### Title
API token scoped to one stack can read CI/build status of any stack via CCMenu endpoint - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::BaseController` scopes API-client stack access via `stacks`/`stack` helpers that filter by `current_api_client.stack_id` when the client is stack-scoped [1](#0-0) . `Shipit::Api::CCMenuController` overrides `stack` with an unscoped lookup, `Stack.from_param!(params[:stack_id])`, bypassing that binding entirely [2](#0-1) .

### Finding Description
`ApiClient` records can be scoped to a single stack via the `stack_id` column, and `BaseController#stacks`/`#stack` enforce this scope: if `current_api_client.stack_id?` is true, only that stack is queryable [1](#0-0) . This is exactly how the `CCMenuUrlController` mints stack-scoped tokens for the CCMenu URL feature, e.g. `ApiClient.create_with(permissions: %w[read:stack]).find_or_create_by!(creator:, name: 'CCMenu Client')` associated with one particular `stack` [3](#0-2) , and matches the test fixture `here_come_the_walrus`, which is a `read:stack`-only client bound to the `shipit` stack [4](#0-3) .

However, `Shipit::Api::CCMenuController` defines its own `stack` method that calls `Stack.from_param!(params[:stack_id])` directly on the `Stack` class instead of the scoped `stacks` relation inherited from `BaseController` [2](#0-1) . The only authorization check performed is `require_permission :read, :stack`, which merely checks that the token's `permissions` array contains `"read:stack"` — it never checks whether the requested `stack_id` matches the token's bound `stack_id` [5](#0-4) .

This breaks the trust binding: **the stack a token authorizes (`ApiClient#stack_id`) ≠ the stack it touches (`params[:stack_id]` resolved via unscoped `Stack.from_param!`)**. Before the mismatch, `stack == current_api_client.stack` is guaranteed for any stack-scoped client hitting any other stack-aware API endpoint (e.g. `Api::StacksController`, `Api::DeploysController`, which use the inherited `BaseController#stack`) [1](#0-0) . After the mismatch, on `CCMenuController` specifically, `stack` can be any `Stack` in the installation regardless of the token's `stack_id`.

### Impact Explanation
A holder of a `read:stack`-scoped token restricted to one stack (the exact pattern generated by `CCMenuUrlController` for arbitrary web UI users) can query `GET /api/stacks/:stack_id/ccmenu.xml?token=...` for **any other stack**, exposing that stack's latest deploy/rollback status, lock state, and build metadata (`show` renders `deploys_and_rollbacks.last`) [6](#0-5) . This is unauthenticated-relative-to-target-stack disclosure of stack state/deploy output across repository boundaries, matching the "High" impact category of unauthorized read of stack state or deploy output.

### Likelihood Explanation
Any user who legitimately obtains a CCMenu token for one stack they have access to (via `CCMenuUrlController#fetch`, reachable by any authenticated Shipit user for any stack they can view) automatically gets a token that, due to this controller bug, works for every stack in the deployment, not just their own. No privilege beyond ordinary Shipit login and a legitimate CCMenu token for a single stack is required to enumerate other stacks' deploy state — the token itself is designed to be embedded in third-party CI status tools (CCMenu clients), increasing its exposure surface.

### Recommendation
Change `Shipit::Api::CCMenuController#stack` to use the inherited, scoped `stacks` relation (i.e., `stacks.from_param!(params[:stack_id])`) instead of the unscoped `Stack.from_param!(params[:stack_id])`, so the `ApiClient#stack_id` binding is honored the same way it is in `BaseController`.

### Proof of Concept
1. As a legitimate Shipit user, request a CCMenu URL for stack A: `GET /stacks/:A_stack_id/ccmenu_url` → returns a token scoped via `ApiClient.create_with(permissions: %w[read:stack])` bound to stack A [7](#0-6) .
2. Use that token against a different stack B that the user should not be able to query through this scoped token:
   `GET /api/stacks/B_stack_id/ccmenu.xml?token=<stack-A-scoped-token>`
3. Because `Api::CCMenuController#stack` resolves via `Stack.from_param!(params[:stack_id])` rather than the scoped `stacks` relation, the request succeeds and returns stack B's build/deploy status XML, even though the token's `ApiClient#stack_id` is stack A's id [2](#0-1) .
