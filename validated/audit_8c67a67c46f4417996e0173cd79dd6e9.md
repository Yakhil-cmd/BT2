Cross-organization membership write via `Team.find_or_create_by!(github_id:)` ignoring authenticated organization - ([File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`Shipit::WebhooksController#verify_signature` authenticates a webhook only against the `webhook_secret` configured for `repository_owner` (derived from `params.dig('organization','login')`), but `MembershipHandler#find_or_create_team!` looks up the target `Team` solely by `github_id`, without ever verifying that `params.organization.login` matches the pre-existing `team.organization`. Any org whose secret validated the request can therefore mutate the membership roster of an unrelated, pre-existing `Team` record simply by supplying its `github_id` in the payload.

### Finding Description
The broken binding: the value that authenticates the request is `repository_owner == params.dig('organization','login')` verified against `Shipit.github(organization: repository_owner).webhook_secret` [1](#0-0) [2](#0-1) . The value that is mutated is `Team#organization` on whichever `Team` row has `github_id == params.team.id` — and that equality is never checked against `params.organization.login` once the record already exists.

`find_or_create_team!` does:
```ruby
Team.find_or_create_by!(github_id: params.team.id) do |team|
  team.github_team = params.team
  team.organization = params.organization.login
end
``` [3](#0-2) 
The block that sets `team.organization` only executes on **creation**. If a `Team` with that `github_id` already exists (created previously through legitimate sync for e.g. `shopify/developers`), `find_or_create_by!` returns the existing record untouched, and `process` proceeds to call `team.add_member(member)` or `team.members.delete(member)` on it [4](#0-3) , regardless of which organization's secret authenticated the request.

`verify_signature` only checks that the HMAC matches the secret configured for `repository_owner`; it never re-checks that `repository_owner` and the eventual `team.organization` being mutated are the same value [5](#0-4) . `ExplicitParameters` (`params do ... end`) only validates shape/type of `team.id`, `organization.login`, `member.login`, not their consistency with each other [6](#0-5) .

Attacker flow: attacker administers an org ("attacker-org") that has been explicitly provisioned in Shipit's multi-org config (`secrets.github.<org>.webhook_secret`) — this is the only way for an org's secret to exist in Shipit at all, per `Shipit.github_app_config` / `Shipit.github` [7](#0-6) . Using that legitimately-known secret, the attacker signs a `membership` webhook with `organization.login = 'attacker-org'` but `team.id` equal to the numeric GitHub team ID of an existing, unrelated `shopify-developers` Team row. `verify_signature` succeeds (attacker-org's secret matches attacker-org's bytes) and `MembershipHandler` then adds `member.login` as a member of the pre-existing team belonging to `shopify`.

### Impact Explanation
`Shipit::Team` membership feeds directly into `User#authorized?`, which grants full application access when the user belongs to any team in `Shipit.github_teams` [8](#0-7)  and to `force_github_authentication` gating every controller action [9](#0-8) . An attacker who is an admin of one Shipit-configured organization can therefore grant an attacker-controlled GitHub identity membership in another organization's authorization-gating team, escalating into `Shipit.github_teams`-based authorization for a tenant they do not control. This is repeatable for any `github_id` the attacker can discover, is cross-tenant, and matches the "High: escalation into `Shipit.github_teams` authorization" impact category.

### Likelihood Explanation
Exploitation requires: (1) Shipit deployed in the multi-organization configuration (`secrets.github` keyed by org) with the attacker's org explicitly provisioned by the operator, giving the attacker a legitimate `webhook_secret` for their own org; (2) knowledge of the numeric GitHub `team.id` of the target team (team IDs are global GitHub identifiers, discoverable via the GitHub API for teams with visibility exposed to the attacker, or through prior legitimate interaction). Given those preconditions — which are realistic in any Shipit instance onboarding multiple customer/partner GitHub orgs — the attack costs only crafting one signed HTTP POST and is fully repeatable against any team whose `github_id` is known.

### Recommendation
In `find_or_create_team!`, after fetching or creating the `Team`, verify `team.organization.casecmp?(params.organization.login)` (and reject/log otherwise) before allowing `add_member`/`members.delete` to run; alternatively, scope the lookup itself with `Team.find_or_create_by!(github_id: params.team.id, organization: params.organization.login)` so a `github_id` collision across organizations cannot resolve to the wrong tenant's record.

### Proof of Concept
Minitest (`test/controllers/webhooks_controller_test.rb` style, ActionController::TestCase):
```ruby
test ":membership from one org cannot mutate another org's pre-existing team" do
  target_team = shipit_teams(:shopify_developers) # organization == 'shopify'

  @request.headers['X-Github-Event'] = 'membership'
  body = {
    action: 'added',
    team: { id: target_team.github_id, name: target_team.name, slug: target_team.slug, url: target_team.api_url },
    organization: { login: 'attacker-org' },
    member: { login: 'attacker-handle' },
    repository: { owner: { login: 'attacker-org' } }
  }.to_json

  # signature verified against attacker-org's own secret (stubbed as legitimately configured)
  GithubHook.any_instance.stubs(:verify_signature).returns(true)

  assert_no_difference -> { Team.count } do
    post :create, body:, as: :json
  end

  target_team.reload
  assert_equal 'shopify', target_team.organization  # binding claim: unchanged organization
  assert target_team.members.exists?(login: 'attacker-handle') # but membership was still written
end
```
Both sides of the equality to assert: `repository_owner` (`'attacker-org'`, the org that authenticated the request) vs `team.organization` (`'shopify'`, the org actually mutated) — the test demonstrates they diverge while the write still succeeds.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
