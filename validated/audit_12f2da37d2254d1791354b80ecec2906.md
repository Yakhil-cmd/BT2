### Title
Commit Status Webhook Handler Allows Cross-Repository Status Forgery - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`Shipit::WebhooksController#verify_signature` authenticates an incoming webhook only against the GitHub organization named in the payload's `repository.owner.login` (or `organization.login`) field, then dispatches the *entire* payload to the handler for the event type. For the `status` event, `StatusHandler` never re-checks that this authenticated organization/repository actually owns the commit being modified — it looks up the target purely by SHA across the whole `Commit` table, which spans every repository/stack ever registered on the Shipit instance. This breaks the trust binding: `organization that authenticated == repository that is written`.

### Finding Description
`WebhooksController#verify_signature` computes the signing secret from the payload itself: [1](#0-0) [2](#0-1) 

The secret used is `Shipit.github(organization: repository_owner)`'s webhook secret, i.e., whatever GitHub organization the attacker's own installed/whitelisted app belongs to (an organization the attacker legitimately controls in a multi-org Shipit deployment) — the signature only proves the payload was signed with *that* organization's secret, not that the organization actually owns the resource referenced elsewhere in the payload.

Once verified, the raw payload is forwarded unchanged to the handler: [3](#0-2) 

`StatusHandler` then processes it with **no repository scoping at all**: [4](#0-3) 

`Commit.where(sha: params.sha)` searches the entire `commits` table application-wide, independent of which stack/repository/organization the commit actually belongs to. Contrast this with other handlers (`PushHandler`, `CheckSuiteHandler`) that correctly scope lookups through `Handler#stacks`, which derives the target repository from `payload.dig('repository', 'full_name')`: [5](#0-4) [6](#0-5) 

`StatusHandler` has no equivalent check tying the SHA to a repository owned by the authenticating organization. Since GitHub commit SHAs are not secret (visible on any public repo, or knowable to any collaborator on a private one), any party that controls a legitimate, distinct GitHub organization configured in this Shipit instance's multi-org `Shipit.github` config can sign a forged `status` webhook using *their own* organization's webhook secret, but supply an `sha` belonging to a commit tracked under a completely different organization's stack.

### Impact Explanation
A forged/attacker-controlled `status` event with `state: 'success'` for a targeted commit SHA in a victim's repository directly rewrites that commit's CI status via `Commit#create_status_from_github!` (see `app/models/shipit/commit.rb`), which feeds into `Stack`/`Commit` deployability logic (`ci.require`) used to gate deploys. Forging a passing CI status on a commit that hasn't actually passed CI can make an otherwise non-deployable commit appear deployable, enabling an unauthorized deploy through the normal UI/API deploy flow — this satisfies the High-impact criterion of "escalation... enabling an unauthorized deploy."

### Likelihood Explanation
Exploitation requires: (1) a multi-organization Shipit deployment where the attacker legitimately controls at least one configured GitHub organization/app (a realistic deployment scenario per `config/secrets.development.example.yml`'s documented multi-org config), and (2) knowledge of a target commit SHA in another organization's tracked repository, which is generally public/non-secret information. No privileged Shipit session, `ApiClient` token, or GitHub App private key for the *victim* organization is required — only the attacker's own organization's webhook secret, which they legitimately possess.

### Recommendation
In `StatusHandler#process` (and any other handler that mutates state by identifiers not scoped to `repository.full_name`), constrain the lookup to commits belonging to the repository named in the authenticated payload, e.g.:
```ruby
def process
  stacks.flat_map(&:commits).select { |c| c.sha == params.sha }.each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
or equivalently join through `Repository.from_github_repo_name(repository_name)` before touching `Commit` records, mirroring the pattern already used by `Handler#stacks` in `app/models/shipit/webhooks/handlers/handler.rb`.

### Proof of Concept
1. Attacker legitimately configures/owns GitHub organization `attacker-org`, which is registered in this Shipit instance's `Shipit.github` multi-org configuration with webhook secret `S_attacker` (known to the attacker).
2. Attacker identifies a public commit SHA `deadbeef...` belonging to `victim-org/victim-repo`, which is tracked as a Stack in the same Shipit instance and has `ci.require` configured.
3. Attacker crafts a `status` webhook payload:
```json
{
  "sha": "deadbeef...",
  "state": "success",
  "context": "required-ci-context",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "attacker-org/whatever" }
}
```
4. Attacker signs the raw body with `S_attacker` and sets `X-Hub-Signature`, `X-Github-Event: status`, and POSTs to `/webhooks`.
5. `verify_signature` resolves `repository_owner` to `attacker-org` and successfully verifies against `S_attacker` [1](#0-0) .
6. `StatusHandler#process` runs `Commit.where(sha: 'deadbeef...')`, finds the victim's commit (unscoped by organization/repository), and marks it as `success` [4](#0-3) , satisfying `ci.require` for `victim-org/victim-repo` and enabling an unauthorized deploy of that commit.
