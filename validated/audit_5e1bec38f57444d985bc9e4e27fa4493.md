### Title
`i128` overflow in RAY-denominated debt valuation permanently freezes an oversized market - (File: common/src/rates/index.rs)

### Summary
Large borrow markets can reach an unrecoverable arithmetic overflow during ordinary interest accrual. `calculate_supplier_rewards` computes the old and new total debt as `borrowed * borrow_index` without constraining the resulting RAY value to the `i128` domain [1](#0-0) . Once `borrowed * borrow_index / RAY` exceeds `i128::MAX`, every market operation that synchronizes interest panics, leaving supply, cash and debt inaccessible.

### Finding Description
Pool state stores `borrowed` as RAY-scaled debt shares and `borrow_index` as a RAY-scaled index [2](#0-1) . Each accrual converts scaled debt back to its RAY-denominated value via `scaled_to_original`, which calls `Ray::mul` [3](#0-2) . `Ray::mul` performs checked `x * index / RAY` arithmetic and returns a checked `i128` result [4](#0-3) .

`accrue_step` calls `scaled_to_original` for market debt before applying the new index, then `calculate_supplier_rewards` multiplies the same scaled debt by both the old and new borrow indexes [5](#0-4) [1](#0-0) . Although `update_borrow_index` caps the index itself at `MAX_BORROW_INDEX_RAY`, that cap is only applied after the multiplication and does not bound the market’s total debt value [6](#0-5) . A sufficiently large debt position can therefore overflow the total-value multiplication while the stored index remains below its configured ceiling.

Every owner-mediated pool mutation first invokes `interest::global_sync` through `synced_market` or `renewed_market` [7](#0-6) . `global_sync` calls `accrue_chunk`, and `accrue_chunk` invokes the vulnerable `accrue_step` before committing updated indexes and revenue [8](#0-7) [9](#0-8) . Since Soroban reverts a panicking invocation, the partially updated cache cannot be committed and the market remains permanently stuck at the last successfully accrued state.

### Impact Explanation
The bug permanently freezes the affected `(hub_id, asset)` market. Suppliers cannot withdraw, borrowers cannot repay, liquidations and bad-debt cleanup cannot settle the market, flash and strategy paths cannot touch it, and even permissionless `update_indexes` cannot recover it because all these paths accrue first [10](#0-9) [11](#0-10) .

The repository’s own integration test demonstrates the failure and confirms that withdrawal and repayment both revert with `MathOverflow` after the accrual cliff is reached [12](#0-11) . User funds remain recorded in pool state but cannot be moved because the common arithmetic prerequisite panics.

### Likelihood Explanation
An unprivileged caller reaches the vulnerable path through `Controller::update_indexes`, which accepts a caller address and a vector of `HubAssetKey` values and forwards them to market accrual [13](#0-12) . The controller then invokes the owner-only pool `update_indexes` method [14](#0-13) , which calls `ops::market::accrue` and `global_sync` for each requested market [15](#0-14) [11](#0-10) .

Triggering requires a market whose RAY-valued debt approaches the `i128` result ceiling before `borrow_index` reaches `MAX_BORROW_INDEX_RAY`. The checked PoC uses an 18-decimal market supplied with one billion whole tokens and 98% utilization under a steep rate curve; repeated accrual overflows before the index cap engages [16](#0-15) . This is not a one-transaction overflow and requires an extremely large funded market plus long-term interest accrual, so it is less likely than an immediately triggerable overflow, but the resulting market freeze is permanent once reached.

### Recommendation
Bound accrual by the maximum representable market value rather than only by the index ceiling. Before evaluating the next accrual step, calculate the maximum `borrow_index` that keeps `borrowed * index / RAY <= i128::MAX` and clamp or stop accrual at that bound. The same saturated limit must be applied consistently to `new_total_debt`, `old_total_debt`, supplier rewards, supply-index updates and revenue calculations so accrual can safely become a no-op instead of panicking.

### Proof of Concept
1. Create an 18-decimal market using the steep `xlm_curve` parameters and permit the maximum asset cap.
2. Call `Controller::supply` to deposit `1_000_000_000 * 10^18` units into the market.
3. Fund another account with sufficient collateral and call `Controller::borrow` for 98% of that market’s liquidity.
4. Allow ledger time to advance under sustained high utilization, periodically calling `Controller::update_indexes(caller, vec![hub_asset])`.
5. Once `borrowed * borrow_index / RAY` exceeds `i128::MAX`, `scaled_to_original` panics inside `accrue_step`.
6. Subsequent `update_indexes`, `withdraw`, `repay`, liquidation and other market-mutating calls all reach `synced_market`/`global_sync` and revert before mutating or committing the market.

The checked harness test `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` implements this sequence and observes `MathOverflow` from `try_update_indexes_for`, `try_withdraw_raw`, and `try_repay` while `borrow_index` remains below `MAX_BORROW_INDEX_RAY` [17](#0-16) .

```rust
pub(crate) fn global_sync(env: &Env, cache: &mut Cache) {
    if !cache.needs_accrual() {
        return;
    }

    let mut remaining = cache.elapsed_ms();
    while let Some(nonzero) = NonZeroU64::new(remaining) {
        let chunk = nonzero.get().min(MAX_COMPOUND_DELTA_MS);

        remaining = remaining.saturating_sub(chunk);
    }
```

```rust
/// The cliff. A billion whole tokens is `1e36` raw ray; the value ceiling is
/// `i128::MAX`, 170 times that. At the XLM curve's steep segment the index
/// grows past 170x in a few years, and the next accrual panics inside
/// `scaled_to_original`. Every verb accrues first, so the market freezes:
/// no repay, no withdraw, no liquidation. The index cap never engages.
#[test]
fn a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap() {
    let mut t = LendingTest::new()
        .with_market(big("BIG18", 18, xlm_curve()))
        .with_market(col())
        .with_max_utilization_disabled_all_markets()
        .build();
    lift_caps(&t, "BIG18", 18);
    lift_caps(&t, "COL", 7);
    let principal = BILLION * 10i128.pow(18);
    t.supply_raw(BOB, "BIG18", principal);
    let debt = principal / 100 * 98;
    t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
    t.borrow_raw(ALICE, "BIG18", debt);

    let mut years = 0u32;
    let failure = loop {
        years += 1;
        assert!(
            years <= 40,
            "no cliff within 40 years; the bound in docs/reference/formulas.md is wrong"
        );
        t.advance_time(YEAR_SECS);
        if let Err(e) = t.try_update_indexes_for(&["BIG18"]) {
            break e;
        }
    };
    let failed: Result<(), soroban_sdk::Error> = Err(failure);
    assert_contract_error(failed, errors::MATH_OVERFLOW);
    let last = book(&t, "BIG18");
    assert!(
        last.borrow_index < MAX_BORROW_INDEX_RAY,
        "the index cap did not engage before the value overflow"
    );
    // The market is frozen: exits and repayments accrue first and hit the same panic.
    assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
    assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
```
