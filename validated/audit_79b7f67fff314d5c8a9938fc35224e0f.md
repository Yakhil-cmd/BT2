### Title
Webhook signature is verified against the organization named in `repository.owner.login`, but the event payload is dispatched to whatever repository/stack is named in `repository.full_name` / commit `sha` — decoupling the authenticating organization from the repository actually written - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/handler.rb`, `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`WebhooksController#verify_signature` picks the GitHub App/organization config (and therefore the `webhook_secret` used for HMAC verification) using a field extracted from the attacker-controlled JSON body (`repository.owner.login`, falling back to `organization.login`). Once the HMAC passes, the *entire* raw payload is handed to the event handlers, which resolve the actual target (`Stack`/`Repository`, or in the status case, a bare `Commit.where(sha:)` lookup with no repository scoping at all) from **other, independent fields of the same attacker-controlled body**. Nothing ties "the organization whose secret signed this request" to "the repository/stack the handler is about to mutate."

### Finding Description
`verify_signature` selects the signing organization like this: [1](#0-0) 

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
```

and [2](#0-1) 

`repository_owner` is just `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` — a value the requester fully controls inside the signed body.

After the signature check passes, dispatch happens over the raw, unfiltered `params`: [3](#0-2) 

Handlers then bind to a *different* field of the same body to determine what to act on. `Handler#stacks` uses `repository.full_name`: [4](#0-3) 

`StatusHandler` doesn't even use repository scoping — it resolves commits **instance-wide** purely by `sha`: [5](#0-4) 

Shipit explicitly supports multiple independently-configured GitHub organizations sharing one Shipit instance and one `/webhooks` endpoint, each with its own `webhook_secret`: [6](#0-5) 

**Before the attacker's request:** organization A's webhook secret authenticates only deliveries that GitHub itself generates for org A's repositories, whose body legitimately contains `repository.owner.login == "orgA"` and `repository.full_name` referring only to org‑A repos.

**After the attacker's request:** anyone who knows org A's `webhook_secret` (e.g. an org admin who configured/rotated it, or someone who obtained it through org A's own GitHub App settings — no Shipit session or `ApiClient` token required) can build an arbitrary JSON body, set `repository.owner.login = "orgA"` (or `organization.login = "orgA"`) so `verify_signature` picks org A's secret and the HMAC they compute over their own crafted body succeeds, while independently setting:
- `repository.full_name = "orgB/victim-repo"` for `push`/`check_suite` events, causing `Handler#stacks` to resolve and mutate a `Stack` that belongs to a completely unrelated organization B that the attacker has no relationship with, or
- an arbitrary `sha` for a `status` event, causing `StatusHandler` to write a fabricated CI status (`state`, `description`, `target_url`) onto **any commit in the entire Shipit instance**, regardless of which organization or repository it belongs to.

This is precisely the binding class called out in scope: "an organization that authenticated versus the repository that is written."

### Impact Explanation
This lets a party who is trusted only within one tenant organization (org A) of a shared, multi-org Shipit deployment forge webhook events that mutate state belonging to a different organization's stacks — a cross‑repository/cross‑tenant write with no Shipit credential, `ApiClient` token, or GitHub write access to the victim repository required. Concretely:
- `StatusHandler` lets the attacker inject a fabricated "success" CI status for any commit sha instance-wide, which can be used to satisfy Shipit's CI-gating logic that many teams rely on before enabling `continuous_deployment`/merge on a stack, effectively pushing a stack toward an unauthorized deploy decision using a status the real CI never produced.
- `PushHandler` lets the attacker cause `stack.sync_github(expected_head_sha:)` to run against a victim stack in another organization the attacker doesn't own, forcing an unsolicited sync/HEAD update on a stack outside their trust boundary.

### Likelihood Explanation
Any operator of a shared multi-org Shipit deployment who legitimately holds one organization's `webhook_secret` (a routine credential, not a Shipit privilege) can exploit this with a single crafted HTTP POST to the shared, unauthenticated `/webhooks` endpoint; no interaction with the victim organization or Shipit session is needed, and the vulnerable code path (`repository_owner` vs. `repository.full_name`/`sha`) is unconditionally reachable on every webhook delivery.

### Recommendation
After `verify_signature` selects `github_app` from `repository_owner`, re-derive and enforce that the same organization owns every repository referenced later in the payload before handlers act on it — i.e. bind the handler's `repository_name`/`sha` lookup to the already-authenticated `repository_owner`, and for `StatusHandler`, scope the `Commit.where(sha:)` lookup to commits whose stack's repository owner matches the organization that signed the request.

### Proof of Concept
1. Attacker legitimately controls org A and its `webhook_secret` (`someorg-secret`) on a shared Shipit instance also serving org B.
2. Attacker builds:
```json
{
  "repository": { "owner": { "login": "orga" }, "full_name": "orgb/victim-repo" },
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>"
}
```
3. Attacker computes `X-Hub-Signature: sha1=<hmac-sha1(body, "someorg-secret")>` and POSTs to `/webhooks` with `X-Github-Event: push`.
4. `verify_signature` loads `Shipit.github(organization: "orga")`, verifies the HMAC successfully (attacker knows org A's secret), and the request proceeds.
5. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("orgb/victim-repo")` [4](#0-3)  and enqueues `stack.sync_github(expected_head_sha: params.after)` for org B's stack, even though org B never authorized this request.
