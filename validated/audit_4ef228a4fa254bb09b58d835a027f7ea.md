Confirmed: AAs can post `data_feed` app messages themselves [1](#0-0) , and an unprivileged unit poster fully controls the oracle address list passed to `data_feed[[oracles=...]]` — there is no requirement that the oracle be a pre-trusted/whitelisted address, only that it be a syntactically valid address [2](#0-1) . ### Title
Single-poster manipulation of unstable/self-controlled `data_feed` oracle values used by AAs for immediate financial decisions - (File: `data_feeds.js`)

### Summary
`data_feed[[oracles=..., feed_name=...]]` in oscript is designed to let an AA read the *latest* value posted to a data feed by an address it treats as an oracle. When invoked from AA (`bAA`/`unstable_opts` truthy), `readDataFeedValue()`/`dataFeedExists()` will also scan `storage.assocUnstableMessages` — data-feed messages contained in units that are posted but not yet stable/final — and use the newest one it finds [3](#0-2) . Because any address (including the trigger sender's own address or an AA the attacker just deployed) can serve as the "oracle" parameter, and because an AA is itself permitted to emit `data_feed` messages [4](#0-3) , an unprivileged actor can post a `data_feed` value and have it consumed by a target AA's formula evaluation before that value is stable/finalized on the DAG — the exact analog of reading a manipulable, single-sample "spot price" instead of a time-weighted/finalized value, as flagged in the original Uniswap-price report.

### Finding Description
The root cause mirrors the external report's core complaint: a financial decision inside protocol logic (there, `rebalance()`; here, any AA case guarded by `data_feed[[...]]` or `in_data_feed[[...]]`) is gated on a single, freshly-posted, unconfirmed value rather than a finalized/aggregated one.

- `readDataFeedValue()` accepts an `unstable_opts` flag; when set (as it is for AA formula evaluation, passed as `bAA` at the call site in `formula/evaluation.js`) it first searches `storage.assocUnstableMessages` for `data_feed` messages from matching author addresses whose owning unit is merely "good" sequence, not necessarily stable [5](#0-4) [6](#0-5) .
- If exactly one unstable candidate exists and `ifseveral==='last'` (the default), that unconfirmed value is returned immediately to the AA without waiting for stabilization [7](#0-6) .
- The `oracles` parameter is validated only for being a syntactically-correct address list, not for being a trusted/whitelisted oracle [2](#0-1) ; an AA author frequently parameterizes it with `this_address` or `trigger.address`, as shown in the shipped sample AAs that read `data_feed[[oracles='X55IWSNMHNDUIYKICDW3EOYAWHRUKANP', feed_name=...]]` to drive payout/blackswan/exchange-rate logic [8](#0-7)  and [9](#0-8) .
- Any account (including the attacker's own address or a freshly-deployed helper AA — no privilege required) can post a `data_feed` message, since data-feed posting has no special ACL, only length/format checks [10](#0-9) .

By chaining "post a manipulated data_feed value from an address the target AA is configured to trust" with "immediately trigger the target AA while that value is still unstable," an attacker reproduces the report's core exploit chain: force an immediate, favorable state transition in a target AA (mint/redeem/payout/rebalance-like branch) based on an ephemeral, self-controlled or freshly-posted value, then reverse the value afterward, exactly as step 1–5 of the PoC in the external report describes for Uniswap spot price.

### Impact Explanation
If an AA's economic logic (asset issuance, collateral payout, "winner"/blackswan branching, bond conversion, etc., as in the sample contracts `futures_contract.oscript`/`option_contract.oscript`) keys off `data_feed[[...]]`/`in_data_feed[[...]]` reads that resolve to unstable, single-sample values, an attacker can:
- mint/withdraw assets at a manipulated, momentary rate before the true/stable value is available, and
- immediately unwind by reposting the correct/opposite value,
extracting value from the AA balance — analogous to the High-severity fund-loss impact ("buy/sell collateral at manipulated price") in the source report. This is an AA-fund-loss/drain class issue reachable purely by an unprivileged trigger sender and AA definition author (no privileged node/oracle access needed), matching the required "AA fund loss" impact bar.

### Likelihood Explanation
Likelihood is Medium-High for any AA design that (a) treats an address supplied by the trigger sender (or the trigger sender's own address) as an oracle, or (b) relies on `ifseveral='last'` semantics without enforcing `min_mci`/stability. This is a known, documented pattern in the shipped sample AAs shown above, meaning it is a realistic, foreseeable usage rather than a contrived edge case; the "unstable" read path is core protocol behavior (`readDataFeedValue`), not a bug isolated to one contract.

### Recommendation
- For AA data-feed reads intended for financial decisions, require oracle addresses to be immutable/hard-coded in the AA definition (never derived from `trigger.address`/`trigger.data`), and disallow using the AA's own or the trigger sender's address as an oracle.
- Prefer requiring `min_mci` bounds and stable-only reads (avoid relying on the unstable-candidate fast path in `readDataFeedValue()` at `data_feeds.js:211-249`) for any branch that moves funds.
- Document/guide AA authors to use TWAP-style aggregation (e.g., require N consecutive feed posts over a time window, or median-of-several) instead of trusting the single "last" value, mirroring the report's original recommendation to prefer TWAP over spot price.

### Proof of Concept
1. Attacker deploys/uses a target AA that reads `data_feed[[oracles="{trigger.address}", feed_name="price"]]` to compute payout ratios (pattern demonstrated in `test/samples/futures_contract.oscript:88-93` and `option_contract.oscript:64`).
2. Attacker posts a unit containing a `data_feed` message with a favorable `price` value from their own address.
3. In the same DAG neighborhood (before the data-feed unit stabilizes), attacker posts the AA trigger unit; because AA evaluation uses the unstable-read path in `readDataFeedValue()` (`data_feeds.js:205-285`), the target AA consumes the still-unstable, attacker-supplied value.
4. AA emits payment/asset messages based on this manipulated value, transferring value to the attacker.
5. Attacker reposts the "true" value (or lets the manipulated unit become final-bad/be orphaned) to hide the manipulation, mirroring "reverse the prices" step of the original report.
