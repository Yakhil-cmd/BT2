### Title
Cross-Organization Status Injection via Decoupled Webhook-Signature-Key Selection vs. Commit-Write Scope - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`WebhooksController#verify_signature` selects which organization's GitHub App/webhook secret to use for HMAC verification based on `repository.owner.login` (or `organization.login`) taken from the *unverified* JSON payload, then hands the *entire, unmodified* payload to the event handler after verification succeeds. `Shipit::Webhooks::Handlers::StatusHandler`, however, does not use `repository.owner.login`/`repository.full_name` at all when deciding what to write — it looks up `Commit.where(sha: params.sha)` globally across every stack in the installation and writes attacker-supplied `state`/`description`/`target_url`/`context` directly onto it. The organization whose key authenticated the request and the repository/commit that is actually mutated are two independent, uncorrelated fields of the same untrusted payload — exactly the "authenticated organization vs. repository written" binding break called out in the analog rules.

### Finding Description
`app/controllers/shipit/webhooks_controller.rb`:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end

`lib/shipit/github_app.rb#verify_webhook_signature` trivially passes when the resolved organization's app has no `webhook_secret` configured:

This is a documented, supported configuration state — the templated multi-org secrets files ship with `webhook_secret: # nil` by default: [3](#0-2) [4](#0-3) 

Once `verify_signature` passes (using whichever org's app config `repository_owner` resolved to), `params` — the raw, attacker-controlled JSON body — is dispatched unchanged to the event handler:
```ruby
def create
  params = JSON.parse(request.raw_post)
  Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }
  head(:ok)
end
``` [5](#0-4) 

`StatusHandler#process` never checks `repository.owner.login`, `repository.full_name`, or any tenant/org scoping — it resolves the target purely by commit SHA, which is global across all stacks/repositories/organizations configured in the Shipit instance, and writes attacker-supplied fields directly:
```ruby
class StatusHandler < Handler
  params do
    requires :sha, String
    requires :state, String
    accepts :description, String
    accepts :target_url, String
    accepts :context, String
    accepts :created_at, String
    ...
  end

  def process
    Commit.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
end
``` [6](#0-5) 

`create_status_from_github!` → `Status#replicate_from_github!` persists the attacker-chosen `state` (`pending`/`success`/`failure`/`error`) as a real `Status` row: [7](#0-6) [8](#0-7) 

Creating a `Status` triggers `schedule_continuous_delivery` and merge-request re-evaluation once the commit's aggregate state reaches `success`/`pending`: [9](#0-8) 

The **binding that should hold** is:
`organization authenticated by verify_signature (repository_owner)` == `organization/repository whose data is mutated by the handler`.

**Before the PR/attack**: for a legitimate webhook, GitHub signs the payload with the secret of the same org/repo whose data the handler updates, so the two sides of the equality always match.
**After an attacker-crafted request**: `repository_owner` is set to any organization configured in `Shipit.github` that has no `webhook_secret` (or whose secret the attacker otherwise satisfies), while `sha` is set to a real commit belonging to an entirely different, unrelated stack. `verify_signature` passes because it only checks the *first* org's config; `StatusHandler` then writes to the *second*, unrelated stack's commit. The equality is broken with no credential belonging to the second org required at all.

### Impact Explanation
This allows an unprivileged remote attacker (no session, no `ApiClient` token, no GitHub credential for the target repository) to inject fabricated CI status entries — including `state: "success"` — onto arbitrary commits of any stack tracked by the Shipit instance, as long as they can guess/observe a real commit SHA (commit SHAs are typically public on GitHub) and as long as any one organization configured in the instance omits a `webhook_secret` (a documented default configuration). Because commit status creation drives `schedule_continuous_delivery` and `ProcessMergeRequestsJob`, this can result in an **unauthorized deploy** of a commit that never actually passed CI/required checks on GitHub, satisfying the "unauthorized deploy" Critical-impact criterion.

### Likelihood Explanation
Likelihood is contingent on the specific deployment having at least one configured GitHub organization without a `webhook_secret` — which the project's own example/template configs (`config/secrets.development.example.yml`, `test/dummy/config/secrets_double_github_app.yml`) show as the out-of-the-box default. Given that, exploitation requires only crafting an HTTP POST to `/github/webhooks` with a `X-Github-Event: status` header and a JSON body containing a known target `sha` and a spoofed `repository.owner.login`; no authentication artifact tied to the target repository/organization is needed.

### Recommendation
Bind the organization/repository resolved during signature verification to the same organization/repository the handler is permitted to mutate — e.g., pass the verified `repository_owner`/`repository.full_name` explicitly into `Handler.call` and have `StatusHandler` (and any other handler that looks up records by cross-tenant-ambiguous keys such as `sha`) scope its `Commit`/`Stack` lookup to that verified repository instead of a global `Commit.where(sha:)`. Additionally, require `webhook_secret` to be present for every configured GitHub App/organization (fail closed rather than fail open when absent).

### Proof of Concept
1. Configure Shipit with two organizations in `secrets.github`: `OrgA` (no `webhook_secret` set — matches documented default) and `OrgB` (tracks a real, sensitive stack, e.g. `orgb/prod-app`).
2. Attacker sends:
```
POST /github/webhooks
X-Github-Event: status
Content-Type: application/json

{
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgA/whatever" },
  "sha": "<real sha of a commit on orgb/prod-app>",
  "state": "success",
  "context": "ci/required-check",
  "description": "forged",
  "target_url": "https://attacker.example"
}
```
3. `repository_owner` resolves to `"OrgA"`; `Shipit.github(organization: "OrgA")#verify_webhook_signature` returns `true` immediately because `OrgA`'s `webhook_secret` is blank [10](#0-9) .
4. `StatusHandler.call(params)` executes, finds the commit by `sha` regardless of organization, and creates a `Status` with `state: "success"` on the `orgb/prod-app` commit [11](#0-10) .
5. If `orgb/prod-app`'s stack has continuous deployment/merge automation gated on that status context, this fabricated success can trigger an unauthorized deploy or merge.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

      end
