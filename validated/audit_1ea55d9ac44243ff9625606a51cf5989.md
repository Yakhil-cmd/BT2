### Title
Webhook signature is validated against the organization named in the payload, not the organization that actually owns the referenced repository - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App's `webhook_secret` to validate the HMAC signature against by reading `repository.owner.login` (or `organization.login`) out of the *same untrusted JSON body* it is about to validate. [1](#0-0)  The handlers invoked afterward, however, locate the `Stack`/`Repository` to act on using a *different* field from that same body: `repository.full_name`. [2](#0-1)  Nothing ties `repository.owner.login` (used for authentication/secret selection) to `repository.full_name` (used for the actual write). This is the same class of bug as the reported Solana issue: two fields that are supposed to represent "the same" resource (the account that authorizes vs. the account that is acted on) are validated independently, so an attacker who legitimately controls one binding can substitute the other.

### Finding Description
`Shipit.github(organization: repository_owner)` in `verify_signature` picks the `GitHubApp` (and therefore the `webhook_secret`) purely from `repository.owner.login`/`organization.login` inside the incoming payload. [3](#0-2)  Anyone who has created their own GitHub App/organization integrated with this Shipit instance (a fully unprivileged, self-service action documented in `docs/setup.md`'s "Using Multiple GitHub Applications" section) knows their own `webhook_secret` and can therefore produce a raw JSON body and a valid HMAC-SHA1 signature for it, because `verify_webhook_signature` only checks `HMAC(webhook_secret_of_repository_owner, raw_body)`; it does not check that any other field of the body is consistent with that organization. [4](#0-3) 

Once the signature check passes, `WebhooksController#create` dispatches the *entire* parsed payload to the registered handlers for the event type, with no further binding to the organization that was used for verification. [5](#0-4)  Handlers such as `PushHandler`, `StatusHandler`, and all `PullRequest::*Handler`s resolve the target `Repository`/`Stack` using `payload.dig('repository', 'full_name')`, completely independent of `repository.owner.login`. [2](#0-1) [6](#0-5) [7](#0-6) 

So the equality that should hold is:
`organization whose secret validated the request == organization that owns the repository being written to`

but the code only enforces:
`organization whose secret validated the request == repository.owner.login (attacker-controlled field in the same unauthenticated body)`

An attacker who owns `attacker-org` (with its own registered GitHub App/webhook secret in Shipit's multi-org config) can craft a payload with `repository.owner.login = "attacker-org"` (so the correct/known secret is selected for signing) but `repository.full_name = "victim-org/victim-repo"` (an arbitrary tracked stack). Because the two fields are never cross-checked, the forged, self-signed webhook is accepted and dispatched against the victim repository's stack.

### Impact Explanation
Depending on the event type this enables an unprivileged outsider (anyone able to register their own GitHub org/app against the shared Shipit instance, or with webhook access to just one tracked org) to act against completely unrelated repositories tracked by the same Shipit instance:
- `push` events trigger `stack.sync_github(expected_head_sha:)` for the victim stack via `PushHandler`, letting the attacker force a resync onto an attacker-chosen `expected_head_sha` for a repo they don't own. [8](#0-7) 
- `status` events let the attacker inject fabricated CI statuses (`commit.create_status_from_github!`) for any commit SHA in the system, independent of which org's secret signed the payload. [9](#0-8)  Since Shipit's merge/deploy safety checks (`required_statuses`, `release_status_context`, etc.) rely on these Status records, forging a "success" status for a victim commit can unblock or bypass required CI checks on merges/deploys they don't control.
- `pull_request` handlers (`opened`, `labeled`, `closed`, etc.) create/archive/unarchive review stacks for the victim repository based purely on the forged `repository.full_name`. [10](#0-9) 

Because forged/fabricated commit statuses can be used to satisfy `required_statuses`/`release_status_context` gates that Shipit's merge queue and deploy flow rely on to authorize a merge/deploy, this can escalate to an **unauthorized deploy or merge** for a stack the attacker does not control — matching the Critical impact bar in scope.

### Likelihood Explanation
Exploitability requires only that the attacker be able to register a second GitHub App/organization against the shared Shipit instance (a documented, self-service multi-tenant configuration path, `docs/setup.md`), or otherwise learn/possess one org's `webhook_secret`; no repository write access, API token, or session on the victim side is needed. The attack is a single crafted HTTP POST to the public webhooks endpoint. This requires the instance to be running in the multi-organization configuration mode (`Shipit.github_organizations`), which is a supported, documented deployment shape, not a misconfiguration.

### Recommendation
After selecting the `GitHubApp`/secret by `repository_owner`, verify that the same field (or the actual `login` associated with the app/org used) matches the owner segment of every `repository.full_name`/`organization.login` referenced anywhere the payload is subsequently used, or resolve the target repository strictly from the verified organization context instead of trusting the payload's `full_name` in isolation. Concretely: pass the verified `repository_owner`/organization into `Handler#stacks`/`#repository_name` and assert equality with the owner segment of `full_name` before any handler acts, rejecting mismatches with `422`.

### Proof of Concept
1. Configure Shipit with two GitHub orgs, `attacker-org` and `victim-org`, each with their own `webhook_secret` (multi-org mode as documented).
2. Attacker (who only controls `attacker-org`, knows only its `webhook_secret`) builds a JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "deadbeef...attacker-chosen-sha",
  "repository": {
    "full_name": "victim-org/victim-repo",
    "owner": { "login": "attacker-org" }
  }
}
```
3. Attacker computes `sha1=HMAC(attacker-org.webhook_secret, body)` and sends it as `X-Hub-Signature` with `X-Github-Event: push` to `POST /webhooks`.
4. `verify_signature` calls `Shipit.github(organization: "attacker-org")` and successfully verifies the signature (attacker knows this secret). [1](#0-0) 
5. `create` dispatches to `PushHandler`, which resolves `stacks` via `Repository.from_github_repo_name("victim-org/victim-repo")` and calls `stack.sync_github(expected_head_sha: "deadbeef...")` on the victim's stack — despite the attacker never having proven any relationship to `victim-org`. [8](#0-7) [2](#0-1)

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
