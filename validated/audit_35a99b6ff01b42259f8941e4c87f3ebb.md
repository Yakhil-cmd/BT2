### Title
Escrow shared address for private assets in arbiter contracts has no self-enforcing release path and permanently freezes funds if the counterparty and arbiter both withhold cooperation - (File: arbiter_contract.js)

### Summary
The `arbiter_contract` module builds a shared (multi-sig) address whose spending conditions are meant to let either the offeror or the acceptor unilaterally settle a private-asset escrow, but the actual "unilateral" branches require an action from the *other* party (a data-feed confirmation), and the fallback path requires the arbiter to post a data-feed resolution. If both the counterparty and the arbiter withhold that cooperation, the escrowed private-asset funds have no other spending path and are frozen forever, mirroring the "authority withholds signature ⇒ user can never move funds" pattern from the Infinex report.

### Finding Description
`deriveSharedAddress()` builds the shared-address `arrDefinition` as an `or` of five branches: mutual agreement, two "unilateral completion" branches, and two arbiter-resolution branches. [1](#0-0) 

For public assets, the "unilateral" branches are truly self-enforcing: either party can spend by posting a transaction that simply pays the agreed amount to the counterparty (`has output`), with no cooperation required from the counterparty. [2](#0-1) 

For **private assets**, however, the same branches are rewritten to require an `in data feed` confirmation, posted by the *other* party, before either side can spend: [3](#0-2) 

This means: for offeror to withdraw, the acceptor must actively post `CONTRACT_DONE_<hash>=offeror_address`; for acceptor to withdraw/refund, the offeror must post the mirror message. Neither party can move funds unilaterally with a private asset - they depend entirely on the other's willingness to post a data-feed message.

The only remaining branches are the arbiter-resolution branches, which similarly require the `arbiter_address` to post a `data_feed` message naming the winner (`CONTRACT_<hash>=<winner_address>`), consumed in `parseWinnerFromUnit()`: [4](#0-3) 

A dispute can be opened unilaterally via `openDispute()`, which forwards the dispute to the arbstore/arbiter, but resolution is entirely at the arbiter's discretion - there is no timeout, no automatic default resolution, and no other path back to either party's own address: [5](#0-4) 

Searching the file confirms `ttl` is only used to expire a *pending, unaccepted* offer before a shared address is even created; it plays no role once funds are locked in the shared address, so there is no time-based fallback to release the escrow. [6](#0-5) 

Consequently, once funds are paid into the private-asset shared address (`pay()` → `sendMultiPayment` to `shared_address`), the only ways out are: (1) mutual signature, (2) counterparty posts the completion data feed, or (3) the arbiter posts a resolution data feed. If the counterparty simply goes silent/refuses to cooperate and the arbiter also withholds a decision (whether by malice, unavailability, or dispute with the arbstore service), the funds are permanently and irrecoverably locked in the shared address, exactly analogous to the Infinex pattern where an administrator-controlled signer that withholds cooperation blocks a user from ever moving their own funds. [7](#0-6) 

### Impact Explanation
Private-asset funds sent into an arbiter-contract escrow address can be permanently frozen with no possible on-chain recourse for the paying/receiving user if the counterparty refuses to post the completion data feed and the arbiter withholds (or is unable to provide) a dispute resolution. This is a full, permanent loss of access to escrowed funds - equivalent in severity to the "AA fund loss or freezing" class called out in the validation rules.

### Likelihood Explanation
Any private-payment counterparty entering an arbiter contract (a normal, unprivileged usage flow reachable by ordinary wallet users through `wallet_defined_by_addresses`/`arbiter_contract`) is exposed. The counterparty need only refuse to post the `CONTRACT_DONE_*` data feed (a unilateral choice fully within their control, with no incentive to cooperate once they've received/withheld value), and the arbiter need only decline or fail to resolve a dispute. No special privileges or race conditions are needed - it is a straightforward, always-available refusal path.

### Recommendation
Add a self-enforcing fallback for private-asset arbiter contracts analogous to the public-asset "has output" branches, e.g., a timeout-based branch (using `min_mci` in `in data feed`/other timelock-style oscript conditions) that allows either party to reclaim funds unilaterally after a defined period if neither the counterparty nor the arbiter has acted, so that withheld cooperation from a counterparty or arbiter can never result in permanent fund freezing.

### Proof of Concept
1. Alice (offeror) and Bob (acceptor) enter a private-asset arbiter contract; Alice pays the agreed amount into the derived `shared_address` per `pay()`. [7](#0-6) 
2. The deal goes bad; Bob refuses to ever post the `CONTRACT_DONE_<hash>` data-feed message that would let Alice reclaim/complete, and also refuses to sign a mutual settlement.
3. Alice calls `openDispute()` to escalate to the arbiter. [5](#0-4) 
4. The arbiter (or arbstore operator) never posts a `CONTRACT_<hash>` data-feed resolution (offline, uncooperative, or simply refuses).
5. None of the five `or` branches in the shared-address definition can be satisfied - Alice's funds in `shared_address` are permanently unspendable. [8](#0-7)

	getByHash(hash, function(objContract) {
		if (!objContract.shared_address || objContract.status !== "signed" || !objContract.me_is_payer)
			return cb("contract can't be paid");
		var opts = {
			asset: objContract.asset,
			to_address: objContract.shared_address,
			amount: objContract.amount,
			spend_unconfirmed: walletInstance.spendUnconfirmed ? 'all' : 'own'

		if (arrSigningDeviceAddresses.length)
			opts.arrSigningDeviceAddresses = arrSigningDeviceAddresses;

					db.query("INSERT "+db.getIgnore()+" INTO my_watched_addresses (address) VALUES (?)", [objContract.peer_address]);
			});

function parseWinnerFromUnit(contract, objUnit) {
	if (objUnit.authors[0].address !== contract.arbiter_address) {
		return;
	}
	var key = "CONTRACT_" + contract.hash;
	var winner;
	objUnit.messages.forEach(function(message){
		if (message.app !== "data_feed" || !message.payload || !message.payload[key]) {
			return;
		}
		winner = message.payload[key];
	});
	if (!winner || (winner !== contract.my_address && winner !== contract.peer_address)) {
		return;
	}
	return winner;
}
