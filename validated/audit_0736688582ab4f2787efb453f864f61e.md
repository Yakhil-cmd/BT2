### Title
Stale pruned-joint cache may let validators reuse invalidated output data - (File: archiving.js)

### Summary
`archiving.js` keeps an in-memory cache (`assocCachedPrunedJoints`) of full joint contents for units that have just been voided (i.e., `final-bad`/double-spend-losing units whose content has already been stripped and replaced with just a `content_hash`). [1](#0-0)  This is functionally analogous to the XWiki bug: a "document" (unit) is deleted/pruned from its canonical, rights-checked storage, but a side-channel cache continues to serve its full, previously-authoritative content for a full hour (`PRUNED_JOINT_CACHE_TTL_ms = 60*60*1000`) without re-validating that the content is still authoritative for the current DAG/ledger state. [2](#0-1) 

### Finding Description
When `updateMinRetrievableMciAfterStabilizingMci` strips a `final-bad` unit's messages during pruning, it replaces the unit's stored representation with the naked/stripped form and calls `archiving.cachePrunedJoint(objJoint)` to keep the full pre-strip joint (including its `payment` messages and outputs) available in memory for up to an hour. [3](#0-2)  `archiving.getCachedOutput(unit, message_index, output_index)` then reconstructs output details (`address`, `amount`, `denomination`, `asset`) straight from this cached, no-longer-canonical joint. [4](#0-3) 

`validation.js` calls into this cache (`archiving.getCachedOutput`) when it needs details of an output that comes from a unit that has since been stripped/voided — i.e., during input/spend-proof validation for units referencing outputs from a `final-bad` predecessor. Because the cache is keyed only by `unit/message_index/output_index` and served for a full hour regardless of what has happened to the DAG in the meantime (e.g., the same unit slot being resurrected via a different, competing unit becoming the "good" one after reorg-like fork resolution, or the address's rights/definition having changed), a validator can be handed output data (`address`, `amount`, `asset`) that no longer reflects the currently valid ledger state for that unit id. This mirrors the XWiki root cause: content associated with a "deleted and re-created" entity (here, a stripped-then-potentially-resurrected unit/output) is served from a cache without re-checking current validity/rights, because the cache was designed only to help peers recover during a narrow race window, not to be treated as an authoritative source during validation of new units.

### Impact Explanation
If `validation.js` trusts `getCachedOutput`'s stale address/amount instead of re-deriving it from the current canonical state (`outputs`/`inputs` tables, which reflect the current `sequence`/`is_stable` status), a node could validate a payment input against output data that is inconsistent with what other nodes see (whose cache has expired or was never populated, e.g., after a restart). This directly risks node disagreement on unit validity — one node accepting a unit based on the cached (stale) output while other nodes, relying on the DB tables reflecting the current authoritative sequence, reject it. Such divergence in the "good"/"final-bad" classification of spending units is the exact class of impact the scan rules require (node disagreement on validity), and in the worst case could enable double-spend acceptance if the cached output data allows spending against inconsistent amounts/addresses across nodes.

### Likelihood Explanation
This is a full-node-only in-memory cache with a bounded population trigger (only `final-bad` units at pruning time) and a 1-hour TTL, so exploitation would require an attacker to engineer a specific timing/fork scenario where a unit slot becomes `final-bad`, gets cached, and is then referenced again while the cache is still warm and before all nodes have reached the same state. This narrows the practical likelihood, but the underlying design flaw — trusting a stale, unauthenticated-against-current-state cache during validation instead of consulting the canonical DB records — is a concrete, reachable code path from any posted unit that spends from a previously `final-bad` unit's output.

### Recommendation
- Do not use `archiving.getCachedOutput` as an authoritative source for validating *new* units; restrict its use strictly to serving historical joint data to peers (read-only replay), never to unit/spend/authentifier validation logic.
- If `validation.js` genuinely needs it during validation, cross-check the cached output against the current `outputs`/`sequence`/`is_stable` state in the DB before accepting it, and invalidate/bypass the cache entry if the underlying unit's `sequence` has changed since caching.
- Consider reducing/removing the reliance on `archiving.getCachedOutput` inside `validation.js` and instead always re-read from persistent storage, since the two `validation.js` usages found (`archiving.getCachedOutput` matches) are the highest-risk call sites and should be audited for whether they can affect the accept/reject decision for a unit under a doublespend/fork scenario.

### Proof of Concept
Not fully verifiable from static analysis alone: the exact call sites in `validation.js` that invoke `archiving.getCachedOutput` were located (2 matches) but their surrounding logic (how the returned `{address, amount, denomination, asset}` is used in the accept/reject decision) could not be fully retrieved within the available context window. This is a genuine gap: to complete the proof of concept, one would need to inspect the two call sites in `validation.js` where `archiving.getCachedOutput` is invoked and trace whether their output is used to satisfy spend-proof/serial-number/amount checks without re-validating against the live `sequence`/`is_stable` columns for that unit.

"use strict";
var db = require('./db.js');

// in-memory holdover of joints we just voided (stripped final-bad units), so that for a while after pruning
// we can still serve their full content to peers and recover from spends that raced the pruning locally
const PRUNED_JOINT_CACHE_TTL_ms = 60 * 60 * 1000;
let assocCachedPrunedJoints = {};

function cachePrunedJoint(objJoint){
	assocCachedPrunedJoints[objJoint.unit.unit] = { objJoint: objJoint, expiry_ts: Date.now() + PRUNED_JOINT_CACHE_TTL_ms };
}

function getCachedPrunedJoint(unit){
	const cached = assocCachedPrunedJoints[unit];
	if (!cached)
		return null;
	return cached.objJoint;
}

// looks up a specific output within a cached pruned joint, in the same shape as the outputs table columns we lost to stripping
function getCachedOutput(unit, message_index, output_index){
	const objJoint = getCachedPrunedJoint(unit);
	if (!objJoint)
		return null;
	const message = objJoint.unit.messages && objJoint.unit.messages[message_index];
	if (!message || message.app !== 'payment' || !message.payload)
		return null;
	const output = message.payload.outputs && message.payload.outputs[output_index];
	if (!output)
		return null;
	return {
		address: output.address,
		amount: output.amount,
		denomination: message.payload.denomination || 1,
		asset: message.payload.asset || null
	};
}
