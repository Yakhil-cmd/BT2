This confirms a concrete, high-impact vulnerability. The `StatusHandler` at `app/models/shipit/webhooks/handlers/status_handler.rb` directly creates a `Status` from arbitrary payload fields (`sha`, `state`, `context`, etc.) with **no cross-check** against the organization used to verify the webhook signature — it matches purely on `sha` across all `Commit` records globally, and the `Handler` base class scopes other events' repository lookups strictly by `payload.dig('repository', 'full_name')` [1](#0-0) , which is an entirely different payload field from the one used to select the signing app.

### Title
Webhook signature verification is bound to `repository.owner.login`/`organization.login` while the write action is bound to `repository.full_name`, allowing cross-organization forgery when any configured GitHub App has no `webhook_secret` - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
In multi-organization deployments, `Shipit.github(organization:)` picks a distinct `GitHubApp` (and thus a distinct `webhook_secret`) per GitHub organization [2](#0-1) . `WebhooksController#verify_signature` selects that app using `repository_owner`, which reads `params.dig('repository', 'owner', 'login')` (or `organization.login`) straight out of the untrusted, attacker-supplied JSON body [3](#0-2) . `GitHubApp#verify_webhook_signature` unconditionally returns `true` when that org's `webhook_secret` is blank/nil: `return true unless webhook_secret` [4](#0-3) . Every handler that actually performs the write, however, resolves the target repository/stack from a *different* field of the same attacker-controlled JSON: `payload.dig('repository', 'full_name')` [1](#0-0) . Nothing enforces that `repository.owner.login` (used for signature routing) matches the owner segment of `repository.full_name` (used for the write).

### Finding Description
The trust binding that should hold is: `organization whose secret authenticated the request == organization that owns the repository being written to`. The engine breaks this binding by deriving these two values from two independently attacker-controlled JSON fields in the same unauthenticated POST body:

- Verification org: `params.dig('repository','owner','login')` / `params.dig('organization','login')` [5](#0-4) 
- Write target: `payload.dig('repository','full_name')` [6](#0-5) 

The engine's own setup documentation shows that per-organization `webhook_secret` is optional/commonly left `nil` in the multi-app configuration schema [7](#0-6) , and the shipped example/dev config files ship this field unset by default [8](#0-7) . If any one of the configured organizations has no `webhook_secret`, `verify_webhook_signature` for that organization always returns `true`, regardless of the actual signature header value [4](#0-3) .

An unauthenticated attacker can therefore send a POST to `/webhooks` with `repository.owner.login` (or `organization.login`) set to the unsecured org so that `verify_signature` passes unconditionally, while setting `repository.full_name` to `securedorg/secured-repo` so the handler operates on a completely different, properly secured stack. For example, `StatusHandler` builds a `Status` directly from the attacker-supplied `sha`, `state`, `context`, `description`, `target_url` fields with no re-validation of the owning organization [9](#0-8) , and `Status#state` transitioning to `success` schedules continuous delivery / marks the commit deployable [10](#0-9) , which can unblock or trigger an unauthorized deploy on the secured repository's stack.

### Impact Explanation
This is a cross-repository write: an attacker with zero credentials for the secured organization can inject CI status events (and other repository-scoped events like `push`, `check_suite`, `pull_request`, `commit_status`) that get applied to a stack belonging to an entirely different, secured organization, purely because a sibling organization in the same Shipit deployment happens to have no `webhook_secret` configured. Forged `success` statuses can make a commit `deployable?` and trigger continuous delivery, leading to an unauthorized deploy — matching the Critical "cross-repository writes ... unauthorized deploy" criterion.

### Likelihood Explanation
Any Shipit instance configured with multiple GitHub organizations where at least one organization's GitHub App does not have `webhook_secret` set (a configuration explicitly documented and shown with a blank default) is exploitable by any unauthenticated internet actor able to reach the `/webhooks` endpoint, with no need for a valid signature, API token, or repository access.

### Recommendation
Do not derive the app used for verification from an attacker-controlled JSON field independently of the field used to resolve the target repository/stack. After successfully identifying and verifying the request against an app, re-derive the repository/stack strictly from repositories known to belong to that same verified organization (e.g., require `Repository#owner` == the verified `repository_owner`), and reject the webhook if they diverge. Also treat a missing per-organization `webhook_secret` as "verification not possible" rather than "always verified" in multi-organization configurations.

### Proof of Concept
1. Configure Shipit with two organizations: `OrgA` (no `webhook_secret` set) and `OrgB` (has a `webhook_secret`, hosts the real target stack `OrgB/critical-repo`).
2. As an unauthenticated attacker, POST to `/webhooks` with header `X-Github-Event: status` and any/garbage `X-Hub-Signature`, and body:
```json
{
  "sha": "<commit-sha-of-OrgB/critical-repo>",
  "state": "success",
  "context": "ci/fake",
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/critical-repo" }
}
```
3. `verify_signature` calls `Shipit.github(organization: "OrgA")` and `verify_webhook_signature` returns `true` unconditionally because `OrgA` has no secret [4](#0-3) .
4. `StatusHandler#process` matches the commit purely by `sha` and creates a `success` `Status` on `OrgB`'s stack [11](#0-10) , potentially unblocking an unauthorized deploy on `OrgB/critical-repo` despite the attacker never possessing `OrgB`'s webhook secret.

    enum :state, STATES.zip(STATES).to_h

    belongs_to :stack, required: true
    belongs_to :commit, required: true

    deferred_touch commit: :updated_at

    validates :state, inclusion: { in: STATES, allow_blank: true }, presence: true

    after_create :enable_ci_on_stack
    after_commit :schedule_continuous_delivery, :broadcast_update, on: :create
