### Title
Unauthenticated P2P Peer Can Remove Valid Bridge Txs from BridgeTxPool via Spoofed `ServiceChainInvalidTxResponseMsg` — (`node/sc/sub_bridge_handler.go`)

---

### Summary

`handleParentChainInvalidTxResponseMsg` unconditionally removes a bridge tx from `BridgeTxPool` when a connected P2P peer sends a `ServiceChainInvalidTxResponseMsg` whose `ErrStr` field equals `blockchain.ErrGasPriceBelowBaseFee.Error()`. The bridge P2P handshake performs no cryptographic authentication of the peer's identity as the legitimate parent-chain node — it only checks `NetworkId` and `ProtocolVersion`. Any attacker who can reach the sub-bridge's P2P port can pass the handshake and send a spoofed message, causing valid bridge txs to be silently evicted.

---

### Finding Description

**Handshake provides no peer-identity authentication.**

`readStatus` in `node/sc/bridgepeer.go` validates only `NetworkId` and `ProtocolVersion`: [1](#0-0) 

Both values are public. `RegisterNewPeer` does check `chainID` but only after the peer is already registered and actively handling messages: [2](#0-1) 

**`HandleMainMsg` dispatches `ServiceChainInvalidTxResponseMsg` to the handler without any per-peer trust check:** [3](#0-2) 

**`handleParentChainInvalidTxResponseMsg` removes the tx if `ErrStr` matches a public constant string:** [4](#0-3) 

The `ErrStr` comparison is a plain string equality check against `blockchain.ErrGasPriceBelowBaseFee.Error()`, a value that is hardcoded in the public source. An attacker simply sets this field in the RLP-encoded message payload.

**`BridgeTxPool.RemoveTx` permanently deletes the tx from the pool:** [5](#0-4) [6](#0-5) 

---

### Impact Explanation

The code comment at the removal site explicitly distinguishes two cases: [7](#0-6) 

1. **Anchoring txs** — no automatic retry mechanism exists. A spoofed message permanently drops the anchoring tx; the corresponding block data is never anchored to the parent chain.

2. **Value-transfer txs** — Value Transfer Recovery (`vt_recovery.go`) can re-submit if `config.VTRecovery` is enabled. However:
   - VTR is **opt-in** (`VTRecovery` flag, default not enforced in code).
   - An attacker can continuously re-send spoofed messages at a rate that outpaces VTR's periodic recovery interval, sustaining a bridge DoS.
   - When VTR is disabled, the cross-chain ERC20/ERC721/KAIA transfer is permanently lost: the user's assets are locked in the source bridge contract and the handle tx is never submitted to the destination chain. [8](#0-7) 

---

### Likelihood Explanation

The sub-bridge P2P port is network-accessible. The only barrier is knowing the parent chain's `NetworkId` and protocol version — both are public. No secret, key, or privileged access is required. An attacker who can reach the port (e.g., on the same network, or if the port is internet-exposed) can execute this attack with a single crafted P2P message.

---

### Recommendation

1. **Authenticate the peer before trusting `ServiceChainInvalidTxResponseMsg`**: Track which peer the sub-bridge dialed out to (the configured parent-chain static peer). Only accept `ServiceChainInvalidTxResponseMsg` from that specific peer's node ID.
2. **Verify the tx was actually rejected on-chain** before removing it from `BridgeTxPool` — e.g., check that the tx hash is absent from the parent chain's pending pool or that a receipt with failure exists.
3. **Enforce VTR as a required safeguard** rather than an optional flag when bridge value-transfer is active.

---

### Proof of Concept

```
1. Sub-bridge node is running with a pending bridge value-transfer tx T
   (hash H) in BridgeTxPool.

2. Attacker opens a TCP connection to the sub-bridge's P2P port.

3. Attacker completes the bridge handshake:
   - Sends StatusMsg{NetworkId: <parent_network_id>, ProtocolVersion: <version>}
   - readStatus() passes (only NetworkId + ProtocolVersion checked).

4. Attacker sends:
   ServiceChainInvalidTxResponseMsg RLP([{TxHash: H,
       ErrStr: "gas price is below the base fee"}])
   (exact string of blockchain.ErrGasPriceBelowBaseFee.Error())

5. handleParentChainInvalidTxResponseMsg():
   - txPool.Get(H) returns T  ✓
   - invalidTx.ErrStr == blockchain.ErrGasPriceBelowBaseFee.Error()  ✓
   - txPool.RemoveTx(T) executes — T is deleted from pool.

6. Assert: txPool.Get(H) == nil.
   The cross-chain transfer for T is never submitted to the parent chain.
   If VTRecovery=false, the user's assets are permanently locked.
```

```go
func (pool *BridgeTxPool) removeTx(hash common.Hash) error {
	// Fetch the transaction we wish to delete
	tx, ok := pool.all[hash]
	if !ok {
		return ErrUnknownTx
	}

	addr, err := types.Sender(pool.signer, tx)
	if err != nil {
		return err
	}

	// Remove it from the list of known transactions
	delete(pool.all, hash)

	// Transaction is in the future queue
	if future := pool.queue[addr]; future != nil {
		future.Remove(tx.Nonce())
		if future.Len() == 0 {
			delete(pool.queue, addr)
		}
	}

	return nil
```
