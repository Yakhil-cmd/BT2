### Title
Denial-of-Service via Memory Exhaustion from Unbounded Device Messages / Private-Payment Chains - (File: device.js)

### Summary
Wagtail's advisory describes untrusted, attacker-controlled file content being loaded fully into memory before any size validation, allowing a privileged-but-limited actor (an admin able to upload) to crash the process. The analogous pattern in `ocore--017` exists in the device-message/private-payment pipeline: a paired device (a "private-payment counterparty") can send an arbitrarily large encrypted message through a hub, and the recipient's node will decrypt the entire payload and `JSON.parse` it — allocating memory proportional to attacker-chosen size — before any byte-length limit is enforced.

### Finding Description
When a hub relays a message to a client, `handleJustsaying(ws, 'hub/message', ...)` in `device.js` validates only the presence of required fields and the ECDSA signature before calling `decryptPackage`: [1](#0-0) 
`decryptPackage` decodes the base64 `encrypted_message`, runs it through `aes-128-gcm` decryption in 4KB chunks (an internal workaround for browserify, not a security limit), concatenates the full plaintext into a single buffer, and then `JSON.parse`s it in one shot: [2](#0-1) 
No maximum size is checked anywhere in this path on `objDeviceMessage.encrypted_package.encrypted_message` before it is fully decrypted and parsed.

The only structural check applied to inbound device messages is `isTooDeeplyNestedOrHasTooManyNodes`, and it is applied only on the hub side, when a peer submits a message via `hub/deliver`: [3](#0-2) 
That function bounds object nesting depth and node *count*, but not the *length of individual string values*: [4](#0-3) 
So a device message with very few top-level fields (well within depth=5/nodes=100 limits) but containing a multi-hundred-megabyte base64 string in `encrypted_message` passes this hub-side check, gets persisted in the hub's `device_messages` table, and is later delivered unmodified to the target device via `hub/message`, where it undergoes full decryption and `JSON.parse` with no size gate at all (the recipient path in `device.js` never calls `isTooDeeplyNestedOrHasTooManyNodes` or any length check).

Once decrypted, the resulting JSON (if it represents a private-payment chain) is handed to `handlePrivatePaymentChains` in `wallet.js`, which again performs no size bound before hashing the entire structure (`objectHash.getBase64Hash(arrChains)`) and iterating/validating it: [5](#0-4) 

### Impact Explanation
A correspondent device (any device that has been paired at least once, or that is delivering a private payment as an untrusted counterparty) can force the recipient wallet/full node to allocate and process an arbitrarily large buffer (limited only by hub storage / network transport, not by ocore's own validation), leading to memory exhaustion and process crash — a denial of service consistent with CWE-400/CWE-770. This can disrupt a user's wallet node, preventing it from processing legitimate private payments or units, which aligns with the "network unable to confirm new units" / node disruption impact criteria for this analog.

### Likelihood Explanation
Any already-paired device or the counterparty of a private-payment/textcoin exchange can trigger this without further privilege, since `hub/message` delivery to a subscribed client bypasses the (weak) nesting/node check that only applies at `hub/deliver` time, and that check does not bound string length in any case. The attack requires only crafting one oversized field in an otherwise well-formed device message.

### Recommendation
- Enforce an explicit maximum byte length on `encrypted_package.encrypted_message` (and other string fields of a device message) both when a hub accepts a message via `hub/deliver` and, defensively, again on the client side in `device.js` before calling `decryptPackage`.
- Extend `isTooDeeplyNestedOrHasTooManyNodes` (or add a companion check similar to `isTooBigObj`, which already tracks a `lengthLimit`) to also validate total serialized size of inbound device messages, and apply it uniformly to both `hub/deliver` and `hub/message` code paths.
- Apply a similar overall byte-size cap to `body.chains` in `handlePrivatePaymentChains` before hashing/validating.

### Proof of Concept
1. Attacker device A is a known correspondent of victim device B (or sends an unsolicited private-payment message, which is whitelisted for non-correspondents per `arrSubjectsAllowedFromNoncorrespondents`).
2. A crafts `objDeviceMessage` with valid `to`, `pubkey`, `signature`, and `encrypted_package.dh.*`, but sets `encrypted_package.encrypted_message` to several hundred MB of base64 data (still passing `isTooDeeplyNestedOrHasTooManyNodes(objDeviceMessage, 5, 100)` since it has few object nodes).
3. A submits this via `hub/deliver`; the hub stores and forwards it via `hub/message` to B.
4. B's `device.js` `handleJustsaying('hub/message', ...)` calls `decryptPackage`, which builds a full in-memory buffer of the decrypted payload and `JSON.parse`s it, consuming memory proportional to the attacker-chosen size and potentially crashing B's process. [6](#0-5) [3](#0-2) [4](#0-3)

function isTooDeeplyNestedOrHasTooManyNodes(obj, depthLimit = 100, nodesLimit = 10000) {
	let nodeCount = 0;

	function check(variable, depth){
		if (depth > depthLimit || nodeCount > nodesLimit)
			return true;
		if (variable === null || typeof variable !== "object")
			return false;
		if (Array.isArray(variable)) {
			nodeCount += variable.length;
			for (let v of variable)
				if (check(v, depth + 1))
					return true;
		}
		else {
			nodeCount += Object.keys(variable).length;
			for (let key in variable)
				if (check(variable[key], depth + 1))
					return true;
		}
		return false;
	}

	return check(obj, 1);
}
