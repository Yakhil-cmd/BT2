### Title
`ReviewStack#env` injects unfiltered PR label names as environment variables into git subprocesses, allowing `SSH_ASKPASS` injection via a pull request label - (File: app/models/shipit/review_stack.rb)

### Summary
`ReviewStack#env` merges every pull-request label name (uppercased) directly into the process environment used to run git commands, with no key allowlist. `LabelCapturingHandler` persists label names verbatim from the unauthenticated-content webhook body (the label text itself is attacker-supplied via a PR the attacker opens on their own fork), so an attacker can name a label `ssh_askpass` (or any other sensitive variable name) and have it become `ENV["SSH_ASKPASS"]` for every git command run against that stack, including `StackCommands#git_clone`.

### Finding Description
The broken binding: `keys(ReviewStack#env) == allowlisted_stack_env_keys` is expected, but in fact `keys(ReviewStack#env) == pull_request.labels.map(&:upcase) ∪ Stack#env_keys`, i.e. **any string** the PR author chooses.

Code path:
- `LabelCapturingHandler#capture_labels` stores `params.pull_request.labels.map(&:name)` verbatim (only validated as `String` by the `ExplicitParameters` schema, no character/keyword restriction): [1](#0-0) 
- `ReviewStack#env` uppercases every label name and merges it into the stack's env hash with no allowlist: [2](#0-1) 
- `StackCommands#env` merges `@stack.env` on top of the base env used for all git operations, including `git_clone`: [3](#0-2)  and `git_clone` (used from `fetch`/`fetch_commit`) passes that `env:` straight through: [4](#0-3) [5](#0-4) 
- `Command#unbundled_env` merges this attacker-influenced `@env` on top of `BASE_ENV`/`PATH` and hands it straight to `PTY.spawn`: [6](#0-5) [7](#0-6) 

Existing guards do not stop this: `capture_labels?`/`labeled_active_stack?`/`unlabeled_active_stack?` only gate *when* labels are captured (opened/labeled/unlabeled/reopened on a present, non-archived stack) — they do not restrict label *content*: [8](#0-7) . The `ExplicitParameters` schema only requires `name` be a `String`: [9](#0-8) . There is no `EnvironmentVariables#permit`-style allowlist anywhere on this path, and `Command#initialize` performs no key filtering, only `to_s`-coercing values: [10](#0-9) . This is confirmed directly by the project's own test asserting arbitrary uppercased label names land in `env`: [11](#0-10) .

The `prevent_with_label` provisioning behavior only controls whether the stack is archived/provisioned based on a specific configured label; it does not gate what labels get captured into `pull_request.labels`, and label capture (via `LabelCapturingHandler`) runs independently of `LabeledHandler`'s archive/unarchive decision for any label the attacker applies to their own PR on a non-archived stack.

Attack: open a PR from a fork, apply a label literally named `ssh_askpass`, wait for `LabelCapturingHandler` to persist it, then whenever `StackCommands#fetch`/`fetch_commit` falls back to `git_clone` (e.g., cache miss/corruption), the spawned `git` process inherits `SSH_ASKPASS=SSH_ASKPASS`→ actually `SSH_ASKPASS="true"` per the merge (`labels[label_name.upcase] = "true"`). Note: the value merged is always the literal string `"true"`, not attacker-chosen content — the attacker controls the **variable name** (which env var gets set) but not its **value** for this specific vector.

### Impact Explanation
Confirmed: the attacker fully controls which environment-variable *names* get set (to the fixed value `"true"`) on every git subprocess for their ReviewStack, with no allowlist. This validates the specific "fast validation" claim in the question — `SSH_ASKPASS` (or any other var name) does reach `Command`/`PTY.spawn` for `git_clone`. However, because the merged value is hardcoded to `"true"` rather than attacker-supplied content, `SSH_ASKPASS=true` is not itself a valid executable path and does not directly grant code execution through this specific variable — `git`/`ssh` would attempt to exec a program named "true" relative to `PATH`/cwd resolution rules, not attacker-supplied shell code. Broader impact (e.g. clobbering `GIT_ASKPASS`, `GITHUB_TOKEN`, `PATH`-like behaviors, or other sensitive flags with a fixed "true") is limited by this same constraint. The unrestricted key injection into subprocess environment is nonetheless a real defect (arbitrary env-key pollution reaching a privileged deploy-host `PTY.spawn`), but is bounded/High rather than a demonstrated Critical RCE, since the exploit as scoped cannot supply attacker-chosen *values*, only names, and the value is fixed to `"true"`.

### Likelihood Explanation
Precondition is minimal: any GitHub user able to open a PR and label it on a repository with review stacks enabled (regardless of `prevent_with_label`/`allow_with_label`/`allow_all`), since label capture is independent of the provisioning behavior. Cost is trivial (one label). Reproducible per PR/label.

### Recommendation
Add an explicit allowlist of permitted environment variable key names for PR-label-derived variables in `ReviewStack#env` (e.g., reject/require a safe prefix such as `LABEL_`, or maintain a denylist of sensitive names like `SSH_ASKPASS`, `GIT_ASKPASS`, `GIT_SSH_COMMAND`, `LD_PRELOAD`, `PATH`, `GITHUB_TOKEN`), and apply the same allowlist centrally wherever untrusted data becomes `Command` env (`lib/shipit/command.rb`), rather than trusting call sites.

### Proof of Concept
```ruby
# test/models/shipit/review_stack_test.rb
test "#env does not allow labels to override sensitive/reserved env var names" do
  stack = shipit_stacks(:review_stack)
  stack.pull_request.labels = ["ssh_askpass"]

  refute_includes stack.env.keys, "SSH_ASKPASS"
end
```
This fails against current code: `stack.env["SSH_ASKPASS"]` equals `"true"`, demonstrating the unfiltered key merge documented above; the value is fixed (`"true"`), so this proves environment-key pollution reaching `Command`/`PTY.spawn`, not attacker-controlled command execution via `SSH_ASKPASS`'s value.
