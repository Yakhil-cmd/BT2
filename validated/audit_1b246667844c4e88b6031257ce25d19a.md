### Title
Cross-organization commit-status forgery via webhook signature/action binding mismatch - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret to validate a webhook's HMAC signature against using `params.dig('repository', 'owner', 'login')` (falling back to `params.dig('organization', 'login')`). [1](#0-0) [2](#0-1)  This confirms only that the *sender* controls a legitimate, Shipit-configured GitHub organization/App — it never confirms that the rest of the payload actually belongs to that organization. The `StatusHandler`, which processes GitHub `status` events, then acts on the payload using nothing but the raw commit SHA, globally, across the entire `commits` table, without ever re-checking which organization or repository it came from: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }`. [3](#0-2) 

### Finding Description
This is the same bug class as the reported analog: a trust check validates one field (`collection.key` / here, the organization inferred from `repository.owner.login`) while the code that performs the sensitive action consumes a *different, unrelated* field (`sha`) that is never cross-checked against the authenticated identity.

Concretely, the binding that should hold is:
`organization that authenticated the webhook == organization owning the repository/commit that Shipit mutates`

Before the fix this engine should apply: nothing enforces that equality. `verify_signature` picks `github_app = Shipit.github(organization: repository_owner)` purely to find the HMAC secret to validate against. [1](#0-0)  Once the signature check passes, `WebhooksController#create` hands the *entire raw JSON payload* to every registered handler for that event type, unmodified and with no additional authorization scoping: `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`. [4](#0-3) 

For the `status` event, `StatusHandler#process` looks up commits by SHA across the whole `commits` table — a global namespace not scoped by repository, organization, or Shipit `Stack` — and then calls `commit.create_status_from_github!(params)`, writing a fabricated status derived from attacker-controlled `state`/`description`/`context` fields onto whatever commit in the database happens to share that SHA. [5](#0-4)  `Commit#create_status_from_github!` feeds directly into `add_status`, which recomputes `status`, fires `Hook.emit(:deployable_status, ...)`, and — critically — calls `stack.schedule_merges` whenever the new status becomes `pending` or `success`. [6](#0-5)  A commit's `deployable?` state is derived purely from these locally-stored statuses (`success? && !blocked?`), which is exactly what CI gating (`ci.require`) and merge-queue automation rely on. [7](#0-6) 

Because `verify_signature` only proves "the requester possesses *some* configured organization's webhook secret," and `StatusHandler` never checks that the commit it is patching belongs to a stack owned by that same organization, an attacker who administers their own Shipit-registered GitHub App/org (with its own known `webhook_secret`) can forge a `status` webhook that signs correctly for their own org while carrying a `sha` for a commit that actually belongs to a completely different, victim-owned repository/stack tracked by the same Shipit instance. This breaks the binding "organization that authenticated versus the repository that is written."

### Impact Explanation
An attacker controlling one legitimately-configured GitHub organization/App entry in Shipit's `secrets.yml` (multi-org deployments are explicitly supported, as shown in `test/dummy/config/secrets_double_github_app.yml`) can forge a valid signature for a `status` webhook while injecting an arbitrary `state`/`description`/`context` for any commit SHA present in any other tracked stack. This can flip an unrelated organization's commit from failing/pending CI to `success`, satisfying `deployable?` and `ci.require` gating, triggering `stack.schedule_merges` and continuous-delivery/merge-queue automation for a repository the attacker has no legitimate access to. This maps to the "unauthorized deploy, rollback, or merge" Critical impact category, since it can cause an unreviewed/unauthorized merge or deploy to proceed on a different organization's stack purely by forging a commit status.

### Likelihood Explanation
Exploitability requires only that the attacker control one configured GitHub App/organization entry recognized by the target Shipit instance (a realistic scenario for any Shipit deployment hosting multiple organizations/tenants, which the engine explicitly supports). No access to the victim organization's webhook secret, repository, or Shipit session is required — only knowledge of a target commit SHA, which is often public (e.g., visible in PRs, CI logs, or the Shipit UI itself) and knowledge of the attacker's own webhook secret, which they legitimately possess.

### Recommendation
`StatusHandler` (and any other handler that mutates commit/stack state from webhook payloads) should scope its lookup by repository, not merely by SHA: derive the repository/stack from `payload.dig('repository', 'full_name')` (as `Handler#stacks`/`repository_name` already does for other handlers) and restrict the `Commit.where(sha: ...)` query to commits belonging to stacks under that repository. Additionally, `verify_signature` should assert that the resolved `github_app`'s organization is the *only* organization consulted for the remainder of request processing, and handlers should reject payloads whose `repository.owner.login` does not match `repository.full_name`'s owner segment, closing the gap between the authenticated organization and the entity actually mutated.

### Proof of Concept
1. Shipit is configured (as in `test/dummy/config/secrets_double_github_app.yml`) with two GitHub App orgs: `OrgOne` (attacker-controlled, known `webhook_secret`) and `OrgTwo` (victim, tracked stack `victim/target-repo`).
2. Attacker obtains a commit SHA `S` belonging to a commit already synced into Shipit's `commits` table for `victim/target-repo` (e.g., observed via the public GitHub repo, or the Shipit UI if publicly viewable).
3. Attacker crafts a `status` event JSON body: `{"sha": "S", "state": "success", "context": "ci/forced", "repository": {"owner": {"login": "OrgOne"}, "full_name": "OrgOne/attacker-repo"}}`.
4. Attacker computes `X-Hub-Signature: sha1=HMAC(webhook_secret_of_OrgOne, raw_body)` — a secret they legitimately know — and POSTs to `/webhooks` with header `X-Github-Event: status`.
5. `verify_signature` resolves `repository_owner` = `"OrgOne"`, fetches `Shipit.github(organization: "OrgOne")`, and the signature check passes. [1](#0-0) 
6. `StatusHandler#process` runs `Commit.where(sha: "S")`, finds the victim's commit (unscoped by org/repo), and calls `create_status_from_github!`, marking it `success`. [3](#0-2) [8](#0-7) 
7. If this satisfies `victim/target-repo`'s `deployable?`/`ci.require` and the stack has `continuous_deployment` enabled, `stack.schedule_merges`/continuous delivery proceeds — an unauthorized deploy/merge triggered entirely by an attacker who never touched the victim organization's credentials.

**Uncertainty note:** I was unable to fully trace `Stack#schedule_merges`/merge-queue implementation and `ContinuousDeliveryJob` internals in this session to confirm the exact downstream automatic-deploy trigger conditions beyond `Commit#schedule_continuous_delivery`/`deployable?`; a Devin session with full file access should verify these code paths end-to-end before remediation.
