### Title
No enforced minimum key size in `is_valid_sig()`/`vrf_verify()` PEM signature verification allows weak-key forgery in AA logic - (File: `signature.js`)

### Summary
`signature.js`'s `validateAndFormatPemPubKey()` only checks the DER *structure* of a supplied PEM public key (sequence tags, algorithm/curve OID, and — for EC keys only — that the key length matches the expected length for that specific curve). It never enforces a minimum key strength for RSA keys, and the "safe curve" allow-list introduced by `pemCurvesFixMci` still unconditionally accepts RSA regardless of modulus size. This mirrors CVE-2025-45765's root cause in ruby-jwt: the library performs no keysize enforcement and defers that responsibility entirely to the caller.

### Finding Description
`validateAndFormatPemPubKey()` in [1](#0-0)  parses the PEM key's ASN.1 structure and looks up the algorithm/curve OID in `objSupportedPemTypes`, then (post-fix) checks membership in `objSafePemTypes`: [2](#0-1) 

`objSafePemTypes` includes the RSA OID `06092a864886f70d0101010500` (`PKCS #1`) unconditionally — there is no branch anywhere in this function that inspects or bounds the RSA modulus size. The only RSA-related size guard is a coarse *upper* bound on the overall PEM blob (`contentAloneB64.length > 736`, i.e. up to ~4096-bit RSA), at [3](#0-2) ; there is no lower bound.

This function is invoked directly from the oscript `is_valid_sig(message, pem_key, sig)` operator, reachable by any unprivileged AA trigger sender, with `algo = "any"`: [4](#0-3) 

and from `vrf_verify(seed, proof, pem_key)` with `algo = "RSA"`: [5](#0-4) 

Tests in the repo explicitly confirm that RSA keys of 512, 700, and 1024 bits are accepted as fully valid by `is_valid_sig`, e.g. [6](#0-5)  (RSA 512 bits) and [7](#0-6)  (RSA 1024 bits). These are cryptographically weak: RSA-512 is routinely factored in hours on commodity/cloud hardware, and RSA-1024 is considered broken against well-resourced attackers.

In contrast, the same `pemCurvesFixMci` fix *did* introduce a deliberate curve allow-list to retire weak/broken elliptic curves (`objSafePemTypes`), showing that key/algorithm strength was previously recognized as a security-relevant property of this exact function — yet the fix left RSA modulus size completely unconstrained, an inconsistent application of the same principle.

### Impact Explanation
`is_valid_sig`/`vrf_verify` results directly gate branching, spending, and issuance logic inside Autonomous Agents. An AA author who uses `is_valid_sig` to authenticate an oracle feed, counterparty attestation, or off-chain approval with an RSA key of insufficient size (which the engine happily accepts as "valid" and provides no warning or rejection for) is exposed to signature forgery once an attacker factors that small modulus offline. A forged signature accepted by the AA can be used to unlock AA-held funds, trigger unauthorized asset issuance, or otherwise manipulate AA state — i.e., concrete AA fund loss or supply inflation. Because the weakness lies in ocore's own validation primitive (no enforced minimum), any AA relying on it inherits the flaw regardless of how carefully the AA logic otherwise is written.

### Likelihood Explanation
Exploitation requires an AA that uses `is_valid_sig`/`vrf_verify` with a small RSA key (a design choice made by the AA author, not by the attacker), so this is not remotely as broadly reachable as a core validation bug. However, ocore provides zero guidance/enforcement steering authors away from weak keys — exactly the same disclaimed responsibility-shifting described in the CVE — and the engine's own test suite demonstrates 512-bit RSA is treated as indistinguishable from 4096-bit RSA. Any deployed AA (now or in the future) built with a weak RSA oracle/signer key is silently and permanently vulnerable to forgery, with no protocol-level safety net.

### Recommendation
Enforce a minimum RSA modulus size (e.g., 2048 bits) inside `validateAndFormatPemPubKey()` for the RSA case, in the same way `objSafePemTypes` restricts allowed elliptic curves, and reject `is_valid_sig`/`vrf_verify` calls (and definition validation, if PEM keys can appear in address definitions) that use weaker RSA keys, gated behind a new MCI-activated protocol upgrade for backward compatibility.

### Proof of Concept
1. An AA is written to validate an oracle-signed data feed via `is_valid_sig(trigger.data.message, ORACLE_PEM_KEY, trigger.data.signature)`, where `ORACLE_PEM_KEY` is a 512-bit RSA public key (accepted without warning, as shown by `test/pem_sig.test.js` "is_valid_sig RSA 512 bits").
2. An attacker factors the 512-bit RSA modulus offline (feasible in hours with commodity cloud resources) to recover the private key.
3. The attacker crafts an arbitrary `message`/`signature` pair that validates successfully, posts a trigger unit containing this forged pair to the AA.
4. `formula/evaluation.js`'s `is_valid_sig` case returns `true` via `signature.verifyMessageWithPemPubKey`, causing the AA to execute the attacker-chosen branch (e.g., releasing funds or minting assets) as if genuinely authorized by the oracle.

function validateAndFormatPemPubKey(pem_key, algo, handle, bPostPemCurvesFix) {

	if (!ValidationUtils.isNonemptyString(pem_key))
		return handle("pem key should be a non empty string");

	//we remove header and footer if present
	var contentAloneB64 = pem_key.replace("-----BEGIN PUBLIC KEY-----", "").replace("-----END PUBLIC KEY-----", ""); 
	
	//we remove space, tab space or carriage returns
	contentAloneB64 = contentAloneB64.replace(/\s/g, "");

	if (contentAloneB64.length > 736) // largest is RSA 4096 bits
		return handle("pem content is too large");

	if (!ValidationUtils.isValidBase64(contentAloneB64))
		return handle("not valid base64 encoding" + contentAloneB64);

	var contentAloneBuffer = Buffer.from(contentAloneB64, 'base64');

	if (contentAloneBuffer[0] != 0x30)
		return handle("pem key doesn't start with a sequence");

//we determine start and length of algo/curve identifiers
	if (contentAloneBuffer[1] <= 0x7F){
		if (contentAloneBuffer[2] != 0x30)
			return handle("pem key doesn't have a second sequence");
		var identifiersStart = 4;
		var identifiersLength = contentAloneBuffer[3];
	} else if (contentAloneBuffer[1] == 0x81){
		if (contentAloneBuffer[3] != 0x30) 
			return handle("pem key doesn't have a second sequence");
		var identifiersStart = 5;
		var identifiersLength = contentAloneBuffer[4];
	} else if (contentAloneBuffer[1] == 0x82){
		if (contentAloneBuffer[4] != 0x30) 
			return handle("pem key doesn't have a second sequence");
		var identifiersStart = 6;
		var identifiersLength = contentAloneBuffer[5];
	} else {
		return handle("wrong length tag");
	}

	//we decode the length of identifiers
	if (identifiersLength != 13 && identifiersLength != 16 && identifiersLength != 19 && identifiersLength != 20)
		return handle("wrong identifiers length" + identifiersLength);

	//we isolate the identifiers
	var contentAloneHex = contentAloneBuffer.toString('hex')
	var typeIdentifiersHex = contentAloneHex.slice(identifiersStart * 2, identifiersStart *2 + identifiersLength *2);

	if (!objSupportedPemTypes[typeIdentifiersHex])
		return handle("unsupported algo or curve in pem key");

	if (bPostPemCurvesFix && !objSafePemTypes.has(typeIdentifiersHex))
		return handle("unsupported curve after pem curves fix MCI");

	if (algo != "any"){
		if (algo == "ECDSA" && objSupportedPemTypes[typeIdentifiersHex].algo != "ECDSA")
			return handle("PEM key is not ECDSA type");
		if (algo == "RSA" && objSupportedPemTypes[typeIdentifiersHex].algo != "RSA")
			return handle("PEM key is not RSA type");
	}

	if (objSupportedPemTypes[typeIdentifiersHex].algo == "ECDSA" && objSupportedPemTypes[typeIdentifiersHex].hex_pub_key_length != (contentAloneHex.length - identifiersStart * 2 - identifiersLength *2 - 8))
		return handle("wrong key length");

	//we add back header and footer
	pem_key =	"-----BEGIN PUBLIC KEY-----" + "\n";
	pem_key += contentAloneB64+"\n";
	pem_key += "-----END PUBLIC KEY-----";
	return handle(null,pem_key);
}
