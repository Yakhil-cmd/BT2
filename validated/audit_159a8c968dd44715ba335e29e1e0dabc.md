### Title
Cross-organization Team hijack via `MembershipHandler` github_id collision bypasses `Shipit.github_teams` authorization - (File: app/models/shipit/webhooks/handlers/membership_handler.rb:38-43)

### Summary
`MembershipHandler#find_or_create_team!` looks up `Team` solely by the numeric `params.team.id` (GitHub's `github_id`), never checking that the resolved `Team#organization` matches the organization whose `webhook_secret` actually verified the incoming signature. An attacker who legitimately controls one org configured in Shipit's multi-org GitHub config can sign a `membership` webhook with their own valid `webhook_secret` but set `team.id` to the numeric `github_id` of an already-existing, privileged `Team` row belonging to a different org, and `member.login` to their own GitHub login, causing `Team#add_member` to add themselves into that privileged team.

### Finding Description
The intended binding is: `verified_organization.login == team.organization` for the `Team` row that `add_member` mutates. This binding is never enforced.

Path:
1. `app/controllers/shipit/webhooks_controller.rb:24-30` verifies the signature using `Shipit.github(organization: repository_owner)`, where for a `membership` event `repository_owner` resolves to `params.dig('organization','login')` (`app/controllers/shipit/webhooks_controller.rb:59-62`). In a multi-org config (`lib/shipit.rb:170-200`, `github_app_config`), this correctly picks the `webhook_secret` for the named org, so the signature only proves "this request was signed by the owner of the org named in `organization.login`" — i.e., it proves the attacker's own org, if the attacker is a legitimate configured tenant.
2. `MembershipHandler#process` (app/models/shipit/webhooks/handlers/membership_handler.rb:22-24) calls `find_or_create_team!`, which does `Team.find_or_create_by!(github_id: params.team.id) { |team| team.organization = params.organization.login }` (app/models/shipit/webhooks/handlers/membership_handler.rb:38-43). The `organization` assignment in the block **only runs on create**. If a `Team` row with that `github_id` already exists (e.g., created earlier for a different, privileged org via `Team.find_or_create_by_handle` or a prior legitimate membership webhook), `find_or_create_by!` returns that **existing** row untouched, regardless of what `params.organization.login` says in this request.
3. `member = User.find_or_create_by_login!(params.member.login)` (app/models/shipit/user.rb:22-28) resolves/creates a `User` purely by login string via the global `Shipit.github.api` client — this correctly resolves the attacker's own real GitHub identity if they set `member.login` to themselves; no forgery of identity is needed here since this doesn't grant anything to a third party.
4. `team.add_member(member)` (app/models/shipit/team.rb:41-43) appends the resolved user to `team.members` with no re-check of `team.organization` against the verified organization.
5. `User#authorized?` (app/models/shipit/user.rb:80-82) and `Shipit.github_teams` (`lib/shipit.rb:256-258`) grant full app access to anyone who is a member of a `Team` whose id is in `Shipit.github_teams`. Since the `Team` row itself is never re-validated against the signing organization, membership in it is now attacker-controlled.

The two scenarios in the question:
- **Victim's login + colliding team never in `Shipit.github_teams`**: no authorization impact — `authorized?` only checks membership against `Shipit.github_teams`; adding an already-authorized user to an unprivileged team changes nothing security-relevant (though it is an unwanted, unauthenticated write to that user's `Membership` record).
- **Attacker's own login + `team.id` colliding with a privileged team's `github_id`** (one present in `Shipit.github_teams`): this is the actual escalation path. The attacker adds themselves to a `Team` object that Shipit trusts for authorization purposes, despite the request being signed only by their own, unrelated org's `webhook_secret`.

Existing guards do not stop this: `verify_signature` only proves the payload was signed by a known org's secret, it says nothing about which `Team` row the payload is allowed to mutate; `ExplicitParameters` (`params do ... end` block, membership_handler.rb:7-21) only validates types/presence, not cross-record ownership; there is no `Team#organization` check anywhere in `MembershipHandler` or `Team#add_member`.

### Impact Explanation
An attacker who controls (or is granted) any org configured under Shipit's multi-org GitHub App config can forge membership into any pre-existing privileged `Team` (any team whose `github_id` is already known/guessable and stored in Shipit's DB, in particular any team referenced by `Shipit.github_teams`/`oauth.teams`), thereby self-granting `authorized?` == true and full access to the Shipit UI/API for stacks, deploys, rollbacks and merges across the entire installation — not scoped to their own org's repositories. This is a genuine escalation into `Shipit.github_teams` authorization (High/Critical per the rubric's "escalation into Shipit.github_teams authorization" category), and is repeatable at will since it's a single signed HTTP POST per grant.

### Likelihood Explanation
Requires: (a) Shipit deployed with the multi-org GitHub App schema (`lib/shipit.rb:170-200`) so distinct orgs have distinct `webhook_secret`s, and the attacker legitimately controls one configured org (able to trigger/craft `membership` webhooks with a valid signature for their org); (b) the target privileged `Team`'s numeric `github_id` already exists as a row in Shipit's `teams` table (created previously by legitimate sync of the target org, e.g. via `Team.find_or_create_by_handle` or an earlier real webhook) and is discoverable/guessable by the attacker. Under a single-org config (`github_default_organization.nil?` branch, `lib/shipit.rb:170-178`), all webhooks use one shared secret and this attack degenerates into a same-tenant issue with less value. Feasibility depends on the attacker being able to learn the target team's numeric GitHub team ID, which is a real but non-trivial precondition; the underlying missing-binding bug itself is unconditional.

### Recommendation
In `MembershipHandler#find_or_create_team!`, always require and verify that the resolved `Team#organization` equals `params.organization.login` (the organization whose webhook secret verified this request) before calling `team.add_member`/`team.members.delete`; if an existing `Team` row has a different `organization`, raise/reject rather than silently reusing it. Additionally, scope the `find_or_create_by!` lookup by `(github_id:, organization: params.organization.login)` instead of `github_id` alone.

### Proof of Concept
Add to `test/models/team_test.rb` or a new webhook handler test:
```ruby
test "MembershipHandler never mutates a Team belonging to a different organization than the verified webhook payload" do
  privileged_team = Shipit::Team.create!(github_id: 999, organization: 'victim-org', slug: 'admins', name: 'Admins')

  payload = {
    'action' => 'added',
    'team' => { 'id' => 999, 'name' => 'Admins', 'slug' => 'admins', 'url' => 'https://x' },
    'organization' => { 'login' => 'attacker-org' }, # this is the org that actually signed the request
    'member' => { 'login' => 'attacker' }
  }

  Shipit::User.stubs(:find_or_create_by_login!).with('attacker').returns(shipit_users(:walrus))

  Shipit::Webhooks::Handlers::MembershipHandler.new.call(resource(payload))

  # Binding under test: team.organization must equal the verified organization.login
  assert_not_equal 'attacker-org', privileged_team.reload.organization
  refute_includes privileged_team.members, shipit_users(:walrus)
end
```
This test currently fails against the existing implementation (the attacker is added to `privileged_team` despite `organization` mismatch), proving the broken binding.
