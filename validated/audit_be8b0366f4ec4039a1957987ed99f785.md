### Title
Signed packages (`signed_message`) lack a network/genesis binding, enabling cross-network replay of `is_valid_signed_package` signatures - (File: `signed_message.js`, `object_hash.js`)

### Summary
The hash that is actually signed for a `signed_message` package (`getSignedPackageHashToSign` in `object_hash.js`) is built only from `version`, `signed_message`, `authors`, `last_ball_unit`/`timestamp`. Unlike a regular unit hash, it never includes the network's `alt` value or any genesis/network-specific identifier. Since `version`/`alt` are simply hard-coded constants selected by `bTestnet`/`bDevnet` env flags (`constants.js`), any two independently operated, code-identical ocore-based production networks (e.g. a hard-fork, or a second production deployment started with default settings) end up with the exact same `version` ('4.0') and `alt` ('1') values. A signature over a `signed_message` package is therefore valid and replayable verbatim across any such network, exactly analogous to the referenced report where the absence of `chainId` in a signed `Offer` makes signatures replayable across EVM chains after a hard fork.

Because `version` and `alt` are process-wide constants tied only to `testnet`/`devnet` env flags (not to the genesis unit or any per-deployment secret), every default "production" deployment of the ocore codebase (any fork, private network, or side-chain that doesn't explicitly change these constants) shares the identical `version`/`alt` pair with the official Obyte mainnet: [8](#0-7) 

A signed package created by a user/oracle for use on one such network is therefore byte-identical and fully valid when replayed on any other network that shares the same `version`/`alt`, because nothing in the signed content or the verification logic ties it to a specific chain/genesis.

### Impact Explanation
Any AA that trusts an externally signed message as authorization (e.g., an oracle price attestation gating a payout, a signed "release funds" approval, a signed vote/order used in a DEX-like AA, as exercised by `is_valid_signed_package`) can be tricked into accepting a signature that was legitimately produced for a *different* network. An attacker who observes such a signed package (from correspondence, a different but code-identical deployment, or a future/past hard fork of the network) can resubmit it unchanged as `trigger.data.signed_package` to an AA on another network sharing the same address/definition, causing the AA to release funds or otherwise act as though a genuine, network-specific authorization was given. This is a concrete AA fund-loss/authorization-bypass vector, not merely a resource issue.

### Likelihood Explanation
Likelihood is elevated by the fact that `version`/`alt` do not encode a deployment-specific network identity — they are default constants shared by every non-testnet/non-devnet deployment of the codebase. Any operator spinning up a second production instance (fork, private chain, or a genuine future hard fork of Obyte) with default settings creates a network that is signature-compatible with the original. Any AA design that relies on `is_valid_signed_package` for authorization (oracle price feeds, signed approvals, order matching, escrow release) is exposed without any special privilege required by the attacker — only observation/possession of a validly signed package and the ability to post an AA trigger.

### Recommendation
Bind the signed-package hash to the specific network instance, e.g. include `constants.GENESIS_UNIT` (or another unique per-deployment/network identifier) inside the object that `getSignedPackageHashToSign` hashes, and enforce/verify this field in `validateSignedMessage`. This mirrors adding `chainId()` to the signed `Offer` struct in the referenced finding and ensures a signed package produced for one network cannot be replayed as valid on a different network sharing the same code and constants.

### Proof of Concept
1. Deploy two independent ocore-based production networks (Network A and Network B) both using default settings (`bTestnet=false`, `bDevnet=false`), so both have `constants.version === '4.0'` and `constants.alt === '1'`.
2. On Network A, a user signs a `signed_message` package (e.g., approving release of funds from an escrow AA) using `signed_message.signMessage`, producing `objUnit` with `{version:'4.0', signed_message, authors:[{address, authentifiers}]}` — no `alt`/genesis binding is present.
3. The identical bytes for `authors[0].address`'s definition (hence identical address) can be recreated on Network B (definitions/addresses are network-independent, derived only from Chash160 of the definition).
4. An attacker submits this exact `signed_message` object as `trigger.data.signed_package` to an equivalent escrow AA deployed on Network B.
5. `is_valid_signed_package` in `formula/evaluation.js` calls `signed_message.validateSignedMessage`, which recomputes `getSignedPackageHashToSign` (identical to Network A's hash, since neither `alt` nor a genesis identifier is part of the hashed content) and successfully verifies the signature, causing the AA on Network B to treat the replayed package as valid authorization.

function getSignedPackageHashToSign(signedPackage) {
	var unsignedPackage = _.cloneDeep(signedPackage);
	for (var i=0; i<unsignedPackage.authors.length; i++)

	var sourceString = (typeof signedPackage.version === 'undefined' || signedPackage.version === constants.versionWithoutTimestamp) ? getSourceString(unsignedPackage) : getJsonSourceString(unsignedPackage);
