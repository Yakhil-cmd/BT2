### Title
Unbounded scan of `storage.assocUnstableMessages` in AA data-feed formulas allows gas/CPU griefing DoS - (File: `data_feeds.js`)

### Summary
The reported bug describes a `while`-loop in `LimitOrderRegistry::performUpkeep` that walks a shared list until it finds the next matching-direction order, letting an attacker insert cheap opposite-direction orders to blow up gas costs and block execution for legitimate participants. The structural analog in `ocore` is `dataFeedExists()` / `readDataFeedValue()` in `data_feeds.js`, which — when called from AA trigger/oscript evaluation (`in_data_feed` / `data_feed[[...]]` in `formula/evaluation.js`) — iterate the entire in-memory `storage.assocUnstableMessages` map on every single call, with no bound on the number of iterations other than "how many unstable units currently exist."

### Finding Description
When an AA formula evaluates `data_feed[[...]]` or `in_data_feed[[...]]` with the (default) "include unstable" behavior, `readDataFeedValue`/`dataFeedExists` loop over **every key** in `storage.assocUnstableMessages`, inspecting each unstable unit's messages to see if it matches the requested oracle addresses/feed name/value: [1](#0-0) [2](#0-1) 

This is directly analogous to the reported `while`-loop walking a shared linked structure until a match is found: the number of loop iterations is proportional to the number of currently unstable units in the DAG, and that number is attacker-influenced. Any unprivileged unit poster can post a large number of cheap, valid units (any of which populate `storage.assocUnstableMessages` while they remain unstable, i.e., until MC stabilization catches up), causing every subsequent AA trigger that uses a data-feed condition to pay for scanning the full unstable set — this cost is borne synchronously during unit/AA validation and response composition (called from oscript authentifier evaluation in `definition.js` and from bounce/response formula evaluation in `formula/evaluation.js`): [3](#0-2) [4](#0-3) [5](#0-4) 

Unlike the Solidity report where a hard per-tx gas limit caps the damage (and can revert the whole upkeep), in `ocore` the effect is unbounded synchronous CPU work performed by every node validating/responding to a unit or AA trigger — worse in one sense (no built-in cap), because there is no `minimumAssets`-style economic floor preventing an attacker from posting many small, valid units with `data_feed` messages or plain payments (the loop iterates the whole unstable set irrespective of message type, `data_feed` filtering happens inside the `forEach`).

### Impact Explanation
Because the loop runs on the hot path of AA trigger evaluation, an attacker who inflates `storage.assocUnstableMessages` (by broadcasting a burst of otherwise-valid units before they stabilize) can materially slow down or stall processing of legitimate AA triggers that rely on `data_feed`/`in_data_feed` conditions across the network — every full node performing validation/AA execution pays the same O(n) cost. In the worst case this degrades to nodes falling behind on validating/executing new units containing such formulas, i.e., a "network unable to confirm new units in a timely manner" condition for AA-heavy oscript paths, matching the accepted impact category from the external report (DoS on a decision-critical execution path reachable by an ordinary poster).

### Likelihood Explanation
Likelihood is moderate-to-high: no special privilege is needed — any address can post standard units to grow the unstable set, and no `minimumAssets`-like floor gates this specific loop (it iterates on any object key in `assocUnstableMessages`, not filtered by economic value before the scan). The main mitigating factor is that `assocUnstableMessages` self-prunes as units stabilize, so the attack requires sustained unit-posting to keep the unstable set large, and the actual per-call cost depends on how many oracle-based AA triggers/executions occur concurrently with the inflated unstable set.

### Recommendation
Bound the "include unstable" scan: index unstable data-feed messages by `(address, feed_name)` (e.g., an auxiliary map maintained incrementally as units are added to/removed from `assocUnstableMessages`) instead of scanning the full unstable-unit map on every formula evaluation, analogous to the report's recommendation of splitting the shared walk into a dedicated, matching-direction structure. This turns the lookup from O(number of unstable units) into O(matches) regardless of how many unrelated unstable units exist.

### Proof of Concept
1. Attacker (or anyone) rapidly posts many valid, low-value units to the network; while unstable, each is added to `storage.assocUnstableMessages` (population path not fully confirmed from the indexed code — `writer.js` and `storage.js` both reference `assocUnstableMessages` but the exact insertion point could not be located within the tool's index; this should be verified directly in the repo).
2. While the unstable set is large, any AA trigger unit (or `bounce`/`response` formula) using `data_feed[[...]]` or `in_data_feed[[...]]` with default "include unstable" behavior triggers `readDataFeedValue`/`dataFeedExists`, which iterates all entries of `storage.assocUnstableMessages`: [6](#0-5) 
3. Each such AA trigger now costs O(n) work proportional to the attacker-inflated unstable set, repeated for every full node validating/executing the trigger, degrading throughput for the whole network for as long as the attacker sustains the flood.

**Uncertainty note:** I was not able to confirm within the available index exactly where/how entries are added to and removed from `storage.assocUnstableMessages` (the population logic in `writer.js`/`storage.js` was referenced but not fully retrieved before the tool budget ran out), so the precise growth rate and any existing implicit caps could not be fully verified — a background session with full file access would be needed to confirm these details.
