### Title
Cross-tenant CCMenu status disclosure via stack-scoping bypass in `CCMenuController#stack` - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::CCMenuController` overrides the base `stack` accessor to call `Stack.from_param!(params[:stack_id])` directly instead of the inherited `stacks.from_param!(params[:stack_id])`, which is the mechanism that confines an `ApiClient` to the single stack referenced by its `stack_id`. As a result, an `ApiClient` token that was issued and scoped to one stack can be used to read the CCMenu build status (`lastBuildStatus`, `activity`, `lastBuildLabel`, etc.) of any other stack in the installation.

### Finding Description
The binding that must hold is: `current_api_client.stack_id.nil? || current_api_client.stack_id == stack.id` for any stack rendered by an authenticated API request. `Shipit::Api::BaseController` enforces exactly this via its `stacks`/`stack` methods: [1](#0-0) 

`stacks` restricts the queryable relation to `Stack.where(id: current_api_client.stack_id)` when the client is stack-scoped, and `stack` resolves `params[:stack_id]` only within that relation, raising `RecordNotFound` for stacks outside the client's scope.

`CCMenuController`, however, redefines `stack` to bypass this relation entirely: [2](#0-1) 

It only enforces `require_permission :read, :stack` (a before_action), which calls `current_api_client.check_permissions!(:read, :stack)`: [3](#0-2) 

`check_permissions!` only checks the string permission `"read:stack"` against the client's `permissions` array; it never inspects `stack_id` or compares it to the resolved `stack`. So any client with the generic `read:stack` permission - including one that was deliberately scoped to a single stack via `stack_id` - can supply any other stack's `to_param` in `params[:stack_id]` and `Stack.from_param!` will happily resolve it, since it queries the whole `Stack` table rather than the client's `stacks` scope.

Exploit flow: an attacker who legitimately possesses (or is issued) an `ApiClient` token scoped to stack A (`stack_id` set, permission `read:stack`) sends `GET /:other_stack_id/ccmenu.xml?token=<their_own_valid_token>` for stack B. `authenticate_api_client` in `CCMenuController` succeeds via `ApiClient.authenticate(params[:token])`, `require_permission!(:read, :stack)` passes because the token has the generic permission, and `stack` resolves stack B directly, leaking stack B's deploy/task status in the rendered CCMenu XML.

### Impact Explanation
This is an unauthenticated-read-equivalent cross-tenant disclosure: a token intentionally restricted to one stack (a common configuration for giving least-privileged CI/monitoring integrations access to a single project) can read build/deploy status of every other stack in the Shipit instance via `/:stack_id/ccmenu.xml`. It exposes `lastBuildStatus`, `activity`, lock state, and deploy timing for arbitrary stacks the caller was never granted access to. This matches "High: escalation... unauthenticated read of stack state" per the severity rubric (the effective confinement guarantee of `stack_id`-scoped tokens is bypassed for this endpoint), and is repeatable against any stack in the installation using a single valid, narrowly-scoped token.

### Likelihood Explanation
The attacker only needs one legitimate `ApiClient` token with `read:stack` permission and a `stack_id` restriction (a normal, supported configuration meant to be least-privilege) — no secrets, no privileged role, no session. The request is a single unauthenticated (session-wise) GET to a documented, publicly reachable endpoint (`/:stack_id/ccmenu.xml`), with the target stack's slug/id guessed or enumerated. This is trivially reproducible and requires no special server configuration beyond having any stack-scoped API client provisioned, which is a documented feature (`ApiClient#stack_id`).

### Recommendation
Change `CCMenuController#stack` to reuse the inherited scoping instead of hitting `Stack` directly, e.g.:

```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```

removing the override entirely so it inherits `BaseController#stack`/`#stacks`, restoring the `stack_id` confinement for stack-scoped `ApiClient`s.

### Proof of Concept
In `test/controllers/api/ccmenu_controller_test.rb` (existing suite already authenticates via `authenticate!` and uses `@client`/`@stack`):

1. Create two stacks, `stack_a` and `stack_b` (e.g. via `Stack.create!` fixtures).
2. Update the authenticated `@client` to be scoped to `stack_a`: `@client.update!(stack_id: stack_a.id, permissions: ['read:stack'])`.
3. Request `get :show, params: { stack_id: stack_b.to_param, token: @client.authentication_token }`.
4. Assert (broken binding, current behavior): `assert_response :ok` and `assert_payload 'name', stack_b.to_param` — i.e., a token scoped to `stack_a` successfully reads `stack_b`'s CCMenu XML.
5. Expected/fixed behavior: the request should raise `RecordNotFound` (via `stacks.from_param!`) and be rescued into a 404, i.e., `assert_response :not_found`, proving `current_api_client.stack_id == stack.id` (or `stacks.exists?(stack.id)`) is enforced.
