### Title
API requests can attribute privileged actions (deploys, task triggers, aborts) to an arbitrary `User` via an unauthenticated `X-Shipit-User` header - ([File: app/controllers/shipit/api/base_controller.rb])

### Summary
The bug class in the report is that `requestId` is derived without binding to any authenticated/unique actor (`msg.sender`), so a value that should be scoped to the caller can instead be supplied/collided by anyone. The Shipit API has the same class of defect in `Api::BaseController#identify_user`: the `User` that gets bound to `current_user` (and therefore recorded as the author of a deploy/task/abort) is selected purely from a client-supplied `X-Shipit-User` header, with no cryptographic binding to the authenticated principal (the `ApiClient` token).

### Finding Description
`ApiClient` authentication is the only verified credential on the API surface. `authenticate_api_client` resolves `@current_api_client` from the `Authorization` header token via `ApiClient.authenticate`, which is checked with `SimpleMessageVerifier` (an HMAC-signed value): [1](#0-0) 

Separately, `current_user` — the actor that ends up recorded on `Deploy#user_id`, `Task#user_id`, or passed as `aborted_by` — is derived like this: [2](#0-1) 

```ruby
def current_user
  @current_user ||= identify_user || AnonymousUser.new
end

def identify_user
  user_login = request.headers['X-Shipit-User'].presence
  User.where('lower(login) = ?', user_login.downcase).first if user_login
end
```

There is no verification that the caller actually is the named user — no signature, no session, no OAuth token check — just a case-insensitive lookup by `login`. This is the same "acted-on field never covered by the verified signature" pattern from the report: the credential that is actually verified (the `ApiClient` bearer token) authorizes only `operation:scope` permissions (`deploy:stack`, etc.) via `check_permissions!`: [3](#0-2) 

but the *identity* attributed to the resulting action (`current_user`) is a completely separate, attacker-controlled field that the verified token/signature does not cover at all.

Concretely, `DeploysController#create` uses `current_user` as the actor of the deploy: [4](#0-3) 

and `TasksController#trigger`/`#abort` use it the same way: [5](#0-4) 

Existing tests confirm this is intentional, header-driven behavior with no additional check: [6](#0-5) 

The binding that is broken, expressed as an equality that should hold but does not:
`identity authorized by the verified credential (ApiClient) == identity recorded/acted upon as current_user`

Any holder of a valid `ApiClient` token with `deploy:stack` permission for a stack can set `X-Shipit-User: <any existing login>` and have Shipit permanently record that arbitrary user as the one who triggered a deploy, triggered a task, or aborted a task — including users who never made the request and have no relationship to the calling `ApiClient`.

### Impact Explanation
This crosses an identity/authentication trust boundary: it lets a caller who only possesses a scoped `ApiClient` token forge the `User` attribution on high-impact actions (`Deploy`, `Task`, aborts). This corrupts the audit trail used throughout the UI/hooks (e.g. `Hook.emit` payloads include the task/deploy which embeds the falsified `user`), and can be used to implicate/frame another user for an unauthorized deploy or rollback, or to defeat any downstream logic/reporting that trusts `task.user`/`deploy.user` as a faithful record of who acted. Because deploy/rollback/task-trigger are the core "unauthorized deploy" primitives Shipit exists to gate, and the actor field is exactly the field meant to establish accountability for that gate, this satisfies the High-impact category of "escalation into authorization" in spirit — though note the underlying `deploy:stack`/`read:stack` permission check itself is not bypassed; what is bypassed is the integrity of *who* is authorized to have performed the privileged action.

### Likelihood Explanation
Likelihood is high for any deployment that grants third parties (e.g. CI systems, chatops bots) `ApiClient` tokens: nothing prevents such an integration, or a compromised low-privilege API client, from setting an arbitrary `X-Shipit-User` value on every request. No secret guessing or race condition is required — it is a single deterministic header value.

### Recommendation
Do not let `current_user` be derived from a bare, unauthenticated request header. Either bind `X-Shipit-User` to the same trust boundary as `ApiClient` (e.g., only honor it for `UnlimitedApiClient`/first-party integrations, or require it be signed/associated with the `ApiClient` record, e.g. a `creator`-scoped allow-list), or remove per-request user impersonation entirely and always attribute API-triggered actions to the `ApiClient`'s own `creator`.

### Proof of Concept
1. Obtain a valid `ApiClient` token with only `deploy:stack` permission (e.g. one meant to be used by an unrelated CI job).
2. `POST /api/stacks/:stack_id/deploys` with `Authorization: Basic <token>` and header `X-Shipit-User: victim-admin-login`.
3. Observe `Deploy#user_id` (and thus the audit trail, hooks, and UI) records `victim-admin-login` as the person who triggered the deploy, even though that user never made this request and has no association with the presented `ApiClient` token — matching test expectations in `test/controllers/api/tasks_controller_test.rb:118-126` where `aborted_by` is set purely from the header value.
