### Title
Stale block-cached liquidity index lets one user's borrow overvalue zToken collateral written down by another user's `socialize-debt` in the same block - ([File: mainnet/contracts/market/v0-4-market.clar])

### Summary
`market.clar` maintains a per-block cache, `index-cache`, keyed only by `{ timestamp: stacks-block-time, aid }`, that is filled by *whichever transaction accrues the vault first* in a block and read by *every* subsequent transaction in that block via `get-cached-indexes` / `resolve-ztoken`. Bad-debt socialization (`socialize-debt`) writes the vault's real `lindex` down directly in the vault contract but never touches or invalidates `market.clar`'s `index-cache`. Consequently, once the cache for an asset is primed in a block, any later caller in that same block who prices a zToken via `resolve-ztoken` receives the pre-socialization (too-high) `lindex`, even though the vault's true backing has just been written down.

### Finding Description
`accrue-and-cache` in `mainnet/contracts/market/v0-4-market.clar` populates a shared, tx-independent cache: [1](#0-0) 

The cache key contains no `tx-sender`/`contract-caller` component — it is `{ timestamp: stacks-block-time, aid }` — so it is a block-wide shared cache primed by the first caller and consumed by everyone else in that same block: [2](#0-1) 

`resolve-ztoken`, used to price zToken collateral (zSTX, zsBTC, zstSTX, zUSDC, zUSDH, zstSTXbtc) for health checks/borrows, reads this cache directly rather than re-querying the vault: [3](#0-2) 

Meanwhile, `socialize-debt` in the vault (e.g. `mainnet/contracts/vault/v0-vault-stx.clar`) writes down `lindex` directly to reflect a liquidation shortfall/bad debt, bypassing `accrue-and-cache` and the market's `index-cache` entirely: [4](#0-3) 

Because `index-cache` only writes on a **miss** and never reconciles with vault state mutated by `socialize-debt`, the following ordering is possible within one block (same `stacks-block-time`):
1. User A performs any market operation touching asset `aid` (e.g. a borrow or accrual on an unrelated position) — this calls `accrue-and-cache(aid)`, which is a cache miss, so it stores the *current* (pre-writedown) `{index, lindex}` for `{timestamp, aid}`.
2. A liquidator triggers bad-debt socialization for `aid` — the vault's real `lindex` is lowered to reflect the loss, but the market's cached `lindex` for that block/asset is untouched.
3. Attacker (or any user) in the same block calls `borrow`/`collateral-add` using the corresponding zToken (e.g. zSTX) as collateral. `resolve-ztoken` hits the cache (step 1's stale, higher `lindex`) instead of the true, written-down value, so the zToken collateral is overvalued for health-check purposes.

The victim here is the shared vault/protocol solvency and the other suppliers of that vault: the attacker's position is approved as healthy using inflated collateral value, letting them extract debt that the real (post-socialization) collateral value does not support.

### Impact Explanation
This allows a user to borrow against collateral valued using a stale, pre-loss index, extracting debt in excess of the true backing value immediately after a bad-debt event. Because the shortfall from bad debt is amplified rather than absorbed, this is theft of protocol funds / a path to protocol insolvency — a Critical-class impact, not merely a stale-price nuisance to the caller himself, since it harms the shared vault's remaining suppliers.

### Likelihood Explanation
The likelihood depends on `socialize-debt` (a liquidation-shortfall / bad-debt path) occurring in the same block as some prior cache-priming transaction for the same asset and a subsequent zToken-collateral operation, all before block time advances. This requires either MEV-style transaction ordering within a block or coincidental multi-transaction blocks — plausible on Stacks where multiple market/liquidation transactions can land in the same block, but it is a narrower, block-scoped timing window rather than an always-exploitable bug.

### Recommendation
Invalidate or update the market's `index-cache-`/`index-cache` entry for an asset whenever `socialize-debt` (or any vault state mutation affecting `lindex`) is invoked, or have `resolve-ztoken` bypass the cache and always fetch the vault's live `lindex` right after any socialization event, e.g., by having `vault-socialize-debt` in `market.clar` explicitly `map-delete`/`map-set` the corresponding `index-cache` entry with the freshly written-down `lindex`.

### Proof of Concept
1. In block N, User A calls `borrow`/`collateral-add` touching vault asset `STX`, priming `index-cache` at `{timestamp: T, aid: STX}` with `{index: I0, lindex: L0}`.
2. Still in block N, a liquidator calls `liquidate`, which triggers `socialize-debt` on `vault-stx`, writing the vault's `lindex` down to `L1 < L0` to absorb a shortfall.
3. Still in block N, an attacker calls `borrow` using `zSTX` as collateral. `resolve-ztoken` calls `get-cached-indexes(STX)`, gets a cache hit returning `{index: I0, lindex: L0}` (stale), and prices the attacker's zSTX collateral using `L0` instead of the true `L1`.
4. The attacker's health check passes using the inflated collateral valuation, and they borrow more debt than the real, written-down collateral value supports, leaving the vault under-collateralized for that amount.

```text
(define-private (accrue-and-cache (aid uint))
  (let ((cache-key { timestamp: stacks-block-time, aid: aid })
        (cached? (map-get? index-cache cache-key)))

    (match cached?
      ;; cache HIT: return cached value (1 read only)
      cached-indexes (ok cached-indexes)

      ;; cache MISS: accrue and cache (vault-accrue now returns indexes)
      (let ((indexes (try! (vault-accrue aid))))
        ;; store in cache
        (map-set index-cache cache-key indexes)
        (ok indexes)))))
```

```text
(define-public (socialize-debt (scaled-amount uint))
  (let ((scaled-principal (var-get principal-scaled))
        (borrowed (var-get total-borrowed))
        (idx (var-get index))
        (current-assets (var-get assets))
        (current-lindex (var-get lindex))
        (old-total-assets (total-assets))
        (debt-reduction (mul-div-down scaled-amount idx INDEX-PRECISION))
        (principal-reduction (if (> scaled-principal u0)
                                (mul-div-down scaled-amount borrowed scaled-principal)
                                u0))
        ;; Write down lindex proportionally to loss in total-assets
        (new-lindex (if (and (> old-total-assets u0) (> old-total-assets debt-reduction))
                       (mul-div-down current-lindex (- old-total-assets debt-reduction) old-total-assets)
                       u0)))

    (try! (check-caller-auth))
    (asserts! (> scaled-amount u0) ERR-AMOUNT-ZERO)

    (var-set lindex new-lindex)
    (var-set principal-scaled (if (> scaled-principal scaled-amount) (- scaled-principal scaled-amount) u0))
    (var-set total-borrowed (if (> borrowed principal-reduction) (- borrowed principal-reduction) u0))
    (var-set assets (if (> current-assets principal-reduction) (- current-assets principal-reduction) u0))

    (print {
      action: "socialize-debt",
      caller: contract-caller,
      data: {
        scaled-amount: scaled-amount,
        debt-reduction: debt-reduction,
        principal-reduction: principal-reduction,
        old-lindex: current-lindex,
        new-lindex: new-lindex,
        old-total-assets: old-total-assets,
        principal-scaled: (if (> scaled-principal scaled-amount) (- scaled-principal scaled-amount) u0),
        total-borrowed: (if (> borrowed principal-reduction) (- borrowed principal-reduction) u0),
        index: idx
      }
    })

    (ok true)))
```
