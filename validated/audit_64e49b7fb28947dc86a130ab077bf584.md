### Title
Autonomous Agents Can Permanently Lock Funds Sent in Assets Not Whitelisted by the AA's Own Logic - (File: aa_composer.js)

### Summary
Any address can trigger an AA by sending it a payment denominated in any existing on-chain asset, because neither `validateAATriggerObject` nor `validateAATrigger` restrict which assets may be sent to an AA — they only verify that the asset exists on-chain. [1](#0-0) [2](#0-1)  If the AA's oscript logic has no `case` that matches this "unsupported" asset and the asset is also absent from `bounce_fees`, the funds are absorbed into the AA's balance with no way to ever bounce or spend them out.

### Finding Description
`getTrigger()` accumulates payment outputs for *any* asset sent to the AA address into `trigger.outputs`, without any asset whitelist. [3](#0-2)  `updateInitialAABalances()` then unconditionally credits every one of these assets to the AA's on-chain balance before any AA-specific logic runs. [4](#0-3) 

When `evaluateAA` runs the AA's `cases`, if none of the `if` conditions match, evaluation reports the error `"neither case is true in " + name` [5](#0-4) , which flows back to `handleTrigger` and calls `bounce(err)`. [6](#0-5) 

Inside `bounce()`, refunds are only generated per-asset using `bounce_fees[asset] || 0` as the fee. If the asset is not declared in `bounce_fees`, `fee` is `0`; since `fee === amount` triggers a `continue` that skips pushing any refund message for that asset. [7](#0-6)  The bytes (`base`) portion is still refunded because `bounce_fees.base` always defaults to `constants.MIN_BYTES_BOUNCE_FEE`, but the unrecognized asset is not — it remains permanently recorded in `aa_balances` for that AA address with no oscript path capable of moving it, since AA definitions are immutable once deployed (no upgrade mechanism, no owner-only rescue function).

### Impact Explanation
Any unprivileged user or contract sending an unsupported/unexpected asset to an existing AA can cause that asset to become permanently and irrecoverably locked in the AA's balance, since AAs have no analogue to `removeFunds`/owner rescue and their logic cannot be amended post-deployment. This is a direct AA fund freezing/loss scenario reachable by any address that posts a payment+trigger unit to an existing AA.

### Likelihood Explanation
Every AA deployed with a `cases`-based `messages` template (a very common oscript pattern, e.g., the sample AAs in the codebase such as `order_book_exchange.oscript`/`a_bank_without_percent.oscript`) is exposed unless its author explicitly coded a catch-all branch that recognizes and either bounces or accounts for arbitrary/foreign assets. [8](#0-7)  Since this requires no special privileges (any address can send any asset as a trigger), and the vast majority of AAs are written to work with one or two specific expected assets, an attacker or careless user can trivially trigger this by paying the AA in a random unrelated asset.

### Recommendation
Consider requiring `bounce()` (or a variant of it) to always attempt to refund *any* asset present in `trigger.outputs`, even those absent from `bounce_fees`, whenever no AA `case` matches, rather than silently absorbing them into the AA balance with `fee=0`. Alternatively, provide oscript authors with a built-in "reject unknown asset" facility so that assets not explicitly whitelisted by the AA are automatically bounced with zero fee retained.

### Proof of Concept
1. Deploy an AA whose `messages.cases` all have `if` conditions referencing `trigger.data` or a specific `asset` (e.g., `sell_asset_for_bytes.oscript`-style AA that only handles `base` and one specific asset). [9](#0-8) 
2. From any address, issue a new, unrelated divisible asset (any user can issue an asset in ocore) and send a trigger unit paying `bounce_fees.base` amount of bytes plus some amount of this new unrelated asset to the AA.
3. Since no `case.if` matches when only bytes+unknown-asset are present (assuming the fallback branch only checks for `asset=base` or `trigger.data`), evaluation reaches `"neither case is true"`, causing `bounce(err)`. [5](#0-4) 
4. `bounce()` refunds the bytes (since `bounce_fees.base` is set) but skips the unrelated asset because `bounce_fees[asset]` is `undefined` → `fee=0` → `fee === amount` → `continue`. [10](#0-9) 
5. `aa_balances` now permanently holds the unrelated asset for that AA address; no future trigger or AA logic can retrieve it because the AA definition cannot be changed and has no matching case for this asset.

		if (message.app === 'data' && !trigger.data) // use the first data message, ignore the subsequent ones
			trigger.data = message.payload;
		else if (message.app === 'payment' && message.payload) {
			var payload = message.payload;
			var asset = payload.asset || 'base';
			payload.outputs.forEach(function (output) {
				if (output.address === receiving_address) {
					if (!trigger.outputs[asset])
						trigger.outputs[asset] = 0;
					trigger.outputs[asset] += output.amount; // in case there are several outputs
				}
			});
		}
	});

	return trigger;
