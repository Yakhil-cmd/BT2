**Why this is invalid:**

The function in question, `genesis::initialize_validator` (and its caller `create_initialize_validator`), is a plain module-private `fun` with no `entry` modifier and no `public` visibility [1](#0-0) . Because it lacks `public entry`, it cannot be invoked by any user-submitted transaction through the normal transaction admission path (mempool → vm-validator → VM dispatch) — Move's script/entry-function dispatch only allows calling functions marked `public entry`. It is only reachable when the special genesis VM session directly executes the `genesis::initialize` sequence of calls at chain bootstrap, as driven by `aptos-move/vm-genesis/src/lib.rs`, not through any authenticator-checked transaction [2](#0-1) .

The `create_signer` native itself simply constructs a signer for the given address with no authentication check by design [3](#0-2) , and this is intentional — it is a privileged native usable only from framework code executed in genesis (and other bootstrap-only paths), not something exposed to arbitrary entry functions callable post-genesis. There is no post-genesis unprivileged entry point that reaches `create_signer(validator.operator_address)` inside `genesis.move`; the analogous "real" operator-authenticated path for consensus-key rotation is the separate `public entry fun` `stake::rotate_consensus_key`, which requires the actual operator's signer derived from a validated transaction authenticator, not `create_signer` [4](#0-3) .

Since the exploit requires invoking a non-`entry`, non-`public` genesis-only function via a normal signed transaction — which the Move VM's dispatch rules and the genesis-only execution model prevent — there is no admission-boundary path for an unprivileged attacker to trigger this code post-genesis.
