### Title
Webhook signature verification is keyed on `repository.owner.login`/`organization.login` while event handlers act on `repository.full_name`, letting an unsecured tenant's org silently authorize forged events for any other tenant's stack - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/`webhook_secret` to validate the incoming HMAC against using a field read straight out of the unverified JSON body (`repository.owner.login` or `organization.login`). The event `Handler` base class, however, resolves the `Stack`/`Repository` that is actually mutated using a *different* field of the very same unverified body (`repository.full_name`). These two fields are never cross-checked. In a multi-organization Shipit install (a supported and documented configuration - see `test/dummy/config/secrets_double_github_app.yml`), the GitHub webhook secret is explicitly optional per organization (docs/setup.md: "Webhook secret (optional)"), and `GithubApp#verify_webhook_signature` unconditionally returns `true` when no secret is configured for the selected org. An attacker can therefore address the signature check to any organization in the install that has no secret configured, while pointing the actual mutating field (`repository.full_name`) at a completely different, secret-protected organization/repository.

### Finding Description
- `verify_signature` picks the org whose secret is used for HMAC verification from the payload itself, before the payload is trusted: [1](#0-0) [2](#0-1) 
- `GithubApp#verify_webhook_signature` trivially returns `true` when that org has no `webhook_secret` configured: [3](#0-2) 
- The webhook secret is explicitly optional per the setup docs, and multiple organizations can be configured simultaneously in one Shipit install: [4](#0-3) 
- After the (bypassable) signature check, `WebhooksController#create` dispatches the raw, unverified body to registered handlers: [5](#0-4) 
- The base `Handler` class resolves the actually-affected `Stack` using `repository.full_name` - a field completely independent from the one used to pick the signing org: [6](#0-5) 
- `PushHandler` uses that resolution to enqueue a sync for real stacks based on attacker-controlled `ref`/`after`: [7](#0-6) 

The binding broken is: **the organization whose credential authenticated the request** (`repository_owner` used in `verify_signature`) **≠ the repository that is actually written to** (`repository_name` used in `Handler#stacks`). Nothing enforces that these two must refer to the same tenant/org, so an attacker only needs one weakly-configured (secret-less) organization anywhere in the Shipit installation to forge events for any other organization's stacks.

### Impact Explanation
By forging a `push` webhook that is "authenticated" against an org with no configured `webhook_secret` but whose `repository.full_name` field names a different, unrelated stack, an unprivileged external attacker can make Shipit believe arbitrary commits were pushed to a victim stack it does not control, enqueuing `GithubSyncJob` for that stack. On stacks with continuous deployment enabled, this can lead to an unauthorized deploy being triggered from attacker-supplied SHA/ref data - satisfying the Critical impact bar ("an unauthorized deploy, rollback or merge"). Other handlers (`status`, `check_suite`, `membership`) are similarly reachable and could be used to write forged commit statuses/team memberships under the same bypass.

### Likelihood Explanation
Requires no credentials, no session, no repository access - only knowledge that the target Shipit instance hosts more than one GitHub organization and that at least one of them has no `webhook_secret` configured (an explicitly optional, documented setting). Multi-org setups are a first-class supported configuration in this engine, so the precondition is realistic for larger deployments serving multiple teams/orgs.

### Recommendation
Bind signature verification to the same identity that is used to resolve the mutated resource. Concretely:
- Verify the webhook signature using the org/secret derived from the `Repository` record that `repository.full_name` actually resolves to (looked up in Shipit's own database), not from attacker-supplied `repository.owner.login`/`organization.login`.
- Alternatively, after selecting the org for signature purposes, assert that `repository.owner.login` matches the owner of the `Repository` resolved via `repository.full_name` before dispatching to handlers, and reject on mismatch.
- Do not allow `verify_webhook_signature` to silently pass (`return true unless webhook_secret`) for any organization if other organizations in the same install do have secrets configured; require every configured organization to have a webhook secret in multi-org deployments, or fail closed rather than open when a secret is absent.

### Proof of Concept
1. Configure Shipit with two organizations, mirroring `test/dummy/config/secrets_double_github_app.yml`: `org-open` (no `webhook_secret`) and `victim-org` (has `webhook_secret` and owns stack `victim-org/critical-app` with continuous delivery enabled).
2. Attacker sends:
```
POST /webhooks
X-Github-Event: push
X-Hub-Signature: sha1=deadbeef   (arbitrary, unverifiable)

{
  "ref": "refs/heads/main",
  "after": "<attacker chosen sha already fetched/known>",
  "repository": {
    "full_name": "victim-org/critical-app",
    "owner": { "login": "org-open" }
  }
}
```
3. `WebhooksController#verify_signature` computes `repository_owner` = `"org-open"`, fetches `Shipit.github(organization: "org-open")`, whose `webhook_secret` is `nil`, so `verify_webhook_signature` returns `true` regardless of the bogus `X-Hub-Signature` header.
4. `PushHandler#stacks` resolves via `repository_name` = `payload.dig('repository','full_name')` = `"victim-org/critical-app"`, matching the real, secret-protected victim stack, and calls `stack.sync_github(expected_head_sha: params.after)`, enqueuing `GithubSyncJob` for it - despite the attacker never knowing `victim-org`'s webhook secret.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
