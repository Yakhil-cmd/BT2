### Title
Webhook Signature Verified Against `repository.owner.login` While Handlers Resolve the Target Repository From the Unchecked `repository.full_name` Field, Enabling Cross-Organization Forged Events - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
This is a direct analog of the reported bug class: a security-relevant decision (which HMAC secret authorizes the request) is bound to one field of an attacker-controlled payload, while a *different*, unchecked field of the same payload is what actually gets written/acted upon. In the Move report, `deposit_init_for_xinit` never coordinated concurrent state (`staking_account.last_height`) against the entities acting on it. Here, `WebhooksController` never cross-checks the organization used to select the verification secret against the repository that the webhook handlers actually mutate.

### Finding Description
`WebhooksController#verify_signature` picks the GitHub App/secret to verify the HMAC signature by reading the *attacker-supplied* organization field out of the still-unverified JSON body: [1](#0-0) [2](#0-1) 

```
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

`Shipit.github(organization: repository_owner)` looks up a per-organization webhook secret (a Shipit deployment can host many independent GitHub organizations/apps, each with its own `webhook_secret`, as documented in `config/secrets.development.shopify.yml` and `docs/setup.md`). If the signature validates for *that* organization, the entire raw body — including all other fields — is treated as trusted: [3](#0-2) 

Critically, `verify_webhook_signature` returns `true` unconditionally whenever that organization has no `webhook_secret` configured at all (`return true unless webhook_secret`), which the docs explicitly allow as valid configuration.

Once `verify_signature` passes, `create` dispatches the *same, single* JSON payload to event handlers: [4](#0-3) 

But every handler resolves the *target* repository/stack from a completely different payload field — `repository.full_name` — via `Handler#repository_name` / `Handler#stacks`: [5](#0-4) 

This pattern repeats in `PushHandler`, `StatusHandler`, `CheckSuiteHandler`, and all `PullRequest::*Handler` classes: [6](#0-5) [7](#0-6) [8](#0-7) 

Nowhere is `repository.owner.login` (the field that selected the verification secret) checked for consistency with `repository.full_name` (the field that selects the `Repository`/`Stack` actually mutated). Both fields originate from the same forgeable JSON body, and an attacker fully controls them independently.

**Binding broken (equality that should hold but doesn't):**
`organization authenticated by verify_signature (repository.owner.login / organization.login)` == `repository actually written by the handler (repository.full_name)`
This equality is never enforced, so the two can diverge.

### Impact Explanation
An attacker who can produce a validly-signed webhook body for *any one* organization configured on the Shipit instance — including an organization whose `webhook_secret` is left blank (an explicitly supported, documented configuration) — can set `repository.full_name` to point at a stack belonging to an *entirely different, unrelated organization* tracked by the same instance. This lets the attacker:

- Trigger `StatusHandler#process`, forging a `success` CI status on an arbitrary commit sha of the victim's repository, defeating the `ci.require` deploy-gate documented in README.md and flipping `Commit#deployable?` to true for a commit that never actually passed CI — enabling an unauthorized deploy of that commit.
- Trigger `PushHandler#process`, forcing `GithubSyncJob` to run against a victim stack with an attacker-chosen `expected_head_sha`.
- Trigger `CheckSuiteHandler#process`, forcing check-run refreshes against victim commits.
- Manipulate PullRequest lifecycle handlers (archive/unarchive review stacks, mutate PR metadata) for repositories the attacker has no legitimate relationship with.

This is a cross-repository / cross-organization write and can lead to an unauthorized deploy, matching the Critical impact bar in scope.

### Likelihood Explanation
Likelihood is high in any multi-organization Shipit deployment (explicitly supported by config, see `config/secrets.development.shopify.yml` listing multiple orgs) where at least one configured organization either has a leaked/weak webhook secret or (per documented, supported configuration) no `webhook_secret` at all. No GitHub App private key, `ApiClient` token, Shipit session, or privileged account is required — only the ability to send an HTTP POST with a crafted JSON body and a signature valid for any one configured, low-trust organization.

### Recommendation
After resolving the target repository/stack from the payload, validate that `repository.owner.login` (the field used to select and pass the signature check) matches the owner encoded in `repository.full_name` before any handler is allowed to act. Alternatively, verify the signature using a secret bound to the resolved `Repository`/`Stack` record itself (looked up from `full_name`) rather than a value taken from the unverified payload, and require every configured organization to have a non-blank `webhook_secret` (removing the `return true unless webhook_secret` bypass) in `lib/shipit/github_app.rb`.

### Proof of Concept
1. Configure two organizations in `secrets.yml`: `orgA` (private repos, protected deploy pipeline) and `orgB` (e.g. left with `webhook_secret: nil`, or whose secret the attacker otherwise knows).
2. Attacker crafts a `status` webhook JSON body:
   - `repository.owner.login` = `"orgB"` (or `organization.login` = `"orgB"`)
   - `repository.full_name` = `"orgA/protected-repo"`
   - `sha` = SHA of a real, unreviewed commit on orgA's protected stack
   - `state` = `"success"`
3. Sends `POST /webhooks` with `X-Github-Event: status` and (if required) a signature computed with `orgB`'s secret.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: 'orgB')` and succeeds (trivially, if `orgB.webhook_secret` is blank).
5. `StatusHandler#process` resolves `Commit.where(sha: params.sha)` scoped by `repository.full_name = "orgA/protected-repo"` and creates a `success` status on that commit via `create_status_from_github!`, even though the request was never authorized by `orgA`.
6. The forged status can satisfy `ci.require` for orgA's stack, making an otherwise-unreviewed commit appear `deployable?`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
