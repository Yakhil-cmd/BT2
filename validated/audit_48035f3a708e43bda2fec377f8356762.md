### Title
Webhook signature verification is keyed to an unrelated `organization`/`repository.owner.login` field while the mutated stack is resolved from the independent `repository.full_name` field, allowing cross-org webhook forgery when any configured org lacks a `webhook_secret` - (File: `app/controllers/shipit/webhooks_controller.rb`, `lib/shipit/github_app.rb`, `app/models/shipit/webhooks/handlers/handler.rb`)

### Summary
`Shipit::WebhooksController#verify_signature` picks the `GitHubApp` used to check the HMAC signature from `params.dig('repository','owner','login') || params.dig('organization','login')`, while the actual write target is later resolved by `Handler#stacks` from the completely independent `payload.dig('repository','full_name')` field [1](#0-0) [2](#0-1) . Since the raw JSON body is fully attacker-controlled, these two fields can be set inconsistently, and `GitHubApp#verify_webhook_signature` returns `true` unconditionally whenever the selected org's `webhook_secret` is absent, regardless of signature bytes [3](#0-2) .

### Finding Description
The broken binding: the code implicitly assumes `repository_owner (used for verification) == owner_of(repository.full_name) (used for mutation)`, but no code enforces this equality.

- `verify_signature` selects the app via `Shipit.github(organization: repository_owner)` where `repository_owner` reads `repository.owner.login` (fallback `organization.login`) [4](#0-3) .
- `GitHubApp.new` sets `@webhook_secret = @config[:webhook_secret].presence`, and `verify_webhook_signature` does `return true unless webhook_secret` before ever inspecting the `X-Hub-Signature` header or hashing the body [3](#0-2) .
- `create` then dispatches the same untouched JSON `params` to `Shipit::Webhooks.for_event(event)` handlers [5](#0-4) .
- `PushHandler` (a `Handler` subclass) resolves the target stack purely from `payload.dig('repository', 'full_name')` via `Repository.from_github_repo_name` [2](#0-1)  and then calls `stack.sync_github` for every matching non-archived stack on the matching branch [6](#0-5) .

Because `repository.owner.login`/`organization.login` (used for auth) and `repository.full_name` (used for the write) are two independent, attacker-supplied strings in the same JSON body, an attacker can set `repository.owner.login` (or `organization.login` if `repository` key is omitted for the owner sub-object) to an org with no `webhook_secret`, while setting `repository.full_name` to `"target-org/target-repo"`. Signature verification short-circuits to `true` for the no-secret org, and the handler then mutates `target-org/target-repo`'s stack - a request never authenticated by `target-org`'s actual secret.

No other guard intercepts this: `drop_unhandled_event` only checks the event type is registered [7](#0-6) ; there is no cross-check anywhere between the org used for verification and the repository owner implied by `full_name`.

### Impact Explanation
Given the stated precondition (at least one org in `Shipit.github_apps` configured without `webhook_secret`), an unauthenticated attacker can submit a `push` (or any handled event) webhook with a forged/garbage `X-Hub-Signature`, claim `organization.login`/`repository.owner.login` = the no-secret org, but point `repository.full_name` at any other org's repository/stack. This triggers `stack.sync_github` (and other handler side effects for other event types) against a stack that was never protected by its own secret - matching the "payload for one repository mutating another's stack" critical impact category. The attack is repeatable against every stack belonging to every configured org, as long as one org lacks a secret; blast radius is tenant-wide across the whole Shipit installation, not limited to the misconfigured org's own repositories.

### Likelihood Explanation
Requires: (1) `Shipit.github_apps` multi-org config in use, and (2) at least one configured org entry with `webhook_secret` absent/blank. This is a plausible operational misconfiguration (e.g., an org onboarded without setting up the GitHub App webhook secret, or a legacy/test org). No credentials, sessions, or GitHub secrets are needed by the attacker - only knowledge (or guessing) of the no-secret org's login name, which may be visible via error messages, admin UI, or documentation. The exploit is a single unauthenticated HTTP POST, fully repeatable.

### Recommendation
Cryptographically bind the verified identity to the resource being mutated: derive the app/secret used for verification from the same field used for stack resolution (`repository.full_name`'s owner segment), not from a separate `organization`/`repository.owner.login` field that can diverge from it. Additionally, treat a missing `webhook_secret` as a hard misconfiguration error (fail closed, e.g. raise/log and reject with 500/422) rather than silently returning `true` in `GitHubApp#verify_webhook_signature`, so operator misconfiguration cannot silently disable signature checking for an entire org's fleet of stacks.

### Proof of Concept
1. Unit test on `GitHubApp#verify_webhook_signature`:
   - `app = GitHubApp.new('org-no-secret', { app_id: 1, installation_id: 1, private_key: 'x' })` (no `webhook_secret` key).
   - Assert `app.verify_webhook_signature('sha1=garbage', 'arbitrary body')` returns `true`.
2. Integration test on `WebhooksController#create`:
   - Configure `Shipit.github_apps` (via `secrets.github`) with two orgs: `org-no-secret` (no `webhook_secret`) and `target-org` (with a `webhook_secret` and an existing stack, e.g. `target-org/target-repo` on branch `master`).
   - POST `/webhooks` with header `X-Github-Event: push`, header `X-Hub-Signature: sha1=deadbeef` (invalid), and JSON body: `{"organization": {"login": "org-no-secret"}, "repository": {"full_name": "target-org/target-repo", "owner": {"login": "org-no-secret"}}, "ref": "refs/heads/master", "after": "<new sha>"}`.
   - Assert response status is `200`.
   - Assert `target-org/target-repo`'s `Stack` was mutated (e.g. `sync_github` was invoked / commit head updated), proving a write to `target-org`'s stack occurred without ever validating `target-org`'s own `webhook_secret` against the request bytes.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
