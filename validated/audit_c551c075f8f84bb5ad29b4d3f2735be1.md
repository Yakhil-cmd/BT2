### Title
CCMenu API bypasses ApiClient stack-scoping, allowing a stack-scoped token to read the build/deploy status of any stack - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Shipit::ApiClient` supports scoping a token to a single stack via `belongs_to :stack, optional: true` [1](#0-0) , and `Api::BaseController` enforces that scoping for every endpoint that resolves a stack from `params[:stack_id]`:

```ruby
def stacks
  @stacks ||= current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all
end

def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
``` [2](#0-1) 

This is confirmed as the intended authorization boundary by the test "an api client scoped to a stack will only see that one stack" [3](#0-2) .

`Api::CCMenuController`, however, overrides `stack` and resolves it directly against the global `Stack` relation, completely skipping the `current_api_client.stack_id` scoping check:

```ruby
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end
``` [4](#0-3) 

### Finding Description
The equality that should hold for every `Api::BaseController` subclass is: **the stack a token authorizes (`current_api_client.stack_id`) == the stack the request actually touches (`params[:stack_id]`)**, enforced by `stacks`/`stack` in `BaseController`. `require_permission :read, :stack` only checks that the *permission bit* `read:stack` is present in `ApiClient#permissions` [5](#0-4)  — it never checks *which* stack the permission applies to; that check is delegated entirely to the `stack`/`stacks` helper.

`CCMenuController` redefines `stack` to call `Stack.from_param!(params[:stack_id])` directly [4](#0-3) , bypassing the `stacks` scoping defined in the parent. As a result, any `ApiClient` bearing the generic `read:stack` permission — regardless of the specific `stack_id` it was created with — can fetch the CCMenu status (name, activity, `lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, `webUrl`) of *every* stack in the Shipit installation by simply substituting a different `stack_id` in the URL.

### Impact Explanation
This breaks the stack-scoping guarantee that the rest of the API relies on. A token intentionally minted for one stack (e.g. a "CCMenu Client" created by `CCMenuUrlController` for a public CI status widget, or any admin-issued stack-restricted `read:stack` token) can be replayed against `GET /api/:stack_id/ccmenu` for any other stack, disclosing its deploy/build status and last-deploy metadata cross-tenant/cross-repository. This is an unauthorized read of stack state outside the token's authorized scope.

### Likelihood Explanation
Exploitation only requires possession of any valid `read:stack`-permissioned token (no privileged account is needed to *use* an already-issued token — many are handed out for embedding in status badges/CI dashboards, i.e., semi-public). No signature forgery, GitHub credentials, or session are needed — only substituting the `stack_id` route/query parameter, matching the "stack a token authorises versus a stack it touches" analog class explicitly in scope.

### Recommendation
Remove the `stack` override in `Api::CCMenuController` and use the inherited, properly-scoped `stack`/`stacks` helpers from `Api::BaseController` (i.e., `stacks.from_param!(params[:stack_id])`) so the `current_api_client.stack_id` restriction is honored, consistent with every other API controller.

### Proof of Concept
1. An admin creates (or the app auto-creates via `CCMenuUrlController#client`) an `ApiClient` with `permissions: ['read:stack']`. Assume it is additionally scoped with `stack: stack_A` (the supported/intended usage per `ApiClient#belongs_to :stack`).
2. An attacker obtains this token (e.g., from a published CI status badge URL for `stack_A`, `/api/stack_A/ccmenu?token=<token>`).
3. The attacker requests `GET /api/stack_B/ccmenu?token=<token>` for an unrelated `stack_B`.
4. `CCMenuController#authenticate_api_client` authenticates the token via `ApiClient.authenticate(params[:token])` [6](#0-5) , and `require_permission :read, :stack` passes because the token has the `read:stack` bit set [7](#0-6) .
5. `stack` resolves via `Stack.from_param!(params[:stack_id])` (unscoped), returning `stack_B` and rendering its build/deploy status in the response — despite the token only being authorized for `stack_A`.
