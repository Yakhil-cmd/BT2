### Title
Unbounded response size during extension asset download enables disk-exhaustion DoS - (File: `pkg/cmd/extension/http.go`)

### Summary
`downloadAsset` in `pkg/cmd/extension/http.go`, invoked by `gh extension install <owner>/<repo>` (via `Manager.installBin` in `pkg/cmd/extension/manager.go`), streams an HTTP response body directly to disk with `io.Copy(f, resp.Body)` with no upper bound on size, no `Content-Length` pre-check, and no client-side timeout or deadline.

### Finding Description
When a user runs `gh extension install owner/gh-extension`, the CLI resolves the latest release via `fetchLatestRelease` and then calls `downloadAsset`: [1](#0-0) 
The function opens the destination file and copies the entire response body into it with an unbounded `io.Copy`, and the `http.Client` used (constructed in `api/http_client.go`) has no `Timeout` field set and no wrapping transport that enforces a maximum body size or read deadline: [2](#0-1) 
The same unbounded-copy pattern recurs at `pkg/cmd/release/download/download.go:300-351` (`gh release download`) and `pkg/cmd/run/download/http.go:31-73` (`gh run download`), all of which stream attacker/repo-controlled content to disk (or a temp file) without any size ceiling. Because the extension repository, its releases, and release asset bytes are fully attacker-controlled (any GitHub user can publish a `gh-*` repository and a release with an asset), this is directly analogous to the reported `callEVM` bug: external, attacker-supplied input drives resource consumption (here, disk I/O and space) with no configured limit, relying only on network transfer speed and available disk to bound the operation.

### Impact Explanation
An attacker who publishes a GitHub repository formatted as an installable `gh` extension (`gh-<name>`) with a release asset matching the user's platform can serve an extremely large or slow-to-terminate response body (e.g., many gigabytes, or a body that trickles bytes indefinitely while keeping the connection open). A victim running `gh extension install attacker/gh-extension` (a normal, expected, unprivileged CLI action, often following a README/blog recommendation) will have `gh` write unbounded bytes to disk in `m.installDir()`, exhausting disk space or hanging indefinitely, i.e., a denial-of-service condition local to the invoking machine—directly paralleling the "attacker deploys a computationally expensive contract, victim's node processes it with no bound" pattern in the original report, translated to "attacker publishes an oversized/slow release asset, victim's `gh` process downloads it with no bound."

### Likelihood Explanation
Likelihood is moderate-to-high in the sense that it requires no special privilege: any GitHub account can create a public repository, name it `gh-<something>`, and attach a release asset of arbitrary size for the user's platform. It only requires social engineering to get the target to run `gh extension install`, which is standard, documented CLI usage advertised throughout `gh`'s own extension ecosystem docs.

### Recommendation
Apply an explicit maximum size limit (e.g., `io.CopyN` or wrapping `resp.Body` in `http.MaxBytesReader`/`io.LimitReader`) and a client/request-level timeout or context deadline for `downloadAsset` in `pkg/cmd/extension/http.go`, and apply the same treatment to the equivalent unbounded `io.Copy` calls in `pkg/cmd/release/download/download.go` and `pkg/cmd/run/download/http.go`. Reject or truncate downloads that exceed a sane configured maximum (with a clear user-facing error), and surface progress/cancellation so a hung remote server cannot block the CLI indefinitely.

### Proof of Concept
1. Attacker creates a public repo `attacker/gh-demo` matching the `gh-<name>` extension naming convention.
2. Attacker publishes a GitHub Release with an asset named to match the victim's platform suffix (e.g., `gh-demo-darwin-amd64`), whose content is either a multi-hundred-GB file or a handler that streams data indefinitely with `Transfer-Encoding: chunked` and never closes the connection.
3. Victim runs `gh extension install attacker/gh-demo`.
4. `Manager.Install` → `isBinExtension`/`installBin` → `downloadAsset` (`pkg/cmd/extension/http.go:79-112`) issues the `GET` and pipes `resp.Body` into `io.Copy(f, resp.Body)` with no cap, filling the victim's disk or hanging the `gh` process until manually killed, since no `Timeout`, `Content-Length` check, or `LimitReader` exists anywhere in the request/response path (`api/http_client.go:33-87`). // downloadAsset downloads a single asset to the given file path.
func downloadAsset(httpClient *http.Client, assetURL safeurl.SafeURL, destPath string) (downloadErr error) {
	var req *http.Request
	if req, downloadErr = http.NewRequest("GET", assetURL.String(), nil); downloadErr != nil {
		return
	}

	req.Header.Set("Accept", "application/octet-stream")

	var resp *http.Response
	// TODO(api-client-rollout)
	// This has been deferred from moving to api.Client due to its custom Accept header and binary response streaming.
	if resp, downloadErr = httpClient.Do(req); downloadErr != nil {
		return
	}
	defer resp.Body.Close()

	if resp.StatusCode > 299 {
		downloadErr = api.HandleHTTPError(resp)
		return
	}

	var f *os.File
	if f, downloadErr = os.OpenFile(destPath, os.O_CREATE|os.O_WRONLY|os.O_TRUNC, 0755); downloadErr != nil {
		return
	}
	defer func() {
		if err := f.Close(); downloadErr == nil && err != nil {
			downloadErr = err
		}
	}()

	_, downloadErr = io.Copy(f, resp.Body)
	return
}
