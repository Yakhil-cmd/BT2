Confirmed: Shipit supports multi-organization GitHub App configuration, where `Shipit.github(organization:)` looks up a per-organization config (including a distinct `webhook_secret`) via `github_app_config(organization)` [1](#0-0) . Each organization entry under `secrets.github` can have its own `webhook_secret`, `app_id`, etc.

### Title
Webhook signature verified against an attacker-selected organization while the acted-upon repository comes from a different unverified field - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization config (and therefore which `webhook_secret`) to validate the request signature against based on `repository_owner`, computed from the untrusted, not-yet-verified JSON body (`params.dig('repository', 'owner', 'login')` or `organization.login`) [2](#0-1) . Once the signature check passes, the same raw payload is handed to handlers that instead resolve the target `Stack`/`Repository` using a *different* field of the same payload: `repository.full_name`, via `Handler#stacks`/`#repository_name` [3](#0-2) , and similarly in the pull-request handlers via `Shipit::Repository.from_github_repo_name(params.repository.full_name)` [4](#0-3) .

### Finding Description
The equality that should hold is: **the organization whose secret authenticated the webhook request == the organization owning the repository whose Stack/PullRequest data is mutated**. Because `repository_owner`, used purely to pick the verification secret, and `repository.full_name`, used to pick the entity acted upon, are two independently attacker-suppliable fields inside the same unverified JSON body, an operator of one legitimately configured GitHub organization (Org A, with its own valid `webhook_secret` in `secrets.github[:orgA]`) can send a POST to `/webhooks` where:
- `repository.owner.login` / `organization.login` = `"orgA"` (so `Shipit.github(organization: "orgA")`'s `webhook_secret` is used and the HMAC over the raw body validates, since Org A signs with its own real, legitimately-known secret),
- `repository.full_name` = `"orgB/some-repo"` — a repository belonging to a completely different, unrelated organization tracked by the same Shipit instance.

Signature verification in `GitHubApp#verify_webhook_signature` only checks that the HMAC over the raw payload matches the secret for the org selected by `repository_owner`; it performs no cross-check that the repository referenced elsewhere in the payload actually belongs to that same organization [5](#0-4) . Handlers then blindly trust `repository.full_name` to look up and mutate stacks (e.g., `push` triggers `sync_github`, `pull_request` events open/close/label review stacks, `check_suite` schedules check-run refreshes) belonging to Org B, which never signed this request.

### Impact Explanation
This breaks the deployment-trust boundary between organizations hosted on a shared Shipit instance: an attacker who legitimately controls one configured organization (and thus its own webhook secret) can forge webhook events that: create/archive/unarchive review stacks, alter PR labels used for provisioning decisions, or trigger `GithubSyncJob`/`sync_github` on a Stack belonging to a repository/organization they do not own. Given `PushHandler` and `ReviewStackAdapter` create resources and re-sync branch state, and provisioning decisions gate on labels/PR state pulled from the forged payload, this can lead to unauthorized creation/archival of stacks or corrupting sync state for another org's stack — i.e., cross-repository, cross-organization state manipulation via a webhook the target org never sent. This qualifies as a High-severity escalation of trust across repository/organization boundaries mediated entirely by the app's own signature-selection logic.

### Likelihood Explanation
Requires the attacker to control at least one organization that is itself configured with a legitimate `webhook_secret` in the multi-org `secrets.github` block (i.e., a tenant of a shared Shipit instance), which is a realistic deployment model this engine explicitly supports (`github_organizations`, `github_app_config` in `lib/shipit.rb`). No repository write access, GitHub token, or Shipit account is needed to exploit the mismatch — only the ability to send an arbitrary POST with a validly-signed-for-orgA body to the shared `/webhooks` endpoint targeting another org's `repository.full_name`.

### Recommendation
After computing the organization used for signature verification (`repository_owner`), also derive the organization implied by `repository.full_name` (the field handlers actually rely on) and reject the request (422) if the two do not match. Alternatively, always verify the signature using the config for the organization derived from `repository.full_name` rather than `repository.owner.login`/`organization.login`, so a single, consistent field of the payload drives both trust decisions.

### Proof of Concept
1. Shipit instance is configured with two organizations, `orgA` and `orgB`, each with its own `webhook_secret` in `secrets.github`, and both host stacks tracked by this Shipit instance.
2. Attacker administers `orgA`'s GitHub App/webhook config and thus knows `orgA`'s `webhook_secret` (a legitimate secret for a tenant they control).
3. Attacker crafts a `pull_request` (or `push`) webhook JSON body with `organization.login`/`repository.owner.login` = `"orgA"` but `repository.full_name` = `"orgB/target-repo"`, computes `X-Hub-Signature` using `orgA`'s secret, and POSTs it to `/webhooks`.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: "orgA")` and successfully verifies the signature [6](#0-5) .
5. The relevant handler (e.g. `PullRequest::OpenedHandler`) resolves `Shipit::Repository.from_github_repo_name("orgB/target-repo")` and creates/archives/mutates a review stack belonging to `orgB`, even though `orgB` never authorized this webhook [7](#0-6) .

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
