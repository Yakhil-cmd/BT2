## Title
Cross-organization team-membership forgery via `membership` webhook bypasses `Shipit.github_teams` authorization — ([File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App's `webhook_secret` to validate a webhook against using an attacker-controlled field of the *same* payload it later processes, but the field used for signature scoping (`organization.login`) is never cross-checked against the actual `Team` record that `MembershipHandler` ends up mutating. For a `Team` that already exists in Shipit's database, `find_or_create_by!(github_id:)` finds it purely by GitHub's numeric team id and skips re-assigning `organization`, so a caller who can produce a validly-signed `membership` webhook for *any* configured GitHub App/organization can add arbitrary GitHub users as members of a `Team` that actually belongs to a completely different organization — including a team referenced by `Shipit.github_teams`, which gates access to the whole application.

### Finding Description
Signature verification picks the signing secret from the payload itself: [1](#0-0) [2](#0-1) 

`repository_owner` falls back to `params.dig('organization', 'login')` for events (like `membership`) that carry no `repository` key. Shipit natively supports multiple independently configured GitHub Apps/organizations, each with its own `webhook_secret`, as shown by `secrets_double_github_app.yml` and `Shipit.github(organization:)`: [3](#0-2) [4](#0-3) 

`MembershipHandler#process` then finds or creates a `Team` keyed **only by the GitHub team's numeric `github_id`**: [5](#0-4) 

`Team.find_or_create_by!(github_id: params.team.id)` only executes the block (which sets `team.organization = params.organization.login`) when the record does **not** already exist. If a `Team` row for that `github_id` already exists (created earlier through a legitimate `membership`/`added` event, or via `Team.find_or_create_by_handle`), the block is skipped and the existing `organization` attribute is left untouched — the payload's `organization.login` is used only to pick the signing secret, never to re-validate that the team truly belongs to that organization: [6](#0-5) 

`team.add_member(member)` unconditionally appends the attacker-specified `User` (created on the fly via `User.find_or_create_by_login!`) to that team's membership: [7](#0-6) 

Authorization to use Shipit at all is gated purely by local `Team`/`Membership` rows, not by a live GitHub lookup: [8](#0-7) 

**The broken equality:** the code implicitly assumes
`organization authenticated by verify_signature == organization that owns the Team being mutated`,
but this only holds on team creation. For any pre-existing `Team`, the equality is never re-checked, so:
`organization authenticated (attacker's own configured org) ≠ organization actually owning the target Team`.

### Impact Explanation
An operator hosting Shipit for multiple GitHub organizations (a documented, supported configuration) has each org's administrators independently create their own GitHub App and choose their own `webhook_secret` — this is not a Shipit-operator secret, it is chosen by whoever set up the org-level GitHub App integration, i.e. by parties who are otherwise unprivileged with respect to *other* orgs hosted on the same Shipit instance. Because `github_id` values for GitHub teams are discoverable (e.g., via the public/team API or `org_teams`), an attacker controlling one org's webhook secret can forge a `membership` `added` event naming their own org (to pass `verify_signature`) while targeting the `github_id` of a privileged team belonging to an unrelated organization referenced in `Shipit.github_teams`. This grants the attacker's own GitHub identity membership in that team inside Shipit's database, which is the sole check performed by `User#authorized?`, escalating them into `Shipit.github_teams` authorization without ever needing a Shipit session, `ApiClient` token, or the target organization's actual credentials.

### Likelihood Explanation
Requires the attacker to control one legitimately configured GitHub App/org integration on the shared Shipit instance (a realistic multi-tenant scenario the code explicitly supports) and knowledge of a target team's numeric GitHub `github_id` (discoverable, non-secret). No access to the target organization's `webhook_secret`, GitHub App private key, or any Shipit session is required, making this a credible cross-tenant escalation path in shared deployments.

### Recommendation
In `MembershipHandler#find_or_create_team!` and `Team.find_or_create_by!`, always validate/refresh `team.organization` against the authenticated organization for both the create and update paths, and reject (or no-op) the event if the payload's `organization.login`/`repository_owner` used for signature verification does not match the `organization` already stored on the found `Team`. More generally, `WebhooksController#verify_signature` should ensure the organization used to select the signing secret is also the organization bound to every entity the corresponding handler is permitted to mutate.

### Proof of Concept
1. Shipit is configured with two orgs, `OrgA` (attacker-controlled GitHub App, attacker knows its `webhook_secret`) and `OrgB` (target org, whose team `shopify/developers`, `github_id: 100`, is listed in `Shipit.github_teams`).
2. A `Team` row for `github_id: 100` already exists in Shipit's DB with `organization: "OrgB"` (created earlier through legitimate `membership` traffic).
3. Attacker POSTs to `/webhooks` with header `X-Github-Event: membership`, body:
```json
{
  "action": "added",
  "team": { "id": 100, "name": "Developers", "slug": "developers", "url": "..." },
  "organization": { "login": "OrgA" },
  "member": { "login": "attacker-github-login" }
}
```
signed with `OrgA`'s `webhook_secret` in `X-Hub-Signature`.
4. `verify_signature` resolves `Shipit.github(organization: "OrgA")` and validates successfully with the attacker's own secret.
5. `MembershipHandler#find_or_create_team!` finds the existing `Team(github_id: 100, organization: "OrgB")` — the block is skipped, `organization` remains `"OrgB"`.
6. `team.add_member(User.find_or_create_by_login!("attacker-github-login"))` adds the attacker as a member of the `OrgB/developers` team.
7. The attacker's Shipit user now passes `User#authorized?` via `Shipit.github_teams`, gaining full access to the application without any legitimate relationship to `OrgB`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
