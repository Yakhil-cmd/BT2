### Title
Webhook signature is verified against the org named in the unverified payload, while handlers act on a different, unchecked `repository.full_name` field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks the HMAC secret to verify against by reading `repository.owner.login` (or `organization.login`) straight out of the still-unauthenticated JSON body, then checks the raw body against that org's `webhook_secret`. Once verification succeeds, every downstream `Webhooks::Handlers::Handler` subclass resolves the target `Stack`/`Repository` using a *different* payload field, `repository.full_name`, which is never cross-checked against the org that was actually used to verify the signature. This is the same class of bug as the reported `Whitelist.addCollateral` issue: a value the code trusts implicitly (`validCollateral[0] != _collateral`, here: "the org whose secret validated this payload") is not the same value the code actually acts on (`collateralParams[_collateral]`, here: `repository.full_name` used to look up the stack).

### Finding Description
- `verify_signature` derives `repository_owner` from the raw, unverified request body and uses it to select which `GitHubApp`/`webhook_secret` to check the signature against: [1](#0-0) [2](#0-1) 
- Multi-organization installs are explicitly supported, each with its own independent `webhook_secret` that its own org owner/admin knows (they created the GitHub App and copied the secret into `config/secrets.yml`), as documented in `docs/setup.md`'s "Using Multiple Github Applications" section.
- Every webhook handler (`PushHandler`, `StatusHandler`, `CheckSuiteHandler`, `PullRequest::*Handler`) resolves the affected repository/stack from `payload.dig('repository', 'full_name')` via `Shipit::Webhooks::Handlers::Handler#repository_name`/`#stacks`, completely independent of `repository_owner`: [3](#0-2) 
- `PushHandler#process` uses that resolved stack set to trigger a sync from the attacker-chosen `after` SHA: [4](#0-3) 
- `PullRequest::ClosedHandler` resolves `repository` the same way and calls `review_stack.archive!`: [5](#0-4) 

Because `repository_owner` (used for authentication) and `repository.full_name` (used for authorization/action target) are two independent fields inside the same JSON body, an operator/admin of *any one* Shipit-configured GitHub organization — who legitimately knows their own org's `webhook_secret` because they created that GitHub App — can craft an arbitrary JSON payload where `repository.owner.login` is set to their own org (so the signature check against their known secret passes) while `repository.full_name` is set to a *different* organization/repository tracked by the same Shipit instance. The signature check in `verify_webhook_signature` only authenticates the raw bytes against the secret for the org named in the payload; it never confirms that the same org actually owns the repository the handlers subsequently act on: [6](#0-5) 

The broken binding, stated as an equality that must hold but doesn't:
`organization whose webhook_secret authenticated the request == organization that owns repository.full_name the handlers act on`

### Impact Explanation
This lets a party who legitimately administers one onboarded GitHub organization (and thus knows only that org's `webhook_secret`) forge webhooks that are processed as if they came from a completely different, unrelated repository/organization also hosted on the same Shipit instance. Depending on which handler fires, this can:
- Force a `GithubSyncJob`/deploy-relevant resync of another team's stack with an attacker-chosen `after` SHA (`PushHandler`), affecting what commit is considered head/deployable.
- Archive another team's review stack via a forged `pull_request` "closed" event (`PullRequest::ClosedHandler`), and other `pull_request` handlers can similarly mutate labels/assignees/merge-request state on a stack that does not belong to the attacker's org.
- More broadly, any handler that trusts `repository.full_name` executes cross-organization/cross-repository state changes it should not be authorized to perform.

This satisfies the "cross-repository writes / unauthorized deploy" bar: the authenticated identity (org owning the signing secret) does not match the repository being written to.

### Likelihood Explanation
Requires the Shipit instance to be configured with more than one GitHub organization (explicitly documented and supported), and requires the attacker to control (as a legitimate admin) at least one of those onboarded organizations. This is a real, low-privilege-relative-to-victim-org scenario — the attacker has zero access to the victim org's secret, GITHUB_TOKEN, or Shipit session, yet can still act against the victim's stacks purely by crafting a raw HTTP POST to the public `/webhooks` endpoint with mismatched `repository.owner.login` vs `repository.full_name` fields.

### Recommendation
Bind authentication and authorization to the same field. Either:
1. Verify the signature using the secret associated with the *repository* being acted upon (derive it from `repository.full_name`'s owner segment, consistently, in every code path) rather than a separately-read `repository.owner.login`/`organization.login` fallback, or
2. After selecting the app/secret via `repository_owner`, explicitly assert that `repository.full_name`'s org segment (and `organization.login`, if present) matches `repository_owner` before dispatching to handlers, rejecting mismatches with `422`.

### Proof of Concept
1. Shipit is configured with two organizations, `OrgA` and `OrgB`, each with their own `webhook_secret` (`docs/setup.md`, "Using Multiple Github Applications").
2. `OrgA`'s admin knows `webhook_secret_A` (they created that GitHub App). `OrgB` hosts a stack the attacker does not administer.
3. Attacker crafts a JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>",
  "repository": { "owner": {"login": "OrgA"}, "full_name": "OrgB/victim-repo" }
}
```
4. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(webhook_secret_A, raw_body)>` and POSTs to `/webhooks` with `X-Github-Event: push`.
5. `verify_signature` reads `repository_owner == "OrgA"`, loads `Shipit.github(organization: "OrgA")`, and `verify_webhook_signature` succeeds (signature matches `webhook_secret_A`) [1](#0-0) .
6. `Webhooks.for_event('push')` dispatches to `PushHandler`, which resolves `stacks` from `repository.full_name == "OrgB/victim-repo"` [3](#0-2)  and calls `stack.sync_github(expected_head_sha: params.after)` on `OrgB`'s stack [4](#0-3)  — an org that never authenticated this request.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
