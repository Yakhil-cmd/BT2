### Title
Capped-asset issuance can be duplicated by concurrent/queued AA triggers before the guarding query observes the first `issue` input - (File: aa_composer.js)

### Summary
The `Erc20Quest.withdrawFee` bug class ("a fund-moving function can execute more than the single time it was meant to, because the only guard is a plain read-check rather than an atomic, persisted flag") maps in ocore to `issueAsset()` in `aa_composer.js`, which is responsible for minting units of a capped, AA-issued asset in response to a trigger.

### Finding Description
When an AA response mints a capped asset, the code path is: [1](#0-0) 

```
function issueAsset(cb2) {
    var objAsset = assetInfos[asset];
    ...
    if (objAsset.cap) { // only our AA can issue, no unstable consensus-breaking issues possible
        conn.query("SELECT 1 FROM inputs WHERE type='issue' AND asset=?", [asset], function(rows){
            if (rows.length > 0) // already issued
                return cb2('already issued');
            addIssueInput(1);
        });
    }
    ...
}
```

The only protection against issuing the capped supply more than once is a `SELECT` against the `inputs` table for any existing `type='issue'` row for that asset. This is exactly the same class of defect as `withdrawFee`: a plain read-then-act check with no atomic reservation, no unique-issue marker created up front, and no serialization guarantee that a second trigger being composed concurrently (or immediately queued after the first, before the first trigger's unit — and therefore its `issue` input — is written via `writer.js`'s `addInlinePaymentQueries`, which is what actually inserts the row into `inputs`) cannot pass the same check. The insertion of the `issue` row into `inputs` only happens when the unit is written by the writer: [2](#0-1) 

Because `issueAsset` merely reads `inputs` and does not itself insert any placeholder/lock row, any AA response composition that runs (or is retried) for the same asset before the winning unit's `inputs` row is committed will see zero rows and proceed to mint again, exactly as `withdrawFee` re-sends the fee because it lacks a persisted "already withdrawn" flag.

### Impact Explanation
If the capped-asset guard can be bypassed, the AA can issue more units of its capped asset than the declared `cap`, breaking the fixed-supply invariant that all holders and integrators rely on (analogous to protocol fees being drained beyond the intended one-time amount in the original report). This is a supply-inflation / unauthorized-minting impact, which the validation rules treat as accepted as long as it satisfies this single query-based check, i.e. the same "check is not atomic with the effect" root cause as `withdrawFee`.

### Likelihood Explanation
The comment in the code ("only our AA can issue, no unstable consensus-breaking issues possible") indicates the developers believe single-threaded execution and eventual serialization by the composer make this safe, and node-level scheduling of trigger handling is intended to be serialized. This significantly reduces likelihood versus the original finding (where literally anyone could call `withdrawFee` after end with no synchronization at all), because here the mint path is gated behind AA response composition rather than a public, permissionless entry point that can be re-invoked. I could not fully trace, within tool-call limits, whether the AA-trigger execution queue (`handleTrigger`/response composer flow in `aa_composer.js`) strictly guarantees serialized, non-reentrant processing per asset/AA before a unit's `inputs` are committed, which is required to fully confirm or refute exploitability of a race here.

### Recommendation
Do not rely solely on a read of the `inputs` table to gate one-time capped issuance. Either (a) ensure the AA-trigger/response composition pipeline is strictly serialized per AA address (so no second composition for the same asset can start before the first's unit, including its `inputs` rows, is durably written), or (b) introduce a persisted, atomically-checked marker (e.g., in `aa_addresses`/asset state or via a DB-level unique constraint reserved at composition start) explicitly recording that the capped asset has been issued, checked and set within the same transaction/lock that produces the issue input.

### Proof of Concept
Not independently reproducible from the indexed context alone: confirming exploitability requires tracing whether `aa_composer.js`'s outer trigger-handling loop (functions referenced but not fully retrievable within the tool-call budget, e.g. the primary/secondary trigger execution queue) can invoke `issueAsset` twice for the same capped asset before the first invocation's unit is persisted via `writer.js`. Due to index/tool-call limits I was unable to fully retrieve and verify the surrounding trigger-scheduling code to definitively prove or disprove a real race window; this should be verified with full repository access (e.g., a Devin session) before treating this as confirmed rather than a plausible analog.
