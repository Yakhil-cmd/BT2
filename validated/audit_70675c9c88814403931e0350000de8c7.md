### Title
Private Payment Chain Acceptance Cached as "Handled" Before Async Validation Completes — Validation Bypass on Resubmission (`GHSA-xg6x-h9c9-2m83` analog) - ([File: wallet.js])

### Summary
`handlePrivatePaymentChains()` in `wallet.js` writes the same-shaped payload into `handledChainsCache` as soon as all chain elements have been *queued* for validation, not after they are actually confirmed valid. Because `network.handleOnlinePrivatePayment`'s `ifQueued` callback invokes `cb()` immediately (deferring the real pass/fail result to a later `eventBus` event), the cache entry is created while genuine validation is still pending — mirroring the reported bug class where a session/authentication state is cached as "good" before the full verification chain (2FA) actually finishes.

### Finding Description
In `wallet.js`, `handlePrivatePaymentChains(ws, body, from_address, callbacks)`: [1](#0-0) 

For every chain element, `network.handleOnlinePrivatePayment` is invoked with three possible outcomes: `ifError`, `ifValidationError`, `ifAccepted`, and `ifQueued`. The `ifQueued` branch (the common outcome for light-wallet/hub message routing) calls `cb()` **synchronously and immediately**, without waiting for the actual asynchronous validation result: [2](#0-1) 

Real completion of validation for a queued element only happens later via `eventBus.once(key, function(bValid){...})`. Because `async.eachSeries`'s completion callback fires once every iteratee has called `cb()` — which for `ifQueued` items happens before `bValid` is known — the "no error" branch executes immediately after parsing/queueing, **not** after real per-chain validation completes: [3](#0-2) 

Here `handledChainsCache[cache_key] = Date.now();` is written unconditionally at this point, i.e., the chain set is marked "handled" while its true validity is still undetermined (or could later resolve to invalid via `cancelAllKeys()` if `bValid` is `false`).

Once this premature cache entry exists, any subsequent submission of the exact same `arrChains` payload (same `objectHash.getBase64Hash(arrChains)` cache key) short-circuits all processing: [4](#0-3) 

This unconditionally emits `all_private_payments_handled` and calls `callbacks.ifOk()` without re-invoking `network.handleOnlinePrivatePayment` or performing any of the actual per-element validation (signature/authentifier checks, spend-proof/double-spend checks, denomination/output_index consistency, etc.) that the first submission was still in the middle of.

This is structurally the same root cause as GHSA-xg6x-h9c9-2m83: a multi-step verification is only partially complete (the second factor / the actual `ifQueued` async validation) when the system records the composite operation as "cached/handled," and a later lookup trusts that cache instead of re-running the still-incomplete or possibly-failing check.

### Impact Explanation
A malicious private-payment counterparty or hub-relayed peer can:
1. Send a private payment chain (`private_payment_chains` message) whose per-element validation goes through the `ifQueued` path (normal for hub-mediated/light-wallet delivery).
2. Immediately resend the byte-identical `chains` payload before the original asynchronous validation (`eventBus` `key` event) resolves.
3. Because `handledChainsCache[cache_key]` was already set from the first attempt's queuing (not its actual validation outcome), the duplicate is accepted via `callbacks.ifOk()`/`all_private_payments_handled` immediately — even though the underlying chain might still be pending, or might ultimately be found invalid (`bValid === false`, which only triggers `cancelAllKeys()` and has no effect on the resend path since the resend never runs the check at all).

This allows an attacker-controlled peer to make the recipient/hub logic believe a private payment chain was accepted/handled without the wallet ever confirming the chain's cryptographic and consistency validity for that specific request, undermining trust guarantees of private (off-chain-communicated) payment processing.

### Likelihood Explanation
The `ifQueued` code path is the documented "most likely outcome for light clients" (per the inline comment), meaning premature caching is the common case rather than an edge case. Any peer capable of sending `private_payment_chains` messages (an unprivileged wallet/hub correspondent) can trivially replay an identical payload to trigger the race — no cryptographic material or privileged access is required, only network message timing.

### Recommendation
Only populate `handledChainsCache[cache_key]` after `checkIfAllValidated()` has confirmed **every** `assocValidatedByKey[key]` entry is `true` (i.e., inside the success branch of `checkIfAllValidated`, not unconditionally in the `async.eachSeries` completion callback). Additionally, ensure that a duplicate submission received while validation is still pending is queued/deduplicated (e.g., tracked in an in-flight map) rather than silently dropped or optimistically accepted, and that a failed validation (`bValid === false`) actively evicts any premature cache/in-flight entry for that `cache_key`.

### Proof of Concept
1. Peer A sends `private_payment_chains` with `chains = X` to a wallet/hub where the element(s) are handled via `network.handleOnlinePrivatePayment`'s `ifQueued` branch (typical hub/light-wallet flow).
2. `async.eachSeries` completes immediately (each `cb()` fired synchronously in `ifQueued`), so `handledChainsCache[hash(X)] = Date.now()` is set and `callbacks.ifOk()` returns to Peer A — while the real validation of `X` is still pending in the background via `eventBus.once(key, ...)`.
3. Peer A (or any observer who can compute/replay the same wire payload) immediately re-sends the identical `chains = X` payload.
4. The second call hits `if (handledChainsCache[cache_key])` and returns `callbacks.ifOk()` plus emits `all_private_payments_handled` without ever calling `network.handleOnlinePrivatePayment` again — bypassing validation entirely for the resend, even if the original in-flight validation for `X` later resolves to invalid.
