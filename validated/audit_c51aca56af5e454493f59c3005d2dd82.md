### Title
Webhook signature verified against a secret selected by an attacker-controlled organization field, while events are processed against a different repository name from the same payload - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the `webhook_secret` used to validate the HMAC signature by reading `repository_owner` from the **unverified** JSON body, then verifies the signature with that org's secret. The org used to select the secret (`repository.owner.login`) is never cross-checked against the repository actually acted upon by the handlers (`repository.full_name`, read separately in `Handler#repository_name`).

### Finding Description
`verify_signature` picks the GitHub App config to validate the signature against based on data taken directly from the still-unauthenticated payload: [1](#0-0) [2](#0-1) 

`repository_owner` is derived from `params.dig('repository', 'owner', 'login')`, i.e. attacker-supplied JSON, before the signature has been proven authentic. Once `verify_signature` passes (because it succeeds with the secret of *some* organization Shipit tracks), `create` dispatches the same raw payload to handlers: [3](#0-2) 

Handlers resolve the target repository/stacks independently, from `payload.dig('repository', 'full_name')`: [4](#0-3) 

Nothing enforces that the org used to authenticate the signature (`repository.owner.login`) equals the owner encoded in `repository.full_name` used for the actual write. `PushHandler`, for example, resolves stacks purely off `repository_name` (via `Repository.from_github_repo_name`) and immediately triggers `stack.sync_github(...)`: [5](#0-4) 

This breaks the binding: `organization authenticated (repository.owner.login → webhook_secret)` ≠ `repository written (repository.full_name → Stack)`. An attacker who possesses (or can obtain, e.g. by owning/administering) a webhook secret for *any* organization onboarded into this Shipit instance can forge a JSON body where `repository.owner.login` is set to their own org (so the HMAC check passes against their known secret) while `repository.full_name` is set to a completely different, victim organization/repository tracked by the same Shipit instance. The signature check never inspects `full_name`, only `owner.login`, so the forgery is accepted and dispatched to handlers that operate on the victim repository.

### Impact Explanation
This crosses a credential boundary matching the "organization authenticated vs. repository written" equality explicitly called out in scope: an attacker with only their own org's webhook secret can trigger writes (e.g., `GithubSyncJob`, commit/status ingestion, membership/team manipulation) against a stack belonging to an unrelated repository/organization onboarded to the same Shipit instance — a cross-repository write achieved without ever compromising the victim's actual webhook secret. Depending on the targeted handler this can desynchronize deploy state, inject spoofed commit statuses that gate deploy safety checks, or manipulate team/membership records tied to `Shipit.github_teams` authorization.

### Likelihood Explanation
Requires the attacker to control (or know) the `webhook_secret` for at least one organization already configured in this Shipit deployment (e.g., their own org with a stack in the same multi-tenant instance) — a realistic scenario for any Shipit installation serving multiple organizations/teams. No GitHub compromise of the victim org is required, only crafting a raw HTTP POST with a body whose `repository.owner.login` differs from `repository.full_name`'s owner segment.

### Recommendation
After a valid signature is confirmed, re-derive the organization from the same field used by the handlers (`repository.full_name`'s owner segment, or `organization.login` consistently) and require it to match `repository_owner` used for signature selection; reject the webhook if they diverge. Alternatively, verify the signature using the webhook secret associated with the `Repository` actually resolved from `full_name`, not a value read independently from an unauthenticated field.

### Proof of Concept
1. Shipit instance is configured with `github.someothergithuborg.webhook_secret` known to Org A (attacker-controlled), and also tracks Org B's repository `victim/victim-repo` as a `Stack`, per `config/secrets.development.shopify.yml` style multi-org config.
2. Attacker crafts a `push` payload:
```json
{
  "ref": "refs/heads/main",
  "after": "deadbeef",
  "repository": {
    "owner": { "login": "someothergithuborg" },
    "full_name": "victim/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=...` using Org A's known `webhook_secret` over this exact raw body.
4. `verify_signature` resolves `repository_owner` = `"someothergithuborg"` (Org A) and validates successfully with Org A's secret. [1](#0-0) 
5. `create` proceeds and `PushHandler` resolves stacks from `repository.full_name` = `"victim/victim-repo"`, triggering `sync_github` on the victim's stack — a cross-repository write the attacker was never authorized to perform. [4](#0-3) [5](#0-4)
