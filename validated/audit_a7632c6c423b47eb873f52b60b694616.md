### Title
Webhook signature verification key is selected from an unauthenticated payload field that differs from the field used to route the event to a stack, allowing cross-repository webhook forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` chooses which GitHub App/organization secret to verify the HMAC signature against using `repository_owner`, a value read directly from the untrusted JSON body (`repository.owner.login` or `organization.login`). Once "verified," the same raw payload is handed to `Shipit::Webhooks::Handlers::Handler`, which instead resolves the target stack using a *different* payload field, `repository.full_name`. These two fields are never cross-checked, so the identity used to authenticate the webhook is not bound to the identity of the repository/stack that is actually acted upon.

### Finding Description
`verify_signature` picks the signing secret for the request like this: [1](#0-0) [2](#0-1) 

`repository_owner` is fully attacker-controlled JSON, taken from the raw POST body before any signature has been checked. `Shipit.github(organization: repository_owner)` looks up the `GithubApp` configuration for that organization and calls `verify_webhook_signature`: [3](#0-2) 

Critically, if that organization's `webhook_secret` was left unconfigured (documented as *optional* in `docs/setup.md`), verification unconditionally returns `true` regardless of the actual `X-Hub-Signature` header — i.e., no proof of authenticity is required at all for that organization.

Once the request passes this check, `WebhooksController#create` dispatches the *entire, still-untrusted* payload to the registered handlers: [4](#0-3) 

Handlers, however, resolve which `Stack`/`Repository` to act on using a *different* field of the same payload — `repository.full_name` — not the `repository.owner.login`/`organization.login` value that was used for signature routing: [5](#0-4) 

For example, `PushHandler` uses this repository resolution to find the stacks to sync, then triggers a GitHub sync using an attacker-supplied `after` SHA: [6](#0-5) 

Multi-organization Shipit deployments are an explicitly supported and tested configuration (see `test/dummy/config/secrets_double_github_app.yml`), so an environment where one onboarded organization has no `webhook_secret` configured while another (the victim) does is realistic, not a hypothetical mis-deployment.

**The broken binding, stated as an equality that should hold but doesn't:**
`organization/app used to verify the webhook signature (repository.owner.login / organization.login)` **==** `organization/repository whose stack is mutated by the handler (repository.full_name)`

Before the attacker's request: both fields normally refer to the same GitHub repository for legitimate webhooks, because GitHub itself populates them consistently.
After the attacker's crafted request: `repository.owner.login` is set to an org with no configured `webhook_secret` (so the "signature" check always passes), while `repository.full_name` is set to an entirely different, victim organization's repository that is registered in the same Shipit instance and does have a webhook secret — yet the request is processed as if it had been legitimately signed by GitHub for that victim repository.

### Impact Explanation
This lets an unauthenticated caller who merely knows (or controls) an onboarded-but-secretless organization forge `push` (and other) webhook events for any other stack hosted by the same Shipit instance. For `push`, this drives `Stack#sync_github(expected_head_sha: params.after)` with an attacker-chosen SHA for the victim repository's branch. If continuous deployment is enabled on the target stack, this can cause Shipit to treat an attacker-chosen (but real, pre-existing) commit as the new head and automatically deploy it — an unauthorized deploy triggered without any signature actually covering the victim repository. This matches the in-scope "unauthorized deploy" impact criterion.

### Likelihood Explanation
Requires no credentials, no Shipit session, and no GitHub write access — only a raw unauthenticated HTTP POST to the public `/webhooks` endpoint. The only precondition is that the Shipit instance hosts at least one organization/app without a configured `webhook_secret` (an explicitly documented, optional, and tested configuration) alongside the victim organization. In shared/multi-tenant Shipit deployments this is a realistic and, per the test fixtures, anticipated configuration.

### Recommendation
Bind signature verification to the same identity used for stack resolution: verify the webhook using the secret associated with `repository.full_name`'s owner (not a separately-read `organization`/`repository.owner.login` field), and reject requests where these fields disagree. Additionally, do not allow `verify_webhook_signature` to silently pass when `webhook_secret` is blank for a repository-scoped hook if any other configured organization enforces one — or better, require a webhook secret to be mandatory rather than optional to close this gap entirely.

### Proof of Concept
1. Configure (or onboard as a low-privilege tenant) an organization `attacker-org` in the Shipit instance without a `webhook_secret`.
2. Send a POST to `/webhooks` with header `X-Github-Event: push` and a body such as:
```json
{
  "ref": "refs/heads/master",
  "after": "<any real commit SHA from victim/repo>",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
No valid `X-Hub-Signature` header is required because `attacker-org` has no `webhook_secret`, so `GithubApp#verify_webhook_signature` returns `true` unconditionally.
3. `WebhooksController#create` dispatches the payload to `PushHandler`, which resolves the stack via `repository.full_name` = `victim-org/victim-repo` and calls `stack.sync_github(expected_head_sha: "<attacker-chosen SHA>")`, causing Shipit to sync/deploy that commit for the victim stack despite the request never being authenticated for `victim-org`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
