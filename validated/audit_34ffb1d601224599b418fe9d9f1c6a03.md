Both of these mechanisms have the same fundamental characteristic as the Deriverse bug: the price a user pays is a deterministic function of state (pool reserves / `perp_clients_count` equivalent) that any unprivileged actor can shift by executing their own transaction beforehand, and then reverse afterward to recapture the shifted value (a swap-back in the AMM case, or in broker's case the price only adjusts between sales, not intra-sale by an attacker). This is the well-known "sandwich"/price-impact pattern inherent to AMM and auction-style pricing.

Critically, this class of issue is explicitly out of scope per the scan's exclusion rule 5: *"pure front-running/economic attacks"* are to be rejected, and the underlying report itself explicitly states "No front-running is required... An attacker can pre-purchase seats and later sell them to extract funds" — i.e., it is a pure economic/price-manipulation issue, not a missing access-control or accounting bug. `pallet-asset-conversion` already documents this exact risk and provides the standard mitigation via `amount_in_max`/`amount_out_min` slippage bounds on `swap_exact_tokens_for_tokens`/`swap_tokens_for_exact_tokens`, which the caller must set to protect themselves — the analogous protection to "quoting immediately before use" mentioned in `QuotePrice`'s docs.
