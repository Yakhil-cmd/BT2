Confirmed: `getTrigger` in `aa_composer.js:375-397` sets `trigger.address = objUnit.authors[0].address` — the author of the unit that sent the payment. For secondary triggers (an AA paying another AA), this author is the sending AA's own address, and there is no check preventing this (unlike primary triggers, which are explicitly checked by `checkAddressIsNotAA` in `aa_composer.js:252-259`, only reachable from `validateAATriggerObject`/dry-run paths for externally-authored units). Combined with the escrow-style oscript patterns (`var['balance_'||trigger.address||...]`, withdrawal gated on `trigger.address == recorded_address`) seen in `test/samples/a_bank_without_percent.oscript`, `order_book_exchange.oscript`, `sell_asset_for_bytes.oscript`, and `things_registry_and_marketplace.oscript`, this gives me enough to map the analog: an AA can deposit into another "bank/escrow" AA and be credited under its own AA address, but since AAs are purely reactive (they only execute when triggered — see `handlePrimaryAATrigger`/`handleTrigger` in `aa_composer.js:91-150`, `399-463` — there is no mechanism for an AA to spontaneously originate a new primary trigger), that depositing AA can never independently re-trigger the escrow AA to reclaim its credited balance unless some external actor happens to trigger it in exactly the right way to re-forward a withdrawal request.

### Title
Escrowed/credited balances attributed to an AA-address depositor become permanently unwithdrawable because AAs cannot self-originate a reclaim trigger - (File: aa_composer.js)

### Summary
Many Autonomous Agent (AA) patterns in Obyte implement an escrow/ledger design: incoming payments are credited to internal state under the key of the sender's address (`trigger.address`), and a later withdrawal is only permitted when a *new* trigger arrives from that exact same `trigger.address`. This mirrors the Solidity `pendingWithdrawals[user]` pattern from the cited report, where funds are correctly attributed to an address but can only be released by a unit/message coming from that precise address. In ocore, `trigger.address` for a secondary (AA-to-AA) trigger is derived from `objUnit.authors[0].address` [1](#0-0) , which allows another AA to be the recorded depositor. Because AAs are strictly reactive and never author units except in direct response to being triggered themselves [2](#0-1) [3](#0-2) , a depositor AA that has no built-in logic to relay/replay a "withdraw" request has no way to originate the specific follow-up trigger required to reclaim its own recorded balance — the funds become permanently stuck in the escrow AA, attributed to an address that structurally cannot act on its own initiative, with no admin/alternate-destination recovery path.

### Finding Description
The primary-trigger validation path explicitly forbids an AA address from being the trigger address of an externally-authored (primary) trigger: `checkAddressIsNotAA()` rejects triggers where `trigger.address` resolves to a row in `aa_addresses` [4](#0-3) . However, this restriction only applies to `validateAATriggerObject`, used for real (primary) unit-authored triggers, and it does **not** apply to secondary triggers generated when one AA sends a payment to another AA. In that case `getTrigger()` sets `trigger.address = objUnit.authors[0].address`, and for an AA-authored response unit, the sole author is the AA itself [1](#0-0) . This is by design and intentionally supported — see the `chain of AAs` test where `secondary_aa`'s `trigger.address` legitimately equals `primary_address`, an AA address [5](#0-4) .

Many common escrow/bank-style AA patterns record ownership/balance by `trigger.address` and gate withdrawal strictly on `trigger.address` matching the recorded owner, e.g.:
- `test/samples/a_bank_without_percent.oscript` credits `var['balance_'||trigger.address||...]` on deposit and only allows withdrawal `if: ... trigger.address == ...` implicitly via the `$key` built from `trigger.address` [6](#0-5) .
- `test/samples/order_book_exchange.oscript` uses the same `balance_<trigger.address>_<asset>` scheme with withdrawal payments sent back to `trigger.address` [7](#0-6) .
- `test/samples/sell_asset_for_bytes.oscript` gates withdrawal strictly on `trigger.address == $my_address` [8](#0-7) .
- `test/samples/things_registry_and_marketplace.oscript` records `owner_<id> = trigger.address` and requires `$owner == trigger.address` to withdraw/resell [9](#0-8) .

None of these patterns provide a `withdrawTo`-style alternate-destination mechanism. If the depositor recorded under `trigger.address` happens to be another AA (a legitimate, supported scenario per the secondary-trigger mechanism), the only way to reclaim the credited funds is for that same AA to autonomously author a brand-new response unit carrying `data.withdraw` (or equivalent) plus a matching payment back to the escrow AA. But AAs have no independent agency: `handleAATriggers`/`handlePrimaryAATrigger` show that an AA only ever executes and only ever emits a response unit when it is itself the recipient of an externally driven trigger [10](#0-9) . Unless the depositor AA's own definition happens to contain logic that forwards a withdrawal instruction whenever it is prompted by some unrelated external trigger — which none of the sampled/tested AA templates do — the AA can never spontaneously send the specific reclaim trigger the escrow AA requires. The credited balance is then permanently frozen inside the escrow AA's balance, correctly attributed but functionally unrecoverable, exactly mirroring the root cause described in the referenced report (funds correctly earmarked for `user` but stuck because only `user` itself can call `withdrawFor`, and `user` cannot act).

### Impact Explanation
This causes a genuine, permanent loss/freezing of AA-held funds (native bytes or issued assets) whenever a depositing address is itself an AA lacking a matching withdrawal-forwarding branch. Because AA-to-AA payments and chained triggers are an explicitly supported and encouraged composition pattern in ocore (factory AAs, remote-function AAs, forwarder AAs, and the tested "chain of AAs" pattern), any escrow/bank/marketplace AA deployed on mainnet that credits balances/ownership keyed by `trigger.address` is exposed to this freezing condition whenever another AA becomes its counterparty. There is no protocol-level or contract-level path to redirect the stuck funds to a capable address, matching the "funds temporarily/permanently unavailable to the rightful owner, correctable only via a state-changing redesign" impact class of the referenced Medium-severity finding.

### Likelihood Explanation
AA-to-AA payments are a first-class, well-tested feature (chains of AAs, factory AAs calling newly-defined AAs, forwarder AAs) rather than an edge case, so an AA acting as a depositor into another AA's escrow/bank logic is a realistic and even encouraged usage pattern. Template authors writing escrow/bank/exchange AAs (as demonstrated by multiple official sample scripts) naturally key ownership/balance on `trigger.address` without considering that the address could itself be an AA incapable of self-triggering, making this freeze condition likely to be reproduced in real deployed AAs that accept deposits from other AAs.

### Recommendation
- Document explicitly, and enforce where feasible in AA best-practice templates, that escrow/withdraw-style AA state should not be keyed exclusively on `trigger.address` without also supporting an owner-specified alternate withdrawal destination (an oscript analog of `withdrawTo`), e.g., allow `trigger.data.to_address` to be validated and used as the payment destination while still authenticating via `trigger.address == recorded_owner`.
- Consider extending `validateAATriggerObject`'s `checkAddressIsNotAA` semantics/documentation to also cover secondary triggers in the AA development guide, explicitly warning AA authors that `trigger.address` can be an AA address that can never itself re-trigger, and provide a recommended pattern (e.g., allowing any address to trigger the withdrawal as long as it supplies a valid signed message from the recorded owner, since AAs cannot sign, this still doesn't fully resolve the case, so alternate-destination withdrawal is the more general fix).
- For any first-party or bundled sample AAs (`a_bank_without_percent.oscript`, `order_book_exchange.oscript`, `sell_asset_for_bytes.oscript`, `things_registry_and_marketplace.oscript`) intended as templates for real deployments, add an explicit `to_address` withdrawal parameter validated against the recorded owner key rather than hard-coding `trigger.address` as both authenticator and destination.

### Proof of Concept
1. Deploy `EscrowAA` implementing the `a_bank_without_percent.oscript` pattern: on any deposit, credit `var['balance_'||trigger.address||'_base']`; on `trigger.data.withdraw`, pay `trigger.data.amount` back to `trigger.address` if the recorded balance covers it [6](#0-5) .
2. Deploy `DepositorAA`, a generic forwarder AA (similar to `forwarder_aa` in the "define new AA and activate it" test) that only forwards funds it receives and has no branch that later re-sends a `withdraw` request to whichever address it once paid [11](#0-10) .
3. Trigger `DepositorAA` such that it sends a payment (with `trigger.output[[asset=base]] > 10000`) to `EscrowAA`. Per `getTrigger()`, `EscrowAA` records `trigger.address = DepositorAA_address` and credits `var['balance_'||DepositorAA_address||'_base']` [1](#0-0) .
4. Attempt to reclaim the balance: because `DepositorAA` has no logic to spontaneously author a new response containing `data.withdraw = true` plus a matching payment to `EscrowAA`, and AAs never act except in reaction to their own trigger, no unit can ever be produced that satisfies `EscrowAA`'s withdrawal condition `trigger.address == DepositorAA_address`.
5. The balance credited to `DepositorAA_address` inside `EscrowAA` remains permanently locked, with no `to_address`-style mechanism in the sample template to redirect it to a wallet address that could actually claim it.

function getTrigger(objUnit, receiving_address) {
	var trigger = { address: objUnit.authors[0].address, unit: objUnit.unit, outputs: {} };
	if ("max_aa_responses" in objUnit)
		trigger.max_aa_responses = objUnit.max_aa_responses;
	objUnit.messages.forEach(function (message) {
		if (message.app === 'data' && !trigger.data) // use the first data message, ignore the subsequent ones
			trigger.data = message.payload;
		else if (message.app === 'payment' && message.payload) {
			var payload = message.payload;
			var asset = payload.asset || 'base';
			payload.outputs.forEach(function (output) {
				if (output.address === receiving_address) {
					if (!trigger.outputs[asset])
						trigger.outputs[asset] = 0;
					trigger.outputs[asset] += output.amount; // in case there are several outputs
				}
			});
		}
	});
	if (Object.keys(trigger.outputs).length === 0)
		throw Error("no outputs to " + receiving_address);
	return trigger;
}
