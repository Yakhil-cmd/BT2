### Title
Reused Bitcoin L1 lockup proof allows a staker to double-count locked sats across multiple bond registrations - (File: `stackslib/src/chainstate/stacks/boot/pox-5.clar`)

### Summary
`verify-l1-lockups` / `validate-l1-lockup` in `pox-5.clar` only dedupes Bitcoin lockup outpoints *within a single call*, via a `seen-outpoints` list that is initialized fresh (`(list)`) inside `verify-l1-lockups` every time it is invoked. There is no persistent, contract-wide map recording which Bitcoin outpoints have already been credited toward an sBTC bond/staker registration. This is structurally the same failure mode as the referenced Sherlock report: a value (there, `feePerClaim`; here, credited locked `sats`) is computed from a batch that is supposed to represent "newly verified, not-yet-counted" units, but nothing prevents the same underlying unit (a claim slot / a Bitcoin outpoint) from being counted again in a later, independent call. ### Finding Description
`verify-l1-lockups` folds `validate-l1-lockup` over the caller-supplied list of Bitcoin lockup outputs, starting the accumulator with `seen-outpoints: (list)`: [1](#0-0) 

`validate-l1-lockup` checks the outpoint against `seen-outpoints` (the in-call accumulator) with `asserts! (is-none (index-of? seen-outpoints outpoint)) ERR_DUPLICATE_LOCKUP_OUTPOINT`, then appends the outpoint to that same local list and adds `(get amount output)` to `sum`: [2](#0-1) 

Everything else it validates — unlock height, script hash (`construct-lockup-output-script`), amount consistency, block header, and merkle proof — proves that *a* Bitcoin transaction output with a given `(txid, output-index)` really exists and really is a lockup script for this staker/bond. None of these checks proves that the *same* outpoint hasn't already been used to credit sats in a *previous, separate* transaction/call to this contract, because `seen-outpoints` never persists outside the single `fold` invocation. If nothing calling `verify-l1-lockups` (e.g. bond registration/staking flows) separately tracks "used" Bitcoin outpoints in a durable map, a staker can submit the identical Bitcoin proof for the same locked BTC output in multiple bond-registration transactions and be credited the same `amount` of sats each time, without ever locking additional BTC.

### Impact Explanation
This maps to "sats credited by an L1 proof that were never locked on Bitcoin" / "double-counting a commitment" — a Critical category per the rules. If replay across calls is possible, a staker's real BTC collateral backing an sBTC bond can be inflated arbitrarily by resubmitting the same lockup proof, letting them claim reward slots / sBTC-denominated allowances (`maxSats`, `stx-value-ratio` computations, etc.) far beyond what is actually locked on Bitcoin — i.e., unbacked crediting of collateral that later pays out real sBTC rewards.

### Likelihood Explanation
Likelihood cannot be fully confirmed from the code paths I was able to inspect in the time available: I verified that `seen-outpoints` dedup is strictly call-local, but I was not able to trace every caller of `verify-l1-lockups` (e.g. `register-for-bond`/`validate-stake!` flows) far enough to rule out an *external* persistent-map check that separately rejects a previously-used outpoint at the call-site level. Given the explicit comment "`seen-outpoints` tracks every (txid, output-index) pair already credited **in this call**" it is likely intentional that cross-call dedup is handled elsewhere (e.g., allowlist single-registration-per-staker semantics) — but I could not verify this within the available exploration, so this should be treated as a finding requiring confirmation of whether any global/persistent outpoint-usage map exists in `pox-5.clar` outside of the fold accumulator.

### Recommendation
Add a persistent map, e.g. `used-l1-lockup-outpoints: {txid, output-index} -> bool`, and in `validate-l1-lockup` (or its caller) `asserts!` that the outpoint is not already present in that map before crediting `sum`, then `map-set` it as used. This closes the replay window regardless of how many independent transactions attempt to reuse the same Bitcoin lockup proof.

### Proof of Concept
1. Staker locks BTC output `O` (txid `T`, index `I`) satisfying the timelock script for bond `B`.
2. Staker calls the registration flow with `verify-l1-lockups` including `O` — `sum` includes `O.amount`, credited toward stake/bond eligibility.
3. Staker later calls the registration flow again (e.g., for a second bond period, or after unstaking and re-registering) supplying the *same* `O` again. Because `seen-outpoints` is re-initialized to `(list)` for this new call, `is-none (index-of? seen-outpoints outpoint)` is `true`, so `ERR_DUPLICATE_LOCKUP_OUTPOINT` does **not** fire, and `O.amount` is credited a second time — without any new BTC being locked.
