## Title
Cross-organization webhook forgery via organization/repository binding mismatch in signature verification - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects the GitHub App/secret used to validate an inbound webhook's HMAC signature based on an organization name pulled straight out of the *unverified* JSON body, while the downstream event handlers (`Shipit::Webhooks::Handlers::Handler#repository_name`, `PushHandler`, `StatusHandler`, `CheckSuiteHandler`, all `PullRequest::*Handler`) resolve the target `Stack`/`Repository` from a *different* field of that same unverified body (`repository.full_name`). Because the two fields are never checked against each other, a valid signature computed with one organization's webhook secret can be replayed with a payload whose `repository.full_name` points at a Stack belonging to a completely different organization.

### Finding Description
`verify_signature` derives the signing organization from the payload before the signature has been checked: [1](#0-0) [2](#0-1) 

`repository_owner` reads `params.dig('repository', 'owner', 'login')` (or `organization.login`) directly out of the raw, not-yet-authenticated request body, and uses it to pick which configured GitHub App (`Shipit.github(organization: repository_owner)`) — and therefore which `webhook_secret` — is used to validate `X-Hub-Signature`: [3](#0-2) 

Shipit explicitly supports multiple independently-configured GitHub organizations, each with its own app/secret (see `config/secrets.development.shopify.yml` listing `somegithuborg` and `someothergithuborg` with distinct `webhook_secret`s). Once the signature check passes for *whatever organization the attacker named in the payload*, `WebhooksController#create` dispatches the entire raw payload to all registered handlers with no re-validation: [4](#0-3) 

Every handler determines the target Stack/Repository from `repository.full_name`, a field completely independent of the `repository.owner.login` used for signature verification: [5](#0-4) [6](#0-5) [7](#0-6) [8](#0-7) 

This is exactly the class of bug the analog rule targets: "an organization that authenticated versus the repository that is written." The signature proves the request was signed with Org A's secret; nothing proves the enclosed `repository.full_name` belongs to Org A. An attacker who legitimately controls a GitHub App installation for Org A (any org onboarded onto this Shipit instance, however low-privilege) knows/derives valid HMAC signatures for Org A's secret, and can therefore forge a signed payload whose `repository.owner.login` = "Org A" but whose `repository.full_name` = "OrgB/target-repo", a Stack belonging to an unrelated organization Org B that the attacker has no access to.

### Impact Explanation
With a forged-but-"validly-signed" payload, an attacker can, without ever touching Org B's credentials:
- Trigger `GithubSyncJob`/`sync_github` for a stack owned by Org B via `PushHandler`, injecting an attacker-chosen `expected_head_sha`.
- Forge GitHub commit statuses for Org B's commits via `StatusHandler#process` → `Commit#create_status_from_github!`, which can influence `commit.deployable?`/CI-gating decisions used to permit deploys.
- Forge `check_suite` completion for Org B's commits via `CheckSuiteHandler`, triggering `schedule_refresh_check_runs!` against Org B's stack.
- Manipulate PR-driven review-stack provisioning/archiving (`labeled_handler.rb`, `closed_handler.rb`, etc.) for Org B's repositories, since these handlers also key off `params.repository.full_name` alone.

Because commit status/CI-state manipulation can feed directly into Shipit's deploy-eligibility checks, this crosses into "unauthorized deploy" / cross-repository-write territory called out as Critical/High impact in scope, achieved purely by exploiting a trust binding this engine itself does not enforce (no GitHub credential or repository access to Org B is required — only participation as any other onboarded, unprivileged organization).

### Likelihood Explanation
Any environment configured with more than one GitHub organization (a documented, supported configuration — see `config/secrets.development.shopify.yml`) is exposed. The only prerequisite is that the attacker be an authenticated member/admin of *any* one of the configured organizations (i.e., can trigger, replay, or otherwise obtain a validly-signed webhook for their own org) — a far lower bar than compromising the target organization. No GitHub token, API client secret, or Shipit session is needed; the request is a plain unauthenticated POST to `/webhooks`.

### Recommendation
After `verify_signature` succeeds, cross-check that the organization implied by `repository.full_name` (or `organization.login`) in the verified payload matches the organization (`repository_owner`) whose secret validated the signature, rejecting the request otherwise. More robustly, bind the webhook secret lookup and the eventual repository resolution to the same, single authoritative field, and re-derive/pass that verified organization context into `Shipit::Webhooks.for_event` handlers so they cannot resolve a Stack whose owning organization differs from the one that authenticated the request.

### Proof of Concept
1. Shipit is configured with two GitHub App organizations: `org-a` (attacker-controlled/installed, secret known/derivable to attacker) and `org-b` (victim org, unrelated to attacker).
2. Attacker crafts JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "deadbeef...attacker-chosen-sha",
  "repository": {
    "owner": { "login": "org-a" },
    "full_name": "org-b/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(org_a_webhook_secret, body)` — a signature they can legitimately produce because they control `org-a`'s App/secret.
4. POST to `/webhooks` with header `X-Github-Event: push`.
5. `verify_signature` calls `Shipit.github(organization: "org-a")`, validates the signature successfully against `org-a`'s secret.
6. `WebhooksController#create` dispatches to `PushHandler`, which resolves `stacks` via `Repository.from_github_repo_name("org-b/victim-repo")` — a stack the attacker has no relationship with — and calls `stack.sync_github(expected_head_sha: "deadbeef...")`, causing Shipit to sync/act on org-b's stack using attacker-supplied data, entirely outside any credential or authorization boundary tied to org-b.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
