### Title
Cross-stack status forgery bypasses `Commit#deployable?` and reaches `Stack#trigger_continuous_delivery` unimpeded because `Stack#deployable?` never checks commit/status provenance - (`app/models/shipit/webhooks/handlers/status_handler.rb`, `app/models/shipit/commit.rb`, `app/models/shipit/stack.rb`)

### Summary
`Commit#deployable?`'s `stack.ignore_ci?` branch is not what matters here — the forged status satisfies the ordinary `success? && !blocked?` branch directly, so `ignore_ci?` is irrelevant to the exploit. Once that branch is satisfied, the only remaining control before an actual `Deploy` is created is `Stack#deployable?`, which checks lock/active-task/provisioning/deployment-checks state only — it performs no check that the triggering `Status` actually originated from the stack's own repository, so any unlocked `continuous_deployment` stack is fully exposed.

### Finding Description
Binding claimed: `Stack#deployable?` (lock/active-task/provisioning gate) == sufficient authorization control for `Stack#trigger_continuous_delivery`. This is false for unlocked, non-busy, provisioned stacks with `continuous_deployment: true`.

Trace:
- `StatusHandler#process` resolves target commits with `Commit.where(sha: params.sha)` with no stack/repository scoping: [1](#0-0) . Any `Commit` row across any stack sharing that sha gets a new `Status` record via `commit.create_status_from_github!(params)`.
- `Commit#deployable?` is `!locked? && (stack.ignore_ci? || (success? && !blocked?))`: [2](#0-1) . A forged `state: 'success'` status satisfies `success?`; if no undeployed reachable commit is `blocking?`, `blocked?` is false — the `ignore_ci?` branch is never needed.
- `Status` has `after_commit :schedule_continuous_delivery, :broadcast_update, on: :create`, calling `commit.schedule_continuous_delivery`: [3](#0-2) .
- `Commit#schedule_continuous_delivery` gates on `deployable? && stack.continuous_deployment? && stack.deployable?` before enqueuing `ContinuousDeliveryJob`: [4](#0-3) .
- `ContinuousDeliveryJob#perform` re-checks `continuous_deployment?`, schedule window, and `occupied?`, then calls `stack.trigger_continuous_delivery`: [5](#0-4) .
- `Stack#trigger_continuous_delivery` picks `next_commit_to_deploy` and calls `trigger_deploy`, which builds and enqueues a real `Deploy`: [6](#0-5) .
- `Stack#deployable?` is `!locked? && !active_task? && !awaiting_provision? && deployment_checks_passed?` — no check on the origin of the commit's statuses: [7](#0-6) .

None of these gates (`occupied?`, `deployed_too_recently?`, `deployment_checks_passed?`, lock state) validate that the `Status` came from the stack's own configured repository. The authorization boundary that should exist — "only statuses reported for *this* repository's commit can make it deployable" — is absent; `deployable?` is a purely local, repository-agnostic predicate.

### Impact Explanation
For any stack that is unlocked, not mid-deploy, provisioned, passes deployment checks, and has `continuous_deployment: true` (a common, default-adjacent configuration), a cross-repository status forgery causes Shipit to enqueue and run an unauthorized `Deploy` for that stack — i.e., a payload/action originating outside the target repository's authentication boundary mutates the target stack's state and triggers real deploy commands. This is Critical: "a payload for one repository mutating another's stack ... or an unauthorized deploy." The blast radius covers every unlocked continuous-deployment stack sharing a commit sha with an attacker-controlled/forged status source. Locked stacks, or stacks with `continuous_deployment: false`, are not reached through this exact automatic path (manual deploy still requires a `deploys#create` request), so the impact is specifically bounded to unlocked, continuous-deployment stacks, as the question's premise states.

### Likelihood Explanation
Preconditions: (1) the target stack has `continuous_deployment: true`, is unlocked, idle, and passes deployment checks — a common production configuration; (2) a `Commit` row with matching sha exists in the target stack (git commit shas are content-addressed, so this is realistic across forks/shared history); (3) the attacker must be able to get a `Status` record created for that commit through some already-established forgery path (the webhook-signature/organization-scoping weakness referenced by the question, which this question intentionally treats as a given precondition rather than re-deriving). Given that precondition holds, no further Shipit secret or privileged role is required to complete the exploit chain traced above — it is fully automatic and repeatable per forged status event.

### Recommendation
Scope any commit/status lookup strictly to the repository asserted by the verified webhook payload (e.g., resolve `stack` by `repository_owner`/`repository.full_name` from the same payload and intersect with `Commit.where(sha:)`, rejecting matches on stacks belonging to a different repository). Additionally, `Stack#deployable?` (or `Commit#deployable?`) should not be treated as a security boundary for cross-tenant provenance; the provenance check belongs in `StatusHandler#process` itself, not downstream in the deploy-trigger gate.

### Proof of Concept
minitest plan (`test/models/commits_test.rb` or a new `stack_continuous_delivery_forgery_test.rb`):
1. Create two stacks, `stack_a` (attacker-controlled, `continuous_deployment: false`) and `stack_b` (target, `continuous_deployment: true`, unlocked, `awaiting_provision: false`, no active task).
2. Create a `Commit` with the same `sha` in both `stack_a.commits` and `stack_b.commits`.
3. Simulate the cross-stack write directly at the model layer (bypassing the webhook-signature precondition, which is out of scope for this question): call `Shipit::Webhooks::Handlers::StatusHandler.new.call('sha' => shared_sha, 'state' => 'success', 'context' => 'ci', ...)`.
4. Assert: `assert_enqueued_with(job: ContinuousDeliveryJob, args: [stack_b])`.
5. `ContinuousDeliveryJob.new.perform(stack_b)`; `assert_difference('Deploy.count', 1)`.
6. Matrix over `Stack#locked?`/`continuous_deployment?` combinations: assert `ContinuousDeliveryJob` enqueued only when `!locked? && continuous_deployment?`, and assert no `Deploy` created when `locked?` is true — proving `Stack#deployable?`'s lock check stops locked stacks but not unlocked continuous-deployment stacks, confirming the equality `Stack#deployable? == full authorization control` is false.
