### Title
Review-stack provisioning label approves a PR head SHA, but subsequent deploy/review automation executes whatever `shipit.yml` is on the same mutable branch ref - ([File: app/models/shipit/webhooks/handlers/pull_request/review_stack_adapter.rb])

### Summary
### Finding Description
The external report's bug class is a binding break between what is "approved"/checked and what is actually executed against uninitialized/mutable state. The equivalent binding in Shipit is: `label approved at PR-head-SHA-at-labeling-time == branch ref whose shipit.yml steps are executed later`. This equality does not hold.

When a maintainer applies the configured provisioning label to a pull request, `Shipit::Webhooks::Handlers::PullRequest::LabeledHandler#unarchive?` gates creation/unarchival of a `ReviewStack` on that single label event: [1](#0-0) 

`ReviewStackAdapter#create!`/`#unarchive!` persist the stack's `branch` as `params.pull_request.head.ref` — a **branch name**, not the commit SHA that existed when the label was applied: [2](#0-1) 

Once the `ReviewStack` exists with that `branch`, ordinary `push` webhooks targeting that same branch (which the PR author fully controls, since it is their own fork/branch and requires no repository write access to the base repo) queue a `GithubSyncJob` for the stack, as shown by the webhook controller's own push-handling behavior tied to `stack.branch`. The stack's deploy configuration is then reloaded from whatever is currently checked out on that branch via `DeploySpec::FileSystem#load_config`, which reads `shipit.yml`/`.shipit/shipit.yml` from the working tree at the latest fetched commit: [3](#0-2) 

and `CacheDeploySpecJob#perform` rebuilds the cached spec from `stack.commits.reachable.last` — the current tip of the branch, not the SHA that was present/approved when the label was added: [4](#0-3) 

The steps declared in that (attacker-controlled, post-approval) `shipit.yml` are turned into `Shipit::Command` instances and executed on the Shipit host with the host's own process environment, git credentials, and network access: [5](#0-4) [6](#0-5) 

So the maintainer's approval act (adding a label) is checked once, against the PR state at that instant, but the artifact that is actually fetched and run (`shipit.yml` steps on the branch head) is re-resolved continuously afterward and is fully within the control of the (potentially unprivileged, outside) PR submitter.

### Impact Explanation
This is a Critical-severity RCE-on-deploy-host path: an external contributor who can open a pull request (no repository write access required) can, after a single maintainer label click, push additional commits that rewrite `shipit.yml` `deploy`/`review.checks`/`machine.environment` steps to run arbitrary shell commands with the Shipit host's git credentials (`GITHUB_TOKEN`/GitHub App installation token used for the repository) and network egress. This crosses exactly the credential/execution boundary called out by the rules ("a ref approved versus a ref whose `shipit.yml` steps execute").

### Likelihood Explanation
Likelihood is Medium: it requires (a) review stacks to be enabled with label-gated provisioning (`provisioning_behavior_allow_with_label?`), a common/documented Shipit configuration for review apps on public/external-contribution repositories, and (b) a maintainer to label a PR once. No further review or re-approval is required for subsequent pushes to the same branch, because the trust decision is encoded as a one-time label event while the executed artifact is resolved by mutable ref, not the approved SHA. I could not fully verify, within available tool budget, whether `docs/review_stacks.md` documents an intended manual re-review step that mitigates this in practice; this should be confirmed by a maintainer/Devin session with full repository access.

### Recommendation
Pin approval to a commit SHA rather than a mutable ref: when the provisioning label is applied, record `params.pull_request.head.sha` and require re-validation (or an explicit re-label/re-approval) whenever the head SHA changes before re-provisioning or re-deploying the review stack's `shipit.yml`. Alternatively, disable automatic re-sync/re-deploy of review stacks on `push` events unless the pushed SHA matches (or a maintainer re-approves) the SHA that was present at label time.

### Proof of Concept
1. Attacker without write access to `org/repo` opens a pull request from a fork, with an innocuous `shipit.yml`.
2. A maintainer, trusting the current diff, adds the configured provisioning label (`repository.provisioning_label_name`), which invokes `LabeledHandler#unarchive!` → `ReviewStackAdapter#create!`, creating a `ReviewStack` with `branch: params.pull_request.head.ref` [7](#0-6) .
3. The attacker pushes a new commit to the same PR branch that rewrites `shipit.yml` `deploy.override`/`review.checks` steps to exfiltrate `ENV`/git credentials or run arbitrary shell commands.
4. The `push` webhook for that branch queues `GithubSyncJob` for the `ReviewStack` (matching `stack.branch`); the deploy spec is reloaded from the new commit via `DeploySpec::FileSystem#load_config` [3](#0-2) , and the malicious steps are executed on the Shipit host as a `Command` with the host's environment/credentials [5](#0-4) , without any second approval step.

    def start(&block)
      return if @started

      @control_block = block
      @out = @pid = nil

      begin
        @out, child_in, @pid = PTY.spawn(unbundled_env, *interpolated_arguments, chdir: @chdir)

      rescue Errno::ENOENT
        raise NotFound, "#{Shellwords.split(interpolated_arguments.first).first}: command not found"
      rescue Errno::EACCES

      end
      @started = true
      self
    end
