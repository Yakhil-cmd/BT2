## Finding

### Title
Multisig approval quorum can be satisfied by counting an owner's explicit **rejection** vote as an implicit **approval** in `validate_multisig_transaction` - (File: `aptos-move/framework/aptos-framework/sources/multisig_account.move`)

### Summary
The multisig execution path (`can_execute`, and the VM-prologue function `validate_multisig_transaction` that gates execution of a `MultisigTransaction`) treats an executing owner as an "implicit approver" whenever that owner has not explicitly voted **approve**. It never checks whether the owner has already voted **reject**. As a result, an owner who has explicitly rejected a pending multisig transaction can call the execute entry point themselves and have their rejection silently converted into an extra approval, corrupting the approval tally used at the admission boundary and letting a transaction execute without the required number of genuine approvals.

### Finding Description
`validate_multisig_transaction` is invoked by the Aptos VM as part of the transaction prologue (both in mempool validation and at execution time), making it the on-chain admission gate for multisig payload execution: [1](#0-0) 

Inside it (and identically in the `can_execute` view function), the approval count is computed from the persisted `votes` map and then an "implicit vote" is added purely based on whether the caller has voted **approve**: [2](#0-1) [3](#0-2) 

The helper used for the check, `has_voted_for_approval`, only reports `true` when the owner voted **and** the vote was `true` (approve). If the owner explicitly voted **reject** (`vote(...) == (true, false)`), `has_voted_for_approval` returns `false`, so the `!has_voted_for_approval(...)` branch fires and unconditionally increments `num_approvals` — treating an explicit "no" vote as an implicit "yes" for quorum purposes: [4](#0-3) 

This is inconsistent with the analogous rejection path `execute_rejected_transaction`, which correctly checks `has_voted_for_rejection` (i.e., "has this owner already voted reject") before adding an implicit vote: [5](#0-4) 

The correct condition for the execute path should be "owner has not voted at all" (`!has_voted_for_approval && !has_voted_for_rejection`), not merely "owner has not voted approve". Because the check only tests one polarity, a genuine reject vote is double counted: once as a rejection in `num_approvals_and_rejections`, and again as a phantom approval in the local tally used to gate execution.

### Impact Explanation
This breaks the core k-of-n admission invariant of the multisig account: the VM prologue (`validate_multisig_transaction`) can admit and execute a transaction payload with fewer genuine approvals than `num_signatures_required`. Concretely, with `num_signatures_required = 2` among 3 owners (A, B, C):
1. A creates the transaction (auto-approves): `votes = {A: true}`.
2. B explicitly rejects: `votes = {A: true, B: false}`. Real approvals = 1, rejections = 1.
3. B (the same owner who rejected) submits the transaction that triggers `validate_multisig_transaction(B, ...)`. `can_execute`/`validate_multisig_transaction` computes `num_approvals = 1` from the map, then adds 1 because `has_voted_for_approval(B) == false`, yielding `num_approvals = 2`, satisfying the 2-of-3 quorum and allowing execution — despite only one genuine approval and an explicit rejection on record.

This is an unauthorized state transition: a payload that should not have passed admission (insufficient real approvals) is executed, which is a high/critical-severity violation of the multisig approval-set binding enforced at the VM prologue admission boundary.

### Likelihood Explanation
The bug is triggered purely by unprivileged multisig owners using standard entry functions (`reject_transaction` then triggering execution of their own multisig account transaction) — no privileged access, race condition, or external dependency is required. It reproduces deterministically whenever a rejecting owner is also the one who submits/executes the pending transaction, which is a realistic scenario (e.g., a minority owner trying to force through a transaction they voted against, or simply re-submitting after voting).

### Recommendation
In `can_execute` (and mirrored logic inside `validate_multisig_transaction`), change the implicit-approval condition from `!has_voted_for_approval(...)` to `!has_voted_for_approval(...) && !has_voted_for_rejection(...)` (i.e., only imply approval if the owner has not voted at all), matching the symmetric, correct pattern already used in `execute_rejected_transaction` for the rejection path. Apply the same fix to `can_reject` for its implicit-rejection branch to avoid the mirror-image issue (an approving owner's vote being counted as an implicit rejection).

### Proof of Concept
1. Create a multisig account with owners `[A, B, C]` and `num_signatures_required = 2`, with `multisig_v2_enhancement_feature_enabled()` on.
2. `A` calls `create_transaction` → `votes = {A: true}` (auto-approval per `create_transaction`, see lines 1163-1183 of the file).
3. `B` calls `reject_transaction` → `votes = {A: true, B: false}`. Real state: 1 approval, 1 rejection.
4. `B` submits a transaction whose payload targets executing this pending multisig transaction (calling the entry function that invokes the VM's `validate_multisig_transaction(B, multisig_account, payload)` prologue).
5. Trace: `can_execute(B, ...)` → `num_approvals_and_rejections` returns `(1, 1)`; `has_voted_for_approval(multisig_account, seq, B)` returns `false` (B voted `false`); therefore `num_approvals` is incremented to `2`, meeting `num_signatures_required = 2`; `can_execute` returns `true`. `validate_multisig_transaction` repeats the same computation and passes the `assert!(num_approvals >= num_signatures_required)` check at lines 1348-1353.
6. The transaction executes even though `C` never voted and `B` explicitly rejected — quorum was never genuinely reached. [2](#0-1) [6](#0-5) [4](#0-3)

    /// Called by the VM as part of transaction prologue, which is invoked during mempool transaction validation and as
    /// the first step of transaction execution.
    ///
    /// Transaction payload is optional if it's already stored on chain for the transaction.
    fun validate_multisig_transaction(
        owner: &signer, multisig_account: address, payload: vector<u8>) {
        assert_multisig_account_exists(multisig_account);
        assert_is_owner(owner, multisig_account);
        let sequence_number = last_resolved_sequence_number(multisig_account) + 1;
        assert_transaction_exists(multisig_account, sequence_number);

        if (features::multisig_v2_enhancement_feature_enabled()) {
            assert!(
                can_execute(address_of(owner), multisig_account, sequence_number),
                error::invalid_argument(ENOT_ENOUGH_APPROVALS),
            );
        }
        else {
            assert!(
                can_be_executed(multisig_account, sequence_number),
                error::invalid_argument(ENOT_ENOUGH_APPROVALS),
            );
        };

        // Count approvals, including the executing owner's implicit vote.
        let (num_approvals, _) = num_approvals_and_rejections(multisig_account, sequence_number);
        if (!has_voted_for_approval(multisig_account, sequence_number, address_of(owner))) {
            num_approvals += 1;
        };
        assert!(num_approvals >= num_signatures_required(multisig_account), error::invalid_argument(ENOT_ENOUGH_APPROVALS));

        // Timelock check — separate from quorum so the error is unambiguous.
        assert!(
            can_execute_with_timelock(multisig_account, sequence_number, num_approvals),
            error::invalid_state(ETIMELOCK_NOT_EXPIRED),
        );

    inline fun has_voted_for_approval(multisig_account: address, sequence_number: u64, owner: address): bool {
        let (voted, vote) = vote(multisig_account, sequence_number, owner);
        voted && vote
    }

    inline fun has_voted_for_rejection(multisig_account: address, sequence_number: u64, owner: address): bool {
        let (voted, vote) = vote(multisig_account, sequence_number, owner);
        voted && !vote
    }
