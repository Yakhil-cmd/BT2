### Title
Emergency OP-list vote count applied on unstable/unfinalized votes and immediately upon unit write, bypassing the stability gate the normal vote-count path enforces - (File: `main_chain.js`)

### Summary
The bug report analog: a state-mutating function (`startRewardsCycle`) skipped a guard (`whenNotPaused`) that a sibling function in the same module already applied, letting anyone advance protocol state under a condition the protocol was supposed to prevent. In `ocore`, the analogous pattern is `applyEmergencyOpListChange()` / `countVotes(..., is_emergency=1, ...)`, which counts and applies OP-list (witness list) votes taken from **unstable** units, and is invoked synchronously right when a `system_vote_count` unit is written — unlike the regular vote-count path, which only tallies votes recorded from units that have already become stable (final).

### Finding Description
Normal system-variable vote counting only reads from the `system_votes`/`op_votes` tables, which are populated exclusively for units that have already reached stability via `saveSystemVote()` inside `markMcIndexStable()`: [1](#0-0) 
Votes are only counted for a subject once its underlying units are final (`vote count must be processed last, after all system_votes`): [2](#0-1) 

However, the *emergency* op_list path breaks this invariant. It pulls votes directly from `storage.assocUnstableMessages` — units that are **not yet stable** — filtering only on the unit's current (possibly still-changing) `sequence === 'good'` flag and a minimum "age" heuristic, not on finality: [3](#0-2) 

This emergency counting is triggered as a side effect of simply writing a unit that contains a `system_vote_count` message for `op_list`, executed immediately in `writer.js`, without waiting for that unit (or the votes it counts) to stabilize: [4](#0-3) 

`applyEmergencyOpListChange()` itself only gates on a *time* condition (how long the main chain has been stuck), not on the finality of the votes being counted, before overwriting `storage.systemVars.op_list` and the `op_votes`-based state used for consensus: [5](#0-4) [6](#0-5) 

Any single unit author can send a `system_vote` + `system_vote_count` (subject `op_list`) message pair — this requires no special privilege, only paying the `SYSTEM_VOTE_COUNT_FEE`: [7](#0-6) [8](#0-7) 

Because `sequence === 'good'` for an *unstable* unit is a provisional, best-parent-dependent classification that can differ between nodes (or change for the same node as the DAG grows) before the unit becomes stable/final, two honest full nodes that have received a different set of not-yet-final units at the moment the emergency trigger fires can compute **different winning OP lists** from `countVotes(..., is_emergency=1, ...)`. This is exactly the missing-guard pattern from the source report: the "sibling" function (regular, non-emergency vote counting) enforces stability before counting, while the emergency function was given a bypass (a time-based timeout) instead of the same finality guard, letting it run over data that isn't yet consensus-final.

### Impact Explanation
The OP (witness) list is foundational to every node's determination of unit validity and DAG stability (`storage.readWitnesses`, `determineIfStableInLaterUnits`, best-parent selection all depend on it). If two nodes momentarily disagree on the counted emergency OP list because they observed a different snapshot of unstable "good" votes when the timeout fired, they will diverge on which units are witnessed/stable and which chain is best, i.e. a genuine node disagreement on validity/stability of the type explicitly listed as an acceptable impact for this scan. This can partition the network's view of the DAG until reconciled, effectively an availability/consensus-safety issue for the whole network, not merely a resource-only or cosmetic bug.

### Likelihood Explanation
The emergency path is designed to be used exactly when the main chain has stalled (the crisis scenario), which is also precisely the scenario in which nodes are most likely to have differing unstable DAG views (since they are stuck disagreeing or racing to catch up). The trigger condition (`system_vote_count` for `op_list`) can be posted by any address at any time once the stall timeout is exceeded, and validation does not require the poster to be a current OP, so likelihood of an attacker (or even an honest but differently-synced node) intentionally or accidentally triggering divergent emergency counts during a stall is realistic, matching the report's Medium-severity “state changed while paused/inconsistent” pattern.

### Recommendation
Require the emergency `countVotes` path to only consider votes from units whose finality/sequence is guaranteed identical across nodes (e.g., restrict to votes already recorded in `system_votes`, or additionally require the *contributing* unstable units to be beyond some deterministic finality proxy such as being included by majority-witnessed later units, not just `sequence === 'good'`) before allowing them into `getUnstableVotes()`/`countVotes(is_emergency=1)`, mirroring the finality gate that the regular (non-emergency) vote-count path already enforces via `markMcIndexStable`.

### Proof of Concept
1. Main chain stalls past `EMERGENCY_OP_LIST_CHANGE_TIMEOUT` (per `applyEmergencyOpListChange`, `main_chain.js:1936-1946`).
2. Node A and Node B have each received a slightly different set of not-yet-stable units containing `system_vote` messages for `op_list` (normal during a DAG stall/fork situation), each locally marked `sequence='good'` by each node's own best-parent-dependent temporary classification.
3. Some author posts a unit with `system_vote_count` payload `op_list`; upon write (`writer.js:639-645`), each node independently calls `applyEmergencyOpListChange` → `countVotes(conn, mci, 'op_list', 1, timestamp)`.
4. Each node's `getUnstableVotes()` (`main_chain.js:1915-1933`) returns a different vote set based on its own currently-unstable "good" units, causing `storage.systemVars.op_list` (`main_chain.js:1866-1876`) to diverge between Node A and Node B, leading them to disagree about the OP list and hence about future stability/validity determinations.

function getUnstableVotes(emergency_count_command_timestamp) {
	let votes = [];
	for (let unit in storage.assocUnstableMessages) {
		for (let m of storage.assocUnstableMessages[unit]) {
			if (m.app === 'system_vote' && m.payload.subject === 'op_list') {
				const { timestamp, author_addresses, sequence, level } = storage.assocUnstableUnits[unit];
				if (sequence !== 'good')
					continue;
				if (emergency_count_command_timestamp - timestamp < constants.EMERGENCY_COUNT_MIN_VOTE_AGE) {
					console.log('unstable vote from', author_addresses, 'is too young');
					continue;
				}
				const arrOPs = m.payload.value;
				votes.push({ timestamp, level, author_addresses, arrOPs });
			}
		}
	}
	return votes;
}

async function applyEmergencyOpListChange(conn, emergency_count_command_timestamp, cb) {
	// last stable unit
	const [{ timestamp, main_chain_index }] = await conn.query("SELECT timestamp, main_chain_index FROM units WHERE is_stable=1 AND is_on_main_chain=1 ORDER BY main_chain_index DESC LIMIT 1");
	if (emergency_count_command_timestamp < timestamp + constants.EMERGENCY_OP_LIST_CHANGE_TIMEOUT) {
		console.log(`too early to apply emergency OP list change yet`);
		return cb();
	}
	console.log(`applying emergency vote count after being stuck at mci ${main_chain_index}`);
	await countVotes(conn, main_chain_index - 1, 'op_list', 1, emergency_count_command_timestamp);
	cb();
}
