## Analysis Summary

The zkSync report describes a two-phase deployment where a "constructing" marker is set on-chain before an optional finalization step (`callConstructor`), and skipping that step permanently bricks the target address while it keeps accepting funds silently.

Obyte (ocore) has a structurally analogous two-phase pattern for **AA-defined child AAs**: an AA can compose an `app: "definition"` message that dynamically generates a brand-new AA definition (e.g., via a formula), and that new address is marked as an AA and can immediately receive a payment from the same response, before its definition has gone through the full structural validation that is mandatory for AAs defined by ordinary (non-AA) authors.

### Root-cause chain
- For a `definition` message authored directly by a wallet, full validation is enforced via `aa_validation.validateAADefinition` before the address is ever treated as an AA. [1](#0-0) 
- But `aa_validation.js`'s own message-level check explicitly skips structural validation whenever the definition is dynamically generated by a formula (as it is for AA-authored, formula-built child definitions) — validation is simply deferred, i.e. "trust it will be fine at runtime." [2](#0-1) 
- At runtime, when an AA response actually contains a `definition` message, the composer only computes the new address as `chash160(payload.definition)` — it does **not** call `aa_validation.validateAADefinition` again on the resolved (post-formula) definition. [3](#0-2) 
- The address is then unconditionally registered as an AA via `storage.insertAADefinitions`, which only calls `aa_validation.determineGetterProps` (getter-complexity accounting) — not the full structural/semantic validation (`bounce_fees`, `messages` shape, formula well-formedness, etc.) that `validateAADefinition` performs. [4](#0-3) [5](#0-4) 
- Once an address row exists in `aa_addresses`, it is **permanently** an AA (analogous to the "constructing" bytecode hash never getting flipped to "constructed"): it can never again be treated as a normal signature-controlled wallet address, and `validateAuthor` special-cases any unit signed by a known `bAA` address, refusing normal spending. [6](#0-5) 
- The factory-style pattern (define a child AA, then immediately pay it in the same response) is a documented/expected usage. [7](#0-6) 
- If the freshly-defined AA's resolved definition is malformed (e.g., missing `messages`, broken bounce_fees, or a formula error) — something the runtime path never checked — its processing of the very payment that funded it can bounce. Critically, for **secondary** triggers (the mechanism by which the newly defined AA receives that same-response payment), `bounce()` takes the early-return branch and finishes without ever sending the funds back: [8](#0-7) 

This mirrors the zkSync bug precisely: the "deployment" step (posting a dynamically generated AA definition) is exempted from the validation that would otherwise be mandatory, the target address is irrevocably marked as active/constructed in storage, and any value sent to it is swallowed silently by an address that can never properly execute, spend, or refund it (no bounce, no signature-based recovery — AAs cannot be spent from via normal authentifiers).

### Title
Runtime-generated AA definitions posted via `definition` messages skip full structural validation, permanently bricking the new AA address and stranding funds sent to it in the same response - (File: aa_validation.js, storage.js, aa_composer.js)

### Summary
An AA can post a dynamically formula-generated `definition` message to create a new child AA and, in the same response (or a chained secondary trigger), send funds to that new address. The static validator explicitly skips structural checks when the definition is a formula, deferring correctness to runtime; but the runtime path (`aa_composer.js` message finalization → `writer.saveJoint` → `storage.insertAADefinitions`) never re-runs `aa_validation.validateAADefinition` on the resolved definition — it only computes getter complexity. The address is unconditionally inserted into `aa_addresses`, permanently switching it to AA-only semantics (no signature-based control ever again). If the resolved definition is malformed or otherwise unable to produce a valid response (missing `messages`, bad formulas, etc.), the trigger that funded it bounces, and for secondary triggers the bounce path deliberately skips any refund, permanently trapping the transferred coins in an address that can never again be spent from or repaired.

### Finding Description
`aa_validation.js`'s definition-message validator bypasses all structural checks (array shape, `messages` presence, `bounce_fees` sanity, formula well-formedness) whenever the definition is a dynamic formula string, which is exactly the case for AA-generated child definitions built with expressions like `` `{$child_aa}` `` [2](#0-1) . The corresponding runtime code that turns this message into a real address only computes the c-hash and never re-validates the resolved array [3](#0-2) . The address is then registered as a permanent AA via `storage.insertAADefinitions`, which performs only getter-complexity accounting, not full semantic validation [4](#0-3) , and this call happens unconditionally as part of committing the defining unit [5](#0-4) . In contrast, when a *non-AA* author posts a `definition` message, full `validateAADefinition` is mandatory before the unit is even accepted [1](#0-0) . Because AA status is permanent and unremovable (`validateAuthor` refuses to treat a `bAA` address as a normally-signed address) [6](#0-5) , any defect in the deferred/unvalidated definition cannot be corrected — the address is stuck exactly like the zkSync contract left in the "constructing" bytecode state.

### Impact Explanation
Sending funds to the newly-minted, insufficiently-validated AA in the same or a chained response is an explicitly supported and tested pattern [7](#0-6) . If the resolved definition is broken in a way not caught by `determineGetterProps` (e.g., a formula bug produces a definition with no `messages`, or one whose evaluation always errors), the funding trigger to this AA will bounce; for the common secondary-trigger delivery path, the bounce handler explicitly skips sending a refund [8](#0-7) . Because the address can never be reverted to a normal, key-controlled address, the funds already credited to its `aa_balances` row are permanently unspendable — an unauthorized, irreversible loss of funds triggered by ordinary AA logic (a bug or unexpected edge case in an AA author's own factory-pattern code, or malicious construction of the dynamic definition by the author to intentionally strand third-party value forwarded through it).

### Likelihood Explanation
The factory pattern (an AA composing and posting a new AA's definition dynamically, then funding it) is a first-class, documented ocore feature, not a corner case — it's directly exercised in the test suite [7](#0-6) . Any AA author (an unprivileged AA-trigger sender/AA author, reachable without special privileges) can construct a dynamic `definition` formula whose result, under certain input branches, is a definition missing required fields or otherwise non-functional, since the static validator never checks such generated content and the runtime insertion path does not either. This makes the trigger condition realistically reachable through normal AA composition, matching the "reliant on a mistake but not requiring a privileged actor" profile the original report was scored Medium for.

### Recommendation
Before (or immediately after) inserting a dynamically-generated AA definition into `aa_addresses` (in `storage.insertAADefinitions`), run it through the same full `aa_validation.validateAADefinition` check used for non-AA-authored `definition` messages, and reject/bounce the defining trigger if it fails, rather than deferring validation indefinitely for formula-based definitions. Additionally, consider allowing a refund path (rather than silent fund absorption) when a freshly-defined AA's very first secondary trigger bounces due to an invalid definition, so that value is not irrecoverably trapped.

### Proof of Concept
1. Author AA `factory_aa` whose `init` formula dynamically builds `$child_aa` such that, for a class of trigger inputs, the produced object lacks a valid `messages` array (or contains a broken formula), while still being a well-formed 2-element `['autonomous agent', {...}]` array so that `getFormula(payload.definition)` short-circuits validation at `aa_validation.js:208-220`.
2. `factory_aa` posts `{ app: 'definition', payload: { definition: `{$child_aa}` } }` and, in the same response, a `payment` message sending funds to `chash160($child_aa)` — exactly as in the existing test pattern [9](#0-8) .
3. `writer.saveJoint` commits the unit and unconditionally calls `storage.insertAADefinitions(..., bForAAsOnly=true, ...)`, registering the new address as a permanent AA without re-validating its structure [5](#0-4) [4](#0-3) .
4. The secondary trigger that delivers the payment to the new AA fails inside `handleTrigger` (e.g., `bounce('no messages')` at the message-filtering stage), and since it's a secondary trigger, `bounce()` returns via `finish(null)` without refunding [8](#0-7) .
5. The transferred coins remain forever credited to the broken AA's `aa_balances` row; since the address is permanently `bAA` in `aa_addresses`, it can never be spent from via a normal signed unit [6](#0-5) , permanently freezing the funds.
