### Title
Stack-scoped API token bypasses stack authorization in `CCMenuController` - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`ApiClient` tokens can be scoped to a single stack via the `stack_id` column, and every other API controller enforces that scope through `BaseController#stacks`/`#stack`. `CCMenuController` overrides `#stack` to bypass that scoping entirely, letting a stack-scoped token read the status of any stack.

### Finding Description
`ApiClient` records can be restricted to one stack: `stack_id?` gates the query in `BaseController#stacks`, and `#stack` resolves the requested resource only from that scoped relation [1](#0-0) . This is the intended binding: "the stack(s) an `ApiClient` token authorizes" == "the stack the controller action touches".

`CCMenuController` requires only the generic `read:stack` permission — which says nothing about *which* stack — via `require_permission :read, :stack` [2](#0-1) , and then resolves the target stack directly from `Stack.from_param!(params[:stack_id])` instead of going through the scoped `stacks` relation used everywhere else: [3](#0-2) 

`Stack.from_param!` performs an unscoped lookup across the entire `stacks` table by owner/name/environment [4](#0-3) , so any stack in the Shipit installation can be resolved regardless of the calling token's `stack_id`.

Contrast this with every other authenticated API controller (`StacksController`, `LocksController`, `TasksController`, etc.), which resolve `stack` via the base implementation `stacks.from_param!(params[:stack_id])`, correctly honoring the `current_api_client.stack_id?` restriction [5](#0-4) .

The fixture `here_come_the_walrus` demonstrates the intended restriction pattern: a token scoped to the `shipit` stack with only `read:stack` permission [6](#0-5) . Under `StacksController`, this token is confirmed to only see its own stack (`test "an api client scoped to a stack will only see that one stack"`) [7](#0-6) . No equivalent restriction exists — or is tested — for `CCMenuController`.

This mirrors the reported bug class: two code paths that are supposed to enforce the same invariant ("token stack scope == accessed stack") use inconsistent enforcement logic, and the weaker path (`CCMenuController#stack`) allows access the stronger path (`BaseController#stack`) would deny.

### Impact Explanation
This grants **unauthenticated read of stack state** beyond the token's authorized scope — an operator who is issued a narrowly-scoped `ApiClient` token (intended to only see one stack's CI status for use in tools like CCMenu clients) can instead retrieve the latest deploy/rollback status, running/ended state, and timestamps of every stack in the Shipit instance, including stacks belonging to repositories/teams the token holder should have no visibility into. This matches the High-severity criterion: "escalation into `Shipit.github_teams` authorization, unauthenticated read of stack state, task streams or deploy output."

### Likelihood Explanation
High likelihood for any deployment that issues scoped `ApiClient` tokens (the documented purpose of the `stack_id` column and the `read:stack`-only CCMenu use case). The attack requires only a valid, stack-scoped token (already a documented, low-privilege credential type) and changing the `stack_id` path segment in the CCMenu URL — no additional exploitation is needed.

### Recommendation
Make `CCMenuController#stack` reuse the base, properly-scoped lookup instead of `Stack.from_param!` directly, e.g.:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
so it inherits the same `current_api_client.stack_id?` restriction enforced everywhere else, and add a regression test asserting a stack-scoped token cannot fetch CCMenu data for a different stack.

### Proof of Concept
1. Create an `ApiClient` scoped to `stack_id: <shipit stack id>` with `permissions: ['read:stack']` (as in fixture `here_come_the_walrus`).
2. Authenticate as this client and call:
   `GET /ccmenu/*stack_id`, e.g. `/ccmenu/rails/rails/staging?token=<token>` for a stack the client is not scoped to.
3. `authenticate_api_client` succeeds (valid token) [8](#0-7) ; `require_permission :read, :stack` passes because the client has `read:stack` generically [2](#0-1) ; `stack` resolves `rails/rails/staging` via the unscoped `Stack.from_param!` [9](#0-8) .
4. The response renders that unrelated stack's latest deploy/rollback status, even though the token is only supposed to authorize the `shipit` stack.
