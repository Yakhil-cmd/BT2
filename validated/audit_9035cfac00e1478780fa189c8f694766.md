## Title
Earned but undistributed epoch rewards are permanently burned (not refunded) when a stake account is withdrawn/closed between reward calculation and its scheduled distribution partition - (File: runtime/src/bank/partitioned_epoch_rewards/distribution.rs)

### Summary
Agave's partitioned epoch-rewards mechanism computes each stake account's reward for an epoch in a single "calculation" block, but actually credits (mints) that reward to the account over many subsequent blocks ("distribution" phase, spread across up to 10% of an epoch's slots). This split is functionally analogous to the Chakra "initiate on one chain, settle later on another" pattern described in the external report: value is calculated/committed at time T0 but only materialized at a later time T1, and the intervening window is attacker/user-influenceable. If the targeted stake account no longer exists in the `StakesCache` at its distribution time (e.g., because the staker withdrew/closed it), the reward is silently burned with no refund path to the staker, mirroring the "no refund mechanism" bug class.

### Finding Description
`store_stake_accounts_in_partition` looks up each `partitioned_stake_reward.stake_pubkey` in the *current* `stakes_cache_accounts` (a live snapshot taken at the current distribution block, not the calculation block) via `build_updated_stake_reward`: [1](#0-0) 

If the account is missing, `DistributionError::AccountNotFound` is returned: [2](#0-1) 

Any `DistributionError` (including `AccountNotFound`) causes the caller to burn the already-committed reward amount instead of crediting it to anyone: [3](#0-2) 

The burned lamports are then permanently removed from total capitalization and from the `EpochRewards` sysvar's outstanding balance, with no code path that credits them back to the staker, the vote account, or any other beneficiary: [4](#0-3) 

The code comment explicitly acknowledges the developers' assumption that this path should be unreachable "because... further state mutation [is] prevent[ed] by stake-program restrictions," implying rewards should never actually be burned in this way: [5](#0-4) 

However, no such restriction exists in the codebase — a search for any "epoch rewards active" guard in the stake program's instruction handlers (e.g., `Withdraw`) returns no matches, and existing CLI/integration tests confirm ordinary stake withdrawal is a normal, unrestricted operation once a stake account is deactivated: [6](#0-5) 

Reward calculation happens once at the first block of the new epoch and is based on the `StakesCache` at that moment, while distribution to any individual stake account can occur many blocks later — the specific partition/block for a given account is determined by hashing, so a staker generally cannot predict exactly which future block their own reward will be credited in: [7](#0-6) 

The test suite itself demonstrates that this "burn on missing account" path is a real, exercised branch (not purely theoretical): `test_build_updated_stake_reward` explicitly feeds a `nonexistent_account` and asserts `DistributionError::AccountNotFound` is returned, and `test_epoch_credit_rewards_and_history_update` pushes an extra `PartitionedStakeReward` "to simulate non-existent account": [8](#0-7) [9](#0-8) 

### Impact Explanation
This results in a concrete loss of lamports that were rightfully owed to a staker (an unprivileged user) for stake they had at risk during the rewarded epoch. The lamports are burned from total supply rather than refunded to the entitled party, which is a direct analog to the reported "no refund mechanism" issue — value is computed and reserved at one point in the async pipeline, and if the destination account state changes before the second phase completes, the value disappears with no recovery path.

### Likelihood Explanation
Any staker who deactivates a stake account in one epoch and then withdraws/closes it (a routine, permission-normal operation via the stake program's `Withdraw` instruction) risks doing so during the window between the epoch-boundary reward calculation block and their own hashed distribution partition block, which can be up to ~10% of an epoch's slots later. Because there is no on-chain signal informing the user which specific future block/partition their reward will land in, this can happen inadvertently during normal wallet/exchange withdrawal flows, not just via deliberate attack, making the loss plausible in ordinary operation.

### Recommendation
Add a refund/fallback mechanism for rewards that cannot be credited during the distribution phase — e.g., re-route the burned stake reward to the corresponding vote account, to a claimable holding account keyed by the original stake pubkey/withdraw authority, or explicitly disallow full withdrawal/closure of a stake account whose pending reward has not yet been distributed (mirroring the code's own stated assumption that such closures shouldn't be possible). At minimum, this discrepancy between the assumed invariant in the code comment and the actual lack of enforcement should be resolved.

### Proof of Concept
1. At the epoch boundary, a staker's stake account is included in `all_stake_rewards` with a nonzero `stake_reward` computed in `distribute_partitioned_epoch_rewards` calculation phase.
2. Before the block corresponding to that staker's hashed partition index is produced (which may be many blocks later, per `hash_rewards_into_partitions`), the staker submits a normal `Withdraw` instruction removing the full balance of the stake account, causing it to be evicted from `StakesCache` (zero-lamport accounts are removed, as shown in `stakes.rs` `check_and_store`).
3. When the staker's partition block arrives, `build_updated_stake_reward` fails to find the account in `stakes_cache_accounts` and returns `DistributionError::AccountNotFound`.
4. `store_stake_accounts_in_partition` burns `stake_reward_amount` for that entry — capitalization is reduced by this amount and the `EpochRewards` sysvar marks it as "distributed" (i.e., debited) even though no one received it, per `distribute_epoch_rewards_in_partition`'s capitalization bookkeeping.
5. The staker permanently loses the reward lamports they had earned for the epoch, with no code path to reclaim them. [10](#0-9) [11](#0-10)

    pub(in crate::bank) fn distribute_partitioned_epoch_rewards(&mut self) {
        let EpochRewardStatus::Active(status) = &self.epoch_reward_status else {
            return;
        };

        let distribution_starting_block_height = match &status {
            EpochRewardPhase::Calculation(status) => status.distribution_starting_block_height,
            EpochRewardPhase::Distribution(status) => status.distribution_starting_block_height,
        };

        let height = self.block_height();
        if height < distribution_starting_block_height {
            return;
        }

        if let EpochRewardPhase::Calculation(status) = &status {
            // epoch rewards have not been partitioned yet, so partition them now
            // This should happen only once immediately on the first rewards distribution block, after reward calculation block.
            let epoch_rewards_sysvar = self.get_epoch_rewards_sysvar();
            let (partition_indices, partition_us) = measure_us!({
                epoch_rewards_hasher::hash_rewards_into_partitions(
                    &status.all_stake_rewards,
                    &epoch_rewards_sysvar.parent_blockhash,
                    epoch_rewards_sysvar.num_partitions as usize,
                )
            });

            // update epoch reward status to distribution phase
            self.set_epoch_reward_status_distribution(
                distribution_starting_block_height,
                Arc::clone(&status.all_stake_rewards),
                partition_indices,
            );

            datapoint_info!(
                "epoch-rewards-status-update",
                ("slot", self.slot(), i64),
                ("block_height", height, i64),
                ("partition_us", partition_us, i64),
                (
                    "distribution_starting_block_height",
                    distribution_starting_block_height,
                    i64
                ),
            );
        }

        let EpochRewardStatus::Active(EpochRewardPhase::Distribution(partition_rewards)) =
            &self.epoch_reward_status
        else {
            // We should never get here.
            unreachable!(
                "epoch rewards status is not in distribution phase, but we are trying to \
                 distribute rewards"
            );
        };

        let distribution_end_exclusive =
            distribution_starting_block_height + partition_rewards.partition_indices.len() as u64;

        assert!(
            self.epoch_schedule.get_slots_in_epoch(self.epoch)
                > partition_rewards.partition_indices.len() as u64
        );

        if height >= distribution_starting_block_height && height < distribution_end_exclusive {
            let partition_index = height - distribution_starting_block_height;

            self.distribute_epoch_rewards_in_partition(partition_rewards, partition_index);
        }
