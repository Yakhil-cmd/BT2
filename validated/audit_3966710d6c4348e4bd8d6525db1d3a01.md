### Title
Cross-organization forged `status` webhooks can mark any tracked commit as `success`, bypassing CI gating for deploys - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to validate an inbound webhook's HMAC signature against based on an attacker-controlled JSON field (`repository.owner.login` or `organization.login`), but the handler that actually mutates state (`Handlers::StatusHandler`) never re-checks that field — it looks up the target `Commit` purely `by sha`, across the entire installation. This breaks the binding "organization that authenticated" == "repository that is written."

### Finding Description
`verify_signature` picks the signing/verification secret from the payload itself: [1](#0-0) [2](#0-1) 

`repository_owner` is read straight from `params.dig('repository', 'owner', 'login')` — fully attacker-controlled JSON, not derived from any authenticated context. Shipit supports multiple independent GitHub App / organization configurations sharing one webhook endpoint (documented multi-tenant setup): [3](#0-2) 

Each organization has its own `webhook_secret`: [4](#0-3) [5](#0-4) 

Once signature verification passes (using OrgA's secret, matched against `repository.owner.login = "OrgA"`), `WebhooksController#create` dispatches the parsed `params` to the registered handlers regardless of which organization the signature actually belonged to: [6](#0-5) 

`Handlers::StatusHandler`, unlike other handlers (`PushHandler`, `PullRequest::*Handler`, which resolve a `Repository`/`Stack` via `payload.dig('repository','full_name')` before acting — see the base `Handler#repository_name`/`#stacks`): [7](#0-6) 

never consults `repository_name`/`stacks` at all. It resolves the target purely by commit SHA across the whole database: [8](#0-7) 

So the value used to select the verification secret (`repository.owner.login`) is never cross-checked against the value that determines which `Stack`/`Commit` is written to (in this handler, no repository scoping exists at all). An attacker who controls one organization's webhook secret (a legitimate, but low-privileged tenant on a shared Shipit instance, or anyone who has ever seen/leaked one org's `webhook_secret`) can forge a raw HTTP POST with:
- `X-Github-Event: status`
- `X-Hub-Signature` computed with **their own org's** `webhook_secret`
- `repository.owner.login` = their own org (to pass `verify_signature`)
- `sha` = the SHA of a commit that actually belongs to a **different**, victim stack/organization tracked by the same Shipit instance

`verify_webhook_signature` will succeed (it validates the signature against the correct secret for the org named in the payload), and `StatusHandler#process` will then create/replicate a `success` status on the victim commit: [9](#0-8) 

### Impact Explanation
Commit status directly drives deploy readiness (`deployable?`) and gating logic, and successful/pending statuses can trigger merges and continuous delivery: [10](#0-9) [11](#0-10) 

By forging a fake "success" CI status for a commit that belongs to a repository/stack the attacker has no authorization over, they can flip `deployable?` to true, unblock `blocked?` gating, and trigger `schedule_continuous_delivery`/`schedule_merges` for a stack under a completely different GitHub organization/tenant — i.e., an unauthorized deploy/merge condition is satisfied without any legitimate CI signal, breaking the authenticated-organization ↔ written-repository binding. This qualifies as "escalation ... unauthenticated read of stack state" adjacent and, more directly, "an unauthorized deploy" impact under the stated criteria.

### Likelihood Explanation
Requires the attacker to know a valid `webhook_secret` for *some* configured GitHub organization on the shared Shipit instance — realistic for any tenant/organization admin who legitimately configured their own GitHub App's webhook secret in a multi-org deployment (as explicitly documented as a supported configuration in `docs/setup.md`). No repository write access, session, or `ApiClient` token is needed; only knowledge of one's own org's webhook secret and the target commit's SHA (SHAs are typically public/guessable via GitHub's public API for public repos). This is a single unprivileged tenant abusing its own valid credential to affect a foreign tenant's state — squarely inside the requested analog class ("an organization that authenticated versus the repository that is written").

### Recommendation
In `StatusHandler` (and any handler that doesn't already do so), scope the lookup to the repository named in the payload, and additionally verify that `repository.full_name`'s owner matches the `repository_owner`/organization used to select the verification secret in `WebhooksController#verify_signature`. Concretely:
- Change `StatusHandler#process` to scope `Commit.where(sha: params.sha)` to `stacks` derived from `payload.dig('repository','full_name')` (as other handlers already do via `Handler#stacks`), and reject/no-op when the resolved repository's owning organization does not match the organization whose secret was used to verify the signature.
- In `WebhooksController`, after verification, assert that `repository_owner` (used to pick the secret) equals the owner implied by `repository.full_name` before dispatching to handlers, so a forged payload can't mix-and-match an authenticated organization with an unrelated target repository.

### Proof of Concept
1. Configure Shipit with two organizations, `OrgA` and `OrgB`, each with distinct `webhook_secret`s (per `docs/setup.md`'s multi-org example), each tracking stacks/commits.
2. As a party who legitimately knows `OrgA`'s `webhook_secret` (e.g., the person who configured `OrgA`'s GitHub App), compute:
   ```
   body = {
     "sha": "<victim_commit_sha_in_OrgB_stack>",
     "state": "success",
     "context": "ci/forged",
     "repository": { "owner": { "login": "OrgA" } }
   }.to_json
   signature = "sha1=" + HMAC_SHA1(OrgA_webhook_secret, body)
   ```
3. POST to the shared `/webhooks` (or engine-mounted equivalent) endpoint with headers `X-Github-Event: status` and `X-Hub-Signature: <signature>`.
4. `verify_signature` resolves `repository_owner == "OrgA"`, fetches `Shipit.github(organization: "OrgA")`, and validates successfully against `OrgA`'s real secret.
5. `StatusHandler#process` finds `Commit.where(sha: "<victim_commit_sha_in_OrgB_stack>")` — with no repository-owner check — and calls `commit.create_status_from_github!(params)`, injecting a forged `success` status onto a commit belonging to `OrgB`, potentially flipping `deployable?` to `true` for that unrelated stack.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

# frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class StatusHandler < Handler
        params do
          requires :sha, String
          requires :state, String
          accepts :description, String
          accepts :target_url, String
          accepts :context, String
          accepts :created_at, String

          accepts :branches, Array do
            requires :name, String
          end
        end

        def process
          Commit.where(sha: params.sha).each do |commit|
            commit.create_status_from_github!(params)
          end
        end
      end
    end
