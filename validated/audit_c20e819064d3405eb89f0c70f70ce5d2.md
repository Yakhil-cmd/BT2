### Title
Unsafe `uint64`→`int64` Narrowing in `consolidatedNode.Split` Corrupts CN/CL Reward Distribution — (File: kaiax/staking/staking_info.go)

### Summary
`consolidatedNode.Split` converts `uint64` staking amounts to `int64` via `big.NewInt(int64(...))`. Any staking amount exceeding `math.MaxInt64` (~9.22 × 10⁹ KAIA) wraps to a negative value, producing a corrupted `totalAmount` divisor. This causes the proportional KAIA split between the CN staking contract and the CL pool to be computed incorrectly — the CN validator can receive more than its entitled share while the CL pool receives a negative (or zero) allocation, or the node panics on division-by-zero.

### Finding Description

In `kaiax/staking/staking_info.go`, `Split` is the sole function that divides a block reward between a validator's CNStaking contract and its Consensus Liquidity (CL) pool (KIP-226, Prague hardfork):

```go
func (c consolidatedNode) Split(amount *big.Int) (*big.Int, *big.Int) {
    if c.CLStakingInfo == nil {
        return amount, big.NewInt(0)
    }

    var (
        cnAmountBig = big.NewInt(int64(c.StakingAmount))              // ← unsafe narrowing
        clAmountBig = big.NewInt(int64(c.CLStakingInfo.CLStakingAmount)) // ← unsafe narrowing
        totalAmount = new(big.Int).Add(cnAmountBig, clAmountBig)
    )

    clAmount := new(big.Int).Mul(clAmountBig, amount)
    clAmount = clAmount.Div(clAmount, totalAmount)          // ← wrong divisor

    cnAmount := big.NewInt(0).Sub(amount, clAmount)
    return cnAmount, clAmount
}
```

Both `c.StakingAmount` and `c.CLStakingInfo.CLStakingAmount` are `uint64` (KAIA units). The Go spec defines `uint64`→`int64` conversion as a bit-reinterpretation: any value above `math.MaxInt64` (9,223,372,036 KAIA) becomes a negative `int64`. `big.NewInt` faithfully preserves that sign, so `cnAmountBig` or `clAmountBig` can be a large negative `big.Int`.

Consequences depending on the exact values:

| Scenario | `totalAmount` | `clAmount` | `cnAmount` |
|---|---|---|---|
| `cnStake > MaxInt64`, `clStake` small positive | Large negative | Negative | `amount + |clAmount|` > `amount` |
| Both overflow | Could be zero | **Panic** (div-by-zero) | — |
| `cnStake` normal, `clStake > MaxInt64` | Negative | Negative | `amount + |clAmount|` > `amount` | [1](#0-0) 

The staking amounts are stored in KAIA units (divided by `params.KAIA = 10^18` from the raw contract balance): [2](#0-1) 

### Impact Explanation

`Split` is called in four reward-distribution functions that execute every block during `FinalizeState`:

1. `assignStakingRewards` — distributes staking rewards (Kore/Prague rules)
2. `assignStakingRewardsFlex` — distributes staking rewards (Osaka/Flex rules)
3. `specWithProposerAndFunds` — distributes proposer reward (Prague rules)
4. `specWithProposerAndFundsFlex` — distributes proposer reward (Osaka/Flex rules) [3](#0-2) [4](#0-3) 

When `cnAmount > amount`, the CN validator's reward address receives more KAIA than the total reward allocated to that validator — an unauthorized minting of KAIA to the CN reward address. The CL pool simultaneously receives a negative `big.Int` reward, which when applied via `AddBalance` reduces the pool's balance, constituting an unauthorized burn from the CL pool.

If `totalAmount == 0` (both staking amounts overflow to the same magnitude with opposite signs), the `Div` call panics, crashing the node during block finalization — a consensus-halting event on the proposer.

### Likelihood Explanation

`StakingAmount` and `CLStakingAmount` are `uint64` values in KAIA. The overflow threshold is `math.MaxInt64 ≈ 9.22 × 10⁹ KAIA`. The current total KAIA supply is approximately 5.9 billion KAIA, so no single validator can currently stake enough to trigger the overflow. However:

- The minting rate is ~9.5 KAIA/block; supply grows continuously.
- The field type (`uint64`) permits values up to ~18.4 billion KAIA with no enforcement cap in `Split`.
- No guard exists between the `uint64` storage and the `int64` cast.
- The bug is latent and will become reachable as supply grows past the threshold, or if a governance parameter change increases minting significantly.

### Recommendation

Replace the narrowing casts with `new(big.Int).SetUint64(...)`, which is lossless for the full `uint64` range:

```go
var (
    cnAmountBig = new(big.Int).SetUint64(c.StakingAmount)
    clAmountBig = new(big.Int).SetUint64(c.CLStakingInfo.CLStakingAmount)
    totalAmount = new(big.Int).Add(cnAmountBig, clAmountBig)
)
if totalAmount.Sign() == 0 {
    return amount, big.NewInt(0) // degenerate: no CL stake, give all to CN
}
```

### Proof of Concept

1. A validator registers in AddressBook with a CNStaking contract balance of `(math.MaxInt64 + 1) * 1e18` kei = 9,223,372,036,854,775,808 KAIA.
2. `parseCallResult` stores `stakingAmounts[i] = big.NewInt(0).Div(a, big.NewInt(params.KAIA)).Uint64()` → `uint64(9223372036854775808)`.
3. The validator also has a CL pool with 1,000,000 KAIA.
4. At block finalization, `assignStakingRewards` calls `cn.Split(reward)`.
5. Inside `Split`: `int64(9223372036854775808)` = `math.MinInt64` = `-9223372036854775808`.
6. `cnAmountBig = big.NewInt(-9223372036854775808)` (negative).
7. `clAmountBig = big.NewInt(1000000)` (positive).
8. `totalAmount = -9223372036854775808 + 1000000` = large negative.
9. `clAmount = 1000000 * reward / totalAmount` → negative value.
10. `cnAmount = reward - clAmount = reward + |clAmount|` → exceeds `reward`.
11. CN validator's reward address receives more KAIA than the total staking reward; CL pool balance is reduced by `|clAmount|`. [5](#0-4)
