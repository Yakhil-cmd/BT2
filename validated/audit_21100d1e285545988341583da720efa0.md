### Title
Attacker-controlled trigger data can inject an unvalidated, structurally arbitrary AA definition via dynamic `app=definition` messages - ([File: aa_validation.js])

### Summary
The reported CVE's bug class is "untrusted data is later re-interpreted and executed as trusted code/commands" (pg_dump embeds attacker data into a dump that `psql` subsequently executes as meta-commands during restore, i.e. a data→code boundary is crossed without re-validation). The same class of bug is reachable in ocore's Autonomous-Agent (AA) engine: a value that is only *data* at definition-authoring time (a formula string wrapped in `{...}`) is allowed to bypass structural/security validation of the code it produces, and that produced "code" (a brand-new AA definition) is later trusted and made live without ever being run through the full validator that normal, statically authored AA definitions must pass.

### Finding Description
When a unit posts an `app=definition` message that defines a nested/child AA, `aa_validation.js` validates the payload in `validateMessage`/`validatePayload`. For the `'definition'` case: [1](#0-0) 

If `payload.definition` (or `payload.definition[1]`, the AA's template body) is itself a formula string (`getFormula(...) !== null`, i.e. wrapped in `{...}`), validation is skipped entirely (`return cb2()`), deferring all structural checks — allowed message apps, formula well-formedness, complexity/op-count limits, valid asset/definition schema, etc. — to be performed "later," at the moment the formula is evaluated. The commented-out line confirms the intended-but-missing safety net: `// (typeof setImmediate === 'function') ? setImmediate(validateAADefinition, payload.definition, cb2) : ...`.

The actual evaluation of such dynamic definitions happens inside `handleTrigger`'s `replace()`/`evaluateAA()` machinery in `aa_composer.js`, which walks the AA template and evaluates every `{...}`-wrapped string as an oscript formula using the *current, attacker-supplied* `trigger` data: [2](#0-1) [3](#0-2) 

The comment at line 617 documents that this is intentional ("app=definition is also replaced using the current trigger and vars ... has to generate `{}`-formulas in order to be dynamic"), but the resulting, fully-substituted nested AA definition — which can contain attacker-influenced strings, and in the value-substitution branch (line 658-695) can even resolve to attacker-controlled **objects/arrays** (`bObjectResultAllowed: true`) — is never passed back through `aa_validation.validateAADefinition`. When the new AA is persisted, only getter properties are computed, not full schema/complexity validation: [4](#0-3) 

By contrast, `readAAGetterProps`/`determineGetterProps` merely computes complexity metadata; it does not re-run `validateAADefinition`'s message/app/formula whitelist checks. This means the deferred validation promised by the skip at `aa_validation.js:209/217` never actually happens for the fully-resolved definition — the "code" that data value evaluates to is trusted without the checks that every other AA definition must pass.

This mirrors the CVE class precisely: a security boundary (schema/structure validation) is bypassed because the payload is "just data" at the point checked, but that data is later interpreted and executed as code (a live, funded, callable AA) in a context that assumes it already passed validation.

### Impact Explanation
An attacker who can trigger a "factory" AA (any unprivileged unit poster who sends a payment/trigger to an AA that dynamically composes a child AA definition, a supported and documented pattern shown in `test/aa_composer.test.js:922-1011` and `test/aa_composer.test.js:554-650`) can influence the resulting nested definition's content through `trigger.data`/`trigger.address`/`trigger.output` substitutions that were never subjected to `validateAADefinition`. If the factory AA's author did not perfectly constrain every substitution point, an attacker-supplied value could produce a child AA definition with disallowed apps, malformed complexity, or unintended payment/oscript logic that the design assumed impossible because "validation happens later." Since child AAs created this way immediately become live, funded contract addresses (per the "define new AA and activate it" test flow), a structurally invalid or maliciously shaped definition slipping through can lead to unintended fund routing/loss within that AA subsystem — a concrete AA fund-loss/freezing condition, matching the "Validate" criteria in scope.

### Likelihood Explanation
This requires: (1) an existing factory-style AA using dynamic `{...}`-based `definition`/`definition[1]` payloads (a supported, documented feature, not exotic), and (2) that AA's author failing to fully sanitize every substitution point reachable from `trigger` data before it flows into the definition template. Because ocore explicitly supports and documents this dynamic-definition feature (and the code contains an explicit, deliberately-disabled call to re-validate), the missing re-validation is a structural gap in the framework itself rather than a one-off application bug — any factory AA is exposed to this gap regardless of how careful its author is, since `aa_validation.js` guarantees no structural safety net for the final materialized definition.

### Recommendation
After `replace()`/`evaluateAA()` fully resolves a dynamic `app=definition` payload's nested `arrDefinition` (i.e., once no `{...}` formulas remain), run the resolved definition through `aa_validation.validateAADefinition` (the same check applied to statically authored AA definitions) before it is accepted into the response unit / before `storage.insertAADefinitions` treats it as valid. This restores the intended behavior hinted at by the commented-out `setImmediate(validateAADefinition, payload.definition, cb2)` line in `aa_validation.js:222`, closing the gap where "we'll validate it later" never actually happens.

### Proof of Concept
1. Deploy a "factory" AA whose `messages` include an `app: 'definition'` message with a dynamic body, e.g. a nested AA definition where some field (message app, formula, or complexity-affecting structure) is derived from `trigger.data` without exhaustive whitelisting (following the pattern in `test/aa_composer.test.js:944-970`, but substituting attacker-controlled `trigger.data` fields into structural positions of `$child_aa` rather than only leaf value fields).
2. Send a trigger unit to the factory AA with `trigger.data` crafted to produce a child-AA definition that would be rejected by `aa_validation.validateAADefinition` if checked directly (e.g., exceeding complexity limits, using disallowed nested structures, or malformed formulas) — because `aa_validation.js:209/217` skip that check for dynamic (formula-wrapped) definitions.
3. Observe that the resulting child AA is created via `storage.insertAADefinitions` (which only computes getter props, not full validation) and becomes live/fundable despite never passing `validateAADefinition`, confirming the missing re-validation gap.
