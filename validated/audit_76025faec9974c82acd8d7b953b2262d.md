## Analog Found

### Title
Stack-scoped API tokens can read CCMenu status for any stack, bypassing token stack authorization - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::ApiClient` tokens can be scoped to a single stack via `stack_id` [1](#0-0) , and `Shipit::Api::BaseController` enforces this scoping by resolving the requested stack through a `stacks` collection filtered on `current_api_client.stack_id` before looking up the `stack_id` param [2](#0-1) . `Shipit::Api::CCMenuController`, however, overrides `stack` to resolve directly against the global `Stack` model instead of the scoped `stacks` collection, breaking the binding between "the stack a token authorizes" and "the stack the request actually touches."

### Finding Description
`BaseController#stack` is the authorization-aware accessor used by every other API endpoint:
```ruby
def stacks
  @stacks ||= current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all
end

def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
``` [2](#0-1) 

`CCMenuController` overrides `stack` and loads it from the unscoped `Stack` class directly:
```ruby
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end

def authenticate_api_client
  @current_api_client = ApiClient.authenticate(params[:token])
  super unless @current_api_client
end
``` [3](#0-2) 

`require_permission :read, :stack` on this controller only checks that the token has the string permission `read:stack` via `ApiClient#check_permissions!`, which does not check `stack_id` at all [4](#0-3) . Since the per-stack restriction is only implemented in `BaseController#stacks`/`#stack`, and `CCMenuController` never calls those methods, any token holding `read:stack`, even one created and intended to be limited to a single stack (as the fixture `here_come_the_walrus` demonstrates — `stack: shipit`, `permissions: ['read:stack']` [5](#0-4) ), can query `CCMenuController#show` for any `stack_id` in the system, not just the one it was scoped to.

This exactly mirrors the reported bug class: a credential/authorization binding (`ApiClient.stack_id` ↔ requested `stack_id`) that is enforced in the general code path but silently skipped in one specific consumer of the same data, letting the caller act on an object outside what it was actually authorized for — analogous to `rebalance`/`rebalanceLite` accepting a caller-supplied `account` instead of being bound to `msg.sender`.

Elsewhere in the codebase this scoping is verified to matter: `StacksControllerTest` explicitly asserts "an api client scoped to a stack will only see that one stack" [6](#0-5) , confirming stack scoping is a deliberate security boundary that `CCMenuController` fails to respect.

### Impact Explanation
This grants unauthenticated (relative to the target stack) read access to stack state/deploy output: `CCMenuController#show` exposes `stack.deploys_and_rollbacks.last` including build status, last build label/time, and web URL, for any stack, using a token that was only meant to be authorized for a different single stack [7](#0-6) . This matches the in-scope "High" impact category: "unauthenticated read of stack state, task streams or deploy output" achieved by a token that should have been restricted.

### Likelihood Explanation
Any holder of a valid, narrowly-scoped `ApiClient` token (e.g., one deliberately issued for a CI badge / CCMenu integration for a single stack, as created by `CCMenuUrlController` with `permissions: %w[read:stack]` [8](#0-7) ) can trivially trigger this by changing the `stack_id` in the request URL/param — no additional privilege, secret, or session is required beyond the token itself, which the requester already legitimately possesses for their own stack.

### Recommendation
Change `CCMenuController#stack` to resolve through the scoped `stacks` collection (i.e., delegate to `super` or use `stacks.from_param!(params[:stack_id])`) instead of `Stack.from_param!`, so a stack-scoped token cannot read data for stacks outside its `stack_id`.

### Proof of Concept
1. Create/obtain an `ApiClient` scoped to stack A with `permissions: ['read:stack']` and `stack_id` = A (e.g., via `CCMenuUrlController#fetch` for stack A) [9](#0-8) .
2. Using that token, send `GET /api/stacks/B/ccmenu.xml?token=<token_for_A>` where B is a different, unauthorized stack.
3. `authenticate_api_client` succeeds because the token is valid [10](#0-9) ; `require_permission :read, :stack` passes because the client has `read:stack` [4](#0-3) ; and `stack` resolves stack B directly via `Stack.from_param!` [11](#0-10) , returning stack B's deploy status even though the token was only authorized for stack A.

module Shipit

    ].freeze
