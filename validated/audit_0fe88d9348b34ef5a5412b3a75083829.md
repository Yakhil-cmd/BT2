### Title
CCMenu API token created without stack scope grants unauthenticated read access to every stack's build status - ([File: app/controllers/shipit/ccmenu_url_controller.rb])

### Summary
The `Coupon`-without-deadline bug reduces to the same root class of flaw as this finding: a credential's verification/authorization does not cover a field it is supposed to be scoped to, so the credential can be used outside the boundary it was intended for. In `PhiDaily.sol` the signature omitted a time boundary; in Shipit the `ApiClient` token minted for the CCMenu widget omits the *stack* boundary, even though `ApiClient` explicitly supports per-stack scoping.

### Finding Description
`CCMenuUrlController#client` mints (or reuses) an `ApiClient` for the CCMenu integration: [1](#0-0) 

`ApiClient.create_with(permissions: %w[read:stack]).find_or_create_by!(creator: current_user, name: 'CCMenu Client')` never sets `stack:`. `ApiClient` has `belongs_to :stack, optional: true`, and `stack_id?`/`current_api_client.stack_id?` in the base controller is the only mechanism that restricts a token to a single stack: [2](#0-1) 

Because `stack` is never assigned, the token is globally scoped (`stack_id` is `nil`), so `current_api_client.stack_id?` is false and, wherever that base-class `stacks` scoping is used, the client would be treated as authorized for `Stack.all`.

Worse, the consuming controller, `Api::CCMenuController`, doesn't even go through that base-class stack-scoping helper — it fetches the target stack directly and unconditionally: [3](#0-2) 

and authenticates purely via a query-string `token` param, bypassing the normal Basic-Auth flow used elsewhere: [4](#0-3) 

`require_permission :read, :stack` only checks that the `ApiClient#permissions` array contains `read:stack` (an operation/scope pair) — it never checks that the token's `stack_id` matches the `stack_id` in the URL: [5](#0-4) 

So the binding that should hold is:
`token.stack (intended, single stack shown in the generated ccmenu_url)` == `stack (any stack_id an unauthenticated holder of the token supplies to Api::CCMenuController#show)`

After the CCMenu URL is generated for stack A, the equality no longer holds: the same token authenticates and returns build data for stack B, C, ... any stack in the installation, because nothing ties the token to stack A at either creation time or verification time.

### Impact Explanation
CCMenu tokens are specifically designed to be embedded in third-party, often unauthenticated consumers (CI dashboard widgets, status pages) as indicated by `CCMenuUrlController` returning a shareable URL with the token baked into the query string. Anyone who obtains that URL/token (through logs, a shared dashboard, a browser history, a leaked widget config, etc.) gets **unauthenticated read access to every stack's deploy/rollback status** in the Shipit instance, not just the one it was generated for — this matches the High-severity impact bucket: "unauthenticated read of stack state, task streams or deploy output."

### Likelihood Explanation
Likelihood is moderate-to-high: no privileged Shipit session or GitHub credentials are required to exploit the token once obtained — only the token string, which by design is meant to be embedded in low-trust contexts (public/semi-public build-status widgets). No additional guessing or brute force is required; the attacker simply changes the `stack_id` in the API path while reusing the leaked `token` query parameter.

### Recommendation
- When creating the CCMenu `ApiClient`, always set `stack:` to the specific stack being viewed (and vary the client `name`/lookup key per stack, e.g. `name: "CCMenu Client (#{stack.to_param})"`), so `stack_id?` correctly scopes the token.
- In `Api::CCMenuController#stack`, honor the client's stack scope the same way `Api::BaseController#stack` does (`stacks.from_param!(params[:stack_id])`) instead of calling `Stack.from_param!` directly, so a stack-scoped token cannot be replayed against a different `stack_id`.

### Proof of Concept
1. As any logged-in Shipit user with access to Stack A, call `GET /stacks/:A/ccmenu_url` (routed to `CCMenuUrlController#fetch`). This returns a URL such as `https://shipit.example.com/api/A/ccmenu.xml?token=<TOKEN>`.
2. Leak/observe `<TOKEN>` (e.g., via a public status page that embeds this widget, browser history, proxy logs, etc.) — no Shipit login is required from this point.
3. Send `GET /api/B/ccmenu.xml?token=<TOKEN>` for a different stack `B` that the token holder was never authorized to view.
4. `Api::CCMenuController#authenticate_api_client` succeeds via `ApiClient.authenticate(params[:token])` since the signature itself is valid; `stack` resolves to `Stack.from_param!('B')` unconditionally; `require_permission :read, :stack` passes because the token has `read:stack` in its `permissions` array (with no stack constraint checked). The response renders Stack B's latest deploy/rollback status — data the token was never scoped to expose.
