### Title
Double-callback crash in `handleSavedPrivatePayments` on malformed private-payment payload - (File: network.js)

### Summary
`network.js`'s `handleSavedPrivatePayments()` processes queued private-payment chains sent by wallet counterparties. In `validateAndSave()`, when `objectHash.getBase64Hash(objHeadPrivateElement.payload, true)` throws (e.g., because the attacker-controlled `payload` object contains a type that the hash serializer cannot handle), the `catch` block calls `deleteHandledPrivateChain(..., cb)` but does **not** `return`, so execution falls through to the line computing `key` and then unconditionally calls `privatePayment.validateAndSavePrivatePaymentChain(arrPrivateElements, {...})`, whose `ifError`/`ifOk`/`ifWaitingForChain` handlers each also eventually call `cb()`. [2](#0-1) [3](#0-2) 

### Finding Description
`cb` is the per-item iterator callback of `async.each()`; calling it more than once for the same item violates the `async` library's callback contract. Depending on the `async` version bundled, this either throws (`Error: Callback was already called`) or corrupts internal iterator state. If it throws, and there is no surrounding `try/catch` at that call frame (the code path runs inside a DB query callback and event-loop tick, outside any request-scoped try/catch), the exception becomes an unhandled exception that crashes the Node.js process running the wallet/hub-connected node. This is the same bug class as the Capstone CVE: a decode/validation branch that fails a structural check (bad opcode combination / malformed input) does not properly abort, leaving the caller to dereference/act on a bad state, resulting in a crash reachable purely by supplying malformed attacker-controlled data (crafted `0F 0F` bytes ↔ crafted private-payment `payload` object that makes `getBase64Hash` throw).

The trigger is fully reachable by an unprivileged private-payment counterparty: `handlePrivatePaymentChains` in `wallet.js` accepts `body.chains` from a device-paired peer with only shallow structural validation (`isNonemptyObject(e.payload)`, `isNonemptyString(e.payload.asset)`, etc.) — it does not validate that `payload` is safely hashable. [4](#0-3) 
Malformed/oversized/self-referential or otherwise unhashable payload content that passes this shallow check but fails inside `objectHash.getBase64Hash` (e.g. via `getSourceString`/`getJsonSourceString` type errors) will reach `handleOnlinePrivatePayment` → `unhandled_private_payments` table → `handleSavedPrivatePayments` → the vulnerable `validateAndSave`. [5](#0-4) 

### Impact Explanation
A successful trigger crashes the receiving node's process (wallet, hub, or full node handling private payments for its users). Because private-payment forwarding is a normal wallet/hub feature reachable from any correspondent device, an attacker with a paired device (a normal private-payment counterparty, not a "malicious peer/hub/node" in the p2p sense) can repeatedly crash the victim's node process, causing denial of service and potential failure to timely process/confirm private and public transactions on that node (matches "network unable to confirm new units" outcome for the affected node). This does not lead to double-spend or fund loss directly, but it is a reliable, remotely triggerable process-crash DoS.

### Likelihood Explanation
Likelihood is moderate-to-high: the attacker only needs to be an established correspondent (paired device) able to send a `private_payment_chain`/`chains` message with a payload object structured to trip an exception inside `objectHash.getBase64Hash` (e.g., unsupported value types, or extremely deep/circular-like nested structures that the shallow `isNonemptyObject` checks in `wallet.js`/`network.js` do not filter). No special privileges beyond being a wallet correspondent are required, and the code path is exercised automatically whenever queued private payments are (re)processed.

### Recommendation
Add a `return` immediately after the `catch` block's `deleteHandledPrivateChain(...)` call in `network.js`'s `validateAndSave()` so execution does not continue to call `privatePayment.validateAndSavePrivatePaymentChain(...)` a second time on the same `cb`. Additionally, harden `objectHash.getBase64Hash`/`getSourceString` (or callers) to validate the payload's structure/types before hashing, and wrap the whole `async.each` iterator body in a try/catch that always calls `cb(err)` exactly once, to prevent any future double-callback or uncaught-exception crash in this handler.

### Proof of Concept
1. As a paired wallet correspondent (private-payment counterparty), craft a `private_payment` chain (`body.chains`) whose head element's `payload` passes the shallow structural checks in `wallet.js:handlePrivatePaymentChains` (`isNonemptyObject(payload)`, valid `asset`, non-empty `inputs`/`outputs` arrays of non-empty objects) but embeds a field/value that causes `objectHash.getBase64Hash(payload, true)` to throw (e.g., a value type unsupported by the hash source-string serializer).
2. Send this chain to the victim node via the paired-device message channel; it is queued into `unhandled_private_payments`.
3. When `handleSavedPrivatePayments()` runs (triggered periodically/by events), `validateAndSave()` hits the exception in `getBase64Hash`, calls `deleteHandledPrivateChain(..., cb)` without returning, then falls through and calls `privatePayment.validateAndSavePrivatePaymentChain(...)`, which invokes `cb()` again.
4. The duplicate invocation of `async.each`'s iterator callback triggers the library's "callback already called" error (or equivalent internal corruption), crashing the node process handling private payments for its users.
