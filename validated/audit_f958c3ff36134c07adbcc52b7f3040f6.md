### Title
API clients can impersonate any Shipit user via the unauthenticated `X-Shipit-User` header - (File: app/controllers/shipit/api/base_controller.rb)

### Summary
The `WithdrawNFTSolvent` bug's root cause is that an unprivileged signer field is trusted to select the account acted upon, without cryptographically binding it to the request's actual authorization. Shipit's `Api::BaseController#identify_user` has the same class of flaw: any request authenticated with a valid `ApiClient` token can additionally set the `X-Shipit-User` header to an arbitrary login, and that value is trusted as the acting `User` for the request with no verification that the token/credential is bound to that user.

### Finding Description
`Api::BaseController` authenticates the caller via HTTP Basic auth against an `ApiClient` token: `ApiClient.authenticate(token)` [1](#0-0) . This proves the caller possesses a valid `ApiClient` credential, but `ApiClient` records are not associated with a specific end-user identity at request time beyond `creator` (who created the client, not who is using it).

Separately, `current_user` is derived purely from a client-supplied header:
```
def current_user
  @current_user ||= identify_user || AnonymousUser.new
end

def identify_user
  user_login = request.headers['X-Shipit-User'].presence
  User.where('lower(login) = ?', user_login.downcase).first if user_login
end
``` [2](#0-1) 

This is the exact analog to the report's binding break: the equality that should hold is `credential holder == User acted-as`, but here `ApiClient token possession` (the verified credential) is disconnected from `X-Shipit-User` (an unverified payload field) that is used to select the `User` record attributed to the action. Any holder of any `ApiClient` token — regardless of that token's `creator` or scope — can set this header to the login of any other Shipit user, including administrators or team leads, and have destructive actions recorded/attributed to that identity.

This value flows into security- and audit-relevant operations:
- `stack.trigger_deploy(commit, current_user, ...)` in `Api::DeploysController#create` [3](#0-2) 
- `stack.lock(params.reason, current_user)` in `Api::LocksController#create`/`#update` [4](#0-3) 
- Similar patterns exist in `Api::RollbacksController`, `Api::TasksController`, `Api::MergeRequestsController`, and `Api::ReleaseStatusesController` (all confirmed to reference `current_user`).

### Impact Explanation
This crosses a credential/identity boundary explicitly called out in scope: "a GitHub identity versus the `User` bound to the session." Any process or integration holding a legitimate but narrowly-scoped `ApiClient` token (e.g., a CI token meant only to trigger deploys) can forge the acting-user identity for every write operation it performs, attributing locks, deploys, rollbacks, and merge actions to arbitrary other users — including administrators — without their knowledge. This undermines audit trails and could be used to bypass user-specific expectations embedded in `shipit.yml` (e.g., checklists that reference "who locked/deployed") or downstream tooling/notifications keyed on `current_user.login`.

However, note that `current_user` in this codebase is not used as an authorization gate itself (permission checks are driven by `ApiClient#check_permissions!` based on the token's own `permissions`, e.g. `require_permission :deploy, :stack`), so this is an identity/attribution spoof rather than a permission escalation. The `ApiClient` token's own permission scope still bounds *what* action can be performed, but not *who* it is attributed to.

### Likelihood Explanation
High likelihood of exploitation by anyone possessing any valid `ApiClient` token (even one with minimal, task-specific permissions), since setting an arbitrary `X-Shipit-User` header requires no special access beyond normal API usage; the tests confirm this header is fully attacker-controlled and unauthenticated: [5](#0-4) .

### Recommendation
Do not let the `X-Shipit-User` header freely select an arbitrary `User`. Either remove this feature, or bind it to the specific `ApiClient`: store an authorized/allowed user (or list of users) on the `ApiClient` record itself and validate that the header value matches an authorized identity for that specific token, rather than trusting the raw header value across all clients uniformly.

### Proof of Concept
1. Obtain (or be issued) any valid, narrowly-permissioned `ApiClient` authentication token (e.g., one scoped only to `deploy:stack`).
2. Issue an authenticated API request, e.g. `POST /api/stacks/:id/locks`, with header `X-Shipit-User: <admin-login>`.
3. Observe that `Shipit::Stack#lock` is called with `current_user` resolved to the admin `User` record purely from the header value [6](#0-5) , with no check that the presenting `ApiClient` is associated with that admin account. Existing tests demonstrate the header is trusted directly, e.g. `request.headers['X-Shipit-User'] = @user.login` sets `deploy.user` with no additional verification [7](#0-6) .
