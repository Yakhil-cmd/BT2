### Title
Webhook signature is verified against `repository.owner.login`, but repository handlers act on the unverified `repository.full_name` field — cross-organization/cross-repository writes ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret to validate the HMAC signature against using `repository_owner`, which is read from the payload's `repository.owner.login` (or `organization.login`). [1](#0-0) [2](#0-1)  However, once the signature is accepted, the event handlers determine *which repository/stack to mutate* using a completely different field of the same payload: `repository.full_name`, via `Handler#repository_name` / `#stacks`. [3](#0-2)  Nothing in the codebase asserts that the owner encoded in `repository.owner.login` (used to pick the verifying secret) matches the owner encoded in `repository.full_name` (used to pick the mutated repository). This breaks the binding: `organization authenticated == repository written`.

### Finding Description
For a multi-organization Shipit deployment, each GitHub organization has its own webhook secret, retrieved via `Shipit.github(organization: repository_owner)`. `verify_signature` computes `repository_owner` purely from payload content:

```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [2](#0-1) 

The signature check itself only proves that the raw body was HMAC-signed with *some* secret belonging to the organization identified by that field — it does not enforce that this same owner is the one whose repository is subsequently acted upon.

Downstream, generic webhook handlers (`Handler#stacks` / `#repository_name`) resolve the target repository from a **different** JSON key, `repository.full_name`:

```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [3](#0-2) 

`PushHandler#process` then iterates over those stacks and triggers a GitHub sync job with an attacker-controlled `expected_head_sha`:

```ruby
def process
  stacks
    .not_archived
    .where(branch:)
    .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
end
``` [4](#0-3) 

Because `repository.owner.login` and `repository.full_name` are independent, attacker-controllable strings inside the same JSON body (both fully under the attacker's control before it is signed with the attacker's own legitimately-known secret for their own organization), an attacker who administers a webhook for Organization A (able to set that org's webhook secret/payload, not a Shipit privileged user) can:

1. Set `repository.owner.login` (or `organization.login`) = `"OrgA"` so `verify_signature` selects and validates against OrgA's webhook secret — a secret the attacker legitimately knows.
2. Set `repository.full_name` = `"OrgB/victim-repo"`, an unrelated repository/stack that already exists in the same Shipit instance under a different, unauthorized organization.
3. Sign the whole payload with OrgA's secret and POST it to `/webhooks`. The signature check passes because it only checks that the org identified by `owner.login` (OrgA) matches the secret used.
4. `Handler#stacks` resolves `Repository.from_github_repo_name("OrgB/victim-repo")` and the handler (e.g. `PushHandler`) mutates OrgB's stacks — enqueuing sync jobs and recording an attacker-supplied `expected_head_sha` — even though the request was never authenticated for OrgB.

This is the direct analog of the reported bug class: a "trusted" field (the value used for the access-control decision) is decoupled from the field actually acted upon, with no cross-check tying the two together, exactly mirroring `_setParams` accepting unchecked/uncorrelated values that later drive privileged behavior.

### Impact Explanation
This allows cross-repository/cross-organization writes: an attacker with only unprivileged control of one organization's GitHub webhook configuration (not a Shipit admin, not holding `Shipit.github_teams` permissions, no API token) can force Shipit to enqueue sync/update jobs against stacks belonging to a completely different, unauthorized organization/repository, and inject attacker-chosen values (e.g. `expected_head_sha`) into that unrelated stack's state. Per the rules, cross-repository writes are classified as Critical impact.

### Likelihood Explanation
Exploitation requires: (a) a multi-tenant Shipit deployment configured with more than one GitHub organization/app secret, (b) the attacker legitimately controlling a webhook for at least one of those organizations (a realistic, low-privilege scenario for large orgs where webhook administration is delegated), and (c) the target repository already existing as a Stack in the same Shipit instance. Given these common multi-tenant deployment conditions, likelihood is moderate — it does not require compromising any secret belonging to the victim organization, only the attacker's own.

### Recommendation
In `WebhooksController#verify_signature` and/or `Handler#repository_name`/`#stacks`, cross-validate that the organization used to select/verify the webhook secret (`repository.owner.login` / `organization.login`) matches the owner portion of `repository.full_name` before any handler is permitted to act on it. Reject the webhook (422) if these two payload-derived identities disagree, closing the gap between the authenticated organization and the repository that is ultimately written.

### Proof of Concept
1. Attacker administers a GitHub webhook for `OrgA` in a Shipit instance that also hosts stacks for `OrgB` (a separate, unrelated org/tenant they do not control).
2. Attacker crafts a `push` event JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>",
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/victim-repo" }
}
```
3. Attacker signs the raw body with OrgA's known webhook secret and sends `X-Hub-Signature: sha1=<hmac>` and `X-Github-Event: push` to `/webhooks`.
4. `verify_signature` calls `Shipit.github(organization: "OrgA")` and validates successfully (attacker knows OrgA's secret). [1](#0-0) 
5. `PushHandler#process` resolves stacks via `Repository.from_github_repo_name("OrgB/victim-repo")` and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` on OrgB's stack, despite the request never being authenticated for OrgB. [4](#0-3)
