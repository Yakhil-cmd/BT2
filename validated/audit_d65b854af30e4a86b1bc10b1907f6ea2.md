### Title
`provision?` operator-precedence bug bypasses `review_stacks_enabled` master switch for `allow_with_label`/`prevent_with_label` - ([File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb])

### Summary
`OpenedHandler#provision?` uses `&&`/`||` without parentheses, so `review_stacks_enabled` only gates the `allow_all` branch and not the `allow_with_label` or `prevent_with_label` branches. An attacker who owns a PR on any repository configured with either of those two provisioning behaviors can create a review stack purely by adding/omitting a label on their own PR, even when the repository's operator has explicitly disabled review stacks (`review_stacks_enabled: false`).

### Finding Description
The intended binding is: `repository.review_stacks_enabled == true` must be true before `respond_to_pull_request_opened?` returns true, for all three values of `provisioning_behavior`. The actual code is: [1](#0-0) 

Due to Ruby operator precedence (`&&` binds tighter than `||`), this parses as:
`(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label) || (prevent_with_label? && !has_label)`

So when `review_stacks_enabled` is `false` but `provisioning_behavior` is `allow_with_label` or `prevent_with_label`, `provision?` can still return `true` purely based on `pull_request_has_provisioning_label?`, which reads label names directly from the attacker-controlled webhook payload: [2](#0-1) 

Compare this to the sibling handler `LabeledHandler#respond_to_label_change?`, which correctly ANDs `review_stacks_enabled` with the behavior-specific `archive?`/`unarchive?` checks: [3](#0-2) 

This confirms the intended semantics (`review_stacks_enabled` must gate every behavior) and that `OpenedHandler` diverges from it.

Exploit flow: attacker opens a PR (or reopens) on a repository they control that is onboarded to Shipit with `provisioning_behavior: allow_with_label` (or `prevent_with_label`) but `review_stacks_enabled: false`. GitHub sends a legitimately-signed `pull_request` "opened" webhook (signature verification is not bypassed — the attacker is the legitimate PR author/owner of that repo, so the webhook is authentic). `process` then calls `ReviewStackAdapter#find_or_create!`, creating a `Shipit::Stack` and driving subsequent deploy tasks (`TaskCommands#perform`) that run with `GITHUB_TOKEN`/`GIT_ASKPASS` in `Command#unbundled_env`. None of the listed guards (`verify_signature`, `ExplicitParameters` schema, `force_github_authentication`, model validations) address this because the flaw is purely in the boolean logic of `provision?`, not in authentication or payload shape.

### Impact Explanation
An attacker on any repository whose owner enabled Shipit with `provisioning_behavior` set to `allow_with_label` or `prevent_with_label` — believing `review_stacks_enabled: false` fully disables review-stack provisioning — can still force stack creation and downstream deploy-command execution (with `GITHUB_TOKEN`/`GIT_ASKPASS`) by controlling only their own PR's labels. This matches "unauthorized deploy" / stack creation for a repository whose operator did not authorize it, a Critical-category impact. It is repeatable against every repository configured this way and requires no privileged role.

### Likelihood Explanation
Preconditions: a repository must be onboarded to Shipit with `provisioning_behavior` set to `allow_with_label` or `prevent_with_label` (a plausible, documented, non-default-only configuration) while `review_stacks_enabled` is `false`. Attacker cost is trivial: open a PR and add/omit one label — no secrets, tokens, or team membership required. This is fully repeatable per-PR.

### Recommendation
Parenthesize `provision?` so `review_stacks_enabled` gates all branches:
```ruby
def provision?
  repository.review_stacks_enabled &&
    (repository.provisioning_behavior_allow_all? ||
     (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
     (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?))
end
```

### Proof of Concept
minitest plan (parameterized), analogous to the `OpenedHandlerTest` fixture pattern described in the prompt:
```ruby
[:allow_with_label, :prevent_with_label].each do |behavior|
  test "#provision? does not create a stack when review_stacks_enabled is false (#{behavior})" do
    repository = stub_repository(review_stacks_enabled: false, provisioning_behavior: behavior)
    label_name = behavior == :allow_with_label ? repository.provisioning_label_name : "unrelated"
    params = build_opened_params(repository: repository, labels: [label_name])

    assert_no_difference -> { Shipit::Stack.count } do
      Shipit::Webhooks::Handlers::PullRequest::OpenedHandler.new(params).process
    end
  end
end
```
Before the fix, this test fails (a `Shipit::Stack` is created despite `review_stacks_enabled: false`); after applying the parenthesization fix, `Shipit::Stack.count` does not change, matching the intended `review_stacks_enabled == true` gate.
