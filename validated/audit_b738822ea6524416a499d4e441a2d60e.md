### Title
Deregistered Bridge Operator's Stale Votes Persist and Combine with New Operator Votes to Reach Threshold — (`contracts/service_chain/bridge/BridgeOperator.sol`)

---

### Summary

`deregisterOperator` removes an operator from the active set but does not clear their existing vote counts from the `votes` mapping. When a new operator is subsequently registered and votes on any nonce the deregistered operator had already voted on, the stale vote count combines with the new vote to reach `operatorThresholds`, executing a bridge value transfer (KLAY / ERC20 / ERC721) with fewer active-operator votes than the threshold requires.

---

### Finding Description

`deregisterOperator` performs only two state mutations:

```solidity
delete operators[_operator];          // removes from active set
operatorList[i] = operatorList[...];  // removes from list
operatorList.length--;
``` [1](#0-0) 

The per-nonce vote accounting stored in `votes[voteType][nonce].voteCounts` and `votes[voteType][nonce].voted` is **never touched**. Any `voteCounts[voteKey]` incremented by the deregistered operator remains at its elevated value.

When a new operator C is later registered and calls `handleKLAYTransfer` (or `handleERC20Transfer` / `handleERC721Transfer`) for nonce N, `_voteCommon` is invoked:

```solidity
vote.voteCounts[_voteKey]++;
if (vote.voteCounts[_voteKey] >= operatorThresholds[uint8(_voteType)]) {
    return true;   // threshold reached → transfer executes
}
``` [2](#0-1) 

Because the deregistered operator A's vote is still counted in `voteCounts[voteKey]`, C's single vote pushes the total to `threshold`, and the transfer is executed. The `onlyOperators` guard on the handle functions only verifies that the *caller* is currently active; it does not re-validate the historical voters already recorded in `voteCounts`. [3](#0-2) 

The code comment acknowledges this scenario but frames it as an operational concern rather than a security invariant:

> *"Note that outstanding votes by the deregistered operator are not revoked … The Owner shall recognize this issue and expect that operator deregistration takes some time to be fully effective."* [4](#0-3) 

The invariant that is broken: **deregistering an operator must prevent their votes from contributing to any future threshold check**. The contract does not enforce this.

---

### Impact Explanation

A bridge value transfer of KLAY, ERC20, or ERC721 tokens can be executed on the destination chain with only **one** currently-active operator's vote when the threshold is 2 (or more generally, with `threshold − 1` fewer active votes than required). If operator A was deregistered because their key was compromised, the attacker who controls A's key has already cast the deciding vote; any legitimate new operator's routine vote on a pending nonce will complete the quorum and release funds.

Affected functions: `handleKLAYTransfer`, `handleERC20Transfer`, `handleERC721Transfer`. [5](#0-4) [6](#0-5) 

---

### Likelihood Explanation

The scenario requires the bridge owner to deregister one operator and register a replacement — a routine operational action (key rotation, operator replacement). The stale-vote window is open for every nonce the deregistered operator voted on before removal. No special attacker capability is needed beyond having previously been a legitimate operator.

---

### Recommendation

In `deregisterOperator`, iterate over all open nonces and decrement (or zero) the deregistered operator's vote contribution before removing them from the active set:

```solidity
function deregisterOperator(address _operator) external onlyOwner {
    require(operators[_operator]);

    // Revoke all outstanding votes by this operator
    for (uint8 vt = 0; vt < uint8(VoteType.Max); vt++) {
        // iterate over known open nonces and clear vote.voted[_operator]
        // decrement voteCounts for the key they voted on
    }

    delete operators[_operator];
    // ... remove from operatorList ...
}
```

Alternatively, add a re-validation step inside `_voteCommon` that checks `operators[voter]` for every address in `vote.voters` before counting their contribution, or store a per-operator "deregistration epoch" and reject votes cast before that epoch.

---

### Proof of Concept

```
Setup: operators = {Owner, A, B}, threshold = 2

1. A calls handleKLAYTransfer(txHash, from, to, 1 ether, nonce=5, blk, "")
   → voteCounts[keccak256(calldata)] = 1   (A's vote recorded)

2. Owner calls deregisterOperator(A)
   → operators[A] = false
   → voteCounts[keccak256(calldata)] still = 1  ← stale vote persists

3. Owner calls registerOperator(C)
   → operators[C] = true

4. C calls handleKLAYTransfer(txHash, from, to, 1 ether, nonce=5, blk, "")
   → _voteCommon: voteCounts[voteKey]++ → 2
   → 2 >= threshold(2) → returns true
   → closedValueTransferVotes[5] = true
   → 1 ether transferred to `to`

Result: bridge transfer executed with only C's active vote;
        A's deregistered (potentially compromised) vote provided the second count.
``` [7](#0-6) [8](#0-7)

    // _voteCommon handles common functionality for voting.
    function _voteCommon(VoteType _voteType, uint64 _nonce, bytes32 _voteKey)
        private
        returns(bool)
    {
        VotesData storage vote = votes[uint8(_voteType)][_nonce];

        // If the same voter voted again, revoke previous vote.
        bytes32 oldVoteKeyOfVoter = vote.voted[msg.sender];
        if (oldVoteKeyOfVoter == bytes32(0)) {
            vote.voters.push(msg.sender);
        } else {
            vote.voteCounts[oldVoteKeyOfVoter]--;
        }

        // Either the current voter has voted before or not, update the vote data.
        vote.voted[msg.sender] = _voteKey;

        if (vote.voteCounts[_voteKey] == 0) {
            vote.voteKeys.push(_voteKey);
        }
        vote.voteCounts[_voteKey]++;

        if (vote.voteCounts[_voteKey] >= operatorThresholds[uint8(_voteType)]) {
            return true;
        }
        return false;
    }
