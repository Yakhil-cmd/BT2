### Title
Network parameter votes (`threshold_size`, `base_tps_fee`, `tps_interval`, `tps_fee_multiplier`) can be finalized from zero-stake voters because the median-vote threshold trivially passes when `total_voted_balance` is `0` - (File: main_chain.js)

### Summary
`countVotes()` in `main_chain.js` computes a stake-weighted median for numerical system-parameter votes by comparing an accumulator to `total_voted_balance / 2`. When the sum of voter balances is `0` (e.g., because voting addresses have no confirmed base-currency balance), the comparison `accumulated >= total_voted_balance / 2` evaluates to `0 >= 0`, which is true on the very first row, letting an attacker's vote (cast from a zero-balance address) set the resulting network parameter. This mirrors the referenced Olympus `Governance.sol` bug where a quorum/threshold check silently passes when the underlying "total supply" denominator is zero.

### Finding Description
In `countVotes`, voter balances are pulled from confirmed, unspent, stable-good outputs of the base asset: [1](#0-0) 

If none of the addresses that cast a `system_vote`/numerical vote for a subject currently hold any confirmed base-currency balance (e.g., brand-new addresses, or addresses whose balance was fully spent/consumed), `balances` will be empty for those addresses and their contribution to `total_balance` is `0`. Crucially, the code does not require voters to have any minimum stake to be counted — the `voter_balances` temporary table is populated straight from whatever `bal_rows` returns, with no floor check: [2](#0-1) 

Then, for numerical subjects (`threshold_size`, `base_tps_fee`, `tps_interval`, `tps_fee_multiplier`), the code computes the total voted balance and picks the value where the cumulative balance crosses half of that total: [3](#0-2) 

If `total_voted_balance` is `0` (all counted voters have zero balance for that vote), then on the very first iteration `accumulated` (`0`) satisfies `accumulated >= total_voted_balance / 2` (`0 >= 0`) immediately, so `value` is set to whatever the first row's vote value is — determined purely by SQL `ORDER BY value` — with no real economic backing. This is structurally identical to the Olympus report: a quorum/threshold guard (`args.required > total_weight`-style check in Olympus, `accumulated >= total_voted_balance/2` here) that is supposed to require a meaningful share of stake, but which is vacuously satisfied when the denominator (`totalSupply`/`total_voted_balance`) is zero, allowing a zero-value/zero-stake actor to unilaterally decide the outcome.

The only downstream safety net is `if (value === undefined) throw Error(...)`, which only fires if `rows` is completely empty — it does **not** fire when `rows` is non-empty but every row's `total_balance` is `0`, i.e., precisely the case exploited here: [4](#0-3) 

### Impact Explanation
`threshold_size`, `base_tps_fee`, `tps_interval`, and `tps_fee_multiplier` are consensus-critical system variables stored in `storage.systemVars` and used network-wide to determine TPS fee accounting and stability thresholds (`system_vars_updated` event is emitted and consumed elsewhere for fee/consensus logic). If an attacker can force one of these into an extreme value using only zero-balance addresses (freely creatable, no cost beyond posting a unit), this can distort transaction fee calculations network-wide or destabilize TPS-fee-related consensus rules, i.e., cause nodes to disagree on fee validity or push the network toward a state where legitimate units are wrongly rejected/accepted, which is a network-wide validity/consensus impact rather than a mere griefing bug.

### Likelihood Explanation
Exploitation requires that all addresses that voted for a given subject within the counted timeframe collectively hold `0` confirmed base-asset balance for the specific temporary `voter_balances` snapshot. This is plausible in edge cases: freshly-created addresses that post a vote before receiving/confirming any funds, or in the early life of the votes-table for a rarely-voted subject where legitimate stakeholders haven't voted yet, allowing an attacker to front-run with disposable zero-balance addresses. The `since_timestamp` expansion loop (searching back in yearly increments for `SYSTEM_VOTE_MIN_SHARE * TOTAL_WHITEBYTES`) is intended to ensure a meaningful share has voted, but that check only breaks the loop early when `total_balance` reaches the minimum share — it does not prevent falling through to `activation_timestamp` with an arbitrarily low (including zero) total balance, so the safeguard can be bypassed by simply waiting out the loop.

### Recommendation
In `countVotes`, before selecting a median value for numerical subjects, explicitly reject (or skip counting/finalizing) the vote when `total_voted_balance` is `0` or below `constants.SYSTEM_VOTE_MIN_SHARE * constants.TOTAL_WHITEBYTES`, instead of allowing the `accumulated >= total_voted_balance / 2` comparison to pass vacuously. Concretely, add a guard such as `if (total_voted_balance === 0 || total_voted_balance < constants.SYSTEM_VOTE_MIN_SHARE * constants.TOTAL_WHITEBYTES) throw Error("insufficient voted balance for " + subject);` immediately after computing `total_voted_balance`, mirroring the recommended fix in the Olympus report of enforcing a real minimum "supply"/stake before counting votes as valid.

### Proof of Concept
1. Create fresh addresses `A1..An` with zero confirmed base-asset balance (no need to fund them).
2. From each address, post a `system_vote` unit voting a numerical value for `threshold_size` (or `base_tps_fee`/`tps_interval`/`tps_fee_multiplier`) chosen by the attacker, e.g. an extreme low/high value.
3. Wait for the votes to stabilize; when `countVotes(conn, mci, "threshold_size", ...)` runs, `bal_rows` returns no balance rows for `A1..An` (or `0`), so `total_voted_balance` computed from `numerical_votes CROSS JOIN voter_balances` is `0`.
4. In the loop `for (let { value: v, total_balance } of rows) { accumulated += total_balance; if (accumulated >= total_voted_balance / 2) { value = v; break; } }`, the very first row (`accumulated = 0`, `total_voted_balance/2 = 0`) satisfies the condition, so `value` is set to that row's `v` — the attacker's chosen value — with zero real stake support.
5. `storage.systemVars["threshold_size"]` (or the corresponding subject) is updated network-wide via `system_vars` table and the `system_vars_updated` event, without any legitimate stakeholder participation.
