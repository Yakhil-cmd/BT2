### Title
`Api::CCMenuController#stack` bypasses `ApiClient#stack_id` scoping enforced by `BaseController#stacks` - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`BaseController#stacks` restricts stack lookups to `current_api_client.stack_id` when that attribute is set, but `Api::CCMenuController` overrides the private `stack` helper with `Stack.from_param!(params[:stack_id])`, which queries the unscoped `Stack` model. Any valid `read:stack`-permissioned `ApiClient` token — even one deliberately scoped to a single stack via `stack_id` — can be used to read build/deploy status for any stack on the instance via `GET /api/stacks/:stack_id/cc.xml`.

### Finding Description
The invariant that should hold is: `Api::CCMenuController#stack.id` must equal a value drawn from `Stack.where(id: current_api_client.stack_id)` whenever `current_api_client.stack_id?` is true — i.e., `stack.id == current_api_client.stack_id` (or the lookup 404s otherwise), exactly as enforced generically in `BaseController#stacks` (`app/controllers/shipit/api/base_controller.rb:74-76`) and used by every other API controller's inherited `stack`/`stacks` calls (e.g. `DeploysController`, `TasksController`, etc., all of which rely on `stacks.from_param!`).

`Api::CCMenuController` breaks this by defining its own `stack` private method (`app/controllers/shipit/api/ccmenu_controller.rb:29-31`) that calls `Stack.from_param!(params[:stack_id])` directly against the `Stack` class, never touching `current_api_client.stack_id` at all. Because Ruby method resolution picks the subclass's `stack` over the inherited one, `#show` (line 22-25) always resolves `params[:stack_id]` against the full `Stack` table.

Attack: an operator issues a `ApiClient` scoped to `stack_id: A` with only `read:stack` permission (the intended "least privilege" CCMenu token pattern — e.g. for embedding a CI-status badge for one project). An attacker who somehow obtains this narrowly-scoped token (e.g. it's meant to be embedded in a public build-status widget, config file, or CI badge, which is a common CCMenu usage) can pass `stack_id=B` (any other stack) as a request parameter and read stack B's deploy/build status, defeating the whole purpose of the per-stack token scope. `require_permission :read, :stack` (line 6) only checks the client's *permissions list* contains `read:stack` — it does not check which stack, so it does not catch this.

### Impact Explanation
This allows unauthenticated-scope-wise read of any stack's build/deploy status/history metadata (name, activity, lastBuildStatus, lastBuildLabel, lastBuildTime, webUrl) using a token that was only meant to authorize reads for one specific stack. This matches the "High - escalation into authorization scope, unauthenticated (out-of-scope) read of stack state" category. It is fully repeatable against any stack ID on the instance, using a single valid CCMenu-token client credential, and works identically for every stack.

### Likelihood Explanation
Requires possession of any valid `ApiClient` token with `read:stack` permission scoped to a single stack — this is exactly the minimally-privileged, per-project token pattern the `stack_id` scoping feature exists to support (e.g. distributed for public CI-badge embedding). No GitHub credentials, no webhook signature, and no session are needed; only the API token and knowledge/guessing of another stack's `stack_id`/slug param. Cost is a single HTTP GET.

### Recommendation
Change `Api::CCMenuController#stack` to reuse the scoped lookup, e.g. remove the override entirely (relying on inherited `BaseController#stack`/`#stacks`) or redefine it as `@stack ||= stacks.from_param!(params[:stack_id])`.

### Proof of Concept
minitest test plan (in `test/controllers/api/ccmenu_controller_test.rb` style, using `ApiControllerTestCase`):
1. Create two stacks, `stack_a` and `stack_b`.
2. Create/authenticate an `ApiClient` with `permissions: ['read:stack']` and `stack_id: stack_a.id`.
3. `GET :show, params: { stack_id: stack_b.to_param }` on `Api::CCMenuController` → currently asserts `response :ok` and payload name == `stack_b.to_param` (proving out-of-scope read succeeds) — this should instead 404 to satisfy the binding.
4. Contrast with `Api::DeploysController#index` (or any controller using inherited `stack`) under the same scoped client and `stack_id: stack_b.to_param` → asserts `response :not_found`, demonstrating the invariant holds everywhere except `CCMenuController`.
