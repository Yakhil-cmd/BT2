### Title
Push-Payment DOS in `handleKLAYTransfer` Permanently Locks KAIA and Corrupts Bridge Nonce State — (`contracts/service_chain/bridge/BridgeTransferKLAY.sol`)

---

### Summary

`handleKLAYTransfer` in the Kaia service-chain bridge uses a push-payment pattern to deliver KAIA to the recipient address. If the recipient is a contract that reverts on receiving KAIA, the entire transaction reverts, the nonce is never marked as handled, `lowerHandleNonce` is permanently stuck, `recoveryBlockNumber` stops advancing, and the bridged KAIA is locked in the bridge contract forever. Any unprivileged user can trigger this by requesting a bridge transfer to a contract they control.

---

### Finding Description

In `contracts/service_chain/bridge/BridgeTransferKLAY.sol`, `handleKLAYTransfer` delivers KAIA to the recipient via a low-level call and hard-reverts if the call fails:

```solidity
(bool ok, ) = _to.call.value(_value)("");
require(ok, "handleKLAYTransfer: transfer failed");
``` [1](#0-0) 

Because this `require` comes **after** all state-writing steps — `_setHandledRequestTxHash`, `handleNoncesToBlockNums[_requestedNonce] = _requestedBlockNumber`, `_updateHandleNonce`, and the `HandleValueTransfer` event — a revert rolls back every one of those writes. [2](#0-1) 

The nonce-advancement logic in `_updateHandleNonce` advances `lowerHandleNonce` only when **consecutive** nonces starting from `lowerHandleNonce` have been recorded in `handleNoncesToBlockNums`:

```solidity
for (i = lowerHandleNonce; i <= limit && handleNoncesToBlockNums[i] > 0; i++) {
    recoveryBlockNumber = handleNoncesToBlockNums[i];
    ...
}
lowerHandleNonce = i;
``` [3](#0-2) 

Because nonce N's `handleNoncesToBlockNums[N]` is never written (the transaction always reverts), `lowerHandleNonce` is permanently stuck at N regardless of how many later nonces are handled. `recoveryBlockNumber` is also stuck at the block of the last successfully handled nonce before N.

The `_lowerHandleNonceCheck` only rejects nonces **below** `lowerHandleNonce`:

```solidity
require(lowerHandleNonce <= _requestedNonce, "removed vote");
``` [4](#0-3) 

So later nonces can still be processed, but the bridge's nonce accounting and recovery pointer are permanently corrupted.

There is no admin function to skip a nonce or force-advance `lowerHandleNonce`. The only path forward is to successfully handle nonce N, which is impossible when `_to` always reverts.

The off-chain recovery system (`vt_recovery.go`) reads `RecoveryBlockNumber` from the contract as its scan start point:

```go
hint.blockNumber, err = to.bridge.RecoveryBlockNumber(nil)
``` [5](#0-4) 

Since `recoveryBlockNumber` is stuck, the recovery goroutine will perpetually re-discover nonce N as a pending event and keep submitting failing `handleKLAYTransfer` transactions.

---

### Impact Explanation

- **KAIA permanently locked**: The KAIA deposited for nonce N is held in the bridge contract and can never be delivered or refunded. The user's funds are lost.
- **`lowerHandleNonce` permanently corrupted**: The bridge's canonical lower-bound nonce pointer is stuck, meaning `recoveryBlockNumber` never advances and the bridge's accounting of "what has been handled" is permanently wrong.
- **Recovery system infinite failure loop**: `vt_recovery.go` keeps re-submitting the failing handle transaction, wasting operator gas indefinitely.
- **No admin escape hatch**: There is no `skipNonce`, `cancelRequest`, or `forceAdvanceLowerNonce` function in any of the bridge contracts.

---

### Likelihood Explanation

Any user who can call `requestKLAYTransfer` (or send KAIA to the bridge's fallback) can specify an arbitrary `_to` address. Deploying a contract with a reverting `receive()` is trivial. The attacker spends only the gas for the request transaction on the source chain; the damage is inflicted on the destination bridge. No privileged access is required.

---

### Recommendation

Replace the push-payment pattern with a pull-payment (escrow) pattern: record the owed amount in a mapping and let the recipient withdraw it themselves. If push must be retained, catch the failure and store the amount in a claimable mapping rather than reverting:

```solidity
// Instead of:
(bool ok, ) = _to.call.value(_value)("");
require(ok, "handleKLAYTransfer: transfer failed");

// Use:
(bool ok, ) = _to.call.value(_value)("");
if (!ok) {
    pendingWithdrawals[_to] += _value;
    emit TransferFailed(_to, _value, _requestedNonce);
}
```

This ensures the nonce is always marked as handled and `lowerHandleNonce` always advances, while still allowing the recipient to recover their KAIA.

**Step 1 — Deploy a reverting receiver on the destination chain:**
```solidity

    receive() external payable { revert("reject"); }

```
