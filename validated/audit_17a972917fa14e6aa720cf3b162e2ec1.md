### Title
Cross-repository status forgery via unscoped `Commit.where(sha:)` in `StatusHandler#process` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` looks up commits by bare SHA across the entire `commits` table instead of scoping to the repository that authenticated the webhook, even though the base `Handler` class already exposes a `stacks` helper for exactly this purpose. Because git SHAs are content-addressed and not repository-scoped, a webhook validly signed for an attacker-owned/attacker-controlled repository can write a `status` (e.g. `context: security/scan`, `state: failure`) onto any other stack in the installation that happens to have a `Commit` row with the same SHA, including a production-environment stack that never authenticated it.

### Finding Description
The broken binding: the code implicitly assumes
`Commit.where(sha: params.sha).stack.repository == payload['repository']['full_name']`
but this equality is never enforced — `Commit.where(sha: params.sha)` is not filtered by repository or stack at all.

Code path:
- `Shipit::WebhooksController#create` parses the payload and dispatches to handlers for the `status` event [1](#0-0) .
- `verify_signature` only confirms that the payload was signed by the GitHub App/secret associated with `repository_owner` (`payload.dig('repository','owner','login')` or `organization.login`) [2](#0-1) [3](#0-2) . It proves *who signed*, not *which commit/repository the status applies to*.
- The base `Handler` class already provides a repository-scoped accessor, `stacks`, derived from `payload.dig('repository','full_name')` [4](#0-3) , but `StatusHandler#process` does not use it:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [5](#0-4) 
- `Commit#create_status_from_github!` writes the status unconditionally and then `add_status` recomputes `status`, potentially triggering `Hook.emit(:deployable_status, ...)` and `stack.schedule_merges` [6](#0-5) [7](#0-6) .
- `Commit#deployable?` and `#blocked?` depend on `status`/`blocking?`, which is driven by the newly-written status row [8](#0-7) .

Attacker's request: the attacker owns (or controls) a GitHub repository/org that is also onboarded to the same Shipit instance (or any repository whose owner is a valid GitHub App installation target), and can legitimately post commit statuses to their own repo via the GitHub API (this is normal, unprivileged repo-owner capability). If the attacker's repository shares a commit history root with a victim's production stack repository (e.g., attacker forks the victim's repo, or the victim's initial/shared commits are unmodified), a `Commit` row with an identical SHA exists in both the attacker's stack and the victim's production stack in Shipit's database (each stack syncs its own `Commit` rows from GitHub but the `sha` values collide when history is shared). The attacker sets `context: security/scan`, `state: failure` on that shared SHA in their own repository. GitHub sends a `status` webhook, correctly signed for the attacker's org/repo. `verify_signature` passes because the signature genuinely matches the attacker's own repository's webhook secret. `StatusHandler#process` then updates **every** `Commit` row across **all** stacks with that SHA — including the victim's production stack — flipping its `security/scan` status to `failure`.

Existing guards fail because: `verify_signature` authenticates the *sender org*, not the *commit/repository* referenced by `sha`; `drop_unhandled_event` and `ExplicitParameters` only validate payload shape (`sha`, `state`, `context`, etc.), not repository ownership; and the handler discards the `payload['repository']['full_name']` context that would have let it scope via `stacks`/`Repository.from_github_repo_name`.

### Impact Explanation
A payload authenticated for one repository can flip the required `security/scan` status of an unrelated production stack's commit to `failure`, directly forcing a block on deploys/merges (or, depending on how `security/scan` is wired into deploy gating/CD triggers, driving unwanted rollback/blocking behavior) for a stack that never authenticated that status. This is a cross-tenant "payload for one repository mutating another's stack/commit," matching the Critical impact category (unauthorized deploy/rollback/merge or a write against a repository that did not authenticate it). The attack is repeatable against any stack whose repository shares commit history (a very common situation for forks, template repos, or monorepo migrations) with an attacker-controlled repository, and can be re-sent for every shared SHA.

### Likelihood Explanation
Preconditions: the attacker needs (a) a GitHub repository that is legitimately webhook-connected to the same Shipit instance (as any onboarded repo/org), and (b) a commit SHA shared with the victim's production stack (achievable by forking the victim repo, or exploiting shared ancestor commits from a common template). Setting a commit status on their own repository via GitHub's API is trivial and requires no special privilege beyond owning that repo. No Shipit secrets, sessions, or API tokens are needed. This is feasible and repeatable, though it depends on the specific data condition of a shared SHA existing between attacker and victim stacks, which is a common real-world occurrence (forks, cherry-picks, shared history).

### Recommendation
Scope `StatusHandler#process` by the repository that authenticated the webhook, using the same `stacks`/`Repository.from_github_repo_name(repository_name)` mechanism already present in `Handler`, e.g.:
```ruby
def process
  stacks.flat_map(&:commits).select { |c| c.sha == params.sha }.each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
or equivalently join through `Stack`/`Repository` so only commits belonging to stacks whose repository matches `payload['repository']['full_name']` are updated.

### Proof of Concept
minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb`, hypothetical since none currently exists):
1. Create `repository_a` (attacker-owned, e.g. `attacker/forked-repo`) and `repository_b` (victim, production environment, e.g. `victim/prod-repo`), each with its own `Stack`.
2. Create `Commit.create!(stack: stack_b, sha: "deadbeef" * 5 truncated appropriately)` for the victim's production stack, and a second `Commit` with the **same sha** for the attacker's stack (`stack: stack_a`), simulating shared history.
3. Assert baseline: `commit_b.reload.status.state != 'failure'` and `commit_b.deployable?` reflects pre-attack state (e.g. `true` if otherwise green).
4. Build a `status` payload with `repository: { full_name: 'attacker/forked-repo', owner: { login: 'attacker' } }`, `sha:` the shared SHA, `context: 'security/scan'`, `state: 'failure'`.
5. Call `Shipit::Webhooks::Handlers::StatusHandler.call(payload)` directly (bypassing signature verification, which is legitimately satisfiable by the attacker for their own repo).
6. Assert the victim's `commit_b.reload.status.state == 'failure'` and `commit_b.deployable? == false` (or `blocked?`) — proving the attacker's own-repo webhook mutated the victim's production stack's commit state, violating "a `security/scan` status affects only the repository that authenticated it."

    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
