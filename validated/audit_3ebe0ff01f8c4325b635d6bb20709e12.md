### Title
Webhook signature verification selects the signing organization from an unsigned trust boundary, letting one onboarded organization forge events for another organization's tracked repository - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
This mirrors the `getPositionValue()` bug class: a value (there, the position's fee-adjusted value; here, the *organization* whose secret is used to validate a request) is computed/selected from data that is not actually bound by the security check that is supposed to cover it. `WebhooksController#verify_signature` picks the GitHub App/secret to validate with based on `repository.owner.login` taken from the still‑unverified request body, then validates the *entire* raw body against that secret [1](#0-0) [2](#0-1) . `GitHubApp#verify_webhook_signature` only proves that the byte sequence was produced by whoever holds the secret configured for that organization name [3](#0-2) . It never asserts that the `repository.full_name` field the handlers later act on actually belongs to that same authenticated organization [4](#0-3) [5](#0-4) .

### Finding Description
Shipit supports multi-organization GitHub App configuration, each with its own `webhook_secret` [6](#0-5) . The binding that should hold is:

`organization whose secret validated the signature == organization that owns the repository the handlers act on`

`verify_signature` derives the verifying organization from `params.dig('repository', 'owner', 'login')` — a field inside the same JSON body that the signature is computed over, but which is read *before* any cryptographic check occurs [2](#0-1) . The HMAC in `verify_webhook_signature` only proves internal consistency of the raw body with *that organization's* secret [3](#0-2) ; it does not prove that `repository.full_name` (the field every handler actually keys off of to select which `Stack`/`Repository` to mutate) refers to a repository owned by that same organization.

Downstream, every handler (`Handler#repository_name`, `PushHandler`, status/pull_request handlers, etc.) resolves the target purely from `repository.full_name` via `Repository.from_github_repo_name` [7](#0-6) [5](#0-4) [8](#0-7) , with no re-check against the organization that was actually authenticated. An operator that legitimately onboarded their own organization (and therefore legitimately knows/controls their own `webhook_secret`) can produce a validly signed payload where `repository.owner.login` is their own org (so it passes `verify_signature`) while `repository.full_name` names a *different* tracked organization's repository. Handlers will then act on that other organization's stack — e.g. enqueueing `GithubSyncJob`, or creating a `Status` for an arbitrary commit sha in that repository's history — using only the attacker's own, unrelated webhook credentials.

### Impact Explanation
This is a confused-deputy across the organizational trust boundary that Shipit's multi-org webhook config is meant to enforce: possession of one organization's webhook secret becomes sufficient to inject state-changing GitHub events (pushes, commit statuses, pull-request events) against a completely different organization's tracked repositories/stacks. Because deploy pipelines (and merge/lock logic) in Shipit react to commit statuses and push events, this can be leveraged to spoof CI/status signals or trigger syncs on stacks the attacker's organization has no legitimate authority over, escalating beyond the attacker's own authorized scope — consistent with the "escalation into authorization" impact bucket.

### Likelihood Explanation
Medium: it requires the attacker to control (own) at least one organization that is legitimately onboarded onto the shared Shipit instance with its own `webhook_secret` — a realistic scenario for any Shipit deployment that hosts multiple organizations/teams behind one instance, as the multi-org config in `lib/shipit.rb` (`github_app_config`, `TOP_LEVEL_GH_KEYS`) is explicitly designed to support [9](#0-8) .

### Recommendation
After `verify_signature` succeeds, re-derive the target repository/organization strictly from the *verified* organization context (the one whose secret matched), and reject or ignore any handler processing where `repository.full_name`'s owner segment does not match the organization whose secret validated the signature. Do not let handlers trust `repository.full_name` in isolation from the verified organization.

### Proof of Concept
1. Attacker legitimately administers `attacker-org`, onboarded on the shared Shipit instance with a known `webhook_secret_A`.
2. Attacker crafts a webhook JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<victim-sha>",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" }
}
```
3. Attacker computes `X-Hub-Signature` with `webhook_secret_A` over this exact body (a secret they legitimately possess) and POSTs to `/webhooks` with `X-Github-Event: push`.
4. `verify_signature` resolves `repository_owner` = `"attacker-org"`, fetches `attacker-org`'s `GitHubApp`, and validates successfully since the signature does match that secret [10](#0-9) .
5. `PushHandler` resolves stacks via `repository.full_name = "victim-org/victim-repo"` [8](#0-7) , and `Repository.from_github_repo_name` looks it up with no cross-check against `attacker-org` [5](#0-4) , enqueuing a `GithubSyncJob`/state change on the victim's stack using only the attacker's own credentials.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
