Cross-repository status forgery via unscoped `Commit.where(sha:)` lookup in `StatusHandler#process` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits to attach a GitHub `status` payload by bare SHA only, with no repository or stack scoping, unlike sibling handlers (`PushHandler`, `CheckSuiteHandler`) which always scope through `stacks` derived from the payload's `repository.full_name`. Because the `commits` table's uniqueness constraint is `(sha, stack_id)` rather than `sha` alone, the same commit SHA can legitimately exist in multiple, unrelated stacks (e.g. a victim's stack and an attacker's stack sharing history via a fork), and a webhook authenticated for the attacker's own repository will still write a `Status` record onto the victim's commit.

### Finding Description
The broken binding is: **a `status` webhook authenticated for repository R must only mutate commits belonging to stacks of repository R** — i.e. `commit.stack.repository == verified_repository` should hold for every commit mutated by the handler. `StatusHandler#process` breaks this:

```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [1](#0-0) 

Contrast with `PushHandler`, which scopes through `stacks` (derived from `Repository.from_github_repo_name(repository_name)`): [2](#0-1) 
and `CheckSuiteHandler`, which likewise filters `stacks.where(branch: ...)` before touching commits: [3](#0-2) 
Both rely on the base `Handler#stacks` helper, which resolves the repository from the payload before touching any records: [4](#0-3) 

`StatusHandler` never calls `stacks`/`repository_name` — it queries the global `Commit` table by `sha` alone, matching every commit row across every stack that has that SHA. The `commits` table's unique index is on `(sha, stack_id)`, not `sha` alone, confirming the schema explicitly anticipates the same SHA existing in multiple stacks: [5](#0-4) 

`Commit#create_status_from_github!` then unconditionally creates a `Status` on whatever commit(s) matched and re-evaluates deployability/blocking: [6](#0-5) [7](#0-6) 

**Attacker's exact request:** The attacker owns/administers a GitHub repository (`attacker/repo`) that has the Shipit GitHub App/webhook installed and thus receives a genuinely GitHub-signed webhook (`verify_signature` validates the signature using `Shipit.github(organization: repository_owner)`, keyed to the *attacker's own* organization — a check that legitimately passes because it's the attacker's own repo emitting the event): [8](#0-7) 
The attacker forks (or otherwise shares unmodified commit history with) the victim's repository so that a specific commit SHA is identical in both `attacker/repo` and `victim/repo`. The attacker then creates a GitHub commit status (`context: ci/circleci`, `state: failure`) on that shared SHA in their own repository — something fully within their control since they own that repo — which GitHub relays as a `status` webhook to Shipit, signed for `attacker`'s organization.

**Exploit flow:** `WebhooksController#verify_signature` passes (real signature, real org). `StatusHandler#process` runs `Commit.where(sha: shared_sha)`, which returns **both** the attacker's own commit row and the victim's commit row (because they share the SHA and are stored as separate `Commit` records keyed by `(sha, stack_id)`). `create_status_from_github!` is called on both, writing a `failure` status for `ci/circleci` onto the victim's commit too. If the victim stack requires `ci/circleci` as a blocking/required context, this can flip `deployable?`/`blocked?` for the victim's stack and trigger `stack.schedule_merges` or block state changes via `add_status`.

**Why existing guards fail:** `verify_signature` only proves the payload came from GitHub for the org identified in the payload's own `repository.owner.login` — it says nothing about which `Commit` rows the payload is permitted to mutate. `drop_unhandled_event`, `ExplicitParameters` schema validation, and model-level validators (`Repository` format, `Stack` environment) are all satisfied because the payload is well-formed and genuinely signed; none of them enforce repository-to-commit ownership. This is precisely the check that `PushHandler`/`CheckSuiteHandler` perform via `stacks` and that `StatusHandler` omits.

### Impact Explanation
Any attacker who owns a GitHub repository that shares commit history (via fork or otherwise) with a Shipit-tracked victim repository can write arbitrary `Status` rows (state/context/target_url/description) onto the victim's commits without any relationship to the victim's Shipit configuration, GitHub org, or webhook secret. Since `Status` state feeds directly into `Commit#deployable?`, `blocked?`, and `stack.schedule_merges`, this can force a required context to `failure` (blocking deploys/merges of legitimate, passing commits) or conversely satisfy a required context with a spoofed `success` (bypassing CI gating and enabling an unauthorized deploy/merge). This is a payload from one repository mutating another repository's commit/stack state — matching the Critical category "a payload for one repository mutating another's stack, commit, task or team."

### Likelihood Explanation
Preconditions: the attacker must control a repository whose GitHub App/webhook delivers signed events to the same Shipit instance (i.e. the org/app is already configured on Shipit for that organization — a realistic scenario for any organization-wide GitHub App install, or if Shipit is multi-tenant across orgs), and a commit SHA must be shared between the attacker's and victim's repositories (trivially achievable by forking the victim repo before it diverges, or by both repos containing a common upstream commit). No Shipit session, API token, or GitHub secret is needed — the attacker uses their own legitimately-signed webhook. This is fully repeatable against any shared SHA the attacker can identify, at zero cost per request.

### Recommendation
Scope `StatusHandler#process` by repository, mirroring `PushHandler`/`CheckSuiteHandler`: resolve `stacks` from `repository_name`/`Repository.from_github_repo_name`, and restrict the commit lookup to `stack.commits.where(sha: params.sha)` for each stack belonging to the verified repository, rather than querying the global `Commit` table by bare SHA.

### Proof of Concept
Minitest plan (no live GitHub, matching existing test conventions in `test/controllers/webhooks_controller_test.rb`):
1. Create `victim_stack` with `repository.full_name = "victim/repo"`, `required_statuses = ["ci/circleci"]`, and a `Commit` with `sha: SHARED_SHA` and a prior successful status, i.e. `commit.deployable?` == `true`.
2. Create `attacker_stack` with `repository.full_name = "attacker/repo"`, and a `Commit` with the same `sha: SHARED_SHA` (allowed since uniqueness is `(sha, stack_id)`).
3. Assert precondition equality: `victim_commit.deployable? == true` and `victim_commit.status.state == "success"`.
4. Stub `GithubHook#verify_signature` (or `Shipit.github(organization: "attacker").verify_webhook_signature`) to return `true`, simulating a genuinely-signed webhook from `attacker/repo`.
5. POST to `/webhooks` with `X-Github-Event: status`, body `{ sha: SHARED_SHA, state: "failure", context: "ci/circleci", repository: { full_name: "attacker/repo", owner: { login: "attacker" } } }`.
6. Assert the broken binding: `victim_commit.reload.statuses.last.state == "failure"` and `victim_commit.deployable? == false` (or `blocked? == true`), even though the webhook only authenticated `attacker/repo` and `victim_commit.stack.repository.full_name != "attacker/repo"`.
7. This demonstrates the equality `commit.stack.repository == verified_repository` is violated: the victim commit was mutated by a payload verified only for the attacker's repository.
