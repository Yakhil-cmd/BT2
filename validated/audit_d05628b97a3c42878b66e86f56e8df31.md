### Title
`StatusHandler#process` writes GitHub status data to commits across all stacks sharing a SHA, independent of which repository authenticated the webhook - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` resolves target commits with `Commit.where(sha: params.sha)`, a global lookup with no `stack_id`/`repository_id` scoping. [1](#0-0)  Any commit row in any stack that happens to share that exact SHA (e.g. a fork/mirror sharing git history with the upstream repo that a victim stack tracks) receives the attacker-originated status, regardless of which repository's webhook actually delivered the event.

### Finding Description
The claimed invariant is: `status.repository == webhook.authenticated_repository` for every `Status` record created from a `status` webhook. The code breaks this: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` matches commits by bare SHA across the entire `commits` table, with no join or filter on `repository`/`stack`. [1](#0-0)  `create_status_from_github!` then calls `statuses.replicate_from_github!(stack_id, github_status)`, which does scope the created `Status` to `commit.stack_id` [2](#0-1) [3](#0-2)  - but `commit.stack_id` here is whatever stack that matching `Commit` row belongs to, which can be the victim's stack, not the stack that owns the webhook that authenticated the request.

Exploit path: an attacker registers/controls a repository that shares git history with the repository backing a victim stack (a fork of the tracked upstream, or any repo containing the same commit objects). Git commit SHAs are content-addressed, so identical commits (e.g. commits merged upstream and present verbatim in the fork) carry the same SHA in both repositories. If the attacker's repository has its own legitimately-configured Shipit webhook (created because the attacker registered a stack for their own fork, or the app/webhook secret is shared across installations), they can cause GitHub to emit a `status` event for that SHA (e.g. via the GitHub Status API against their own repo) with an attacker-chosen `context`/`state`, and Shipit will accept and process it. `StatusHandler` then applies that status to the `Commit` row of the *victim* stack because the lookup is by bare SHA only.

Once a status/state lands on the victim's commit, `Commit#deployable?` evaluates `!locked? && (stack.ignore_ci? || (success? && !blocked?))`. [4](#0-3)  Note: when `stack.ignore_ci?` is `true`, `deployable?` already bypasses CI entirely and would be `true` even without any injected status - so the "review/approved" context contributes nothing extra in that specific configuration. The real amplification is for stacks that are **not** `ignore_ci` and rely on `blocking_statuses`/`required_statuses`/`status` content to gate `deployable?` and merges (`Stack#allows_merges?`, `Stack#merge_status`, `Commit#blocked?`) [5](#0-4) [6](#0-5)  - there, an attacker-forged status for a shared SHA can flip those gates for the victim stack.

Existing guards do not prevent this: webhook signature verification (`GithubApp#verify_webhook_signature`) proves the payload came from GitHub for *some* installed repository, but does not bind the resulting DB write to that repository; `ExplicitParameters` only validates the shape of `sha`/`state`/`context`, not repository scope; there is no `repository_id`/`stack_id` filter anywhere in `StatusHandler#process`.

### Impact Explanation
A payload delivered for one repository's webhook mutates another stack's `Commit`/`Status` records - matching the Critical category "a payload for one repository mutating another's stack, commit, task." This can flip `blocked?`/`deployable?`/merge-gating for a victim stack that does not use `ignore_ci`, potentially causing an unauthorized deploy or blocking a legitimate one, repeatable for any SHA the attacker's repository shares with the victim's tracked history (most reliably against forks of open-source projects tracked by Shipit).

### Likelihood Explanation
Requires: (1) the victim stack's tracked repository has commits shared (identical SHA) with a repository the attacker controls (trivial for forks of the upstream repo), and (2) the attacker's repository has a working Shipit-recognized webhook delivering `status` events (requires the attacker being able to register a stack/webhook for their own fork, or the installation-wide webhook validation accepting events from any installed repo). Given those preconditions, the exploit is cheap and repeatable - one GitHub status API call per attempt. The specific "review/approved + ignore_ci" framing in the question overstates the ignore_ci angle (ignore_ci already bypasses CI regardless of status), but the underlying unscoped-lookup bug is real and independently exploitable against non-`ignore_ci` stacks via `blocking_statuses`/`required_statuses`.

### Recommendation
Scope the commit lookup in `StatusHandler#process` by the webhook's authenticated repository, e.g. join through `Stack`/`Repository` (`Commit.joins(:stack).merge(Stack.where(repository: repository_from_webhook)).where(sha: params.sha)`), so a status can only ever be applied to commits belonging to stacks whose repository matches the one that authenticated the webhook delivery.

### Proof of Concept
minitest (`test/models/shipit/webhooks/handlers/status_handler_test.rb`, `test/models/commits_test.rb`):
1. Create two repositories, `repo_a` (victim, `ignore_ci: false`, `required_statuses: ['ci/build']`, `blocking_statuses: ['ci/build']`) and `repo_b` (attacker-controlled), each with its own `Stack`.
2. Create a `Commit` with `sha: "aaaa...aaaa"` under `repo_a`'s stack (simulating shared git history from a fork) AND a `Commit` with the same `sha` under `repo_b`'s stack.
3. Assert precondition: `repo_a_commit.deployable?` is `false` (no successful `ci/build` status yet) - `assert_equal false, repo_a_commit.reload.deployable?`.
4. Invoke `StatusHandler.new(params: { sha: "aaaa...aaaa", state: "success", context: "ci/build" }, delivery: repo_b_delivery).process` (as would be dispatched from a webhook authenticated for `repo_b`).
5. Assert the victim's commit was mutated despite the webhook belonging to `repo_b`: `assert_equal true, repo_a_commit.reload.deployable?` and `assert repo_a_commit.statuses.exists?(context: "ci/build", state: "success")`.
6. This demonstrates `status.repository == webhook.authenticated_repository` (expected) vs. actual (`repo_a`'s commit updated by `repo_b`'s webhook) diverge, confirming the cross-tenant write.
