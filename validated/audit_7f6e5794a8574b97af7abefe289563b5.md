### Title
Reachable assertion in `validateAndSaveUnit` crashes full nodes when a composed AA-response unit fails an "impossible" validation branch - ([File: aa_composer.js])

### Summary
`aa_composer.js`'s `validateAndSaveUnit()` re-validates every AA-composed response unit through `validation.validate()`, but treats several of the validation callback outcomes as invariants that can never happen and reacts to them with an unconditional `throw Error(...)` instead of a graceful bounce/error path. This mirrors the TensorFlow bug class: an internal step is *assumed* to always succeed (there, `SpecializeType` is only checked with a no-op `DCHECK`; here, the composed unit is assumed to always validate as `ifOk` with `sequence==='good'`), and when that assumption is violated the code crashes instead of failing safely.

### Finding Description
`handleTrigger()` composes a response unit for an AA trigger and hands it to `validateAndSaveUnit()`: [1](#0-0) 

Here, `ifJointError`, `ifTransientError`, `ifNeedHashTree`, `ifNeedParentUnits`, and `ifOkUnsigned` are all treated as "should never happen" and immediately `throw Error(...)`. The `ifOk` branch additionally throws if `objAAValidationState.sequence !== 'good'` (i.e., the composed unit is judged non-serial, e.g. because it double-spends an output that was already consumed by a concurrently processed unit/trigger at the same MCI). These throws occur deep inside nested asynchronous callbacks (`updateInitialAABalances` → `evaluateAA` → `sendUnit` → `pickParents` → `completePaymentPayload` → `validateAndSaveUnit`), none of which are wrapped in a `try/catch` at any call site I could locate, so a thrown `Error` here becomes an uncaught exception rather than a value that is propagated through the `cb`/`bounce` error-handling machinery already built into `handleTrigger` (compare with the many `bounce(err)` calls used for ordinary validation failures, e.g. `aa_composer.js:1866-1867`).

This is structurally identical to the TensorFlow pattern in the report: a step whose failure is only guarded by an assumption (`DCHECK`, here "this will always be `ifOk`/`sequence==='good'`") is followed unconditionally by code that behaves fatally if the assumption doesn't hold (`ValueOrDie()`, here `throw Error(...)`).

### Impact Explanation
AA response-unit composition and validation via `handleTrigger`/`validateAndSaveUnit` run deterministically on **every full node** that processes a given AA trigger unit (this is not a single operator or hub-only code path; it executes wherever `aa_composer.handleTrigger` is invoked for a stabilizing trigger). If an attacker can craft a trigger (or a pair of triggers/state interactions) that causes the composed AA response unit to hit `ifJointError`, `ifTransientError`, or the non-serial (`sequence !== 'good'`) branch of `ifOk` — for example via a double-spend race on AA-consumed outputs across concurrently processed triggers — the resulting uncaught exception crashes the Node.js process on every full node executing that AA. Because this fires deterministically for all nodes processing the same trigger, it can halt further stabilization/confirmation of units depending on that AA, i.e., "a network unable to confirm new units" for the affected chain of activity, until node operators patch or filter the offending unit.

### Likelihood Explanation
Reaching these branches requires the attacker to be an ordinary, unprivileged AA trigger sender — no special node/peer/hub access is needed, matching an in-scope actor (AA trigger sender). Constructing a concrete trigger/state combination that forces `sequence !== 'good'` on the composed response (e.g., via a race between two AA triggers spending overlapping AA-owned outputs within the same batch) is a non-trivial but plausible engineering exercise given the complexity of the composer's input/output selection logic; the exact reproduction steps could not be fully confirmed without executing the full aa_composer/validation state machine, which was outside the scope of static code review here.

### Recommendation
Replace the unconditional `throw Error(...)` calls in `validateAndSaveUnit`'s `ifJointError`, `ifTransientError`, `ifNeedHashTree`, `ifNeedParentUnits`, `ifOkUnsigned`, and non-serial `ifOk` branches with calls into the existing `bounce()`/`revert()` error paths already used elsewhere in `handleTrigger`, so that an unexpected validation outcome results in a bounced/reverted AA response instead of a process crash. Additionally, wrap the top-level entry points that drive `handleTrigger` in a `try/catch` (or a `process.on('uncaughtException')`-safe boundary) so that any residual unexpected exception degrades to a handled unit-processing failure rather than terminating the node.

	function validateAndSaveUnit(objUnit, cb) {
		var objJoint = { unit: objUnit, aa: true, aa_mci: mci };
		validation.validate(objJoint, {
			ifJointError: function (err) {
				throw Error("AA validation joint error: " + err);
			},
			ifUnitError: function (err) {
				console.log("AA validation unit error: " + err);
				return cb(err);
			},
			ifTransientError: function (err) {
				throw Error("AA validation transient error: " + err);
			},
			ifNeedHashTree: function () {
				throw Error("AA validation unexpected need hash tree");
			},
			ifNeedParentUnits: function (arrMissingUnits) {
				throw Error("AA validation unexpected dependencies: " + arrMissingUnits.join(", "));
			},
			ifOkUnsigned: function () {
				throw Error("AA validation returned ok unsigned");
			},
			ifOk: function (objAAValidationState, validation_unlock) {
				if (objAAValidationState.sequence !== 'good')
					throw Error("nonserial AA");
				validation_unlock();
				objAAValidationState.bUnderWriteLock = true;
				objAAValidationState.conn = conn;
				objAAValidationState.batch = batch;
				objAAValidationState.initial_trigger_mci = mci;
				objAAValidationState.bDryRun = trigger_opts.bDryRun;
				writer.saveJoint(objJoint, objAAValidationState, null, function(err){
					if (err)
						throw Error('AA writer returned error: ' + err);
					cb();
				});
			}
		}, conn);
	}
