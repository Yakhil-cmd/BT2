### Title
Stale `signer-rewards-per-token-for-cycle` snapshot when staked shares are zero lets a staker's reward baseline be set too low, allowing over-payment of sBTC staker rewards - (File: `stackslib/src/chainstate/stacks/boot/pox-5.clar`)

### Summary
`pox-5.clar`'s reward-accounting functions contain the exact "skip the update because the gating value is zero" pattern described in the external report. In `settle-rewards`, the per-staker distribution accumulator `signer-rewards-per-token-for-cycle` is only refreshed to the current `rewards-per-token-for-cycle` value **if the signer's current STX-only staked shares are non-zero**; when shares are zero the accumulator is left stale instead of being caught up. [1](#0-0) 

### Finding Description
`settle-rewards` computes `rewards-per-token` from `get-rewards-per-token-for-cycle` (a global, signer-independent accumulator) and only writes it into `signer-rewards-per-token-for-cycle` when `shares > 0`:
```
(if (> shares u0)
    (map-set signer-rewards-per-token-for-cycle {...} rewards-per-token)
    true)
``` [2](#0-1) 

This `signer-rewards-per-token-for-cycle` value is the `rpt-current` term used to compute every staker's earned reward for that signer:
```
(compute-earned-rewards
    (get-staker-shares-staked-for-cycle staker reward-cycle bond-index signer)
    (get-signer-rewards-per-token-for-cycle signer reward-cycle bond-index)
    (get-staker-rewards-per-token-settled-for-cycle signer reward-cycle bond-index staker)
    ...)
``` [3](#0-2) 

When a new staker joins a signer for a cycle, `add-staker-to-signer-for-cycle` first calls `settle-rewards` (using the *pre-join* shares, which can be `0` for the first staker of the cycle), then unconditionally snapshots the staker's baseline from whatever `signer-rewards-per-token-for-cycle` currently holds:
```
(settle-rewards signer cycle none)
...
(map-set staker-rewards-per-token-settled-for-cycle {...}
    (get-signer-rewards-per-token-for-cycle signer cycle none))
``` [4](#0-3) [5](#0-4) 

Note the code explicitly reasons about and neutralizes the *symmetric* skip for `settle-staker-rewards` (`if (> prev-staker-shares u0) ... else {earned: u0, rewards-per-token: u0}`), with a comment stating it is a safe no-op because the caller unconditionally re-writes the staker's settled snapshot afterward. [6](#0-5) 

No equivalent correction exists for the `signer`-level accumulator: if `shares == 0` at the moment `settle-rewards` runs (i.e., the signer currently has no STX-only stakers for that cycle), `signer-rewards-per-token-for-cycle` is left at its old, lower value instead of being caught up to `rewards-per-token-for-cycle`. The very next line snapshots the newly-joining staker's baseline from that stale, too-low value. When a subsequent call to `settle-rewards` (triggered by any later staker action, once `shares > 0`) finally jumps `signer-rewards-per-token-for-cycle` up to the current, higher `rewards-per-token-for-cycle`, `compute-earned-rewards` will attribute the entire `rpt-current - rpt-paid` gap to the first staker's shares — including the portion of the gap that accrued **before** that staker's stake actually existed.

### Impact Explanation
This lets a staker's earned-reward baseline be recorded lower than the true value at the moment they joined, so `compute-earned-rewards`'s `shares * (rpt-current - rpt-paid)` later credits them sBTC rewards for a period during which they had no shares staked. This is a reward paid that was not earned, funded out of the shared sBTC reward pool at the expense of other stakers/signers — matching the "sBTC rewards paid that were not earned or counted twice" analog class, an unbacked-minting/double-counting-of-reward condition (Critical/High per the rubric).

### Likelihood Explanation
The trigger condition — a signer having zero STX-only staked shares for a given reward cycle at the moment `settle-rewards` executes, followed later by staking activity and further reward inflow before another `settle-rewards`/`add-staker-to-signer-for-cycle` call — is an ordinary condition reachable at the start of any reward cycle for a signer with no (or fully-unstaked) STX-only stakers, requiring no privileged role and no manipulation beyond normal `stake`/`register-for-bond`/reward-crediting flows.

### Recommendation
Remove the `(if (> shares u0) ...)` gate in `settle-rewards` and unconditionally write `signer-rewards-per-token-for-cycle` to the freshly computed `rewards-per-token`, mirroring how `staker-rewards-per-token-settled-for-cycle` is always refreshed regardless of `prev-staker-shares`, so the per-staker distribution accumulator can never lag behind the global reward accumulator.

### Proof of Concept
Conceptual sequence within `pox-5.clar`:
1. Cycle `C` begins for signer `S` with zero STX-only staked shares (`get-signer-shares-staked-for-cycle S C none == 0`). sBTC rewards accrue into `get-rewards-per-token-for-cycle C none`, raising it to `RPT1`.
2. Some other action forces `settle-rewards S C none` to run while shares are still `0` — the `(> shares u0)` branch is skipped, so `signer-rewards-per-token-for-cycle` stays at its old value `RPT0 < RPT1`.
3. Staker `A` calls a staking entrypoint that routes through `add-staker-to-signer-for-cycle`. `settle-rewards` runs again with pre-join shares still `0`; `staker-rewards-per-token-settled-for-cycle[A]` is set to the stale `RPT0` (line 1773-1781), even though the true current rate is `RPT1`.
4. More sBTC rewards arrive, and another `settle-rewards S C none` call (now with `shares > 0`) jumps `signer-rewards-per-token-for-cycle` from `RPT0` straight to the new current value `RPT2 (>= RPT1)`.
5. `A` calls `claim-rewards` / `get-earned-staker-rewards`: `earned = shares_A * (RPT2 - RPT0) / PRECISION`, which includes the `RPT1 - RPT0` portion that accrued before `A` ever staked — rewards `A` did not earn, paid out of the shared sBTC pool.

Because I could not fully trace the exact global-formula definition of `get-rewards-per-token-for-cycle` (index budget exhausted before reaching it), I was unable to empirically confirm the precise numeric magnitude of `RPT1 - RPT0` in a running scenario; the structural flaw (asymmetric, uncorrected zero-gated skip of `signer-rewards-per-token-for-cycle`) is confirmed directly from the cited source lines.

(define-private (settle-rewards
        (signer principal)
        (reward-cycle uint)
        (bond-index (optional uint))
    )
    (let (
            (shares (get-signer-shares-staked-for-cycle signer reward-cycle bond-index))
            (rewards-per-token (get-rewards-per-token-for-cycle reward-cycle bond-index))
            (earned (compute-earned-rewards
                shares
                rewards-per-token
                (get-signer-rewards-per-token-settled-for-cycle signer reward-cycle bond-index)
                (get-signer-unclaimed-rewards-for-cycle signer reward-cycle bond-index)
            ))
        )
        (map-set signer-unclaimed-rewards-for-cycle {
            reward-cycle: reward-cycle,
            bond-index: bond-index,
            signer: signer,
        }
            earned
        )
        (map-set signer-rewards-per-token-settled-for-cycle {
            reward-cycle: reward-cycle,
            bond-index: bond-index,
            signer: signer,
        }
            rewards-per-token
        )
        (if (> shares u0)
            (map-set signer-rewards-per-token-for-cycle {
                signer: signer,
                reward-cycle: reward-cycle,
                bond-index: bond-index,
            }
                rewards-per-token
            )
            true
        )
