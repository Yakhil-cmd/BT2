### Title
Reused Bitcoin L1 lockup outpoint can be credited to multiple bond registrations, double-counting `sats-total` reward shares - (File: stackslib/src/chainstate/stacks/boot/pox-5.clar)

### Summary
`register-for-bond` in `pox-5.clar` lets a staker back their protocol-bond membership with an L1 Bitcoin timelock output instead of custodying sBTC. The function verifies that the referenced Bitcoin output really is a valid, correctly-scripted lockup via `verify-l1-lockups`/`validate-l1-lockup`, and it does reject duplicate outpoints *within a single call* using a locally-scoped `seen-outpoints` accumulator. However, that de-duplication list is never persisted; nothing in the contract records which `(txid, output-index)` outpoints have already been credited across *different* calls (by the same staker or different stakers). The same on-chain BTC lockup transaction can therefore be submitted again in a later, independent `register-for-bond` call and be accepted a second time.

### Finding Description
`verify-l1-lockups` initializes `seen-outpoints: (list)` fresh on every invocation: [1](#0-0) 

`validate-l1-lockup` only checks `(index-of? seen-outpoints outpoint)` against that fold-local list, and the check is scoped entirely to the outputs supplied in the *current* call: [2](#0-1) 

There is no map such as `used-l1-outpoints` (or similar) that records previously-consumed outpoints persistently, unlike `protocol-bond-memberships` / `protocol-bond-allowances`, which are checked elsewhere. Because `construct-lockup-output-script` binds the output's script to `staker` (i.e., `tx-sender`), an attacker cannot claim *someone else's* differently-scripted lockup, but nothing stops:
- The *same* staker from calling `register-for-bond` (or a later `update-bond-registration`/rollover path that revalidates lockups) a second time with the identical Bitcoin transaction/output, crediting `sats-total` again even though no new BTC was locked.
- Multiple bond periods (e.g., bond-index 0 and bond-index 6, both allow-listing the same staker for the same lockup script) each independently accepting the same BTC outpoint as backing, since `get-bond-l1-unlock-height`/`minimum-unlock-height` differs per bond but the outpoint itself is never marked "consumed."

Each successful `register-for-bond` writes the computed `sats-total` into `protocol-bond-memberships` and adds it into `protocol-bonds-total-staked`: [3](#0-2) 

and into the per-cycle share maps via `add-staker-to-bond-cycles` / `add-staker-to-signer-cycles`, which directly drive proportional sBTC reward distribution in `calculate-rewards`. Because the same physical BTC lock can back more than one bond-share credit, the equality "total protocol-bond sats-total credited == total sats actually time-locked on Bitcoin for pox-5" can be broken: credited shares exceed real backing.

### Impact Explanation
Reward payouts (`calculate-rewards`, `claim-staker-rewards-for-signer`) are distributed in proportion to `sats-total` recorded per bond/staker. If the same L1 outpoint is credited into more than one bond membership, the staker (or colluding stakers using the same lockup) receives reward shares that are not backed 1:1 by actual locked Bitcoin — this is a double-counting of a commitment that inflates one party's claim on the sBTC reward pool at the expense of other honest stakers/the reserve, matching the Critical impact category "double-counting a commitment or reward" / "unbacked minting of ... sBTC rewards."

### Likelihood Explanation
The action is fully triggerable by any unprivileged allow-listed staker; it requires only re-submitting a previously used, still on-chain, valid Bitcoin lockup output as the `btc-lockup` argument to another `register-for-bond` call (e.g., for a different `bond-index` the staker/signer is also allow-listed for, or after being removed and re-added to an allowlist). No admin action, miner cooperation, or cryptographic break is needed — only that no code path currently marks the outpoint as globally consumed. However, exploitation also depends on the staker being allow-listed for a second bond concurrently and on `roll-sbtc`/membership-clearing logic not incidentally preventing the reuse in practice, which I could not fully verify without tracing every `update-bond-registration` and rollover branch; this introduces some uncertainty about whether all double-credit paths are reachable end-to-end versus caught by an unseen guard.

### Recommendation
Persist consumed L1 outpoints in a durable map (e.g., `(define-map used-l1-outpoints {txid: (buff 32), output-index: uint} bool)`), and have `validate-l1-lockup` `map-insert` each outpoint (asserting `ERR_DUPLICATE_LOCKUP_OUTPOINT` on failure) instead of only checking the ephemeral, call-scoped `seen-outpoints` list. Consider also tracking outpoint consumption per-staker vs. globally depending on intended semantics (whether the same lockup may ever back more than one bond membership simultaneously).

### Proof of Concept
Not independently executable from the indexed context (no test harness reproduction was run); the following steps describe the reachable path based on the code above:
1. Bond admin sets up bond 0 and bond 6, both allow-listing staker A for the same `maxSats`.
2. Staker A calls `register-for-bond(bond-index=0, ..., btc-lockup=ok([output O]), ...)`; `validate-l1-lockup` accepts O (first time seen), credits `sats-total` into bond 0's shares.
3. Without spending or altering the Bitcoin output O, staker A calls `register-for-bond(bond-index=6, ..., btc-lockup=ok([output O]), ...)` again; because `seen-outpoints` resets per call, O passes all `asserts!` again and is credited a second time into bond 6's shares.
4. Staker A now holds reward-share credit in two bonds backed by a single real BTC lockup, doubling their claim on distributed sBTC rewards relative to actual locked collateral.
