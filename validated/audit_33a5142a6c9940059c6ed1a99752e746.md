### Title
Webhook signature verification binds to an attacker-chosen organization while downstream handlers act on an unrelated `repository.full_name` from the same unverified payload - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`Shipit::WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to validate the HMAC signature against using `repository.owner.login` (falling back to `organization.login`) taken directly from the untrusted, not-yet-verified JSON body. All webhook event handlers, however, resolve the actual `Repository`/`Stack` to act on using a *different* field from the very same body: `repository.full_name`. Because these two fields are never checked for consistency, an attacker who legitimately controls a GitHub App/organization (and therefore genuinely knows that organization's `webhook_secret`) can forge a payload whose `owner.login` matches their own org (so signature verification passes) while `full_name` names any other repository tracked by the Shipit instance.

### Finding Description [1](#0-0) 

`verify_signature` does: [2](#0-1) 
selecting the `github_app` (and thus the `webhook_secret` HMAC key) via `repository_owner`: [3](#0-2) 

Both `params.dig('repository','owner','login')` and `params.dig('organization','login')` come straight from `request.raw_post` before any cryptographic check has occurred — the value is attacker-supplied.

`verify_webhook_signature` itself only proves the raw bytes were signed with *some* known-to-Shipit organization's `webhook_secret`: [4](#0-3) 

Once verification "passes," `WebhooksController#create` dispatches the entire parsed body to handlers: [5](#0-4) 

But every handler (base class and all `pull_request` handlers) determines the target `Repository`/`Stack` using `repository.full_name`, not `repository.owner.login`: [6](#0-5) [7](#0-6) 

For `push` events, `PushHandler` uses `stacks` (derived from `full_name`) to enqueue a sync job: [8](#0-7) 

For `status` events, `StatusHandler` looks commits up globally by `sha` (not scoped to the signing org at all) and records a GitHub-attributed CI status: [9](#0-8) 

That recorded status directly feeds `Commit#deployable?`, which gates both manual deploys and Shipit's continuous-deployment auto-trigger: [10](#0-9) 

This is exactly the bug class from the report: a field the verification step trusts (`repository.owner.login`, used to pick the HMAC key) is not the field the subsequent state-changing logic acts on (`repository.full_name` / bare `sha`). The "signing organization" and the "written repository" are never bound together, so a valid signature from organization A says nothing about which repository's data is actually being mutated.

### Impact Explanation
An attacker who owns/administers any GitHub organization or repository with its own GitHub App installed on this Shipit instance (i.e., is a legitimate, low-privileged webhook sender for *their own* stack) can forge `status`, `push`, `check_suite`, `membership`, and `pull_request` webhook events for **any other repository/stack** tracked by the same Shipit instance, by simply signing the payload with their own known `webhook_secret` while setting `repository.full_name` (and/or `sha` for status events) to point at the victim repository. Concretely:
- Forged `status` events can flip a victim commit's CI status to `success`, satisfying `Commit#deployable?` and enabling/auto-triggering an unauthorized deploy of that commit via continuous delivery or a subsequent manual deploy request — an unauthorized deploy without ever passing real CI on the victim's GitHub repo.
- Forged `push`/`check_suite` events can force sync jobs, check-run refreshes, or PR provisioning/archival actions on stacks the attacker does not own.
- Forged `membership` events can create/manipulate `Team`/`User` records tied to the victim org context.

This crosses a real trust boundary (organization the app authenticated for vs. the repository the effect is applied to) without requiring any Shipit session, `ApiClient` token, or GitHub write access to the victim repository — only requiring the attacker to be a legitimate webhook sender for *some* org configured on the instance. This matches the required High/Critical impact bucket of "an unauthorized deploy."

### Likelihood Explanation
Requires the instance to be configured with multiple GitHub organizations/Apps (a documented, supported configuration — see `TOP_LEVEL_GH_KEYS`/multi-org secrets examples), and the attacker must control one of them (e.g., by installing their own GitHub App pointed at the shared `/webhooks` endpoint, which is realistic for any organization onboarded to a shared Shipit deployment). No secret guessing or brute force is needed — the attacker uses their own legitimately-known `webhook_secret`. Likelihood is moderate-to-high in any multi-tenant/multi-org Shipit deployment.

### Recommendation
Bind signature-key selection to the same identity that is used for all downstream lookups. Concretely, derive the organization used for `verify_webhook_signature` from `repository.full_name`'s owner segment (or reject payloads where `repository.owner.login` doesn't match the owner segment of `repository.full_name`), and additionally have each handler assert that the resolved `Repository`'s owner matches the organization whose secret validated the signature before acting on the payload.

### Proof of Concept
1. Shipit instance configured with two orgs, `attacker-org` (attacker controls the GitHub App / knows its `webhook_secret`) and `victim-org` (has a tracked `Stack` for `victim-org/victim-repo`).
2. Attacker crafts a `status` webhook JSON body:
   ```json
   {
     "sha": "<victim-commit-sha>",
     "state": "success",
     "context": "ci/circleci",
     "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" }
   }
   ```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(attacker-org webhook_secret, body)>` and POSTs to `/webhooks` with `X-Github-Event: status`.
4. `verify_signature` resolves `Shipit.github(organization: "attacker-org")` from `repository.owner.login`, and the signature validates successfully because it truly was signed by that org's real secret.
5. `StatusHandler#process` finds the victim `Commit` by `sha` (global lookup, no org scoping) and calls `create_status_from_github!`, marking it `success`; if that satisfies `Commit#deployable?`, a subsequent (or continuous-delivery-triggered) deploy of `victim-org/victim-repo` proceeds without the commit ever having passed real CI on GitHub.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
