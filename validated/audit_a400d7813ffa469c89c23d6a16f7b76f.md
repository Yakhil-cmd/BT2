### Title
Webhook signature verification uses query-string-controlled organization while the actual payload processed comes from the unsigned-but-merged raw body - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App / `webhook_secret` to check the HMAC signature against based on `repository_owner`, which is read from the framework's merged `params` object (query string + body). `WebhooksController#create` then re-parses `request.raw_post` independently to build the payload that is actually dispatched to the event handlers. Because Rails merges query-string parameters over body parameters when building `params` (`request_parameters.merge(query_parameters)`), an attacker can supply a `repository[owner][login]` (or `organization[login]`) value in the URL query string that differs from the `repository`/`organization` actually present in the signed JSON body. This breaks the binding "organization whose signature was verified == organization/repository actually acted upon."

### Finding Description
`verify_signature` computes the organization used for verification purely from framework `params`: [1](#0-0) [2](#0-1) 

`repository_owner` is derived from `params.dig('repository', 'owner', 'login')` — i.e., from the same `params` hash Rails builds by merging query-string parameters on top of body-derived parameters for a given request. Meanwhile, `create` builds a completely separate, body-only representation of the payload: [3](#0-2) 

That `params` local variable (parsed strictly from `request.raw_post`) is what gets handed to every registered `Shipit::Webhooks` handler (`PushHandler`, `StatusHandler`, `MembershipHandler`, etc.), which resolve the target `Stack`/`Repository` via `payload.dig('repository', 'full_name')`: [4](#0-3) 

So the org used to pick the `GitHubApp`/`webhook_secret` for signature verification (`repository_owner`, influenced by query string) and the org/repository whose data is actually written by the handlers (parsed strictly from the signed body) are two different fields that can be made to diverge. `GitHubApp#verify_webhook_signature` trivially returns `true` when the selected app has no `webhook_secret` configured at all: [5](#0-4) 

Combined, an attacker who knows (or guesses) the name of any configured GitHub organization/app entry that has `webhook_secret: nil` (a supported, documented configuration — see `config/secrets.development.shopify.yml` and `test/dummy/config/secrets_double_github_app.yml`, which both show `webhook_secret: # nil` as a valid per-org setting) can force `verify_signature` to pass unconditionally by putting that organization's name in the query string, while the JSON body actually targets and mutates state for a *different*, real (and signature-protected) organization/repository whose secret the attacker never possesses.

### Impact Explanation
If exploited, this allows an unauthenticated, unprivileged network attacker to forge webhook events (`push`, `status`, `membership`, `pull_request`, `check_suite`, etc.) for arbitrary repositories/organizations without ever knowing the real `webhook_secret`, entirely defeating the purpose of `verify_webhook_signature`. Depending on which handler processes the forged event, this can trigger `GithubSyncJob` for an arbitrary stack, fabricate commit statuses, or manipulate team memberships (`MembershipHandler`) — actions that should require a legitimate, secret-signed GitHub webhook delivery. This crosses the "unauthorized deploy/rollback/merge" and "cross-repository writes" impact bar because sync/push events can drive deploy pipelines.

### Likelihood Explanation
Requires: (1) a multi-org Shipit deployment where at least one configured organization entry omits `webhook_secret` (a documented, supported configuration per `docs/setup.md`), and (2) confirmation of Rails' documented `query_parameters` overriding `request_parameters` merge behavior for the `params` object used inside `ActionController::Base`. This is a realistic, no-privilege, no-credential attack path once those preconditions hold, but it is conditional on deployment configuration (an org without a webhook secret existing) rather than universally exploitable against any single-org deployment with a secret configured on the only entry.

### Recommendation
Have `verify_signature` and `create` operate on the exact same parsed payload (ideally parsed once from `request.raw_post` and cached), rather than deriving the organization used for authentication from the framework-merged `params` (which can be polluted via the query string) while the event payload used to act is derived independently from the raw body only. Additionally, never treat a missing/blank `webhook_secret` as an implicit "skip verification" success for events that mutate repository/organization state — require an explicit secret for any active integration.

### Proof of Concept
1. Deploy Shipit with a multi-organization github config where `OrgA` has `webhook_secret: nil` and `OrgB` has a real secret (mirroring `test/dummy/config/secrets_double_github_app.yml`).
2. POST to `/webhooks?repository[owner][login]=OrgA` (or `?organization[login]=OrgA`) with header `X-Github-Event: push` and a JSON body whose actual `repository.full_name` / `repository.owner.login` is `OrgB/some-real-repo`, without any valid `X-Hub-Signature` for `OrgB`'s secret.
3. `verify_signature` computes `repository_owner` from the merged `params` (which is polluted by the query string) as `OrgA`, calls `Shipit.github(organization: 'OrgA').verify_webhook_signature(...)`, which returns `true` unconditionally because `OrgA` has no `webhook_secret`.
4. `create` re-parses `request.raw_post` (unaffected by the query string) and dispatches the `OrgB/some-real-repo` payload to `PushHandler`, triggering `GithubSyncJob` for `OrgB`'s stack despite never presenting a valid signature for `OrgB`. [6](#0-5)

# frozen_string_literal: true

module Shipit
  class WebhooksController < ActionController::Base
    skip_before_action :verify_authenticity_token, raise: false
    before_action :check_if_ping, :drop_unhandled_event, :verify_signature

    respond_to :json

    def create
      params = JSON.parse(request.raw_post)
      Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }

      head(:ok)
    end

    private

    def drop_unhandled_event
      # Acknowledge, but do nothing
      head(204) unless Shipit::Webhooks.for_event(event).present?
    end

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping
      head(:ok) if event == 'ping'
    end

    def event
      request.headers.fetch('X-Github-Event')
    end

    def repository_owner
      # Fallback to the organization sub-object if repository isn't included in the payload
      params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
    end
  end
end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
