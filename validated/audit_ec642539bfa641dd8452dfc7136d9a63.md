Confirmed: `isTooDeeplyNestedOrHasTooManyNodes(obj, depthLimit, nodesLimit)` in `string_utils.js:260-284` counts nodes and depth but never sums up string field lengths — a shallow object with one enormous string value passes the check trivially since `nodeCount` only increments per key/array element, not per character.

### Title
Unbounded memory consumption via unchecked `encrypted_message`/DH string field sizes in hub device-message relay (`network.js` `hub/deliver`, `device.js` `decryptPackage`)

### Summary
The `hub/deliver` request handler in `network.js` validates an incoming `objDeviceMessage` only against field presence and a depth/node-count check (`isTooDeeplyNestedOrHasTooManyNodes(objDeviceMessage, 5, 100)`), never bounding the byte length of the individual string fields such as `encrypted_package.encrypted_message`, `iv`, `authtag`, or the DH pubkeys. Any unpaired peer connected to a hub (or acting as hub target) can submit a `hub/deliver` request with a normal-shaped, shallow JSON object whose `encrypted_message` field is an arbitrarily large base64 string (many megabytes/gigabytes), and the node will fully buffer it into memory multiple times (as a raw string, as JSON, as a re-stringified DB row, and again during decryption) with no throttling.

### Finding Description
The relevant validation lives in `network.js:3509-3521`: [1](#0-0) 
It checks required fields and calls `isTooDeeplyNestedOrHasTooManyNodes(objDeviceMessage, 5, 100)`. That helper, defined in `string_utils.js:260-284`, only tracks `nodeCount` (number of array elements/object keys visited) and recursion `depth` — it does **not** accumulate string byte length anywhere: [2](#0-1) 
Because `objDeviceMessage` is intentionally shallow (`{signature, pubkey, to, encrypted_package: {dh: {...}, encrypted_message, iv, authtag}}`), it contains only a handful of nodes regardless of how long the string values are, so a multi-hundred-megabyte `encrypted_message` string sails through this check.

After the check, the message is signature-verified (`ecdsaSig.verify`, cheap relative to the payload) and then, if not delivered directly to a locally-connected client, it is JSON-stringified and inserted into the `device_messages` table (`network.js:3554-3557`), fully materializing the oversized string again in the Node.js process and in SQLite. When the (or another) recipient later receives it via `hub/message`, `device.js`'s `handleJustsaying` (`device.js:147-183`) calls `decryptPackage()`, which does `Buffer.from(objEncryptedPackage.encrypted_message, "base64")` (`device.js:447`) — allocating another large buffer from attacker-controlled length — then splits it into 4096-byte chunks for `decipher.update()`, building an array of buffer chunks that are concatenated via `Buffer.concat(arrChunks)` (`device.js:456`), i.e. the same "attacker-controlled-size string decoded and repeatedly buffered/concatenated with no cap" pattern described in the `basic-ftp` `StringWriter` advisory. [3](#0-2) 

There is no `MAX_MESSAGE_LENGTH`-style cap enforced before this point (confirmed no such constant exists in the codebase), and the only length-based cleanup, `deleteOverlengthMessagesIfLimitIsSet` (`network.js:2735-2742`), is opt-in per-connection (`ws.max_message_length`) and runs only when *sending* stored messages back out, not when *accepting* `hub/deliver` in the first place. [4](#0-3) 

### Impact Explanation
Any unprivileged peer that can reach a hub (or a device acting as its own hub) can submit `hub/deliver` requests with unbounded-size `encrypted_message`/DH string fields. Each such message causes the hub process to allocate memory proportional to the attacker-chosen string length multiple times (raw JSON parse of the WS frame, `JSON.stringify` for DB insert, base64 decode, chunked decrypt buffer concat) without any cap, and persists the oversized blob into `device_messages`. Repeated submissions accumulate unbounded memory and disk usage, and forwarding/broadcast to online clients (`network.js:3560-3567`) propagates the same oversized payload to the recipient device, which repeats the allocation in `decryptPackage()`. This matches the CWE-400/CWE-770 memory-exhaustion class from the report and can destabilize or crash the hub/wallet process — a network-facing denial-of-service reachable by an ordinary paired-or-unpaired peer, not requiring a malicious hub/node.

### Likelihood Explanation
High. `hub/deliver` is a request any connected peer can send without prior pairing (only sender-signature verification is required, and the signature check succeeds for a self-signed device key the attacker controls). No rate limiting or per-field size validation exists before the expensive processing steps. This is trivially automatable and requires no privileged access.

### Recommendation
1. Add explicit maximum length checks on `encrypted_package.encrypted_message`, `iv`, `authtag`, and the DH pubkey fields in the `hub/deliver` handler (`network.js:3509-3521`) before any further processing, e.g. reject payloads whose `JSON.stringify(objDeviceMessage).length` (or per-field length) exceeds a small fixed constant such as `constants.MAX_ENCRYPTED_MESSAGE_LENGTH` (a few KB is sufficient for legitimate encrypted device-chat payloads).
2. Extend `isTooDeeplyNestedOrHasTooManyNodes` (or add a companion function similar to the existing `isTooBigObj`, which already tracks string `length`) and use that variant for `hub/deliver`/`hub/message` validation instead of the length-blind node/depth check.
3. Enforce the same cap in `device.js`'s `decryptPackage()` before calling `Buffer.from(objEncryptedPackage.encrypted_message, "base64")`, as defense in depth.

### Proof of Concept
1. Connect to a hub as an unpaired peer (only need a valid secp256k1 keypair; no correspondent relationship required).
2. Generate a device keypair and construct:
```js
var objDeviceMessage = {
  to: <any valid device address>,
  pubkey: myPubKeyB64,
  encrypted_package: {
    dh: { sender_ephemeral_pubkey: ephemeralPubB64, recipient_ephemeral_pubkey: ephemeralPubB64 },
    encrypted_message: "A".repeat(500 * 1024 * 1024), // 500MB base64 blob
    iv: someB64,
    authtag: someB64
  }
};
objDeviceMessage.signature = ecdsaSig.sign(objectHash.getDeviceMessageHashToSign(objDeviceMessage), myPriv);
ws.sendRequest('hub/deliver', objDeviceMessage);
```
3. Because the object has only ~7 nodes and depth ~3, it passes `isTooDeeplyNestedOrHasTooManyNodes(objDeviceMessage, 5, 100)`. The hub proceeds to verify the signature, `JSON.stringify` the whole object, and insert it into `device_messages`, allocating hundreds of MB per request.
4. Repeating this with many parallel connections/requests drives the hub's memory usage up without bound until the process becomes unstable or is OOM-killed.

```javascript
function isTooDeeplyNestedOrHasTooManyNodes(obj, depthLimit = 100, nodesLimit = 10000) {
	let nodeCount = 0;

	function check(variable, depth){
		if (depth > depthLimit || nodeCount > nodesLimit)
			return true;
		if (variable === null || typeof variable !== "object")
			return false;
		if (Array.isArray(variable)) {
			nodeCount += variable.length;
			for (let v of variable)
				if (check(v, depth + 1))
					return true;
		}
		else {
			nodeCount += Object.keys(variable).length;
			for (let key in variable)
				if (check(variable[key], depth + 1))
					return true;
		}
		return false;
	}

	return check(obj, 1);
}
```
