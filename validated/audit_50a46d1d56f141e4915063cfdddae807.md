### Title
Webhook Signature Verified Against `repository.owner.login` While Handlers Act On the Independently-Attacker-Controlled `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
In a multi-GitHub-App deployment of Shipit, `WebhooksController#verify_signature` selects which organization's `webhook_secret` to validate a webhook against using `repository.owner.login` from the JSON payload, but the event handlers that actually mutate application state select the target `Repository`/`Stack` using `repository.full_name` from the very same payload. Nothing ties these two fields together, so a party who legitimately controls one onboarded GitHub organization's App/webhook secret can forge a validly-signed webhook whose `repository.owner.login` matches their own org (passing verification) while `repository.full_name` points at a completely different, unrelated organization's repository tracked by the same Shipit instance.

### Finding Description
`WebhooksController#verify_signature` picks the GitHub App config (and thus the HMAC secret) to check the signature against like this: [1](#0-0) 

`repository_owner` is derived purely from the untrusted JSON body: [2](#0-1) 

Once the signature is accepted, `create` re-parses the same raw body and dispatches it, unmodified, to the registered handlers: [3](#0-2) 

Every handler (`PushHandler`, `StatusHandler`, `CheckSuiteHandler`, the `PullRequest::*` handlers) resolves the actual `Repository`/`Stack` to act on from a *different* field of the same payload: `repository.full_name`, via `Handler#repository_name`/`Handler#stacks`: [4](#0-3) 

and, e.g., in `PushHandler`: [5](#0-4) 

Since the entire JSON body is a single attacker-authored/attacker-signed blob, there is no requirement enforced anywhere in this code path that `repository.owner.login` (used to pick/verify the signing secret) matches the owner encoded in `repository.full_name` (used to pick the target Stack). Documented multi-tenant setups explicitly configure one `webhook_secret` per GitHub organization: [6](#0-5) 

An org administrator who legitimately owns one tenant's GitHub App (and therefore legitimately knows/controls that tenant's `webhook_secret`) can sign an arbitrary payload with `repository.owner.login` set to their own org (so `verify_webhook_signature` succeeds against their own secret) while setting `repository.full_name` to `OtherOrg/some-repo`. This breaks the equality that should hold: `organization whose secret authenticated the request == organization owning the repository being written to`.

### Impact Explanation
Once this signature check is bypassed for a foreign tenant's repository, an attacker with zero Shipit privileges over the target organization can:
- Trigger `push` events causing `GithubSyncJob`/`stack.sync_github(expected_head_sha:)` to run against a target stack outside their org, potentially advancing/rewinding what Shipit believes is the deployable head and, on stacks with `continuous_deployment` enabled, triggering an unauthorized deploy of a chosen legitimate commit SHA.
- Forge `status` events to fabricate CI check results for arbitrary commits on the victim's stacks, which can satisfy `ci.require` gating and unlock deploys/merges that should have been blocked.
- Forge `check_suite` events similarly to manipulate merge-queue/CI gating logic.

This matches the "unauthorized deploy" / cross-tenant state-mutation impact class called out as in-scope (High/Critical): an attacker who never obtained a Shipit session, `ApiClient` token, or write access to the victim repository can still cause deploy-relevant state changes for it.

### Likelihood Explanation
Exploitation requires the Shipit instance to be configured for **multiple GitHub organizations** (a documented, supported configuration — see `docs/setup.md` "Using Multiple Github Applications") and requires the attacker to legitimately administer at least one of the onboarded orgs (thus knowing that org's own `webhook_secret`). This is a realistic scenario for shared/self-hosted Shipit deployments serving several internal teams/orgs where no single team is meant to trust another. Given that condition, forging the cross-org payload is trivial (pure HTTP + HMAC using the attacker's own known secret) and requires no interaction with GitHub's UI or the victim.

### Recommendation
- Do not let a single attacker-controlled JSON field (`repository.owner.login`) both select the verifying secret and be divorced from the field used for state mutation (`repository.full_name`). After verifying the signature, re-derive/validate that the resolved `Repository`'s owner matches the `organization`/App that successfully verified the signature (i.e., `Shipit.github(organization: repository_owner)` must correspond to the same GitHub App installation that owns the `Repository` matched by `repository.full_name`), and reject the webhook otherwise.
- Alternatively, store on each `Repository`/App-config which organization it is scoped to and cross-check that against the verified organization before handlers run, rather than trusting `full_name` in isolation.
- Consider deriving the org used to select the webhook secret and the org used to resolve the repository from the same normalized value, rather than two independently-attacker-suppliable JSON paths.

### Proof of Concept
Preconditions: Shipit instance configured with two GitHub Apps, `OrgTwo` (attacker administers this org's GitHub App and therefore knows `OrgTwo`'s `webhook_secret`) and `OrgOne` (victim org, tracked stack `OrgOne/victim-repo`, branch `main`, with `continuous_deployment: true`).

1. Attacker crafts a JSON payload:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-legit-sha-from-OrgOne/victim-repo>",
  "repository": {
    "owner": { "login": "OrgTwo" },
    "full_name": "OrgOne/victim-repo"
  }
}
```
2. Attacker computes `X-Hub-Signature: sha1=<hmac>` over this exact JSON body using `OrgTwo`'s known `webhook_secret`.
3. Attacker POSTs this to `/github/webhooks` (or configured webhook route) with header `X-Github-Event: push`.
4. `verify_signature` calls `Shipit.github(organization: "OrgTwo")` (from `repository.owner.login`) and validates the signature successfully against `OrgTwo`'s secret — verification passes.
5. `create` re-parses the body and dispatches to `PushHandler`, which resolves the target repository via `payload.dig('repository','full_name')` = `"OrgOne/victim-repo"`, matching the victim stack and enqueuing `GithubSyncJob` with the attacker-chosen `expected_head_sha`, potentially triggering deploy activity on a stack the attacker has no legitimate access to.
