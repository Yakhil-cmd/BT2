### Title
Blank `webhook_secret` bypasses HMAC verification, letting an unauthenticated attacker forge a `membership` webhook and self-grant membership in any `Shipit.github_teams` team - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` delegates to `GitHubApp#verify_webhook_signature`, which returns `true` unconditionally when the org's configured `webhook_secret` is blank, regardless of the request's `X-Hub-Signature` header. For any organization configured this way, an unauthenticated internet client can POST an arbitrary, unsigned `membership` event whose `team.id` matches a real `Shipit.github_teams` team, causing `MembershipHandler#process` to create a `Membership` and flip `User#authorized?` to `true` for an attacker-chosen login.

### Finding Description
The security boundary equality claimed is: `webhook_secret.presence == the entire authentication requirement for the webhook endpoint`. Tracing the code confirms this holds exactly:

- `GitHubApp#initialize` sets `@webhook_secret = @config[:webhook_secret].presence` [1](#0-0) .
- `verify_webhook_signature` short-circuits: `return true unless webhook_secret` — before touching the `X-Hub-Signature` header or computing any HMAC [2](#0-1) .
- `WebhooksController#verify_signature` calls this method with `request.headers['X-Hub-Signature']` and `request.raw_post`, and only `head(422)` when `verified` is falsy [3](#0-2) . If the header is absent entirely, `signature` is `nil`, but that branch is never reached because `webhook_secret` is blank and the method already returned `true`.
- `drop_unhandled_event` and `check_if_ping` do not require authentication and pass `membership` through to `create`, which parses `params` and dispatches to `Shipit::Webhooks.for_event(event)` handlers [4](#0-3) .
- `MembershipHandler` validates only the payload's shape via `ExplicitParameters` (`action`, `team.id/name/slug/url`, `organization.login`, `member.login`) with no ownership or signature check, then calls `find_or_create_team!` (a `Team.find_or_create_by!(github_id: params.team.id)`) and, for `action == 'added'`, `team.add_member(member)` [5](#0-4) .
- `Team#add_member` unconditionally appends the member to `members` (creating a `Membership` row) [6](#0-5) .
- `User#authorized?` is computed as `Shipit.github_teams.empty? || teams.where(id: Shipit.github_teams.map(&:id)).exists?` [7](#0-6) . If the attacker crafts `team.id` equal to the `github_id` of a team already resolved via `Shipit.github_teams` (which resolves org OAuth teams into `Team` rows keyed by `github_id`, see `Team.find_or_create_by_handle`/`github_team=` [8](#0-7)  and `Shipit.github_teams` [9](#0-8) ), `find_or_create_team!` reuses that exact `Team` row (matched by `github_id`), and the forged membership satisfies `authorized?` for that user.

No other guard intervenes: `repository_owner` merely selects which org's `GitHubApp`/secret to check [10](#0-9) , and once that org has no secret, the whole endpoint is open for events under that org's name, including `membership`, which is org-scoped and not repository-scoped at all. Both sides of the equality match: when `webhook_secret` is blank, verification is trivially `true` for any/no signature, confirming the divergence.

### Impact Explanation
An attacker with zero Shipit credentials can create a `Membership` associating an attacker-controlled `User` (`params.member.login`, auto-vivified via `find_or_create_by_login!`) with a real privileged `Team` whose `github_id` is in `Shipit.github_teams`, granting `authorized?` for that user, which the app-wide `Authentication`/`require_permission!` concern uses to permit deploys, rollbacks, and other privileged stack operations. This is a full authentication bypass on the webhook surface for that org and an unauthorized escalation into `Shipit.github_teams` authorization — repeatable for any org configured without `webhook_secret`, and blast radius extends to every stack/repository that relies on that org's team membership for authorization decisions.

### Likelihood Explanation
Precondition: at least one org in `secrets.github` is configured with a blank/absent `webhook_secret` — an explicitly supported ("insecure default") configuration path in `GitHubApp`. Given that precondition, exploitation costs the attacker only knowledge of the org's login name (public) and a single unauthenticated HTTP POST with `X-Github-Event: membership` and a crafted JSON body; no GitHub account, no Shipit session, and no secrets are required. This is trivially repeatable.

### Recommendation
Do not allow `verify_webhook_signature` to silently pass when `webhook_secret` is blank. Either (a) fail closed (`return false` / reject requests) when no secret is configured for an org that has handlers registered for security-sensitive events like `membership`, or (b) make `webhook_secret` mandatory for orgs at boot/config-validation time, and log/alert operators loudly instead of silently trusting unsigned payloads.

### Proof of Concept
Minitest plan (mirrors the existing `test/controllers/webhooks_controller_test.rb` patterns):
1. Configure a fake org (e.g., stub `Shipit.github(organization: 'acme')` or set `Rails.application.credentials.github[:acme]` fixture) with `webhook_secret: nil`.
2. Ensure a `Team` exists with `github_id` equal to a value present in `Shipit.github_teams` (stub `Shipit.github_teams` to return `[team]`).
3. POST to `/webhooks` with header `X-Github-Event: membership`, no `X-Hub-Signature` header, and JSON body: `{"action":"added","team":{"id":<team.github_id>,"name":"Admins","slug":"admins","url":"https://api.github.com/teams/1"},"organization":{"login":"acme"},"member":{"login":"attacker"}}`.
4. Assert response is `200`/`:ok` (not `422`).
5. Assert `Shipit::Membership.exists?(user: Shipit::User.find_by(login: 'attacker'), team:)` is `true`.
6. Assert `Shipit::User.find_by(login: 'attacker').authorized?` is `true`.

Both sides of the binding differ before/after: before the request, `webhook_secret.presence` was `nil` → no security boundary existed; after the request, an unauthenticated write occurred that should have required a valid HMAC signature, confirming the vulnerability.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
