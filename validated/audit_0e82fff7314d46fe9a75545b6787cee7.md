## Analysis

The `_onlyWhiteListed()` bug is a case where a check that should *gate* a privileged write instead *substitutes for* it, so an entity that should be authorized to act is prevented from being properly re-checked against the actual resource being written. The closest reachable analog in this engine is in `Shipit::Api::StacksController`: the permission check (`require_permission :write, :stack`) is enforced at the *action* level, but the *scope* binding — "the `Stack` this `ApiClient` is authorized to write" — is never applied to `#create`, because `#create` builds a brand-new `Stack`/`Repository` from client-supplied `repo_owner`/`repo_name` instead of going through the scoped `stacks` collection used everywhere else (`show`, `update`, `destroy`, `refresh`). ### Title
`ApiClient#stack_id` scope binding is not enforced on stack creation, allowing a stack-scoped token to create arbitrary new stacks - ([File: app/controllers/shipit/api/stacks_controller.rb])

### Summary
An `ApiClient` can optionally be bound to a single `Stack` via `belongs_to :stack, optional: true`, and the base controller's `stacks` helper enforces that binding by restricting the queryable scope to `Stack.where(id: current_api_client.stack_id)` whenever `stack_id` is present. Every read/write action on an existing stack (`show`, `update`, `destroy`, `refresh`) resolves its target through this scoped `stacks.from_param!(...)`, so a token scoped to stack X cannot touch stack Y. However, `StacksController#create` never consults the scoped `stacks` collection at all — it builds an entirely new `Stack.new(create_params)` and a `Repository.find_or_create_by(owner: repo_owner, name: repo_name)` straight from client-supplied parameters, gated only by the coarse `write:stack` permission check.

### Finding Description
The binding that should hold is: `token.stack_id (authorized stack)` == `stack acted upon`. `require_permission!` only checks the permission *name* (`write:stack`), not which stack the operation targets: [5](#0-4) 

For `show`/`update`/`destroy`/`refresh`, the `stack` method is defined as `@stack ||= stacks.from_param!(params[:id])`, where `stacks` is the scoped collection — this is where the `stack_id` binding is actually enforced. But `create` does not call `stack`/`stacks` at all: [6](#0-5) [7](#0-6) 

So a token created with `stack_id: X` and `permissions: ["write:stack"]` (e.g., issued for narrow, single-stack CI integration use, as done by `CCMenuUrlController` for read-only tokens) still passes `require_permission :write, :stack` for `create`, and can create a `Stack` for **any** `repo_owner`/`repo_name`, on any repository already known to (or newly registered in) the Shipit instance — completely outside the one stack the token was scoped to.

### Impact Explanation
This breaks the intended isolation between tenants/repos in a multi-stack Shipit deployment: a token meant to be usable only against a single stack (its `stack_id`) can register new deployment stacks for arbitrary repositories, which is an unauthorized state-changing/write operation on resources the token was never meant to reach — matching the "escalation into `Shipit.github_teams`/stack authorization" bucket described in scope. It does not by itself yield RCE, but it does allow cross-repository/cross-stack writes via a low-privilege, narrowly-scoped credential — a direct instance of the binding-violation class the report calls out (token authorizes stack X, but the code path lets it touch stack Y/instantiate new ones).

### Likelihood Explanation
Exploitability requires possession of any `ApiClient` token that has `write:stack` permission and a non-null `stack_id` (a legitimately-issued, narrowly scoped token) — no privileged or admin token is required beyond that, and no signature/webhook forgery is needed. Because `stack_id`-scoped tokens are a supported, documented feature (`ApiClient#stack_id`, used in the base controller's `stacks` method), this is a realistic configuration in any deployment that issues per-stack API credentials.

### Recommendation
In `Shipit::Api::StacksController#create`, verify that the current `ApiClient` is either unscoped (`stack_id` nil) or explicitly permitted to create new stacks, e.g. reject the request (403) when `current_api_client.stack_id?` is true, or require a distinct higher-privileged permission for stack creation instead of overloading the generic `write:stack` permission.

### Proof of Concept
1. As an admin, create an `ApiClient` scoped to stack `A` with `permissions: ["write:stack"]`, `stack_id: A.id` (mirrors the existing `here_come_the_walrus` fixture pattern seen scoping index results to a single stack).
2. Authenticate as that client and call:
   `POST /api/stacks` with `repo_owner: "victim-org", repo_name: "victim-repo", environment: "production", branch: "main"`.
3. Observe `require_permission :write, :stack` passes (the client has `write:stack`), and `create` succeeds, creating a brand-new `Stack`/`Repository` unrelated to the client's bound `stack_id` — confirmed by the absence of any `stacks.from_param!`/`stack_id` check in `#create` (contrast with `#show`/`#update`/`#destroy`, which route through the scoped `stack` method).
