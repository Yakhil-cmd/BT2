This confirms the exploit is not viable. The critical binding check is at `third_party/move/move-vm/runtime/src/storage/publishing.rs:158-173`, which enforces that a module's self-address must equal the transaction sender before it is ever staged for publishing: any mismatch is rejected with `StatusCode::MODULE_ADDRESS_DOES_NOT_MATCH_SENDER`. This means an attacker cannot get a module published under any address other than their own signer's address, regardless of what metadata they observe via `unmetered_get_module_state_value_metadata`. [1](#0-0) 

Additionally, `convert_modules_into_write_ops` in `aptos-move/aptos-vm/src/move_vm_ext/write_op_converter.rs:57-77` only uses `unmetered_get_module_state_value_metadata` to decide `Op::Modify` vs `Op::New` for the `module_id` derived directly from the already-staged, address-checked `verified_module_bundle` — it does not take any attacker-supplied address as a separate/untrusted argument that could be spoofed independently of the staged module identity. [2](#0-1) 

The `StateKey::module(address, module_name)` construction inside `AptosCodeStorageAdapter::unmetered_get_module_state_value_metadata` is a public state-read helper reachable from any Move code, including view functions, and merely returns metadata (existence/creation time) for a given key — reading such metadata is not privileged information (module existence is publicly observable on-chain via any full node query, e.g. `unmetered_check_module_exists`). [3](#0-2) 

Even granting the attacker full knowledge of this metadata, there is no code path in `finish_with_module_publishing_and_initialization` (`aptos-move/aptos-vm/src/move_vm_ext/session/user_transaction_sessions/user.rs:81-183`) that allows the `destination` address used for staging/publishing to diverge from the transaction's authenticated sender — `destination` comes from the `PublishRequest` produced by the native `code::request_publish` call, and the module's `self_addr()` is checked against `sender` at staging time as shown above. There is no mechanism by which leaked state-value metadata could be used to "forge" the classification of a new publish as a Modify under someone else's module — the `Op::Modify` vs `Op::New` decision is purely a bookkeeping detail for gas/storage-fee refund and does not bypass the ownership/address check that gates whether the write is even accepted under a given address in the first place.
