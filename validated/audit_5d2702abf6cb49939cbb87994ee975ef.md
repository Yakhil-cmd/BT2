### Title
Webhook organization-to-secret binding is not cross-checked against the repository actually mutated by handlers - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` picks which GitHub App (and therefore which `webhook_secret`) to verify the request signature with, based on `repository_owner`, a field read directly out of the still-unverified JSON body. Handlers then act on a *different* payload field, `repository.full_name`, to resolve the `Repository`/`Stack` to mutate. Nothing binds "the organization whose secret validated this signature" to "the repository that gets written."

### Finding Description
`verify_signature` computes `repository_owner` from `params.dig('repository', 'owner', 'login')` (falling back to `organization.login`), fetches the corresponding `GitHubApp` via `Shipit.github(organization: repository_owner)`, and checks the request's `X-Hub-Signature` against that org's `webhook_secret`: [2](#0-1) . This is exactly the equality that should hold: `organization authenticated == organization whose repository is written`.

Every handler, however, resolves the actual target repository from a separate JSON field, `repository.full_name`, via `Repository.from_github_repo_name`, e.g. `Handler#stacks`/`#repository_name` [3](#0-2) , and the same pattern repeats in every pull-request handler (`OpenedHandler`, `ClosedHandler`, `LabeledHandler`, `ReopenedHandler`, `LabelCapturingHandler`, `EditedHandler`) and `PushHandler` [4](#0-3) [5](#0-4) .

In a single-organization deployment this is harmless because `Shipit.github` ignores the `organization:` argument and always returns the one configured app (`github_default_organization` is `nil`) [6](#0-5) . But Shipit explicitly supports multi-organization configuration, where each organization key under `secrets.github` has its own independent `webhook_secret`, resolved by `github_app_config(organization)` [7](#0-6) . In that mode, an attacker who legitimately controls one onboarded organization's webhook secret (e.g., because they administer their own GitHub App installation registered under that org in Shipit's multi-tenant config) can craft a raw payload where `repository.owner.login` = their own organization (so the signature check passes with their own secret) but `repository.full_name` = `other-org/some-repo` (a repository belonging to a different, unrelated organization tracked by the same Shipit instance). `repository_owner` and `repository.full_name`'s owner are never compared, so the forged event is processed as if it legitimately originated from `other-org`.

### Impact Explanation
This breaks the binding "an organization that authenticated versus the repository that is written," letting an attacker who legally owns webhook credentials for organization A forge webhook events attributed to organization B's repositories. Depending on handler, this can trigger unwanted `GithubSyncJob` runs, archive/unarchive review stacks, or otherwise mutate `Stack`/`PullRequest` state for a repository the attacker does not control — a cross-repository/cross-organization write performed without ever authenticating as that repository's real organization.

### Likelihood Explanation
Exploitability is contingent on the host actually deploying Shipit in multi-organization mode with per-organization `webhook_secret`s and onboarding multiple, mutually-untrusted organizations — a configuration the engine explicitly supports (`TOP_LEVEL_GH_KEYS`, `github_app_config`) [8](#0-7) . Given that precondition, any org member who can trigger their own registered GitHub App's webhook delivery (or who simply knows/has access to their org's `webhook_secret`) can compute a valid HMAC and cross-address another org's repository, with no additional privilege required on the target org.

### Recommendation
After computing `repository_owner` and verifying the signature, re-derive the owner from `repository.full_name` (or `organization.login`) and require it to match `repository_owner` before dispatching to handlers; reject the request otherwise. Alternatively, have every handler validate that `payload.dig('repository','owner','login')` matches the resolved `Repository#owner` before mutating state, rather than trusting `full_name` alone.

### Proof of Concept
1. Shipit is configured with two organizations, `org-a` and `org-b`, each with its own GitHub App and `webhook_secret` (multi-org mode, `secrets.github` keyed by org).
2. Attacker (a legitimate admin of `org-a`'s GitHub App) computes `sha1=HMAC(org-a-webhook-secret, body)` for a `push` payload where `body.repository.owner.login = "org-a"` but `body.repository.full_name = "org-b/target-repo"`.
3. POST to `/webhooks` with `X-Hub-Signature` set to that value.
4. `verify_signature` calls `Shipit.github(organization: "org-a")` and validates successfully against `org-a`'s secret [9](#0-8) .
5. `PushHandler#process` resolves `Repository.from_github_repo_name("org-b/target-repo")` via `Handler#repository_name` and triggers `stack.sync_github` for `org-b`'s stack [3](#0-2) [10](#0-9) , despite the signature never having been checked against `org-b`'s secret.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
