### Title
Merkle tree implementation lacks leaf/internal-node domain separation, enabling "node-as-leaf" forgery of Merkle membership proofs - (File: merkle.js)

### Summary
`merkle.js` builds and verifies Merkle trees using the same hash function for both leaves and internal nodes with no domain-separation prefix, exactly the class of bug flagged in the external report (ambiguous pre-image data allowing a leaf to be reinterpreted as an internal node, or vice versa). This construction is exposed to unprivileged callers via the `'in merkle'` address/AA authentifier in `definition.js` and via the `is_valid_merkle_proof` oscript function in `formula/evaluation.js`, both of which accept attacker-controlled proofs (and, for AAs, attacker-controlled "element" values) at unit/trigger validation time.

### Finding Description
`merkle.js` hashes a leaf as `hash(element)` and an internal node as `hash(childHashLeft + childHashRight)`, using the identical `hash()` primitive (plain SHA-256/base64) for both: [1](#0-0) 

`verifyMerkleProof` walks up from `hash(element)` combining with each supplied sibling exactly the same way the tree was built, and the code even contains an explicit acknowledgment of the risk: [2](#0-1) 

Because there is no leaf/node domain separation (e.g., a `0x00`/`0x01` prefix distinguishing "hash of raw data" from "hash of two child hashes"), an attacker who has observed two adjacent hash values `A` and `B` anywhere in a legitimately published tree (siblings are, by design, revealed in every real proof) can submit `element = A + B` as the "leaf" at the corresponding tree depth, together with the true siblings above that subtree. `hash(element)` then collides with the real internal node's hash, and the remaining chain of hashing up to the root succeeds — producing a valid proof for an `element` that was never an actual leaf of the committed data set.

This primitive is reachable by unprivileged actors through two paths:
1. The `'in merkle'` authentifier evaluated while validating any address/AA definition during unit validation — the caller fully controls the serialized proof (`assocAuthentifiers[path]`): [3](#0-2) 
2. The `is_valid_merkle_proof` oscript primitive, usable inside AA trigger evaluation, where both the `element` and `proof` operands are evaluated from attacker-supplied expressions (e.g., `trigger.data.*`): [4](#0-3) [5](#0-4) 

### Impact Explanation
Any AA or address definition that gates spending/authorization on Merkle-tree membership (e.g., a whitelist encoded as a Merkle root published via a data feed, checked with `'in merkle'`, or an AA-side airdrop/claim check using `is_valid_merkle_proof`) can be bypassed by an attacker who never held true membership in the set. This allows unauthorized spending from a merkle-gated address, or unauthorized fund release/state mutation from an AA that relies on `is_valid_merkle_proof` to authorize a claim — i.e., concrete unauthorized value transfer/fund loss as required by the scope's validation bar.

### Likelihood Explanation
Exploitability requires only that the attacker can observe any two sibling hashes from a legitimately generated proof for the target Merkle root (which is inherent to how Merkle proofs work — siblings are always disclosed to prove membership) and then craft a fake leaf equal to their concatenation, following the exact algorithm in `getMerkleProof`/`verifyMerkleProof`. No secret key material or protocol-level privilege is needed; this is a pure application of the well-known "second pre-image"/CVE-2012-2459-style Merkle ambiguity, which the code's own inline comment ("Node-as-Leaf issue might matter in some cases") acknowledges without mitigating.

### Recommendation
Add domain separation to the hash function used for tree construction and verification, e.g., prefix leaves with `0x00` and internal nodes with `0x01` before hashing (`hash("\x00"+element)` for leaves, `hash("\x01"+left+right)` for internal nodes) in `getMerkleRoot`, `getMerkleProof`, and `verifyMerkleProof` in `merkle.js`. This must be a protocol-level, versioned/MCI-gated change since it affects consensus-relevant validation (`'in merkle'` authentifier and `is_valid_merkle_proof`).

### Proof of Concept
1. Build (or observe) a Merkle tree of ≥4 elements whose root `R` is published (e.g., posted as a data feed value referenced by an `'in merkle'` address definition, or stored as an AA state var checked via `is_valid_merkle_proof`).
2. From any legitimate proof for a real leaf, record two sibling hashes `A` and `B` at some internal level (these are always exposed as `proof.siblings`).
3. Construct a "fake leaf" string `element = A + B`.
4. Build a `proof` object using `{index, siblings, root: R}` where `siblings` are the real siblings from the level of the `A,B` pair up to the root (skipping the actual bottom-level siblings, since `hash(element) === hash(A+B)` already equals the real internal node's hash).
5. Call `merkle.verifyMerkleProof(element, proof)` (directly, or via `is_valid_merkle_proof(element, proof)` in an oscript formula, or via the `'in merkle'` authentifier with `serialized_proof` encoding this forged proof) — verification succeeds and returns `true` even though `element` was never part of the original data set, demonstrating unauthorized "membership" acceptance.

function hash(str){
	return crypto.createHash("sha256").update(str, "utf8").digest("base64");

function getMerkleRoot(arrElements){
	var arrHashes = arrElements.map(hash);
	while (arrHashes.length > 1){
		var arrOverHashes = []; // hashes over hashes
		for (var i=0; i<arrHashes.length; i+=2){
			var hash2_index = (i+1 < arrHashes.length) ? (i+1) : i; // for odd number of hashes
			arrOverHashes.push(hash(arrHashes[i] + arrHashes[hash2_index]));
		}
		arrHashes = arrOverHashes;
	}
	return arrHashes[0];
}

function verifyMerkleProof(element, proof){
	// Node-as-Leaf issue might matter in some cases
	try {
		var index = proof.index;
		var the_other_sibling = hash(element);
		for (var i = 0; i < proof.siblings.length; i++) {
			// this also works for duplicated trailing nodes
			if (index % 2 === 0)
				the_other_sibling = hash(the_other_sibling + proof.siblings[i]);
			else
				the_other_sibling = hash(proof.siblings[i] + the_other_sibling);
			index = Math.floor(index / 2);
		}
		return (the_other_sibling === proof.root);
	}
