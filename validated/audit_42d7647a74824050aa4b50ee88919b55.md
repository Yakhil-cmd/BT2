### Title
Webhook signature verified against the payload's own claimed organization, decoupled from the repository/commit actually mutated - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects which organization's HMAC `webhook_secret` to check the request against by reading the value straight out of the untrusted JSON body, then the event handlers (`StatusHandler`, `PushHandler`, etc.) act on other fields of that same body without re-confirming they belong to the organization that was actually authenticated. In Shipit's supported multi-organization configuration, this breaks the binding `organization that authenticated == repository/commit that is written`.

### Finding Description
`verify_signature` computes the organization used for signature verification purely from payload content:

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) [2](#0-1) 

`Shipit.github(organization:)` in multi-tenant mode looks up a per-organization config (and thus a per-organization `webhook_secret`) keyed by whatever string is passed in:
```ruby
def github(organization: github_default_organization)
  ...
  config = github_app_config(organization)
  raise GithubOrganizationUnknown, organization if config.nil?
  @github[organization] ||= GitHubApp.new(organization, config)
end

def github_app_config(organization)
  github_config = secrets.github.deep_transform_keys(&:downcase)
  github_config[organization.downcase.to_sym]
end
``` [3](#0-2) 

So the HMAC secret used to accept/reject the delivery is chosen by the *claimed* `repository.owner.login`/`organization.login` field inside the body being verified, not by any channel independent of the payload. The event body is then handed unmodified to handlers, which look up state using *other* fields from the same body and never re-check that those fields are consistent with the organization that was authenticated. `StatusHandler` is the starkest case — it updates commit statuses installation-wide, matched only by `sha`, with no repository/organization scoping at all:

```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [4](#0-3) 

`PushHandler` similarly advances the head of any stack whose `branch` name matches `params.ref`, using `params.after` as the new head sha, again without cross-checking `repository.owner.login` against the org actually used to validate the signature: [5](#0-4) 

In a shared/multi-organization Shipit deployment, `secrets.github` holds one entry per onboarded organization, each with its own `webhook_secret` set by that organization's own GitHub App administrator, as documented in the setup guide: [6](#0-5) 

An administrator of *any* onboarded organization therefore knows a valid `webhook_secret` and can compute a correct `X-Hub-Signature` for an arbitrary payload, as long as `repository.owner.login`/`organization.login` in that payload names *their own* organization — the field the controller uses to pick the secret. Nothing then stops that same payload from carrying a `sha`, `ref`, or `repository.full_name` belonging to a completely different, victim organization's stack, because the handlers never verify that the resolved `Commit`/`Stack`/`Repository` actually belongs to `repository_owner`.

### Impact Explanation
This breaks the binding "organization that authenticated == repository that is written," matching the High-impact criterion of "unauthenticated/cross-tenant write of stack state." Concretely, an attacker who administers their own onboarded organization (and thus knows only their own `webhook_secret`, never the victim's) can:
- Forge a `status` webhook that flips the CI status of an arbitrary commit SHA belonging to a victim's stack (`StatusHandler`), which can be used to satisfy merge/deploy gating conditions that depend on commit status.
- Forge a `push` webhook that causes `PushHandler` to enqueue `GithubSyncJob` with an attacker-chosen `expected_head_sha` for any stack whose branch name matches, potentially causing Shipit to treat an attacker-chosen commit as the new head of a victim's branch.

Both are cross-organization writes to stack/commit state performed without any credential tied to the victim repository, which lines up with the "cross-repository writes" / "unauthorized deploy" impact bar.

### Likelihood Explanation
Requires only that the Shipit instance is configured for multiple organizations (a documented, supported configuration via `secrets.github` keyed by org, see `github_app_config`/`github_organizations`) [7](#0-6) , and that the attacker controls (administers) at least one onboarded organization — a materially lower privilege bar than write access to the victim's actual repository or any Shipit session/API token. No Shipit account, session, or `ApiClient` token is needed at all; the whole path is through the public `/webhooks` endpoint.

### Recommendation
Handlers must scope every lookup (`Commit`, `Stack`, `Repository`) by the organization that was actually used to validate the signature (`repository_owner`), not merely by fields taken from elsewhere in the same untrusted payload. At minimum, `StatusHandler` and `PushHandler` (and other handlers resolving stacks/commits/repositories) should reject or ignore events whose `repository.owner.login`/`repository.full_name` does not match the `repository_owner` value used in `verify_signature`, ideally by passing the authenticated organization down to the handler layer and asserting equality before mutating any record.

### Proof of Concept
1. Attacker administers `attacker-org`, one of several organizations onboarded to a shared Shipit instance, and knows `secrets.github[:attacker_org][:webhook_secret]` (they configured it themselves per `docs/setup.md`).
2. Attacker crafts a `status` event JSON body with:
   - `organization.login` = `attacker-org` (or `repository.owner.login` = `attacker-org`) — used only to pick the verification secret,
   - `sha` = a real commit SHA belonging to `victim-org/victim-repo`'s tracked stack (observable publicly on GitHub),
   - `state` = `"success"`, plus required `context`/`description`.
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(attacker-org secret, body)>` and POSTs to `/webhooks` with `X-Github-Event: status`.
4. `verify_signature` resolves `repository_owner` = `attacker-org`, fetches `attacker-org`'s `GitHubApp`, and the signature validates successfully [1](#0-0) .
5. `StatusHandler#process` finds `Commit.where(sha: params.sha)` — the victim's commit — and calls `create_status_from_github!`, writing an attacker-controlled status onto a commit the attacker never had write access to [4](#0-3) .

**Note on confidence**: I was unable to locate and inspect `Shipit::Webhooks::Handler` (the shared base class defining the `stacks`/repository-resolution helper used by `PushHandler` and others) within the available tool budget, so the exact matching logic for `PushHandler`'s `stacks` scope (e.g., whether it additionally filters by `repository.full_name`, and whether that filter is itself independent of `repository_owner`) is not fully confirmed from source — `StatusHandler`'s installation-wide, unscoped `Commit.where(sha:)` lookup, however, is directly verified and is sufficient on its own to substantiate the cross-organization write.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
