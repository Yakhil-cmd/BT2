### Title
Duplicate leaves in `r of set` / `weighted and` address-definition conditions let one signature satisfy multiple "required" slots, bypassing intended multi-party threshold - ([File: definition.js])

### Summary
`QVBaseStrategy.reviewRecipients` lets one authorized reviewer's action be counted repeatedly against a threshold that was meant to require independent approvals from multiple distinct parties. The same root-cause pattern — a threshold-counting routine that counts "votes"/entries without verifying that each counted unit corresponds to a distinct, independent authority — exists in ocore's address-definition evaluator for the `r of set` and `weighted and` operators in `definition.js`.

### Finding Description
`validateDefinition`'s `evaluate()` function in `definition.js` implements the `r of set` and `weighted and` boolean-condition operators used inside address (and asset) spending-condition definitions: [1](#0-0) [2](#0-1) 

For both operators, the code iterates over `args.set`, evaluates each leaf independently for whether it "has a signature" (`bHasSig`), and simply counts how many leaves are satisfied, comparing against `args.required` (or `args.required` weight). Nowhere in `evaluate()`, nor in the earlier structural checks (`args.set.length < 2`, `args.required > args.set.length`, etc.), is there a check that the leaves in `args.set` are distinct sub-conditions (e.g., distinct pubkeys/addresses). A definition author can therefore construct a set such as:

```
["r of set", { required: 2, set: [
    ["sig", {pubkey: PUBKEY_A}],
    ["sig", {pubkey: PUBKEY_A}]   // duplicate leaf, same key
]}]
```

When such a definition is used to author a unit, `validateAuthentifiers` evaluates each leaf against its own authentifier path (`r.0`, `r.1`, …). Because ECDSA signatures over the same unit hash are deterministic-message/key-verifiable regardless of which JSON path they are attached to, the single actual signer can supply the very same signature bytes at both `r.0` and `r.1`, satisfying both duplicate leaves and thus meeting `required: 2` with only one private key. The "2 of N" threshold that other cosigners (in a shared/multisig address created via `wallet_defined_by_addresses.js` / `wallet_defined_by_keys.js`) believe protects the funds is silently reduced to "1 of N" for the party who included the duplicate.

The `weighted and` operator has the same gap — `args.set` elements are validated for `weight` positivity and total, but never for uniqueness of the underlying signing conditions.

### Impact Explanation
If a shared/multisig address is set up expecting M independent cosigner approvals (e.g., 2-of-3), but the definer/one participant sneaks in a duplicated leaf referencing their own key, that participant can unilaterally satisfy the `required` count and authorize spending of the shared funds without the cooperation of the other cosigners. This is a concrete unauthorized-spending / fund-theft path: it directly undermines the "shared address" security guarantee that is central to ocore's `wallet_defined_by_addresses.js` cosigning flow, and any code (e.g. `validateAddressDefinitionTemplate` in `wallet_defined_by_keys.js`) that is supposed to enforce a real multi-party consensus.

### Likelihood Explanation
Reachable purely through defining/creating an address (any user can define any address definition — this is inherent to the "address definitions and authentifiers" attack surface, no privileged network/hub role required) and then posting a unit signed with duplicated authentifier paths. The other reachable path is a malicious cosigner in a shared-address creation flow (`wallet_defined_by_addresses.js`'s `handleNewSharedAddress`), who proposes a definition containing the duplicate leaf; unless the other participants manually and carefully inspect the raw JSON tree for duplicated leaves (which is not automatically checked by any validation routine shown), they will approve it believing the stated `required` count enforces genuine multi-party consensus.

### Recommendation
In `evaluate()`'s handling of `r of set` and `weighted and` (definition.js), detect and reject duplicate sub-condition leaves within the same `set` (e.g., by canonicalizing/hashing each `arg` and checking for collisions before allowing the definition), or otherwise ensure that satisfying multiple counted slots requires genuinely distinct signing keys/authentifier material.

### Proof of Concept
1. Construct an address definition `D = ["r of set", {required: 2, set: [["sig", {pubkey: P}], ["sig", {pubkey: P}]]}]` where `P` is a single key controlled by the attacker (this passes `validateDefinition`'s structural checks: `set.length>=2`, `required<=set.length`).
2. Compute the address `A = chash160(D)`.
3. Have other honest cosigners believe `A` requires 2 independent signatures (e.g. presented as a 2-of-2/2-of-3 shared address) and fund it.
4. Author a unit spending from `A` with a single signature `S` from key `P`, placed at authentifier paths `r.0` and `r.1` (`authentifiers: {"r.0": S, "r.1": S}`).
5. `Definition.validateAuthentifiers`/`evaluate` will independently verify `S` against `P` at both paths, count `count_options_with_sig = 2`, satisfy `required: 2`, and validate the unit — allowing the attacker to spend funds alone despite the address nominally requiring 2 signers.
