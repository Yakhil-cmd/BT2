### Title
`OpenedHandler#provision?` operator-precedence bug bypasses `Repository#review_stacks_enabled` gate - (File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb)

### Summary
`OpenedHandler#provision?` intends to require `repository.review_stacks_enabled == true` for any provisioning to occur, but Ruby's `&&`/`||` precedence makes `review_stacks_enabled` only gate the `allow_all` branch, not the `allow_with_label` or `prevent_with_label` branches. An attacker who opens a PR from a fork and labels it appropriately can trigger creation and provisioning of a `Shipit::ReviewStack` even though the repository owner never enabled review stacks.

### Finding Description
The claimed binding is: `repository.review_stacks_enabled` (should be `true`) must equal the value actually enforced by `provision?` for the `allow_with_label`/`prevent_with_label` branches (currently unconstrained/`true` regardless).

```ruby
def provision?
  repository.review_stacks_enabled &&
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
``` [1](#0-0) 

Because `&&` binds tighter than `||`, this parses as:
`(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?)`.

So when `review_stacks_enabled == false` and `provisioning_behavior == 'allow_with_label'`, the second disjunct alone decides the outcome — `review_stacks_enabled` is never consulted. This is called from `respond_to_pull_request_opened?`, itself called from `process`, which on success immediately calls `ReviewStackAdapter#find_or_create!`: [2](#0-1) 

`find_or_create!` builds a new `Shipit::ReviewStack` from attacker-controlled `params.pull_request.head.ref` as the `branch`, then enqueues it for provisioning via `Shipit::ReviewStackProvisioningQueue.add(stack)`: [3](#0-2) 

**Attacker request:** Fork the target repo, push a branch, add the label matching `repository.provisioning_label_name` to their own PR, then send a `pull_request` `opened` webhook payload referencing that PR/label/branch to `POST /webhooks`.

**Why existing guards don't stop this:** webhook signature verification (`verify_signature`/`GitHubApp#verify_webhook_signature`) only proves the payload came from GitHub for that repository — it does not validate application-level authorization logic like `review_stacks_enabled`. The `ExplicitParameters` schema validates payload shape, not business rules. None of `force_github_authentication`, `User#authorized?`, `require_permission!`, or model validations on `Repository`/`Stack` reference `provision?`'s internal logic; they have no visibility into this bug. `NullRepository` also defines `review_stacks_enabled` returning `false` but is irrelevant here since a real repository record is fetched. This confirms the two sides of the binding diverge: `review_stacks_enabled == false` (owner's actual setting) vs. the value effectively required for the `allow_with_label` path (`true` is never checked — behaves as if it were `true`/irrelevant).

### Impact Explanation
Any external actor who can open a labeled PR against a repository configured with `provisioning_behavior: allow_with_label` (and a `provisioning_label_name`) can force Shipit to create and enqueue provisioning for a `Shipit::ReviewStack`, even though the repository owner explicitly disabled review stacks (`review_stacks_enabled: false`). This results in unauthorized creation of infrastructure/deploy records for a repository that never opted into this feature, matching "unauthorized deploy" under the Critical impact category. This is repeatable for every repository sharing this misconfiguration (`allow_with_label` + `review_stacks_enabled: false`) and for every PR/label combination an attacker controls on their own fork.

### Likelihood Explanation
Preconditions: `repository.review_stacks_enabled == false` and `repository.provisioning_behavior == 'allow_with_label'` with a `provisioning_label_name` set — an internally inconsistent but plausible configuration (e.g., an operator disables review stacks broadly while leaving the per-repo `provisioning_behavior` field at a non-default value, or migrates settings and forgets to reset it). Attacker cost is minimal: fork, open a PR, add a label they control, and the corresponding webhook is delivered by GitHub automatically. No secrets, tokens, or elevated GitHub permissions are required.

### Recommendation
Add explicit parentheses so `review_stacks_enabled` gates all branches:
```ruby
def provision?
  repository.review_stacks_enabled && (
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
  )
end
```

### Proof of Concept
Minitest under `test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb` (existing file, extend with a new case):
1. Create a `Shipit::Repository` with `review_stacks_enabled: false`, `provisioning_behavior: 'allow_with_label'`, `provisioning_label_name: 'deploy-preview'`.
2. Build a valid `pull_request` `opened` payload with `labels: [{ name: 'deploy-preview' }]` and `head.ref` set to an attacker-chosen branch name.
3. Assert before: `repository.review_stacks_enabled == false` and no `Shipit::ReviewStack` exists for the environment.
4. Call `OpenedHandler.new(payload).process`.
5. Assert after: `Shipit::ReviewStack.count` increased by 1 (or `Shipit::Stack.count` if review stacks inherit from `Stack`), proving `review_stacks_enabled == false` was not enforced against the effective gate (`true`) actually applied by `provision?`.
