### Title
Uncaught exception in real (non-dry-run) AA trigger execution can permanently halt stabilization and AA processing for the whole network - ([File: aa_composer.js])

### Summary
`aa_composer.handleTrigger()` (invoked by `handleAATriggers()` during main-chain stabilization from `writer.js`) is executed synchronously/asynchronously with numerous `throw Error(...)` statements scattered through the code for conditions the developers believed "can never happen" in a well-formed trigger/definition [1](#0-0) . Just like the audited contract that trusted `safeTransferFrom()` to always succeed and thus let an attacker-controlled bidder brick the whole auction house, ocore trusts that a stable, previously-validated AA definition/trigger combination will never hit one of these `throw Error` branches during real execution. The code explicitly acknowledges the risk by dry-running new triggers before committing them, with the comment "if it would crash, let it crash now, not when we execute the trigger for real" [2](#0-1) , but that dry-run protection is opt-in (`conf.bDryRunNewTriggers`), only covers *new* triggers hitting *already-known* AA addresses in the *unit being validated*, and does not protect against triggers arising later from secondary AA chains, remote-getter calls, or the state existing at the time of real stabilization diverging from the state during the dry run (different `mci`, `stateVars`, balances, or unrelated concurrent triggers that change global state, e.g. `count_signed_packages`, storage size, or parent-selection logic in `pickParents()`).

### Finding Description
Any uncaught `throw Error(...)` inside the real `handleTrigger()`/`sendUnit()`/`pickParents()`/`handleSecondaryTriggers()` execution path (triggered from `writer.js`'s post-commit `handleAATriggers()` call at stabilization time, not the pre-commit dry run) is not defensively caught. Examples include the invariant checks `throw Error("limci of last AA > mci")` and `throw Error("assocBalances and bAir do not match")` in `pickParents()`/`handleTrigger()` [3](#0-2) , and `throw Error("secondary triggers while bouncing")` in `handleSecondaryTriggers()` [4](#0-3) . These "should never happen" assumptions are the direct analog of trusting `onERC721Received()` to never revert: an attacker who can construct a specific combination of a nested/secondary AA definition (which is unprivileged - anyone can post an AA definition and any unprivileged unit poster can trigger it) and payment outputs can attempt to drive the AA composer into one of these unreachable-in-theory branches at the moment of real stabilization (post-commit `handleAATriggers()`), which is executed deterministically and identically on every full node [5](#0-4) . Because it happens deterministically for all full nodes processing the same stabilized MC unit, this is not a local crash but a network-wide processing halt: every full node crashes/throws at the same MCI, unable to progress past that point (analogous to the auction house being permanently bricked for every user, not just one).

### Impact Explanation
If reachable, this crashes the AA-trigger execution phase that happens after MC stabilization, inside `writer.saveJoint()`'s callback chain in `writer.js` [6](#0-5) . Because `handleAATriggers()` runs deterministically for every node once the underlying unit stabilizes, all full nodes would hit the identical `throw` at the same point, stalling stabilization and preventing the network from confirming any further units that depend on that MCI - satisfying "a network unable to confirm new units." Funds already locked in the affected AA(s) would also become permanently unreachable, matching the "AA fund loss or freezing" criterion.

### Likelihood Explanation
Likelihood is Medium: reaching one of these invariant-violation branches requires a very specific and currently unconfirmed combination of AA definitions/triggers (nested/secondary AA chains, state-var/balance edge cases, or bouncing timing), and I was not able to construct or verify a concrete unit/trigger sequence that trips one of these `throw Error` guards without deeper interactive analysis of `pickParents()`, `bAir`/`assocBalances` estimation flows, and the async ordering of `bBouncing`/secondary-trigger handling. The `bDryRunNewTriggers` mitigation reduces but does not eliminate the risk, since it only covers the primary trigger in the newly-submitted unit and not all downstream state transitions that occur at actual stabilization time.

### Recommendation
Wrap the real (non-dry-run) invocation of `handleTrigger()` from `handleAATriggers()`/`writer.js` in defensive error handling that converts unexpected internal invariant violations into a bounce/no-op response for that specific trigger (recording the unit as failed/bounced) instead of allowing an uncaught exception to propagate out of the deterministic stabilization path. Audit each `throw Error(...)` inside `aa_composer.js`'s real-trigger execution path (`pickParents`, `handleSecondaryTriggers`, `bounce`, `finish`) to determine whether it can be reached by attacker-supplied AA definitions/triggers, and convert genuinely reachable ones into `bounce()`/`revert()` calls rather than `throw`.

### Proof of Concept
Not constructed - identifying a concrete AA definition/trigger sequence that reaches one of the internal `throw Error` invariants in `pickParents()`/`handleSecondaryTriggers()`/`handleTrigger()` during real (non-dry-run) execution requires deeper interactive tracing of the async state machine (bAir/assocBalances estimation vs. real balances, bBouncing sequencing across secondary AAs, and MC parent selection edge cases) than could be completed within the available tool budget. This should be validated with a live/staging Devin session that can run the AA composer test harness (`test/aa_composer.test.js`) and attempt to craft a trigger unit that reaches one of the flagged `throw` statements.
