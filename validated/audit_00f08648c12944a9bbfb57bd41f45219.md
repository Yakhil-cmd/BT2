### Title
Webhook signature verification and payload handler resolve organization identity from different JSON paths, allowing cross-organization stack mutation - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#repository_owner` picks the organization used to select which `GitHubApp#webhook_secret` verifies the HMAC, but it silently falls back to the top-level `organization.login` field whenever `repository.owner.login` is absent, while the actual event handler (`ClosedHandler#repository`) resolves the repository to act on strictly from `repository.full_name`. Because these two lookups read different JSON paths, an attacker who owns a legitimate organization (and therefore knows its own configured `webhook_secret`) can sign a payload with their own org's secret while embedding an arbitrary victim `repository.full_name`, causing Shipit to mutate a victim organization's stack under a signature that only proves authenticity of the attacker's own org.

### Finding Description
The broken binding is: **organization whose secret HMAC-verifies the request** (`repository_owner` in `verify_signature`) **== organization that owns the repository the handler mutates** (`repository.full_name`'s owner in the handler). This does not hold.

- `repository_owner` (`app/controllers/shipit/webhooks_controller.rb:59-62`) does:
  `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`
- `verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-30`) uses that value to select `Shipit.github(organization: repository_owner)` and then calls `GitHubApp#verify_webhook_signature` (`lib/shipit/github_app.rb:76-83`), which just computes `OpenSSL::HMAC.hexdigest('sha1', webhook_secret, message)` over the *entire raw body* using the secret configured for whatever organization name was picked.
- `Shipit::Webhooks::Handlers::PullRequest::ClosedHandler#repository` (`app/models/shipit/webhooks/handlers/pull_request/closed_handler.rb:49-53`) instead resolves the target repository purely from `params.repository.full_name`, independent of whatever value `verify_signature` used.
- The handler's `ExplicitParameters` schema (`closed_handler.rb:8-39`) only `requires :repository do requires :full_name, String end` — it never requires `repository.owner.login`, so a payload can legally omit `repository.owner` while still supplying `repository.full_name`.

Exploit: an attacker who administers their own GitHub org (`attacker-org`) knows that org's `webhook_secret` as configured in Shipit (they set it up themselves when wiring their own org's webhook). They send `POST /webhooks` directly to the Shipit host (bypassing GitHub) with `X-Github-Event: pull_request` and a body such as:
```json
{
  "action": "closed",
  "number": 1,
  "pull_request": { ... },
  "organization": { "login": "attacker-org" },
  "repository": { "full_name": "victim-org/repo" },
  "sender": { "login": "attacker" }
}
```
Because `repository.owner.login` is absent, `repository_owner` returns `"attacker-org"` via the fallback at line 61. `verify_signature` therefore verifies the HMAC against `attacker-org`'s secret — which the attacker can compute correctly since they know that secret. The request passes. `Shipit::Webhooks.for_event('pull_request')` handlers, including `ClosedHandler`, are invoked with the raw parsed body; `ClosedHandler#repository` loads `Shipit::Repository.from_github_repo_name('victim-org/repo')` and calls `review_stack.archive!`, mutating the victim's stack.

None of the existing guards stop this: `drop_unhandled_event` only checks that handlers exist for the event name, not the payload shape; `verify_signature` only checks the HMAC against whichever org name it derived, without checking that name matches `repository.full_name`'s owner; the handler's `ExplicitParameters` schema validates field presence/types, not organizational consistency.

### Impact Explanation
An attacker with a legitimate, but unprivileged (from Shipit's perspective), GitHub organization can forge a `pull_request` (or any other event whose handler resolves repository from `repository.full_name` while `verify_signature` can be pointed at a different org) webhook that is authenticated with their own org's secret yet acts on an arbitrary victim organization's repository/stack. In the `ClosedHandler` case this results in an unauthorized `review_stack.archive!` on the victim's stack — an unauthorized write to another tenant's resource. This is repeatable for every request and against any repository whose full name the attacker knows, matching the Critical category "a payload for one repository mutating another's stack."

### Likelihood Explanation
Preconditions: the attacker must control at least one GitHub organization that is configured in Shipit with its own `webhook_secret` (this is a normal, low-privilege configuration state — any org onboarded to Shipit has one, and the org's own administrator/attacker knows it, since they configured it when wiring GitHub webhooks). The attacker needs no Shipit session, API token, or victim-org secrets — just knowledge of the victim's `owner/repo` full name, which is public. The request is a single unauthenticated HTTP POST to `/webhooks`, fully repeatable and requiring no live GitHub interaction.

### Recommendation
Make `verify_signature` and the handler agree on a single, unambiguous source of organization identity. Concretely:
- Require `repository.owner.login` (or `repository.full_name`) to be present and use the *same* path consistently in `repository_owner` that handlers use to resolve the target repository; do not silently fall back to `organization.login` for events whose registered handlers key off `repository.full_name`.
- After determining the verifying organization, assert that it matches the owner embedded in `repository.full_name` before dispatching to handlers, rejecting (422) on mismatch.
- Alternatively, verify the signature using the organization derived by parsing `repository.full_name` first when a `repository` key is present, only falling back to `organization.login` for events that are exclusively organization-scoped (e.g. real GitHub `membership`/`organization` events) and never for repository-mutating events.

### Proof of Concept
Minitest plan (`test/controllers/webhooks_controller_test.rb` style — for review, not to be added under `test/`):
1. Configure two orgs in `Shipit.github_configuration` fixture-style: `attacker-org` with a known `webhook_secret_a`, and `victim-org` (repository `victim-org/repo` with an existing `Stack`/review stack).
2. Build a `pull_request` `action: "closed"` payload where `organization.login == "attacker-org"`, `repository.full_name == "victim-org/repo"`, and `repository` has no `owner` key.
3. Compute `X-Hub-Signature` as `"sha1=" + OpenSSL::HMAC.hexdigest('sha1', webhook_secret_a, raw_body)`.
4. `post :create, body: raw_body, headers: { 'X-Github-Event' => 'pull_request', 'X-Hub-Signature' => signature }`.
5. Assert response is `200 OK` (not `422`), and assert **before**: `victim_stack.review_stack.active? == true`; **after**: `victim_stack.review_stack.reload.active? == false` (archived) — proving `attacker-org`'s secret authorized a mutation on `victim-org`'s stack, violating the binding `repository_owner (verifier) == repository.full_name owner (mutated)`.     def verify_webhook_signature(signature, message)
```ruby
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
