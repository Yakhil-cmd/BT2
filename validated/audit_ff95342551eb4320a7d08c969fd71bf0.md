### Title
Check-then-act race on `count_aa_responses` allows a second primary AA trigger from the same unit before the first trigger's completion is recorded - (File: aa_composer.js)

### Summary
The reported bug is a classic check-then-act reentrancy: `propose()` in GovernorBravo checks `latestProposalIds[msg.sender]` for an active proposal, but that state is only set *after* the external, attacker-controllable call inside `_isHighRiskProposal` returns, so a reentrant call to `propose()` sees stale state and bypasses the "one active proposal" invariant. The equivalent structural weakness in `ocore` is the "second primary trigger from the same unit" guard in `aa_composer.js`, which checks a cached counter (`storage.assocStableUnits[trigger.unit].count_aa_responses`) that is only updated in memory and in the DB *after* the entire (potentially long, deeply recursive) trigger-handling chain for the earlier AA call from that same unit has fully completed and committed.

### Finding Description
`handleTrigger()` enforces that a single triggering unit cannot be used to invoke more than one primary AA response: [1](#0-0) 

This check reads `storage.assocStableUnits[trigger.unit].count_aa_responses`, an in-memory cache value. That value is only incremented once the *entire* asynchronous processing of the first primary trigger for that unit — including all secondary (cascading) AA triggers, `evaluateAA`, `sendUnit`, `validateAndSaveUnit`, and `handleSecondaryTriggers` — has fully finished and its database transaction has been committed: [2](#0-1) 

Between the moment the first row's `handleTrigger` begins (count still 0/`undefined`) and the moment `objUnitProps.count_aa_responses` is finally incremented after `batch.write`/`COMMIT`, any other code path that reads/uses `trigger.unit`'s response count against the cache will see the pre-update value. `handleAATriggers()` iterates all `aa_triggers` rows (which can include multiple rows for the *same* `mci`+`unit` but different target AA `address`, e.g. when one funding unit pays several AA addresses) using `async.eachSeries`: [3](#0-2) 

Under normal sequential execution this ordering is safe because `eachSeries` waits for each row's callback before starting the next. The invariant, however, depends entirely on the *timing* of when `count_aa_responses` is written back to `storage.assocStableUnits`, not on any lock tied to the triggering unit itself. `handleTrigger`/`handleSecondaryTriggers` recursively call back into `handleTrigger` for every AA reachable through cascading payments from the same original unit, and those secondary calls run to completion, post new units, and can themselves cause further stabilization and additional `aa_composer.handleAATriggers()` invocations from `writer.js`'s stabilization loop before the *outer* transaction that would set `count_aa_responses` for the original trigger unit is committed: [4](#0-3) 

Because the guard is a read of a value that is written back only long after the check executes (mirroring the Bravo `latestProposalId` bug, where the check happens before the state that would prevent re-entry is persisted), any path that lets a second `aa_triggers` row for the same `unit` be evaluated by a fresh `handleAATriggers()`/`handlePrimaryAATrigger()` invocation while the first is still in-flight will not observe the "second primary trigger" guard and will process it as if it were the first.

### Impact Explanation
If the "one primary AA response per triggering unit" invariant can be bypassed, a single payment/trigger unit could fund or invoke more than one primary AA response than the protocol design allows. This directly affects AA fund accounting (`assocBalances`, `aa_balances` table) and the deterministic, once-only semantics nodes are supposed to agree on for a given trigger unit. If different nodes process the recursive stabilization/trigger queue in different orders (which is plausible, since it depends on connection pool scheduling of async database operations rather than a strict per-unit lock), different nodes could compute different sets of AA responses for the same trigger unit, causing consensus-relevant disagreement about which AA state changes and units are valid — i.e., a High severity node-disagreement / fund-accounting risk analogous to the referenced governance bug's "multiple active items from one identity" defect.

### Likelihood Explanation
The `aa_triggers` table can genuinely contain multiple rows sharing the same `mci`+`unit` (one row per receiving AA address the same unit pays), so the exact scenario the guard is meant to prevent is reachable purely by constructing a unit that pays two or more AA addresses — no privileged access is required, any user can post such a unit. The only uncertainty is whether the current locking (`mutex.lock(['aa_triggers'])` in `handleAATriggers`, and per-address-set locks in `validation.js`) is sufficient in all recursive/nested-stabilization code paths to fully serialize processing of same-unit rows so the in-memory counter is always updated before the next row for that unit is evaluated. Given the multiple nested async chains (`handleSecondaryTriggers` → `handleTrigger` → `sendUnit` → `validateAndSaveUnit` → stabilization → `writer.js`'s `advanceMcStability` loop → `aa_composer.handleAATriggers()` again), and that `count_aa_responses` is written only at the very end of the *outer* trigger's flow, likelihood is assessed as Medium-High: it requires a specific interleaving/recursion depth to manifest, which cannot be fully confirmed without dynamic tracing of the mutex/connection scheduling, but the code structure shows the same check-then-act pattern flagged as high risk in the original report.

### Recommendation
Move the "second primary trigger from the same unit" check to occur transactionally with its own state update (e.g., use a DB-level `UPDATE ... WHERE count_aa_responses IS NULL/0` guarded increment inside the same transaction that begins processing the trigger, or acquire a mutex keyed specifically on `trigger.unit` for the whole duration of `handlePrimaryAATrigger`, not just on the global `'aa_triggers'` key) so that the check-and-increment is atomic with respect to any other row referencing the same triggering unit, eliminating the window where a second row for the same unit can be evaluated before the first row's completion is recorded.

### Proof of Concept
Not independently confirmed with a runnable test; note is a structural analog derived from static analysis of `aa_composer.js` and `writer.js`. A dynamic PoC would need to: (1) create a unit with payment outputs to two different AA addresses (`A` and `B`), producing two `aa_triggers` rows for the same `unit`; (2) craft AA `A`'s definition so that its response cascades through many chained secondary AA triggers and/or triggers new unit stabilizations that cause `writer.js`'s `advanceMcStability`/`handleAATriggers` loop to re-enter before `A`'s own outer `handlePrimaryAATrigger` transaction commits and updates `count_aa_responses`; (3) observe whether `B`'s trigger row is processed as a valid primary trigger (i.e., does not hit `'a second primary trigger from the same unit is not allowed'`) despite `A`'s trigger for the same unit still being in flight. This step (3) would need to be exercised against the actual mutex/connection-pool behavior to confirm exploitability, which could not be verified from static code reading alone.
