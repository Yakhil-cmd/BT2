## Title
Webhook signature is validated against the organization derived from `repository.owner.login`, but event handlers act on the completely independent `repository.full_name` field, allowing cross-organization stack writes in multi-org Shipit deployments - (`File: app/controllers/shipit/webhooks_controller.rb`)

### Summary
In a multi-organization Shipit configuration (`secrets.github` keyed by org, see `lib/shipit.rb` `github_app_config`/`github_organizations`), `WebhooksController#verify_signature` selects *which organization's* `webhook_secret` to HMAC-verify against using an unauthenticated payload field (`repository.owner.login`), while every event `Handler` resolves the *stack/repository to act on* using a different, equally unauthenticated payload field (`repository.full_name`). Because these two fields are never cross-checked, an attacker who legitimately administers one connected GitHub organization (and therefore knows that org's own `webhook_secret`, which they configured themselves) can forge a validly-signed webhook whose signature authenticates as "my org" but whose payload body targets a victim organization's repository tracked by the same Shipit instance.

### Finding Description
`verify_signature` picks the GitHub App/secret based on the payload's own claim about which org is sending the event: [1](#0-0) 

`repository_owner` is read straight from the untrusted JSON body: [2](#0-1) 

`Shipit.github(organization: repository_owner)` resolves to a `GitHubApp` instance holding that specific organization's `webhook_secret` (configured independently per org): [3](#0-2) [4](#0-3) 

`verify_webhook_signature` only proves that the *entire raw body* was HMAC-signed with **that org's** secret — it says nothing about which repository the body's other fields refer to. Once verification passes, the raw payload is dispatched unmodified to handlers: [5](#0-4) 

Every handler then determines which `Stack`/`Repository` to mutate from a **different** field of the same attacker-controlled body, `repository.full_name`, with no relation back to `repository.owner.login`: [6](#0-5) 

For example, `PushHandler` uses that resolved repository's stacks to trigger a resync straight from attacker-supplied `after`/`ref`: [7](#0-6) 

The equality that should hold but doesn't:
`organization whose secret authenticated the signature (repository.owner.login)` == `organization/repository the handler actually writes to (repository.full_name)`.

Before the attacker's request: only genuine GitHub-originated webhooks for org X, signed with org X's secret, ever reference org X's own repositories (GitHub itself keeps these fields consistent).
After the attacker's request: the attacker (who administers org "OrgB", connected via a separate GitHub App entry with its own `webhook_secret` that the attacker set themselves) POSTs directly to `/webhooks` with `repository.owner.login = "OrgB"` (so the org-secret lookup and HMAC succeed) but `repository.full_name = "OrgA/victim-repo"` (a stack belonging to a different tenant/org entirely). `verify_signature` passes; the handler for `push` (or `status`, `check_suite`, `membership`, etc.) then acts on `OrgA/victim-repo`'s stacks.

### Impact Explanation
This is Critical: it enables cross-organization/cross-repository writes and unauthorized deploy triggers without any credential belonging to the victim organization. A forged `push` event forces `stack.sync_github(expected_head_sha:)` on a victim stack; combined with continuous deployment settings this can push an unreviewed/attacker-chosen SHA into the deploy pipeline. A forged `status`/`check_suite` event can flip CI state recorded for a victim commit, which downstream continuous-deployment logic treats as green, resulting in an unauthorized deploy. A forged `membership` event can create/delete `Membership` records tying arbitrary GitHub logins to `Shipit.github_teams`, potentially escalating an attacker's own or a colluding account's access to the victim's teams, which govern `current_user.authorized?`. All of this is reachable purely because the org used to select the verifying secret and the repository the payload is applied to are two independently attacker-controlled fields in the same unauthenticated JSON body.

### Likelihood Explanation
Requires a multi-organization Shipit deployment (documented and supported via `secrets.github` keyed by org name, see `docs/setup.md` and `lib/shipit.rb#github_app_config`) where the attacker administers at least one of the connected orgs (and thus legitimately possesses that org's own `webhook_secret`, which is not a leak of the victim's or Shipit's core secret — it's a secret the attacker set up themselves). Given that Shipit explicitly supports and documents this multi-org configuration shape, this is a realistic deployment topology, not a theoretical one.

### Recommendation
Bind signature verification and target-resolution to the same identity: after computing `Repository.from_github_repo_name(payload.dig('repository','full_name'))` (or equivalent), verify that its owning organization matches `repository_owner` used to select the `webhook_secret`, and reject the request otherwise. Alternatively, verify the signature using the `webhook_secret` associated with the *resolved* repository/stack (not the raw payload's claimed owner), so the signing key is tied to the entity actually being written to.

### Proof of Concept
1. Configure Shipit with two orgs, `OrgA` (victim, has a stack `OrgA/victim-repo`) and `OrgB` (attacker-administered, attacker knows `OrgB`'s `webhook_secret` because they configured the GitHub App themselves).
2. Attacker crafts a `push` event JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>",
  "repository": { "owner": { "login": "OrgB" }, "full_name": "OrgA/victim-repo" }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(OrgB_webhook_secret, raw_body)` and POSTs it to `/webhooks` with `X-Github-Event: push`.
4. `WebhooksController#verify_signature` resolves `Shipit.github(organization: "OrgB")` and successfully verifies the signature using `OrgB`'s secret (`lib/shipit/github_app.rb#verify_webhook_signature`).
5. `Shipit::Webhooks.for_event('push')` dispatches to `PushHandler`, which resolves stacks via `payload.dig('repository','full_name')` → `"OrgA/victim-repo"` and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")`, acting on the victim organization's stack despite the signature only proving authorization as `OrgB`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
