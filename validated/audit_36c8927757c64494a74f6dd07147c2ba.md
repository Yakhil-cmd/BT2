Based on my investigation, I've confirmed the relevant analog in ocore's `spender_attested` asset mechanism.

### Title
Spender-attestation check in payment validation dynamically re-verifies current attestation status at spend time, freezing previously-legitimate asset holdings whenever the attestor changes the attestor list or fails to re-attest after a definition change - ([File: validation.js])

### Summary
Notional's `checkValidMaturity` performs a strict validity check (`!isIdiosyncratic`) intended to protect the AMM trade path, but the check is unconditionally applied even to accounts that don't need to trade fCash at all (zero-debt exits), permanently blocking a legitimate, harmless action for as long as the external state (market structure) remains in the disallowed condition. The analogous pattern in ocore is `spender_attested` assets: every payment input/output spending such an asset is validated against the *current* (as of `last_ball_mci`) attestation state via `storage.loadAssetWithListOfAttestedAuthors` / `storage.filterAttestedAddresses`, rather than the attestation state at the time the balance was received [1](#0-0) . This means a wallet holding a perfectly legitimately-acquired balance can become permanently unable to spend/exit it if the current external attestation state changes, even though the holder did nothing wrong.

### Finding Description
`validatePayment` loads the asset together with the list of currently-attested authors and requires the spending author(s)/owner(s) to be attested *right now*, not at the time the coins were received [2](#0-1) [1](#0-0) . The same live re-check is repeated per-input when validating each transfer input's owner address [3](#0-2)  and for private fixed-denomination transfers [4](#0-3) , and again on the output side for non-transferrable assets [5](#0-4) .

The attestation lookup (`filterAttestedAddresses`) requires a stable attestation from one of the asset's *current* attestors that is more recent than the address's last definition change [6](#0-5) . The current attestor set itself is not fixed at asset-definition time either — the definer can update it at any point via an `asset_attestors` message [7](#0-6) , and `readAsset` always resolves to the *latest* attestor-list unit when loading the asset [8](#0-7) .

Consequently, a holder who was properly attested when they received the asset can become permanently unable to spend it if:
- the definer replaces the attestor list and the new attestor(s) never (re-)attest the holder, or
- the holder rotates their address definition (e.g., after a suspected key compromise) and the previous attestation predates that change, requiring a fresh attestation that may never come.

In both cases there is no fallback path in `validatePaymentInputsAndOutputs`/`validatePayment` that allows a holder to exit or move their own funds without satisfying the live attestation check — exactly analogous to `lendToExitVault` having no path to exit without passing `checkValidMaturity`. The check that is meant to gate *new* issuance/acquisition of the restricted asset (KYC-style control at receipt) is instead re-applied on every subsequent spend, indefinitely, based on state the holder does not control.

### Impact Explanation
Any holder of a `spender_attested` asset can have their balance permanently frozen through no fault of their own, purely because of a definer/attestor-side action (attestor list change, attestor going dark, or the holder's own necessary key-rotation not being immediately matched by a fresh attestation). This is a fund-freezing condition reachable by an asset issuer with no cooperation from, or wrongdoing by, the token holder, matching the High-severity impact class ("AA fund loss or freezing" / inability to exit) described in the source report.

### Likelihood Explanation
This requires no attacker-controlled malicious input beyond ordinary use of the documented `asset_attestors` feature by the asset's own definer, or ordinary use of address-definition-change by the holder (e.g. for security hygiene). Both are first-class, commonly-used features (`asset_attestors` message, `address_definition_changes` mechanism), so the freezing condition can arise from routine, non-adversarial operations, making likelihood moderate-to-high wherever `spender_attested` assets with real economic value are used.

### Recommendation
Decouple "may this asset be spent by its current owner" from "is the owner attested right now." Options include:
- Evaluate spender-attestation only at issuance/first-transfer time, and have the protocol persist an "attested-at-acquisition" flag on the output that is honored on subsequent spends by the same owner, rather than re-querying live attestor state on every spend as done today in `validatePaymentInputsAndOutputs` [9](#0-8) .
- Alternatively, provide an explicit unattested "exit-only" path (e.g., mandatory transfer-to-definer or burn) that bypasses the attestation check, analogous to the report's recommendation to let Notional's `exitVault` bypass the trade/maturity check for debt-free exits.

### Proof of Concept
1. Definer issues a `spender_attested` asset with attestor `A`; `A` attests holder `H`; `H` receives a payment output of this asset — valid per `validatePayment` since `H` is in `objAsset.arrAttestedAddresses` [1](#0-0) .
2. Definer posts a new `asset_attestors` message replacing attestor `A` with attestor `B` [7](#0-6) .
3. `B` never attests `H` (attestor is offline, non-cooperative, or simply hasn't gotten to it).
4. `H` attempts to spend/transfer their previously-received, legitimately-held balance. `loadAssetWithListOfAttestedAuthors` now resolves the asset's `arrAttestorAddresses` to `[B]` only [8](#0-7) , `filterAttestedAddresses` finds no attestation by `B` for `H`, so `arrAttestedAddresses` is empty, and `validatePayment` rejects the unit with `"none of the authors is attested"` [10](#0-9) . `H`'s funds are stuck with no way to exit as long as `B` withholds attestation.

function validateAttestorListUpdate(conn, payload, objUnit, objValidationState, callback){
	if (objUnit.authors.length !== 1)
		return callback("attestor list must be single-authored");
	if (!isNonemptyObject(payload))
		return callback("attestor update must be a non-empty object");
	if (hasFieldsExcept(payload, ['asset', 'attestors']))
		return callback("foreign fields in attestor list update");
	storage.readAsset(conn, payload.asset, objValidationState.last_ball_mci, false, function(err, objAsset){
		if (err)
			return callback(err);
		if (!objAsset.spender_attested)
			return callback("this asset does not require attestors");
		if (objUnit.authors[0].address !== objAsset.definer_address)
			return callback("attestor list can be edited only by definer");
		err = checkAttestorList(payload.attestors);
		if (err)
			return callback(err);
		callback();
	});
}
