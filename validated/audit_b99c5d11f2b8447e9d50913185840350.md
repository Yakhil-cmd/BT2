**Analysis:** In `scripts/sweep.ts`, the `endpoint` string passed to `githubRequest` is always constructed via template literals like `` `/repos/${owner}/${repo}/issues/${issue.number}` `` [1](#0-0) , and the request URL is built as `` `https://api.github.com${endpoint}` `` [2](#0-1) . The `https://api.github.com` host prefix is a hardcoded literal in the template, not a variable — no amount of attacker-controlled content concatenated after it can change the resolved authority/host of the URL, since string concatenation onto a fixed prefix cannot produce an absolute URL redirect (e.g. appending `evil.com` just yields `https://api.github.comevil.com`, still resolving under the `api.github.com` authority, not a separate host).

Additionally, the only attacker-influenceable values reaching the endpoint are `issue.number` (an integer field from GitHub's own API response, not raw text the attacker supplies) and `label` (drawn from the fixed internal `lifecycle` config array, not from issue content) [3](#0-2) . `owner`/`repo` come from `GITHUB_REPOSITORY_OWNER`/`GITHUB_REPOSITORY_NAME` environment variables set by the workflow runner, not from issue/PR content [4](#0-3) . There is no code path where issue title, body, reactions, or comment text is interpolated into the `endpoint` string at all — those fields are only read for comparison/logging purposes (e.g. `issue.title`, `issue.reactions["+1"]`, `comments.some(...)`) [5](#0-4) [6](#0-5) .

Since neither the host is variable nor is any attacker-supplied free-text field concatenated into the endpoint, there is no reachable path for an unprivileged issue/PR commenter to redirect the `fetch` call or leak the `Authorization: Bearer` token to an external endpoint.
