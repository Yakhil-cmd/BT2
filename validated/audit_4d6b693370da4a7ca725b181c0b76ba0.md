### Title
Missing zero-check on pool reserves before division in `token_price_x32` causes a swap-halting panic and can permanently freeze pool liquidity - (File: `programs/cp-swap/src/states/pool.rs`)

### Summary
`PoolState::token_price_x32` divides the pool's net token reserves directly with the raw `/` operator, without any check that either operand is non‑zero, unlike every other arithmetic path in the program which uses `checked_*` helpers and returns an `Option`/`Result`. This is reachable from `swap_base_input` and `swap_base_output` on every single swap, and a net reserve of zero on one side is achievable through normal, unprivileged LP withdrawal rounding, causing an unrecoverable panic and permanent inability to swap or re-deposit into the affected side of the pool.

### Finding Description
`token_price_x32` computes the oracle-observation prices for both sides of the pool by dividing the *net* (fee-excluded) reserves: [1](#0-0) 

Both `token_0_amount` and `token_1_amount` come from `vault_amount_without_fee`, which simply does a `checked_sub` of accrued protocol/fund/creator fees from the raw vault balance and returns whatever remains (including zero): [2](#0-1) 

`token_price_x32` is invoked unconditionally on every swap through `get_swap_params`, which is called at the very start of `swap_base_input` and `swap_base_output`, before the actual swap math executes: [3](#0-2) [4](#0-3) 

If either `total_input_token_amount` or `total_output_token_amount` is `0`, the plain `/` operator panics with a division-by-zero trap — the exact same bug class as the referenced `YTokenL2` report, just triggered by pool reserves instead of an oracle price.

A net reserve of exactly zero for one token side is reachable by an unprivileged LP through normal withdrawal rounding. `initialize` permanently "locks" `lock_lp_amount = 100` LP units by minting only `liquidity - lock_lp_amount` to the creator while setting `pool_state.lp_supply = liquidity` (the full, un-discounted amount): [5](#0-4) 

Because only `liquidity - lock_lp_amount` LP tokens are actually mintable/burnable, `pool_state.lp_supply` can never be driven below `lock_lp_amount` (100) through legitimate burns via `withdraw`. However, `withdraw` computes the trading-token amounts to return with a **floor**-rounded ratio (`RoundDirection::Floor`): [6](#0-5) [7](#0-6) 

When the last redeemable LPs (`lp_supply - lock_lp_amount` tokens) are burned, the returned `token_0_amount`/`token_1_amount` is `floor(burn_amount * reserve / lp_supply)`. Because `lock_lp_amount` (100) is a fixed, small residual relative to `lp_supply` (which scales with `sqrt(reserve_0 * reserve_1)`), it is straightforward for one side's remaining "locked" reserve fraction to floor to `0` while the other side still holds a nonzero balance (e.g. highly imbalanced reserves, or reserves with very different decimal magnitudes). At that point `vault_amount_without_fee` legitimately returns `0` for that token, and the pool is left with `total_token_0_amount == 0` (or `total_token_1_amount == 0`) while `lp_supply == lock_lp_amount > 0` and while the vault may still hold real, un-collected token balance.

### Impact Explanation
Once one side's net reserve is `0`:
- Any subsequent call to `swap_base_input` or `swap_base_output` panics inside `token_price_x32`, permanently reverting/aborting all swaps on that pool.
- `deposit` cannot repair the pool either: `lp_tokens_to_trading_tokens` computes required deposit amounts proportionally to the existing (zero) reserve, so `results.token_0_amount` (or `token_1_amount`) is always `0`, and the instruction immediately rejects with `ZeroTradingTokens`: [8](#0-7) 

This permanently bricks the pool's core AMM function (swap) and blocks the only mechanism (deposit) that could otherwise restore reserves, freezing any remaining/un-collected token balance and locked LP value in the vaults with no recovery path through user-facing instructions.

### Likelihood Explanation
This requires no privileged access — any LP performing a full/near-full withdrawal on a pool with sufficiently skewed or small reserves (relative to `lp_supply`) can trigger the floor-rounding edge case, and any subsequent unprivileged swapper submitting a normal `swap_base_input`/`swap_base_output` transaction triggers the panic. No malicious validator, off-chain component, or special build feature is needed — only ordinary sequences of `withdraw` followed by `swap`.

### Recommendation
Add explicit zero-checks (mirroring the pattern already used via `CurveCalculator::validate_supply` at pool initialization) before performing the divisions in `token_price_x32`, returning a graceful error (e.g., a new `ErrorCode::ZeroReserve` or reusing `ZeroTradingTokens`) instead of allowing the raw `/` operator to panic. Additionally, consider preventing `withdraw` from floor-rounding a side's reserve down to `0` while `lp_supply` remains above zero (e.g., reject withdrawals that would leave one side's tracked reserve at exactly zero), matching the intent of the existing minimum-liquidity lock.

### Proof of Concept
1. Initialize a pool with imbalanced reserves (e.g., `init_amount_0` very small relative to `init_amount_1`, or with disparate token decimals) so that `sqrt(reserve_0 * reserve_1)` (i.e., `lp_supply`) is large relative to `reserve_0`.
2. As the sole/majority LP, call `withdraw` for `lp_token_amount = owner_lp_token.amount` (all redeemable LP tokens, i.e., `lp_supply - 100`).
3. Because `lp_tokens_to_trading_tokens` uses `RoundDirection::Floor`, the returned `token_0_amount` can floor to a value that leaves the pool's `vault_amount_without_fee` result for token_0 equal to `0` after the withdrawal completes (verify via emitted `LpChangeEvent`/subsequent vault balances).
4. Call `swap_base_input` (or `swap_base_output`) on the pool with any input amount — the transaction panics inside `token_price_x32`'s division (`token_1_amount as u128 * Q32 as u128 / token_0_amount as u128`) because `token_0_amount == 0`.
5. Attempt `deposit` to restore liquidity — it fails with `ZeroTradingTokens` because the proportional calculation against a zero reserve always yields `0` for that token, permanently blocking recovery.

            .protocol_fees_token_0
            .checked_add(self.fund_fees_token_0)
            .ok_or(ErrorCode::MathOverflow)?
            .checked_add(self.creator_fees_token_0)
            .ok_or(ErrorCode::MathOverflow)?;
        let fees_token_1 = self
            .protocol_fees_token_1
            .checked_add(self.fund_fees_token_1)
            .ok_or(ErrorCode::MathOverflow)?
            .checked_add(self.creator_fees_token_1)
            .ok_or(ErrorCode::MathOverflow)?;
        Ok((
            vault_0
                .checked_sub(fees_token_0)
                .ok_or(ErrorCode::InsufficientVault)?,
            vault_1
                .checked_sub(fees_token_1)
                .ok_or(ErrorCode::InsufficientVault)?,
        ))
    }

    pub fn token_price_x32(&self, vault_0: u64, vault_1: u64) -> Result<(u128, u128)> {
        let (token_0_amount, token_1_amount) = self.vault_amount_without_fee(vault_0, vault_1)?;
        Ok((
            token_1_amount as u128 * Q32 as u128 / token_0_amount as u128,

    pub fn get_swap_params(
        &self,
        input_vault_key: Pubkey,
        output_vault_key: Pubkey,
        input_vault_amount: u64,
        output_vault_amount: u64,
    ) -> Result<SwapParams> {
        let (
            trade_direction,
            total_input_token_amount,
            total_output_token_amount,
            token_0_price_x64,
            token_1_price_x64,
            is_creator_fee_on_input,
        ) = if input_vault_key == self.token_0_vault && output_vault_key == self.token_1_vault {
            let (total_input_token_amount, total_output_token_amount) =
                self.vault_amount_without_fee(input_vault_amount, output_vault_amount)?;
            let (token_0_price_x64, token_1_price_x64) =
                self.token_price_x32(input_vault_amount, output_vault_amount)?;

            (
                TradeDirection::ZeroForOne,
                total_input_token_amount,
                total_output_token_amount,
                token_0_price_x64,
                token_1_price_x64,
                self.is_creator_fee_on_input(TradeDirection::ZeroForOne)?,
            )
        } else if input_vault_key == self.token_1_vault && output_vault_key == self.token_0_vault {
            let (total_output_token_amount, total_input_token_amount) =
                self.vault_amount_without_fee(output_vault_amount, input_vault_amount)?;
            let (token_0_price_x64, token_1_price_x64) =
                self.token_price_x32(output_vault_amount, input_vault_amount)?;

            (
                TradeDirection::OneForZero,
                total_input_token_amount,
                total_output_token_amount,
                token_0_price_x64,
                token_1_price_x64,
                self.is_creator_fee_on_input(TradeDirection::OneForZero)?,
            )
        } else {
            return err!(ErrorCode::InvalidVault);
        };
        Ok(SwapParams {
            trade_direction,
            total_input_token_amount,
            total_output_token_amount,
            token_0_price_x64,
            token_1_price_x64,
            is_creator_fee_on_input,
        })
    }
