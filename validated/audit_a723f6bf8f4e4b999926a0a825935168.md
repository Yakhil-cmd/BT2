### Title
Api::CCMenuController bypasses ApiClient stack scoping, letting a stack-scoped token read any stack's CI status - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Api::CCMenuController#stack` (used by `GET /api/stacks/*stack_id/ccmenu`) resolves the target stack with `Stack.from_param!(params[:stack_id])`, ignoring the `ApiClient#stack_id` scoping that every other API controller enforces via `BaseController#stacks`/`stack`. This breaks the binding "stack a token authorizes == stack a request touches."

### Finding Description
`Api::BaseController` defines the canonical scoping helpers used by the rest of the API surface: [1](#0-0) 

```
def stacks
  @stacks ||= current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all
end

def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```

An `ApiClient` created scoped to a single stack (`stack_id` set, e.g. via `Api::StacksController` or the UI) is meant to only ever resolve stacks matching that id — this is exactly the scoping used and tested by `Api::StacksController`, `Api::TasksController`, `Api::DeploysController`, `Api::LocksController`, etc., all of which call the inherited `stack`/`stacks` helpers.

`Api::CCMenuController`, however, overrides `stack` and completely discards the scoping: [2](#0-1) 

```
class CCMenuController < BaseController
  require_permission :read, :stack
  ...
  def show
    latest_deploy = stack.deploys_and_rollbacks.last || NoDeploy.new
    render('shipit/ccmenu/project', formats: [:xml], locals: { stack:, deploy: latest_deploy })
  end

  private

  def stack
    @stack ||= Stack.from_param!(params[:stack_id])
  end
  ...
end
```

`require_permission :read, :stack` only checks `ApiClient#permissions` via `ApiClient#check_permissions!`, which is purely a string-membership check on the permission name and never consults `stack_id`: [3](#0-2) 

Consequently, any token that carries `read:stack` — including one intentionally minted with `stack_id` set to restrict it to a single stack (this is exactly how `CCMenuUrlController` mints tokens: `ApiClient.create_with(permissions: %w[read:stack]).find_or_create_by!(creator: current_user, name: 'CCMenu Client')`, see [4](#0-3)  then embedded in a URL, `uri.query = { 'token' => client.authentication_token }.to_query` at [5](#0-4) ) — can be replayed against `GET /api/stacks/*stack_id/ccmenu` with an arbitrary `stack_id` route segment (see `config/routes.rb` line 27-28: `scope '/stacks/*stack_id' ... get '/ccmenu' => 'ccmenu#show'`) and it will render CI/deploy status for *any* stack in the installation, not just the one it was scoped to.

Binding broken (equality that should hold but doesn't):
`current_api_client.stack_id (the stack the token authorizes)` == `params[:stack_id] resolved by Api::CCMenuController#stack (the stack the request actually touches)`

Before the divergent code path: every other API endpoint enforces this equality through `BaseController#stack`. After: `Api::CCMenuController#stack` unconditionally resolves via `Stack.from_param!`, dropping the `stacks` (scoped) relation entirely, so the equality never holds for a stack-scoped token pointed at a different stack.

### Impact Explanation
This grants **unauthenticated-relative-to-scope read of stack state** (deploy status, last build label/status/time, running state) for any stack, using a token that was deliberately minted narrow-scoped for exactly one stack (the CCMenu integration pattern in this engine). This matches the High-severity class "escalation into `Shipit.github_teams` authorization" / "unauthenticated read of stack state, task streams or deploy output" since a credential intended to authorize reads on stack A is used to read stack B's deploy/CI state — a cross-stack authorization escalation via the deployment-trust binding "token's authorized stack vs. stack actually touched."

### Likelihood Explanation
Likelihood is high for anyone in possession of any valid stack-scoped CCMenu token (these tokens are handed out via `CCMenuUrlController#fetch` and are meant to be embedded in CI status-monitor tools, i.e., relatively widely distributed and low-privilege by design). No additional secrets, GitHub App keys, or session access are required — only a previously-issued, legitimately-scoped CCMenu API token and knowledge/guessing of another stack's `owner/repo/environment` path segment (which is often public/knowable, e.g., visible in the Shipit UI or repo name).

### Recommendation
Change `Api::CCMenuController#stack` to reuse the inherited, scoped `stack`/`stacks` helpers from `Api::BaseController` instead of calling `Stack.from_param!` directly, e.g.:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
This restores the invariant that `current_api_client.stack_id` (if set) always constrains which stack a request can resolve to, consistent with every other controller in `app/controllers/shipit/api/`.

### Proof of Concept
1. As a legitimate user, visit a stack's CCMenu URL page; `CCMenuUrlController#fetch` creates/finds an `ApiClient` with `permissions: %w[read:stack]` and (implicitly, per the pattern) tied to the requesting stack context, returning a token embedded in `ccmenu_url` (`app/controllers/shipit/ccmenu_url_controller.rb:7-11`).
2. Take the returned token (`?token=<TOKEN>`), and instead of requesting `GET /api/stacks/<authorized-owner>/<authorized-repo>/<authorized-env>/ccmenu?token=<TOKEN>`, request `GET /api/stacks/<other-owner>/<other-repo>/<other-env>/ccmenu?token=<TOKEN>`.
3. `Api::BaseController#authenticate_api_client` accepts the token via Basic Auth or query param and sets `current_api_client` to the scoped `ApiClient` (`app/controllers/shipit/api/base_controller.rb:48-56`).
4. `require_permission :read, :stack` passes because the client has `read:stack` in its `permissions` array — `stack_id` scoping is never checked (`app/models/shipit/api_client.rb:38-45`).
5. `Api::CCMenuController#stack` resolves via `Stack.from_param!(params[:stack_id])`, returning the *other* stack regardless of `current_api_client.stack_id` (`app/controllers/shipit/api/ccmenu_controller.rb:29-31`).
6. The response renders the other stack's live CI/deploy status XML, proving cross-stack read with a token that was only meant to authorize one stack.
