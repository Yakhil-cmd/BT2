### Title
ECDH shared-secret derivation with unvalidated peer public keys via `elliptic` fallback backend - (File: device.js)

### Summary
`ocore` derives per-message symmetric keys for encrypted device-to-device communication using ECDH over secp256k1. In browser/Cordova builds, `package.json`'s `browser` field remaps the `secp256k1` module to `secp256k1/elliptic`, causing the ECDH point-multiplication to run through the `elliptic` library's key-derivation path rather than native bindings. [1](#0-0)  The vulnerable versions of `elliptic` (<6.5.4, GHSA-r9p9-mrjm-926w / CVE-2020-28498) perform ECDH `derive()` without validating that the supplied point actually lies on the secp256k1 curve, which can leak bits of the local private key after repeated ECDH operations with attacker-chosen points.

### Finding Description
`device.js` implements pairwise encrypted messaging between wallet/device correspondents. `deriveSharedSecret()` takes a base64-encoded peer public key straight from an incoming (or outgoing) encrypted package and feeds it into `ecdsa.ecdh(pubkey, privKey, {hashfn: (x, y) => x}, Buffer.alloc(32))`: [2](#0-1) 

The peer key comes directly from the `dh.sender_ephemeral_pubkey` / `dh.recipient_ephemeral_pubkey` fields of an `objEncryptedPackage`, which is attacker-controlled input received from any paired correspondent device (or via the hub relay) with only shallow `typeof` checks (string type, no curve-membership validation) before being passed to `deriveSharedSecret`: [3](#0-2) [4](#0-3) 

On the outgoing side, `createEncryptedPackage()` similarly derives a shared secret from a `recipient_device_pubkey` value that originates from the `correspondent_devices` table, populated from pairing data exchanged with a counterparty; if a malicious "device" pairs with a victim and supplies crafted (off-curve or twist) public keys, or resends manipulated `sender_ephemeral_pubkey`/`recipient_ephemeral_pubkey` values in the DH envelope, the ECDH step will silently accept them if the underlying `derive()` implementation doesn't check curve membership: [5](#0-4) 

Because `hashfn: (x, y) => x` is used (raw x-coordinate returned, no hashing of the shared point before deriving the AES key), an attacker who can force use of invalid-curve/twist points and observe decryption success/failure (e.g., AEAD tag verification result in `decryptPackage`) can mount an invalid-curve attack to recover bits of the victim's permanent or temporary device private key across repeated probing messages — directly mirroring the `elliptic` advisory's root cause (missing on-curve validation in the ECDH `derive` path).

### Impact Explanation
If exploitable, a paired correspondent (or anyone who can get the victim's hub to relay crafted encrypted packages to them) could, over repeated ECDH probes and AEAD-tag oracle feedback in `decryptPackage`, incrementally leak the victim's permanent device private key (`objMyPermanentDeviceKey.priv`) or temp key (`objMyTempDeviceKey.priv`). The device's permanent private key is used to sign device messages (pairing, address introduction, private-payment chain relays, wallet sync) via `objMyPermanentDeviceKey.priv` in `createTempPubkeyPackage` and elsewhere, so its compromise would allow impersonation of the victim device, forging of paired messages, and interception/redirection of private payments and wallet coordination traffic sent to that device.

### Likelihood Explanation
Exploitability hinges entirely on whether the actual runtime backend used performs curve-membership validation. The primary declared dependency is `"secp256k1": "^4.0.3"` (native bindings, which do validate points), and this is what runs in Node.js server/hub contexts. [6](#0-5)  However, the `browser` field explicitly overrides this to `secp256k1/elliptic` for any bundled/browser/Cordova build (mobile wallet, light client, GUI wallet) — precisely the "paired device" client population this analog targets. [1](#0-0)  I was unable to inspect the installed `elliptic`/`secp256k1` node_modules sources or lockfile in this index to confirm the exact resolved `elliptic` version or whether the `secp256k1` wrapper adds its own point-validation layer on top of `elliptic`'s `derive()` before calling into it, so I cannot fully confirm the vulnerable code path is reached unpatched. This is a material gap: the `secp256k1` JS package's public API (`publicKeyVerify`, `ecdh`) is documented to validate the public key format/on-curve status itself in newer versions, which could mean the wrapper mitigates the underlying `elliptic` flaw even in the browser fallback build. Given this uncertainty, likelihood is assessed as medium/uncertain rather than confirmed.

### Recommendation
- Pin/audit the resolved `elliptic` version behind `secp256k1/elliptic` to ensure it is ≥6.5.4 (patched), and add curve-membership validation (`secp256k1.publicKeyVerify()`) explicitly in `deriveSharedSecret()` in device.js before calling `ecdsa.ecdh(...)`, regardless of backend.
- Avoid the raw-x `hashfn: (x, y) => x` pass-through in `device.js:399`; hash the full shared point (x and y, or use the library's default SHA-256 KDF) so that partial-point leakage is not directly exposed to a decryption oracle.
- Add explicit rejection of malformed/off-curve `dh.sender_ephemeral_pubkey` / `dh.recipient_ephemeral_pubkey` values in `decryptPackage()` prior to invoking ECDH.

### Proof of Concept
Conceptual (not verified against the actual bundled `elliptic` version due to inability to inspect resolved dependency sources in this index):
1. Attacker pairs as a correspondent device with the victim, or otherwise gets messages relayed to the victim through the hub.
2. Attacker crafts an `objEncryptedPackage` (or a `recipient_device_pubkey`/`sender_ephemeral_pubkey`) that encodes a point not on the secp256k1 curve but valid on its twist.
3. Victim's client (running the browser/elliptic backend) calls `deriveSharedSecret()` → `ecdsa.ecdh()`, which, if backed by unpatched `elliptic`, computes a "shared secret" from the invalid point without rejecting it.
4. Attacker observes whether `decryptPackage()`'s AEAD tag check in device.js succeeds or fails (an oracle), repeats with different twist points, and reconstructs bits of the victim's private key over multiple messages, per the standard invalid-curve/twist-attack technique referenced in the advisory.
