### Title
Signature verification keyed on attacker-controlled `repository.owner.login`/`organization.login` allows selection of an unsecured GitHub App config, bypassing HMAC verification for any tracked stack - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App (and therefore which `webhook_secret`) to verify the inbound webhook HMAC against by reading `repository_owner` straight out of the **unverified** JSON body, before the signature has been checked. In multi-organization deployments (`Shipit.github(organization:)`), each org can have its own, independently-configured `webhook_secret`, and that secret is explicitly optional/nilable, as shown in `docs/setup.md` and the test fixture `test/dummy/config/secrets_double_github_app.yml` (`webhook_secret: # nil`). Because the org used for signature *selection* is not bound to the repository actually acted upon by the event handlers, an attacker can pick an org name whose secret is nil to fully bypass signature verification while the payload still targets a real, protected stack.

### Finding Description
`app/controllers/shipit/webhooks_controller.rb`:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) 

`repository_owner` is read from the raw, attacker-controlled request body **before** any signature has been proven valid. That value is used only to select the app config whose `webhook_secret` verifies the request:

```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
``` [2](#0-1) 

Critically, once the request is accepted (`head(:ok)` never actually blocks `create` from running — `verify_signature` only calls `head(422)` and does not `return`/halt the filter chain, but even where it does properly reject, the org used to verify has no relationship to what the *handlers* subsequently act on. The handlers derive the actual target repository/stack from a **different** field of the same untrusted payload:

```ruby
def repository_name
  payload.dig('repository', 'full_name')
end
``` [3](#0-2) 

and for the `membership` event, the actual `Team#organization` written to the database comes from `params.organization.login`:
```ruby
def find_or_create_team!
  Team.find_or_create_by!(github_id: params.team.id) do |team|
    team.github_team = params.team
    team.organization = params.organization.login
  end
end
``` [4](#0-3) 

Nothing in the code enforces that the organization/owner used to pick the verifying secret is the same value later trusted as the identity of the acted-upon repository/organization. Multi-org secrets are explicitly allowed to have a nil `webhook_secret` per org (`docs/setup.md` lines 181-209, and the dummy fixture `test/dummy/config/secrets_double_github_app.yml` where `OrgTwo` has `webhook_secret: # nil`): [5](#0-4) [6](#0-5) 

This is a direct structural analog to the reported bug: `_getSwapAmt` trusted an unverified assumption about which reserve slot mapped to which token; here, the controller trusts an unverified assumption that the org name used to pick the HMAC secret is bound to the repository the payload will actually mutate. The break is: `organization authenticated (repository_owner used to select webhook_secret)` ≠ `repository/organization written (repository.full_name / organization.login consumed by handlers)`.

### Impact Explanation
If any organization configured in a multi-org `secrets.yml`/credentials has no `webhook_secret` set (a supported, documented configuration), an unprivileged network attacker with zero Shipit credentials can:
1. Craft a JSON payload where `repository.owner.login` (or `organization.login`) names the unsecured org, while `repository.full_name` names a real, tracked Stack belonging to a different, secret-protected organization.
2. POST it to `/webhooks` with an arbitrary/garbage `X-Hub-Signature`.
3. `verify_signature` resolves `Shipit.github(organization: "unsecured-org")`, whose `verify_webhook_signature` short-circuits `true` because `webhook_secret` is nil — bypassing signature verification entirely for a webhook that manipulates the protected stack.

Depending on event type this yields, for example, forged `status` webhooks writing arbitrary CI status (`state`, `target_url`, `description`, `context`) directly onto a real commit — as shown in the existing test that maps these fields verbatim from payload to the `Status` record (`test/controllers/webhooks_controller_test.rb`, `":state create a Status for the specific commit"`). Shipit gates deploys on commit CI status, so a forged "success" status can defeat deploy safety checks and enable an **unauthorized deploy** of a commit that never actually passed CI — matching the required Critical impact category (unauthorized deploy).

### Likelihood Explanation
Requires only that the operator has configured the documented multi-org mode with at least one org lacking a `webhook_secret` (explicitly supported/optional per `docs/setup.md`), plus knowledge of a target stack's `repo_owner`/`repo_name` (public information visible in the Shipit UI/API for any tracked repo). No credentials, tokens, or GitHub App access are needed — purely an unauthenticated HTTP POST to `/webhooks`.

### Recommendation
Do not select the verifying GitHub App/secret from unverified request-body fields that are also later trusted as the mutation target. Either:
- Verify the signature against every configured org's secret (or a single canonical app per Shipit deployment) rather than the payload-declared owner, or
- After verifying with the payload-declared org, re-validate that `repository.full_name`'s owner segment (and `organization.login` for org-scoped events) matches the org whose secret was used, rejecting any mismatch, and require `webhook_secret` to be mandatory (non-nil) for every configured organization.

### Proof of Concept
Given a multi-org config where `OrgTwo` has `webhook_secret: nil` and `OrgOne` (protected) owns tracked stack `OrgOne/protected-repo`:
```
POST /webhooks
X-Github-Event: status
X-Hub-Signature: sha1=deadbeef   # arbitrary, unverifiable signature

{
  "sha": "<real-commit-sha-of-OrgOne/protected-repo>",
  "state": "success",
  "target_url": "https://ci.example.com/fake",
  "description": "forged",
  "context": "ci/forged",
  "created_at": "...",
  "repository": {
    "full_name": "OrgOne/protected-repo",
    "owner": { "login": "OrgTwo" }
  }
}
```
`repository_owner` resolves to `"OrgTwo"`, whose app has `webhook_secret: nil`, so `verify_webhook_signature` returns `true` unconditionally per `lib/shipit/github_app.rb` lines 76-83, while `StatusHandler`/`Handler#repository_name` (lines 36-38 of `handler.rb`) resolves the target using `repository.full_name`, i.e. `OrgOne/protected-repo`. The forged success status is written to the real stack.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

### Using Multiple Github Applications

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently. The top-level keys should be the name of each Github organization, and the following sub-keys are the Github app details for that particular organization.

For example:

```yml
production:
  github:
    somegithuborg:
      app_id:
      installation_id:
      webhook_secret:
      private_key:
      oauth:
        id:
        secret:
        teams:
    someothergithuborg:
      app_id:
      installation_id:
      webhook_secret:
      private_key:
      oauth:
        id:
        secret:
        teams:
```
