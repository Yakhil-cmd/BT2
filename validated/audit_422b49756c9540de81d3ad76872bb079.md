### Title
Bridge Owner Front-Runs Pending Value-Transfer Votes by Immediately Lowering `operatorThresholds`, Executing Unauthorized Asset Transfers — (`contracts/service_chain/bridge/BridgeOperator.sol`)

---

### Summary

`setOperatorThreshold` in `BridgeOperator.sol` takes effect immediately and is read live at every vote. A bridge owner who is also an operator can lower the threshold mid-vote to make an already-open vote session reach quorum with fewer signatures than originally required, then re-vote to trigger execution of an unauthorized KAIA/ERC20/ERC721 transfer.

---

### Finding Description

`setOperatorThreshold` writes directly to `operatorThresholds` with no delay: [1](#0-0) 

The quorum check in `_voteCommon` reads the live value of `operatorThresholds` at the moment each vote is cast: [2](#0-1) 

There is no snapshot of the threshold taken when a vote session opens. Every call to `_voteValueTransfer` (and therefore `handleKLAYTransfer`, `handleERC20Transfer`, `handleERC721Transfer`) re-reads the current threshold. A threshold change between two votes retroactively applies to all open (not yet `closedValueTransferVotes`) sessions.

The constructor makes the deployer both owner and operator by default: [3](#0-2) 

`_voteCommon` allows a voter to re-vote (changing or re-confirming their vote), which decrements the old count and increments the new count: [4](#0-3) 

This means after lowering the threshold, the owner can re-submit the same calldata to trigger the quorum check again on the same nonce.

The `handleKLAYTransfer` function that executes the actual KAIA transfer is the downstream target: [5](#0-4) 

---

### Impact Explanation

A malicious bridge owner can execute an unauthorized transfer of KAIA, ERC20, or ERC721 tokens from the bridge contract to an arbitrary address. The bridge holds the locked assets of all users who have bridged tokens from the parent chain to the service chain (or vice versa). Draining the bridge contract directly steals user funds.

This matches the allowed impact gate: **unauthorized transfer of KAIA or bridged assets**.

---

### Likelihood Explanation

The bridge owner is the service chain operator — a privileged but semi-trusted role. The attack requires no external cooperation and no majority-validator collusion. The owner simply needs to:
1. Be (or become) one of the registered operators (the default state).
2. Observe a pending vote session with `N-1` votes already cast.
3. Call `setOperatorThreshold` to lower the threshold to `N-1`, then re-vote.

The code itself already acknowledges a related timing issue with `deregisterOperator`: [6](#0-5) 

The threshold-lowering attack is strictly more powerful because it is fully owner-controlled and does not require waiting for another operator.

---

### Recommendation

1. **Snapshot the threshold at session open.** Store the threshold in `VotesData` when the first vote for a nonce is cast, and use that stored value for all subsequent quorum checks on the same nonce — not the live `operatorThresholds`.
2. **Apply threshold changes only to future sessions.** Alternatively, record the current `configurationNonce` (or a monotonic session counter) at the time `setOperatorThreshold` is called, and only apply the new threshold to vote sessions opened after that point.
3. **Two-step threshold change with a time lock.** Require a pending period between announcing and committing a threshold change, giving operators time to observe and react.

---

### Proof of Concept

```
Setup:
  Bridge deployed with operators [Owner, B, C], threshold = 3 (ValueTransfer)
  Bridge holds 1000 KAIA

Step 1 — Owner votes on a malicious transfer:
  Owner calls handleKLAYTransfer(hash, from, attacker, 1000 KAIA, nonce=5, ...)
  → voteCounts[voteKey] = 1; 1 < 3; not executed

Step 2 — Legitimate operator B votes:
  B calls handleKLAYTransfer(same args, nonce=5)
  → voteCounts[voteKey] = 2; 2 < 3; not executed

Step 3 — Owner front-runs by lowering threshold:
  Owner calls setOperatorThreshold(VoteType.ValueTransfer, 2)
  → operatorThresholds[ValueTransfer] = 2 (immediate, no delay)

Step 4 — Owner re-votes (same calldata):
  Owner calls handleKLAYTransfer(same args, nonce=5) again
  → _voteCommon: oldVoteKey = keccak256(calldata) (same key as before)
  → voteCounts[voteKey]-- → count = 1
  → voteCounts[voteKey]++ → count = 2
  → 2 >= operatorThresholds[ValueTransfer] (= 2) → returns true
  → closedValueTransferVotes[5] = true
  → handleKLAYTransfer executes: 1000 KAIA sent to attacker address
```

The attack succeeds with only 2 distinct operator votes (Owner + B) on a bridge configured for threshold 3. The owner unilaterally bypassed the multi-sig security guarantee.
