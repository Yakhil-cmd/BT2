### Title
`EphemeralCommitChecks#build_commands` passes `Shipit.env` unfiltered, allowing host `ENV` fallback exfiltration - ([File: app/models/shipit/ephemeral_commit_checks.rb])

### Summary
`EphemeralCommitChecks#build_commands` builds each dependency/review-check `Command` with `env: Shipit.env` and never calls `EnvironmentVariables#permit` (unlike `DeploySpec#filter_deploy_envs`/`filter_rollback_envs` used for deploy/rollback commands). Because `EnvironmentVariables#interpolate` falls back to the real process `ENV` for any variable not found in the given env hash, a repository's `shipit.yml` `dependencies.override`/`review.checks` step can reference `$INTERNAL_SECRET` and have it interpolated from the Shipit host process's own `ENV`, with the resulting command/output written verbatim into `@output`, which is exposed via the commit-checks page.

### Finding Description
The broken binding: for commands executed via `EphemeralCommitChecks`, the set of environment variables visible to interpolation should be `= Shipit.env` (or an explicitly permitted subset), but in practice it is `= Shipit.env ∪ ENV` because of the fallback in `EnvironmentVariables#interpolate`: [1](#0-0) 

`EphemeralCommitChecks#build_commands` constructs commands directly from the repo-controlled `dependencies_steps` and `review_checks` arrays with `env: Shipit.env` and no `permit` call at all: [2](#0-1) 

`Shipit::DeploySpec#dependencies_steps` and `#review_checks` are sourced straight from the repository's `shipit.yml` (`config('dependencies', 'override')`, `config('review', 'checks')`), i.e. fully attacker-controlled content in a PR's checked-out tree: [3](#0-2) [4](#0-3) 

`Command#interpolated_arguments` calls `EnvironmentVariables.with(env).interpolate` on each argument before spawning the process, using the exact fallback shown above: [5](#0-4) [6](#0-5) 

Contrast: for deploy/rollback commands, `Stack`/`DeployCommands` route the env hash through `DeploySpec#filter_deploy_envs`/`#filter_rollback_envs`, which call `EnvironmentVariables#permit` and raise `NotPermitted` for any key not in the declared whitelist (`deploy_variables`/`rollback_variables`) — this is the guard that is supposed to bound what a repo can reference, and it is completely absent on the `EphemeralCommitChecks` path. Even if `permit` were called, though, `permit` only sanitizes the explicit `env` hash passed to `Command`; it does not affect the separate ENV-fallback behavior baked into `interpolate`, so the fallback itself is the root cause, and `EphemeralCommitChecks` is simply the path with zero mitigation.

Attacker's exact action: open a PR against a Shipit-managed repository, adding to `shipit.yml`:
```yaml
dependencies:
  override:
    - "echo $INTERNAL_SECRET"
```
When `EphemeralCommitChecks#run` executes for that commit (dependency/review pre-checks triggered by CI/webhook flow), `capture` writes `"$ echo $INTERNAL_SECRET\n"` followed by the command's stdout into `@output` via `#write`, and that value/text is what appears on the commit-checks page.

### Impact Explanation
Any contributor able to open a pull request (no Shipit session, no API token, no team membership) against a repository onboarded to this Shipit instance can cause the Shipit host process to interpolate arbitrary environment variable names into a shell command, and have the resulting command line and/or output rendered on a page tied to that commit's checks. This matches the "exfiltration of ... deploy-time secrets" Critical category if `Shipit.env` legitimately contains sensitive deploy-time secrets that get exposed via ENV fallback, or the "unauthenticated read of ... task streams / deploy output" High category, since the check output is the actual disclosure surface. The blast radius is scoped to whatever secrets are present in the Shipit host process's `ENV` (not scoped per repository or tenant) — a single onboarded repository with an unprivileged PR can read process-wide secrets shared across all stacks managed by that Shipit instance.

### Likelihood Explanation
Preconditions are modest: the repository must already be onboarded to Shipit (an existing stack) and have `EphemeralCommitChecks` invoked for a PR's commit (dependency/review pre-checks), and the Shipit host process `ENV` must actually contain a sensitive value under a guessable/discoverable name. The attacker does not need to know the exact variable name to attempt exfiltration broadly (they could try common names like `GITHUB_TOKEN`, `DATABASE_URL`, `SECRET_KEY_BASE`, etc.), and the action is fully repeatable — every new PR/commit re-triggers the check. This makes it a low-cost, repeatable attack for anyone who can open PRs against an onboarded repo.

### Recommendation
Remove the `ENV` fallback from `EnvironmentVariables#interpolate` (only interpolate from the explicitly provided/permitted `@env`, raising or leaving unresolved otherwise), and additionally have `EphemeralCommitChecks#build_commands` pass a whitelisted env (e.g. via `deploy_spec.filter_deploy_envs`/a dedicated permitted set) instead of raw `Shipit.env`, so unapproved repositories cannot reach host process secrets through commit checks.

### Proof of Concept
```ruby
# test/unit/ephemeral_commit_checks_test.rb (conceptual)
test "dependencies.override referencing host ENV leaks the secret into #output" do
  ENV['INTERNAL_SECRET'] = 'super-secret-value'
  stack = shipit_stacks(:shipit)
  commit = stack.commits.first

  checks = Shipit::EphemeralCommitChecks.new(commit)
  deploy_spec = stub(
    dependencies_steps: ['echo $INTERNAL_SECRET'],
    review_checks: [],
  )
  Shipit::DeploySpec::FileSystem.stubs(:new).returns(deploy_spec)
  Shipit::StackCommands.any_instance.stubs(:with_temporary_working_directory).yields('/tmp/dir')

  checks.run

  # Binding before: env passed to Command should equal Shipit.env only (no ENV leakage)
  # Binding after (actual): interpolation falls back to process ENV
  assert_includes checks.output, 'super-secret-value'
ensure
  ENV.delete('INTERNAL_SECRET')
end
```
This asserts that a value present only in the host process `ENV` (never in `Shipit.env`, never passed by the app) ends up in `EphemeralCommitChecks#output`, confirming the unfiltered/fallback env leak.

    def run
      self.status = 'running'
      commands = StackCommands.new(stack)
      commands.with_temporary_working_directory(commit:) do |directory|
        deploy_spec = DeploySpec::FileSystem.new(directory, stack)
        capture_all(build_commands(deploy_spec.dependencies_steps, chdir: directory))
        capture_all(build_commands(deploy_spec.review_checks, chdir: directory))
      end
      self
    rescue Command::Error
      self.status = 'failed'
      self
    rescue StandardError
      self.status = 'error'
      raise
    else
      self.status = 'success'
      self
    end

    def success?
      status == 'success'
    end

    def finished?
      FINAL_STATUSES.include?(status)
    end

    def write(output)
      @output ||= ''
      @output += output
    end

    private

    def build_commands(commands, chdir:)
      commands.map { |c| Command.new(c, env: Shipit.env, chdir:) }
    end

    def capture_all(commands)
      commands.map { |c| capture(c) }
    end
