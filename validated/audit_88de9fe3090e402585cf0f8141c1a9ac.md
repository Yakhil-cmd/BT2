### Title
Webhook signature verification binds the wrong field (`repository.owner.login`) to the secret lookup while handlers act on a different field (`repository.full_name`), enabling cross-organization webhook forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App configuration (and therefore which `webhook_secret`) to verify the HMAC against using `repository_owner`, computed from `params.dig('repository', 'owner', 'login')` (or `organization.login`). All downstream event handlers, however, resolve the target `Stack`/`Repository` to act on using a completely different JSON field: `payload.dig('repository', 'full_name')`. Because Shipit supports multiple independently configured GitHub organizations, each with its own `webhook_secret` [1](#0-0) , an attacker who administers one organization's GitHub App (and therefore legitimately possesses that organization's `webhook_secret`, since they configured it themselves) can craft an arbitrary raw JSON body where `repository.owner.login` names their own org (so signature verification picks their own known secret) while `repository.full_name` names a victim organization's repository (so the handler resolves and acts on the victim's `Stack`).

### Finding Description
`verify_signature` picks the GitHub App/secret to check against based on `repository_owner`: [2](#0-1) [3](#0-2) 

`Shipit.github(organization: repository_owner)` returns a `GithubApp`/`GithubHook` instance configured for that specific organization, and `verify_webhook_signature` only proves that the raw body was signed with whatever secret is configured for that organization: [4](#0-3) 

Once the request passes, `create` blindly parses the same raw body and dispatches it to all registered handlers for the event: [5](#0-4) 

Every handler (e.g. push, status, check_suite) resolves the affected `Stack`s via the base `Handler` class, which reads a *different* JSON key than the one used for signature-secret selection — `repository.full_name` — and looks up the `Repository`/`Stack` purely from that field, with no cross-check against `repository.owner.login`: [6](#0-5) [7](#0-6) 

The binding that should hold is:
`organization authenticated by verify_signature (repository.owner.login → webhook_secret)` == `organization/repository actually written to by handlers (repository.full_name)`.

Because both fields live in the same attacker-suppliable JSON body and are not tied together, an attacker who legitimately owns the GitHub App/secret for "attacker-org" (one of potentially several orgs configured under `config/secrets.yml`'s `github:` multi-org block [1](#0-0) ) can:
1. Set `repository.owner.login = "attacker-org"` so `verify_signature` selects the secret they know.
2. Set `repository.full_name = "victim-org/victim-repo"` so handlers resolve and act on the victim's `Stack`.
3. Sign the whole crafted body with `attacker-org`'s secret — the HMAC check passes because it only validates "this sender knows attacker-org's secret," not "this payload's target repository belongs to attacker-org."

The push handler test confirms handlers use exactly this `full_name`-driven resolution to enqueue jobs against a `Stack`: [8](#0-7) 

### Impact Explanation
This lets an attacker who is only an administrator of *one* organization configured on a shared/multi-tenant Shipit instance forge webhook events (`push`, `status`, `check_suite`, `pull_request`, `membership`, etc.) against a *different* organization's stacks. Depending on the handler, this can trigger unauthorized `GithubSyncJob`/`RefreshCheckRunsJob` runs, fabricate commit `Status` records that CI-gate deploys, or manipulate `Team`/`Membership` records — undermining the deploy/merge authorization model across organizational trust boundaries. This crosses the "cross-repository writes" / "unauthorized deploy" impact bar since it lets one org's credential holder influence another org's stack state and CI signal used to gate deploys.

### Likelihood Explanation
Requires the engine to be configured with the multi-organization `github:` block (explicitly documented and supported) [1](#0-0) , and requires the attacker to control (i.e., be permitted to configure) at least one of the organizations onboarded to that shared Shipit instance — no GitHub App private key, `ApiClient` token, or Shipit session is needed, only knowledge of a legitimately-configured `webhook_secret` for their own org, which they control by definition. This is a realistic scenario for any shared Shipit deployment serving multiple orgs/teams.

### Recommendation
After signature verification, re-derive the organization strictly from the same trusted field used to select the secret (`repository.owner.login`), and require that all repository/stack resolution in handlers (`Handler#repository_name`, `Repository.from_github_repo_name`) validate that the resolved repository's `owner` matches the organization whose secret validated the signature. Reject the webhook if `repository.full_name`'s owner segment differs from `repository.owner.login`/`organization.login` used in `verify_signature`.

### Proof of Concept
1. Shipit is configured with two orgs, `attacker-org` and `victim-org`, each with its own GitHub App and `webhook_secret` (per the documented multi-org config) [1](#0-0) .
2. Attacker administers `attacker-org`'s GitHub App and therefore knows `attacker-org`'s `webhook_secret`.
3. Attacker crafts a `push` event JSON body:
```json
{
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  },
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>"
}
```
4. Attacker computes `X-Hub-Signature: sha1=HMAC(attacker-org secret, body)` and POSTs directly to `/webhooks` with `X-Github-Event: push`.
5. `verify_signature` calls `Shipit.github(organization: "attacker-org")` and the HMAC validates successfully [2](#0-1) .
6. The `push` handler resolves stacks via `repository.full_name = "victim-org/victim-repo"` [6](#0-5)  and enqueues a `GithubSyncJob` against the victim's `Stack`, as shown by the equivalent legitimate-path test [8](#0-7) .

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
