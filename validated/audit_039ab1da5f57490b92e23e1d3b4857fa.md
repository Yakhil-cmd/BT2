### Title
Webhook organization used for signature verification is never bound to the repository the handlers act on, enabling cross-repository event forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary

### Finding Description
`WebhooksController` picks which GitHub App configuration (and thus which `webhook_secret`) to verify a webhook against using only one field of the JSON body: [1](#0-0) 

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(...)
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

`GitHubApp#verify_webhook_signature` explicitly no-ops when that organization's `webhook_secret` is unset — a state the setup docs describe as valid/optional (`docs/setup.md`, "Webhook secret (optional)"): [2](#0-1) 

Meanwhile, the actual repository/stack that is mutated by every downstream handler is resolved from a *different, uncorrelated* payload field, `repository.full_name`, with no check that it belongs to the organization used above for authentication: [3](#0-2) 

```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
```

This pattern repeats in `PushHandler#process` (drives `stack.sync_github`), `CheckSuiteHandler#process` (schedules check-run refresh), `StatusHandler#process` (writes CI status onto commits by SHA, with no repository check at all), and `PullRequest::OpenedHandler#repository` (drives review-stack provisioning): [4](#0-3) [5](#0-4) [6](#0-5) [7](#0-6) 

This is the same class of bug as the referenced report: a value used at the "check" step (`repository.owner.login`, used to select the verifying app/secret) is never re-validated against the value actually consumed at the "act" step (`repository.full_name`, used to pick the repository/stacks mutated). The binding `organization authenticated == repository written` is never enforced.

### Impact Explanation
If any one of the multiple GitHub Apps configured in `Shipit.github` (a documented, supported multi-org configuration, see `docs/setup.md` "Using Multiple Github Applications") is left without a `webhook_secret` — an explicitly optional field — `verify_webhook_signature` returns `true` unconditionally for any payload whose `repository.owner.login`/`organization.login` names that org, regardless of what `repository.full_name` is set to. An unprivileged, unauthenticated remote attacker (no session, no `ApiClient` token, no repository write access) can then POST an arbitrary, unsigned JSON body to the public `/webhooks` endpoint naming that unsecured org for verification purposes while pointing `repository.full_name` at a completely different, secured organization's repository. Because handlers never re-check that the acted-upon repository belongs to the organization that was authenticated, this achieves cross-repository writes:
- `push` → forces `stack.sync_github` on an arbitrary target stack.
- `check_suite` → forces check-run refresh workflows on arbitrary commits/stacks.
- `status` → writes attacker-controlled CI status directly onto commits by SHA with no repository ownership check at all.
- `pull_request` (`opened`) → triggers review-stack provisioning on an arbitrary target repository.

This satisfies the "cross-repository writes" Critical-impact criterion.

### Likelihood Explanation
Requires only that one configured GitHub organization omits `webhook_secret`, which the project's own setup documentation calls optional; no credentials, sessions, or GitHub write access are needed to reach `/webhooks`, which is mounted unauthenticated by design.

### Recommendation
Bind the organization used for signature verification to the repository actually acted upon: after selecting `github_app` via `repository_owner`, re-derive and compare it against the owner encoded in `payload.dig('repository', 'full_name')` (and reject on mismatch) before dispatching to handlers, and/or make `webhook_secret` mandatory per configured organization so `verify_webhook_signature` can never silently short-circuit.

### Proof of Concept
1. Configure two GitHub Apps, `orgA` (no `webhook_secret` set — a documented valid state) and `orgB` (secured, hosts a private/target stack).
2. As an unauthenticated attacker, POST to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "ref": "refs/heads/main",
  "after": "deadbeef",
  "repository": { "owner": { "login": "orgA" }, "full_name": "orgB/target-repo" }
}
```
No `X-Hub-Signature` needs to be valid — `Shipit.github(organization: "orgA").verify_webhook_signature` returns `true` because `orgA` has no secret configured.
3. `WebhooksController#create` dispatches to `PushHandler`, whose `repository_name` resolves to `"orgB/target-repo"`, causing `stack.sync_github` to run against `orgB`'s stack — a stack the attacker has no credentials for.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
