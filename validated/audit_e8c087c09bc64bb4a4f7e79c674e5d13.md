### Title
CCMenuController#stack bypasses `current_api_client.stack_id` scoping, allowing cross-tenant stack status read - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::Api::BaseController` restricts an `ApiClient` scoped to a single stack (`stack_id` set) to only that stack via the `stacks` scoping helper, but `CCMenuController` overrides the `stack` method to call `Stack.from_param!` directly on the unscoped `Stack` model, completely bypassing that restriction. Any valid CCMenu token scoped to stack A can therefore be used to read the CCMenu XML build/deploy status of any other stack B.

### Finding Description
The binding that should hold is `current_api_client.stack_id == stack.id` (when `current_api_client.stack_id?` is true) before any stack data is rendered.

In `BaseController`, this is normally enforced by the `stacks` helper: [1](#0-0) 
`stacks` returns `Stack.where(id: current_api_client.stack_id)` when the client is scoped, and `#stack` resolves via `stacks.from_param!`, so an out-of-scope stack ID simply won't be found (404).

`CCMenuController`, however, defines its own `stack` method that calls `Stack.from_param!` on the unscoped `Stack` class directly, and its own `authenticate_api_client` that authenticates purely via `ApiClient.authenticate(params[:token])`: [2](#0-1) 

`ApiClient.authenticate` only verifies the signed client id and returns the record — it performs no stack check at all: [3](#0-2) 

The only authorization guard on the action is `require_permission :read, :stack`, which calls `check_permissions!`, itself only checking the string permission `"read:stack"` is present in `permissions` — it never compares `stack_id`: [4](#0-3) [5](#0-4) 

Attacker flow: attacker holds `tokenA` for `ApiClient` A with `stack_id == A.id` and `permissions` including `read:stack` (e.g. obtained from stack A's CCMenu URL, which they had legitimate access to). They send `GET /stacks/:stack_id/ccmenu?token=tokenA` with `stack_id` set to stack B's param. `authenticate_api_client` accepts the token and sets `@current_api_client` to client A. `#stack` then calls `Stack.from_param!(params[:stack_id])` against the full `Stack` table, resolving stack B regardless of `current_api_client.stack_id`. `#show` renders `shipit/ccmenu/project` with stack B's data, leaking stack B's latest deploy/build status to a token that was never granted access to stack B.

None of the standard guards catch this: `require_permission!`/`check_permissions!` only check the permission string, not stack scope; the `stacks` scoping helper that would prevent this is never invoked because `CCMenuController` shadows `#stack` with its own unscoped implementation.

### Impact Explanation
An attacker with any single stack-scoped CCMenu token can enumerate/read CCMenu build and deploy status (stack name, latest deploy id, success/failure, timestamps) for arbitrary other stacks/repositories, including ones belonging to different tenants/teams they have no relationship to. This is a cross-tenant unauthorized read of stack state, repeatable for every stack id in the system, matching the "High: unauthenticated/unauthorized read of stack state" impact category (the attacker is authenticated as *some* client but not authorized for the target stack).

### Likelihood Explanation
Preconditions are modest: the attacker needs any one valid CCMenu token for any stack — CCMenu tokens are routinely embedded in plaintext query strings distributed via stack settings pages/CI badges (`CCMenuUrlController#fetch`), making leakage plausible. No GitHub or Shipit secret is required and no privileged role is needed. The attacker only needs to guess/enumerate another stack's `to_param` (slug), which is far less secret than a token. This is trivially repeatable against every stack in the instance with a single leaked token.

### Recommendation
In `CCMenuController`, resolve the stack through the same scoped path as the rest of the API (`stacks.from_param!` from `BaseController`), or explicitly verify `current_api_client.stack_id.nil? || current_api_client.stack_id == stack.id` before rendering, matching `authenticate_api_client`'s use of the standard flow instead of a bespoke unscoped lookup.

### Proof of Concept
Minitest controller test (`test/controllers/api/ccmenu_controller_test.rb`, hypothetical since actual test dir is out of scope for edits but demonstrates the exploit):
```ruby
setup do
  @stack_a = shipit_stacks(:shipit)
  @stack_b = shipit_stacks(:cyclimse) # different repository/tenant
  @client = ApiClient.create!(creator: shipit_users(:walrus), name: 'scoped',
                               stack_id: @stack_a.id, permissions: %w[read:stack])
end

test "token scoped to stack A cannot read stack B via ccmenu" do
  get :show, params: { stack_id: @stack_b.to_param, token: @client.authentication_token }
  # Binding under test: current_api_client.stack_id == stack.id
  assert_not_equal @client.stack_id, @stack_b.id
  assert_response :not_found # EXPECTED after fix; currently returns :ok and leaks stack B data
end
```
Before the fix, this request returns `:ok` with `@stack_b`'s project data in the rendered XML despite `@client.stack_id != @stack_b.id`, proving the divergence.
