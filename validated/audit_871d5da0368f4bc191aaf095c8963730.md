Confirmed: `Shipit.github` supports a multi-organization configuration schema (`secrets.github` keyed by organization, see `lib/shipit.rb:170-200`), each organization having its own independent `webhook_secret` in `GitHubApp` [1](#0-0) [2](#0-1) . This confirms the multi-tenant scenario is a supported, documented deployment mode of the engine itself (not a misconfiguration), so the analog is in-scope.

### Title
Webhook signature verification authenticates the payload's `repository.owner.login` organization while handlers act on the independently-controlled `repository.full_name` field, allowing any onboarded organization to forge events for another organization's repositories - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
In a multi-organization Shipit deployment, `WebhooksController#verify_signature` selects which organization's HMAC secret to validate a webhook against based on `repository.owner.login` (or `organization.login`), but every event handler determines *which repository/stacks to act on* using a completely separate field, `repository.full_name`, that is never cross-checked against the authenticated owner. This breaks the equality `authenticated_organization == acted_upon_repository_owner`, letting an org that legitimately knows its own webhook secret forge events targeting any other onboarded organization's repositories.

### Finding Description
`verify_signature` computes:
```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```
and picks the `GitHubApp` (and thus the `webhook_secret` used for HMAC verification) accordingly: [3](#0-2) [4](#0-3) 

`verify_webhook_signature` only proves that the raw body was HMAC-signed with *some org's* secret; it does not tie any specific field's value to that org: [5](#0-4) 

But every handler (`Handler#repository_name`, used transitively by `stacks`) resolves the target repository from `repository.full_name`, a sibling field inside the same `repository` object, with no assertion that its owner segment matches `repository.owner.login`: [6](#0-5) 

Concretely:
- `PushHandler#process` triggers `stack.sync_github` for stacks under `Repository.from_github_repo_name(payload.dig('repository','full_name'))`: [7](#0-6) 
- `StatusHandler#process` is even weaker — it doesn't scope by repository at all, only by commit `sha`, and directly writes a GitHub-sourced commit status: [8](#0-7) 
- Pull-request handlers (`OpenedHandler`, `LabeledHandler`, `LabelCapturingHandler`, etc.) resolve `repository` via `Shipit::Repository.from_github_repo_name(params.repository.full_name)` and then create/archive/unarchive review stacks or mutate PR labels/state accordingly: [9](#0-8) [10](#0-9) 

Because the whole raw HTTP body (`request.raw_post`) is signed, an attacker cannot tamper with a payload signed by a *different* org's secret. But the attacker doesn't need to: they control the entire JSON payload for the request they sign with **their own, legitimately-known** organization's `webhook_secret` (every org owner necessarily knows/sets their own GitHub webhook secret when wiring up the integration). They simply craft a payload where `repository.owner.login` is set to their own organization (so `verify_signature` selects their own correctly-known secret and passes) while `repository.full_name` is set to `"victim-org/victim-repo"` (a repository belonging to a different organization also onboarded on the same Shipit instance). The signature check has no way to detect this divergence, since it only validates *whose secret produced the HMAC*, not *what repository the payload claims to describe*.

### Impact Explanation
This is a cross-organization write primitive gated only by owning any one organization's own webhook secret (self-service, not privileged for the target org):
- Forged `status` events let an attacker post arbitrary commit statuses against a victim repository's commit `sha` (matched with no repository scoping whatsoever), which can flip a commit from "not deployable" to CI-deployable via `ci.require`, enabling an **unauthorized deploy** to proceed once a legitimate user (or continuous deployment) triggers it.
- Forged `push` events can force `stack.sync_github` on a victim organization's stacks, and forged `pull_request` events can create/archive/unarchive review stacks or overwrite PR label/state metadata belonging to a victim org's repository — all cross-tenant writes the attacker has no authorization for.

This matches the Critical bucket ("cross-repository writes, or an unauthorized deploy") because the attacker never needed the victim's webhook secret, GitHub App credentials, or any Shipit session/API token — only their own organization's webhook secret, which they legitimately possess by design.

### Likelihood Explanation
Requires: (1) a Shipit instance configured for multi-organization webhooks (`secrets.github` keyed by org — a documented, supported configuration in `lib/shipit.rb`), and (2) the attacker's own organization is one of the onboarded tenants. Given those preconditions (self-service signup style deployments), forging the payload is trivial — it's a single HTTP POST with a correctly computed HMAC using a secret the attacker already owns.

### Recommendation
After signature verification succeeds for organization `O`, additionally assert that `repository.full_name`'s owner segment (and `organization.login`, if present) equals `O` before dispatching to handlers; reject with 422/403 on mismatch. Alternatively, derive `repository_owner` strictly from a value that is also independently validated against `full_name` in every handler, not merely used to pick a signing key.

### Proof of Concept
1. Shipit instance configured with two organizations, `attacker-org` and `victim-org`, each with independent `webhook_secret`s per `lib/shipit.rb#github_app_config`.
2. Attacker, as an owner of `attacker-org`, knows `attacker-org`'s webhook secret (they configured it when wiring the GitHub webhook).
3. Attacker crafts a `status` (or `push`/`pull_request`) JSON payload:
```json
{
  "sha": "<commit sha that exists in victim-org/victim-repo>",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" }
}
```
4. Attacker computes `X-Hub-Signature` using `attacker-org`'s known `webhook_secret` over the raw JSON body and POSTs to `/webhooks`.
5. `verify_signature` calls `Shipit.github(organization: "attacker-org")` (from `repository.owner.login`), verifies successfully since the attacker used the correct secret for that org.
6. `Webhooks.for_event('status')` dispatches to `StatusHandler`, which matches `Commit.where(sha: ...)` with no repository check and writes `create_status_from_github!`, or for `push`/`pull_request` events, `Handler#repository_name` resolves `victim-org/victim-repo` and mutates that stack/review-stack — a write the attacker was never authorized to perform.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e

        'Webhook from unknown organization',

        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
    end
  end
end
