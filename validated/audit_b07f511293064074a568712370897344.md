### Title
Borrower shields an underwater account from liquidation by planting a dust collateral leg priced through an Aquarius LP source, then draining the pool below `min_pool_value_wad` — (File: contracts/price-aggregator/src/providers/aquarius.rs)

### Summary
XOXNO Lending's liquidation, bad-debt cleanup, and withdrawal paths all value *every* supply position of an account through strict (fail-closed) price reads. `supply` itself does not need a price for the supplied asset, so an unprivileged borrower can attach a dust-sized collateral leg of any listed asset — including Aquarius LP share tokens — to their account. If that leg's price becomes unresolvable, `calculate_account_risk_totals` panics inside `build_liquidation_plan`, so *no* liquidation of that account can execute, `clean_bad_debt` reverts, and even the account's own withdrawals revert. For LP-priced assets the outage is attacker-controllable: an Aquarius liquidity provider can withdraw pool value below `min_pool_value_wad`, turning the read into `InsufficientAquariusLiquidity`.

### Finding Description
- `liquidate` calls `plan::build_liquidation_plan`, which calls `risk::calculate_account_risk_totals` over the account's full supply map [1](#0-0) .
- `calculate_account_risk_totals_body` iterates **every** supply position and calls `cache.cached_price(&hub_asset.asset)` for each; a missing/unusable price aborts the whole call — there is no skip or fallback [2](#0-1) .
- The aggregator's strict read panics on any unusable outcome (`force`), including market-condition failures [3](#0-2) .
- For `AquariusLp`/`AquariusStableLp` sources, `providers::aquarius::read` returns `InsufficientAquariusLiquidity` whenever `pool_value_wad < lp.min_pool_value_wad`, a condition any LP can cause by withdrawing [4](#0-3) . Real mainnet markets use such sources with floors of $200k–$1M [5](#0-4) .
- Supply is not price-gated for the supplied asset, so the dust leg can be planted even while its feed is already broken — proven by the harness test `audit_supply_setup_blocks_liquidation_via_stale_dust_leg`, which plants a stale-WBTC leg and shows `liquidate`, `clean_bad_debt`, and `withdraw` all reverting with `PRICE_FEED_STALE` while a twin account liquidates normally [6](#0-5) .
- The threat model itself acknowledges the shape: "an indebted borrower can add a dust leg of any listed collateral and choose which feed outage shields the account. For an Aquarius LP leg, liquidity providers can cause that outage by withdrawing pool value below `min_pool_value_wad`. The same leg blocks bad-debt cleanup and force-socialization" [7](#0-6) .

### Impact Explanation
A single unprivileged borrower can make their own account unliquidatable on demand, indefinitely, at the cost of a dust deposit plus the LP withdrawal (reversible after the danger passes). While the shield is up, interest accrues and collateral can fall further, converting a liquidatable position into protocol bad debt — and `clean_bad_debt`/`recapitalize` paths that also value the account revert too, so socialization cannot proceed either. This matches the accepted impact classes: protocol insolvency accrual and temporary freezing of funds (the account's collateral is also stuck, but the attacker chooses that trade-off; suppliers bear the loss).

### Likelihood Explanation
All required actions are permissionless: `supply` (dust leg), an Aquarius `withdraw_liquidity` on their own position, and no privileged flags or timing are needed. Position-count limits permit at least one extra leg, and the leg persists once planted since top-ups aren't required. The cost is bounded by the LP withdrawal and the dust amount.

### Recommendation
Let risk totals treat an unpriceable supply leg as zero-value collateral instead of aborting: skip/zero the leg's contribution in `calculate_account_risk_totals` when `cached_price` fails (or pre-filter legs via `resolve_status`-style soft quotes), so liquidation proceeds against the priceable collateral. Equivalently, restrict the pro-rata seizure/HF computation to legs with usable prices. Alternatively, prevent planting: require a successful strict price read for the supplied asset inside `supply`/`merge_supply_leg` when the account carries debt.

### Proof of Concept
```rust
// tests/test-harness/tests/controller/audit_supply_stale_shield.rs
// (existing reproduction, abbreviated)
t.supply(ALICE, "USDC", 10_000.0);
t.borrow(ALICE, "ETH", 3.0);                       // healthy

// 1. Break the target feed (or, for an AquariusLp-priced leg,
//    withdraw own pool liquidity below min_pool_value_wad).
t.mock_reflector_client()
    .set_price_at(&wbtc, &usd(60_000), &(now - 3_600)); // stale

// 2. Supply path accepts the leg anyway — no price needed.
t.try_supply(ALICE, "WBTC", 0.001).unwrap();

// 3. Crash the real collateral; account is now HF < 1.
t.set_price("USDC", usd_cents(50));

// 4. Every rescue path reverts inside calculate_account_risk_totals.
assert_contract_error(t.try_liquidate(LIQUIDATOR, ALICE, "ETH", 1.0), PRICE_FEED_STALE);
assert_contract_error(t.try_clean_bad_debt_by_id(alice_id),        PRICE_FEED_STALE);
assert_contract_error(t.try_withdraw(ALICE, "WBTC", 0.0001),       PRICE_FEED_STALE);
// Debt keeps accruing; liquidation impossible until the feed heals.
```

pub(crate) fn force(env: &Env, outcome: &Outcome, oracle: Option<&AssetOracle>) -> PriceFeedRaw {
    if let Some(err) = outcome.failure(oracle) {
        panic_with_error!(env, err);
    }
    let Some(oracle) = oracle else {
        panic_with_error!(env, OracleError::OracleNotConfigured)
    };
    outcome.to_feed(oracle.asset_decimals)
}
