### Title
Webhook signature verification keys off `repository.owner.login` while `pull_request` handlers act on `repository.full_name`, letting a no-secret org's identity authorize writes to a different org's `PullRequest` - (File: app/controllers/shipit/webhooks_controller.rb, lib/shipit/github_app.rb, app/models/shipit/webhooks/handlers/pull_request/edited_handler.rb)

### Summary
`WebhooksController#verify_signature` selects the `GitHubApp` (and therefore the HMAC secret) using `repository_owner`, which reads only `params.dig('repository','owner','login')`, while every `pull_request` handler — including `EditedHandler` — resolves the actual `Shipit::Repository`/`PullRequest` to mutate using the independent `params.repository.full_name` field. Because `GitHubApp#verify_webhook_signature` returns `true` unconditionally when the selected org has no configured `webhook_secret`, an attacker who names a no-secret org in `owner.login` gets automatic signature-verification success while `full_name` can point at an entirely different, secret-protected victim repository, whose persisted `PullRequest` record is then overwritten with attacker-controlled JSON.

### Finding Description
The broken binding, stated as an equality that should hold but does not:
`org_used_to_verify_signature(params.repository.owner.login) == org_that_owns_the_repository_mutated(params.repository.full_name.split('/').first)`

Trace:
1. `WebhooksController#verify_signature` (app/controllers/shipit/webhooks_controller.rb:24-30) computes `github_app = Shipit.github(organization: repository_owner)` where `repository_owner` (line 59-62) is `params.dig('repository','owner','login') || params.dig('organization','login')`.
2. `GitHubApp#verify_webhook_signature` (lib/shipit/github_app.rb:76-83) contains `return true unless webhook_secret` — if the org picked in step 1 has no `webhook_secret` configured in Shipit's config, **any** signature (even a garbage one, or none) is accepted for the entire request body.
3. `EditedHandler` never re-checks that org. It builds its own repository scope purely from `params.repository.full_name` (edited_handler.rb:33-35, 63-65): `Shipit::Repository.from_github_repo_name(params.repository.full_name)`, then does `Shipit::PullRequest.joins(:stack, stack: :repository).find_by(number: params.number, stacks: { repositories: { id: repository.id } })` (lines 49-61) and finally `pull_request.update(github_pull_request: params.pull_request)` (line 44).
4. Nothing anywhere compares `params.repository.owner.login` to `params.repository.full_name`'s owner segment, and no downstream validation (`ExplicitParameters` schema only checks types/presence, not cross-field consistency) closes this gap.

Attacker's request: forge `POST /webhooks` with header `X-Github-Event: pull_request`, any `X-Hub-Signature` value, and a JSON body where `repository.owner.login` = an org that is configured in Shipit but has no `webhook_secret` set, and `repository.full_name` = `"victim-org/victim-repo"` (a real repository/stack Shipit tracks, with `ignore_ci: true`), `number` = an existing PR number on that stack, `action: "edited"`, and `pull_request` containing attacker-chosen `head.sha`, `head.ref`, `title`, `labels`, `assignees`, etc.

Exploit flow: `verify_signature` resolves the GitHub app for the no-secret org and trivially passes (`return true unless webhook_secret`) regardless of the actual `X-Hub-Signature` sent. `Shipit::Webhooks.for_event('pull_request')` dispatches to `EditedHandler`, which looks up the repository by `full_name` (the victim's real repo) and updates the persisted `PullRequest#github_pull_request` for the victim stack — a write to a repository/stack that never authenticated this webhook at all. Combined with `Commit#deployable?` (app/models/shipit/commit.rb:227-229): `!locked? && (stack.ignore_ci? || (success? && !blocked?))`, once `stack.ignore_ci?` is true, CI status is bypassed entirely, so any commit associated through the corrupted PR/merge-request state (`github_pull_request` feeds `MergeRequest`/`PullRequest` logic referenced across `app/models/shipit/merge_request.rb` and `app/models/shipit/pull_request.rb`) is treated as shippable.

Existing guards do not stop this: `drop_unhandled_event`, `ExplicitParameters` (type/presence only), `force_github_authentication`, `User#authorized?`, `require_permission!`, and model validations on `Repository`/`Stack` are irrelevant to this unauthenticated webhook path, and none of them cross-check `owner.login` against `full_name`.

### Impact Explanation
The write lands in the `PullRequest` record of a repository/stack that is not the one whose secret authenticated the request — this matches "a payload for one repository mutating another's stack, commit, task or team" (Critical). The mutated `github_pull_request` JSON feeds PR/merge-request state consumed elsewhere in the app (`app/models/shipit/merge_request.rb`, `app/models/shipit/pull_request.rb`, `app/serializers/shipit/pull_request_serializer.rb`), and on an `ignore_ci: true` stack, `Commit#deployable?` removes the CI gate, so any commit tied into this corrupted merge/PR state can proceed toward deploy without genuine CI success. This is repeatable against any Shipit-tracked repository as long as at least one configured GitHub org in the same Shipit instance lacks a `webhook_secret`.

### Likelihood Explanation
Preconditions: (a) the Shipit instance has at least one configured GitHub org/app entry with no `webhook_secret` set (a realistic and common misconfiguration in multi-org Shipit deployments), and (b) a victim stack exists with `ignore_ci: true` and a tracked open pull request. No GitHub or Shipit secrets, no session, and no API token are required — the attacker only needs to know or guess a real victim `owner/repo` and PR `number` (both are public GitHub information for public repos). The attack is a single unauthenticated HTTP POST and is trivially repeatable.

### Recommendation
Verify the webhook signature and select the signing org using the same field (`repository.full_name`'s owner, or an explicit cross-check that `repository.owner.login == full_name.split('/').first`) that handlers use to resolve records; reject requests where they diverge. Additionally, do not treat a missing `webhook_secret` as automatic verification success for organizations that host real Shipit-tracked repositories — require an explicit "no verification" opt-in per org rather than an implicit bypass.

### Proof of Concept
minitest plan (under `test/controllers/webhooks_controller_test.rb` pattern, no live GitHub):
1. Configure two orgs in `Shipit.github_apps` for the test: `"no-secret-org"` (no `webhook_secret`) and `"victim-org"` (with a `webhook_secret`).
2. Create `victim_repo = Shipit::Repository.create!(owner: "victim-org", name: "victim-repo")`, a `Shipit::Stack` with `ignore_ci: true` on it, and a `Shipit::PullRequest` with `number: 42` and an initial `github_pull_request` value.
3. Assert the pre-state binding: `pull_request.github_pull_request["head"]["sha"] == "original_sha"`.
4. POST to `/webhooks` with `X-Github-Event: pull_request`, an arbitrary/invalid `X-Hub-Signature`, and body: `{ "action": "edited", "number": 42, "pull_request": { ..., "head": { "sha": "attacker_sha", "ref": "attacker-branch" }, ... }, "repository": { "owner": { "login": "no-secret-org" }, "full_name": "victim-org/victim-repo" }, "sender": { "login": "attacker" } }`.
5. Assert response is `200 OK` (not `422`), proving `verify_signature` passed despite no secret matching `victim-org`.
6. Reload `pull_request` and assert `pull_request.github_pull_request["head"]["sha"] == "attacker_sha"`, proving the victim's `PullRequest` was mutated by a request that never authenticated against `victim-org`'s secret — violating the stated invariant.
```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
