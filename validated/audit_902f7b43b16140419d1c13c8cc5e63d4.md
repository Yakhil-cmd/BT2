### Title
Missing Zero-Address Check on `_to` in `requestKLAYTransfer` Causes Permanent KLAY Loss on Destination Bridge — (File: `contracts/service_chain/bridge/BridgeTransferKLAY.sol`)

---

### Summary

`requestKLAYTransfer` and its internal helper `_requestKLAYTransfer` in `BridgeTransferKLAY.sol` accept a caller-supplied `_to` address with no zero-address guard. A user who calls `requestKLAYTransfer(address(0), _value, _extraData)` locks their KLAY in the source bridge and causes the bridge operator to relay a `handleKLAYTransfer` call on the counterpart chain that sends KLAY to `address(0)` via a low-level `.call.value()`. Because a low-level call to `address(0)` succeeds in the EVM, the KLAY is permanently burned on the destination chain and the source-side KLAY is permanently locked in the bridge with no recovery path.

---

### Finding Description

`requestKLAYTransfer` is a public, permissionless function callable by any user:

```solidity
// BridgeTransferKLAY.sol line 132
function requestKLAYTransfer(address _to, uint256 _value, bytes calldata _extraData) external payable {
    uint256 feeLimit = msg.value.sub(_value);
    _requestKLAYTransfer(_to, feeLimit, _extraData);
}
```

`_requestKLAYTransfer` performs no zero-address check on `_to`:

```solidity
// BridgeTransferKLAY.sol line 103-124
function _requestKLAYTransfer(address _to, uint256 _feeLimit, bytes memory _extraData)
    internal unlockedKLAY nonReentrant
{
    require(isRunning, "stopped bridge");
    require(msg.value > _feeLimit, "insufficient amount");
    uint256 fee = _payKLAYFeeAndRefundChange(_feeLimit);
    emit RequestValueTransfer(TokenType.KLAY, msg.sender, _to, address(0), ...);
    requestNonce++;
}
```

The emitted `RequestValueTransfer` event with `to = address(0)` is picked up by the bridge operator daemon (`handleRequestValueTransferEvent` in `node/sc/bridge_manager.go`), which also performs no zero-address check and directly relays the value to the counterpart bridge:

```go
// node/sc/bridge_manager.go line 333
handleTx, err = bi.bridge.HandleKLAYTransfer(auth, txHash, from, to, valueOrTokenId, ...)
```

On the counterpart chain, `handleKLAYTransfer` executes the transfer using a low-level call:

```solidity
// BridgeTransferKLAY.sol line 98-99
(bool ok, ) = _to.call.value(_value)("");
require(ok, "handleKLAYTransfer: transfer failed");
```

In the EVM, `address(0).call{value: v}("")` returns `(true, "")` — the call succeeds, the `require` passes, and the KLAY is permanently sent to `address(0)`.

---

### Impact Explanation

- **Destination chain**: KLAY equal to `_value` is permanently burned (sent to `address(0)`) on the counterpart bridge chain. The funds are irrecoverable.
- **Source chain**: The user's KLAY (`msg.value`) is permanently locked inside the source bridge contract. There is no refund or recovery mechanism triggered by a zero-address destination.
- Both losses occur atomically from the user's perspective: one transaction on the source chain triggers the irreversible destruction of assets on both sides.

This is an **unauthorized burn of bridged KAIA/KLAY** matching the allowed impact gate: "Unauthorized transfer, mint, unlock, burn … affecting KAIA, bridged assets, or system-managed funds."

---

### Likelihood Explanation

The trigger is a single permissionless call by any user. No special role, no majority-validator collusion, and no compromised key is required. The scenario is directly analogous to the Gearbox reference bug: a user who mistakenly (or deliberately) passes `address(0)` as the recipient loses all assets with no on-chain protection. The fallback function `()` is hardcoded to use `msg.sender` so it is safe, but the explicit `requestKLAYTransfer` entry point is fully exposed.

---

### Recommendation

Add a zero-address guard at the earliest entry point, inside `_requestKLAYTransfer`, so all callers (both `requestKLAYTransfer` and the fallback) are protected:

```solidity
function _requestKLAYTransfer(address _to, uint256 _feeLimit, bytes memory _extraData)
    internal unlockedKLAY nonReentrant
{
    require(_to != address(0), "zero recipient");   // <-- add this
    require(isRunning, "stopped bridge");
    require(msg.value > _feeLimit, "insufficient amount");
    ...
}
```

The same guard should be added to `_requestERC20Transfer` and `_requestERC721Transfer` for consistency, even though the OpenZeppelin token internals would revert on the handle side for those token types (causing a different bridge-stuck issue rather than silent asset loss).

---

### Proof of Concept

1. Deploy the `Bridge` contract (service-chain bridge) with KLAY liquidity on the counterpart chain.
2. Call `requestKLAYTransfer(address(0), 1 ether, "0x")` with `msg.value = 1 ether` from any EOA.
3. Observe: source bridge balance increases by `1 ether`; `RequestValueTransfer` event emitted with `to = 0x0000…0000`.
4. Bridge operator daemon reads the event and submits `handleKLAYTransfer(txHash, from, address(0), 1 ether, nonce, blockNum, "0x")` on the counterpart chain.
5. Inside `handleKLAYTransfer`: `(bool ok,) = address(0).call{value: 1 ether}("")` → `ok == true`, `require` passes.
6. Counterpart bridge balance decreases by `1 ether`; `address(0)` balance increases by `1 ether` (permanently inaccessible).
7. User has lost `1 ether` on the destination chain and `1 ether` is locked in the source bridge — total loss of `2 ether` worth of KLAY.
