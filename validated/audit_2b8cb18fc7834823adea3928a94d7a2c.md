### Title
Cross-organization team-membership injection via unscoped `github_id` lookup in `MembershipHandler` - (File: `app/models/shipit/webhooks/handlers/membership_handler.rb`)

### Summary
`MembershipHandler#find_or_create_team!` resolves the target `Team` solely by `params.team.id` (`github_id`), with no check that the found/created `Team#organization` matches `params.organization.login` from the same payload. In a multi-organization Shipit deployment, an org that legitimately owns its own `webhook_secret` can sign a `membership` webhook whose `team.id` collides with a `Shipit::Team` record that actually belongs to a different configured organization, causing an attacker-chosen `member.login` to be added to that unrelated team's `memberships`.

### Finding Description
Broken binding: `Membership#team_id` (and thus the `github_id` a webhook is allowed to affect) should equal a `github_id` that GitHub actually issued for a team under `params.organization.login`. Instead, `Team.find_or_create_by!(github_id: params.team.id) { |team| team.github_team = params.team; team.organization = params.organization.login }` [1](#0-0)  only sets `organization`/`slug`/`name` in the creation block, which ActiveRecord skips whenever a record with that `github_id` **already exists**. If a `Team` row for a different org (e.g. one loaded via `Shipit.github_teams`, see `lib/shipit.rb:256-258`) already has that `github_id`, `find_or_create_by!` simply returns it unmodified — `params.organization.login` is never compared against the existing `team.organization`.

Webhook signature verification is org-scoped but not team-scoped: `WebhooksController#verify_signature` calls `Shipit.github(organization: repository_owner)`, and for `membership` events `repository_owner` falls back to `params.dig('organization', 'login')` — an attacker-supplied field [2](#0-1) . In a multi-org config (`secrets.github` keyed by organization, each with its own `webhook_secret`, see `config/secrets.development.example.yml:18-38` and `lib/shipit.rb:170-200`), an org that is legitimately configured in Shipit can correctly sign its own payload with its own secret, satisfying `verify_webhook_signature`, while embedding an arbitrary `team.id` that belongs to a totally different tenant org.

Exploit flow:
1. Shipit is configured for multiple GitHub orgs (`attacker-org` and `victim-org`), each with distinct `webhook_secret`s, as supported by `github_app_config` [3](#0-2) .
2. Attacker, who administers `attacker-org` (and thus knows `attacker-org`'s legitimate `webhook_secret`), sends `POST /webhooks` with `X-Github-Event: membership`, a valid HMAC signature computed with `attacker-org`'s secret, `organization.login = "attacker-org"`, but `team.id` set to the `github_id` of a `Shipit::Team` known to belong to `victim-org`, and `member.login` set to the attacker's own GitHub login.
3. `verify_signature` passes because `Shipit.github(organization: "attacker-org")` is the correct app/secret for the signed payload.
4. `MembershipHandler#process` calls `find_or_create_team!`, which finds the pre-existing `victim-org` `Team` by `github_id` and returns it without any re-validation against `organization.login`.
5. `team.add_member(member)` adds the attacker's `User` to that `victim-org` team's `memberships`, with no call to `Shipit.github(organization:).api` to confirm the claimed team really belongs to `attacker-org` or that the member is actually part of it.

Existing guards do not stop this: `verify_signature`/`verify_webhook_signature` only prove the message came from *some* configured org, not that the referenced `team.id` belongs to that org; the `ExplicitParameters` schema only enforces types/presence, not cross-field ownership; there is no `require_permission!`/`force_github_authentication` on the webhooks path since it is unauthenticated by design and relies entirely on HMAC + payload content for trust boundaries.

### Impact Explanation
An attacker who controls (as an org owner/admin) any organization that Shipit has legitimately configured with its own webhook can add an arbitrary GitHub login as a member of any `Shipit::Team` record whose `github_id` they can guess or discover, regardless of which org that team actually belongs to. If that `Team` is part of `Shipit.github_teams` (used for authorization decisions via `User#authorized?`), this constitutes escalation into `Shipit.github_teams` authorization for a tenant the attacker does not control — matching the High severity category ("escalation into `Shipit.github_teams` authorization"). The action is repeatable per team/org pair and blast radius spans every tenant sharing the same Shipit multi-org instance.

### Likelihood Explanation
Requires a multi-organization Shipit deployment (`secrets.github` keyed by multiple orgs) where the attacker is an owner/admin of at least one configured org (able to legitimately know that org's `webhook_secret` — a normal condition for that org's admin, not a Shipit operator secret). The attacker must also know or guess the numeric `github_id` of the victim team stored in Shipit's DB, which is plausible since these are often discoverable (public team pages, prior webhook traffic, sequential IDs, or Shipit's own team listings). In a single-org Shipit deployment this bug is not exploitable because `organization.login` is effectively pinned to the one configured org. Given the precondition (multi-org config + attacker being an admin of one configured org), the attack is low-cost and fully repeatable.

### Recommendation
In `MembershipHandler#find_or_create_team!`, after finding/creating the `Team`, verify `team.organization.casecmp(params.organization.login).zero?` and reject (raise) the event if it doesn't match; additionally, re-fetch or verify the team via `Shipit.github(organization: params.organization.login).api` before trusting `team.id`/`slug`/`name` from the payload, rather than trusting the raw webhook body as sole source of truth for identity.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (conceptual addition)
test ":membership from a different configured org cannot add members to another org's team" do
  victim_team = shipit_teams(:shopify_developers) # organization: 'shopify', github_id known
  Shipit.stubs(:github).with(organization: 'attacker-org').returns(
    stub(verify_webhook_signature: true)
  )
  @request.headers['X-Github-Event'] = 'membership'
  payload = {
    action: 'added',
    team: { id: victim_team.github_id, name: 'Attacker Team', slug: 'attacker-team', url: 'https://example.com' },
    organization: { login: 'attacker-org' },
    member: { login: 'attacker-login' },
    repository: { owner: { login: 'attacker-org' } }
  }.to_json

  post :create, body: payload, as: :json

  assert_response :ok
  refute_equal 'attacker-org', victim_team.reload.organization
  assert victim_team.members.exists?(login: 'attacker-login'),
         "attacker-controlled user should NOT have been added to victim-org's team, but binding is broken"
end
```
Both sides of the binding (`Team#organization` before vs. after the webhook, and `params.organization.login`) diverge: the team keeps `organization == 'shopify'` while the request claimed `organization.login == 'attacker-org'`, yet the membership write still succeeds.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping
      head(:ok) if event == 'ping'
    end

    end
