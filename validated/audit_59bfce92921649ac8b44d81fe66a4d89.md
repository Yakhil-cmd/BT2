### Title
StatusHandler#process mutates Commit/Status rows across repositories without resolving `repository.full_name` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`Shipit::Webhooks::Handlers::Handler` exposes `#stacks`, which scopes any lookup to the repository resolved from `payload.dig('repository', 'full_name')` [1](#0-0) . `CheckSuiteHandler#process` uses this scope (`stacks.where(branch: ...)`) before touching any commit [2](#0-1) , but `StatusHandler#process` looks up commits globally by SHA with `Commit.where(sha: params.sha)` and never calls `#stacks` or `#repository_name` [3](#0-2) .

### Finding Description
Binding claimed: `StatusHandler#process` resolves `repository_name` (i.e. `payload.dig('repository','full_name') == commit.stack.repository.full_name`) before calling `commit.create_status_from_github!`. Tracing the code shows this equality is never checked.

- `WebhooksController#create` parses the raw JSON body and dispatches it unmodified to `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` [4](#0-3) .
- `verify_signature` only checks the HMAC signature against `Shipit.github(organization: repository_owner)`, i.e. the GitHub App/organization-level secret, not anything specific to the individual repository named in the payload [5](#0-4) . It does not verify that `repository.full_name` matches any known Shipit stack, nor does it bind the SHA to a specific repo.
- `Handler#initialize` just parses params from the raw payload and does not enforce repository scoping at the base class level; only the opt-in `#stacks` helper does that [6](#0-5) .
- `StatusHandler#process` runs `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` — an unscoped, cross-tenant query against the entire `commits` table keyed only by `sha` [3](#0-2) . This directly contrasts with `CheckSuiteHandler#process`, which first narrows to `stacks` derived from the payload's repository before touching any commit [2](#0-1) .
- `Commit#create_status_from_github!` calls `statuses.replicate_from_github!(stack_id, github_status)` [7](#0-6) , which creates a `Status` row scoped to `commit.stack_id` — the stack of whatever commit happened to match the SHA, regardless of which repository's webhook produced the request. `Status#replicate_from_github!` performs `find_or_create_by!` keyed on `stack_id`, `state`, `description`, etc., with no repository check at all [8](#0-7) .
- `Status#after_create :enable_ci_on_stack` and `after_commit :schedule_continuous_delivery, :broadcast_update` then act on `commit.stack`, which can belong to a different tenant than the one whose webhook fired [9](#0-8) , and `enable_ci_on_stack`/`schedule_continuous_delivery` can trigger downstream automated merges/deploys on that unrelated stack.

Exploit flow: an attacker who controls a repository whose organization is already connected to Shipit (so `verify_signature` succeeds using that org's shared GitHub App secret) pushes a commit whose SHA is known to also exist in another stack's history (e.g., a shared upstream commit, a cherry-picked/rebased commit, or a commit copied into a fork that is also tracked by Shipit under a different `Stack`). The attacker triggers (or POSTs a `status` webhook mimicking) a status change with `state: 'success'` for that SHA. Because `StatusHandler#process` matches purely on `sha` across the whole `commits` table, the forged status is written against the victim stack's commit, potentially flipping it to `success` and triggering `ProcessMergeRequestsJob`/continuous delivery on a repository the attacker never authenticated against.

Existing guards fail to prevent this: `verify_signature` binds only to the organization-level secret, not to the specific repository asserted in the payload's `repository.full_name`; the `ExplicitParameters` schema on `StatusHandler` validates types (`sha`, `state`, etc.) but not repository consistency; and `drop_unhandled_event`/`check_if_ping` are irrelevant to this path.

### Impact Explanation
An attacker can write a `Status` row (and cascade into `enable_ci_on_stack`, `schedule_continuous_delivery`, `ProcessMergeRequestsJob`) against a `Commit`/`Stack` belonging to a repository they do not own or control, as long as they can produce (or find) a colliding SHA and can get a validly-signed `status` webhook delivered (e.g., from their own repository under an org already onboarded to Shipit). This is a cross-tenant mutation of `Commit`/`Stack` state — matching the Critical category "a payload for one repository mutating another's stack, commit ... row." The blast radius spans every stack/repository whose commits share a SHA with the attacker-controlled repository, and it is repeatable for any such repository pair.

### Likelihood Explanation
Preconditions: the attacking repository's GitHub organization/App installation must already be configured in Shipit (so `verify_signature` accepts the signature), and a colliding commit SHA must exist between the attacker's repository and a victim stack (realistic for forks, mirrors, monorepos, or shared upstream branches within the same org — a common Shipit deployment pattern). No Shipit session, API token, or GitHub secret is required beyond normal repository push access and the ability to trigger (or directly send, if signature can be produced) a `status` event. This is feasible without any privileged role and is fully repeatable against any repository sharing the org-level webhook trust boundary.

### Recommendation
Scope `StatusHandler#process` the same way `CheckSuiteHandler#process` does: resolve `stacks` (or otherwise verify `payload.dig('repository','full_name')` matches `commit.stack.repository.full_name`) before calling `commit.create_status_from_github!`, e.g. filter `Commit.where(sha: params.sha)` to only those commits whose `stack` is contained in `stacks`.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_scoping_test.rb
require 'test_helper'

module Shipit
  module Webhooks
    module Handlers
      class StatusHandlerScopingTest < ActiveSupport::TestCase
        test "CheckSuiteHandler#process scopes lookups via #stacks (repository-scoped)" do
          handler = CheckSuiteHandler.new(check_suite_payload_for('victim/repo'))
          handler.expects(:stacks).returns(Stack.none)
          handler.process # should not raise, and #stacks was consulted
        end

        test "StatusHandler#process never resolves repository_name yet still mutates Commit/Status" do
          victim_commit = shipit_commits(:first) # belongs to a DIFFERENT repository/stack
          attacker_payload = {
            'sha' => victim_commit.sha,
            'state' => 'success',
            'repository' => { 'full_name' => 'attacker/unrelated-repo' }
          }

          handler = StatusHandler.new(attacker_payload)
          handler.expects(:repository_name).never
          handler.expects(:stacks).never

          assert_difference -> { victim_commit.statuses.count }, 1 do
            handler.process
          end
        end
      end
    end
  end
end
```
Both assertions demonstrate the asymmetry: `CheckSuiteHandler` cannot mutate state without consulting `#stacks` (repository-scoped), while `StatusHandler` mutates `victim_commit`'s `Status` (and thus its `Stack`) despite never invoking `#repository_name`/`#stacks`, confirming the cross-tenant write via `Commit.where(sha: ...)` in `StatusHandler#process`.
