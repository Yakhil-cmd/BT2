This confirms Shipit supports multi-organization GitHub App configuration, where each organization key in `secrets.github` has its own `webhook_secret` [1](#0-0) . This is exactly the binding-breaking pattern requested.

### Title
Webhook signature verified against `repository.owner.login`'s organization while handlers act on the unrelated `repository.full_name` field - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects the GitHub App/organization secret to verify the HMAC signature using `params.dig('repository', 'owner', 'login')` (falling back to `organization.login`), but every webhook handler resolves the actual `Stack`/`Repository` to mutate using the independent `repository.full_name` field, which is never checked for consistency with `owner.login`.

### Finding Description
In multi-org mode, `Shipit.github(organization:)` loads a per-organization `webhook_secret` from `secrets.github[org]` [1](#0-0) . `WebhooksController#verify_signature` picks that organization purely from the payload's `repository.owner.login` (or `organization.login`) field and uses it to verify `X-Hub-Signature`: [2](#0-1) .

Once the signature check passes, `create` dispatches the raw, attacker-supplied JSON body to the registered handler for the event, without re-validating that the organization used for verification matches anything else in the payload: [3](#0-2) .

Every handler, however, determines the target repository/stack using a completely different field, `repository.full_name`, via `Repository.from_github_repo_name`: [4](#0-3)  and similarly in `PullRequest` handlers such as `OpenedHandler`, `LabeledHandler`, `UnlabeledHandler`, `LabelCapturingHandler`, and `AssignedHandler`: [5](#0-4) [6](#0-5) . `Repository.from_github_repo_name` simply splits `"owner/name"` and looks it up directly, with no cross-check against the signing organization: [7](#0-6) .

The broken equality is:
`organization authenticated (repository.owner.login used to fetch webhook_secret)` ≠ `repository actually written (repository.full_name used by the handler)`.

Both fields are attacker-controlled in the raw JSON body (there is no re-derivation from a trusted GitHub source—everything comes from `request.raw_post`), so an attacker who controls (or has compromised) any organization/installation configured under `secrets.github` with its own `webhook_secret` can craft a payload where:
- `repository.owner.login` = the org they control (so `verify_signature` fetches that org's secret and their self-computed HMAC validates), and
- `repository.full_name` = `"victim-org/victim-repo"`, an entirely unrelated organization/repository also configured in the same Shipit instance.

The signature check passes because it uses the attacker's own secret, but the handler then operates on the victim repository resolved from `full_name`.

### Impact Explanation
Handlers keyed off `full_name` perform real actions on `Stack`/`ReviewStack` records: `PushHandler` triggers `stack.sync_github(expected_head_sha: ...)` on the victim's stacks [8](#0-7) , and PR handlers can archive/unarchive review stacks or open/provision review stacks for the victim's repository (`LabeledHandler#handle`, `OpenedHandler#process`) [9](#0-8) [10](#0-9) . This is a cross-repository/cross-organization write: an attacker with a legitimately configured but unrelated organization can force stack sync, archive/unarchive, or provisioning actions against a victim's repository they were never granted access to, satisfying the "cross-repository writes" / "unauthorized deploy trigger via sync" high/critical impact bar.

### Likelihood Explanation
This requires the attacker to control (or have compromised) at least one organization entry configured in the Shipit instance's `secrets.github` multi-org map with its own `webhook_secret`—this is plausible in any Shipit deployment serving multiple organizations/tenants, which is precisely the use case the multi-org `github_app_config` mechanism exists for [11](#0-10) . No GitHub App private key, no `ApiClient` token, and no privileged Shipit account are needed—only the ability to sign a request with a secret belonging to one configured org while spoofing the `full_name` of another.

### Recommendation
After signature verification, `verify_signature` (or the handlers) should ensure the organization used to verify the signature matches the owner segment of `repository.full_name` for every payload, rejecting (422) any mismatch. Alternatively, derive the repository unambiguously from the same field used for signature verification, rather than trusting two independently attacker-controlled JSON fields to agree.

### Proof of Concept
1. Configure Shipit with two organizations in `secrets.github`: `attacker-org` (attacker installs the GitHub App, knows its `webhook_secret`) and `victim-org` (hosts `victim-org/victim-repo`, has a `Stack` configured in Shipit).
2. Attacker crafts a `push` event JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC(attacker-org's webhook_secret, raw_body)` and sets `X-Github-Event: push`.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: 'attacker-org')` and successfully verifies the attacker's own signature [12](#0-11) .
5. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name('victim-org/victim-repo')` [4](#0-3)  and calls `stack.sync_github(expected_head_sha: <attacker-chosen sha>)` on the victim's stack [8](#0-7) , an action the attacker was never authorized to trigger on `victim-org/victim-repo`.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping
