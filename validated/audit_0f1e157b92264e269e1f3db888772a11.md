## Title
Webhook signature verified against the `repository.owner.login` organization while event handlers act on the (independently attacker-controlled) `repository.full_name` field - ([File: app/controllers/shipit/webhooks_controller.rb])

## Summary
`Shipit::WebhooksController#verify_signature` selects the GitHub App/organization config (and thus the HMAC `webhook_secret`) using `repository.owner.login` (or `organization.login`) from the raw JSON payload, then verifies the `X-Hub-Signature` HMAC against the whole raw body. Every downstream event `Handler`, however, resolves the target `Repository`/`Stack` to act on using a *different* field of the very same payload: `repository.full_name`. Because the HMAC only proves the payload came from whoever holds the secret for the organization named in `repository.owner.login`, and does not tie that verification to `repository.full_name`, an attacker who legitimately controls one organization's webhook secret (e.g. by installing/configuring the multi-org GitHub App config on their own org, which is a supported, documented configuration in this engine) can craft a payload whose `repository.owner.login` matches their own org (so it authenticates) while `repository.full_name` points at a victim repository/stack, causing the victim stack to be manipulated with a signature that only proves authenticity for a different organization.

## Finding Description
The trust boundary is: **the organization whose secret validated the signature MUST equal the repository the handler acts upon**. This binding is broken:

- Verification uses `repository_owner`, derived only from `repository.owner.login`/`organization.login`, to pick the `GitHubApp` (and its `webhook_secret`) via `Shipit.github(organization: repository_owner)`, then calls `github_app.verify_webhook_signature(signature, raw_post)`: [1](#0-0) [2](#0-1) 

- `verify_webhook_signature` only proves the raw body bytes were HMAC-signed with *some* org's secret; it never checks that the org matches the repository being mutated: [3](#0-2) 

- Multiple organizations can be configured with independent `webhook_secret`s under `secrets.github`, each selected purely by name: [4](#0-3) 

- After verification succeeds, the entire raw payload is dispatched to handlers keyed only by event type, with no re-check of which org's secret validated it: [5](#0-4) 

- Every handler resolves its target repository from `payload.dig('repository', 'full_name')`, a field independent of `repository.owner.login`: [6](#0-5) [7](#0-6) [8](#0-7) 

Because `repository.owner.login` and `repository.full_name` are two independently-attacker-supplied JSON fields inside the same signed body, nothing forces `full_name` to start with `owner.login/`. An attacker who is an authenticated member of any organization configured in `secrets.github` (each with its own installed GitHub App and independent `webhook_secret`) can send a POST to `/webhooks` with:
```json
{"repository": {"owner": {"login": "attacker-org"}, "full_name": "victim-org/victim-repo"}, "ref": "refs/heads/main", "after": "<attacker-sha>"}
```
signed with `attacker-org`'s own `webhook_secret` (which the attacker legitimately knows, since it's their own GitHub App installation). `verify_signature` computes `repository_owner == "attacker-org"`, fetches `attacker-org`'s `GitHubApp`, and the HMAC check passes because the attacker signed with the correct (their own) secret. The payload is then forwarded to `PushHandler`, which looks up stacks by `repository.full_name == "victim-org/victim-repo"` and triggers `stack.sync_github(expected_head_sha: params.after)` on the victim's stack — an org whose secret never authenticated this request.

**Equality that should hold, but doesn't:**
`organization that authenticated the signature == repository (owner) that is acted upon by the handler`
Before the fix this is enforced only via a *shared* field (`repository.owner.login`), but the code re-derives the acted-upon repository from an unrelated, independently-controlled field (`repository.full_name`), breaking the equality whenever the attacker controls a second organization's secret.

## Impact Explanation
This allows an attacker who is a legitimate owner of one GitHub App/organization installation in a multi-tenant Shipit instance to inject spoofed webhook events (`push`, `pull_request`, `status`, `check_suite`, `membership`, etc., depending on which handler is targeted) against **any other organization's stacks/repositories** tracked by the same Shipit instance, without ever holding that other org's webhook secret. Depending on the handler this can trigger unwanted `GithubSyncJob`s, review-stack provisioning/archival, PR/status/label state changes on a victim's stack — i.e., cross-repository/cross-organization writes performed under a security guarantee (per-org HMAC signature) that was supposed to prevent exactly this.

## Likelihood Explanation
Requires the Shipit deployment to use the multi-organization `secrets.github` schema (`github_organizations`/`github_app_config`) with at least two organizations configured, and the attacker to control (or have compromised) the webhook secret of one of them — a normal, supported configuration explicitly implemented in `lib/shipit.rb#github_app_config`, not a misconfiguration of the host app. No repository write access, API token, or Shipit session is needed; only the ability to sign a POST body with one org's `webhook_secret`, which the attacker/org owner already legitimately possesses.

## Recommendation
Bind the signature-verifying organization to the same repository field the handlers use to determine the target stack: after computing `repository_owner`, cross-validate that `repository.full_name`'s namespace segment matches `repository_owner` (or verify handlers derive the repository owner from the same value used for signature selection), rejecting mismatched payloads before dispatching to handlers.

## Proof of Concept
1. Configure Shipit with two organizations in `secrets.github`, e.g. `attacker-org` and `victim-org`, each with its own GitHub App installation and `webhook_secret` (a supported configuration per `lib/shipit.rb#github_app_config`).
2. As the owner of `attacker-org`'s GitHub App, compute `X-Hub-Signature: sha1=<hmac>` over the following JSON body using `attacker-org`'s `webhook_secret`:
```json
{"ref":"refs/heads/main","after":"<attacker-controlled-sha>","repository":{"owner":{"login":"attacker-org"},"full_name":"victim-org/victim-repo"}}
```
3. POST this body with header `X-Github-Event: push` to `/webhooks`.
4. `verify_signature` resolves `repository_owner == "attacker-org"`, fetches its `GitHubApp`, and the HMAC verifies successfully (`app/controllers/shipit/webhooks_controller.rb:24-30`, `lib/shipit/github_app.rb:76-83`).
5. `PushHandler#process` resolves stacks via `repository.full_name == "victim-org/victim-repo"` and calls `stack.sync_github(expected_head_sha: "<attacker-controlled-sha>")` on the victim's stack (`app/models/shipit/webhooks/handlers/handler.rb:32-38`, `app/models/shipit/webhooks/handlers/push_handler.rb:12-17`), despite the request never being authenticated as `victim-org`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
