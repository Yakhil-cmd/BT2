## Analysis: Cross-organization commit status forgery via webhook signature scope mismatch

### Title
Webhook signature is verified per-organization but `StatusHandler` writes commit statuses with no repository/organization scoping, allowing a legitimate but unrelated GitHub App tenant to forge CI status for any other tenant's commits - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` authenticates an inbound webhook by selecting a per-organization secret keyed off attacker-supplied payload fields (`repository.owner.login` / `organization.login`) and validating the HMAC over the raw body. [1](#0-0) [2](#0-1) 

This proves only "this payload was signed with organization X's webhook secret." It does not prove which repository the event content actually applies to. `StatusHandler#process`, however, resolves the target purely by commit SHA, globally, with no reference to the organization that authenticated the request or even to `repository.full_name`: [3](#0-2) 

This breaks the trust binding: `organization authenticated (repository_owner used to pick the HMAC secret) == repository/commit being written (Commit.where(sha:))`. Any Shipit tenant that legitimately knows its own GitHub App's `webhook_secret` (an org admin who configured their own App per `docs/setup.md`'s multi-org instructions) can sign an arbitrary payload with that secret while making the payload body's `state`/`context`/`target_url`/`sha` refer to a commit belonging to a completely different organization's stack hosted on the same Shipit instance. [4](#0-3) 

### Finding Description
1. `verify_signature` picks the `GitHubApp` (and its `webhook_secret`) using `repository_owner`, which is read straight from the JSON body the attacker fully controls: [2](#0-1) 
2. Signature validation is a straight HMAC compare using that organization's secret over the raw POST body: [5](#0-4) 
3. Because the attacker knows the secret for "their own" org, they can compute a valid HMAC over a body whose `repository.owner.login` says "my-org" (to pick the known secret) while `sha`/`state`/`context`/`target_url` are freely chosen and unrelated to that org.
4. `StatusHandler#process` never checks which organization or repository the SHA belongs to - it queries `Commit.where(sha: params.sha)` across the entire Shipit database and calls `create_status_from_github!` with fully attacker-controlled `state`, `description`, `target_url`, `context`, `created_at`: [6](#0-5) 
This is confirmed by the existing test, which shows the handler blindly persists whatever `state`/`description`/`context`/`target_url` values are in the payload for a matched commit: [7](#0-6) 

The other handlers (`PushHandler`, `CheckSuiteHandler`) at least scope through `Handler#stacks`, which resolves `Repository.from_github_repo_name(repository_name)`, but `repository_name` (`repository.full_name`) is likewise just another attacker-controlled field in the same signed-by-someone-else payload, independent from `repository_owner` used to select the verifying secret: [8](#0-7) 
`StatusHandler` doesn't even use that (weaker) scoping - it is the most exposed path.

### Impact Explanation
Commit CI status drives Shipit's deploy/merge safety gates (`ci.require`, merge-queue revalidation) described in the README's CI/Merge Queue configuration. By forging a passing status for a commit SHA belonging to a victim organization's repository - using only credentials the attacker legitimately possesses for their *own*, unrelated GitHub App/organization on the same multi-tenant Shipit instance - an attacker can make a victim stack believe CI succeeded for an arbitrary commit, enabling an unauthorized deploy or an unauthorized merge through the merge queue. This satisfies the Critical impact bar of "an unauthorized deploy, rollback, or merge" via a cross-repository write into another organization's `Status`/`Commit` records.

### Likelihood Explanation
Exploitability requires: (1) the target Shipit instance hosts more than one GitHub organization (an explicitly documented and supported configuration), (2) the attacker administers/controls the GitHub App for at least one of those organizations (hence knows its `webhook_secret`), and (3) knowledge of a target commit SHA in the victim repository (public information for public repos, or discoverable via the Shipit UI/API for stacks visible to the attacker). No compromise of the victim org's credentials, no Shipit session, and no privileged Shipit role are required - only the attacker's own legitimately-issued webhook secret for their own tenant.

### Recommendation
In `StatusHandler` (and ideally in the shared `Handler` base), scope any state-changing lookup by the same organization/repository that produced a verified signature, not merely by SHA. Concretely: pass the authenticated `repository_owner`/`installation` context from `WebhooksController` into the handler, and require `Commit.joins(stack: :repository).where(sha: params.sha, repositories: { owner: authenticated_owner })` (or equivalent) before calling `create_status_from_github!`. More generally, `verify_signature` should also assert that `repository.full_name`'s owner matches the organization whose secret validated the signature, rejecting any webhook where these two payload-derived identifiers diverge.

### Proof of Concept
1. Attacker is the admin of `attacker-org`, a GitHub organization that legitimately has its own GitHub App configured in the same Shipit instance's `secrets.yml` (multi-org setup per `docs/setup.md`), and thus knows `attacker-org`'s `webhook_secret`.
2. Attacker obtains the SHA of a commit in `victim-org/victim-repo` that is pending in Shipit's merge queue or deploy safety checks (e.g., from the public GitHub repo or Shipit UI).
3. Attacker crafts a `status` event payload:
```json
{
  "repository": { "owner": { "login": "attacker-org" } },
  "sha": "<victim commit sha>",
  "state": "success",
  "context": "required-ci-context",
  "target_url": "https://attacker.example/fake"
}
```
4. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(attacker-org_webhook_secret, raw_body)` and POSTs to `/webhooks`.
5. `verify_signature` selects `Shipit.github(organization: "attacker-org")` and successfully verifies the signature (it is valid for that org's own secret).
6. `StatusHandler#process` executes `Commit.where(sha: "<victim commit sha>").each { |c| c.create_status_from_github!(params) }`, writing a forged "success" status onto the victim organization's commit with no relation to `attacker-org` whatsoever, potentially unblocking an unauthorized merge or deploy for `victim-org/victim-repo`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
