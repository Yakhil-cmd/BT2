This confirms the analog. `StatusHandler#process` directly persists attacker-supplied `state`, `context`, `target_url`, `description` onto any commit matching `params.sha` (`Commit.where(sha: params.sha)`), with no re-verification against GitHub's API. `Status#replicate_from_github!`/`create_status_from_github!` write these values verbatim, and `Status#schedule_continuous_delivery`/`enable_ci_on_stack` and `MergeRequest#all_status_checks_passed?` (via `StatusChecker`) consume them to gate continuous deployment and PR merges.

### Title
Webhook signature verified against `repository.owner.login`, but Status/Check handlers act on unrelated `repository.full_name` / commit `sha` fields — cross-repository status forgery enabling unauthorized merge/deploy - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects the GitHub App/secret to validate the HMAC signature using `repository_owner`, taken from `params.dig('repository', 'owner', 'login')` (falling back to `params.dig('organization', 'login')`). This value is the only field the controller uses to decide "which organization sent this". It never checks that the `repository.full_name` field — the value handlers actually use to select which `Stack`/`Commit` to mutate — belongs to that same organization. [1](#0-0)  `Webhooks::Handlers::Handler#repository_name` reads `payload.dig('repository', 'full_name')` independently to resolve the target `Repository`/`Stack`. [2](#0-1)  `StatusHandler#process` goes further and doesn't even use `repository_name` — it looks up commits purely by `sha` across the entire installation and writes attacker-controlled status fields directly. [3](#0-2) 

### Finding Description
Binding that should hold: `organization authenticated by verify_signature == organization owning the repository/commit that handlers write to`. Shipit supports multiple GitHub organizations, each with its own `webhook_secret`, configured under `github: <org>: webhook_secret:` [4](#0-3) . Any Shipit administrator who installs the app on their own (attacker-controlled) organization legitimately knows that organization's `webhook_secret` (they set it during GitHub App creation).

`verify_signature` does:
```
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
```
using `repository_owner` from the payload body itself. Since the HMAC is computed over the entire `raw_post`, an attacker who controls org "Attacker" can send a `status` webhook whose top-level `repository.owner.login` (or `organization.login`) is `"Attacker"`, but whose event-specific fields — `sha`, `state`, `context`, `target_url`, `description` — reference a commit belonging to an entirely different, victim stack. Because the signature is validated with Attacker's own known secret, `verify_signature` passes. [1](#0-0) 

`StatusHandler` then processes the event with no organization/repository check at all: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }`. `sha` is globally unique-ish but not scoped to the authenticated org, so any commit sha across any stack hosted by this Shipit instance can be targeted. [5](#0-4) 

`Commit#create_status_from_github!` and `Status.replicate_from_github!` persist the attacker-supplied `state`/`context`/`target_url`/`description` verbatim without contacting GitHub to confirm them. [6](#0-5) [7](#0-6) 

These forged `Status` rows feed directly into merge/deploy gating logic: `MergeRequest#all_status_checks_passed?` / `any_status_checks_failed?` use `StatusChecker` over `head.statuses_and_check_runs`, and `Status#schedule_continuous_delivery` triggers continuous deployment when state becomes `success`. [8](#0-7) [9](#0-8) 

This is the direct analog of the CVGT bug: the report's `config_pool_state_handler`/`initialize_handler` write pool-state fields that are never validated to be "legitimate" for the account performing the action, letting an attacker point staking operations to a spoofed state. Here, the "field acted on" (`repository.full_name` / `sha`, used to pick the Stack/Commit to mutate) is never bound to the "field covered by the verified signature/organization" (`repository.owner.login`), letting a legitimate-but-unprivileged-with-respect-to-victim attacker (admin of any org onboarded to the same Shipit instance) write CI status onto a victim stack's commits.

### Impact Explanation
Forged `success` statuses can unblock the merge queue's `all_status_checks_passed?` check and can trigger `schedule_continuous_delivery`, resulting in an **unauthorized merge or deploy** of a victim's stack — matching the Critical impact bar ("unauthorized deploy, rollback or merge"). It also allows an attacker to forge `failure`/`error` statuses to block legitimate deploys (denial of legitimate service is out of scope, but the merge/deploy bypass direction is in-scope Critical impact).

### Likelihood Explanation
Requires only that: (1) the Shipit instance hosts more than one GitHub organization (a documented, supported configuration — "Using Multiple Github Applications"), and (2) the attacker administers/owns one of those organizations (thus knows its own `webhook_secret`, which is not the victim's secret and not any Shipit-privileged credential). No `ApiClient` token, no GitHub App private key, and no access to the victim org's secrets are required — only the attacker's own legitimately-known webhook secret for their own org's installation and knowledge/guessability of a target commit `sha` in the victim stack.

### Recommendation
In `WebhooksController#verify_signature` and in `Webhooks::Handlers::Handler`/`StatusHandler`, bind the field used for signature-organization selection to the field(s) used for repository/commit resolution: verify that `repository.full_name`'s owner matches the `repository_owner` (or `organization.login`) used to select the signing secret, and scope `StatusHandler`'s `Commit.where(sha: params.sha)` lookup to commits belonging to stacks of the verified repository, not a global `sha` lookup.

### Proof of Concept
1. Shipit instance configured with two orgs: `Victim` (real customer) and `Attacker` (attacker-controlled org that legitimately installed the Shipit GitHub App and therefore knows its own `webhook_secret`).
2. Attacker crafts a `status` webhook payload:
```json
{
  "sha": "<victim commit sha, e.g. head of an open PR>",
  "state": "success",
  "context": "ci/required-check",
  "target_url": "http://attacker.example",
  "repository": { "owner": { "login": "Attacker" }, "full_name": "Attacker/some-repo" }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC(Attacker_webhook_secret, raw_body)` and POSTs to `/webhooks` with `X-Github-Event: status`.
4. `verify_signature` extracts `repository_owner = "Attacker"`, fetches `Shipit.github(organization: "Attacker")`, and successfully validates the signature using the attacker's own known secret. [10](#0-9) 
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)`, finds the victim's commit (unrelated to "Attacker"/"some-repo"), and calls `create_status_from_github!(params)`, writing a fabricated `success` status onto the victim's commit. [5](#0-4) 
6. If this was the last required/missing status for a queued PR, `ProcessMergeRequestsJob`/`MergeRequest#all_status_checks_passed?` merges the victim's PR, or `Status#schedule_continuous_delivery` triggers a deploy — an unauthorized merge/deploy performed by an attacker with no privileges on the victim's stack. [11](#0-10) [9](#0-8)
