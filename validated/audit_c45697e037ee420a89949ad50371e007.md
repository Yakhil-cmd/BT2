### Title
Unvalidated Peer-Supplied `StakingInfo` During Fast Sync Corrupts KEFAddr/KIFAddr Used for Pre-Kaia Block Reward Distribution — (`datasync/downloader/downloader.go`, `datasync/downloader/queue.go`)

---

### Summary

During fast sync, a malicious P2P peer can supply a `P2PStakingInfo` with arbitrary `KEFAddr`/`KIFAddr` values. The downloader writes this data directly to the staking DB via `PutStakingInfoToDB` with no cross-validation against the AddressBook contract state. For pre-Kaia blocks, `GetStakingInfo` treats the DB as the authoritative source and returns the corrupted entry without consulting the state trie, causing block rewards destined for KEF/KIF treasury addresses to be redirected to attacker-controlled addresses.

---

### Finding Description

**1. No validation in `DeliverStakingInfos`**

The `validate` function in `queue.DeliverStakingInfos` is a stub that always returns `nil`:

```go
validate := func(index int, header *types.Header) error {
    // TODO-Kaia-Snapsync update validation logic
    return nil
}
``` [1](#0-0) 

Any `P2PStakingInfo` content — including forged `KEFAddr`/`KIFAddr` — passes through without any check against the block header, the AddressBook contract, or any on-chain state.

**2. `commitPivotBlock` and `commitFastSyncData` write peer data directly to DB**

Both code paths call `PutStakingInfoToDB` unconditionally on the peer-supplied `result.StakingInfo`:

``` [2](#0-1) [3](#0-2) 

`PutStakingInfoToDB` is a direct DB write with no validation: [4](#0-3) 

**3. `GetStakingInfo` uses the DB as the authoritative source for pre-Kaia blocks**

```go

    if si := ReadStakingInfo(s.ChainKv, sourceNum); si != nil {

Once a corrupted entry exists in the DB, it is returned as-is and cached. The state trie is never consulted.

**4. Staking info is only synced for pre-Kaia blocks**

`newFetchResult` only marks a block as requiring staking info when `!isKaiaFork`:

```go

``` [6](#0-5) 

This means the attack surface is pre-Kaia blocks at staking interval boundaries. Post-Kaia blocks bypass the DB entirely and read from state.

**5. Corrupted KEFAddr/KIFAddr directly affects reward distribution**

`specWithProposerAndFunds` and `specWithProposerAndFundsFlex` use `si.KEFAddr`/`si.KIFAddr` directly to route KAIA block rewards:

```go

}
``` [7](#0-6) 

If `KEFAddr` is replaced with an attacker address, the KEF portion of every block reward in the affected staking epoch is sent to the attacker.

### Impact Explanation

For any chain that has pre-Kaia blocks (including Kaia mainnet's historical chain) and any node performing fast sync:

- The attacker connects as a P2P sync peer (permissionless).
- During fast sync, the attacker serves `P2PStakingInfo` with `KEFAddr`/`KIFAddr` replaced by attacker-controlled addresses for one or more staking interval blocks.
- The corrupted entries are written to the staking DB.
- When the node subsequently processes pre-Kaia blocks (either in the `afterP` range or via `PostInsertBlock`), `GetStakingInfo` returns the corrupted DB entry.
- Block rewards (KEF/KIF portions, which are a fixed percentage of every block's minting amount) are transferred to the attacker's address instead of the legitimate treasury addresses.

The KEF+KIF allocation is typically 54%+ of the minting reward per block. Over a full staking epoch (e.g., 86,400 blocks at the default interval), this represents a substantial unauthorized KAIA transfer.

---

### Likelihood Explanation

- **Permissionless entry point**: Any node can connect as a P2P peer and serve staking info during fast sync. No special privileges are required.
- **No detection**: The victim node logs the import but performs no integrity check.
- **Explicitly unimplemented**: The `TODO-Kaia-Snapsync update validation logic` comment confirms this is a known gap, not an oversight.
- **Scope**: Affects any node doing fast sync on a chain with pre-Kaia blocks, which includes all nodes syncing Kaia mainnet from scratch.

---

### Recommendation

In `queue.DeliverStakingInfos`, implement the validation function to cross-check the received `P2PStakingInfo` against the block header's state root. Specifically:

1. After fast sync state is available, re-derive `StakingInfo` from the AddressBook contract at the source block's state and compare `KEFAddr`/`KIFAddr` against the peer-supplied values.
2. Alternatively, reject any `P2PStakingInfo` whose `KEFAddr`/`KIFAddr` do not match the value derivable from the already-validated state trie (which is synced and Merkle-verified independently).
3. At minimum, add a post-sync reconciliation step in `commitPivotBlock` that re-derives staking info from state and overwrites any peer-supplied DB entries.

---

### Proof of Concept

1. Start a victim node in fast sync mode against a chain with pre-Kaia blocks.
2. The attacker's node connects as a P2P peer and responds to `StakingInfoRequestMsg` with a `P2PStakingInfo` where `KEFAddr` is set to `attacker_address` for a staking interval block.
3. The victim's `DeliverStakingInfos` → `queue.DeliverStakingInfos` accepts it (validate returns nil).
4. `commitFastSyncData` or `commitPivotBlock` calls `PutStakingInfoToDB`, writing the forged entry.
5. After fast sync, the victim processes pre-Kaia blocks. `GetStakingInfo` reads the corrupted DB entry and returns `KEFAddr = attacker_address`.
6. `FinalizeState` → `GetDeferredReward` → `specWithProposerAndFunds` routes the KEF portion of block rewards to `attacker_address`.
7. Assert: `state.GetBalance(attacker_address)` increases by the KEF reward amount each block; `state.GetBalance(legitimate_KEF_address)` receives nothing.
