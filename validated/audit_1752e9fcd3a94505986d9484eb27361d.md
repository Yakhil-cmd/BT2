### Title
Malicious secondary-AA recipient can force cascading revert of an entire multi-recipient AA payment, freezing funds owed to unrelated recipients - ([File: aa_composer.js])

### Summary
The Y2K report describes a queue whose progress is blocked because one hostile recipient contract reverts on `onERC1155Received`, and later participants cannot get their funds until they manually delist. The analogous mechanism in `ocore` is the way `handleTrigger()` propagates **secondary AA triggers**: when a primary AA's response pays several output addresses and one of those addresses is itself an AA, that AA is invoked as a "secondary trigger". If that secondary AA's own execution bounces, the failure is not isolated — it causes the *entire* primary response (all payments to all other, unrelated recipients) to be rolled back via `revert()`.

### Finding Description
`handleSecondaryTriggers()` iterates the AA addresses that received outputs from a response unit with `async.eachSeries`, invoking `handleTrigger()` recursively for each one as a secondary trigger: [1](#0-0) 

If any secondary AA bounces (its `onDone` callback is invoked with a `bounce_message`), the series callback treats this as a fatal error for the whole batch and, for a primary (non-secondary) caller, calls `revert(...)`: [2](#0-1) 

`revert()` then rolls back the whole transaction to the initial savepoint, discards every response unit generated so far (including any that already paid out to *other*, well-behaved recipients), clears all accumulated state-variable changes, and re-invokes `bounce()`, which converts the whole trigger into a bounce that returns funds to the *original trigger sender* rather than distributing them as the AA's logic intended: [3](#0-2) [4](#0-3) 

Whether a secondary AA bounces is entirely controlled by that AA's own definition/state: an attacker who controls or authors an AA address (analogous to Alice's `onERC1155Received` that intentionally reverts) can make that AA `bounce(...)` unconditionally whenever it is invoked as a secondary trigger — for example, by always executing `bounce("nope")` in its trigger-handling formula. Because AA addresses are permissionless (anyone can define and publish an AA definition, and any other AA's oscript logic can choose to pay an attacker-supplied/attacker-controlled address as one of several outputs — e.g., in an auction, raffle, marketplace, or payout-splitting AA where a recipient address is taken from `trigger.data` or state), an attacker can insert their own poison-pill AA as one of the recipients of a multi-output AA response. Every time that response is composed, `handleSecondaryTriggers` will hit the malicious AA, it will bounce, and `revert()` will undo the entire batch, including outputs destined for innocent third parties.

This mirrors the Y2K bug class precisely: a single non-cooperative recipient (secondary AA) that always fails its own "receive" callback breaks the shared multi-party operation for everyone else, not just for itself.

### Impact Explanation
Unlike the Y2K case where affected users can "delist" themselves from the queue to escape, victims of this ocore analog have **no self-service remedy**: they are simply outputs in someone else's AA response and cannot remove the malicious AA from that AA's payout logic. Every trigger that would have produced payouts including the malicious secondary AA is converted into a bounce, so:
- Legitimate recipients never receive the funds they were owed by the distributing AA's logic (AA fund freezing/denial of expected payouts).
- The distributing AA's designed behavior (e.g. splitting funds among multiple parties) can be permanently and repeatedly disrupted by a single attacker-controlled address, as long as that address keeps being selected as an output.
- Because the whole state-variable update is also rolled back, any bookkeeping the primary AA intended to perform together with the payment (e.g., marking a payout as done) is undone too, so the operation can be forced to bounce indefinitely — a persistent denial-of-service against fund distribution logic built on top of secondary AA triggers.

This satisfies "AA fund loss or freezing" from the validation criteria: it is not merely a griefing nuisance but a deterministic, repeatable freeze of legitimate recipients' expected funds caused by a single attacker-controlled AA in the DAG.

### Likelihood Explanation
Likelihood is high wherever an AA's oscript logic includes an output address that is influenced by an untrusted party (auction bidder, raffle participant, marketplace counterpart, user-supplied referral/beneficiary address, etc.) and that address happens to be (or can be made to be) an AA address. Defining an AA that always bounces is trivial (a one-line oscript `bounce('x')`), and AA definition/publication is permissionless, so an attacker needs only to get their poison-pill AA address included as one of the outputs of the target composite payment — a common pattern in multi-party payout AAs.

### Recommendation
- Do not let a failure in one secondary trigger revert the entire primary response's other, unrelated payments; isolate/decouple secondary-trigger failures from the primary payment's other outputs (e.g., treat a failed secondary AA delivery the same way a plain non-AA output payment behaves — the coins simply land on the address without forcing any AA-side state changes, and do not roll back sibling outputs).
- Alternatively, when a secondary AA bounces, keep the primary AA's already-produced units/state changes intact and only mark the secondary branch as failed, rather than calling `revert()` for the whole chain.
- Warn/require AA authors that pay attacker-influenceable addresses as part of multi-recipient outputs to use "pull" style secondary payouts (recipient must actively claim) rather than "push" payouts that depend on the recipient AA's cooperative execution, since a hostile secondary AA can currently break the entire batch.

### Proof of Concept
1. Publish AA `M` ("malicious") whose messages/state formula unconditionally calls `bounce('always fail')` for any trigger.
2. Publish (or use an existing) AA `D` ("distributor") whose response, given some trigger, pays several outputs in one message, one of which is `M`'s address (directly, or because `M`'s address is supplied through `trigger.data`/state, as would be the case in permissionless auction/raffle/marketplace AAs).
3. Send a trigger to `D` that causes it to include `M` among the payment outputs, along with legitimate user address `U`.
4. Observe execution: `sendUnit()` creates the response unit, `handleSecondaryTriggers()` is invoked with `M` and `U`'s address, `M` is triggered as a secondary AA and calls `bounce()` (traced through `aa_composer.js:1720-1741` and `aa_composer.js:910-944`).
5. Because `M` bounced, `handleSecondaryTriggers`'s `async.eachSeries` callback receives an error and (since this is a primary trigger) calls `revert(...)` at `aa_composer.js:1749`, which rolls back the entire response, including the payment that should have reached `U` (`aa_composer.js:1759-1783`).
6. Repeat: every time `D` is triggered in a way that includes `M` as an output, the whole operation bounces, and `U` (and any other legitimate co-recipient) never receives funds — a persistent freeze caused solely by `M`'s uncooperative secondary-trigger behavior.
