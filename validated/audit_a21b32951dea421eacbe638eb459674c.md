### Title
Unvalidated Peer-Supplied `StakingInfo.BlockNum` Written to Staking DB Before Block Insertion Succeeds — (`datasync/downloader/downloader.go`)

### Summary

During fast-sync, a remote P2P peer can supply a `P2PStakingInfo` with an arbitrary `BlockNum` and fabricated `StakingAmounts`. The downloader writes this directly to the staking DB using `PutStakingInfoToDB` **before** `InsertReceiptChain` validates the block. There is no check that `result.StakingInfo.BlockNum` matches `result.Header.Number`, and there is no rollback if `InsertReceiptChain` subsequently fails. This allows a malicious peer to durably corrupt staking DB entries for arbitrary block numbers, affecting proposer selection and reward distribution after fast-sync completes.

### Finding Description

In `commitFastSyncData`, the loop at lines 1878–1884 iterates over all `fetchResult` items and unconditionally calls `PutStakingInfoToDB(result.StakingInfo.BlockNum, ...)` using the **peer-supplied** `BlockNum` as the DB key: [1](#0-0) 

The same pattern exists in `commitPivotBlock`: [2](#0-1) 

`PutStakingInfoToDB` calls `WriteStakingInfo` which immediately persists to the key-value store with no transactional semantics: [3](#0-2) 

Two independent defects combine here:

**Defect 1 — No `BlockNum` vs. header number validation.** The code uses `result.StakingInfo.BlockNum` (peer-controlled) as the DB key without ever checking it equals `result.Header.Number`. A malicious peer can set `BlockNum` to any value — a future block, a past block, or a block the victim node has already correctly stored — and the write proceeds unconditionally.

**Defect 2 — Write before validation, no rollback.** `PutStakingInfoToDB` is called inside the loop, before `InsertReceiptChain` is called at line 1886. If `InsertReceiptChain` fails (e.g., because the peer also supplied invalid receipts), the error path at line 1887–1888 returns without undoing the staking DB write. The corrupted entry persists. [4](#0-3) 

### Impact Explanation

The staking DB is the authoritative source for proposer selection and reward distribution after fast-sync completes. `GetStakingInfo` reads from this DB: [5](#0-4) 

An attacker who corrupts DB key `N` with fabricated `StakingAmounts` causes the node to use those amounts when computing the validator set and distributing block rewards for all blocks that reference staking info at block `N`. This is an unauthorized manipulation of reward distribution — a direct match for the allowed impact gate.

Even without causing `InsertReceiptChain` to fail, Defect 1 alone is sufficient: the attacker supplies valid receipts (matching the header's receipt root, so `InsertReceiptChain` succeeds) but sets `BlockNum` to a target slot (e.g., a future block or a past block whose staking info the attacker wants to overwrite). The write succeeds and the fabricated data persists.

### Likelihood Explanation

Any node performing fast-sync is exposed. Fast-sync peers are selected from the public P2P peer pool — no privileged access is required. The attacker only needs to:
1. Announce a sufficiently high TD to be selected as a sync peer.
2. Serve valid headers (which are hash-validated against the announced chain) and valid receipts.
3. Return a `P2PStakingInfo` with a crafted `BlockNum` and fabricated `StakingAmounts`.

No cryptographic break, key compromise, or validator-majority collusion is needed.

### Recommendation

1. **Validate `BlockNum` against the header number.** Before calling `PutStakingInfoToDB`, assert that `result.StakingInfo.BlockNum == result.Header.Number.Uint64()`. If they differ, drop the peer and skip the write.

2. **Write after successful insertion.** Move the `PutStakingInfoToDB` call to after `InsertReceiptChain` returns without error, so the DB is only updated when the block is durably accepted.

3. **Consider a second pass.** Restructure `commitFastSyncData` to collect staking writes in a pending list, then apply them only after `InsertReceiptChain` succeeds for the entire batch.

### Proof of Concept

1. Stand up a fast-sync peer that serves valid headers and valid receipts for blocks `[N, N+k]`.
2. For block `N`, return a `P2PStakingInfo` with `BlockNum = N+1000` and fabricated `StakingAmounts` (e.g., all stake assigned to attacker address).
3. Observe that `PutStakingInfoToDB` writes to DB key `N+1000`.
4. After fast-sync completes, call `GetStakingInfo(N+1000)` and verify it returns the fabricated amounts.
5. Confirm that proposer selection for blocks referencing staking info at `N+1000` uses the attacker-supplied data.

For the rollback variant: in step 2, also return receipts that do not match the header's receipt root. Observe that `InsertReceiptChain` fails, the error is returned, but the staking DB entry for `N+1000` remains written.
