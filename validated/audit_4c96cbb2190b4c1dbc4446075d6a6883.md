### Title
CCMenu API client is not scoped to a stack, so one leaked CCMenu token reads every stack the same user has fetched a URL for - (File: app/controllers/shipit/ccmenu_url_controller.rb)

### Summary
`CCMenuUrlController#client` looks up or creates the CCMenu `ApiClient` keyed only on `creator: current_user, name: 'CCMenu Client'`, never setting the `stack` association even though `ApiClient` has a `belongs_to :stack, optional: true`. Because `Api::CCMenuController` only checks the generic `read:stack` permission and never verifies which stack the token was minted for, the same token/URL works for every stack the user has ever requested a CCMenu URL for.

### Finding Description
Broken binding: `client(stack_A).id == client(stack_B).id` (and therefore `client(stack_A).authentication_token == client(stack_B).authentication_token`) for the same `current_user`, when it should hold that these are distinct, stack-scoped credentials.

Code path:
- `CCMenuUrlController#client` [1](#0-0)  does `ApiClient.create_with(permissions: %w[read:stack]).find_or_create_by!(creator: current_user, name: 'CCMenu Client')` — no `stack:` attribute is passed despite `ApiClient` supporting one.
- `ApiClient` model defines `belongs_to :stack, optional: true` [2](#0-1)  and `check_permissions!` only checks the permission string, not any stack ownership [3](#0-2) .
- The generated token just encodes the `ApiClient` id via a message verifier [4](#0-3) , with no stack binding.
- `Api::CCMenuController` authenticates the token and requires `read:stack` permission generically, then loads whatever stack is in `params[:stack_id]` and renders it — it never checks that the authenticated client is tied to that particular stack [5](#0-4) .

Root cause: the same singleton `ApiClient` row (identified by `creator + name`) is reused across all stacks for a given user, and the authorization check for the CCMenu endpoint is stack-agnostic (`read:stack` only, not `read:stack for stack X`). The existing test suite confirms the intended behavior of returning one token and reusing it, without covering multi-stack use [6](#0-5) .

### Impact Explanation
Any stack settings page a user visits generates/reuses this one `ApiClient`; the token embedded in that stack's CCMenu URL is valid to call `GET /api/stacks/:stack_id/ccmenu.xml?token=...` for **any** stack the same token authenticates against, since the controller checks only the `read:stack` permission bit, not stack identity. If a user leaks the CCMenu URL for a low-sensitivity stack (e.g. posted in a public CI badge or dashboard), an attacker gains read access (build/deploy status, commit info) to every other stack that user has fetched a CCMenu URL for — an unauthenticated read of stack state once a single token is obtained, matching the High severity category ("unauthenticated read of stack state ... task streams or deploy output"). Blast radius: cross-stack, bounded by how many stacks a given user has visited settings pages for.

### Likelihood Explanation
No special configuration is required; the flaw is inherent in how `client` and the API controller are written. The only precondition is that the token for one stack's CCMenu URL is disclosed (e.g. through the URL appearing in a public CI dashboard, being copy-pasted into a public issue, or via other information leakage vectors), which is the deployment's stated threat model in the question. Once obtained, exploitation is a trivial repeatable GET request against any other `stack_id` the token's owner has generated a URL for; cost to the attacker is essentially zero beyond obtaining the leaked token.

### Recommendation
Scope the CCMenu `ApiClient` per stack: include `stack: stack` in the `find_or_create_by!`/`create_with` call in `CCMenuUrlController#client`, and have `Api::CCMenuController` (or `require_permission`) additionally verify `current_api_client.stack_id == stack.id` before rendering, rejecting mismatched stacks.

### Proof of Concept
```ruby
# test/controllers/ccmenu_controller_test.rb
test "CCMenu tokens are shared across stacks for the same user" do
  stack_a = shipit_stacks(:shipit)
  stack_b = shipit_stacks(:cyclimse) # any second stack fixture

  get :fetch, params: { stack_id: stack_a.to_param }
  data_a = JSON.parse(response.body)
  token_a = Rack::Utils.parse_nested_query(URI(data_a['ccmenu_url']).query)['token']

  assert_no_difference 'ApiClient.count' do
    get :fetch, params: { stack_id: stack_b.to_param }
  end
  data_b = JSON.parse(response.body)
  token_b = Rack::Utils.parse_nested_query(URI(data_b['ccmenu_url']).query)['token']

  assert_equal token_a, token_b # same ApiClient/token reused across stacks

  # confirm the leaked token from stack_a also reads stack_b via the API endpoint
  get :show, params: { stack_id: stack_b.to_param, token: token_a }, controller: 'shipit/api/ccmenu'
  assert_response :ok
end
```
This demonstrates `ApiClient.count` only increases once and the identical token authorizes reads across distinct stacks belonging to the same user.

module Shipit
  module Api
    class CCMenuController < BaseController
      require_permission :read, :stack

      class NoDeploy
        def id
          0
        end

        def ended_at
          Time.now.utc
        end

        def running?
          false
        end
      end

      def show
        latest_deploy = stack.deploys_and_rollbacks.last || NoDeploy.new
        render('shipit/ccmenu/project', formats: [:xml], locals: { stack:, deploy: latest_deploy })
      end

      private

      def stack
        @stack ||= Stack.from_param!(params[:stack_id])
      end
