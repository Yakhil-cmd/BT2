### Title
Unvalidated `creator` account in `initialize_with_permission` permanently fixes the wrong creator-fee recipient - ([File: programs/cp-swap/src/instructions/initialize_with_permission.rs])

### Summary
`initialize_with_permission` records an attacker/caller-supplied, unauthenticated `creator` account as the pool's permanent `pool_creator`, while all liquidity, fee payments, and LP tokens actually flow from a different account, `payer`. That `pool_creator` field is later used as the sole, immutable destination for all accumulated creator swap fees, mirroring the Cooler.sol bug class where a hardcoded/recorded "owner" role diverges from the actual party that funded the operation.

### Finding Description
In `InitializeWithPermission`, `payer` is the `Signer` that funds `payer_token_0`/`payer_token_1`, pays the pool-creation fee, and receives the initial LP tokens, while `creator` is declared as a plain `UncheckedAccount` with no signature requirement and no constraint tying it to `payer`: [1](#0-0) 

At the end of the instruction, `pool_state.initialize(...)` stores `ctx.accounts.creator.key()` (not `payer.key()`) as the pool's `pool_creator`: [2](#0-1) 

This `pool_creator` value is fixed permanently in `PoolState` at creation time (there is no instruction to change it) and is later used as the exclusive recipient of accumulated swap creator fees in both `collect_creator_fee`, which requires `creator` to sign and match `pool_state.pool_creator`: [3](#0-2) 

and `collect_creator_fee_permissionless`, which sends the fee to `pool_state.pool_creator` regardless of who calls it: [4](#0-3) 

Because `creator` in `initialize_with_permission` is never verified to be the same entity as `payer` (unlike the plain `initialize` instruction, where `creator` itself is the `Signer` and sole funder, so `pool_creator` correctly equals the funder), the address that ultimately receives all future creator-fee revenue can be set to any arbitrary pubkey supplied in the transaction, independent of who actually funded/created the pool.

### Impact Explanation
Any account with a valid `Permission` PDA (the only gating check on `payer`) can create a pool and designate an arbitrary, unrelated `creator` pubkey as the permanent creator-fee recipient. If this account is set incorrectly (by front-end bug, operator error, or malicious tooling controlling the `payer`), all subsequently accumulated `creator_fees_token_0`/`creator_fees_token_1` for that pool are irrecoverably directed to the wrong address, since `pool_creator` cannot be updated after `initialize`. This is a permanent misdirection/loss of fee revenue that should belong to the legitimate pool creator/LP ecosystem, matching the "collateral sent to wrong recipient" bug class in the reference report.

### Likelihood Explanation
Exploitation only requires a single call to `initialize_with_permission` with attacker-chosen `creator` account data; no privileged signer beyond the already-required `Permission` PDA check on `payer` is needed, and Anchor performs no additional relationship check between `payer` and `creator`.

### Recommendation
Either require `creator` to sign (mirroring `initialize.rs`), or add an explicit account constraint tying `creator` to `payer`/the `Permission` record so the pool-creator fee recipient cannot be decoupled from the actual pool funder without an authenticated, intentional designation.

### Proof of Concept
1. Obtain/hold a valid `Permission` PDA for `payer`.
2. Call `initialize_with_permission` supplying `payer` (signer, funds liquidity/fees) and `creator` = an arbitrary pubkey unrelated to `payer` (no signature required).
3. `pool_state.pool_creator` is permanently set to that arbitrary pubkey: [2](#0-1) 
4. As swaps accrue creator fees, only the arbitrary `creator` address (or anyone triggering `collect_creator_fee_permissionless` on its behalf) can ever receive them, with no way to correct the recipient.
