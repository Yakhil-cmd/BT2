### Title
`StatusHandler#process` writes `Status` records to commits from any repository/stack, archived or not - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` resolves target commits via `Commit.where(sha: params.sha)` with no scoping to `stacks` (the stacks belonging to the payload's own repository) and no `not_archived` filter, unlike `PushHandler#process` which scopes to `stacks.not_archived.where(branch:)`. Any commit sha already known to Shipit - from an archived stack or from an entirely different repository - receives a new `Status` and fires `after_create`/`after_commit` side effects whenever a `status` webhook event references that sha, regardless of which repository the webhook payload claims to be for.

### Finding Description
The binding that should hold: `commit.stack.repository == payload.repository AND commit.stack.archived? == false`, i.e. `Status` mutation should be limited to non-archived stacks that the payload's repository actually owns.

Actual code: [1](#0-0) 
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
This queries `Commit` across the entire table by `sha` alone; there is no `stacks` scope, no `not_archived`, and no join/filter against `params.dig('repository', ...)`. Compare with `PushHandler`, which explicitly scopes to `stacks.not_archived.where(branch:)` before acting: [2](#0-1) .

`create_status_from_github!` unconditionally creates a `Status` row and triggers `enable_ci_on_stack`, `schedule_continuous_delivery`, and `broadcast_update`: [3](#0-2) [4](#0-3) . `Commit#schedule_continuous_delivery` re-evaluates `deployable?` and can enqueue `ContinuousDeliveryJob`: [5](#0-4) [6](#0-5) .

**Path to reach this code**: `WebhooksController#create` verifies the signature against the GitHub App configured for the payload's `repository.owner.login` via `Shipit.github(organization: repository_owner).verify_webhook_signature` before dispatching to handlers: [7](#0-6) . This check binds the *organization*, not the specific *repository*, to the secret. It does not bind `params.sha` to any particular repository at all - nothing in the controller or in `StatusHandler` cross-checks that the sha being reported actually belongs to a commit fetched from the same `repository.full_name` in the payload.

**Root cause**: `StatusHandler` treats `sha` as a globally unique key across the whole `commits` table, when in reality commit shas can legitimately be shared across repositories (forks sharing git history) or, once the fact is known/observed (shas are public information visible on GitHub), can be targeted directly. Any actor who can trigger a real, validly-signed `status` webhook for **any** repository under an organization already configured in Shipit (e.g., their own repository in that org, or a repository they have commit-status write access to) can supply an arbitrary `sha` value equal to a commit that exists in a completely different (and possibly archived) victim stack. `StatusHandler` will then create a `Status` for that victim commit, driven entirely by the attacker's own webhook payload, without ever verifying that `params.dig('repository', 'full_name')` matches `commit.stack.repository.full_name`, and without excluding archived stacks.

**Why existing guards don't help**: `verify_signature` only proves the request came from GitHub for the claimed *organization*; it says nothing about which *repository within that organization* the payload is about, and nothing about which repository *owns* the sha being referenced. The `ExplicitParameters` schema only validates types/presence of `sha`/`state`/etc., it does not tie `sha` back to `repository`. There is no `require_permission!`/stack-ownership check inside `StatusHandler` at all.

### Impact Explanation
A `Status` record - and its cascading `after_create`/`after_commit` callbacks (`enable_ci_on_stack`, `schedule_continuous_delivery`, `broadcast_update`) - can be written against a commit belonging to a stack/repository the attacker's webhook payload does not actually correspond to, including an **archived** victim stack. This matches the Critical category "a payload for one repository mutating another's stack, commit, task or task or team": the mutation (`Status` creation, CI-enablement, deployability re-evaluation) is performed on behalf of a repository/stack that never authenticated or authorized that specific commit-status event. This is repeatable for any sha the attacker can discover (shas are not secret) and can be replayed against any stack that has ever ingested that commit, archived or otherwise.

### Likelihood Explanation
Exploitation requires the attacker to get a *validly signed* `status` webhook delivered - this requires either (a) a genuine GitHub-side event under an organization already configured with a Shipit `webhook_secret` (e.g., the attacker has write/commit-status access to some repository in that same org), or (b) the organization has no `webhook_secret` configured, in which case `verify_webhook_signature` returns `true` unconditionally (a deployment-configuration gap, not part of `StatusHandler` itself). Given (a), the cost is low: any contributor with commit-status API access to one repo in the org can set a status on any sha they know, and if that sha also exists as a `Commit` row for a different, unrelated stack (via shared history from a fork or simply a previously-observed commit), the victim's `Status`/CI state is mutated. This is fully repeatable and requires no elevated Shipit privileges.

### Recommendation
Scope `StatusHandler#process` the same way `PushHandler` scopes its query: resolve the repository from `params.dig('repository', 'full_name')`, restrict to `stacks.not_archived` for that repository, and join through to the `commits` (or filter `Commit.where(sha: ...).merge(stacks.not_archived))`) so that only commits belonging to a non-archived stack of the payload's own repository can receive a `Status`. Concretely:
```ruby
def process
  stacks.not_archived.joins(:commits).merge(Commit.where(sha: params.sha)).find_each do |stack|
    stack.commits.find_by(sha: params.sha)&.create_status_from_github!(params)
  end
end
```
(or equivalent) so the repository-of-record and archived state are both enforced, matching the behavior already present in `PushHandler`.

### Proof of Concept
minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb` style, no live GitHub):
1. Create `repository_a` (victim) and `stack_a` under it; archive `stack_a` (`stack_a.update!(archived: true)`).
2. Create a `Commit` under `stack_a` with `sha: "deadbeef..."`.
3. Build a `status` webhook payload with `repository.full_name` set to an unrelated `repository_b` (attacker's), and `sha: "deadbeef..."`, `state: "success"`.
4. Call `Shipit::Webhooks::Handlers::StatusHandler.new(...).call(payload)` (or invoke the same way the controller does after `verify_signature` passes).
5. Assert:
   - `Status.where(commit: commit_a).count` is now `1` (mutation occurred) — even though `stack_a.archived?` is `true` and `payload['repository']['full_name'] != stack_a.repository.full_name`.
   - `commit_a.reload.deployable?` and `ContinuousDeliveryJob` enqueue (`schedule_continuous_delivery`) both fire, evidencing side effects on an archived, unrelated stack.
6. Contrast with `PushHandler`, where an equivalent test against an archived stack asserts **no** `sync_github` call occurs, demonstrating the binding is enforced there but absent in `StatusHandler`.

      head(422) unless verified

    rescue Shipit::GithubOrganizationUnknown => e

        "unknown_organization=#{e.message}",
