### Title
`Api::CCMenuController` lets a stack-scoped `ApiClient` token read the CCMenu status of any stack, not just the stack it was authorized for - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`ApiClient` records can be scoped to a single `Stack` via the optional `stack` association, and `Api::BaseController` enforces that scope by resolving the current stack through the `stacks` relation (`stacks.from_param!`), which is restricted to `current_api_client.stack_id` when the client is stack-scoped. `Api::CCMenuController` overrides the `stack` resolver to call `Stack.from_param!(params[:stack_id])` directly on the unscoped `Stack` model, bypassing that authorization binding entirely.

### Finding Description
`ApiClient` belongs to an optional `stack`, and its only authorization primitive is a flat permission list checked via `check_permissions!(operation, scope)`, which does not know about *which* stack is being accessed: [1](#0-0) [2](#0-1) 

The stack-level restriction is enforced separately, in `Api::BaseController`, by scoping the visible `Stack` set to the client's own `stack_id` when present, and then resolving the requested stack from within that scoped set: [3](#0-2) 

This is the binding that every other API controller relies on (`stacks_controller.rb`, `tasks_controller.rb`, `deploys_controller.rb`, `locks_controller.rb`, `hooks_controller.rb`, etc. all resolve `stack` through this scoped helper). `Api::CCMenuController`, however, redefines `stack` to bypass the scoped relation and query `Stack.from_param!` directly against the unrestricted `Stack` model: [4](#0-3) 

The controller still declares `require_permission :read, :stack`, but that check only verifies the client has the generic `read:stack` permission string in its `permissions` array — it never verifies the `stack_id` the client is scoped to matches the `params[:stack_id]` being requested: [5](#0-4) 

The route accepts an arbitrary `stack_id` segment for any stack in the installation: [6](#0-5) 

**Binding broken (equality that should hold but doesn't):**
`stack authorized for token (ApiClient#stack_id, enforced via BaseController#stacks)` == `stack actually touched (Stack.from_param!(params[:stack_id]) in CCMenuController#stack)`

Before the fix, in every other API resource controller, this equality holds because `stack` is always resolved through `stacks.from_param!`. In `CCMenuController`, the equality is broken: a client scoped to stack A (e.g. fixture `here_come_the_walrus`, scoped to `shipit`) can supply stack B's `stack_id` in the URL and the controller will happily resolve and render stack B's data, since `Stack.from_param!` is not filtered by the client's `stack_id`.

### Impact Explanation
This is an authenticated escalation of authorization scope: a token that was deliberately restricted to a single stack (a common configuration, e.g. for the CCMenu integration itself, or any token created with `stack:` set) can read the CI/build state (`lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, `activity`, `webUrl`, lock status) of *every other stack* in the Shipit installation by only changing the `stack_id` path segment. This matches "unauthenticated/uncontrolled read of stack state" beyond the token's intended authorization boundary — an escalation of the stack-scoping guarantee that the rest of the API enforces.

### Likelihood Explanation
High. Exploitation only requires possession of any valid `ApiClient` token that is scoped to a single stack (`stack_id` set) with `read:stack` permission — a normal, supported configuration (e.g. tokens minted by `CCMenuUrlController#client`, or any admin-created client restricted to one stack for least-privilege purposes). No additional privileges, GitHub access, or session are needed; the attacker simply changes the `stack_id` in the request path.

### Recommendation
Remove the `stack` override in `Api::CCMenuController` (and any other place doing the same) and resolve the stack through the scoped `stacks` relation from `Api::BaseController`, consistent with every other API controller, e.g.:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
so that a stack-scoped `ApiClient` cannot resolve a `Stack` outside its authorized `stack_id`.

### Proof of Concept
1. Create/obtain an `ApiClient` scoped to `stack_id: <stack A>.id` with permission `read:stack` (as in the fixture `here_come_the_walrus`, scoped to the `shipit` stack): [7](#0-6) 
2. Authenticate as this client (basic auth or `?token=`) and request `GET /api/stacks/<stack B owner>/<stack B repo>/<stack B env>/ccmenu`, where stack B is a different stack the client was never scoped to.
3. Because `Api::CCMenuController#stack` calls `Stack.from_param!(params[:stack_id])` directly instead of `stacks.from_param!`, the request succeeds and returns stack B's CCMenu XML (build status/label/time), even though the client's `ApiClient#stack_id` restricts it to stack A only — confirmed by comparing `Api::CCMenuController#stack` [8](#0-7)  against the scoped resolver used everywhere else [3](#0-2) .
