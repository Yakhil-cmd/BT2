### Title
Liquidator-controlled Pyth price updates in `liquidate` enable atomic price manipulation to over-seize borrower collateral - (File: `mainnet/contracts/market/v0-4-market.clar`)

### Summary
`liquidate` accepts an optional `price-feeds` parameter and calls `write-feeds` before any valuation happens. This lets the liquidator (attacker) atomically push a fresh, self-selected Pyth update into the shared oracle-price cache (`last-update` map / `price-resolve`) in the very same transaction used to compute the borrower's (victim's) collateral/debt valuation and the seized-collateral amount, exactly the class of "insecure liquidity valuation with oracle updates" described in the report, but here it affects a third party (the borrower being liquidated) rather than only the caller.

### Finding Description
`liquidate` is defined at [1](#0-0)  and begins by executing `(feeds-check (try! (write-feeds price-feeds)))` before resolving the borrower's collateral/debt notional values. `write-feeds`/`write-feed` forwards the caller-supplied `feed` bytes straight into `pyth-oracle-v4.verify-and-update-price-feeds`, which writes the decoded price into the shared oracle price store consumed by `price-resolve` for every asset valuation in the same call, as shown at [2](#0-1)  and the resolution/staleness logic at [3](#0-2) .

Because Pyth allows any valid, not-yet-consumed signed update within the staleness window to be submitted on-chain by anyone, the liquidator chooses which of several valid recent price updates to submit atomically with the liquidation call. The oracle only enforces that the timestamp is fresh and monotonic (`oracle-timestamp-fresh`), not that it reflects a time-weighted or bounded price - so the liquidator can select whichever available signed update maximizes `total-debt-usd`/`current-ltv` and the resulting `coll-expected`/`coll-final` seized from the borrower, computed at [4](#0-3) . The victim borrower has no ability to intervene since the whole valuation and seizure happens in the liquidator's transaction.

The existing protection at [5](#0-4)  ("Oracle frontrunning protection: prevent same-block liquidation") only blocks a borrower who just borrowed in the same block from being liquidated in that block - it does nothing to stop the liquidator from injecting a favorable price update in the same transaction as the liquidation call itself.

Victim outcome comparison:
- Without the attacker's crafted-timing transaction: liquidation would occur (or not) using whatever price is already cached/fresh from ordinary keeper updates, and the seized collateral/penalty would reflect the price at that natural update cadence.
- With the attacker's transaction: the liquidator submits the specific valid signed Pyth update (among those available within the staleness window) that maximizes `current-ltv`, `liq-penalty`, and `coll-expected`, seizing more of the borrower's collateral than would occur under a fair/typical valuation, and potentially triggering liquidation on a position that would be healthy under a less favorable-to-attacker but equally valid price snapshot.

### Impact Explanation
This is a direct theft of victim (borrower) funds at rest: the liquidator can extract collateral beyond what an unbiased valuation would allow at the moment of liquidation by cherry-picking which valid oracle update to push atomically. This falls under the Critical impact class ("direct theft of user funds ... other than unclaimed yield").

### Likelihood Explanation
Likelihood is meaningful but not trivial: it requires (a) a position near the liquidation threshold, and (b) the existence of an alternative valid, unconsumed, signed Pyth price update within the staleness window that is more favorable to the liquidator than the currently cached price - achievable during periods of price volatility where Pyth publishes several updates within the `max-staleness` window. This is entirely feasible for a sophisticated MEV/liquidation bot monitoring Pyth's price update stream.

### Recommendation
Do not let the liquidator (or any single-transaction caller) choose the exact price snapshot used to value a victim's position for seizure purposes within the same transaction as the seizure. Concretely:
- Decouple price feed submission from the valuation used for liquidation: require the price update to be confirmed in a prior block/transaction before it can be used to liquidate a position (as already effectively done for the borrow side via `last-borrow-block`), or
- Implement the epoch-based min/max price bound recommended in the original report: track the last two epochs' price bounds per asset and, for liquidation, use the price that is least favorable to the liquidator among the recent epochs (i.e., bound the debt price by the highest recent value and the collateral price by the lowest recent value, or vice versa depending on direction) so that a same-transaction price injection cannot be used to extract more value than a fair valuation would allow.

### Proof of Concept
1. Attacker monitors Pyth for two valid, signed price updates for the borrower's collateral asset within the `max-staleness` window - one showing a lower collateral price (P_low) and one a higher price (P_high), both currently unconsumed on-chain.
2. Borrower's position has `current-ltv` just below `ltv-liq-partial` under P_low (healthy) but above it under P_high applied inversely to the debt asset (or a similar combination that raises `current-ltv`/`liq-penalty`).
3. Attacker submits `liquidate(borrower, collateral-ft, debt-ft, debt-amount, min-collateral-expected, receiver, (some (list feed-debt-high feed-coll-low)))`.
4. Inside the single transaction, `write-feeds` at [6](#0-5)  pushes both updates into the oracle cache; `price-resolve` immediately reads them back for `get-notional-evaluation`, `process-debt-asset`, and `process-collateral-asset`, computing `current-ltv`, `liq-penalty`, and `coll-final` from the attacker-chosen combination.
5. Liquidation executes at the attacker-favorable valuation, seizing more of the borrower's collateral (or triggering a liquidation that would not occur under alternative valid price data) than a valuation immune to same-transaction price selection would allow. [1](#0-0) [7](#0-6)

(define-private (price-resolve
  (data { type: (buff 1), ident: (buff 32), callcode: (optional (buff 1)), max-staleness: uint }))
  (let ((type (get type data))
        (ident (get ident data))
        (key { type: type, ident: ident })
        (resolution (try! (resolve-price-feed type ident)))
        (price (get value resolution))
        (callcode (get callcode data))
        (final-price (try! (resolve-callcode price callcode)))
        (last-update-time (oracle-last-update key))
        (timestamp (get timestamp resolution))
        (max-staleness (get max-staleness data)))

    ;; validate price and timestamp using max-staleness from oracle data
    (asserts! (and (oracle-price-legal final-price) (oracle-timestamp-fresh timestamp last-update-time max-staleness))
              ERR-ORACLE-INVARIANT)

    ;; update timestamp if newer
    (if (> timestamp last-update-time)
        (map-set last-update key timestamp)
        false)

    (ok final-price)))
