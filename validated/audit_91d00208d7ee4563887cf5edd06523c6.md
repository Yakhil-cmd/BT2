**Analysis:** The premise — that mempool prevalidation and VM execution use *different* `VerifierConfig` instances, with one lacking `max_push_size` enforcement — does not hold in this codebase.

The `VerifierConfig` used in production is built by a single function, `aptos_prod_verifier_config`, which always sets `max_push_size: Some(10000)` [1](#0-0) . This config is derived deterministically from on-chain `Features`/`TimedFeatures`/gas feature version — not from any caller-supplied or path-specific source.

Mempool's vm-validator does not construct its own bespoke verifier config; it delegates transaction validation to `AptosVM::validate_transaction` (the `VMValidator` trait impl), which is the exact same `AptosVM`/environment logic used at actual execution time, reading the same on-chain state view [2](#0-1) . Both paths resolve `Features`/config from the same state, so they converge on the same `VerifierConfig`, including the same `max_push_size` bound.

The `Default::default()` for `VerifierConfig` (which does leave `max_push_size: None`) is explicitly a test/library default [3](#0-2)  — it is not used in the production admission path described in the exploit question. The `VerifierConfig::production()` helper (also `Some(10000)`) exists for approximating prod config in tests/tools, not as a divergent live-execution config [4](#0-3) .

Since both mempool prevalidation and VM execution derive the `VerifierConfig` from the same on-chain feature-driven function against the same state, there is no code path in which one component enforces `max_push_size` and the other silently skips it for the same module/transaction. The scenario described requires an artificial mismatch that isn't present in the actual admission stack, so it does not meet the bar of an unprivileged-input exploit causing divergent accept/reject outcomes.
