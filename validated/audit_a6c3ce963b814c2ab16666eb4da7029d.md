### Title
Unauthenticated disclosure of stack merge-queue status via `MergeStatusController#check` - ([File: app/controllers/shipit/merge_status_controller.rb])

### Summary
`MergeStatusController` skips the `force_github_authentication` before_action for both `#check` and `#show`, but only `#show` re-adds an explicit `current_user.logged_in?` gate before rendering stack data. `#check` has no such gate, so any anonymous caller who supplies a valid `referrer` (a public `https://github.com/<owner>/<repo>/pull/<number>` URL) or a `stack_id` gets the real `stack.merge_status` back.

### Finding Description
The broken binding, stated as an equality that should hold but does not: for `#check`, `authorization_required(check) == true` is claimed by the security model (all Shipit controllers require `force_github_authentication` && `current_user.authorized?`), but the actual code computes `authorization_required(check) == false`.

Code path:
- `skip_authentication only: %i[check show]` calls `skip_before_action(:force_github_authentication, only: %i[check show])`, at [1](#0-0) , removing the only authentication/authorization gate (`force_github_authentication`, `app/controllers/concerns/shipit/authentication.rb` lines 8, 20-34) for both actions.
- `#show` compensates by explicitly checking `current_user.logged_in?` and rendering `'logged_out'` if the caller has no session: [2](#0-1) .
- `#check` has no equivalent check at all: [3](#0-2) . It goes straight to `stack_status`, which calls `stack.merge_status(backlog_leniency_factor: 1.0)` at [4](#0-3)  and serializes it in `render(json: { stack_status: })`.
- The `stack` lookup resolves purely from request params — either `params[:stack_id]` via `Stack.from_param!`, or by parsing `params[:referrer]` with `ReferrerParser` (a public PR URL regex) to find owner/name/branch and pick a matching `Stack`: [5](#0-4) . Neither path requires any session, token, or team membership.

Attacker request: `GET /merge_status/check?referrer=https://github.com/<owner>/<repo>/pull/<n>&format=json` with no session cookie, no `Authorization` header, from any browser/anonymous HTTP client. The response is `render(json: { stack_status: stack.merge_status(...) })`, exposing merge-queue health/state for that stack.

Existing guards fail because: `force_github_authentication` is explicitly skipped for `check`; there is no equivalent inline `current_user.logged_in?`/`authorized?` check inside `#check` as there is in `#show`; `ExplicitParameters`, `verify_signature`, and model validators are irrelevant to this controller action, and `Stack.from_param!`/`ReferrerParser` perform no authorization, only lookup.

### Impact Explanation
Any unauthenticated requester can read `stack.merge_status` for any stack whose owner/repo/branch (or `stack_id`) they can guess or observe (e.g., from a public PR URL), with no session, API token, or team membership. This is a repeatable, unauthenticated disclosure of merge-queue/stack state, matching the "High - unauthenticated read of stack state" impact category. It does not expose secrets or allow writes, so it does not rise to Critical, but it is a real authorization gap distinct from `#show`'s intended behavior, and is trivially repeatable against arbitrary reachable stacks.

### Likelihood Explanation
No preconditions beyond network reachability to the Shipit host and knowledge of a `referrer` PR URL or `stack_id` (both are effectively public/guessable, since GitHub PR URLs are public). Attacker cost is a single unauthenticated HTTP GET; fully repeatable across stacks/repos by varying `referrer`/`stack_id`. No secrets, GitHub App credentials, or webhook signing keys are needed.

### Recommendation
Add the same `current_user.logged_in?` (and ideally `current_user.authorized?`) gate inside `#check` that `#show` already has, or remove `check` from `skip_authentication` and instead special-case the JSON/health-check use case with an explicit, intentional public-access decision reviewed for information exposure (e.g., only return a boolean “ok/not ok” rather than full `stack_status` payload to unauthenticated callers).

### Proof of Concept
In a minitest under `test/controllers/shipit/merge_status_controller_test.rb`, add:
```ruby
test "#check does not require authentication and leaks stack_status" do
  session.delete(:user_id) # ensure fully anonymous, current_user.logged_in? == false
  stack = shipit_stacks(:shipit)
  get :check, params: { stack_id: stack.to_param }, format: :json
  assert_response :success
  json = JSON.parse(response.body)
  assert json.key?("stack_status") # real stack_status leaked with no session
end
```
Assert both sides of the binding explicitly:
- Expected (per security model): `current_user.logged_in? == true` required before `stack_status` is returned for `#check`, same as `#show`.
- Actual: `current_user.logged_in? == false` and `response.body` still contains `stack_status` data — the equality fails, confirming the vulnerability.
