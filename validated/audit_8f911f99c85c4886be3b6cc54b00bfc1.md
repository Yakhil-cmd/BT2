### Title
Stack-scoped ApiClient token authorizes cross-stack CCMenu reads - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::Api::BaseController` implements per-`ApiClient` stack scoping through the `stacks`/`stack` helper methods, but `Shipit::Api::CCMenuController` overrides `stack` with an unscoped lookup, breaking the binding between the stack a token is authorized for and the stack whose data it can read.

### Finding Description
`ApiClient` records can be scoped to a single stack via `belongs_to :stack, optional: true` and `stack_id?`. [1](#0-0) 
In `BaseController`, this scoping is enforced generically: `stacks` restricts the queryable set to the client's own stack when `stack_id?` is true, and `stack` resolves `params[:stack_id]` only within that restricted relation. [2](#0-1) 
Permission checks (`require_permission`, `check_permissions!`) only validate an operation/scope string like `read:stack` against the client's `permissions` array — they never validate which specific stack is being accessed. [3](#0-2) [4](#0-3) 
So the only place that actually enforces "this token may only touch its own stack" is the `stacks`/`stack` scoping in `BaseController`.

`CCMenuController` inherits from `BaseController` and declares `require_permission :read, :stack`, but it overrides `stack` to bypass the scoped relation entirely, doing a global unscoped lookup instead: [5](#0-4) 
It also overrides `authenticate_api_client` to accept the token via `params[:token]` (falling back to the same Basic-Auth mechanism), which is functionally equivalent authentication, but does not restore the missing scoping. [6](#0-5) 

Binding broken (equality that should hold but doesn't):
`stack authorized by current_api_client.stack_id` == `stack actually rendered by CCMenuController#show`

Before: for a stack-restricted `ApiClient` (`stack_id` set to stack A), calling any endpoint under `BaseController#stack` for `stack_id=B` (a different stack) returns 404/empty because `stacks` excludes B.
After: calling `Api::CCMenuController#show` with the same token and `stack_id=B` succeeds, because `stack` in this controller resolves via `Stack.from_param!` against the entire `Stack` table, ignoring `current_api_client.stack_id`.

### Impact Explanation
This lets a low-privilege API token — deliberately scoped by an operator to a single stack (e.g., a public CI-status widget token for one project) — read the deploy/build status (`lastBuildStatus`, `lastBuildLabel`, `webUrl`, lock status, etc.) of any other stack in the Shipit instance, including private/internal stacks it was never meant to see. This is an unauthenticated-relative-to-intent read of stack state, matching the "High" impact bucket of unauthorized read of stack state via a scoping bypass, since the attacker only needs a token legitimately scoped to one stack (no elevated permission) to enumerate/read all others.

### Likelihood Explanation
Any holder of a stack-scoped `ApiClient` token with `read:stack` permission (a routine, low-privilege credential intentionally restricted to one project) can trivially trigger this by supplying a different `stack_id` in the request — no additional exploitation complexity, no timing/race requirement, and it is directly reachable through a documented, unauthenticated (per the app's own model) CCMenu endpoint.

### Recommendation
Remove the `stack` override in `CCMenuController`, or reimplement it using the inherited `stacks` scope (`stacks.from_param!(params[:stack_id])`) so that stack-scoped `ApiClient` tokens cannot resolve stacks outside their authorized `stack_id`.

### Proof of Concept
1. Operator creates an `ApiClient` with `stack_id` set to Stack A and permission `read:stack` (a "CI badge" token for project A only).
2. Attacker (holder of that token) issues:
   `GET /api/stacks/<STACK_B_ID>/ccmenu.xml?token=<the_token>` where `STACK_B_ID` is a stack the token was never granted access to.
3. `CCMenuController#authenticate_api_client` authenticates the client via the token. [6](#0-5) 
4. `require_permission :read, :stack` passes because the token has `read:stack` in its `permissions` list, regardless of which stack. [3](#0-2) 
5. `stack` resolves `Stack.from_param!(params[:stack_id])` unscoped, returning Stack B, and `show` renders Stack B's deploy status/XML — data the token's `stack_id` restriction was meant to prevent. [7](#0-6)
