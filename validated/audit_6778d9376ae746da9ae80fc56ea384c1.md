### Title
Cross-org signature bypass via `repository.owner.login`/`repository.full_name` split lets an attacker's `check_suite` webhook mutate a victim stack's commit check-run state - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/handler.rb`)

### Summary
`Shipit::WebhooksController#verify_signature` selects the GitHub App/org used to validate the webhook HMAC using `repository.owner.login`, while `Handler#stacks` (used by `CheckSuiteHandler`) resolves the target stack using the unrelated `repository.full_name` field. An attacker who owns/controls an org with no `webhook_secret` configured in `Shipit.github_app_configs` can set `repository.owner.login` to that org (making `verify_webhook_signature` return `true` unconditionally) while setting `repository.full_name` to point at a victim repository/stack in a completely different org, causing the `check_suite` payload to mutate the victim's commit/check-run state.

### Finding Description
The broken binding is the implicit invariant: `repository_owner` (used to select the authenticating org) SHOULD equal the org embedded in `repository.full_name` (used to select the mutated stack). In code:

- `WebhooksController#repository_owner` reads `params.dig('repository', 'owner', 'login')` and is used to fetch a `GitHubApp` instance via `Shipit.github(organization: repository_owner)`, whose `verify_webhook_signature` is then run against the raw body: [1](#0-0) [2](#0-1) 
- `GitHubApp#verify_webhook_signature` returns `true` unconditionally when `webhook_secret` is blank for that org's config: [3](#0-2) 
- After verification passes, `Handler#stacks` and `#repository_name` resolve the target `Repository`/`Stack` using an entirely different field, `payload.dig('repository', 'full_name')`, never checking it against `repository_owner`: [4](#0-3) 
- `CheckSuiteHandler#process` then uses that mismatched `stacks` scope to select stacks by `params.check_suite.head_branch` and schedule check-run refresh for commits matching `params.check_suite.head_sha`: [5](#0-4) 

Exploit flow: attacker registers/controls a GitHub org (e.g. `attacker-org`) that is either unknown to Shipit's config (triggering `GithubOrganizationUnknown`, which is rejected) — so instead they pick a *configured* org that has no `webhook_secret` set (or that they can otherwise satisfy). They POST to `/webhooks` with `X-Github-Event: check_suite`, body `{"repository": {"owner": {"login": "attacker-org"}, "full_name": "victim-org/victim-repo"}, "check_suite": {"head_sha": "<victim commit sha>", "head_branch": "<victim branch>"}}`. `verify_signature` resolves `Shipit.github(organization: "attacker-org")`, which has no secret, so `verify_webhook_signature` returns `true` regardless of the actual `X-Hub-Signature` header. The request proceeds to `CheckSuiteHandler`, which looks up `Repository.from_github_repo_name("victim-org/victim-repo")` and mutates its stacks/commits — a payload that was never authenticated by `victim-org`'s secret.

None of the existing guards catch this: `drop_unhandled_event` only checks the event type exists a handler; `ExplicitParameters` schema for `CheckSuiteHandler` only requires `head_sha`/`head_branch` and never validates `repository.owner.login == repository.full_name`'s owner; there is no `require_permission!`/session check on this unauthenticated webhook endpoint; and `verify_signature` explicitly decouples authentication (via `owner.login`) from authorization/target-resolution (via `full_name`).

### Impact Explanation
This lets an unprivileged attacker who controls (or can satisfy the secret-less config of) an unrelated GitHub org cause writes against a victim repository's `Stack`/`Commit`/`CheckRun` records that were never authenticated by the victim's own webhook secret — this is a cross-tenant/cross-repository state manipulation, matching the "Critical: payload for one repository mutating another's stack/commit/task" category. Concretely, `schedule_refresh_check_runs!` on victim commits re-evaluates check-run/status state; combined with a stack that has `blocking_statuses` configured, forcing/altering check-run status transitions can flip `Commit#blocked?`, which gates deploy eligibility for the victim stack. The attack is repeatable against any repository whose `full_name` the attacker can guess/know (repo full names are public), and is not scoped to any repo the attacker owns.

### Likelihood Explanation
Preconditions: the attacker needs an org entry in Shipit's GitHub App/webhook configuration that has no `webhook_secret` set (or one whose secret they can otherwise compute/guess), so that `owner.login` resolves to a `GitHubApp` instance where `verify_webhook_signature` short-circuits to `true`. This requires no session, no API token, no team membership, and no repository write access to the victim repo — only knowledge of the victim's `owner-org/repo-name` full_name and a target branch/commit SHA (both public information via GitHub). The attack is a single unauthenticated HTTP POST to `/webhooks`, fully repeatable, and works against any victim stack with `blocking_statuses` configured.

### Recommendation
Bind the org used for signature verification to the org that is actually authorized to mutate the resolved resource: after loading the target `Repository`/`Stack` via `repository.full_name`, verify that `repository.owner.login` matches the owner portion of that same `full_name` (reject if they differ) before running the handler; alternatively, derive `repository_owner` from `full_name`'s owner segment directly rather than trusting the separate `owner.login` field, and require a configured, non-blank `webhook_secret` for every org (fail closed rather than treating an absent secret as automatically verified).

### Proof of Concept
minitest under `test/controllers/shipit/webhooks_controller_test.rb` (existing suite) — new test:
1. Configure `Shipit.github_app_configs` (or stub `Shipit.github`) with two orgs: `attacker-org` (no `webhook_secret`) and `victim-org` (with a `webhook_secret` the attacker does not know).
2. Create a `victim-org/victim-repo` `Repository`, a `Stack` with `branch: "main"` and `blocking_statuses` configured, and a `Commit` with `sha: "abc123"` on that stack.
3. POST to `/webhooks` with header `X-Github-Event: check_suite` and body:
   `{"repository": {"owner": {"login": "attacker-org"}, "full_name": "victim-org/victim-repo"}, "check_suite": {"head_sha": "abc123", "head_branch": "main"}}`, omitting/forging `X-Hub-Signature` arbitrarily.
4. Assert the response is `200 OK` (not `422`), and assert that `commit.reload` had `schedule_refresh_check_runs!` invoked (e.g. stub/mock expectation, or assert a corresponding job/check-run refresh was enqueued) — proving the victim's commit was mutated by a request authenticated only against `attacker-org`'s (secret-less) config.
5. Equality check before/after: assert `params.dig('repository','owner','login') != params.dig('repository','full_name').split('/').first` (i.e., `"attacker-org" != "victim-org"`) while the handler still executed against `victim-org/victim-repo`'s stack — demonstrating the divergence was never checked.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
