### Title
Bridge Operator Gas Griefing via Malicious Recipient in `handleKLAYTransfer` — (`contracts/service_chain/bridge/BridgeTransferKLAY.sol`)

---

### Summary

`handleKLAYTransfer` in the Kaia service-chain bridge pushes KLAY to an arbitrary recipient address via a low-level call after all nonce-accounting state has been written. If the recipient is a malicious contract that reverts (or exhausts gas), the entire transaction reverts, the nonce is **not** consumed, and the `valueTransferRecovery` (VTR) daemon re-queues the event indefinitely. The bridge operator pays gas for every failed attempt with no on-chain mechanism to skip or cancel the stuck transfer.

---

### Finding Description

`handleKLAYTransfer` in `BridgeTransferKLAY.sol` follows this sequence:

1. Validates the nonce (`_lowerHandleNonceCheck`, `_voteValueTransfer`)
2. Writes all accounting state: `_setHandledRequestTxHash`, `handleNoncesToBlockNums[_requestedNonce]`, `_updateHandleNonce`
3. Emits `HandleValueTransfer`
4. Executes the external push: `(bool ok, ) = _to.call.value(_value)("")`
5. Requires success: `require(ok, "handleKLAYTransfer: transfer failed")` [1](#0-0) 

If `_to` is a contract whose fallback reverts or exhausts gas, step 5 causes the entire transaction to revert. Because Solidity reverts all state changes atomically, the nonce written in step 2 is **also** reverted. `HandleNoncesToBlockNums[nonce]` remains zero, so `isHandledEvent` returns `false`. [2](#0-1) 

The VTR daemon polls `HandleNoncesToBlockNums` to detect pending events and re-submits them: [3](#0-2) 

Because the nonce is never consumed, `retrievePendingEventsFrom` keeps returning the same event, and `recoverPendingEvents` keeps re-adding it to the operator's pending queue: [4](#0-3) 

The operator's Go-layer handler submits a new on-chain transaction for every VTR cycle: [5](#0-4) 

There is no on-chain or off-chain mechanism to mark a specific nonce as permanently failed and skip it. The only recourse is to stop the entire VTR, which halts recovery for **all** pending transfers.

---

### Impact Explanation

**Bridged-asset lock:** The user's KLAY is locked in the source-chain bridge contract permanently. `requestKLAYTransfer` transfers KLAY into the bridge and increments `requestNonce`; there is no user-facing refund path if the destination handle never succeeds. [6](#0-5) 

**Operator KAIA drain:** Every VTR retry costs the bridge operator a full transaction's worth of KAIA gas. A determined attacker can register multiple source-chain transfers pointing to the same malicious contract, multiplying the per-cycle cost. The operator's only escape is to shut down the VTR entirely, which also blocks all legitimate pending transfers.

**No selective skip:** `_updateHandleNonce` advances `lowerHandleNonce` only when consecutive nonces are present in `handleNoncesToBlockNums`. A stuck nonce prevents the window from advancing, potentially blocking the `lowerHandleNonce` check for subsequent nonces as well. [7](#0-6) 

---

### Likelihood Explanation

Any user with a small amount of KLAY on the source chain can trigger this:

1. Deploy a contract on the destination chain whose fallback always reverts (zero cost beyond deployment).
2. Call `requestKLAYTransfer` on the source bridge specifying that contract as `_to`.
3. The bridge operator's VTR will retry the handle transaction every `VTRecoveryInterval` seconds indefinitely.

No privileged access is required. The attacker's only cost is the KLAY locked in the source bridge (which they sacrifice) and the deployment gas for the malicious contract.

---

### Recommendation

Replace the push pattern with a **pull** (claim) pattern for KLAY delivery:

```solidity
mapping(address => uint256) public pendingWithdrawals;

function handleKLAYTransfer(...) public onlyOperators nonReentrant {
    // ... nonce checks and state updates ...
    pendingWithdrawals[_to] += _value;
    emit HandleValueTransfer(...);
}

function withdraw() external nonReentrant {
    uint256 amount = pendingWithdrawals[msg.sender];
    require(amount > 0, "nothing to withdraw");
    pendingWithdrawals[msg.sender] = 0;
    (bool ok, ) = msg.sender.call.value(amount)("");
    require(ok, "withdraw failed");
}
```

This ensures the nonce is always consumed regardless of whether the recipient can accept KLAY, eliminating both the gas-griefing loop and the permanent asset lock.

Alternatively, add an owner-callable `skipHandleNonce(uint64 nonce)` that manually marks a nonce as handled and credits the KLAY to a recovery address, giving the operator a selective escape without shutting down the entire VTR.

---

### Proof of Concept

**Attacker contract (destination chain):**
```solidity
pragma solidity 0.5.6;
contract MaliciousReceiver {
    // Fallback reverts unconditionally
    function() external payable {
        revert("grief");
    }
}
```

**Attack steps:**
1. Deploy `MaliciousReceiver` on the destination chain.
2. On the source chain, call `bridge.requestKLAYTransfer{value: 1 ether}(maliciousReceiverAddr, 1 ether, "")`.
3. The source bridge emits `RequestValueTransfer` with `requestNonce = N`.
4. The bridge operator's VTR detects nonce `N` as pending and calls `handleKLAYTransfer(..., maliciousReceiverAddr, 1 ether, N, ...)`.
5. `MaliciousReceiver.fallback()` reverts → `require(ok, ...)` reverts the transaction.
6. `HandleNoncesToBlockNums[N]` remains `0`; `isHandledEvent` returns `false`.
7. Next VTR cycle re-queues nonce `N`; step 4–6 repeat indefinitely.
8. The operator loses gas on every cycle; the 1 KAIA is permanently locked in the source bridge.

	vtRecoveredRequestEventMeter.Mark(int64(len(vtr.childEvents)))

		events[i] = event

	return nil
}
