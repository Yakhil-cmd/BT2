### Title
Cross-mutex race lets a dry-run AA response corrupt / dangle the live unit-cache used by real AA trigger execution - ([File: aa_composer.js])

### Summary
Chrome's CVE-2025-3066 is a use-after-free caused by an object being freed on one execution path while another concurrently running path (Site Isolation) still holds and dereferences a stale pointer to it. The closest reachable analog in ocore is a **shared-cache race between two independently-mutexed code paths that both create, cache, and then "free" (forget) in-memory unit objects**: the speculative dry-run trigger executed synchronously during ordinary joint validation (`network.js`, guarded only by the `'handleJoint'` mutex) and the real, stabilized AA-trigger executor (`aa_composer.js:handleAATriggers`, guarded by a separate `'aa_triggers'` mutex). Both mutate the same global in-memory caches in `storage.js` (`assocUnstableUnits`, `assocCachedUnits`, `assocBestChildren`, `assocUnstableMessages`) and both call `storage.forgetUnit()` / `aa_composer.revertResponsesInCaches()` to "free" cache entries for units that were only provisionally created. Because these two paths are serialized by *different* mutexes, they are not mutually exclusive, and a dangling/stale reference in the shared cache can be produced or consumed by the other path.

### Finding Description
An unprivileged unit poster who sends a payment to an AA can force the node to run `aa_composer.dryRunPrimaryAATrigger()` synchronously while validating/saving the newly submitted unit: [1](#0-0) 

This call happens inside `handleJoint`'s `ifOk` callback, which is executed while holding the `'handleJoint'` mutex (acquired earlier in the same function) — the mutex is only released after `writer.saveJoint()` finishes: [2](#0-1) [3](#0-2) 

`dryRunPrimaryAATrigger()` runs the *real* trigger-handling code (`handleTrigger`), which validates and actually calls `validateAndSaveUnit`/`writer.saveJoint` for the synthetic response unit(s), populating storage's global in-memory caches (`assocUnstableUnits`, `assocCachedUnits`, `assocBestChildren`) exactly as if they were confirmed units, then rolls back the DB transaction and purges the cache entries again via `revertResponsesInCaches()`: [4](#0-3) [5](#0-4) 

`revertResponsesInCaches()`/`storage.forgetUnit()` unconditionally dereferences `storage.assocUnstableUnits[unit]` to read `.parent_units` and to pull the unit object out of its parent's `assocBestChildren` list: [6](#0-5) 

Meanwhile, **independently**, `writer.saveJoint()` (after a real stabilization) invokes `aa_composer.handleAATriggers()` to execute real, stabilized AA triggers — this is guarded only by the separate `'aa_triggers'` mutex, not `'handleJoint'`: [7](#0-6) [8](#0-7) 

Because `'handleJoint'` (used by the dry run) and `'aa_triggers'` (used by real trigger execution) are two different mutexes, both flows can be "in flight" at the same time and both read/write the same global, un-namespaced maps in `storage.js` (`assocUnstableUnits`, `assocCachedUnits`, `assocBestChildren`, `assocUnstableMessages`, `assocStableUnits`) as well as `stateVars`/`assocBalances` derived from `aa_addresses`/`aa_balances` for the *same AA address*. If a real trigger for AA `X` is mid-execution (its response unit(s) already inserted into `assocUnstableUnits`/`assocBestChildren` by `writer.saveJoint`, not yet committed/finalized) at the moment a dry run for a different unit sent to the *same* AA `X` starts and finishes its own `revertResponsesInCaches()`, the dry run's cache mutations (`delete assocUnstableUnits[unit]`, `_.pull(assocBestChildren[parent_unit], assocUnstableUnits[unit])`) operate on cache state that the concurrently-running real trigger execution is simultaneously building/reading. This is structurally the same bug class as the Chrome UAF: two logically distinct executions (isolated by the developer's intent — "dry run vs. real run") that are not actually isolated from each other because they hold different locks, mutating a shared heap of long-lived unit-cache objects and freeing entries out from under the other execution.

### Impact Explanation
If the dry-run path frees (`forgetUnit`) or corrupts `assocBestChildren`/`assocUnstableUnits` entries that the concurrently executing real AA-trigger flow still expects to be present and consistent (e.g., a parent unit's list of best children, or a unit's cached `parent_units`), the real flow can:
- crash the node (`assocUnstableUnits[unit].parent_units` throwing on `undefined`, a `throw Error("no unstable props of ...")`/`throw Error("trying to forget stable unit ...")` style invariant violation elsewhere in `storage.js`), causing a denial of service that stops the node from confirming new units, or
- proceed with an inconsistent view of `is_free`/best-child bookkeeping, potentially causing the two mutex domains to disagree about unit stability/validity — the same "node disagreement on validity or stability" impact class called out as in-scope.

This is triggerable by any unprivileged party who posts a unit paying an AA (to trigger the dry run) while another trigger to the same AA is being processed for real, requiring no special privileges, peer trust, or node-operator access.

### Likelihood Explanation
`conf.bDryRunNewTriggers` gates this code path; I could not verify from the indexed code whether it is enabled by default in this repository revision, so likelihood depends on that configuration flag being on (it is explicitly designed to run untrusted, attacker-supplied trigger payloads before real execution, which is its whole purpose). Given AAs are commonly high-traffic (bots, DEX, exchanges), the timing window for a real trigger execution and a dry run against the same AA address overlapping is plausible under normal network load, though winning the race reliably would likely require some effort/timing control by the attacker.

### Recommendation
- Serialize dry-run trigger execution and real AA-trigger execution under the *same* mutex (e.g., have `dryRunPrimaryAATrigger` also acquire the `'aa_triggers'` lock, or acquire a combined lock covering both), so the two paths can never mutate `storage.js`'s global caches concurrently.
- Alternatively, make dry-run execution fully cache-isolated (operate on a deep-cloned/sandboxed snapshot of `assocUnstableUnits`/`assocBestChildren`/`assocCachedUnits` rather than mutating the live global caches), so `revertResponsesInCaches`/`forgetUnit` never touches the shared, globally-visible cache used by real execution.
- Add defensive existence checks in `storage.forgetUnit` (verify `assocUnstableUnits[unit]` exists before dereferencing `.parent_units`) to fail safely (transient error) instead of crashing on cache-consistency violations, as a mitigation while the concurrency issue is fixed at the root.

### Proof of Concept
I was not able to fully verify (due to index/tool limitations) whether `conf.bDryRunNewTriggers` defaults to `true` in this deployment, nor could I trace the exact interleaving needed to hit the crash deterministically from the indexed snippets alone. A concrete PoC would require:
1. Deploy/confirm an AA address `X`.
2. Post unit `U1` paying `X`, causing its AA trigger to be scheduled and, upon stabilization, executed by `handleAATriggers()` (holding `'aa_triggers'` lock) — ideally with a chain of secondary AAs to widen the execution time window.
3. While `U1`'s real trigger is mid-flight, post a second unit `U2` also paying `X` (or another AA reachable via `U1`'s call chain) so that `network.js`'s `ifOk` dry-run path (`dryRunPrimaryAATrigger`, holding only `'handleJoint'`) runs concurrently and calls `revertResponsesInCaches`/`forgetUnit` against shared caches while `handleAATriggers()` is still populating/reading them.
4. Observe either a crash (`throw Error(...)` from `storage.js` invariant checks) or, if the caches end up silently inconsistent, an incorrect `is_free`/best-child state used in subsequent stability determination (`main_chain.js`).

This should be validated by a background Devin agent with full repository/test access, since confirming the exact race timing and the default value of `conf.bDryRunNewTriggers` requires executing the actual code paths, which is beyond what the indexed snippets alone can prove.
