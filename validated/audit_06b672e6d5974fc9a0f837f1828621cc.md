### Title
`RuleEngine._regex_match` fails to catch `TypeError` from non-string pattern, causing `pretooluse.py`'s blanket handler to fail-open on block rules - ([File: plugins/hookify/hooks/pretooluse.py])

### Summary
`pretooluse.py`'s `main()` wraps rule evaluation in a bare `except Exception` combined with a `finally: sys.exit(0)`, so any unhandled exception raised inside `RuleEngine.evaluate_rules` results in the tool call being implicitly allowed rather than denied. `RuleEngine._regex_match` only catches `re.error`, not `TypeError`, and a rule frontmatter value of `pattern: true` (unquoted boolean) is parsed as a Python `bool` rather than a `str`, causing `re.compile()` to raise `TypeError` when that rule is evaluated, which aborts evaluation of *all* rules for that hook call.

### Finding Description
In `plugins/hookify/hooks/pretooluse.py`, `main()` reads stdin, loads rules via `load_rules()`, and calls `RuleEngine().evaluate_rules(rules, input_data)` inside a `try/except Exception ... finally: sys.exit(0)` block [1](#0-0) . If `evaluate_rules` raises, the handler prints an error `systemMessage` and unconditionally exits 0 — no `permissionDecision: deny` is ever emitted, so Claude Code treats the tool call as allowed.

`RuleEngine.evaluate_rules` iterates over all loaded rules and, for each, calls `_rule_matches` → `_check_condition` → `_regex_match` for `regex_match` conditions [2](#0-1) . `_regex_match` only guards against `re.error`: [3](#0-2) 
It does not catch `TypeError`, which `re.compile()`/`compile_regex()` raises when the `pattern` argument is not a `str`/`bytes`/compiled pattern object.

The root cause of a non-string pattern reaching this code is in `config_loader.py`'s minimal hand-rolled YAML parser. For a simple top-level `key: value` frontmatter line, the value is coerced to a Python `bool` if it equals `"true"`/`"false"` case-insensitively, regardless of key name: [4](#0-3) 
This means a rule file frontmatter of `pattern: true` (legacy simple-pattern style, no `conditions:` list) sets `frontmatter['pattern'] = True` (a bool). `Rule.from_dict` then builds a `Condition(field=..., operator='regex_match', pattern=simple_pattern)` where `pattern` is `True`, not a string [5](#0-4) . This rule loads successfully (no exception during `load_rule_file`, since the parser itself never errors on this input) and is returned by `load_rules()`.

At evaluation time, `compile_regex(True)` is called and `re.compile(True, re.IGNORECASE)` raises `TypeError: first argument must be string or compiled pattern`, which is not `re.error` and therefore propagates out of `_regex_match`, `_check_condition`, `_rule_matches`, and `evaluate_rules`. Because `evaluate_rules` iterates rules in a single loop without per-rule exception isolation [2](#0-1) , this exception aborts evaluation of *every* rule in that hook invocation — not just the malformed one — including any legitimate `action: block` rules meant to stop dangerous commands. The exception is then swallowed by `pretooluse.py`'s blanket handler, and the hook exits 0 with no deny decision, converting the intended PreToolUse block into an implicit allow.

### Impact Explanation
A single malformed/malicious hookify rule file (checked into the repo under `.claude/hookify.*.local.md`, or generated by a workflow that materializes rules from PR/issue content) with an unquoted boolean `pattern:` value silently disables all block-type PreToolUse enforcement for that invocation, allowing an otherwise-blocked dangerous `Bash`/`Edit`/`Write` operation to execute. This is a fail-open trust-boundary bypass of the hook enforcement mechanism, violating the stated invariant that hook failures must fail closed for block-type rules.

### Likelihood Explanation
Feasibility is high and repeatable: it requires only that a `.claude/hookify.*.local.md` file exist with a legacy `pattern:` frontmatter field whose value parses as a YAML-like boolean (`true`/`false`, case-insensitive, unquoted). No special repo write privileges beyond the ability to add/modify a hookify rule file are needed, and the custom parser's boolean coercion applies uniformly to any top-level key, so this is not a contrived edge case but a straightforward consequence of the parser's design. Every PreToolUse/PostToolUse/Stop invocation while such a rule is loaded and enabled will trigger the same fail-open behavior.

### Recommendation
- In `RuleEngine._regex_match`, catch `(re.error, TypeError)` (or validate `isinstance(pattern, str)` before compiling) and treat non-matching/invalid patterns as non-matches with a logged warning, not a propagated exception.
- In `config_loader.py`, only coerce `true`/`false` string values to booleans for known boolean fields (e.g., `enabled`), not for arbitrary keys like `pattern`.
- In `pretooluse.py` (and the other hookify hook scripts), change the fail-open policy for exceptions raised specifically while evaluating `action: block` rules — e.g., isolate each rule's evaluation in its own try/except inside `evaluate_rules`, and only fail-open for rule-loading/parsing errors, not for genuine block-rule matches. At minimum, add a regex execution timeout to defend against catastrophic-backtracking DoS in `compile_regex`/`_regex_match`.

### Proof of Concept
Integration test (pytest) for `plugins/hookify/hooks/pretooluse.py`:
1. Create a temp `.claude/hookify.bad.local.md` containing:
   ```
   ---
   name: block-rm
   enabled: true
   event: bash
   action: block
   pattern: true
   ---
   Blocked!
   ```
2. Run `pretooluse.py` as a subprocess with stdin:
   ```json
   {"tool_name": "Bash", "tool_input": {"command": "rm -rf /"}, "hook_event_name": "PreToolUse"}
   ```
3. Assert that stdout JSON's `hookSpecificOutput.permissionDecision == "deny"` (expected fail-closed behavior) OR that the process exits non-zero.
4. Current behavior (bug reproduction): stdout is `{"systemMessage": "Hookify error: first argument must be string or compiled pattern"}` and the process exits 0 with no `permissionDecision` key, i.e., the dangerous `rm -rf /` command is implicitly allowed — assertion of deny fails, proving the vulnerability.
