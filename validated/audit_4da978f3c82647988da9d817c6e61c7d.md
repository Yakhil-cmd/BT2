## Title
Permissionless AA can force a primary AA response to fully revert by bouncing as a secondary trigger, causing DOS of multi‑recipient payouts (Files: `aa_composer.js`)

## Summary
`handleTrigger()` in `aa_composer.js` treats **any address that receives an output from an AA response unit** as a potential secondary AA trigger. If that recipient address happens to be an Autonomous Agent (AA) that bounces, the whole chain — including the primary AA's own committed response and any payments to *other, unrelated* recipients in the same response unit — is reverted via `revert()`. Because anyone can permissionlessly define and deploy an AA (no special privilege needed, exactly like anyone calling `notifyRewardAmount()` in the Velodrome report), an attacker can plant a "always‑bounce" AA and become (or arrange to be) one of the output addresses of a shared, multi‑recipient distributing AA (e.g., a rewards/bribes/airdrop AA), thereby denying payment to everyone else who was supposed to be paid in that same trigger.

## Finding Description
`handleSecondaryTriggers()` looks up every output address of a just‑built response unit that is itself an AA address, and fires a nested `handleTrigger()` call for each of them: [1](#0-0) 

If any of these secondary triggers bounces (`onDone` is called with a `bounce_message`), the `async.eachSeries` error callback does **not** limit the damage to the failing secondary AA — for a primary trigger it calls `revert()`, wiping out *all* AA responses accumulated so far for the entire trigger chain: [2](#0-1) 

`revert()` clears `arrResponses`, rolls back the DB to the savepoint taken before the trigger started, and finally calls `bounce()` on the primary AA: [3](#0-2) 

Whether an address is treated as a secondary trigger only depends on it being a known AA address and having received a nonzero output — anyone can create such an address for free, no allow‑list or permission check is enforced: [4](#0-3) 

So a multi‑recipient payout produced in a single AA response unit — e.g. an AA that distributes rewards/bribes/refunds to several addresses collected from prior deposits/votes in one `payment` message — can be entirely blocked: if even one of those recipient addresses is/behaves as an always‑bouncing AA, the *whole* response (including transfers meant for all the innocent recipients) is rolled back and bounced instead of delivered. This is exactly analogous to the reported Bribe/Gauge issue where a single malicious reward token in a shared, iterated list caused the entire `deliverBribes()`/`distribute()`/`getReward()` call to revert for everyone.

## Impact Explanation
Any AA design that batches payments to multiple beneficiaries in one response unit (rewards distribution, refund/airdrop AAs, matching pools, bribe‑like reward AAs, etc.) can be permanently denied by a single attacker: the attacker only needs to (a) deploy a trivial AA whose logic unconditionally calls `bounce()`, and (b) ensure that address is among the recipients of the distributing AA's payout (e.g., by being a legitimate participant, or by getting listed via normal deposit/voting flow). From that point, every trigger that would pay out to the whole batch reverts, and no legitimate recipient in that batch receives funds, and the distributing AA's own state changes for that round are rolled back too — a lasting funds‑freezing / DOS condition for the shared distribution AA, matching the "AA fund loss or freezing" / "node disagreement on validity" impact bar.

## Likelihood Explanation
Deploying an AA definition is fully permissionless and free (posting a `definition` message), matching the report's baseline of "callable by anyone." Getting oneself included as an output recipient in a shared multi‑party AA is a normal use case for many AA designs (rewards pools, matching engines, refund AAs) rather than a contrived edge case, so the precondition is easily met by any user who wants to grief such an AA.

## Recommendation
Do not let a failing secondary trigger revert the primary trigger's already‑produced response and payments to unrelated recipients. Options:
- Isolate each secondary trigger's execution/rollback scope so that a bounce in one branch only reverts that branch's own state/balance changes, not the entire response chain.
- Alternatively, require AA authors who want to pay multiple independent parties in one response to use separate response units/messages per recipient so a single recipient's AA behavior cannot cascade-fail the batch.
- At minimum, document this atomicity behavior prominently so AA authors avoid batching payouts to attacker‑influenceable addresses in a single response unit, and consider adding a trigger option to suppress secondary‑trigger propagation for selected outputs.

## Proof of Concept
1. Deploy AA `M` (malicious) whose only logic is:
   ```
   ['autonomous agent', { messages: [ { app: 'state', state: '{ bounce("dos"); }' } ] }]
   ```
   Anyone can post this `definition` unit — no privilege required.
2. Deploy (or use an existing) distributor AA `D` whose response, in a single trigger, pays multiple recipients in one `payment` message, e.g. outputs to `[A, B, M]` where `A`/`B` are legitimate users and `M` is the attacker's AA.
3. Trigger `D` (e.g., an epoch‑based payout, as in `handleTrigger()`/`sendUnit()` building a multi‑output payment message): [5](#0-4) 
4. After `D`'s response unit is built and saved, `handleSecondaryTriggers()` finds `M` among the output addresses and triggers it: [1](#0-0) 
5. `M` immediately bounces, its `onDone` reports `bounce_message`, and `async.eachSeries`'s final callback calls `revert()`: [2](#0-1) 
6. `revert()` clears all of `D`'s accumulated responses and rolls back the transaction, so `A` and `B` receive **nothing**, even though they were legitimate, unrelated recipients: [3](#0-2) 

This can be repeated on every subsequent trigger of `D` as long as `M` remains (or is re‑added as) a payout recipient, permanently denying service to all co‑recipients of that distribution round.

function getTrigger(objUnit, receiving_address) {
	var trigger = { address: objUnit.authors[0].address, unit: objUnit.unit, outputs: {} };
	if ("max_aa_responses" in objUnit)
		trigger.max_aa_responses = objUnit.max_aa_responses;
	objUnit.messages.forEach(function (message) {
		if (message.app === 'data' && !trigger.data) // use the first data message, ignore the subsequent ones
			trigger.data = message.payload;
		else if (message.app === 'payment' && message.payload) {
			var payload = message.payload;
			var asset = payload.asset || 'base';
			payload.outputs.forEach(function (output) {
				if (output.address === receiving_address) {
					if (!trigger.outputs[asset])
						trigger.outputs[asset] = 0;
					trigger.outputs[asset] += output.amount; // in case there are several outputs
				}
			});
		}
	});
	if (Object.keys(trigger.outputs).length === 0)
		throw Error("no outputs to " + receiving_address);
	return trigger;
}
