This confirms the vulnerability. `Shipit.github(organization:)` at [1](#0-0)  looks up a distinct `GitHubApp` config (with its own `webhook_secret`) per organization when multi-org config is used. Each organization thus owns and controls its own webhook secret, but nothing binds the signature-verified organization to the repository that the webhook payload is subsequently allowed to act on.

### Title
Webhook Signature Verified Against `repository.owner.login` but Stack Lookup Uses Unbound `repository.full_name`, Allowing Cross-Organization Deploy Triggers - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects the GitHub App / webhook secret to validate against using `repository_owner`, taken from `params.dig('repository', 'owner', 'login')`. Once verified, `Shipit::Webhooks::Handlers::Handler#stacks` locates the target `Repository`/`Stack` using a *different* field of the same payload, `payload.dig('repository', 'full_name')`. In Shipit's multi-organization GitHub App configuration, each organization has its own independently-held `webhook_secret`. Nothing ties "the organization whose secret validated this request" to "the repository whose stack gets mutated," so a party who legitimately controls one organization's webhook secret can forge a payload naming a different organization's repository in `full_name` while keeping `owner.login` pointed at their own org for signature selection.

### Finding Description
- Signature verification: `Shipit.github(organization: repository_owner)` where `repository_owner` comes from `params.dig('repository', 'owner', 'login')`. [2](#0-1) 
- Multi-org resolution, each org configured with its own `webhook_secret`: [3](#0-2) 
- Downstream handler resolves the acted-upon repository/stack from a **different** JSON key of the same body, `repository.full_name`, with no cross-check against `repository.owner.login`: [4](#0-3) 
- `PushHandler` uses that `stacks` scope to trigger `stack.sync_github(expected_head_sha:)` for every matching, non-archived stack on the parsed branch: [5](#0-4) 
- Similarly, PR handlers resolve the acted `repository`/`review_stacks` purely from `params.repository.full_name`: [6](#0-5) 

The binding that is broken: **organization authenticated (via HMAC signature keyed to `repository.owner.login`) ≠ repository actually written to (`repository.full_name`)**. Because the webhook secret is per-organization in multi-tenant configuration, "possession of a valid signature for org A" is treated by the controller as sufficient authorization, but the handlers never re-validate that the acted-upon repository actually belongs to org A. An attacker who controls Org A's GitHub App/webhook secret (a legitimate, unprivileged party relative to Org B) can post directly to `/webhooks` (bypassing GitHub entirely) with `repository.owner.login = "OrgA"` (so `verify_signature` selects and passes with OrgA's known secret) but `repository.full_name = "OrgB/private-repo"` (targeting a stack owned by a different, unrelated tenant).

### Impact Explanation
This allows cross-repository/cross-tenant writes: a `push` webhook can force `GithubSyncJob` to run against another organization's `Stack` (potentially triggering resyncs of arbitrary shas via `sync_github(expected_head_sha:)`), and PR-event handlers can archive/unarchive/create review stacks belonging to a completely different organization's repository. This matches the "unauthorized deploy/write across repository boundaries" Critical impact category, since it lets a party authenticated only for their own tenant manipulate deploy state for a repository they have no access to, directly analogous to the report's core issue: a verified credential (TSS/observer trust, here webhook secret) is treated as authorizing an action (chain state/stack state change) on an entity (repository) it was never actually scoped to.

### Likelihood Explanation
This only materializes in Shipit deployments using the multi-organization GitHub App configuration schema (`secrets.github` keyed by org name) documented in `test/dummy/config/secrets_double_github_app.yml`, where multiple organizations share one Shipit instance. In that configuration, the trust boundary between tenants relies entirely on this signature/repository-name binding, which does not exist. This is not a hypothetical GitHub-side spoof — the attacker sends the crafted payload directly to Shipit's `/webhooks` endpoint, so GitHub's own repository-ownership enforcement is bypassed entirely; only knowledge of one tenant's webhook secret is required.

### Recommendation
In `WebhooksController#verify_signature` (or in `Shipit::Webhooks::Handlers::Handler`), after resolving `repository_owner` for secret selection, assert that `payload.dig('repository', 'full_name')` (and `payload.dig('organization','login')` when present) is actually owned by that same organization before dispatching to handlers — e.g., reject the webhook if `full_name.split('/').first.casecmp(repository_owner) != 0`. More robustly, scope `stacks`/`Repository.from_github_repo_name` lookups within handlers to only repositories registered under the verified organization.

### Proof of Concept
1. Configure Shipit with two organizations, `orga` and `orgb`, each with a distinct `webhook_secret` (`test/dummy/config/secrets_double_github_app.yml` pattern).
2. As a party who possesses/administers `orga`'s GitHub App (and thus knows `orga`'s `webhook_secret`), craft a `push` event JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha already reachable in orgb/target-repo>",
  "repository": { "owner": { "login": "orga" }, "full_name": "orgb/target-repo" }
}
```
3. Compute `X-Hub-Signature: sha1=<hmac-sha1(orga_webhook_secret, body)>` and POST directly to `https://<shipit-host>/webhooks` with `X-Github-Event: push`.
4. `verify_signature` resolves `repository_owner = "orga"`, fetches OrgA's `GitHubApp`, and the signature validates successfully (per [7](#0-6) ).
5. `PushHandler#process` calls `stacks` → `Handler#stacks`, which resolves `Repository.from_github_repo_name("orgb/target-repo")` (per [8](#0-7) ) — a repository belonging to the unrelated `orgb` tenant — and enqueues `stack.sync_github(expected_head_sha:)` for it, despite the request never being authenticated for `orgb`.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
