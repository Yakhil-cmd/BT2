### Title
CCMenu API token is created without stack scoping, granting unauthenticated read access to every stack instead of the one it was generated for - (File: app/controllers/shipit/ccmenu_url_controller.rb)

### Summary
The reported bug class is a deployment-trust binding break where a value that is supposed to be authorized/scoped ends up applying more broadly than intended. The `shipit-engine` analog is in the CCMenu token minting flow: `Shipit::ApiClient` supports being scoped to a single stack via its `belongs_to :stack, optional: true` association, and `Api::BaseController` explicitly restricts an `ApiClient`'s visible stacks to that one stack when `stack_id` is set [1](#0-0) . However, the controller that mints the CCMenu token never sets that scope, so the token silently authorizes every stack, not just the one displayed in the UI.

### Finding Description
`CCMenuUrlController#fetch` builds a per-stack "CCMenu URL" for the currently authenticated Shipit user and embeds an API token in the query string: [2](#0-1) 

The `client` method creates (or reuses) an `ApiClient` keyed only by `creator` and a fixed `name: 'CCMenu Client'`, granting `read:stack` — but it never passes `stack:` to bind the client to the specific stack the URL is being generated for:
```ruby
def client
  @client ||= ApiClient.create_with(permissions: %w[read:stack])
                       .find_or_create_by!(creator: current_user, name: 'CCMenu Client')
end
```
This is the same `ApiClient` record for a given user across *all* stacks: the first time a user requests a CCMenu URL (for stack A), a stackless client is created; every subsequent CCMenu URL generated by that user (for stack B, C, …) reuses that exact record and token, since `find_or_create_by!` matches on `creator` + `name` only.

Downstream, `Api::CCMenuController` (the endpoint the token is actually used against) authenticates via this bare token and then resolves the target stack with an unscoped, global lookup: [3](#0-2) 

Even if that controller instead used the inherited scoped `stack`/`stacks` helpers from `Api::BaseController`, it would make no difference here, because those helpers only narrow to one stack when `current_api_client.stack_id?` is true: [4](#0-3) 

Since the CCMenu client's `stack_id` is never populated, `stacks` degrades to `Stack.all`. The binding that should hold is:

`stack the CCMenu token was minted for` == `stack the CCMenu token can read`

but because `stack:` is omitted at creation time, the right-hand side becomes "every stack in the installation."

### Impact Explanation
A CCMenu URL is designed to be handed out to third-party, unauthenticated CI dashboard tools (CCTray-style monitors) and is often embedded in semi-public places (status boards, wiki pages, Slack channels) under the assumption it exposes only the one stack's build/deploy status. Because the underlying `ApiClient` is never scoped to that stack, anyone in possession of a single leaked CCMenu URL/token can query `Api::CCMenuController#show` for **any** `stack_id` in the Shipit instance and obtain that stack's latest deploy/rollback status — this is an unauthenticated read of stack state for stacks the token was never meant to expose, which matches the High-impact category "unauthenticated read of stack state, task streams or deploy output."

### Likelihood Explanation
No special privileges are needed beyond what any ordinary Shipit user already has to request a CCMenu URL for one stack via the Settings page. No mistake by an attacker is required — the flaw is deterministic and always reproducible, and once a single link is shared/leaked (the expected, documented use case for CCMenu URLs), the exposure is total (every stack) rather than the intended single stack.

### Recommendation
- Pass `stack:` explicitly when creating/looking up the CCMenu `ApiClient`, scoping `find_or_create_by!` by `creator`, `name`, and `stack` (so each stack gets its own scoped client/token) in `app/controllers/shipit/ccmenu_url_controller.rb`.
- Ensure `Api::CCMenuController#stack` uses the scoped `stacks` helper (or otherwise enforces `current_api_client.stack_id == stack.id` when `stack_id` is present) instead of the global `Stack.from_param!`.

### Proof of Concept
1. As any authenticated Shipit user, open Stack A's Settings page and trigger the CCMenu URL generation flow (`GET /ccmenu_url/*stack_id`, i.e. `CCMenuUrlController#fetch`) for Stack A. This mints/reuses an `ApiClient` named `CCMenu Client` for that user with `permissions: ['read:stack']` and `stack_id: nil`, returning a URL such as:
   `https://shipit.example.com/api/stack-a/ccmenu?token=<TOKEN>`
2. Take the same `<TOKEN>` and swap in Stack B's identifier (any other stack in the installation, including ones the token was never generated for):
   `https://shipit.example.com/api/stack-b/ccmenu?token=<TOKEN>`
3. `Api::CCMenuController#authenticate_api_client` accepts `<TOKEN>` (it is a valid `ApiClient` token) and `#show`/`#stack` resolves Stack B via the unscoped `Stack.from_param!`, returning Stack B's deploy status — despite the token/URL being labeled and shared as belonging only to Stack A. # frozen_string_literal: true

module Shipit
  module Api
    class CCMenuController < BaseController
      require_permission :read, :stack

      class NoDeploy
        def id
          0
        end

        def ended_at
          Time.now.utc
        end

        def running?
          false
        end
      end

      def show
        latest_deploy = stack.deploys_and_rollbacks.last || NoDeploy.new
        render('shipit/ccmenu/project', formats: [:xml], locals: { stack:, deploy: latest_deploy })
      end

      private

      def stack
        @stack ||= Stack.from_param!(params[:stack_id])
      end

      def authenticate_api_client
        @current_api_client = ApiClient.authenticate(params[:token])
        super unless @current_api_client
      end
    end
  end
end
