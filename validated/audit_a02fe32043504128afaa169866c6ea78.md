### Title
Unvalidated route pool can execute a victim-authorized token transfer and drain wallet assets - ([File: contracts/swap-aggregator/src/execute/mod.rs](contracts/swap-aggregator/src/execute/mod.rs))

### Summary
Swap routes supply arbitrary pool addresses that the router invokes while the account owner’s `require_auth` context is active. A malicious route pool can therefore call `token.transfer(victim, attacker, amount)`; Soroban records that nested authorization under the victim’s top-level controller authorization. If the victim signs the poisoned authorization tree, the route succeeds while transferring unrelated wallet tokens to the attacker.

### Finding Description
`swap_collateral` authenticates `caller`, then invokes the configured router through `swap_tokens`. [1](#0-0) 

The controller narrowly authorizes only `token_in.transfer(controller, router, amount_in)`, but this protects the controller’s routed collateral rather than the caller’s broader wallet authorization tree. [2](#0-1) 

The router decodes the caller-supplied `StrategyPayload`, resolves `hop.pool` from the attacker-controlled `assets` registry, and dispatches that address to a venue adapter. [3](#0-2) [4](#0-3) 

There is no venue-pool allowlist or contract-identity check: Soroswap invokes `get_reserves` and `swap` on the supplied pool address, while Aquarius invokes `get_tokens` and `swap` on it. [5](#0-4) [6](#0-5) [7](#0-6) 

Because the victim’s `caller.require_auth()` remains the authorization root for the whole controller call, malicious code reached through the route can request a `token.transfer` from the victim. Simulation reports it as a child invocation beneath `swap_collateral`; signing that tree authorizes the transfer. [8](#0-7) [9](#0-8) 

### Impact Explanation
An attacker can steal token balances held in the victim’s wallet, including assets unrelated to the lending position and not deposited into the protocol. The malicious pool only needs to return enough output for the swap’s measured-output and account-risk checks to pass, so the protocol operation can appear economically valid while unrelated wallet funds are transferred to the attacker. [10](#0-9) [11](#0-10) 

### Likelihood Explanation
This requires victim interaction: the attacker must induce the victim to submit a malicious route and sign an authorization tree containing the unexpected token transfer. Wallet display quality and the victim’s failure to inspect nested auth determine exploitability, so the likelihood is lower than a fully permissionless exploit, but the resulting loss can be the victim’s full balance of a targeted token. [12](#0-11) 

### Recommendation
Do not invoke payload-supplied pool addresses without authenticating them. Maintain a governance-approved pool registry or verify each pool against the intended venue’s factory/deployer identity before dispatch. Reject authorization trees that add calls unrelated to the expected route where technically possible, and make clients/wallets explicitly reject any `swap_collateral`, `swap_debt`, `multiply`, or `repay_debt_with_collateral` authorization containing child transfers from the user other than the documented input flow. [13](#0-12) [9](#0-8) 

### Proof of Concept
1. The attacker deploys a malicious contract implementing the selected venue interface, funded with enough output token to satisfy the route.
2. For a Soroswap-shaped hop, its `get_reserves` returns reserves that produce a valid `requested_out`, and its `swap` function:
   - calls `token::Client::new(&env, &victim_token).transfer(&victim, &attacker, &victim_balance)`;
   - transfers the expected `token_out` amount from itself to the router;
   - returns normally.
3. The attacker constructs `swap_collateral(caller=victim, account_id, current, from_amount, new, swap)`, where `swap` encodes a `StrategyPayload` whose `assets` registry contains the input token, output token, and malicious pool address, and whose program performs one swap through that pool.
4. The victim simulates the call. The simulation reports the malicious wallet-token transfer as a child of the victim’s `swap_collateral` authorization rather than as a separate top-level authorization.
5. If the victim signs that tree, the malicious `transfer` executes, the router receives sufficient output, measured-output checks pass, and the victim loses `victim_balance` of an otherwise unrelated token. [14](#0-13) [15](#0-14) [9](#0-8)

```markdown
That bound covers the controller's own grant only. The router calls the pool
and token addresses its payload names and keeps no allowlist of them, so a
route can put third-party code on the call stack below the caller's
authorization. A token transfer that such code makes from the caller is
recorded by an honest simulation as a child of the caller's authorization
entry, and it executes if the caller signs that tree. The loss is then the
caller's wallet, not the routed amount, and neither the payload minimum nor the
final risk gate bounds it. An honest swap strategy gives the caller no child
entry, and a direct router swap gives exactly one input transfer. A client must
decode the route it signs and refuse an authorization tree with any other
child. The direct `execute_strategy` path has the same exposure for every swap
user.
```
