### Title
Unbounded, attacker-controlled submodule fan-out during `configureWorktree` causes permanent per-cycle sync denial - (File: `main.go`)

### Summary
`git-sync` automatically expands and checks out git submodules on every sync cycle via `git submodule update --init --recursive` inside `configureWorktree`. The number and depth of submodules is defined entirely by content the synced repository controls (`.gitmodules`), so a single commit that a pusher places on the tracked `--ref` can force git-sync to recursively resolve and clone an arbitrarily large/deep submodule tree on every sync attempt, with no cap on submodule count, nesting depth, or cumulative cost. This is the same bug class as the reported "linear iteration over unbounded, attacker-created collection in unmetered, automatically-triggered execution" — instead of Rewards Plans iterated every `BeginBlock`, it is submodules iterated every sync period.

### Finding Description
In the sync path, `configureWorktree` unconditionally invokes recursive submodule resolution whenever submodules are not disabled (the default is `recursive`): [1](#0-0) 

This call is driven purely by the `.gitmodules` file and submodule commit graph found inside the synced repository — content that is fully attacker-controlled if the attacker can push to the tracked ref (or if `--repo` points at an untrusted upstream, which is the documented threat model for git-sync sidecars). There is no limit anywhere in git-sync on:
- the number of `[submodule]` entries in `.gitmodules`,
- the nesting depth of submodule-of-submodule chains, or
- the aggregate time/CPU/network/disk consumed resolving them.

`configureWorktree` is called unconditionally from the main `SyncRepo` per-cycle path: [2](#0-1) 

which itself runs inside the outer, infinite sync loop that re-invokes `SyncRepo` every `--period`: [3](#0-2) 

The only bound on a single attempt is `--sync-timeout` (`flSyncTimeout`, default 120s), enforced via `context.WithTimeout`: [4](#0-3) 

but that only aborts one attempt — the loop immediately retries on the next `--period` tick, re-running the same expensive/failing submodule resolution forever. This matches the "unmetered iteration executed automatically every cycle with no scaling cost" root cause described in the report: git-sync applies no work-proportional cost or limit to submodule fan-out before spending wall-clock/CPU/disk resources on it.

### Impact Explanation
Once an attacker's commit (containing a very large or deeply/circularly nested `.gitmodules` submodule graph) becomes the target of `--ref`, every subsequent sync attempt:
1. Consumes disk, network, and CPU proportional to the attacker-chosen submodule fan-out (recursive clones of each submodule, and sub-submodules, at up to full history if `--depth` unset).
2. Repeatedly exceeds `--sync-timeout`, so the sync never completes and the published symlink/worktree is never advanced — a **persistent sync denial** of the specific accepted-impact category (denial of freshness for every consumer of the `--link` volume, e.g. all pods mounting the shared `emptyDir`).
3. Repeats on every `--period` indefinitely (not a one-time cost), because failed attempts are simply retried by the outer loop, and the failure condition (huge/deep submodule tree at the synced ref) doesn't self-heal without operator intervention (e.g. changing `--ref`/`--submodules=off`).

This is a low-cost (a single crafted commit/push, or control of `--repo`'s content), high-impact denial-of-service against the git-sync sidecar, directly analogous to the reported unbounded Rewards Plan iteration causing a chain halt every `BeginBlock`.

### Likelihood Explanation
Likelihood is **Medium-High** in the deployments git-sync explicitly targets:
- `--submodules` defaults to `recursive`, so no special configuration is needed to be exposed.
- Any principal able to push a commit to the synced branch/ref (a common trust boundary for CI/GitOps sidecars watching a shared or less-trusted branch) can trigger it with a single commit.
- No fee, quota, or gas-like mechanism exists to make the attack progressively expensive, unlike the on-chain case which at least charges 1 TIA per plan.

### Recommendation
Add explicit, operator-configurable bounds before invoking recursive submodule resolution in `configureWorktree`:
- Cap the number of submodules processed (e.g., pre-scan `.gitmodules` and refuse/skip if the count exceeds a configurable limit).
- Cap recursive nesting depth independently of `--depth` (which only bounds per-repo history depth, not submodule-tree depth).
- Consider making `git submodule update` bound by its own sub-timeout distinct from `--sync-timeout` so a hung/huge submodule tree doesn't repeatedly consume the full sync-timeout budget every cycle, and surface a clear, actionable error (e.g., "submodule count/depth exceeds limit") instead of a silent timeout retried forever.

### Proof of Concept
1. In a test upstream repository, add `.gitmodules` referencing thousands of trivial submodule repositories (or a chain of submodules-of-submodules many levels deep), analogous to the existing nested-submodule e2e test infrastructure: [5](#0-4) 
2. Point `git-sync` at this repo with default flags (`--submodules` unset ⇒ `recursive`) and a short `--sync-timeout`.
3. Observe that `configureWorktree`'s submodule step never completes within `--sync-timeout`: [6](#0-5) 
4. Observe the outer loop retries every `--period`, repeating the same expensive/failing resolution indefinitely and never advancing the published symlink — a persistent sync denial: [7](#0-6)
