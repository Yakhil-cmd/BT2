### Title
Headers-commission split rounds independently per recipient, allowing GBYTE supply inflation - (File: `headers_commission.js`)

### Summary
`calcHeadersCommissions()` in `headers_commission.js` splits a unit's headers commission among multiple `earned_headers_commission_recipients` by rounding each recipient's share independently with `Math.round()`, instead of rounding down for all-but-one recipient and assigning the remainder to the last one. Because each fractional share is rounded to the nearest integer independently, the sum of the rounded amounts can exceed the original `full_amount` that is actually available to be paid out. This mirrors the reported Arcadia bug class: a value split/converted with a rounding operation that benefits the recipient(s) instead of the protocol, causing the total credited value to exceed the true underlying value.

### Finding Description
When a stable child unit "wins" a parent's headers commission, the commission (`full_amount`) is split among the unit's `earned_headers_commission_recipients` (attacker-controlled for multi-authored units, validated only to sum to exactly 100 in `validateHeadersCommissionRecipients()`): [1](#0-0) 

The actual split and rounding happens in `headers_commission.js`: [2](#0-1) [3](#0-2) 

Each recipient's share is computed as `Math.round(full_amount * share / 100.0)` completely independently of the other recipients. Because `Math.round` rounds each fraction to the nearest integer (rounding `.5` up), and each recipient's rounding error is not tracked or offset against the others, the sum of all rounded `amount` values inserted into `headers_commission_contributions` can be strictly greater than `full_amount`. For example, with `full_amount = 3` and two recipients each holding a 50% share: `Math.round(3*50/100) = Math.round(1.5) = 2` for each recipient, so `2 + 2 = 4 > 3`, one extra byte is minted out of nowhere.

These per-recipient contribution rows are aggregated into `headers_commission_outputs`: [4](#0-3) 

and later spent as a `headers_commission` input via `mc_outputs.calcEarnings()`, which simply sums `amount` from `headers_commission_outputs` for the address/MCI range and treats it as real, spendable `total_input` of base-asset bytes in `validatePaymentInputsAndOutputs()`: [5](#0-4) [6](#0-5) 

There is no reconciliation step verifying that `SUM(headers_commission_outputs.amount)` for a payer unit's winning child equals the payer's `headers_commission` field; the extra rounded-up bytes become genuinely spendable, unbacked base-asset (bytes) — an inflation of the effective money supply, exactly analogous to the reported bug's "rounds in the wrong direction, benefiting the party receiving the converted value instead of the protocol."

### Impact Explanation
An attacker who authors a multi-authored unit (which the protocol explicitly supports and lets the author choose arbitrary `earned_headers_commission_recipients` shares summing to 100) can deliberately choose shares (e.g., several recipients at fractions like `x.5%`) that cause the independently-rounded per-recipient amounts to sum to more than the true headers commission `full_amount`. Each time such a unit wins a headers-commission "race" (an unprivileged/permissionless event that any author can arrange for their own units), a small amount of extra, unbacked bytes is created and later spent as legitimate `headers_commission` input in a real payment, directly inflating the effective GBYTE supply. This is a concrete, repeatable, protocol-level fund-creation bug (supply inflation), reachable purely by posting ordinary multi-authored units with attacker-chosen commission-recipient splits — no privileged, malicious-node, or network-level access is required.

### Likelihood Explanation
The `earned_headers_commission_recipients` array and its shares are fully attacker controlled for multi-authored units (validated only for a 100% sum and valid, sorted addresses in `validateHeadersCommissionRecipients`), and every stable unit with at least one child competes for/wins headers commission by design. An attacker only needs to control (or collude with) 2+ authors on a single unit and pick recipient share percentages that create rounding surplus (e.g., `50/50` on odd `full_amount`, or more recipients with `.5`-fraction shares for larger surplus), then repeat this over many units to accumulate inflated bytes over time. This makes the issue systematically and repeatedly exploitable by any ordinary user.

### Recommendation
Change the commission-splitting logic in `headers_commission.js` so the sum of distributed amounts can never exceed `full_amount`: round down (`Math.floor`) for all recipients except one, and assign that one recipient the remainder (`full_amount - sum_of_others`), ensuring `Σ amount === full_amount` exactly for every payer/child pair, both in the in-RAM path (`arrValuesRAM`) and the SQL-comparison path (`arrValues`).

### Proof of Concept
1. Post a 2-author unit `U` (author A and author B) that will act as a child of some parent unit `P` in the graph, with:
   - `earned_headers_commission_recipients = [{address: A, earned_headers_commission_share: 50}, {address: B, earned_headers_commission_share: 50}]` (valid per `validateHeadersCommissionRecipients`, since the shares sum to 100).
2. Ensure `U` becomes the "winning" child of `P` for headers commission (deterministic hash-based selection in `getWinnerInfo()`), and `P.headers_commission` is an odd value, e.g. `3`.
3. When `calcHeadersCommissions()` runs, for each recipient: `amount = Math.round(3 * 50/100) = Math.round(1.5) = 2`. Two entries of `2` are inserted into `headers_commission_contributions`/`headers_commission_outputs`, totaling `4`, exceeding the actual `full_amount = 3` by `1`.
4. Addresses `A` and `B` can later each spend their `headers_commission` output (`mc_outputs.calcEarnings` sums `headers_commission_outputs.amount`) as legitimate `total_input` in payment units, producing `4` real spendable bytes from an underlying `3`-byte commission — net GBYTE supply inflation of `1` byte per occurrence. Repeating this pattern across many units accumulates unbounded inflation over time.

function validateHeadersCommissionRecipients(objUnit, cb){
	if (objUnit.authors.length > 1 && typeof objUnit.earned_headers_commission_recipients !== "object")
		return cb("must specify earned_headers_commission_recipients when more than 1 author");
	if ("earned_headers_commission_recipients" in objUnit){
		if (!isNonemptyArray(objUnit.earned_headers_commission_recipients))
			return cb("empty earned_headers_commission_recipients array");
		var total_earned_headers_commission_share = 0;
		var prev_address = "";
		for (var i=0; i<objUnit.earned_headers_commission_recipients.length; i++){
			var recipient = objUnit.earned_headers_commission_recipients[i];
			if (!isPositiveInteger(recipient.earned_headers_commission_share))
				return cb("earned_headers_commission_share must be positive integer");
			if (hasFieldsExcept(recipient, ["address", "earned_headers_commission_share"]))
				return cb("unknown fields in recipient");
			if (!isValidAddress(recipient.address))
				return cb("invalid recipient address checksum");
			if (recipient.address <= prev_address)
				return cb("recipient list must be sorted by address");
			total_earned_headers_commission_share += recipient.earned_headers_commission_share;
			prev_address = recipient.address;
		}
		if (total_earned_headers_commission_share !== 100)
			return cb("sum of earned_headers_commission_share is not 100");

function calcEarnings(conn, type, from_main_chain_index, to_main_chain_index, address, callbacks){
	var table = type + '_outputs';
	conn.query(
		"SELECT SUM(amount) AS total \n\
		FROM "+table+" \n\
		WHERE main_chain_index>=? AND main_chain_index<=? AND +address=?",
		[from_main_chain_index, to_main_chain_index, address],
		function(rows){
			var total = rows[0].total;
			if (total === null)
				total = 0;
			if (typeof total !== 'number')
				throw Error("mc outputs total is not a number");
			callbacks.ifOk(total);
		}
	);
}
