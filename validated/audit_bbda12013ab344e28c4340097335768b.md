### Title
Cross-repository status forgery via unscoped `Commit.where(sha:)` lookup - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` looks up commits solely by `sha`, with no join or filter on the webhook's `payload['repository']['full_name']`, then writes a `Status` and can trigger `stack.schedule_merges` on whatever stack owns that commit. Since SHA1 values are global content hashes (not repository-scoped identifiers), any GitHub organization with the Shipit app installed can send a legitimately signed `status` webhook whose `sha` collides with a commit that actually belongs to a different, victim stack, causing state mutation and a merge-scheduling side effect on a repository the attacker never controls.

### Finding Description
The broken binding, stated as an equality that should hold but doesn't: for every `Status` row created as a result of a webhook, `commit.stack.repository.full_name` should equal `payload.dig('repository','full_name')`. In `StatusHandler#process` this is never checked: [1](#0-0) 

`params.sha` is parsed from the payload but the `payload` itself (which contains `repository.full_name`) is discarded when selecting commits — the query is `Commit.where(sha: params.sha)` across the *entire* `commits` table, not scoped via `stacks.where(...)` (the `Handler` base class even exposes a `stacks`/`repository_name` scoping helper that this handler doesn't use): [2](#0-1) 

For each matching commit (potentially several, across unrelated stacks, if the same SHA happens to exist in multiple repos — plausible for empty-tree commits, cherry-picks, or coincidental collisions on 40-hex prefixes since app also allows short-sha ambiguity elsewhere), `create_status_from_github!` runs and calls `add_status`, which can invoke `stack.schedule_merges`: [3](#0-2) [4](#0-3) 

`verify_signature` in `WebhooksController` confirms the request came from a real, HMAC-signed webhook for *some* legitimate organization (`Shipit.github(organization: repository_owner)`), but this only proves the sender controls that organization/app installation — it does not confirm that the `sha` inside the same payload belongs to a commit in that organization's repository: [5](#0-4) 

So the attacker's own, properly configured org can produce a fully valid signature while the `sha` field references an unrelated victim commit. The `ExplicitParameters` schema only validates the shape/types of `sha`, `state`, etc. — it has no cross-field/cross-repository constraint. No other guard (`force_github_authentication`, `require_permission!`, model validators) intervenes because this is a server-to-server webhook path, not a user session/API-client path.

### Impact Explanation
A forged `status` webhook from an attacker-controlled repository can flip the CI status of a commit belonging to a completely different Shipit stack to `success`, and — via `Commit#add_status` → `Stack#schedule_merges` — enqueue `ProcessMergeRequestsJob` for that victim stack. This is a cross-tenant write (a payload authenticated for repo A mutating stack/commit data belonging to repo B), matching the "Critical" category of "a payload for one repository mutating another's stack, commit... or an unauthorized deploy, rollback or merge." The practical exploitability depends on finding a real SHA collision between the attacker's commits and a target's commit history, which is unlikely for genuinely random SHAs but not implausible when: (a) the target repository has forked/mirrored history that overlaps with a repo the attacker can push to, (b) both repos share common ancestry (fork of the target), or (c) empty/trivial commits produce identical trees+messages+timestamps. This narrows the realistic blast radius versus a fully general "attacker picks any target sha," but the code path itself has no repository check at all.

### Likelihood Explanation
Preconditions: the attacker needs a real GitHub organization/repository with the Shipit GitHub App/webhook properly installed (satisfiable — GitHub App installs are self-service for orgs an attacker administers), and needs a commit whose SHA equals one already present in `shipit_commits` for a victim stack (most practically achievable via forking the victim's repo, since git SHAs are deterministic and identical trees/parents/messages/timestamps produce identical SHAs). This is a real but non-trivial precondition — it is not "any sha the attacker names," but any sha that already exists as a real commit in the target's fork lineage. Given many Shipit stacks track open-source or internally forked repos, an attacker forking the target and re-pushing the exact same commit (including via `git commit --amend` to reintroduce a known upstream SHA) is a low-cost, repeatable action.

### Recommendation
Scope the commit lookup by repository in `StatusHandler#process`, mirroring the `Handler#stacks` helper: e.g. `Commit.where(sha: params.sha, stack_id: stacks.select(:id))` or `stacks.flat_map { |s| s.commits.where(sha: params.sha) }`, using `payload.dig('repository','full_name')` to constrain results to stacks whose `Repository#full_name` matches the webhook's own repository before calling `create_status_from_github!`.

### Proof of Concept
```ruby
# test/models/webhooks/status_handler_test.rb
test "status webhook cannot mutate a commit belonging to a different repository" do
  victim_commit = shipit_commits(:fixture) # belongs to a specific stack/repository
  victim_stack = victim_commit.stack

  payload = {
    'sha' => victim_commit.sha,
    'state' => 'success',
    'context' => 'ci/attacker',
    'repository' => { 'full_name' => 'attacker-org/unrelated-repo', 'owner' => { 'login' => 'attacker-org' } }
  }

  assert_no_enqueued_jobs(only: Shipit::ProcessMergeRequestsJob) do
    Shipit::Webhooks::Handlers::StatusHandler.call(payload)
  end

  assert_not victim_commit.reload.statuses.exists?(context: 'ci/attacker'),
    "a status from an unrelated repository's webhook should not be written onto another stack's commit"
end
```
This test currently fails against the existing implementation (the status is written and `ProcessMergeRequestsJob` may be enqueued for `victim_stack`), demonstrating the cross-repository write.

    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
