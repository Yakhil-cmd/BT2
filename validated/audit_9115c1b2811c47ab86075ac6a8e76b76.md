### Title
Cross-organization team hijack via `MembershipHandler#find_or_create_team!` looking up `Team` by global `github_id` without organization binding - (File: `app/models/shipit/webhooks/handlers/membership_handler.rb`)

### Summary
`MembershipHandler#process` resolves the target `Team` solely by the numeric `github_id` supplied in the webhook body, and `WebhooksController#verify_signature` selects which organization's webhook secret to validate against using an attacker-controlled field (`organization.login`/`repository.owner.login`) from that same body. In a multi-organization Shipit deployment (the officially documented "Using Multiple GitHub Applications" configuration), an org administrator who legitimately controls their own low-privilege organization's webhook secret can forge a `membership` event that is correctly signed for their own org but references another organization's privileged `Team.github_id`, causing Shipit to add an arbitrary attacker-controlled GitHub login to that privileged team without any callback to GitHub verifying real membership.

### Finding Description
The broken binding: `Team.github_id_found_by_handler == Team.organization_that_signed_the_request` is assumed but never enforced.

Trace:
- `WebhooksController#verify_signature` picks the verification secret using `repository_owner`, which is read straight out of the untrusted JSON body: `params.dig('repository','owner','login') || params.dig('organization','login')` [1](#0-0) [2](#0-1) . `Shipit.github(organization:)` resolves per-organization config from `secrets.github[org]`, and in the documented multi-app schema each organization has its own independently-configured `webhook_secret` [3](#0-2) [4](#0-3) . An org admin who set up their own GitHub App integration for their own (unprivileged) organization legitimately knows that org's `webhook_secret`, and thus can produce a validly-signed request whose body content (`organization.login`, `team`, `member`) is entirely attacker-chosen.
- `MembershipHandler#process` then does: `team = find_or_create_team!; member = User.find_or_create_by_login!(params.member.login)` and, for `action == 'added'`, `team.add_member(member)` [5](#0-4) .
- `find_or_create_team!` looks the team up **only** by `github_id: params.team.id`; the `organization` value from the payload is written **only inside the create block**, i.e. it is never checked against an already-existing `Team` row [6](#0-5) .
- `User.find_or_create_by_login!` fetches the attacker's real (public) GitHub profile using the *default* app client `Shipit.github.api.user(login)` to populate name/avatar — it performs no membership check whatsoever [7](#0-6) .
- `Team#add_member` unconditionally appends the member to the found `Team`'s membership association [8](#0-7) .
- Authorization teams are the ones lazily created from the default org's `oauth.teams` config: `Shipit.github_teams` calls `github.oauth_teams.map { |t| Team.find_or_create_by_handle(t) }` [9](#0-8) , and `User#authorized?` checks `teams.where(id: Shipit.github_teams.map(&:id)).exists?` [10](#0-9) . Once such a `Team` row exists (has a real `github_id`), any subsequent `membership` webhook referencing that same `github_id` — regardless of which organization actually signed it — matches it via `find_or_create_by!(github_id: ...)`.

Attacker's exact request: POST `/webhooks` with header `X-Github-Event: membership`, `X-Hub-Signature` computed with the secret of the attacker's own configured organization, and JSON body `{"action":"added","organization":{"login":"attacker-org"},"team":{"id":<privileged_team_github_id>,"name":"...","slug":"...","url":"..."},"member":{"login":"attacker-login"}}`.

Existing guards do not stop this: `verify_signature` only proves the request was signed by *some* configured organization's secret — it does not prove that the `team`/`member` fields it authorizes belong to that same organization [11](#0-10) . `ExplicitParameters` schema for `MembershipHandler` only validates types/presence, not cross-field organizational consistency [12](#0-11) . `require_permission!`/`force_github_authentication` are irrelevant here since `/webhooks` is unauthenticated by design.

### Impact Explanation
A single forged webhook lets the attacker (who only administers their own unprivileged organization within a shared multi-org Shipit deployment) insert an arbitrary GitHub login — their own account — into any `Shipit::Team` row that already exists in the database, including teams referenced by `Shipit.github_teams` for authorization. This flips `User#authorized?` to `true` for that identity, granting them Shipit login/UI access and any privileges gated behind team membership, without ever being added to the real GitHub team. The action is repeatable against any existing team `github_id` known to the attacker and is not confined to the attacker's own tenant, so it can cross tenant boundaries in a shared Shipit install — matching the "escalation into `Shipit.github_teams` authorization" High-severity category.

### Likelihood Explanation
Requires: (1) Shipit configured in the documented multi-organization mode with the attacker administering one of the configured (even low-privilege) organizations, thereby legitimately knowing that organization's own `webhook_secret`; (2) the attacker knowing/guessing the numeric `github_id` of a privileged team that already exists as a `Shipit::Team` row (e.g. from prior sync, GitHub team API responses visible to org members, or `lib/tasks/teams.rake`-driven refreshes). Given these two realistic preconditions for a shared multi-tenant Shipit deployment, the attack costs only crafting and POSTing one JSON body with a correctly computed HMAC using a secret the attacker already possesses — no session, no private key, no TLS interception needed.

### Recommendation
In `MembershipHandler#find_or_create_team!`, scope the lookup by both `github_id` and `organization` (derived from the *authenticated* organization used to verify the signature, not from the request body), and reject/ignore membership events whose `params.organization.login` does not match the `Team#organization` of an already-existing row with that `github_id`. Additionally, pass the organization that was cryptographically verified in `WebhooksController#verify_signature` down to the handler instead of re-deriving it from the untrusted payload inside the handler.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (conceptual addition)
test ":membership forged from a different org's secret cannot add a member to another org's team" do
  # Existing privileged team, real github_id, belongs to "shopify"
  privileged_team = shipit_teams(:shopify_developers)

  @request.headers['X-Github-Event'] = 'membership'
  body = {
    action: 'added',
    organization: { login: 'attacker-org' },       # attacker's own org
    team: { id: privileged_team.github_id, name: privileged_team.name,
            slug: privileged_team.slug, url: privileged_team.api_url },
    member: { login: 'attacker-login' }
  }.to_json

  # Signed with attacker-org's OWN legitimately-known webhook_secret
  signature = 'sha1=' + OpenSSL::HMAC.hexdigest('sha1', 'attacker-org-secret', body)
  @request.headers['X-Hub-Signature'] = signature
  Shipit.stubs(:github).with(organization: 'attacker-org').returns(attacker_org_github_app_stub)
  Shipit.github.api.stubs(:user).with('attacker-login').returns(stub(login: 'attacker-login', id: 999, name: 'x', email: 'x@x.com', avatar_url: 'x', url: 'x'))

  assert_no_difference -> { Shipit::Team.count } do
    post :create, body:, as: :json
  end
  assert_response :ok

  attacker = Shipit::User.find_by(login: 'attacker-login')
  Shipit.stubs(:github_teams).returns([privileged_team])
  assert attacker.teams.include?(privileged_team)   # LHS: team the forged webhook granted
  assert_predicate attacker, :authorized?            # RHS should be false, but is true — binding broken
end
```
Both sides of the equality — "team GitHub reports `attacker-login` as belonging to" vs. "team Shipit recorded `attacker-login` as belonging to" — diverge: the assertion `attacker.teams.include?(privileged_team)` passes even though the attacker was never added to that team on GitHub, proving the vulnerability.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
