### Title
Webhook signature verification binds to `repository.owner.login`, but every event handler acts on `repository.full_name` — an attacker who controls one configured GitHub organization can forge signed events against a victim repository - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App / `webhook_secret` to validate the HMAC signature against using `repository.owner.login` (or `organization.login`) from the JSON body, but every webhook `Handler` subsequently resolves the target `Repository`/`Stack` using the independent `repository.full_name` field from the same body. Because Shipit supports multi-tenant configuration (a distinct `webhook_secret` per GitHub organization), an attacker who legitimately owns one configured organization's GitHub App can produce a validly-signed webhook whose `repository.owner.login` matches their own org (so the signature check passes with a secret they know) while `repository.full_name` points at a repository belonging to a different, victim organization that is also configured in the same Shipit instance.

### Finding Description
`WebhooksController#verify_signature` picks the GitHub App/organization used for HMAC verification purely from `repository.owner.login`: [1](#0-0) [2](#0-1) 

`Shipit.github(organization:)` looks up a `GithubApp` instance configured per-organization, each with its own independently-provisioned `webhook_secret`: [3](#0-2) [4](#0-3) 

This is documented/supported as a first-class multi-org configuration in `docs/setup.md`/example secrets files, where each organization has a distinct `webhook_secret`: [5](#0-4) 

Once the signature check passes, `WebhooksController#create` dispatches the raw, already-parsed `params` hash — including the untouched `repository.full_name` field — to the event handler: [6](#0-5) 

Every handler (the base `Handler` class and all subclasses such as `PushHandler`, `StatusHandler`, the `PullRequest::*` handlers) resolves the `Repository`/`Stack` to act on using `repository.full_name`, a completely different field of the same payload that was never covered by the signature-selection logic (the signature only proves the payload was signed by *some* org's secret, not that `full_name` belongs to that org): [7](#0-6) [8](#0-7) 

Test fixtures confirm `repository.owner.login` and the commit/sha targeted by a `status` event are supplied independently in the payload (`repository_params` overrides only the owner, while `sha`/`state` target an arbitrary existing commit): [9](#0-8) 

**Binding broken (as an equality):**
`organization authenticated by HMAC (repository.owner.login)` ≠ `repository/stack actually mutated (repository.full_name)`.

Before the attack: an org's webhook secret can only be used to forge events that Shipit will interpret as belonging to that same org's repositories (implicit assumption). After the attack: an attacker holding one org's `webhook_secret` (because they are a legitimate installer/admin of that org's GitHub App) can sign a payload with `repository.owner.login` set to their own org while setting `repository.full_name` to `victim-org/victim-repo`, causing `verify_signature` to pass and the handler to mutate the victim's `Stack`.

### Impact Explanation
Concretely, via the `status` webhook handler, the attacker can inject a fabricated `state: "success"` `Status` for an arbitrary SHA on a victim's tracked repository. `Commit#deployable?` treats a commit as deployable once its aggregated status is `success` (and required contexts, defined by `ci.require` in `shipit.yml`, are present): [10](#0-9) [11](#0-10) 

This lets a cross-tenant attacker mark a commit that never actually passed CI as deployable, which can drive continuous-deployment (`Stack.schedule_continuous_delivery`) into shipping an unreviewed/unvetted commit to production — an unauthorized deploy. Other handlers reachable the same way (`PushHandler`, `PullRequest` opened/closed/labeled handlers, `CheckSuiteHandler`) similarly let the attacker trigger `GithubSyncJob`s, archive/unarchive review stacks, or refresh check runs for a repository/org they do not own.

### Likelihood Explanation
This requires the attacker to be a legitimate operator of at least one GitHub organization that is configured in the same multi-tenant Shipit instance as the victim (i.e., they know their own org's `webhook_secret`, which Shipit's own setup docs treat as attacker-controllable/self-provisioned). No access to the victim's secret, session, or `ApiClient` token is needed — only the ability to send an HTTP POST to `/webhooks` with a validly-signed-for-their-own-org body whose `repository.full_name` is spoofed to the victim's repository. This is realistic for any Shipit deployment serving multiple GitHub organizations (explicitly supported, per `config/secrets.development.shopify.yml`).

### Recommendation
After signature verification, cross-check that the organization whose secret validated the signature (`repository_owner`) matches the owner encoded in `repository.full_name` (and any other repository identifier used later, e.g., `organization.login` for membership events) before dispatching to handlers; reject the webhook otherwise. Alternatively, derive the target repository exclusively from the same field that was authenticated, rather than trusting a second, unauthenticated field deeper in the payload.

### Proof of Concept
1. Configure Shipit with two organizations, `attacker-org` and `victim-org`, each with its own `webhook_secret` (as in `config/secrets.development.shopify.yml`). Attacker legitimately controls `attacker-org`'s GitHub App and therefore knows `attacker-org`'s `webhook_secret`.
2. Attacker crafts a `status` event JSON body:
```json
{
  "sha": "<victim-commit-sha>",
  "state": "success",
  "target_url": "https://ci.example.com/fake",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" }
}
```
3. Attacker computes `X-Hub-Signature` using `attacker-org`'s `webhook_secret` over this exact body (as `Hook::DeliverySigner`/`verify_webhook_signature` expects).
4. POST to `/webhooks` with header `X-Github-Event: status`.
5. `WebhooksController#verify_signature` calls `Shipit.github(organization: "attacker-org")` and validates successfully against the attacker's own secret.
6. `StatusHandler` (dispatched via `Shipit::Webhooks.for_event`) resolves the target repository/commit via `repository.full_name` = `"victim-org/victim-repo"`, and records a fabricated successful `Status` on the victim's commit, potentially making it `deployable?` and eligible for continuous deployment despite never having passed real CI.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
    end
  end
end
