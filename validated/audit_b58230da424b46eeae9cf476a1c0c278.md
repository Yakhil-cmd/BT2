### Title
Webhook signature verification is keyed by an attacker-controlled `repository.owner.login`, but the write action operates on an independently-controlled `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/webhook secret to authenticate a request with based on `params.dig('repository', 'owner', 'login')` (or `organization.login`), while `Shipit::Webhooks::Handlers::Handler#repository_name` (used by every handler, e.g. `PushHandler`, `PullRequest::ClosedHandler`) independently reads `payload.dig('repository', 'full_name')` to decide which `Stack`/`Repository` to act on. Both values come from the same attacker-supplied JSON body and are never cross-checked against each other.

### Finding Description [1](#0-0) 

`verify_signature` computes `repository_owner` from the payload and uses it to pick a `GithubApp` instance: [2](#0-1) 

That `GithubApp` instance's secret is used to validate the HMAC over the raw body: [3](#0-2) 

Note `return true unless webhook_secret` - if the org selected by `repository_owner` has **no** `webhook_secret` configured, verification is skipped unconditionally, regardless of the request's actual content. Shipit explicitly supports multiple GitHub Apps/organizations, each configured independently with an optional `webhook_secret`: [4](#0-3) [5](#0-4) 

The documentation itself marks `webhook_secret` as optional ("Webhook secret (optional): Fill it with some randomly generated string"), and the shipped example config ships with it left blank: [6](#0-5) 

After (or regardless of) this "verification," `WebhooksController#create` dispatches the full raw payload to handlers: [7](#0-6) 

Every handler resolves the target repository/stacks from a *different* field of the same payload: [8](#0-7) [9](#0-8) 

Because `repository_owner` (used to pick the authenticating secret) and `repository.full_name` (used to pick the acted-upon repository) are read independently from attacker-controlled JSON with no cross-validation, an attacker can:
1. Set `repository.owner.login` / `organization.login` to any organization configured in Shipit's multi-org `github:` config that has no `webhook_secret` set (a documented, supported configuration) - this causes `verify_webhook_signature` to return `true` for free, with **no secret and no signature required at all**.
2. Set `repository.full_name` (and other handler-required fields such as `ref`, `after`, `pull_request`, `sender`, `team`, `member`) to point at a *completely different, properly-secured* organization/repository that is genuinely deployed via Shipit.

The signature check "authenticates" the wrong binding: it authenticates *an organization identity chosen by the attacker*, not *the repository that ends up being written to*. This is structurally the same class of bug as the reported `TimelockController` issue: a verification step whose scope (which secret/role applies) is computed from data that is disjoint from the data that is actually acted upon, letting an unprivileged caller satisfy the check on a cheap/free path while causing effects on a privileged path.

### Impact Explanation
With zero credentials, an attacker can forge `push`, `status`, `check_suite`, `membership`, and `pull_request` webhook events for any stack/repository configured under any *other*, secured GitHub organization in a multi-org Shipit deployment, as long as at least one configured organization has no `webhook_secret` set. Concretely this allows:
- Forcing `GithubSyncJob` to run for arbitrary stacks via `PushHandler`, injecting an attacker-chosen `expected_head_sha`/commit sync trigger [10](#0-9) , which can trigger downstream deploy-pipeline behavior (`sync_github`, spec caching, continuous delivery scheduling) on repositories the attacker has no access to.
- Forging arbitrary commit `status` events, affecting CI-gating logic used to permit/deny deploys [11](#0-10) .
- Archiving/altering review stacks tied to pull requests on repositories under a different organization [12](#0-11) .
- Creating/removing `Team`/`Membership` records used for authorization (`Shipit.github_teams`), as shown by the test suite's own membership handler behavior.

This falls under "unauthorized deploy/rollback" and "escalation into `Shipit.github_teams` authorization" impact categories, and crosses a repository/organization trust boundary without any credential.

### Likelihood Explanation
Requires: (a) a multi-org `github:` configuration (a documented, supported Shipit deployment mode), and (b) at least one configured organization lacking a `webhook_secret` (explicitly documented as optional, and shipped as blank in example configs). Given these preconditions - which are realistic for organizations onboarding additional GitHub orgs incrementally, or leaving a secret blank as the docs suggest is acceptable - the attack requires no authentication, no token, and no prior access; it is a single crafted HTTP POST to the public `/webhooks` endpoint.

### Recommendation
- Bind webhook signature verification to the exact repository/organization the handler will act on: derive `repository_owner` and the handler's `repository_name`/target from the same, single authoritative field, and reject payloads where `repository.owner.login` does not match the owner segment of `repository.full_name`.
- Do not allow `verify_webhook_signature` to silently pass (`return true unless webhook_secret`) for any organization in a multi-org configuration; require a `webhook_secret` for all configured organizations, or fail closed when one is missing rather than treating it as "trusted by default."
- Consider verifying the signature using a single, deployment-wide default secret when in doubt, or explicitly validate that the resolved `GithubApp`'s organization matches the repository actually targeted by every handler before processing.

### Proof of Concept
Preconditions: Shipit configured with multi-org `github:` schema, e.g. `OrgA` (attacker knows/no secret configured) and `OrgB` (secured, has a real Shipit stack `OrgB/prod-app`).

```
POST /webhooks HTTP/1.1
X-Github-Event: push
Content-Type: application/json
(no X-Hub-Signature header needed if OrgA has no webhook_secret)

{
  "ref": "refs/heads/main",
  "after": "deadbeefdeadbeefdeadbeefdeadbeefdeadbeef",
  "repository": {
    "owner": { "login": "OrgA" },
    "full_name": "OrgB/prod-app"
  }
}
```

`WebhooksController#verify_signature` resolves `Shipit.github(organization: "OrgA")`; since `OrgA` has no `webhook_secret`, `verify_webhook_signature` returns `true` unconditionally, allowing the request through with no valid signature. `PushHandler#process` then calls `Repository.from_github_repo_name("OrgB/prod-app")` and enqueues `GithubSyncJob` for `OrgB`'s real, secured stack - despite the request never being authenticated for `OrgB`.

Note: I was not able to fully trace `Stack#sync_github`'s exact downstream deploy-triggering behavior in this session (only its callers were located), so the precise extent of automatic deploy triggering versus commit-sync-only behavior should be confirmed by a background agent with full file access.

      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

### Using Multiple Github Applications

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently. The top-level keys should be the name of each Github organization, and the following sub-keys are the Github app details for that particular organization.

For example:

```yml
production:
  github:
    somegithuborg:
      app_id:
      installation_id:
      webhook_secret:
      private_key:
      oauth:
        id:
        secret:
        teams:
    someothergithuborg:
      app_id:
      installation_id:
      webhook_secret:
      private_key:
      oauth:
        id:
        secret:
        teams:
```
