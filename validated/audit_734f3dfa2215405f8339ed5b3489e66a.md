### Title
Intra-transaction balance visibility across chained AAs enables flash-loan-style manipulation of vault-style AAs - (File: formula/evaluation.js, aa_composer.js)

### Summary
BT.Finance was drained because its strategies could be manipulated atomically within a single flash-loaned transaction: state (price/share ratio) was read and acted upon before it reflected the "true", externally-verifiable value. The ocore analog is that `balance[address][asset]` (and `var[address][name]`) reads performed by one AA can observe balance/state mutations already committed *within the same still-open database transaction* by another AA earlier in the same primary-trigger cascade, because the entire chain of primary + secondary AA triggers spawned from a single posted unit runs inside one `BEGIN…COMMIT` block on one connection.

### Finding Description
A single unit posted by an unprivileged trigger sender can pay bytes/assets to AA `A`, and `A`'s response can pay onward to AA `B` (a secondary trigger), all processed atomically inside `handlePrimaryAATrigger` under one `conn`/transaction: [1](#0-0) 

`updateFinalAABalances` writes the new balance for an AA immediately into `aa_balances` on the shared connection as soon as its response unit is produced, before the top-level transaction commits: [2](#0-1) 

Any AA in the same chain (including `B`, triggered right after via `handleSecondaryTriggers`) can then read another address's *current* balance with the `balance[...]` operator. If that balance isn't already cached in the per-call `objValidationState.assocBalances`, it is fetched with a live SQL query on the same connection, which — being in the same uncommitted transaction — sees the just-written intermediate value rather than a pre-transaction snapshot: [3](#0-2) 

The secondary-trigger cascade that produces this ordering is: [4](#0-3) 

This is precisely the primitive behind flash-loan price/TVL manipulation: an attacker's single posted unit can (1) inflate/deflate an AA's `balance[]`-visible state via a first hop, then (2) immediately have a chained AA compute a payout/ratio using that manipulated, not-yet-finalized balance, then (3) unwind — all before any other unit/user can observe or react, and all guaranteed atomic because the whole cascade commits or rolls back together (`revert`/`ROLLBACK TO SAVEPOINT`): [5](#0-4) 

Sample AA patterns already present in the codebase compute payouts directly from another AA's live `balance[$destination_aa][base]`, illustrating the exact vulnerable pattern an ordinary AA author would write: [6](#0-5) 

### Impact Explanation
Any vault/aggregator-style AA that reads another AA's `balance[]` (or state `var[]`) to price shares, compute a payout, or gate an action can be manipulated within one atomic multi-hop trigger unit sent by a single unprivileged trigger sender — no separate blocks, confirmations, or cooperating counterparties are required, mirroring the atomicity that makes flash-loan attacks possible in EVM DeFi. This can result in AA fund loss/drain (a vault paying out more than it should based on a manipulated intra-transaction balance) — a concrete "AA fund loss" impact per the validation criteria.

### Likelihood Explanation
Medium. Exploitation requires an AA author to have written a contract whose logic reads a counterparty/vault AA's live `balance[]`/`var[]` inside the same trigger cascade to compute payouts (a documented, encouraged composability pattern, as shown by the shipped sample AAs `fundraising_proxy.oscript` and `order_book_exchange.oscript`). The underlying mechanism (shared open transaction across the whole cascade) is unconditionally present for any unprivileged trigger sender who can construct a multi-hop AA chain in one unit.

### Recommendation
- Document explicitly (and, where feasible, enforce) that `balance[]`/`var[]` reads of a *different* AA address inside the same trigger cascade may reflect not-yet-finalized, intra-transaction state, and are unsafe as a sole basis for computing payouts/ratios.
- Consider providing a "snapshot" balance/state read primitive that reflects only the last *stable* (pre-trigger) values for cross-AA reads, distinct from the live in-cascade values, so AA authors can opt into either semantic explicitly.
- Add complexity/audit tooling warnings when an AA formula reads `balance[X]`/`var[X]` for a non-`this_address` `X` and uses it in a payment/asset-issuance amount expression, since this is the pattern most exposed to the flash-loan-style analog described here.

### Proof of Concept
Conceptual reproduction (cannot be fully executed without deploying two live AAs, but the mechanism is directly traceable in code):
1. Deploy AA `V` (a naive vault) whose payout formula uses `balance[V][asset]` read via a secondary trigger from AA `P` in the same chain, e.g. modeled on `test/samples/fundraising_proxy.oscript` lines 44-53, computing `$missing_amount` from `balance[$destination_aa][base]`.
2. Attacker posts a single unit that pays to AA `P`; `P`'s response pays into `V`, inflating `V`'s `aa_balances.balance` via `updateFinalAABalances` (`aa_composer.js:543-587`) before the top-level transaction commits.
3. A further chained secondary trigger (or `P` itself, before finishing) reads `balance[V][asset]` (`formula/evaluation.js:1510-1528`), observing the inflated value from step 2 within the same open transaction, and computes/authorizes a payout based on it.
4. Because the whole cascade is atomic (`handleSecondaryTriggers`, `aa_composer.js:1702-1741`) and reversible only as a whole (`revert`, `aa_composer.js:1759-1783`), the attacker can structure the sequence so that if the exploit condition isn't met the whole unit safely bounces with no cost, while a successful construction drains `V` in a single unit — the same all-or-nothing, single-transaction economics that made the BT.Finance flash-loan drain possible.
