### Title
Multisig transaction approvals are validated against the *current* `num_signatures_required` instead of the threshold in effect when they were created, allowing stale/under-approved transactions to execute after a threshold reduction - (File: `aptos-move/framework/aptos-framework/sources/multisig_account.move`)

### Summary
This is the closest Aptos-native analog to the OZ `GovernorVotesQuorumFraction` bug: quorum/threshold parameters that are mutable and read live at execution time, rather than snapshotted per-proposal, so a threshold change retroactively changes what counts as "enough approval" for transactions that were created and voted on under a different (higher) threshold.

### Finding Description
`MultisigAccount.num_signatures_required` is a single mutable field, updatable via `update_signatures_required` [1](#0-0) . Pending `MultisigTransaction`s only store `votes`, `creator`, and `creation_time_secs` [2](#0-1)  - there is no snapshot of the threshold that applied when the transaction was proposed or approved.

Both `can_execute` (view function) and the VM-invoked `validate_multisig_transaction` (called during mempool admission and again during execution prologue) compute the approval count for a pending transaction and compare it to `num_signatures_required(multisig_account)`, which reads the account's *current* field value: [3](#0-2) [4](#0-3) 

Because Aptos multisig transactions must execute strictly in order (`sequence_number == last_resolved_sequence_number(multisig_account) + 1`), a transaction that was proposed and received some approvals under an old (higher) threshold, but not yet executed, becomes admissible with only its old vote count once an *earlier* transaction lowers the threshold and is executed. No re-approval by owners is required for the pending transaction to reflect the new, weaker threshold - the "approval set" originally required is silently redefined between proposal time and admission time.

### Impact Explanation
This is the same bug class as the OZ Governor issue: a quorum/threshold parameter mutated after a proposal was created is applied retroactively to that pending proposal, so it can execute with fewer approvals than the owners who voted on it believed were required. In the multisig case this means a transaction (e.g., a funds transfer) that only ever received, say, 1-of-3 approvals under the account's original 3-of-3 policy can suddenly execute with just that 1 approval once the threshold is lowered by a separate, unrelated transaction — without the remaining owners ever being asked to reconsider that specific pending transaction. This is exactly the "approval validation accepting the wrong approval set" pattern the admission gate targets.

### Likelihood Explanation
Exploitation requires that the account's owners (or a colluding subset with enough votes) execute a threshold-lowering transaction while an older, under-approved transaction is still pending in the queue — i.e., it depends on a privileged, in-band multisig governance action (`update_signatures_required`) rather than an unprivileged external attacker. This substantially limits the likelihood and blast radius: the same set of owners capable of lowering the threshold could, in most cases, alternatively just approve a new malicious transaction outright. The realistic risk scenario is unintentional: owners forget about an old low-approval proposal, later legitimately lower the threshold for unrelated reasons (e.g., losing a key), and the stale proposal becomes executable without further owner consent.

### Recommendation
Snapshot `num_signatures_required` (and any other threshold-relevant configuration) into the `MultisigTransaction` at creation time (`create_transaction` / `create_transaction_with_hash`), and use that stored value in `can_execute`, `can_be_executed`, `can_reject`, `can_be_rejected`, and `validate_multisig_transaction` instead of re-reading the live account threshold. Alternatively, invalidate/require re-approval of all pending transactions whenever `num_signatures_required` changes.

### Proof of Concept
1. Create a 3-of-3 multisig account with owners A, B, C.
2. Owner A creates transaction #1 (malicious transfer). Only A has approved (auto-vote on creation).
3. Owner A creates transaction #2: `update_signatures_required(1)`. Owners A, B, C all approve #2 (3-of-3, satisfying the current policy).
4. Transaction #2 executes (in order, since it's `last_resolved_sequence_number + 1`), setting `num_signatures_required = 1`.
5. Owner A now calls `validate_multisig_transaction` / executes transaction #1. `num_signatures_required(multisig_account)` now returns `1`, and #1's existing single approval (from A) satisfies `num_approvals >= num_signatures_required` at line 1353, so #1 executes despite having only ever received 1-of-3 approvals under the account's original 3-of-3 policy.

Note: I was unable to find any snapshot/versioning mechanism protecting against this in the reviewed portions of `multisig_account.move`; this analysis is based on the code sections cited above and standard multisig test coverage in `multisig_transactions_test.rs`, which only exercises the "raise/lower threshold with sufficient current approvals" case, not the retroactive-application-to-other-pending-transactions scenario described here.

    /// Return true if the owner can execute the transaction with given transaction id now.
    public fun can_execute(owner: address, multisig_account: address, sequence_number: u64): bool {
        assert_valid_sequence_number(multisig_account, sequence_number);
        let (num_approvals, _) = num_approvals_and_rejections(multisig_account, sequence_number);
        if (!has_voted_for_approval(multisig_account, sequence_number, owner)) {
            num_approvals += 1;
        };

        is_owner(owner, multisig_account) &&
            sequence_number == last_resolved_sequence_number(multisig_account) + 1 &&
            num_approvals >= num_signatures_required(multisig_account) && can_execute_with_timelock(multisig_account, sequence_number, num_approvals)
    }

    fun validate_multisig_transaction(
        owner: &signer, multisig_account: address, payload: vector<u8>) {
        assert_multisig_account_exists(multisig_account);
        assert_is_owner(owner, multisig_account);
        let sequence_number = last_resolved_sequence_number(multisig_account) + 1;
        assert_transaction_exists(multisig_account, sequence_number);

        if (features::multisig_v2_enhancement_feature_enabled()) {
            assert!(
                can_execute(address_of(owner), multisig_account, sequence_number),
                error::invalid_argument(ENOT_ENOUGH_APPROVALS),
            );
        }
        else {
            assert!(
                can_be_executed(multisig_account, sequence_number),
                error::invalid_argument(ENOT_ENOUGH_APPROVALS),
            );
        };

        // Count approvals, including the executing owner's implicit vote.
        let (num_approvals, _) = num_approvals_and_rejections(multisig_account, sequence_number);
        if (!has_voted_for_approval(multisig_account, sequence_number, address_of(owner))) {
            num_approvals += 1;
        };
        assert!(num_approvals >= num_signatures_required(multisig_account), error::invalid_argument(ENOT_ENOUGH_APPROVALS));
