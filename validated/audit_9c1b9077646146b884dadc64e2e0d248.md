### Title
Unauthenticated P2P `ServiceChainResponse` Injection Allows Fake `RequestValueTransfer` Log Delivery, Triggering Unauthorized Token Minting on Child Chain — (`node/sc/sub_bridge_handler.go`)

---

### Summary

The SubBridge's `HandleMainMsg` function writes raw bytes from any connected P2P peer's `ServiceChainResponse` message directly into the RPC pipe that feeds the `RemoteBackend`'s `rpcClient`. Because the parent bridge contract subscription uses `SubscribeFilterLogs` over this same pipe, a malicious peer that controls the pipe's response stream can inject a crafted JSON-RPC subscription notification carrying a fake `RequestValueTransfer` log. The SubBridge processes it as a legitimate event and calls `HandleERC20Transfer` / `HandleKLAYTransfer` on the child bridge contract using the legitimate bridge operator account, minting or transferring tokens to an attacker-controlled address.

---

### Finding Description

**Step 1 — The RPC pipe architecture**

`NewRpcClientP2P` creates a `net.Pipe()`. One end (`p1`) is stored as `sb.rpcConn`; the other (`p2`) becomes the codec for the `rpc.Client`. [1](#0-0) 

Outbound RPC requests flow: `rpcClient` → `p2` → `p1` → `SetRPCConn` goroutine → `rpcSendCh` → `SendRPCData` → P2P `ServiceChainCall`.

Inbound RPC responses flow: P2P `ServiceChainResponse` → `HandleMainMsg` → `rpcConn.Write(data)` → `p1` → `p2` → `rpcClient`.

**Step 2 — No peer authentication on `ServiceChainResponse`**

`HandleMainMsg` writes the raw P2P payload from **any** connected peer directly to `rpcConn` with zero validation: [2](#0-1) 

There is no check that the responding peer is the same peer that received the original request, no HMAC, no sequence number, and no source-address binding.

**Step 3 — Parent bridge subscription uses the P2P pipe**

When a bridge pair is restored or subscribed, the parent bridge object is created with `remoteBackend`: [3](#0-2) 

`subscribeEvent` then calls `bridge.WatchRequestValueTransfer`, which internally calls `SubscribeFilterLogs`: [4](#0-3) 

This sends a `kaia_subscribe` JSON-RPC request through the P2P pipe. The peer that receives it assigns the subscription ID and controls all subsequent notifications on that ID.

**Step 4 — Fake log is unpacked and queued**

The generated binding's `WatchRequestValueTransfer` loop calls `UnpackLog` on every `types.Log` delivered by the subscription channel. The attacker crafts a log with:
- `Address` = legitimate parent bridge contract address (public)
- `Topics[0]` = `RequestValueTransfer` event topic (`0xeff76c36e53fa5ff52f27acc8a34d5047a8246abb07b77b12f1309f71e337f09`)
- ABI-encoded data with attacker-controlled `to`, `value`, and a fresh `requestNonce` [5](#0-4) 

`ProcessRequestEvent` checks only that `ev.GetRaw().Address` has a registered counterpart bridge — which the attacker satisfies by using the real parent bridge address: [6](#0-5) 

**Step 5 — `handleRequestValueTransferEvent` calls the child bridge**

The event is added to `pendingRequestEvent` and processed: [7](#0-6) 

For ERC20, this calls `bi.bridge.HandleERC20Transfer(auth, txHash, from, to, ctpartTokenAddr, valueOrTokenId, requestNonce, blkNumber, extraData)` where `auth` is the legitimate bridge operator account.

**Step 6 — Child bridge contract executes the mint**

`handleERC20Transfer` has `onlyOperators` — but the caller IS the registered bridge operator. With the default threshold of 1, a single operator vote suffices: [8](#0-7) [9](#0-8) 

The contract mints `valueOrTokenId` tokens to the attacker-controlled `_to` address.

---

### Impact Explanation

A malicious P2P peer that controls the `ServiceChainResponse` stream can cause the SubBridge to mint or transfer arbitrary amounts of ERC20, ERC721, or KAIA tokens on the child chain to any address. The child bridge contract's `onlyOperators` guard is bypassed in effect because the SubBridge's own operator account is the caller — the attacker only needs to control the *parameters* passed to it, which come entirely from the injected fake log.

---

### Likelihood Explanation

The SubBridge's P2P port is publicly reachable. The only peer admission check is chainID equality, which is public information: [10](#0-9) 

An attacker who connects before the legitimate MainBridge (or who is the sole peer) receives the `kaia_subscribe` request and controls the subscription ID. Even as a second peer, subscription IDs in the Kaia RPC client are sequential and guessable. The `SendRPCData` function also returns after the first peer, so a race to connect first is winnable.

---

### Recommendation

1. **Authenticate the RPC response source**: Track which peer sent each `ServiceChainCall` request (by request ID) and only accept `ServiceChainResponse` data from that same peer.
2. **Validate log origin**: After receiving a log via `SubscribeFilterLogs`, verify that `log.Address` matches the expected parent bridge contract address *and* that the log's block hash / transaction hash exists on the canonical parent chain (via a separate authenticated call).
3. **Restrict peer admission**: Require cryptographic authentication (e.g., TLS or a shared secret) for bridge P2P peers, not just chainID matching.
4. **Enforce operator threshold > 1**: Require at least 2 independent operator signatures for value transfers, so a single compromised event source cannot unilaterally execute a transfer.

---

### Proof of Concept

```
1. Deploy a child chain with a SubBridge configured to connect to a "parent" node.
2. Run a malicious node that:
   a. Accepts the SubBridge's P2P connection (presents the correct parentChainID).
   b. Receives the kaia_subscribe JSON-RPC request forwarded via ServiceChainCall.
   c. Responds with subscription ID "0x1" via ServiceChainResponse.
3. After the subscription is established, send a ServiceChainResponse containing:
   {
     "jsonrpc":"2.0",
     "method":"kaia_subscription",
     "params":{
       "subscription":"0x1",
       "result":{
         "address":"<parent_bridge_addr>",
         "topics":["0xeff76c36e53fa5ff52f27acc8a34d5047a8246abb07b77b12f1309f71e337f09",
                   "<from_indexed>","<attacker_addr_indexed>","<token_addr_indexed>"],
         "data":"<abi_encoded: tokenType=ERC20, value=1000000, requestNonce=999, fee=0, extraData=0x>",
         "blockNumber":"0x1","transactionHash":"<fresh_hash>","logIndex":"0x0"
       }
     }
   }
4. Observe that the SubBridge calls HandleERC20Transfer on the child bridge contract
   with _to = attacker address and _value = 1000000, minting tokens to the attacker.
```

func (bi *BridgeInfo) handleRequestValueTransferEvent(ev IRequestValueTransferEvent) error {
	var (
		tokenType                         = ev.GetTokenType()
		tokenAddr, from, to, contractAddr = ev.GetTokenAddress(), ev.GetFrom(), ev.GetTo(), ev.GetRaw().Address
		txHash                            = ev.GetRaw().TxHash
		valueOrTokenId                    = ev.GetValueOrTokenId()
		requestNonce, blkNumber           = ev.GetRequestNonce(), ev.GetRaw().BlockNumber
		extraData                         = ev.GetExtraData()
	)

	ctpartTokenAddr := bi.GetCounterPartToken(tokenAddr)
	// TODO-Kaia-Servicechain Add counterpart token address in requestValueTransferEvent
	if tokenType != KAIA && ctpartTokenAddr == (common.Address{}) {
		logger.Warn("Unregistered counter part token address.", "addr", ctpartTokenAddr.Hex())
		ctTokenAddr, err := bi.counterpartBridge.RegisteredTokens(nil, tokenAddr)
		if err != nil {
			return err
		}
		if ctTokenAddr == (common.Address{}) {
			return errors.New("can't get counterpart token from bridge")
		}
		if err := bi.RegisterToken(tokenAddr, ctTokenAddr); err != nil {
			return err
		}
		ctpartTokenAddr = ctTokenAddr
		logger.Info("Register counter part token address.", "addr", ctpartTokenAddr.Hex(), "cpAddr", ctTokenAddr.Hex())
	}

	bridgeAcc := bi.account

	bridgeAcc.Lock()
	defer bridgeAcc.UnLock()

	auth := bridgeAcc.GenerateTransactOpts()

	var handleTx *types.Transaction
	var err error

	switch tokenType {
	case KAIA:
		handleTx, err = bi.bridge.HandleKLAYTransfer(auth, txHash, from, to, valueOrTokenId, requestNonce, blkNumber, extraData)
		if err != nil {
			return err
		}
		handleValueTransferLog(bi.onChildChain, handleVTmethods[KAIA], handleTx.Hash().String(), requestNonce, from, to, valueOrTokenId)
	case ERC20:
		handleTx, err = bi.bridge.HandleERC20Transfer(auth, txHash, from, to, ctpartTokenAddr, valueOrTokenId, requestNonce, blkNumber, extraData)
		if err != nil {
			return err
		}
		handleValueTransferLog(bi.onChildChain, handleVTmethods[ERC20], handleTx.Hash().String(), requestNonce, from, to, valueOrTokenId)
	case ERC721:
		uri := GetURI(ev)
		handleTx, err = bi.bridge.HandleERC721Transfer(auth, txHash, from, to, ctpartTokenAddr, valueOrTokenId, requestNonce, blkNumber, uri, extraData)
		if err != nil {
			return err
		}
		handleValueTransferLog(bi.onChildChain, handleVTmethods[ERC721], handleTx.Hash().String(), requestNonce, from, to, valueOrTokenId)
	default:
		logger.Error("Got Unknown Token Type ReceivedEvent", "bridge", contractAddr, "nonce", requestNonce, "from", from)
		return nil
	}

	bridgeAcc.IncNonce()

	bi.bridgeDB.WriteHandleTxHashFromRequestTxHash(txHash, handleTx.Hash())
	return nil

func (cce *ChildChainEventHandler) ProcessRequestEvent(ev IRequestValueTransferEvent) error {
	addr := ev.GetRaw().Address

	handleBridgeAddr := cce.subbridge.bridgeManager.GetCounterPartBridgeAddr(addr)
	if handleBridgeAddr == (common.Address{}) {
		return fmt.Errorf("there is no counter part bridge of the bridge(%v)", addr.String())
	}

	handleBridgeInfo, ok := cce.subbridge.bridgeManager.GetBridgeInfo(handleBridgeAddr)
	if !ok {
		return fmt.Errorf("there is no counter part bridge info(%v) of the bridge(%v)", handleBridgeAddr.String(), addr.String())
	}

	// TODO-Kaia need to manage the size limitation of pending event list.
	handleBridgeInfo.AddRequestValueTransferEvents([]IRequestValueTransferEvent{ev})
	return nil
