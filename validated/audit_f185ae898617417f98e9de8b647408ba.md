### Title
Cross-repository status forgery via unscoped SHA lookup in `StatusHandler#process` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` looks up commits by bare SHA across the entire `commits` table (`Commit.where(sha: params.sha)`) instead of scoping to the repository that authenticated the webhook, unlike other handlers that use the base `Handler#stacks` helper. Because `Commit#blocked?` and `Commit#deployable?` are computed from `stack.blocking_statuses`/`stack.commits`, a legitimately-signed `status` webhook from repository A can flip the CI state (and therefore `blocked?`/`deployable?`) of a commit belonging to an unrelated stack B, whenever both stacks happen to contain a `Commit` row with the same SHA.

### Finding Description
The broken binding is: **a `status` webhook authenticated for repository R should only ever update `Commit` rows belonging to stacks whose `Repository` equals R** — i.e. `commit.stack.repository == R` for every `commit` mutated by the handler. The code does not enforce this.

`StatusHandler#process` (app/models/shipit/webhooks/handlers/status_handler.rb:20-24):
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
This queries `Commit` globally by `sha` with no join/filter on `stack_id`/repository. Compare with the base `Handler` class (app/models/shipit/webhooks/handlers/handler.rb:32-38), which provides a `stacks` helper that scopes to `Repository.from_github_repo_name(repository_name)` — used by `check_suite_handler.rb`, `push_handler.rb`, and the `pull_request/*` handlers — but `StatusHandler` never calls it.

`WebhooksController#verify_signature` (app/controllers/shipit/webhooks_controller.rb:24-30) only validates that the payload's `X-Hub-Signature` matches the webhook secret configured for `repository_owner` (the *organization* in the payload), it never re-validates that the `sha`/commits touched by the handler belong to that same repository. So the signature check authenticates "this event really came from GitHub for organization/repo R," but the handler then acts on any `Commit` row anywhere in the database that shares the SHA.

`Commit#sha` is not unique per-repository at the DB level (no `add_index :commits, :sha, unique: true` was found), and `Commit#blocked?` (app/models/shipit/commit.rb:231-237) and `#deployable?` (:227-229) are derived from `stack.commits`/`stack.blocking_statuses`, i.e. purely from the local `Commit`/`Status` rows, not from any repository check. A forged/incidental `ci/test` `failure` status attached to a `Commit` row in stack B (whose SHA happens to equal one produced by real GitHub activity in repository A) will change `blocking?`/`blocked?` for that commit in stack B, gating or unblocking deploys there.

Exploit flow:
1. Attacker controls (or contributes CI activity to) a repository/stack A that is legitimately registered with Shipit (so GitHub will sign and deliver real `status` webhooks for it).
2. Victim stack B (different repository/org, blocking_statuses configured, e.g. requiring `ci/test`) independently contains a `Commit` row with the same `sha` as one in stack A — plausible via forks, mirrored repos, cherry-picks, or shared upstream history where the identical commit object (content-addressed by git) is tracked by two separate Shipit stacks.
3. Attacker triggers (or receives) a genuine, correctly-signed `status` webhook for repository A: `context: ci/test`, `state: failure`, for that shared `sha`.
4. `WebhooksController#verify_signature` accepts it (it's genuinely signed for org/repo A).
5. `StatusHandler#process` runs `Commit.where(sha: ...)`, which matches the row in stack B too, and calls `create_status_from_github!` on it, writing a `failure` status into stack B's status list.
6. `Commit#blocked?`/`#deployable?` for stack B recompute using this now-hostile status, potentially blocking (or, by a follow-up `success` status, unblocking) deploys in a stack that never received a webhook authenticated for it.

None of the existing guards prevent this: `verify_signature` authenticates the organization of the sender, not the ultimate write target; `drop_unhandled_event` only filters by event type; `ExplicitParameters` (`params do ... end` block) only validates payload shape, not scope; there is no `stacks`/repository filter applied in `StatusHandler#process` unlike sibling handlers.

### Impact Explanation
A webhook correctly authenticated for one repository can write `Status` rows against `Commit` records belonging to a completely different stack/repository/tenant, altering `blocked?`/`deployable?` and thus gating or forcing deploys, merges, or continuous-delivery scheduling (`Commit#schedule_continuous_delivery`, `stack.schedule_merges`) for a stack that never authorized the change. This matches the "Critical — payload for one repository mutating another's stack/commit" category. The blast radius is any Shipit stack that shares a `Commit.sha` value with another stack's repository history, which is realistic in fork/mirror/monorepo-split setups common to open-source projects using Shipit.

### Likelihood Explanation
Preconditions: (1) an existing Shipit stack B configured with `blocking_statuses` requiring `ci/test`; (2) some other Shipit-registered repository/stack A that independently shares a git commit SHA with B (via fork/mirror/shared history/cherry-pick) — a scenario plausible in real deployments tracking forks of the same open-source project or monorepo splits; (3) attacker able to cause/observe a real `status` event on repository A (e.g., by contributing a PR that triggers CI, no elevated Shipit privileges needed). The attacker never needs the webhook secret — GitHub itself signs the event for repo A. This is fully repeatable against any stack pair sharing SHAs, at zero cost beyond normal contribution activity.

### Recommendation
Scope `StatusHandler#process` to only the commits belonging to the repository/stack that authenticated the webhook, analogous to the `stacks` helper used by other handlers, e.g.:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
end
```
Additionally consider adding a composite uniqueness constraint or at least documenting/enforcing that `Commit` lookups by `sha` must always be joined against the repository derived from `payload['repository']['full_name']`.

### Proof of Concept
minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb`, illustrative):
```ruby
test "a status for repo A's SHA must not affect stack B's commit sharing the same SHA" do
  stack_a = shipit_stacks(:shipit) # repository "shopify/shipit-engine"
  stack_b = create_stack(repository: create_repository(owner: 'other-org', name: 'other-repo'))
  stack_b.update!(blocking_statuses: ['ci/test'])

  shared_sha = 'a' * 40
  commit_a = stack_a.commits.create!(sha: shared_sha, ...)
  commit_b = stack_b.commits.create!(sha: shared_sha, ...)

  # binding under test, BEFORE:
  assert_equal false, commit_b.reload.blocked?

  payload = {
    'sha' => shared_sha,
    'state' => 'failure',
    'context' => 'ci/test',
    'repository' => { 'full_name' => stack_a.repository.full_name, 'owner' => { 'login' => stack_a.repository.owner } },
  }
  Shipit::Webhooks::Handlers::StatusHandler.call(payload)

  # binding under test, AFTER: commit_b (unrelated repository) must remain unaffected
  assert_equal false, commit_b.reload.blocked?, "status webhook for repo A must not mutate stack B's commit"
end
```
With the current implementation this assertion fails: `commit_b.blocked?` flips to `true` (or its deployability changes) because `StatusHandler#process` matched `commit_b` via the unscoped `Commit.where(sha: ...)` query.
