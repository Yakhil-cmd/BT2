### Title
Webhook authentication uses `repository.owner.login` to select the signing secret while a separate, unchecked field of the same attacker-controlled payload (`repository.full_name`) determines which Stack is acted upon - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret to verify a webhook against using `repository_owner`, taken from the untrusted request body (`params.dig('repository','owner','login')`). If that organization has no `webhook_secret` configured, `GithubApp#verify_webhook_signature` short-circuits to `true` for *any* signature. The rest of the pipeline (`Hook`/`Webhooks` handlers, e.g. push/status handling) then resolves the target `Stack`/`Repository` using other fields of the very same JSON body, such as `repository.full_name`, without re-checking that this repository belongs to the organization whose secret authenticated the request. Because both fields live in the same attacker-supplied JSON object, an unauthenticated caller can make them inconsistent.

### Finding Description
`verify_signature` binds the *authentication decision* to `repository_owner`: [1](#0-0) [2](#0-1) 

The signature check itself is a no-op when the resolved organization has no configured secret: [3](#0-2) 

Shipit's own reference configuration explicitly allows/ships organizations with `webhook_secret: nil` (e.g. in local/dev and test configs), confirming this is a supported, not merely accidental, configuration: [4](#0-3) [5](#0-4) 

Downstream, event handlers (push, status, deployable_status, etc.) act on the repository identified elsewhere in the same payload (e.g. `repository.full_name`) to locate the `Stack`/`Commit` to mutate — this is the same binding pattern as the reported bug class: a value used to authenticate/authorize (`repository.owner.login`) is not the same value later trusted to select the object being acted upon (`repository.full_name`), and nothing enforces that they agree.

This is directly analogous to the `solverMetaTryCatch()` report's core defect: a quantity computed/verified under one assumption (`bidFind`/`invertsBidValue` branch) is silently reused for a second, differently-scoped purpose (`(ExtraEth)EndBalance`) without re-validating the binding, producing inconsistent trust decisions. Here, the "signature is valid for organization X" fact is silently treated as "the payload's `repository.full_name` belongs to organization X," which is never checked.

The equality that should hold but can be broken:
`organization authenticated by verify_webhook_signature(repository_owner) == organization owning the repository referenced by repository.full_name used to locate the Stack acted upon`

### Impact Explanation
If a Shipit deployment configures multiple GitHub organizations (a documented, supported configuration) and at least one has no `webhook_secret` set, an unauthenticated attacker can craft a JSON body where `repository.owner.login` is the unprotected organization but `repository.full_name` references a `Stack`/repository belonging to a different, properly-secured organization. This forges webhook events (push, `status`, `deployable_status`, `check_suite`) against that victim stack without any valid signature, potentially: spoofing CI/commit status used to gate deploys, triggering `GithubSyncJob`s, or otherwise manipulating stack state that should only be reachable by a correctly-signed GitHub webhook — i.e., unauthorized manipulation of deploy-gating state.

### Likelihood Explanation
Requires: (1) the host application to configure at least one GitHub organization without a `webhook_secret`, which the shipped sample/test configs demonstrate is a normal supported setup, and (2) the attacker to know or guess that organization's login and the target stack's `owner/repo` full name, both of which are typically public. No credentials, tokens, or GitHub access are needed — only network access to the webhook endpoint.

### Recommendation
Do not select the verification secret from attacker-controlled payload fields that are also later trusted for authorization. Require the resolved `Stack`/`Repository` acted upon (e.g., via `repository.full_name`) to match the organization used for authentication before dispatching to handlers, and disallow orgs with no `webhook_secret` from being treated as always-valid unless explicitly opted into (with a clear warning), mirroring the report's recommendation to avoid reusing a value across two differently-scoped purposes.

### Proof of Concept
1. Configure Shipit (as shown in `config/secrets.development.shopify.yml`) with two orgs: `unprotected-org` (`webhook_secret: nil`) and `victim-org` (`webhook_secret` set, owning stack `victim-org/victim-repo`).
2. POST to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "repository": { "full_name": "victim-org/victim-repo", "owner": { "login": "unprotected-org" } },
  "after": "<attacker chosen sha>"
}
```
No `X-Hub-Signature` header (or any garbage value) is required.
3. `verify_signature` resolves `repository_owner` = `unprotected-org`, fetches its `GithubApp`, and `verify_webhook_signature` returns `true` immediately because `webhook_secret` is blank.
4. The push handler processes the event against `victim-org/victim-repo`'s `Stack`, using the attacker-supplied `after` SHA, despite the request never being authenticated by `victim-org`'s secret.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
