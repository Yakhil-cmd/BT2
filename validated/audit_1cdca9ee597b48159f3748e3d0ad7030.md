### Title
Webhook signature is bound to `repository.owner.login`, but `StatusHandler` writes commit-status data with no repository scoping at all - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
Shipit supports multiple GitHub organizations, each with its own GitHub App and `webhook_secret`, configured under `github: <org>: webhook_secret` in `secrets.yml`. Every inbound webhook to the single shared `/webhooks` endpoint is authenticated by picking the verification secret from `repository.owner.login` (or `organization.login`) inside the *same, attacker-supplied* JSON body, then HMAC-verifying the whole raw body against that secret's key. [1](#0-0) [2](#0-1) 

For `status` events, the handler that actually applies the payload does not scope its effect to any repository, owner, or stack at all — it matches purely on commit SHA across the entire Shipit database: [3](#0-2) 

So the "organization that authenticated the request" (`repository.owner.login`, used to pick the HMAC secret) and "the repository/stack whose data is actually mutated" (implicitly, whichever commit anywhere in the instance happens to share that SHA) are two entirely independent bindings. Nothing ties the org used to select the signing secret to the repository/commit being written.

### Finding Description
`WebhooksController#verify_signature` resolves the GitHub App/secret to use for HMAC verification purely from `params.dig('repository','owner','login')` (falling back to `organization.login`), both fields fully controlled by whoever crafts the HTTP body: [4](#0-3) 

Because the entire raw POST body is what gets HMAC'd (`OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message)` in `verify_webhook_signature`), anyone who legitimately knows the `webhook_secret` for *any one* configured organization on the Shipit instance (e.g., an administrator of that org's own GitHub App installation) can produce a validly-signed `status` webhook whose `repository.owner.login`/`organization.login` is their own org, while every other field in the payload (`sha`, `state`, `description`, `target_url`, `context`) is fully attacker-chosen: [5](#0-4) 

`Shipit::Webhooks::Handlers::StatusHandler#process` then applies that payload to `Commit.where(sha: params.sha)` — a global, unscoped lookup with no join or filter on repository/owner/stack: [3](#0-2) 

This breaks the equality that should hold: `organization authorized by the signature == repository/stack whose commit status is mutated`. Instead, any org's own webhook secret authorizes writing a forged CI status onto a commit belonging to **any other organization/repository** tracked by the same Shipit instance, as long as the attacker can guess/observe a target commit SHA (SHAs are public git data, trivially obtainable from the victim's GitHub repo).

Note this differs from the other handlers (`PushHandler`, `CheckSuiteHandler`, PR handlers), which at least re-derive the affected `Repository`/`Stack` from `payload.dig('repository','full_name')` via `Handler#stacks`: [6](#0-5) 
Even those are still logically decoupled from the org used for signature verification (`repository.owner.login` vs `repository.full_name`), but `StatusHandler` is strictly worse: it performs **no repository binding whatsoever**.

### Impact Explanation
An attacker who administers/controls one legitimate GitHub organization onboarded to a shared, multi-org Shipit instance can inject fabricated commit CI statuses (`success`/`failure`/`pending`, arbitrary `description`/`target_url`/`context`) onto commits belonging to a **different tenant's repository**, without ever needing that tenant's webhook secret, an `ApiClient` token, or repository write access on GitHub. Since Shipit's deploy UI/workflow relies on `Status` records to represent whether a commit is safe/CI-green to deploy, this is a cross-repository/cross-tenant data-integrity break that can be used to make an unrelated organization's broken or malicious commit appear to have passed CI, undermining the commit-status gate that legitimate deployers rely on before shipping. This satisfies the "cross-repository writes" bucket of accepted impacts, since state belonging to one tenant's repository is written by an actor authenticated only for a different tenant's organization.

### Likelihood Explanation
Exploitability only requires: (1) the deployment runs Shipit in the documented multi-org configuration (each org with its own GitHub App/webhook_secret, as documented in `docs/setup.md`'s "Using Multiple Github Applications" section), and (2) the attacker administers/creates the GitHub App for at least one of those onboarded orgs (thus legitimately knowing that org's own `webhook_secret`) and knows a target commit SHA in a victim tenant's repository (public via `git log`/GitHub UI). No Shipit session, `ApiClient` token, or victim-org credentials are required — only knowledge of one's *own* org's webhook secret, which every onboarded org necessarily possesses. This is a realistic multi-tenant threat model for a shared Shipit deployment.

### Recommendation
- In `StatusHandler#process` (and ideally in the base `Handler`), scope the `Commit` lookup to commits belonging to the repository identified in the payload (`payload.dig('repository','full_name')`), e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` or an equivalent join through `Repository.from_github_repo_name`.
- More fundamentally, tie the org used for signature verification to the repository actually being mutated: verify that `repository.full_name`'s owner matches the `repository.owner.login`/`organization.login` used to select the webhook secret, and reject payloads where they diverge.
- Consider deriving the webhook secret per-repository (via the `Repository` record) rather than solely from attacker-suppliable payload fields.

### Proof of Concept
1. Shipit is configured with two orgs, `attacker-org` and `victim-org`, each with its own GitHub App and `webhook_secret` (per `docs/setup.md`'s multi-org setup).
2. Attacker is an administrator of `attacker-org`'s GitHub App and therefore knows `attacker-org`'s `webhook_secret`.
3. Attacker observes a commit SHA `S` belonging to a stack tracked under `victim-org/some-repo` (public information).
4. Attacker crafts a `status` webhook body:
```json
{
  "sha": "S",
  "state": "success",
  "description": "forged CI pass",
  "target_url": "https://ci.example.com/fake",
  "context": "ci/forged",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "attacker-org/whatever" }
}
```
5. Attacker computes `sha1=HMAC-SHA1(attacker-org webhook_secret, raw_body)` and sends the request with header `X-Github-Event: status` and `X-Hub-Signature` set to that value, per `WebhooksController#verify_signature` [1](#0-0) .
6. Because `repository.owner.login == "attacker-org"`, the signature is verified successfully with `attacker-org`'s secret.
7. `StatusHandler#process` runs `Commit.where(sha: "S")` and creates a forged `success` status on the victim commit `S` in `victim-org/some-repo`, despite the request never having been authenticated for `victim-org` at all: [3](#0-2) .

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
