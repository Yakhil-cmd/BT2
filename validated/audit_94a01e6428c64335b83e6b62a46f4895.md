## Analysis

The Rubicon finding describes a pattern where a single malicious, un-executable entry sitting at the "head" of an automatically-processed list causes the *entire* batch operation to abort/revert, denying service to everyone else and potentially freezing funds. The closest reachable analog in `ocore` is in the Autonomous Agent (AA) trigger-cascade engine in `aa_composer.js`.

When a primary AA trigger executes and its response unit pays out to addresses, every output address that happens to be a registered AA is unconditionally re-triggered as a "secondary trigger", with no opt-out and no isolation: [1](#0-0) 

The result of that secondary trigger is fed straight back into `async.eachSeries`; if the secondary AA bounces for *any* reason, the error propagates and the entire primary trigger — including all state changes, balances, and payments to unrelated parties already computed in the same response — is unwound via `revert()`: [2](#0-1) [3](#0-2) 

An attacker can deploy an "autonomous agent" address whose definition unconditionally calls `bounce(...)` (a normal formula primitive) regardless of trigger data: [4](#0-3) 

Any target AA that forwards a payment to an address influenced by attacker-controlled input (a very common AA pattern — e.g. paying out to `trigger.data.address`, forwarding swap/match proceeds to a maker-chosen recipient, referral payouts, etc.) will automatically re-trigger that address if it is a registered AA. If the attacker arranges for that address to be their "poison" AA, the *entire* victim trigger — including legitimate state updates and payouts to third parties within the same response — is reverted every time, exactly mirroring the Rubicon pattern of "one unfillable/poisoned entry blocks the whole batch," except here it's a mandatory secondary-trigger cascade rather than an order-book linked list.

### Title
Unconditional secondary-AA triggering with all-or-nothing revert enables DoS/fund-freezing of any AA that pays attacker-influenced addresses - (File: aa_composer.js)

### Summary
`handleSecondaryTriggers()` in `aa_composer.js` automatically re-triggers every registered AA that receives an output from another AA's response unit, with no way for the paying AA to opt out and no isolation between the primary trigger's success and a downstream secondary AA's outcome. If any secondary AA bounces, `handleSecondaryTriggers` propagates the error and calls `revert()`, undoing the *entire* primary trigger's response — including state changes and payments unrelated to the poisoned recipient.

### Finding Description
Secondary AA triggering is mandatory and address-driven: any output address found among `aa_addresses` (i.e., any registered AA) is queried and triggered regardless of the paying AA's intent [5](#0-4) . The chain is executed with `async.eachSeries`, and the completion handler treats *any* bounce from *any* secondary AA in the chain as a fatal error for the whole primary trigger:

```
child_trigger_opts.onDone = function (objSecondaryUnit, bounce_message) {
    if (bounce_message)
        return cb(bounce_message);
    cb();
};
...
function (err) {
    if (err) {
        if (bSecondary)
            return bounce(err);
        return revert({message: "one of secondary AAs bounced with error: ", callChain: {address, next: err}});
    }

``` [6](#0-5) 

`revert()` rolls back everything the primary AA had already computed for this trigger, including balances, state vars, and any responses that were about to be committed, then converts the whole operation into a bounce [3](#0-2) .

Anyone can permissionlessly deploy an AA whose init/messages unconditionally execute `bounce(...)` for any trigger [4](#0-3) , so an attacker fully controls at least one address that will always cause a secondary-trigger failure.

Many practical AA designs let the trigger sender or a stored counterparty influence an output address that a target AA subsequently pays (e.g. `trigger.data.recipient`, a maker's stored payout address in an order-matching AA, referral/reward payouts, escrow releases). Because output addresses are checked against `aa_addresses` with no allow-list or try/isolate semantics, routing a payment to such an attacker-controlled poison AA guarantees the *entire* triggering AA's operation reverts, no matter what unrelated, legitimate work that trigger also performed.

### Impact Explanation
This lets an attacker force a full revert of any AA execution that ends up paying an attacker-chosen (or attacker-registered) address, without needing to compromise the target AA itself. For AAs that manage shared state across many users in a single trigger call (e.g., order/queue processing, batched payouts, matching engines), one attacker-poisoned recipient embedded in the flow is enough to make that entire trigger execution permanently fail every time it is attempted, freezing whatever funds/state depend on completing that trigger — the same "freeze/DoS via unconditionally-reverting recipient" outcome described in the Rubicon report, achieved here through the mandatory, non-isolated secondary-AA cascade rather than a sorted order-book.

### Likelihood Explanation
Deploying a "poison" AA is a normal, permissionless, cheap action (posting one `definition` unit). The only requirement for exploitation is that some target AA's payment logic allow an output address to be influenced, directly or indirectly, by attacker-supplied data or attacker-controlled state — a common and often necessary pattern for AAs that pay third parties (swap proceeds, order fills, rewards, escrow release). Given AA composability is a core, encouraged feature of the platform, this is a realistic and reachable design-level pitfall baked into the engine's secondary-trigger semantics rather than a niche edge case.

### Recommendation
- Isolate secondary-trigger failures from the primary trigger's success: a bounce in one secondary AA branch should not force reverting the primary AA's already-computed state changes and unrelated payments, unless the primary AA's own logic explicitly depends on the secondary AA's success.
- Consider allowing an AA to explicitly mark certain outputs as "fire-and-forget" (not requiring secondary success) or provide a documented pattern/primitive so AA authors paying attacker-influenced addresses can avoid unconditional atomic coupling to arbitrary downstream AAs.
- At minimum, clearly document in the AA developer guidance that any AA forwarding funds to an address partly influenced by trigger data or third-party-supplied state is exposed to full-transaction DoS via a poison secondary AA, and provide a recommended mitigation pattern (e.g., validating the recipient is not a registered AA, or using `bounce_fees`/state checkpoints that are immune to downstream reverts).

### Proof of Concept
1. Attacker posts `["autonomous agent", { messages: [...], init: "{ bounce('always'); }" }]` at address `P`; `P` becomes a registered AA in `aa_addresses`.
2. Attacker interacts with victim AA `V`, whose logic sends part of its response payment to an address influenced by trigger data or by state the attacker can set (e.g., `trigger.data.recipient`, or a stored "payout address" that the attacker previously registered as `P` in an earlier, legitimate-looking trigger to `V`).
3. When `V` executes a trigger that outputs funds to `P`, `handleSecondaryTriggers` in `aa_composer.js` automatically triggers `P` (line 1703 query matches `P` in `aa_addresses`).
4. `P`'s `init` unconditionally calls `bounce('always')`, so `P`'s secondary trigger returns a bounce message; `handleSecondaryTriggers`'s `async.eachSeries` completion handler at lines 1743-1749 calls `revert()` on `V`'s entire trigger.
5. `V`'s whole operation (including any unrelated state changes/payouts computed in the same response) is undone and converted to a bounce, even though `V`'s own logic was correct — repeatable at will by the attacker to permanently DoS any `V` operation that routes to `P`.
