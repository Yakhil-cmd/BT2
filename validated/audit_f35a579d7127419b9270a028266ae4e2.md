Based on my investigation, I found a concrete binding-mismatch analog: the field used to select the webhook-signature key differs from the field the `MembershipHandler` trusts to decide which `Team`'s `organization` gets a member added — and this only matters (i.e., is actually exploitable) when Shipit is configured for multi-organization mode.

### Title
Webhook signature verified against `repository.owner.login` while `MembershipHandler` trusts a distinct `organization.login` field, enabling cross-org `Shipit.github_teams` membership escalation - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which configured GitHub App/organization's `webhook_secret` to HMAC-verify the request against using `repository_owner`, which reads `params.dig('repository','owner','login')` first, falling back to `params.dig('organization','login')` only when no `repository` key is present. [1](#0-0) [2](#0-1) 

`MembershipHandler`, however, never looks at `repository`; it derives the `Team#organization` value (and thus which `Team` a member is added to) purely from the payload's `organization.login` field: [3](#0-2) 

Because these are two different JSON fields in the same attacker-controlled request body, an attacker who legitimately controls a GitHub App/org that is *also* configured under Shipit's multi-org `secrets.yml` schema (i.e., they know their *own* org's `webhook_secret`) can craft a raw payload where `repository.owner.login` names their own org (satisfying `verify_signature`, since that's the key looked up and HMAC'd against), while `organization.login` names a different, privileged org (e.g., `shopify`). The signature check passes using the attacker's own known secret, but `MembershipHandler` will create/update a `Team` scoped to the victim organization and add the attacker (or any `member.login`) to it.

### Finding Description
`Shipit.github(organization:)` looks up a GitHub App config keyed by organization name in multi-org deployments (`github_app_config`), and each org can have its own independent `webhook_secret`. [4](#0-3) 

The equality that should hold is:
`organization whose secret authenticated the request == organization whose Team/membership state is written`

Before the attacker's request: verification and mutation both implicitly assume `repository.owner.login` (or, if absent, `organization.login`) is the *same* organization that owns the webhook and the same one referenced by handlers.

After the attacker's crafted request: `verify_signature` authenticates against the attacker's own low-privilege org (via `repository.owner.login`), but `MembershipHandler#find_or_create_team!`/`#process` writes to a `Team` scoped to whatever `organization.login` says, unconditionally trusting it as the mutation target. [5](#0-4) 

This breaks the equality because the field used for authentication and the field used for authorization-relevant mutation are not the same, and nothing cross-checks them against each other.

### Impact Explanation
`Shipit::User#authorized?` and the engine-wide authentication gate `force_github_authentication` both key off membership in `Shipit.github_teams`, i.e., `Team` records scoped by `organization`/`slug`. [6](#0-5) [7](#0-6) 

If an attacker can forge a `membership` webhook that is accepted (valid signature for org A) but writes membership into a `Team` for org B (`Shipit.github_teams`'s configured org), they can grant themselves (or any GitHub login) team membership that Shipit treats as authorization to access the entire application — this matches the explicitly in-scope High impact "escalation into `Shipit.github_teams` authorization."

### Likelihood Explanation
This requires Shipit to be configured with the documented multi-organization `secrets.yml` schema (which the engine explicitly supports and documents) and for the attacker to control (or have installed) at least one GitHub App on any org configured in that file, however minor/unprivileged, so they know its `webhook_secret`. I was not able to fully verify from the available in-scope files whether `verify_webhook_signature`'s `return true unless webhook_secret` (i.e., verification is skipped entirely when an org has no configured secret) could make this attack even easier by requiring no secret knowledge at all for a low-privilege org — this is a plausible amplifying factor but I could not trace all configuration-loading code paths within the given time to confirm which orgs would realistically have `webhook_secret` unset in a production multi-org deployment. [8](#0-7) 

### Recommendation
In `WebhooksController#verify_signature` and/or `Webhooks::Handlers::MembershipHandler`, ensure the organization/repository field used to select the verification key is the exact same field the handler subsequently trusts for the mutation — e.g., have `MembershipHandler` re-derive/validate `organization.login` against the same `repository_owner` resolution logic used in `verify_signature`, or pass the already-authenticated organization identity into the handler rather than letting it re-read an independent field from the raw payload.

### Proof of Concept
1. Configure Shipit with multi-org `secrets.yml` including both `victim-org` (target, has `Shipit.github_teams` referencing `victim-org/some-team`) and `attacker-org` (attacker has installed their own GitHub App and knows its `webhook_secret`).
2. Attacker computes `X-Hub-Signature` HMAC over a raw JSON body using `attacker-org`'s known `webhook_secret`, where the body is:
```json
{
  "action": "added",
  "team": {"id": 999, "name": "Fake", "slug": "fake", "url": "https://example.com"},
  "organization": {"login": "victim-org"},
  "member": {"login": "attacker-github-login"},
  "repository": {"owner": {"login": "attacker-org"}}
}
```
3. `verify_signature` resolves `repository_owner` to `"attacker-org"` (`app/controllers/shipit/webhooks_controller.rb:59-62`), fetches `Shipit.github(organization: "attacker-org")`, and the signature verifies successfully.
4. `MembershipHandler#process` ignores `repository` entirely and creates/finds a `Team` with `organization: "victim-org"`, then adds `attacker-github-login` as a member (`app/models/shipit/webhooks/handlers/membership_handler.rb:22-43`).
5. If `victim-org/some-team` is in `Shipit.github_teams`, the attacker's Shipit `User` (created via `User.find_or_create_by_login!`) is now `authorized?` and can access the application.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
