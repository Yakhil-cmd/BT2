### Title
Direct token transfers to the pool are permanently unclaimable — untracked donations can never be withdrawn - (File: contracts/pool/src/cache/cash.rs)

### Summary
The FeeSplitter bug class is "value accrues into a contract against an accounting total, but the accounting total can never fully reach the physical balance, so the excess is permanently stuck with no rescue path." XOXNO Lending's pool exhibits the same shape via its cash ledger: the pool's real token balance is `actual_balance`, but every credit/debit path operates on a separate `cash` counter that is only increased by measured, contract-initiated receipts. Tokens pushed directly to the pool address raise the real balance without raising `cash`, and no entrypoint — privileged or otherwise — can touch the difference.

### Finding Description
INV-ACCT-02 documents the design: "Reserve checks use tracked market cash; token donations alone do not increase it" [1](#0-0) . `formulas.md` repeats that tracked cash is "a separate reserve balance that incidental token donations do not increase" [2](#0-1) . All outbound token movement is gated by the `cash` counter: `claim_revenue` pays out only `min(cash, floor(revenue_value))` via `Cache::burn_claimable_revenue` and then debits `cash` [3](#0-2) , `ops::revenue::accounting` enforces `require_reserves`-style cash debiting through `cache.debit_cash(net_transfer)` [4](#0-3) , and user withdrawals are bounded by the same tracked reserves. Because INV-ACCT-03 credits only the *measured balance increase during a contract-driven transfer in* [5](#0-4) , a raw `token.transfer(pool, amount)` by any address inflates the pool's SAC balance while `cash`, `supplied`, and `revenue` are all unchanged. There is no skim/sweep/rescue entrypoint in the pool ABI (the `sweep` function found in the repo belongs to the out-of-scope `swap-aggregator`), so `actual_balance − cash` can never leave the contract.

### Impact Explanation
Any tokens sent directly to a pool contract — by mistake, by an air-dropper, by a third-party protocol settling to the pool address, or by griefers — are permanently frozen: no supplier claim, no revenue claim, and no admin path can release them, since every payout is clamped by the `cash` ledger. This matches the report's impact (funds locked in-contract forever, monotonically growing balance-vs-accounting divergence) and falls in the accepted "permanent freezing of funds" class.

### Likelihood Explanation
On Stellar, SAC transfers to contract addresses are common (fee rebates, router dust returns, refund paths that resolve to the pool rather than the caller). The router strategies and measured-receipt settlement make it plausible that third parties route tokens at the pool address expecting credit. Each occurrence irreversibly locks value; over the pool's lifetime the stranded amount grows monotonically with no recovery mechanism. The direct-transfer vector is explicitly listed as an in-scope unprivileged path.

### Recommendation
Add a permissionless or owner-gated sweep of `actual_balance − cash` per market asset (forwarding to the accumulator), or alternatively credit stray receipts into `revenue`/`supplied` on the next accrual so the value remains claimable rather than permanently locked. The controller's own `claim_revenue_for_asset` already demonstrates the measured-delta pattern that could be reused for a donation sweep [6](#0-5) .

```rust
// 1. Attacker/errant user sends tokens directly to the pool.
usdc.transfer(&alice, &pool, &1_000_000_000);

// 2. Observe divergence: real balance grew, tracked cash did not.
//    get_reserves(hub_asset) returns `cash` — unchanged.
//    token.balance(pool) — increased by 1_000_000_000.

// 3. Attempt to recover: every exit path is clamped by `cash`.
//    - claim_revenue: burn_claimable_revenue caps at self.cash and returns
//      only the tracked amount; the donation is unreachable.
//    - withdraw: require_reserves debits only from `cash`.
//    - recapitalize: credits measured receipt then refunds excess —
//      it cannot touch pre-existing untracked balance.
//    No sweep entrypoint exists in the pool ABI.

// 4. The 1_000_000_000 is permanently frozen; repeating the transfer
//    grows the stranded amount indefinitely.
```

Note: I could not enumerate the full pool ABI in the remaining budget to confirm the absence of a rescue function by exhaustive listing; the conclusion rests on INV-ACCT-02/03's explicit "donations do not increase cash" invariant, the documented payout formulas all clamping to `cash`, and the fact that the only `sweep` implementation in the repository lives in the out-of-scope swap-aggregator.

```rust
    pub(crate) fn burn_claimable_revenue(&mut self) -> i128 {
        let treasury_actual = self.unscale_supply_floor(self.revenue);
        let amount = self.cash.min(treasury_actual);
        if amount <= 0 {
            return 0;
        }
        let scaled_to_burn = if amount >= treasury_actual {
            self.revenue
        } else {
            self.revenue
                .mul_ratio_ceil(&self.env, amount, treasury_actual)
        };

        assert_with_error!(
            self.env,
            scaled_to_burn != Ray::ZERO,
            GenericError::InternalError
        );
        self.revenue = self.revenue.checked_sub(&self.env, scaled_to_burn);
        self.supplied = self.supplied.checked_sub(&self.env, scaled_to_burn);
        amount
    }
```

```rust
pub(crate) fn accounting(env: &Env, hub_asset: HubAssetKey) -> RevenueOutcome {
    let mut cache = ops::renewed_market(env, &hub_asset);

    let net_transfer = cache.burn_claimable_revenue();

    guards::require_utilization_below_max(env, &cache);
    guards::require_supply_for_debt(env, &cache);
    cache.debit_cash(net_transfer);

    cache.commit();
    RevenueOutcome {
        cache,
        mutation: PoolAmountMutation {
            actual_amount: net_transfer,
        },
    }
```
