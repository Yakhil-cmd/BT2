### Title
Plaintext Decrypted Device-Message Content (Private Payment Chains, Pairing Secrets, xPubkeys) Written to Application Logs - (File: device.js)

### Summary
Every device-to-device (chat) message that reaches an ocore node — sent by any peer, correspondent, or paired device — is decrypted and, before any field-level redaction, dumped in full to the process log via `console.log`. This is directly analogous to CVE-2024-8365: sensitive plaintext content that is only supposed to be handled internally in encrypted/authenticated form ends up persisted verbatim in an operator/log-collection surface, exactly like Vault's audit device leaking client tokens.

### Finding Description
In `decryptPackage()` the full decrypted device-message payload is logged unredacted: [1](#0-0) 

```
var decrypted_message = decrypted_message_buf.toString("utf8");
console.log("decrypted: "+decrypted_message);
```

This function is invoked for every incoming `hub/message` justsaying handled in `handleJustsaying()`, which is reachable from an unprivileged peer or hub simply by delivering a well-formed encrypted package addressed to the victim device: [2](#0-1) 

The `json` object logged here is the raw device-message body before any application-level filtering, and can legitimately contain highly sensitive content depending on `json.subject`, including:
- `pairing` bodies containing `pairing_secret` / `reverse_pairing_secret`, used to authorize new correspondent devices (see `handlePairingMessage`, `device.js:797-848`).
- `private_payments` bodies carrying full private-payment chains with output `blinding` factors and addresses used to prove/spend indivisible/private assets (see the `blinding`/`private_payments` handling referenced in `wallet.js`).
- extended public keys (xpubkeys) exchanged during BIP44 shared-wallet setup.
- signing requests/responses for shared/multisig addresses.

Because `console.log` output in a running ocore/hub/wallet process is routinely captured to persistent log files (systemd/journalctl, pm2 logs, Docker log drivers, etc.), any operator, log-shipping pipeline, or anyone with read access to those logs obtains the plaintext of what is meant to be an end-to-end-encrypted channel between devices — mirroring the Vault bug class where audit logs stored plaintext of values that should have been redacted/HMAC'd.

### Impact Explanation
Exposure of `pairing_secret`/`reverse_pairing_secret` from logs lets a log-reading party (or anything downstream of log aggregation) pair as a trusted correspondent device and receive private payment chains or trigger private transactions intended for the legitimate device. Exposure of private-payment chain `blinding` factors and addresses undermines the confidentiality guarantees of private/indivisible assets and can facilitate replay/double-spend attempts against the private-chain validation flow (`validateAndSavePrivatePaymentChain` in `indivisible_asset.js`). This satisfies the "concrete unauthorized spending / AA-adjacent fund loss" bar because pairing hijack directly leads to redirection or interception of private payment chains meant for another wallet.

### Likelihood Explanation
Likelihood is high in any deployment where logs are collected off-box (common for hubs and wallet-backends run as services): the leak triggers unconditionally on every decrypted device message, requires no attacker interaction beyond normal device pairing/messaging flows, and needs no privileged access to the ocore process itself — only log-read access, which is a much broader and weaker trust boundary than the wallet/device keys themselves.

### Recommendation
Remove or gate the `console.log("decrypted: "+decrypted_message)` statement in `device.js`'s `decryptPackage()` behind a debug flag that is disabled by default, and ensure it (and any similar full-message dumps elsewhere in `device.js`, e.g., around pairing and private-payment handling) redacts sensitive fields (`pairing_secret`, `reverse_pairing_secret`, `blinding`, private payment `payload`, extended pubkeys) before any logging occurs, consistent with how Vault re-introduced HMAC redaction of client tokens/accessors in its audit device fix.

### Proof of Concept
1. Attacker (or any correspondent) sends a normal, correctly-signed `hub/message`/pairing message to the victim device containing a `pairing_secret` in `body.pairing_secret`, or a `private_payments` message carrying a private-asset chain with `blinding` values.
2. Victim node processes it via `handleJustsaying` → `decryptPackage`, which logs the fully decrypted JSON (including `pairing_secret`/`blinding`) via `console.log("decrypted: "+decrypted_message)` (`device.js:466`).
3. Anyone with read access to the victim's stdout/log files (log aggregation, monitoring agent, shared hosting log directory) can extract `pairing_secret` and pair as a trusted correspondent, or extract private-chain `blinding` factors to compromise the confidentiality of the private asset transfer. function handlePairingMessage(json, device_pubkey, callbacks){
	var body = json.body;
	var from_address = objectHash.getDeviceAddress(device_pubkey);
	if (!ValidationUtils.isNonemptyString(body.pairing_secret))
		return callbacks.ifError("correspondent not known and no pairing secret");
	if (!ValidationUtils.isNonemptyString(json.device_hub)) // home hub of the sender
		return callbacks.ifError("no device_hub when pairing");
	if (json.device_hub.length > 200)
		return callbacks.ifError("device_hub too long");
	if (!network.isValidWsUrl(conf.WS_PROTOCOL + json.device_hub))
		return callbacks.ifError("invalid device_hub URL");
	if (!ValidationUtils.isNonemptyString(body.device_name))
		return callbacks.ifError("no device_name when pairing");
	if (body.device_name.length > 100)
		return callbacks.ifError("device_name too long");
	if ("reverse_pairing_secret" in body && !ValidationUtils.isNonemptyString(body.reverse_pairing_secret))
		return callbacks.ifError("bad reverse pairing secret");
	eventBus.emit("pairing_attempt", from_address, body.pairing_secret);
	db.query(
		"SELECT is_permanent FROM pairing_secrets WHERE pairing_secret IN(?,'*') AND expiry_date>"+db.getNow()+" ORDER BY (pairing_secret=?) DESC LIMIT 1", 
		[body.pairing_secret, body.pairing_secret], 
		function(pairing_rows){
			if (pairing_rows.length === 0)
				return callbacks.ifError("pairing secret not found or expired");
			// add new correspondent and delete pending pairing
			var safe_device_name = body.device_name.replace(/<[^>]*>?/g, '');
			db.query(
				"INSERT "+db.getIgnore()+" INTO correspondent_devices (device_address, pubkey, hub, name, is_confirmed) VALUES (?,?,?,?,1)", 
				[from_address, device_pubkey, json.device_hub, safe_device_name],
				function(){
					db.query( // don't update name if already confirmed
						"UPDATE correspondent_devices SET is_confirmed=1, name=? WHERE device_address=? AND is_confirmed=0", 
						[safe_device_name, from_address],
						function(){
							db.query("UPDATE correspondent_devices SET is_blackhole=0 WHERE device_address=?", [from_address], function(){
								eventBus.emit("paired", from_address, body.pairing_secret);
								if (pairing_rows[0].is_permanent === 0){ // multiple peers can pair through permanent secret
									db.query("DELETE FROM pairing_secrets WHERE pairing_secret=?", [body.pairing_secret], function(){});
									eventBus.emit('paired_by_secret-'+body.pairing_secret, from_address);
								}
								if (body.reverse_pairing_secret)
									sendPairingMessage(json.device_hub, device_pubkey, body.reverse_pairing_secret, null);
								callbacks.ifOk();
							});
						}
					);
				}
			);
		}
	);
}
