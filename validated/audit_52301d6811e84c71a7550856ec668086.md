### Title
`recapitalize` pays a refund for tokens never received, draining pool custody to an unprivileged payer - (File: contracts/pool/src/ops/recapitalize.rs)

### Summary
The Open5GS bug class is "a message processed while a required element is missing, triggering a crash/invalid state." The analog here is a settlement processed while the required element — the actual token receipt — is missing. `pool.recapitalize` credits cash up to the backing shortfall and transfers the "excess" back to `payer`, but it never measures that `amount` tokens actually arrived. It trusts a doc comment ("The controller transfers `amount` into the pool before this call") instead of a balance check. When the market's shortfall is smaller than `amount` (including zero on a solvent market), the pool pays `payer` real tokens that were never deposited, out of supplier custody.

### Finding Description
`accounting` in `contracts/pool/src/ops/recapitalize.rs:44-67` computes `applied = amount.min(backing_shortfall(&cache))` and `refund = amount - applied`, then `apply` calls `outcome.cache.transfer_out(&payer, outcome.refund)` at line 34. Nothing in the function or its cache checks `token::balance` before or after — unlike `flash_loan`, which the lib.rs docs note "checks the token balance after payout, after the callback and after repayment" (`contracts/pool/src/lib.rs:34-36`). The shortfall itself is a pure book computation over `cache.cash()`, `supplied`, and `borrowed` (`contracts/pool/src/guards.rs:61-66`), so `refund` can be arbitrarily large with zero tokens received.

The in-repo test `test_unfunded_recapitalize_leaves_the_cash_book_overstating_custody` (`contracts/pool/tests/flows.rs:3408-3482`) demonstrates both halves: an unfunded `recapitalize` drains the pool's entire token balance to `payer` (`assert_eq!(token.balance(&t.pool), 0)`), while the cash book still claims the full deposit — so the next supplier withdraw passes the pool's own liquidity and solvency guards and then fails inside the SAC transfer with `BalanceError = 10`, permanently locking remaining supplier claims.

### Impact Explanation
Two reachable outcomes, both in scope:

1. **Theft of user funds**: on a solvent or nearly-solvent market, `refund ≈ amount` is paid from pool custody to `payer`. `payer` is a caller-supplied address argument, so the beneficiary is the caller.
2. **Permanent freezing of funds / insolvency**: when the injected `amount` is not actually funded but is applied to the book (shortfall > 0), `credit_cash` inflates the cash ledger past real custody. Withdrawals then clear `require_reserves`/`require_backed_market` (which read the book) and revert inside the token transfer — suppliers' shares cannot be redeemed even though the market reports itself solvent.

### Likelihood Explanation
`recapitalize` is listed among the unprivileged-reachable controller entrypoints, and the pool-side op performs no receipt verification — the missing required element is exactly the token transfer, mirroring the missing `MME_UE_S1AP_ID`. An attacker only needs to invoke the path with an `amount` exceeding the current shortfall, or with no funding at all, and name themselves `payer`. No price manipulation, no privileged role on the attacker, and no cooperation from other users is required. The only uncertainty is whether the controller wrapper enforces the inbound transfer itself; the pool contract demonstrably does not, and the test harness confirms the drain is reproducible at the pool boundary.

### Recommendation
Make `recapitalize` measured-receipt, consistent with the flash-loan invariant: record `token::balance(pool)` before crediting, require the post-call balance to be at least `before + applied` (or measure `applied` directly from the balance delta), and compute `refund` only from funds actually received. Alternatively, pull the tokens inside `recapitalize` via `transfer_from` so custody and book cannot diverge. Add a guard so `transfer_out(payer, refund)` can never exceed a balance delta attributable to this call.

### Proof of Concept
`contracts/pool/tests/flows.rs:3408-3482` is an executable PoC:

```rust
// Supplier deposits; book cash == custody.
token_admin.mint(&t.pool, &deposit);
t.client().supply(&t.sup(0, deposit));

// Unfunded recapitalize: no transfer in, yet custody is drained to `payer`.
let custody = token.balance(&t.pool);
t.client().recapitalize(&hub(&t.asset), &payer, &custody);
assert_eq!(token.balance(&t.pool), 0);              // custody gone
assert!(t.state_snapshot().cash >= deposit);        // book still claims it

// Supplier withdraw now fails inside the SAC transfer (BalanceError = 10),
// not in any pool guard — funds are permanently frozen for remaining claims.
let outcome = t.client().try_withdraw(&receiver, &false, &t.wdr(supplied, i128::MAX, 0));
assert!(outcome.is_err());
```

Root cause lines: `applied`/`refund` computed from book state only (`contracts/pool/src/ops/recapitalize.rs:52-57`) and unconditional `transfer_out` of the refund (`contracts/pool/src/ops/recapitalize.rs:34`).
