### Title
Webhook organization used for signature verification is decoupled from the repository the event actually acts on - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
The Crowdsale report is about a "mandatory guard" that is silently optional (`finalizeAgent`), letting state advance without the intended authorization check. The equivalent binding in Shipit is: *the GitHub organization whose secret is used to authenticate an inbound webhook* must equal *the organization/repository the webhook payload is actually applied to*. `WebhooksController#verify_signature` selects the signing secret using one attacker-controlled field (`repository.owner.login`), while the event handlers (`Handler#repository_name`, used by `PushHandler`, `StatusHandler`, `CheckSuiteHandler`) resolve the target `Repository`/`Stack` using a different attacker-controlled field (`repository.full_name`) from the same unauthenticated JSON body. Nothing cross-checks that these two fields agree.

### Finding Description
`WebhooksController#verify_signature` picks which `GitHubApp`/secret to validate against purely from the untrusted payload: [1](#0-0) [2](#0-1) 

`repository_owner` is read from `params.dig('repository', 'owner', 'login')`. Signature verification itself is: [3](#0-2) 

Critically, `return true unless webhook_secret` — if the organization resolved by `repository_owner` has **no `webhook_secret` configured** (the documented/example default, e.g. `webhook_secret: # nil` in `config/secrets.development.example.yml` and `docs/setup.md`), signature verification is skipped entirely and the request is treated as authentic, regardless of what is actually signed.

Once past `verify_signature`, the actual event handlers resolve the target repository from a **different** field of the same payload: [4](#0-3) 

This is used by `PushHandler`: [5](#0-4) 

`repository.owner.login` (used to choose the verification secret) and `repository.full_name` (used to resolve `Repository.from_github_repo_name`, which then resolves `Stack`) are two independent keys inside the same untrusted `repository` object. In genuine GitHub webhooks they are always consistent (`full_name` = `"<owner.login>/<name>"`), and the whole body is HMAC-signed as one blob by GitHub for that specific org's installation, so the two values can never diverge from GitHub's perspective. The controller's logic implicitly assumes this invariant holds for the entire lifetime of the request, but nothing enforces it once an attacker crafts a raw payload directly.

Concretely, the "mandatory-but-actually-optional" pattern from the reported bug class appears here as: the organization used to gate authenticity (`repository.owner.login`) is optional/bypassable (no-secret org), while the repository actually mutated (`repository.full_name`) is a separate, unauthenticated field. The equality that should hold and is silently broken is:
`org(secret used to verify signature) == org(repository/stack actually acted upon)`

### Impact Explanation
If any organization configured under `Shipit.github` (single- or multi-org config, see `lib/shipit.rb#github`, `docs/setup.md` "Using Multiple Github Applications") has no `webhook_secret` set — which is the shown default value in the shipped example config — the `/webhooks` endpoint becomes an open, unauthenticated event injector for **every other configured organization's repositories/stacks**, because the org used to bypass the signature check is decoupled from the org whose `Stack` is mutated. An attacker with no credentials, no session, no `ApiClient` token, and no knowledge of any real secret can:
- Set `X-Github-Event: push`, `repository.owner.login` = the no-secret org, `repository.full_name` = `victim-org/victim-repo`, `ref`/`after` = an attacker-chosen (real, published) commit SHA, and trigger `stack.sync_github(expected_head_sha:)` on the victim's stack via `PushHandler`.
- Similarly forge `status`/`check_suite` events against a victim's commits.

If the victim stack has continuous deployment/merge-queue enabled, this can lead to an **unauthorized deploy** being triggered against an attacker-selected commit — matching the "Critical: unauthorized deploy" impact bucket. Even without continuous deployment, it is an unauthenticated cross-organization write into stack/commit state.

### Likelihood Explanation
Exploitability depends entirely on a specific, but realistic and documented, misconfiguration: at least one org entry in `Shipit.github` with `webhook_secret` left blank. This is the literal example value shown in `config/secrets.development.example.yml` and `config/secrets.development.shopify.yml`, so it is a plausible real-world state, especially for a newly-added org that a team forgets to configure a secret for. Once that condition is met, exploitation requires no privileges of any kind — a bare unauthenticated HTTP POST to `/webhooks` with a hand-crafted JSON body. I was not able to fully trace the downstream `GithubSyncJob` and continuous-deployment auto-trigger logic within the remaining budget, so the exact conditions for an unattended deploy to fire (vs. just corrupting sync state / commit records) are not fully confirmed and should be verified in code (`app/jobs/shipit/github_sync_job.rb`, `app/jobs/shipit/continuous_delivery_job.rb`).

### Recommendation
- In `WebhooksController#verify_signature` / `Handler`, enforce that the organization used to select the verification secret is the same organization actually operated on by the handler (e.g., re-derive and compare `repository.full_name`'s owner segment against `repository_owner` before dispatching, and reject on mismatch).
- Treat a missing `webhook_secret` as "reject all webhooks for this org" rather than "accept all webhooks for this org," or require `webhook_secret` to be present for any organization defined in `Shipit.github`.
- Consider signing/verifying against a canonical, single field (e.g., always derive both the app selection and the repository target from `repository.full_name`) instead of two independently-attacker-controlled JSON fields.

### Proof of Concept
Precondition: `Shipit.github` is configured with at least two organizations, e.g. `no-secret-org` (no `webhook_secret` set) and `victim-org` (owns a real `Stack`/`Repository` in Shipit).

```
POST /webhooks HTTP/1.1
X-Github-Event: push
Content-Type: application/json
(no valid X-Hub-Signature needed)

{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-existing-sha-on-victim-org/victim-repo>",
  "repository": {
    "owner": { "login": "no-secret-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
`verify_signature` calls `Shipit.github(organization: "no-secret-org")`, whose `webhook_secret` is nil, so `verify_webhook_signature` returns `true` unconditionally — the request is accepted with no valid signature at all. `PushHandler` then resolves `Repository.from_github_repo_name("victim-org/victim-repo")` and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` on the victim's real stack, entirely unauthenticated.

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
# frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
    end
  end
end
```
