### Title
Malicious Proposer Can Silently Skip `BroadcastVRankPreprepare` to Inflate All Candidates' CFS Scores — (`kaiax/vrank/impl/handler.go`)

---

### Summary

The VRank module's `HandleIstanbulPreprepare` function requires the block-N proposer to voluntarily broadcast a `VRankPreprepare` message to candidates. No consensus mechanism enforces this broadcast. A malicious proposer can silently omit it, causing every candidate to appear to have failed to respond, which inflates their Candidate Failure Scores (CFS) committed into `header(N+1).VRank`. The `VerifyHeader` guard only checks that reported addresses are valid candidates; it cannot detect whether the proposer actually sent the trigger message.

---

### Finding Description

**The proposer-only, unenforceable action:**

In `HandleIstanbulPreprepare`, when the local node is the proposer for block N, it calls `BroadcastVRankPreprepare` to notify candidates that a response is expected:

```go
// kaiax/vrank/impl/handler.go lines 57-59
if v.isProposer(blockNum, view.Round.Uint64()) {
    v.BroadcastVRankPreprepare(&vrank.VRankPreprepare{Block: block, View: view})
}
```

This is a fire-and-forget P2P broadcast. No other node can verify whether the proposer executed it. A malicious proposer simply does not call this (or runs a patched binary that skips it).

**The downstream effect:**

Candidates only send `VRankCandidate` responses after receiving `VRankPreprepare`. If the proposer skips the broadcast, candidates receive nothing and send nothing. Committee members of block N record a `prepreparedAt` timestamp (from `HandleIstanbulPreprepare`) but collect zero `VRankCandidate` messages in their collector.

When the proposer of block N+1 calls `encodeCandidateFailureVRank` → `EvaluateCandidates(N, round)`:

```go
// kaiax/vrank/impl/getter.go lines 116-138
prepreparedAt, expectedBlockHash, viewMap := v.collector.GetViewData(vk)
if prepreparedAt.IsZero() {
    return []common.Address{}, nil   // proposer of N+1 was not a committee member
}
// ...
for _, addr := range candidates {
    msgWithTime, arrived := viewMap[addr]
    if !arrived || ... {
        cfReport = append(cfReport, addr)  // every candidate is "failed"
    }
}
```

Because no `VRankCandidate` messages arrived, every candidate in `GetCandTesting(N)` is appended to `cfReport`. The honest proposer of block N+1 then writes this fully-inflated report into `header(N+1).VRank`.

**The verification gap:**

`VerifyHeader` only validates that reported addresses are members of `GetCandTesting(N-1)`:

```go
// kaiax/vrank/impl/consensus.go lines 63-71
report, err := vrank.DecodeReport(header.VRank)
...
candidates, err := v.Valset.GetCandTesting(number - 1)
...
return validateNonEpochVRank(report, candidates)
```

`validateNonEpochVRank` checks sortedness, deduplication, and membership — but **not accuracy**. A cfReport listing all candidates as failed passes verification identically to a correct empty report.

---

### Impact Explanation

CFS accumulates per-candidate failure counts across an epoch and is consulted at epoch-end state transitions that govern candidate promotion to validator status. A malicious proposer who skips `BroadcastVRankPreprepare` for every block they propose causes the honest next-proposer to commit a fully-inflated cfReport. Over an epoch of 86,400 blocks, even a single validator with modest proposer frequency can accumulate enough false failures against all candidates to suppress their promotion. This constitutes validator-set privilege manipulation: the malicious proposer unilaterally controls which candidates can advance, without any on-chain evidence of wrongdoing.

The byzantine filter (`F = floor(N/3)` distinct proposers discarded) provides partial mitigation, but:
- Early in an epoch when fewer than 3 distinct proposers have proposed, `F = 0` and no filtering occurs.
- A single malicious proposer's false reports are only filtered once enough honest proposers have also reported, which may be too late for candidates evaluated near epoch boundaries.

---

### Likelihood Explanation

Any qualified validator selected as proposer can execute this attack by running a patched binary that omits the `BroadcastVRankPreprepare` call. No special privilege beyond being a scheduled proposer is required. In a network with a small committee, a single validator may be selected as proposer multiple times per epoch, amplifying the effect. The attack is silent — no on-chain artifact distinguishes a proposer who skipped the broadcast from one whose message was lost to network conditions.

---

### Recommendation

1. **Do not rely on the proposer to voluntarily trigger candidate evaluation.** Candidates should be able to self-attest readiness by querying the chain for the current block proposal and responding without waiting for a `VRankPreprepare` message.
2. **Extend `VerifyHeader` to bound the cfReport size.** If the number of reported failures equals `len(GetCandTesting(N-1))` (all candidates failed), require additional evidence or reject the report as implausible.
3. **Strengthen the byzantine filter at epoch start.** Apply a minimum filter threshold (e.g., `F ≥ 1`) regardless of how few distinct proposers have been seen, to prevent early-epoch manipulation.
4. **Remove the `skipCandidate` testing flag** before production release, as it provides a ready-made mechanism for candidates to also suppress their responses.

---

### Proof of Concept

```
Epoch block range: [0, 86400)
Actors: Malicious proposer M, candidates C1..Ck, honest committee validators V1..Vm

For each block N where M is selected as proposer:
  1. M receives Istanbul PREPREPARE for block N.
  2. M's HandleIstanbulPreprepare runs; the isProposer() check is true.
  3. M's patched binary skips BroadcastVRankPreprepare (or M simply drops the outbound message).
  4. C1..Ck receive no VRankPreprepare; they send no VRankCandidate.
  5. V1..Vm record prepreparedAt for block N but collect zero VRankCandidate messages.
  6. Proposer of block N+1 (honest) calls EvaluateCandidates(N, round):
       - prepreparedAt is non-zero (V was a committee member)
       - viewMap is empty (no VRankCandidate arrived)
       - All of C1..Ck are appended to cfReport
  7. header(N+1).VRank = RLPEncode([C1, C2, ..., Ck])  ← all candidates "failed"
  8. VerifyHeader accepts this report (all addresses ∈ GetCandTesting(N)).

After enough such blocks, CFS[Ci] exceeds the promotion threshold for every candidate,
blocking all candidates from advancing to validator status for the epoch.
```

```go
func (v *VRankModule) encodeCandidateFailureVRank(number uint64) ([]byte, error) {
	if number == 0 {
		return nil, nil
	}
	parentNum := number - 1
	parent := v.Chain.GetHeaderByNumber(parentNum)
	if parent == nil {
		logger.Error("Failed to read parent header for VRank", "num", number, "parentNum", parentNum)
		return nil, vrank.ErrHeaderNotFound
	}
	parentRound, err := v.RoundReader.Round(parent)
	if err != nil {
		logger.Error("Failed to read parent round for VRank", "err", err, "parentNum", parentNum)
		return nil, err
	}
	report, err := v.EvaluateCandidates(parentNum, uint64(parentRound))
	if err != nil {
		logger.Error("Failed to evaluate VRank candidates", "err", err, "prevBlockNum", parentNum, "prevRound", parentRound)
		return nil, err
	}
	if len(report) == 0 {
		return nil, nil
	}
	encoded, err := vrank.EncodeReport(report)
	if err != nil {
		logger.Error("Failed to encode VRank report", "err", err, "report", report)
		return nil, err
	}
	return encoded, nil
```

```markdown

The CP matrix is then passed through a **byzantine filter** before producing the final CFS. The filter discards the top-F reporter totals per candidate, where `F = N - ceil(2N/3) = floor(N/3)` and `N = cpMatrix.ProposerCount()` (the number of distinct proposers in the epoch so far). This protects against up to F malicious proposers falsely accusing candidates. Early in an epoch `N` is small and the filter is correspondingly weak, but CFS is only consulted at epoch-end state transitions.
```
