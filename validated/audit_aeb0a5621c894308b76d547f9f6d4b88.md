### Title
`r of set` (and `weighted and`) address definitions accept duplicate set members, allowing a single signer to satisfy a multi-signature threshold alone - (File: definition.js)

### Summary
Address (and asset issue/transfer condition) definitions in ocore support the `r of set` operator, which is meant to require signatures/conditions from `required` distinct members out of a `set` of `N` sub-definitions (e.g. an M-of-N multisig). Neither the structural validator (`validateDefinition`) nor the runtime evaluator (`validateAuthentifiers`) checks that the entries in `args.set` are distinct. A `set` can therefore contain the same sub-definition (e.g. the same `["sig", {pubkey: P}]` or `["address", A]`) more than once. Because each set element is evaluated independently at its own signing path (`path+'.'+index`), and signature verification only checks that the signature at that path is valid for that sub-definition's key (not that distinct keys were used across the whole set), a single real signer can satisfy multiple "slots" of the set by reusing/copying their one valid signature into multiple paths. This is directly analogous to the reported bug class: an item is "registered" into an array without a duplicate check, and something that should be counted once (one distinct collateral token / one distinct co-signer) is instead counted multiple times, defeating a security threshold.

### Finding Description
- Structural validation of `r of set` in `validateDefinition` checks `required`, array-ness, and minimum length, but never checks that `args.set` members are distinct: [1](#0-0) 

- The same lack of duplicate checking exists for `weighted and`: [2](#0-1) 

- At signature-verification time (`validateAuthentifiers`), `r of set` simply iterates `args.set` and evaluates each member at its own path, summing up how many return true, then compares to `args.required`: [3](#0-2) 

- The `sig` authentifier check verifies the signature found at `assocAuthentifiers[path]` against `args.pubkey` and the (path-independent) `unit_hash_to_sign`. Nothing ties the signature to path uniqueness in terms of the key used elsewhere in the same `r of set`: [4](#0-3) 

Because the value being signed (`objValidationState.unit_hash_to_sign`) does not depend on `path`, a single ECDSA signature produced by one private key is valid at every path that references that same public key. If the address definition is:
```
["r of set", {
  "required": 2,
  "set": [
    ["sig", {"pubkey": "P_A"}],
    ["sig", {"pubkey": "P_A"}],   // duplicate of the first entry
    ["sig", {"pubkey": "P_B"}]
  ]
}]
```
the author holding only `P_A`'s private key can supply the same signature at both `r.0` and `r.1`, satisfying `required=2` without any cooperation from `P_B`. The address hash (`chash`) is still well-defined (it's just a hash of the JSON structure including the duplicate), so this passes `objectHash.getChash160` checks with no issue, and the definition passes `validateDefinition` unmodified.

### Impact Explanation
This breaks the security guarantee of any M-of-N address definition (shared/multisig wallets created via `wallet_defined_by_keys.js`'s `createMultisigWallet`, which builds exactly this `r of set` structure from a `set` of per-device `sig` sub-definitions) or of any custom `r of set`/`weighted and` condition used for asset issue/transfer conditions. A party who can influence how the `set` is constructed (or who controls one member's key and manages to get their own sub-definition duplicated in the set, e.g. by supplying the same device/pubkey twice under a different nominal "member" slot) can unilaterally satisfy a threshold that other cosigners believe requires independent, distinct approvals. This is a concrete path to unauthorized spending of funds locked behind such a definition, and it is reachable purely by an ordinary unit author defining (or co-defining) an address — no privileged network position is required.

### Likelihood Explanation
Exploitation requires that a `set` used in `r of set` (or `weighted and`) contain a duplicated sub-definition. This can occur either through:
1. A malicious participant in wallet setup crafting/proposing a shared-address definition template with a repeated member (nothing in `validateAddressDefinitionTemplate` / `getMemberDeviceAddressesBySigningPaths` rejects a `set` entry appearing twice), or
2. Any application/AA that programmatically builds `r of set` conditions from user or dynamic input without deduplicating.

Since the vulnerable code path is standard address-definition validation and signature verification used for every unit, any single author is able to trigger and exploit it by constructing their own address this way, making the likelihood high once such a definition exists.

### Recommendation
In `validateDefinition`, when validating `r of set` and `weighted and`, reject definitions whose `args.set` contains duplicate (structurally identical, e.g. by comparing `JSON.stringify`/hash of each element) sub-definitions:
```diff
case 'r of set':
    ...
    if (args.set.length < 2)
        return cb("set must have at least 2 options");
+   var arrSerializedSet = args.set.map(el => JSON.stringify(el));
+   if (_.uniq(arrSerializedSet).length !== arrSerializedSet.length)
+       return cb("set must not contain duplicate members");
    if (args.required > args.set.length)
        return cb("required must be <= than set length");
```
Apply the equivalent check to `weighted and`'s `args.set` (comparing the `value` sub-definitions). This should be introduced behind an upgrade MCI (as is done elsewhere in `definition.js`, e.g. `pemCurvesFixMci`) to avoid breaking already-existing addresses, while blocking new ones from using duplicated set members.

### Proof of Concept
1. Construct an address definition:
```js
var def = ["r of set", {
  required: 2,
  set: [
    ["sig", {pubkey: pubkeyA}],
    ["sig", {pubkey: pubkeyA}],
    ["sig", {pubkey: pubkeyB}]
  ]
}];
var address = objectHash.getChash160(def);
```
2. Fund `address` with bytes/assets (e.g. via a shared/multisig wallet flow that believes 2 of {A, B, C} — but where slot 0 and 1 both secretly resolve to `A`).
3. Party A alone signs a spending unit: compute `unit_hash_to_sign`, sign once with `pubkeyA`'s private key to get `sigA`.
4. Submit the unit with `author.authentifiers = {"r.0": sigA, "r.1": sigA}` (reusing the same signature at both paths).
5. `validateAuthentifiers`'s `r of set` handler evaluates path `r.0` → `sig` check passes (valid signature for `pubkeyA`), path `r.1` → `sig` check passes again for the same key/signature, path `r.2` → not signed. `count = 2 >= required (2)` → unit is accepted, and A has moved funds without B's participation.
