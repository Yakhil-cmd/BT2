### Title
`merkle.js` merkle proof verification is vulnerable to the classic second-preimage attack, allowing forged inclusion proofs to bypass `in merkle` address authentifiers and `is_valid_merkle_proof()` in oscript — (File: `merkle.js`)

### Summary
ocore's Merkle tree implementation hashes leaves and internal nodes with the exact same domain: `hash(element)` for leaves and `hash(hash1+hash2)` for internal nodes, with no prefix/tag distinguishing the two. This is the classical second-preimage weakness (CVE-2012-2459 class) and is structurally identical to the reported AvailBridge issue, where a 64-byte concatenation of two legitimate tree hashes can be mistaken for — and successfully verified as — a genuine leaf.

### Finding Description

and verification: [2](#0-1) 

The code even contains the comment `// Node-as-Leaf issue might matter in some cases` at the top of `verifyMerkleProof`, acknowledging the exact weakness, but no domain-separation fix (e.g., prefixing leaves with `0x00` and internal nodes with `0x01`) was applied.

Because a leaf is simply `hash(element)` and an internal node is `hash(child1+child2)`, anyone who knows two sibling hash values `h1`, `h2` inside a real, published tree can set `element = h1 + h2`. Then `hash(element)` equals exactly the internal node value that `h1` and `h2` produce, and a proof consisting of the siblings *above* that internal node (with the correct index/path) will successfully verify against the tree's real, published root — even though `element` was never an actual entry of the original data set.

This primitive is reachable from two unprivileged surfaces:

1. **Address definition authentifier `in merkle`** — used to authorize spending by proving that a fixed `element` is a member of a Merkle root published by an oracle via a data feed: [3](#0-2) 
Here `proof` (`serialized_proof`) is supplied by the unit poster at spend time via `assocAuthentifiers[path]`, and it is checked with `merkle.verifyMerkleProof(element, proof)` before confirming `proof.root` exists in the oracle's data feed history via `dataFeeds.dataFeedExists(...)`. Since the vulnerable equality only depends on `element` matching a concatenation of two real internal hashes of the oracle's committed tree, an attacker constructing a definition can pick an `element` equal to `h1+h2` for two internal nodes of a legitimately published tree and supply a proof for the corresponding path — satisfying the authentifier without the "element" ever having been a genuine leaf of the oracle's dataset.

2. **oscript primitive `is_valid_merkle_proof(element, proof)`**, directly exposed to AA trigger authors and formula authors: [4](#0-3) 
Both `element` and `proof` (including `proof.root`) come from evaluated formula expressions, which in AA context are typically derived from `trigger.data`, i.e., fully attacker-controlled. AA authors commonly compare `proof.root` against a trusted value (e.g., an oracle-posted data feed root) to gate an action (claim, whitelist check, payout). Because `merkle.verifyMerkleProof` doesn't separate leaf/node hash domains, an attacker can supply a forged `element` (concatenation of two real internal hash strings from the publicly known dataset) plus a proof path that validates against the legitimate, trusted root.

### Impact Explanation
Any oscript-based access-control or eligibility scheme relying on `in merkle` (definition.js) or `is_valid_merkle_proof` (AA formulas) to gate spending, claims, or fund releases against an externally trusted Merkle root can be bypassed by a party who is not a genuine member of the committed set. In the address-definition case this can directly translate into unauthorized satisfaction of a spending condition (unauthorized fund access); in the AA case it can allow bypass of allowlist/airdrop/claim eligibility checks, leading to AA fund loss to non-eligible parties. This matches the "unauthorized spending / AA fund loss" impact class.

### Likelihood Explanation
Exploitation requires only that the attacker know two adjacent hash values inside the already-published tree (the published tree/data feed value, and typically its underlying data set, are public), and can freely craft `element`/`proof` fields at unit-posting or AA-trigger time — no privileged access is required. The vulnerability is deterministic and always present because leaf and internal-node hashing share the same domain in `merkle.js`; there is no randomness or race condition needed.

### Recommendation
Add domain separation in `merkle.js`: hash leaves with a distinct prefix (e.g., `hash(0x00 + element)`) and internal nodes with another (e.g., `hash(0x01 + left + right)`), or otherwise make it structurally impossible for a valid leaf hash input to collide with the internal-node concatenation format. Apply the same fix to `getMerkleRoot`, `getMerkleProof`, and `verifyMerkleProof` consistently, and bump proof serialization if backward compatibility is a concern.

### Proof of Concept
1. Given a Merkle tree built by `merkle.getMerkleRoot`/`getMerkleProof` over some dataset (e.g., an oracle's whitelist), take any two sibling hashes `h1` and `h2` (the base64 sha256 hash strings) that appear as children of some internal node `N` at depth `d`.
2. Set `element = h1 + h2`.
3. Take the tree's original sibling list for `N`'s path from depth `d` to the root (i.e., the same siblings that would have been used to prove `N` if it were a leaf) as `proof.siblings`, with the correct `proof.index` for `N`'s position, and `proof.root` equal to the real published root.
4. Call `merkle.verifyMerkleProof(element, proof)` — it returns `true`, even though `element` (the raw concatenation string) is not an actual entry of the original dataset.
5. This forged `(element, proof)` pair can be supplied as the `assocAuthentifiers[path]` value for an `in merkle` clause in `definition.js`, or as `trigger.data.element`/`trigger.data.proof` to an AA calling `is_valid_merkle_proof`, bypassing the intended membership check.

function getMerkleRoot(arrElements){
	var arrHashes = arrElements.map(hash);
	while (arrHashes.length > 1){
		var arrOverHashes = []; // hashes over hashes
		for (var i=0; i<arrHashes.length; i+=2){
			var hash2_index = (i+1 < arrHashes.length) ? (i+1) : i; // for odd number of hashes
			arrOverHashes.push(hash(arrHashes[i] + arrHashes[hash2_index]));
		}
		arrHashes = arrOverHashes;
	}
	return arrHashes[0];
}

function verifyMerkleProof(element, proof){
	// Node-as-Leaf issue might matter in some cases
	try {
		var index = proof.index;
		var the_other_sibling = hash(element);
		for (var i = 0; i < proof.siblings.length; i++) {
			// this also works for duplicated trailing nodes
			if (index % 2 === 0)
				the_other_sibling = hash(the_other_sibling + proof.siblings[i]);
			else
				the_other_sibling = hash(proof.siblings[i] + the_other_sibling);
			index = Math.floor(index / 2);
		}
		return (the_other_sibling === proof.root);
	}
	catch (e){
		return false;
	}
}
