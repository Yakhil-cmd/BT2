### Title
Unauthorized/unsigned `stack-stx` lock of a victim's STX via attacker-forged `PreStxOp` output address and self-registered signer-key authorization — ([File: stackslib/src/chainstate/burn/operations/stack_stx.rs])

### Summary
`PreStxOp::parse_from_tx` derives the `output` (later used as `sender`/`tx-sender`) solely from the first output's Bitcoin `P2PKH` hash160, which anyone can construct without owning the corresponding private key. Combined with pox-4's `signer-key-authorizations` map being keyed only on `{pox-addr, period, reward-cycle, topic, signer-key, auth-id, max-amount}` (never on the stacker/sender), an attacker can self-register a signer-key authorization and then submit a `PreStxOp`/`StackStxOp` pair, funded entirely by their own BTC, that locks a victim's real STX balance for a reward address and signer key the attacker chose — with zero signature or action from the victim.

### Finding Description
The broken equality: **AUTHORITY** — "every stacking action == one the staker or their signer signed for exactly those parameters" is violated because `sender`/`tx-sender` for `stack-stx` comes purely from a Bitcoin output address the attacker chooses, and the "signer authorization" check is not scoped to that sender at all.

Code path:
1. `PreStxOp::parse_from_tx` reads only `outputs.get(0)....address` and converts it to a `StacksAddress` — no signature or input-key relationship to that output is required [1](#0-0) .
2. `burnchain.rs::classify_transaction` sets `sender = &pre_stack_stx.output` and feeds it into `StackStxOp::from_tx` as the op's `sender` [2](#0-1) .
3. `StacksChainState::process_stacking_ops` executes pox-4's `stack-stx` directly via `run_contract_call` with `&sender.clone().into()` as the origin/`tx-sender`, and `collect_pox_4_stacking_args` always injects `signer-sig = Value::none()` [3](#0-2) [4](#0-3) .
4. `pox-4.clar::stack-stx` only checks `tx-sender`'s balance (`stx-get-balance tx-sender`) and calls `consume-signer-key-authorization`/`verify-signer-key-sig`, which, with `signer-sig = none`, falls back to `map-get? signer-key-authorizations {pox-addr, reward-cycle, period, topic, signer-key, auth-id, max-amount}` — a map with **no sender/stacker field** [5](#0-4) [6](#0-5) .
5. `set-signer-key-authorization` only requires `tx-sender` to own `signer-key` (`principal-construct? (hash160 signer-key) == tx-sender`) — the attacker trivially satisfies this using their own key/account, and the resulting authorization entry is reusable by any `tx-sender` [7](#0-6) .

Exploit flow: attacker calls `set-signer-key-authorization` from their own account with their own `signer-key`, for `pox-addr` = attacker's own reward address, chosen `period`/`reward-cycle`/`auth-id`/`max-amount`. Attacker then crafts a `PreStxOp` Bitcoin transaction whose first output's hash160 equals the victim's `StacksAddress` hash160, funded/spent entirely with attacker BTC, and a `StackStxOp` spending the `PreStxOp`'s second (attacker-controlled) output, naming `stacked_ustx` ≤ victim balance and ≤ `max-amount`, `num_cycles = period`, `signer_key` = attacker's registered key, `reward_addr` = attacker's own address. When processed, `tx-sender` in the Clarity call equals the victim's address, the balance check passes against the real victim balance, and the signer-key authorization check passes because it was never bound to the victim. `pox_lock_v4` then locks the victim's real STX and the PoX reward slot/weight is credited to the attacker's chosen reward address.

No existing guard (`check-caller-allowed`, `get-stacker-info`, `get-check-delegation`, `verify-signer-key-sig`, the `<=` max-amount check) prevents this, because none of them tie the authorization or the `sender` field back to a signature from the victim's key — the entire mechanism assumes `PreStxOp.output` proves key ownership, which it does not (a Bitcoin P2PKH output only needs a hash160, not a signature).

### Impact Explanation
The victim's unlocked STX is locked into PoX for `num_cycles` without any authorization from the victim (unsigned stacking action / temporary freezing of staked funds), and the associated reward slot/weight and its Bitcoin-denominated PoX rewards are directed to an address chosen entirely by the attacker (reward-slot hijack/theft), while the attacker spends no STX of their own — only Bitcoin transaction fees. This is repeatable against any address whose owner has an unlocked STX balance and is not currently stacking, for the cost of two cheap Bitcoin transactions and one Clarity contract call per attack, matching Critical/High severity (unsigned stacking action, temporary freezing of staked STX, hijacked reward slot value).

### Likelihood Explanation
Preconditions are easily met and fully attacker-controlled: the attacker needs only (a) enough STX/gas to call `set-signer-key-authorization` once from their own account, (b) minimal BTC to submit the `PreStxOp`/`StackStxOp` pair, and (c) knowledge of the victim's public `StacksAddress` (trivially public). No victim cooperation, no privileged role, and no reentrancy/pause/prepare-phase interaction is needed — this is a straightforward, repeatable operation for every reward cycle and every unlocked victim address.

### Recommendation
Bind `signer-key-authorizations` (and its consumption) to the stacker (`tx-sender`)—not just `pox-addr`/`period`/`reward-cycle`/`topic`/`signer-key`/`auth-id`/`max-amount`—so that an authorization created by a signer cannot be redeemed for an arbitrary, unrelated stacker. Additionally/alternatively, require that burnchain-native `StackStxOp`s only be honored when `signer-sig` (a real signature over the stacking parameters) is supplied and verified, rather than silently defaulting to `Value::none()` in `collect_pox_4_stacking_args`, and/or require cryptographic proof that the `PreStxOp` output address's private key participated in signing the burn transaction before treating it as an authorized `sender`.

### Proof of Concept
Rust integration test (e.g. extending `stackslib/src/chainstate/stacks/boot/pox_4_tests.rs` or a `nakamoto_integrations.rs`-style burnchain-ops test):
1. Boot a chainstate/peer with a funded "victim" `StacksAddress` V (STX balance ≥ threshold, not currently stacking, no delegation).
2. As "attacker" account A (separate STX/BTC keys), call `set-signer-key-authorization` with `pox-addr` = attacker's BTC address, chosen `period`, `reward-cycle` = current, `topic = "stack-stx"`, `signer-key` = attacker's own pubkey, `allowed = true`, `max-amount`, `auth-id`. Assert `(ok true)`.
3. Construct a `PreStxOp` Bitcoin tx whose first output's hash160 == `hash160(V)`, second output attacker-controlled, funded by attacker's own UTXOs only.
4. Construct a `StackStxOp` Bitcoin tx spending the `PreStxOp`'s second output, with `stacked_ustx` ≤ V's balance and ≤ `max-amount`, `num_cycles = period`, `signer_key` = attacker's key, `reward_addr` = attacker's address, `auth_id` matching step 2.
5. Mine the block containing both ops; run `process_stacking_ops`.
6. Assert: before, `stx-account(V).locked == 0`; after, `stx-account(V).locked == stacked_ustx` and `stacking-state{stacker: V}.pox-addr == attacker's reward address`, while V never signed any Stacks transaction and the attacker's Stacks/BTC keys never touched V's private key.
