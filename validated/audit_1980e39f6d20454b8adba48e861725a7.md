### Title
Webhook signature verified against attacker's own GitHub organization is not bound to the repository the payload actually mutates, allowing cross-organization CI status forgery and unauthorized deploys - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/handler.rb], [File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` authenticates a webhook by looking up the GitHub App/`webhook_secret` for the organization named in the payload itself (`repository.owner.login`, falling back to `organization.login`), then checks the HMAC signature against that org's secret. Downstream handlers, however, act on data taken from unrelated fields of the same attacker-controlled payload — `Handler#repository_name` uses `payload.dig('repository', 'full_name')`, and `StatusHandler` doesn't scope by repository at all. Because Shipit explicitly supports multiple independent GitHub organizations each with its own `webhook_secret`, an attacker who controls (or has installed the Shipit GitHub App on) their **own** organization can produce a validly-signed webhook whose repository-identifying fields point at a **different, victim** organization/repository, letting them forge CI check statuses or push events against stacks they do not own.

### Finding Description
`verify_signature` resolves the signing secret using only the org name asserted in the JSON body: [1](#0-0) [2](#0-1) 

`Shipit.github(organization: ...)` looks up a per-organization config (`app_id`, `installation_id`, `webhook_secret`) as documented for multi-org installs, and `verify_webhook_signature` just HMAC-verifies the raw payload against that org's `webhook_secret`: [3](#0-2) 

Nothing ties the *organization used for verification* to the *repository the handler subsequently writes to*. `Handler#repository_name`/`#stacks` re-derives the target repository from `repository.full_name` in the same attacker-supplied payload, independent of the `repository.owner.login`/`organization.login` value used for signature lookup: [4](#0-3) 

Worse, `StatusHandler#process` doesn't scope by repository at all — it matches purely on commit SHA across the entire Shipit instance: [5](#0-4) 

`PushHandler#process` similarly resolves stacks via `stacks` (i.e., via `repository.full_name`) but that field is never cross-checked against the org whose secret validated the signature: [6](#0-5) 

**Binding broken (equality that should hold but doesn't):**
`organization authenticated by verify_signature (repository.owner.login / organization.login)` == `repository/commit actually mutated by the handler (repository.full_name / commit SHA lookup)`

Before the attack: for legitimate GitHub-delivered webhooks, these two values are always consistent because GitHub itself populates both fields from the same real repository. After the attack: an attacker forges a JSON body where the signature-verification field names their own org (whose `webhook_secret` they possess by having installed the app on their own org, as per the documented multi-org support in `config/secrets.development.example.yml`), while the repository/commit-affecting fields name a victim repository/commit that is completely unrelated to that org.

### Impact Explanation
This is a High/Critical-classed issue per the rules ("unauthorized deploy, rollback or merge"): using `StatusHandler`, an attacker with a validly signed webhook (from their own organization) can inject a fabricated `success` status for any commit SHA in the system, including SHAs belonging to a victim stack that gates deploys on required CI contexts (`ci.require` in `shipit.yml`). Since `Commit.where(sha: params.sha)` has no repository filter, this bypasses the CI gate entirely for stacks the attacker has no access to, enabling deploy of a commit that never legitimately passed CI. Similarly, `PushHandler` can force `stack.sync_github(expected_head_sha: ...)` on a victim's stack by spoofing `repository.full_name`.

### Likelihood Explanation
Requires the attacker to control/administer their own GitHub organization with the Shipit GitHub App installed (a normal, low-privilege action any org owner can take if the Shipit instance is configured for the documented multi-org mode), which gives them a legitimate `webhook_secret` for computing valid HMAC signatures. No access to the victim org, victim repository, or any Shipit session/API token is required — only crafting a raw HTTP POST to the shared `/webhooks` endpoint.

### Recommendation
Bind the verified organization to the data acted upon: after `verify_signature` succeeds, re-derive `repository_name`/commit scoping strictly from the same `repository.owner.login`/`organization.login` value that was cryptographically verified, and reject the payload if `repository.full_name`'s owner segment does not match the verified organization. In `StatusHandler`, restrict the `Commit` lookup to commits belonging to stacks under the verified organization/repository rather than a bare SHA match across the whole instance.

### Proof of Concept
1. Attacker creates their own GitHub organization `attacker-org` and installs the Shipit GitHub App on it, obtaining a valid `webhook_secret` for `attacker-org` (multi-org config as shown in `config/secrets.development.example.yml`).
2. Attacker crafts a `status` event JSON body:
   ```json
   {
     "sha": "<victim-commit-sha-under-required-ci>",
     "state": "success",
     "context": "ci/circleci",
     "repository": { "owner": { "login": "attacker-org" }, "full_name": "attacker-org/whatever" }
   }
   ```
3. Attacker computes `X-Hub-Signature: sha1=HMAC(attacker-org-webhook-secret, body)` and POSTs to `/webhooks` with `X-Github-Event: status`.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: 'attacker-org')` and successfully verifies the signature against the attacker's own secret.
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)` and finds and updates the **victim's** commit's status to `success`, regardless of which org verified the signature — potentially unblocking a deploy gated by `ci.require`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
