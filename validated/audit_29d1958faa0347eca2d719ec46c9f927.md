### Title
Rounding drift in per-recipient headers-commission split allows systematic supply inflation - (File: `headers_commission.js`)

### Summary
`earned_headers_commission_recipients` lets any unit author split the headers commission it wins into shares for multiple addresses. The percentage shares must sum to exactly 100 (enforced in `validation.js`), but the actual byte amount each recipient receives is computed by rounding each share independently (`Math.round(full_amount * share / 100.0)` in JS, `ROUND(...)` in the MySQL variant). Because rounding is applied per-recipient instead of once on the whole pool with a remainder distributed deterministically, the sum of the rounded amounts can exceed the original `headers_commission` fee that was actually deducted from the payer unit. This is the same class of bug as the referenced Ajna report: individually-rounded shares of a fixed pool do not necessarily reconstitute the original total, and the excess is silently credited as new spendable balance.

### Finding Description
Any unit author (even a single-authored unit) may optionally include `earned_headers_commission_recipients`, an array of `{address, earned_headers_commission_share}` whose shares must be positive integers summing to exactly 100: [1](#0-0) 

There is no requirement that recipients correspond to unit authors, and no count limit tied to `MAX_AUTHORS_PER_UNIT`, so an attacker fully controls the list of recipient addresses and their share percentages. [2](#0-1) 

When this unit later wins headers commission from an included parent unit, `calcHeadersCommissions` splits the parent's fixed `headers_commission` byte-fee (`full_amount`) among the recipients by rounding each share independently: [3](#0-2) 

The MySQL code path performs the identical per-row rounding: [4](#0-3) 

The resulting rounded contributions are aggregated (summed) into `headers_commission_outputs`, which is the ledger of genuinely spendable balances: [5](#0-4) 

These outputs are later consumed as real `type: "headers_commission"` payment inputs and validated/credited at face value, with no cross-check against the original fee amount actually paid by the payer unit: [6](#0-5) [7](#0-6) 

Because each of the `n` recipient shares is rounded independently, the aggregate rounding error can be as large as roughly `n/2` bytes per winning unit, biased in either direction depending on the fractional parts of `full_amount * share_i / 100`. An attacker who controls the recipient list can choose shares (and, since they control many candidate units, effectively sample over `headers_commission` values) to consistently bias the rounding upward, extracting more bytes than were ever deducted from the payer.

### Impact Explanation
`headers_commission_outputs` amounts become spendable bytes with no source input backing the excess — this is a direct, deterministic supply-inflation vector: total credited headers-commission bytes network-wide can permanently exceed the sum of `headers_commission` fees actually paid by unit authors, violating the fixed `TOTAL_WHITEBYTES` invariant. Every full node computes the same over-credited amount deterministically from consensus data, so the excess bytes are treated as legitimate and spendable, and the divergence accumulates unit after unit as attacker units keep winning headers commission with rigged recipient splits.

### Likelihood Explanation
This requires no special privilege — any address can post an ordinary unit (single- or multi-authored) with a custom `earned_headers_commission_recipients` array, and simply needs it to occasionally be selected as the "winner" child unit for a parent's headers commission (a routine, permissionless event determined by hash tie-break in `getWinnerInfo`). Repeating this over many units accumulates a small but real per-unit surplus, making the attack cheap, repeatable, and consensus-safe (all nodes derive the same, inflated result).

### Recommendation
Do not round each recipient's share independently. Instead, compute recipient amounts using an integer-safe remainder distribution: allocate `floor(full_amount * share / 100)` to each recipient, then deterministically distribute the leftover remainder (`full_amount - sum(floor(...))`) to recipients (e.g., largest-remainder method, sorted by address for determinism) so the total credited never differs from `full_amount`. Apply the same fix in both the SQLite (JS) and MySQL query paths in `headers_commission.js`.

### Proof of Concept
1. Attacker posts a unit (single author is sufficient) with:
```
earned_headers_commission_recipients: [
  {address: "ADDR_A", earned_headers_commission_share: 1},
  {address: "ADDR_B", earned_headers_commission_share: 1},
  {address: "ADDR_C", earned_headers_commission_share: 98}
]
```
This passes validation since shares are positive integers summing to 100 (`validation.js:1101-1126`).
2. Suppose this unit wins headers commission from a parent whose `headers_commission = 150` (a real, deterministically-computed header byte size).
3. `calcHeadersCommissions` computes:
   - ADDR_A: `Math.round(150*1/100) = Math.round(1.5) = 2`
   - ADDR_B: `Math.round(150*1/100) = 2`
   - ADDR_C: `Math.round(150*98/100) = 147`
   - Sum credited = `2+2+147 = 151`, i.e. `1` byte more than the `150` actually reserved from the payer unit.
4. This `151` is summed into `headers_commission_outputs` (`headers_commission.js:221-226`) and later spent as normal, fully-backed bytes via a `headers_commission` payment input (`validation.js:2582-2599`), which any node accepts because it recomputes the same (inflated) figure deterministically.
5. Repeating this with carefully chosen recipient counts/shares across many units the attacker manages to "win" produces a steady, permanent, network-wide excess of spendable bytes beyond `TOTAL_WHITEBYTES`.

function validateHeadersCommissionRecipients(objUnit, cb){
	if (objUnit.authors.length > 1 && typeof objUnit.earned_headers_commission_recipients !== "object")
		return cb("must specify earned_headers_commission_recipients when more than 1 author");
	if ("earned_headers_commission_recipients" in objUnit){
		if (!isNonemptyArray(objUnit.earned_headers_commission_recipients))
			return cb("empty earned_headers_commission_recipients array");
		var total_earned_headers_commission_share = 0;
		var prev_address = "";
		for (var i=0; i<objUnit.earned_headers_commission_recipients.length; i++){
			var recipient = objUnit.earned_headers_commission_recipients[i];
			if (!isPositiveInteger(recipient.earned_headers_commission_share))
				return cb("earned_headers_commission_share must be positive integer");
			if (hasFieldsExcept(recipient, ["address", "earned_headers_commission_share"]))
				return cb("unknown fields in recipient");
			if (!isValidAddress(recipient.address))
				return cb("invalid recipient address checksum");
			if (recipient.address <= prev_address)
				return cb("recipient list must be sorted by address");
			total_earned_headers_commission_share += recipient.earned_headers_commission_share;
			prev_address = recipient.address;
		}
		if (total_earned_headers_commission_share !== 100)
			return cb("sum of earned_headers_commission_share is not 100");
	}
	cb();
}

function calcEarnings(conn, type, from_main_chain_index, to_main_chain_index, address, callbacks){
	var table = type + '_outputs';
	conn.query(
		"SELECT SUM(amount) AS total \n\
		FROM "+table+" \n\
		WHERE main_chain_index>=? AND main_chain_index<=? AND +address=?",
		[from_main_chain_index, to_main_chain_index, address],
		function(rows){
			var total = rows[0].total;
			if (total === null)
				total = 0;
			if (typeof total !== 'number')
				throw Error("mc outputs total is not a number");
			callbacks.ifOk(total);
		}
	);
