### Title
Non-Standard NEP-141 Response Causes Silent Loss of Attached Deposit in `nep_141_storage_balance_callback` - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The Wallet Contract's ERC-20 emulation path assumes that any NEP-141 token contract it calls via `storage_balance_of` will always return a value that deserializes into `Option<StorageBalance>`. If the token returns something else (a non-standard/non-compliant response, analogous to USDT's non-standard `transfer()` behavior for `IERC20`), the callback bails out with an error but — unlike the sibling failure path in `rlp_execute_callback` — never refunds the `caller_deposit` that was tracked specifically to cover this situation.

### Finding Description
`inner_rlp_execute` builds a `CallerDeposit` from the attached deposit whenever an external (non-self) predecessor calls `rlp_execute` [1](#0-0) . The doc comment on `CallerDeposit` states explicitly: "This allows us to refund the caller's deposit if the cross-contract call fails" [2](#0-1) .

For `ERC20Transfer` emulation, the contract first calls the target NEP-141 token's `storage_balance_of` and routes the result to `nep_141_storage_balance_callback` [3](#0-2) . Inside that callback, the `PromiseResult::Successful` branch attempts `serde_json::from_slice(&value)` into `Option<StorageBalance>`; if this fails (e.g., because the target contract is not a standard NEP-141 implementation and returns an unexpected JSON shape, or no meaningful value at all), the function immediately returns an `ExecuteResponse` with an error and **does not use `caller_deposit` to issue any refund**: [4](#0-3) 

This is inconsistent with the designed failure-handling path in `rlp_execute_callback`, where a `PromiseResult::Failed` explicitly triggers a refund transfer back to the `caller_deposit.account_id`: [5](#0-4) 

The same unrefunded pattern also exists in the analogous deserialization-failure branch of `address_check_callback` [6](#0-5) , though `caller_deposit` handling there is less directly implicated.

This maps to the same bug class as the external report: code assumes an external, third-party contract will always conform to a standard interface/response format, and does not defensively handle the (very reachable, non-malicious) case where it doesn't — resulting in silent loss of user funds rather than a graceful revert-with-refund.

### Impact Explanation
Any unprivileged account can hold an eth-implicit Wallet Contract and issue an `ERC20Transfer`-emulated transaction (or have a relayer submit one on their behalf) targeting any NEP-141-named `target` account. If that target account is a contract that does not return the exact standard `storage_balance_of` response shape (deployed by any third party, no cooperation from a validator or node operator required), the attached deposit that was meant to be refundable is retained by the Wallet Contract instead of being returned to the caller. This is an unauthorized/incorrect balance outcome for an unprivileged, permissionless transaction flow — funds that should be refunded are effectively lost to the caller.

### Likelihood Explanation
Reaching this path only requires: (1) an eth-implicit Wallet Contract deployed on NEAR (a supported production feature), and (2) sending an RLP-encoded ERC-20 `transfer` calldata whose `target` is some account whose `storage_balance_of` method does not return the exact expected NEP-141 JSON shape. No validator, relayer collusion, or privileged role is needed — the target contract need not even be malicious, just non-conformant (the exact class of "non-ERC20/NEP-141-compliant token" scenario highlighted by the source report). This makes the trigger condition realistically reachable from ordinary transaction submission.

### Recommendation
In `nep_141_storage_balance_callback`, treat a malformed/unexpected `storage_balance_of` response the same way `PromiseResult::Failed` and `rlp_execute_callback`'s failure branch are treated: issue a refund transfer to `caller_deposit.account_id` for `caller_deposit.yocto_near` before returning the error `ExecuteResponse`. The same review should be applied to `address_check_callback`'s deserialization-failure branch to ensure any attached deposit tracked for refund purposes is consistently returned to the caller whenever the flow terminates in an error state.

### Proof of Concept
1. Deploy a Wallet Contract for an eth-implicit account `E` and fund it.
2. Have an external (non-self) predecessor call `rlp_execute` with `target` set to a deployed "fake NEP-141" contract whose `storage_balance_of` method returns `"not-a-storage-balance"` (or any payload that fails to deserialize as `Option<StorageBalance>`), with calldata encoding an ERC-20 `transfer` selector, and attach a deposit `> 0`.
3. `inner_rlp_execute` builds `Some(CallerDeposit { account_id: predecessor, yocto_near })` per `runtime/near-wallet-contract/implementation/wallet-contract/src/types.rs` lines 180-191, and routes to `nep_141_storage_balance_callback` per `lib.rs` lines 433-457.
4. The token's `storage_balance_of` call succeeds but its result fails `serde_json::from_slice` into `Option<StorageBalance>`, hitting `lib.rs` lines 211-220, returning an error `ExecuteResponse` with `success: false` and no refund promise created.
5. Observe the predecessor's attached deposit is retained by the Wallet Contract permanently, whereas an equivalent failure via `PromiseResult::Failed` in `rlp_execute_callback` (lines 296-312) would have refunded it.
