This confirms the finding. `Handler#stacks` scopes lookups to the webhook payload's `repository.full_name` via `Repository.from_github_repo_name` [1](#0-0) , and `PushHandler`/`CheckSuiteHandler` correctly use this scoped `stacks` before touching any commit [2](#0-1) [3](#0-2) . `StatusHandler#process`, however, queries `Commit.where(sha: params.sha)` with no repository scoping at all [4](#0-3) , and `verify_signature` in `WebhooksController` only checks the signature against the app keyed by `repository_owner`, never that the *commit being mutated* belongs to that same repository [5](#0-4) . Additionally, when Shipit is configured with the (documented, default) single-app schema, `Shipit.github(organization:)` ignores the `organization` argument entirely and returns the same app/secret for every repository [6](#0-5) , so one webhook secret can validly sign events for many unrelated repositories that the App is installed on.

### Title
Cross-repository Status forgery via unscoped `Commit.where(sha:)` lookup in `StatusHandler` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` writes a GitHub commit status onto any local `Commit` row matching `params.sha`, with no check that the webhook's `repository.full_name` matches the commit's stack/repository. Because SHA1 commit hashes are content-addressed (not repository-scoped), and because a validly-signed webhook only proves authenticity of the *sending* repository/app-installation, an attacker who controls a commit-status-writable repository (repo A) can emit a legitimately-signed `status` webhook carrying a sha identical to an unrelated stack B's PR head commit, causing Shipit to record a forged `success` status against stack B's commit.

### Finding Description
The broken binding: the question posits that "mergeability determined by `MergeRequest::StatusChecker` must be computed solely from statuses authorized under stack B's own repository signature," i.e. `Status.stack_id == MergeRequest.stack_id ⇒ Status.repository == MergeRequest.stack.repository`. This binding is violated because `StatusHandler` never enforces the right-hand side.

Path: `POST /webhooks` with `X-Github-Event: status` → `WebhooksController#verify_signature` picks the app via `Shipit.github(organization: repository_owner)` and verifies the HMAC over the raw body using that app's `webhook_secret` [7](#0-6)  — this only proves "this payload was really sent by an installation of app X for repo A," not "this sha belongs to repo A." → `Webhooks.for_event('status')` dispatches to `Handlers::StatusHandler` [8](#0-7)  → `StatusHandler#process` does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [4](#0-3) , an *unscoped, cross-stack, cross-repository* lookup. Compare with `PushHandler` and `CheckSuiteHandler`, which both filter through `stacks` (scoped to `payload.dig('repository','full_name')`) before touching any commit [1](#0-0) [2](#0-1) [3](#0-2)  — `StatusHandler` is the sole handler that skips this scoping.

`Commit#create_status_from_github!` then writes into `commit.statuses` using `commit.stack_id`, the real stack B [9](#0-8) , and `add_status` schedules `stack.schedule_merges` when the new status is `success` [10](#0-9) . `MergeRequest#any_status_checks_failed?`/`#any_status_checks_missing?` read `head.statuses_and_check_runs` for stack B's head commit [11](#0-10) , so the forged status directly flips `reject_unless_mergeable!` from rejecting to allowing `merge!`, which then calls the real `stack.github_api.merge_pull_request(stack.github_repo_name, number, ...)` against stack B's repository [12](#0-11) .

Attacker request/PR: attacker owns a repository A on which the Shipit GitHub App is installed (any user can install a public GitHub App on their own repo — this is self-service and requires no Shipit privilege). They reconstruct an identical git commit object (same tree, parents, author/committer identity and timestamps, message — all public via GitHub's API/UI for stack B's target PR head) inside repo A, giving it the identical SHA1 as stack B's PR head. They then set a `success` commit status on that sha in repo A (using their own write access there), which GitHub delivers as a real, correctly-signed `status` webhook to Shipit's `/webhooks` endpoint. `verify_signature` passes (real signature, real installation, possibly even the same shared app-level `webhook_secret` if Shipit uses the common single-app config, per `Shipit.github` ignoring the `organization` parameter in that mode) [6](#0-5) . `StatusHandler` then finds and mutates stack B's commit purely by sha match, with no verification that `payload['repository']['full_name']` corresponds to stack B's repository.

Existing guards fail specifically because: `verify_signature` authenticates the *sender* (repo A/its app installation), not the *target record being mutated*; `ExplicitParameters` schema only validates payload shape, not authorization scope [13](#0-12) ; and `StatusHandler`, unlike its sibling handlers, never calls `stacks`/`Repository.from_github_repo_name` to restrict the lookup.

### Impact Explanation
A forged `success`/`failure`/`error` `Status` record is written against an arbitrary stack's commit that the attacker does not control, without ever authenticating against that stack's actual repository. For a `MergeRequest`, this directly manipulates `reject_unless_mergeable!` and enables `merge!`'s real `stack.github_api.merge_pull_request` call, i.e., an unauthorized merge triggered on fabricated CI state — one repository's webhook mutating another repository's stack/commit/merge outcome. This is repeatable against any stack whose commit sha the attacker can reproduce/predict (any public PR head), and blast radius spans every stack reachable by the shared app installation/webhook secret. This matches "Critical: a payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy, rollback or merge."

### Likelihood Explanation
Preconditions: attacker needs (a) write/status access to some repository where the relevant Shipit GitHub App is installed (self-serviceable if the app is public, or achievable with any repo they already have push access to under an org sharing Shipit's webhook secret), and (b) the ability to reconstruct a git commit object byte-identical to the target's PR head commit sha — feasible because git commit metadata (tree, parents, author/committer identity+timestamps, message) for public PRs is fully visible via the GitHub API, so duplicating it in another repo yields the identical SHA1 deterministically, no hash break required. No Shipit session, API token, or secret is needed. This is a real authentication/authorization-scope bug in the engine's own webhook handler dispatch, not a theoretical hash collision.

### Recommendation
Scope `StatusHandler#process` to the webhook's own repository the same way `PushHandler`/`CheckSuiteHandler` do: resolve `stacks` via `Repository.from_github_repo_name(payload.dig('repository','full_name'))` and only update commits belonging to those stacks (i.e. `stacks.flat_map(&:commits).where(sha: params.sha)` or equivalent `Commit.where(sha: params.sha, stack: stacks)`), rejecting/ignoring status events whose declared repository does not own the matched commit's stack.

### Proof of Concept
```ruby
# test/models/webhooks/handlers/status_handler_cross_repo_test.rb
require 'test_helper'

module Shipit
  class StatusHandlerCrossRepoTest < ActiveSupport::TestCase
    test "status webhook from repo A cannot mark stack B's commit as successful" do
      stack_b = shipit_stacks(:shipit) # belongs to repo B, e.g. "shopify/shipit-engine"
      pr = shipit_merge_requests(:shipit_pending) # pending MR on stack B
      shared_sha = pr.head.sha

      # Simulate attacker's repo A sending a validly-parsed status payload
      # with stack B's exact sha (collision via identical commit reconstruction)
      payload = {
        'sha' => shared_sha,
        'state' => 'success',
        'context' => 'ci/attacker',
        'repository' => { 'full_name' => 'attacker-org/unrelated-repo' } # repo A, not stack_b.repository
      }

      assert_difference -> { pr.head.statuses.count }, 1 do
        Shipit::Webhooks::Handlers::StatusHandler.call(payload)
      end

      refute_predicate pr, :any_status_checks_failed? # forged success now visible on stack B's commit

      Shipit.github.api.expects(:merge_pull_request).once
      pr.stubs(:merge_conflict?).returns(false)
      pr.stubs(:stale?).returns(false)
      assert_equal false, pr.reject_unless_mergeable!
      pr.merge! # proceeds to call github_api.merge_pull_request for stack B's real repo
    end
  end
end
```
Binding checked before/after: `Status.stack_id == pr.stack_id` (true, expected) vs. `Status.repository == pr.stack.repository` (false — the status originated from `attacker-org/unrelated-repo`, not stack B's repository) — the two sides diverge, confirming the vulnerability.
