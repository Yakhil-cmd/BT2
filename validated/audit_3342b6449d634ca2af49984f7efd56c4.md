## Finding: Arbiter contract shared-address definition permanently bakes in a mutable ArbStore payout address

### Title
Shared address definition bakes in a permanently cached ArbStore payout address that can diverge from the fresh address used to pay it, permanently freezing contract funds - (File: arbiter_contract.js)

### Summary
`arbiter_contract.js`'s `deriveSharedAddress()` builds the multisig definition of an arbiter-contract's shared address by embedding the ArbStore's payout address as a hard "has output" spending condition. That address is obtained from `arbiters.getArbstoreInfo()`, which caches the value **forever** in the in-memory `arbStoreInfos` map. Later, when the contract is settled in `complete()`, the actual payment output is sent to a **separately and freshly fetched** address, `objContract.arbstore_address`, obtained via `fillArbstoreAddresses()`/`getArbstoreAddresses()` (a distinct hub lookup, not cached). Because the shared address is immutable (its address is the hash of its definition, exactly like `UXDToken`'s immutable `controller`), any divergence between these two independently sourced "arbstore address" values makes the spending condition permanently unsatisfiable, freezing the funds already deposited to the shared address with no possible remediation.

### Finding Description
`deriveSharedAddress()` calls `arbiters.getArbstoreInfo(contract.arbiter_address, ...)`: [1](#0-0) 

`getArbstoreInfo` caches the arbstore's `info.address` (and `cut`) in the module-level `arbStoreInfos` object and reuses this cached value for the lifetime of the process, with no invalidation or refresh path: [2](#0-1) 

That cached `arbstoreInfo.address` is baked directly into the shared address's oscript definition as a hard spending condition when the non-payer offeror/acceptor branch is built: [3](#0-2) 

This `arrDefinition` is hashed to derive the immutable `shared_address` and stored via `wallet_defined_by_addresses.createNewSharedAddress`: [4](#0-3) 

Separately, when the contract is completed, `complete()` fills `objContract.arbstore_address` through `fillArbstoreAddresses()`/`getArbstoreAddresses()`, which performs a fresh, uncached lookup via `hub/get_arbstore_address` (a different code path/source than `arbiters.getArbstoreInfo`): [5](#0-4) 

`complete()` then reads the arbstore cut amount from the already-committed shared-address definition, but pays it to `objContract.arbstore_address` (the freshly-fetched value), not to the address baked into the definition: [6](#0-5) 

Because a shared/multisig address in Obyte is content-addressed (the address equals `objectHash.getChash160(arrDefinition)`), the `"has output" ... address: arbstoreInfo.address` condition baked in at contract-creation time can never be modified — there is no analog to a `setController`-style update function. If the ArbStore ever changes its payout address (key rotation, migration, security incident) between contract creation and completion, and the update is only reflected in one of the two divergent lookup paths (the ArbStore's own `/api/get_info` cached in `arbStoreInfos`, versus the hub's `hub/get_arbstore_address` record used to populate `objContract.arbstore_address`), the payment constructed in `complete()` will never satisfy the `has output` condition in the multisig definition.

### Impact Explanation
When the two lookups diverge, the transaction built in `complete()` fails on-chain validation of the shared address's spending condition (the required `"has output"` to the old, immutable `arbstoreInfo.address` is not present). This is not just a failed local attempt — it means the funds already deposited into the shared address by `pay()` become permanently unspendable through the designed "complete" path for that specific contract, since the underlying definition (and thus the exact address that must receive the arbstore cut) can never be altered. This is a fund-freezing vulnerability affecting both counterparties of a private/multisig contract, directly matching the "immutable controller cannot be upgraded" bug class from the report (Medium severity: loss of availability of funds, not directly exploitable for theft, but a hard freeze with no recovery mechanism).

### Likelihood Explanation
This requires no malicious actor: it is triggered by the normal, expected lifecycle event of an ArbStore rotating or updating its payout address (e.g., for security or operational reasons) sometime between when a user creates an arbiter contract (baking the then-current address into an immutable multisig definition) and when the contract is completed. Any long-running wallet process that cached the arbstore info early is especially exposed, since `arbStoreInfos` is never invalidated. This is reachable purely through the standard, unprivileged wallet arbiter-contract flow (`deriveSharedAddress` → `pay` → `complete`), not through any privileged/administrative action.

### Recommendation
- Use a single, consistently-sourced, and refreshed lookup for the ArbStore payout address in both `deriveSharedAddress()` (when baking the spending condition) and `complete()` (when constructing the payout), rather than two independent lookups (`arbiters.getArbstoreInfo` cached forever vs. `getArbstoreAddresses` fetched fresh from the hub).
- Remove or bound the lifetime of the `arbStoreInfos` cache in `arbiters.js` so stale addresses cannot silently diverge from the live registration used elsewhere.
- Consider persisting the exact `arbstoreInfo.address` used at contract-creation time on the `wallet_arbiter_contracts` record (alongside `arbstore_address`), and always reuse that persisted value for the payout in `complete()`, since it is the only address the immutable shared-address definition will ever accept.

### Proof of Concept
1. User A creates an arbiter contract; `deriveSharedAddress()` calls `arbiters.getArbstoreInfo(arbiter_address)`, which fetches and caches `arbstoreInfo.address = ADDR_OLD` from the ArbStore's `/api/get_info`. This address is baked into the shared address's `has output` condition, and the shared multisig address `SA` is derived and funded via `pay()`.
2. Before the contract is completed, the ArbStore rotates its payout address and updates its hub registration (`hub/get_arbstore_address` now returns `ADDR_NEW`), but the wallet process handling the payer's `complete()` call still has `ADDR_OLD` cached in `arbStoreInfos` (used only in step 1, already consumed) — meanwhile `fillArbstoreAddresses()` in `complete()` performs a **fresh** `hub/get_arbstore_address` lookup and populates `objContract.arbstore_address = ADDR_NEW`.
3. `complete()` builds a payment output `{ address: ADDR_NEW, amount: arbstore_amount }`, but the shared address `SA`'s immutable definition requires `{ address: ADDR_OLD, amount: arbstore_amount }` to be present in the outputs.
4. The unit fails validation of the `SA` author's definition (the `has output` condition is unsatisfied); the transaction cannot be posted/accepted, and the funds locked in `SA` cannot be released through the intended completion path — they are frozen.

function getArbstoreInfo(arbiter_address, cb) {
	if (!cb)
		return new Promise(function(resolve, reject){
			getArbstoreInfo(arbiter_address, function(err, info){
				if (err) return reject(err);
				resolve(info);
			});
		});
	if (arbStoreInfos[arbiter_address]) return cb(null, arbStoreInfos[arbiter_address]);
	device.requestFromHub("hub/get_arbstore_url", arbiter_address, function(err, url){
		if (err) {
			return cb(err);
		}
		if (!validationUtils.isNonemptyString(url))
			return cb("invalid url received from hub");
		requestInfoFromArbStore(url+'/api/get_info', function(err, info){
			if (err)
				return cb(err);
			if (!validationUtils.isNonemptyObject(info))
				return cb("invalid info received from arbstore");
			const cut = parseFloat(info.cut);
			if (!info.address || !validationUtils.isValidAddress(info.address) || isNaN(cut) || cut < 0 || cut >= 1) {
				return cb("malformed info received from ArbStore");
			}
			info.url = url;
			arbStoreInfos[arbiter_address] = info;
			cb(null, info);
		});
	});
}

function getArbstoreAddresses(arbiter_address, cb) {
	device.requestFromHub("hub/get_arbstore_url", arbiter_address, function(err, url){
		if (err)
			return cb(err);
		device.requestFromHub("hub/get_arbstore_address", arbiter_address, function(err, arbstore_address){
			if (err) {
				return cb(err);
			}
			httpRequest(url, "/api/get_device_address", "", function(err, arbstore_device_address) {
				if (err) {
					console.warn("no arbstore_device_address", err);
					return cb(err);
				}
				cb(null, { arbstore_address, arbstore_device_address });
			});
		});
	});
}

function fillArbstoreAddresses(objContract, cb) {
	if (!cb)
		return new Promise(resolve => fillArbstoreAddresses(objContract, resolve));
	if (objContract.arbstore_device_address && objContract.arbstore_address)
		return cb();
	getArbstoreAddresses(objContract.arbiter_address, function(err, result) {
		if (err)
			return cb(err);
		var { arbstore_address, arbstore_device_address } = result;
		objContract.arbstore_address = arbstore_address;
		objContract.arbstore_device_address = arbstore_device_address;
		db.query("UPDATE wallet_arbiter_contracts SET arbstore_address=?, arbstore_device_address=? WHERE hash=?", [arbstore_address, arbstore_device_address, objContract.hash], function () { cb(); });
	});
}
