### Title
Webhook signature verification is bound to `repository.owner.login`, but the mutated repository/stack is resolved from the unrelated `repository.full_name` field, allowing cross-organization writes - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/handler.rb`, `app/models/shipit/repository.rb`)

### Summary
In Shipit's multi-tenant "Using Multiple GitHub Applications" mode, a single Shipit instance is configured with a distinct GitHub App (and distinct `webhook_secret`) per onboarded GitHub organization [1](#0-0) . Incoming webhooks are routed to the correct secret using `Shipit.github(organization: repository_owner)` [2](#0-1) , where `repository_owner` is read directly from the untrusted JSON body (`repository.owner.login`, falling back to `organization.login`) [3](#0-2) . Signature validation only proves the payload was HMAC-signed with the secret belonging to whichever organization name is embedded in that field [4](#0-3) .

However, once the signature passes, the event handlers determine *which repository/stack to mutate* using a **different** field from the same untrusted body: `repository.full_name` [5](#0-4) , which is looked up verbatim via `Repository.from_github_repo_name` (splitting on `/`, no ownership cross-check against `repository.owner.login`) [6](#0-5) . Nothing enforces that `repository.full_name`'s owner segment equals `repository.owner.login`.

### Finding Description
The trust binding the code is supposed to enforce is:

```
organization whose secret signed the payload  ==  organization that owns the repository being written to
```

Before the attacker's request: for a legitimate GitHub-originated webhook, `repository.owner.login` and the owner segment of `repository.full_name` are always identical, because GitHub itself populates both fields from the same underlying repository object.

After the attacker's request: an operator/admin of one onboarded organization ("OrgA", with a legitimate `webhook_secret` for OrgA) can POST a hand-crafted JSON body to `/webhooks` where:
- `repository.owner.login = "OrgA"` (used only to select the verifying secret via `repository_owner` in `WebhooksController#verify_signature`)
- `repository.full_name = "OrgB/victim-repo"` (used by `Handler#stacks` / `Repository.from_github_repo_name` to select the mutated `Stack`)

The signature is computed correctly with OrgA's secret over this crafted body, so `verify_webhook_signature` succeeds [7](#0-6) . The handler for the event (e.g. `PushHandler`, `StatusHandler`, `CheckSuiteHandler`) then resolves `stacks`/`repository_name` purely from `repository.full_name`, i.e. `"OrgB/victim-repo"`, and acts on OrgB's stack — an organization whose secret never signed anything [8](#0-7) [9](#0-8) [10](#0-9) .

This is the exact class of bug in the external report: validation checks exist for one attribute of the incoming data ("is this signature valid for *some* org") but omit the check that actually matters ("is this signature's org the *same* org as the data being acted upon"), letting an authenticated-but-wrong-scope actor push a payload that crosses the trust boundary — here, into a different tenant's repository/stack instead of a different blockchain's zetaclient queue.

### Impact Explanation
This breaks the cross-repository/cross-organization isolation that the multi-GitHub-App feature is designed to provide. An org admin who is entitled to configure webhooks only for their own organization can force actions against another tenant's `Stack` on the same Shipit instance: e.g. `PushHandler` invokes `stack.sync_github(expected_head_sha:)` on the victim's stack, `CheckSuiteHandler` schedules `RefreshCheckRunsJob` for the victim's commits, and `StatusHandler` writes fabricated commit statuses (`create_status_from_github!`) onto the victim's commits — all without ever authenticating as, or being invited by, OrgB. This matches the "cross-repository writes" Critical-impact category.

### Likelihood Explanation
Exploitation requires only (a) the Shipit instance to be configured in the multi-org mode described in `docs/setup.md`, and (b) the attacker to be a legitimate operator of any one of the onboarded organizations (which is an expected, unprivileged-relative-to-other-tenants actor, not a privileged Shipit account, GitHub App private key holder, or Shipit session). No repository write access to the victim org, no Shipit `ApiClient` token, and no signature-forgery are needed — the attacker uses their *own* valid secret to sign a body whose declarative "owner" field is spoofed independently of the "full_name" field that actually drives the mutation.

### Recommendation
In `WebhooksController#verify_signature` / `Handler#repository_name`, cross-validate that the owner segment of `repository.full_name` matches `repository.owner.login` (or `organization.login`) used to select the signing organization, and reject the webhook (422) on mismatch. Alternatively, derive the org used for both secret selection and repository lookup from a single canonical field, rather than trusting two independently attacker-suppliable JSON paths to agree.

### Proof of Concept
1. Shipit is configured with multi-org GitHub Apps, including `OrgA` (attacker-controlled, legitimate `webhook_secret_A`) and `OrgB` (victim, hosting stack `OrgB/victim-repo`).
2. Attacker crafts a `push` event body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "OrgA" },
    "full_name": "OrgB/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(webhook_secret_A, body)>` and POSTs it to `/webhooks` with `X-Github-Event: push`.
4. `WebhooksController#verify_signature` resolves `repository_owner` = `"OrgA"`, loads `Shipit.github(organization: "OrgA")`, and the signature check passes [4](#0-3) .
5. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("OrgB/victim-repo")` [5](#0-4)  and calls `stack.sync_github(expected_head_sha: params.after)` on OrgB's stack [8](#0-7)  — an unauthorized cross-organization action triggered entirely with OrgA's own credentials.

    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
