### Title
Aged-but-in-budget secondary oracle leg blends a stale price into the accepted midpoint, letting a borrower over-borrow against inflated collateral - ([File: contracts/price-aggregator/src/engine.rs])

### Summary
The bug class is "an old price is accepted for settlement after a gap, letting a trader evade loss." In XOXNO Lending the analog lives in the dual-source price blend: each leg's staleness is judged only against its own `feed.max_stale_seconds` budget, and when both legs produce readings the accepted price is their midpoint. A secondary (anchor) leg that is many hours old but still inside its configured staleness window is treated as "fresh" and averaged with a live primary, so the blended price can sit materially away from the true market price. The controller's strict price path accepts that blend for health-factor and LTV computations in `borrow`, `withdraw`, and `liquidate`, so an attacker can borrow against collateral valued above the real market value — the mirror image of the report's stop-loss evasion.

### Finding Description
`read_feed` in `contracts/price-aggregator/src/engine.rs` marks a leg stale only when `is_stale(now, timestamp, feed.max_stale_seconds)`, where each `FeedSource` carries its own budget up to `MAX_PRICE_STALE_SECONDS` (93,600 s, 26 h) in `common/src/oracle/observation.rs`. When both legs of a dual-source oracle return readings, the engine blends them into a midpoint within the configured tolerance band and the oracle's sanity band; `Outcome::failure` only rejects when `stale`, `deviation`, a non-positive price, or a sanity-bound violation applies.

Consequence: if the anchor leg's last write is, e.g., 23 h old (within a 24 h `max_stale_seconds`) and the market moved, the blend lands halfway between the stale anchor and the fresh primary. As long as the leg spread stays inside `tolerance_bps`, `valid` is true and the controller accepts it via `force`/`resolve`. `calculate_account_risk_totals` in `contracts/controller/src/risk/totals.rs` then values supply legs at this skewed `feed.price`, and `require_post_pool_risk_gates` in `contracts/controller/src/risk/validation.rs` checks `ltv_collateral >= total_debt` against the inflated valuation — so `borrow`/`withdraw` succeed beyond true capacity.

This is not hypothetical: the repo's own harness test `audit_borrow_withdraw_liquidate_stale_anchor_blends_5pct_skew_into_ltv` (`tests/test-harness/tests/controller/audit_borrow_withdraw_liquidate_stale_anchor_blend.rs`) freezes a RedStone anchor at $1.00 while the true price is $0.91, ages the anchor 82,800 s inside a 86,400 s budget, and asserts (a) collateral valuation inflates >4% versus the honest-anchor control and (b) `try_borrow` of $70,000 succeeds where the control reverts with `InsufficientCollateral`.

### Impact Explanation
An unprivileged account supplies collateral whose oracle blend is skewed by a stale-but-in-budget anchor leg, then calls `borrow` (or `withdraw`, `multiply`, `flash_position`) and extracts more debt than true collateral supports — direct theft of pool funds / protocol insolvency once the blend converges to the real price and the position becomes bad debt. Symmetrically, an underwater borrower whose debt asset has a stale-low anchor blend keeps HF ≥ 1 and evades liquidation, the exact "trader evades loss" outcome of the source report.

### Likelihood Explanation
Requires (a) a dual-source oracle where one provider's update cadence is much slower than the other's within its configured staleness budget (e.g., daily NAV-style or heartbeat feeds at 24–26 h), and (b) a price move that keeps the leg spread inside `tolerance_bps` while still materially skewing the midpoint, and (c) a timing window where the stale write is still accepted. No privileged action needed: the attacker only calls `borrow`/`withdraw`/`liquidate` during the window. Likelihood is low-to-moderate; impact is theft of user funds → Medium/High.

### Recommendation
Bound the age spread between the two legs of a dual-source blend (the `MAX_LEG_AGE_SPREAD_SECONDS` check applied to market-nature legs should cover, or be extended to, any pairing where one leg can be orders of magnitude older than the other), and/or compute the effective staleness of the blend from the oldest leg timestamp rather than each leg's own budget. Alternatively, use the fresher leg (not the midpoint) when leg ages diverge beyond a threshold, and expose the per-leg timestamps in `PriceStatus` so integrators can enforce a maximum observation age at the controller.

### Proof of Concept
The harness test `tests/test-harness/tests/controller/audit_borrow_withdraw_liquidate_stale_anchor_blend.rs` is the executable PoC:

1. Configure XLM with a Reflector primary and a RedStone anchor, `anchor max_stale_seconds = 86_400`, tolerance 1,000 bps.
2. Set the anchor's stored price to $1.00 with a write timestamp `now - 82_800` s (accepted as "fresh"); set the primary to the true price $0.91.
3. `supply(ALICE, XLM, 100_000)` — collateral valued at the ~$0.955 midpoint instead of $0.91 (>4% inflation).
4. `borrow(ALICE, USDC, 70_000)` succeeds; the identical borrow with a fresh $0.91 anchor reverts `InsufficientCollateral`.

Note: I verified the staleness gates (`is_stale`, `Outcome::failure`) and the risk gates (`calculate_account_risk_totals`, `require_post_pool_risk_gates`) directly, and the behavior is demonstrated by the in-repo audit test. One caveat: if the anchor's staleness budget is set so tight that no exploitable lag is possible for a given feed, this vector closes for that market — the exposure is a function of configured `max_stale_seconds` versus the feed's real update cadence.
