### Title
Missing Order Expiry Check Allows Execution of Stale Orders at Outdated Prices - (File: `test/samples/order_book_exchange.oscript`)

### Summary
The order-book exchange Autonomous Agent (AA) template shipped in the ocore repository executes signed limit orders (`trigger.data.order1`/`trigger.data.order2`) without ever validating an expiry/freshness condition on the order, even though the author explicitly flagged this gap with a `// to do check expiry` comment left in the trading logic.

### Finding Description
The AA case that matches and executes two counter-orders reconstructs each order from `trigger.data.order1.signed_message` / `trigger.data.order2.signed_message`, verifies only that the assets are complementary and that the accompanying signature is valid via `is_valid_signed_package`, then immediately proceeds to compute fill amounts and update balances: [1](#0-0) 

The comment `// to do check expiry` sits directly in the validation branch, but no timestamp, expiry field, or `timestamp` builtin check is ever consulted before the trade executes. The order's uniqueness key (`$id1`/`$id2`) is derived purely from `address`, `sell_asset`, `buy_asset`, `sell_amount`, `price`, and `last_ball_unit` — none of which bound how long the signed message remains executable: [2](#0-1) 

`is_valid_signed_package` (implemented in `formula/evaluation.js`) only checks that the signature and, optionally, the `last_ball_unit`'s stability/MC membership are valid — it performs no freshness/expiry enforcement of its own: [3](#0-2) 

`signed_message.validateSignedMessage` similarly only validates authors, definitions and authentifiers; it accepts an optional `timestamp` field but never enforces any expiry semantics on it: [4](#0-3) 

Because the AA neither requires nor checks any expiry claim on the order, a signed order created and shared off-chain (e.g., over a matching relay) remains valid and executable by anyone holding it indefinitely, exactly mirroring the vulnerability class described in the external report for Hubble's OrderBook contract.

### Impact Explanation
Any user who signs a limit order for this AA pattern (fixing `price`, `sell_amount`, `sell_asset`, `buy_asset`) is exposed to having that order matched and executed at any future point, no matter how much market conditions have diverged from the original intent. A counterparty (or the AA operator/matcher submitting the trigger) can hold an old, favorable-to-them order and trigger it against the signer's AA balance long after the signer would have wanted it cancelled, extracting value at a stale price. This directly causes unauthorized/unfavorable fund movement out of the signer's balance inside the AA — a concrete fund-loss impact for any deployment based on this reference pattern.

### Likelihood Explanation
Likelihood is high for any real deployment following this documented pattern: the order format and matching logic are provided as-is in the codebase's own oscript sample/test suite (`test/ojson.test.js` parses and validates this exact template), so it is likely to be copied or adapted by AA developers building decentralized exchanges on Obyte. The missing check is trivial to exploit — an attacker (or slow/adversarial matcher) merely needs to withhold submission of a signed order until conditions become unfavorable to the signer, then submit the trigger.

### Recommendation
Add an explicit `expiry_ts` (or similar) field to the signed order message and enforce it in the AA's matching condition, e.g. `AND timestamp <= $order1.expiry_ts AND timestamp <= $order2.expiry_ts`, bouncing/rejecting the trigger if either order has expired. This closes the gap flagged by the existing `// to do check expiry` comment and should be applied to this template before it is used as a basis for production order-book AAs.

### Proof of Concept
1. Alice signs `order1 = {sell_asset: X, buy_asset: Y, sell_amount: 100, price: 1.0, address: Alice}` and shares it with a matching venue, expecting near-term execution at price 1.0.
2. No expiry is enforced by the AA (`test/samples/order_book_exchange.oscript` lines 27-49), so the matcher/venue holds the signed package.
3. Months later, market price of X/Y moves far from 1.0, making the trade highly unfavorable to Alice.
4. Anyone with a complementary order and Alice's still-valid signed package submits `trigger.data.order1`/`order2` to the AA; `is_valid_signed_package` succeeds (signature and last_ball_unit checks pass), the trade executes at the stale price 1.0, and Alice's AA balance is debited at a price she never agreed to at the time of execution.
