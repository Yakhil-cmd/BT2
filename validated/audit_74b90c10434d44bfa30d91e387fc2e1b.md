### Title
Permanent market freeze from `i128` overflow during mandatory interest accrual - (File: `common/src/rates/simulate.rs`)

### Summary
A sufficiently large market can reach a state where converting scaled supply or debt shares into their current RAY value produces a result above `i128::MAX`. Because every pool mutation runs `global_sync` before repayment, withdrawal, liquidation accounting, or index updates, the first such overflow permanently prevents all state-changing operations for that market. [1](#0-0) 

### Finding Description
`accrue_step` begins each compounding interval by calculating `scaled_to_original(borrowed, borrow_index)` and `scaled_to_original(supplied, supply_index)`. [2](#0-1)   
`scaled_to_original` calls `Ray::mul`, whose exact intermediate handling still rejects a final quotient that does not fit `i128` with `MathOverflow`. [3](#0-2) [4](#0-3) 

The configured index ceiling is `MAX_BORROW_INDEX_RAY`, but the representable market-value ceiling is lower: it is reached once approximately `scaled_shares * index / RAY > i128::MAX`. [5](#0-4)   
For example, an 18-decimal deposit of one billion whole tokens creates approximately `1e36` scaled RAY shares; an index above roughly `170.14 * RAY` makes the position value exceed `i128::MAX`. [6](#0-5) 

`global_sync` executes this multiplication before mutating any market operation. [7](#0-6)   
Consequently, after the threshold is crossed, `update_indexes`, `withdraw`, `repay`, liquidation-related pool calls, further borrowing, and other paths loading `synced_market` all revert before their own logic can reduce shares or transfer funds. [8](#0-7) [9](#0-8) [10](#0-9) 

### Impact Explanation
This permanently freezes all supplier principal and accrued yield in the affected `(hub_id, asset)` market and prevents borrowers or third parties from repaying the outstanding debt. [11](#0-10)   
Because the panic occurs during mandatory synchronization, it also prevents liquidation and bad-debt cleanup from reaching the market’s pool state. [12](#0-11)   
The impact is permanent freezing of user funds and can leave the protocol unable to recover or socialize trapped debt.

### Likelihood Explanation
An unprivileged user can establish the vulnerable state through ordinary `supply` and `borrow` calls when the market caps, available token supply, collateral value, and rate model permit the required exposure. [13](#0-12)   
No governance call is needed after the market exists: the attacker supplies a large amount of the target asset, supplies collateral in another market, borrows enough of the target to sustain high utilization, and lets normal interest accrual raise the index until the aggregate RAY value no longer fits `i128`. [14](#0-13)   
The repository’s harness demonstrates this path at 98% utilization and confirms that the borrow index remains below `MAX_BORROW_INDEX_RAY`, proving that the configured index ceiling does not prevent the earlier market-value overflow. [11](#0-10) 

### Recommendation
Do not allow an accrual step to commit an index whose corresponding aggregate supplied or borrowed value cannot be represented in `i128`.

- Before each `accrue_step`, calculate the maximum representable index for the current `borrowed` and `supplied` share counts using widened arithmetic, such as `floor(i128::MAX * RAY / scaled_shares)`.
- Clamp accrual to the smaller safe index and treat that state as an explicit arithmetic ceiling rather than trapping.
- Ensure `update_supply_index`, `calculate_supplier_rewards`, and `supply_index_reward_shortfall` cannot be invoked with an index that would make `supplied * index / RAY` or `borrowed * index / RAY` unrepresentable. [15](#0-14) [16](#0-15) 
- Keep exits and repayments operational at the ceiling instead of requiring another accruing multiplication that can overflow.
- Add invariant tests for each supported decimal count asserting that any committed market state satisfies both `supplied * supply_index / RAY <= i128::MAX` and `borrowed * borrow_index / RAY <= i128::MAX`.

### Proof of Concept
The repository already contains an executable scenario demonstrating the issue. [17](#0-16) 

1. Create an 18-decimal market using the XLM rate curve and a second collateral market.
2. Call:

```text
supply(
  caller = BOB,
  account_id = 0,
  spoke_id = <spoke>,
  assets = [(HubAssetKey { hub_id, asset: BIG18 }, 1_000_000_000 * 10^18)]
)
```

This books approximately `1e36` scaled RAY shares. [18](#0-17) 

3. Supply collateral from `ALICE` and call:

```text
borrow(
  caller = ALICE,
  account_id = <alice_account>,
  borrows = [(HubAssetKey { hub_id, asset: BIG18 }, 980_000_000 * 10^18)],
  to = None
)
```

This leaves the target market at 98% utilization. [19](#0-18) 

4. Advance ledger time and call `update_indexes(caller, [BIG18])` until the next accrual reaches the representable-value boundary. [20](#0-19) 
5. The call fails with `MathOverflow` while `borrow_index < MAX_BORROW_INDEX_RAY`. [21](#0-20) 
6. Afterwards, both `withdraw(BOB, account_id, [(BIG18, 1)], None)` and `repay(<anyone>, ALICE_account, [(BIG18, amount)])` fail with the same error because both load the market through `ops::synced_market` before processing the operation. [22](#0-21) [12](#0-11)

pub fn try_mul_div_half_up(env: &Env, x: i128, y: i128, d: i128) -> Option<i128> {
    if x < 0 || y < 0 || d <= 0 {
        return None;
    }
    let half = d / 2;

    // Fast path: the biased product fits `i128`, so the whole computation is
    // native. `x * y + half` is non-negative here, so `/` is the floor the
    // widened path would produce.
    if let Some(biased) = x
        .checked_mul(y)
        .and_then(|product| product.checked_add(half))
    {
        return Some(biased / d);
    }

    let (x256, y256, d256) = to_i256_operands(env, x, y, d);
    x256.mul(&y256)
        .add(&I256::from_i128(env, half))
        .div(&d256)
        .to_i128()
}
