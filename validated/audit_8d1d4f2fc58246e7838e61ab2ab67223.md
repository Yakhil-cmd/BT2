### Title
Cross-repository commit status forgery via unscoped `StatusHandler` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`Shipit::Webhooks::Handlers::StatusHandler` writes a GitHub `status` webhook payload to `Commit` records looked up **only by SHA**, with no scoping to the repository/organization whose webhook signature was actually verified. Every other handler in the same directory (`PushHandler`, the `PullRequest::*` handlers) resolves the target through `Handler#stacks`, which scopes by `Repository.from_github_repo_name(payload['repository']['full_name'])`. `StatusHandler` skips that scoping entirely, so the binding "organization authenticated by `verify_signature`" ≠ "repository whose commit is actually mutated" is broken.

### Finding Description
`WebhooksController#verify_signature` selects the GitHub App/secret to check based on `repository_owner`, derived from the unverified JSON body, then verifies the raw body's HMAC against that organization's `webhook_secret`: [1](#0-0) 

This only proves the payload was signed by *some* configured organization's secret — it says nothing about which `Stack`/`Repository` the payload is allowed to affect. The base `Handler` class enforces that additional binding for every other event by scoping lookups to the repository named in the payload: [2](#0-1) 

`StatusHandler`, however, resolves its target purely by commit SHA, with no call to `stacks` / `Repository.from_github_repo_name`: [3](#0-2) 

Because `Commit.where(sha: params.sha)` is a global, unscoped query across the whole Shipit install, any organization that Shipit trusts (i.e., has a configured `webhook_secret`/GitHub App) can submit a `status` event for a SHA that happens to exist in a *different* organization's tracked repository (e.g., commits shared through a public fork, cherry-picks, or any commit an attacker can reproduce byte-for-byte, since git object hashes are content-addressed and independent of which repo hosts them). The forged status is then written via `Commit#create_status_from_github!`, which drives Shipit's CI/merge-status/continuous-deployment state for a stack that has nothing to do with the organization that signed the webhook.

Binding broken: `organization authenticated by verify_signature` == `organization owning the repository/stack actually written`, which `StatusHandler` fails to enforce.

### Impact Explanation
An organization that legitimately controls one Shipit-configured GitHub App/webhook secret can inject fabricated commit statuses (success/failure, arbitrary `context`, `description`, `target_url`) onto commits belonging to a completely unrelated stack/repository, as long as it can produce a payload referencing a matching SHA. Since Shipit uses commit statuses to compute `merge_status`, gate CI (`ci.require`), and drive continuous deployment eligibility, this can be leveraged to mark commits on a victim stack as "green" and trigger an unauthorized deploy/rollback path, or conversely poison a victim's CI state — a cross-repository write of security-relevant state that the affected organization never authorized.

### Likelihood Explanation
Exploitability depends on obtaining a SHA that both matches a commit tracked by the victim stack and can be delivered as a signed `status` webhook from an org the attacker controls. This is realistic for public/forked repositories (shared commit history across forks, or intentionally reproduced commit objects with identical author/committer/timestamp/tree/parent) and for any Shipit instance configured with multiple organizations (a documented supported configuration — `config/secrets.development.example.yml` shows the multi-org `github:` schema). No privileged Shipit session or `ApiClient` token is required — only a legitimate webhook delivery for an org the attacker already administers.

### Recommendation
Scope `StatusHandler#process` (and any other handler processing commit-level events) to the repository named in the payload, consistent with `Handler#stacks`/`repository_name`, e.g. restrict the `Commit` lookup to `stacks.find_each { ... }` or join through `Repository.from_github_repo_name(payload.dig('repository','full_name'))` before matching by SHA, rejecting or ignoring statuses whose repository does not match the commit's actual stack/repository.

### Proof of Concept
1. Shipit is configured with two organizations, `victim-org` (hosting the tracked repository/stack) and `attacker-org` (an org the attacker legitimately administers, with its own valid `webhook_secret`).
2. The attacker forks or otherwise obtains a repository containing a commit with the exact same SHA as a commit currently tracked in `victim-org`'s stack (shared ancestry/fork, or a reproduced commit object).
3. Attacker triggers (or crafts, then has GitHub deliver) a `status` webhook from `attacker-org`'s repository for that SHA with `state: success` and a forged `context`/`target_url`.
4. `WebhooksController#verify_signature` validates the HMAC using `attacker-org`'s own `webhook_secret` — verification succeeds because it only checks "is this a genuine `attacker-org` webhook," not "does this event apply to a repository `attacker-org` owns." [1](#0-0) 
5. `StatusHandler#process` matches the commit by SHA across the entire database and writes the forged status onto the `victim-org` commit: [3](#0-2) 
6. The victim stack's CI/merge status is now influenced by data injected by an unrelated organization.
