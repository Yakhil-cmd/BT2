### Title
Unvalidated swap-route venues can execute unauthorized token transfers beneath the caller’s signed authorization tree - ([File: contracts/controller/src/strategies/swap.rs])

### Summary
The controller accepts an opaque user-supplied `swap` payload and forwards it to the configured router during `multiply`, `swap_debt`, `swap_collateral`, and `repay_debt_with_collateral`. [1](#0-0) 

Because route venues are not constrained by the controller, a malicious route can place attacker-controlled contract code on the call stack while the caller’s strategy authorization is active. [2](#0-1) 

That code can request a token transfer from the caller; transaction simulation records it as a child of the caller’s signed strategy authorization, allowing arbitrary wallet tokens to be stolen if the generated authorization tree is signed. [3](#0-2) 

### Finding Description
`swap_collateral` authenticates `caller` once before executing the strategy. [4](#0-3) 

It then forwards the caller-provided `swap` payload through `withdraw_and_swap_from_supply`. [5](#0-4) 

`swap_tokens` invokes the configured router with that payload after authorizing only the controller’s exact input-token transfer; it does not decode venue addresses or restrict which downstream contracts the route may invoke. [6](#0-5) 

The repository’s route model confirms that payload-selected pool and token addresses are not allowlisted and may put third-party code beneath the caller’s authorization. [7](#0-6) 

A malicious venue can therefore call `token.transfer(caller, attacker, amount)`; under Soroban authorization recording, this becomes an additional child authorization attached to the victim’s `swap_collateral` invocation rather than a separate top-level approval. [3](#0-2) 

### Impact Explanation
A malicious route can steal unrelated tokens held directly by the caller, beyond the collateral amount intended for the strategy. [8](#0-7) 

The controller’s measured input/output checks bound only the controller-held swap input and do not prevent an additional authorized transfer from the caller’s wallet. [9](#0-8) 

This affects the user-facing strategy entrypoints that accept opaque route bytes, including `swap_collateral`, `swap_debt`, `multiply`, and `repay_debt_with_collateral`. [10](#0-9) 

### Likelihood Explanation
Exploitation requires the victim to submit a malicious route and sign the authorization tree produced by simulation, so it is not an unauthenticated protocol-wide theft. [11](#0-10) 

The residual risk is nevertheless realistic because route bytes are opaque to the controller and a malicious route producer can cause simulation to append an unexpected wallet-transfer authorization. [7](#0-6) 

The included adversarial test demonstrates that the poisoned simulated tree executes successfully and transfers the victim’s entire unrelated wallet-token balance to the attacker. [11](#0-10) 

### Recommendation
Do not allow strategy routes to invoke arbitrary venue contracts beneath the caller’s authorization. [1](#0-0) 

Constrain every route-selected pool, token, or venue address to a governance-approved allowlist, or execute swaps through a boundary that cannot cause additional authorizations to be attached beneath the user’s strategy invocation. [7](#0-6) 

Clients should also decode routes and reject any simulated authorization tree containing children other than the expected input-token transfer, but route-address validation should be enforced by the contract boundary rather than relying solely on wallet inspection. [12](#0-11) 

### Proof of Concept
The adversarial test registers a router that invokes the route-selected `hop_pool` after receiving the strategy input. [13](#0-12) 

The attacker-controlled pool stores a plan naming the victim, an unrelated wallet token, the attacker recipient, and the amount to steal. [14](#0-13) 

Simulation records the rogue `transfer` as a child of Alice’s `swap_collateral` authorization, and execution leaves Alice with zero wallet tokens while crediting the attacker. [3](#0-2) 

The enforcing test then confirms that the same route succeeds when the poisoned child authorization is signed and fails when it is absent. [15](#0-14)

fn simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry() {
    let s = Scene::new();
    let route = s.route_through_pool_stealing(WALLET_BALANCE);

    // `simulateTransaction` runs recording mode with non-root auth disabled.
    s.t.env.mock_all_auths();
    s.try_swap(&route)
        .expect("recording mode accepts the route");
    let recorded = s.t.env.auths();
    std::println!("recorded auth tree = {recorded:#?}");

    let stolen_transfer = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.wallet_token.clone(),
            symbol_short!("transfer"),
            (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),
        )),
        sub_invocations: std::vec![],
    };
    let poisoned_root = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.t.controller.clone(),
            Symbol::new(&s.t.env, "swap_collateral"),
            s.swap_args(&route),
        )),
        sub_invocations: std::vec![stolen_transfer],
    };
    assert_eq!(recorded, std::vec![(s.alice.clone(), poisoned_root)]);

    assert_eq!(s.wallet(&s.alice), 0);
    assert_eq!(s.wallet(&s.attacker), WALLET_BALANCE);
    assert_eq!(s.t.supply_balance_raw(ALICE, "ETH"), FAIR_OUT_ETH);
}

fn enforced_auth_moves_the_wallet_token_only_when_the_signed_tree_lists_the_rogue_transfer() {
    let s = Scene::new();

    // Control: a pool that touches nothing passes with the honest root-only tree.
    let benign = s.route_through_pool_stealing(0);
    s.try_swap_with_signed_tree(&benign, &[])
        .expect("the honest tree authorizes an honest route");
    assert_eq!(s.wallet(&s.alice), WALLET_BALANCE);

    // Rogue pool, honest tree: the host refuses the transfer and the whole call rolls back.
    s.t.env.mock_all_auths_allowing_non_root_auth();
    let rogue = s.route_through_pool_stealing(WALLET_BALANCE);
    let usdc_before = s.t.supply_balance_raw(ALICE, "USDC");
    let refused = s
        .try_swap_with_signed_tree(&rogue, &[])
        .expect_err("a transfer outside the signed tree is unauthorized");
    std::println!("rogue transfer under the honest tree = {refused:?}");
    assert!(
        refused.is_type(ScErrorType::Auth) || refused.is_type(ScErrorType::Context),
        "expected a host auth failure, got {refused:?}"
    );
    assert!(s
        .diagnostics()
        .contains("Unauthorized function call for address"));
    assert_eq!(s.wallet(&s.alice), WALLET_BALANCE);
    assert_eq!(s.wallet(&s.attacker), 0);
    assert_eq!(s.t.supply_balance_raw(ALICE, "USDC"), usdc_before);

    // Same route, with the tree that simulation returned.
    let stolen_transfer = MockAuthInvoke {
        contract: &s.wallet_token,
        fn_name: "transfer",
        args: (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),
        sub_invokes: &[],
    };
    s.try_swap_with_signed_tree(&rogue, core::slice::from_ref(&stolen_transfer))
