### Title
Cross-organization Team membership escalation via unchecked `team.organization` binding in `MembershipHandler#process` - (File: `app/models/shipit/webhooks/handlers/membership_handler.rb`)

### Summary
`MembershipHandler#process` trusts that the `team.id` in a `membership` webhook belongs to the same organization that signed the request, but it never checks this for teams that already exist in the database. A genuinely-signed webhook from a low-value organization can therefore add an arbitrary GitHub user to a pre-existing high-value `Team` row (e.g. one listed in `Shipit.github_teams`), granting that user Shipit-side authorization they never earned.

### Finding Description
The broken binding, stated explicitly: the code should enforce `params.organization.login == team.organization` for every mutated `Team`, but it only enforces it `team.organization = params.organization.login` inside the `find_or_create_by!` block, which runs **only when the row is newly created**: [1](#0-0) 

`process` then calls `team.add_member(member)` / `team.members.delete(member)` unconditionally, with no re-check that `team.organization` matches the signer: [2](#0-1) 

Signature verification in `WebhooksController#verify_signature` only proves the payload was signed by *some* configured organization — specifically the one derived from `repository_owner`/`organization.login` in the payload: [3](#0-2) [4](#0-3) 

It never cross-checks that org against the `team.id` embedded elsewhere in the same JSON body. `Shipit.github_teams`-based authorization is a simple membership check with no additional organization verification: [5](#0-4) 

**Exploit flow:**
1. High-value `Team` row (e.g., `shopify_developers`, `github_id: X`, `organization: 'shopify'`) already exists from a prior legitimate sync, and is included in `Shipit.github_teams`.
2. Attacker owns/administers a legitimate, low-value GitHub organization (`attacker-org`) that is configured in Shipit (so a real `webhook_secret` exists for it) — attacker is a maintainer there and controls webhook delivery.
3. Attacker crafts and correctly signs a `membership` webhook body with `organization.login: 'attacker-org'`, `member.login: 'attacker'`, but `team.id: X` (the victim team's numeric `github_id`).
4. `verify_signature` computes `repository_owner = 'attacker-org'`, fetches `Shipit.github(organization: 'attacker-org')`, and the HMAC verifies successfully because it is a genuinely attacker-controlled org secret.
5. `MembershipHandler#process` runs: `find_or_create_team!` finds the **existing** victim `Team` by `github_id`, bypassing the `organization =` assignment block entirely.
6. `team.add_member(User.find_or_create_by_login!('attacker'))` inserts a `Membership` linking the attacker's `User` to the victim `Team`.
7. `User#authorized?` for the attacker now returns `true` because their `teams` include an id in `Shipit.github_teams`.

None of the existing guards prevent this: `verify_signature` only authenticates the org that signed, not the resource IDs inside the payload; `drop_unhandled_event` and `ExplicitParameters` schema only validate shape/type of `team.id` (an `Integer`), not ownership; there is no `require_permission!`/scope check tying `team.id` to `params.organization.login` for existing records.

### Impact Explanation
A genuinely-signed webhook from an attacker-controlled, low-privilege GitHub organization mutates `Membership`/`Team` state belonging to a completely different organization. Because Shipit's own authorization model (`User#authorized?`, `Shipit.github_teams`) is driven directly by `Membership` rows, this is a direct authentication/authorization bypass allowing escalation into `Shipit.github_teams`-gated capabilities (deploys, rollbacks, admin actions) without ever compromising GitHub credentials for the victim org, matching the "escalation into `Shipit.github_teams` authorization" and "a payload for one repository/org mutating another's team" severity categories. The attack is repeatable against any known/guessable `github_id` of a `Team` row already present in the database (team IDs are sequential GitHub numeric IDs, often discoverable via public GitHub API), and against any number of attacker-controlled logins, for as long as the attacker's own low-value org remains configured in Shipit.

### Likelihood Explanation
Preconditions: the attacker must control (or be a member/admin of) at least one GitHub organization that is legitimately configured in Shipit with its own webhook secret — a low bar, since Shipit typically onboards many orgs; the victim `Team` row must already exist in Shipit's DB (true for any team that has ever had a membership sync, which is the normal steady state for teams listed in `Shipit.github_teams`). The attacker needs no Shipit session, API token, or GitHub App/webhook secret belonging to the victim org — only the ability to sign a webhook with their own org's secret and knowledge of the victim team's numeric `github_id`. This is low-cost and fully repeatable.

### Recommendation
In `MembershipHandler#process` (and `find_or_create_team!`), always validate that the found/created `Team#organization` equals `params.organization.login` before performing `add_member`/`members.delete`; if they diverge, reject/log the event instead of mutating membership. Additionally, `find_or_create_by!` should validate on every call (not just on creation) that the org matches, e.g. `team = Team.find_or_initialize_by(github_id: params.team.id); raise/reject if team.persisted? && team.organization != params.organization.login`.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (conceptual addition)
test "membership webhook cannot add member to a team belonging to a different organization" do
  victim_team = shipit_teams(:shopify_developers) # exists, organization == 'shopify', in Shipit.github_teams
  attacker_login = 'attacker'

  Shipit.stubs(:github).with(organization: 'attacker-org').returns(
    stub(verify_webhook_signature: true)
  )

  assert_no_difference -> { Membership.where(team_id: victim_team.id).count } do
    post :create, body: {
      action: 'added',
      team: { id: victim_team.github_id, name: victim_team.name, slug: victim_team.slug, url: victim_team.api_url },
      organization: { login: 'attacker-org' },
      member: { login: attacker_login }
    }.to_json, params: {}, headers: { 'X-Github-Event' => 'membership', 'X-Hub-Signature' => 'sha1=valid-for-attacker-org' }
  end

  attacker = User.find_by(login: attacker_login)
  refute attacker&.authorized?, "attacker must not gain authorization via a cross-org signed webhook"
end
```
Binding to assert on both sides: `params.organization.login` (`'attacker-org'`, the verified signer) must equal `victim_team.organization` (`'shopify'`) before any `Membership` row referencing `victim_team` is written; the current code allows the mutation to proceed despite the mismatch, which the fixed code must reject.
