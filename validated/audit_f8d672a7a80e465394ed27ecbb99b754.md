### Title
Malicious counterparty AA can permanently block a lending/escrow AA's repayment step by forcing a secondary-trigger bounce, freezing or misdirecting collateral - (File: aa_composer.js)

### Summary
In the Teller finding, a lender who is an ERC777 hook can revert the borrower's repayment transfer, so the borrower can never mark the loan repaid and is later liquidated. The analogous mechanism in ocore is Autonomous Agent (AA) *secondary triggers*: when a primary AA sends a payment message to an address, and that address is itself an AA, ocore automatically fires that recipient as a secondary trigger within the *same* transaction. If the secondary AA bounces, the entire primary trigger's state changes (not just the payment) are rolled back and bounced, per the `revert()`/`bounce()` logic in `aa_composer.js`.

### Finding Description
When `sendUnit()` finishes composing a response unit, it calls `handleSecondaryTriggers(objUnit, arrOutputAddresses)`, which looks up whether any output address is an AA and, if so, invokes `handleTrigger()` recursively with `bSecondary=true` for each one [1](#0-0) . If any secondary AA bounces, the callback surfaces an error which is propagated up: `if (err) { if (bSecondary) return bounce(err); return revert({message: "one of secondary AAs bounced with error: ", callChain: {address, next: err}}); }` [2](#0-1) .

`revert()` unconditionally discards *all* state variable updates and rolls back balances of the primary AA trigger via `ROLLBACK TO SAVEPOINT initial_balances`, then calls `bounce()` [3](#0-2) . This means: a lending/escrow AA that, in one trigger execution, both (a) forwards a repayment/collateral-release payment to a counterparty address and (b) updates its own state (e.g., "loan repaid", "collateral released") will have step (b) wiped out if the counterparty's address happens to be an AA that deliberately bounces on receipt — exactly mirroring the ERC777 hook revert described in the source report, since anyone can freely deploy an AA at an address they control and make it always bounce (e.g., an AA whose only messages array is empty, or whose formula always fails, or which has `bounce_fees` set higher than what it can pay after receiving the "counterparty" payment).

The existing test `test/aa_composer.test.js:156-253` ("chain of AAs") explicitly demonstrates that a primary AA's payment to a secondary AA can cascade into a fully composed multi-hop trigger — confirming the recipient-triggers-code-execution-within-your-transaction behavior is by design and reachable from any ordinary payment message sent by an AA to any address [4](#0-3) .

### Impact Explanation
Any Oscript AA implementing a lending/escrow/marketplace pattern (borrower posts a trigger to repay a debt or release collateral, and that trigger's response both pays the counterparty and updates internal state) is vulnerable to a "counterparty as malicious secondary AA" griefing attack: the counterparty can guarantee their own payment always bounces, which reverts the entire primary AA's state update (e.g., marking the debt repaid or releasing collateral back to the borrower) even though bytes were spent trying. Repeated attempts cost the trigger-poster bounce fees each time and never succeed, effectively freezing the borrower's ability to close the loan on-chain while the counterparty proceeds to invoke a separate "liquidate" trigger against the still-open loan state — the same end-state as the original Teller vulnerability (unauthorized appropriation of collateral due to unresolvable repayment).

### Likelihood Explanation
Deploying an AA that always bounces (e.g., a trivial `{"messages": []}` or one that intentionally fails a formula) requires no privilege and no cooperation from network operators — only a public AA address definition, which is standard, permissionless functionality in ocore. Any lending/escrow AA author who naively places state-changing logic in the same message chain as a payment to a counterparty-controlled address is exposed to this pattern.

### Recommendation
This is inherent AA-composition semantics (a design tradeoff of oscript, not a memory-safety bug in transaction validation), so it can't be "fixed" in the core protocol without breaking secondary-trigger composability that other AAs rely on. Practical mitigations belong at the AA-authoring level: state changes that must be irreversible (e.g., "debt repaid") should be committed via `state` messages/`var[]` updates that occur in a message *sequence before* payments are sent to counterparty addresses in the same primary trigger, or the lending AA should use a pull-payment/claim pattern (record a claimable balance for the lender, let the lender withdraw with a separate trigger) instead of push-paying the lender directly during the borrower's repay trigger, exactly analogous to the ERC777 report's suggested remediation of "send to the contract, let the lender claim it later." ocore documentation for AA developers should explicitly call out this secondary-trigger bounce/revert propagation risk near the `aa_composer.js` `handleSecondaryTriggers`/`revert` logic.

### Proof of Concept
1. Deploy `LendingAA` whose repay-trigger response contains, in order: (a) a `payment` message sending the repayment amount to `trigger.data.lender_or_stored_lender_address`, then (b) a `state` message setting `var['loan_repaid'] = 1`, matching the pattern shown working end-to-end in `test/aa_composer.test.js:156-253` (payment-then-state chain to a secondary address).
2. Have the "lender" deploy a trivial `MaliciousLenderAA` at the address recorded as `lender_address`, defined simply as `['autonomous agent', { messages: [] }]` — per `aa_composer.js:1868-1877`, an AA with no post-filter messages after receiving payment yields `handleSuccessfulEmptyResponseUnit`, but if instead `bounce_fees.base` is set higher than the forwarded amount, or a formula deliberately fails, the secondary trigger bounces (`aa_composer.js:1852-1857`, `bounce()` at `aa_composer.js:910-945`).
3. Borrower posts the repay trigger to `LendingAA`. `LendingAA` sends the payment to `MaliciousLenderAA` as a secondary trigger; `MaliciousLenderAA` bounces; `handleSecondaryTriggers` sees the error and calls `revert()` on `LendingAA`'s primary trigger (`aa_composer.js:1743-1749`, `1759-1783`), wiping the `var['loan_repaid'] = 1` update and refunding only bounce-fee-adjusted bytes to the borrower.
4. `LendingAA`'s stored loan state remains "not repaid"; the lender's own separate `liquidate` trigger (checking `loan_repaid` state var) can now seize the collateral even though the borrower attempted to repay in good faith.
