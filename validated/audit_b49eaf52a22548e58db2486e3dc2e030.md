### Title
Webhook signature is verified against the organization named in `repository.owner.login`, but every event handler dispatches on `repository.full_name` with no cross-check between the two — allowing a multi-tenant Shipit App to be tricked into acting on another organization's repository - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit.github(organization:)` supports a "multiple Github Applications" configuration (`docs/setup.md`, `test/dummy/config/secrets_double_github_app.yml`) where each organization has its own independent `webhook_secret`. `WebhooksController#verify_signature` selects which organization's secret to validate the HMAC against using `repository_owner`, which is read straight out of the *unverified* JSON body (`params.dig('repository','owner','login')`). Once the signature check passes, `Shipit::Webhooks::Handlers::Handler#repository_name` (and every concrete handler, e.g. `PushHandler`) looks up the target `Stack`/`Repository` using a *different* field of the same payload: `payload.dig('repository','full_name')`. Nothing in the code enforces that `repository.full_name` actually belongs to the organization identified by `repository.owner.login`.

### Finding Description
In a single-organization deployment this is harmless because there is only one secret. But the engine explicitly documents and tests a multi-org mode (`lib/shipit.rb:170-200`, `github_app_config`, `test/dummy/config/secrets_double_github_app.yml`) where each org (e.g. `OrgOne`, `OrgTwo`) gets its own `GitHubApp` instance with its own `webhook_secret`. [1](#0-0) 

selects the verification key:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [2](#0-1) 

The signature itself, `verify_webhook_signature`, is a plain HMAC over the whole raw body using the org's `webhook_secret`: [3](#0-2) 

Meanwhile, every default handler resolves the repository to act on from a *different* JSON key, `repository.full_name`, via `Handler#repository_name`/`#stacks`: [4](#0-3) 

and e.g. `PushHandler#process` triggers `stack.sync_github` for every matching, non-archived stack: [5](#0-4) 

Because `repository.owner.login` (used to pick the secret) and `repository.full_name` (used to pick the target Stack) are two independent fields inside the same signed body, an attacker who legitimately possesses the `webhook_secret` for one configured organization (e.g. by installing/operating their own installation of the multi-tenant GitHub App on `OrgOne`) can hand-craft an arbitrary JSON payload, set `repository.owner.login: "OrgOne"` (so `verify_signature` selects and validates against the secret they know) while setting `repository.full_name: "OrgTwo/victim-repo"` (or any tracked repository's full name), and sign the whole body with `OrgOne`'s secret. The HMAC will validate successfully (it only proves "signed by someone who knows OrgOne's secret", not "this payload is about an OrgOne repo"), and the dispatched handler will act on `OrgTwo/victim-repo` — a repository/organization the attacker's secret was never meant to authorize.

This is the same class of bug as the `findNewOwner` report: a boundary/consistency check (`_loopCounter == maxDeletions` mis-inferring "done") substitutes an indirect signal for the real state; here, "signature valid for organization X" is used as a proxy for "this event is authorized to mutate organization X's/other orgs' resources," but the signed field selecting the trust boundary (`owner.login`) is never bound to the field that actually gets acted upon (`full_name`).

### Impact Explanation
This crosses the "an organization that authenticated versus the repository that is written" binding explicitly called out as in-scope. A holder of one organization's legitimate, low-privilege webhook secret can forge webhook deliveries (`push`, `status`, `check_suite`, `pull_request`) that are processed as if they originated from GitHub for a completely different, unrelated tracked repository/stack — e.g. queuing `GithubSyncJob`/`stack.sync_github` with an attacker-chosen `expected_head_sha`, creating commit `Status` records, or archiving/unarchiving review stacks via the PR label handlers — none of which the attacker's own GitHub App installation has any authorization over. This is a cross-repository/cross-tenant write through the webhook trust boundary, matching the "cross-repository writes" Critical-impact category defined by the scan rules.

### Likelihood Explanation
Requires Shipit to be configured in the documented multi-organization mode and requires the attacker to control (or have compromised) a legitimate, independently-scoped `webhook_secret` for at least one configured org — which is a materially weaker credential than repository write access or a Shipit session/API token. Given the engine explicitly supports and documents this multi-tenant configuration as a first-class feature, this is a realistic deployment shape, not a hypothetical one.

### Recommendation
Bind the field used for secret selection to the field used for repository resolution: after selecting `github_app` via `repository_owner`, verify that `payload.dig('repository','full_name')` (or `organization.login` for org-scoped events) is actually owned by/matches `repository_owner` before dispatching to handlers, or resolve the target `Stack`/`Repository` only from a github-owner-scoped lookup rather than a bare `full_name` match, so a valid signature for org X can only ever affect resources belonging to org X.

### Proof of Concept
1. Configure Shipit with two organizations, `OrgOne` and `OrgTwo`, each with its own `webhook_secret` (as in `test/dummy/config/secrets_double_github_app.yml`).
2. As an attacker who legitimately knows `OrgOne`'s `webhook_secret` (e.g., they administer the GitHub App installation on `OrgOne`), craft a `push` payload:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "full_name": "OrgTwo/victim-repo",
    "owner": { "login": "OrgOne" }
  }
}
```
3. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(OrgOne_webhook_secret, raw_body)>` and POST to `/webhooks` with header `X-Github-Event: push`.
4. `verify_signature` calls `Shipit.github(organization: "OrgOne")` and successfully validates the signature against `OrgOne`'s secret.
5. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("OrgTwo/victim-repo")` and enqueues `GithubSyncJob`/`stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` for the `OrgTwo` stack, even though the attacker only ever proved knowledge of `OrgOne`'s secret.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
