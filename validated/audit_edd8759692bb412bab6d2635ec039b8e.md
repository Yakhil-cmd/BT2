### Title
Webhook signature verification keys off `repository.owner.login`, but handlers act on the independent `repository.full_name` field, enabling cross-organization stack writes - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
The `WebhooksController` selects *which* GitHub organization's `webhook_secret` verifies an inbound webhook's HMAC by reading `repository.owner.login` (or `organization.login`) from the JSON body, then verifies the signature over the whole raw payload. However, every webhook `Handler` looks up the `Repository`/`Stack` it will actually mutate using a *different* field of that same body: `repository.full_name`. Because these are two independent, attacker-supplied strings inside the same signed payload, an attacker who legitimately controls (and knows the `webhook_secret` of) one tracked GitHub organization in a multi-org Shipit install can forge a payload that authenticates as their own org while acting on a completely different, victim organization's repository/stack.

### Finding Description
`WebhooksController#verify_signature` selects the HMAC secret to validate against based on `repository_owner`: [1](#0-0) [2](#0-1) 

The secret itself is a per-organization config value looked up via `Shipit.github(organization: repository_owner)`, and `GitHubApp#verify_webhook_signature` only proves that *some* org's configured secret was used to sign the raw body — it says nothing about which repository the body claims to target: [3](#0-2) [4](#0-3) 

Every `Handler` subclass, however, resolves the `Repository` to act on from a *different* JSON field, `repository.full_name`, not `repository.owner.login`: [5](#0-4) 

Since the attacker fully controls the raw JSON body before computing the HMAC (they know their own org's `webhook_secret` because they had to configure it on the GitHub side when setting up the webhook), they can set `repository.owner.login` to their own org (so `Shipit.github(organization: ...)` picks a secret they know and the signature check passes) while setting `repository.full_name` to any other org/repo tracked by the same Shipit instance. Concretely:

- `PushHandler` would enqueue `GithubSyncJob` against any tracked stack matching the forged `full_name`/branch: [6](#0-5) 

- `PullRequest::OpenedHandler` will create a brand-new `ReviewStack` for the victim repository, using attacker-controlled PR data (including the branch to check out) taken straight from the payload, and immediately queue it for provisioning: [7](#0-6) [8](#0-7) [9](#0-8) 

This breaks exactly the trust binding called out in the rules: the organization that authenticated the request (via its `webhook_secret`) is not the repository that ends up written to (resolved via an independent, unverified-against-owner `full_name` field).

### Impact Explanation
An attacker who administers a webhook for any one GitHub organization tracked by the Shipit instance (and therefore knows that org's `webhook_secret`, which they must configure identically on GitHub's side) can forge signed webhook deliveries that target *any other* organization's repository/stack tracked by the same Shipit instance. This allows:
- Creating/archiving/unarchiving `ReviewStack`s for a victim repository with an attacker-chosen branch, which are then queued for provisioning (`ReviewStackProvisioningQueue.add` → `stack.provision`), effectively causing Shipit to check out and run `shipit.yml`-driven provisioning against a ref the attacker specifies for a repository they do not own.
- Forcing `GithubSyncJob` re-syncs against arbitrary tracked stacks by spoofing `push` events.

This is a cross-repository write triggered purely by knowledge of a webhook secret the attacker legitimately possesses for an unrelated, lower-trust organization — no `ApiClient` token, GitHub App private key, or Shipit account is required.

### Likelihood Explanation
Exploitability depends entirely on the deployment hosting multiple GitHub organizations (each with distinct `webhook_secret`s) behind a single shared Shipit instance and `/webhooks` endpoint — a supported and documented configuration. Any org admin able to configure a webhook for their own tracked org (a comparatively low-privilege, self-service action) can carry out the attack with a single crafted HTTP POST; no timing tricks, races, or victim interaction are needed.

### Recommendation
Bind the authenticated organization to the entity being mutated: after verifying the signature, re-derive `repository_owner` (or `organization.login`) from the *same* field used to select the secret, and require that the `Repository`/`Stack` resolved by each `Handler` (via `repository.full_name`) belongs to that same authenticated organization before performing any mutation (e.g., pass the verified `repository_owner` into `Handler.call` and assert `repository.full_name.split('/').first == repository_owner` before proceeding, or key repository lookups off the owner login instead of an independent `full_name` string).

### Proof of Concept
1. Attacker administers `attacker-org`, tracked in this Shipit instance with `webhook_secret = S`, and legitimately knows `S` (they configured it on GitHub's webhook settings page).
2. Attacker crafts a `pull_request` "opened" JSON payload where:
   - `organization.login` / `repository.owner.login` = `"attacker-org"` (so `WebhooksController#repository_owner` selects `attacker-org`'s secret for verification)
   - `repository.full_name` = `"victim-org/victim-repo"` (a repository actually tracked by the same Shipit instance under a different, unrelated organization)
   - `pull_request.head.ref` = an attacker-chosen branch
3. Attacker computes `X-Hub-Signature = HMAC-SHA1(S, raw_body)` and POSTs to `/webhooks`.
4. `WebhooksController#verify_signature` passes (secret matches `attacker-org`).
5. `PullRequest::OpenedHandler#process` resolves `repository` via `params.repository.full_name` = `victim-org/victim-repo`, and (if review stacks/auto-provisioning are enabled for that repo) creates a `ReviewStack` for `victim-repo` with the attacker's chosen branch and enqueues it for provisioning — despite the attacker never having any credential tied to `victim-org`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

# frozen_string_literal: true

module Shipit
  class ReviewStackProvisioningQueue
    def self.work
      new.work
    end

    def self.add(stack)
      stack.enqueue_for_provisioning
    end

    def self.queued_stacks
      new.queued_stacks
    end

    def work
      queued_stacks.find_each(&method(:provision))
    end

    def queued_stacks
      @queued_stacks ||= Shipit::ReviewStack
                         .with_provision_status(:deprovisioned)
                         .where(awaiting_provision: true)
    end

    private

    def provision(stack)
      if stack.provisioner.provision?
        stack.provision
      else
        Rails.logger.info(
          "Putting review ReviewStack<#{stack.id}> back into the provisioning queue - #provision? was falsey."
        )
      end
    end
  end
end
