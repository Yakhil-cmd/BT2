### Title
Webhook signature verified against the payload's `repository.owner.login`, but downstream handlers act on the payload's independently-controlled `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects which tenant's `GitHubApp`/`webhook_secret` to verify the HMAC signature against using `repository_owner`, a value taken from the same attacker-suppliable JSON body (`params.dig('repository', 'owner', 'login')` or `params.dig('organization', 'login')`). Once the signature check passes, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` dispatches to handlers (e.g. `PushHandler`) which resolve the actual repository/stack to act on via a *different* field in the same body: `payload.dig('repository', 'full_name')`. Nothing ties these two fields together, so a signature proven valid for organization "A" is accepted as authorization to act on a repository belonging to organization "B", if the request body simply sets `repository.owner.login = "A"` and `repository.full_name = "B/victim-repo"`.

### Finding Description
In a multi-tenant Shipit deployment (`docs/setup.md` "Using Multiple Github Applications" — `github: { OrgA: {...}, OrgB: {...} }`), each tenant organization has its own GitHub App and its own `webhook_secret`, known to that organization's own (unprivileged, from the other tenant's perspective) administrators, because they typed it in when creating their GitHub App.

The controller's signature check is: [1](#0-0) 

`repository_owner` is derived purely from the incoming JSON: [2](#0-1) 

That value picks the `GitHubApp`/secret used to verify `X-Hub-Signature`: [3](#0-2) 

Once `verified` is true, the same raw payload is dispatched to handlers: [4](#0-3) 

But every handler determines *which repository/stack to act on* from a separate, independently-forgeable field of the same body — `repository.full_name` — not from `repository.owner.login`: [5](#0-4) 

`PushHandler`, for example, uses this to find stacks and trigger a GitHub sync for a target branch/SHA the attacker also fully controls (`params.after`): [6](#0-5) 

Other handlers (`OpenedHandler`, `LabeledHandler`, `ClosedHandler`, `ReopenedHandler`, `UnlabeledHandler`, etc.) follow the identical pattern of resolving the acted-upon `Shipit::Repository` via `params.repository.full_name`, entirely decoupled from the field used for signature verification: [7](#0-6) 

**The broken binding, as an equality that fails to hold:**
`organization authenticated by signature (repository.owner.login / organization.login)` ≠ `organization actually written to (repository.full_name)`.

Before the attack: the engine's implicit trust model assumes that a validly-signed webhook can only originate from GitHub for the organization whose secret produced the signature, and that the repository referenced inside that webhook necessarily belongs to that same organization (true for genuine GitHub-originated deliveries). After the attacker's crafted POST: the signature is valid for tenant org "AttackerOrg" (which the attacker administers and thus knows the `webhook_secret` for), but `repository.full_name` names a repository/stack that belongs to a different, victim tenant org, "VictimOrg" — a repository the attacker was never authorized to affect.

### Impact Explanation
This allows a party who administers only their own tenant organization inside a shared, multi-org Shipit installation to forge webhook deliveries that pass signature verification using their own org's secret, yet trigger side effects against a different organization's tracked stacks — an unauthorized cross-repository/cross-organization action reachable with no GitHub credentials for the victim org, no Shipit session, and no API token. Concretely this can force `stack.sync_github(expected_head_sha:)` to run against a victim's stack for an attacker-chosen SHA/branch (`PushHandler`), or archive/unarchive victim review stacks and mutate pull-request-driven stack state (`ClosedHandler`, `LabeledHandler`, `UnlabeledHandler`, `ReopenedHandler`), all without ever proving any relationship to the victim organization. This crosses the "cross-repository writes" bar from the rules because a tenant boundary meant to isolate organizations from each other is bypassed purely by mismatching two fields inside one forged JSON body.

### Likelihood Explanation
Likelihood is Medium: it requires the attacker to control (administer) at least one tenant organization configured in the same multi-org Shipit instance (a documented, supported configuration — see `docs/setup.md` "Using Multiple Github Applications" and `test/dummy/config/secrets_double_github_app.yml`), which grants them their own `webhook_secret` used to correctly sign a forged request body. No access to the victim organization, no Shipit account, and no GitHub App private key for the victim org is required.

### Recommendation
After verifying the HMAC signature for the resolved `repository_owner`, re-derive the acted-upon organization/repository strictly from the same verified identity, or explicitly assert that `payload.dig('repository', 'full_name')`'s owner segment equals the `repository_owner` used for signature selection, rejecting the request otherwise. Alternatively, bind the signature verification key deterministically to the same `full_name`-derived owner that every handler subsequently uses to resolve `Shipit::Repository`, so a single "acted-upon organization" identity is used for both signature selection and effect target resolution.

### Proof of Concept
1. Deploy Shipit with `github: { AttackerOrg: {...}, VictimOrg: {...} }` (as documented for multi-org support), and note the `webhook_secret` configured for `AttackerOrg` (known to whoever set up that tenant's GitHub App).
2. Ensure `VictimOrg/victim-repo` is a tracked `Shipit::Repository` with an existing stack/branch.
3. Craft body:
```json
{
  "repository": { "owner": { "login": "AttackerOrg" }, "full_name": "VictimOrg/victim-repo" },
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>"
}
```
4. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(AttackerOrg_webhook_secret, body)>` and POST to `/webhooks` with `X-Github-Event: push`.
5. `verify_signature` selects `Shipit.github(organization: "AttackerOrg")` (from `repository.owner.login`), the signature validates, and `PushHandler` resolves the target via `repository.full_name` = `"VictimOrg/victim-repo"`, invoking `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` on the victim's stack — despite the attacker having proven authenticity only for `AttackerOrg`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

module Shipit
  module Webhooks

          requires :after

        def process
