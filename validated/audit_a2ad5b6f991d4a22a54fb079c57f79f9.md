### Title
AA identity checks based on `trigger.address` can be bypassed by an attacker-deployed proxy AA, enabling self-dealing that a same-address check was meant to prevent - (File: aa_composer.js)

### Summary
`ocore` lets any user post a new AA definition and then have that AA forward a payment/trigger to a second, already-deployed AA (a "chain of AAs"). When AA₂ receives a call originating from AA₁ rather than directly from a human wallet, `getTrigger()` sets `trigger.address` to `objUnit.authors[0].address`, i.e. the address of the calling AA (AA₁), not the human who ultimately funded and controls AA₁. This is structurally identical to the Licredity bug: a privileged/self-referential check compares against the immediate caller's identity (`msg.sender` / `trigger.address`), and an attacker can interpose a contract/AA they control to change what that immediate-caller identity looks like to the target, defeating checks such as "the caller must not be the owner/position-holder."

### Finding Description
`getTrigger()` derives the trigger identity purely from the sending unit's first author: [1](#0-0) 

This is used both for primary triggers (posted directly by a wallet) and, unchanged in shape, for secondary triggers dispatched when one AA pays another: [2](#0-1) 

Note that `child_trigger = getTrigger(objUnit, row.address)` re-derives `trigger.address` as the *paying AA's own address* for the downstream AA, while `trigger.initial_address`/`trigger.initial_unit` are separately threaded through to preserve the original human trigger's identity: [3](#0-2) [4](#0-3) 

The very existence of `trigger.initial_address` as a distinct field (separate from `trigger.address`) is the framework's tacit acknowledgment that `trigger.address` alone is not a reliable "true caller" identity once AA-to-AA chaining is possible — exactly the same caveat Licredity's own code called out for `seize`'s `msg.sender` check ("side effect is that positions cannot be seized by owner contract ... acceptable"). Multiple test fixtures in the codebase demonstrate that an ordinary user can freely deploy a brand-new AA and have it call an existing AA atomically within the same primary trigger's response chain (`test/aa_composer.test.js:557-649` "define new AA and activate it", `test/aa_composer.test.js:922-1010` "AA with generated definition of new AA and immediately sending to this new AA"), confirming that self-service proxy-AA deployment and invocation is a normal, unprivileged capability of the platform: [5](#0-4) 

Multiple bundled/example AAs in the repo implement authorization or self-dealing checks by comparing `trigger.address` directly to a stored identity, e.g. ownership checks in the things/marketplace AA: [6](#0-5) 
and party-identity checks in the payment-channel AA: [7](#0-6) 

Any AA author who follows this same, widely-used idiom to build a "position owner"/"lender/borrower"/"party A vs. party B" contract and gates a self-dealing-prevention rule (e.g. "the liquidator/closer must not be the position owner") on `trigger.address != stored_owner` can be bypassed: the owner deploys their own throwaway proxy AA, funds it, and has the proxy AA immediately forward the payment/trigger to the target AA within the same DAG unit/response chain. From the target AA's perspective, `trigger.address` is now the proxy AA's address (never before recorded as `owner`), so the "not the owner" check silently passes, while `this_address`/state changes still ultimately benefit the human who deployed and controls the proxy AA (who can retrieve any returned funds via a subsequent payment from the proxy AA, exactly as `AttackerRouter`/`AttackerSeizer` do for the Solidity case).

### Impact Explanation
Any AA-based financial protocol (lending/collateral, escrow, insurance, marketplace, payment channel, or fee-sharing AA) that uses `trigger.address` — rather than a value it cannot control, such as a signed message's `address` field, or that fails to also cross-check `trigger.initial_address` — to prevent an actor from acting against their own account in a way that is meant to be restricted to third parties (self-liquidation, self-reporting, self-dispute-resolution, "not your own listing", etc.) can have that restriction defeated by the account owner via a self-deployed proxy AA. Depending on the protocol's specific incentive/penalty design, this can let a user extract liquidation bonuses, penalty payouts, or other protocol funds meant to reward disinterested third parties, at the expense of counterparties or the AA's balance/lenders — the same fund-loss category as the reported Licredity bug (AA fund loss).

### Likelihood Explanation
Deploying a new AA and having it immediately forward a trigger to another AA in the same transaction chain is a completely unprivileged, well-supported, and explicitly tested capability of ocore (`test/aa_composer.test.js` "chain of AAs", "define new AA and activate it", "AA with generated definition of new AA and immediately sending to this new AA"). No special permissions, timing races, or malicious peers/nodes are required — only that the target AA's own logic relies on `trigger.address` for a self-dealing check instead of a value the caller cannot spoof (e.g., a signed package address, or careful use of `trigger.initial_address` combined with a check that the trigger is not a secondary/chained one). This is a design-pattern pitfall rather than a bug in the DAG/consensus engine itself, so exploitability is entirely contingent on how individual AA authors write their contracts — the core platform provides no built-in equivalent of Euler's "Locker: reject if position already touched this transaction" guard that Licredity adopted as its fix.

### Recommendation
- Document explicitly (and provide it as a first-class pattern/getter) that `trigger.address` can be another AA when the call is part of a chain, and that AAs implementing self-dealing prevention (e.g., "X cannot act on their own Y") must not rely solely on `trigger.address`; they should authenticate the true human counterparty via signed messages (`is_valid_signed_package`) or explicitly reject calls where `trigger.address != trigger.initial_address` (i.e., reject non-primary/chained triggers) for security-sensitive branches.
- Consider adding an oscript primitive/getter, analogous to Euler's/Licredity's "already touched this transaction" check, that lets an AA detect whether it is being invoked as a secondary trigger within the same unit/response chain as a specific prior action on the same state (e.g., "was this position modified earlier in this same trigger chain?"), so AA authors can block atomic "open unhealthy position + self-liquidate via proxy" style exploits.
- Audit bundled example AAs (`test/samples/*.oscript`) that use `trigger.address ==`/`!=` for ownership/party checks and add commentary warning that these patterns are unsafe if the AA could ever be invoked as part of a chain from an attacker-controlled AA.

### Proof of Concept
Conceptual PoC (mirrors the Solidity PoC's structure), based on the "chain of AAs" mechanism already demonstrated in the test suite:

1. Deploy `TargetAA`, a lending-style AA that stores `var['owner_' || id] = trigger.address` on deposit and pays a "liquidation bonus" to whichever address triggers a `liquidate` action, while checking only `if (trigger.address == var['owner_' || id]) bounce('cannot self-liquidate');` — following the exact same idiom already used for ownership checks in `test/samples/things_registry_and_marketplace.oscript:45-69`.
2. As the position owner, deploy a new throw-away `ProxyAA` (unprivileged — see `test/aa_composer.test.js:557-649` / `922-1010` for how trivially this is done and chained atomically).
3. In a single primary trigger to `ProxyAA`, have `ProxyAA`'s `messages` immediately forward a payment/data trigger to `TargetAA` requesting liquidation of the owner's own under-collateralized position.
4. Inside `TargetAA`'s execution (a secondary trigger), `trigger.address` (per `getTrigger()`, `aa_composer.js:375-397` and `handleSecondaryTriggers`, `aa_composer.js:1702-1727`) equals `ProxyAA`'s address, not the owner's, so the `trigger.address == var['owner_' || id]` check passes and the "self-liquidation" bounce is bypassed. `TargetAA` pays the liquidation bonus to `ProxyAA`, which forwards it back to the owner in a follow-up message — all within the same DAG unit/response chain, atomically and without price movement, exactly mirroring the Solidity `AttackerRouter`/`AttackerSeizer` exploit.

function getTrigger(objUnit, receiving_address) {
	var trigger = { address: objUnit.authors[0].address, unit: objUnit.unit, outputs: {} };
	if ("max_aa_responses" in objUnit)
		trigger.max_aa_responses = objUnit.max_aa_responses;
	objUnit.messages.forEach(function (message) {
		if (message.app === 'data' && !trigger.data) // use the first data message, ignore the subsequent ones
			trigger.data = message.payload;
		else if (message.app === 'payment' && message.payload) {
			var payload = message.payload;
			var asset = payload.asset || 'base';
			payload.outputs.forEach(function (output) {
				if (output.address === receiving_address) {
					if (!trigger.outputs[asset])
						trigger.outputs[asset] = 0;
					trigger.outputs[asset] += output.amount; // in case there are several outputs
				}
			});
		}
	});
	if (Object.keys(trigger.outputs).length === 0)
		throw Error("no outputs to " + receiving_address);
	return trigger;
}
