### Title
Webhook signature verification authenticates the payload's `organization`/`repository.owner.login` field but the event handlers dispatch to stacks resolved from the independent `repository.full_name` field, allowing a valid webhook sender for one GitHub organization to force actions on stacks belonging to a completely different, unrelated organization - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which organization's `webhook_secret` to verify the HMAC against based on `repository_owner`, extracted as `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`. Once the signature check passes, the actual routing of the event to Shipit stacks is done independently by `Shipit::Webhooks::Handlers::Handler#repository_name`, which reads a *different* JSON path: `payload.dig('repository', 'full_name')`, and looks up `Repository.from_github_repo_name(repository_name)`. Nothing enforces that `repository.owner.login` (used for authentication) and `repository.full_name` (used for authorization/dispatch) refer to the same repository/organization.

The subsequent `GithubSyncJob` does correctly use the *stored* repository's own GitHub App credentials to fetch commits (via `Repository#github_app`, which reads the DB `owner` column, not the payload) [6](#0-5)

This is exactly the binding-break pattern described in the report: the entity that authenticates the request (`organization` derived from `repository.owner.login`) is not the same entity the code subsequently acts on (`repository.full_name` used to select the target `Stack`/`Repository`), and no reconciliation between the two is performed before the write side-effect happens.

### Impact Explanation
An attacker who is a legitimate webhook administrator (or otherwise possesses) the `webhook_secret` for any one organization configured in this Shipit instance can trigger `GithubSyncJob` / status-, check_suite-, pull_request-type handlers against stacks that belong to an entirely unrelated organization also configured in the same instance. This can force a resync (and, with continuous delivery configured, an unauthorized deploy) of a foreign stack using an attacker-selected existing commit SHA, constituting a cross-repository write / unauthorized deploy despite the attacker never possessing that victim organization's webhook secret or GitHub credentials.

### Likelihood Explanation
Exploitability requires the attacker to know a valid `webhook_secret` for at least one organization onboarded to the Shipit instance — a routine capability for anyone who set up or was given access to that org's GitHub webhook configuration, not an elevated Shipit-internal privilege. Multi-tenant Shipit deployments (multiple organizations sharing one instance) are explicitly supported via `Shipit.github(organization: ...)`, so this scenario is realistic wherever such multi-org configuration exists.

### Recommendation
After signature verification succeeds, `WebhooksController`/`Handler` should re-derive the authorized organization from the verified secret's own configuration and require that `repository.full_name`'s owner segment matches `repository_owner` (the field used to select the verifying secret) before resolving `Repository.from_github_repo_name`. Reject the event (e.g. `head(422)`) if the two disagree, closing the gap between the authenticated entity and the entity acted upon.

### Proof of Concept
1. Attacker administers GitHub org `attacker-org`, which is configured in Shipit with `webhook_secret` `S`.
2. Shipit also hosts a stack for `victim-org/victim-repo` with continuous delivery enabled.
3. Attacker crafts a JSON body:
```json
{
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  },
  "ref": "refs/heads/main",
  "after": "<sha-of-an-existing-commit-on-victim-repo-main>"
}
```
4. Attacker computes `X-Hub-Signature: sha1=HMAC(S, body)` and POSTs to `/webhooks` with `X-Github-Event: push`.
5. `verify_signature` looks up `Shipit.github(organization: "attacker-org")` (from `repository.owner.login`), verifies successfully using `S`.
6. `PushHandler#process` resolves stacks via `Repository.from_github_repo_name("victim-org/victim-repo")` and enqueues `GithubSyncJob` for `expected_head_sha` pointing at the victim's stack — an event the attacker had no legitimate access to trigger.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
