Based on my investigation, the strongest reachable analog is a genuine binding-break: the organization used to select/verify the webhook HMAC secret (`repository.owner.login`) is disjoint from the repository the payload is actually applied to (`repository.full_name`), and both fields live in the same attacker-influenced JSON body but are never cross-checked.

### Title
Webhook signature verifies against the claimed organization, not the repository actually mutated - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/secret to validate the HMAC against using `repository.owner.login` (or `organization.login`) taken straight from the unverified JSON body, then, once verification "succeeds," the event handlers act on `repository.full_name` from that same body without ever asserting that `full_name`'s owner equals the `owner.login` used for verification.

### Finding Description
`repository_owner` is read from the parsed body before/while the signature is checked: [1](#0-0) . That value picks the `github_app`/secret used for HMAC verification: [2](#0-1) . The dispatched handlers, however, resolve the target `Repository`/`Stack` from `repository.full_name`, a separate field of the same body: [3](#0-2) , and `PushHandler` mutates that stack's commit history (`sync_github`) based on it: [4](#0-3) . Nowhere is `repository.full_name`'s owner cross-checked against `repository.owner.login`/`organization.login` that was used to select the signing secret. In a multi-org configuration (the engine explicitly supports per-org `webhook_secret`s, see `config/secrets.development.shopify.yml`) an operator who legitimately controls a GitHub App/webhook secret for "orgA" can send a payload where `repository.owner.login = "orgA"` (so verification uses orgA's known secret and succeeds) while `repository.full_name = "orgB/victim-repo"`, causing the push handler to sync/write commit state for a stack belonging to a completely different, unrelated organization ("orgB") that they do not otherwise control.

### Impact Explanation
This breaks the equality `organization authenticated == repository written`, letting a party with legitimate access to only one configured org's webhook secret inject forged push/status/commit events against stacks belonging to a different org configured in the same Shipit instance — an unauthorized write of commit/deploy-relevant state on a repository they do not control, satisfying the "cross-repository writes" High/Critical impact bucket.

### Likelihood Explanation
Requires the deployment to be configured with more than one GitHub organization/app (a documented, supported configuration: `config/secrets.development.shopify.yml`), and requires the attacker to already hold a valid webhook secret for at least one of those configured orgs — this is a real but non-default multi-tenant configuration, so likelihood is moderate and configuration-dependent rather than universally exploitable.

### Recommendation
In `WebhooksController#verify_signature` (or in `Shipit::Webhooks::Handlers::Handler`), assert that `repository.full_name`'s owner segment matches the `repository_owner`/`organization.login` that was used to select the verification secret, rejecting the webhook (422) on mismatch before dispatching to any handler.

### Proof of Concept
1. Configure Shipit with two orgs, `orgA` and `orgB`, each with its own `webhook_secret` (as in `config/secrets.development.shopify.yml`).
2. As someone with access to `orgA`'s webhook secret (e.g., an admin of the GitHub App installed on `orgA`), craft a `push` payload with `repository.owner.login = "orgA"` but `repository.full_name = "orgB/some-stack-repo"`, and sign it with `orgA`'s secret.
3. POST to `/webhooks`; `verify_signature` resolves `Shipit.github(organization: "orgA")` and the HMAC validates successfully.
4. `PushHandler` resolves the target stack via `Repository.from_github_repo_name("orgB/some-stack-repo")` and calls `stack.sync_github`, mutating state for a stack under `orgB` despite the request being authenticated only for `orgA`.
