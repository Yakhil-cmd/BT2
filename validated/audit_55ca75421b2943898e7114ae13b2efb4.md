## Analysis

Shipit supports multiple GitHub organizations each with their own `GithubApp` instance and independent `webhook_secret`, resolved by organization login [1](#0-0) . Webhook signature verification selects *which* organization's secret to check against using one payload field, while the handlers that act on the payload use an entirely different, unauthenticated-relative-to-that-field, field to decide which repository/stack is mutated. This is exactly the "organization that authenticated versus the repository that is written" binding class.

### Title
Webhook signature verification is bound to `repository.owner.login`/`organization.login` while stack resolution is bound to the unrelated `repository.full_name` field, allowing cross-repository webhook forgery - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects the HMAC secret to verify against based on `repository.owner.login` (falling back to `organization.login`), then checks the signature over the raw request body [2](#0-1) [3](#0-2) . But every `Handler` subclass (e.g. `PushHandler`) resolves the target `Stack`(s) using `payload.dig('repository', 'full_name')` — a completely separate JSON field [4](#0-3) . Nothing in the code enforces that `repository.full_name`'s owner segment matches `repository.owner.login`/`organization.login`. Since these are independent JSON fields inside a single raw POST body that the caller fully controls, an attacker who legitimately owns/administers one org onboarded to this Shipit instance (and thus legitimately knows that org's `webhook_secret`) can compute a valid signature over a forged payload whose `owner.login` is their own org (so verification passes) but whose `repository.full_name` names a victim repository/stack that they do not control.

### Finding Description
- `repository_owner` (used only for secret selection) — `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` [3](#0-2) .
- `repository_name` (used for stack resolution in every handler) — `payload.dig('repository', 'full_name')` [5](#0-4) , feeding `stacks` via `Repository.from_github_repo_name` [6](#0-5) .

Before the attack: for legitimate GitHub-originated webhooks, GitHub itself guarantees `repository.owner.login` and `repository.full_name`'s owner segment always refer to the same repository, so the binding "trusted org == acted-on repo" holds implicitly.

After the attack: an attacker POSTs directly to Shipit's `/webhooks` endpoint (bypassing GitHub) with a JSON body where `organization.login`/`repository.owner.login` = attacker's own org (whose secret they know) but `repository.full_name` = `"victim-org/victim-repo"`. `verify_signature` succeeds because it only checks that the body was signed with the attacker's own known secret; `PushHandler#process` (or any other handler) then resolves and acts on the victim's `Stack` [7](#0-6) , which enqueues `GithubSyncJob` with an attacker-controlled `expected_head_sha` and no origin-authenticity relationship to the victim's own GitHub organization/App configuration [8](#0-7) .

### Impact Explanation
The forged webhook lets an unprivileged-but-onboarded org owner drive events (push/pull_request/etc.) against a repository/stack they do not own, forcing unscheduled `GithubSyncJob` execution (and, depending on which of the several handlers sharing this same `repository_name` pattern is targeted — e.g. `pull_request/closed_handler.rb`, `labeled_handler.rb`, `opened_handler.rb`, which all resolve stacks via the identical `Handler#repository_name`/`stacks` helper), potentially interfering with merge-queue state transitions or continuous-deployment triggers on a repository outside the attacker's authorization boundary. This crosses a genuine authentication boundary: cross-repository interaction not backed by any secret tied to the victim repo/org.

### Likelihood Explanation
Exploitation requires the attacker to already control at least one organization/repository legitimately onboarded to the same Shipit instance (so they know that org's `webhook_secret`), and to send a hand-crafted POST directly to the `/webhooks` endpoint rather than a real GitHub-originated request. This is plausible in any multi-tenant Shipit deployment where multiple independent GitHub orgs are configured, since onboarding itself does not require special trust beyond having a repository with Shipit installed.

### Recommendation
After signature verification, cross-check that the resolved repository (`repository.full_name`) actually belongs to the same organization/owner that supplied the verified secret (`repository.owner.login`/`organization.login`), rejecting the webhook if they diverge, in `WebhooksController#verify_signature` and/or `Handler#repository_name`.

### Proof of Concept
1. Attacker legitimately owns `attacker-org/some-repo`, onboarded to the shared Shipit instance, and knows `attacker-org`'s `webhook_secret`.
2. Attacker crafts payload: `{"ref": "refs/heads/main", "after": "<attacker-chosen-sha>", "repository": {"full_name": "victim-org/victim-repo", "owner": {"login": "attacker-org"}}}`.
3. Attacker computes `sha1=` HMAC over the raw JSON using `attacker-org`'s webhook secret and sets `X-Hub-Signature` and `X-Github-Event: push`.
4. POST to `/webhooks`. `verify_signature` resolves `Shipit.github(organization: "attacker-org")` and the HMAC check passes [2](#0-1) .
5. `PushHandler#process` resolves stacks via `repository.full_name = "victim-org/victim-repo"` and calls `stack.sync_github(expected_head_sha: ...)` on the victim's stack [7](#0-6) , an action the attacker was never authorized to trigger for that repository.

    def perform(params)
      @stack = Stack.find(params[:stack_id])
      expected_head_sha = params[:expected_head_sha]
      retry_count = params[:retry_count] || 0
      head_before_sync = spec_cache_target
      appended_commits = []

      handle_github_errors do
        new_commits, shared_parent = fetch_missing_commits { stack.github_commits }

        # Retry on Github eventual consistency: webhook indicated new commits but we found none
        if expected_head_sha && new_commits.empty? && !commit_exists?(expected_head_sha) &&
           retry_count < MAX_RETRY_ATTEMPTS
          GithubSyncJob.set(wait: RETRY_DELAY * retry_count).perform_later(params.merge(retry_count: retry_count + 1))
          return
        end

        stack.transaction do
          shared_parent&.detach_children!
          appended_commits = new_commits.map do |gh_commit|
            append_commit(gh_commit)
          end
          stack.lock_reverted_commits! if appended_commits.any?(&:revert?)
        end
      end
      sync_changed_nothing = appended_commits.empty? &&
                             spec_cache_target == head_before_sync &&
                             stack.cached_deploy_spec.present?
      return if sync_changed_nothing && !params[:force_spec_cache]

      CacheDeploySpecJob.perform_later(stack)
    end
