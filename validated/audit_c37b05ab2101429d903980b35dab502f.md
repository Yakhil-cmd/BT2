### Title
Commit author attribution can be spoofed via forged `Merge-Requested-By:` commit message trailer - ([File: app/models/shipit/user.rb])

### Summary
`Shipit::User.find_or_create_author_from_github_commit` trusts a free-text `Merge-Requested-By: <login>` line inside the raw GitHub commit message to assign `Commit#author`, without checking that the named login actually pushed, merged, or approved the commit. Since GitHub commit messages are fully attacker-controlled content (e.g. via a squash-merge PR title, or any commit message on a branch the attacker controls), an unprivileged contributor can attribute an arbitrary commit to any existing Shipit user.

### Finding Description
The broken binding: `Commit#author` should equal the GitHub identity that authenticated/authored the push or merge, i.e. `commit.author == github_commit.author` (or `github_commit.commit.author`), but the code instead allows `commit.author == User.find_or_create_by_login!(<login extracted from commit message text>)` whenever the commit message matches `/^Merge-Requested-By: ([\w\-.]+)$/`, per `app/models/shipit/user.rb:34-44`:

```ruby
def self.find_or_create_author_from_github_commit(github_commit)
  if (match_info = github_commit.commit.message.match(/^#{MergeRequest::MERGE_REQUEST_FIELD}: ([\w\-.]+)$/))
    ...
    return find_or_create_by_login!(match_info[1])
```

This trailer is normally written only by Shipit itself in `MergeRequest#merge_message` (`app/models/shipit/merge_request.rb:262-266`) when Shipit performs an authorized merge-queue merge. However, nothing prevents an attacker from embedding this exact trailer in an ordinary commit message on their own branch/fork. That commit is ingested by `Shipit::GithubSyncJob#append_commit` → `Commit.create_from_github!` → `Commit.from_github` (`app/models/shipit/commit.rb:105-125`), which calls `User.find_or_create_author_from_github_commit(commit)` unconditionally for every synced commit - not just Shipit-generated merge commits.

Webhook signature verification (`webhooks_controller.rb`, `GithubApp#verify_webhook_signature`) only proves the payload came from GitHub; it does not, and cannot, validate the semantic content of a commit message, which is attacker-authored text. Once the attacker's commit becomes reachable in the stack's first-parent history (e.g. merged to the tracked branch, or via a squash-merge where the attacker sets the PR title used as the squash commit message), `GithubSyncJob` fetches it via `FirstParentCommitsIterator` and calls `append_commit`, triggering the spoofing.

### Impact Explanation
A successful exploit misattributes `Commit#author` to an arbitrary existing `Shipit::User` (the "victim"). This corrupts the audit trail (`Commit#author`), influences merge-queue trust decisions and `Task#SHIPIT_USER` attribution flows that key off commit/author identity, and lets any unprivileged contributor impersonate another user's identity in Shipit's authorization/attribution records for a given stack. This matches "unauthorized deploy/merge... payload... mutating another's... commit" style Critical impact, scoped to identity/attribution forgery for repositories the attacker can push to and that are tracked by a Shipit stack.

### Likelihood Explanation
Preconditions: a Shipit stack must be syncing commits from a repository the attacker can contribute to (push a branch/open a PR), and the malicious commit message must reach the tracked branch's first-parent history (e.g., merged/squash-merged). No secrets, tokens, team membership, or webhook signing keys are required — the attacker only needs to control the commit message text, which is trivially available to any contributor. This is repeatable per commit and against any stack tracking the affected repository.

### Recommendation
Remove or gate the `Merge-Requested-By` message-based author override in `User.find_or_create_author_from_github_commit`, or restrict its use to commits that are verified to be Shipit-generated merge commits (e.g., only trust it when `commit.parents.size > 1` and the merge was performed through `MergeRequest#merge!`, cross-checked against the stored `MergeRequest#merge_requested_by` for that PR number rather than re-parsing free text from the GitHub commit body).

### Proof of Concept
In `test/models/commits_test.rb` style (out of scope to modify per rules, but illustrating the necessary assertion):
```ruby
test "author is not spoofable via arbitrary commit message trailer" do
  attacker_commit = stub_github_commit(
    author: users(:anonymous_or_attacker_github_login),
    message: "trigger build\n\nMerge-Requested-By: walrus\n"
  )
  commit = Shipit::Commit.from_github(attacker_commit)
  refute_equal shipit_users(:walrus), commit.author
  assert_equal expected_actual_github_author, commit.author
end
```
Both sides of the binding (`commit.author` vs the actual GitHub-authenticated author of the push) diverge under current code, confirming the vulnerability.
