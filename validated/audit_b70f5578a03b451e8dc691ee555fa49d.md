### Title
`BridgeTransferERC721.handleERC721Transfer()` Uses `transferFrom()` Instead of `safeTransferFrom()`, Permanently Freezing Bridged NFTs in Non-ERC721-Receiver Contracts — (`contracts/service_chain/bridge/BridgeTransferERC721.sol`)

---

### Summary

In the lock/unlock mode of the Kaia service-chain bridge, `handleERC721Transfer()` delivers a bridged ERC721 token to the user-specified `_to` address using the unsafe `IERC721.transferFrom()`. If `_to` is a smart contract that does not implement `IERC721Receiver`, the NFT is permanently frozen there. The source-chain token has already been locked inside the bridge (or burned in mintBurn mode), so the loss is irreversible.

---

### Finding Description

`BridgeTransferERC721.handleERC721Transfer()` is the on-chain settlement function called by bridge operators after quorum is reached for a cross-chain ERC721 transfer request. In the non-mintBurn (lock/unlock) path, it executes:

```solidity
IERC721(_tokenAddress).transferFrom(address(this), _to, _tokenId);
``` [1](#0-0) 

The `_to` address originates directly from the user who called `requestERC721Transfer()` or `onERC721Received()` on the source chain:

```solidity
function requestERC721Transfer(address _tokenAddress, address _to, uint256 _tokenId, bytes memory _extraData) public {
    IERC721(_tokenAddress).transferFrom(msg.sender, address(this), _tokenId);
    _requestERC721Transfer(_tokenAddress, msg.sender, _to, _tokenId, _extraData);
}
``` [2](#0-1) 

`transferFrom()` performs no check that the recipient contract implements `onERC721Received`. The OpenZeppelin `ERC721.sol` bundled in this repository explicitly documents this:

> "Usage of this method is discouraged, use `safeTransferFrom` whenever possible." [3](#0-2) 

By contrast, `safeTransferFrom` calls `_checkOnERC721Received` and reverts if the recipient contract does not return the correct magic value: [4](#0-3) 

The ERC20 bridge counterpart correctly uses `SafeERC20.safeTransfer`, making the asymmetry clear: [5](#0-4) 

The mintBurn path (`mintWithTokenURI`) calls the internal `_mint()` which also does not invoke `_checkOnERC721Received`, so both delivery paths are affected. [6](#0-5) 

---

### Impact Explanation

A bridged ERC721 token is permanently frozen in a non-ERC721-receiver contract on the destination chain. The source-chain token is already locked inside the bridge contract (lock/unlock mode) or burned (mintBurn mode) at the time the request was emitted, so there is no recovery path. The NFT is effectively destroyed from the user's perspective — an unauthorized, irreversible asset loss affecting bridged NFTs.

---

### Likelihood Explanation

Any user who specifies a contract address as `_to` that does not implement `IERC721Receiver` triggers this. Common real-world cases include:

- Multisig wallets (Gnosis Safe and similar) that were not deployed with ERC721 receiver support
- DAO treasury contracts
- Any contract address the user mistakenly copies as the recipient

The trigger requires no privilege — any user initiating a cross-chain ERC721 transfer can hit this path. The bridge operators faithfully relay whatever `_to` was specified; they perform no recipient validation.

---

### Recommendation

Replace `transferFrom` with `safeTransferFrom` in the lock/unlock delivery path:

```solidity
// Before (unsafe):
IERC721(_tokenAddress).transferFrom(address(this), _to, _tokenId);

// After (safe):
IERC721(_tokenAddress).safeTransferFrom(address(this), _to, _tokenId);
```

For the mintBurn path, replace `mintWithTokenURI` (which calls `_mint`) with a variant that calls `_safeMint` and checks `onERC721Received` on the recipient.

---

### Proof of Concept

1. Alice owns token ID `42` of an ERC721 registered on the service chain bridge.
2. Alice calls `requestERC721Transfer(nftAddress, contractWithNoReceiver, 42, "0x")` on the source-chain bridge. Token `42` is transferred from Alice to the bridge and locked. A `RequestValueTransferEncoded` event is emitted.
3. Bridge operators observe the event and call `handleERC721Transfer(txHash, alice, contractWithNoReceiver, nftAddress, 42, nonce, blockNum, uri, "0x")` on the destination-chain bridge, reaching quorum.
4. The destination bridge executes `IERC721(nftAddress).transferFrom(address(this), contractWithNoReceiver, 42)`.
5. `contractWithNoReceiver` has no `onERC721Received` function. Because `transferFrom` (not `safeTransferFrom`) is used, no check is performed and the call succeeds.
6. Token `42` is now owned by `contractWithNoReceiver` with no way to retrieve it. The source-chain token remains locked in the bridge. Alice has permanently lost her NFT. [7](#0-6)
