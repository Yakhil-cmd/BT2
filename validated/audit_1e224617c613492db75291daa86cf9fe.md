### Title
Old address definition remains a valid spending authority after a definition change until the change unit is stable - (File: [validation.js](https://github.com/hirayap/ocore--013/blob/main/validation.js))

### Summary
When an ocore address owner rotates its spending authority via an `address_definition_change` message (the equivalent of "replacing the default superuser with a new administrator"), the protocol does not immediately and exclusively invalidate the old definition. `storage.readDefinitionByAddress`/`readDefinitionChashByAddress` only resolve to the **latest stable** definition change before `last_ball_mci`, so until the change unit becomes stable, the previous definition remains a fully valid signer for that address, exactly mirroring the Bitnami issue where the new administrator is created but the old default superuser is "left active... in certain scenarios."

### Finding Description
Address key rotation in ocore is implemented with the `address_definition_change` message, recorded in `address_definition_changes` and looked up via: [1](#0-0) 

`readDefinitionChashByAddress` explicitly picks "the last definition change" only if it is `is_stable=1 AND main_chain_index<=max_mci`; otherwise the definition_chash still equals the address, i.e., the **original/old** definition. Consequently, until a change becomes stable, the previous ("old") definition keeps validating signatures.

`validateAuthor` in `validation.js` codifies this awareness directly in a comment: [2](#0-1) 

The comment states verbatim: *"in one particular case, the attacker changes his definition then quickly sends a new ball with the old definition - the new definition will not be active yet"* — and the code's resolution is to simply accept the unit and defer to eventual-consistency ("let it be for now. Eventually, at most one of the balls will be declared good"). This is the direct structural analog of the Bitnami bug: a new authority (new definition / new superuser) is established, but the initialization/rotation process does not atomically and immediately revoke the old authority (old definition / default superuser), leaving a window where both are simultaneously valid.

The nonserial/forked-path handling in `checkNoPendingChangeOfDefinitionChash` / `checkNoPendingDefinition` further widens this window: while a pending, not-yet-stable definition change exists, only units on a path that does not include the change are blocked; an attacker who arranges his own transaction to *not* build on top of his definition-change unit can still spend using the old definition, since the address can post units on a competing/parallel path before the change stabilizes. [3](#0-2) 

### Impact Explanation
Any single-address wallet owner (or an entity impersonating one after leaking the old keys) can use the pre-rotation ("old superuser") key material to authorize spends after having supposedly rotated to a new definition, as long as the definition-change unit has not yet stabilized. Because stabilization can take multiple main-chain advances, this creates a window of unauthorized-spending / disputed-authority risk: funds sent to the address, and any AA/asset logic gated on "whoever currently controls this address," can be spent or manipulated using the retired key, undermining the intended access revocation and potentially causing double-authorization disputes that the network resolves only after the fact via the nonserial/'good' vs 'bad' sequencing mechanism.

### Likelihood Explanation
This does not require a malicious peer, node, or hub — it is fully reachable by a single unprivileged unit poster performing a normal key-rotation (`address_definition_change`) followed immediately by another unit signed with the old key, which is precisely the scenario the code comment itself documents as an anticipated attack pattern. No special network position or leaked infrastructure secret beyond the address owner's already-known "old" private key is needed.

### Recommendation
Enforce that once an `address_definition_change` unit for an address is included (even before full stabilization) in a valid, non-conflicting sequence, subsequent units built on that path must reject signatures produced with the superseded definition, rather than relying purely on post-hoc stable/non-stable sequencing to resolve the conflict. At minimum, tighten `checkNoPendingChangeOfDefinitionChash`/`checkNoPendingDefinition` so an old definition cannot be used to authorize new spends once a pending, non-conflicting definition change from the same address is known, closing the window described in the code comment in `validation.js`.

### Proof of Concept
1. Address `A` is defined by key `K_old`.
2. Owner (or attacker in possession of `K_old`) posts unit `U1` containing an `address_definition_change` message setting `A`'s definition to `K_new` (see `writer.js` insertion into `address_definition_changes`, cited above).
3. Before `U1` becomes stable, the same actor posts unit `U2` from address `A`, signed with `K_old`, on a parent path that does not include `U1`.
4. Per `readDefinitionChashByAddress`, since no stable definition change exists yet at `U2`'s `last_ball_mci`, `A`'s definition still resolves to `K_old`, so `U2` validates successfully — the "old superuser" key is still an accepted authority even though a replacement was already broadcast.

function readDefinitionChashByAddress(conn, address, max_mci, handle){
	if (!handle)
		return new Promise(resolve => readDefinitionChashByAddress(conn, address, max_mci, resolve));
	if (max_mci == null || max_mci == undefined)
		max_mci = MAX_INT32;
	// try to find last definition change, otherwise definition_chash=address
	conn.query(
		"SELECT definition_chash FROM address_definition_changes CROSS JOIN units USING(unit) \n\
		WHERE address=? AND is_stable=1 AND sequence='good' AND main_chain_index<=? ORDER BY main_chain_index DESC, level DESC LIMIT 1", 
		[address, max_mci], 
		function(rows){
			var definition_chash = (rows.length > 0) ? rows[0].definition_chash : address;
			handle(definition_chash);
	});
}
