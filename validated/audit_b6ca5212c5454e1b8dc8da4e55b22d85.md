### Title
Cross-repository status forgery bypasses merge-queue CI gate via unscoped `Commit.where(sha:)` lookup - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` looks up commits purely by `sha` with no repository scoping, unlike `CheckSuiteHandler` which correctly scopes lookups through `stacks.where(...)` derived from the payload's `repository.full_name`. Any GitHub webhook sender (an attacker who owns an unrelated repo B) can post a `status` event naming a sha that also exists as a pending `MergeRequest#head` commit on a victim's stack A, and that status will be recorded against stack A's commit, flipping `MergeRequest#all_status_checks_passed?` to true.

### Finding Description
The broken binding is: `payload.repository.full_name == stack_that_owns(Commit.find_by(sha: params.sha)).repository.full_name`. This equality is never checked.

`StatusHandler#process` is:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [1](#0-0) 

Note the base `Handler` class exposes a `stacks` helper that scopes by `repository_name` (`payload.dig('repository', 'full_name')`), and `CheckSuiteHandler` uses it correctly (`stacks.where(branch: ...).each { |stack| stack.commits.where(sha: ...) }`) [2](#0-1) . `StatusHandler`, however, bypasses this scoping entirely and queries the global `Commit` table by `sha` only.

The controller's `verify_signature` only checks that the payload's `repository.owner.login` belongs to a GitHub App/organization Shipit trusts [3](#0-2) ; it does not verify that the specific repository named in the payload is the one that actually owns the sha being updated. So an attacker who owns repo B (in an org Shipit is configured for, or any org where they can install/trigger the app's webhook - this could even be the attacker's own free GitHub org connected as a Shipit organization) can send a legitimately-signed `status` webhook for repo B, with `sha` cherry-picked/copied to be identical to the head sha of a pending MergeRequest on unrelated stack A.

`Commit.where(sha: params.sha)` will match commit rows across all stacks with that sha, and `create_status_from_github!` will write a new `Status` row for stack A's commit [4](#0-3) . This causes `MergeRequest::StatusChecker.new(head, ...).success?` to become true, so `MergeRequest#all_status_checks_passed?` returns true [5](#0-4) , and `reject_unless_mergeable!` no longer rejects on `ci_missing`/`ci_failing` [6](#0-5) . `ProcessMergeRequestsJob#perform` then proceeds to call `merge_request.merge!`, which merges the PR on GitHub via `stack.github_api.merge_pull_request` [7](#0-6) [8](#0-7) .

Existing guards do not close the gap: `verify_signature` authenticates that the payload originated from a GitHub org/app Shipit trusts, not that the sha belongs to that repo's own commit graph; `ExplicitParameters` schema on `StatusHandler` only validates types/presence of `sha`, `state`, etc. and performs no repository binding [9](#0-8) .

### Impact Explanation
A payload authenticated for one repository (B) causes state mutation (a `Status` record, and consequently merge-queue approval and an actual GitHub merge) on a different repository/stack (A) that never authenticated it. This matches the Critical category: "a payload for one repository mutating another's stack, commit, task or team" and "an unauthorized deploy, rollback or merge." The blast radius spans any two repositories/stacks configured in the same Shipit instance (or even any Shipit instance where the attacker can get a `status` webhook accepted, e.g., via an org they control being registered), since the vulnerable lookup is entirely global and repository-agnostic.

### Likelihood Explanation
Preconditions: (1) stack A must have a pending `MergeRequest` with `merge_queue_enabled` whose CI is not yet green, (2) attacker needs a repo (B) whose webhooks are accepted by the Shipit instance's `verify_signature` (i.e., an org in `Shipit.github_teams`/configured GitHub App installs), and (3) attacker must be able to produce an identical sha across repos (trivial via cherry-pick, since git SHAs are computed from tree+parent+metadata, or simply guessable/observable if commits are pushed to both a public upstream and attacker's fork before the PR is opened). None of these require any Shipit credentials — only the ability to author commits and trigger a real `status` webhook from a repository the attacker controls. This is a low-cost, repeatable attack once the attacker has webhook access to any trusted-org repo.

### Recommendation
Scope `StatusHandler#process` to the repository named in the payload, mirroring `CheckSuiteHandler`:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
end
```
This uses the inherited `stacks` helper (`Repository.from_github_repo_name(repository_name)&.stacks`) to ensure a status can only ever be applied to commits belonging to the repository that authenticated the webhook.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb` or equivalent):
```ruby
test "status webhook for a different repository does not update an unrelated stack's commit" do
  stack_a = shipit_stacks(:shipit) # repository X
  sha = "deadbeef" * 5 # 40 hex chars
  commit = stack_a.commits.create!(sha:, message: "test")
  merge_request = stack_a.merge_requests.create!(number: 999, head: commit, merge_status: "pending")

  refute merge_request.all_status_checks_passed?

  # Forged payload: repository.full_name = "attacker/repo-b", but sha matches stack_a's commit
  payload = {
    "sha" => sha,
    "state" => "success",
    "context" => "ci/attacker",
    "repository" => { "full_name" => "attacker/repo-b" },
  }
  Shipit::Webhooks::Handlers::StatusHandler.call(payload)

  commit.reload
  merge_request.reload

  # Assert both sides of the broken binding: repository that authenticated payload != stack_a.repository
  refute_equal "attacker/repo-b", stack_a.repository.full_name

  # Yet the forged status was applied and flips the CI gate
  assert merge_request.all_status_checks_passed?, "forged cross-repo status should NOT satisfy stack A's CI gate"
  assert_equal false, merge_request.reject_unless_mergeable!
end
```
Expected (buggy) result: `all_status_checks_passed?` becomes `true` and `reject_unless_mergeable!` returns `false`, despite the payload's repository never matching stack A's repository — demonstrating the violation. After applying the fix (scoping by `stacks`), the status will not be created against `stack_a`'s commit and the assertions should be inverted (`refute merge_request.all_status_checks_passed?`).
