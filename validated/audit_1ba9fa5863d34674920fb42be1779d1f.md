### Title
Cross-repository commit-status forgery via unscoped SHA lookup in webhook `StatusHandler` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
The webhook signature-verification layer authenticates a `status` event only against the GitHub organization derived from the payload's `repository.owner.login`, but the handler that actually mutates state, `StatusHandler`, never re-checks that the `sha` in the payload belongs to a commit in that same repository. It matches purely by SHA across the entire `commits` table, so a status webhook that is validly signed for organization/repository A can write a commit status onto a commit that actually belongs to a completely different, unrelated repository B tracked by the same Shipit instance.

### Finding Description
`WebhooksController#verify_signature` selects the GitHub App/webhook secret to validate the signature using only `repository_owner`, taken from the untrusted JSON body (`params.dig('repository', 'owner', 'login')`): [1](#0-0) [2](#0-1) 

This only proves the request came from GitHub for *some* repository owned by that organization (an organization that legitimately has commits synced into Shipit) — it says nothing about which specific commit/repository the payload's `sha` should apply to.

The dispatched handler for `status` events is `Shipit::Webhooks::Handlers::StatusHandler`: [3](#0-2) 

Unlike every other handler (`PushHandler`, `PullRequest::*Handler`, `MembershipHandler`), which resolve `Repository.from_github_repo_name(params.repository.full_name)` before touching any records (see `Handler#stacks`/`#repository_name`) [4](#0-3) , `StatusHandler#process` performs a **global, unscoped** lookup:

```ruby
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
``` [5](#0-4) 

`Commit.sha` is not required to be globally unique per-repository semantics in Shipit's schema — different repositories can independently contain commits whose SHA values collide (e.g., an attacker can craft a commit with content chosen so its SHA1 matches a target commit's SHA1, or, more simply, cherry-pick/replay the exact same commit into an org/repo they control, producing an identical SHA). Because the handler ignores `params.repository` entirely, any signed `status` webhook from an org the attacker can push commits/CI statuses to can update `create_status_from_github!` on a commit belonging to a totally different stack/repository, as long as the SHA matches.

This breaks the binding the task asks to evaluate as an equality:
`organization that authenticated == repository whose commit is written`
Before the attack: signature verification org == webhook's own repository == commit written. After the attack: signature verification org (attacker-controlled repo's org) != actual repository owning the `Commit` row that gets mutated.

### Impact Explanation
`create_status_from_github!` directly feeds `Commit#status`, `Commit#blocked?`/`deployable?`, and the merge queue/continuous-delivery decision logic: [6](#0-5) [7](#0-6) 

An attacker who controls (or has push/CI access to) any single repository whose organization is registered in Shipit's GitHub App configuration can forge a `status` webhook (with a real, validly-signed delivery from GitHub for that repo) carrying a SHA that collides with a commit in a victim stack, and mark it `success`, thereby unblocking `blocked?` and enabling deploys/continuous delivery for a repository the attacker has no access to. This is a cross-repository write and can lead to an unauthorized deploy — matching the Critical/High impact categories in scope (cross-repository writes / unauthorized deploy).

### Likelihood Explanation
The likelihood is constrained by the difficulty of producing a genuine SHA1 collision or otherwise getting the exact same commit SHA recognized in two different tracked repositories/organizations (e.g., via commit replay/cherry-pick across forks/mirrors that Shipit also tracks, or shared-history repos). It does not require any Shipit session, API token, or webhook secret — only the ability to have GitHub deliver one legitimately-signed `status` event for a repository the attacker controls. This is more constrained than a trivial forgery but is a genuine architectural gap: the handler was clearly intended to be scoped by repository (as all sibling handlers are) but omits that check.

### Recommendation
Scope `StatusHandler#process` to the repository named in the payload, mirroring `Handler#stacks`/`Repository.from_github_repo_name(params.repository.full_name)`, e.g. `stacks.joins(:commits).merge(Commit.where(sha: params.sha))`, or otherwise verify `commit.stack.repository == repository_from_payload` before calling `create_status_from_github!`.

### Proof of Concept
1. Attacker controls (or has CI/push rights to) repository `attacker-org/repo-x`, whose organization `attacker-org` is configured as a valid GitHub App organization in Shipit's `secrets.github` multi-org config (a real, distinct org from the victim's).
2. Attacker crafts/replays a commit into `repo-x` whose SHA1 is identical to a commit SHA already tracked by Shipit for the victim stack `victim-org/repo-y` (e.g. via cherry-pick/fork history reuse, or a genuine SHA1 collision).
3. Attacker triggers (via GitHub Actions/CI in `repo-x`, which they control) a `status` API call setting state `success` for that SHA. GitHub delivers a `status` webhook to Shipit, signed with `attacker-org`'s webhook secret.
4. `WebhooksController#verify_signature` validates the signature successfully because it only checks against `attacker-org`'s secret, matching `repository.owner.login == "attacker-org"`.
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)`, finds the victim's commit row (belonging to `victim-org/repo-y`), and calls `create_status_from_github!`, marking it `success` regardless of the real CI state on `repo-y`.
6. If this satisfies `victim-org/repo-y`'s required/blocking statuses, `deployable?` becomes true and continuous delivery/merge queue proceeds — an unauthorized deploy triggered purely by webhook traffic the attacker generated on their own unrelated repository.

module Shipit
  module Webhooks
    module Handlers
      class StatusHandler < Handler
        params do
          requires :sha, String
          requires :state, String
          accepts :description, String
          accepts :target_url, String
          accepts :context, String
          accepts :created_at, String

          accepts :branches, Array do
            requires :name, String
          end
        end

        def process
          Commit.where(sha: params.sha).each do |commit|
            commit.create_status_from_github!(params)
          end
        end
      end
