This confirms the exploit path. `require_permission :read, :stack` is checked via `ApiClient#check_permissions!`, which only checks the `permissions` array — it never checks `stack_id`. Scoping is enforced separately, only through `BaseController#stack` calling `stacks.from_param!`, where `stacks` returns `Stack.all` whenever `current_api_client.stack_id` is nil.### Title
CCMenu API token minted for one stack authorises reading every stack in the deployment - ([File: app/controllers/shipit/ccmenu_url_controller.rb])

### Summary
`CCMenuUrlController#fetch` mints an `ApiClient` token intended to expose a single stack's CI status to unauthenticated CCTray/CCMenu consumers, but the token it creates carries the `read:stack` permission with no `stack` (and therefore no `stack_id`) binding. Because `Shipit::ApiClient#check_permissions!` only checks the permission name, and `Api::BaseController#stacks` treats an absent `stack_id` as "all stacks," the resulting token silently authorizes reading any stack, task, deploy, and task output in the Shipit instance — not just the stack the user requested a CCMenu URL for.

### Finding Description
`CCMenuUrlController#fetch` builds the token this way: [1](#0-0) 

```ruby
def fetch
  uri = URI(api_stack_ccmenu_url(stack_id: stack.to_param))
  uri.query = { 'token' => client.authentication_token }.to_query
  render(json: { ccmenu_url: uri.to_s })
end

private

def client
  @client ||= ApiClient.create_with(permissions: %w[read:stack])
                       .find_or_create_by!(creator: current_user, name: 'CCMenu Client')
end

def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end
```

`stack` is resolved from `params[:stack_id]` purely to build the display URL; it is never passed into the `ApiClient` (no `stack:` attribute is set on `create_with`/`find_or_create_by!`). The `ApiClient` model's `stack` association is optional and permission enforcement is name-only: [2](#0-1) 

Authorization for stack-scoped API endpoints is enforced in two independent, unlinked places: `require_permission` checks only the named permission, while stack scoping is a *separate* mechanism based on `stack_id?`: [3](#0-2) [4](#0-3) 

```ruby
def stacks
  @stacks ||= current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all
end

def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end

def require_permission!(operation, scope)
  current_api_client.check_permissions!(operation, scope)
end
```

Since the CCMenu client never sets `stack_id`, `current_api_client.stack_id?` is false, so `stacks` resolves to `Stack.all` for every controller that uses `require_permission :read, :stack` — including `Api::TasksController` (task list/show), `Api::OutputsController` (raw deploy/task log output), `Api::CommitsController`, and `Api::StacksController#show`: [5](#0-4) [6](#0-5) 

Additionally, `find_or_create_by!(creator: current_user, name: 'CCMenu Client')` means the *same* single ApiClient record and the *same* token are reused across every stack for which that user ever clicks "Fetch URL" (the settings page invokes this per-stack) — confirmed by the test asserting no new `ApiClient` is created on repeat fetches, and confirmed the token is embedded directly and persistently in the returned URL: [7](#0-6) 

This breaks the intended binding: "the stack a token authorises == the stack a token can touch." Before the flaw, one would expect a per-stack scoped `ApiClient` (as `Api::CCMenuController#authenticate_api_client` implies is the expected model, since it authenticates arbitrary tokens against arbitrary `stack_id`s in the URL). After minting via `CCMenuUrlController`, the token authorises exactly one stack in the visible URL, but the underlying `ApiClient` record touches every stack in the Shipit instance.

### Impact Explanation
Any authenticated Shipit user (an unprivileged team member with UI access, not an `ApiClient` token holder) can navigate to any stack's settings page, click "Fetch URL," and receive a long-lived bearer token (`api_clients_secret`-signed) that grants `read:stack` over the entire Shipit installation. The `token` query parameter is designed to be pasted into third-party CCTray tools and is not treated as highly sensitive by the UI (displayed in plain HTML, not masked), increasing the chance of accidental exposure (e.g., leaked in CI logs, browser history, shared CCTray configs, or via `Referer` headers to the third-party monitoring tool). Once obtained by another party, that token can read deploy/task output (`OutputsController`), task metadata, and stack details for every repository/stack managed by the Shipit instance, regardless of which specific stack the token nominally belongs to. This is an unauthenticated read of stack state and task/deploy output across the entire deployment, which maps to the "High" impact category (unauthenticated read of stack state, task streams, or deploy output).

### Likelihood Explanation
The flaw requires no special privilege beyond being a logged-in Shipit user able to view a single stack's settings page — the standard, lowest level of application access. The vulnerable code path (`CCMenuUrlController#fetch`) is reachable via a documented UI feature (the "Fetch URL" button on `app/views/shipit/stacks/settings.html.erb`), and the resulting URL/token is meant to be shared externally with CI-status-monitoring tools, which increases the realistic chance of accidental broader exposure of an over-scoped credential.

### Recommendation
Bind the `ApiClient` created by `CCMenuUrlController#client` to the specific `stack`, e.g. `ApiClient.create_with(permissions: %w[read:stack], stack:).find_or_create_by!(creator: current_user, name: 'CCMenu Client')`, and make the `find_or_create_by!` lookup itself scoped per stack (currently it is scoped only by `creator` and `name`, so a single client is shared/reused across all of that user's stacks). This restores the invariant that a token's authorized scope (`stack_id`) matches the single stack it is intended to expose.

### Proof of Concept
1. As any authenticated Shipit user, visit `Stack A`'s settings page and click "Fetch URL" under CCMenu — this calls `GET /ccmenu/*stack_id_A` → `CCMenuUrlController#fetch`, creating (or reusing) an `ApiClient` named "CCMenu Client" with `permissions: ["read:stack"]` and `stack_id: nil`, returning a token `T`.
2. Using token `T`, issue `GET /api/stacks/<owner>/<repo-B>/<env-B>/tasks/<id>/output` with HTTP Basic auth `T` (per `Api::BaseController#authenticate_api_client`), for a completely unrelated `Stack B` that the user never selected when fetching the CCMenu URL.
3. Because `current_api_client.stack_id?` is `false`, `Api::BaseController#stacks` returns `Stack.all`, so `stack` resolves successfully to `Stack B`, `require_permission :read, :stack` passes (permission name matches), and the raw task/deploy log output for `Stack B` is returned — despite the token having been issued and displayed to the user as belonging only to `Stack A`.
