### Title
Webhook signature verified against `repository.owner.login`, but event processed against unrelated `repository.full_name` — cross-repository status/commit forgery - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`Shipit::WebhooksController#verify_signature` selects which GitHub App/organization secret to validate the incoming webhook's HMAC signature against based on `repository.owner.login` (with an `organization.login` fallback), but the handler that actually mutates state (`Handler#repository_name`, used by `Repository.from_github_repo_name`) reads a completely independent field, `repository.full_name`, taken from the same attacker-controlled JSON body. Because these two fields are not cross-validated, a party who legitimately administers (and therefore knows the `webhook_secret` for) one Shipit-configured GitHub organization can forge a signed payload whose `owner.login` matches their own org but whose `full_name` points at any other organization/repository tracked by the same Shipit instance, causing Shipit to write state for a repository the requester does not control.

### Finding Description
`verify_signature` computes the app/secret to check against from the payload itself: [1](#0-0) [2](#0-1) 

The signature check itself only verifies the raw body against the secret associated with that derived organization, via HMAC: [3](#0-2) 

Once the request passes this check, every registered handler for the event is invoked with the full, attacker-suppliable JSON body: [4](#0-3) 

All handlers (`push_handler.rb`, `status_handler.rb`, `check_suite_handler.rb`, the `pull_request/*` handlers) resolve the target `Repository`/`Stack` using a *different* field of the same body, `repository.full_name`, via the shared base class: [5](#0-4) [6](#0-5) 

Because the signature is only proof that "the sender knows the webhook secret configured for the organization named in `repository.owner.login`," and nothing binds that org to the `owner`/`name` encoded in `repository.full_name`, the equality the engine implicitly relies on — *organization that authenticated == repository that is written* — does not hold. An operator/admin of Organization A (who knows Org A's `webhook_secret`, e.g., because they configured that GitHub App installation themselves in a multi-tenant Shipit deployment) can:
1. Craft a JSON body with `repository.owner.login = "org-a"` (satisfies `verify_signature`'s lookup and the HMAC check against org A's known secret) but `repository.full_name = "org-b/victim-repo"` (used by every handler to select the `Stack`/`Repository` to act on).
2. Sign the raw body with Org A's secret and send it to `POST /webhooks` with the corresponding `X-Hub-Signature` and `X-Github-Event` headers.
3. Shipit accepts the signature (Org A's secret matches) and then executes the handler logic against Org B's `Stack`, over which the requester has no legitimate authority.

This is not a theoretical GitHub-relay scenario: GitHub itself signs the *entire* raw body it delivers, so a genuine GitHub-originated webhook can't have mismatched `owner.login`/`full_name`. The exploitable path is that Shipit's endpoint is reachable directly by anyone who knows any one configured org's `webhook_secret` — which multiple organization admins onboarded onto a shared Shipit instance legitimately possess for their own org — and nothing stops them from using it to sign payloads describing a different org's repository.

### Impact Explanation
Depending on event type, this allows cross-repository writes without holding any credential for the victim repository:
- `status` events create/overwrite a `Status` for an arbitrary commit SHA on the victim stack, which can satisfy `required_statuses`/CI gating checks defined in the victim's `shipit.yml` (`deploy_spec.rb#required_statuses`), potentially enabling deploy safety checks to pass fraudulently — feeding directly into `Stack#trigger_deploy`/continuous delivery flows.
- `push` events enqueue `GithubSyncJob` for the victim `Stack`, altering the commit list Shipit believes exists for that stack.
- `check_suite`/`membership`/`pull_request` handlers likewise act on attacker-chosen `full_name` or team/membership data.

This crosses the "cross-repository writes" / "unauthorized deploy" Critical-impact bar because it lets a party outside a repository's trust boundary influence the deploy-gating state of a stack they don't own.

### Likelihood Explanation
Requires the attacker to know a `webhook_secret` for at least one organization configured in the same Shipit instance — plausible in any multi-tenant deployment where Shipit hosts several unrelated GitHub orgs/App installations, since each org's admin necessarily knows (or set) that secret when installing the App. No Shipit session, `ApiClient` token, or repository write access is needed for the victim's repository.

### Recommendation
Bind the field used to select the GitHub App/secret to the field used to select the target repository: derive the verification organization strictly from the same `repository.full_name`/`repository.owner.login` pair the handlers use to resolve the `Repository`, and reject payloads where the two disagree. Alternatively, verify the signature per-repository (looking up the `GitHubApp` via the resolved `Repository`'s stored owner rather than trusting an unauthenticated field pulled straight out of the still-unverified payload) before dispatching to any handler.

### Proof of Concept
1. Shipit instance configures two orgs in `secrets.yml`: `org-a` (secret known to attacker, who administers the App installation for `org-a`) and `org-b` (tracked victim org with a `Stack` for `org-b/victim-repo`).
2. Attacker builds a `push` payload body:
```json
{
  "repository": { "owner": { "login": "org-a" }, "full_name": "org-b/victim-repo" },
  "ref": "refs/heads/main",
  "after": "deadbeef...",
  "commits": [...]
}
```
3. Attacker computes `sha1=<hmac>` over the exact raw body using `org-a`'s `webhook_secret` (matches `DeliverySigner`/`verify_webhook_signature` in `lib/shipit/github_app.rb:76-83`) and sends:
```
POST /webhooks
X-Github-Event: push
X-Hub-Signature: sha1=<hmac>
```
4. `verify_signature` resolves `repository_owner` = `"org-a"`, fetches `org-a`'s `GitHubApp`, and the signature validates successfully (`app/controllers/shipit/webhooks_controller.rb:24-30,59-62`).
5. `PushHandler` (subclass of `Handler`) resolves `repository_name` from `payload.dig('repository','full_name')` = `"org-b/victim-repo"` (`app/models/shipit/webhooks/handlers/handler.rb:36-38`), loads Org B's `Stack`, and enqueues `GithubSyncJob` for it — a write performed on a repository the requester never authenticated against.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
