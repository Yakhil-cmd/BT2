### Title
Bad-debt wipeout clamps the supply index instead of zeroing claims, leaving stranded shares that drain future depositors - (File: contracts/pool/src/interest.rs)

### Summary
`apply_bad_debt_to_supply_index` socializes bad debt by shrinking `supply_index`, but unconditionally floors the result at `SUPPLY_INDEX_FLOOR_RAW` (RAY/1000). When the written-down debt equals or exceeds the entire supplied value, supplier shares are not zeroed — they retain a residual claim valued at the floored index. The pool continues to honor `withdraw` for these stranded shares against any future cash, so wiped-out lenders can drain deposits made by subsequent suppliers. This is the on-chain analog of the report's class: a missing boundary check (index floor instead of claim zeroing) lets corrupted state persist and keep producing harm after the triggering event.

### Finding Description
`apply_bad_debt_to_supply_index` computes `remaining = total_supplied_value - min(bad_debt, total_supplied_value)`, derives `reduction_factor = remaining / total_supplied_value`, and sets `supply_index = max(supply_index * reduction_factor, SUPPLY_INDEX_FLOOR_RAW)` (contracts/pool/src/interest.rs:73-89). When `bad_debt >= total_supplied_value`, `remaining` is zero and the mathematically correct new index is zero — but the floor forces it to `RAY/1000`, resurrecting a ~0.1% claim on every share that economically should be worthless.

Shares are never burned: the pool stores only totals, and account positions keep their `scaled_amount`. Withdrawal then values the position as `unscale_supply_floor(pos_scaled, supply_index)` — still positive — and pays it via `resolve_withdrawal` → `require_reserves` → `debit_cash` → `transfer_out` (contracts/pool/src/ops/withdraw.rs:93-119, common/src/rates/scaling.rs:105-121, contracts/pool/src/cache/cash.rs:34-53). The only supply-side guard, `require_supply_for_debt`, rejects `supplied == 0 && borrowed != 0`, which does not apply here since `supplied` remains nonzero and debt was burned (contracts/pool/src/guards.rs:69-73). `require_utilization_below_max` returns early when `borrowed == 0` (guards.rs:19-27). So nothing blocks the payout.

The repo's own unit tests demonstrate both mechanics in `contracts/pool/tests/interest.rs`: `test_raw_cache_floor_clamp_strands_claim_without_supply_guard` and `test_raw_cache_seizure_residual_would_drain_fresh_cash_without_supply_guard` show a wiped position extracting exactly a fresh depositor's funds (interest.rs:372-494). They assert the flow fails only "without supply guard" — but the guards that exist (`require_reserves`, `require_supply_for_debt`, utilization check) do not prevent it, because they check cash sufficiency and empty-supply state, not whether the shares still represent real backing.

Reachability: the write-down path is driven by permissionless `liquidate`/`clean_bad_debt` flows (both listed in scope). An attacker engineers a position that goes deeply underwater (or accumulates dust bad debt across `clean_bad_debt` calls) until remaining debt reaches the supplied total, producing the clamp.

### Impact Explanation
Permanent loss for fresh depositors: any supplier depositing after a full wipeout funds the stranded residual claims of wiped lenders. Each withdrawal of stranded shares transfers real tokens against no backing — direct theft of user funds, quantified by the residual claim (~0.1% of pre-wipeout supply value per share set, unbounded across repeated deposit/withdraw cycles as long as new cash arrives). The pool's books silently become insolvent (`supplied` claim > `cash + debt`) with no revert.

### Likelihood Explanation
Requires a complete (or near-complete) bad-debt wipeout of a market: debt written down must reach total supplied value so `reduction_factor` hits zero. That is an extreme but reachable state via the listed `liquidate`/`clean_bad_debt` entrypoints in a severe price move, and the flaw also applies to partial write-downs where the residual inflates claims beyond actual backing whenever `bad_debt` approaches the cap. Once triggered, exploitation needs only a subsequent `supply` by any victim plus a `withdraw` by a stranded-share holder — both permissionless. Medium-to-low likelihood, matching Medium severity.

### Recommendation
When `bad_debt >= total_supplied_value`, the index floor must not resurrect claims. Either (a) zero the market: burn/flag `supplied` and `revenue` shares as worthless and skip the floor, or (b) add a withdrawal-time guard that rejects payouts when the floored index was reached via a wipeout (e.g., persist a `wiped` flag in `PoolState` and have `resolve_withdrawal` return zero for pre-wipeout shares). At minimum, apply the floor only when `remaining > 0`, so a fully consumed supply value yields index 0 and `unscale_supply_floor` returns 0 for all stranded shares (contracts/pool/src/interest.rs:80-88).

### Proof of Concept
Conceptual sequence (mirroring `test_raw_cache_floor_clamp_strands_claim_without_supply_guard` at contracts/pool/tests/interest.rs:372-428):

1. Attacker supplies and borrows to build a position; a price crash makes it deeply underwater. Keeper/attacker calls `liquidate`/`clean_bad_debt` until bad debt written down ≥ total supplied value.
2. `apply_bad_debt_to_supply_index` clamps `supply_index` to `SUPPLY_INDEX_FLOOR_RAW` instead of 0; all supply shares keep a positive `unscale_supply_floor` value while `cash == 0` and `borrowed == 0`.
3. Victim calls `supply(amount)` → `mint_supply` + `credit_cash`; market now holds real tokens.
4. Stranded-share holder calls `withdraw(0)` (withdraw-all): `resolve_withdrawal` returns `(pos_scaled, floor_value > 0)`; `require_reserves` passes against the victim's cash; `debit_cash` + `transfer_out` pay real tokens.
5. Victim's remaining claim `unscale_supply_floor(their_scaled)` now exceeds `cache.cash()` — their deposit is unrecoverable; the attacker netted the residual claim value in tokens.

Caveat: I verified the pool-side math and guards directly, but did not fully trace the controller's liquidation/clean_bad_debt call path to confirm no additional zeroing of positions occurs there; if the controller burns wiped positions' shares, the residual survives only for shares not passed through that path (e.g., other suppliers), which the seizure-residual test (interest.rs:430-494) indicates is exactly the case.
