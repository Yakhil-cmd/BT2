### Title
`StatusHandler#process` writes GitHub status updates to commits in any stack sharing a `sha`, not just the webhook's own repository - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` looks up commits via `Commit.where(sha: params.sha).each`, which is global across all stacks/repositories, and calls `commit.create_status_from_github!(params)` on every match. The verified webhook payload's `repository.full_name` is never used to scope this query, so a status event legitimately signed for one repository can mutate `Status` rows attached to a `Commit` belonging to a completely different tenant's `Stack` if the sha happens to collide.

### Finding Description
The broken binding is: the webhook is only cryptographically bound to `repository_owner` (`payload.dig('repository','owner','login')`) via `verify_signature`/`GithubApp#verify_webhook_signature` in `app/controllers/shipit/webhooks_controller.rb` [1](#0-0)  - i.e. `commit.stack.repository.owner == payload.repository.owner` is verified, but the code never checks `commit.stack.repository.full_name == payload.repository.full_name`.

`StatusHandler#process` does:
```ruby
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
``` [2](#0-1) 

This queries `Commit` globally by `sha` alone with no `stack_id`/repository filter, even though the base `Handler` class already exposes a `stacks` helper method scoped to the payload's repository (`Repository.from_github_repo_name(repository_name)&.stacks`) [3](#0-2) , which `StatusHandler` does not use. `Commit#sha` has no uniqueness validation scoped to `stack_id` and is not namespaced by repository in the schema, so two different stacks (owned by different organizations, verified independently by `verify_signature` per `repository_owner`) can legitimately contain `Commit` rows with an identical `sha` (fork cherry-picks, shared upstream commits, or crafted empty-commit sha collisions).

`create_status_from_github!` unconditionally writes to `statuses` scoped to that commit's `stack_id`:
```ruby
def create_status_from_github!(github_status)
  add_status do
    statuses.replicate_from_github!(stack_id, github_status)
  end
end
``` [4](#0-3) 

`add_status` further triggers `Hook.emit(:commit_status, ...)`/`Hook.emit(:deployable_status, ...)` and `stack.schedule_merges` for the *victim* stack, potentially unblocking a merge or deploy for a repository the attacker never authenticated against [5](#0-4) .

Exploit flow: attacker pushes a commit to their own fork/branch whose sha matches (or is crafted to match, e.g. an empty commit with identical tree/parent/author/committer timestamps and message) a commit sha that already exists as a `Commit` row in a victim stack (e.g., both forked from the same upstream, or attacker mirrors victim's public commit). Attacker's own repo emits a `status` webhook (which they fully control since it's their own repo/CI) with that sha and `state: success`. GitHub signs this using the attacker's own repo's signature, verified correctly by `verify_signature`. `StatusHandler#process` then updates status for *every* `Commit` row with that sha across *all* stacks in the Shipit install, including the victim's, marking it as success/failure and potentially triggering `stack.schedule_merges` or deployability changes for the victim's stack.

No existing guard prevents this: `verify_signature` only checks the signing organization matches `repository_owner`, not that `Commit.stack.repository == payload.repository`; `ExplicitParameters` schema in `StatusHandler` only validates payload shape, not repository scoping; `drop_unhandled_event` and `check_if_ping` are unrelated.

### Impact Explanation
A single crafted/collided status webhook from an attacker-controlled repository can flip commit status (success/failure/pending) on a commit row belonging to a different, unrelated tenant's stack, which can (a) unblock `deployable?`/`blocked?` checks for that victim commit, (b) trigger `stack.schedule_merges` via `add_status`, and (c) fire `Hook.emit` for the victim stack. This is a cross-tenant payload writing to another repository's stack/commit state without that repository authenticating the request - matching the Critical category "a payload for one repository mutating another's stack, commit, task or team." The attack is repeatable against any sha collision the attacker can arrange or find, and scales to any number of stacks sharing the sha.

### Likelihood Explanation
Requires the attacker to control a real GitHub repository (any account can create one) and to get a matching `sha` into a victim's `Commit` table - the most reliable route being cherry-picking/forking a commit that already exists upstream and is also tracked by a victim's Shipit stack (a common and low-cost scenario for public open-source projects using Shipit, e.g. tracking the same upstream repo from multiple forks/orgs). Full sha-preimage collision crafting is not required for the common case. No Shipit secrets, sessions, or privileged roles are needed - only the ability to push a commit and have GitHub emit a `status` event for it, which is standard CI behavior.

### Recommendation
Scope the commit lookup in `StatusHandler#process` to the stacks associated with the verified webhook's own repository, e.g. use the `stacks` helper (`Repository.from_github_repo_name(repository_name)&.stacks`) already defined in `Handler`, and query `Commit.where(sha: params.sha, stack_id: stacks.select(:id))`, or otherwise validate `commit.stack.repository.full_name == repository_name` before calling `create_status_from_github!`.

### Proof of Concept
minitest plan (to be placed under `test/` for `StatusHandler`, e.g. `test/models/webhooks/handlers/status_handler_test.rb`):

1. Create `repo_a = Shipit::Repository.create!(owner: 'org-a', name: 'app')` and `stack_a = Shipit::Stack.create!(repository: repo_a, ...)`.
2. Create `repo_b = Shipit::Repository.create!(owner: 'org-b', name: 'app')` and `stack_b = Shipit::Stack.create!(repository: repo_b, ...)`.
3. Create `commit_a = Shipit::Commit.create!(stack: stack_a, sha: 'deadbeef'*5, ...)` and `commit_b = Shipit::Commit.create!(stack: stack_b, sha: 'deadbeef'*5, ...)` (same sha, different stacks).
4. Build a payload where `payload['repository']['full_name'] == 'org-a/app'` and `sha == 'deadbeef'*5`, `state: 'success'`.
5. Call `Shipit::Webhooks::Handlers::StatusHandler.call(payload)`.
6. Assert: `commit_a.reload.status.success?` is true (expected, matches payload's repo).
7. Assert: `commit_b.reload.status` is unchanged / not success (currently fails - `commit_b`'s status gets updated too because the query in `StatusHandler#process` is not scoped by repository, demonstrating `commit.stack_id` (mutated) != stack owned by `payload.repository.full_name`).

    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
