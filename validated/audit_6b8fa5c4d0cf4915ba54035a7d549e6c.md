### Title
Terminal escape sequence injection via unsanitized release body/asset names in `renderReleaseTTY` - ([File: pkg/cmd/release/view/view.go])

### Summary
`renderReleaseTTY` prints `release.Body` through `markdown.Render` and `release.Assets[].Name` through `tableprinter.AddField` as plain Go `string` values, without ever routing them through `iostreams.NewUntrusted`, the sanitization wrapper the codebase already defines specifically for external content printed to a terminal. An attacker who publishes a release on a repo the victim points `gh release view` at can embed ANSI/C0 control sequences in the release body or an asset file name and have them reproduced verbatim in the victim's terminal output.

### Finding Description
`shared.FetchRelease`/`shared.FetchLatestRelease` populate `release.Body` and `release.Assets[].Name` as ordinary `string` fields decoded straight from the GitHub API JSON response, i.e. fully attacker-controlled content [1](#0-0) . In `renderReleaseTTY`, the body is passed directly to `markdown.Render(release.Body, ...)` [2](#0-1) , and each asset name is passed directly to `table.AddField(a.Name)` [3](#0-2) . Neither value is wrapped in `iostreams.NewUntrusted`, which the codebase defines exactly for this purpose: `NewUntrusted` labels external content so that any `fmt` print path calls `Untrusted.String()`, which runs the content through `asciisanitizer.Sanitizer` (falling back to `stripControl`) to neutralize ANSI escape sequences and other control bytes before they reach a terminal writer [4](#0-3) . Other commands in the same codebase (e.g. `pkg/cmd/gist/view/view.go`, `internal/skills/discovery/discovery.go`) already use this `NewUntrusted` pattern for remote content, confirming this is the codebase's established output-safety mechanism, but `pkg/cmd/release/view/view.go` does not apply it to `release.Body` or `Assets[].Name`. `markdown.Render` (`pkg/markdown/markdown.go`) is a thin wrapper around `github.com/cli/go-gh/v2/pkg/markdown.Render` (glamour), which is a Markdown renderer, not an ANSI sanitizer — arbitrary bytes inside raw text/code spans are not guaranteed to be stripped. `tableprinter.AddField` likewise does not perform ANSI stripping on the field text.

### Impact Explanation
This allows terminal escape sequence injection into the victim's terminal (impact class: output/terminal escape sequence injection, potentially enabling cursor manipulation, title-bar spoofing, hidden text, or in vulnerable terminal emulators more severe effects such as clipboard writes) whenever a victim runs `gh release view` against an attacker-controlled repository's release. The attack surface is the release body (Markdown) and each asset's file name, both of which are set entirely by whoever publishes the release.

### Likelihood Explanation
Preconditions are minimal: any unprivileged GitHub user can create a public repository and publish a release with a crafted body or asset name containing ESC (0x1B) sequences, then have the victim run `gh release view` (or be lured to do so, e.g. via a README instruction) against that repo with output going to a TTY. No authentication, elevated privileges, or MITM is required, making this readily repeatable.

### Recommendation
Wrap `release.Body` and each `Assets[].Name` in `iostreams.NewUntrusted` before passing them to `markdown.Render` and `table.AddField` in `renderReleaseTTY` (and consider `renderReleasePlain` too), consistent with the pattern already used in `pkg/cmd/gist/view/view.go`. If `markdown.Render` requires a plain `string`, sanitize via `iostreams.NewUntrusted(release.Body).String()` before calling render, and similarly use `iostreams.NewUntrusted(a.Name).String()` for asset names before calling `AddField`.

### Proof of Concept
Add an httpmock-based test in `pkg/cmd/release/view/view_test.go` modeled on `Test_viewRun`:
1. Stub the release-fetch GraphQL/REST response with `body` containing `"Hello \x1b[31mRED\x1b[0m World"` and one asset with `name` set to `"evil\x1b]0;pwned\x07.zip"`.
2. Run `viewRun` with `opts.IO` set to a TTY-simulated `iostreams.Test()` (forcing `IsStdoutTTY()` to `true`).
3. Capture `stdout.Bytes()` and assert it contains no `0x1B` (ESC) or other C0 control bytes outside `\t`, `\n`, `\r` — e.g. `assert.NotContains(t, stdout.String(), "\x1b")`.
4. Currently this assertion fails because the raw escape bytes from `release.Body`/`a.Name` pass through unmodified; after wrapping the fields in `iostreams.NewUntrusted`, the sanitized output should pass the assertion.

// Untrusted wraps string content the application did not author: HTTP response
// bodies, file contents fetched from a remote, anything that originates outside
// the CLI. The raw bytes are unexported so the only ways out are the methods
// below.
//
// Untrusted satisfies fmt.Stringer, and String sanitizes, so any fmt print path
// (Fprint, Fprintf with %s or %v, Sprint) renders the content with ANSI escape
// sequences neutralized. The only way to reach the raw bytes is Raw, which is
// deliberately easy to grep for and is intended for non-terminal uses such as
// hashing, writing to a file, or piping to another program.
type Untrusted struct {
	raw string
}

// NewUntrusted labels a string as untrusted external content.
func NewUntrusted(s string) Untrusted {
	return Untrusted{raw: s}
}

// NewUntrustedBytes labels a byte slice as untrusted external content.
func NewUntrustedBytes(b []byte) Untrusted {
	return Untrusted{raw: string(b)}
}

// String returns the content with ANSI escape sequences neutralized. It is
// called automatically by the fmt package, so printing an Untrusted value is
// safe by default on every fmt path.
func (u Untrusted) String() string {
	sanitized, _, err := transform.String(&asciisanitizer.Sanitizer{}, u.raw)
	if err != nil {
		return stripControl(u.raw)
	}
	return sanitized
}
