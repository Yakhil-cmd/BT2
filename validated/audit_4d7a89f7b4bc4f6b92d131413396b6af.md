Path traversal (CVE-2023-44395) is a web-application bug class where user-supplied file names/paths are used unsanitized in filesystem operations, exposed via HTTP parameters. I searched for any analogous pattern in Polkadot SDK where an attacker-controlled input from a signed extrinsic, XCM message, or contract call is used to construct a filesystem path. The only path-construction code found operates on either:
- Node-operator-controlled CLI arguments (e.g. `--file`, `--password-filename`) which are not attacker-reachable inputs [1](#0-0) [2](#0-1) 
- Content-addressed hashes (hex-encoded hash of the data, computed server-side via `blake2_256`) rather than attacker-supplied strings, so there is no traversal surface [3](#0-2) [4](#0-3) 

No consensus-critical entry point (signed extrinsic, XCM executor/transactor, contracts/revive call, or public proof submission) constructs a filesystem path from user-supplied data in this codebase, so there is no reachable analog to the Autolab path-traversal bug class here.

	/// Path to a file within a shard subdirectory rooted at `data_dir`.
	fn entry_path(data_dir: &Path, hash: &HopHash, subdir: &str, ext: &str) -> PathBuf {
		let hex = hex::encode(hash);
		data_dir.join(subdir).join(&hex[..2]).join(format!("{}.{}", hex, ext))
	}

	/// Path to the blob file for a given hash.
