**Rationale:**

The premise misreads the code's own documentation and ignores a separate, later-added runtime safeguard. The comment in `ty_depth_checker.rs` explicitly acknowledges this exact limitation but the codebase already mitigates it with a *value-level* depth check that is independent of the type-level formula.

1. `calculate_type_depth_formula` does return `DepthFormula::constant(1)` for `Type::Function` and documents that captured arguments aren't visible in the type, so type-level bounds don't bound value depth for closures. [1](#0-0) 

2. However, this is a known and intentionally-accepted gap because a **runtime value-depth check** was added specifically to close it. When a closure is packed (`PackClosure`/`PackClosureGeneric`), the interpreter calls `check_depth_of_closure_captured_values`, which walks the actual captured values (not just their types) and rejects packing if `max_value_nest_depth` would be exceeded. [2](#0-1) [3](#0-2) 

3. Production config explicitly documents that this exact tradeoff (shallow type, deep value via captures) was the reason value-level checks were introduced, and is gated on `enable_closure_depth_check`/`enable_depth_checks`, tied to the function-values feature flag. [4](#0-3) 

4. `Value::visit_impl`/`Closure::visit_impl` recursively walk captured arguments with increasing depth, and `DepthCheckingVisitor` enforces the bound on every nested value, including nested closures. [5](#0-4) [6](#0-5) 

5. There is a dedicated regression test that constructs exactly the scenario described (a closure recursively capturing itself in a loop, building a deep chain) and confirms the VM rejects it once depth exceeds the maximum (`VM_MAX_VALUE_DEPTH_REACHED`), while accepting it one level below the max — i.e., the "off by one" boundary is explicitly tested. [7](#0-6) 

Additionally, this code path has nothing to do with transaction admission, authenticators, sender/signer binding, sequence numbers, gas/sponsor validation, or replay protection as required by the boundary conditions — it is an internal Move VM interpreter safety check against stack overflow from deeply nested closures, unrelated to authentication data structures. The scenario conflates Move "function values" (closures) with transaction "authenticators" (signature/public-key structures), which are unrelated concepts in this codebase. Given the existing dynamic value-depth enforcement and the explicit regression test proving the bound is respected, the described exploit path does not hold.

    /// Check that the depth of captured closure values does not exceed the configured maximum.
    ///
    /// Closures can capture other closures, creating arbitrary nesting depth that is not visible
    /// in the type system (all closures have the same function type regardless of what they capture).
    /// This check ensures that deeply nested closure chains cannot be created, preventing potential
    /// stack overflows or excessive resource consumption when operating on such values.
    ///
    /// The check uses `max_depth - 1` because the closure being packed adds one additional level
    /// of nesting on top of its captured values.
    fn check_depth_of_closure_captured_values(&self, captured: &[Value]) -> PartialVMResult<()> {
        if !self.vm_config.enable_closure_depth_check {
            return Ok(());
        }
        if let Some(max_depth) = self.vm_config.max_value_nest_depth {
            let limit = max_depth.saturating_sub(1);
            for v in captured.iter() {
                v.check_depth_of_value(limit)?;
            }
        }
        Ok(())
    }
