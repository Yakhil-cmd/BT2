Based on my research, I found a legitimate Polkadot SDK analog to the reported bug class (a fixed/hardcoded gas budget applied to a value-carrying external call that can fail for contracts with non-trivial receive logic).

### Title
Hardcoded `WeightLimit` for ERC20 `transfer()` calls in `ERC20Transactor` can cause asset deposit/withdraw failures for tokens with non-trivial transfer logic - (File: `cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs`)

### Summary
`ERC20Transactor::withdraw_asset_with_surplus` and `ERC20Transactor::deposit_asset_with_surplus` execute an ERC20 `transfer()` call via `pallet_revive::Pallet::<T>::bare_call` bounded by a chain-configured, fixed `WeightLimit::get()` value [1](#0-0) [2](#0-1) . This mirrors the reported bug class: an externally-triggered value transfer bounded by a fixed, non-adjustable gas/weight budget that may not suffice for contracts whose transfer logic is more expensive than the "happy path" the limit was sized for (e.g. fee-on-transfer, blacklist checks, rebasing, hooks).

### Finding Description
When an XCM message (e.g. a reserve transfer or local transact/deposit initiated through `pallet_xcm`'s public extrinsics) causes the executor to withdraw or deposit an ERC20-backed fungible asset that this transactor handles, the transactor issues a `bare_call` to the ERC20 contract's `transfer` function, capped by `TransactionLimits::WeightAndDeposit { weight_limit: WeightLimit::get(), .. }` [3](#0-2) . `WeightLimit` is a fixed constant configured in the runtime (parameterized as a generic `Get<Weight>`), not derived from the actual complexity of the target ERC20 contract's `transfer` implementation. If the contract execution consumes more weight than this fixed limit (analogous to a `.transfer()` receiver whose logic exceeds the 2300-gas stipend on zkSync), `bare_call`'s `result` will be an `Err` (out-of-gas/weight exhausted), and the code path explicitly acknowledges this exact class of failure in its own comment: "This error could've been duplicate smart contract, out of gas, etc. If the issue is gas, there's nothing the user can change in the XCM that will make this work since there's a hardcoded gas limit." [4](#0-3) [5](#0-4) .

In `TransactAsset`'s design, `deposit_asset_with_surplus`/`withdraw_asset_with_surplus` are invoked by the XCM executor while processing instructions such as `WithdrawAsset`/`DepositAsset` [6](#0-5) . A failure returns `XcmError::FailedToTransactAsset`, and per the trait's tuple-composition semantics only one transactor short-circuits with `Ok`; if this is the sole/authoritative transactor for the ERC20 asset, the deposit leg failing after a prior successful withdraw leaves the asset stranded in the XCM holding register for that message, subject to the executor's asset-trap handling rather than being delivered to the intended beneficiary.

### Impact Explanation
This is functionally the same failure mode as the reported issue: a fixed external-call gas/weight budget that is sufficient for "normal" receivers but can be exhausted by contracts with non-trivial transfer logic, causing the value-transfer to revert/error deterministically for those tokens. Unlike a plain EOA `.transfer()`, this failure occurs inside XCM asset accounting, so a legitimate ERC20 (registered by governance/asset managers as an XCM-transactable asset) whose `transfer` function is more gas-expensive than `WeightLimit` becomes effectively unusable for any deposit path through this transactor - every reserve-transfer or local-transact deposit of that asset would fail, and any assets already withdrawn into holding in the same XCM program become trapped, requiring a separate `ClaimAsset` recovery rather than direct delivery.

### Likelihood Explanation
Likelihood depends entirely on the runtime's configured `WeightLimit` value versus the actual weight cost of the registered ERC20 contract(s)' `transfer` implementation, and on whether governance registers ERC20 assets whose `transfer` function is more complex than a simple balance-mapping update. I could not confirm the concrete `WeightLimit` value configured in `asset-hub-westend/src/xcm_config.rs` in this pass (only found textual matches, did not resolve the constant), nor could I trace the exact `drop_assets`/trap behavior in the executor to state definitively that funds are "irretrievable" versus "reclaimable via `ClaimAsset`". This uncertainty should be resolved before treating this as more than a Medium-severity, config-dependent finding — it is not a universal, unconditionally-triggerable loss like a bug in core weight/fee arithmetic.

### Recommendation
- Avoid a single hardcoded `WeightLimit` for all ERC20 contracts; either allow per-asset weight limits (e.g., stored alongside the asset registration/metadata) sized to that specific contract's `transfer` cost, or dry-run/benchmark the call with a generous limit and only charge/refund the weight actually consumed.
- Ensure that when `deposit_asset_with_surplus`/`withdraw_asset_with_surplus` fail, the caller path guarantees assets are safely trapped and recoverable, and document/alert when a registered ERC20 asset's `transfer` weight exceeds the configured `WeightLimit` (e.g., via a registration-time weight probe that rejects assets that cannot fit the budget).

### Proof of Concept
Not executed. This finding is derived purely from static code reading (`erc20_transactor.rs`, `transact_asset.rs`); I did not build a minimal Rust/FRAME integration test invoking `pallet_xcm`'s public entry points against a deliberately gas-heavy ERC20 fixture to reproduce the failure end-to-end, and I could not verify the exact `WeightLimit` constant or asset-trap/claim mechanics in this session due to tool-call limits. A concrete reproduction would require: (1) deploying an ERC20 contract via `pallet-revive` whose `transfer` function performs enough state writes to exceed the runtime's configured `WeightLimit`, (2) registering it with `ERC20Transactor`/`MatchesFungibles`, and (3) issuing a `pallet_xcm::transfer_assets`/local `Transact`+`DepositAsset` XCM program moving that asset, then asserting the deposit leg returns `FailedToTransactAsset` and observing whether the withdrawn amount is trapped and claimable.

		_context: Option<&XcmContext>,

		Err((what, XcmError::Unimplemented))

	/// Identical to `deposit_asset` but returning the surplus, if any.
	///
	/// Return the difference between the worst-case weight and the actual weight consumed.
	/// This can be zero most of the time unless there's some metering involved.
	fn deposit_asset_with_surplus(
		what: AssetsInHolding,
		who: &Location,
		context: Option<&XcmContext>,
	) -> Result<Weight, (AssetsInHolding, XcmError)> {
		Self::deposit_asset(what, who, context).map(|()| Weight::zero())
	}

	/// The surplus is the difference between the worst-case weight and the actual weight consumed.
