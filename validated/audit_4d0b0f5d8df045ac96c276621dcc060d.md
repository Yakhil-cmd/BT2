### Title
Webhook signature is selected by attacker-chosen `repository.owner.login`, but `StatusHandler` writes statuses to any commit matching `sha` with no repository/org scoping - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks the `GitHubApp` (and therefore the secret) used to authenticate the webhook based solely on `params.dig('repository','owner','login')`, not on the actual repository the payload will mutate. `StatusHandler#process` then does `Commit.where(sha: params.sha).each { |c| c.create_status_from_github!(params) }`, with zero repository/org scoping, so any commit sha in the entire database can be targeted regardless of which org's secret validated the signature. This lets an attacker who controls (or picks) a no-secret/unknown-config org for `repository.owner.login`, while crafting `sha`/`state`/`context` for a *different* target commit, forge cross-tenant status updates that can set or clear `blocked?` on a victim stack with `blocking_statuses` configured.

### Finding Description
The broken binding is: `repository_owner` used in `verify_signature` (i.e., `Shipit.github(organization: repository_owner)`'s webhook_secret) MUST equal the org/repo that legitimately owns the commit/stack that `StatusHandler` mutates. This is not enforced anywhere in the path.

Trace:
1. `Shipit::WebhooksController#verify_signature` computes `repository_owner` from `params.dig('repository','owner','login')` and looks up `Shipit.github(organization: repository_owner)` [1](#0-0) [2](#0-1) .
2. `GitHubApp#verify_webhook_signature` returns `true` unconditionally `unless webhook_secret` is configured for that org [3](#0-2) . If the attacker names an org present in `Shipit.github_organizations` (or the single-org legacy config) that has no `webhook_secret` set, or otherwise satisfies the signature check for an org they don't need to compromise, the whole request is accepted as "verified" independent of which repository/stack is actually targeted.
3. `Shipit::Webhooks.for_event('status')` dispatches to `StatusHandler#process`, which resolves affected records purely by `Commit.where(sha: params.sha)` — no `repository.full_name`, `stack_id`, or org check is performed at all [4](#0-3) .
4. `Commit#create_status_from_github!` records the forged status and recomputes `status` [5](#0-4) .
5. `Commit#blocked?` scans `stack.commits.reachable.newer_than(stack.last_deployed_commit).older_than(self).any?(&:blocking?)` against `stack.blocking_statuses`, and `deployable?` depends on `!blocked?` [6](#0-5) . A forged status on any commit sha in the victim stack's undeployed range can flip `blocked?`, gating or unblocking deploys for that stack.

Exploit flow: attacker sends `POST /webhooks` with header `X-Github-Event: status` and a JSON body where `repository.owner.login` names a configured-but-secretless (or otherwise easily satisfied) org, while `sha` is the victim's real commit sha (obtainable via the victim's public GitHub repo, Shipit's own public commit-status UI, or CI logs) and `state`/`context` chosen to match/violate the victim's `blocking_statuses`. There is no re-validation that the sha or `repository.full_name` in the payload actually belongs to the org whose secret was used, and `StatusHandler` never checks `repository.full_name` in the first place — it is completely unused in this handler.

This defeats the "existing guards" enumerated in the audit brief: `verify_signature` only authenticates *an* org's secret exists and matches, not that the org matches the target repository/stack; `drop_unhandled_event` and the `ExplicitParameters` schema only validate shape of `status`/`sha`/`state`, not repository identity; there is no `stacks` scope, `User#authorized?`, or model validation anywhere in this unauthenticated webhook path that ties `sha` to a repository.

### Impact Explanation
A successful forged `status` webhook writes a `Status` record for a commit belonging to a stack/repository the attacker does not control and did not authenticate against. Because `Commit#blocked?`/`#deployable?` depend on these statuses when `blocking_statuses` is configured, the attacker can force a victim's commit range to become blocked (denying legitimate deploys) or become unblocked (potentially allowing an otherwise-blocked, unsafe commit to be deployed/merged/continuous-delivered via `schedule_continuous_delivery`). This is a payload for one repository (the attacker's chosen no-secret org) mutating another repository/stack's state — matching the Critical category "a payload for one repository mutating another's stack, commit, task or team." The attack is repeatable against any commit sha the attacker can learn, across arbitrarily many victim stacks, as long as some org in the Shipit-wide GitHub config has no `webhook_secret` (or a guessable/known-weak one).

### Likelihood Explanation
Preconditions: (a) the Shipit instance must be configured with multiple GitHub orgs (multi-org github config) where at least one org lacks a `webhook_secret` (or the attacker can otherwise satisfy `verify_webhook_signature` for some org — note `webhook_secret` blank causes automatic `true`); (b) attacker needs to know/guess a target commit `sha` for a stack with `blocking_statuses` configured — commit shas are frequently public (public repos, PR pages, CI badges). Attacker cost is a single unauthenticated HTTP POST, fully repeatable, with no privileged access needed. Likelihood is contingent on the specific multi-org secret-configuration gap described, which is plausible in real deployments (e.g., an org onboarded without a webhook secret set) but not universal — it requires that specific configuration weakness to exist.

### Recommendation
Bind webhook authentication to the actual target repository, not just to an org name chosen by the attacker:
1. In `StatusHandler` (and other handlers), scope `Commit.where(sha: params.sha)` by the stack/repository derived from `params.repository.full_name`, and reject/ignore the event if that repository does not match the org/repo that authenticated the signature.
2. In `WebhooksController#verify_signature`, after selecting `github_app` by `repository_owner`, also verify that `params.dig('repository','full_name')`'s owner matches `repository_owner` exactly (case-insensitively) before proceeding, and reject (422) if they diverge.
3. Do not treat `webhook_secret.blank?` as an automatic pass; require an explicit "no verification intended" flag or fail closed instead, especially in multi-org configurations.

### Proof of Concept
Minitest plan (`test/controllers/webhooks_controller_test.rb`-style, no live GitHub):
```ruby
test "status event with owner/full_name split writes status to unrelated victim stack" do
  # Victim setup: real org "victim-org" with webhook_secret configured, stack has blocking_statuses: ['ci/build']
  victim_stack = shipit_stacks(:shipit) # or create stack with blocking_statuses: ['ci/build']
  victim_stack.update!(blocking_statuses: ['ci/build'])
  victim_commit = victim_stack.commits.create!(sha: 'deadbeef' * 5, message: 'victim commit')

  # Attacker-controlled org "attacker-org" has NO webhook_secret configured in Shipit.github config
  payload = {
    repository: { owner: { login: 'attacker-org' }, full_name: 'attacker-org/some-other-repo' },
    sha: victim_commit.sha,
    state: 'error',
    context: 'ci/build'
  }.to_json

  # BEFORE: victim_commit is not blocked
  assert_not victim_commit.reload.blocked?

  post shipit.webhooks_path, params: payload, headers: {
    'X-Github-Event' => 'status',
    'X-Hub-Signature' => 'sha1=irrelevant', # accepted because attacker-org has no webhook_secret
    'CONTENT_TYPE' => 'application/json'
  }
  assert_response :ok

  # AFTER: assert cross-tenant equality violated -
  # binding claimed: authenticated_org(repository_owner) == owning_org(victim_commit.stack)
  # attacker-org != victim-org, yet victim_commit was mutated
  victim_commit.reload
  assert_equal 'error', victim_commit.status.state
  assert victim_commit.blocked?, "victim commit should now be blocked by forged unrelated-org status"
end
```
This demonstrates the equality `repository_owner (attacker-org) == stack.repository.owner (victim-org)` is false, yet the write to `victim_commit`'s statuses succeeds, confirming the cross-tenant state manipulation.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
