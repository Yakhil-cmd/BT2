### Title
Fork-controlled `RUBYOPT` via `shipit.yml` `machine.environment` enables RCE in `ruby`/`bundle` dependency steps - ([File: lib/shipit/task_commands.rb])

### Summary
On a repository configured with `provisioning_behavior=allow_all`, opening a pull request causes Shipit to auto-create a `ReviewStack` whose `branch` is the fork's PR head ref. `TaskCommands#install_dependencies` executes `dependencies_steps!` (e.g. `bundle install`) using an environment built by `TaskCommands#env`, which merges `deploy_spec.machine_env` — parsed directly from that fork branch's `shipit.yml` `machine.environment` key — into the child process environment passed to `PTY.spawn`. An attacker-controlled `RUBYOPT` value (e.g. `-r/path/to/evil`) is honored by the Ruby interpreter/`bundle` at startup, yielding code execution on the Shipit deploy host.

### Finding Description
The broken invariant: `deploy_spec.machine_env` (attacker-controlled) ∩ {reserved loader/interpreter env vars} should be `∅` before reaching `PTY.spawn`, but in fact `deploy_spec.machine_env == fork_branch_shipit_yml['machine']['environment']` unfiltered, and this hash is merged verbatim into the process env.

Path:
1. `DeploySpec#machine_env` returns `config('machine', 'environment') || {}` with no allow/deny-listing of variable names [1](#0-0) .
2. `TaskCommands#env` merges this directly into the command environment, after task/stack metadata, so it can override or introduce arbitrary keys such as `RUBYOPT`: `super.merge(@stack.env).merge({...}).merge(deploy_spec.machine_env).merge(@task.env)` [2](#0-1) .
3. `TaskCommands#install_dependencies` builds each dependency-step `Command` with this exact `env:` [3](#0-2) .
4. `Command#start` calls `PTY.spawn(unbundled_env, *interpolated_arguments, chdir: @chdir)`, where `unbundled_env` merges `@env.stringify_keys` (the attacker-controlled hash) on top of the base sanitized env [4](#0-3) .
5. `deploy_spec` is `DeploySpec::FileSystem.new(@task.working_directory, @stack)`, reading `shipit.yml` from the checked-out working directory of the stack's branch [5](#0-4) .
6. For a `ReviewStack`, that branch is set directly from the incoming pull request's head ref, which is the fork branch under attacker control: `stack_attributes` sets `branch: params.pull_request.head.ref` when creating the stack via `ReviewStackAdapter#create!` [6](#0-5) .
7. Under `provisioning_behavior_allow_all?`, `OpenedHandler#provision?` auto-triggers this creation for any opened PR with no maintainer approval or label required [7](#0-6) .
8. Once provisioned, `PerformTaskJob`/`TaskExecutionStrategy::Default#perform_task` runs `@commands.install_dependencies`, which for a bundler-detected repo runs `bundle install` (or equivalent ruby-toolchain command), inheriting the poisoned `RUBYOPT` [8](#0-7) .

This is explicitly documented as intended behavior in the README ("`machine.environment` contains the extra environment variables that you want to provide during task execution"), and no existing guard (webhook signature verification, `ExplicitParameters` schema, `EnvironmentVariables#permit`, or model validations) filters or denies dangerous variable names like `RUBYOPT`, `RUBYLIB`, `BUNDLE_GEMFILE`, `GEM_PATH`, etc. `EnvironmentVariables#permit` is applied to deploy/rollback UI-submitted variables, not to `machine.environment` values sourced from `shipit.yml`.

### Impact Explanation
Any unprivileged GitHub user who can open a pull request against a repository with `review_stacks_enabled=true` and `provisioning_behavior=allow_all` can achieve arbitrary code execution on the Shipit deploy host, in the context of the Shipit process/user — the same host that holds `GITHUB_TOKEN`, deploy secrets, and can execute deploys for the affected repository (and potentially others sharing the host). This matches the Critical/RCE-on-deploy-host category. It is trivially repeatable: each new PR (or each dependency-install run) re-executes the injected command.

### Likelihood Explanation
Preconditions: the target repository must have review stacks enabled with `provisioning_behavior=allow_all` (the documented default per the migration `provisioning_behavior` default `:allow_all`) [9](#0-8) , and the repository must use a `ruby`/`bundle` dependency step (auto-detected by `BundlerDiscovery` when a `Gemfile` is present). No secrets, sessions, or GitHub App credentials are needed — the attacker only needs to open a PR from a fork containing a `shipit.yml` with a `machine.environment.RUBYOPT` entry. Cost is minimal and fully repeatable.

### Recommendation
Do not allow `machine.environment` (or any fork-controlled `shipit.yml` value) to set interpreter/loader-influencing variables such as `RUBYOPT`, `RUBYLIB`, `RUBYOPT`, `BUNDLE_GEMFILE`, `GEM_PATH`, `PYTHONSTARTUP`, `NODE_OPTIONS`, `LD_PRELOAD`, `PATH`, etc. Apply an explicit allow-list (or deny-list of known dangerous variable names) in `DeploySpec#machine_env`/`TaskCommands#env` before merging into the process environment, and/or run dependency-installation steps for review stacks (which are driven by untrusted fork content) in a sandboxed/isolated execution context distinct from trusted deploy/rollback steps.

### Proof of Concept
```ruby
# test/lib/shipit/task_commands_test.rb (add)
test "#install_dependencies does not leak attacker-controlled RUBYOPT from shipit.yml machine.environment" do
  stack = shipit_stacks(:review_stack) # branch == fork PR head ref
  task  = shipit_tasks(:shipit_restart)
  task.stack = stack

  commands = Shipit::TaskCommands.new(task)
  commands.deploy_spec.stubs(:machine_env).returns('RUBYOPT' => '-r/tmp/evil')
  commands.deploy_spec.stubs(:dependencies_steps!).returns(['bundle install'])

  cmd = commands.install_dependencies.first

  # Binding under test: fork-controlled machine.environment key must NOT reach
  # the ruby/bundle dependency-step process env.
  assert_nil cmd.env['RUBYOPT'], "RUBYOPT from fork's shipit.yml reached install_dependencies env: #{cmd.env.inspect}"
end
```
Given current code, `cmd.env['RUBYOPT']` equals `'-r/tmp/evil'` (test fails), demonstrating the vulnerability: the fork-controlled `machine.environment` value from `shipit.yml` flows unfiltered into the `Command` environment used for `PTY.spawn` in a `ruby`/`bundle` dependency step.
