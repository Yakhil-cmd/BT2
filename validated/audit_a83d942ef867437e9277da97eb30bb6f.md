### Title
Webhook organization used for signature verification is not bound to the repository the event handlers act on - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to verify the HMAC signature against using an attacker-controlled field taken straight from the *unauthenticated* request body (`repository.owner.login` or `organization.login`), before the signature has been checked. Once verification passes, every webhook `Handler` (e.g. `PushHandler`, `StatusHandler`) determines the actual repository/stack to act on using a *different* field of the same payload: `repository.full_name`. Because these two fields are never checked for consistency, a payload can be signed against Organization A's secret while acting on Organization B's repository.

### Finding Description
`app/controllers/shipit/webhooks_controller.rb` computes: [1](#0-0) [2](#0-1) 

`repository_owner` is read directly from the JSON body (`params.dig('repository','owner','login')` or `params.dig('organization','login')`) and used to pick which configured GitHub App (`Shipit.github(organization: repository_owner)`) — and therefore which `webhook_secret` — to verify the `X-Hub-Signature` HMAC against, as implemented in `lib/shipit/github_app.rb`: [3](#0-2) 

After signature verification succeeds, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` dispatches the *entire raw payload* to handlers such as `PushHandler` and `StatusHandler`. These handlers resolve the target `Repository`/`Stack` using a completely different field of the same payload — `repository.full_name` — via the shared base class: [4](#0-3) [5](#0-4) [6](#0-5) 

Shipit explicitly supports hosting multiple GitHub Apps/organizations from a single instance, each with its own `webhook_secret` and configuration, as documented in the multi-org secrets format: [7](#0-6) 

The equality the code implicitly assumes but never enforces is:
`organization used to select the verifying webhook_secret (repository.owner.login / organization.login)` == `organization implied by repository.full_name that handlers act on`.

Before the fix that would be required, these two values are read from independent, attacker-supplied JSON paths in the same unsigned-at-read-time body, so nothing prevents `repository.owner.login = "OrgA"` (whose secret the attacker knows/controls, e.g. because they own a GitHub App installed on OrgA, or OrgA is any org the attacker can trigger events from) while `repository.full_name = "OrgB/victim-repo"` — a repository belonging to a different organization also configured on the same Shipit instance. The HMAC is computed over the raw body using OrgA's secret and will verify correctly, since `verify_webhook_signature` only checks the signature against the raw bytes, not that the embedded organization/repository fields agree with each other.

### Impact Explanation
This crosses an authentication boundary: an attacker with the ability to legitimately generate a validly-signed webhook for **any** organization configured on the shared Shipit instance can make that signed envelope act on a repository belonging to a **different** organization. Concretely:
- Via `PushHandler`, an attacker can force `stack.sync_github(expected_head_sha: ...)` to run against another organization's stack/branch, causing Shipit to resync/re-evaluate history it should not be triggered on.
- Via `StatusHandler`, an attacker can inject arbitrary CI `status` records (`commit.create_status_from_github!`) against commits belonging to another organization's repository. Because commit statuses are used by Shipit to gate whether a commit is considered CI-passed/deployable in the merge queue and deploy flow, forging a "success" status for a victim commit can push a commit through Shipit's safety checks as if CI had passed, contributing to an unauthorized deploy on a repository the attacker has no access to.

This matches the required "Critical: cross-repository writes / unauthorized deploy" impact bar, because the write (sync trigger, forged CI status) lands on a repository outside the organization whose credentials were actually used to authenticate the request.

### Likelihood Explanation
Exploitability depends entirely on the deployment being multi-org (one Shipit instance serving several GitHub organizations/Apps, each with its own `webhook_secret`), which the engine explicitly documents and supports (`config/secrets.development.shopify.yml`, `test/dummy/config/secrets_double_github_app.yml`). In that configuration, any actor able to produce a validly-signed webhook for *any one* of the configured organizations (e.g., an org they themselves administer, or where they can trigger arbitrary repository/push/status events) can target any *other* org sharing the same Shipit instance, without needing that other org's secret, a Shipit session, or an `ApiClient` token. In a single-org deployment this analog collapses (there is only one secret/org, so the mismatch is moot), so likelihood is conditional on the documented multi-org use case, which Shipit is designed to support.

### Recommendation
In `WebhooksController#verify_signature` (or in the base `Shipit::Webhooks::Handlers::Handler`), after selecting the GitHub App by `repository_owner`, verify that `repository.full_name`'s owner segment matches `repository_owner` (or `organization.login`) before dispatching to handlers. Reject the webhook (422) if the two disagree, so a signature verified against Org A's secret can never be used to act on Org B's repository.

### Proof of Concept
1. Configure Shipit with two organizations, e.g. `OrgA` and `OrgB`, each with its own `github.webhook_secret` (as supported by `config/secrets.development.shopify.yml`).
2. As an actor who knows/controls `OrgA`'s `webhook_secret` (e.g., an admin of `OrgA`'s GitHub App who is unrelated to `OrgB`), craft a `push` event payload:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "OrgA" },
    "full_name": "OrgB/victim-repo"
  }
}
```
3. Compute `X-Hub-Signature: sha1=<hmac-sha1(payload, OrgA_webhook_secret)>` and POST to `/webhooks` with `X-Github-Event: push`.
4. `WebhooksController#verify_signature` resolves `repository_owner` = `"OrgA"`, fetches `Shipit.github(organization: "OrgA")`, and successfully verifies the signature using `OrgA`'s secret.
5. `PushHandler#process` (via `Handler#stacks` / `Handler#repository_name`) resolves the target using `repository.full_name` = `"OrgB/victim-repo"`, and calls `stack.sync_github(expected_head_sha: ...)` on `OrgB`'s stack — a write performed against `OrgB`'s repository authorized solely by `OrgA`'s webhook secret.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
