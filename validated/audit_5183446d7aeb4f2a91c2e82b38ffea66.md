### Title
Webhook signature verification uses `repository.owner.login`, but push/pull_request/status handlers act on the independently-supplied `repository.full_name` — allowing a webhook authenticated for one GitHub organization to force sync/deploy activity on a stack belonging to a different organization - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
Shipit's `WebhooksController` verifies the incoming HMAC signature using the GitHub App/secret associated with `repository.owner.login` (or `organization.login`) pulled from the JSON body [1](#0-0) , but every event `Handler` resolves the target `Repository`/`Stack` using a *different* field of the same attacker-controlled body: `repository.full_name` [2](#0-1) . Nothing binds these two fields together, so the field that authorizes the request is not the field that determines what gets written.

### Finding Description
`verify_signature` computes `repository_owner` from the raw JSON body and fetches the GitHub App config (and hence the HMAC `webhook_secret`) for that organization: [3](#0-2) 
It then verifies the signature over the *entire* raw POST body using that org's secret [4](#0-3) .

Once verified, `WebhooksController#create` dispatches the parsed body to the registered handlers for the event [5](#0-4) . Every handler (`PushHandler`, `StatusHandler`, `MembershipHandler`, `CheckSuiteHandler`, all `PullRequest::*Handler`s) resolves the affected repository/stack through the base `Handler#repository_name`/`#stacks` helpers, which read `payload.dig('repository', 'full_name')` — a completely separate key from the one used for signature verification: [2](#0-1) [6](#0-5) 

Since Shipit supports multi-tenant deployments where each GitHub organization has its own `webhook_secret`/App config (`docs/setup.md` "Using Multiple Github Applications") [7](#0-6) , an attacker who legitimately controls one onboarded organization ("org-a", with a real, correctly configured GitHub App/webhook secret for that org) can compute a valid HMAC-SHA1 signature over an arbitrary JSON body of their choosing (they are POSTing directly to Shipit's webhook endpoint, not relaying an actual GitHub-signed payload). They can set:
```
repository.owner.login = "org-a"     // selects org-a's secret for signature check
repository.full_name   = "org-b/some-repo"  // handler's actual write target
```
This passes `verify_signature` (org-a's secret matches) but the `PushHandler`/`StatusHandler`/etc. act on `org-b/some-repo`'s stacks, which org-a has no authorization over.

The equality this breaks: `organization authenticated by verify_signature (repository.owner.login)` **should equal** `organization of the repository the handler writes to (repository.full_name)`. Before a malicious PR/request, an org's webhook can only affect its own repositories because in genuine GitHub-originated payloads these two fields are always consistent. After the attack, this invariant is not enforced anywhere in Ruby code, so the two fields can diverge under attacker control.

### Impact Explanation
For `push` events, a mismatched payload causes `Stack#sync_github` to be invoked for a stack belonging to a different, unauthorized organization [8](#0-7) , enqueuing `GithubSyncJob` for that victim stack [9](#0-8) . This forces an unscheduled synchronization of the victim's stack (using the victim stack's own correctly-configured GitHub API credentials, since `github_api` is resolved from `stack.repository.owner`), and if the victim stack has continuous deployment/continuous delivery enabled, syncing new commits can trigger an unauthorized deploy pipeline run that the victim organization did not request and has no relationship to the attacker's organization. Similar cross-organization effects apply to `StatusHandler` (spoofing CI status for a foreign commit) and `MembershipHandler`/`CheckSuiteHandler`. This matches the "unauthorized deploy" and cross-repository-write impact bar.

### Likelihood Explanation
Requires only (a) the attacker to be a legitimate admin of one org that Shipit has legitimately onboarded (their own, correctly configured, webhook secret) — not a compromise of any other credential, no `ApiClient` token, no GitHub App private key, and no session — and (b) knowledge of the victim organization's repository full name (public information for public repos, or guessable in many deployments). No repository write access to the victim repo, no privileged Shipit account, and no interception is needed; only crafting an arbitrary JSON POST with a self-computed valid HMAC.

### Recommendation
In `WebhooksController#verify_signature` (or in `Shipit::Webhooks::Handlers::Handler`), enforce that the organization used to select the webhook secret matches the owner embedded in `repository.full_name` before dispatching to handlers — e.g., reject the request if `repository_owner != payload.dig('repository', 'full_name')&.split('/')&.first` (case-insensitively). Alternatively, have every handler validate that the resolved `Repository#owner` equals the verified `repository_owner` before acting.

### Proof of Concept
1. Shipit instance configured with two orgs, `org-a` and `org-b`, each with a real, independent `webhook_secret` (per `docs/setup.md` multiple GitHub Apps section).
2. Attacker, who legitimately controls `org-a`'s webhook secret, crafts:
```json
{
  "ref": "refs/heads/master",
  "after": "<any sha org-b already has, or one that will trigger sync>",
  "repository": {
    "owner": { "login": "org-a" },
    "full_name": "org-b/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(org-a-webhook-secret, raw_body)>`.
4. `verify_signature` fetches `Shipit.github(organization: "org-a")` and validates successfully [1](#0-0) .
5. `PushHandler#process` runs `Repository.from_github_repo_name("org-b/victim-repo")` and enqueues `GithubSyncJob` for `org-b`'s stack [8](#0-7) [2](#0-1) , forcing an unauthorized sync/deploy pipeline trigger against `org-b`, despite the attacker having no access whatsoever to `org-b`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
    def perform(params)
      @stack = Stack.find(params[:stack_id])
      expected_head_sha = params[:expected_head_sha]
      retry_count = params[:retry_count] || 0
      head_before_sync = spec_cache_target
      appended_commits = []

      handle_github_errors do
        new_commits, shared_parent = fetch_missing_commits { stack.github_commits }

        # Retry on Github eventual consistency: webhook indicated new commits but we found none
        if expected_head_sha && new_commits.empty? && !commit_exists?(expected_head_sha) &&
           retry_count < MAX_RETRY_ATTEMPTS
          GithubSyncJob.set(wait: RETRY_DELAY * retry_count).perform_later(params.merge(retry_count: retry_count + 1))
          return
        end

        stack.transaction do
          shared_parent&.detach_children!
          appended_commits = new_commits.map do |gh_commit|
            append_commit(gh_commit)
          end
          stack.lock_reverted_commits! if appended_commits.any?(&:revert?)
        end
      end
      sync_changed_nothing = appended_commits.empty? &&
                             spec_cache_target == head_before_sync &&
                             stack.cached_deploy_spec.present?
      return if sync_changed_nothing && !params[:force_spec_cache]

      CacheDeploySpecJob.perform_later(stack)
    end
```
