This confirms the vulnerability. The `CCMenuUrlController#fetch` creates an `ApiClient` with `permissions: %w[read:stack]` but never sets `stack:` or `stack_id:` on it, despite the client being minted in the context of a specific `stack` (used only to build the URL). Since `ApiClient#stack` is `optional: true` and defaults to `nil`, `current_api_client.stack_id?` in `BaseController#stacks` is always false for CCMenu tokens, causing `Stack.all` to be returned instead of a scoped stack.

### Title
CCMenu API token is not scoped to the stack it was minted for, allowing cross-stack reads - (File: app/controllers/shipit/ccmenu_url_controller.rb)

### Summary
`CCMenuUrlController#fetch` mints an `ApiClient` with `read:stack` permission but never sets its `stack_id`, so `Api::BaseController#stacks` falls back to `Stack.all` for that token instead of restricting it to the stack the user requested the CCMenu URL for. Any holder of a leaked CCMenu token can read `Api::CCMenuController#show` for any stack in the installation, not just the one it was generated for.

### Finding Description
The broken binding: the intended equality is `client.stack_id == stack.id` (the ApiClient minted for a CCMenu URL should be bound to that specific stack), but the actual code produces `client.stack_id == nil` for every CCMenu client, regardless of which stack triggered its creation.

Path:
1. `CCMenuUrlController#fetch` (`app/controllers/shipit/ccmenu_url_controller.rb:7-11`) resolves `stack = Stack.from_param!(params[:stack_id])` and builds `client = ApiClient.create_with(permissions: %w[read:stack]).find_or_create_by!(creator: current_user, name: 'CCMenu Client')` (`app/controllers/shipit/ccmenu_url_controller.rb:15-18`). Note `find_or_create_by!` keys only on `creator` and `name` — the `stack` variable is used solely to build the returned URL, never assigned to the client.
2. `ApiClient` has an optional `belongs_to :stack` (`app/models/shipit/api_client.rb:8`), so `stack_id` remains `nil` on every token minted this way.
3. `Api::CCMenuController#authenticate_api_client` (`app/controllers/shipit/api/ccmenu_controller.rb:33-36`) authenticates via `ApiClient.authenticate(params[:token])`.
4. `Api::BaseController#stacks` (`app/controllers/shipit/api/base_controller.rb:74-76`) computes `current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all`. Since `stack_id` is `nil`, the ternary always evaluates to `Stack.all`.
5. `Api::CCMenuController#stack` calls `Stack.from_param!(params[:stack_id])` directly (`app/controllers/shipit/api/ccmenu_controller.rb:29-31`), bypassing the scoped `stacks` helper entirely and resolving against the unrestricted `Stack` relation regardless of `params[:stack_id]`.

Attacker request: after a legitimate user requests a CCMenu URL for `shipit/shipit` (`GET /shipit/shipit/master/ccmenu_url`, handled by `fetch`), the returned token authenticates against **any** stack. The attacker sends `GET /api/stacks/other-owner/other-repo/other-branch/ccmenu?token=<leaked_token>` and `Api::CCMenuController#show` renders that stack's deploy/task state successfully, since `require_permission :read, :stack` only checks the `permissions` array (`read:stack`), not stack ownership, and `stack` resolution never filters by `current_api_client.stack_id`.

Existing guards don't help: `require_permission!` (`app/controllers/shipit/api/base_controller.rb:82-84`) only checks the permission string, not the target stack; there is no `stacks` scope enforcement in `CCMenuController#stack`, and no validation ties `ApiClient#stack_id` to the stack used at minting time.

### Impact Explanation
An attacker holding a leaked/observed CCMenu token (e.g., captured from a CI dashboard, browser history, log, or shared screen) can read deploy/task state — `lastBuildStatus`, `lastBuildLabel`, lock status, activity — for **any** stack in the Shipit installation, not just the one it was issued for. This is an unauthenticated (relative to other tenants) read of deploy state across tenant boundaries, matching the High-severity category "unauthenticated read of stack state, task streams or deploy output." The attack is fully repeatable against arbitrary stacks with the same single token.

### Likelihood Explanation
Preconditions are minimal: any authenticated Shipit user (even one with legitimate access to only one stack) can self-mint a CCMenu token via `CCMenuUrlController#fetch` on a stack they can view, then use that same token against unrelated stacks. No GitHub secrets, admin privileges, or webhook forgery is needed — only possession of a valid CCMenu token, which by design is embedded in plaintext URLs meant for external CI-status tools (CCMenu clients), making leakage likely. This is trivial and fully reproducible.

### Recommendation
Bind the `ApiClient` created in `CCMenuUrlController#fetch` to the specific stack, e.g. `ApiClient.create_with(permissions: %w[read:stack], stack: stack).find_or_create_by!(creator: current_user, stack: stack, name: 'CCMenu Client')`, and make `Api::CCMenuController#stack` resolve through the scoped `stacks` helper (`stacks.from_param!(params[:stack_id])`) instead of `Stack.from_param!` directly, so `stack_id?` enforcement in `BaseController#stacks` actually applies.
