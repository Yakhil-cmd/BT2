### Title
Webhook signature verification is scoped to an attacker-chosen organization while event processing is scoped by unrelated payload fields, allowing unauthenticated forgery of build status / push events for any tracked stack - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects *which* GitHub App/organization's secret is used to validate `X-Hub-Signature` based on an attacker-controlled JSON field (`repository.owner.login`, falling back to `organization.login`), while the handlers that actually act on the payload (`StatusHandler`, `PushHandler`, via `Handler#stacks`/`#repository_name`) key off entirely different fields (`sha` alone, or `repository.full_name`). If any organization configured in a multi-org Shipit deployment has no `webhook_secret` set — a state explicitly documented as optional — signature verification for that organization is a no-op, letting an unauthenticated attacker forge events that are processed against a completely different, "secured" organization's stacks/commits.

### Finding Description
`verify_signature` resolves the GitHub App purely from payload content, before any cryptographic check: [1](#0-0) [2](#0-1) 

`GitHubApp#verify_webhook_signature` unconditionally returns `true` when the resolved organization has no `webhook_secret` configured: [3](#0-2) 

This is a documented, "optional" configuration per `docs/setup.md` ("Webhook secret (optional): Fill it with some randomly generated string...") and the multi-org example in the same file, so it is a supported deployment shape, not a misuse of the engine.

Once `verify_signature` passes (trivially, for the secret-less organization), `WebhooksController#create` dispatches the raw, attacker-controlled JSON straight to the handlers: [4](#0-3) 

The handlers never re-check that the event actually belongs to the organization that was "authenticated":
- `StatusHandler#process` looks up commits **globally by `sha` only**, with no repository/organization scoping at all: [5](#0-4) 
- `PushHandler`/`Handler#stacks` scope by `repository.full_name`, a field independent from `repository.owner.login`/`organization.login` used for signature routing: [6](#0-5) [7](#0-6) 

**Binding broken:** *organization authenticated* (`repository.owner.login` / `organization.login`, checked in `verify_signature`) ≠ *repository/commit written* (`repository.full_name` for push/check_suite, or bare `sha` for status). Before the attacker's request: only organizations with a configured `webhook_secret` can inject events for their stacks. After: an attacker who can name any organization lacking a secret (even an unrelated, low-value one) can forge signature-valid requests that are then processed as if targeting any other stack/commit in the same Shipit instance, because the processing code never re-derives or compares against the organization that satisfied `verify_signature`.

### Impact Explanation
This breaks the deployment-trust boundary between "which org's secret validated this request" and "which repository's state gets mutated":
- Forged `status` events (`StatusHandler`) can mark an arbitrary, attacker-chosen commit `sha` (public information from any repository's commit history) as `state: "success"`, which can satisfy Shipit's required-status deploy gating and enable an **unauthorized deploy** of a stack the attacker has no access to.
- Forged `push` events (`PushHandler`) can trigger `stack.sync_github` for any tracked repository/branch by setting `repository.full_name` to the victim repo while the signature is checked against an unrelated, secret-less organization.

This maps to the in-scope Critical impact category "an unauthorized deploy, rollback or merge."

### Likelihood Explanation
No credentials, tokens, or GitHub access are required — only knowledge that the Shipit instance is deployed with the documented multi-organization configuration and that at least one configured organization omits `webhook_secret` (an explicitly supported, "optional" setting per `docs/setup.md`). The attacker also needs a target commit SHA, which is public. This is a plain unauthenticated POST to `/webhooks`.

### Recommendation
- Require `webhook_secret` to be present for every configured organization (fail closed) rather than treating it as optional, or
- After signature verification, re-derive the acting organization from the same field that satisfied verification and reject/ignore any handler processing whose target repository's owner does not match, and
- In `StatusHandler`, scope the `Commit` lookup to the repository identified in the payload (and cross-check it against the verified organization) instead of matching by `sha` alone.

### Proof of Concept
1. Deploy Shipit with multiple organizations per `docs/setup.md`'s "Using Multiple Github Applications" section; leave `webhook_secret` blank for organization `low-value-org` (a supported configuration) while `victim-org` has a real secret and a tracked stack/commit.
2. Send `POST /webhooks` with header `X-Github-Event: status`, no valid `X-Hub-Signature` for `victim-org`, and body:
```json
{
  "organization": {"login": "low-value-org"},
  "repository": {"owner": {"login": "low-value-org"}, "full_name": "victim-org/victim-repo"},
  "sha": "<known commit sha in victim-org/victim-repo>",
  "state": "success"
}
```
3. `verify_signature` resolves `Shipit.github(organization: "low-value-org")`, whose `verify_webhook_signature` returns `true` unconditionally (`lib/shipit/github_app.rb:77`) because no secret is configured.
4. `StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`) matches the commit by `sha` alone and records a forged successful status for `victim-org`'s commit, with no verification tied to `victim-org`'s actual secret.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
