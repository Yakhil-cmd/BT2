### Title
Webhook signature verified against attacker's own org while payload's `repository.full_name` targets a victim repository, allowing cross-tenant ReviewStack deprovision/archive with forged actor - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/pull_request/closed_handler.rb], [File: app/models/shipit/webhooks/handlers/pull_request/review_stack_adapter.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App/secret used to authenticate the payload based on `params.dig('repository', 'owner', 'login')`, but `ClosedHandler` resolves the *actual* repository/stack to mutate using the independent `params.repository.full_name` field. Because these two fields are never required to match, and because a secret-less org config makes `verify_webhook_signature` trivially return `true`, an attacker can sign a payload "as" their own unconfigured org while naming a victim's repository and PR number, causing the victim's `ReviewStack` to be deprovisioned and archived under an attacker-chosen actor identity.

### Finding Description
The broken binding: `repository_owner` used to select the verifying `GitHubApp` (`params.dig('repository','owner','login')` in [1](#0-0)  ) must equal the owner of the repository actually acted upon (`params.repository.full_name`'s owner segment, resolved in [2](#0-1)  ). Nothing enforces this equality — these are two separate, independently attacker-controlled JSON fields in the same payload.

Flow:
1. `WebhooksController#create` parses raw JSON and dispatches to handlers keyed by `X-Github-Event` header, with `verify_signature` run as a `before_action`: [3](#0-2) .
2. `verify_signature` picks `Shipit.github(organization: repository_owner)` where `repository_owner` comes from `repository.owner.login` in the payload, then calls `github_app.verify_webhook_signature`: [4](#0-3) .
3. `GitHubApp#verify_webhook_signature` returns `true` unconditionally if that org has no `webhook_secret` configured: [5](#0-4) . An attacker who controls (or names) any org present in `Shipit.github` config without a secret can make this pass with zero cryptographic proof.
4. `ClosedHandler#process` never looks at `repository.owner.login` at all. It resolves the repository purely via `Shipit::Repository.from_github_repo_name(params.repository.full_name)`, which splits the string on `/` and does a plain `find_by(owner:, name:)`: [6](#0-5) . This is fully attacker-supplied and independent of the field checked in step 2.
5. `ReviewStackAdapter#archive!` finds the victim's stack by `environment` (`pr#{number}`), calls `stack.remove_from_provisioning_queue`, `stack.deprovision`, and `stack.archive!(user)` where `user = Shipit::User.find_or_create_by_login!(params.sender['login'])` — an arbitrary attacker-chosen string: [7](#0-6)  and [8](#0-7) .

Root cause: signature verification scope (`repository.owner.login`) and mutation scope (`repository.full_name`) are decoupled fields in the same JSON body, with no schema-level or handler-level check tying them together. Existing guards (`drop_unhandled_event`, `ExplicitParameters` schema, `check_if_ping`) don't check this either — the `pull_request` schema only `requires :repository { requires :full_name }`, it never requires or cross-validates `repository.owner.login` against the field used by the controller: [9](#0-8) .

### Impact Explanation
A payload for one repository (attacker's secret-less org) mutates another tenant's stack: the victim's real `ReviewStack` is deprovisioned (`stack.deprovision`, which per the state machine triggers `stack.provisioner.down`, an actual infrastructure teardown action) and archived, with the acting user forged to any `sender.login` the attacker supplies (creating a `User` record and misattributing the action). This matches the Critical category "a payload for one repository mutating another's stack" and "an unauthorized deploy, rollback"-class action, since deprovisioning a review environment is a destructive infra operation. It is repeatable against any victim repository/PR-number pair as long as at least one secret-less org exists in the multi-org `Shipit.github` config (or the attacker's own installed/configured org lacks `webhook_secret`).

### Likelihood Explanation
Requires a multi-org Shipit deployment (`Shipit.github` keyed by organization) with at least one org configured without a `webhook_secret` — documented as an explicitly supported/optional configuration (`webhook_secret: # nil`) in `docs/setup.md` and `config/secrets.*.yml` examples. Given that precondition, the attacker needs zero secrets: they craft a raw JSON POST to `/webhooks` with `X-Github-Event: pull_request`, `action: closed`, a real `number` and victim `repository.full_name`, and any `repository.owner.login` matching a configured secret-less org. No authentication, session, or GitHub-side action is needed beyond sending the HTTP request.

### Recommendation
Bind the two fields: require that `params.repository.full_name`'s owner segment equals the `repository_owner` used for signature verification (or better, always derive the org for signature verification from the same `full_name` field the handlers use), and reject the request if they diverge. Additionally, do not allow `verify_webhook_signature` to short-circuit to `true` for any org lacking a secret in production, or restrict which orgs can be selected via `repository.owner.login` to only those actually associated with the resolved `Repository` record.

### Proof of Concept
Minitest under `test/controllers/webhooks_controller_test.rb` (integration, no live GitHub):
1. Configure `Shipit.stubs(:github)` (or seed credentials) so `Shipit.github(organization: 'attacker-org')` returns a `GitHubApp` with no `webhook_secret` (secret-less), while a separate `victim-org` has its own repository/stack.
2. Create a real victim `Shipit::ReviewStack` under repository `victim-org/victim-repo` with `environment: "pr#{number}"`, not archived, `provision_status: :provisioned`.
3. POST to `/webhooks` with header `X-Github-Event: pull_request`, and body:
```json
{
  "action": "closed",
  "number": <victim_pr_number>,
  "pull_request": { ... valid nested fields ... },
  "repository": { "full_name": "victim-org/victim-repo", "owner": { "login": "attacker-org" } },
  "sender": { "login": "attacker-chosen-login" }
}
```
No `X-Hub-Signature` header needed (or an arbitrary one), since `attacker-org` has no secret.
4. Assert: `victim_stack.reload.archived?` is `true`, `victim_stack.reload.provision_status` is `"deprovisioning"`/`"deprovisioned"`, and `Shipit::User.find_by(login: "attacker-chosen-login")` exists and is recorded as the actor on the archive audit trail — proving the equality `repository_owner (attacker-org, secret-less) == owning org of mutated stack (victim-org)` does NOT hold, yet the mutation succeeded.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
