### Title
Asset "spender_attested" and address "attested" conditions grant an attestor's attestation more power than intended — presence-only check with no purpose/context scoping - ([File: validation.js], [File: storage.js], [File: definition.js])

### Summary
This is the closest reachable analog to the "FreezerAddress has more power than required" pattern. In the rICO report, an action meant for one narrow purpose (freezing) silently produces additional, undocumented effects in unrelated parts of the system (extending the buy phase, disabling the escape hatch) because the mechanism checks only "did the privileged action happen," not "what was it scoped to." In `ocore`, the `attested` / `spender_attested` primitives have the same structural weakness: an attestor's on-chain attestation is recorded and consumed purely by its existence for an `(attestor_address, address)` pair, without any binding to the asset, AA, or context that the relying party (asset issuer or address definer) actually intended the attestation to vouch for.

### Finding Description
An asset issuer that sets `spender_attested: true` and lists trusted attestors is trusting that attestor to vet spenders **specifically for this asset**. The actual check performed at validation time, however, only verifies that *some* attestation exists from that attestor for the address, irrespective of what the attestation profile says or what it was originally meant to represent: [1](#0-0) 

This helper is invoked identically for `spender_attested` enforcement on both issuance and transfer: [2](#0-1) [3](#0-2) 

The same presence-only semantics apply to the address-definition primitive `attested`, which is validated only for having a valid address and a list of attestor addresses — with no requirement that the attestation carry any particular field/value tied to the definition's purpose: [4](#0-3) 

And on the write path, an `attestation` message stores an arbitrary free-form `profile` object per `(attestor_address, address)` pair, with no linkage to any specific asset, AA, or definition that will later consume it: [5](#0-4) 

Because none of these consumers restrict "attested" to a specific field/value/context, a single attestation issued by a trusted attestor for one purpose (e.g., general KYC for platform A) silently and permanently satisfies `spender_attested` for any other asset that lists the same attestor as trusted, and satisfies `attested` in any address definition referencing that attestor — regardless of whether the attestor ever intended, or was asked, to vouch for that specific asset/definition. This is exactly the "more power than required" pattern: the attestor's single action has reach far beyond the scope the relying party (asset issuer/address definer) documented or expects, with no on-chain signal distinguishing "attested for asset X" from "attested for something unrelated," and no event notifying the relying party that their trust assumption has been exercised outside its intended scope.

### Impact Explanation
- **Unauthorized spending/transfer of a restricted asset**: An address that received an attestation from the trusted attestor for a completely unrelated purpose becomes eligible to issue or receive/transfer a `spender_attested` asset it was never vetted for, because `filterAttestedAddresses` and the `spender_attested` checks in `validation.js` do not verify *what* was attested, only *that* an attestation from that attestor exists. This can bypass the compliance/whitelisting guarantee the asset issuer built the asset around.
- **Trust-boundary violation reachable by an unprivileged actor**: the asset issuer, definer, and any counterparty relying on `attested`/`spender_attested` for access control are affected without any new consent from the attestor, and without any event distinguishing scope — mirroring the "no notification for participants" concern in the original report.

### Likelihood Explanation
Likelihood is Medium: it requires only that (a) an attestor is trusted by more than one asset/definition (common in practice, since well-known attestors like KYC providers are widely reused), and (b) the relying party assumed per-asset/per-purpose scoping which the protocol does not enforce. No malicious node, hub, or network condition is needed — this is purely a consequence of how `validatePayment`/`validatePaymentInputsAndOutputs` and `definition.js` interpret attestation records, triggerable by a normal asset issuer configuration plus an ordinary attestation unit.

### Recommendation
If cross-context reuse of a single attestation is intentional, it should be explicitly documented (as was done for `FreezerAddress`), and asset/definition authors should be given a way to scope `spender_attested`/`attested` checks to a specific profile field/value (similar to how `attestation[[...]]` in formulas can check a field) rather than mere existence of any attestation from the attestor. If not intentional, `spender_attested` and `attested` should require that the referenced attestation include a field/value binding relevant to the consuming asset/definition (e.g., an asset-specific claim), preventing an attestation issued for one purpose from silently authorizing unrelated assets or definitions.

### Proof of Concept
1. Attestor `T` is listed as a trusted attestor by Asset `X` (`spender_attested: true, attestors: [T]`), intended to vouch that a spender is KYC-verified for Asset `X` specifically.
2. Attestor `T` is also a well-known general KYC provider and issues an `attestation` message for address `A` for an unrelated dApp/context, with payload `{address: A, profile: {kyc: true}}` — this is inserted into the generic `attestations` table with no asset binding, per `writer.js` lines 205-216.
3. Address `A`, which was never vetted for Asset `X`, attempts to receive/spend Asset `X`. `validatePayment` calls `storage.loadAssetWithListOfAttestedAuthors` → `filterAttestedAddresses`, which only checks `attestor_address IN(?) AND address IN(?)` with no field/context filter (storage.js:1959-1974), so `A` passes the `spender_attested` check in `validation.js` (lines 2115-2122 / 2630-2641) despite never having been attested for Asset `X`'s intended purpose.
4. Asset `X`'s issuer, who documented the attestor relationship only for their asset's specific compliance requirements, has no visibility that `T`'s unrelated attestation now silently satisfies their asset's access control — the same "more power than required, undocumented, no notification" pattern flagged in the FreezerAddress report.
