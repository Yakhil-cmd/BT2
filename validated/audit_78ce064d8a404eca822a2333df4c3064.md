### Title
Webhook signature is verified against the org derived from `repository.owner.login`, but handlers act on the stack derived from the unrelated `repository.full_name` field, allowing a valid signer for one configured org to spoof events for any other tracked repository - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App/webhook secret to validate the HMAC against using `repository_owner`, computed from the untrusted JSON body as `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`. [1](#0-0) [2](#0-1)  Once the signature check passes, every `Handler` subclass resolves the target repository/stacks using a *different* field of the same untrusted body: `payload.dig('repository', 'full_name')`. [3](#0-2)  Nothing ties `full_name` to `owner.login`, so the field that authorizes the request (which org's secret is used) is not the field that determines which repository is actually written to.

### Finding Description
Shipit explicitly supports "Using Multiple GitHub Applications", where each configured GitHub organization has its own `webhook_secret` (and app credentials) under `config/secrets.yml`, documented in `docs/setup.md`. [4](#0-3)  `Shipit.github(organization:)` picks the `GithubApp` (and thus the `webhook_secret`) for the org named by the payload itself:
```
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(...)
``` [1](#0-0) 
with `repository_owner` read straight out of the unverified JSON body:
```
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [2](#0-1) 

`GithubApp#verify_webhook_signature` performs a straightforward HMAC compare with that org's secret against the raw body. [5](#0-4) 

After the check passes, `Handler#stacks`/`#repository_name` resolve the actual repository to operate on from the same JSON payload, but from an unrelated field:
```
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [3](#0-2) 

Equality broken: `organization authenticated (repository.owner.login used to pick the signing secret) == repository written (repository.full_name used to resolve the Stack)`. An attacker who knows (or controls) the webhook secret for **any one** GitHub organization configured in a multi-tenant Shipit instance can forge a signature valid for `repository.owner.login = <their org>` while setting `repository.full_name = "<victim-org>/<victim-repo>"`. Because the two fields are never cross-checked, the request is accepted and dispatched against the victim stack, e.g. `PushHandler#process` calls `stack.sync_github(expected_head_sha: params.after)` on stacks resolved from the forged `full_name`. [6](#0-5) 

This mirrors the analog bug class from the report: a stale/loosely-bound authorization (old AmoManager keeping its allowance after replacement) — here the "authorization" (which secret validated the request) is bound to one identity (`repository.owner.login`) while the actual privileged action is executed against a different, attacker-chosen identity (`repository.full_name`), i.e. the authenticated scope and the acted-upon scope diverge.

### Impact Explanation
Any organization onboarded to a multi-org Shipit deployment (i.e., an entity that only has legitimate access to its own GitHub App webhook secret) can forge webhook deliveries that are processed as if they came from GitHub for **any other repository tracked by the same Shipit instance**. Depending on handler, this can:
- Force `GithubSyncJob` to run against arbitrary stacks (`PushHandler`), potentially forcing a resync/spoofed HEAD SHA processing for a victim's stack.
- Spoof commit statuses/checks for a victim's commits (`StatusHandler`/`CheckSuiteHandler`), which can satisfy `ci.require`/`ci.blocking` checks used to gate deploys/merges, moving toward an unauthorized deploy or merge for a repository the attacker organization has no legitimate access to.

This crosses a repository-authorization boundary (writing/altering state for a repository the caller does not own), matching the required "cross-repository writes / unauthorized deploy" impact bar for the High/Critical classes.

### Likelihood Explanation
Requires the deployment to use the documented multi-organization GitHub App configuration (a supported, documented feature, not a misconfiguration) and requires the attacker to control/know the webhook secret for at least one of the onboarded organizations — which is normal for any admin of one of the participating orgs in this deployment mode. No repository write access, GitHub App private key, or Shipit session/API token is needed; the request is a plain unauthenticated HTTP POST to `/webhooks` with a self-computed HMAC.

### Recommendation
In `WebhooksController#verify_signature` / `Handler`, cross-validate that the organization used to select the signing secret matches the owner of `repository.full_name` (or, better, always derive the signing organization from `repository.full_name`'s owner rather than from a separate `repository.owner.login`/`organization.login` field) before dispatching to handlers. Reject the webhook if the two disagree.

### Proof of Concept
1. Deploy Shipit with the multi-app config from `docs/setup.md` (`OrgOne`, `OrgTwo`, each with distinct `webhook_secret`), tracking a stack for `OrgTwo/victim-repo`.
2. As an operator who only knows `OrgOne`'s `webhook_secret` (e.g., an org admin who installed the app themselves), compute `sha1=HMAC(OrgOne_secret, body)` for a crafted push payload:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>",
  "repository": { "owner": { "login": "OrgOne" }, "full_name": "OrgTwo/victim-repo" }
}
```
3. POST to `/webhooks` with header `X-Github-Event: push` and `X-Hub-Signature: sha1=<computed>`.
4. `verify_signature` looks up `Shipit.github(organization: "OrgOne")` and validates successfully against `OrgOne`'s secret. [1](#0-0) 
5. `PushHandler` resolves stacks via `repository.full_name = "OrgTwo/victim-repo"` [3](#0-2)  and enqueues `GithubSyncJob` for the victim's stack, despite the request having only been authenticated as `OrgOne`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
