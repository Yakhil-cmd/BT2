### Title
Webhook signature scoping via `repository.owner.login`/`organization.login` is decoupled from the `repository.full_name` used to resolve the target stack, allowing cross-organization forged status/push events - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
Shipit selects which GitHub App (and therefore which `webhook_secret`) to validate a webhook's HMAC signature against using `repository.owner.login` (falling back to `organization.login`) pulled straight out of the *unverified* JSON body. But the handlers that actually act on the payload (`PushHandler`, `StatusHandler`, and all `PullRequest::*Handler`s) resolve the target `Repository`/`Stack` using an entirely different field from the same body: `repository.full_name` via `Repository.from_github_repo_name`. Nothing ties these two fields together, so the "authenticated organization" and the "repository being written to" are two independent, attacker-controlled values inside one signed blob.

### Finding Description
`verify_signature` picks the app/secret purely from attacker-supplied JSON: [1](#0-0) [2](#0-1) 

`repository_owner` is read from `repository.owner.login` (or `organization.login`) - a value that is part of the same raw body being signed, but is only used to pick *whose* secret to check the signature against, not to constrain which repository the event is allowed to reference.

Once the signature check passes, the dispatched handlers ignore `repository.owner.login`/`organization.login` entirely and instead resolve the affected `Stack` via `repository.full_name`: [3](#0-2) [4](#0-3) [5](#0-4) [6](#0-5) 

Because Shipit supports multiple independently configured GitHub organizations, each with its own `webhook_secret`: [7](#0-6) 

an attacker who legitimately owns/administers *any one* of the configured GitHub organizations (or who otherwise learns that organization's `webhook_secret`, e.g. by having their own low-trust org onboarded to the shared Shipit instance) knows a valid HMAC secret usable against this endpoint. That attacker can:

1. Sign a webhook payload with their own organization's secret (`repository.owner.login` = "attacker-org", satisfying `verify_signature`).
2. Set `repository.full_name` = `"victim-org/victim-repo"` inside the exact same payload.
3. Because `Handler#stacks`/`#repository` uses `repository.full_name` only, the event is applied to the victim's stack even though the victim organization never authenticated anything.

This breaks the intended binding **organization that authenticated == repository that is written**, which is explicitly one of the analog classes in scope.

### Impact Explanation
Concretely reachable, unprivileged-to-privileged-write impacts through the in-scope handlers:

- `StatusHandler` lets the attacker forge arbitrary commit statuses (`state`, `context`, `target_url`) for any commit SHA belonging to the victim's stack: [5](#0-4) . If that stack relies on CI status to gate `deployable?`/continuous deployment, an attacker can mark an unreviewed/malicious commit's status as `success`, which can unblock an unauthorized deploy.
- `PushHandler` can force `sync_github(expected_head_sha:)` on a victim stack's branch, causing Shipit to re-sync GitHub state using an attacker-chosen `after` SHA: [8](#0-7) .
- `PullRequest::*Handler`s (open/close/label/reopen) can archive/unarchive review stacks or mutate `PullRequest` records tied to the victim repository by supplying a victim `repository.full_name` while satisfying the signature check against the attacker's own org: e.g. [9](#0-8) .

This meets the "unauthorized deploy" / cross-repository-write bar defined in scope, since the attacker's authenticated organization is not the organization whose repository state is modified.

### Likelihood Explanation
Requires only that the attacker control (or know the `webhook_secret` for) a single GitHub organization that is configured in this Shipit instance's `secrets.yml` `github` multi-org block — a routine, low-privilege setup for any self-service/multi-tenant Shipit deployment (this pattern is explicitly documented and supported: `docs/setup.md` "Using Multiple Github Applications"). No GitHub write access to the victim repository, no Shipit session, and no `ApiClient` token are required — only a validly-signed HTTP POST to `/github/webhooks` is needed, which is unauthenticated network access. This is a realistic, "unprivileged attacker" path per the rules.

### Recommendation
Bind the signature-verifying organization to the organization actually referenced by the payload's `repository.full_name` (or `organization.login`) before dispatching to handlers — i.e., after `verify_webhook_signature` succeeds, assert that `repository.owner.login` (used to pick the secret) equals the owner segment of `repository.full_name` used by `Handler#repository_name`/`Repository.from_github_repo_name`, rejecting the request (422) on mismatch. Alternatively, resolve the target `Repository` first, derive its `github_app`/organization from the stored `Repository#owner`, and verify the signature against that organization's secret rather than trusting an attacker-controlled top-level field to pick the verification key.

### Proof of Concept
1. Attacker registers/administers GitHub organization `attacker-org`, which is configured in this Shipit instance's multi-org `secrets.yml` with its own `webhook_secret`.
2. Attacker computes `sha1=HMAC-SHA1(webhook_secret_attacker_org, body)` for a hand-crafted JSON body:
```json
{
  "sha": "<victim commit sha>",
  "state": "success",
  "context": "ci/required-check",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. POST to `/github/webhooks` with header `X-Github-Event: status` and `X-Hub-Signature: sha1=<computed>`.
4. `verify_signature` looks up `Shipit.github(organization: "attacker-org")` (from `repository.owner.login`) and validates the signature successfully against the attacker's own secret: [1](#0-0) .
5. `StatusHandler#process` then updates the commit status for the SHA belonging to `victim-org/victim-repo`, resolved solely via `repository.full_name`, without ever validating against `victim-org`'s webhook secret: [5](#0-4) .
