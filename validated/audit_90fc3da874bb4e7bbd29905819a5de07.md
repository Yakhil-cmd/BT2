## Title
Unsanitized `peer_party_name`/`my_party_name`/`my_contact_info` in Arbiter Contract Offers Allows ANSI/Control-Character Injection into the Counterparty-Verification Display - (File: `wallet.js`)

### Summary
The `arbiter_contract_offer` device-message handler validates `my_party_name`, `peer_party_name`, and `my_contact_info` only for `typeof === "string"`, with no stripping of control characters or terminal/markup escape sequences, unlike the analogous `device_name` and cosigner-`name` fields elsewhere in the codebase which are explicitly sanitized. This mirrors the openssl_encrypt CVE-2026-81707 pattern (unsanitized identity field used to forge an out-of-band verification cue), except here the forged field is the contract counterparty's displayed name/contact info that the user relies on before approving a shared address and funding an arbiter contract.

### Finding Description
When a peer device sends an `arbiter_contract_offer`, the handler swaps "my"/"peer" fields and only checks that the optional identity fields are strings: [1](#0-0) 

There is no filtering of `<`, `>`, ANSI escape sequences (`\x1b[...`), or other control characters from `body.my_party_name` (becomes `peer_party_name` after swap), `body.peer_party_name`, or `body.my_contact_info`, before the contract is stored and surfaced to the local user for review/approval: [2](#0-1) 

This is inconsistent with how the codebase treats other attacker-supplied identity strings that end up in user-facing trust/verification UI:
- `device_name` during pairing is stripped of HTML-tag-like sequences before being stored/shown as a correspondent's display name: [3](#0-2) 
- `cosigner.name` in multisig-wallet creation offers is likewise stripped of `<>`: [4](#0-3) 
- `wallet_name` in the same flow is also stripped of `<>`: [5](#0-4) 

By contrast, the arbiter-contract party name/contact fields pass through unsanitized into the contract record and are re-derived into the tamper-evident hash: [6](#0-5) 

Since `peer_party_name` is exactly the string an attacker (a paired correspondent device, i.e. the contract counterparty) fully controls, they can embed ANSI escape sequences or other terminal/rendering-control payloads. Any GUI or terminal-based wallet client that renders this field verbatim during the "review contract" / "confirm shared address creation" / "confirm signing" step (the human verification gate before the user authorizes moving `CHARGE_AMOUNT` and later the full contract `amount` into the jointly-controlled `shared_address`) can have its displayed text overwritten or spoofed — e.g., masking the real counterparty name/address or the amount/asset that will actually be encoded in the definition and payment, similar to how the CVE's crafted email forges the fingerprint verification line.

### Impact Explanation
The party name/contact info is the human-readable identity cue the user checks before approving an arbiter contract, which subsequently creates a shared address (`createSharedAddressAndPostUnit`) and sends real funds (`CHARGE_AMOUNT` plus the contracted `amount`) via `sendMultiPayment`: [7](#0-6) 
If the identity/verification text can be spoofed via escape-sequence injection, a malicious counterparty can trick the victim into approving a contract/shared-address/payment they believe is with a different, trusted party or under different terms, leading to unauthorized spending of the victim's funds — the same class of harm (trust bypass leading to fund loss) targeted by the CVE.

### Likelihood Explanation
Any already-paired device (a normal, low-privilege counterparty in a P2P contract negotiation — explicitly in scope) can send an `arbiter_contract_offer` with a crafted `peer_party_name`/`my_contact_info` value; no special privileges beyond an existing device pairing are needed, and the message passes the existing hash/type/format validation because those checks do not constrain the *content* of the name/contact strings, only their presence and type.

### Recommendation
Sanitize `my_party_name`, `peer_party_name`, and `my_contact_info` (and any other free-text fields intended for identity/verification display, e.g. in `prosaic_contract.js`) the same way `device_name`/`cosigner.name`/`wallet_name` are sanitized — strip or reject control characters (including ANSI CSI/OSC escape sequences `\x1b...`) and HTML-like tags, and enforce this at the point the message is received in `wallet.js`'s `arbiter_contract_offer` handler before the value is persisted, hashed, or emitted to any UI event.

### Proof of Concept
1. Device A pairs with Device B (normal, unprivileged pairing flow).
2. Device B sends an `arbiter_contract_offer` message to Device A with `my_party_name` set to a string containing an ANSI escape sequence designed to overwrite subsequent terminal/GUI output, e.g. `"Alice\x1b[2K\x1b[1G" + "Trusted-Escrow-Bot"` (or, for GUI clients, characters/markup that visually relocate/hide text depending on the renderer).
3. `wallet.js` handler at lines 617-634 accepts the field (only `typeof` check passes), swaps it into `peer_party_name` on Device A's side, and stores/forwards it via `arbiter_contract.store`/`getHash`.
4. When Device A's client renders the contract offer for user confirmation (party name / contact info used as the verification cue for "who am I dealing with"), the injected sequence manipulates the displayed text, potentially hiding or replacing the real counterparty identity.
5. The victim approves the shared address and contract, sending `CHARGE_AMOUNT` and later the full contracted `amount` under a false belief about the counterparty's identity.
