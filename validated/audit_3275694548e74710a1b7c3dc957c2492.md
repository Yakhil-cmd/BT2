### Title
Webhook signature is verified against the organization named in an unverified payload field, letting a trusted org's webhook secret forge a `status` event for any repository's commit - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which `GitHubApp` (and therefore which `webhook_secret`) is used to validate the inbound `X-Hub-Signature` by reading `repository_owner` straight out of the still-unverified JSON body. The `StatusHandler` that later processes a validated `status` event never re-checks that field against the commit it updates — it looks the commit up globally by `sha` with no repository scoping at all. This breaks the equality that should hold: *the organization whose secret authenticated the request* must equal *the repository/commit that the request is allowed to mutate*.

### Finding Description
The signature check derives the signing organization purely from attacker-supplied JSON, before the signature has been verified: [1](#0-0) [2](#0-1) 

`repository_owner` is read from `params.dig('repository', 'owner', 'login')` or falls back to `params.dig('organization', 'login')` — both attacker-controlled fields of the same untrusted body used to compute `Shipit.github(organization: repository_owner)` and thus the `webhook_secret` used for HMAC comparison: [3](#0-2) 

Once the signature is accepted, `Shipit::Webhooks.for_event(event)` dispatches to handlers that operate on a *different* field of the same body. `StatusHandler` in particular performs a completely global lookup by `sha`, with no relation at all to `repository_owner` or even to `repository.full_name`: [4](#0-3) 

Shipit natively supports multiple GitHub organizations configured with independent `webhook_secret`s, each installed via its own GitHub App: [5](#0-4) 

An operator who legitimately owns/administers one of these configured organizations (e.g., `OrgTwo`) — and therefore knows its `webhook_secret` — can compute a valid `X-Hub-Signature` for that organization, while putting an arbitrary `sha` value (belonging to a commit tracked under a completely different, unrelated repository/stack) in the payload. `verify_signature` only checks "does this signature match OrgTwo's secret," never "does OrgTwo actually own the commit/repository this payload is about." `StatusHandler#process` then writes a forged CI status onto that unrelated commit via `commit.create_status_from_github!(params)`.

This is the direct analog of the reported bug class: a value that gates/authenticates an operation (`repository_owner`, standing in for "requested/authorized amount") is disconnected from the value actually acted upon (`sha`/commit, standing in for "amount transferred"), and the downstream code (`StatusHandler`) treats the two as if they were the same trust domain.

### Impact Explanation
A forged CI status can flip `commit.deployable?` for a commit in a repository the attacker does not own. The API deploy endpoint gates deploys on this exact property when `require_ci` is requested: [6](#0-5) 

An attacker who controls only their own organization's GitHub App / webhook secret can therefore fabricate a passing CI status for an arbitrary victim commit, satisfying the `require_ci` deployability check and enabling an unauthorized deploy of that commit — a cross-repository write into state (`Statuses`/`deployable?`) that should only be writable by the actual owning organization. This matches the Critical bucket ("cross-repository writes" / "an unauthorized deploy").

### Likelihood Explanation
Requires only that the attacker be the legitimate administrator/owner of one organization already configured in a multi-org Shipit deployment (a supported, documented configuration), and that they can reach the public `/webhooks` endpoint — no Shipit session, `ApiClient` token, or repository write access to the victim repo is needed. This is a realistic, medium-likelihood setup for any Shipit instance managing more than one GitHub organization.

### Recommendation
`verify_signature` must not trust the payload for determining *which* secret is authoritative independently of what is later authorized. Concretely:
- Bind webhook events to the same organization/repository that produced the valid signature — e.g., after determining `repository_owner` and validating the signature, re-derive/require that `repository.full_name`'s owner segment (and any handler's target repository/commit) matches `repository_owner`, rejecting mismatches.
- Scope `StatusHandler` (and any other handler that looks up state by an ID/sha alone) to the repository/stack derived from `repository.full_name`, consistent with `Handler#stacks`/`Handler#repository_name`, instead of doing a global `Commit.where(sha:)` lookup.

### Proof of Concept
1. Configure Shipit with two organizations, `OrgOne` and `OrgTwo`, each with distinct `webhook_secret`s (supported configuration, see `test/dummy/config/secrets_double_github_app.yml`).
2. Attacker legitimately administers `OrgTwo`'s GitHub App and therefore knows `OrgTwo`'s `webhook_secret`.
3. Attacker crafts a `status` event body:
```json
{
  "repository": { "owner": { "login": "OrgTwo" }, "full_name": "OrgTwo/some-repo" },
  "sha": "<sha of a commit belonging to a stack under OrgOne>",
  "state": "success",
  "context": "ci/forged"
}
```
4. Attacker computes `X-Hub-Signature: sha1=HMAC(webhook_secret_of_OrgTwo, body)` and POSTs to `/webhooks` with `X-Github-Event: status`.
5. `verify_signature` calls `Shipit.github(organization: "OrgTwo")` and successfully verifies the attacker's own signature [1](#0-0) .
6. `StatusHandler#process` runs `Commit.where(sha: params.sha)` — matching the OrgOne commit regardless of the signing organization — and calls `create_status_from_github!`, writing a forged "success" status onto a commit the attacker does not control [4](#0-3) .
7. If that OrgOne commit is later targeted with `POST /api/stacks/:id/deploys` with `require_ci: true`, `commit.deployable?` now returns true due to the forged status, permitting an unauthorized deploy [6](#0-5) .

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
