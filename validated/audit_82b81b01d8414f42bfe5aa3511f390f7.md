### Title
Cross-organization webhook forgery leads to unauthorized deploy via forged CI status — ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App secret to validate the HMAC signature against based on `repository_owner`, which is read straight out of the untrusted, attacker-supplied JSON body (`params.dig('repository','owner','login')` or `params.dig('organization','login')`). However, the handlers that actually act on the payload (e.g. `Handler#repository_name`, used to look up the target `Repository`/`Stack`) independently read `payload.dig('repository','full_name')` from the same body, with no cross-check that this repository belongs to the organization whose secret validated the signature.

### Finding Description
In a multi-org Shipit deployment (explicitly documented and supported, see `docs/setup.md` "Using Multiple Github Applications" and `test/dummy/config/secrets_double_github_app.yml`), each GitHub organization has its own `webhook_secret`. `WebhooksController#verify_signature` picks the app/secret via:

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [4](#0-3) 

The signature is verified over the *entire raw body* using the secret picked from `repository.owner.login`/`organization.login`. Nothing stops an attacker who knows (or controls) organization A's `webhook_secret` from crafting a JSON body where `repository.owner.login` (or `organization.login`) is `"A"` (so the correct/known secret is selected and the HMAC validates) while `repository.full_name` is set to `"B/some-repo"` — a completely different, target organization's repository.

Downstream, `Shipit::Webhooks::Handlers::Handler#repository_name` and `#stacks` blindly trust `repository.full_name` from the same body to resolve the target `Repository`/`Stack`, independent of which org's secret validated the signature:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [5](#0-4) 

The `status` event handler creates `Shipit::Status` records for the commit sha given in the payload, scoped to whatever stack `repository_name` resolves to:

```ruby
status = commit.statuses.last
...
status.target_url ... status.state ...
```
(test evidence) [6](#0-5) 

Creating a `success` status on a commit triggers `Commit#schedule_continuous_delivery`, which enqueues `ContinuousDeliveryJob` when `stack.continuous_deployment?` is true, and that job calls `Stack#trigger_continuous_delivery`, which builds and runs an actual `Deploy` if the commit is now considered `deployable?`: [2](#0-1) [3](#0-2) [1](#0-0) 

### Impact Explanation
An attacker who only possesses (or is a legitimate low-privilege webhook admin of) organization A's webhook secret can forge a `status` (or `push`, `pull_request`, `check_suite`, `membership`) event whose signature validates against A's secret, but whose `repository.full_name` targets a Stack belonging to organization B — an org the attacker has no access to. For a stack with `continuous_deployment: true` and CI-based deployability gating, forging a `success` status for the required CI context is sufficient to trigger an unauthorized `Deploy` on organization B's stack, i.e., an unauthorized deploy triggered purely by crafting an HTTP request the attacker can self-sign with a secret from an unrelated, lower-trust organization they legitimately control. This satisfies the Critical impact bar: "an unauthorized deploy."

### Likelihood Explanation
This requires the target Shipit instance to be configured with multiple GitHub organizations (an explicitly documented, supported configuration), and the attacker must know one organization's `webhook_secret` (e.g., because they administer that org's GitHub App settings, which is a plausible position for a partner/customer organization onboarded to a shared Shipit instance) — no access to the target organization or to any Shipit account/API token is required. Since `webhook_secret` per-org is meant to prove "this request originated from org A's GitHub App," but the code never binds the verified org to the repository actually acted upon, likelihood is elevated to realistic for any Shipit deployment serving more than one organization.

### Recommendation
After successfully verifying the signature for `repository_owner`, additionally verify that `payload.dig('repository','full_name')`'s owner matches `repository_owner` (or, more robustly, derive the app/secret to check purely from `repository.full_name` and reject payloads where `organization.login`/`repository.owner.login` disagree). Handlers resolving stacks via `repository_name` should also assert that the resolved `Repository#owner` equals the organization whose secret validated the request before acting on the payload.

### Proof of Concept
1. Configure Shipit with two orgs, `OrgA` and `OrgB`, each with its own `webhook_secret` (per `docs/setup.md` multi-org setup).
2. Attacker knows `OrgA`'s `webhook_secret` (e.g., they are OrgA's own GitHub App admin).
3. Attacker POSTs to `/webhooks` with header `X-Github-Event: status` and body:
```json
{
  "sha": "<commit-sha-of-OrgB-stack>",
  "state": "success",
  "context": "ci/required-context",
  "repository": { "full_name": "OrgB/target-repo", "owner": { "login": "OrgA" } }
}
```
4. Signs the raw body with `OrgA`'s `webhook_secret`, sets `X-Hub-Signature` accordingly.
5. `WebhooksController#verify_signature` computes `repository_owner` = `"OrgA"`, fetches `OrgA`'s app, validates the signature successfully.
6. `Handlers::StatusHandler` uses `repository.full_name` = `"OrgB/target-repo"` to find `OrgB`'s stack and creates a `success` `Status` on the target commit, which — if `OrgB`'s stack has `continuous_deployment: true` and this was the last required CI check — immediately triggers a live `Deploy` on `OrgB`'s stack, entirely bypassing OrgB's real CI/CD pipeline and org boundary.
