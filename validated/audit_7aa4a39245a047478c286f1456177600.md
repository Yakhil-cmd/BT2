### Title
Stack-scoped API tokens can read CCMenu build status for arbitrary stacks - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::ApiClient` records can be scoped to a single stack via the `stack_id` column, and `Shipit::Api::BaseController` enforces that scoping for every API endpoint by resolving stacks through the `stacks` helper. `Shipit::Api::CCMenuController`, however, overrides `stack` to resolve directly from `Stack.from_param!(params[:stack_id])`, bypassing the per-client stack scoping entirely.

### Finding Description
`Shipit::ApiClient#stack_id` allows an operator to mint a token that is authorised to act only on one particular stack: [1](#0-0) 

`Shipit::Api::BaseController` is the shared authentication/authorization layer for the JSON API. It enforces this scoping by restricting the queryable set of stacks to the client's own `stack_id` when one is set, and resolving the requested stack from that restricted set: [2](#0-1) 

This is the binding the engine intends to hold: `token.stack_id == requested_stack.id` (or, when unscoped, "any stack") must be true before any per-stack data is returned. `require_permission!` only checks the coarse-grained permission string (e.g. `read:stack`); it never checks which stack the token is bound to — that check is entirely delegated to the `stacks`/`stack` helper.

`Shipit::Api::CCMenuController` re-implements `stack` without going through `stacks`: [3](#0-2) 

Because `Stack.from_param!` queries the full `Stack` table rather than `current_api_client.stack_id`-restricted `stacks`, the equality the rest of the API enforces (`token.stack_id == requested_stack.id`) is silently dropped for this one controller. `require_permission :read, :stack` on this controller only proves the token holds the generic `read:stack` permission, not that it is bound to the stack being fetched: [4](#0-3) 

The same authentication mechanism as the rest of the API is used (`ApiClient.authenticate` via Basic auth or the `token` query param): [5](#0-4) 

### Impact Explanation
A stack-scoped, `read:stack`-only token (the kind Shipit itself mints for the "CCMenu URL" feature, which is designed to be embedded in third-party CI dashboard tools and is therefore lower-trust and more exposed than a full admin token) can be replayed against `/api/stacks/:stack_id/ccmenu.xml` with an arbitrary `stack_id` to read another stack's build/deploy status, lock state, and lock reason — data the token was never authorised to see. This crosses the "a stack a token authorises versus a stack it touches" trust boundary called out in scope, and matches the CCMenu URL creation path: [6](#0-5) 

This is an unauthenticated-for-other-stacks read of stack state (deploy status, lock reason), which the rules classify as High impact ("unauthenticated read of stack state, task streams or deploy output" via authorization-scope escalation). It does not, by itself, rise to Critical since no write, deploy, or credential exfiltration is possible through this endpoint.

### Likelihood Explanation
Likelihood is moderate-to-high in any deployment that uses stack-scoped tokens (e.g., the built-in CCMenu-URL flow, or any operator who scopes tokens to a stack for least-privilege reasons). Exploitation requires only possession of one valid stack-scoped token with `read:stack` permission — no special privilege, no secret material beyond that single token, and no interaction with other users.

### Recommendation
Make `Shipit::Api::CCMenuController#stack` go through the same `stacks` scoping used everywhere else in the API, e.g. `stacks.from_param!(params[:stack_id])`, so a stack-scoped `ApiClient` cannot resolve stacks outside its `stack_id`.

### Proof of Concept
1. As an operator/user with access to Stack A, generate a CCMenu URL for Stack A (`CCMenuUrlController#fetch`), which mints an `ApiClient` scoped to Stack A with `permissions: ['read:stack']` and yields a token `T`.
2. As an unprivileged holder of `T` (e.g., anyone who obtained the CCMenu URL, which is designed to be embedded in external CI dashboards), request:
   `GET /api/stacks/<stack-B-id>/ccmenu.xml?token=T`
   where Stack B is a different, unrelated stack.
3. Because `CCMenuController#stack` calls `Stack.from_param!(params[:stack_id])` directly instead of the client-scoped `stacks` helper, the request succeeds and returns Stack B's build status, lock state, and lock reason, even though `T.stack_id == Stack A.id` and `T` was never authorised for Stack B — compare with the equivalent request against `Shipit::Api::StacksController#show`, which is correctly scoped and would 404/empty out for a token bound to a different stack via `stacks.from_param!`: [2](#0-1)
