### Title
Unvalidated `data_length` field in `temp_data` messages allows negative-size manipulation of payload commission accounting - ([File: object_length.js])

### Summary
`object_length.js`'s `extractTempData()`/`getTotalPayloadSize()` sums the attacker-supplied `payload.data_length` field with no sign or magnitude check before it is used to compute the unit's required `payload_commission`, mirroring the FreeSWITCH `Content-Length` bug where an untrusted length field flows straight into a size computation (`malloc(len+1)`) with no bounds validation.

### Finding Description
`extractTempData()` iterates over a unit's messages and, for any `app === "temp_data"` message, adds `m.payload.data_length + 4` to a running `temp_data_length`, requiring only that `data_length` be of `typeof "number"` — no check that it is positive, integral, or bounded: [1](#0-0) 

This `temp_data_length` is fed straight into `getTotalPayloadSize()`, which computes `Math.ceil(temp_data_length * constants.TEMP_DATA_PRICE) + getLength(...)` — the value used to compare against the unit's claimed `payload_commission`: [2](#0-1) 

In `validate()`, this unchecked computation is performed and compared against `objUnit.payload_commission` very early in joint validation, at the header/joint level: [3](#0-2) 

The actual `isPositiveInteger(payload.data_length)` sanity check on the field only happens later, per-message, inside `validateInlinePayload()`'s `"temp_data"` case: [4](#0-3) 

Because the joint-level commission check (`objectLength.getTotalPayloadSize(objUnit) !== objUnit.payload_commission`) runs before the per-message `isPositiveInteger` check, an attacker can post a unit with a negative `data_length` in a `temp_data` message. This drives `temp_data_length` negative, which can offset/undercount the true payload size used in the `payload_commission` equality check, letting an attacker construct a unit whose declared `payload_commission` (and therefore the fee charged / MAX_UNIT_LENGTH oversize check at line 267) does not match the real serialized size of the unit's messages.

### Impact Explanation
This falls under "payment inputs/outputs and commissions" — a validator could accept a unit whose commission/size accounting is wrong, which can be leveraged to under-pay headers/payload commission or to bypass the `MAX_UNIT_LENGTH`/oversize-fee check (`objUnit.headers_commission + objUnit.payload_commission > constants.MAX_UNIT_LENGTH`) at validation.js:267, potentially letting a poster smuggle a larger effective payload than the network fee structure intends, or triggering an inconsistency between nodes that compute commission at different validation stages. This is a commission/accounting integrity issue reachable by any unprivileged unit poster.

### Likelihood Explanation
Any unprivileged node can post a unit containing a `temp_data` message with an out-of-range `data_length` (e.g., negative) as long as `last_ball_mci >= constants.v4UpgradeMci` (temp_data is available). The vulnerable computation (`extractTempData`/`getTotalPayloadSize`) runs unconditionally in `validate()` before the compensating per-message check, so the attack surface is directly reachable from the standard unit-validation path with no special privileges.

### Recommendation
Move (or duplicate) the `isPositiveInteger(payload.data_length)` bound/sign check into `extractTempData()`/`getTotalPayloadSize()` itself (or run per-message inline-payload structural validation before computing `getTotalPayloadSize()` in `validate()`), so that a malformed/negative `data_length` causes immediate rejection rather than being summed into the commission calculation unchecked.

### Proof of Concept
1. Craft a unit with a `temp_data` message: `{ app: "temp_data", payload: { data_length: -100000000, data_hash: "<valid-base64>" }, payload_location: "inline" }`.
2. Set `objUnit.payload_commission` to a value consistent with `getTotalPayloadSize()`'s output given the negative `data_length` (computable locally since the formula is deterministic and public).
3. Submit the joint; `validate()` at validation.js:257-269 accepts the mismatched/negative-adjusted size before the later `isPositiveInteger` check in `validateInlinePayload` (validation.js:1975) is reached — demonstrating the ordering flaw that lets a crafted negative length pass the commission-size gate.

function extractTempData(messages) {
	let temp_data_length = 0;
	let messages_without_temp_data = messages;
	for (let i = 0; i < messages.length; i++) {
		const m = messages[i];
		if (m.app === "temp_data") {
			if (!m.payload || typeof m.payload.data_length !== "number") // invalid message, but we don't want to throw exceptions here, so just ignore, and validation will fail later
				continue;
			temp_data_length += m.payload.data_length + 4; // "data".length is 4
			if (m.payload.data) {
				if (messages_without_temp_data === messages) // not copied yet
					messages_without_temp_data = _.cloneDeep(messages);
				delete messages_without_temp_data[i].payload.data;
			}
		}
	}
	return { temp_data_length, messages_without_temp_data };
}
