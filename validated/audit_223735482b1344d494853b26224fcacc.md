### Title
StatusHandler#process updates Commit rows across all stacks/repositories without scoping by the webhook's repository - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` queries `Commit.where(sha: params.sha)` and calls `create_status_from_github!` on every match, without restricting to the stacks belonging to the repository named in the webhook payload. This differs from `PushHandler#process`, which correctly scopes via `stacks.not_archived.where(branch:)` [1](#0-0) . Since git commit SHAs are content-addressed and identical across forks/mirrors, an attacker who owns a legitimately-installed GitHub App/repo can send a validly-signed status webhook whose `sha` matches a commit that also exists (with the same SHA) in an unrelated victim stack, and that victim's `Commit` row will be mutated too.

### Finding Description
The broken binding: `StatusHandler#process`'s update set should equal `Handler#stacks(repository_name).commits.where(sha: params.sha)`, but it instead equals `Commit.where(sha: params.sha)` unscoped over the entire table.

Code path:
1. `WebhooksController#create` parses the JSON body and dispatches to handlers for the event, calling `handler.call(params)` [2](#0-1) .
2. `verify_signature` only checks that the payload is validly signed by the GitHub App installed for `repository_owner` (derived from `payload['repository']['owner']['login']`) [3](#0-2) . This proves the payload came from a GitHub App installed on the *attacker's own org*, not any authorization over which `Commit` rows can be touched.
3. `Handler#initialize` -> `Handler.call` -> `StatusHandler#process` executes `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [4](#0-3) . `params.sha` and `params.state` are attacker-controlled fields from the JSON body (validated only for type/presence by `ExplicitParameters`) [5](#0-4) .
4. `Handler#stacks` exists and correctly scopes to `Repository.from_github_repo_name(repository_name)&.stacks` [6](#0-5) , but `StatusHandler#process` never calls it.
5. `Commit#create_status_from_github!` writes a new `Status` row and triggers `add_status`, which emits `Hook.emit(:commit_status, ...)` / `:deployable_status` hooks and can call `stack.schedule_merges` when the new status is pending/successful [7](#0-6) [8](#0-7) .

Exploit: attacker installs/owns a GitHub App-authenticated repo `attacker-org/repo`, obtains a public commit SHA that a victim's Shipit stack also tracks (common for forks/mirrors/vendoring where identical commits produce identical SHAs), and sends a `status` webhook payload naming `attacker-org/repo` but with `sha` = victim's commit SHA and an attacker-chosen `state` (e.g., `success`). `verify_signature` passes because the signature is valid for the attacker's own org's app installation. `StatusHandler` then matches and updates *every* `Commit` row across the entire database with that SHA — including the victim's — potentially marking a victim's commit as passing status checks, which can trigger `stack.schedule_merges` and downstream deploy/merge automation on the victim's stack.

None of the listed guards prevent this: `verify_signature` authenticates the *sender's own org*, not the target of the mutation; the `ExplicitParameters` schema only validates types; there is no `stacks`/`subset` scoping applied in this handler.

### Impact Explanation
An attacker fully controlling only their own repository/org can inject arbitrary commit statuses (`success`, `failure`, `error`, `pending` with attacker-chosen `description`/`target_url`) onto commit records belonging to a completely different, unrelated stack/tenant, as long as the SHA collides (which is guaranteed for identical mirrored/forked commits). This can flip a victim commit's `deployable?`/blocking status and trigger `stack.schedule_merges`, i.e., a payload for one repository mutates another repository's/tenant's commit and status records — matching the "Critical: a payload for one repository mutating another's stack, commit, task or team" category. The attack is repeatable against any victim stack that happens to track a SHA the attacker can also produce/reference via their own installation.

### Likelihood Explanation
Preconditions: the attacker needs their own GitHub App installation (or any repo covered by a Shipit-recognized org) to pass `verify_signature`, and a target victim stack must contain a `Commit` with the same SHA as one the attacker references (realistic for forks, mirrors, or shared upstream dependencies/vendoring workflows, which the prompt states is the scenario). No Shipit session, API token, or team membership is required — only the ability to trigger/craft a GitHub status webhook for a repository the attacker controls. This is low-cost and fully repeatable.

### Recommendation
Scope `StatusHandler#process` the same way `PushHandler` does, e.g.:
```ruby
def process
  stacks.flat_map(&:commits).select { |c| c.sha == params.sha }... 
end
```
or more precisely, join through the repository's stacks:
```ruby
def process
  Commit.where(sha: params.sha).joins(:stack).merge(stacks).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
using the existing `Handler#stacks` scope so only commits belonging to stacks of the webhook's own repository are updated.

### Proof of Concept
Minitest plan (under `test/models/shipit/webhooks/handlers/status_handler_test.rb`, illustrative):
```ruby
test "process only updates commits belonging to the webhook's own repository's stacks" do
  attacker_stack = shipit_stacks(:shipit)          # tracks repo "attacker-org/repo"
  victim_stack   = create_stack(repository: create_repository(owner: 'victim-org', name: 'repo'))

  shared_sha = 'a' * 40
  attacker_commit = attacker_stack.commits.create!(sha: shared_sha, ...)
  victim_commit   = victim_stack.commits.create!(sha: shared_sha, ...)

  payload = {
    'sha' => shared_sha,
    'state' => 'success',
    'repository' => { 'full_name' => 'attacker-org/repo', 'owner' => { 'login' => 'attacker-org' } }
  }

  Shipit::Webhooks::Handlers::StatusHandler.call(payload)

  # Binding under test: only attacker_stack's commit (Handler#stacks("attacker-org/repo")) should change
  assert attacker_commit.reload.statuses.any?, "expected attacker's own commit to receive status"
  assert_empty victim_commit.reload.statuses, "victim's unrelated commit must NOT be mutated by attacker-org's webhook"
end
```
With current code, `victim_commit.statuses` is non-empty (test fails), proving the vulnerability; after applying the recommended fix scoping by `stacks`, the assertion passes.

    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
