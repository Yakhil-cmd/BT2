### Title
`provision?` operator-precedence bug bypasses `review_stacks_enabled` gate for `allow_with_label`/`prevent_with_label` behaviors, and no test in `opened_handler_test.rb` catches it - (File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb)

### Summary
`provision?` is written as `a && b || c || d` where Ruby's operator precedence groups `&&` tighter than `||`, so `repository.review_stacks_enabled` only gates the `allow_all?` branch and not the `allow_with_label?`/`prevent_with_label?` branches. The suite in `test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb` never exercises `review_stacks_enabled: false` together with `allow_with_label`/`prevent_with_label`, so this precedence bug is not caught by CI.

### Finding Description
The intended binding is:
`provision? == repository.review_stacks_enabled && (allow_all? || (allow_with_label? && label) || (prevent_with_label? && !label))`

The actual code is: [1](#0-0) 

which Ruby parses as:
`(review_stacks_enabled && allow_all?) || (allow_with_label? && label) || (prevent_with_label? && !label)`

These two forms diverge whenever `review_stacks_enabled == false` and `provisioning_behavior` is `allow_with_label` or `prevent_with_label`: the intended form always yields `false`, but the actual code can yield `true` (e.g. `prevent_with_label` with no matching label present evaluates `!label == true`, so `provision?` is `true` even though review stacks are disabled for the repository).

`respond_to_pull_request_opened?` gates `process`, which calls `ReviewStackAdapter#find_or_create!` to provision a new review stack from the attacker-controlled PR branch: [2](#0-1) 

`repository` is resolved from `params.repository.full_name`, i.e., an already-tracked repository record, and `provisioning_behavior`/`provisioning_label_name`/`review_stacks_enabled` are read straight off that ActiveRecord model with no additional AND-gating logic: [3](#0-2) [4](#0-3) 

The existing test suite verifies `review_stacks_enabled: false` only for the `allow_all` behavior: [5](#0-4) 

and separately verifies `allow_with_label`/`prevent_with_label` behavior only with `review_stacks_enabled` left at its (enabled) default: [6](#0-5) 

No test combines `review_stacks_enabled: false` with `allow_with_label` or `prevent_with_label`, so the precedence bug ships undetected.

### Impact Explanation
For a repository whose operator has explicitly disabled review-stack auto-provisioning (`review_stacks_enabled: false`) but left `provisioning_behavior` at `allow_with_label` or `prevent_with_label` (the enum's non-default states), an unprivileged contributor who can open a pull request (and, for `allow_with_label`, apply/omit a label on their own PR) can still trigger `provision?` to return `true`, causing Shipit to auto-provision a review stack from the attacker's branch despite the operator's explicit opt-out. Because review-stack provisioning ultimately runs the deploy-spec–defined provisioning commands sourced from the PR's own branch, this is a path to executing attacker-controlled commands on the deploy host — matching the Critical "RCE via `Command`/task execution on an unauthorized repository configuration" category. The blast radius is scoped to repositories configured this specific way, but it is fully repeatable per PR.

### Likelihood Explanation
Requires a Shipit-tracked repository configured with `review_stacks_enabled: false` and `provisioning_behavior` set to `allow_with_label` or `prevent_with_label` — a plausible, even expected, configuration (operator wants no review stacks but hasn't reset behavior back to a neutral value, or is in the middle of disabling the feature). No secrets or elevated privileges are needed by the attacker beyond the ability to open a PR (and label it, for the `allow_with_label` case, which any PR author or maintainer with label rights could do, or which defaults to `false`/no-label satisfying `prevent_with_label`). This is a pure logic defect, deterministic and 100% reproducible against any repo in that configuration state.

### Recommendation
Explicitly parenthesize the boolean expression to match intended semantics:
```ruby
def provision?
  repository.review_stacks_enabled &&
    (repository.provisioning_behavior_allow_all? ||
     (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
     (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?))
end
```
Additionally add minitest coverage in `test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb` enumerating all `review_stacks_enabled` × `provisioning_behavior` × label-presence combinations and asserting `provision? == false` whenever `review_stacks_enabled == false`.

### Proof of Concept
Add to `test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb`:
```ruby
[:allow_all, :allow_with_label, :prevent_with_label].each do |behavior|
  [true, false].each do |label_present|
    test "does not create stacks when review_stacks_enabled is false (behavior=#{behavior}, label_present=#{label_present})" do
      repository = shipit_repositories(:shipit)
      configure_provisioning_behavior(
        repository:,
        provisioning_enabled: false,
        behavior:,
        label: "pull-requests-label"
      )
      payload = payload_parsed(:pull_request_opened)
      payload["pull_request"]["labels"] = label_present ? [{ "name" => "pull-requests-label" }] : []

      assert_no_difference -> { Shipit::Stack.count } do
        OpenedHandler.new(payload).process
      end
    end
  end
end
```
Before the fix, the `behavior: :prevent_with_label, label_present: false` (and `allow_with_label, label_present: true`) cases fail — a stack IS created — proving `provision?` diverges from `repository.review_stacks_enabled && (...)` when `review_stacks_enabled` is `false`.
