### Title
Independently-rounded `earned_headers_commission_share` splits let a multi-author unit fabricate extra bytes when winning headers commission - (File: headers_commission.js)

### Summary
`calcHeadersCommissions()` splits a fixed headers-commission pool (`full_amount`, the `headers_commission` of the parent unit) among the `earned_headers_commission_recipients` of the winning child unit by rounding each recipient's share independently: `Math.round(full_amount * share / 100.0)`. Because rounding is applied per-recipient instead of once with a remainder correction, the sum of the rounded amounts can exceed `full_amount`, minting extra bytes that were never actually paid by anyone. This is the same rounding-without-remainder-correction bug class as the referenced Tessera `GroupBuy` finding (dividing/splitting a fixed pool per-share without accounting for the residual), except here the arithmetic error benefits everyone at once rather than penalizing a "last" claimant, i.e. it inflates the byte supply instead of running one recipient short.

### Finding Description
`headers_commission.js` distributes each parent unit's `headers_commission` to the child unit that wins it. If the winning child unit has more than one author (or explicitly declares `earned_headers_commission_recipients`), the commission is split across recipients according to `earned_headers_commission_share` percentages that a unit author fully controls and that are only required to sum to exactly 100 (`validateHeadersCommissionRecipients` in `validation.js`, requiring `total_earned_headers_commission_share === 100`). The actual split, however, is computed by rounding each recipient's fractional share separately: [1](#0-0) 

and, in the (default) MySQL/production code path, the same independent per-recipient rounding is done both in the in-RAM computation and via `ROUND(...)` in SQL: [2](#0-1) [3](#0-2) 

Because `Math.round`/SQL `ROUND` are applied to each share independently, a set of shares that sums exactly to 100% can still produce individually rounded amounts whose sum is strictly greater than `full_amount`. For example, with `full_amount = 150` and two recipients holding shares `1` and `99`:
- recipient A: `round(150 * 1 / 100) = round(1.5) = 2`
- recipient B: `round(150 * 99 / 100) = round(148.5) = 149`
- total inserted into `headers_commission_contributions` = 151, i.e. 1 byte more than the `headers_commission` actually available for distribution.

These per-recipient amounts are inserted directly into `headers_commission_contributions` and later aggregated into `headers_commission_outputs`, which become spendable balances via `headers_commission`-type inputs validated in `validation.js`: [4](#0-3) 

An unprivileged unit author fully controls both the number of authors on a unit and the `earned_headers_commission_recipients` percentage split (subject only to the 100%-sum and sorted-address constraints validated in `validateHeadersCommissionRecipients`): [5](#0-4) 

so an attacker can deliberately choose share percentages (e.g. skewed splits like `1%/99%`, or many small shares) that maximize the rounding surplus on every occasion the unit wins headers commission from a parent, systematically fabricating extra bytes with no counterparty loss.

### Impact Explanation
This is a supply-inflation bug: bytes are created that were never paid into the network by any unit, directly analogous to the impact category "supply inflation" called out in the validation rules. Every multi-author unit an attacker gets to win headers commission (which is a normal, cheap, and repeatable occurrence — headers commission is earned any time a unit is selected as the "best child" of a parent unit) can leak a few extra bytes into `headers_commission_outputs`, spendable balances that did not exist before. Repeated over many units/parent commissions this steadily inflates the total byte supply, which is a High-severity systemic integrity violation (undermines the fixed/predictable issuance guarantees of the DAG).

### Likelihood Explanation
Likelihood is high: no special privilege is needed — any address can author a unit with multiple authors (or a single author plus an explicit `earned_headers_commission_recipients` override) and choose arbitrary percentage splits that sum to 100. Headers commission is won routinely by ordinary units (whichever child is selected as "best child" of a parent per the existing tie-break logic in `getWinnerInfo`), so an attacker only needs to get their crafted multi-recipient unit selected as a winning child, which happens naturally through normal DAG growth, not through any adversarial network condition.

### Recommendation
Do not round each recipient's share independently. Instead, compute the last recipient's amount as the remainder (`full_amount - sum of already-rounded amounts for previous recipients`) so the total distributed always exactly equals `full_amount`, mirroring the standard fix for the `GroupBuy`-style rounding bug (adjust one designated recipient to absorb the rounding delta rather than letting every recipient round independently). This should be applied consistently in both the RAM computation path and the SQL/`ROUND(...)`-based query path in `headers_commission.js`, and the invariant `sum(distributed amounts) === full_amount` should be asserted/tested for every set of `earned_headers_commission_recipients`.

### Proof of Concept
1. Author a unit `U` with two authors `A` and `B` (or a single author with an explicit `earned_headers_commission_recipients` override) declaring `earned_headers_commission_recipients = [{address: A, earned_headers_commission_share: 1}, {address: B, earned_headers_commission_share: 99}]` — this passes `validateHeadersCommissionRecipients` since the shares sum to 100.
2. Get `U` selected as the winning child of some parent unit `P` whose `headers_commission` is, e.g., 150 bytes (any parent unit with a matching size works; an attacker can also post many parents/children to guarantee hitting a favorable `headers_commission` value).
3. When `calcHeadersCommissions()` runs for that parent's MC index, it computes:
   - `A`'s amount: `Math.round(150 * 1 / 100) = 2`
   - `B`'s amount: `Math.round(150 * 99 / 100) = 149`
   - Total inserted into `headers_commission_contributions`/`headers_commission_outputs`: `151`, i.e., 1 extra byte fabricated versus the actual `150`-byte commission pool.
4. `A` and `B` can later spend these balances via `headers_commission`-type inputs (validated in `validation.js`), realizing the extra byte as real, unauthorized supply. Repeating this pattern across many won units accumulates inflation over time.

function validateHeadersCommissionRecipients(objUnit, cb){
	if (objUnit.authors.length > 1 && typeof objUnit.earned_headers_commission_recipients !== "object")
		return cb("must specify earned_headers_commission_recipients when more than 1 author");
	if ("earned_headers_commission_recipients" in objUnit){
		if (!isNonemptyArray(objUnit.earned_headers_commission_recipients))
			return cb("empty earned_headers_commission_recipients array");
		var total_earned_headers_commission_share = 0;
		var prev_address = "";
		for (var i=0; i<objUnit.earned_headers_commission_recipients.length; i++){
			var recipient = objUnit.earned_headers_commission_recipients[i];
			if (!isPositiveInteger(recipient.earned_headers_commission_share))
				return cb("earned_headers_commission_share must be positive integer");
			if (hasFieldsExcept(recipient, ["address", "earned_headers_commission_share"]))
				return cb("unknown fields in recipient");
			if (!isValidAddress(recipient.address))
				return cb("invalid recipient address checksum");
			if (recipient.address <= prev_address)
				return cb("recipient list must be sorted by address");
			total_earned_headers_commission_share += recipient.earned_headers_commission_share;
			prev_address = recipient.address;
		}
		if (total_earned_headers_commission_share !== 100)
			return cb("sum of earned_headers_commission_share is not 100");
	}
