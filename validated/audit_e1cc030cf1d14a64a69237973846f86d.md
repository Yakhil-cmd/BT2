This is a highly significant finding: the `StatusHandler` doesn't even scope by repository at all — it matches `Commit.where(sha: params.sha)` globally across every stack in the Shipit instance. Combined with the org/repo binding gap in signature verification, this confirms the vulnerability.

### Title
Cross-Organization Signature Confusion Allows Forged Push/Status Webhooks to Trigger Unauthorized Syncs and CI-Status/Deploy Manipulation on Repositories the Attacker Does Not Control - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to validate an inbound webhook HMAC against using `repository.owner.login` (or `organization.login`) taken from the **unverified** JSON body, then verifies the raw payload against that secret. However, once verification passes, the event handlers (`PushHandler`, `Handler#repository_name`, `StatusHandler`) act on a *different* field of that same attacker-controlled payload: `repository.full_name` for push/pull-request handlers, or, worse, no repository scoping at all for `StatusHandler`, which matches purely by commit `sha`. There is no requirement that the org whose secret validated the signature is the same org/repo the handlers subsequently mutate.

### Finding Description
- `verify_signature` picks the signing secret via `repository_owner`, computed only from `params.dig('repository','owner','login')`: [1](#0-0) [2](#0-1) 
- Shipit explicitly supports hosting **multiple GitHub organizations** in one instance, each with its own `webhook_secret`, as documented and exercised in tests: [3](#0-2) [4](#0-3) 
- Once the signature is verified for *whatever organization the attacker names in the body*, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` dispatches the same raw, attacker-controlled `params` to handlers: [5](#0-4) 
- `Handler#repository_name` (used by `PushHandler`, `PullRequest::LabeledHandler`, `PullRequest::ClosedHandler`, etc.) resolves the target repository from `repository.full_name` — a field never checked against `repository.owner.login`: [6](#0-5) 
- `PushHandler` uses this repository lookup to enqueue `GithubSyncJob` for every matching, non-archived stack on the named branch: [7](#0-6) 
- `StatusHandler` is even less scoped: it doesn't consult `repository` at all, and updates the CI status of **any** commit in the entire Shipit database sharing the given `sha`: [8](#0-7) 
- A `Status` creation on a commit can flip a commit's CI state and trigger continuous delivery / merge-queue processing (`ProcessMergeRequestsJob`) and deploy-gating logic: [9](#0-8) [10](#0-9) 

**Broken binding:** *organization authenticated* (`repository.owner.login`, used to select the `webhook_secret`) `≠` *organization/repository written* (`repository.full_name` for push handlers, or no scoping at all for status handlers).

### Impact Explanation
In a multi-organization Shipit deployment (a documented, first-class configuration), any party who legitimately controls a GitHub App / webhook secret for **one** onboarded organization (Org A) can craft an arbitrary JSON body, set `repository.owner.login = "OrgA"` to pass signature verification with the secret they know, but set `repository.full_name` (or simply reuse a known `sha`, for the `status` event) to target a stack belonging to a **different, unrelated organization (Org B)** hosted on the same Shipit instance. This lets the attacker:
- Force `GithubSyncJob` execution and CI-gated merge/deploy processing (`ProcessMergeRequestsJob`) against Org B's stacks, without any relationship to Org B — a cross-repository/cross-organization write and a path to an unauthorized merge or deploy trigger.
- Forge/replicate arbitrary commit `state`/`context`/`description` CI statuses onto any commit `sha` across the entire instance via `StatusHandler`, since it isn't scoped to a repository at all, which can flip a commit into `success` and trigger the merge queue and continuous deployment for stacks the attacker has no relation to.

This matches the accepted High-severity class: escalation into cross-repository writes / an unauthorized deploy or merge, achieved purely by exploiting a mismatch between the field used to authenticate the webhook and the field(s) used to select what gets mutated.

### Likelihood Explanation
Requires only that the attacker be a legitimate webhook-secret holder for *any one* organization configured on a multi-org Shipit instance (a normal, documented deployment topology) — no privileged Shipit account, GitHub App private key, or `ApiClient` token is needed. The `status` event vector requires no organization/repo match at all, only knowledge of a target commit `sha`, which is often public (visible in PRs, CI logs, GitHub UI).

### Recommendation
In `WebhooksController#verify_signature`, and in every `Handlers::Handler` subclass, always resolve/compare `repository.owner.login` (or `organization.login`) against `repository.full_name`'s owner segment, and reject the webhook if the parties diverge or the resulting stack's configured organization doesn't match the organization whose secret validated the signature. For `StatusHandler`, scope the `Commit.where(sha:)` lookup to the repository/stack in the request payload rather than matching globally by SHA.

### Proof of Concept
1. Configure Shipit with two organizations in `config/secrets.yml`: `OrgA` (attacker-controlled, webhook secret known to attacker) and `OrgB` (victim, unrelated), per the documented multi-org schema.
2. Attacker crafts a `push` (or `status`) webhook JSON body with `repository.owner.login = "OrgA"` but `repository.full_name = "OrgB/victim-repo"` (for `status`, just set `sha` to a known commit belonging to an `OrgB` stack).
3. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(OrgA_webhook_secret, raw_body)` and POSTs to `/webhooks`.
4. `verify_signature` calls `Shipit.github(organization: "OrgA")` and successfully verifies the signature using OrgA's secret.
5. `Shipit::Webhooks.for_event('push').each { |h| h.call(params) }` runs `PushHandler`, which resolves `Repository.from_github_repo_name("OrgB/victim-repo")` and enqueues `GithubSyncJob` for OrgB's stack — or, for the `status` event, `StatusHandler` creates a forged `success` status on OrgB's commit, potentially triggering `ProcessMergeRequestsJob` / continuous deployment — despite the attacker having no relationship to OrgB.
