### Title
Webhook signature verification org can diverge from the org used to resolve the target stack, allowing cross-repository `RefreshCheckRunsJob` scheduling - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/handler.rb], [File: app/models/shipit/webhooks/handlers/check_suite_handler.rb])

### Summary
`WebhooksController#verify_signature` derives the signing organization from `params.dig('repository', 'owner', 'login')`, while `Handler#stacks` (used by `CheckSuiteHandler#process`) resolves the target repository/stack from the independent field `payload.dig('repository', 'full_name')`. Because the entire JSON body is attacker-controlled, these two fields can be made inconsistent, letting an attacker who owns repository A sign a webhook with A's secret while pointing `repository.full_name` at repository B, causing Shipit to schedule `RefreshCheckRunsJob` for B's commit.

### Finding Description
The broken binding: `repository_owner` (`params.dig('repository','owner','login')`, used in `Shipit.github(organization: repository_owner)` for signature verification) should equal the organization embedded in `repository.full_name` (used by `Repository.from_github_repo_name` in `Handler#stacks`) — but nothing enforces this equality.

Code path:
- `WebhooksController#verify_signature` [1](#0-0)  computes `repository_owner` from `params.dig('repository', 'owner', 'login')` [2](#0-1)  and verifies the signature against `Shipit.github(organization: repository_owner)`.
- `CheckSuiteHandler#process` calls `stacks.where(branch: ...)` [3](#0-2) , and `Handler#stacks`/`#repository_name` resolve the repository via `payload.dig('repository', 'full_name')` [4](#0-3) , independent from `repository.owner.login`.

Since an attacker fully controls the raw JSON body (this is an unauthenticated `POST /webhooks` endpoint prior to signature check), they can submit:
```json
{
  "repository": { "full_name": "B/repo", "owner": { "login": "A" } },
  "check_suite": { "head_branch": "<B's real branch>", "head_sha": "<B's real commit sha>" }
}
```
signed with `A`'s webhook secret (which the attacker legitimately knows, since A is their own GitHub org/repo). `verify_signature` calls `Shipit.github(organization: 'A')` and succeeds because the signature was computed over the exact raw body using A's real secret. Once past that gate, `CheckSuiteHandler` uses `full_name` = `"B/repo"` to resolve `Repository.from_github_repo_name`, matches B's stack/commit by branch/sha, and calls `commit.schedule_refresh_check_runs!` [5](#0-4) , enqueuing `RefreshCheckRunsJob.perform_later(commit_id: id)` for B's commit.

`RefreshCheckRunsJob#perform` then calls `Commit#refresh_check_runs!`, which uses `stack.github_api` (i.e., `Shipit.github(organization: 'B')`, B's legitimate credentials) to fetch and persist check runs for B's commit [6](#0-5) [7](#0-6) . No credentials leak, but the *decision* to run cross-org GitHub API calls and mutate B's check-run records was triggered entirely by attacker-forged input verified only against A's secret — B never authorized or verified this webhook.

Existing guards do not prevent this: `verify_signature` never cross-checks `owner.login` against `full_name`; `ExplicitParameters` schema on `CheckSuiteHandler` only requires `check_suite.head_sha`/`head_branch` are strings, not that `repository.full_name` and `repository.owner.login` agree; `Repository.from_github_repo_name` performs a straightforward `find_by(owner:, name:)` lookup with no ownership cross-check.

### Impact Explanation
An unprivileged attacker who controls any GitHub org/repo (A) with a registered Shipit webhook secret can force Shipit to schedule and execute `RefreshCheckRunsJob` against any other tracked repository (B) whose branch/commit sha they can guess or observe publicly (branch names and commit shas are typically public). This is a cross-tenant write: check-run records are created/updated in Shipit's database for B's commit without B's webhook ever firing, and B's GitHub API rate limit/credentials are consumed on attacker's command. This matches the "payload for one repository mutating another's stack/commit" Critical category, since the forged provenance from A drives real data writes and GitHub API usage scoped to B. It is repeatable against any repository/branch/commit combination already tracked by Shipit.

### Likelihood Explanation
Preconditions are modest: the attacker needs (a) their own repository A registered with Shipit with a known webhook secret (trivial — they own it), and (b) knowledge of a real branch name and commit sha on a target stack B that Shipit tracks (both are typically public GitHub information). No Shipit session, API token, or team membership is required. The attack is a single crafted HTTP POST to `/webhooks` with a valid `X-Hub-Signature` computed using A's own secret — well within reach of an "unprivileged internet user who can send HTTP requests to the Shipit host."

### Recommendation
In `WebhooksController#verify_signature`, verify the signature using the same organization/repository that will actually be processed, and/or have `Handler#stacks` cross-check that the resolved repository's owner matches the `repository.owner.login` (or the org used for signature verification) before scheduling any job. Concretely: derive `repository_owner` from `repository.full_name`'s owner segment (not the separate `owner.login` field), or add an explicit assertion in `Handler` that `payload.dig('repository','owner','login')` equals the owner segment of `payload.dig('repository','full_name')`, rejecting the webhook otherwise.

### Proof of Concept
Add to `test/controllers/webhooks_controller_test.rb`:
```ruby
test ":check_suite with mismatched owner/full_name still enqueues RefreshCheckRunsJob for the other repo's commit" do
  # Attacker owns org "attacker-org" and knows its webhook secret.
  # Target stack "shopify/shipit-engine" exists with a commit matching sha/branch.
  commit = shipit_commits(:first) # belongs to shopify/shipit-engine stack

  body = {
    repository: {
      full_name: "shopify/shipit-engine", # points at victim's repo
      owner: { login: "attacker-org" }    # signature checked against attacker's org
    },
    check_suite: {
      head_branch: commit.stack.branch,
      head_sha: commit.sha
    }
  }.to_json

  request.headers['X-Github-Event'] = 'check_suite'
  Shipit.github(organization: 'attacker-org').expects(:verify_webhook_signature).returns(true)

  assert_enqueued_with(job: RefreshCheckRunsJob, args: [{ commit_id: commit.id }]) do
    post :create, body:, as: :json
    assert_response :ok
  end
end
```
This demonstrates that signing with `attacker-org`'s credentials (`repository.owner.login`) results in `RefreshCheckRunsJob` being enqueued for a commit belonging to the unrelated `shopify/shipit-engine` stack (`repository.full_name`), proving the divergence between the signature-verifying org and the org whose stack/commit is acted upon.
