## Analysis

I examined the areas of ocore reachable by an unprivileged unit poster, AA trigger sender, asset issuer, private-payment counterparty, and paired device, looking for an "excessive allocation" analog to the OpenCanary MongoDB DoS (attacker supplies an oversized/unbounded structure that the victim eagerly processes/allocates for).

Most user-controlled arrays and strings in ocore are explicitly length-capped: `MAX_MESSAGES_PER_UNIT`, `MAX_SPEND_PROOFS_PER_MESSAGE`, `MAX_AA_STRING_LENGTH`, the `arrItemExprs.length > 100` array-literal cap and the `count <= 100` cap on `foreach`/`map`/`filter`/`reduce` in `formula/evaluation.js` and `formula/validation.js` [1](#0-0) [2](#0-1) , and structural nesting/size checks such as `isTooDeeplyNestedOrHasTooManyNodes` applied to units and device messages [3](#0-2) [4](#0-3) .

However, the private-payment chain handling path lacks any such bound. `handlePrivatePaymentChains` in `wallet.js`, reachable from a paired/correspondent device sending a `private_payments` message, only validates that `body.chains` is a non-empty array and that each element has the expected shape — it never caps the number of chains, the number of elements per chain, or performs any total-size check before doing expensive work (hashing every element, `JSON.stringify`-based cache-key computation, DB inserts) on the whole structure: [5](#0-4) 

Each chain is then handed to `network.handleOnlinePrivatePayment`, which likewise only checks `isNonemptyArray(arrPrivateElements)` before it computes hashes and calls `JSON.stringify(arrPrivateElements)` to persist it in `unhandled_private_payments`: [6](#0-5) 

Because the enclosing device-message envelope check (`isTooDeeplyNestedOrHasTooManyNodes(objDeviceMessage, 5, 100)`) is applied only to the *outer*, still-encrypted message object (signature/pubkey/`encrypted_package`), it does not constrain the size or shape of the *decrypted* JSON payload once `device.decryptPackage` succeeds [4](#0-3) [7](#0-6) . A paired device (or hub relaying on its behalf) can therefore deliver a `private_payments` body whose `chains` array contains an arbitrarily large number of chains/elements, each of which is individually well-formed enough to pass the shallow shape check in `handlePrivatePaymentChains`, but whose aggregate size triggers unbounded hashing, `JSON.stringify`, and DB work on the victim's wallet — an excessive-allocation/CPU-exhaustion DoS, analogous to the OpenCanary MongoDB module bug, but I was not able to fully verify whether an underlying WebSocket `maxPayload`/message-size cap in `network.js` indirectly bounds this before reaching `wallet.js`, since I ran out of iterations to inspect the WS server setup code.

### Title
Denial-of-Service via unbounded private-payment chain array in wallet message handling - (File: wallet.js)

### Summary
`handlePrivatePaymentChains` (wallet.js) and `handleOnlinePrivatePayment` (network.js) accept a `private_payments` device message containing an arbitrary-length `chains` array (and arbitrary-length chain-element arrays) from any paired/correspondent device, with no upper bound on the number of chains or elements, unlike comparable structures elsewhere in ocore (units, AA arrays/loops, spend-proof lists) which all enforce explicit size caps.

### Finding Description
`handlePrivatePaymentChains` validates only that `arrChains` is a non-empty array and that each chain element has the right shape (`isNonemptyObject`, required string/array fields) — it never checks `arrChains.length` or the length of each chain `c` [8](#0-7) . It then computes `objectHash.getBase64Hash(arrChains)` over the whole attacker-controlled structure for a cache key [9](#0-8) , and iterates every chain through `network.handleOnlinePrivatePayment`, which itself does no length validation on `arrPrivateElements` beyond non-emptiness [10](#0-9) , and persists the entire chain via `JSON.stringify(arrPrivateElements)` into `unhandled_private_payments` [11](#0-10) .

By contrast, every other user-reachable structure that could grow unbounded in ocore is explicitly capped (unit message count, spend-proof count, AA array-literal length, `foreach`/`map`/`filter`/`reduce` iteration counts, AA string/state-var lengths) [12](#0-11) [2](#0-1) [13](#0-12) . The private-payment-chain path is a gap in this pattern: the only structural guard applied before decryption, `isTooDeeplyNestedOrHasTooManyNodes(objDeviceMessage, 5, 100)`, is evaluated on the still-encrypted envelope and does not constrain the size of the plaintext JSON once decrypted [4](#0-3) [7](#0-6) .

### Impact Explanation
A malicious paired/correspondent device (an explicitly in-scope actor: "private-payment counterparty" / "paired device") can send a single `private_payments` message with a very large `chains` array (or very large chains), causing the victim wallet to perform unbounded hashing, `JSON.stringify` serialization, and repeated DB inserts/queries per element. This can exhaust CPU and memory on the receiving node, denying it the ability to process legitimate private payments or other wallet operations — a concrete availability impact matching "network unable to confirm/process" style DoS harms.

### Likelihood Explanation
Likelihood is moderate-to-high in principle: no privileged access is required, only an established device pairing (which private-payment counterparties routinely have), and no cap exists on chain/array sizes at this layer. However, I could not confirm within the available searches whether an outer WebSocket `maxPayload` limit in `network.js` bounds the overall device-message size before it reaches this code, which would reduce (but likely not eliminate, given cheap small elements can still be packed densely) the practical severity.

### Recommendation
Add explicit upper bounds (analogous to `MAX_SPEND_PROOFS_PER_MESSAGE` / `MAX_MESSAGES_PER_UNIT`) on `body.chains.length` and on the length of each chain element array in `handlePrivatePaymentChains` (wallet.js) and in `handleOnlinePrivatePayment` (network.js), rejecting oversized payloads before any hashing, stringification, or DB work is performed.

### Proof of Concept
Not executed — this is a static code-review finding. Conceptually: an attacker who is a paired device sends a `private_payments` justsaying/message whose `body.chains` array contains a very large number of syntactically-valid minimal chain elements (or long individual chains); `handlePrivatePaymentChains` and `handleOnlinePrivatePayment` process the entire structure without any length cap, consuming CPU/memory disproportionate to the message's transport size.
