### Title
Caller-selected flash receiver can execute unintended transfers from the initiator's wallet - (File: contracts/controller/src/strategies/flash_position.rs)

### Summary

`flash_position` authorizes the initiator with `caller.require_auth()`, then invokes a caller-selected Wasm receiver without constraining what that receiver does with the initiator’s authorization context. A malicious receiver can call `token.transfer(caller, attacker, amount)`. Simulation records that transfer as a nested authorization under the caller’s `flash_position` authorization, and enforcement accepts it if the caller signs the generated authorization tree. The controller validates only the resulting collateral, refund, debt, and account-risk state; it does not verify that the callback confined its token movements to the declared flash-position operation. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description

The entrypoint accepts an arbitrary `receiver` address and requires only that it is a deployed Wasm contract different from the controller and pool. [4](#0-3)  After authenticating `caller`, the controller mints debt, forwards the measured debt tokens to that receiver, and invokes `receiver.execute_flash_position(..., initiator = caller, ..., data)`. [5](#0-4) [2](#0-1) [3](#0-2) 

The callback is third-party code running below the caller-authorized controller invocation. It can make an unrelated token transfer from `initiator` to an attacker. The controller’s post-callback checks measure only declared collateral deltas and listed refund assets, then enforce that the position remains open and solvent; they do not account for unrelated token movements by the callback. [6](#0-5) [7](#0-6) [8](#0-7) 

The repository’s authorization test demonstrates the relevant host behavior: code reached under a caller-authorized root invocation can place a `token.transfer(victim, attacker, amount)` child in the victim’s recorded authorization tree, and that transfer executes when the victim signs the tree. [9](#0-8) [10](#0-9) 

### Impact Explanation

A malicious receiver can steal arbitrary tokens from the initiating account’s wallet. This theft is independent of the borrowed amount and the declared collateral or refund assets, because the receiver can invoke a token contract directly and name the authenticated `initiator` as `from`. [11](#0-10) 

The loss can exceed every value visible in the `flash_position` arguments. The post-callback collateral minimums, refund list, solvency checks, and `FlashPositionClosed` checks do not place a bound on unrelated wallet-token transfers performed by the callback. [6](#0-5) [12](#0-11) 

### Likelihood Explanation

The attack requires the victim to invoke `flash_position` with an attacker-controlled `receiver` and sign the authorization tree produced by simulation. That is comparable to the reported proxy pattern: the contract being invoked by the victim supplies the operation that subsequently uses the victim’s authority for an unrelated transfer. [3](#0-2) 

The receiver must still satisfy the protocol’s declared collateral minimums and leave a solvent open position to keep the transaction from reverting. Those requirements constrain the flash-position accounting but do not prevent a separate wallet transfer, so the receiver can return enough declared collateral while also stealing another token. [6](#0-5) 

Severity is Medium: it enables theft of user wallet funds, but successful execution depends on tricking the user into selecting the malicious receiver and signing the expanded authorization tree.

### Recommendation

Do not expose a raw caller-authenticated root invocation to arbitrary callback code. At minimum, use a dedicated operation authorization scheme that binds the receiver, account, debt asset, amount, collateral expectations, and expiry to an initiator-approved payload, and have the receiver prove that payload before it can execute inside the caller’s authorization context.

Clients should also treat any additional child authorization as fatal: an honest `flash_position` callback should require no unrelated token transfer from the initiator. Prefer a callback architecture in which the initiator is a contract with explicit invoker-contract authorization or pre-commits exactly the operations the receiver may perform.

### Proof of Concept

1. Alice owns lending account `A` and holds token `T`, which need not be listed by the protocol.
2. Eve deploys `RogueReceiver` with stored values `(victim = Alice, token = T, recipient = Eve, amount = Alice's T balance)`.
3. Eve induces Alice to call:

   `controller.flash_position(
     caller = Alice,
     account_id = A,
     spoke_id = Alice's spoke,
     mode = PositionMode::Multiply,
     debt = listed_debt_asset,
     amount = borrowed_amount,
     receiver = RogueReceiver,
     data = attack_payload,
     collaterals = [(listed_collateral, minimum)],
     refund_assets = []
   )`

   The controller authenticates Alice, validates `RogueReceiver` only as a non-controller/non-pool Wasm contract, mints and forwards the debt tokens, and invokes `execute_flash_position`. [13](#0-12) [14](#0-13) 
4. Inside `execute_flash_position`, `RogueReceiver` uses its `initiator` argument as Alice and executes `T.transfer(Alice, Eve, amount)`, while also transferring enough declared collateral to the controller. [3](#0-2) 
5. Simulation records the rogue `T.transfer` as a child invocation under Alice’s `flash_position` authorization. If Alice signs that generated tree, the transfer executes even though it is unrelated to the flash-position parameters. [9](#0-8) 
6. The controller sees the required collateral delta, leaves Alice’s account solvent with debt and supply, and returns success. Alice’s `T` balance is transferred to Eve; no post-callback check detects or refunds that unrelated transfer. [6](#0-5) [15](#0-14)

fn mint_and_forward(
    env: &Env,
    account: &mut Account,
    debt: &HubAssetKey,
    amount: i128,
    receiver: &Address,
    cache: &mut Context,
) -> i128 {
    let controller = env.current_contract_address();
    let before = token::Client::new(env, &debt.asset).balance(&controller);

        amount,
        false,
        PositionAction::FlashPos,

    assert_with_error!(env, measured > 0, GenericError::AmountMustBePositive);

        env,
        &debt.asset,
        &controller,
        receiver,
        measured,
        GenericError::AmountMustBePositive,
    );
    assert_with_error!(env, forwarded > 0, GenericError::AmountMustBePositive);

fn collect_collateral_deposits(
    env: &Env,
    controller: &Address,
    collaterals: &Vec<(HubAssetKey, i128)>,
    before: &Map<Address, i128>,
) -> Vec<(HubAssetKey, i128)> {
    let mut deposits: Vec<(HubAssetKey, i128)> = Vec::new(env);
    for (hub_asset, min_amount) in collaterals.iter() {
        let baseline = before
            .get(hub_asset.asset.clone())
            .unwrap_or_else(|| panic_with_error!(env, GenericError::InternalError));
        let delta = balance_delta_since(env, &hub_asset.asset, controller, baseline);
        assert_with_error!(
            env,
            delta >= min_amount,
            StrategyError::CollateralMinimumNotMet
        );
        if delta > 0 {
            deposits.push_back((hub_asset, delta));
        }
    }
    assert_with_error!(
        env,
        !deposits.is_empty(),
        StrategyError::CollateralMinimumNotMet
    );
    deposits
