### Title
Unvalidated router payload lets attacker-named pool contracts pull the signer's wallet tokens via the `swap_collateral`/`swap_debt` auth tree — (File: contracts/controller/src/strategies/swap.rs)

### Summary
The TAR traversal bug class — attacker-controlled names written outside the intended scope — maps onto the controller's strategy router path: the caller supplies an opaque `route`/`swap` byte payload naming arbitrary pool and token contracts, and the controller forwards it to the configured swap aggregator with no allowlist or decoding. Like `tarfile.extract()` writing `../` members outside the destination, code inside a route-named contract executes under the caller's authorization and can invoke `token.transfer(caller, attacker, amount)` on tokens completely unrelated to the swap, draining the signer's wallet.

### Finding Description
`swap_tokens` in `contracts/controller/src/strategies/swap.rs:34-38` performs exactly one scoped authorization — `authorize_transfer_as_current(env, token_in, controller, router_addr, amount_in)` — and then calls `router.execute_strategy(&controller, &amount_in, swap)` with the raw, undecoded `swap` payload inside `with_flash_guard`. The only post-conditions enforced are measured balances on `token_in`/`token_out` (`RouterOverspend`, `NoSwapOutput`, lines 41-54); nothing constrains which contracts the route touches or what those contracts do under auth.

The project's own threat model confirms the router "keeps no allowlist" of the pool/token addresses its payload names, so "a route can put third-party code on the call stack below the caller's authorization," and a `transfer` made by that code "is recorded by an honest simulation as a child of the caller's authorization entry, and it executes if the caller signs that tree" (`docs/explanation/threat-model.md:154-165`). The proof test `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs:195-227` demonstrates it end-to-end: a route through `RogueHopPool` whose `swap()` calls `token::Client::transfer(alice, attacker, WALLET_BALANCE)` on an unlisted wallet token succeeds during `swap_collateral`, and the recorded auth tree attaches the theft transfer as a child of Alice's `swap_collateral` entry; signing that tree moves her entire 77,770-token wallet balance while the swap itself settles fairly.

### Impact Explanation
Theft of user funds: every token in the victim's wallet for which the attacker names a contract in the route can be transferred out, bounded only by what the victim signs. The exposure applies to all six strategy entrypoints that forward a route (`swap_collateral`, `swap_debt`, `repay_debt_with_collateral`, `multiply`, `flash_position` callback flows, `migrate_from_blend` return path), and — per the threat model — to direct `execute_strategy` router users. The controller's measured-output and final-health gates do not bound the loss, exactly as the traversal's extraction-directory checks cannot bound a write outside it.

### Likelihood Explanation
High conditional likelihood: exploitation requires the victim to sign a route containing a malicious hop (phishing, malicious front-end, or a compromised quote path producing the payload). Because simulation silently folds the rogue `transfer` into the signable tree and the route XDR is opaque to the controller, a wallet/UI that does not decode and diff the auth tree will present it as a normal swap signature. Severity is reduced only by the signing prerequisite, not by any on-chain control.

### Recommendation
- Decode/validate the route server-side and UI-side: refuse any authorization tree whose `swap_*` root has children other than the single expected `token_in` pull and the controller's transfer sub-invocation (the threat model prescribes this client check).
- Prefer a protocol-level fix: have the controller pass a structured, enumerated route (known venue + allowlisted pool addresses) instead of opaque XDR, or require the aggregator to restrict hop calls to a governance-managed venue/pool registry, so attacker-named contracts can never sit under the caller's auth tree.

### Proof of Concept
`tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs` already proves it: `Scene::route_through_pool_stealing` registers `RogueHopPool` with a `(victim, wallet_token, attacker, amount)` plan; `simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry` shows `swap_collateral` draining Alice's `WALLET_BALANCE` of an unrelated token to the attacker, and `enforced_auth_moves_the_wallet_token_only_when_the_signed_tree_lists_the_rogue_transfer` confirms the theft executes whenever the signed tree includes the recorded child.
