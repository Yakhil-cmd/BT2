### Title
Uncaught `throw` in AA-trigger dry-run / trigger construction crashes full nodes on an attacker-crafted payment to an AA address - (File: `network.js`, `aa_composer.js`)

### Summary
The external report describes a Rust `ostree` bug where an unhandled `panic!`/`eprintln!`-based abort in `print_panic` (repo_checkout_filter.rs) lets an attacker crash a process that should only ever return an error. The equivalent bug class in `ocore` is the use of `throw Error(...)` inside asynchronous callback chains that run in response to a freshly-posted, attacker-controlled unit, where the throw is not caught by any `try/catch` and is not awaited by the caller, so it becomes either an unhandled exception or an unhandled promise rejection and kills the Node.js process.

### Finding Description
When a new joint is validated successfully (`ifOk`), and `conf.bDryRunNewTriggers` is enabled, the node builds a synthetic AA trigger from the just-posted unit and dry-runs it *before* saving, explicitly so that "if it would crash, let it crash now, not when we execute the trigger for real": [1](#0-0) 

`ifOk` is declared `async`, and is invoked by `validation.validate()` as a plain (non-awaited) callback: [2](#0-1) 

Inside this `async` `ifOk`, `aa_composer.getTrigger(objJoint.unit, address)` is called to build the trigger object from the posted unit's payment messages. `getTrigger` throws a plain `Error` whenever it cannot find any output whose recipient matches the AA address being triggered: [3](#0-2) 

Because `ifOk` is an `async` function and its caller in `validation.js` never attaches a `.catch()`/awaits it, any `throw` inside `getTrigger` (or inside `aa_composer.dryRunPrimaryAATrigger`, which recursively calls into `formula/evaluation.js` and `aa_composer.handleTrigger`, both of which contain numerous unguarded `throw Error(...)` statements reachable from attacker-supplied trigger data/definitions, e.g. [4](#0-3)  and [5](#0-4) ) turns into an unhandled promise rejection. Node's default `unhandledRejection` behavior (relied upon throughout `ocore`, e.g. the explicit re-`throw` pattern used everywhere else in the codebase to intentionally "crash the process to avoid ending up in an inconsistent state", as seen in the `uncaughtException` handler) is to terminate the process: [6](#0-5) 

This mirrors the `ostree` bug class exactly: a code path meant only to *reject/bounce* malformed input instead unconditionally aborts the whole process, and it is reachable by any unprivileged peer simply by broadcasting/posting a single unit.

### Impact Explanation
Any full node running with `conf.bDryRunNewTriggers` enabled can be crashed remotely by an unprivileged unit poster who sends a payment referencing an existing AA address with a message/output layout that makes `getTrigger` (or the deeper AA trigger/formula evaluation it feeds into) throw instead of calling back with an error. Because the crash happens inside the "let it crash now" pre-save dry run — i.e., before the unit is even written to the DB — every node that receives and validates this single unit independently hits the same throw and independently crashes, which is a genuine "network unable to confirm new units" condition rather than a resource-only DoS: repeated broadcasting of the same crafted unit can be used to keep taking full nodes offline as they restart and re-validate the backlog.

### Likelihood Explanation
Likelihood depends on whether `conf.bDryRunNewTriggers` is enabled by default on production/relay nodes — this could not be confirmed from `conf.js` (no default assignment was found in the indexed content, only its two usages in `network.js`), so it is uncertain whether this path is exercised by default or only when operators opt in. If enabled, the trigger is straightforward to construct because it only requires posting a normal payment unit to a live AA address with a message list engineered to reach one of the many un-guarded `throw` statements in `getTrigger`/`handleTrigger`/`formula/evaluation.js`, all of which are fed directly from unit content or AA-trigger data supplied by the poster.

### Recommendation
- Wrap the body of the `async ifOk` handler in `network.js` (lines 1258-1282) in a `try { ... } catch (e) { ... }` that logs and safely aborts the dry run instead of letting the exception escape, and/or explicitly `.catch()` the promise returned by the `async` `ifOk` where it is invoked in `validation.js`.
- Audit `aa_composer.getTrigger`, `aa_composer.handleTrigger`, and `formula/evaluation.js` for `throw Error(...)` statements that are reachable from attacker-controlled unit/trigger content (as opposed to genuine internal invariant violations), and convert those specifically reachable from external input into callback-style errors (`cb(err)`/`setFatalError`) rather than exceptions.
- Add a global `process.on('unhandledRejection', ...)` policy (or ensure existing ones are exhaustive) so that at minimum the failure mode is diagnosable and, ideally, does not require a full process crash for input-validation-class failures.

### Proof of Concept
Conceptual PoC (exact malformed payload was not verified end-to-end due to index limitations):
1. Deploy or identify a live AA address `A`.
2. Craft and broadcast a unit `U` whose `messages` array contains a `payment` message paying to some address, and is otherwise shaped so that when `network.js`'s `ifOk` filters `objJoint.unit.messages` for `app === 'payment'` and collects `outputs.map(o => o.address)`, address `A` is included in `outputAddresses`, but by the time `aa_composer.getTrigger(objJoint.unit, A)` is called, no matching output resolves into `trigger.outputs` for `A` and every key produced is empty (e.g., a race window / edge case in output filtering, or by using multiple payment messages/assets so the ordering assumption in the SQL `IN (?)` match versus the per-message filter in `getTrigger` diverges).
3. `getTrigger` throws `Error("no outputs to " + A)` inside the `async ifOk`, which is unhandled by the caller, producing an unhandled promise rejection and crashing the node process per Node's default unhandled-rejection termination behavior.

Because the exact combination of message/output shapes needed to make `outputAddresses` (network.js) and `trigger.outputs` (aa_composer.js) disagree could not be fully traced through the indexed snippets, this should be validated directly against a running node build (start a Devin session with repo access) before treating the PoC as proven; the architectural hazard — an `async` callback with unguarded `throw` invoked without `await`/`catch` on the "new unit received" hot path — is confirmed by the cited code.

function getTrigger(objUnit, receiving_address) {
	var trigger = { address: objUnit.authors[0].address, unit: objUnit.unit, outputs: {} };
	if ("max_aa_responses" in objUnit)
		trigger.max_aa_responses = objUnit.max_aa_responses;
	objUnit.messages.forEach(function (message) {
		if (message.app === 'data' && !trigger.data) // use the first data message, ignore the subsequent ones
			trigger.data = message.payload;
		else if (message.app === 'payment' && message.payload) {
			var payload = message.payload;
			var asset = payload.asset || 'base';
			payload.outputs.forEach(function (output) {
				if (output.address === receiving_address) {
					if (!trigger.outputs[asset])
						trigger.outputs[asset] = 0;
					trigger.outputs[asset] += output.amount; // in case there are several outputs
				}
			});
		}
	});
	if (Object.keys(trigger.outputs).length === 0)
		throw Error("no outputs to " + receiving_address);
	return trigger;
}
