### Title
Webhook Organization Used for Signature Verification Is Decoupled From the Repository Acted Upon - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/webhook secret to validate a request against using `repository.owner.login` (or `organization.login`) read straight out of the *unverified* JSON body, while the handlers that actually act on the payload (e.g. `PushHandler`) resolve the target `Stack`/`Repository` using a completely different field, `repository.full_name`, from that same unverified body. Nothing binds these two fields together, so the "organization whose secret authenticated the request" is not guaranteed to equal "the repository that gets written to."

### Finding Description
`verify_signature` picks the app/secret to check against based on a field taken from the raw, not-yet-verified payload: [1](#0-0) [2](#0-1) 

`Shipit::GithubApp#verify_webhook_signature` trivially returns `true` whenever no `webhook_secret` is configured for that organization — and per the setup docs, the webhook secret is explicitly optional per organization: [3](#0-2) [4](#0-3) 

Once the request is accepted, the actual event handlers (e.g. `PushHandler`) never re-check `repository.owner.login` — they resolve the target `Stack` purely from `repository.full_name`, again pulled from the same attacker-supplied JSON body: [5](#0-4) [6](#0-5) 

Binding broken (equality that should hold but does not): `organization used to select/pass signature verification == organization that owns the repository being written to`.

Before the attacker's request: only requests whose HMAC matches the secret of the organization named in `repository.owner.login` are supposed to be able to mutate stacks belonging to that organization's repositories.

After the attacker's request: because the org used for verification (`repository.owner.login`) and the repo used for the write (`repository.full_name`) are independent fields with no cross-validation, an attacker can name an organization with no `webhook_secret` configured (or one whose secret they hold) in `repository.owner.login`/`organization.login` — trivially or trivially-satisfiable passing `verify_signature` — while pointing `repository.full_name` at an entirely different, secret-protected organization's repository. The handler will then execute `stack.sync_github(...)`, membership changes, or status updates against that unrelated repository/stack without ever having proven knowledge of its secret.

### Impact Explanation
This lets an unprivileged network attacker trigger `GithubSyncJob` (forcing head SHA sync), fabricate commit `Status` entries, or manipulate team `Membership` records for a stack/repository they do not control, as long as any organization onboarded into the same Shipit instance has no webhook secret configured (which the documentation presents as an optional field, so it is a realistic misconfiguration). Because commit `Status` records and sync state directly influence whether `shipit.yml` deploy tasks run and what CI status stacks display, this can enable an unauthorized deploy trigger on a repository the attacker has no access to — matching the "unauthorized deploy" / "cross-repository writes" Critical-impact class.

### Likelihood Explanation
Likelihood depends on at least one onboarded GitHub organization in a multi-org (or default) Shipit deployment having a blank `webhook_secret`, which the setup guide explicitly documents as optional. No authentication, session, `ApiClient` token, or GitHub App credentials are needed by the attacker for the target repository — only knowledge of the target's `repository.full_name` and any onboarded org name lacking a secret (or an org whose secret the attacker legitimately holds for a different, unrelated repository).

### Recommendation
Bind the two fields together before dispatch: derive the organization used for both secret selection and target-repository resolution from a single, verified source (e.g., require `repository.full_name`'s owner segment to equal `repository.owner.login`, or resolve the target `Stack`'s organization first and verify the signature using that stack's own configured secret) rather than trusting two independent, unrelated fields of the same unverified body. Additionally, treat a missing `webhook_secret` as "reject all deliveries for this org" rather than "accept all deliveries," to remove the silent bypass in `verify_webhook_signature`.

### Proof of Concept
1. Configure Shipit with two organizations: `no-secret-org` (webhook_secret left blank per docs) and `victim-org` (has a Stack for `victim-org/victim-repo` with a real secret).
2. Attacker POSTs to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "ref": "refs/heads/master",
  "after": "deadbeef",
  "repository": {
    "owner": { "login": "no-secret-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. `repository_owner` resolves to `no-secret-org`; `Shipit.github(organization: 'no-secret-org').verify_webhook_signature` returns `true` immediately because no secret is configured for that org [7](#0-6) .
4. `PushHandler` resolves `stacks` via `Repository.from_github_repo_name('victim-org/victim-repo')` [5](#0-4) , and calls `stack.sync_github(expected_head_sha: 'deadbeef')` on the victim's stack — despite never having satisfied `victim-org`'s webhook secret.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
