### Title
Webhook trust binding lets attacker-controlled `repository.full_name` drive stack lookups while only `repository.owner.login` is checked against the signing organization - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/webhook secret to validate a request against using `params.dig('repository', 'owner', 'login')`, but every webhook `Handler` resolves the target `Repository`/`Stack` from a *different* payload field, `payload.dig('repository', 'full_name')`. Nothing enforces that these two attacker-supplied JSON fields refer to the same repository/organization.

### Finding Description
`repository_owner` is used purely to pick the `Shipit.github(organization: ...)` config for signature verification: [1](#0-0) [2](#0-1) 

Every concrete handler, however, looks up the stack/repository to act on using a completely separate field of the same untrusted body: [3](#0-2) 

This is the same class of bug as the royalty report: the code assumes two values that are *usually* correlated (an NFT's price used for the whole batch vs. its own weight; here, `repository.owner.login` vs `repository.full_name`) are interchangeable, and never actually checks that the field used for the trust decision (owner/signature) matches the field used for the effectful action (full_name → `Repository.from_github_repo_name` → `Stack`).

Combined with `GithubApp#verify_webhook_signature`: [4](#0-3) 

`return true unless webhook_secret` means that for any organization configured *without* a webhook secret (explicitly documented as optional in `docs/setup.md`), signature verification is a no-op — any request with `repository.owner.login` set to that organization's name is accepted regardless of body content, and the handler then acts on whatever `repository.full_name` is supplied, which can name a *different* organization/repository's `Stack` (e.g. `PushHandler` calls `stack.sync_github(expected_head_sha: ...)`).

### Impact Explanation
This breaks the binding: `organization that authenticated == repository that is written`. An unprivileged, unauthenticated caller who knows only that some onboarded organization in a multi-org Shipit deployment has no `webhook_secret` configured can forge webhook deliveries that are accepted as verified for that organization, yet whose `repository.full_name`/stack-affecting fields target any other stack tracked by the instance, triggering `GithubSyncJob`/`sync_github` (or other handler side effects such as `CheckSuiteJob`, `Status` creation, PR label/archival state changes) on repositories unrelated to the "authenticated" organization. This matches the High/Critical impact classes for this scan (unauthenticated manipulation of stack/task state via a credential the app never actually verified for the acted-upon repository).

### Likelihood Explanation
Requires that some organization configured on the Shipit instance has an unset `webhook_secret` (documented default/optional setting) — a realistic, self-inflicted but not attacker-controlled misconfiguration, not requiring possession of any secret, GitHub App key, or session. No repository write access or privileged account is needed by the attacker; they only need network access to the `/webhooks` endpoint and knowledge of a stack's real GitHub repo name.

### Recommendation
After signature verification succeeds, re-derive the acted-upon repository strictly from the same verified organization scope (e.g., assert `payload.dig('repository','full_name')` starts with `repository_owner + '/'`), or require `webhook_secret` to be mandatory for every configured organization so the "no secret configured" bypass path cannot exist.

### Proof of Concept
Conceptual (cannot be executed without a running instance/host access):
1. Configure two orgs in `config/secrets.yml`: `org-a` (no `webhook_secret`) and `org-b` (has a real stack, e.g. `org-b/real-repo`).
2. POST to `/webhooks` with header `X-Github-Event: push`, no `X-Hub-Signature`, and body:
```json
{"repository": {"owner": {"login": "org-a"}, "full_name": "org-b/real-repo"}, "ref": "refs/heads/master", "after": "<attacker-chosen-sha>"}
```
3. `verify_signature` resolves `Shipit.github(organization: "org-a")`, whose `verify_webhook_signature` returns `true` unconditionally (no secret configured) — request passes.
4. `PushHandler` resolves the stack via `full_name` = `org-b/real-repo` and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")`, affecting a stack that has nothing to do with `org-a`.

Note: I was unable to fully trace `Stack#sync_github`'s downstream effects within the remaining iterations (e.g., whether it merely triggers a resync or can influence deploy/merge state), so the exact severity ceiling (High vs. Critical) is not fully confirmed — this would need further review of `app/models/shipit/stack.rb`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
