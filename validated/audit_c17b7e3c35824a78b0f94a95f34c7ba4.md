### Title
Cross-repository status forgery via unscoped commit sha lookup in `StatusHandler#process` enables unauthorized merges - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` resolves the target `Commit` purely by `sha` across the entire database, with no scoping to the repository/stack that the webhook actually originated from [1](#0-0) . Since git commit shas are content-addressed and identical objects legitimately exist across forks/mirrors of the same public repository, an attacker who owns any repository containing a commit with the same sha as a victim stack's PR head can send a genuinely GitHub-signed `status` webhook for their own repo that gets applied to the victim's `Commit` record, feeding `MergeRequest#all_status_checks_passed?` and triggering an unauthorized `merge!` with the victim stack's `GITHUB_TOKEN`.

### Finding Description
The broken binding is:
`Shipit::MergeRequest#all_status_checks_passed?` evaluates `StatusChecker.new(head, head.statuses_and_check_runs, ...)` where `head.statuses_and_check_runs` == the set of `Status`/`CheckRun` rows attached to `Commit#id` for stack A's PR head sha [2](#0-1) .
This should equal "the CI status set GitHub itself reports for repository `owner/A`'s commit at that sha." It does not, because the row-creation path never checks which repository the webhook came from:

```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [1](#0-0) 

Compare with `Handler#stacks`, used by other handlers, which correctly scopes lookups via `Repository.from_github_repo_name(repository_name)` [3](#0-2) . `StatusHandler` does not use this scoping at all; its `params` schema doesn't even require a `repository` field [4](#0-3) .

`create_status_from_github!` then persists the forged state under the commit's *own* `stack_id` (the victim's), not the webhook payload's repository [5](#0-4) , and `Status.replicate_from_github!` writes the attacker-controlled `state`/`context`/`description` verbatim [6](#0-5) .

Signature verification (`WebhooksController#verify_signature`) only proves the webhook was really sent by GitHub for the attacker's own organization/repo — it does not, and cannot, prove the `sha` field belongs to that repository [7](#0-6) . Because git objects are content-addressed, an attacker who forks or mirrors the victim's public repository (or otherwise obtains a repository containing an identical commit object, e.g. via cherry-pick with matching author/committer/timestamp/tree) legitimately possesses that same sha in a repo they administer. They can then use the GitHub Statuses API on their own repo to set an arbitrary `state`/`context` for that sha, causing GitHub to emit a validly-signed webhook that `StatusHandler` will misapply to the victim's `Commit` row purely because the sha string matches.

Once the forged `success` status is attached to `head.statuses_and_check_runs` for the victim's `MergeRequest`, `all_status_checks_passed?` / `any_status_checks_failed?` are evaluated over the polluted set [8](#0-7) . If `reject_unless_mergeable!` passes, `ProcessMergeRequestsJob`'s merge flow calls `MergeRequest#merge!`, which executes `stack.github_api.merge_pull_request` using the victim stack's own GitHub App/installation token [9](#0-8) .

None of the listed guards prevent this: `verify_signature` validates only that the sender is a legitimate GitHub organization, not that the `sha` in the payload belongs to that organization's repo; `drop_unhandled_event` only filters unknown event types; `ExplicitParameters` schema for `StatusHandler` validates types, not repository ownership; there is no `force_github_authentication`/`require_permission!` involved since this is an unauthenticated webhook endpoint by design.

### Impact Explanation
Critical: a payload sent under one repository's identity (attacker-owned) mutates CI-status state belonging to a completely different stack/repository, and can drive that other stack to execute `merge_pull_request` — an unauthorized merge performed with the victim stack's `GITHUB_TOKEN`. This is repeatable against any stack in the Shipit instance whose PR head sha the attacker can reproduce in a repository they control (trivial for public repos via forking), and the blast radius spans all tenants/stacks hosted by the same Shipit instance, not just repos in the attacker's own GitHub organization.

### Likelihood Explanation
Preconditions: victim stack A has `merge_queue_enabled: true` and a pending `MergeRequest`; the attacker needs a repository (fork or otherwise) containing a commit object with the exact same sha as the victim PR's head — straightforward for any public repository since forks share commit objects, and achievable for non-forked cases by reconstructing an identical commit (same parent, tree, author/committer identities and timestamps, message). The attacker needs no Shipit credentials, no webhook secret of the victim's org, and no elevated GitHub permissions beyond write access to their own repository (to call the Statuses API). This makes the attack cheap and repeatable, limited only by the attacker's ability to obtain/produce a matching sha, which is easy for public target repositories.

### Recommendation
Scope the `StatusHandler` (and any other sha-keyed handler) lookup to the repository the webhook actually reports, mirroring `Handler#stacks`:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
end
```
This requires adding `repository.full_name` (or equivalent) to the `StatusHandler` params schema and validating it, and applying an analogous repository/stack scope everywhere a `Commit` is looked up solely by `sha` from webhook input.

### Proof of Concept
Minitest plan (`test/controllers/webhooks_controller_test.rb` or `test/models/webhooks/handlers/status_handler_test.rb`):
1. Create two stacks/repos in fixtures: `stack_a` (victim, `merge_queue_enabled: true`, with a pending `MergeRequest` whose `head` commit has `sha: "deadbeef..."`) and `stack_b` (attacker-controlled, unrelated repo).
2. Assert the binding before: `stack_a.commits.find_by(sha: "deadbeef...").statuses.count == 0` and `merge_request.all_status_checks_passed? == false`.
3. Post a `status` webhook whose `repository.full_name` is `stack_b`'s repo but whose `sha` equals `stack_a`'s head commit sha, with `state: "success"`, signed correctly for `stack_b`'s org (stub `verify_webhook_signature` to true for that org only).
4. Assert `stack_a`'s commit now has a `success` status attached (`assert_difference 'stack_a_commit.statuses.count', 1`) even though the payload's `repository` belongs to `stack_b`.
5. Assert `merge_request.all_status_checks_passed?` becomes true purely from the cross-repo status, and, using Mocha, `stack_a.github_api.expects(:merge_pull_request)` to show `ProcessMergeRequestsJob` would invoke `merge!` on `stack_a` off the back of `stack_b`'s webhook — demonstrating the binding `head.statuses_and_check_runs == GitHub's real reported statuses for stack A's sha` is broken.
