### Title
Webhook signature verification is bound to an attacker-controlled organization field, not to the repository the payload writes to - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
### Finding Description
`WebhooksController#verify_signature` selects which GitHub App/webhook secret to authenticate a payload against using `repository_owner`, a value taken directly from the unauthenticated request body: [1](#0-0) [2](#0-1) 

That resolved app's `verify_webhook_signature` is used to gate the request: [3](#0-2) 

Critically, `verify_webhook_signature` returns `true` unconditionally when no `webhook_secret` is configured for the resolved organization (`return true unless webhook_secret`). The engine's own sample/documented configuration explicitly allows `webhook_secret` to be blank per-organization: [4](#0-3) 

Meanwhile, every webhook handler determines *which repository/stack to act on* from a completely different, independently-controlled field in the same JSON body — `repository.full_name` — not from `repository.owner.login`/`organization.login` used for authentication: [5](#0-4) [6](#0-5) 

This breaks the intended binding: **"organization that authenticated" == "repository that is written."** An attacker can craft a JSON body where `repository.owner.login` (or top-level `organization.login`) names an organization that has no `webhook_secret` configured in `Shipit.secrets.github` (or any org they can otherwise trivially satisfy), causing `verify_signature` to pass with a fabricated/empty `X-Hub-Signature`, while `repository.full_name` in the very same payload names a completely different, victim repository/stack that the request handlers then act on unauthenticated. This is directly analogous to the reported Solidity bug: the check validates something true‑but‑unrelated (any org with `USDC_SPOT_INDEX` in the Solidity case; any org with a blank secret here) instead of proving the specific asset/repository in question is the one actually authenticated.

### Impact Explanation
Once signature verification is bypassed for an unrelated org, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` runs handlers against attacker-chosen `repository.full_name`/stack data: [7](#0-6) 

Concrete unauthenticated write primitives reachable this way include: queuing `GithubSyncJob` with attacker-supplied `expected_head_sha` for a push event, forging commit statuses, and archiving/unarchiving review stacks via label handlers that key off `Repository.from_github_repo_name(params.repository.full_name)`: [8](#0-7) 

This satisfies the "unauthenticated read/write of stack state" / cross-repository write class of impact, since an attacker who knows or guesses one organization slug with no configured secret can forge events attributed to any other repository tracked by Shipit.

### Likelihood Explanation
Exploitation requires only: (1) a multi-organization Shipit deployment (documented and supported, see `docs/setup.md` "Using Multiple Github Applications"), and (2) at least one configured organization lacking a `webhook_secret` — a state the shipped sample config treats as normal/valid (`webhook_secret: # nil`). No credentials, GitHub App keys, or prior access are needed; the attacker only needs to send a POST to the public webhooks endpoint with a crafted body and an arbitrary `X-Hub-Signature` header, resolvable purely from payload content the controller itself reads before verification.

### Recommendation
Bind the field used for authentication to the field used for the write. Concretely: derive the organization used for `Shipit.github(organization:)` from the same repository record identified by `repository.full_name` used in the handlers (e.g., resolve `Repository.from_github_repo_name(params.dig('repository','full_name'))&.owner`), reject the request if the two disagree, and treat a missing `webhook_secret` for an organization as a fail-closed configuration error (raise/`head(422)`) rather than an implicit `verified = true`.

### Proof of Concept
1. Configure Shipit with two organizations in `secrets.github`: `victim-org` (has `webhook_secret` set) and `open-org` (no `webhook_secret`, e.g. left blank as in `config/secrets.development.shopify.yml`).
2. POST to `/webhooks` with headers `X-Github-Event: push` and any `X-Hub-Signature` value, and body:
```json
{
  "organization": { "login": "open-org" },
  "repository": { "owner": { "login": "open-org" }, "full_name": "victim-org/victim-repo" },
  "after": "<attacker-chosen-sha>"
}
```
3. `repository_owner` resolves to `open-org`; `Shipit.github(organization: 'open-org').verify_webhook_signature` returns `true` because `open-org` has no `webhook_secret`, so `verify_signature` does not halt the request.
4. `Shipit::Webhooks.for_event('push')` handlers run against `repository.full_name == "victim-org/victim-repo"`, causing a `GithubSyncJob` to be enqueued with the attacker-supplied `expected_head_sha` for the victim stack — despite the request never being authenticated by `victim-org`'s secret.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
