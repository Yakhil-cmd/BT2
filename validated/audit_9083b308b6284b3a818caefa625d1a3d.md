## Title
Webhook signature is verified against an organization derived from an attacker-controlled payload field that differs from the repository the event actually mutates - ([File: app/controllers/shipit/webhooks_controller.rb])

## Summary
`WebhooksController#verify_signature` selects the GitHub App/webhook secret to validate `X-Hub-Signature` against by reading `repository.owner.login` (or `organization.login`) directly out of the unauthenticated JSON body, while every event `Handler` resolves the repository/stack it actually writes to from a different field of the same attacker-controlled body: `repository.full_name` [1](#0-0) [2](#0-1) . In a multi-organization Shipit deployment (a documented, supported configuration - see `github:` keyed by multiple org names in `config/secrets.development.shopify.yml`), these two fields are never required to agree.

## Finding Description
The binding that should hold is: `organization whose secret verified the signature == organization owning the repository the handler mutates`. The controller breaks this equality:

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) 

`Shipit.github(organization:)` looks up per-organization config (`app_id`, `webhook_secret`, `private_key`, etc.) keyed by that string [3](#0-2) , and `GitHubApp#verify_webhook_signature` explicitly treats a blank/unset `webhook_secret` as automatically verified: `return true unless webhook_secret` [4](#0-3) . The sample/dev configuration for multi-org installs (`config/secrets.development.shopify.yml`) shows `webhook_secret:` left blank as a normal state for a configured org [5](#0-4) .

Once the (weak) signature check passes, `WebhooksController#create` hands the entire attacker-controlled JSON straight to the handlers: `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` [6](#0-5) . Every handler resolves its target repository/stack from `payload.dig('repository', 'full_name')`, a field completely independent from the one used for signature routing:

```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [2](#0-1) 

`StatusHandler#process` uses this to create a commit `Status` record directly from unverified payload fields for any commit matching `sha` across the whole instance: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [7](#0-6) , and `PushHandler`/sync jobs act on `repository.full_name` similarly.

**Attack path:** In a Shipit instance configured for org `A` (with a real `webhook_secret`, tracking valuable repositories) and org `B` (also configured but with `webhook_secret` left blank - a documented valid state), an unauthenticated attacker sends a POST to `/webhooks` with:
```json
{ "repository": { "owner": {"login": "B"}, "full_name": "A/valuable-repo" }, "sha": "<target sha>", "state": "success" }
```
`verify_signature` resolves `repository_owner` = `"B"`, loads org `B`'s (secret-less) `GitHubApp`, and `verify_webhook_signature` returns `true` unconditionally - no signature needed. `create` then dispatches the same payload to `StatusHandler`, which matches `sha` against commits in org `A`'s tracked stacks and forges a `success` (or any) CI status on them, with no cryptographic binding to org `A`'s actual webhook secret at all.

## Impact Explanation
This lets an unauthenticated network attacker forge GitHub webhook events (push notifications, commit statuses, check-suite/check-run refresh triggers, pull_request state changes, membership/team changes) against any repository tracked by *any* organization configured in the Shipit instance, as long as at least one configured organization has no `webhook_secret` set - which the codebase and its own sample configuration treat as a legitimate, supported state rather than a hardening failure. Forged `success` commit statuses can satisfy `required_statuses`/CI gating used by `Commit#deployable?` [8](#0-7) , enabling an unauthorized deploy of a commit that never actually passed CI - this is a High/Critical-adjacent "escalation into deploy authorization" outcome explicitly in scope of the rules.

## Likelihood Explanation
Requires only an unauthenticated HTTP POST to the public `/webhooks` endpoint; no session, API token, or GitHub credentials are needed. The only precondition is that the Shipit instance is configured with multiple GitHub organizations and at least one has no `webhook_secret` - a state the shipped sample config (`config/secrets.development.shopify.yml`) presents as normal/expected, not as misuse. Given multi-org support is an intentional, documented feature (`Shipit.github(organization:)`, `TOP_LEVEL_GH_KEYS` including `webhook_secret` per org) [9](#0-8) , this is a realistic operational configuration, not a contrived edge case.

## Recommendation
The organization used to select/verify the webhook signature must be cryptographically bound to the same repository the handlers subsequently act on. Concretely: derive the organization strictly from `repository.full_name`'s owner segment (the same field handlers use) rather than a separate `repository.owner.login`/`organization.login` field, and reject/require a non-blank `webhook_secret` for every organization that owns any tracked `Repository`, so the "no secret configured" bypass cannot be reached for orgs holding real, tracked repositories.

## Proof of Concept
Given a multi-org Shipit install: org `shopify` (tracks `Shopify/shipit-engine`, has `webhook_secret` set) and org `unsecured-org` (configured, `webhook_secret` blank):

```
POST /webhooks
X-Github-Event: status
(no X-Hub-Signature needed, or any garbage value)

{
  "repository": { "owner": { "login": "unsecured-org" }, "full_name": "Shopify/shipit-engine" },
  "sha": "<sha of a real, untested Shopify/shipit-engine commit>",
  "state": "success",
  "context": "ci/required-check"
}
```
`verify_signature` resolves `repository_owner` = `"unsecured-org"`, loads its secret-less `GitHubApp`, and `verify_webhook_signature` short-circuits to `true`. `create` then calls `StatusHandler`, which creates a `success` `Status` on the targeted commit belonging to the `Shopify` org's stack, satisfying `deployable?` checks without ever presenting a valid `shopify` org signature.

**Uncertainty:** I could not fully trace `github_app_config`'s exact org-name normalization/lookup logic (only the wrapper `github` method in `lib/shipit.rb` was inspected due to iteration limits), so edge cases in case-sensitivity or org-name matching are not fully verified. The severity is also conditional on an operator actually running a multi-org instance with a secret-less org that also has tracked repositories - I could not confirm from the code whether Shipit enforces `webhook_secret` presence for orgs with active `Repository` records (it appears it does not, but this warrants direct confirmation in a full session with the running app).

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
