### Title
`pull_request` webhook signature is verified against `organization.login`/`repository.owner.login` but the handler mutates the stack selected by the independent `repository.full_name` field, letting one tenant's secret authorize writes to another tenant's ReviewStack - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects which organization's `webhook_secret` to validate the HMAC against using `repository_owner`, which falls back from `repository.owner.login` to `organization.login` when the former is absent. `LabelCapturingHandler`/`ReopenedHandler`/`ReviewStackAdapter` instead resolve the target `Repository`/`Stack` from the completely independent `repository.full_name` field, with no cross-check that the two point at the same tenant.

### Finding Description
The broken binding, stated as an equality that the code assumes but never enforces: `repository_owner(params) == owner_of(params.repository.full_name)`.

- `repository_owner` is computed as `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` [1](#0-0)  and used to pick the `GitHubApp` (and therefore the `webhook_secret`) used in `verify_webhook_signature` [2](#0-1) .
- Shipit supports a genuinely multi-tenant config where each organization has its own `webhook_secret`, resolved via `Shipit.github_app_config(organization)` / `Shipit.github(organization:)` [3](#0-2) .
- `LabelCapturingHandler#repository` (and `ReopenedHandler#repository`, `ReviewStackAdapter#repo_name`) derive the target `Repository`/`ReviewStack` purely from `params.repository.full_name`, never from `repository_owner` [4](#0-3) [5](#0-4) [6](#0-5) .

Exploit flow: An attacker who legitimately administers "OrgA" (an org they onboarded into the same multi-tenant Shipit instance, so they know OrgA's own `webhook_secret`) POSTs directly to `/webhooks` with `X-Github-Event: pull_request` and a body:
```json
{
  "action": "reopened",
  "number": 1,
  "pull_request": {"labels": [{"name": "malicious_key"}], "head": {"sha": "...", "ref": "..."}, "user": {"login": "attacker"}, "...": "..."},
  "organization": {"login": "OrgA"},
  "repository": {"full_name": "OrgB/victim-repo"},
  "sender": {"login": "attacker"}
}
```
signed with `X-Hub-Signature` computed using OrgA's secret. Because `repository.owner.login` is omitted, `repository_owner` falls back to `organization.login = "OrgA"`; signature verification succeeds using OrgA's known secret. `Shipit::Webhooks.for_event('pull_request')` then dispatches handlers that derive the repository from `repository.full_name = "OrgB/victim-repo"` instead — a completely different, victim tenant. If `OrgB/victim-repo` has `review_stacks_enabled: true` and `provisioning_behavior_allow_all`, `ReopenedHandler#unarchive?` is satisfied and `ReviewStackAdapter` unarchives/creates a `ReviewStack` for `environment: "pr#{number}"` under the victim repository [7](#0-6) [8](#0-7) . `LabelCapturingHandler#capture_labels` then persists `params.pull_request.labels.map(&:name)` (fully attacker-controlled strings) onto that victim `PullRequest` [9](#0-8) . `ReviewStack#env` then uppercases each label and merges `"LABEL" => "true"` into the stack's environment [10](#0-9) , which flows into `TaskCommands#env` and ultimately into the environment passed to executed deploy/rollback commands, as confirmed by existing tests asserting labels become env vars reaching command execution [11](#0-10) [12](#0-11) .

No existing guard closes this gap: `verify_signature` only checks the HMAC against whichever org `repository_owner` names — it never validates that org owns `repository.full_name` [13](#0-12) ; the `ExplicitParameters` schemas in the handlers only validate field presence/types, not cross-field consistency [14](#0-13) ; there is no session/API-client/team check involved since `/webhooks` is intentionally unauthenticated by design and relies solely on the HMAC-to-repository binding, which this bug breaks.

### Impact Explanation
An attacker who controls (and knows the webhook secret of) any single organization onboarded to a multi-tenant Shipit instance can inject attacker-chosen environment variable keys (value `"true"`) into another tenant's ReviewStack build/deploy/rollback environment, and can unarchive/auto-provision review stacks for a victim repository whose `review_stacks_enabled`/`allow_all` policy was meant to only trust that repository's own webhooks. This is "a payload for one repository mutating another's stack," matching the Critical impact class; depending on how the victim's `shipit.yml` consumes environment variables (e.g., toggles like `SAFETY_DISABLED`, or values substituted via `$VAR` interpolation into shell commands executed via `Command`/`PTY.spawn`), this can escalate to unauthorized deploys or command execution influenced by attacker-controlled data. The attack is repeatable against any victim org/repo pair sharing the Shipit instance and costs the attacker nothing beyond controlling one legitimately onboarded org.

### Likelihood Explanation
Requires: (1) the Shipit instance run in multi-tenant GitHub App mode with per-organization `webhook_secret`s (a supported, documented configuration in `lib/shipit.rb`), (2) the attacker legitimately administers at least one onboarded organization (so they know its own secret — this is a normal, low-privilege onboarding action, not a stolen secret), and (3) a victim repository configured with `review_stacks_enabled: true` and `provisioning_behavior_allow_all` (a common, intentionally permissive setting for open-source-style review flows). Given these realistic preconditions, exploitation is a single crafted HTTP POST with no live GitHub interaction required, fully reproducible in a minitest against the controller/handlers.

### Recommendation
Bind signature verification to the same field the handlers use for repository resolution. Either (a) always use `params.dig('repository', 'full_name')`'s owner (not `organization.login`) to select the verifying `GitHubApp`, and reject events where `repository` is absent instead of falling back to `organization`, or (b) after successful signature verification, explicitly assert `repository_owner == Repository.from_github_repo_name(params.repository.full_name)&.owner` before dispatching to any handler, rejecting mismatches.

### Proof of Concept
Minitest plan (`test/controllers/shipit/webhooks_controller_test.rb` style, no live GitHub):
1. Configure `Shipit.stubs(:secrets).returns(github: {orga: {webhook_secret: 'orga-secret', app_id: 1, installation_id: 1, private_key: '...'}, orgb: {webhook_secret: 'orgb-secret', ...}})` (or equivalent multi-org fixture) representing two tenants.
2. Create `shipit_repositories(:orgb_repo)` with `owner: 'OrgB'`, `review_stacks_enabled: true`, `provisioning_behavior: 'allow_all'`.
3. Build a `pull_request` `action=reopened` JSON body with `organization: {login: 'OrgA'}` (no `repository.owner.login`), `repository: {full_name: 'OrgB/victim-repo'}`, `pull_request.labels: [{name: 'pwned'}]`.
4. Compute `X-Hub-Signature` using `orga-secret` (the "lenient"/attacker-known verifier) and POST to `/webhooks`.
5. Assert the equality check that should hold but doesn't: `repository_owner` resolved by the controller (`'OrgA'`) vs. the actual owner of the mutated repository (`'OrgB'`) — assert they differ, proving cross-tenant mutation.
6. Assert response is `200 OK` (not `422`), and assert `Shipit::Repository.from_github_repo_name('OrgB/victim-repo').review_stacks.find_by(environment: 'pr1').pull_request.labels` includes `'pwned'`, and that `ReviewStack#env['PWNED']` equals `'true'` — demonstrating the victim's stack was mutated using OrgA's secret.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
