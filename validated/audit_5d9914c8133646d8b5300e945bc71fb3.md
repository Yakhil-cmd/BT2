### Title
Bash-written file changes bypass the security-review pattern hooks - ([File: plugins/security-guidance/hooks/security_reminder_hook.py])

### Summary
The `security-guidance` plugin's `PostToolUse` handler only calls `record_touched_path()` and the pattern-matching security checks (`check_patterns`, `record_pending_warnings`, `atomic_check_and_mark_warning`) when `tool_name` is one of `Edit`, `Write`, `MultiEdit`, or `NotebookEdit`. File modifications performed through the `Bash` tool (e.g. `sed -i`, `cat >>`, heredocs, `python -c "open(...).write(...)"`) never pass through this branch, so those state-changing writes never update the touched-path/pending-warning "oracle" that the rest of the security pipeline relies on.

### Finding Description
`main()` in `security_reminder_hook.py` routes `PostToolUse` events by `tool_name`: [1](#0-0) 

Only `Edit`, `Write`, `MultiEdit`, and `NotebookEdit` reach `record_touched_path(session_id, file_path)` and the pattern-rule engine (`check_patterns`, `record_pending_warnings`, `atomic_check_and_mark_warning`). `Bash` tool calls are handled by a separate branch that only fires on `git commit`/`git push` command strings: [2](#0-1) 

This mirrors the HydraDX bug class: an action that mutates protected state (`remove_token()` transferring reserve liquidity) failed to invoke the hook (`on_liquidity_changed`) that keeps a downstream consumer (the oracle) in sync. Here, a state-changing action (writing/modifying a file via `Bash`) fails to invoke the equivalent hook (`record_touched_path` / pattern check), leaving the security-guidance state (`touched_paths`, `previous_findings`, per-file pending-warning tracking consumed later in `handle_stop_hook`) unaware that the file changed via that path.

### Impact Explanation
The immediate, deterministic pattern-based reminders (secrets, SQL injection, insecure patterns, etc.) that are surfaced synchronously right after an edit are skipped entirely when the same edit is made via `Bash` instead of `Edit`/`Write`/`MultiEdit`/`NotebookEdit`. This creates an inconsistency in the "oracle" state (`touched_paths`, `pending_warnings`) that downstream code (`consume_stop_state`, `handle_stop_hook`) relies on for metrics and dedup bookkeeping. The final Stop-hook review (`compute_v2_review_set` / `analyze_code_security`) appears to work from git-diff state rather than solely from `touched_paths`, which likely provides a backstop and limits the security impact to metric/warning drift rather than a full bypass of review — I could not fully confirm this from the available context (the exact inputs and gating logic of `compute_v2_review_set` in `diffstate.py` were not fully retrievable within the tool-call budget). At minimum, this is a state-consistency bug of the same class as the referenced report; at most it is a coverage gap in the fast pattern-based review layer.

### Likelihood Explanation
High likelihood of occurrence: any Claude Code session that edits files via shell commands (very common, e.g. `sed`, `awk`, heredocs, generated scripts) rather than the structured `Edit`/`Write` tools will silently skip the pattern-based `PostToolUse` reminder path. This does not require any special privilege beyond normal tool use.

### Recommendation
Extend the `PostToolUse` routing in `security_reminder_hook.py` to also invoke `record_touched_path()` and the pattern-check pipeline for `Bash` invocations that create or modify files (e.g., via `>`, `>>`, `sed -i`, `tee`, redirections, or heredocs), not just for `git commit`/`git push`. Alternatively, ensure the Stop-hook's diff computation (`compute_v2_review_set`) is fully independent of `touched_paths` for determining `review_paths`, and treat `touched_paths` purely as a metrics/telemetry signal so its incompleteness cannot mask a security gap.

### Proof of Concept
1. Start a Claude Code session with the `security-guidance` plugin enabled.
2. Have Claude write a file containing an obviously insecure pattern (e.g., a hardcoded secret or `eval()` on user input) using the `Bash` tool, e.g. `bash -c "echo 'API_KEY=\"sk-abc123\"' > config.py"`, instead of the `Write` tool.
3. Observe that no `PostToolUse` `additionalContext` pattern-reminder is emitted (compare with the same content written via the `Write` tool, which triggers `check_patterns` → `record_pending_warnings` → an inline warning), confirming `record_touched_path`/pattern checks in [3](#0-2)  are never invoked for the `Bash` code path.
