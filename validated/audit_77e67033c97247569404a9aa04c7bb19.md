### Title
Withdraw Instruction Allows Redirecting Withdrawn Tokens to Attacker-Controlled Accounts - ([File: programs/cp-swap/src/instructions/withdraw.rs])

### Summary
In `Withdraw`, the `owner` signer burns their own `owner_lp_token`, but the destination accounts `token_0_account` and `token_1_account` are only constrained by mint, not by ownership/authority of the signer, so LP-token proceeds can be routed to any attacker-chosen token account.

### Finding Description
The `Withdraw` accounts struct enforces `token::authority = owner` on `owner_lp_token` (the account being debited), but the receiving accounts `token_0_account` and `token_1_account` only carry a `token::mint = token_0_vault.mint` / `token::mint = token_1_vault.mint` constraint — there is no check that these accounts are owned by `owner` (or by any authority derived from the signer). [1](#0-0) 

This is the exact bug class from the external report: a fund-destination parameter (`sender`/refund target in the report; here `token_0_account`/`token_1_account`) is fully attacker-configurable and never checked against the actual owner/signer of the transaction. Compare with `deposit.rs`, where the analogous payer-side accounts do carry `token::authority = owner`: [2](#0-1) 

In `withdraw`, the program burns the LP tokens from the owner and then transfers the underlying token_0/token_1 amounts to whatever `token_0_account`/`token_1_account` were supplied, with no ownership check: [3](#0-2) 

### Impact Explanation
A user's LP position can be burned while the corresponding underlying token_0/token_1 payout is sent to an address the user did not intend (e.g., set by a malicious front-end/dApp before the user signs). Because Anchor's `Signer` only requires `owner` to sign, and there is no assertion tying `token_0_account`/`token_1_account` ownership to `owner`, a maliciously-constructed transaction can drain a user's underlying assets on withdrawal even though the user is the one signing and burning their own LP tokens. This is a direct theft of user funds.

### Likelihood Explanation
Likelihood is moderate-to-high: exploitation only requires a malicious or compromised transaction-building layer (e.g., a phishing dApp/wallet integration) to substitute the recipient token accounts before the victim signs — no privileged program authority, no validator collusion, and no unusual on-chain conditions are needed. The victim's own signature authorizes the burn, but the destination of the payout is not something the on-chain program verifies belongs to them.

### Recommendation
Add ownership constraints to the receiving accounts, mirroring `deposit.rs` and `owner_lp_token`:
```rust
#[account(mut, token::mint = token_0_vault.mint, token::authority = owner)]
pub token_0_account: Box<InterfaceAccount<'info, TokenAccount>>,

#[account(mut, token::mint = token_1_vault.mint, token::authority = owner)]
pub token_1_account: Box<InterfaceAccount<'info, TokenAccount>>,
```
This ensures withdrawn funds can only be paid out to accounts actually owned/authorized by the signer who burned the LP tokens.

### Proof of Concept
1. Attacker/malicious front-end builds a `withdraw` transaction for victim `owner`, setting `owner_lp_token` to the victim's real LP token account (required, since it must have `token::authority = owner`), but setting `token_0_account`/`token_1_account` to token accounts owned by the attacker (only constrained by mint, which the attacker can freely satisfy by creating their own token accounts for the same mints).
2. Victim signs the transaction (e.g., via a compromised or malicious wallet/dApp UI) believing they are withdrawing their liquidity to their own wallet.
3. On execution: `token_burn` burns the victim's LP tokens from `owner_lp_token`, and `transfer_from_pool_vault_to_user` pays out `token_0_amount`/`token_1_amount` into the attacker-controlled `token_0_account`/`token_1_account`. [4](#0-3) 
4. The victim's LP position is destroyed with no corresponding underlying tokens received; the attacker receives the full payout.
