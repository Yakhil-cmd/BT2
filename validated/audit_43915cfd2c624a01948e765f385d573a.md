### Title
Integer Overflow in `RewardRatio` Part Validation Bypasses Sum-of-100 Constraint, Enabling Unauthorized KAIA Minting via Governance Vote — (File: `kaiax/gov/param.go`, `kaiax/reward/config.go`)

---

### Summary

The `FormatChecker` for `RewardRatio` in `kaiax/gov/param.go` and `NewRewardRatio` in `kaiax/reward/config.go` validate that ratio parts sum to 100 using signed 64-bit integer arithmetic, but never check that each individual part is within `[0, 100]`. This is the direct Kaia analog of the OpenVM missing-range-check bug: the parts satisfy the sum constraint, but out-of-range parts are never individually bounded. A malicious council member who is the block proposer (in `"none"` governance mode — the default — where `VerifyVote` imposes no voter restriction) can cast a vote with an integer-overflowed ratio string such as `"9223372036854775807/9223372036854775807/102"`. Both the format checker and `NewRewardRatio` accept it because `MaxInt64 + MaxInt64 + 102 = 100` in signed 64-bit arithmetic. After the epoch boundary the ratio is committed to chain state. The subsequent block's reward distribution calls `RewardRatio.Split` using `big.Int` arithmetic (no overflow), computing `gAmount = mintingAmount × 9223372036854775807 / 100` — an astronomical value — and mints that amount to the proposer's address.

---

### Finding Description

**Root cause — `kaiax/gov/param.go` `FormatChecker` for `RewardRatio`:**

```go
sum := 0                          // int (= int64 on 64-bit)
for _, part := range parts {
    num, err := strconv.Atoi(part) // int, accepts up to MaxInt64
    if err != nil { return false }
    if num < 0   { return false }  // only lower-bound check
    sum += num                     // NO overflow guard
}
return sum == 100                  // passes when overflow wraps to 100
``` [1](#0-0) 

The check `if num < 0` is the only per-part constraint. There is no `if num > 100` guard. `strconv.Atoi("9223372036854775807")` succeeds on a 64-bit host (returns `MaxInt64 = 9223372036854775807`). The accumulation `MaxInt64 + MaxInt64 + 102` wraps to `100` in signed 64-bit arithmetic, so `sum == 100` is `true`.

**Root cause — `kaiax/reward/config.go` `NewRewardRatio`:**

```go
g, err1 := strconv.ParseInt(parts[0], 10, 64)
x, err2 := strconv.ParseInt(parts[1], 10, 64)
y, err3 := strconv.ParseInt(parts[2], 10, 64)
// ...
if ... || g+x+y+z != 100 || g < 0 || x < 0 || y < 0 || z < 0 {
    return nil, errMalformedRewardRatio(ratio)
}
``` [2](#0-1) 

The same signed-64-bit overflow applies: `g + x + y = MaxInt64 + MaxInt64 + 102 = 100`, so the guard `g+x+y+z != 100` is `false` and the function returns a `RewardRatio` with `g = 9223372036854775807`.

**Downstream impact — `RewardRatio.Split` uses `big.Int` (no overflow):**

```go
gAmount := new(big.Int).Mul(amount, big.NewInt(r.g))
gAmount = gAmount.Div(gAmount, big100)
``` [3](#0-2) 

`big.NewInt(9223372036854775807)` is a valid arbitrary-precision integer. For a typical minting amount of `6.4 × 10¹⁸` kei, `gAmount ≈ 5.9 × 10³⁵` kei — roughly `10⁸` times the entire KAIA total supply. `state.AddBalance` is called with this value, minting it to the proposer.

**`calcRemainder` then produces a huge negative value:**

```go
ratioRemainder := calcRemainder(minted, proposer, stakers, kif, kef)
kif.Add(kif, ratioRemainder)   // kif becomes ≈ −1.18 × 10³⁶
``` [4](#0-3) 

The KIF fund address receives a negative `AddBalance` call, draining it.

**Trigger path — `VerifyVote` imposes no governance-mode restriction in `"none"` mode:**

```go
// In single mode, only the governing node can write header.Vote after Permissionless.
if h.ChainConfig.IsPermissionlessForkEnabled(...) &&
    params.GovernanceMode == "single" &&
    vote.Voter() != params.GoverningNode {
    return ErrVotePermissionDenied
}
``` [5](#0-4) 

In `"none"` mode (the default `DefaultValue: "none"`) this branch is never entered. Any council member who is the block proposer may include a vote. `checkConsistency` for `RewardRatio` unconditionally returns `nil`: [6](#0-5) 

---

### Impact Explanation

A single council member who is the block proposer in `"none"` governance mode can:

1. Mint an astronomically large amount of KAIA to their own address (unauthorized token creation).
2. Cause the KIF/KEF fund addresses to receive a negative balance adjustment, draining system-managed funds.
3. Corrupt the canonical reward state for all subsequent blocks until the ratio is overwritten.

This satisfies the allowed impact gate: *unauthorized mint affecting KAIA and system-managed funds*, and *invalid state transition on honest nodes* (subsequent reward calculations operate on a broken ratio).

---

### Likelihood Explanation

`"none"` is the `DefaultValue` for `GovernanceGovernanceMode`. [7](#0-6) 

Any chain that has not explicitly overridden the governance mode operates in `"none"` mode. In that mode, every council member who wins the block-proposer slot (which rotates among validators) can cast this vote without any additional privilege. This is a semi-trusted, single-actor trigger — not majority collusion.

---

### Recommendation

Add per-part upper-bound checks in both locations:

**`kaiax/gov/param.go` `FormatChecker`:**
```go
if num < 0 || num > 100 {
    return false
}
```

**`kaiax/reward/config.go` `NewRewardRatio` and `NewRewardKip82Ratio`:**
```go
if g < 0 || g > 100 || x < 0 || x > 100 || y < 0 || y > 100 || z < 0 || z > 100 {
    return nil, errMalformedRewardRatio(ratio)
}
```

func (r *RewardRatio) Split(amount *big.Int) (*big.Int, *big.Int, *big.Int) {
	gAmount := new(big.Int).Mul(amount, big.NewInt(r.g))
	gAmount = gAmount.Div(gAmount, big100)

	xAmount := new(big.Int).Mul(amount, big.NewInt(r.x))
	xAmount = xAmount.Div(xAmount, big100)

	yAmount := new(big.Int).Mul(amount, big.NewInt(r.y))
	yAmount = yAmount.Div(yAmount, big100)

	return gAmount, xAmount, yAmount
}
