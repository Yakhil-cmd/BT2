### Title
`shipit.yml` `machine.environment.GITHUB_TOKEN` overrides `Shipit.github.token` via merge order in `TaskCommands#env` - ([File: lib/shipit/task_commands.rb])

### Summary
`TaskCommands#env` merges `deploy_spec.machine_env` (parsed from the repository's `shipit.yml`, checked out on disk from the deployed commit) after `Commands#base_env` sets `GITHUB_TOKEN`, and no filtering is applied to `machine_env` unlike `deploy_variables`/`rollback_variables`. For review stacks, this checked-out commit is the PR author's own `head.sha`, so a PR author can declare `machine: { environment: { GITHUB_TOKEN: <anything> } }` and have that value flow to `Command#unbundled_env` at `PTY.spawn` time for every step of the task, including the `git`/checkout steps.

### Finding Description
Binding claimed: `merged_env['GITHUB_TOKEN'] == Shipit.github.token` for the repository. Trace:

- `Commands#base_env` sets `'GITHUB_TOKEN' => github.token` (`lib/shipit/commands.rb:37-50`), and `TaskCommands` overrides `github` to `Shipit.github(organization: @stack.repository.owner)` (`lib/shipit/task_commands.rb:102-104`) — this is a trusted, engine-controlled value.
- `TaskCommands#env` builds the final environment as:
```ruby
super
  .merge(@stack.env)
  .merge(...)
  .merge(deploy_spec.machine_env)
  .merge(@task.env)
```
(`lib/shipit/task_commands.rb:33-48`). `Hash#merge` lets later hashes overwrite earlier keys, so if `deploy_spec.machine_env` contains a `GITHUB_TOKEN` key, it silently overrides the trusted value set in `base_env`.
- `deploy_spec` is `DeploySpec::FileSystem.new(@task.working_directory, @stack)` (`lib/shipit/task_commands.rb:13-15`), and `machine_env` is `config('machine', 'environment') || {}` (`app/models/shipit/deploy_spec.rb:69-71`), read directly from the checked-out `shipit.yml`/`.shipit/shipit.yml` file (`app/models/shipit/deploy_spec/file_system.rb:98-142`) — no allow-list or sanitization is applied to this hash anywhere (contrast with `filter_deploy_envs`/`filter_rollback_envs`, which apply `EnvironmentVariables#permit` but only to task-invocation env, not to `machine.environment`).
- For a `ReviewStack`, `ReopenedHandler#process` calls `stack.unarchive!` (`app/models/shipit/webhooks/handlers/pull_request/reopened_handler.rb:41-45`) after validating only that the PR is reopened and matches the repo's provisioning policy (label-based or "allow all") — there is no validation of the PR's file contents. The subsequent deploy checks out the PR's `head.sha`, i.e., attacker-controlled content, and loads `shipit.yml` from it.
- Merged env eventually reaches `Command#unbundled_env` (`BASE_ENV.merge(...).merge(@env.stringify_keys)`, `lib/shipit/command.rb:103-105`) and is passed directly to `PTY.spawn(unbundled_env, *interpolated_arguments, ...)` (`lib/shipit/command.rb:92`), so any `git` step run for that task (`checkout`, `clone`, or steps defined by `deploy.override`) executes with the attacker's `GITHUB_TOKEN` in its environment, not `Shipit.github.token`.

No existing guard (`verify_signature`, `ExplicitParameters` schema, `force_github_authentication`, `EnvironmentVariables#permit`) inspects or filters `machine.environment`, so the divergence is real: the equality `merged_env['GITHUB_TOKEN'] == Shipit.github.token` does **not** hold once the repository's `shipit.yml` sets that key.

### Impact Explanation
If a script or tool invoked during the task's steps reads `$GITHUB_TOKEN` from its environment (a common convention for `git`/`hub`/`gh` and many CI-style tooling used in deploy steps), it will authenticate outbound GitHub API/git operations using the attacker-supplied token value instead of Shipit's own App/installation token. This could be used to redirect Shipit's authenticated GitHub calls (e.g., a custom deploy step performing `gh api` or `git push` using `$GITHUB_TOKEN`) to act with a token of the attacker's choosing (e.g., stealing partial trust, causing a request against an attacker-controlled GitHub Enterprise-compatible endpoint that captures Shipit's own token via `GITHUB_TOKEN`/`GITHUB_DOMAIN` combination — note `GITHUB_DOMAIN` is also settable this way, which strengthens the redirect risk). This matches the "Critical - authentication bypass ... exfiltration of `GITHUB_TOKEN`" category, since the effective credential seen by any GitHub-token-consuming step is attacker-controlled, for the attacker's own repository/stack. Blast radius is confined to the review stack/task for the repository whose `shipit.yml` was modified (single tenant per repository), since `deploy_spec.machine_env` is scoped to that stack's own checkout.

### Likelihood Explanation
Preconditions: the target repository must have review stacks enabled (`repository.review_stacks_enabled`) with a provisioning policy that allows the attacker's PR to trigger `unarchive!`/deploy (either "allow all" or label-based, where the attacker may need a collaborator to apply a label — for "allow all" repos, no privilege is needed at all). The attacker needs only to open/push a PR containing a `shipit.yml` with `machine.environment.GITHUB_TOKEN` set, which is trivial and repeatable against any repository configured this way. The actual security impact is bounded by whether deploy steps invoke tools that consume `GITHUB_TOKEN` from the environment — this is a very common pattern (`git` credential helpers, `gh` CLI, custom scripts) but is not proven to be universally exploitable without knowing the specific deploy steps of a target stack.

### Recommendation
In `DeploySpec::FileSystem`/`DeploySpec#machine_env`, reject or filter reserved/security-sensitive keys (`GITHUB_TOKEN`, `GITHUB_DOMAIN`, etc.) from user-supplied `machine.environment`, or change `TaskCommands#env`'s merge order so `base_env`'s `GITHUB_TOKEN`/`GITHUB_DOMAIN` are applied last (after `deploy_spec.machine_env` and `@task.env`) so they cannot be overridden by repository-controlled configuration.

### Proof of Concept
```ruby
# test/unit/task_commands_test.rb (illustrative)
test "deploy_spec.machine_env cannot override GITHUB_TOKEN" do
  stack = shipit_stacks(:shipit)
  task = stack.tasks.build(...)
  commands = TaskCommands.new(task)

  deploy_spec = mock
  deploy_spec.stubs(:machine_env).returns('GITHUB_TOKEN' => 'attacker-token')
  commands.stubs(:deploy_spec).returns(deploy_spec)

  env = commands.env

  assert_equal Shipit.github(organization: stack.repository.owner).token, env['GITHUB_TOKEN']
  refute_equal 'attacker-token', env['GITHUB_TOKEN']
end
```
