Found a valid analog: an `ApiClient` scoped to a specific stack via `stack_id` can still read deploy/build data of any other stack through `Api::CCMenuController`, because that controller resolves the stack with the unscoped `Stack.from_param!` instead of the client-scoped `stacks.from_param!` used everywhere else.

### Title
API client scoped to one stack can read any stack's CCMenu status - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`ApiClient` records can be scoped to a single stack (`stack_id`), and `Shipit::Api::BaseController` enforces that scoping through the `stacks`/`stack` helpers so that a scoped client can only reach records belonging to its authorized stack. `Api::CCMenuController` overrides `stack` to resolve directly against the global `Stack` relation instead of the client-scoped `stacks` relation, breaking the "stack a token authorizes" == "stack a token touches" binding that the rest of the API enforces.

### Finding Description
`Api::BaseController#stacks` restricts the queryable set of stacks to the ones the current `ApiClient` is authorized for: `current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all`, and `#stack` is defined as `stacks.from_param!(params[:stack_id])`. [1](#0-0) 

Every other stack-scoped API controller (e.g. `Api::StacksController`) relies on this same scoped `stacks.from_param!` helper to resolve the target stack, ensuring an `ApiClient` created with `stack: shipit` (see fixture `here_come_the_walrus`) cannot address a different stack's resources. [2](#0-1) [3](#0-2) 

`Api::CCMenuController`, however, defines its own `stack` method that bypasses the client's `stack_id` scope entirely and resolves against the unscoped `Stack` class:

```ruby
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end
``` [4](#0-3) 

This is the same class of bug as the report's `IsNonTombstonedObserver()` vs `CheckObserverCanVote()` gap: a narrower, correct authorization primitive (`stacks.from_param!`, scope-aware) exists and is used elsewhere, but one code path uses the weaker, unscoped primitive (`Stack.from_param!`) that omits the binding check. The controller does require `read:stack` permission via `require_permission :read, :stack`, but that check only validates the permission *string* on the client, not that the specific `stack_id` in the request matches the stack the client is scoped to. [5](#0-4) [6](#0-5) 

### Impact Explanation
An `ApiClient` token that was deliberately scoped to a single stack (a common pattern used by the app itself, e.g. `CCMenuUrlController` mints a `read:stack`-scoped client per-stack for CCMenu/CI-status URLs) can be replayed against `Api::CCMenuController#show` with a different `stack_id` and will successfully render that other stack's latest deploy/rollback status (`stack.deploys_and_rollbacks.last`), leaking deploy state and build status across stacks the token was never authorized to see. [7](#0-6) [8](#0-7) 

This matches the "unauthenticated/unauthorized read of stack state" High-impact category: an attacker holding one stack-scoped CCMenu token (which is embedded in a URL, e.g. sharable CI status badges) can enumerate/read the deploy status of arbitrary stacks by varying `stack_id`.

### Likelihood Explanation
Likely to be triggerable by anyone in possession of any single-stack-scoped `ApiClient` token (these tokens are routinely generated and shared via `CCMenuUrlController#fetch`'s CCMenu URL, which embeds the token as a URL query parameter). No privileged repository access or additional secret is needed beyond a token that legitimately exists for one stack; the vulnerable code path is reached with a single unauthenticated (aside from the token) HTTP GET where only `params[:stack_id]` is varied.

### Recommendation
Change `Api::CCMenuController#stack` to reuse the client-scoped helper, consistent with every other stack-scoped API endpoint:

```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```

### Proof of Concept
1. Using the `CCMenuUrlController#fetch` flow (or directly via `ApiClient.create_with(permissions: %w[read:stack], stack: stack_a)`), obtain a `read:stack` token scoped to `stack_a`.
2. As an attacker holding that token, issue `GET /api/stacks/:stack_b_id/ccmenu.xml?token=<token>` where `stack_b` is a different stack.
3. Because `Api::CCMenuController#stack` calls `Stack.from_param!(params[:stack_id])` (unscoped) rather than `stacks.from_param!` (client-scoped), the request resolves `stack_b` and returns `stack_b`'s deploy/build status in the XML response, despite the token being authorized only for `stack_a`. [9](#0-8)
