### Title
Webhook signature verification keys off `repository.owner.login` while `PushHandler` resolves the mutated Stack from the independent `repository.full_name` field, letting an attacker sign with their own org's secret but target another org's Stack - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App/secret to validate the HMAC signature using `repository_owner` (`params.dig('repository', 'owner', 'login')`), while `Handler#stacks` (used by `PushHandler#process`) resolves the repository/stack to mutate using the separate `repository.full_name` field of the very same JSON body. Because these two fields are independently attacker-supplied (this is a raw HTTP POST, not a genuine GitHub-signed payload consistency check), an attacker who owns `attacker/attacker-repo` and knows only their own `webhook_secret` can sign a payload whose `repository.owner.login` is `"attacker"` (so the signature check passes) but whose `repository.full_name` is `"victim-org/victim-repo"` (so `sync_github` is invoked on the victim's Stack).

### Finding Description
The broken binding: the code implicitly assumes
`repository_owner (used to select the verifying webhook_secret) == owner segment of repository.full_name (used to select the mutated Stack)`.
No code enforces this equality.

Trace:
1. `verify_signature` in [1](#0-0)  computes `github_app = Shipit.github(organization: repository_owner)` and calls `github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)`.
2. `repository_owner` is defined purely as [2](#0-1) , reading `params.dig('repository', 'owner', 'login')` from the attacker-controlled raw JSON body.
3. `verify_webhook_signature` in [3](#0-2)  only checks that the HMAC-SHA1 of `request.raw_post` matches the secret configured for whatever organization was passed in — it performs no cross-check against any other field of the payload.
4. Once verified, `WebhooksController#create` dispatches to `PushHandler.call(params)` [4](#0-3) .
5. `PushHandler#process` calls `stacks.not_archived.where(branch:).find_each { |stack| stack.sync_github(...) }` [5](#0-4) .
6. `stacks` is inherited from `Handler`, and resolves the repository via `Repository.from_github_repo_name(repository_name)`, where `repository_name = payload.dig('repository', 'full_name')` [6](#0-5)  — a field entirely independent of `repository.owner.login` used for signing.
7. `PushHandler`'s `ExplicitParameters` schema only requires `:ref` and `:after` [7](#0-6) ; it does not validate or constrain `repository` at all, so nothing stops `repository.owner.login` and `repository.full_name`'s owner from diverging.

Exploit flow: attacker (who administers the GitHub App installation for org `attacker`, and therefore knows the `webhook_secret` Shipit's operator configured for that org — the standard multi-org threat model) crafts a raw JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker chosen sha>",
  "repository": { "owner": { "login": "attacker" }, "full_name": "victim-org/victim-repo" }
}
```
computes `X-Hub-Signature: sha1=<HMAC-SHA1(attacker_webhook_secret, raw_body)>`, and POSTs it to `/webhooks` with `X-Github-Event: push`. `verify_signature` resolves `Shipit.github(organization: "attacker")` and the signature validates against the attacker's own known secret. `PushHandler` then looks up `victim-org/victim-repo`'s real `Repository`/`Stack` rows and calls `sync_github(expected_head_sha: <attacker sha>)` on them — a write against a repository/organization whose secret never validated the request.

No existing guard prevents this: `drop_unhandled_event` only filters by event type; the `ExplicitParameters` schema for `PushHandler` doesn't require or validate `repository`; there is no comparison anywhere between `repository_owner` and `repository.full_name`'s owner segment.

### Impact Explanation
The attacker can force `Stack#sync_github` to run against any repository/Stack registered in Shipit, purely by knowing the `webhook_secret` for their own, unrelated organization. This is a cross-tenant mutation: a request authenticated (signed) for organization `attacker` produces a write (`sync_github`, which schedules GitHub-sync work and updates commit/HEAD tracking) on organization `victim-org`'s Stack. This matches the explicitly listed Critical category "a payload for one repository mutating another's stack." It is trivially repeatable against any repository whose `owner/name` the attacker can guess or discover (Shipit repository/stack pages are typically enumerable), and works identically for every org configured on a multi-org Shipit instance, so the blast radius spans all tenants sharing the instance.

### Likelihood Explanation
Preconditions: Shipit must be configured for multiple GitHub organizations (multi-org `Shipit.github(organization:)` config), and the attacker must control (own, or be an admin/installer of) at least one such organization, giving them legitimate knowledge of that organization's `webhook_secret` — a standard, low-cost precondition for anyone onboarding their own org into a shared Shipit instance. No Shipit session, API token, or GitHub token is required. The attacker only needs to know or guess a target `owner/repo` name, which is generally discoverable via Shipit's own stack pages. Cost per request is a single signed HTTP POST; the attack is fully repeatable and automatable.

### Recommendation
In `PushHandler` (and any other handler that both signs against `repository.owner.login` and resolves records from `repository.full_name`), enforce that the owner segment of `repository.full_name` matches `repository.owner.login` before processing — reject the payload (or require `repository.owner.login` as part of `ExplicitParameters` and cross-check it) in `Handler#repository_name`/`stacks`, or in `WebhooksController#create` before dispatch. More robust: derive both the signing organization and the mutated repository from a single canonical field, or verify that `Shipit.github(organization: repository_owner)` is actually the GitHub App backing the repository named in `repository.full_name` (e.g., by checking the resolved `Repository`'s configured organization equals `repository_owner`) prior to calling any handler.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (minitest, no live GitHub)
test "push payload signed by attacker org cannot mutate victim stack" do
  victim_repo = shipit_repositories(:rails) # owner: 'shopify', name: 'rails' (existing fixture)
  victim_stack = victim_repo.stacks.first
  attacker_secret = 'attacker-known-secret'

  # Stub Shipit.github(organization: 'attacker') to return an app configured with attacker_secret
  attacker_app = Shipit::GitHubApp.new('attacker', webhook_secret: attacker_secret)
  Shipit.stubs(:github).with(organization: 'attacker').returns(attacker_app)

  body = {
    ref: "refs/heads/#{victim_stack.branch}",
    after: 'deadbeef' * 5,
    repository: {
      owner: { login: 'attacker' },       # used only for signature org lookup
      full_name: victim_repo.github_repo_name # e.g. 'shopify/rails' - used by PushHandler#stacks
    }
  }.to_json

  signature = 'sha1=' + OpenSSL::HMAC.hexdigest('sha1', attacker_secret, body)

  Shipit::Stack.any_instance.expects(:sync_github).never

  post shipit.webhooks_path,
       params: body,
       headers: { 'X-Github-Event' => 'push', 'X-Hub-Signature' => signature, 'CONTENT_TYPE' => 'application/json' }

  assert_response :ok
  # Binding check: repository_owner used for signing ('attacker') != owner segment of full_name used for stack lookup ('shopify')
end
```
Before the fix, this test fails: the mocked `sync_github` expectation (`.never`) is violated because `PushHandler` invokes `sync_github` on `victim_stack` despite the signature having been verified against organization `"attacker"`, not `"shopify"`.
