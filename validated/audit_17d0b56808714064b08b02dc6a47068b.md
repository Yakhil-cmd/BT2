### Title
A malicious swap route can steal unrelated caller funds through nested authorization - (File: `contracts/controller/src/strategies/swap.rs`)

### Summary
`swap_collateral`, `swap_debt`, `multiply`, and `repay_debt_with_collateral` accept an opaque `Bytes` route and forward it to the configured router. The controller authenticates the caller, permits only the controller’s exact input-token transfer, and measures only the controller’s input/output balances, but it does not constrain which external contracts the route invokes. A malicious venue can therefore place an unrelated `token.transfer(victim, attacker, amount)` beneath the victim’s signed authorization tree and steal wallet funds if the victim signs the simulated tree.

### Finding Description
`StrategySwap` is raw encoded `Bytes` supplied by the caller, not a controller-validated route structure. [1](#0-0)  `swap_collateral` exposes that route as its final `swap` argument, while `swap_debt`, `multiply`, and `repay_debt_with_collateral` expose equivalent router payloads. [2](#0-1)  The account owner or delegate authorizes the strategy call, after which the controller withdraws the specified collateral and calls the shared swap path. [3](#0-2) 

The shared swap path snapshots the controller’s balances, creates a leaf authorization allowing only `token_in.transfer(controller, router, amount_in)`, invokes `execute_strategy(controller, amount_in, swap)`, and then checks the controller’s measured spend and output. [4](#0-3)  These checks bound only the routed controller balance; they do not prevent third-party code reached through the payload from adding another invocation that requires the original caller’s authorization. [5](#0-4) 

### Impact Explanation
An attacker who supplies a poisoned route to a prospective victim can steal any token in the victim’s wallet, including tokens unrelated to the lending position and not listed by the protocol. The malicious venue can return enough output for the account operation to satisfy the controller’s positive-output and post-operation risk checks while separately transferring victim funds to the attacker. [6](#0-5) 

The loss is the victim’s wallet balance rather than pool assets, so this is theft of user funds. The malicious invocation must appear in the signed authorization tree and therefore requires the victim to sign the poisoned transaction, but neither the controller API nor the opaque `Bytes` argument provides a protocol-level venue restriction. [7](#0-6) 

### Likelihood Explanation
No privileged role, leaked key, oracle manipulation, or compromised configured router is required: an unprivileged attacker can deploy the malicious venue and distribute a route containing it. [1](#0-0)  The attack requires a victim to use the malicious route and approve the additional child authorization, so it is less likely than a fully autonomous drain, but users relying on route-generation services or only checking the top-level call are exposed. [8](#0-7) 

The controller’s final risk checks do not detect the theft because the unrelated wallet-token transfer does not alter the measured `token_in` or `token_out` balances used by `verify_router_output`. [6](#0-5) 

### Recommendation
Do not allow arbitrary external contract calls to execute beneath the caller’s authorization. Prefer a route architecture in which venue adapters call only protocol-validated pool/venue contracts and the router cannot execute caller-selected contract addresses. [9](#0-8) 

Until that is enforced, clients must decode every route before signing and reject authorization trees containing any child invocation other than the exact expected input transfer. [10](#0-9)  The controller should additionally document the authorization-tree requirement for `swap_collateral`, `swap_debt`, `multiply`, and `repay_debt_with_collateral`. [11](#0-10) 

### Proof of Concept
1. A victim owns an account with USDC supply and also holds an unrelated `wallet_token` in their wallet.
2. An attacker deploys a contract exposing a venue-like `swap` function. When invoked during route execution, that function calls `token.transfer(victim, attacker, wallet_token_balance)`.
3. The attacker gives the victim a `swap_collateral` request with `current = USDC`, `new = ETH`, `amount = supplied_amount`, and a route whose hop reaches the malicious contract. [2](#0-1) 
4. The victim’s account authorization is checked and ownership is validated. [8](#0-7) 
5. The controller withdraws USDC to itself and authorizes only its own exact USDC transfer to the configured router. [12](#0-11) 
6. During `execute_strategy`, the malicious venue performs the unrelated wallet-token transfer. The transaction’s simulated authorization tree shows that transfer as an extra child under the victim’s `swap_collateral` authorization, and signing that tree authorizes it. [7](#0-6) 
7. The malicious route pays a positive ETH output to the controller, so the spend/output checks and final account-risk checks pass. [6](#0-5) 
8. The transaction completes, the victim’s ETH supply is credited, and the attacker receives the victim’s unrelated `wallet_token` balance.
