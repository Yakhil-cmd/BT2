### Title
Webhook signature verified against `repository.owner.login`'s secret while target repository is resolved from unrelated `repository.full_name` field, enabling cross-organization writes - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
In a multi-tenant Shipit deployment (multiple GitHub Apps/organizations each with an independent `webhook_secret`), the webhook controller selects which organization's secret to use for HMAC verification from `repository.owner.login`, but every event handler resolves the actual `Repository`/`Stack` to act on from the independent `repository.full_name` field. GitHub never enforces that these two fields agree, and Shipit never cross-checks them, so a payload can be signed with organization X's real secret while acting on organization Y's repository.

### Finding Description
`WebhooksController#verify_signature` picks the GitHub App config to verify against solely from the payload's claimed owner: [1](#0-0) [2](#0-1) 

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

`Shipit.github(organization:)` looks up per-organization configuration (`app_id`, `installation_id`, `webhook_secret`) via `github_app_config`, confirming multi-tenant configuration is a first-class, supported feature: [3](#0-2) 

Once the signature is accepted, every handler determines *which* repository/stack to mutate using a completely different field — `repository.full_name` — parsed independently into `owner`/`name`: [4](#0-3) [5](#0-4) 

```ruby
def self.from_github_repo_name(github_repo_name)
  repo_owner, repo_name = github_repo_name.downcase.split('/')
  find_by(owner: repo_owner, name: repo_name)
end
```

The equality that should hold is:
`organization whose webhook_secret validated the request (repository.owner.login)` == `organization of the repository actually written to (repository.full_name prefix)`.

Nothing in `WebhooksController` or `Handler` enforces this. An attacker who legitimately controls organization `X` in this Shipit instance (and thus can generate a genuinely HMAC-signed payload using `X`'s real, GitHub-issued webhook secret — no privileged Shipit credential needed, just install/trigger from their own GitHub org) can set `repository.owner.login = "X"` (so `verify_signature` picks `X`'s secret and the HMAC matches) while setting `repository.full_name = "Y/some-repo"` for a victim organization `Y` also configured on the same Shipit instance. The signature check passes because it only validates that the whole raw body was signed by *some* known secret — it never confirms that secret's organization actually owns the repository referenced inside the body.

Handlers that then act purely on `repository.full_name`:
- `PushHandler#process` triggers `stack.sync_github` for org Y's stacks: [6](#0-5) 
- Pull-request handlers create/archive/unarchive Review Stacks for org Y's repository: [7](#0-6) , [8](#0-7) 

None of these paths re-check that `Y` (the org whose repository is mutated) matches `X` (the org whose secret validated the request).

### Impact Explanation
This breaks the "organization authenticated" vs "repository written" trust binding explicitly called out as in-scope. It allows an attacker who only controls one organization's GitHub App installation on a shared/multi-tenant Shipit instance to forge webhook events that create, archive, unarchive Review Stacks, or trigger `sync_github` (which updates tracked commits, PR/CI state used for gating deploys) for a completely unrelated organization's repository — a cross-repository write with no legitimate authorization over that repository, satisfying the "cross-repository writes" High/Critical impact criterion.

### Likelihood Explanation
This requires the deployment to be configured with more than one organization under `secrets.github` (a documented, supported feature via `github_app_config`/`github_organizations`), and requires the attacker to control one such organization's real GitHub App installation to obtain a validly-signed payload. This is a realistic scenario for any shared/multi-org Shipit instance (e.g., an internal platform team hosting deploys for many teams/orgs), and requires no access to Shipit sessions, API tokens, or the victim organization's secret.

### Recommendation
After signature verification, before dispatching to handlers, verify that the organization whose secret validated the signature (`repository_owner`) matches the owner encoded in `repository.full_name` (and in `organization.login` for org-scoped events). Reject the webhook (422) on mismatch. Alternatively, key the `Repository`/`Stack` lookup by the already-authenticated organization instead of trusting an independent payload field.

### Proof of Concept
1. Deploy Shipit with two configured GitHub App organizations, `X` and `Y`, each with its own `webhook_secret`, both tracking repositories in Shipit (`org-x/repo-x`, `org-y/repo-y`).
2. As an attacker who controls org `X`'s GitHub App installation (e.g., an admin of `X`, or anyone who can trigger/replay a webhook from `X`), craft a `push` (or `pull_request`) JSON payload where:
   - `repository.owner.login = "X"`
   - `repository.full_name = "org-y/repo-y"`
3. Compute the `X-Hub-Signature` HMAC over this crafted raw body using `X`'s real webhook secret (known/controlled by the attacker).
4. POST to `/webhooks` with `X-Github-Event: push` and the forged signature.
5. `verify_signature` resolves `Shipit.github(organization: "X")` and successfully verifies the HMAC.
6. `PushHandler` resolves `stacks` via `Repository.from_github_repo_name("org-y/repo-y")`, and calls `sync_github`/creates or archives Review Stacks belonging to org `Y`, despite the attacker never having proven any relationship to org `Y`.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
