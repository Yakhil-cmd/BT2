### Title
Webhook signature is verified against the wrong-org key while handlers act on the payload's `repository.full_name` — cross-organization forged webhook events - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/webhook secret to validate a webhook against using `repository_owner`, a value taken straight from the untrusted request body (`params.dig('repository','owner','login')` or `params.dig('organization','login')`). All downstream event handlers, however, resolve the actual `Repository`/`Stack` to act on using a different field from that same untrusted body: `payload.dig('repository', 'full_name')`. Because Shipit explicitly supports multiple GitHub Apps/organizations, each with its own independent `webhook_secret` [1](#0-0) , an attacker who legitimately controls one configured organization's webhook secret can sign a payload with that key while setting `repository.full_name` to point at a completely different organization's repository, causing Shipit to execute the event against a repository/stack it was never authenticated for.

### Finding Description
`verify_signature` picks the app config via `repository_owner` and checks the HMAC signature against that app's `webhook_secret`: [2](#0-1) [3](#0-2) 

The signature check only proves "whoever sent this owns the webhook secret configured for org `repository_owner`" — it never checks that the rest of the JSON body is actually about a repository owned by that same org. Every `Handler` subclass, however, uses a completely independent lookup of the target repository/stack, taken from `repository.full_name` in the same attacker-controlled body: [4](#0-3) 

For example `PushHandler` uses `stacks` (derived from `repository.full_name`) to trigger `stack.sync_github(expected_head_sha: params.after)`: [5](#0-4) 

Pull-request handlers likewise resolve `Shipit::Repository.from_github_repo_name(params.repository.full_name)` and perform state-changing actions (archive/unarchive review stacks, capture labels, create review stacks) purely from this attacker-supplied `full_name`: [6](#0-5) [7](#0-6) 

Since Shipit's multi-org configuration schema is a first-class, documented feature (`Shipit.github(organization:)` looks up a config keyed by organization, each with its own `webhook_secret`) [8](#0-7) [9](#0-8) , the binding that should hold is: **organization authenticated (the org whose secret validated the signature) == organization that owns the repository being acted upon (`repository.full_name`)**. The controller never enforces this equality — it only uses `repository_owner` to select the verification key, then discards it. The equality that is broken is exactly the analog called out in scope: *"an organization that authenticated versus the repository that is written."*

### Impact Explanation
In a Shipit instance configured with multiple GitHub organizations (a supported, documented deployment topology), an attacker who is a legitimate GitHub App/webhook administrator for their own organization (`OrgA`, tracked by the same Shipit instance) can forge webhook payloads — signed with `OrgA`'s own webhook secret — that claim to originate from a repository belonging to `OrgB` (any other org/repository tracked by the instance) by setting `repository.owner.login: "OrgA"` (to pass signature verification) and `repository.full_name: "OrgB/victim-repo"` (to select the actual target acted upon). This lets the attacker:
- Trigger `GithubSyncJob`/`stack.sync_github` on an arbitrary stack belonging to another organization, which can lead to unauthorized deploys via continuous delivery, or
- Archive/unarchive/create review stacks and manipulate pull-request-driven state for repositories the attacker does not own.

This crosses a genuine credential/authorization boundary (one org's webhook secret is used to affect another org's repository state) without requiring any Shipit session, API token, or GitHub write access — satisfying the "cross-repository writes" / "unauthorized deploy" High/Critical impact bar.

### Likelihood Explanation
Exploitability requires the attacker to control (or know) a valid `webhook_secret` for at least one organization configured in the same multi-tenant Shipit instance — which is exactly the credential such an attacker is expected to have as a legitimate admin of their own org's GitHub App integration, not a privileged Shipit credential. No repository write access, Shipit session, or `GITHUB_TOKEN` is needed; the attacker only needs to POST directly to `/webhooks` with a correctly-signed, attacker-crafted JSON body. This is realistically reachable whenever an operator uses the documented multi-org configuration.

### Recommendation
After determining `repository_owner` and validating the signature against that org's secret, additionally verify that the repository actually referenced by the payload (`repository.full_name`'s owner segment, or an explicit repository-to-organization mapping stored in Shipit, e.g. via `Repository`/`Stack` records) belongs to the same organization used for signature selection. Reject (422) the webhook if `repository.full_name`'s owner does not match the `repository_owner`/organization whose secret validated the request.

### Proof of Concept
1. Configure Shipit with two organizations, `OrgA` and `OrgB`, each with distinct `webhook_secret`s, and a tracked `Stack`/`Repository` for `OrgB/victim-repo` with continuous deployment enabled — mirroring the supported multi-org config in `test/dummy/config/secrets_double_github_app.yml`.
2. As an attacker who is a legitimate admin of `OrgA`'s GitHub App (and therefore knows `OrgA`'s `webhook_secret`), craft a `push` event JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "OrgA" },
    "full_name": "OrgB/victim-repo"
  }
}
```
3. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(OrgA_webhook_secret, body)>` and POST to `/webhooks` with header `X-Github-Event: push`.
4. `WebhooksController#verify_signature` resolves `repository_owner == "OrgA"`, fetches `OrgA`'s `GitHubApp`, and the signature check passes (since it was signed with `OrgA`'s real secret).
5. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("OrgB/victim-repo")` (unrelated to `OrgA`) and calls `stack.sync_github(expected_head_sha: ...)`, causing Shipit to sync/deploy a commit on `OrgB`'s stack triggered entirely by `OrgA`'s credentials.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))

**File:** lib/shipit.rb (L170-200)
```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
