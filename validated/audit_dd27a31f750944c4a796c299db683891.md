### Title
Webhook organization used to select the signature-verification secret is decoupled from the repository/organization the event handlers act on, enabling cross-tenant forged webhooks - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks which GitHub App configuration (and therefore which HMAC secret) to verify a webhook against using `repository_owner`, a value read directly out of the *unauthenticated* JSON body [1](#0-0) . That field is derived as `params.dig('repository','owner','login') || params.dig('organization','login')` [2](#0-1) . Once the signature "passes" (because it was computed with the secret belonging to whatever organization the attacker named in that field), every downstream `Handler` re-reads the *same untrusted body* but keys its mutations off a **different** field — `payload.dig('repository','full_name')` in the generic `Handler#repository_name` used by `PushHandler`/PR handlers [3](#0-2) , or `params.organization.login` in `MembershipHandler` [4](#0-3) . Nothing enforces that the organization used to authenticate the request equals the repository/organization the handler actually writes to.

Shipit explicitly supports multi-tenant configuration where several independent GitHub Apps (one per organization) share a single Shipit instance and its `config/secrets.yml`/`webhooks` endpoint [5](#0-4) , as documented in `docs/setup.md` "Using Multiple Github Applications" and exercised in `test/dummy/config/secrets_double_github_app.yml`. This is the exact analog of M-31: a privileged action (`setFeeRecipient`, gated by `onlyOwner`) is bound to one identity, while the exploitable consequence is reachable through a caller/field that was never actually checked against that identity.

### Finding Description
`Shipit.github(organization:)` resolves a distinct `GitHubApp` (and webhook secret) per organization key in `secrets.github` [5](#0-4) . `verify_signature` uses this to choose *which* secret must match the `X-Hub-Signature` header:

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(...)
``` [1](#0-0) 

`repository_owner` is attacker-controlled input from the raw JSON body, not anything cryptographically bound to the request:
```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [2](#0-1) 

If an attacker administers their own GitHub App on *any* organization configured in the same multi-tenant Shipit instance ("OrgA"), they legitimately know OrgA's `webhook_secret` and can sign an arbitrary JSON body with it. Because the body is fully attacker-crafted (this is not a real GitHub-originated webhook), they can set `repository.owner.login = "OrgA"` (so `verify_signature` selects and matches OrgA's real secret) while setting a *different* field — `repository.full_name` — to name a victim repository belonging to "OrgB", a completely different tenant on the same instance.

Every handler trusts `repository.full_name` (or `organization.login` for membership events) to decide what to mutate:
- `PushHandler` looks up stacks via `Repository.from_github_repo_name(repository_name)` (i.e. `repository.full_name`) and calls `stack.sync_github(expected_head_sha:)` for stacks it finds [6](#0-5) [3](#0-2) .
- Pull-request handlers (`OpenedHandler`, `ClosedHandler`, `LabeledHandler`, etc.) resolve `Repository.from_github_repo_name(params.repository.full_name)` and archive/unarchive/create `ReviewStack`s for it [7](#0-6) [8](#0-7) .
- `MembershipHandler` creates/updates a `Team` and adds/removes an arbitrary member based on `params.organization.login` and `params.member.login`, independent of `repository_owner` when the crafted payload supplies both a `repository` and a differing `organization` object [9](#0-8) .

The equality that should hold — `organization authenticated by verify_signature == organization/repository the handler writes to` — is never enforced anywhere in the controller or handler layer.

### Impact Explanation
This lets an attacker who only controls one tenant organization's GitHub App/webhook secret in a multi-tenant Shipit deployment forge signed-looking webhooks that mutate a victim tenant's data:
- Trigger `GithubSyncJob`/`sync_github` on a victim's `Stack` at will (`PushHandler`), which can feed into continuous-deployment and merge-queue logic for a repository the attacker does not own — an unauthorized deploy trigger.
- Archive/unarchive or force-create `ReviewStack`s (which provision/deprovision infrastructure) for a victim's repository via forged `pull_request` events.
- Manipulate `Team`/`Membership` records via forged `membership` events using a mismatched `organization.login`, which can affect `Shipit.github_teams` resolution (`Team.find_or_create_by_handle` matches on `organization`+`slug`) and thus escalate into the application's team-based authorization if a required team record does not yet exist locally.

These map to the required Critical/High categories: unauthorized deploy trigger, cross-repository writes, and potential escalation into `Shipit.github_teams` authorization.

### Likelihood Explanation
Requires the operator to run Shipit with the documented multi-organization GitHub App configuration (explicitly supported and documented) and for the attacker to control/administer at least one of the configured tenant organizations' GitHub App (i.e., know that org's `webhook_secret`) — this is a normal, low-privilege position for any of the instance's legitimate tenants, not a privileged Shipit account. No `ApiClient` token, session, or private key for the *victim* org is needed.

### Recommendation
After `verify_signature` succeeds, re-derive the organization/repository the handler is about to act on and assert it matches the organization whose secret was used to verify the signature (e.g., compare `repository.full_name`'s owner and `organization.login` against `repository_owner` before dispatching to handlers, rejecting mismatches). Alternatively, do not use attacker-supplied payload fields to select the verification key at all — route webhooks per-organization via distinct, pre-registered endpoint paths/config rather than trusting a JSON field to pick the secret.

### Proof of Concept
Assume a multi-tenant `secrets.yml` with `OrgA` (attacker-administered) and `OrgB` (victim), as in the supported schema shown in `docs/setup.md`/`test/dummy/config/secrets_double_github_app.yml`.

1. Attacker builds a `push` webhook JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<victim_commit_sha>",
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/victim-repo" }
}
```
2. Attacker signs the raw body with OrgA's real (known-to-them) `webhook_secret` and sets `X-Hub-Signature`.
3. `WebhooksController#verify_signature` computes `repository_owner = "OrgA"`, loads OrgA's `GitHubApp`, and `verify_webhook_signature` succeeds because the attacker did sign with OrgA's secret [1](#0-0) .
4. `PushHandler` is invoked with the same body; `repository_name` reads `full_name` = `"OrgB/victim-repo"` [3](#0-2) , resolves the victim's `Stack`, and calls `stack.sync_github(expected_head_sha: params.after)` [10](#0-9)  — a sync/deploy-relevant action on a repository the attacker never had legitimate access to, using only credentials for an unrelated tenant organization.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
    end
  end
end
