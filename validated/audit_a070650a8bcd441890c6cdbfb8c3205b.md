### Title
`membership` webhook org used for `Team.organization` diverges from org used for signature verification, enabling `Shipit.github_teams` privilege escalation - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/membership_handler.rb`)

### Summary
`WebhooksController#verify_signature` selects which org's `webhook_secret` to check the request against using `params.dig('repository','owner','login') || params.dig('organization','login')`, while `MembershipHandler#find_or_create_team!` unconditionally trusts `params.organization.login` to set the newly created `Team#organization`. Nothing forces these two values to be equal, so a request that authenticates as one org can plant a `Team` row scoped to a different, unrelated org.

### Finding Description
The claimed binding is: `org_used_to_verify_signature == params['organization']['login']` (the org written into `Team#organization`). This binding does not hold.

- `WebhooksController#verify_signature` computes the authenticating org via `repository_owner`, which prefers `params.dig('repository','owner','login')` and only falls back to `params.dig('organization','login')` when no `repository` key is present: [1](#0-0) 
- `Shipit::Webhooks::Handlers::MembershipHandler#find_or_create_team!` always uses `params.organization.login` (a completely different top-level key of the same JSON body) to create the `Team`, with no cross-check against whatever org string was used to select the verifying `GitHubApp`: [2](#0-1) 
- Real GitHub `membership` events never include a top-level `repository` key, so under normal traffic both fields happen to coincide. But `WebhooksController#create` does `JSON.parse(request.raw_post)` with no schema restricting extra top-level keys before signature verification, and `MembershipHandler`'s `ExplicitParameters` schema only requires `action`, `team`, `organization`, `member` - it does not forbid an attacker from adding an arbitrary `repository` key: [3](#0-2) [4](#0-3) 

Exploit flow: attacker POSTs to `/webhooks` with `X-Github-Event: membership`, a valid `X-Hub-Signature` computed against an org they legitimately control on this multi-tenant Shipit instance ("attacker-org"), and a body containing a spoofed `repository: {owner: {login: "attacker-org"}}` (so `verify_signature` authenticates against attacker-org's secret) plus `organization: {login: "shopify"}`, `team: {id: <fresh id>, slug: <slug matching a Shipit.github_teams entry>, name, url}`, `member: {login: <attacker>}`, `action: "added"`. `verify_signature` succeeds against attacker-org's own secret. `MembershipHandler#find_or_create_team!` then creates a brand-new `Team` row with `organization: 'shopify'` and the attacker-chosen `github_id`/slug via `Team.find_or_create_by!(github_id: params.team.id)`, and `team.add_member(member)` adds the attacker's `User` to it.

Later, when `Shipit.github_teams` is (re)computed, it resolves each configured handle by `organization`+`slug` lookup: [5](#0-4) [6](#0-5) 
Because `find_or_create_by_handle` does `find_by(organization:, slug:)` first, it matches the attacker's fabricated row (same organization + slug as the configured team) before ever calling GitHub, returning that row's `id`. `User#authorized?` then grants access because the attacker's `User` is a member of that exact `Team.id`: [7](#0-6) 

None of the existing guards prevent this: `verify_signature` only checks the HMAC against whichever org string it derives, it never re-derives or compares that org to `MembershipHandler`'s `params.organization.login`; `drop_unhandled_event` and the `ExplicitParameters` schema only validate presence/types of required fields, not that extraneous keys are absent or that organization values agree; there is no `force_github_authentication`/`require_permission!` involved in webhook ingestion at all.

### Impact Explanation
A successful request creates an unauthorized `Shipit::Team` row scoped to a privileged organization ('shopify') and grants the attacker membership in it, without any interaction from that organization. If the slug collides with an entry configured in `Shipit.github_teams`, this directly escalates the attacker into the authorization set checked by `User#authorized?`, granting full Shipit access (viewing/deploying stacks, etc.) gated on org-team membership. This matches the High/Critical category "escalation into `Shipit.github_teams` authorization" / "authentication bypass," and is repeatable against any organization name and any team-id/slug combination the attacker chooses, as long as the attacker has authenticated access to *some* org configured on the same multi-tenant Shipit instance to pass `verify_signature`.

### Likelihood Explanation
Preconditions: (1) the Shipit instance is multi-tenant, i.e. multiple orgs are configured in `secrets.github` (documented pattern in `docs/setup.md`) so the attacker can legitimately authenticate a webhook under their own org's secret; (2) the target org ('shopify') has entries in `Shipit.github_teams` whose `organization`/`slug` the attacker can guess or know (these are often documented/well-known team names); (3) `Shipit.github_teams` has not already been memoized with the real team before the forged row is created (first-access race) - or the real team's `github_id` differs from the attacker's chosen fresh id so `find_or_create_by!(github_id:)` doesn't collide, and `find_by(organization:, slug:)` matches the attacker's row first. Given these, attacker cost is a single crafted HTTP POST with a signature computed from a secret they already know for their own org - no privileged secrets of the target are needed. This is fully repeatable.

### Recommendation
In `MembershipHandler#find_or_create_team!` (and generally in `WebhooksController#repository_owner`), require that the org used to authenticate the webhook signature equals the org referenced by the payload for that event type. Concretely: pass the authenticated `repository_owner` value down into each handler (e.g., via the payload or an explicit parameter) and validate it against `params.organization.login` before creating/updating a `Team`; reject the request (422) on mismatch. Additionally, harden `repository_owner` so it is not influenced by attacker-controlled keys inconsistent with the actual event type (e.g., don't allow a `repository` key to override org selection for org-scoped events like `membership`).

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (new test)
test ":membership webhook verified for one org can create a Team scoped to another org" do
  # Simulate a multi-tenant setup where attacker-org's webhook secret is known/used for signing,
  # but organization.login in the payload claims to be 'shopify'.
  GithubHook.any_instance.stubs(:verify_signature).returns(true) # signature succeeds for attacker-org

  @request.headers['X-Github-Event'] = 'membership'

  forged_payload = {
    action: 'added',
    team: { id: 999_999, name: 'Fake Team', slug: 'developers', url: 'https://example.com' },
    organization: { login: 'shopify' },          # trusted org written into Team#organization
    member: { login: 'attacker' },
    repository: { owner: { login: 'attacker-org' } } # org actually used by verify_signature
  }.to_json

  assert_difference -> { Shipit::Team.count }, 1 do
    post :create, body: forged_payload, as: :json
    assert_response :ok
  end

  team = Shipit::Team.find_by(github_id: 999_999)
  assert_equal 'shopify', team.organization
  assert_equal 'developers', team.slug
  assert team.members.exists?(login: 'attacker')

  # Assert the binding is broken: authenticated org != org written to Team
  # verified_org (attacker-org) != team.organization (shopify)
  refute_equal 'attacker-org', team.organization
end
```
This demonstrates the write of `Team#organization = 'shopify'` succeeding under a request whose signature was verified for a different org ('attacker-org'), with no cross-check anywhere in the call path.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([

        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
