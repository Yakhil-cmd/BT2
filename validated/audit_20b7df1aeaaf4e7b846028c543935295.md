### Title
Membership webhook handler binds attacker-controlled `team.id` to existing `Team` rows without validating webhook-verifying organization ownership, allowing self-escalation into privileged `Shipit.github_teams` - (File: app/models/shipit/webhooks/handlers/membership_handler.rb)

### Summary
`Shipit::Webhooks::Handlers::MembershipHandler#find_or_create_team!` looks up a `Team` solely by attacker-controlled `params.team.id` (github_id) and never checks that the `organization` which the webhook's signature was verified against actually owns that `Team`. Combined with `WebhooksController#verify_signature`, which falls back to `organization.login` for signature-org resolution and trivially "verifies" (returns `true`) when that organization has no `webhook_secret` configured, an attacker can post a forged `membership` webhook that adds themselves as a member of any pre-existing `Team` row (including one referenced in `Shipit.github_teams`), by simply guessing/using that team's numeric `github_id`.

### Finding Description
The broken binding is: `organization_that_verified_signature (params.organization.login, resolved via repository_owner fallback in WebhooksController#repository_owner) == organization_that_owns_the_target_Team (Team#organization for the row matched by github_id)`. These two are never asserted equal.

Path:
1. `WebhooksController#repository_owner` (app/controllers/shipit/webhooks_controller.rb:59-62) falls back to `params.dig('organization', 'login')` when no `repository` key is present in the payload — true for `membership` events, which the attacker controls entirely.
2. `verify_signature` (webhooks_controller.rb:24-49) calls `Shipit.github(organization: repository_owner)` and `verify_webhook_signature`. In `GitHubApp#verify_webhook_signature` (lib/shipit/github_app.rb:76-83), `return true unless webhook_secret` — i.e., if the attacker names an organization with no configured `webhook_secret`, the signature check passes unconditionally, with no cryptographic binding to any real GitHub org.
3. `MembershipHandler#process`/`#find_or_create_team!` (app/models/shipit/webhooks/handlers/membership_handler.rb:22-43) does `Team.find_or_create_by!(github_id: params.team.id) { |team| team.organization = params.organization.login }`. The block only runs on *creation*; if a `Team` with that `github_id` already exists (e.g., a real privileged team bound to `organization: "shopify"`), it is fetched as-is — `organization` is never re-validated against `params.organization.login`.
4. `team.add_member(member)` (app/models/shipit/team.rb:41-43) then appends `User.find_or_create_by_login!(params.member.login)` — an attacker-chosen GitHub login — to that team's `members`.
5. `User#authorized?` (app/models/shipit/user.rb:80-82) checks `teams.where(id: Shipit.github_teams.map(&:id)).exists?`. If the mutated `Team` is one of `Shipit.github_teams`, the attacker is now authorized.

No existing guard catches this: `drop_unhandled_event` only checks the event is registered; `ExplicitParameters` schema only validates types/presence, not cross-field integrity; `verify_signature` verifies against the wrong/absent-secret organization by design of the fallback; `Team.find_or_create_by!` performs no ownership check on fetch.

### Impact Explanation
An unauthenticated internet attacker can add their own GitHub-login-derived `User` record as a `Membership` of any existing `Team` row by guessing/enumerating its numeric `github_id` (small integers, easily brute-forced or observed via public GitHub team IDs) and naming, in the payload, any GitHub organization that has not configured a `webhook_secret` in the host's Shipit config. If that `Team` is part of `Shipit.github_teams`, the attacker becomes `authorized?` for the entire Shipit instance — an authorization bypass that can cascade into triggering deploys/rollbacks/merges gated by `authorized?`/`require_permission!` elsewhere in the app. This is repeatable against any Team by github_id and is not scoped to a single tenant; it is a cross-tenant authorization escalation. This matches "High - escalation into `Shipit.github_teams` authorization."

### Likelihood Explanation
Preconditions are attacker-cheap: (1) the Shipit deployment must have at least one configured GitHub organization with no `webhook_secret` set (common in dev/staging configs or orgs onboarded without webhook secrets) — this determines the "verifying" org, not the target; (2) attacker needs the numeric `github_id` of the target `Team`, obtainable via GitHub's public team API/UI in many cases or by brute-force over a small ID space; (3) no session, API token, or GitHub secret is required. This is entirely feasible from an unauthenticated HTTP client and is fully repeatable.

### Recommendation
In `MembershipHandler#find_or_create_team!`, after fetching an existing `Team`, verify `team.organization == params.organization.login` (or equivalently, verify the org used to authenticate the webhook signature matches `team.organization`) before mutating membership; raise/drop the event on mismatch. More generally, `WebhooksController#verify_signature` should not silently accept an unsigned webhook for the resolved organization if that organization has no secret configured for events that mutate authorization-relevant state — consider requiring `webhook_secret` to be present for any org handling `membership` events, and never accept a webhook whose declared organization differs from the actual resource (`Team#organization`) being modified.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/membership_handler_test.rb
test "membership webhook cannot hijack an existing Team bound to another org" do
  privileged_team = shipit_teams(:shopify) # or Team.create!(organization: 'shopify', github_id: 48, slug: 'ops', name: 'Ops', api_url: 'https://api.github.com/teams/48')
  attacker_login = 'attacker'

  payload = {
    'action' => 'added',
    'team' => { 'id' => privileged_team.github_id, 'name' => privileged_team.name, 'slug' => privileged_team.slug, 'url' => privileged_team.api_url },
    'organization' => { 'login' => 'unrelated-no-secret-org' },
    'member' => { 'login' => attacker_login }
  }

  # Simulates verify_signature passing because 'unrelated-no-secret-org' has no webhook_secret configured
  Shipit::Webhooks::Handlers::MembershipHandler.call(payload)

  attacker_user = Shipit::User.find_by!(login: attacker_login)

  # Binding check: verifying org != team's actual org, yet membership was still written
  assert_not_equal 'unrelated-no-secret-org', privileged_team.organization
  assert Shipit::Membership.exists?(team: privileged_team, user: attacker_user)
end
```
This demonstrates a `Membership` row created on a `Team` owned by `organization: 'shopify'` while the webhook was only "verified" (i.e., not verified at all) under an unrelated organization with no `webhook_secret`.
