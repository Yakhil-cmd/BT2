### Title
`provision?` bypasses `review_stacks_enabled` for `allow_with_label`/`prevent_with_label` behaviors due to `&&`/`||` precedence - (File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb)

### Summary
`PullRequest::OpenedHandler#provision?` intends `review_stacks_enabled` to gate all provisioning, but due to Ruby operator precedence it only gates the `allow_all` clause. A repository with `review_stacks_enabled: false` but `provisioning_behavior: allow_with_label` (or `prevent_with_label`) will still create a `ReviewStack` and enqueue provisioning when a PR carries (or lacks) the configured label.

### Finding Description
The claimed binding is: `repository.review_stacks_enabled == true` must hold for every path reaching `ReviewStackAdapter#create!`. Tracing `provision?`:

```ruby
repository.review_stacks_enabled &&
  repository.provisioning_behavior_allow_all? ||
  (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
  (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
```
Ruby parses this as `(A && B) || (C && D) || (E && F)`, so with `review_stacks_enabled = false`, `provisioning_behavior = allow_with_label`, and a PR labeled with `provisioning_label_name`, the middle clause `(C && D)` evaluates to `true` independent of `A`. `provision?` returns `true`, `process` calls `ReviewStackAdapter#find_or_create!`, which calls `create!` unconditionally (no re-check of `review_stacks_enabled`), creating a `ReviewStack` scoped to `repository.review_stacks` and enqueuing it via `ReviewStackProvisioningQueue.add(stack)`, which downstream leads to task execution against the attacker-controlled branch/commit. Comparing with the sibling `LabeledHandler#respond_to_label_change?`, that method correctly parenthesizes `repository.review_stacks_enabled && (archive? || unarchive?)`, confirming the intended binding and that `OpenedHandler` is the outlier with a genuine logic defect. No other guard (`params` schema, webhook signature checks, `drop_unhandled_event`) re-validates `review_stacks_enabled` downstream; the divergence is real and unguarded.

### Impact Explanation
This causes a `ReviewStack` and its provisioning pipeline to run for a repository whose owner explicitly disabled review-stack provisioning (`review_stacks_enabled: false`), executing whatever `shipit.yml`/deploy steps that pipeline runs on the PR's head branch/commit. This is a logic bug that undermines the repository owner's own configuration intent, but it is confined to the repository that itself has this specific misconfiguration (`review_stacks_enabled: false` combined with `provisioning_behavior: allow_with_label`/`prevent_with_label`) — it does not let an attacker cross into a different repository's or tenant's stack, since `ReviewStackAdapter` is scoped by `repository.review_stacks` derived from `params.repository.full_name`, and stack creation still requires the PR to originate from a repository already onboarded to Shipit with a webhook configured. It is not an authentication bypass and does not exfiltrate credentials on its own merit beyond what the review-stack provisioning pipeline already exposes to any accepted PR under `allow_all` mode for that same repo.

### Likelihood Explanation
Requires a specific repository configuration: `review_stacks_enabled: false` AND `provisioning_behavior_allow_with_label` (or `prevent_with_label`) — an unusual combination since disabling `review_stacks_enabled` is generally meant to fully disable the feature. The attacker also needs the ability to open a PR against that repository and apply/omit a label, meaning they need at least fork/PR access to a repo already connected to Shipit via a legitimately configured webhook (signature verification is not bypassed — the webhook must be validly signed, which requires the repository to already be integrated with Shipit).

### Recommendation
Parenthesize the full disjunction so `review_stacks_enabled` gates all clauses, matching `LabeledHandler`:
```ruby
def provision?
  repository.review_stacks_enabled &&
    (
      repository.provisioning_behavior_allow_all? ||
      (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
      (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
    )
end
```
