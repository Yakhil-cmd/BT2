### Title
`writeServiceChainTxReceipts` Ignores Receipt Execution Status, Permanently Corrupting Anchored Block State and Silently Discarding Failed Bridge Handle Transactions — (File: `node/sc/sub_bridge_handler.go`)

---

### Summary

`writeServiceChainTxReceipts` in `node/sc/sub_bridge_handler.go` processes receipts returned from the parent chain for service-chain-originated transactions (both chain-data-anchoring and value-transfer handle txs). It never inspects `receipt.Status`. A reverted parent-chain transaction is treated identically to a successful one: the anchored block number is advanced and the transaction is evicted from the bridge pool regardless of whether execution actually succeeded.

---

### Finding Description

`handleParentChainReceiptResponseMsg` decodes the receipt batch sent by the parent-chain peer and immediately delegates to `writeServiceChainTxReceipts`:

`receipt.Status` (populated by the EVM and present in `types.ReceiptForStorage`) is **never read**. Two distinct broken invariants follow:

**Path 1 — Anchoring transactions**

When an anchoring transaction reverts on the parent chain (e.g., out-of-gas, base-fee rejection, or any revert), `WriteReceiptFromParentChain` and `WriteAnchoredBlockNumber` are still called with the data from the failed transaction. The child chain's persistent `AnchoredBlockNumber` is advanced to a block that was never actually anchored. The comment in `handleParentChainInvalidTxResponseMsg` explicitly acknowledges that anchoring has no automatic retry mechanism:

```go
// Remove the tx from the pool. For value transfer txs, Value Transfer Recovery
// will retry if enabled. For anchoring txs, there is no automatic retry mechanism;
``` [3](#0-2) 

Once `AnchoredBlockNumber` is advanced past the un-anchored block, the anchoring manager will never re-anchor it, permanently breaking the child-chain security guarantee.

**Path 2 — Value-transfer handle transactions**

When a `handleERC20Transfer` / `handleKLAYTransfer` / `handleERC721Transfer` call reverts on the parent chain (e.g., insufficient bridge balance in lock mode, or a mint failure in MintBurn mode), the handle transaction is still evicted from the bridge pool. If Value Transfer Recovery (`VTRecovery`) is disabled, the transfer is permanently lost: tokens were already burned on the child chain (MintBurn mode) or locked, but the corresponding mint/release on the parent chain never occurred.

The MintBurn burn on the source side happens unconditionally at request time:

```go
if modeMintBurn {
    ERC20Burnable(_tokenAddress).burn(_value);
}
``` [4](#0-3)

### Impact Explanation

| Scenario | Corrupted Value | Asset Impact |
|---|---|---|
| Anchoring tx reverts on parent chain | `AnchoredBlockNumber` advanced past un-anchored block | Permanent anchoring gap; child-chain blocks never provably committed to parent chain |
| Value-transfer handle tx reverts on parent chain (VTR disabled) | Bridge pool entry removed; no retry | Tokens burned on child chain, never minted/released on parent chain — permanent fund loss |
| Value-transfer handle tx reverts on parent chain (VTR enabled) | Bridge pool entry removed prematurely | VTR detects gap via `LowerHandleNonce` and retries; mitigated but pool state is still incorrect |

---

### Likelihood Explanation

A parent-chain transaction can revert for several non-privileged reasons that are entirely within normal operation:

- The parent-chain bridge contract has insufficient KLAY/ERC20 balance (lock mode).
- The ERC20 `mint()` call fails (MintBurn mode) — e.g., minter role revoked or token paused.
- The parent-chain base fee spikes above the gas price embedded in the bridge transaction, causing the transaction to be dropped and re-submitted with a stale gas price.
- Any transient parent-chain congestion that causes the transaction to revert.

None of these require privileged access. The child chain operator's bridge account submits these transactions automatically.

---

### Recommendation

Check `receipt.Status` before acting on a receipt. Treat any non-`ReceiptStatusSuccessful` status as a failure:

```go
func (sbh *SubBridgeHandler) writeServiceChainTxReceipts(bc *blockchain.BlockChain, receipts []*types.ReceiptForStorage) {
    for _, receipt := range receipts {
        txHash := receipt.TxHash
        if tx := sbh.subbridge.GetBridgeTxPool().Get(txHash); tx != nil {
            // Only process successful receipts
            if receipt.Status != types.ReceiptStatusSuccessful {
                logger.Error("bridge tx failed on parent chain, will not remove from pool",
                    "txHash", txHash.String(), "status", receipt.Status)
                continue  // leave in pool for retry / operator intervention
            }
            if tx.Type().IsChainDataAnchoring() {
                // ... existing anchoring logic ...
                sbh.WriteReceiptFromParentChain(decodedData.GetBlockHash(), (*types.Receipt)(receipt))
                sbh.WriteAnchoredBlockNumber(decodedData.GetBlockNumber().Uint64())
            }
            sbh.subbridge.GetBridgeTxPool().RemoveTx(tx)
        }
    }
}
```

For anchoring transactions specifically, a failed receipt must never advance `AnchoredBlockNumber`, and a retry or alerting mechanism should be introduced since none currently exists.

### Proof of Concept

1. Deploy a service chain with anchoring enabled and a bridge pair in MintBurn mode.
2. Revoke the minter role from the parent-chain bridge contract so that `handleERC20Transfer` will revert.
3. Initiate an ERC20 transfer from child to parent chain. The child-chain bridge burns the tokens and emits `RequestValueTransfer`.
4. The child-chain bridge operator sends `handleERC20Transfer` to the parent chain; the call reverts (minter role missing). The receipt has `Status = 0`.
5. The parent chain returns the failed receipt to the child chain via `ServiceChainReceiptResponseMsg`.
6. `writeServiceChainTxReceipts` receives the receipt, **does not check `receipt.Status`**, and calls `GetBridgeTxPool().RemoveTx(tx)`.
7. With VTR disabled: the handle transaction is gone from the pool. The user's tokens are burned on the child chain and never minted on the parent chain — permanent loss.
8. Separately, trigger an anchoring transaction that reverts on the parent chain. Observe that `WriteAnchoredBlockNumber` is still called, advancing the anchored block number past the un-anchored block. Subsequent anchoring skips that block permanently. [2](#0-1) [1](#0-0)

// writeServiceChainTxReceipts writes the received receipts of service chain transactions.
func (sbh *SubBridgeHandler) writeServiceChainTxReceipts(bc *blockchain.BlockChain, receipts []*types.ReceiptForStorage) {
	for _, receipt := range receipts {
		txHash := receipt.TxHash
		if tx := sbh.subbridge.GetBridgeTxPool().Get(txHash); tx != nil {
			if tx.Type().IsChainDataAnchoring() {
				data, err := tx.AnchoredData()
				if err != nil {
					logger.Error("failed to get anchoring data", "txHash", txHash.String(), "err", err)
					continue
				}
				decodedData, err := types.DecodeAnchoringData(data)
				if err != nil {
					logger.Warn("failed to decode anchoring tx", "txHash", txHash.String(), "err", err)
					continue
				}
				sbh.WriteReceiptFromParentChain(decodedData.GetBlockHash(), (*types.Receipt)(receipt))
				sbh.WriteAnchoredBlockNumber(decodedData.GetBlockNumber().Uint64())
			}
			// TODO-Kaia-ServiceChain: support other tx types if needed.
			sbh.subbridge.GetBridgeTxPool().RemoveTx(tx)
		} else {
			logger.Trace("received service chain transaction receipt does not exist in sentServiceChainTxs", "txHash", txHash.String())
		}
		logger.Trace("received service chain transaction receipt", "anchoring txHash", txHash.String())
	}
}
