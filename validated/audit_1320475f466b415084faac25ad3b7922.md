### Title
AA payment to multiple recipients of a `spender_attested` asset bounces (losing/refunding all funds) if only one output address loses its attestation - ([File: validation.js])

### Summary
When an Autonomous Agent (AA) sends a single `payment` message with several outputs of a `spender_attested` custom asset, `validatePaymentInputsAndOutputs` requires that **every** output address be attested before the unit can be accepted. If even one recipient among many is not (or is no longer) attested — the functional analog of being "blacklisted" — the entire payment message, and therefore the whole AA response unit, is rejected. This bounces the AA's response and reverts all state changes for that trigger, so all the other, perfectly legitimate recipients in the same message lose their payout along with the "blacklisted" one.

### Finding Description
`validatePaymentInputsAndOutputs` collects all output addresses (`arrOutputAddresses`) of a payment message and, for `spender_attested` assets, checks that the number of attested output addresses equals the total number of output addresses: [1](#0-0)

This is an all-or-nothing check on the whole message: it is not per-output. `filterAttestedAddresses` only returns addresses that currently hold a valid, un-superseded attestation from one of the asset's designated attestors: [2](#0-1) 

Attestors can freely stop attesting an address (the exact analog of a blacklist/deny-list operated by a trusted issuer such as a KYC/AML attestor), which instantly makes that address fail this check on any future payment.

When an AA composes and sends such a payment (e.g., distributing a `spender_attested` asset to several parties in one `outputs` array), `sendUnit` builds the message, calls `validateAndSaveUnit`, and if validation fails for any reason — including "some output addresses are not attested" — it calls `bounce(err)`, which discards the state update and refunds only the trigger's own bytes, not the intended asset distribution to the other, still-attested recipients: [3](#0-2) [4](#0-3) 

Because `payload.outputs.sort(sortOutputs)` merges all recipients of the same asset into a single payment message whenever possible (`mergeMessagesAndOutputs`), an AA that intends to pay N parties in one round can easily end up with several distinct recipients bundled into one message, all of which fail together if just one of them is unattested.

### Impact Explanation
Any AA (or protocol built on AAs) that distributes a `spender_attested` asset to multiple addresses in one payment message is exposed to a denial-of-funds condition: revocation or non-issuance of an attestation for a single recipient causes the AA's entire response to bounce, so:
- The intended distribution never happens, even for addresses that are properly attested.
- Depending on the AA's logic, the state changes that were supposed to record the payout (e.g., decrementing balances, marking an escrow as settled) are rolled back, and the AA can be left in a state where it keeps re-attempting (or is stuck expecting) a payment to an address that will never be attested again — permanently freezing those specific funds/logic path for all other honest counterparties in that AA.
- This maps directly to the reported bug class: a single "blacklisted" (here: de-attested) participant blocks fund delivery to everyone else in the same transaction.

### Likelihood Explanation
`spender_attested` is a first-class, documented asset feature intended for exactly this kind of compliance/whitelisting use case, and it is explicitly supported inside AAs (asset issuance and asset definitions are validated for AA use in `aa_validation.js`). Any AA-based product (subscription payouts, dividend/airdrop distributor, escrow, DAO treasury) built on top of a `spender_attested` asset and paying multiple parties per trigger is naturally susceptible; the attestor merely needs to withdraw attestation from one address (a normal, expected administrative action for compliance assets) to trigger the freeze.

### Recommendation
- In `validatePaymentInputsAndOutputs`, do not fail the whole payment message when some—but not all—output addresses are unattested; either reject only the non-compliant outputs (not currently supported by the protocol’s atomic-message model) or require AA/wallet authors to send one output per message/unit per recipient so that a single non-attested recipient cannot block payments to others.
- Alternatively, provide AAs a way to query attestation status before composing outputs (e.g., an `is_attested`-style getter) so contract authors can split payments defensively, and document this pitfall prominently for `spender_attested` asset issuers and AA developers.
- Consider making `filterAttestedAddresses`/`validatePaymentInputsAndOutputs` return per-address results to calling AA logic (via a bounce reason that names the offending address) so contract authors can implement retry/skip logic instead of losing the whole batch.

### Proof of Concept
1. Define a custom asset with `spender_attested: true` and a designated attestor address.
2. Deploy an AA whose response, for a given trigger, sends one `payment` message with multiple outputs of this asset to addresses `A`, `B`, and `C`.
3. Have the attestor attest `A` and `C` but not `B` (or attest `B` and later have the attestor stop re-attesting it, simulating a "blacklist").
4. Trigger the AA. `validatePaymentInputsAndOutputs` computes `arrOutputAddresses = [A, B, C]`; `filterAttestedAddresses` returns only `[A, C]`; the length mismatch causes `cb("some output addresses are not attested")`, which propagates up to `validateAndSaveUnit`'s error callback and calls `bounce(err)` in `aa_composer.js`.
5. Observe that the AA response bounces: `A` and `C` receive nothing despite being fully compliant, and the AA's state changes intended to record the distribution are discarded.
