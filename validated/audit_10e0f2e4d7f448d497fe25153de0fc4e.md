### Title
Block-Revenue-Sharing Rewards Silently Dropped When `total_active_stake == 0` in `calculate_block_reward()` - (File: `runtime/src/bank/partitioned_epoch_rewards/calculation.rs`)

### Summary
`calculate_block_reward()` mirrors the exact bug class described in the external report: a reward pool is split proportionally by dividing by a "total supply"-like denominator, and when that denominator is `0` the function short-circuits to `0` instead of preserving or otherwise accounting for the funds, silently discarding the vote account's accumulated `pending_delegator_rewards` for that epoch.

### Finding Description
`calculate_block_reward()` distributes a vote account's `pending_delegator_rewards` (SIMD-0123 block-revenue-sharing pool, funded via `DepositDelegatorRewards`) to each of its delegated stake accounts proportionally to `stake / total_active_stake`: [1](#0-0) 

`total_active_stake` is looked up from `reward_epoch_delegated_stakes.delegated_stakes` with `.unwrap_or(0)`, and the code explicitly branches: `if total_active_stake == 0 { 0 } else { ... }`. This is structurally identical to the reported `LiquidityGauge._checkpoint()` bug: a reward pool (`pending_delegator_rewards` ≈ `d_reward`) is divided by a denominator that represents the total active/staked amount (≈ `erc4626.erc20.totalSupply`); when that denominator is zero, the reward share collapses to `0` for every claimant instead of being preserved for later or redistributed.

This function is invoked once per stake delegation inside `calculate_stake_rewards_and_commissions()`: [2](#0-1) 

The comment at lines 221-226 acknowledges the awareness that `stake` can exceed `total_active_stake` during recalculation, and the code's fallback is to zero out the reward instead of any compensating accounting (e.g., re-queuing the block reward against `pending_delegator_rewards`, or falling back to an even split). There is no code path found (in the vote program's `pending_delegator_rewards` accounting, `programs/vote/src/vote_state/handler.rs` and related modules) that decrements `pending_delegator_rewards` proportionally only for what was actually distributed — `add_pending_delegator_rewards()` is the only mutator located during this investigation: [3](#0-2) 

I could not locate the exact reset/decrement logic invoked after `calculate_block_reward()` returns to confirm precisely how (or whether) `pending_delegator_rewards` is reduced when the computed share is `0`. This is a genuine gap in my analysis: it is possible the funds are merely deferred (retried next epoch once `total_active_stake` becomes non-zero) rather than permanently lost, which would make the impact considerably milder than the reported Vyper bug. I was not able to verify this with the tools available.

### Impact Explanation
If `total_active_stake == 0` is reachable for a `vote_pubkey` that still has stake delegations recorded in `stake_delegations` (e.g., delegated stake that has fully deactivated by the end of the AG reward epoch, matching the code's own acknowledgment that `stake` can diverge from `reward_epoch_delegated_stakes`), every stake account delegated to that vote account receives `0` block reward that epoch even though the vote account holds real, already-deposited lamports in `pending_delegator_rewards`. This is a misattribution/loss-of-rewards condition: the block-revenue-sharing pool intended for delegators is not paid out and (per my incomplete review) may not be properly re-queued, unlike the guarded `points == 0` / `point_value.points == 0` cases which are explicitly handled with `skip_reward()`/`SkippedReason` semantics elsewhere in `redeem_rewards()` (see `runtime/src/inflation_rewards/mod.rs:280-298` for contrast).

### Likelihood Explanation
Low-to-moderate. It requires a specific edge condition — a vote account whose SIMD-0123 delegated-stake mapping (`reward_epoch_delegated_stakes.delegated_stakes`) reports `0` for a `vote_pubkey` while stake accounts still reference it in `stake_delegations` — which can occur during the recalculation path noted in the code's own comments about stake activation timing mismatches. It does not require any privileged/validator role to trigger; it is purely a function of stake (de)activation timing relative to epoch boundaries, which any staker's deactivation schedule can influence.

### Recommendation
1. Confirm (via a Devin session with full repo access) whether and how `pending_delegator_rewards` is decremented after `calculate_block_reward()` is computed, to determine if the `total_active_stake == 0` branch causes permanent loss or merely deferred payment.
2. If it is permanent loss, guard the payout so that the vote account's `pending_delegator_rewards` is not implicitly forfeited when `total_active_stake == 0` — e.g., skip decrementing/consuming the pool for that epoch and retry in a later epoch, or explicitly route unattributed funds to a well-defined destination (e.g., leave them in `pending_delegator_rewards` untouched, as is presumably intended, and confirm this invariant with a regression test similar to `test_calculate_block_reward_specific` at `runtime/src/bank/partitioned_epoch_rewards/calculation.rs:4320-4332` that also asserts `pending_delegator_rewards` is preserved (not silently reset) when `total_active_stake == 0`.

### Proof of Concept
Not independently confirmed with a runnable reproduction, since I could not trace the full lifecycle of `pending_delegator_rewards` to establish whether zeroed distributions are retried or permanently dropped. The clearest, verifiable code evidence is the guard itself: [4](#0-3) 
combined with the existing unit test demonstrating the `0`-reward output for `total_stake == 0`: [5](#0-4) 

Given the incomplete confirmation of downstream accounting, this should be treated as a **candidate** finding requiring further investigation in a full-repo session rather than a fully proven vulnerability.
