## Title
Alpenglow per-validator reward denominator counts stake ineligible for this epoch's credits, diluting rewards for eligible delegators - (File: `runtime/src/inflation_rewards/points.rs`, `runtime/src/stakes.rs`)

### Summary
This is the same reward-dilution bug class as the Canto Liquidity Mining report: a shared "total weight" denominator is computed independently of the per-participant eligibility check used for the numerator, so any participant that is ineligible for this epoch's rewards still inflates the denominator and dilutes the payout of eligible participants.

### Finding Description
For Alpenglow reward epochs, per-stake reward points are computed in `calculate_alpenglow_points`: [1](#0-0) 

`earned_points = earned_credits * stake_amount / total_stake`, where `total_stake` is looked up from `RewardEpochDelegatedStakes.delegated_stakes` for the voter [2](#0-1) .

`earned_credits` is computed by `calc_earned_credits`, which returns **0** whenever a stake's `credits_observed` already meets or exceeds the epoch's `final_epoch_credits` — i.e., the delegation was activated/redelegated late relative to this reward epoch and is not entitled to any of this epoch's credits: [3](#0-2) 

However, the denominator `total_stake` (`RewardEpochDelegatedStakes.delegated_stakes`) is built completely independently, in `Stakes::calculate_activated_stake`, by summing `activation_status.effective` for every stake delegation to a voter — with **no eligibility filter based on credits/observed state**: [4](#0-3) 

So a stake delegation that is "effective" (has nonzero warmed-up stake for the rewarded epoch) but earns **zero** credits this epoch (because its `credits_observed` was already set to/above the vote account's current credit total, e.g. from a recent re-delegation) still contributes its full `stake_amount` to `total_stake`, while contributing `0` to the numerator sum for that same voter. This is structurally identical to the Canto bug: the denominator ("total liquidity time weight") is not restricted to the subset of participants meeting reward conditions ("liquidity time weight of the pool that meets the reward conditions"), so eligible delegators effectively receive `earned_credits * stake_amount / total_stake` with an inflated `total_stake`, i.e. less than their true proportional share of the vote account's earned lamports.

By contrast, the Tower path does not have this defect: its network-wide `point_value.points` denominator is computed by summing the *same* per-stake eligibility-aware `calculate_points_for_tower` used for the numerator (see `calculate_reward_points_partitioned`), so ineligible stakes contribute 0 to both sides consistently: [5](#0-4) 

Only the Alpenglow path uses a separately-computed, eligibility-blind `total_stake`.

### Impact Explanation
Delegators whose stake is actively earning credits with a vote account can receive systematically reduced Alpenglow inflation rewards whenever other delegations to the same voter are "effective" (warmed-up) but not credit-eligible for the epoch (e.g., stake that was recently redelegated to that voter and inherited a `credits_observed` at/above the current vote credit tally). This is a misattribution of rewards among stakers of the same validator: the eligible staker's payout share is computed against an inflated denominator, so lamports that should flow to them are effectively withheld/lost rather than paid to anyone. This falls under "misattributed rewards" in the reward distribution path, reachable by ordinary unprivileged delegators without any validator/operator privilege — simply by staking to a validator that also has another delegator whose stake is warmed up but not credit-eligible this epoch.

### Likelihood Explanation
This requires only normal, permissionless staking operations (e.g., someone delegating/redelegating stake to a validator such that their `credits_observed` starts at or above the vote account's current credit value for that epoch) coexisting with another delegator to the same validator who is actively earning credits. This is a plausible, commonly occurring stake-delegation pattern (not an attacker-crafted edge case), so it can occur organically during any Alpenglow reward epoch.

### Recommendation
Compute the Alpenglow per-voter reward denominator (`RewardEpochDelegatedStakes.delegated_stakes`) using the same eligibility criteria as the numerator (`calc_earned_credits`/`calculate_alpenglow_points`), i.e., only sum the effective stake of delegations that will actually earn nonzero credits this reward epoch, mirroring how the Tower path derives its total points from the same eligibility-aware per-stake calculation.

### Proof of Concept
1. Bootstrap an Alpenglow epoch with vote account `V` and two delegations to `V`: `stake_A` (long-standing, `credits_observed` below the epoch's `initial_epoch_credits`, so it earns the full epoch's credits) and `stake_B` (freshly redelegated to `V` such that `stake_B.credits_observed >= final_epoch_credits` for the reward epoch).
2. At epoch boundary, `Stakes::calculate_activated_stake` sums both `stake_A` and `stake_B`'s effective stake into `RewardEpochDelegatedStakes.delegated_stakes[V]` (`runtime/src/stakes.rs:447-502`), regardless of `stake_B`'s credit eligibility.
3. `calculate_alpenglow_points` for `stake_A` computes `earned_points = earned_credits * stake_A_amount / total_stake` where `total_stake = stake_A_amount + stake_B_amount` (`runtime/src/inflation_rewards/points.rs:280-301`), while `stake_B` earns `0` points via `calc_earned_credits` (`runtime/src/inflation_rewards/points.rs:158-181`).
4. `stake_A` receives a payout proportionally reduced by `stake_B`'s presence even though `stake_B` earns nothing from the vote account this epoch — verifiable by comparing `stake_A`'s `ag_points`/redeemed lamports with and without `stake_B` present under otherwise identical conditions, analogous to the diff-based Hardhat PoC in the Canto report showing rewards dropping to a fraction of `rewardPerWeek` when ineligible liquidity is added to the pool.

fn calc_earned_credits(
    stake: &Stake,
    final_epoch_credits: u64,
    initial_epoch_credits: u64,
    new_credits_observed: &mut u64,
) -> u128 {
    let credits_in_stake = stake.credits_observed;

    // figure out how much this stake has seen that
    //   for which the vote account has a record
    let earned_credits = if credits_in_stake < initial_epoch_credits {
        // the staker observed the entire epoch
        final_epoch_credits - initial_epoch_credits
    } else if credits_in_stake < final_epoch_credits {
        // the staker registered sometime during the epoch, partial credit
        final_epoch_credits - *new_credits_observed
    } else {
        // the staker has already observed or been redeemed this epoch
        //  or was activated after this epoch
        0
    };
    *new_credits_observed = (*new_credits_observed).max(final_epoch_credits);
    u128::from(earned_credits)
}
