### Title
Webhook status forgery via organization/repository binding mismatch enables unauthorized deploy - (File: app/controllers/shipit/webhooks_controller.rb, app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
Shipit supports multi-organization GitHub App configuration, where each organization has its own `webhook_secret` [1](#0-0) . `WebhooksController#verify_signature` selects *which* organization's secret to verify the HMAC signature against using a field read directly from the untrusted payload (`repository.owner.login`, falling back to `organization.login`) [2](#0-1) . Once the signature check passes, the full attacker-controlled `params` hash is dispatched to event handlers, and `Webhooks::Handlers::StatusHandler` mutates commit state using only the `sha` field, with **no scoping to the organization or repository that was authenticated** [3](#0-2) . This breaks the binding: `organization that authenticated (verified via HMAC using repository_owner-selected secret) == repository/commit that is written`.

### Finding Description
`verify_signature` picks the `GitHubApp` (and thus the webhook secret) to check the signature against based on `repository_owner`:
```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [4](#0-3) 

This value is read straight out of the JSON body the attacker controls; it is *itself covered* by the signature only in the sense that changing it invalidates the signature computed with a *different* org's secret — but an attacker who legitimately controls their own organization's webhook secret (e.g., they administer their own GitHub App/repo that is also configured on this same multi-tenant Shipit instance) can freely construct any payload, sign it correctly with their own secret, and set `repository.owner.login` to their own org so verification succeeds.

Once verification passes, `WebhooksController#create` dispatches the entire raw JSON to the matching handler(s) for the event type [5](#0-4) . For a `status` event, `StatusHandler#process` does:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [3](#0-2) 

This looks up commits **globally by `sha` alone** — it never checks that the commit's stack/repository belongs to the organization that was used to authenticate the request (`repository_owner`). Contrast this with other handlers such as `PushHandler`/`CheckSuiteHandler`, which correctly scope to `Repository.from_github_repo_name(payload.dig('repository', 'full_name'))` via the shared `Handler#stacks` helper [6](#0-5)  — even that scoping field (`repository.full_name`) is itself attacker-controlled and independent from the `repository.owner.login`/`organization.login` field used for signature-org selection, since these are separate JSON keys in the same forgeable payload.

The net effect: the equality that should hold —
`org whose secret verified the signature == org/repo whose state is mutated`
— does not hold. An attacker who owns valid webhook credentials for **any** organization/repository tracked by the Shipit instance can forge a `status` webhook naming an arbitrary `sha` belonging to a **different** organization's commit, and inject a fabricated CI state (e.g. `success`) for it via `Commit#create_status_from_github!`.

### Impact Explanation
Commit statuses feed directly into deploy-gating logic (`Commit#deployable?`, `required_statuses`, blocking-status checks) as seen throughout the test suite (`test/models/commits_test.rb`, `deployable?` checks) [7](#0-6) . By forging a `success` status for a victim commit sha that the attacker does not control but knows (e.g. observed in the victim's public GitHub commit history or the Shipit UI), the attacker can make an otherwise CI-failing/pending commit appear deployable, enabling an **unauthorized deploy** of that commit through the victim's stack — satisfying the explicit "unauthorized deploy" Critical impact criterion, without needing any Shipit session, `ApiClient` token, or the victim organization's own `webhook_secret`.

### Likelihood Explanation
Exploitation only requires the attacker to be a legitimate webhook sender for *any* organization configured on the shared Shipit instance (a realistic scenario for any multi-tenant deployment serving several GitHub orgs/teams, which the engine explicitly supports via `github_app_config`) [8](#0-7) . No repository write access, no GitHub App private key, and no target-org secret are needed — only the attacker's own org's webhook secret plus knowledge of a target commit sha, which is commonly public information.

### Recommendation
Scope all webhook handler side effects to the same organization/repository that was cryptographically authenticated. Concretely:
- Pass the verified `repository_owner`/organization identity from `WebhooksController#verify_signature` down into the handler dispatch, and have `StatusHandler` (and any other handler that mutates state) filter `Commit`/`Stack` lookups by that verified owner rather than trusting `repository.full_name` or matching by `sha` alone.
- Ensure `Handler#stacks` and `StatusHandler#process` both derive the repository scope from the same authenticated field used in `verify_signature`, not from independently-controlled payload fields.

### Proof of Concept
1. Attacker legitimately administers "org-attacker", which is configured in this shared Shipit instance with its own `webhook_secret` (`Shipit.github(organization: 'org-attacker')`).
2. Attacker learns the git SHA of a commit belonging to "org-victim/prod-repo" tracked by the same Shipit instance (public GitHub commit, or observed via Shipit UI).
3. Attacker POSTs to `/github/webhooks` with `X-Github-Event: status`, body:
   ```json
   {
     "sha": "<victim commit sha>",
     "state": "success",
     "context": "ci/required-check",
     "repository": {"owner": {"login": "org-attacker"}, "full_name": "org-attacker/some-repo"}
   }
   ```
   signed with `org-attacker`'s webhook secret via `X-Hub-Signature`.
4. `verify_signature` resolves `repository_owner` to `org-attacker`, loads `org-attacker`'s `GitHubApp`, and the signature verifies successfully [9](#0-8) .
5. `StatusHandler#process` executes `Commit.where(sha: params.sha)`, finds the victim's commit (unrelated to `org-attacker`), and calls `create_status_from_github!`, injecting a forged `success` status [3](#0-2) .
6. The victim commit now satisfies `required_statuses`/`deployable?`, and can be shipped through the victim's stack as an unauthorized deploy.

**Note on verification limits:** I was not able to execute this end-to-end in a live environment (no test/terminal access here), so the exact downstream deploy-trigger path (continuous delivery vs. manual deploy) was confirmed only via static code/tests, not a live PoC run. The core root cause — signature-org selection and handler write-scope using disjoint, independently attacker-controlled payload fields — is confirmed directly in the cited source.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping
      head(:ok) if event == 'ping'
    end

    def event
      request.headers.fetch('X-Github-Event')
    end

    def repository_owner
      # Fallback to the organization sub-object if repository isn't included in the payload
      params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
    end
