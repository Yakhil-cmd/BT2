### Title
Cross-repository CI status forgery via unscoped `Commit.where(sha:)` lookup in `StatusHandler` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` looks up commits to attach a GitHub `status` event to using only the commit `sha`, with no scoping to the repository that the webhook was verified for. Every other webhook handler (`OpenedHandler`, `LabeledHandler`, `ClosedHandler`, etc.) derives a `repository`/`stacks` scope from `payload.dig('repository','full_name')` via the base `Handler#repository_name`/`#stacks` helpers, but `StatusHandler` never calls into that scoping logic. This breaks the binding "the organization/repository whose webhook secret authenticated the request" == "the repository whose data actually gets written," which is exactly the trust boundary this scan is looking for.

### Finding Description
`WebhooksController#verify_signature` selects which GitHub App / `webhook_secret` to validate the HMAC signature against based on the payload's `repository.owner.login` (or `organization.login`) field: [1](#0-0) 

This design explicitly supports multiple organizations sharing one Shipit instance (`Shipit.github_app_config`, `secrets.github` keyed by org): [2](#0-1) [3](#0-2) 

Once the signature check passes for *some* organization, the raw JSON payload (fully attacker-controlled aside from the signed bytes) is dispatched to `Shipit::Webhooks.for_event(event)` handlers: [4](#0-3) 

The base `Handler` class provides a `stacks`/`repository_name` helper meant to scope processing to the repository named in the payload: [5](#0-4) 

However, `StatusHandler#process` bypasses this scoping entirely and finds commits **globally by `sha` alone**: [6](#0-5) 

Because `sha` is a global 40-hex-char field with no repository qualifier in the query, any commit sharing that SHA across **any** stack/repository configured in the same Shipit instance (a common situation for forks, mirrors, vendored/mono-repo setups, or an attacker deliberately mirroring the target repo's commit into their own org) will have `create_status_from_github!` invoked on it — even though the webhook was signed and verified only for the attacker's own organization/repository.

### Impact Explanation
Commit statuses recorded via `create_status_from_github!` feed directly into `Stack`/`Commit` deployability checks (`required_statuses`, `blocking_statuses`, `deployable_commits`, continuous delivery triggering) as configured in `deploy_spec.rb` and `stack.rb`: [7](#0-6) [8](#0-7) 

An attacker who controls (or is a legitimate low-trust member of) one organization/repository on a shared Shipit instance can send a validly-signed `status` webhook for their own repo, but set the `sha` field to match a commit that is tracked under a victim organization's stack. This injects a forged (e.g., `"success"`) status onto that commit in the victim's stack, satisfying CI requirements and enabling an **unauthorized deploy** of a commit that never actually passed CI in the victim repository — without ever needing the victim org's webhook secret, GitHub App credentials, or repository access.

### Likelihood Explanation
Exploitability requires: (1) a Shipit instance configured for multiple GitHub organizations/tenants (an explicitly documented and supported configuration, see `secrets.development.shopify.yml` and `Shipit.github_organizations`), and (2) a SHA collision between a commit the attacker can trigger a status for and a commit tracked in the target stack — achievable deliberately by forking/mirroring the target repository (or referencing a shared/vendored commit) into the attacker's own org and sending a status event for the identical SHA. No privileged Shipit session, `ApiClient` token, or victim-org secret is required — only a legitimate webhook signature for any one tenant on the shared instance.

### Recommendation
Scope `StatusHandler#process` (and any other handler using bare model lookups) to the repository derived from the verified webhook payload, matching the pattern used by `Handler#stacks`/`#repository_name`, e.g.:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
end
```
Additionally, consider having `WebhooksController#verify_signature` cross-check that `repository.full_name`'s owner matches the `repository_owner`/organization used to select the webhook secret, rather than trusting it implicitly for downstream handlers.

### Proof of Concept
1. Shipit instance is configured with two organizations, `orgA` (victim) and `orgB` (attacker-accessible), per the multi-org `github:` secrets schema.
2. Victim's stack tracks a commit with `sha = X` in `orgA/victim-repo` (e.g. because the attacker forked/mirrored `orgA/victim-repo` into `orgB/mirror-repo`, producing an identical commit `X`).
3. Attacker triggers (or synthesizes) a `status` GitHub webhook event for `orgB/mirror-repo` with `sha: X`, `state: "success"`, `context: "ci/required-check"`, and computes a valid `X-Hub-Signature` using `orgB`'s legitimately known webhook secret.
4. `WebhooksController#verify_signature` resolves `repository_owner` from the payload as `orgB` and successfully verifies the signature against `orgB`'s secret.
5. `StatusHandler#process` runs `Commit.where(sha: 'X')`, which matches the commit in `orgA`'s stack (unscoped to repository), and calls `create_status_from_github!`, recording a forged `"success"` status on `orgA`'s commit.
6. If `orgA`'s stack requires that CI context for deployability/continuous delivery, the forged status can unblock or trigger an unauthorized deploy of commit `X` in `orgA`, without the attacker ever possessing `orgA`'s webhook secret, GitHub App credentials, or repository write access.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
