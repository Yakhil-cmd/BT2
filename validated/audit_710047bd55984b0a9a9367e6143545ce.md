### Title
Cross-repository status forgery via bare-SHA lookup enables unauthorized merge/deploy - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` resolves the target `Commit` purely by `Commit.where(sha: params.sha)`, with no scoping to the repository that authenticated the webhook. Any GitHub organization owner who can pass their own `X-Hub-Signature` (i.e., a repo they control, with their own webhook secret configured in `Shipit.github`) can forge a `status` event whose `sha` field names a commit that belongs to a different, victim stack, writing an attacker-controlled `ci/circleci` `success` status onto that victim commit.

### Finding Description
The broken binding: the invariant that should hold is `commit.stack.repository.full_name == payload.repository.full_name` (the status write must apply only to the repository that authenticated the webhook). Instead, the actual code enforces only `commit.sha == params.sha`, with `stack`/`repository` never checked: [1](#0-0) 

`WebhooksController#verify_signature` verifies the HMAC signature using the secret associated with `repository_owner`, which is read straight out of the attacker-supplied JSON payload (`params.dig('repository','owner','login')`): [2](#0-1) [3](#0-2) 

This means the signature check only proves "this request was signed with the secret of the org/repo named in the payload" — it says nothing about the `sha` field, which is an arbitrary attacker-controlled string in the JSON body, unconnected to `repository.owner.login`. An attacker who owns any GitHub org/repo integrated with this Shipit instance can:
1. Set `repository.owner.login` to their own org (so `verify_signature` passes with their own legitimate webhook secret).
2. Set `sha` to the known SHA of a commit in a victim stack (git commit SHAs of public repos are public information, easily observed via GitHub).
3. Set `context: "ci/circleci"`, `state: "success"`.

`StatusHandler#process` then finds all `Commit` records across the entire installation matching that raw SHA — irrespective of which stack/repository they belong to — and calls `commit.create_status_from_github!(params)` on each, which invokes `Status::Group` logic through `add_status` and, on a status transition to `success`/`pending`, calls `stack.schedule_merges`: [4](#0-3) 

If the victim stack has `merge_queue_enabled: true`, `Shipit::MergeRequest.schedule_merges` (via `Stack#schedule_merges`) picks up stacks with the queue enabled and attempts to advance/merge the head merge request once required statuses are green, ultimately calling `MergeRequest#merge!`, which invokes `stack.github_api.merge_pull_request` with `stack`'s own GitHub App credentials: [5](#0-4) [6](#0-5) 

None of the existing guards (`verify_signature`, `ExplicitParameters` schema on `StatusHandler`, `drop_unhandled_event`) validate that the `sha` in the payload actually belongs to the repository that was authenticated — the schema only requires `sha`/`state`/`context` to be present strings, with no repository binding check.

### Impact Explanation
An attacker controlling any onboarded repository can inject a forged `ci/circleci` `success` status onto an arbitrary commit belonging to an unrelated victim stack, without ever authenticating against or having write access to that victim's repository. If the victim stack requires `ci/circleci` and has `merge_queue_enabled: true`, this can force `MergeRequest#merge!` to run and merge a pull request via the victim stack's own GitHub credentials — an unauthorized merge/deploy of attacker-influenced state, matching the "payload for one repository mutating another's stack/commit" and "unauthorized deploy/merge" Critical impact categories. The blast radius spans every stack hosted on the same Shipit instance; the only requirement is that the attacker knows (or can find) a target commit SHA, which is public GitHub information.

### Likelihood Explanation
Preconditions: attacker needs any repository registered with the Shipit instance's GitHub App/organization for which they can trigger (or directly POST) a signed `status` webhook using their own valid secret — a low bar, satisfied by owning/forking any repo under an org configured in `Shipit.github`. The victim stack must require `ci/circleci` and have `merge_queue_enabled: true` (a documented, common configuration) with a pending merge request whose head SHA the attacker targets. The attack is fully repeatable and requires no privileged Shipit role, session, or secret — only standard GitHub webhook delivery for a repo the attacker controls, with a forged `sha` field.

### Recommendation
Scope every webhook handler's DB lookups by the authenticated repository, not by the bare SHA. `StatusHandler#process` should resolve `Commit` only within stacks belonging to `params.repository.full_name` (e.g., via `Stack.where(repository: repo).joins(:commits).where(commits: { sha: params.sha })` or by first resolving `Repository.from_github_repo_name(...)` and scoping `commit.stack.repository` equality before calling `create_status_from_github!`). Apply the same repository-scoping fix to any other handler performing bare `Commit.where(sha:)`/`by_sha` lookups without checking the owning stack's repository against the authenticated payload's `repository` field.

```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb (conceptual addition)
test "status webhook for an unrelated repository's SHA flips a victim stack's commit state and can trigger merge" do
  victim_stack = shipit_stacks(:shipit) # merge_queue_enabled: true, requires ci/circleci
  victim_commit = victim_stack.commits.create!(sha: "a" * 40, message: "victim commit")

  # Binding claimed by the invariant: commit.stack.repository == payload.repository
  assert_not_equal victim_stack.repository.full_name, "attacker-org/attacker-repo"

  params = Shipit::Webhooks::Handlers::StatusHandler::Params.new(
    sha: victim_commit.sha,
    state: "success",
    context: "ci/circleci"
  )

  # Simulates a request whose signature was verified against attacker-org's own secret
  # (repository_owner in payload == "attacker-org"), while sha targets victim_commit.
  Shipit::Webhooks::Handlers::StatusHandler.new(params).process

  victim_commit.reload
  assert victim_commit.statuses.exists?(context: "ci/circleci", state: "success"),
    "Attacker-authenticated webhook wrote a status onto a commit belonging to a stack it never authenticated for"

  # Demonstrates the binding is broken: no check ties commit.stack.repository to the
  # repository that produced a valid signature.
end
```

```ruby
    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
```
