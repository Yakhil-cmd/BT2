### Title
Unbounded private-payment chain depth lets a counterparty grow validation cost without limit, permanently blocking a victim's coin from being spent - (File: indivisible_asset.js / private_payment.js)

### Summary
For indivisible (fixed-denomination, e.g. blackbytes) private assets, every time a coin is transferred it is validated by walking the *entire* chain of private elements back to the original issuance (`parsePrivatePaymentChain` → `validatePrivatePayment` → `buildPrivateElementsChain`). There is no cap anywhere in `indivisible_asset.js`, `private_payment.js`, or `validation.js` on how many hops (chain length) this history can contain. A private-payment counterparty (an unprivileged actor who is by definition allowed to exchange private payments with the victim) can bounce a tiny private coin back and forth an arbitrary number of times before finally sending it to the victim, making the chain the victim receives arbitrarily deep.

### Finding Description
`buildPrivateElementsChain` recursively/iteratively walks up the `inputs` table one hop at a time until it reaches an `issue` input, pushing every hop into `arrPrivateElements`: [1](#0-0) [2](#0-1) 

When a victim (or a light wallet on the victim's behalf) receives this chain, `validateAndSavePrivatePaymentChain` in `private_payment.js` dispatches to `indivisibleAsset.validateAndSavePrivatePaymentChain`, which calls `parsePrivatePaymentChain`, which validates every single element of `arrPrivateElements` in series, each with its own DB queries and a spend-proof recomputation: [3](#0-2) [4](#0-3) 

Nowhere in this code path (`validatePrivatePayment`, `parsePrivatePaymentChain`, `readPayloadAndGoUp`) is there a maximum chain length check analogous to `constants.MAX_INPUTS_PER_PAYMENT_MESSAGE` or `constants.MAX_MESSAGES_PER_UNIT`. Those anti-spam limits bound a single unit's messages/inputs, not the number of *historical hops* a private coin has accumulated across many units. Because each hop is a separate, individually-valid unit (posted over time, potentially between two colluding/attacker-controlled addresses), none of the per-unit limits prevent the attacker from ping-ponging the same tiny coin thousands of times before finally sending it to the victim.

Once the victim holds this deeply-chained coin, they cannot spend it without re-sending (and the next recipient re-validating) the whole chain via `handleOnlinePrivatePayment` / `handlePrivatePaymentChains`, and light clients must additionally fetch/validate every unit in the chain (`findUnfinishedPastUnitsOfPrivateChains`, `checkThatEachChainElementIncludesThePrevious`): [5](#0-4) [6](#0-5) 

This is directly analogous to the reported bug class: an unprivileged, reachable actor (here, a private-payment counterparty, which the scan brief explicitly allows) can force an unbounded data structure tied to the victim (the private-payment chain) that must be fully walked/re-validated on every future legitimate operation (accepting the coin, spending it, or a light wallet catching up), with no size cap enforced by the core.

### Impact Explanation
Each additional hop costs at least one DB round trip and one signature/hash recomputation on both the recipient's initial validation and on every subsequent spend of that same coin (the whole history must be replayed each time it changes hands, since it's a hidden, unlinkable private chain, not a UTXO with a fixed proof). An attacker can grow this chain to thousands or millions of hops cheaply (spam between their own two addresses, paying only base-currency network fees for tiny messages), then send the resulting coin to the victim. The victim's wallet (especially a light wallet, which must also fetch every historical joint in the chain from a vendor/peer) can be forced into pathological CPU/DB/network load when trying to accept or later spend that coin, potentially preventing it from ever completing validation/spending in practice — funds become effectively unusable/frozen for the victim. This matches the "Impact" bar required (AA/fund freezing analog: here, private-asset fund freezing due to unbounded validation cost) rather than a mere resource/perf nuisance, because there is no mechanism for the victim to reject or truncate the chain and still safely accept/spend the coin.

### Likelihood Explanation
Likelihood is limited by cost and practicality: creating N hops requires N separate confirmed units (paying byte fees each time) authored by the attacker (or colluding parties) before delivery to the victim, so this is not a zero-cost griefing vector like the original DeFi report (which required only free/cheap calls). However, it is fully reachable by any private-payment counterparty without any privileged role, uses only standard payment/private-payment protocol messages, and requires no cooperation from the victim — the victim has no way to detect or refuse a coin's chain length until they receive and attempt to process it.

### Recommendation
Introduce and enforce an explicit maximum private-payment chain length (analogous to the existing `MAX_INPUTS_PER_PAYMENT_MESSAGE` / `MAX_MESSAGES_PER_UNIT` anti-spam constants) in `parsePrivatePaymentChain` / `buildPrivateElementsChain`, rejecting (or requiring compaction/re-issuance of) chains beyond a bounded depth so that validation cost for any received private coin is capped regardless of how many times an adversarial counterparty chooses to re-transfer it before delivery.

### Proof of Concept
Conceptual, not executed (no test harness access in ask-only mode):
1. Attacker controls two addresses A and B and issues (or already owns) one indivisible private coin of denomination D.
2. Attacker repeatedly sends the coin A→B→A→B... via `divisible_asset`/`indivisible_asset` private payment composer, each time producing a new valid unit; repeat N times (N large, e.g. tens of thousands), paying only minimal per-unit byte fees.
3. Attacker finally sends the coin from B to the victim's address.
4. Victim's wallet receives the private elements chain via `handleOnlinePrivatePayment`/`handlePrivatePaymentChains` and must call `indivisibleAsset.validateAndSavePrivatePaymentChain` → `parsePrivatePaymentChain`, which performs `N` sequential DB validations (`validatePrivatePayment`) before it can accept the coin — see the unbounded loop with no depth cap: [7](#0-6) 
5. To later spend the coin, the victim (or, worse, their light-wallet vendor/peer) must reconstruct and re-transmit the same `N`-hop chain (`buildPrivateElementsChain`), repeating the cost on every future transfer.

		isNonemptyArray(c) &&
		c.every(e =>
			isNonemptyObject(e) &&
			isNonemptyString(e.unit) &&
			isNonemptyObject(e.payload) &&
			isNonemptyString(e.payload.asset) &&
			isNonemptyArray(e.payload.inputs) &&
			isNonemptyArray(e.payload.outputs) &&
			e.payload.inputs.every(isNonemptyObject) &&
			e.payload.outputs.every(isNonemptyObject)
