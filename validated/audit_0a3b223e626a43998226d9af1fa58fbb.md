### Title
Cross-organization webhook forgery via `repository.owner.login` / `repository.full_name` mismatch - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/webhook secret to use for HMAC verification based on `repository.owner.login` (or `organization.login`) extracted from the JSON payload, but every webhook handler that actually acts on data (e.g. `PushHandler`, the `PullRequest::*Handler`s, `Handler#stacks`) resolves the target repository/stack using a *different* field, `repository.full_name`. Nothing ties these two fields together, so on a multi-organization Shipit deployment an attacker who legitimately controls one configured organization's webhook secret can forge a payload naming a different organization's repository, pass signature verification, and have the engine act on the victim repository's stacks.

### Finding Description
`Shipit.github(organization:)` supports a multi-tenant configuration where each GitHub organization has its own webhook secret, app id, private key, etc., selected from `secrets.github` keyed by organization name. [1](#0-0) 

The webhook signature check picks the verifying `GitHubApp` (and thus the HMAC secret) using `repository_owner`, derived only from `params.dig('repository','owner','login')` or `params.dig('organization','login')`: [2](#0-1) 

Once `head(422)` is not triggered, the entire raw, attacker-controlled JSON body is dispatched unchanged to the registered handlers: [3](#0-2) 

Every handler that resolves "which repository/stack to act on" uses `repository.full_name`, not `repository.owner.login`: [4](#0-3) 
and, e.g., the push handler: [5](#0-4) 
and the pull-request handlers (open/close/label/reopen) which archive/unarchive/create review stacks based on `params.repository.full_name`: [6](#0-5) [7](#0-6) 

Because the HMAC signature is computed over the raw JSON body as a single opaque blob, and the attacker fully controls that body (both `repository.owner.login` and `repository.full_name` are just JSON string values they write), an attacker who is a legitimate admin of "Organization A" (a second org configured on the same Shipit instance, with its own known `webhook_secret`) can:

1. Set `repository.owner.login` (or `organization.login`) = `"org-a"` — so `verify_signature` selects Org A's `GitHubApp`/secret, which the attacker legitimately knows.
2. Set `repository.full_name` = `"org-b/victim-repo"` (or any other repository, including ones the attacker has no access to at all).
3. Sign the raw body with Org A's webhook secret.
4. POST to `/webhooks`.

`verify_signature` succeeds (Org A's secret matches Org A's HMAC), and the handler layer then acts on `org-b/victim-repo` — completely decoupling the "organization that authenticated" from the "repository that is written," exactly the binding this scan is looking for.

### Impact Explanation
Concretely, this lets an attacker (who only needs write access to their own, unrelated org's webhook config, no Shipit credentials) reach into a foreign repository's Shipit state:
- `PushHandler#process` triggers `stack.sync_github(expected_head_sha:)` for any non-archived `Stack` matching `org-b/victim-repo` + arbitrary branch, forcing sync jobs for a repo the attacker doesn't own.
- `PullRequest::OpenedHandler`/`ClosedHandler`/`LabeledHandler`/`ReopenedHandler` will create, archive, or unarchive Review Stacks for `org-b`'s pull requests, based purely on attacker-supplied `full_name`/`pull_request` JSON, without any real activity happening on GitHub.
- `MembershipHandler` was located but not fully inspected before the tool budget ran out; based on the tests observed (`":membership creates the mentioned team/user on the fly"`), membership webhooks create `Team`/`User` records tied to an `organization.login` value that is likewise attacker-suppliable and only checked against the org used for signing — this is a plausible path toward polluting `Shipit.github_teams` membership data, but I could not confirm the exact code path or whether team authorization (`User#authorized?`) is actually affected, since I ran out of iterations before reading `membership_handler.rb`. This part should be treated as unconfirmed.

The confirmed impact (forged cross-repository Push/PullRequest event processing) is a cross-repository state-mutation primitive (creating/archiving review stacks, forcing syncs) triggered by an attacker who holds no privilege over the victim's repository — this satisfies the "cross-repository writes" criterion under Critical impact, contingent on the deployment actually using the multi-organization `secrets.github` configuration with more than one org.

### Likelihood Explanation
Requires: (a) the Shipit instance to be configured for multiple GitHub organizations (`github_default_organization` non-nil, multiple keys under `secrets.github`), and (b) the attacker to control (or know) the webhook secret of at least one of those configured organizations (e.g., they are a legitimate admin of one org whose repos are also tracked by the same Shipit instance, a realistic scenario for shared internal Shipit deployments serving multiple GitHub orgs). Given that, exploitation requires no Shipit session, API token, or GitHub write access to the victim repo — only crafting and POSTing a JSON payload. This is a moderate-likelihood, config-dependent issue: single-org deployments (the common case, `github_default_organization` nil) are not affected, since there both `repository.owner.login` and `repository.full_name` roots resolve to the same single secret and the same account, though even there a full_name reference to another repo on the same org could still be forged, but the practical attacker would need to be the owner of an app installed on that same, single org, which is a smaller escalation window.

### Recommendation
Cross-validate that the organization login used to select the verification secret matches the owner segment of `repository.full_name` before dispatching to handlers, e.g., reject the webhook if `repository.full_name.split('/').first.downcase != repository_owner.downcase`. Alternatively, have handlers resolve the target `Repository`/`Stack` using the same trusted `repository_owner` value that was cryptographically verified, rather than trusting a second, unrelated field (`repository.full_name`) from the same unauthenticated JSON body.

### Proof of Concept
Given a Shipit instance configured with two GitHub orgs in `secrets.github`, `org-a` (attacker-administered, webhook secret known to attacker) and `org-b` (victim, has stack `org-b/victim-repo` tracked in Shipit):

```
payload = {
  "ref" => "refs/heads/main",
  "after" => "deadbeef",
  "repository" => {
    "owner" => { "login" => "org-a" },   # used only for signature verification
    "full_name" => "org-b/victim-repo"   # used by PushHandler to select the Stack to act on
  }
}.to_json

signature = "sha1=" + OpenSSL::HMAC.hexdigest("sha1", ORG_A_KNOWN_WEBHOOK_SECRET, payload)

POST /webhooks
X-Github-Event: push
X-Hub-Signature: <signature>
Body: <payload>
```

`verify_signature` succeeds because `Shipit.github(organization: "org-a")` is queried and the HMAC matches Org A's secret. `PushHandler#process` then resolves `stacks` via `Repository.from_github_repo_name("org-b/victim-repo")` and calls `sync_github` on any matching, non-archived stack on branch `main`, even though the attacker has no legitimate relationship to `org-b`.   def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping
      head(:ok) if event == 'ping'
    end

    def event
      request.headers.fetch('X-Github-Event')
    end

    def repository_owner
      # Fallback to the organization sub-object if repository isn't included in the payload
      params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
    end

# frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
    end
  end
end
