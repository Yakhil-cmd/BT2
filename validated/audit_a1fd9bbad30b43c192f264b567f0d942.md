### Title
Incorrect TPS/TPS-fee calculation when elapsed time is zero, causing consensus-critical fee value divergence - (File: storage.js)

### Summary
The reported bug is a "view" style function (`rewardPerShft()`) that fails to special-case an uninitialized/zero state variable (`lastUpdateTime == 0`) and consequently returns an incorrect computed value instead of `0`. The equivalent pattern in `ocore` exists in the TPS-fee calculation helpers in `storage.js`, which are used to compute the deterministic, consensus-critical `tps_fee`/`actual_tps_fee` that every unit must pay and that every node must independently and identically recompute. These helpers divide by an `elapsed` time value and silently substitute a hardcoded constant when that value is `0`, rather than correctly handling that edge case, which can make the derived fee/tps value diverge from what an honest, careful implementation would compute for that specific state.

### Finding Description
`storage.js` defines a fallback constant used whenever the time elapsed between a unit and its last-ball unit is `0`: [1](#0-0) 

This fallback is applied, without any additional validation of the "elapsed == 0" state, in the core deterministic TPS calculation routines: [2](#0-1) [3](#0-2) [4](#0-3) 

`getCurrentTps` even documents awareness of this exact issue by throwing when `since_timestamp === 0` in one branch: [5](#0-4) 
but `getFinalTps` and `getLocalTps` do not perform the same defensive check — they simply substitute `elapsedTimeWhenZero` (a constant `1`) for the real elapsed time whenever `objMcUnitProps.timestamp - objLastBallUnitProps.timestamp` (or `objUnitProps.timestamp - objLastBallUnitProps.timestamp`) equals `0`, rather than treating this as a state that should be handled correctly (e.g., proportionally to true elapsed time, or deterministically excluded). Because a unit's `timestamp` field is attacker-influenced (subject only to loose monotonicity constraints, not strict increase relative to `last_ball`), an unprivileged unit poster can potentially construct a unit whose `timestamp` equals its `last_ball_unit`'s `timestamp`, forcing `elapsed` to `0` and forcing the TPS/TPS-fee computation down the fallback path with a fixed divisor of `1`, producing a `tps` (and hence `tps_fee`/`actual_tps_fee`) value that does not reflect the actual instantaneous throughput at that point in the DAG.

This mirrors the reported bug class precisely: a value-computing function fails to correctly special-case the "zero" state of a key input (here, `elapsed == 0`, analogous to `lastUpdateTime == 0`), and instead of returning the mathematically/semantically correct output for that state, it substitutes an arbitrary placeholder that skews the result.

### Impact Explanation
`tps_fee`/`actual_tps_fee` computed by `getFinalTps`/`getFinalTpsFee`/`getLocalTps`/`getLocalTpsFee` is a consensus value: it is written into the `units` table (`actual_tps_fee`) via `updateTpsFees`, and used to update `tps_fees_balances`, which subsequently affects fee obligations of every future unit from the same author/recipients: [6](#0-5) 
If the fallback constant causes a computed `tps` to diverge from the value other, unaffected code paths would produce, this can lead to inconsistent fee bookkeeping across the network (some nodes/paths compute the "real" elapsed-based tps, others hit the same `elapsed==0` edge differently depending on when the calculation runs), risking under/over-charging of TPS fees and, in the worst case, disagreement between nodes about whether a unit's `tps_fee` payment was correct — a core requirement for unit validity. Because `tps_fee` validity/sufficiency is enforced in `validation.js`, an incorrect or inconsistent TPS computation for the zero-elapsed edge case can result in units that some parts of the network treat as valid (fee satisfied) and others do not, i.e., a node disagreement on unit validity class of issue.

### Likelihood Explanation
Triggering `elapsed == 0` requires a unit whose `timestamp` matches its `last_ball_unit`'s `timestamp` exactly. Timestamps are attacker-supplied within the constraints enforced by unit/timestamp validation rules (which primarily bound timestamps against clock drift and MC progression, not strict inequality against `last_ball` timestamp). This makes the zero-elapsed condition plausible for a determined unit poster to engineer, especially around low-activity periods or same-second unit chains, giving this a realistic (not purely theoretical) likelihood, though it depends on exact timestamp validation bounds not fully enumerated in the reviewed code.

### Recommendation
Do not use a fixed placeholder (`elapsedTimeWhenZero`) to paper over the `elapsed == 0` case in `getFinalTps` and `getLocalTps`. Instead, apply the same defensive handling used in `getCurrentTps` (explicit detection and either a well-defined, spec-correct behavior or a hard failure) so all TPS/TPS-fee-dependent code paths behave identically and deterministically for the zero-elapsed edge case, matching the semantics documented for the network's fee model.

### Proof of Concept
Conceptual PoC (protocol-level, not runnable code):
1. An attacker crafts and composes a unit whose `timestamp` is set equal to the `timestamp` of the unit referenced as `last_ball_unit` (both attacker-controlled/composable fields), producing `elapsed = objUnitProps.timestamp - objLastBallUnitProps.timestamp === 0`.
2. When `getLocalTps`/`getFinalTps` are invoked for this unit (during TPS-fee validation/finalization in `storage.js`), the `elapsed` value falls back to the hardcoded `elapsedTimeWhenZero` (`1`) instead of a value derived from actual chain timing, altering the computed `tps` and downstream `tps_fee`.
3. Depending on when/if other nodes recompute this value under different cached state (e.g., before vs. after full stabilization), the derived `tps_fee`/`actual_tps_fee` may not match, creating potential inconsistency in fee sufficiency checks across nodes for the same unit.

Note: I was not able to fully verify, within the available indexed context, the exact timestamp-monotonicity constraints enforced elsewhere in `validation.js`/`composer.js` that would bound how easily `elapsed == 0` can be engineered, nor confirm a concrete double-spend/inflation path beyond fee/tps miscalculation. A full Devin session with complete repository access would be needed to trace all timestamp validation rules and confirm the exact severity and exploitability of this divergence.
