### Title
Missing dust-amount floor on non-base asset outputs lets an unprivileged sender pollute an AA's UTXO set and force its payment responses to bloat/fail - ([File: aa_composer.js])

### Summary
`aa_composer.js`'s `readStableOutputs`/`readUnstableOutputsSentByAAs` (used inside `completePaymentPayload`/`sendUnit` when an AA responds with a payment) explicitly filter out dust bytes outputs below `FULL_TRANSFER_INPUT_SIZE` for the base asset, but apply **no minimum-amount filter at all** when `asset` is a custom (non-base) asset: [1](#0-0) [2](#0-1) 

The developers' own comment acknowledges the dust-attack class ("spamming the AA with very small outputs so that the AA spends all its money for fees when it tries to respond") but the mitigation (`amount>=FULL_TRANSFER_INPUT_SIZE`) is applied only in the `asset IS NULL` (base) branch, not the asset branch.

### Finding Description
Any unprivileged user can post ordinary payment units sending arbitrarily many tiny-amount outputs of a custom asset to an AA's address — this requires no special permission, mirroring the "missing access control" root cause in the report where any user could freely append collateral items to a bid without being the borrower or protocol.

When the AA later needs to construct a response payment in that asset (e.g., paying out a user's balance, in `sendUnit`/`completePaymentPayload`), `iterateUnspentOutputs` loops over `readStableOutputs`'s result set with **no `LIMIT`/dust floor for assets**, accumulating inputs one-by-one until `total_amount >= target_amount`: [3](#0-2) 

Because the attacker's dust outputs are tiny, many of them must be consumed to reach any meaningful `target_amount`, so `payload.inputs` can grow to include hundreds/thousands of entries.

Compounding this, `validatePaymentInputsAndOutputs` explicitly **exempts AA-generated payments from the `MAX_INPUTS_PER_PAYMENT_MESSAGE` cap**: [4](#0-3) 

So there is no core-level backstop preventing the AA's own response payload from having an unbounded number of inputs, the way ordinary user-composed payments are bounded. The number of inputs is only implicitly bounded by falling foul of `MAX_UNIT_LENGTH`, which would cause the AA response construction itself to fail, or by extreme growth in the response unit's oversize fee (`getOversizeFee`), effectively causing the AA response to either become uneconomical, error out ("not enough funds for ... of asset ..."), or unusually costly for byte balance to cover.

### Impact Explanation
This directly maps to the report's impact class ("AA fund loss or freezing"): a malicious, unprivileged third party can degrade or deny a specific AA's ability to pay out a given custom asset it deals with, purely by spamming that AA's address with self-created dust outputs of that asset (something anyone can freely do, exactly as in the reported bug where anyone could commit unlimited collateral without permission). Legitimate triggers depending on the AA sending back that asset can bounce or fail to be composed, freezing funds/operations for the AA and its users.

### Likelihood Explanation
Likelihood is moderate-to-high for any custom asset that an AA is designed to hold/transfer, since:
- No special privilege, cosigning, or definer status is needed — the attacker just issues (if allowed) or transfers many tiny-amount outputs of the asset to the AA's own address.
- The core already recognizes and defends against this exact dust-DoS pattern for base bytes, showing the vulnerability class is realistic and intentionally mitigated elsewhere, but the parallel case for assets was left unguarded.
- The AA-side `MAX_INPUTS_PER_PAYMENT_MESSAGE` exemption removes a safety net that would otherwise bound the damage.

### Recommendation
Apply an equivalent dust floor (or a `LIMIT`) to the asset branch of `readStableOutputs` and `readUnstableOutputsSentByAAs` in `aa_composer.js`, analogous to the `amount>=FULL_TRANSFER_INPUT_SIZE` check used for base-asset outputs, and/or reinstate an inputs cap (or a hard cap independent of `bAA`) so that a flood of tiny asset outputs cannot force an AA response's `payload.inputs` array to grow unboundedly.

### Proof of Concept
1. Attacker identifies an AA address that holds/trades a custom asset `X` (non-`auto_destroy`).
2. Attacker repeatedly posts ordinary payment units sending outputs of asset `X` with amount `1` (or minimal denomination) to the AA's address — any number of times, no permission required.
3. A legitimate user triggers the AA in a way that requires the AA to send back asset `X` to them (`sendUnit`/`completePaymentPayload` with `asset = X`).
4. `readStableOutputs` returns every unspent `X` output at that address with no amount floor; `iterateUnspentOutputs` walks through all of the attacker's dust entries, potentially pushing thousands of tiny inputs into `payload.inputs` before `target_amount` is reached, unconstrained by `MAX_INPUTS_PER_PAYMENT_MESSAGE` due to the `!objValidationState.bAA` exemption at `validation.js:2137`.
5. The resulting response unit is at risk of exceeding `MAX_UNIT_LENGTH`/incurring an outsized `getOversizeFee`, causing the AA's legitimate response to error ("not enough funds for ... of asset ...") or bounce, freezing the AA's ability to service that trigger.
