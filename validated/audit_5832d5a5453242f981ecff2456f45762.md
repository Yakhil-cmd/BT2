### Title
CCMenu API endpoint bypasses stack-scoped ApiClient authorization, allowing a stack-restricted token to read CI status of any stack - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::Api::CCMenuController#stack` overrides the base controller's stack resolution and looks up the target `Stack` directly from `params[:stack_id]` without ever checking whether the authenticated `ApiClient` is scoped to that stack. This breaks the intended binding: *the stack an `ApiClient` token authorizes* vs. *the stack the request actually touches*, mirroring the bug class from the external report where one field is trusted/validated but a different, related field is the one actually acted upon.

### Finding Description
`Shipit::Api::BaseController` implements stack scoping generically: [1](#0-0) 

`stacks` restricts the queryable set to `Stack.where(id: current_api_client.stack_id)` when the authenticated `ApiClient` has a `stack_id` set, and `stack` resolves `params[:stack_id]` only within that restricted scope. This is the mechanism that makes a stack-scoped `ApiClient#stack_id` binding meaningful.

`CCMenuController`, however, both replaces `authenticate_api_client` to allow raw query-string token auth, and re-implements `stack` to bypass the scoped `stacks` relation entirely: [2](#0-1) 

Here `stack` calls `Stack.from_param!(params[:stack_id])` directly on the unscoped `Stack` model, never consulting `current_api_client.stack_id`. The only authorization check performed is `require_permission :read, :stack`, which validates the *permission scope* (`read:stack`) but not *which* stack the token is bound to: [3](#0-2) 

`ApiClient` records can legitimately carry a `stack_id`, restricting them to a single stack — this is exactly how the CCMenu token-issuing endpoint creates them: [4](#0-3) 

`CCMenuUrlController#client` creates (or reuses) a per-user, per-stack, read-only `ApiClient` (`permissions: %w[read:stack]`) and embeds its `authentication_token` in a shareable CCMenu/CCTray URL for that one stack — these URLs are designed to be handed out to low-trust consumers (build-status dashboards, IRC bots, etc.), under the assumption that the token only discloses information about the stack it was minted for.

Because `CCMenuController#stack` ignores `current_api_client.stack_id`, anyone holding one such token can substitute a different `stack_id` in the request path and receive that other stack's build/deploy status, defeating the scoping the token was supposed to enforce.

### Impact Explanation
This is an authorization/scoping bypass: a token that is only supposed to authorize read access to one specific stack's CI/build status can instead be used to read the CI/build status (last deploy, running/failure state, lock state) of **any** stack in the Shipit instance. This matches the in-scope High-impact category of "unauthenticated read of stack state" in spirit — the token is a low-privilege, widely-shared, single-purpose credential (embedded in a shareable dashboard URL) rather than a general-purpose authenticated session, and the bug lets it read state for stacks it was never authorized for. It does not require a privileged account, session, `webhook_secret`, or `api_clients_secret` — only possession of any single valid CCMenu token, which by design is meant to be shared broadly and is scoped-down specifically to prevent this kind of cross-stack disclosure.

### Likelihood Explanation
High. Any legitimate user of the CCMenu/CCTray integration already possesses such a token (it is embedded directly in the generated URL, per `CCMenuUrlController#fetch`), and exploitation only requires changing the `stack_id` in the request path — no additional privilege, secret, or interaction is needed.

### Recommendation
Have `CCMenuController#stack` resolve the requested stack through the same scoped `stacks` relation used by `BaseController` (i.e., `stacks.from_param!(params[:stack_id])`) so that a stack-restricted `ApiClient#stack_id` is actually enforced, instead of querying `Stack` directly and unscoped.

### Proof of Concept
1. As a normal Shipit user, visit stack A's page and trigger `GET /:stack_id/ccmenu_url` (`CCMenuUrlController#fetch`) to obtain a CCMenu token scoped to stack A (`ApiClient` with `stack_id = A.id`, `permissions = ["read:stack"]`). [5](#0-4) 
2. Call the CCMenu API endpoint for a different stack B using that same token: `GET /api/:B_stack_id/ccmenu.xml?token=<stack-A-token>`.
3. `authenticate_api_client` accepts the token (it is a valid `ApiClient`), and `require_permission :read, :stack` passes because the token has `read:stack` permission.
4. `stack` resolves `Stack.from_param!(params[:stack_id])` = stack B directly, ignoring that `current_api_client.stack_id == A.id`, and the response discloses stack B's latest deploy/build status — data the token was never authorized to access.
