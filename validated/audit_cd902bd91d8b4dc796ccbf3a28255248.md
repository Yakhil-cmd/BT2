### Title
Cross-organization team membership forgery via unauthenticated `github_id` reuse in `MembershipHandler#process` - ([File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`WebhooksController#verify_signature` only proves that the request was signed by *some* GitHub organization configured in Shipit's `github:` secrets — the org named in the payload's `repository.owner.login`/`organization.login` (`repository_owner`) — not that this org owns the `team` referenced in the payload. `MembershipHandler#find_or_create_team!` looks a `Team` up (and mutates its membership) purely by the numeric `team.id` (mapped to `Team#github_id`), and never checks that `Team#organization` matches `repository_owner`. An attacker who controls any org configured under Shipit's multi-app `github:` secrets can therefore forge a `membership` webhook, self-sign it with their own org's webhook secret, and add themselves to a `Team` belonging to a completely different, unrelated organization.

### Finding Description
The broken binding is: `Shipit::Team.find_by(github_id: params.team.id).organization` must equal `Shipit::WebhooksController#repository_owner` (the org whose signature was verified) for the membership mutation to be legitimately authorized. This equality is never checked.

Code path:
1. `WebhooksController#verify_signature` computes `repository_owner` from the payload (`params.dig('repository','owner','login') || params.dig('organization','login')`) and calls `Shipit.github(organization: repository_owner)` to verify the HMAC signature [1](#0-0) [2](#0-1) . This only proves the request was signed by whatever org `repository_owner` claims to be — an attacker who owns that org and configured it (per `docs/setup.md`, "Using Multiple Github Applications") can always make this pass for their own org.
2. `MembershipHandler#process` calls `find_or_create_team!`, which resolves the `Team` solely by `github_id: params.team.id`, ignoring `params.organization.login` entirely when the team already exists (the block only runs on create) [3](#0-2) .
3. `process` then unconditionally does `team.add_member(member)` for `action: 'added'`, creating a `Membership` row [4](#0-3) , with no comparison anywhere between `team.organization` and `params.organization.login`/`repository_owner`.

Attack: attacker owns org `evilcorp`, configured as a valid `github:` app in Shipit. They send `POST /webhooks` with header `X-Github-Event: membership`, signed with `evilcorp`'s webhook secret, and body:
```json
{
  "action": "added",
  "team": { "id": <github_id of a real Shipit.github_teams team, e.g. shopify/developers>, "name": "x", "slug": "y", "url": "z" },
  "organization": { "login": "evilcorp" },
  "member": { "login": "attacker-account" },
  "repository": { "owner": { "login": "evilcorp" } }
}
```
`verify_signature` passes because `repository_owner == "evilcorp"` and the attacker legitimately signed with `evilcorp`'s secret. `find_or_create_team!` finds the pre-existing team (github_id matches the real `shopify/developers` team), completely ignoring that `organization.login` is `evilcorp`, not `shopify`. `attacker-account` is added as a `Membership` of that team.

`Team#organization` (as stored, `"shopify"`) does **not** equal `repository_owner` for this request (`"evilcorp"`), yet no code anywhere checks this — confirming the reported divergence.

### Impact Explanation
This lets an attacker who controls any Shipit-configured GitHub org add an arbitrary attacker-controlled GitHub login as a member of any existing `Shipit::Team`, including one of the teams enumerated in `Shipit.github_teams` (the OAuth authorization teams) [5](#0-4) . `User#authorized?` grants full Shipit access based on membership in `Shipit.github_teams` [6](#0-5) , so this is a direct authorization-bypass/privilege-escalation path: the attacker's own GitHub account becomes "authorized" in the victim's Shipit instance without ever being a real member of the victim's GitHub org or team. From there the attacker can log in via OAuth (once `authorized?` is true) and access stacks, trigger deploys/rollbacks, etc. — repeatable against any team whose numeric `github_id` the attacker can learn or guess, and blast radius spans every tenant/org sharing the same Shipit instance's `github:` multi-app config.

### Likelihood Explanation
Preconditions: Shipit must be configured with multiple `github:` orgs (as documented) so that the attacker legitimately controls at least one org's webhook secret; the attacker needs to know the target team's numeric GitHub `id` (obtainable via GitHub's team API for teams the attacker can view, or by brute-forcing small sequential IDs). No Shipit secrets, sessions, or privileged roles are required — only ownership of one configured GitHub org, which is exactly the "unprivileged attacker" scenario described. The attack is a single crafted `POST /webhooks` request and is fully repeatable against any team ID.

### Recommendation
In `MembershipHandler#find_or_create_team!`, verify that the resolved (or newly created) team's `organization` equals the webhook's authenticated `params.organization.login` (or `repository_owner`) before performing any membership mutation; reject/raise if they differ instead of trusting `github_id` lookup alone.

### Proof of Concept
Minitest plan (extends `test/controllers/webhooks_controller_test.rb`):
```ruby
test ":membership from a foreign organization must not modify a team belonging to another org" do
  foreign_team = shipit_teams(:shopify_developers) # organization == "shopify"
  @request.headers['X-Github-Event'] = 'membership'

  payload = {
    action: 'added',
    team: { id: foreign_team.github_id, name: 'x', slug: 'y', url: 'z' },
    organization: { login: 'cyclimse' },       # attacker's own, unrelated org
    member: { login: 'attacker-account' },
    repository: { owner: { login: 'cyclimse' } } # repository_owner == attacker org, signs successfully
  }.to_json

  assert_no_difference -> { Shipit::Membership.where(team: foreign_team).count } do
    post :create, body: payload, as: :json
    assert_response :ok
  end
end
```
Assertions on both sides of the binding: `foreign_team.organization` (`"shopify"`) vs. `repository_owner` for the request (`"cyclimse"`) — they differ, yet current code returns `200 OK` and creates the `Membership`; the test's `assert_no_difference` fails against the current implementation, proving the vulnerability.
