### Title
`StatusHandler#process` mutates commits/stacks for any repository by SHA lookup, bypassing the per-repository binding enforced by every other handler - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
Every other handler in `Shipit::Webhooks::Handlers` scopes its writes through `stacks`, which is derived from the webhook's own `payload.dig('repository', 'full_name')` [1](#0-0) . `StatusHandler#process` instead resolves target records with a global `Commit.where(sha: params.sha)` query that never touches `stacks`, `repository_name`, or `payload['repository']` [2](#0-1) . This lets a correctly-signed "status" webhook for repository A write a `Status` (state/description/target_url/context) onto any commit that matches the SHA, even if that commit belongs to repository B's stack.

### Finding Description
The intended binding, honored by every sibling handler, is:
`authenticated_repository (payload['repository']['full_name'], verified via HMAC in WebhooksController#verify_signature) == repository whose records are mutated (via Handler#stacks)`.

- `CheckSuiteHandler#process` scopes through `stacks.where(branch: ...)` [3](#0-2) .
- `PushHandler#process` scopes through `stacks.not_archived.where(branch:)` [4](#0-3) .
- `MembershipHandler` operates on organization-scoped `Team`/`User` records tied to `params.organization.login`, not repository-scoped stack data [5](#0-4) .
- `StatusHandler#process`, however, does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` — it never derives or checks the commit's owning repository against `payload['repository']` [2](#0-1) .

`WebhooksController#verify_signature` only proves that the request was legitimately emitted by GitHub for the organization named in `payload['repository']['owner']['login']` [6](#0-5) ; it says nothing about which specific repository's commits the handler is allowed to touch. Since `Commit` is a global table keyed by `sha` and `stack_id` [7](#0-6) , and git SHAs are shared verbatim between a repository and any fork/mirror of it, an attacker who can generate a legitimately-signed "status" event referencing a SHA that is also tracked as a commit in another team's Shipit stack (e.g., because that stack tracks a fork or mirror of the same upstream history) can write an arbitrary `Status` (`state`, `description`, `target_url`, `context`) onto that foreign commit. This downstream triggers `Status#enable_ci_on_stack`, `Status#schedule_continuous_delivery` and hook emission for `commit_status`/`deployable_status`, which can move a victim stack's commit into a "deployable" state and enqueue `ProcessMergeRequestsJob` [8](#0-7) .

None of the existing guards catch this: `verify_signature` only authenticates the sender's own organization/repository, not the target of the write; `ExplicitParameters` only validates the shape of `sha`/`state`/etc., not repository ownership; and `stacks`/`repository_name` are simply never called by this handler.

### Impact Explanation
An attacker who controls (or can trigger legitimately-signed status events from) one repository/stack under a Shipit-trusted GitHub organization can write forged CI status records onto commits belonging to a different repository's stack, purely by reusing that commit's SHA. This is a cross-tenant write ("a payload for one repository mutating another's stack, commit, task or team") that can influence deployability and trigger `ProcessMergeRequestsJob`/continuous-delivery scheduling on a stack the attacker does not own or control - matching the Critical severity bucket. The blast radius is any pair of Shipit-tracked repositories that ever share commit SHAs (forks, mirrors, subtree-shared history).

### Likelihood Explanation
Exploitation requires the attacker to be able to emit a webhook event that passes `verify_signature` — i.e., the event must genuinely originate from GitHub for an organization/repository already onboarded into Shipit's `github_apps` configuration (per the rules, "emit webhooks from a repository they own" is an explicitly granted attacker capability). It further requires a target commit SHA that is also tracked by another stack in the same Shipit instance, which is a realistic and common situation for forked/mirrored repositories tracked as separate Shipit stacks. No secrets, sessions, or elevated GitHub roles are needed beyond ordinary control of a repository whose events Shipit already trusts.

### Recommendation
In `StatusHandler#process`, scope the `Commit` lookup by the stack(s) resolved from the verified `stacks`/`repository_name`, e.g. restrict to `Commit.where(sha: params.sha, stack_id: stacks.select(:id))` (or equivalent join through `Stack`), mirroring the pattern used by `PushHandler`/`CheckSuiteHandler`.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb
require 'test_helper'

module Shipit
  module Webhooks
    module Handlers
      class StatusHandlerCrossRepoTest < ActiveSupport::TestCase
        test "StatusHandler#process never scopes by stacks/repository_name" do
          victim_stack = shipit_stacks(:shipit) # belongs to repo "shopify/shipit-engine"
          victim_commit = victim_stack.commits.create!(sha: "deadbeef", author: shipit_users(:walrus), committer: shipit_users(:walrus), authored_at: Time.now, committed_at: Time.now)

          payload = {
            'sha' => victim_commit.sha,
            'state' => 'success',
            'repository' => { 'full_name' => 'attacker/unrelated-repo' } # does NOT own victim_stack
          }

          assert_difference -> { victim_commit.statuses.count }, 1 do
            StatusHandler.call(payload)
          end
          # Demonstrates a payload naming "attacker/unrelated-repo" mutated
          # "shopify/shipit-engine"'s commit, because `process` never calls
          # `stacks` or `repository_name`.
        end

        test "sibling handlers isolate writes via stacks/repository_name" do
          [PushHandler, CheckSuiteHandler].each do |handler_class|
            source = handler_class.instance_method(:process).source_location
            body = File.read(source.first)
            assert_match(/stacks/, body, "#{handler_class} should reference `stacks`")
          end

          status_body = File.read(StatusHandler.instance_method(:process).source_location.first)
          refute_match(/stacks|repository_name|payload\.dig\('repository'/, status_body)
        end
      end
    end
  end
end
```

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
