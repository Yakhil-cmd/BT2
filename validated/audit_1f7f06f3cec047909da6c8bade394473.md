### Title
Unscoped caller authorization can be rebound to attacker-selected route code to drain unrelated wallet assets - ([File: contracts/controller/src/strategies/swap.rs])

### Summary
Controller strategy swaps execute caller-supplied route bytes through the configured router but only constrain the controller’s own input transfer. A malicious route can place attacker-controlled pool code below the caller’s authorization, allowing that code to request an unrelated `token.transfer(caller, attacker, amount)` that transaction simulation attaches to the caller’s signed authorization tree.

### Finding Description
`swap_tokens` accepts arbitrary `StrategySwap` bytes, obtains the configured router, authorizes exactly `token_in.transfer(controller, router, amount_in)`, and invokes `router.execute_strategy(controller, amount_in, swap)` without constraining what contract code the route later invokes. [1](#0-0)  The caller-facing `swap_collateral` entrypoint forwards that caller-controlled `swap` payload after account authorization, and the same pattern is reachable from `multiply`, `swap_debt`, and `repay_debt_with_collateral`. [2](#0-1) [3](#0-2) [4](#0-3) 

The protocol’s own threat model states that routes may name arbitrary pool and token addresses and have no venue allowlist; a nested third-party contract can therefore call an unrelated token transfer from the caller, which simulation records as a child of the caller’s authorization entry. [5](#0-4)  This mirrors the reported bug class: authorization originating from a high-trust identity is rebound to lower-trust attacker-selected execution context rather than remaining scoped to the intended operation.

The regression test demonstrates the exploit with a malicious hop pool whose `swap` function calls `wallet_token.transfer(victim, attacker, amount)`. [6](#0-5)  In recording mode, that theft appears as a child beneath the victim’s `swap_collateral` authorization and drains the unrelated token. [7](#0-6)  In enforcing mode, an honest root-only authorization rejects the theft, while the simulation-produced poisoned tree executes it. [8](#0-7) 

### Impact Explanation
An attacker can cause loss of unrelated wallet assets that were not deposited into the protocol, not merely the routed input amount, if the victim signs the authorization tree produced for the malicious route. [9](#0-8)  The controller’s input-limit and measured-output checks do not bound this loss because the malicious transfer occurs through route-selected third-party code rather than through the controller’s own token movement. [10](#0-9)  This is theft of user funds reachable by an unprivileged route supplier through a normal user strategy call. [5](#0-4) 

### Likelihood Explanation
Exploitation requires the victim to submit a malicious route and sign the authorization tree containing the unexpected child transfer. [11](#0-10)  The necessary route mechanics are exposed through ordinary user calls such as `swap_collateral`, and the swap payload is intentionally supplied by the caller. [4](#0-3)  The vulnerability does not require privileged access, a compromised configured router, package lifecycle execution, or theft of protocol liquidity. [12](#0-11) 

### Recommendation
Contain route execution to an authorization boundary that cannot request unrelated caller-auth children, or reject route venues that are not explicitly allowlisted by governance. [5](#0-4)  At minimum, controller-side route validation should bind the route to known venue contracts and known token addresses before invoking the router, rather than treating opaque route bytes as safe because the controller authorized only one input transfer. [13](#0-12)  Clients should additionally reject any simulated authorization tree containing children other than the expected input transfer, but this UI safeguard should not replace contract-level venue containment. [5](#0-4) 

### Proof of Concept
1. Deploy a malicious contract exposing the venue’s expected `swap` entrypoint; inside it, call `token.transfer(victim, attacker, victim_balance)` for an unrelated token held by the victim. [6](#0-5) 
2. Give the victim a `swap_collateral` route whose `pool` address is the malicious contract and whose nominal input and output still satisfy the controller’s measured-output checks. [14](#0-13) 
3. During transaction simulation, the malicious wallet transfer is attached as a child of the victim’s `swap_collateral` authorization entry. [15](#0-14) 
4. If the victim signs that tree, the malicious hop steals the unrelated wallet balance while the strategy itself can still produce a fair collateral output. [16](#0-15) [11](#0-10)

fn simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry() {
    let s = Scene::new();
    let route = s.route_through_pool_stealing(WALLET_BALANCE);

    // `simulateTransaction` runs recording mode with non-root auth disabled.
    s.t.env.mock_all_auths();
    s.try_swap(&route)
        .expect("recording mode accepts the route");
    let recorded = s.t.env.auths();
    std::println!("recorded auth tree = {recorded:#?}");

    let stolen_transfer = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.wallet_token.clone(),
            symbol_short!("transfer"),
            (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),
        )),
        sub_invocations: std::vec![],
    };
    let poisoned_root = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.t.controller.clone(),
            Symbol::new(&s.t.env, "swap_collateral"),

        )),
        sub_invocations: std::vec![stolen_transfer],
    };
