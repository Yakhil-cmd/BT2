Based on the investigation, the `pallet_staking_async::Config` for Asset Hub Kusama uses `Currency = Balances` exclusively — it operates entirely on the native KSM balance via `pallet_balances`, with no interaction with `Assets`, `ForeignAssets`, `PoolAssets`, or `AssetConversion` swap paths. Reward/slash handling routes only through `ResolveTo<xcm_config::TreasuryAccount, Balances>`, a native-currency-only path. [1](#0-0) 

The `ProxyType::Staking` and `ProxyType::StakingOperator` filters restrict signed-user proxy calls strictly to `Staking`, `StakingRcClient`, `Session`, `VoterList`, and `NominationPools` calls — none of which touch `Assets`, `ForeignAssets`, `PoolAssets`, `AssetConversion`, or `PolkadotXcm`. [2](#0-1) 

The `ProxyType::StakingOperator` filter explicitly disallows `Utility::as_derivative`, `dispatch_as`, and `with_weight` — the wrapping mechanisms that could otherwise be abused to smuggle arbitrary calls under a different effective origin — permitting only `batch`, `batch_all`, `force_batch`, which do not change call origin and thus cannot widen permissions or redirect the caller identity mid-execution. [3](#0-2) 

Tests explicitly confirm the fund-management boundary: an operator proxying `Staking::bond` (fund movement) is filtered out via `CallFiltered`, and the `NominationPools`, `AssetConversion`, `Assets`, `ForeignAssets`, `PoolAssets`, and `PolkadotXcm` calls are never reachable from the `StakingOperator`/`Staking` proxy filters or from a plain signed `Staking::*` extrinsic. [4](#0-3) 

There is no code path by which a signed `Staking::*` call — or a proxy/utility-wrapped variant of it — reaches `pallet_asset_conversion`, `pallet_assets` (`Assets`/`ForeignAssets`/`PoolAssets`), or `PolkadotXcm` swap/asset-movement logic. The only place `AssetConversion` intersects with `StakingPot`/treasury-style accounts is in fee payment machinery (`SwapAssetAdapter`, `SwapFirstAssetTrader`), which is triggered by transaction-fee charging on any extrinsic (not specific to Staking) and is a separate, well-tested accounting path with its own balanced-issuance checks. [5](#0-4) [6](#0-5) 

The premise of the question — that an unprivileged signed user entering through `Staking::*` can control proofs/remote-account mappings and wrapped calls that "settle with a different asset identity than the accounting path expects" — has no corresponding code path in this runtime. `Staking` and `StakingRcClient` calls operate solely on native `Balances`/session-key proofs for validator/session management; there is no asset-identity resolution, swap path, or `AssetConversion`/`PolkadotXcm` dispatch reachable from this entry point, whether directly, via proxy, or via `Utility` batching.
