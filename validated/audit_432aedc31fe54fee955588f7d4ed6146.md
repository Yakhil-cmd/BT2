### Title
Cross-organization webhook can hijack an existing `Team` record and grant attacker membership - ([File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`MembershipHandler#find_or_create_team!` looks up a `Team` solely by `github_id`, with no check that the `organization` in the verified payload matches the `organization` already stored on that `Team`. Because GitHub team IDs are global while `webhook_secret` verification is scoped per-organization, an attacker who controls their own configured GitHub organization can forge a `membership` webhook whose `team.id` collides with a real team belonging to a different, victim organization, and have themselves added as a member of that victim team.

### Finding Description
The broken binding is: the organization that produced a valid signature for this request (`params.organization.login` == `"attacker-org"`, verified via `Shipit.github(organization: repository_owner).verify_webhook_signature`, see [1](#0-0)  and [2](#0-1) ) must equal the organization that owns the `Team` record being mutated (`"shopify"`, `github_id=48`). Nothing in the code enforces this.

`verify_signature` derives `repository_owner` from `params.dig('repository','owner','login') || params.dig('organization','login')`. For a `membership` event there is no `repository` key, so `repository_owner` resolves to `params.organization.login`, i.e. `"attacker-org"`. Since `attacker-org` is a legitimately configured org with its own valid `webhook_secret`, the signature check passes for a payload the attacker fully controls.

The payload is then dispatched to `MembershipHandler#process`: [3](#0-2) 

`find_or_create_team!` calls `Team.find_or_create_by!(github_id: params.team.id)`, matching purely on `github_id`. It does not filter by `organization`. If the attacker sets `params.team.id = 48` (the real `github_id` of the pre-existing `shopify/developers` team), `find_or_create_by!` finds that existing record instead of creating a new one, and the `do |team| ... end` block (which would set `team.organization`) is skipped entirely because the record already exists. `process` then calls `team.add_member(User.find_or_create_by_login!('attacker-login'))`, appending the attacker to the real Shopify team's `members` association (`app/models/shipit/team.rb:41-43`).

None of the existing guards catch this: `verify_signature` only proves the payload came from *some* org with a valid secret, not that it's the org the `Team` belongs to; the `ExplicitParameters` schema only validates types/presence, not organization ownership; there is no `organization` filter added to the `find_or_create_by!` call.

### Impact Explanation
A successful request adds an attacker-controlled GitHub login as a member of a `Team` belonging to an entirely different organization. Since `User#authorized?` checks `teams.where(id: Shipit.github_teams.map(&:id)).exists?` (`app/models/shipit/user.rb:80-82`), and `Shipit.github_teams` gates deploy/authorization checks across the app, this is a direct escalation into another organization's authorization boundary — matching the "High: escalation into `Shipit.github_teams` authorization" category. It is repeatable against any `github_id` the attacker can guess or observe (team IDs are often discoverable via GitHub's public API) and works across tenants sharing the same Shipit deployment.

### Likelihood Explanation
Preconditions: attacker must control a GitHub organization that is configured in Shipit with its own `webhook_secret` (a normal, low-cost setup for any multi-tenant Shipit instance supporting several orgs), and must know/guess the target team's `github_id`. No Shipit session, API token, or victim secrets are required — only the ability to send a signed webhook from the attacker's own org, which the attacker fully controls. This is straightforward and repeatable.

### Recommendation
Scope the team lookup by both `github_id` and `organization`:
```ruby
Team.find_or_create_by!(github_id: params.team.id, organization: params.organization.login) do |team|
  team.github_team = params.team
end
```
and additionally validate/raise if an existing `Team` with that `github_id` has a different `organization` than `params.organization.login`, to detect ID collisions rather than silently rebinding.

### Proof of Concept
```ruby
test "membership webhook from a different organization cannot hijack an existing team's github_id" do
  victim_team = Team.create!(github_id: 48, organization: 'shopify', slug: 'developers', name: 'Developers', api_url: 'https://api.github.com/teams/48')

  payload = {
    'action' => 'added',
    'team' => { 'id' => 48, 'name' => 'Developers', 'slug' => 'developers', 'url' => 'https://api.github.com/teams/48' },
    'organization' => { 'login' => 'attacker-org' },
    'member' => { 'login' => 'attacker-login' }
  }

  Shipit::Webhooks::Handlers::MembershipHandler.new(payload).process

  attacker = User.find_by(login: 'attacker-login')
  assert_not victim_team.members.reload.include?(attacker), "attacker must not be added to a team owned by a different organization"
end
```
This test demonstrates that, with the current implementation, `find_or_create_by!(github_id: 48)` matches `victim_team` regardless of `organization`, and `team.add_member` succeeds, so the assertion fails — confirming the vulnerability.

        def process
          team = find_or_create_team!
          member = User.find_or_create_by_login!(params.member.login)

          case params.action
          when 'added'
            team.add_member(member)
          when 'removed'
            team.members.delete(member)
          else
            raise ArgumentError, "Don't know how to perform action: `#{action.inspect}`"
          end
        end

        private

        def find_or_create_team!
          Team.find_or_create_by!(github_id: params.team.id) do |team|
            team.github_team = params.team

          end
        end
