No vulnerability found for this question.

**Rationale:** `chain_id` is a field embedded directly inside `RawTransaction` and is part of the signed byte sequence (the struct derives `CryptoHasher, BCSCryptoHash` and is what gets signed), so an attacker cannot "replay unchanged signed bytes" across chains — the signed payload already commits to a specific `chain_id` value [1](#0-0) . Both mempool/VM admission and the on-chain Move prologue enforce that the transaction's embedded `chain_id` matches the local network's configured chain id, rejecting any mismatch with `EBAD_CHAIN_ID`/`StatusCode::BAD_CHAIN_ID` [2](#0-1) [3](#0-2) .

This is verified end-to-end by the existing `verify_chain_id` test, which signs a transaction with one chain id and asserts that submitting it against a different configured chain id causes both `validate_transaction` and `execute_transaction` to reject it with `StatusCode::BAD_CHAIN_ID` [4](#0-3) . This is exactly the proof-of-concept scenario proposed in the question, and it already demonstrates rejection, not admission — so the attack does not succeed.

There is no code path where changing `chain_id` after signing would go undetected: doing so would invalidate the signature (since `chain_id` is part of the signed message via `RawTransaction`'s hash) [5](#0-4) , and even a properly signed transaction for a different chain id is explicitly checked and discarded by the prologue before execution. This applies uniformly regardless of payload type (including `ModuleBundle`), since the chain-id check in `prologue_common` happens before any payload-specific logic [6](#0-5) .
