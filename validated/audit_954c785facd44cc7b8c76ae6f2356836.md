### Title
Missing slippage/deadline protection in the reference "Uniswap-like market maker" AA lets balances (and thus the exchange rate) be manipulated between broadcast and execution - (File: test/samples/uniswap_like_market_maker.oscript)

### Summary
The bundled reference AA `uniswap_like_market_maker.oscript` computes swap output and LP issuance amounts purely from the AA's *current* `balance[asset]`/`balance[base]` state read at trigger-execution time, exactly like Compound's `exchangeRateStoredInternal()` computes `cToken` redemption rates from live `totalCash`/`totalBorrows`/`totalSupply`. Since the trigger carries no minimum-output, minimum-ratio, or expiry parameter, any unit that gets processed before the victim's trigger (invest, divest, or another swap) changes the balances the victim's trade is priced against, exactly mirroring the reported Compound exchange-rate manipulation issue in `SoftVault.sol`.

### Finding Description
In `formula/evaluation.js`, the `balance` opcode reads the *live* `assocBalances`/`aa_balances` state at the moment the AA's `init`/`if` formulas are evaluated for a given trigger unit: [1](#0-0) . This is the same live "spot" quantity that Compound's `exchangeRateStoredInternal()` uses (`totalCash + totalBorrows - totalReserves) / totalSupply`) — a value that changes with every state-mutating message processed by the AA, without any TWAP, oracle, or commit-reveal protection.

The shipped reference market-maker AA uses exactly this live value to price both liquidity provision and swaps:
- Liquidity investment amount is derived from `$current_ratio = $asset_balance / $bytes_balance` computed from `balance[$asset]` and `balance[base]` net of the trigger's own outputs: [2](#0-1) 
- Swap output amount is derived from the constant-product `$p = $asset_balance * $bytes_balance` using the same live balances, with no minimum-received or deadline field checked from `trigger.data`: [3](#0-2) 

Because AA triggers are executed one at a time as units are processed (in whatever order they become part of the DAG/stabilize), an attacker can submit a unit that changes the pool balance (e.g., a large swap or an invest/divest) so that it lands immediately before a victim's pending swap/invest unit, shifting `$asset_balance`/`$bytes_balance` (and hence `$current_ratio`/`$p`) at the exact moment the victim's trigger is evaluated. The victim's `init` block has no way to bound acceptable slippage or set an expiry, so the trade executes at whatever price results from the attacker's intervening trigger — root-caused by the unconditional live `balance[...]` read [4](#0-3)  combined with the absence of any minimum-amount/deadline guard in the AA's `if`/`init` logic [5](#0-4) .

### Impact Explanation
A trigger sender interacting with this AA (or any AA copied from this reference pattern) can have their swap or liquidity-provision output value degraded by a preceding attacker transaction, resulting in direct fund loss/extraction from the victim without their consent — i.e., unauthorized value transfer analogous to the sandwich-style loss described in the Compound/SoftVault report. This qualifies as "AA fund loss" under the accepted impact categories.

### Likelihood Explanation
Likelihood is high for any deployment following this exact reference pattern: any unprivileged address can post a unit paying into the AA (invest/swap) to move the pool ratio immediately ahead of a known pending trigger, since AA trigger units and their `trigger.data`/`trigger.output` amounts are visible before final execution and no fee/priority mechanism prevents reordering by whoever gets their unit included/stabilized first.

### Recommendation
Add slippage protection to the AA logic: require callers to pass a `min_amount_out` (or `min_share`/`max_ratio`) field in `trigger.data` and `bounce()` if the amount computed from the live `balance[...]` state at execution time is worse than the caller's specified bound. Optionally support a `deadline`/`expiry_ts` compared against `timestamp` to invalidate stale trigger units, mirroring standard AMM slippage/deadline guards.

### Proof of Concept
1. Attacker observes a pending unit `U_victim` calling the swap case of `uniswap_like_market_maker.oscript` (`trigger.output[[asset=base]] > 1e5`) with a large byte amount.
2. Before `U_victim` is processed, attacker submits `U_attack`, a smaller swap in the same direction, referencing a parent chain that gets it stabilized/processed first (achievable by controlling unit propagation timing/parent selection since no ordering guarantee exists between independent trigger units targeting the same AA).
3. `U_attack`'s execution updates `aa_balances` for the AA address via `updateFinalAABalances` [6](#0-5) , shifting `$asset_balance`/`$bytes_balance`.
4. When `U_victim` executes, its `init` block recomputes `$p = $asset_balance * $bytes_balance` and `$amount` from the now-worse balances [7](#0-6) , so the victim receives less than expected with no on-chain check to reject the unfavorable rate.

		var arrNewAssets = [];

			if (!assocDeltas[output.asset])
				assocDeltas[output.asset] = 0;
			assocDeltas[output.asset] -= output.amount;
			// this might happen if there is another pending invocation of our AA that created the outputs we are spending now
			if (!objValidationState.assocBalances[address][output.asset])
				arrNewAssets.push(output.asset);
		});
		objUnit.messages.forEach(function (message) {
			if (message.app !== 'payment')
				return;
			var payload = message.payload;
			var asset = payload.asset || 'base';
			payload.outputs.forEach(function (output) {
				if (output.address !== address)
					return;
				if (!assocDeltas[asset]) { // it can happen if the asset was issued by AA
					assocDeltas[asset] = 0;
					arrNewAssets.push(asset);
				}
				assocDeltas[asset] += output.amount;
			});
		});
		var arrQueries = [];
		if (arrNewAssets.length > 0) {
			var arrValues = arrNewAssets.map(function (asset) { return "(" + conn.escape(address) + ", " + conn.escape(asset) + ", 0)"; });
			conn.addQuery(arrQueries, "INSERT "+conn.getIgnore()+" INTO aa_balances (address, asset, balance) VALUES "+arrValues.join(', '));

		for (var asset in assocDeltas) {
			if (assocDeltas[asset]) {

			}

			byte_balance += assocDeltas.base;
