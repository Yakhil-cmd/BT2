### Title
Liquidation-parameter gate measures health with the new threshold only, letting a keeper stamp an adverse bonus/fee onto accounts below the safety floor in mixed-direction edits - (File: contracts/controller/src/risk/params.rs)

### Summary
`update_account_threshold` is permissionless: any authenticated caller can force a stored liquidation tuple refresh on arbitrary accounts. The protective gate (`apply_gated_liquidation_params` / `clears_min_hf`) exists so that a liquidator-favorable config change cannot be stamped onto an account whose health factor cannot absorb it — the regression tests call this the "M1 vintage hold" guarantee. The gate, however, validates only the *threshold* component of the change. When a governance edit simultaneously raises the liquidation threshold (borrower-favorable) and raises the bonus or cuts the fee (liquidator-favorable), `clears_min_hf` computes the hypothetical health factor using the **raised** threshold — inflating the numerator — while the harm being gated (bonus, fee) does not enter the health factor at all. The account therefore passes the ≥1.05 floor under the new threshold even though its health under its held vintage is below the floor the mechanism is designed to enforce, and it is stamped with the adverse bonus/fee anyway.

### Finding Description
In `contracts/controller/src/risk/params.rs`, `favors_liquidator` (lines 96–100) returns true if *any* of the three tuple fields moves against the borrower: lower `liquidation_threshold`, higher `liquidation_bonus`, or lower `liquidation_fees`. When it fires, `clears_min_hf` (lines 103–119) builds a hypothetical position that replaces **only** `liquidation_threshold` with the new config value and requires `HF >= 1.05` (`THRESHOLD_UPDATE_MIN_HF_RAW`).

The defect is a measurement asymmetry of the same class as GHSA-phcg-h58r-gmcq: the seal covers only part of the protected state. The gate re-measures the account under the new threshold but never prices the adverse component. Concretely, after `editAssetInSpoke` sets `liquidation_threshold` up (e.g., 8000 → 8500) and `liquidation_bonus` up (e.g., 500 → 1000):

- `favors_liquidator` → true (bonus raised),
- the account has debt, so the gate runs,
- `clears_min_hf` computes HF with LT = 8500, which is strictly higher than the HF under its stamped LT = 8000,
- an account with stored-vintage HF in [1.00, ~1.06) passes the gate and takes `liquidation_bonus = 1000` (and any fee cut) immediately.

The M1 invariant this gate implements — "an account below the 1.05 floor keeps its old liquidation terms until safe" — is enforced by `regression_third_party_keeper_cannot_force_adverse_tuple_below_min_hf` (tests/test-harness/tests/controller/keeper.rs:302) only for uniformly adverse edits. A mixed-direction edit slips through because the measurement leg that would fail (old-vintage HF) is never checked: the gate substitutes the favorable leg before measuring, exactly like attesting a disk while skipping the modified partition.

The reachable path is `update_account_threshold(caller, has_risks = true, account_ids)` (params.rs:124–144), callable by any authenticated address while unpaused; `sync_account_thresholds` (lines 149–237) iterates each victim's supply legs and writes the tuple via `update_or_remove_supply_position`. The same gate is also triggered inside `merge_supply_leg` and `merge_withdraw_leg`, so a third party can force the stamp via `supply` to the victim's account as well.

### Impact Explanation
The stored `liquidation_bonus` and `liquidation_fees` feed `get_account_bonus_params`: the USD-weighted stored bonus becomes `base_bps` for every subsequent liquidation of that account (docs/reference/formulas.md §"Blended threshold and bonus bounds"). Stamping a raised bonus onto an account the protocol itself deems too weak for adverse terms directly transfers collateral value to future liquidators that the vintage-hold mechanism was built to shield — quantifiable excess seizure of `bonus_delta / (1 + bonus)` per repaid USD, and reduced protocol fee revenue if the fee was cut. The theft is bounded by the tuple delta and executes through normal liquidation once HF < 1.

### Likelihood Explanation
Requires a governance `EditAssetInSpoke` that moves threshold and bonus/fee in opposite directions — a routine parameter tuning shape (e.g., compensating a higher threshold with a higher bonus to keep liquidations attractive). Once such a config is live, any unprivileged keeper calls `update_account_threshold(true, [victim_ids])` and forces the stamp; no cooperation from the victim is needed, and the batch only reverts if the post-refresh HF — computed under the new, higher threshold — is below 1.05, which is exactly the population being exploited. Severity is Medium: conditional on a plausible config edit, loss is partial (bonus delta), and the victim retains the favorable threshold.

### Recommendation
Measure the gate against the component that is actually adverse, or against both vintages:

1. In `clears_min_hf`, also require the health factor computed with the position's **stored** threshold (i.e., the current account HF) to be ≥ `THRESHOLD_UPDATE_MIN_HF_RAW` before applying any liquidator-favorable field; or
2. Gate each field separately: apply the threshold change when its own HF check passes, but only propagate `liquidation_bonus`/`liquidation_fees` when the account clears the floor under the *minimum* of old and new thresholds — the weakest measurement, matching the vault-key fix that added PCR14 rather than trusting a partial measurement.

### Proof of Concept
Sequence (all entrypoints real; mirror of `regression_third_party_keeper_cannot_force_adverse_tuple_below_min_hf` but with a mixed-direction edit):

1. ALICE supplies 10,000 USDC, borrows 3.0 ETH; stored tuple `(ltv 7500, lt 8000, bonus 500, fee 1200)`. Push USDC price down so the account's HF under LT 8000 lands in `[1.00, 1.05)` — still healthy, below the restamp floor.
2. Governance executes `AdminOperation::EditAssetInSpoke` on the USDC listing: `liquidation_threshold = 8500`, `liquidation_bonus = 1000`. Now HF under the *new* LT = old HF × 8500/8000 ≥ 1.05.
3. Any keeper calls `controller.update_account_threshold(keeper, true, [alice_id])`.
   - `favors_liquidator` → true (bonus 1000 > 500);
   - `clears_min_hf` substitutes LT = 8500 → hypothetical HF ≥ 1.05 → **passes**, even though the account's held-vintage HF is below the floor;
   - `position.liquidation_bonus = 1000` is written by `update_or_remove_supply_position` and persisted at params.rs:218.
4. After a further price decline makes HF < 1, `liquidate` computes `base_bps = min(weighted stored bonus, max)` = 1000 instead of 500, doubling the liquidator's extraction per repaid dollar relative to the vintage the M1 guarantee was supposed to preserve.

Existing test `test_update_account_threshold_propagates_adverse_tuple_to_healthy_account` (keeper.rs:269) confirms mixed tuples propagate wholesale when the gate passes; no test covers a mixed-direction edit against a sub-floor account.
