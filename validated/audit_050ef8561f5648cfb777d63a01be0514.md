### Title
Uncontrolled Recursion in Address Definition Evaluation Leads to Node Crash - (File: definition.js)

### Summary
The Wireshark CVE describes a dissector that recurses without a hard depth bound while parsing untrusted nested data, crashing the process via stack exhaustion. The ocore analog is `validateDefinition`'s nested `evaluate(arr, path, bInNegation, cb)` function in `definition.js`, which recursively walks an address/asset-condition definition tree (`and`, `or`, `r of set`, `weighted and`, nested `address`, `definition template`) using native synchronous/callback recursion rather than a depth-bounded or trampolined loop [1](#0-0) .

### Finding Description
`evaluate()` only bounds recursion indirectly through `complexity` and `count_ops` counters checked against `constants.MAX_COMPLEXITY` / `constants.MAX_OPS` at the top of each call [2](#0-1) . There is no explicit recursion-depth counter analogous to `MAX_DEPTH` used elsewhere (e.g., `aa_validation.js`'s `validateFieldWrappedInCases`/`validate` functions, which explicitly track `depth` and abort with `"max depth reached"` [3](#0-2) [4](#0-3) , and `formula/validation.js`'s `evaluate`, which tracks `depth` and aborts at `depth > 100` [5](#0-4) ). In `definition.js`, each nested `and`/`or`/`r of set`/`weighted and` node causes a new synchronous call into `evaluate()` via `async.eachSeries`, and each `address` op triggers a fresh nested `evaluate()` call after resolving the inner address's definition from storage or from co-author-supplied definitions in the same unit [6](#0-5) . Because posting a unit lets an attacker fully control the `definition` field structure (an unprivileged unit poster defining a new address, or an AA author defining/triggering an AA with an address definition), an attacker can submit a deeply nested boolean-condition tree (e.g., thousands of nested `['and', [[...]]]` levels) that increments `complexity`/`count_ops` by only 1 per level while driving JS call-stack depth to the same value, well before `MAX_COMPLEXITY`/`MAX_OPS` are reached if those limits are large relative to available stack frames, or even if they are hit, the check happens only after already recursing to that depth — meaning the stack growth itself, not the error return, is the crash vector.

### Impact Explanation
A crafted unit or AA definition with deeply nested boolean/address conditions can cause `evaluate()` in `definition.js` to blow the V8 call stack ("Maximum call stack size exceeded"), crashing the ocore process that is validating the unit. Because full nodes, hubs, and wallets all execute `validateDefinition`/`validateAuthentifiers` when validating any incoming unit that defines or uses an address definition, a single malicious unit broadcast to the network can crash multiple nodes attempting to validate/process it, potentially halting confirmation of new units on affected nodes (denial of service), which matches the required impact bar of "a network unable to confirm new units."

### Likelihood Explanation
Likelihood is high for the "reachability" dimension: any unprivileged user can post a unit containing an arbitrarily deep address definition (new address definition, AA definition with nested conditions, or asset issue/transfer conditions) since these fields are attacker-controlled unit payload content, not privileged/network-only fields. The actual crash trigger depends on whether `MAX_COMPLEXITY`/`MAX_OPS`/stack limits allow reaching V8's default stack frame limit before the complexity/op count checks trip — this exact threshold could not be fully confirmed from the available context because the numeric values of `constants.MAX_COMPLEXITY` and `constants.MAX_OPS` in `constants.js` were not retrievable in this session (tool budget exhausted before the file content loaded).

### Recommendation
Add an explicit depth counter to `evaluate()` in `definition.js` (mirroring the `MAX_DEPTH` pattern already used in `aa_validation.js` and the `depth > 100` pattern in `formula/validation.js`), and reject or fail validation once a bounded nesting depth is exceeded — independent of the complexity/op counters — before recursing further. Alternatively, convert `evaluate()`'s recursion into an explicit iterative worklist/stack-based traversal to remove reliance on the native call stack altogether.

### Proof of Concept
Post a unit whose address `definition` (or AA definition's nested address/asset condition) is a deeply right-nested boolean expression, e.g. programmatically construct:
```
['and', [['and', [['and', [ ... thousands of levels ... ['sig', {...}]] ]]]]]
```
and submit it as the `definition` field of a new address-defining unit (or as an `issue_condition`/`transfer_condition` in an asset-defining message, or as a nested AA definition). When a node calls `validateAuthentifiers` → `validateDefinition` → `evaluate` on this payload during standard unit validation, the recursive descent through thousands of nested `and` nodes can exhaust the call stack and crash the validating process.

**Note on completeness:** I was unable to verify the exact numeric values of `constants.MAX_COMPLEXITY`, `constants.MAX_OPS`, and `constants.pemCurvesFixMci` in `constants.js` before running out of tool iterations, so I cannot state with certainty whether these limits are reached before or after a stack-overflow-inducing depth is hit in practice. A Devin session with full file access would be needed to confirm the exact threshold and reproduce the crash empirically.
