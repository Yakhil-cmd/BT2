StatusHandler#process binds a GitHub status to a bare `sha` with no repository scoping, letting any repository's status webhook write `Shipit::Status` rows for identical-sha commits tracked by unrelated stacks - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` executes `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` with no join or filter on the payload's `repository.full_name`. Every other handler (`PushHandler`, `PullRequest::*`) uses the base `Handler#stacks` helper, which scopes work to `Repository.from_github_repo_name(repository_name)&.stacks`, but `StatusHandler` bypasses this scoping entirely, so a legitimately-signed webhook from repository B can write status rows onto commits belonging to any other stack (including private stack A) that happens to share the same sha.

### Finding Description
The intended binding should be: the set of `Stack` rows whose `deployable?`/`blocked?` state can be affected by one `StatusHandler#process` invocation == `{the stack(s) belonging to the repository named in that invocation's payload}`. In actual code this is: [1](#0-0) 

`process` iterates `Commit.where(sha: params.sha)` across the *entire* `commits` table, with no `repository` or `stack_id` filter, and calls `commit.create_status_from_github!(params)` on each match. Compare this to `Handler#stacks`: [2](#0-1) 

which is what every other handler (`PushHandler`, `PullRequest::*Handler`) uses to constrain its side effects to the repository named in `payload['repository']['full_name']`. `StatusHandler` never calls `stacks` and never reads `repository_name` at all — the repository field of the payload is used only by `WebhooksController#verify_signature` to look up which GitHub App/organization secret to check: [3](#0-2) 

That check only proves "this payload was legitimately signed by GitHub for organization X" — it says nothing about which `sha`s the payload is allowed to touch. Because git commit SHAs are content-addressed, a commit cherry-picked, merged, or otherwise present verbatim in two different repositories (e.g., a shared open-source upstream pulled into a public repo A and a private downstream repo B, or simply two Shipit stacks that both created `Commit` rows for the same upstream sha) will have identical `sha` values across unrelated `Commit` rows in unrelated stacks.

Exploit flow:
1. Attacker owns repository B (or any repo whose commits happen to share a sha with a commit tracked by victim stack(s), e.g. a shared upstream dependency mirrored/vendored into both repos).
2. Attacker observes/learns a sha `S` that is also tracked as a `Commit` row by one or more private Shipit stacks (learned by watching public repo A's history).
3. Attacker triggers (or fabricates, since they control repo B's GitHub integration) a real, GitHub-signed `status` webhook for repository B carrying `sha: S`, `state: "success"`.
4. `WebhooksController#verify_signature` validates the signature against repo B's/organization B's legitimate webhook secret — this passes because it *is* a legitimately-delivered webhook, just for the wrong repository's commit graph.
5. `StatusHandler.call` runs `Commit.where(sha: S)` and finds every `Commit` row across every stack with that sha — including the victim's private stacks — and calls `create_status_from_github!` on each, creating a `success` `Status` for CI context `params.context` on all of them.
6. `Commit#deployable?` / `Commit#blocked?` on the victim stacks now see this forged success status, potentially unblocking `deployable?` and triggering `schedule_continuous_delivery` for continuous-deployment stacks that were gated on that CI context.

Existing guards do not prevent this: `verify_signature` authenticates the sender/organization of the payload, not the scope of the sha the payload can mutate; `drop_unhandled_event` and the `ExplicitParameters` schema only validate presence/shape of `sha`/`state`, not repository ownership; there is no `stacks`/`repository` filter anywhere in `StatusHandler`.

### Impact Explanation
An attacker who controls (or can trigger a webhook from) any single GitHub repository can forge a `success`/`failure`/`error` `Shipit::Status` for an arbitrary sha on every unrelated Shipit stack across every tenant that happens to have a `Commit` row with that sha — regardless of whether that stack's repository has anything to do with the attacker's repository. This can silently satisfy CI/required-status gating (`Commit#deployable?`, `blocked?`) for continuous-deployment stacks, causing unauthorized deploys to proceed on infrastructure the attacker has no access to. This is a payload for one repository mutating another repository's stack/commit records, i.e., Critical impact per the stated categories (unauthorized deploy triggered via cross-tenant record mutation).

### Likelihood Explanation
The only precondition is a sha collision between a commit tracked by the victim stack and a commit the attacker can name in their own repository's status payload — trivially achievable via a shared open-source upstream, a vendored/mirrored commit, or a monorepo split where the same commit content is pushed to multiple GitHub repos with GitHub App/webhook integration. The attacker needs no privileges beyond owning a GitHub repo with the Shipit GitHub App/webhook installed (which is documented as attacker-controllable in-scope). No secrets, sessions, or team membership are required. This is fully repeatable against any number of shas/stacks.

### Recommendation
Scope `StatusHandler#process` to the repository named in the payload, mirroring `Handler#stacks`:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
end
```
This restores the intended binding that a `status` webhook can only affect commits belonging to stacks of the repository that GitHub actually reports the status for.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb
test "status for a shared sha only updates the reporting repository's stack, not unrelated stacks" do
  shared_sha = 'deadbeef' * 5

  stack_a = shipit_stacks(:shipit) # belongs to repo "shopify/shipit-engine" (example)
  stack_b = create_stack(repository_name: 'attacker/unrelated-repo')

  commit_a = stack_a.commits.create!(sha: shared_sha, message: 'upstream commit')
  commit_b = stack_b.commits.create!(sha: shared_sha, message: 'upstream commit')

  payload = {
    'sha' => shared_sha,
    'state' => 'success',
    'context' => 'ci/attacker',
    'repository' => { 'full_name' => stack_b.repository.full_name }
  }

  assert_difference -> { commit_b.statuses.count }, 1 do
    assert_no_difference -> { commit_a.statuses.count } do
      Shipit::Webhooks::Handlers::StatusHandler.call(payload)
    end
  end
end
```
Currently this assertion fails: `commit_a.statuses.count` also increases by 1, because `StatusHandler#process` matches on `sha` alone across the whole `commits` table, proving the cross-repository status forgery.
