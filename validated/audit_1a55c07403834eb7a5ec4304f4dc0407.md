### Title
Stale/attacker-suppliable in-memory pruned-output cache accepted as authoritative spend data without full re-validation - ([File: archiving.js])

### Summary
Chrome's UAF in ANGLE was exploitable because a freed GPU object's memory could be reused for attacker data before its old reference was cleared, letting stale/attacker-controlled bytes be treated as a live valid object. `ocore--002` has a structurally analogous bug class in the "pruning/recovery" machinery for `final-bad` units: when a unit's row content is stripped from SQL (freed) after `min_retrievable_mci` advances, the code substitutes an **in-memory cache entry** (`archiving.js`) or a **freshly-fetched joint from any peer** (`network.js: tryRecoverPrunedContentOfFinalBadUnit`) as the ground truth for spend validation in `validation.js`, verified only by a **ball/hash check**, not full consensus-level validation (sequence, spentness, uniqueness). This lets an unprivileged unit poster construct a payment that spends a locally-pruned `final-bad` output and have different nodes accept divergent output data (address/amount/asset) for the same input, depending on which node happened to have the pruned joint cached at that moment.

### Finding Description
`storage.js:updateMinRetrievableMciAfterStabilizingMci` strips SQL columns for old `final-bad` units and calls `archiving.cachePrunedJoint(objJoint)` [1](#0-0)  to keep the joint body around in a process-local map `assocCachedPrunedJoints` with a 1‑hour TTL [2](#0-1) .

When a new unit's input claims to spend an output of such a stripped unit, `validation.js` no longer has real DB data for that output (`src_output.address` is `null`), so it falls back to `archiving.getCachedOutput(...)` to reconstruct `address/amount/denomination/asset` and treats it as trustworthy: [3](#0-2) 

If the cache miss occurs (TTL expired via `purgeExpiredCachedPrunedJoints`, node restarted, or simply never populated locally), validation instead asks `network.js` to fetch the pruned content from *any peer* and re-populate the cache: [4](#0-3) . That recovered content is accepted into the cache after only `validation.allHashesAreValid(objJoint)` (a ball/hash-chain integrity check) — not a full re-run of `validation.validate` against sequence/uniqueness/spentness state: [5](#0-4) .

This is the ocore analog of a "freed-object-reuse" bug: the authoritative record (SQL row, "freed" by pruning) is replaced by a secondary, weakly-verified in-memory/network-supplied substitute whose lifetime/consistency is not the same as the real object it stands in for. Because different nodes strip content and populate/expire their local cache at different real-time moments (`PRUNED_JOINT_CACHE_TTL_ms = 60*60*1000` vs. arbitrary MCI advancement timing), the *same* input-spending unit can be validated using different substitute data on different nodes, or rejected on some nodes (`cb("output being spent ... not found")`) and accepted on others (via cache hit or peer recovery), producing a **node disagreement on unit validity** for a unit that legitimately spends a pruned final-bad output. Because `final-bad` outputs are explicitly excluded from double-spend detection (`sequence!='final-bad'` in the double-spend queries, e.g. [6](#0-5) ), multiple competing spends of the same pruned output validated with cache-derived data on different nodes are not cross-checked against each other consistently, risking double-spend-like state divergence across the network.

### Impact Explanation
An attacker (any unit poster) who can identify or induce a `final-bad` unit whose content has been locally pruned on some nodes but not others can craft units spending its outputs. Because the substitute data path bypasses the normal fully-validated SQL-backed uniqueness/spentness bookkeeping and instead trusts either a local cache (with a fixed TTL unrelated to actual pruning cadence) or content fetched fresh from an arbitrary peer (validated only by hash, not by full consensus rules), nodes can diverge on whether such a spend is valid, and outputs believed by one node to be a specific address/amount/asset can differ from what another node reconstructs — a direct path to double-spend/consensus-disagreement, which the task's validation targets explicitly recognize as impactful ("node disagreement on validity or stability").

### Likelihood Explanation
This path is reachable purely by posting a normal payment unit (no special privileges needed) whose input references a unit that is old enough to be pruned (`main_chain_index < storage.getMinRetrievableMci()`), a condition that occurs naturally as the chain advances and is deterministic to predict from public MCI data. No malicious peer/hub/network-DoS is required to trigger the "accept differently on different nodes" path; it happens organically from cache-TTL/timing differences that are inherent to normal node operation.

### Recommendation
- Do not substitute cached/peer-recovered joint content as authoritative for spend validation without re-deriving and re-checking full consensus state (uniqueness, spentness, sequence) equivalent to what the original SQL row enforced.
- Make the pruned-joint cache TTL and population deterministic and tied to protocol-level state (e.g., persist stripped-output essentials, such as address/amount/asset/denomination, permanently rather than in a memory cache with wall-clock TTL) so all nodes reconstruct identical data regardless of local timing.
- When recovering pruned content from a peer (`tryRecoverPrunedContentOfFinalBadUnit`), require more than a ball-hash check — replay it through the same double-spend/uniqueness validation as newly-seen units before trusting derived output fields for another unit's validation.

### Proof of Concept
1. Wait for (or identify) a `final-bad` unit `U` whose outputs have been stripped locally (`main_chain_index(U) < getMinRetrievableMci()`), e.g. an old failed double-spend branch.
2. On Node A (which still has `U` in `assocCachedPrunedJoints`, cache not yet expired), post a new unit `V1` that spends `U`'s output — `validation.js:2464` finds `objCachedOutput` and accepts `V1` using that address/amount.
3. On Node B (cache expired, or restarted after the TTL/never received `U`'s recovery), the same or a maliciously modified `U` content is fetched from a possibly different attacker-controlled peer via `tryRecoverPrunedContentOfFinalBadUnit`, verified only by ball-hash equality, and cached; post unit `V2` spending the same output but reconstructed from this independently-sourced content.
4. Because `final-bad` inputs are excluded from cross-unit double-spend detection (`sequence!='final-bad'`), `V1` and `V2` can each be accepted as valid on their respective nodes with different derived output data, demonstrating a reachable path to node disagreement / potential double-spend of a stable(pruned) output via an unprivileged, ordinary unit-posting flow.

const PRUNED_JOINT_CACHE_TTL_ms = 60 * 60 * 1000;
let assocCachedPrunedJoints = {};

function cachePrunedJoint(objJoint){
	assocCachedPrunedJoints[objJoint.unit.unit] = { objJoint: objJoint, expiry_ts: Date.now() + PRUNED_JOINT_CACHE_TTL_ms };
}

function getCachedPrunedJoint(unit){
	const cached = assocCachedPrunedJoints[unit];
	if (!cached)
		return null;
	return cached.objJoint;
}
