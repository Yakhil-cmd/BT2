### Title
Webhook signature verified against org selected from `repository.owner.login` while target Stack/Commit are resolved from unrelated payload fields, enabling cross-organization forged CI status and sync events - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which `GitHubApp` (and therefore which `webhook_secret`) to HMAC-verify the delivery against by reading `repository.owner.login`/`organization.login` straight out of the **unauthenticated** JSON body [1](#0-0) . Once the signature check passes using that attacker-chosen organization's secret, the actual webhook handlers determine *what to act on* using **different, independent fields** of the same body — `repository.full_name` in `Handler#repository_name` [2](#0-1) , or, worse, a bare `sha` lookup with no repository/org scoping at all in `StatusHandler#process` [3](#0-2)  / `Commit.create_status_from_github!` [4](#0-3) . This breaks the trust binding: **organization whose secret authenticated the request ≠ repository/commit that the handler writes to.**

### Finding Description
In a multi-org Shipit deployment (a documented, tested configuration — see `test/dummy/config/secrets_double_github_app.yml` with `OrgOne`/`OrgTwo`, each carrying its own `webhook_secret`) [5](#0-4) , `Shipit.github(organization:)` looks up a distinct `GitHubApp` (and distinct `webhook_secret`) per organization [6](#0-5) .

`WebhooksController#verify_signature` picks that organization purely from the request body:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [7](#0-6) 

This means an attacker who legitimately controls/knows the `webhook_secret` for **any one** organization configured on the shared Shipit instance (e.g. they administer their own org `OrgTwo` on the same Shipit installation and thus know `OrgTwo`'s webhook secret) can set `repository.owner.login = "OrgTwo"` so the signature check passes with a secret they possess, while putting arbitrary other values in the fields the handlers actually consult:

- `PushHandler`/other handlers resolve the target `Stack` via `Handler#repository_name`, which reads `payload.dig('repository', 'full_name')` — a completely separate field from `repository.owner.login` used for signature selection, and never cross-checked against it [2](#0-1) . An attacker can therefore set `repository.owner.login = OrgTwo` (to pick a secret they know) but `repository.full_name = OrgOne/some-repo` to target a stack owned by a completely different, non-consenting organization.
- `StatusHandler` is even weaker: it resolves target commits purely by `Commit.where(sha: params.sha)` with **no repository scoping whatsoever** [3](#0-2) . Any attacker who knows the secret of *any* configured org, plus a target commit SHA (commit SHAs are public information visible on GitHub), can forge a `status` event carrying `state: success` for a commit belonging to a totally unrelated stack/organization. `Commit#create_status_from_github!` then records that status and feeds `Commit#deployable?`/CI gating logic [8](#0-7) , and `add_status` triggers `stack.schedule_merges` and `ContinuousDeliveryJob` for continuous-deployment-enabled stacks [9](#0-8) .

This is structurally the ZkSync bug class translated to this engine: the entity whose credential authenticated the request (the org whose `webhook_secret` matched) is not the entity the resulting write is scoped to (the repository/commit actually mutated). The verification step and the authorization/scoping step read two different untrusted fields of the same payload without cross-validating them.

### Impact Explanation
This allows an attacker who is a legitimate, authorized administrator of Org B (and therefore knows Org B's real `webhook_secret`, configured on the same shared Shipit instance) to forge webhook events that are accepted as valid and are applied to Org A's stacks/commits, even though the attacker has no access to Org A's repository, webhook secret, or GitHub App installation. Concretely:
- Forcing a fake `success` CI status onto an Org A commit, satisfying `ci.require` checks and enabling that commit to become `deployable?` and be auto-deployed via continuous delivery — an **unauthorized deploy**.
- Triggering `sync_github`/branch-sync side effects on Org A's stacks via `PushHandler` using a mismatched `repository.full_name`.

This satisfies the "unauthorized deploy" / "cross-repository writes" High-severity impact criteria, since the write boundary crossed is between organizations that only share the same Shipit application instance, not any shared credential the victim organization issued.

### Likelihood Explanation
Exploitability requires the attacker to be a legitimate member/admin of *some* organization configured on the same multi-tenant Shipit instance (a realistic and intended supported configuration per `docs/setup.md`'s "Using Multiple GitHub Applications" section) [10](#0-9) . No compromise of the victim org's GitHub App, private key, or webhook secret is needed — only knowledge of one's own org's webhook secret and, for the `StatusHandler` path, the target commit SHA (public on GitHub). This is a realistic likelihood for any Shipit deployment shared across multiple GitHub organizations.

### Recommendation
After the HMAC signature is verified for the organization derived from `repository_owner`, cross-validate that every payload field consumed by the downstream handler (`repository.full_name`'s owner, or in `StatusHandler`, the repository owning the target commit) actually belongs to that same verified organization before dispatching to handlers. For `StatusHandler` specifically, scope the `Commit` lookup by the stack's repository/organization matching the verified `repository_owner`, not merely by `sha`.

### Proof of Concept
1. Configure Shipit with two organizations, `OrgA` (victim, has a stack `OrgA/app`) and `OrgB` (attacker-controlled, admin knows `OrgB`'s `webhook_secret`), per the documented multi-org `secrets.yml` schema.
2. Attacker computes `sha1=` HMAC over a crafted JSON body using `OrgB`'s known `webhook_secret`:
```json
{
  "sha": "<sha-of-OrgA-app-commit>",
  "state": "success",
  "context": "ci/forged",
  "repository": { "owner": { "login": "OrgB" }, "full_name": "OrgB/irrelevant" }
}
```
3. POST to `/github/webhooks` with header `X-Github-Event: status` and `X-Hub-Signature: sha1=<computed>`.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: "OrgB")` and verifies the signature successfully (attacker knows `OrgB`'s secret) [1](#0-0) .
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)` — matching the `OrgA/app` commit regardless of the `OrgB` scoping used for signature verification — and calls `create_status_from_github!`, marking the `OrgA` commit `success` [3](#0-2) .
6. If `OrgA/app` has `continuous_deployment` enabled and `ignore_ci`/other required statuses are satisfied, `Commit#deployable?` becomes true and `schedule_continuous_delivery` queues an auto-deploy [11](#0-10)  — an unauthorized deploy triggered entirely with `OrgB`'s own webhook credentials against `OrgA`'s stack.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
