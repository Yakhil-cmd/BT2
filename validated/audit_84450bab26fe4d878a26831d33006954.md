Confirmed: `readAsset` in `storage.js` picks the **latest single `asset_attestors` unit** (highest level/rowid) and treats it as the *complete* attestor list — it does not merge/append across updates (<cite repo="Camomtat/ocore--016" path="storage.js" start="1921-1945" />). Combined with `validateAttestorListUpdate` in `validation.js`, which lets the sole asset definer replace the whole trusted-attestor list in one single-authored message with no confirmation/staging step, this is a direct analog to the reported "single-step critical setter" bug class.### Title
Single-step, unstaged replacement of an asset's spender-attestor list can permanently freeze transfers of an attested asset - (File: validation.js, storage.js)

### Summary
For `spender_attested` assets, the asset definer updates the trusted attestor list by posting a single `asset_attestors` message. This is validated in one pass by `validateAttestorListUpdate` and, once stable, `storage.readAsset` treats the newest `asset_attestors` unit as the *complete, authoritative* attestor list — not an incremental add/remove. There is no staged/two-step confirmation (e.g., propose-then-activate) before the new list takes effect, mirroring the reported anti-pattern of critical, non-recoverable state changes executed in a single atomic call.

### Finding Description
`validateAttestorListUpdate` only checks that the message is single-authored, sent by the asset's `definer_address`, and that the attestor addresses are well-formed and sorted: [1](#0-0) 

There is no restriction limiting the update to an incremental diff, no requirement that the new list overlap with the old one, and no delay/approval mechanism. Once the message becomes stable, `storage.readAsset` locates the single most recent `asset_attestors` unit for the asset (by level/rowid) and uses **only** the attestor rows attached to that unit as the asset's current attestor set, discarding all previously configured attestors: [2](#0-1) 

This full-replacement, single-message design means a mistake by the definer — e.g., a typo in an attestor address, omission of the active attestor(s), or accidentally reusing a template with the wrong addresses — instantly and irrevocably replaces the entire trusted-attestor set for that asset as soon as the unit stabilizes. There is no "propose new list / confirm activation" step analogous to `approve-transferFrom`, which is exactly the missing two-step pattern the original report calls out for critical address/role setters.

### Impact Explanation
`spender_attested` is enforced at payment-validation time: a payment of the asset is rejected unless the payer/issuer address is attested by one of the addresses in the current attestor list: [3](#0-2) 

If the definer's single-step attestor-list update removes or corrupts the addresses that are actually attesting real users (unintentionally, since the whole list is replaced with each update rather than merged), every holder whose only valid attestation was issued by an attestor now excluded from the list becomes unable to prove attestation for future spends. Since `spender_attested` conditions the ability to move the asset at all, this results in funds becoming permanently unspendable/frozen for affected holders until a fresh attestation from a currently-listed attestor is re-obtained (which may be impossible if the removed attestor is unavailable or the mistake is otherwise unrecoverable) — a concrete instance of asset/fund freezing caused by an unstaged critical operation.

### Likelihood Explanation
This requires action only by the asset definer (an ordinary, unprivileged unit poster in ocore's permission model — no special network role) sending one `asset_attestors` message, exactly the kind of single, error-prone call the original report warns about. Given that the update completely replaces rather than incrementally modifies the list, any partial or mistaken update (common in operational key rotations, adding a new attestor while forgetting to re-include existing ones, or copy-paste errors) triggers the freeze without requiring malicious intent.

### Recommendation
- **Short term**: Support incremental attestor list changes (`add`/`remove` semantics) instead of wholesale replacement, and/or require a two-step process: post a proposed new list, then a separate confirmation message (after some validation delay) before it becomes effective, so a mistaken update can be corrected before finalization.
- **Long term**: Document a policy that attestor-list updates should preserve currently-valid attestors unless explicitly intended to be removed, and consider off-chain/tooling checks (e.g., wallet UI diff-view) warning definers when an update would drop previously active attestors, reducing the chance of an irreversible freeze.

### Proof of Concept
1. Definer `D` issues asset `A` with `spender_attested: true` and an initial `asset_attestors` message listing attestors `[X, Y]`.
2. Attestor `X` attests user `U`'s address; `U` can now spend `A` because `validatePayment` finds `U` in `objAsset.arrAttestedAddresses` (derived from list `[X, Y]`).
3. `D` later needs to add attestor `Z` but, due to human error or a buggy tool, posts a new `asset_attestors` message containing only `[Z]` (mistakenly omitting `X` and `Y`).
4. Once this unit stabilizes, `storage.readAsset` picks this newest unit as the sole current attestor list, dropping `X` and `Y`.
5. `U`, still only attested by `X`, can no longer pass the `spender_attested` check in `validatePayment` (`objAsset.arrAttestedAddresses` no longer includes `U`), permanently freezing `U`'s holdings of `A` until re-attested by `Z` — which may not be possible if `Z` is unaware of `U` or unwilling to attest, and there was no way to catch/reverse `D`'s mistake before it took effect.

function validateAttestorListUpdate(conn, payload, objUnit, objValidationState, callback){
	if (objUnit.authors.length !== 1)
		return callback("attestor list must be single-authored");
	if (!isNonemptyObject(payload))
		return callback("attestor update must be a non-empty object");
	if (hasFieldsExcept(payload, ['asset', 'attestors']))
		return callback("foreign fields in attestor list update");
	storage.readAsset(conn, payload.asset, objValidationState.last_ball_mci, false, function(err, objAsset){
		if (err)
			return callback(err);
		if (!objAsset.spender_attested)
			return callback("this asset does not require attestors");
		if (objUnit.authors[0].address !== objAsset.definer_address)
			return callback("attestor list can be edited only by definer");
		err = checkAttestorList(payload.attestors);
		if (err)
			return callback(err);
		callback();
	});
}
