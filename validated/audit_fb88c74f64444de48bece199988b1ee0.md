### Title
Webhook signature is verified against the organization derived from `repository.owner.login`, while handlers act on the independently-attacker-controlled `repository.full_name` — allowing cross-organization/cross-repository forged webhooks - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/`webhook_secret` to verify an inbound webhook's HMAC signature against using `repository_owner`, a value read from the same untrusted JSON body it is about to validate [1](#0-0) [2](#0-1) . However, every event `Handler` determines *which repository/stack to mutate* using a different field of the same body, `repository.full_name`, via `Handler#repository_name` [3](#0-2) . Because the attacker fully controls the raw JSON body before computing its own valid HMAC (using a webhook secret they legitimately know for *their own* onboarded organization), nothing forces `repository.owner.login` and `repository.full_name` to refer to the same repository. This lets a party that only possesses credentials/webhook-secret for organization A forge events that are processed against stacks/repositories belonging to organization B.

### Finding Description
In a multi-organization Shipit deployment — an explicitly documented and supported configuration where each GitHub org has its own `app_id`/`webhook_secret` [4](#0-3)  and is loaded via `Shipit.github(organization:)` [5](#0-4)  — the webhook entry point performs authentication and authorization on two different fields:

1. **Authentication key selection** (`WebhooksController#verify_signature`) uses `repository_owner`, computed as `params.dig('repository','owner','login') || params.dig('organization','login')` [2](#0-1) , to fetch the `GitHubApp` instance and thus the `webhook_secret` used for the HMAC comparison [1](#0-0) .
2. **Target resource resolution** (`Handler#repository_name`/`Handler#stacks`) uses `payload.dig('repository','full_name')` to look up the `Repository`/`Stack` that the event will actually mutate [3](#0-2) .

The HMAC signature only proves that the raw body was signed with *some* org's known secret — it says nothing about internal consistency between `repository.owner.login` and `repository.full_name`. An attacker who legitimately administers (or has been granted a webhook for) organization A — and therefore knows organization A's `webhook_secret` — can hand-craft a JSON payload where `repository.owner.login` = `"orgA"` (so `verify_signature` resolves and validates against orgA's secret) but `repository.full_name` = `"orgB/target-repo"` (a completely unrelated repository under a different, unauthenticated organization). The signature check passes, and the handler proceeds to mutate state for `orgB/target-repo`.

This is structurally identical to the reported `BunniHub`/`ERC20Referrer` bug class: a value (`referrer`) that a privileged action is *supposed* to bind to the depositor is instead taken from an independently-supplied field controlled by the transaction sender, letting the sender overwrite state that belongs to someone else. Here, the value that should be bound to "whoever authenticated" (`repository.owner.login`) is decoupled from the value actually used to select the mutated record (`repository.full_name`), and both are attacker-supplied inside the same signed body.

### Impact Explanation
Concretely reachable handlers that trust `repository.full_name` without re-validating it against the authenticating organization:
- `PushHandler#process` triggers `stack.sync_github(expected_head_sha: params.after)` for every non-archived stack matching the branch of the forged `repository.full_name`, forcing a GitHub sync job against a stack belonging to a different, non-consenting organization [6](#0-5) .
- `StatusHandler#process` creates a `CommitStatus` (`commit.create_status_from_github!`) for any `Commit` matching an attacker-chosen `sha`, without any check that the commit belongs to the org that authenticated the webhook [7](#0-6) . Forged "success" statuses on a stack whose continuous-delivery/merge-queue depends on GitHub status events can move a stack toward an unintended deploy/merge state.
- `MembershipHandler#process` creates/mutates `Team`/`Membership` records scoped to whatever `organization.login` is supplied in the payload, independent of the org used for signature verification [8](#0-7) .

This satisfies the "cross-repository writes" / escalation into stack state and status-stream mutation impact categories: an attacker with credentials scoped to only their own organization's GitHub App/webhook secret can write into the state of stacks belonging to a different organization hosted on the same Shipit instance.

### Likelihood Explanation
High for any Shipit instance configured with more than one GitHub organization (the multi-org config is a first-class, documented feature, not a misconfiguration) [4](#0-3) . The attacker only needs the legitimately-issued webhook secret for their own organization (which they possess by design, since they administer that org's GitHub App/webhook) and the target repository's `full_name`, which is generally public/known information (e.g., `github.com/orgB/repo`).

### Recommendation
After resolving the organization used for signature verification, re-derive the repository/stack strictly from that same trusted organization context (e.g., verify `repository.owner.login == repository_owner` before dispatching to handlers, or pass the authenticated organization explicitly into each `Handler` and require it match `repository.full_name`'s owner segment) rather than letting handlers independently re-parse an unrelated field of the same untrusted payload.

### Proof of Concept
1. Configure Shipit with two organizations, `orgA` and `orgB`, each with its own `webhook_secret` (per `docs/setup.md` multi-org example).
2. As an admin of `orgA` only (attacker), craft a JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "orgA" },
    "full_name": "orgB/target-repo"
  }
}
```
3. Compute `X-Hub-Signature: sha1=<hmac>` using `orgA`'s known `webhook_secret` over the raw body.
4. POST to `/webhooks` with `X-Github-Event: push`. `verify_signature` calls `Shipit.github(organization: 'orgA')` and validates successfully [1](#0-0) .
5. `PushHandler` resolves stacks via `Repository.from_github_repo_name('orgB/target-repo')` [3](#0-2)  and triggers `sync_github` on `orgB`'s stack, despite the request only being authenticated with `orgA`'s secret.

## Creating the GitHub App

Shipit needs a GitHub App to authenticate users, receive Webhooks and access the API.

You can create a new one for your organization at `https://github.com/organizations/<your-org>/settings/apps/new`, or [https://github.com/settings/apps/new](https://github.com/settings/apps/new) for a regular user.

  - Homepage URL: The URL where Shipit will be deployed, e.g. `https://example.com`.
  - User authorization callback URL: It must be set to `<homepage>/github/auth/github/callback`, e.g. `https://example.com/github/auth/github/callback`.
  - Setup URL: Leave it empty.
  - Webhook URL: It must be set to `<homepage>/webhooks`, e.g. `https://example.com/webhooks`.
  - Webhook secret (optional): Fill it with some randomly generated string, and *keep it in clear on the side, you'll need it later*.
