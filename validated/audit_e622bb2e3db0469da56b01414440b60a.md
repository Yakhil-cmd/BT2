### Title
Unbound device_address in `new_shared_address` lets any paired device hijack signing-request routing for a shared/multisig address - ([File: wallet_defined_by_addresses.js])

### Summary
`handleNewSharedAddress()` accepts a `new_shared_address` device message and writes attacker-supplied `device_address` values into `shared_address_signing_paths` for every signing path in the shared-address definition, without ever checking that the sender of the message (`from_address`) is actually authorized to claim those signing paths/devices. This is analogous to the Rdiffweb flaw: the message handler enforces no binding between the authenticated subject (the paired device that sent the message) and the identity/device it is asserting control over on behalf of other cosigners.

### Finding Description
The device-message dispatcher in `wallet.js` routes the `new_shared_address` subject straight into `walletDefinedByAddresses.handleNewSharedAddress(body, callbacks)` **without passing `from_address`**: [1](#0-0) 

`handleNewSharedAddress()` itself has no `from_address`/sender parameter at all: [2](#0-1) 

Its only checks are:
1. `body.definition` hashes to `body.address` (chash check).
2. Each `signerInfo.address` in `body.signers` is a syntactically valid address.
3. Each signing-path's `signerInfo.address` matches the address encoded in the `definition` tree (`extractAddressPathsFromDefinition`).
4. `determineIfIncludesMeAndRewriteDeviceAddress()` verifies that at least one of the member addresses in `signers` belongs to *my* `my_addresses`/`shared_addresses`, and rewrites `device_address` to my own device **only for the paths that are mine**: [3](#0-2) 

Crucially, for every *other* signing path (the ones representing other cosigners), the `device_address` supplied by the message sender is trusted verbatim and persisted: [4](#0-3) 

There is no check anywhere in this flow that the peer sending the `new_shared_address` message (`from_address`) is the device that actually owns the addresses/paths it is asserting in `signers`. Nothing ties the authenticated sender identity to the `device_address` fields being written into the database.

This `device_address` value later drives signing-request routing. When my wallet needs a cosigner's signature for a payment from that shared address, `findAddress()` looks up `shared_address_signing_paths` and, if the resolved `device_address` isn't mine, forwards the entire unsigned unit to that (attacker-controlled) device instead of the real cosigner: [5](#0-4) [6](#0-5) 

### Impact Explanation
Any device that is merely a *paired correspondent* (not necessarily a legitimate cosigner of the shared address) can send a crafted `new_shared_address` message that includes my own address as one member (satisfying `determineIfIncludesMeAndRewriteDeviceAddress`) plus arbitrary `device_address` values for the *other* signing paths. My wallet will accept and store this shared-address record and its (attacker-poisoned) routing table. From that point on, whenever my wallet composes a transaction from that shared/multisig address requiring a cosigner's signature, the signing request (containing the full unsigned unit / payment details) is sent to the attacker-designated `device_address` instead of the genuine cosigner device.
- The genuine cosigner never receives the signing request, so the multisig output can never be validly signed and spent — a real, unauthorized freezing of funds held at that shared address (denial of spending / node fund-freezing impact).
- The unsigned transaction (amounts, addresses) is disclosed to the attacker-controlled device, a confidentiality breach of what should be a private multi-party signing negotiation.
- Because `shared_addresses`/`shared_address_signing_paths` are also propagated (`forwardNewSharedAddressToCosignersOfMyMemberAddresses`), a single forged message can poison the routing view held by multiple parties in the multisig group.

This matches the CWE-284 pattern in the analog report: an authenticated principal (a paired device) can act on behalf of / impersonate control over a resource (another cosigner's routing entry) that it does not own, because the API never binds the message body's claims to the sender's own identity.

### Likelihood Explanation
`new_shared_address` is reachable from any already-paired correspondent device (it is not even required to be in the noncorrespondent whitelist, and pairing itself is trivially achievable via any shared pairing code/URI). No signature over the `signers` mapping is required, and none of the described checks verify sender-to-claim binding. Constructing the message only requires knowledge of a legitimate shared-address definition template (which is exchanged during normal cosigner offer/approval flows the attacker can observe/participate in as one of the paired devices), making this straightforward for a malicious paired counterparty to exploit.

### Recommendation
Pass `from_address` into `handleNewSharedAddress` (and `addNewSharedAddress`) and enforce that:
- Each `device_address` claimed in `signers` for a signing path must be independently verified — e.g., only accept `device_address` values that are already known to be the genuine owners of that member address (via existing `peer_addresses`/`my_addresses`/prior correspondent records), or require that non-self entries be corroborated by a message/notification originating from the claimed device itself.
- Reject or flag `new_shared_address` submissions where the sender (`from_address`) is not one of the `device_address` values already associated (via `wallet_signing_paths`/`peer_addresses`) with the corresponding member address, rather than trusting the message body outright.

### Proof of Concept
1. Attacker device A pairs with victim device V (normal pairing flow).
2. A crafts a `definition` for a 2-of-2 (or n-of-n) shared address where one leaf address is V's real address (`my_addresses`), and another leaf is a legitimate third cosigner C's real address.
3. A sends V a `new_shared_address` message with `signers` mapping: V's path → V's own address (satisfies "I am a member" check), and C's path → `{address: C's real address, device_address: A's own device_address}` (instead of C's true device).
4. V's `handleNewSharedAddress` validates the definition/chash and the "am I a member" check, rewrites only V's own path to V's device, and stores C's path with `device_address = A` in `shared_address_signing_paths` — no verification that A actually is C.
5. V later attempts to spend from the shared address; `findAddress` resolves C's signing path to device A and sends the unsigned unit to A via `ifRemote`, instead of to C. C never sees the signing request; the transaction can never be completed, freezing funds at that shared address, and A obtains a copy of the (private) unsigned transaction.

function determineIfIncludesMeAndRewriteDeviceAddress(assocSignersByPath, handleResult){
	var assocMemberAddresses = {};
	var bHasMyDeviceAddress = false;
	for (var signing_path in assocSignersByPath){
		var signerInfo = assocSignersByPath[signing_path];
		if (signerInfo.device_address === device.getMyDeviceAddress())
			bHasMyDeviceAddress = true;
		if (signerInfo.address)
			assocMemberAddresses[signerInfo.address] = true;
	}
	var arrMemberAddresses = Object.keys(assocMemberAddresses);
	if (arrMemberAddresses.length === 0)
		return handleResult("no member addresses?");
	db.query(
		"SELECT address, 'my' AS type FROM my_addresses WHERE address IN(?) \n\
		UNION \n\
		SELECT shared_address AS address, 'shared' AS type FROM shared_addresses WHERE shared_address IN(?)", 
		[arrMemberAddresses, arrMemberAddresses],
		function(rows){
		//	handleResult(rows.length === arrMyMemberAddresses.length ? null : "Some of my member addresses not found");
			if (rows.length === 0)
				return handleResult("I am not a member of this shared address");
			var arrMyMemberAddresses = rows.filter(function(row){ return (row.type === 'my'); }).map(function(row){ return row.address; });
			// rewrite device address for my addresses
			if (!bHasMyDeviceAddress){
				for (var signing_path in assocSignersByPath){
					var signerInfo = assocSignersByPath[signing_path];
					if (signerInfo.address && arrMyMemberAddresses.indexOf(signerInfo.address) >= 0)
						signerInfo.device_address = device.getMyDeviceAddress();
				}
			}
			handleResult();
		}
	);
}

// {address: "BASE32", definition: [...], signers: {...}}
function handleNewSharedAddress(body, callbacks){
	if (!ValidationUtils.isArrayOfLength(body.definition, 2))
		return callbacks.ifError("invalid definition");
	if (typeof body.signers !== "object" || Object.keys(body.signers).length === 0)
		return callbacks.ifError("invalid signers");
	try {
		var addr = objectHash.getChash160(body.definition);
	}
	catch (e) {
		return callbacks.ifError("invalid definition: " + e);
	}
	if (body.address !== addr)
		return callbacks.ifError("definition doesn't match its c-hash");
	for (var signing_path in body.signers){
		var signerInfo = body.signers[signing_path];
		if (signerInfo.address && signerInfo.address !== 'secret' && !ValidationUtils.isValidAddress(signerInfo.address))
			return callbacks.ifError("invalid member address: " + JSON.stringify(signerInfo.address));
	}
	const assocDefinitionAddresses = extractAddressPathsFromDefinition(body.definition);
	for (let signing_path in body.signers) {
		const signerInfo = body.signers[signing_path];
		if (assocDefinitionAddresses[signing_path] !== signerInfo.address)
			return callbacks.ifError("signer address at path " + signing_path + " doesn't match definition");
	}
	for (let def_path in assocDefinitionAddresses) {
		if (!body.signers[def_path])
			return callbacks.ifError("no signer for definition address at path " + def_path);
	}
	determineIfIncludesMeAndRewriteDeviceAddress(body.signers, function(err){
		if (err)
			return callbacks.ifError(err);
		validateAddressDefinition(body.definition, function(err){
			if (err)
				return callbacks.ifError(err);
			addNewSharedAddress(body.address, body.definition, body.signers, body.forwarded, callbacks.ifOk);
		});
	});
}
