### Title
Offline (non-network-aware) `is_valid_signed_package` sets `last_ball_timestamp = 0`, letting attackers retroactively satisfy time-gated address-definition conditions - (File: `signed_message.js`, `definition.js`)

### Summary
`is_valid_signed_package` in `formula/evaluation.js` allows an AA to verify a caller-supplied signed package without requiring a `last_ball_unit` reference (network-aware mode). When `last_ball_unit` is omitted, `signed_message.js`'s `validateOrReadDefinition` hard-codes `last_ball_timestamp = 0` for the definition evaluation. If the target address's definition (or any nested definition being verified through the signed package) contains a `['timestamp', [relation, T]]` clause used to gate authorization to a specific time window, that clause is evaluated against `0` instead of any real, attacker-supplied point in time — silently satisfying "before/at time T" conditions that were never actually true when the signature was produced, or defeating "not before T" style windows entirely.

### Finding Description
- `formula/evaluation.js` (`case 'is_valid_signed_package'`) accepts a `signedPackage` object with optional `last_ball_unit`. If `last_ball_unit` is present, the current mci/timestamp bounds are read from the DB; if absent, `signed_message.validateSignedMessage` is called with `bNetworkAware = false`. [1](#0-0) 
- In `signed_message.js`, when `bNetworkAware` is false, the definition is validated with a fixed, meaningless timestamp: `cb(objAuthor.definition, (mci >= constants.pemCurvesFixMci) ? mci : -1, 0);` — the third argument (`last_ball_timestamp`) is unconditionally `0`. [2](#0-1) 
- This `last_ball_timestamp` is placed directly into `objValidationState.last_ball_timestamp`, which is what backs the `timestamp` opcode in address-definition evaluation. [3](#0-2) 
- `definition.js`'s `validateAuthentifiers` implements the `timestamp` operator purely as a comparison against `objValidationState.last_ball_timestamp`, with no separate sanity check that this value reflects a real point in time. [4](#0-3) 
- Note also that `objSignedMessage` explicitly permits (and silently ignores) a `timestamp` field in its schema (`hasFieldsExcept(objSignedMessage, [..., "timestamp", ...])`), but this field is never read or enforced anywhere — an unused "boundary" field exactly analogous to the unchecked `cashbackClaim.startTime` in the reference report. [5](#0-4) 

This is architecturally identical to the referenced bug class: a time-boundary value that exists in the protocol data model but is never enforced/derived correctly, so any consumer relying on it for time-window gating gets an incorrect (here, always-zero) value, causing time conditions to be trivially and unconditionally satisfied instead of reflecting the real signing time.

### Impact Explanation
Any AA definition using `is_valid_signed_package(...)` to authorize actions from off-chain signed packages, in combination with `timestamp`-based conditions in the counterparty's address definition (e.g. "signature only valid before expiry T" or "only valid after some vesting/lock start T"), can be bypassed: because `last_ball_timestamp` is forced to `0` in the non-network-aware path, any `timestamp < T` check trivially passes and `timestamp > T` trivially fails, regardless of when the package was actually produced. This can be exploited in AA patterns such as payment/state channels or order-book/timelocked exchange contracts (both present as reference samples using `is_valid_signed_package`) to forge validity for stale, expired, or not-yet-valid signed authorizations, resulting in unauthorized fund movement or bypass of a timelock enforced purely through the definition's `timestamp` clause — i.e., concrete AA fund loss/miscalculated authorization, analogous to the retroactive-reward drain in the reference report.

### Likelihood Explanation
Exploitation requires an AA author to combine `is_valid_signed_package` with a `timestamp`-gated address definition on the counter-signing address, and for the offline package to omit `last_ball_unit` — a documented, legitimate usage mode of signed packages (mentioned directly in `signMessage`'s comment: "with bNetworkAware=true, last_ball_unit is added ... otherwise no last_ball_unit"). This is a realistic pattern for off-chain-negotiated payment/state channels (as shown by `test/samples/payment_channels.oscript`, which uses `is_valid_signed_package` on peer-supplied packages), so any AA author who adds a `timestamp` check to the definition of a peer's signing address (e.g. for signature expiry) would unknowingly introduce this bypass. Likelihood is medium: it depends on an AA design decision by the AA author to combine these two primitives, but the primitives themselves are directly reachable by any unprivileged AA trigger sender supplying attacker-controlled `signed_message` payloads in `trigger.data`.

### Recommendation
Do not silently default `last_ball_timestamp` to `0` for non-network-aware signed packages. Either:
1. Reject `timestamp`-opcode usage in definitions evaluated via a non-network-aware signed package (mirroring how `bNoReferences` already disables reference-based opcodes for this case), or
2. Require an actual timestamp to be supplied and cryptographically bound into the signed package (using the previously-unused `objSignedMessage.timestamp` field) and validate it in `validateSignedMessage`, and use it for the `timestamp` opcode instead of the hard-coded `0`.

### Proof of Concept
1. Address `B` sets its definition to `['and', [ ['sig', ...], ['timestamp', ['<', EXPIRY_TS]] ]]`, intending signatures to expire at `EXPIRY_TS`.
2. `AA` contains oscript logic: `is_valid_signed_package(trigger.data.sentByPeer, addressB)` to authorize a state transition (e.g., closing a channel with a claimed balance), modeled directly on `test/samples/payment_channels.oscript` lines 45/111.
3. Attacker (controlling address `B`, or having obtained an old/expired signature from `B`) constructs `signedPackage` without a `last_ball_unit` field (a legitimately supported, "offline" mode per `signMessage`'s own comment).
4. `is_valid_signed_package` routes to `signed_message.validateSignedMessage` with `bNetworkAware=false`, which calls back with `last_ball_timestamp = 0`. [6](#0-5) 
5. `definition.js`'s `timestamp` opcode evaluates `0 < EXPIRY_TS` → always true, so the intended expiry check is defeated and the (should-be-expired) signature is accepted as currently valid, letting the attacker push a stale claim (e.g., an outdated/unfavorable channel balance) through the AA's message logic.
