Key finding: `verify_signature` in `WebhooksController` looks up `Shipit.github(organization: repository_owner)` and validates the HMAC against that **specific organization's** `webhook_secret` [1](#0-0) [2](#0-1) . `repository_owner` is derived from `params.dig('repository','owner','login') || params.dig('organization','login')` — i.e., for a membership event it's the attacker's own org login, since that's the only org data present in the payload [3](#0-2) . This means the signature only proves the payload was signed with **the attacker's own org's webhook secret** — it does not, and cannot, prove anything about the victim org's `github_id` values.

The binding the question claims is broken — "org that authenticated payload == org owning team mutated" — is enforced at signature-verification time by binding `webhook_secret(repository_owner)` to the signature, but this only proves authenticity of the sender's identity as `repository_owner = organization.login` from the attacker's own payload; it does **not** bind `team.id` to that organization at all in `find_or_create_team!`, which matches solely on `github_id` [4](#0-3) . So the equality that should hold — `Team.find_by(github_id: params.team.id).organization == params.organization.login` — is never checked; if a `Team` row already exists in the DB with `github_id` equal to whatever integer the attacker supplies in `params.team.id`, `find_or_create_by!` will match that row regardless of which org's secret signed the request, and `team.add_member(member)` will add the attacker's own (attacker-controlled) user to that victim team [5](#0-4) . This is a real cross-tenant write: an attacker who controls a GitHub org (and thus its webhook secret from Shipit's perspective) can send a validly-signed `membership` event naming a `team.id` that collides with a previously-synced victim team, and Shipit will grant them membership.

The described "enumerability" precondition (GitHub team ids being sequential/discoverable via public org team listing) does not change this core defect — it only affects how easily the attacker can discover a colliding `github_id`. GitHub does assign monotonically increasing team IDs across the entire platform, and team IDs for any org with at least one publicly-listable team are visible via `GET /orgs/{org}/teams`, so guessing/discovering a collision with a smaller-scale target is plausible, though this specific enumeration mechanic is outside this engine's own code and not independently provable here — the core vulnerability is the missing organization-scoping in `find_or_create_team!`, which is the same root cause as the primary/headline finding on this same line.

### Title
Cross-tenant team hijack via unscoped `Team.find_or_create_by!(github_id:)` in membership webhook handler - (File: app/models/shipit/webhooks/handlers/membership_handler.rb)

### Summary
`MembershipHandler#find_or_create_team!` looks up teams solely by `github_id`, with no check that the requesting organization (validated only against its own webhook secret) actually owns that `github_id`. An attacker who controls any GitHub organization can sign a `membership` webhook naming a `team.id` belonging to a different, previously-synced victim org, and Shipit will add the attacker's chosen user to that victim team.

### Finding Description
The broken binding is: `Team.find_by(github_id: params.team.id).organization == params.organization.login`. This is never checked. `verify_signature` only establishes `signature == HMAC(webhook_secret(repository_owner), raw_post)` for the attacker's own organization — it authenticates *who sent the request*, not *which team the request may mutate* [1](#0-0) . `find_or_create_team!` then does `Team.find_or_create_by!(github_id: params.team.id) { |team| team.organization = params.organization.login }` [4](#0-3) . Since the lookup key is only `github_id` (not scoped by `organization`), and the `Team` model enforces no uniqueness or cross-field validation between `organization` and `github_id` [6](#0-5) , if a `Team` row already exists (from `rake teams:fetch` or a prior legitimate event) with that `github_id` belonging to a victim org, the existing (victim) row is returned unchanged and `team.add_member(member)` runs against it [5](#0-4) .

Exploit flow: attacker registers/owns GitHub org `evil-org`, configures it (or it's already configured) in Shipit's `github_apps` config with its own `webhook_secret`. Attacker sends `POST /webhooks` with `X-Github-Event: membership`, signed with `evil-org`'s webhook secret, payload: `{"action":"added","team":{"id":<victim_team_github_id>,...},"organization":{"login":"evil-org"},"member":{"login":"attacker-user"}}`. Signature verification passes (it only checks `evil-org`'s secret). The handler finds the existing victim `Team` row by `github_id` and adds `attacker-user` as a member.

### Impact Explanation
This grants the attacker's chosen user unauthorized membership in a victim organization's `Team` record inside Shipit. If that team is referenced by `Shipit.github_teams`/`User#authorized?` or by stack-level team-based authorization, this escalates the attacker into privileged Shipit roles for a repository/stack they do not own — matching the High/Critical categories of "escalation into `Shipit.github_teams` authorization" or "a payload for one repository mutating another's ... team." It is fully repeatable against any victim `github_id` the attacker can discover, and blast radius spans all tenants whose teams have been synced into Shipit.

### Likelihood Explanation
Preconditions: the victim org's team must already exist as a `Team` row in Shipit (via `rake teams:fetch` or a prior `membership` webhook) so its `github_id` is fixed; the attacker must control some GitHub org configured in Shipit (or any org for which Shipit accepts webhooks) to obtain a valid signature over an attacker-chosen payload; and the attacker must know or guess the victim's `github_id` value. GitHub team IDs are global sequential integers, and org team lists are viewable via the GitHub API for orgs with public teams, making guessing/discovery feasible without any Shipit secrets. Attacker cost is a single signed HTTP POST; no session, API token, or Shipit secret is needed beyond control of one legitimate (even low-privilege) GitHub org webhook.

### Recommendation
Scope the team lookup by both `organization` and `github_id` (e.g., `Team.find_or_create_by!(organization: params.organization.login, github_id: params.team.id)`), add a DB/model uniqueness validation on `(organization, github_id)` or on `github_id` alone tied to `organization`, and reject the webhook if an existing `Team` with that `github_id` has a different `organization` than the payload's `organization.login`.

### Proof of Concept
1. In `test/models/shipit/webhooks/handlers/membership_handler_test.rb`-style test: create `Team` fixture `victim_team` with `organization: 'victim-org'`, `github_id: 4242`.
2. Build a `membership` webhook payload with `organization.login = 'evil-org'`, `team.id = 4242`, `member.login = 'attacker-user'`, `action = 'added'`.
3. Assert before: `victim_team.members` does not include any user named `attacker-user`.
4. Invoke `MembershipHandler.new(payload).call` (or POST through the controller stubbing `Shipit.github(organization: 'evil-org').verify_webhook_signature` to return true, simulating a validly-signed request from `evil-org`).
5. Assert after: `Team.find_by(github_id: 4242).organization == 'victim-org'` (unchanged) AND `Team.find_by(github_id: 4242).members.map(&:login)` now includes `'attacker-user'`, proving a user was added to `victim-org`'s team via a payload authenticated only for `evil-org`.

# frozen_string_literal: true

module Shipit
  class Team < Record
    REQUIRED_HOOKS = %i[membership].freeze

    has_many :memberships
    has_many :members, class_name: :User, through: :memberships, source: :user

    has_many :github_hooks,
             -> { where(event: REQUIRED_HOOKS) },
             foreign_key: :organization,
             primary_key: :organization,
             class_name: 'GithubHook::Organization',
             inverse_of: false

    class << self
      def find_or_create_by_handle(handle)
        organization, slug = handle.split('/').map(&:downcase)
        find_by(organization:, slug:) || fetch_and_create_from_github(organization, slug)
      end

      def fetch_and_create_from_github(organization, slug)
        return unless github_team = find_team_on_github(organization, slug)

        create!(github_team:, organization:)
      end

      def find_team_on_github(organization, slug)
        gh_api = Shipit.github(organization:).api
        teams = Shipit::OctokitIterator.new(github_api: gh_api) { gh_api.org_teams(organization, per_page: 100) }
        teams.find { |t| t.slug == slug }
      rescue Octokit::NotFound
      end
    end

    def handle
      "#{organization}/#{slug}"
    end

    def add_member(member)
      members.append(member) unless members.include?(member)
    end

    def refresh_members!
      github_api = Shipit.github(organization:).api
      github_members = Shipit::OctokitIterator.new(github_api.get(api_url).rels[:members])
      members = github_members.map { |u| User.find_or_create_from_github(u) }
      self.members = members
      save!
    end

    def github_team=(github_team)
      self.name = github_team.name
      self.slug = github_team.slug
      self.api_url = github_team.url
      self.github_id = github_team.id
    end
  end
