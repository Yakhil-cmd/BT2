### Title
Unbounded batching of private payment chains causes resource exhaustion in wallet message handling - (File: wallet.js)

### Summary
`wallet.js`'s `handlePrivatePaymentChains()` accepts a `body.chains` array from any paired device (a private-payment counterparty forwarding a payment) and processes every chain, and every element inside every chain, with `async.eachSeries`, without ever bounding the number of chains or the length of each chain before doing expensive work (hashing, crypto/signature validation, and DB queries) for each element. [1](#0-0) [2](#0-1) 

### Finding Description
The only checks performed on the incoming payload are structural (`isNonemptyArray`, `isNonemptyObject`, presence of certain fields) — there is no cap on `arrChains.length`, nor on the length of each `arrPrivateElements` chain: [3](#0-2) 

Each chain is then handed to `network.handleOnlinePrivatePayment`, which performs hash computation (`objectHash.getBase64Hash`) and, per the queued/validated flow, triggers full private-payment chain validation (crypto/signature checks and multiple DB lookups for each element of the chain) via the existing private-payment validation pipeline (`private_payment.js` / `network.js`): [4](#0-3) 

This is structurally analogous to the Saleor GraphQL vulnerability: a single external message (the GraphQL "query"/"chains" batch) contains an attacker-controlled number of independent sub-operations (aliased GraphQL fields / private-payment chain elements), each of which is fully processed by the server without any per-request cap on how many sub-operations can be bundled together, so cost scales linearly (or worse, given nested DB calls and forwarding) with attacker-chosen input size.

Contrast this with the unit-level validation path, which strictly limits nested/repeated structures: `constants.MAX_MESSAGES_PER_UNIT`, `MAX_INPUTS_PER_PAYMENT_MESSAGE`, `MAX_OUTPUTS_PER_PAYMENT_MESSAGE`, `MAX_RESPONSES_PER_PRIMARY_TRIGGER`, `MAX_COMPLEXITY`/`MAX_OPS` for oscript/AA formulas, and `MAX_DEPTH` for AA definitions and formula recursion — all of which exist specifically to prevent this class of resource-exhaustion bug elsewhere in ocore. [5](#0-4) [6](#0-5) [7](#0-6) [8](#0-7) 

No equivalent cap exists for the number of private-payment chains or chain length accepted in a single `private_payment_chain` device message.

### Impact Explanation
A malicious paired device (any private-payment counterparty who has an active pairing/correspondence with the victim's wallet) can send a single `private_payment_chain` message containing a very large `chains` array (or chains with very long element sequences). The victim wallet will iterate over every chain and element, computing hashes and performing full crypto/DB validation for each one, and will additionally attempt to forward the chains to other wallet members (`forwardPrivateChainsToOtherMembersOfOutputAddresses`), multiplying the cost. This consumes CPU, memory, and DB connection resources on the victim's node/wallet with a single message, potentially freezing the wallet process and preventing it from processing legitimate payments or unit validation — a resource exhaustion outcome directly analogous to the reported GraphQL batching vulnerability.

### Likelihood Explanation
Any device that has an established pairing with the victim (a normal, unprivileged private-payment counterparty) can trigger this by sending a crafted `private_payment_chain` message through the hub. No special privileges, node compromise, or protocol violation is required — just a large but otherwise well-formed request object satisfying the loose structural checks in `handlePrivatePaymentChains`.

### Recommendation
Add explicit upper bounds (e.g., new `constants.MAX_PRIVATE_CHAINS_PER_MESSAGE` and `constants.MAX_PRIVATE_CHAIN_LENGTH`) in `handlePrivatePaymentChains()` in `wallet.js`, rejecting requests whose `chains` array or any individual chain exceeds the limit, mirroring the existing `MAX_MESSAGES_PER_UNIT` / `MAX_INPUTS_PER_PAYMENT_MESSAGE` style limits used elsewhere in unit validation.

### Proof of Concept
1. Establish a normal device pairing with a victim wallet (standard private-payment counterparty relationship).
2. Construct a `private_payment_chain` message where `body.chains` contains, e.g., tens of thousands of syntactically-valid minimal chain entries (each satisfying the `isNonemptyObject`/`isNonemptyString` checks in the validator), or a smaller number of chains each with an extremely long `arrPrivateElements` sequence.
3. Send the message to the victim through the hub.
4. Observe `handlePrivatePaymentChains` (`wallet.js`) sequentially process every chain/element with hashing and full private-payment validation/DB queries and then attempt to forward them, consuming CPU/DB resources proportionally to the attacker-chosen array sizes with no rejection at the entry check.

function handlePrivatePaymentChains(ws, body, from_address, callbacks){
	var arrChains = body.chains;
	if (!ValidationUtils.isNonemptyArray(arrChains))
		return callbacks.ifError("no chains found");
	if (!arrChains.every(c =>
		isNonemptyArray(c) &&

		)
	))
