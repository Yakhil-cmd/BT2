### Title
Webhook signature verification binds only the *claimed* `repository.owner.login`, not the org/repo actually written by the handler — cross-organization writes via Membership/Push webhooks - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
This is the same trust-binding flaw as the Tensor report: a value the code *acts on* (which repository/team/stack gets written) is not the same value that was *cryptographically verified* (which organization's secret signed the request). In Tensor, the taker could swap the collateral NFT between the signed "deposit" step and the "withdraw" step because the two steps didn't force `order_type == taker_receives_nft`. In Shipit, `WebhooksController#verify_signature` picks the HMAC secret to check using `repository_owner`, itself read straight out of the same untrusted JSON body, and then the event handlers independently pick their write target from `repository.full_name` (or `organization.login` for membership events) — a *different* field of the same payload, never cross-checked against the field used to select the verifying secret.

### Finding Description
`WebhooksController#verify_signature` selects which `GitHubApp`/webhook secret to validate against using a value pulled from the attacker-supplied JSON body itself: [1](#0-0) [2](#0-1) 

`Shipit.github(organization:)` looks up per-organization config (app id, `installation_id`, `webhook_secret`, oauth) from `secrets.github`, which — per the documented multi-org setup — is populated with one independently-administered GitHub App/secret per organization: [3](#0-2) 

Once the HMAC check passes against that org's secret, `create` dispatches the payload to handlers that never re-check `repository_owner`; instead they derive the write target from `repository.full_name`: [4](#0-3) [5](#0-4) 

`MembershipHandler` is worse: it trusts `params.organization.login` and an attacker-chosen `params.team.id`/`params.member.login` to create/update a `Team` and add a `member` to it, with no check that this organization matches the one whose secret validated the signature: [6](#0-5) 

Because `webhook_secret` is administered per-organization by whoever owns that GitHub App/organization (see the documented multi-org `secrets.yml` schema), any organization admin in a multi-tenant Shipit install knows their own org's secret and can therefore produce a *validly signed* HTTP request to `/github/webhooks` (or wherever the engine is mounted) whose signature is checked against their own org's secret, while the JSON body's `repository.full_name` / `organization.login` fields point at a completely different organization/repository that they don't control. The binding that should hold — `verified_signing_organization == organization/repository written by the handler` — is never enforced.

### Impact Explanation
- Via `PushHandler`, an attacker can point `repository.full_name` at a `Stack` belonging to a different, unrelated repository and force `stack.sync_github(expected_head_sha:)`, triggering `GithubSyncJob` (and possibly continuous-deployment sync) against a stack the attacker's own webhook secret has no legitimate authority over — a cross-repository "write"/state-mutation triggered under a foreign organization's identity. [7](#0-6) 
- Via `MembershipHandler`, an attacker can craft `team.id` matching the `github_id` of an existing `Team` used in `Shipit.github_teams` (the set of teams that gate authorization, see `User#authorized?` / `Shipit.github_teams`), and add an arbitrary `member.login` (which will be `find_or_create_by_login!`'d as a real Shipit `User`) to that team — escalating an unrelated GitHub identity into `Shipit.github_teams` authorization without ever being a real member of the victim organization. [8](#0-7) [9](#0-8) 

This matches the "High" impact class: escalation into `Shipit.github_teams` authorization.

### Likelihood Explanation
This requires: (1) a multi-organization Shipit deployment (explicitly documented and supported), and (2) the attacker controlling/administering at least one of the configured organizations' GitHub App (hence knowing its `webhook_secret`) while not being authorized on the victim organization. This is a realistic deployment shape for any shared/multi-tenant Shipit instance serving several GitHub orgs, and requires no privileged Shipit session, API token, or the app's own GitHub App private key — only knowledge of a webhook secret the attacker legitimately owns for their own org.

### Recommendation
In `WebhooksController#verify_signature`/`create`, after verifying the HMAC, re-derive `repository_owner` a second time from the same trusted field used to select the secret and assert it is identical to the organization/repository-owner referenced by every field the handlers act on (`repository.full_name`'s owner segment, `organization.login`), rejecting the request if they differ. Equivalently, pass the already-authenticated organization identity into the handler layer explicitly and have each handler scope its `Repository`/`Stack`/`Team` lookups to that organization instead of trusting `repository.full_name`/`organization.login` taken verbatim from the payload.

### Proof of Concept
1. Deploy Shipit with the documented multi-org config, e.g. organizations `OrgA` (attacker-administered) and `OrgB` (victim), each with its own GitHub App and `webhook_secret`. [10](#0-9) 
2. Attacker, knowing `OrgA`'s `webhook_secret` (since they created that GitHub App), crafts a `membership` event JSON body with `organization.login = "OrgA"` (or `repository.owner.login = "OrgA"`, so `verify_signature` selects `OrgA`'s secret and passes) but `team.id` set to the real `github_id` of a `Team` belonging to `OrgB` that is present in `Shipit.github_teams`, and `member.login` set to an attacker-controlled GitHub login.
3. Attacker signs the raw JSON body with `OrgA`'s `webhook_secret` using HMAC-SHA1 and sends it as `X-Hub-Signature` to the webhooks endpoint with `X-Github-Event: membership`.
4. `verify_signature` passes (correct signature for `OrgA`). `MembershipHandler#process` runs, finds the `OrgB` team by `github_id`, and adds the attacker's login as a member. [11](#0-10) 
5. The attacker's Shipit `User` is now a member of a team counted in `Shipit.github_teams`, satisfying `User#authorized?` for `OrgB`'s stacks without ever being vetted by `OrgB`.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
