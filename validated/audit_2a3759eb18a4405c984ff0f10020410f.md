Given ocore forces last_ball to advance to the most recent stable point compatible with parents, the naive "pick an older last_ball to avoid a price update" analog doesn't hold up as a distinct vulnerability — this is enforced by the node/wallet logic itself, not a user-controlled bypassable choice at the protocol validation layer (a custom client could still construct a unit with an older, still-valid last_ball, since `validateParents` only requires the last_ball to be stable and included in parents, not that it be the *latest* possible one).### Title
Users can pick a stale `last_ball` to read a favorable/pre-drop data feed value in an AA, avoiding losses from a just-posted (not-yet-referenced) price update - ([File: aa_composer.js])

### Summary
Napier's H-2 lets stakers monitor an incoming unfavorable LST price update and race to redeem before it takes effect. In Obyte's oscript/AA model there is a structural analog: AA formulas that read oracle prices via `data_feed[[...]]`/`in_data_feed[[...]]` are evaluated against `objValidationState.last_ball_mci`, which is fixed by whatever `last_ball_unit` the *trigger's author* chose when composing their unit [1](#0-0) . Protocol validation only requires that this referenced last ball be *some* stable ball included in the unit's parents — it does not require it to be the most recent stable ball available [2](#0-1) [3](#0-2) . Consequently, a user (running custom composer code rather than the standard wallet flow) can knowingly reference an older last ball that predates a freshly-stabilized, unfavorable oracle data-feed post, and thereby get their AA trigger (e.g., a redemption/exchange call in a price-oracle-driven AA such as the bundled `futures_contract.oscript`/bonding-curve style templates) executed against the stale, more favorable price.

### Finding Description
- `data_feed`/`in_data_feed` formula evaluation resolves values by scanning data feeds up to `max_mci = objValidationState.last_ball_mci` [4](#0-3) [5](#0-4) .
- `last_ball_mci` for an AA trigger is derived from the `last_ball_unit` field the *poster* selected at composition time, and this is only checked for stability/inclusion, not recency [6](#0-5) .
- The reference composer (`parent_composer.js: pickParentUnitsAndLastBall`/`findLastStableMcBall`) does default to advancing to the newest usable stable ball [7](#0-6) [8](#0-7) , but this is client-side wallet behavior, not a network-enforced invariant. Nothing in `validateParents` (`validation.js`) rejects a syntactically valid, stable, properly-included but *older* last ball. An attacker with custom unit-composing code can deliberately choose an older last ball that omits an oracle's just-posted price-decrease data feed message.
- Because AA triggers execute deterministically off `last_ball_mci` (set at `aa_composer.js: handleTrigger` via `objValidationState.last_ball_mci = mci`) [9](#0-8) , the AA has no visibility into the fact that a newer, worse price has *already stabilized* elsewhere in the DAG — it only sees what's reachable from the chosen last ball.
- This is analogous to the Napier finding: the "true" price has already changed off-chain/on-DAG (oracle post is stable), but the affected on-chain financial logic (AA) can still be triggered using the old value by an attacker who controls unit construction, extracting value at the expense of the AA's pool/other counterparties.

### Impact Explanation
Any AA that prices redemptions, swaps, or settlements from an oracle `data_feed` (bonding-curve/synthetic-asset/futures-style AAs, as illustrated by `test/samples/futures_contract.oscript` and similar templates) is exposed. An attacker who withholds broadcasting their redeem/exchange trigger until an unfavorable oracle update is about to stabilize, then submits a trigger referencing an older last ball, extracts value at the stale price before the AA's other users/backers are protected by the new price. This causes fund loss to the AA's liquidity pool / other counterparties, matching the "AA fund loss" acceptance criterion.

### Likelihood Explanation
Requires: (1) an AA whose payout logic depends on a `data_feed` price that can move unfavorably, (2) an attacker capable of composing units directly (bypassing the standard wallet's "always advance to latest stable ball" behavior) and monitoring the DAG/oracle for pending price drops, and (3) enough of a window between an oracle unit's stabilization and its exclusion becoming impossible (i.e., the attacker must still be able to construct a valid, stable, parent-included last ball that omits the update). This is feasible but requires deliberate customization of the standard composer and reasonably fast reaction, so likelihood is Medium.

### Recommendation
- For AAs (protocol-level guidance/documentation), avoid relying on the trigger author's freely-chosen `last_ball_mci` for pricing decisions; where possible, require freshness relative to the current point of stabilization (e.g., enforce `min_mci` bounds tightly or add a maximum staleness/age check on the oracle post itself before using it) so that maliciously old last balls are rejected within the AA logic (`bounce` if the fetched data feed's `mci`/timestamp is too old relative to `timestamp`).
- Consider tightening the core protocol so that `last_ball_unit` for units authored after a certain point must be within some bounded distance of the best-known stable ball, closing the general staleness-selection window (this is a broader protocol design change, not just an AA-level mitigation).

### Proof of Concept
1. An oracle address posts a `data_feed` unit lowering `PRICE` at MCI `N`; the unit stabilizes.
2. Before this, an AA-priced redemption formula (`data_feed[[oracles=ORACLE, feed_name='PRICE']]`) is used by a swap/redeem AA.
3. Attacker, using custom unit-composing code (not the standard wallet, which auto-advances to the freshest stable ball per `parent_composer.js`), constructs a payment+trigger unit whose `last_ball_unit`/`parent_units` reference a stable ball at MCI `< N` (still valid per `validateParents`, since only stability+inclusion is checked, not recency).
4. The trigger unit passes validation (`validation.js`) and is processed by `aa_composer.js: handleTrigger`, which sets `last_ball_mci` to the trigger's own resolved value, causing `data_feed[[...]]` to return the pre-drop `PRICE`.
5. Attacker redeems/exchanges at the stale, favorable price, extracting more value than post-drop pricing would allow, at the expense of the AA's balance/other participants.
