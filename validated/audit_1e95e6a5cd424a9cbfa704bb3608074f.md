### Title
Webhook signature is verified against the org named in `repository.owner.login`, but the mutated repository is resolved from `repository.full_name` — a payload for an unsecured/attacker-named org can write `PullRequest` records for an unrelated org's stack - (File: `app/controllers/shipit/webhooks_controller.rb`, `lib/shipit/github_app.rb`, `app/models/shipit/webhooks/handlers/pull_request/assigned_handler.rb`)

### Summary
`WebhooksController#verify_signature` selects the `GitHubApp` (and thus the HMAC secret) to check using `repository_owner`, which is read from `params.dig('repository', 'owner', 'login')`. `AssignedHandler#repository`, however, resolves the row to mutate using `Shipit::Repository.from_github_repo_name(params.repository.full_name)`, an entirely separate field the attacker also controls. Because `GitHubApp#verify_webhook_signature` returns `true` unconditionally when no `webhook_secret` is configured for the selected organization [1](#0-0) , an attacker who can get any org onboarded without a webhook secret (or who owns/controls such a "no-secret" org config) can forge a `pull_request` webhook whose `repository.owner.login` names that org while `repository.full_name` points at a victim org's real repository, and the handler will happily write to the victim's `PullRequest` row.

### Finding Description
The broken binding: the code implicitly assumes
`org_that_signed_the_request(params.repository.owner.login) == org_that_owns_the_mutated_repository(params.repository.full_name)`.
Nothing enforces this equality.

Path:
1. `verify_signature` picks the app config via `repository_owner` = `params.dig('repository','owner','login')` and calls `github_app.verify_webhook_signature(...)` [2](#0-1) .
2. `GitHubApp#verify_webhook_signature` short-circuits to `true` when `@webhook_secret` is blank for that org's config [1](#0-0) . If the selected org has no `webhook_secret` configured, *any* signature (or none) passes.
3. `create` then dispatches `params` to handlers, including `Shipit::Webhooks::Handlers::PullRequest::AssignedHandler` for `action=unassigned`/`assigned` [3](#0-2) .
4. `AssignedHandler#repository` resolves the repository from `params.repository.full_name` — not `repository_owner` — via `Shipit::Repository.from_github_repo_name` [4](#0-3) .
5. `AssignedHandler#process` then finds the matching `Shipit::PullRequest` for that (attacker-chosen) repository/stack and calls `pull_request.update(github_pull_request: params.pull_request)` [5](#0-4) , which overwrites `state`, `assignees`, `labels`, and — critically — `head` (resolved via SHA lookup/creation against `stack.github_api`) via `PullRequest#github_pull_request=` [6](#0-5) .

Root cause: `Shipit.github(organization:)`/`github_app_config` returns per-org config keyed by whatever org name is supplied, and organizations without a `webhook_secret` entry are treated as globally trusted senders (`return true unless webhook_secret`) [7](#0-6) , while the entity actually mutated is determined from a completely independent, attacker-controlled field (`full_name`).

Why guards don't help: `ExplicitParameters` (`params do ... end` in `AssignedHandler`) only validates types/shape of `repository.full_name`, not that it matches `repository_owner` used for signature verification [8](#0-7) . `drop_unhandled_event` and `check_if_ping` don't touch this. `Repository` model validations only constrain the format of `owner`/`name`, not cross-consistency with the authenticating org [9](#0-8) .

Caveat on the "merge queue / `merge!`" amplification claimed in the question: `AssignedHandler` operates on `Shipit::PullRequest`, a model distinct from `Shipit::MergeRequest` (which drives `merge_queue_enabled` and `MergeRequest#merge!`) [10](#0-9) . I found no code path by which `AssignedHandler#process` triggers `Stack#schedule_merges`, `ProcessMergeRequestsJob`, or `MergeRequest#merge!`; that job is instead triggered from `Commit#add_status` when a status/check-run changes simple state [11](#0-10) . So the specific "green head advances the merge queue and `merge!` fires" mechanism is not substantiated by the traced code — the confirmed, in-scope impact is limited to unauthorized writes to a victim's `PullRequest` record (state/labels/assignees/head), not a forced GitHub merge.

### Impact Explanation
An attacker who controls (or can get onboarded) an organization whose `Shipit.github` config lacks a `webhook_secret` can forge a `pull_request` webhook that is authenticated as "from" their own no-secret org but whose `repository.full_name` names a victim org's repository/stack. This lets them create/overwrite `Shipit::PullRequest` rows for that victim stack — a genuine "payload for one repository mutating another's stack" condition, which is explicitly listed as Critical. It is repeatable against any repository as long as its owner/name can be guessed or discovered (repo names are typically public), and it requires no session, API token, or GitHub secret. However, the further leap to an unauthorized GitHub merge via `MergeRequest#merge!` is not demonstrated by the traced code path from `AssignedHandler`.

### Likelihood Explanation
Preconditions: (a) at least one GitHub organization configured in Shipit's `secrets.github` without a `webhook_secret` (or the attacker being able to add such a config, which is an operator error rather than a Shipit code guarantee), and (b) knowledge of a victim `owner/name` repository already tracked by a Shipit stack. Attacker cost is a single unauthenticated `POST /webhooks` with a crafted JSON body and the `X-Github-Event: pull_request` header — no signature needed if the chosen org has no secret. This is fully repeatable and scriptable. The severity of this specific finding hinges on the "no-secret org" precondition actually existing in a deployment; the engine's own code does not prevent an operator from configuring such an org, and does not defend against the owner/full_name divergence regardless.

### Recommendation
In `AssignedHandler#repository` (and all other handlers using `params.repository.full_name`), verify that the resolved `Shipit::Repository#owner` matches the `repository_owner` value used to select the webhook secret in `WebhooksController#verify_signature`, and reject the event otherwise. More robustly, `verify_signature` should re-derive the organization solely from `full_name` (single source of truth) rather than from a separate `owner.login` field, and `GitHubApp#verify_webhook_signature` should not silently authenticate all payloads when `webhook_secret` is blank — an unconfigured secret should fail closed for orgs that are supposed to have one, or the app should refuse to instantiate a `GitHubApp` for orgs lacking a secret.

### Proof of Concept
Minitest plan (`test/controllers/webhooks_controller_test.rb`-style):
1. Configure two orgs in test secrets: `attacker-org` (no `webhook_secret`) and `victim-org` (with a `webhook_secret`), using the existing `secrets_double_github_app.yml` fixture pattern.
2. Create `victim_repo = shipit_repositories(:victim)` under `victim-org`, a `stack` with `merge_queue_enabled: true`, and a `Shipit::PullRequest` fixture `pr` for that stack with `number: 42`.
3. POST to `/webhooks` with header `X-Github-Event: pull_request`, no valid `X-Hub-Signature` (or an arbitrary bogus one), and body:
   ```json
   {
     "action": "unassigned",
     "number": 42,
     "pull_request": { ...valid fields..., "head": {"sha": "attacker-sha", "ref": "attacker-branch"} },
     "repository": { "owner": {"login": "attacker-org"}, "full_name": "victim-org/victim-repo" },
     "sender": {"login": "attacker"}
   }
   ```
4. Assert response is `200 OK` (signature check passed via the no-secret `attacker-org` path).
5. Assert `pr.reload.head.sha == "attacker-sha"` (or whatever mutation was applied) — i.e., the record for `victim-org`'s stack was written despite the request never being authenticated by `victim-org`'s secret.
6. Equality check both sides: before, `pr.head.sha != "attacker-sha"`; after the forged request, `pr.head.sha == "attacker-sha"`, proving `org_that_signed != org_that_was_mutated`.

Note: no assertion on `MergeRequest#merge!`/`ProcessMergeRequestsJob` firing should be included, as no code path from `AssignedHandler` was found to trigger it.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
