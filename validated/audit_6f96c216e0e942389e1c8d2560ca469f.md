### Title
Webhook signature verified against the payload's top-level organization/owner while the event is processed against an attacker-controlled `repository.full_name` — cross-tenant/cross-repository write - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App (and therefore which `webhook_secret`) is used to authenticate an inbound webhook based solely on `params.dig('repository','owner','login')` (falling back to `params.dig('organization','login')`). Once the HMAC check passes, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` is invoked, and the handlers (`Shipit::Webhooks::Handlers::Handler#repository_name`/`#stacks`) resolve the target `Stack`/`Repository` from a *different* field of the same attacker-supplied JSON body: `payload.dig('repository', 'full_name')`. Nothing ties the value used for signature verification to the value used for the actual write. This is directly analogous to `_onlyNotGameOver()` checking only the `WinningEmpire`/deadline "domination is not yet true" path while a whole other path (a live domination victory) can already make the game over — here, the engine checks "is this organization's secret valid" but never checks "does the repository this payload targets actually belong to that organization."

### Finding Description
`Shipit` supports multi-tenant configuration where each GitHub organization has its own `webhook_secret` [1](#0-0) . The webhook endpoint verifies the signature using an app looked up by `repository_owner`:

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(...)
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [2](#0-1) 

Once verification succeeds (i.e. the HMAC matches the `webhook_secret` configured for whatever organization `repository_owner` names — including an organization the attacker legitimately administers/has installed the GitHub App for), the raw, fully attacker-controlled JSON body is dispatched to handlers unmodified:

```ruby
def create
  params = JSON.parse(request.raw_post)
  Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }
  head(:ok)
end
``` [3](#0-2) 

The handlers determine which `Stack`/`Repository` to act on from a completely separate JSON field, `repository.full_name`, with no cross-check against `repository.owner.login`/`organization.login` used above:

```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [4](#0-3) 

Since the whole request body is attacker-controlled (this is a forged direct HTTP POST, not a genuine GitHub-generated payload), nothing in Shipit enforces `repository.full_name` starting with `repository.owner.login`. An attacker who legitimately controls organization `attacker-org` (and therefore its `webhook_secret`, since they configured the GitHub App integration themselves) can send a signed request where `repository.owner.login`/`organization.login` = `attacker-org` (so it authenticates successfully against `attacker-org`'s secret) but `repository.full_name` = `victim-org/some-repo` (so the handler acts on the victim's stack). This breaks the binding: *organization that authenticated* (`attacker-org`) ≠ *repository that is written* (`victim-org/some-repo`).

Concretely reachable handlers that write state keyed off `repository.full_name`:
- `PushHandler#process` calls `stack.sync_github(expected_head_sha: params.after)` for any not-archived stack of the victim repo matching the branch [5](#0-4) .
- The status handler creates arbitrary commit `statuses` for a specified `sha`/`state`, as shown in tests, which feeds directly into deployability checks (`Commit#deployable?`) used to gate deploys [6](#0-5) .
- `check_suite` triggers `RefreshCheckRunsJob` for the resolved stack [7](#0-6) .

### Impact Explanation
This crosses a repository/organization trust boundary: possession of one organization's legitimately-configured `webhook_secret` is sufficient to forge webhook events against *any other* organization/repository tracked by the same Shipit instance, because the field used to authenticate (`owner.login`/`organization.login`) is never checked against the field used to select the write target (`repository.full_name`). By injecting forged `status` events reporting success for arbitrary commit SHAs on a victim stack, an attacker can flip `Commit#deployable?` to `true` for commits that never actually passed CI, directly enabling an unauthorized/unreviewed deploy of a repository the attacker does not control — this matches the "unauthorized deploy" and "cross-repository writes" Critical impact categories.

### Likelihood Explanation
Likelihood is Medium: it requires the attacker to be a legitimate operator of at least one GitHub organization that is configured as a tenant in the same Shipit deployment (so they know that organization's own `webhook_secret`), and to know or guess the `owner/repo` full name of the victim stack they want to target (repo names are often public/guessable). No other credential (session, API token, GitHub App private key) is required — only their own tenant's webhook secret, which they legitimately possess.

### Recommendation
In `verify_signature`, and in `Shipit::Webhooks::Handlers::Handler`, derive the organization used for verification and the repository used for the write from the *same* trusted GitHub-App-scoped installation, and explicitly assert that `repository.full_name`'s owner segment matches the organization whose secret validated the signature (or vice versa) before dispatching to handlers. Reject the webhook (422) on mismatch, the same way an equivalent "domination victory" check must be added alongside the existing winner/deadline check in the referenced report.

### Proof of Concept
1. Shipit is configured with two tenants, `attacker-org` and `victim-org`, each with its own GitHub App / `webhook_secret` (per `config/secrets.*.yml` multi-org schema) [1](#0-0) .
2. Attacker legitimately owns/administers `attacker-org` and thus knows `attacker-org`'s `webhook_secret`.
3. Attacker crafts a `status` (or `push`) webhook JSON body with:
   - `repository.owner.login` = `"attacker-org"` (and/or `organization.login` = `"attacker-org"`)
   - `repository.full_name` = `"victim-org/victim-repo"`
   - `sha` = the SHA of an unreviewed commit on the victim stack, `state` = `"success"`
4. Attacker computes `X-Hub-Signature` using `attacker-org`'s known `webhook_secret` over the raw body and POSTs directly to `/github/webhooks` (bypassing GitHub entirely).
5. `verify_signature` resolves `Shipit.github(organization: "attacker-org")` and the HMAC check passes [8](#0-7) .
6. The status handler resolves the stack via `Repository.from_github_repo_name("victim-org/victim-repo")` [4](#0-3)  and creates a `success` status on the victim's commit, which can subsequently be deployed as if it had passed CI.

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping
      head(:ok) if event == 'ping'
    end

    def event
      request.headers.fetch('X-Github-Event')
    end

    def repository_owner
      # Fallback to the organization sub-object if repository isn't included in the payload
      params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
    end
```
