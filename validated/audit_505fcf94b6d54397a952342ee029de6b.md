### Title
Unauthenticated peers can spam a wallet's `unhandled_private_payments` table indefinitely via `private_payment` messages - ([File: network.js])

### Summary
The `onERC721Received` finding lets an unprivileged caller invoke a callback that unconditionally appends attacker-controlled data to a persistent array (`nfts`), with no check that the caller/data is legitimate, degrading the victim's future operations and imposing cleanup costs. The analogous pattern in ocore is `handleOnlinePrivatePayment` (invoked from the `private_payment` justsaying handler in `network.js`), which persists attacker-supplied private-payment chain elements into the `unhandled_private_payments` table before the referenced unit or chain content is actually validated.

### Finding Description
`handleOnlinePrivatePayment` in [1](#0-0)  only performs shallow structural checks on the incoming `arrPrivateElements` (that the unit is a valid base64 hash, `message_index`/`output_index` are non-negative integers) before deciding what to do with it. In several branches — `ifNew`, `ifKnownUnverified`, and `ifWaitingForChain` (light clients with multi-element chains) — the handler calls `savePrivatePayment`, which unconditionally inserts a row into `unhandled_private_payments` keyed by `(unit, message_index, output_index)`: [2](#0-1) 

This insertion happens regardless of whether the referenced `unit` will ever actually arrive/validate, and regardless of whether the sender (`ws.peer` or via hub) is a known correspondent — the caller of this code path is any connected peer or hub relay sending a `private_payment` justsaying message, similar to how `onERC721Received` can be invoked by any external contract regardless of whether a genuine NFT transfer occurred. The deep content validation of the private payload (via `private_payment.js`'s `validateAndSavePrivatePaymentChain`, which enforces asset/denomination/duplicate checks) is only performed in the `ifKnown` branch, i.e., after the corresponding unit is already known; in the `ifNew`/`ifKnownUnverified`/`ifWaitingForChain` branches the raw JSON is stored first and validated later (or never, if the referenced unit is never actually posted).

Because the primary key is `(unit, message_index, output_index)`, an attacker can trivially generate many distinct, well-formed-looking but never-to-be-posted 44-byte base64 "unit" hashes, each with a fabricated `arrPrivateElements` payload containing an `asset`, `inputs`, and `outputs` object satisfying only the shallow `isNonemptyObject`/`isNonemptyArray` checks performed by `handlePrivatePaymentChains` in wallet.js: [3](#0-2)  or by directly sending crafted `private_payment` justsaying messages, and have each accepted and stored indefinitely, growing the `unhandled_private_payments` table (and the JSON blobs within it) without bound and without any deduplication/authorization tied to a legitimate corresponding on-chain payment.

### Impact Explanation
Growth of `unhandled_private_payments` with attacker-controlled, never-to-be-resolved entries increases local storage usage on the recipient/light-wallet node and increases the cost of any later cleanup/query logic (e.g., `updateLinkProofsOfPrivateChain`, `rerequestLostJointsOfPrivatePayments`, and the `ifKnown`/reprocessing paths that iterate over this table when the corresponding unit finally becomes known). This is directly analogous to the reported bug class: an unauthenticated/unprivileged party can force persistent state growth on a victim by exploiting a lightly-guarded callback/handler, imposing an ongoing resource and remediation cost with no compensating validation of the counterparty's legitimacy.

### Likelihood Explanation
Any peer that can open a network connection or any device that can send a `private_payment` message (or forwarded chain via `handlePrivatePaymentChains`) can trigger this path; no special privilege, funds, or correspondent relationship is strictly required for the message to be persisted (only the structural checks shown above are enforced before writing to the database). This makes the attack straightforward and repeatable at low cost to the attacker (message crafting only, no on-chain fee is required since no real unit needs to be composed or broadcast).

### Recommendation
- Before persisting to `unhandled_private_payments`, perform stronger pre-validation of the private payload structure (asset existence, denomination consistency, output/is_private checks) similar to what `private_payment.js`'s `validateAndSavePrivatePaymentChain` does for the `ifKnown` case, rather than deferring nearly all validation until the referenced unit is confirmed known.
- Enforce a rate limit / cap on the number of pending `unhandled_private_payments` rows accepted per peer or per sender device, and add periodic garbage collection of entries whose referenced unit never becomes known within a bounded time window.
- Track provenance (peer/device) more strictly and tie acceptance of speculative private-payment entries to an existing correspondent/hub relationship where feasible, rather than accepting from any connection.

### Proof of Concept
Conceptual PoC (structural, not exploit code — network/message-crafting details are peer-facing and out of scope for source-only analysis):
1. Attacker crafts an `arrPrivateElements` array whose head element has: a syntactically valid but non-existent 44-byte base64 `unit`, a `message_index`, and a `payload` containing `asset`, `inputs` (array of objects), and `outputs` (array of objects) satisfying only `isNonemptyObject`/`isNonemptyArray`.
2. Attacker sends this repeatedly (with a new fake `unit` each time) as a `private_payment` justsaying message to a victim node/light wallet.
3. `handleOnlinePrivatePayment` classifies the referenced unit as new/unverified and calls `savePrivatePayment`, inserting the row into `unhandled_private_payments` unconditionally: [4](#0-3) .
4. Since the fake unit is never actually posted to the DAG, the entry remains in `unhandled_private_payments` indefinitely, and the process repeats to grow the table without bound.

function handleOnlinePrivatePayment(ws, arrPrivateElements, bViaHub, callbacks){
	if (!ValidationUtils.isNonemptyArray(arrPrivateElements))
		return callbacks.ifError("private_payment content must be non-empty array");
	
	var unit = arrPrivateElements[0].unit;
	var message_index = arrPrivateElements[0].message_index;
	var output_index = arrPrivateElements[0].payload.denomination ? arrPrivateElements[0].output_index : -1;
	if (!ValidationUtils.isValidBase64(unit, constants.HASH_LENGTH))
		return callbacks.ifError("invalid unit");
	if (!ValidationUtils.isNonnegativeInteger(message_index))
		return callbacks.ifError("invalid message_index");
	if (!(ValidationUtils.isNonnegativeInteger(output_index) || output_index === -1))
		return callbacks.ifError("invalid output_index");

function handlePrivatePaymentChains(ws, body, from_address, callbacks){
	var arrChains = body.chains;
	if (!ValidationUtils.isNonemptyArray(arrChains))
		return callbacks.ifError("no chains found");
	if (!arrChains.every(c =>
		isNonemptyArray(c) &&
		c.every(e =>
			isNonemptyObject(e) &&
			isNonemptyString(e.unit) &&
			isNonemptyObject(e.payload) &&
			isNonemptyString(e.payload.asset) &&
			isNonemptyArray(e.payload.inputs) &&
			isNonemptyArray(e.payload.outputs) &&
			e.payload.inputs.every(isNonemptyObject) &&
			e.payload.outputs.every(isNonemptyObject)
		)
	))
		return callbacks.ifError("malformed private chain");

		var cache_key = objectHash.getBase64Hash(arrChains);
