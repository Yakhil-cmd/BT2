### Title
Webhook signature verification keys on `repository.owner.login` while event handlers act on `repository.full_name`, letting an unsigned/forged payload mutate a different org's stack - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects the `GitHubApp` used for HMAC verification solely from `params.dig('repository','owner','login')`, then hands the *entire* raw payload to the event handlers, which resolve the target `Repository`/`Stack` from `params['repository']['full_name']` instead. Nothing in the controller or the `ExplicitParameters`-free flow enforces that these two attacker-supplied fields refer to the same organization, so a payload can be verified under one org's (mis)configuration while it is applied to another org's repository.

### Finding Description
Binding claimed: `organization_whose_webhook_secret_verified(payload) == organization_owning(params.repository.full_name)`.

- Verification side: `repository_owner` reads `params.dig('repository', 'owner', 'login')` (fallback `organization.login`) and this value alone selects the `GitHubApp` instance used to HMAC-check the request. [1](#0-0) [2](#0-1) 

- Signature check itself: `GitHubApp#verify_webhook_signature` unconditionally returns `true` when no `webhook_secret` is configured for that resolved org (`return true unless webhook_secret`), i.e. verification is a no-op for any org onboarded without a secret. [3](#0-2) 

- Mutation side: the same raw JSON body (`params` re-parsed at `create`) is dispatched to `Shipit::Webhooks.for_event(event)` handlers, and the `pull_request`-family handlers (`OpenedHandler`, `ClosedHandler`, `LabeledHandler`, `UnlabeledHandler`, `ReopenedHandler`, `LabelCapturingHandler`, etc.) resolve/create the target `Repository`/`Stack`/`PullRequest` using `params['repository']['full_name']` — a completely different field from the one used to pick the verifying `GitHubApp`. [4](#0-3) 

No code path cross-checks that the owner segment of `full_name` matches `repository.owner.login`. An attacker who knows (or who exploits an org with no `webhook_secret` configured — a supported, optional config value: `@webhook_secret = @config[:webhook_secret].presence`) can craft:
```
X-Github-Event: pull_request
{
  "repository": {
    "owner": { "login": "OrgA" },   // selects OrgA's GitHubApp for verification (no secret => auto-verified)
    "full_name": "OrgB/repo"        // this is what the handler actually looks up and mutates
  },
  ...
}
```
`verify_signature` resolves `Shipit.github(organization: "OrgA")`, gets `verified == true` (because `OrgA` has no secret), and the request proceeds to `create`, where the handler uses `full_name = "OrgB/repo"` to find and mutate OrgB's real `Stack`/`PullRequest` record — despite the payload never being validated against OrgB's actual webhook secret.

Existing guards do not stop this: `drop_unhandled_event` only checks the event name is registered; `Shipit::GithubOrganizationUnknown` is only raised if `OrgA` itself isn't a configured org (attacker must pick a real, configured-but-secret-less org, not an arbitrary string); there is no `ExplicitParameters` schema or model validation anywhere that ties `repository.owner.login` to `repository.full_name`. [5](#0-4) 

### Impact Explanation
An attacker can cause pull-request-driven mutations (labeling capture, close/reopen handling, review-stack provisioning triggers) to be applied to `OrgB/repo`'s `Stack`/`PullRequest` records while the signature check that gated the request was performed entirely against an unrelated organization (`OrgA`) that lacks a webhook secret. This is a cross-tenant "payload for one repository mutating another's stack" scenario explicitly listed as Critical impact. Blast radius is bounded by which handlers act on `pull_request`/similar events and by which orgs are configured in the Shipit instance's multi-app config (`secrets_double_github_app.yml`-style setups demonstrate multiple `GitHubApp`s are a supported deployment shape).

### Likelihood Explanation
Exploitability strictly depends on operational configuration: the Shipit instance must be integrated with more than one GitHub organization, and at least one of them must have no `webhook_secret` configured (an explicitly optional config value in `GitHubApp#initialize`). Under that precondition the attacker needs zero secrets — just knowledge of the org's name (visible/public) — to have `verify_webhook_signature` short-circuit to `true`. If every configured org has a secret set, forging a valid HMAC for any of them is infeasible without the secret, and the finding does not apply. The vulnerability is therefore real and repeatable but conditional on a specific, documented, and plausible operator configuration (an org onboarded without a webhook secret).

### Recommendation
Cross-validate the owner derived from `repository.owner.login` (used to pick the verifying `GitHubApp`) against the owner segment of `repository.full_name` before dispatching to handlers, rejecting mismatches with `422`. Additionally, reconsider the `return true unless webhook_secret` fallback in `GitHubApp#verify_webhook_signature` — treating "no secret configured" as "always verified" silently disables authentication for that org and should instead fail closed (reject) or be an explicit, loudly-logged opt-in.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb
test "pull_request payload with owner/full_name org mismatch mutates the wrong org's stack" do
  # OrgA configured with NO webhook_secret -> verify_webhook_signature always true
  org_a_app = Shipit::GitHubApp.new('OrgA', {})
  # OrgB is the org that actually owns the target stack, with a real secret
  Shipit.stubs(:github).with(organization: 'OrgA').returns(org_a_app)

  body = JSON.parse(payload(:pull_request_opened))
  body['repository']['owner']['login'] = 'OrgA'
  body['repository']['full_name'] = 'OrgB/repo' # real stack under test lives here

  request.headers['X-Github-Event'] = 'pull_request'
  request.headers['X-Hub-Signature'] = 'sha1=deadbeef' # forged / arbitrary

  assert_difference -> { Shipit::PullRequest.count }, 1 do
    post :create, body: body.to_json, as: :json
  end

  assert_response :ok # NOT 422, despite invalid signature relative to OrgB
  pr = Shipit::PullRequest.last
  assert_equal 'OrgB/repo', pr.stack.repository.full_name
  # Binding check: organization used for verification ("OrgA") != organization owning
  # the mutated record ("OrgB") -- the equality claimed by the question is broken.
  refute_equal 'OrgA', pr.stack.repository.owner
end
```

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
