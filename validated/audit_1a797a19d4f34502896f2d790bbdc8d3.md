### Title
`collect_creator_fee` / `collect_creator_fee_permissionless` will permanently lock accrued creator fees if the pool creator's token account is frozen/blacklisted - (File: `programs/cp-swap/src/instructions/collect_creator_fee.rs`, `programs/cp-swap/src/instructions/collect_creator_fee_permissionless.rs`)

### Summary
Both `collect_creator_fee` and `collect_creator_fee_permissionless` are hard-wired to transfer accrued `creator_fees_token_0`/`creator_fees_token_1` to the pool creator's associated token account, with no way to specify an alternate destination. If that specific token account is frozen (via the mint's freeze authority, e.g. on USDC or any Token/Token-2022 mint with a freeze authority), fee collection permanently reverts and the accrued fees are stuck in the pool vault forever, with no admin-level recovery path for this specific fee bucket.

### Finding Description
`CollectCreatorFee` constrains the fee recipient's ATA to `associated_token::authority = creator`, where `creator` is itself constrained by `address = pool_state.load()?.pool_creator` [1](#0-0)  and the destination ATAs are derived deterministically from that fixed creator address [2](#0-1) . The permissionless variant is identical: anyone can pay to create the ATA, but the authority/recipient is always the fixed `pool_creator` [3](#0-2) [4](#0-3) .

The actual movement of funds uses `transfer_from_pool_vault_to_user`, which performs a `token_2022::transfer_checked` CPI directly to that same fixed destination account [5](#0-4) , called from both instructions [6](#0-5) [7](#0-6) .

If the token mint has a freeze authority (a standard SPL Token/Token-2022 feature used by regulated stablecoins) and the specific creator ATA gets frozen, any `transfer_checked` into that account will fail on-chain, causing the instruction to revert. Since there is no parameter to redirect the destination and no other instruction touches `creator_fees_token_0`/`creator_fees_token_1` (unlike `protocol_fees`/`fund_fees`, which are collected via `collect_protocol_fee`/`collect_fund_fee` where the admin freely supplies an arbitrary, unconstrained `recipient_token_*_account`), the accrued creator fees become permanently unrecoverable while still being tracked as a liability in `pool_state.creator_fees_token_0`/`creator_fees_token_1` [8](#0-7) .

This is directly analogous to the referenced report: a fee/asset-recovery function whose recipient address is immutably fixed by the contract, so once that address is blacklisted/frozen, the funds tied to it can never be moved out.

### Impact Explanation
The accumulated creator fee balance for a pool becomes permanently frozen inside the pool's token vaults with no recovery mechanism once the pool creator's ATA is frozen by the mint's freeze authority. This is a fee-ledger accounting freeze: the funds remain forever unreachable by any instruction in the program, since `creator_fees_token_0`/`creator_fees_token_1` are only ever debited by these two instructions, both of which target the same frozen account.

### Likelihood Explanation
This requires a token with a freeze authority (common for centralized stablecoins) to freeze the specific creator ATA — an action outside the program's control but realistic for regulated assets pools may be created with. Once frozen, every future call to either collection instruction (permissioned or permissionless) will deterministically fail, making the freeze permanent and not a one-off/transient failure.

### Recommendation
Allow the pool creator to designate/redirect a beneficiary token account for fee collection (similar to how `collect_protocol_fee`/`collect_fund_fee` let the admin supply an arbitrary `recipient_token_*_account`), rather than hard-constraining the destination to a fixed ATA derived from `pool_creator`.

### Proof of Concept
1. A pool is created with `pool_creator = C` and `enable_creator_fee = true`, trading on a mint with a freeze authority (e.g., USDC-like token).
2. Swaps accrue `creator_fees_token_0`/`creator_fees_token_1` in `pool_state`.
3. The mint's freeze authority freezes `C`'s associated token account for that mint (a normal compliance action, independent of this program).
4. Any subsequent call to `collect_creator_fee` (by `C`) or `collect_creator_fee_permissionless` (by anyone) reaches `transfer_from_pool_vault_to_user` → `token_2022::transfer_checked`, which fails because the destination account is frozen.
5. Because both instructions unconditionally target that same fixed ATA and no other instruction can debit `creator_fees_token_0`/`creator_fees_token_1`, these fees remain permanently locked in `token_0_vault`/`token_1_vault`.

pub fn transfer_from_pool_vault_to_user<'a>(
    authority: AccountInfo<'a>,
    from_vault: AccountInfo<'a>,
    to: AccountInfo<'a>,
    mint: AccountInfo<'a>,
    token_program: AccountInfo<'a>,
    amount: u64,
    mint_decimals: u8,
    signer_seeds: &[&[&[u8]]],
) -> Result<()> {
    if amount == 0 {
        return Ok(());
    }
    token_2022::transfer_checked(
        CpiContext::new_with_signer(
            *token_program.key,
            token_2022::TransferChecked {
                from: from_vault,
                to,
                authority,
                mint,
            },
            signer_seeds,
        ),
        amount,
        mint_decimals,
    )
}
