This is a genuinely significant finding: `bls12_381_g1_addition_unchecked`, `bls12_381_g1_subtraction_unchecked`, and their G2 equivalents are explicitly named "unchecked" and, unlike `GROUP_OP_MUL`'s `bls12_381_g1_multiplication` and unlike the `CURVE25519_EDWARDS`/`CURVE25519_RISTRETTO` branches (whose `add_edwards`/`subtract_edwards`/`multiply_edwards` internally decompress and thereby validate the point is on-curve), the BLS12-381 add/sub group-op path calls an "_unchecked" variant.

### Title
Missing curve-membership validation in BLS12-381 group-operation add/subtract syscall path - ([File: syscalls/src/lib.rs])

### Summary
`SyscallCurveGroupOps` (the `sol_curve_group_op` syscall) dispatches BLS12-381 G1/G2 `ADD`/`SUB` operations to `solana_bls12_381_syscall::bls12_381_g1_addition_unchecked` / `bls12_381_g2_addition_unchecked` / `bls12_381_g1_subtraction_unchecked` / `bls12_381_g2_subtraction_unchecked`, functions whose names indicate they skip the curve-membership check that the `MUL` path (`bls12_381_g1_multiplication`) and the parallel Curve25519 Edwards/Ristretto add/sub paths perform implicitly via point decompression. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
The `sol_curve_group_op` syscall implementation (`SyscallCurveGroupOps`) is registered for any BPF program to invoke directly. [4](#0-3)  For `CURVE25519_EDWARDS`/`CURVE25519_RISTRETTO`, the `ADD`/`SUB`/`MUL` operations call `edwards::add_edwards`, `edwards::subtract_edwards`, `edwards::multiply_edwards` (and Ristretto equivalents), which return `None` when passed byte inputs that don't decompress to a valid curve point — the unit tests explicitly confirm invalid points return error code `1` for ADD, SUB, and MUL. [5](#0-4) [6](#0-5) 

For BLS12-381, however, the `GROUP_OP_ADD` and `GROUP_OP_SUB` branches for both G1 and G2 explicitly call the `_unchecked` variants (`bls12_381_g1_addition_unchecked`, `bls12_381_g1_subtraction_unchecked`, `bls12_381_g2_addition_unchecked`, `bls12_381_g2_subtraction_unchecked`), while `GROUP_OP_MUL` calls the non-"_unchecked" `bls12_381_g1_multiplication`/`bls12_381_g2_multiplication`. [7](#0-6) [8](#0-7)  This naming asymmetry directly parallels the reported Circom bug class: `BabyAdd()`/`BabyDbl()` lack the `BabyCheck()` curve-membership assertion that other logic (e.g. `BabyPbk()`'s expected usage) implies should be present, allowing off-curve "points" to be fed into curve arithmetic and downstream cryptographic assumptions (subgroup membership, pairing correctness) to be silently violated.

Separately, a companion `sol_curve_validate_point` syscall does exist and does perform BLS12-381 point validation via `bls12_381_g1_point_validation`/`bls12_381_g2_point_validation`. [9](#0-8)  But nothing in `SyscallCurveGroupOps` forces a caller to invoke that validation syscall before calling `sol_curve_group_op` with `ADD`/`SUB` — a caller (or an on-chain program acting on attacker-controlled instruction data) can pass arbitrary 48/96-byte inputs directly to the add/sub path without ever validating curve membership.

### Impact Explanation
Whether this is actually exploitable depends entirely on the internal behavior of `solana_bls12_381_syscall::bls12_381_g1_addition_unchecked`/`bls12_381_g2_addition_unchecked` (defined in the external `solana-bls12-381-syscall` crate, not indexed in this repository), which I could not inspect. If these "_unchecked" functions truly skip subgroup/curve-membership checks and still return a `Some(result)` for off-curve inputs, a BPF program relying on `sol_curve_group_op` ADD/SUB for BLS12-381 signature aggregation or pairing-based protocols could be fed adversarial "points" that are not valid curve elements, potentially producing forged aggregate points, breaking pairing-equation invariants used for signature verification, or corrupting values used by ZK/aggregate-signature programs built on top of this syscall (e.g. mint/burn authorization gated by an aggregate BLS check). That would translate to unsigned fund movement or a security-check bypass in any downstream program trusting these primitives — but this is a **conditional/inferred** vulnerability, not a directly proven one, because the semantics of "_unchecked" here could plausibly mean "does not re-verify caller has already validated" rather than "does not check curve membership at all," and I cannot confirm which from the code available.

### Likelihood Explanation
Reachability is high — `sol_curve_group_op` is a permissionless syscall callable by any executing BPF program from an unprivileged transaction. [4](#0-3)  However, actual exploitability is gated on whether the underlying `solana-bls12-381-syscall` crate's "_unchecked" functions perform any implicit validation (e.g., via decompression/deserialization failing for non-group-element byte patterns) similar to the Curve25519 path. Given the explicit naming discrepancy between `ADD`/`SUB` ("_unchecked") and `MUL` (no such suffix) for the same point types in the same file, and given the existence of a separate opt-in `sol_curve_validate_point` syscall that callers must invoke themselves, there is a real risk this is an intentional but risky performance optimization, not a proven safety net.

### Recommendation
Verify the implementation of `bls12_381_g1_addition_unchecked`/`bls12_381_g2_addition_unchecked`/`bls12_381_g1_subtraction_unchecked`/`bls12_381_g2_subtraction_unchecked` in the `solana-bls12-381-syscall` crate. If they omit curve-membership (and, for G2/G1, correct-subgroup) checks, either (a) rename/replace these calls with checked variants consistent with the `MUL` path, or (b) explicitly call `bls12_381_g1_point_validation`/`bls12_381_g2_point_validation` on both `left_point` and `right_point` before invoking the "_unchecked" arithmetic in `SyscallCurveGroupOps`, mirroring how `edwards::add_edwards`/`subtract_edwards` already reject invalid points for Curve25519.

### Proof of Concept
Not constructible from the indexed repository alone: reproducing the issue requires crafting non-curve-member 48-byte (G1) or 96-byte (G2) byte strings and calling `sol_curve_group_op(BLS12_381_G1_BE, ADD, ...)` via a CPI/BPF test harness (analogous to the existing `test_syscall_edwards_curve_group_ops`/`test_syscall_ristretto_curve_group_ops` tests) and asserting whether the call succeeds with a non-identity, off-curve "result," instead of returning `1` as Curve25519 does. This test does not currently exist in `syscalls/src/lib.rs` for the BLS12-381 ADD/SUB paths (only implicit trust is shown, no explicit invalid-point test case was found for BLS12-381 add/sub) — its absence itself supports that this path has not been validated against malformed input the way the Curve25519 path has.
