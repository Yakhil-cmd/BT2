### No vulnerability found for this question. [1](#0-0) [2](#0-1) [3](#0-2) 

`calc-liq-debt-repay` at `mainnet/contracts/market/v0-4-market.clar:723` is a pure function of `liq-factor` and `total-debt-usd`, both of which are computed from the borrower's aggregate position state (`current-ltv`, egroup thresholds) in `calc-liquidation-params`, entirely independent of which `collateral-ft`/`debt-ft` pair is passed to `liquidate`. Varying the asset pair changes which debt/collateral asset is processed downstream (`process-debt-asset`, `process-collateral-asset`), but `max-debt-usd` (the value returned via `calc-liq-debt-repay`) is computed once from `total-debt-usd` and the liquidation factor before any asset-specific processing, so it cannot diverge between two `liquidate` calls that differ only in the targeted asset pair — contradicting the premise of the question's fast-validation test.

Additionally, the "payout routed through a principal that always rejects delivery" scenario does not describe a two-victim state-corruption path: the collateral receiver (`actual-receiver`) is chosen by the caller of `liquidate` (the liquidator, i.e., attacker A) for their own benefit via `collateral-receiver`, defaulting to `liquidator` itself if unset. If that receiver contract rejects the transfer, the `try!` on `collateral-remove` aborts the entire transaction, so no state changes are committed — this affects only the liquidator's own transaction, not a distinct unprivileged victim B's funds or withdrawable balance. There is no shared-state write by A that corrupts what B can withdraw; the borrower B's collateral/debt state is untouched unless the liquidation transaction fully succeeds under the existing health/slippage checks (`ERR-HEALTHY`, `ERR-SLIPPAGE`, `ERR-ZERO-LIQUIDATION-AMOUNTS`).

This fails the required two-unprivileged-principal shared-state pattern and the underlying computation is invariant to the asset pair, so the claim does not hold.
