Confirmed: `User#authorized?` gates all access on `Shipit.github_teams` membership [1](#0-0) , and `Authentication#force_github_authentication` enforces this on every controller request [2](#0-1) . `MembershipHandler#process` adds an arbitrary GitHub login to a `Team` purely from unauthenticated webhook payload fields [3](#0-2) .

### Title
Unauthenticated Webhook Signature Bypass Escalates into `Shipit.github_teams` Authorization - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` derives the GitHub organization to check the signature against solely from the untrusted request body, and `GitHubApp#verify_webhook_signature` treats an organization with no configured `webhook_secret` as automatically verified. This is the exact "onlyOwner missing" bug class from the report: a security-critical operation (accepting and acting on a webhook body) lacks a binding check between "the identity that was authenticated" and "the resource that gets written."

### Finding Description
`WebhooksController#verify_signature` selects the `GitHubApp` instance using `repository_owner`, a value read directly out of the unauthenticated JSON body (`params.dig('repository','owner','login') || params.dig('organization','login')`), then asks that app to verify the signature: [4](#0-3) 

`GitHubApp#verify_webhook_signature` short-circuits to `true` whenever no `webhook_secret` is configured for that organization: [5](#0-4) 

Setting `webhook_secret` is explicitly documented as optional: "Webhook secret (optional): Fill it with some randomly generated string" [6](#0-5) , and the shipped multi-org example configs leave it blank for every organization (`webhook_secret: # nil`) [7](#0-6) [8](#0-7) .

Consequently, for any configured organization that has not set a webhook secret (a documented, supported configuration), `verify_signature` passes for **any anonymous internet request**, regardless of the `X-Hub-Signature` header. Once past this gate, `WebhooksController#create` dispatches the raw, attacker-controlled JSON body to every registered handler for the claimed event [9](#0-8) .

The handlers never re-validate that the payload's "acted upon" identity matches the "authenticated" organization used at the gate:
- `Handler#stacks` resolves the target `Stack` purely from `payload.dig('repository','full_name')`, a field independent of and never cross-checked against the organization used in `verify_signature` [10](#0-9) .
- `MembershipHandler#process` takes attacker-supplied `team.id` and `member.login` and unconditionally adds that GitHub login to the local `Team` record, with no check that the sender actually belongs to that team on GitHub: [3](#0-2) 
- `Team#add_member` performs the addition unconditionally [11](#0-10) .

This directly feeds Shipit's authorization model: `User#authorized?` grants application access to any user who is a member of one of `Shipit.github_teams` [1](#0-0) , enforced on every request by `Authentication#force_github_authentication` [2](#0-1) .

**The binding that is broken:** "organization authenticated by `verify_signature`" (derived from an attacker-controlled field, and trivially bypassable when no `webhook_secret` is set) ≠ "identity/resource actually written by the handler" (`team.id`/`member.login` for membership, `repository.full_name` for push/status/check_suite). Nothing enforces that these are the same, or that the organization was ever cryptographically authenticated at all in the common no-secret configuration.

### Impact Explanation
This escalates into `Shipit.github_teams` authorization exactly as scoped: an unauthenticated attacker can forge a `membership` webhook event for any organization configured without a `webhook_secret`, targeting the `github_id` of any `Team` that exists in Shipit and gates access via `Shipit.github_teams`. `MembershipHandler` will create the `User` record for an arbitrary login (via `User.find_or_create_by_login!`, which fetches the public GitHub user profile) and add it as a team member, satisfying `User#authorized?` without ever having a real GitHub OAuth session belonging to that team. Combined with session/login flows, this is an authorization bypass into Shipit. The same signature bypass also lets an attacker forge `push`/`status`/`check_suite` events against any `Stack` (not limited to the "authenticated" org), influencing `GithubSyncJob`'s `expected_head_sha` and commit CI status, which can affect what is considered deployable and enable an unauthorized deploy.

### Likelihood Explanation
The `webhook_secret` field is explicitly documented as optional, and Shipit's own example multi-org configuration files ship with it unset for every organization, meaning this is not a rare misconfiguration but a directly-supported operating mode. Any deployment following the documented "Using Multiple Github Applications" setup without filling in every org's webhook secret is exposed, and no code in `WebhooksController` or the handlers enforces a second layer of binding between the organization used for verification and the resource acted upon.

### Recommendation
- Do not treat a missing `webhook_secret` as an automatic pass; require every configured organization to have a non-blank `webhook_secret`, or reject webhooks for organizations without one, in `GitHubApp#verify_webhook_signature`.
- In each `Handler`, cross-validate that the organization used to authenticate the webhook (`repository_owner`/`organization.login`) matches the organization owning the resource being mutated (`repository.full_name`'s owner segment, or the `Team#organization` for `MembershipHandler`) before performing any write.
- Consider additionally validating team membership changes against a live GitHub API call rather than trusting the webhook body outright.

### Proof of Concept
1. Configure Shipit (per documented, supported setup) with an organization, e.g. `victim-org`, and leave `webhook_secret` blank as the docs describe as optional.
2. As an anonymous attacker with no credentials, `POST /webhooks` with header `X-Github-Event: membership` and body:
```json
{
  "action": "added",
  "team": { "id": <existing_team_github_id>, "name": "x", "slug": "x", "url": "x" },
  "organization": { "login": "victim-org" },
  "member": { "login": "attacker-github-login" }
}
```
No valid `X-Hub-Signature` is required because `webhook_secret` is blank, so `verify_webhook_signature` returns `true` unconditionally.
3. `MembershipHandler#process` creates/finds the `attacker-github-login` `User` and adds it to the `Team` matching `team.id`.
4. If that team is included in `Shipit.github_teams`, the attacker's `User` now satisfies `User#authorized?`; upon completing GitHub OAuth login as that account, they gain full access to the Shipit instance.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
