### Title
Block revenue (`pending_delegator_rewards`) is distributed by current stake weight without regard to how long each stake contributed to the pool, letting newly-activated/increased stake dilute or steal already-accrued rewards from long-standing stakers — ([File: runtime/src/bank/partitioned_epoch_rewards/calculation.rs])

### Summary
`pending_delegator_rewards` on a vote account is a running pool that accumulates block-revenue deposits over an arbitrary number of epochs via `deposit_delegator_rewards()`, and is later split among all currently-delegated stake accounts strictly by their *current* proportional stake, with no memory of which stakers actually contributed stake while the pool was accruing. This is structurally the same flaw as the referenced wagmi-leverage bug, where fees owed are split by `individual_amount / total_amount` at redemption time instead of tracking each depositor's historical contribution, letting newer participants siphon rewards earned by earlier ones.

### Finding Description
`deposit_delegator_rewards` (SIMD-0123) accumulates arbitrary lamport deposits into `vote_state.pending_delegator_rewards` with a simple `checked_add`, and can be called repeatedly across many epochs before a distribution happens: [1](#0-0) 

When rewards are distributed for a given `rewarded_epoch`, `calculate_block_reward` splits the *entire current* `pending_delegator_rewards` balance among stake accounts purely by `stake / total_active_stake` for that one epoch's snapshot: [2](#0-1) 

There is no analog of `credits_observed` here — the mechanism that in the ordinary inflation-reward path (`calc_earned_credits`, `calculate_stake_points_and_credits`) explicitly prevents a stake account from being credited for periods before its own observed epoch: [3](#0-2) 

Unlike inflation rewards, where each stake tracks its own `credits_observed` per-account state to gate exactly how much of the vote account's accumulated credits it is entitled to, the block-revenue path has no equivalent "since-when" bookkeeping per stake account for `pending_delegator_rewards`. If the pool accrues deposits over several epochs (e.g., because distribution/recalculation is deferred, or deposits simply keep coming in via CPI from block-producer revenue), any stake account whose delegation only became active in the final reward epoch is treated identically to stake that was active the entire time the pool was accruing, and receives a full proportional cut of the whole historical pool. Conversely, stake accounts that deactivated during the accrual window (and are thus absent from `reward_epoch_delegated_stakes` at distribution time) receive nothing for the portion of the pool that accrued while they were staked and contributing to that validator's revenue-generating stake weight.

### Impact Explanation
This causes misattributed rewards between stakers of the same vote account: newly-delegated or newly-active stake captures a pro-rata share of block revenue that accrued before that stake existed/activated, at the direct expense of stakers who were delegated throughout the accrual period. It is the reward-distribution analog of the referenced report's "loss of funds for lenders / theft of fees by newer participants," mapped onto stake/vote program reward distribution rather than a lending protocol. Because this affects real lamport payouts recorded via `store_stake_accounts_in_partition`, it constitutes concrete misattribution/loss of already-earned rewards rather than a theoretical issue: [4](#0-3) 

### Likelihood Explanation
This requires the `block_revenue_sharing` feature to be active and for `pending_delegator_rewards` to accumulate deposits across more than one epoch before being fully distributed (plausible given deposits are driven by continuous block-producer revenue rather than being tied to per-epoch resets), combined with normal delegator churn (new delegations activating, or existing delegations deactivating) during that accrual window. No special privilege is required — any staker performing ordinary delegate/deactivate/split/merge operations around the accrual window is naturally exposed to this dynamic, and any user could also intentionally time large delegations right before a distribution to capture a disproportionate share.

### Recommendation
Track, per stake account, the portion of `pending_delegator_rewards` (or an epoch/timestamp marker analogous to `credits_observed`) that existed at the time the delegation became active, and only allow a stake account to claim its proportional share of the pool that accrued *since* it began contributing stake to that validator, mirroring how `credits_observed` gates inflation-reward eligibility in `calculate_stake_points_and_credits`/`calc_earned_credits`. Alternatively, distribute/reset `pending_delegator_rewards` every epoch based on that epoch's stake snapshot rather than allowing it to silently accumulate across multiple epochs with differing stake compositions.

### Proof of Concept
1. Validator enables block revenue sharing; over several epochs, block-producer revenue is deposited via `deposit_delegator_rewards`, growing `vote_state.pending_delegator_rewards` to a large value while only Staker A is delegated to the vote account for those epochs.
2. Just before the epoch in which rewards are calculated/distributed, Staker B delegates a large stake to the same vote account (and it becomes active/warmed by the `rewarded_epoch` used in `calculate_block_reward`).
3. At distribution, `calculate_block_reward` computes each staker's share as `pending_delegator_rewards * stake / total_active_stake` using only the current epoch's `reward_epoch_delegated_stakes` snapshot — Staker B receives a proportional share of the entire multi-epoch accumulated pool despite having contributed none of the block revenue that generated it, while Staker A's share is correspondingly diluted.
4. This can be confirmed against the existing test harness `get_block_reward_for_test`/`test_calculate_block_reward_specific` in `runtime/src/bank/partitioned_epoch_rewards/calculation.rs`, which demonstrates the reward is computed purely from `(individual_stake, total_stake, pending_delegator_rewards)` for a single epoch snapshot with no historical-contribution tracking: [5](#0-4)

fn calc_earned_credits(
    stake: &Stake,
    final_epoch_credits: u64,
    initial_epoch_credits: u64,
    new_credits_observed: &mut u64,
) -> u128 {
    let credits_in_stake = stake.credits_observed;

    // figure out how much this stake has seen that
    //   for which the vote account has a record
    let earned_credits = if credits_in_stake < initial_epoch_credits {
        // the staker observed the entire epoch
        final_epoch_credits - initial_epoch_credits
    } else if credits_in_stake < final_epoch_credits {
        // the staker registered sometime during the epoch, partial credit
        final_epoch_credits - *new_credits_observed
    } else {
        // the staker has already observed or been redeemed this epoch
        //  or was activated after this epoch
        0
    };
    *new_credits_observed = (*new_credits_observed).max(final_epoch_credits);
    u128::from(earned_credits)
}
