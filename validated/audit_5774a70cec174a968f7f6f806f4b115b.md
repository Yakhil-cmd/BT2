## Title
Missing authorization check on local signing requests allows any paired correspondent to trigger signing of transactions for addresses they do not co-sign - (File: wallet.js)

### Summary
`wallet.js`'s device-message handler for the `"sign"` command validates, on the **remote proxy** path (`ifRemote`), that the sender is actually listed among the cosigners of the address before forwarding/relaying a signing request. However, on the **local** path (`ifLocal`) — used when the requested address is a wallet address (single-sig or a shared/multisig address) whose signing key is hosted on the receiving device — the equivalent cosigner-membership check has been explicitly commented out, and no other authorization check replaces it.

### Finding Description
In `handleMessageFromHub`, the `"sign"` case calls `findAddress(body.address, body.signing_path, {...})` and dispatches based on where the signing key lives:

- `ifRemote(device_address, other_device_addresses)` — correctly enforces authorization:
```javascript
ifRemote: function(device_address, other_device_addresses){
    if (device_address === from_address)
        return callbacks.ifError("looping signing request for address "+body.address+", path "+body.signing_path);
    if (!other_device_addresses.includes(from_address))
        return callbacks.ifError("you are not listed as a cosigner for this address "+body.address);
    ...
``` [1](#0-0) 

- `ifLocal(objAddress)` — the equivalent check is dead code:
```javascript
ifLocal: function(objAddress){
    // the commented check would make multilateral signing impossible
    //db.query("SELECT 1 FROM extended_pubkeys WHERE wallet=? AND device_address=?", [row.wallet, from_address], function(sender_rows){
    //    if (sender_rows.length !== 1)
    //        return callbacks.ifError("sender is not cosigner of this address");
        callbacks.ifOk();
        ...
        eventBus.emit("signing_request", objAddress, body.address, objUnit, assocPrivatePayloads, from_address, body.signing_path);
``` [2](#0-1) 

This is the same class of bug as the Nuclio advisory: two sibling code paths that should both enforce membership/authorization before permitting a privileged operation diverge — one path populates/uses the membership check (`other_device_addresses.includes(from_address)` on `ifRemote`), the other short-circuits it entirely (commented-out cosigner lookup on `ifLocal`), so the "short-circuit" silently accepts any caller.

Because `handleMessageFromHub` is reached for any message from a paired correspondent whose device-level signature has already been verified (not necessarily a cosigner of `body.address`), the missing check means: **any device that is paired with the wallet (a correspondent) — not specifically a cosigner of the requested address — can submit a `sign` request naming an arbitrary local address and signing path**, and the wallet will proceed to `callbacks.ifOk()`, hash/validate the attacker-supplied unit, and emit `"signing_request"` for that address/unit, which is fed directly into `network.handleOnlineJoint(ws, objJoint)` and the `"signing_request"` event pipeline that ultimately produces a signature via the locally-held keys. [3](#0-2) 

### Impact Explanation
This affects payment inputs/outputs and shared-address ("wallet and contract message handling") authorization within ocore. On any deployment where the `"signing_request"` event handler does not perform its own independent authorization (e.g., automated/headless signer daemons, exchange-style hot wallets, or any integration that treats "already a paired correspondent" as sufficient trust), an attacker who is merely paired with the victim device — without ever being added as a cosigner path for the target shared address — can force the wallet to build, validate and sign a transaction spending from a shared address hosted on the victim's device. This directly maps to unauthorized spending of funds from a multi-signature address the attacker does not control, mirroring the write-path authorization bypass in the referenced advisory (a correctly-checked sibling path vs. a check that was disabled/omitted).

### Likelihood Explanation
Exploitation requires only that the attacker be paired with the target device (a standard, low-friction requirement of the pairing protocol) and know a valid `body.address` and `signing_path` for a shared address hosted there (obtainable via the shared-address exchange messages such as `new_shared_address`, which are also handled in the same file). No cosigner relationship on that address is required. The check was deliberately removed (per the inline comment) rather than merely forgotten, but no compensating identity/ownership check was substituted, leaving the authorization gap in the code path itself.

### Recommendation
Restore (or replace with an equivalent working query) the cosigner-membership check on the `ifLocal` branch of the `"sign"` handler in `wallet.js`, verifying that `from_address` is actually one of the device addresses associated with `body.address`/`body.signing_path` (e.g., via `shared_address_signing_paths` or `extended_pubkeys`, consistent with how `ifRemote` validates `other_device_addresses.includes(from_address)`) before emitting `"signing_request"` or invoking `network.handleOnlineJoint`.

### Proof of Concept
1. Device B pairs with Device A (standard pairing flow; B becomes a correspondent of A but is not a cosigner of any of A's shared addresses).
2. Device A hosts a shared/multisig address `SHARED_ADDR` with signing path `r.0` held locally, cosigned by devices C and D (not B).
3. Device B sends a `"sign"` message to Device A:
```json
{"address": "SHARED_ADDR", "signing_path": "r.0", "unsigned_unit": { ...attacker-crafted spend... }}
```
4. `handleMessageFromHub` resolves `findAddress` to `ifLocal` (since the key is hosted on A). Because the cosigner check is commented out, `callbacks.ifOk()` fires immediately and `"signing_request"` is emitted with `from_address = B`, even though B is not in `SHARED_ADDR`'s definition.
5. Any listener that proceeds to sign (e.g., an automated signer, or a UI that doesn't re-verify device membership) will sign the attacker-supplied unit using Device A's key share for `SHARED_ADDR`, contributing an unauthorized signature toward spending funds from that shared address.
