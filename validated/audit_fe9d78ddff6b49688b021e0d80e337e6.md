### Title
Reachable "unreachable" assertion in double-spend validation causes full node crash on a single crafted unit - (File: validation.js)

### Summary
CVE-2021-28090 describes a remote, unprivileged input reaching a directory authority and hitting an `assert()`, crashing the Tor process (TROVE-2021-002). The equivalent bug class in `ocore` is a `throw Error(...)` used as an internal "this should never happen" assertion inside the payment double-spend validation path, which is reachable from any unprivileged unit poster via the normal joint-validation flow and, if the invariant is ever violated, crashes the validating node instead of returning a controlled validation error.

### Finding Description
`checkForDoublespends()` in [1](#0-0)  is invoked from `validatePaymentInputsAndOutputs()` (via `checkInputDoubleSpend`) for every payment input of every posted unit, e.g. at [2](#0-1)  and again at the transfer-input branch [3](#0-2) .

Inside it, three code paths are guarded only by `throw Error(...)` rather than returning a normal `cb(err)` validation failure:
- `throw Error("conflicting "+type+" spent from another address?")` [4](#0-3) 
- `throw Error("unreachable code, conflicting "+type+" in unit "+objConflictingRecord.unit)` [5](#0-4) 
- `throw Error("double spending "+type+" without double spending address?")` [6](#0-5) 

These assumptions rely on the invariant that a conflicting spend record for the exact same source output (matched by `type, src_unit, src_message_index, src_output_index` or, for hc/witnessing, `type, from_main_chain_index, address`) must always carry an address that is among the current unit's authors, because ownership of that output/range was already checked earlier (e.g. `owner_address` check at [7](#0-6) ). This path is reached purely by an unprivileged unit poster: any node processing an inbound joint calls `validation.validate()` from `handleJoint()` in `network.js` [8](#0-7) , which for the base-asset/divisible/indivisible payment message types funnels into `validatePaymentInputsAndOutputs` → `checkForDoublespends`. If any edge case in the double-spend bookkeeping (e.g. interactions between `arrAddressesWithForkedPath`, nonserial/final-bad sequence transitions, private-asset paths, or asset denomination/attestor combinations) violates the assumed invariant even once, the `throw` executes deep inside an `async.eachSeries` callback chain, i.e., outside of any surrounding `try/catch` in `validate()`. This becomes an uncaught exception that crashes the Node.js process on every full node (and witness) that processes the same unit — mirroring the Tor assertion-failure crash triggerable by a single remote message.

### Impact Explanation
If triggered, an uncaught `throw Error` here crashes the entire node process, not just the single validation call. Because the same unit is broadcast and independently validated by every full node and witness in the network, a single specially crafted unit can potentially crash all nodes that receive it, matching the "network unable to confirm new units" impact criterion — an availability failure analogous to Tor directory authorities crashing on a crafted client request.

### Likelihood Explanation
Reachability of the code path itself is trivial and unauthenticated: any address can post a payment unit with input/output combinations, and this code executes on every double-spend check. However, actually forcing one of the three specific mismatched-address conditions requires finding a concrete sequence of prior double-spend/nonserial states that violates the developer's invariant (e.g., through `arrAddressesWithForkedPath` bookkeeping edge cases across multiple conflicting nonserial units). This is a genuine internal-consistency assumption, not an input-format check, so exploitability depends on finding such a sequence — the report cannot confirm a concrete input demonstrating the violation, only that the code structurally mirrors the Tor assertion-crash bug class (developer-assumed invariant enforced via `throw` on attacker-reachable validation code, with no containing try/catch).

### Recommendation
Replace the three internal `throw Error(...)` assertions in `checkForDoublespends()` ( [4](#0-3) , [5](#0-4) , [6](#0-5) ) with graceful `cb2(err)`/`ifUnitError`-style failures instead of hard crashes, and audit all other `throw Error` assertions reachable from `validate()`'s payment/double-spend/author code paths (e.g. lines 2417, 2420, 2422, 2424, 2451, 2458, 2476 in the same region) to ensure a maliciously or accidentally crafted unit can never bring down node availability, only fail validation of that unit.

### Proof of Concept
Not reproduced — this report identifies the structural analog (an internal "unreachable"/assertion `throw` reachable through unauthenticated unit posting and double-spend bookkeeping in `checkForDoublespends`) but does not include a concrete crafted unit sequence proven to violate the address-matching invariant.
