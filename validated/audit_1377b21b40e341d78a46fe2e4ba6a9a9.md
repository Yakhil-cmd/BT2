### Title
Reentrancy-guard coverage gap in pox-5's `signer-manager-validate-stake` allows a signer-manager callback to re-enter unrelated pox-5 state-mutating entry points during `register-for-bond` / `update-bond-registration` - (File: stackslib/src/chainstate/stacks/boot/pox-5.clar)

### Summary
`pox-5.clar` guards against re-entering `validate-stake!` calls specifically via a boolean flag (`signer-manager-call-active`), set/checked only inside the `signer-manager-validate-stake` helper. `register-for-bond` and `update-bond-registration` invoke this helper — and thus call out to an attacker-controlled `signer-manager-trait` contract — *before* they commit their own map mutations (`protocol-bond-memberships`, `staker-info`, per-cycle share/reward maps). Because the flag is only asserted inside the helper itself, it does not block re-entry into *other* public functions of pox-5 that do not go through `signer-manager-validate-stake`, during the window where the outer call's state has been read but not yet written.

### Finding Description
In `register-for-bond` (`stackslib/src/chainstate/stacks/boot/pox-5.clar`, around lines 642-842), the flow is:
1. Read `existing-membership`, `old-sbtc`, `existing-stake`, `bond`, `allowance` from maps (lines 679-707).
2. Perform several `asserts!` based on that state.
3. Call `signer-manager-validate-stake` (line 754), which performs a `contract-call?` into an attacker-supplied `signer-manager` contract implementing `signer-manager-trait` (lines 408-427).
4. Only *after* that external call returns does it call `settle-rewards`, `roll-sbtc`, and finally `map-set protocol-bond-memberships`/`protocol-bonds-total-staked`/per-cycle maps (lines 772-819).

The reentrancy flag `signer-manager-call-active` is set to `true` immediately before the external call and reset to `false` immediately after (lines 419-424), and is *only checked inside `signer-manager-validate-stake` itself* (line 419, and via `validate-no-reentrancy` in `set-bond-admin`, `set-pause-admin`, `pause-rewards`, `setup-bond`, and `register-signer`). It is **not** checked at the top of `register-for-bond`, `update-bond-registration`, `stake`, or other state-mutating stacker-facing entry points (only `register-signer`/admin setters call `validate-no-reentrancy`).

This means that while the outer `register-for-bond` call is paused waiting on the external `signer-manager.validate-stake!` call, the same `tx-sender` (Clarity's `contract-call?` does not change `tx-sender`, only `contract-caller`) can have the malicious `signer-manager` contract issue a nested `contract-call?` back into pox-5's other public entry points (e.g. a second, independent `register-for-bond` for a *different* bond-index, or any stacker function that reads `protocol-bond-memberships`/`staker-info`/`get-staker-custodied-sbtc` and mutates locked/custodied sBTC or STX) while the outer call's map state is still the *pre-registration* snapshot. Only a second call that itself tries to invoke `signer-manager-validate-stake` would be blocked by the flag; any other stacker-facing operation acting on the stale (not-yet-updated) `protocol-bond-memberships`/custody state is not blocked.

### Impact Explanation
If a reentrant call can act on the stale membership/custody snapshot before the outer call's `map-set` commits the new bond membership and moves `old-sbtc`→`new-sbtc` via `roll-sbtc`, the staker (acting through their own malicious `signer-manager`) could cause pox-5's custodied-sBTC accounting or per-cycle share bookkeeping to be updated twice for a single locked amount, or have registration state diverge from actual locked funds — i.e., breaking the equality between sats/STX actually locked and sats/STX credited toward reward shares/custody. That maps to the report's in-scope impact categories of double-counting a commitment/reward or unbacked crediting of locked value.

### Likelihood Explanation
Exploitability depends entirely on the attacker's own `signer-manager` contract (which they fully control, since `register-for-bond`/`update-bond-registration` accept an arbitrary `<signer-manager-trait>` reference) and on whether some other pox-5 entry point mutates the same custody/membership maps in a way exploitable mid-flight. This is a plausible but not fully proven path — I could not load and inspect the full `unstake`/`claim-rewards`/`roll-sbtc` implementations (the file is 3845 lines and truncated in the tool output at line 1000), so I cannot confirm with certainty that a concrete double-credit/double-unlock sequence exists, only that the reentrancy-guard's scope is narrower than the set of state-mutating functions that run around the external call.

### Recommendation
Extend the reentrancy guard so that `signer-manager-call-active` is checked (via `validate-no-reentrancy`) at the top of every public, state-mutating pox-5 function that can execute concurrently with an in-flight `signer-manager-validate-stake` call — not just the admin setters and `register-signer`. Alternatively, follow strict checks-effects-interactions ordering: commit all map mutations for `register-for-bond`/`update-bond-registration` before invoking the external `signer-manager` trait call, or use a global (not helper-scoped) reentrancy flag checked at the entry of every stacker-facing public function.

### Proof of Concept
Not independently verified end-to-end due to inability to read the full `unstake`/`roll-sbtc`/claim-rewards implementations (truncated file). Conceptually:
1. Attacker deploys a malicious contract implementing `signer-manager-trait`.
2. Attacker calls `register-for-bond` with this contract as `signer-manager`, for `bond-index` A, while already holding an active bond membership for a different/earlier position.
3. Inside `validate-stake!`, before returning `(ok true)`, the malicious contract issues a nested `contract-call?` into another pox-5 public function that reads/mutates `protocol-bond-memberships`, `staker-info`, or custody-related state for the same `tx-sender`, exploiting the fact that the outer call's `map-set` (lines 786-795) has not yet executed.
4. If that nested call can shift/duplicate custodied-sBTC or per-cycle share bookkeeping, the outer call then completes its own `map-set`, resulting in double-credited shares or STX/sBTC unlocked/counted against a single locked amount. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3)

(define-private (validate-no-reentrancy)
    (ok (asserts! (not (var-get signer-manager-call-active)) ERR_REENTRANT_CALL))
)

;; A helper function to call the `validate-stake!` function on a given
;; signer-manager, wrapping the reentrancy guard logic around it. This should
;; be the only way that `validate-stake!` is called in the contract, since it
;; is critical to ensure that reentrancy attacks are prevented.
(define-private (signer-manager-validate-stake
        (signer-manager <signer-manager-trait>)
        (staker principal)
        (first-index uint)
        (num-indexes uint)
        (amount-ustx uint)
        (amount-sats uint)
        (is-bond bool)
        (signer-calldata (optional (buff 500)))
    )
    (begin
        (asserts! (not (var-get signer-manager-call-active)) ERR_REENTRANT_CALL)
        (var-set signer-manager-call-active true)
        (try! (contract-call? signer-manager validate-stake! staker first-index
            num-indexes amount-ustx amount-sats is-bond signer-calldata
        ))
        (var-set signer-manager-call-active false)
        (ok true)
    )
)
