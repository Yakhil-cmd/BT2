### Title
Creator fee collection (`collect_creator_fee` / `collect_creator_fee_permissionless`) permanently locks creator fees if either token transfer reverts - (File: `programs/cp-swap/src/instructions/collect_creator_fee.rs`, `programs/cp-swap/src/instructions/collect_creator_fee_permissionless.rs`)

### Summary
Both creator-fee collection instructions perform two sequential CPI transfers (`transfer_from_pool_vault_to_user` for token_0 then token_1) inside a single all-or-nothing instruction, and only zero out the `creator_fees_token_0`/`creator_fees_token_1` counters after both transfers succeed. If either transfer reverts — e.g. because the pool creator's token account is frozen, blacklisted, paused, or subject to a Token-2022 transfer hook/permanent-delegate condition that rejects the transfer — the whole instruction fails, the fee counters are never reset, and the accrued creator fees remain permanently stuck in the pool vaults with no alternate withdrawal path.

### Finding Description
`collect_creator_fee` and `collect_creator_fee_permissionless` read the accumulated fee counters, then call `transfer_from_pool_vault_to_user` twice — once for `token_0_vault -> creator_token_0` and once for `token_1_vault -> creator_token_1` — before finally zeroing the counters: [1](#0-0) 

The permissionless variant is identical in structure and equally vulnerable, even though `payer` (any user) can trigger it, because the receiving accounts are always the fixed `pool_creator`'s associated token accounts: [2](#0-1) 

Both instructions delegate the actual CPI to `transfer_from_pool_vault_to_user`, which uses `token_2022::transfer_checked`. This call can fail for Token-2022 mints with extensions (freeze, permanent delegate, or a transfer hook that reverts under certain conditions) or for standard SPL tokens whose owner/authority has frozen the destination account: [3](#0-2) 

Because the instruction is atomic, a failure on either the token_0 or the token_1 leg reverts the entire transaction, so `pool_state.creator_fees_token_0`/`creator_fees_token_1` are never reset. Those amounts are already carved out of the tradeable pool balance — `vault_amount_without_fee` explicitly subtracts protocol, fund, and creator fees from the raw vault balances used for LP math — confirming that this portion of the vault balance is earmarked strictly for creator collection and has no other exit path: [4](#0-3) 

Every subsequent swap keeps incrementing `creator_fees_token_0`/`creator_fees_token_1` via `update_fees` regardless of whether collection is possible: [5](#0-4) 

Since there is no `clearBid()`-equivalent recovery mechanism (no way to redirect, skip, or partially collect fees, or to change the destination account), if the pool_creator's token account becomes permanently unable to receive the mint (frozen, blacklisted, or a reverting transfer hook), the creator fees for that pool are irrecoverably locked in the vault forever — exactly the bug class described in the report, mapped onto this program's only two reachable "distribute accrued balance via external transfer" entry points.

### Impact Explanation
Creator fee funds legitimately owed to the pool creator become permanently frozen inside the pool vaults with no way to ever withdraw them, since collection always attempts both legs atomically and there's no partial-collection or rerouting fallback. This is a genuine permanent freezing of user funds (the creator's accrued fee entitlement), growing unboundedly as swaps continue, and unrecoverable by any instruction in the current program surface (`initialize`, `deposit`, `withdraw`, `swap_base_input/output`, `collect_creator_fee[_permissionless]`).

### Likelihood Explanation
This requires the pool creator's own token account (or the mint) to enter a state that rejects incoming transfers — for example a Token-2022 mint with a freeze authority that freezes the creator's ATA, or a transfer-hook extension that reverts under some condition. Given the program explicitly supports Token-2022 mints with extensions (as seen in `utils/token.rs` importing `transfer_fee`, `ExtensionType`, etc.), pools built on such mints are directly exposed. The condition is plausible but depends on external token/mint configuration rather than being triggerable purely by an unprivileged swapper without any such mint properties.

### Recommendation
Decouple the two transfers so a failure on one leg does not block collection of the other, and only zero out the specific counter whose transfer succeeded (e.g., collect and reset token_0 fees and token_1 fees independently, each guarded by its own success/failure). Consider introducing an internal balance-tracking/`withdraw`-style pattern (as the referenced fix did) so that failed transfers do not brick future collection attempts, and/or allow the creator to redirect fee collection to an alternate account if the default one becomes unable to receive tokens.

### Proof of Concept
1. Create a pool where `token_0_mint` (or `token_1_mint`) is a Token-2022 mint with a freeze authority or a transfer-hook extension.
2. Let swaps occur so `creator_fees_token_0`/`creator_fees_token_1` accrue in `pool_state`.
3. Freeze the pool creator's associated token account for that mint (or otherwise cause the transfer-hook to always reject transfers to it).
4. Call `collect_creator_fee` or `collect_creator_fee_permissionless`; the `transfer_from_pool_vault_to_user` CPI for that leg reverts, the whole instruction reverts, and `creator_fees_token_0`/`creator_fees_token_1` are never reset — funds remain stuck in the vault indefinitely with no recovery instruction available.

pub fn transfer_from_pool_vault_to_user<'a>(
    authority: AccountInfo<'a>,
    from_vault: AccountInfo<'a>,
    to: AccountInfo<'a>,
    mint: AccountInfo<'a>,
    token_program: AccountInfo<'a>,
    amount: u64,
    mint_decimals: u8,
    signer_seeds: &[&[&[u8]]],
) -> Result<()> {
    if amount == 0 {
        return Ok(());
    }
    token_2022::transfer_checked(
        CpiContext::new_with_signer(
            *token_program.key,
            token_2022::TransferChecked {
                from: from_vault,
                to,
                authority,
                mint,
            },
            signer_seeds,
        ),
        amount,
        mint_decimals,
    )
}

    pub fn update_fees(
        &mut self,
        protocol_fee: u64,
        fund_fee: u64,
        creator_fee: u64,
        direction: TradeDirection,
    ) -> Result<()> {
        if !self.enable_creator_fee {
            require_eq!(creator_fee, 0)
        }
        let is_creator_fee_on_input = self.is_creator_fee_on_input(direction)?;
        match direction {
            TradeDirection::ZeroForOne => {
                self.protocol_fees_token_0 = self
                    .protocol_fees_token_0
                    .checked_add(protocol_fee)
                    .unwrap();
                self.fund_fees_token_0 = self.fund_fees_token_0.checked_add(fund_fee).unwrap();

                if is_creator_fee_on_input {
                    self.creator_fees_token_0 =
                        self.creator_fees_token_0.checked_add(creator_fee).unwrap();
                } else {
                    self.creator_fees_token_1 =
                        self.creator_fees_token_1.checked_add(creator_fee).unwrap();
                }
            }
            TradeDirection::OneForZero => {
                self.protocol_fees_token_1 = self
                    .protocol_fees_token_1
                    .checked_add(protocol_fee)
                    .unwrap();
                self.fund_fees_token_1 = self.fund_fees_token_1.checked_add(fund_fee).unwrap();
                if is_creator_fee_on_input {
                    self.creator_fees_token_1 =
                        self.creator_fees_token_1.checked_add(creator_fee).unwrap();
                } else {
                    self.creator_fees_token_0 =
                        self.creator_fees_token_0.checked_add(creator_fee).unwrap();
                }
            }
        };
        Ok(())
    }
