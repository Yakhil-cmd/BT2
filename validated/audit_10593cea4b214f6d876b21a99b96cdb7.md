### Title
`provision?` operator-precedence bug bypasses `review_stacks_enabled` gate, allowing unauthorized `ReviewStack` creation - (File: `app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb`)

### Summary
`OpenedHandler#provision?` combines `review_stacks_enabled` with the three `provisioning_behavior` checks using bare `&&`/`||` without parentheses, so `review_stacks_enabled` only gates the `allow_all` branch and is never applied to the `allow_with_label` or `prevent_with_label` branches. As a result, a repository with review stacks disabled (`review_stacks_enabled: false`) but `provisioning_behavior: allow_with_label` will still provision a `ReviewStack` if the incoming PR carries the configured label.

### Finding Description
The broken binding: the intended invariant is `repository.review_stacks_enabled == true` must hold for any stack creation via this handler, but the code allows creation when `repository.review_stacks_enabled == false` (with `provisioning_behavior_allow_with_label?` true and the PR label present), or symmetrically for `prevent_with_label?` when the label is absent.

Code path: [1](#0-0) 

Ruby precedence evaluates this as `(review_stacks_enabled && allow_all?) || (allow_with_label? && label_present) || (prevent_with_label? && !label_present)`. With `review_stacks_enabled = false`, `provisioning_behavior = :allow_with_label`, and the PR containing the repo's `provisioning_label_name`, the first term is `false`, the second term is `true`, so `provision?` returns `true` even though review stacks are disabled for this repository.

`respond_to_pull_request_opened?` then permits `process` to call: [2](#0-1) 

`ReviewStackAdapter#find_or_create!`/`create!` does not itself re-check `review_stacks_enabled` — it just uses the `repository.review_stacks` association scope for lookups and creates unconditionally: [3](#0-2) 

`Repository#review_stacks` is a plain `has_many` association with no filtering by the enabled flag: [4](#0-3) 

So the only enforcement point for `review_stacks_enabled` in this flow is the buggy `provision?` expression, and it fails to enforce it for two of the three provisioning-behavior branches.

Existing guards do not prevent this: `WebhooksController#verify_signature` only ensures the payload genuinely came from GitHub for the given organization (a legitimately configured GitHub App delivering a webhook for a real `opened` pull_request event on a tracked repository) — it does not validate any business authorization about whether review stacks should be provisioned, so it does not stop this logic bug: [5](#0-4) 

Exploit flow: an attacker who can open a pull request against a repository already tracked by Shipit (their own fork/branch, or a public repo where they can label their own PR) opens a PR and adds a label equal to `repository.provisioning_label_name`. If that repository is configured with `review_stacks_enabled: false` and `provisioning_behavior: allow_with_label` (a legitimate, presumably-safe configuration meant to fully disable review-stack automation), the webhook still reaches `OpenedHandler`, `provision?` incorrectly returns `true`, and a `ReviewStack` is created with `branch: params.pull_request.head.ref` and queued via `Shipit::ReviewStackProvisioningQueue.add`, triggering downstream provisioning/step execution on the deploy host for that repository.

### Impact Explanation
This causes creation of an unauthorized `Shipit::ReviewStack`/`Stack` record and queues it for provisioning even though the repository operator explicitly disabled review stacks (`review_stacks_enabled: false`). Provisioning a stack leads to task/step execution on the deploy host tied to attacker-controlled `branch`/`head.ref` and PR metadata. This is repeatable against any repository configured with `review_stacks_enabled: false` + `provisioning_behavior: allow_with_label` (or `prevent_with_label` with the label omitted), by any user able to open/label a PR on that repository. This matches the "unauthorized deploy/record written for a repository whose configuration should have prevented it" Critical impact category.

### Likelihood Explanation
Preconditions: repository must exist in Shipit, have `review_stacks_enabled: false`, and `provisioning_behavior` set to `allow_with_label` (or `prevent_with_label`). Attacker cost is low — opening a PR and applying a label they control (or that's auto-applied) on a repo they can PR against. No secrets, sessions, or elevated GitHub permissions are required beyond standard PR/label rights on the target repo, both of which are within the stated unprivileged-attacker capabilities. This is fully repeatable per matching repository configuration.

### Recommendation
Add explicit parentheses so `review_stacks_enabled` gates the entire behavior decision:
```ruby
def provision?
  repository.review_stacks_enabled &&
    (
      repository.provisioning_behavior_allow_all? ||
      (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
      (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
    )
end
```
Additionally, consider defense-in-depth by having `ReviewStackAdapter#create!` (or its scope) verify `repository.review_stacks_enabled` before creating, rather than relying solely on caller-side gating.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb (conceptual addition)
test "does not provision a review stack when review_stacks_enabled is false, even with matching label" do
  repository = shipit_repositories(:shipit)
  repository.update!(
    review_stacks_enabled: false,
    provisioning_behavior: :allow_with_label,
    provisioning_label_name: "deploy-preview"
  )

  payload = pull_request_opened_payload(
    repository: repository,
    labels: [{ "name" => "deploy-preview" }]
  )

  assert_no_difference -> { Shipit::Stack.count } do
    Shipit::Webhooks::Handlers::PullRequest::OpenedHandler.new(payload).process
  end
end
```
Before the fix: `Shipit::Stack.count` increases by 1 (bug reproduced — `repository.review_stacks_enabled == false` yet a stack is created, violating the required `repository.review_stacks_enabled == true` binding). After applying the recommended parenthesization, the assertion passes with no stack created.
