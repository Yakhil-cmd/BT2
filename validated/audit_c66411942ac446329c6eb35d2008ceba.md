### Title
Webhook signature is verified against the organization derived from `repository.owner.login`, but every event handler resolves the target repository from the independently-attacker-controlled `repository.full_name` field - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App / `webhook_secret` to validate a delivery against using `repository_owner`, computed from the JSON body itself. `Webhooks::Handlers::Handler#repository_name`, used by every handler (push, status, check_suite, pull_request) to look up the `Repository`/`Stack` to act on, reads a *different* field of the same attacker-supplied body: `repository.full_name`. Nothing enforces that `repository.full_name`'s owner segment matches `repository.owner.login`.

### Finding Description
In a multi-organization Shipit deployment (`config/secrets.yml` `github:` keyed by org, see `docs/setup.md` "Using Multiple Github Applications" and `test/dummy/config/secrets_double_github_app.yml`), each organization has its own `webhook_secret`. Signature verification is: [1](#0-0) [2](#0-1) 

`repository_owner` is derived purely from the JSON body (`repository.owner.login`, falling back to `organization.login`) and used to pick the `GitHubApp`/secret via `Shipit.github(organization: repository_owner)`. Once the HMAC check passes, the raw `params` are dispatched unchanged to handlers: [3](#0-2) 

Every handler, however, resolves which `Repository`/`Stack` to operate on from a *different* field of the same body: [4](#0-3) 

For example `PushHandler`, which triggers `GithubSyncJob`/`stack.sync_github` (and, for continuously-deployed stacks, downstream automatic deploys): [5](#0-4) 

`Repository.from_github_repo_name` performs a bare DB lookup by owner/name parsed out of `full_name`, with no cross-check against `repository.owner.login`: [6](#0-5) 

Binding broken (as an equality that should hold but doesn't):
`organization_that_authenticated_the_signature (repository.owner.login / organization.login)` == `organization_embedded_in(repository.full_name)` — this equality is never checked. GitHub itself always keeps these two fields consistent in genuine deliveries, but nothing in Shipit's own code enforces it; the whole payload is attacker-controlled once a valid HMAC for *any* configured org's secret is produced.

### Impact Explanation
An attacker who legitimately controls (or has been granted) any one of the multiple GitHub organizations configured on a shared Shipit instance — and therefore knows that organization's own `webhook_secret` — can sign a webhook body whose `repository.owner.login` matches their org (satisfying signature verification) while setting `repository.full_name` to `"other-org/other-repo"`, a repository belonging to a completely different tenant organization on the same instance. This lets the attacker drive `PushHandler`/`StatusHandler`/`CheckSuiteHandler` logic against stacks they do not own, e.g. forcing `stack.sync_github(expected_head_sha: ...)` for another organization's stack, which can trigger deploy-review/continuous-deployment state transitions for that stack without ever having a valid credential for the target organization. This matches the "unauthorized deploy/rollback" class of High-severity impact and is a direct analog of the report's "value the guard checks vs. value the logic consumes" mismatch (oracle vs. actual balance used).

### Likelihood Explanation
Requires the deployment to use the multi-organization GitHub App configuration (explicitly documented and supported: `docs/setup.md`, `test/dummy/config/secrets_double_github_app.yml`) and requires the attacker to control one legitimate organization/webhook secret out of several configured on the shared instance — a realistic scenario for platform teams running one Shipit instance across many orgs/teams. No access to the *target* organization's credentials is needed, only to any one tenant's own webhook secret, which each org's own admins legitimately possess.

### Recommendation
In `Webhooks::Handlers::Handler#repository_name` (or centrally in `WebhooksController#create`), assert that the owner segment of `payload.dig('repository', 'full_name')` matches the `repository_owner`/organization already authenticated by `verify_signature`, and reject the delivery (422) on mismatch. Alternatively, pass the authenticated organization down into handlers and scope `Repository.from_github_repo_name` lookups to `owner: authenticated_organization` explicitly rather than trusting the unrelated `full_name` field.

### Proof of Concept
1. Operator runs one Shipit instance configured with two orgs, `OrgA` (secret `secretA`) and `OrgB` (secret `secretB`), each per `docs/setup.md`'s multi-org config. `OrgA` hosts `OrgA/victim-repo`, tracked by a continuously-deployed Shipit stack.
2. Attacker is a legitimate GitHub App admin of `OrgB` only, and thus knows `secretB`.
3. Attacker crafts a `push` payload body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "OrgB" },
    "full_name": "OrgA/victim-repo"
  }
}
```
4. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(secretB, body)` and POSTs to `/webhooks` with `X-Github-Event: push`.
5. `verify_signature` resolves `repository_owner => "OrgB"`, loads `Shipit.github(organization: "OrgB")`, and the signature validates successfully (attacker legitimately knows `secretB`).
6. `PushHandler#process` is invoked with the full payload; `repository_name` reads `"OrgA/victim-repo"` from `full_name`, looks up `OrgA`'s `Repository`/`Stack`, and calls `stack.sync_github(expected_head_sha: "<attacker-chosen sha>")` — acting on `OrgA`'s stack despite the delivery only being authenticated for `OrgB`.
