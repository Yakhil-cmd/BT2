### Title
Webhook signature verification is bound to an attacker-controlled `repository_owner`/`organization` field, not to the repository the event actually mutates - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub organization's `webhook_secret` to validate a payload against using a field taken from the same unauthenticated JSON body (`repository.owner.login` / `organization.login`), rather than from anything cryptographically tied to the commit/repository the handler subsequently mutates. `StatusHandler` then updates commit statuses by looking up `Commit.where(sha: params.sha)` **without any repository scoping at all**. Because Shipit natively supports multi-organization deployments (`Shipit.github_organizations`, `Shipit.github_app_config`), a party who legitimately administers the webhook for *any one* onboarded GitHub organization can produce a validly-signed payload for that organization, but populate `sha`/`repository` fields that belong to a completely different organization's stack, forging a CI status for a commit they do not own.

### Finding Description
The equality that must hold is:

`organization_whose_secret_signed(payload) == organization_that_owns(target_of(payload))`

**Signature verification side** — the org used to pick the verifying secret is taken straight from attacker-controlled JSON, not derived from anything the signature independently authenticates: [1](#0-0) [2](#0-1) 

`Shipit.github(organization: repository_owner)` looks up a per-organization `GitHubApp` instance/secret keyed by this same attacker-supplied string: [3](#0-2) 

**Mutation side** — `StatusHandler#process` looks up commits purely by `sha`, with **no repository/stack scoping whatsoever**, unlike `PushHandler`/`CheckSuiteHandler` which at least filter via `Handler#stacks` (`Repository.from_github_repo_name(repository_name)`): [4](#0-3) [5](#0-4) 

Nothing anywhere checks that `repository.owner.login` (used to pick the verifying secret) matches the owner of the repository that actually contains the commit named by `sha`. The HMAC only proves "this body was signed with organization X's secret" — it says nothing about which commit/repository the body's other fields are allowed to reference.

### Impact Explanation
Since Shipit is designed to host multiple organizations behind one instance (`Shipit.github_organizations`), the attacker only needs to be a legitimate admin/owner of the webhook configuration for **any one** onboarded organization (a low-trust, unprivileged position with respect to Shipit — they hold no `ApiClient` token, no `api_clients_secret`, no GitHub App private key, and no access to the *target* organization's `webhook_secret`). Using their own organization's secret, they can forge a `status` event whose `sha` matches a commit belonging to a *different* organization's stack in the same Shipit instance, injecting a fabricated `success` status for a `context` referenced by that stack's `ci.require` configuration. Since Shipit gates deploys on required commit statuses, this can be used to satisfy CI-required checks it did not actually pass, leading to an **unauthorized deploy** — a Critical impact per the program's rules.

### Likelihood Explanation
This requires no privileged Shipit credential — only administrative control of the webhook for one organization already configured in a shared, multi-tenant Shipit deployment, which is an explicitly supported and documented configuration mode (`github_organizations`/`github_app_config`). The `StatusHandler` lacking any repository scoping (in contrast to every other handler that uses `Handler#stacks`) makes this directly and trivially reachable once a valid signature for any onboarded org is obtainable.

### Recommendation
- Bind the verified signature to the actual target: derive the organization used to look up the webhook secret from the *matched* `Repository`/`Stack` record (looked up by `repository.full_name`) rather than from the raw, attacker-supplied `repository.owner.login` field, and reject the payload if the two disagree.
- Fix `StatusHandler#process` to scope its `Commit` lookup to `stacks` (as `PushHandler`/`CheckSuiteHandler` already do), so it cannot update commits belonging to stacks/repositories outside the payload's claimed repository.
- Add an invariant test asserting that a validly-signed payload for organization A can never mutate state belonging to organization B's stacks.

### Proof of Concept
1. Shipit instance is configured for multiple GitHub organizations, e.g. `org-a` and `org-b`, each with its own Shipit-App webhook secret (`secrets.github.org-a.webhook_secret`, `secrets.github.org-b.webhook_secret`), per `lib/shipit.rb#github_app_config`.
2. Attacker administers the GitHub App/webhook installation for `org-b` (their own organization) and therefore knows `org-b`'s `webhook_secret`.
3. Attacker crafts a `status` event JSON body:
   ```json
   {
     "sha": "<sha of a commit belonging to org-a's stack>",
     "state": "success",
     "context": "required-ci-check",
     "repository": { "owner": { "login": "org-b" }, "full_name": "org-b/some-repo" }
   }
   ```
4. Attacker computes `X-Hub-Signature: sha1=HMAC(org-b_webhook_secret, body)` and POSTs to `/webhooks` with `X-Github-Event: status`.
5. `WebhooksController#verify_signature` resolves `repository_owner` = `"org-b"`, fetches `org-b`'s `GitHubApp`, and the HMAC validates successfully — [1](#0-0) .
6. `StatusHandler#process` runs `Commit.where(sha: params.sha)` — matching the `org-a` commit regardless of the `repository` field in the payload — and calls `commit.create_status_from_github!(params)`, injecting a forged `success` status onto `org-a`'s commit — [4](#0-3) .
7. If `org-a`'s `shipit.yml` lists `required-ci-check` in `ci.require`, the forged status satisfies the deploy gate, enabling an unauthorized deploy of `org-a`'s stack.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
