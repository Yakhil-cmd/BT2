## Title
Uncaught NULL/TypeError DoS in `handleOnlinePrivatePayment()` when `payload` field is missing from a peer/device-sent private payment element - (File: network.js)

## Summary
`network.js:handleOnlinePrivatePayment()` is the direct analog of the OpenSSL CMS bug class: an optional/attacker-supplied structure field is dereferenced before its presence is validated, causing a NULL/undefined property access that crashes (throws) before any authentication or validation logic runs.

## Finding Description
`handleOnlinePrivatePayment(ws, arrPrivateElements, bViaHub, callbacks)` only validates that `arrPrivateElements` is a non-empty array before immediately accessing a nested optional field: [1](#0-0) 

```
function handleOnlinePrivatePayment(ws, arrPrivateElements, bViaHub, callbacks){
	if (!ValidationUtils.isNonemptyArray(arrPrivateElements))
		return callbacks.ifError("private_payment content must be non-empty array");
	
	var unit = arrPrivateElements[0].unit;
	var message_index = arrPrivateElements[0].message_index;
	var output_index = arrPrivateElements[0].payload.denomination ? arrPrivateElements[0].output_index : -1;
	...
```

Line 2382 dereferences `arrPrivateElements[0].payload.denomination` without first checking that `.payload` exists (analogous to the OpenSSL bug reading `KeyEncryptionAlgorithmIdentifier`'s optional `parameters` field without checking `if (params != NULL)`). If `arrPrivateElements[0].payload` is `undefined` (a crafted or malformed device/hub message with a `unit`, `message_index`, but no `payload` key), this throws `TypeError: Cannot read properties of undefined (reading 'denomination')` before any of the subsequent validation (`isValidBase64`, `isNonnegativeInteger`, etc.) or asset/cryptographic checks occur.

This function is reachable from the wallet device-message path via `network.handleOnlinePrivatePayment` called from `wallet.js`'s hub-forwarded private payment chain handler; while `wallet.js:handlePrivatePaymentChains()` does pre-validate `isNonemptyObject(e.payload)` for chains delivered through that specific route, `handleOnlinePrivatePayment` is a separately exported/callable entry point invoked from multiple call sites in `network.js`/`wallet.js` (5 references in `wallet.js`, 3 in `network.js`), and it performs no independent defense against a missing `payload` on its own. Any call path that reaches it without first guaranteeing `payload` is a non-empty object (e.g., a directly received `private_payment` justsaying message processed via this function) can trigger the crash purely from attacker-controlled message content, with no signature check having occurred yet.

## Impact Explanation
An unhandled `TypeError` thrown synchronously inside a network/wallet message handler crashes or destabilizes the process (uncaught exception in Node.js terminates the process unless a global handler swallows it), producing a Denial of Service against the wallet/hub component that processes private payment messages — matching the "network unable to confirm/process new units" impact class permitted by the rules. This occurs before any cryptographic/authentication validation of the private payment chain, exactly mirroring the CVE's "applications may crash before authentication or cryptographic operations occur."

## Likelihood Explanation
The trigger requires only sending a `private_payment`-class message (or a chain via the hub-relay path) with the first element containing `unit`/`message_index` fields but omitting `payload`. This is a minimal, easily crafted malformed message from any device/peer able to reach `handleOnlinePrivatePayment`, requiring no valid signatures or prior state.

## Recommendation
Add an explicit presence/type check for `arrPrivateElements[0].payload` (e.g., `ValidationUtils.isNonemptyObject(arrPrivateElements[0].payload)`) immediately after the array-emptiness check in `handleOnlinePrivatePayment`, before accessing `.payload.denomination`, and return `callbacks.ifError(...)` on failure, consistent with how `wallet.js:handlePrivatePaymentChains()` already validates payload presence.

## Proof of Concept
Send (or relay) a private-payment message where `arrPrivateElements` is `[{ unit: "<44-char base64>", message_index: 0 }]` (no `payload` key) to a node/wallet path that calls `network.handleOnlinePrivatePayment` directly. Execution reaches line 2382, `arrPrivateElements[0].payload` is `undefined`, and `.denomination` access throws a `TypeError`, crashing/destabilizing the handler before any further validation is performed.
