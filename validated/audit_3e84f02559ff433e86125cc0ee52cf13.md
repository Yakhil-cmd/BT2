### Title
Cross-repository commit-status forgery via unscoped `sha` lookup in `StatusHandler` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
GitHub webhook signature verification is scoped per-organization: `WebhooksController#verify_signature` selects the GitHub App config (and therefore the `webhook_secret` used to validate the HMAC) based on `repository.owner.login` in the incoming payload. [1](#0-0)  However, the `status` event handler never re-checks that the target commit actually belongs to the repository/organization whose secret authenticated the request — it matches purely on commit `sha` across the entire `Commit` table. [2](#0-1)  This breaks the intended binding "organization that authenticated == repository that is written."

### Finding Description
Most webhook handlers correctly scope mutations to the repository named in the payload by going through `Handler#stacks`, which resolves `Repository.from_github_repo_name(repository_name)` using `payload.dig('repository', 'full_name')` before touching any records — see `PushHandler#process` [3](#0-2)  and `CheckSuiteHandler#process`, which additionally filters `stacks.where(branch: ...)` before touching `stack.commits`. [4](#0-3)  The base `Handler` class itself defines this repository-scoping helper. [5](#0-4) 

`StatusHandler` deviates from this pattern: it never calls `stacks`/`repository_name` at all, and instead does a global lookup:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [2](#0-1) 

The `Commit` table is not partitioned by repository ownership at the query level here — any commit row in the entire Shipit installation whose `sha` matches `params.sha` will have a status created from the attacker-authored payload, regardless of which repository/organization that commit belongs to.

Because the HMAC signature only proves that the payload was signed with the `webhook_secret` configured for `repository.owner.login` (the org named in the payload), it proves "this request is a legitimate status event for some repository under org X" — it does **not** prove "the sha referenced only exists in a repository under org X." In a Shipit deployment tracking multiple organizations/repositories (the multi-org GitHub App config supported by `Shipit.github(organization:)` / `github_app_config`) [6](#0-5) , an attacker who legitimately controls a GitHub App installation/webhook for their own low-privilege organization/repo can send (or have GitHub send, since GitHub itself emits `status` events for any commit pushed, including on forks) a `status` webhook whose `sha` collides with a commit sha tracked under a different organization's stack. Sha collisions are not contrived: forked repositories, shared template-generated initial commits, or vendored/cherry-picked commits routinely share identical SHA1 hashes across unrelated repositories that Shipit has ingested as separate `Stack`/`Commit` rows.

The impact of forging a commit status is significant in Shipit: commit statuses gate CI-based deploy safety checks (`required_statuses`, `soft_failing_statuses`, `blocking_statuses` in `DeploySpec`) [7](#0-6)  and mark commits `deployable?`. Injecting a fabricated `success` status onto a commit belonging to an unrelated stack can flip that commit to deployable, bypassing the CI gate for a repository the attacker's authenticated organization has no relationship to — an unauthorized-deploy precondition achieved purely by an org that legitimately owns a *different* webhook secret.

### Impact Explanation
This is a cross-repository write: an entity authenticated only for organization/repo A can mutate commit-status state belonging to organization/repo B, which can be leveraged to make an unrelated stack's commit falsely appear CI-green/deployable, satisfying the "unauthorized deploy" / "cross-repository writes" Critical impact category defined in scope.

### Likelihood Explanation
Requires the attacker to control (or have GitHub deliver events for) a legitimately configured repository/organization within the same Shipit instance, and for a commit sha to coincide between that repository and the victim stack's tracked commits — realistic for forks, shared templates, or reused history, but not guaranteed for arbitrary victim repositories, so likelihood is moderate rather than trivial.

### Recommendation
Scope `StatusHandler#process` the same way as other handlers: resolve the target repository via `Handler#stacks` (using `payload.dig('repository', 'full_name')`) and restrict the `Commit` lookup to commits within stacks belonging to that resolved repository, e.g. `stacks.flat_map(&:commits).where(sha: params.sha)`, mirroring the scoping already done in `CheckSuiteHandler`.

### Proof of Concept
1. Shipit instance is configured with multiple GitHub organizations, each with its own `webhook_secret` (per `github_app_config`). [8](#0-7) 
2. Attacker legitimately controls org `attacker-org`'s GitHub App/webhook secret and pushes a commit `C` whose sha happens to match a commit already tracked by Shipit under stack `victim-org/victim-repo` (e.g., because `victim-org/victim-repo` is a public fork of a repo attacker-org also forked, sharing ancestor commit `C`).
3. Attacker triggers (or GitHub naturally sends) a `status` webhook for commit `C` with `state: "success"`, signed with `attacker-org`'s valid `webhook_secret`.
4. `WebhooksController#verify_signature` selects `Shipit.github(organization: "attacker-org")` and verifies successfully, since the signature is valid for that org's secret. [1](#0-0) 
5. `StatusHandler#process` runs `Commit.where(sha: "C")`, which returns the commit row under `victim-org/victim-repo` too (global query, no repository scoping), and calls `create_status_from_github!` on it — writing a forged `success` status onto a commit in a repository the attacker has no relationship to. [2](#0-1)

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
