### Title
Cross-repository status forgery via unscoped `Commit.where(sha:)` lookup - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` matches incoming GitHub `status` webhooks purely by commit SHA (`Commit.where(sha: params.sha)`), with no repository/stack scoping, unlike other handlers (e.g. `PullRequest::OpenedHandler`) that resolve `Shipit::Repository.from_github_repo_name(params.repository.full_name)` before touching any records. [1](#0-0) [2](#0-1)  Because git SHAs are content-addressed and identical across forks/mirrors of the same history, a webhook signed for one repository/organization can write a `Status` row onto a `Commit` belonging to an entirely different stack whose repository shares that SHA.

### Finding Description
The broken binding: the code implicitly assumes `commit.stack.repository == payload.repository`, but nothing enforces `Commit.where(sha:).stack.repository.full_name == payload['repository']['full_name']`.

Path: `POST /webhooks` → `WebhooksController#create` → `verify_signature` checks the HMAC signature using the secret configured for `repository_owner` (derived from `payload['repository']['owner']['login']`) [3](#0-2)  — this only proves the request came from GitHub for *that* owning organization/app installation, it says nothing about which stacks may be mutated. `Handler` base class exposes a `stacks` helper scoped by `repository_name` from the payload, intended for handlers to restrict their writes to the originating repository's stacks [4](#0-3) . `StatusHandler#process`, however, never uses this scoping — it queries the global `Commit` table by bare `sha` and calls `commit.create_status_from_github!(params)` on every match [1](#0-0) .

The `commits` table's uniqueness constraint is `(sha, stack_id)`, not `sha` alone [5](#0-4) , confirming the schema expects and permits the *same* SHA to exist as distinct `Commit` rows across multiple stacks (e.g., a repo mirrored/forked into two Shipit stacks, or a monorepo with several stacks referencing overlapping history). An attacker who owns a fork of the victim's repository, with their own legitimate Shipit stack/GitHub App webhook configured (satisfying `verify_signature` with their own valid secret), can send a `status` event for a SHA shared with the victim's upstream history: `context: ci/jenkins`, `state: failure`. `StatusHandler` finds all `Commit` rows with that SHA — including the victim stack's row — and calls `commit.create_status_from_github!` on it, exactly as if the victim's own CI had reported the status.

Downstream, `Status::Common#blocking?` returns true when `!success? && commit.blocking_statuses.include?(context)` [6](#0-5) , and `Commit#blocked?` walks `stack.commits.reachable.newer_than(...).older_than(self).any?(&:blocking?)` [7](#0-6) , which gates `Commit#deployable?` [8](#0-7) . A forged `failure` on a shared SHA in a `blocking_statuses`-configured stack thus blocks (or, with a forged `success`, unblocks) deploys for a stack the attacker never authenticated against. `create_status_from_github!` (via `add_status`) also emits `commit_status`/`deployable_status` hooks and triggers `stack.schedule_merges` [9](#0-8) , so the forged event can additionally drive merge-queue behavior on the victim stack.

None of the existing guards prevent this: `verify_signature` authenticates the sender's own organization but is irrelevant to which stack's records get mutated; `drop_unhandled_event` only checks the event type is handled; the `ExplicitParameters` schema for `StatusHandler` requires only `sha`/`state`/`context`, with no `repository` object at all, so there's no repository binding to even check against.

### Impact Explanation
A forged status webhook signed only for the attacker's own repository writes a `Status` record onto a `Commit` belonging to a victim's stack, flips `blocked?`/`deployable?` for that stack, and can suppress or force deploy gating and trigger merge scheduling — a cross-tenant state mutation matching the "payload for one repository mutating another's stack, commit" Critical category. The blast radius extends to any pair of stacks whose repositories share commit SHAs (forks, mirrors, repo renames/splits), which is a realistic and common Shipit deployment pattern.

### Likelihood Explanation
Preconditions: the attacker needs (a) a repository with a legitimate Shipit stack and working webhook (achievable by any GitHub user who forks/mirrors a project and sets up their own Shipit instance/stack pointing at it, or otherwise obtains a valid signed `status` event for a SHA that also exists in the victim stack's `commits` table), and (b) the victim stack must have `blocking_statuses` configured and contain a `Commit` row with the shared SHA (true for any commit that predates the fork point or is otherwise shared history). No Shipit secrets, sessions, or privileged roles are required beyond the attacker's own repo's webhook signing key, which they legitimately control. This is repeatable per shared SHA and per stack.

### Recommendation
Scope `StatusHandler#process` by the originating repository, mirroring the `stacks` pattern used elsewhere: require `repository.full_name` in the params schema, resolve `Shipit::Repository.from_github_repo_name(params.repository.full_name)`, and only update `Commit` rows belonging to that repository's stacks (`stacks.commits.where(sha: params.sha)` or equivalent joined scope), rather than matching by bare SHA across the entire `commits` table.

### Proof of Concept
minitest plan (e.g. in `test/models/webhooks/handlers/status_handler_test.rb`):
1. Create two stacks, `victim_stack` (repo `victim/app`, with `cached_deploy_spec` configuring `blocking_statuses: ['ci/jenkins']`) and `attacker_stack` (repo `attacker/app-fork`).
2. Create a `Commit` with the same `sha` (e.g. `"deadbeef" * 5`) under both stacks (permitted by the `(sha, stack_id)` unique index), and set `victim_stack.commits` up so the shared-SHA commit is an *older* undeployed commit relative to a newer commit under test.
3. Assert baseline: `refute victim_newer_commit.blocked?` (equality check: `victim_commit_for_sha.stack_id == victim_stack.id` and no blocking status exists yet).
4. Build a `status` webhook payload with `repository.full_name = "attacker/app-fork"`, `sha` = the shared SHA, `context: "ci/jenkins"`, `state: "failure"`.
5. Call `Shipit::Webhooks::Handlers::StatusHandler.call(payload)` directly (bypassing signature verification, as permitted by the rule "no live GitHub").
6. Assert the victim's commit row (looked up via `victim_stack.commits.find_by(sha: shared_sha)`) now has a `failure` status for `ci/jenkins`, and `assert victim_newer_commit.reload.blocked?` — proving a payload addressed to `attacker/app-fork` mutated `victim_stack`'s commit/deployability state, violating the invariant that a `ci/jenkins` status should affect only the repository that authenticated it.
