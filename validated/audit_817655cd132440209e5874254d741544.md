### Title
Attacker-controlled `Task#env` overrides `GIT_ASKPASS`/`GITHUB_TOKEN` in `Command#unbundled_env` - ([File: lib/shipit/task_commands.rb], [File: lib/shipit/command.rb])

### Summary
`Api::DeploysController#create` and `Api::TasksController#trigger` accept an arbitrary `env` Hash param with no key allowlist and pass it straight through to `Stack#trigger_deploy`/`#trigger_task` as `Task#env`. `TaskCommands#env` merges `@task.env` last, after `base_env` and `deploy_spec.machine_env`, and `Command#unbundled_env` merges `@env.stringify_keys` last over `BASE_ENV`, so any client with only `deploy:stack` permission can override `GIT_ASKPASS` and `GITHUB_TOKEN` for the spawned git process.

### Finding Description
The broken binding: the question claims `key_set(Task#env as permitted) == key_set(merged into Command#unbundled_env)`, but in reality there is no permitted key set at all — `params do accepts :env, Hash, default: {} end` in both `app/controllers/shipit/api/deploys_controller.rb:12-18` and `app/controllers/shipit/api/tasks_controller.rb:17-19` accepts any Hash with no key restriction, and it is passed unfiltered:
`stack.trigger_deploy(commit, current_user, env: params.env, ...)` (`app/controllers/shipit/api/deploys_controller.rb:25`).

That value flows into `Task#env`, and `TaskCommands#env`: [1](#0-0) 
merges `base_env` (from `Commands#base_env`, which sets `GITHUB_TOKEN` and `GIT_ASKPASS`) first, then `deploy_spec.machine_env`, then `@task.env` **last**, so attacker-controlled keys win.

That merged env is passed as `env:` into `Command.new`, and `Command#unbundled_env`: [2](#0-1) 
merges `BASE_ENV` with `Shipit.shell_paths`/`PATH`, then `@env.stringify_keys` last, again letting the attacker-controlled value win. This is fed directly to `PTY.spawn(unbundled_env, *interpolated_arguments, chdir: @chdir)` at `lib/shipit/command.rb:92`.

Attack: an `ApiClient` holding only the `deploy:stack` permission (no GitHub scope, no maintainer role) calls `POST /api/stacks/:owner/:repo/:env/deploys` with body `{sha: "<valid sha>", env: {"GIT_ASKPASS": "/tmp/attacker-script", "GITHUB_TOKEN": "leaked-sentinel"}}`. `require_permission :deploy, :stack` only checks stack-level deploy permission, not env-key content, so it passes. The resulting task's git operations execute `/tmp/attacker-script` as `GIT_ASKPASS` (RCE) or use the attacker's `GITHUB_TOKEN` value, and separately the real `GITHUB_TOKEN` supplied by Shipit's GitHub App can be exfiltrated by having a malicious `GIT_ASKPASS` script print environment variables to an attacker URL, since it is invoked by git with access to the full process environment.

No existing guard filters this: `ExplicitParameters` only validates type (`Hash`) and presence, not key names; `require_permission!`/`stacks` scope only gate deploy authorization on the stack, not env variable names; there is no `EnvironmentVariables#permit`-based allowlist applied to `Task#env` before merge (that concept, if it exists elsewhere, is not applied here — `deploy_spec.machine_env`, `@stack.env`, and `@task.env` are merged with plain `Hash#merge`, no filtering).

### Impact Explanation
An authenticated but low-privileged `ApiClient` (with only `deploy:stack` scope, no special GitHub permission) can achieve remote code execution on the deploy host by controlling `GIT_ASKPASS` executed as a subprocess by git during clone/fetch/checkout operations performed by `TaskCommands`, or exfiltrate the real `GITHUB_TOKEN` set by Shipit's GitHub App integration. This is repeatable per-deploy/per-task-trigger against any stack the client has `deploy:stack` permission for, and matches the Critical severity bar (RCE via `Command`/`PTY.spawn`, exfiltration of `GITHUB_TOKEN`).

### Likelihood Explanation
Preconditions are modest: the attacker needs a valid `ApiClient` token scoped only to `deploy:stack` for the target stack (the lowest deploy-capable privilege), and the ability to send a normal deploy/task trigger API request with an `env` hash — a feature explicitly exposed by the public API. No GitHub secrets, webhook secrets, or session are required. This is fully within the documented API surface and requires no race condition or timing dependency, making it highly feasible and trivially repeatable.

### Recommendation
Introduce an explicit key allowlist/denylist for user- and spec-supplied env: reject or strip reserved keys (`GITHUB_TOKEN`, `GIT_ASKPASS`, `GITHUB_DOMAIN`, `PATH`, etc.) from `deploy_spec.machine_env` and `@task.env` before merging in `TaskCommands#env`, or reorder/re-apply `base_env` values after user-supplied env so they cannot be overridden, and validate the `env` API param against a denylist of reserved variable names in `Api::DeploysController`/`Api::TasksController`.

### Proof of Concept
Minitest plan (unit test on `TaskCommands`, no live GitHub required):
```ruby
test "task-supplied env cannot override GIT_ASKPASS or GITHUB_TOKEN" do
  task = shipit_tasks(:cyclim_deploy) # or any Task fixture
  task.env = {
    'GIT_ASKPASS' => '/tmp/attacker-script',
    'GITHUB_TOKEN' => 'leaked-sentinel'
  }

  commands = TaskCommands.new(task)
  merged_env = commands.env

  expected_askpass = Shipit::Engine.root.join('lib', 'snippets', 'git-askpass').realpath.to_s
  assert_equal expected_askpass, merged_env['GIT_ASKPASS'],
    "attacker-controlled Task#env overrode GIT_ASKPASS: got #{merged_env['GIT_ASKPASS'].inspect}"
  refute_equal 'leaked-sentinel', merged_env['GITHUB_TOKEN'],
    "attacker-controlled Task#env overrode GITHUB_TOKEN"
end
```
Given the current code, both assertions fail: `merged_env['GIT_ASKPASS']` equals `'/tmp/attacker-script'` and `merged_env['GITHUB_TOKEN']` equals `'leaked-sentinel'`, confirming the binding violation traced through `lib/shipit/task_commands.rb:46-47` and `lib/shipit/command.rb:104`.
