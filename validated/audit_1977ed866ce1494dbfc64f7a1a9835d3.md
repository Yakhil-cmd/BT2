### Title
Webhook signature verification silently bypassed for any organization without `webhook_secret` configured - ([File: lib/shipit/github_app.rb])

### Summary
`GitHubApp#verify_webhook_signature` returns `true` unconditionally when no `webhook_secret` is configured for an organization, rather than rejecting the request. Combined with `WebhooksController#verify_signature` only checking the boolean result, this allows any unauthenticated party to POST forged webhook events for that organization's repositories.

### Finding Description
The broken binding: `verify_signature`'s outcome (`verified == true`) is supposed to equal "these exact request bytes were HMAC-authenticated with the organization's `webhook_secret`." Instead, for an org with no `webhook_secret` set, `verified == true` unconditionally, regardless of what bytes or signature (or lack of signature) the request contains.

Code path:
1. `WebhooksController#verify_signature` resolves `github_app = Shipit.github(organization: repository_owner)` from the attacker-controlled `params.dig('repository', 'owner', 'login')`, then calls `github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)`. [1](#0-0) 
2. In `GitHubApp#verify_webhook_signature`, the first line is `return true unless webhook_secret`. [2](#0-1) 
3. `webhook_secret` is set from `@config[:webhook_secret].presence` in the constructor, so any organization config lacking a `webhook_secret` key (or with a blank value) makes `webhook_secret` `nil`, and verification always succeeds. [3](#0-2) 
4. `head(422) unless verified` never fires in this case, and `create` proceeds to parse `request.raw_post` as JSON and dispatch to `Shipit::Webhooks.for_event(event)` handlers with no further authentication. [4](#0-3) 

Existing guards do not close this gap: `drop_unhandled_event` only filters events with no registered handler, not authentication; `check_if_ping` only short-circuits `ping` events; `GithubOrganizationUnknown` handling only matters if the org name doesn't resolve to any configured org at all — it does not detect "org resolved but has no secret." None of these guards verify the actual authenticity of the payload bytes when `webhook_secret` is absent.

Attacker request: any unauthenticated `POST /webhooks` with `X-Github-Event: push` (or `status`, `check_suite`, `pull_request`, `membership`, etc.), a JSON body whose `repository.owner.login` names an organization that is configured in `Shipit.github_app_config` but without a `webhook_secret`, and any (or no) `X-Hub-Signature` header. The existing test suite's own webhook fixtures (e.g. `shopify` org in `test/dummy` secrets) demonstrate the mechanism, though the specific vulnerable state requires an org entry with no `webhook_secret`.

### Impact Explanation
For any organization lacking a `webhook_secret`, an attacker can forge arbitrary webhook payloads that are dispatched unauthenticated to handlers like `GithubSyncJob` enqueueing (push), `Status` creation (status), `RefreshCheckRunsJob` (check_suite), team/membership mutation (membership), and PR-related handlers — all without holding any Shipit or GitHub credential. Because `repository_owner` and other identifying fields come straight from the attacker-supplied JSON body, this also enables targeting arbitrary repositories nominally owned by that organization (subject to whatever repository-existence checks the individual handlers perform), i.e., a payload can mutate stack/commit/task/team state that the attacker never authenticated for. This is an authentication bypass matching the Critical impact category (forged webhook accepted, unauthorized state mutation for a repository/organization that never validated the request).

### Likelihood Explanation
The only precondition is a deployment-side one: the operator configures at least one entry under `Shipit.secrets.github` for a named organization without setting `webhook_secret` for it (the `webhook_secret` config key is optional per the `GitHubApp` constructor, not enforced as mandatory anywhere in this engine's code or its config loading). Given that precondition, exploitation costs nothing — no signature computation, no secret, no privileged role — and is fully repeatable for every event type registered in `Shipit::Webhooks.for_event`.

### Recommendation
In `GitHubApp#verify_webhook_signature`, fail closed instead of failing open when `webhook_secret` is blank — e.g., raise/return `false` (and ideally have `Shipit.github`/engine boot-time validation refuse to start, or log loudly, when an organization is configured with a missing `webhook_secret`), so that a misconfigured or incompletely configured organization cannot silently accept unauthenticated webhooks.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (added test)
test "org with no webhook_secret accepts forged push webhook" do
  Shipit.stubs(:github).with(organization: 'no-secret-org').returns(
    Shipit::GitHubApp.new('no-secret-org', { app_id: 1, installation_id: 1 }) # no webhook_secret key
  )

  request.headers['X-Github-Event'] = 'push'
  forged_payload = JSON.parse(payload(:push_master))
  forged_payload['repository']['owner']['login'] = 'no-secret-org'
  forged_payload['repository']['full_name'] = 'no-secret-org/victim-repo'

  # No X-Hub-Signature header at all
  assert_enqueued_with(job: GithubSyncJob) do
    post :create, body: forged_payload.to_json, as: :json
  end
  assert_response :ok # proves verified == true even though bytes were never authenticated
end
```
This demonstrates `verified == true` on the controller side while the right-hand side of the intended binding ("bytes authenticated by org's shared secret") is false — the two sides diverge, confirming the bypass.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
