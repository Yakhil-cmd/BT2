### Title
`StatusHandler#process` applies a status webhook to every `Commit` sharing a SHA, without verifying the SHA belongs to the repository that authenticated the webhook - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` looks up commits with `Commit.where(sha: params.sha)` and applies the incoming GitHub `status` payload to **every** matching `Commit` row across **every** stack in the database, regardless of which repository/organization actually sent the webhook. Unlike `PushHandler`, which scopes its lookup to `Repository.from_github_repo_name(payload.dig('repository','full_name'))` via the shared `stacks` helper, `StatusHandler` never consults the repository named in the payload. Because git SHAs are content-addressable, an attacker who owns a fork containing a commit identical (same tree/parents/author/committer/message/timestamps) to a commit already tracked by a victim stack can legitimately, correctly-signed, send a `status` webhook for their own repository and have `Status` rows injected onto the victim stack's identical-SHA `Commit`.

### Finding Description
The claimed broken binding, made explicit: `Status.stack_id == commit.stack.id` for the stack whose repository/CI actually authenticated the webhook — this equality is violated because `StatusHandler#process` resolves the target `Commit` purely by `sha`, with no repository check: [1](#0-0) 

Compare this with `PushHandler`, which correctly scopes to the repository named in the payload before touching any stack: [2](#0-1) [3](#0-2) 

`WebhooksController#verify_signature` only verifies that the request was signed with the webhook secret belonging to `Shipit.github(organization: repository_owner)`, where `repository_owner` is read straight from the attacker-controlled JSON body (`params.dig('repository','owner','login')`): [4](#0-3) [5](#0-4) 

This proves the signature check binds the request only to "some organization configured in Shipit," not to "the specific stack/commit being mutated." `Status.replicate_from_github!` then persists the row using only `stack_id` (derived from the matched `Commit#stack_id`), `state`, `description`, `target_url`, `context`, `created_at` — with no column recording which repository/app authenticated the webhook that produced it: [6](#0-5) 

**Exploit flow:** An attacker forks a victim's public repository (or otherwise reproduces byte-identical commit content), pushes it to their own repo/org where the same GitHub App/webhook is legitimately installed, and sends (or has GitHub send) a real, correctly-signed `status` event for their own repo/SHA with an arbitrary `state`/`description`/`context`. Because the SHA is identical, `Commit.where(sha: params.sha)` in the victim's Shipit instance matches the victim stack's `Commit` too (git commit SHAs are computed from content, not repository), and `commit.create_status_from_github!(params)` writes a `Status` scoped to the **victim's** `stack_id`, indistinguishable from a real status produced by the victim's own registered CI. This is `Status` on `Commit#status`/`#statuses_and_check_runs` becoming polluted with a value the victim stack's CI never emitted, matching the impact category "a payload for one repository mutating another's stack, commit."

None of the listed guards catch this: `verify_signature` validates a per-organization webhook secret but never checks that the organization owns the SHA being mutated; `drop_unhandled_event` only checks the event type is registered; the `ExplicitParameters` schema on `StatusHandler` only validates shape (`sha`, `state`, etc.), not repository scope; there is no `Repository.from_github_repo_name` check anywhere in `StatusHandler`, unlike `PushHandler`.

### Impact Explanation
An attacker can inject arbitrary CI status data (`success`/`failure`/`pending`/`error`, description, target_url, context) onto any commit in any victim stack that shares a SHA with a commit the attacker controls in their own repository. Since `Commit#status` (`app/models/shipit/commit.rb:144-146`) and downstream logic such as `Commit#add_status` trigger `deployable_status` hooks, `stack.schedule_merges`, and CI-gating for auto-merge/auto-deploy flows, a forged `success` status can unblock deploys or merge queues that should have been blocked, and a forged `failure`/`error` can block a legitimate deploy (denial of legitimate operations). This crosses stack/tenant boundaries — the attacker never had any relationship with the victim stack — matching "a payload for one repository mutating another's stack, commit" (Critical).

### Likelihood Explanation
Preconditions: the Shipit instance must track more than one stack whose commits could plausibly share a SHA with attacker-controlled content — most realistically via forks of the same public/shared upstream repository, or any deliberately duplicated commit (same tree, parents, author/committer identity and timestamps, message) pushed to a repository the attacker controls that also has the status webhook wired to the same Shipit instance. The attacker needs no Shipit secrets, session, or API token — only the ability to push commits to their own repo/fork and receive a real (correctly signed) `status` webhook for it, which is unprivileged, repeatable, and requires no interaction with the victim's infrastructure.

### Recommendation
In `StatusHandler#process`, scope the `Commit` lookup to the repository that authenticated the webhook (as `PushHandler` already does via `stacks`), e.g. `stacks.joins(:commits).merge(Commit.where(sha: params.sha))` or filter `commit.stack.repository == Repository.from_github_repo_name(repository_name)` before calling `create_status_from_github!`. Consider also recording the originating repository/app on `Status` to make forgeries auditable even if such scoping is bypassed elsewhere.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb (conceptual)
test "status handler does not mutate a commit belonging to another repository's stack" do
  victim_stack = shipit_stacks(:shipit) # tracks Repository owner/name = "shopify/shipit-engine"
  attacker_stack_repo = shipit_repositories(:some_other_repo) # owner/name = "attacker/evil-fork"

  shared_sha = "deadbeef" * 5
  victim_commit = victim_stack.commits.create!(sha: shared_sha, ...)

  payload = {
    "sha" => shared_sha,
    "state" => "success",
    "context" => "ci/attacker",
    "repository" => { "full_name" => "attacker/evil-fork", "owner" => { "login" => "attacker" } }
  }

  assert_no_difference -> { victim_commit.statuses.count } do
    Shipit::Webhooks::Handlers::StatusHandler.call(payload)
  end
end
```
Currently, running this against `StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`) FAILS: `victim_commit.statuses.count` increases by 1 even though the payload names `attacker/evil-fork`, proving the handler mutates a commit belonging to a stack it was never authenticated against.
