### Title
Cross-stack CI-state mutation via unscoped `Commit.where(sha:)` lookup - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` resolves the target commits solely by `sha`, with no filter on the `stack_id`/`repository` that the webhook's signature actually authenticates. Any commit sha shared by more than one `Stack` (e.g. two environments tracking the same repository, or a fork with common ancestry) causes a single legitimately-signed `status` webhook to write a `Status` row on every matching `Commit`, across every `Stack`, not just the one that owns the authenticated repository.

### Finding Description
The binding that should hold is: `{ stack.id for stack in Repository.from_github_repo_name(payload['repository']['full_name']).stacks }` (the set of stacks legitimately reachable from the authenticated repository) must equal `{ commit.stack_id for commit in <commits mutated by this webhook> }`.

`StatusHandler` breaks this: [1](#0-0) 
It does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` with no `stack_id`/repository constraint at all, unlike its sibling handlers which explicitly scope through `stacks` (derived from `payload['repository']['full_name']`): [2](#0-1) [3](#0-2) [4](#0-3) 

`WebhooksController#verify_signature` only proves the request came from GitHub for the organization named in the payload; it says nothing about which `Stack`/`Commit` rows the handler is allowed to touch: [5](#0-4) 

Because `Commit#sha` is not unique across stacks (`Commit belongs_to :stack`, no uniqueness scope shown), any two `Stack` rows that happen to import a commit with the same sha (e.g. two `Stack`s tracking different branches/environments of the *same* repository that share a merge-base commit, or two repositories with common git history) will both have their `Commit#create_status_from_github!` invoked and a `Status` row inserted, even though the webhook's signature only authenticates one repository's organization. `create_status_from_github!` performs a real write and side effects (`add_status` emits `Hook.emit`, schedules merges, etc.): [6](#0-5) [7](#0-6) 

None of the guards listed in the audit rules (`verify_signature`, `drop_unhandled_event`, `ExplicitParameters` schema, model validations) restrict the query to the authenticated repository's stacks — they only validate the payload shape and the HMAC of the sending organization, not the scope of the resulting `ActiveRecord` query.

### Impact Explanation
A single, real, correctly-signed `status` webhook for a repository/organization the attacker legitimately controls (e.g. their own fork, or a second environment/branch of a tracked repo sharing a common commit) causes `Status` rows to be created for `Commit` rows belonging to **every** `Stack` that has ever recorded that sha — including stacks belonging to unrelated tenants/repositories if the sha collision spans repositories. This is a write to another repository's `Stack`/`Commit` state that did not authenticate that mutation, matching the "payload for one repository mutating another's stack, commit... " Critical category. Because `create_status_from_github!` participates in `deployable?`/`schedule_continuous_delivery`, forging a `success` status on a shared sha can flip a foreign stack's commit into a deployable state, potentially triggering continuous deployment on a stack the attacker never authenticated against.

### Likelihood Explanation
The attacker needs the ability to make GitHub deliver one legitimately-signed `status` event for a repository/org it operates (trivial: push a commit and post a commit status via the GitHub API or Actions on their own repo/fork). The only non-trivial precondition is a *sha collision* across stacks, which is not exotic in Shipit's normal usage: multiple `Stack` rows commonly track the same underlying repository (e.g. staging/production, or repository forks with shared history), so shared ancestor commit shas across `Stack` boundaries are an expected and common condition, not a hash-collision-style stretch. No secrets, sessions, or elevated roles are required beyond ordinary control of a tracked repository/fork.

### Recommendation
Scope `StatusHandler#process` the same way `PushHandler`/`CheckSuiteHandler` do: resolve `stacks` from `payload['repository']['full_name']` and restrict the commit lookup to `stacks.flat_map(&:commits).where(sha: params.sha)` (or `Commit.where(sha: params.sha, stack_id: stacks.select(:id))`) instead of the unscoped `Commit.where(sha: params.sha)`.

### Proof of Concept
Minitest plan (in `test/models/shipit/webhooks/handlers/status_handler_test.rb` or `test/controllers/webhooks_controller_test.rb`, following existing patterns):
1. Fixtures: `stack_a` and `stack_b` (different repositories/full_names), each with a `Commit` fixture using the identical `sha` value, e.g. `shipit_commits(:first)` (stack A) and a new fixture `shipit_commits(:shared_sha_other_stack)` with `stack_id: stack_b.id`, `sha: shipit_commits(:first).sha`.
2. POST a `status` webhook whose `repository.full_name` matches `stack_a`'s repository (with a valid/stubbed signature as in the existing test `":state create a Status for the specific commit"`).
3. Assert: `assert_difference 'shipit_commits(:first).statuses.count', 1` (expected, stack A is authenticated) **and** `assert_difference 'shipit_commits(:shared_sha_other_stack).statuses.count', 1` (unexpected — proves stack B, whose repository never authenticated this webhook, was mutated).
4. The binding check: assert that `commit.stack_id` for every newly created `Status`'s commit is `== stack_a.id`; the test should fail today because a `Status` is also created for `stack_b`'s commit, proving the touched-stack set is unbounded (`> 1`) rather than the required `1`.

      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
