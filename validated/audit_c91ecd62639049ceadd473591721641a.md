### Title

Unrestricted swap routes can graft unrelated token transfers into the caller’s authorization tree - ([File: contracts/controller/src/strategies/swap.rs](contracts/controller/src/strategies/swap.rs))

### Summary

The controller lets user-supplied `swap` bytes drive arbitrary nested contract calls while the position owner is the authorized root caller. A malicious route can include a venue that invokes `token.transfer(victim, attacker, amount)`, causing transaction simulation to add that unrelated wallet transfer beneath the user’s `swap_collateral` authorization. If the crafted request is signed, the attacker receives tokens unrelated to the lending operation.

### Finding Description

`Controller::swap_collateral` accepts caller-controlled `swap: Bytes` and forwards it to `process_swap_collateral`. [1](#0-0)  That function authenticates the caller and verifies account ownership before executing the supplied strategy. [2](#0-1)  The strategy eventually calls `router.execute_strategy` with the uninterpreted swap payload. [3](#0-2) 

The controller restricts the router’s direct pull to `amount_in`, but it does not restrict which contracts the route invokes while the caller’s authorization context is active. [3](#0-2)  A rogue venue can therefore request `victim.require_auth()` for an unrelated token transfer, which the host binds to the user’s root authorization. The repository’s regression test demonstrates that simulation records such a transfer as a child of `swap_collateral` and that signing the poisoned tree moves the victim’s wallet tokens to the attacker. [4](#0-3) 

### Impact Explanation

This enables theft of arbitrary spendable tokens held by the victim, independent of the collateral being swapped. The attacker only needs the victim to sign a simulated authorization tree containing the injected child call; the test confirms the victim’s wallet balance becomes zero while the attacker receives the full amount. [5](#0-4) 

### Likelihood Explanation

The attack requires user interaction because the injected transfer must appear in the signed authorization tree. That is consistent with the crafted-page bug class: a malicious interface or route can generate a seemingly legitimate `swap_collateral` request whose simulated authorization includes an unrelated transfer. The regression test shows enforced authorization rejects the rogue transfer when it is absent from the signed tree but executes it when included. [6](#0-5) 

### Recommendation

Do not permit user-controlled routes to execute arbitrary, unallowlisted venue contracts during an operation rooted in the account owner’s authorization. Restrict routes to a governance-managed venue allowlist, or execute swaps through a trusted router that cannot make arbitrary nested calls with externally supplied addresses. Wallets and frontends should additionally warn when an operation’s authorization tree contains token transfers unrelated to the declared swap input and output.

### Proof of Concept

1. Victim owns a funded lending account and an unrelated wallet token.
2. Attacker deploys a venue whose `swap()` function invokes `Token.transfer(victim, attacker, victim_balance)`.
3. Attacker crafts `swap` bytes that route through that venue while still returning enough `token_out` to satisfy the controller’s positive-output check.
4. Victim submits `swap_collateral(caller=victim, account_id, current, amount, new, swap)`.
5. During simulation, the rogue transfer is recorded as a child of the caller’s `swap_collateral` authorization. [7](#0-6) 
6. If the victim signs the generated tree, the unrelated wallet token is transferred to the attacker while the collateral swap completes normally. [8](#0-7)
