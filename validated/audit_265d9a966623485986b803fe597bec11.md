### Title
Hardcoded `bAllowUnresolvedInnerDefinitions = true` bypasses address-definition validation in nested `address` conditions - ([File: definition.js])

### Summary
`definition.js`'s `validateDefinition()` evaluates address-definition/authentifier trees, including the `address` op which references another address by chash (`['address', other_address]`). When the referenced address's definition cannot be resolved from storage, the code is supposed to gate acceptance behind an explicit `bAllowUnresolvedInnerDefinitions` flag passed via `objValidationState`, but that gate has been hardcoded to `true` unconditionally, exactly mirroring the Xinference bug class where a `trust_remote_code` flag that should be conditional was hardcoded to `True` at the call site.

### Finding Description
In the `evaluate()` closure inside `validateDefinition()`, the `case 'address':` branch resolves nested address references: [1](#0-0) 

The comment and dead code make the regression explicit:
```
ifDefinitionNotFound: function(definition_chash){
//	if (objValidationState.bAllowUnresolvedInnerDefinitions)
//		return cb(null, true);
var bAllowUnresolvedInnerDefinitions = true;
```
The intended logic — only tolerate an unresolved inner definition when the caller explicitly opts in via `objValidationState.bAllowUnresolvedInnerDefinitions` — has been replaced by a local variable hardcoded to `true`, discarding the caller-supplied flag entirely. This is structurally identical to the Xinference issue: multiple call sites hardcode a security-relevant boolean to the permissive value instead of reading it from configuration/caller-supplied state, removing the intended trust gate.

The consequence: if no co-author in the *same unit* supplies a matching `author.definition` that hashes to `definition_chash` (`arrDefiningAuthors.length === 0`), the branch still returns `cb(null, true)` — i.e., the `['address', other_address]` condition is treated as satisfied — instead of returning an error ("definition of inner address ... not found"). This removes the intended requirement that a definition referencing another (unwitnessed) address can only be considered valid if that address's definition is actually known/resolvable, regardless of what the original caller (`objValidationState.bAllowUnresolvedInnerDefinitions`) intended.

### Impact Explanation
`validateDefinition` is the authoritative check used to validate a spending-condition/address-definition tree (for AA definitions, asset conditions, address-definition-change payloads, and address-definition templates in wallets). An `address` condition (`['address', 'SOME_ADDRESS']`) is meant to require that the definition of `SOME_ADDRESS` be resolvable and satisfied recursively when depth requires re-evaluation (`needToEvaluateNestedAddress`). With the hardcoded bypass, an attacker constructing a definition containing an `['address', X]` sub-condition — where `X` is any syntactically valid address that has no known/resolved definition and is not co-authoring the unit — can get this branch accepted as `true` unconditionally at definition-validation time. Depending on which code path (`needToEvaluateNestedAddress`) drives whether the nested definition is actually evaluated for authentifier purposes, this can allow constructing address definitions/asset conditions that appear well-formed and syntactically valid but do not enforce the real ownership/signature requirement of the referenced address, undermining the guarantee that `each branch must have a signature` enforced elsewhere in the same function. This can enable spending-condition or AA-definition trees to pass validation while omitting a real signature requirement tied to `X`, a validation-bypass class of bug (potential for unauthorized/under-authorized spending conditions and node disagreement about whether such definitions are valid).

### Likelihood Explanation
Any unprivileged unit poster, AA/asset definer, or shared-address definer can trigger this code path simply by constructing a definition tree with an `address` condition pointing to an address whose definition is not attached/known. No special privileges are required — `validateDefinition` is invoked over the address/asset/AA definitions supplied directly by ordinary users in unit payloads (`definition`, asset conditions, `address_definition_change`) and processed unconditionally by every full node during unit validation.

### Recommendation
Restore the intended gating logic: only allow `cb(null, true)` for an unresolved inner definition when `objValidationState.bAllowUnresolvedInnerDefinitions` is explicitly `true` (as originally commented), otherwise return the error `"definition of inner address " + other_address + " not found"`. Audit all callers of `validateDefinition`/`validateAuthentifiers` to confirm which legitimately need `bAllowUnresolvedInnerDefinitions: true` (e.g., local wallet-side pre-checks in `wallet_defined_by_addresses.js`) versus real consensus-critical unit validation, which should never silently accept unresolved nested addresses.

### Proof of Concept
Not independently reproducible from static analysis alone with full certainty of end-to-end exploitability (would require confirming, at runtime, whether `needToEvaluateNestedAddress(path)` causes this branch to actually gate a signature requirement for typical AA/asset/address-definition submissions, and whether any downstream consumer relies on `bAllowUnresolvedInnerDefinitions` being `false` during real consensus validation). Conceptually:
1. Craft an address/AA definition or asset condition containing `['and', [['address', 'SOME_UNRELATED_ADDRESS'], ['sig', {...}]]]` where `SOME_UNRELATED_ADDRESS` has no on-chain definition and does not co-author the unit.
2. Submit it as an AA definition, asset condition, or `address_definition_change` payload.
3. Because of the hardcoded `bAllowUnresolvedInnerDefinitions = true`, the `address` branch returns `true` even though the address's definition can't be verified, letting the composite condition validate more permissively than intended.
