## Analysis

The free5GC advisory describes a crafted API request reaching an assertion/panic that was not properly guarded, crashing the service (CWE-617, Reachable Assertion → DoS). The closest analog in `ocore` is an unguarded `throw` inside a raw DB-callback in the private-payment handling path, reachable by any private-payment counterparty (wallet peer) without requiring any special privilege.

### Title
Reachable assertion crash via duplicate/overlapping divisible private payment message - (File: private_payment.js)

### Summary
`validateAndSavePrivatePaymentChain()` in `private_payment.js` performs a duplicate-detection query before persisting a received private payment, but the query is not properly scoped for divisible (non-fixed-denomination) assets, so it can legitimately return more than one row. When that happens the code executes an unguarded `throw Error(...)` inside a DB callback instead of returning an error to the caller, crashing the node process.

### Finding Description
`validateAndSavePrivatePaymentChain` builds a lookup query to check whether the incoming private output was already stored: [1](#0-0) 
For a divisible (non-`fixed_denominations`) private asset, the query filters only by `unit, asset, message_index` — it does **not** filter by `output_index`, because divisible payments legitimately store multiple output rows (e.g. a payment output plus a change output) under the same `unit/message_index`: [2](#0-1) 
Those multiple output rows are exactly what gets written the first time such a payment is saved, in `validateAndSaveDivisiblePrivatePayment` in `divisible_asset.js`, which inserts one row per output of the payload in a single loop: [3](#0-2) 
Consequently, as soon as a divisible private payment with 2+ outputs for the same `message_index` has been saved once, any subsequent inbound private-payment message referencing the same `(unit, asset, message_index)` (even legitimately re-sent, replayed, or slightly modified so it evades the in-memory `handledChainsCache` hash dedup) will make the duplicate-check query return more than one row: [4](#0-3) 
This hits the unconditional `throw Error("more than one output "...)`, which occurs inside a `db.query` callback with no surrounding `try/catch`, and is not one of the callback-based error paths (`ifError`/`ifOk`) that the rest of the module uses consistently everywhere else. An uncaught exception thrown from an asynchronous callback in Node.js crashes the process (unless a generic `process.on('uncaughtException')` handler exists, which does not prevent the in-flight DB transaction/connection from being abandoned in a bad state).

This code path is reached from `handleOnlinePrivatePayment` in `network.js`, called for private payments delivered over the network/hub: [5](#0-4) 
and from `handlePrivatePaymentChains` in `wallet.js`, which is the device-message handler for `private_payments` messages sent by any paired/private-payment counterparty: [6](#0-5) [7](#0-6) 
Neither entry point requires the sender to be a privileged party — only that they are a private-payment counterparty (or hub relaying such messages), matching the required threat model of an "unprivileged... private-payment counterparty."

### Impact Explanation
A crafted or replayed private-payment message causes an uncaught JS exception in the unit/message processing pipeline, crashing the receiving node/wallet process — the network becomes unable to process further units/messages until restarted, which matches the required "network unable to confirm new units" / node-crash impact bar for this analog.

### Likelihood Explanation
Any two-output divisible private payment (a very common real-world case: payment + change output) creates the necessary preconditions automatically. An attacker who is (or has previously been) a counterparty to such a payment can trivially resend a private-payment message for the same `unit/message_index` — with any cosmetic difference to defeat the `handledChainsCache` hash-based short-circuit — to trigger the crash reliably and repeatedly.

### Recommendation
Replace the unconditional `throw Error(...)` at `private_payment.js:74-75` with a normal error callback (`transaction_callbacks.ifError(...)`) so malformed/duplicate input is rejected gracefully instead of crashing the process. Additionally, scope the duplicate-detection query for divisible assets more precisely (e.g., compare against the full set of expected outputs) instead of relying on `rows.length <= 1` as an implicit invariant.

### Proof of Concept
1. Complete a normal divisible private-asset payment with at least two outputs in the same message (e.g., payment to recipient + change back to sender) so that `outputs` table has 2 rows for `(unit, asset, message_index)`.
2. As the recipient (or any private-payment counterparty), send a new `private_payments` device message (or online private payment via hub) referencing the same `unit`, `asset`, and `message_index`, with payload content altered slightly enough to change `objectHash.getBase64Hash(arrChains)` (bypassing `handledChainsCache`).
3. The victim node executes the duplicate-check `SELECT ... FROM outputs WHERE unit=? AND asset=? AND message_index=?`, which returns 2 rows, hitting `throw Error("more than one output ...")` inside the DB callback and crashing the process.
