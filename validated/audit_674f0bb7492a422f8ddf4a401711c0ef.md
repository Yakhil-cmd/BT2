### Title
Webhook signature verification authenticates the payload's `repository.owner.login`/`organization.login`, but handlers act on the independently-supplied `repository.full_name`, allowing cross-organization repository writes - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret to validate the HMAC signature against using `repository_owner`, computed from `params.dig('repository', 'owner', 'login')` (or `organization.login`). Once the signature is verified, the entire raw JSON payload — including a separately-controlled `repository.full_name` field — is handed unmodified to `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`. Handlers (e.g. `PushHandler`, via `Handler#repository_name`) resolve the target `Repository`/`Stack` using `payload.dig('repository', 'full_name')`, a completely different JSON field than the one used for authentication.

### Finding Description
`verify_webhook_signature` in `lib/shipit/github_app.rb` only proves that the raw request body was HMAC-signed by *some* configured organization's `webhook_secret` — it says nothing about which repository record the payload's other fields should be trusted to reference: [1](#0-0) [2](#0-1) [3](#0-2) 

The authenticated field (`repository.owner.login` / `organization.login`) is never cross-checked against the field the downstream handlers actually use to resolve state (`repository.full_name`): [4](#0-3) [5](#0-4) 

Because Shipit supports multiple configured GitHub organizations, each with its own `webhook_secret` (`Shipit.github(organization:)` / `github_app_config`), a webhook delivered and correctly signed by organization A's app installation (e.g. following a legitimate push in a repo under org A) can carry a JSON body where `repository.full_name` names a repository belonging to org B, as long as `repository.owner.login`/`organization.login` (used purely for secret selection) still resolves to org A's config: [6](#0-5) 

This is directly analogous to the Pendle finding: a value used to compute/verify a guarantee (`minPtOut` bound to the swap call vs. the actual amount transferred) is decoupled from the parameter that is actually acted upon. Here, the field verified by the signature (owner/organization) is decoupled from the field acted upon by the handler (repository full name).

### Impact Explanation
If exploitable, this would enable an attacker who controls (or compromises) a GitHub App installation/webhook delivery for one onboarded organization to forge webhook events (e.g. `push`, `status`) that Shipit will process as if they originated from a *different* organization's repository — e.g. triggering `GithubSyncJob` (`PushHandler#process` → `stack.sync_github`) or fabricating commit statuses (`StatusHandler#process` → `commit.create_status_from_github!`) for a stack that belongs to a repository the attacker does not control. This crosses the "cross-repository writes" / "unauthorized deploy" boundary defined as Critical impact.

### Likelihood Explanation
Exploitation requires the attacker to already control a legitimate, correctly-configured GitHub App webhook delivery channel for at least one organization onboarded to the same Shipit instance (i.e., ability to get GitHub to deliver an event, or control of that org's repository to trigger a push/status event with an attacker-influenced `full_name`-independent owner field). In the common single-organization Shipit deployment (`github_default_organization.nil?`) there is only one webhook secret, so this scenario collapses to a non-issue. The realistic exposure is limited to multi-organization deployments (`Using Multiple Github Applications` in `docs/setup.md`) and to fields of the payload GitHub itself would populate consistently, which limits practical likelihood — GitHub does not let an arbitrary sender freely mismatch `repository.owner.login` and `repository.full_name` in a naturally generated event. I could not find code in-scope that would let an unprivileged, credential-less external actor directly cause GitHub to emit such a mismatched, validly-signed payload.

### Recommendation
Cross-validate that the organization used to select/verify the webhook signature (`repository.owner.login` / `organization.login`) matches the owner segment of `repository.full_name` before dispatching to handlers, rejecting the request (422) on mismatch, so the same field that is cryptographically authenticated is the one used to resolve which `Repository`/`Stack` records are mutated.

### Proof of Concept
Conceptual (not confirmed exploitable without a genuine multi-org GitHub delivery mismatch):
1. Shipit is configured with two organizations, `org-a` and `org-b`, each with its own `webhook_secret` (per `docs/setup.md` "Using Multiple Github Applications").
2. A webhook delivery is correctly HMAC-signed with `org-a`'s `webhook_secret`, and its JSON body has `repository.owner.login == "org-a"` (satisfying `verify_signature`) but `repository.full_name == "org-b/some-repo"`.
3. `WebhooksController#create` parses the body and dispatches to `PushHandler`, which resolves the target repository purely from `full_name` via `Repository.from_github_repo_name`, causing a sync/deploy action against `org-b`'s stack despite the request being authenticated only for `org-a`.     def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
