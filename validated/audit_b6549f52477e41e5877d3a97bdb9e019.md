### Title
Webhook signature verification is bypassed when `webhook_secret` is unset, allowing forged `membership` events to grant unauthorized `Shipit.github_teams` access - ([File: lib/shipit/github_app.rb])

### Summary
`GitHubApp#verify_webhook_signature` fails open: when no `webhook_secret` is configured for a GitHub organization, it returns `true` unconditionally, treating every unsigned request as if it originated from GitHub. This lets an unprivileged attacker send a forged `membership` webhook that creates `Team`/`Membership` records, which are the exact records `User#authorized?` consults to grant access to `Shipit.github_teams`-restricted stacks — an authentication-bypass-class escalation into the app's team authorization.

### Finding Description
`WebhooksController#verify_signature` is the only gate before any webhook payload is dispatched to handlers: [1](#0-0) 

It delegates trust decisions entirely to `GitHubApp#verify_webhook_signature`: [2](#0-1) 

The first line, `return true unless webhook_secret`, means that for any organization configured **without** a `webhook_secret` — which is the documented/default state in the sample secrets file (`webhook_secret: # nil`) — signature verification is entirely skipped and *every* unsigned payload is accepted as authentic: [3](#0-2) 

The setup docs likewise describe `webhook_secret` as an optional field to fill in only "if you've set a webhook secret during the App creation": [4](#0-3) 

This breaks the trust binding the engine is supposed to enforce: **organization authenticated by the verified GitHub signature == organization/team data the webhook handlers are allowed to write**. When `webhook_secret` is absent, that equality collapses — the "authenticated" side is vacuous (`true` for anyone), while the "written" side (Team/Membership rows) remains fully live.

Once past `verify_signature`, the `membership` event is routed to `Shipit::Webhooks::Handlers::MembershipHandler` via the handler registry: [5](#0-4) 

The existing test suite demonstrates the handler creates a `Team` record and appends arbitrary `User` logins to it directly from attacker-controlled payload fields (`team.id`, `team.slug`, `member.login`), with no further authorization check: [6](#0-5) 

`Team#add_member` simply appends the given member with no cross-check against real GitHub org membership: [7](#0-6) 

Finally, `User#authorized?` — the single gate that `Authentication#force_github_authentication` uses to allow access — is computed purely from local `Membership` rows matching `Shipit.github_teams`: [8](#0-7) [9](#0-8) 

So an attacker who forges a `membership` webhook (with a `slug`/`organization` matching one of `Shipit.github_teams`, and their own already-registered GitHub login as `member`) can insert themselves into that `Team`, satisfying `authorized?` and gaining access to restricted stacks/deploys without ever being a real member of the GitHub organization or team.

### Impact Explanation
This is an escalation into `Shipit.github_teams` authorization — explicitly one of the defined High-impact categories. An attacker with no privileged credentials (no GitHub org membership, no Shipit session) forges a webhook and gains authorized access to the application by manipulating the local authorization records that back `User#authorized?`.

### Likelihood Explanation
Likelihood depends on the organization's config having no `webhook_secret` set, which is the state shown by the shipped example config and treated as an acceptable/optional setting by the docs, not a hardening requirement. No credentials are required — only knowledge of the `X-Github-Event: membership` webhook shape and the target organization/team slugs, which are unauthenticated engine implementation details, not secrets.

### Recommendation
Make `verify_webhook_signature` fail closed: if `webhook_secret` is blank, reject the webhook (return `false`) instead of implicitly trusting it, and/or require `webhook_secret` to be present as part of GitHub organization configuration validation. Additionally, `MembershipHandler`/`Team#add_member` should not be able to grant `Shipit.github_teams`-equivalent access purely from webhook payload data without corroborating it against a live GitHub API call.

### Proof of Concept
1. Target a Shipit deployment where an organization entry in `config/secrets.yml` has no `webhook_secret` (matches the documented example configuration).
2. Attacker sends a POST to `/webhooks` with header `X-Github-Event: membership` and a JSON body:
```json
{
  "action": "added",
  "team": { "id": 1, "name": "Ops", "slug": "ops", "url": "https://example.com" },
  "organization": { "login": "target-org" },
  "member": { "login": "attacker-github-login" }
}
```
No `X-Hub-Signature` header is required.
3. `WebhooksController#verify_signature` calls `Shipit.github(organization: "target-org").verify_webhook_signature(nil, raw_body)`, which returns `true` because `webhook_secret` is blank [10](#0-9) .
4. `MembershipHandler` processes the forged payload, creating/finding `Team(organization: "target-org", slug: "ops")` and adding a `User` with login `attacker-github-login` as a member.
5. If `attacker-github-login` corresponds to a `Shipit::User` who can complete OAuth login (even without real org/team membership on GitHub), `authorized?` now returns `true` for the `ops` team match, granting access to any stack gated by `Shipit.github_teams` including `["target-org/ops"]`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
