### Title
Cross-repository status forgery — `StatusHandler#process` applies GitHub status webhooks to any commit sharing the SHA, regardless of which repository sent the webhook - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` looks up commits solely by `sha` (`Commit.where(sha: params.sha)`) and never checks that the reporting `repository` in the webhook payload actually owns that commit. Since Shipit's `Handler` base class already provides a `stacks`/`repository_name` scoping mechanism that every other handler uses, `StatusHandler` is the outlier that breaks the "status came from CI that ran against this commit's repo" binding.

### Finding Description
The binding that should hold is: `status.repository == commit.stack.repository` (the CI status for a SHA must originate from the same repository whose CI produced it). Instead, the code is: [1](#0-0) 

This ignores `payload['repository']` entirely and matches on `sha` across the whole `commits` table, unlike the `Handler` base class's `stacks`/`repository_name` helpers used by other handlers: [2](#0-1) 

`WebhooksController#verify_signature` only validates that the payload was signed by the GitHub App/organization named in `payload['repository']['owner']['login']` (or `organization.login`) — it authenticates *who sent the webhook*, not *which commit the status applies to*: [3](#0-2) 

Git commit SHAs are content-derived and identical across a repository and any of its forks for shared history. An attacker who forks a victim's public repository (or otherwise creates a repository sharing history/SHAs with the victim, e.g. via `git push` of the same objects) legitimately owns that fork, can configure a CI/status app on it that always reports `success`, and GitHub will sign the resulting `status` webhook with a secret valid for the attacker's own organization/installation — passing `verify_signature` legitimately. When Shipit receives this webhook, `StatusHandler.process` finds `Commit.where(sha: <shared-sha>)`, which returns the **victim's** `Commit` record(s) belonging to the victim's `Stack` (if that commit was previously ingested via the victim's own `push` webhooks), and calls `commit.create_status_from_github!(params)` on it — writing a forged "success" status onto the victim's commit.

Once a `success` status lands on the victim's commit, `Commit#deployable?` (`!locked? && (stack.ignore_ci? || (success? && !blocked?))`) can become true, and if the victim stack has `continuous_deployment: true`, `Commit#schedule_continuous_delivery` enqueues `ContinuousDeliveryJob`, which can trigger an actual deploy of that commit. Independently of continuous deployment, the dashboard's deploy affordances (`deploy_button`/`redeploy_button` helpers, driven by `UndeployedCommit#expected_to_be_deployed?`) will show the commit as deployable/allowed for a human operator to click.

None of the existing guards prevent this: `verify_signature` authenticates the sender's organization, not the target commit/stack; `ExplicitParameters` only validates the shape of `sha`/`state`/etc., not repository ownership; and `Handler#stacks`/`repository_name` scoping (which would fix this) is simply not used by `StatusHandler`.

### Impact Explanation
An attacker who controls any repository sharing commit SHAs with a victim (trivially achievable via a public fork) can inject arbitrary CI status (`success`/`failure`/`error`) onto commits belonging to a victim's Shipit stack that they do not own or administer. This is a payload for one repository mutating another repository's commit/stack state — matching the Critical category "a payload for one repository mutating another's stack, commit, task or team" and can lead to an unauthorized deploy when combined with `continuous_deployment: true`, or to blocking/breaking a victim's legitimate deploy pipeline by forging `failure`/`error` statuses. The attack is repeatable against any stack in the Shipit instance whose commits happen to share a SHA with a repository the attacker controls (forks being the primary vector), so it is not limited to a single victim and represents a cross-tenant blast radius.

### Likelihood Explanation
Preconditions: the victim's repository must be forkable/public (typical), the victim stack must have ingested the shared commit (via its own push webhook — normal operation for any active stack tracking that branch/history), and the attacker needs only to own a fork and configure any status-reporting integration (or, since they own the target repo, directly control what statuses get generated for it). No Shipit credentials, session, API token, or GitHub org membership are required — only the ability to fork a public repo and receive/send GitHub status webhooks for it, which is available to any unprivileged GitHub user. This is low-cost and repeatable.

### Recommendation
Scope `StatusHandler#process` the same way other handlers scope events: resolve the target `stacks`/repository via `payload.dig('repository', 'full_name')` (using the existing `Handler#stacks` helper) and only update commits belonging to that repository's stacks, e.g. `stacks.each { |stack| stack.commits.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) } }`, instead of the global `Commit.where(sha: params.sha)`.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb`, illustrative — actual file is out of scope per rules but describes the assertions):
1. Create `stack_victim` for repository `victim/repo` and `stack_attacker` for repository `attacker/fork`.
2. Create `commit = stack_victim.commits.create!(sha: 'deadbeef' * 5 ...)` with no passing status (`commit.deployable?` == `false`).
3. Build a `status` webhook payload with `repository.full_name = 'attacker/fork'`, `sha` equal to `commit.sha`, `state = 'success'`.
4. Call `Shipit::Webhooks::Handlers::StatusHandler.call(payload)` directly (bypassing signature verification, which is orthogonal — it only authenticates `attacker/fork`, not the target commit).
5. Assert: before, `commit.reload.deployable?` is `false`; after, `commit.reload.deployable?` is `true`, demonstrating the victim commit's status was set by a payload declaring a different repository (`attacker/fork` != `victim/repo`), proving the broken binding `status.repository == commit.stack.repository`.
