### Title
Signature verification keyed on `repository.owner.login` while all webhook handlers act on the unrelated `repository.full_name` field, allowing cross-organization webhook forgery - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to HMAC-verify a webhook against using `repository_owner`, derived from `params.dig('repository', 'owner', 'login')` (or `organization.login`) [1](#0-0) . Every event handler, however, resolves the actual `Repository`/`Stack` to act on using a completely different field of the same JSON body: `payload.dig('repository', 'full_name')` [2](#0-1) , and this pattern repeats in `OpenedHandler`, `ClosedHandler`, `EditedHandler`, etc., which all call `Shipit::Repository.from_github_repo_name(params.repository.full_name)` [3](#0-2) [4](#0-3) .

### Finding Description
In a multi-organization Shipit deployment (the engine explicitly supports configuring several GitHub Apps, one per organization, via `Shipit.github(organization:)` / `github_app_config` [5](#0-4) ), each organization has its own `webhook_secret`. `verify_signature` picks the secret to check the `X-Hub-Signature` against solely from `repository.owner.login` (or `organization.login`) in the *unauthenticated* JSON body, then HMACs the *entire raw body* with that secret [6](#0-5) .

Because the HMAC only proves "whoever holds Org X's `webhook_secret` produced this exact byte stream," and the byte stream is attacker-composed JSON, an attacker who is a legitimate installer/administrator of GitHub App for **Org A** (and therefore legitimately knows Org A's own `webhook_secret` for their own repositories) can craft a payload where:
- `repository.owner.login` = `"OrgA"` (used only to pick which secret verifies the signature)
- `repository.full_name` = `"OrgB/target-repo"` (used by every downstream handler to resolve the `Repository`/`Stack` to mutate)

Real GitHub webhooks always keep these fields consistent, but nothing in `verify_signature` or in `Handler#repository_name` cross-checks that `repository.owner.login` matches the owner prefix of `repository.full_name`. The signature check only binds the raw bytes to "some HMAC-holder," not to the specific organization named in `full_name` that the handlers actually act on. This breaks the intended binding: *organization that authenticated ≠ repository that is written*.

### Impact Explanation
If Shipit hosts stacks/repositories for multiple organizations (as documented and directly supported via `config/secrets*.yml`'s `github:` multi-org schema [7](#0-6) ), an attacker who controls (or is an admin of) only one weakly-trusted organization's GitHub App installation can forge webhook events that are accepted as authentic for a *different, unrelated* organization's repository. This lets them:
- Trigger `GithubSyncJob`/`sync_github` and downstream deploy-eligibility logic on stacks belonging to Org B via `PushHandler#process` → `stack.sync_github` [8](#0-7) .
- Fabricate/close/edit pull-request state and provisioning of review stacks for Org B's repositories through `OpenedHandler`, `ClosedHandler`, `EditedHandler`, etc. [9](#0-8) [10](#0-9) .

This is a cross-repository/cross-organization write performed with a credential the attacker legitimately possesses only for a different, unrelated tenant — matching the Critical "cross-repository writes" impact category.

### Likelihood Explanation
Requires: (1) a Shipit deployment configured with more than one GitHub organization/App (explicitly documented as a supported configuration), and (2) the attacker administering or having leaked access to one of those orgs' installed GitHub Apps (their own webhook secret, not the victim org's). Given multi-tenant Shipit installs are a documented, intended configuration, and organization admins/CI systems are a broader trust surface than the Shipit deployment itself, this is a realistic scenario for any shared/multi-org Shipit instance.

### Recommendation
After signature verification succeeds, re-derive the organization/owner strictly from the same field used for repository resolution (`repository.full_name`'s owner segment, or `repository.owner.login`) and reject the webhook (422) if the owner used to select the `webhook_secret` does not match the owner encoded in `repository.full_name`. Alternatively, verify the signature using the owner parsed out of `repository.full_name` instead of the separate `repository.owner.login` field, so a single field is both authenticated and acted upon.

### Proof of Concept
1. Shipit is configured with two orgs, `OrgA` and `OrgB`, each with its own `webhook_secret` (per `docs/setup.md`'s "Using Multiple Github Applications" section).
2. Attacker is an admin of `OrgA`'s installed GitHub App and knows `OrgA`'s `webhook_secret`.
3. Attacker POSTs to `/webhooks` with `X-Github-Event: push` and a JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>",
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/target-repo" }
}
```
4. `WebhooksController#verify_signature` computes `repository_owner` = `"OrgA"`, loads `Shipit.github(organization: 'OrgA')`, and verifies the HMAC signature the attacker computed with the known `OrgA` secret — it succeeds [11](#0-10) .
5. `PushHandler#process` runs `stacks` → `Handler#repository_name` returns `"OrgB/target-repo"` → `Repository.from_github_repo_name` resolves Org B's actual repository, and `stack.sync_github` is invoked on it [2](#0-1) [8](#0-7) , despite the attacker never having any credential tied to Org B.

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

### Using Multiple Github Applications

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently. The top-level keys should be the name of each Github organization, and the following sub-keys are the Github app details for that particular organization.

    someothergithuborg:

      installation_id:
      webhook_secret:

        id:
