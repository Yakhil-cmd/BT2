### Title
AA trigger identity (`trigger.address`) is bound to the lexicographically-first unit author, not to the address that actually funded the payment, letting a co-signer of a multi-authored trigger misappropriate another author's deposit — ([File: aa_composer.js])

### Summary
`getTrigger()` derives the identity that an Autonomous Agent (AA) uses to attribute/credit an incoming payment (`trigger.address`) from `objUnit.authors[0].address` — the alphabetically smallest author of the *trigger unit* — while `trigger.outputs` is computed by summing **all** payment outputs addressed to the AA regardless of which author's inputs actually funded them. When a trigger unit is multi-authored (a supported, validated feature of ocore), the party whose signature happens to sort first is credited with funds that another co-signing author actually paid, exactly mirroring the reported bug class where a state/"balance" record keyed on one identity (`msg.sender`) is updated while the actual assets moved belong to a different identity (`owner`).

### Finding Description
`getTrigger()` sets:
```
var trigger = { address: objUnit.authors[0].address, unit: objUnit.unit, outputs: {} };
``` [1](#0-0) 

`objUnit.authors[0]` is not "the author who paid" — it is simply the first entry after author addresses are sorted ascending, a rule enforced independently in `validateAuthors`:
```
for (var i=0; i<arrAuthors.length; i++){
    var objAuthor = arrAuthors[i];
    if (objAuthor.address <= prev_address)
        return callback("author addresses not sorted");
    prev_address = objAuthor.address;
}
``` [2](#0-1) 

Nothing in unit/AA-trigger validation restricts a primary AA trigger to a single author, nor ties `trigger.address` to the address whose output(s) fund the payment to the AA. `validateAATrigger` only checks that at most one AA address receives outputs and (post-upgrade) at most one output per asset to that AA — it does not inspect which author owns the spent inputs:
```
for (let o of m.payload.outputs) {
    if (!outputCounts[o.address]) outputCounts[o.address] = {};
    ...
}
``` [3](#0-2) 

Meanwhile `getTrigger`'s output-summation loop aggregates the payment purely by destination address, ignoring the source/owner address of the inputs:
```
payload.outputs.forEach(function (output) {
    if (output.address === receiving_address) {
        if (!trigger.outputs[asset]) trigger.outputs[asset] = 0;
        trigger.outputs[asset] += output.amount;
    }
});
``` [4](#0-3) 

Idiomatic AA balance/escrow accounting keys entirely off `trigger.address` — see the shipped sample bank/vault AA, which credits and later refunds `var['balance_'||trigger.address||...]`:
```
if (trigger.output[[asset=base]] > 10000){
    $base_key = 'balance_'||trigger.address||'_'||'base';
    var[$base_key] = var[$base_key] + trigger.output[[asset=base]];
``` [5](#0-4) 
and later the withdrawal path pays back to `trigger.address`:
```
{
    app: 'payment',
    payload: {
        asset: "{trigger.data.asset}",
        outputs: [ {address: "{trigger.address}", amount: "{trigger.data.amount}"} ]
    }
}
``` [6](#0-5) 

If two independently-controlled addresses jointly co-sign a single trigger unit (each signing for their own spent output — a normal, validated ocore feature for combined/batched payments), the AA credits the *entire* combined deposit to whichever co-author's address happens to sort first, not to whoever actually supplied the funds. This is the same root cause as the reported ERC4626 bug: the accounting key (`trigger.address` / `msg.sender`) is decoupled from the true asset owner authorizing the spend (the co-author whose output/shares are actually consumed), letting one party siphon the other's deposit or, by choosing which address to add as a minimal co-author, be credited coins it never contributed.

### Impact Explanation
An attacker who arranges (or is offered, e.g. by a wallet/service that batches several users into one unit to save fees, or via a legitimate atomic multi-party payment) to be a co-author of a trigger unit alongside a victim can be credited with all of the victim's deposited funds in any AA (bank/vault/escrow/DEX style) that attributes deposits and pays out withdrawals using `trigger.address`. This is a direct, permanent theft of AA-managed funds/state (High impact): the victim's contribution is credited to the attacker's key and can be withdrawn by the attacker, while the victim's own balance record under their own address remains empty.

### Likelihood Explanation
Exploitation requires the victim's address to be present as a co-author of the same trigger unit as the attacker's chosen address, with the attacker's address sorting first. Since ocore addresses are base32-encoded hashes, an attacker can pre-generate (grind) a single throwaway address whose leading characters are minimal, and this one crafted address will sort before the overwhelming majority of victim addresses without needing to target any specific victim in advance. The scenario requires only that a genuine multi-authored (jointly-signed) payment to an AA occurs with the attacker's address included — a supported protocol pattern (batched/atomic multi-party payments) that is not gated by any AA-trigger validation rule tying `trigger.address` to input ownership. This mirrors the "Medium" likelihood rated in the original report, where the attacker also needed a cooperating/approving counterparty.

### Recommendation
Do not derive the crediting/withdrawal identity for an AA trigger from `objUnit.authors[0].address`. Either:
1. Reject multi-authored primary AA triggers outright (require exactly one author, mirroring the existing restriction already enforced for AA *response* units in `validateAuthors`: `if (objValidationState.bAA && arrAuthors.length !== 1) throw Error(...)`), or
2. If multi-author triggers must be supported, derive `trigger.address`/attribution per-output from the actual input owner that funded each output sent to the AA (i.e., trace `payload.inputs`/`src_output.address`) rather than from the sorted author list, and document/enforce that AA authors must not rely on `trigger.address` unless the trigger is guaranteed single-authored.

### Proof of Concept
1. Attacker generates (grinds) a keypair whose address `A` sorts alphabetically before essentially any other address (e.g. leading with the smallest base32 symbol) — a one-time, reusable cost.
2. Victim `V` is convinced (via a batching wallet service, or an atomic joint-payment flow) to co-sign a single unit together with `A`, where `V`'s own output funds a large payment to a deposit/bank AA (as in `test/samples/a_bank_without_percent.oscript`), and `A` merely appears as a second author (e.g., contributing a negligible/dust amount so its signature is required and legitimately obtained).
3. Author addresses are sorted `[A, V]` per `validateAuthors`, so `objUnit.authors[0].address === A`.
4. When the unit stabilizes, `handleAATriggers`/`handlePrimaryAATrigger` calls `getTrigger(objUnit, aa_address)`, which sets `trigger.address = A` while `trigger.outputs` includes the full amount `V` sent to the AA (per `aa_composer.js:375-397`).
5. The AA script executes `var['balance_'||trigger.address||'_base'] += trigger.output[[asset=base]]`, crediting `A` (attacker) with the funds `V` deposited.
6. Attacker later sends a withdrawal trigger from `A` and receives `V`'s funds via the AA's payment message to `trigger.address` (`A`), while `V`'s recorded balance under key `balance_V_base` remains zero, permanently losing the deposited amount.

function getTrigger(objUnit, receiving_address) {
	var trigger = { address: objUnit.authors[0].address, unit: objUnit.unit, outputs: {} };
	if ("max_aa_responses" in objUnit)
		trigger.max_aa_responses = objUnit.max_aa_responses;
	objUnit.messages.forEach(function (message) {
		if (message.app === 'data' && !trigger.data) // use the first data message, ignore the subsequent ones
			trigger.data = message.payload;
		else if (message.app === 'payment' && message.payload) {
			var payload = message.payload;
			var asset = payload.asset || 'base';
			payload.outputs.forEach(function (output) {
				if (output.address === receiving_address) {
					if (!trigger.outputs[asset])
						trigger.outputs[asset] = 0;
					trigger.outputs[asset] += output.amount; // in case there are several outputs
				}
			});
		}
	});
	if (Object.keys(trigger.outputs).length === 0)
		throw Error("no outputs to " + receiving_address);
	return trigger;
}
