### Title
Commit#deployable? and StatusHandler#process trust CI state without verifying the issuing repository, enabling cross-repository status forgery - (File: app/models/shipit/webhooks/handlers/status_handler.rb, app/models/shipit/commit.rb)

### Summary
`StatusHandler#process` resolves commits with `Commit.where(sha: params.sha)`, which is scoped only by SHA and never checks that the webhook's `repository`/organization matches the `Stack` that owns the found commit(s). Because git commit SHAs are content-addressed and identical across forks/mirrors of the same history, an attacker who owns any repository sharing a commit with a victim's tracked repo can send a genuinely-signed GitHub status webhook for their own repository and have it applied to the victim's commit, flipping `Commit#deployable?` to `true`.

### Finding Description
The broken binding is: `repository that authenticated/produced the Status webhook == repository of the Stack that owns the Commit the Status gets attached to`. This never holds because:

- `StatusHandler#process` does:
```ruby
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
``` [1](#0-0) 
This query has no `stack_id`/repository filter — it matches every `Commit` row across every `Stack` sharing the SHA.

- `Commit#create_status_from_github!` then does `statuses.replicate_from_github!(stack_id, github_status)`, using the found commit's own `stack_id`. [2](#0-1)  So the forged `Status` is legitimately attached to the victim's own `Stack`/`Commit`, since `stack_id` comes from the DB record, not from the payload.

- `Commit#deployable?` performs no repository check whatsoever: `!locked? && (stack.ignore_ci? || (success? && !blocked?))`, and `success?`/`state` are delegated to `status`, which is `Status::Group.compact(self, statuses_and_check_runs)` — an aggregate purely over the commit's own `statuses`/`check_runs` records, with zero provenance/repository verification. [3](#0-2) [4](#0-3) 

- `WebhooksController#verify_signature` only validates the HMAC signature against the App/organization secret named by the payload's own `repository_owner` — i.e., it verifies "this webhook truly came from GitHub for the organization/repo the payload claims," not "this commit's SHA truly belongs to that repository." [5](#0-4) 

**Exploit flow:** An attacker forks (or otherwise obtains an identical-history copy of) the victim's tracked public repository — forks preserve commit SHAs exactly. The victim's Stack B has a pending commit with SHA X (matching a commit that also exists, byte-for-byte, in the attacker's fork). The attacker installs/has the GitHub App enabled on their own fork (a routine, unprivileged GitHub action for a public app) and uses their own commit-status API access on their own repository to post a genuine `success` status with the context Stack B's `ci.require` expects, for SHA X. GitHub signs and delivers this webhook correctly (it's legitimately from the attacker's own repository), so `verify_signature` passes. `StatusHandler#process` then matches `Commit.where(sha: X)`, which includes the victim's Stack B commit (unrelated repository), and creates a `Status` scoped to Stack B via `commit.stack_id`. `Commit#deployable?` on the victim's commit becomes `true` purely from this forged evidence, since it never checks that the Status's issuing repository matches Stack B's configured repository.

None of the existing guards close this gap: `verify_signature` authenticates the sender's own organization, not a match to the target commit's stack; `drop_unhandled_event` only checks the event type is handled; there is no `ExplicitParameters` schema field or model validation tying `Status`/`params.repository` to `Commit#stack`/`Stack#repository`.

### Impact Explanation
A forged `success` status can make `Commit#deployable?` true for a commit the attacker does not own or control CI for, and can trigger `schedule_continuous_delivery` → `ContinuousDeliveryJob`, potentially causing an unauthorized deploy of a victim's Stack based on a fabricated CI result. This is a cross-tenant integrity violation: a payload legitimately originating from one repository mutates another repository's `Stack`/`Commit` state (`Status` row), matching the "Critical — a payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy" category. It is repeatable against any victim Stack whose tracked repository history is public/forkable or otherwise shares commit SHAs with a repository the attacker controls, and each shared SHA is one forgeable status.

### Likelihood Explanation
Preconditions: victim Stack requires the forged CI context (`ci.require`) and is not `ignore_ci`; a commit SHA must be shared between the attacker's own repository and the victim's tracked repository — trivially achievable for forks of public/open-source projects, and requires only routine, unprivileged actions (create a fork, enable the app/webhook on it, POST a commit status via a personal GitHub token for one's own repo). No Shipit secrets, sessions, or GitHub App keys are needed. This is a low-cost, fully repeatable attack against any Shipit deployment tracking a forkable/mirrored repository.

### Recommendation
In `StatusHandler#process` (and the analogous check-run handler), scope the `Commit` lookup by the webhook payload's repository (e.g., match `params.repository.full_name`/`repository_owner` against `commit.stack.repository`/`github_repo_name`) before calling `create_status_from_github!`, rejecting or skipping commits whose owning Stack's repository does not match the webhook's asserted repository.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb (conceptual)
test "status webhook from unrelated repository forges CI state on victim stack's commit" do
  victim_stack = shipit_stacks(:shipit)  # repo: "shopify/shipit-engine"
  victim_commit = victim_stack.commits.create!(sha: "deadbeef"*5, ...) # pending, matching stack.ci.require context

  refute victim_commit.reload.deployable?

  # Attacker's payload claims a different repository ("attacker/fork") but the SAME sha
  payload = Webhooks::Handlers::StatusHandler.params_class.new(
    sha: victim_commit.sha,
    state: "success",
    context: victim_stack.required_statuses.first, # ci.require context
    repository: { full_name: "attacker/fork", owner: { login: "attacker" } }
  )

  Webhooks::Handlers::StatusHandler.new.process # simulating with attacker-controlled payload

  assert victim_commit.reload.deployable?, "commit became deployable via a status sourced from an unrelated repository"
end
```
This demonstrates the equality `payload.repository != victim_stack.repository` while `Commit.where(sha:)` still matches and mutates `victim_commit`'s status/deployability.
