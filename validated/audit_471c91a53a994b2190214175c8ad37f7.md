Now I have found the key vulnerability. Let me confirm the exact binding mismatch: `verify_signature` authenticates the org derived from `repository.owner.login` in the JSON payload, then `Webhooks::Handlers::Handler#stacks`/`#repository_name` resolves the actual repository via `repository.full_name` (owner/name) from the *same* payload — but these are two independent, separately-controllable fields in an unverified JSON body evaluated before the signature check passes.### Title
Webhook signature verified against `repository.owner.login`, but events processed against `repository.full_name` — cross-organization webhook spoofing - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/webhook secret to authenticate a webhook against by reading `repository.owner.login` (or `organization.login`) straight out of the unverified JSON body. Once verification passes, every event handler resolves the repository/stack to mutate using a *different* field of the same unverified body: `repository.full_name`. In a multi-organization Shipit deployment (explicitly supported and documented), these two fields are never checked for consistency, so a valid signature computed with one organization's webhook secret can be replayed with a forged body that targets a completely different organization's repository.

### Finding Description
`verify_signature` picks the `GitHubApp` (and thus the `webhook_secret`) to authenticate against via: [1](#0-0) [2](#0-1) 

`repository_owner` reads `params.dig('repository', 'owner', 'login')` from the raw, not-yet-verified JSON body. `Shipit.github(organization: repository_owner)` then looks up the corresponding `GitHubApp` and its `webhook_secret`, and `verify_webhook_signature` HMACs the raw body against that secret: [3](#0-2) 

Once the signature is accepted, `WebhooksController#create` dispatches to the registered handlers, passing the entire parsed payload: [4](#0-3) 

Every handler (e.g. `PushHandler`, the `PullRequest::*` handlers, `Handler#stacks`) resolves which `Repository`/`Stack` to act on using a *separate* field, `repository.full_name`, not `repository.owner.login`: [5](#0-4) [6](#0-5) 

Shipit explicitly supports hosting multiple GitHub organizations from a single instance, each with its own webhook secret: [7](#0-6) [8](#0-7) 

**Binding broken:** the organization that authenticated the request (`repository.owner.login`, checked against that organization's `webhook_secret`) is assumed to equal the repository that gets written (`repository.full_name`), but nothing enforces this equality. Both are independent, attacker-controlled fields inside the same JSON body. GitHub itself would always keep them consistent, but a forged request does not have to.

An attacker who legitimately controls (or has otherwise obtained the webhook secret of) *any one* organization hosted on the shared Shipit instance — call it `OrgAttacker` — can compute a valid `X-Hub-Signature` over a body they fully control, then set `repository.owner.login = "OrgAttacker"` (so `verify_signature` checks the signature against a secret they know and it passes) while setting `repository.full_name = "OrgVictim/some-repo"` (so the handler acts on a completely different tenant's stack).

### Impact Explanation
This breaks the tenant boundary between organizations sharing one Shipit deployment. Concretely reachable effects, using only handlers already registered by default:
- `push` events let the attacker trigger `stack.sync_github(expected_head_sha:)` for `OrgVictim`'s stack with an attacker-chosen `after` SHA [9](#0-8) .
- `status`/`check_suite` events (registered the same way, resolving the repository the same way via `Handler#repository_name`) let the attacker inject fabricated commit statuses/check runs against `OrgVictim`'s commits. Those stored statuses feed directly into `MergeRequest#all_status_checks_passed?` / `any_status_checks_failed?`, which gate `MergeRequest#merge!` [10](#0-9) , i.e. spoofed CI results without ever knowing `OrgVictim`'s secret can push a merge to completion for another organization's repository — an unauthorized merge, matching the Critical impact category ("unauthorized deploy, rollback or merge").
- `membership` events fall back to `organization.login` for both authentication and processing, so they are internally consistent and not exploitable this way; the mismatch is specific to handlers keyed off `repository.full_name` (push, pull_request family, status, check_suite).

### Likelihood Explanation
Exploitation requires the attacker to know the `webhook_secret` of at least one organization configured on the shared instance. In the documented multi-org setup, each organization administrator independently manages their own GitHub App and its webhook secret, so any one of the (potentially many) participating organizations having a weaker security posture, a leaked secret, or a malicious/compromised admin is sufficient to attack every other organization hosted on the same Shipit instance. This is a realistic and fairly low-effort scenario for any multi-tenant deployment, which the engine explicitly supports and documents.

### Recommendation
After verifying the HMAC signature using the organization derived from the payload, re-derive the repository/organization used by every handler from the *same, already-authenticated* organization value (or explicitly validate that `repository.full_name`'s owner segment equals the authenticated `repository.owner.login`/`organization.login`) before dispatching to handlers. Reject the webhook if the two disagree.

### Proof of Concept
1. Attacker administers `OrgAttacker`'s GitHub App on the shared Shipit instance and knows its `webhook_secret`.
2. Attacker crafts a JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "OrgAttacker" },
    "full_name": "OrgVictim/private-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(OrgAttacker_webhook_secret, body)>`.
4. Attacker sends `POST /webhooks` with `X-Github-Event: push`, the body above, and the computed signature.
5. `verify_signature` computes `repository_owner => "OrgAttacker"`, fetches `OrgAttacker`'s `GitHubApp`, and the signature check passes because the attacker used `OrgAttacker`'s own secret [1](#0-0) .
6. `PushHandler.process` resolves `repository_name` from `repository.full_name = "OrgVictim/private-repo"` and triggers `sync_github` on `OrgVictim`'s stack [5](#0-4) [9](#0-8) , despite the request never being signed with `OrgVictim`'s secret. The same technique can be applied to `status`/`check_suite` payloads to inject fabricated CI results consumed by the merge queue.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
