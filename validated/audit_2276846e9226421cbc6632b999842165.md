### Title
Accrual value overflow permanently freezes an overlarge market - (File: common/src/rates/index.rs)

### Summary
A sufficiently large borrowed market can reach a state where accrual panics while converting scaled debt to its new RAY value; because every pool mutation accrues first, this permanently blocks repayment, withdrawal, liquidation, bad-debt cleanup, and recapitalization for that market. [1](#0-0) [2](#0-1) 

### Finding Description
`update_borrow_index` caps the borrow index itself at `MAX_BORROW_INDEX_RAY`, but it does not ensure that `borrowed * new_borrow_index / RAY` remains representable in `i128`. [3](#0-2) 

During accrual, `calculate_supplier_rewards` computes both the old and new total debt values using `borrowed.mul(index)`, and `Ray::mul` performs checked fixed-point arithmetic that panics when the result does not fit `i128`. [1](#0-0) [4](#0-3) 

`global_sync` executes this accrual for every elapsed chunk before committing the updated indexes and revenue shares. [5](#0-4) [6](#0-5) 

Once `scaled_debt * new_index / RAY > i128::MAX`, the accrual transaction reverts atomically, leaving the same oversized scaled debt in storage; every later attempt therefore attempts the same overflowing product again. [7](#0-6) 

An unprivileged attacker can create this state through `supply` and `borrow` when the market's configured caps admit enough exposure, and can trigger the freeze through permissionless `update_indexes(caller, assets)` once the index has grown sufficiently. [8](#0-7) [9](#0-8) [10](#0-9) 

### Impact Explanation
All supplier funds in the affected market become inaccessible because withdrawal runs the same accrual path before burning supply shares. [11](#0-10) [2](#0-1) 

Borrowers cannot reduce their positions because repayment also accrues before debt shares are burned, and liquidators cannot rescue the position through repayment or seizure. [12](#0-11) [13](#0-12) 

Recapitalization cannot recover the market because it also loads and accrues the overflowing market before crediting cash. [14](#0-13) [2](#0-1) 

The result is permanent freezing of user funds and an inability to operate that market unless the contract is replaced with corrected logic. [15](#0-14) 

### Likelihood Explanation
The attack requires a market whose configured borrow cap, collateral capacity, and liquidity allow scaled debt large enough that index growth can push its RAY value beyond `i128::MAX`. [1](#0-0) [16](#0-15) 

No privileged call is needed after such a market exists: the attacker supplies liquidity and collateral, draws the permitted borrow, waits for enough accrual, and calls `update_indexes`. [10](#0-9) [17](#0-16) 

The existing regression test demonstrates that a high-utilization market can hit the value ceiling before the index ceiling and that both withdrawal and repayment then fail with `MathOverflow`. [7](#0-6) 

### Recommendation
Before accruing a market, clamp the new borrow index to the greatest value for which `borrowed * new_index / RAY` fits `i128`, rather than relying only on the global `MAX_BORROW_INDEX_RAY` cap. [3](#0-2) [1](#0-0) 

Apply an equivalent headroom check to `supplied * new_supply_index / RAY` before distributing supplier rewards, since `update_supply_index` also multiplies scaled supply by the index before adding rewards. [18](#0-17) 

A secondary defense is to reduce admitted supply and borrow caps dynamically according to the remaining value headroom at the applicable index ceiling, so new positions cannot create an unrepresentable future market total. [19](#0-18) 

### Proof of Concept
Assume a market with asset decimals `d`, an active spoke `S`, debt key `K_debt`, collateral key `K_coll`, a borrow cap permitting debt `D`, and enough collateral value `C`.

```text
1. attacker supplies the debt-market liquidity:
   supply(attacker, 0, S, [(K_debt, P)])

2. attacker creates a collateralized account:
   account_id = supply(attacker, 0, S, [(K_coll, C)])

3. attacker draws the permitted debt:
   borrow(attacker, account_id, [(K_debt, D)], Some(attacker))
```

Choose `D` such that the resulting scaled debt `B_scaled` satisfies:

```text
B_scaled * future_borrow_index / RAY > i128::MAX
```

while both the initial borrow and `B_scaled * RAY / RAY` remain representable. [20](#0-19) [21](#0-20) 

After ledger time advances under a positive borrow rate, the attacker calls:

```text
update_indexes(attacker, [K_debt])
```

`global_sync` attempts the accrual, `calculate_supplier_rewards` evaluates `B_scaled.mul(new_borrow_index)`, and the transaction panics with `MathOverflow`. [22](#0-21) [1](#0-0) 

Subsequent calls such as `repay`, `withdraw`, `liquidate`, `clean_bad_debt`, and `recapitalize` for `K_debt` all enter a pool mutation that accrues first, so they hit the same overflow and cannot clear the state. [2](#0-1) [15](#0-14)

pub fn update_supply_index(env: &Env, supplied: Ray, old_index: Ray, rewards_increase: Ray) -> Ray {
    if supplied == Ray::ZERO || rewards_increase == Ray::ZERO {
        return old_index;
    }

    let total_supplied_value = supplied.mul(env, old_index);

    if total_supplied_value == Ray::ZERO {
        return old_index;
    }

    let new_value = total_supplied_value.checked_add(env, rewards_increase);

    let bounded_old = old_index.raw().min(MAX_SUPPLY_INDEX_RAY);
    Ray::from(grown.min(MAX_SUPPLY_INDEX_RAY).max(bounded_old))

pub(crate) fn global_sync(env: &Env, cache: &mut Cache) {
    if !cache.needs_accrual() {
        return;
    }

    let mut remaining = cache.elapsed_ms();
    while let Some(nonzero) = NonZeroU64::new(remaining) {
        let chunk = nonzero.get().min(MAX_COMPOUND_DELTA_MS);
        accrue_chunk(env, cache, chunk);
        remaining = remaining.saturating_sub(chunk);
    }

    cache.mark_accrued();

    t.supply_raw(BOB, "BIG18", principal);

**File:** docs/reference/formulas.md (L407-417)
```markdown
A cap is in native token units. Entry compares stored scaled usage plus the
new scaled amount with the cap floor-converted at the current index. Zero cap
allows no positive exposure. Exits subtract usage without checking caps;
missing usage rows and zero exit deltas are no-ops. Cap→scaled conversion
saturates at `i128::MAX` (`calculate_scaled_cap`), so the entry check fails
open instead of trapping. A saturated scaled cap does not enforce the
configured asset-unit limit. An admitted cap saturates only at an index below
one RAY. Only a bad-debt write-down moves the supply index below one RAY; at
its floor (`RAY / 1000`), a supply cap above 1/1000 of the admitted maximum
saturates. The borrow index never falls below one RAY, so an admitted borrow
cap cannot saturate. Position conversion still rejects overflow.
```

**File:** docs/reference/formulas.md (L432-437)
```markdown
The token-to-RAY maximum is also the admitted cap maximum. Accrued position
values and market totals must independently fit the RAY domain; valid caps and
bounded indexes do not guarantee that future accrual fits. Value overflow can
occur before the index ceiling and block repayment/withdrawal because those
operations accrue first. At the borrow-index ceiling, further accrual produces
no borrower interest. No dedicated ceiling alarm is emitted.
```
