This confirms the multi-org configuration where `Shipit.github(organization:)` selects a different `GitHubApp` instance—with its own distinct `webhook_secret`—per organization key, as documented in `docs/setup.md:182-209` and demonstrated in `test/dummy/config/secrets_double_github_app.yml`.

The vulnerability chain is now clear:

- `WebhooksController#verify_signature` picks the HMAC key based solely on `repository_owner`, derived from `params.dig('repository', 'owner', 'login')` (or `organization.login`) [1](#0-0) [2](#0-1) .
- Once the signature validates, the raw parsed JSON is dispatched unmodified to every registered handler for that event: `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` [3](#0-2) .
- Every handler resolves the target `Repository`/`Stack` using a completely different payload field: `payload.dig('repository', 'full_name')` [4](#0-3) .
- Nothing ties `repository.owner.login` (the field that selected the signing key) to `repository.full_name` (the field that selects which stack is mutated). They are independent JSON fields inside the same signed body, and the signer only proves "this body was HMAC'd with org X's secret" — not "the org-X part of the body matches the repository being acted on."

Given `Shipit.github_organizations` returning multiple orgs each with their own `webhook_secret` [5](#0-4) , an attacker who legitimately controls the webhook secret for one onboarded organization (e.g., they administer their own sandbox org that was deliberately onboarded to this shared Shipit instance) can compute a valid `X-Hub-Signature` over an arbitrary JSON body of their choosing. They set `repository.owner.login` to their own org (so `verify_signature` picks their own known secret) while setting `repository.full_name` to `victim-org/victim-repo` (so the handler acts on a stack they don't control).

Concretely, via the `status` event handler, `StatusHandler#process` looks up `Commit.where(sha: params.sha)` — scoped globally, not by the signing org — and calls `commit.create_status_from_github!`, which can flip a required CI context to `success`, which triggers `stack.schedule_merges` / continuous delivery scheduling [6](#0-5) [7](#0-6) . This lets an attacker who only owns a webhook secret for an unrelated onboarded org mark commits on a victim stack as CI-green, enabling continuous-deployment merges/deploys they have no authorization over — a cross-repository write achieved purely by exploiting the mismatch between "which org's secret validated this request" and "which repository/stack the request payload claims to describe."

This is a legitimate, narrow analog to the report's core pattern (a state-changing operation that doesn't respect the boundary meant to gate it) but expressed as: verified-signer-org ≠ acted-upon-repository, rather than a missing `whenNotPaused` modifier. It requires a multi-org Shipit deployment where the attacker controls at least one onboarded organization's webhook secret — a real, documented, supported configuration [8](#0-7) .

### Title
Webhook signature verification binds to `repository.owner.login`, but handlers act on `repository.full_name`, letting one onboarded organization forge webhooks for another's stacks - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
In multi-organization Shipit deployments, each organization has its own `webhook_secret` used to validate `X-Hub-Signature`. The signature check selects which secret to use based on `repository.owner.login` (or `organization.login`) inside the JSON payload, but the event handlers that actually mutate state look up the target `Repository`/`Stack`/`Commit` using an unrelated field, `repository.full_name`. Since both fields live in the same attacker-controlled payload and neither is cross-checked against the other, an org whose webhook secret is known to the attacker can forge a validly-signed webhook whose `repository.owner.login` matches their own org (to pass signature verification) while `repository.full_name` names a completely different, victim-owned repository.

### Finding Description
`WebhooksController#verify_signature` computes `repository_owner` and fetches the corresponding `GitHubApp`/secret via `Shipit.github(organization: repository_owner)` [1](#0-0) , where `repository_owner` reads `params.dig('repository', 'owner', 'login')` [2](#0-1) . `Shipit.github` resolves a distinct `GitHubApp` (and thus distinct `webhook_secret`) per organization key configured in `secrets.github` [5](#0-4) , exactly as documented for "Using Multiple Github Applications" [8](#0-7) .

Once `verify_signature` passes, `create` parses the whole raw body and dispatches it to all handlers for the event, unfiltered by organization [3](#0-2) . Every handler's base class resolves the affected `Repository`/`stacks` via `payload.dig('repository', 'full_name')` [4](#0-3)  — a different JSON key than the one used to pick the signing secret.

Because HMAC-SHA1 verification only proves "this exact byte string was signed with key K"; it does not constrain which fields inside that string are internally consistent. An attacker who knows the `webhook_secret` for organization A (fully expected if they are a legitimate admin/integrator of org A, which was itself onboarded to the shared Shipit instance) can freely construct a JSON body where `repository.owner.login = "org-a"` (so the correct/known secret is selected) and `repository.full_name = "org-b/victim-repo"` (so the handler operates on org B's stack).

### Impact Explanation
This breaks the equality the deployment model depends on: `organization whose credential authenticated the request == organization whose repository is mutated by the request`. Concretely:
- `Handlers::StatusHandler#process` finds commits purely `by sha` (globally, not scoped by validated org) and records a GitHub status, which can flip CI state to `success` and trigger `stack.schedule_merges` [6](#0-5) [9](#0-8) , which can advance continuous delivery / merge queue processing for a victim's stack that the attacker has no legitimate access to.
- Other handlers (`PushHandler`, `PullRequest::*Handler`, `MembershipHandler`, `CheckSuiteHandler`) are all reachable the same way, since none of them re-validate that the acted-upon repository belongs to the org whose secret validated the signature.

This is an unauthorized cross-repository write/state change achievable by an attacker who possesses only their own organization's legitimate webhook secret — meeting the "cross-repository writes" / "unauthorized deploy/merge" bar.

### Likelihood Explanation
Requires a Shipit instance configured with multiple GitHub organizations (a supported, documented configuration) where the attacker legitimately controls (or previously leaked/rotated into) one onboarded org's webhook secret. Given that bar, forging the payload is trivial (compute HMAC-SHA1 over an arbitrary JSON string with the known secret) and requires no other privilege, session, or API token.

### Recommendation
After signature verification, re-derive `repository.owner.login` (or `organization.login`) from the payload and require it to match the organization portion of `repository.full_name` before dispatching to handlers; reject the webhook (422) on mismatch. Alternatively, pass the already-resolved `repository_owner` into each handler and have handlers scope their repository/stack/commit lookups to that verified organization rather than trusting `repository.full_name` independently.

### Proof of Concept
1. Shipit is configured with `github.OrgA` and `github.OrgB`, each with its own `webhook_secret` (per `docs/setup.md` multi-org setup).
2. Attacker controls/knows `OrgA`'s `webhook_secret` (e.g., they are OrgA's own GitHub App owner).
3. Attacker builds a JSON body for the `status` event:
```json
{
  "sha": "<victim-commit-sha>",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/victim-repo" }
}
```
4. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(OrgA_webhook_secret, body)>` and POSTs to `/webhooks` with `X-Github-Event: status`.
5. `verify_signature` resolves `repository_owner = "OrgA"`, fetches OrgA's secret, and the signature validates.
6. `Handlers::StatusHandler#process` finds the commit by `sha` (regardless of org) and creates a `success` status on it, potentially advancing merge/deploy state for `OrgB/victim-repo`'s stack — despite the attacker never having proven any relationship to OrgB.

    # Backward compatibility
    # nil signifies the single github app config schema is being used

    else
