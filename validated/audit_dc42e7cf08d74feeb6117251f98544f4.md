### Title
Missing cosigner authorization check in wallet "sign" IPC handler allows any paired device to trigger local signing of attacker-crafted units - (File: wallet.js)

### Summary
The Pacemaker CVE stems from an IPC interface that accepted privileged requests from any local, unprivileged caller without verifying the caller actually had the right to invoke that action. `wallet.js` has an analogous device-message ("device IPC") handler for the `"sign"` subject where the intended authorization check — that the requesting device is actually a registered cosigner of the wallet owning the address — is explicitly commented out.

### Finding Description
`handleMessageFromHub()` dispatches messages received from paired devices via the hub. For the `"sign"` subject, after basic structural validation of the unsigned unit, it calls `findAddress(body.address, body.signing_path, {...})`. When the address is locally hosted (`ifLocal`), the handler is supposed to verify that `from_address` (the device that sent the sign request) is registered as a cosigner of the wallet for that address. That check is present only as a comment: [1](#0-0)

As a result, any device that is merely paired/correspondent with the victim node (not necessarily a wallet cosigner) can send a `"sign"` message referencing *any* locally-hosted address the node controls, and `findAddress`'s `ifLocal` branch will proceed unconditionally — firing `signing_request`/`validated-<unit>` events with attacker-supplied unit content (including payment inputs/outputs and messages) rather than being rejected up front for lack of cosigner authorization [2](#0-1) . This mirrors the Pacemaker flaw: the entity that should only be trusted for a narrow, cooperative use case (multisig/multilateral co-signing) is instead treated as fully privileged to request signing operations on any address the node hosts, with the address-ownership check removed.

Contrast this with `ifRemote`, where an explicit membership check *is* enforced (`other_device_addresses.includes(from_address)`) before proxying the request [3](#0-2) . The local-address branch lacks the equivalent guard.

### Impact Explanation
This weakens the wallet's IPC-like trust boundary between "paired device" and "cosigner of a specific address." A malicious or compromised paired device (an unprivileged counterparty in the correspondence relationship) can:
- Force the node to run unit validation (`network.handleOnlineJoint`) and emit `signing_request` for arbitrary unsigned units addressed to any locally-controlled address/signing path, without being an authorized cosigner of that address.
- For shared/multisig addresses, spoof requests that should only originate from genuine cosigners, potentially tricking a poorly-implemented downstream signer (UI) into approving signatures for units it did not construct, or flooding it with signing requests as denial-of-confirmation noise.
- Combined with any weakness in the UI's confirmation-dialog logic (outside this repo but downstream of this event), this can lead to unauthorized fund movement from a shared/multisig address — matching the "unauthorized spending" impact criterion, since the core library itself performs no cosigner-authorization check before entering the signing-request flow.

### Likelihood Explanation
Reaching this code path requires only being a paired device of the victim (already a common, low-privilege trust relationship in Obyte's device-pairing model — not a hub, not the network, not root/mocked access), and sending a well-formed `"sign"` device message referencing an address hosted locally by the victim. No additional privilege is required, and the missing check is unconditional (not gated by any flag), so the vulnerable path is always reachable by any correspondent device.

### Recommendation
Restore an authorization check in the `ifLocal` branch of the `"sign"` handler: before calling `callbacks.ifOk()` and emitting `signing_request`, verify that `from_address` is actually associated with the wallet/address (e.g., listed among `wallet_signing_paths` or `extended_pubkeys` for that wallet's device set, or, for shared addresses, among `shared_address_signing_paths` device addresses), analogous to the check already performed in the `ifRemote` branch. If multilateral signing (unrelated devices signing separate leaves of the same contract) must remain supported, restrict the bypass to that narrow scenario explicitly rather than removing the check for all local addresses.

### Proof of Concept
1. Device A pairs with victim node V (a normal, non-cosigner pairing).
2. V hosts address `ADDR` in a wallet/shared address where A is *not* listed as a cosigner.
3. A sends V a hub message:
```
{
  subject: "sign",
  body: {
    address: "ADDR",
    signing_path: "r",
    unsigned_unit: { authors: [{ address: "ADDR", authentifiers: {...} }], messages: [...] }
  }
}
```
4. In `handleMessageFromHub`, structural checks pass, `findAddress` resolves `ADDR` to `ifLocal` (since V hosts it), and the commented-out cosigner check never executes — `callbacks.ifOk()` fires and `network.handleOnlineJoint` / `signing_request` proceeds for A's crafted unit, despite A never being verified as a cosigner of `ADDR`.

Note: I could not find, within this repo, the UI-side handler of the `signing_request` event (it lives in the downstream wallet application), so I cannot confirm whether every deployment auto-rejects unauthorized requests at that layer; the vulnerability described here is specifically the missing authorization guard inside `ocore`'s own IPC handler, which is the correct locus for this defense-in-depth check.
