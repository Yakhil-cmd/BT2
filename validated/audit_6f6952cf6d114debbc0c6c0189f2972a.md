### Title
Cross-organization webhook forgery via secret selected from unverified payload field, distinct from the field acted on - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects *which* GitHub App / webhook secret to verify the incoming HMAC signature against based on `repository_owner`, which is read straight out of the untrusted, not-yet-verified JSON body [1](#0-0) [2](#0-1) . In a multi-organization Shipit deployment (`secrets.github` keyed by org, see `Shipit.github_app_config`) [3](#0-2) , each organization has its own `webhook_secret`. The field used to pick the secret (`repository.owner.login` / `organization.login`) is not the same field the event handlers actually act on — handlers derive the target repository from `repository.full_name` [4](#0-3)  and from `params.repository.full_name` in the pull-request and push handlers [5](#0-4) [6](#0-5) .

### Finding Description
The binding that should hold is: **the organization whose secret validated the signature == the organization owning the repository the handler acts on**. The controller breaks this equality:

1. `repository_owner` is computed from `params.dig('repository', 'owner', 'login')` (or `organization.login`) before any signature check has occurred [2](#0-1) .
2. `verify_signature` uses that attacker-supplied value to fetch a `GitHubApp` (and thus a `webhook_secret`) via `Shipit.github(organization: repository_owner)` [1](#0-0) , resolved through `Shipit.github_app_config(organization)` [7](#0-6) .
3. The HMAC signature is validated only against the secret associated with `repository.owner.login`, not against `repository.full_name` [8](#0-7) .
4. Once the check passes, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` runs handlers that resolve the actual target stack/repository purely from `repository.full_name` inside the same JSON body [9](#0-8) [4](#0-3) .

An attacker who legitimately owns/administers *any* organization onboarded to the same multi-tenant Shipit instance (and therefore knows their own org's `webhook_secret`) can craft a payload where `repository.owner.login` = their own org (so the correct, known secret validates the signature) while `repository.full_name` = a victim org's repository. The signature check passes because it only ever binds to `repository.owner.login`; the handler then acts on the victim's repository/stack using data entirely controlled by the attacker (e.g. forged commit SHAs for `push`, or forged status/check-run/pull-request payloads), analogous to the `addCandidate` report's "arbitrary hash/name not validated against the true intended target" bug class.

This directly maps to the report’s bug class: a hash/identifier used to gate an action (`addCandidate`'s `hash`) is attacker-controlled and not bound to the true actor, letting an unprivileged party interfere with another party's state. Here the "identifier" is the organization login used purely to pick a signing secret, decoupled from the repository the resulting action actually targets.

### Impact Explanation
This crosses an explicit trust boundary named in the rules: "an organization that authenticated versus the repository that is written". Concretely reachable handlers (`PushHandler`, `StatusHandler`, `CheckSuiteHandler`, pull-request handlers) resolve their target stack from `repository.full_name` and then perform authenticated writes/state changes for that stack (e.g., queuing `GithubSyncJob`, creating `Status`/`CheckRun` records, updating `PullRequest` records, archiving/unarchiving review stacks) — all attributable to a webhook signed by a different, unrelated organization. Depending on how CI/status gating and continuous delivery are configured for the victim stack, forged `status`/`check_suite` events can flip a commit's CI/deployable state, which can enable an unauthorized deploy through Shipit's continuous delivery path. This satisfies the "High" bar (unauthenticated/incorrectly-authenticated write into another repository's state) and potentially escalates to "Critical" (unauthorized deploy) if continuous deployment is enabled on the targeted stack.

### Likelihood Explanation
Requires the attacker to control at least one organization/installation that is legitimately onboarded to the same Shipit instance (multi-org `secrets.github` configuration) — i.e., they must know one valid `webhook_secret`, which is realistic for any tenant/organization administrator in a shared Shipit deployment. No Shipit session, `ApiClient` token, or GitHub App private key is needed; only a legitimate webhook secret for the attacker's own org, which they possess by design. This is a design flaw in secret selection, not a brute-force or session-based attack, making it a genuine unprivileged-organization vs. victim-organization crossing.

### Recommendation
Bind webhook signature verification to the ultimate resource being acted upon, not to a spoofable field selected before verification:
- After verifying the signature with an organization's secret, re-derive and cross-check that `repository.owner.login` (or `organization.login`) used for secret selection matches `repository.full_name`'s owner before dispatching to handlers; reject on mismatch.
- Alternatively, in multi-org setups, verify the signature against *all* configured organization secrets and only accept the event if the same organization's secret both verifies the signature and matches the repository owner referenced by `repository.full_name`.
- Document that "one org per Shipit webhook secret" is not a security boundary unless this cross-check is enforced.

### Proof of Concept
1. Deploy Shipit with multi-org config: `secrets.github` containing `OrgA` (victim, has stacks tracking `OrgA/victim-repo`) and `OrgB` (attacker-controlled org with known `webhook_secret_B`), per `lib/shipit.rb#github_app_config` [7](#0-6) .
2. Attacker crafts a `push` event JSON body:
   ```json
   {
     "ref": "refs/heads/main",
     "after": "<attacker-chosen sha>",
     "repository": { "owner": { "login": "OrgB" }, "full_name": "OrgA/victim-repo" }
   }
   ```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(webhook_secret_B, raw_body)>` and POSTs to `/webhooks` with `X-Github-Event: push`.
4. `WebhooksController#repository_owner` returns `"OrgB"` [2](#0-1) ; `verify_signature` looks up `OrgB`'s app/secret and the signature validates [1](#0-0) .
5. `Webhooks.for_event('push')` dispatches to `PushHandler`, which resolves `stacks` via `Repository.from_github_repo_name` using `repository.full_name = "OrgA/victim-repo"` [4](#0-3) [10](#0-9) , and enqueues `stack.sync_github(expected_head_sha: params.after)` for the victim's stack — an action attributed to a webhook that was never signed by OrgA.

I was unable to fully trace `Stack#sync_github` / `GithubSyncJob` internals or `StatusHandler`/`CheckSuiteHandler` bodies within the available context to confirm the exact downstream write (e.g., whether it can flip `deployable?` to directly trigger continuous deployment) — this would need to be validated by a Devin session with full file access before treating the "unauthorized deploy" escalation as confirmed rather than plausible.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
