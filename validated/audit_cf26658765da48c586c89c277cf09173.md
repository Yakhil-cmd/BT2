Confirmed: `is_signature_normalized` at [1](#0-0)  only checks the S component (low-S canonical form) and never inspects or constrains byte 64 (the V/recovery-id byte) of the 65-byte signature. It cannot reject a non-canonical V value of 27/28.

### Title
Typed (non-Legacy) Ethereum transactions in pallet-revive accept V-values of 27/28 instead of requiring strict `y_parity ∈ {0,1}` - ([File: substrate/frame/revive/src/evm/api/signature.rs])

### Summary
`pallet-revive`'s Ethereum-compatible transaction decoding accepts `y_parity` values of 27/28 (the legacy pre-EIP-155 `v` convention) for EIP-2930/1559/4844/7702 typed transactions instead of enforcing the EIP-1559-family requirement that `y_parity` be exactly 0 or 1. This is the direct Substrate/pallet-revive analog of the Nethermind `EL-2026-11` finding.

### Finding Description
`TransactionSigned::raw_signature()` builds the raw `[r,s,v]` 65-byte signature for every transaction type by converting the RLP-decoded `y_parity` field directly into `sig[64]` via `tx.y_parity.try_into().map_err(|_| ())?`, for all of `Transaction7702Signed`, `Transaction4844Signed`, `Transaction1559Signed`, and `Transaction2930Signed`: [2](#0-1) 

This byte is then passed to `recover_eth_address_from_message`, which only checks low-S normalization before calling the host function `secp256k1_ecdsa_recover`: [3](#0-2) 

The `secp256k1_ecdsa_recover` host implementation silently normalizes any V byte `> 26` by subtracting 27 (`if sig[64] > 26 { sig[64] - 27 }`), i.e. it treats 27/28 the same as 0/1, without producing an error: [4](#0-3) 

Per EIP-2930/EIP-1559/EIP-4844/EIP-7702, `yParity` MUST be a strict boolean (0 or 1); a value of 27/28 is a spec violation that go-ethereum rejects (`invalid sender`), exactly as documented in the referenced Nethermind report. Notably, the pallet-revive maintainers were aware of this exact bug class for EIP-7702 **authorization-list tuples** and explicitly patched it there: `recover_authority()` in `eip7702.rs` rejects `y_parity.bits() > 1` before calling `recover_eth_address_from_message`, with a comment directly describing this exact silent-normalization hazard: [5](#0-4) 
and `GenericTransaction::into_call` similarly bounds-checks `auth.y_parity.bits() > 8` for authorization tuples: [6](#0-5) 

However, this same fix was **not** applied to the top-level transaction signature (`raw_signature()`/`recover_eth_address()`) used to recover the transaction sender for typed transactions 0x01/0x02/0x03/0x04. There is no code path that rejects `y_parity ∈ {27, 28}` (or any value `> 1`) for the primary transaction signature before it reaches `recover_eth_address_from_message`.

### Impact Explanation
Because ECDSA recovery is deterministic given `(r, s, effective_recovery_id)`, a transaction sender submitting `y_parity=27` recovers to the identical address as `y_parity=0` for the same `(r,s)`. This means:
- The chain accepts a non-canonical/spec-noncompliant wire encoding as valid, diverging from the Ethereum JSON-RPC/tooling ecosystem's expectations (go-ethereum, ethers.js, viem, etc. would reject or produce a different canonical form), causing cross-tooling/indexer/wallet interoperability breaks and potential transaction-hash mismatches for anyone re-deriving or re-signing based on strict EIP encoding assumptions.
- It does not, by itself, allow recovering a *different* signer or forging a signature (unlike a true malleability bug), because the effective recovery id collapses to the same value. Severity is therefore bounded to a spec-conformance/interop issue rather than fund theft or consensus-halting.

Given the bug report's own severity classification (Medium) for the equivalent go-ethereum/Nethermind divergence, and the absence of a directly demonstrable fund-loss or unauthorized-dispatch path here (no different key recovers, and pallet-revive's own signature check is authoritative rather than one of several divergent client implementations), the corresponding polkadot-sdk analog is a low-severity spec-conformance defect rather than a High/Critical vulnerability.

### Likelihood Explanation
High likelihood of triggering: any user can construct a raw typed Ethereum transaction RLP with `yParity` field set to 27 or 28 (fits trivially in the `U256`→`u8` conversion) and submit it via `eth_sendRawTransaction`/`eth_transact`. No privileged role or governance action is required; this is a permissionless, unsigned-inherent-free public entry point (`Call::eth_transact`) validated in `Checkable::check` at `substrate/frame/revive/src/evm/runtime.rs:189-199`, which calls `EthExtra::try_into_checked_extrinsic`, itself relying on `recover_eth_address()`.

### Recommendation
Apply the same fix already used for EIP-7702 authorization tuples (`y_parity.bits() > 1` rejection) to the primary transaction signature path in `TransactionSigned::raw_signature()` for all non-Legacy transaction types (`Transaction7702Signed`, `Transaction4844Signed`, `Transaction1559Signed`, `Transaction2930Signed`), rejecting `y_parity` values other than 0 or 1 before constructing the raw signature / calling `recover_eth_address_from_message`.

### Proof of Concept
No local Rust/FRAME integration reproduction was executed (no filesystem/terminal access in this environment); this is a static code-path analysis. The guard-failure trace is: `TransactionSigned::decode` (RLP, no `y_parity` range check) → `raw_signature()` (`y_parity.try_into::<u8>()` succeeds for 27/28, no explicit `∈{0,1}` check, unlike the sibling fix in `eip7702.rs::recover_authority`) → `recover_eth_address_from_message` (`is_signature_normalized` checks S only) → `sp_io::crypto::secp256k1_ecdsa_recover` (silently maps `V>26 → V-27`). A test analogous to `high_s_signature_is_rejected` in `signature.rs` (constructing a `Transaction1559Signed`/`Transaction2930Signed` with `y_parity = 27` and asserting `recover_eth_address()` returns `Err`) would be expected to **fail** (i.e., incorrectly succeed) with the current code, confirming the gap; this was not executed against the actual repository due to tooling constraints in this session, and should be run by a background agent to obtain empirical PASS/FAIL evidence before filing.

```rust
/// Returns `true` if the S component of a 65-byte ECDSA signature (R||S||V) is in
/// the low range (s <= N/2), i.e. the signature is canonical.
pub fn is_signature_normalized(sig: &[u8; 65]) -> bool {
	let Ok(parsed) = k256::ecdsa::Signature::try_from(&sig[..64]) else {
		return false;
	};
	parsed.normalize_s().is_none()
}
```

```rust
pub fn recover_eth_address_from_message(message: &[u8], signature: &[u8; 65]) -> Result<H160, ()> {
	if !sp_core::ecdsa::is_signature_normalized(signature) {
		log::debug!(target: "evm", "Rejected high-S ECDSA signature (EIP-2 violation)");
		return Err(());
	}

	let hash = keccak_256(message);
	let pk = secp256k1_ecdsa_recover(signature, &hash).map_err(|_| ())?;
	let mut addr = H160::default();
	addr.assign_from_slice(&keccak_256(&pk[..])[12..]);
	Ok(addr)
}
```

```rust
impl TransactionSigned {
	/// Get the raw 65 bytes signature from the signed transaction.
	pub fn raw_signature(&self) -> Result<[u8; 65], ()> {
		use TransactionSigned::*;
		let (r, s, v) = match self {
			TransactionLegacySigned(tx) => (tx.r, tx.s, tx.extract_recovery_id().ok_or(())?),
			Transaction7702Signed(tx) => (tx.r, tx.s, tx.y_parity.try_into().map_err(|_| ())?),
			Transaction4844Signed(tx) => (tx.r, tx.s, tx.y_parity.try_into().map_err(|_| ())?),
			Transaction1559Signed(tx) => (tx.r, tx.s, tx.y_parity.try_into().map_err(|_| ())?),
			Transaction2930Signed(tx) => (tx.r, tx.s, tx.y_parity.try_into().map_err(|_| ())?),
		};
		let mut sig = [0u8; 65];
		r.write_as_big_endian(sig[0..32].as_mut());
		s.write_as_big_endian(sig[32..64].as_mut());
		sig[64] = v;
		Ok(sig)
	}
```

```rust
	fn secp256k1_ecdsa_recover(
		sig: PassPointerAndRead<&[u8; 65], 65>,
		msg: PassPointerAndRead<&[u8; 32], 32>,
	) -> AllocateAndReturnByCodec<Result<[u8; 64], EcdsaVerifyError>> {
		let rid = libsecp256k1::RecoveryId::parse(
			if sig[64] > 26 { sig[64] - 27 } else { sig[64] } as u8,
		)
		.map_err(|_| EcdsaVerifyError::BadV)?;
		let sig = libsecp256k1::Signature::parse_overflowing_slice(&sig[..64])
			.map_err(|_| EcdsaVerifyError::BadRS)?;
		let msg = libsecp256k1::Message::parse(msg);
		let pubkey =
			libsecp256k1::recover(&msg, &sig, &rid).map_err(|_| EcdsaVerifyError::BadSignature)?;
		let mut res = [0u8; 64];
		res.copy_from_slice(&pubkey.serialize()[1..65]);
		Ok(res)
	}
```

```rust
/// Recover the authority address from an authorization signature.
///
/// EIP-7702 mandates `y_parity ∈ {0, 1}`. The shared `sp_io::crypto::secp256k1_ecdsa_recover`
/// primitive accepts the legacy Bitcoin/pre-EIP-155 `v ∈ {27, 28}` convention and silently
/// normalises it to `{0, 1}`, which would let those values pass through here as valid 7702
/// signatures (spec deviation). Filter strictly before recovery so the per-tuple skip path in
/// `process_authorizations` catches them.
fn recover_authority(auth: &AuthorizationListEntry) -> Result<H160, ()> {
	if auth.y_parity.bits() > 1 {
		return Err(());
	}
	recover_eth_address_from_message(&signing_message(auth), &auth.signature())
}
```
