### Title
Webhook signature verification keys on `repository.owner.login` while stack mutation resolves via `repository.full_name`, allowing cross-tenant confusion in multi-org deployments - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/handler.rb])

### Summary
`Shipit::WebhooksController#verify_signature` picks which org's `webhook_secret` to check using `params.dig('repository','owner','login')` (`repository_owner`), while `Shipit::Webhooks::Handlers::Handler#stacks` resolves the actual mutated repository/stack using the independent `params.dig('repository','full_name')` field. Nothing binds these two fields to the same value, so if any configured org in `Shipit.github_config` has a blank `webhook_secret`, an attacker can pick that org for `repository.owner.login` (making signature verification a no-op) while setting `repository.full_name` to `"other-org/real-repo"` to mutate a stack owned by a different, properly secured org.

### Finding Description
The broken binding, stated as an equality that the code fails to enforce: `Repository.from_github_repo_name(payload.dig('repository','full_name')).owner` must equal the organization verified via `Shipit.github(organization: repository_owner)` — but the codebase never checks this.

Trace:
- `WebhooksController#verify_signature` computes `repository_owner` from `params.dig('repository','owner','login')` (or `organization.login`) and calls `Shipit.github(organization: repository_owner).verify_webhook_signature(...)`. [1](#0-0) [2](#0-1) 
- `GitHubApp#verify_webhook_signature` returns `true` unconditionally when the resolved org's `webhook_secret` is blank/nil: `return true unless webhook_secret`. [3](#0-2) 
- If verification passes, `WebhooksController#create` dispatches the raw JSON body to every registered `Handler`, e.g. `PushHandler`, `CheckSuiteHandler`, `PullRequest::LabeledHandler`, `PullRequest::ClosedHandler`, etc. [4](#0-3) 
- Every one of these handlers resolves the target repository/stack from `payload.dig('repository', 'full_name')`, completely independent of `repository_owner`: `Repository.from_github_repo_name(repository_name)&.stacks`. [5](#0-4) 
- `Repository.from_github_repo_name` simply splits `owner/name` from the string and looks up by those columns — it has no relation to `repository_owner` used during signature verification. [6](#0-5) 

Exploit flow: attacker registers/controls a GitHub org (`AttackerOrg`) that a Shipit operator has configured in `Shipit.github_config` with a blank `webhook_secret` (a documented/valid configuration shape, per `config/secrets.development.example.yml` and the multi-org test fixture `test/dummy/config/secrets_double_github_app.yml`). The attacker then sends `POST /webhooks` directly (no real GitHub signature needed) with:
```json
{
  "repository": { "owner": { "login": "AttackerOrg" }, "full_name": "VictimOrg/victim-repo" },
  ... event-specific fields for push/check_suite/pull_request ...
}
```
`verify_signature` resolves `Shipit.github(organization: "AttackerOrg")`, whose `webhook_secret` is blank, so `verify_webhook_signature` short-circuits to `true` regardless of the (irrelevant) `X-Hub-Signature` header or body content. The request is accepted and forwarded to handlers, which resolve `Repository.from_github_repo_name("VictimOrg/victim-repo")` and mutate the victim's stack (enqueue `GithubSyncJob`, schedule check-run refresh, archive/unarchive review stacks, etc.) — all without ever validating a signature scoped to `VictimOrg`.

Existing guards do not close this gap: `drop_unhandled_event` only filters by event type, not by owner/full_name consistency; `GithubOrganizationUnknown` only guards against an org name absent from config, not a mismatched-but-valid org; `ExplicitParameters` schemas validate field types/presence, not cross-field consistency between `repository.owner.login` and `repository.full_name`; and no model validation (`Repository`, `Stack`) ties incoming webhook owner claims to signature verification scope.

### Impact Explanation
An unauthenticated, unprivileged attacker who merely has a GitHub org configured in Shipit's multi-org `github_config` with a blank `webhook_secret` can forge webhook payloads that mutate stacks, commits, pull-request review-stack lifecycle (archive/unarchive) and trigger sync/deploy-adjacent jobs belonging to **any other org** configured in the same Shipit instance, including orgs with properly configured secrets. This is a cross-tenant authentication bypass: a payload attributed to one org mutates another's stack — matching the Critical impact category defined in the rules. The attack is fully repeatable against arbitrary victim repositories/stacks as long as their `owner/name` is known (which is public GitHub information), and the blast radius spans every tenant in the shared Shipit deployment.

### Likelihood Explanation
Preconditions: a Shipit instance must be configured for multiple GitHub organizations (`Shipit.github_config` keyed by org) with at least one org having no `webhook_secret` set. This is not a hypothetical edge case — the repo's own example configs (`config/secrets.development.example.yml`, `config/secrets.development.shopify.yml`, `test/dummy/config/secrets_double_github_app.yml`) all show `webhook_secret: # nil` as an accepted/documented default for multi-org setups, indicating this is a realistic and easy-to-hit misconfiguration. Attacker cost is trivial: no Shipit credentials, no GitHub App keys, and no valid HMAC signature are needed once the blank-secret org is chosen; a single crafted HTTP POST suffices, and it is trivially scriptable/repeatable against any stack.

### Recommendation
Bind webhook signature verification to the same repository ownership actually used for the mutation. Concretely:
1. In `WebhooksController#verify_signature` and/or `Handler#stacks`, derive `repository_owner` from `repository.full_name`'s owner segment (not `repository.owner.login`) — or require both to match and reject (422) on mismatch before dispatching to handlers.
2. Do not allow `verify_webhook_signature` to silently return `true` for blank secrets in multi-org deployments; treat a blank `webhook_secret` for a configured org as an explicit "this org accepts unsigned/any webhook" state and disallow it from being used to authorize actions for a *different* org's resources — i.e., after determining `verified`, re-validate that `Repository.from_github_repo_name(repository_name).owner == repository_owner` before invoking handlers.

### Proof of Concept
Minitest plan (`test/controllers/webhooks_controller_test.rb`), using two configured orgs via `test/dummy/config/secrets_double_github_app.yml`-style fixtures, one with a secret and one blank:

```ruby
test "a blank-secret org cannot mutate another org's stack via full_name spoofing" do
  # Precondition: Shipit.github_config has 'VictimOrg' (webhook_secret set)
  # and 'AttackerOrg' (webhook_secret blank).
  victim_repo   = shipit_repositories(:victim_repo)      # owner: 'victimorg'
  victim_stack  = victim_repo.stacks.first

  request.headers['X-Github-Event'] = 'push'
  payload = {
    'repository' => { 'owner' => { 'login' => 'AttackerOrg' }, 'full_name' => victim_repo.github_repo_name },
    'ref' => "refs/heads/#{victim_stack.branch}",
    'after' => 'deadbeef'
  }.to_json

  # No X-Hub-Signature needed because AttackerOrg has a blank secret.
  assert_equal Shipit.github(organization: 'AttackerOrg').send(:webhook_secret), nil
  refute_equal 'AttackerOrg', Repository.from_github_repo_name(victim_repo.github_repo_name).owner

  assert_enqueued_with(job: GithubSyncJob, args: [stack_id: victim_stack.id, expected_head_sha: 'deadbeef']) do
    post :create, body: payload, as: :json
  end
  assert_response :ok  # proves victim's stack was mutated without VictimOrg's secret ever being checked
end
```
This asserts both sides of the broken binding explicitly: `Shipit.github(organization: repository_owner)` (AttackerOrg, blank secret, trivially "verified") vs. `Repository.from_github_repo_name(repository.full_name).owner` (VictimOrg) — showing they diverge yet the request still succeeds and mutates VictimOrg's stack.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
