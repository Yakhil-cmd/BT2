## Title
Scoped API token can read the CI status of any stack via `Api::CCMenuController` - unscoped `stack` lookup bypasses `stack_id` binding ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::ApiClient` can be scoped to a single stack via its `stack_id` column, and `Api::BaseController#stack` enforces this scope on every other API controller. `Api::CCMenuController` overrides `stack` to bypass that scoping entirely, breaking the binding "stack a token authorizes == stack the request touches."

### Finding Description
`Shipit::Api::BaseController` defines the standard, scope-respecting lookup used by every other API endpoint (stacks, tasks, deploys, etc.): [1](#0-0) 

`stacks` is filtered to `Stack.where(id: current_api_client.stack_id)` whenever the authenticated `ApiClient` is scoped (`stack_id?` true), and `stack` resolves the `:stack_id` request param only from within that filtered relation. This is exactly the mechanism that keeps a stack-scoped token from touching a different stack.

`Api::CCMenuController`, however, overrides `stack` to resolve directly against the global `Stack` relation, discarding the client's scope entirely: [2](#0-1) 

The only authorization check performed before `#show` runs is `require_permission :read, :stack`, which merely verifies the token carries the `read:stack` permission string: [3](#0-2) [4](#0-3) 

`ApiClient#check_permissions!` only checks whether `"read:stack"` is in the token's `permissions` array; it has no notion of which specific stack the token is bound to: [5](#0-4) 

So the equality that should hold — `stack a token is scoped to (client.stack_id)` == `stack the request actually reads (params[:stack_id])` — is broken specifically in `CCMenuController`. Every other controller inherits `BaseController#stack`/`#stacks` and enforces this equality; `CCMenuController` alone re-implements `stack` without the scope filter.

This is exactly the "SquidMulticall" bug-class analog required by the report: a caller holding a narrowly-scoped credential (approval bound to one target) can direct the privileged action (the multicall/API call) at an entirely different target (a different stack) because the code path that executes the action never re-checks the binding that was supposed to constrain it.

### Impact Explanation
Any holder of a valid, stack-scoped `ApiClient` token (e.g. a CI system or CCMenu integration issued a token restricted to stack A via `stack_id`) can supply an arbitrary `stack_id` in the request to `Api::CCMenuController#show` and read the CI/build status (last deploy status, label, activity, web URL) of any other stack in the installation, including stacks it was never authorized to see. This is an unauthorized read of stack state that escapes the deployment-trust binding intentionally enforced by `ApiClient.stack_id`. It matches the "High — unauthenticated/unauthorized read of stack state" impact category: the token is valid but never authorized for the stack actually disclosed.

### Likelihood Explanation
Exploitation only requires possession of any valid `ApiClient` token with `read:stack` permission (the minimal, most commonly issued scope — e.g. tokens created by `CCMenuUrlController#client` for the CCMenu integration use exactly `%w[read:stack]`, see `app/controllers/shipit/ccmenu_url_controller.rb`). No elevated privileges, GitHub access, or session are needed beyond the token itself, and the request is a simple authenticated GET with a different `stack_id` path parameter. Likelihood is high given how routinely `read:stack`-scoped tokens are minted for this exact controller.

### Recommendation
Remove the `stack` override in `Api::CCMenuController` and rely on the inherited, scope-respecting `BaseController#stack`/`#stacks` methods so that a stack-scoped `ApiClient` can only resolve stacks within `current_api_client.stack_id`. If the override exists for a functional reason (e.g., token authentication via `params[:token]` needing to run before scope filtering), keep the custom `authenticate_api_client` but delegate stack lookup back to `stacks.from_param!(params[:stack_id])`.

### Proof of Concept
1. Create (or obtain) two stacks, `stack_a` and `stack_b`.
2. Create an `ApiClient` scoped to `stack_a` (`stack_id: stack_a.id`, `permissions: ['read:stack']`) — this is exactly what `CCMenuUrlController#client` does for any authenticated user requesting a CCMenu URL for `stack_a`.
3. As the holder of that token, issue: `GET /api/<stack_b_owner>/<stack_b_repo>/<stack_b_env>/ccmenu.xml?token=<stack_a_scoped_token>` (per `app/controllers/shipit/api/ccmenu_controller.rb`, `authenticate_api_client` accepts the token via the `token` query param).
4. The response renders `stack_b`'s CI project status (`app/views/shipit/ccmenu/project`), even though the token was only ever authorized for `stack_a`, because `CCMenuController#stack` (`app/controllers/shipit/api/ccmenu_controller.rb:29-31`) resolves `Stack.from_param!` unscoped instead of via `stacks.from_param!` as `BaseController` does.
