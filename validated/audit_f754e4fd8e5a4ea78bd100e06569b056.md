### Title
Cross-repository commit-status collision toggles a victim `Stack`'s `ignore_ci` flag - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` resolves target commits with `Commit.where(sha: params.sha)` — a global, repository-unscoped query — instead of restricting to commits belonging to the repository that authenticated the webhook. Any commit-status webhook whose SHA collides with a commit tracked by an unrelated `Stack` will create a `Status` on that unrelated commit, whose `after_create :enable_ci_on_stack` callback unconditionally calls `commit.stack.enable_ci!`, flipping the victim `Stack#ignore_ci` from `true` to `false`.

### Finding Description
The broken binding: the code implicitly assumes `commit.stack.repository.full_name == payload['repository']['full_name']`, but nothing enforces this equality.

Path:
- `WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-49`) validates that the webhook's signature matches the GitHub App/organization derived from `params.dig('repository','owner','login')`. This proves the webhook genuinely originated from GitHub for the attacker's own organization/repository — it says nothing about which `Stack`/`Commit` rows the payload may affect.
- `StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`):
  ```
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
  ```
  This is a bare SHA lookup across the entire `commits` table, with no `stack_id`/`repository` filter. Notably, the base `Handler` class already provides a `stacks` helper (`app/models/shipit/webhooks/handlers/handler.rb:32-34`) that scopes work via `Repository.from_github_repo_name(repository_name)`; `StatusHandler` does not use it.
- `Commit#create_status_from_github!` → `statuses.replicate_from_github!` → `Status.create!` (`app/models/shipit/commit.rb:165-169`, `app/models/shipit/status.rb:23-33`).
- `Status` `after_create :enable_ci_on_stack` (`app/models/shipit/status.rb:18,38-40`) calls `commit.stack.enable_ci!` unconditionally on every new `Status`, regardless of which repository sent the webhook.

Exploit flow: an attacker owns/controls a GitHub repository (e.g., a fork of, or any repo sharing history/content with, the victim's tracked repository) and can legitimately push a commit whose SHA matches one already recorded in the victim `Stack`'s `commits` table (SHAs are content-addressed; identical trees/parents/author-committer timestamps yield identical SHAs — this routinely happens with forks, cherry-picks, or shared upstream commits referenced by multiple tracked repositories/stacks). The attacker then posts (or has GitHub post, via a genuine status update on their own repo/commit) a `status` webhook. `verify_signature` passes because the signature is valid for the attacker's own organization. `StatusHandler#process` finds the victim's `Commit` row (same SHA, different `stack_id`) via the unscoped `Commit.where(sha: ...)` query and creates a `Status` on it, triggering `enable_ci_on_stack` on the victim `Stack`.

None of the existing guards prevent this: `verify_signature` only authenticates *who sent* the webhook, not *which stack's data it is allowed to mutate*; `drop_unhandled_event` only filters unsupported event types; the `ExplicitParameters` schema for `StatusHandler` validates field shapes, not repository ownership; there is no `Repository`/`stacks` scoping check in `StatusHandler#process` at all.

### Impact Explanation
An attacker who controls any repository can flip `ignore_ci` (a CI-gating configuration flag) on an arbitrary victim `Stack` they do not operate and never configured, purely via SHA collision plus a status event on their own, unrelated repository. This is a cross-tenant configuration mutation matching the rules' Critical category ("a payload for one repository mutating another's stack"). Once `ignore_ci?` is `false→true`... actually the direction here is `true→false` (CI enforcement gets enabled where the operator hadn't turned it on), which changes deploy-gating behavior (`Commit#deployable?` at `app/models/shipit/commit.rb:227-229` depends on `stack.ignore_ci?`) — an unrequested change to gating behavior for the victim stack. Repeatable against any stack whose commit table contains a SHA the attacker can also reproduce/control in their own repository.

### Likelihood Explanation
Preconditions: victim `Stack.ignore_ci?` is `true` prior to attack (given), and a SHA collision must exist between a commit already tracked in the victim `Stack`'s `commits` table and a commit the attacker can trigger a status webhook for from their own repository. SHA collisions are not cryptographic breaks — they occur naturally through forks, shared upstream history, or cherry-picked commits with identical author/committer/timestamp/tree, which is a realistic and low-cost condition for an attacker who controls a fork of the victim's repository or shares commit history with it. No Shipit secrets, sessions, or privileged roles are required — the attacker only needs a GitHub repository of their own and the ability to trigger a normal status webhook, which is granted automatically by the webhook signature verification being scoped to organization identity rather than to the target `Stack`.

### Recommendation
Scope `StatusHandler#process` (and analogous handlers such as `CheckRunHandler`) to only touch commits belonging to the repository/stack that authenticated the webhook, e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` or joining through `Repository.from_github_repo_name(repository_name)` as the base `Handler#stacks` helper already does, instead of the global `Commit.where(sha: params.sha)`.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb (conceptual)
test "a status webhook for a colliding SHA on an unrelated repository enables CI on a victim stack" do
  victim_stack = shipit_stacks(:shipit) # repository: "shipit/shipit-engine", ignore_ci: true
  colliding_sha = "a" * 40

  victim_commit = victim_stack.commits.create!(sha: colliding_sha, message: "victim commit")
  assert_equal true, victim_stack.reload.ignore_ci?

  # Webhook payload authenticated for an entirely different repository the attacker owns
  attacker_payload = {
    'sha' => colliding_sha,
    'state' => 'success',
    'context' => 'ci',
    'repository' => { 'full_name' => 'attacker/unrelated-repo', 'owner' => { 'login' => 'attacker' } }
  }

  Shipit::Webhooks::Handlers::StatusHandler.call(attacker_payload)

  assert_equal false, victim_stack.reload.ignore_ci?
end
```

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)

        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
