Based on the investigation, the claimed binding break is real but requires a precondition beyond pure attacker control that the audit prompt understates.

### Title
Membership webhook writes `organization.login` from payload without validating it matches the signature-verifying org - (File: app/models/shipit/webhooks/handlers/membership_handler.rb)

### Summary
`WebhooksController#verify_signature` selects the `GitHubApp` to verify the signature using `repository.owner.login` (or `organization.login` as fallback) [1](#0-0) , while `MembershipHandler#find_or_create_team!` persists `team.organization = params.organization.login` read from the same unverified body [2](#0-1) . If `repository.owner.login` and `organization.login` differ, and the app selected via `repository.owner.login` has no `webhook_secret` configured (so `verify_webhook_signature` unconditionally returns `true`) [3](#0-2) , a `Team` row is created with an `organization` value that was never actually verified.

### Finding Description
The broken binding: `repository.owner.login` (read by `verify_signature` to pick the verifying `GitHubApp`) should equal `organization.login` (written by `find_or_create_team!` into `team.organization`), but nothing in the code enforces this. `WebhooksController#verify_signature` computes `github_app = Shipit.github(organization: repository_owner)` and calls `github_app.verify_webhook_signature(...)` [1](#0-0) . `repository_owner` falls back to `organization.login` only if `repository.owner.login` is absent [4](#0-3) ; when both are present, they are read independently and never cross-checked. `MembershipHandler` only requires `organization.login` in its params schema and uses it directly to set `team.organization` on first creation via `Team.find_or_create_by!(github_id: params.team.id)` [5](#0-4) .

`Shipit.github(organization:)` only returns a `GitHubApp` for organizations explicitly present in `secrets.github`; an unconfigured organization raises `GithubOrganizationUnknown` and the request is rejected with 422 [6](#0-5) . This means the attacker cannot pick an arbitrary `repository.owner.login` - it must be one of the organizations the Shipit operator has actually configured (e.g., `test/dummy/config/secrets_double_github_app.yml` shows a real multi-org config where one org, `OrgTwo`, has `webhook_secret: # nil`) [7](#0-6) . Only for an organization whose configured `webhook_secret` is blank does `verify_webhook_signature` return `true` regardless of the actual signature header, per `return true unless webhook_secret` [8](#0-7) .

Given such a misconfigured org exists (call it `attacker-org`), the attacker sends `POST /webhooks` with header `X-Github-Event: membership`, body `{"repository":{"owner":{"login":"attacker-org"}}, "organization":{"login":"victim-org"}, "team":{"id": <arbitrary>, "name":..., "slug":..., "url":...}, "member":{"login":"attacker-login"}, "action":"added"}`. `verify_signature` resolves `Shipit.github(organization: 'attacker-org')`, which returns `true` unconditionally (blank secret), so the request passes. `MembershipHandler` then runs `Team.find_or_create_by!(github_id: <arbitrary>) { |team| team.organization = 'victim-org' }`, creating a `Team` row falsely attributed to `victim-org`, and adds the attacker's GitHub login as a member of it [9](#0-8) .

Existing guards do not close this gap: `drop_unhandled_event` and `check_if_ping` are unrelated; `ExplicitParameters` schema for `MembershipHandler` only validates types/presence of `organization.login`, not its relationship to `repository.owner.login` [10](#0-9) ; `GithubOrganizationUnknown` handling only rejects truly unconfigured orgs, not mismatched-but-configured ones.

### Impact Explanation
The attacker can create arbitrary `Team` rows with a forged `organization` field belonging to a different (real) organization than the one that verified the request, and immediately add themselves as members via the same unverified request. If any team `handle` (`organization/slug`) matching this forged team is referenced by `Shipit.github_teams`/`oauth_teams` for OAuth authorization, the attacker's login becomes a member of a team that the app treats as belonging to `victim-org`, an escalation into the team-based authorization surface. This matches the High severity category "escalation into `Shipit.github_teams` authorization." The blast radius is bounded to organizations the Shipit installation configured with a blank `webhook_secret`; it is not exploitable against arbitrary internet-chosen organizations because `Shipit.github_app_config` rejects unknown organizations [11](#0-10) .

### Likelihood Explanation
Exploitation requires the Shipit operator to run in multi-organization mode (`secrets.github` keyed by org) and to have at least one configured organization with `webhook_secret` blank/absent - a real but non-default misconfiguration, documented as a valid state in `test/dummy/config/secrets_double_github_app.yml` [7](#0-6) . If that precondition holds, the attack costs a single unauthenticated POST, is fully repeatable, and requires no secrets - only knowledge of one configured (misconfigured) organization's login and any `victim-org` login string.

### Recommendation
In `MembershipHandler` (and any other handler that sets an `organization`/owner-derived field from the payload), require that `params.organization.login` (or the relevant owner field) matches the `repository_owner` value that `verify_signature` used to select the verifying `GitHubApp`, rejecting the request otherwise. Additionally, `WebhooksController#verify_signature` should reject requests where `repository.owner.login` and `organization.login` are both present but differ, closing the general class of cross-field trust splits.

### Proof of Concept
Minitest plan (`test/controllers/webhooks_controller_test.rb`-style, illustrative - actual file is out of scope per rules but demonstrates the equality check):
1. Configure two orgs in test secrets: `attacker-org` (webhook_secret: nil) and `victim-org` (webhook_secret: set).
2. `request.headers['X-Github-Event'] = 'membership'`.
3. `body = { action: 'added', team: { id: 999, name: 'Fake', slug: 'fake', url: 'https://x' }, organization: { login: 'victim-org' }, member: { login: 'attacker' }, repository: { owner: { login: 'attacker-org' } } }.to_json`.
4. `post :create, body:, as: :json`.
5. Assert `Shipit.github(organization: 'attacker-org').verify_webhook_signature(...)` returned `true` (blank secret) while `repository.owner.login == 'attacker-org' != organization.login == 'victim-org'`.
6. Assert `Team.find_by(github_id: 999, organization: 'victim-org').present?` and that its members include `User.find_by(login: 'attacker')`, proving a cross-organization write attributed to `victim-org` was persisted from a request verified only against `attacker-org`'s (blank) secret.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
