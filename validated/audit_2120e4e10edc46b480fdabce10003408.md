### Title
Deterministic same-MCI AA trigger ordering by DAG level/unit-hash enables MEV sandwich attacks against AMM-style Autonomous Agents - (File: main_chain.js, aa_composer.js)

### Summary
GMGN's incident involved MEV sandwich attacks: an adversary observes a pending user swap, then inserts a front-run and back-run trade around it to extract value from the price impact. ocore's Autonomous Agent (AA) engine has an analogous, protocol-level weakness: when multiple trigger units addressed to the same AA (e.g. an AMM/market-maker AA) become stable in the same main-chain index (MCI), they are executed in a **fully deterministic and attacker-influenceable order** based on `level` and `unit` hash rather than arrival/commitment order that is opaque to an attacker until finalization.

### Finding Description
When an MCI is stabilized, ocore collects all AA triggers that were included in units at that MCI and inserts them into `aa_triggers`, then later executes them in the order: [1](#0-0) 

and re-reads them for execution with: [2](#0-1) 

The sort key is `(mci, level, unit, address)`. `level` is the DAG level of the trigger unit, computed deterministically as `max(level of parents) + 1`, and `unit` is the unit hash. Both are known to the author of a unit at the moment they choose their parents and finalize their own content, and — critically — a would-be attacker can observe a **victim's unstable (not-yet-stable) trigger unit as soon as it is broadcast** (e.g. via `storage.assocUnstableUnits`/`assocUnstableMessages`, exposed to any full node) long before it becomes part of a stable MCI. Since a unit's `level` depends on which parents are chosen, an attacker can:
- Craft a "front-run" unit that does **not** include the victim's unit as an ancestor, keeping its `level` at or below the victim's, so it sorts before the victim's trigger in the deterministic order.
- Craft a "back-run" unit that **does** include the victim's unit as a parent, guaranteeing a strictly higher `level`, so it sorts after the victim's trigger.

Because AMM-style AAs price trades using the *current* pooled balances at execution time (e.g. the constant-product formula in the sample market-maker AA), an attacker who controls the pre- and post-execution order around a victim's swap can extract the victim's slippage exactly as in a classical sandwich attack: [3](#0-2) [4](#0-3) 

Note `balance[asset]`/`balance[base]` reflect AA state as of the moment each trigger actually executes, which is fully determined by the sort key above — not by fee bidding or private mempool protection, but by an openly inspectable and manipulable ordering rule.

### Impact Explanation
Any AA that behaves like an AMM or otherwise prices execution based on its live balance (a natural and encouraged design pattern per ocore's own sample AAs) is exposed to deterministic, reproducible sandwich attacks by any unprivileged unit poster who watches the DAG for profitable pending trigger units and races compatible parent sets. This causes concrete AA fund loss for the victim trader (excess slippage extracted by the attacker) each time it is exploited, and is systemic rather than a one-off bug, since the ordering key `(level, unit)` is deterministic and known/controllable at trigger-authoring time.

### Likelihood Explanation
Any full node (no special privilege) can observe unstable/pending units and their intended AA addresses, and only needs to be able to post two additional units with appropriate parent selection before the target MCI stabilizes. No cryptographic secrets, hub/peer privileges, or protocol violations are required — this is achievable purely through unit composition, i.e., exactly the capabilities available to a normal unit poster / AA trigger sender.

### Recommendation
For core-engine mitigations: consider randomizing or making unpredictable the tie-breaking/ordering key used for same-MCI AA triggers (e.g., derive order from information unknown to authors at composition time, such as a value only fixed at stabilization), or document and provide primitives (e.g., minimum-output / slippage-protection parameters, commit-reveal patterns) that AA authors can use to make execution order-independent. At minimum, ocore's AA documentation and sample AAs (like `uniswap_like_market_maker.oscript`) should be updated to warn that trigger execution order within an MCI is public and attacker-influenceable via `level`/`unit` ordering, and AMM-style AAs should implement price-impact/slippage bounds enforced in the trigger itself (e.g., `min_amount` checked against `$amount` and bounced otherwise) to blunt sandwich extraction.

### Proof of Concept
1. Attacker's node watches `storage.assocUnstableMessages` for a `payment` trigger unit `V` addressed to a known AMM AA (per `uniswap_like_market_maker.oscript`, case "exchange bytes to asset" / "exchange asset to bytes").
2. Attacker immediately composes trigger unit `F` (front-run: buy the same asset) selecting parents that do **not** descend from `V`, so `level(F) <= level(V)`, ensuring `F` sorts before `V` in `main_chain.js`'s `ORDER BY units.level, units.unit, address` once both stabilize in the same MCI.
3. Attacker composes trigger unit `B` (back-run: sell the asset back) that explicitly includes `V` (and possibly `F`) as a parent, guaranteeing `level(B) > level(V)`, so `B` executes after `V`.
4. Once the MCI stabilizes, `aa_composer.js`'s `handleAATriggers` executes `F`, then `V`, then `B` in that deterministic order — the AMM's `balance[$asset]`/`balance[base]` move against `V` between `F` and `B`, letting the attacker capture the price impact caused by the victim's own trade, mirroring the exact "sandwich attack" pattern in the GMGN report, adapted to ocore's deterministic DAG-based AA execution ordering.
