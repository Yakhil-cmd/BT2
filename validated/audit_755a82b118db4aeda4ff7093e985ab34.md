### Title
Webhook signature is verified against the organization named in the payload, but event handlers act on a different payload field (`repository.full_name`) — allowing cross-repository/cross-organization forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks which organization's `webhook_secret` to validate the incoming HMAC against using the `repository.owner.login` (or `organization.login`) field taken from the *same, unverified* JSON body. Once the signature checks out, every downstream `Shipit::Webhooks::Handlers::Handler` subclass resolves the target `Repository`/`Stack` from a *different* field of that same body, `repository.full_name`, without re-checking that its owner matches the organization whose secret produced the valid signature.

### Finding Description
`verify_signature` derives the org to authenticate against from attacker-supplied JSON before the signature has been checked: [1](#0-0) [2](#0-1) 

`GitHubApp#verify_webhook_signature` only proves the request was signed with *that organization's* secret; it says nothing about which repository the payload claims to describe: [3](#0-2) 

Every handler then derives the acted-upon repository from a sibling field of the same untrusted body, independent of `repository_owner`: [4](#0-3) 
For example, `PullRequest::OpenedHandler` resolves `Shipit::Repository.from_github_repo_name(params.repository.full_name)` and, if a matching stack/review-stack configuration exists, provisions a review stack, all driven by `params.repository.full_name`: [5](#0-4) 

Because Shipit supports multiple configured GitHub Apps/organizations (`Shipit.github(organization: ...)`, exercised by fixtures like `secrets_double_github_app.yml`), each organization has its own `webhook_secret`. The equality the code implicitly assumes but never enforces is:
`organization that produced a valid signature == owner of repository.full_name acted upon by the handler`.

An attacker who legitimately administers Organization A's GitHub App/webhook configuration in a shared Shipit deployment (and therefore legitimately knows Organization A's `webhook_secret`) can compute a valid `X-Hub-Signature` for a payload where `repository.owner.login` (or `organization.login`) is set to `"OrgA"` (so `verify_signature` selects and validates against OrgA's secret) while `repository.full_name` is set to `"OrgB/some-repo"` — a repository belonging to an entirely different organization/tenant of the same Shipit instance. The signature check passes, and the handler dispatch proceeds to act on `OrgB/some-repo`.

### Impact Explanation
This breaks the "organization that authenticated versus the repository that is written" trust boundary called out for this class of bug. Depending on which handler is targeted, this enables cross-tenant/cross-repository state changes without any legitimate access to the target repository: forged `membership` events create arbitrary `Team`/`User` records, `pull_request` events can provision review stacks or close/label PRs, `commit_status`/`check_suite` events can alter commit and merge status used to gate deploys, for a repository the attacker does not control. This matches the "cross-repository writes" Critical-impact criterion.

### Likelihood Explanation
Exploitability requires only that the attacker control (be an admin of) the webhook configuration for any one organization hosted on the shared Shipit instance — a routine, low-privilege scenario in multi-tenant Shipit deployments (many orgs sharing one instance) — combined with the ability to send an arbitrary HTTP POST to `/github/webhooks` with a self-crafted body and matching signature. No GitHub write access to the *target* repository, no Shipit session, and no API token are required.

### Recommendation
After signature verification succeeds for organization `O`, require that `repository.owner.login` (used for signature selection) equals the owner segment of `repository.full_name` (used for repository resolution) before dispatching to any handler; reject the webhook otherwise. Alternatively, resolve the target `Repository` first, look up its configured organization/secret, and use that single source of truth both for signature verification and for the object acted upon, instead of trusting two independent, unverified fields of the same payload.

### Proof of Concept
1. Attacker is an admin of `OrgA`'s GitHub App installation in a Shipit instance that also hosts `OrgB` (each configured with its own `webhook_secret` via `Shipit.github(organization:)`).
2. Attacker builds a JSON body for the `membership` (or `pull_request`) event with:
   - `organization.login` / `repository.owner.login` = `"OrgA"`
   - `repository.full_name` = `"OrgB/target-repo"`
3. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(OrgA_webhook_secret, body)` and POSTs to `/github/webhooks` with `X-Github-Event: membership` (or `pull_request`).
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: "OrgA")` and successfully verifies the signature against `OrgA`'s secret.
5. `Shipit::Webhooks.for_event('membership')` handlers execute using `repository.full_name = "OrgB/target-repo"`, mutating `OrgB`'s data (e.g., creating a `Team`/`User`, or provisioning/labeling a PR on `OrgB`'s repository) despite the attacker never having been granted access to `OrgB`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
