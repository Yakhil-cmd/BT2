### Title
Webhook signature verification selects the GitHub App/secret from the `repository.owner.login` field while stack resolution can use a different repository reference, allowing cross-organization writes in multi-org deployments - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` picks which per-organization webhook secret to validate a payload against using `repository_owner`, a value taken directly from the untrusted JSON body (`params.dig('repository', 'owner', 'login')` or the `organization.login` fallback). In Shipit's documented multi-GitHub-App deployment mode, each organization has its own distinct `webhook_secret`. An attacker who legitimately controls one configured organization's webhook secret can craft a payload whose `repository.owner.login` matches their own organization (so the HMAC check passes against their own known secret), while the actual repository/stack identifying fields consumed later by the event handlers point at a different, victim organization's repository.

### Finding Description
`Shipit.github(organization:)` resolves a distinct `GitHubApp` (and thus a distinct `webhook_secret`) per organization when the multi-app config schema is used: [1](#0-0) 

This is a first-class, documented deployment mode (`docs/setup.md`, "Using Multiple Github Applications"), not an unsupported configuration: [2](#0-1) 

`WebhooksController` determines *which* organization's secret to verify the signature against purely from the JSON payload itself, before any handler validates that the claimed owner is consistent with the rest of the payload: [3](#0-2) 

The binding that should hold is:
`organization whose secret authenticated the HMAC` == `organization/repository that Shipit's event handlers act on`.

Because `repository_owner` is read from the same JSON body that a webhook-secret-holder fully controls, and the HMAC only proves "this body was signed by *some* configured organization's secret," nothing in `verify_signature` cross-checks that the `repository.full_name` (or other repository-identifying fields consumed downstream by `Shipit::Webhooks::Handlers::*`, e.g. `PushHandler`, `StatusHandler`, `CheckSuiteHandler`) actually belongs to the same organization named in `repository.owner.login`. An organization-B webhook-secret holder can therefore sign a payload where `repository.owner.login == "org-b"` (satisfying signature verification against org B's secret) while `repository.full_name` (or equivalent fields used by the handler to locate the `Repository`/`Stack` record) references `"org-a/some-repo"`.

I was not able to retrieve the exact body of `app/models/shipit/webhooks/handlers/push_handler.rb` / `status_handler.rb` / `handler.rb` in this session (tool calls for those files failed), so I could not pin the exact line(s) that resolve the target `Stack`/`Repository` from `full_name` independent of `owner.login`. `grep_search` did confirm `full_name` is referenced in `app/models/shipit/repository.rb` and once in `app/models/shipit/webhooks/handlers/handler.rb`, consistent with stack/repository lookup being keyed off `full_name` rather than `owner.login`, but this specific coupling should be re-verified against the handler source before treating this as fully proven.

### Impact Explanation
If the decoupling described above is confirmed in the handler code, this breaks the "organization that authenticated versus the repository that is written" binding called out in scope: a party who only controls one org's webhook secret in a multi-tenant Shipit instance could forge push/status/check_suite events that are attributed to and processed against a different organization's repository/stack (e.g., marking commits as CI-passing/failing, updating check-run/commit-status state, or affecting continuous-deployment eligibility for a repository outside their control) — a cross-repository/cross-organization write, which maps to the Critical impact bucket ("cross-repository writes, or an unauthorized deploy, rollback or merge") if it can influence commit statuses gating deploys.

### Likelihood Explanation
This only manifests in the documented multi-GitHub-App configuration, and requires the attacker to already control the webhook secret of at least one organization onboarded to the shared Shipit instance — a non-privileged-but-non-trivial precondition (they must be an org whose GitHub App is legitimately configured on this Shipit instance). Given this precondition, forging the payload itself is straightforward since HMAC-SHA1 signing only requires knowledge of that org's own secret.

### Recommendation
In `WebhooksController#verify_signature` / the individual `Shipit::Webhooks::Handlers`, cross-check that the organization used to select the verifying secret (`repository.owner.login` / `organization.login`) matches the organization embedded in every other repository-identifying field consumed by the handler (e.g., `repository.full_name`'s owner segment) before acting on the event, rejecting mismatches with `422`.

### Proof of Concept
Conceptual PoC (pending confirmation of exact handler code):
1. Deploy Shipit with the multi-org config (`config/secrets.yml` → `github: { org-a: {...}, org-b: {...} }`), each with its own `webhook_secret`.
2. As the operator/holder of `org-b`'s webhook secret, POST to `/webhooks` a `push` (or `status`/`check_suite`) event with:
   - `repository.owner.login = "org-b"`
   - `repository.full_name = "org-a/victim-repo"` (or whatever field the specific handler uses to resolve the target `Repository`/`Stack`)
   - Signed with `org-b`'s `webhook_secret` via `X-Hub-Signature`.
3. `verify_signature` computes `repository_owner = "org-b"`, calls `Shipit.github(organization: "org-b")`, and the HMAC check succeeds because it was legitimately signed with org B's secret.
4. The corresponding handler processes the event using `repository.full_name`, acting on `org-a/victim-repo`'s `Stack`/`Repository` despite the request never being authenticated as `org-a`.

Because I could not confirm the exact handler code in this session, this should be validated against `app/models/shipit/webhooks/handlers/push_handler.rb`, `status_handler.rb`, and `handler.rb` (specifically how they resolve the target `Repository`/`Stack`) before treating the PoC as conclusively reproducible.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently.     def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping
      head(:ok) if event == 'ping'
    end

    def event
      request.headers.fetch('X-Github-Event')
    end

    def repository_owner
      # Fallback to the organization sub-object if repository isn't included in the payload
      params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
    end
