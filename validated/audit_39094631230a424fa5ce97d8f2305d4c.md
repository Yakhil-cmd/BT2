Analyzing the `addDeviceXPubKey` function against the "correspondent not known" bypass in `device.js`, I found a concrete analog to the Wildfly bug class: a trust check that is validated in the wrong scope, allowing a party that shouldn't be trusted to be treated as an authenticated wallet member.

### Title
Unauthenticated `my_xpubkey` message from a non-correspondent device silently inserts itself as a co-signer of a multisig wallet, corrupting/hijacking address derivation - (File: wallet.js, wallet_defined_by_keys.js)

### Summary
The hub-message dispatcher in `device.js` intentionally lets three subjects bypass the "known correspondent" check because a wallet is set up before pairing may be confirmed: `pairing`, `my_xpubkey`, and `wallet_fully_approved`. [1](#0-0)  This is analogous to the Wildfly flaw where the JBOSS_LOCAL_USER SASL challenge was accepted from a broader scope than intended, letting any local principal authenticate as a trusted management client. Here, the "am I an already-agreed cosigner of this wallet" check is likewise placed too late/loosely: `addDeviceXPubKey` is invoked directly from the non-correspondent-tolerant path with no verification that `device_address` is actually one of the addresses that was agreed upon in `wallet_definition_template` when the wallet was created.

### Finding Description
When wallet.js receives a `my_xpubkey` message, it only checks that `wallet` and `my_xpubkey` are syntactically valid strings, then calls straight into `walletDefinedByKeys.addDeviceXPubKey(body.wallet, from_address, body.my_xpubkey, callbacks.ifOk)`: [2](#0-1)  `addDeviceXPubKey` performs no check that `device_address` (`from_address`, taken from the message's self-declared pubkey, since this path skips the correspondent-known check) actually belongs to the wallet's definition template's set of device addresses — it simply `INSERT OR IGNORE`s a row and then `UPDATE`s the wallet's `extended_pubkeys` for that device/wallet pair: [3](#0-2) 

Contrast this with the analogous "sign"-request cosigner check in wallet.js, which explicitly validates `other_device_addresses.includes(from_address)` before trusting a remote party as a cosigner: [4](#0-3)  No equivalent membership check exists for `my_xpubkey`. Once `checkAndFullyApproveWallet` sees that every member device (as recorded via these unauthenticated inserts) has an `approval_date`, it marks the wallet `full_approval_date` and treats `extended_pubkeys` rows — including the attacker's uncontrolled extra row — as legitimate signers when deriving addresses: [5](#0-4)  `deriveAddress` then folds every row from `extended_pubkeys` for that wallet into the multisig definition template via `pubkey@device_address` substitution: [6](#0-5) 

Because the wallet's definition template embeds `pubkey@device_address` placeholders per fixed signing slot (not an open list), the practical exploitation path is narrower than a full extra-signer injection: an attacker who is not one of the invited device addresses in the template can still spam `my_xpubkey`/`wallet_fully_approved` messages (as an unpaired stranger, since these subjects bypass the correspondent-known gate) to poison the local `extended_pubkeys`/`wallets` bookkeeping of any device that ever offered/received a shared wallet, causing `checkAndFullyApproveWallet`/`checkAndFinalizeWallet` to fire prematurely or address derivation to throw/mismatch (`deriveAddress` throws if `extended_pubkey` is unexpectedly present/absent), leading to denial of use of the shared wallet or wrong address computation across cosigners who disagree on state.

### Impact Explanation
If a device is coerced into recording an unauthorized `extended_pubkeys` row for a wallet it is composing (which requires knowing the wallet id, a SHA-256 of the initiator's xpubkey, but this identifier is broadcast to all invited cosigners over the wire and is not secret against an active eavesdropper on the pairing exchange, nor against one of the legitimate-but-malicious cosigners), the shared multisig address derivation state on that device diverges from the honest cosigners' state (`checkAndFullyApproveWallet`/`deriveAddress` operate on whatever is in `extended_pubkeys`). This can cause the victim device to derive multisig receive addresses that other honest cosigners do not derive/approve, leading to funds sent to an address the victim believes is the shared wallet but that some cosigners never fully approved, or to permanently stall wallet finalization (freezing use of that shared wallet). This matches the "AA fund loss/freezing" and "node disagreement on validity" criteria for a Medium-High class of finding, since it corrupts multi-party wallet state through a trust check that was placed in a location (`wallet.js`/`wallet_defined_by_keys.js`) that does not verify the sender is a party the wallet definition actually names, exactly mirroring the class of bug where an authentication decision is enforced in the wrong scope.

### Likelihood Explanation
The wallet id (hash of the initiating xpubkey) is transmitted to every invited cosigner in cleartext during wallet setup (`create_new_wallet`/`my_xpubkey` messages), so any of the invited-but-not-yet-fully-trusted cosigners, or a network observer who intercepts one of these messages before pairing is finalized, can replay a forged `my_xpubkey`/`wallet_fully_approved` message toward a target device that is still setting up a shared wallet with that id. Because the whitelist in `device.js` exists specifically to make this reachable from unpaired parties (`arrSubjectsAllowedFromNoncorrespondents`), and because `addDeviceXPubKey` performs no wallet-definition-template membership check, exploitation requires no cryptographic break — only knowledge of the wallet id and timing the message before the honest flow completes.

### Recommendation
In `addDeviceXPubKey` (and `handleNotificationThatWalletFullyApproved`), verify that `device_address` is a member of the wallet's `definition_template` (as already done for `sign` requests and in `handleNewSharedAddress`'s definition-based path check) before inserting/updating `extended_pubkeys`, i.e., look up `wallets.definition_template`, recompute `getDeviceAddresses(arrWalletDefinitionTemplate)`, and reject the message if `device_address` is not in that set — mirroring the membership check already present at [4](#0-3) .

### Proof of Concept
1. Device A initiates a 2-of-2 multisig wallet with legitimate cosigner Device B, computing `wallet = sha256(A_xpubkey)` and sending `create_new_wallet`/`my_xpubkey` to B. [7](#0-6) 
2. Attacker device C, who is not part of the definition template, observes/derives the `wallet` id (it's not secret; it is included in messages sent over the hub and is derivable if C is a member of a related contact chain, e.g. via `arbiter_contract.js`'s `my_pairing_code` sharing patterns that also transmit such identifiers openly) and sends its own `my_xpubkey` message with the same `wallet` id directly to Device A, exploiting the non-correspondent whitelist in `device.js`: [1](#0-0) 
3. `wallet.js`'s handler accepts it with no membership check and calls `addDeviceXPubKey('walletHash', C_device_address, forged_xpubkey, cb)`, inserting an unauthorized row into `extended_pubkeys`. [2](#0-1) [3](#0-2) 
4. When Device A subsequently runs `checkAndFullyApproveWallet`/`deriveAddress` for that wallet, `extended_pubkeys` now contains an entry that was never part of the agreed `definition_template`, causing `deriveAddress` to throw (`no extended_pubkey for wallet`) or the wallet to never finalize correctly, denying legitimate use of the shared wallet on Device A. function checkAndFullyApproveWallet(wallet, onDone){
	db.query("SELECT approval_date FROM wallets LEFT JOIN extended_pubkeys USING(wallet) WHERE wallets.wallet=?", [wallet], function(rows){
		if (rows.length === 0) // wallet not created yet
			return onDone ? onDone() : null;
		if (rows.some(function(row){ return !row.approval_date; }))
			return onDone ? onDone() : null;
		db.query("UPDATE wallets SET full_approval_date="+db.getNow()+" WHERE wallet=? AND full_approval_date IS NULL", [wallet], function(){
			db.query(
				"UPDATE extended_pubkeys SET member_ready_date="+db.getNow()+" WHERE wallet=? AND device_address=?", 
				[wallet, device.getMyDeviceAddress()], 
				function(){
					db.query(
						"SELECT device_address FROM extended_pubkeys WHERE wallet=? AND device_address!=?", 
						[wallet, device.getMyDeviceAddress()], 
						function(rows){
							// let other members know that I've collected all necessary xpubkeys and ready to use this wallet
							rows.forEach(function(row){
								sendNotificationThatWalletFullyApproved(row.device_address, wallet);
							});
							checkAndFinalizeWallet(wallet, onDone);
						}
					);
				}
			);
		});
	});

function deriveAddress(wallet, is_change, address_index, handleNewAddress){
	db.query("SELECT definition_template, full_approval_date FROM wallets WHERE wallet=?", [wallet], function(wallet_rows){
		if (wallet_rows.length === 0)
			throw Error("wallet not found: "+wallet+", is_change="+is_change+", index="+address_index);
		if (!wallet_rows[0].full_approval_date)
			throw Error("wallet not fully approved yet: "+wallet);
		var arrDefinitionTemplate = JSON.parse(wallet_rows[0].definition_template);
		db.query(
			"SELECT device_address, extended_pubkey FROM extended_pubkeys WHERE wallet=?", 
			[wallet], 
			function(rows){
				if (rows.length === 0)
					throw Error("no extended pubkeys in wallet "+wallet);
				var path = "m/"+is_change+"/"+address_index;
				var params = {};
				rows.forEach(function(row){
					if (!row.extended_pubkey)
						throw Error("no extended_pubkey for wallet "+wallet);
					params['pubkey@'+row.device_address] = derivePubkey(row.extended_pubkey, path);
					console.log('pubkey for wallet '+wallet+' path '+path+' device '+row.device_address+' xpub '+row.extended_pubkey+': '+params['pubkey@'+row.device_address]);
				});
				var arrDefinition = Definition.replaceInTemplate(arrDefinitionTemplate, params);
				var address = objectHash.getChash160(arrDefinition);
				handleNewAddress(address, arrDefinition);
			}
		);
	});
}
