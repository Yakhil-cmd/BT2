### Title
`gh skill install --force` silently overwrites a pinned skill with an unpinned (attacker-controlled) version, bypassing the pin invariant enforced elsewhere - ([File: pkg/cmd/skills/install/install.go])

### Summary
The bug class in the report is a state invariant ("locked" balance) that is correctly enforced on one code path but silently reset/bypassed via a second, different call path. The `gh skill` subsystem has the same shape: `gh skill update` treats a `--pin`'d skill as immutable and refuses to touch it unless `--unpin` is explicitly passed, but `gh skill install --force` reinstalls into the exact same directory without ever checking whether the existing skill is pinned, silently replacing pinned (trusted) content with whatever the repository currently serves.

### Finding Description
`gh skill update` explicitly protects pinned skills: an installed skill with a non-empty `pinned` field is skipped unless `--unpin` is supplied. [1](#0-0) 

Contrast this with the overwrite check used by `gh skill install`. `checkOverwrite` only looks at whether the target directory already exists on disk and whether `--force` was passed — it never reads the existing `SKILL.md` frontmatter to determine if the currently-installed copy was `--pin`'d to a specific ref: [2](#0-1) 

`installRun` resolves a version via `resolveVersion`, which defaults to the latest tagged release or branch HEAD when no `--pin`/`@version` is supplied, then calls `installer.Install` with the freshly-resolved `SHA`/`Ref`, without consulting the previously stored `PinnedRef`: [3](#0-2) [4](#0-3) 

So, a user who previously ran `gh skill install owner/repo skill --pin v1.0.0` to lock the content to a known-good, reviewed release, and later re-runs `gh skill install owner/repo skill --force` (e.g., to fix a corrupted local copy, or via an agent-driven self-management loop as documented in the skill's own `SKILL.md`) will have the pinned content silently replaced by whatever `owner/repo` currently serves on its default branch/latest tag — with no warning that a pin is being broken. This is the same root-cause shape as the PoolTogether bug: an invariant ("this asset is locked/pinned and must not change without explicit unlock/unpin") is enforced through one API but is bypassable through a sibling API that mutates the same underlying state without checking it.

The `SKILL.md` for the `gh-skill` skill itself documents an agent self-management loop that periodically calls `gh skill update --all` and installs with `--pin` for reproducibility, but also documents plain reinstall/`--force` flows, making this a realistic operational pattern for autonomous agents: [5](#0-4) 

### Impact Explanation
Skills installed via `gh skill install` are Markdown instruction files (`SKILL.md`, plus optional scripts) that are directly consumed and acted upon by AI coding agents (Copilot, Claude Code, Cursor, etc.). If a user or agent pins a skill specifically to avoid picking up untrusted/unreviewed future changes from the source repository, a subsequent `--force` reinstall silently discards that safety boundary and pulls whatever content the repository maintainer (or an attacker who has since compromised that repository/account) currently publishes. Because skills can include executable scripts and are designed to be acted upon autonomously by an agent, this can lead to execution of attacker-controlled instructions/scripts under the guise of a "trusted, pinned" skill — the same "confirm no pin, then honor it" contract used by `update` is not honored by `install`.

### Likelihood Explanation
This does not require any privilege escalation or MITM: a normal, unprivileged user (or an agent running `gh` commands on the user's behalf) simply needs to run `gh skill install <repo> <skill> --force` a second time without repeating `--pin`. This is a plausible, even encouraged, workflow (fixing/reinstalling a broken skill, "self-management" loops documented in `skills/gh-skill/SKILL.md`), and there is no confirmation prompt, warning, or error analogous to the one `update` produces ("... is pinned to ... (skipped)").

### Recommendation
In `checkOverwrite` (or `installRun` before calling `installer.Install`), read the existing skill's frontmatter (as `existingSkillPrompt` already does) and detect a `github-pinned` value. If present and the new install does not supply a matching `--pin`, refuse the overwrite (mirroring `update`'s pinned-skip behavior) unless the user passes an explicit override flag (e.g., `--unpin`, consistent with `gh skill update`), and clearly warn when a pin is about to be dropped.

### Proof of Concept
```bash
# Attacker controls or later compromises owner/repo, or simply pushes a new
# release/commit to the default branch/tag after the user pinned a known-good version.

# 1. User pins to a reviewed, known-good version.
gh skill install owner/repo my-skill --pin v1.0.0

# 2. Attacker updates owner/repo's default branch / latest tag with malicious
#    SKILL.md content / scripts.

# 3. User (or an autonomous agent) later re-installs to fix a local issue,
#    forgetting (or not knowing it's required) to repeat --pin:
gh skill install owner/repo my-skill --force

# Result: checkOverwrite() only checks `opts.Force` and directory existence
# (pkg/cmd/skills/install/install.go:1045-1062); it never inspects the
# existing "github-pinned" frontmatter. The pinned v1.0.0 content is
# silently replaced with the attacker's current (unpinned, unreviewed)
# content, with no warning that the pin was broken.
```

```go
func checkOverwrite(opts *InstallOptions, skills []discovery.Skill, targetDir string, canPrompt bool) ([]discovery.Skill, error) {
	var existing, fresh []discovery.Skill
	for _, s := range skills {
		dir := filepath.Join(targetDir, s.Name)
		if _, err := os.Stat(dir); err == nil {
			existing = append(existing, s)
		} else {
			fresh = append(fresh, s)
		}
	}

	if len(existing) == 0 {
		return skills, nil
	}

	if opts.Force {
		return skills, nil
	}
```
