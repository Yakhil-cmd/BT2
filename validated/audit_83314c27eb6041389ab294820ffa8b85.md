### Title
Webhook authentication bypass via unauthenticated organization field breaks the "authenticated organization ↔ repository/commit written" binding, enabling cross-repository status/membership forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController` selects which GitHub App/organization's `webhook_secret` to verify a payload against by reading an **unauthenticated field of the very payload it is about to verify**, and `GitHubApp#verify_webhook_signature` unconditionally trusts any request when that organization's `webhook_secret` is blank. Because several webhook handlers (`StatusHandler` in particular) never re-validate that the object they mutate actually belongs to the organization/repository that was used for signature verification, an unprivileged attacker who controls (or merely names) any Shipit-configured GitHub organization with no `webhook_secret` set can forge arbitrary `status`, `membership`, `push`, `check_suite`, etc. events targeting commits/stacks belonging to completely unrelated organizations.

### Finding Description
`WebhooksController#verify_signature` picks the GitHub App/secret to validate against using a field taken from the raw, not-yet-verified JSON body: [1](#0-0) [2](#0-1) 

`repository_owner` is `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` - both attacker-controlled at this point, since nothing has been verified yet.

`GitHubApp#verify_webhook_signature` then does: [3](#0-2) 

`return true unless webhook_secret` means that for any configured organization whose `webhook_secret` is blank/nil (an explicitly supported configuration, e.g. `OrgTwo` in the test fixture below), **signature verification is a no-op** and the request is treated as fully authenticated: [4](#0-3) 

Once "verified" this way, `WebhooksController#create` dispatches the raw, attacker-supplied JSON to the registered handlers: [5](#0-4) 

Handlers determine *what data to mutate* using other, independent fields of the same attacker-controlled payload, with no cross-check against the organization used during signature verification. `StatusHandler` is the worst case - it does not even scope by repository, only by commit `sha`, which is public information for any tracked repository: [6](#0-5) 

`MembershipHandler` similarly trusts the payload's `organization.login`/`team`/`member.login` fields to add arbitrary users to arbitrary teams: [7](#0-6) 

This breaks the required binding: **organization that authenticated (via `repository_owner`/blank-secret bypass) ≠ repository/commit/team that is actually written** (via `repository.full_name`, `sha`, `organization.login`, `team.id`, `member.login`).

### Impact Explanation
- Forging a `status` event with `state: "success"` for an arbitrary commit `sha` belonging to a stack the attacker has no relationship to can flip `Commit#deployable?` to `true` (via `success?`/CI-state logic), enabling an **unauthorized deploy** of a commit that never actually passed CI - Critical impact per program scope.
- Forging a `membership` `added` event lets an attacker add an arbitrary `User` (including their own GitHub login) to any `Team`, including one listed in `Shipit.github_teams`, directly achieving **escalation into `Shipit.github_teams` authorization** - High impact per program scope.
- Forging `push`/`check_suite` events can trigger `GithubSyncJob`/`RefreshCheckRunsJob` for arbitrary stacks, causing spurious syncs/state changes for repositories unrelated to the organization that was "authenticated."

### Likelihood Explanation
The only precondition is that the Shipit deployment has at least one configured GitHub organization/App with a blank `webhook_secret` (an explicitly supported, documented configuration shape, as shown in the engine's own multi-app fixture). No token, session, or prior repository access is required - the attacker only needs to know (or guess/enumerate) that organization's login and send a raw HTTP POST with a crafted JSON body to the public `/webhooks` endpoint.

### Recommendation
- Never derive the verification key from unauthenticated payload data without re-validating downstream that the object being mutated actually belongs to that authenticated organization/repository.
- Require every configured GitHub App/organization to have a non-blank `webhook_secret`; fail closed (`head(422)`) instead of returning `true` when `webhook_secret` is blank in `GitHubApp#verify_webhook_signature`.
- In every handler (especially `StatusHandler`), scope lookups by the verified/authenticated organization and by `repository.full_name`, not solely by attacker-suppliable identifiers such as `sha`.

### Proof of Concept
1. Ensure/observe a Shipit instance configured with two organizations, where one (`OrgTwo`) has no `webhook_secret` (matches the engine's own supported config format).
2. Attacker sends:
```
POST /webhooks
X-Github-Event: status
X-Hub-Signature: sha1=anything   (ignored, since OrgTwo has no webhook_secret)

{
  "repository": {"owner": {"login": "OrgTwo"}},
  "sha": "<public sha of a commit belonging to victim stack in OrgOne>",
  "state": "success",
  "context": "ci/forged"
}
```
3. `verify_signature` resolves `Shipit.github(organization: "OrgTwo")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` regardless of the signature header.
4. `StatusHandler#process` runs `Commit.where(sha: params.sha)` - matching the victim's commit in a completely unrelated stack - and calls `create_status_from_github!`, marking it "success" and potentially making it deployable. [6](#0-5)

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
