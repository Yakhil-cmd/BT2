## Title
Underpriced complexity charge for `map`/`filter`/`reduce`/`foreach` when the callback has zero complexity - ([File: formula/validation.js])

### Summary
The reported Stylus bug shows that when a WASM opcode's cost calculation is delegated to a separate pricing subsystem (the "memory pricer"), and that subsystem's precondition doesn't hold (no `pay_func` import / fixed memory), the opcode falls back to a flat, unrepresentative cost of `1`, decoupled from the actual amount of work performed. The same pattern exists in ocore's formula (oscript) complexity accounting for the `map`/`filter`/`reduce`/`foreach` iteration constructs: the per-iteration cost is normally scaled by the iteration count, but there is a fallback branch that charges a flat `1` regardless of how many iterations actually occur.

### Finding Description
In `formula/validation.js`, the cost of iterator opcodes (`map`, `filter`, `reduce`, `foreach`) is computed as: [1](#0-0) 

```
complexity += (funcProps.complexity === 0) ? 1 : count * funcProps.complexity;
count_ops += count * funcProps.count_ops;
```

This is directly analogous to the reported bug: the "correctly scaled" cost path is `count * funcProps.complexity` (comparable to the WASM "memory pricer" that correctly charges based on actual memory delta). But when the callback function itself has `complexity === 0` — which is a normal, reachable state for a callback that only performs field reads/simple assignments and no further formula/getter calls, as demonstrated by the test showing `props: { complexity: 0, count_ops: 3, count_args: 1 }` for `$f = ($x)=>{ $x.b=9; $x }` [2](#0-1)  — the code takes the "fixed memory"-equivalent fallback path and charges a constant `1` regardless of `count`, exactly like `MemoryGrow`'s fallback ink cost of `1` regardless of actual cost.

This is reachable by any unprivileged AA author: an AA's `init`/`state`/message formulas are validated through `validateFormula` in `aa_validation.js`, which enforces `constants.MAX_COMPLEXITY` and `constants.MAX_OPS` bounds computed from these same `complexity`/`count_ops` counters [3](#0-2) . An attacker-controlled formula in an AA definition can therefore under-report `complexity` for large-count iteration constructs while `count_ops` is still properly scaled (`count * funcProps.count_ops`), meaning the `complexity` accounting (used to gate remote/nested calls and cross-AA cost propagation, e.g. `remote_func_call` and `readFuncProps`'s remote-func complexity math at [4](#0-3) ) becomes decoupled from the real amount of computation actually charged/limited.

### Impact Explanation
`complexity` is the accounting unit used to bound both direct AA formula execution and, more importantly, chained/remote AA calls across the network (`remote_func_call` propagates `complexity`, not `count_ops`, when computing conservative caps, e.g. `complexity += max_remote_complexity + 1`). Because the fallback branch pins per-iteration complexity to a flat `1` irrespective of `count`, an attacker can craft AAs whose formulas execute proportionally more real work (bounded ops still capped by `MAX_OPS=2000`) while reporting artificially low aggregate `complexity`. Any downstream logic keying off of `complexity` as a proxy for "how much work/validator resource this AA invocation consumes" (rather than `count_ops`) under-estimates true cost for AAs using this pattern, which is the same underlying failure mode as the report: the cost of an opcode/operation degenerates to a fixed minimum instead of one proportional to the actual work performed, for a specific, reachable code path (an unprivileged AA author can trivially write a zero-complexity callback).

### Likelihood Explanation
Reaching the vulnerable path requires nothing more than posting a valid AA definition with a `map`/`filter`/`reduce`/`foreach` construct whose callback has `complexity === 0` (e.g. a callback that only accesses/copies data without further getter/remote calls, string ops, or other complexity-incrementing constructs) — a pattern directly demonstrated in the existing test suite [2](#0-1) . This makes the trigger condition easy to hit for any AA author, with no special privilege required.

### Recommendation
- **Short term:** Remove the special-case fallback and always scale complexity by `count` for iterator opcodes: `complexity += count * funcProps.complexity` (with a minimum floor added separately, e.g. `Math.max(1, count) * Math.max(1, funcProps.complexity)` or an explicit small per-iteration base charge), so complexity is never decoupled from the actual number of iterations.
- **Long term:** Audit all places in `formula/validation.js` / `formula/evaluation.js` where a cost/complexity charge falls back to a fixed constant instead of being derived from the size of the input (arrays, strings, objects) to ensure no opcode's charged complexity can be driven arbitrarily below its `count_ops` — and add fuzz/property tests asserting `complexity` is monotonic non-decreasing in `count` for these constructs.

### Proof of Concept
```
$f = ($x) => { $x.b = 9; $x };   // funcProps.complexity === 0, count_ops === 3
$big_array = <array with N elements, N up to MAX_OPS / count_ops(f)>;
map($big_array, N, $f);
```
Per `formula/validation.js:1030`, regardless of `N`, this expression contributes only `complexity += 1`, while `count_ops` scales properly with `N`. This lets an AA author submit iteration-heavy formulas whose reported `complexity` stays minimal (`1`) even as `N` approaches the `MAX_OPS` ceiling, decoupling the `complexity` metric from real work — mirroring the underpriced `MemoryGrow` fallback in the referenced report.

**Note on confidence:** I could not fully verify from the indexed code how `complexity` (as opposed to `count_ops`) is used elsewhere at runtime to bound actual validator resource consumption beyond formula/AA validation and remote-call chaining shown above (e.g., whether it feeds into any fee/ink-like charge to the trigger sender). I was unable to locate the definition of `constants.MAX_COMPLEXITY` itself in the indexed content (only `constants.js` was found to reference it once, but its exact value wasn't returned by the search). A Devin session with full repository access would allow confirming the exact numeric limits and whether `complexity` maps to any spendable/fee-bearing resource beyond validation gating.
