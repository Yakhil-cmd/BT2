### Title
Stale delegate authorization reactivates after position-NFT ownership round-trip - (File: contracts/controller/src/storage/account.rs)

### Summary
Account delegates are keyed to the address recorded as `granted_by`, while account ownership is resolved dynamically from the position NFT. Transferring the NFT to another owner makes the old grant unusable, but does not delete it. If the NFT later returns to the original owner, the stale grant becomes valid again without a new `add_delegate` call. An authorized active position manager can then borrow or withdraw the returned account’s assets.

### Finding Description
`try_account_owner` resolves the current account owner dynamically from the position NFT rather than from persistent controller state. [1](#0-0) 

`get_delegates` returns a stored delegate list whenever its `granted_by` field equals the current NFT owner. [2](#0-1) 

`is_owner_or_delegate` accepts a caller when that caller is an active position manager and is contained in the list stamped by the current owner. [3](#0-2) 

The stale-grant cleanup only runs when a different current owner explicitly calls `remove_delegate`; merely transferring the NFT does not remove the prior grant. [4](#0-3) 

Consequently, a grant from owner `A` persists across `A -> B -> A` ownership. When the account returns to `A`, the stored `granted_by == A` predicate again matches, restoring the delegate’s authority without fresh authorization.

### Impact Explanation
The reactivated delegate can act as an account owner or delegate in privileged position flows. `borrow` authorizes against `account.owner` and can pay proceeds to an attacker-selected `to` address. [5](#0-4) 

Likewise, `withdraw` uses the same authorization check and permits an arbitrary external recipient through `to`. [6](#0-5) 

This allows theft of withdrawable collateral and creation of debt paid directly to the stale delegate, up to the account’s collateral and market limits.

### Likelihood Explanation
The exploit requires the original owner to have previously delegated an active position manager and then transferred the position NFT away, for example through a sale, migration, custody transfer, or wallet-management flow. The recipient can return the NFT through the normal position-NFT transfer path, after which no owner action is needed to restore the old grant.

The issue is exploitable entirely by unprivileged addresses because both NFT transfers and the subsequent controller `borrow`/`withdraw` calls are user-reachable entrypoints. The main prerequisite is a pre-existing delegation and an NFT ownership round-trip.

### Recommendation
Invalidate delegate grants by an explicit ownership epoch or NFT owner snapshot rather than only the owner address. For example, store an `owner_epoch` or transfer-generation value in `DelegateGrant`, increment it on every position-NFT ownership change, and require `grant.owner_epoch == current_epoch`.

Alternatively, add a controller callback/transfer hook that clears `ControllerKey::Delegates(account_id)` whenever NFT ownership changes. A stored grant from an earlier ownership period must never become usable again merely because the NFT returns to the granting address.

### Proof of Concept
Assume `M` is an active position manager and `A` owns account `N`.

1. `A` calls `Controller::add_delegate(caller=A, account_id=N, delegate=M)`, storing a `DelegateGrant { granted_by: A, delegates: [M] }`.
2. `A` transfers position NFT `N` to `B`. The grant is now stale because `account_owner(N) == B`, but it remains in persistent storage.
3. `B` transfers NFT `N` back to `A`. No delegate cleanup occurs during either transfer.
4. `account_owner(N)` is again `A`, so `get_delegates(N, A)` returns the old `[M]` grant.
5. `M` calls `Controller::borrow(caller=M, account_id=N, borrows=[...], to=Some(M))` or `Controller::withdraw(caller=M, account_id=N, withdrawals=[...], to=Some(M))`.
6. `require_owner_or_delegate` succeeds because `M` is active and appears in the reactivated grant, even though `A` did not authorize `M` after regaining ownership.

```rust
/// Returns grants stamped by `owner`, or an empty list. Ownership changes
/// invalidate a previous owner's grants without deleting them.
pub(crate) fn get_delegates(env: &Env, account_id: u64, owner: &Address) -> Vec<Address> {
    get_user::<DelegateGrant>(env, &ControllerKey::Delegates(account_id))
        .filter(|grant| grant.granted_by == *owner)
        .map(|grant| grant.delegates)
        .unwrap_or_else(|| Vec::new(env))
```
