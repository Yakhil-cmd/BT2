### Title
RAY-scaled debt valuation overflows during permissionless accrual and freezes a large market - ([File: common/src/rates/scaling.rs])

### Summary
A market whose scaled borrow shares and borrow index multiply beyond `i128::MAX` can no longer complete accrual because `accrue_step` converts debt through `scaled_to_original`, which calls the checked `Ray::mul` path. The controller exposes `update_indexes(caller, assets)` as a permissionless authenticated call and forwards it to the pool, so once ordinary interest growth reaches that bound, any caller can trigger the state transition that permanently blocks subsequent market operations. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) 

### Finding Description
For every accrual step, `accrue_step` computes `borrowed * borrow_index` before deriving utilization, the next borrow index, accrued interest, and the supply-index update. [5](#0-4)  Both that conversion and the later old/new debt comparison use `scaled.mul(index)`, which panics with `MathOverflow` if the RAY-scaled quotient does not fit `i128`. [2](#0-1) [6](#0-5) [7](#0-6)  The borrow-index ceiling does not prevent the overflow because the panic is on the position’s RAY value, not the index itself; the included regression test demonstrates failure while `borrow_index < MAX_BORROW_INDEX_RAY`. [8](#0-7) 

A funded user can create this state through normal controller calls: supply a very large amount of the borrow asset, supply collateral, and borrow most of the market’s liquidity. [9](#0-8)  The regression test uses `1_000_000_000` units of an 18-decimal asset and borrows 98% of it; after repeated annual accrual, `update_indexes` fails with `MATH_OVERFLOW`. [10](#0-9) 

### Impact Explanation
All pool mutations load market state and run `global_sync` before the requested mutation, while `global_sync` always invokes the same fallible `accrue_step`. [11](#0-10) [12](#0-11)  Consequently, once the market crosses the representable RAY-value boundary, repay, withdraw, liquidation, additional supply/borrow, recapitalization, and future index updates for that market all revert before their own logic can run; the regression test verifies both withdrawal and repayment fail with `MATH_OVERFLOW`. [13](#0-12)  Suppliers cannot exit and borrowers cannot deleverage, leaving the market’s funds frozen absent a code fix or state migration. [11](#0-10) 

### Likelihood Explanation
No privileged runtime call is needed after the market exists: `supply` and `borrow` are user entrypoints, and `update_indexes` only requires caller authorization. [9](#0-8) [3](#0-2)  The exploit requires a market whose configured caps and real liquidity permit very large positions, together with sustained high utilization so that the borrow index grows to roughly the `i128::MAX / borrowed_shares` boundary; the test fixture reaches that boundary with a billion-token market before the protocol’s index cap is reached. [14](#0-13)  These are demanding but ordinary market-size and utilization conditions, not leaked keys, malformed parameters, off-chain behavior, or a privileged emergency action. [15](#0-14) 

### Recommendation
Use saturating or widened arithmetic for `borrowed * index` and `supplied * index` inside accrual, or explicitly clamp the resulting debt/supply values before deriving utilization and reward deltas. [5](#0-4)  At minimum, detect the boundary before `scaled_to_original` and `calculate_supplier_rewards`, cap index growth at the largest index that keeps all market RAY values representable, and ensure repayment/withdrawal have a recovery path that does not require another overflowing full-value conversion. [2](#0-1) [6](#0-5) 

### Proof of Concept
1. On an active market for an 18-decimal asset with sufficient configured caps, call `controller.supply(attacker, 0, spoke_id, [(HubAssetKey { hub_id, asset }, 1_000_000_000 * 10^18)])`.
2. From another account owned by `attacker`, call `controller.supply(attacker, 0, spoke_id, [(collateral_key, 3_000_000_000 * 10^7)])`.
3. Call `controller.borrow(attacker, borrower_account_id, [(HubAssetKey { hub_id, asset }, 980_000_000 * 10^18)], Some(attacker))`.
4. Let interest accrue while utilization remains high, then call `controller.update_indexes(attacker, [HubAssetKey { hub_id, asset }])`.
5. Once `borrowed_shares * borrow_index / RAY` exceeds `i128::MAX`, step 4 returns `MathOverflow`; subsequent `repay`, `withdraw`, `liquidate`, and `update_indexes` calls for that market run the same accrual and fail before state can be repaired. [16](#0-15)

```rust
pub(crate) fn global_sync(env: &Env, cache: &mut Cache) {
    if !cache.needs_accrual() {
        return;
    }

    let mut remaining = cache.elapsed_ms();
    while let Some(nonzero) = NonZeroU64::new(remaining) {
        let chunk = nonzero.get().min(MAX_COMPOUND_DELTA_MS);
        accrue_chunk(env, cache, chunk);
        remaining = remaining.saturating_sub(chunk);
    }

    cache.mark_accrued();
}

/// Applies one compound step of `delta_ms` to indexes and protocol revenue.
///
/// The arithmetic lives in [`accrue_step`], shared with the read-only
/// `simulate_update_indexes` so the view and the mutator cannot drift.
fn accrue_chunk(env: &Env, cache: &mut Cache, delta_ms: u64) {
    let step = accrue_step(
        env,
        cache.params(),
        cache.borrowed(),
        cache.supplied(),
        cache.borrow_index(),
        cache.supply_index(),
        delta_ms,
    );

    cache.set_borrow_index(step.borrow_index);
    cache.set_supply_index(step.supply_index);
    cache.accrue_revenue(step.revenue_shares);
```

```markdown
| Bound | Consequence |

| Asset decimals 0..=18 | Exact token-to-RAY upscaling. Below 3: collateral only, no flash loans, no liquidation fee, its account's only supply position, at least 2 whole units while in debt |

| Borrow APR maximum 2 RAY | 200% annual rate; not a bound on balance growth alone |
| Token-to-RAY input maximum `i128::MAX / 10^(27-d)` | About 170.14 billion whole tokens, before other limits |
| Deposit conversion at the supply-index floor | About 170.14 million whole tokens before scaled-share overflow |

The token-to-RAY maximum is also the admitted cap maximum. Accrued position
values and market totals must independently fit the RAY domain; valid caps and
bounded indexes do not guarantee that future accrual fits. Value overflow can
occur before the index ceiling and block repayment/withdrawal because those
operations accrue first. At the borrow-index ceiling, further accrual produces
no borrower interest. No dedicated ceiling alarm is emitted.
```
