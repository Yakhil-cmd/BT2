This confirms the vulnerability is entirely in `StatusHandler#process`. The base `Handler` class provides a `stacks` helper (scoped via `Repository.from_github_repo_name(repository_name)`) at [1](#0-0) , but `StatusHandler#process` never calls `stacks` or `repository_name` — it queries `Commit` globally by SHA regardless of the payload's `repository.full_name`.### Title
`StatusHandler#process` matches commits by SHA globally without validating `repository.full_name` against the commit's stack repository - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` looks up commits solely by `Commit.where(sha: params.sha)`, never consulting the payload's `repository.full_name` or the `stacks`/`repository_name` helpers inherited from `Handler`. This means any minitest (or webhook) can call the handler directly with an arbitrary, non-resolvable repository name and still trigger `Commit#create_status_from_github!` against a pre-existing commit fixture, proving the repository-scope check is entirely absent from this business logic, independent of signature verification or app-selection.

### Finding Description
The broken binding, stated as an equality that should hold but does not: `commit.stack.repository.full_name == payload.dig('repository', 'full_name')` is never asserted anywhere in the code path, even though the base `Shipit::Webhooks::Handlers::Handler` class exposes exactly the primitives needed to check it — `repository_name` (`payload.dig('repository', 'full_name')`) and `stacks` (`Repository.from_github_repo_name(repository_name)&.stacks || Stack.none`) at [1](#0-0) .

`StatusHandler#process` ignores both helpers entirely:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [2](#0-1) 

This is a pure SHA lookup across the entire `commits` table, unscoped by repository. `Handler.call` (`app/models/shipit/webhooks/handlers/handler.rb:15-17`) simply instantiates the handler and parses params via `ExplicitParameters`; the params schema only validates types/presence of `sha`, `state`, etc. — it has no notion of repository ownership, and `repository` itself is not even part of the declared schema for `StatusHandler` ( [3](#0-2) ), so the `repository_name` field flows into `@payload` (accessible to `Handler#repository_name`) but is simply never read by this subclass.

Because `Handler.call` is a plain Ruby class method with no HTTP, no signature check, and no controller-level authorization, this can be invoked directly in a minitest with a fabricated payload hash, bypassing `GithubHook`, `verify_signature`, and any app-selection logic entirely — confirming the defect lives purely in `StatusHandler#process`'s Ruby logic.

### Impact Explanation
Calling `StatusHandler.call('sha' => commit.sha, 'state' => 'success', 'repository' => {'full_name' => 'totally/unrelated'})` writes a `Status` record onto `commit`, which belongs to some real `Stack`, even though the attacker-controlled payload names a repository that shares no relationship with that stack. Via the real webhook path (`POST /webhooks`), this lets an attacker who controls *any* repository configured in Shipit (or who can guess/brute-force commit SHAs, which are 40-hex and often discoverable from PR pages, CI logs, etc.) inject fabricated commit statuses (`success`/`failure`/`pending`, including CI check states) for commits belonging to a completely different repository/stack than the one that emitted the webhook. Since `create_status_from_github!` triggers `Status#enable_ci_on_stack`, `schedule_continuous_delivery`, and deployable-status webhooks (`app/models/shipit/status.rb:18-19`, `app/models/shipit/commit.rb:165-169`), a forged "success" status can make an otherwise-blocked commit appear deployable, potentially enabling continuous-delivery/auto-merge machinery to proceed on a commit whose actual CI never passed — a cross-repository/cross-tenant integrity violation matching the "payload for one repository mutating another's stack/commit" Critical category. This is repeatable against any commit SHA present in the datastore, for any repository whose webhook reaches this handler.

### Likelihood Explanation
Preconditions: the attacker needs (a) a target commit SHA that exists in Shipit's `commits` table (easily discoverable — SHAs are public on GitHub, visible in PRs/pushes/CI), and (b) the ability to have Shipit's `/webhooks` endpoint process a `status` event carrying that SHA — which requires the payload to originate from a GitHub App/webhook that Shipit's `GithubHook`/`verify_signature` accepts. Note: at the controller/webhook layer, signature verification still gates *which apps* can deliver events, but it does not scope *which repository's status a given signed event can affect* — the vulnerability is that the repository binding is never checked once inside `StatusHandler`, regardless of who delivered the event. Any repository owner who has Shipit's GitHub App installed on their own (unrelated) repo can trigger a real `status` webhook from their own repo containing an arbitrary `sha` string matching another tenant's commit, and it will be accepted since `Commit.where(sha:)` matches globally. This is low-cost, repeatable, and requires no privileged Shipit role — only ownership of some repository that can emit a signed webhook to the shared endpoint.

### Recommendation
In `StatusHandler#process`, scope the commit lookup to the repository asserted by the payload, e.g.:
```ruby
def process
  stacks.flat_map(&:commits).select { |c| c.sha == params.sha }.each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
or equivalently `Commit.where(sha: params.sha, stack_id: stacks.select(:id))`, using the inherited `stacks`/`repository_name` helpers so that a status payload can only mutate commits belonging to the repository named in `payload['repository']['full_name']`.
