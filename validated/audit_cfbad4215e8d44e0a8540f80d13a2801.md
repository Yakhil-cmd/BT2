### Title
`StatusHandler#process` mutates `Commit`/`Status` records globally by SHA without scoping to the webhook's own repository, unlike every other handler - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`Shipit::Webhooks::Handlers::Handler` defines `#stacks`/`#repository_name` so handlers scope their writes to `Repository.from_github_repo_name(payload.repository.full_name).stacks` [1](#0-0) . `PushHandler#process` honors this by only touching `stacks.not_archived.where(branch:)` [2](#0-1) , but `StatusHandler#process` instead runs `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` with no reference to `repository_name`/`stacks` at all [3](#0-2) . Because git commit SHAs are content hashes (not secrets), an attacker who controls any repository wired to the same GitHub App/webhook secret can reproduce a target repository's commit object (identical tree/parents/author/committer/timestamps/message), giving it the same SHA, and then legitimately trigger a `status` event on their own repo for that SHA — which Shipit will apply to the *other* tenant's `Commit`/`Status` rows.

### Finding Description
Broken binding (asserted equality that must hold for every handler):
`mutated_records == Repository.from_github_repo_name(payload.dig('repository','full_name')).stacks.commits` (i.e. every write a handler performs must be confined to the stacks resolvable from the webhook's own `repository.full_name`).

Trace:
1. `WebhooksController#create` parses the JSON body and dispatches to `Shipit::Webhooks.for_event(event)` handlers after `verify_signature`, which verifies the HMAC using `Shipit.github(organization: repository_owner)` — the shared per-App/org webhook secret, not a per-repository or per-tenant secret [4](#0-3) .
2. `StatusHandler#process` is invoked with the parsed payload and immediately looks up `Commit.where(sha: params.sha)` — a **global**, unscoped ActiveRecord query across all stacks/repositories in the installation [3](#0-2) .
3. For every matching `Commit` (which `belongs_to :stack`, i.e. some other tenant's stack), it calls `commit.create_status_from_github!(params)`, which writes a new `Status` row and can emit `commit_status`/`deployable_status` hooks and schedule merges via `stack.schedule_merges` [5](#0-4) [6](#0-5) .
4. Nothing in this path checks that `commit.stack.repository` matches `payload['repository']['full_name']`, unlike `PushHandler`/other handlers that always filter through `stacks`.

Attacker path: the attacker owns (or has push/CI access to) any repository whose organization is connected to the same Shipit GitHub App installation (satisfying "emit webhooks from a repository they own"). Because a git commit's SHA is a pure content hash of tree+parents+author+committer+timestamps+message, the attacker can reconstruct/replicate a target commit object bit-for-bit in their own repo (e.g. by fetching the public commit from the victim's public GitHub repo/PR and pushing an identical commit object to their own repo — GitHub will compute the identical SHA). The attacker then sets a `status` on that commit in their own repo (via the GitHub Status API, GitHub Actions, or a check that posts a status) with any `state`/`description`/`target_url` they choose. GitHub signs and delivers this `status` webhook using the shared App secret for the attacker's own installation, so `verify_signature` passes. `StatusHandler` then applies that attacker-chosen status to the **victim's** `Commit` row purely because the SHA matches, regardless of which repository actually owns it.

Existing guards do not stop this: `verify_signature` only proves the payload came from *some* legitimate GitHub App delivery for the org owning the sending repo — it says nothing about whether the `repository.full_name` in the JSON body is the one whose commit actually gets mutated, since `StatusHandler` never reads that field. `drop_unhandled_event`, `ExplicitParameters` schema (`sha`, `state`, etc. are all attacker-supplied strings), and model validations on `Status`/`Commit` do not enforce cross-referencing the commit's actual stack/repository against the webhook's declared repository.

### Impact Explanation
An attacker can write arbitrary CI/status data (state: success/failure/error/pending, description, target_url) onto a `Commit` belonging to a stack/repository they do not own, as long as they can reproduce that commit's SHA in a repo they control and post a status against it there. Since `create_status_from_github!` can flip `deployable?`/`blocked?` state and triggers `stack.schedule_merges` when the resulting status becomes `pending?`/`success?`, this can affect whether the victim stack's commits look deployable, potentially interfering with continuous deployment or merge-queue behavior. This is a genuine cross-tenant write into another repository's stack/commit records ("a payload for one repository mutating another's stack, commit"), matching the Critical impact category, and is repeatable against any commit whose SHA the attacker can reproduce (which, for public repos/PRs, is trivial since SHAs and full commit metadata are public).

### Likelihood Explanation
Preconditions: attacker needs the ability to push a commit and trigger a `status` webhook from some repository connected to the same Shipit GitHub App/webhook-secret scope as the victim's repository (multi-tenant Shipit installations, or any installation where the App is installed on multiple orgs/repos, satisfy this). No Shipit credentials, sessions, or API tokens are needed — only ordinary GitHub push/CI access on a repo the attacker owns, matching the stated attacker capabilities. Reconstructing a target commit object to obtain an identical SHA is mechanical for public commits (all inputs to the SHA-1 computation — tree, parents, author/committer identity and timestamps, message — are visible on GitHub). This is repeatable for every commit SHA the attacker can reproduce, across arbitrary target stacks.

### Recommendation
Scope `StatusHandler#process` through the base `Handler#stacks`/`#repository_name`, e.g. resolve commits via `stacks.joins(:commit set).merge(Commit.where(sha: params.sha))` (or equivalently, after loading `Commit.where(sha: params.sha)`, filter to only those whose `commit.stack.repository == Repository.from_github_repo_name(repository_name)`), discarding any commit not owned by the repository named in the payload, mirroring how `PushHandler` scopes via `stacks.not_archived.where(branch:)`.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb`-style, no live GitHub needed):
1. Create `repository_a` with `stack_a`, and `repository_b` (different `full_name`) with `stack_b`.
2. Create `commit_b = stack_b.commits.create!(sha: "deadbeef" * 5, ...)` belonging to `stack_b`/`repository_b`.
3. Build a payload: `{ "repository" => { "full_name" => repository_a.github_repo_name }, "sha" => commit_b.sha, "state" => "success", "context" => "attacker" }`.
4. Assert equality-based binding before: `Repository.from_github_repo_name(payload['repository']['full_name']).stacks` does **not** include `stack_b` (i.e. `stack_b` is absent from `Handler#stacks` for this payload) — `refute_includes stacks_for(payload), stack_b`.
5. Call `Shipit::Webhooks::Handlers::StatusHandler.call(payload)`.
6. Assert `commit_b.reload.statuses.last.state == "success"` and `commit_b.statuses.last.description`/context reflect the attacker's payload — proving a write occurred on `stack_b`'s commit despite `stack_b` never appearing in `stacks` for the attacker's declared `repository_a` payload.
7. Contrast: run the equivalent scenario through `PushHandler` with a payload declaring `repository_a` and `ref`/`after` values that would only match `stack_b`'s branch; assert `stack_b` is untouched (`sync_github` never called), because `PushHandler` filters through `stacks`. This differential establishes that `StatusHandler` uniquely breaks the binding.

      already_deployed = deployed?

      reload # to get the statuses into the right order (since sorted :desc)

        payload = { commit: self, stack:, status: new_status.state }
