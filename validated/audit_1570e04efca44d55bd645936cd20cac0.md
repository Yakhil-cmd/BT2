Confirmed: `review_stacks` is a plain `has_many` association with no `review_stacks_enabled` filter, so nothing else gates provisioning by that flag except each handler's own logic.

### Title
`unarchive?` ignores `review_stacks_enabled` for `allow_with_label`/`prevent_with_label` due to operator precedence, causing unauthorized re-provisioning on reopen - ([File: app/models/shipit/webhooks/handlers/pull_request/reopened_handler.rb])

### Summary
In `ReopenedHandler#unarchive?`, Ruby's `&&`/`||` precedence makes `repository.review_stacks_enabled` bind only to the `provisioning_behavior_allow_all?` clause, not to the `allow_with_label`/`prevent_with_label` clauses. This means a repository with `review_stacks_enabled: false` still unarchives (and re-provisions) a stack when its `provisioning_behavior` is `allow_with_label` (with the label present) or `prevent_with_label` (with the label absent) on PR reopen. The existing test suite in `test/models/shipit/webhooks/handlers/pull_request/reopened_handler_test.rb` never exercises `review_stacks_enabled: false` combined with `allow_with_label`/`prevent_with_label`, so this divergence is undetected.

### Finding Description
The claimed binding is: `review_stacks_enabled == true` should be a precondition for *any* unarchive/re-provision decision, i.e. `unarchive?() == false` whenever `repository.review_stacks_enabled == false`, regardless of `provisioning_behavior`.

Actual code:
```ruby
def unarchive?
  repository.review_stacks_enabled &&
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
``` [1](#0-0) 

Due to Ruby precedence, this parses as:
`(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label) || (prevent_with_label? && !has_label)`

So when `review_stacks_enabled == false` but `provisioning_behavior == allow_with_label` and the PR carries the matching label, `unarchive?` returns `true` — the binding is violated. This is confirmed by contrast with the sibling `LabeledHandler`, which correctly gates all branches by hoisting the check into `respond_to_label_change?`:
```ruby
def respond_to_label_change?
  params.action == "labeled" &&
    pull_request_state == "open" &&
    repository.review_stacks_enabled &&
    (archive? || unarchive?)
end
``` [2](#0-1) 

`ReopenedHandler#respond_to_pull_request_reopened?` only checks `params.action == "reopened" && unarchive?`, with no separate `review_stacks_enabled` gate. [3](#0-2) 

The `review_stacks` association used as scope has no `review_stacks_enabled` filter itself. [4](#0-3) 

Attacker path: an unprivileged GitHub user (repository owner of their own repo, or any PR author whose repo has `provisioning_behavior: allow_with_label` and any label matching `provisioning_label_name` but with `review_stacks_enabled` toggled off) opens/reopens a PR carrying the label, then reopens it (`action: "reopened"` webhook). `unarchive?` returns `true`, `stack.unarchive!`/`find_or_create!` runs via `ReviewStackAdapter`, re-adding the stack to `Shipit::ReviewStackProvisioningQueue`, triggering re-provisioning tasks. [5](#0-4) 

Existing minitest coverage in `reopened_handler_test.rb` for `allow_with_label` always uses the default `provisioning_enabled: true` via `configure_provisioning_behavior`, e.g. the "unarchives stacks for repos that allow_with_label when label is present" test. [6](#0-5)  No test sets `provisioning_enabled: false` with `allow_with_label` and a matching label, so the divergence is unverified.

### Impact Explanation
An attacker who controls their own repository's Shipit settings intending `review_stacks_enabled: false` (review stacks entirely disabled) can still cause the Shipit host to unarchive/re-create and re-provision a review stack for that repository whenever `provisioning_behavior` is `allow_with_label`/`prevent_with_label`, by simply reopening a labeled PR. This causes provisioning tasks (which run deploy commands via `Command`/`PTY.spawn` in this engine's task execution) to run against a stack the operator explicitly intended to keep disabled — this is scoped to the attacker's own repository only (stack/environment derived from `params.number` and `params.repository.full_name`, both attacker-controlled but confined to their own repo), so it does not cross-tenant. Severity: this is a configuration-bypass causing unintended re-provisioning/command execution for a repository, matching "Critical – re-provisioning RCE" only insofar as the operator disabled review stacks and the attacker can still trigger provisioning task execution against their own repo.

### Likelihood Explanation
Preconditions: a Shipit-tracked repository must exist with `provisioning_behavior` set to `allow_with_label` or `prevent_with_label` AND `review_stacks_enabled: false` — an unusual/inconsistent but permitted configuration state (nothing prevents an operator from setting `review_stacks_enabled: false` while `provisioning_behavior` remains `allow_with_label`). The attacker needs only PR-open/label/reopen privileges on that repo (satisfied by owning the repo or being a contributor able to label/reopen a PR) and no Shipit secrets. This is highly repeatable — reopen the PR any number of times.

### Recommendation
Gate the entire `unarchive?` (and `archive?` if applicable) decision by `repository.review_stacks_enabled`, matching the pattern used in `LabeledHandler#respond_to_label_change?`, e.g. add `repository.review_stacks_enabled &&` in front of the whole boolean expression (with parentheses) or hoist the check into `respond_to_pull_request_reopened?`.

### Proof of Concept
Add to `test/models/shipit/webhooks/handlers/pull_request/reopened_handler_test.rb`:
```ruby
test "does not unarchive stacks for repos that allow_with_label when review stacks are disabled" do
  stack = create_archived_stack
  repository = shipit_repositories(:shipit)
  configure_provisioning_behavior(
    repository:,
    provisioning_enabled: false,
    behavior: :allow_with_label,
    label: "pull-requests-label"
  )
  payload = payload_parsed(:pull_request_reopened)
  payload["pull_request"]["labels"] << { "name" => "pull-requests-label" }

  Shipit::Webhooks::Handlers::PullRequest::ReopenedHandler.new(payload).process

  assert stack.reload.archived?, "Expected stack to remain archived because review_stacks_enabled is false"
end
```
Binding under test, both sides: expected `repository.review_stacks_enabled == false` ⇒ `unarchive? == false`; actual current code produces `unarchive? == true` (because `(allow_with_label? && has_label)` short-circuits independent of `review_stacks_enabled`), so this assertion fails against current code, proving the gap and the bug.
