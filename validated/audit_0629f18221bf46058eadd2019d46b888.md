Based on the codebase analysis, I found a race-condition analog in the AA (Autonomous Agent) dry-run trigger execution path, structurally similar to the nilfs2 bug: shared in-process caches are mutated by an operation that is expected to be transient/rolled back, without the mutex protection that guards the very same caches elsewhere.

### Title
Unlocked mutation of shared unit-cache state during AA dry-run trigger execution can corrupt node's view of best-parent/free-unit state - (File: `aa_composer.js`)

### Summary
`dryRunPrimaryAATrigger()` in `aa_composer.js` runs a full trigger-execution simulation (including `writer.saveJoint`-style mutation of the shared, process-global in-memory caches `storage.assocUnstableUnits`, `storage.assocBestChildren`, `storage.assocCachedUnits`, `storage.assocKnownUnits`) inside a DB transaction that is later rolled back, and then attempts manual cleanup via `revertResponsesInCaches()`. Unlike the real write path, which is always serialized behind the `"write"` mutex lock, the dry-run path does not hold that lock while it performs these cache mutations. [1](#0-0) 

### Finding Description
The normal unit-write path (`writer.saveJoint`) always executes its cache mutations (`storage.assocUnstableUnits[...]=...`, `assocBestChildren` pushes, `is_free` flag flips, etc.) either as part of genesis processing or protected by the callers taking the `"write"` mutex lock before invoking it (see the commented-out/legacy lock wrapper and the explicit `mutex.lock(["write"], ...)` calls used throughout `storage.js` for cache maintenance such as `shrinkCache()` and `resetMemory()`). [2](#0-1) [3](#0-2) 

`dryRunPrimaryAATrigger`, however, is invoked from `network.js` during ordinary unit validation of *any* posted/received unit that triggers a primary AA (i.e., any unprivileged unit poster who sends a payment to an AA address can cause it to run, when the node operator has enabled `conf.bDryRunNewTriggers`): [4](#0-3) 

Inside `dryRunPrimaryAATrigger`, `handleTrigger()` is executed against a scratch DB connection wrapped in `BEGIN ... ROLLBACK`, but its side effects on the **shared, singleton, process-wide** caches in `storage.js` (which are not scoped per-connection or per-transaction) happen synchronously as callbacks fire — with no `mutex.lock(["write"], ...)` around any of it. Only after the whole simulated trigger chain completes does `revertResponsesInCaches()` attempt to undo the damage: [5](#0-4) 

This cleanup only pulls the fabricated response units out of `assocBestChildren` of their immediate parent and deletes their own cache entries via `storage.forgetUnit()`: [6](#0-5) 

Because Node.js callbacks yield the event loop at every DB query boundary (`conn.query(...)`), any other asynchronous operation queued in the meantime — a real `writer.saveJoint()` for a genuinely-arriving unit (protected by `"write"` lock, but that lock says nothing about concurrent *unlocked* dry-run mutations happening interleaved with it), a `main_chain` best-parent/witnessed-level computation, or `storage.shrinkCache()`/`resetMemory()` — can observe or build on top of a temporarily-inserted, not-yet-committed (and never going to be durably committed) unit in `assocUnstableUnits`/`assocBestChildren`/`assocCachedUnits`. This is the same class of bug as the nilfs2 CVE: a consumer iterates/uses a data structure that another code path is asynchronously about to invalidate/free, with no lock serializing the two.

### Impact Explanation
If a real, concurrently-processed unit's best-parent selection, `is_free` bookkeeping, or level/witnessed-level calculation reads `storage.assocBestChildren`/`assocUnstableUnits` while it transiently contains the dry-run's fabricated (never-persisted) AA response unit, the resulting in-memory unit-graph state used by this node diverges from what is actually written to SQL/rocksdb and from what other nodes compute. This can lead to a node computing a different best parent / free-unit set / stability decision than the network, i.e., node disagreement on unit validity or stability — one of the accepted impact categories.

### Likelihood Explanation
Triggering the dry-run path only requires posting/broadcasting a unit with a payment to any known AA address — fully reachable by an unprivileged unit poster — provided the node operator has `conf.bDryRunNewTriggers` enabled (an existing config option, not a privileged runtime capability). The race window depends on interleaving multiple async DB-callback chains in the same event loop tick sequence, which is plausible but not guaranteed on every call; this keeps likelihood at low-to-medium rather than trivially deterministic, similar to many single-threaded-JS races that depend on I/O timing.

### Recommendation
Wrap the entirety of `dryRunPrimaryAATrigger()` (from before `handleTrigger` starts mutating caches through `revertResponsesInCaches()`/`batch.clear()`/`ROLLBACK`) in `mutex.lock(["write"], ...)`, exactly like the real `writer.saveJoint` write path is serialized, so that no other cache-mutating or cache-reading logic can interleave with the transient/rolled-back state. Alternatively, make the dry-run path operate on a deep-cloned, isolated copy of the relevant caches rather than the shared singletons in `storage.js`.

### Proof of Concept
Conceptual (not fully verified end-to-end within available tool budget, since the exact concurrent reader in `main_chain.js`/`writer.js` best-parent code that would consume the stale cache entry was not traced line-by-line):
1. Enable `conf.bDryRunNewTriggers` on a full node.
2. Attacker A posts unit U1 with a payment to AA address `X` (any AA), causing `network.js` to invoke `aa_composer.dryRunPrimaryAATrigger` during U1's validation, which begins mutating `storage.assocUnstableUnits`/`assocBestChildren` for fabricated response units under transaction T (not yet committed, will be rolled back).
3. While T is still in flight (between its `conn.query` callback boundaries), attacker B (or ordinary network traffic) causes a second, real unit U2 to be validated and written via `writer.saveJoint`, which reads/writes the same global `storage.assocBestChildren`/`assocUnstableUnits` objects without any lock preventing interleaving with step 2.
4. If U2's best-parent computation observes the fabricated in-memory unit from step 2 before `revertResponsesInCaches()` runs, U2's committed on-disk unit properties (`best_parent_unit`, `is_free`, `witnessed_level`) can be computed from state that never existed in the durable database, causing this node's view of the DAG to diverge from peers that never ran the dry run.

Note: I was unable to fully confirm, within the remaining tool budget, the exact downstream code path in `main_chain.js`/`writer.js` that reads `assocBestChildren` concurrently in a way that reliably demonstrates the divergent outcome; the finding is based on confirmed absence of `"write"` mutex protection around `dryRunPrimaryAATrigger`'s cache mutations versus its presence everywhere else these same caches are touched.
