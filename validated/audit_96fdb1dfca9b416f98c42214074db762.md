### Title
Cross-tenant Status forgery via unscoped `Commit.where(sha:)` lookup in `StatusHandler` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` resolves the target `Commit` records purely by `sha`, with no scoping to the repository/stack that the webhook payload's `repository.full_name` identifies, unlike every other webhook handler (e.g. `CheckSuiteHandler`, `PullRequest::*Handler`) which route through `Repository.from_github_repo_name(...)` before touching any commit. Because `Commit#sha` is only unique per `stack_id` (`add_index :commits, %i(sha stack_id), unique: true`), an attacker who owns any repository connected to the same Shipit instance can trigger a real, correctly-signed `status` webhook from their own repo with a `sha` value that happens to collide with a commit that already exists in a victim's stack, and Shipit will write a forged `Status` onto the victim's commit.

### Finding Description
Broken binding: the code implicitly assumes `Commit.where(sha: params.sha) == commits belonging to the reporting repository`, but in reality `Commit.where(sha: params.sha)` returns commits from **every stack in the database** whose `sha` matches, since `sha` has no global uniqueness constraint: [1](#0-0) 

`StatusHandler#process`: [2](#0-1) 

does not call `Repository.from_github_repo_name(repository_name)` or filter by `stacks` at all, in contrast to `CheckSuiteHandler`, which explicitly scopes lookups to stacks belonging to the reporting repository: [3](#0-2) 

and in contrast to the base `Handler` class which provides exactly this scoping helper (`stacks`) for handlers to use: [4](#0-3) 

`WebhooksController#verify_signature` only checks the HMAC signature against the GitHub App configured for `repository_owner` (the org in the payload) — it never checks that the commits being mutated belong to that repository: [5](#0-4) 

For each matching commit, `Commit#create_status_from_github!` writes a `Status` using **that commit's own `stack_id`** (not the attacker's), so the forged status lands correctly attributed inside the victim's stack's data model: [6](#0-5) [7](#0-6) 

Exploit flow:
1. Attacker owns/administers a repository that is a legitimate Shipit tenant (satisfies "emit webhooks from a repository they own").
2. Attacker creates or references a commit in their own repo whose `sha` also exists as a `Commit#sha` in a victim's stack (e.g. GitHub's well-known empty-tree/empty-commit SHA `4b825dc642cb6eb9a060e54bf8d69288fbee4904`, or a public open-source commit vendored into both the attacker's and victim's repos via `git subtree`/vendoring — both scenarios are deterministic, no SHA-1 brute-force needed).
3. Attacker sets an arbitrary commit status (`state`, `description`, `context`, `target_url`) on that sha in their own repo, via the GitHub API on a repo they control — this is a completely legitimate action on their own repository and triggers a real, correctly-signed GitHub `status` webhook delivered to Shipit.
4. `WebhooksController#verify_signature` passes because the signature is genuinely valid for the attacker's own organization/App installation.
5. `StatusHandler#process` runs `Commit.where(sha: <colliding sha>)`, which also matches the victim's `Commit` row in a different stack, and writes an attacker-controlled `Status` (e.g. `state: "success"`) into the victim's stack.

Existing guards fail because: (a) `verify_signature` authenticates *organization identity*, not *commit ownership*; (b) no model validation enforces global `sha` uniqueness (confirmed by the migration/schema only indexing `[sha, stack_id]` unique, not `sha` alone); (c) `StatusHandler` uniquely among handlers skips the `Repository`/`stacks` scoping used elsewhere in the codebase.

### Impact Explanation
The attacker can write a fabricated CI `Status` (including `state: "success"`) onto any victim commit whose sha they can predict/collide with, in a stack they do not own and never authenticated for. `Commit#add_status` reacts to new statuses by calling `stack.schedule_merges if new_status.pending? || new_status.success?`: [8](#0-7) 

This can make an untested/CI-less commit appear deployable or eligible for auto-merge in the victim's stack, and fires `commit_status`/`deployable_status` hooks with attacker-controlled payload data. This matches "a payload for one repository mutating another's stack, commit... or an unauthorized deploy/rollback/merge" — Critical severity, and is repeatable against any stack/commit whose sha the attacker can reproduce (trivial for well-known git object shas or shared vendored commits), representing a genuine cross-tenant blast radius.

### Likelihood Explanation
Preconditions: attacker must control (own or administer) at least one repository connected as a tenant to the same Shipit instance, so their `status` webhooks are validly signed — this matches the stated attacker capability ("emit webhooks from a repository they own"). No Shipit secrets, sessions, or API tokens are needed. Sha collision is achieved deterministically (not brute-forced) using well-known git object shas (empty tree/commit) or public commits vendored into both attacker and victim repos (e.g. via `git subtree`), which is a realistic occurrence in monorepos importing common OSS libraries. Cost is a single API call to set a commit status on their own repo/commit — trivially repeatable against any number of target stacks/commits.

### Recommendation
Scope `StatusHandler#process` (and any similar handler) to only mutate commits belonging to the reporting repository, mirroring `CheckSuiteHandler`'s pattern, e.g.:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
end
```
using the existing `stacks` helper from `Handler` (`Repository.from_github_repo_name(repository_name)&.stacks`). Additionally, consider whether `sha` collisions across stacks are an acceptable data model given this class of bug, or if handlers touching `Commit` by `sha` should always require repository-scoping as a matter of course.

# test/controllers/webhooks_controller_status_cross_tenant_test.rb
require 'test_helper'

module Shipit
  class WebhooksControllerCrossTenantTest < ActionController::TestCase
    tests Shipit::WebhooksController

    setup do
      GithubHook.any_instance.stubs(:verify_signature).returns(true)
      Shipit::GitHubApp.any_instance.stubs(:verify_webhook_signature).returns(true)
    end

    test "status webhook from attacker repo forges a Status on an unrelated victim stack sharing the same sha" do
      colliding_sha = '4b825dc642cb6eb9a060e54bf8d69288fbee4904' # GitHub empty tree sha

      victim_stack = shipit_stacks(:shipit) # some other tenant's stack
      victim_commit = victim_stack.commits.create!(
        author: shipit_users(:walrus), committer: shipit_users(:walrus),
        sha: colliding_sha, authored_at: Time.now, committed_at: Time.now,
        message: 'victim commit'
      )

      attacker_payload = {
        'sha' => colliding_sha,
        'state' => 'success',
        'context' => 'attacker/fake-ci',
        'description' => 'forged status',
        'target_url' => 'https://attacker.example.com',
        'repository' => { 'full_name' => 'attacker-org/attacker-repo', 'owner' => { 'login' => 'attacker-org' } },
        'branches' => [{ 'name' => 'main' }]
      }.to_json

      request.headers['X-Github-Event'] = 'status'

      assert_difference -> { victim_commit.statuses.count }, 1 do
        post :create, body: attacker_payload, as: :json
      end

      status = victim_commit.statuses.last
      assert_equal 'success', status.state
      assert_equal 'attacker/fake-ci', status.context
      # Binding check: sha collided across stacks despite no global uniqueness constraint
      refute_equal victim_stack.id, Repository.from_github_repo_name('attacker-org/attacker-repo')&.id
    end
  end
end
