### Title
Routed strategy venues can smuggle arbitrary token transfers into the caller's signed auth tree, draining wallet funds — ([File: contracts/controller/src/strategies/swap.rs])

### Summary
The Curve incident is a front-end/approval-harvest class: users were induced to authorize a malicious contract that pulled their tokens. The XOXNO Lending analog is the controller's routed swap strategies (`swap_collateral`, `swap_debt`, `repay_debt_with_collateral`, `multiply`, `flash_position`), which forward a caller-supplied `StrategySwap` route to the swap aggregator. The router keeps no allowlist of the pool/token contracts a route names, so a route can place attacker-controlled contract code on the call stack *beneath the victim's `require_auth` entry*. From there the rogue venue contract can invoke `token.transfer(victim, attacker, amount)` on any token, and Soroban records it as a child invocation of the victim's authorization. If the victim signs the simulated tree — the natural path when a front end or quote service supplies the route — the host executes the theft. This is proven in-repo by `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs` and documented in `docs/explanation/threat-model.md` (the "Routes, callbacks, and external integrations" section).

### Finding Description
`swap_tokens` in `contracts/controller/src/strategies/swap.rs:36-38` invokes `router.execute_strategy` with the caller-provided `swap` payload under the controller's flash guard. The router dispatches hops to whatever `hop.pool` address the route encodes; there is no venue allowlist. Soroban's authorization model attaches any `require_auth` demand raised inside that call chain to the closest enclosing authorized invocation — the victim's signature on `swap_collateral`/`swap_debt`/etc.

The harness test `rogue_hop_pool_transfer_joins_caller_auth_tree.rs` demonstrates end-to-end:

- A rogue `hop_pool` contract registered inside the route calls `wallet_token.transfer(alice, attacker, WALLET_BALANCE)` during its `swap` invocation.
- Under simulation (`mock_all_auths`, recording mode), the recorded auth tree for Alice contains the stolen transfer as a `sub_invocation` of `Controller.swap_collateral` (lines 195–227).
- Under enforced auth, the call succeeds only when the signed tree lists the rogue child; an honest root-only tree is rejected by the host (lines 229–269). So the attack requires the victim to sign the poisoned tree — identical precondition to Curve users signing the malicious approval.
- The threat model at `docs/explanation/threat-model.md:153-165` explicitly describes this: "the router calls the pool and token addresses its payload names and keeps no allowlist of them, so a route can put third-party code on the call stack below the caller's authorization… The loss is then the caller's wallet, not the routed amount, and neither the payload minimum nor the final risk gate bounds it."

Crucially, neither of the controller's protections bounds this loss: `verify_router_output` (`swap.rs:75-84`) only requires positive measured `token_out` to the controller, and the post-swap account risk check only validates collateral ratios. The stolen wallet tokens never touch the swap's measured input/output.

### Impact Explanation
An unprivileged attacker who can get a victim to submit a crafted route (via a malicious/compromised front end, quote server output, or social engineering — exactly the Curve vector) can drain any token balance in the victim's wallet in a single transaction, not just the routed amount. Theft is unbounded by slippage parameters or risk gates. The same exposure exists on the direct `execute_strategy` path for every swap user. Impact: theft of user funds → Medium/High depending on whether "victim signs presented tree" is treated as in-scope; the Curve report itself relies on users authorizing a malicious contract, so the precondition is equivalent.

### Likelihood Explanation
Requires the victim to sign a transaction whose authorization tree contains the extra child invocation. Wallets that display auth trees poorly, or users who auto-accept simulation output (the dominant behavior — the Curve users approved what the compromised front end presented), make this realistic. The attacker only needs to craft a route; the venue contract is deployed by the attacker at zero cost. No privileged access is needed. Likelihood is moderate: it hinges on UI/wallet signing hygiene, but the attack surface is permissionless.

### Recommendation
- Enforce an allowlist of route venue contracts (pool addresses) in the controller or router, so routes can only reference vetted pools — matching how governance already gates approved Blend pools.
- Alternatively/additionally, constrain the caller's authorization: have the controller perform the venue call through an intermediate contract address the victim's auth doesn't cover, or verify at the controller that the executed route produced no additional `require_auth` demands (not directly introspectable on-chain — favor the allowlist).
- Front ends/clients must decode the signed auth tree and reject any child invocation other than the expected input transfer (the threat model already prescribes this client-side check; it should be enforced in-protocol for defense in depth).

### Proof of Concept
See `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs`:

1. Alice supplies 10 000 USDC; attacker deploys `RogueHopPool` whose `swap` calls `wallet_token.transfer(alice, attacker, WALLET_BALANCE)`.
2. Alice calls `controller.swap_collateral(alice, account_id, USDC, 50e9, ETH, route)` where `route` names the rogue pool.
3. Simulation records the theft as a child of Alice's `swap_collateral` auth entry; with the poisoned tree signed, `wallet(alice) == 0` and `wallet(attacker) == WALLET_BALANCE`, while the swap itself still returns fair ETH output and all controller checks pass.

Key caveats: the exploit requires the victim to sign the augmented auth tree (the phishing precondition shared with the Curve incident), and mitigation via protocol-level venue allowlisting is a design change rather than a code fix; the threat-model doc suggests the authors currently assign this responsibility to clients, which means this finding may be considered a documented/accepted trade-off — though it is not marked as an ADR choice and the loss mode (unbounded wallet theft) is more severe than the documented residual risks.
