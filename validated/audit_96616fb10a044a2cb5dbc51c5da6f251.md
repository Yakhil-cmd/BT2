### Title
Silent truncation of core assignments beyond 28 entries in `CoretimeAllocator::assign_core` causes paid-for coretime assignments to be dropped - ([File: system-parachains/coretime/coretime-kusama/src/coretime.rs])

### Summary
`CoretimeAllocator::assign_core` truncates the `assignment: Vec<(CoreAssignment, PartsOf57600)>` to at most 28 entries (1 synthetic `Idle` slot + first 27 non-`Idle` entries) whenever `pallet_broker` builds a workplan for a core with more than 28 distinct task assignments, silently dropping the remainder and replacing them with `Idle`. Because `pallet_broker`'s public extrinsics (`purchase`, `renew`, `interlace`, `partition`, `assign`, `pool`) let ordinary signed accounts split and assign coretime for a single core/timeslice into many independent pieces, a core that is shared across many different task owners (via the Instantaneous Coretime Pool, leases, and on-demand/renewal activity) can legitimately accumulate more than 28 distinct assignments, at which point some already-paid assignments are dropped from the message actually sent to the relay chain.

### Finding Description
`CoretimeAllocator::assign_core` is the `CoretimeInterface::assign_core` implementation used by `pallet_broker` (`type Coretime = CoretimeAllocator` in the pallet config) to push each core's finalized workplan to the relay chain via XCM `Transact`. [1](#0-0) 

The comment in the code explicitly documents the reason for the truncation: the relay chain's `assign_core` extrinsic currently only accepts a single call per core with a complete mask, so if `pallet_broker` produces more than 28 entries for one core, the runtime truncates to the synthetic `Idle` slot plus the first 27 non-idle entries, dropping everything past index 27 and reassigning the freed parts to `Idle`. [2](#0-1) 

The number of distinct assignments for a single core is not bounded to ≤28 anywhere in this runtime's `pallet_broker::Config`. `MaxLeasedCores`, `MaxReservedCores`, and `MaxAutoRenewals` bound the total number of leased/reserved cores and auto-renewals globally, but they do not bound how many distinct tasks/regions can be interlaced or pooled onto the *same* core in the *same* timeslice. [3](#0-2) 

`pallet_broker` exposes public, signed extrinsics (`purchase`, `renew`, `interlace`, `partition`, `assign`, `pool`) that let any account that owns/purchases a bulk-coretime region split it (via `interlace`) into many disjoint mask fragments and assign each fragment to a different `TaskId` (via `assign`), or contribute fragments to the shared Instantaneous Coretime Pool. Because coretime regions and on-demand purchases for the *same* physical core and timeslice can originate from many independent, unprivileged accounts (leaseholders, renewers, on-demand/pool buyers), the aggregate number of distinct non-idle assignments queued in `Workplan` for one core in one rotation is a function of total user activity on that core, not of any single account's per-account limits. This is not mocked/privileged access — it is the real, intended user flow for buying and using coretime.

### Impact Explanation
When the per-core assignment count for a rotation exceeds 28, the truncation branch drops all non-idle entries beyond the first 27 and replaces the freed capacity with `Idle`. Any task assignment beyond that cutoff is never sent to the relay chain even though `pallet_broker`'s own ledger (`Workplan`/region ownership/revenue accounting) still records it as sold and paid for. This creates a persistent divergence between the broker's accounting (which believes coretime was sold and used) and the relay's actual schedule (where the assignment silently never executed), with no error, event, or refund surfaced to the affected task owners. The affected parties are whichever assignments land after index 27 in the vector — which can include victims who did nothing wrong other than sharing a busy core with other legitimate users.

### Likelihood Explanation
Triggering this requires accumulating >28 distinct non-idle assignments for one core in one timeslice. This is plausible only under specific, unusual saturation of a single core (heavy interlacing/pooling/on-demand activity concentrated on the same core and timeslice) — it is not something a lone attacker can trivially force onto a core they don't control, since assignment placement onto specific cores is largely managed by `pallet_broker`'s internal sale/rotation logic rather than freely chosen by the caller. A single account can deliberately interlace its own purchased region into many fragments and assign each to a distinct task to build up entries on a core it does own, but harming *other* users' assignments requires those other assignments to coincidentally land on the same core/timeslice, which is not fully attacker-controlled. The runtime authors are already aware of this relay-chain limitation, as shown by the explicit comment describing it as a temporary workaround pending a relay-chain change allowing multiple `assign_core` messages per core.

### Recommendation
- Enforce (or verify) an upper bound of ≤28 total assignments per core per rotation inside `pallet_broker`'s workplan-building/rotation logic itself (rather than silently truncating downstream in the parachain runtime), rejecting or deferring excess assignments with an explicit error/event so the broker's ledger stays consistent with what is actually sent to the relay.
- Alternatively, emit a runtime event and/or refund logic when truncation occurs in `CoretimeAllocator::assign_core`, so dropped assignments are observable and can be compensated instead of silently disappearing.
- Track upstream progress on allowing the relay chain to accept multiple `assign_core` messages per core (as referenced in the code comment) to remove the need for truncation entirely.

### Proof of Concept
Rust unit test in the coretime-kusama/coretime-polkadot runtime crate:
```rust
#[test]
fn assign_core_truncation_drops_paid_assignments() {
    // Build a synthetic assignment vector with 30 distinct non-idle Task assignments,
    // each carrying a nonzero PartsOf57600 that would represent "paid for" coretime.
    let assignment: Vec<(CoreAssignment, PartsOf57600)> = (0..30)
        .map(|i| (CoreAssignment::Task(i as u32), 57_600 / 30))
        .collect();

    // Simulate the truncation logic exactly as implemented in assign_core.
    let truncated = if assignment.len() > 28 {
        let mut total_parts = 0u16;
        let mut assignment_truncated = vec![(CoreAssignment::Idle, 0)];
        assignment_truncated.extend(
            assignment
                .clone()
                .into_iter()
                .filter(|(a, _)| *a != CoreAssignment::Idle)
                .take(27)
                .inspect(|(_, parts)| total_parts += *parts)
                .collect::<Vec<_>>(),
        );
        assignment_truncated[0].1 = 57_600u16.saturating_sub(total_parts);
        assignment_truncated
    } else {
        assignment.clone()
    };

    // Assert that tasks 27, 28, 29 (paid-for assignments) are missing from the final message.
    let sent_tasks: Vec<_> = truncated.iter().filter_map(|(a, _)| match a {
        CoreAssignment::Task(id) => Some(*id),
        _ => None,
    }).collect();

    for missing in [27u32, 28, 29] {
        assert!(
            !sent_tasks.contains(&missing),
            "Task {missing} was paid for but silently dropped by truncation"
        );
    }
    // This assertion demonstrates the accounting mismatch: pallet_broker's ledger
    // still believes tasks 27-29 were assigned coretime, but the relay never received them.
}
```
Expected result: the test confirms that tasks 27–29 (paid, non-idle assignments) are absent from the truncated vector actually sent to the relay via XCM, proving the accounting mismatch described.
