### Title
`ProxyType::is_superset` in the Rococo relay-chain runtime falsely claims `NonTransfer` is a superset of `OnDemandOrdering`, letting a `NonTransfer` proxy self-escalate to calls its own filter denies - (File: `polkadot/runtime/rococo/src/lib.rs`)

### Summary
The advisory describes a session-key allowlist that could be bypassed because the enforcement path didn't correctly check the configured allowlist before granting access. The Polkadot SDK analog of an "allowlist" is `pallet_proxy`'s `InstanceFilter::filter` (the actual list of admitted calls) combined with `InstanceFilter::is_superset` (the lattice relation `pallet-proxy` trusts when a proxy tries to grant/remove another proxy on behalf of the delegator without re-checking `filter`). In Rococo's runtime, `ProxyType::is_superset` unconditionally declares `NonTransfer` a superset of every other `ProxyType`, including `OnDemandOrdering`, even though `NonTransfer::filter` never admits `RuntimeCall::OnDemandAssignmentProvider(..)`, which is exactly what `OnDemandOrdering::filter` admits.

### Finding Description
`ProxyType::filter` for `NonTransfer` is an explicit allow-list of pallets/calls (`System`, `Session`, `Treasury`, `Proxy`, ... `Auctions`) and it does **not** include `RuntimeCall::OnDemandAssignmentProvider(..)`: [1](#0-0) 

`OnDemandOrdering::filter` admits exactly `RuntimeCall::OnDemandAssignmentProvider(..)`: [2](#0-1) 

Yet `is_superset` claims `NonTransfer` is a superset of *every* other proxy type via the wildcard arm `(ProxyType::NonTransfer, _) => true`: [3](#0-2) 

`pallet_proxy` trusts `is_superset` — not `filter` — when a delegate proxy tries to add/remove another proxy relationship on behalf of the delegator (documented explicitly by the regression test added for the sibling bug on Asset Hub Westend): [4](#0-3) 

This is precisely the same bug class that was already found and fixed for the `NonTransfer`/`Governance` pair on Asset Hub Westend: [5](#0-4) [6](#0-5) 

However, the fix and its accompanying lattice-wide regression test (`proxy_type_superset_relation_matches_call_filters`) were only applied to `asset-hub-westend-runtime`; the relay-chain runtime `polkadot/runtime/rococo/src/lib.rs` still uses the naive `(ProxyType::NonTransfer, _) => true` rule and was not covered by an equivalent test, so the analogous mismatch for `OnDemandOrdering` was never caught.

The `Proxy::proxy` call itself is admitted by `NonTransfer` (it whitelists `RuntimeCall::Proxy(..)` wholesale): [7](#0-6) 

so a delegate holding only `NonTransfer` can dispatch `Proxy::add_proxy(delegate2, ProxyType::OnDemandOrdering, 0)` on behalf of the delegator via `Proxy::proxy`: [8](#0-7) 

Because `is_superset(NonTransfer, OnDemandOrdering)` returns `true`, this is authorized despite `NonTransfer`'s own `filter` never admitting `OnDemandAssignmentProvider` calls. The newly created `OnDemandOrdering` proxy can then dispatch `OnDemandAssignmentProvider` calls (place/cancel on-demand core orders, which move funds) on behalf of the delegator — permissions the original `NonTransfer` grant was explicitly designed to withhold.

### Impact Explanation
A holder of a restricted `NonTransfer` proxy permission can escalate itself to a permission (`OnDemandOrdering`) that its own filter denies, and thereby dispatch `OnDemandAssignmentProvider` calls (spending the delegator's balance on on-demand coretime orders) that the delegator never intended to authorize. This is an authorization/allowlist-bypass, structurally identical to the reported advisory's session-key bypass of an allowlist. The blast radius is bounded to Rococo, however: Westend and Polkadot relay-chain `ProxyType` enums do not define an `OnDemandOrdering` variant (confirmed absent from `polkadot/runtime/westend/src/lib.rs`), so this specific mismatch does not reproduce there.

### Likelihood Explanation
Reachability requires no privilege beyond a delegator having already granted some account a `NonTransfer` proxy — a routine, unprivileged setup. Once granted, escalation is a single `Proxy::proxy` call with no additional cost besides normal transaction fees. The main mitigating factor is scope: Rococo is Parity's public testnet, not a production network, which likely places it outside live bug-bounty program eligibility even though the logic flaw is real and demonstrable in this repository's source.

### Recommendation
Apply the same fix pattern used in `prdoc/pr_12769.prdoc` for Asset Hub Westend to `polkadot/runtime/rococo/src/lib.rs`: replace the blanket `(ProxyType::NonTransfer, _) => true` arm with explicit, filter-consistent superset relations (e.g., exclude `OnDemandOrdering` unless `NonTransfer::filter` is extended to admit `OnDemandAssignmentProvider` calls), and add the lattice-wide regression test (`proxy_type_superset_relation_matches_call_filters`) to Rococo (and ideally to every runtime defining `ProxyType`) so `is_superset` can never silently diverge from `filter` again.

### Proof of Concept
Not executed against a live network or reference-runtime harness within this analysis (no filesystem/terminal execution available in this session). The reasoning above is a static-analysis reproduction: it traces the exact authorization path (`Proxy::proxy` → `filter` admits nested `Proxy::add_proxy` → `pallet_proxy` trusts `is_superset` rather than `filter` for the nested grant → `is_superset` wildcard returns `true` for `OnDemandOrdering`) using the same evidentiary pattern (regression test + prdoc) Parity itself used to document and fix the sibling `NonTransfer`/`Governance` bug. A concrete `#[test]` analogous to `non_transfer_proxy_is_not_a_superset_of_governance` (asserting `!ProxyType::NonTransfer.is_superset(&ProxyType::OnDemandOrdering)` and that `OnDemandOrdering::filter` admits an `OnDemandAssignmentProvider` call while `NonTransfer::filter` denies it) would need to be run in `polkadot/runtime/rococo` to obtain an executed pass/fail result; this was not run in this session, so the finding should be treated as a static-analysis-confirmed, execution-unverified analog, scoped only to the Rococo testnet runtime.

/// `pallet_proxy` authorizes `add_proxy`/`remove_proxy` through `ProxyType::is_superset`, so a
/// proxy type that *declares* itself a superset of another must also *admit* every call that other
/// type admits. Otherwise the "smaller" type is reachable as an escalation: the declared superset
/// can grant itself the subset proxy and thereby gain permissions its own filter denies.
///
/// This checks that property across the whole lattice rather than a single pair, so the class of
/// bug cannot silently reappear on another edge.
#[test]
fn proxy_type_superset_relation_matches_call_filters() {
	use frame_support::traits::InstanceFilter;

	let calls = representative_proxy_calls();

	for superset in all_proxy_types() {
		for subset in all_proxy_types() {
			if !superset.is_superset(&subset) {
				continue;
			}

			for call in calls.iter() {
				if subset.filter(call) {
					assert!(
						superset.filter(call),
						"lattice violated: {superset:?} declares itself a superset of {subset:?}, \
						 but rejects {call:?} which {subset:?} admits",
					);
				}
			}
		}
	}

/// Regression test for <https://github.com/paritytech/polkadot-sdk/issues/12724>.
///
/// `NonTransfer` used to claim `Governance` as a subset while denying the `Treasury`,
/// `ConvictionVoting`, `Referenda` and `Whitelist` calls that `Governance` admits, which let a
/// `NonTransfer` proxy add a `Governance` proxy and widen its own permissions.
#[test]
fn non_transfer_proxy_is_not_a_superset_of_governance() {
	use asset_hub_westend_runtime::ProxyType;
	use frame_support::traits::InstanceFilter;

	// `NonTransfer` denies every governance call family that `Governance` admits, except `Utility`.
	for call in [
		RuntimeCall::Treasury(pallet_treasury::Call::void_spend { index: 0 }),
		RuntimeCall::ConvictionVoting(pallet_conviction_voting::Call::remove_vote {
			class: None,
			index: 0,
		}),
		RuntimeCall::Referenda(pallet_referenda::Call::refund_decision_deposit { index: 0 }),
		RuntimeCall::Whitelist(pallet_whitelist::Call::remove_whitelisted_call {
			call_hash: Default::default(),
		}),
	] {
		assert!(ProxyType::Governance.filter(&call), "Governance must admit {call:?}");
		assert!(!ProxyType::NonTransfer.filter(&call), "NonTransfer must deny {call:?}");
	}

	// So it must not declare itself a superset of it. This is what stops a `NonTransfer` proxy
	// from granting itself a `Governance` proxy: `pallet_proxy` gates `add_proxy`/`remove_proxy`
	// on `is_superset` before it ever consults `filter`, which by itself does not deny `Proxy`
	// calls.
	assert!(!ProxyType::NonTransfer.is_superset(&ProxyType::Governance));

	// The other declared `NonTransfer` subsets are unaffected.
	for subset in [
		ProxyType::Collator,
		ProxyType::Staking,
		ProxyType::NominationPools,
		ProxyType::StakingOperator,
	] {
		assert!(ProxyType::NonTransfer.is_superset(&subset));
	}
}

title: 'asset-hub-westend: fix `NonTransfer` proxy falsely claiming `Governance` containment'
doc:
- audience: Runtime User
  description: |-
    On Asset Hub Westend, the `NonTransfer` proxy type declared itself a superset of the
    `Governance` proxy type while its call filter denied the `Treasury`, `ConvictionVoting`,
    `Referenda` and `Whitelist` calls that `Governance` admits.

    Because `pallet_proxy` authorizes `add_proxy`/`remove_proxy` through `is_superset`, a
    `NonTransfer` proxy could add a `Governance` proxy for its delegator and thereby reach calls
    that its own filter denies. `NonTransfer` no longer declares `Governance` as a subset, so this
    is rejected.

    Existing `Governance` proxies are unaffected; only the ability of a `NonTransfer` proxy to
    create or remove one changes. The `Collator`, `Staking`, `NominationPools` and
    `StakingOperator` subsets of `NonTransfer` are unchanged.
