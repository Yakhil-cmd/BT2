### Title
`MembershipHandler#process` matches `Team.github_id` across organizations without validating `params.organization.login` against the matched team's `organization` - ([File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`MembershipHandler#find_or_create_team!` looks up a `Team` solely by `github_id`, with the `organization` field only set in the create block that never runs when a row already exists. `WebhooksController#verify_signature` validates the payload signature against the webhook secret of the organization named in the payload itself, not the organization owning the matched `Team`, so an attacker who owns their own GitHub organization can send a validly-signed `membership` webhook that mutates another organization's `Team`/`Membership` records.

### Finding Description
The broken binding is: `Team.find_or_create_by!(github_id: params.team.id).organization == params.organization.login`. This equality is never checked.

Code path:
1. `WebhooksController#verify_signature` computes `repository_owner` as `params.dig('repository','owner','login') || params.dig('organization','login')` [1](#0-0)  and then does `Shipit.github(organization: repository_owner).verify_webhook_signature(...)` [2](#0-1) . For a `membership` event there is no `repository` key, so `repository_owner` resolves to `params.organization.login`, i.e., **the attacker's own organization**. Since the attacker owns `attacker-org` and controls its `webhook_secret`, they can produce a valid `X-Hub-Signature` for any payload body they choose.
2. `MembershipHandler#process` then calls `find_or_create_team!`, which does `Team.find_or_create_by!(github_id: params.team.id) { |team| team.organization = params.organization.login }` [3](#0-2) . The block that assigns `organization` only executes on record creation; if a `Team` row with that `github_id` already exists (e.g. Shopify's team), it is fetched as-is and `organization` is **not** re-checked or overwritten.
3. `team.add_member(member)` / `team.members.delete(member)` [4](#0-3)  then mutates the pre-existing team's membership using `Team#add_member` [5](#0-4) , which unconditionally appends the member with no organization ownership check.

Root cause: the controller authenticates the *payload* against the organization named in the payload, but the handler resolves the target `Team` purely by `github_id` (a GitHub-global integer, not scoped per organization) and never cross-checks that the matched `Team#organization` equals the authenticated `params.organization.login`. No `require_permission!`, `User#authorized?`, or controller-level guard intervenes for webhook-created records — those checks only apply to authenticated user/session paths, not to `WebhooksController`.

Exploit flow: attacker registers `attacker-org` on GitHub, configures it as a Shipit GitHub App/organization with its own distinct `webhook_secret` (a legitimate, unprivileged administrative action over their own org, not a Shipit secret). They discover or guess Shopify's `Team#github_id` (GitHub team IDs are sequential integers, often enumerable/discoverable via other public GitHub API responses for org members), then POST to `/webhooks` a `membership` event with `X-Github-Event: membership`, a signature computed with `attacker-org`'s `webhook_secret`, and body:
```json
{
  "action": "added",
  "team": { "id": <shopify_team_github_id>, "name": "...", "slug": "...", "url": "..." },
  "organization": { "login": "attacker-org" },
  "member": { "login": "attacker-github-login" }
}
```
`verify_signature` succeeds (checked against attacker-org's own secret), `find_or_create_team!` matches Shopify's existing `Team` row, and `team.add_member(User.find_or_create_by_login!("attacker-github-login"))` adds the attacker to Shopify's team roster.

### Impact Explanation
The attacker mutates another organization's `Team`/`Membership` records — a payload authenticated for `attacker-org` writes into `shopify`'s data — matching the "payload for one repository/organization mutating another's stack/team" Critical category. If the affected `Team` corresponds to one of `Shipit.github_teams` used for authorization (`User#authorized?`/`require_permission!` paths reference team membership for granting deploy/operator permissions), this becomes an escalation into privileged Shipit roles, allowing the attacker to subsequently authorize deploys/rollbacks they should not have access to. Repeatable against any `Team#github_id` the attacker can enumerate, across arbitrary organizations onboarded to the same Shipit instance.

### Likelihood Explanation
Preconditions are attacker-controlled and cheap: own any GitHub organization, register it with Shipit (a normal onboarding action, not privileged over the *target* org), and know/guess a target `Team`'s numeric GitHub ID. No Shipit or target-org secrets are required — the attacker only needs their own organization's `webhook_secret`, which they legitimately possess. The request is a single unauthenticated HTTP POST to `/webhooks`, fully repeatable, and does not require live GitHub interaction to reach the vulnerable code path.

### Recommendation
In `MembershipHandler#find_or_create_team!`, scope the lookup by both `github_id` and `organization`, and reject/raise when an existing `Team` row's `organization` does not equal `params.organization.login`:
```ruby
def find_or_create_team!
  team = Team.find_by(github_id: params.team.id)
  if team && team.organization != params.organization.login
    raise ArgumentError, "Team #{params.team.id} does not belong to organization #{params.organization.login}"
  end
  Team.find_or_create_by!(github_id: params.team.id) do |t|
    t.github_team = params.team
    t.organization = params.organization.login
  end
end
```

### Proof of Concept
Add to `test/models/shipit/webhooks/handlers/membership_handler_test.rb` (not shown in current index but inferable from the handler's structure):
```ruby
test "process does not mutate a team belonging to a different organization" do
  shopify_team = Shipit::Team.create!(organization: 'shopify', github_id: 4242, name: 'ops', slug: 'ops', api_url: 'https://api.github.com/teams/4242')

  payload = {
    'action' => 'added',
    'team' => { 'id' => 4242, 'name' => 'ops', 'slug' => 'ops', 'url' => shopify_team.api_url },
    'organization' => { 'login' => 'attacker-org' },
    'member' => { 'login' => 'attacker' }
  }

  assert_raises(ArgumentError) do
    Shipit::Webhooks::Handlers::MembershipHandler.new.call(payload)
  end

  shopify_team.reload
  # binding under test: matched team's organization must equal payload organization
  assert_equal 'shopify', shopify_team.organization
  refute shopify_team.members.exists?(login: 'attacker')
end
```
This asserts the equality `shopify_team.organization == payload['organization']['login']` is enforced (currently false/unchecked) and that no cross-org membership write occurs.
