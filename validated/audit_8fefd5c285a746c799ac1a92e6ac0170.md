## Title
Atomic bounce of AA response units lets a malicious reward asset's unsatisfiable conditions permanently freeze user principal held by the AA - (File: `aa_composer.js`)

### Summary
This is a valid architectural analog to the C4 finding. In ocore, an Autonomous Agent (AA) that pays out a user's principal together with a reward-asset payment in the same response unit is vulnerable to the same failure mode: if the reward asset's `transfer_condition`/`spender_attested`/`is_private` rules can never be satisfied, `sendUnit()` bounces the **entire** response atomically — including the principal payout — every single time the withdrawal trigger is processed, permanently freezing the user's funds inside the AA.

### Finding Description
When an AA's `messages` template produces several `payment` messages in one response (e.g. one output returning the user's deposited bytes/asset, another paying out a reward token), `sendUnit()` builds and validates them together as a single unit: [1](#0-0) 

Any failure while completing a single payment message — including `storage.loadAssetWithListOfAttestedAuthors` errors, `objAsset.is_private` (explicitly rejected with `"sending private asset from AA"`), or a failure inside `completePaymentPayload` — aborts the whole `async.eachSeries` and calls `bounce(err)` for the **entire** unit, not just the offending message: [2](#0-1) 

Even after the individual messages are assembled, the composed unit still goes through full validation via `validateAndSaveUnit`; if it fails (e.g. an asset's `transfer_condition` is not satisfied), the whole response bounces again: [3](#0-2) 

The condition check that a malicious/adversarial asset issuer can weaponize is in `validation.js`, where any `transfer_condition`/`issue_condition` or `spender_attested` attestor requirement attached to the asset must be satisfied for every payment of that asset, or the unit is rejected: [4](#0-3) 

Crucially, `bounce()` discards all pending state changes for that trigger (`objStateUpdate = null`), so nothing about the intended withdrawal is ever committed: [5](#0-4) 

An asset issuer (a normal, unprivileged unit poster) can freely attach a `transfer_condition`/`spender_attested` attestor list to an asset that can never be satisfied by an AA-generated unit (AA response units carry no interactive signature/authentifier flow beyond the fixed AA-address rules, so conditions requiring specific signatures, attestations that will never be issued, or self-referential constraints are permanently unsatisfiable). If any AA design pays out this asset bundled together with a user's principal withdrawal in the same response (a common "staking/farming" pattern), the withdrawal can never succeed: every trigger the user posts produces the exact same messages, which fail the exact same way, bouncing atomically forever.

### Impact Explanation
This results in **AA fund freezing**: user principal held in the AA's balance becomes permanently unwithdrawable as long as the AA logic ties its payout together with a reward/other asset payment whose transfer/issue condition the AA can never satisfy. Unlike a normal bounce (which safely refunds bytes and lets the user retry), here retrying is futile because the same deterministic formula always produces the same unsatisfiable payment, and the state change reducing the user's recorded balance is never even committed, so the user is stuck with no path to get their funds out through that AA logic.

### Likelihood Explanation
Likelihood is Medium: it requires (a) an AA design that permissionlessly accepts an asset chosen by a pool creator/depositor (or the AA developer) as a reward/paired asset, and (b) that asset carrying restrictive `transfer_condition`/`spender_attested`/`is_private` settings that the AA can never satisfy. This mirrors the original permissionless-pool-factory scenario exactly and is realistic for any Oscript AA implementing pluggable reward-token pools, prediction markets, or vesting/staking-style contracts where the reward asset is user- or attacker-supplied.

### Recommendation
- AA authors composing withdrawal responses should not bundle principal payouts atomically with payouts of externally supplied/untrusted assets in the same response unit; instead, split them into independent triggers/response units (or separate AA-to-AA hops) so a failure of one payment message does not block the other.
- Where an AA must accept an arbitrary reward asset, validate up front (e.g., at pool-creation time) that the asset has no `transfer_condition`, no `spender_attested` requirement, and `is_private: false`, rejecting assets that could make the AA's own payouts permanently unsendable.
- Consider providing an explicit "principal-only" fallback trigger/branch in the AA's `messages` template so that if the reward-asset payment message fails to complete, the AA still returns only the principal in a message set that does not include the unsendable asset, rather than relying on `bounce()` reverting everything atomically.

### Proof of Concept
1. An attacker deploys asset `X` with `spender_attested: true` and an attestor list that will never attest any address (or a `transfer_condition` requiring an unsatisfiable formula).
2. Attacker creates a farming/staking-style AA pool (or uses a permissionless pool-factory AA) configured with `X` as the reward asset, using deposits in `base`.
3. A user deposits `base` bytes into the pool AA, recorded in AA state as a claimable balance.
4. On the user's withdrawal trigger, the AA's `messages` template emits two `payment` messages in the same response: one returning the user's principal in `base`, one paying the reward in asset `X`.
5. In `sendUnit()`, the payment message for asset `X` fails `storage.loadAssetWithListOfAttestedAuthors`/condition checks or later fails `validateAndSaveUnit` (`aa_composer.js:1408-1411`), triggering `bounce(err)` which discards the whole response, including the principal-in-`base` message, per `aa_composer.js:909-922` and `1346-1348`.
6. Every subsequent identical withdrawal trigger reproduces the same deterministic failure, so the user's principal remains stuck in the AA indefinitely.
