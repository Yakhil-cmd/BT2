### Title
Autonomous Agents can permanently freeze incoming funds for assets defined with `cosigned_by_definer` (or non-transferrable, definer-only) flags, because AA `bounce()`/response logic can never satisfy the definer-cosignature/definer-participation requirement - ([File: aa_composer.js])

### Summary
An unprivileged asset issuer can define a public asset with `cosigned_by_definer: true` (or `is_transferrable: false`) and send it to any Autonomous Agent (AA) as part of a trigger. Because an AA can only ever sign its own response unit with its own single address — it has no mechanism to add the asset definer as a second signer — every attempt by the AA to move that asset (either as a normal response output or as part of the `bounce()` refund path) will fail core payment validation. When this failure happens inside `bounce()` itself, the AA's own re-entrant guard (`bBouncing`) causes the entire bounce, including any bytes and other assets bundled with it, to be silently dropped, permanently trapping the funds at the AA address.

### Finding Description
`validatePaymentInputsAndOutputs()` unconditionally enforces the asset's `cosigned_by_definer` and `is_transferrable` flags on every payment, regardless of who the current spender is: [1](#0-0) [2](#0-1) 

An AA is explicitly forbidden from *defining* an asset with `cosigned_by_definer: true`, because the developers recognize an AA cannot cosign: [3](#0-2) 

However, nothing prevents a regular (non-AA) address from defining such an asset and then sending it to an arbitrary AA as trigger output. When the AA later tries to move that balance — either in its normal state-transition messages or in the automatic `bounce()` refund path — the unit it composes is validated the same way any other unit is, via `executeStateUpdateFormula`/`validateAndSaveUnit`, and fails with `"must be cosigned by definer"` or `"the asset is not transferrable"`: [4](#0-3) 

That failure calls `bounce(err)`. The `bounce()` function has a re-entrancy guard `bBouncing` that, once set, causes any subsequent call to `bounce()` to silently `finish(null)` without sending any refund unit at all — even for the other, unaffected assets/bytes bundled in the same trigger: [5](#0-4) 

So the sequence is:
1. AA receives a trigger carrying the poisoned asset (plus possibly bytes/other assets).
2. AA's primary logic tries to forward/spend the poisoned asset (or some unrelated condition causes a bounce) → `sendUnit` fails validation → `bounce(err)` is invoked (first time, `bBouncing` becomes `true`).
3. `bounce()` builds refund messages for *all* assets in `trigger.outputs`, including the poisoned one, and calls `sendUnit(messages)`.
4. `sendUnit` validation again fails on the poisoned asset's transfer/cosign restriction → `bounce(err)` invoked a second time.
5. Because `bBouncing` is already `true`, this second call returns `finish(null)` immediately — no unit is emitted, no state change occurs, and none of the trigger's funds (poisoned asset or otherwise) are returned.

The net effect: the trigger's funds are credited to the AA's balance in bookkeeping, but there is no code path by which the AA can ever move them out again, because every attempted payment of that asset fails the same definer-authorization checks that the AA structurally cannot satisfy (it cannot co-sign with the definer in any autonomous response). This directly mirrors the Eigenlayer report's root cause: a downstream authorization flag (`thirdPartyTransfersForbidden` / `cosigned_by_definer`) that is decoupled from and unenforceable by the acting contract/AA, causing its core fund-movement routine (`rebalance()` / AA `bounce`/response) to permanently revert and lock funds.

### Impact Explanation
Any unprivileged user can craft an asset with `cosigned_by_definer: true` (or a restrictive `is_transferrable: false` combination) and send it into any AA that accepts arbitrary triggers/assets (e.g., exchange or pool-style AAs that echo back received assets, or simply any AA whose bounce path would need to refund it). Once such an asset lands in the AA's balance, it becomes permanently frozen — unrecoverable by the AA, the original sender, or anyone else — and because a failed bounce silently swallows the *entire* batch, legitimate bytes/other assets bundled in the same trigger are also lost. This is a concrete "AA fund loss or freezing" condition triggered entirely by an unprivileged asset issuer/trigger sender.

### Likelihood Explanation
Reachable by any unprivileged address: defining an asset via a normal `asset` message with `cosigned_by_definer: true` is unrestricted for non-AA issuers, and sending assets to any AA via a trigger unit is a standard, permissionless operation. No special privileges, timing, or race conditions are required — only that the target AA accepts/handles arbitrary assets in its trigger outputs (common in exchange/liquidity-style AAs) and that some bounce condition is eventually reached for a unit carrying the poisoned asset.

### Recommendation
- Before crediting/handling non-`base` assets received by an AA, validate (in `aa_composer.js`) that the asset does not carry `cosigned_by_definer: true` and, if `is_transferrable: false`, that the AA itself is the definer, or otherwise reject/bounce the trigger immediately without registering the assets into the AA's spendable balance.
- Alternatively, make `bounce()`'s asset loop skip/burn only the problematic asset per-asset instead of aborting the entire refund via the `bBouncing` guard, so unaffected bytes/assets in the same trigger are not also frozen.
- Document and enforce (at the protocol or wallet-composition layer) that `cosigned_by_definer` assets should not be treated as normal transferable payloads sent into AAs, since AAs cannot fulfill multi-author cosigning.

### Proof of Concept
1. Address `U` (not an AA) issues asset `P` with `{ is_private: false, is_transferrable: true, fixed_denominations: false, issued_by_definer_only: true, cosigned_by_definer: true, spender_attested: false }`. This definition passes `validateAssetDefinition` because the `cosigned_by_definer` restriction on AA-defined assets in `aa_validation.js` only applies to `asset` messages authored by an AA, not by `U`.
2. `U` sends a trigger unit to any AA `X` carrying, among the trigger outputs, some amount of asset `P` (issued to itself first, then transferred alongside base bytes as trigger outputs — `U` is the definer so this transfer to `X` satisfies the "definer on either side" rule inbound; the issue is on the way *out* of `X`).
3. If `X`'s primary-trigger logic ever attempts to forward, return-as-change, or refund asset `P` (either via its own state-transition `payment` messages or via the implicit `bounce()` fallback), `validatePaymentInputsAndOutputs` rejects the unit with `"must be cosigned by definer"` because `X`'s authors array only contains `X`'s own address, never `U`'s (`aa_composer.js` cannot add a second signer).
4. `sendUnit` propagates this error into `bounce(err)`. Since this is the (at least) second bounce attempt for the same trigger, `bBouncing` is `true`, so `bounce()` returns `finish(null)` — no refund unit is ever produced.
5. Asset `P` (and any bytes bundled in the same trigger) remain permanently credited to `X`'s balance with no code path capable of spending them out, since every future attempt hits the same `cosigned_by_definer` check.
