### Title
Cross-repository status injection via unscoped `Commit.where(sha:)` lookup in `StatusHandler#process` - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` resolves target commits by bare SHA with no repository/stack scoping, so a `status` webhook that is legitimately signed for an attacker-owned repository (e.g. a fork of the victim's public repo, which shares identical commit SHAs) can write a `buildkite/deploy` `success` status onto the victim stack's `Commit` row for that same SHA. On a stack with `merge_queue_enabled: true`, this state flip triggers `stack.schedule_merges`, advancing the merge queue against attacker-controlled status data.

### Finding Description
The broken invariant, stated as an equality that the code never enforces:

`commit.stack.repository.full_name == webhook_payload.dig('repository','full_name')`

should hold before `StatusHandler` mutates any `Commit`, but it does not.

Code path:
- `Shipit::WebhooksController#create` parses the JSON body and dispatches to handlers for the `status` event after `verify_signature`, which only checks that the HMAC matches the secret configured for `repository_owner` (`params.dig('repository','owner','login')`) — i.e., it proves the request came from GitHub for *some* repository owned by that account/org, not that the SHA belongs to that repository's stack. [1](#0-0) 
- `StatusHandler#process` then does:
```ruby
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
```
with no filter on repository, owner, or stack id. [2](#0-1) 
- `Commit#create_status_from_github!` → `add_status` replicates the status and, on a state transition to `pending?` or `success?`, calls `stack.schedule_merges`:
```ruby
if previous_status.simple_state != new_status.simple_state
  ...
  stack.schedule_merges if new_status.pending? || new_status.success?
end
``` [3](#0-2) 

Because git commit SHAs are content-addressed, an attacker who forks a victim's public repository obtains a repository they own that contains commits with the **exact same SHAs** already tracked by the victim's Shipit `Stack`. The attacker's own GitHub-side automation (their own CI, or a manual API call against their own fork/installation) emits a genuine, correctly-signed `status` webhook with `context: buildkite/deploy`, `state: success`, and `sha` equal to one of these shared commits. `verify_signature` passes because the webhook truly originates from GitHub for the attacker's own repository. `StatusHandler#process`, however, matches on bare SHA across all stacks in the database, so it also updates the **victim's** `Commit` row for that SHA — flipping the `buildkite/deploy` status the victim stack requires. If `merge_queue_enabled` is true on the victim stack, this success state change reaches `stack.schedule_merges`, letting the attacker's forged status drive the merge queue.

`ExplicitParameters` only validates the shape of the payload (`sha`, `state`, `context` types), not repository ownership, so it provides no protection here. `drop_unhandled_event` and `check_if_ping` are irrelevant gates for event type only.

### Impact Explanation
An attacker with no Shipit privileges can inject a fabricated CI status onto a victim stack's commit purely by controlling their own fork/repository, causing the victim's merge-queue evaluation (and any deployability computation depending on `buildkite/deploy`) to be based on forged data. This is a payload authenticated for one repository mutating another repository's stack/commit state — matching the "Critical: a payload for one repository mutating another's stack, commit, task or team" / "unauthorized deploy, rollback or merge" category when combined with `merge_queue_enabled`. It is repeatable against any public repository that has commits shared with a forkable/mirrorable victim repo and is not limited to a single stack.

### Likelihood Explanation
Preconditions: victim's repository must be public (or otherwise forkable/mirrorable by the attacker) so SHAs can be reproduced in an attacker-owned repo; victim stack must require/watch `buildkite/deploy` context and have `merge_queue_enabled: true`. Attacker cost is low: fork the repo, install/trigger their own status-posting automation for shared SHAs, no Shipit credentials or GitHub secrets needed. This is fully repeatable per SHA and per victim stack meeting these conditions.

### Recommendation
Scope the `Commit` lookup in `StatusHandler#process` (and the analogous `CheckRunHandler`/other SHA-keyed handlers) by the repository identified in the webhook payload — e.g., resolve `Repository` from `params.dig('repository','full_name')`/owner+name, then restrict `Commit.where(sha: ...)` to `stack: Stack.where(repository: repo)` before applying the status, rejecting or ignoring updates where the commit's stack repository does not match the webhook's authenticated repository.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb`-style):
1. Create two `Stack`s, `victim_stack` (with `merge_queue_enabled: true`, `required_statuses` including `buildkite/deploy`) and `attacker_stack`, backed by different `Repository` records (different full_names).
2. Create a `Commit` with the same `sha` under both `victim_stack` and `attacker_stack` (simulating shared history via fork).
3. Assert baseline: `victim_commit.deployable?` is `false` (no successful `buildkite/deploy` status yet) — LHS of binding: `victim_commit.stack.repository.full_name != attacker_repository.full_name`.
4. Build a `status` payload with `sha: shared_sha`, `context: 'buildkite/deploy'`, `state: 'success'`, and a `repository` block matching `attacker_stack`'s repo.
5. Call `Shipit::Webhooks::Handlers::StatusHandler.new.call(payload)` (or `.process`) directly (bypassing controller-level signature check, per the question's threat model that a signed webhook for the attacker's own repo is genuine).
6. Assert that `victim_commit.reload.status.success?` is now `true` and that `victim_stack.schedule_merges` was invoked/queue advanced — proving the binding `commit.stack.repository == webhook.repository` was violated and a cross-repository write occurred.
7. Assert repeatability by using a different shared SHA against a second victim stack.
