## Analysis

This confirms the exploitable binding mismatch analog to the ERC-7484 "verified set ≠ acted-upon set" bug class.

### Title
Webhook signature is verified against the organization derived from `repository.owner.login`, but event handlers act on the independently-controlled `repository.full_name` field, allowing a malicious GitHub organization to forge webhooks for any repository - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/webhook secret to validate the HMAC signature against by reading `repository.owner.login` (falling back to `organization.login`) out of the **same untrusted JSON body** it is about to verify. [1](#0-0) [2](#0-1) 

Once the signature check passes, `create` dispatches the full raw payload to `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`. [3](#0-2) 

But every handler resolves the target `Stack`/`Repository` from a **different** field — `payload.dig('repository', 'full_name')` — via `Handler#repository_name` / `Handler#stacks`, with no cross-check that `full_name`'s owner matches the `owner.login` used to select the verifying organization's secret. [4](#0-3) [5](#0-4) 

### Finding Description
The binding that should hold is:
`organization whose secret authenticated the payload == organization that owns the repository the handler writes to`

Because both values are read from the same attacker-supplied JSON body, and Shipit supports multiple GitHub Apps/organizations each with their own `webhook_secret` (`Shipit.github(organization:)` / `github_app_config`), an attacker who controls (or has installed a Shipit-connected GitHub App/organization for) `attacker-org` knows `attacker-org`'s own `webhook_secret`. They can craft a raw POST body such as:

```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-controlled-sha>",
  "repository": {
    "full_name": "victim-org/victim-repo",
    "owner": { "login": "attacker-org" }
  }
}
```

`repository_owner` resolves to `attacker-org` (from `repository.owner.login`), so `Shipit.github(organization: "attacker-org")` is used to verify the signature — which the attacker can correctly compute since they know that org's `webhook_secret`. [1](#0-0) 

The signature check passes, and `create` calls the registered handler (e.g. `PushHandler`) with the full payload. `PushHandler#process` (via `Handler#stacks`/`Handler#repository_name`) looks up `Repository.from_github_repo_name("victim-org/victim-repo")` — completely independent of the org whose secret was verified — and calls `stack.sync_github(expected_head_sha: params.after)` on every matching, non-archived stack. [4](#0-3) [6](#0-5) 

This is structurally identical to the ERC-7484 finding: the field that gets *verified* (`repository.owner.login`, used to pick the signing key) is not the field that gets *acted upon* (`repository.full_name`, used to select what state is written), and nothing enforces they refer to the same repository/organization.

### Impact Explanation
An attacker who administers their own GitHub organization/App connected to this Shipit instance (a scenario explicitly supported by the multi-org config in `config/secrets.development.shopify.yml` / `docs/setup.md`) can forge `push`, `status`, `check_suite`, `pull_request`, etc. webhooks that are attributed to (and act on) a victim repository/stack they do not own. Depending on handler:
- `PushHandler` triggers `stack.sync_github(expected_head_sha: ...)` for the victim stack with an attacker-chosen "after" SHA, corrupting synced state and potentially the deployable HEAD used to decide what gets shipped.
- `StatusHandler` lets the attacker inject arbitrary CI status for any commit sha simply by knowing it, since `StatusHandler#process` looks up commits by `sha` globally with no repository scoping check tied to the verified org at all. [7](#0-6) 

Forged/failed CI statuses feed directly into `Commit#deployable?` and merge-queue gating (`Stack#deployable?`, `Stack#merge_status`), so this can be used to mark unreviewed/broken commits as deployable or to block/poison a victim's deploy pipeline — this satisfies the "unauthorized deploy" bar since deployability gating is subverted by a party never authorized for that repository. [8](#0-7) 

### Likelihood Explanation
Requires the attacker to control/administer a GitHub organization that already has a legitimate GitHub App installed against this Shipit instance (a normal, documented multi-org configuration, not a privileged Shipit account) — no `ApiClient` token, `webhook_secret` of the victim, or repository write access to the victim repo is needed. The only requirement is knowledge of the attacker's own org's `webhook_secret`, which the attacker inherently possesses.

### Recommendation
After signature verification, re-derive the organization from `repository.full_name`'s owner (or from `params.dig('repository','owner','login')` consistently used for both verification and dispatch), and reject the webhook if it does not match the organization whose secret validated the signature. Alternatively, verify using per-repository-scoped secrets (e.g., `GithubHook` records already store a `secret` per repo/org) rather than trusting attacker-supplied fields to select the verification key.

### Proof of Concept
1. Attacker's org `attacker-org` has a Shipit-integrated GitHub App with webhook secret `S_attacker` (known to the attacker as owner of that org/App).
2. Attacker crafts body:
```json
{"ref":"refs/heads/master","after":"deadbeef...","repository":{"full_name":"victim-org/victim-repo","owner":{"login":"attacker-org"}}}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(S_attacker, body)`.
4. POST to `/webhooks` with header `X-Github-Event: push`.
5. `verify_signature` resolves `repository_owner` = `"attacker-org"`, loads `Shipit.github(organization: "attacker-org")`, and the signature validates.
6. `PushHandler.call(params)` resolves `Repository.from_github_repo_name("victim-org/victim-repo")` and invokes `sync_github(expected_head_sha: "deadbeef...")` on the victim's stacks — attacker-controlled action performed on a repository the attacker never authenticated for.
