### Title
Unfiltered `machine.environment` (e.g. `RUBYLIB`) from an attacker's `shipit.yml` reaches `PTY.spawn` via `Command#unbundled_env` - (File: `app/models/shipit/deploy_spec.rb`, `lib/shipit/task_commands.rb`, `lib/shipit/command.rb`)

### Summary
`DeploySpec#machine_env` reads `machine.environment` straight from the `shipit.yml` checked out for the task, with no allow-list, unlike `deploy_variables`/task `variables` which are always passed through `EnvironmentVariables#permit`. For a `ReviewStack`, that `shipit.yml` is fetched at the exact PR head commit, so a PR author fully controls its contents. That unfiltered hash flows through `TaskCommands#env` → `Command#env` → `Command#unbundled_env` → `PTY.spawn(unbundled_env, *interpolated_arguments, ...)`, so a key like `RUBYLIB` set in the attacker's own `shipit.yml` is present in the environment of every subsequently spawned shell step.

### Finding Description
The broken binding: it is assumed that `Command#env` (the hash reaching `PTY.spawn`) is always constrained to `Shipit.env` (operator config) ∪ operator-declared `deploy_variables`/task `variables` (both sanitized via `EnvironmentVariables#permit`, see `app/models/shipit/deploy_spec.rb:174-180` and `app/models/shipit/task_definition.rb:63-65`). In reality:

- `DeploySpec#machine_env` is defined as `config('machine', 'environment') || {}` (`app/models/shipit/deploy_spec.rb:69-71`), with **no call to `EnvironmentVariables#permit`**.
- `TaskCommands#env` merges this unfiltered hash directly: `.merge(deploy_spec.machine_env)` (`lib/shipit/task_commands.rb:33-48`), after the sanitized deploy/task env has already been merged.
- `deploy_spec` is `DeploySpec::FileSystem.new(@task.working_directory, @stack)` (`lib/shipit/task_commands.rb:13-15`) — i.e., it is parsed from the actual git checkout of the commit being run, not from a cached/pinned trusted spec.
- For a `ReviewStack`, `@task.working_directory` is checked out at the PR's `until_commit`/`since_commit` SHA (`checkout` in `lib/shipit/task_commands.rb:50-59`), which for a fork-originated PR is the attacker's own commit, fetched by SHA via `StackCommands#fetch_commit`/`#fetch` (`lib/shipit/stack_commands.rb:17-35`) — GitHub makes commits belonging to an open PR fetchable from the base repository even when they only exist on a fork.
- `Command#env`/`unbundled_env` performs no key allow-listing at all (`lib/shipit/command.rb:103-105`): `BASE_ENV.merge('PATH'=>...).merge(@env.stringify_keys)` — any key the caller supplies, including `RUBYLIB`, `LD_PRELOAD`, `BUNDLE_GEMFILE`, etc., is passed straight through.
- `Command#parse_arguments` (`lib/shipit/command.rb:227-240`) keeps a `shipit.yml` step as a single string; `start` calls `PTY.spawn(unbundled_env, *interpolated_arguments, chdir: @chdir)` (`lib/shipit/command.rb:92`) — with a single string element this is executed via `/bin/sh -c`.

Exploit flow: an attacker opens/labels a PR against an `allow_with_label` review-stack repository and, in their own fork's `shipit.yml`, sets `machine: {environment: {RUBYLIB: "/tmp/evilpath"}}` (or any similarly dangerous variable). When Shipit runs any review/deploy/task step that shells out to `ruby` (directly, or transitively via `bundle exec`, `rake`, `cap`, etc.), the injected `RUBYLIB` causes that ruby process's `require` calls to resolve against attacker-supplied files, achieving code execution on the Shipit deploy host under the Shipit worker's privileges.

Existing guards do not stop this because they target a different surface: `filter_deploy_envs`/`filter_rollback_envs`/`TaskDefinition#filter_envs` (all backed by `EnvironmentVariables#permit`) constrain the API-supplied `env:` parameter on deploy/task triggers, but `machine_env` is a completely separate code path that bypasses `permit` entirely. `provisioning_behavior`/label gating (`labeled_handler.rb`, `opened_handler.rb`) only controls whether a review stack is created/kept alive; it does not constrain what the `shipit.yml` inside that PR's own checkout may contain.

### Impact Explanation
Any environment variable set under `machine.environment` in a PR's own `shipit.yml` is merged unfiltered into the environment of every shell-interpreted step Shipit executes for that review stack's deploy/rollback/review/task commands (`lib/shipit/task_commands.rb:33-48`, `lib/shipit/command.rb:92`). Interpreter-hijacking variables (`RUBYLIB`, `GEM_PATH`, `BUNDLE_GEMFILE`, `PYTHONPATH`, `NODE_OPTIONS`, `LD_PRELOAD`, etc.) let the PR author execute arbitrary code as the Shipit deploy-host user the moment any step invokes the corresponding interpreter — this is Remote Code Execution on the deploy host, matching the Critical severity category (`Command`/`PTY.spawn` RCE). Because Shipit hosts and their `PATH`/`Shipit.shell_paths`/secrets are shared across all stacks handled by that worker, this is a full blast-radius compromise of the Shipit host, not limited to the attacker's own repository/stack.

### Likelihood Explanation
Preconditions: the target repository must have `review_stacks_enabled` and `provisioning_behavior_allow_with_label` (or `allow_all`) configured, and the attacker must be able to add the configured provisioning label to their own PR (self-serviceable if they have any write to their own PR's labels, or trivially achievable under `allow_all`). No Shipit credentials, GitHub App keys, or maintainer approval are required — this is exactly the documented "opt-in" review-stack workflow intended for external contributors. The attack is a single, repeatable `shipit.yml` edit in the attacker's own fork; every subsequent task/deploy/rollback run against that review stack re-triggers the injection.

### Recommendation
Sanitize `DeploySpec#machine_env` the same way `deploy_variables`/task `variables` are sanitized: require operator-declared allow-lists (e.g., an operator-controlled `machine.environment` schema validated against `Shipit.env`/`secrets.yml`) rather than accepting arbitrary keys straight from the repository's own `shipit.yml`, especially for review stacks whose spec is sourced from unprivileged, fork-controllable commits. Additionally, add a hard deny-list/allow-list at `Command#unbundled_env` for known interpreter-hijacking variables (`RUBYLIB`, `LD_PRELOAD`, `PYTHONPATH`, `NODE_OPTIONS`, `BUNDLE_GEMFILE`, `GEM_PATH`, etc.) so that no per-task `env` hash — regardless of origin — can override these host-critical variables.

### Proof of Concept
minitest plan (unit-level, no live GitHub required):
```ruby
test "machine_env from an untrusted shipit.yml reaches the spawned command's env unfiltered" do
  repository = shipit_repositories(:shipit)
  configure_provisioning_behavior(repository:, behavior: :allow_with_label, label: "pull-requests-label")

  # simulate attacker-controlled shipit.yml checked out at the PR head commit
  stack = shipit_stacks(:review_stack)
  deploy_spec = DeploySpec.new(
    "machine" => { "environment" => { "RUBYLIB" => "/tmp/evil-load-path" } },
    "deploy" => { "override" => ["ruby -e 'require \'pwn\''"] }
  )
  DeploySpec::FileSystem.any_instance.stubs(:cacheable).returns(deploy_spec)
  DeploySpec::FileSystem.any_instance.stubs(:machine_env).returns(deploy_spec.machine_env)

  task = shipit_deploys(:review_stack_deploy) # a Deploy/Task belonging to `stack`
  commands = TaskCommands.new(task)

  # Binding under test:
  # LHS (expected/invariant): commands.env['RUBYLIB'] should be nil/absent (no fork-controllable key
  #   should reach the interpreter env without going through EnvironmentVariables#permit)
  # RHS (actual): the value injected via the untrusted shipit.yml's machine.environment
  assert_nil commands.env['RUBYLIB'], "RUBYLIB should not be settable from an unfiltered shipit.yml"

  # Demonstrate propagation into the spawned Command's actual env hash used by PTY.spawn
  command = commands.perform.first
  assert_equal "/tmp/evil-load-path", command.env['RUBYLIB']
  assert_equal "/tmp/evil-load-path", command.unbundled_env['RUBYLIB']
end
```
The first assertion (`assert_nil`) is expected to **fail** on the current code, proving the binding is broken: `commands.env['RUBYLIB']` equals the attacker-supplied value instead of being absent/allow-listed, and that same value is confirmed present in `command.unbundled_env`, the exact hash passed to `PTY.spawn`. # frozen_string_literal: true

module Shipit
  class EnvironmentVariables
    NotPermitted = Class.new(StandardError)

    class << self
      def with(env)
        EnvironmentVariables.new(env)
      end
    end

    def permit(variable_definitions)
      return {} unless @env
      raise "A whitelist is required to sanitize environment variables" unless variable_definitions

      sanitize_env_vars(variable_definitions)
    end

    def interpolate(argument)
      return argument unless @env

      argument.gsub(/(\$\w+)/) do |variable|
        variable.sub!('$', '')
        Shellwords.escape(@env.fetch(variable) { ENV[variable] })
      end
    end

    private

    def initialize(env)
      @env = env
    end

    def sanitize_env_vars(variable_definitions)
      allowed_variables = variable_definitions.map(&:name)

      allowed, disallowed = @env.partition { |k, _| allowed_variables.include?(k) }.map(&:to_h)

      error_message = "Variables #{disallowed.keys.to_sentence} have not been whitelisted"
      raise NotPermitted, error_message unless disallowed.empty?

      allowed
    end
  end
end
