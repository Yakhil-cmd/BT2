### Title
Stale shared-address cosigner list causes private payment data to leak to removed cosigners - ([File: wallet_defined_by_addresses.js])

### Summary
When forwarding private (blinded) payment chains to cosigners of a shared/multisig address, ocore resolves the list of devices to notify from the `shared_address_signing_paths` table, which is populated once when the shared address is created and is never updated when the address's definition is later changed (e.g. a cosigner is removed via an `address_definition_change`). As a result, a device that was removed from an address's definition keeps receiving full private-payment payloads (amounts, addresses, blinding factors, prior chain history) for that address indefinitely, exactly mirroring the GitLab bug class where a stale reference to a prior (now-invalid) authorization/membership context caused private data to leak to a party that should no longer have access.

### Finding Description
`shared_address_signing_paths` is populated exactly once, when a shared address is first created via `addNewSharedAddress`: [1](#0-0) [2](#0-1) 

This table is the sole source used to route private-payment forwarding to cosigners of a shared address: [3](#0-2) [4](#0-3) 

and it's consumed from `wallet.js` both when a light/full node receives a new private payment (`handlePrivatePaymentChains` → `forwardPrivateChainsToOtherMembersOfOutputAddresses`) and when composing a new payment (`sendMultiPayment` → `forwardPrivateChainsToOtherMembersOfSharedAddresses`): [5](#0-4) [6](#0-5) 

Separately, ocore fully supports changing an address's definition on-chain (`address_definition_changes`, validated e.g. via the `seen definition change` evaluator): [7](#0-6) 

However, none of the code that applies a definition change (`writer.js`, `validation.js`, `storage.js`) touches `shared_address_signing_paths` — that table is never pruned or updated when a member is removed from an address's definition. Consequently, `readAllControlAddresses`/`forwardPrivateChainsToOtherMembersOfAddresses` will keep resolving and forwarding private payment chains to the device of a cosigner who has since been dropped from the address's actual current definition.

This is directly analogous to BIT-gitlab-2022-0344: in both cases, an object's authorization/visibility context changes (issue moved to a public project / address definition changed to drop a cosigner), but a piece of retained metadata (the system note referencing the old private path / the `shared_address_signing_paths` row referencing the old member) is never invalidated, so subsequent activity keeps disclosing private information to a party who is no longer supposed to have access.

### Impact Explanation
Any legitimate private-asset payment sent to, or forwarded through, a shared/multisig address whose definition was changed to remove a cosigner will still be silently forwarded (with full plaintext amounts, addresses, and blinding factors reconstructing the private payment chain) to the removed cosigner's device. This is an unauthorized disclosure of private financial data to a party that the wallet owner explicitly intended to strip of access/control over the address, undermining the confidentiality guarantee of private assets (a core feature of ocore) — classified Medium severity as a confidentiality breach of private-asset transaction data, without directly enabling fund theft.

### Likelihood Explanation
Reachable by any unprivileged private-payment counterparty: simply sending (or causing to be forwarded) a private payment to/through a shared address is a normal wallet operation that any private-asset payer can trigger. The only additional condition is that the address owner previously executed a routine, supported feature (changing a shared address's definition to remove a member) — no malicious peer/node behavior is required, and the removed device does not need to do anything to receive the leaked data; it simply remains a registered recipient in stale local state.

### Recommendation
When an `address_definition_change` is validated/applied for an address that is also a `shared_addresses` entry, update or invalidate the corresponding rows in `shared_address_signing_paths` (and any per-device forwarding decisions derived from it) to reflect the new definition's actual member set, so that private payment forwarding logic (`forwardPrivateChainsToOtherMembersOfAddresses`, `readAllControlAddresses`) only notifies currently-authorized cosigner devices.

### Proof of Concept
1. Device A and Device B jointly create a shared/multisig address `S` (`addNewSharedAddress` populates `shared_address_signing_paths` for A and B) — see [2](#0-1)  .
2. The owner later changes the definition of `S` on-chain to remove Device B as a signer (standard `address_definition_change`) — validated per [7](#0-6) ; `shared_address_signing_paths` is not updated.
3. Any counterparty sends a private-asset payment to `S`. On receipt, `handlePrivatePaymentChains` calls `forwardPrivateChainsToOtherMembersOfOutputAddresses`, which still queries `shared_address_signing_paths` and forwards the full private payment chain to Device B — see [5](#0-4)  and [3](#0-2) .
4. Device B, despite no longer being a valid cosigner of `S`, receives and can decode the private payment data (amounts, addresses, blinding) for an address it no longer controls.

function readAllControlAddresses(conn, arrAddresses, handleLists){
	conn = conn || db;
	conn.query(
		"SELECT DISTINCT address, shared_address_signing_paths.device_address, (correspondent_devices.device_address IS NOT NULL) AS have_correspondent \n\
		FROM shared_address_signing_paths LEFT JOIN correspondent_devices USING(device_address) WHERE shared_address IN(?)", 
		[arrAddresses], 
		function(rows){
			if (rows.length === 0)
				return handleLists([], []);
			var arrControlAddresses = rows.map(function(row){ return row.address; });
			var arrControlDeviceAddresses = rows.filter(function(row){ return row.have_correspondent; }).map(function(row){ return row.device_address; });
			readAllControlAddresses(conn, arrControlAddresses, function(arrControlAddresses2, arrControlDeviceAddresses2){
				handleLists(_.union(arrControlAddresses, arrControlAddresses2), _.union(arrControlDeviceAddresses, arrControlDeviceAddresses2));
			});
		}
	);
}
