### Title
Permanent market freeze via i128 RAY-value overflow in accrual — unprivileged supplier/borrower can wedge a market so no repay, withdraw, liquidation, or bad-debt cleanup can ever execute - (File: common/src/rates/simulate.rs)

### Summary
The MariaDB report's bug class is a denial of service triggered by a specially crafted input pushed through a copy/conversion operator. The analog in XOXNO Lending is `accrue_step`: it unconditionally rescales total debt and total supply through `scaled_to_original` (`Ray::mul`), which panics with `GenericError::MathOverflow` on `i128` overflow. Every state-changing entrypoint on a market — including repay, withdraw, liquidate, clean_bad_debt, recapitalize, and claim_revenue — runs `interest::global_sync` first, so once `borrowed × borrow_index` (or `supplied × supply_index`) exceeds `i128::MAX`, the market is permanently bricked and all supplier funds are frozen forever.

### Finding Description
`contracts/pool/src/interest.rs::global_sync` runs `accrue_chunk` → `common/src/rates/simulate.rs::accrue_step`, which computes `scaled_to_original(env, borrowed, borrow_index)` and `scaled_to_original(env, supplied, supply_index)` before anything else (`simulate.rs:60-61`). `scaled_to_original` is `scaled.mul(env, index)` → `fp_core::mul_div_half_up`, which panics on `i128` overflow (`common/src/rates/scaling.rs:14-15`, `common/src/math/fp.rs`). The pool README confirms the fixed sequence `entrypoint → Cache::load → interest::global_sync → mutate → guards` for every market verb (`contracts/pool/README.md:159-168`). Index bounds (`MAX_BORROW_INDEX_RAY`/`MAX_SUPPLY_INDEX_RAY` = 1e36) cap the *index* but not the *product*: `calculate_supplier_rewards` and the utilization read both multiply `borrowed`/`supplied` by the index, so a book whose scaled shares are large can cross the `i128` value ceiling well before the index cap engages. The harness test `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` demonstrates exactly this: at 98% utilization on a steep curve the index grows past ~170x, `update_indexes` panics with `MATH_OVERFLOW`, and afterwards `withdraw` and `repay` revert with the same error (`tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:316-361`).

Reachability by a single unprivileged address:
- `supply` a very large amount of a high-decimal listed asset (caps are the only gate; on an 18-decimal listing the admitted maximum is ~170 billion whole tokens, and the scaled-share ceiling is reached at ~170 million whole tokens per the numeric-limits table in `docs/reference/formulas.md:425-430`).
- `borrow` up to the utilization limit so the borrow index compounds at the steep curve segment.
- Anyone can then call `update_indexes`; once the accrual product overflows, every subsequent call to *any* verb on that market reverts in `global_sync` before reaching the mutation or guard phase. `clean_bad_debt` does not help — `socialize_bad_debt` calls `risk::calculate_account_risk_totals`, which fetches indexes via `Context`-cached simulated accrual over the same `accrue_step` math, and any pool-side seizure/exit accrues first. `recapitalize` also accrues first (it is a market mutation). There is no path that skips accrual.

### Impact Explanation
Permanent freezing of funds: once the market crosses the value ceiling, all supplier claims in that market are unrecoverable — `withdraw` reverts, `repay` reverts, `liquidate`/`seize_positions` revert, `claim_revenue` reverts, and `clean_bad_debt`/`recapitalize` revert. The panic is in shared read-only arithmetic (`accrue_step`), so even `get_bulk_indexes` and controller account views that simulate the market revert. Borrower debt is equally frozen — the attacker loses their collateral position too, but every supplier in the market loses everything. This maps to the accepted impact "permanent freezing of funds / contract unable to operate."

### Likelihood Explanation
Likelihood is constrained but nonzero, and it needs only unprivileged calls plus time:
- Requirements: a listed market whose caps admit a large position, an 18-decimal (or high-decimal) asset, and sustained high utilization at a high borrow-rate curve segment. The max borrow rate is 200% APR (`docs/reference/formulas.md:428`); at that rate the index multiplies ~7.4x/year, so a book near the RAY domain edge crosses `i128::MAX` after a few years, exactly as the harness test measures. No governance action, no oracle manipulation, and no privileged parameter is needed — the attacker supplies, borrows against their own collateral in a second market, and waits (or repeatedly calls the permissionless `update_indexes` to keep accrual chunked favorably).
- Cheaper variant: `supplied × supply_index` also overflows independently — pure supply volume, with no borrow needed, can wedge the market through the `supplied_original` multiplication in `accrue_step:61`, and the revenue-share mint inside `accrue_chunk` grows `supplied` each chunk, accelerating the crossing.
- The docs themselves acknowledge "Value overflow can occur before the index ceiling and block repayment/withdrawal" (`docs/reference/formulas.md:432-437`) but treat it as a bound, not a fix — there is no ceiling alarm and no escape hatch, so the freeze is unmitigated once reached.

Severity: High (permanent freeze of all supplier funds in the affected market); likelihood bounded by the capital and time required, keeping it below Critical.

### Recommendation
Make accrual fail-safe rather than trapping the whole market:
- Compute `scaled_to_original` for the utilization/debt read inside `accrue_step` with a saturating multiplication (analogous to the existing `mul_div_floor_saturating` used by `calculate_scaled_cap`). At saturation, utilization pins at ≥ RAY 1.0 and accrued interest can be clamped to zero or to a bounded step rather than panicking, preserving repay/withdraw/liquidate paths.
- Alternatively, clamp `borrow_index`/`supply_index` growth at a *value-aware* ceiling inside `update_borrow_index`/`update_supply_index` — i.e., cap the index so that `borrowed × index` and `supplied × index` remain representable — and emit an alarm event when the clamp engages, matching the existing "no dedicated ceiling alarm" gap noted in the docs.
- Add a regression test mirroring `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` asserting that `withdraw`/`repay` still succeed after the value ceiling is reached.

### Proof of Concept
```rust
// Modeled on tests/test-harness/tests/controller/
// large_positions_and_long_horizons.rs:321-361

let mut t = LendingTest::new()
    .with_market(big("BIG18", 18, xlm_curve()))   // 18-decimal market, steep curve
    .with_market(col())
    .with_max_utilization_disabled_all_markets()
    .build();
lift_caps(&t, "BIG18", 18);
lift_caps(&t, "COL", 7);

// Unprivileged: attacker (or any whale) supplies ~1e9 whole 18-dec tokens and
// borrows ~98% of the book against collateral in the COL market.
let principal = BILLION * 10i128.pow(18);
t.supply_raw(BOB, "BIG18", principal);
t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
t.borrow_raw(ALICE, "BIG18", principal / 100 * 98);

// Permissionless update_indexes each year; index compounds at ~200% APR segment.
loop {
    t.advance_time(YEAR_SECS);
    if t.try_update_indexes_for(&["BIG18"]).is_err() { break; }
}
// borrow_index is BELOW MAX_BORROW_INDEX_RAY — the index cap never engaged —
// but borrowed * borrow_index no longer fits i128 inside
// common/src/rates/simulate.rs::accrue_step -> scaled_to_original.

// Permanent freeze: every verb accrues first via pool interest::global_sync.
assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), MATH_OVERFLOW); // suppliers stuck
assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0),   MATH_OVERFLOW); // debt stuck
// liquidate / clean_bad_debt / recapitalize / claim_revenue revert identically
// because each goes through Cache::load -> global_sync -> accrue_step.
```

```rust
pub(crate) fn global_sync(env: &Env, cache: &mut Cache) {
    if !cache.needs_accrual() {
        return;
    }

    let mut remaining = cache.elapsed_ms();
    while let Some(nonzero) = NonZeroU64::new(remaining) {
        let chunk = nonzero.get().min(MAX_COMPOUND_DELTA_MS);
        accrue_chunk(env, cache, chunk);
        remaining = remaining.saturating_sub(chunk);
    }

    cache.mark_accrued();
}
```
