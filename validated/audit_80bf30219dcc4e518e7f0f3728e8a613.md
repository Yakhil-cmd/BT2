### Title
CCMenu API endpoint bypasses ApiClient stack-scoping, allowing a token authorized for one stack to read the state of any stack - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::CCMenuController` overrides the `stack` lookup method used by the rest of the API to resolve the target stack directly from `params[:stack_id]` via `Stack.from_param!`, instead of using the stack-scoped collection (`stacks`) that every other controller in the `Api` namespace relies on. This breaks the binding between the stack an `ApiClient` token is authorized for and the stack the request actually touches.

### Finding Description
`Shipit::Api::BaseController` establishes the authorization model for API tokens: a token can optionally be scoped to a single stack via `ApiClient#stack_id`, and the `stacks` helper restricts the visible collection accordingly: [1](#0-0) 

Every other stack-scoped API controller resolves its target stack through this scoped `stacks` collection (see `stack` in `BaseController`, used as the default), which ensures `current_api_client.stack_id` — when set — actually constrains which stack can be manipulated or read.

`CCMenuController`, however, defines its own `stack` method that ignores this scoping entirely: [2](#0-1) 

It still declares `require_permission :read, :stack`, but `ApiClient#check_permissions!` only checks that the permission string `"read:stack"` is present in the token's `permissions` array — it performs no comparison against the specific stack being accessed: [3](#0-2) 

Because `stack` in `CCMenuController` calls `Stack.from_param!(params[:stack_id])` directly rather than `stacks.from_param!(...)`, a token that is scoped to Stack A (i.e. `api_client.stack_id == A.id`) and holds only `read:stack` permission can be replayed against `/api/stacks/*stack_id/ccmenu` with any other `stack_id`, and the controller will happily resolve and render that other stack's CCMenu status.

The equality that should hold but is broken:
`current_api_client.stack_id (the stack a token authorizes) == stack.id (the stack the request touches)`

For every other API endpoint this equality is enforced through `stacks.from_param!`; for `CCMenuController` it is not.

### Impact Explanation
This allows an attacker holding a legitimately-issued, narrowly-scoped `ApiClient` token (e.g. a CCMenu token auto-created per stack via `CCMenuUrlController`, or any other client explicitly scoped to a single stack with `read:stack` permission) to read the deploy/lock/build status (`lastBuildStatus`, `activity`, `lastBuildLabel`, lock state, etc., as exercised in `test/controllers/api/ccmenu_controller_test.rb`) of any stack in the Shipit instance, not just the one it was authorized for. This is an unauthorized cross-stack read of stack state, which corresponds to the High-severity impact class defined by the rules ("escalation into ... authorization, unauthenticated read of stack state, task streams or deploy output").

Note: I was unable to locate the actual `app/views/shipit/ccmenu/project.xml.erb` template in the index to confirm exactly which fields are rendered (the file was not found by direct lookup, likely excluded per the assets/views exclusion in scope, or index size limits), but `test/controllers/api/ccmenu_controller_test.rb` confirms the rendered XML exposes `name`, `activity`, `lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, `webUrl`, i.e., meaningful deploy/lock state.

### Likelihood Explanation
Any holder of a stack-scoped `ApiClient` token with `read:stack` permission — which is the normal, lowest-privilege token type created automatically for the CCMenu integration (`CCMenuUrlController#client`) or manually via the `api_clients` UI — can exploit this simply by changing the `stack_id` segment of the URL. No special privilege beyond possessing one valid, narrowly-scoped token is required, and the request is a simple unauthenticated-in-effect (from the target stack's perspective) HTTP GET.

### Recommendation
Change `CCMenuController#stack` to resolve through the scoped collection, consistent with `BaseController`:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
This ensures `current_api_client.stack_id`, when set, is enforced as an equality constraint against the stack being accessed, matching the behavior of every other API controller in the engine.

### Proof of Concept
1. Create Stack A and Stack B.
2. Create an `ApiClient` scoped to Stack A only (`stack_id: A.id`, `permissions: ['read:stack']`) — e.g. via the `/api_clients` UI, or automatically via visiting Stack A's CCMenu URL (`CCMenuUrlController#fetch`), which creates such a client.
3. Using that client's `authentication_token` (via Basic Auth per `BaseController#authenticate_api_client`, or the `token` query param used by `CCMenuController#authenticate_api_client`), send:
   `GET /api/stacks/<owner>/<stack-B-name>/<environment>/ccmenu`
4. Observe the response returns Stack B's CCMenu XML (`lastBuildStatus`, `activity`, lock state, etc.) with HTTP 200, even though the token was only ever authorized for Stack A.
