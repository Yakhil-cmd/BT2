### Title
Historical double-counting of a single deposit as two primary AA triggers can inflate an Autonomous Agent's perceived balance and let a proportional-payout AA over-pay claimants - (File: [aa_composer.js](aa_composer.js), [validation.js](validation.js))

### Summary
Byteball/Obyte Autonomous Agents (AAs) compute payouts based on the AA's tracked `aa_balances` and formulas such as "pay `share * balance[asset]`" (the same "repeated-claim-drains-shared-pool" pattern as the reported `Shelter.withdraw` bug, where funds are handed out proportionally to a pool that grows/shrinks as claims are processed). If the *same triggering unit* could ever cause the *same AA address* to be primary-triggered and have its `aa_balances` credited more than once for the coins it actually received once, later proportional-share payouts (e.g. "divest MM shares", `share = trigger_asset_amount / var['outstanding']`, `pay round(share*balance[asset])`) would pay out against an inflated balance that does not correspond to real, spendable coins - functionally identical to Mallory calling `Shelter.withdraw` a second time and being paid against value that isn't backed by her own deposit.

### Finding Description
`getTrigger()` sums all payment outputs in a unit that are addressed to a given AA into `trigger.outputs[asset]` [1](#0-0) . `handleTrigger()`'s `updateInitialAABalances()` then credits `aa_balances` by exactly that summed amount every time the trigger is handled [2](#0-1) . Nothing in `updateInitialAABalances` itself is idempotent against being invoked twice for the same `(mci, unit, address)` triple - each invocation blindly adds the trigger's outputs to the balance again.

The codebase shows that this was in fact a real historical risk that the developers had to explicitly guard against. `handleTrigger()` contains a dedicated check:
```
if (trigger.unit !== constants.GENESIS_UNIT && !trigger_opts.bAir && storage.assocStableUnits[trigger.unit].count_aa_responses && mci >= constants.pemCurvesFixMci)
    return bounce('a second primary trigger from the same unit is not allowed');
``` [3](#0-2) 

and `validateAATrigger()` in `validation.js` separately restricts a unit to at most one primary AA trigger and at most one output per asset to that AA, but only from `constants.pemCurvesFixMci` onward:
```
objValidationState.count_primary_aa_triggers = rows.length;
if (objValidationState.count_primary_aa_triggers > 1) {
    if (objValidationState.last_ball_mci >= constants.pemCurvesFixMci)
        return callback(`more than 1 primary AA trigger (${objValidationState.count_primary_aa_triggers})`);
    ...
}
if ((objValidationState.last_ball_mci >= constants.pemCurvesFixMci || ...) && objValidationState.count_primary_aa_triggers === 1) {
    for (let asset in outputCounts[address]) {
        if (outputCounts[address][asset] > 1)
            return callback(`more than 1 output to the same AA ${address} for asset ${asset}`);
    }
}
``` [4](#0-3) 

The existence of both of these gates - one in consensus validation and a second, independent one in the AA execution engine itself - is a strong signal that, prior to the `pemCurvesFixMci` upgrade, a single posted unit could be counted as more than one primary AA trigger (e.g. a unit with two output messages to the same AA address, or with outputs to the same AA for the same asset split across multiple outputs), and each of those triggers independently incremented `aa_balances` for coins that were only received once. An AA whose logic pays out shares proportional to `balance[asset]` (exactly the `Shelter`-style "pay according to my fraction of the pool" pattern demonstrated in the sample AAs, e.g. `uniswap_like_market_maker.oscript`'s "divest MM shares" case: `$investor_share = $mm_asset_amount / var['mm_asset_outstanding']; ... amount: round($investor_share * balance[$asset])`) [5](#0-4)  would then pay real coins out of its balance against an inflated, phantom portion of that balance - draining value that belongs to other share/token holders, exactly mirroring the external report's "share of the pool" over-payment mechanic.

### Impact Explanation
If the duplicate-trigger condition could still be reached today (e.g. via light-client dry-run estimation paths that use `bAir` and skip the guard, via nodes that haven't yet fully enforced `pemCurvesFixMci` semantics, or via any code path that calls `handlePrimaryAATrigger`/`handleTrigger` for the same `(mci, unit, address)` a second time without the `count_aa_responses` short-circuit engaging), the impact is High: an attacker's single genuine deposit would be credited twice to `aa_balances`, letting them (or any subsequent claimant relying on `balance[asset]`-proportional formulas) withdraw funds that were never actually deposited, draining the AA's real balance and defrauding other legitimate depositors/shareholders - the same "drain all funds" outcome as the original `Shelter.withdraw` finding.

### Likelihood Explanation
Likelihood is currently constrained because the two independent guards (`validateAATrigger`'s consensus-level rejection of >1 primary trigger / >1 same-asset output to an AA, and `handleTrigger`'s runtime `count_aa_responses` check) appear to close the exploitable window from `pemCurvesFixMci` onward. However, the very presence of these two separate patches for the same underlying issue, gated by an upgrade MCI rather than being an inherent invariant of the code, indicates the underlying mechanism (crediting `aa_balances` per triggering event rather than per genuinely-spent output, with no atomic "already processed this unit for this AA" invariant baked into `updateInitialAABalances` itself) is fragile. Any code path that reaches `handleTrigger`/`updateInitialAABalances` outside of the exact conditions checked by these two gates (for example the `bAir`-estimation code path, which explicitly bypasses the `handleTrigger` guard) remains a plausible vector for reintroducing double-counting, especially in edge cases around upgrades, catch-up/reorg reprocessing, or estimation-then-real-execution inconsistencies that were not exhaustively explored here.

### Recommendation
- Make the "at most one primary trigger per unit per AA, at most one output per asset" invariant a hard, unconditional invariant in the AA execution path itself rather than only in consensus validation gated by an upgrade MCI - i.e., have `updateInitialAABalances`/`handleTrigger` itself refuse to process a trigger a second time for a given `(unit, address)` regardless of `mci` or `bAir`, instead of relying on `count_aa_responses` which is only checked under specific `mci`/`bAir` conditions.
- Audit all callers of `handleTrigger` (including `estimatePrimaryAATrigger`'s `bAir` path) to confirm none of them can, even transiently, double-credit `aa_balances` for the same real output.
- Add invariant tests asserting that replaying `handlePrimaryAATrigger` for the same `(mci, unit, address)` is a no-op/rejected in every code path, not just the currently-guarded ones.

### Proof of Concept
Conceptual PoC (mirrors the Shelter PoC's "repeat the claim to steal others' share" structure):
1. An AA implements a pooled-share payout, e.g. the `divest MM shares` case in `uniswap_like_market_maker.oscript`, where a user's payout is `round(investor_share * balance[asset])` with `investor_share = trigger_asset_amount / var['outstanding']` [6](#0-5) .
2. A unit is crafted so that, under conditions predating (or otherwise bypassing) the `pemCurvesFixMci`/`count_aa_responses` guards, the same unit's output to the AA is counted as more than one primary trigger (e.g., `validateAATrigger`'s `count_primary_aa_triggers > 1` / `outputCounts[address][asset] > 1` scenario) [7](#0-6) .
3. Each duplicate trigger runs `updateInitialAABalances`, which increments `aa_balances[address][asset]` by the trigger's output amount again [8](#0-7) , without the attacker having deposited additional real coins.
4. A subsequent legitimate depositor's payout (or the attacker's own follow-up claim), computed as a fraction of the now-inflated `balance[asset]`, pays out more real bytes/asset coins than were ever deposited, draining the pool - the AA-level analog of Mallory's repeated `Shelter.withdraw()` calls.

Note: I was unable to fully trace, within the available search budget, whether any currently-reachable code path (outside the historically-patched consensus/`handleTrigger` conditions) can still trigger this double-credit today; this would require deeper review of `main_chain.js`'s AA-trigger scheduling logic and the `bAir`/dry-run estimation call sites, which the index did not surface in full detail.

function getTrigger(objUnit, receiving_address) {
	var trigger = { address: objUnit.authors[0].address, unit: objUnit.unit, outputs: {} };
	if ("max_aa_responses" in objUnit)
		trigger.max_aa_responses = objUnit.max_aa_responses;
	objUnit.messages.forEach(function (message) {
		if (message.app === 'data' && !trigger.data) // use the first data message, ignore the subsequent ones
			trigger.data = message.payload;
		else if (message.app === 'payment' && message.payload) {
			var payload = message.payload;
			var asset = payload.asset || 'base';
			payload.outputs.forEach(function (output) {
				if (output.address === receiving_address) {
					if (!trigger.outputs[asset])
						trigger.outputs[asset] = 0;
					trigger.outputs[asset] += output.amount; // in case there are several outputs
				}
			});
		}
	});
	if (Object.keys(trigger.outputs).length === 0)
		throw Error("no outputs to " + receiving_address);
	return trigger;
}
