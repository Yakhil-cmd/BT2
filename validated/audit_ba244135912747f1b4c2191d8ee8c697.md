### Title
System-parameter vote counting uses balance at count time, letting a flash-loan style buy/sell manipulate `op_list`/fee votes - ([File: main_chain.js])

### Summary
`countVotes()` in `main_chain.js` weighs each voter's ballot by their *current* bytes balance at the moment the vote is tallied, not by a balance snapshot taken when the vote was cast. Any address can trigger a count at will by posting a `system_vote_count` message, which any unprivileged unit author can send with no special requirement (only that it's not sent by an AA and only one per unit).

### Finding Description
Governance of `op_list` (the ordered list of witnesses/order-providers), `threshold_size`, `base_tps_fee`, `tps_interval`, and `tps_fee_multiplier` is decided by `system_vote` messages, weighted by the voter's byte balance, and finalized by anyone posting a `system_vote_count` message for the desired subject. [1](#0-0) 

A vote itself, once posted, is retained indefinitely in the `system_votes` / `op_votes` / `numerical_votes` tables until overridden by the same address; it is not weighted by the balance held at the time of casting. When any `system_vote_count` message stabilizes, `countVotes()` is invoked and it computes the weight for every voting address as the address's **current** stable-good balance at the moment of counting: [2](#0-1) 

The result for `op_list` sums balances per candidate op address and picks the top `COUNT_WITNESSES` (12) addresses as the new witness list; for numeric subjects it picks the balance-weighted median. [3](#0-2) 

Because the weight is taken from the balance at count time (not vote time), and because counting is triggered by an ordinary `system_vote_count` unit that anyone can send, an attacker can:
1. Cast a `system_vote` for their preferred `op_list`/parameter once (cheaply, with a trivial balance).
2. Wait until they can amass a large temporary balance (e.g., borrow/acquire a large amount of bytes for one block via an exchange, DEX swap, or coordinated transfer).
3. Immediately post a `system_vote_count` unit for that subject while holding the large balance, forcing `countVotes()` to run and sum balances using their currently-inflated balance.
4. As soon as the count is finalized (`system_vars` updated, `storage.systemVars` mutated), move/spend the bytes away — the balance snapshot has already been consumed.

This is the exact "quick buy and sell" pattern from the report: since balances are read live at counting time rather than pinned to a fixed pre-announced snapshot block/height, and any address may pull the counting trigger opportunistically, an attacker never needs to be a long-term stakeholder or even hold funds for more than the time needed to get one unit accepted before spending them elsewhere.

### Impact Explanation
`op_list` directly determines the set of order providers (witnesses) that establish DAG stability and ordering for the entire network — capturing a majority of `op_list` seats via a momentary balance spike lets an attacker seat malicious/colluding witnesses, which can then be leveraged toward main-chain manipulation, stability disagreements between nodes, or degraded censorship resistance. Manipulating `threshold_size`, `base_tps_fee`, `tps_interval`, or `tps_fee_multiplier` can also distort network fee economics and TPS-fee enforcement network-wide. Because the outcome is written into `system_vars` and propagated via `system_vars_updated`/`system_var_vote` events that all nodes apply deterministically once the triggering unit is stable, this is a protocol-level (not merely economic) integrity issue reachable by an ordinary, unprivileged unit poster — satisfying "node disagreement on validity or stability" / systemic fund-relevant governance capture criteria.

### Likelihood Explanation
Exploitation requires only: (a) previously posting one cheap `system_vote` unit, (b) obtaining a large temporary balance for the span of a single unit's inclusion (achievable via flash-style same-block/near-block acquisition, exchange withdrawal, or coordination with a large holder), and (c) posting a `system_vote_count` unit (cost `SYSTEM_VOTE_COUNT_FEE` = 1e9 bytes, i.e. 1 GB fee) while that balance is held. No special privilege, hub/peer compromise, or node bug is needed — any wallet with enough temporary capital and access to compose messages can attempt this at any time counting is not already pending, making this a realistically reachable, if capital-intensive, attack, exactly mirroring the reported "quick buy/sell" analog.

### Recommendation
Use a fixed balance snapshot (e.g., balance as of the MCI at which the vote was cast, or the balance at first-vote timestamp already tracked in `system_votes.timestamp`) rather than the live/current balance evaluated at `countVotes()` time. Alternatively, require votes to "age" for a minimum holding period before being counted, and/or weight votes by balance held continuously since the vote timestamp using historical output data instead of `outputs`/`units` snapshotted at count time. This removes the incentive/ability to inflate voting weight only for the instant that `system_vote_count` executes.

### Proof of Concept
1. Address A posts a `system_vote` unit voting for candidate op-list `X` with a small balance (message validated per `validation.js:1844-1911`).
2. A acquires a large temporary balance (e.g., via a large incoming payment or swap) shortly before triggering the count.
3. While holding the large balance, A posts a `system_vote_count` unit for subject `op_list` (`validation.js:1913-1923`), which becomes stable and triggers `countVotes(conn, mci, 'op_list')`.
4. `countVotes()` reads A's balance live via the `bal_rows` query (`main_chain.js:1757-1773`), giving A's vote outsized weight in the `op_rows` aggregation (`main_chain.js:1850-1858`), potentially placing A's preferred candidates into the new `op_list`.
5. Once `system_vars` is updated and `storage.systemVars.op_list` set (`main_chain.js:1870`), A immediately spends/transfers the large balance elsewhere — the vote weight has already been "spent" and cannot be revised, yet A no longer holds any stake in the network.

async function countVotes(conn, mci, subject, is_emergency = 0, emergency_count_command_timestamp = 0) {
	console.log('countVotes', mci, subject, is_emergency, emergency_count_command_timestamp);
	if (is_emergency && subject !== "op_list")
		throw Error("emergency vote count supported for op_list only, got " + subject);
	const address_rows = await conn.query("SELECT DISTINCT address FROM system_votes WHERE subject=?", [subject]);
	let addresses = address_rows.map(r => r.address);
	const unstable_votes = (is_emergency && mci >= constants.pemCurvesFixMci) ? getUnstableVotes(emergency_count_command_timestamp) : null;
	if (unstable_votes) {
		for (let { author_addresses } of unstable_votes) {
			for (let address of author_addresses)
				addresses.push(address);
		}
		addresses = _.uniq(addresses);
	}
	const strAddresses = addresses.map(db.escape).join(', ');
	let balances = {};
	// Count all stable-good outputs that have no stable-good spender.
	// This correctly handles outputs whose only spending unit was propagated to final-bad
	// (leaving is_spent=1 in the DB while no good unit claims the output), which the
	// previous two-query approach (bal_rows + spent_rows) silently undercounted.
	const bal_rows = await conn.query(`
		SELECT outputs.address, SUM(outputs.amount) AS balance
		FROM outputs
		JOIN units ON outputs.unit = units.unit
		WHERE outputs.address IN(${strAddresses})
			AND outputs.asset IS NULL
			AND units.is_stable = 1 AND units.sequence = 'good'
			AND NOT EXISTS (
				SELECT 1 FROM inputs
				JOIN units AS su ON inputs.unit = su.unit
				WHERE inputs.src_unit = outputs.unit
					AND inputs.src_message_index = outputs.message_index
					AND inputs.src_output_index = outputs.output_index
					AND su.sequence = 'good'
					AND su.is_stable = 1
			)
		GROUP BY outputs.address`);
	console.log('bal rows', bal_rows)
	for (let { address, balance } of bal_rows) {
		balances[address] = balance;
	}
