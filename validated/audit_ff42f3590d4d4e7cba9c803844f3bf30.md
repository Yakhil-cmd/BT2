### Title
Cross-organization commit status forgery via webhook signature verification bound to an attacker-controlled, unscoped field - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
The `WebhooksController` selects which GitHub App/webhook secret to verify a webhook's HMAC signature against using an organization name taken directly from the untrusted JSON payload, not from any pre-registered repository/installation mapping. Several webhook handlers — most critically `StatusHandler` — then act on data (a bare commit `sha`) with **no organization or repository scoping at all**. This breaks the binding "organization that authenticated == repository/commit that is written": an attacker can get a forged webhook verified under one (weakly- or unconfigured) organization and have it mutate state belonging to an entirely different, victim organization's stack.

### Finding Description
`WebhooksController#verify_signature` picks the signing secret using a value pulled straight out of the unauthenticated request body: [1](#0-0) [2](#0-1) 

`repository_owner` is `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` — both fully attacker-controlled fields inside the raw POST body that the attacker crafted. `Shipit.github(organization: repository_owner)` resolves to whichever `GitHubApp` config matches that attacker-chosen name: [3](#0-2) 

Signature verification itself is a no-op whenever that organization's config has no `webhook_secret` set: [4](#0-3) 

`webhook_secret` is documented and shipped as **optional** and defaults to `nil` in the setup docs, templates, and example secrets files, so real-world multi-organization Shipit deployments commonly have at least one configured organization with signature verification effectively disabled: [5](#0-4) [6](#0-5) [7](#0-6) 

Once the (weak) signature check passes, `WebhooksController#create` dispatches to handlers purely by event type, with no re-validation that the "organization" used for signing matches the target of the mutation: [8](#0-7) 

Most handlers at least scope by `repository.full_name` via the base `Handler` class: [9](#0-8) 

But `StatusHandler`, which drives commit CI/deploy-check state, performs **no repository scoping whatsoever** — it matches by SHA across the entire application: [10](#0-9) 

So the equality that should hold — `organization authenticated by verify_signature == organization/repository owning the Commit being mutated` — does not hold anywhere in this path. Before the attack, a legitimate GitHub-originated webhook always has consistent `repository.owner.login`/`full_name`/commit ownership because GitHub itself builds the payload. After the attack, the attacker builds the entire payload themselves and can freely decouple the "signing organization" field from the "target commit" field, since `Commit.where(sha:)` has no organization filter at all.

### Impact Explanation
Commit statuses reported here feed the deploy/merge decision path (`Commit#create_status_from_github!`, used by blocking-status checks and the merge queue) [11](#0-10) . By forging a `status` webhook that is verified against an organization with no (or a leaked) `webhook_secret`, but whose `sha` matches a commit belonging to a victim organization's stack, an unprivileged attacker can inject a fabricated `success` status for a required/blocking CI context on a commit they do not control and that never actually passed the real CI defined for that repository/organization. This can make a malicious or unreviewed commit appear deployable/mergeable, leading to an unauthorized deploy or merge — squarely within the accepted impact category ("unauthorized deploy, rollback, or merge").

### Likelihood Explanation
This requires: (1) the target Shipit instance to be configured for multiple GitHub organizations (a documented, supported configuration), and (2) at least one configured organization to have no `webhook_secret` set — a state the project's own docs/templates present as the normal/default choice ("optional"). Given that combination, exploitation requires no credentials, no session, and no GitHub App installation access — only knowledge of a target commit's SHA, which is public information on GitHub. The `/webhooks` endpoint is unauthenticated by design (it must accept unauthenticated POSTs from GitHub), so the only real protection is the signature check that this bug bypasses for cross-organization targets.

### Recommendation
- Do not derive the verifying organization/secret from attacker-supplied payload fields. Instead, verify the signature against the secret registered for the specific repository/installation the payload claims to be from, and reject if any handler subsequently observes a different repository/organization than the one whose secret validated the signature.
- Require `webhook_secret` to be present for every configured organization (fail closed) rather than treating it as optional/no-op when absent.
- Scope `StatusHandler` (and any other handler that doesn't already) to the repository named in the payload, and cross-check that repository's owning organization against the organization whose secret validated the request signature, rejecting mismatches.

### Proof of Concept
1. Operator configures Shipit with two GitHub organizations per the documented multi-org format: `OrgA` (no `webhook_secret` set, as shown as an accepted default in `docs/setup.md`/example secrets) and `OrgB` (target/victim, has a `webhook_secret`).
2. Attacker sends `POST /webhooks` with header `X-Github-Event: status` and body:
   ```json
   {
     "sha": "<sha of a real, unmerged commit tracked by an OrgB stack>",
     "state": "success",
     "context": "required-ci",
     "repository": { "owner": { "login": "OrgA" } }
   }
   ```
   No valid `X-Hub-Signature` is required because `OrgA` has no `webhook_secret`, so `GitHubApp#verify_webhook_signature` returns `true` unconditionally (`app/controllers/shipit/webhooks_controller.rb` lines 24-30, `lib/shipit/github_app.rb` lines 76-83).
3. `StatusHandler#process` looks up `Commit.where(sha: params.sha)` with no organization/repository filter and creates a `success` status on the matching commit, which actually belongs to `OrgB`'s stack (`app/models/shipit/webhooks/handlers/status_handler.rb` lines 20-24).
4. The forged "success" status can satisfy blocking-status/merge-queue checks for `OrgB`'s commit, enabling an unauthorized merge/deploy of that commit.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
