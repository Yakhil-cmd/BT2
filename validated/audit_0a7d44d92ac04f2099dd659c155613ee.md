### Title
API token scoped to one stack can read CI status of any stack via `Api::CCMenuController` - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::StacksController` and other stack-scoped API endpoints resolve the target `Stack` through the current `ApiClient`'s scope (`stacks.from_param!`), which restricts a stack-bound `ApiClient` to only its own stack. `Shipit::Api::CCMenuController` overrides this lookup with an unscoped `Stack.from_param!(params[:stack_id])`, breaking the binding between "the stack a token authorizes" and "the stack it actually touches."

### Finding Description
`Shipit::Api::BaseController#stacks` enforces the scoping invariant for every stack-scoped endpoint: [1](#0-0) 

`current_api_client.stack_id?` is true whenever an `ApiClient` `belongs_to :stack` (i.e. it was created scoped to one particular stack, as `CCMenuUrlController` does): [2](#0-1) [3](#0-2) 

`Api::StacksController` (and the rest of the stack-scoped API controllers) correctly resolves the stack through this scoped relation: [4](#0-3) 

`Api::CCMenuController`, however, overrides `stack` to bypass the scope entirely and fetch by param directly from the global `Stack` table: [5](#0-4) 

The only check performed before `show` runs is `require_permission :read, :stack`, which merely asserts the token's `permissions` array includes `read:stack` — it never asserts that `params[:stack_id]` matches `current_api_client.stack_id`: [6](#0-5) [7](#0-6) 

The equality that should hold — `current_api_client.stack_id == stack.id` (or "unscoped" for `UnlimitedApiClient`/tokens without `stack_id`) — is broken specifically in this controller. Every `ApiClient` created for the CCMenu integration is intentionally scoped to a single stack with only `read:stack` permission, exactly the token shape this bug lets an attacker abuse against other stacks: [8](#0-7) 

`authenticate_api_client` in this controller also accepts the token from a URL query parameter (as designed, for CI tooling), meaning the token is routinely present in logs/history and is the credential most likely to leak or be reused across stacks: [9](#0-8) 

### Impact Explanation
An attacker holding a valid `read:stack`-only `ApiClient` token issued for stack A (e.g. captured from a CCMenu URL, which is designed to be embedded in CI dashboards/build tools and is not treated as a highly sensitive secret) can supply any other `stack_id` in the request path and read that stack's CI/deploy status (latest deploy id, running status, `lastBuildStatus`, `lastBuildLabel`, etc.) even though the token was never authorized for that stack. This is an unauthorized read of stack state across a trust boundary that the token system is explicitly designed to enforce (compare with `Api::StacksController#stack`, which correctly scopes). This matches the High-impact category: "unauthenticated read of stack state."

### Likelihood Explanation
Likelihood is high for any deployment with more than one stack and CCMenu integration enabled: the CCMenu token is handed out liberally (auto-created per user/stack, embedded in URLs used by third-party CI tools), and exploitation requires nothing more than substituting the `stack_id` path segment in an otherwise valid, unprivileged CCMenu request — no elevated credentials, session, or write access are required beyond the single scoped read-only token the feature normally issues.

### Recommendation
Change `Api::CCMenuController#stack` to reuse the scoped `stacks` lookup from `BaseController` (i.e. `stacks.from_param!(params[:stack_id])`) instead of the unscoped `Stack.from_param!(params[:stack_id])`, so a stack-bound `ApiClient` cannot resolve to any stack other than the one it was issued for.

### Proof of Concept
1. Visit `GET /merge_status` (or any stack page) as an authenticated user for stack A, triggering `CCMenuUrlController#fetch`, which creates/fetches a `read:stack`-scoped `ApiClient` bound to stack A and returns a CCMenu URL containing `token=<A's token>`. [10](#0-9) 
2. Take that token and issue `GET /api/stacks/<owner>/<other-repo>/<other-env>/ccmenu?token=<A's token>` for an unrelated stack B.
3. `CCMenuController#authenticate_api_client` authenticates the token successfully (it is a valid `ApiClient` row), `require_permission :read, :stack` passes because the token has `read:stack` in its `permissions`, and `stack` resolves stack B via the unscoped `Stack.from_param!`, returning stack B's CI status/deploy info to the holder of stack A's token. [11](#0-10)
