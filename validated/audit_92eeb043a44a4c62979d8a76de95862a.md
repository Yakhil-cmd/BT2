### Title
Webhook signature verification keyed on `repository.owner.login` while event handlers act on `repository.full_name` - allows forged status/push events on unrelated stacks - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App / `webhook_secret` used to validate an incoming webhook based on `repository.owner.login` (or `organization.login`) extracted from the JSON body, but the event handlers that actually act on the payload (`Shipit::Webhooks::Handlers::Handler#repository_name`, used by `PushHandler`, `StatusHandler`, etc.) resolve the target `Repository`/`Stack` from the unrelated `repository.full_name` field of the very same payload. Because these two fields are never checked against each other, and because `GitHubApp#verify_webhook_signature` unconditionally returns `true` when no `webhook_secret` is configured for the organization resolved by `repository_owner`, an attacker can pick any Shipit-configured organization that has no `webhook_secret` set, put that organization's name in `repository.owner.login`, and put an arbitrary *other*, secret-protected organization/repo's `full_name` in `repository.full_name`. The signature check passes trivially (no secret configured) while the handler operates on the victim repository chosen via `full_name`.

### Finding Description
- Signature verification path: `verify_signature` computes `repository_owner = params.dig('repository','owner','login') || params.dig('organization','login')` and fetches `Shipit.github(organization: repository_owner)`, then calls `verify_webhook_signature`. [1](#0-0) [2](#0-1) 
- `GitHubApp#verify_webhook_signature` short-circuits to `true` whenever the resolved organization has no `webhook_secret` configured, without inspecting the signature header at all: `return true unless webhook_secret`. [3](#0-2) 
- `webhook_secret` is documented as optional and multiple GitHub Apps/organizations can be configured simultaneously, each with its own (possibly blank) secret. [4](#0-3) 
- After verification, `create` dispatches the raw, unvalidated JSON payload to all registered handlers for the event: `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`. [5](#0-4) 
- Handlers resolve the *target* repository/stack from a completely different field, `repository.full_name`, via `Handler#repository_name` / `#stacks`, with no cross-check against `repository_owner` used earlier for signature selection. [6](#0-5) 
- `PushHandler#process` uses `stacks` (derived from `full_name`) to trigger `stack.sync_github(expected_head_sha: ...)`, and `StatusHandler#process` uses the (globally scoped) `sha` to create a GitHub-originated commit status via `commit.create_status_from_github!(params)`. [7](#0-6) [8](#0-7) 

Binding broken (as equality): the organization whose credential (`webhook_secret`) authenticated the request must equal the organization/repository that the handler subsequently writes state for. Here: `repository_owner (used to select webhook_secret)` ≠ `repository.full_name (used to select the Repository/Stack that is mutated)`. Before the attacker's request, both fields agree in genuine GitHub-originated traffic. After a forged POST, `repository_owner` can be set to any org with an unset `webhook_secret` while `repository.full_name` names a victim org/repo Shipit already tracks, breaking the equality and letting the request bypass authentication for the org it actually mutates.

### Impact Explanation
`StatusHandler` writes commit statuses that other parts of Shipit rely on to gate deploys (`ci.require` in `shipit.yml` checks required commit statuses recorded via this exact webhook flow). By forging `status` events for a victim repository under cover of an unrelated, secret-less organization, an unprivileged network attacker can inject fabricated "success" statuses on arbitrary commit SHAs it knows (SHAs are public on GitHub), potentially satisfying CI gating logic in the deploy pipeline without any actual GitHub credential, `ApiClient` token, or GitHub App access — directly touching the "unauthorized deploy" impact tier. It can additionally trigger `PushHandler`-driven `GithubSyncJob` syncs on arbitrary stacks. The severity depends on how strongly the specific deployment relies on webhook-derived statuses versus live GitHub API checks, which could not be fully confirmed from the excluded `Status`/`CommitChecks` gating internals in this pass.

### Likelihood Explanation
Requires only: (1) the target Shipit instance to have at least one configured GitHub organization/App with `webhook_secret` left blank (explicitly documented as "optional"), and (2) the attacker knowing that org's name and a victim repository's `full_name`/commit SHA that Shipit tracks — both obtainable without any privileged access. No session, `ApiClient` token, or GitHub App key is needed, matching the required unprivileged threat model.

### Recommendation
In `WebhooksController#verify_signature`, always require the same repository/organization identity that handlers will act upon, and refuse to skip signature verification just because a config entry lacks a secret unless that specific `repository.full_name`'s owner matches the intentionally-permissive organization. At minimum, cross-validate that `repository.owner.login` (or `organization.login`) equals the owner segment of `repository.full_name` before dispatching to handlers, and treat a missing `webhook_secret` as "reject" rather than "always verified" for any organization that has stacks with a configured secret elsewhere.

### Proof of Concept
1. Configure Shipit with two GitHub organizations in `secrets.yml`: `orgA` (no `webhook_secret`) and `orgB` (has `webhook_secret` and a stack tracking `orgB/victim-repo`).
2. POST to `/webhooks` with header `X-Github-Event: status` and body:
```json
{
  "repository": { "owner": { "login": "orgA" }, "full_name": "orgB/victim-repo" },
  "sha": "<known-victim-commit-sha>",
  "state": "success",
  "context": "ci/required-check"
}
```
No valid `X-Hub-Signature` is required because `Shipit.github(organization: "orgA")` has no `webhook_secret`, so `verify_webhook_signature` returns `true` unconditionally. [3](#0-2) 
3. `StatusHandler` processes the payload using `sha`/`state`/`context` (unrelated to `orgA`) and creates/updates a `Status` on the commit belonging to `orgB/victim-repo`. [8](#0-7)

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
