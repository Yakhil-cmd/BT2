### Title
AA storage-size accounting can go negative and permanently crash the node instead of bouncing the trigger - ([File: aa_composer.js])

### Summary
The Flatcoin bug is a class of "tracked accounting total diverges from real balance and is asymmetrically clamped at zero, then a strict invariant check reverts on every future operation, bricking the protocol." The closest reachable analog in `ocore--023` is the AA storage-size bookkeeping in `aa_composer.js`, where a tracked value (`storage_size`, persisted in `aa_addresses`) is updated by a delta computed from per-trigger state-variable diffs, and a negative outcome causes a hard `throw Error` (process crash) instead of a graceful bounce, unlike every other AA failure path.

### Finding Description
`updateStorageSize()` computes `delta_storage_size` from the state-var changes recorded during trigger evaluation and adds it to the AA's persisted `storage_size`: [1](#0-0) 

Note the asymmetry with every other failure condition in `handleTrigger`: almost all invalid states (insufficient balance, oversize fee, missing bounce fee, etc.) are handled by calling `bounce(error)`, which safely reverts state/balances and, if possible, sends a bounce response — this is the AA-analog of a graceful revert. But when `new_storage_size < 0`, the code does not bounce; it throws a hard JS `Error`:
```
if (new_storage_size < 0)
    throw Error("storage size would become negative: " + new_storage_size);
```
This is architecturally different from the `bounce()`-based error handling used elsewhere in `handleTrigger` (e.g. `bounce("not enough balance in base")` in `sendDummyUnit`, or `bounce('received bytes are not enough to cover bounce fees')`), and different from a `cb(error)` return that is convertible into a bounce, as is done for the sibling check on the very next line (byte balance below storage size): [2](#0-1) 

Because `storage_size` is a running total tracked separately from the ever-changing/append-only underlying key-value store, and `delta_storage_size` is computed only from *this trigger's* recorded diffs (`state.original_old_value` vs new value), any state where the computed delta undercounts a removed/shrunk value relative to the actually recorded `storage_size` baseline — or where multiple concurrent/secondary triggers to the same AA interleave their deltas incorrectly — can drive `new_storage_size` below zero. The system already anticipates that `storage_size` bookkeeping can silently diverge from the real key-value store contents: there is a dedicated periodic consistency check, `checkStorageSizes()`, which recomputes the real KV size and throws if it disagrees with the DB-tracked `storage_size`: [3](#0-2) 

This mirrors exactly the structural weakness in the Flatcoin bug: (1) a shadow/tracked total (`storageSize`/`stableCollateralTotal`) that can legitimately diverge from ground truth under adversarial or edge-case sequences, and (2) a strict invariant enforcement path that does not degrade gracefully (revert-only in Flatcoin, hard-crash-only here) once the divergence occurs, instead of bouncing/rejecting only the offending trigger.

### Impact Explanation
Where Flatcoin's bug reverts every subsequent user call to the vault (bricking withdrawals for all users), the ocore analog is worse in one respect and different in another: a `throw Error` inside `handleTrigger`'s trigger-processing pipeline is not a normal validation failure that gets contained to a single bounce — it propagates as an unhandled exception in the unit-processing/writer code path. If this is reachable from an unprivileged AA (any AA author can define arbitrarily complex state-var read/write patterns via oscript, and any user can send a trigger to it), a state that drives `new_storage_size` negative would crash node processing of that unit for every node validating/executing the DAG, i.e., a network-wide denial-of-service / consensus-halting condition for that branch of the DAG — the ocore equivalent of "the protocol becomes bricked" for the affected AA and potentially for units depending on it.

### Likelihood Explanation
This requires an accounting corner case in delta computation (e.g., a value shrinking/being deleted whose recorded `original_old_value` doesn't match the true previously-stored value, or concurrent primary/secondary trigger deltas being combined incorrectly on the same address in the same or interleaved responses) similar in spirit to the Flatcoin scenario requiring an extreme price move. It is a specific-state/edge-case bug, not trivially triggerable by a single simple state-var write, and I could not fully trace every code path that populates `state.original_old_value` and `storage_size` under `bSecondary`/multi-response scenarios within the available context. This uncertainty is analogous to the disputed likelihood in the original report (downgraded from High to Medium by the judges because it required extensive specific conditions).

### Recommendation
Convert the `new_storage_size < 0` condition from a hard `throw Error` into a normal bounce/rejection path (`return cb("storage size would become negative")`), consistent with the neighboring check on `byte_balance < new_storage_size`, so that only the offending trigger is bounced instead of crashing node processing. Additionally, reconcile `storage_size` against the authoritative KV-store contents (as `checkStorageSizes()` already verifies asynchronously) synchronously/defensively at the point of use, so a divergence cannot manifest as an unrecoverable crash in the trigger-execution hot path.

### Proof of Concept
Not independently reproduced — I did not have access to construct/execute an actual malicious oscript AA definition and trigger sequence in this environment. Based on code inspection, the theoretical trigger sequence is:
1. Deploy an AA that writes and later deletes/shrinks large state-var values across multiple triggers (potentially split between a primary and secondary/dependent trigger), such that `state.original_old_value` tracked in this invocation doesn't match the true prior on-disk size (e.g., due to a prior invocation whose `storage_size` write raced with or was fixed up incorrectly, or due to `base_aa` redirection paths that reset/duplicate tracking, seen at [4](#0-3) ).
2. Send a trigger causing `delta_storage_size` to be computed larger in magnitude (more negative) than the true remaining `storage_size`.
3. `updateStorageSize()` computes `new_storage_size < 0` and the node throws instead of bouncing, at [5](#0-4) .

I was unable to confirm within the available index whether an unprivileged path can actually cause `delta_storage_size` to be miscomputed in this way (this would need deeper tracing of `original_old_value` assignment across `bSecondary`/base_aa/parameterized-AA flows). If more certainty is needed, a Devin session with full file access should trace `state.original_old_value` initialization and all `storage_size`-affecting code paths, including base_aa parameterized redirection and secondary-trigger interleaving, to construct a concrete reproduction.

function checkStorageSizes() {
	mutex.lockOrSkip(['checkStorageSizes'], function (unlock) {
		db.takeConnectionFromPool(function (conn) { // block conection for the entire duration of the check
			var options = {};
			options.gte = "st\n";
			options.lte = "st\n\uFFFF";

			var assocSizes = {};
			var handleData = function (data) {
				var address = data.key.substr(3, 32);
				var var_name = data.key.substr(36);
				if (!assocSizes[address])
					assocSizes[address] = 0;
				assocSizes[address] += var_name.length + data.value.length - 2; // -2 for type and \n
			}
			var stream = kvstore.createReadStream(options);
			stream.on('data', handleData)
				.on('end', function () {
					conn.query("SELECT address, storage_size FROM aa_addresses", function (rows) {
						rows.forEach(function (row) {
							if (!assocSizes[row.address])
								assocSizes[row.address] = 0;
							if (row.storage_size !== assocSizes[row.address])
								throw Error("storage size mismatch on " + row.address + ": db=" + row.storage_size + ", kv=" + assocSizes[row.address]);
						});
						conn.release();
						unlock();
					});
				})
