### Title
Missing zero-address check in stake/vote `Authorize` instruction handlers can permanently freeze stake/vote accounts - ([File: programs/vote/src/vote_state/mod.rs])

### Summary
Both the stake program's `Authorize`/`AuthorizeChecked` instruction path and the vote program's `authorize()` handler set a new staker/withdrawer or voter/withdrawer pubkey supplied directly from instruction data, with no validation that the new authority is non-default (i.e., not `Pubkey::default()`/all-zero). This mirrors the reported Governable.sol `transferGovernor()` bug class: an authority-transfer function that accepts and stores an unchecked new-authority value, which — once set to a value nobody controls — permanently locks out all `onlyGovernor`-equivalent (here, `onlyAuthorized`) actions.

### Finding Description
In the vote program, `authorize()` unconditionally calls `vote_state.set_authorized_withdrawer(*authorized)` for `VoteAuthorize::Withdrawer`, and `vote_state.set_new_authorized_voter(authorized, ...)` for `VoteAuthorize::Voter`, using the `authorized` pubkey taken straight from the instruction data with no zero/default-address validation. [1](#0-0) 

The stake program's client-side/CLI authorize path likewise forwards `new_authority_pubkey` straight into `stake_instruction::authorize`/`authorize_checked` without any zero-address filtering (the on-chain handler updates `Authorized.staker`/`Authorized.withdrawer` the same way). [2](#0-1) 

The only validation performed is `check_current_authority`/`verify_authorized_signer` against the *current* authority (proving the caller has signing rights), and `check_unique_pubkeys` to prevent setting the same value — there is no check rejecting `Pubkey::default()` or another unspendable/unrecoverable address as the *new* authority. [3](#0-2) [4](#0-3) 

### Impact Explanation
If the current stake/vote authority (staker, withdrawer, or vote authority) is set to `Pubkey::default()` (or any address whose private key is unrecoverable), all future `authorize`, `withdraw`, `delegate`, or `deactivate` calls that require a signature from that authority become permanently impossible to satisfy, since no one holds the corresponding private key. This produces a permanently frozen stake or vote account, exactly matching the "permanently frozen accounts" impact class.

### Likelihood Explanation
Likelihood is low-to-moderate: triggering this requires the account's own current authority (staker/withdrawer/voter authority) to submit an `Authorize` transaction naming an invalid/default pubkey, either due to a client-side bug (e.g. malformed CLI/SDK input defaulting to `Pubkey::default()`), a misconfigured automation script, or user error — analogous to the original report's scenario where the governor itself calls `transferGovernor(address(0))`. No separate on-chain sanity check exists to catch this class of mistake before it becomes irreversible.

### Recommendation
Add an explicit check rejecting `Pubkey::default()` (and any other well-known unspendable sentinel value) as the `new_authority`/`authorized` pubkey in:
- the vote program's `authorize()` function in `programs/vote/src/vote_state/mod.rs` for both `VoteAuthorize::Voter` and `VoteAuthorize::Withdrawer` branches, and
- the stake program's `Authorize`/`AuthorizeChecked` instruction processing path (mirroring the CLI-side authorize construction in `cli/src/stake.rs`).

Return `InstructionError::InvalidInstructionData` (or equivalent) if the new authority equals the default pubkey.

### Proof of Concept
1. Create/own a stake or vote account with authority `A`.
2. As authority `A`, submit `Authorize`/`AuthorizeChecked` (stake) or `VoteInstruction::Authorize` (vote) naming `new_authorized = Pubkey::default()`.
3. The instruction succeeds because no zero-address check exists in `authorize()` (`programs/vote/src/vote_state/mod.rs:686-731`) or in the corresponding stake authorize path.
4. All subsequent instructions requiring a signature from that authority (withdraw, delegate, deactivate, re-authorize) now fail permanently, since no private key exists for `Pubkey::default()` — the account's staker/withdrawer/voter control is permanently frozen. [1](#0-0) [5](#0-4)

pub fn authorize<S: std::hash::BuildHasher, F>(
    vote_account: &mut BorrowedInstructionAccount,
    target_version: VoteStateTargetVersion,
    authorized: &Pubkey,
    vote_authorize: VoteAuthorize,
    signers: &HashSet<Pubkey, S>,
    clock: &Clock,
    is_vote_authorize_with_bls_enabled: bool,
    consume_pop_compute_units: F,
) -> Result<(), InstructionError>
where
    F: FnOnce() -> Result<(), InstructionError>,
{
    let mut vote_state = get_vote_state_handler_checked(vote_account, target_version)?;

    match vote_authorize {
        VoteAuthorize::Voter => {
            if is_vote_authorize_with_bls_enabled && vote_state.has_bls_pubkey() {
                return Err(InstructionError::InvalidInstructionData);
            }
            let authorized_withdrawer_signer =
                verify_authorized_signer(vote_state.authorized_withdrawer(), signers).is_ok();

            vote_state.set_new_authorized_voter(
                authorized,
                clock.epoch,
                clock
                    .leader_schedule_epoch
                    .checked_add(1)
                    .ok_or(InstructionError::InvalidAccountData)?,
                None,
                |epoch_authorized_voter| {
                    // current authorized withdrawer or authorized voter must say "yay"
                    if authorized_withdrawer_signer {
                        Ok(())
                    } else {
                        verify_authorized_signer(&epoch_authorized_voter, signers)
                    }
                },
            )?;
        }
        VoteAuthorize::Withdrawer => {
            // current authorized withdrawer must say "yay"
            verify_authorized_signer(vote_state.authorized_withdrawer(), signers)?;
            vote_state.set_authorized_withdrawer(*authorized);
        }
