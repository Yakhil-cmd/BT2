[1](#0-0) ### Title
Malicious route venue steals unrelated wallet tokens through the caller's authorization tree - (File: contracts/controller/src/strategies/swap.rs)

### Summary
High. A malicious swap route can place attacker-controlled contract code below a victim-authorized `swap_collateral` call, add an unrelated `token.transfer(victim, attacker, amount)` as a signed authorization child, and steal arbitrary wallet tokens while still delivering a valid swap output. [2](#0-1) [3](#0-2) 

### Finding Description
`swap_collateral` authenticates `caller`, confirms that the caller owns or manages the account, and then forwards the caller-supplied opaque `swap` bytes into the router strategy. [1](#0-0) [4](#0-3) 

The controller separately authorizes only the exact controller-to-router input-token transfer. [5](#0-4) [6](#0-5)  That narrowly scoped controller authorization does not prevent route-selected downstream code from requesting the original caller's authority as another child invocation. [7](#0-6) 

After router execution, the controller checks that the router did not overspend the input and that it produced a positive output balance, but these checks observe only the controller's token balances. [8](#0-7) [9](#0-8)  Consequently, an unrelated debit from the caller's wallet does not affect the strategy's settlement or final account-risk checks. [10](#0-9) 

### Impact Explanation
An attacker can steal arbitrary unrelated tokens held by the account owner or delegate, not merely the collateral amount routed through the strategy. [11](#0-10) [12](#0-11)  The lending position can still receive a fair-looking output and remain solvent, so the strategy itself does not expose the theft as an economic failure. [13](#0-12) 

### Likelihood Explanation
The attack requires the victim to submit a malicious route and sign the resulting authorization tree containing the extra token transfer; an honest tree without that child is rejected by host authorization. [14](#0-13) [15](#0-14)  This is analogous to accepting a certificate exception that is silently broader than intended: the victim authorizes a swap, while the signed tree also grants authority for an unrelated transfer. [7](#0-6) 

Because `swap` is an opaque byte argument chosen by the caller and is not decoded or venue-bound by the controller, a malicious quote or route construction path can induce the additional child invocation while preserving a positive measured output. [16](#0-15) [4](#0-3) 

### Recommendation
Do not let route payloads select arbitrary venue/pool contracts during an account-authorized operation. Resolve venue contracts from a governance-approved registry or otherwise bind each opcode to known audited contract identities before invoking it. [2](#0-1) 

Clients and wallets should additionally reject authorization trees containing any child invocation outside the exact expected strategy authorization, but this should remain defense-in-depth rather than the sole control. [3](#0-2) 

### Proof of Concept
1. A victim holds an unrelated `WALLET_TOKEN` balance and owns a funded lending account. [17](#0-16) 
2. The attacker provides a `swap_collateral(victim, account_id, current, amount, new, swap)` transaction whose route invokes a pool contract controlled by the attacker. [2](#0-1) [18](#0-17) 
3. During its route callback, the pool transfers enough `new` tokens back to make the measured swap output positive and also calls `WALLET_TOKEN.transfer(victim, attacker, amount)`. [19](#0-18) 
4. Simulation records the wallet transfer as an additional child beneath the victim's `swap_collateral` authorization. [20](#0-19) 
5. If the victim signs that tree, the wallet token moves to the attacker while the lending account still receives the expected collateral output. [3](#0-2)
