### Title
Unhandled/mismatched pox-5 instruction names in `handle_contract_call` silently skip lock application and post-condition gating - (File: pox-locking/src/pox_5.rs)

### Summary
`handle_contract_call` (the pox-5 analog of `BasePongHandler`) hard-codes a fixed match on `function_name` for both (a) which pox-5 entry points get a lock/rollover/unstake VM-side effect applied, and (b) which entry points get gated via `log_pox_action` for `Pox` post-conditions. Any pox-5 contract function whose name does not appear verbatim in these two match arms is silently treated as a no-op by this trust boundary — exactly the "silent failure due to unhandled instruction" bug class from the report.

### Finding Description
Locking/unlocking of STX for pox-5 is not performed by the Clarity contract itself; the contract computes and returns a result tuple, and the actual balance mutation happens only in this Rust handler via `pox_lock_v5`, `pox_rollover_v5`, `pox_lock_update_v5`, and `pox_unstake_v5` [3](#0-2) [4](#0-3) [5](#0-4) . The dispatcher that decides whether to call any of these is a literal string match:

```
"stake" | "register-for-bond" => handle_lockup_pox_v5(...),
"stake-update" => handle_stake_lockup_update_pox_v5(...),
"unstake" => handle_unstake_pox_v5(...),
_ => None,
``` [1](#0-0) 

Separately, `log_pox_action` — which records that a position-altering PoX action occurred so that `Pox` post-conditions / `with-pox` allowances can constrain the tx-sender — is gated on a *different* literal list: `"unstake" | "unstake-sbtc" | "update-bond-registration" | "announce-l1-early-exit"` [2](#0-1) . This list omits `"stake"`, `"register-for-bond"`, and `"stake-update"` — i.e., every function that actually locks/rolls-over/increases a lock is not recorded as a "PoX action" for post-condition purposes, while `"unstake-sbtc"`, `"update-bond-registration"`, and `"announce-l1-early-exit"` are gated even though `handle_contract_call` never applies any balance effect for them (they fall to `_ => None` in the first match, so no lock/unlock actually happens for them at the VM level despite being treated as "position altering").

This mirrors the reported bug class precisely: the handler enumerates only a subset of the instruction/function set it must support, silently no-ops on anything else, and there's no fallback "not implemented, revert" branch (`_ => None` swallows unknown calls rather than asserting they are unexpected).

### Impact Explanation
If the pox-5 Clarity contract (not in the excluded/superseded-only scope; pox-5.clar is explicitly in-scope) is later extended, or is currently reachable, with any staking/bonding entry point whose function name isn't exactly one of the four handled strings, that call can return a well-formed `(ok {staker, amount-ustx, unlock-burn-height, ...})` tuple from the contract's own bookkeeping (e.g. contract-side maps say STX is locked/committed to a reward cycle) while the VM-level account lock is never applied via `pox_lock_v5`/`pox_rollover_v5` — breaking the equality between "amount the contract believes is committed/stacked" and "amount actually locked on the account." This can allow STX that the contract accounted as locked (and thus eligible for reward-cycle inclusion) to remain fully spendable/unlocked at the account level — i.e., double-counted commitment (contract-side stacked total vs. real balance-lock) without giving up spendability, which is a form of the "double-counting a commitment" and "reward slots/signing weight exceeding locked value" impact class.

### Likelihood Explanation
Likelihood depends on whether pox-5.clar (in scope) actually exposes additional staking-affecting public functions beyond `stake`, `register-for-bond`, `stake-update`, and `unstake` that are meant to route through this locking side effect. I was not able to fully enumerate pox-5.clar's public function surface within the available tool budget, so I cannot definitively confirm a currently-reachable contract function whose name falls outside the four handled strings while still requiring a lock mutation. This is a structural/maintenance-hazard finding (same class as the reported issue) rather than a confirmed exploit against a specific additional public function I verified end-to-end in pox-5.clar.

### Recommendation
1. Make the `_ => None` arm in `handle_contract_call` explicit about which functions are intentionally side-effect-free, and revert/panic (or at least a loud `debug_assert`/invariant log) for any *staking-affecting* pox-5 function name it doesn't recognize, rather than silently treating it as a no-op.
2. Reconcile the `log_pox_action` gating list with the actual set of functions that mutate locks — `stake`, `register-for-bond`, and `stake-update` should be included if a post-condition/allowance system is meant to constrain them, and `unstake-sbtc`/`update-bond-registration`/`announce-l1-early-exit` should be verified against whether they have a real VM-level lock effect at all.
3. Add an exhaustive test (or a compile-time check against the contract's public function list) asserting every pox-5 public function that can alter a stacker's lock is present in the `handle_contract_call` match.

### Proof of Concept
Not independently reproducible from the indexed code alone: doing so requires confirming pox-5.clar exposes a public function (beyond the four handled) that Legitimately returns the same `(ok {staker, amount-ustx, unlock-burn-height})` shape while mutating contract-side stacked-amount/reward-cycle-commitment state — which I could not fully verify within the tool budget. The structural gap itself (mismatched, non-exhaustive string match with a silent `_ => None`, and the `log_pox_action` list disagreeing with the lock-effect list) is directly confirmed at [6](#0-5) .

/// Handle responses from pox-5 entry points that lock STX for a staker:
/// `stake` (STX-only) and `register-for-bond` (protocol bond). A first-time
/// call (no existing pox-5 lock) acquires a fresh lock via
/// [`pox_lock_v5`]; a roll-over (the account is already locked from an
/// ending bond or stake) carries the lock forward via
/// [`pox_rollover_v5`] -- the amount may go up or down and the
/// unlock height is rescheduled, so the lock never releases. The contract
/// is responsible for gating the roll-over (non-overlap + L1 unlock window
/// for bond sources); if the contract returns ok, this handler trusts the
/// call is legitimate.
fn handle_lockup_pox_v5(
    global_context: &mut GlobalContext,
    function_name: &str,
    value: &Value,
) -> Result<Option<StacksTransactionEvent>, VmExecutionError> {
    debug!(
        "Handle special-case contract-call to {:?} {function_name} (which returned {value:?})",
        boot_code_id(POX_5_NAME, global_context.mainnet)
    );
    runtime_cost(
        ClarityCostFunction::StxTransfer,
        &mut global_context.cost_track,
        1,
    )?;

    let parsed = parse_pox_stake_result(value).map_err(|e| {
        locking_error_to_vm_error(e, &format!("pox-5 {function_name}: bad response"))
    })?;
    let (staker, locked_amount, unlock_height) = match parsed {
        ParsedStakeResult::Ok {
            staker,
            amount_ustx,
            unlock_burn_height,
        } => (staker, amount_ustx, unlock_burn_height),
        ParsedStakeResult::ContractErr => return Ok(None),
    };

    // A staker rolling from one bond/stake position into another is already
    // locked; carry the lock forward instead of acquiring a fresh one (which
    // would fail with `PoxAlreadyLocked`). A first-time call locks fresh.
    let already_locked = {
        let mut snapshot = global_context.database.get_stx_balance_snapshot(&staker)?;
        snapshot.has_locked_tokens()?
    };

    let lock_result = if already_locked {
        pox_rollover_v5(
            &mut global_context.database,
            &staker,
            unlock_height,
            locked_amount,
        )
        .map(|_| ())
    } else {
        pox_lock_v5(
            &mut global_context.database,
            &staker,
            locked_amount,
            unlock_height,
        )
    };

    match lock_result {
        Ok(()) => {
            // Log the staking in the asset map
            global_context.log_stacking(&staker, locked_amount)?;

            let event =
                StacksTransactionEvent::STXEvent(STXEventType::STXLockEvent(STXLockEventData {
                    locked_amount,
                    unlock_height,
                    locked_address: staker,
                    contract_identifier: boot_code_id(POX_5_NAME, global_context.mainnet),
                }));
            Ok(Some(event))
        }
        Err(e) => Err(locking_error_to_vm_error(
            e,
            &format!("pox-5 {function_name}: failed to lock {locked_amount} from {staker} until {unlock_height}"),
        )),
    }
}
