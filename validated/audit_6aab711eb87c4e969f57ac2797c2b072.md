### Title
Flash-loan-funded reserve donation inflates Aquarius LP collateral price, enabling over-borrowing and bad debt - (File: contracts/price-aggregator/src/providers/aquarius.rs)

### Summary
The same class as Elephant Money — an attacker moves a price the protocol reads during a collateral valuation — maps onto XOXNO Lending's `AquariusLp` / `AquariusStableLp` oracle source. The price of an LP share is derived as `2 * sqrt(value_a * value_b) / total_shares` from **live pool reserves** read via `get_reserves`, while the leg prices come from external feeds. Reserve donation is not symmetric: `fair_lp_price_wad` uses `sqrt(reserve_a * reserve_b)`, so a direct token transfer into the Aquarius pool (a donation that mints no shares) raises the computed fair value for **all** shares while the donor retains a pro-rata claim on the donated reserve. An attacker who holds the dominant share of a listed LP pool can flash-loan one leg asset, donate it to the pool, borrow against the inflated LP collateral valuation, and walk away — leaving suppliers with bad debt. Deployed LP sanity bands are up to ~10x wide (e.g. XLMAQUA_LP `5.35e15`–`5.36e16` WAD), so large inflations stay inside the band.

### Finding Description
- `providers/aquarius.rs:90-114` reads live `reserve_a`, `reserve_b`, and `total_shares` from the pool contract in the same ledger transaction that values the collateral, then calls `fair_lp_price_wad`.
- `common/src/oracle/lp.rs:57-87` computes `2 * sqrt(value_a * value_b) / share_supply_wad`. Donating `D` of leg A inflates the price by `sqrt(1 + D·p_a/value_a)`; a swap cannot do this (product is invariant), but a plain `token::transfer` to the pool raises `reserve_a` with no share issuance.
- The donation is recoverable pro-rata by the donor's own LP shares (which remain in the pool backing them), so when the attacker owns most of the pool supply the net cost of manipulation is only the fraction of the donation attributable to other LPs.
- The only backstops are `min_pool_value_wad` (`aquarius.rs:118-122`, which a donation *increases*) and the sanity band. `validate_lp_sanity_band` (`common/src/validation.rs:201-208`) permits bands far wider than a manipulation margin — the regression test at `common/tests/validation.rs:549-575` lists deployed bands spanning up to 10x (XLMAQUA_LP, AQUAUSDC_LP, XLMSolvBTC_LP).
- There is no dual-source tolerance check for LP oracles — `validate_asset_oracle` waives smoothing and tolerance for Aquarius LP sources (`admin.rs:157-163`, `191-197`) and rejects any second source (`admin.rs:181-184`), so the manipulated read is the sole input to `Context`-cached strict prices driving LTV/health-factor in the controller.
- Funding is reachable by an unprivileged address: `pool` `flash_loan` (fee ~9 bps, `is_flashloanable: true` on deployed markets) or `flash_position` debt minted before the callback provides the leg tokens; the donation, supply of LP collateral, and `borrow` all settle in one transaction.

### Impact Explanation
Theft of supplier funds / protocol insolvency. The attacker borrows up to LTV against an LP valuation inflated by up to `sqrt(band_headroom)` (e.g. ~3x on a 10x band), repays the flash loan from borrowed proceeds, and defaults. Liquidation seizes LP collateral whose true value is below the debt, creating bad debt that the pool's `clean_bad_debt`/index write-down socializes onto suppliers. Scale is bounded by the listed LP market's supply cap and the borrowable market's liquidity — the same "critical loss vs. protocol size" shape as the reference incident.

### Likelihood Explanation
Requires a listed `AquariusLp` collateral market whose underlying pool is thin enough for one actor to dominate share supply and whose sanity band admits useful inflation — conditions the wide deployed bands (10x) accommodate. All steps use public entrypoints: `flash_loan`/`flash_position`, direct `token::transfer` to the Aquarius pool, `supply`, `borrow`. No privileged access, oracle dishonesty, or off-chain component is needed.

### Recommendation
Use manipulation-resistant reserve accounting for the constant-product leg: derive each leg's contribution from the *smaller* side normalized by oracle price (i.e. `2 * min(value_a, value_b) / total_shares`, or the Alpha-style `sqrt(k)-priced-at-oracle` formulation using `k = reserve_a * reserve_b` with oracle-implied balanced values rather than raw reserves), so a one-sided donation cannot raise the computed value. Alternatively/additionally: read reserves via a donation-resistant interface (pool-tracked balances rather than token balances), and tighten `MAX_LP_SANITY_BAND_BPS` / deployed LP bands toward the feed-implied fair value so that donation-driven inflation exits the band and fails closed.

### Proof of Concept
1. Over time (or in the same tx via Aquarius `deposit`), acquire ≥ ~90% of the shares of the Aquarius pool backing a listed `XLMUSDC_LP`-style collateral market; supply the shares via controller `supply` on an account.
2. Call pool `flash_loan` for `D` units of leg token A (a flashloanable market), or use `flash_position` minted debt.
3. In the receiver callback, `token::transfer` `D` of token A directly to the Aquarius pool contract. `get_reserves` now returns `reserve_a + D`; `fair_lp_price_wad` rises by `sqrt(1 + D·p_a/value_a)` while `total_shares` is unchanged (`aquarius.rs:90-114`, `lp.rs:75-84`).
4. Call controller `borrow` on the LP-collateralized account; `Context` resolves the inflated LP price through `prices` and passes the sanity band (band admits up to ~10x). Withdraw the borrowed assets.
5. Repay the flash loan from borrowed proceeds (`InvalidFlashloanRepay` check passes since repayment is a balance/allowance pull). The donation remains in the pool, still largely owned by the attacker's shares.
6. Let the position go under water: `liquidate` seizes LP collateral worth less than the debt; residual debt is written down via `clean_bad_debt`/`recapitalize`, transferring the loss to suppliers.
