### Title
Webhook signature verification is bound to `repository.owner.login` while all event handlers act on `repository.full_name`, allowing sync/status/check-run forgery for any repository whose organization has no `webhook_secret` configured - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App / HMAC secret to validate a webhook against using `repository_owner`, computed from `params.dig('repository', 'owner', 'login')` [1](#0-0) . But every event handler locates the target `Repository`/`Stack` using a *different* field from the same payload, `payload.dig('repository', 'full_name')` [2](#0-1) . These two fields are never checked for consistency, and `GitHubApp#verify_webhook_signature` explicitly trusts the request unconditionally when no `webhook_secret` is configured for that organization: `return true unless webhook_secret` [3](#0-2) .

### Finding Description
Shipit supports multiple GitHub organizations, each with its own independently configured, *optional*, `webhook_secret` [4](#0-3) [5](#0-4) . The setup docs explicitly describe the webhook secret as "(optional)" [6](#0-5) .

The equality binding that should hold is:
`organization authenticated by verify_signature (repository.owner.login)` == `organization/repository actually written to by the handler (repository.full_name)`

Before the attacker's request: for a legitimate webhook, GitHub itself guarantees `repository.owner.login` and `repository.full_name` describe the same repository, and the signature is computed by GitHub over the whole raw body using that org's real secret.

After the attacker's request: since the JSON body is entirely attacker-controlled from `WebhooksController#create` (`params = JSON.parse(request.raw_post)` [7](#0-6) ), nothing stops an attacker from crafting a payload where `repository.owner.login` names an organization configured in Shipit **without** a `webhook_secret` (verification then trivially passes via `return true unless webhook_secret`), while `repository.full_name` names a completely different, victim organization/repository that Shipit also tracks. `Handler#stacks` and `Handler#repository_name` will resolve and act on the victim repository's `Stack`s/`Commit`s regardless of which organization satisfied `verify_signature` [2](#0-1) , and `Repository.from_github_repo_name` parses `owner/name` straight out of that string with no cross-check against the authenticated organization [8](#0-7) .

This lets an unprivileged attacker (who needs no secret, no GitHub App credentials, and no prior authorization for the victim org) trigger handlers on the victim's stacks:
- `PushHandler#process` forces `stack.sync_github(expected_head_sha: params.after)` for any not-archived stack on the guessed branch of the victim repo [9](#0-8) .
- `StatusHandler#process` injects a forged commit status (`create_status_from_github!`) for any commit sha in the system, which the merge queue/deploy-readiness logic elsewhere relies on [10](#0-9) .
- `CheckSuiteHandler#process` schedules `schedule_refresh_check_runs!` for arbitrary stacks/commits [11](#0-10) .

### Impact Explanation
Forged/spoofed commit statuses and forced GitHub-sync events can influence Shipit's deploy/merge-readiness gating for a repository the attacker does not own and has no relationship to, purely because a *different, unrelated* organization in the same Shipit installation happens to have no `webhook_secret` configured. This crosses a repository/organization trust boundary without any credential belonging to the victim organization, matching the "cross-repository writes / unauthorized deploy or merge" impact class: an attacker can push forged commit statuses or force sync events against a stack they don't control, corrupting its deploy state and check-run status without holding that org's `webhook_secret`, `api_clients_secret`, or `GITHUB_TOKEN`.

### Likelihood Explanation
Any Shipit installation using the multi-organization `github:` config format documented in `docs/setup.md`, where at least one configured organization omits `webhook_secret` (explicitly called out as optional, and shown as `nil` in the shipped example `config/secrets.development.shopify.yml`), is exposed. The attacker needs no authentication at all - only knowledge of the name of an org in the installation lacking a secret and the `owner/name` of the victim repository, both of which are typically public information (GitHub org/repo names).

### Recommendation
- Verify the webhook signature using the organization/app config resolved from a value that is also used later for handler dispatch, and enforce that `repository.owner.login` and `repository.full_name`'s owner segment match before/along with signature verification.
- Do not silently accept unsigned webhooks (`return true unless webhook_secret`) for organizations lacking a `webhook_secret`; either require `webhook_secret` for all configured organizations, or reject cross-organization payload mismatches independent of whether a secret is configured.
- In `Handler#repository_name`/`Repository.from_github_repo_name`, cross-check the resolved repository's owner against the authenticated `repository_owner` used in `verify_signature`, rejecting the request on mismatch.

### Proof of Concept
1. Configure Shipit (multi-org mode) with two organizations: `orgA` (no `webhook_secret`) and `victimOrg` (has `webhook_secret`), both with repositories tracked as Shipit stacks.
2. As an unauthenticated attacker, POST to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha already known to exist>",
  "repository": {
    "owner": { "login": "orgA" },
    "full_name": "victimOrg/victim-repo"
  }
}
```
3. `WebhooksController#verify_signature` computes `repository_owner = "orgA"`, calls `Shipit.github(organization: "orgA").verify_webhook_signature(...)`, which returns `true` unconditionally because `orgA` has no `webhook_secret` [3](#0-2) .
4. `PushHandler` then resolves `repository_name = "victimOrg/victim-repo"` and calls `stack.sync_github(...)` on the victim's real stack, even though the request was never signed by `victimOrg`'s secret.
