### Title
Missing state-var length cap on `||=` (concat) assignment allows unbounded AA state var value to be persisted before size validation - (File: formula/evaluation.js)

### Summary
`evaluate()`'s `state_var_assignment` case in the AA formula interpreter enforces `MAX_STATE_VAR_VALUE_LENGTH` only on the `=` accessor path, but not on the `||=` (concat) accessor path, mirroring the ZCR_EL2 pattern where one accessor traps/sanitizes a value and another silently bypasses the cap.

### Finding Description
In `formula/evaluation.js`, the `state_var_assignment` opcode handler computes the new value for a state variable differently depending on the assignment operator:

- For `assignment_op === "="`, the code explicitly caps the value: it checks `res.length > constants.MAX_STATE_VAR_VALUE_LENGTH` for strings before storing. [4](#0-3) 

- For `assignment_op === "||="`, the code instead calls `concat(value, res)` to build the new value and stores it directly with **no length check at all**, unlike the `"="` branch. [5](#0-4) 

This is structurally the same defect class as CVE-2026-63941: two different "accessors" write to the same underlying state (`ZCR_EL2` register vs. AA state var value), one accessor enforces the cap/sanitization rule, the other does not, and the un-capped value is later consumed by a privileged/trusted downstream operation (writing to HW / persisting to the AA's on-disk KV store) that assumes the invariant was already enforced.

The only downstream enforcement of `MAX_STATE_VAR_VALUE_LENGTH` for the byte-balance/storage-size accounting is in `aa_composer.js`'s `updateStorageSize()`, which is called from `finish()` **after** `saveStateVars()` has already written the (potentially oversized) value into the LevelDB batch: [6](#0-5) 
and similarly in `handleSecondaryTriggers()`: [3](#0-2) 

`saveStateVars()` unconditionally serializes and writes any `state.updated` var without re-checking its size: [7](#0-6) 

So even if `updateStorageSize()` subsequently detects the var is too large and returns an error causing `revert()`, the write into `batch` has already happened; whether this materially escapes depends on whether `revert()`'s `batch.clear()` ( [8](#0-7) ) reliably discards the batched writes in every code path (primary vs. secondary triggers, `bAir` mode, etc.) before the batch is flushed to storage — this ordering/rollback interaction is exactly the kind of "restore point programs unsanitized value into persistent state" issue the ZCR_EL2 bug describes.

### Impact Explanation
If the `revert()` path does not fully undo the batched `saveStateVars()` write in every case (e.g. a secondary-trigger chain where an earlier AA in the chain already committed via `saveStateVars()` before a later AA in the same chain fails and triggers `revert()`, or the `bAir`/dry-run divergence), an unprivileged AA author could craft a `var[key] ||= long_string` state update whose resulting string exceeds `MAX_STATE_VAR_VALUE_LENGTH`, causing the AA's storage-size accounting to diverge from the actual persisted state-var size. This can lead to freezing of AA funds (byte-balance vs storage-size invariant violated) or storage bloat inconsistent with what nodes' balance-tracking assumes, i.e., a node-disagreement/AA-fund-freezing class impact.

### Likelihood Explanation
Any address can trigger any AA with a `var[key] ||= <huge string>;` state-update formula (a common, documented oscript pattern); the formula validator (`formula/validation.js`) does not statically forbid `||=` on strings, and nothing in the interpreter's `||=` branch rejects an oversized result at evaluation time. Reaching the vulnerable code path requires no special privilege — any unit poster/AA trigger sender can invoke it directly.

### Recommendation
Add the same `MAX_STATE_VAR_VALUE_LENGTH` (and well-formedness) check to the `||=` branch of `state_var_assignment` in `formula/evaluation.js` immediately after `concat(value, res)` computes `value`, before it is assigned to `stateVars[address][var_name].value`, so that all accessors that can set a state var enforce the identical cap prior to any persistence attempt — not only relying on `aa_composer.js`'s post-hoc `updateStorageSize()` check.

### Proof of Concept
1. Deploy an AA with a state-update message:
   ```
   {
     app: 'state',
     state: `{
       var['x'] ||= 'a'.repeat-equivalent-huge-literal-string-built-via-repeated-concatenation-across-many-triggers;
     }`
   }
   ```
   or more directly within a single formula using nested `||=` concatenations exceeding `MAX_STATE_VAR_VALUE_LENGTH` bytes in one evaluation.
2. Trigger the AA; the `||=` branch in `formula/evaluation.js` (lines 1365-1403) stores the oversized `value` into `stateVars[address][var_name]` without any length check, unlike the `=` branch.
3. Observe that `saveStateVars()` in `aa_composer.js` persists this oversized value to the KV store before `updateStorageSize()` gets a chance to reject it, creating a window where storage-size accounting and stored data diverge if the subsequent rollback is incomplete.

**Uncertainty note:** I could not fully trace every branch of `batch.clear()`/`revert()` to confirm whether it reliably undoes the `saveStateVars()` write in all trigger-chain configurations, since the full LevelDB `batch` implementation was outside what I could inspect via the index. This should be verified with a live Devin session to confirm whether the write truly escapes rollback, or whether it is always safely discarded (in which case the missing cap is a defense-in-depth/consistency bug rather than an exploitable persistence bug).
