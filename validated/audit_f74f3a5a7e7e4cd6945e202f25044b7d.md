### Title
Semi-blind SSRF via attacker-controlled arbiter address in arbiter contract flow - (File: arbiters.js)

### Summary
A private-payment/contract counterparty can offer an `arbiter_contract_offer` device message naming an arbitrary `arbiter_address` of their choosing (or one they control together with an accomplice). When the victim wallet later needs arbitration data for that address, it resolves an "arbstore URL" via the hub and then makes an outbound HTTP(S) request to that URL without validating that it points to a legitimate, external, non-internal endpoint, analogous to the DHIS2 SSRF where server-side code fetches an attacker-influenced URL.

### Finding Description
`wallet.js` accepts an `arbiter_contract_offer` from a paired peer and only checks that `body.arbiter_address` is a syntactically valid address, `arbiter_contract.js` stores it as-is: [1](#0-0) 

Later, resolving the arbstore endpoint for that `arbiter_address` fetches a URL via the hub and then issues raw HTTP requests to it with no allow-list, scheme restriction, or private-IP filtering: [2](#0-1) [3](#0-2) [4](#0-3) 

The only validation performed on the resolved URL is that it is a non-empty string: [5](#0-4) 

None of these code paths restrict the URL to `https://`, to a public host, or to a known arbstore domain — `url.parse(host)` in `httpRequest` and the raw `http.get`/`https.get` calls in `requestInfoFromArbStore` will happily connect to `http://127.0.0.1:...`, `http://169.254.169.254/...` (cloud metadata), or any internal hostname/port that the hub is willing to return.

A related, separately reachable, but more clearly attacker-controlled fetch exists in `uri.js`, where a `data?app=definition&definition=https://...` payload causes the wallet to directly `https.get()` an attacker-supplied URL with no host restriction: [6](#0-5) [7](#0-6) 

### Impact Explanation
If exploited, the victim's node/wallet process can be coerced into making outbound HTTP requests to internal-only endpoints (cloud metadata service, internal admin panels, LAN hosts) reachable from the node, disclosing whether such services exist/respond (port-scanning/service-fingerprinting), matching the CVE-2022-41949 "semi-blind SSRF" bug class: identifying vulnerable internal services or confirming file/service presence. This does not directly cause double-spend/fund loss, but it is a genuine information-disclosure and internal-network-probing primitive reachable from an unprivileged private-payment counterparty (or a maliciously crafted `obyte:` URI), consistent with Medium severity like the referenced advisory.

### Likelihood Explanation
Reaching the `arbiter_contract.js`/`arbiters.js` path requires the victim to interact with an arbiter contract naming the attacker's chosen arbiter (a normal user flow in this feature) and requires the hub to return a URL for that arbiter (the hub is the user's own trusted hub, but the URL string itself is supplied by whoever registered as the arbiter/arbstore — a role obtainable by any user, not just node operators). The `uri.js` path is more directly attacker-controlled but requires the victim to open/scan a crafted `obyte:data?app=definition&definition=https://...` link.

### Recommendation
- Validate resolved/attacker-influenced URLs before making outbound requests: enforce `https://` scheme, resolve and reject private/loopback/link-local IP ranges (RFC1918, 127.0.0.0/8, 169.254.0.0/16, etc.), and consider an allow-list of expected arbstore/definition hosts.
- Apply the same checks in `arbiters.js:requestInfoFromArbStore`, `arbiter_contract.js:httpRequest`, and `uri.js:fetchUrl`.
- Add request timeouts and response-size caps to reduce blind-SSRF probing utility even if the above is partially bypassed.

### Proof of Concept
1. Attacker pairs with victim's wallet and sends an `arbiter_contract_offer` device message where `arbiter_address` corresponds to an address that the attacker (or a colluding "arbstore operator") has registered with the shared hub via `hub/get_arbstore_url`, returning e.g. `http://169.254.169.254` or an internal LAN URL instead of a real arbstore.
2. Victim accepts/interacts with the contract (e.g., pays, disputes, or checks appeal fee), triggering `arbiter_contract.js:getAppealFee`/`appeal`/`getArbstoreAddresses` or `arbiters.js:getInfo`/`getArbstoreInfo`.
3. Victim's node issues an HTTP(S) request to the attacker-chosen internal URL via `httpRequest`/`requestInfoFromArbStore`, and any error/response difference (timeout vs. connection refused vs. data returned) leaks information about the internal target's presence/behavior — the classic semi-blind SSRF oracle. function requestInfoFromArbStore(url, cb){
	http.get(url, function(resp){
		var data = '';
		resp.on('data', function(chunk){
			data += chunk;
		});
		resp.on('end', function(){
			try {
				cb(null, JSON.parse(data));
			} catch(ex) {
				cb(ex);
			}
		});
	}).on("error", cb);
}

function httpRequest(host, path, data, cb) {
	var reqParams = Object.assign(url.parse(host),
		{
			path: path,
			method: "POST",
			headers: {
				"Content-Type": "application/json",
				"Content-Length": (new TextEncoder().encode(data)).length
			}
		}
	);
	var req = http.request(
		reqParams,
		function(resp){
			var data = "";
			resp.on("data", function(chunk){
				data += chunk;
			});
			resp.on("end", function(){
				try {
					data = JSON.parse(data);
					if (data.error) {
						return cb(data.error);
					}
					cb(null, data);
				} catch (e) {
					cb(e);
				}
			});
		}).on("error", cb);
	req.write(data);
	req.end();
}

function fetchUrl(url, cb) {
	var https = require('https');
	var bDone = false;
	function returnError(err) {
		console.log(err);
		if (bDone)
			return;
		bDone = true;
		cb(err);
	}
	try {
		https.get(url, function (resp) {
			if (resp.statusCode !== 200)
				return returnError("non-200 response while trying to fetch " + url);
			var data = '';

			// A chunk of data has been recieved.
			resp.on('data', function(chunk) {
				data += chunk;
			});

			// aborted before the whole response has been received
			resp.on('aborted', function () {
				returnError("connection aborted while trying to fetch " + url);
			});

			// The whole response has been received
			resp.on('end', function () {
				if (bDone)
					return;
				bDone = true;
				cb(null, data);
			});
		}).on("error", function(err) {
			returnError("non-200 response while trying to fetch " + url + ": " + err.message);
		});
	}
	catch(err) {
		returnError(err.message);
	}
}
