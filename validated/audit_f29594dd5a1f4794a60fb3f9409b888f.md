### Title
Status webhook forges CI status on commits belonging to any repository in the Shipit instance - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` authenticates an incoming GitHub webhook only against the `webhook_secret` of the **organization** derived from `repository.owner.login` (or `organization.login`) in the payload. [1](#0-0)  That authenticated "organization" identity is never re-checked against the actual repository/commit that the corresponding handler mutates. `StatusHandler#process` looks up the target purely by `sha`, across the whole database, with no repository or stack scoping at all. [2](#0-1)  This breaks the binding "organization that authenticated the request == repository that is written to."

### Finding Description
Shipit supports hosting multiple GitHub organizations/tenants from one instance, each configured with its own `webhook_secret` (see `config/secrets.development.shopify.yml`, which lists `somegithuborg`/`someothergithuborg` each with independent `webhook_secret`/`oauth` config). [3](#0-2)  The webhook signature check picks the app/secret to verify against based on `repository_owner`, computed from the attacker-controlled payload itself:

```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [4](#0-3) 

and

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(...)
  ...
end
``` [5](#0-4) 

A tenant that legitimately owns one organization onboarded to the shared instance knows (or can obtain, e.g. from their own GitHub App/organization settings) that organization's `webhook_secret`, and can therefore produce a validly-signed request where `repository.owner.login`/`organization.login` equals their own org. Signature verification only confirms "this request was signed by organization X's secret" — it never confirms that the data acted upon by the handler actually belongs to organization X.

`StatusHandler`, unlike other handlers, does not scope by `repository.full_name` via the base `Handler#stacks` helper at all. [6](#0-5)  It instead does a global commit lookup:

```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [2](#0-1) 

Since `sha` is an attacker-supplied string in the payload and commit SHAs are globally addressable within the Shipit database (not namespaced per organization in this query), a request signed with organization X's `webhook_secret` can set/forge a CI status (`state`, `context`, `description`, `target_url`) on any commit belonging to any stack/repository in the instance, including ones owned by a completely different, unrelated organization Y.

### Impact Explanation
CI status is used by Shipit to gate deploys (`required_statuses`, `blocking_statuses`, `hidden_statuses` in `DeploySpec`, feeding `Commit#deployable?`). By forging a "success" status on a victim organization's commit that is normally blocked by a failing/pending real CI check, an attacker who only controls a co-tenant organization on the same shared Shipit instance can make an otherwise non-deployable commit appear deployable, enabling an **unauthorized deploy** of that commit for a stack they have no legitimate access to. This matches the required Critical impact category "unauthorized deploy, rollback or merge," achieved purely by exploiting the mismatch between the authenticated organization and the (unscoped) written commit.

### Likelihood Explanation
This requires the attacker to control one legitimate, low-trust GitHub organization/repository already onboarded to the same multi-tenant Shipit instance (a supported and documented configuration), but crucially does **not** require any privileged access to the victim's organization, repository, or Shipit account/session/API token — it only exploits the engine's own commit-lookup logic being unscoped by repository. Given that shared/multi-tenant Shipit deployments are an explicit supported use case, this is a realistic likelihood for any installation onboarding more than one organization.

### Recommendation
Scope `StatusHandler#process` (and any other handler doing global lookups keyed only by `sha`) to the repository identified in the payload, using the same `Repository.from_github_repo_name` / `stacks` mechanism used by other handlers, and additionally verify that the `repository.full_name`'s owner matches the `repository_owner`/`organization.login` used for signature verification, so that the organization that cryptographically authenticated the webhook is the same one whose repository/commit data is mutated.

### Proof of Concept
1. Attacker legitimately owns organization `attacker-org`, onboarded to a shared Shipit instance alongside victim organization `victim-org`, each with distinct `webhook_secret`s. [3](#0-2) 
2. Attacker crafts a `status` event payload: `{"repository": {"owner": {"login": "attacker-org"}}, "sha": "<victim-org commit sha>", "state": "success", ...}` and signs it with `attacker-org`'s known `webhook_secret`.
3. `WebhooksController#verify_signature` resolves `repository_owner` = `"attacker-org"`, fetches `attacker-org`'s `GitHubApp`, and verifies the signature successfully, since the attacker legitimately controls that secret. [5](#0-4) 
4. `StatusHandler#process` runs `Commit.where(sha: params.sha)`, finds the victim's commit (belonging to `victim-org`'s stack) and calls `create_status_from_github!(params)`, writing the forged `"success"` status onto it — with no check that the commit's repository owner matches `attacker-org`. [2](#0-1) 
5. If `victim-org`'s deploy gating relies on this status (via `required_statuses`), the forged status can unblock/trigger an unauthorized deploy on the victim's stack.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
