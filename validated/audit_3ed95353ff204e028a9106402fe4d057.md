## Title
Arbiter/ArbStore contract flow performs authenticated HTTP requests to an unvalidated attacker-supplied URL - (File: arbiter_contract.js)

### Summary
This is analogous to the n8n bug: a URL obtained indirectly (via a hub lookup keyed on an untrusted, peer-supplied `arbiter_address`) is used directly to make outbound authenticated HTTP requests, without validating that the URL belongs to a trusted/expected origin. In ocore, the arbiter contract feature (`arbiter_contract.js`) resolves an ArbStore base URL through `device.requestFromHub("hub/get_arbstore_url", address, ...)` and then immediately issues POST/GET requests to that URL, carrying sensitive contract data (pairing codes, party addresses, contract terms, encrypted packages) — with no allow-list, no pinning, and no scheme/host restriction.

### Finding Description
An arbiter contract can be initiated by any paired device (a "private-payment counterparty") sending an `arbiter_contract_offer` message that includes an `arbiter_address` field [1](#0-0) . Nothing in `store()` (which persists incoming offers received from a peer) validates that `arbiter_address` is a real/legitimate arbiter — it is stored and later used verbatim to derive the ArbStore endpoint [2](#0-1) .

When the user later interacts with the contract (`openDispute`, `appeal`, `getAppealFee`, `getArbstoreAddresses`), the wallet calls `device.requestFromHub("hub/get_arbstore_url", address, ...)` to fetch a URL string associated with `arbiter_address` (or `arbstore_address`), and then passes that URL straight into `httpRequest()`, which does a raw `http.request`/`https.get` to `<url>/api/...` with no validation of the returned string's origin, scheme, or format: [3](#0-2) [4](#0-3) [5](#0-4) [6](#0-5) .

Unlike `arbiters.js`, which validates the hub-returned URL with `validationUtils.isNonemptyString(url)` before use [7](#0-6) , `arbiter_contract.js`'s `getArbstoreAddresses`, `openDispute`, `appeal`, and `getAppealFee` perform **no such check** on the URL returned by the hub before constructing an HTTP request from it with `url.parse(host)` [8](#0-7) . Because the `arbiter_address` that drives this lookup is attacker-controlled (supplied by the offering peer in `arbiter_contract_offer`, and separately re-used in `getArbstoreAddresses`/`openDispute`/`appeal`/`getAppealFee` which key off `objContract.arbiter_address` read straight from the stored, peer-originated contract row), a malicious peer can steer the local wallet toward a hub-registered arbiter/arbstore whose URL points to an attacker-controlled host. The wallet then sends sensitive contract payloads — including `my_pairing_code` (permanent device pairing secret material), `my_address`, `peer_address`, contract terms, and (for private assets) `encrypted_contract` packages — to that URL via `httpRequest`/`openDispute`'s POST bodies [9](#0-8) .

### Impact Explanation
Sending `my_pairing_code` (which encodes the permanent pairing secret used to re-establish a device correspondent relationship) and contract/party addresses to an attacker-chosen origin allows an attacker to impersonate or pair as a party to disputes, harvest wallet/party addresses and contract metadata, and potentially manipulate the arbitration/appeal flow (fake appeal fees, fake dispute responses) which drives on-chain shared-address fund release logic in `deriveSharedAddress`/`complete`. This can lead to fund loss or dispute manipulation for parties relying on the arbiter/arbstore protocol, satisfying the "AA fund loss" / "unauthorized spending" class of impact via a paired/counterparty-controlled trigger.

### Likelihood Explanation
Reachable by any paired device acting as a "private-payment counterparty" simply by proposing an arbiter contract with an `arbiter_address` under the attacker's control (or by registering as an arbiter on the hub, if permitted) — no special privilege beyond normal pairing is required. The victim only needs to accept/interact with the offered contract (open a dispute, appeal, or check appeal fee) for the outbound request to fire.

### Recommendation
Validate the URL returned from `hub/get_arbstore_url`/`hub/get_arbstore_url_by_address` in `arbiter_contract.js` the same way `arbiters.js` already does (`validationUtils.isNonemptyString(url)`), and additionally enforce it matches an expected scheme/format (e.g., `https://` with a valid hostname) before calling `httpRequest`. Consider pinning/verifying the ArbStore's identity (e.g., via `arbstore_device_address`) prior to sending any pairing codes or contract details, and avoid sending `my_pairing_code`/`encrypted_contract` to a URL that hasn't been corroborated against a known-good arbiter registry entry.

### Proof of Concept
1. Attacker pairs with victim's wallet as a normal correspondent device.
2. Attacker sends `arbiter_contract_offer` with `arbiter_address` set to an address that attacker has registered with the hub via `hub/get_arbstore_url` to resolve to `https://attacker.example.com`.
3. Victim accepts/uses the contract and later calls `openDispute`/`appeal`/`getAppealFee`; `arbiter_contract.js` resolves the URL via `device.requestFromHub("hub/get_arbstore_url", objContract.arbiter_address, ...)` [10](#0-9)  without validating it, then POSTs `my_pairing_code`, addresses, and contract details to `https://attacker.example.com/api/dispute/new` [11](#0-10) .
4. Attacker's server receives sensitive pairing/contract data and can respond with attacker-controlled `arbstore_address`/`arbstore_device_address`, further poisoning the shared-address definition derivation in `deriveSharedAddress` [12](#0-11) .

function httpRequest(host, path, data, cb) {
	var reqParams = Object.assign(url.parse(host),
		{
			path: path,
			method: "POST",
			headers: {
				"Content-Type": "application/json",
				"Content-Length": (new TextEncoder().encode(data)).length
			}
		}
	);
	var req = http.request(
		reqParams,
		function(resp){
			var data = "";
			resp.on("data", function(chunk){
				data += chunk;
			});
			resp.on("end", function(){
				try {
					data = JSON.parse(data);
					if (data.error) {
						return cb(data.error);
					}
					cb(null, data);
				} catch (e) {
					cb(e);
				}
			});
		}).on("error", cb);
	req.write(data);
	req.end();
}
