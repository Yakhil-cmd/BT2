### Title
Heap-Buffer-Over-Read Analog via Unvalidated DER Signature Parsing in `is_valid_sig`/`vrf_verify` - (File: signature.js)

### Summary
`signature.js` exposes a PEM-signature verification path that hands attacker-controlled, arbitrary-length byte buffers straight into the native `secp256k1` module's DER signature parser (`ecdsa.signatureImport`) without validating the DER structure or length fields first. This mirrors the CVE-2018-19756 bug class: an image/byte-blob decoder (`stbi__tga_load`) trusts internal length fields in untrusted input and reads past the allocated buffer. Here, the untrusted "signature" string supplied through oscript's `is_valid_sig`/`vrf_verify` functions is decoded to raw bytes and fed to a native DER parser whose internal offset/length arithmetic is not bounds-checked by ocore before the call.

### Finding Description
`verifyMessageWithSecp256k1PemPubKey` in [1](#0-0)  does:
```
var sigBytes = Buffer.from(signature, encoding);
var rawCompact = sigBytes.length === 64 ? sigBytes : Buffer.from(ecdsa.signatureImport(sigBytes));
```
When the decoded signature is not exactly 64 bytes, the raw bytes are passed unmodified to `ecdsa.signatureImport()`, which is the DER-signature-to-compact-signature converter of the native `secp256k1` binding [2](#0-1) . No prior validation is performed on the DER envelope (e.g., that the declared length bytes are consistent with `sigBytes.length`), so a truncated or malformed DER blob is handed directly to the native parser exactly like a crafted TGA header being handed to `stbi__tga_load`.

This code path is reachable by any unprivileged AA trigger sender through the oscript `is_valid_sig` operator, which only bounds the *string* length (≤1024 chars) and checks it is valid hex/base64 — it performs no structural validation of the decoded bytes before they reach the signature-verification routine [3](#0-2) . The same `verifyMessageWithPemPubKey`/`signatureImport` path is also reachable via `vrf_verify` [4](#0-3) .

### Impact Explanation
If the native `secp256k1` DER parser under-validates length fields on malformed input (the class of bug the CVE describes for `stb_image.h`), a heap-buffer over-read/crash in the native addon would abort the Node.js process handling AA-trigger evaluation. Because AA trigger evaluation is part of consensus-critical unit/response processing that every full node must perform identically to agree on AA state, a crash triggered by a single posted trigger unit containing a crafted `is_valid_sig`/`vrf_verify` call would cause nodes to disagree on/abort processing of that unit, i.e., a node inability to confirm/process the response unit consistently — this differs from a generic network-flooding DoS because it is triggered by a single, deterministically-reachable oscript evaluation path available to any AA trigger sender.

### Likelihood Explanation
Reaching this code requires only posting an AA trigger unit whose data contains an `is_valid_sig(...)` or `vrf_verify(...)` formula call with a crafted "signature"/"proof" string — something any unprivileged user can construct and send to trigger an AA. No special privileges, peer/hub role, or network position is required.

### Recommendation
Validate the decoded signature buffer's DER structure (minimum length, sequence tag, declared vs. actual lengths) in `signature.js` before calling `ecdsa.signatureImport`, and wrap/verify that the underlying `secp256k1` native binding performs its own bounds checking on malformed DER input (upgrade the dependency if a fix exists upstream, analogous to the `stb_image.h` patch for CVE-2018-19756). Add an explicit try/catch boundary (already partially present) plus a pre-check rejecting inputs that are not well-formed minimal DER before they reach native code.

### Proof of Concept
1. Deploy an AA whose formula contains `is_valid_sig($msg, $pem_key, $sig)` with a valid `secp256k1` PEM key path enabled (`bPostPemCurvesFix`), per [5](#0-4) .
2. Send an AA trigger unit where `trigger.data.sig` is a crafted, malformed DER byte sequence (valid hex/base64 string, length ≤1024, but with an inconsistent internal length field, e.g., declared length exceeding actual remaining bytes) so it fails the `sigBytes.length === 64` check and is routed to `ecdsa.signatureImport(sigBytes)` in [6](#0-5) .
3. If the native parser under-validates the length field the same way `stbi__tga_load` did, it reads past the buffer, potentially crashing the validating node process during AA response computation.

```javascript
function verifyMessageWithSecp256k1PemPubKey(message, signature, der) {
	try {
		// Locate the BIT STRING for an uncompressed public key: 03 42 00 04 <32 X> <32 Y>
		var bitStringIdx = der.indexOf(Buffer.from([0x03, 0x42, 0x00]));
		if (bitStringIdx === -1) return false;
		var pubkey = der.slice(bitStringIdx + 3, bitStringIdx + 68); // 65 bytes: 04 + 32 + 32
		if (pubkey.length !== 65 || pubkey[0] !== 0x04) return false;

		var encoding = ValidationUtils.isValidHexadecimal(signature) ? 'hex' : 'base64';
		var sigBytes = Buffer.from(signature, encoding);
		var rawCompact = sigBytes.length === 64 ? sigBytes : Buffer.from(ecdsa.signatureImport(sigBytes));
		var compactSig = Buffer.from(ecdsa.signatureNormalize(rawCompact));

		var msgBuf = Buffer.isBuffer(message) ? message : Buffer.from(message);
		var hash = crypto.createHash('sha256').update(msgBuf).digest();
		return ecdsa.ecdsaVerify(compactSig, hash, pubkey);
```
