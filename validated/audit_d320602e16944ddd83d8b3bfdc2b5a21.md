### Title
Cross-field forged `pull_request` webhook reaches `ReopenedHandler` via `repository.owner.login`/`repository.full_name` mismatch and no-secret org bypass - (File: app/controllers/shipit/webhooks_controller.rb, lib/shipit/github_app.rb, app/models/shipit/webhooks/handlers/pull_request/reopened_handler.rb)

### Summary
`Shipit::WebhooksController#verify_signature` authenticates a webhook using `repository_owner`, which is read from `params.dig('repository','owner','login')`, and selects the matching `GitHubApp` config via `Shipit.github(organization: repository_owner)` [1](#0-0) . `GitHubApp#verify_webhook_signature` returns `true` unconditionally when that organization's config has no `webhook_secret` configured [2](#0-1) . Downstream, `ReopenedHandler`/`ReviewStackAdapter` never re-check `repository.owner.login`; they resolve the target repository/stack purely from `params.repository.full_name` via `Shipit::Repository.from_github_repo_name` [3](#0-2) .

### Finding Description
The broken binding: the system implicitly assumes `repository_owner (params.repository.owner.login)` used for HMAC selection == `owner` embedded in `params.repository.full_name` used for stack resolution. Nothing enforces this equality in code — since Shipit itself constructs and forges no cross-check, and the attacker fully controls the raw JSON body of the webhook POST, these two independently-read fields can be set to different values.

Path:
1. `Shipit::WebhooksController#create` parses `request.raw_post` as JSON with no other authentication (`before_action :verify_signature`) [4](#0-3) .
2. `verify_signature` computes `repository_owner` strictly from `repository.owner.login` (falling back to `organization.login`) [5](#0-4) , and looks up the `GitHubApp` for that org.
3. If that org's Shipit config has a blank `webhook_secret`, `verify_webhook_signature` short-circuits `return true unless webhook_secret` — no HMAC of the raw body is performed at all [2](#0-1) .
4. The now-"verified" payload is dispatched to `Shipit::Webhooks.for_event(event)` handlers, including `ReopenedHandler`, unmodified [6](#0-5) .
5. `ReopenedHandler#repository` resolves the actual target purely off `params.repository.full_name` (a separate JSON field the attacker also controls) via `Repository.from_github_repo_name`, with no comparison back to `repository.owner.login` [3](#0-2) ; `Repository.from_github_repo_name` simply splits the string on `/` and does a `find_by(owner:, name:)` [7](#0-6) .
6. If that repository's `review_stacks_enabled` is true and `provisioning_behavior_allow_all?`, `unarchive?` returns true and `stack.unarchive!` runs, or if no `ReviewStack` exists yet, `ReviewStackAdapter#unarchive!` creates one via `create!`, which provisions the stack and enqueues it (`ReviewStackProvisioningQueue.add`) [8](#0-7) [9](#0-8) .

Exploit: attacker POSTs a forged `pull_request`/`reopened` body where `repository.owner.login` = `no-secret-org` (an org configured in Shipit with `webhook_secret` blank) but `repository.full_name` = `<any-org>/<any-repo>` — including a different, victim organization that does have its own `webhook_secret` configured (since that org's secret is never checked against this request). Because signature verification only gates on the org named in `repository.owner.login`, and stack resolution only uses `repository.full_name`, the attacker bypasses HMAC entirely and can target any repository's `review_stacks_enabled: true, allow_all` review stack. Existing guards (`ExplicitParameters` schema, `drop_unhandled_event`) only validate field types/presence, not the owner/full_name equality, so they do not close this gap.

### Impact Explanation
A single unauthenticated request can cause Shipit to unarchive or auto-provision a `ReviewStack` for an arbitrary, attacker-chosen repository/stack that has `review_stacks_enabled: true` and `allow_all` provisioning, without ever supplying that repository's real `webhook_secret`. Auto-provisioned review stacks execute `shipit.yml` from the target repository, so an attacker who can also get an arbitrary `shipit.yml`/branch merged or referenced (e.g., via their own fork/PR against the review-stacks-enabled repo) can leverage this to trigger execution of deploy tasks. This is a payload for one (no-secret) organization mutating another organization's stack/records, matching the Critical "payload for one repository mutating another's stack" / authentication-bypass class.

### Likelihood Explanation
Preconditions: (a) at least one organization is configured in Shipit's `Shipit.github` config without a `webhook_secret` (this is the intentional "no-secret organization" case being tested), and (b) a target repository exists with a `Repository` record having `review_stacks_enabled: true` and `provisioning_behavior: allow_all`. Given those, the attack requires only a single crafted HTTP POST to `/webhooks` with forged headers (`X-Github-Event: pull_request`) and a JSON body where `repository.owner.login` and `repository.full_name` diverge — no GitHub session, API token, or secret needed. This is fully repeatable against any repository satisfying (b), for any event type whose handler resolves the repository from `full_name` (also affects `OpenedHandler`, `ClosedHandler`, `LabeledHandler`, etc., since they share the same pattern).

### Recommendation
- In `verify_signature`, refuse to trust any request when `webhook_secret` is blank instead of returning `true`; treat a missing secret as misconfiguration (fail closed), or require every configured GitHub org to have a non-blank `webhook_secret`.
- Independently, enforce that `repository.owner.login` (the field used to select/verify the webhook secret) matches the owner segment of `repository.full_name` (the field used to resolve the target `Repository`/`Stack`) before dispatching to any handler — reject the request if they diverge.

### Proof of Concept
minitest plan (`test/controllers/webhooks_controller_test.rb` style, hypothetical additions):
```ruby
test "pull_request reopened with mismatched owner/full_name and no-secret org unarchives victim stack" do
  # Setup: configure Shipit.github_config to include org "no-secret-org" with webhook_secret: nil,
  # and a separate Repository "victim-org/victim-repo" with review_stacks_enabled: true,
  # provisioning_behavior: "allow_all", plus an archived ReviewStack for environment "pr42".

  payload = {
    action: "reopened",
    number: 42,
    pull_request: {
      id: 1, number: 42, url: "...", title: "t", state: "open",
      additions: 1, deletions: 0,
      head: { sha: "abc", ref: "feature" },
      user: { login: "attacker" },
      assignees: [], labels: []
    },
    repository: {
      owner: { login: "no-secret-org" },   # selects org with NO webhook_secret -> HMAC bypassed
      full_name: "victim-org/victim-repo"  # targets a DIFFERENT org's stack
    },
    sender: { login: "attacker" }
  }.to_json

  post shipit.webhooks_path,
       params: payload,
       headers: { "X-Github-Event" => "pull_request", "Content-Type" => "application/json" }
       # deliberately NO X-Hub-Signature matching victim-org's real secret

  assert_response :ok
  assert Shipit::ReviewStack.find_by(environment: "pr42").reload.active?
  # Equality claim under test:
  #   repository_owner ("no-secret-org") used to authenticate
  #   != owner embedded in repository.full_name ("victim-org")
  # yet the write succeeded against victim-org's stack -> invariant violated.
end
```
Both sides of the binding: `repository_owner` (`no-secret-org`, drives auth) vs. owner segment of `params.repository.full_name` (`victim-org`, drives the actual DB write) — they differ, and the write still succeeds, demonstrating the invariant "a `pull_request` event only affects the repository/stack whose secret authenticated it" is violated.
