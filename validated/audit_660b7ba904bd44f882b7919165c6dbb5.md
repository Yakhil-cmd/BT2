The relevant vulnerability class exists here. The webhook signature is verified against a secret selected by the `repository.owner.login` field in the untrusted payload, but the actual write path — `StatusHandler` — resolves the target purely by commit SHA with **no scoping to that organization/repository at all**. This breaks the same "org that authenticated vs. entity that is written" binding described in the report.

### Title
Cross-Tenant Commit Status Forgery via `StatusHandler` — No Repository/Organization Scoping on SHA Lookup - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`WebhooksController#verify_signature` selects the HMAC secret to validate a webhook using `repository_owner`, a value taken straight from the untrusted JSON body (`repository.owner.login` or `organization.login`). Once verified, the event is dispatched to handlers keyed only by event type, not by the organization that was used to authenticate it. `StatusHandler#process` looks up commits with `Commit.where(sha: params.sha)` — a completely global query, unscoped to any repository or organization. Any tenant that is legitimately configured in `Shipit.github` (and therefore knows its own valid `webhook_secret`) can sign a payload whose `repository.owner.login` is its own org (so signature verification passes) while `sha` is a commit belonging to a completely different tenant's repository. This mirrors the DebtorNFT bug: a security check (signature/balance) validates one binding while a different, unguarded field is used to select the object actually mutated.

### Finding Description [1](#0-0) 
verifies the HMAC using `Shipit.github(organization: repository_owner)`, where: [2](#0-1) 
derives `repository_owner` from the payload itself.

The event is then dispatched generically: [3](#0-2) 

`StatusHandler` never re-derives or checks which repository/organization the commit SHA belongs to: [4](#0-3) 

Compare this with other handlers (`PushHandler`, PR handlers) which correctly scope work through `Repository.from_github_repo_name(...)`: [5](#0-4) [6](#0-5) 

`StatusHandler` uniquely omits this scoping, relying purely on the (globally non-unique) `sha` field, which is not covered by any binding to the organization that produced a valid signature.

Setting a status ultimately drives merge/deploy eligibility: [7](#0-6) 
`stack.schedule_merges if new_status.pending? || new_status.success?` — a forged `success` status for a required CI context can trigger the merge queue to consider a commit mergeable, and it will also satisfy deploy-blocking CI checks elsewhere in the engine.

Multiple organizations legitimately coexist in one Shipit deployment, each with their own webhook secret, as shown by the documented multi-org configuration: [8](#0-7) 

### Impact Explanation
An attacker who is merely an admin of their own legitimately-configured GitHub organization (any org present in `Shipit.github`'s config, e.g. an "Allow All" open-source or self-service tenant) can:
1. Sign an arbitrary JSON body with their own org's valid `webhook_secret` (this passes `verify_webhook_signature` because the secret lookup is keyed off `repository.owner.login`, a value they control in the payload).
2. Set `sha` to a known commit SHA belonging to a victim's repository/stack tracked by the same Shipit instance (commit SHAs are public GitHub data).
3. Set `state: "success"` with the `context` matching a CI check the victim's merge queue / deploy gating requires.

This forges CI status for a commit outside the attacker's own repository, which can unblock the merge queue (`stack.schedule_merges`) or clear a deploy-blocking status check for a completely unrelated tenant's stack — an unauthorized merge/deploy, which is explicitly a High severity impact under this engine's threat model (escalation causing an unauthorized deploy or merge).

### Likelihood Explanation
Any tenant organization onboarded into a multi-tenant Shipit instance already possesses a valid webhook secret for itself; no additional secret, session, or privileged Shipit account is required — only the ability to send an HTTP POST with a correctly-HMAC'd body for their own organization. The victim's commit SHAs are public GitHub information. The only non-trivial part is knowing/guessing a `context` string that matches a required check, which is often standard (`ci/...`, `continuous-integration/...`) or discoverable from the target's public GitHub status API.

### Recommendation
`StatusHandler` (and any handler relying on cross-cutting lookups) must scope its work to the repository/organization that produced the verified signature — i.e., resolve `stacks` the same way `Handler#stacks`/`#repository_name` does, and filter commits through that repository's stacks rather than a bare `Commit.where(sha:)`. Additionally, consider binding the authenticated organization into the request context (e.g., set during `verify_signature`) and have every handler assert that the resource it mutates belongs to that same organization before acting.

### Proof of Concept
1. Attacker controls `attacker-org`, a legitimate tenant in the Shipit instance with its own configured `webhook_secret`.
2. Attacker learns `victim-org/victim-repo`'s commit sha `S` that is currently blocked on a pending/failing CI context `ci/required-check` in Shipit.
3. Attacker crafts payload:
```json
{
  "sha": "S",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "attacker-org" } }
}
```
4. Attacker computes `X-Hub-Signature` using `attacker-org`'s own `webhook_secret` and POSTs to `/webhooks` with `X-Github-Event: status`.
5. `verify_signature` passes because `Shipit.github(organization: "attacker-org")` matches the signing secret.
6. `StatusHandler#process` executes `Commit.where(sha: "S")`, finds the victim's commit (no ownership check), and calls `create_status_from_github!`, setting a spoofed `success` status that can unblock merges/deploys on `victim-org/victim-repo`.
