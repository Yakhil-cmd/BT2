### Title
Cross-tenant `ReopenedHandler` stack mutation via organization-selection/full_name mismatch when one configured GitHub org has no `webhook_secret` - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects the `GitHubApp` to verify against using an attacker-controlled `organization.login`/`repository.owner.login` field, and `GitHubApp#verify_webhook_signature` unconditionally returns `true` when that org has no `webhook_secret` configured. Because `ReopenedHandler#repository` resolves the target repository from the independent, unauthenticated `params.repository.full_name` field, a payload can be "verified" under an unsecured org's identity while mutating a stack that belongs to a completely different, properly-secured org.

### Finding Description
Binding claimed by the question: `org whose webhook_secret verified the body == org owning repository.review_stacks / stack mutated by ReopenedHandler`.

Trace:
- `verify_signature` derives `repository_owner` purely from JSON body fields: `params.dig('repository','owner','login') || params.dig('organization','login')` [1](#0-0)  and looks up the app config with `Shipit.github(organization: repository_owner)` [2](#0-1) .
- `GitHubApp#verify_webhook_signature` returns `true` unconditionally whenever that org's `webhook_secret` is blank/unset: `return true unless webhook_secret` [3](#0-2) . The example/documented secrets schema explicitly supports `webhook_secret: # nil` per-org in multi-org mode [4](#0-3) .
- `ReopenedHandler#repository` resolves the record to mutate solely from `params.repository.full_name`, a completely separate JSON field never checked against `repository_owner`: `Shipit::Repository.from_github_repo_name(params.repository.full_name)` [5](#0-4) , then `stack.unarchive!` is invoked on that repository's `review_stacks` [6](#0-5) [7](#0-6) .
- `ReopenedHandler`'s `ExplicitParameters` schema requires only `repository.full_name`, not `repository.owner.login`, so an attacker can freely omit `repository.owner` and drive org selection via the top-level `organization.login` fallback instead [8](#0-7) .

Exploit flow: In a multi-org Shipit deployment (per the documented "Using Multiple Github Applications" schema) [9](#0-8) , suppose org `unsecured-org` is configured but its `webhook_secret` was left blank (a documented, supported state), while org `victim-org` is properly secured with a real secret. An attacker (no secrets held) POSTs to `/webhooks` with header `X-Github-Event: pull_request`, body `action: "reopened"`, `organization.login: "unsecured-org"` (no `repository.owner`), and `repository.full_name: "victim-org/some-repo"`. `verify_signature` resolves `Shipit.github(organization: "unsecured-org")`, whose `verify_webhook_signature` trivially returns `true` regardless of the `X-Hub-Signature` header/value, since that org has no configured secret. The request passes with `head 422` never triggered, `create` then dispatches to `ReopenedHandler`, which resolves the real `victim-org/some-repo` `Repository` via `full_name` and calls `stack.unarchive!` — mutating a stack belonging to `victim-org`, an org whose secret never verified this request at all.

Existing guards fail here because: `verify_signature` never cross-checks `repository_owner` against `repository.full_name`'s owner segment; `drop_unhandled_event` only filters by event type, not payload consistency; and `ExplicitParameters` only validates field presence/types, not cross-field provenance.

### Impact Explanation
A crafted, unsigned-in-practice webhook can cause `Shipit::ReviewStack#unarchive!` to run for a repository belonging to a different, properly-secured tenant/org than the one whose (absent) secret satisfied verification — a payload for one repository/org mutating another repository's stack, matching the Critical impact category ("a payload for one repository mutating another's stack"). This is repeatable against any repository/stack as long as its `owner/name` full_name is known, and works identically for the sibling `LabeledHandler`/`UnlabeledHandler`/`OpenedHandler`/`ClosedHandler` which share the identical `repository`/`full_name` resolution pattern.

### Likelihood Explanation
Preconditions: the Shipit instance must be running in multi-org GitHub App configuration (`github_default_organization` present) and at least one configured org must have a blank `webhook_secret` — a state explicitly shown as valid/supported in the example secrets file. Given that precondition, attacker cost is a single unauthenticated HTTP POST with no secrets, GitHub session, or privileged role — fully within the stated attacker capabilities. If no org has a blank secret, this specific path is not exploitable (attacker cannot forge a valid HMAC for any org without its secret), so the finding is conditioned on this specific, but documented and plausible, misconfiguration.

### Recommendation
In `WebhooksController#verify_signature`, derive the verifying organization strictly from `repository.full_name`'s owner segment (or require they match when `repository.owner.login` is present), and reject the request if they diverge. Additionally, in `GitHubApp#verify_webhook_signature`, do not silently return `true` when `webhook_secret` is blank for a multi-org configuration — require an explicit signature bypass flag, or refuse verification (return `false`) unless a secret is present in multi-org mode. In each PR handler (`ReopenedHandler`, `LabeledHandler`, `UnlabeledHandler`, `OpenedHandler`, `ClosedHandler`), assert that `Repository.from_github_repo_name(params.repository.full_name).owner` equals the organization that was used to verify the webhook signature before mutating any stack.

### Proof of Concept
Minitest plan (`test/controllers/webhooks_controller_test.rb`, `ActionDispatch::IntegrationTest` or `ActionController::TestCase` style, matching existing test conventions):

```ruby
test "pull_request reopened payload naming a different org's repository is not applied cross-tenant" do
  # Arrange: multi-org secrets with `unsecured-org` (webhook_secret blank) and `victim-org` (secret configured)
  Shipit.stubs(:secrets).returns(
    OpenStruct.new(github: {
      "unsecured-org" => { webhook_secret: nil },
      "victim-org" => { webhook_secret: "victim-secret" }
    }.with_indifferent_access)
  )

  victim_repo = shipit_repositories(:shipit) # owner: "victim-org", name: "some-repo"
  stack = create_archived_review_stack_for(victim_repo)

  body = payload_parsed(:pull_request_reopened)
  body.delete("repository")
  body["organization"] = { "login" => "unsecured-org" }
  body["repository"] = { "full_name" => "victim-org/some-repo" }

  request.headers['X-Github-Event'] = 'pull_request'
  request.headers['X-Hub-Signature'] = 'sha1=deadbeef' # arbitrary/invalid signature

  # Binding equality being asserted:
  #   org_that_verified = "unsecured-org"  (via Shipit.github(organization: "unsecured-org"))
  #   org_owning_target_repo = "victim-org" (via Repository.from_github_repo_name(full_name).owner)
  # Expectation if fixed: request must be rejected (422) OR ReopenedHandler must never mutate victim-org's stack.

  assert_no_changes -> { stack.reload.archived? } do
    post :create, body: body.to_json, as: :json
  end
  assert_response :unprocessable_entity
end
```

This test demonstrates that, prior to a fix, `verify_signature` passes (org `"unsecured-org"` has no secret so `verify_webhook_signature` returns `true`), and `ReopenedHandler` unarchives `victim-org`'s stack despite `victim-org`'s own secret never having verified the request — violating the WEBHOOK PROVENANCE binding.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
