### Title
Open redirect via unvalidated `omniauth.origin` in `GithubAuthenticationController#callback` - (File: `app/controllers/shipit/github_authentication_controller.rb`)

### Summary
`GithubAuthenticationController#callback` computes `return_url` directly from `request.env['omniauth.origin']` and passes it unmodified to `redirect_to`, with no check that the value is a same-origin/relative path or a URL under `Shipit.host`. Because the OmniAuth request phase stores whatever `origin` parameter it received (and this engine does not constrain or re-validate it at callback time), an attacker can force a freshly-authenticated victim to be redirected to an arbitrary external URL immediately after a real GitHub OAuth login.

### Finding Description
The broken binding: the code assumes `request.env['omniauth.origin']` == "a URL under `Shipit.host` (same engine origin)", but in reality `request.env['omniauth.origin']` == "attacker-controlled string, sourced from the `origin` request parameter set when the OAuth flow is initiated" with no validation performed anywhere in this engine.

Path:
- `Shipit::Authentication#force_github_authentication` redirects an unauthenticated visitor to `github_authentication_path(origin: request.original_url)` [1](#0-0)  — this is the *intended* legitimate use, where `origin` is always the app's own current URL.
- However, nothing prevents an attacker from directly sending a victim to the OmniAuth request endpoint (`GET /github/auth/github?origin=https://attacker.example`) with an arbitrary `origin` value; OmniAuth's request phase stores that raw value into `request.env['omniauth.origin']` for later retrieval at callback, without engine-side validation.
- At callback, `GithubAuthenticationController#callback` reads it back with zero host/scheme checking: `return_url = request.env['omniauth.origin'] || root_path` and then `redirect_to(return_url)` [2](#0-1) .
- The victim completes a genuine GitHub OAuth exchange (their session is authenticated: `session[:user_id]` and `session[:authenticated] = true` are set at lines 13 and 18 of the same file), and is then redirected off-site to `attacker.example`.

Existing guards do not prevent this: `force_github_authentication` only builds the legitimate redirect URL from `request.original_url`; it does not sanitize or restrict what an attacker can pass directly to the OmniAuth request endpoint, and `callback` performs no allowlist/host check on the value it reads back. There is no `verify_signature`, `require_permission!`, or model validation anywhere on this path since it's unrelated to webhook/API flows — the omission is purely in `callback`'s redirect-target handling.

### Impact Explanation
This is a post-authentication open redirect: the attacker's own request does not disclose secrets or execute privileged actions directly, but it lets an attacker redirect a just-authenticated Shipit user's browser to an arbitrary attacker-controlled destination. This can be chained into phishing (fake re-login page harvesting GitHub credentials) or used to leak referrer/state from the authenticated session into an attacker page. It affects any victim who clicks the crafted login link and is repeatable against any Shipit deployment without requiring any special repository/stack configuration — it is a deployment-wide issue, not scoped to a single stack or repository. Per the severity rubric this matches "session fixation / forced OAuth completion" territory (High), since the attacker forces the OAuth completion flow to terminate at a location of their choosing.

### Likelihood Explanation
No privileged access is required: any unauthenticated internet user can construct the link `GET /github/auth/github?origin=https://attacker.example` and send it to a victim. The only precondition is that the victim clicks the link and completes the real GitHub OAuth consent (which they would do believing they are logging into the legitimate Shipit instance, since the initial domain and OAuth provider are genuinely Shipit/GitHub). No Shipit or GitHub secrets are needed by the attacker. This is fully reproducible and low-cost.

### Recommendation
Validate `return_url` before redirecting: only allow relative paths (e.g., using `request.env['omniauth.origin']` only if it starts with `/` and is not `//` — protocol-relative — or by parsing it and asserting `URI(return_url).host` is blank or equals `Shipit.host`'s host), falling back to `root_path` otherwise. E.g.:
```ruby
def callback
  return_url = safe_return_url(request.env['omniauth.origin'])
  ...
end

def safe_return_url(url)
  return root_path if url.blank?
  uri = URI.parse(url) rescue nil
  return root_path unless uri
  return root_path if uri.host.present? # reject absolute/external URLs
  url
end
```

### Proof of Concept
```ruby
# test/controllers/github_authentication_controller_test.rb
test ":callback does not redirect to an external attacker-controlled origin" do
  auth = OmniAuth::AuthHash.new(
    credentials: OmniAuth::AuthHash.new(token: 's3cr3t'),
    extra: OmniAuth::AuthHash.new(raw_info: OmniAuth::AuthHash.new(
      id: 44, name: 'Shipit User', email: 'shipit-user@example.com',
      login: 'shipit-user', avatar_url: 'https://example.com',
      api_url: 'https://github.com/api/v3/users/shipit-user'
    ))
  )
  @request.env['omniauth.auth'] = auth
  @request.env['omniauth.origin'] = 'https://attacker.example'

  get :callback

  # Binding under test: redirect target host must equal Shipit's own host,
  # never the attacker-supplied external origin.
  refute_equal 'https://attacker.example', @response.location
  assert_no_match(/\Ahttps?:\/\/attacker\.example/, @response.location.to_s)
end
```
Running this against the current implementation fails, because `@response.location` is exactly `https://attacker.example`, demonstrating the unvalidated redirect. [2](#0-1)
