This confirms the escalation path: `User#authorized?` gates entire application access on membership in `Shipit.github_teams` [1](#0-0) , and `force_github_authentication` enforces it on every controller [2](#0-1) . `Shipit.github_teams` resolves configured team handles to `Team` records via `find_or_create_by_handle` [3](#0-2) , and authorization is checked purely by `team_id` membership in the `Membership` table, with no organization cross-check [1](#0-0) .

### Title
Cross-tenant `Team`/`Membership` mutation via unscoped `github_id` lookup in `MembershipHandler` bypasses webhook organization provenance - (File: app/models/shipit/webhooks/handlers/membership_handler.rb)

### Summary
`Shipit::WebhooksController#verify_signature` only proves that the HMAC signature matches the `webhook_secret` configured for the organization named in the payload's `organization.login`/`repository.owner.login` field; it never verifies that any other object referenced elsewhere in the same payload (e.g. `team.id`) actually belongs to that organization. `MembershipHandler#find_or_create_team!` looks up `Team` by `github_id` alone, globally, with no `organization` scoping, so a payload correctly signed by tenant A can mutate a `Team`/`Membership` row that was created for tenant B.

### Finding Description
Broken binding as an explicit equality: the code assumes `Shipit.github(organization: params.dig('organization','login')).verify_webhook_signature(...) == true` implies `params.team.id belongs to organization == params.organization.login`. These are never actually equated. `verify_signature` in `app/controllers/shipit/webhooks_controller.rb:24-30` selects the GitHub App config solely from `repository_owner` (`app/controllers/shipit/webhooks_controller.rb:59-62`, which reads `params.dig('repository','owner','login') || params.dig('organization','login')`) and checks the HMAC of the raw body against that org's `webhook_secret`. Once verified, `Shipit::Webhooks.for_event('membership').each { |handler| handler.call(params) }` (`app/controllers/shipit/webhooks_controller.rb:12`) dispatches the entire raw, attacker-controlled JSON to `MembershipHandler`, which trusts every nested field.

`MembershipHandler#find_or_create_team!` (`app/models/shipit/webhooks/handlers/membership_handler.rb:38-42`) does `Team.find_or_create_by!(github_id: params.team.id) { |team| team.organization = params.organization.login }`. Because ActiveRecord's `find_or_create_by!` first performs a `find_by(github_id: ...)` with no `organization` predicate, if a `Team` row already exists for that `github_id` (created earlier by a legitimate webhook from a *different*, unrelated organization — call it org B), it is returned unchanged; the block (which would set `organization`) never runs. `process` (`app/models/shipit/webhooks/handlers/membership_handler.rb:22-34`) then calls `team.add_member(member)` or `team.members.delete(member)` on that pre-existing org-B `Team`, writing/deleting rows in `Membership` for org B, using a `member.login` the attacker fully controls via `User.find_or_create_by_login!` (which creates the user record if it doesn't already exist).

Exact attacker request: in a multi-org `secrets.yml` deployment (`docs/setup.md` "Using Multiple Github Applications"), the attacker is themselves the operator of tenant "attacker-org" and therefore knows attacker-org's own `webhook_secret` (this is provisioned by the tenant, per the documented multi-org flow, and shared with the Shipit operator — it is not a Shipit- or GitHub-generated app secret unknown to that org's admin). They POST directly to `/webhooks` (bypassing GitHub) with header `X-Github-Event: membership`, body:
```json
{"action":"added","team":{"id":<victim_team_github_id>,"name":"x","slug":"x","url":"http://x"},"organization":{"login":"attacker-org"},"member":{"login":"attacker-login"}}
```
signed with `sha1=HMAC(attacker-org's webhook_secret, body)`. `verify_signature` fetches `Shipit.github(organization: 'attacker-org')`, HMAC matches, request passes. `MembershipHandler` then finds the pre-existing victim-org `Team` by `github_id` and appends `attacker-login` as a member.

None of the documented guards catch this: `verify_signature` only authenticates *which secret matched*, not what the payload's nested IDs reference; `drop_unhandled_event` only checks event-name-to-handler mapping; the `ExplicitParameters` schema in `MembershipHandler.params` only validates types/presence, not organization consistency; `Repository`/`Stack` validators are irrelevant since no `Repository` is involved; and there is no `require_permission!`/`current_user` check at all on the unauthenticated `/webhooks` endpoint.

### Impact Explanation
If `Shipit.github_teams` (configured via `github.oauth.teams`) includes org B's team, the attacker can add an attacker-controlled GitHub login (which need not even exist as a real GitHub account with any relationship to org B) to that team's `Membership` table, and that login then satisfies `User#authorized?` (`app/models/shipit/user.rb:80-82`), granting it full access to Shipit through `force_github_authentication` (`app/controllers/concerns/shipit/authentication.rb:20-34`) — an authorization-team escalation across tenants. Even absent `github_teams` usage, this is an unauthenticated, unauthorized write of another tenant's `Membership`/`Team` state from a fully separate tenant's webhook credentials — a cross-tenant record mutation. This is repeatable at will (any `action: added/removed`, any `member.login`, against any `team.id` the attacker can enumerate/guess, which are small sequential GitHub integers) and scales across every organization sharing the Shipit instance.

### Likelihood Explanation
Requires: (1) a multi-tenant Shipit deployment with `secrets.yml` configured per the documented "Using Multiple Github Applications" pattern, (2) the attacker controlling one of the onboarded tenant orgs (and thus legitimately knowing that org's own `webhook_secret`, which they themselves provisioned when creating their GitHub App), (3) knowledge or brute-forcible guessing of a target `team.id` (GitHub team IDs are sequential integers, and are also disclosed if the attacker was previously a legitimate member of any team anywhere). No GitHub-side action or private key is needed — the request is a raw HTTP POST to `/webhooks`. Cost is low and the vulnerability is deterministically reproducible.

### Recommendation
Scope the `Team` lookup by both `github_id` and `organization` (`Team.find_or_create_by!(github_id: params.team.id, organization: params.organization.login)`), and additionally assert in `WebhooksController` or `MembershipHandler` that `params.organization.login` (the value used to select the verifying `webhook_secret`) matches any `organization`/`repository.owner.login` value elsewhere in the payload, rejecting the request otherwise.

### Proof of Concept
minitest controller test plan (extending `test/controllers/webhooks_controller_test.rb`):
1. Fixtures: two `GithubHook::Organization` records — `shopify_membership` (org `shopify`, secret `1234`) and a new `attacker_org_membership` (org `attacker-org`, secret `4321`) — and an existing `Team` fixture `shopify_developers` with `github_id: 1, organization: 'shopify'`.
2. Build payload: `{"action":"added","team":{"id":1,"name":"Developers","slug":"developers","url":"http://x"},"organization":{"login":"attacker-org"},"member":{"login":"mallory"}}`.
3. Compute `signature = "sha1=" + OpenSSL::HMAC.hexdigest('sha1', '4321', payload_json)`.
4. `assert_equal 'shopify', Team.find_by(github_id: 1).organization` (pre-condition: left side of the broken binding — verifying org — is `attacker-org`; right side — team's true org — is `shopify`; they differ).
5. `post :create, body: payload_json, as: :json` with `X-Github-Event: membership` and `X-Hub-Signature: signature`.
6. `assert_response :ok`.
7. `assert Team.find_by(github_id: 1).members.exists?(login: 'mallory')` — proves org `shopify`'s `Membership` table was mutated by a request authenticated as `attacker-org`, i.e. the binding `verifying_organization == team.organization` was never enforced and remains broken after the request.
