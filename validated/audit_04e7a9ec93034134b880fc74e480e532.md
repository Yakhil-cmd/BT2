## Title
Unsynchronized concurrent mutation of `storage.assocBestChildren`/`assocUnstableUnits` between `writer.saveJoint()` and `storage.shrinkCache()` causes node-crashing consensus-state corruption - (File: `writer.js`, `storage.js`, `main_chain.js`)

### Summary
The CVE describes an rbtree that is updated by two code paths that don't share a common lock, creating a race window that corrupts the tree and crashes the node. `ocore` has the same anti-pattern: the in-memory maps that back main-chain/stability bookkeeping (`storage.assocUnstableUnits`, `storage.assocBestChildren`, `storage.assocStableUnits`, etc.) are mutated by two independent async flows that are gated by **different** mutex keys, so they are not mutually exclusive.

### Finding Description
When a new unit is written, `writer.saveJoint()` pushes the new unit into `storage.assocUnstableUnits` and appends it to `storage.assocBestChildren[my_best_parent_unit]`. The code explicitly notes that the `"write"` mutex that used to protect this section was removed ("without this locking, we get frequent deadlocks from mysql") and the mutation is left protected only by the `"handleJoint"` lock that the *caller* (network.js/composer.js) already holds: [1](#0-0) 

Separately, `storage.shrinkCache()` runs every 5 minutes via `setInterval` and deletes entries from the very same maps (`assocKnownUnits`, `assocCachedUnits`, `assocBestChildren`, `assocStableUnits`, `assocCachedUnitAuthors`, `assocCachedUnitWitnesses`) — but it acquires the `"write"` mutex, not `"handleJoint"`: [2](#0-1) 

Because `"write"` and `"handleJoint"` are unrelated lock keys in `mutex.js`, acquiring one does not block the other: [3](#0-2) 

So a unit being written by `saveJoint()` (guarded by `handleJoint`) can interleave, at any `await`/callback boundary, with `shrinkCache()` (guarded by `write`) that is concurrently deleting keys from the same associative arrays. This is architecturally identical to the CVE's rbtree bug: a shared tree/map is updated from two code paths without a single lock consistently held across the whole update, opening a race window.

These same maps are later read by main-chain/stability code with hard invariant checks that `throw Error(...)` on any inconsistency, e.g.: [4](#0-3) [5](#0-4) [6](#0-5) 

If `shrinkCache()`'s deletion of `assocBestChildren[best_parent_unit]` (or of a unit still referenced from `assocKnownUnits`/`assocCachedUnits`) races with `saveJoint()`'s push of a new best-child entry for the same parent, or with concurrent stability-advancement code in `main_chain.js` (`updateMainChain`, `determineIfStableInLaterUnitsAndUpdateStableMcFlag`) that also reads/writes `assocUnstableUnits`/`assocBestChildren` while holding only `"handleJoint"`, the resulting map can end up missing an entry, holding a stale entry, or otherwise inconsistent with the DB state that the same functions assert against with `throw Error(...)`/`throwError(...)`.

### Impact Explanation
An uncaught `Error` thrown from these assertion paths in Node.js terminates the process (there is no recovery), producing a Denial of Service against the full node. Because `shrinkCache` is an unconditional, periodic background task and `saveJoint`/main-chain advancement run on every accepted unit, any ordinary unit submission that happens to land in the race window between the two lock domains can crash the node — this matches the "reachable by an unprivileged unit poster" and DoS criteria of the analog.

### Likelihood Explanation
The race window opens every 5 minutes (the `shrinkCache` interval) and lasts for the duration of its DB round-trips over `MAX_ITEMS_IN_CACHE`-sized unit lists, during which any freshly posted/forwarded unit being written via `saveJoint()` (guarded only by `handleJoint`) can mutate the same maps concurrently. No special privilege beyond being able to get a unit accepted/validated is required, and the trigger is largely a matter of timing rather than crafted payload content, making it a plausible if intermittent DoS vector rather than a certainty on every unit.

### Recommendation
Use a single, consistently-held lock (or explicitly document/ensure `shrinkCache` only touches keys that cannot simultaneously be touched by `saveJoint`/`main_chain` code) for all mutations of `assocUnstableUnits`, `assocBestChildren`, `assocStableUnits`, `assocKnownUnits`, `assocCachedUnits`, `assocCachedUnitAuthors`, and `assocCachedUnitWitnesses`. Either restore locking of `saveJoint`'s cache-mutation section with the same `"write"` key that `shrinkCache` uses, or change `shrinkCache` to acquire `"handleJoint"` (or both) before mutating these caches, so that the two paths cannot interleave.

### Proof of Concept
1. Run a node with `conf.bFaster`/typical settings so that `storage.shrinkCache()` is scheduled via `setInterval(shrinkCache, 300*1000)` (`storage.js:2296`).
2. Continuously submit/relay valid units so that `writer.saveJoint()` frequently mutates `storage.assocBestChildren`/`assocUnstableUnits` under only the `"handleJoint"` lock (`writer.js:586-602`).
3. Ensure the node's cache sizes exceed `MAX_ITEMS_IN_CACHE` so `shrinkCache()` performs its DB queries and subsequent `delete storage.assocBestChildren[row.unit]` (etc.) under the `"write"` lock (`storage.js:2250-2296`), which does not block `saveJoint()`.
4. Because both paths execute asynchronously without a common lock, repeated unit submissions during the 5-minute cache-shrink cycle can eventually cause a `saveJoint`/`main_chain` invariant check (e.g. `throw Error("no best children of last stable MC unit...")` or `throwError("different best children of ...")`) to fire on inconsistent map state, crashing the node process.
