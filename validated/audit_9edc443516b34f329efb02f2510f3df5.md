## Finding

### Title
Missing access control on `BridgeCommittee.initializeConfig()` allows front-running to hijack the bridge's token/chain configuration - (File: `bridge/evm/contracts/BridgeCommittee.sol`)

### Summary
This is the same root-cause class as the reported `startDistribution()` bug: a state-transition function that should only ever be called once by the deployer/owner has **no access-control modifier at all**, only a "not yet set" guard. In `BridgeCommittee`, `initializeConfig()` is the analog of `startDistribution()` — it is meant to be called exactly once, immediately after deployment, but any unprivileged address can call it first.

### Finding Description
`initializeConfig()` is declared `external` with **no `onlyOwner`, no `initializer` modifier, and no committee-signature check** — only a one-time guard on the storage variable itself: [1](#0-0) 

Compare this to every other privileged state-change in the same contract, all of which are gated by `verifyMessageAndSignatures`/committee stake thresholds, e.g. `updateBlocklistWithSignatures`: [2](#0-1) 

The deployment script calls `initialize()` on the `BridgeCommittee` proxy, then in a **separate later transaction** calls `initializeConfig()` on both the proxy and the raw implementation address: [3](#0-2) 

Because `initialize()` and `initializeConfig()` are two distinct on-chain transactions (not atomic), an attacker who observes the deployer's `initialize()` transaction in the mempool can front-run/race the deployer's `initializeConfig()` call and set `config` to an attacker-controlled contract that implements `IBridgeConfig`. Once `config` is non-zero, the guard `require(address(config) == address(0), ...)` permanently blocks the legitimate deployer from ever fixing it — this is a one-shot capability with no recovery path, matching the "unpause bug can be triggered by anyone before the privileged party intends" pattern from the ERC20Distribution report exactly, but here the mis-set value is unrecoverable (worse than a re-pausable boolean).

### Impact Explanation
`IBridgeConfig` supplies `tokenAddressOf(tokenID)` and token/chain metadata that `SuiBridge` uses to decide which ERC20 contract and how much to release from the vault when settling an incoming bridge message, per the documented flow: [4](#0-3) 

If `config` is attacker-controlled, the attacker can arbitrarily remap `tokenID → tokenAddress` (or price/decimals) to point at a different, more valuable ERC20 already funded in the `BridgeVault`, or otherwise corrupt the token/chain metadata that other bridge logic trusts unconditionally. Since the committee's signature verification only authenticates the *message* (chain, token id, amount), and it is the `config` mapping that translates `token id → real token address/decimals`, a hijacked config lets an attacker cause `vault.transferERC20` to release the wrong (higher-value) token for a legitimately-signed low-value transfer, i.e., theft of vault funds — squarely in the "bridge governance bypass enabling illegitimate ... unlock" Critical bucket.

### Likelihood Explanation
This requires the attacker to win a mempool race between two deployment-time transactions on a public chain (e.g., Ethereum mainnet or Sepolia, per `deploy_bridge.s.sol`'s explicit handling of `chainID == 1` / `11155111`). This is a narrow window (a few blocks around initial deployment), and depends on the deployer not deploying/initializing config atomically. It is a real, unprivileged, no-guard bug, but the exploit window is deployment-time only, not persistently reachable post-launch — this materially reduces (but does not eliminate) practical likelihood relative to a bug reachable at any time.

### Recommendation
Add an `onlyOwner`/`initializer`-style guard to `initializeConfig()` (e.g., restrict to the deployer address recorded during `initialize()`, or fold the config address into the `initialize()` call itself so both are set atomically in one transaction), removing the ability for an arbitrary unprivileged caller to win the race.

### Proof of Concept
1. Deployer submits `BridgeCommittee.initialize(...)` to a public mempool.
2. Attacker observes the pending/confirmed `initialize()` tx, and before the deployer's follow-up `initializeConfig(bridgeConfig)` transaction lands, attacker submits `BridgeCommittee(bridgeCommitteeProxy).initializeConfig(attackerConfig)` with higher gas.
3. Attacker's transaction is mined first; `config` is now permanently set to `attackerConfig` (the `require(address(config) == address(0))` guard blocks the deployer's legitimate call from ever succeeding).
4. Attacker's `IBridgeConfig` implementation returns attacker-chosen `tokenAddressOf`/decimals/price mappings.
5. When a legitimately-signed bridge transfer message for a low-value token id is processed by `SuiBridge`, it resolves the token address via the poisoned `config`, causing the vault to release a different/higher-value ERC20 to the attacker's recipient address.
