Confirmed. `CCMenuController` in `app/controllers/shipit/api/ccmenu_controller.rb` overrides `BaseController#stack` and `#authenticate_api_client`, breaking the stack-scoping binding that every other API controller relies on.

## Title
Stack-scoped `ApiClient` token can read any stack's CCMenu status, bypassing its `stack_id` authorization scope - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::ApiClient` records can be scoped to a single stack via `stack_id`, and `Api::BaseController#stack` enforces that scope by resolving the requested stack through `stacks`, which filters to `Stack.where(id: current_api_client.stack_id)` whenever the client is stack-scoped: `stacks ||= current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all` and `stack ||= stacks.from_param!(params[:stack_id])`. [1](#0-0)  `Api::CCMenuController` overrides both `stack` and `authenticate_api_client`, resolving the target stack directly with `Stack.from_param!(params[:stack_id])` instead of going through the scoped `stacks` relation. [2](#0-1) 

### Finding Description
The binding that should hold is: `stack a token authorizes == stack a request touches`. For every other API resource this equality is enforced because `stack` is always derived from the client-scoped `stacks` relation. [1](#0-0)  The `CCMenuUrlController#client`/`ccmenu_url_controller.rb` flow demonstrates the intended design: it mints a fresh `ApiClient` with `permissions: %w[read:stack]` and no `stack_id`, meaning any legitimately-scoped CCMenu client is expected to be tied to one stack by an admin creating it with `stack:` set. [3](#0-2) 

However, `CCMenuController` breaks this: it authenticates via `ApiClient.authenticate(params[:token])`, which finds *any* valid `ApiClient` by verifying only the signed `id` in the token — it never checks `stack_id` at authentication time. [4](#0-3)  The `require_permission :read, :stack` before_action only checks that the client's `permissions` array contains `read:stack` — it is a global capability check, not a per-resource ownership check: `current_api_client.check_permissions!(operation, scope)` → `permissions.include?(required_permission)`. [5](#0-4) [6](#0-5)  Because `CCMenuController#stack` resolves `params[:stack_id]` against the unscoped `Stack` model rather than the `stacks` relation, a request supplying a *different* `stack_id` than the one the token was minted for still passes both the authentication and permission checks, and returns data for the attacker-chosen stack. [7](#0-6) 

### Impact Explanation
This is an unauthenticated-scope-bypass read of stack/deploy state: any holder of a stack-scoped `read:stack` CCMenu token (which is routinely embedded in unauthenticated CI-dashboard URLs, e.g. via `CCMenuUrlController#fetch`, which the front-end exposes as a plain query-string URL) can enumerate/read `deploys_and_rollbacks` status (name, activity, lastBuildStatus, lastBuildLabel, lastBuildTime, webUrl) for *every* stack in the Shipit instance, not just the one the token was scoped to. [8](#0-7)  This matches the "unauthenticated read of stack state" High-severity bucket, since the token holder never needed elevated permission for the other stacks — the authorization scope check for stack identity was simply skipped.

### Likelihood Explanation
Likelihood is high given normal usage: CCMenu tokens are generated and distributed as plain URLs (`ccmenu_url`) for use in unauthenticated CI status widgets, so a leaked/observed URL for stack A is trivially replayed with a different `stack_id` param to read stack B, C, etc., with no need for credentials beyond the one legitimately-obtained token.

### Recommendation
Change `Api::CCMenuController#stack` to resolve through the base controller's stack-scoped `stacks` relation (i.e., `stacks.from_param!(params[:stack_id])`) instead of calling `Stack.from_param!` directly, so a stack-scoped `ApiClient`'s token can only ever resolve to the stack it was created for.

### Proof of Concept
1. Admin creates (or the app auto-creates via `CCMenuUrlController#fetch`) a stack-scoped `ApiClient` for stack A with `permissions: ['read:stack']`, `stack_id: A.id`, and obtains its `authentication_token`. [3](#0-2) 
2. Attacker who obtains this token (e.g., from a shared CCMenu/CI dashboard URL) sends `GET /api/stacks/:other_owner/:other_repo/:other_env/ccmenu.xml?token=<stolen_token>` with `stack_id` pointing to stack B, which the client was never scoped to.
3. `authenticate_api_client` succeeds because `ApiClient.authenticate(token)` only verifies the signature/id, not `stack_id`. [4](#0-3) 
4. `require_permission :read, :stack` passes because the client's `permissions` includes `read:stack` globally. [5](#0-4) 
5. `stack` resolves stack B via unscoped `Stack.from_param!(params[:stack_id])`, and the controller renders stack B's deploy/build status XML to the attacker. [7](#0-6)
