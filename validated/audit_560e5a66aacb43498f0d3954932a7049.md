### Title
Arbitrary route contract can execute unauthorized token transfers under the caller's signed authorization tree - ([File: contracts/controller/src/strategies/swap.rs](contracts/controller/src/strategies/swap.rs))

### Summary
The controller forwards caller-supplied opaque swap bytes to the configured aggregator and authorizes only the expected input-token transfer. The route payload can nevertheless name an arbitrary pool contract. During route execution, that contract can invoke an unrelated token’s `transfer(victim, attacker, amount)` entrypoint. Soroban records this authorization request beneath the victim’s signed `swap_collateral`/strategy invocation, so if the victim signs the simulated tree—including a UI-hidden child transfer—the rogue contract drains wallet assets outside the lending position.

### Finding Description
`process_swap_collateral` authenticates the account owner or delegate, withdraws the requested collateral, and passes the caller’s `swap` bytes to `swap_tokens_or_passthrough` through `withdraw_and_swap_from_supply`. `swap_tokens` snapshots input/output balances, calls `authorize_transfer_as_current` for exactly `amount_in` from the controller to the configured router, then invokes `router.execute_strategy(controller, amount_in, swap)`.

The route remains opaque to the controller. The router decodes pool and token addresses from the payload’s asset registry and dispatches each hop to the selected address without a pool-address allowlist. Consequently, third-party code executes below the caller’s authorization context.

The repository contains a direct proof of this authorization-tree behavior in `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs`:

- The router double invokes the route-selected `hop_pool`.
- `RogueHopPool::swap` calls `token.transfer(victim, attacker, amount)` for a token unrelated to the lending markets.
- Simulation records that transfer as a child of the victim’s `swap_collateral` authorization.
- Enforcing mode rejects the transfer when the signed tree omits it, but succeeds when the victim signs the tree containing it.
- The test confirms that the lending swap can still produce and credit a fair output while the unrelated wallet token is stolen.

The same route boundary exists for `multiply`, `swap_debt`, `swap_collateral`, and `repay_debt_with_collateral` whenever a non-empty route is used.

### Impact Explanation
This is theft of user funds beyond the collateral/debt assets involved in the strategy. A malicious route contract can transfer any token for which the victim’s signed authorization tree can satisfy `from.require_auth()`. The stolen amount is not bounded by the swap input, `amountOutMin`, positive-output checks, `RouterOverspend`, or the account’s final health factor because those checks measure only the controller’s input/output token balances.

The operation can still be economically successful and risk-valid: the rogue venue can return a fair output or the attacker can pre-fund it with output tokens. The victim therefore receives the expected position mutation while unrelated wallet funds are transferred to the attacker.

### Likelihood Explanation
The attack requires the victim to submit a malicious route and sign the authorization tree containing the extra transfer. That is user interaction, but it is plausible through a malicious quote provider, compromised frontend, injected route payload, or wallet display that does not clearly reveal nested authorization children. No privileged role, leaked key, oracle manipulation, upgrade, or flawed market parameter is required.

The vulnerable execution path is reachable by an unprivileged account through public strategy entrypoints. Existing controller checks do not decode or constrain route pool addresses, and the documented client-side mitigation is outside the contracts’ enforcement boundary.

### Recommendation
Do not allow route payloads to select arbitrary executable pool contracts inside an authorization-bearing lending call.

The strongest mitigation is a governance-maintained venue/pool registry or venue-specific pool allowlist checked by the router before dispatch. If arbitrary new pools must be supported, require an approved adapter/registry entry rather than trusting an address embedded in route bytes. This should apply to all strategy verbs using `swap_tokens`.

Additionally, require clients and the quote pipeline to display and validate the complete authorization tree, explicitly rejecting children other than the expected router input transfer. This is defense in depth and not a substitute for on-chain pool validation.

### Proof of Concept
1. Victim holds `USDC` supply and an unrelated token `VAULT` not used by the route.
2. Attacker deploys `RoguePool` implementing the venue ABI expected by the selected opcode. Its swap implementation:
   - accepts the routed input or is pre-funded with the expected output,
   - calls `VAULT.transfer(victim, attacker, victim_balance)`,
   - returns enough `ETH` to satisfy `amountOutMin`.
3. Attacker provides the victim a route payload whose asset registry includes:
   - `USDC`,
   - `ETH`,
   - `RoguePool`.
4. The encoded program contains one swap instruction selecting `RoguePool`, `USDC -> ETH`, and a positive `amountOutMin`.
5. Victim invokes:

```text
swap_collateral(
    caller = victim,
    account_id = victim_account,
    current = HubAssetKey { hub_id: H, asset: USDC },
    amount = 5_000_000_000,
    new = HubAssetKey { hub_id: H, asset: ETH },
    swap = malicious_route_xdr
)
```

6. `swap_tokens` authorizes only the expected `controller -> router` USDC transfer and calls `execute_strategy`.
7. `RoguePool` executes under the route and requests `VAULT.transfer(victim, attacker, victim_balance)`.
8. Transaction simulation records that transfer as a child authorization under the victim’s `swap_collateral` invocation.
9. If the victim signs that returned tree, both effects execute:
   - the account receives/credits the ETH swap output,
   - the attacker receives the victim’s entire `VAULT` balance.

The repository’s regression test demonstrates both branches: an honest signed tree rejects the rogue transfer, while the simulation-generated tree containing the child transfer authorizes it and moves the full unrelated token balance to the attacker.
