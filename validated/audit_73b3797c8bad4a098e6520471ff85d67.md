### Title
Webhook signature verification checks `repository.owner.login` while the stack lookup and `GithubSyncJob` act on `repository.full_name`, letting one org's (secret-less) verification authorize state changes on another org's stacks - (File: app/controllers/shipit/webhooks_controller.rb, app/models/shipit/webhooks/handlers/handler.rb, app/jobs/shipit/github_sync_job.rb)

### Summary
`WebhooksController#verify_signature` authenticates a webhook using `Shipit.github(organization: repository_owner)` where `repository_owner` is read from `params.dig('repository','owner','login')`, but the handler that actually resolves the target `Stack` (`Shipit::Webhooks::Handlers::Handler#repository_name`) reads a completely independent field, `payload.dig('repository','full_name')`. Because nothing enforces `repository.owner.login`'s prefix matches `repository.full_name`'s owner segment, and because a secret-less org's `verify_webhook_signature` always returns `true` (`lib/shipit/github_app.rb:76-77`), an attacker can forge a payload that "verifies" against a configured secret-less org while acting on a `Stack` belonging to a different (even unknown) org.

### Finding Description
The broken binding: the code implicitly assumes `params.dig('repository','owner','login') == owner_prefix_of(params.dig('repository','full_name'))`, but nothing checks or enforces this equality.

- `verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-49`) computes `repository_owner` from `repository.owner.login` and calls `Shipit.github(organization: repository_owner).verify_webhook_signature(...)`. If that org has `webhook_secret` unset, `GitHubApp#verify_webhook_signature` returns `true` unconditionally (`lib/shipit/github_app.rb:76-77`), regardless of the request body content.
- After verification, `WebhooksController#create` dispatches to handlers with the raw parsed `params` (`app/controllers/shipit/webhooks_controller.rb:10-15`).
- `Handler#stacks`/`#repository_name` (`app/models/shipit/webhooks/handlers/handler.rb:32-38`) looks up `Repository.from_github_repo_name(payload.dig('repository','full_name'))` — a completely separate field from the one used for signature verification.
- `PushHandler#process` (`app/models/shipit/webhooks/handlers/push_handler.rb:12-17`) calls `stack.sync_github(...)` for each matching stack, enqueuing `GithubSyncJob`.
- `GithubSyncJob#perform` → `fetch_missing_commits` → `stack.github_api`, which internally calls `Shipit.github(organization: stack's actual owner)`. If that owner was removed from `Shipit.github_apps`, `Shipit.github` raises `GithubOrganizationUnknown` (`lib/shipit.rb:170-181`), caught in `handle_github_errors` (`app/jobs/shipit/github_sync_job.rb:80-89`), which calls `stack.mark_as_inaccessible!`.

Attacker request: POST `/webhooks` with `X-Github-Event: push`, body:
```json
{
  "ref": "refs/heads/master",
  "after": "deadbeef",
  "repository": {
    "owner": {"login": "secretless-org"},
    "full_name": "removed-org/some-repo"
  }
}
```
No `X-Hub-Signature` needed since `secretless-org` has no `webhook_secret`. `verify_signature` passes trivially. `PushHandler` then resolves `Repository.from_github_repo_name("removed-org/some-repo")`, finds the persisted `Stack`, and enqueues `GithubSyncJob`, which ultimately calls `stack.mark_as_inaccessible!` — a write on a stack that was never authenticated by the org that "verified" the request.

Existing guards do not close this: `drop_unhandled_event`, `check_if_ping`, and `ExplicitParameters` schemas (`PushHandler` only requires `:ref` and `:after`) do not validate the owner/full_name relationship; `verify_signature` never re-checks `full_name`'s owner against the org it authenticated.

### Impact Explanation
The attacker forces `Shipit::Stack#mark_as_inaccessible!` to run against a stack whose owning organization never authenticated the request — a state mutation on a party (the removed-org repository/stack) whose credentials were not exercised in the verification step, satisfying the "payload for one repository mutating another's stack" criterion. It is repeatable against any persisted stack whose organization has since been dropped from `Shipit.github_apps`, as long as at least one secret-less org remains configured. The blast radius is limited to stacks in this specific state (previously configured org, later removed) and to the `mark_as_inaccessible!`/`mark_as_accessible!` toggle plus whatever side effects that has (e.g., UI banners, deploy blocking) — it does not achieve RCE, credential exfiltration, or an unauthorized deploy/merge/rollback by itself.

### Likelihood Explanation
Requires: (1) at least one github org configured with no `webhook_secret` (a supported, documented configuration per `docs/setup.md`), and (2) an existing `Stack`/`Repository` row for an organization no longer present in `Shipit.github_apps` (an operational/config-drift precondition, not something the attacker can create from scratch). Given those preconditions, exploitation costs a single unauthenticated HTTP POST with no secrets required. Without a stale/orphaned stack in the database, the attack has no target — `GithubOrganizationUnknown` only fires for orgs unknown to the current config, and stacks are typically only created for orgs that were configured at creation time via `CreateOnGithubJob`.

### Recommendation
In `WebhooksController#verify_signature`, or in `Shipit::Webhooks::Handlers::Handler`, enforce that the organization used to verify the webhook matches the organization embedded in `repository.full_name` (and any other repository identifiers used downstream) before dispatching to handlers — e.g., derive `repository_owner` from `full_name`'s owner segment instead of (or in addition to, with equality check against) `repository.owner.login`.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb
test "secret-less org verification does not authorize actions on another org's stack" do
  # Configure `secretless-org` with no webhook_secret (default test config already secret-less for :shopify)
  stack = shipit_stacks(:shipit) # persisted for a different owner, e.g. "removed-org/cyclonus"
  request.headers['X-Github-Event'] = 'push'

  payload = {
    ref: 'refs/heads/master',
    after: 'deadbeef',
    repository: {
      owner: { login: 'shopify' },              # secret-less org, verifies trivially
      full_name: stack.repository.github_repo_name # different org's repository
    }
  }.to_json

  assert_enqueued_with(job: GithubSyncJob, args: [stack_id: stack.id, expected_head_sha: 'deadbeef']) do
    post :create, body: payload, as: :json
  end
  assert_response :ok
end
```
Combined with the existing `test/jobs/github_sync_job_test.rb` test "if the GitHub organization is unknown, the stack is marked as inaccessible and a warning is logged" (lines 162-168), this demonstrates the full chain: a webhook "verified" under one org's (secret-less) credentials results in `mark_as_inaccessible!` being called on a stack belonging to a different, unrelated organization.
```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
