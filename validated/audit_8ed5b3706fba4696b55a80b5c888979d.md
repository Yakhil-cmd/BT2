### Title
Receipts can exceed `max_receipt_size` after validation via post-validation mutation (`output_data_receivers`/large return values) - ([File: core/primitives/src/receipt.rs, runtime/runtime/src/verifier.rs])

### Summary
An unprivileged attacker can craft a contract that generates a receipt sized right at `max_receipt_size`, which passes `validate_receipt`, but is subsequently mutated (e.g. `output_data_receivers` appended, or a large returned value wrapped into a `DataReceipt`) after the size check, producing a receipt whose encoded (borsh) size exceeds the protocol's enforced `max_receipt_size` limit. This is a known, already-tracked bug (nearcore issue #12606) with workaround clamping present throughout the congestion-control code, but the root cause — size validation happening before, not after, receipt mutation — is not fixed.

### Finding Description
`validate_receipt` in `runtime/runtime/src/verifier.rs` computes `borsh::object_length(receipt)` and rejects receipts above `limit_config.max_receipt_size` only in `ValidateReceiptMode::NewReceipt` mode: [1](#0-0) 

The bug is that some code paths add extra data (`output_data_receivers`, promise return values converted into `DataReceipt`) to an already-validated receipt after this check has run, which is exactly what the existing `test-loop-tests/src/tests/max_receipt_size.rs::test_max_receipt_size_promise_return` and `test_max_receipt_size_value_return` tests demonstrate: a receipt is built to be exactly `max_receipt_size` in size, passes validation, and then `output_data_receivers` is populated afterward, pushing the final serialized receipt above the limit. [2](#0-1) 

The rest of the codebase is aware of this and explicitly documents the bug with tracking-issue references and defensive clamping in multiple places, rather than fixing the root cause:
- `ValidateReceiptMode::ExistingReceipt` mode exists specifically to tolerate previously created over-limit receipts: [3](#0-2) 
- `try_forward` in congestion control clamps oversized receipts to `max_receipt_size` to avoid receipts getting permanently stuck in the outgoing buffer: [4](#0-3) 
- Bandwidth request generation applies the same clamp for the same reason: [5](#0-4) 

`compute_receipt_size`/`receipt_size` (used for `CongestionInfo` accounting) compute the real borsh size, so oversized receipts are accounted with their true (over-limit) size in `receipt_bytes`, meaning congestion accounting sees a value above the protocol's own configured maximum: [6](#0-5) 

### Impact Explanation
This breaks the invariant "receipt encoded size is bounded by `max_receipt_size` and charged accordingly." An oversized receipt can propagate through the delayed/outgoing receipt queues and into `ChunkStateWitness`, undermining the size limits that were specifically introduced to bound `ChunkStateWitness` to ~17MiB (per `docs/misc/state_witness_size_limits.md`), and it distorts congestion-control byte accounting used for allowed-shard/backpressure decisions. This matches "greatly increasing the computational cost of the network" via oversized witnesses / degraded congestion control rather than a direct fund-loss primitive. The maintainers have already rated this significant enough to add multiple defensive workarounds but have not fixed the root cause.

### Likelihood Explanation
Fully reachable by an ordinary account: deploy a contract, call methods that build a receipt near `max_receipt_size` and then trigger a promise return or large returned value, exactly as reproduced in the existing tests `test_max_receipt_size_promise_return` and `test_max_receipt_size_value_return` in `test-loop-tests/src/tests/max_receipt_size.rs`. No special privileges, protocol-version gating bypass, or race conditions are required; it is deterministic and repeatable.

### Recommendation
Perform the `max_receipt_size` validation after all receipt fields are finalized (i.e., after `output_data_receivers`/return-value wrapping), or re-validate the final receipt size immediately before it is queued/buffered/committed to state, rather than only at receipt-creation time before later mutation. Remove the compensating clamps in `try_forward` and bandwidth request generation once the root cause is fixed, since they exist purely as workarounds for the size-limit bug tracked in https://github.com/near/nearcore/issues/12606.

### Proof of Concept
Existing repository tests already reproduce this exactly:
- `test-loop-tests/src/tests/max_receipt_size.rs::test_max_receipt_size_promise_return` — builds a promise DAG so the last receipt is at `max_receipt_size`, then `output_data_receivers` is appended, producing an oversized receipt; asserted via `assert_oversized_receipt_occurred`.
- `test-loop-tests/src/tests/max_receipt_size.rs::test_max_receipt_size_value_return` — returns a value of size `max_receipt_size`, wrapped into a `DataReceipt`, exceeding the limit; same assertion helper. [7](#0-6) 

For the requested fast-validation path (`runtime/runtime/src/tests/apply.rs`), add a test that: deploys a contract generating an action receipt sized at `max_receipt_size` with a pending promise return, applies the chunk, and asserts (a) the balance checker passes, (b) the resulting receipt's `borsh::object_length` exceeds `apply_state.config.wasm_config.limit_config.max_receipt_size`, and (c) total gas charged does not scale with the actual oversized bytes (i.e., the attacker is not charged proportionally for the excess size), confirming underpriced/free execution for the oversized portion.
