### Title
Quadratic-complexity double-spend key lookup in payment input validation - (File: validation.js)

### Summary
`validatePaymentInputsAndOutputs()` in `validation.js` tracks every payment input's dedup key in `objValidationState.arrInputKeys` and checks for duplicates with `Array.prototype.indexOf` before pushing the new key, for every input of every payment message in a unit. Because this array is not scoped to a single message but is carried on `objValidationState` across the whole unit's message list, an attacker who posts one unit with many payment messages, each near the `MAX_INPUTS_PER_PAYMENT_MESSAGE` limit, can drive this check to O(N²) over the total input count in the unit — structurally the same bug class as CVE-2026-66046 (repeated linear scan over a growing list for each of N items during untrusted-document parsing).

### Finding Description
For each input, `validatePaymentInputsAndOutputs()` builds a `input_key` string and performs a linear scan of the entire `arrInputKeys` array so far before appending it, for all three input kinds: [1](#0-0) [2](#0-1) [3](#0-2) 

The same message also scans `arrOutputAddresses` with `indexOf` for every output: [4](#0-3) 

The per-message output/input counts are capped, but the cap is only enforced per payment message, not for the sum across all messages in a unit: [5](#0-4) [6](#0-5) 

A unit can contain up to `MAX_MESSAGES_PER_UNIT` (128) messages, and `objValidationState` (and its `arrInputKeys` array) is created once per unit and passed through validation of every message in that unit, so the array keeps growing as successive payment messages are validated. With up to 128 payment messages each carrying up to 128 inputs, the attacker can construct a unit with on the order of 16,384 inputs. Each of these performs an `indexOf` scan over the previously-accumulated keys, giving roughly N²/2 ≈ 1.3×10⁸ string comparisons purely for double-spend-key deduplication — all before any database I/O for that check. This directly mirrors the reported bug class: an O(N²) scan triggered by a single, well-formed, attacker-controlled document (here, a unit) that a validator must fully process.

### Impact Explanation
This is reachable by any unprivileged unit poster — no special privilege, hub role, or peer position is required; it is triggered purely by unit content that every full node must validate as part of normal DAG processing. The impact is a CPU-based denial of service during unit validation: a single crafted unit forces disproportionate CPU work on every validating node, which can slow down or stall processing of legitimate units on that node, i.e., degrade the network's ability to confirm new units in a timely manner. Because the cost is incurred synchronously inside validation logic (`validatePaymentInputsAndOutputs`), this can also create validation-latency asymmetries between nodes, though it does not by itself cause double-spending, consensus disagreement, or fund loss.

### Likelihood Explanation
Likelihood is high for causing measurable CPU load, but the practical severity is bounded: the maximum total inputs achievable via `MAX_MESSAGES_PER_UNIT` × `MAX_INPUTS_PER_PAYMENT_MESSAGE` (128 × 128 = 16,384) is much smaller than the "few megabytes" XML case in the original CVE, and other O(N) work (e.g., DB queries per input for `checkInputDoubleSpend`) already dominates cost per input, so the marginal quadratic overhead from `indexOf` is a secondary amplifier rather than the primary cost driver. This tempers the finding from a severe to a moderate DoS amplifier, contingent on how much of the total validation time is actually spent in this particular linear scan versus the surrounding I/O-bound checks — a point that would require profiling to fully confirm.

### Recommendation
Replace the `arrInputKeys`/`arrOutputAddresses` linear array scans with a hash-set (plain object or `Map`) keyed by the same dedup key, turning duplicate detection from O(N) into O(1) per input/output and eliminating the O(N²) growth pattern for large units with many payment messages.

### Proof of Concept
Construct a single unit with the maximum allowed messages (128), each a `payment` message with the maximum allowed inputs (128, e.g., `headers_commission`/`witnessing` type inputs which don't require existing spendable outputs to reference other units), each with a distinct `(asset, from_main_chain_index, address)` triple. Submitting this unit for validation causes `validatePaymentInputsAndOutputs()` to perform ~16,384 `indexOf` scans over a monotonically growing `arrInputKeys` array (up to ~1.3×10⁸ comparisons), inflating validation CPU time compared to a well-formed unit of similar byte size but fewer messages.
