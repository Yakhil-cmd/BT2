### Title
CCMenu API token scoped to one stack can read CI/deploy status of any stack - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::CCMenuController` authenticates requests with a bare `?token=` query parameter instead of the usual HTTP Basic auth, then checks only the generic `read:stack` permission before resolving the `stack` from the request path. Unlike every other controller inheriting from `Shipit::Api::BaseController`, it does not scope stack lookup to the token's own `stack_id`, so a token that was only ever meant to authorize reading one specific stack's CI status can be used to read the CI status of *any* stack in the installation.

### Finding Description
`Shipit::CCMenuUrlController#client` mints a per-user `ApiClient` scoped to a single stack and with only `read:stack` permission: [1](#0-0) 

That token is meant to authorize CCMenu polling of exactly the stack it was minted for — this is the binding: `token.stack_id == stack being read`.

`Shipit::Api::BaseController` normally enforces this binding for every other endpoint: it restricts the queryable `stacks` relation to the client's own `stack_id` when the client is stack-scoped, and `stack` is derived from that restricted relation: [2](#0-1) 

However, `Shipit::Api::CCMenuController` overrides `stack` to resolve directly from the global `Stack` table using the URL parameter, bypassing the scoped `stacks` relation entirely, and only checks that the client has *a* `read:stack` permission (not that it is authorized for *this* stack): [3](#0-2) 

Because `require_permission :read, :stack` only calls `ApiClient#check_permissions!`, which merely checks the permissions array and never compares `stack_id`: [4](#0-3) 

the equality `token.stack_id == stack_id_in_path` is never checked in this controller, even though it is checked everywhere else in the API (`BaseController#stacks`/`#stack`).

### Impact Explanation
Any holder of a legitimately-issued CCMenu token (scoped to a single stack they were permitted to view) can substitute an arbitrary `stack_id` in the CCMenu XML request path and read the deploy/rollback status, last deploy id, and timing information of any other stack in the Shipit instance — including stacks the token holder has no access to. This is an unauthenticated (relative to the target stack) read of stack state/deploy output, matching the "unauthenticated read of stack state, task streams or deploy output" High-impact category. It requires no privileged credential beyond a normal CCMenu URL that a low-privileged user can obtain for a stack they're already permitted to view.

### Likelihood Explanation
High. CCMenu URLs are routinely shared/embedded in CI dashboards and IDE plugins, so tokens are exposed outside of interactive sessions. Exploitation only requires editing the `stack_id` segment of an already-obtained CCMenu URL; no signature, secret, or additional authentication is needed since the flaw is the missing scope check in `CCMenuController#stack`.

### Recommendation
Make `CCMenuController#stack` use the same scoped resolution as `BaseController#stack` (i.e., `stacks.from_param!(params[:stack_id])`, honoring `current_api_client.stack_id`) instead of `Stack.from_param!(params[:stack_id])`, so a stack-scoped token can only ever resolve the stack it was issued for.

### Proof of Concept
1. As a legitimate user with access to `stack-A`, visit the "settings" page and fetch the CCMenu URL, e.g. `GET /repo/A/env/ccmenu` → `CCMenuUrlController#fetch` returns `.../api/ccmenu/repo/A/env?token=<T>`, where token `T` is an `ApiClient` with `stack_id = stack-A.id` and `permissions = ['read:stack']`. [5](#0-4) 
2. Request `.../api/ccmenu/repo/B/env?token=<T>` for an unrelated `stack-B` that the same token was never scoped to.
3. `authenticate_api_client` accepts `T` (valid signature, valid `read:stack` permission) and `stack` resolves `stack-B` directly via `Stack.from_param!`, bypassing the `stacks` scoping used elsewhere: [6](#0-5) 
4. The response renders `stack-B`'s latest deploy/rollback XML status, disclosing information the token was never authorized to access.
