### Title
Unhandled exception in device message decryption crashes the node process - ([File: device.js])

### Summary
`device.js`'s `decryptPackage()` throws an `Error` inside a `setTimeout` callback when a received device message's `encrypted_package.dh.recipient_ephemeral_pubkey` does not match any of the recipient's known keys. This throw happens asynchronously outside the normal try/catch call stack that invoked `decryptPackage`, so it becomes an uncaught exception. `network.js` installs a global `process.on('uncaughtException', ...)` handler that explicitly re-throws to crash the process (`throw err; // crash the process to avoid ending up in an inconsistent state`). This mirrors the CTDB bug class: a remote, low-privilege sender (any correspondent/paired device, or even any peer relaying through the hub) can supply a malformed/adversarial message field that the receiver fails to validate before acting on it, leading to a process crash (DoS), analogous to CVE-2026-58224's "insufficient integrity validation ... allows malformed packets ... to be processed without adequate bounds checking ... denial of service through process crashes."

### Finding Description
`decryptPackage()` in [1](#0-0)  checks the shape of `objEncryptedPackage.dh` fields but only validates that `recipient_ephemeral_pubkey` matches one of the receiver's known keys (temp, prev-temp, or permanent). If none matches, instead of calling back with an error synchronously, the code does:
```
setTimeout(function(){
    throw Error("message encrypted to unknown key, device "+my_device_address+...);
}, 100);
return null;
```
This is reachable from `handleJustsaying`'s `'hub/message'` case in [2](#0-1) , which is invoked whenever any device (paired or not, since only signature/hash of the outer envelope are checked, not correspondent status) delivers a message addressed to `getMyDeviceAddress()`. The outer envelope checks (hash, ECDSA signature) only prove the sender controls `objDeviceMessage.pubkey`; they do not constrain the `dh.recipient_ephemeral_pubkey` field inside `encrypted_package`, which is attacker-controlled and easily set to an arbitrary invalid base64 string.

Because the `throw` occurs inside a `setTimeout` callback, it executes on a fresh stack, outside of any caller's `try { ... } catch` block (note that `handleJustsaying`'s call site at [3](#0-2)  wraps only the synchronous portion of `decryptPackage` in try/catch — the delayed `throw` fires independently 100ms later). It therefore becomes an uncaught exception, which is handled by the global handler in [4](#0-3) , which unconditionally re-throws to crash the process ("crash the process to avoid ending up in an inconsistent state").

### Impact Explanation
Any remote counterparty capable of sending a device message to a node's device address (via a hub relay, or the `hub/deliver` path in [5](#0-4)  when the node is its own hub) can trigger a guaranteed process crash by sending one message with a bogus `dh.recipient_ephemeral_pubkey`. This is a full node-availability denial-of-service: the wallet/hub process terminates, halting AA processing, unit posting, and any hub services it provides for its own correspondent devices — until manually restarted. This satisfies "a network unable to confirm new units" / node-DoS style impact within the allowed categories (wallet and contract message handling).

### Likelihood Explanation
High. Triggering the crash requires no privileged access, no valid pairing (only that the receiver's device address is public/known, which it typically is since it's shared for pairing/correspondence), and no cryptographic breaking — the attacker crafts `encrypted_package.dh.recipient_ephemeral_pubkey` to be any pubkey-shaped base64 string that doesn't match the current or previous temp key or the permanent key. The `hub/message` code path performs hash and signature checks that only require the attacker to sign with their own permanent key (self-consistent, trivially satisfiable), then reaches `decryptPackage` unconditionally.

### Recommendation
- Do not `throw` inside the `setTimeout` in `decryptPackage()`; instead, emit a `nonfatal_error` event (the already-present but commented-out `eventBus.emit('nonfatal_error', ...)`) or simply log and return `null` without scheduling a delayed throw.
- Ensure any error signaled from `decryptPackage` is delivered synchronously (via return value / callback) so callers such as `handleJustsaying`'s `'hub/message'` handler can call `respondWithError` and drop the malformed message instead of the process crashing.
- Audit other `setTimeout(() => { throw ... })` patterns in the codebase for the same asynchronous-uncaught-exception issue.

### Proof of Concept
1. Node A is running with device address `D` and is reachable (registered on its hub or a `hub/deliver`-capable peer).
2. Attacker crafts an `objDeviceMessage`:
   - `to`: `D`
   - `pubkey`: attacker's own device pubkey `P`
   - `encrypted_package`: `{ iv, authtag, encrypted_message: <any base64>, dh: { sender_ephemeral_pubkey: <any valid-length base64>, recipient_ephemeral_pubkey: <any base64 string not equal to A's current/prev temp or permanent pubkey> } }`
   - `signature`: valid ECDSA signature over `objectHash.getDeviceMessageHashToSign(objDeviceMessage)` using the attacker's own private key for `P` (self-consistent — no need to compromise A's keys).
3. Attacker sends this via `hub/deliver` (if A is a hub) or has A's hub relay it as `hub/message`.
4. `handleJustsaying('hub/message', ...)` on A passes hash/signature checks (self-consistent), then calls `decryptPackage(objDeviceMessage.encrypted_package)`.
5. Inside `decryptPackage`, none of the three key comparisons match, so the `else` branch runs `setTimeout(() => { throw Error(...) }, 100)`.
6. 100ms later, the thrown error escapes as an uncaught exception; `network.js`'s global handler re-throws, crashing node A's process.
