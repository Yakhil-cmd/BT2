## Analysis

I confirmed the multi-org webhook flow in this engine:

- `WebhooksController#verify_signature` selects which GitHub App/secret to verify against using **`repository_owner`**, taken from `params.dig('repository', 'owner', 'login')` (falling back to `params.dig('organization', 'login')`), and looks it up via `Shipit.github(organization: repository_owner)`. [1](#0-0) [2](#0-1) 
- Each per-org `GitHubApp` is configured with its own independent `webhook_secret` under the `github.<org>` key, exactly as documented for "Using Multiple GitHub Applications". [3](#0-2) [4](#0-3) 
- `verify_webhook_signature` HMACs the **entire raw request body** against the secret picked using that single `repository.owner.login` field. [5](#0-4) 
- However, once signature verification passes, the actual event handlers locate the target `Stack`/`Repository` using a **different field of the same payload**: `repository.full_name`, in `Handler#repository_name`/`Handler#stacks`. [6](#0-5) 
- `PushHandler` and `StatusHandler` (and other handlers) operate on whatever `stacks`/`Commit` records the payload happens to name, with no re-check that `repository.owner.login` (used to select the signing secret) matches the owner embedded in `repository.full_name` (used to select the stack to mutate). [7](#0-6) [8](#0-7) 

Real GitHub webhooks always keep `repository.owner.login` and `repository.full_name` consistent, but nothing in this engine enforces that invariant on the attacker-controlled JSON body it receives.

### Title
Webhook Signature Verified Against Attacker-Controlled `repository.owner.login` While Handlers Act on a Different `repository.full_name` — Cross-Organization Forged Webhook - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` picks the HMAC secret to validate an inbound webhook using `repository.owner.login` (or `organization.login`) taken directly from the unverified JSON body. Once the signature check passes, downstream `Webhooks::Handlers` (e.g. `PushHandler`, `StatusHandler`) resolve which `Stack`/`Repository`/`Commit` to mutate using a *different* field of the same body: `repository.full_name`. In a multi-GitHub-App Shipit deployment (a documented, supported configuration), an attacker who legitimately controls one onboarded GitHub organization's app/webhook secret can forge a webhook whose `repository.owner.login`/`organization.login` names their own org (so the signature check passes using the secret they know) while `repository.full_name` names a completely different organization/repository whose Shipit stacks they have no access to. The check that authenticates the sender (their own org) is never bound to the object that is written (a victim org's stack).

### Finding Description
This is the direct structural analog of the reported `executeMigration()` bug: a privileged action executes on the strength of one condition/field (`votesForMigration`/`migrationTime` in the report; here, "this signature belongs to organization X") while the actual state mutation acts on unrelated, unchecked data (arbitrary transfer destination in the report; here, an arbitrary `repository.full_name`/stack in Shipit).

- Verification binds trust to `repository_owner` = `params.dig('repository','owner','login') || params.dig('organization','login')`. [2](#0-1) 
- The signature is a raw-body HMAC (`OpenSSL::HMAC.hexdigest('sha1', webhook_secret, message)`), so it only proves the payload was signed *by whichever secret was selected* — it says nothing about which repository fields inside the payload are truthful, since the attacker who owns that secret can put any content they want in the body, including a `repository.full_name` for a repo/org they don't own. [5](#0-4) 
- Handlers never re-derive or cross-check the owner used for signing against the owner embedded in `full_name`; they simply trust `full_name` to find `Repository`/`Stack` records to act on. [6](#0-5) 

### Impact Explanation
Handlers driven by `full_name`/`sha` can mutate victim stacks the attacker's own org has no rights to:
- `PushHandler` triggers `stack.sync_github(expected_head_sha:)` for any stack matching the forged branch, which is used to advance the "last known commit" state that downstream continuous-delivery/merge logic relies on (`Stack#trigger_continuous_delivery`, `Stack#schedule_merges`). [7](#0-6) [9](#0-8) 
- `StatusHandler` writes arbitrary CI status (`state`, `context`) onto any `Commit` matching a forged `sha`, which directly feeds `Commit#deployable?`/blocking logic and `MergeRequest#all_status_checks_passed?`, both gatekeeping deploys and PR auto-merges. [8](#0-7) [10](#0-9) [11](#0-10) 

Forging a passing status on a stack with `merge_queue_enabled` and `continuous_deployment` set can push `ProcessMergeRequestsJob`/`ContinuousDeliveryJob` into merging or deploying commits that were never actually vetted by CI — an unauthorized ship condition, meeting the "unauthorized deploy" bar in the rules.

### Likelihood Explanation
Requires only: (1) the target Shipit instance uses the documented "Multiple GitHub Applications" configuration (explicitly supported/documented), and (2) the attacker legitimately controls at least one onboarded GitHub organization/app (i.e., is a member/owner of any org that has installed the Shipit GitHub App and knows or can view its own `webhook_secret`, which is standard for any org admin who set up the integration). No access to the victim organization, its GitHub App, or Shipit sessions is required — only the ability to send an arbitrary HTTP POST to the public `/webhooks` endpoint with a self-crafted body and a valid signature computed from a secret the attacker already possesses for their own tenant.

### Recommendation
After signature verification, re-validate that the resolved GitHub App organization equals the owner embedded in every `repository.full_name` (and any other repository identifiers) actually used by the handlers, rejecting the webhook (422) on mismatch. Alternatively, only trust `repository.owner.login` (the field used for verification) to resolve the repository, deriving `full_name` server-side from `owner.login` + `name` rather than trusting the payload's independent `full_name` string.

### Proof of Concept
```
# Setup: multi-org secrets.yml
# github:
#   attacker-org: { webhook_secret: "known_to_attacker", ... }
#   victim-org:   { webhook_secret: "not_known_to_attacker", ... }

payload = {
  "ref" => "refs/heads/master",
  "after" => "<victim commit sha>",
  "repository" => {
    "owner" => { "login" => "attacker-org" },   # used to pick verification secret
    "full_name" => "victim-org/victim-repo"     # used by PushHandler to select stacks
  }
}.to_json

signature = "sha1=" + OpenSSL::HMAC.hexdigest("sha1", "known_to_attacker", payload)

POST /webhooks
X-Github-Event: push
X-Hub-Signature: <signature>
body: payload

# verify_signature: repository_owner == "attacker-org" -> passes with attacker's own secret
# PushHandler#process -> stacks (Repository.from_github_repo_name("victim-org/victim-repo")) 
#   -> stack.sync_github(expected_head_sha: "<victim commit sha>") executed on victim's stack
```

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
