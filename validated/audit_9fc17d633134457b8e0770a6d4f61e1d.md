### Title
Webhook signature verification is bound to `repository.owner.login`, but every event handler acts on unrelated fields (`repository.full_name`, or raw `sha` with no repository scoping at all) - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects which GitHub App config/secret to verify the HMAC signature against using `repository_owner`, a value taken straight from the untrusted JSON body (`repository.owner.login`, or `organization.login` as fallback). Once the signature check passes, `create` dispatches the *same raw payload* to handlers that determine which `Stack`/`Commit` to mutate using a **different** field — `repository.full_name` (most handlers) or, in the worst case, no repository field at all (`StatusHandler`, which looks up commits globally by `sha`). Nothing enforces that the org used to authenticate the signature is the org whose data actually gets written.

### Finding Description
`verify_signature` in [1](#0-0)  does:

```ruby
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
```

where `repository_owner` is: [2](#0-1) 

`Shipit.github(organization:)` resolves a per-organization GitHub App config in the documented multi-organization deployment schema (see `TOP_LEVEL_GH_KEYS`, `github_app_config`, and the shipped example `test/dummy/config/secrets_double_github_app.yml`) [3](#0-2) . Each organization can have its own, independently-configured `webhook_secret` — including `nil` (unset), which is an explicitly supported and documented value (`webhook_secret: # nil` in the multi-org secrets fixture). When `webhook_secret` is blank, `verify_webhook_signature` short-circuits to `true` for *any* payload: [4](#0-3) 

So the entire signature check is keyed off an attacker-controlled JSON field (`repository.owner.login`) that selects *which* secret is used, while the request `create` action then dispatches the raw, unconstrained payload to handlers: [5](#0-4) 

Handlers resolve the target `Stack`/`Repository` using `repository.full_name`, a completely independent field from `repository.owner.login`: [6](#0-5) [7](#0-6) 

`StatusHandler` is the most exposed: it doesn't even use the repository field, only `sha`, and queries **all commits across all stacks** in the Shipit instance: [8](#0-7) [9](#0-8) 

This breaks the intended binding: **organization authenticated (via `repository.owner.login`) ≠ repository/commit actually written (via `repository.full_name` / raw `sha`)**. An attacker who controls or knows the webhook secret of *any one* configured organization on the instance (or any org whose `webhook_secret` is unset) can forge a signed payload naming that org as `repository.owner.login`/`organization.login`, while setting `repository.full_name` or `sha` to point at a completely different organization's repository/commit that is also hosted on the same Shipit instance.

### Impact Explanation
Forged commit statuses directly influence deploy automation: `Commit#deployable?` gates on `success?` derived from `Status::Group` built from `statuses`/`check_runs` [10](#0-9) , and a status transition also triggers `stack.schedule_merges` and `ContinuousDeliveryJob` for continuous-deployment-enabled stacks [11](#0-10) . An attacker who authenticates as an unrelated, low-trust org (or an org with no `webhook_secret` configured) can inject a fake "success" status onto a commit belonging to a victim stack that has continuous deployment enabled, causing an **unauthorized deploy**. For `push`/`pull_request` handlers, the same owner/full_name mismatch allows triggering `sync_github`, archiving/unarchiving review stacks, etc. for repositories the forged organization has no relationship to. This satisfies the Critical "unauthorized deploy" impact category.

### Likelihood Explanation
Exploitability requires the Shipit deployment to use the multi-organization GitHub App config schema (explicitly documented and shipped as a fixture, `secrets_double_github_app.yml`) with at least one organization whose `webhook_secret` is unset, or knowledge/control of one organization's webhook secret (e.g., an attacker who is a legitimate admin of a small, low-trust org hosted on the same shared Shipit instance). Given multi-tenant Shipit instances that host many orgs/repos, having at least one org with a blank `webhook_secret` is a plausible operational misconfiguration the code explicitly tolerates (`return true unless webhook_secret`), and no additional cross-checking of `repository.owner.login` vs. `repository.full_name`/`sha`'s owning stack exists anywhere in the handler chain.

### Recommendation
- In `WebhooksController#verify_signature`, do not use an attacker-controlled field to select the verification secret without re-validating that the same field's organization matches the organization implied by every field the dispatched handler will act on (`repository.full_name`, `sha`'s owning stack, etc.).
- In `Shipit::Webhooks::Handlers::Handler` and `StatusHandler`, scope commit/status lookups to the repository/organization that was actually authenticated for this request (pass the verified organization through to handlers and filter `Commit.where(sha:)` by `stack.repository.owner == verified_organization`).
- Treat a blank/nil `webhook_secret` for any configured organization as a hard misconfiguration (fail closed) rather than bypassing signature verification.

### Proof of Concept
1. Configure a Shipit instance with two GitHub App organizations, `LowTrustOrg` (attacker-controlled, `webhook_secret` unset/nil) and `VictimOrg` (hosts a stack with `continuous_deployment` enabled), per the supported multi-org schema in `secrets_double_github_app.yml`.
2. Attacker crafts a `status` webhook POST to `/webhooks` with header `X-Github-Event: status`, no valid `X-Hub-Signature` needed since `LowTrustOrg`'s secret is nil:
```json
{
  "organization": { "login": "LowTrustOrg" },
  "sha": "<victim commit sha>",
  "state": "success",
  "context": "ci/forged",
  "created_at": "2026-09-01T00:00:00Z"
}
```
3. `verify_signature` resolves `Shipit.github(organization: 'LowTrustOrg')`, whose `webhook_secret` is nil, so `verify_webhook_signature` returns `true` unconditionally.
4. `Shipit::Webhooks::Handlers::StatusHandler#process` runs `Commit.where(sha: params.sha)` globally (no org/repo filter) and calls `create_status_from_github!`, writing a forged "success" status onto the victim's commit, potentially triggering `stack.schedule_merges` / `ContinuousDeliveryJob` for `VictimOrg`'s continuously-deployed stack — an unauthorized deploy triggered by an actor with no relationship to `VictimOrg`.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
