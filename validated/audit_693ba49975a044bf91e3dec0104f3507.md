### Title
Cross-stack Status forgery via unscoped `Commit.where(sha:)` lookup in `StatusHandler#process` — ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` resolves target commits purely by `sha`, with no check that the webhook's `repository`/organization actually corresponds to the `stack` that owns the matched `Commit` row. Because Shipit routinely tracks multiple `Stack` records for the same GitHub repository (production stacks, review stacks, other environments/branches), a real, validly-signed "status" webhook triggered by an attacker's own low-privilege activity (e.g. a PR/branch in a stack they control) can inject a `Status` row into a `Commit` belonging to a *different, unrelated* stack that happens to share the same commit sha, defeating `MergeRequest#reject_unless_mergeable!`/`any_status_checks_failed?` on that other stack.

### Finding Description
The broken binding, stated as an explicit equality that the code fails to enforce:

`webhook.repository.full_name == commit.stack.repository.full_name` must hold for every `Status` row created from a webhook, but `StatusHandler#process` never checks it: [1](#0-0) 

```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```

This iterates over **every** `Commit` row in the entire installation matching `sha`, across all stacks, and writes a `Status` for each one via `commit.create_status_from_github! -> statuses.replicate_from_github!(stack_id, github_status)`: [2](#0-1) 

The only gate before `process` runs is `verify_signature`, which validates the HMAC against the secret configured for `repository_owner` (derived from the payload's own `repository.owner.login`/`organization.login`): [3](#0-2) [4](#0-3) 

This proves the webhook truly originated from that org/App installation, but it says nothing about which `Stack`/`Commit` rows should be updated — that decision is made afterward solely by SHA equality. `Commit` belongs to exactly one `stack`, and Shipit legitimately creates multiple `Stack` rows referencing the *same* GitHub repository (e.g. distinct branches/environments, review stacks spawned per pull request) — each maintaining its own `Commit` rows, which will carry an identical `sha` whenever the same commit object is shared between them (e.g. a PR's head commit tracked by a review stack and also present as a `MergeRequest#head` on the target merge-queue stack). Because the sha match is the *only* criterion, a status event that is 100% legitimate for the attacker's own review stack/PR is silently replicated into `victim_stack`'s `Commit` row for that sha, and `MergeRequest#any_status_checks_failed?`/`all_status_checks_passed?` will read it as ground truth: [5](#0-4) 

`ProcessMergeRequestsJob` performs no additional attribution check when it later reads `head.statuses_and_check_runs` — it just re-queries the DB fresh: [6](#0-5) 

None of `verify_signature`, `drop_unhandled_event`, the `ExplicitParameters` schema on `StatusHandler` (which only validates the shape of the payload, not repo attribution), or any model validation on `Status`/`Commit` enforces stack/repository attribution — `Status.replicate_from_github!` blindly trusts the `stack_id` it's called with, which itself was derived only from the SHA match: [7](#0-6) 

### Impact Explanation
An attacker who can only open pull requests / control their own branch triggers a genuine, correctly-signed "status" webhook for a commit sha that is also tracked as a `MergeRequest#head` (or any commit) on an unrelated stack for the same repository. The forged `Status` row causes `reject_unless_mergeable!` to see fabricated CI state, letting `ProcessMergeRequestsJob` proceed to `merge!` a pull request whose real CI never ran — an unauthorized merge, matching the Critical category "a payload for one repository mutating another's stack, commit, task or team" / "an unauthorized deploy, rollback or merge." This is repeatable against any repository configured with more than one `Stack` (multiple environments/branches or review stacks), which is a common, supported Shipit configuration, not an edge case.

### Likelihood Explanation
Requires: (1) the target repository has ≥2 `Stack` rows sharing commit history (branches/environments/review stacks — a standard feature, not exotic config), (2) `victim_stack` has `merge_queue_enabled` with a pending `MergeRequest` whose `head` sha coincides with a commit reachable through the attacker's own webhook-triggering activity, and (3) the attacker's activity (PR, push to their own tracked branch) causes a real "status" event to be delivered by GitHub for that shared sha. No secrets, no signature forgery, and no SHA collision are needed — only that the same commit object is legitimately tracked by two stacks, which is exactly what review-stack/multi-branch setups produce.

### Recommendation
In `StatusHandler#process`, scope the `Commit` lookup by the repository identified in the webhook payload (`params.repository.full_name`) joined through `stack`, not by `sha` alone — e.g. `Commit.joins(:stack).where(sha: params.sha, shipit_stacks: { repo_owner: ..., repo_name: ... })`. Apply the same repository-scoping to `CheckSuiteHandler`/`PushHandler` if they share this pattern, and add a regression test asserting that a status webhook for repo A never mutates a `Commit` belonging to a `Stack` for repo B (or a sibling stack of the same repo with a different intended scope).

### Proof of Concept
```ruby
test "status webhook mutates a Commit belonging to an unrelated stack sharing the same sha" do
  victim_stack = shipit_stacks(:shipit) # merge_queue_enabled
  attacker_stack = shipit_stacks(:some_other_stack_same_repo_or_review_stack)

  shared_sha = "deadbeef" * 5
  victim_commit = victim_stack.commits.create!(sha: shared_sha, ...)
  merge_request = victim_stack.merge_requests.create!(head: victim_commit, merge_status: 'pending', ...)
  attacker_stack.commits.create!(sha: shared_sha, ...) # attacker's own PR/review-stack commit, same sha

  # attacker-controlled webhook, correctly signed for attacker_stack's own repo/org
  params = { sha: shared_sha, state: 'success', context: 'ci/attacker', branches: [{ name: 'attacker-branch' }] }
  Shipit::Webhooks::Handlers::StatusHandler.call(params)

  assert victim_commit.reload.statuses.exists?(context: 'ci/attacker'),
    "forged status was written onto victim_stack's commit though the webhook never authenticated victim_stack"

  merge_request.reload
  refute merge_request.reject_unless_mergeable!, "merge request incorrectly treated as passing CI via unrelated stack's status"
end
```

    def perform(stack)
      merge_requests = stack.merge_requests.to_be_merged.to_a
      merge_requests.each do |merge_request|
        merge_request.refresh!
        merge_request.reject_unless_mergeable!
        merge_request.cancel! if merge_request.closed?
        merge_request.revalidate! if merge_request.need_revalidation?
      end

      return false unless stack.allows_merges?

      merge_requests.select(&:pending?).each do |merge_request|
        merge_request.refresh!
        next unless merge_request.all_status_checks_passed?

        begin
          merge_request.merge!
        rescue MergeRequest::NotReady
          ProcessMergeRequestsJob.set(wait: 10.seconds).perform_later(stack)
          return false
        end
      end
    end
