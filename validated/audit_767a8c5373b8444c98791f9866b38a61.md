### Title
Stack-Scoped API Token Bypasses Stack Binding via CCMenu Endpoint - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
An `ApiClient` (API token) can be created scoped to a single `Stack` via `belongs_to :stack, optional: true` on `ApiClient`, and `Shipit::Api::BaseController#stacks`/`#stack` enforces that scoping for every other API endpoint. `CCMenuController`, however, overrides `#stack` to bypass this scoping entirely, breaking the binding between "the stack a token authorizes" and "the stack it touches."

### Finding Description
`ApiClient` records can optionally be bound to one stack: `belongs_to :stack, optional: true` [1](#0-0) . The intended enforcement of that binding lives in `Shipit::Api::BaseController`:

```ruby
def stacks
  @stacks ||= current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all
end

def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
``` [2](#0-1) 

Any controller that relies on this `stack` helper (e.g. the stacks/tasks/deploys/hooks controllers) is correctly limited to the token's bound stack. `CCMenuController`, however, defines its own `stack`, resolving directly from `Stack.from_param!(params[:stack_id])` without going through `stacks`:

```ruby
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end
``` [3](#0-2) 

The permission check `require_permission :read, :stack` [4](#0-3)  only verifies that the token has the `read:stack` permission string — it never checks *which* stack the token is authorized for. Since `stack` is resolved independently of `current_api_client.stack_id`, a token created scoped to Stack A (e.g. via the CCMenu URL generator at `app/controllers/shipit/ccmenu_url_controller.rb:15-18`, which creates a `read:stack`-only, single-stack `ApiClient`) can be replayed against `/api/stacks/:stack_id/ccmenu` for any other stack B, disclosing that stack's latest deploy/rollback status, activity, and build labels.

**Binding broken:** `ApiClient.stack_id` (the stack the token authorizes) ≠ the `stack` resolved and rendered by `CCMenuController#show` (the stack actually touched).

### Impact Explanation
This is an authorization escalation: a token intentionally minted to read the state of one specific stack (the common case, since `CCMenuUrlController` always creates a stack-scoped, `read:stack`-only client for CI-status-badge use cases) can read the deploy/rollback status of every other stack in the installation, including private/internal stacks the token holder was never granted visibility into. This matches the "escalation into ... unauthenticated read of stack state" impact category, since the stack-scoping is exactly the authorization boundary that is bypassed.

### Likelihood Explanation
Likelihood is high given how easy it is to trigger: any holder of a single stack-scoped CCMenu token (which are widely distributed, e.g. embedded in CI badge URLs or CCTray monitors) only needs to change the `stack_id` route segment of the request to `/api/stacks/*stack_id/ccmenu` to read other stacks' status. No additional secret or privilege is required beyond possessing one legitimately-scoped token.

### Recommendation
- Remove the `stack` override in `CCMenuController` and use the inherited, scoped `stacks.from_param!(params[:stack_id])` from `BaseController`, so the `current_api_client.stack_id` binding is enforced consistently across all API controllers.
- Add a regression test asserting that a token scoped to stack A receives `404`/`403` when requesting `/api/stacks/<stack-B>/ccmenu`.

### Proof of Concept
1. As an authenticated Shipit user, visit `/ccmenu/*stack_id` for Stack A. `CCMenuUrlController#client` creates (or reuses) an `ApiClient` with `permissions: %w[read:stack]` and `stack: StackA` [5](#0-4) , and returns `ccmenu_url` containing `?token=<StackA-scoped-token>`.
2. Take that token and issue: `GET /api/stacks/<StackB-full-name>/ccmenu?token=<StackA-scoped-token>`.
3. `CCMenuController#authenticate_api_client` authenticates the token successfully (`ApiClient.authenticate(params[:token])`) [6](#0-5) ; `require_permission :read, :stack` passes because the token has `read:stack` in its permission list, regardless of which stack it's bound to [7](#0-6) .
4. `CCMenuController#stack` resolves Stack B directly, bypassing the `current_api_client.stack_id` restriction [3](#0-2) , and `#show` renders Stack B's latest deploy/rollback status in the response [8](#0-7) .
