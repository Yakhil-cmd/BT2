### Title
Attacker-chosen `receiver` lets `flash_loan` pull principal+fee via `transfer_from` from any WASM contract holding allowance to the pool - (File: contracts/pool/src/ops/flash.rs)

### Summary
`Pool::flash_loan` accepts a caller-supplied `receiver` address and, after paying out principal and invoking the receiver callback, repays itself with `token::transfer_from(pool, receiver, pool, total_repayment)` — pulling tokens from an address chosen entirely by the initiator, exactly like the Lens `FeeFollowModule::processFollow(follower, …)` pattern. Any WASM contract that holds an outstanding allowance to the pool (which flash receivers must create to repay loans, or which any integrator contract may grant standingly) can be drained of the flash fee — and by repeated calls, of arbitrary amounts up to its allowance — by an unprivileged initiator.

### Finding Description
In `apply`, the pool transfers `amount` to `receiver`, calls `execute_flash_loan` on it, then `collect_repayment` checks `asset.allowance(receiver, pool) >= total_repayment` and executes `asset.transfer_from(pool, receiver, pool, &terms.total_repayment)` (`contracts/pool/src/ops/flash.rs:166-180`). `receiver` is an input parameter; `initiator.require_auth` (or equivalent) authorizes the initiator, never the receiver. The only constraint is `require_wasm_receiver(env, &receiver)` (line 49) — the victim must be a contract, not a wallet.

Unlike the LensHub case there is no upgradeable proxy admin; instead the reachable abuse is: any third-party contract that has granted the pool a token allowance — legit flash-loan receivers do this, and allowance entries persist on the token contract until spent/expired — can be named as `receiver`. Each call forces the pool to extract `amount + fee` from the victim's balance; the victim only received `amount`, so it loses `fee` per invocation. The attacker doesn't need the victim's callback to cooperate beyond not reverting: `invoke_receiver` (lines 150-162) merely calls `execute_flash_loan`; a permissive or no-op receiver implementation lets the call succeed.

Worse, the fee is `Bps::flash_loan_fee_on(amount)` and `amount` is attacker-chosen up to pool cash, so each iteration extracts a nontrivial slice; looping `flash_loan` drains the victim contract's tokens up to its approved allowance — theft of funds belonging to users of that contract.

### Impact Explanation
Theft of user funds: tokens held by any WASM contract with live allowance to the pool are extracted as flash-loan fees without that contract's consent, at a rate of `fee = amount * flashloan_fee / BPS_MAX` per call, repeatable until the victim's balance or allowance is exhausted. The stolen value is booked as protocol revenue (`book_fee`, lines 124-128), so it is split between the protocol and the attacker's ability to keep invoking — the victim bears 100% of the loss while the attacker pays nothing (principal is returned to the victim by the pool itself).

### Likelihood Explanation
Requires a victim contract that (a) implements `execute_flash_loan` without restricting `initiator`, and (b) holds a residual or standing allowance to the pool. Condition (b) is structurally encouraged: `collect_repayment` requires allowance ≥ principal+fee, so receiver implementations that approve the pool inside or before the callback — the natural integration pattern — satisfy it whenever the allowance has remaining TTL or was over-approved. (a) is also plausible: the callback signature includes `initiator`, but nothing in the pool enforces that receivers validate it. Conditional on such a contract existing, the attack is fully permissionless and repeatable — Medium likelihood / Medium severity.

### Recommendation
Apply the same rules as the original report:

1. Only pull `transfer_from` from an address that authorized this call — e.g., require `receiver.require_auth()` (the contract can authorize via its own invocation) or restrict repayment to the `initiator` who authed the entrypoint.
2. Prefer the measured-receipt pattern already used elsewhere (`payments::balance_delta_since`): after the callback, require the receiver (or initiator) to *push* `total_repayment` and check `balance(pool) == balance_after_repayment`, removing the standing-allowance dependency entirely. This also removes the per-receiver `approve` requirement, matching the report's "approve one contract" benefit.

### Proof of Concept
Given: `V` is a WASM flash-receiver contract holding user deposits of `WETH` and a `type-max`-style allowance to `Pool` (granted during prior legitimate flash loans), with an `execute_flash_loan` that does not revert on unknown initiators.

1. Attacker `A` calls `Pool::flash_loan(hub_asset, initiator=A, receiver=V, amount=K, data)` for market-maximum `K`.
2. Pool transfers `K` to `V` (line 60), invokes `V.execute_flash_loan(A, WETH, K, fee, pool, data)` (lines 150-162); `V` returns normally.
3. Pool executes `WETH.transfer_from(pool, V, pool, K + fee)` using `V`'s allowance (line 178) — succeeds without any auth from `V`.
4. Net effect: `V` loses `fee`; `book_fee` credits it as protocol revenue.
5. Repeat: each iteration costs `A` nothing (principal round-trips through `V`) and extracts another `fee`-sized slice, draining `V`'s balance up to its allowance. [1](#0-0) [2](#0-1)

pub(crate) fn apply(
    env: &Env,
    hub_asset: HubAssetKey,
    initiator: Address,
    receiver: Address,
    amount: i128,
    data: Bytes,
) -> i128 {
    let mut cache = prepare(env, hub_asset, amount);
    require_wasm_receiver(env, &receiver);

    let pool = env.current_contract_address();
    let asset = token::Client::new(env, &cache.params().asset_id);
    let terms = terms(
        env,
        amount,
        cache.params().flashloan_fee,
        asset.balance(&pool),
    );

    asset.transfer(&pool, &receiver, &amount);
    require_balance(env, &asset, &pool, terms.balance_after_payout);
    invoke_receiver(
        env, &cache, &receiver, initiator, amount, terms.fee, &pool, data,
    );

    require_balance(env, &asset, &pool, terms.balance_after_payout);
    collect_repayment(env, &asset, &pool, &receiver, &terms);

    finalize(env, &mut cache, terms.fee);
    terms.fee

/// Pulls principal + fee via `transfer_from` after verifying allowance.
fn collect_repayment(
    env: &Env,
    asset: &token::Client,
    pool: &Address,
    receiver: &Address,
    terms: &FlashTerms,
) {
    assert_with_error!(
        env,
        asset.allowance(receiver, pool) >= terms.total_repayment,
        FlashLoanError::InvalidFlashloanRepay
    );
    asset.transfer_from(pool, receiver, pool, &terms.total_repayment);
    require_balance(env, asset, pool, terms.balance_after_repayment);
}
