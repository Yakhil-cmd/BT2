### Title
Webhook signature verification authenticates the payload's `repository.owner.login`, but dispatch acts on the unbound `repository.full_name` field, enabling cross-organization webhook forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks which GitHub App / webhook secret to use for HMAC verification based on `repository.owner.login` (or `organization.login`) in the incoming JSON payload. Once the signature check passes, every webhook handler (`Shipit::Webhooks::Handlers::Handler#repository_name`, used by `PushHandler` and all `pull_request` handlers) instead resolves the target `Stack`/`Repository` from a *different*, unchecked field: `repository.full_name`. There is no code that verifies these two fields refer to the same organization. In a multi-organization Shipit deployment (explicitly supported, see `test/dummy/config/secrets_double_github_app.yml`), an attacker who legitimately controls one configured GitHub App/organization can sign a payload whose `owner.login` matches their own org (so their own valid secret is selected and verification succeeds) while `full_name` points at a victim org's repository, causing Shipit to sync/act on that victim repository.

### Finding Description
Verification path: [1](#0-0) 
```
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(...)
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [2](#0-1) 

`Shipit.github(organization:)` returns a `GithubApp` instance configured per-organization, each with its own independent `webhook_secret`: [3](#0-2) [4](#0-3) 

Multiple orgs with distinct secrets is a documented/supported configuration: [5](#0-4) 

However, once `verify_signature` passes, dispatch to a handler happens purely from `event`, and each handler resolves the target repository from an *entirely different* payload field: [6](#0-5) 
```
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
```

`PushHandler` then acts on stacks belonging to whatever `full_name` says, regardless of which org's secret validated the signature: [7](#0-6) 

**Binding broken**: `organization authenticated (repository.owner.login, used to select the webhook secret) == repository written (repository.full_name, used to select the Stack/Repository that is mutated)`. Before this analysis, these two payload fields are implicitly assumed identical (as in a genuine GitHub-originated webhook), but the code never enforces the equality. An attacker who legitimately administers their own GitHub App installation (and therefore possesses/knows their own org's valid `webhook_secret`) can decouple the two fields and forge a signed payload whose `owner.login` is their own org (to pass verification with their own secret) but whose `full_name` names a victim organization's repository.

### Impact Explanation
This breaks a repository-authorization boundary and results in a cross-repository/cross-organization write: the attacker can cause `GithubSyncJob`/`stack.sync_github(expected_head_sha:)` to run for a victim's `Stack`, forcing Shipit to sync an attacker-chosen commit SHA into the victim's commit history, and (since `pull_request` handlers use the identical `repository_name` resolution) can also forge `closed`, `labeled`, `opened`, etc. events against victim repositories/stacks — e.g., invoking merge-related logic on a victim stack's pull requests. Depending on continuous-delivery configuration, syncing an attacker-chosen SHA into a victim stack can lead to that SHA being deployed. This falls under the "Critical" bucket: cross-repository writes / unauthorized deploy or merge.

### Likelihood Explanation
Exploitation requires only that the Shipit deployment is configured with more than one GitHub App/organization (a supported, documented configuration pattern) and that the attacker legitimately controls one of those organizations/apps (their own `webhook_secret`, obtained without any privilege escalation against Shipit itself — they own their org's GitHub App config). No access to the victim's secret, session, or API token is needed; only knowledge of the victim's public repository `full_name`. This is a self-contained authentication/authorization design flaw in the engine, not merely a theoretical concern, given the explicit multi-org support in the codebase.

### Recommendation
After successfully verifying the webhook signature against the org selected via `repository_owner`, cross-check that every field used by handlers to select the target repository (`payload.dig('repository', 'full_name')`, and `organization.login` in membership events, etc.) is consistent with the organization whose secret validated the signature — e.g., assert that `repository.full_name.split('/').first == repository_owner` (case-insensitively) before dispatching to handlers, and reject (422) on mismatch.

### Proof of Concept
1. Configure Shipit with two GitHub Apps/orgs as in `test/dummy/config/secrets_double_github_app.yml` (`OrgOne`, `OrgTwo`), each with a distinct `webhook_secret`.
2. Attacker controls `OrgOne`'s GitHub App and therefore knows `OrgOne`'s `webhook_secret`.
3. Attacker crafts a `push` payload:
```json
{
  "repository": { "owner": { "login": "OrgOne" }, "full_name": "OrgTwo/victim-repo" },
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha-existing-in-victim-repo>"
}
```
4. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(OrgOne_webhook_secret, raw_body)>` and POSTs to `/webhooks` with `X-Github-Event: push`.
5. `verify_signature` computes `repository_owner == "OrgOne"`, loads `OrgOne`'s `GithubApp`, and the signature verifies successfully (attacker used the correct secret for `OrgOne`).
6. `Shipit::Webhooks.for_event('push')` invokes `PushHandler`, whose `repository_name` resolves to `"OrgTwo/victim-repo"` via `payload.dig('repository', 'full_name')`, locating and syncing the victim's `Stack` with the attacker-chosen `after` SHA — despite the request never being signed by `OrgTwo`'s webhook secret.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
