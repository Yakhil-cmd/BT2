### Title
Webhook signature verification is bypassed when `webhook_secret` is not configured, allowing unauthenticated writes into stack/commit state - ([File: lib/shipit/github_app.rb])

### Summary
`GithubApp#verify_webhook_signature` short-circuits to `true` whenever no `webhook_secret` is configured for the organization the payload claims to belong to, and `WebhooksController` uses an attacker-controlled field of the *unverified* JSON body (`repository.owner.login`) to select which organization's app/secret should even be consulted. This breaks the trust binding the report describes: "the organization that authenticated" (i.e., the org whose secret was supposed to validate the request) is not enforced to be equal to "the repository/state that gets written" by the handler, because the verification step can be defeated entirely for any configured org that has a blank secret.

### Finding Description
Signature verification is performed in a `before_action`: [1](#0-0) 

`repository_owner` — the value used to select *which* `GithubApp` (and thus which secret) is used for verification — is read straight out of the unauthenticated JSON body: [2](#0-1) 

The actual signature check is: [3](#0-2) 

`return true unless webhook_secret` means that for any organization configured in `github_apps` without a `webhook_secret` value, **every** payload claiming to belong to that org is treated as verified, regardless of its actual origin. Since `repository_owner` is attacker-supplied (it's just a JSON field in the raw POST body, read before any verification occurs), an unprivileged attacker can craft a request whose `repository.owner.login` matches an org that has no secret configured, and the controller will accept it as authentic and dispatch it to the handler pipeline (`Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`, `app/controllers/shipit/webhooks_controller.rb:12`).

From there, handlers act on a second, independently attacker-controlled field — `repository.full_name` — to decide which `Repository`/`Stack` state to mutate, e.g.: [4](#0-3) [5](#0-4) [6](#0-5) 

This is the analog of the APWine binding break: the check is performed against one field (`repository.owner.login`, used only to pick a possibly-secretless verifier), while the write is performed against a different, unauthenticated field (`repository.full_name`), so "the organization that authenticated" and "the repository that is written" are never actually tied together by the signature.

### Impact Explanation
If any configured GitHub App/organization lacks a `webhook_secret` (a state the code explicitly tolerates via `.presence` and the `return true unless webhook_secret` short-circuit in `lib/shipit/github_app.rb:50,77`), an unauthenticated attacker can forge arbitrary webhook events (`push`, `status`, `check_suite`, `pull_request`, `membership`, etc.) for *any* repository name of their choosing, as long as the JSON's `repository.owner.login` matches the secretless org. This allows forged `push`/`status` events to trigger `stack.sync_github`, fabricate commit statuses via `commit.create_status_from_github!`, or manipulate team/membership records — i.e., unauthorized writes to stack/commit state without any GitHub credential or Shipit session, matching the "High: unauthenticated read of stack state" / write-state-manipulation class of impact.

### Likelihood Explanation
Exploitability is entirely gated on whether an operator has left `webhook_secret` blank for an organization in their `github_apps` configuration. The code does not enforce a non-blank secret, so this is a plausible latent misconfiguration rather than a universal, always-exploitable bug. I was not able to confirm within the indexed context whether `config/routes.rb` or an initializer enforces presence of `webhook_secret` at boot; if such validation exists elsewhere it would reduce likelihood, but no such check was found in `lib/shipit/github_app.rb` or `lib/shipit.rb`.

### Recommendation
Fail closed instead of open: if `webhook_secret` is blank for a configured organization, `verify_webhook_signature` should reject the request (or the app should refuse to boot without a secret) rather than treating an absent secret as automatic success. Additionally, the organization used to select the verifying app should be re-validated to actually correspond to the repository being mutated by the handler (i.e., don't let `repository.owner.login` and `repository.full_name` diverge without being cross-checked against the org that owns the matched `Repository`/`Stack`).

### Proof of Concept
1. Operator configures two GitHub Apps in `github_apps`, where `org-a` has a valid `webhook_secret` but `org-b` has none (blank/omitted), per the optional-secret handling in `lib/shipit/github_app.rb:44-50`.
2. Attacker sends `POST /webhooks` with header `X-Github-Event: push`, no valid `X-Hub-Signature`, and body:
```json
{ "ref": "refs/heads/master", "after": "<attacker-chosen-sha>",
  "repository": { "owner": { "login": "org-b" }, "full_name": "org-a/private-repo" } }
```
3. `repository_owner` resolves to `org-b`; `Shipit.github(organization: "org-b")` returns the secretless app; `verify_webhook_signature` returns `true` unconditionally (`lib/shipit/github_app.rb:77`).
4. `PushHandler#process` resolves stacks via `repository.full_name` = `org-a/private-repo` (`app/models/shipit/webhooks/handlers/handler.rb:36-38`) and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")`, mutating state for a repository/org the attacker never authenticated against.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
