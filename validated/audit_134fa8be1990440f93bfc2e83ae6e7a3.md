### Title
`Api::CCMenuController#stack` bypasses `ApiClient#stack_id` scoping, allowing any valid API token to read any stack's build status - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::BaseController` enforces that a stack-scoped `ApiClient` (one with `stack_id` set) can only access the stack it was issued for, via the `stacks` helper. `Api::CCMenuController` overrides the `stack` accessor with its own private method that calls `Stack.from_param!(params[:stack_id])` directly, skipping that scoping check entirely, so a token minted for one stack can be replayed against `Api::CCMenuController#show` for any other stack.

### Finding Description
The intended binding, enforced elsewhere in the API, is:
`current_api_client.stack_id.nil? || current_api_client.stack_id == stack.id` (as implemented by `stacks`/`stack` in `BaseController`) [1](#0-0) .

`ApiClient` supports being scoped to a single stack via the optional `belongs_to :stack` association [2](#0-1) , and `BaseController#stacks` deliberately restricts the queryable set to `Stack.where(id: current_api_client.stack_id)` when `stack_id` is present [3](#0-2) .

`Api::CCMenuController`, however, defines its own private `stack` method that ignores `current_api_client` entirely and resolves the path segment against the full `Stack` table:
```ruby
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end
``` [4](#0-3) 

`require_permission :read, :stack` only checks the client's global `permissions` array (`check_permissions!`), not any relationship between the client and the specific stack in the URL [5](#0-4) . `ApiClient.authenticate` itself only verifies the signature and looks up the row by `id`; it performs no comparison against `params[:stack_id]` [6](#0-5) , and `CCMenuController#authenticate_api_client` calls it directly with `params[:token]` [7](#0-6) .

Attack: obtain (or legitimately possess) a valid CCMenu token for Stack A (e.g., from a publicly shared `ccmenu_url` badge). Send `GET /api/stacks/<owner>/<repo-B>/<branch-B>/ccmenu?token=<stack-A-token>`. `ApiClient.authenticate` succeeds (signature valid, row exists), `check_permissions!(:read, :stack)` passes (token has `read:stack`), and `stack` resolves Stack B from the path with no cross-check against the token's `stack_id`. The response renders Stack B's deploy/build status XML.

None of the existing guards prevent this: `verify_signature`/webhook checks are irrelevant here, `ExplicitParameters` isn't used on this action, and the only scoping mechanism (`BaseController#stacks`) is shadowed by `CCMenuController`'s private override.

### Impact Explanation
An attacker holding any valid `read:stack`-scoped API token can enumerate `lastBuildStatus`, `lastBuildLabel`, `activity`, lock status, and last deploy metadata for **any** stack in the installation, not just the one the token was issued for. This is a cross-tenant unauthenticated-relative-to-target read of stack state — matching the "High: escalation... unauthenticated read of stack state" category. It is fully repeatable per request against arbitrary `stack_id` path values and requires no privilege beyond possessing one valid token (which, per the scenario, may be trivially obtained from a publicly shared CCMenu badge URL belonging to an unrelated stack).

### Likelihood Explanation
Preconditions are minimal: the attacker needs one valid CCMenu-style token (readily obtainable since these URLs/tokens are designed to be embedded in public build-status badges) and the target's `stack_id` path (owner/repo/branch), which is itself typically public (repository name + branch). No knowledge of `Shipit.api_clients_secret` or any other secret is required. Cost is a single unauthenticated HTTP GET; the exploit is deterministic and repeatable against any stack.

### Recommendation
Remove the private `stack` override in `Api::CCMenuController` (or make it consistent with `BaseController#stack`), so requests go through the `stacks` helper that enforces `current_api_client.stack_id` scoping:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
This makes CCMenu access respect the same per-client stack binding already enforced for every other API endpoint.

### Proof of Concept
```ruby
# test/controllers/api/ccmenu_controller_test.rb (new test)
test "a token scoped to stack A cannot read stack B's ccmenu status" do
  stack_a = shipit_stacks(:shipit)
  stack_b = Stack.create!(repository: Repository.create!(owner: 'foo', name: 'bar'), branch: 'main')

  client_a = ApiClient.create!(
    creator: @user, name: 'scoped-a',
    permissions: %w[read:stack], stack: stack_a
  )

  # Binding under test: client_a.stack_id (== stack_a.id) must equal the stack
  # resolved from params[:stack_id] (stack_b.id) for the request to be authorized.
  assert_not_equal client_a.stack_id, stack_b.id

  get :show, params: { stack_id: stack_b.to_param, token: client_a.authentication_token }

  # Vulnerable behavior: request succeeds and leaks stack_b's data despite the
  # inequality above.
  assert_response :ok
  project = Hash.from_xml(response.body)['Projects']['Project']
  assert_equal stack_b.to_param, project['name']
end
```
This test decodes/uses `client_a`'s token (issued for `stack_a`) against `Api::CCMenuController#show` with `stack_b`'s `stack_id`, asserting the two stack identifiers are unequal beforehand and that the controller nonetheless returns Stack B's XML — demonstrating the missing binding in `app/controllers/shipit/api/ccmenu_controller.rb`.
