### Title
Global, unscoped `Commit.where(sha:)` lookup in `StatusHandler` lets a signature-verified webhook from *any* installed repository forge commit statuses on commits belonging to a *different* repository/stack - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` authenticates a webhook by resolving the GitHub App/organization from the payload's `repository.owner.login` and validating the HMAC signature with that organization's `webhook_secret`. That authentication only proves "this payload was sent by GitHub for org X." It does not bind the payload's `sha`/status fields to the repository that was authenticated. `StatusHandler#process`, however, looks up commits with `Commit.where(sha: params.sha)` - globally, across the entire Shipit installation, with no scoping to the authenticated repository/organization at all.

### Finding Description
`WebhooksController#verify_signature` derives `repository_owner` from the payload and calls `Shipit.github(organization: repository_owner)`, then verifies the signature using that org's `webhook_secret`: [1](#0-0) 

Shipit explicitly supports hosting multiple, independent GitHub organizations/apps from a single instance, each with its own `webhook_secret`: [2](#0-1) 

Once the signature check for *that org* passes, the controller dispatches the raw `params` (which still contains the full attacker/GitHub-controlled payload, including whatever `repository` object was sent) to every registered handler for the event, with no re-validation that the payload's repository matches the org used for signing: [3](#0-2) 

The base `Handler` class does define a `repository_name`/`stacks` helper that properly scopes to `Repository.from_github_repo_name(repository_name)`: [4](#0-3) 

`PushHandler` correctly uses this scoped `stacks` helper: [5](#0-4) 

But `StatusHandler` does **not** use `repository_name`/`stacks` at all. It resolves target commits purely by SHA, across the whole `commits` table (i.e., every stack, every repository, every organization managed by this Shipit instance): [6](#0-5) 

This breaks the trust binding: **"the organization that authenticated the webhook" ≠ "the repository/commit whose state is actually written."** A genuine, correctly-signed `status` webhook from Organization A (or any repository the app is installed on) whose payload carries a `sha` that happens to match a commit belonging to Organization B's stack will be applied to Organization B's commit, because `StatusHandler` never checks that the commit's `stack.github_repo_name`/owner matches the webhook's authenticated repository/organization.

### Impact Explanation
Commit status directly gates deploy eligibility and continuous delivery: `Commit#deployable?` requires `success?` (derived from `statuses`), and successful/pending status transitions trigger `stack.schedule_merges` and `ContinuousDeliveryJob` for the target stack: [7](#0-6) [8](#0-7) 

Because the status write is not scoped to the authenticated repository, an attacker who can trigger (or is a legitimate contributor able to send) a status event for one repository/org managed by this Shipit instance can inject fabricated "success" statuses onto commits in a completely different, unrelated repository/stack (identified only by a matching git SHA, which is public information easily obtainable via `git log`/GitHub API). This can flip `deployable?` to true and trigger continuous deployment/merge scheduling for a stack the attacker has no legitimate relationship to, i.e. an unauthorized deploy trigger - satisfying the Critical "unauthorized deploy" impact criterion.

### Likelihood Explanation
Exploitability depends on the attacker being able to produce a validly-signed `status` webhook for *some* repository hosted by the same Shipit instance while targeting a commit SHA belonging to a *different* repository/stack on that instance. This is realistic in the common Shipit deployment model, which explicitly documents hosting multiple organizations/repositories from a single instance sharing one Shipit database of `commits`/`stacks`. Any legitimate GitHub Status API caller for one onboarded repo (CI systems, GitHub Apps with status write access, or a user with commit-status write permission on any one managed repo) can supply an arbitrary `sha` in the payload; GitHub does not require that `sha` belong to the repository sending the webhook for Shipit's own signature check to pass, since Shipit's check is purely about the signing secret, not the payload's internal consistency.

### Recommendation
In `StatusHandler#process`, scope the lookup to commits belonging to the webhook's authenticated repository, mirroring the pattern in `PushHandler`/`Handler#stacks`, e.g. `stacks.find_each { |stack| stack.commits.where(sha: params.sha).each { |c| c.create_status_from_github!(params) } }`, instead of the unscoped `Commit.where(sha: params.sha)`.

### Proof of Concept
1. Shipit instance manages two organizations, `OrgA` and `OrgB`, each configured under `config/secrets.yml`'s multi-org `github` block with independent `webhook_secret`s, as documented in `docs/setup.md`.
2. Attacker has legitimate ability to send a GitHub `status` event for a repository in `OrgA` (e.g., via a CI integration with commit-status permissions on that one repo, or by controlling a GitHub App/service with status-write access there).
3. Attacker crafts a `status` webhook payload where `repository.owner.login = "OrgA"` (so `WebhooksController#verify_signature` selects and validates against `OrgA`'s webhook secret, which the attacker can legitimately produce) but sets `sha` to the current HEAD SHA of a commit tracked in an `OrgB` stack, with `state: "success"`.
4. `WebhooksController#verify_signature` passes because the signature is valid for `OrgA`.
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)`, finds the `OrgB` commit (since the lookup is global, not scoped to `OrgA`), and calls `commit.create_status_from_github!(params)`, writing a fabricated "success" status onto the `OrgB` commit.
6. If that commit was the tip of an `OrgB` stack with `continuous_deployment?` enabled and previously blocked only by pending/missing CI status, `Commit#deployable?` now returns true and `ContinuousDeliveryJob`/`stack.schedule_merges` fire, producing an unauthorized deploy on `OrgB`'s stack triggered entirely from `OrgA`'s webhook credentials.
