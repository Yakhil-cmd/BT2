### Title
Missing cross-transaction deduplication of Bitcoin lockup outpoints in `verify-l1-lockups` allows double-crediting of L1-locked sats - (File: stackslib/src/chainstate/stacks/boot/pox-5.clar)

### Summary
`verify-l1-lockups` in `pox-5.clar` only deduplicates Bitcoin lockup outpoints *within a single call* via a freshly-initialized `seen-outpoints` accumulator passed into the `fold` over `validate-l1-lockup`. There is no persistent, contract-level map recording outpoints that have already been credited across separate transactions/registrations, unlike the `used-signer-key-authorizations` map used in `pox-4.clar` to prevent authorization reuse. This mirrors the reported bug class: a single underlying locked resource (here, a Bitcoin UTXO) can be presented more than once to the same validating function to be credited multiple times, because the check for "already used" is not durable across calls.

### Finding Description
`verify-l1-lockups` builds its `seen-outpoints` list starting from `(list)` on every invocation: [1](#0-0) 

The per-output dedup check lives inside `validate-l1-lockup`, and only consults the `seen-outpoints` accumulated *during the current fold*: [2](#0-1) 

Because this accumulator is reset to `(list)` each time `verify-l1-lockups` is called (line 2013), nothing in the reviewed contract prevents an attacker/staker from calling the registration/bond function that invokes `verify-l1-lockups` a second time — either for a new `bond-index`, a different reward cycle, or a new registration — while supplying the exact same Bitcoin `{txid, output-index}` outpoint that was already credited in a prior call. Each call would independently pass merkle-proof, script-hash, and unlock-height checks (all of which validate the outpoint against the chain, not against prior contract state), and each would add the same `amount-sats` to a *new* `sum`, which then flows into `total-shares-staked-for-cycle` / `signer-shares-staked-for-cycle` / `staker-shares-staked-for-cycle` bookkeeping used elsewhere in the file (e.g., the un-stake path shown at lines 1900–1935).

I was not able to fully trace every call site of `verify-l1-lockups` (e.g., the top-level `register`/stack-registration function that supplies `bond-index` and invokes it) within the available search budget, so I cannot confirm with certainty whether an outer, persistent guard (such as a global "outpoint already registered" map) exists elsewhere in `pox-5.clar` outside the range I inspected. The dedup mechanism I found (`seen-outpoints`) is explicitly documented as being scoped to "every ... pair already credited **in this call**" (see comment at lines 2028–2029), which is the concrete root-cause evidence for the analog.

### Impact Explanation
If no outer persistent map exists, this would let an attacker credit the same BTC lockup sats into the sBTC-staking shares system multiple times without locking additional Bitcoin — i.e., "sats credited by an L1 proof that were never locked on Bitcoin" for the duplicated amount, and double-counting a commitment across reward cycles/signers. That would inflate `total-shares-staked-for-cycle` and a staker's own `staker-shares-staked-for-cycle`, giving disproportionate reward/voting weight relative to actual locked BTC — a Critical-class issue per the given impact bar (double-counting a commitment / unbacked crediting).

### Likelihood Explanation
Likelihood depends entirely on whether a persistent (non-reset) outpoint registry exists at the call sites that invoke `verify-l1-lockups`, which I could not confirm from the code paths retrieved. Given the explicit in-code comment scoping the dedup guarantee to "this call" only, and the absence (in everything I could search) of a `map-set`/`map-insert` keyed on outpoint outside the fold accumulator, there is a plausible gap, but this is not proven conclusively without inspecting the full registration/top-up entry points and any surrounding maps.

### Recommendation
Introduce a persistent map (e.g., `used-l1-outpoints { txid, output-index } -> bool`) that is checked and updated with `map-insert` (failing on duplicate) inside `validate-l1-lockup`, in addition to the per-call `seen-outpoints` list, so that a given Bitcoin outpoint can never be credited by more than one `verify-l1-lockups` invocation across the contract's lifetime — analogous to how `used-signer-key-authorizations` prevents reuse of a signer authorization in `pox-4.clar`.

### Proof of Concept
Not able to construct a concrete end-to-end PoC without confirming the exact outer entry point(s) that call `verify-l1-lockups` and whether they impose their own uniqueness constraint on `(txid, output-index)`. Conceptually: (1) staker locks BTC in a valid timelock output; (2) staker calls the pox-5 registration function once, presenting that output, and is credited `amount-sats`; (3) staker calls the same (or a related) registration function again — for a new `bond-index` or reward cycle — presenting the identical output; since `seen-outpoints` restarts empty, `validate-l1-lockup` re-validates and re-credits the same sats, doubling the staker's counted stake without any additional BTC being locked.
