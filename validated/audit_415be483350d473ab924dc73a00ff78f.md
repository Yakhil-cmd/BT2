### Title
Unsigned `stack-stx` burnchain op lets any Bitcoin funder force-lock a victim's STX by spoofing `PreStxOp::output` - (File: stackslib/src/chainstate/burn/operations/stack_stx.rs)

### Summary
`PreStxOp::parse_from_tx` derives the future `StackStxOp.sender` purely from the *address bytes* of the first Bitcoin output, with no proof that whoever crafts the transaction (or later spends the second output) controls the corresponding private key. Any unprivileged actor can therefore fund a `PreStxOp`/`StackStxOp` pair naming a victim's `StacksAddress` as `sender`, pass `verify-signer-key-sig` with a self-generated signer key (its message hash never includes the stacker/sender identity), and cause `process_stacking_ops` to run `stack-stx` "as" the victim, locking the victim's real STX balance without any Stacks or Bitcoin signature from the victim.

### Finding Description
The broken equality: **the principal that authorizes a `stack-stx` lock (via `run_contract_call`'s `sender` argument) must equal the principal whose private key signed/authorized the action.** Here, `sender == victim` while the actual authorizer/broadcaster is the attacker.

Code path:
1. `PreStxOp::parse_from_tx` builds `output` solely from `outputs.get(0)....address...try_into_stacks_address()` — a pure address-hash derivation, no signature check: [1](#0-0) 
2. `burnchain.rs`'s `classify_transaction` binds `sender = &pre_stack_stx.output` and feeds it into `StackStxOp::from_tx`, which just clones it into `StackStxOp.sender`: [2](#0-1) [3](#0-2) 
3. `StackStxOp::get_sender_txid` only enforces that the StackStxOp's input spends vout=1 of the PreStxOp — it never checks who signed vout=0's address: [4](#0-3) 
4. `process_stacking_ops` executes the `stack-stx` contract call directly `as &sender.clone().into()` — i.e., as the victim principal, with no Stacks-transaction signature verification at all (this is a burn-op, not a signed Stacks tx): [5](#0-4) 
5. Inside `pox-4.clar`'s `stack-stx`, the only cryptographic guard is `consume-signer-key-authorization`/`verify-signer-key-sig`, whose signed message hash covers only `{pox-addr, reward-cycle, topic, period, auth-id, max-amount}` — it never binds to the stacker/sender identity, so the attacker can pick and self-sign an arbitrary `signer-key` of their own choosing: [6](#0-5)  The only remaining checks are balance/state checks on `tx-sender` (i.e., the victim): [7](#0-6) 

Exploit flow: attacker funds a Bitcoin transaction whose first output's `Hash160` equals victim's Stacks address hash, and whose second output attacker controls; broadcasts `PreStxOp`. Attacker then spends vout=1 themselves, embedding `stacked_ustx`, `num_cycles`, a self-chosen `signer_key` and a self-generated `signer_sig` over that key's message hash, and broadcasts `StackStxOp`. `classify_transaction`/`process_stacking_ops` then execute `stack-stx` with `tx-sender = victim`, checking only `stx-get-balance victim >= stacked_ustx` and that victim is not already stacking/delegating — both of which are outside attacker's control but easily satisfiable against any funded, non-stacking victim.

No existing guard (`verify-not-prepare-phase`, `check-pox-lock-period`, `verify-signer-key-grant`, etc.) ties the signer-key authorization or the burn-op sender field back to a signature by the sender/stacker itself.

### Impact Explanation
The attacker cannot steal or permanently freeze the victim's STX (it unlocks automatically at `unlock-burn-height`, as with any legitimate `stack-stx`), and no rewards are diverted to the attacker (the `reward_addr`/PoX payout address is whatever the attacker's second Bitcoin output specifies, at the attacker's choosing — the attacker can, however, direct all PoX BTC rewards for the victim's locked STX to itself). This is: (a) temporary freezing of the victim's STX for `num_cycles` reward cycles, and (b) an unsigned stacking action, both explicitly listed as **High** severity. Repeatable against any funded, non-stacking Stacks address, at the cost of one Bitcoin `PreStxOp` + `StackStxOp` pair (dust amounts) per victim/cycle.

### Likelihood Explanation
Preconditions: victim must have a free (non-stacking, non-delegating) STX balance ≥ the amount attacker specifies, and be in the correct cycle timing window for `start-burn-ht`. No privileged access or victim cooperation is required — only knowledge of the victim's `StacksAddress` (public information) and normal Bitcoin funds to pay tx fees. Feasible and cheap; repeatable each cycle against different or the same victim as balances free up.

### Recommendation
Require that `StackStxOp` (and `TransferStxOp`/`DelegateStxOp`, which share the identical `pre_stx.output`-as-`sender` pattern) only designates as `sender` an address the *broadcaster* actually controls — e.g., require the PreStxOp's first output to be provably spent/signed by the same key that signs the follow-up op, or bind the pox-4/5 signer-key authorization message hash to the `sender` principal so a self-chosen signer key cannot authorize locking an unrelated address's balance.

### Proof of Concept
Rust integration test outline (extending `stackslib/src/chainstate/burn/operations/test/mod.rs` / `stackslib/src/chainstate/coordinator/tests.rs` patterns):
1. Create `victim` and `attacker` keypairs; ensure `victim` has a funded, unlocked STX balance and is not currently stacking.
2. Attacker crafts a `PreStxOp` whose Bitcoin output 0 address hash160 equals `victim`'s `StacksAddress` hash, funded entirely by attacker's UTXO; broadcast and mine it.
3. Attacker crafts a `StackStxOp` spending vout=1 of that PreStxOp, with `stacked_ustx`, `num_cycles`, a self-generated `signer_key`/`signer_sig` pair (attacker's own key, self-signed over the SIP-018 message hash), and a `reward_addr` attacker controls; broadcast and mine it.
4. Run the coordinator/chainstate processing (`process_stacking_ops`) and assert:
   - Before: `victim`'s STX balance is unlocked, `get-stacker-info victim` is `none`.
   - After: `get-stacker-info victim` is `some`, with `victim`'s STX now locked for `num_cycles`, even though `victim`'s private key never signed any Stacks or Bitcoin transaction — assert the STX lock event's `locked_address == victim` while all Bitcoin inputs/signatures across both transactions belong to `attacker`.

;; Generate a message hash for validating a signer key.
;; The message hash follows SIP018 for signing structured data. The structured data
;; is the tuple `{ pox-addr: { version, hashbytes }, reward-cycle, auth-id, max-amount }`.
;; The domain is `{ name: "pox-4-signer", version: "1.0.0", chain-id: chain-id }`.
(define-read-only (get-signer-key-message-hash (pox-addr { version: (buff 1), hashbytes: (buff 32) })
                                               (reward-cycle uint)
                                               (topic (string-ascii 14))
                                               (period uint)
                                               (max-amount uint)
                                               (auth-id uint))
  (sha256 (concat
    SIP018_MSG_PREFIX
    (concat
      (sha256 (unwrap-panic (to-consensus-buff? { name: "pox-4-signer", version: "1.0.0", chain-id: chain-id })))
      (sha256 (unwrap-panic
        (to-consensus-buff? {
          pox-addr: pox-addr,
          reward-cycle: reward-cycle,
          topic: topic,
          period: period,
          auth-id: auth-id,
          max-amount: max-amount,
        })))))))

;; Verify a signature from the signing key for this specific stacker.
;; See `get-signer-key-message-hash` for details on the message hash.
;;
;; Note that `reward-cycle` corresponds to the _current_ reward cycle,
;; when used with `stack-stx` and `stack-extend`. Both the reward cycle and
;; the lock period are inflexible, which means that the stacker must confirm their transaction
;; during the exact reward cycle and with the exact period that the signature or authorization was
;; generated for.
;; 
;; The `amount` field is checked to ensure it is not larger than `max-amount`, which is
;; a field in the authorization. `auth-id` is a random uint to prevent authorization
;; replays.
;;
;; This function does not verify the payload of the authorization. The caller of
;; this function must ensure that the payload (reward cycle, period, topic, and pox-addr)
;; are valid according to the caller function's requirements.
;;
;; When `signer-sig` is present, the public key is recovered from the signature
;; and compared to `signer-key`. If `signer-sig` is `none`, the function verifies that an authorization was previously
;; added for this key.
;; 
;; This function checks to ensure that the authorization hasn't been used yet, but it
;; does _not_ store the authorization as used. The function `consume-signer-key-authorization`
;; handles that, and this read-only function is exposed for client-side verification.
(define-read-only (verify-signer-key-sig (pox-addr { version: (buff 1), hashbytes: (buff 32) })
                                         (reward-cycle uint)
                                         (topic (string-ascii 14))
                                         (period uint)
                                         (signer-sig-opt (optional (buff 65)))
                                         (signer-key (buff 33))
                                         (amount uint)
                                         (max-amount uint)
                                         (auth-id uint))
  (begin
    ;; Validate that amount is less than or equal to `max-amount`
    (asserts! (>= max-amount amount) (err ERR_SIGNER_AUTH_AMOUNT_TOO_HIGH))
    (asserts! (is-none (map-get? used-signer-key-authorizations { signer-key: signer-key, reward-cycle: reward-cycle, topic: topic, period: period, pox-addr: pox-addr, auth-id: auth-id, max-amount: max-amount }))
              (err ERR_SIGNER_AUTH_USED))
    (match signer-sig-opt
      ;; `signer-sig` is present, verify the signature
      signer-sig (ok (asserts!
        (is-eq
          (unwrap! (secp256k1-recover?
            (get-signer-key-message-hash pox-addr reward-cycle topic period max-amount auth-id)
            signer-sig) (err ERR_INVALID_SIGNATURE_RECOVER))
          signer-key)
        (err ERR_INVALID_SIGNATURE_PUBKEY)))
      ;; `signer-sig` is not present, verify that an authorization was previously added for this key
      (ok (asserts! (default-to false (map-get? signer-key-authorizations
            { signer-key: signer-key, reward-cycle: reward-cycle, period: period, topic: topic, pox-addr: pox-addr, auth-id: auth-id, max-amount: max-amount }))
          (err ERR_NOT_ALLOWED)))
    ))
