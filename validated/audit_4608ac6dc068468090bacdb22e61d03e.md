## Finding: `remove-staker-from-bond-for-cycle` zeroes staker shares without settling rewards first — permanent loss of accrued sBTC bond rewards

### Title
Bond-cycle staker removal skips reward settlement before zeroing shares, permanently forfeiting accrued sBTC rewards - (File: `stackslib/src/chainstate/stacks/boot/pox-5.clar`)

### Summary
`pox-5.clar` documents an explicit invariant: `settle-staker-rewards` "MUST be called before any update to `staker-shares-staked-for-cycle`, because changes to that state will effect rewards calculations" [1](#0-0) . All sibling mutators of per-cycle staked shares honor this — `unstake-sats-from-bond-cycle` [2](#0-1) , `remove-staker-from-signer-for-cycle` [3](#0-2) , and `add-staker-to-signer-for-cycle` [4](#0-3)  all call `settle-rewards`/`settle-staker-rewards` before touching the shares maps. `remove-staker-from-bond-for-cycle`, however, mutates `total-shares-staked-for-cycle`, `signer-shares-staked-for-cycle`, and zeroes `staker-shares-staked-for-cycle` for the staker without calling `settle-staker-rewards` (or `settle-rewards`) at all [5](#0-4) .

### Finding Description
This is the same bug class as the Derby Yield Optimiser report: a function that recalculates a reward-per-unit value (`get-earned-staker-rewards` / `compute-earned-rewards`) reads a "shares" quantity that gets mutated by a sibling code path before the reward snapshot is taken, corrupting the reward accounting.

`compute-earned-rewards` computes:
`earned = pending + shares * (rpt_current - rpt_paid) / PRECISION` [6](#0-5) 

`settle-staker-rewards` is the only function that captures this `earned` value into `staker-unclaimed-rewards-for-cycle` and advances the staker's `rpt_paid` checkpoint (`staker-rewards-per-token-settled-for-cycle`) [7](#0-6) .

In `remove-staker-from-bond-for-cycle`, the staker's `staker-shares-staked-for-cycle` entry is set directly to `u0` without first invoking `settle-staker-rewards` [8](#0-7) . Because `staker-rewards-per-token-settled-for-cycle` is left stale (unchanged) after this, any subsequent call to `get-earned-staker-rewards`/`compute-earned-rewards` for that (staker, signer, cycle, bond-index) will compute `shares * (rpt_current - rpt_paid)` with `shares = 0`, permanently zeroing out the multiplicative term. Any reward that had accrued between the staker's last settlement and this removal call is silently discarded — the staker can never claim it via `claim-rewards` or `claim-staker-rewards-for-signer` [9](#0-8) [10](#0-9) .

### Impact Explanation
This is a permanent freezing/loss of already-earned sBTC bond rewards for the affected staker, with no way to recover the lost accrual once shares are zeroed and the settlement checkpoint is skipped. The contract's sBTC reserve/reward pool remains implicitly over-collateralized (funds allocated to this staker's earned-but-unsettled reward are never paid out to anyone), which functionally matches the Critical/High bucket of "permanent freezing of ... sBTC rewards."

### Likelihood Explanation
I was not able to fully trace, within the available tool budget, every caller of `remove-staker-from-bond-cycles`/`remove-staker-from-bond-for-cycle` to confirm whether an outer wrapper always performs an equivalent settlement pass before invoking it (the way `register`/rollover flow does for `add-staker-to-bond-cycles` at lines 772–776). Given the pattern seen elsewhere in the file (dedicated settle-before-mutate calls placed directly adjacent to the shares mutation inside the same private function, e.g. `unstake-sats-from-bond-cycle`), the missing call inside `remove-staker-from-bond-for-cycle` itself is a strong structural signal of an intentional or accidental omission, but I could not conclusively rule out an external safeguard without reading the full call graph of every entry point that reaches this function.

### Recommendation
Add `(settle-rewards signer reward-cycle (some bond-index))` and `(settle-staker-rewards signer reward-cycle (some bond-index) staker)` at the start of `remove-staker-from-bond-for-cycle`, mirroring `unstake-sats-from-bond-cycle`, before any `map-set` to `total-shares-staked-for-cycle`, `signer-shares-staked-for-cycle`, or `staker-shares-staked-for-cycle`.

### Proof of Concept
1. Staker joins a protocol bond for `bond-index` at `reward-cycle` C with `amount-sats` shares (`add-staker-to-bond-for-cycle`), and `staker-rewards-per-token-settled-for-cycle` is snapshotted at the signer's current rpt at join time.
2. Rewards accrue for several blocks/tenures via `calculate-bond-rewards`, increasing `rewards-per-token-for-cycle` for (C, bond-index) [11](#0-10) , without the staker calling `claim-rewards` yet.
3. The staker is removed from the bond for cycle C via a path that calls `remove-staker-from-bond-cycles` → `remove-staker-from-bond-for-cycle`, which zeroes `staker-shares-staked-for-cycle` for (staker, signer, C, bond-index) without calling `settle-staker-rewards` first.
4. The staker (or `claim-staker-rewards-for-signer` on their behalf) subsequently calls into `get-earned-staker-rewards`/`settle-staker-rewards`: since `shares` is now `0`, `earned = pending + 0*(rpt_current - rpt_paid) = pending` — the reward accrued during step 2 is permanently unaccounted for and unclaimable, while `last-accounted-rewards-only`/reserve bookkeeping in `calculate-rewards` already counted it as distributed to this bond/cycle.
