### Title
Missing cosigner-authorization check allows any paired device to request signatures for a shared address it is not a member of - ([File: wallet.js])

### Summary
The GHSA-79m3 bug is a case where the read/access-control gate for a resource (a draft article) is not mirrored by the write/interaction gate (commenting), letting an unprivileged actor act on a resource it should not be able to touch. The closest reachable analog in ocore is in the `"sign"` case of `handleMessageFromHub` in `wallet.js`, which processes signing requests received from paired ("correspondent") devices over the hub. The code that would verify that the requesting device is actually a legitimate cosigner of the target address has been explicitly disabled, so any correspondent device can request a signature for any locally-owned address, regardless of whether it is actually part of that address's multisig/cosigning definition.

### Finding Description
`handleMessageFromHub` dispatches the `"sign"` message subject, which is used for multisig and multilateral signing flows across devices [1](#0-0) . After validating the address/signing-path format and the presence of an unsigned unit, the handler calls `findAddress(body.address, body.signing_path, {...})`. In the `ifLocal` branch, the check that would confirm the sending device is actually a cosigner for that wallet/address has been commented out: [2](#0-1) 

The comment explicitly states the reason it was removed: *"the commented check would make multilateral signing impossible"* — i.e., the authorization check was intentionally disabled to support a legitimate use case, but this removed the only gate that ensured the request-to-sign came from an actual member of the address's cosigning set. As a result, `callbacks.ifOk()` is invoked and a `"signing_request"` event is emitted for **any** correspondent device that knows a valid local address and a syntactically valid signing path, not just genuine cosigners: [3](#0-2) 

This mirrors the Publify bug class: the "read" side (whether the requester is even allowed to know about / interact with this address's signing state) is not checked at all before the "write" side (triggering a real signing flow, private-payload validation, and a user-facing sign confirmation) proceeds.

### Impact Explanation
Because this code path is reachable by any device that is merely paired ("correspondent") with the victim's wallet — not necessarily an actual cosigner of the specific shared address in question — an attacker who has paired with the victim (e.g., via a bot or chat pairing) can:
- Enumerate/probe which addresses the victim's wallet considers local and matching signing paths (via the `ifUnknownAddress` / `ifLocal` / `ifRemote` outcomes), leaking information about the wallet's address structure.
- Submit crafted `unsigned_unit` payloads (including private payment payloads, which are separately validated for hash consistency but not for whether the submitter is authorized to initiate a spend) that get funneled into `eventBus.emit("signing_request", ...)`, triggering wallet UI signing confirmations for transactions the requesting device had no legitimate right to originate.
- If the address has cosigners across multiple devices and the confirmation UI on the receiving side does not clearly indicate that the request came from a non-member device, this materially increases the risk of the user unknowingly co-signing a transaction proposed by an unauthorized party (leading to loss of funds from a shared/multisig address).

The actual signing operation still requires the local device to hold keys and the user to approve via the `"signing_request"` UI event, which limits (but does not eliminate) the impact — it primarily enables spoofed signing requests / information disclosure about wallet addresses, and creates the entry point for user-confirmation phishing that can result in unauthorized co-signing of a shared address.

### Likelihood Explanation
Likelihood is Medium: it requires only that the attacker's device be an established correspondent (paired device) of the victim — a normal, low-friction interaction in this wallet protocol (any device that has exchanged a pairing code can become a correspondent, or in the "non-correspondent whitelist" flow, some subjects are even allowed without pairing). No cryptographic bypass is needed; the missing check is a straightforward logic gap that is trivially reachable by crafting a `"sign"` message with an arbitrary `address` that happens to be a locally-known address and a syntactically valid `signing_path`.

### Recommendation
Re-enable and properly implement the cosigner-authorization check that was commented out: before proceeding to `callbacks.ifOk()` / emitting `"signing_request"`, verify that `from_address` is actually listed as a cosigning device for `body.address` (e.g., via `wallet_signing_paths` / `shared_addresses` membership for the specific `signing_path`), rather than only checking that the address is locally known. If multilateral signing genuinely requires accepting requests from non-cosigner devices for certain use cases (e.g., dumb contracts), that policy should be scoped narrowly and explicitly, with clear UI disclosure of the requester's authorization status, rather than blanket-disabling the check for all local addresses.

### Proof of Concept
1. Attacker device pairs with the victim's wallet (or otherwise becomes a `correspondent_devices` entry).
2. Victim owns a shared/multisig address `A` with cosigning device `B` (attacker is not `B`).
3. Attacker sends a `hub/message` with `subject: "sign"`, `body: { address: A, signing_path: "r.0", unsigned_unit: {...crafted unit...} }`.
4. `wallet.js` `handleMessageFromHub` reaches the `"sign"` case, calls `findAddress(A, "r.0", ...)`; since `A` is a local address, `ifLocal` fires.
5. Because the cosigner-membership check is commented out at [4](#0-3) , `callbacks.ifOk()` runs and a `"signing_request"` event fires for the victim's wallet UI, even though the attacker device is not part of `A`'s definition — demonstrating the unauthorized read/interact bypass.
