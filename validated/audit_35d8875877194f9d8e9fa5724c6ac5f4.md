### Title
Missing request timeout in `repoExists` (and sibling extension HTTP calls) allows attacker-controlled host to hang `gh` indefinitely - (File: pkg/cmd/extension/http.go)

### Summary
`repoExists` in [1](#0-0)  builds a plain `http.Request` and calls `httpClient.Do(req)` with no `context.WithTimeout`/`context.WithDeadline` attached to the request and no per-call deadline override on the client. The same pattern (raw `http.NewRequest` + `httpClient.Do`, no context deadline) recurs in `downloadAsset` and `fetchCommitSHA` in the same file.

### Finding Description
`repoExists` is reachable from `gh extension install <owner/repo>` where `owner/repo` is fully attacker-chosen (an attacker publishes any repository/host reference that `ghrepo.Interface` can represent, subject to `ghinstance`/`safeurl` host validation, which restricts *which* host is contacted but does nothing to bound *how long* the response can take). The request is built directly via `http.NewRequest` and executed with `httpClient.Do(req)` [2](#0-1) , with no `req = req.WithContext(ctx)` call and no timeout configured on `httpClient` at this call site.

The `httpClient` passed into `repoExists` originates from `api.NewHTTPClient` / `ghAPI.NewHTTPClient` (the `go-gh` library) [3](#0-2) . Within this repository there is no `Timeout:` field set on the resulting `http.Client`, and no per-request context deadline is applied in `pkg/cmd/extension/http.go`. Because Go's `http.Client.Timeout` defaults to `0` (no timeout) unless explicitly set, and `net/http`'s built-in transport timeouts (dial timeout, TLS handshake timeout) only bound connection setup — not a slow-loris style drip-fed response body or a server that holds the connection open while trickling bytes — a malicious or compromised host that a victim's `gh` is pointed at (e.g., via `GH_HOST`/enterprise host, or by controlling the responding server for a request that already passed host validation) can stall the response indefinitely. Since `resp.Body.Close()` is deferred until after `httpClient.Do` returns, and `Do` itself blocks until headers are received (or forever, if the attacker never finishes sending them), the calling goroutine hangs.

I could not fully verify from this index whether the underlying `go-gh` `ghAPI.NewHTTPClient` sets an internal timeout by default, since that library's source is external to this repository and not indexed here. This is a material gap: if `go-gh` internally sets `http.Client.Timeout`, the vulnerability as stated would not hold. Within the code visible in this repo, no such timeout is configured, and no context deadline is passed at the `pkg/cmd/extension/http.go` call sites.

### Impact Explanation
If confirmed (i.e., if `go-gh`'s client indeed has no timeout), this would allow a single attacker-controlled/attacker-influenced host to hang the invoking `gh extension install`/`gh extension upgrade` process indefinitely, causing unbounded resource consumption (a blocked goroutine/process) on the victim's machine, and in CI pipelines this could stall builds indefinitely (denial of service) until an external timeout (e.g., CI job timeout) intervenes.

### Likelihood Explanation
Reaching this code path only requires the victim to run `gh extension install`/`gh extension upgrade` against a repository/host the attacker controls or influences (e.g., a GitHub Enterprise host or a redirect target after host validation passes). No credentials, admin rights, or MITM are required — only that the attacker's server can hold open a TCP/TLS connection and delay finishing the HTTP response.

### Recommendation
Attach an explicit context deadline to every outbound request in `pkg/cmd/extension/http.go` (`repoExists`, `hasScript`, `downloadAsset`, `fetchLatestRelease`, `fetchReleaseFromTag`, `fetchCommitSHA`), e.g. `req = req.WithContext(ctx)` with a bounded `context.WithTimeout`, and/or explicitly set `http.Client.Timeout` on the clients constructed in `api.NewHTTPClient`/`api.NewExternalHTTPClient` rather than relying on library defaults.

### Proof of Concept
Plan for validation (cannot be executed from this read-only index):
1. Start an `httptest.Server` whose handler accepts the connection, writes partial/no headers, and sleeps (e.g., 30s+) before responding, simulating a slow-loris response.
2. Construct `httpClient` exactly as production code does (`api.NewHTTPClient` with default options, no custom `Timeout`).
3. Call `repoExists(httpClient, ghrepo.New("owner", "repo"))` pointed at the test server's host, wrapped with a test-level deadline (e.g., `time.AfterFunc` or run in a goroutine with `select` on a channel and `time.After(2*time.Second)`).
4. Assert that the call does NOT return within the expected bound (e.g., 2s), demonstrating the hang; then contrast with a fixed version where `req.WithContext(ctx)` is used with a `context.WithTimeout(ctx, 2*time.Second)`, asserting the call returns promptly with a context-deadline-exceeded error.

Note: this finding is contingent on confirming that `go-gh`'s `ghAPI.NewHTTPClient` does not itself set `http.Client.Timeout` — that library's internals were not available in this codebase's index, so this should be verified directly (e.g., via a Devin session with full dependency access) before treating this as fully confirmed.

func repoExists(httpClient *http.Client, repo ghrepo.Interface) (bool, error) {
	url, err := safeurl.JoinPathWithHostPrefix(ghinstance.RESTPrefix(repo.RepoHost()), "repos", repo.RepoOwner(), repo.RepoName())
	if err != nil {
		return false, err
	}

	req, err := http.NewRequest(http.MethodGet, url.String(), nil)
	if err != nil {
		return false, err
	}

	// TODO(api-client-rollout)
	// This has been deferred from moving to api.Client due to its exact-status contract and body-blind response handling.
	resp, err := httpClient.Do(req)
	if err != nil {
		return false, err
	}
	defer resp.Body.Close()

	switch resp.StatusCode {
	case http.StatusOK:
		return true, nil
	case http.StatusNotFound:
		return false, nil
	default:
		return false, api.HandleHTTPError(resp)
	}
}

func NewHTTPClient(opts HTTPClientOptions) (*http.Client, error) {
	// Provide invalid host, and token values so gh.HTTPClient will not automatically resolve them.
	// The real host and token are inserted at request time.
	clientOpts := ghAPI.ClientOptions{
		Host:               "none",
		AuthToken:          "none",
		LogIgnoreEnv:       true,
		SkipDefaultHeaders: opts.SkipDefaultHeaders,
	}

	debugEnabled, debugValue := utils.IsDebugEnabled()
	if strings.Contains(debugValue, "api") {
		opts.LogVerboseHTTP = true
	}

	if opts.LogVerboseHTTP || debugEnabled {
		clientOpts.Log = opts.Log
		clientOpts.LogColorize = opts.LogColorize
		clientOpts.LogVerboseHTTP = opts.LogVerboseHTTP
	}

	ua := fmt.Sprintf("GitHub CLI %s", opts.AppVersion)
	if opts.InvokingAgent != "" {
		ua = fmt.Sprintf("%s Agent/%s", ua, opts.InvokingAgent)
	}

	headers := map[string]string{
		userAgent:  ua,
		apiVersion: apiVersionValue,
	}
	clientOpts.Headers = headers

	if opts.EnableCache {
		clientOpts.EnableCache = opts.EnableCache
		clientOpts.CacheTTL = opts.CacheTTL
	}

	client, err := ghAPI.NewHTTPClient(clientOpts)
	if err != nil {
		return nil, err
	}

	if opts.Config != nil {
		client.Transport = AddAuthTokenHeader(client.Transport, opts.Config)
	}

	if opts.TelemetryDisabler != nil {
		client.Transport = telemetryDisablerTransport{
			wrappedTransport:  client.Transport,
			telemetryDisabler: opts.TelemetryDisabler,
		}
	}

	return client, nil
}
