### Title
`StatusHandler#process` applies GitHub `status` webhooks to commits by SHA alone with no repository scoping, unlike `ReleaseStatus`'s outbound writes - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`ReleaseStatus#create_status_on_github!` correctly scopes its outbound GitHub write to `stack.github_api`/`stack.github_repo_name`, but the inbound `status` webhook handler, `StatusHandler#process`, looks up commits by SHA alone across the entire `commits` table with no check that the payload's `repository.full_name` matches the owning stack's repository. This breaks a trust boundary that every other handler in the same base class enforces via `Handler#stacks`/`repository_name`, allowing a webhook signed for one repository (any repo within an organization Shipit has configured) to mutate the commit status of a completely unrelated stack whose commit happens to share the same SHA.

### Finding Description
The broken binding, stated as an equality that should hold but does not:
`payload.dig('repository','full_name') == commit.stack.github_repo_name` for every commit mutated by a `status` webhook.

- `Handler` base class provides `stacks`/`repository_name` helpers that scope lookups to `Repository.from_github_repo_name(repository_name)` [1](#0-0) , and `PushHandler` correctly uses this scoping to restrict which stacks it can touch [2](#0-1) .
- `StatusHandler#process`, by contrast, does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` - a global, unscoped lookup that never consults `payload['repository']` at all [3](#0-2) .
- Compare this to the outbound write path, `ReleaseStatus#create_status_on_github!`, which is correctly scoped through `stack.github_api` and `stack.github_repo_name` before writing to GitHub [4](#0-3) .
- `WebhooksController#verify_signature` only verifies the HMAC signature against the webhook secret configured for the payload's `repository.owner.login` (organization), not per-repository [5](#0-4) . A GitHub App/organization webhook secret is shared across every repository in that organization, so a legitimately-signed `status` event from any repository in the org (including a low-privilege public repo an outside contributor can trigger CI status on) passes signature verification.

Exploit flow: an unprivileged contributor with push/PR access to any low-security repository within the same GitHub organization as `victim/prod` triggers a CI system to post a `status` event for a commit SHA that is identical to a commit that also exists in `victim/prod`'s commit history (trivially achievable because Git commit hashes are content-addressed and identical across forks/shared history within an organization). This event is authentically signed by the org's webhook secret and passes `verify_signature`. `StatusHandler#process` then finds `victim/prod`'s `Commit` record purely by SHA and applies the forged status to it via `commit.create_status_from_github!`, which can flip the commit's deployable state and trigger `stack.schedule_merges` / `Hook.emit(:deployable_status, ...)` for a repository the forged payload never claimed to belong to [6](#0-5) .

None of the existing guards catch this: `verify_signature` validates organization-level authenticity, not repository identity; the `ExplicitParameters` schema for `StatusHandler` only requires `sha`/`state`/etc, with no `repository` binding enforced [7](#0-6) ; there is no analogous `stacks`/`repository_name` scoping call in `StatusHandler#process` as there is in `PushHandler`.

### Impact Explanation
A forged/replayed `status` webhook lets an attacker with only write access to an unrelated, co-located repository mutate the commit status of any stack/repository whose commit history shares a SHA with their own repo, regardless of which repository the payload nominally targets. This is a cross-tenant write: a payload attributable to one repository altering another repository's stack/commit state, matching the Critical impact category ("a payload for one repository mutating another's stack, commit, task or team"). It is repeatable against any stack sharing history/SHA with an attacker-reachable repository within the same GitHub organization, and downstream effects (auto-merge scheduling, deployable-status hooks) can influence deploy eligibility for the victim stack.

### Likelihood Explanation
Exploitation requires (a) the attacker to have push/PR access to some repository within the same GitHub organization as the victim stack (a low bar, e.g., an outside contributor to a public repo in that org) so that a legitimately-signed `status` event can be generated for a commit SHA of their choosing, and (b) a SHA collision with a commit belonging to the victim stack, which is realistically achievable via forks/shared history rather than requiring a hash break. No Shipit session, API token, or secret is needed. The likelihood is moderate-to-high in organizations with multiple repos/forks sharing a Shipit-managed GitHub App/webhook secret.

### Recommendation
Scope `StatusHandler#process` the same way `PushHandler` and other handlers are scoped: restrict the `Commit` lookup to commits whose `stack` belongs to `Repository.from_github_repo_name(payload.dig('repository','full_name'))` (i.e., use the existing `stacks` helper) before applying `create_status_from_github!`, so inbound status writes mirror the repository-scoping already enforced on outbound writes like `ReleaseStatus#create_status_on_github!`.

   - Create two stacks/repos, `victim/prod` (stack A, commit with `sha: 'deadbeef...'`) and `attacker/lowsec` (stack B, commit with the SAME `sha: 'deadbeef...'`) via fixtures.
   - Build a `status` payload with `repository.full_name = 'attacker/lowsec'`, `sha = 'deadbeef...'`, `state = 'success'`.
   - Assert (`StatusHandler#process`): `commitA.statuses.count` increases and `commitA.reload.state == 'success'` even though the payload's repository is `attacker/lowsec`, i.e. `payload['repository']['full_name'] != commitA.stack.github_repo_name` yet the write succeeded - demonstrating the missing binding.
2. Comparison assertion (`test/models/release_status_test.rb`, extending existing `release_statuses_test.rb`):
   - Stub `Shipit.github.api.expects(:create_status)` with the exact `stack.github_repo_name` argument for `ReleaseStatus#create_status_on_github!`, and assert it raises/fails a mock expectation if called with any other repo name - showing the outbound path IS correctly scoped (`stack.github_repo_name == 'shopify/shipit-engine'` required), contrasting with the inbound test in step 1 where no such equality is ever checked.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([

        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e

        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }

      end

      end
      new_status
