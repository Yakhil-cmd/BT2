### Title
Webhook signature verification is keyed by attacker-controlled `repository.owner.login`, allowing forged webhooks to mutate any victim repository's stack - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects the `GitHubApp` (and thus the HMAC secret) to validate a webhook against using `repository_owner`, a value read directly from the untrusted request body, not from the repository the payload actually targets. An attacker who controls any organization configured in `Shipit.github_apps` without a `webhook_secret` (or any organization not configured at all is rejected, but one configured with a blank secret is not) can send a completely unsigned `POST /webhooks` whose `repository.owner.login` claims to be their own org while `repository.full_name` names a different, victim repository, and the request will be accepted and dispatched to handlers that act on the victim's stack.

### Finding Description
The broken binding is: `webhook_secret.present?` for the organization used to verify **==** the organization the payload's `repository.full_name` actually belongs to and is being mutated for. This does not hold.

Trace:
- `verify_signature` computes the verifying app strictly from attacker-supplied JSON: `github_app = Shipit.github(organization: repository_owner)` where `repository_owner` is `params.dig('repository', 'owner', 'login')` [1](#0-0) [2](#0-1) .
- `Shipit.github(organization:)` looks up `github_app_config(organization)` in `Shipit.github_apps`/secrets and raises `GithubOrganizationUnknown` only if the org key is entirely absent; if it exists but has no `webhook_secret`, `GitHubApp.new` sets `@webhook_secret = @config[:webhook_secret].presence` which is `nil` [3](#0-2) [4](#0-3) .
- `verify_webhook_signature` then unconditionally returns `true` when `webhook_secret` is falsy, before ever inspecting the signature header or the body: `return true unless webhook_secret` [5](#0-4) .
- Once `verify_signature` passes, `create` parses the same attacker-controlled body and dispatches it to `Shipit::Webhooks.for_event(event)` handlers [6](#0-5) . Those handlers resolve the target `Stack`/`Repository` from `repository.full_name` in the same JSON body — a field wholly independent from, and never cross-checked against, the `repository.owner.login` used for authentication.

Root cause: the field used to select the verification secret (`repository.owner.login`) and the field used to select the record to mutate (`repository.full_name`) are both attacker-supplied and are never required to agree, and the verification path additionally has a bypass-by-default (`return true unless webhook_secret`) for any org lacking a configured secret. There is no check that `repository.full_name`'s owner matches `repository_owner`, and no check that the resolved `GitHubApp` actually owns the target stack's repository.

Attacker's exact request: an attacker who administers `AttackerOrg` (configured in `Shipit.github_apps` with no `webhook_secret`, e.g., because it's a newly onboarded/legacy org) sends:
```
POST /webhooks
X-Github-Event: push (or any handled event)
(no X-Hub-Signature, or an arbitrary bogus value)
{
  "repository": { "owner": {"login": "AttackerOrg"}, "full_name": "Victim/repo" },
  ... event-specific fields for Victim/repo ...
}
```
`verify_signature` resolves `GitHubApp` for `AttackerOrg`, finds no secret, returns `true`, and the event handler proceeds to update `Victim/repo`'s `Stack`/`Commit`/`Task` state using the forged payload.

None of the listed guards prevent this: `drop_unhandled_event` only filters unrecognized event types, not the repository binding; `ExplicitParameters` schemas (used by handlers) validate shape, not repository ownership; there's no `force_github_authentication`, `require_permission!`, or ownership cross-check anywhere on this unauthenticated endpoint.

### Impact Explanation
A payload authenticated (nominally) as belonging to `AttackerOrg` is used to mutate state belonging to `Victim/repo`, a different tenant's stack/commit/task records — this is exactly the "payload for one repository mutating another's stack, commit, task or team" Critical category, combined with an outright authentication bypass since no valid signature is ever required for organizations without a configured secret. This is repeatable indefinitely against any victim repository as long as at least one configured organization has an unset `webhook_secret`, and the blast radius spans every stack across every organization configured in the Shipit instance, since `repository.full_name` in the forged body can name any of them.

### Likelihood Explanation
Exploitability strictly depends on Shipit operator configuration: at least one organization entry in `Shipit.github_apps`/`secrets.github` must be present with a missing/blank `webhook_secret`. This is a plausible real-world misconfiguration (e.g., an org added without setting up the GitHub App webhook secret, or a config with a top-level default secret that isn't applied per-org). Given that precondition, the attacker's cost is a single unauthenticated HTTP POST — no credentials, no valid GitHub webhook delivery, no signature computation required.

### Recommendation
- In `verify_signature`, never treat an absent `webhook_secret` as "verified" for organizations that exist in config — either require `webhook_secret` to be present for every configured org and fail closed (`head(422)`) when it is missing, or restrict the "no secret" bypass to strictly the single-app legacy mode.
- Cross-validate that `repository.full_name`'s owner matches `repository_owner` before dispatching to handlers, and additionally verify that the resolved `Stack`/`Repository` for `repository.full_name` actually belongs to the `GitHubApp`/organization that produced a valid signature.

### Proof of Concept
Minitest plan (`test/controllers/webhooks_controller_test.rb`, no live GitHub, no WebMock):
1. Stub `Shipit.github_apps`/secrets so `Shipit.github(organization: 'attackerorg')` resolves a `GitHubApp` config with no `webhook_secret`, and separately create a real `Stack`/`Repository` for `Victim/repo` under a different, properly configured org.
2. Record `victim_stack.commits.count` and `victim_stack.updated_at` (or relevant `Commit`) before the request.
3. POST to `/webhooks` with header `X-Github-Event: push` and **no** `X-Hub-Signature` header (or a garbage value), with body:
   ```json
   { "repository": {"owner": {"login": "attackerorg"}, "full_name": "Victim/repo"}, "ref": "refs/heads/<victim-branch>", "after": "<forged-sha>", "commits": [...] }
   ```
4. Assert `response.status == 200` (not `422`), proving `verify_webhook_signature` bound to `AttackerOrg`'s nil secret returned `true` for a request naming `Victim/repo`.
5. Assert `victim_stack.commits.count` changed / a new `Shipit::Commit` row with sha `"<forged-sha>"` was created on `Victim/repo`'s stack, proving cross-tenant mutation with zero valid authentication — i.e., `webhook_secret.present?` for `AttackerOrg` (`false`) was substituted for actual validation of `Victim/repo`'s webhook, and the two sides of the binding (verifying org vs. mutated repository's org) diverged undetected.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
