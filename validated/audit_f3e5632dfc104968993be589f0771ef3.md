This confirms the issue: the benchmark for `remote_proxy` uses `create_remote_proxy_proof`, which builds a trie with exactly **one** key-value pair, producing a minimal proof (few nodes). The resulting benchmarked weight (`Weight::from_parts(18_259_000, 0)` in `system-parachains/asset-hubs/asset-hub-kusama/src/weights/pallet_remote_proxy.rs:56-64`) is a fixed constant that does not scale with `proof.len()`. There is no `ensure!`/bound check on `proof.len()` inside `do_remote_proxy`, and the `proof: RemoteProxyProof<...>` extrinsic argument itself is a plain `Vec<Vec<u8>>` bounded only by the runtime's generic max-extrinsic/block-length limit, not by pallet-specific weight-scaled limits.

### Title
Unbounded, unweighted `RelayChain` trie-proof size in `remote_proxy`/`remote_proxy_with_registered_proof` allows execution-time DoS - (File: pallets/remote-proxy/src/lib.rs)

### Summary
`Pallet::do_remote_proxy` builds a `MemoryDB` from an attacker-supplied `Vec<Vec<u8>>` proof and calls `sp_trie::read_trie_value` over it, with cost proportional to the number/size of proof nodes, but the declared extrinsic weight (`WeightInfoOf::<T, I>::remote_proxy()`) is a fixed constant benchmarked against a minimal single-entry trie proof and does not scale with `proof.len()`.

### Finding Description
In `pallets/remote-proxy/src/lib.rs:405-419`, the `RelayChain` proof variant is processed as: [1](#0-0) 
This constructs `sp_trie::StorageProof::new(proof).into_memory_db::<RemoteHasherOf<T, I>>()` and then calls `sp_trie::read_trie_value`, both of which do CPU work (hashing every supplied node, decoding/traversing nodes) proportional to the number and size of nodes in `proof`, regardless of whether they are on the actual path to the target key.

The dispatch weight for `remote_proxy` is declared as: [2](#0-1) 
`WeightInfoOf::<T, I>::remote_proxy()` resolves to a fixed benchmarked constant (e.g. `Weight::from_parts(18_259_000, 0)` plus one DB read) as seen in `system-parachains/asset-hubs/asset-hub-kusama/src/weights/pallet_remote_proxy.rs:56-64`. This constant was derived from the benchmark in `pallets/remote-proxy/src/benchmarking.rs:48-71`, which uses `T::RemoteProxy::create_remote_proxy_proof`, itself implemented in `relay/kusama/constants/src/lib.rs:236-266` (and the Polkadot analog) to build a trie containing exactly **one** proxy definition entry — producing a minimal-size proof of only a handful of nodes.

There is no check in `do_remote_proxy`, `remote_proxy`, or the pallet's `Config` that bounds `proof.len()`, the number of nodes, or scales the weight with the proof's actual size (unlike the `di.call_weight` addition for the inner call, which only accounts for the wrapped call, not the proof-processing work). The only implicit bound is the runtime's generic maximum extrinsic/block length, which is far larger than the minimal proof used for benchmarking. An unprivileged signed account can therefore submit a `remote_proxy` extrinsic with `proof` containing many large, structurally-valid-but-irrelevant trie nodes (e.g., padding nodes not on the path to the queried key, or many extension/branch nodes) up to the block length limit, while the declared weight remains the fixed constant from the one-node benchmark.

### Impact Explanation
Since a block's total weight budget is enforced using the declared (fixed) weight rather than actual execution time, a validator/collator executing such a transaction spends CPU time proportional to the (potentially very large) proof, well beyond what was budgeted for the block. Repeated across multiple transactions in a block (each individually within block weight limits per the *declared* weight, but not per actual execution time), this causes block execution time to significantly exceed the expected budget, contributing to a block-execution stall / slowdown, consistent with the scoped impact (this is a weight-accounting bug, not an asset-theft or origin-forgery bug).

### Likelihood Explanation
Feasibility is high and fully attacker-controlled: no privileged access is required, only a signed origin (`ensure_signed(origin)?`) and the ability to submit an extrinsic. The attacker can precompute a valid trie proof (they know their own path/key since `T::RemoteProxy::proxy_definition_storage_key` is derived from a known public key derivation and public relay-chain storage layout), and can pad the proof with additional valid-format nodes copied/crafted from the same or other tries, since `sp_trie::StorageProof`/`into_memory_db` does not require that every node reachable be exactly minimal — it accepts a `Vec<Vec<u8>>` of arbitrary nodes and only requires that the actual path nodes needed to resolve the target key be present and correctly hash-linked; additional unrelated nodes can be included without affecting the lookup's correctness for the *targeted key*, but they still get hashed/copied into the `MemoryDB`. This is fully repeatable — every call to `remote_proxy` can be crafted this way.

### Recommendation
Scale the extrinsic weight of `remote_proxy` / `remote_proxy_with_registered_proof` / `register_remote_proxy_proof` with `proof.len()` (total proof size in bytes and/or number of nodes), e.g., add a per-byte or per-node weight component benchmarked against worst-case node counts, and/or enforce a hard cap (`ensure!`) on the maximum number of nodes / total encoded proof size accepted, rejecting the extrinsic with `Error::InvalidProof` (or a new dedicated error) before calling `into_memory_db`/`read_trie_value` if the bound is exceeded.

### Proof of Concept
Rust benchmark/timing test in `pallets/remote-proxy/src/tests.rs`:
1. Build a `sp_trie::TrieDBMutBuilder` trie containing the target proxy-definition key/value plus a large number (e.g. 10k–100k) of additional unrelated key/value pairs sized to approach the runtime's max extrinsic length, producing a `StorageProof` via `sp_state_machine::prove_read` or manual `TrieDBMut` + `db.drain()` including extra nodes.
2. Call `RemoteProxy::remote_proxy(...)` with this maximal proof and measure wall-clock execution time of `Pallet::do_remote_proxy`.
3. Compare against the wall-clock execution time using the minimal single-entry proof (as used in benchmarking) and against the fixed weight-derived time bound (`WeightInfoOf::remote_proxy()` converted to nanoseconds via the runtime's `WeightToFee`/reference time constants).
4. Assert: `execution_time(large_proof) > execution_time(minimal_proof) * K` for some significant `K`, and `execution_time(large_proof) > weight_declared_time_budget`, demonstrating the fixed weight under-estimates actual cost as `proof.len()` grows.
