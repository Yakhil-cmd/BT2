### Title
Cross-organization webhook forgery via secret-selector/repository-actor mismatch - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to validate a signature against by reading `repository.owner.login` (or `organization.login`) straight out of the *unauthenticated* JSON body, then hands the same body to `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`. Handlers, however, resolve which `Stack`/`Repository` to act on using a *different* field from that same body: `payload.dig('repository', 'full_name')` in `Shipit::Webhooks::Handlers::Handler#repository_name`. [1](#0-0) [2](#0-1) 

### Finding Description
Shipit supports multiple GitHub App configurations keyed per-organization (`Shipit.github(organization:)` / `github_app_config`), each with its own `webhook_secret`, as documented by the multi-org secrets fixture. [3](#0-2) [4](#0-3) 

The signature check binds "the raw body is authentic" to "the org named in `repository.owner.login`/`organization.login`":
```
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
``` [5](#0-4) 

This only proves the payload was HMAC-signed with *that org's* secret — it does not bind the verified org to the repository the handler will subsequently act on. The handler layer independently trusts `repository.full_name` from the same payload to look up the target `Repository`/`Stack`:
```
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [2](#0-1) 

Because `repository.owner.login`/`organization.login` and `repository.full_name` are two independent, attacker-controlled fields inside the same JSON body, an operator of any org that is configured in Shipit (e.g. their own GitHub org "AttackerOrg" with its own `webhook_secret`) can:
1. Craft a JSON body with `organization.login`/`repository.owner.login = "AttackerOrg"` but `repository.full_name = "VictimOrg/private-repo"`.
2. Sign the raw body with `AttackerOrg`'s own legitimately known webhook secret.
3. `verify_signature` resolves `Shipit.github(organization: "AttackerOrg")` and successfully verifies the signature (it was genuinely signed with that secret).
4. `Webhooks.for_event(event).each { |handler| handler.call(params) }` then runs, e.g., `PushHandler`, which resolves `stacks` via `repository.full_name = "VictimOrg/private-repo"` — a stack that belongs to a completely different, unrelated organization. [6](#0-5) [7](#0-6) 

This is the same trust-binding class as the reported bug: a value that authenticates a request (here, the organization used to pick the HMAC secret) is not the same value that the code subsequently acts on (here, the repository whose stacks get mutated). The equality that should hold — `organization_that_signed == organization_owning_repository.full_name` — is never enforced; `verify_signature` only checks "was this signed by *some* configured org's secret", not "was this signed by the org that owns the repository named in the payload."

### Impact Explanation
`PushHandler#process` calls `stack.sync_github(expected_head_sha: params.after)` for every matching stack, and other handlers (`StatusHandler`, `CheckSuiteHandler`, `MembershipHandler`, pull-request handlers) similarly act using `full_name`-derived stacks/repositories. An attacker who controls their own onboarded organization's webhook secret in a multi-tenant Shipit deployment can forge events against any other organization's repositories tracked by that Shipit instance — triggering sync jobs, pull-request metadata mutation, team/membership changes, and status writes on stacks they do not own. This crosses the "cross-repository writes" boundary called out in scope.

### Likelihood Explanation
Requires a multi-org Shipit deployment (an explicitly supported and documented configuration — see the double-github-app fixture) and requires the attacker to control (or be an authorized member/webhook-configurer of) at least one of the configured organizations, which is a much weaker requirement than repository write access or a GitHub App private key on the *victim* org. No signature secret for the victim org is ever needed.

### Recommendation
After verifying the HMAC signature, cross-check that the resolved `github_app`'s organization actually matches the owner of `repository.full_name` (not just `repository.owner.login`), or better, verify the signature using the webhook secret associated with the *repository being acted upon* rather than a value read from the untrusted body before any authentication has occurred. Reject the payload if the two disagree.

### Proof of Concept
1. Configure Shipit with two orgs, `AttackerOrg` and `VictimOrg`, each with distinct `webhook_secret`s (as supported by `secrets.github.<org>.webhook_secret`).
2. `VictimOrg/private-repo` has a Stack tracked on branch `master`.
3. Attacker (who knows only `AttackerOrg`'s webhook secret) builds body:
```json
{"organization": {"login": "AttackerOrg"}, "repository": {"owner": {"login": "AttackerOrg"}, "full_name": "VictimOrg/private-repo"}, "ref": "refs/heads/master", "after": "<attacker-chosen sha>"}
```
4. Attacker computes `X-Hub-Signature: sha1=HMAC(AttackerOrg_webhook_secret, body)` and sends `POST /github/webhooks` with `X-Github-Event: push`.
5. `verify_signature` resolves `Shipit.github(organization: "AttackerOrg")`, verifies successfully.
6. `PushHandler.call(params)` resolves `Repository.from_github_repo_name("VictimOrg/private-repo")` and invokes `stack.sync_github(expected_head_sha: "<attacker-chosen sha>")` on the victim's stack, despite the attacker never possessing `VictimOrg`'s secret or repository access.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
