### Title
Uncaught exception / crash in `chash.isChashValid` via unvalidated case-insensitive address input - (File: chash.js)

### Summary
`chash.js` reconstructs a checksum-bearing binary string from a decoded address and asserts its bit-length equals exactly 160 or 288 bits before further processing. When that assertion fails, the code `throw`s instead of returning `false`, and the throw is not caught anywhere inside `isChashValid`. Any code path that reaches `isChashValid` with attacker-supplied bytes that decode to an unexpected length will crash with an uncaught exception, analogous to the LibTIFF bug where a buffer-length computed from an untrusted "shift"/bit-depth value did not match the allocated buffer, producing an out-of-bounds write / crash on a crafted input.

### Finding Description
`chash.isChashValid()` decodes an encoded address string (via `base32.decode()` for 32-char strings or `Buffer.from(x,'base64')` for 48-char strings), converts it to a bit string with `buffer2bin()`, and passes it to `separateIntoCleanDataAndChecksum()`: [1](#0-0) 

`separateIntoCleanDataAndChecksum` requires the bit-string length to be exactly 160 or 288, otherwise it throws: [2](#0-1) 

This throw happens **outside** the `try { ... } catch(e) { return false; }` block in `isChashValid` (that block only wraps the initial decode step), so a length mismatch propagates as an uncaught exception rather than a graceful `false` result: [3](#0-2) 

`validation_utils.js` exposes two entry points into this logic:
- `isValidAddress()` first enforces a strict `/^[A-Z2-7]{32}$/` regex (proper base32 alphabet, exact length) before calling `isChashValid`, which guarantees `base32.decode` yields exactly 20 bytes (160 bits) — safe. [4](#0-3) 
- `isValidAddressAnyCase()`, however, skips that character-class/regex guard entirely and calls `isValidChash` (and thus `chash.isChashValid`) directly on any 32-character string: [5](#0-4) 

Because `isValidAddressAnyCase` does not restrict the character set the way `isValidAddress` does, a string containing characters outside the strict base32 alphabet (e.g., lowercase letters or digits like `0/1/8/9`) can be passed to `base32.decode()`. Depending on how the `thirty-two` decoder treats such characters (padding/truncation/extra bits), the resulting buffer's bit length can end up different from 160/288, triggering the uncaught `throw` in `separateIntoCleanDataAndChecksum` and crashing whatever process called validation — this is the direct analog of the LibTIFF out-of-bounds write: a length derived from untrusted input is not validated for consistency with the buffer/format invariants the rest of the routine assumes, and the mismatch causes an unhandled fault deep in a helper function rather than a controlled error.

`isValidAddressAnyCase` is referenced once in `validation.js` in addition to its two definitions/exports in `validation_utils.js`; I was not able to confirm within the available exploration budget which specific field in unit/AA/message validation calls it, so I cannot cite the exact reachable field with certainty.

### Impact Explanation
If `isValidAddressAnyCase` is reachable from an attacker-controlled field in a posted unit, AA trigger, or similar untrusted input, a single crafted string can crash unit validation with an uncaught JS exception. Depending on where the call sits in the async control flow, this can crash the node process or leave a promise unhandled, matching the "network unable to confirm new units" outcome category (denial of service against validating nodes) rather than a memory corruption (JS has no true OOB write, but the effect — a crash from an untrusted length-derived value — is the direct analog to the LibTIFF bug).

### Likelihood Explanation
Likelihood is Medium: exploitation only requires constructing a 32-character string that is a syntactically-invalid-but-decodable base32 payload and getting it validated through the `isValidAddressAnyCase` path. The main uncertainty is confirming the exact call site in `validation.js` and how `thirty-two`'s decoder handles out-of-alphabet characters — both would need direct code confirmation (index limits prevented full tracing of this call site and the third-party `thirty-two` decoder internals).

### Recommendation
- Wrap the length checks in `separateIntoCleanDataAndChecksum` / `mixChecksumIntoCleanData` (and the outer call in `isChashValid`) in a full `try/catch` that returns `false` instead of throwing, so malformed input is rejected rather than crashing the caller.
- Add the same alphabet/length regex guard used in `isValidAddress` to `isValidAddressAnyCase` (or explicitly validate the decoded buffer length equals 20/36 bytes) before further processing.
- Audit `thirty-two`'s `decode()` behavior for out-of-alphabet or malformed input to ensure it always throws (never silently returns a wrong-length buffer).

### Proof of Concept
Conceptually:
```js
const chash = require('./chash.js');
// 32-char string containing characters outside standard base32 alphabet,
// exploiting the missing regex guard in isValidAddressAnyCase
chash.isChashValid('0000000000000000000000000000001'); // if base32.decode does not throw but returns a buffer whose bit length != 160, this throws uncaught inside isChashValid
```
Full confirmation requires validating `thirty-two`'s decode behavior on such strings and identifying the exact `validation.js` call site consuming `isValidAddressAnyCase`, which was not verifiable within the current investigation.
