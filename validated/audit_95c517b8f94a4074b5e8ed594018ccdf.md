### Title
Reachable `MATH_OVERFLOW` panic in `scaled_to_original` permanently freezes a high-utilization market — no repay, withdraw, or liquidation can execute - ([File: tests/test-harness/tests/controller/large_positions_and_long_horizons.rs](tests/test-harness/tests/controller/large_positions_and_long_horizons.rs))

### Summary
CVE-2017-17722 is a reachable assertion that crashes the parser on crafted input — the analog class here is a reachable arithmetic panic on an unprivileged, protocol-shaped input. In XOXNO Lending, RAY-scaled interest accrual can overflow `i128` inside `scaled_to_original` **before** the borrow-index cap `MAX_BORROW_INDEX_RAY` engages. Because every stateful verb (supply, borrow, withdraw, repay, liquidate, clean_bad_debt) accrues the market index first, once the index crosses the value-overflow boundary every subsequent call on that market reverts with `MATH_OVERFLOW`. The market is permanently bricked.

### Finding Description
`tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:316-361` demonstrates the flaw end-to-end: a whale-scale market (10^18-decimal asset, ~98% sustained utilization on the XLM rate curve) accrues until the next accrual panics inside `scaled_to_original` with `errors::MATH_OVERFLOW`. The test asserts `last.borrow_index < MAX_BORROW_INDEX_RAY`, i.e., the index cap that is supposed to bound accrual never triggers — the raw `index × scaled_amount` value multiplication overflows `i128` first, at roughly 170× index growth versus the ~170× headroom the cap was meant to preserve.

The same panic then hits every entrypoint because accrual runs before any business logic: the test verifies `try_withdraw_raw` and `try_repay` both revert with `MATH_OVERFLOW`, and liquidation takes the same path through `Context::cached_market_index` / `sum_debt_usd` (`contracts/controller/src/risk/totals.rs:48-60`).

An unprivileged address reaches this with ordinary calls: `supply` a large principal, `borrow` ~98% of it, then let `update_indexes` (permissionless) accrue. No privileged action, upgrade, or oracle dishonesty is required — only size and a steep-utilization curve.

### Impact Explanation
Permanent freezing of funds and protocol insolvency for the affected (hub, token) book: suppliers can never withdraw or be repaid out of that market, borrowers can never repay, liquidators cannot liquidate underwater accounts, and `clean_bad_debt`/`recapitalize` cannot run since they also accrue. Other books are unaffected, but the bricked book's entire TVL is frozen forever — the contract is unable to operate for that market.

### Likelihood Explanation
Medium. It requires a very large market (billion-unit scale at 18 decimals) sustained near the steep segment of the utilization curve for an extended accrual horizon (~years at 98% utilization per the test). Caps must be lifted far enough to admit that principal, which is a configuration precondition rather than a privileged exploit step. Once conditions exist, any unprivileged `update_indexes` call triggers the freeze; there is no recovery path since every recovery verb accrues first.

### Recommendation
Cap the borrow index growth before the value multiplication can overflow — enforce `MAX_BORROW_INDEX_RAY` (or a tighter bound derived from `i128::MAX / total_scaled_debt`) inside the accrual step so the cap actually engages, and/or saturate `scaled_to_original` results rather than panicking. Add a regression asserting the cap engages before the value ceiling for the maximum supported supply × index product.

### Proof of Concept
`tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:321-361`:
- Supplies `BILLION * 10^18` of `BIG18`, borrows 98%, advances time in yearly chunks calling `try_update_indexes_for(&["BIG18"])` until it returns `Err`.
- Asserts the error is `errors::MATH_OVERFLOW` and `last.borrow_index < MAX_BORROW_INDEX_RAY`.
- Then asserts `try_withdraw_raw(BOB, "BIG18", 1)` and `try_repay(ALICE, "BIG18", 1.0)` both fail with `MATH_OVERFLOW`, proving the market is permanently frozen.
