### Title
API token stack-scoping bypass in CCMenu endpoint - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::ApiClient` records can be scoped to a single `Stack` via the `stack_id` column, and `Api::BaseController` is designed to enforce that scoping for every API endpoint by routing all stack lookups through the `stacks` helper. `Api::CCMenuController` overrides the `stack` lookup method and bypasses that scoping, so a token that is only supposed to authorize reads for one stack can be used to read CI/build state for any stack in the installation.

### Finding Description
`Api::BaseController` defines the authorization-scoped lookup path used by every other API controller: [1](#0-0) 

`stacks` restricts the visible `Stack` set to `current_api_client.stack_id` when the authenticated `ApiClient` is scoped to one, and `stack` (used by `Api::StacksController`, `Api::TasksController`, etc.) always resolves through this scoped relation via `stacks.from_param!(...)`. The `require_permission` mechanism only checks that the client's `permissions` array contains the required string (e.g. `read:stack`) via `ApiClient#check_permissions!`: [2](#0-1) 

It performs no per-stack check on its own — the per-stack restriction is entirely implemented by the `stacks`/`stack` scoping in `BaseController`. `Api::CCMenuController` re-implements `stack` directly against the unscoped model: [3](#0-2) 

```ruby
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end
```

This calls `Stack.from_param!` directly instead of `stacks.from_param!`, entirely skipping the `current_api_client.stack_id?` restriction that every other API resource honors. The binding that should hold is:

`stack the ApiClient authorizes (current_api_client.stack_id) == stack the request is allowed to touch (params[:stack_id] resolved via #stack)`

For `CCMenuController` this equality is never enforced — `params[:stack_id]` can be any stack in the system regardless of `current_api_client.stack_id`.

### Impact Explanation
Any holder of a `read:stack`-scoped `ApiClient` token — including tokens intentionally scoped to a single stack (fixture `here_come_the_walrus` demonstrates this scoping pattern, and the associated stacks-controller test `"an api client scoped to a stack will only see that one stack"` confirms this is the intended security boundary) — can query `GET /api/stacks/:stack_id/ccmenu.xml?token=<token>` for **any** `stack_id`, not just the one the token was scoped to. This discloses build/deploy status, lock state, and stack name for stacks the token issuer never intended to expose. This matches the High-severity criteria: "escalation into `Shipit.github_teams` authorization... unauthorized read of stack state" — a token deliberately narrowed to one stack's state is used to read another stack's state.

### Likelihood Explanation
Exploitation requires only possession of any valid, stack-scoped `ApiClient` token with `read:stack` permission (no special privilege beyond what a normal integration/token holder already has) and knowledge of another stack's `stack_id`/`repo_owner/repo_name/environment` param format, which is discoverable/guessable since it is just `owner/name/environment`. The bypass is a direct, unconditional method override with no additional gating, so likelihood is high once a scoped token is available (e.g., leaked CI badge URL, since CCMenu URLs are typically embedded in dashboards/status badges via `CCMenuUrlController`).

### Recommendation
Change `Api::CCMenuController#stack` to reuse the scoped lookup from `BaseController` (i.e., `stacks.from_param!(params[:stack_id])`) instead of calling `Stack.from_param!` directly, so that a stack-scoped `ApiClient` cannot read CI status for stacks outside its `stack_id` scope.

### Proof of Concept
1. Create/obtain an `ApiClient` scoped to Stack A (`stack_id` set to A's id, `permissions: ['read:stack']`), e.g. as created transparently by `CCMenuUrlController#client` for stack A, yielding a token `T`.
2. Call `GET /api/stacks/<owner>/<name-of-stack-B>/<environment-B>/ccmenu.xml?token=T` where stack B is a different, unrelated stack.
3. Observe the response returns build/deploy status XML for stack B (per `Api::CCMenuController#show`), even though `T` was only meant to authorize reads of stack A — because `#stack` resolves via unscoped `Stack.from_param!` rather than `stacks.from_param!`.
