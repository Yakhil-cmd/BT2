### Title
Path traversal in release asset name allows arbitrary file write via `gh release download` - ([File: pkg/cmd/release/download/download.go])

### Summary
`gh release download` builds destination file names directly from the attacker-controlled `Name` field of a release asset without any traversal or absolute-path validation, unlike the analogous `internal/zip` and `pkg/cmd/run/download` code paths which use `internal/safepaths.Absolute.Join` to confine paths to the destination directory.

### Finding Description
In `downloadRun`, the download targets are built straight from `release.Assets`: `targets[i] = downloadTarget{url: ..., name: a.Name}` [1](#0-0) . This flows into `downloadAsset(dest, httpClient, a.url, a.name, isArchive)`, which calls `dest.Check(fileName)` and later `dest.Copy(fileName, resp.Body)` [2](#0-1) [3](#0-2) .

Both `Check` and `Copy` resolve the on-disk path via `destinationWriter.makePath`, which does a plain `filepath.Join(w.dir, name)` with no confinement check: [4](#0-3) 

`Copy` then creates parent directories with `os.MkdirAll(dir, 0755)` and opens the file with `os.OpenFile(fp, os.O_WRONLY|os.O_CREATE|os.O_TRUNC, 0644)`: [5](#0-4) 

Since `filepath.Join` normalizes `..` segments and also allows an absolute second argument to override the first entirely (`filepath.Join("/dest", "/tmp/evil.txt")` = `/dest/tmp/evil.txt`, but `filepath.Join("/dest", "../../evil.txt")` escapes `/dest`), an asset named e.g. `../../.ssh/authorized_keys` will resolve outside `--dir`. There is no equivalent of `internal/safepaths.Absolute.Join`, which is used elsewhere in the codebase (`internal/zip/zip.go`, `pkg/cmd/run/download/download.go`, `pkg/cmd/run/download/http.go`) specifically to reject `PathTraversalError` when joining archive/asset entry names to a destination directory. This confirms the omission here is inconsistent with the project's established mitigation for the same class of bug in adjacent, analogous code (workflow-run artifact downloads and zip extraction), and no other validation (host allowlist, name sanitization, `filepath.Base`) is applied to `a.Name` before it reaches `makePath`.

The only filename normalization present is `isWindowsReservedFilename`, which checks reserved DOS device names but does not strip `..` or leading `/` components, and only runs on `runtime.GOOS == "windows"` [6](#0-5) .

Since GitHub Releases asset names are attacker-controlled (any repo owner/collaborator with release-publish rights can set the asset's display `name` via the Releases API independent of the actual uploaded blob), and the victim runs `gh release download` (optionally without `--pattern`) against that release, this is a reachable attacker-to-victim path.

### Impact Explanation
An attacker who controls a repository release (their own repo, or a repo where they have release-publish permission, e.g. a fork the victim is instructed to pull from) can name an asset with a traversal sequence such as `../../.bashrc`, `../../.ssh/authorized_keys`, or `../../.git/hooks/pre-commit`. When the victim runs `gh release download` (with or without `--dir`) without a `--pattern`/`--output` that happens to exclude the malicious name, the tool will write attacker-supplied content to a path outside the intended destination directory, up to and including files with security consequences (SSH authorized keys, shell startup files, git hooks) if the victim's OS user has write permission there. This matches the "arbitrary file write outside intended path" impact class, potentially escalating to persistence/code execution depending on which file is overwritten.

### Likelihood Explanation
Preconditions are modest: the victim must run `gh release download` (a very common workflow, e.g. `gh release download v1.2.3`) against a release the attacker controls, without a `--pattern` that filters out the malicious asset name. No special privileges, token leakage, or MITM are required — publishing a release with a specially named asset is within normal, unprivileged GitHub repository owner/collaborator capabilities. The vulnerability is deterministic and repeatable for any victim who downloads assets from the crafted release.

### Recommendation
Validate/sanitize `a.Name` before using it to construct filesystem paths in `destinationWriter.makePath`. Reuse the existing `internal/safepaths.Absolute.Join` pattern (as already used in `internal/zip/zip.go` and `pkg/cmd/run/download`) to confine the joined path to `w.dir`, returning a `PathTraversalError` (and surfacing it as a hard error, not a skip) when an asset name traverses outside the destination directory or is an absolute path.

### Proof of Concept
Extend `Test_downloadRun` (or add a new test) in `pkg/cmd/release/download/download_test.go`:
1. Use `httpmock` to register a release with an asset whose `name` is `"../evil.txt"` (or `"/tmp/evil.txt"`).
2. Run `downloadRun` with `opts.Destination = "tmp/packages"` in a temp dir sandbox (chdir into a fresh temp directory to avoid polluting the real filesystem).
3. Assert that either:
   - `downloadRun` returns an error (expected fix behavior), or
   - Currently (bug): assert the resulting file exists at a path outside `filepath.Join(tmpDir, "tmp/packages")`, e.g. at `filepath.Join(tmpDir, "evil.txt")` — proving path confinement is violated since `destinationWriter.makePath` uses raw `filepath.Join` with no `safepaths.Absolute.Join`-style check [4](#0-3) .
