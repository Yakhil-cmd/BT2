### Title
Unchecked `burn()` Return in Bridge MintBurn Mode Enables Unauthorized Cross-Chain Token Minting — (`contracts/service_chain/bridge/BridgeTransferERC20.sol`, `contracts/service_chain/bridge/BridgeTransferERC721.sol`)

---

### Summary

In `modeMintBurn` mode, the Kaia service-chain bridge calls `ERC20Burnable(_tokenAddress).burn(_value)` and `ERC721Burnable(_tokenAddress).burn(_tokenId)` without any success guard. The counterpart mint operations on the same paths are wrapped in `require(...)`. If a registered token's `burn` silently fails (returns without reverting), the bridge still emits `RequestValueTransfer` and increments `requestNonce`, causing the counterpart bridge to mint tokens on the destination chain without any tokens being destroyed on the source chain.

---

### Finding Description

`_requestERC20Transfer` in `BridgeTransferERC20.sol` calls burn with no return-value check:

```solidity
if (modeMintBurn) {
    ERC20Burnable(_tokenAddress).burn(_value);   // ← no require, no success check
}
emit RequestValueTransfer(...);
requestNonce++;
``` [1](#0-0) 

The same pattern appears in `_requestERC721Transfer`:

```solidity
if (modeMintBurn) {
    ERC721Burnable(_tokenAddress).burn(_tokenId);  // ← no require, no success check
}
emit RequestValueTransferEncoded(...);
requestNonce++;
``` [2](#0-1) 

The **mint** paths on the same contracts are explicitly guarded:

```solidity
require(ERC20Mintable(_tokenAddress).mint(_to, _value), "handleERC20Transfer: mint failed");
``` [3](#0-2) 

```solidity
require(ERC721MetadataMintable(_tokenAddress).mintWithTokenURI(_to, _tokenId, _tokenURI), "mint failed");
``` [4](#0-3) 

The `ERC20Burnable` interface declares `burn` as `void` (no return value). [5](#0-4)  Under Solidity 0.5.x ABI rules, if the actual token's `burn` implementation returns `false` instead of reverting, the bridge ignores the return data and continues execution. The `RequestValueTransfer` event is emitted and `requestNonce` is incremented, which operators on the counterpart chain treat as a valid cross-chain transfer request and respond to by minting tokens.

The `requestNonce` is the sole sequencing signal used by bridge operators to trigger minting on the counterpart chain. [6](#0-5) 

---

### Impact Explanation

If a registered token's `burn` silently fails (no revert, no actual state change):

1. Source chain: tokens are **not** burned — they remain in the bridge contract or in the user's wallet (depending on the 1-step vs 2-step path).
2. Source chain: `RequestValueTransfer` event is emitted and `requestNonce` is incremented as if the burn succeeded.
3. Destination chain: bridge operators observe the event and call `handleERC20Transfer`, which mints `_value` tokens to the recipient.

Result: **tokens are minted on the destination chain without any tokens being destroyed on the source chain** — a net unauthorized creation of bridged assets. This directly satisfies the impact gate criterion: *unauthorized mint of bridged assets*.

---

### Likelihood Explanation

**Conditions required:**
- The bridge must be in `modeMintBurn` mode.
- The token must be registered by the bridge owner (`onlyRegisteredToken` guard). [7](#0-6) 
- The token's `burn(uint256)` function (selector `0x42966c68`) must silently fail rather than revert.

The third condition is the key constraint. Standard OpenZeppelin `ERC20Burnable` always reverts on failure via `SafeMath.sub`. However, the bridge is designed to interoperate with any registered ERC20Burnable-compatible token. Non-standard tokens with access-controlled or pausable burn functions that return `false` instead of reverting are common in practice. The bridge owner registering such a token — even inadvertently — opens this path to any user who calls `requestERC20Transfer` or triggers `onERC20Received`.

The trigger itself is **unprivileged**: any user can call `requestERC20Transfer` with a registered token.

---

### Recommendation

Mirror the `require` guard used on the mint path. Since `ERC20Burnable.burn` is declared `void`, the fix requires either:

1. Checking the token balance before and after the burn call:
```solidity
uint256 balanceBefore = IERC20(_tokenAddress).balanceOf(address(this));
ERC20Burnable(_tokenAddress).burn(_value);
require(
    IERC20(_tokenAddress).balanceOf(address(this)) == balanceBefore - _value,
    "_requestERC20Transfer: burn failed"
);
```

2. Or defining a `IBurnable` interface that returns `bool` and wrapping in `require`:
```solidity
require(IBurnable(_tokenAddress).burn(_value), "_requestERC20Transfer: burn failed");
```

Apply the same fix to `_requestERC721Transfer` in `BridgeTransferERC721.sol`. [8](#0-7) 

---

### Proof of Concept

1. Deploy a token `MaliciousBurnable` with selector `0x42966c68` (`burn(uint256)`) that returns without reverting and without modifying any balance (a no-op burn).
2. Bridge owner registers `MaliciousBurnable` on a bridge deployed in `modeMintBurn = true` mode.
3. User calls `requestERC20Transfer(MaliciousBurnable, recipient, 1000e18, 0, "0x")`.
   - `safeTransferFrom` moves 1000 tokens from user to bridge.
   - `ERC20Burnable(MaliciousBurnable).burn(1000e18)` executes the no-op, returns silently.
   - `RequestValueTransfer` is emitted with `requestNonce = 0`.
   - `requestNonce` becomes 1.
4. Bridge operators on the counterpart chain observe the event and call `handleERC20Transfer(txhash, user, recipient, MaliciousBurnable_counterpart, 1000e18, 0, blockNum, "0x")`.
   - `require(ERC20Mintable(MaliciousBurnable_counterpart).mint(recipient, 1000e18), ...)` succeeds.
   - Recipient receives 1000 tokens on the destination chain.
5. Source chain: 1000 tokens remain in the bridge contract (not burned). Destination chain: 1000 new tokens minted. Net result: 1000 tokens created out of thin air.
