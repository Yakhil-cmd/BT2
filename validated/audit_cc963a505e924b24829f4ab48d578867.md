This is confirmed. `ReviewStack#env` merges PR labels directly into the environment hash with upcased label name as key and `"true"` as value [1](#0-0) , and this is a real, tested behavior — a fixture test explicitly asserts labels `wip`/`bug` become `WIP=true`/`BUG=true` in `stack.env` [2](#0-1) . So a PR labeled `bundle_gemfile` produces `stack.env['BUNDLE_GEMFILE'] = 'true'`. This flows into `TaskCommands#env`, which merges `@stack.env` into the task environment [3](#0-2) , which is passed as `env:` to each `Command.new(...)` for install/deploy steps [4](#0-3) .

However, the critical question is whether this `BUNDLE_GEMFILE=true` actually reaches the spawned process's environment via `Command#unbundled_env`/`PTY.spawn`. Tracing `Command`:

- `BASE_ENV` is computed once at class-load time from `Bundler.unbundled_env`/`Bundler.clean_env`, which strips bundler-specific env vars (including `BUNDLE_GEMFILE`) from the *host process's* environment, replacing them with `nil` overrides so the child doesn't inherit the operator's own Bundler context [5](#0-4) .
- `Command#unbundled_env` is `BASE_ENV.merge('PATH' => ...).merge(@env.stringify_keys)` [6](#0-5) . Here `@env` is exactly the `env` hash passed into `Command.new` — i.e., the stack/task env, which **does** include attacker-controlled keys.

So the binding the question poses — "`BUNDLE_GEMFILE` in `unbundled_env`, if present at all, `==` the operator-configured path, never a PR-label-derived value" — is **false**. `@env.stringify_keys` is merged last and will override any `BASE_ENV` entry, so if the task/stack env hash contains a `BUNDLE_GEMFILE` key (from a `bundle_gemfile` label), it **is** included in the final env dict handed to `PTY.spawn` at [7](#0-6) .

That said, this only sets `BUNDLE_GEMFILE=true` as a literal string. For this to matter, some bundler invocation must occur inside `chdir` (the task's working directory, which is the checked-out PR branch) with `BUNDLE_GEMFILE=true` in env — bundler would then try to load a file named `true` relative to cwd. Reaching that requires (a) the deploy spec / step definitions to invoke `bundle` (e.g. via `bundle_exec` helpers in `BundlerDiscovery`) [8](#0-7) , and (b) the attacker planting a file literally named `true` in the repo (via a second commit) containing malicious Ruby that gets `eval`'d as a Gemfile DSL when bundler loads it — this is standard Bundler behavior, not a defect introduced by Shipit, but Shipit's code is what makes the attacker-controlled value reach the child process env at all.

### Title
Pull request labels injected into task/command environment allow attacker control of `BUNDLE_GEMFILE` (and any other env var) reaching `PTY.spawn` - (File: app/models/shipit/review_stack.rb)

### Summary
`ReviewStack#env` merges every PR label into the environment as `LABEL_NAME=true` with no allowlist or key filtering, and this hash is merged into `Command`'s `@env`, which is applied last in `Command#unbundled_env` on top of the sanitized `BASE_ENV`, so it reaches `PTY.spawn` unmodified. An attacker who can label their own PR (e.g. label named `bundle_gemfile`) can therefore set arbitrary environment variables, including `BUNDLE_GEMFILE`, for any command run against that PR's review stack.

### Finding Description
The claimed binding — `BUNDLE_GEMFILE ∈ Command#unbundled_env` implies `BUNDLE_GEMFILE == operator_configured_path` — is broken. The actual equality is `Command#unbundled_env['BUNDLE_GEMFILE'] == @env['BUNDLE_GEMFILE']` whenever `@env` (the hash passed to `Command.new`) contains that key, per the merge order `BASE_ENV.merge(PATH).merge(@env.stringify_keys)` [6](#0-5) .

Path: GitHub PR labeled with `bundle_gemfile` → webhook syncs `PullRequest#labels` via `github_pull_request=` (`self.labels = github_pull_request.labels.map(&:name)`) [9](#0-8)  → `ReviewStack#env` upcases and injects each label as `LABEL => "true"` [1](#0-0)  → `TaskCommands#env` merges `@stack.env` [10](#0-9)  → passed as `env:` into every `Command.new` for install/deploy steps [4](#0-3)  → `Command#start` calls `PTY.spawn(unbundled_env, *interpolated_arguments, chdir: @chdir)` [7](#0-6) .

No guard filters label names against reserved/dangerous env var names before merging into `env`; the `EnvironmentVariables#permit`/interpolation logic operates on argument interpolation, not on which keys populate `Command#env`. This is confirmed as intended-but-unsafe behavior by an existing test that explicitly checks arbitrary label names become env vars [2](#0-1) .

### Impact Explanation
Any GitHub user who can open/label a PR in a repository hooked to Shipit (attacker owns their own PR, review stacks are typically auto-provisioned per PR) can inject arbitrary environment variable names/values (capped to `"true"` string values, but the variable *name* is fully attacker-chosen) into every command executed for that PR's review stack, including `install_dependencies` and deploy `steps`. Whether this reaches full RCE depends on downstream consumption by bundler or other tools invoked in the deploy spec/steps (out of scope of this engine's own committed code path, and requires bundler to actually be invoked with a Gemfile named `true` planted via a second commit — a chain not established purely within this engine). The clearly demonstrable, in-scope impact is: unauthorized environment-variable injection into command execution for the labeling PR's own review stack (scoped to that stack only, not cross-tenant).

### Likelihood Explanation
Low operator cost for the attacker: label their own PR with `bundle_gemfile` (or any sensitive-sounding name) requires only PR-labeling permission, which for a repo the attacker owns/forks-into is trivial. No secrets or privileged roles needed. Full RCE additionally requires the deploy spec to shell out to `bundle` and the attacker to plant a file literally named `true`, which is plausible but not guaranteed by generic Shipit configuration — feasibility depends on deploy spec content.

### Recommendation
In `ReviewStack#env`, do not allow labels to set reserved/dangerous environment variable names (e.g., `BUNDLE_GEMFILE`, `PATH`, `RUBYOPT`, `LD_PRELOAD`, etc.) — either allowlist a safe prefix (e.g., require labels to be namespaced like `LABEL_*`) or explicitly filter out keys colliding with `Command::BASE_ENV` / bundler-reserved variable names before merging.
