### Title
Unbounded HTTP server via `http.Serve` with no timeouts enables goroutine/FD exhaustion (Slowloris) - (File: main.go)

### Summary
When `--http-bind` is set, git-sync starts its liveness/metrics/pprof HTTP endpoint with a bare `http.Serve(ln, mux)` call instead of a configured `http.Server` with timeouts. Because no `ReadTimeout`, `ReadHeaderTimeout`, `WriteTimeout`, or `IdleTimeout` is set, a remote client that opens connections and sends data (or nothing) slowly can hold each accepted connection's goroutine and file descriptor open indefinitely, eventually starving the process of file descriptors/goroutines and breaking the readiness/liveness probe that Kubernetes and other consumers rely on. Note: the question's cited target (`pkg/logging/logging.go` `Logger.Error`/`writeContent`/`ExportError`/`DeleteErrorFile`) is unrelated to this issue — the actual vulnerable code is the HTTP bootstrap in `main.go`.

### Finding Description
In `main.go`, the HTTP endpoint is wired up as: [1](#0-0) 

Specifically, the server is started with:
```go
go func() {
    err := http.Serve(ln, mux)
    log.Error(err, "HTTP server terminated")
    os.Exit(1)
}()
```
`http.Serve` uses Go's zero-value `http.Server` semantics implicitly — there is no `ReadTimeout`, `ReadHeaderTimeout`, `WriteTimeout`, or `IdleTimeout` configured anywhere in the file (confirmed: no other `http.Server{...}` construction exists in `main.go`). Each accepted TCP connection spawns a goroutine (`net/http`'s `conn.serve`) that blocks reading the request headers/body for as long as the client trickles bytes (or never sends anything at all, up to TCP keepalive/timeout limits), holding one file descriptor and one goroutine per connection with no server-side cutoff.

An attacker who can merely reach the `--http-bind` TCP port (documented in README.md as intended for "Kubernetes startup and liveness probes") can open many such slow/idle connections, exhausting file descriptors and/or goroutines. Because the same `mux` serves `/` (liveness), `/metrics`, and `/debug/pprof/*` on one listener, once the process is starved, the liveness probe itself becomes unresponsive, and depending on how it's used, kubelet may restart the container or, if used by the injecting sidecar pattern as a "consumer readiness gate," downstream consumers relying on `wait_for_sync`/HTTP readiness will stall.

This is a real, reachable code path requiring only the documented `--http-bind` flag (a normal, supported setting used throughout `test_e2e.sh`, e.g. `--http-bind=":$HTTP_PORT"`), not any misconfiguration or privileged action. No existing validation, timeout, or `http.Server` field mitigates it.

### Impact Explanation
This matches the "sidecar denial of service: updates stop" style impact: exhausting the container's file descriptors/goroutines can crash or hang the whole git-sync process (not just the HTTP handler), since fetch/checkout also need FDs and goroutines. Even short of a full crash, it degrades the liveness/readiness endpoint that Kubernetes and consumers depend on for gating on sync completeness, causing consumers to be starved of updates or the pod to be killed/restarted.

### Likelihood Explanation
Requires only that the operator has set `--http-bind` (a common, documented, supported configuration — used by default in the e2e test harness) and that the attacker can reach that port (typically same-namespace/in-cluster network access, consistent with the "unauthenticated in-cluster request" threat model in the question). No authentication exists on the endpoint. The attack is trivially repeatable and requires no special privileges, flags, or exec access — only many concurrent slow TCP connections (classic Slowloris), which is straightforward to script.

### Recommendation
Replace the bare `http.Serve(ln, mux)` call with an explicit `http.Server` that sets conservative timeouts, e.g.:
```go
srv := &http.Server{
    Handler:           mux,
    ReadTimeout:       5 * time.Second,
    ReadHeaderTimeout: 5 * time.Second,
    WriteTimeout:      10 * time.Second,
    IdleTimeout:       60 * time.Second,
}
go func() {
    err := srv.Serve(ln)
    log.Error(err, "HTTP server terminated")
    os.Exit(1)
}()
```
Optionally also cap `MaxHeaderBytes` and/or use `netutil.LimitListener` to bound total concurrent connections.
