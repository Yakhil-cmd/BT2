Confirmed: `Commit#sha` has no uniqueness scoping to `stack_id` at the model level (only `belongs_to :stack`), so the same SHA can legitimately exist across many `Stack`/`Commit` rows tracked by different tenants.

### Title
StatusHandler bypasses repository-scoped `stacks` binding, mutating any Commit sharing a SHA - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`Shipit::Webhooks::Handlers::Handler#stacks` exists specifically to scope webhook processing to the stacks authorized by the payload's `repository.full_name`, but `StatusHandler#process` never calls it. Instead it runs `Commit.where(sha: params.sha)` globally and calls `create_status_from_github!` on every match, so a validly-signed "status" webhook for a repository that owns zero Shipit stacks can still create/mutate `Status` rows on `Commit`s belonging to completely unrelated, legitimately tracked `Stack`s whose commit happens to share the same SHA.

### Finding Description
The claimed binding is: `stacks` (the set of `Stack`s the payload's `repository.full_name` authorizes via `Handler#stacks`, `Repository.from_github_repo_name(repository_name)&.stacks`) == the actual set of stacks whose `Commit` rows get mutated by processing the webhook. [1](#0-0) 

`StatusHandler` never references `stacks` or `repository_name` at all: [2](#0-1) 

`process` does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` — a global, cross-tenant lookup keyed only by `sha`, with no `stack_id`/`repository_id` filter. Since `Commit` has no uniqueness constraint scoping `sha` to a `stack` (`belongs_to :stack` only, no scoped uniqueness validator) [3](#0-2) , the same SHA can legitimately exist for `Commit` rows in multiple unrelated `Stack`s (e.g. two Stacks tracking mirrored/forked history of the same upstream commit, or any org where multiple repos share commit ancestry).

The webhook still has to pass `WebhooksController#verify_signature`, which computes the HMAC using `Shipit.github(organization: repository_owner)` [4](#0-3) . This is keyed on the payload's `repository.owner.login` (the org), not on whether that specific repository is a registered `Shipit::Repository`. GitHub Apps are installed at the org/repo-selection level (per `docs/setup.md`, "Installing the GitHub App on your organization"), and a single `webhook_secret` is shared across every repository the App is installed on within that org — regardless of whether Shipit has created a `Stack` for it. So any repository under an org where the App is installed produces a validly-signed "status" webhook even if that repository has zero corresponding `Shipit::Repository`/`Stack` rows (`repository_name` resolves to nothing, so `Handler#stacks` would be `Stack.none` if it were consulted).

Because `StatusHandler` skips `stacks` entirely, that empty authorization set is never checked. Existing guards (`verify_signature`, `drop_unhandled_event`, `ExplicitParameters` schema on `sha`/`state`) only validate signature and shape, not scope-to-repository. `Status` creation goes on to touch `commit.stack.enable_ci!` and schedules `commit.schedule_continuous_delivery` [5](#0-4)  and [6](#0-5) , so the mutation has real side effects on the victim stack (CI-enablement, merge-queue/continuous-delivery scheduling), not just a cosmetic row insert.

### Impact Explanation
An attacker who controls (or has push/CI access to) any single repository under an org where the GitHub App happens to be installed — even one never registered as a Shipit `Repository`/`Stack` — can send a "status" event whose `sha` matches a commit tracked by a completely different, legitimate `Stack`. This creates a `Status` row attributed to that foreign commit, which can flip the commit's CI state, trigger `enable_ci_on_stack`, and enqueue `ProcessMergeRequestsJob`/continuous-delivery scheduling for a repository the attacker never authenticated against. This is a payload for one repository mutating another repository's stack/commit records — matching the Critical category ("a payload for one repository mutating another's stack, commit, task or team").

### Likelihood Explanation
Preconditions: the attacker needs a repository capable of emitting a validly-signed "status" webhook to the Shipit instance — either because the org's GitHub App installation covers additional/all repos beyond those tracked as Shipit stacks (a very common, documented setup), or because the operator left `webhook_secret` unset (documented as "optional", in which case `verify_webhook_signature` returns `true` unconditionally) [7](#0-6) . Getting the matching SHA onto a commit in the attacker's own repo is feasible in realistic scenarios (mirrors/forks sharing history, monorepo splits) without any preimage attack. No Shipit session, API token, or team membership is required — this is purely a webhook-path issue.

### Recommendation
Make `StatusHandler#process` scope the commit lookup through the same `stacks` binding every other stack-affecting handler uses, e.g. `stacks.joins(:commits).merge(Commit.where(sha: params.sha))` or `Commit.where(sha: params.sha, stack: stacks)`, so only commits belonging to stacks whose repository matches the payload's `repository.full_name` can be mutated.

### Proof of Concept
minitest plan (in `test/models/shipit/webhooks/handlers/status_handler_test.rb` or `test/controllers/webhooks_controller_test.rb`, no live GitHub):
1. Load fixture `commit = shipit_commits(:first)` belonging to tracked stack `shipit_stacks(:shipit)`.
2. Build a status payload with `sha: commit.sha` but `repository.full_name = "attacker/unregistered-repo"` (assert `Repository.from_github_repo_name("attacker/unregistered-repo")` is `nil`, so `Handler#stacks` for that payload would be `Stack.none`).
3. POST it to `/webhooks` with `X-Github-Event: status`, stubbing `GithubHook`/`verify_signature` as done in existing tests (`GithubHook.any_instance.stubs(:verify_signature).returns(true)`).
4. Assert `commit.statuses.count` increases by 1 (`assert_difference 'commit.statuses.count', 1 { post :create, body:, as: :json }`), proving a webhook for a repository with zero authorized stacks mutated a `Commit` belonging to an unrelated, legitimately tracked `Stack`.

Both sides of the equality diverge: left side (`stacks` for `attacker/unregistered-repo`) = `[]`; right side (stacks whose commits actually get a new `Status`) = `[shipit_stacks(:shipit)]`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
