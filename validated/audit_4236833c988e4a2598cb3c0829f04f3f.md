## Analysis

The Blueberry report describes a class of bug: an aggregator that combines multiple independent oracle values throws (reverts) in an ambiguous-comparison edge case, even though enough valid values exist to produce a result. In ocore, the closest reachable analog is the multi-oracle `data_feed[[...]]` resolution path in `readDataFeedValue`, which aggregates candidate values from multiple oracle addresses (an AA formula author can specify several `oracles` separated by `:`) posted by unstable AA units, and which contains an unhandled/uncaught `throw Error` in its tie-break comparator — a strictly worse outcome than a graceful bounce, since it is a synchronous exception rather than a caught formula error. [1](#0-0) 

### Title
Uncaught exception in `readDataFeedValue()` tie-break sort crashes node/AA evaluation when multiple oracle candidates tie - (File: data_feeds.js)

### Summary
`readDataFeedValue()` supports querying several oracle addresses at once via `data_feed[[oracles="addr1:addr2:...", ...]]` in AA formulas [2](#0-1) . When `unstable_opts` is set (reading unstable AA-posted data feeds), it collects all matching candidates across the listed oracle addresses into `arrCandidates` [3](#0-2) . If more than one candidate exists and `ifseveral !== 'abort'`, it attempts to pick the most recent one via `Array.prototype.sort`, comparing `latest_included_mc_index` then `level`; if both are equal (a genuine tie between two distinct oracle-authored units) and `bIncludeAllUnstable` is false, the comparator does not return an ordering — it throws a raw `Error("can't sort candidates ...")` [4](#0-3) .

### Finding Description
Unlike the rest of the data-feed/formula-evaluation error paths, which return controlled errors that `formula/evaluation.js` converts into a fatal formula error (bouncing just the triggering AA) via `setFatalError('error from data feed: '+err, ...)` [5](#0-4) , this particular failure is a synchronous JavaScript `throw` executed directly inside the `Array.sort` comparator, prior to any callback being invoked. It propagates up through the synchronous call stack of `readDataFeedValue` → `getDataFeed` → `evaluate()` → the AA trigger-handling code in `aa_composer.js`, none of which appear to wrap this particular code path in a `try/catch` that specifically anticipates this exception (only `try/catch` blocks tied to formula parsing/execution errors returned via callbacks are shown; a raw synchronous throw from deep inside a `.sort()` predicate bypasses the callback-based error-handling convention used everywhere else in this module).

The precondition to trigger the tie is that two (or more) *different* oracle-authored data-feed messages for the same `feed_name`, posted by two of the addresses listed in `oracles`, are simultaneously unstable and have identical `latest_included_mc_index` and identical DAG `level`. Because `level` is computed purely from the unit's parents (`level = max(parent levels) + 1`), it is entirely possible for two independently-authored sibling units (neither being an ancestor of the other) to land on the same level while both are still unstable, especially soon after being posted. Any user can arrange for two oracle AAs (or a malicious/careless pair of legitimate oracles) to emit conflicting/duplicate `data_feed` messages around the same time, and then post a trigger to a third AA that reads `data_feed[[oracles="oracle1:oracle2", feed_name=..., unstable_opts]]` (or a formula using `unstable_opts` conceptually equivalent) while those two candidate units are still unstable and tied.

### Impact Explanation
This is worse than a simple, contained revert: it is an unhandled synchronous exception in the middle of AA trigger/formula evaluation. Depending on how far up the call stack lacks a matching `try/catch`, this can crash the node process handling AA triggers rather than merely bouncing the offending AA call, since the throw happens outside the normal async-callback error-propagation pattern that the rest of the module relies on. A crash of a full node (or of the AA-composer/validation process) that processes AA triggers is a denial-of-service against the network's ability to process further units/AA triggers, which is more severe than the original Sherlock finding (which only caused a controlled revert of a single price read).

### Likelihood Explanation
Likelihood is moderate: it requires two oracle-authored unstable units, referenced together in the same `oracles` list of a `data_feed` read, to tie exactly on `latest_included_mc_index` and `level` while posting values for the same `feed_name`. This is plausible in busy periods with parallel oracle posts (feed value discrepancies or duplicate posts by legitimate oracles), and is fully triggerable by any unprivileged unit poster who controls the AA trigger and can arrange (or wait for) two oracle posts to tie, since nothing in the codebase prevents two distinct units from sharing level and LIMCI while both are unstable.

### Recommendation
Replace the `throw Error("can't sort candidates ...")` inside the sort comparator with a deterministic, total-order tie-breaker (e.g., compare `unit` hash lexicographically as a final fallback) instead of throwing, and route any residual, genuinely-unresolvable ambiguity through the same callback-based error path used elsewhere (`handleResult`/`objResult.bAbortedBecauseOfSeveral`) rather than a synchronous `throw`, so evaluation always fails gracefully as a formula error rather than as an uncaught process-level exception.

### Proof of Concept
1. Deploy two AAs, `OracleA` and `OracleB`, each capable of emitting a `data_feed` app message with the same `feed_name` (e.g., `"price"`).
2. Trigger `OracleA` and `OracleB` with sibling (non-ancestor) parent units so their resulting unstable units land on the same DAG `level`, and with parents chosen so their `latest_included_mc_index` values are identical.
3. Deploy/trigger a consumer AA whose formula includes `data_feed[[oracles="OracleA:OracleB", feed_name="price", ifseveral="last", ...]]` with `unstable_opts` behavior engaged (reading unstable AA data feeds) while both `OracleA` and `OracleB` units are still unstable.
4. When the consumer AA formula is evaluated, `readDataFeedValue()` collects both candidates, finds `arrCandidates.length > 1`, and its `sort()` comparator hits the tie branch, throwing `Error("can't sort candidates ...")` synchronously instead of returning a controlled formula-level bounce, potentially crashing the evaluating process instead of simply bouncing the trigger. 

Note: I was not able to fully trace every intermediate frame between `evaluate()` in `formula/evaluation.js` and the top-level AA trigger dispatcher in `aa_composer.js` to conclusively confirm whether some outer `try/catch` ultimately intercepts this specific synchronous throw before it reaches the process level; this would require deeper live tracing/testing beyond what the indexed code excerpts show.
