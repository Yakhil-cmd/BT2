Fork PR can inject `NODE_OPTIONS=--require /tmp/evil.js` via `machine.environment` in `shipit.yml` to achieve RCE on the deploy host - (File: app/models/shipit/deploy_spec.rb, lib/shipit/task_commands.rb, lib/shipit/command.rb)

### Summary
`DeploySpec#machine_env` returns `config('machine', 'environment')` from the checked-out `shipit.yml` verbatim, with no key/value allow-listing. `TaskCommands#env` merges this hash unfiltered into the environment passed to `Command.new`, and `Command#unbundled_env` merges it verbatim into the hash handed to `PTY.spawn`. Because review stacks check out and load their `shipit.yml` from the fork PR's own branch, a PR author fully controls this hash, including setting `NODE_OPTIONS`.

### Finding Description
The broken binding: the invariant "no spawned deploy process ever sees a fork-controlled `NODE_OPTIONS`" requires `env_seen_by_PTY_spawn['NODE_OPTIONS'] == value_set_by_Shipit_operator`, but in practice `env_seen_by_PTY_spawn['NODE_OPTIONS'] == value_from_fork_PR_shipit_yml['machine']['environment']['NODE_OPTIONS']`.

Trace:
1. `DeploySpec#machine_env` at [1](#0-0)  returns `config('machine', 'environment') || {}` with no filtering.
2. `DeploySpec::FileSystem` loads this config from the task's working directory, which is a checkout of the review stack's own branch — the fork PR's branch — via `config_file_path`/`load_config` [2](#0-1) .
3. `TaskCommands#env` merges `deploy_spec.machine_env` directly into the environment hash used to build every `Command` for install/deploy/task steps: [3](#0-2) .
4. `Command#initialize` stores `@env` as-is (only `.to_s`-coerced, no key filtering) [4](#0-3) , and `Command#unbundled_env` merges `@env` verbatim into the environment passed to `PTY.spawn` [5](#0-4) .

Unlike `deploy.variables`/`rollback.variables`/task `variables`, which are explicitly allow-listed through `EnvironmentVariables#permit` (`filter_deploy_envs`, `filter_rollback_envs`, `TaskDefinition#filter_envs` at [6](#0-5)  and [7](#0-6) ), `machine_env` has no equivalent allow-list — `EnvironmentVariables#permit` at [8](#0-7)  is never invoked on it. `ReviewStack#env` at [9](#0-8)  only adds PR-label-derived vars but does not restrict or sanitize `machine_env` either, and there is no code path that strips dangerous variable names (`NODE_OPTIONS`, `LD_PRELOAD`, `RUBYOPT`, `PYTHONSTARTUP`, etc.) before merging into the spawn env.

An attacker opens a PR against a repository with review stacks enabled, adds a `shipit.yml` (or `.shipit/shipit.yml`) to their fork branch containing:
```yml
machine:
  environment:
    NODE_OPTIONS: "--require /tmp/evil.js"
```
and places `/tmp/evil.js` (or any reachable path) content in the same PR. When the review stack is provisioned/deployed (`PerformTaskJob` → `TaskCommands#install_dependencies`/`#perform` → `Command.new(..., env: env, ...)` → `PTY.spawn`), any Node.js invocation in the deploy/dependency-install steps runs with `NODE_OPTIONS` set, causing Node to `--require` the attacker's file, achieving code execution as the Shipit deploy host process.

### Impact Explanation
This is Critical — Remote Code Execution on the Shipit deploy host. Any Node.js-based step (install dependencies, deploy steps, custom tasks) run for that review stack's task will load and execute attacker-supplied JavaScript with the privileges of the deploy worker process, including access to `GITHUB_TOKEN` and other secrets available to `Command`/`base_env`. This is repeatable on every task run for that stack and is fully attacker-controlled per PR/branch; it does not require any Shipit operator privilege, only the ability to open a PR against a repo with review stacks configured.

### Likelihood Explanation
Preconditions: the target repository must have review stacks enabled (a documented Shipit feature) and the attacker must be able to open a PR / push a branch (fork PR, no special permissions needed). No secrets, tokens, or maintainer approval are required to have the deploy process read the malicious `shipit.yml` — provisioning/deploying a review stack is triggered by normal PR webhook activity. This is low-cost and fully reproducible.

### Recommendation
Apply the same explicit allow-list mechanism used for `deploy.variables`/`rollback.variables`/task `variables` to `machine.environment`: require repository/stack maintainers (via a separate, non-fork-controlled configuration, e.g., set on the `Stack`/`Repository` model rather than from the untrusted `shipit.yml`) to declare which `machine.environment` keys are permitted, and run `EnvironmentVariables.with(machine_env).permit(allowed_machine_vars)` before merging it into `TaskCommands#env`. At minimum, block security-sensitive variable names (`NODE_OPTIONS`, `LD_PRELOAD`, `LD_LIBRARY_PATH`, `RUBYOPT`, `PYTHONSTARTUP`, `BASH_ENV`, etc.) from ever being set via a repo-controlled `shipit.yml` on review stacks/fork branches.

test "machine.environment NODE_OPTIONS from fork shipit.yml reaches Command#unbundled_env verbatim" do
