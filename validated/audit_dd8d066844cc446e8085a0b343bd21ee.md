### Title
Webhook signature is verified against `repository.owner.login`'s GitHub App while `PushHandler` resolves the target stack from the independent `repository.full_name` field, allowing cross-repository `GithubSyncJob` triggering - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/handler.rb], [File: app/models/shipit/webhooks/handlers/push_handler.rb])

### Summary
`WebhooksController#verify_signature` selects which `GitHubApp` (and thus which `webhook_secret`) to verify against using `repository_owner`, derived from `payload.dig('repository','owner','login')`. `Handler#stacks` (used by `PushHandler`) instead resolves the target `Repository`/`Stack` from `payload.dig('repository','full_name')`. These two payload fields are never compared, so an attacker who controls an organization with no `webhook_secret` configured can send a JSON body where `repository.owner.login` names their own org and `repository.full_name` names a victim org's repository, causing `stack.sync_github(expected_head_sha: params.after)` to run against the victim's stack.

### Finding Description
The broken binding: the code implicitly assumes
`payload.dig('repository','owner','login') == payload.dig('repository','full_name').split('/').first`
but this equality is never asserted anywhere in the request path.

Path:
1. `WebhooksController#verify_signature` computes `repository_owner = params.dig('repository','owner','login') || params.dig('organization','login')` and calls `Shipit.github(organization: repository_owner)` [1](#0-0)  then [2](#0-1) .
2. `GitHubApp#verify_webhook_signature` short-circuits to `true` when that organization's `webhook_secret` is blank/unconfigured: `return true unless webhook_secret` [3](#0-2) . So if the attacker's own org ("attacker-org") is configured in Shipit with no `webhook_secret`, any signature (or none) is accepted for a webhook whose `repository.owner.login` claims to be "attacker-org".
3. On acceptance, `WebhooksController#create` dispatches to `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`, passing the full raw JSON `params` (including the attacker-chosen `repository.full_name`) [4](#0-3) .
4. `PushHandler#process` calls `stacks.not_archived.where(branch:).find_each { |stack| stack.sync_github(expected_head_sha: params.after) }` [5](#0-4) .
5. `Handler#stacks` resolves via `Repository.from_github_repo_name(repository_name)` where `repository_name = payload.dig('repository', 'full_name')` — an entirely separate JSON field from the one used for signature verification [6](#0-5) .
6. `Repository.from_github_repo_name` simply splits `"owner/name"` and does a `find_by` lookup with no relation to who was authenticated in step 1 [7](#0-6) .

Attacker request: POST `/webhooks` with header `X-Github-Event: push`, body:
```json
{
  "repository": {"owner": {"login": "attacker-org"}, "full_name": "victim-org/victim-repo"},
  "ref": "refs/heads/<victim-deploy-branch>",
  "after": "<attacker-chosen-sha>"
}
```
Since `attacker-org` is a real org the attacker registered in Shipit (or any org with no `webhook_secret` set — including one with a misconfigured/absent secret), `verify_webhook_signature` returns `true` unconditionally regardless of the `X-Hub-Signature` header content. The handler then looks up `victim-org/victim-repo`'s stack by `full_name` and branch, and enqueues `GithubSyncJob` (via `stack.sync_github`) with an attacker-supplied `expected_head_sha`, entirely for a repository the attacker does not own and never authenticated against.

Existing guards do not prevent this: `drop_unhandled_event` only checks the event type is handled, not repository identity [8](#0-7) ; the `ExplicitParameters` schema on `PushHandler` only requires `ref` and `after` are present, not that they relate to the verified organization [9](#0-8) ; and `Repository`/`Stack` model validations only constrain format, not provenance.

### Impact Explanation
An attacker who controls (or registers) any Shipit-connected organization with no configured `webhook_secret` can force a `GithubSyncJob` to run against any other tenant's stack whose `owner/name` they can guess or discover, and can pin an arbitrary `expected_head_sha` to race the victim's sync process. This is a payload for one repository (an attacker-controlled org) mutating another repository's stack state (triggering sync jobs, potentially interfering with deploy state/expected-head-sha checks), matching the Critical category "a payload for one repository mutating another's stack." It is fully repeatable against any repository name/branch combination known to the attacker, and the blast radius spans all tenants hosted by the same Shipit instance.

### Likelihood Explanation
Preconditions: the attacker needs to control at least one GitHub organization/app entry configured in Shipit's `github_teams`/`github_apps` config with no `webhook_secret` set (a plausible, low-effort self-service configuration in many real deployments, e.g. a newly onboarded org before secrets are set, or any org intentionally left without a secret). No Shipit session, API token, or GitHub secret of the victim is required — only knowledge of the victim's `owner/name` and target branch, both public/discoverable information for most GitHub repos. The attack is a single unauthenticated HTTP POST, trivially repeatable.

### Recommendation
In `Handler#stacks` (or in `WebhooksController`), verify that the organization used to select/verify the `GitHubApp` (`repository.owner.login`) matches the owner segment of `repository.full_name` before resolving stacks; reject the webhook (e.g. `head(422)`) on mismatch. Additionally, consider requiring a `webhook_secret` to be configured for every registered organization (fail closed instead of `return true unless webhook_secret`) so an org without a secret cannot be used as a trusted relay for signature bypass.

### Proof of Concept
In `test/controllers/webhooks_controller_test.rb`, add a test:
1. Create an organization/app config `attacker-org` with no `webhook_secret` (via test fixtures/`Shipit.github_apps` config used in existing tests).
2. Create a victim `Stack`/`Repository` with `owner: 'victim-org', name: 'repo'` and a deploy `branch`.
3. POST to `/webhooks` with header `X-Github-Event: push` and body:
   ```json
   {"repository":{"owner":{"login":"attacker-org"},"full_name":"victim-org/repo"},"ref":"refs/heads/<branch>","after":"deadbeef"}
   ```
   with an arbitrary/absent `X-Hub-Signature`.
4. Assert response is `200 OK` (not `422`), and assert `GithubSyncJob` was enqueued with `stack_id` equal to the victim stack's id and `expected_head_sha: 'deadbeef'`, proving:
   - LHS binding: `params.dig('repository','owner','login') == 'attacker-org'` (used for signature verification org selection)
   - RHS binding: `params.dig('repository','full_name').split('/').first == 'victim-org'` (used for stack resolution)
   - These differ, yet the job for `victim-org/repo`'s stack still fires.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
