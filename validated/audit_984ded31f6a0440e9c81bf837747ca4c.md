### Title
CCMenu API endpoint bypasses per-stack token scoping, allowing any `read:stack` client to read any stack's build status - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::CCMenuController` authenticates an `ApiClient` token but resolves the target `Stack` with `Stack.from_param!(params[:stack_id])` instead of the scoped `stacks` helper that every other API controller uses, breaking the binding "stack a token authorizes == stack it touches."

### Finding Description
`ApiClient` tokens can be scoped to a single stack via `stack_id` [1](#0-0) . `Shipit::Api::BaseController` enforces this scoping generically through its `stacks` helper, which restricts the queryable `Stack` set to `current_api_client.stack_id` when the client is scoped: `@stacks ||= current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all` [2](#0-1) . Controllers like `Shipit::Api::StacksController` correctly go through this scoped lookup via `stacks.from_param!(params[:id])` [3](#0-2) .

`Shipit::Api::CCMenuController`, however, overrides `stack` to bypass the scoping entirely, resolving directly against the global `Stack` relation: `@stack ||= Stack.from_param!(params[:stack_id])` [4](#0-3) . The controller only checks the coarse `read:stack` permission via `require_permission :read, :stack` [5](#0-4) , and `ApiClient#check_permissions!` only checks that the permission string is present in the client's list — it never checks `stack_id` [6](#0-5) .

This means a token that was issued and is authorized to read exactly one stack (e.g. a "CCMenu Client" created by `CCMenuUrlController` scoped to a specific stack: `ApiClient.create_with(permissions: %w[read:stack]).find_or_create_by!(creator: current_user, name: 'CCMenu Client')` bound to a single `stack_id` [7](#0-6) ) can be replayed against any `stack_id` in the deployment, because the controller ignores the `stack_id` scoping and only checks the generic `read:stack` permission bit.

Equality that should hold but is broken:
`stack the ApiClient token authorizes (current_api_client.stack_id)` == `stack the CCMenuController actually serves (params[:stack_id])`
The controller only tests the latter against `Stack.from_param!`, never against the former.

### Impact Explanation
This is an "unauthenticated read of stack state ... task streams or deploy output" style escalation: any holder of a `read:stack`-scoped-to-one-stack token (e.g. leaked from a CI status badge URL, a low-privilege integration, or a link shared for one stack's CCMenu URL) can enumerate and read the build/deploy status (`lastBuildStatus`, `lastBuildLabel`, `activity`, `webUrl`, lock state) of every other stack in the Shipit install, including stacks they were never granted access to. This matches the High severity criterion "escalation into `Shipit.github_teams` authorization, unauthenticated read of stack state, task streams or deploy output."

### Likelihood Explanation
High likelihood: exploitation requires only possession of any valid `ApiClient` token with the `read:stack` permission (regardless of its `stack_id` scope) and knowledge/guessing of another stack's `to_param` (a predictable slug like `owner/repo/environment`). No privileged account, webhook secret, or GitHub credentials are needed beyond the already-issued token — which is exactly the class of token the scoping mechanism (`stack_id`) is meant to constrain.

### Recommendation
Change `Shipit::Api::CCMenuController#stack` to resolve through the scoped `stacks` helper, consistent with `StacksController` and the rest of the API surface:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
This ensures `current_api_client.stack_id`-scoped tokens can only ever resolve to their authorized stack, restoring the "authorized stack == accessed stack" invariant enforced elsewhere in `BaseController`.

### Proof of Concept
1. As a legitimate user, visit a stack's CCMenu URL generation endpoint, which creates (or reuses) an `ApiClient` named "CCMenu Client" scoped to `stack: A` with `permissions: ['read:stack']`, and returns a token `T` (see `CCMenuUrlController#client`/`#fetch`) [8](#0-7) .
2. Using token `T`, issue: `GET /api/stacks/<STACK_B_PARAM>/ccmenu.xml?token=T` where `STACK_B` is any other stack in the install that the token was never scoped to.
3. `authenticate_api_client` in `CCMenuController` succeeds because `T` is a valid token (`ApiClient.authenticate(params[:token])`) [9](#0-8) .
4. `require_permission :read, :stack` succeeds because `T`'s permissions include `read:stack`, with no stack-id check [6](#0-5) .
5. `stack` resolves `STACK_B` directly via `Stack.from_param!(params[:stack_id])`, bypassing the `current_api_client.stack_id` restriction that the token was issued under [4](#0-3) .
6. The response renders `STACK_B`'s deploy/build status XML, which the token holder was never authorized to see.
