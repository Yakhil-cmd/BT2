### Title
Webhook signature verification is bound to an attacker-chosen organization, not to the repository the payload actually writes to - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/webhook secret to check the `X-Hub-Signature` against by reading `repository.owner.login` (or `organization.login`) directly out of the still-unverified JSON body. `GithubApp#verify_webhook_signature` then returns `true` unconditionally whenever that organization's `webhook_secret` is blank/nil - a state that is explicitly documented and shipped as the default in multi-org configuration (`webhook_secret: # nil`). Because the attacker fully controls the JSON body used to pick the organization, they can name an org with no configured secret to make the "authenticated organization" check pass trivially, while the rest of the same payload (`repository.full_name`, `sha`, `state`, `check_suite.head_sha`, `member`, `team`, etc.) is processed by the event handlers exactly as sent - with no re-check that the acted-upon repository/organization is the one whose secret was actually verified.

### Finding Description
`repository_owner` is derived from the raw, unauthenticated payload before any cryptographic check occurs: [1](#0-0) [2](#0-1) 

`Shipit.github(organization: repository_owner)` looks up the per-organization `GithubApp`/secret and `verify_webhook_signature` is called against it: [3](#0-2) 

Note the guard `return true unless webhook_secret` - if the organization named in the attacker-supplied payload has no `webhook_secret` configured, signature verification is bypassed entirely for that request, regardless of the payload's actual signature header. Leaving `webhook_secret` empty per organization is a first-class, documented configuration: [4](#0-3) [5](#0-4) 

After `verify_signature` passes (because the "authenticating organization" had no secret), `create` re-parses the same raw body and dispatches it, unmodified, to registered handlers for the event type: [6](#0-5) 

Nothing at any point re-validates that the `repository`/`organization` fields the handlers actually act on match the organization that gated the signature check. The two values - "organization that authenticated" and "repository that is written" - come from the same untrusted JSON and are never cross-checked, which is exactly the class of binding break described in the report: a payload field (`repository.full_name`, `sha`, `state`, `member`, `team`, `check_suite.head_sha`, …) is acted upon by the handler but was never actually covered by a verified signature, because the signature check was satisfied by a different, secret-less identity picked from the same payload.

This is demonstrated by the handlers' behavior once dispatched, e.g. status webhooks create a `Status` directly from unauthenticated fields: [7](#0-6) 
and `membership` webhooks create/append/remove `Team`/`Membership` records purely from payload content: [8](#0-7) 

### Impact Explanation
An unprivileged network attacker who knows (or guesses) the name of any organization configured in Shipit's multi-org `github:` block without a `webhook_secret` can send arbitrary, unsigned webhook payloads that Shipit will treat as fully verified GitHub events, as long as `repository.owner.login`/`organization.login` in the JSON body names that secret-less org. The `repository`, `sha`, `state`, `member`, `team`, etc. fields inside that same request are not bound to the org used for the check, so the attacker can target stacks/commits/teams belonging to any other, properly secured organization tracked by the same Shipit instance. Concretely this enables:
- Forging `status`/`check_suite` events to mark arbitrary commits as passing required CI checks (`ci.require`), which `MergeRequest#reject_unless_mergeable!`/deploy gating rely on - degrading the CI-gate binding that protects merges/deploys.
- Forging `membership` events to add or remove users from `Team`s that back `Shipit.github_teams` authorization - a direct escalation into `Shipit.github_teams` authorization, one of the explicitly in-scope High-impact outcomes.
- Forging `push` events to enqueue `GithubSyncJob` for arbitrary stacks with attacker-chosen `expected_head_sha`, perturbing the sync state machine for repositories the attacker has no access to.

### Likelihood Explanation
Exploitation requires no credentials, no Shipit session, and no API token - only knowledge of an organization name configured in Shipit's `github:` block that has an empty `webhook_secret`, which is the documented default for organizations that haven't set one up. Any Shipit instance running the shipped multi-org configuration pattern with even one unconfigured org secret is exposed; the webhook endpoint is unauthenticated by design (it must accept anonymous GitHub deliveries), so this is directly reachable by an unprivileged network attacker.

### Recommendation
Bind the verified identity to the resource being written: require every configured organization to have a non-blank `webhook_secret` (fail closed instead of `return true unless webhook_secret`), and additionally verify that the `repository`/`organization` fields acted upon by the dispatched handler belong to the same organization whose secret produced a valid signature, rejecting the event otherwise.

### Proof of Concept
1. Configure Shipit with two organizations in `github:` (a common, documented pattern): `org-a` with no `webhook_secret` set, `org-b` with a real `webhook_secret` protecting a tracked stack/repository.
2. Send a POST to `/github/webhooks` with header `X-Github-Event: status` (no valid `X-Hub-Signature`, or any arbitrary value) and JSON body:
   ```json
   {
     "sha": "<target commit sha in org-b's repo>",
     "state": "success",
     "context": "required-ci-check",
     "target_url": "https://attacker.example.com",
     "repository": { "owner": { "login": "org-a" }, "full_name": "org-b/protected-repo" }
   }
   ```
3. `verify_signature` computes `repository_owner = "org-a"`, fetches `org-a`'s `GithubApp` (no secret), and `verify_webhook_signature` returns `true` unconditionally.
4. `create` dispatches the same payload to the `status` handler, which creates a `Status` for the commit named in the payload belonging to `org-b/protected-repo`, even though the request was never signed by `org-b`'s secret.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
