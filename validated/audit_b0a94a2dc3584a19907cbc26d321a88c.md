Based on my research, I found a genuine trust-boundary issue in the webhook verification flow that matches the requested bug class ("an organization that authenticated versus the repository that is written").

### Title
Webhook signature verification selects the signing organization from an unvalidated payload field, decoupling "org authenticated" from "repository acted upon" - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks which GitHub App configuration (and therefore which `webhook_secret`) to verify a webhook against using `repository_owner`, a value read straight out of the JSON body. Event handlers, however, act on the repository identified by `repository.full_name`/`repository.owner.login` inside that same body. Nothing enforces that these two payload readings must agree on which tenant/org the request is "for" versus which repository will actually be mutated, so a party holding a valid `webhook_secret` for one configured organization can forge a payload that authenticates against that org's secret while directing the resulting job at a stack belonging to a different, unrelated organization configured on the same Shipit instance.

### Finding Description
`verify_signature` computes the org used for signature verification directly from attacker-suppliable JSON, before any cryptographic check has occurred: [1](#0-0) [2](#0-1) 

`GitHubApp#verify_webhook_signature` only verifies that `request.raw_post` matches the HMAC computed with the secret belonging to whichever organization was selected by `repository_owner`: [3](#0-2) 

Shipit supports hosting multiple GitHub organizations/Apps from a single instance, each with its own `app_id`, `installation_id`, and `webhook_secret` (see the multi-org config format): [4](#0-3) 

Because `repository_owner` is derived from `repository.owner.login` (falling back to `organization.login`) while the downstream handlers (e.g. the push handler enqueuing `GithubSyncJob`, the status handler, membership handler, etc.) key off other fields of the same JSON body such as `repository.full_name`, an attacker who legitimately possesses the `webhook_secret` for Org A (e.g., because they compromised or were issued a webhook endpoint secret scoped only to Org A's installation) can craft a raw payload where the "owner" field used for HMAC-key selection says `"OrgA"` but the repository object used by the handler logic references a stack under Org B. The HMAC is computed over the entire raw body using Org A's key and will validate correctly (since the attacker knows that key), yet the handler that runs afterward operates on Org B's repository/stack.

This breaks the equality that should hold: **organization authenticated (key used to verify the HMAC) == organization whose repository is written (repository used by the handler to locate a Stack and enqueue jobs)**. Before the attack: an org's webhook secret authorizes actions only on that org's own repositories. After the crafted payload: the same secret can be used to trigger `GithubSyncJob`/status/check-run processing for a stack under a completely different, unrelated organization hosted on the same Shipit instance.

### Impact Explanation
Triggering `GithubSyncJob`, status updates, or check-run refreshes for another organization's stack is a cross-repository/cross-tenant write performed without any credential tied to that target organization — this squarely matches the "cross-repository writes" / unauthorized action criteria for High/Critical impact, since it lets a party in control of one tenant's webhook secret manipulate state (sync jobs, commit statuses, CI-driven auto-deploy pipelines) belonging to a different tenant they have no legitimate relationship with.

### Likelihood Explanation
This requires the deploying organization to run a multi-org Shipit configuration (explicitly documented and supported) and requires the attacker to already hold a valid `webhook_secret` for at least one of the hosted organizations — a credential weaker than full repository write access or an `ApiClient` token, but which the engine's own webhook endpoint treats as sufficient to freely choose which of the other configured organizations' repositories to affect, since the org-selection logic trusts the unauthenticated request body.

### Recommendation
After successfully verifying the HMAC signature for the organization selected via `repository_owner`, re-derive the "acting" organization from the verified payload and assert it is consistent with the organization whose secret validated the signature (i.e., confirm `repository.owner.login` / `repository.full_name`'s owner segment matches the org used to fetch `Shipit.github`). Reject the webhook if there is any mismatch between the org used to select the signing key and the org that owns the repository the handlers are about to act on.

### Proof of Concept
1. Configure Shipit with two organizations, `OrgA` and `OrgB`, each with its own `webhook_secret` (as in `config/secrets.development.shopify.yml`).
2. As an attacker who knows only `OrgA`'s `webhook_secret`, craft a `push` event JSON body where `repository.owner.login` (or `organization.login`) is `"OrgA"`, but the rest of the payload (e.g. `repository.full_name`) references a repository owned by `OrgB`, e.g. `"OrgB/some-stack"`.
3. Compute `X-Hub-Signature: sha1=<hmac>` over the raw body using `OrgA`'s known `webhook_secret`.
4. POST to `/webhooks` with header `X-Github-Event: push`. `verify_signature` calls `Shipit.github(organization: "OrgA")` (from `repository.owner.login`) and successfully verifies the HMAC using `OrgA`'s secret.
5. `Shipit::Webhooks.for_event('push')` handlers then process the same body and act on `repository.full_name == "OrgB/some-stack"`, enqueuing `GithubSyncJob` (or updating statuses/check runs) for `OrgB`'s stack — despite the attacker never possessing any credential for `OrgB`.

**Note on verification limits:** I was unable to inspect `app/models/shipit/webhooks/handlers/push_handler.rb` and `app/models/shipit/user.rb` in this session (tool read failed on the final iteration), so I could not directly confirm the exact field(s) the push/status/membership handlers use to resolve the target `Stack`/`Repository`, beyond what is inferable from `app/controllers/shipit/webhooks_controller.rb` and the webhook controller tests (`test/controllers/webhooks_controller_test.rb`), which show stack/repository resolution happening from the same JSON body used for `repository_owner`. Full confirmation of the exact handler code paths would benefit from a Devin session with full file access.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
