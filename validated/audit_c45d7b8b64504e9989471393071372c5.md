### Title
Block-reward share computed from post-epoch delegation state allows over-crediting a staker at the expense of others - (File: runtime/src/bank/partitioned_epoch_rewards/calculation.rs)

### Summary
`calculate_block_reward` (SIMD-0123 block-revenue-sharing) computes a staker's share of a vote account's `pending_delegator_rewards` as `stake / total_active_stake`, where `stake` is derived from the *current* `Delegation` object passed into the reward calculation at the moment rewards are computed (potentially at the epoch boundary or during snapshot-restore recalculation), while `total_active_stake` is a fixed snapshot taken at the *end of the rewarded epoch* (`RewardEpochDelegatedStakes`). This mirrors the Notional H-10 pattern: a per-account "current-state" numerator divided by a "snapshotted" denominator that were captured at different times, so growing the numerator after the snapshot lets one staker capture reward otherwise due to peers.

### Finding Description
`calculate_block_reward` divides `pending_delegator_rewards` between stake accounts delegated to a vote account using:
```
stake = delegation_effective_stake(delegation, rewarded_epoch, stake_history, ...)
total_active_stake = reward_epoch_delegated_stakes.delegated_stakes[vote_pubkey]   // fixed snapshot at end of rewarded_epoch
share = pending_delegator_rewards * stake / total_active_stake
``` [1](#0-0) 

The code's own comment acknowledges the divergence: "during recalculation, `distribution_epoch_vote_accounts` already includes updated stake activation values from after the new epoch calculation, so we need to use `RewardEpochDelegatedStakes` for the exact values at the end of the reward epoch" and later "if stake account has already received rewards, it's possible to have `stake > total_active_stake`" [2](#0-1) .

The `stake_delegations` vector fed into this computation is read live from the `StakesCache` (`stakes.stake_delegations_vec()`), not a frozen snapshot matched to `RewardEpochDelegatedStakes` [3](#0-2) . The same live-read pattern is used again during post-snapshot-restore recalculation via `get_epoch_params_for_recalculation`, which explicitly re-reads `stakes.stake_delegations_vec()` at recalculation time rather than reconstructing the original rewarded-epoch state [4](#0-3) .

Because Solana's stake `merge` instruction allows combining stake accounts delegated to the same vote account (with the merged amount becoming instantly "effective" once both delegations are fully active, as demonstrated by the `stake_merge_immediately_after_activation` test) [5](#0-4) , an unprivileged stake authority can inflate the raw `delegation.stake` value used in `calculate_block_reward` between the time the `RewardEpochDelegatedStakes` denominator snapshot was fixed and the time the numerator (`stake`) is (re)computed — for example during the snapshot-restore recalculation path, which re-derives `stake_delegations` from the live `StakesCache` rather than the epoch-end state.

### Impact Explanation
An attacker who merges additional already-active stake into a delegation targeting a given vote account after `RewardEpochDelegatedStakes` for that epoch has been fixed (but before/during block-reward recalculation) increases their numerator (`stake`) without a corresponding increase in the fixed denominator (`total_active_stake`). This produces a share of `pending_delegator_rewards` disproportionate to the stake actually delegated during the rewarded epoch, siphoning block-revenue-sharing rewards that should have gone to other delegators of the same validator. This is a concrete reward-misattribution/duplication class impact (one staker receives lamports that rightfully belong to others), consistent with the accepted impact categories.

### Likelihood Explanation
This requires the `block_revenue_sharing` (SIMD-0123) and Alpenglow-related feature gates to be active, and specifically exercises the snapshot-restore recalculation path (`initialize_after_snapshot_restore` / `get_epoch_params_for_recalculation`), which the code and tests confirm re-derives `stake_delegations` from current live state rather than the exact rewarded-epoch state. This is a validator-restart-dependent condition, not exploitable in ordinary steady-state block production, which reduces likelihood; however, the underlying arithmetic bug (numerator/denominator time mismatch) is unconditionally present in `calculate_block_reward`, and the code's own inline comments show the developers are aware `stake > total_active_stake` can occur, only defensively clamping the overflow, not the unfairness.

### Recommendation
Ensure the `stake` numerator used in `calculate_block_reward` is derived from the same point-in-time snapshot as `RewardEpochDelegatedStakes` (i.e., persist/reuse the exact per-delegation effective-stake values captured when `RewardEpochDelegatedStakes` was computed) rather than re-reading live `StakeAccount` delegation state from `StakesCache` during recalculation. Alternatively, reject or ignore stake-account mutations (merge/split) that occurred after `RewardEpochDelegatedStakes.epoch` was finalized when computing an individual account's numerator for block-reward distribution.

### Proof of Concept
1. Stand up a validator with `block_revenue_sharing` and Alpenglow active.
2. Staker A creates two fully-active stake accounts, `S1` and `S2`, both delegated to vote account `V`, each holding stake amounts that sum with other delegators' stake to `total_active_stake` recorded in `RewardEpochDelegatedStakes` for epoch `E`.
3. After epoch `E`'s `RewardEpochDelegatedStakes` snapshot is finalized (`reward_epoch_delegated_stakes.epoch == E`), but before/at a snapshot-restore recalculation event, Staker A merges `S2` into `S1` (`stake_instruction::merge`), instantly growing `S1`'s `Delegation.stake`.
4. Trigger `initialize_after_snapshot_restore`, which calls `get_epoch_params_for_recalculation` and re-reads `stakes.stake_delegations_vec()` live [6](#0-5) , feeding the now-inflated `S1.delegation.stake` into `calculate_block_reward` against the unchanged, pre-merge `total_active_stake` denominator.
5. Observe `S1`'s computed `block_reward` share exceeds what `S1` + `S2` combined would have earned under the original (pre-merge) accounting, at the expense of other delegators to `V` whose share of the fixed `pending_delegator_rewards` pool is correspondingly reduced.

    // includes updated stake activation values from after the new epoch
    // calculation, so we need to use `RewardEpochDelegatedStakes` for the exact
    // values at the end of the reward epoch.
    let (AlpenglowEpochType::Alpenglow {
        reward_epoch_delegated_stakes,
        ..
    }
    | AlpenglowEpochType::MigrationEpoch {
        reward_epoch_delegated_stakes,
        ..
    }) = ag_epoch_type
    else {
        debug!("Alpenglow must be enabled for block reward calculation");
        return 0;
    };
    let total_active_stake = reward_epoch_delegated_stakes
        .delegated_stakes
        .get(&vote_pubkey)
        .copied()
        .unwrap_or(0);
    if total_active_stake == 0 {
        0
    } else {
        let stake = delegation_effective_stake(
            delegation,
            rewarded_epoch,
            stake_history,
            new_warmup_cooldown_rate_epoch,
            use_fixed_point_stake_math,
        );
        // During recalculation, if stake account has already received rewards,
        // it's possible to have `stake > total_active_stake`. If
        // `pending_delegator_rewards` is a huge number, we could potentially
        // overflow a `u64`. We can also have individual rewards look greater
        // than the pending rewards. This is harmless in practice, but we
        // clamp it just to be safe
        (pending_delegator_rewards as u128 * stake as u128 / total_active_stake as u128)
            .try_into()
            .unwrap_or(u64::MAX)
            .min(pending_delegator_rewards)
    }

    /// Retrieves stake history and delegations for stake reward recalculation

    fn get_epoch_params_for_recalculation<'a>(
        &'a self,
        rewarded_epoch: Epoch,
        stakes: &'a Stakes<StakeAccount<Delegation>>,
    ) -> EpochRewardCalculateParamInfo<'a> {
        // Use `stakes` for stake-related info
        let stake_history = stakes.history().clone();
        let stake_delegations = stakes.stake_delegations_vec();

        // Use the VAT-filtered vote-account snapshot from epoch_stakes.
        // Recalculation should match the vote-account admission policy used for
        // distribution.
        let leader_schedule_epoch = self.epoch_schedule().get_leader_schedule_epoch(self.slot());
        let distribution_epoch_vote_accounts = self
            .epoch_stakes(leader_schedule_epoch)
            .expect("calculation should always run after Bank::update_epoch_stakes()")
            .stakes()
            .vote_accounts();
        let cached_vote_accounts =
            self.get_cached_vote_accounts(rewarded_epoch, distribution_epoch_vote_accounts);

        EpochRewardCalculateParamInfo {
            stake_history,
            stake_delegations,
            cached_vote_accounts,
        }
    }

    let mut current_slot = first_normal_slot + slots_per_epoch;
    context.warp_to_slot(current_slot).unwrap();
    context.warp_forward_force_reward_interval_end().unwrap();

    // iterate through the stakes at all, which means we can only test the
    // behavior of advancing credits observed if another stake is earning rewards

    let stake_lamports = 1_000_000_000_000;
    let base_stake_address =
        setup_stake(&mut context, &user_keypair, &vote_address, stake_lamports).await;
    check_credits_observed(&mut context.banks_client, base_stake_address, 100).await;
    context.increment_vote_account_credits(&vote_address, 100);

    let clock_account = context
        .banks_client
        .get_account(clock::id())
        .await
        .expect("account exists")
        .unwrap();
