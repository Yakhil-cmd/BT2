### Title
`StatusHandler#process` writes CI status to every stack sharing a SHA with no repository check, letting a status webhook from any repo in the same GitHub org trigger `ContinuousDeliveryJob` on an unrelated stack - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` looks up commits purely `Commit.where(sha: params.sha)` with no repository/stack scoping, and `WebhooksController#verify_signature` only validates the webhook's HMAC against the *organization*-level GitHub App secret, not the specific repository. Any repo belonging to an organization already onboarded to Shipit can therefore emit a validly-signed `status` webhook that mutates the CI state of a commit row belonging to a completely different stack, and if that victim stack has `continuous_deployment` enabled, `Status#schedule_continuous_delivery` will enqueue `ContinuousDeliveryJob` for it.

### Finding Description
The broken binding: the code should enforce `status.repository == commit.stack.repository` before writing/using a status, but it actually only enforces `status.repository.owner == commit.stack.repository.owner` (at the HTTP layer) and nothing at all at the handler layer.

- `WebhooksController#verify_signature` resolves the GitHub App by `repository_owner` (the org/user login from the payload) and calls `Shipit.github(organization: repository_owner).verify_webhook_signature(...)`, [1](#0-0) . This proves only that the payload was signed by GitHub for *some repository owned by that organization/login* — it says nothing about which repository within that org emitted it.
- `StatusHandler#process` then does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` with no filter on repository or stack at all [2](#0-1) .
- `create_status_from_github!` → `add_status` computes the new aggregate status and, on a state transition to `pending`/`success`, calls `stack.schedule_merges`, and via `Status#schedule_continuous_delivery` → `commit.schedule_continuous_delivery` triggers continuous delivery evaluation for that commit's stack [3](#0-2) [4](#0-3) .
- `ContinuousDeliveryJob#perform` only checks `stack.continuous_deployment?`, schedule windows, and `stack.occupied?` before calling `stack.trigger_continuous_delivery` — it performs no verification that the status that triggered it originated from the stack's own repository [5](#0-4) .

Exploit flow: git commit SHAs are content-addressed and are identical across any fork/clone/cherry-pick that reproduces the same blob/tree/parent/author/message data (e.g., a fork of the victim repo, or a shared "template" ancestor commit). An attacker who owns (or can push/label/comment on) any repository within the same GitHub organization already integrated with Shipit can cause a `status` event to be emitted for that repo with a `sha` that is bit-identical to a commit that also exists in the victim's tracked stack (via a shared fork ancestor, a cherry-pick, or an intentionally reproduced commit with matching author/committer/timestamps/tree). GitHub signs that webhook with the org-level secret, `verify_signature` passes, and `StatusHandler` blindly applies the state to **every** `Commit` row across all stacks with that SHA, including the victim's — irrespective of which repository actually authenticated the webhook.

None of the existing guards defend against this: `verify_signature` checks org identity, not repo identity; `drop_unhandled_event` and the `ExplicitParameters` schema (`requires :sha`, `:state`, etc.) only validate shape, not origin; there is no `Repository`/`stack_id` scoping anywhere in `StatusHandler` or in `Commit.where(sha:)`.

### Impact Explanation
A payload that authenticated for repository A (or any repo in A's org) can flip the CI status and — because `continuous_deployment` auto-ships newly green commits via `ContinuousDeliveryJob` — force an unauthorized deploy/merge/block on stack B, whose repository never emitted or authenticated that webhook. This is a cross-tenant write: "a payload for one repository mutating another's stack/commit," matching the Critical category (unauthorized deploy triggered on a victim stack). The blast radius is every stack in the same GitHub organization that has `continuous_deployment` enabled and that shares (or can be made to share) a commit SHA with a repository the attacker controls.

### Likelihood Explanation
The attacker must control (or have push/webhook-triggering ability on) at least one repository within a GitHub organization that Shipit already trusts (i.e., for which `Shipit.github(organization: ...)` has valid credentials/webhook secret configured) — this is a real but non-trivial precondition, since it requires the attacker's repo and the victim stack's repo to share an org-level webhook secret. Producing a colliding SHA is feasible via forks/cherry-picks/shared ancestor commits (not a SHA-1 collision attack, just identical git objects), which is a normal, low-cost operation. Given those two preconditions, the exploit is fully repeatable and does not require any Shipit credentials, session, or team membership.

### Recommendation
Scope `StatusHandler#process` (and the analogous check-run handler) to only update commits belonging to the stack(s) whose `Repository` matches the webhook's `repository.full_name`/`repository.owner.login`, e.g. filter `Commit.joins(stack: :repository).where(sha: params.sha, repositories: { owner: repository_owner, name: repository_name })` instead of a bare `Commit.where(sha: params.sha)`. Alternatively/additionally, make `verify_signature` scope validation to the exact repository the payload claims, not just the organization.

### Proof of Concept
```ruby
test "a status webhook from repo A cannot trigger continuous delivery on stack B sharing the same sha" do
  stack_a = shipit_stacks(:shipit)                     # repo attacker controls / authenticates webhooks for
  stack_b = shipit_stacks(:cyclimse)                    # victim stack, continuous_deployment enabled
  stack_b.update!(continuous_deployment: true)

  shared_sha = "deadbeef" * 5
  commit_a = stack_a.commits.create!(sha: shared_sha, ...)
  commit_b = stack_b.commits.create!(sha: shared_sha, ...)

  request.headers['X-Github-Event'] = 'status'
  body = {
    sha: shared_sha,
    state: 'success',
    context: 'continuous-integration/travis-ci',
    repository: { full_name: stack_a.repository.full_name, owner: { login: stack_a.repository.owner } }
  }.to_json

  assert_enqueued_with(job: ContinuousDeliveryJob, args: [stack_b]) do
    post :create, body:, as: :json
  end
end
```
Both sides of the intended invariant — `status.repository == commit.stack.repository` — should be equal before any state write; the test shows they diverge (`stack_a.repository != stack_b.repository`) yet `stack_b`'s commit is still updated and continuous delivery is still enqueued for `stack_b`.
