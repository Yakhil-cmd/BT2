### Title
Receipt size validation bypass allows creation and propagation of oversized receipts exceeding `max_receipt_size` - (File: `runtime/runtime/src/lib.rs`, `runtime/runtime/src/verifier.rs`)

### Summary
An unprivileged contract call can produce an `ActionReceipt`/`DataReceipt` that exceeds the protocol's `max_receipt_size` limit. Size validation is performed on the receipt *before* the runtime appends `output_data_receivers` (used for promise-chaining/value-return), so the resulting receipt can be pushed onto the chain and propagated across shards despite exceeding the configured resource-consumption bound. This is an acknowledged, unresolved bug (nearcore issue #12606).

### Finding Description
`validate_receipt` in `runtime/runtime/src/verifier.rs` checks `borsh::object_length(receipt) <= limit_config.max_receipt_size` only when called with `ValidateReceiptMode::NewReceipt`, and it must tolerate a known bypass in `ValidateReceiptMode::ExistingReceipt` mode, whose doc comment explicitly states: [1](#0-0) 

The bypass happens because, in `runtime/runtime/src/lib.rs`, after the function-call outcome and its `new_receipts` are validated/produced, the runtime mutates a receipt already in `result.new_receipts` by appending `output_data_receivers` from the *calling* action receipt — a step that occurs after the per-receipt size check has already happened: [2](#0-1) 

Similarly, `value_return` in the VM host functions only enforces `max_length_returned_data` (a much larger bound, e.g. 4 MiB) on the returned value, with no cross-check against the *receipt-level* `max_receipt_size` when that value is subsequently wrapped into a `DataReceipt`: [3](#0-2) 

The dedicated regression tests explicitly document that this bypass is real and currently unresolved, producing receipts above `max_receipt_size` via both the `promise_return` output-data-receiver-append path and the `value_return` path: [4](#0-3) [5](#0-4) 

### Impact Explanation
`max_receipt_size` exists specifically to bound the memory/CPU/network cost of processing and transmitting a single receipt (it appears alongside other resource-consumption bounds like `outgoing_receipts_usual_size_limit`, `max_arguments_length`, and `per_receipt_storage_proof_size_limit` in `core/parameters/res/runtime_configs/parameters.snap`). By bypassing this check, an unprivileged contract call can generate receipts larger than the protocol-intended cap, which get persisted to state, included in outgoing/incoming receipt proofs, and processed by validators — increasing memory and CPU usage beyond the configured bound. This matches the reported bug class (uncontrolled resource consumption from crafted input) directly mapped onto nearcore's receipt-size accounting mechanism. The tests confirm the runtime does not crash (so it is not an immediate DoS crash), but the core guarantee that `max_receipt_size` bounds receipt-processing cost is violated for a defined class of oversized receipts.

### Likelihood Explanation
Low-to-medium: reaching this bug only requires submitting a signed transaction that calls a `FunctionCall` action performing `promise_then`/`promise_return` or returning a value near the size limit — fully reachable via an ordinary RPC-submitted transaction with no special privileges, as demonstrated by `test_max_receipt_size_promise_return` and `test_max_receipt_size_value_return`.

### Recommendation
Move (or duplicate) the `max_receipt_size` check in `validate_receipt`/`ValidateReceiptMode::NewReceipt` to run *after* `output_data_receivers` are appended in `runtime/runtime/src/lib.rs` (i.e., re-validate the final receipt object right before it is added to `result.new_receipts` / before persisting/sending), and add an equivalent receipt-size-aware check for `value_return`-derived data receipts, closing out nearcore issue #12606 rather than only tolerating it via `ValidateReceiptMode::ExistingReceipt`.

### Proof of Concept [6](#0-5) 
Both `test_max_receipt_size_promise_return` and `test_max_receipt_size_value_return` deploy a standard test contract, then submit an ordinary signed `FunctionCall` transaction (`max_receipt_size_promise_return_method1` / `max_receipt_size_value_return_method`) sized so that the resulting receipt's base size is at the `max_receipt_size` limit; after `output_data_receivers`/return-value wrapping is applied post-validation, the receipt exceeds `max_receipt_size` and is nonetheless accepted and propagated, verified by `assert_oversized_receipt_occurred` scanning committed blocks for an oversized receipt.

fn test_max_receipt_size_promise_return() {
    init_test_logger();

    let account = create_account_id("account0");
    let account_signer = create_user_test_signer(&account);
    let mut env = TestLoopBuilder::new()
        .enable_rpc()
        .add_user_account(&account, Balance::from_near(10_000))
        .build();

    // Deploy the test contract
    let deploy_contract_tx = SignedTransaction::deploy_contract(
        101,
        &account,
        near_test_contracts::rs_contract().into(),
        &account_signer,
        env.rpc_node().head().last_block_hash,
    );
    env.rpc_runner().run_tx(deploy_contract_tx, Duration::seconds(5));

    // User calls a contract method
    // Contract method creates a DAG with two promises: [A -then-> B]
    // When promise A is executed, it creates a third promise - `C` and does a `promise_return`.
    // The DAG changes to: [C ->then-> B]
    // The receipt for promise C is a maximum size receipt.
    // Adding the `output_data_receivers` to C's receipt makes it go over the size limit.
    let base_receipt_template = Receipt::V0(ReceiptV0 {
        predecessor_id: account.clone(),
        receiver_id: account.clone(),
        receipt_id: CryptoHash::default(),
        receipt: ReceiptEnum::Action(ActionReceipt {
            signer_id: account.clone(),
            signer_public_key: account_signer.public_key().into(),
            gas_price: Balance::ZERO,
            output_data_receivers: vec![],
            input_data_ids: vec![],
            actions: vec![Action::FunctionCall(Box::new(FunctionCallAction {
                method_name: "noop".into(),
                args: vec![],
                gas: Gas::ZERO,
                deposit: Balance::ZERO,
            }))],
        }),
    });
    let base_receipt_template = action_receipt_v1_to_latest(&base_receipt_template);
    let base_receipt_size = borsh::object_length(&base_receipt_template).unwrap();
    let max_receipt_size = 4_194_304;
    let args_size = max_receipt_size - base_receipt_size;

    // Call the contract
    let large_receipt_tx = SignedTransaction::call(
        102,
        account.clone(),
        account.clone(),
        &account_signer,
        Balance::ZERO,
        "max_receipt_size_promise_return_method1".into(),
        format!("{{\"args_size\": {}}}", args_size).into(),
        Gas::from_teragas(300),
        env.rpc_node().head().last_block_hash,
    );
    env.rpc_runner().run_tx(large_receipt_tx, Duration::seconds(5));

    // Make sure that the last promise in the DAG was called
    let assert_test_completed = SignedTransaction::call(
        103,
        account.clone(),
        account,
        &account_signer,
        Balance::ZERO,
        "assert_test_completed".into(),
        "".into(),
        Gas::from_teragas(300),
        env.rpc_node().head().last_block_hash,
    );
    env.rpc_runner().run_tx(assert_test_completed, Duration::seconds(5));

    assert_oversized_receipt_occurred(&env.validator());
}
