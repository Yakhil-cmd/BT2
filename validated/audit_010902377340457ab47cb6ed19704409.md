### Title
Webhook signature verified against `repository.owner.login`'s secret while stack resolution uses independently-read `repository.full_name`, allowing a push payload to sync an unrelated victim stack - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects the HMAC secret using `repository_owner` (`params.dig('repository','owner','login')`), while `Handler#stacks` resolves the target stacks using a completely separate field, `payload.dig('repository','full_name')`, via `Repository.from_github_repo_name`. Nothing binds these two values together, so an attacker who owns any GitHub org configured in Shipit with a blank `webhook_secret` can forge a payload whose `repository.owner.login` is their own (unconfigured-secret) org, passing signature verification, while `repository.full_name` names a victim org/repo, causing `PushHandler#process` to call `victim_stack.sync_github` for a repository they do not control.

### Finding Description
The binding the codebase implicitly assumes is:
`payload['repository']['owner']['login'] == payload['repository']['full_name'].split('/').first`

This is never enforced. Trace:
- `WebhooksController#verify_signature` computes `repository_owner` purely from `params.dig('repository','owner','login')` (or `organization.login`) and fetches `Shipit.github(organization: repository_owner)`, then calls `verify_webhook_signature`: [1](#0-0) [2](#0-1) 
- `GitHubApp#verify_webhook_signature` returns `true` unconditionally when the resolved org's `@webhook_secret` is blank: [3](#0-2) 
- Once verification passes, `WebhooksController#create` dispatches the raw parsed `params` (the full JSON payload, not just the owner field) to the handler: [4](#0-3) 
- `Handler#stacks` and `#repository_name` re-read the payload independently, using `payload.dig('repository', 'full_name')` — a different key than the one used for signature selection: [5](#0-4) 
- `Repository.from_github_repo_name` splits this attacker-supplied `full_name` on `/` and looks up any repository by that owner/name: [6](#0-5) 
- `PushHandler#process` then calls `stack.sync_github(expected_head_sha: params.after)` for every non-archived stack on the matching branch of the resolved (victim) repository: [7](#0-6) 

Exploit request: POST `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" },
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>"
}
```
If `attacker-org` is configured in Shipit's GitHub app config with no `webhook_secret`, `verify_signature` passes (`true unless webhook_secret`), and the handler then resolves and syncs `victim-org/victim-repo`'s stacks using the attacker-controlled `after` SHA, with no cross-check that `victim-org == attacker-org`.

None of the existing guards catch this: `drop_unhandled_event` only checks the event type, `verify_signature` only checks the signature against the owner field's secret (which is satisfiable when that secret is blank), and there is no `ExplicitParameters` or model validation anywhere comparing `repository.owner.login` to `repository.full_name`.

### Impact Explanation
An attacker controlling any GitHub org configured in Shipit with an empty `webhook_secret` can trigger `GithubSyncJob`/`sync_github` for an arbitrary victim stack on any branch, forcing an unauthenticated write against a repository the attacker did not authenticate for. This is a cross-tenant "payload for one repository mutating another's stack" scenario explicitly called out as Critical in the rules, since it lets one repository/org's unauthenticated (secret-less) webhook drive sync/deploy pipeline state for an unrelated victim repository. It is repeatable against any victim repo/branch known to the attacker and scales to every stack hosted by the Shipit instance, as long as one org exists with a blank webhook secret.

### Likelihood Explanation
Requires: (1) the Shipit instance to have at least one GitHub org/app configured with a blank `webhook_secret` (a documented and plausible misconfiguration, explicitly the premise of the question and directly enabled by the `return true unless webhook_secret` short-circuit), and (2) the attacker to control (or simply register) that org in a multi-tenant Shipit deployment, or knowledge that some configured org has no secret set. No Shipit session, API token, or GitHub secret is needed — only the ability to send an HTTP POST to `/webhooks`, which is explicitly in-scope for the unprivileged attacker model. Cost is a single crafted HTTP request; the attack is trivially repeatable.

### Recommendation
Bind signature verification and stack resolution to the same value. Concretely, in `Shipit::WebhooksController#create`/`Handler`, verify that `payload.dig('repository','owner','login')` matches the owner segment of `payload.dig('repository','full_name')` before processing, or derive `repository_owner` and the handler's resolved repository from the same parsed field, and reject the request (422) on mismatch. Additionally, consider making a blank/misconfigured `webhook_secret` fail closed (reject the webhook) rather than defaulting to verified.

### Proof of Concept
Minitest under `test/controllers/webhooks_controller_test.rb` style:
```ruby
test "push webhook with owner/full_name mismatch does not sync an unrelated victim stack" do
  attacker_org = "attacker-org" # configured with no webhook_secret in test github app config
  victim_stack = shipit_stacks(:shipit)
  victim_full_name = victim_stack.repository.full_name

  payload = {
    "repository" => { "owner" => { "login" => attacker_org }, "full_name" => victim_full_name },
    "ref" => "refs/heads/#{victim_stack.branch}",
    "after" => "0" * 40
  }

  # Equality under test BEFORE: payload['repository']['owner']['login'] (attacker_org)
  #                              != victim_full_name.split('/').first (victim owner)
  assert_not_equal attacker_org, victim_full_name.split('/').first

  assert_enqueued_with(job: GithubSyncJob, args: [{ stack_id: victim_stack.id, expected_head_sha: payload["after"] }]) do
    post shipit.webhooks_path, params: payload.to_json,
      headers: { 'X-Github-Event' => 'push', 'Content-Type' => 'application/json' }
  end

  assert_response :ok
end
```
This asserts the broken binding directly: the signature-selecting field (`attacker_org`) and the stack-resolving field (`victim_full_name`'s owner) diverge, yet `GithubSyncJob` is still enqueued for the victim's `stack_id`.
