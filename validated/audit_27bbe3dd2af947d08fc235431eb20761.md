### Title
Membership webhook `team.id` collision lets an attacker-owned org grant its GitHub users membership in a privileged `Shipit.github_teams` `Team` row - ([File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`MembershipHandler#find_or_create_team!` resolves `Team` solely by `github_id` from the webhook payload, with no check that the payload's `organization.login` matches the `Team#organization` already stored on that row. In a multi-tenant Shipit deployment (multiple GitHub orgs configured under `secrets.github`), any configured-but-attacker-owned org can send a genuinely-signed `membership` webhook whose `team.id` collides with a privileged team's `github_id`, causing `Team.find_or_create_by!(github_id:)` to return the existing privileged row and add the attacker's chosen GitHub login as a member of it.

### Finding Description
The broken binding: the code assumes `params.team.id == <privileged Team>.github_id` implies `params.organization.login == <privileged Team>.organization`, but nothing enforces that equality.

Path: `POST /webhooks` → `WebhooksController#verify_signature` picks the GitHub App config via `repository_owner`, which for membership events falls back to `params.dig('organization','login')` [1](#0-0) , and verifies the HMAC using `Shipit.github(organization: repository_owner)`'s secret [2](#0-1) . This only proves the request came from *some* org configured in `secrets.github` — it says nothing about which `team.id` is legitimate for that org. The dispatched handler is `MembershipHandler`, whose `params` schema only requires `team.id`/`name`/`slug`/`url`, `organization.login`, and `member.login` — all attacker-supplied fields inside a payload the attacker's own org signs [3](#0-2) .

`find_or_create_team!` then does:
```ruby
Team.find_or_create_by!(github_id: params.team.id) do |team|
  team.github_team = params.team
  team.organization = params.organization.login
end
``` [4](#0-3) 
The block only runs on *creation*. If a `Team` row with that `github_id` already exists (e.g. a privileged team pre-populated via `Shipit.github_teams` at boot, which calls `Team.find_or_create_by_handle` using real GitHub API lookups [5](#0-4)  and `app/models/shipit/team.rb` `find_or_create_by_handle`/`fetch_and_create_from_github` [6](#0-5) ), `find_or_create_by!` simply returns that existing row untouched — no organization comparison is performed anywhere in `Team` or `MembershipHandler#process`.

`process` then does `team.add_member(member)` where `member = User.find_or_create_by_login!(params.member.login)` [7](#0-6)  — `params.member.login` is fully attacker-controlled and resolves via a real, global GitHub API user lookup (users aren't org-scoped) [8](#0-7) . `Membership` has no organization-consistency validation, only a `user_id` uniqueness-per-team check [9](#0-8) .

Attacker request: send `POST /webhooks` with `X-Github-Event: membership`, signed with attacker-owned Org B's webhook secret, body `{"action":"added","team":{"id":<guessed/known github_id of privileged team>, "name":"x","slug":"x","url":"..."},"organization":{"login":"org-b"},"member":{"login":"<attacker-github-login>"},"repository":{"owner":{"login":"org-b"}}}`. If `<guessed id>` collides with a real privileged team's `github_id` (GitHub team IDs are small sequential integers, easily brute-forced or already known if the attacker was previously a legitimate member of any GitHub team and observed its ID), the existing privileged `Team` row is fetched and the attacker's own GitHub login becomes a member.

Why existing guards fail: `verify_signature` authenticates *which org* sent the request, not *which team* the request may reference; there is no cross-check between `organization.login` and the resolved `Team#organization` in `find_or_create_team!`, `Team`, or `Membership`. `User#authorized?` trusts team membership alone, without regard to how/when that membership was created: `teams.where(id: Shipit.github_teams.map(&:id)).exists?` [10](#0-9) .

### Impact Explanation
Once the `Membership` row is created, the attacker logs in to Shipit via normal GitHub OAuth as the GitHub login they specified in the webhook. `force_github_authentication` calls `current_user.authorized?`, which now returns true because the user belongs to a `Team` whose `id` is in `Shipit.github_teams` [11](#0-10) . This is authentication/authorization bypass into whatever privileges `Shipit.github_teams` membership grants across the whole instance (not scoped to a single repository) — matching the "High: escalation into `Shipit.github_teams` authorization" category. Repeatable per attacker-controlled GitHub login, against any privileged team whose `github_id` the attacker can guess.

### Likelihood Explanation
Preconditions: the Shipit deployment must be multi-tenant (multiple orgs configured under `secrets.github`, so a real, separate, attacker-controlled org's webhook secret is usable to hit `Shipit.github(organization: repository_owner)` successfully) and `Shipit.github_teams` must be non-empty (i.e. team-restricted authorization is in use) — the default single-org threat model this question targets. GitHub team IDs are sequential/low, so brute-forcing a match is feasible offline (no live GitHub calls needed to attempt collisions; only success requires no rate limiting on `/webhooks`, which is out of scope to evaluate here). Attacker cost is low: they only need control of one legitimately configured org's webhook channel, which the ruleset explicitly grants as in-scope attacker capability.

### Recommendation
In `MembershipHandler#find_or_create_team!`, verify that any existing `Team` matched by `github_id` belongs to the same `organization` as `params.organization.login` before acting on it (e.g. raise/reject on mismatch, or scope the lookup by `github_id` **and** `organization`). Additionally, consider validating in `Team` that `github_id` uniqueness is enforced per-organization semantics consistent with GitHub's actual namespace, and add a model-level guard preventing `add_member`/`Membership` creation when the webhook's asserted organization does not match the team's stored organization.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (conceptual addition)
test "membership webhook cannot add member to a team owned by a different org" do
  privileged_team = shipit_teams(:shopify_developers) # organization: 'shopify', github_id: X
  attacker_org = 'attacker-org' # configured in secrets.github but distinct tenant

  @request.headers['X-Github-Event'] = 'membership'
  payload = {
    action: 'added',
    team: { id: privileged_team.github_id, name: 'x', slug: 'x', url: 'http://example.com' },
    organization: { login: attacker_org },
    member: { login: 'attacker-login' },
    repository: { owner: { login: attacker_org } }
  }.to_json

  # signature genuinely computed with attacker_org's real webhook secret
  Shipit.github(organization: attacker_org).expects(:verify_webhook_signature).returns(true)
  Shipit.github.api.stubs(:user).with('attacker-login').returns(stub(id: 999, login: 'attacker-login', name: 'A', email: 'a@a.com', avatar_url: '', url: ''))

  assert_no_difference -> { Team.count } do
    post :create, body: payload, as: :json
  end

  refute privileged_team.members.exists?(login: 'attacker-login'),
    "attacker gained membership in a Team belonging to organization=#{privileged_team.organization} via org=#{attacker_org}"
end
```
Binding to assert before/after: `privileged_team.organization` ("shopify") vs `payload["organization"]["login"]` ("attacker-org") must remain unequal, yet `Membership.exists?(team: privileged_team, user: attacker_user)` becomes true after the request — demonstrating the missing organization check in `find_or_create_team!` / `process`.
