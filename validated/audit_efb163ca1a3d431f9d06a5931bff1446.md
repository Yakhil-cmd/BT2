Confirmed root cause: Shipit supports a multi-tenant GitHub configuration where each organization key under `secrets.github` has its own `webhook_secret` (`Shipit.github_app_config` / `Shipit.github`), and `WebhooksController#verify_signature` selects which organization's secret to verify the HMAC against using `repository_owner`, which is read from the same untrusted JSON payload (`params.dig('repository', 'owner', 'login')`) that later determines which `Repository`/`Stack` the event handler acts on via `Handler#repository_name` (`payload.dig('repository', 'full_name')`).

### Title
Webhook signature verified against attacker-chosen organization secret while handlers act on an independently attacker-controlled repository field - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
The multi-tenant webhook verification path selects the HMAC secret using `repository.owner.login` from the unauthenticated JSON body, but the handlers that mutate state key off the separate `repository.full_name` field from that same unauthenticated body. Because these are two independent, attacker-supplied strings in one unsigned-until-verified payload, and verification only proves the request was signed by *some* configured organization's secret (not that it matches the acted-upon repository), an attacker who controls (or has compromised) the webhook secret for one onboarded GitHub organization can forge a request whose `owner.login` matches their own org (to pass `verify_signature`) while `full_name` names a stack belonging to a different, victim organization also onboarded to the same Shipit instance.

### Finding Description
`WebhooksController#verify_signature` computes: [1](#0-0) 
using `repository_owner = params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`, then calls `Shipit.github(organization: repository_owner).verify_webhook_signature(...)`. `Shipit.github` resolves a distinct `GitHubApp` (and distinct `webhook_secret`) per organization key configured in `secrets.github`: [2](#0-1) 

Once verification passes, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` dispatches the *entire raw params hash* to handlers, e.g. `PushHandler`, whose base class resolves the target `Repository`/`Stack` set via: [3](#0-2) 
i.e. `payload.dig('repository', 'full_name')` — a completely different JSON field than the one used for signature-org selection. `Repository.from_github_repo_name` then splits this attacker-controlled string on `/` to look up any repository record in the database: [4](#0-3) 

Equality broken: the binding the system relies on is *organization whose secret authenticated the request* == *repository the handler writes to*. In the single-tenant/legacy config this holds because there is only one secret for the whole instance, so `owner.login` doesn't select anything. But under the documented multi-org config schema (`Shipit.github_app_config`, keyed by organization, each with its own `webhook_secret`), the two fields are never cross-checked against each other, so the equality no longer holds.

### Impact Explanation
An attacker who legitimately controls one organization/GitHub App onboarded to a shared Shipit instance (and therefore knows or can obtain that organization's `webhook_secret`, e.g. by configuring the GitHub App they own themselves) can sign a payload with `repository.owner.login` set to their own org and `repository.full_name` set to `victim-org/some-repo`. This lets them trigger `GithubSyncJob` for the victim's stack (forcing a resync from a spoofed `expected_head_sha`), or drive other handlers keyed by `full_name` (pull_request label/closed handlers touching `Repository.from_github_repo_name(params.repository.full_name)`) against a repository/stack they do not own — a cross-repository write/trigger performed with credentials that were only ever proven valid for a different repository's organization. This matches the "Critical: cross-repository writes / unauthorized deploy" category, since sync jobs can influence which commits are considered deployable and can be chained toward triggering deploy actions on a stack the attacker doesn't control.

### Likelihood Explanation
Requires the deployment to use the multi-organization `github` config schema (more than one org key under `secrets.github`) and requires the attacker to control (or have compromised) the webhook secret of at least one onboarded organization — a realistic scenario for any shared/multi-tenant Shipit instance serving several GitHub orgs, since each org's own administrators legitimately hold their own app's webhook secret. No GitHub App private key, `ApiClient` token, or Shipit session is needed, satisfying the "unprivileged attacker" bar for this class of finding.

### Recommendation
After `verify_webhook_signature` succeeds, re-derive `repository_owner` a second time from the field actually consumed by handlers (`repository.full_name`'s owner segment) and assert it is identical to the organization whose secret verified the signature, rejecting the request otherwise. Alternatively, verify the signature once per distinct organization implied by the payload and require all organization-identifying fields (`repository.owner.login`, `organization.login`, `repository.full_name`'s owner) to agree before dispatch.

### Proof of Concept
1. Shipit instance configured with two organizations, `org-a` and `org-b`, each with its own `webhook_secret` under `secrets.github` (multi-tenant schema per `Shipit.github_app_config`).
2. Attacker controls `org-a`'s GitHub App and therefore its `webhook_secret`.
3. Attacker POSTs to `/webhooks` with `X-Github-Event: push` and a body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker chosen sha>",
  "repository": { "owner": { "login": "org-a" }, "full_name": "org-b/victim-repo" }
}
```
4. `X-Hub-Signature` is computed with `org-a`'s `webhook_secret`.
5. `verify_signature` resolves `Shipit.github(organization: "org-a")` and the signature checks out, so the request passes.
6. `PushHandler#process` resolves stacks via `Handler#repository_name` = `"org-b/victim-repo"`, and enqueues `GithubSyncJob` against `org-b`'s stack, even though the request was never signed by `org-b`'s secret. [5](#0-4)

```ruby
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
```

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
