## Analysis

The reported bug is a **merkle-tree context-binding failure**: `MultiMerkleDistributor.claim()` hashes `keccak256(index, account, amount)` into a leaf without binding it to the specific `questID`/`period` the tree belongs to, so a leaf/proof valid in one tree can be replayed against a different (wrong) merkle root if the wrong tree is registered for a given context.

ocore's own core-protocol merkle-proof primitives have the exact same structural weakness: the leaf format is opaque to the verifier and no context id is bound into the hash by the protocol itself.

### Relevant ocore code

`merkle.verifyMerkleProof(element, proof)` in [1](#0-0)  only checks that `element` hashes up the sibling chain to `proof.root` — it has no notion of which "tree"/round/context the element belongs to; that binding is entirely up to whoever constructs `element`.

This primitive is exposed to oscript/AA authors two ways:

1. **`is_valid_merkle_proof(element, proof)`** formula operator, evaluated in [2](#0-1) . The AA author supplies both `element` and `proof` (including `proof.root`) directly from trigger data, and is fully responsible for separately comparing `proof.root` against a trusted, context-specific root (e.g., a state var keyed by round/asset). Nothing in ocore enforces that the root belongs to the round/asset the caller thinks it does.

2. **`['in merkle', [addresses, feed_name, element, min_mci]]`** address-definition operator, evaluated in [3](#0-2) . Here the accepted root is checked with `dataFeeds.dataFeedExists(arrAddresses, feed_name, '=', proof.root, min_mci, objValidationState.last_ball_mci, false, cb2)` — i.e. it accepts the proof as long as the oracle **ever** posted that exact root to that feed name within the mci window, with no requirement that it's the *current*/*latest* round's root, and no protocol-enforced linkage between the `element` content and any specific period/asset/round identifier.

Because the leaf (`element`) format and any "round"/"context" discriminator are entirely up to the oscript author to embed (exactly as `balance-tree.ts`/`MultiMerkleDistributor.sol` originally omitted `questID`/`period` from the leaf), an AA that manages sequential merkle-based reward/whitelist rounds and stores each round's root under the same oracle/feed_name (or the same state-var namespace) is vulnerable to leaves from an old/wrong round being validated as if they belonged to the currently active round — enabling reuse of a stale (or wrong-context) merkle proof to authorize a payout or authentication that should only be valid for a different round/asset. The double-spend/anti-replay protection for a given leaf (e.g. "already claimed index X") must likewise be implemented by the AA author using a state var keyed only by whatever fields the author chose to hash — if the leaf/element doesn't itself encode the round id, the anti-replay bitmap can collide across rounds just like the original Solidity bug.

### Why this matches the "medium" bar

- **Root cause parity**: identical class of bug — hash/proof leaf omits a context discriminator (`questID`/`period` in the Solidity report ↔ round/asset/context id in the oscript case), and the verifier (`verifyMerkleProof` / `dataFeedExists`) has no protocol-level way to enforce it.
- **Reachable by an unprivileged party**: any AA author designing a merkle-based airdrop/claim/whitelist AA using `is_valid_merkle_proof` or `in merkle` inherits this footgun; a malicious trigger sender can supply a proof/element from a stale or foreign tree if the AA's own logic (mirroring the original vulnerable Solidity contract) fails to bind context into the leaf.
- **Impact**: unauthorized/duplicate AA fund payout (analogous to "wrong rewards claimed") is possible if the AA's leaf format is under-specified — a concrete AA-fund-loss scenario. [1](#0-0) [2](#0-1) [3](#0-2)

### Title
Merkle-proof primitives (`is_valid_merkle_proof` / `in merkle`) do not bind proofs to a context identifier, enabling cross-round/cross-context replay in AA-based merkle distributions - (File: merkle.js, formula/evaluation.js, definition.js)

### Summary
ocore's merkle-proof verification (`merkle.verifyMerkleProof`), and its two exposed entry points — the oscript formula function `is_valid_merkle_proof` and the address-definition operator `in merkle` — validate only that `hash(element)` chains up to a claimed root. Neither the core verifier nor the oracle/data-feed lookup (`dataFeedExists`) enforces that the accepted root corresponds to the specific round/period/asset context the calling AA intends. This mirrors the "MultiMerkleDistributor" bug class: the leaf format must itself embed a context id (round/questID/asset) or a wrong/stale tree's proof can be validated as belonging to the current context.

### Finding Description
`merkle.verifyMerkleProof` (`merkle.js:84-102`) treats `element` as an opaque string and only proves membership under `proof.root`; it has zero knowledge of "which tree" that root should represent. The two protocol-level consumers pass this responsibility fully to the AA/definition author:
- `is_valid_merkle_proof` (`formula/evaluation.js:1768-1806`) lets the caller supply the `proof` (including `root`) straight from trigger data; the AA is expected to separately compare `proof.root` to a trusted, context-scoped value it stored itself.
- `in merkle` (`definition.js:1004-1020`) accepts a proof if `proof.root` was *ever* posted by the named oracle(s) to `feed_name` within the mci window (`dataFeeds.dataFeedExists(... '=', proof.root ...)`), with no built-in restriction that it be the *current* round's root.

If an AA reuses a single oracle/feed_name/state-var namespace across successive reward rounds/periods/quests without embedding the round id inside the hashed `element` (or without re-checking `proof.root` against the round-specific stored root), a leaf that was valid for an earlier round can still verify successfully in a later round — because nothing in the protocol layer ties the leaf to a round/context.

### Impact Explanation
An AA implementing periodic merkle-based reward distribution, whitelisting, or private-payment-style claim mechanisms using `is_valid_merkle_proof`/`in merkle` can be tricked into approving a claim/authorization intended for a different round or asset, leading to unauthorized AA fund payouts or double-claims — the same "wrong rewards claimed" impact described in the source report, translated to AA fund loss.

### Likelihood Explanation
Likelihood is low-to-medium: it requires an AA author to (a) use merkle-proof primitives for a multi-round/multi-context distribution and (b) fail to embed the round/context id in the leaf or fail to bind the accepted root to the current round via a state var — a plausible but avoidable implementation mistake, exactly like the original Solidity report's medium-risk rating.

### Recommendation
Document/require that any AA using `is_valid_merkle_proof` or `in merkle` for sequential/periodic distributions must (1) include the round/period/questID inside the hashed leaf `element`, and (2) explicitly compare `proof.root` against a state var scoped to that exact round rather than relying on `in merkle`'s "was ever posted" oracle check. Consider tightening `dataFeedExists`/`in merkle` semantics (or adding a variant) that only matches the *latest* value for a feed rather than any historical value, reducing the chance that stale roots remain acceptable indefinitely.

### Proof of Concept
1. An AA stores merkle root `R1` for round 1 rewards via a data feed posted by its own oracle/definer address, and uses `['in merkle', [[oracle_addr], 'rewards_root', trigger.data.leaf]]` in its address definition (or `is_valid_merkle_proof` in its bytecode) to authorize a payout keyed only by `(index, account, amount)` — no round id in the leaf.
2. Round 1 completes; the AA posts a new root `R2` for round 2 to the same `feed_name`.
3. A user who was part of round 1's tree replays their old leaf+proof for `R1`. Under `in merkle` semantics (`dataFeedExists` with `'='`), `R1` is still "in" the feed's history (within the mci window), so the proof still verifies even though the AA intended only `R2` to be currently valid — resulting in an unintended payout for a stale round if the AA's own state tracking doesn't separately gate by round.

function verifyMerkleProof(element, proof){
	// Node-as-Leaf issue might matter in some cases
	try {
		var index = proof.index;
		var the_other_sibling = hash(element);
		for (var i = 0; i < proof.siblings.length; i++) {
			// this also works for duplicated trailing nodes
			if (index % 2 === 0)
				the_other_sibling = hash(the_other_sibling + proof.siblings[i]);
			else
				the_other_sibling = hash(proof.siblings[i] + the_other_sibling);
			index = Math.floor(index / 2);
		}
		return (the_other_sibling === proof.root);
	}
	catch (e){
		return false;
	}
}
