### Title
Malicious swap routes can turn strategy authorization into arbitrary wallet token transfers - (File: contracts/controller/src/strategies/swap.rs)

### Summary
A route supplied to `swap_collateral`, `swap_debt`, `repay_debt_with_collateral`, or `multiply` can cause code below the caller’s authorization tree to request additional authorization from that same caller. If the victim signs the authorization tree produced by simulation, an attacker-controlled route contract can transfer unrelated wallet assets while the lending strategy still succeeds.

### Finding Description
`Controller::swap_collateral` accepts caller-controlled `swap` bytes, authenticates `caller`, verifies account ownership or delegation, and forwards the route into the strategy flow. [1](#0-0) [2](#0-1) 

The controller grants the configured router only one exact transfer of the strategy input token from the controller, but then invokes `execute_strategy` with the attacker-supplied route payload. [3](#0-2) 

The router treats route-selected pool addresses as executable venue contracts: each swap operation reads `pool`, `token_in`, and `token_out` from the route asset table and dispatches the hop to that selected address. [4](#0-3) 

A malicious venue can therefore execute a token transfer from the victim to the attacker during the strategy, and Soroban records that `from.require_auth()` call as a child of the victim’s existing `swap_collateral` authorization rather than as the expected router-input transfer. [5](#0-4) 

The repository’s threat model confirms that route destinations are not allowlisted and that such a child transfer executes when the caller signs the poisoned authorization tree. [6](#0-5) 

### Impact Explanation
This is theft of user funds beyond the strategy amount: the malicious hop can target any token contract that accepts the victim’s authorization, including assets unrelated to the lending markets. [7](#0-6) [8](#0-7) 

The measured-output check, route minimum, and final account risk check do not bound this loss because the stolen transfer is outside the router’s input/output accounting. [9](#0-8) 

### Likelihood Explanation
Exploitation requires the victim to sign a transaction whose simulated authorization tree contains the malicious child invocation, so it is a phishing/signing-UX attack rather than an unauthenticated direct theft. [10](#0-9) 

The likelihood is still material because the route is an opaque byte payload to the controller, route destinations are intentionally unconstrained, and a fair-looking swap output can make the malicious transaction appear economically normal. [11](#0-10) [12](#0-11) 

### Recommendation
Wallets and SDKs that build these transactions must decode the complete Soroban authorization tree and reject any child invocation other than the expected protocol operations. [13](#0-12) 

For protocol-level mitigation, route execution should be restricted to a governed registry of known venue/pool contracts, or strategy routes should be isolated so untrusted venue code cannot execute beneath the account owner’s authorization context. [12](#0-11) 

### Proof of Concept
1. Victim owns a lending account with USDC collateral and holds an unrelated token that is not listed by the protocol. [14](#0-13) 
2. Attacker deploys a fake pool whose `swap` method calls `token.transfer(victim, attacker, wallet_balance)`. [15](#0-14) 
3. Attacker gives the victim a USDC-to-ETH route naming that fake pool while arranging a fair output amount so the strategy’s output checks pass. [16](#0-15) 
4. Simulation records the fake pool’s wallet transfer as a child of the victim’s `swap_collateral` authorization. [17](#0-16) 
5. If the victim signs that tree, the transaction both completes the collateral swap and moves the victim’s unrelated token balance to the attacker. [18](#0-17) [19](#0-18)

fn enforced_auth_moves_the_wallet_token_only_when_the_signed_tree_lists_the_rogue_transfer() {
    let s = Scene::new();

    // Control: a pool that touches nothing passes with the honest root-only tree.
    let benign = s.route_through_pool_stealing(0);
    s.try_swap_with_signed_tree(&benign, &[])
        .expect("the honest tree authorizes an honest route");
    assert_eq!(s.wallet(&s.alice), WALLET_BALANCE);

    // Rogue pool, honest tree: the host refuses the transfer and the whole call rolls back.
    s.t.env.mock_all_auths_allowing_non_root_auth();
    let rogue = s.route_through_pool_stealing(WALLET_BALANCE);
    let usdc_before = s.t.supply_balance_raw(ALICE, "USDC");
    let refused = s
        .try_swap_with_signed_tree(&rogue, &[])
        .expect_err("a transfer outside the signed tree is unauthorized");
    std::println!("rogue transfer under the honest tree = {refused:?}");
    assert!(
        refused.is_type(ScErrorType::Auth) || refused.is_type(ScErrorType::Context),
        "expected a host auth failure, got {refused:?}"
    );
    assert!(s
        .diagnostics()
        .contains("Unauthorized function call for address"));
    assert_eq!(s.wallet(&s.alice), WALLET_BALANCE);
    assert_eq!(s.wallet(&s.attacker), 0);
    assert_eq!(s.t.supply_balance_raw(ALICE, "USDC"), usdc_before);

    // Same route, with the tree that simulation returned.
    let stolen_transfer = MockAuthInvoke {
        contract: &s.wallet_token,
        fn_name: "transfer",
        args: (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),

**File:** docs/explanation/threat-model.md (L144-165)
```markdown
Router swaps settle measured input/output changes. The controller grants
one exact input-transfer invocation, not a token allowance, and refunds
unspent input still held by the controller. The router checks its payload
minimum against output after fees but before payout; its own residuals
follow a capped admin-revenue policy. The controller requires positive
measured output and final account risk, not an independent slippage bound.
A compromised router may consume authorized input for dust output while the
final account passes its risk gates. Exposure is bounded by routed funds and
those gates, not by an independent controller slippage limit.

That bound covers the controller's own grant only. The router calls the pool
and token addresses its payload names and keeps no allowlist of them, so a
route can put third-party code on the call stack below the caller's
authorization. A token transfer that such code makes from the caller is
recorded by an honest simulation as a child of the caller's authorization
entry, and it executes if the caller signs that tree. The loss is then the
caller's wallet, not the routed amount, and neither the payload minimum nor the
final risk gate bounds it. An honest swap strategy gives the caller no child
entry, and a direct router swap gives exactly one input transfer. A client must
decode the route it signs and refuse an authorization tree with any other
child. The direct `execute_strategy` path has the same exposure for every swap
user.
```
