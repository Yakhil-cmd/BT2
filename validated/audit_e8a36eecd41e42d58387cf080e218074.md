### Title
Cross-stack disclosure of build/deploy status via unscoped CCMenu API token - (File: `app/controllers/shipit/ccmenu_url_controller.rb`, `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
The CCMenu integration issues an `ApiClient` token that is presented to the user as being scoped to a single stack, but the token is created without any `stack_id`, and the endpoint that consumes it does not enforce stack scoping at all. Any holder of a single CCMenu token can use it to read the CI/deploy status of every stack in the Shipit instance, not just the one it was generated for.

### Finding Description
`Shipit::CCMenuUrlController#fetch` mints a token for a given stack, embedding `stack_id` only in the *URL path* used for later requests, but the backing `ApiClient` record is created without a `stack` association: [1](#0-0) 

`ApiClient.find_or_create_by!(creator: current_user, name: 'CCMenu Client')` looks up/creates a client keyed only by `creator` and `name` — there is no `stack:` scoping argument, so `stack_id` remains `nil` on the created record, and this single client/token is shared and reused across every stack for which the current user requests a CCMenu URL.

The consuming controller, `Shipit::Api::CCMenuController`, compounds this by overriding the base class's stack-resolution method and dropping the tenant-scoping check entirely: [2](#0-1) 

Compare this to `Shipit::Api::BaseController`, which is designed to scope stack lookups to the token's authorized stack when one is set: [3](#0-2) 

`stacks` filters by `current_api_client.stack_id` when present, and `stack` is derived from that filtered scope. `CCMenuController#stack`, however, calls `Stack.from_param!(params[:stack_id])` directly — bypassing `stacks`/`current_api_client.stack_id` entirely. `require_permission :read, :stack` (inherited from `BaseController`) only checks the `read:stack` permission bit via `ApiClient#check_permissions!`: [4](#0-3) 

`check_permissions!` never checks `stack_id` against the requested resource. So even if the token *did* carry a `stack_id`, `CCMenuController` would not enforce it since it bypasses `stacks`/`stack` from the base class.

The broken binding, expressed as an equality that should hold but doesn't:
`stack the CCMenu token is intended to authorize == stack the CCMenu endpoint actually serves data for`

Before the attacker acts: a user with legitimate access to Stack A requests `CCMenuUrlController#fetch` for Stack A, getting a token intended only to expose Stack A's CI status via the CCMenu XML feed.
After the attacker acts: using the very same token (just changing `stack_id` in the request path to Stack B, or any other stack in the instance, including private/restricted ones the user's GitHub team membership would not otherwise grant read access to via `Shipit::Authentication`), the attacker retrieves Stack B's deploy/build status through `Api::CCMenuController#show`.

### Impact Explanation
This is an authorization-scope escalation letting a token meant for one stack read build/deploy state (`stack.deploys_and_rollbacks.last`, deploy status/timing) for any stack in the Shipit deployment, including stacks belonging to repositories/teams the token holder was never authorized to see through the normal `Shipit::Authentication`/`Shipit.github_teams` checks. This falls squarely in the "stack a token authorises vs. stack it touches" analog class and matches the High-severity bucket ("unauthorized read of stack state ... via broken authorization scoping").

### Likelihood Explanation
High. Any user who can reach `CCMenuUrlController#fetch` for a single stack (a normal, low-privilege UI action available from the stack settings page) obtains a durable, reusable token with no stack restriction; no additional exploitation complexity, race condition, or privileged access is required — only substituting `stack_id` in the already-known API path.

### Recommendation
When creating the CCMenu `ApiClient`, scope it explicitly to the requesting stack (e.g., `find_or_create_by!(creator: current_user, name: 'CCMenu Client', stack: stack)`), and remove `Api::CCMenuController#stack`'s override so it reuses `Api::BaseController#stack`/`#stacks`, ensuring `current_api_client.stack_id` is enforced against the requested `params[:stack_id]` on every CCMenu request.

### Proof of Concept
1. As User with access to Stack A, call `GET /api/stacks/:stack_a_id/ccmenu/fetch` (via `CCMenuUrlController#fetch`) to obtain `{"ccmenu_url": ".../api/stacks/<stack_a>/ccmenu?token=<T>"}`.
2. Note the `ApiClient` backing `<T>` has `stack_id: nil` (verifiable via `ApiClient.find_by(...).stack_id`).
3. Replay the request against a different, unrelated stack: `GET /api/stacks/:stack_b_id/ccmenu?token=<T>`.
4. `Api::CCMenuController#show` renders Stack B's CI/deploy status XML using the same token `<T>`, even though `<T>` was only ever presented as a token for Stack A and the user may have no independent access to Stack B.

```ruby
# frozen_string_literal: true

module Shipit
  module Api
    class CCMenuController < BaseController
      require_permission :read, :stack

      class NoDeploy
        def id
          0
        end

        def ended_at
          Time.now.utc
        end

        def running?
          false
        end
      end

      def show
        latest_deploy = stack.deploys_and_rollbacks.last || NoDeploy.new
        render('shipit/ccmenu/project', formats: [:xml], locals: { stack:, deploy: latest_deploy })
      end

      private

      def stack
        @stack ||= Stack.from_param!(params[:stack_id])
      end

      def authenticate_api_client
        @current_api_client = ApiClient.authenticate(params[:token])
        super unless @current_api_client
      end
    end
  end
```
