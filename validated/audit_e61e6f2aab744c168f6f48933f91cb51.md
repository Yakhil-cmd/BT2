## Confirmed analog

`ERC20Matcher` confirms this attack is fully permissionless: `pub type ERC20Matcher = MatchedConvertedConcreteId<H160, u128, IsLocalAccountKey20, AccountKey20ToH160, TryConvertInto>` matches **any** `AccountKey20` location, i.e. any deployed contract address, with **no on-chain registration/allowlist**. Any signed account can deploy an arbitrary EVM contract via `pallet_revive` (`UploadOrigin`/`InstantiateOrigin` = `EnsureSigned`, `AllowEVMBytecode: ConstBool<true>`), and immediately use it as an XCM-transactable "asset" through `ERC20Transactor`.

### Title
XCM `ERC20Transactor` credits/debits the requested `value` instead of the actual amount moved by the ERC20 contract, breaking accounting for fee-on-transfer/deflationary tokens and allowing cross-user fund loss via the shared checking account - ([File: cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs])

### Summary
`ERC20Transactor::withdraw_asset_with_surplus` and `deposit_asset_with_surplus` [1](#0-0) [2](#0-1)  only check the boolean return value of a Solidity `IERC20::transfer` call and then unconditionally credit/debit the XCM holding with the full `amount` that was *requested*, never verifying the actual balance delta on the `TransfersCheckingAccount`. This reproduces the exact violated invariant from the report: "recorded amount" vs. "actually received amount" diverge for any token contract that takes a fee/burn on transfer while still returning `true`.

### Finding Description
`Matcher::matches_fungibles(what)` extracts `(asset_id, amount)` from the XCM `Asset` purely from the user-supplied XCM message; `asset_id` is an arbitrary `H160` contract address (via `ERC20Matcher`/`AccountKey20ToH160`) with no allowlist [3](#0-2) .

In `withdraw_asset_with_surplus`, the transactor calls `IERC20::transferCall{ to: checking_address, value: amount }` on that arbitrary contract via `pallet_revive::Pallet::<T>::bare_call` [4](#0-3) . If the call succeeds and decodes to `true`, the code unconditionally constructs `AssetsInHolding::new_from_fungible_credit(what.id.clone(), Box::new(Erc20Credit(amount)))` [5](#0-4) , i.e. it trusts the caller-supplied `amount`, not any observed balance change of the `checking_address`. A malicious ERC20 contract (freely deployable by the attacker via permissionless `pallet_revive` upload/instantiate) can implement a deflationary `transfer` that moves `amount - fee` to `to` but still returns `true`.

Symmetrically, `deposit_asset_with_surplus` transfers `amount` (the holding's recorded amount, inherited from the tainted withdraw) from the shared `TransfersCheckingAccount` to the beneficiary [6](#0-5) , again trusting the boolean return rather than an actual balance check.

Crucially, `TransfersCheckingAccount` is a single, shared account for *all* ERC20 XCM transfers on the chain: `ERC20TransfersCheckingAccount: AccountId = PalletId(*b"py/revch").into_account_truncating();` [7](#0-6) . Because withdrawals and deposits for this token type are pooled through one account, the shortfall left by a fee-on-transfer token during withdraw is not isolated per-user: it either (a) causes an unrelated later `deposit_asset_with_surplus` for a *different* asset transfer instruction to revert for lack of funds because the checking account balance is lower than the sum of all `amount`s recorded in outstanding holdings, or (b) if the checking account happens to hold a surplus from other unrelated flows, permits one XCM operation's `amount` to be silently satisfied out of another user's/asset's balance in that same pooled account — the same "one user unknowingly takes another user's funds" outcome described in the original report.

### Impact Explanation
This breaks the accounting invariant that XCM asset holdings must equal the actual balance change effected on-chain. The `ERC20Transactor` is wired into `AssetTransactors` on Asset Hub Westend's XCM config [8](#0-7) , meaning any XCM program (local execute, reserve transfer, teleport-style withdraw/deposit sequences) that references such an ERC20 asset location is exposed. Depending on which side (withdraw over-credits vs. deposit under-covers) the fee lands, this can result in: value materializing in an XCM holding that the checking account never actually possesses (accounting desync/possible unbacked issuance in the holding), or later deposits draining balance that in fact belongs to a different, unrelated transfer through the shared checking account. This is a Medium-severity accounting integrity issue rather than an outright unbacked-issuance/theft-by-default because it requires the attacker's own contract to be the target asset of the transfer.

### Likelihood Explanation
Reachability requires only a signed account: deploying an arbitrary EVM contract is fully permissionless (`UploadOrigin`/`InstantiateOrigin = EnsureSigned<Self::AccountId>`, `AllowEVMBytecode: ConstBool<true>`) and using it as an XCM asset requires no registration since `ERC20Matcher` accepts any `AccountKey20` location. The attacker needs to author a deflationary/fee-on-transfer ERC20 contract (standard, well-known Solidity pattern) and issue an XCM program (e.g. via `pallet-xcm::execute`) that withdraws/deposits that asset through the `ERC20Transactor`. No governance or privileged role is needed.

### Recommendation
In both `withdraw_asset_with_surplus` and `deposit_asset_with_surplus`, read the ERC20 contract's `balanceOf` for the relevant account before and after the `transfer` call (or otherwise derive the actual delta), and use that observed delta — not the caller-supplied `amount` — when constructing/consuming the `AssetsInHolding` credit and when computing the amount to forward in `deposit_asset_with_surplus`. Reject transfers where the observed delta is less than requested rather than trusting the boolean return value alone.

### Proof of Concept
Execution status: not run against a live network/test harness. The analysis above is based on static code tracing:
1. `ERC20Matcher`/`AccountKey20ToH160` accept any deployed `H160` contract as a valid XCM fungible asset id with no allowlist [3](#0-2) .
2. `withdraw_asset_with_surplus` trusts `amount` for the holding credit regardless of the ERC20 contract's actual balance movement [9](#0-8) .
3. `deposit_asset_with_surplus` moves `amount` out of the single shared `TransfersCheckingAccount` [6](#0-5) , and that account is a single PalletId-derived account shared across all users/assets of this transactor [10](#0-9) .

A concrete minimal repro to confirm/deny this in a background Devin session would deploy a fee-on-transfer ERC20 fixture contract in `pallet-revive`'s test harness, register it as the ERC20 transactor's matched asset, execute an XCM `WithdrawAsset`/`DepositAsset` program referencing it, and assert the resulting holding/checking-account balances diverge from `amount`. This was not executed here; no test was run and no result should be assumed.

	fn withdraw_asset_with_surplus(
		what: &Asset,
		who: &Location,
		_context: Option<&XcmContext>,
	) -> Result<(AssetsInHolding, Weight), XcmError> {
		tracing::trace!(
			target: "xcm::transactor::erc20::withdraw",
			?what, ?who,
		);
		let (asset_id, amount) = Matcher::matches_fungibles(what)?;
		let who = AccountIdConverter::convert_location(who)
			.ok_or(MatchError::AccountIdConversionFailed)?;
		// We need to map the 32 byte checking account to a 20 byte account.
		let checking_account_eth = T::AddressMapper::to_address(&TransfersCheckingAccount::get());
		let checking_address = Address::from(Into::<[u8; 20]>::into(checking_account_eth));
		let weight_limit = WeightLimit::get();
		// To withdraw, we actually transfer to the checking account.
		// We do this using the solidity ERC20 interface.
		let data =
			IERC20::transferCall { to: checking_address, value: EU256::from(amount) }.abi_encode();
		let ContractResult { result, weight_consumed, storage_deposit, .. } =
			pallet_revive::Pallet::<T>::bare_call(
				OriginFor::<T>::signed(who.clone()),
				asset_id,
				U256::zero(),
				TransactionLimits::WeightAndDeposit {
					weight_limit,
					deposit_limit: StorageDepositLimit::get(),
				},
				data,
				&ExecConfig::new_substrate_tx(),
			);
		// We need to return this surplus for the executor to allow refunding it.
		let surplus = weight_limit.saturating_sub(weight_consumed);
		tracing::trace!(target: "xcm::transactor::erc20::withdraw", ?weight_consumed, ?surplus, ?storage_deposit);
		if let Ok(return_value) = result {
			tracing::trace!(target: "xcm::transactor::erc20::withdraw", ?return_value, "Return value by withdraw_asset");
			if return_value.did_revert() {
				tracing::debug!(target: "xcm::transactor::erc20::withdraw", "ERC20 contract reverted");
				Err(XcmError::FailedToTransactAsset("ERC20 contract reverted"))
			} else {
				let is_success = IERC20::transferCall::abi_decode_returns_validate(&return_value.data).map_err(|error| {
					tracing::debug!(target: "xcm::transactor::erc20::withdraw", ?error, "ERC20 contract result couldn't decode");
					XcmError::FailedToTransactAsset("ERC20 contract result couldn't decode")
				})?;
				if is_success {
					tracing::trace!(target: "xcm::transactor::erc20::withdraw", "ERC20 contract was successful");
					Ok((
						AssetsInHolding::new_from_fungible_credit(
							what.id.clone(),
							Box::new(Erc20Credit(amount)),
						),
						surplus,
					))
				} else {
					tracing::debug!(target: "xcm::transactor::erc20::withdraw", "contract transfer failed");
					Err(XcmError::FailedToTransactAsset("ERC20 contract transfer failed"))
				}
			}
		} else {
			tracing::debug!(target: "xcm::transactor::erc20::withdraw", ?result, "Error");
			// This error could've been duplicate smart contract, out of gas, etc.
			// If the issue is gas, there's nothing the user can change in the XCM
			// that will make this work since there's a hardcoded gas limit.
			Err(XcmError::FailedToTransactAsset("ERC20 contract execution errored"))
		}
	}

/// Fallible converter from a location to a `H160` that matches any location ending with
/// an `AccountKey20` junction.
pub struct AccountKey20ToH160;
impl MaybeEquivalence<Location, H160> for AccountKey20ToH160 {
	fn convert(location: &Location) -> Option<H160> {
		match location.unpack() {
			(0, [AccountKey20 { key, .. }]) => Some((*key).into()),
			_ => None,
		}
	}

	fn convert_back(key: &H160) -> Option<Location> {
		Some(Location::new(0, [AccountKey20 { key: (*key).into(), network: None }]))
	}
}
