### Title
Cross-repository commit-status forgery causing unauthorized deploy/merge - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` applies an incoming `status` webhook to **every** `Commit` record in the database whose `sha` matches the payload, without checking that the commit belongs to the `repository` named in that same payload. Because the signature only proves the webhook came from *some* GitHub organization/installation known to Shipit, and does not bind the `sha` to the specific `repository.full_name` when Shipit later resolves which commit to update, a status event genuinely signed for one repository can be applied to a commit that happens to share the same SHA in a completely different, unrelated stack.

### Finding Description
`WebhooksController#verify_signature` selects the GitHub app/secret used to verify `X-Hub-Signature` using only the organization extracted from the payload (`repository_owner`), and then hands the raw parsed JSON to the handler: [1](#0-0) 

Every other handler (e.g. `PushHandler`) explicitly scopes its side effects to stacks whose `Repository` matches `payload.dig('repository', 'full_name')`: [2](#0-1) 

`StatusHandler`, however, never consults `repository_name`/`stacks` at all — it looks up commits **globally by SHA** and mutates their status: [3](#0-2) 

The equality that is supposed to hold is: `organization that authenticated the webhook == repository/stack that is written`. Here the code writes to `Commit.where(sha:)` — any stack, any repository — while the signature only authenticates that the request originated from an organization known to Shipit's GitHub App config; the `repository` field of the payload (which GitHub itself binds the event to) is read only to select the verification secret, and is otherwise ignored when deciding *which* commit's status to overwrite.

Since a git commit SHA is fully determined by its content, tree, parents, author/committer identities and timestamps, an attacker who can push a commit with byte-identical metadata to any repository that has the same Shipit GitHub App installed (their own repository, if the app is installable by any account) can reproduce the exact SHA of a commit that already exists in a victim stack's history. Sending (or having GitHub deliver) a `status` webhook for that SHA — correctly signed for the attacker's own organization/installation — will be applied by `StatusHandler` to the victim's commit too, because the lookup is unscoped.

Once the status is written, `Commit#add_status` fires `stack.schedule_merges` and can trigger `deployable_status`/merge-queue progression for the victim stack: [4](#0-3) 

### Impact Explanation
This breaks the "unauthorized deploy, rollback, or merge" boundary (Critical). An attacker with no access to the victim repository or its Shipit stack can inject a fabricated "success" CI status for a commit in the victim's stack merely by controlling a different repository that shares the commit SHA, unblocking `ProcessMergeRequestsJob`/continuous-delivery gating that depends on commit status, and causing the merge queue to advance/deploy a commit that never actually passed the victim's real CI.

### Likelihood Explanation
Producing a colliding SHA requires knowledge of the exact commit metadata (tree, parents, author, committer, timestamps, message) of the target commit — this information is public for open-source/public repos (visible via the GitHub API/UI) and is trivial for an attacker to replicate byte-for-byte in a repository they control, assuming they can get the same GitHub App installed on that repository so a legitimately signed webhook is produced. No Shipit session, `ApiClient` token, or webhook secret needs to be known or stolen.

### Recommendation
Scope `StatusHandler#process` (and any other handler that looks up records purely by SHA) to only the stacks associated with `payload.dig('repository', 'full_name')`, mirroring the `stacks` helper already used by `PushHandler`, e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` instead of the unscoped `Commit.where(sha: params.sha)`.

### Proof of Concept
1. Identify a target commit SHA `S` in `victim-org/victim-repo`'s Shipit-tracked branch, including its full tree, parent, author, committer and timestamps (all public via the GitHub API).
2. From an attacker-controlled account/repo `attacker/repo` that has the same Shipit GitHub App installed, recreate a commit with identical content/metadata so it hashes to the same SHA `S` (e.g., via `git commit-tree`/`git cherry-pick` with fixed dates), then push it.
3. Post (or let GitHub deliver) a `status` event for `attacker/repo` at SHA `S` with `state: "success"`. It is signed correctly for `attacker`'s org, so `WebhooksController#verify_signature` passes.
4. `Shipit::Webhooks::Handlers::StatusHandler#process` executes `Commit.where(sha: S)`, which also matches the victim's commit object, and calls `create_status_from_github!`, applying the forged "success" status to the victim's stack and triggering `stack.schedule_merges`.
