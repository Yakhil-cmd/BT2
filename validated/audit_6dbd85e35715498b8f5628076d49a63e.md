### Title
Assets sent to a child-bounty sub-account are permanently unrecoverable after the child bounty is claimed or closed - ([File: substrate/frame/child-bounties/src/lib.rs])

### Summary
`pallet-child-bounties` derives a deterministic `PalletId` sub-account for every child bounty [1](#0-0)  that any signed, unprivileged account can send fungible assets to directly (e.g. via `pallet_assets::transfer`), exactly as they could for a parent bounty's sub-account. `pallet-bounties` recently fixed the equivalent problem for parent bounties by adding a permissionless `reclaim_bounty_funds` extrinsic and by making `close_bounty` sweep `TransferAllAssets` back to the treasury, because "closed bounties would not refund any balance to the treasury [and] assets were blocking the withdrawal" [2](#0-1) [3](#0-2) . No equivalent fix exists in `pallet-child-bounties`: `claim_child_bounty` and `impl_close_child_bounty` only move `T::Currency` (native balance) out of the child-bounty account and then delete the `ChildBounties` storage entry, never touching any other asset balance held by that account, and there is no `reclaim_child_bounty_funds`-style sweep anywhere in the pallet.

### Finding Description
- `claim_child_bounty` transfers only the native currency (`T::Currency::transfer`) for curator fee and beneficiary payout, then deletes the child-bounty record [4](#0-3) .
- `impl_close_child_bounty` (used by `close_child_bounty`) does the same: it only transfers `T::Currency` balance from the child-bounty account to the parent-bounty account, then sets `*maybe_child_bounty = None`, permanently forgetting the sub-account [5](#0-4) .
- After either path runs, `ChildBounties::<T>::get(parent_bounty_id, child_bounty_id)` returns `None`, and no code anywhere in `pallet-child-bounties` ever revisits `child_bounty_account_id(parent_bounty_id, child_bounty_id)` again for any asset type.
- Meanwhile, `pallet-bounties` was given `TransferAllAssets` precisely to sweep configured fungible assets (via `force_transfer_all_assets`) out of a bounty account, both on `close_bounty` [6](#0-5)  and via the new permissionless `reclaim_bounty_funds` extrinsic once the bounty record is gone [7](#0-6) . `pallet-child-bounties` has no `TransferAllAssets`-equivalent field and no analogous reclaim call at all.
- Any unprivileged, signed account can permissionlessly send non-native fungible assets (e.g. `pallet-assets` tokens) straight to the deterministic child-bounty sub-account (it is a normal `AccountId`, no special permission is required to transfer assets into it), just as they could to a parent-bounty account before the parent-pallet fix. Once the child bounty completes its lifecycle (claim/award or close/cancel), those non-native assets are permanently stranded with no code path in the runtime capable of recovering them — this mirrors the report's underlying invariant violation ("funds frozen in the contract without the possibility of refund or claiming") transplanted onto a FRAME pallet: a legitimate deposit path exists, but the corresponding cleanup/reclaim path does not cover it.

### Impact Explanation
Funds (non-native fungible assets) deposited into a child-bounty account are permanently locked once the child bounty is claimed or closed, with no dispatchable in the pallet able to move them anywhere. This is an irreversible freezing of user funds, matching the class of impact the original report describes, though weaker than the original in that it does not require a malicious/reverting token to block a *whole* claim — it simply omits a reclaim path that the sibling pallet (`pallet-bounties`) was explicitly given to fix the identical root cause (see the `TransferAllAssets`/`reclaim_bounty_funds` PRs referencing issue #10996).

### Likelihood Explanation
Likelihood is moderate: exploitation/triggering does not require any privilege, governance action, or malicious validator/collator — any signed account can send assets to the well-known, deterministically derivable child-bounty sub-account. It does, however, require a runtime that both uses `pallet-child-bounties` and has other fungible-asset pallets whose account balances aren't otherwise protected/reaped, and it requires someone (attacker, careless funder, or automated tooling) to actually place assets there, since child-bounty accounts are not part of the pallet's normal "deposit" flow. I was not able to confirm from the indexed code whether the currently live Rococo/production runtimes configure any asset pallet in a way that a real user would realistically send tokens to this address (this would need runtime-config verification and integration testing that exceeds what I can execute in this read-only review).

### Recommendation
Add a `TransferAllAssets`-style associated type (or reuse `pallet_bounties::Config::TransferAllAssets`) to `pallet-child-bounties::Config`, and either (a) sweep it during `impl_close_child_bounty`/`claim_child_bounty` back to the parent bounty account, or (b) add a permissionless `reclaim_child_bounty_funds` extrinsic mirroring `pallet_bounties::reclaim_bounty_funds`, gated on the child-bounty record no longer existing in `ChildBounties`.

### Proof of Concept
No executable PoC was run; this is a static-analysis finding based on comparing the fixed parent-pallet code path against the unfixed child-pallet code path. Reproduction would require: (1) a test runtime wiring `pallet-child-bounties` alongside `pallet-assets`, (2) creating and funding a child bounty, (3) transferring a non-native asset directly to `ChildBounties::child_bounty_account_id(parent_id, child_id)`, (4) calling `claim_child_bounty` or `close_child_bounty` to completion, and (5) asserting the asset balance remains on the now-orphaned sub-account with no extrinsic in `pallet-child-bounties` able to retrieve it — analogous to the existing `reclaim_bounty_funds_works_with_additional_assets` test for the parent pallet [8](#0-7) , which has no counterpart in `substrate/frame/child-bounties/src/tests.rs`. This gap in test coverage itself corroborates that the child-bounty asset-stranding path is unaddressed.

		pub fn reclaim_bounty_funds(
			origin: OriginFor<T>,
			#[pallet::compact] bounty_id: BountyIndex,
		) -> DispatchResultWithPostInfo {
			ensure_signed(origin)?;

			// A live bounty still manages its account, so leave it untouched.
			ensure!(!Bounties::<T, I>::contains_key(bounty_id), Error::<T, I>::BountyStillActive);

			debug_assert!(
				T::ChildBountyManager::child_bounties_count(bounty_id) == 0,
				"child bounties should not exist for a closed bounty"
			);

			let bounty_account = Self::bounty_account_id(bounty_id);
			let treasury_account = Self::account_id();

			let transferred = T::TransferAllAssets::force_transfer_all_assets(
				&bounty_account,
				&treasury_account,
			)?;

			// Free only if something moved, otherwise paid to prevent griefing.
			if !transferred {
				return Ok(Pays::Yes.into());
			}

			Self::deposit_event(Event::<T, I>::BountyFundsReclaimed { bounty_id });

			Ok(Pays::No.into())
		}

#[test]
fn reclaim_bounty_funds_works_with_additional_assets() {
	ExtBuilder::default().build_and_execute(|| {
		Balances::make_free_balance_be(&Treasury::account_id(), 101);
		assert_ok!(Bounties::propose_bounty(RuntimeOrigin::signed(0), 50, b"12345".to_vec()));
		assert_ok!(Bounties::approve_bounty(RuntimeOrigin::root(), 0));
		go_to_block(2);
		assert_ok!(Bounties::propose_curator(RuntimeOrigin::root(), 0, 0, 1));
		assert_ok!(Bounties::accept_curator(RuntimeOrigin::signed(0), 0));

		let bounty_account = Bounties::bounty_account_id(0);

		// Load the bounty account with both native and asset 1.
		Balances::make_free_balance_be(&bounty_account, 100);
		assert_ok!(Assets::transfer(RuntimeOrigin::signed(0), 1, bounty_account, 10));

		pallet_bounties::Bounties::<Test>::remove(0);
		pallet_bounties::BountyDescriptions::<Test>::remove(0);

		let treasury_native_before = Balances::free_balance(Bounties::account_id());
		let treasury_asset1_before = Assets::balance(1, &Bounties::account_id());

		// A single call reclaims both the native token and asset 1.
		assert_ok!(Bounties::reclaim_bounty_funds(RuntimeOrigin::signed(5), 0));
		assert_eq!(last_event(), BountiesEvent::BountyFundsReclaimed { bounty_id: 0 },);

		// Native balance drained to at most ED.
		assert!(Balances::free_balance(&bounty_account) <= 1);

		// Asset 1 swept to treasury.
		assert_eq!(Assets::balance(1, &bounty_account), 0);
		assert!(Assets::balance(1, &Bounties::account_id()) > treasury_asset1_before);

		// Treasury received native funds.
		assert!(Balances::free_balance(Bounties::account_id()) > treasury_native_before);
	});
}
