### Title
Unfiltered `shipit.yml` `machine.environment` (and PR-label keys) from an attacker's fork commit reaches `Command#unbundled_env` for review-stack tasks - ([File: lib/shipit/task_commands.rb], [File: app/models/shipit/review_stack.rb], [File: lib/shipit/command.rb])

### Summary
`DeploySpec#machine_env` reads `machine.environment` straight out of the `shipit.yml` found in the checked-out commit and `TaskCommands#env`/`DeployCommands` (via `Commands`) merge it directly into the process environment with no whitelist check, unlike API-supplied env which goes through `EnvironmentVariables#permit`. For a `ReviewStack` under `provisioning_behavior=allow_with_label`, that checked-out commit is the PR head commit, which an unprivileged fork contributor fully controls (including its `shipit.yml`), and the provisioning gate for `allow_with_label` is satisfied by the PR author simply adding a label to their own PR. `ReviewStack#env` additionally merges the PR's label names (attacker-chosen keys) directly into the stack env with no whitelist either.

### Finding Description
The broken binding: it is assumed that `env_reaching_PTY_spawn.keys ⊆ whitelist(deploy_variables/rollback_variables/task_variables)`, i.e. every key/value pair in the environment handed to `Command#start` → `PTY.spawn` has passed through `EnvironmentVariables#permit`. This holds for explicit API-triggered `env` params (`Stack#build_deploy` → `filter_deploy_envs`, `Stack#trigger_task` → `definition.filter_envs`, both calling `EnvironmentVariables#permit`, `lib/shipit/environment_variables.rb:13-18,35-44`) but it does **not** hold for `machine.environment` values sourced from `shipit.yml`:

- `DeploySpec#machine_env` reads `config('machine', 'environment') || {}` verbatim from the parsed `shipit.yml` of the checked-out commit (`app/models/shipit/deploy_spec.rb:69-71`).
- `TaskCommands#env` merges `deploy_spec.machine_env` directly, unfiltered, into the environment hash passed to every `Shipit::Command` used for that task/deploy: `.merge(deploy_spec.machine_env)` (`lib/shipit/task_commands.rb:33-48`).
- `Command#initialize` stores `@env = env.transform_values { |v| v&.to_s }` with no key filtering (`lib/shipit/command.rb:31-37`), and `Command#unbundled_env` merges `@env.stringify_keys` on top of `BASE_ENV` (which is itself derived from `Bundler.unbundled_env`) right before `PTY.spawn` (`lib/shipit/command.rb:17-18, 92, 103-105`).
- Separately, `ReviewStack#env` merges the PR's GitHub label names (uppercased, attacker-chosen key, fixed value `"true"`) into the stack env with no whitelist at all (`app/models/shipit/review_stack.rb:84-93`).

For a normal (non-review) stack, `shipit.yml` is trusted because only people with push/merge rights to the deployed branch can change it. For a `ReviewStack`, `Stack#repo_git_url`/`git_path` still point at the *base* repository's git remote (`app/models/shipit/stack.rb:392-405`), but `StackCommands#fetch_commit` fetches by raw SHA (`git fetch origin ... commit.sha`, `lib/shipit/stack_commands.rb:20`) rather than by branch name. On GitHub, forks share the underlying object store of their parent's network, so a commit SHA that only exists on a fork is fetchable from the base repository's remote even though no branch in the base repo references it. Consequently the exact commit authored by the unprivileged PR submitter - including their custom `shipit.yml` - is what gets checked out at `@task.working_directory` and used by `DeploySpec::FileSystem` for that task/deploy.

Provisioning of the `ReviewStack` under `allow_with_label` requires only that the PR author add the repository's configured `provisioning_label_name` to their own PR (`app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb:65-74`, `labeled_handler.rb:78-97`) - an action fully within an unprivileged fork contributor's control, no maintainer approval, no repository-write permission, no Shipit session or API token.

No existing guard intercepts this: `verify_signature`/webhook auth only authenticates that the webhook came from GitHub for that repo, it says nothing about who authored the PR's commits; `EnvironmentVariables#permit` is never invoked on `machine_env`; there is no model validation on `shipit.yml` content; `ExplicitParameters` only validates webhook payload shape, not commit contents.

### Impact Explanation
Once a review-stack task (dependency install, deploy, or custom task step) runs, the spawned `Command` inherits `GEM_PATH` (or any other env var, e.g. `RUBYOPT`, `BUNDLE_GEMFILE`, `LD_PRELOAD`) as set by the attacker's own `shipit.yml`, unfiltered, directly into the environment of a `PTY.spawn`'d process on the Shipit deploy host. Because the same checked-out working directory is the attacker's own fork commit (which they also fully control), they can co-locate a malicious gem/library at a path referenced by their injected `GEM_PATH`/`LD_PRELOAD`, and have it loaded when the deploy scripts subsequently run `bundle`/`ruby`. This is host-level code execution under the Shipit deploy user, i.e. Critical RCE via `Command`/`PTY.spawn`, matching the stated Immunefi severity class. Because provisioning and this environment merge happen per-`ReviewStack` (scoped to `environment: "pr#{number}"`), the blast radius is any repository that has enabled review stacks with `allow_with_label`; it is repeatable against any such repository by any external contributor able to open a PR and self-label it.

### Likelihood Explanation
Preconditions: repository has `review_stacks_enabled: true` and `provisioning_behavior: allow_with_label` (a documented, common opt-in configuration meant to let outside contributors preview PRs). Given that, the only attacker cost is: open a PR from a fork with a crafted `shipit.yml` (`machine.environment.GEM_PATH = ...`), and add the configured provisioning label to their own PR - both are actions available to any GitHub user with fork/PR/label permission on their own PR, no privileged Shipit role required. The subsequent task/deploy invocation that actually spawns `Command`s with this environment may be triggered automatically (continuous delivery) or by a maintainer clicking "Deploy"/"Retry" in the Shipit UI for that review stack, which is expected normal operation of the feature, not a privileged bypass of a control - the vulnerability is that no control filters `machine_env` at all, for any stack type.

### Recommendation
Do not trust `shipit.yml`'s `machine.environment` (or `ReviewStack#env`'s label-derived keys) unconditionally for dynamically-provisioned review stacks sourced from third-party forks:
- Route `deploy_spec.machine_env` (and any PR-label-derived keys in `ReviewStack#env`) through `EnvironmentVariables#permit` against an explicit, repository-maintainer-controlled allowlist (e.g., configured on the `Repository` record, not derived from the PR's own commit), the same way `deploy_variables`/`rollback_variables`/task `variables` already are (`app/models/shipit/deploy_spec.rb:174-180`, `app/models/shipit/task_definition.rb:63-65`).
- Alternatively/additionally, for `ReviewStack`s specifically, source `machine.environment` from the base repository's trusted `shipit.yml` (e.g., pinned to the default branch) rather than the PR head commit, or explicitly deny-list sensitive keys (`GEM_PATH`, `LD_PRELOAD`, `RUBYOPT`, `BUNDLE_GEMFILE`, `PATH`, etc.) before merging into `Command`'s `@env`.
- Require maintainer approval (e.g., a maintainer-only label, or a check requiring a maintainer to have reviewed the diff) rather than a self-appliable label as the sole gate for `allow_with_label` provisioning that leads to command execution using attacker-supplied repository content.

### Proof of Concept
minitest plan (`test/unit/task_commands_test.rb` or a new `test/models/shipit/review_stack_env_test.rb`):
```ruby
test "GEM_PATH from an attacker-controlled shipit.yml machine_env reaches Command#unbundled_env for a review stack" do
  repository = shipit_repositories(:shipit)
  configure_provisioning_behavior(repository:, behavior: :allow_with_label, label: "pull-requests-label")

  review_stack = ReviewStack.create!(
    repository:, branch: "pr-1234", environment: "pr1234"
  )
  # Simulate the attacker's shipit.yml, as if fetched/checked out from the PR head commit
  malicious_spec = DeploySpec.new(
    "machine" => { "environment" => { "GEM_PATH" => "/tmp/attacker-controlled-gems" } }
  )
  review_stack.stubs(:cached_deploy_spec).returns(malicious_spec)

  task = review_stack.tasks.build(user: shipit_users(:walrus))
  commands = TaskCommands.new(task)
  commands.stubs(:deploy_spec).returns(malicious_spec)

  # Binding under test: no key of `deploy_spec.machine_env` should reach the spawned env unless whitelisted
  refute_includes DeploySpec::VariableDefinition, "GEM_PATH" # no whitelist exists for machine_env at all

  command = Command.new("true", env: commands.env, chdir: ".")
  assert_equal "/tmp/attacker-controlled-gems", command.env["GEM_PATH"]
  assert_equal "/tmp/attacker-controlled-gems", command.unbundled_env["GEM_PATH"]
end
```
This demonstrates both sides of the equality diverge: the intended invariant "`env reaching PTY.spawn` ⊆ whitelisted variables" is false for `machine_env`-sourced keys, and for `ReviewStack`s that `machine_env` is attacker-controlled content from the PR head commit.
