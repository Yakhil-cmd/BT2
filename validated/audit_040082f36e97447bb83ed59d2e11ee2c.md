### Title
Webhook Signature Verification Selects the HMAC Secret From an Unverified Field, Decoupling the Authenticated Organization From the Repository Written - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
This is the shipit-engine analog of the Enigma `deposit()` bug class: a field that is *acted upon* is never actually bound to the check that is supposed to protect it. In Enigma, `amount0Desired`/`amount1Desired` were validated against pool state that could be manipulated across fee tiers, without any minimum-shares guarantee tying the check to the real outcome. In `WebhooksController`, the GitHub App/webhook secret used to *verify* an inbound webhook's HMAC signature is selected using `repository_owner`, a field read straight out of the **unverified, attacker-controlled JSON body**, before signature verification happens. The event handlers that subsequently *act* on the payload (writing `Status` rows, syncing stacks, etc.) select their target using a **different** unverified field (`repository.full_name`, or in the `StatusHandler` case, no repository scoping at all). There is no cryptographic binding tying "the organization whose secret validated this signature" to "the repository/commit the handler will mutate."

### Finding Description
`WebhooksController#verify_signature` computes which `GithubApp`/secret to check the signature against directly from the raw, not-yet-verified body: [1](#0-0) [2](#0-1) 

Shipit explicitly supports **multiple GitHub Apps for multiple organizations**, each with its own independent `webhook_secret`: [3](#0-2) 

Once the signature "passes" (because it was checked against the secret of whichever organization the attacker named in `repository.owner.login`), `WebhooksController#create` dispatches the *entire* unverified payload to the registered handlers with no further binding to that organization: [4](#0-3) 

Handlers each independently re-derive their own target from a *different* payload field, `repository.full_name`: [5](#0-4) [6](#0-5) 

Critically, `StatusHandler` does not scope by repository/organization at all — it matches purely by commit SHA across the **entire** Shipit instance: [7](#0-6) 

**The broken binding, stated as an equality that the code assumes but never enforces:**
`organization authenticated by verify_signature (via repository.owner.login)` == `repository/commit actually written by the handler (via repository.full_name / commit sha)`

**Before the attack:** for a single-org Shipit instance this equality holds trivially. Shipit's multi-org configuration is documented and supported, at which point the two fields diverge in provenance but the code silently assumes they refer to the same org.

**Attack sequence (multi-org Shipit instance, e.g. `OrgA` and `OrgB` both onboarded, as in `test/dummy/config/secrets_double_github_app.yml`):**
1. Attacker is a legitimate, unprivileged member/admin of `OrgA`'s GitHub App (or otherwise knows `OrgA`'s `webhook_secret` — e.g., because they configured that org's app themselves, a normal unprivileged action for their own org).
2. Attacker crafts a JSON body with `repository.owner.login = "OrgA"` (so `verify_signature` looks up and validates against `OrgA`'s known secret) but `repository.full_name = "OrgB/victim-repo"` (a repository tracked in Shipit but belonging to `OrgB`, which the attacker has no access to).
3. Attacker computes `X-Hub-Signature` using `OrgA`'s secret over this crafted body and POSTs it to `/webhooks`.
4. `verify_signature` passes because it validated the signature against the correct secret for the *claimed* `repository_owner` (`OrgA`), which the attacker legitimately controls.
5. The dispatched handler (e.g. `PushHandler` or `StatusHandler`) then acts on `OrgB/victim-repo` or on any commit SHA matching `params.sha` instance-wide, using data entirely fabricated by the attacker.

### Impact Explanation
This is a cross-repository/cross-organization write: an attacker who legitimately controls credentials for one onboarded organization (`OrgA`) can forge state-changing webhook events against a *different* organization's repository/commits tracked by the same Shipit instance. For `StatusHandler` specifically, there is no repository scoping whatsoever, so any known commit SHA in the entire Shipit deployment can have arbitrary CI status records (`success`/`failure`, `target_url`, `description`) injected by any org onboarded to the instance, without ever touching the victim org's actual webhook secret. Since commit status is part of the signal Shipit surfaces/relies on to gate whether commits are considered CI-passing for deploy readiness, this directly satisfies the "unauthorized deploy" / "cross-repository writes" Critical impact category.

### Likelihood Explanation
Requires only that the Shipit instance is configured for multiple GitHub organizations (a documented, first-class configuration in `docs/setup.md`) and that the attacker legitimately controls one of those organizations' webhook secrets — no privileged Shipit account, `ApiClient` token, or `GITHUB_TOKEN` access is needed, only the ability to compute a valid HMAC with a secret the attacker is entitled to know for their own org. This is a realistic multi-tenant misconfiguration-independent flaw, not a theoretical one, since the code path is exercised on every webhook delivery.

### Recommendation
Bind the verified signature to the exact organization/repository the handlers subsequently act on:
- After selecting `github_app` via `repository_owner`, re-validate that every entity the dispatched handlers will mutate (`repository.full_name`'s owner, and for `StatusHandler`, the owning repository/organization of the matched `Commit`) belongs to the same organization that authenticated the request.
- `StatusHandler` should scope `Commit.where(sha: params.sha)` to commits belonging to stacks whose repository owner matches the authenticated `repository_owner`, not to all commits instance-wide.
- Consider deriving the app/secret lookup key from a single canonical, then have all handlers reuse that exact validated organization identity rather than re-parsing the raw payload independently.

### Proof of Concept
Given a Shipit instance configured per `test/dummy/config/secrets_double_github_app.yml` with `OrgA` and `OrgB`, and a victim commit `sha=deadbeef` belonging to a stack under `OrgB/victim-repo`:

```
POST /webhooks HTTP/1.1
X-Github-Event: status
X-Hub-Signature: sha1=<HMAC-SHA1(OrgA_webhook_secret, BODY)>

BODY:
{
  "sha": "deadbeef",
  "state": "success",
  "context": "ci/forged",
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/victim-repo" }
}
```

`verify_signature` (app/controllers/shipit/webhooks_controller.rb:24-30) resolves `Shipit.github(organization: "OrgA")` and validates successfully because the attacker signed with `OrgA`'s real secret. `StatusHandler#process` (app/models/shipit/webhooks/handlers/status_handler.rb:20-24) then finds `Commit.where(sha: "deadbeef")` — a commit that may belong to `OrgB/victim-repo` — and calls `create_status_from_github!`, writing an attacker-forged "success" status despite the attacker having no relationship to `OrgB` whatsoever.
