### Title
Instant, timelock-free changes to an asset's `spender_attested` attestor list allow the asset definer to freeze holders' funds without notice - ([File: validation.js])

### Summary
Ocore lets the definer of a `spender_attested` asset replace the entire list of trusted attestors at any time via a single `asset_attestors` message, with the new list taking effect immediately for all subsequent payment validation. There is no delay/timelock analogous to what code-423n4/2022-03-joyn recommended for `setPlatformFee()`.

### Finding Description
When an asset is defined with `spender_attested: true`, every payment of that asset requires that at least one author of the payment be attested by one of the asset's currently valid attestors [1](#0-0) . The attestor list itself can be updated at will by the asset's definer through an `asset_attestors` message; the only checks are that the sender is the single author and is the asset's `definer_address` — there is no cooldown, vote, or delay before the new list becomes effective: [2](#0-1) 

The updated list is persisted and immediately read back by `storage.readAsset`/`loadAssetWithListOfAttestedAuthors` for any subsequent payment validation, and enforced without exception in `validatePayment`, `checkForDoublespends`, and downstream input/output validation.

By contrast, structural parameters of the asset that are set once at definition time (`cap`, `is_private`, `issued_by_definer_only`, etc.) are immutable [3](#0-2) , but `spender_attested`'s supporting attestor list is explicitly designed to be mutable post-issuance (see the SQL comment "must subsequently publish and update the list of trusted attestors") [4](#0-3) , yet no protection against an abrupt, malicious, or accidental update exists.

### Impact Explanation
An asset definer (an ordinary, unprivileged DAG participant who simply posted an `asset` definition unit) can, at any moment and with a single unit, drop all previously-attested addresses from the attestor list. Every existing holder whose spendability depended on being attested by the old list instantly loses the ability to spend their already-issued, already-held asset units — a form of fund freezing enforced consensus-wide with no notice period for holders to react, withdraw, or migrate. Conversely, the definer could swap in new, colluding attestors to instantly grant spend eligibility to addresses that were never vetted under the terms holders originally transacted under, undermining the trust assumption that made holders accept the asset in the first place. Both directions are unilateral, instantaneous, and irreversible from the perspective of unprivileged asset holders/counterparties.

### Likelihood Explanation
This requires no special network position — any user can define a `spender_attested` asset and later act as its own attestor-list-updating definer, or a legitimate definer may be compromised or turn malicious after holders have accumulated balances. Since the change is a single ordinary unit (`asset_attestors`) validated the same way as any other message, the likelihood of an update being posted and taking effect immediately is high; only the resulting harm to existing holders (fund freeze) makes it worth calling out.

### Recommendation
Add a timelock/notice mechanism to attestor list updates for `spender_attested` assets, e.g., require a minimum number of stable MCIs (or an explicit `activation_mci`) between when an `asset_attestors` update is posted and when it takes effect, so that existing holders have on-chain, provable advance warning before a change to the attestor set can restrict or alter their ability to spend already-held units of the asset.

### Proof of Concept
1. Definer posts an `asset` unit with `spender_attested: true` and an initial attestor list `[A]`; attestor `A` attests address `H`.
2. `H` receives/holds a large balance of this asset in reliance on being attestable and spendable per `validatePayment`'s check at [1](#0-0) .
3. The definer posts a single `asset_attestors` unit immediately replacing the attestor list with `[B]`, passing the checks in `validateAttestorListUpdate` (only requires single-author + definer match) [2](#0-1) .
4. As soon as this unit is stable, `H`'s previously-valid attestation to `A` is no longer in the effective attestor set; any payment `H` tries to send is rejected by `validatePayment` with "none of the authors is attested" [5](#0-4) , freezing `H`'s funds with zero advance notice.

function validateAttestorListUpdate(conn, payload, objUnit, objValidationState, callback){
	if (objUnit.authors.length !== 1)
		return callback("attestor list must be single-authored");
	if (!isNonemptyObject(payload))
		return callback("attestor update must be a non-empty object");
	if (hasFieldsExcept(payload, ['asset', 'attestors']))
		return callback("foreign fields in attestor list update");
	storage.readAsset(conn, payload.asset, objValidationState.last_ball_mci, false, function(err, objAsset){
		if (err)
			return callback(err);
		if (!objAsset.spender_attested)
			return callback("this asset does not require attestors");
		if (objUnit.authors[0].address !== objAsset.definer_address)
			return callback("attestor list can be edited only by definer");
		err = checkAttestorList(payload.attestors);
		if (err)
			return callback(err);
		callback();
	});
}
