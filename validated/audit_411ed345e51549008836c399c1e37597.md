### Title
Cross-repository status forgery via unscoped `Commit.where(sha:)` lookup - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` resolves target commits by SHA alone, without constraining the lookup to the repository named in the webhook payload, unlike every other handler in the same module which scopes through the `Handler#stacks` helper (filtered by `repository_name`). Any GitHub organization whose webhook signature Shipit can verify (i.e., any repository legitimately registered in Shipit) can post a `status` event for a commit whose SHA also exists as the `head` of a pending `MergeRequest` on a completely different, victim stack — most plausibly via forked/shared git history — and have that status attached to the victim's commit record, driving `any_status_checks_failed?` to `true` and causing `reject!('ci_failing')` on a pull request the attacker does not own.

### Finding Description
The broken binding is: `commit.stack.github_repo_name == webhook.payload['repository']['full_name']`. This should hold for every `Commit` a handler mutates in response to a webhook, but for `StatusHandler` it does not.

Code path:
- `app/controllers/shipit/webhooks_controller.rb#verify_signature` verifies the HMAC signature using `Shipit.github(organization: repository_owner)`, where `repository_owner` is derived from `params.dig('repository', 'owner', 'login')` [1](#0-0) . This only proves the webhook truly originates from GitHub for the organization that owns the *reported* repository — it says nothing about which commits that organization is allowed to affect.
- `Shipit::Webhooks.for_event('status')` dispatches to `StatusHandler.call(params)` [2](#0-1) .
- `StatusHandler#process` does:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [3](#0-2) 
This iterates over **every** `Commit` row across **every** stack/repository sharing that SHA — there is no `stacks`/`repository_name` filter. Contrast with `PushHandler#process`, which correctly scopes via `stacks.not_archived.where(branch:)` where `stacks` is derived from `Repository.from_github_repo_name(repository_name)` [4](#0-3) [5](#0-4) . `StatusHandler` is the outlier that skips this scoping entirely.
- `commit.create_status_from_github!` writes a `Status` row for the commit via `add_status`/`replicate_from_github!` [6](#0-5) [7](#0-6) .
- On the next `ProcessMergeRequestsJob#perform` run, `merge_request.refresh!` re-pulls the PR and its head's statuses, then `reject_unless_mergeable!` calls `any_status_checks_failed?`, which builds a `StatusChecker` off `head.statuses_and_check_runs` and returns true if any is `failure`/`error` [8](#0-7) ; this triggers `reject!('ci_failing')` [9](#0-8) .

Exploit flow: the attacker owns/administers a repository legitimately registered with Shipit (their own fork or any repo enrolled under a GitHub App/organization Shipit trusts). If a commit SHA on the victim's pending PR's `head` also exists in the attacker's repository (natural via shared git ancestry from forking, cherry-picks, or any identical commit object), the attacker sets a `failure` status on that SHA in their own repo via the ordinary GitHub Statuses UI/API. GitHub delivers a legitimately-signed `status` webhook naming the attacker's repository; `verify_signature` passes because it only checks that organization's signature. `StatusHandler` then blindly attaches the `failure` status to **every** `Commit` row with that SHA in the database, including the victim's, which corrupts the victim's `MergeRequest#head` status set and causes an unauthorized `reject!('ci_failing')` on the next `ProcessMergeRequestsJob` pass.

No existing guard closes this gap: `verify_signature` authenticates the org, not the SHA-to-repository binding; `ExplicitParameters` in `StatusHandler.params` only validates payload shape (`sha`, `state`, etc.), not repository scoping; and there is no model-level uniqueness/ownership constraint tying a `Commit.sha` to a single `Repository`/stack (by design, since `Commit` is stored per-stack, but the handler fails to filter by stack).

### Impact Explanation
An attacker with no privileges on the victim's Shipit stack can force an authenticated write (`Status` row / `rejection_reason`, `merge_status`) into another tenant's `MergeRequest`, denying a legitimate merge queued via the merge queue feature. This is a cross-tenant write triggered purely by an SHA coincidence attainable through ordinary fork/shared-history mechanics, not requiring a true SHA-1 collision. It is repeatable against any victim stack/repository whose pending `MergeRequest#head.sha` happens to coincide with a commit the attacker can drive a status for, and scales to any number of repositories sharing history with the attacker-controlled one. This matches the "payload for one repository mutating another's ... commit" Critical category, though the specific direction here is denial (rejection) rather than an unauthorized merge/deploy.

### Likelihood Explanation
Preconditions: the attacker's own repository must already be enrolled in Shipit with a valid webhook signature verifiable via `Shipit.github(organization: ...)` (i.e., the attacker's org/repo is a legitimate Shipit-tracked GitHub App installation — a normal, low-privilege state for any repo owner using Shipit, not a secret-holding privilege). The victim repository must have a pending `MergeRequest` whose `head.sha` coincides with a commit reachable/statusable by the attacker (trivially achievable by forking a public repo that includes the victim's PR base history, or by crafting identical commit objects). Attacker cost is low: one GitHub status API call/webhook per attempt, fully repeatable, and does not require guessing any secret, session, or API token.

### Recommendation
Scope `StatusHandler#process` to the repository named in the webhook payload, mirroring the `Handler#stacks` pattern used elsewhere, e.g. restrict the SHA lookup to `Commit.where(sha: params.sha, stack: stacks)` (or join through the commit's `stack.repository` and compare against `repository_name`) before calling `create_status_from_github!`, so a status webhook can only mutate commits belonging to the repository that legitimately signed and reported the event.

### Proof of Concept
Minitest plan (model/controller level, no live GitHub):
1. Create two stacks/repositories: `victim/repo` and `attacker/repo`, each with a `Commit` record sharing the same `sha` value (simulate the fork/shared-history collision).
2. Create a pending `MergeRequest` on `victim/repo` whose `head` is the shared-sha commit, with a passing/no CI status initially; assert `merge_request.pending?` and `refute merge_request.any_status_checks_failed?`.
3. Post a `status` webhook payload naming `attacker/repo` as `repository.full_name` with `state: 'failure'` and the shared `sha`, using `GithubHook.any_instance.stubs(:verify_signature).returns(true)` (as done in `test/controllers/webhooks_controller_test.rb`) to simulate a legitimately-signed webhook for the attacker's own repo.
4. Assert that a `Shipit::Status` row with `state: 'failure'` now exists on the **victim's** shared-sha `Commit` (`victim_commit.statuses.where(state: 'failure').exists?` is true) even though the webhook only named `attacker/repo`.
5. Run `ProcessMergeRequestsJob.perform_now(victim_stack)` (or directly call `merge_request.reject_unless_mergeable!`), then assert:
   - `merge_request.reload.rejected?` is `true`
   - `merge_request.rejection_reason == 'ci_failing'`
   even though the only interaction performed was a status webhook for `attacker/repo`, never touching `victim/repo`.

This demonstrates the binding `commit.stack.github_repo_name == payload.repository.full_name` is violated by `StatusHandler#process`'s unscoped `Commit.where(sha: params.sha)` query.
