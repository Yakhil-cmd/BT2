### Title
Webhook signature verification is bound to the attacker-controlled `repository.owner`/`organization.login` field, not to the `repository.full_name` field actually used to select the Stack to act on - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks which organization's webhook secret to verify a GitHub webhook against by reading `repository.owner.login` (or `organization.login`) directly out of the **unverified** JSON body, then HMAC-checks the entire raw body against that organization's configured secret. Every webhook handler, however, resolves the `Repository`/`Stack` to act on from a *different* field in the same body — `repository.full_name`. Because both fields live in the same attacker-supplied JSON, and the whole body (including `full_name`) is HMAC'd with whatever secret the attacker used to sign it, an attacker who knows one configured organization's webhook secret can forge a payload where the "authenticating" field points at their own org while the "acted-on" field points at any other repository/stack hosted on the same Shipit instance.

### Finding Description
`WebhooksController#verify_signature` in [1](#0-0)  does:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
```
where `repository_owner` is computed as [2](#0-1) 
```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```
This is parsed straight from `request.raw_post` **before** any signature has been checked — i.e. the value used to select *which organization's secret to verify with* is fully attacker-controlled.

`Shipit.github(organization:)` resolves to a `GithubApp`/`GithubAppOrganization` configured per-organization from `secrets.yml` (see `github_app_config(organization)` in `lib/shipit.rb`), each with its own `webhook_secret`, and `verify_webhook_signature` in [3](#0-2)  just does an HMAC-SHA1 compare of the raw body against that organization's secret.

Crucially, this only proves "the body was signed by someone who knows organization X's secret" — it proves nothing about *which repository the body's content actually claims to describe*. Every downstream handler independently trusts a **different** field of the same body to determine the target:

- `Handler#stacks`/`#repository_name` in [4](#0-3)  resolves stacks via `payload.dig('repository', 'full_name')`.
- `PushHandler#process` in [5](#0-4)  uses those stacks to call `stack.sync_github(expected_head_sha: params.after)`.
- The pull-request handlers (`opened_handler.rb`, `closed_handler.rb`, `reopened_handler.rb`, `unlabeled_handler.rb`, `label_capturing_handler.rb`) all resolve `repository` via `Shipit::Repository.from_github_repo_name(params.repository.full_name)` and then archive/unarchive/provision review stacks accordingly.

Because `repository.owner.login` (used for authentication) and `repository.full_name` (used for authorization/target-selection) are two independent, attacker-writable strings inside the same JSON body, and the *entire* body is what gets HMAC'd, an attacker who legitimately knows (or is issued) the webhook secret for **organization A** can craft a body where:
- `repository.owner.login = "A"` / `organization.login = "A"` → satisfies `verify_signature`, since it looks up and validates against A's real secret, which the attacker knows and used to sign the whole payload.
- `repository.full_name = "B/victim-repo"` → an entirely different repository/stack, e.g. belonging to organization B, hosted on the same multi-tenant Shipit instance.

This breaks the trust binding "organization that authenticated the webhook == repository the webhook payload is allowed to affect," analogous to the Cork Protocol bug where the field tracked/accounted (`locked`) diverged from the field actually transferred (`ra` via `lockUnchecked`) because the code updated one side of an equality while trusting the untracked other side.

### Impact Explanation
On a Shipit deployment hosting Stacks for multiple GitHub organizations/repositories (each with its own `secrets.github[org].webhook_secret`), anyone who legitimately controls the webhook secret for *any one* configured organization (e.g., an app admin/maintainer for org A) can forge:
- Push events (`PushHandler`) causing `stack.sync_github` to run against any other org/repo's Stack that exists in the instance, which can drive commit ingestion and downstream continuous-delivery triggers for a Stack they have no legitimate authorization over.
- Pull-request lifecycle events causing review stacks belonging to other repositories to be provisioned, archived, or unarchived.
- Status/check-run events that influence merge/deploy readiness checks for other repositories' Stacks.

This can result in unauthorized actions (provisioning/deprovisioning review stacks, triggering syncs that feed into continuous-deployment eligibility) against repositories the attacker does not control — an authentication-bypass style crossing of the organization/repository trust boundary, matching the "cross-repository writes" / "unauthorized deploy" impact bucket.

### Likelihood Explanation
Exploitability requires: (1) the Shipit instance is multi-tenant, configuring more than one organization's webhook secret in `secrets.yml`, and (2) a Stack already exists for the targeted repository. Both are common in real deployments (Shipit is explicitly designed to host many orgs/repos). The attacker only needs the webhook secret for *one* of those organizations (which they may legitimately hold as an app owner for their own org on a shared instance) — no GitHub write access, no `ApiClient` token, and no privileged Shipit account is required, satisfying the "unprivileged attacker" constraint.

### Recommendation
Bind the verified organization to the field(s) actually used for authorization: after computing the HMAC-verified organization, re-derive/validate that `repository.full_name`'s owner segment matches the organization used for verification (or, better, only resolve `Repository`/`Stack` scoped to the verified `repository_owner`) before any handler acts on the payload. Alternatively, verify signatures per-repository using each repository's own registered secret rather than a shared per-organization secret keyed off an untrusted field.

### Proof of Concept
1. Instance hosts orgs A and B, each configured in `secrets.yml` with distinct `webhook_secret`s; Stack `B/victim-repo` exists.
2. Attacker (who holds/knows org A's `webhook_secret`, e.g. as A's GitHub App owner) crafts a `push` payload body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker chosen sha existing in B/victim-repo>",
  "repository": { "owner": { "login": "A" }, "full_name": "B/victim-repo" }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC(webhook_secret_A, body)` and POSTs to `/webhooks` with `X-Github-Event: push`.
4. `WebhooksController#repository_owner` returns `"A"`; `verify_signature` calls `Shipit.github(organization: "A").verify_webhook_signature(sig, raw_post)`, which succeeds because the attacker signed the body with A's real secret — see [1](#0-0) .
5. `PushHandler#process` resolves stacks via `payload.dig('repository','full_name') == "B/victim-repo"` (per [4](#0-3) ) and calls `stack.sync_github(expected_head_sha: params.after)` on the `B/victim-repo` Stack — an org B resource the attacker never authenticated for.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
