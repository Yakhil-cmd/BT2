## Analysis

The audited bug class ("value used to gate/authorize an action is never bound to the field that determines what gets acted upon") maps directly onto a break in `WebhooksController`'s trust binding: the GitHub organization used to select the HMAC secret for verification is **not** the same field the event handlers use to decide which repository/commit to mutate. [1](#0-0) 

- `verify_signature` computes `repository_owner` from `params.dig('repository','owner','login')` (or `organization.login`) and looks up the app config/secret for **that org** via `Shipit.github(organization: repository_owner)` [2](#0-1) , then verifies the raw body HMAC against that org's `webhook_secret` [3](#0-2) . Note `verify_webhook_signature` returns `true` unconditionally if that org's `webhook_secret` is blank (a documented/valid config state, see `webhook_secret: # nil` in `docs/setup.md` and `secrets.development.shopify.yml`).
- The event handler base class instead derives the acted-upon repository from an **independent** field, `payload.dig('repository','full_name')` [4](#0-3) .
- `StatusHandler`, in particular, doesn't even scope by repository at all — it matches purely on commit SHA globally: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [5](#0-4) .

Because `repository.owner.login` (used for auth) and `repository.full_name`/SHA (used for effect) are independent JSON fields with no cross-check, an attacker who can produce a valid signature for **any** org configured in this Shipit instance (including one with a blank `webhook_secret`, which is an explicitly supported configuration) can forge a `status` event whose `repository.owner.login` names that unprotected org while the `sha` targets a commit belonging to a **different**, unrelated tracked stack. `commit.deployable?` depends on `success? && !blocked?`, which is computed from these injected statuses [6](#0-5) , and `ci.require`/`ci.blocking` deploy gating is documented to rely on exactly these statuses [7](#0-6) . This lets an attacker who owns no privileges on the target repository inject a fabricated "success" CI status for a target commit, bypassing the CI-required gate and enabling `require_ci: true` deploys via `Api::DeploysController#create` [8](#0-7)  for a repository they never authenticated against.

### Title
Webhook signature is verified against `repository.owner.login` while handlers act on the unrelated `repository.full_name` / commit `sha`, allowing cross-repository CI-status forgery - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to verify the payload signature against using `repository.owner.login` (or `organization.login`) taken from the untrusted, attacker-controlled JSON body. The event handlers, however, determine which repository/commit is mutated using a different field of the same body (`repository.full_name`, or for `StatusHandler`, only the raw commit `sha` with no repository scoping at all). These two values are never cross-validated.

### Finding Description
`verify_signature` in `app/controllers/shipit/webhooks_controller.rb` computes `repository_owner` from the payload and fetches the corresponding `GithubApp` config/secret via `Shipit.github(organization: repository_owner)`, then HMAC-verifies `X-Hub-Signature` against that org's secret (`lib/shipit/github_app.rb#verify_webhook_signature`). If that organization's `webhook_secret` is blank — an explicitly supported, documented configuration (see `docs/setup.md`, `config/secrets.development.shopify.yml`) — verification trivially passes for any signature/body.

Once verification passes, `WebhooksController#create` dispatches the full payload to `Shipit::Webhooks.for_event(event)` handlers unchanged. `Handlers::Handler#repository_name` (used by push/pull_request handlers) reads `payload.dig('repository','full_name')` — a completely separate field from the one used for signature-org selection. `Handlers::StatusHandler#process` goes further and does not consult the repository field at all: it matches solely on `Commit.where(sha: params.sha)`, so any tracked commit across any stack in the entire Shipit instance can receive a forged status update as long as the (unrelated) org used for signature bypass has no secret configured.

The equality that should hold — "the organization whose secret authenticated this request" == "the repository/commit that is written by the resulting handler" — is never enforced.

### Impact Explanation
This is a High-impact issue: it allows an unauthenticated read/write of stack state — specifically, forging commit CI statuses for a target repository the attacker never controls. Since `Commit#deployable?` and the documented `ci.require`/`ci.blocking` gates rely directly on these statuses, an attacker can fabricate a "success" status for a targeted commit and unblock CI-gated deploys, undermining the deploy-authorization model without ever holding a session, `ApiClient` token, or GitHub write access to the target repository.

### Likelihood Explanation
Exploitability requires only that the Shipit deployment hosts more than one GitHub organization config (a documented, supported multi-tenant setup) where at least one configured organization has no `webhook_secret` set (also an explicitly supported/documented state) — or, more generally, any organization for which the attacker can produce a valid HMAC (e.g., they administer that org's GitHub App). No repository write access, session, or API token is required, and the target commit SHA is public information from git history.

### Recommendation
Verify the webhook signature using the secret belonging to the same organization/repository that the handler will actually act upon, and reject payloads where `repository.owner.login`/`organization.login` doesn't match the resolved target repository. Additionally, scope `StatusHandler` (and any other handler) lookups by the verified repository, not by a bare commit SHA lookup across all stacks.

### Proof of Concept
1. Shipit is configured with two orgs in `secrets.yml`: `victim-org` (has a real `webhook_secret`, and a tracked stack/commit `abcd123`) and `attacker-org` (installed by the attacker, `webhook_secret` left blank per supported config).
2. Attacker sends `POST /webhooks` with `X-Github-Event: status`, an arbitrary/absent `X-Hub-Signature`, and body:
```json
{
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "attacker-org/whatever" },
  "sha": "abcd123",
  "state": "success",
  "context": "ci/required-check"
}
```
3. `verify_signature` resolves `repository_owner = "attacker-org"`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` regardless of the signature.
4. `StatusHandler#process` runs `Commit.where(sha: "abcd123")` and creates a `success` status for that commit — which actually belongs to `victim-org`'s stack — bypassing that stack's CI-required deploy gate.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
