## Title
Unbounded private‑payment chain length causes large‑loop CPU/DB consumption (DoS) - (File: `indivisible_asset.js`, `divisible_asset.js`, `private_payment.js`, `wallet.js`, `network.js`)

### Summary
The CVE describes an ImageMagick DoS where a crafted file makes the parser loop an attacker-controlled, unbounded number of times, consuming CPU. The analogous pattern in ocore is that a private‑payment chain (`arrPrivateElements` / `body.chains`) received from a private‑payment counterparty or paired device has no upper bound on its length before the code begins iterating over it element‑by‑element, each iteration issuing DB queries and (for indivisible assets) chained recursive DB lookups.

### Finding Description
Private payments (used for private assets and payment channels) are represented as a chain of elements going back to the issuance. When a peer or paired device sends such a chain (`wallet.js` `handlePrivatePaymentChains`, `network.js` `handleOnlinePrivatePayment` / `handleSavedPrivatePayments`), the only validation performed on the whole chain is that it is a non‑empty array of objects with the right shape — there is no maximum length check: [1](#0-0) 

The chain is then handed to `validateAndSavePrivatePaymentChain` (`private_payment.js`), which again only checks `isNonemptyArray` before dispatching to the asset‑specific handler: [2](#0-1) 

For indivisible assets, `parsePrivatePaymentChain` iterates the whole attacker‑supplied array with `async.forEachOfSeries`, and for every element performs a `validatePrivatePayment` call that itself issues a DB query (spend‑proof lookup) and, outside light mode, a `graph.determineIfIncluded` traversal: [3](#0-2) [4](#0-3) 

None of these code paths cap `arrPrivateElements.length` (or `body.chains[i].length`) to a sane maximum before doing per‑element work. `validateAndSavePrivatePaymentChain` then loops again over the same array to build and run one SQL query per input and per output: [5](#0-4) 

`wallet.js`'s `handlePrivatePaymentChains` additionally allows `body.chains` itself (an array of chains) to be arbitrarily large/long, multiplying the effect, and processes them with `async.eachSeries`: [6](#0-5) 

This mirrors the CVE's root cause class: a size/count value taken directly from untrusted, attacker-supplied data is used to drive a loop with no upper bound, and each iteration does non‑trivial work (DB round trips, graph traversal), so the total cost scales linearly (or worse, given the nested `async.eachSeries`/`forEachOfSeries` over both the outer chain list and each chain's elements) with a value fully controlled by the sender.

### Impact Explanation
A malicious private‑payment counterparty or paired device can send a `private_payment_chains` / `sign` / device message containing one or more extremely long private‑payment chains (thousands of fabricated elements referencing arbitrary unit/message/output indexes). Processing this triggers a large number of sequential DB queries and, for indivisible assets, recursive `determineIfIncluded` graph checks per element, tying up the DB connection pool and event loop of the victim's wallet/hub process. Because chain elements can reference nonexistent or bogus data, most of the work is wasted validation before failure, so an attacker gets a large amount of CPU/DB consumption per small message sent — a hub or full wallet processing many devices can be pushed into resource exhaustion, delaying legitimate validation/payment processing (a node "unable to confirm/process new units" in a practical sense for that peer's private-asset traffic).

### Likelihood Explanation
Any device paired with the victim wallet, or any peer that can reach `network.js`'s private‑payment handlers, can trigger this by simply constructing a JSON array with many entries — no valid signatures or real DAG data are required to start the loop, since the format-shape checks (`isNonemptyObject`, `isNonemptyString`, etc.) are satisfied trivially and the expensive per‑element work (DB queries, `determineIfIncluded`) happens before content is proven correct. This makes exploitation low‑effort for a permitted counterparty/paired device.

### Recommendation
Add explicit upper bounds (similar to `constants.MAX_INPUTS_PER_PAYMENT_MESSAGE` / `MAX_OUTPUTS_PER_PAYMENT_MESSAGE`) on:
- the number of chains in `body.chains` in `wallet.js`'s `handlePrivatePaymentChains`,
- the number of elements in a single private‑payment chain in `private_payment.js`'s `validateAndSavePrivatePaymentChain`, `indivisible_asset.js`'s `parsePrivatePaymentChain`, and the equivalent path in `divisible_asset.js`,
- the corresponding checks in `network.js`'s `handleOnlinePrivatePayment`/`handleSavedPrivatePayments`.

Reject the message immediately once the bound is exceeded, before any DB query or graph traversal is performed.

### Proof of Concept
1. Establish a paired-device or peer connection to a victim wallet/hub.
2. Send a `private_payment_chains` message (or device `private_payments`) with `body.chains` containing one chain whose element array has e.g. 50,000–100,000 synthetic elements, each satisfying only the shape checks in `handlePrivatePaymentChains` (`isNonemptyObject`, valid‑looking `unit`/`payload.asset`/`inputs`/`outputs`).
3. Observe that `parsePrivatePaymentChain`/`validateAndSavePrivatePaymentChain` begins issuing one (or more) DB query per element sequentially, consuming CPU/DB connections proportional to the attacker‑chosen array length, with no bound rejecting the request up front.

function parsePrivatePaymentChain(conn, arrPrivateElements, callbacks){
	var bAllStable = true;
	var issuePrivateElement = arrPrivateElements[arrPrivateElements.length-1];
	if (!issuePrivateElement.payload || !issuePrivateElement.payload.inputs || !issuePrivateElement.payload.inputs[0])
		return callbacks.ifError("invalid issue private element");
	var asset = issuePrivateElement.payload.asset;
	if (!asset)
		return callbacks.ifError("no asset in issue private element");
	var denomination = issuePrivateElement.payload.denomination;
	if (!denomination)
		return callbacks.ifError("no denomination in issue private element");
	async.forEachOfSeries(
		arrPrivateElements,
		function(objPrivateElement, i, cb){
			if (!objPrivateElement.payload || !objPrivateElement.payload.inputs || !objPrivateElement.payload.inputs[0])
				return cb("invalid payload");
			if (!objPrivateElement.output)
				return cb("no output in private element");
			if (objPrivateElement.payload.asset !== asset)
				return cb("private element has a different asset");
			if (objPrivateElement.payload.denomination !== denomination)
				return cb("private element has a different denomination");
			var prevElement = null; 
			if (i+1 < arrPrivateElements.length){ // excluding issue transaction
				var prevElement = arrPrivateElements[i+1];
				if (prevElement.unit !== objPrivateElement.payload.inputs[0].unit)
					return cb("not referencing previous element unit");
				if (prevElement.message_index !== objPrivateElement.payload.inputs[0].message_index)
					return cb("not referencing previous element message index");
				if (prevElement.output_index !== objPrivateElement.payload.inputs[0].output_index)
					return cb("not referencing previous element output index");
			}
			validatePrivatePayment(conn, objPrivateElement, prevElement, {
				ifError: cb,
				ifOk: function(bStable, input_address){
					objPrivateElement.bStable = bStable;
					objPrivateElement.input_address = input_address;
					if (!bStable)
						bAllStable = false;
					cb();
				}
			});
		},
		function(err){
			if (err)
				return callbacks.ifError(err);
			callbacks.ifOk(bAllStable);
		}
	);
}
