### Title
Sui→EVM bridge burns tokens before finality; no revert/refund path if destination `transferBridgedTokensWithSignatures` never succeeds - (File: `crates/sui-framework/packages/bridge/sources/bridge.move`)

### Summary
`bridge::send_token`/`send_token_v2` burn the user's Sui coin *immediately* and only afterwards create a pending `BridgeRecord` awaiting off-chain committee approval and execution on the EVM side. There is no "revert" message type or refund entrypoint in the Move bridge module analogous to ZetaChain's `onRevert`. If the corresponding EVM claim (`SuiBridge.transferBridgedTokensWithSignatures`) can never succeed for a given message, the burned Sui-side value is permanently unrecoverable — the same "burn now, mint/settle later, no fallback if settlement fails" root cause as the ZetaChain finding.

### Finding Description
`send_token_internal` unconditionally burns the deposited coin before any cross-chain confirmation: [1](#0-0) 

The resulting `BridgeRecord` sits in `token_transfer_records` waiting for `approve_token_transfer` (committee signatures) and then execution on the EVM side via `SuiBridge.transferBridgedTokensWithSignatures`: [2](#0-1) 

Examining `message_types.move`, the only system message kinds are `emergency_op`, `committee_blocklist`, `update_bridge_limit`, `update_asset_price`, and `add_tokens_on_sui` — there is no revert/cancel/refund message type, and `execute_system_message` has no branch to unwind a pending `send_token` record and re-mint the coin back to the original sender: [3](#0-2) 

Contrast this with the *inbound* (EVM→Sui) claim path, `claim_token_internal`, which was clearly designed to be retry-safe: it does **not** burn/mint until all checks (route, token type, limiter) pass, and on failure it returns `option::none()` instead of aborting or destroying state, explicitly to let relayers "retry when the 24h window resets": [4](#0-3) 

No equivalent safety net exists for the outbound direction: the burn in `send_token_internal` happens *before* the EVM-side execution, and if that EVM execution can never complete for a given message (e.g., permanent EVM-side limiter/config state, vault under-collateralization from unrelated accounting divergence, or any other durable failure condition on the destination), the Sui-side coin is gone with no code path to reconstitute it.

### Impact Explanation
This matches the "permanent fund lock" High-tier allowed impact: a user's bridged coin can be irrecoverably burned on Sui while the corresponding claim on Ethereum never executes, with no protocol-level unlock/refund mechanism. Unlike the EVM inbound claim path (which is deliberately retry-friendly), the Move outbound path commits an irreversible state change (`treasury.burn`) prior to the point where success is guaranteed.

### Likelihood Explanation
This is a design-level gap rather than a directly attacker-forced state (the trigger condition — a permanently non-executable EVM-side claim — depends on bridge/committee operational conditions and is not purely user-triggerable on demand). Per the scope's attacker model, malicious bridge authorities/committees are out of scope, and I could not identify a purely public-input path (ordinary user action alone, without any authority/config anomaly) that reliably forces the EVM claim into a permanent failure state. I was not able to fully verify whether the bridge orchestrator/committee layer (in `crates/sui-bridge`) has an off-chain compensating mechanism that mitigates this at the infrastructure level, since that code was only partially indexed.

### Recommendation
Add a revert/refund message type and corresponding Move entrypoint (mirroring ZetaChain's audit recommendation) that lets governance or, ideally, an automated timeout mechanism re-mint the burned coin back to the original Sui sender if the EVM-side claim message is proven to be permanently unexecutable (e.g., past a long timeout with no `TokenTransferClaimed`/processed event observed cross-chain). Alternatively, defer the burn until a two-phase commit confirms EVM-side execution readiness.

### Proof of Concept
Conceptual (cannot be fully demonstrated without live bridge deployment/committee state):
1. User calls `bridge::send_token<T>` on Sui, burning `Coin<T>` and creating a pending `BridgeRecord`.
2. Committee signs and calls `approve_token_transfer`, then the executor calls `SuiBridge.transferBridgedTokensWithSignatures` on Ethereum.
3. If that EVM call durably fails (config/vault state prevents any future success for this specific token/route), `isTransferProcessed[nonce]` stays `false` forever, but the Sui-side coin was already destroyed in step 1.
4. No Move function exists to reverse the burn — the user's funds are permanently lost, matching the ZetaChain root cause but without a corresponding proven, purely-public trigger, which weakens confidence this rises above a design-risk observation.

Given the uncertainty about a clean, purely public-input trigger (as required by the attacker model) and the operational/off-chain-dependent nature of "destination call permanently fails," I present this as a plausible analog but with lower confidence than a fully demonstrated exploit chain.

fun send_token_internal<T>(
    inner: &mut BridgeInner,
    target_chain: u8,
    token: Coin<T>,
    message: BridgeMessage,
) {
    assert!(!inner.paused, EBridgeUnavailable);
    assert!(chain_ids::is_valid_route(inner.chain_id, target_chain), EInvalidBridgeRoute);

    // burn / escrow token, unsupported coins will fail in this step
    inner.treasury.burn(token);

    // Store pending bridge request
    inner
        .token_transfer_records
        .push_back(
            message.key(),
            BridgeRecord {
                message,
                verified_signatures: option::none(),
                claimed: false,
            },
        );
}

    function transferBridgedTokensWithSignatures(
        bytes[] memory signatures,
        BridgeUtils.Message memory message
    )
        external
        nonReentrant
        verifyMessageAndSignatures(message, signatures, BridgeUtils.TOKEN_TRANSFER)
        onlySupportedChain(message.chainID)
    {
        // verify that message has not been processed
        require(!isTransferProcessed[message.nonce], "SuiBridge: Message already processed");

        IBridgeConfig config = committee.config();

        BridgeUtils.TokenTransferPayload memory tokenTransferPayload =
            BridgeUtils.decodeTokenTransferPayload(message.payload);

        // verify target chain ID is this chain ID
        require(
            tokenTransferPayload.targetChain == config.chainID(), "SuiBridge: Invalid target chain"
        );

        // convert amount to ERC20 token decimals
        uint256 erc20AdjustedAmount = BridgeUtils.convertSuiToERC20Decimal(
            IERC20Metadata(config.tokenAddressOf(tokenTransferPayload.tokenID)).decimals(),
            config.tokenSuiDecimalOf(tokenTransferPayload.tokenID),
            tokenTransferPayload.amount
        );

        _transferTokensFromVault(
            message.chainID,
            tokenTransferPayload.tokenID,
            tokenTransferPayload.recipientAddress,
            erc20AdjustedAmount
        );

        // mark message as processed
        isTransferProcessed[message.nonce] = true;

        emit TokensClaimed(
            message.chainID,
            message.nonce,
            config.chainID(),
            tokenTransferPayload.tokenID,
            erc20AdjustedAmount,
            tokenTransferPayload.senderAddress,
            tokenTransferPayload.recipientAddress
        );
    }
