### Title
Arbitrary PR-label controlled `LD_PRELOAD`/`LD_LIBRARY_PATH` injection into deploy `Command#unbundled_env` enables dynamic-linker code execution - (File: `app/models/shipit/review_stack.rb`)

### Summary
`Shipit::ReviewStack#env` blindly converts every GitHub PR label into an env var (`label_name.upcase => "true"`) and merges it into the stack env, which `Shipit::TaskCommands#env` forwards unfiltered into `Shipit::Command#env` and ultimately `Command#unbundled_env`, which is passed straight to `PTY.spawn`. Because git clone/checkout happens with a *different*, un-labeled env (`Commands#base_env`) but subsequent `perform`/`install_dependencies` steps run with the labeled env and `chdir` set to the already-checked-out PR working directory, an attacker who controls both the PR labels and the PR branch content can plant a malicious shared object and get it preloaded by the dynamic linker on the deploy host.

### Finding Description
Broken binding, stated explicitly:

- Claimed invariant: `Command#unbundled_env['LD_PRELOAD']` is set **iff** `deploy_spec.machine_env['LD_PRELOAD']` or `Shipit.env['LD_PRELOAD']` set it.
- Actual behavior: `Command#unbundled_env['LD_PRELOAD']` is also set whenever a PR carries a label named `ld_preload` (case-insensitive upcasing), fully attacker-controlled, with **no allow-list/deny-list**.

Path:
1. `Shipit::ReviewStack#env` [1](#0-0)  takes `pull_request.labels` and, for **every** label, sets `labels[label_name.upcase] = "true"`, then merges this hash on top of `Stack#env`.
2. `Shipit::TaskCommands#env` merges `@stack.env` (the `ReviewStack#env` result) into the env used for `perform`/`install_dependencies` [2](#0-1) .
3. `Command#initialize` stores this as `@env`, and `Command#unbundled_env` merges `@env.stringify_keys` on top of `BASE_ENV`/`PATH`, with **no filtering of any key name** (no LD_PRELOAD/LD_LIBRARY_PATH blocklist) [3](#0-2) .
4. `Command#start` passes this hash directly to `PTY.spawn(unbundled_env, *interpolated_arguments, chdir: @chdir)` [4](#0-3) .
5. Crucially, `checkout`/`clone` (which fetch the attacker's PR content onto disk) use `Commands#git`, whose env defaults to `base_env` (`Shipit.env` + GitHub token), **not** `TaskCommands#env` [5](#0-4) [6](#0-5) . So the label-poisoned env is *not* used during checkout, but IS used for `install_dependencies`/`perform`, both of which run with `chdir: steps_directory`, i.e., inside the already-checked-out PR working directory [7](#0-6) .

Exploit flow:
- Attacker opens a PR against a repository with a provisioned `Shipit::ReviewStack` (`provision_status == provisioned`).
- Attacker's branch commits a directory literally named `true` containing a valid ELF shared object also literally named `true` with a malicious constructor (`__attribute__((constructor))`).
- Attacker labels the PR `ld_preload` and `ld_library_path` (both unprivileged actions on their own PR).
- `ReviewStack#env` yields `{'LD_PRELOAD' => 'true', 'LD_LIBRARY_PATH' => 'true'}`, merged into `TaskCommands#env`.
- Any deploy step (`install_dependencies` or a task step) invoking a dynamically linked ELF (`git`, `bundle`, `ruby`) is spawned with `chdir` inside the checked-out repo and `LD_LIBRARY_PATH=true` (a relative path resolved against the process CWD) plus `LD_PRELOAD=true`; the dynamic linker resolves `./true/true` and loads the attacker's shared object into the process before `main()` runs, executing on the deploy host with the Shipit worker's privileges.

Why guards don't stop this: there is no `EnvironmentVariables#permit`/deny-list applied at this merge point (that mechanism operates elsewhere on presentation, not on `Command#env`), `deploy_spec.machine_env`/`Shipit.env` are additive but do not gate what `ReviewStack#env` may inject, and label creation is a normal unprivileged PR action requiring no Shipit session, API token, or team membership—`force_github_authentication`/webhook signature checks are irrelevant because labels arrive via the standard, legitimately-authenticated PR label webhook and this is a logic flaw in `ReviewStack#env`, not a forged request.

### Impact Explanation
This is Critical: arbitrary code execution on the deploy host via `Command`/`PTY.spawn`, achievable by any unprivileged user able to open a PR and label it on a repository with review-stack provisioning enabled. It grants execution in the Shipit worker's process/user context, potentially exposing `GITHUB_TOKEN`, other stacks' secrets on the same host, and the ability to tamper with subsequent deploys. It is repeatable against any repository that provisions `ReviewStack`s for PRs, and blast radius extends to the whole shared deploy host, not just the attacker's own stack.

### Likelihood Explanation
Preconditions: the target repository must have review-stack provisioning enabled and at least one deploy/task step in `shipit.yml` that shells out to a dynamically linked ELF binary (virtually all real deploy pipelines do: `git`, `bundle`, `ruby`, etc.). Attacker cost is trivial—open a PR, add two labels, commit two files—no secrets or elevated roles needed. This is fully repeatable and requires no timing/race conditions.

### Recommendation
In `Shipit::ReviewStack#env`, deny-list (or better, allow-list) label-derived environment variable names before merging—at minimum reject/strip loader-influencing names such as `LD_PRELOAD`, `LD_LIBRARY_PATH`, `LD_AUDIT`, `DYLD_INSERT_LIBRARIES`, `DYLD_LIBRARY_PATH`, `BASH_ENV`, `ENV`, `PERL5OPT`, etc., or scope label-derived vars to a safe, non-overridable prefix (e.g., `SHIPIT_LABEL_<NAME>`) instead of writing directly into the top-level process environment merged into `Command#unbundled_env`.

### Proof of Concept
```ruby
# test/models/shipit/review_stack_test.rb (extend existing style)
test "#env must not allow labels to set loader-influencing variables" do
  stack = shipit_stacks(:review_stack)
  stack.pull_request.labels = ["ld_preload", "ld_library_path"]

  env = stack.env

  refute env.key?("LD_PRELOAD"), "PR label must not be able to set LD_PRELOAD"
  refute env.key?("LD_LIBRARY_PATH"), "PR label must not be able to set LD_LIBRARY_PATH"
end

# test/lib/shipit/task_commands_test.rb
test "#env forwarded to Command#unbundled_env must not contain LD_PRELOAD from a label" do
  stack = shipit_stacks(:review_stack)
  stack.pull_request.labels = ["ld_preload"]
  task = shipit_tasks(:shipit_restart)
  task.stack = stack

  env = Shipit::TaskCommands.new(task).env
  command = Shipit::Command.new('true', env:, chdir: '.')

  refute command.unbundled_env.key?("LD_PRELOAD"),
    "Command#unbundled_env should never contain LD_PRELOAD sourced from a PR label"
end

# test/unit/command_test.rb - confirms PTY.spawn receives the poisoned key today (red test before fix)
test "PTY.spawn is invoked with attacker-controlled LD_PRELOAD" do
  command = Shipit::Command.new('true', env: { 'LD_PRELOAD' => 'true' }, chdir: '.')
  PTY.expects(:spawn).with(has_entry('LD_PRELOAD' => 'true'), anything, chdir: '.').returns([StringIO.new, StringIO.new, 1])
  command.start
end
```
These tests currently fail against the unfixed code (the first two assertions currently hold `LD_PRELOAD`/`LD_LIBRARY_PATH` present), demonstrating the broken binding; they should pass once the recommended filtering is added to `ReviewStack#env`.

    def start(&block)
      return if @started

      @control_block = block
      @out = @pid = nil
      FileUtils.mkdir_p(@chdir)
      begin
        @out, child_in, @pid = PTY.spawn(unbundled_env, *interpolated_arguments, chdir: @chdir)
        child_in.close
      rescue Errno::ENOENT
        raise NotFound, "#{Shellwords.split(interpolated_arguments.first).first}: command not found"
      rescue Errno::EACCES
        raise Denied, "#{Shellwords.split(interpolated_arguments.first).first}: Permission denied"
      end
      @started = true
      self
    end
