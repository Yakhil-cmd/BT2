### Title
Cross-tenant `Team`/`Membership` mutation via `github_id`-only lookup in `MembershipHandler` bypasses per-organization webhook provenance - (File: `app/models/shipit/webhooks/handlers/membership_handler.rb`)

### Summary
`WebhooksController#verify_signature` selects the webhook secret to check against based solely on the `organization.login`/`repository.owner.login` value taken from the *unverified* JSON payload itself, then hands the fully attacker-controlled payload to `MembershipHandler#process`, which looks up the target `Team` only by `github_id` with no check that the team's `organization` matches the org whose secret actually verified the request. This lets an operator of Org A (who legitimately knows Org A's own `webhook_secret` in a multi-organization Shipit install) forge a `membership`/`removed` webhook naming Org B's `team.id` and strip a Membership row belonging to Org B, deauthorizing one of Org B's operators.

### Finding Description
The broken binding is: `organization_that_verified_signature == organization_owning_the_mutated_Team`. Before any code runs, this should always hold; the code never asserts it.

Trace:
1. `WebhooksController#verify_signature` computes `repository_owner` purely from payload fields the attacker controls: `params.dig('repository','owner','login') || params.dig('organization','login')` [1](#0-0)  and uses it to pick which `GitHubApp` (and therefore which `webhook_secret`) to verify against: `Shipit.github(organization: repository_owner).verify_webhook_signature(...)` [2](#0-1) . In a multi-organization Shipit install (`Shipit.github_app_config(organization)`, per `docs/setup.md` "Using Multiple Github Applications") each org has its own independently-configured `webhook_secret` [3](#0-2) . An org's own admin legitimately knows only *their own* secret.
2. Because the org name used for verification comes straight from the payload, an attacker who is the legitimate admin of Org A can sign a payload with `organization.login: "org-a"` using Org A's real secret, and it will pass `verify_signature` — even though the `team`/`member` fields inside that same payload reference Org B's resources.
3. `MembershipHandler#process` then calls `find_or_create_team!`, which resolves the `Team` **only** by `github_id`: `Team.find_or_create_by!(github_id: params.team.id) { ... }` [4](#0-3) . If a `Team` with that `github_id` already exists (Org B's team, part of `Shipit.github_teams`), the block is skipped and the existing Org‑B‑owned record is returned unchanged — there is no comparison between `team.organization` and the verified `params.organization.login`.
4. `process` resolves/creates the member via `User.find_or_create_by_login!(params.member.login)` [5](#0-4)  — for an existing operator this simply loads them by login, no GitHub API round trip is needed [6](#0-5) .
5. On `action: 'removed'`, `team.members.delete(member)` deletes the `Membership` row tying that operator to Org B's team [7](#0-6) , exactly mirroring the existing test `":membership can delete an user membership"` [8](#0-7) .
6. `User#authorized?` is computed from `teams.where(id: Shipit.github_teams.map(&:id)).exists?` [9](#0-8) , so deleting the qualifying `Membership` immediately flips a legitimate operator from authorized to unauthorized.

No existing guard prevents this: `verify_signature` only proves "the sender knows the secret for the org named in the payload," not "the sender is authorized to mutate the team named in the payload." `find_or_create_team!` never cross-checks `team.organization` against the verified org. `ExplicitParameters` schema on `MembershipHandler` only validates shapes/types (`team.id`, `organization.login`, `member.login` presence), not ownership [10](#0-9) .

### Impact Explanation
An attacker who administers any single organization configured in a multi-org Shipit instance can, with a single forged webhook signed under their own org's secret, delete the `Membership` record binding an arbitrary operator to an arbitrary `Team` in `Shipit.github_teams` as long as they can guess/know that team's numeric GitHub `github_id`. This immediately revokes that operator's `authorized?` status for the entire Shipit install (loss of access to stacks, deploys, API clients), a cross-tenant authorization write that the victim org never approved and whose webhook was never verified by the victim's own secret. This matches "escalation/reduction of `Shipit.github_teams` authorization" and is repeatable indefinitely against any operator/team combination whose `github_id`/login the attacker can determine (team IDs are visible via the public GitHub API for any team the attacker can view, and operator logins are public GitHub usernames).

### Likelihood Explanation
Requires: (a) Shipit configured for multiple GitHub organizations (documented supported configuration), (b) attacker is a legitimate administrator/owner of at least one of those configured orgs (able to configure that org's own GitHub App webhook secret — no compromise of Shipit's own secrets or the victim org's secrets required), (c) attacker knows the victim `Team`'s GitHub `team.id` and the target operator's GitHub `login` (both discoverable via ordinary GitHub UI/API access, no special permission needed). Cost is a single crafted HTTP POST to `/webhooks` with a correctly HMAC-signed body using the attacker's own known secret — trivial and fully repeatable.

### Recommendation
In `MembershipHandler#find_or_create_team!`, scope the lookup by both `github_id` and `organization`, and reject/no-op when an existing `Team` record's `organization` does not match `params.organization.login` (the org that was actually used to verify the webhook signature in `WebhooksController#verify_signature`). More generally, `WebhooksController#verify_signature` should pass the resolved/verifying organization down to the handler (rather than trusting a second, independently attacker-controlled payload field), and `MembershipHandler#process` should hard-fail (e.g., raise or drop the event) if `team.organization != verified_organization`.

### Proof of Concept
Minitest plan (in `test/controllers/webhooks_controller_test.rb` style, illustrative — not to be placed in `test/**` per audit scope but describing the exact assertions):
1. Configure two orgs in `Shipit.github` config: `"org-a"` with `webhook_secret: "secret-a"`, and `"org-b"` with `webhook_secret: "secret-b"`.
2. Pre-create `victim_team = Team.create!(github_id: 999, organization: "org-b", slug: "ops")`, add it to `Shipit.stubs(:github_teams).returns([victim_team])`, and create `operator = User.create!(login: "victim-operator", ...)` with `victim_team.add_member(operator)`. Assert `operator.authorized?` is `true`.
3. Build payload: `{action: "removed", team: {id: 999, name: "ops", slug: "ops", url: "..."}, organization: {login: "org-a"}, member: {login: "victim-operator"}}`, sign it with HMAC-SHA1 using `"secret-a"` (the attacker's own, legitimately-known secret) and set `X-Hub-Signature`, `X-Github-Event: membership`.
4. POST to `/webhooks`.
5. Assert response is `:ok` (i.e., `verify_signature` succeeded using org-a's secret, proving the equality `organization_that_verified == organization_owning_team` was violated: `"org-a" != "org-b"`).
6. Assert `Membership.exists?(team: victim_team, user: operator)` is now `false`, and `operator.reload.authorized?` is now `false` — demonstrating the cross-tenant deauthorization despite the webhook never being verified by `"secret-b"`.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
