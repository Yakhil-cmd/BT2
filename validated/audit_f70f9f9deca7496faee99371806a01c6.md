### Title
Arbitrary outbound HTTP request (SSRF) to attacker-chosen ArbStore URL via arbiter contract flow - (File: arbiter_contract.js)

### Summary
The arbiter-contract feature lets a peer, over a paired-device chat message, propose a contract that names an `arbiter_address` of their choosing. When the local wallet later needs to interact with that arbiter (open a dispute, appeal, get fee, or just fetch arbiter info), it resolves the arbiter's ArbStore URL through its own hub (`hub/get_arbstore_url`) and then performs an unrestricted outbound HTTP(S) request to that URL, sending it contract details (including private asset/amount data). Because the URL is whatever the attacker (acting as, or colluding with, the named "arbiter") registered, the attacker fully controls the destination host/port/path of a server-initiated request — a classic SSRF, analogous to FFmpeg's DASH-playlist SSRF (CVE-2023-6605) where an attacker-crafted playlist causes the victim process to issue an HTTP GET to an arbitrary attacker-chosen URL.

### Finding Description
`arbiter_contract.js` builds contracts from data received via device messages. `createAndSend`/`store` persist `objContract.arbiter_address` as supplied by the offering peer with no restriction other than being a syntactically valid address [1](#0-0) .

Later actions on the contract — `getArbstoreAddresses`, `openDispute`, `appeal`, `getAppealFee` — resolve the URL for that `arbiter_address` via the local hub (`hub/get_arbstore_url`) and then issue a raw HTTP(S) request built directly from the returned string, with the wallet's own contract data as the request body: [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4) .

The low-level request function performs no allow-listing of scheme/host/port; it simply parses the `url` string and issues a `POST`: [6](#0-5) .

`arbiters.js` has the same pattern for `getInfo`/`getArbstoreInfo`, doing a raw `https.get(url, ...)` against a URL that originates from `hub/get_arbstore_url` for an attacker-nameable `arbiter_address`: [7](#0-6) [8](#0-7) .

Since the URL ultimately traces back to whatever the entity registered as the ArbStore for the chosen `arbiter_address`, and any user can nominate themselves (or a colluding address) as the `arbiter_address` in a contract offer sent to a victim over the paired-device channel, the attacker fully controls the target of the outbound request — including internal/private IPs, cloud metadata endpoints, or other locally-reachable services — while the wallet process also leaks contract metadata (parties, amount, asset, private-payment inclusion) in the POST body of `openDispute`/`appeal`.

### Impact Explanation
An attacker can cause a victim wallet to perform arbitrary outbound HTTP(S) requests to a host of the attacker's choosing (SSRF), potentially reaching internal-network-only services, cloud metadata endpoints, or triggering requests against third parties as an attack relay, and can additionally exfiltrate contract/private-payment details (amount, asset, parties) via the request body in `openDispute`/`appeal`. This falls within the "AA/asset/private-payment counterparty and paired device" reachable surface allowed by the rules; it does not require a malicious hub or node — only that the victim accept/interact with an arbiter contract naming an attacker-controlled arbiter.

### Likelihood Explanation
Likelihood is moderate-to-high: creating an arbiter contract offer with an arbitrary `arbiter_address` requires no special privilege — any paired device can send `arbiter_contract_offer`/`arbiter_contract_shared` messages [9](#0-8) [1](#0-0) , and the victim only needs to interact with the contract (view arbiter info, open a dispute, appeal, or check the appeal fee) to trigger the outbound request to the attacker's URL.

### Recommendation
- Restrict `httpRequest`/`requestInfoFromArbStore` to `https://` only, and validate/resolve the target host, rejecting private/loopback/link-local IP ranges (SSRF allow-listing) before connecting.
- Consider requiring ArbStore URLs to be pinned/verified out-of-band (e.g., signed registration, allow-list of known ArbStores) rather than trusting whatever is returned for an arbitrary `arbiter_address`.
- Avoid sending sensitive contract fields (asset, amount, private-payment flag) in requests to an unverified endpoint; require explicit user confirmation showing the resolved URL before any dispute/appeal request is sent.

### Proof of Concept
1. Attacker pairs with victim's wallet as a normal contact.
2. Attacker sends `arbiter_contract_offer` with `arbiter_address` set to an address that the attacker (or a colluding party) has registered with an ArbStore whose `hub/get_arbstore_url` resolves to `http://169.254.169.254` (or any internal host), per [9](#0-8) .
3. Victim accepts the contract and later calls `openDispute` (or `appeal`/`getAppealFee`) on it.
4. The wallet resolves the URL via its own hub and issues an HTTP POST containing contract data directly to the attacker-chosen host, per [10](#0-9)  and [6](#0-5) , demonstrating SSRF plus data exfiltration.

function httpRequest(host, path, data, cb) {
	var reqParams = Object.assign(url.parse(host),
		{
			path: path,
			method: "POST",
			headers: {
				"Content-Type": "application/json",
				"Content-Length": (new TextEncoder().encode(data)).length
			}
		}
	);
	var req = http.request(
		reqParams,
		function(resp){
			var data = "";
			resp.on("data", function(chunk){
				data += chunk;
			});
			resp.on("end", function(){
				try {
					data = JSON.parse(data);
					if (data.error) {
						return cb(data.error);
					}
					cb(null, data);
				} catch (e) {
					cb(e);
				}
			});
		}).on("error", cb);
	req.write(data);
	req.end();
}

function getInfo(address, cb) {
	cb = cb || function() {};
	db.query("SELECT device_pub_key, real_name FROM wallet_arbiters WHERE arbiter_address=?", [address], function(rows){
		if (rows.length && rows[0].real_name) { // request again if no real name
			cb(null, rows[0]);
		} else {
			device.requestFromHub("hub/get_arbstore_url", address, function(err, url){
				if (err) {
					return cb(err);
				}
				if (!validationUtils.isNonemptyString(url))
					return cb("invalid url received from hub");
				requestInfoFromArbStore(url+'/api/arbiter/'+address, function(err, info){
					if (err) {
						return cb(err);
					}
					if (!validationUtils.isNonemptyObject(info))
						return cb("invalid arbiter info received from arbstore");
					db.query("REPLACE INTO wallet_arbiters (arbiter_address, device_pub_key, real_name) VALUES (?, ?, ?)", [address, info.device_pub_key, info.real_name], function() {cb(null, info);});
				});
			});
		}
	});
}

function getArbstoreInfo(arbiter_address, cb) {
	if (!cb)
		return new Promise(function(resolve, reject){
			getArbstoreInfo(arbiter_address, function(err, info){
				if (err) return reject(err);
				resolve(info);
			});
		});
	if (arbStoreInfos[arbiter_address]) return cb(null, arbStoreInfos[arbiter_address]);
	device.requestFromHub("hub/get_arbstore_url", arbiter_address, function(err, url){
		if (err) {
			return cb(err);
		}
		if (!validationUtils.isNonemptyString(url))
			return cb("invalid url received from hub");
		requestInfoFromArbStore(url+'/api/get_info', function(err, info){
			if (err)
				return cb(err);
			if (!validationUtils.isNonemptyObject(info))
				return cb("invalid info received from arbstore");
			const cut = parseFloat(info.cut);
			if (!info.address || !validationUtils.isValidAddress(info.address) || isNaN(cut) || cut < 0 || cut >= 1) {
				return cb("malformed info received from ArbStore");
			}
			info.url = url;
			arbStoreInfos[arbiter_address] = info;
			cb(null, info);
		});
	});
}
