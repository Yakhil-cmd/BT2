## Analysis

The CVE describes a Group Replication Plugin bug in MySQL that lets a network-reachable attacker cause a hang/crash (complete DoS). In `ocore` the closest reachable analog is a **crash-inducing uncaught exception thrown from inside an asynchronous `setTimeout` callback**, which escapes the local `try/catch` and is re-thrown by the global `uncaughtException` handler, deliberately killing the whole node process. This is reachable by any device message sender (paired device / contract counterparty / wallet correspondent) simply by knowing the victim's device address.

### Title
Remote crash (complete DoS) of a wallet/node via a device message with an unrecognized `recipient_ephemeral_pubkey` - (File: `device.js`)

### Summary
`decryptPackage()` in `device.js` throws an `Error` from inside a `setTimeout` callback when the `dh.recipient_ephemeral_pubkey` field of an incoming device message does not match any of the recipient's known keys (temp, previous temp, or permanent). Because the throw happens asynchronously, it escapes the caller's synchronous `try/catch`, and the process-wide `uncaughtException` handler in `network.js` deliberately re-throws to crash the entire process.

### Finding Description
`handleJustsaying()` processes the `hub/message` justsaying by validating the outer signature and hash of the incoming `objDeviceMessage` (both fully attacker-controlled/self-signed), then calls `decryptPackage()` inside a `try/catch`: [1](#0-0) 

`decryptPackage()` inspects `objEncryptedPackage.dh.recipient_ephemeral_pubkey`. If it does not match the recipient's temp key, previous temp key, or permanent key, it schedules a `throw` inside `setTimeout(..., 100)` and returns `null`: [2](#0-1) 

Because the `throw` is inside a `setTimeout` callback, it fires ~100ms later, after the enclosing `try { decryptPackage(...) } catch(e) {...}` block in `handleJustsaying` has already completed. The exception is therefore never caught locally and becomes an `uncaughtException` on the process. `network.js` installs a handler that intentionally re-throws to crash the process: [3](#0-2) 

The only preconditions to reach the vulnerable branch are: knowing the victim's device address (used to route the message and pass the `to === my_device_address` check), and producing a self-consistent signature over the message (trivial, since the attacker signs with their own key): [4](#0-3) 

Notably, this branch is reached before any correspondent/pairing check, so it does not require being an actual paired correspondent — merely knowledge of the recipient's device address, which is routinely shared for pairing, textcoins, arbiter contracts, and other wallet/contract flows. The same code path is also reachable through the hub-relayed `hub/deliver` → `hub/message` flow.

### Impact Explanation
A successful trigger causes the target Obyte node/wallet process to crash immediately (complete denial of service), matching the "hang or frequently repeatable crash" impact described in the CVE. If the victim is a full/witness node running as a wallet-enabled process, this halts its ability to validate/relay units, contributing to network-wide unavailability from repeated crashes; if it is a personal wallet, funds become temporarily inaccessible and pending payment/contract flows are disrupted.

### Likelihood Explanation
Likelihood is high: the attacker needs no special privileges, no valid decryption key, and no successful AES-GCM auth-tag — the vulnerable check occurs purely on the plaintext `dh.recipient_ephemeral_pubkey` string before any cryptographic operation that could fail. The only requirement is knowledge of the victim's device address, which is commonly exchanged in normal wallet/contract/pairing interactions (chat, textcoins, arbiter/prosaic contracts).

### Recommendation
Change the `else` branch in `decryptPackage()` to synchronously return an error/`null` (or throw synchronously so it is caught by the caller's `try/catch`) rather than scheduling a `throw` via `setTimeout`. If the intent was to surface the event without crashing (e.g., emit a `nonfatal_error` event, as suggested by the commented-out line just below the `throw`), replace the `setTimeout(() => throw ...)` with `eventBus.emit('nonfatal_error', ...)` and let `decryptPackage` return `null` so `handleJustsaying` calls `respondWithError("failed to decrypt")` instead of crashing.

### Proof of Concept
1. Attacker learns the victim's device address `to` (e.g., from a pairing link, chat, or contract offer).
2. Attacker generates their own device keypair, builds `objDeviceMessage`:
   - `to`: victim's device address
   - `pubkey`: attacker's own device pubkey
   - `encrypted_package.dh.sender_ephemeral_pubkey`: any valid-looking base64 string
   - `encrypted_package.dh.recipient_ephemeral_pubkey`: random base64 string that does NOT match the victim's temp/prev-temp/permanent keys
   - `encrypted_package.iv`, `.authtag`, `.encrypted_message`: any base64 strings (content doesn't need to decrypt)
   - Sign `objectHash.getDeviceMessageHashToSign(objDeviceMessage)` with the attacker's own private key so `ecdsaSig.verify` passes.
3. Send this via the hub as a `hub/message` justsaying (or via `hub/deliver` to be relayed).
4. On the victim node, `handleJustsaying('hub/message', ...)` passes signature/hash checks, calls `decryptPackage()`, which hits the `else` branch and schedules the delayed `throw`.
5. ~100ms later the exception fires uncaught, `process.on('uncaughtException')` in `network.js` re-throws, and the victim's node process crashes.
