### Title
Webhook Signature Verified Against `repository.owner.login`, but Repo Actions Are Performed Using an Unverified `repository.full_name` from the Same Payload - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App (and thus which `webhook_secret`) to validate an incoming webhook against using `repository_owner`, a field read from the attacker-supplied JSON body itself. Every webhook `Handler` (used to locate and mutate `Stack`/`Repository` records) instead resolves the target repository from a *different* field of the same body: `payload.dig('repository', 'full_name')`. Because these two fields are never cross-validated, a payload that is legitimately signed for organization A can carry a `repository.full_name` pointing at organization B's repository, causing Shipit to act on B's stack using a signature that only proves knowledge of A's secret.

### Finding Description
In a multi-organization Shipit deployment (explicitly supported, see `config/secrets.development.shopify.yml` and `test/dummy/config/secrets_double_github_app.yml`), each GitHub organization has its own `webhook_secret`: [1](#0-0) 

`verify_signature` computes `repository_owner` from `params.dig('repository', 'owner', 'login')` (falling back to `organization.login`) and uses it purely to pick which `GitHubApp` instance's `webhook_secret` to HMAC-verify against: [2](#0-1) 

Once the signature check passes, the raw JSON body is dispatched unchanged to the registered handlers: [3](#0-2) 

Every handler (`PushHandler`, `StatusHandler`, `CheckSuiteHandler`, `MembershipHandler`, the `PullRequest::*` handlers) inherits `Handler#stacks`/`#repository_name`, which resolves the *actual* repository to act on from a completely separate JSON field, `repository.full_name`: [4](#0-3) 

`PushHandler#process` then loads matching stacks by that resolved repository and immediately invokes `stack.sync_github(expected_head_sha: params.after)`, using the attacker-controlled `after` SHA: [5](#0-4) 

Nothing ties `repository.owner.login` (the identity the signature authenticates) to `repository.full_name` (the identity whose state is mutated). Additionally, `verify_webhook_signature` short-circuits to `true` if an organization has no `webhook_secret` configured at all: [6](#0-5) 

This is exactly the "organization that authenticated versus the repository that is written" equality break described in the rules: the request authenticates as `org(repository.owner.login)`, but the write target is `repo(repository.full_name)`, and these are never required to be equal or even related.

### Impact Explanation
An attacker who can produce a validly-signed webhook for *any one* organization configured on the Shipit instance (including one whose `webhook_secret` is unset/blank, which bypasses signature checking entirely per `verify_webhook_signature`) can forge `repository.full_name` to reference a stack belonging to a completely different, unrelated organization hosted on the same Shipit instance. This lets the attacker:
- Force `GithubSyncJob`/`stack.sync_github` to run against an arbitrary target stack with an attacker-chosen `expected_head_sha`, which can trigger commit ingestion and, on stacks with `continuous_deployment` enabled, an unauthorized deploy of that SHA.
- Manipulate commit statuses (`StatusHandler`), check suites (`CheckSuiteHandler`), or pull-request-derived state on a repository the attacker was never authorized to interact with.

This crosses a genuine authentication boundary (a signature scoped to org A being treated as authorization to write org B's stack state), matching the "unauthorized deploy" / "cross-repository writes" impact tier.

### Likelihood Explanation
Exploitability requires only the ability to submit an HTTP POST to the public `/webhooks` endpoint with a body signed for an organization the attacker controls or that has no `webhook_secret` configured — no Shipit session, API token, or GitHub write access is needed, satisfying the "unprivileged attacker" constraint. The mismatch is a structural property of the code (two different payload fields used for two different trust decisions), not a misconfiguration, so it is reliably reachable on any multi-org install.

### Recommendation
In `WebhooksController#verify_signature`, require that `repository.owner.login` (or `organization.login`) equal the owner segment of `repository.full_name` before dispatching to handlers, or better, have every `Handler` resolve the target repository strictly from the same organization identity that was cryptographically verified, rejecting payloads where they diverge.

### Proof of Concept
1. Configure Shipit with two GitHub orgs, `OrgA` and `OrgB`, each with its own `webhook_secret` (as in `test/dummy/config/secrets_double_github_app.yml`), and a tracked stack for `OrgB/target-repo`.
2. As an attacker with access to `OrgA`'s webhook secret (or targeting an org with no `webhook_secret` set, in which case any signature/no signature passes per `lib/shipit/github_app.rb` L76-77), craft a `push` event payload:
   ```json
   {
     "ref": "refs/heads/main",
     "after": "<attacker-chosen-sha>",
     "repository": {
       "owner": { "login": "OrgA" },
       "full_name": "OrgB/target-repo"
     }
   }
   ```
3. Sign the payload with `OrgA`'s `webhook_secret` and send it to `POST /webhooks` with `X-Github-Event: push`.
4. `verify_signature` resolves `Shipit.github(organization: "OrgA")` and validates successfully.
5. `PushHandler` resolves `repository_name` as `"OrgB/target-repo"`, finds the matching `Stack`, and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` — mutating `OrgB`'s stack despite the request only ever proving knowledge of `OrgA`'s secret.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
