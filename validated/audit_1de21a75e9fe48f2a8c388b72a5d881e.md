### Title
Newly-added unstable unit is published to `storage.assocUnstableUnits` before `level`/`best_parent_unit`/`witnessed_level` are computed, exposing a torn/partial object to concurrently validated sibling units - ([File: writer.js])

### Summary
`writer.saveJoint()` inserts a new, only partially-initialized unit-props object into the process-global `storage.assocUnstableUnits` map, and only afterwards runs a chain of asynchronous steps (`updateBestParent`, `updateLevel`, `updateWitnessedLevel`) that fill in the remaining fields. Because `validation.validate()` only serializes on the *author addresses* of the unit being validated (not on the global "write" lock held by `saveJoint`), a second unit from a different author can be validated concurrently while the first unit's writer is still mid-flight, and can read the incompletely-initialized cached object via `storage.readUnitProps()`'s `conf.bFaster` fast-path. This is the same bug class as CVE-2023-53020: an object is made visible in a shared/global structure before its initialization is complete, allowing concurrent consumers to observe (and use) inconsistent state.

### Finding Description
`writer.js` builds `objNewUnitProps` for a new unit with placeholder values: [1](#0-0) 

Immediately after, the (incomplete) object is published into the global cache `storage.assocUnstableUnits[objUnit.unit]` and, when `conf.bFaster` is enabled, also linked into `storage.assocBestChildren`: [2](#0-1) 

Only afterwards does an `arrOps` async chain compute and fill in the remaining, safety-critical fields: [3](#0-2) 

`updateLevel()` performs a DB query and only then sets `objNewUnitProps.level`: [4](#0-3) 

`updateBestParent()`/`updateWitnessedLevel()` similarly do multi-step async DB work before assigning `best_parent_unit`/`witnessed_level` on the same object: [5](#0-4) [6](#0-5) 

Meanwhile, `storage.readUnitProps()` — the primary accessor used throughout validation and main-chain code — has a fast path that returns the raw, possibly-incomplete cached object with no synchronization whatsoever when `conf.bFaster` is set: [7](#0-6) 

`validation.validate()` locks only on the *unit's own author addresses*, not on a global "write" mutex: [8](#0-7) 

`writer.saveJoint()` runs under the `"write"` mutex, but that lock does not block validation of a different unit keyed by different author addresses, and the async DB round-trips inside `updateLevel`/`updateBestParent`/`updateWitnessedLevel` yield the event loop, giving other queued validations (locked on different keys) a chance to run concurrently: [9](#0-8) 

If a second unit (posted by any unprivileged network participant) names the still-being-written unit as a parent, its validation/main-chain code paths (e.g. `main_chain.js`'s direct reads of `storage.assocUnstableUnits[unit]`, or `readBestChildrenProps`) can observe `level: null`, missing `best_parent_unit`, or missing `witnessed_level` on the parent, because these fields are populated on the *same shared object reference* only after further async I/O completes: [10](#0-9) [11](#0-10) 

This is structurally analogous to the l2tp bug: a shared object (`sk`/tunnel socket in the kernel case, the unit-props object here) is published into a global lookup table before all of its fields are initialized, and it is then mutated in place without any lock that a concurrent reader is required to respect.

### Impact Explanation
`level`, `best_parent_unit`, and `witnessed_level` are inputs to best-parent selection, DAG-level assignment, and stability determination (`main_chain.js`). If concurrent validation of a second unit observes a torn version of these fields for its just-published parent, different nodes — depending on precisely how their event loops interleave incoming units — can compute different best-parent/level/witnessed-level results for the same unit, or crash via the `throwError`/`throw Error("null level...")` guards embedded in `updateLevel`/`determineMaxLevel`, which are consistency assertions rather than validation-time checks. Either outcome can produce node disagreement on unit validity/level/stability (a DAG-consensus-integrity issue) or an assertion-triggered process crash reachable by ordinary unit posting from an unprivileged network participant, without requiring any special privilege, hub role, or peer trust.

### Likelihood Explanation
Triggering the race requires only posting two ordinary units in quick succession where the second references the first as a parent before the first's writer has finished its `updateLevel`/`updateBestParent`/`updateWitnessedLevel` chain (each of which performs a genuine DB round-trip and therefore yields the event loop). This is a normal, unprivileged posting pattern (not reliant on malicious peers, hubs, or catch-up/sync-specific code paths) and is more easily triggered under high transaction throughput or on slower storage backends where the DB round-trips inside the writer take measurably longer, widening the race window. The `conf.bFaster` fast-path in `readUnitProps` is the direct enabler; whether `conf.bFaster` is enabled by default is not established from the code reviewed, which affects exact exploitability, but the underlying publish-then-populate pattern in `writer.js` exists regardless of this flag for other consumers that read `storage.assocUnstableUnits` directly (e.g., `main_chain.js`).

### Recommendation
- Build the complete `objNewUnitProps` object (including `level`, `best_parent_unit`, `witnessed_level`) fully before inserting it into `storage.assocUnstableUnits`/`storage.assocBestChildren`, instead of publishing a placeholder and mutating it in place afterward.
- Alternatively, serialize unit-writing against unit-validation more strictly (e.g., have `validation.validate()` also acquire the `"write"` lock, or a per-unit lock covering the publish window) so that no other validation can observe `assocUnstableUnits[unit]` until it is fully populated.
- Add defensive checks in `readUnitProps`/`readStaticUnitProps` fast paths to detect and reject (or await) still-initializing entries (e.g., `level === null` for a non-genesis, already-published unit) rather than returning them as if complete.

### Proof of Concept
1. Configure/observe a node running with `conf.bFaster = true` (this is required for the vulnerable direct-return fast path in `readUnitProps` at storage.js:1504-1505; behavior with a slow storage backend — e.g. remote/high-latency DB — widens the race window for `updateLevel`/`updateBestParent`/`updateWitnessedLevel`).
2. From an unprivileged posting client, submit unit A (any valid content-bearing unit).
3. As soon as A passes validation and `writer.saveJoint()` begins executing (i.e., `storage.assocUnstableUnits[A]` has just been set at writer.js:597, with `level: null`), immediately submit unit B whose `parent_units` include A.
4. Because `validation.validate()` for B is locked only on B's author addresses (validation.js:357), and A's writer is mid-flight inside its own `"write"`-locked async chain (writer.js:34, 617-635) which yields the event loop during its DB round trips, B's validation path can read `storage.assocUnstableUnits[A]` (via `storage.readUnitProps`, storage.js:1497-1505, or direct cache access in `main_chain.js`) while `A.level` is still `null` / `best_parent_unit`/`witnessed_level` are unset.
5. Observe divergent behavior: either an internal consistency `throw Error(...)` (e.g., "null level in updateWitnessedLevel", writer.js:529) crashing the node process, or B being processed with an incomplete view of A's DAG position, which can lead to a best-parent/level/witnessed-level computation for B that differs from what other nodes (which happened not to race) compute for the same unit — producing node disagreement on validity/stability.

**Note on verification**: I could not fully trace every downstream consumer of `storage.assocUnstableUnits`/`assocBestChildren` to confirm a concrete, deterministic double-spend or supply-inflation outcome (as opposed to a crash or stability/level divergence) within the available search iterations; the finding is grounded in the exact publish-before-initialize pattern and the read-time absence of synchronization, mirroring the CVE's root cause, but the full blast radius of the resulting DAG-metadata divergence across `main_chain.js` stability logic was not exhaustively traced.
