### Title
`OpenedHandler#provision?` operator-precedence bug lets review stacks be created even when `review_stacks_enabled: false` - ([File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb])

### Summary
`provision?` in `OpenedHandler` combines `repository.review_stacks_enabled` with the three `provisioning_behavior` predicates using `&&`/`||` without parentheses. Because `&&` binds tighter than `||`, `review_stacks_enabled` is only ANDed into the first (`allow_all`) branch; the `allow_with_label` and `prevent_with_label` branches are evaluated independently of the flag. A repository configured with `review_stacks_enabled: false` and `provisioning_behavior: :prevent_with_label` will still provision a review `Stack` for any opened, unlabeled pull request.

### Finding Description
The broken binding: the code's intended invariant is `repository.review_stacks_enabled == false → Stack.count unchanged` for any `provisioning_behavior`. The actual code is: [1](#0-0) 

which Ruby parses as:
```
(review_stacks_enabled && allow_all?) ||
(allow_with_label? && has_label?) ||
(prevent_with_label? && !has_label?)
```
`review_stacks_enabled` is not distributed across the `||` clauses, so when `provisioning_behavior` is `prevent_with_label` and the PR carries no provisioning label, the third clause alone evaluates to `true`, making `provision?` return `true` regardless of `review_stacks_enabled`.

`process` then unconditionally calls `ReviewStackAdapter#find_or_create!`, which creates a `Stack` record, its `PullRequest`, and enqueues it via `ReviewStackProvisioningQueue.add`: [2](#0-1) [3](#0-2) 

That queue later calls `stack.provisioner.provision?` and `stack.provision`, i.e. actual provisioning/task execution: [4](#0-3) 

Attacker's exact action: open (or have anyone open, since this is triggered by GitHub webhooks on any PR against the configured repo) a pull request without adding any label, against a repository whose owner set `review_stacks_enabled: false` intending to fully disable review stacks, but left `provisioning_behavior: prevent_with_label` configured (e.g. a residual/staged setting). No signature bypass, no privilege escalation of webhook auth is needed — this is purely a logic flaw downstream of a validly-signed webhook for an already-configured repository; `verify_signature`/`GitHubApp#verify_webhook_signature` and `drop_unhandled_event` are irrelevant since the webhook itself is legitimate for that repo. The comparable `LabeledHandler` correctly gates its logic with `repository.review_stacks_enabled && (archive? || unarchive?)` at the top level: [5](#0-4) , confirming `OpenedHandler` diverges from the intended pattern.

### Impact Explanation
For any repository misconfigured this way (an operator-controlled but easily overlooked combination, since disabling review stacks via `review_stacks_enabled: false` is the documented "kill switch"), an unprivileged contributor opening a PR causes creation of a `Stack`/`ReviewStack` and downstream provisioning/task execution that the operator explicitly believed was disabled. This is repeatable per PR opened, is unauthenticated with respect to the acting GitHub user (only requires ability to open a PR against the target repo), and results in resource creation and task execution the repository owner did not authorize. This matches "a record written for a repository that did not authenticate it" / unauthorized task execution triggered by an unprivileged actor.

### Likelihood Explanation
Requires: (1) `review_stacks_enabled: false` set on the `Repository` record, and (2) `provisioning_behavior` set to `prevent_with_label` (or `allow_with_label`, which is also unaffected by the flag) — both are legitimate, operator-set configuration values, not attacker-controlled. Given those settings, exploitation is trivial and 100% reliable: any opened PR without the provisioning label triggers stack creation. This is a real configuration an operator could set expecting the boolean to be a hard kill switch, so likelihood of the misconfiguration existing is plausible, and exploitation cost for an attacker (once misconfigured) is zero.

### Recommendation
Parenthesize the intended grouping so `review_stacks_enabled` gates every branch:
```ruby
def provision?
  repository.review_stacks_enabled &&
    (repository.provisioning_behavior_allow_all? ||
     (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
     (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?))
end
```

### Proof of Concept
Minitest in `test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb` (existing file, add a case):
```ruby
test "#process does not create a stack when review_stacks_enabled is false, even with prevent_with_label and no label" do
  repository = shipit_repositories(:shipit)
  repository.update!(review_stacks_enabled: false, provisioning_behavior: :prevent_with_label)

  params = build_opened_params(repository: repository, labels: [])
  assert_no_difference "Shipit::Stack.count" do
    Shipit::Webhooks::Handlers::PullRequest::OpenedHandler.new(params).process
  end
end
```
Binding checked: `repository.review_stacks_enabled == false` (left side) must imply `Stack.count` unchanged (right side); currently the assertion fails because `provision?` returns `true` via the `prevent_with_label` branch, creating a `Stack`.
