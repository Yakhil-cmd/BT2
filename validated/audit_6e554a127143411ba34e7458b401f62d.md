### Title
Uncaught exceptions thrown deep inside the AA-trigger execution loop crash the whole ocore node - ([File: aa_composer.js])

### Summary
`aa_composer.js` processes Autonomous Agent (AA) triggers in `handleAATriggers()` / `handlePrimaryAATrigger()` / `handleTrigger()`, a synchronous-looking async chain that is invoked directly from the unit-write path (`writer.js` `saveJoint()` → `main_chain.js` `stabilizeMci()`/`markMcIndexStable()` → `aa_composer.handleAATriggers()`), i.e. every time an MCI stabilizes and any pending AA trigger exists. Several code paths inside this chain use `throw Error(...)` instead of routing the error to the `onDone`/`cb` callback, e.g. the "unit not found in cache" check, the "batch write failed" check, and — most importantly — the AA-response-unit validation callbacks `ifJointError`, `ifTransientError`, `ifNeedHashTree`, `ifNeedParentUnits`, `ifOkUnsigned`, and the `sequence !== 'good'` check in `validateAndSaveUnit()`. [1](#0-0) 
None of these throws are wrapped in a `try/catch` anywhere along the call chain (`handleTrigger` → `handlePrimaryAATrigger` → `handleAATriggers` → `writer.js` `saveJoint`), so the exception propagates all the way to the top of the event loop and fires Node's global `process.on('uncaughtException', ...)` handler in `network.js`, which explicitly re-throws to crash the process: [2](#0-1) 

This is the same bug class as CVE-2025-68135 (EVerest `TbdController`): a critical processing loop that is reachable from external/untrusted input does not defensively handle exceptions, so a single failure silently (or loudly) terminates the entire process rather than just failing the one operation.

### Finding Description
Any user can define an Autonomous Agent by simply posting a `definition` message (`AA` oscript) — this is a completely permissionless, unprivileged action. Anyone can then trigger that AA by sending it a payment. When the AA’s trigger becomes part of a stable MCI, `main_chain.js`’s `stabilizeMci()`/`markMcIndexStable()` schedules the trigger and unconditionally calls `aa_composer.handleAATriggers()`: [3](#0-2) [4](#0-3) 

`handleAATriggers()` iterates all pending triggers and calls `handlePrimaryAATrigger()`, which reads the AA definition, builds a `trigger`, and calls `handleTrigger()` to actually execute the AA's oscript and assemble/save a response unit: [5](#0-4) 

Inside `handleTrigger()`, once the AA formula is evaluated and the response messages are assembled, `validateAndSaveUnit()` re-validates the freshly composed AA-response unit through the normal `validation.validate()` machinery. Because the AA author fully controls the AA's oscript (message templates, `outputs`, `asset` messages, `definition` messages, etc.), the author can shape the composed response unit so that it fails validation in one of the "should never happen" branches that the code treats as fatal instead of recoverable:
- `ifJointError` → `throw Error("AA validation joint error: " + err)`
- `ifTransientError` → `throw Error("AA validation transient error: " + err)`
- `ifNeedHashTree` → `throw Error(...)`
- `ifNeedParentUnits` → `throw Error(...)`
- `ifOkUnsigned` → `throw Error(...)`
- non-`'good'` sequence → `throw Error("nonserial AA")` [6](#0-5) 

Other unconditional throws in the same call chain that an attacker-controlled AA/trigger can plausibly reach include the `batch.write` failure check and the post-write cache-consistency check inside `handlePrimaryAATrigger`: [7](#0-6) 

None of these `throw`s are caught by the callers. `handleTrigger`/`handlePrimaryAATrigger`/`handleAATriggers` are plain callback-style functions with no `try/catch`, and the outer caller in `writer.js` simply `await`s `aa_composer.handleAATriggers()` inside `saveJoint()`, which itself is invoked from unit validation/writing of a normally-received network unit: [8](#0-7) 

An uncaught synchronous throw from a callback executed off the microtask/callback queue is not captured by any `try/catch` up the stack and becomes a Node.js `uncaughtException`. `network.js` installs a global handler that logs it and then deliberately re-throws to terminate the process: [2](#0-1) 

Because AA-trigger processing is mandatory and synchronous with respect to MCI stabilization (every full node must execute the same triggers to agree on state), this code path runs on every node that has this AA and processes network traffic, not just the AA owner.

### Impact Explanation
A crash of the ocore process is a denial-of-service condition for the entire node: no more units can be validated, written, gossiped, or served (hub, relay, light-vendor functionality all die with the process). Since AA-trigger execution is deterministic and mandatory for all full nodes to keep the DAG/state consistent, an attacker who can compose a payload that causes any node executing the trigger to hit one of the unguarded `throw` branches can force that node's process down — an unprivileged AA trigger sender can effectively deny service to the network's ability to confirm new units on affected nodes. This matches "a network unable to confirm new units" in the acceptance criteria, and is analogous to CVE-2025-68135, where an unhandled exception in a critical processing loop silently killed the controller and its DoS-relevant subsystems.

### Likelihood Explanation
Both AA definition and AA triggering are completely permissionless operations available to any wallet holder — no special privilege, hub cooperation, or malicious peer/node is required, satisfying the "AA author / trigger sender" reachability requirement. The exact conditions that flip `ifOk` into `ifJointError`/`ifTransientError`/etc. are internal validation edge cases (I was not able to fully enumerate, in the time available, every joint/unit-level check in `validation.js` that would need to fire for a legitimately-composed-but-attacker-shaped AA response to fail there instead of via the normal `ifUnitError` path, which is properly caught via `cb(err)`/`bounce(err)`). This is the main uncertainty in this analysis: proving a concrete, minimal AA definition that deterministically reaches `ifJointError`/`ifTransientError` (rather than the safely-handled `ifUnitError`) requires deeper enumeration of `validation.js`'s joint- vs unit-level checks than could be completed here. The structural flaw itself — unguarded `throw` on "should never happen" branches inside a mandatory, externally-triggerable execution loop, feeding into a `process.on('uncaughtException')` handler that re-throws to kill the process — is clearly present and independently exploitable if any one of those throw sites can be reached with attacker-influenced data (which is plausible given the AA author fully controls the shape of the messages assembled into the response unit).

### Recommendation
- Wrap the body of `handleTrigger()`/`handlePrimaryAATrigger()`/`handleAATriggers()`, and especially the `validateAndSaveUnit()` validation callbacks, so that all "unexpected" conditions (`ifJointError`, `ifTransientError`, `ifNeedHashTree`, `ifNeedParentUnits`, `ifOkUnsigned`, non-`'good'` sequence, cache-consistency checks, batch-write failures) call the trigger's `bounce`/`onDone`/`cb` with an error instead of throwing synchronously.
- At minimum, wrap the top-level entry points that are reachable from network-processed data (`handleAATriggers`, `saveJoint`'s AA-trigger invocation) in `try/catch`, log the failure, mark the specific trigger/response as bounced or skip it, and continue processing other triggers/units rather than crashing the entire process.
- Reassess the blanket `throw err` in `network.js`'s `uncaughtException` handler for AA-trigger-originated errors specifically — killing the whole node in response to a single malformed/malicious AA is too aggressive; consider narrower error containment for the AA execution engine (similar to how sandboxed formula evaluation already reports errors via callbacks rather than throwing).

### Proof of Concept
Not fully constructible without deeper enumeration of `validation.js`'s joint-vs-unit error classification (see Likelihood Explanation). Conceptually: (1) attacker posts an AA definition whose oscript, when triggered, assembles response `messages` that are individually well-formed per AA-composer rules but violate a joint-level invariant checked by `validation.validate()` (e.g., an inconsistency between `objJoint`-level fields set by `aa_composer.js`'s `validateAndSaveUnit` such as `aa: true, aa_mci: mci` combined with attacker-controlled message content); (2) attacker sends any payment to this AA address; (3) when the triggering unit's MCI stabilizes on any full node, `aa_composer.handleAATriggers()` runs, `validateAndSaveUnit()`'s `ifJointError`/`ifTransientError` callback fires, `throw Error(...)` executes uncaught, and `network.js`'s `uncaughtException` handler crashes the node process.
