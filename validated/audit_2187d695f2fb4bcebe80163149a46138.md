## Title
Uniswap-like AA market maker computes investor payouts from raw `balance[asset]`/`balance[base]`, letting anyone inflate the pool by donating coins outside any matching case and drain LPs on divest - ([File: test/samples/uniswap_like_market_maker.oscript])

### Summary
The bundled `uniswap_like_market_maker.oscript` AA (an Autonomous Agent template shipped with ocore that anyone can deploy or copy) tracks liquidity-provider (LP) shares in the state variable `var['mm_asset_outstanding']`, but computes the amount of `base`/`$asset` to pay out on divest as a fraction of the AA's *actual on-chain balance* (`balance[$asset]`, `balance[base]`), which is read directly from the `aa_balances` table maintained by ocore's AA engine. Any unit author can send a payment to the AA's address that doesn't satisfy any of the defined `if` cases; the trigger's coins are still credited to the AA's real balance (silently absorbed, "no messages after filtering") while `mm_asset_outstanding` is left untouched. This is the oscript/ocore analog of the reported Vault bug: `totalSupply`/`balance` can be inflated by a direct transfer that bypasses the internal share-accounting variable, so a holder of even a tiny amount of the share asset can redeem a disproportionately large payout.

### Finding Description
The AA defines an internal share token `$mm_asset` and tracks the total outstanding shares in `var['mm_asset_outstanding']` [1](#0-0) . Investors "invest" by sending `base` + `$asset` in the correct ratio, and are issued shares proportional to `trigger.output[[asset=base]] / $bytes_balance` [2](#0-1) . On "divest", the payout is calculated as:
```
$investor_share = $mm_asset_amount / var['mm_asset_outstanding'];
... amount: "{ round($investor_share * balance[$asset]) }"
... amount: "{ round($investor_share * balance[base]) }"
``` [3](#0-2) 

`balance[...]` is not an internally-tracked accounting variable; it is evaluated by ocore's formula engine directly against `objValidationState.assocBalances`, which is populated from the real `aa_balances` table (the AA's true DAG balance, updated whenever *any* payment reaches the AA's address) [4](#0-3) [5](#0-4) .

Crucially, in ocore's AA execution model, when a trigger unit is sent to an AA address but none of the `messages.cases[].if` conditions evaluate to true, the AA still keeps the received coins - it just emits no messages and the trigger is treated as accepted with an empty response: `messages.length === 0` leads to `handleSuccessfulEmptyResponseUnit(null)`, not a bounce [6](#0-5) . Because this sample AA defines no `bounce_fees` override, the AA only requires the default minimal bounce fee to accept a trigger. Thus an attacker can send, e.g., a small amount of `base` (above the minimal bounce fee but below the `1e5` threshold used by the "invest" and "exchange bytes to asset" cases, with no `$asset` output) so that none of the four defined cases match; the funds are silently absorbed into `balance[base]` without any state update to `mm_asset_outstanding`.

Any address that already holds even 1 unit of `$mm_asset` (acquired cheaply through a prior small, correctly-ratioed investment) can then trigger the divest case. Since `$investor_share` is computed against the artificially inflated `balance[base]`/`balance[$asset]`, that holder receives more `base`/`$asset` than their legitimate share of the pool, draining value that rightfully belongs to other LPs - the same "donation inflates the redemption denominator" root cause as the referenced Vault report, just expressed through ocore's `balance[]` formula operator and AA trigger/case-matching semantics instead of `ERC20.transfer()`/`totalSupply()`.

### Impact Explanation
Any unprivileged sender who can post a unit (no special privilege, no operator/hub role) can donate coins directly to the AA to inflate `balance[base]`/`balance[$asset]` relative to `mm_asset_outstanding`, then redeem existing (or minimally purchased) shares for a disproportionately large payout, draining funds belonging to other LPs of the pool. This is a concrete unauthorized-fund-loss/AA-fund-drain scenario reachable purely from posted units/triggers, matching the High-severity class of the original report (draining a shared vault via a totalSupply/share accounting mismatch).

### Likelihood Explanation
The attack requires only: (1) acquiring a small amount of `$mm_asset` shares via a normal, correctly-ratioed "invest" (cheap, and could even be from a prior legitimate LP position), and (2) sending one additional payment to the AA's address structured to avoid matching any `if` case (e.g., `base` amount above the default bounce fee but below `1e5`, with no `$asset` output). Both steps are ordinary DAG payments requiring no special access, making this readily exploitable by any user, with profitability scaling with the size of the donation relative to the existing pool - the same dynamic noted in the original report.

### Recommendation
Track the pool's accounting balances in explicit state variables (e.g., `var['asset_reserve']`, `var['bytes_reserve']`) that are updated only inside the matched `if` cases, rather than deriving investor payouts from the AA's raw `balance[...]`, which reflects the total DAG balance and can be inflated by out-of-band donations or by payments that don't match any case. Alternatively, add a fallback case in `messages.cases` that bounces (or explicitly rejects/attributes) any payment that does not match one of the defined economic actions, so unmatched payments cannot silently inflate `balance[...]` without a corresponding update to `mm_asset_outstanding`.

### Proof of Concept
1. AA is deployed from `test/samples/uniswap_like_market_maker.oscript`; LPs have invested so that `balance[$asset]=A`, `balance[base]=B`, `var['mm_asset_outstanding']=S`.
2. Attacker sends a small correctly-ratioed investment to obtain 1 unit of `$mm_asset` (cases at lines 33-66 of the file [7](#0-6) ), so `S` increases by 1.
3. Attacker sends a second payment to the AA address containing only `base` with amount above the default minimum bounce fee but below `1e5`, and no `$asset` output. None of the four cases' `if` conditions match (invest needs `base>1e5`; divest needs `$mm_asset` output; exchange-bytes-to-asset needs `base>1e5`; exchange-asset-to-bytes needs `$asset` output). Ocore's AA engine treats this as an accepted trigger with no messages and keeps the coins in the AA's balance [6](#0-5) , so `balance[base]` becomes `B + donation` while `S` is unchanged.
4. Attacker triggers "divest" with their 1 unit of `$mm_asset`: `$investor_share = 1/S`; payout = `round((1/S) * (B + donation))` in bytes plus `round((1/S) * A)` in `$asset` [3](#0-2) , receiving far more `base` than the fair share `B/S` that 1 unit should be worth, at the expense of the remaining LPs.
