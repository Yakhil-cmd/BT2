### Title
`Shipit::Webhooks::Handlers::StatusHandler#process` applies GitHub status webhooks to commits by SHA alone, without scoping to the webhook's originating repository, allowing cross-tenant merge-queue unblocking - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` looks up commits with `Commit.where(sha: params.sha)` and applies the incoming `state` to every matching commit across the entire database, regardless of which repository the webhook payload claims to originate from. Unlike `PushHandler`, which uses the base `Handler#stacks` helper to scope work to `Repository.from_github_repo_name(repository_name)`, `StatusHandler` never checks `payload.dig('repository', 'full_name')` against the commit's owning stack/repository.

### Finding Description
The broken binding is: **the repository authorized by `verify_signature` (`repository_owner` from the payload, checked against `Shipit.github(organization: repository_owner)`) must equal the repository that owns the `Commit` record being mutated**. In `StatusHandler`, that equality is never enforced.

Code path:
- `WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-38`) only verifies that the payload was signed by the GitHub App/org associated with `repository_owner` in the payload. It does not verify that the `sha` referenced in the payload actually belongs to that same repository. [1](#0-0) 
- `StatusHandler#process` then does:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [2](#0-1) 
This is a global, unscoped lookup by `sha` across **all stacks/repositories** tracked by the Shipit instance. Compare this to `PushHandler#process`, which correctly scopes to the owning repository via the base `Handler#stacks` helper:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end
``` [3](#0-2) [4](#0-3) 
`StatusHandler` does not call `stacks` or otherwise filter on `repository_name` at all.

Once a matching `Commit` record is found (regardless of which stack/repository it belongs to), `commit.create_status_from_github!` creates a `Status` scoped to the **commit's own `stack_id`** (not the webhook payload's repo), so the update is durably attributed to the victim stack:
```ruby
def create_status_from_github!(github_status)
  add_status do
    statuses.replicate_from_github!(stack_id, github_status)
  end
end
``` [5](#0-4) 
This feeds `Commit#blocking?`/`#blocked?` (`app/models/shipit/commit.rb:219,231-237`), `Stack#merge_status`/`#branch_status` (`app/models/shipit/stack.rb:286-292,298`), and `Stack#allows_merges?` (`app/models/shipit/stack.rb:380-382`), and status transitions to `success`/`pending` explicitly enqueue `ProcessMergeRequestsJob` (as shown in `test/models/commits_test.rb:763-777`), which will merge queued PRs once `allows_merges?` is true. [6](#0-5) [7](#0-6) [8](#0-7) 

Exploit flow: because a git commit's SHA-1 is computed from its content (tree, parents, author/committer, message) and does not encode which repository it lives in, the *same* commit SHA can legitimately exist in two different repositories/stacks tracked by Shipit — e.g. a fork sharing pre-fork history with the victim repo, or a repository that has cherry-picked/replayed the exact same raw commit object. If Shipit already has a `Commit` row for that SHA under the victim's `merge_queue_enabled` stack (synced via a legitimate prior push), the attacker only needs:
1. A repository they control that is also connected to Shipit (and under a GitHub org/App the attacker can trigger real, correctly-signed status webhooks for — e.g., their own repo, or any repo they can push commit-status-generating CI to within an org Shipit is configured for), and
2. That repository to contain (or reference) a commit with the same SHA as the victim's currently-blocking commit.

The attacker then triggers a genuine GitHub status event (e.g., via their own CI) with `state: success` for that SHA. GitHub signs and delivers it correctly (`verify_signature` passes, since it's a real webhook for a real, attacker-owned repo/org). `StatusHandler#process` ignores which repository the payload came from and updates the `Status` for **every** `Commit` row with that SHA — including the one belonging to the victim's stack — flipping `commit.blocking?` to `false`, `Stack#blocking_statuses`/`branch_status` to `success`, `Stack#merge_status` to `'success'`, and `Stack#allows_merges?` to `true`, at which point `ProcessMergeRequestsJob` (already scheduled by the state transition) merges queued PRs on the victim's stack.

No existing guard catches this: `verify_signature` only authenticates "this payload came from GitHub for this org," not "this SHA belongs to the repo that org owns"; `drop_unhandled_event`/`check_if_ping` are irrelevant; the `ExplicitParameters` schema for `StatusHandler` only validates `sha`/`state` types, not repository ownership.

### Impact Explanation
An attacker who controls a repository connected to Shipit (their own fork/repo, no special privilege, no Shipit session/token, no `webhook_secret`) can cause a `Status` record to be written against another tenant's `Commit`, unblocking that victim stack's merge gate and causing `ProcessMergeRequestsJob` to merge queued pull requests without the victim repository's actual CI having passed. This is a cross-tenant write ("a payload for one repository mutating another's stack/commit") culminating in an unauthorized merge — matching the Critical impact category. It is repeatable against any stack/commit sha collision the attacker can arrange or discover (e.g., shared history via forks, which is common), and the blast radius spans all stacks that happen to share commit objects with attacker-reachable repositories.

### Likelihood Explanation
Preconditions: victim stack has `merge_queue_enabled: true` and is currently blocked by a real failing/pending blocking status on a specific commit SHA; that same SHA must also be resolvable to a `Commit` row (i.e., previously synced by a push) that the attacker can trigger a legitimately-signed status webhook for, from a repository/org they control or contribute to. This is most straightforward when the victim repo has been forked (all pre-fork commits share identical SHAs), a common real-world scenario, or when a shared/vendored/cherry-picked commit exists across repos in the same GitHub org monitored by one Shipit instance. Attacker cost is low: no secrets needed, only ownership/push access to a repository already connected to Shipit and knowledge of the target SHA (visible from the victim's public GitHub commit history or the merge status page).

### Recommendation
Scope `StatusHandler#process` to the repository named in the webhook payload, mirroring `PushHandler`/`Handler#stacks`:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
end
```
using the base `Handler#stacks` (`Repository.from_github_repo_name(repository_name)`) so a status update can only affect commits belonging to stacks whose repository matches the authenticated webhook's `repository.full_name`. Apply the same scoping review to any other handler that resolves records purely by `sha` without checking `payload['repository']['full_name']` (e.g., `CheckSuiteHandler`, if it has the same pattern — not fully verified in this review).

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb`, new or extended):
```ruby
test "StatusHandler does not update commits belonging to a different repository's stack" do
  victim_stack = shipit_stacks(:shipit) # repo: shopify/shipit-engine, merge_queue_enabled: true
  attacker_repo = Repository.create!(owner: 'attacker', name: 'attacker-repo')
  attacker_stack = Stack.create!(repository: attacker_repo, environment: 'production')

  shared_sha = 'deadbeef' * 5 # same content-addressed sha existing in both repos' histories
  victim_commit = victim_stack.commits.create!(sha: shared_sha, message: 'shared ancestor')
  victim_commit.statuses.create!(stack: victim_stack, state: 'failure', context: 'ci/blocking')

  attacker_commit = attacker_stack.commits.create!(sha: shared_sha, message: 'shared ancestor')

  # Binding under test:
  # webhook_authorized_repository == 'attacker/attacker-repo'
  # commit_mutated.stack.repository == victim_stack.repository  <-- should be false, currently true
  assert_equal 'attacker/attacker-repo', ... # payload repository
  refute_equal victim_stack.repository, attacker_stack.repository

  refute_predicate victim_stack.reload, :allows_merges?

  payload = {
    'sha' => shared_sha,
    'state' => 'success',
    'context' => 'ci/blocking',
    'repository' => { 'full_name' => 'attacker/attacker-repo', 'owner' => { 'login' => 'attacker' } }
  }
  Shipit::Webhooks::Handlers::StatusHandler.call(payload)

  # After fix: victim commit/stack must be untouched by attacker's webhook.
  refute victim_commit.reload.statuses.exists?(context: 'ci/blocking', state: 'success')
  refute_predicate victim_stack.reload, :allows_merges?
end
```
Currently (pre-fix), this assertion fails: `victim_stack.reload.allows_merges?` becomes `true` and `victim_commit`'s status flips to `success`, demonstrating the cross-tenant mutation via `StatusHandler#process`'s unscoped `Commit.where(sha:)` lookup.
