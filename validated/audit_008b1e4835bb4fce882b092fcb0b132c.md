### Title
Incorrect voting-weight math in `countVotes()` uses present balance instead of balance-at-vote-time for system parameter votes - (File: main_chain.js)

### Summary
`countVotes()` in `main_chain.js` determines consensus-critical system variables (`op_list`, `threshold_size`, `base_tps_fee`, `tps_interval`, `tps_fee_multiplier`) by summing each voter's **current** stable balance and applying it to every vote the address has ever cast, regardless of when the vote was cast relative to when the balance was held. This is the same bug class as the reported `EscrowManager.getPastVotes()` issue: a present-time rate/value (current balance) is substituted for the historical value that should apply to a past event (the vote), producing incorrect weighting.

### Finding Description
Any address can post a `system_vote` or `numerical_vote` message. When an MCI stabilizes, `countVotes()` is invoked to tally these votes: [1](#0-0) 

The balances collected here are computed against the **current** stable UTXO set at the time counting happens (`bal_rows` — outputs that are stable and unspent as of now), not the balance the address actually held when it authored the `system_vote`/`numerical_vote` unit. These current balances are stored into a temporary `voter_balances` table and then joined against votes filtered only by `timestamp>=since_timestamp`: [2](#0-1) 

The vote-timeframe window (`since_timestamp`) can span multiple years into the past: [3](#0-2) 

Yet the weight applied to a vote cast at any point inside that multi-year window is always the voter's **present** balance: [4](#0-3) [5](#0-4) 

This mirrors the reported class of bug exactly: the current "rate" (balance) is used to compute the weight of a past action (the vote), instead of the balance that existed when the vote was cast, so the tally diverges from the historically correct value.

### Impact Explanation
`countVotes()` sets `storage.systemVars.op_list`, `threshold_size`, `base_tps_fee`, `tps_interval`, and `tps_fee_multiplier` — parameters that directly control witness/order-provider selection and TPS fee economics network-wide. Because vote weight is decoupled from the balance actually held at vote time, an address can cast a `system_vote`/`numerical_vote` while holding a negligible balance and later acquire (or borrow/park) a large balance right before the annual vote-count runs, causing that old, cheaply-cast vote to be counted with disproportionately large weight it never actually possessed historically. Conversely, a voter who legitimately voted with a large balance and later spent it down has their vote's weight silently reduced even though the vote reflected their holdings at the time. Because this can steer the elected `op_list` (order providers/witnesses), it creates a path for the network to disagree over time on who the legitimate operators are, or to skew TPS-fee-related system variables, both of which affect the network's ability to reach consistent, correct consensus state.

### Likelihood Explanation
Any unprivileged address can send a `system_vote` or `numerical_vote` message at any time for negligible cost; balances can be moved between addresses cheaply and are entirely under user control. Since the vote-counting window can reach back multiple years, an attacker has ample opportunity to time balance accumulation to exploit the mismatch between vote-time balance and count-time balance, making the flaw practically exploitable rather than purely theoretical.

### Recommendation
Snapshot and record the voter's balance (or use a balance measured as of the vote's own timestamp/MCI) at the moment the `system_vote`/`numerical_vote` unit is written, and use that historical balance — not the balance queried at counting time — when aggregating vote weight in `countVotes()`.

### Proof of Concept
1. Address A holds a negligible balance and sends a `numerical_vote` for `base_tps_fee` (or a `system_vote` for `op_list`) at time T0.
2. Over the following months, A accumulates a very large balance (e.g., receives many bytes).
3. When `countVotes()` runs at MCI stabilization near the end of the annual window, the `bal_rows` query in main_chain.js:1757-1777 picks up A's large **current** balance and applies it to A's old vote from T0, even though A held almost nothing at that time — inflating A's influence over the final `op_list`/`threshold_size`/etc. far beyond what their holdings justified when they actually voted.
