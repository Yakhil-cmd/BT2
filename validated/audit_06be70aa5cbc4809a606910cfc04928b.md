### Title
Cross-repository commit status forgery via `StatusHandler` — organization authenticated by webhook signature is never bound to the commit/stack actually written - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
This is a direct analog of the `LiquidateWithReplacement` bug class: a verification step authenticates one entity (the organization owning the webhook secret) while a *different*, unchecked field of the same payload is used to determine what gets mutated (the commit/stack that receives the forged status). `WebhooksController#verify_signature` selects the HMAC secret using `repository.owner.login` from the untrusted JSON body, but the `StatusHandler` that actually writes data ignores `repository` entirely and looks up commits globally by `sha`.

### Finding Description
`WebhooksController#verify_signature` derives the signing organization exclusively from the attacker-supplied payload and verifies the raw body against that organization's webhook secret: [1](#0-0) [2](#0-1) 

Once the signature is accepted, `WebhooksController#create` dispatches the full JSON `params` to the registered handler for the event, with no re-binding of the verified organization to any specific repository: [3](#0-2) 

For most events, `Handler#stacks` correctly scopes the mutation to the repository named in the payload (`Repository.from_github_repo_name(repository_name)`): [4](#0-3) 

However, `StatusHandler#process` never calls `stacks` / never scopes by repository at all — it looks up commits **instance‑wide** purely by `sha` and writes a status to every match: [5](#0-4) 

This breaks the binding `verified_organization == mutated_repository`. Any organization that is legitimately onboarded to this Shipit instance (and therefore knows its own webhook secret, exactly as intended by the deployment model) can send a `status` event whose signature is valid for *its own* organization, but whose `sha` corresponds to a commit tracked under a completely unrelated stack/repository belonging to a different organization in the same instance. Because commit SHAs are not secrets (they're visible in any public GitHub UI, PR link, or CI log), the attacker does not need any access to the victim repository to learn a valid target SHA.

### Impact Explanation
Commit status directly drives deploy authorization. `Commit#deployable?` is `success? && !blocked?` (or `stack.ignore_ci?`), and `state`/`success?` are delegated to `Status`, which is populated from `Commit#create_status_from_github!`: [6](#0-5) [7](#0-6) 

`Stack#trigger_continuous_delivery` / `next_commit_to_deploy` pick the next commit to deploy based on `deployable?`: [8](#0-7) [9](#0-8) 

By forging a `status` webhook (signed with their own, legitimately-known organization secret) that targets a victim commit's `sha` with `state: "success"`, an unprivileged-relative-to-the-victim attacker can flip a victim commit into `deployable?`, unlocking `trigger_continuous_delivery`/`deploy` for a repository they have no authorization over. This matches the required "unauthorized deploy" impact class.

### Likelihood Explanation
The prerequisite (being a legitimately onboarded organization with its own webhook secret configured in this Shipit instance) is the normal, documented multi-tenant deployment model — no `ApiClient` token, GitHub App private key, or Shipit session is required, only knowledge of a public commit SHA belonging to another onboarded repository. This is realistic in shared/multi-org Shipit deployments and requires only crafting one unauthenticated-to-Shipit HTTP POST with a valid signature for the attacker's own org.

### Recommendation
Scope `StatusHandler` (and any other handler that doesn't already do so) through `Handler#stacks`, i.e. resolve commits only within `Repository.from_github_repo_name(payload.dig('repository','full_name'))&.stacks`, and additionally verify that the `repository.owner.login` used to select the webhook secret matches the owner encoded in `repository.full_name` before dispatching to handlers.

### Proof of Concept
1. Onboard/attacker-control Org A in the Shipit instance; know Org A's webhook secret (as any legitimate Org A admin does).
2. Find a public commit SHA belonging to Org B's repository, tracked in Org B's stack (e.g., from a public PR or CI log).
3. POST to `/github_hooks` (or configured webhook path) with `X-Github-Event: status`, a body `{"sha": "<Org B commit sha>", "state": "success", ...}` (no `repository` scoping matters since `StatusHandler` ignores it), and `X-Hub-Signature` computed with Org A's known secret.
4. `verify_signature` succeeds (Org A's secret matches Org A's own signature) as shown in [1](#0-0) .
5. `StatusHandler#process` ( [10](#0-9) ) finds the matching commit belonging to Org B and writes a fabricated `success` status, regardless of the fact that the signature only ever proved knowledge of Org A's secret.
6. If Org B's stack has continuous deployment enabled, the forged status can make the targeted commit `deployable?`, triggering an unauthorized deploy.

# frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class StatusHandler < Handler
        params do
          requires :sha, String
          requires :state, String
          accepts :description, String
          accepts :target_url, String
          accepts :context, String
          accepts :created_at, String

          accepts :branches, Array do
            requires :name, String
          end
        end

        def process
          Commit.where(sha: params.sha).each do |commit|
            commit.create_status_from_github!(params)
          end
        end
      end
    end
