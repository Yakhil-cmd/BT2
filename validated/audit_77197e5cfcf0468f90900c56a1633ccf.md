### Title
Cross-network replay of `signed_message`/`is_valid_signed_package` due to missing chain/network identifier in the signed hash - ([File: signed_message.js])

### Summary
The `signed_message` mechanism (used by wallets, `Device.getLoginMessage`, and AA oscript's `is_valid_signed_package()`) signs a hash produced by `objectHash.getSignedPackageHashToSign()`, which never includes any network/chain identifier (no `alt`, no genesis unit, no network name). Because address derivation via `getChash160()` is also independent of the network, the exact same address/keypair and the exact same signed message produce an identical signable hash on every Obyte-compatible network (mainnet, testnet, or any other ocore-based fork). A signature produced for use on one network can therefore be replayed verbatim on another.

### Finding Description
`signMessage()` in `signed_message.js` builds an object containing only `version`, `signed_message`, `authors`, and optionally `last_ball_unit`, and signs `objectHash.getSignedPackageHashToSign(objUnit)`: [1](#0-0) 

`getSignedPackageHashToSign()` simply strips `authentifiers` and hashes the remaining fields with `getSourceString`/`getJsonSourceString` — no chain/network identifier is mixed into the hash: [2](#0-1) 

The corresponding validator, `validateSignedMessage()`, explicitly whitelists only `["signed_message", "authors", "last_ball_unit", "timestamp", "version"]` as allowed fields — there is no `alt` (the network/chain discriminator used elsewhere in the codebase, e.g. `constants.alt`) or any other network-identifying field in this whitelist: [3](#0-2) 

For comparison, ordinary DAG units *do* include `alt` in the hashed content via `getStrippedUnit()`/`getNakedUnit()`, which is exactly the field that prevents cross-network replay for regular unit signatures: [4](#0-3) [5](#0-4) 

However, `signed_message` objects (used for off-chain attestations, order signing, and oracle-style data, unrelated to the DAG unit itself) do not carry this field at all, and `getSignedPackageHashToSign` does not add one. Since address derivation (`getChash160`) is also network-agnostic, an address with a given private key is identical on every Obyte-derived network, so a signature that authenticates a `signed_message` on one network is valid input to `is_valid_signed_package()` on any other network running the same/similar AA logic.

This primitive is directly reachable by an unprivileged AA trigger sender: oscript's `is_valid_signed_package(signed_package, address)` function calls straight into `signed_message.validateSignedMessage()`: [6](#0-5) 

and is used by AA templates such as order-book/exchange and payment-channel contracts to authorize actions (e.g., order placement/cancellation, channel state updates) based on a counterparty's off-chain signature: [7](#0-6) 

### Impact Explanation
Any off-chain authorization built on `signed_message` / `is_valid_signed_package` (order signing for exchange AAs, payment-channel state signatures, or wallet login-style attestations reused inside an AA) can be replayed identically on a different Obyte-based network or a hard fork sharing the same address space, because the signed hash carries no chain/network binding. An attacker who obtains a legitimately-signed `signed_message` (e.g., a user's signed order or payment-channel update on testnet, or a future fork) can resubmit it as a trigger to an AA on mainnet (or vice versa) that performs equivalent logic, causing the AA to accept an authorization the user never intended to make on that network — leading to unauthorized state changes / fund loss in AAs that rely on this signature scheme for access control.

### Likelihood Explanation
Exploitability requires: (1) an AA using `is_valid_signed_package` for authorization (a documented, supported oscript pattern, demonstrated in the shipped `order_book_exchange.oscript` and `payment_channels.oscript` samples), and (2) the same address/private key being used or reachable across two networks that both run compatible AA logic (e.g., a project deployed on both testnet and mainnet with identical AA code, or a future/alternate ocore-based network). This is a realistic deployment pattern since testnet and mainnet share the exact same address derivation and wallet software. No privileged access is needed — any holder of a validly-signed message can replay it.

### Recommendation
Bind the signed hash to the network by including `constants.alt` (or another explicit network/genesis identifier) in the object hashed by `getSignedPackageHashToSign()`, and add `alt` to the field whitelist enforced in `signed_message.js`'s `validateSignedMessage()` so that a signed package is only valid on the network it names, mirroring how regular unit signing already includes `alt` via `getStrippedUnit()`.

### Proof of Concept
1. On network A (e.g. testnet, `constants.alt = "T"`), a user calls `signMessage()` to produce a `signed_message` object `{version, signed_message, authors, last_ball_unit}` authorizing e.g. an order or channel update, targeting an AA that checks `is_valid_signed_package(trigger.data.signed_package, expected_address)`.
2. `objectHash.getSignedPackageHashToSign()` hashes only `version/signed_message/authors/last_ball_unit` — no `alt` — per `object_hash.js` lines 97-103.
3. The identical signed object (same address, same signature bytes) is submitted as `trigger.data.signed_package` in a unit sent to an equivalent AA deployed on network B (e.g. mainnet, or a differently-configured ocore fork) where the same address/definition is valid.
4. `signed_message.validateSignedMessage()` on network B accepts the package because its field whitelist and hash computation are identical and contain no network discriminator (`signed_message.js` lines 130-137, `object_hash.js` lines 97-103), so `is_valid_signed_package` returns `true` and the AA executes the (unintended, cross-network) authorization.

function getSignedPackageHashToSign(signedPackage) {
	var unsignedPackage = _.cloneDeep(signedPackage);
	for (var i=0; i<unsignedPackage.authors.length; i++)
		delete unsignedPackage.authors[i].authentifiers;
	var sourceString = (typeof signedPackage.version === 'undefined' || signedPackage.version === constants.versionWithoutTimestamp) ? getSourceString(unsignedPackage) : getJsonSourceString(unsignedPackage);
	return crypto.createHash("sha256").update(sourceString, "utf8").digest();
}
