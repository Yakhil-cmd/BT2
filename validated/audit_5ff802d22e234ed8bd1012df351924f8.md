### Title
Webhook signature verification authenticates the payload's `repository.owner.login`, but all event handlers resolve state by the unverified `repository.full_name` — allowing cross-repository/cross-tenant writes - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`Shipit::WebhooksController#verify_signature` selects the HMAC secret used to validate an inbound webhook based on `repository.owner.login` (or `organization.login`) taken from the JSON body, then verifies the *entire* raw body against that org's `webhook_secret`. Once verification succeeds, `create` dispatches the same raw body to event handlers, but every handler (`PushHandler`, `CheckSuiteHandler`, pull-request handlers, etc.) resolves the target `Repository`/`Stack` from a *different* field in the same body — `repository.full_name` — via `Shipit::Webhooks::Handlers::Handler#repository_name`. Nothing ties the verified `repository.owner.login` to the `full_name` actually acted upon.

### Finding Description
Signature verification: [1](#0-0) [2](#0-1) 

`verify_signature` calls `Shipit.github(organization: repository_owner)` to look up the org-specific `GitHubApp` instance and validate `X-Hub-Signature` against *that org's* `webhook_secret`: [3](#0-2) [4](#0-3) 

Shipit explicitly supports one `webhook_secret` per organization for multi-tenant setups (`config/secrets.yml`'s `github:` section keyed by organization). Any organization owner who installs their own GitHub App on Shipit chooses (and therefore knows) their own org's `webhook_secret`.

Once the signature is accepted, the raw body is handed unmodified to every registered handler: [5](#0-4) 

All handlers extend the base `Handler` class, which resolves the acted-upon repository/stacks from `repository.full_name`, not `repository.owner.login`: [6](#0-5) 

`PushHandler` uses this to look up and synchronize an arbitrary `Stack`: [7](#0-6) 

`CheckSuiteHandler` similarly schedules check-run refreshes for commits on any matched stack: [8](#0-7) 

`Repository.from_github_repo_name` performs a plain DB lookup on the `owner/name` parsed out of the (unverified-against-signature-selection) `full_name` field, with no cross-check against the org whose secret validated the request: [9](#0-8) 

**Binding broken:** the request is trusted under the equality `verified_org (repository.owner.login) == acted_upon_owner (owner segment of repository.full_name)`. This equality is never checked anywhere in `WebhooksController` or `Handler`. The two fields are read independently from the same untrusted JSON body.

### Impact Explanation
An attacker who controls (and legitimately owns the webhook secret for) any single GitHub organization configured on a multi-tenant Shipit instance can forge a webhook body where `repository.owner.login` names their own org (so `verify_signature` selects and validates against a secret they know) while `repository.full_name` names a completely unrelated victim organization's repository. The forged, "verified" request then drives `PushHandler` to call `stack.sync_github(expected_head_sha:)` on the victim's `Stack`, and similarly lets `CheckSuiteHandler`/pull-request handlers mutate commit/check-run/pull-request state, review-stack provisioning, and archival state belonging to a repository the attacker has no access to. This is a cross-repository/cross-tenant write achieved purely by possessing a webhook secret scoped to an unrelated, attacker-owned organization — matching the High-impact criterion of unauthorized writes into another repository's stack state, and can cascade into an unauthorized sync/deploy trigger if the victim stack has continuous deployment configured.

### Likelihood Explanation
Requires only that the target Shipit instance is configured for multiple GitHub organizations (a documented, supported configuration) and that the attacker is a legitimate owner/administrator of one of those unrelated organizations — i.e., the attacker needs no privileged access to Shipit itself, no `ApiClient` token, and no access to the victim's repository or GitHub App. They only need to know a webhook secret they themselves provisioned for their own org's GitHub App, then craft an arbitrary JSON body and POST it to the shared `/webhooks` endpoint.

### Recommendation
After `verify_signature` succeeds, bind the verified organization identity to the event processing: require that the owner segment parsed from `repository.full_name` (and/or `organization.login`) matches `repository_owner` (the identity whose secret validated the signature) before dispatching to handlers, rejecting the request otherwise. Alternatively, have `Handler#repository_name`/`stacks` be constructed with the already-verified organization rather than re-reading an independent, unchecked field from the payload.

### Proof of Concept
1. Deploy Shipit configured with two organizations in `github:` (e.g. `attacker-org` and `victim-org`), each with its own `webhook_secret` (a supported, documented configuration).
2. As the legitimate owner of `attacker-org`'s GitHub App, know `attacker-org`'s `webhook_secret`.
3. Craft a JSON body imitating a `push` event:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
4. Compute `X-Hub-Signature: sha1=<hmac-sha1(attacker-org secret, body)>`.
5. POST to `/webhooks` with `X-Github-Event: push` and the header from step 4.
6. `WebhooksController#verify_signature` resolves `repository_owner == "attacker-org"`, fetches `attacker-org`'s `GitHubApp`, and the signature validates successfully (`app/controllers/shipit/webhooks_controller.rb:24-30`, `lib/shipit/github_app.rb:76-83`).
7. `create` dispatches to `PushHandler`, which resolves stacks via `repository.full_name = "victim-org/victim-repo"` (`app/models/shipit/webhooks/handlers/handler.rb:32-38`, `app/models/shipit/repository.rb:53-56`) and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` on the victim's stack (`app/models/shipit/webhooks/handlers/push_handler.rb:12-17`) — a write the attacker has no authorization to trigger.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
