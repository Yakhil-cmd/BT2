### Title
Attacker-controlled submodule growth causes unbounded, single-context git operations that permanently exceed `--sync-timeout`, resulting in persistent sync denial - (File: main.go)

### Summary
The original finding (H-08) describes an unbounded, attacker-fed loop (`vest()` calls anyone can trigger, growing `timelocks[beneficiary]`) that eventually makes a fixed-gas operation (`claim()`) always revert, permanently locking legitimate funds. The closest reachable analog in `git-sync` is the submodule/recursive-checkout path in `configureWorktree()`, where the number and depth of git submodules is entirely dictated by the content of the upstream repository (i.e., by whoever can push a commit/ref there), and the entire fetch+checkout+submodule-init sequence for a sync attempt is bounded by a single `context.WithTimeout(..., *flSyncTimeout)` that is never adjusted for content size.

### Finding Description
Each sync iteration creates one `ctx` with a fixed deadline (`*flSyncTimeout`) and passes that same `ctx` through the entire `SyncRepo` call chain — fetch, `rev-parse`, `reset --soft`, `createWorktree`, and `configureWorktree` (which runs `reset --hard` and, if submodules aren't disabled, `git submodule update --init [--recursive]`): [1](#0-0) [2](#0-1) 

The submodule step iterates over whatever `.gitmodules` entries exist in the fetched commit, with no cap on submodule count or recursion depth, and issues a single blocking `git.Run` call for the whole operation: [3](#0-2) 

Because `.gitmodules` content is fully attacker-controlled (anyone who can push a commit to the tracked ref, exactly analogous to "anyone can call `vest()`"), an attacker can commit a large number of submodule entries or a deep chain of nested submodules. On the next sync attempt, `configureWorktree`'s `git submodule update --init --recursive` will take an amount of time proportional to that attacker-chosen size, with no partial-progress checkpointing across sync attempts — each retry re-runs the same operation from scratch inside a fresh `flSyncTimeout`-bounded context. If the submodule tree is large enough to always exceed `--sync-timeout`, `SyncRepo` will always return a context-deadline error, exactly mirroring the H-08 pattern where an ever-growing unbounded structure guarantees a fixed-resource operation can never complete.

### Impact Explanation
If `--max-failures` is left at its default/unlimited-tolerant setting, this manifests as **persistent sync denial**: the current published symlink is never advanced to the malicious/new commit, and legitimate downstream content updates are permanently blocked (the underlying worktree creation happens before publish, so `publishSymlink` is never reached, per `SyncRepo`'s ordering — this avoids partial-content publication, but it also means the pipeline is stuck). If `--max-failures` is bounded, the process instead calls `os.Exit(1)` repeatedly: [4](#0-3) 
causing a persistent crash-loop in the sidecar container, which in a Kubernetes deployment denies the intended "keep files up to date" contract indefinitely for any consumer depending on that `git-sync` sidecar.

### Likelihood Explanation
Reachability requires only push/commit access to the tracked repository/ref — no special git-sync flags, credentials, or privileged configuration are needed beyond the default `--submodules=recursive` behavior (submodules are on by default per the CLI help: `submodules` defaults to `"recursive"`). This is a low-effort, unprivileged action for anyone who can influence the content of the synced ref (e.g., an open-source repo, a shared branch, or any actor who can land a commit), which matches the "no special flags" spirit of the original bug (no special privilege needed to call `vest()`).

### Recommendation
- Bound the size/duration of submodule initialization independent of the outer `--sync-timeout`, or make the timeout scale with the amount of work (or fail fast with a clear "submodule set too large" diagnostic rather than silently reusing the same fixed timeout each retry).
- Add a configurable cap on submodule count/recursion depth (e.g., `--max-submodules`) and refuse/alert on refs whose `.gitmodules` exceeds it, similar to the H-08 recommendation to "create a minimum/maximum bound" to prevent unbounded growth from making a downstream operation permanently unable to complete.
- Consider decoupling worktree creation/checkout from submodule initialization so that a failure in the (attacker-influenced) submodule stage doesn't force a full redo of the (already-completed) checkout on every retry.

### Proof of Concept
1. Configure `git-sync` against a repository the attacker can push to (default flags, i.e., `--submodules=recursive`, default `--sync-timeout`).
2. Attacker pushes a commit adding a very large number of `.gitmodules` entries or a deeply nested submodule chain (all pointing to trivial/empty repos to keep clone cost low but count high).
3. On the next scheduled sync, `SyncRepo` reaches `configureWorktree`, which invokes `git submodule update --init --recursive` under the shared `ctx`: [3](#0-2) 
4. Because the number of submodule init subprocesses scales with attacker-chosen input, the call exceeds `*flSyncTimeout` and `ctx` is cancelled, causing `SyncRepo` to return an error.
5. This repeats on every subsequent sync attempt (no cached progress), so the sync either denies forever (unbounded `--max-failures`) or crash-loops the process (bounded `--max-failures`), matching the "persistent sync denial" acceptance criterion.

Note: I was not able to inspect the exact default value of `--sync-timeout`/`--max-failures` or the `pkg/cmd` runner's per-command timeout behavior in this pass (index coverage was limited to the snippets retrieved); a Devin session with full repository access would be needed to confirm the exact default constants and whether any additional internal timeout exists specifically for the `submodule update` subcommand.
