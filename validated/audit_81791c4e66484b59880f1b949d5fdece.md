### Title
CCMenu API endpoint lets a stack-scoped ApiClient token read build status of any stack - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::ApiClient` tokens can be scoped to a single stack via `stack_id`, and `Api::BaseController` is designed to enforce that scope by resolving the current stack through the `stacks` helper, which restricts the visible `Stack` relation to `current_api_client.stack_id` when one is set. [1](#0-0) 
`Api::CCMenuController`, however, overrides `stack` to resolve directly against `Stack.from_param!(params[:stack_id])`, completely bypassing the `stacks` scoping helper, while still only checking the client's global `read:stack` permission bit. [2](#0-1) 

### Finding Description
The binding this breaks is: *the stack a token authorizes* (`ApiClient#stack_id`, enforced through `BaseController#stacks`/`#stack`) *versus the stack the request actually touches* (`params[:stack_id]` resolved unscoped in `CCMenuController#stack`).

`ApiClient` supports being scoped to a single `Stack` (`belongs_to :stack, optional: true`), and permission checks are only a global list of operation:scope pairs (`read:stack`, `write:stack`, etc.) with no stack-id binding at the permission-check level. [3](#0-2) 
The actual per-token stack restriction lives entirely in `Api::BaseController#stacks`/`#stack`:
```ruby
def stacks
  @stacks ||= current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all
end

def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
``` [1](#0-0) 
Every other API controller (e.g. `Api::MergeRequestsController`, `Api::StacksController`) relies on this inherited `stack`/`stacks` method, so a scoped token is confined to its stack. [4](#0-3) 

`Api::CCMenuController` redefines `stack` to look the record up unscoped:
```ruby
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end
``` [5](#0-4) 
It only enforces `require_permission :read, :stack`, which merely checks that the client's `permissions` array contains `"read:stack"` — a check that is completely independent of which stack is requested. [6](#0-5) [7](#0-6) 

Consequently, a token issued and scoped to Stack A (e.g. `here_come_the_walrus` fixture, which has `stack: shipit` and only `read:stack` permission) can call `GET /api/:other_stack_id/cc.xml` with any other stack's `stack_id` param and receive that stack's build data, even though `BaseController#stacks` was specifically designed to prevent this by returning `Stack.where(id: current_api_client.stack_id)` for scoped clients. [8](#0-7) 

### Impact Explanation
The `show` action renders `app/views/shipit/ccmenu/project.xml.builder`, exposing the stack's name, activity, `lastBuildStatus`, `lastBuildLabel`, `lastBuildTime` and `webUrl` for the latest deploy/rollback. [9](#0-8) 
This is an unauthorized read of stack state/deploy status for stacks the token was never granted access to, using only a token that was deliberately scoped to a different stack — matching the "a stack a token authorizes versus a stack it touches" trust boundary and the "unauthenticated [i.e. out-of-scope] read of stack state ... or deploy output" High-impact category, since the attacker only needs any single valid, narrowly-scoped `ApiClient` token (e.g. one created for a low-trust integration) to enumerate build status across every stack hosted by the Shipit instance.

### Likelihood Explanation
Likelihood is high for anyone already holding a legitimately-scoped `ApiClient` token (e.g. a third-party CI badge integration granted only `read:stack` on one repository's stack): the CCMenu endpoint takes the target stack purely from the URL/`stack_id` param, requires no additional per-stack authorization, and the `token` param based `authenticate_api_client` override makes the endpoint trivially reachable (`GET /api/<any-other-stack>/cc.xml?token=<my-scoped-token>`). [10](#0-9) 

### Recommendation
Change `Api::CCMenuController#stack` to resolve through the inherited, scope-aware `stacks` helper (i.e. `stacks.from_param!(params[:stack_id])`) instead of calling `Stack.from_param!` directly, so stack-scoped tokens cannot view other stacks' build status.

### Proof of Concept
1. Create an `ApiClient` scoped to Stack A with only `read:stack` permission (as in the `here_come_the_walrus` fixture).
2. As an attacker in possession of that token, issue: `GET /api/<stack-B-owner>/<stack-B-name>/<stack-B-env>/cc.xml?token=<stack-A-scoped-token>`.
3. `authenticate_api_client` succeeds via `ApiClient.authenticate(params[:token])`. [10](#0-9) 
4. `require_permission :read, :stack` passes because the client's permission list includes `read:stack` (no stack binding checked). [7](#0-6) 
5. `stack` resolves `Stack B` unscoped via `Stack.from_param!(params[:stack_id])`, and `show` renders Stack B's `lastBuildStatus`/`webUrl`/deploy info to the caller — data the token was never authorized to see. [11](#0-10)

module Shipit
  module Api
    class CCMenuController < BaseController
      require_permission :read, :stack

      class NoDeploy
        def id
          0
        end

        def ended_at
          Time.now.utc
        end

        def running?
          false
        end
      end

# frozen_string_literal: true

module Shipit
  class ApiClient < Record
    InsufficientPermission = Class.new(StandardError)

    belongs_to :creator, class_name: 'User'
    belongs_to :stack, optional: true

    validates :creator, :name, presence: true

    serialize :permissions, coder: Shipit.serialized_column(:permissions, type: Array)
    PERMISSIONS = %w[
      read:stack
      write:stack
      deploy:stack
      lock:stack
      read:hook
      write:hook
    ].freeze
    validates :permissions, subset: { of: PERMISSIONS }

    class << self
      def authenticate(token)
        find_by(id: message_verifier.verify(token).to_i)
      rescue Shipit::SimpleMessageVerifier::InvalidSignature
      end

      def message_verifier
        @message_verifier ||= Shipit::SimpleMessageVerifier.new(Shipit.api_clients_secret)
      end
    end

    def authentication_token
      self.class.message_verifier.generate(id)
    end

    def check_permissions!(operation, scope)
      required_permission = "#{operation}:#{scope}"
      unless permissions.include?(required_permission)
        raise InsufficientPermission, "This operation requires the `#{required_permission}` permission"
      end

      true
    end
  end
