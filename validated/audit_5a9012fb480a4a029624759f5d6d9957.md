### Title
Webhook signature verification is keyed to an attacker-controlled `repository.owner.login` field that is decoupled from the repository the event actually mutates, allowing forged commit statuses / push events to bypass CI gating and trigger unauthorized continuous deployment - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App / webhook secret to use for HMAC verification based on `params.dig('repository', 'owner', 'login')` — a field taken directly from the *unauthenticated* request body — while the handlers that actually mutate application state (`StatusHandler`, `PushHandler`, and the `PullRequest` handlers) resolve the target `Stack`/`Commit` using a *different* field from the same untrusted body (`repository.full_name`, or in `StatusHandler`'s case, a global `Commit.where(sha:)` lookup with no repository scoping at all). Because the "organization that authenticated" and "the repository that is written" are two independently attacker-supplied values from the same payload, an attacker can pick an organization for which signature verification is weak or absent (webhook secret is documented as optional and can be `nil`) while forging events that affect a completely different, protected stack/repository.

### Finding Description
`verify_signature` is:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) 

`GitHubApp#verify_webhook_signature` explicitly no-ops when no secret is configured for that organization:
```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
``` [2](#0-1) 

The multi-org configuration schema in the setup docs explicitly allows `webhook_secret` to be left blank per-organization:
```
github:
  somegithuborg:
    ...
    webhook_secret: # nil
someothergithuborg:
    ...
    webhook_secret: # nil
``` [3](#0-2) 

Meanwhile, the actual data mutated by an event handler is picked from an *entirely different, unauthenticated* field of the same JSON body. The base `Handler` resolves the affected repository via `repository.full_name`:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [4](#0-3) 

`StatusHandler`, used to record CI status against commits, doesn't even scope by repository — it matches purely by commit SHA across the entire installation:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [5](#0-4) 

Because `repository.owner.login` (used only for picking the HMAC secret) and `repository.full_name`/`sha` (used to decide what gets written) come from the same forgeable request body, an attacker can set `repository.owner.login` to any organization configured in `Shipit.github` whose `webhook_secret` is unset (or otherwise known/weak), causing `verify_signature` to pass unconditionally, while setting the payload's actual mutation target (`repository.full_name` for push/pull_request events, or simply `sha` for status events) to point at a stack belonging to a *different*, properly-secured organization.

This breaks the binding: `organization that authenticated == repository that is written`. The engine authenticates the request against org A's (weak/absent) secret but the handler applies the event to org B's stack.

### Impact Explanation
A forged `status` event let through this way lets an unauthenticated attacker create a fabricated "success" `Status` on an arbitrary target commit (identified only by SHA, which is routinely public — e.g. visible in the app UI/GitHub). `Commit#deployable?` treats a commit as deployable once `success?` is true and the commit isn't blocked:
```ruby
def deployable?
  !locked? && (stack.ignore_ci? || (success? && !blocked?))
end
``` [6](#0-5) 

And every newly created commit schedules continuous delivery automatically once it is deployable and the stack has `continuous_deployment` enabled:
```ruby
def schedule_continuous_delivery
  return unless deployable? && stack.continuous_deployment? && stack.deployable?
  ContinuousDeliveryJob.set(wait: RECENT_COMMIT_THRESHOLD).perform_later(stack)
end
``` [7](#0-6) 

A forged success status can therefore satisfy the CI requirement and trigger an unauthorized automatic deploy on a stack the attacker has no legitimate access to — meeting the "unauthorized deploy" Critical-impact criterion. The same mechanism can also unblock merge-queue gating (`stack.schedule_merges` is invoked on status transitions in `Commit#add_status`), potentially enabling an unauthorized merge.

### Likelihood Explanation
Exploitability depends on the deployment having more than one GitHub organization configured under `Shipit.github`, with at least one of them lacking a `webhook_secret` (explicitly documented as optional/nil) or having a weaker/known secret. In that (documented-as-supported) configuration, the attack requires no credentials, no session, and no GitHub App access — only knowledge of a target commit SHA, which the application itself exposes in its UI. This is a realistic, low-effort path once the multi-org feature (added to support several GitHub Apps) is in use, and the engine provides no mechanism to bind the authenticating organization to the repository actually being mutated.

### Recommendation
- Do not select the verification secret using an unauthenticated payload field. Verify the signature first using the app-level default secret (or all configured secrets) and only after successful verification trust any payload-derived field to select the affected stack.
- Cross-check that `repository.owner.login`/`organization.login` used for the signature lookup matches the organization implied by `repository.full_name` before processing the event.
- Scope `StatusHandler` (and any other handler) lookups by repository, not just by commit SHA, to avoid one repository's forged status affecting a commit belonging to an unrelated stack.
- Make `webhook_secret` mandatory for every configured organization, or reject events entirely (rather than accepting unsigned events) when no secret is configured.

### Proof of Concept
1. Shipit is configured with two GitHub orgs: `secure-org` (has `webhook_secret` set) and `weak-org` (has `webhook_secret` left blank), per the documented multi-org schema.
2. Attacker finds a target commit SHA belonging to a stack under `secure-org` (visible via the Shipit UI).
3. Attacker POSTs to `/webhooks` with header `X-Github-Event: status` and no valid `X-Hub-Signature`, and body:
```json
{
  "sha": "<target-commit-sha-in-secure-org-stack>",
  "state": "success",
  "context": "<required-ci-context>",
  "repository": { "owner": { "login": "weak-org" }, "full_name": "weak-org/some-repo" }
}
```
4. `verify_signature` calls `Shipit.github(organization: "weak-org")`, whose `webhook_secret` is nil, so `verify_webhook_signature` returns `true` regardless of signature.
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)`, finds the target commit that actually belongs to `secure-org`'s stack (no repository scoping is applied), and creates a "success" status on it.
6. If that stack requires only this CI context and has `continuous_deployment` enabled, `Commit#schedule_continuous_delivery` fires, deploying `secure-org`'s stack without any legitimate CI signal or valid webhook credentials.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
