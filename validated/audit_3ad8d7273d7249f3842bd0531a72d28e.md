The Polkadot SDK's `pallet-asset-conversion` already implements exactly the slippage protection that the Unitas report says is missing. Both `swap_exact_tokens_for_tokens` and `swap_tokens_for_exact_tokens` extrinsics require explicit `amount_out_min` / `amount_in_max` parameters supplied by the caller, and `do_swap_exact_tokens_for_tokens` enforces `amount_out >= amount_out_min` (erroring with `ProvidedMinimumNotSufficientForSwap`) before any transfer executes [1](#0-0) [2](#0-1) . The symmetric check exists for `swap_tokens_for_exact_tokens` (`ProvidedMaximumNotSufficientForSwap`) as confirmed by tests [3](#0-2) , and the "insufficient slippage" scenario itself is covered by a dedicated regression test `swap_should_not_work_if_too_much_slippage` [4](#0-3) .

This is precisely the recommendation from the Unitas report ("Provide the necessary `amountInMaximum` and for `amountOutMinimum` for swaps") — already baked into the `Swap`/`SwapCredit` trait interfaces (`amount_out_min: Option<Self::Balance>`, `amount_in_max: Option<Self::Balance>`) [5](#0-4) , the credit-based swap path [6](#0-5) , and the newer EVM-facing precompile which also forwards `amountOutMin`/`amountInMax` and is exercised by a matching `swap_fails_with_insufficient_output` test [7](#0-6) [8](#0-7) .

The runtime API docs even explicitly warn callers to use these bounds because "the price may have changed by the time the transaction is executed" [9](#0-8) . There is no code path where the swap extrinsics execute without the caller-supplied bound being checked against the actual pool-computed output/input, so the pending-transaction/price-drift scenario described in the Unitas report does not reproduce here — the analog is not a vulnerability but the fixed pattern.
