### Title
Cross-organization commit status forgery via unscoped SHA lookup in `StatusHandler` - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
The `WebhooksController` authenticates a webhook by resolving the organization from the payload's `repository.owner.login` (or `organization.login`) and verifying the request signature against **that organization's** `webhook_secret`. This proves only that the sender legitimately controls webhooks for the named organization — it says nothing about any other organization's repositories. `StatusHandler`, however, applies the payload to any `Commit` row that matches the SHA, without ever checking that the commit belongs to a stack/repository owned by the organization that was actually authenticated. This breaks the binding "organization authenticated == repository written."

### Finding Description
`WebhooksController#verify_signature` picks the GitHub App/organization to validate against from the payload itself: [1](#0-0) [2](#0-1) 

Every other built-in handler that mutates state scopes its effect through `Handler#stacks`, which resolves `Repository.from_github_repo_name(repository_name)` where `repository_name` is `payload.dig('repository', 'full_name')` — i.e., the same repository whose owner was used for signature verification: [3](#0-2) [4](#0-3) [5](#0-4) 

`StatusHandler` is the exception — it never calls `stacks`/`repository_name`. It looks up commits by SHA alone, across the entire `Commit` table, regardless of which repository/organization actually owns them: [6](#0-5) 

Because Shipit explicitly supports installing multiple independent GitHub Apps/organizations against the same instance (each with its own `webhook_secret`, as documented and exercised in the test fixtures for a "double github app" setup): [7](#0-6) [8](#0-7) 

an attacker who only controls a repository/webhooks in one configured organization (OrgB) can send a validly-signed `status` event whose `sha` collides with a commit SHA that Shipit is tracking under a *different* configured organization (OrgA). Git SHAs are content-addressed, not repository-bound, so an attacker can trivially obtain a matching SHA by forking/importing a public commit from OrgA's repo into a repo they control in OrgB, then firing a status webhook from OrgB for that identical SHA. `verify_signature` succeeds (it is genuinely signed by OrgB), yet `Commit.where(sha: params.sha)` will match and update the `Commit` row belonging to OrgA's stack.

### Impact Explanation
CI status on a `Commit` gates whether it is considered `deployable?` (used by `ci.require`/status checks that `Stack#build_deploy` and `Commit` deployability logic rely on). By forging a passing status on a commit the attacker does not own, in an organization the attacker has no access to, the attacker can flip that commit's tracked status to `success`, satisfying CI gating and enabling an **unauthorized deploy** of that revision in the victim organization's stack — without ever holding a Shipit session, `ApiClient` token, or credentials for the victim organization. This crosses the authorization boundary the webhook signature is supposed to enforce (organization authenticated ≠ repository/commit written), qualifying as an unauthorized deploy under the stated Critical impact criteria.

### Likelihood Explanation
Requires: (1) the Shipit deployment to have more than one GitHub App/organization configured (a documented, supported configuration), and (2) the attacker to control at least one repository/webhook delivery in one of those organizations while targeting a commit tracked under another. Obtaining a matching SHA is straightforward for any public commit (fork/import). This is a realistic scenario for any Shipit instance servicing multiple organizations, which the engine explicitly supports and documents.

### Recommendation
Scope `StatusHandler#process` (and any other handler processing arbitrary payload fields) to commits/stacks belonging to the repository named in the webhook payload, mirroring `Handler#stacks`/`repository_name`, e.g.:
```ruby
def process
  stacks.flat_map(&:commits).select { |c| c.sha == params.sha }.each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
or otherwise join through `Repository`/`Stack` so that the authenticated organization's repository is the same one whose `Commit` rows are mutated.

### Proof of Concept
1. Configure Shipit with two organizations, `OrgA` and `OrgB`, each with a distinct `webhook_secret` (supported per `docs/setup.md` multi-org config).
2. Shipit tracks a stack for `OrgA/target-repo`, with a known deployed/tracked commit `SHA_X` (obtainable via the public GitHub API/commit history).
3. Attacker, who only controls a repo in `OrgB` (e.g., `OrgB/attacker-repo`), imports/forks the exact git commit object for `SHA_X` into their own repo (git objects are content-addressed, so pushing/fetching the identical commit reproduces the identical SHA in a different repository).
4. Attacker triggers (or crafts, since they control delivery of their own org's webhooks) a `status` event for `OrgB/attacker-repo` with `sha: SHA_X`, `state: success`.
5. `WebhooksController#verify_signature` validates the signature against `OrgB`'s `webhook_secret` — succeeds, because it is a legitimately-signed OrgB webhook.
6. `StatusHandler#process` executes `Commit.where(sha: 'SHA_X')`, which matches the `Commit` row under `OrgA`'s stack, and calls `commit.create_status_from_github!(params)` — writing a forged `success` status onto a commit the attacker never had access to, potentially unlocking a deploy for `OrgA/target-repo`.
