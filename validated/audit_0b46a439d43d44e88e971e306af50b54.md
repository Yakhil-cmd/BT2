### Title
Webhook signature is validated against `repository.owner.login`, but the target stack is resolved from the independent `repository.full_name` field — allowing cross-organization forgery of GitHub events - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App secret to verify the HMAC signature against using `repository.owner.login` (or `organization.login`) from the JSON body, but the handlers that actually act on the payload (`Shipit::Webhooks::Handlers::Handler#stacks`) resolve the target `Repository`/`Stack` using the unrelated `repository.full_name` field from the same attacker-controlled body. Because these two fields are never cross-checked, a signature that is valid for one configured GitHub organization can be replayed with a `repository.full_name` pointing at a repository belonging to a *different* organization hosted on the same shared Shipit instance.

### Finding Description
In a multi-org Shipit deployment (explicitly supported, see `config/secrets.development.shopify.yml` and `test/dummy/config/secrets_double_github_app.yml`, each org has its own `webhook_secret`), the webhook signature check is: [1](#0-0) 

`repository_owner` is derived purely from the JSON body: [2](#0-1) 

`Shipit.github(organization: repository_owner)` looks up the `GitHubApp`/secret keyed by that owner login, and the HMAC is verified against **that** app's `webhook_secret` only: [3](#0-2) 

Once the signature check passes, the event handlers never re-check `repository.owner.login`. Instead they resolve the affected `Repository`/`Stack` using `repository.full_name`, an entirely separate field from the same JSON body: [4](#0-3) [5](#0-4) 

So the equality the app implicitly relies on is:
`organization whose secret authenticated the request == organization that owns the repository being acted upon`

This equality is never enforced. An attacker who legitimately controls a GitHub App/organization "OrgA" configured on the shared Shipit instance (and therefore knows OrgA's `webhook_secret`, which they can freely obtain by installing/inspecting their own app settings) can sign an arbitrary payload with OrgA's secret while setting `repository.owner.login`/`organization.login` = `"OrgA"` (to pass `verify_signature`) and `repository.full_name` = `"OrgB/some-repo"` (a repository/stack belonging to a completely unrelated tenant "OrgB"). The request passes signature verification (correct secret for the claimed owner) yet is processed against OrgB's stacks.

Concrete abuse via existing handlers:
- `PushHandler#process` finds `stacks.not_archived.where(branch:)` for `Repository.from_github_repo_name(repository_name)` and calls `stack.sync_github(expected_head_sha: params.after)` — forcing a GitHub sync job against OrgB's stack: [6](#0-5) 
- `StatusHandler#process` creates a `Status` (build/CI state) on any commit matching `sha` regardless of which repo/org it belongs to, since `Commit.where(sha:)` is not scoped by the verified organization: [7](#0-6) . Commit statuses feed into `deployable?` checks that gate whether a deploy can be triggered, so forging a passing status for OrgB's commit can help unlock an otherwise-blocked deploy.

### Impact Explanation
This breaks the "organization authenticated vs. repository written" binding called out as in-scope. It allows an attacker who controls one tenant's GitHub App configuration in a shared, multi-org Shipit deployment to inject validly-signed-looking events (push syncs, forged commit statuses) against a completely different tenant's repositories/stacks — a cross-repository/cross-tenant write with no legitimate authorization over the target repository. Forged commit statuses can also manipulate deployability gates, contributing to an unauthorized deploy path. This matches the Critical/High impact categories (cross-repository writes / contributing to unauthorized deploy).

### Likelihood Explanation
Requires only that the target instance be configured for multiple GitHub organizations (an explicitly documented and supported configuration — see `docs/setup.md` and `test/dummy/config/secrets_double_github_app.yml`) and that the attacker administers one of those orgs' GitHub Apps (giving them their own `webhook_secret`, not the victim's). No Shipit session, `ApiClient` token, or `api_clients_secret` is needed — only knowledge of their own org's webhook secret and the ability to POST to the public `/webhooks` endpoint, which is unauthenticated at the routing layer by design (it's meant to be called by GitHub).

### Recommendation
After signature verification, the handler layer must cross-validate that the resolved `Repository` (via `full_name`) actually belongs to the same organization (`owner`) whose secret was used to authenticate the request (`repository_owner`), rejecting the event if they diverge. Equivalently, resolve the target repository/organization once, verify the signature using that repository's owning organization's secret, and use that same resolved value for all subsequent lookups, rather than trusting two independent, unvalidated fields from the same untrusted payload.

### Proof of Concept
1. Shipit is configured for two orgs, `OrgA` and `OrgB`, each with distinct `webhook_secret`s (as in `test/dummy/config/secrets_double_github_app.yml`).
2. Attacker administers `OrgA`'s GitHub App and thus knows `OrgA`'s `webhook_secret`; they have no access to `OrgB`.
3. Attacker crafts a `push` event JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "OrgA" },
    "full_name": "OrgB/victim-repo"
  }
}
```
4. Attacker computes `X-Hub-Signature: sha1=<hmac-sha1(OrgA_webhook_secret, body)>` and POSTs to `/webhooks` with `X-Github-Event: push`.
5. `WebhooksController#verify_signature` resolves `repository_owner` = `"OrgA"`, fetches `Shipit.github(organization: "OrgA")`, and the HMAC verifies successfully.
6. `PushHandler#process` resolves the target repository via `repository.full_name` = `"OrgB/victim-repo"`, finds OrgB's `Stack`, and triggers `stack.sync_github(expected_head_sha: ...)` — a write action against a repository/organization the attacker has no authorization over, entirely bypassing OrgB's own webhook secret.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
