## Reentrancy Guard in `pox-5.clar` Is Never Cleared on a Failed `validate-stake!` Call, Permanently Freezing Reward Claims

### Summary
`pox-5.clar` implements a global reentrancy guard, `signer-manager-call-active`, meant to stop a malicious `signer-manager-trait` implementation from re-entering the contract during `validate-stake!` callbacks [1](#0-0) . The guard is set in `signer-manager-validate-stake`, but it is only cleared *after* the external `contract-call?` to the signer manager succeeds:

```
(begin
    (asserts! (not (var-get signer-manager-call-active)) ERR_REENTRANT_CALL)
    (var-set signer-manager-call-active true)
    (try! (contract-call? signer-manager validate-stake! staker first-index
        num-indexes amount-ustx amount-sats is-bond signer-calldata
    ))
    (var-set signer-manager-call-active false)
    (ok true)
)
``` [2](#0-1) 

### Finding Description
`try!` short-circuits on any `(err ...)` from the `contract-call?` to `validate-stake!` and returns immediately from `signer-manager-validate-stake`, so the `(var-set signer-manager-call-active false)` line is never reached whenever the signer-manager rejects the stake. This is a normal, expected outcome — any signer-manager implementation that validates business logic (insufficient allowlist amount, wrong caller, expired bond, etc.) will legitimately return an error from time to time — not just a malicious re-entrant one.

Once `signer-manager-call-active` is stuck at `true`, every other function in the contract gated by `validate-no-reentrancy` becomes permanently unusable, because that check only tests whether the flag is set, with no way to reset it:
```
(define-private (validate-no-reentrancy)
    (ok (asserts! (not (var-get signer-manager-call-active)) ERR_REENTRANT_CALL))
)
``` [3](#0-2) 

This guard is checked in `claim-rewards` (sBTC reward payout to signers) [4](#0-3) , `claim-staker-rewards-for-signer` (per-staker reward settlement) [5](#0-4) , `set-bond-admin`, `set-pause-admin`, and `pause-rewards` [6](#0-5) . There is no admin or automated path anywhere in the contract that resets `signer-manager-call-active` back to `false` once it is stuck — it is a `define-data-var` with no setter other than the guarded call itself.

### Impact Explanation
Any unprivileged staker can trigger this: calling `stake`/`register-for-bond` (which invokes `signer-manager-validate-stake` under the hood) with any signer-manager whose `validate-stake!` legitimately returns an error (e.g., because of an out-of-range amount, an unregistered staker, or any ordinary validation failure) leaves `signer-manager-call-active` permanently `true`. From that point on, `claim-rewards` and `claim-staker-rewards-for-signer` unconditionally fail with `ERR_REENTRANT_CALL` for every signer and every staker, contract-wide, forever (there is no un-pause/reset path). This is a permanent freeze of all sBTC staking rewards for every participant in the contract — this matches the "permanent freezing of staked STX or sBTC" / reward class of impact.

### Likelihood Explanation
High: this does not require a malicious re-entrant contract at all — an ordinary, honest signer-manager rejecting a single stake attempt (which is an expected, common code path) is sufficient to brick the flag permanently. No privileged role or race condition is needed.

### Recommendation
Reset `signer-manager-call-active` unconditionally regardless of the `contract-call?` outcome, e.g. by wrapping the external call so cleanup happens even on error (using a `let`/`match` on the response and explicitly `var-set`-ing `false` in both branches before propagating the error), rather than relying on `try!`'s early return.

### Proof of Concept
1. Deploy a compliant `signer-manager-trait` implementation whose `validate-stake!` returns `(err u1)` for some address/amount combination that legitimately fails validation (e.g., attacker over the allowlisted max).
2. Have the attacker call `register-for-bond` (or `stake`) with that combination; `signer-manager-validate-stake` sets `signer-manager-call-active` to `true`, the trait call returns `err`, and `try!` returns before the flag is reset.
3. Any subsequent call, by any user, to `claim-rewards` or `claim-staker-rewards-for-signer` now fails with `ERR_REENTRANT_CALL` indefinitely, freezing all sBTC rewards contract-wide (as shown in the existing reentrancy test file [7](#0-6) , which exercises the guard but does not cover the failure-to-reset path on a non-reentrant error).

Note: I was not able to fully inspect the bodies of `register-for-bond`/`stake` in this pass to confirm they are the sole callers of `signer-manager-validate-stake` with no additional cleanup wrapper elsewhere in the ~2500-line `pox-5.clar` file; a Devin session with full file access would be needed to rule out an unseen reset path before treating this as fully confirmed.
