### Title
Webhook Signature Verification Selects the HMAC Key From an Unauthenticated Payload Field, Allowing Cross-Organization Forgery - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` picks which GitHub App/organization's `webhook_secret` to validate a delivery against using a field taken straight out of the *unverified* JSON body, before the HMAC has been checked. In a multi-tenant Shipit deployment (multiple GitHub organizations configured under one instance), this lets an attacker who legitimately controls one onboarded organization forge webhook deliveries that are cryptographically "valid" for their own org but whose payload content (the actual `repository` acted upon by handlers) targets a different tenant's repository/stack.

### Finding Description
`verify_signature` derives the signing key from the payload itself: [1](#0-0) 

and [2](#0-1) 

`repository_owner` reads `params.dig('repository', 'owner', 'login')`, falling back to `params.dig('organization', 'login')` when the `repository.owner.login` sub-path is absent. `Shipit.github(organization:)` looks up a distinct `GitHubApp`/`webhook_secret` per organization key, exactly as documented for multi-org installs: [3](#0-2) [4](#0-3) 

Because the field used to *select the verification key* is read out of the same untrusted JSON body whose *content* (e.g. `repository.full_name`, used downstream by handlers such as `PushHandler` to resolve the target `Stack`) drives what gets written, an attacker who is a legitimate tenant of the Shipit instance (i.e., knows their own org's `webhook_secret` because they configured the GitHub App for their own org) can build a payload where:
- the `organization.login` (or `repository.owner.login`) fallback path used by `verify_signature` resolves to *their own* organization (so the HMAC verifies with a secret they possess), while
- the `repository.full_name` / other repository fields consumed by the actual event handler (e.g. `PushHandler.process` at `app/models/shipit/webhooks/handlers/push_handler.rb`) reference a **different tenant's** repository/stack. [5](#0-4) 

This breaks the trust binding "the organization that authenticated == the repository that is written": the signature only proves the request was authorized by *some* configured organization, not that it was authorized by the organization that owns the repository the handler subsequently mutates (triggering `sync_github`, commit statuses, membership changes, PR-driven review-stack creation, etc., depending on event type).

### Impact Explanation
This allows an unprivileged-relative-to-the-victim attacker (privileged only within their own onboarded org) to inject forged, signature-valid webhook events that write to or trigger actions against another tenant's repository/stack in the same Shipit instance — a cross-repository/cross-tenant write, matching the Critical impact bar ("cross-repository writes"/"unauthorized deploy" depending on which event handler is reached, e.g. triggering syncs, statuses, or merge-queue behavior for a repo the attacker does not own).

### Likelihood Explanation
Requires a multi-organization Shipit deployment (explicitly supported and documented) and requires the attacker to control at least one legitimately onboarded organization's webhook secret — a realistic scenario for any shared/multi-tenant Shipit instance, and does not require compromising the victim org, a GitHub App private key, or any Shipit session/API token.

### Recommendation
- Verify the signature using the secret for the organization actually referenced by the fields the handlers use to resolve the target repository/stack (i.e., derive the verification key and the repository target from the exact same, single field), rather than allowing an `organization.login` fallback that can diverge from `repository.full_name`.
- After successful signature verification, explicitly assert that the organization whose secret verified the payload matches the owner of every repository referenced in the payload before invoking handlers.
- Reject payloads where `repository.owner.login` is missing/inconsistent with `organization.login` rather than silently falling back.

### Proof of Concept
1. Shipit is configured for two organizations, `AttackerOrg` and `VictimOrg`, each with its own `webhook_secret` (per `docs/setup.md`'s "Using Multiple Github Applications").
2. Attacker, who administers `AttackerOrg`'s GitHub App integration, knows `AttackerOrg`'s `webhook_secret`.
3. Attacker crafts a JSON body for a `push` event where the top-level `organization.login` is `"AttackerOrg"` but the `repository` object's `full_name`/`owner` fields reference `"VictimOrg/some-repo"`, arranging the payload so `repository.owner.login` is absent so `repository_owner` falls back to `organization.login` (`AttackerOrg`).
4. Attacker computes `X-Hub-Signature` using `AttackerOrg`'s known secret over the raw body and POSTs it to `WebhooksController#create`.
5. `verify_signature` calls `Shipit.github(organization: 'AttackerOrg')` and successfully verifies the HMAC.
6. The handler dispatch in `create` processes the event using the `repository` fields pointing at `VictimOrg/some-repo`, triggering unauthorized actions (e.g. `sync_github`) against a stack the attacker does not control.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
