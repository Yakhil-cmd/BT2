### Title
Front-running of `stack-stx`/`stack-extend`/`stack-aggregation-commit` via `used-signer-key-authorizations` pre-consumption locks stackers out of using a signer's authorization - (File: stackslib/src/chainstate/stacks/boot/pox-4.clar)

### Summary
`consume-signer-key-authorization` in `pox-4.clar` gates every stacking action (`stack-stx`, `stack-extend`, `delegate-stack-*`, `stack-aggregation-commit`, `stack-aggregation-increase`) behind a one-time-use authorization keyed on `{signer-key, reward-cycle, topic, period, pox-addr, auth-id, max-amount}`, inserted with `map-insert` (fails if the tuple already exists). Because the tuple does not bind the caller (`tx-sender`) or the exact `amount-ustx`, any unprivileged account that observes a pending, signed authorization (via mempool, or a signer publishing/broadcasting the signature off-chain for a batch of stackers) can replay it in its own transaction with a trivial `amount-ustx` (as low as `u1`, since only `amount <= max-amount` is checked, not equality) to consume the tuple first, permanently denying the legitimate stacker the ability to use that specific authorization. [1](#0-0) [2](#0-1) 

### Finding Description
`verify-signer-key-sig` recovers the public key from `signer-sig` over a message hash of `(pox-addr, reward-cycle, topic, period, max-amount, auth-id)` and checks it equals `signer-key`; it does **not** include `tx-sender`/`amount-ustx` in the signed payload, and the function is explicitly documented as not being restricted to a particular caller: "This function does not verify the payload of the authorization. The caller of this function must ensure that the payload... are valid according to the caller function's requirements." [3](#0-2) 

`consume-signer-key-authorization` then performs `map-insert used-signer-key-authorizations {...} true`, which fails (`ERR_SIGNER_AUTH_USED`) if the exact tuple already exists. [4](#0-3) 

Since the tuple key omits `tx-sender` and only bounds `amount` by `<= max-amount` (not equality), the authorization is fungible across any caller and any amount up to `max-amount`. This is directly analogous to the `CreateBondingCurve` bug: a resource whose "existence" is checked with a strict, unprivileged, front-runnable primitive (`init`/`map-insert`), which any account can trigger ahead of the legitimate user to permanently block them.

`stack-stx` calls this exactly in this vulnerable way — any account can call `stack-stx` with the victim's `signer-sig`, `signer-key`, `pox-addr`, `lock-period`, `max-amount`, `auth-id` but their own (attacker's) `amount-ustx` and `start-burn-ht`: [5](#0-4) 

### Impact Explanation
This breaks the "unsigned stacking action" / authorization-integrity equality: the signer authorized a specific stacker's specific stacking commitment, but the contract lets an unrelated, unauthorized account consume that grant and permanently prevent the intended stacker from stacking with it (until the signer produces a brand-new `auth-id`, which for `signer-key-authorizations`-based flows may not be under the victim's control at all). This is a temporary/permanent freezing of the victim's ability to lock STX in the intended reward cycle (a griefing/DoS on the stacking action), impacting reward-cycle participation and locking timing — matching the "temporary freezing of staked funds" / "unsigned stacking action" impact classes in scope.

### Likelihood Explanation
Medium: it requires the attacker to observe the signed authorization payload before it is consumed on-chain — achievable via mempool sniffing of the victim's pending `stack-stx`/`stack-extend`/`stack-aggregation-commit` transaction (which carries `signer-sig`, `signer-key`, `auth-id`, `max-amount`, `pox-addr`, `period` in cleartext), or via any off-chain distribution of the same signature to multiple candidate stackers (a common signer-operations pattern where one signature is meant to be usable by a specific known stacker). No cryptographic secret is needed — only observation and front-running with a minimal `amount-ustx`.

### Recommendation
Bind the authorization consumption to the actual caller/stacked amount, e.g. include `tx-sender` (or the intended stacker) and require `amount == max-amount` (or otherwise commit to the exact amount) in both the signed message hash and the `used-signer-key-authorizations` map key, so a third party cannot pre-consume another stacker's authorization with an arbitrary smaller amount.

### Proof of Concept
1. Signer produces a signature authorizing `stack-stx` for `pox-addr`, `reward-cycle`, `lock-period`, `max-amount = M`, `auth-id = A`, intended for Alice to lock `M` uSTX.
2. Alice broadcasts `stack-stx(M, pox-addr, start-burn-ht, lock-period, some(sig), signer-key, M, A)`.
3. Attacker Bob observes this pending transaction in the mempool, extracts `sig`, `signer-key`, `pox-addr`, `lock-period`, `M`, `A`, and submits his own `stack-stx(1, pox-addr, start-burn-ht, lock-period, some(sig), signer-key, M, A)` with higher fee/priority.
4. Bob's transaction is mined first: `consume-signer-key-authorization` succeeds (since `1 <= M`) and inserts the tuple `{signer-key, reward-cycle, "stack-stx", lock-period, pox-addr, auth-id: A, max-amount: M}` into `used-signer-key-authorizations`.
5. Alice's original transaction is then mined and fails with `ERR_SIGNER_AUTH_USED` from `map-insert` returning false, permanently blocking her stacking action for that `auth-id`.

;; This function does not verify the payload of the authorization. The caller of
;; this function must ensure that the payload (reward cycle, period, topic, and pox-addr)
;; are valid according to the caller function's requirements.
;;
;; When `signer-sig` is present, the public key is recovered from the signature
;; and compared to `signer-key`. If `signer-sig` is `none`, the function verifies that an authorization was previously
;; added for this key.
;; 
;; This function checks to ensure that the authorization hasn't been used yet, but it
;; does _not_ store the authorization as used. The function `consume-signer-key-authorization`
;; handles that, and this read-only function is exposed for client-side verification.
(define-read-only (verify-signer-key-sig (pox-addr { version: (buff 1), hashbytes: (buff 32) })
                                         (reward-cycle uint)
                                         (topic (string-ascii 14))
                                         (period uint)
                                         (signer-sig-opt (optional (buff 65)))
                                         (signer-key (buff 33))
                                         (amount uint)
                                         (max-amount uint)
                                         (auth-id uint))
  (begin
    ;; Validate that amount is less than or equal to `max-amount`
    (asserts! (>= max-amount amount) (err ERR_SIGNER_AUTH_AMOUNT_TOO_HIGH))
    (asserts! (is-none (map-get? used-signer-key-authorizations { signer-key: signer-key, reward-cycle: reward-cycle, topic: topic, period: period, pox-addr: pox-addr, auth-id: auth-id, max-amount: max-amount }))
              (err ERR_SIGNER_AUTH_USED))
    (match signer-sig-opt
      ;; `signer-sig` is present, verify the signature
      signer-sig (ok (asserts!
        (is-eq
          (unwrap! (secp256k1-recover?
            (get-signer-key-message-hash pox-addr reward-cycle topic period max-amount auth-id)
            signer-sig) (err ERR_INVALID_SIGNATURE_RECOVER))
          signer-key)
        (err ERR_INVALID_SIGNATURE_PUBKEY)))
      ;; `signer-sig` is not present, verify that an authorization was previously added for this key
      (ok (asserts! (default-to false (map-get? signer-key-authorizations
            { signer-key: signer-key, reward-cycle: reward-cycle, period: period, topic: topic, pox-addr: pox-addr, auth-id: auth-id, max-amount: max-amount }))
          (err ERR_NOT_ALLOWED)))
    ))

(define-private (consume-signer-key-authorization (pox-addr { version: (buff 1), hashbytes: (buff 32) })
                                                  (reward-cycle uint)
                                                  (topic (string-ascii 14))
                                                  (period uint)
                                                  (signer-sig-opt (optional (buff 65)))
                                                  (signer-key (buff 33))
                                                  (amount uint)
                                                  (max-amount uint)
                                                  (auth-id uint))
  (begin
    ;; verify the authorization
    (try! (verify-signer-key-sig pox-addr reward-cycle topic period signer-sig-opt signer-key amount max-amount auth-id))
    ;; update the `used-signer-key-authorizations` map
    (asserts! (map-insert used-signer-key-authorizations
      { signer-key: signer-key, reward-cycle: reward-cycle, topic: topic, period: period, pox-addr: pox-addr, auth-id: auth-id, max-amount: max-amount } true)
      (err ERR_SIGNER_AUTH_USED))
    (ok true)))
