## Title
Uncapped asset issuance in AA-composed payments can compute a zero `issue_amount`, causing the AA response unit to fail validation and bounce, freezing the trigger's funds - (File: aa_composer.js)

### Summary
In `aa_composer.js`, the `issueAsset()` helper used when an AA composes a payment message for an asset it doesn't yet have enough balance for computes `issue_amount = objAsset.cap || (target_amount - total_amount)` with no floor. [1](#0-0)  This mirrors the reported bug class: a quantity used to fill a shortfall is computed without guarding against the "already exactly covered" edge case, unlike the otherwise-identical logic path in `inputs.js`, which explicitly adds a `|| 1` fallback for the same computation with the comment "1 currency unit in case required_amount = total_amount". [2](#0-1) 

### Finding Description
`inputs.js`'s `pickDivisibleCoinsForAmount` reaches its own `issueAsset()` when existing coins/inputs exactly cover `required_amount` is not proven found and issuance is needed to close the last unit of value; it defensively falls back to `1` unit when `required_amount - total_amount` evaluates to `0` because equality would otherwise produce an invalid zero-amount output/change. [3](#0-2) 

The AA composer's `sendUnit`/`completePaymentPayload` flow implements the exact same "not enough funds yet, so issue an uncapped asset for the shortfall" logic for AA-composed payments, but omits the `|| 1` floor: `var issue_amount = objAsset.cap || (target_amount - total_amount);` [4](#0-3) . If this branch is reached when `target_amount === total_amount` (e.g., due to how `iterateUnspentOutputs`/`bFound` bookkeeping interacts with `issueAsset` being chained after `addWitnessingInputs`/`addHeadersCommissionInputs`-equivalent balance accumulation), `issue_amount` becomes `0`, and `addIssueInput(serial_number)` pushes an issue input with `amount: 0`. [5](#0-4) 

Unit validation elsewhere in the codebase requires the issue input's `amount` to be a positive integer (`isPositiveInteger(input.amount)`), which a `0` amount fails: [6](#0-5) . Since the AA response unit is a normal unit subject to the same `validation.validate` pipeline as any posted unit, a `0`-amount issue input makes the composed response unit invalid.

### Impact Explanation
When an AA's payment-composition logic hits this edge case, the response unit it tries to send becomes unvalidatable, which forces the AA trigger to bounce instead of completing its intended action (e.g., an asset-issuing AA that is also supposed to forward funds/complete other side effects). Since AA triggers charge bounce fees and the AA's other state changes for a genuinely completable operation are lost/reverted, this results in unintended fund loss/freezing for whoever triggered the AA and unreliable AA behavior for any AA design that issues uncapped assets to cover exact remaining shortfalls (a routine pattern for auto-issuing tokens matched 1:1 to incoming value). This matches the "AA fund loss or freezing" acceptance criterion.

### Likelihood Explanation
Likelihood is Low: it requires the specific arithmetic condition `target_amount === total_amount` to be reached inside `issueAsset()` for an uncapped asset (i.e., existing balances/collected inputs land exactly on the required amount before the issuance branch executes), which is a narrow, though externally influenceable, condition (an attacker/AA author can craft trigger amounts/outputs to hit exact equality, since `target_amount` is derived from trigger-controlled output amounts). This is analogous to the original finding's "High impact / Low likelihood" rating, since it is a single-post/trigger-reachable edge case, not an attacker-privileged or multi-party scenario.

### Recommendation
Apply the same defensive floor used in `inputs.js` to `aa_composer.js`'s `issueAsset()`:
```js
var issue_amount = objAsset.cap || (target_amount - total_amount) || 1; // 1 currency unit in case target_amount === total_amount
```
This keeps both issuance code paths (`inputs.js` for wallet composition and `aa_composer.js` for AA-composed payments) consistent, exactly as the external report recommends applying the same edge-case handling in the mirrored function.

### Proof of Concept
Not independently executable from the index alone — this requires constructing an AA definition that issues an uncapped asset while also spending down its balance for a payment message such that, after `iterateUnspentOutputs` runs over stable and then unstable outputs, `total_amount` lands exactly equal to `target_amount` right before `issueAsset()` is invoked (i.e., the "not found, but exact" case that in `inputs.js` is explicitly called out and handled). [7](#0-6)  A background Devin session with the ability to run the AA test suite (e.g., `test/aa_composer.test.js`) would be needed to construct and confirm this exact-equality trigger scenario end-to-end.
