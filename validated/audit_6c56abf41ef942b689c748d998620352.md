### Title
Unsanitized repository `Description` flows into tview List UI in `gh extension browse` - ([File: pkg/cmd/extension/browse/browse.go])

### Finding Description
`getExtensions` builds an `extEntry` directly from the GitHub search API response, copying `repo.Description` — a plain, attacker-controlled `string` — into `extEntry.description` with no filtering: [1](#0-0) 

`extEntry.Description()` returns that raw value unchanged: [2](#0-1) 

and `extList.Reset`/`Filter` pass it straight into `tview.List.AddItem`, which is drawn to the victim's real terminal: [3](#0-2) [4](#0-3) 

The attacker input is a repository `Description` on a repo tagged `gh-extension`, which anyone can publish without any privilege — a fully attacker-controlled, remotely-reachable field surfaced through `opts.Searcher.Repositories(...)` in `getExtensions`.

Critically, this codebase already has an established mitigation for exactly this class of problem: `pkg/iostreams/untrusted.go` defines an `Untrusted` wrapper whose explicit purpose is to neutralize ANSI/terminal escape sequences in "content the application did not author" (HTTP responses, remote file contents, etc.) before it reaches a terminal writer: [5](#0-4) 

This pattern is referenced/used across many other display paths in the CLI (gist view, pr diff, repo view, run view, etc.), showing the project's own threat model treats externally-authored text (including repository metadata surfaced via search) as needing sanitization before terminal rendering. `browse.go`'s `extEntry.description` is a bare `string`, never wrapped in `Untrusted` or passed through any ANSI-stripping step, which is an inconsistency with the rest of the codebase's handling of untrusted remote text.

What I could **not** verify from this repo alone is the exact terminal-writing behavior of the vendored `tview`/`tcell` libraries (i.e., whether raw C0 control bytes such as ESC placed in `List` item text are emitted verbatim to the terminal's output stream, or whether `tcell`'s cell-based screen model filters/replaces non-printable runes before writing). That behavior lives in a third-party dependency not present in this repo's index, so I cannot give a fully reproducible proof that a specific payload defeats `tcell`'s output layer. This uncertainty is a caveat, not a claim that no risk exists — the code path unquestionably has no sanitization step for content the project's own conventions (`Untrusted`) treat as requiring one.

### Impact Explanation
If `tcell`/`tview` does not filter control/escape bytes embedded in list item text (a real, previously-reported class of bug for terminal UI libraries), a malicious repo `Description` could inject terminal escape/control sequences rendered on the victim's terminal during `gh extension browse`, before any install action — e.g., cursor manipulation, clearing/overwriting visible content, or (with OSC-class sequences depending on the terminal emulator) more severe terminal-level effects. This matches the "terminal escape/output injection via untrusted content" impact class the project already mitigates elsewhere via `Untrusted`.

### Likelihood Explanation
Preconditions are low-effort and require no privilege: an attacker only needs to publish a public GitHub repository named `gh-*` tagged `gh-extension` with a crafted `Description` containing escape bytes, then wait for a victim to run `gh extension browse`. Every listed repository's description is loaded unconditionally via `getExtensions`, so exploitation is repeatable and does not require victim interaction with the malicious entry beyond opening the browse UI. The residual uncertainty is solely whether the underlying rendering library passes the bytes through verbatim, which I could not confirm from this codebase.

### Recommendation
Wrap `repo.Description` (and similarly `repo.FullName`/`Name` if not already validated) in `iostreams.NewUntrusted(...)` (or an equivalent ANSI-sanitizing step) before storing it in `extEntry.description`, consistent with how other commands treat externally-sourced text, e.g.:
```go
ee := extEntry{
    ...
    description: iostreams.NewUntrusted(repo.Description).String(),
}
```
so that `Description()` can never return a value containing raw C0/ANSI escape sequences before it reaches `tview.List.AddItem`.

### Proof of Concept
```go
func TestExtEntryDescriptionSanitization(t *testing.T) {
    ee := extEntry{description: "\x1b[2J\x1b[H malicious title\x07"}
    got := ee.Description()
    // Today this fails: got == the raw string containing ESC bytes.
    if strings.ContainsAny(got, "\x1b\x07") {
        t.Fatalf("Description() leaked raw escape/control bytes: %q", got)
    }
}
```
A fuller integration PoC would httpmock `opts.Searcher.Repositories` to return a `search.RepositoriesResult` with one `Item` whose `Description` contains `\x1b[...` sequences, run `getExtensions`, and assert the resulting `extEntry.Description()` (or the string passed to `ui.List.AddItem`) no longer contains raw ESC/C0 bytes — matching the guarantee already provided by `iostreams.Untrusted.String()`.

// Untrusted wraps string content the application did not author: HTTP response
// bodies, file contents fetched from a remote, anything that originates outside
// the CLI. The raw bytes are unexported so the only ways out are the methods
// below.
//
// Untrusted satisfies fmt.Stringer, and String sanitizes, so any fmt print path
// (Fprint, Fprintf with %s or %v, Sprint) renders the content with ANSI escape
// sequences neutralized. The only way to reach the raw bytes is Raw, which is
// deliberately easy to grep for and is intended for non-terminal uses such as
// hashing, writing to a file, or piping to another program.
type Untrusted struct {
	raw string
}

// NewUntrusted labels a string as untrusted external content.
func NewUntrusted(s string) Untrusted {
	return Untrusted{raw: s}
}

// NewUntrustedBytes labels a byte slice as untrusted external content.
func NewUntrustedBytes(b []byte) Untrusted {
	return Untrusted{raw: string(b)}
}

// String returns the content with ANSI escape sequences neutralized. It is
// called automatically by the fmt package, so printing an Untrusted value is
// safe by default on every fmt path.
func (u Untrusted) String() string {
	sanitized, _, err := transform.String(&asciisanitizer.Sanitizer{}, u.raw)
	if err != nil {
		return stripControl(u.raw)
	}
	return sanitized
}
