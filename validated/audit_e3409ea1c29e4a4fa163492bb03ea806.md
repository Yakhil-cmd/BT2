### Title
Webhook signature is validated against the payload's `repository.owner`/`organization` login while every event handler resolves and writes to the stack keyed off `repository.full_name`, letting an attacker who controls one organization's webhook secret drive actions against another organization's repositories - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks the GitHub App/secret to validate the HMAC signature using `repository_owner`, derived from the payload's `repository.owner.login` (or `organization.login`) field. [1](#0-0) [2](#0-1)  But every downstream handler resolves the actual stack/repository to act on using a *different* field of the same attacker-supplied JSON body: `payload.dig('repository', 'full_name')`. [3](#0-2)  Neither of these two fields is cross-checked against the other, and the HMAC only proves the request was signed by *some* configured organization's secret — not that the signing organization matches the repository the handler is about to mutate.

### Finding Description
In multi-organization deployments, `Shipit.github(organization:)` looks up a distinct `GitHubApp` (and thus a distinct `webhook_secret`) per organization key in `secrets.github`. [4](#0-3)  `WebhooksController#verify_signature` selects which app/secret to verify against solely based on `repository_owner`, which is read straight out of the untrusted JSON body (`params.dig('repository','owner','login')` or `params.dig('organization','login')`). [2](#0-1) 

Once the signature check passes, `WebhooksController#create` parses the same raw body again and dispatches it to all registered handlers for the event type. [5](#0-4)  Every handler (base `Handler#stacks`/`#repository_name`, `PushHandler`, `StatusHandler`, `CheckSuiteHandler`, the `PullRequest::*Handler`s) determines *what to write to* using `repository.full_name`, completely independent of the `repository.owner.login` value that gated the signature check. [3](#0-2) [6](#0-5) [7](#0-6) 

This breaks the intended trust binding: `{organization that authenticated the signature} == {repository/stack that gets written}`. An attacker who has legitimate access to configure or leak the `webhook_secret` for organization A (e.g., a low-privileged admin of an A-owned GitHub App, or anyone who can read A's webhook secret through any means outside Shipit) can craft a JSON body where `repository.owner.login` (and `organization.login`) is set to `"A"` — so `verify_signature` picks A's secret and the HMAC validates — while `repository.full_name` is set to `"B/some-repo"`, an entirely different organization's repository that is also configured in this Shipit instance. The forged payload will pass signature verification and then be processed by handlers that act on organization B's stack.

### Impact Explanation
Depending on event type this enables, for org B's stack, without any credential or access to org B:
- `PushHandler` calls `stack.sync_github(expected_head_sha:)`, which enqueues `GithubSyncJob` to fetch commits from GitHub and can drive `trigger_continuous_delivery`/deploys for the target stack, i.e., an attacker-triggered, effectively unauthorized deploy pipeline action on a repository the attacker doesn't own. [8](#0-7) [9](#0-8) 
- `StatusHandler` writes forged CI/check statuses onto commits of the target stack (`commit.create_status_from_github!`), which can be used to satisfy deploy-blocking status checks and unlock an otherwise-blocked deploy on org B's stack. [10](#0-9) 
- `CheckSuiteHandler` schedules check-run refreshes for org B's commits. [11](#0-10) 

This is a cross-organization write into repository/stack state that the caller (org A's credential) has no authorization over, matching the "cross-repository writes / unauthorized deploy" Critical impact category.

### Likelihood Explanation
This requires the target Shipit instance to be configured with the multi-organization GitHub App schema (multiple orgs, each with its own `webhook_secret`, as shown in `test/dummy/config/secrets_double_github_app.yml`) and requires the attacker to know one organization's webhook secret (a credential that is, by design, scoped to only that organization's repos). Given that constraint, the exploit itself needs only a single crafted, self-signed HTTP POST to `/webhooks` — no session, no `ApiClient` token, no GitHub write access on the target repository is needed to affect it.

### Recommendation
In `WebhooksController#verify_signature` (or in `Webhooks::Handlers::Handler`), after signature verification succeeds, assert that the organization used to select the verifying `GitHubApp` matches the owner segment of `repository.full_name` (or `organization.login`) actually used by the handler to resolve the stack, and reject (422) the webhook if they differ. Alternatively, bind `repository_name`/`stacks` resolution in `Handler` to the same `repository_owner` value validated by the controller, rather than trusting `repository.full_name` independently.

### Proof of Concept
1. Configure Shipit with the multi-org schema: organization `OrgA` (secret `sA`) and organization `OrgB` (secret `sB`), each with a stack tracking a distinct GitHub repo (`OrgA/repoA`, `OrgB/repoB`).
2. Attacker knows/controls `sA` (e.g., is an admin of OrgA's GitHub App) but has no access to `OrgB`.
3. Attacker crafts a push webhook body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>",
  "repository": { "full_name": "OrgB/repoB", "owner": { "login": "OrgA" } }
}
```
4. Attacker signs the raw body with `sA` and sets `X-Hub-Signature`, `X-Github-Event: push`, and POSTs to `/webhooks`.
5. `verify_signature` calls `Shipit.github(organization: "OrgA")` and the HMAC validates successfully. [1](#0-0) 
6. `PushHandler#stacks` resolves `Repository.from_github_repo_name("OrgB/repoB")` and enqueues sync/deploy activity for OrgB's stack, despite the request only being authenticated as OrgA. [3](#0-2) [8](#0-7)

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def perform(params)
      @stack = Stack.find(params[:stack_id])
      expected_head_sha = params[:expected_head_sha]
      retry_count = params[:retry_count] || 0
      head_before_sync = spec_cache_target
      appended_commits = []

      handle_github_errors do
        new_commits, shared_parent = fetch_missing_commits { stack.github_commits }

        # Retry on Github eventual consistency: webhook indicated new commits but we found none
        if expected_head_sha && new_commits.empty? && !commit_exists?(expected_head_sha) &&
           retry_count < MAX_RETRY_ATTEMPTS
          GithubSyncJob.set(wait: RETRY_DELAY * retry_count).perform_later(params.merge(retry_count: retry_count + 1))
          return
        end

        stack.transaction do
          shared_parent&.detach_children!
          appended_commits = new_commits.map do |gh_commit|
            append_commit(gh_commit)
          end
          stack.lock_reverted_commits! if appended_commits.any?(&:revert?)
        end
      end
      sync_changed_nothing = appended_commits.empty? &&
                             spec_cache_target == head_before_sync &&
                             stack.cached_deploy_spec.present?
      return if sync_changed_nothing && !params[:force_spec_cache]

      CacheDeploySpecJob.perform_later(stack)
    end
