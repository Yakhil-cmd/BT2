### Title
Cross-repository unauthorized sync/write via `repository.owner.login` vs `repository.full_name` split in webhook signature verification - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/webhook secret to validate the inbound webhook signature against using `repository_owner`, which is read from `params.dig('repository', 'owner', 'login')` (or `organization.login`). However, the actual write operation performed by the event handlers (`PushHandler`, `StatusHandler`, `CheckSuiteHandler`, `MembershipHandler`, etc.) resolves the target `Repository`/`Stack` using a **different** field of the same JSON body: `payload.dig('repository', 'full_name')` (in `Handler#repository_name`). The field used to pick the verification secret is not the field used to determine which repository/stack is mutated.

### Finding Description
`verify_signature` in `app/controllers/shipit/webhooks_controller.rb` does: [1](#0-0) 

`repository_owner` is derived purely from the JSON body: [2](#0-1) 

The GitHub App config (and thus the HMAC secret used for signature verification) is looked up per-organization via `Shipit.github(organization: repository_owner)`, whose secret comes from `github_app_config`/`secrets.github`: [3](#0-2) 

Critically, `GitHubApp#verify_webhook_signature` **trivially returns `true` when no `webhook_secret` is configured for that organization**: [4](#0-3) 

Meanwhile, once the request passes `verify_signature`, the actual handler dispatch resolves the target repository using a *different* JSON field — `repository.full_name` — via `Handler#repository_name`/`#stacks`: [5](#0-4) 

and e.g. `PushHandler#process` calls `stack.sync_github(expected_head_sha: params.after)` for every matching, non-archived stack on the resolved repository/branch: [6](#0-5) 

This breaks the intended binding: **organization authenticated (via `repository.owner.login`, used to choose the signing secret) == repository actually written (via `repository.full_name`, used to resolve the Stack that gets mutated)**. An attacker who knows (or controls) an organization configured in Shipit's multi-org `secrets.yml` with a blank/unset `webhook_secret` (documented as optional, see `docs/setup.md` and `config/secrets.development.shopify.yml`) can craft a webhook body where `repository.owner.login` is set to that unsecured organization while `repository.full_name` points at an entirely different, legitimately-secured target repository/stack. Because `webhook_secret` is blank for the org chosen for verification, `verify_webhook_signature` always returns `true` regardless of the (bogus or missing) `X-Hub-Signature` header, and the request proceeds to act on the unrelated target stack named in `repository.full_name`.

This is directly analogous to the EIP-777 report's core bug class: a field that is acted upon (`repository.full_name`, which determines the write target) is not the field bound to the authentication decision (`repository.owner.login`, which determines the verification secret) — the two are only coincidentally linked by convention, not enforced equality.

### Impact Explanation
If exploitable (i.e., an organization is configured in `secrets.yml` with a webhook entry but no `webhook_secret`, which the docs treat as optional/valid), an unprivileged external attacker can forge webhook deliveries that:
- Trigger `GithubSyncJob`/`stack.sync_github` for arbitrary stacks belonging to *other*, properly-secured organizations (`PushHandler`), potentially causing unintended commit ingestion, cache invalidation, or feeding attacker-influenced `expected_head_sha` into Shipit's github sync flow.
- Forge commit statuses for arbitrary tracked commits (`StatusHandler`), influencing CI-gated deploy/merge decisions.
- Create teams/memberships (`MembershipHandler`) tied to arbitrary organizations claimed in the payload.

This crosses the "organization that authenticated versus the repository that is written" trust boundary called out in scope, and can lead to unauthorized state changes (commit status forgery affecting merge/deploy gating) on repositories outside the attacker's control.

### Likelihood Explanation
Exploitability is conditional: it requires that at least one configured GitHub organization in the deployment's `secrets.yml` has a blank `webhook_secret` (explicitly supported/documented as optional per `docs/setup.md`), which the attacker can determine by probing (repeated webhook posts with different `owner.login` guesses and observing which get accepted with any/garbage signature). In single-app (non-multi-org) deployments this specific path collapses to the single configured secret being used regardless of payload content, reducing exploitability to only genuinely misconfigured multi-org setups. This is a real, code-level authorization/data binding flaw but its practical reach depends on host configuration choices (multiple orgs, one without a secret), which is a legitimate but non-default configuration.

### Recommendation
- Enforce that the organization used for signature verification (`repository.owner.login`/`organization.login`) matches the organization portion of `repository.full_name` used by the handlers before dispatching to handlers.
- Do not allow `verify_webhook_signature` to silently return `true` when `webhook_secret` is blank; instead, require and validate a secret for every organization that has webhooks configured, or explicitly reject/log-and-alert when an org has none configured.
- Consider passing the already-resolved, verified organization context into the handler layer instead of letting handlers independently re-derive the target repository from a different JSON field.

### Proof of Concept
Given a multi-org `secrets.yml` where organization `unsecured-org` has webhook entries but `webhook_secret: nil`, and organization `victim-org` (with a real `victim-org/target-repo` stack configured) has its own secret:

```
POST /webhooks
X-Github-Event: push
X-Hub-Signature: sha1=deadbeef   (arbitrary/garbage)

{
  "ref": "refs/heads/main",
  "after": "attacker-chosen-sha",
  "repository": {
    "owner": { "login": "unsecured-org" },
    "full_name": "victim-org/target-repo"
  }
}
```

`verify_signature` calls `Shipit.github(organization: "unsecured-org")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` unconditionally regardless of the bogus signature. The request then reaches `PushHandler`, which resolves the stack via `repository.full_name = "victim-org/target-repo"` and calls `stack.sync_github(expected_head_sha: "attacker-chosen-sha")`, acting on the victim's stack despite the forged/unverifiable signature.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
