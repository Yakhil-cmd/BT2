### Title
CCMenu API token authorized for one stack can read the build/deploy status of any stack - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
The `Shipit::Api::CCMenuController` overrides the stack-lookup helper used by `Shipit::Api::BaseController` in a way that discards the `ApiClient`'s stack scoping. Any valid CCMenu token can be replayed against an arbitrary `stack_id` to read that stack's deploy/build status, even though the token was only ever intended to authorize CI-status reads for the single stack it was minted for.

### Finding Description
`Shipit::Api::BaseController#stack` scopes lookups through `stacks`, which restricts the visible `Stack` set to the one bound to the API client when the client has a `stack_id`: [1](#0-0) 

`Shipit::Api::CCMenuController`, however, redefines `stack` to bypass that scope entirely and load directly by param: [2](#0-1) 

The only authorization check performed before `show` renders the CI status XML is `require_permission :read, :stack`, which merely checks that the `read:stack` permission string is present on the token — it never verifies that the requested `stack_id` matches the client's bound stack: [3](#0-2) [4](#0-3) 

CCMenu tokens are created by `CCMenuUrlController` with `read:stack` permission and handed out as bare query-string tokens embedded in a URL (`?token=...`), specifically designed for unauthenticated, machine-to-machine consumption (CI dashboard widgets, build-status trays), scoped to a single stack at creation time: [5](#0-4) 

The equality this breaks is:
`stack the token authorizes (the one it was generated/bound for) == stack the token can touch (any Stack.from_param!)`

Before the (implicit) fix, both sides are equal only if the CCMenu route enforced the same `stacks`-scoped lookup as every other API controller; instead the right-hand side is unconstrained — `Stack.from_param!(params[:stack_id])` accepts any existing stack identifier regardless of the token's binding.

### Impact Explanation
This maps to the "High — unauthenticated read of stack state ... deploy output" category: an attacker who obtains any single CCMenu token (these are routinely shared in CI badges, build trays, Slack integrations, or leaked via Referer headers/browser history because they are bare, long-lived query-string tokens) can enumerate `stack_id` values and pull the merge/lock status, latest build result, build label, and web URL for every stack hosted by the Shipit instance — not just the one the token owner intended to expose. This is a cross-stack authorization boundary crossing analogous to the report's "signature covers one field but a different field is executed" ABI-encoding class: the signature (token) authorizes stack A, but the code acts on stack B.

### Likelihood Explanation
Likelihood is moderate-to-high: CCMenu tokens are explicitly designed to be embedded in unauthenticated, third-party consumable URLs (build trays, status badges), so they are more exposure-prone than typical `ApiClient` tokens used over `Authorization: Basic`. The `test/controllers/api/ccmenu_controller_test.rb` suite confirms tokens can authenticate via query string (`token=`) with no further stack check, and no test in the suite asserts stack-scoping is enforced for CCMenu clients, consistent with the missing check in code. [6](#0-5) 

### Recommendation
Have `Shipit::Api::CCMenuController#stack` reuse the scoped `stacks` collection from `BaseController` (i.e., `stacks.from_param!(params[:stack_id])`) instead of `Stack.from_param!`, so a stack-bound `ApiClient` cannot be replayed against stacks outside its `stack_id` binding.

### Proof of Concept
1. As a legitimate user, generate a CCMenu URL for stack A via `CCMenuUrlController#fetch` (e.g. `GET /stacks/:owner/:repo/:env/ccmenu_url`), obtaining a token `T` scoped (by intent) to stack A.
2. Call the CI status endpoint for a different stack B that the token was never meant to expose:
   `GET /api/stacks/<stack-B-id>/ccmenu.xml?token=T`
3. Because `CCMenuController#stack` uses `Stack.from_param!(params[:stack_id])` directly (bypassing `BaseController#stacks` scoping), the request succeeds and returns stack B's build status, label, activity, and lock state, even though `T` was intended only for stack A.
