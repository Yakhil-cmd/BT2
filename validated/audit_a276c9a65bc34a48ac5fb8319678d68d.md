### Title
Webhook signature verified against `repository.owner.login`/`organization.login` while `pull_request` handlers act on an independently attacker-supplied `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects which GitHub App (and thus which HMAC secret) authenticates a webhook using `repository_owner`, which falls back from `repository.owner.login` to `organization.login` [1](#0-0) . `ClosedHandler`, however, resolves the affected repository/stack from the independent `params.repository.full_name` field [2](#0-1) . In a multi-GitHub-App deployment (`Shipit.github(organization:)`) this lets a payload authenticated under one organization's (weak/secret-less) app archive a `ReviewStack` belonging to a different organization/repository.

### Finding Description
The broken binding is the assumption: `organization_used_to_verify_signature == organization_owning_repository.full_name_used_by_handler`. In practice these are two independently attacker-controlled JSON fields.

- `repository_owner` in the controller reads `params.dig('repository','owner','login') || params.dig('organization','login')` [1](#0-0) .
- `verify_signature` calls `Shipit.github(organization: repository_owner)` to pick the `GitHubApp` instance and then `verify_webhook_signature` [3](#0-2) .
- `GitHubApp#verify_webhook_signature` returns `true` unconditionally when that particular org's config has no `webhook_secret` set: `return true unless webhook_secret` [4](#0-3) . The docs explicitly show `webhook_secret` is optional and each org gets independent config under `Shipit.github` multi-app mode [5](#0-4) , and `Shipit#github` resolves per-organization config via `github_app_config(organization)` when `github_default_organization` is not nil [6](#0-5) .
- `ClosedHandler#repository` never looks at `repository.owner.login`/`organization.login`; it only requires and reads `params.repository.full_name` [7](#0-6) , and `ReviewStackAdapter#archive!` archives/deprovisions whatever `ReviewStack` matches `environment` (`"pr#{number}"`) scoped to that resolved repository [8](#0-7) .

Exploit flow: attacker crafts a `pull_request` `action=closed` payload where `repository.full_name = "victim-org/victim-repo"` (satisfies the handler's `ExplicitParameters` schema, which only requires `full_name`, not `owner.login`) but omits `repository.owner.login` and instead sets a top-level `organization.login` to some other, attacker-known/secret-less configured org (e.g., a public org where the Shipit operator forgot to set `webhook_secret`, or one whose secret has otherwise leaked/is empty). `repository_owner` falls back to that lenient org, `verify_webhook_signature` returns `true` unconditionally, and the request is processed. The handler then resolves and archives the victim's `ReviewStack` using `repository.full_name`, entirely independent of which org authenticated the request.

Existing guards do not prevent this: `drop_unhandled_event` only checks the event type is registered [9](#0-8) ; `GithubOrganizationUnknown` only blocks entirely unconfigured org names, not configured-but-secretless ones [10](#0-9) ; the `ExplicitParameters` schema on `ClosedHandler` does not require `repository.owner.login` to match anything [11](#0-10) .

Note: this divergence is inert in the common single-GitHub-App deployment, because `Shipit.github` ignores the `organization:` argument entirely when `github_default_organization` is `nil` (single app schema) and always resolves the one global `secrets.github` config [10](#0-9) . It only becomes exploitable under the documented "Using Multiple Github Applications" multi-tenant configuration [5](#0-4) , and further requires that at least one configured organization lacks (or has a leaked) `webhook_secret`.

### Impact Explanation
Under multi-org configuration with one org missing `webhook_secret`, an attacker can submit forged `pull_request`/`closed` webhooks that get authenticated as "from" the secret-less org but cause `ClosedHandler` to archive (and deprovision) a `ReviewStack` belonging to an entirely different, correctly-secured tenant/organization's repository — "a record written/mutated for a repository that did not authenticate it," matching the Critical category "a payload for one repository mutating another's stack." The `Commit#deployable?`/`ignore_ci` amplification claimed in the question is not actually exercised by `ClosedHandler` (it only archives; it does not deploy), so the "unauthorized deploy/rollback" escalation described in the prompt is not substantiated by this handler — the concretely demonstrable impact is limited to unauthorized archival/deprovisioning of a foreign stack, not an unauthorized deploy of attacker code.

### Likelihood Explanation
Requires: (1) the operator to run Shipit in the multi-GitHub-App configuration (`Shipit.github` keyed by organization) rather than the default single-app config, and (2) at least one configured organization to have no `webhook_secret` set (an explicitly optional field per docs) or a leaked one. Given both preconditions, the attack is cheap and repeatable (a single unauthenticated `POST /webhooks` per target PR number/repository), but it is not exploitable in the default/typical single-org deployment, and depends on an operator misconfiguration (missing per-org secret) rather than being universally exploitable.

### Recommendation
Verify the webhook signature using the same organization/app config that will actually be used to process the event: derive the app/secret from `repository.full_name`'s owner (or require `repository.owner.login` to be present and match `repository.full_name`'s owner) rather than allowing an independent `organization.login` fallback to select a different app's secret. Additionally, treat a per-organization `webhook_secret` of `nil` in multi-app mode as a hard misconfiguration to reject rather than silently accepting unsigned requests.

### Proof of Concept
Not producible as a fully valid, in-scope minitest without additional fixtures: reproducing this requires switching test config to the multi-org secrets file (`test/dummy/config/secrets_double_github_app.yml`, which already models two orgs `OrgOne`/`OrgTwo` both with `webhook_secret: nil`) and asserting that a `pull_request`/`closed` payload with `organization.login: "OrgOne"` and `repository.full_name: "OrgTwo/repo"` archives `OrgTwo`'s `ReviewStack`. That test would need to construct a `ReviewStack` fixture under `OrgTwo`, stub `Shipit.secrets` to the double-org fixture, and assert `stack.reload.archived?` is `true` while no valid signature for `OrgTwo`'s app was ever presented — this is plausible given the code paths found, but I did not execute it and cannot fully confirm ancillary constraints (e.g., `Repository.from_github_repo_name` normalization, `ReviewStack` scoping via `repository.review_stacks`) without running the suite.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
