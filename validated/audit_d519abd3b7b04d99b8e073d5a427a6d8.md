## Finding: `reportUnauthorizedSigning`-style front-running maps to a cross-tenant webhook confused-deputy in Shipit's multi-org signature verification

### Title
Webhook signature verification key is selected from an attacker-controlled payload field, allowing cross-organization forgery of GitHub events - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
The external report's root cause is that a privileged action (claiming the fraud-report reward) was gated only by a proof that was *not* bound to the identity of the actor invoking it, letting anyone reuse someone else's valid proof for their own benefit. The same class of bug — a verification step that is bound to the wrong identity — exists in Shipit's webhook ingestion pipeline: the GitHub App (and thus the `webhook_secret`) used to verify the HMAC signature of an inbound webhook is selected using an attacker-controlled field from the same untrusted payload (`repository.owner.login`), while the actual repository/stack that is mutated is selected from a *different* field of that same payload (`repository.full_name`). In a single-organization deployment this is harmless because GitHub always keeps those fields consistent. But Shipit explicitly supports and documents multi-organization deployments where each organization has its own independent `webhook_secret`, and nothing binds the verified secret's organization to the "acted-upon" repository's owner.

### Finding Description
`WebhooksController#verify_signature` selects which `GitHubApp`/`webhook_secret` to validate the request against using `repository_owner`, which is read straight from the JSON body: [1](#0-0) [2](#0-1) 

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

Once the signature is accepted, the actual event handlers determine which `Repository`/`Stack` to mutate using a *different* JSON field, `repository.full_name`, defined in the shared `Handler` base class: [3](#0-2) 

```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
```

Shipit's documented configuration schema supports configuring multiple independent GitHub Apps/organizations on one Shipit instance, each with its own `webhook_secret`: [4](#0-3) 

`Shipit.github(organization: repository_owner)` resolves the app/secret purely by the `organization` string, and `GitHubApp#verify_webhook_signature` just checks the HMAC against whichever secret was resolved: [5](#0-4) 

The binding that should hold is:
`organization whose secret authenticated the request == owner of the repository actually written to (Repository.from_github_repo_name(repository.full_name))`

Because both `repository.owner.login` and `repository.full_name` are independent, attacker-suppliable JSON keys in the same POST body — and `POST /webhooks` is a public, unauthenticated endpoint that accepts a raw body from anyone who can produce a valid `X-Hub-Signature` — an operator of **any one** organization configured on the shared Shipit instance can forge a payload where `repository.owner.login` names *their own* organization (so `verify_signature` selects and successfully checks against a secret they know) while `repository.full_name` names a **victim** organization's repository. The handler never re-validates that the two fields refer to the same organization.

### Impact Explanation
This breaks a cross-tenant trust boundary equivalent to "an organization that authenticated versus the repository that is written." A tenant admin who legitimately knows their own org's `webhook_secret` can, without any credentials or write access to a victim org/repo hosted on the same Shipit instance, forge webhook events (`push`, `status`, `check_suite`, `pull_request`, `membership`) that Shipit will process as authentic for the victim repository. Concretely:
- Forging a `status` event lets the attacker inject arbitrary commit statuses for any commit SHA known to exist on the victim's stack (`StatusHandler`), which can satisfy deploy-blocking/CI-gating checks and enable an unauthorized deploy.
- Forging a `push` event can trigger `GithubSyncJob` for the victim's stack.
- Forging a `membership` event can add/remove `Team`/`Membership` records tied to the victim's authorization configuration.

This satisfies the Critical impact bar of "cross-repository writes" / "an unauthorized deploy."

### Likelihood Explanation
Requires only: (1) the target Shipit deployment to be configured with more than one GitHub organization (a documented, supported configuration), and (2) the attacker to control/administer one of those configured organizations (their own `webhook_secret`, which they set up themselves and is not privileged relative to any *other* tenant). No Shipit session, API token, or GitHub write access to the victim repository is needed — this is exactly the class of unprivileged, cross-tenant attacker the rules call for.

### Recommendation
After signature verification, re-derive the organization from the same field the handlers use to select the target repository (`repository.full_name`'s owner segment, or `organization.login`), and reject the webhook if it does not match the organization whose secret validated the signature. Alternatively, verify the signature once per uniquely-configured secret and require that the resolved app's organization equals the owner of `repository.full_name` before dispatching to any handler.

### Proof of Concept
1. Deploy Shipit configured with two organizations, `org-a` (attacker-controlled, webhook_secret known to attacker) and `org-b` (victim, has a `Repository`/`Stack` tracked by Shipit).
2. Attacker crafts a JSON body for a `status` event:
```json
{
  "sha": "<victim commit sha>",
  "state": "success",
  "repository": { "owner": { "login": "org-a" }, "full_name": "org-b/victim-repo" }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(org-a_webhook_secret, body)` and POSTs to `/webhooks` with header `X-Github-Event: status`.
4. `WebhooksController#verify_signature` resolves `repository_owner` = `org-a`, fetches `Shipit.github(organization: 'org-a')`, and successfully verifies the signature using the attacker's known secret.
5. `StatusHandler#process` (via `Handler#stacks`/`repository_name`) resolves the target repository from `repository.full_name` = `org-b/victim-repo`, and creates/updates a commit status on the victim's stack — despite the request never having been authenticated by `org-b`'s own GitHub App or secret.     def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
