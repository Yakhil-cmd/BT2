### Title
Webhook signature verification binds to `repository.owner.login`, but the mutating action binds to the unverified `repository.full_name` field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App / HMAC secret to use for validating an inbound webhook based on `repository.owner.login` (falling back to `organization.login`), then hands the *entire raw JSON payload* to the event handlers. Every handler resolves the target `Stack`/`Repository` using a completely different field of the same payload: `repository.full_name`, via `Handler#stacks` / `Handler#repository_name`. Because the signature check never verifies that `repository.full_name` actually belongs to the organization whose secret validated the request, the "organization that authenticated" and "the repository that is written" are two independent, uncorrelated fields inside one HMAC-signed blob.

### Finding Description
`verify_signature` picks the `GithubApp` (and therefore the per-organization `webhook_secret`) purely from: [1](#0-0) [2](#0-1) 

`verify_webhook_signature` HMACs the *raw* request body with that organization's own secret: [3](#0-2) 

If verification passes, `create` forwards the parsed `params` — unchanged — to every registered handler for the event: [4](#0-3) 

All handlers inherit from `Handler`, which locates the `Stack`(s) to mutate using `repository.full_name`, a field that plays no role whatsoever in signature verification: [5](#0-4) 

Shipit explicitly supports multiple GitHub Apps for multiple organizations, each with its own independently configured (and optional) `webhook_secret`: [6](#0-5) [7](#0-6) 

This creates the exact binding break the bug class targets: the field the signature covers (`repository.owner.login`, used only to pick a secret) is not the field the code acts on (`repository.full_name`, used to find the real `Stack`/`Repository`). An attacker who legitimately controls, or can obtain a valid signature for, *any* single organization configured in Shipit (e.g., their own low-privilege GitHub org where they installed a Shipit-linked GitHub App and thus know that org's `webhook_secret`), can sign a payload where `repository.owner.login` matches their own org (so `Shipit.github(organization: ...)` resolves to their own app/secret and the HMAC validates), while `repository.full_name` is forged to point at an unrelated, privileged `owner/repo` actually tracked by Shipit. Handlers such as `PushHandler`, `StatusHandler`, `CheckSuiteHandler`, `MembershipHandler`, and the pull-request handlers will all resolve stacks/commits/teams/users for that forged `full_name`/`organization.login`, not the organization whose key actually signed the request.

Concretely:
- `PushHandler` enqueues `stack.sync_github(expected_head_sha: ...)` for any stack matching the forged `full_name`+branch: [8](#0-7) 
- `StatusHandler` writes attacker-controlled commit statuses (`state`, `target_url`, `description`, `context`) for any commit SHA the attacker names, without checking that the SHA belongs to the forged repository at all: [9](#0-8) 

Since Shipit gates deploy/merge/rollback decisions on synced commit state and CI status, this lets an attacker who only controls a *second*, unrelated GitHub organization forge CI/push signals for a stack they have no access to.

### Impact Explanation
This breaks the "organization authenticated vs. repository written" binding required by the scope rules. Forged `push` events can trigger `GithubSyncJob`/`sync_github` against a victim stack, and forged `status` events can inject fabricated commit statuses that Shipit uses to gate deploy/merge eligibility — enabling an unauthorized deploy/merge path without any credential belonging to the victim organization. This meets the High-impact bar ("escalation ... unauthorized deploy, rollback or merge" territory) since the attacker never needed the victim organization's webhook secret, only a signature valid for *some* organization configured in the same Shipit instance (or an org with no `webhook_secret` set at all, which `verify_webhook_signature` explicitly treats as always-valid).

### Likelihood Explanation
Requires: (1) Shipit configured to serve more than one GitHub organization (or one org with `webhook_secret` left blank, which is documented as optional), and (2) the attacker be able to sign or replay a request under any one of those configured organizations. This is realistic in multi-tenant Shipit deployments, and the "optional secret" case requires no attacker capability beyond crafting an HTTP POST to `/webhooks`.

### Recommendation
Cross-validate that `repository.full_name`'s owner segment matches the `repository.owner.login`/`organization.login` used to select the verifying `GithubApp`, and additionally verify that the resolved `Repository`/`Stack` actually belongs to the organization that produced a valid signature before handlers are invoked. Do not allow an organization with an empty `webhook_secret` to implicitly authenticate payloads describing other organizations' repositories.

### Proof of Concept
1. Configure (or find) Shipit multi-org setup where organization `attacker-org` is registered with its own GitHub App/`webhook_secret`, and organization `victim-org` hosts a real tracked repository/stack.
2. Attacker, controlling `attacker-org`'s webhook secret (as the admin of their own org's GitHub App installation), crafts a `push` (or `status`) webhook payload:
   ```json
   {
     "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" },
     "ref": "refs/heads/main",
     "after": "<attacker-chosen sha>"
   }
   ```
3. Sign the raw body with `attacker-org`'s `webhook_secret` and send `X-Hub-Signature`, `X-Github-Event: push`.
4. `verify_signature` resolves `Shipit.github(organization: "attacker-org")` and validates successfully against the attacker's own secret. `create` then calls `PushHandler.call(params)`, which resolves `Repository.from_github_repo_name("victim-org/victim-repo")` and syncs that stack using the attacker-supplied `after` SHA — despite the request never being signed by `victim-org`'s credentials.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
