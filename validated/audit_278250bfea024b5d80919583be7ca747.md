## Finding: Multisig payload-mismatch check is feature-gated, letting a quorum executor substitute an unapproved payload [1](#0-0) 

### Summary
`validate_multisig_transaction` — the Move function the VM calls in the transaction prologue to admit a multisig-authorized transaction — only verifies that the execution-time payload matches what was approved by the multisig owners *if* the `abort_if_multisig_payload_mismatch_enabled` feature flag is on. When a transaction is proposed via `create_transaction` (full payload stored on-chain rather than a hash), and that feature flag is disabled, the equality check between the payload supplied at execution time and the payload that owners actually voted on is skipped entirely.

### Finding Description
Two proposal styles exist in `multisig_account.move`:
- `create_transaction_with_hash` stores only `payload_hash` (32-byte SHA3-256 digest) on-chain [2](#0-1) .
- `create_transaction` stores the **full payload** on-chain in `transaction.payload` [3](#0-2) .

At execution time, the VM builds `provided_payload` from the *actual* entry function/script the executor put into the outer transaction (attacker/executor controlled) and passes it into `run_multisig_prologue` → `validate_multisig_transaction` [4](#0-3) .

Inside `validate_multisig_transaction`:
1. If `transaction.payload_hash.is_some()` (the hash-based flow), the hash of the provided payload is checked against the stored hash — this path is sound.
2. If instead the full payload was stored on-chain (`create_transaction` flow, `payload_hash` is `None`), the only comparison of provided-vs-approved payload is gated behind the feature flag:
```move
if (features::abort_if_multisig_payload_mismatch_enabled()
    && transaction.payload.is_some()
    && !payload.is_empty()
) {
    let stored_payload = transaction.payload.borrow();
    assert!(payload == *stored_payload, error::invalid_argument(EPAYLOAD_DOES_NOT_MATCH));
}
``` [5](#0-4) 

If `abort_if_multisig_payload_mismatch_enabled` is disabled, this block is skipped unconditionally — regardless of whether `transaction.payload` is populated and non-empty. All the preceding checks (`can_execute`/`can_be_executed`, `num_approvals >= num_signatures_required`, timelock) only bind to the `sequence_number`, not to the *content* of the payload being executed. Consequently, once quorum has approved *a* transaction at that sequence number, any owner who submits the execution can pair that approval with an entirely different entry function payload of their choosing, and `validate_multisig_transaction` will admit it.

The unit test `test_multisig_script_transaction_with_mismatching_payload` in the repo does exercise a mismatch-detection path, but only after explicitly enabling `MULTISIG_SCRIPT`; it does not establish that `abort_if_multisig_payload_mismatch_enabled` is on by default in all configurations [6](#0-5) .

### Impact Explanation
This breaks the "approval validation accepting the wrong approval set" admission invariant: the multisig owners' k-of-n approvals are meant to authorize a *specific* payload, but the check binding execution to that specific payload is optional and feature-gated. If the flag is disabled (e.g., on a fork, testnet, or any deployment where this newer flag hasn't been turned on), an executing owner can run arbitrary approved-looking-but-unapproved entry functions through the multisig account — including fund transfers or privileged calls — using stale quorum approval, which is a critical unauthorized-execution-under-the-wrong-approval-set class of bug.

### Likelihood Explanation
This requires: (a) the multisig transaction was proposed with `create_transaction` (full payload, not hash) — a normal, commonly used proposal path — and (b) `abort_if_multisig_payload_mismatch_enabled` is not active. I was not able to conclusively determine the default/current activation status of this feature flag on Aptos mainnet from the indexed code within this session (the `features.move` / `aptos_features.rs` definitions were located but their exact default-enabled state could not be confirmed before the tool budget ran out) — this is the key open question that determines whether this is currently exploitable in production or is a dormant/legacy code path.

### Recommendation
Make the payload-content check unconditional whenever `transaction.payload.is_some()`, independent of the `abort_if_multisig_payload_mismatch_enabled` feature flag, i.e., always assert `payload == *stored_payload` (and reject empty/mismatched payloads) for the `create_transaction` flow, mirroring the mandatory hash check used in the `create_transaction_with_hash` flow. If the flag was intended purely for staged rollout, it should be resolved/removed for this specific enforcement path rather than left as a permanent bypass switch.

### Proof of Concept
1. Multisig account `M` with owners `A, B` and `num_signatures_required = 2`.
2. Owner `A` calls `create_transaction(M, payload_transfer_1_APT_to_A)`, which auto-approves for `A`.
3. Owner `B` reviews and calls `approve_transaction(M, seq)` believing they are approving `payload_transfer_1_APT_to_A`. Quorum (2/2) is now met for `seq`.
4. If `abort_if_multisig_payload_mismatch_enabled` is off, owner `A` submits the outer transaction with `TransactionExecutableRef::EntryFunction` set to `payload_transfer_all_APT_to_A` (a different payload than what was stored/approved).
5. `validate_multisig_transaction` finds `transaction.payload_hash` is `None` (skips hash check) and the mismatch-check block is skipped because the feature is disabled — approvals for `seq` are still satisfied, timelock passes, and the substituted payload executes, draining more funds than `B` approved.

```rust
pub(crate) fn run_multisig_prologue(
    session: &mut SessionExt<impl AptosMoveResolver>,
    module_storage: &impl ModuleStorage,
    txn_data: &TransactionMetadata,
    executable: TransactionExecutableRef,
    multisig_address: AccountAddress,
    features: &Features,
    log_context: &AdapterLogSchema,
    traversal_context: &mut TraversalContext,
) -> Result<(), VMStatus> {
    let unreachable_error = VMStatus::error(StatusCode::UNREACHABLE, None);
    // Note[Orderless]: Earlier the `provided_payload` was being calculated as bcs::to_bytes(MultisigTransactionPayload::EntryFunction(entry_function)).
    // So, converting the executable to this format.
    let provided_payload = match executable {
        TransactionExecutableRef::EntryFunction(entry_function) => bcs::to_bytes(
            &MultisigTransactionPayload::EntryFunction(entry_function.clone()),
        )
        .map_err(|_| unreachable_error.clone())?,
        TransactionExecutableRef::Empty => {
            if features.is_abort_if_multisig_payload_mismatch_enabled() {
                vec![]
            } else {
                bcs::to_bytes::<Vec<u8>>(&vec![]).map_err(|_| unreachable_error.clone())?
            }
        },
        TransactionExecutableRef::Script(script) => {
            if !features.is_multisig_script_enabled() {
                return Err(VMStatus::error(
                    StatusCode::FEATURE_UNDER_GATING,
                    Some("Multisig script payload is not enabled".to_string()),
                ));
            }
            bcs::to_bytes(&MultisigTransactionPayload::Script(script.clone()))
                .map_err(|_| unreachable_error.clone())?
        },
        TransactionExecutableRef::Encrypted => {
            return Err(VMStatus::error(
                StatusCode::FEATURE_UNDER_GATING,
                Some("Encrypted payload not supported for multisig transactions".to_string()),
            ));
        },
    };

        .enable_feature(FeatureFlag::MULTISIG_SCRIPT as u64)
        .await;

    let multisig_account = context
        .create_multisig_account(owner_account, vec![], 1, 1000)
        .await;
    let multisig_payload = construct_multisig_txn_script_payload(owner_account.address(), 1000);
    context
        .create_multisig_transaction(owner_account, multisig_account, multisig_payload.clone())
        .await;
