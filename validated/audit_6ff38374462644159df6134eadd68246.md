### Title
Webhook signature verification selects the GitHub App by an unverified `repository.owner.login`, decoupled from the `repository.full_name` the handlers act on - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks which `GitHubApp`/`webhook_secret` to validate an incoming webhook against using `repository.owner.login` (or `organization.login`), fields taken straight from the *unverified* JSON body. Once the signature check passes, every event handler (`PushHandler`, `StatusHandler`, `Handler#stacks`, the `pull_request/*` handlers, etc.) resolves the target `Stack`/`Repository` using a *different* field of that same unverified body: `repository.full_name`. Nothing ties the organization whose secret validated the request to the repository the handler subsequently writes to.

### Finding Description
`verify_signature` builds the verifying GitHub App from attacker-supplied data before any cryptographic check occurs: [1](#0-0) 

`repository_owner` is read straight out of the JSON payload: [2](#0-1) 

`GitHubApp#verify_webhook_signature` returns `true` unconditionally when the selected app/org has no `webhook_secret` configured: [3](#0-2) 

This is a first-class, documented deployment mode: Shipit supports one `GitHubApp` per GitHub organization, selected by name, and `webhook_secret` is optional/nilable per-org in every shipped example (`docs/setup.md`, `template.rb`, `test/dummy/config/secrets_double_github_app.yml`). [4](#0-3) 

Meanwhile, every webhook handler resolves the affected `Repository`/`Stack` using `repository.full_name`, a completely independent field of the same unverified body: [5](#0-4) [6](#0-5) [7](#0-6) 

The binding that should hold is: `organization whose secret authenticated the request == organization that owns the repository being written to`. Nothing enforces this. An attacker can set `repository.owner.login` (or `organization.login`) to any org configured in `Shipit.github` that has no `webhook_secret` set (verification then trivially passes for any signature/body), while setting `repository.full_name` to a *different*, secret-protected organization's repository that has real Shipit stacks. The handler dispatch never re-checks that the two match.

### Impact Explanation
This breaks cross-repository/cross-organization write isolation without any credential, in violation of the deployment-trust boundary Shipit is meant to enforce for multi-org installs:
- Forged `push` events (`PushHandler`) call `stack.sync_github(expected_head_sha: <attacker-controlled sha>)` on stacks belonging to an organization the attacker never authenticated against.
- Forged `status`/`check_run`/`check_suite` events (`StatusHandler`, etc.) create fabricated CI statuses on arbitrary commits via `Commit#create_status_from_github!`, which feeds directly into `Status#schedule_continuous_delivery` → `Commit#schedule_continuous_delivery` → `ContinuousDeliveryJob` → `Stack#trigger_continuous_delivery` → `trigger_deploy`, i.e. forging a passing CI status can trigger an **unauthorized deploy** on a stack the attacker has no legitimate GitHub relationship to. [8](#0-7) [9](#0-8) 

This matches the required "Critical" bucket: cross-repository writes / an unauthorized deploy, achieved purely by crafting an HTTP POST body — no `ApiClient` token, GitHub App key, or `webhook_secret` is required.

### Likelihood Explanation
Exploitability depends entirely on operator configuration that the engine itself documents and ships as an example: multi-organization `github:` sections where at least one organization entry has `webhook_secret` left blank (the literal default shown in every template/example file in this repo). Any Shipit install onboarding more than one GitHub org, where even one of them hasn't set a webhook secret, exposes every other org's stacks to forged webhook events. Because the vulnerable code path (`repository_owner` for auth selection vs `repository.full_name` for the write target) is unconditional application logic, not something an integrator can accidentally get right, likelihood is high for any multi-org deployment with an unset secret on any single org.

### Recommendation
Cross-check the authenticated organization against the organization implied by `repository.full_name` (and `organization.login`) before dispatching to handlers — reject the webhook if they don't match the org whose secret verified the signature. Additionally, do not silently treat a missing `webhook_secret` as "verification passed"; require an explicit opt-in (e.g. only used for local/dev installs) or fail closed, and warn loudly at boot when any configured organization lacks a webhook secret in a multi-org config.

### Proof of Concept
Preconditions: Shipit configured with multiple GitHub organizations (as documented in `docs/setup.md`), e.g. `OrgA` (no `webhook_secret` configured) and `OrgB` (has `webhook_secret` set and owns a real Shipit stack, e.g. `OrgB/prod-app`).

1. Attacker sends:
```
POST /webhooks
X-Github-Event: push
X-Hub-Signature: sha1=anything   # irrelevant, org has no secret
Content-Type: application/json

{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha already known/merged upstream>",
  "repository": {
    "owner": {"login": "OrgA"},
    "full_name": "OrgB/prod-app"
  }
}
```
2. `verify_signature` calls `Shipit.github(organization: "OrgA")`; `verify_webhook_signature` returns `true` because `OrgA`'s `webhook_secret` is blank — no signature is actually checked.
3. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("OrgB/prod-app")`, and calls `stack.sync_github(expected_head_sha: ...)` on `OrgB`'s real stack — a write the attacker was never authenticated to perform.
4. The same technique with a forged `status` event (`state: "success"`) on a commit in `OrgB/prod-app` can trigger `ContinuousDeliveryJob`, producing an unauthorized deploy if `OrgB`'s stack has `continuous_deployment` enabled.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
