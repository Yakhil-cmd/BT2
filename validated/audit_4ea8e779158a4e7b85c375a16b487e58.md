### Title
Gas-griefing / returndata-bomb DoS in `BridgeVault.transferETH` causes permanent lock of bridged ETH withdrawals - (File: bridge/evm/contracts/BridgeVault.sol)

### Summary
`BridgeVault.transferETH` performs a raw `.call{value: amount}("")` to the withdrawal recipient and `require`s success, exactly the anti-pattern described in the external report (checking success of a low-level call whose returned data is copied into memory even though it is never used).

### Finding Description
In `BridgeVault.sol`, `transferETH` unwraps WETH and forwards ETH to the recipient with:
```solidity
(bool success,) = recipientAddress.call{value: amount}("");
require(success, "ETH transfer failed");
``` [2](#0-1) 

Solidity's low-level `.call` always copies the callee's return data into memory before the `(bool success,)` tuple is populated, regardless of whether the caller uses that data. If `recipientAddress` is a contract with a `receive`/`fallback` function that returns (or reverts with) an arbitrarily large data blob, forwarding that blob back to the caller consumes memory-expansion gas quadratically, which can exhaust the gas supplied to the call and make it revert even though it did nothing malicious with the funds themselves — this is the same anti-pattern flagged in the external "Token.sol" report, and the fix (using `assembly` to ignore returndata, e.g. via a fixed-gas-stipend transfer or explicit `returndatacopy(0,0,0)`) is directly applicable here.

`transferETH` is invoked from `SuiBridge._transferTokensFromVault`, which in turn is called from `transferBridgedTokensWithSignatures` — the entry point used to release funds validated by committee signatures for a message coming from Sui: [3](#0-2) 

Critically, `isTransferProcessed[message.nonce]` is only set to `true` *after* `_transferTokensFromVault` returns successfully: [1](#0-0) 

The identical pattern is duplicated in `SuiBridgeV2.sol`: [4](#0-3) [5](#0-4) 

### Impact Explanation
An unprivileged Sui-side depositor controls the `recipientAddress` field of a bridge-out message (it is user-supplied recipient data forwarded from Sui to Ethereum). By setting the recipient to an attacker-deployed contract whose `receive()`/`fallback()` returns (or reverts with) a large returndata blob, the attacker guarantees that any call to `transferBridgedTokensWithSignatures` for that message will always run out of gas inside `BridgeVault.transferETH`'s low-level call, causing the whole transaction to revert before `isTransferProcessed` is ever set. Because the nonce is never marked processed, and the failure is deterministic (any gas amount a caller supplies just shifts where the gas exhaustion happens, since the memory-expansion cost scales with the returned data size which the attacker controls), the ETH allocated to that withdrawal becomes permanently stuck in `BridgeVault` — a real fund-lock condition, not merely a transient gas-only nuisance, since there is no alternate code path to redirect or reclaim those specific committee-signed funds once the message has been generated on the Sui side.

### Likelihood Explanation
This requires only that an unprivileged attacker deposit through the normal `bridgeETH`/`bridgeETHV2` flow on the Sui side while designating a malicious contract address as the Ethereum recipient — no privileged access, malicious validator, or governance action is needed. Given how cheap it is to deploy a fallback contract that returns a large blob, and that this can be done by any Sui bridge user targeting their own future withdrawal (or, if the recipient field is otherwise attacker-influenceable elsewhere in the payload construction, potentially targeting a third party's withdrawal), the trigger conditions are straightforward.

### Recommendation
Avoid forwarding return data from low-level ETH transfers. Use an assembly-based call that ignores returndata (e.g., `call(gas(), recipient, amount, 0, 0, 0, 0)` in inline assembly) instead of the high-level `.call{value: amount}("")` pattern in `BridgeVault.transferETH`, mirroring the recommendation in the external report. Alternatively, cap the gas stipend forwarded to the call (e.g., using `.call{value: amount, gas: 2300}`) or bound/discard returndata explicitly, and apply the same fix consistently to both `SuiBridge.sol`/`BridgeVault.sol` and `SuiBridgeV2.sol` paths.

### Proof of Concept
1. Attacker deploys `Evil` contract on Ethereum with:
```solidity
receive() external payable {
    assembly { revert(0, 1000000) } // or return(0, 1000000) with huge memory expansion
}
```
2. Attacker calls `bridgeETH`/`bridgeETHV2` on the Sui side (or via the corresponding Move bridge deposit call) specifying `Evil`'s address as the Ethereum-side recipient, and the amount to withdraw.
3. Once the Sui committee signs the corresponding `TOKEN_TRANSFER` message, any relayer calling `SuiBridge.transferBridgedTokensWithSignatures` with valid signatures will trigger `BridgeVault.transferETH`, which does `recipientAddress.call{value: amount}("")` against `Evil`.
4. `Evil`'s fallback forces a large returndata copy, exhausting the gas forwarded in the call; `success` is `false`, `require(success, "ETH transfer failed")` reverts the entire `transferBridgedTokensWithSignatures` transaction.
5. Because the revert happens before `isTransferProcessed[message.nonce] = true` executes, every subsequent attempt to claim this message with the same signatures fails identically — the ETH remains permanently locked in `BridgeVault`.
