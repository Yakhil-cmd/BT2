## Title
Permanent ETH fund lock via unguarded `.call{value:}` push transfer in bridge withdrawal path — (File: `bridge/evm/contracts/BridgeVault.sol`, `bridge/evm/contracts/SuiBridge.sol`)

### Summary
The Sui↔EVM bridge withdraws ETH to an attacker/user-controlled `recipientAddress` using a direct low-level `.call{value:}` in `BridgeVault.transferETH()`, invoked from `SuiBridge.transferBridgedTokensWithSignatures()`. The processed-flag `isTransferProcessed[nonce]` is only set to `true` *after* the ETH push succeeds. If the recipient address is a contract that reverts on receiving plain ETH (no `receive`/non-payable fallback, or deliberately reverting logic), the whole withdrawal transaction reverts and the flag is never set — this is the exact "ETH transfer griefing" root cause from the external report, applied to a bridge withdrawal instead of an escrow refund.

### Finding Description
`BridgeVault.transferETH()` does:
```solidity
(bool success,) = recipientAddress.call{value: amount}("");
require(success, "ETH transfer failed");
``` [1](#0-0) 

This is invoked from `SuiBridge._transferTokensFromVault()`/`SuiBridgeV2._transferTokensFromVault()` when `tokenID == BridgeUtils.ETH`: [2](#0-1) 

Crucially, in `transferBridgedTokensWithSignatures()`, `isTransferProcessed[message.nonce]` is only marked `true` **after** `_transferTokensFromVault` returns successfully:
```solidity
_transferTokensFromVault(
    message.chainID,
    tokenTransferPayload.tokenID,
    tokenTransferPayload.recipientAddress,
    erc20AdjustedAmount
);

// mark message as processed
isTransferProcessed[message.nonce] = true;
``` [3](#0-2) 

The `recipientAddress` embedded in the committee-signed `message` is fixed at the time the transfer was initiated on the Sui side and cannot be altered afterwards — there is no owner/admin override, no alternate "claim" or "pull" withdrawal function, and no way to redirect funds to a different address once the message has been signed by the committee. If `recipientAddress` is any contract without a working `receive()`/payable fallback (e.g., a plain non-payable contract, a multisig without receive, or one that intentionally reverts), every call to `transferBridgedTokensWithSignatures` for that nonce will permanently revert, and `isTransferProcessed[nonce]` can never become `true`. The ETH remains stuck in `BridgeVault` forever with no recovery path, mirroring the external report's core flaw: push-based ETH transfer combined with a revert-blocks-everything design, but here escalated to bridge-scale permanent fund lock instead of a two-party griefing standoff.

### Impact Explanation
This matches the allowed **High** impact category "permanent fund lock ... reachable from public input." Any ordinary bridge user (unprivileged, no validator/governance/admin role needed) who specifies (or is sent funds to) a non-ETH-receiving contract address as `recipientAddress` when bridging ETH from Sui to Ethereum causes that specific withdrawal's ETH to be irrecoverably locked in `BridgeVault`, since:
- the processed flag is never flipped, so the nonce can be retried indefinitely but will always fail identically,
- there is no claim/pull-based fallback logic as recommended in the source report,
- no privileged function exists to redirect or manually release the stuck ETH to a different address.

### Likelihood Explanation
Likelihood is realistic and does not require any privileged actor: any contract address without a working ETH receiver (a common, non-malicious oversight — e.g., a Safe/multisig without a `receive()` function prior to certain versions, or any generic non-payable contract) triggers this permanently once chosen as the bridge recipient. It can also be deliberately triggered by a user targeting their own transfer or a third-party recipient contract to lock funds as a griefing/DoS vector, exactly as described as a "not intentional" as well as intentional revert scenario in the source report.

### Recommendation
Adopt a pull/claim-based withdrawal pattern for ETH transfers in `BridgeVault`/`SuiBridge`, as the original report recommends: on push failure, credit `recipientAddress` with a pending-withdrawal balance in storage (mark `isTransferProcessed[nonce] = true` regardless of push success) and expose a separate `claimETH()`/`withdraw()` function that recipients (or anyone on their behalf) can call later to pull the funds via a safe, retryable transfer. This removes the dependency on the recipient's ability/willingness to accept a synchronous ETH push and eliminates the permanent-lock condition.

### Proof of Concept
1. Deploy/identify a contract `Bad` on Ethereum with no `receive()`/payable `fallback()` (or one that always reverts).
2. Initiate a Sui→Ethereum ETH bridge transfer specifying `recipientAddress = address(Bad)`.
3. Once the Sui validator committee signs the corresponding `TOKEN_TRANSFER` message (nonce `N`), call `SuiBridge.transferBridgedTokensWithSignatures(signatures, message)`.
4. `BridgeVault.transferETH` executes `Bad.call{value: amount}("")`, which reverts because `Bad` has no payable receiver; the `require(success, ...)` bubbles the revert up through `_transferTokensFromVault` and the outer function.
5. `isTransferProcessed[N]` remains `false` forever; every subsequent call with the same signed message reverts identically. The bridged ETH is permanently stuck in `BridgeVault` with no function available to redirect or reclaim it.
