### Title
Zero-Share DoS/Fund-Loss in `uniswap_like_market_maker.oscript` Sample AA via Balance Pre-Loading Before First `mm_asset_outstanding` Update - (File: test/samples/uniswap_like_market_maker.oscript)

### Summary
The bundled Uniswap-like market-maker AA template computes newly-issued pool shares as `round($investor_share_of_prev_balance * var['mm_asset_outstanding'])`. An attacker can pre-load the AA's `base` and `$asset` balances by sending a payment that matches none of the AA's `if` cases (so no state var is updated), while still increasing `balance[base]` and `balance[$asset]`. This causes the "initial deposit" detection (`$asset_balance == 0 OR $bytes_balance == 0`) inside the `invest in MM` case to be bypassed for the real first investor, while `var['mm_asset_outstanding']` is still `0`, forcing `$issue_amount` to round to `0` for that investor's real deposit.

### Finding Description
In the `invest in MM` case: [1](#0-0) 

the special-cased first deposit is detected only by checking whether the raw token balances of the AA (`$asset_balance`, `$bytes_balance`, both computed by subtracting the *current* trigger's outputs from `balance[...]`) are zero — not by checking the internal accounting variable `var['mm_asset_outstanding']`.

Because Obyte AAs silently accept payments that don't match any `if` case in their `cases` list (the funds are absorbed into the AA's `balance[...]` without executing any `messages`/`state` block), an attacker can send a single payment containing:
- some `$asset` tokens (`trigger.output[[asset=$asset]] > 0`), and
- bytes below the `1e5` threshold used everywhere in the template,

This payment fails the condition of every case (`invest`, `exchange bytes to asset`, `exchange asset to bytes` — the latter requires `var['mm_asset_outstanding']` to be truthy, which is still `0`), so the AA takes no action but still keeps the received `base` and `$asset` balances. [2](#0-1) 

When the real first investor subsequently sends a valid `invest` trigger, `$asset_balance` and `$bytes_balance` (computed excluding the investor's own outputs) are now both non-zero due to the attacker's earlier stealth deposit, so the "initial deposit" branch (`return` with `$issue_amount = balance[base]`) is skipped. The code falls through to:

```
$investor_share_of_prev_balance = trigger.output[[asset=base]] / $bytes_balance;
$issue_amount = round($investor_share_of_prev_balance * var['mm_asset_outstanding']);
```

Since `var['mm_asset_outstanding']` is still `0` (never incremented by the attacker's non-matching payment), `$issue_amount` rounds to `0` regardless of the investor's contributed amount, exactly mirroring the reported `Pool.tokenToShares()` bug where a pre-loaded balance combined with a zero internal supply counter yields zero minted shares while the deposit is still accepted.

### Impact Explanation
The legitimate investor's `base` and `$asset` tokens are absorbed into the AA balance and `payment` message still sends `0` of `$mm_asset` — the investor receives no shares for real, non-recoverable funds locked in the AA (fund loss). Because `var['mm_asset_outstanding']` remains `0` after this event too, every subsequent investor hits the same zero-share outcome, permanently disabling ("DoS-ing") normal accounting for the pool instance and freezing all deposited funds with no shares minted to reclaim them via the `divest` case, which is gated on `trigger.output[[asset=$mm_asset]]` (nobody can ever hold `$mm_asset` to divest). This is a fund-loss/freezing condition reachable by any unprivileged AA trigger sender.

### Likelihood Explanation
Any address can trigger this by sending a single crafted payment to a freshly-deployed instance of this AA before (or racing) the first legitimate `invest` call — no special privileges, front-running of a mempool, or valuable stake are required, only ordinary knowledge of the AA's deployment address, matching the "DoS any pool before the first deposit" pattern from the source report.

### Recommendation
Detect "first deposit" state using the internal accounting variable rather than raw balances, e.g. treat the pool as uninitialized when `!var['mm_asset_outstanding']` (or an explicit `var['initialized']` flag) rather than `$asset_balance == 0 OR $bytes_balance == 0`. Additionally, either bounce any payment that doesn't match a recognized case (so stray funds cannot silently inflate balance[...]), or explicitly reconcile/ignore untracked balance deltas when computing ratios and share issuance.

### Proof of Concept
1. Deploy `uniswap_like_market_maker.oscript` AA and define its asset (`trigger.data.define`).
2. Attacker sends a unit paying the AA: `trigger.output[[asset=base]] = 1000` (below `1e5`) and `trigger.output[[asset=$asset]] = 1`. No case's `if` matches (`invest` needs `base > 1e5`; `exchange asset to bytes` needs truthy `var['mm_asset_outstanding']`), so the AA takes no action, but `balance[base]` and `balance[$asset]` are now `1000` and `1` respectively.
3. Victim sends a legitimate `invest` trigger with `base = 1e6`, `asset = X` tokens.
4. Inside `invest in MM`: `$asset_balance = 1` (nonzero), `$bytes_balance = 1000` (nonzero) → the `if ($asset_balance == 0 OR $bytes_balance == 0)` initial-deposit branch is skipped.
5. `$investor_share_of_prev_balance = 1e6 / 1000 = 1000`; `$issue_amount = round(1000 * var['mm_asset_outstanding'])` where `var['mm_asset_outstanding'] = 0` → `$issue_amount = 0`.
6. Victim's `base`/`asset` payment is accepted by the AA, but the `payment` message sends `0` of `$mm_asset` to them — funds are absorbed with no shares issued, and `mm_asset_outstanding` stays `0` for all future investors.
