### Title
Unfiltered stack/PR-label and shipit.yml `machine.environment` merge into deploy-process env allows `DYLD_INSERT_LIBRARIES` injection - (File: app/models/shipit/review_stack.rb, lib/shipit/task_commands.rb, lib/shipit/command.rb)

### Summary
`ReviewStack#env` merges every PR label (uppercased) directly into the stack's environment hash with no whitelist, and `DeploySpec#machine_env` (parsed from the fork's own `shipit.yml`, checked out on the PR's `head.ref`) is merged unfiltered as well. Both paths flow straight through `TaskCommands#env` → `Command#env`/`unbundled_env` → `PTY.spawn`, so a fork PR author can set `DYLD_INSERT_LIBRARIES` (or `LD_PRELOAD`, `RUBYOPT`, etc.) in either a PR label or their fork's `shipit.yml` and have it preloaded into the deploy process.

### Finding Description
The broken binding: the invariant should be `env(spawned deploy process) ⊆ EnvironmentVariables#permit(whitelisted_variable_definitions)` for every attacker-influenced source. In fact `env(spawned process) ⊇ {label_names} ∪ machine_env_keys`, unfiltered.

- `Repository#provisioning_behavior_prevent_with_label?` combined with `respond_to_label_change?`/`archive?`/`unarchive?` in `LabeledHandler`/`OpenedHandler` means a fork PR is auto-provisioned into a `ReviewStack` by default (label absent case), confirmed by tests such as `test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb:159-172` ("create stacks for repos what prevent_with_label when label is absent"). No maintainer action is required. [1](#0-0) 
- The provisioned `ReviewStack`'s branch is the fork's `head.ref` [2](#0-1) , so `DeploySpec::FileSystem` loads `shipit.yml` from attacker-controlled fork content, including `machine.environment`, exposed via `DeploySpec#machine_env`, with zero key filtering: [3](#0-2) 
- `ReviewStack#env` unconditionally merges every PR label name (uppercased) as an env var set to `"true"`, again with no whitelist: [4](#0-3) 
- `TaskCommands#env` merges `@stack.env` and `deploy_spec.machine_env` directly into the process environment hash, alongside `Shipit.env`, task/deploy metadata, and `@task.env` — none of these merges pass through `EnvironmentVariables#permit`: [5](#0-4) 
- `EnvironmentVariables#permit` (the only sanitizer in the codebase) is only invoked for user-supplied API params (`DeploySpec#filter_deploy_envs`, `#filter_rollback_envs`, `TaskDefinition#filter_envs`), never for `stack.env` or `machine_env`: [6](#0-5) [7](#0-6) 
- `Command#initialize`/`#unbundled_env` take that hash and stringify/merge it on top of `BASE_ENV` and `PATH`, with no denylist for dangerous dynamic-linker variables, then hand it to `PTY.spawn`: [8](#0-7) [9](#0-8) 

Exploit flow: attacker opens a PR from their fork against a repository configured with `provisioning_behavior=prevent_with_label` and `review_stacks_enabled=true`. Either (a) they add a label literally named `DYLD_INSERT_LIBRARIES` to their own PR (rules grant "label their own PR" as an unprivileged capability), or (b) they commit a `shipit.yml` with `machine: {environment: {DYLD_INSERT_LIBRARIES: "/path/to/evil.dylib"}}` to their fork branch. The webhook auto-provisions a `ReviewStack` (label absent by default under `prevent_with_label`), Shipit checks out the fork's branch, and any subsequent deploy/task command (`cap ... deploy`, dependency install, etc.) is spawned via `PTY.spawn` carrying `DYLD_INSERT_LIBRARIES` unfiltered.

Existing guards do not stop this: `verify_signature`/`GitHubApp#verify_webhook_signature` only validate the webhook came from GitHub, not that its label/branch content is safe; `EnvironmentVariables#permit` is never applied to `stack.env`/`machine_env`; and `Stack`/`Repository` model validations constrain names like `environment`/`owner`, not env content.

### Impact Explanation
Whichever shell/build step the deploy spec invokes (dependency install, deploy command, rollback, or a task) runs with `DYLD_INSERT_LIBRARIES` set. On a macOS deploy host, dynamic-linker preloading of an attacker-supplied dylib into that spawned process constitutes arbitrary code execution on the Shipit deploy host under whatever privileges the deploy process runs as — this is the same host that also has `GITHUB_TOKEN`/deploy credentials in its base environment (merged via `Command::BASE_ENV`/`Bundler.unbundled_env`), so the blast radius includes exfiltration of deploy secrets. This is repeatable per PR/per repository configured for review stacks with `prevent_with_label`, matching the Critical RCE class.

### Likelihood Explanation
Preconditions: target repository has `review_stacks_enabled=true` and `provisioning_behavior=prevent_with_label` (or `allow_all`, where the PR needs no label at all and injection is only via `shipit.yml`). Attacker cost is minimal — open a PR from a fork, optionally add one label, and/or commit a `shipit.yml` with the offending `machine.environment` key. No secrets, no maintainer approval, and no special permissions beyond what any external contributor has are required. This is fully repeatable and requires only standard GitHub fork/PR mechanics plus (for the label vector) the ability to add a label to one's own PR, which the threat model grants.

### Recommendation
Route `Stack#env`/`ReviewStack#env` and `DeploySpec#machine_env` through an explicit deny/allow-list before merging into `TaskCommands#env` (e.g., reject or drop dynamic-linker/interpreter-hijacking variables such as `DYLD_INSERT_LIBRARIES`, `DYLD_LIBRARY_PATH`, `LD_PRELOAD`, `LD_LIBRARY_PATH`, `RUBYOPT`, `PYTHONSTARTUP`, `NODE_OPTIONS`, `PATH`, `BUNDLE_*`, etc.), or require these merges to go through `EnvironmentVariables#permit` against an explicit safe-variable list defined by the *target* repo (not the fork), never derived from PR labels or from `shipit.yml` on an unreviewed fork branch/head-ref checkout.

### Proof of Concept
minitest (conceptual, add under a non-`test/` sanctioned area or reference existing test patterns for review — described here per rules for reproducibility):
1. Provision a `ReviewStack` fixture with `provisioning_behavior: prevent_with_label`, `review_stacks_enabled: true`, and an associated `PullRequest` whose `labels` include `"DYLD_INSERT_LIBRARIES"`.
2. Assert `review_stack.env["DYLD_INSERT_LIBRARIES"] == "true"` (binding broken: `stack.env` should equal only `EnvironmentVariables.with(labels).permit(whitelisted_definitions)`, but instead equals the raw label set).
3. Build `TaskCommands.new(deploy).env` for a deploy on that stack and assert it includes `"DYLD_INSERT_LIBRARIES" => "true"`.
4. Construct `Command.new('true', env: commands.env, chdir: '.')` and assert `command.unbundled_env["DYLD_INSERT_LIBRARIES"] == "true"`, proving the value reaches the `PTY.spawn` argument unfiltered.
5. Repeat with a stubbed `deploy_spec.machine_env` returning `{"DYLD_INSERT_LIBRARIES" => "/tmp/evil.dylib"}` and assert the same propagation through `TaskCommands#env` → `Command#unbundled_env`.
