### Title
SolvBTC collateral is priced at a hard floor of 1.0×BTC via a fundamental NAV factor, so a depeg of SolvBTC below BTC leaves collateral permanently overvalued - (File: contracts/price-aggregator/src/oracle via `Scaled` source bounds)

### Summary
The price-aggregator prices SolvBTC tokens (`CAUP7NFABXE5TJRL3FKTPMWRLC7IAXYDCTHQRFSCLR5TMGKHOOQO772J`, `CBIJBDNZNF4X35BJ4FFZWCDBSCKOP5NB4PLG4SNENRMLAPYG4P5FM6VN`) using a `Scaled` source whose factor feed is `SolvBTC_FUNDAMENTAL` quoted against the `Ref("BTC")` BTC/USD composite, with `min_factor_wad = 1e18` — i.e. the configured oracle cannot ever value SolvBTC below 1.0 BTC. The second source, `SolvBTC_FUNDAMENTAL/USD`, is the same fundamental NAV in USD, so both legs agree with each other by construction and neither reflects the actual market price of SolvBTC. This is the exact class of the reported issue: a wrapped/receipt asset priced from the underlying's feed rather than the asset's own market price.

### Finding Description [1](#0-0) 

The deployed oracle for SolvBTC is:

- Source 1: `Scaled { factor: RedStone("SolvBTC_FUNDAMENTAL"), quote: Ref("BTC"), min_factor_wad: 1e18, max_factor_wad: 1.05e18 }` → price = factor × BTC price, clamped to [1.0, 1.05] × BTC.
- Source 2: `Feed { RedStone("SolvBTC_FUNDAMENTAL/USD") }` → the same fundamental NAV directly in USD.
- Tolerance ±5–10%, `independence: AllowShared` on the same RedStone contract, sanity band $40k–$120k.

Both sources derive from SolvBTC's *fundamental* (NAV/backing) value published by the same provider. There is no market-price leg (no SolvBTC/XLM or SolvBTC/USDC Aquarius spot or TWAP, no SolvBTC trade feed). If the SolvBTC issuer/bridge is compromised and the token trades at a discount on Stellar DEX/CEX venues, the fundamental feeds will keep reporting NAV ≈ 1 BTC for as long as the provider has not marked it down — precisely the failure mode described in the referenced WBTC/BTC report. The `min_factor_wad = 1e18` floor additionally guarantees that even if the factor feed reports a sub-1 ratio, the source is rejected rather than pricing the depeg, while the USD feed continues to return the stale NAV and still passes the sanity band.

An unprivileged attacker reaches this through `controller.borrow`: supply depegged SolvBTC bought cheaply on Aquarius/Soroswap, have it valued at ~BTC price, and borrow USDC/XLM/ETH against it. Because `borrow` uses Context-cached strict prices from the aggregator, the overvalued collateral directly inflates borrowing capacity; `clean_bad_debt`/`liquidate` cannot recover value because the collateral is actually worth a fraction of the priced amount.

### Impact Explanation
If SolvBTC depegs (issuer insolvency, bridge hack, redemption halt), every unit supplied as collateral is credited at ≥ BTC price while its real liquidation value is far lower. Attackers can mint bad loans up to the market's LTV, and existing SolvBTC-collateralized positions become unrecoverable; liquidation seizes near-worthless tokens. The residual deficit is written down via the supply index / `recapitalize`, i.e. protocol insolvency borne by suppliers of the borrowed assets.

### Likelihood Explanation
Requires a SolvBTC backing/peg failure — an external, non-certain event, but exactly the tail risk this oracle shape fails to capture (see the analogous Blueberry/JOJO findings, and real-world wrapped-asset depegs). When it occurs, exploitation is permissionless: any address can buy the depegged token cheaply and `supply` + `borrow` in two calls. No privileged action, oracle manipulation, or timing race is needed; the oracle mispricing is structural.

### Recommendation
- Add a market-price leg for SolvBTC: an Aquarius LP/spot or TWAP source (or a market-nature feed) in addition to the fundamental feeds, and set `independence: RequireDisjoint` so it cannot share the same provider as the NAV legs.
- Drop `min_factor_wad` below 1.0 (or remove the scaled NAV leg) so a reported sub-peg ratio is reflected rather than rejected.
- Optionally gate `borrow` when the market leg deviates below the fundamental leg beyond a threshold, matching the dual-oracle recommendation in the source report.

### Proof of Concept
1. Assume SolvBTC depegs to 0.5 BTC on Stellar venues while `SolvBTC_FUNDAMENTAL` and `SolvBTC_FUNDAMENTAL/USD` still report NAV ≈ 1 BTC (provider has not yet marked down backing).
2. Attacker buys 1.0 SolvBTC on Aquarius for ~0.5 BTC-equivalent of USDC.
3. Attacker calls `controller.supply(solvbtc, 1e8)` — aggregator resolves the `Scaled` source (factor within [1.0, 1.05], passing bounds) agreeing with the `SolvBTC_FUNDAMENTAL/USD` feed within tolerance → collateral valued at ~$100k.
4. Attacker calls `controller.borrow(usdc, <LTV-max>)` and withdraws ~$80k+ of real USDC.
5. Liquidators cannot profitably seize the SolvBTC (worth ~$50k); debt is written down via `clean_bad_debt`/index write-down, socializing the loss to suppliers.

Uncertainty note: the exploitability depends on `SolvBTC_FUNDAMENTAL` feeds continuing to report NAV during a depeg — I could not inspect RedStone's feed semantics from this repo, so whether the fundamental feed tracks backing NAV vs. a market price is inferred from its `Fundamental` nature and the `[1.0, 1.05]` factor bounds. If those feeds are actually market-priced, the issue reduces to feed semantics and the analog does not hold.
