### Title
Unauthenticated Remote DoS via Missing Key Validation in Own-Hub Device Message Delivery - ([File: network.js])

### Summary
When an ocore node acts as its own hub (`my_device_address === objDeviceMessage.to` in the `hub/deliver` handler), the code skips the check that normally verifies `encrypted_package.dh.recipient_ephemeral_pubkey` matches one of the recipient's known keys. The forged message is handed directly to `device.js`'s `decryptPackage()`, which — on encountering an unrecognized key — schedules an unconditional `throw Error(...)` inside a `setTimeout`, crashing the process. This is reachable by any unprivileged peer that can open a WebSocket connection to the node and send a single `hub/deliver` command; no pairing/correspondent relationship is required, mirroring the wire-ios CVE-2026-35049 pattern where a crafted encrypted message with a validation gap crashes the client on receipt.

### Finding Description
In `network.js`, the `hub/deliver` request handler validates a device message's structure and signature, then branches: [1](#0-0) 

```
var bToMe = (my_device_address && my_device_address === objDeviceMessage.to);
if (!conf.bServeAsHub && !bToMe)
    return sendErrorResponse(ws, tag, "I'm not a hub");
```

If the message is addressed to the node's own device address (`bToMe`), the handler immediately forwards it for processing without the recipient-key check that is otherwise mandatory in the non-`bToMe` branch: [2](#0-1) 

Notice the `keys.includes(objDeviceMessage.encrypted_package.dh.recipient_ephemeral_pubkey)` check exists only in the `else` (non-`bToMe`) branch. Any attacker-controlled `dh.recipient_ephemeral_pubkey` value therefore reaches `device.js`'s `handleJustsaying('hub/message', ...)` → `decryptPackage()` unchecked: [3](#0-2) 

```
function decryptPackage(objEncryptedPackage, depth = 0){
    ...
    if (objEncryptedPackage.dh.recipient_ephemeral_pubkey === objMyTempDeviceKey.pub_b64){ ... }
    else if (objMyPrevTempDeviceKey && ... === objMyPrevTempDeviceKey.pub_b64){ ... }
    else if (... === objMyPermanentDeviceKey.pub_b64){ ... }
    else{
        console.log("message encrypted to unknown key");
        setTimeout(function(){
            throw Error("message encrypted to unknown key, device "+my_device_address+...);
        }, 100);
        return null;
    }
```

Because the attacker only needs *any* string as `dh.recipient_ephemeral_pubkey` (it merely needs to be a `typeof === 'string'` to pass the earlier type checks in `decryptPackage`, `device.js:408`), the "unknown key" branch is trivially reached, and the deferred `throw` fires 100 ms later as an uncaught exception in the event loop, terminating the Node.js process. Moreover, this whole flow in `device.js`'s `handleJustsaying` runs the decryption *before* the "is this a known correspondent" check, so no pairing relationship with the victim is required: [4](#0-3) 

Also note in `device.js` the signature check on the outer envelope only verifies that `objDeviceMessage.pubkey` signed the message — the attacker can use a freshly-generated throwaway keypair to sign their own forged message, since signature ownership is not tied to the recipient's identity: [5](#0-4) 

### Impact Explanation
Any peer that can establish a WebSocket connection to an ocore node that hosts its own device messaging endpoint (`my_device_address` set and reachable, e.g. bots, exchanges, or full nodes that are always-online and act as their own hub) can crash that process remotely with a single crafted `hub/deliver` request, with no authentication, pairing, or prior correspondence. Because the crash is triggered on every delivery of such a forged message, an attacker can repeatedly reconnect and resend the payload to keep the node down, producing a persistent denial of service against that node's ability to process units, relay, or serve as a witness/hub — directly analogous to the "network unable to confirm new units" impact category if the affected node is a witness or heavily relied-upon service node.

### Likelihood Explanation
Likelihood is high: the only prerequisite is knowing the target's public device address (routinely published for pairing links, bots, or hub services) and being able to open a network connection to it — both trivially available to any unprivileged network participant. No cryptographic secrets, private keys, or insider access are needed, and the exploit is a single crafted JSON message.

### Recommendation
Apply the same recipient-key validation used in the `!bToMe` branch (`keys.includes(objDeviceMessage.encrypted_package.dh.recipient_ephemeral_pubkey)`) to the `bToMe` branch in `network.js` before forwarding to `decryptPackage`. Additionally, in `device.js`'s `decryptPackage`, replace the delayed `setTimeout(() => { throw ... })` self-destruct pattern for the "unknown key" case with a graceful error return (as already done for other decrypt failures), since a remotely triggerable unconditional process crash should never be reachable from untrusted network input.

### Proof of Concept
1. Attacker generates a throwaway ECDSA keypair and computes `pubkey`/`signature` for a forged `objDeviceMessage` with:
   - `to`: victim's known device address (`my_device_address`, matching the target node itself)
   - `encrypted_package.dh.recipient_ephemeral_pubkey`: any well-formed but bogus base64 string (not matching any of the victim's real temp/prev-temp/permanent pubkeys)
   - `encrypted_package.dh.sender_ephemeral_pubkey`, `iv`, `authtag`, `encrypted_message`: any valid base64 strings satisfying the `typeof === 'string'` checks
2. Attacker connects via WebSocket to the victim node (which is running with device messaging enabled and is its own hub) and sends a `hub/deliver` request with this payload.
3. `network.js`'s handler detects `bToMe === true`, skips the recipient-key check, and emits `message_from_hub`.
4. `device.js` processes the message, calls `decryptPackage`, hits the `else` branch ("message encrypted to unknown key"), and schedules the `throw` via `setTimeout`.
5. 100 ms later, the uncaught exception crashes the victim's Node.js process.

*Note: it was not fully verified whether a global `process.on('uncaughtException', ...)` handler elsewhere in the codebase (two matches were found in `network.js` but not inspected in detail) intercepts and suppresses this crash instead of terminating the process; this should be confirmed/tested against the running deployment to establish the exact crash behavior versus a caught, logged error.*
