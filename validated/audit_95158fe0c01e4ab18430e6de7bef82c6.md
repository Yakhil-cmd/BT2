### Title
Webhook signature is verified against the organization named in `repository.owner.login`, but the repository actually acted upon is taken from the independent `repository.full_name` field — allowing cross-organization forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks *which* GitHub App/organization secret to verify the `X-Hub-Signature` against using a field read straight out of the attacker-supplied JSON body, while the webhook *handlers* that actually mutate state (`PushHandler`, and `Handler#stacks` in general) resolve the target repository from a **different, independently-controlled** field of that same body. Nothing binds the two fields together, so a payload can be crafted to authenticate as one organization while acting on a repository belonging to a completely different organization.

### Finding Description
`verify_signature` computes: [1](#0-0) 

and resolves the organization used to select the app/secret via: [2](#0-1) 

`repository_owner` is `params.dig('repository', 'owner', 'login')` — a value taken directly from the unauthenticated JSON body before the signature is checked. `Shipit.github(organization: repository_owner)` returns a `GitHubApp` whose `webhook_secret` may be **organization-specific** (Shipit explicitly supports multiple, independently-configured GitHub Apps, one per organization, each with its own `webhook_secret`, as seen in the dummy multi-app fixture `test/dummy/config/secrets_double_github_app.yml` and the `GitHubApp#verify_webhook_signature` implementation): [3](#0-2) .

Once `verified` is true, the controller dispatches the *entire, unmodified* payload to every registered handler: [4](#0-3) 

The handlers, however, do **not** use `repository.owner.login` (the field that determined which secret validated the signature). They resolve the target repository/stacks from `repository.full_name`, a sibling field in the same attacker-controlled body: [5](#0-4) 

`PushHandler` then uses that repository's stacks to force-sync an attacker-chosen commit SHA: [6](#0-5) 

Because `owner.login` and `full_name` are two unrelated JSON keys inside the same request body, an attacker only needs to know the `webhook_secret` for **any one** organization configured in the Shipit instance (e.g. their own legitimate organization, for which they were given the secret when wiring up the GitHub webhook) to sign a payload of the form:

```json
{
  "repository": {
    "owner": { "login": "OrgTheyControl" },
    "full_name": "VictimOrg/victim-repo"
  },
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>"
}
```

`verify_signature` will select `OrgTheyControl`'s secret, the HMAC will check out, and the request will be treated as authentic. The `PushHandler` will then look up `VictimOrg/victim-repo`'s stacks and call `stack.sync_github(expected_head_sha: params.after)` — an organization the attacker never had any credential or access to.

This is exactly the deployment-trust binding break called out in scope: **the organization that authenticated the request ≠ the repository whose state is written**.

### Impact Explanation
An attacker who only controls (or has been issued) the webhook secret for one organization/repository on a shared Shipit instance can forge webhook events that are processed as if they came from GitHub for a **different** organization's repository. Via `PushHandler`, this lets them push an arbitrary/rolled-back commit SHA as the new "head" for a victim stack's branch (`stack.sync_github(expected_head_sha: ...)`), which can lead to unauthorized deploy candidates being recorded and subsequently shipped for repositories the attacker has no legitimate access to — a cross-repository write / unauthorized-deploy-adjacent primitive, matching the "cross-repository writes" / "unauthorized deploy" impact category.

### Likelihood Explanation
Exploitation requires only knowledge of a valid `webhook_secret` for *some* organization hosted on the shared Shipit instance (something any organization admin configuring their own GitHub webhook legitimately receives) plus the ability to send an HTTP POST to the public `/github/webhooks` endpoint — no Shipit session, `ApiClient` token, or GitHub repository write access to the victim org is needed. This is a realistic multi-tenant scenario since Shipit explicitly supports multiple GitHub Apps/organizations per instance.

### Recommendation
Bind signature verification to the same repository identity that handlers act upon: verify against the secret matching `repository.full_name`'s owner (or better, verify against every configured app whose repo scope includes the target `full_name`, not an org name pulled from a different, independently-forgeable field), and reject the webhook if the two fields disagree.

### Proof of Concept
1. Attacker legitimately configures Shipit's GitHub App for `OrgTheyControl` and knows its `webhook_secret`.
2. Attacker crafts a `push` event JSON body with `repository.owner.login = "OrgTheyControl"` and `repository.full_name = "VictimOrg/victim-repo"`, `ref = "refs/heads/main"`, `after = "<attacker sha>"`.
3. Attacker computes `X-Hub-Signature: sha1=HMAC(webhook_secret_of_OrgTheyControl, raw_body)` and POSTs to `/github/webhooks` with `X-Github-Event: push`.
4. `WebhooksController#verify_signature` looks up `Shipit.github(organization: "OrgTheyControl")`, verifies the HMAC successfully, and dispatches the full payload to `PushHandler`.
5. `PushHandler#process` resolves stacks via `Repository.from_github_repo_name("VictimOrg/victim-repo")` and calls `sync_github(expected_head_sha: "<attacker sha>")` on `VictimOrg`'s stack, despite the attacker having no relationship whatsoever to `VictimOrg`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
