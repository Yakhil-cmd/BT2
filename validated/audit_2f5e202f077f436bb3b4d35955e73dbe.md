Confirmed: `Repository.from_github_repo_name` resolves purely off `params.repository.full_name` (`owner/name` string), completely independent of the `owner->login` value used for signature verification. There is no code anywhere in `WebhooksController`, `OpenedHandler`, or `ReviewStackAdapter` that cross-checks these two fields.

### Title
Webhook signature verified against attacker's org while `full_name` resolves a victim's repository, allowing cross-tenant ReviewStack provisioning - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb`)

### Summary
`WebhooksController#verify_signature` derives the signing organization solely from `params.dig('repository','owner','login')`, while `OpenedHandler#repository` resolves the target `Shipit::Repository` solely from `params.repository.full_name`. Because a JSON payload can set these two fields independently, an attacker who owns a webhook-configured org can sign a payload whose `owner.login` matches their own org (passing signature verification) but whose `full_name` names a different, review-stack-enabled victim repository, causing `ReviewStackAdapter#create!` to provision a stack under the victim's repository.

### Finding Description
The broken binding, stated explicitly:
`organization verifying signature (repository_owner = params.repository.owner.login)` **should equal** `organization owning the repository being mutated (owner segment of params.repository.full_name)`, but the code never enforces this equality.

Path:
1. `WebhooksController#verify_signature` computes `repository_owner` from `params.dig('repository', 'owner', 'login')` and looks up `Shipit.github(organization: repository_owner)` to verify HMAC signature [1](#0-0) [2](#0-1) . If the attacker owns an org with a configured `webhook_secret`, this passes for a payload the attacker legitimately signs with their own secret.
2. `OpenedHandler#repository` resolves the actual `Shipit::Repository` model using `params.repository.full_name` via `Shipit::Repository.from_github_repo_name`, which just splits the string on `/` and does a `find_by(owner:, name:)` lookup — it never checks `params.repository.owner.login` [3](#0-2) [4](#0-3) .
3. `provision?` and `respond_to_pull_request_opened?` are evaluated entirely against the resolved (victim) `repository`'s flags — `review_stacks_enabled`, `provisioning_behavior_allow_all?`, etc. — with no ownership check [5](#0-4) .
4. `ReviewStackAdapter#create!` then creates a `ReviewStack` scoped to `repository.review_stacks` (the victim repo) and enqueues it for provisioning [6](#0-5) .

Attacker request: A POST to `/webhooks` with `X-Github-Event: pull_request`, body `{"action":"opened", "repository": {"owner": {"login": "attacker-org"}, "full_name": "victim-org/victim-repo"}, ...}`, signed with `X-Hub-Signature` computed using the attacker's own `webhook_secret` for `attacker-org`. `verify_signature` passes because it only checks `attacker-org`'s secret against the raw body; nothing ties that check to `full_name`.

Existing guards do not close this gap: `verify_signature` only authenticates that *some* org with a matching secret signed the bytes, not that the org matches the target repo referenced inside the payload; `drop_unhandled_event` only checks the event type is handled; the `ExplicitParameters` schema in `OpenedHandler` only validates types/presence of fields, not cross-field consistency between `repository.owner.login` and `repository.full_name`; and `Repository.from_github_repo_name` performs a plain string lookup with no tenant check.

### Impact Explanation
An attacker who owns any Shipit-tracked repository/org (with its own configured `webhook_secret`) can forge a `pull_request opened` event that provisions a new `ReviewStack` (and, depending on config, subsequently drives real provisioning tasks via `ReviewStackProvisioningQueue`/`Command`/`PTY.spawn`) against **any other tracked repository** that has `review_stacks_enabled` and a permissive `provisioning_behavior` (`allow_all`, or label-based behaviors satisfiable by attacker-controlled PR labels). This is a record-written-for-a-repository-that-did-not-authenticate-it scenario and can trigger unauthorized provisioning workloads on the victim's infrastructure — matching the Critical category ("a payload for one repository mutating another's stack ... or an unauthorized deploy"). The attack is repeatable against any repository whose `full_name` the attacker knows, requires no privilege on the victim repo, and can be repeated for multiple victim repos from a single attacker-owned signing org.

### Likelihood Explanation
Preconditions: attacker must own/control at least one Shipit-tracked repository or org with a configured `webhook_secret` (a normal, low-privilege onboarding action, not a secret grant), and the victim repository must have `review_stacks_enabled` and a provisioning behavior satisfiable without victim-repo privileges (`allow_all` or label-based, since PR labels/actions are attacker-controlled on their own PR against the victim repo is not even required — the entire event is forged, not a real GitHub webhook). Attacker cost is minimal: craft a JSON body and compute one HMAC-SHA1 signature with a secret they already know. This is fully repeatable and scales to any number of victim repositories.

### Recommendation
In `WebhooksController#verify_signature` (or in each handler's `repository` resolution), enforce that the verified `repository_owner` used for signature validation equals the owner segment parsed from `params.repository.full_name` before any handler processes the payload; reject the request (422) on mismatch. Alternatively, always derive the GitHub app/secret to verify against from the `full_name`-derived owner rather than from `repository.owner.login`, so the two can never diverge.

### Proof of Concept
Minitest plan (`test/controllers/webhooks_controller_test.rb`):
1. Create two `Shipit::Repository` fixtures/records: `attacker/attacker-repo` (any config) and `victim/victim-repo` with `review_stacks_enabled: true`, `provisioning_behavior: allow_all`.
2. Configure `Shipit.github(organization: 'attacker')` with a known `webhook_secret`, and ensure `Shipit.github(organization: 'victim')` has a different/unset secret.
3. Build a `pull_request` `opened` JSON payload where `repository.owner.login == 'attacker'` but `repository.full_name == 'victim/victim-repo'`, with a valid `pull_request.head.ref`, `user.login`, `sender.login`, etc.
4. Compute `X-Hub-Signature` using the attacker org's `webhook_secret` and the raw JSON body (mirroring `DeliverySigner`/`OpenSSL::HMAC.hexdigest('sha1', webhook_secret, message)`).
5. POST to `:create` with `X-Github-Event: pull_request` and the computed signature header.
6. Assert response is `:ok` (not `:unprocessable_entity`), and assert `Shipit::Repository.find_by(owner: 'victim', name: 'victim-repo').review_stacks.count` increased by 1 — i.e., `ReviewStack.create!` was invoked for the victim repository despite the request being signed only by the attacker's org secret.
7. Assert the equality that should have held did not: `repository_owner` (`'attacker'`, verified) != owner segment of `full_name` (`'victim'`, mutated), yet the stack was still created.
