### Title
Legacy `pattern` rules for `event: file` silently fail to inspect `Write`-tool content, allowing block rules to be evaded - (File: `plugins/hookify/core/config_loader.py` / `plugins/hookify/core/rule_engine.py`)

### Summary
`Rule.from_dict` converts a legacy `pattern` field for `event: file` rules into a single condition on field `new_text`, exactly as documented. However, `RuleEngine._extract_field` resolves `new_text` to `tool_input.get('new_string', '')`, which is only populated for `Edit`/`MultiEdit` tool calls, not `Write` (which stores its payload under `content`). An equivalent rule written with explicit `conditions` using `field: content` works correctly for both tools, so the legacy and explicit forms of the same intended rule diverge in effective coverage.

### Finding Description
`Rule.from_dict` legacy branch infers the field from the event type: for `event: file` it hardcodes `field = 'new_text'` [1](#0-0) . This matches the documented behavior ("pattern... matches against command (bash) or new_text (file)") in the README and skill docs [2](#0-1)  and the skill guidance's minimum-viable rule examples [3](#0-2) .

At evaluation time, `RuleEngine._extract_field` handles the `new_text` field for `Write`/`Edit` tools by returning only `tool_input.get('new_string', '')` [4](#0-3) . The `Write` tool's payload key is `content`, not `new_string`, so for `Write` calls this lookup always yields an empty string (not `None`). Because the returned value is `''` rather than `None`, `_check_condition` does not short-circuit on "field not found" — it proceeds to test the regex/operator against the empty string [5](#0-4) , which for any non-trivial "dangerous content" pattern will not match, silently causing the rule to never fire for `Write` operations.

By contrast, the "explicit conditions" form supports a distinct `content` field, whose extraction logic correctly falls back across both `content` and `new_string`: `tool_input.get('content') or tool_input.get('new_string', '')` [6](#0-5) . A rule author (or a rule generated by `/hookify rule creation`, which the docs steer toward the simple `pattern` shorthand for basic rules [7](#0-6) ) who writes a legacy `event: file` / `pattern:` block rule intending to catch dangerous content in both `Write` and `Edit` calls gets a rule that is silently inert against `Write`. The only way to get correct coverage of both tools is to hand-author the more advanced explicit `conditions` form with `field: content` — an option that is not the default/simple path shown first in the documentation and generation flow.

This is a real divergence between "legacy" and "explicit" rule forms that produces different effective security semantics for logically identical intent, and it is reachable purely through ordinary rule authoring/consumption: any `.claude/hookify.*.local.md` file (repo-shipped or generated via `/hookify rule creation`) using the simple/legacy `pattern` shorthand for `event: file` is affected. No existing validation, matcher, or parser check flags or normalizes this discrepancy — `load_rule_file`/`load_rules` load the rule as-is and no code cross-checks that `new_text` covers `Write` inputs [8](#0-7) .

### Impact Explanation
This is a Security-control bypass: a block rule that appears (per the plugin's own documentation) to guard against dangerous `Write`/`Edit` file content actually never triggers for `Write` tool calls, silently disabling the intended blocking behavior for a whole class of file-writing operations while still working (and thus appearing functional/tested) for `Edit`. An attacker who can influence which tool Claude uses to write a file (e.g., through prompt injection, repo instructions, or by shipping instructions that bias Claude toward `Write` over `Edit`) can route around an operator-configured block rule that was believed to cover all file edits, undermining a locally-configured safety guardrail without any error or warning being surfaced to the user.

### Likelihood Explanation
High feasibility and fully repeatable: this is a deterministic code-path issue, not a race condition or timing-dependent bug. Preconditions are simply (1) a `.claude/hookify.*.local.md` rule with `event: file`, `action: block`, and the simple/legacy `pattern` field (the form explicitly documented and generated as the default/simple option), and (2) the attacker or Claude subsequently performing the disallowed file operation via the `Write` tool rather than `Edit`/`MultiEdit`. No admin privileges, exploitation of other bugs, or social engineering beyond ordinary repo content/rule authoring is required.

### Recommendation
Fix the legacy-to-explicit condition conversion and/or the field extraction so both forms are semantically equivalent:
- In `Rule.from_dict`, for `event == 'file'` legacy pattern rules, use `field = 'content'` (which already has correct fallback logic across `Write`'s `content` and `Edit`'s `new_string`) instead of `field = 'new_text'`, or
- In `RuleEngine._extract_field`, make the `new_text`/`new_string` branch fall back to `tool_input.get('content')` the same way the `content` branch does, so `new_text` and `content` are guaranteed equivalent for `Write`/`Edit`.
Additionally, add an explicit unit test asserting that a legacy `pattern`-based `event: file` block rule triggers identically for both `Write` and `Edit` tool inputs carrying the same dangerous text, to prevent regression of this invariant.

### Proof of Concept
```python
from hookify.core.config_loader import Rule
from hookify.core.rule_engine import RuleEngine

frontmatter = {
    "name": "block-eval",
    "enabled": True,
    "event": "file",
    "pattern": r"eval\(",
    "action": "block",
}
rule = Rule.from_dict(frontmatter, "Blocked: eval() detected")
engine = RuleEngine()

edit_input = {
    "hook_event_name": "PreToolUse",
    "tool_name": "Edit",
    "tool_input": {"file_path": "a.py", "old_string": "x", "new_string": "eval(user_input)"},
}
write_input = {
    "hook_event_name": "PreToolUse",
    "tool_name": "Write",
    "tool_input": {"file_path": "a.py", "content": "eval(user_input)"},
}

edit_result = engine.evaluate_rules([rule], edit_input)
write_result = engine.evaluate_rules([rule], write_input)

# Expected (intended) behavior: both should be blocked
assert edit_result.get("hookSpecificOutput", {}).get("permissionDecision") == "deny"
assert write_result.get("hookSpecificOutput", {}).get("permissionDecision") == "deny"  # FAILS: write_result == {}
```
This test currently fails on the `Write` assertion, confirming the same dangerous content is blocked via `Edit` but silently allowed via `Write` using the documented legacy `pattern` rule form, while an equivalent explicit `conditions` rule with `field: content` blocks both.
