**`WriteVoteDataBlockNums`** (`schema.go` lines 55-57): calls `writeStoredUint64Array` directly — **no lock acquired**.

**`migrate()`** (`init.go` lines 151-177): background goroutine → `accumulateVotesInEpoch()` → `InsertVoteDataBlockNum()` (acquires `mu`).

The race is real. The dangerous interleaving:

1. `InsertVoteDataBlockNum` reads DB = `[1, 2, 3, 4]`, prepares to append `5`
2. `RemoveVotesAfter` (triggered by reorg) removes `3`, `4` from in-memory, calls `WriteVoteDataBlockNums([1, 2])` → DB = `[1, 2]`
3. `InsertVoteDataBlockNum` writes `[1, 2, 3, 4, 5]` → DB = `[1, 2, 3, 4, 5]` (stale entries `3`, `4` restored)

For stale entries `3` and `4` (reorged-out block numbers), `GetHeaderByNumber` returns the **canonical** header at those heights — which may have no vote or a different vote — causing incorrect governance votes to be loaded.

### Title
Race Between `InsertVoteDataBlockNum` and `WriteVoteDataBlockNums` Corrupts Persisted Vote Index — (`kaiax/gov/headergov/impl/schema.go`, `rewind.go`)

### Summary
A lost-update race between the background migration goroutine's `InsertVoteDataBlockNum` (which holds the package-level `mu` lock) and `RemoveVotesAfter`'s call to `WriteVoteDataBlockNums` (which holds **no** lock) can corrupt the persisted `voteDataBlockNums` DB key, causing incorrect governance votes to be loaded after a node restart.

### Finding Description
`InsertVoteDataBlockNum` performs a read-modify-write on `voteDataBlockNumsKey` under the package-level `mu` lock: [2](#0-1) 

`WriteVoteDataBlockNums` is an unguarded write with no lock: [5](#0-4) 

`RemoveVotesAfter` calls it without acquiring `mu`: [3](#0-2) 

The background `migrate()` goroutine calls `InsertVoteDataBlockNum` concurrently: [6](#0-5) 

The dangerous interleaving: `InsertVoteDataBlockNum` reads the DB array, then `WriteVoteDataBlockNums` overwrites it with the post-reorg set, then `InsertVoteDataBlockNum` writes back the pre-reorg array with the new entry appended — restoring stale (reorged-out) block numbers to the DB.

### Impact Explanation
After a node restart, `readVoteDataFromDB` reads `voteDataBlockNums` and calls `GetHeaderByNumber` for each stored block number. Stale entries (reorged-out block numbers) cause it to load the **canonical** header at those heights, which may carry no vote or a different vote, silently corrupting the in-memory governance vote cache. This can cause the node to apply wrong governance parameters (epoch length, committee size, base fee bounds), diverging from consensus. [7](#0-6) 

### Likelihood Explanation
The race requires the background migration goroutine to be active (it runs from node start until all historical epochs are scanned) and a reorg to occur simultaneously. Reorgs are normal P2P events. The migration goroutine is throttled at 50ms per epoch, keeping it alive for extended periods on long chains. The race window per iteration is small but the goroutine runs for a long time, making the cumulative probability non-negligible. [8](#0-7) 

### Recommendation
`WriteVoteDataBlockNums` and `RemoveVotesAfter` must acquire the package-level `mu` lock before writing `voteDataBlockNumsKey`. Either:
1. Have `RemoveVotesAfter` acquire `mu` before calling `WriteVoteDataBlockNums`, or
2. Add locking inside `WriteVoteDataBlockNums` itself (making it consistent with `InsertVoteDataBlockNum`).

func InsertVoteDataBlockNum(db database.Database, blockNum uint64) {
	mu.Lock()
	defer mu.Unlock()

	blockNums := readStoredUint64Array(db, voteDataBlockNumsKey)
	if blockNums == nil {
		blockNums = StoredUint64Array{}
	}

	// Check if blockNum already exists in the array
	if slices.Contains(blockNums, blockNum) {
		return
	}

	blockNums = append(blockNums, blockNum)
	slices.Sort(blockNums)

	writeStoredUint64Array(db, voteDataBlockNumsKey, blockNums)
}
