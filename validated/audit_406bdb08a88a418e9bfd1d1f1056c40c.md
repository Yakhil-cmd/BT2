### Title
Local `Membership`/`authorized?` check trusts DB state populated by forged webhooks, letting a mis-teamed login trigger deploys/rollbacks - ([File: app/controllers/concerns/shipit/authentication.rb])

### Summary
`force_github_authentication` gates every stack/task mutating action solely on `current_user.authorized?`, which is a pure local DB lookup (`teams.where(id: Shipit.github_teams.map(&:id)).exists?`) with no live re-verification against GitHub. Because `MembershipHandler` writes `Team`/`Membership` rows from webhook payloads without binding them to any repository/installation the target `Stack` actually belongs to, a forged `membership` event that lands a `Membership` row in a `Shipit.github_teams`-configured team flips `authorized?` to `true` for that login the next time it logs in, giving it unrestricted access to `StacksController`/`TasksController` deploy/rollback actions.

### Finding Description
The binding claimed is: `current_user.authorized?` (`app/models/shipit/user.rb:80-82`) == "a legitimately GitHub-reported, org-scoped membership in a `Shipit.github_teams` team." In reality `authorized?` only checks `teams.where(id: Shipit.github_teams.map(&:id)).exists?`, purely against local rows created by `MembershipHandler#process` (`app/models/shipit/webhooks/handlers/membership_handler.rb:22-34`), which is fed straight from webhook JSON (`params.team.id`, `params.organization.login`, `params.member.login`) with no re-check against which installation/repository sent the event.

`force_github_authentication` (`app/controllers/concerns/shipit/authentication.rb:20-34`) is the only gate applied to `StacksController`/`TasksController` (via `ShipitController`/`Authentication` concern) - it calls `current_user.authorized?` and renders 403 only if false; there is no additional per-stack/per-repository permission check (`app/controllers/shipit/tasks_controller.rb` has no `require_permission!`/authorization beyond `before_action :stack`).

Once a `Membership` row exists for the attacker's login in a team whose `github_id` matches one of `Shipit.github_teams`, that user's next OAuth login (an unprivileged, self-service action - anyone can complete GitHub OAuth as themselves) sets `session[:user_id]`, and every subsequent request re-derives `current_user` from that `User` row and re-evaluates `authorized?` as `true`. No further live GitHub team check occurs. This lets the attacker directly `POST` to task-triggering endpoints such as `TasksController#create` (`app/controllers/shipit/tasks_controller.rb:30-44`, calling `stack.trigger_task`) or `abort` (rollback), for any `Stack` reachable via `Stack.from_param!(params[:stack_id])`, with no ownership/team-to-stack correlation enforced.

### Impact Explanation
This is Critical: it converts a forged webhook-authored `Membership` record into a durable, session-portable authorization bypass that unlocks deploy/rollback triggering (`TasksController#create`/`#abort`) engine-wide, not scoped to any particular repository the forged membership was nominally about. Because `Shipit.github_teams` membership is the *only* authorization primitive in the engine (`app/models/shipit/user.rb:80-82`), and it's evaluated purely from local state, the compromise is repeatable for as long as the forged `Membership` row persists and blast radius extends to every stack the Shipit instance manages, matching "unauthorized deploy, rollback...of attacker-controlled code."

### Likelihood Explanation
Feasibility is entirely conditioned on the prerequisite already assumed true by the question: a forged `membership` webhook successfully creating/updating a `Team`/`Membership` for a team ID configured in `Shipit.github_teams`. Given that precondition, exploitation of this specific step is trivial and requires no secrets - only the attacker completing normal GitHub OAuth login as themselves (`session[:user_id]` set to their own already-existing `User` row) and issuing normal authenticated HTTP requests to deploy endpoints.

### Recommendation
Do not treat locally-stored `Membership` rows as an authoritative, static allowlist. Either (a) re-validate team membership live against GitHub at session/authorization time (or on a short TTL) rather than trusting webhook-populated rows indefinitely, or (b) bind `Team`/`Membership` writes in `MembershipHandler` to the verified GitHub App installation/organization context of the webhook delivery (so a membership event cannot silently attach to an unrelated `Shipit.github_teams` team), closing the forgery at its source as identified in the prior question.

    def force_github_authentication
      if current_user.logged_in? && current_user.requires_fresh_login?
        Rails.logger.warn("User #{current_user.id} requires a fresh login, logging out...")
        reset_session
        redirect_to(Shipit::Engine.routes.url_helpers.github_authentication_path(origin: request.original_url))
      elsif Shipit.authentication_disabled? || current_user.logged_in?
        unless current_user.authorized?
          team_handles = Shipit.github_teams.map(&:handle)
          team_list = team_handles.to_sentence(two_words_connector: ' or ', last_word_connector: ', or ')
          render(plain: "You must be a member of #{team_list} to access this application.", status: :forbidden)
        end
      else
        redirect_to(Shipit::Engine.routes.url_helpers.github_authentication_path(origin: request.original_url))
      end
    end

        def process
          team = find_or_create_team!
          member = User.find_or_create_by_login!(params.member.login)

          case params.action
          when 'added'
            team.add_member(member)
          when 'removed'
            team.members.delete(member)
          else
            raise ArgumentError, "Don't know how to perform action: `#{action.inspect}`"
          end
        end

          end
        end
