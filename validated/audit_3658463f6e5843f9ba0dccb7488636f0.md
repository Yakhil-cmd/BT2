### Title
Arbiter dispute/appeal flow leaks the victim's permanent device-pairing secret to an attacker-chosen ArbStore URL - (File: `arbiter_contract.js`)

### Summary
When a user opens a dispute (`openDispute`) or files an appeal (`appeal`) on an arbiter contract, ocore fetches the ArbStore URL for the contract's `arbiter_address` and then POSTs a JSON payload to that URL that includes `my_pairing_code` — the device's **permanent** pairing secret. The `arbiter_address` is a field of the contract that is set by whichever party (offeror) created and sent the `arbiter_contract_offer`. A malicious counterparty can name themselves (or a colluding "arbiter") as `arbiter_address`, causing the victim's own client to later transmit the victim's permanent pairing secret directly, over plain HTTP(S), to a server the attacker controls — exactly analogous to bbot's `gitlab.py` bug where a globally-configured secret is sent to a URL determined by data supplied to the tool, rather than to the intended trusted endpoint.

### Finding Description
`createAndSend()` lets one party build an arbiter contract, including `arbiter_address`, and sends it to the counterparty as `arbiter_contract_offer`: [1](#0-0) 

The counterparty stores this data verbatim via `store()`; nothing here validates that `arbiter_address` is a real, trustworthy arbiter — it is fully attacker-supplied. Later, when the victim needs to dispute or appeal a contract, ocore resolves an ArbStore URL for that address via the victim's own hub and immediately POSTs sensitive data to it: [2](#0-1) [3](#0-2) 

In both `openDispute` and `appeal`, `device.getOrGeneratePermanentPairingInfo()` retrieves the **permanent** pairing secret (`is_permanent=1`, valid until 2038) and embeds it as `my_pairing_code` in the JSON body sent via `httpRequest(url, ...)`: [4](#0-3) 

`httpRequest` performs a plain POST with no pinning/verification tying `url` to a known-good ArbStore, and no restriction on what is sent to it: [5](#0-4) 

The `url` itself is resolved through `hub/get_arbstore_url` for the attacker-supplied `arbiter_address` — the mapping is not scoped to a hardcoded/allow-listed set of legitimate ArbStores: [6](#0-5) [7](#0-6) 

Because the pairing secret is **permanent** and is the same one used elsewhere for legitimate pairing (`getOrGeneratePermanentPairingInfo`), leaking it to an attacker allows the attacker to pair with the victim's device as a trusted correspondent at will: [4](#0-3) 

This mirrors the reported bug class: a credential/secret meant for one specific, trusted destination is instead transmitted to a destination selected by attacker-influenceable data.

### Impact Explanation
A victim who accepts (even inadvertently) an arbiter contract naming an attacker-controlled `arbiter_address`/ArbStore, and later opens a dispute or appeal (a normal, expected wallet action when a deal goes wrong — which the attacker can engineer by simply not paying/cooperating), will have their client automatically POST their permanent device pairing secret to the attacker's server. With that secret the attacker can add themselves as a confirmed correspondent device (`handlePairingMessage`) without further victim interaction: [8](#0-7) 

Being an authenticated device correspondent enables the attacker to send arbitrary device messages (chat, multisig signing requests, wallet-approval flows, further arbiter contract offers, etc.) to the victim, which can be leveraged as a stepping stone toward tricking the victim into approving fraudulent multi-signature transactions or other fund-affecting actions. This satisfies the "AA/contract fund loss" escalation path via social engineering enabled by unauthorized device access.

### Likelihood Explanation
Likelihood is moderate-to-high for any user who engages in arbiter-mediated deals: the attacker only needs to be the counterparty in an arbiter_contract who supplies a controlled `arbiter_address`, and the dispute/appeal flow is a normal part of the arbiter contract lifecycle that a user is likely to trigger once a deal is contested (which the attacker can force by simply defaulting on payment or refusing to complete). No hub compromise, no TLS bypass, and no privileged access is required — only the ability to send a device message (`arbiter_contract_offer`) that includes an attacker-chosen `arbiter_address`.

### Recommendation
- Do not send `my_pairing_code` (or any device-pairing secret) to third-party HTTP endpoints resolved from contract-supplied identifiers; if ArbStores genuinely need to relay pairing info between parties, exchange it end-to-end over the already-authenticated device-messaging channel instead of raw HTTP POST.
- Validate/pin ArbStore URLs against a signed, hub-independent allow-list or require that `arbiter_address`/ArbStore registration itself be attested (e.g., signed by a known registry) before any secret material is transmitted to it.
- Prefer ephemeral, single-use pairing secrets scoped to the specific dispute/appeal instead of reusing the permanent pairing secret for this purpose.

### Proof of Concept
1. Attacker creates a wallet identity and publishes themselves (or a colluding third party) as an "arbiter" with an ArbStore URL pointing to `https://attacker.example/`, resolvable via `hub/get_arbstore_url`.
2. Attacker sends an `arbiter_contract_offer` to the victim (via `device.sendMessageToDevice`) with `arbiter_address` set to the attacker's arbiter address (`arbiter_contract.js:createAndSend`).
3. Victim accepts the contract, pays into the shared address, and the deal goes wrong (attacker refuses to release funds/cooperate).
4. Victim calls `openDispute(hash, cb)` (or later `appeal`). ocore resolves the URL via `hub/get_arbstore_url` for the attacker's `arbiter_address`, builds `data` including `my_pairing_code` (the permanent pairing secret from `getOrGeneratePermanentPairingInfo`), and POSTs it to `https://attacker.example/api/dispute/new` (`arbiter_contract.js:262-318`).
5. Attacker's server logs the received `my_pairing_code`, then uses it to pair with the victim's device (`device.js:handlePairingMessage`), becoming a trusted correspondent able to send further messages/requests to the victim.

function httpRequest(host, path, data, cb) {
	var reqParams = Object.assign(url.parse(host),
		{
			path: path,
			method: "POST",
			headers: {
				"Content-Type": "application/json",
				"Content-Length": (new TextEncoder().encode(data)).length
			}
		}
	);
	var req = http.request(
		reqParams,
		function(resp){
			var data = "";
			resp.on("data", function(chunk){
				data += chunk;
			});
			resp.on("end", function(){
				try {
					data = JSON.parse(data);
					if (data.error) {
						return cb(data.error);
					}
					cb(null, data);
				} catch (e) {
					cb(e);
				}
			});
		}).on("error", cb);
	req.write(data);
	req.end();
}

function handlePairingMessage(json, device_pubkey, callbacks){
	var body = json.body;
	var from_address = objectHash.getDeviceAddress(device_pubkey);
	if (!ValidationUtils.isNonemptyString(body.pairing_secret))
		return callbacks.ifError("correspondent not known and no pairing secret");
	if (!ValidationUtils.isNonemptyString(json.device_hub)) // home hub of the sender
		return callbacks.ifError("no device_hub when pairing");
	if (json.device_hub.length > 200)
		return callbacks.ifError("device_hub too long");
	if (!network.isValidWsUrl(conf.WS_PROTOCOL + json.device_hub))
		return callbacks.ifError("invalid device_hub URL");
	if (!ValidationUtils.isNonemptyString(body.device_name))
		return callbacks.ifError("no device_name when pairing");
	if (body.device_name.length > 100)
		return callbacks.ifError("device_name too long");
	if ("reverse_pairing_secret" in body && !ValidationUtils.isNonemptyString(body.reverse_pairing_secret))
		return callbacks.ifError("bad reverse pairing secret");
	eventBus.emit("pairing_attempt", from_address, body.pairing_secret);
	db.query(
		"SELECT is_permanent FROM pairing_secrets WHERE pairing_secret IN(?,'*') AND expiry_date>"+db.getNow()+" ORDER BY (pairing_secret=?) DESC LIMIT 1", 
		[body.pairing_secret, body.pairing_secret], 
		function(pairing_rows){
			if (pairing_rows.length === 0)
				return callbacks.ifError("pairing secret not found or expired");
			// add new correspondent and delete pending pairing
			var safe_device_name = body.device_name.replace(/<[^>]*>?/g, '');
			db.query(
				"INSERT "+db.getIgnore()+" INTO correspondent_devices (device_address, pubkey, hub, name, is_confirmed) VALUES (?,?,?,?,1)", 
				[from_address, device_pubkey, json.device_hub, safe_device_name],
				function(){
					db.query( // don't update name if already confirmed
						"UPDATE correspondent_devices SET is_confirmed=1, name=? WHERE device_address=? AND is_confirmed=0", 
						[safe_device_name, from_address],
						function(){
							db.query("UPDATE correspondent_devices SET is_blackhole=0 WHERE device_address=?", [from_address], function(){
								eventBus.emit("paired", from_address, body.pairing_secret);
								if (pairing_rows[0].is_permanent === 0){ // multiple peers can pair through permanent secret
									db.query("DELETE FROM pairing_secrets WHERE pairing_secret=?", [body.pairing_secret], function(){});
									eventBus.emit('paired_by_secret-'+body.pairing_secret, from_address);
								}
								if (body.reverse_pairing_secret)
									sendPairingMessage(json.device_hub, device_pubkey, body.reverse_pairing_secret, null);
								callbacks.ifOk();
							});
						}
					);
				}
			);
		}
	);
}
