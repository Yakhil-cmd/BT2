### Title
Webhook signature verified against `repository.owner.login` while `EditedHandler` mutates data keyed by unrelated `repository.full_name` - (File: `app/controllers/shipit/webhooks_controller.rb`, `lib/shipit/github_app.rb`, `app/models/shipit/webhooks/handlers/pull_request/edited_handler.rb`)

### Summary
`Shipit::WebhooksController#verify_signature` selects which org's `GitHubApp`/secret to authenticate a webhook with using `repository_owner`, which is read solely from `params.dig('repository','owner','login')`. `EditedHandler#pull_request` (and `#repository`) instead resolves the target repository/stack entirely from `params.repository.full_name`, an independent, attacker-controlled field with no cross-check against `repository.owner.login`. If any org configured in `Shipit.github_apps` lacks a `webhook_secret`, `GitHubApp#verify_webhook_signature` returns `true` unconditionally, letting an attacker forge an `edited` event that authenticates as the no-secret org but mutates a `PullRequest` belonging to a completely different, victim org/repo.

### Finding Description
The broken invariant, stated as an equality that should hold but does not:

`repository_owner` (used to select the verifying `GitHubApp`) == owner segment of `params.repository.full_name` (used to resolve the `Repository`/`PullRequest` mutated by the handler).

Code path:
1. `WebhooksController#verify_signature` computes `repository_owner = params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` and calls `Shipit.github(organization: repository_owner).verify_webhook_signature(...)`. [1](#0-0) [2](#0-1) 
2. `GitHubApp#verify_webhook_signature` short-circuits to `true` when the selected org has no `webhook_secret` configured: `return true unless webhook_secret`. [3](#0-2) 
3. On success, `WebhooksController#create` dispatches the raw, unmodified `params` (including `repository.full_name`) to `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`. [4](#0-3) 
4. `EditedHandler#repository` resolves the repository purely via `Shipit::Repository.from_github_repo_name(params.repository.full_name)`, and `#pull_request` looks up an existing `PullRequest` scoped to that repository's `id` by `number`. [5](#0-4) 
5. `Repository.from_github_repo_name` just splits `full_name` on `/` — it never checks that the split owner matches `repository.owner.login` used for signature selection. [6](#0-5) 
6. `EditedHandler#process` then calls `pull_request.update(github_pull_request: params.pull_request)`, persisting attacker-supplied fields (title, state, additions/deletions, head sha/ref, assignees, labels) onto that victim `PullRequest` record. [7](#0-6) 

Exploit flow: attacker sets `repository.owner.login` (and/or `organization.login`) to the login of an org that the Shipit operator configured in `Shipit.github_apps` **without** a `webhook_secret`. `verify_signature` selects that org's `GitHubApp`, whose `verify_webhook_signature` returns `true` unconditionally regardless of the `X-Hub-Signature` header/body. The attacker sets `repository.full_name` to `victim-org/victim-repo` (any repo Shipit tracks) and `number`/`pull_request` fields to target an existing PR on the victim stack. `drop_unhandled_event` and the `ExplicitParameters` schema in `EditedHandler` only check structural shape of the JSON, not organization consistency, so they don't block this. There is no code anywhere that compares the org used for signature verification against the org embedded in `full_name`.

### Impact Explanation
An unprivileged, unauthenticated attacker can write attacker-chosen data into any tracked `PullRequest` record belonging to a stack in a completely different, victim GitHub org — this is a "payload for one repository mutating another's stack/commit/task" scenario per the Critical impact category. The persisted `github_pull_request` fields (title, state, head sha/ref, labels, assignees) feed downstream UI/logic (e.g., review-stack provisioning/labels-driven archive/unarchive behavior used by sibling handlers, and PR status display), so forged data can misrepresent PR state for a repository the attacker never touched. The attack is fully repeatable against any number of victim repos/stacks as long as at least one org configured on the instance lacks a `webhook_secret`, and costs the attacker nothing beyond crafting one HTTP POST per forged event.

### Likelihood Explanation
Preconditions: (1) the Shipit instance must have at least one org entry in its GitHub app configuration with no `webhook_secret` set — this is an operator misconfiguration but plausible in multi-org setups where only some orgs' secrets were configured; (2) the victim org/repo/PR must already exist in Shipit's database. No GitHub credentials, Shipit session, or API token are required — the attacker only needs to know (or guess) the login of a no-secret org and the `owner/name`/PR number of a victim stack, both of which are typically public information (GitHub org/repo names, PR numbers). Given those two preconditions, exploitation is trivial and repeatable at will.

### Recommendation
Enforce the invariant that the org used to select/verify the webhook secret matches the org embedded in the payload actually consumed by handlers. Concretely: derive `repository_owner` from the same `full_name` field the handlers use (e.g., `params.dig('repository', 'full_name')&.split('/')&.first`) rather than trusting the separate `repository.owner.login`/`organization.login` fields, or explicitly validate that `repository.owner.login == repository.full_name.split('/').first` before verifying the signature and reject (422) on mismatch. Additionally, treat "org configured without `webhook_secret`" as a hard misconfiguration (fail closed / log loudly / require operators to set a secret) instead of silently accepting all webhooks for that org.

### Proof of Concept
Minitest plan (under `test/controllers/webhooks_controller_test.rb`, no live GitHub):
1. Seed two orgs in `Shipit.github_apps` config for the test: `no_secret_org` (no `webhook_secret`) and implicitly the victim org (any string, no config needed since it's never used for verification).
2. Create `victim_repo = Shipit::Repository.create!(owner: 'victim-org', name: 'victim-repo')`, a `Stack` under it, and a `Shipit::PullRequest` with `number: 42` and some baseline `github_pull_request` attributes (e.g., `title: "original"`).
3. Build a JSON payload for `pull_request` `action=edited` where:
   - `repository.owner.login = "no_secret_org"`
   - `repository.full_name = "victim-org/victim-repo"`
   - `number = 42`
   - `pull_request.title = "PWNED"` (attacker-controlled)
4. POST to `/webhooks` with header `X-Github-Event: pull_request` and an arbitrary/garbage `X-Hub-Signature` (since `no_secret_org` has no secret, verification is bypassed).
5. Assert response is `200 OK` (not `422`).
6. Reload the seeded `PullRequest` and assert `pull_request.github_pull_request['title'] == "PWNED"` — proving the org that "authenticated" the request (`no_secret_org`) is not the org whose data (`victim-org`) was mutated.
7. Equality-before/after check: before the request, `repository_owner` ("no_secret_org") != owner of `params.repository.full_name` ("victim-org"); after the request, the victim's PR record was still updated — demonstrating the invariant "a `pull_request` event only affects the repository/stack whose secret authenticated it" is violated.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
