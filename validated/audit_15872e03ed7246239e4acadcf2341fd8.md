### Title
Disabled-debt assets are silently excluded from LTV/liquidation calculations, hiding real debt and socializing losses to vault suppliers - (File: `mainnet/contracts/market/v0-4-market.clar`)

### Summary
The Lombard report's root cause is that an "enabled" check exists at some call sites but not others, letting a disabled/compromised entity be treated as valid. The Zest codebase has the same structural gap: the DAO can disable an asset for *debt* via `assets.disable(asset, collateral: false)` [1](#0-0)  at any time, independent of whether accounts still owe that asset. Every position lookup used for health/LTV math (`get-position`, and critically `get-liquidation-position`) filters *both* collateral and debt bits through the single, current `get-enabled-bitmap` mask [2](#0-1) , so any debt asset later disabled silently disappears from the debt list returned by `market-vault`'s `iter-lookup-debt`/`relevant` filter [3](#0-2) . Only the *collateral* side of this problem was fixed (in `collateral-remove`, which explicitly branches to `get-full-position` when `is-collateral-enabled` is false) [4](#0-3) ; the debt side never received the analogous fix, even though `get-liquidation-position`'s own comment says it should return "enabled collateral + all debt" [5](#0-4) .

### Finding Description
`get-liquidation-position` is documented as returning "enabled collateral + all debt", implying debt should be unfiltered (analogous to `get-full-position`'s `MAX-U64` mask): [6](#0-5) 

But its implementation passes the *same* `get-enabled-bitmap()` mask that is used for the plain (non-liquidation) `get-position`, and this single mask is applied to both collateral and debt bits inside `market-vault`. `relevant` performs a `subset` check against this one mask for both `iter-lookup-collateral` and `iter-lookup-debt`: [3](#0-2) 

Consequently, once the DAO disables an asset for debt (`assets.disable(asset, false)`), any account that still carries scaled debt in that asset has that debt entry dropped from every downstream `get-notional-evaluation` computation in:
- `borrow` (uses `get-position`, which is enabled-filtered, to compute `debt-value` for the pre-check `is-healthy`) [7](#0-6) 
- `collateral-add` (uses `get-position` to compute `current-debt-usd`) [8](#0-7) 
- `collateral-remove` when the removed collateral is still enabled (uses filtered `position`, not `pos-full`) [9](#0-8) 
- `liquidate` (uses `get-liquidation-position`, which — despite its comment — is just as filtered) [10](#0-9) 

The hidden debt is real: `get-account-scaled-debt`/vault-level debt maps still track it and interest keeps accruing (`repay` reads it directly, bypassing the filtered list) [11](#0-10) , but it is invisible to every health/LTV/liquidation check. This is structurally identical to the reported bug class: an "enabled" check that exists in one code path (collateral-remove's `is-collateral-enabled` branch) but is missing from the parallel, equally security-critical path (debt in borrow/collateral-add/liquidate).

### Impact Explanation
Because the hidden debt is excluded from `current-ltv`/`total-debt-usd`, a position that is actually unhealthy or even liquidatable will report an artificially low LTV:
- In `liquidate`, `health-check (asserts! (>= current-ltv ltv-liq-partial) ERR-HEALTHY)` will incorrectly revert, blocking liquidators from acting on a genuinely under-collateralized position [12](#0-11) .
- In `borrow`/`collateral-add`, the account can pass `is-healthy`/future-capacity checks and withdraw collateral or add further debt in still-enabled assets while the disabled debt continues accruing interest, unmonitored and unrepaid.

The account holding the disabled debt benefits (it is not the "victim" of its own action), but the harmed party is every other, unrelated depositor in the vault of the disabled-debt asset: since this debt can never be captured by `liquidate` (it's invisible to the LTV check) nor is the borrower incentivized to voluntarily repay it, it accumulates as permanent bad debt in that vault. Eventually the vault must fall back to `vault-socialize-debt`, spreading the shortfall as a haircut across all suppliers who deposited into that vault [13](#0-12) . This is a socialized loss to unclaimed yield/principal of every supplier of that vault — a Critical/High impact (temporary/permanent freezing and loss of supplier funds), and is exactly the "unprivileged principal harms another via socialized shortfall" pattern permitted by the scope rules.

### Likelihood Explanation
Triggering requires only: (1) an account taking on debt in some asset while it is debt-enabled, and (2) the DAO later disabling that asset for debt (a routine, documented governance action — e.g., in response to a depeg or oracle risk, exactly the kind of situation this feature is meant to handle). No collusion, privileged access, or DAO compromise is needed by the borrower; the borrower simply needs to hold debt at the time of a legitimate, expected DAO action, then continue normal operations (borrow more elsewhere, remove other collateral) while their disabled debt silently rides for free. This is a realistic, plausible governance-driven scenario rather than an edge case.

### Recommendation
Make debt-side "enabled" filtering consistent with the collateral-side fix already present in `collateral-remove`:
- In `get-liquidation-position`, use a mask that includes ALL debt bits (analogous to how `get-full-position` uses `MAX-U64`), while still restricting collateral bits to the enabled set, so liquidation and health-check math always account for every real debt position.
- In `borrow` and `collateral-add`, when computing `current-debt-usd`/`debt-value` for health checks, resolve and include any disabled-debt entries the account still holds (mirroring the `is-collateral-enabled` → `get-full-position` fallback used in `collateral-remove`), instead of relying solely on the filtered `get-position`.
- Add an invariant/test ensuring that disabling debt for an asset with `asset.disable(asset, false)` cannot cause any account's true outstanding debt to be omitted from LTV, health, or liquidation calculations.

### Proof of Concept
1. Alice borrows `USDH` (asset id 8) against sBTC collateral; her scaled debt is recorded in `market-vault`'s `debt` map [14](#0-13) .
2. The DAO calls `assets.disable(USDH-contract, false)` (e.g., due to a depeg event), clearing USDH's debt-enabled bit in the global bitmap [1](#0-0) .
3. Alice's USDH position collapses in value (depeg), making her true LTV far above `LTV-LIQ-PARTIAL`. A liquidator calls `liquidate(alice, sbtc-ft, usdh-ft, ...)`.
4. Inside `liquidate`, `get-liquidation-position(alice)` computes `mask` from `get-enabled-bitmap()`, which no longer contains USDH's debt bit; `market-vault get-position` therefore omits Alice's USDH debt entry from the returned debt list [15](#0-14) , [16](#0-15) .
5. `total-debt-usd` is computed without the USDH debt, so `current-ltv` looks healthy; `health-check (asserts! (>= current-ltv ltv-liq-partial) ERR-HEALTHY)` reverts and the liquidation fails, even though Alice is genuinely insolvent.
6. Alice's real USDH debt remains outstanding and unrecoverable; when the USDH vault eventually needs to cover the shortfall it calls `vault-socialize-debt`, haircutting all USDH suppliers' balances [13](#0-12)  — harming depositors who had no involvement in Alice's position.

(define-public (repay (ft <ft-trait>) (amount uint) (on-behalf-of (optional principal)))
  (let ((address (contract-of ft))
        (asset (try! (get-asset address)))
        (asset-id (get id asset))
        ;; defaults to payer (contract-caller) if not specified
        (account (match on-behalf-of behalf behalf contract-caller))
        
        ;; Step 1: Get position WITHOUT resolving prices
        (position (try! (get-position account)))
        (mask (get mask position))
        
        ;; Step 2: Accrue user's positions (populates cache for ztokens)
        (u-debt (accrue-user-debts (get debt position)))
        
        (borrow-index (get index (unwrap-panic (get-cached-indexes asset-id))))
        
        ;; Step 3: Get account debt FIRST to enable safe amount capping
        (account-scaled-debt (get-account-scaled-debt account asset-id))
        
        ;; Step 4: Calculate max repayable amount (actual debt in token), mul-div-up for safe upper bound
        (max-repay-tokens (mul-div-up account-scaled-debt borrow-index INDEX-PRECISION))
        
        ;; Step 5: Cap input amount at actual debt - prevents overflow in scaled calculation
        (safe-amount (min amount max-repay-tokens))
        
        ;; Step 6: Convert to scaled debt (amount is bounded)
        (scaled-debt-repayment (mul-div-down safe-amount INDEX-PRECISION borrow-index))

        (repaid-scaled-debt (min account-scaled-debt scaled-debt-repayment))
        (amount-to-repay (mul-div-up repaid-scaled-debt borrow-index INDEX-PRECISION))
        
        ;; Check if repaying ALL debt for this asset
        (repaying-all (is-eq repaid-scaled-debt account-scaled-debt)))

(define-private (relevant (asset uint) (enabled-mask uint) (c bool))
  (let ((position (mask-pos asset c))
        (mask (bit-or u0 (pow u2 position))))
    (subset mask enabled-mask)))

(define-private (iter-lookup-collateral
                (asset uint)
                (acc {
                    id: uint,
                    result: (list 64 { aid: uint, amount: uint}),
                    enabled-mask: uint
                }))
  (let ((mask (get enabled-mask acc))
        (relevant? (asserts! (relevant asset mask true) acc))
        (user-id (get id acc))
        (value (get-collateral user-id asset))
        (entry { aid: asset, amount: value }))
    {
      id: user-id,
      result: (unwrap-panic (as-max-len? (append (get result acc) entry) u64)),
      enabled-mask: mask
    }))

(define-private (add-user-collateral (user-id uint) (asset-id uint) (amount uint))
  (let ((key { id: user-id, asset: asset-id })
        (collateral-amount (default-to u0 (map-get? collateral key))) ;; graceful default
        (updated-collateral-amount (+ collateral-amount amount)))
      (map-set collateral key updated-collateral-amount)
      updated-collateral-amount))

(define-private (remove-user-collateral (user-id uint) (asset-id uint) (amount uint))
  (let ((key { id: user-id, asset: asset-id })
        (collateral-amount (default-to u0 (map-get? collateral key))) ;; graceful default
        (legal? (asserts! (<= amount collateral-amount) ERR-INSUFFICIENT-COLLATERAL))
        (updated-collateral-amount (- collateral-amount amount)))

      (if (is-eq updated-collateral-amount u0)
          (map-delete collateral key)
          (map-set collateral key updated-collateral-amount))
      (ok updated-collateral-amount)))
