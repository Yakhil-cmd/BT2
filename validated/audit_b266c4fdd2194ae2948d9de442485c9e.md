### Title
Webhook signature verification binds to `organization`/`repository.owner.login`, but stack mutation binds to `repository.full_name` — cross-org webhook forgery in multi-tenant deployments - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
In multi-organization Shipit deployments, `WebhooksController#verify_signature` selects the HMAC secret to validate an inbound webhook using `repository_owner`, a field read from the JSON body itself (`repository.owner.login` or `organization.login`). The actual handlers that mutate state — e.g. `PushHandler` — instead resolve the target `Stack`/`Repository` using an entirely different field from the same body: `repository.full_name`. Because the signature only proves "this body was signed with organization A's `webhook_secret`," and nothing ties `repository.owner.login` to `repository.full_name`, an attacker who legitimately controls organization A's GitHub App installation (and therefore knows A's `webhook_secret`) can forge a signed payload whose `repository.full_name` points at organization B's repository, causing Shipit to act on B's stacks.

### Finding Description
`verify_signature` picks the GitHub App config purely from attacker-suppliable JSON fields and uses that config's secret to validate the HMAC over the raw body: [1](#0-0) [2](#0-1) 

Once verification succeeds, `create` blindly re-parses the same raw body and dispatches it to every handler registered for the event, passing the raw `params` hash through unmodified: [3](#0-2) 

Every handler resolves which repository/stack to mutate from a *different* field of that same body — `repository.full_name` — with no cross-check against the `repository.owner.login`/`organization.login` value that was used to select the verifying secret: [4](#0-3) 

`PushHandler` (and other handlers such as the pull-request family and membership handler) then act directly on whatever `Repository`/`Stack` that lookup returns: [5](#0-4) 

This is the exact bug class from the report: a field that is acted upon (`repository.full_name`, driving which repository is written to) is never actually covered by the trust check that was performed (which only binds `repository.owner.login`/`organization.login` to the secret used for the HMAC). The per-organization secret model is a documented, supported configuration of this engine: [6](#0-5) [7](#0-6) 

### Impact Explanation
In a multi-org Shipit instance, each customer organization independently knows only its own `webhook_secret` (it configures its own GitHub App/webhook). Because signature-secret selection and repository-resolution use unrelated, independently-forgeable fields in the same untrusted JSON body, organization A can craft and sign a payload (with its own valid secret) whose `repository.full_name` names organization B's repository. This passes `verify_signature` (secret matches A) and is then dispatched to handlers that mutate B's data: `PushHandler` triggers `stack.sync_github` on B's stacks, pull-request handlers can open/close/label/merge PRs recorded against B's repositories, and the membership handler creates/mutates `Team`/`User` records — all without B's GitHub App ever sending anything. This is a cross-organization/cross-repository write achieved purely by crafting an HTTP request to a public endpoint, matching the "cross-repository writes" Critical impact category.

### Likelihood Explanation
Exploitability requires only that the attacker be an authorized administrator of *any one* organization onboarded to a shared, multi-org Shipit instance (a supported, documented deployment topology) — no Shipit account, `ApiClient` token, or privileged Shipit role is needed. The attacker only needs to know their own org's `webhook_secret`, which they control by virtue of having configured their own GitHub App. This is a realistic tenant-isolation break for any operator running Shipit with `config.github` keyed by multiple organizations.

### Recommendation
After signature verification, validate that the organization/owner used to select the verifying secret is consistent with the actual `repository.full_name`'s owner (and/or resolve `Repository`/`Stack` scoped to the verified organization only), rejecting webhooks where these two identities diverge, e.g. in `WebhooksController#verify_signature` or centrally in `Handler#repository_name`/`#stacks`.

### Proof of Concept
1. Deploy Shipit configured for two organizations, `org-a` and `org-b`, each with its own `webhook_secret` (per `docs/setup.md` "Using Multiple Github Applications").
2. As an administrator of `org-a` (who legitimately possesses `org-a`'s `webhook_secret`), craft a JSON push payload:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>",
  "repository": { "owner": { "login": "org-a" }, "full_name": "org-b/target-repo" }
}
```
3. Compute `X-Hub-Signature: sha1=HMAC(webhook_secret_org_a, body)` and POST it to `/github/webhooks`.
4. `WebhooksController#verify_signature` resolves `repository_owner` = `"org-a"`, fetches `org-a`'s config, and the signature validates successfully.
5. `Shipit::Webhooks.for_event('push')` dispatches to `PushHandler`, which resolves `repository_name` = `"org-b/target-repo"` via `Handler#repository_name`, finds `org-b`'s stack, and calls `stack.sync_github(expected_head_sha: ...)` — mutating `org-b`'s stack despite the request never having been signed or authorized by `org-b`.

### Using Multiple Github Applications

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently. The top-level keys should be the name of each Github organization, and the following sub-keys are the Github app details for that particular organization.
