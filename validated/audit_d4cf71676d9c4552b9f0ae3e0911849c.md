### Title
Membership webhook lets an authenticated organization inject its members into any Team, bypassing `Shipit.github_teams` authorization - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/secret to check the HMAC signature against based on `organization.login` (or `repository.owner.login`) taken from the request body itself, i.e. it authenticates *which organization sent this event*. The `membership` handler, however, writes to a `Team` looked up purely by the numeric `github_id` from the same payload, with no check that this team actually belongs to the organization that was cryptographically authenticated. This breaks the binding "organization authenticated == team/organization written to."

### Finding Description
`verify_signature` picks the GitHub App config to validate the signature with using a payload-supplied organization identifier: [1](#0-0) [2](#0-1) 

For a `membership` event the `repository` key is absent, so `repository_owner` falls back to `params.dig('organization', 'login')`. This means the signature check only proves "this HTTP request was signed by the GitHub App installed on organization X," where X is read straight out of the attacker-suppliable JSON body.

Once verified, the event is dispatched to `MembershipHandler`, which looks up (or creates) a `Team` solely by the numeric GitHub team `id`, and unconditionally adds the named member to that team: [3](#0-2) 

Note that `Team.find_or_create_by!(github_id: params.team.id)` only sets `team.organization = params.organization.login` inside the creation block — it is **not** re-checked or updated when the team already exists. So if a `Team` record for organization B's team already exists in the database (created earlier from a legitimate `membership` webhook from organization B), and an attacker sends a forged `membership` webhook that is validly signed by *organization A's* own GitHub App (which the attacker legitimately controls, e.g. because they administer org A, one of several organizations configured under Shipit's documented multi-org support), the payload's `organization.login` will be "org A" for signature-selection purposes, but `team.id` can be set to org B's real team ID and `member.login` to the attacker's own GitHub login. The handler will find the pre-existing org-B `Team` object by `github_id` and call `team.add_member(member)`, adding the attacker as a member of org B's team — despite the request only ever being authenticated as coming from org A.

If that team is one of the entries in `Shipit.github_teams` (the configured authorization allow-list), the attacker's `User` now satisfies: [4](#0-3) 

which is exactly the check gating access to the whole application: [5](#0-4) 

This is a genuine equality-breaking analog to the report's root cause: the report's bug is "state used for the authorization check (`supportedMarkets[token]`) is not the same state consulted at withdrawal time"; here the analog is "the identity used for the signature/authentication check (`organization.login`) is not the same identity enforced when the write (`team.add_member`) is performed (`team.github_id` alone, without an organization-match assertion)."

### Impact Explanation
A user who legitimately administers, or otherwise controls a GitHub App installation for, any one of the multiple organizations configured in a shared Shipit deployment (a documented, supported configuration — see `docs/setup.md` "Using Multiple GitHub Applications") can forge a `membership` webhook that is correctly signed under their own organization's secret but targets a `Team` belonging to a *different* configured organization by numeric team ID, adding themselves as a member. If that team is part of `Shipit.github_teams`, this is a direct escalation into the application's authorization gate — the attacker gains full authenticated access to the Shipit deployment (and everything it protects: deploy/rollback triggers, stack configuration, etc.) for repositories/organizations they have no legitimate relationship with. This matches the "escalation into `Shipit.github_teams` authorization" High-impact category.

### Likelihood Explanation
Exploitability depends on: (1) the deployment using the multi-organization GitHub App configuration described in the docs, (2) the attacker legitimately controlling a GitHub App/webhook secret for at least one of the configured organizations (which requires no privilege on the *target* org, only on their own), and (3) knowing or guessing the numeric GitHub `team.id` of the target's authorized team (team IDs are sequential, discoverable via GitHub's API for teams the attacker can otherwise see, or via other org membership webhooks that leak `team.id`). Because it requires the specific multi-org configuration, likelihood is moderate rather than trivial, but no Shipit session, `ApiClient` token, or the target organization's own webhook secret is ever needed — only the attacker's own organization's legitimately-held secret.

### Recommendation
In `MembershipHandler#find_or_create_team!` / `#process`, verify that the `Team` matched by `github_id` actually belongs to `params.organization.login` before performing any mutation (`add_member`/`members.delete`); if the organization on the payload does not match the team's stored `organization`, reject the event. More generally, `WebhooksController#verify_signature` should bind the verified organization identity through to every subsequent handler, and handlers should assert that any entity they mutate belongs to that same authenticated organization rather than trusting a bare numeric ID from the payload.

### Proof of Concept
1. Shipit is configured with two organizations, `org-a` and `org-b`, each with its own GitHub App/`webhook_secret` (per `docs/setup.md` "Using Multiple Github Applications").
2. `org-b` has an authorized team `org-b/core` (`Shipit.github_teams`) with GitHub team id `999`; a `Team` row already exists in Shipit's DB with `github_id: 999, organization: "org-b"` (created from a prior legitimate membership event).
3. Attacker legitimately administers `org-a`'s GitHub App (their own org, no privilege on `org-b`) and can produce validly-signed webhook deliveries for `org-a`.
4. Attacker POSTs to `/webhooks` with header `X-Github-Event: membership`, a valid `X-Hub-Signature` computed with `org-a`'s webhook secret, and body:
```json
{
  "action": "added",
  "team": { "id": 999, "name": "core", "slug": "core", "url": "..." },
  "organization": { "login": "org-a" },
  "member": { "login": "attacker-github-login" }
}
```
5. `verify_signature` resolves `Shipit.github(organization: "org-a")` and verifies successfully (using `org-a`'s legitimately-held secret). [2](#0-1) 
6. `MembershipHandler#process` runs `Team.find_or_create_by!(github_id: 999)`, finds the pre-existing `org-b/core` team (organization field untouched since it's not a new record), and calls `team.add_member(User.find_or_create_by_login!("attacker-github-login"))`. [3](#0-2) 
7. Attacker's Shipit `User` now belongs to `org-b/core`, satisfying `User#authorized?`, and can log in and access the full Shipit instance including `org-b`'s stacks. [4](#0-3)

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e

        'Webhook from unknown organization',

        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

        def process
          team = find_or_create_team!
          member = User.find_or_create_by_login!(params.member.login)

          case params.action
          when 'added'
            team.add_member(member)
          when 'removed'
            team.members.delete(member)
          else
            raise ArgumentError, "Don't know how to perform action: `#{action.inspect}`"
          end
        end

        private

        def find_or_create_team!
          Team.find_or_create_by!(github_id: params.team.id) do |team|
            team.github_team = params.team
            team.organization = params.organization.login
          end
        end
