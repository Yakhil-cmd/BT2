### Title
Cross-repository CI status injection via unscoped `sha` lookup in `StatusHandler` - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
The `status` webhook handler binds a GitHub status update only to a commit `sha`, never to the repository/organization whose signature was verified for the incoming webhook. This breaks the binding "organization/repository that authenticated the webhook == the repository whose data is written," letting anyone who controls a repo wired to this Shipit instance inject a fake commit status onto a commit that belongs to a completely different stack/repository, as long as the SHA happens to match (e.g. via a public fork sharing git history).

### Finding Description
`WebhooksController#verify_signature` selects the signing app/secret based on `repository_owner` taken from the payload (`repository.owner.login`, falling back to `organization.login`) and only checks that the raw body's HMAC matches that organization's secret: [1](#0-0) [2](#0-1) 

Once verified, the controller dispatches the entire raw payload to every registered handler for the event type, without re-checking that the payload's `repository` field is the one that was actually authenticated: [3](#0-2) 

Most handlers correctly scope their side effects by resolving `Repository.from_github_repo_name(repository_name)` from `payload.dig('repository', 'full_name')` before touching any state, via the base `Handler#stacks` helper: [4](#0-3) 

`StatusHandler`, however, never calls `stacks` and never checks `repository`/`repository_owner` at all. It looks up commits **globally by `sha` alone**, across every stack/repository tracked by this Shipit install: [5](#0-4) 

`Commit#create_status_from_github!` then unconditionally records the attacker-supplied state/description/target_url as a real status on that commit: [6](#0-5) 

So the equality that should hold — *organization/repository whose webhook signature was verified == repository whose commit gets a new status* — is broken: the signature only proves the sender is an authenticated organization for **some** repository, but the write path (`Commit.where(sha: params.sha)`) is keyed purely on the SHA value, which is attacker-controlled input from the JSON body and not covered by any check that it belongs to the signing organization's repository.

### Impact Explanation
Git commit SHAs are content-addressed, so identical commits (and therefore identical SHAs) exist across a public repository and any fork of it. An attacker who owns or administers a fork of a repository tracked by a Shipit stack (or any repo whose org is a recognized/authenticated webhook sender for this Shipit instance) can send a `status` event referencing a SHA that is shared with the upstream/target stack's commit. Because `StatusHandler` never validates that the SHA belongs to the repository the signature authenticated for, it will happily create a `success` status on the victim stack's commit via `commit.create_status_from_github!`. `Commit#deployable?`/`#status` and continuous-delivery scheduling (`schedule_continuous_delivery`) rely on aggregated statuses, so a forged "success" status can help make an otherwise-unverified or CI-failing commit appear deployable, contributing to an unauthorized deploy of that stack — matching the High-impact category "escalation into ... unauthorized deploy."

### Likelihood Explanation
This does not require a Shipit session, API token, or any privileged Shipit-side credential — only the ability to have a GitHub webhook from a recognized organization deliver a `status` event (e.g. by owning/administering a fork of a public repo tracked as a stack, or any org already wired for webhooks to this instance) and knowledge of a target commit SHA, which is public information for any public repository. This is a purely code-level omission (missing repository scoping in one specific handler while every sibling handler enforces it), making it a concrete, reachable analog rather than theoretical.

### Recommendation
In `StatusHandler#process`, scope the lookup by the authenticated repository, mirroring the base `Handler#stacks` pattern used by `PushHandler` and `CheckSuiteHandler`, e.g. restrict to `stacks.flat_map(&:commits).where(sha: params.sha)` (or add a `repository_id`/`stack_id` filter derived from `payload.dig('repository', 'full_name')`) so a commit status can only be written for commits belonging to the repository that was actually verified for this webhook delivery.

### Proof of Concept
1. Repository `victim/app` is tracked by Shipit as a stack; it has a commit with SHA `abc123...`.
2. Attacker forks `victim/app` into their own org `attacker-org/app-fork`, which retains the identical commit `abc123...` due to git's content-addressed history, and configures/owns a GitHub App/webhook installation on `attacker-org` that this Shipit instance recognizes (`Shipit.github(organization: 'attacker-org')` resolves successfully).
3. Attacker triggers (or crafts, if their integration allows arbitrary status pushes) a `status` webhook event from `attacker-org` with `sha: "abc123..."`, `state: "success"`, pointing to `repository.full_name: "attacker-org/app-fork"`.
4. `WebhooksController#verify_signature` validates the HMAC against `attacker-org`'s secret and passes — this only proves the sender is `attacker-org`, not that the SHA belongs to a repo `attacker-org` owns in Shipit's records.
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)`, which matches the commit in `victim/app`'s stack, and calls `commit.create_status_from_github!(params)`, writing a fabricated `success` status onto `victim/app`'s commit — even though `victim/app`'s organization/webhook was never involved in this request.

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```
