### Title
Reachable Assertion (`throw Error(...)`) in oscript Formula Evaluation Causes Full-Node Crash - (File: formula/evaluation.js)

### Finding Description
CVE-2022-0865 describes a *reachable assertion* in `tiffcp`: a crafted, syntactically-valid but semantically unusual input drives the program into an internal `assert()` that was written on the assumption "this state can never happen," causing the process to abort. `ocore` uses the same pattern throughout its codebase: `throw Error(...)` calls placed at points the author believed were logically unreachable (`"unreachable code, conflicting ..."`, `"AA definition not found ..."`, etc.). These are not caught locally — they propagate up as unhandled/uncaught exceptions.

The most attacker-reachable instance of this pattern is in `formula/evaluation.js`, the oscript interpreter that every full node runs to evaluate an Autonomous Agent's `messages`/`state`/`init` formulas whenever an AA is triggered by *any* posted unit (i.e., anyone can send a payment/message to an AA address to fire evaluation of AA-author-supplied oscript). The evaluator contains dozens of `throw Error(...)` statements (49 in this file) guarding conditions the implementer assumed were impossible given prior validation (`aa_validation.js`) — e.g. unexpected AST node shapes, unexpected operand type combinations, or state inconsistencies reached only through specific arrangements of nested formulas, remote AA calls (`response_or_state`), or bounce responses. Unlike the ordinary error-callback path used for "expected" validation failures during evaluation (which safely bounces the trigger without crashing), these `throw Error(...)` sites bypass that path entirely.

Because `network.js` installs a global `process.on('uncaughtException', ...)` handler that deliberately re-throws to kill the process (`network.js:4530-4543`, "crash the process to avoid ending up in an inconsistent state"), any oscript formula (embedded in an AA definition, or in a template/parameterized AA reachable via `base_aa`/`params`) that manages to steer the evaluator into one of these "impossible" branches will crash every full node that processes the triggering unit, not just the attacker's own node.

### Impact Explanation
A crash triggered during AA-trigger evaluation is not confined to one node: every full node that receives and evaluates the same triggering unit (which is required for consensus on the AA's output) hits the identical code path and the identical `throw`. This can:
- Take down witness/full nodes network-wide when they attempt to process the poisoned trigger, matching the "network unable to confirm new units" acceptance criterion.
- Cause disagreement/instability if some nodes crash before writing the resulting bounce/response unit while others (with different code versions or timing) succeed, risking a stability/validity split.

This is reachable by anyone able to define an AA (permissionless) and send a trigger unit to it (also permissionless) — no privileged network position, hub role, or key leak is required, distinguishing it from excluded classes such as malicious-peer/network-DoS bugs.

### Likelihood Explanation
`aa_validation.js` performs a great deal of static checking on an AA definition before allowing it to be installed, and `formula/validation.js` restricts the oscript grammar. However, both files are large, hand-written allow-lists, and the sheer number of `throw Error(...)` "impossible" invariants in `formula/evaluation.js` indicates the runtime evaluator's assumptions are broader than what pre-validation actually guarantees. Historically this exact class of bug (validator not fully agreeing with the runtime evaluator's assumptions) is a common source of reachable-assertion crashes in interpreters, and the sheer count of unguarded `throw` sites here makes accidental or deliberate triggering plausible with a sufficiently creative combination of nested expressions, remote AA state reads, or bounce/response interactions. Concretely proving one specific formula that reaches one specific `throw` requires enumerating and exercising the AST evaluator branch-by-branch, which was not completed in this pass.

### Recommendation
- Audit every `throw Error(...)` in `formula/evaluation.js` (and the analogous sites in `validation.js`, `aa_composer.js`, `writer.js`) that is reachable during processing of externally-supplied data (units, triggers, formulas). For each one, either prove it truly unreachable given the current `aa_validation.js`/`formula/validation.js` checks (and add a regression test that attempts to reach it), or convert it into a graceful `bounce`/`ifError` path instead of an uncaught `throw`.
- Consider hardening `process.on('uncaughtException', ...)` in `network.js` so that formula-evaluation errors during AA trigger handling are caught and turned into a bounced trigger response rather than a full process crash, isolating the fault to the single trigger instead of killing the node.
- Add fuzzing of the oscript evaluator (feeding syntactically-valid but adversarial ASTs) to find inputs that hit the "impossible" throws before they reach production.
