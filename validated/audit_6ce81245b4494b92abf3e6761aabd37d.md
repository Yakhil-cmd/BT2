### Title
Webhook signature verified for one GitHub organization is used to authorize writes to any organization's repository/commit — cross-repository status/commit forgery via `Shipit::Webhooks::Handlers::StatusHandler` — (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/handler.rb`, `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`WebhooksController#verify_signature` selects the HMAC secret to check against using the organization derived from the *payload itself* (`repository.owner.login` or `organization.login`), then hands the *entire parsed JSON payload* to event handlers unmodified. Handlers such as `StatusHandler` and `Handler#stacks` then act on repository/commit identifiers taken from other fields of that same untrusted payload (`repository.full_name`, or, for `StatusHandler`, no repository scoping at all — just a bare `sha`). Nothing enforces that the organization whose secret validated the signature is the same organization/repository the handler subsequently writes to. In a multi-org Shipit deployment, an attacker who legitimately administers their own configured GitHub org (and therefore knows/controls that org's webhook secret) can forge a signed webhook whose "owner" field matches their own org but whose actual target (full repository name, or raw commit sha) belongs to a different, victim organization tracked by the same Shipit instance.

### Finding Description
`WebhooksController#verify_signature` picks the `GitHubApp` (and thus the webhook secret) to validate against based on payload content: [1](#0-0) [2](#0-1) 

`repository_owner` is read straight out of the attacker-supplied JSON body (`params.dig('repository', 'owner', 'login')` or `params.dig('organization', 'login')`), not from any cryptographically-verified source at that point — verification happens *after* this field is extracted, using it to select which secret to check against.

`Shipit.github(organization:)` looks up the per-organization config keyed by that same attacker-supplied string in the documented multi-org configuration: [3](#0-2) 

`GitHubApp#verify_webhook_signature` only compares the signature against the secret configured for the resolved organization: [4](#0-3) 

Once verification passes (using the *attacker's own org's* secret), the raw payload is dispatched unchanged to every registered handler: [5](#0-4) 

Handlers resolve the actual repository/stack to act on from a *different* payload field, `repository.full_name`, which is never cross-checked against `repository.owner.login`/the field used for signature selection: [6](#0-5) 

`StatusHandler` is worse: it performs **no repository scoping whatsoever** and looks up commits by `sha` alone, globally across the entire Shipit instance (all orgs, all repos, all stacks): [7](#0-6) 

The broken equality is: *"organization whose secret authenticated the request" == "organization/repository/commit the handler subsequently writes to"*. The engine only checks the left-hand side; the right-hand side is taken from unauthenticated-with-respect-to-that-binding payload data.

`Status` records created this way feed directly into CI/deploy gating logic (`enable_ci_on_stack`, `schedule_continuous_delivery`): [8](#0-7) [9](#0-8) 

### Impact Explanation
In the documented multi-organization configuration (`docs/setup.md` "Using Multiple Github Applications", `config/secrets.development.shopify.yml`), each org has its own independent `webhook_secret`. An attacker who legitimately controls (and has installed the Shipit GitHub App on) one configured org, "org-A", can:
1. Compute a valid `X-Hub-Signature` using org-A's own known webhook secret.
2. Set `repository.owner.login`/`organization.login` = "org-A" so `verify_signature` validates against org-A's secret and passes.
3. Set the `sha`/`repository.full_name` fields to reference a commit/repository belonging to victim org-B, which is also tracked by the same Shipit instance.

Because `StatusHandler` performs zero repository scoping, the attacker can inject a forged `success` commit status onto *any* commit sha tracked anywhere in the Shipit install, including org-B's commits. Since `Status` creation drives `enable_ci_on_stack` and `schedule_continuous_delivery`, this can cause Shipit to treat a commit that never actually passed CI as deployable/mergeable, resulting in an unauthorized deploy — matching the "High: unauthorized deploy" impact category. Other handlers relying on `Handler#repository_name` (full_name) similarly let org-A's signature authorize actions (push-triggered sync, PR label/merge handling) against org-B's stacks.

### Likelihood Explanation
Exploitability requires only that the target Shipit instance is configured with the documented multi-organization GitHub setup and that the attacker legitimately administers at least one of the configured orgs (a low, self-service bar — they only need to install the App on their own org, not gain any privilege in the victim org). No compromise of the victim's credentials, GitHub App, or Shipit session is required; the webhook endpoint is unauthenticated by design (it relies solely on signature verification), and the identifier used for signature selection is never bound to the identifier used for the actual write.

### Recommendation
- In `WebhooksController#verify_signature`, after resolving `repository_owner` and validating the signature, re-validate that every organization-identifying field elsewhere in the payload (`repository.full_name`'s owner segment, `organization.login`) is consistent with `repository_owner`; reject on mismatch.
- In `Shipit::Webhooks::Handlers::Handler`/`StatusHandler`, scope all lookups (commits, stacks, repositories) by the verified organization/repository, not by unscoped fields like a bare `sha`. `StatusHandler` in particular must join through `Repository`/`Stack` filtered by the verified owner rather than querying `Commit.where(sha:)` globally.

### Proof of Concept
1. Configure Shipit with two organizations, `org-a` and `org-b`, each with its own `webhook_secret` (per `docs/setup.md` multi-org setup).
2. As an attacker who administers `org-a` (and thus knows `org-a`'s webhook secret), build a `status` event payload:
```json
{
  "sha": "<victim commit sha belonging to org-b/repo>",
  "state": "success",
  "context": "ci/forged",
  "repository": { "owner": { "login": "org-a" }, "full_name": "org-a/some-repo" }
}
```
3. Compute `X-Hub-Signature: sha1=HMAC-SHA1(org-a's webhook_secret, raw_body)` and POST to `/webhooks` with `X-Github-Event: status`.
4. `WebhooksController#verify_signature` resolves `repository_owner` = `org-a`, validates against `org-a`'s secret — passes. [1](#0-0) 
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)`, which matches the victim commit belonging to `org-b`, and creates a forged `success` status on it, regardless of the `repository` field used for authentication. [7](#0-6)

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
