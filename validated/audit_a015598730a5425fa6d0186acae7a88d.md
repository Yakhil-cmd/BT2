### Title
Webhook signature is verified against the organization named in `repository.owner.login`, but the event is processed against the repository named in `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App / webhook secret to validate a delivery against using one field of the untrusted JSON payload, while the downstream handler layer resolves which `Stack`/`Repository` the event actually mutates using a *different* field of the same payload. These two fields are never cross-checked, so a payload that is correctly signed for organization A can be crafted to act on a repository belonging to organization B.

### Finding Description
`verify_signature` picks the GitHub App config to validate the HMAC against solely from the attacker-controlled body: [1](#0-0) [2](#0-1) 

`repository_owner` is read from `params.dig('repository', 'owner', 'login')` (falling back to `organization.login`). `Shipit.github(organization: repository_owner)` then looks up that organization's `webhook_secret` from `secrets.github` and checks the `X-Hub-Signature` against it: [3](#0-2) 

Once the signature check passes, the actual event payload is handed to a handler such as `PushHandler`, `StatusHandler`, or `CheckSuiteHandler`. These handlers resolve which `Stack` to touch via `Handler#stacks`, which uses a **different** payload field, `repository.full_name`: [4](#0-3) 

Because `repository.owner.login` (used to pick the verifying secret) and `repository.full_name` (used to resolve the target stack) are independent, attacker-controlled JSON fields, they are never required to agree. An attacker who legitimately configures their own GitHub organization/App in a multi-tenant Shipit deployment (`Shipit.github_organizations`, `github_app_config`) possesses a valid `webhook_secret` for their own organization. They can sign a payload with `repository.owner.login = "attacker-org"` (so `verify_signature` selects and validates against the attacker's own legitimate secret) while setting `repository.full_name = "victim-org/victim-repo"`, causing `Handler#stacks` to resolve and act on a completely unrelated stack that belongs to another organization.

The `status` event handler is the most consequential target: it persists `state`, `target_url`, `description`, and `context` verbatim from the payload onto the resolved commit, as confirmed by the existing controller test: [5](#0-4) 

This is the binding-break pattern called out in the rules: **the organization that authenticated (via signature) is not the same as the repository that is written to** — analogous to the Sherlock report's mismatch between the entry accounting and the exit accounting for the same LP position.

### Impact Explanation
By forging a `status` webhook signed with their own organization's webhook secret but naming a victim stack's commit (`sha`) in an unrelated `repository.full_name`, an attacker can set an arbitrary CI status (e.g. `state: success`) on a commit belonging to another team's stack. If that stack's deploy flow or merge queue gates on required statuses/checks, this allows bypassing CI gating and triggering an **unauthorized deploy or merge** — one of the accepted Critical/High impacts. It also allows forcing spurious `GithubSyncJob`/`RefreshCheckRunsJob` runs against arbitrary stacks via forged `push`/`check_suite` events.

### Likelihood Explanation
Requires only that the attacker control (or have legitimately configured) one organization's webhook secret within the same multi-tenant Shipit deployment — not the victim's secret, not `GITHUB_TOKEN`, not an `ApiClient` token, and not repository write access to the victim repo. This is a low bar in any Shipit instance onboarding multiple organizations/repositories, since each org's secret only needs to authenticate the delivery, not the target repository named in the body.

### Recommendation
After `verify_signature` succeeds, re-derive the repository/stack to act on using the **same** trust-bound organization that was used to select the webhook secret (e.g., require that `repository.full_name`'s owner segment equals the verified `repository_owner`/`organization.login`), and reject the payload otherwise. Alternatively, look up the `GithubHook` record matching the `stack_id`/`github_id` embedded in the delivery instead of trusting the payload's `owner.login` for secret selection while trusting `full_name` for target resolution.

### Proof of Concept
1. Attacker configures organization `attacker-org` in a multi-tenant Shipit instance (`secrets.github[:attacker-org][:webhook_secret] = S`), a normal, unprivileged onboarding action.
2. Attacker crafts a `status` event JSON body:
```json
{
  "sha": "<victim commit sha, known via public GitHub or Shipit UI>",
  "state": "success",
  "target_url": "https://ci.example.com/1",
  "description": "forged",
  "context": "ci/required-check",
  "repository": { "full_name": "victim-org/victim-repo", "owner": { "login": "attacker-org" } }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC(S, body)` and POSTs to `/github/webhooks`.
4. `verify_signature` calls `Shipit.github(organization: "attacker-org")` and validates successfully against `attacker-org`'s secret (`app/controllers/shipit/webhooks_controller.rb:24-30`).
5. `StatusHandler` resolves the target stack via `repository.full_name = "victim-org/victim-repo"` (`app/models/shipit/webhooks/handlers/handler.rb:32-38`) and persists the forged `success` status on the victim's commit, independent of the organization that actually authenticated the request.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
