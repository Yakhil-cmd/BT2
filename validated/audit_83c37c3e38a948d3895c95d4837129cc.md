### Title
Missing Duplicate-Signer Check in `r of set` / `weighted and` Address Definitions Allows a Single Key to Satisfy a Multi-Signer Threshold - ([File: definition.js])

### Summary
The `oracle.fc` report describes a threshold-bypass bug: because duplicate signatures were not detected, one signer could count multiple times toward a threshold that was intended to require several independent signers. The same bug class exists in ocore's generic address-definition engine. `validateDefinition()` and `validateAuthentifiers()` in `definition.js` never check whether the same public key (or address) is repeated across the branches of an `r of set` or `weighted and` expression, and signature validation is done per-path, independently, with no cross-path deduplication.

### Finding Description
When an address is defined with a threshold-style expression such as:
```
["r of set", {required: 2, set: [["sig",{pubkey:A}], ["sig",{pubkey:A}], ["sig",{pubkey:B}]]}]
```
`validateDefinition()` (definition.js, `case 'r of set'`, [1](#0-0) ) only checks structural properties of the set (`required` is a positive integer ≤ `set.length`, `set.length >= 2`, each branch has a signature). It never checks whether two branches reference the same `pubkey`/`address`, so a set with a duplicated key passes definition validation.

At authentication time, `validateAuthentifiers()`'s `case 'r of set'` (definition.js, [2](#0-1) ) simply iterates over `args.set`, evaluates each branch at its own path, and increments `count` for every branch that returns true, then checks `count >= args.required`. The `case 'sig'` handler ( [3](#0-2) ) verifies the signature at `path` against `args.pubkey` using `ecdsaSig.verify`, with no tracking of which underlying key/signer already contributed. Because the "sig" op for pubkey `A` appears at two different paths (e.g. `r.0` and `r.1`), a single holder of the private key for `A` can supply the *same* valid signature value at both paths (the signed message/unit hash is identical for all authentifiers in one unit), so `count` reaches 2 even though only one real signer participated. The `weighted and` branch (definition.js, [4](#0-3)  for evaluation and [5](#0-4)  for definition validation) has the identical weakness: weight is summed per branch with no de-duplication of the underlying signer/key.

This directly parallels the oracle bug: the intended security property ("N independent signers must approve") is undermined because duplicate/repeated authorizers are counted as separate approvals.

### Impact Explanation
Threshold multi-sig constructs (`r of set`, `weighted and`) are a core, widely-used ocore primitive for shared wallets, escrow/arbiter-style contracts, and any AA- or user-defined address that is supposed to require cooperation of several distinct keys (e.g., 2-of-3 multisig wallets built via `wallet_defined_by_keys.js`'s `createMultisigWallet()`, which builds exactly `["r of set", {required: N, set: [...]}]` from a list of member pubkeys, [6](#0-5) ). If an attacker (either the address creator or anyone able to influence which pubkeys are included, e.g. in a shared-address template negotiation) inserts the same signer's pubkey into multiple branches of the set, that single signer can unilaterally satisfy what other participants believe is a genuine multi-party threshold, allowing unauthorized spending of funds held at that address without the cooperation of the other intended co-signers — a fund-loss / unauthorized-spending impact.

### Likelihood Explanation
Exploitation requires the malicious definition (with a duplicated key) to actually be adopted as the address definition that other parties trust to enforce N-of-M control — e.g., a dishonest party in a shared-address negotiation (`wallet_defined_by_addresses.js`) proposing a definition where their own key occupies two "independent" slots, or a broken template-generation path that unintentionally repeats a signer. This is reachable by any unprivileged user constructing/signing an address definition or shared-address template; no special network/node privilege is needed. Likelihood is Medium: it requires a specific misuse pattern (getting counterparties to accept a definition with a hidden duplicate key) rather than being automatically triggerable against arbitrary existing multisig addresses, but the validation code provides no defense-in-depth against it at all.

### Recommendation
In `definition.js`, when validating `'r of set'` and `'weighted and'` (and any other counting construct), track the set of distinct `pubkey`/`address` identifiers actually used to satisfy each branch and require that `count`/`weight` only be accumulated from branches backed by distinct underlying signer keys/addresses (mirroring the oracle fix recommendation of sorting/deduplicating by key). At minimum, `validateDefinition()` should reject `r of set` and `weighted and` definitions whose `set` contains structurally identical branches (same `sig`/`hash`/`address` leaf) so duplicate keys cannot be introduced in the first place.

### Proof of Concept
1. Attacker (as one of the intended co-signers of a "2-of-3" shared address) proposes/derives the shared-address definition:
   `["r of set", {required: 2, set: [["sig",{pubkey: attacker_pubkey}], ["sig",{pubkey: attacker_pubkey}], ["sig",{pubkey: honest_pubkey}]]}]`
   This passes `validateDefinition()` because each branch independently satisfies "has at least 2 options" / "each branch has a signature", with no duplicate-key check (definition.js:147-184).
2. The resulting address is accepted by counterparties as address_chash = `objectHash.getChash160(arrDefinition)`.
3. To spend, the attacker signs the unit hash once with `attacker_pubkey`'s private key and places that identical signature string under authentifier paths `r.0` and `r.1`.
4. `validateAuthentifiers()`'s `'r of set'` handler (definition.js:692-711) evaluates `r.0` → true, `r.1` → true (both verify against the same valid signature and pubkey), `count = 2 >= required(2)`, and the unit is accepted — allowing the attacker to move funds without the honest co-signer's participation.
