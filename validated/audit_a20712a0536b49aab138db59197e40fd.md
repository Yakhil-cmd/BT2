## Analysis



The controller responsible for all inbound GitHub events is `Shipit::WebhooksController`. It selects the webhook secret to validate against using a value taken from the JSON body, then dispatches to handlers that act on other fields of that same body: [1](#0-0) [2](#0-1) 

`Shipit.github(organization: repository_owner)` looks up the App/secret configured for whatever organization name is embedded in `params['repository']['owner']['login']` (or `params['organization']['login']`), per the documented multi-org configuration: [3](#0-2) 

The HMAC itself (`X-Hub-Signature`) only proves that *someone who knows that organization's `webhook_secret`* produced the raw body — it says nothing about which repository the payload claims to describe. `verify_webhook_signature` just does an HMAC/secure-compare over the raw bytes: [4](#0-3) 

Since the organization used to pick the secret (`repository_owner`) and the repository/stack that handlers subsequently mutate are read from two independent fields of the same attacker-controlled JSON, nothing forces them to refer to the same tenant. This is the exact structural analog of the reported bug: a value trusted at the authorization boundary (`repository_owner` → secret selection) is not the same value bound by the cryptographic check as the value acted upon later (`repository.full_name`, PR `head`/`base` shas, commit shas used to create/update `Commit`, `Status`, `MergeRequest`, `Stack` records via `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`).

### Title
Webhook signature verification is keyed on an unauthenticated field, allowing any org owning a configured GitHub App to forge events for other orgs' repositories - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which organization's webhook secret to validate the HMAC signature against using `repository_owner`, a value read directly out of the still-unverified JSON payload. Once the signature check passes (using that organization's own legitimately-known secret), the same payload is handed unmodified to event handlers that read a different field (`repository.full_name`, PR/commit SHAs) to decide which `Stack`/`Commit`/`Status`/`MergeRequest` records to create or mutate — with no re-check that this second field belongs to the organization whose secret validated the request.

### Finding Description
Shipit explicitly supports hosting multiple GitHub Organizations from one instance, each with its own GitHub App and `webhook_secret`, configured under `github.<org_name>.webhook_secret` [3](#0-2) . `Shipit.github(organization:)` is the mechanism that resolves per-organization credentials, and `verify_signature` calls it with the org name extracted from the request body itself, not from any pre-authenticated source such as TLS client identity or a validated App installation callback: [5](#0-4) 

The binding this breaks: `organization authenticated by HMAC == organization owning repository written by handlers`. Before the request: the attacker (an org admin who legitimately owns their own GitHub App/organization "OrgA" registered in this multi-tenant Shipit's `secrets.yml`) knows OrgA's `webhook_secret` because they configured it. After: they can POST directly to `/webhooks` (bypassing GitHub) with `repository.owner.login = "OrgA"` (so `verify_signature` fetches and validates against the secret they know) but with `repository.full_name`, PR numbers, and commit SHAs pointing at a completely different, victim-owned repository/stack ("OrgB/victim-repo") tracked by the same Shipit instance. `verify_webhook_signature` only proves the bytes were signed with OrgA's secret [4](#0-3) ; it says nothing about which repository the payload's business fields describe. The dispatched handlers (`push`, `status`, `pull_request`, `check_suite`, etc.) then act on those unrelated fields via `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` [6](#0-5)  to locate/mutate `Stack`, `Commit`, `Status`, and `MergeRequest` records that belong to OrgB, e.g. flipping commit statuses or driving merge-request state (`MergeRequest#refresh!`, `github_pull_request=`) using SHAs and repository names the attacker fully controls [7](#0-6) .

### Impact Explanation
This crosses the "cross-repository writes" impact bar explicitly listed as Critical: an attacker who only administers their own low-trust organization's GitHub App (a routine, unprivileged onboarding action for a multi-tenant Shipit deployment) can forge webhook events that are accepted as authentic and used to write state (commit statuses, merge-request status transitions, stack sync triggers) for repositories/organizations they do not own or have access to.

### Likelihood Explanation
Any deployment following the documented "Using Multiple Github Applications" multi-tenant setup is affected. No repository write access, GITHUB_TOKEN, or `api_clients_secret` is required — only knowledge of a webhook secret for any one organization configured on the instance, which is trivially available to that organization's own (unprivileged, relative to other tenants) GitHub App owner. This is a direct request-forgery, not a race condition or resource-exhaustion issue, so it is excluded from the DoS carve-out.

### Recommendation
Bind the value used to select the verification secret to the same value the handlers act on: after resolving `github_app` via `repository_owner`, re-validate that every repository/organization reference inside the payload (`repository.full_name`, `repository.owner.login`, any nested `pull_request.base.repo`/`head.repo`) belongs to that same verified organization before dispatching to handlers, rejecting (422) any payload with inconsistent organization references.

### Proof of Concept
1. Deploy Shipit configured for two organizations, `OrgA` and `OrgB`, per `docs/setup.md` multi-app instructions, each with its own `webhook_secret`.
2. As the administrator of `OrgA`'s own GitHub App (an action requiring no privilege on `OrgB`), compute `sha1=HMAC(OrgA_webhook_secret, body)` for a crafted `status` payload where `repository.owner.login = "OrgA"` but `repository.full_name = "OrgB/victim-repo"` and `sha` refers to a real commit on an `OrgB`-owned stack.
3. `POST /webhooks` with header `X-Github-Event: status` and `X-Hub-Signature` set to the computed value.
4. `verify_signature` resolves `Shipit.github(organization: "OrgA")`, validates the signature successfully (since it was signed with the known `OrgA` secret over these exact bytes), and `StatusHandler` proceeds to create a `Status` on the commit belonging to `OrgB/victim-repo` even though the requester never proved any relationship with `OrgB`.

```ruby
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
