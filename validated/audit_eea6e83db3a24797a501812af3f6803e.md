### Title
Cross-repository commit status forgery via SHA-only lookup in `StatusHandler` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
The webhook signature verification binds a request only to the *organization* named in the payload's `repository.owner.login`/`organization.login` field, but `Shipit::Webhooks::Handlers::StatusHandler` never re-checks that binding when deciding which `Commit` row to mutate — it looks the commit up by `sha` alone, across the entire `commits` table, regardless of which repository/organization the verified webhook belongs to.

### Finding Description
`WebhooksController#verify_signature` picks the GitHub App/secret to validate the HMAC against using only the payload-derived organization: [1](#0-0) [2](#0-1) 

Once the signature is accepted, `create` dispatches the entire JSON payload to the registered handler for the event type: [3](#0-2) 

For `status` events, `StatusHandler#process` resolves the target record purely by `sha`, with no scoping to the repository/organization that the signature was actually verified for: [4](#0-3) 

Every other handler in the engine derives its scope from `payload.dig('repository', 'full_name')` via `Handler#repository_name`/`#stacks`: [5](#0-4) [6](#0-5) 

`StatusHandler` is the outlier: it does not inherit this repository-scoped lookup and instead queries `Commit.where(sha: params.sha)` globally, so any commit in *any* stack/repository tracked by the Shipit instance that shares the same SHA as the one named in the (correctly-signed) webhook will have its status updated.

The binding broken is: **organization that authenticated the webhook == repository whose commit is written**. The signature only proves "this payload came from GitHub for organization/repo X's installed app," but the actual write (`commit.create_status_from_github!`) is applied to whichever `Commit` row matches the SHA, with no assertion that the commit belongs to the repository named in the same payload.

Git SHAs are content-addressed, so an attacker who legitimately owns/administers *any* repository onboarded to the same multi-tenant Shipit instance (a normal, low-privilege scenario for Shipit, which is designed to serve many orgs/repos) can:
1. Identify a target commit SHA in a *different*, unrelated tracked repository/stack (commit SHAs are public on GitHub).
2. Reproduce an identical commit object (same tree, parents, author/committer identity and timestamps, message) in their own repository — trivial when the target commit is a shared/mirrored/forked commit, or when the attacker cherry-picks/rebases to reconstruct the exact same commit — producing the identical SHA1.
3. Cause GitHub to fire a genuine, correctly-signed `status` webhook for *their own* repository/org referencing that SHA (e.g. by setting a commit status via the GitHub API on their own repo, which they are fully authorized to do).
4. Shipit verifies the signature against the attacker's own org's webhook secret (valid), then `StatusHandler` updates the status of the SHA-matching `Commit` belonging to the *unrelated victim stack*.

### Impact Explanation
Commit statuses drive Shipit's deployability checks (`ci.require` gating, continuous-deployment triggers). Forging a "success" status on an unrelated organization's commit can unblock/trigger continuous delivery or otherwise manipulate deploy-gating logic for a stack the attacker has no legitimate access to — an unauthorized cross-repository state change that can lead to an unauthorized deploy. This satisfies the "cross-repository writes" / "unauthorized deploy" high-impact bar, without requiring an `ApiClient` token, session, or `webhook_secret`/GitHub App key belonging to the victim organization — only requiring the attacker's own legitimately-provisioned org/webhook secret.

### Likelihood Explanation
Requires the attacker to control a repository/org already registered with the same Shipit instance (realistic for Shipit's typical multi-tenant deployment model) and to be able to reproduce an identical commit SHA in that repository — feasible when commits are shared across forks/mirrors, or reconstructible bit-for-bit. This is a non-trivial but concrete precondition rather than a theoretical one; the root cause (missing repository scoping in `StatusHandler`, in contrast to every other handler) is a clear code-level bug.

### Recommendation
Scope `StatusHandler#process` to commits belonging to the repository named in the webhook payload (as the other handlers do via `repository_name`/`stacks`), e.g. filter `Commit.where(sha: params.sha)` further by `commit.stack.repository == Repository.from_github_repo_name(repository_name)` before calling `create_status_from_github!`.

### Proof of Concept
Not independently executable from static analysis alone (requires live GitHub App configs for two orgs plus a reproduced-SHA commit); the code-path proof is:
1. Register two orgs/webhook secrets in Shipit, each tracking a different repository/stack.
2. Push an identical commit object (same tree/parents/authorship/timestamps ⇒ same SHA) to both repositories, or reuse a shared/forked commit that already exists in both.
3. From org B, trigger/forge a `status` webhook (`state: success`) for that shared SHA; the request is correctly HMAC-signed with org B's `webhook_secret`.
4. Observe `StatusHandler#process` — `Commit.where(sha: params.sha)` — updates the status on the org-A commit as well, since the lookup in [4](#0-3)  has no repository filter, unlike [5](#0-4) .
