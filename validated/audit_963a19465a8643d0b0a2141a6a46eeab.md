### Title
Replayable L1 Bitcoin Lockup Proof Enables Double-Counted sBTC Collateral in `register-for-bond` - ([File: stackslib/src/chainstate/stacks/boot/pox-5.clar])

### Summary
`register-for-bond` accepts a Bitcoin SPV proof of a BTC timelock output as collateral for a protocol bond, but the contract never persists which lockup outpoints (`txid`, `output-index`) have already been consumed. The only duplicate-check is a per-call, in-memory list (`seen-outpoints`) that only prevents the same outpoint being counted twice *within a single transaction*. Nothing stops the exact same on-chain BTC lockup transaction from being submitted again in a later, separate `register-for-bond` call for a different (non-overlapping) `bond-index`.

### Finding Description
`verify-l1-lockups` folds over the caller-supplied list of BTC outputs with `validate-l1-lockup`, which builds a `seen-outpoints` accumulator scoped to the single fold call: [1](#0-0) 

The dedup check only queries this transient list, never a contract-level map: [2](#0-1) 

The only other validations are that the SPV proof is genuine (script/amount/merkle-root/header) and that `unlock-burn-height >= minimum-unlock-height` for the *bond being registered*: [3](#0-2) 

In `register-for-bond`, the L1 path computes `sats-total` from `verify-l1-lockups` and credits it as `new-sbtc`/`sats-total` into the new bond's per-cycle share accounting (`protocol-bonds-total-staked`, `add-staker-to-bond-cycles`, `add-staker-to-signer-cycles`) without any check that this same outpoint backed a *previous* bond registration for that staker: [4](#0-3) [5](#0-4) 

The only guard against re-registering is `bond-overlaps-new-position?`, which only checks that the *staker's own reward-cycle windows* don't overlap — it says nothing about the underlying BTC UTXO being distinct: [6](#0-5) 

Critically, when a staker rolls from an ending bond into a new one, the *prior* bond's recorded `protocol-bonds-total-staked` and per-cycle shares are intentionally **not** torn down — the code comment and test confirm the old bond's shares are "preserved" through its remaining cycles: [7](#0-6) 

This is correct/expected for the sBTC path, because `roll-sbtc` moves real, contract-custodied sBTC balances and nets the delta: [8](#0-7) 

But for the L1 path, `old-sbtc`/`new-sbtc` are both `0` (the contract never custodies anything for L1 locks), so `roll-sbtc` moves nothing, and there is no on-chain artifact that ties the new bond's credited `sats-total` to a *fresh* BTC lock. The same physical, still-unspent Bitcoin UTXO — provided its `unlock-burn-height` happens to satisfy the new bond's `minimum-unlock-height` — can be re-submitted as proof for bond N, then again later for bond N+6, N+12, etc., each time crediting `sats-total` sats' worth of reward shares to a *different* bond's pool, while only one BTC UTXO was ever actually locked.

### Impact Explanation
This breaks the equality "sats credited by an L1 proof == sats actually locked on Bitcoin, once." Each additional bond registered on the same replayed outpoint mints new reward-share claims (`bondSignerSharesForCycle`/`bondStakerSharesForCycle`, and downstream `calculate-rewards` distributions) backed by zero incremental BTC. Because `calculate-rewards` allocates sBTC-denominated protocol rewards proportionally to recorded staked sats per bond/cycle, this results in unbacked sBTC reward minting for the attacker at the expense of other honest stakers/signers sharing the same reward pool — a double-counted commitment producing rewards that were never earned by newly-locked collateral. This is a Critical-severity impact per the rules ("double-counting a commitment or reward", "sats credited by an L1 proof that were never locked on Bitcoin").

### Likelihood Explanation
Exploitation requires only an unprivileged staker with a single BTC timelock output whose `unlock-burn-height` is far enough in the future to satisfy several successive bonds' `minimum-unlock-height` requirements (easily arranged by locking with a long timelock up front). No admin, miner, or other user's key is required — the staker simply waits for each bond's rollover window (`verify-bond-rollover-window`) and resubmits the identical, previously-used SPV proof to `register-for-bond` for the next non-overlapping `bond-index`.

### Recommendation
Persist consumed L1 lockup outpoints in a contract-level map (e.g. `used-l1-lockup-outpoints: {txid, output-index} -> bool`), checked and inserted inside `validate-l1-lockup`/`verify-l1-lockups` (analogous to `used-signer-key-authorizations`), so that any given Bitcoin UTXO can only ever back one bond registration for its full backing lifetime, regardless of how many separate `register-for-bond` transactions are submitted.

### Proof of Concept
1. Staker Alice locks 5,000,000 sats on Bitcoin in the canonical timelock P2WSH computed by `construct-lockup-output-script`, with `unlock-burn-height` set far enough in the future to satisfy `get-bond-l1-unlock-height` for bonds 0, 6, 12, ….
2. Alice calls `register-for-bond(bond-index=0, ..., btc-lockup=(ok [output_A]))`. `verify-l1-lockups`/`validate-l1-lockup` validate the SPV proof and credit `sats-total=5,000,000` into bond 0's shares (`stackslib/src/chainstate/stacks/boot/pox-5.clar:751-805`).
3. Time passes to bond 0's rollover window (`get-bond-l1-unlock-height(0)`), matching the flow already exercised in `check_pox_5_register_for_bond_l1_lockup_lifecycle` [9](#0-8) .
4. Alice calls `register-for-bond(bond-index=6, ..., btc-lockup=(ok [output_A]))` again, submitting the *same* `output_A` (same `txid`/`output-index`/`header`). `bond-overlaps-new-position?` passes because bond 6 doesn't overlap bond 0's cycles; `validate-l1-lockup` passes because `seen-outpoints` is empty for this fresh call and there is no persistent used-outpoint map to reject the replay.
5. Bond 6 is now credited another 5,000,000 sats of shares, while bond 0's shares for its remaining cycles are still intact (per the documented "preserve old bond's shares" rollover semantics). The system now recognizes 10,000,000 sats of collateral across the two bonds' overlapping validity for the transition cycle, backed by only one 5,000,000-sat UTXO — Alice can repeat this indefinitely at every 6-cycle boundary to keep claiming reward shares from a single, never-reused Bitcoin lock.
