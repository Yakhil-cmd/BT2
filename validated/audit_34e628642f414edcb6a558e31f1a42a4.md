### Title
Accrual value overflow permanently freezes a market before the borrow-index cap engages - ([File: common/src/rates/simulate.rs](common/src/rates/simulate.rs))

### Summary
CVE-2023-21866 is a repeatable crash/DoS class. In XOXNO Lending, the analog is a permanently crashing interest accrual: once `borrowed * borrow_index` (or `supplied * supply_index`) exceeds `i128`, `scaled_to_original` inside `accrue_step` panics with `MathOverflow` on every subsequent accrual. Since every mutating pool operation runs `global_sync` first, the market is bricked forever — no repay, withdraw, borrow, liquidation, or `update_indexes` can ever execute again for that hub asset.

### Finding Description
Every pool mutation loads the cache and calls `interest::global_sync`, which loops `accrue_chunk` until `last_timestamp` catches up to now. `accrue_chunk` delegates to `accrue_step`, whose first lines compute `scaled_to_original(env, borrowed, borrow_index)` and `scaled_to_original(env, supplied, supply_index)` — half-up multiply-divides that panic with `GenericError::MathOverflow` when `scaled * index` overflows `i128` (`common/src/math/fp_core.rs:108-118`).

The borrow index is monotone and capped at `MAX_BORROW_INDEX_RAY` (10^36), but the *value* `borrowed × borrow_index` hits the `i128` ceiling well before the index cap for a sufficiently large book, because the cap clamps the product *after* `old_index.mul(interest_factor)` is computed — and more importantly because `scaled_to_original` itself overflows first. `docs/reference/invariants.md` (INV-IDX-01) and `docs/reference/formulas.md` (numeric-limits) acknowledge this: "Debt-value overflow can still revert accrual before that ceiling is reached" and "Value overflow can occur before the index ceiling and block repayment/withdrawal because those operations accrue first."

The repo's own test demonstrates the end state: `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` (`tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:316-361`) supplies ~10^27 base units of an 18-decimal asset, borrows 98%, advances time, and observes `update_indexes`, `withdraw`, and `repay` all permanently reverting with `MATH_OVERFLOW` while `borrow_index < MAX_BORROW_INDEX_RAY`.

Reachability for an unprivileged user: `supply`, `borrow`, `repay` and permissionless `update_indexes` are all open to any address (`caller-auth`, `scripts/permissionless_entrypoints.txt:69-77`). An attacker seeds the market with a large supply of a high-decimal, high-supply token and takes a near-maximal borrow (their own collateral, possibly leveraged via `multiply`/`flash_position`). From then on time alone — which the attacker does not control but cannot be stopped — pushes `borrow_index` up until `borrowed × borrow_index` overflows. There is no recovery path: `recapitalize` credits cash but does not reduce scaled `borrowed`; `clean_bad_debt`/`seize_positions` also accrue first; and the panic occurs inside `Cache::load`/`global_sync` before any mutation logic runs.

### Impact Explanation
Permanent freezing of funds — an accepted impact class. Once the panic state is reached, every supplier's deposit, every borrower's collateral pledged through other markets touching this one, and all accrued revenue in the affected `(hub, token)` market are permanently locked: withdraw, repay, liquidate, `clean_bad_debt`, `claim_revenue`, and `update_indexes` all revert at the accrual preface. For volatile collateral positions this also means the market cannot be liquidated, converting a freeze into protocol insolvency. This mirrors the CVE's "frequently repeatable crash (complete DOS)" mapped onto a state machine that accrues first on every verb — the crash is not transient, it is terminal for the market.

### Likelihood Explanation
Medium. The trigger requires a market whose raw token scale times index growth reaches ~1.7e38. For 7-decimal assets like XLM/USDC the required book exceeds real token supply, so the cliff is unreachable. For a high-decimal token (e.g., 18 decimals, where the token-to-RAY limit permits ~1.7e20 whole-token-equivalent scaled values), a whale-scale supply-and-borrow suffices; `supply`/`borrow` caps set by governance determine whether a single actor can reach it, and caps near the admitted maximum make it feasible. No privileged action is needed to *trigger* the freeze — only time passing after the position is opened, or permissionless `update_indexes` calls to advance accrual. The exploit demands substantial capital and a favorable listing configuration, which is why severity is Medium rather than High.

### Recommendation
Make accrual saturate rather than panic on value overflow: use `mul_div_floor_saturating` (already available in `common::math::fp_core`) for `scaled_to_original` in the accrual path, or clamp `borrowed`/`supplied` effective values so `scaled × index` stays in `i128`. Alternatively, cap the borrow index low enough (or debt shares high enough in denominator terms) that `MAX_BORROW_INDEX_RAY × max_scaled_debt` provably fits — i.e., enforce at borrow-mint time that `scaled_borrowed ≤ i128::MAX / MAX_BORROW_INDEX_RAY` so the overflow state is unreachable. A fail-safe variant: on accrual overflow, advance `last_timestamp` without accruing (interest-freeze rather than market-freeze) so exits remain possible.

### Proof of Concept
The repository already contains a working PoC: `tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:316-361`.

```rust
let mut t = LendingTest::new()
    .with_market(big("BIG18", 18, xlm_curve()))
    .with_market(col())
    .with_max_utilization_disabled_all_markets()
    .build();
lift_caps(&t, "BIG18", 18);
lift_caps(&t, "COL", 7);
let principal = BILLION * 10i128.pow(18);
t.supply_raw(BOB, "BIG18", principal);
let debt = principal / 100 * 98;
t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
t.borrow_raw(ALICE, "BIG18", debt);          // 98% utilization whale borrow

loop {
    t.advance_time(YEAR_SECS);               // attacker只需要等待 / keep calling update_indexes
    if let Err(e) = t.try_update_indexes_for(&["BIG18"]) { break e; }
}
// Once it fails:
assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
// last.borrow_index < MAX_BORROW_INDEX_RAY — the index cap never engages;
// the market is permanently frozen: no repay, withdraw, or liquidation.
```

Unprivileged path: attacker calls `supply(caller, 0, spoke, [(big18_key, principal)])` then `borrow(caller, acct, [(big18_key, debt)])` — both `caller-auth` entrypoints — then any address can poke `update_indexes` each ledger until `scaled_to_original` in `accrue_step` (`common/src/rates/simulate.rs:60-61`) overflows `i128` and panics inside `global_sync` (`contracts/pool/src/interest.rs:20-33`), which precedes every mutation of that market.
