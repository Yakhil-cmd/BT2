### Title
Attacker-controlled swap route can add unauthorized child token transfers under the caller’s signed authorization tree - ([File: contracts/controller/src/strategies/swap.rs](contracts/controller/src/strategies/swap.rs))

### Summary
`swap_collateral` and the other routed strategy entrypoints accept caller-supplied route bytes and execute them through the configured router. A route can place attacker-controlled venue code beneath the caller’s `require_auth` invocation; if simulation records and the victim signs the resulting child invocation, that code can transfer arbitrary tokens from the victim’s wallet to the attacker. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
`process_swap_collateral` authenticates the supplied `caller`, verifies that the caller controls the account, and forwards the opaque `swap` payload into the swap path. [4](#0-3)  `swap_tokens` only pre-authorizes the controller’s exact input transfer to the router; it does not constrain the authorization tree to that transfer or otherwise prevent route-selected contracts from requesting additional authority from the original caller. [2](#0-1) 

The adversarial test demonstrates the mechanism: a route-selected pool calls `token.transfer(victim, attacker, amount)` while processing the swap. [5](#0-4)  Simulation records that transfer as a child of the victim’s `swap_collateral` authorization entry. [6](#0-5)  If the victim signs the recorded tree, the unrelated wallet-token transfer executes and the attacker receives the full balance, while an honest root-only tree rejects it. [7](#0-6) 

### Impact Explanation
This is theft of user funds beyond the assets supplied to the lending strategy. The test steals an unrelated, unlisted wallet token’s entire balance while the routed strategy itself still returns fair output and satisfies the account-level checks. [8](#0-7) [9](#0-8)  Severity is High because attacker-controlled strategy content can cause a victim’s signed transaction to perform an arbitrary token transfer.

### Likelihood Explanation
An unprivileged attacker can deploy a malicious venue-compatible contract and encode it into a swap payload submitted through an allowed route path; `swap_collateral`, `swap_debt`, `multiply`, and `repay_debt_with_collateral` all reach the same router mechanism. [10](#0-9) [11](#0-10)  Successful theft requires the victim to sign the poisoned authorization tree produced by simulation, so likelihood depends on wallet or client behavior not clearly exposing the additional child transfer. [12](#0-11) 

### Recommendation
Do not rely on callers safely interpreting arbitrary route-generated authorization subtrees. Prefer constraining routed execution at the authorization boundary—for example, execute swaps through a contract-controlled flow that cannot inherit user-level authorization, or introduce an explicit per-route authorization/commitment mechanism that rejects child invocations beyond the expected input transfer. At minimum, protocol clients should decode the complete route, simulate the transaction, and refuse any `swap_collateral`, `swap_debt`, `multiply`, or `repay_debt_with_collateral` authorization tree containing children other than the expected token pull.

### Proof of Concept
1. Alice supplies USDC and owns a lending account; she also holds an unrelated wallet token not listed by the protocol. [8](#0-7) 
2. The attacker deploys a route-compatible pool whose `swap` function calls `token.transfer(alice, attacker, WALLET_BALANCE)` on the unrelated token. [13](#0-12) 
3. The attacker constructs a `swap_collateral` payload routing through that pool while still returning fair ETH output. [14](#0-13) 
4. Simulation records the rogue transfer as a child of Alice’s `swap_collateral` authorization. [6](#0-5) 
5. Alice signs the simulated authorization tree. The malicious child transfer executes, reducing Alice’s unrelated token balance to zero and crediting the attacker. [3](#0-2)

That bound covers the controller's own grant only. The router calls the pool
and token addresses its payload names and keeps no allowlist of them, so a
route can put third-party code on the call stack below the caller's
authorization. A token transfer that such code makes from the caller is
recorded by an honest simulation as a child of the caller's authorization
entry, and it executes if the caller signs that tree. The loss is then the
caller's wallet, not the routed amount, and neither the payload minimum nor the
final risk gate bounds it. An honest swap strategy gives the caller no child
entry, and a direct router swap gives exactly one input transfer. A client must
decode the route it signs and refuse an authorization tree with any other
