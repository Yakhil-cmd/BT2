### Title
Webhook signature verified with the secret of `repository.owner.login` while the handlers act on the stack resolved from `repository.full_name`, letting a webhook signed for one GitHub organization write to any stack across the entire installation - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`Shipit` supports a multi-organization configuration where each GitHub organization has its own `webhook_secret` [1](#0-0) . `WebhooksController#verify_signature` selects which organization's `GitHubApp` (and therefore which `webhook_secret`) to verify the request against using `repository_owner`, a value read straight out of the unauthenticated JSON body: `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` [2](#0-1) . Once the HMAC check passes, the actual event handler resolves the target `Stack`/`Repository` using a completely different, independently-attacker-controlled field in the same body: `payload.dig('repository', 'full_name')` [3](#0-2) .

### Finding Description
This is the same class of bug as the External Report: a field that is *acted upon* (`repository.full_name`, which selects the stack to mutate) is never bound to the field that was *cryptographically verified* (`repository.owner.login`, which selects the HMAC secret). The HMAC only proves that the signer knew `webhook_secret` for the organization named in `repository.owner.login`; it says nothing about which `repository.full_name` accompanies that owner in the JSON body, because both are independent, attacker-controlled fields inside the same signed payload.

The binding that should hold is:
`organization whose secret authenticated the request == organization that owns the repository being written to`

but the code enforces only:
`organization whose secret authenticated the request == repository.owner.login` (attacker-supplied)
while
`repository being written to == Repository.from_github_repo_name(repository.full_name)` (also attacker-supplied, and never checked against `repository.owner.login`)

Concretely:
- `verify_signature` looks up `Shipit.github(organization: repository_owner)` and validates `X-Hub-Signature` against `request.raw_post` using that organization's `webhook_secret` [4](#0-3) .
- `Shipit::Webhooks::Handlers::Handler#stacks` resolves the target repository purely from `payload.dig('repository', 'full_name')`, with no cross-check against the `repository.owner.login`/`organization.login` value used for signing [3](#0-2) .
- `PushHandler#process` then calls `stack.sync_github(expected_head_sha: params.after)` for every non-archived stack on that branch of the resolved repository [5](#0-4) .

Anyone who legitimately possesses (or has leaked/guessed/rotated-but-cached) the `webhook_secret` for *any one* configured GitHub organization in a multi-org Shipit deployment — e.g., a low-privilege org admin who set up their own org's webhook in GitHub's UI and can see/copy that secret — can build a raw POST body where:
- `repository.owner.login` (or `organization.login`) = their own, low-trust organization (so the correct `webhook_secret` is selected and the HMAC passes), and
- `repository.full_name` = `"other-org/other-repo"`, naming a stack that belongs to a completely different, higher-trust organization also hosted on the same Shipit instance.

Since the HMAC only covers "this body came from someone holding org A's secret," and the handler dispatch uses `repository.full_name` from that same body without re-validating it against org A, the forged event is accepted and dispatched against org B's stack.

### Impact Explanation
This breaks the "organization that authenticated versus the repository that is written" binding explicitly listed as in-scope. In a multi-organization Shipit deployment, knowledge of one organization's `webhook_secret` is sufficient to trigger the `push` handler's `stack.sync_github` (and, depending on registered handlers, `status`/`check_suite`/`pull_request` handlers) against stacks belonging to a different, unrelated organization, causing an unauthorized deploy/rollback pipeline trigger (`sync_github`) cross-organization/cross-repository. This is a High-severity cross-repository-write-class issue per the impact list (unauthorized deploy trigger across repository boundaries) achievable purely by an entity that legitimately controls a webhook secret for one org but not another — no session, `ApiClient` token, or GitHub App private key is required for the target organization.

### Likelihood Explanation
Requires: (1) a Shipit instance configured with more than one GitHub organization (`secrets.github` keyed by org, as documented in `config/secrets.development.example.yml`) [6](#0-5) , and (2) the attacker possessing the `webhook_secret` of at least one of those organizations (which is routinely visible to that org's own GitHub webhook admins, and is explicitly designed to be organization-scoped rather than a shared installation-wide trust root). Given that Shipit is explicitly built to support multiple organizations with per-org secrets, this configuration is a documented, intended deployment mode, not a corner case.

### Recommendation
After signature verification succeeds for organization `repository_owner`, re-validate that the repository resolved by the handler (`repository.full_name`) actually belongs to that same organization (e.g., assert `full_name.split('/').first.casecmp?(repository_owner)`) before dispatching to `Shipit::Webhooks.for_event(event)`, or have `Handler#stacks` take the verified organization as an explicit argument and scope `Repository.from_github_repo_name` lookups to repositories owned by that organization.

### Proof of Concept
1. Configure Shipit with two organizations, e.g. `org-low` and `org-high`, each with its own `webhook_secret`, per the multi-org schema in `config/secrets.development.example.yml`.
2. As an admin of `org-low`'s own GitHub org (who legitimately knows `org-low`'s `webhook_secret` because they configured the webhook themselves), craft a JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker chosen sha>",
  "repository": {
    "owner": { "login": "org-low" },
    "full_name": "org-high/sensitive-repo"
  }
}
```
3. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(org-low webhook_secret, raw_body)>` and set `X-Github-Event: push`.
4. POST to `/github/webhooks`. `verify_signature` calls `Shipit.github(organization: 'org-low')` and successfully verifies the signature against `org-low`'s secret [4](#0-3) .
5. `PushHandler.call(params)` resolves `stacks` via `Repository.from_github_repo_name('org-high/sensitive-repo')` [3](#0-2)  and invokes `stack.sync_github(expected_head_sha: ...)` on `org-high`'s stack [5](#0-4)  — despite the request only ever being authenticated for `org-low`.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping
      head(:ok) if event == 'ping'
    end

    def event
      request.headers.fetch('X-Github-Event')
    end

    def repository_owner
      # Fallback to the organization sub-object if repository isn't included in the payload
      params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
    end
```
