## Analog Found

### Title
Unbounded number of payment inputs in AA response units causes synchronous per-input DB validation DoS - (File: `validation.js`, `aa_composer.js`)

### Summary
The Tornado CVE is about `multipart/form-data` bodies containing an unbounded number of "parts," each of which is parsed synchronously with no per-request cap, so a single request can consume disproportionate CPU/IO on the server. In ocore, the analogous "parts" are the `inputs` array of a payment message. Ordinary units are capped at `constants.MAX_INPUTS_PER_PAYMENT_MESSAGE` (128), but AA-response payment messages are explicitly exempted from that cap, and the AA composer's output-selection queries that populate those inputs have no `LIMIT` at all.

### Finding Description
`validatePaymentInputsAndOutputs()` only enforces the anti-spam input cap for non-AA units: [1](#0-0) 

Every input in `payload.inputs` is then validated one at a time via `async.forEachOfSeries`, and each iteration issues its own double-spend SQL query (`checkInputDoubleSpend`) and, for unstable inputs, a graph inclusion check: [2](#0-1) [3](#0-2) 

The AA composer's coin-selection queries used to build an AA's payment response have no row limit, unlike the equivalent wallet-side query in `inputs.js` which caps at `MAX_INPUTS_PER_PAYMENT_MESSAGE-2`: [4](#0-3) [5](#0-4) 

When an AA response contains a "send-all" output (`amount` omitted, a common pattern for forwarding/exchange-style AAs), `iterateUnspentOutputs` does not break out of the loop after reaching the target amount — it keeps consuming every returned unspent output row as a separate input: [6](#0-5) 

Putting these together: an unprivileged unit poster can pre-fund an AA address with a very large number of small outputs (each above the dust threshold `FULL_TRANSFER_INPUT_SIZE`) across many cheap units, then send a trigger that causes the AA to respond with a send-all payment. The composer will pull *all* of those outputs (no `LIMIT`) into `payload.inputs` of one message, and `validation.js` will not reject the resulting response unit for having too many inputs because `objValidationState.bAA` bypasses `MAX_INPUTS_PER_PAYMENT_MESSAGE`. Every node in the network that receives and validates this AA response unit must then serially execute one double-spend query (and possibly a graph-inclusion check) per input — a cost that scales linearly with an attacker-controlled, effectively unbounded input count, exactly mirroring the Tornado bug class ("too many parts, no limit on complexity, synchronous linear-cost processing per unit").

### Impact Explanation
This is reachable by any unprivileged party who can post units and trigger an AA (`unit poster` / `AA trigger sender` in scope). It forces every full node validating the resulting AA-response unit to perform O(N) serial database round-trips for double-spend/graph checks with N attacker-controlled and not bounded by the normal anti-spam constant. Because unit validation in ocore is processed unit-by-unit and gates acceptance of subsequent units/consensus advancement, a sufficiently large N can materially slow down or stall the validation pipeline for the network, i.e., "a network unable to confirm new units" in a timely manner — the concrete impact bar required here.

### Likelihood Explanation
The prerequisite (funding an AA address with many small outputs) costs the attacker in unit fees, but is straightforward, requires no special privilege, and can be done in advance/off-chain-timing before a single trigger. Because the cap bypass (`!objValidationState.bAA`) is explicit and intentional-looking code (rather than an edge case), and the AA composer read query has no limit, the path is directly reachable without needing to exploit any parsing/formula bug — only ordinary payment/trigger messages.

### Recommendation
- Enforce a maximum number of inputs per AA-generated payment message (either reuse `MAX_INPUTS_PER_PAYMENT_MESSAGE` or introduce an AA-specific cap) instead of exempting `objValidationState.bAA` from `validatePaymentInputsAndOutputs`'s input-count check in `validation.js`.
- Add a `LIMIT` (e.g., `MAX_INPUTS_PER_PAYMENT_MESSAGE`) to the `readStableOutputs`/`readUnstableOutputsSentByAAs` queries in `aa_composer.js`, and change `iterateUnspentOutputs` to stop pulling in further outputs once the cap is reached, splitting a send-all payout across multiple response units/messages if necessary instead of consuming unlimited outputs in one message.

### Proof of Concept
1. Attacker crafts N (e.g. tens of thousands) small units, each sending a single output just above the dust threshold (`FULL_TRANSFER_INPUT_SIZE`) to a target AA address `A`, where `A`'s definition includes a "forward all received funds" / send-all response pattern.
2. Once these N outputs are stable, attacker sends a trigger unit to `A`.
3. During `handleTrigger` → `sendUnit` → `completePaymentPayload`, `readStableOutputs`/`readUnstableOutputsSentByAAs` (no `LIMIT`) return all N rows, and because the payload has a send-all output, `iterateUnspentOutputs` consumes all N as `payload.inputs` [6](#0-5) .
4. The resulting AA response unit passes `validation.js`'s input-count gate solely because `objValidationState.bAA` is true [1](#0-0) .
5. Every node validating this unit must run N serial double-spend/graph queries in `validatePaymentInputsAndOutputs`'s `async.forEachOfSeries` loop [2](#0-1) , imposing an attacker-controlled, effectively unbounded synchronous validation cost on the whole network for a single unit — the same bug class as CVE-2026-31958 (unbounded "parts" count parsed synchronously with no per-message limit).
