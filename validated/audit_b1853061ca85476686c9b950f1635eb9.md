### Title
Webhook signature verified against attacker-controlled organization while repository/commit written is taken from an unchecked payload field, enabling cross-organization commit-status/push forgery - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects the GitHub App/webhook config to validate against using `repository_owner`, which is read straight out of the untrusted JSON body (`params.dig('repository','owner','login')` or `organization.login`). The individual webhook handlers, however, resolve the object that actually gets mutated (the `Stack`/`Repository` via `full_name`, or in `StatusHandler` a bare `Commit.where(sha: ...)` lookup with no repository scoping at all) from a *different* field of the same attacker-supplied payload. Nothing ties the organization whose secret validated the HMAC to the repository/commit that ends up written. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) 

### Finding Description
On any installation that serves more than one GitHub organization (a documented, first-class configuration, see `config/secrets.development.shopify.yml` and `docs/setup.md`), each org gets its own `GithubApp` instance with its own `webhook_secret`: [5](#0-4) 

`verify_signature` picks the org's `GithubApp` purely from `repository_owner` (payload-controlled) and HMAC-verifies the raw body against that org's secret: [6](#0-5) [7](#0-6) 

If the HMAC check passes, `Shipit::Webhooks.for_event(event)` runs the corresponding handler over the *entire* raw payload — including fields the signature-selection step never inspected, such as `repository.full_name` (used by `Handler#stacks`/`#repository_name`) and, in `StatusHandler`, the commit `sha` which is looked up **globally with no repository filter whatsoever**: [3](#0-2) [8](#0-7) [9](#0-8) 

Equality that should hold but doesn't:
`organization whose secret validated the HMAC (repository_owner)` == `organization that owns the repository/commit actually mutated (full_name / sha lookup)`

Before the attacker's request: only the legitimate owning org's app credentials can produce records for that org's stacks/commits.
After the attacker's request: an attacker who is a legitimate installer of *any* org configured on the same Shipit instance (and therefore knows *that* org's `webhook_secret`) can sign a payload whose `repository.owner.login` is their own org (so the HMAC check passes) while `repository.full_name`/`sha` reference a stack or commit belonging to a completely different, victim organization. `StatusHandler` in particular does not check the repository at all — it matches any `Commit` in the database by `sha` — so a correctly-signed-for-org-A payload can inject a forged CI status ("success"/"failure") onto a commit that belongs to org B's stack, and `PushHandler` can similarly trigger `stack.sync_github` for a stack it does not own.

### Impact Explanation
This is a genuine cross-repository/cross-organization write performed by an entity that never held credentials for the target organization: forged commit statuses land on commits under a stack the attacker doesn't control, and forged push events can trigger Github sync jobs for stacks belonging to another organization. Because Shipit commonly gates continuous deployment on commit/CI status, injecting a fabricated "success" status can push a specific commit past the CI-status safety gate it never actually passed, resulting in an unauthorized deploy of that commit. This matches the Critical bucket ("cross-repository writes ... an unauthorized deploy") in the rubric.

### Likelihood Explanation
Exploitation requires only that the attacker be a legitimate participant (installer) of *any one* organization hosted on the same multi-tenant Shipit instance — a normal, unprivileged, documented deployment topology — and knowledge of that one org's own `webhook_secret` (which they legitimately possess, since it's their own org's GitHub App secret). No access to the victim organization's secret, `GITHUB_TOKEN`, `api_clients_secret`, or a Shipit session/API token is needed. The only unknown quantities the attacker must guess are the target `full_name`/commit `sha`, which are frequently public (public repositories, PR pages, commit history).

### Recommendation
- Bind the signature-selection organization to the same value used for subsequent repository resolution: after `verify_signature` succeeds, re-derive `repository_owner` from `repository.full_name` (or reject requests where `repository.owner.login` doesn't match the owner prefix of `repository.full_name`) and reject the request if they diverge.
- In every handler, scope any lookup (e.g. `StatusHandler#process`'s `Commit.where(sha: ...)`) to the repository/stack resolved from the verified organization, never globally by `sha` alone.
- Consider deriving `repository_owner`/`full_name` once in the controller (post-signature verification) and passing an immutable, already-validated repository/organization context into handlers instead of letting each handler re-parse the raw payload independently.

### Proof of Concept
1. Multi-org Shipit instance hosts `attacker-org` and `victim-org`, each with its own GitHub App and `webhook_secret` (documented configuration, see `config/secrets.development.shopify.yml`).
2. Attacker is a legitimate installer of `attacker-org`'s GitHub App and therefore knows `attacker-org`'s `webhook_secret`.
3. Attacker crafts a JSON body:
```json
{
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" },
  "sha": "<known commit sha of a victim-org stack>",
  "state": "success",
  "context": "ci/required-check"
}
```
4. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(attacker-org_webhook_secret, body)` and sends `POST /webhooks` with `X-Github-Event: status`.
5. `WebhooksController#verify_signature` looks up `Shipit.github(organization: "attacker-org")` and successfully verifies the signature using the attacker's own known secret.
6. `StatusHandler#process` runs `Commit.where(sha: params.sha)` with no repository check, and creates a "success" status on the victim commit — a write the attacker was never authorized to make, potentially unblocking an unauthorized automatic deploy of that commit under `victim-org`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
    end
  end
end
