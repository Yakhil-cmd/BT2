### Title
Cross-organization webhook forgery triggers `GithubSyncJob` for stacks owned by a different (properly-secured) organization - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/push_handler.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App/secret to verify against using `repository.owner.login` from the attacker-controlled JSON body, and `GithubApp#verify_webhook_signature` trivially returns `true` when that organization has no `webhook_secret` configured. `PushHandler#process`, however, resolves the target `stacks` from `repository.full_name` (a separate, independently attacker-controlled field), with no check that the verified organization actually owns that repository. This breaks the intended binding `organization that authenticated the request == organization owning the affected repository/stack`.

### Finding Description
Binding claimed: `repository_owner used in verify_signature (org whose secret authenticated the request)` == `organization owning the Stack whose sync_github is invoked via PushHandler#process`.

Trace:
- `WebhooksController#verify_signature` picks the app config via `Shipit.github(organization: repository_owner)`, where `repository_owner = params.dig('repository','owner','login') || params.dig('organization','login')` [1](#0-0) [2](#0-1) .
- `GithubApp#verify_webhook_signature` explicitly short-circuits to `true` when no `webhook_secret` is configured for that organization: `return true unless webhook_secret` [3](#0-2) .
- Once verification passes (because "attacker-org" has no secret), `PushHandler#process` runs `stacks.not_archived.where(branch:).find_each { |stack| stack.sync_github(expected_head_sha: params.after) }`, using only `ref`/`after` from the body [4](#0-3) . The `stacks` scope resolved by the handler base class comes from `repository.full_name` in the same JSON body — a field completely independent from `repository.owner.login`, which was the only value used to pick the verifying organization. Nothing re-checks that the full_name's owner matches the organization whose (missing) secret was used to "verify" the request.

Attacker request: unsigned/arbitrary-signature POST to `/webhooks` with header `X-Github-Event: push` and JSON body: `repository.owner.login = "attacker-org"`, `repository.full_name = "victim/repo"`, `ref = "refs/heads/master"`, `after = "<attacker-chosen sha>"`. If Shipit's multi-org config (a supported configuration in this codebase — see `test/dummy/config/secrets_double_github_app.yml`, which explicitly configures multiple orgs with `webhook_secret: # nil`) contains any org without a configured `webhook_secret`, the signature check passes unconditionally regardless of the actual signature header, and the push is processed against victim/repo's real `Stack` on `master`, enqueuing `GithubSyncJob` with the victim stack's id and the attacker's `after` value.

Existing guards do not stop this: `drop_unhandled_event` only checks the event name is handled; `verify_signature` only binds trust to `repository.owner.login`, not to `repository.full_name`; there is no `ExplicitParameters` validation tying the two together; `PushHandler` performs no additional organization check.

### Impact Explanation
An attacker can force `GithubSyncJob` to run against a victim's real `Stack` (a repository/stack they did not authenticate for) with an attacker-chosen `expected_head_sha`, purely because a distinct, unrelated org configured in the same Shipit instance lacks a `webhook_secret`. This matches "a payload for one repository mutating another's stack" — an unauthorized job dispatch triggered without a valid signature from the owning organization. Blast radius is limited to Shipit instances configured with multiple GitHub App organizations (per `docs/setup.md`'s "Using Multiple Github Applications" section) where at least one configured org omits `webhook_secret`; in that scenario every other org's stacks become reachable via that org's lack of verification.

### Likelihood Explanation
Requires: (1) the target Shipit instance to have multi-org GitHub App configuration, and (2) at least one configured org with no `webhook_secret` set — an explicitly supported state in this codebase (`nil` webhook_secret handled gracefully by `GithubApp#verify_webhook_signature`, and used in test fixtures for multiple orgs simultaneously). If such a misconfigured/secret-less org exists, exploitation costs the attacker a single unauthenticated HTTP POST with a guessed or known org login name; no secrets, sessions, or tokens are needed, and the attack is fully repeatable against any repository/stack registered in Shipit.

### Recommendation
In `PushHandler` (and other handlers), verify that the organization used to authenticate the webhook (`repository.owner.login` checked in `verify_signature`) matches the organization that actually owns the target `repository.full_name`/`Stack` before acting. Alternatively, pass the verified `repository_owner` into the handler and reject/short-circuit processing if it doesn't match the resolved stack's own repository owner. Additionally, consider making `webhook_secret` mandatory for all configured organizations (fail fast at boot if any org config omits it) rather than silently trusting unsigned requests.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (minitest)
test "cross-org push payload triggers sync on victim stack when attacker-org has no webhook_secret" do
  victim_stack = shipit_stacks(:shipit) # belongs to org "shopify" in fixtures
  attacker_org_config = { app_id: 1, installation_id: 1, private_key: TEST_PRIVATE_KEY } # no webhook_secret key
  Shipit.stubs(:github).with(organization: 'attacker-org').returns(Shipit::GithubApp.new('attacker-org', attacker_org_config))

  request.headers['X-Github-Event'] = 'push'
  forged_payload = {
    ref: 'refs/heads/master',
    after: 'deadbeefdeadbeefdeadbeefdeadbeefdeadbeef',
    repository: { full_name: victim_stack.repo_name_and_owner, owner: { login: 'attacker-org' } }
  }.to_json

  assert_enqueued_with(job: GithubSyncJob, args: [stack_id: victim_stack.id, expected_head_sha: 'deadbeefdeadbeefdeadbeefdeadbeefdeadbeef']) do
    post :create, body: forged_payload, as: :json
  end
end
```
This proves that `repository.owner.login` ("attacker-org", unauthenticated) diverges from the organization owning the affected `Stack` ("shopify"/victim), yet `GithubSyncJob` is still enqueued for the victim's stack with the attacker-controlled `expected_head_sha`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
