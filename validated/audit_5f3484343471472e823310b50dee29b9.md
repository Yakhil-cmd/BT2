### Title
Missing validation of the `creator` account when setting `pool_creator` in `initialize_with_permission` permanently locks creator fees - (File: programs/cp-swap/src/instructions/initialize_with_permission.rs)

### Summary
`initialize_with_permission` accepts `creator` as an `UncheckedAccount` that is neither required to sign nor validated against `Pubkey::default()` or other degenerate values, and stores it directly as `pool_state.pool_creator` via `pool_state.initialize(...)`. This mirrors the referenced report's root cause — writing a new "owner"-style address to persistent state without any validity check.

### Finding Description
In `InitializeWithPermission`, the `creator` field is declared only as `/// CHECK: creator of pool` `pub creator: UncheckedAccount<'info>` with no signer requirement and no `constraint` guarding against invalid values. [1](#0-0) 

The instruction handler then persists this unchecked key directly into the pool state as the permanent `pool_creator` field: [2](#0-1) 

Unlike `update_amm_config`, which explicitly validates new owner addresses with `require_keys_neq!(new_owner, Pubkey::default())` before writing `protocol_owner`/`fund_owner`, no equivalent check exists for `creator` here — the same class of bug flagged in the original report (writing an authority-like field to state without validating it is a usable, non-degenerate key).

Downstream, `pool_creator` is later relied on as an authority: `CollectCreatorFee` requires the `creator` account to be a `Signer` whose address must equal `pool_state.pool_creator`: [3](#0-2) 

If `pool_creator` is set to `Pubkey::default()` (the System Program address, for which no private key exists) — either by a permissioned payer's mistake or by a malicious permissioned payer intentionally bricking their own pool's creator-fee stream (or targeting a shared/predictable value) — no signature can ever be produced for that key. `collect_creator_fee` becomes permanently uncallable for that pool. The permissionless alternative, `CollectCreatorFeePermissionless`, does not require a signature from `creator`, but it creates the destination ATA with `associated_token::authority = creator`, i.e. authority `Pubkey::default()`; tokens delivered there are held by an account no one can ever move out via SPL token authority checks, since token transfer/withdraw from that ATA still requires the token account's `authority` (the default pubkey) to sign.

### Impact Explanation
Accumulated `creator_fees_token_0` / `creator_fees_token_1` for the affected pool become permanently frozen: they can never be withdrawn by `collect_creator_fee` (no signer for `Pubkey::default()`), and once swept via `collect_creator_fee_permissionless` they land in a token account whose authority can never sign to move them further. This is a permanent freezing of protocol/creator-designated funds, matching the accepted impact class (permanent freezing of funds).

### Likelihood Explanation
`initialize_with_permission` is reachable by any payer who has been granted a `Permission` PDA (a normal, non-privileged pool-creation path within scope, analogous to `initialize`). The `creator` field is entirely attacker/payer-chosen and unchecked, so triggering this only requires a single call to `initialize_with_permission` with `creator` set to `Pubkey::default()` (or any other unsignable/attacker-controlled degenerate key) — no elevated privileges beyond having been granted pool-creation permission are needed.

### Recommendation
Add an explicit validation in `InitializeWithPermission` (or in `initialize_with_permission`/`pool_state.initialize`) rejecting `creator == Pubkey::default()`, mirroring the `require_keys_neq!(new_owner, Pubkey::default())` pattern already used in `update_amm_config`'s `set_new_protocol_owner`/`set_new_fund_owner`.

### Proof of Concept
1. Admin grants a `Permission` PDA to attacker/payer `P` via `create_permission_pda`.
2. `P` calls `initialize_with_permission` supplying `creator = Pubkey::default()` (or any address it knows cannot sign, e.g. another program's PDA with no matching seeds under this program).
3. Pool is created successfully; `pool_state.pool_creator = Pubkey::default()`.
4. Swaps accrue `creator_fees_token_0/1` in `pool_state`.
5. `collect_creator_fee` can never be called because no one can sign as `Pubkey::default()`.
6. `collect_creator_fee_permissionless` can be called by anyone, but the SPL/ATA `creator_token_0`/`creator_token_1` accounts are created with `authority = Pubkey::default()`; the transferred fee tokens are now held in accounts that can never authorize a further transfer, permanently locking the funds.
