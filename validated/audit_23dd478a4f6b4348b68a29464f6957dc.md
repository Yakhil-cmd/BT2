### Title
Unbounded recursive-descent parsing of attacker-controlled oscript formulas can crash full nodes via stack overflow - ([File: formula/evaluation.js], [File: formula/validation.js])

### Summary
CVE-2020-12723 is a stack-overflow-class bug in Perl's regex compiler caused by unbounded recursion (`S_study_chunk`) when compiling a crafted, deeply-nested pattern. The equivalent bug class in ocore is unbounded native recursion in a grammar/AST-driven parser triggered by attacker-supplied input, before any of the code's own depth/complexity guards are ever reached.

### Finding Description
Oscript formulas embedded in AA definitions and AA trigger `data`/`state`/`init` payloads are parsed with a nearley Earley-parser grammar before any application-level safety checks run: [1](#0-0) [2](#0-1) 

`nearley.Parser.feed(formula)` performs recursive-descent style expansion of the grammar rules for nested expressions (parentheses, nested function calls, nested conditionals). This call happens **before** any of the application's own recursion-limiting logic executes. The application-level guards that exist are all *post-parse*, operating on the already-built AST:
- `formula/validation.js`'s `evaluate()` only checks `depth > 100` inside the AST-walking function, and that check is itself gated behind an upgrade MCI (`pemCurvesFixMci`) rather than applying unconditionally: [3](#0-2) 
- `formula/evaluation.js`'s `evaluate()` only interrupts the call stack every 100 *AST-node* visits via `setImmediate`, again after parsing has already completed: [4](#0-3) 
- `definition.js`'s address-definition `evaluate()` is bounded indirectly by `MAX_COMPLEXITY` (100) since every recursive call increments `complexity`, but this bound applies only to the definition-op tree, not to formula parsing: [5](#0-4) [6](#0-5) 
- `aa_validation.js` has an explicit `MAX_DEPTH` check, but again this only bounds the AA-definition JSON tree walk, not the internal parsing of each formula string once reached: [7](#0-6) 

None of these mechanisms constrain the recursion that occurs *inside* `nearley.Parser.feed()` itself while parsing a single formula string. A formula field (`getFormula`) has no length limit applied prior to parsing: [8](#0-7) . The only outer bound is the unit-size limit `MAX_UNIT_LENGTH` (5,000,000 bytes): [9](#0-8) , which still allows a single message payload/formula string on the order of megabytes — far more than enough (tens of KB of nested parentheses is typically sufficient) to exhaust the V8 call stack during grammar expansion.

### Impact Explanation
A crafted unit containing an AA definition (`app: 'definition'`, `['autonomous agent', ...]`) or a trigger `data`/`state`/`init` field with a formula string containing thousands of nested parentheses/expressions would be parsed by every full node that validates the unit (`aa_validation.js` → `validateFormula` → `formula/validation.js`) and again by every node executing the AA trigger (`aa_composer.js` → `formulaParser.evaluate` → `formula/evaluation.js`). If the recursive parse exceeds the JS engine's native call-stack limit, the node process crashes with an uncatchable `RangeError: Maximum call stack size exceeded` (or in native addons, undefined behavior), which is a denial-of-service that prevents affected nodes from validating/confirming new units — matching the "network unable to confirm new units" impact criterion.

### Likelihood Explanation
Any unprivileged unit poster or AA-trigger sender can construct such a payload without needing any special privileges, keys, or network position; the formula is simply embedded in the `data`, `state`, `init`, `definition`, or `cap`/`denominations` fields of a normally-signed unit and broadcast like any other unit. Because the parse happens synchronously and before all complexity/depth accounting, no legitimate spam-prevention limit (`MAX_COMPLEXITY`, `MAX_OPS`, `MAX_DEPTH`) currently protects against it.

### Recommendation
Impose a hard length limit on formula source strings (`getFormula` output) before calling `nearley.Parser.feed()`, and/or wrap the nearley parse invocation with a bracket/nesting-depth pre-scan that rejects formulas whose paren/expression nesting exceeds a safe bound (e.g., matching the existing `MAX_DEPTH`/`depth > 100` limits) prior to invoking the parser, in both `formula/validation.js` and `formula/evaluation.js`.

### Proof of Concept
Construct an AA definition (or trigger `data` message) containing a formula field such as:
```
"{" + "(".repeat(50000) + "1" + ")".repeat(50000) + "}"
```
embedded in a `definition`/`state`/`init` field of a unit within the `MAX_UNIT_LENGTH` (5MB) budget, then post the unit. When a full node calls `validateFormula`/`formulaParser.evaluate` on this string, `nearley.Parser.feed()` recurses through the grammar's expression rules for each nested paren before any AST-level depth check is reached, exhausting the call stack.

function getFormula(str, bOptionalBraces) {

		return null;
	if (str[0] === '{' && str[str.length - 1] === '}')
