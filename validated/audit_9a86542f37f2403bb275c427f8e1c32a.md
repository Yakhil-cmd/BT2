### Title
Webhook signature verification keyed on `repository.owner.login`/`organization.login` while stack dispatch uses unrelated `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App / `webhook_secret` to validate the HMAC signature against based on `repository_owner`, a value read directly from the untrusted JSON body (`repository.owner.login` or `organization.login`). Every downstream `Webhooks::Handlers::Handler` subclass instead resolves the target `Stack`/`Repository` using a completely different, independently attacker-controlled field: `payload.dig('repository', 'full_name')`. Because these two fields are never checked for consistency, the "organization whose secret authenticated the request" and "repository that is actually written to" are not the same binding.

### Finding Description
`verify_signature` does:
```
app/controllers/shipit/webhooks_controller.rb:24-30
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
head(422) unless verified
```
with
```
app/controllers/shipit/webhooks_controller.rb:59-62
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) [2](#0-1) 

`GitHubApp#verify_webhook_signature` intentionally treats a missing `webhook_secret` for an organization as automatically verified:
```
lib/shipit/github_app.rb:76-83
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
``` [3](#0-2) 

The multi-org secrets schema explicitly supports an organization configured with `webhook_secret: nil` (see the fixture `test/dummy/config/secrets_double_github_app.yml`, `OrgTwo`), for which `verify_webhook_signature` unconditionally returns `true`.

Once the request passes `verify_signature`, the actual event handler (any subclass of `Shipit::Webhooks::Handlers::Handler`, e.g. `PushHandler`, `StatusHandler`, `CheckSuiteHandler`, `PullRequest::*Handler`) resolves the target repository purely from `full_name`:
```
app/models/shipit/webhooks/handlers/handler.rb:32-38
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [4](#0-3) 

`Repository.from_github_repo_name` simply splits `owner/name` from that string and does a DB lookup, with no cross-check back to `repository_owner`/the app used for verification:
```
app/models/shipit/repository.rb:53-56
def self.from_github_repo_name(github_repo_name)
  repo_owner, repo_name = github_repo_name.downcase.split('/')
  find_by(owner: repo_owner, name: repo_name)
end
``` [5](#0-4) 

The binding that is broken (equality that should hold but doesn't):
`organization used to select webhook_secret for signature verification (repository.owner.login / organization.login)` == `repository actually acted upon (repository.full_name)`

An unprivileged, unauthenticated attacker (this endpoint has no session, no `ApiClient` token — it is reached by any POST to the public webhooks route) can craft a JSON body where:
- `repository.owner.login` = an organization configured in `Shipit.github` with `webhook_secret` unset/blank (this can occur in single-tenant deployments too if `webhook_secret` is left blank, which the app explicitly allows and treats as "trust unsigned"),
- `repository.full_name` = `"victim-org/victim-repo"`, a completely different, real, secured stack.

`verify_signature` will pass (because the org keyed off `repository.owner.login` has no secret), and the handler will then process the event against the victim stack identified by `repository.full_name`, with no signature check ever having covered that value.

### Impact Explanation
This crosses the "organization that authenticated versus the repository that is written" trust boundary explicitly called out as in-scope. Concretely, once a handler resolves an attacker-chosen `stacks` collection for a real, security-relevant repository:
- `PushHandler`/`StatusHandler` can forge commit sync and CI status updates for a target stack that the request was never actually verified for, feeding fabricated commit-status/CI state into `ci.require` checks that gate continuous deployment — this can influence whether commits are considered deployable/mergeable for a stack the attacker never proved control of.
- Because none of these events required possessing the victim organization's real `webhook_secret`, this is effectively a cross-repository forged-write path reachable by any unauthenticated party who can enumerate/guess an org name with no configured secret in the deployment's `Shipit.github` config.

This satisfies the High-tier bar ("escalation... unauthenticated read of stack state" is explicitly listed, and forged commit/CI status writes onto an arbitrary stack go further than read). It does not, on the evidence gathered, provide a direct RCE/credential-exfiltration/unauthorized-deploy primitive by itself (that would additionally require a specific handler that triggers a deploy/merge purely off webhook input, which I was not able to fully confirm within the remaining exploration budget for `merge`/`deployment_status` style events — those handler files were not fully read).

### Likelihood Explanation
Likelihood depends entirely on operator configuration: it requires (a) a multi-org `Shipit.github` config (i.e., `github_default_organization` non-nil) with at least one organization that has `webhook_secret` blank/unset, or a single-org deployment that has left `webhook_secret` unset entirely (which `verify_webhook_signature` explicitly tolerates via `return true unless webhook_secret`), and (b) the attacker being able to name that org in `repository.owner.login`/`organization.login`. Since the multi-org secrets schema is a first-class, documented feature (`TOP_LEVEL_GH_KEYS`, `github_app_config`), and per-org `webhook_secret` is optional, this is a realistic misconfiguration rather than a contrived one, but it is not exploitable against a fully-hardened deployment where every configured organization has a non-blank `webhook_secret`.

### Recommendation
- Verify the webhook signature using the GitHub App/secret that corresponds to the repository actually being acted upon (`payload.dig('repository', 'full_name')` owner), not a separately-read `repository.owner.login`/`organization.login` field, or require both to match before proceeding.
- Do not allow `verify_webhook_signature` to return `true` when `webhook_secret` is blank if any other configured organization does define a secret; either require every configured org to set a secret, or fail closed for organizations without one, rather than treating "no secret configured" as an implicit bypass.
- Reject/425 requests where `repository.owner.login` and `repository.full_name`'s owner segment disagree.

### Proof of Concept
Given a multi-org `Shipit.github` config where `OrgTwo` is configured with `webhook_secret: nil` (as in `test/dummy/config/secrets_double_github_app.yml`) and `AcmeCorp` (owning `acme/victim-repo`, a real tracked Stack) is configured with a strong secret:

```
POST /webhooks
X-Github-Event: push
X-Hub-Signature: sha1=anything-or-omitted
Content-Type: application/json

{
  "repository": {
    "owner": { "login": "OrgTwo" },
    "full_name": "acme/victim-repo"
  },
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha already known to exist/be reachable>"
}
```
1. `WebhooksController#verify_signature` calls `Shipit.github(organization: "OrgTwo")`, whose `webhook_secret` is `nil`, so `verify_webhook_signature` returns `true` regardless of the (bogus) `X-Hub-Signature` header — `lib/shipit/github_app.rb:76-77`.
2. `Shipit::Webhooks.for_event('push')` dispatches to `PushHandler`, whose `stacks` (via `Handler#stacks`/`#repository_name`) resolves `Repository.from_github_repo_name("acme/victim-repo")` — `app/models/shipit/webhooks/handlers/handler.rb:32-38`, `app/models/shipit/repository.rb:53-56` — targeting the real, secured `acme/victim-repo` stack even though the signature check was only ever performed against `OrgTwo`'s (absent) secret.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
