### Title
Cross-tenant Team membership write via unverified `organization.login` binding in `MembershipHandler#find_or_create_team!` - ([File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`Shipit::WebhooksController#verify_signature` only validates that the webhook signature matches *some* configured GitHub organization's secret (resolved from `repository_owner`), and never validates that the mutated `Team` actually belongs to that organization. `MembershipHandler#find_or_create_team!` looks up an existing team purely by `params.team.id` (GitHub numeric team id) and, when the team already exists, never re-checks or updates `Team#organization` against `params.organization.login`. An attacker who administers their own GitHub organization (with a legitimately configured `GithubHook::Organization` and thus a real `webhook_secret`) can therefore sign an arbitrary `membership` payload with their own secret while pointing `team.id` at a pre-existing `Team` record belonging to a completely different organization, and the handler will add/remove members on that victim team.

### Finding Description
The broken binding, stated as an equality that must hold but doesn't:
`repository_owner` (the org whose secret verified the payload) == `Team#organization` (the org that actually owns the mutated team).

Trace:
1. `verify_signature` computes `repository_owner` as `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` [1](#0-0)  A real GitHub `membership` webhook payload has no `repository` key, so `repository_owner` resolves to `params['organization']['login']` — a value fully controlled by the sender.
2. `verify_signature` then does `Shipit.github(organization: repository_owner).verify_webhook_signature(...)` and only checks the HMAC against that org's own configured `webhook_secret` [2](#0-1) . It never inspects `params.team` at all.
3. The verified body is parsed and dispatched: `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` [3](#0-2) .
4. `MembershipHandler#process` calls `find_or_create_team!`, which does `Team.find_or_create_by!(github_id: params.team.id) do |team| team.github_team = params.team; team.organization = params.organization.login end` [4](#0-3) . The block that assigns `team.organization` only runs on *creation*; when a `Team` with that `github_id` already exists (belonging to a different, victim organization), the block is skipped entirely and `params.organization.login` is never compared to the existing `Team#organization`.
5. `process` then resolves/creates the member by login and calls `team.add_member(member)` or `team.members.delete(member)` on whatever team was returned, unconditionally [5](#0-4) .

Attacker's request: an unsigned-looking but validly-HMAC'd POST to `/webhooks` with header `X-Github-Event: membership`, body:
```json
{"action":"added","team":{"id":<victim_team_github_id>,"name":"x","slug":"x","url":"https://example.com"},"organization":{"login":"attacker-org"},"member":{"login":"attacker-login"}}
```
signed with `attacker-org`'s own legitimately-configured `webhook_secret`. `verify_signature` succeeds because it only checks `attacker-org`'s secret against the raw body, which the attacker fully controls and signs correctly. `find_or_create_team!` then finds the pre-existing victim `Team` (matched by `github_id`) and `team.add_member(attacker's user)` runs, granting membership in a team the attacker does not own.

No other guard catches this: `drop_unhandled_event` only checks the event name is registered; the `ExplicitParameters` schema in `MembershipHandler` only validates types/presence of `team.id`, `organization.login`, `member.login`, not their relationship to each other or to any pre-existing record [6](#0-5) ; `force_github_authentication`/`User#authorized?` are irrelevant since this is an unauthenticated webhook endpoint (`WebhooksController` doesn't include `Authentication`).

### Impact Explanation
If the victim `Team` is one referenced in `Shipit.github_teams` (i.e., a team gating access to the Shipit UI, computed from `secrets.github.oauth.teams` and matched by `Team#id` in `User#authorized?`) [7](#0-6) [8](#0-7) , the attacker can add an arbitrary GitHub login (their own) as a `Membership` of that team, which directly grants that user `authorized?` status and full access to Shipit stacks, deploys and API-client management — an authentication/authorization bypass into `Shipit.github_teams` (High). Even for teams unrelated to authorization, this is still an unauthorized cross-tenant write: one organization's verified webhook mutates another organization's `Team`/`Membership` records. The attack is repeatable against any team whose numeric `github_id` the attacker knows or can enumerate, and requires no privileges beyond owning/administering one org already onboarded to the multi-org Shipit deployment.

### Likelihood Explanation
Preconditions: a multi-org Shipit deployment where multiple GitHub organizations each have their own `GithubHook::Organization` / secret (as in `test/dummy/config/secrets_double_github_app.yml`), and the attacker legitimately controls one of those orgs (thus has its `webhook_secret`). The attacker needs to know only the target team's numeric GitHub `id` (discoverable via the GitHub API/UI for any team they can view, or by brute force since it's a small integer namespace) — no other Shipit secret, session, or token is required. This is fully feasible and repeatable with plain HTTP requests.

### Recommendation
In `MembershipHandler#find_or_create_team!`, when the team already exists, verify that `existing_team.organization == params.organization.login` (case-insensitively) before proceeding, and raise/reject (or no-op) on mismatch rather than silently reusing the existing record. Additionally, `verify_signature` should be hardened so that the resolved `repository_owner`/organization used for signature verification is cross-checked against any organization referenced inside nested payload objects (`team`, `member`) that identify ownership, rather than trusting `params['organization']['login']` unconditionally.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (conceptual addition)
test ":membership from attacker-org cannot mutate a team belonging to another org" do
  victim_team = shipit_teams(:shopify_developers) # organization: 'shopify', github_id: 1
  # Configure two orgs with distinct secrets, e.g. via secrets_double_github_app.yml fixtures
  Shipit.stubs(:secrets).returns(multi_org_secrets_with('attacker-org', 'shopify'))

  attacker_secret = Shipit.github(organization: 'attacker-org').send(:webhook_secret)
  payload = {
    action: 'added',
    team: { id: victim_team.github_id, name: 'x', slug: 'x', url: 'https://example.com' },
    organization: { login: 'attacker-org' },
    member: { login: 'attacker-login' }
  }.to_json

  signature = "sha1=#{OpenSSL::HMAC.hexdigest('sha1', attacker_secret, payload)}"
  @request.headers['X-Github-Event'] = 'membership'
  @request.headers['X-Hub-Signature'] = signature

  # Binding under test, before:
  assert_not_equal 'attacker-org', victim_team.organization

  post :create, body: payload, as: :json
  assert_response :ok

  victim_team.reload
  # Binding under test, after: still should not equal, but membership was written cross-tenant
  refute_equal 'attacker-org', victim_team.organization
  assert victim_team.members.exists?(login: 'attacker-login') # demonstrates the unauthorized write
end
```
This demonstrates that `verify_signature` accepting `attacker-org`'s own secret is sufficient to mutate a `Team` whose real `organization` never matched, proving the provenance binding is broken.
