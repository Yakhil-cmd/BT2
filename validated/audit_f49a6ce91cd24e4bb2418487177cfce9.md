### Title
Cross-tenant Team/Membership mutation via divergent webhook verification org and attribution org - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects the GitHub App/secret used to authenticate a webhook based on `params.dig('repository','owner','login')` (falling back to `params.dig('organization','login')` only when `repository` is absent), while `MembershipHandler#find_or_create_team!` attributes the created/updated `Team` to `params.organization.login`. Because both fields are attacker-controlled JSON keys in the same POST body and are never checked for equality, a request that verifies under organization X's credentials can write a `Team` row scoped to organization Y.

### Finding Description
The claimed binding is: `repository_owner` (used to pick the verifying `Shipit::GitHubApp`) == `Team#organization` (the value written by the handler). Tracing the code shows these are independent reads of the same JSON body with no cross-check:

- `repository_owner` [1](#0-0)  resolves the verifying identity as `params.dig('repository','owner','login')`, only falling back to `params.dig('organization','login')` if `repository` is missing.
- `verify_signature` uses that value to fetch `Shipit.github(organization: repository_owner)` and calls `verify_webhook_signature` [2](#0-1) .
- `GitHubApp#verify_webhook_signature` short-circuits to `true` when no `webhook_secret` is configured for that org: `return true unless webhook_secret` [3](#0-2) .
- `MembershipHandler#find_or_create_team!` independently reads `params.organization.login` to set `team.organization` on create, with no reference at all to `repository_owner` or any consistency check against it [4](#0-3) .

Because the attacker fully controls the raw JSON body sent to the public `POST /webhooks` endpoint, they can include both a `repository.owner.login` (chosen to match an org X whose `webhook_secret` is unset, or whose secret the attacker knows) and an unrelated `organization.login` (target org Y) in the same `membership` event payload. `verify_signature` only proves the request was accepted for org X; it never proves the payload's `organization`/team-attribution fields belong to X. The handler then creates/mutates `Team` rows keyed by `organization: 'Y'`, and subsequent `added`/`removed` actions manipulate `Membership` rows on that team — effectively forging organization membership state for org Y using only org X's (or no) credentials.

Existing guards do not close this gap: `drop_unhandled_event` and `check_if_ping` only gate on event type/existence, not payload consistency; the `ExplicitParameters` schema on `MembershipHandler` only validates the shape/types of `organization.login`, `team.*`, `member.login` — it does not compare them against `repository_owner` [5](#0-4) ; and no model validation on `Team` enforces that `organization` matches the verifying webhook source.

### Impact Explanation
An attacker who can get any request accepted under org X's verification (either because X's `Shipit::GitHubApp` config has no `webhook_secret`, or because they otherwise know/forge a valid signature for X) can create or mutate `Team` and `Membership` records attributed to an arbitrary, unrelated organization Y (e.g. `shopify`) that they do not control and have no credentials for. Since `Shipit.github_teams` and other authorization surfaces key off `Team#organization`/membership, this is a cross-tenant write of authorization-relevant state, matching the Critical category ("a payload for one repository mutating another's stack, commit, task or team"). The attack is repeatable against any organization login string the attacker chooses to place in the `organization.login` field, for every `membership` event action (`added`/`removed`), enabling arbitrary team/member churn scoped to victim orgs.

### Likelihood Explanation
Exploitability is conditioned on Shipit's multi-tenant GitHub App configuration: it requires at least one configured organization (X) with no `webhook_secret` set (a plausible, permitted configuration state per `GitHubApp#verify_webhook_signature`'s `return true unless webhook_secret`), or an org whose secret the attacker otherwise possesses. Given that precondition, the attacker cost is trivial — a single unauthenticated `POST /webhooks` with a crafted JSON body containing mismatched `repository.owner.login` and `organization.login` — and it is fully repeatable against any target organization name known to the attacker. This is a real, demonstrable engine-level bug (missing equality check), but its severity in a given deployment depends on whether such an under-secured org entry exists in `Shipit.secrets.github`.

### Recommendation
In `MembershipHandler` (and any other multi-tenant-sensitive handler), assert that the attributed organization matches the verified `repository_owner`/verification identity before creating or mutating records — e.g., pass the verified organization through to handlers and require `params.organization.login == verified_organization`, rejecting the webhook otherwise. More generally, `WebhooksController#repository_owner` should not silently accept an attacker-suppliable `repository` key that is unrelated to the event's actual organization scope; the verification identity and the identity used for data attribution must be the same trusted value, not independently attacker-controlled JSON fields.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb
test ":membership binds Team.organization to the verified org, not an attacker-chosen org" do
  @request.headers['X-Github-Event'] = 'membership'

  # Org X ("attacker-org") is configured with no webhook_secret (or attacker knows its secret),
  # so verify_webhook_signature returns true unconditionally for it.
  Shipit.stubs(:github).with(organization: 'attacker-org').returns(
    stub(verify_webhook_signature: true)
  )

  body = {
    action: 'added',
    team: { id: 999, name: 'Forged Team', slug: 'forged-team', url: 'https://example.com' },
    organization: { login: 'shopify' },      # Y: victim org attributed by the handler
    member: { login: 'attacker' },
    repository: { owner: { login: 'attacker-org' } } # X: org used to select verification secret
  }.to_json

  assert_difference -> { Shipit::Team.count }, 1 do
    post :create, body: body, as: :json
    assert_response :ok
  end

  team = Shipit::Team.find_by(github_id: 999)
  # Binding under test: verifying org (X = 'attacker-org') should equal attributed org (Y = 'shopify').
  # It does not -- demonstrating the cross-tenant write.
  refute_equal 'attacker-org', team.organization
  assert_equal 'shopify', team.organization
end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
