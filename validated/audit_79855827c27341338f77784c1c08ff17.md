### Title
Stale delegate grants regain account-management authority when the position NFT returns to the granting owner - (File: contracts/controller/src/storage/account.rs)

### Summary

A delegate removed from power by an NFT transfer can silently regain authority if the NFT is later transferred back to the original owner. `get_delegates` validates grants solely by comparing `granted_by` with the current NFT owner, while `is_owner_or_delegate` accepts any listed active manager; nothing records that ownership changed in between. [1](#0-0) [2](#0-1) 

### Finding Description

`set_account_delegate` authenticates the current NFT owner and stores the delegate list under the account ID with `granted_by` set to that owner. [3](#0-2) 

When authorization is later checked, `get_delegates` returns that stored list whenever its stamped owner equals the NFT's current owner. [1](#0-0)  `is_owner_or_delegate` then authorizes an active position manager contained in that list. [4](#0-3) 

The position NFT exposes the standard non-fungible token interface, including ownership transfer functionality. [5](#0-4)  A direct NFT transfer therefore changes the resolved owner without removing the previous owner's delegate grant.

The code recognizes that stale grants can otherwise reactivate: `remove_delegate` explicitly deletes a grant whose `granted_by` no longer matches the caller, specifically to prevent reactivation if the NFT returns to the original owner. [6](#0-5)  However, deletion is only performed if a later owner invokes `remove_delegate`; an untouched stale grant survives the intermediate ownership period and becomes valid again on return to its original owner.

Delegate authority reaches account-management paths through `AccountGuard::Migrate` and `AccountGuard::Multiply`, which call `require_owner_or_delegate`. [7](#0-6)  For example, `flash_position` loads an existing account with `AccountGuard::Multiply`, so the stale manager can invoke it with the account's spoke and mode after authorization is revived. [8](#0-7) 

### Impact Explanation

A formerly revoked-by-transfer delegate can re-enter delegate-gated account flows without any new authorization from either the intermediate owner or the returning owner. [9](#0-8) 

Through `multiply`/`flash_position`-style flows, the stale delegate can choose the debt market, amount, receiver, callback data, collateral legs, and routing parameters for an account it no longer legitimately controls. [10](#0-9)  The attacker can extract economic value by keeping part of the borrowed proceeds or routing value through attacker-controlled venues while supplying only enough collateral for the transaction's post-operation checks, leaving the victim with debt and impaired collateral value. [11](#0-10) 

This is theft of user funds or account equity because the attacker is acting on stale authorization rather than a grant from the current ownership epoch.

### Likelihood Explanation

The trigger requires only ordinary NFT transfers and an existing delegate grant. The original owner can transfer the position NFT to any address, receive it back later, and the old manager's authority automatically revives when the stamped owner again equals `owner_of(account_id)`. [1](#0-0) 

No privileged action, leaked key, malformed parameter, or third-party service is required. The intermediate holder does not need to collude beyond returning the NFT, and the stale delegate can initiate the profitable transaction itself because delegate-gated paths authenticate the delegate as `caller`. [7](#0-6) 

### Recommendation

Bind delegate grants to an ownership epoch or transfer nonce rather than to the owner's address alone.

The NFT contract should maintain a monotonically increasing per-token ownership epoch that changes on every transfer, burn, or mint, and the controller should store that epoch in `DelegateGrant`; `get_delegates` should reject a grant unless both `granted_by` and the epoch match the NFT's current owner and epoch. Alternatively, the NFT must notify or expose a versioned ownership record so the controller can invalidate all existing grants atomically when ownership changes.

Add a regression test for:

1. Owner `A` grants manager `M`.
2. `A` transfers the NFT to `B`.
3. `B` transfers it back to `A`.
4. `M` attempts a delegate-gated operation.
5. The operation must fail unless `A` grants `M` again after regaining ownership.

### Proof of Concept

A source-level reproduction is:

1. `A` creates an account and obtains `account_id = N`.
2. `M` is registered as an active position manager.
3. `A` calls `add_delegate(caller=A, account_id=N, delegate=M)`, storing `DelegateGrant { granted_by: A, delegates: [M] }`. [12](#0-11) 
4. `A` calls the position NFT's standard `transfer` entrypoint to move token `N` to `B`.
5. Neither `A` nor `B` calls `remove_delegate`, so the stale `DelegateGrant` remains in persistent storage.
6. `B` calls `transfer` to return token `N` to `A`.
7. `M` calls `flash_position(caller=M, account_id=N, spoke_id=account.spoke_id, mode=account.mode, debt=<listed HubAssetKey>, amount=<positive borrow amount>, receiver=<attacker receiver contract>, data=<callback payload>, collaterals=<minimum collateral legs>, refund_assets=[])`.
8. `load_or_create_account` resolves the account owner as `A`, `get_delegates(N, A)` returns the stale list containing `M`, and `AccountGuard::Multiply` accepts `M`. [13](#0-12) [1](#0-0) 
9. The flow mints and forwards debt to `M`'s chosen receiver before invoking that receiver and collecting only the configured minimum collateral. [11](#0-10) 

Expected vulnerable result: `M` is authorized despite its grant predating the `A -> B -> A` ownership cycle. Expected fixed result: the stale grant is rejected because the ownership epoch changed.

/// Accepts the owner or a registered, active manager delegated by that owner.
pub(crate) fn is_owner_or_delegate(
    env: &Env,
    account_id: u64,
    caller: &Address,
    owner: &Address,
) -> bool {
    if caller == owner {
        return true;
    }
    let active_manager =
        storage::get_position_manager(env, caller).is_some_and(|config| config.is_active);
    active_manager && storage::get_delegates(env, account_id, owner).contains(caller)
}

/// Authenticates the NFT owner and updates delegates; grants require an active
/// manager. Emits an event only when the current owner's delegate list changes.
fn set_account_delegate(
    env: &Env,
    caller: &Address,
    account_id: u64,
    delegate: &Address,
    add: bool,
) {
    caller.require_auth();
    require_account_owner(env, account_id, caller);
    if add {
        // Reject dormant grants that could gain authority on later manager activation.
        assert_with_error!(
            env,
            storage::get_position_manager(env, delegate).is_some_and(|c| c.is_active),
            GenericError::NotAuthorized
        );
    }

    let changed = if add {
        storage::add_delegate(env, account_id, caller, delegate)
    } else {
        storage::remove_delegate(env, account_id, caller, delegate)
    };
