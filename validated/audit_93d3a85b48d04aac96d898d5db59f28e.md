Confirmed analog found. The signature-verification path in `WebhooksController` selects which organization's `webhook_secret` to verify against using an unverified, attacker-supplied field from the payload itself, before the signature has been checked.

### Title
Webhook signature verification key is selected using an unverified payload field, allowing cross-organization signature confusion in multi-org deployments - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` picks the `GitHubApp` (and thus the `webhook_secret` used for HMAC verification) by reading `repository.owner.login` / `organization.login` directly out of the still-unverified JSON body, before `verify_webhook_signature` has run. [1](#0-0) [2](#0-1) 

### Finding Description
In a single-organization deployment this is harmless, since there is only one `GitHubApp`/secret. However, Shipit explicitly supports a multi-organization configuration schema where each top-level key under `github:` in `secrets.yml` is a distinct organization with its own `webhook_secret`: [3](#0-2) [4](#0-3) 

`Shipit.github(organization:)` looks up the app config by the `organization` string, case-insensitively, and raises `GithubOrganizationUnknown` only if no matching key exists at all: [5](#0-4) 

The controller derives that `organization` argument entirely from the request body:
```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [2](#0-1) 

This is the exact analog of the reported bug class: a payload field (`repository.owner.login`) is *acted upon* (used to choose the cryptographic secret/binding) but is never itself covered or authenticated by the signature check that follows. The equality binding that should hold is:

`organization whose secret verifies the signature == organization that actually owns the repository being written to (webhook events applied)`

but the code instead lets the attacker's own payload dictate the left-hand side of that equality. Any org in the multi-org config whose `webhook_secret` is unset (`nil`) causes `verify_webhook_signature` to `return true unless webhook_secret` — i.e. verification is skipped entirely: [6](#0-5) 

An attacker who knows (or guesses) that any configured organization in the instance has a blank `webhook_secret` (a state explicitly shown as the example/default in the docs and test fixtures) can craft a forged webhook payload naming a *different, victim* repository/organization in the actual event fields, while setting `repository.owner.login` to the org with no secret. `verify_signature` resolves `Shipit.github(organization: 'org-with-no-secret')`, `verify_webhook_signature` returns `true` unconditionally, and the request proceeds to `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` with the full attacker-controlled `params`, including whatever repository/branch/commit fields the handlers key off of. [7](#0-6) 

### Impact Explanation
Webhook handlers act on tracked stacks/commits/statuses based on repository name/owner and commit SHAs taken from `params` (e.g., updating commit statuses, triggering continuous delivery via `status`/`check_suite` events, syncing pull request/merge state). By exploiting the unauthenticated `webhook_secret`-less org to bypass signature verification, an attacker can inject forged GitHub events for repositories tracked in the *other* (secured) organization, since the event/handler dispatch never re-validates that the events' repository fields belong to the organization whose secret was used. This can lead to fabricated commit statuses influencing merge-queue/continuous-deployment decisions, or a fully unauthorized deploy sequence if a forged event flips CI/status gates. That matches the "unauthorized deploy" criterion.

### Likelihood Explanation
Requires the instance to be configured for multiple GitHub organizations (an explicitly documented and supported feature) with at least one organization's `webhook_secret` left blank, which is exactly the value shown in the shipped example config and test fixtures. No credentials are needed — only an unprivileged HTTP request to the public `/github_authentication`-adjacent webhooks endpoint, so this is genuinely reachable by an unprivileged attacker in the documented multi-org setup.

### Recommendation
Do not let the attacker-controlled payload select the verification key. Either:
1. Enumerate all configured organizations' `webhook_secret`s and verify the signature against every one, only proceeding if exactly one, unambiguous match is found and cross-checking that its org matches `repository_owner`, or
2. Require `webhook_secret` to be present for every organization when running in multi-org mode (fail closed instead of `return true unless webhook_secret`), and additionally verify, post-signature-check, that the resolved `organization` actually matches the ownership of any stack referenced by the payload before dispatching handlers.

### Proof of Concept
1. Configure Shipit with two GitHub organizations, `SecureOrg` (has `webhook_secret` set) and `OpenOrg` (has `webhook_secret` left blank/nil), as in `test/dummy/config/secrets_double_github_app.yml`.
2. Attacker sends `POST /github_webhooks` (or engine-mounted webhook path) with header `X-Github-Event: status` and body:
```json
{
  "repository": { "owner": { "login": "OpenOrg" }, "name": "any" },
  "sha": "<sha of a commit tracked under SecureOrg's stack>",
  "state": "success",
  "branches": [{"name": "master"}]
}
```
3. `verify_signature` computes `Shipit.github(organization: 'OpenOrg')`, whose `webhook_secret` is nil, so `verify_webhook_signature` returns `true` immediately regardless of the (missing/garbage) `X-Hub-Signature` header. [6](#0-5) 
4. The request is accepted and `Shipit::Webhooks.for_event('status').each { |handler| handler.call(params) }` runs against the forged status payload for a commit that actually belongs to `SecureOrg`'s protected stack, without ever validating that `SecureOrg`'s (real) webhook secret was used.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

**File:** lib/shipit.rb (L170-200)
```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
