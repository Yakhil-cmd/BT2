### Title
Silent KAIA Loss on Low-Level Call to Non-Existent Recipient in `handleKLAYTransfer` — (`contracts/service_chain/bridge/BridgeTransferKLAY.sol`)

---

### Summary

`handleKLAYTransfer` in `BridgeTransferKLAY.sol` transfers KAIA to `_to` via a low-level call without verifying that `_to` is a live account. Per the EVM specification, low-level calls to non-existent accounts return `true`. If `_to` is a self-destructed contract, the `require(ok, ...)` guard passes silently, the bridge handle-nonce is permanently consumed, and the KAIA is irrecoverably sent to a dead address with no retry possible. The same unchecked pattern appears in `BridgeFee.sol` for the `feeReceiver` address.

---

### Finding Description

In `handleKLAYTransfer`, the bridge contract updates its state (nonce, event) and then sends KAIA via a bare low-level call:

```solidity
// BridgeTransferKLAY.sol lines 83-99
handleNoncesToBlockNums[_requestedNonce] = _requestedBlockNumber;
_updateHandleNonce(_requestedNonce);          // nonce consumed here

emit HandleValueTransfer(...);                // event emitted here

(bool ok, ) = _to.call.value(_value)("");    // line 98
require(ok, "handleKLAYTransfer: transfer failed");
```

The Solidity documentation states: *"The low-level functions `call`, `delegatecall` and `staticcall` return `true` as their first return value if the account called is non-existent, as part of the design of the EVM."*

If `_to` is a contract address whose code was removed via `selfdestruct` after the cross-chain transfer was initiated on the source chain, the call on line 98 returns `ok = true`. The `require` passes, the handle-nonce is permanently consumed (preventing any re-submission of the same request), and the KAIA balance is credited to the dead address — where it is inaccessible unless someone redeploys code there via `CREATE2`.

The identical unchecked pattern exists in `BridgeFee.sol` for the `feeReceiver` address:

```solidity
// BridgeFee.sol lines 49-50
(bool ok, ) = feeReceiver.call.value(fee)("");
require(ok, "transfer fee failed");
```

If `feeReceiver` is a self-destructed contract, the fee is silently lost and the transfer proceeds as if the fee was correctly paid.

Notably, the codebase already contains an `Address.isContract()` helper (using `extcodesize`) in `contracts/libs/openzeppelin-contracts-v2/contracts/utils/Address.sol`, and `SafeERC20` (which is imported by `BridgeFee.sol`) explicitly requires `address(token).isContract()` before its own low-level calls — but this guard is absent for the native KAIA transfer paths.

---

### Impact Explanation

- **Bridged KAIA permanently lost**: KAIA is sent to a dead address with no code to retrieve it.
- **Bridge handle-nonce consumed**: `_updateHandleNonce` runs before the transfer; after the silent "success", the nonce cannot be reused, making the transfer permanently unretriable.
- **False event emitted**: `HandleValueTransfer` is emitted before the call, signalling a completed transfer to off-chain monitors even though the recipient never received usable funds.
- **Fee receiver loss**: In `BridgeFee.sol`, a self-destructed `feeReceiver` causes fee KAIA to be silently lost on every `_requestKLAYTransfer` call.

---

### Likelihood Explanation

The trigger requires:
1. A user initiates a cross-chain KAIA transfer specifying a contract address as `_to` on the destination chain (no restriction in the protocol prevents this).
2. The contract at `_to` is self-destructed (by its owner) between the source-chain request and the bridge operators processing it on the destination chain.
3. Bridge operators — following normal protocol — call `handleKLAYTransfer` with the original `_to`.

Step 2 can be performed by the contract owner (who may be the same user), making this a user-triggerable loss scenario. The bridge operators have no on-chain mechanism to detect that `_to` no longer has code. The window between a cross-chain request and its handling can span multiple blocks, making the race condition realistic.

---

### Recommendation

Before the low-level call in `handleKLAYTransfer`, verify that `_to` is either an EOA (nonce > 0 or balance > 0) or a live contract. The simplest guard using the already-available `Address` library:

```solidity
// In BridgeTransferKLAY.sol, before line 98:
uint256 size;
assembly { size := extcodesize(_to) }
// If _to has no code and no prior balance/nonce, it may be a dead contract.
// Require code presence when _to is expected to be a contract:
require(size > 0 || /* _to is a known EOA */ true,
    "handleKLAYTransfer: recipient contract does not exist");
```

A more robust fix is to add an explicit existence check helper and apply it to both `_to` in `handleKLAYTransfer` and `feeReceiver` in `_payKLAYFeeAndRefundChange`:

```solidity
function _safeTransferKAIA(address payable _to, uint256 _value, string memory errMsg) internal {
    uint256 size;
    assembly { size := extcodesize(_to) }
    // Revert if _to looks like a destroyed contract (no code, no balance)
    if (size == 0) {
        require(_to.balance > 0 || /* nonce check via off-chain */ true,
            "safeTransferKAIA: recipient may be non-existent");
    }
    (bool ok, ) = _to.call.value(_value)("");
    require(ok, errMsg);
}
```

At minimum, move the `emit HandleValueTransfer` and `_updateHandleNonce` calls to **after** the transfer succeeds, so that a revert rolls back the nonce consumption and allows retry.

---

### Proof of Concept

1. Deploy `BridgeTransferKLAY` on the destination chain and fund it with KAIA.
2. On the source chain, call `requestKLAYTransfer` specifying `_to = address(victimContract)`.
3. Before bridge operators process the request, call `victimContract.selfDestruct()`.
4. Bridge operators call `handleKLAYTransfer(..., _to=victimContract, _value=X, ...)`.
5. Line 84 (`_updateHandleNonce`) consumes the nonce. Line 98 executes `victimContract.call.value(X)("")` — EVM returns `true` because the account is non-existent. Line 99 `require(ok, ...)` passes.
6. `X` KAIA is credited to the dead address. The handle-nonce is consumed. No retry is possible.
