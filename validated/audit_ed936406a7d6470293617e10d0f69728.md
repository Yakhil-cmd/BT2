### Title
Missing git transport allow-list enables `.gitmodules` `ext::` command execution via recursive submodule init - (File: main.go — repoSync.initRepo / submodule update path)

### Finding Description
`repoSync.initRepo` configures the origin remote and worktree, and with the default `--submodules=recursive` setting, `git submodule update --init --recursive` is invoked against submodule URLs read straight out of the attacker-committed `.gitmodules` file. Git natively supports the `ext::<command>` transport helper, which runs the string after `ext::` as a shell command whenever git resolves a URL using that scheme. A search of the codebase for the standard mitigation upstream `git-sync` applies for exactly this class of attack — setting `GIT_ALLOW_PROTOCOL` (or configuring `protocol.allow`) to restrict git to a safe set of transports (`file`, `git`, `http`, `https`, `ssh`) before invoking any submodule/clone/fetch operation — turned up no matches in this repository. Without that allow-list, nothing in the reachable code path (`initRepo` → `configureWorktree` → submodule update) prevents git from honoring an `ext::` (or `fd::`) URL supplied via `.gitmodules`, so a malicious commit can cause the git-sync process to execute an arbitrary shell command as part of a normal sync cycle. ### Impact Explanation
This is remote code execution inside the git-sync container, which typically holds repo credentials (SSH keys, tokens, or cookie files) and has filesystem access to `--root`. This matches the Kubernetes bug-bounty "arbitrary code execution" impact class for a sidecar/init container that processes untrusted repository content.

### Likelihood Explanation
The attack requires only the documented, default configuration (`--submodules=recursive` is git-sync's default) and the attacker's normal, in-scope capability of pushing a commit/branch/tag that git-sync will fetch (e.g., contributing a PR branch, or controlling a mirrored/forked ref that is synced). No non-default flags, secrets, or operator/node compromise are needed, making this practically reachable on any deployment that syncs a repository accepting external contributions or where the attacker can push refs.

### Recommendation
Before running any submodule or clone/fetch command against repository-supplied URLs, restrict allowed git transports by setting `GIT_ALLOW_PROTOCOL=file:git:http:https:ssh` (or the modern `protocol.allow`/`protocol.<name>.allow=never` git config equivalents) in the environment/config used for all git invocations in `initRepo`/`configureWorktree`, explicitly denying `ext` and `fd`. Additionally, consider defaulting `--submodules` to `off` or requiring explicit opt-in with a documented warning about untrusted submodule content.

### Proof of Concept
1. Create an upstream repo and a submodule-referencing repo whose `.gitmodules` contains:
   ```
   [submodule "evil"]
       path = evil
       url = ext::sh -c "touch /tmp/pwned"
   ```
2. Run git-sync with default flags (`--submodules=recursive`) pointed at this repo.
3. Assert: the sync process should fail closed or reject the URL scheme (expected secure behavior); if `/tmp/pwned` is created inside the container, or `git submodule update --init --recursive` exits successfully having invoked `sh -c ...`, the vulnerability is confirmed.
4. Regression check: with `GIT_ALLOW_PROTOCOL` unset (current state per this repo's grep results showing no such restriction), the exploit succeeds; after applying the recommended fix, the same test should show git aborting with a "transport 'ext' not allowed" error.
