### Title
Webhook signature verification uses an attacker-controlled organization field that is decoupled from the repository the payload actually targets, allowing cross-organization webhook forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks which GitHub App config (and therefore which `webhook_secret`) to validate an incoming webhook's HMAC against by reading `repository.owner.login` (or `organization.login`) straight out of the *unverified* JSON body, before the signature has been checked. The handler code that actually acts on the webhook (`PushHandler`, `StatusHandler`, etc.) independently reads `repository.full_name` from the same unverified body to select the `Stack`/`Repository` to operate on. Nothing ties these two payload fields together, so a signature that is valid for organization A can be attached to a payload whose `repository.full_name` targets organization B's repository.

### Finding Description
`verify_signature` in [1](#0-0)  does:
```ruby
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
```
where `repository_owner` is derived from the untrusted body itself: [2](#0-1) .

`Shipit.github(organization:)` resolves this attacker-supplied string to one of possibly several independently configured GitHub Apps/secrets (multi-org setups are an explicitly supported configuration, see `test/dummy/config/secrets_double_github_app.yml`) via [3](#0-2) .

The HMAC check itself, `GitHubApp#verify_webhook_signature`, only proves that *some* configured org's secret was used to sign the raw body — it proves nothing about which repository the body's `repository.full_name` refers to: [4](#0-3) .

After verification passes, `create` re-parses the same raw body and dispatches it to handlers keyed only by event type, with no re-check that the verifying organization matches the repository being acted on: [5](#0-4) .

Handlers then resolve the target `Repository`/`Stack` purely from `repository.full_name` in the same body, e.g. the base `Handler#stacks`/`#repository_name` [6](#0-5) , and `PushHandler#process`, which enqueues a sync against those stacks: [7](#0-6) .

**Binding broken:** *organization that authenticated the request (via `repository.owner.login` → selected `webhook_secret`)* ≠ *repository that is actually written to / acted upon (via `repository.full_name`)*. The signature only proves knowledge of one configured org's secret; it says nothing about the repository named elsewhere in the same JSON body.

### Impact Explanation
In any Shipit deployment configured with more than one GitHub organization (the multi-app config format Shipit explicitly supports), an attacker who can obtain or trigger a validly-signed webhook for *any one* of the configured organizations (e.g. their own org, where they administer the GitHub App or can read its webhook secret through normal use) can reuse that valid signature with a forged body whose `repository.owner.login` still names their own org (to pass `verify_signature`) but whose `repository.full_name`/`repository.id`/`sha` fields target a different, victim organization's repository/stack that is also configured on the same Shipit instance. Because `PushHandler`, `StatusHandler`, `CheckSuiteHandler`, and the pull-request handlers all resolve the acted-upon `Stack`/`Repository` solely from body fields, this allows triggering `GithubSyncJob`, fabricating commit statuses, or manipulating review-stack provisioning/archival for a repository the attacker does not control — an unauthorized action against another organization's stack, using Shipit's own configured GitHub credentials for that stack's deploy pipeline.

### Likelihood Explanation
Exploitability requires only a webhook signature valid for *any one* configured organization on the instance plus knowledge of another configured organization's repository name — both are realistically obtainable by any developer/admin with legitimate access to one org on a multi-tenant Shipit deployment, with no need for a Shipit session, API token, or write access to the victim repository.

### Recommendation
`verify_signature` should validate the webhook against the organization/app configuration derived from the actual repository being processed, and that same resolved organization must be the one used by every handler to look up `Repository`/`Stack` records — i.e., pin the verified organization for the remainder of the request and reject payloads whose `repository.full_name` owner does not match the organization whose secret validated the signature.

### Proof of Concept
1. Configure Shipit with two organizations, `OrgA` and `OrgB`, each with its own `webhook_secret` (as in `test/dummy/config/secrets_double_github_app.yml`), both hosting stacks on the same Shipit instance.
2. As a user with access to `OrgA`'s GitHub App webhook secret (e.g., an OrgA admin), compute a valid `X-Hub-Signature` for a JSON body of the form:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>",
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/victim-repo" }
}
```
3. POST this body with `X-Github-Event: push` and the OrgA-computed signature to `/webhooks`.
4. `verify_signature` resolves `repository_owner` = `"OrgA"`, fetches OrgA's `webhook_secret`, and the signature checks out — `head(422)` is never called.
5. `PushHandler#process` then resolves stacks via `Repository.from_github_repo_name("OrgB/victim-repo")` and enqueues `GithubSyncJob`/deploy sync for OrgB's stack, even though the attacker never possessed OrgB's webhook secret or any Shipit credentials for OrgB.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
