### Title
`StatusHandler#process` updates commit statuses for any repository sharing a `sha`, without validating the webhook's repository — ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` resolves target `Commit` rows purely by SHA (`Commit.where(sha: params.sha)`) and calls `create_status_from_github!` on every match, with no check that the payload's authenticated repository equals the repository of the `Stack` each `Commit` belongs to. Because `sha` is not scoped to a repository in this query, and because git commit SHAs are content-derived (not repo-derived), an attacker who reproduces the exact commit content of a public commit in their own fork/repo, or who otherwise causes SHA overlap, can send a `status` webhook signed for their own repository and have it write `Status` rows onto every `Stack`/`Commit` across any tenant that happens to share that SHA — including multiple environments (`production`, `staging`) of an unrelated victim.

### Finding Description
The claimed binding is: `payload.repository.full_name == commit.stack.repository.full_name` must hold for every `commit` touched inside the loop. In `app/models/shipit/webhooks/handlers/status_handler.rb`:

```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [1](#0-0) 

there is no filter on `commit.stack.repository`, `commit.stack_id`, or any reference to the repository that authenticated/signed the incoming webhook. `Commit#create_status_from_github!` unconditionally records a new `Status` and fires hooks:

```ruby
def create_status_from_github!(github_status)
  add_status do
    statuses.replicate_from_github!(stack_id, github_status)
  end
end
``` [2](#0-1) 

The webhook signature (`verify_signature`) only proves the payload came from GitHub for *some* repository configured with the same `webhook_secret` — it authenticates the sender, not which `Stack`/`Commit` rows may be mutated. Because a git commit SHA is a hash of tree, parent(s), author/committer identities and timestamps, and message — not of the repository name — any actor who can reproduce identical commit metadata in a repository they control (e.g., cloning a public commit and pushing it into their own repo/fork with unchanged author/committer dates) obtains an identical `sha`. The engine then treats that SHA as globally unique across all repositories/stacks, allowing a single forged/legitimate webhook from the attacker's own repo to fan out into every `Stack` row (regardless of tenant) whose `Commit.sha` matches.

None of the existing guards close this gap:
- `verify_signature`/GitHub App signature verification only proves the request was signed with a valid secret for the sending repository; it says nothing about `sha` ownership.
- `drop_unhandled_event` only filters event types, not scope.
- `ExplicitParameters` schema only validates payload shape (`sha`, `state`, etc.), not repository binding.
- No model validation ties `Commit.sha` uniqueness/authorization to a particular repository at write time in this code path.

### Impact Explanation
A single crafted/forwarded `status` webhook, authenticated only for the attacker's own repository, writes `Status` rows (and triggers `Hook.emit(:commit_status, ...)`/`:deployable_status` and `stack.schedule_merges`) against every `Stack`/`Commit` across the installation that shares the colliding `sha` — including multiple environments of a victim's repository (`production`, `staging`) in one request. This is a payload for one repository mutating another's stack/commit state, matching the Critical category ("a payload for one repository mutating another's stack, commit, task or team"). Effects include falsely marking victim commits as CI-passing, which can feed into `deployable?`/`schedule_continuous_delivery` and downstream automatic deploys.

### Likelihood Explanation
This requires the attacker to produce a commit with an identical SHA to a target commit already recorded as a `Commit` row for the victim's stack(s). For public repositories this is straightforward: fork/clone the exact commit (same tree, parents, author/committer identities and timestamps, message) into a repository the attacker owns, then have Shipit process a `status` event for that repo/commit (GitHub will emit this automatically, or the attacker can directly POST to `/webhooks` if they can otherwise produce a validly signed request for their own configured repository). No Shipit session, API token, or GitHub secret is needed beyond what the attacker already controls for their own repository. The victim precondition (same `Repository` used by multiple `Stack`s, e.g. multi-environment) is common in Shipit deployments.

### Recommendation
Scope the lookup and status application to the repository that authenticated the webhook: join/filter `Commit.where(sha: params.sha)` through `Stack` to `Stack#repository` and require `stack.repository == repository` (the repository resolved/authenticated for this webhook request) before calling `create_status_from_github!`, e.g. `Commit.where(sha: params.sha, stacks: { repository_id: repository.id }).joins(:stack)`, ensuring the binding `payload.repository == commit.stack.repository` holds for every iteration.

### Proof of Concept
Minitest plan (models/webhooks controller test, no live GitHub, using existing fixtures/signing helpers):
1. Create `victim/prod` `Repository`, and two `Stack`s on it (`production`, `staging`).
2. Create two `Commit` rows, one per stack, both with `sha: "deadbeef..."` (simulating same content commit in both environments).
3. Create an unrelated `attacker/evil` `Repository`.
4. POST to `/webhooks` a `status` event payload with `sha: "deadbeef..."`, `repository.full_name: "attacker/evil"`, signed with the secret configured for `attacker/evil`.
5. Assert `assert_no_difference -> { production_commit.statuses.count }` and `assert_no_difference -> { staging_commit.statuses.count }` around the request — currently this assertion FAILS because both counts increase by 1, demonstrating the payload for `attacker/evil` mutated `victim/prod`'s `production` and `staging` stacks.
