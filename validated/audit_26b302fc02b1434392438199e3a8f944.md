### Title
RAY-scaled market value overflow permanently freezes withdrawals, repayments, and liquidation - (File: common/src/rates/scaling.rs)

### Summary

**Severity: Medium**

A market whose scaled supply or debt value grows beyond `i128::MAX` causes every interest-accrual path to panic. Because all primary pool operations synchronize the market before mutating state, the market becomes unusable once its aggregate scaled value crosses the representable range.

### Finding Description

`accrue_step` unconditionally converts total scaled debt and total scaled supply into RAY-denominated values before calculating utilization or applying the borrow-index ceiling. [1](#0-0) 

Both conversions call `scaled_to_original`, which delegates to `Ray::mul`. [2](#0-1)  `Ray::mul` calls `mul_div_half_up`, which widens the intermediate product but still requires the final quotient to fit in `i128`; otherwise it returns `None` and panics with `MathOverflow`. [3](#0-2) [4](#0-3) 

The borrow-index ceiling does not prevent this condition. `update_borrow_index` caps the index only after `borrowed * borrow_index / RAY` has already been evaluated in `accrue_step`, so the aggregate value can overflow before index clamping becomes relevant. [5](#0-4) 

The public controller path `update_indexes(caller, assets)` is permissionless and forwards the assets to the pool. [6](#0-5) [7](#0-6)  The pool loads each market, calls `global_sync`, and commits only after synchronization succeeds. [8](#0-7) 

All normal market legs have the same dependency: `load_leg` calls `synced_market`, which calls `global_sync` before supply, borrow, repay, withdraw, seizure, or strategy accounting proceeds. [9](#0-8) 

### Impact Explanation

Once `borrowed * borrow_index / RAY` or `supplied * supply_index / RAY` exceeds `i128::MAX`, the transaction panics before `mark_accrued` or `commit` can execute. [10](#0-9) [8](#0-7) 

Because rollback leaves `last_timestamp` and the indexes unchanged, every subsequent operation reaches the same overflow. Suppliers cannot withdraw, borrowers cannot repay, liquidators cannot use paths that load the affected market, and protocol revenue on that market cannot be processed through accrual-dependent calls.

This permanently freezes the affected market in the deployed implementation unless governance upgrades the contracts to a fixed implementation. Rate-model replacement is not a current recovery path because it deliberately synchronizes the market before writing the new model. [11](#0-10) 

### Likelihood Explanation

Triggering the condition requires a very large market position and sufficient index growth. An unprivileged borrower can establish the debt through `borrow` if the market's configured caps, liquidity, collateral, and risk limits admit it; an unprivileged caller can then trigger the failed accrual through `update_indexes`.

The repository's own stress test demonstrates that a one-billion-whole-token 18-decimal market at high utilization overflows the aggregate RAY value before the borrow-index ceiling, after which both withdrawal and repayment fail with `MathOverflow`. [12](#0-11) 

The high capital requirement and dependence on a listed market reaching sustained high utilization reduce the likelihood, but the resulting market-wide freeze makes this more than a transaction-level fail-closed error.

### Recommendation

Do not require aggregate `scaled * index / RAY` to fit in `i128` during mandatory accrual.

Use one or more of the following changes:

- Return an `I256` value from aggregate debt/supply unscale operations used by accrual and utilization, rather than forcing the final result into `i128`.
- Apply the borrow-index ceiling before unbounded aggregate-value multiplication.
- Add a market-level solvency bound such that `borrowed * MAX_BORROW_INDEX_RAY / RAY` and `supplied * MAX_SUPPLY_INDEX_RAY / RAY` remain representable.
- If saturation is chosen, ensure repayment, withdrawal, liquidation, and bad-debt cleanup remain functional at the index ceilings rather than using the saturated value as an accounting balance.
- Add an emergency rate-model or accrual-recovery path that can handle an already-overflowing market without first performing the overflowing aggregate multiplication.

### Proof of Concept

The existing regression case constructs an admitted market with one billion 18-decimal tokens supplied and 98% utilization borrowed. It repeatedly invokes `update_indexes`; once the borrow index reaches approximately 170 times its initial value, `scaled_to_original` overflows `i128`, before `MAX_BORROW_INDEX_RAY` is reached. Subsequent withdrawal and repayment calls both fail with `MathOverflow`. [13](#0-12) 

A transaction-level equivalent is:

```text
1. supply(caller, 0, spoke_id, [(collateral_key, collateral_amount)])
2. supply(caller, account_id, spoke_id, [(debt_key, large_supply_amount)])
3. borrow(caller, account_id, [(debt_key, large_borrow_amount)], Some(caller))
4. Wait until:
   scaled_borrowed * borrow_index / RAY > i128::MAX
5. update_indexes(caller, [debt_key])
6. withdraw(...), repay(...), liquidate(...), and later update_indexes(...)
   all re-enter global_sync and panic before state is committed
```

/// Computes `x * y / d` rounded half up. Requires `x >= 0`, `y >= 0`, and `d > 0`; a
/// `debug_assert` checks this in debug builds. Panics with `GenericError::DivisionByZero` if
/// `d == 0`, and with `GenericError::MathOverflow` if any other precondition is violated or if
/// the result does not fit in `i128`.
pub fn mul_div_half_up(env: &Env, x: i128, y: i128, d: i128) -> i128 {
    // The zero check runs first so debug and release builds agree on a zero
    // divisor: both surface `DivisionByZero` rather than tripping the assert.
    require_nonzero_divisor(env, d);
    debug_assert!(
        x >= 0 && y >= 0 && d > 0,
        "mul_div_half_up: non-negative x, y and positive d"
    );
    try_mul_div_half_up(env, x, y, d)
        .unwrap_or_else(|| panic_with_error!(env, GenericError::MathOverflow))
}

pub(crate) fn global_sync(env: &Env, cache: &mut Cache) {
    if !cache.needs_accrual() {
        return;
    }

    let mut remaining = cache.elapsed_ms();
    while let Some(nonzero) = NonZeroU64::new(remaining) {
        let chunk = nonzero.get().min(MAX_COMPOUND_DELTA_MS);
        accrue_chunk(env, cache, chunk);
        remaining = remaining.saturating_sub(chunk);
    }

    cache.mark_accrued();
}

/// `i128::MAX`, 170 times that. At the XLM curve's steep segment the index
/// grows past 170x in a few years, and the next accrual panics inside
/// `scaled_to_original`. Every verb accrues first, so the market freezes:
/// no repay, no withdraw, no liquidation. The index cap never engages.
#[test]
fn a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap() {
    let mut t = LendingTest::new()
        .with_market(big("BIG18", 18, xlm_curve()))
        .with_market(col())
        .with_max_utilization_disabled_all_markets()
        .build();
    lift_caps(&t, "BIG18", 18);
    lift_caps(&t, "COL", 7);
    let principal = BILLION * 10i128.pow(18);
    t.supply_raw(BOB, "BIG18", principal);
    let debt = principal / 100 * 98;
    t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
    t.borrow_raw(ALICE, "BIG18", debt);

    let mut years = 0u32;
    let failure = loop {
        years += 1;
        assert!(
            years <= 40,
            "no cliff within 40 years; the bound in docs/reference/formulas.md is wrong"
        );
        t.advance_time(YEAR_SECS);
        if let Err(e) = t.try_update_indexes_for(&["BIG18"]) {
            break e;
        }
    };
    let failed: Result<(), soroban_sdk::Error> = Err(failure);
    assert_contract_error(failed, errors::MATH_OVERFLOW);
    let last = book(&t, "BIG18");
    assert!(
        last.borrow_index < MAX_BORROW_INDEX_RAY,
        "the index cap did not engage before the value overflow"
    );
    // The market is frozen: exits and repayments accrue first and hit the same panic.
    assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
    assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
