### Title
Stack-scoped API token can read CCMenu build status of any stack, bypassing the token's stack scope - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::CCMenuController` overrides the shared `stack` lookup helper from `BaseController` and resolves the requested stack directly against the global `Stack` relation instead of the caller's authorized scope, breaking the binding between "the stack an `ApiClient` token authorizes" and "the stack the request actually touches."

### Finding Description
`Shipit::Api::BaseController` enforces per-token stack scoping through two cooperating methods: [1](#0-0) 

`stacks` restricts the queryable set to `Stack.where(id: current_api_client.stack_id)` whenever the authenticated `ApiClient` is bound to a single stack (`stack_id?`), and `stack` resolves the requested id only within that restricted relation. Every other API controller (`DeploysController`, `RollbacksController`, `MergeRequestsController`, `StacksController`, etc.) relies on this shared `stack`/`stacks` helper, so a token created with a `stack_id` (see the `here_come_the_walrus` fixture bound to `stack: shipit`) can only ever resolve to its own stack, even if it also has a `read:stack`/`deploy:stack` permission grant.

`CCMenuController`, however, overrides `stack` to bypass the scoped `stacks` relation entirely: [2](#0-1) 

`stack` here calls `Stack.from_param!(params[:stack_id])` directly on the unscoped `Stack` model, not the scoped `stacks` helper used elsewhere. The `require_permission :read, :stack` check only verifies that the token carries the `read:stack` permission string (`ApiClient#check_permissions!`), it does not verify that the requested stack matches the token's `stack_id`: [3](#0-2) 

So the equality that should hold — `current_api_client.stack_id == requested_stack.id` (when the token is stack-scoped) — is never checked in this controller. Any `params[:stack_id]` value is accepted and resolved globally.

`CCMenuController` also supports authenticating via a query-string `token` parameter in addition to Basic Auth, which is how CCMenu/CI-status URLs are typically shared (embedded in build-status widgets), making the token likely to be handled/logged/shared outside of an Authorization header: [4](#0-3) 

### Impact Explanation
An `ApiClient` deliberately restricted to a single stack (a common pattern for third-party CI dashboards/status widgets that should only see one project's build status) can instead use its token to read the CCMenu/build-status payload — `name`, `activity`, `lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, `webUrl` — of **every** stack in the Shipit instance, including stacks belonging to unrelated repositories/teams. This is an unauthorized read of stack state across an authorization boundary that the token issuer explicitly set up (`stack_id` scoping), matching the "unauthenticated/unauthorized read of stack state" High-impact category: the attacker only needs a single stack-scoped, `read:stack`-permitted token (which is the intended, least-privileged token type for exactly this endpoint) to enumerate build status for arbitrary stacks.

### Likelihood Explanation
Likelihood is high for anyone who already holds a legitimately-issued, stack-scoped API token (the exact credential type this endpoint exists to serve, per the `here_come_the_walrus` fixture and the CCMenu use case). No additional privilege, session, or GitHub credential is required — only a change to the `stack_id` route segment/query parameter on a request that would otherwise be legitimate.

### Recommendation
Change `CCMenuController#stack` to resolve through the same scoped `stacks` relation used by `BaseController`/every other API controller (i.e. `stacks.from_param!(params[:stack_id])`) so that stack-scoped tokens cannot resolve stacks outside `current_api_client.stack_id`.

### Proof of Concept
1. Create/obtain a stack-scoped `ApiClient` token bound to `stack_id` = Stack A, with only the `read:stack` permission (e.g. equivalent to the `here_come_the_walrus` fixture in `test/fixtures/shipit/api_clients.yml`).
2. `GET /api/stacks/<Stack-A-owner>/<Stack-A-repo>/<Stack-A-env>/ccmenu?token=<token>` succeeds as expected.
3. `GET /api/stacks/<Stack-B-owner>/<Stack-B-repo>/<Stack-B-env>/ccmenu?token=<token>` — using the *same* Stack-A-scoped token but Stack B's identifiers — also succeeds and returns Stack B's build status, even though the token was never granted access to Stack B. Contrast with `DeploysController#index` (`GET /api/stacks/<Stack-B-...>/deploys?token=<token>`), which correctly 404s/empties out because it uses the scoped `stacks` helper.
