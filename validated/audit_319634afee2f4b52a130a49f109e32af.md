## Title
Webhook signature verified against attacker-selected organization while target repository is read from an unbound field, allowing cross-organization webhook forgery in multi-org deployments - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
In a multi-organization Shipit deployment (each GitHub organization has its own App/`webhook_secret`, as documented in `config/secrets.development.shopify.yml`), the webhook signature check and the target-repository lookup are derived from two independent, attacker-controlled fields of the same unauthenticated JSON body, with no binding between them.

### Finding Description
`WebhooksController#verify_signature` picks which `GitHubApp` (and therefore which `webhook_secret`) to validate the HMAC signature against using `repository_owner`, computed as `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`: [1](#0-0) [2](#0-1) 

`Shipit.github(organization:)` selects the app config (and its secret) purely by this string, looking it up in `secrets.github`: [3](#0-2) 

Once the signature passes, every event handler determines *which tracked repository/stack to act on* from a completely separate JSON field, `repository.full_name`, via `Handler#repository_name` / `Repository.from_github_repo_name`: [4](#0-3) [5](#0-4) 

Because `repository.owner.login` (used to select the verifying secret) and `repository.full_name` (used to select the acted-upon repository) are two distinct keys in the same raw JSON body, an attacker who legitimately controls one onboarded organization (and therefore knows/derives that organization's `webhook_secret` by triggering real GitHub events, or who otherwise has a valid webhook subscription for their own org) can craft a payload where:
- `repository.owner.login` = attacker's own org (so `Shipit.github(organization: repository_owner)` resolves to the attacker's known secret and the HMAC check passes), while
- `repository.full_name` = `<victim-org>/<victim-repo>` (an unrelated repository tracked by the same Shipit instance under a different GitHub App/org).

The equality the system implicitly relies on — *the organization whose secret authenticated the request* == *the organization owning the repository the handler mutates* — is never enforced. This is the direct analog of the reported bug class: a value trusted to gate an action (`feeRecipient`/fee settings in the report; here, the signing organization) is decoupled from the value actually used to perform the action (rewards recipient in the report; here, `repository.full_name` used for the DB lookup).

### Impact Explanation
Depending on which webhook event/handler is triggered, this can cause cross-repository state changes on repositories the attacker does not control, satisfying the "cross-repository writes" / "unauthorized deploy" bar:
- `PullRequest::OpenedHandler` calls `ReviewStack.find_or_create!`, which creates a review stack scoped to `repository.review_stacks` (resolved from the forged `full_name`) with a `branch` taken from the attacker-supplied `pull_request.head.ref`, and enqueues it for provisioning: [6](#0-5)  and [7](#0-6) . If the victim repository has `review_stacks_enabled`, this forces provisioning/deploy commands to run against the victim's own repository/branch — an unauthorized deploy triggered cross-organization.
- `PullRequest::ClosedHandler`/`LabeledHandler`/`UnlabeledHandler`/`ReopenedHandler` can archive/unarchive review stacks belonging to the victim repository.
- `PushHandler` can force a `sync_github` refresh against the victim's stacks using an attacker-chosen `expected_head_sha`.

The severity depends on operators actually running the multi-org configuration (each org with its own webhook secret) and on the target repository having review stacks / provisioning enabled, but the underlying binding gap exists unconditionally in the engine code itself.

### Likelihood Explanation
Exploitability requires: (1) the Shipit instance configured with multiple GitHub organizations/Apps sharing the single `/github/webhooks` endpoint (a documented, supported configuration), and (2) the attacker controlling — or having legitimately been granted — a webhook subscription for at least one of those organizations, so they can supply an arbitrary raw body whose HMAC they can compute with their own known secret. This is a lower bar than "GitHub App private key" or "ApiClient token" compromise: it only requires being an authorized member/admin of *any one* of the multiple organizations onboarded to the shared Shipit instance, not privileged access to the victim organization or repository.

### Recommendation
Bind the signature-verification identity to the identity used for repository resolution: derive both the signing organization and the acted-upon repository from the same trusted source, or explicitly verify (post-signature-check) that `repository.full_name.split('/').first == repository_owner` before dispatching to any handler, rejecting mismatches with `422`.

### Proof of Concept
1. Configure Shipit with two organizations, `org-a` (attacker-controlled, webhook secret known to the attacker) and `org-b` (victim, owns `org-b/victim-repo`, tracked by this Shipit instance with `review_stacks_enabled`).
2. Attacker crafts a `pull_request` "opened" webhook JSON body with `repository.owner.login = "org-a"` and `repository.full_name = "org-b/victim-repo"`, `pull_request.head.ref = "arbitrary-branch"`.
3. Attacker computes `X-Hub-Signature` using `org-a`'s known webhook secret and POSTs to `/github/webhooks`.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: "org-a")`, verifies successfully against the attacker's own secret.
5. `PullRequest::OpenedHandler` resolves `repository` via `Repository.from_github_repo_name("org-b/victim-repo")` and, if provisioning conditions are met, creates and enqueues a review stack for provisioning against `org-b/victim-repo` on the attacker-chosen branch — despite the request never being authenticated by `org-b`'s webhook secret.

```ruby
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
```

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
