### Title
Webhook signature verification is optional and defaults to fully unauthenticated event processing - (File: `lib/shipit/github_app.rb`)

### Summary
`GitHubApp#verify_webhook_signature` treats the absence of a configured `webhook_secret` as an implicit pass, exactly mirroring the reported issue: a security control exists but is opt-in rather than enforced, so the "authenticated organization" side of the binding can be entirely absent while the "repository being written" side is still fully attacker-controlled.

### Finding Description
`WebhooksController#verify_signature` looks up the GitHub App config for the organization named in the *unauthenticated* payload and asks it to verify the signature: [1](#0-0) [1](#0-0) 

That verification is implemented as: [2](#0-1) 

`return true unless webhook_secret` means that if the deployer never configured `webhook_secret` (it is explicitly presented as optional in the setup docs and secrets template), **every** request to `/webhooks` is accepted as authentic regardless of signature, sender, or organization: [3](#0-2) [4](#0-3) 

Once past `verify_signature`, the raw JSON body is dispatched to handlers keyed only by the client-supplied `X-Github-Event` header and payload contents: [5](#0-4) 

Several handlers act on state using only fields taken from this unauthenticated payload:
- `StatusHandler` creates a CI status for **any** commit matching a client-supplied SHA, with no repository scoping at all: [6](#0-5) 
- `PushHandler` triggers a GitHub sync to an attacker-chosen `expected_head_sha` for any stack matching the attacker-supplied repository/branch: [7](#0-6) 

The fabricated CI status is exactly what `MergeRequest` uses to gate an automated merge: [8](#0-7) [9](#0-8) 

The broken binding is: **the organization that "authenticated" the webhook request (none, when `webhook_secret` is unset) versus the repository/commit that is actually written to** (fully attacker-chosen via payload fields). This is structurally identical to the reported Android issue — a security control (Network Security Configuration / HMAC signature verification) exists but is not enabled by default, so the app silently accepts unauthenticated/unencrypted input as trusted.

### Impact Explanation
An unauthenticated attacker who can reach the public `/webhooks` endpoint (which must be internet-reachable by design, per GitHub's webhook delivery model documented in `docs/setup.md`) can, on any deployment that has not set `webhook_secret`:
- Forge `status` events to mark arbitrary commits as CI-passing, satisfying `reject_unless_mergeable!`'s CI checks and enabling an **unauthorized merge** through the merge queue.
- Forge `push` events to force `GithubSyncJob` to sync a stack's head to an attacker-chosen SHA, influencing which commit becomes deployable.
- Forge `membership`/`pull_request` events to create/delete `Team` memberships or archive/unarchive review stacks.

This reaches the "Critical – an unauthorized deploy, rollback, or merge" impact bucket.

### Likelihood Explanation
`webhook_secret` is documented as optional (`config/secrets.development.example.yml`, `docs/setup.md`), so this is a realistic, in-scope default-configuration state, not a documented misuse of the engine. No GitHub App private key, `ApiClient` token, or session is required — only network reachability to the standard webhook endpoint.

### Recommendation
Make `webhook_secret` mandatory (fail closed) rather than optional in `GitHubApp#verify_webhook_signature`, and scope `StatusHandler`/`PushHandler` lookups to the repository named in the payload rather than global commit-SHA matches.

### Proof of Concept
1. Deploy Shipit without setting `github.webhook_secret` (an explicitly supported, documented configuration).
2. `POST /webhooks` with header `X-Github-Event: status` and body `{"sha":"<victim commit sha>","state":"success","context":"ci/required","repository":{"owner":{"login":"<any org>"}}}` — no `X-Hub-Signature` needed since `verify_webhook_signature` short-circuits to `true`.
3. The forged success status is created via `Commit#create_status_from_github!`, satisfying `MergeRequest#reject_unless_mergeable!`'s CI gate for that commit, enabling an unauthorized merge.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
