### Title
Cross-organization CI status injection via webhook signature scoped to attacker-chosen `repository.owner.login` while status writes are unscoped by repository - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App's secret to verify a webhook's HMAC signature with, based on `repository.owner.login` (or `organization.login`) taken directly from the unauthenticated request body. [1](#0-0) [2](#0-1)  Once that check passes, the `status` event handler applies the same payload's `sha`/`state` to **any** `Commit` row in the database matching that SHA, with no scoping to the organization that was used for signature verification, nor to the `repository.full_name` in the same payload. [3](#0-2) 

### Finding Description
Multi-org Shipit deployments configure one `GitHubApp` per GitHub organization, each with its own optional `webhook_secret`. [4](#0-3)  `GitHubApp#verify_webhook_signature` explicitly treats an unset secret as "always verified": `return true unless webhook_secret`. [5](#0-4)  This is a documented, supported configuration - the README's multi-org example and the test fixtures both show `webhook_secret:` left blank per organization. [6](#0-5) [7](#0-6) 

The controller picks *which* organization's app/secret to check against using an attacker-controlled field of the same unauthenticated JSON body:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(...)
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [8](#0-7) 

The event is then dispatched to handlers with the raw, parsed JSON body, unmodified: `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`. [9](#0-8) 

`StatusHandler#process` writes a GitHub-commit-status record for **every** local `Commit` whose SHA matches `params.sha`, regardless of which repository/stack it belongs to:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [3](#0-2) 

Binding broken: **organization authenticated (`repository.owner.login` used to pick the `GitHubApp`/secret) ≠ repository whose commit-status data is written (`Commit.where(sha:)`, unscoped)**. If any single organization configured in Shipit has no `webhook_secret` (a supported, documented setup), an attacker can send a forged `status` webhook claiming `repository.owner.login` equal to that unsecured organization, trivially pass `verify_signature`, and set `sha`/`state` to target a commit SHA that belongs to a completely different, security-sensitive stack/organization also configured in the same Shipit instance. `Commit.where(sha:)` performs no repository/stack filtering, so the forged status is attached to the real commit.

### Impact Explanation
Injected/forged commit statuses feed directly into deploy and merge-queue gating: `MergeRequest::StatusChecker` (built on `Status::Group`) determines `all_status_checks_passed?`/`any_status_checks_failed?`/`missing?` from exactly these `Status` rows, and `MergeRequest#reject_unless_mergeable!`/`#merge!` use that result to decide whether a pull request may be auto-merged. [10](#0-9)  A forged "success" status for a required CI context can cause Shipit to consider an unreviewed/failing commit as CI-passing, letting the merge queue proceed to call `stack.github_api.merge_pull_request(...)` and merge it - an unauthorized merge, matching the "Critical: unauthorized deploy, rollback or merge" impact category. The same commit is also used for deployability checks feeding continuous deployment (`Status#schedule_continuous_delivery`, `Status#enable_ci_on_stack`). [11](#0-10) 

### Likelihood Explanation
Requires (1) a multi-org Shipit instance where at least one configured organization has no `webhook_secret` set - an explicitly documented, supported configuration, not a bug in itself - and (2) knowledge of a target commit's SHA, which is public information visible on the corresponding GitHub pull request/commit page. No GitHub App private key, `webhook_secret`, session, or `ApiClient` token is required for the second, security-sensitive organization. The webhook endpoint is a fixed, unauthenticated route reachable by anyone.

### Recommendation
Do not select the verification secret using attacker-supplied payload fields. Either require `X-Hub-Signature` verification against every configured organization's App (or a global fallback) rather than one chosen from the payload, and/or reject unsigned/`webhook_secret`-less configurations from being usable to satisfy verification for events pertaining to other organizations. Additionally, `StatusHandler` (and any other handler) should scope commit/status writes to the repository asserted in the same verified payload (`repository.full_name`) rather than matching by bare SHA across the entire database.

### Proof of Concept
1. Operator configures Shipit with two orgs in `secrets.yml`: `low-security-org` (no `webhook_secret`) and `high-security-org` (with `webhook_secret` set), per the documented multi-org format. [6](#0-5) 
2. Attacker finds the SHA of an open, unreviewed PR's head commit in `high-security-org/critical-repo` (public on GitHub) that is registered as a Shipit stack.
3. Attacker POSTs to `/github/webhooks` with header `X-Github-Event: status` and body:
```json
{
  "sha": "<head-sha-of-target-pr>",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "low-security-org" } }
}
```
No valid `X-Hub-Signature` is needed because `low-security-org` has no `webhook_secret`, so `verify_webhook_signature` returns `true` unconditionally. [5](#0-4) 
4. `StatusHandler#process` finds the `Commit` with that SHA (belonging to `high-security-org/critical-repo`) and creates a `success` `Status` for it, with no check that the commit's repository matches `low-security-org`. [3](#0-2) 
5. On the next merge-queue evaluation, `MergeRequest#all_status_checks_passed?` sees the forged status and the PR can be merged even though it never actually passed the required CI check. [12](#0-11)

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
