### Title
L1 BTC lockup proofs can be reused across unrelated bond registrations because pox-5 never persists a "consumed" outpoint record - ([File: stackslib/src/chainstate/stacks/boot/pox-5.clar])

### Summary
`register-for-bond` accepts a Bitcoin timelock UTXO as proof of collateral via `verify-l1-lockups` / `validate-l1-lockup`. The only anti-replay control (`seen-outpoints`) is scoped to the single call's `fold` and is discarded once the function returns. There is no contract-level map that marks a `(txid, output-index)` outpoint as already credited to a bond. As a result, the exact same on-chain Bitcoin lockup ("escrow") can be presented again in a later, independent `register-for-bond` call to join a different (or the same, once vacated) bond, crediting `sats-total` a second time even though no additional BTC was ever locked.

### Finding Description
`validate-l1-lockup` verifies four things about a caller-supplied lockup: the script hash matches `construct-lockup-output-script(staker, unlock-burn-height, ...)`, the amount matches, the block header is a real burn header, and the merkle proof places the tx in that block. [1](#0-0) 
Deduplication of outpoints is only performed via the `seen-outpoints` accumulator inside the single `fold` call: [2](#0-1) [3](#0-2) 
That accumulator is a local variable, never written to persistent contract state, so it offers no protection across separate transactions/calls.

`register-for-bond` computes `sats-total` from this proof and stores it directly into the new bond's membership and aggregate counters: [4](#0-3) [5](#0-4) 
The only "already used" guard for the caller is `bond-overlaps-new-position?`, which checks the staker's single, current `protocol-bond-memberships` entry — it says nothing about whether the specific L1 UTXO backing that membership was already spent-for-credit in a prior (now-ended) membership: [6](#0-5) 

Because the underlying Bitcoin UTXO's script commits only to `(staker, unlock-burn-height, staker-unlock-bytes, early-unlock-bytes)` — not to a specific bond-index or a one-time nonce — and `unlock-burn-height` is a value the staker/contract picks (constrained only by `>= minimum-unlock-height` of the bond being joined at proof time), a single locked UTXO whose baked-in unlock height is far enough in the future satisfies the `minimum-unlock-height` check of many different, sequential bonds. Once a staker's earlier bond membership ends (naturally, via unstake, or via any state clearing the `protocol-bond-memberships` entry), nothing prevents them from calling `register-for-bond` again with the identical `(tx, output-index, header, leaf-hashes, ...)` tuple to join a new bond, re-crediting `sats-total` sats that are still locked in the very same still-unspent UTXO that was already used to earn membership/rewards once.

This is the "escrow reuse" bug class applied to pox-5: the L1 lockup functions as an escrow attesting that BTC is committed as collateral, but the same escrow attestation can be replayed indefinitely to open new bond memberships, so the contract's bookkeeping of "sats staked/credited" no longer corresponds 1:1 with real, distinct Bitcoin collateral commitments.

### Impact Explanation
Each successful replay lets a staker be counted as contributing `sats-total` sats of L1 collateral to `protocol-bonds-total-staked` and to their own `amount-sats` in `protocol-bond-memberships`, without locking any new BTC. Since reward computation (`calculate-rewards`) and signer voting weight scale with recorded `amount-sats` / `sats-total`, this lets an attacker earn sBTC/STX bond rewards, and reward/voting weight, that exceed what is actually backed by locked Bitcoin — a double-counting of a single committed BTC amount across multiple bonds. This falls under the Critical category ("sats credited by an L1 proof that were never locked on Bitcoin," "double-counting a commitment or reward").

### Likelihood Explanation
No special privileges are needed — any allow-listed staker who once legitimately locked BTC can replay their own proof for any subsequent bond they're eligible for, as long as their prior membership has ended (a normal, expected state transition, not an edge case). No collusion with the bond admin, signer, or another user's key is required. The only friction is the `minimum-unlock-height` check against the newly-joined bond, but a staker can simply choose a distant `unlock-burn-height` when constructing the original lockup script so the same UTXO qualifies for many future bonds.

### Recommendation
Persist a record of every L1 outpoint that has ever been credited (e.g., a `define-map used-l1-outpoints {txid, output-index} bool`), and check/set it inside `validate-l1-lockup` (or `verify-l1-lockups`) so that once an outpoint has funded one bond membership it can never be presented again for a different registration, regardless of how much time has passed or how many prior memberships have ended.

### Proof of Concept
1. Staker locks `X` sats into the canonical P2WSH lockup script (`construct-lockup-output-script`) with a distant `unlock-burn-height` (e.g., far beyond the next several bonds' minimum unlock heights), as shown in the integration test flow in `stacks-node/src/tests/pox_5_integrations.rs`. [7](#0-6) 
2. Staker calls `register-for-bond` for bond A, submitting the proof `(tx, output-index, header, leaf-hashes, amount=X, unlock-burn-height)`. `validate-l1-lockup` passes all checks; `sats-total = X` is credited to bond A's membership and totals. [5](#0-4) 
3. Bond A's term ends (or the staker exits), clearing `protocol-bond-memberships` for the staker; the Bitcoin UTXO itself remains untouched/unspent (its BTC timelock hasn't matured, or even if matured, the staker just never spends it).
4. Staker calls `register-for-bond` again for a new bond B, submitting the exact same `(tx, output-index, header, leaf-hashes, amount=X, unlock-burn-height)` proof. `bond-overlaps-new-position?` passes (no current membership), `validate-l1-lockup` passes again (nothing tracks that this outpoint was already consumed), and `sats-total = X` is credited a second time to bond B — for the same physical BTC that already earned credit/rewards under bond A.
