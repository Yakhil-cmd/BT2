### Title
Unauthenticated `X-Shipit-User` header lets any API client impersonate arbitrary users for merges, deploy approvals and locks - ([File: app/controllers/shipit/api/base_controller.rb])

### Summary
The `Settlement` bug class described in the external report is a *trust-binding gap*: an action is executed under an identity/authority that was never actually verified to belong to the entity performing the action (stale/forged signer vs. real signer). Shipit-engine has a direct analog: the API layer resolves `current_user` — the identity attributed to and, in some cases, authorizing, an action — purely from a self-asserted `X-Shipit-User` request header, with no cryptographic or session-based proof that the caller is that user.

### Finding Description
`Api::BaseController#identify_user` binds `current_user` to whatever login string the caller supplies in the `X-Shipit-User` header, with a simple case-insensitive DB lookup and no verification that the request actually originates from that user: [1](#0-0) 

Authentication of the *request* only proves the caller holds a valid `ApiClient` token; it establishes nothing about the human identity claimed via the header: [2](#0-1) 

That unauthenticated `current_user` is then propagated to `require_permission!`/model logic in security-relevant places that are documented as trusting the field for author attribution, e.g. `MergeRequestsController#update` calls `MergeRequest.request_merge!(stack, params[:id], current_user)` and `ReleaseStatusesController#create` calls `deploy.report_healthy!(user: current_user)` / `report_faulty!(user: current_user)`: [3](#0-2) [4](#0-3) 

`LocksController` similarly binds `stack.lock(params.reason, current_user)` to the spoofed identity, which becomes the persisted `lock_author`: [5](#0-4) 

The equality that should hold but is broken is:
`GitHub identity that actually issued the request == User record bound to the action's authorship/authorization`.
In practice, the only credential checked is the `ApiClient` bearer token (`ApiClient.authenticate`, `check_permissions!`), which authorizes an *operation class* (e.g. `deploy:stack`, `lock:stack`) but says nothing about *who* the human actor is. Any holder of a token with the relevant scope can set `X-Shipit-User` to the login of any existing `User` (e.g. a repo admin, a team lead, or the bot account) and have Shipit record that user as having approved, locked, merged, or health-checked a release — this is directly analogous to the report's core flaw: an authorization decision is made based on an identity/authority binding that is asserted by the attacker rather than verified by the protocol.

This is confirmed as intended/tested behavior, not a hypothetical: the test suite explicitly documents that the header is trusted verbatim to set deploy authorship: [6](#0-5) 

### Impact Explanation
An attacker holding any valid `ApiClient` token (e.g. a low-scoped CI integration token with only `deploy:stack`/`lock:stack`) can forge the identity of a different, more privileged or more trusted human user for every action that records/authorizes via `current_user`: merge-request approvals (`MergeRequest.request_merge!`), deploy health/faulty reporting (`report_healthy!`/`report_faulty!`), and stack locking/archiving. This corrupts the audit trail of who approved a merge or signaled a release healthy, and can be used to attribute a malicious/unsafe action to an innocent user, or to make an unauthorized actor appear as the legitimate approver of a merge into a deployable branch — this maps to the rules' "unauthorized ... merge" impact category, since `MergeRequest.request_merge!` is invoked with a forged `current_user` that the merge-queue logic treats as the actor requesting the merge.

### Likelihood Explanation
Likelihood is moderate-to-high in any deployment that issues scoped `ApiClient` tokens to multiple integrations/services (a common Shipit setup, e.g. CI systems triggering deploys). Any such token holder, regardless of the scope granted, can set an arbitrary `X-Shipit-User` value; the header is not restricted to a subset of trusted callers, and there is no separate credential check tying the header value to the token owner.

### Recommendation
Do not treat `X-Shipit-User` as authoritative. Either remove the header-based identity mechanism entirely (attribute actions to a per-`ApiClient` service identity) or require an explicit, scoped permission (e.g. `impersonate:user`) plus a signed assertion (e.g. an internally issued JWT/`ActiveSupport::MessageVerifier` token identifying the human) rather than a bare login string that any token holder can supply.

### Proof of Concept
1. Obtain any `ApiClient` token with `deploy:stack` scope (as documented/tested in `test/controllers/api/deploys_controller_test.rb`).
2. `POST /api/stacks/:owner/:repo/:env/deploys` with header `X-Shipit-User: <victim-login>` and `sha: <commit>`.
3. Observe `Deploy.last.user == User.find_by(login: 'victim-login')`, i.e. the deploy is attributed to the victim although the victim never made the request — as directly exercised by the existing test `"#create use the claimed user as author"` [7](#0-6) . The same pattern applies to `Api::LocksController#create` (forged `lock_author`) and `Api::MergeRequestsController#update` (forged merge requester).
