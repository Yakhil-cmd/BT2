### Title
Frozen `last-update` timestamp during zero-rate periods causes retroactive interest burst that overcharges borrowers and is socialized to all vault-share holders - (File: `mainnet/contracts/vault/v0-vault-stx.clar` and equivalent v0-vault-* contracts)

### Summary
The `accrue` function in each Zest v0 vault contract only advances `last-update` when the computed `index`/`lindex` actually changes. When the interpolated borrow rate is `0` (a normal, DAO-configurable curve point), `next-index`/`next-liquidity-index` equal the current `index`/`lindex`, so `last-update` is left stale. Once the rate later becomes positive, the very next call to `accrue` treats the *entire* elapsed time — including the whole zero-rate window — as if it accrued interest at the new positive rate, producing a single retroactive interest burst.

### Finding Description
`accrue` computes elapsed time from `last-update`: [1](#0-0) 

and only bumps `last-update` when `index` or `lindex` actually changed: [2](#0-1) 

`calc-multiplier-delta` computes the multiplier from `rate * time-delta`; if `rate` (from `interest-rate`, derived from the DAO-controlled `points-ir` curve) is `0`, the multiplier equals `INDEX-PRECISION` regardless of how large `time-delta` is, so `next == idx`: [3](#0-2) 

This is structurally identical to the reported bug in `accumulate_strategy_reward`/`accumulate_strategys_reward`, where `last_reward_time` is not advanced whenever `emission_per_second == 0`. Here, `last-update` is not advanced whenever the resulting index doesn't move, which happens whenever the effective rate is zero. DAO rate changes explicitly call `accrue()` *before* updating the curve (using the still-zero old rate), so the stale timestamp survives the rate change itself: [4](#0-3) 

Every vault entrypoint (`deposit`, `redeem`, `system-borrow`, `transfer`, etc.) calls `accrue()` first: [5](#0-4) [6](#0-5) 

so whichever unprivileged user happens to interact with the vault first after the rate turns positive triggers the full retroactive burst: `debt-delta` (and thus each borrower's owed debt, `total-debt`) jumps by an amount computed as if the new positive rate had applied for the entire frozen window, even though borrowers only actually incurred debt while the true rate was zero. That inflated `debt-delta` simultaneously raises `total-assets`, which raises the share price of `zft` for every current holder and mints extra `treasury-lp` to `dao-treasury` — i.e., the erroneous charge is socialized across all suppliers/shareholders at the direct expense of borrowers who took on debt during the zero-rate window.

### Impact Explanation
Borrowers who took loans while the effective rate was zero are retroactively charged interest for that entire period at whatever rate is later configured, with no way to avoid or contest it — this is a direct, protocol-caused theft of value from borrowers' collateral-backed positions, socialized as unearned yield to all current `zft` holders and the DAO treasury. This matches the in-scope impact class of theft of user funds (borrower debt inflated beyond what was actually owed) and/or theft of unclaimed yield (LPs/treasury receive interest that was never actually earned during the frozen window).

### Likelihood Explanation
This requires no attacker privilege or DAO compromise: a zero-rate curve point is a normal, expected DAO configuration (the default `points-ir` is `{util: u0, rate: u0}`), and any ordinary vault interaction (deposit, borrow, repay, redeem, transfer) during that window silently perpetuates the stale timestamp. The burst fires automatically on the first subsequent interaction after the rate becomes positive, with no special timing needed by any party — the borrower harm is deterministic and reachable through routine protocol use.

### Recommendation
Update `last-update` to `stacks-block-time` on every call to `accrue()` regardless of whether `index`/`lindex` changed, mirroring the patch applied for `accumulate_strategy_reward`/`accumulate_strategys_reward` (commit `971cfd9`), so elapsed time during zero-rate periods is never later charged at a subsequently configured rate.

### Proof of Concept
1. DAO configures `points-ir` such that utilization/rate curve yields `rate = 0` (e.g., default state, or a curve segment at low utilization).
2. Some borrower opens debt (`system-borrow`) while `rate == 0`; `principal-scaled` becomes nonzero, `last-update` reflects the time of this borrow (or earlier).
3. Time passes (e.g., weeks) with the rate remaining `0`. Any vault call during this time invokes `accrue()`, computes `next == idx` (since rate is 0), and per lines 851-862 of `v0-vault-stx.clar` leaves `last-update` unchanged.
4. DAO calls `set-points-rate` to set a positive rate; this internally calls `accrue()` first using the *old* zero rate (no burst, `last-update` still stale), then commits the new positive rate.
5. Any subsequent user calls `deposit`, `redeem`, or `system-borrow`. `accrue()` now computes `time-delta = stacks-block-time - last-update` spanning the entire stale window, multiplies it by the new positive rate, and applies the full retroactive `debt-delta` to `principal-scaled`, inflating every borrower's owed debt and immediately raising `total-assets` (and thus share price for all `zft` holders plus `dao-treasury`'s minted `treasury-lp`).
6. Borrowers now owe interest for a period during which the true configured rate was zero, while all current LP/share holders receive a windfall gain funded entirely by that mischarge.

(define-public (accrue)
  (let ((states (var-get pause-states))
        (idx (var-get index))
        (lidx (var-get lindex)))
      (if (get accrue states)
          ;; PAUSED: Pass-through without reverting
          (ok { index: idx, lindex: lidx })
          ;; NOT PAUSED: Normal accrual logic
          (let ((next (next-index))
                (nliq (next-liquidity-index))
                (scaled-principal (var-get principal-scaled))
                (old-debt (mul-div-down scaled-principal idx INDEX-PRECISION))
                (new-debt (mul-div-down scaled-principal next INDEX-PRECISION))
                (debt-delta (if (> new-debt old-debt) (- new-debt old-debt) u0))
                (reserve-inc (mul-div-down debt-delta (var-get fee-reserve) BPS))
                (treasury-lp (if (> reserve-inc u0) (mul-div-down reserve-inc (total-supply) (- (total-assets-preview) reserve-inc)) u0)))
            (if (not (is-eq idx next))
                (var-set index next)
                false)
            (if (not (is-eq lidx nliq))
                (var-set lindex nliq)
                false)

                false)
