### Title
Attacker-controlled Split/Merge/Withdraw on a stake account queued for partitioned reward distribution can desynchronize live `StakesCache` state from the calculation-time snapshot, triggering the `assert_eq!` panic in `build_updated_stake_reward` - ([File: runtime/src/bank/partitioned_epoch_rewards/distribution.rs])

### Summary
`build_updated_stake_reward` (`runtime/src/bank/partitioned_epoch_rewards/distribution.rs:239-325`) compares a stake account's *current, live* `delegation.stake` (fetched fresh from `self.stakes_cache.stakes()` at the start of the specific distribution block/partition) against the delegation value computed once at the epoch-boundary reward-calculation phase and stored in `PartitionedStakeReward`. An unprivileged stake authority who knows their account is queued for a later partition can send an ordinary `Split`, `Merge`, or `Withdraw` instruction against their own stake account in a block that lands between calculation and their partition's distribution block, changing the live `delegation.stake` and causing the non-`adjust_delegations_for_rent` branch's `assert_eq!` to fail, panicking the node.

### Finding Description
`distribute_partitioned_epoch_rewards` processes one partition per block over many blocks while `EpochRewardStatus::Active(EpochRewardPhase::Distribution(...))` is set [1](#0-0) . Each invocation of `store_stake_accounts_in_partition` re-fetches the *current* `StakesCache` state for the block being processed rather than reusing a snapshot taken during calculation: `let stakes_cache = self.stakes_cache.stakes(); let stakes_cache_accounts = stakes_cache.stake_delegations();` [2](#0-1) .

Inside `build_updated_stake_reward`, the live account's current delegation (`stake.delegation.stake`) is combined with the reward amount frozen at calculation time (`partitioned_stake_reward.inflation.stake_reward`) to form `expected_delegation`, then asserted equal to `new_stake.delegation.stake`, which is the delegation value that was computed once during the calculation phase (`partitioned_stake_reward.inflation.stake`), based on the stake state *as it existed at epoch boundary*: [3](#0-2) 

If the attacker (owning the stake/withdraw authority) submits `StakeInstruction::Split`, `Merge`, or `Withdraw` on this same stake pubkey in any block after calculation but before the distribution block for their assigned partition, the live `delegation.stake` read by `stakes_cache_accounts.get(...)` will differ from the value implicitly assumed at calculation time (e.g. `Split` reduces the original account's `delegation.stake` by the split amount; `Merge` increases it). This makes `expected_delegation != new_stake.delegation.stake`, hitting the `assert_eq!` and panicking every validator that processes that block deterministically — since the transaction and its state effects are part of consensus, all correct validators panic identically, producing a chain-wide halt rather than divergence, but still a critical availability failure reachable by a single unprivileged, unstaked-authority-controlled transaction.

There is no visible guard in this code path (nor found elsewhere in the reachable code) that freezes or locks a stake account's mutability while it is queued in `PartitionedStakeRewards` awaiting its distribution block, nor any check that rejects Split/Merge/Withdraw against accounts pending reward distribution. The reward-calculation phase (`runtime/src/bank/partitioned_epoch_rewards/calculation.rs`) computes and freezes `PartitionedStakeReward` entries once at epoch boundary, but ordinary transaction processing for the stake program continues unrestricted throughout the multi-block distribution window.

Separately, when `adjust_delegations_for_rent` (SIMD-0392) is active, the code takes the non-panicking branch and instead clamps `new_stake.delegation` using the *live* `account.lamports()` value via `adjust_delegation_for_rent` [4](#0-3) . Because this branch is explicitly designed to reconcile the reward-credited delegation against actual live balance (intended for rent changes), an attacker-driven lamport/delegation change via Withdraw before distribution feeds directly into this reconciliation logic rather than causing a hard panic, so it is a materially different (and apparently intended-to-be-tolerant) code path; I could not find sufficient evidence in the reachable code that this branch mints or burns lamports beyond what is already credited via `checked_add_lamports`, so I do not have high confidence this sub-path (rent-adjustment) itself creates a capitalization mismatch — only that it silently changes the resulting delegation representation.

### Impact Explanation
The `assert_eq!` panic path is a deterministic, cluster-wide crash-on-a-given-block bug reachable with a single stake-authority-signed transaction from an unprivileged attacker who merely needs their own stake account to be scheduled in a future partition of the current epoch's reward distribution (a condition that occurs naturally every epoch for essentially every active stake account with non-zero probability, and that the attacker can detect once partitioning is public after the calculation block). This matches the "epoch-boundary halt" / consensus-halt bounty category: a validator (indeed, all correct validators) panics processing a normal block, which is a network-wide availability failure, not merely a local crash.

### Likelihood Explanation
Preconditions: attacker owns a stake account with any lamports/delegation, has stake-authority (or withdraw-authority, sufficient for `Withdraw`) over it, and the account happens to be assigned to a partition index processed later than the current block height during the active distribution window (`EpochRewardStatus::Active(EpochRewardPhase::Distribution)`), which spans multiple blocks by design [5](#0-4) . No privileged access, mocked paths, or protocol-level exploits are required — just a normal `Split`/`Merge`/`Withdraw` transaction timed within the public multi-block reward window. This is fully repeatable each epoch by any staker.

### Recommendation
Prevent stake accounts from being mutated by Split/Merge/Withdraw while they are queued for pending partitioned reward distribution — e.g., have the stake program consult `Bank::epoch_reward_status` (or an equivalent sysvar-exposed flag) and reject such instructions for accounts still awaiting distribution in the current epoch, or alternatively make `build_updated_stake_reward` tolerant of externally-changed delegation by re-deriving the reward relative to the account's state at calculation time (stored/snapshotted per-account) instead of asserting against the live `StakesCache` value, converting the panic into a graceful `DistributionError` (already returned for `AccountNotFound`) when the live state has diverged from the calculation-time assumption.

### Proof of Concept
Integration test extending `create_reward_bank_with_specific_stakes` (used in `test_rewards_computation`, `runtime/src/bank/partitioned_epoch_rewards/calculation.rs:1492-1551`):
1. Create a reward bank with several stake accounts across multiple partitions so the distribution spans multiple blocks.
2. After the calculation block executes (reward amounts frozen in `PartitionedStakeRewards`), before the specific stake account's partition index is reached, submit a `stake_instruction::split` (or `merge`/`withdraw`) transaction reducing/changing that account's `delegation.stake`, signed by the account's stake authority.
3. Advance blocks until the targeted partition's distribution block executes `distribute_partitioned_epoch_rewards`.
4. Assert expected behavior: distribution should either (a) safely no-op / return `DistributionError` without panicking, and conservation of total lamports (`bank.capitalization()` delta) should hold, or (b) demonstrate the current bug by observing the process panic on `assert_eq!` at `distribution.rs:289-293` when `relax_post_exec_min_balance_check` is disabled — confirming the non-deterministic-relative-to-attacker-timing panic described.

fn adjust_delegation_for_rent(
    delegation: &mut Delegation,
    rewarded_epoch: Epoch,
    new_delegation_with_rewards: u64,
    lamports_with_rewards: u64,
    minimum_lamports: u64,
) {
    let new_delegation = std::cmp::min(
        new_delegation_with_rewards,
        lamports_with_rewards.saturating_sub(minimum_lamports),
    );

    if new_delegation != delegation.stake {

        // unlike a requested deactivation which happens at the next epoch
        // boundary
        if new_delegation == 0 {
            delegation.deactivation_epoch = rewarded_epoch;
        }
    }
}
