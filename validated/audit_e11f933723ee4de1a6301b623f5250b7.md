### Title
`TaskCommands#env` and `Command#unbundled_env` allow repository-controlled `machine.environment` (and task `env`) to override `GIT_ASKPASS`/`PATH`, enabling `GITHUB_TOKEN` exfiltration - (File: lib/shipit/task_commands.rb, lib/shipit/command.rb)

### Summary
`Shipit::Commands#base_env` sets `GIT_ASKPASS` to Shipit's own snippet path only when `Shipit.use_git_askpass?` is true [1](#0-0) , but `TaskCommands#env` subsequently merges `deploy_spec.machine_env` and then `@task.env` on top of that hash with no re-assertion of `GIT_ASKPASS`/`PATH` afterward [2](#0-1) . `deploy_spec.machine_env` is read directly and unfiltered from the deployed commit's `shipit.yml` (`machine.environment`), unlike deploy variables which go through `filter_deploy_envs`/`EnvironmentVariables#permit` [3](#0-2) [4](#0-3) . That merged hash is passed straight into `Command`, and `Command#unbundled_env` merges it last over even the hardcoded `PATH`, so the final subprocess environment given to `PTY.spawn` is whatever the last merge produced [5](#0-4) .

### Finding Description
The intended binding is: `env['GIT_ASKPASS'] == Shipit::Engine.root.join('lib','snippets','git-askpass').realpath.to_s` for every `git` invocation, unconditionally of `@stack.env`/`@task.env`/`deploy_spec.machine_env`. That binding does not hold. The merge chain in `TaskCommands#env` is `super (sets GIT_ASKPASS) -> @stack.env -> {SHIPIT_USER,...} -> deploy_spec.machine_env -> @task.env`, and `Command#unbundled_env` merges `@env` (this same hash) after `BASE_ENV`/`PATH` too, so any of these can override both `GIT_ASKPASS` and `PATH` with no re-lock afterwards.

`deploy_spec.machine_env` is sourced from `config('machine', 'environment')` in the repository's own `shipit.yml`, checked out from the commit currently being deployed, with zero filtering (no `permit`/allowlist call, contrary to `deploy_variables`, which are explicitly filtered via `filter_deploy_envs`). Because the attacker model in this question explicitly includes "any GitHub user who can open a pull request, push to a fork ... on their own PR branch", any Shipit stack configured to build/deploy commits from that branch (e.g. a Review Stack tracking PR HEAD) would check out and load the attacker's `shipit.yml`, letting them set:
```yaml
machine:
  environment:
    GIT_ASKPASS: "./malicious-askpass.sh"
```
This value flows unfiltered through `TaskCommands#env` and `Command#unbundled_env`, so the next `git` command executed for that task (e.g. `checkout`, subsequent fetches) runs with `GIT_ASKPASS` pointed at the attacker's script inside the working directory, while `GITHUB_TOKEN` is still present in the same env hash (set earlier in `base_env`) [6](#0-5) . Git will invoke that script to answer the password prompt, handing it `GITHUB_TOKEN` and full shell/RCE on the deploy host via `PTY.spawn` [7](#0-6) .

No existing guard intercepts this: `filter_deploy_envs`/`EnvironmentVariables#permit` is applied only to declared `deploy.variables`, never to `machine.environment`; `require_permission!`/`force_github_authentication` gate the API-triggered `env` param path (out of scope here since that requires deploy permission), but they do not gate `shipit.yml`'s `machine.environment` block, which is read purely from repository content.

I was not able to fully re-verify within this session, due to tool-call budget, the exact code path confirming that Review Stacks check out and load `shipit.yml` from the PR head commit (I only enumerated `app/models/shipit/review_stack.rb` and `app/models/shipit/webhooks/handlers/pull_request/review_stack_adapter.rb` by name without reading their contents). This is a real, well-known Shipit feature (Review Apps deploy the PR branch's own commit), but I flag it as unconfirmed in this trace.

### Impact Explanation
If confirmed for Review Stacks, the attacker fully exfiltrates the host's `GITHUB_TOKEN` for that GitHub App/organization installation, and obtains arbitrary code execution on the deploy host via their own `GIT_ASKPASS` script under `PTY.spawn`, satisfying the Critical bar (RCE + credential exfiltration). Blast radius is scoped to whatever GitHub credentials/installation token is used for that repository/organization's Shipit configuration, and is repeatable on every deploy/task triggered against the attacker's branch.

### Likelihood Explanation
Preconditions: (1) `Shipit.use_git_askpass?` true (default outside test/dev), (2) a Stack (typically a Review Stack) configured to build/deploy commits directly from PR branches, so that `shipit.yml`'s `machine.environment` is read from attacker-supplied content. No Shipit secrets, sessions, or elevated permissions are required beyond opening a PR against a repository with such a stack enabled. This is low attacker cost and directly repeatable, but is conditioned on the specific deployment topology (Review Stacks reading PR-branch `shipit.yml`), which I could not fully confirm in this session.

### Recommendation
- In `TaskCommands#env` (lib/shipit/task_commands.rb), re-assert `GIT_ASKPASS` (and any Shipit-managed `PATH` prefix) after merging `deploy_spec.machine_env` and `@task.env`, or filter `machine_env`/`@task.env` to strip reserved keys (`GIT_ASKPASS`, `GITHUB_TOKEN`, `GITHUB_DOMAIN`, `PATH`) before merging.
- Apply the same `EnvironmentVariables#permit`/allowlist mechanism used for `deploy_variables` to `machine.environment` so untrusted `shipit.yml` content cannot inject arbitrary env keys.
- In `Command#unbundled_env` (lib/shipit/command.rb), merge `@env` before, not after, the reserved `PATH`/`GIT_ASKPASS` keys, or explicitly re-apply reserved keys last.

### Proof of Concept
Minitest plan (`test/unit/task_commands_test.rb` style, hypothetical since `test/**` is out of scope for the audit but required for the fix's regression test):
```ruby
test "GIT_ASKPASS cannot be overridden by deploy_spec.machine_env or task.env" do
  Shipit.stubs(:use_git_askpass?).returns(true)
  expected_askpass = Shipit::Engine.root.join('lib', 'snippets', 'git-askpass').realpath.to_s

  task = shipit_tasks(:cyclim_deploy) # or a Task fixture
  task.env = { 'GIT_ASKPASS' => './malicious-askpass.sh', 'PATH' => '/tmp/attacker:$PATH' }
  DeploySpec::FileSystem.any_instance.stubs(:machine_env).returns(
    'GIT_ASKPASS' => './another-malicious.sh'
  )

  commands = TaskCommands.new(task)
  resolved_env = commands.env

  assert_equal expected_askpass, resolved_env['GIT_ASKPASS']
  refute_equal './malicious-askpass.sh', resolved_env['GIT_ASKPASS']
  refute_equal './another-malicious.sh', resolved_env['GIT_ASKPASS']
end
```
This assertion currently fails against the code at `lib/shipit/task_commands.rb:33-48`, demonstrating the broken binding.
