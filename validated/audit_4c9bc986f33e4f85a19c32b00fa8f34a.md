### Title
Cross-organization CI status forgery bypasses repository binding in `StatusHandler`, enabling unauthorized continuous deployment - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`WebhooksController#verify_signature` selects which organization's `webhook_secret` to validate a payload against based on the attacker-controlled `repository.owner.login` (or `organization.login`) field in the JSON body [1](#0-0) . Once that signature check passes, `StatusHandler.process` looks up the target `Commit` purely by `sha`, with no verification that the commit's `stack`/`repository` actually corresponds to the organization whose secret produced the valid signature: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [2](#0-1) . The `params` block for this handler never even requires a `repository` field [3](#0-2) , unlike other handlers (e.g. `PushHandler`, pull-request handlers) which scope to `Repository.from_github_repo_name(payload.dig('repository','full_name'))` [4](#0-3) .

### Finding Description
The binding that should hold is: **organization whose credential (webhook secret) authenticated the request == organization owning the repository/stack that the webhook payload is allowed to mutate**. This is broken for the `status` event:

1. `verify_signature` picks `Shipit.github(organization: repository_owner)` where `repository_owner` comes straight from the untrusted JSON body [5](#0-4) .
2. An attacker who administers *any* GitHub organization onboarded to this Shipit instance (and therefore legitimately knows/controls that org's `webhook_secret`, since org admins configure their own GitHub App webhook secret) can compute a **valid HMAC signature** over an arbitrary payload of their choosing, as long as `repository.owner.login` in that payload equals their own org login.
3. `StatusHandler` then acts on `params.sha` without any cross-check against `repository.owner.login`/`full_name`, and `Commit.where(sha: ...)` is a global, unscoped query across *all* stacks/repositories in the Shipit instance [2](#0-1) .
4. `create_status_from_github!` creates a `Status` record which, via `after_create :enable_ci_on_stack` and `after_commit :schedule_continuous_delivery`, can flip a commit into "success"/deployable state on a target stack completely unrelated to the attacker's org [6](#0-5) .
5. `Commit#schedule_continuous_delivery` enqueues `ContinuousDeliveryJob` when `deployable? && stack.continuous_deployment? && stack.deployable?` [7](#0-6) , and the test suite confirms that a `success` status transition on a commit with continuous deployment enabled directly triggers a real `Deploy` [8](#0-7) .

Before the attack: attacker's signature only authenticates events about attacker's own org's repositories.
After the attack: attacker's signature (still validated against attacker's own org secret) is accepted by `StatusHandler` to mutate CI state for a commit belonging to an arbitrary victim org/stack, because the commit lookup and status-creation path is never re-checked against the authenticated organization.

### Impact Explanation
If the victim stack has `continuous_deployment` enabled and the forged "success" status satisfies its required-status set, this results in an **unauthorized deploy** triggered purely by a webhook forged with credentials belonging to a different, unrelated organization the attacker legitimately controls. This matches the "unauthorized deploy" Critical/High impact criterion. Even without triggering continuous deployment, an attacker can pollute `commit.statuses` (CI state) for arbitrary commits/stacks they have no relationship to, corrupting deploy gating logic (`deployable?`) that other legitimate deploy/rollback flows rely on.

### Likelihood Explanation
Requires only that the attacker (a) controls/administers any single GitHub organization already configured in this Shipit instance's multi-org GitHub App config (a routine, low-privilege prerequisite consistent with the engine's documented multi-tenant support), and (b) knows the target commit's SHA in the victim stack (visible on GitHub, or brute-forceable/guessable for public repos). No repository write access, `ApiClient` token, or Shipit session is needed — only the ability to send a raw HTTP POST to `/github/webhooks` with a self-signed HMAC. This is a realistic, low-effort path given the multi-org webhook-signature-selection design.

### Recommendation
In `StatusHandler` (and any other handler that doesn't already scope through `Handler#stacks`), require and verify the `repository.full_name`/`repository.owner.login` in the payload matches the organization whose secret validated the signature, and scope the `Commit` lookup to `stacks` derived from that verified repository, e.g.:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }
  end
end
```
and add a `requires :repository { requires :full_name, String }` param, consistent with `PushHandler`/pull-request handlers. Additionally, `WebhooksController#verify_signature` should not let a payload-controlled field alone determine trust scope without a corresponding invariant enforced downstream in every handler.

### Proof of Concept
1. Attacker administers `attacker-org`, which is a legitimately configured GitHub App organization in this Shipit deployment with a known `webhook_secret`.
2. Victim stack belongs to `victim-org/victim-repo`, with `continuous_deployment: true`, and has a pending commit `abc123` whose only required status context is `ci/travis`.
3. Attacker crafts a JSON body:
```json
{
  "sha": "abc123",
  "state": "success",
  "context": "ci/travis",
  "repository": { "owner": { "login": "attacker-org" } }
}
```
4. Attacker computes `X-Hub-Signature: sha1=HMAC(attacker_webhook_secret, body)` and POSTs to `/github/webhooks` with `X-Github-Event: status`.
5. `verify_signature` resolves `Shipit.github(organization: "attacker-org")` and the signature validates successfully [9](#0-8) .
6. `StatusHandler.process` finds `Commit` `abc123` (belonging to `victim-org/victim-repo`'s stack) purely by `sha` and creates a `success` status on it [2](#0-1) .
7. `schedule_continuous_delivery` fires and, since the victim stack is continuous-deployment-enabled and now deployable, a real deploy is enqueued/executed on the victim's infrastructure — an unauthorized deploy triggered entirely with attacker-org credentials.
