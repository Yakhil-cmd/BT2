### Title
Signature verification uses `repository.owner.login` while handlers act on `repository.full_name` - forged `pull_request` webhook writes to a different org's stack - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`Shipit::WebhooksController#verify_signature` selects the GitHub App/org used for HMAC verification purely from `params.dig('repository','owner','login')`, while every `pull_request` handler (e.g. `LabelCapturingHandler`) resolves the actual `Repository`/`Stack` to mutate from the independent `params.repository.full_name` field. If the org named by `owner.login` has no `webhook_secret` configured, `GitHubApp#verify_webhook_signature` returns `true` unconditionally, letting an attacker forge a payload that "verifies" under a harmless org but whose `repository.full_name` points at a completely different org's repo/stack that the handler then mutates.

### Finding Description
The broken invariant, stated as an equality that must hold but doesn't:
`org_that_verified_signature (params.repository.owner.login) == org_that_owns_mutated_repository (Repository.from_github_repo_name(params.repository.full_name).owner)`

Trace:
1. `WebhooksController#verify_signature` computes `repository_owner` solely from `params.dig('repository', 'owner', 'login')` (or `organization.login`) and fetches `github_app = Shipit.github(organization: repository_owner)`. [1](#0-0) , [2](#0-1) 
2. `GitHubApp#verify_webhook_signature` short-circuits with `return true unless webhook_secret` — i.e., for any org configured without a `webhook_secret`, ANY signature (even garbage) is accepted. [3](#0-2) 
3. Once verification passes, `WebhooksController#create` dispatches the raw parsed JSON to all handlers for the event, unmodified. [4](#0-3) 
4. `LabelCapturingHandler` (and its siblings) never re-check `repository.owner.login`; they resolve the target repository purely from `params.repository.full_name` via `Repository.from_github_repo_name`, then locate/mutate the `ReviewStack`/`PullRequest` under that repo. [5](#0-4) 
5. `capture_labels` persists attacker-controlled `params.pull_request.labels.map(&:name)` directly onto `stack.pull_request`, with no ownership check tying it back to `repository_owner`. [6](#0-5) 

Exploit request: an attacker who controls (or names) a no-secret org — e.g. one that exists in `Shipit.github_apps`/config without a `webhook_secret`, or a name that will hit the "unknown organization" fallback intentionally set to a configured no-secret org — POSTs to `/webhooks` with `X-Github-Event: pull_request`, `action: "opened"`, `repository.owner.login: "no-secret-org"`, but `repository.full_name: "victim-org/victim-repo"`. Since `no-secret-org` has no `webhook_secret`, `verify_webhook_signature` returns `true` regardless of the `X-Hub-Signature` header content. The request reaches the handler, which resolves `victim-org/victim-repo`'s repository/stack via `full_name` and persists the attacker's forged label names onto that stack's `PullRequest`.

Why existing guards fail: `drop_unhandled_event` only checks the event type exists a handler; it does nothing about repository identity. [7](#0-6)  There is no code anywhere in `verify_signature`, `create`, or the handler base class (`Handler`) that cross-checks `repository.owner.login` against `repository.full_name`'s owner segment, or against the resolved `Repository#owner`.

### Impact Explanation
An attacker with no Shipit secrets can inject/overwrite label state on any review-stack `PullRequest` belonging to any other tenant/org configured on the instance, as long as one org on the instance has no `webhook_secret` set. Labels are later consumed as environment variable keys in `ReviewStack#env` (uppercased), so forged label names can inject or overwrite deploy-time environment variables for that other org's review stack — a cross-tenant/cross-repository state manipulation matching the "Critical: a payload for one repository mutating another's stack" category. This is repeatable against any `full_name` the attacker chooses, for every `pull_request` event action supported by the handler dispatch (`opened`, `labeled`, `unlabeled`, `reopened`), not merely a one-off.

### Likelihood Explanation
Preconditions: the Shipit instance must have at least one configured GitHub org/app with no `webhook_secret` (a documented/plausible admin configuration state, e.g. for internal or low-risk orgs), and a victim org/repo with an active `ReviewStack`. Attacker cost is a single unauthenticated HTTP POST with a crafted JSON body and arbitrary/garbage `X-Hub-Signature`; no GitHub credentials, no Shipit session, and no correct HMAC secret are required. This is trivially repeatable and scriptable.

### Recommendation
In `WebhooksController#verify_signature`, do not rely solely on `repository.owner.login`/`organization.login` for selecting the verifying org; additionally require that verification succeed using the actual owner org derived from `repository.full_name` (or reject when `full_name`'s owner segment differs from `owner.login`). More robustly, `GitHubApp#verify_webhook_signature` should not silently return `true` when `webhook_secret` is blank — either require every configured org to set a secret, or fail closed (reject) rather than fail open when a secret is absent. Handlers should also validate that the resolved `Repository#owner` matches the org whose secret verified the incoming request before mutating any records.

### Proof of Concept
minitest under `test/controllers/webhooks_controller_test.rb` (or new test file):
```ruby
test "pull_request opened with owner/full_name org mismatch writes to another org's stack" do
  # Setup: configure "no-secret-org" with no webhook_secret in Shipit.github_apps config
  # Setup: create Repository owner: "victim-org", name: "victim-repo"
  # Setup: create ReviewStack under that repo with environment "pr123", and its PullRequest
  before_owner = stack.pull_request.labels # assert empty/baseline
  post "/webhooks", params: {
    action: "opened",
    number: 123,
    pull_request: {
      id: 1, number: 123, url: "...", title: "x", state: "open",
      additions: 1, deletions: 0,
      head: { sha: "abc", ref: "feature" },
      user: { login: "attacker" },
      assignees: [],
      labels: [{ name: "MALICIOUS_ENV_KEY" }]
    },
    repository: { full_name: "victim-org/victim-repo", owner: { login: "no-secret-org" } },
    sender: { login: "attacker" }
  }.to_json, headers: { "X-Github-Event" => "pull_request", "X-Hub-Signature" => "sha1=garbage", "Content-Type" => "application/json" }

  assert_response :ok
  after_owner = stack.pull_request.reload.labels
  # Equality that should have held: request verified under "no-secret-org" == owner of mutated repo "victim-org"
  refute_equal "no-secret-org", "victim-org"
  assert_equal ["MALICIOUS_ENV_KEY"], after_owner # proves the mismatch was exploited
end
```
This demonstrates the org used for signature verification (`no-secret-org`, no secret) differs from the org owning the mutated `Repository`/`ReviewStack`/`PullRequest` (`victim-org`), and the write still succeeds.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
