### Title
`StatusHandler#process` mutates `Commit`/`Status` rows for any repository sharing a webhook `sha`, bypassing `Handler#stacks` repository scoping - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` looks up commits with `Commit.where(sha: params.sha)` across the entire database instead of scoping to `stacks.flat_map(&:commits)` (the set authorized by the payload's `repository.full_name`). Any repository sharing a commit `sha` with another Shipit-tracked repository (e.g. a fork/template of it) can trigger `create_status_from_github!` on that other repository's `Commit`, writing a `Status` and potentially altering deployability for a stack the sender never authenticated for.

### Finding Description
The invariant that should hold is: `Set(Commits mutated by StatusHandler#process) == Set(stacks.flat_map(&:commits))`, where `stacks` is `Repository.from_github_repo_name(payload.dig('repository','full_name'))&.stacks` [1](#0-0) . Instead, `process` does:

```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [2](#0-1) 

`Handler#stacks` is defined but never referenced anywhere in `StatusHandler` [3](#0-2) , so the query is entirely unscoped by repository/stack, using only the attacker-supplied `sha` string.

`WebhooksController#verify_signature` only checks the HMAC signature for `repository_owner` (the org derived from the payload) via `Shipit.github(organization: repository_owner)` [4](#0-3) ; it never checks that the `sha`, or the commit being mutated, actually belongs to that repository/org. So a genuinely-signed status event from Repository A can update `Commit` rows belonging to Repository B's stack whenever both repos contain a commit object with the same `sha` (this occurs naturally for forks/templates, which share git history and therefore identical commit SHAs for unmodified commits).

`Commit#create_status_from_github!` writes a new `Status`, recomputes `status`, and can trigger `Hook.emit(:commit_status, ...)`, `Hook.emit(:deployable_status, ...)`, and `stack.schedule_merges` [5](#0-4) [6](#0-5)  — all against a stack the attacker's webhook was never authorized for.

None of the existing guards prevent this: `verify_signature` authenticates the sender's org, not the target commit's owning repository; `drop_unhandled_event` only checks the event type is registered; the `ExplicitParameters` schema only validates `sha`/`state` are strings, with no repository binding; and `Handler#stacks` — the only scoping mechanism that exists in the codebase for this purpose — is simply unused by `StatusHandler`.

### Impact Explanation
A payload authenticated for Repository A can write `Status` records and mutate deployability state for `Commit`s belonging to Repository B's stack, with no authorization from Repository B's own `webhook_secret`/GitHub App installation. This is a cross-repository mutation, matching the Critical category ("a payload for one repository mutating another's stack, commit, task or team"). It is repeatable against any pair of repositories with overlapping commit SHAs (forks, templates, or squash/rebase-shared history), and can influence `stack.schedule_merges` and `deployable_status` hooks on the victim stack.

### Likelihood Explanation
This requires two Shipit-tracked repositories that share at least one commit SHA (a common real-world condition for forks/templates), and requires the attacker to control (or trigger) a genuine, correctly-signed status webhook for their own repository referencing that shared SHA — which is trivial (push/CI status on a shared/forked commit). No secrets, sessions, or elevated GitHub roles are needed beyond ownership of one of the two repositories.

### Recommendation
Scope the commit lookup in `StatusHandler#process` to the payload-authorized stacks, e.g.:
```ruby
def process
  Commit.where(sha: params.sha, stack_id: stacks.select(:id)).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
so the mutated set is provably a subset of `stacks.flat_map(&:commits)`.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb (new)
test "process only mutates commits within stacks scoped to the payload repository" do
  victim_stack = shipit_stacks(:shipit)
  attacker_stack = create_stack(repo_owner: 'attacker-org', repo_name: 'evil-fork')
  shared_sha = 'a' * 40

  victim_commit = victim_stack.commits.create!(sha: shared_sha, message: 'shared history commit')
  attacker_commit = attacker_stack.commits.create!(sha: shared_sha, message: 'shared history commit')

  payload = {
    'sha' => shared_sha,
    'state' => 'success',
    'repository' => { 'full_name' => attacker_stack.github_repo_name }
  }

  handler = Shipit::Webhooks::Handlers::StatusHandler.new(payload)
  authorized_commit_ids = handler.send(:stacks).flat_map(&:commits).map(&:id)

  handler.process

  # Binding under test: mutated commits ⊆ authorized_commit_ids
  assert_includes authorized_commit_ids, attacker_commit.id
  refute_includes authorized_commit_ids, victim_commit.id

  # Fails today: victim_commit gets a new status even though its stack
  # was never in `stacks` for this payload.
  assert_empty victim_commit.reload.statuses, "victim repository's commit must not be mutated"
  assert_not_empty attacker_commit.reload.statuses
end
```
