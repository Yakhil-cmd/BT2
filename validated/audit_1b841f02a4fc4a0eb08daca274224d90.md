### Title
Cross-organization webhook trust confusion allows forged commit statuses and stack actions to bypass deploy gating - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/webhook secret to validate a webhook against using a value taken directly from the still-unverified request body, while the handlers that subsequently act on that same body operate on an unrelated, attacker-controlled repository/commit reference. The binding that should hold — "the organization whose secret verified the signature" == "the repository/commit the handler writes to" — is never enforced.

### Finding Description
`verify_signature` computes `repository_owner` from the raw, unauthenticated payload (`params.dig('repository','owner','login')` or `params.dig('organization','login')`) and uses it to pick the `GitHubApp`/secret to check the HMAC against: [1](#0-0) [2](#0-1) 

In a multi-tenant configuration (documented in `docs/setup.md`, "Using Multiple Github Applications"), each organization has its own `webhook_secret`. Because `repository_owner` is read out of the body before the signature is validated, an attacker who legitimately controls their own tenant organization (and therefore knows *their own* `webhook_secret`, which they configured themselves) can produce a request that:
- sets `repository.owner.login` (or `organization.login`) to **their own** org, so `verify_signature` picks their own org's secret and the HMAC passes, and
- sets other payload fields (`repository.full_name`, `sha`, etc.) to reference a **different** tenant's repository or a commit belonging to it.

`Shipit::Webhooks::Handlers::Handler` resolves target data purely from the payload, not from the verified `repository_owner`: [3](#0-2) 

Worse, `StatusHandler` does not scope by repository at all — it matches by SHA globally: [4](#0-3) 

`PushHandler` resolves stacks by `repository.full_name` from the body and triggers a GitHub sync: [5](#0-4) 

`Repository.from_github_repo_name` performs a straightforward lookup with no ownership/org cross-check against the verified signer: [6](#0-5) 

Before/after the attacker's request:
- Before: signature verification is meant to bind "this request came from GitHub for organization X" to "the data in this request pertains to organization X's repositories".
- After: the attacker satisfies "signature valid for organization X" (their own org) while the payload content actually targets organization Y's commit/repository — the equality `verified_org == target_repository_org` is broken.

### Impact Explanation
Because `StatusHandler` writes a commit status keyed only by SHA with no repository check, a tenant that controls any correctly-configured GitHub App/secret in the same Shipit instance can inject arbitrary commit statuses (e.g., a fabricated "success" for a CI context) against another tenant's commit. `Stack#required_statuses`/`blocking_statuses` gate whether a commit is `deployable?`; forging a passing status for a required CI context can make an otherwise-blocked commit appear deployable, enabling an **unauthorized deploy** of another organization's stack — the impact this program treats as Critical. `PushHandler` and `CheckSuiteHandler` similarly let an attacker with only their own-org webhook credentials trigger `sync_github`/`RefreshCheckRunsJob` against a stack belonging to a repository name of their choosing.

### Likelihood Explanation
This requires a Shipit deployment configured for multiple GitHub organizations (per `docs/setup.md`), where an attacker legitimately administers one tenant's GitHub App and therefore knows that tenant's own `webhook_secret` (not a secret they need to steal — it's their own). No repository write access, session, or API token is required; only the ability to send an HTTP POST to `/webhooks` with a validly-signed-for-their-own-org body whose content fields reference another tenant. This is a realistic misuse of an intended multi-tenant feature rather than a theoretical scenario.

### Recommendation
Do not derive the trust-establishing organization from the same unverified body used for the data payload. After signature verification succeeds for organization `repository_owner`, enforce that every entity acted upon (repository, commit, stack) actually belongs to that verified organization before performing any write — e.g., in `Handler#stacks`/`StatusHandler#process`, cross-check that the resolved `Repository#owner` (or the commit's stack's repository owner) equals the `repository_owner` that was validated by `verify_signature`, and reject/ignore the event otherwise.

### Proof of Concept
1. Operate a legitimate tenant organization "attacker-org" configured in Shipit's multi-org `github:` secrets with its own known `webhook_secret`.
2. Identify (or guess) the SHA of a commit belonging to a victim stack in another tenant, e.g. "victim-org/victim-repo", that is pending a required CI status.
3. Craft a `status` event JSON body:
```json
{
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "attacker-org/whatever" },
  "sha": "<victim commit sha>",
  "state": "success",
  "context": "<required ci context>"
}
```
4. Compute `X-Hub-Signature` using `attacker-org`'s own `webhook_secret` (`sha1=` + HMAC-SHA1 over the raw body).
5. POST to `/webhooks` with header `X-Github-Event: status`. `verify_signature` selects `attacker-org`'s app via `repository_owner` and the signature validates successfully.
6. `StatusHandler#process` runs `Commit.where(sha: params.sha)` — matching the victim's commit regardless of organization — and calls `commit.create_status_from_github!(params)`, injecting a fabricated passing status that can satisfy `Stack#required_statuses`, potentially enabling an unauthorized deploy of the victim stack.
