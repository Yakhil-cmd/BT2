### Title
Cross-organization webhook forgery via mismatched signing-organization vs. processed-repository binding - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects the GitHub App/HMAC secret used to authenticate an inbound webhook using `repository_owner`, a field read directly out of the still-unverified JSON body (`params.dig('repository','owner','login')`, falling back to `params.dig('organization','login')`). Once the signature check passes for *that* organization, `create` dispatches the very same raw payload to the event handlers, which independently pick the repository/stack to mutate using a *different* field of the same payload: `payload.dig('repository','full_name')` in `Handler#repository_name`. Nothing ties the two lookups together, so the organization whose secret authenticated the request is not provably the organization whose repository gets written to.

### Finding Description
The verified binding should be: `organization that authenticated the request == organization whose repository/stack is mutated by the handler`. In this engine that equality is never enforced.

- `WebhooksController#verify_signature` computes `repository_owner` from the payload, fetches that organization's `GitHubApp` via `Shipit.github(organization: repository_owner)`, and calls `GitHubApp#verify_webhook_signature(signature, raw_post)`: [1](#0-0) [2](#0-1) 
- `GitHubApp#verify_webhook_signature` HMACs the *entire raw request body* against that one organization's `webhook_secret` — it validates that *some* known secret produced this exact byte stream, but the secret is chosen based on an attacker-controlled field inside that same body: [3](#0-2) 
- Once verification succeeds, `create` fans the raw, parsed payload out to all registered handlers for the event type: [4](#0-3) [5](#0-4) 
- Every handler resolves the target `Repository`/`Stack` using `payload.dig('repository','full_name')`, a field that is never checked against the `repository_owner`/organization used for the signature check: [6](#0-5) 
- `Repository.from_github_repo_name` performs a plain, unauthenticated lookup by owner/name parsed out of `full_name`: [7](#0-6) 
- Handlers such as `PullRequest::ClosedHandler` use exactly this repository resolution to select the review stack to `archive!`, and other handlers (`PushHandler`, `StatusHandler`, `CheckSuiteHandler`, label/assignment handlers) similarly act on whatever stack `full_name` names: [8](#0-7) 

This engine explicitly supports multiple GitHub organizations sharing one Shipit instance, each with its own App/secret (`lib/shipit.rb`'s `TOP_LEVEL_GH_KEYS`, and the multi-org fixture in `test/dummy/config/secrets_double_github_app.yml`). An attacker who legitimately controls (or has push/webhook-triggering rights on) their **own** onboarded organization "OrgAttacker" knows or can trigger genuine, correctly-signed webhooks for OrgAttacker. Nothing stops them from crafting a raw payload where `repository.owner.login = "OrgAttacker"` (used only for signature-org selection) but `repository.full_name = "victim-org/victim-repo"` (used by every handler to select the mutated Stack), sign it with OrgAttacker's own known webhook secret, and send it to the shared `/webhooks` endpoint. `verify_signature` authenticates it as a legitimate OrgAttacker event; `create` then processes it as an event about `victim-org/victim-repo`.

### Impact Explanation
This breaks the "organization that authenticated versus the repository that is written" trust boundary described in scope. Concretely, an attacker who only controls their own unrelated organization can:
- Forge `pull_request` `closed` events that call `review_stack.archive!` on another organization's review stack.
- Forge `push` events that enqueue `GithubSyncJob` against another organization's `Stack` (state confusion / forced resync using attacker-chosen `expected_head_sha`).
- Forge `status` / `check_suite` events that fabricate commit-status / check-run state for another organization's tracked commits, which Shipit's deploy-gating logic (`deployable_status`, statuses) may rely on to permit deploys.

Given the engine explicitly allows the standard base case of a single, uncontested trust domain (one org, one secret) to be safe, the realistic exploitation window requires the attacker to already operate a second organization onboarded onto the *same* shared Shipit instance — this narrows applicability but does not eliminate it, since multi-tenant Shipit deployments are an explicitly supported and documented configuration.

### Likelihood Explanation
Requires: (1) a Shipit deployment configured for multiple GitHub organizations, and (2) the attacker to legitimately control one of those organizations (or be able to make it emit a webhook signed with a secret they know). This is a real, supported deployment topology but not the default single-org setup, so likelihood is moderate rather than trivial — it depends on multi-tenancy being in use.

### Recommendation
In `WebhooksController#verify_signature` / `create`, after signature verification succeeds, re-derive the repository owner used for verification and assert it matches the owner embedded in every `repository.full_name` the dispatched handlers will act on (or, simpler, verify the signature using the owner parsed consistently from `full_name` rather than from the separate `repository.owner.login` field), rejecting the request if they diverge.

### Proof of Concept
1. Configure Shipit with two organizations, `OrgAttacker` and `victim-org`, each with its own `webhook_secret` (as supported by `config/secrets.yml`, cf. `test/dummy/config/secrets_double_github_app.yml`).
2. Attacker legitimately controls `OrgAttacker` and knows/derives its `webhook_secret` (e.g. by triggering their own real webhook and observing header/config, or because they administer that org's GitHub App).
3. Attacker crafts a `pull_request` JSON body:
   ```json
   {
     "action": "closed",
     "number": 1,
     "pull_request": { "...": "...", "head": {"sha": "x", "ref": "x"}, "user": {"login": "attacker"}, "assignees": [], "labels": [] },
     "repository": { "owner": {"login": "OrgAttacker"}, "full_name": "victim-org/victim-repo" },
     "sender": { "login": "attacker" }
   }
   ```
4. Computes `X-Hub-Signature: sha1=<HMAC-SHA1(OrgAttacker_webhook_secret, raw_body)>`.
5. POSTs to `/webhooks` with `X-Github-Event: pull_request`. `verify_signature` resolves `repository_owner = "OrgAttacker"`, fetches OrgAttacker's `GitHubApp`, and the HMAC matches — request passes.
6. `PullRequest::ClosedHandler` resolves `Repository.from_github_repo_name("victim-org/victim-repo")` and archives that repository's review stack, an action the attacker has no authorization to perform on `victim-org`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
