### Title
Cross-organization webhook spoofing via `repository.owner.login` / `repository.full_name` mismatch - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`Shipit::WebhooksController#verify_signature` authenticates an incoming webhook using the GitHub App/secret for the organization named in `payload.dig('repository','owner','login')` (via `repository_owner`), but every event handler resolves the target repository/stacks solely from `payload.dig('repository','full_name')`. Because these two payload fields are never checked for consistency, an attacker who can satisfy signature verification for org-a (e.g. because org-a has no `webhook_secret` configured, making `verify_webhook_signature` return `true` unconditionally) can set `full_name` to `org-b/some-repo` and have the handler mutate org-b's stack/commit/task state.

### Finding Description
The broken binding is the equality that should hold but doesn't:
`Shipit.github(organization: payload.dig('repository','owner','login'))` (used to select the HMAC secret in `verify_signature`, app/controllers/shipit/webhooks_controller.rb:59-62) **should equal** the organization implied by `payload.dig('repository','full_name')` (used by `Handler#repository_name`/`#stacks` to select the actual `Repository`/`Stack` records, app/models/shipit/webhooks/handlers/handler.rb:33-38). Nothing in the code enforces this. `verify_signature` never re-reads `full_name`, and no handler re-validates `owner.login` against `full_name`.

Root cause: `GitHubApp#verify_webhook_signature` (lib/shipit/github_app.rb:76-83) returns `true` unconditionally `unless webhook_secret` — i.e., if the organization resolved via `repository_owner` has no configured `webhook_secret`, **any** signature (or none) passes for that organization. Combined with the handler's independent lookup of the target repo via `full_name` (`Repository.from_github_repo_name(repository_name)` in app/models/shipit/repository.rb:53-56), an attacker can craft:

```json
{
  "repository": {
    "owner": { "login": "org-a" },
    "full_name": "org-b/some-repo"
  },
  ...
}
```

`verify_signature` calls `Shipit.github(organization: 'org-a')`; if org-a's `webhook_secret` is nil/blank, verification trivially succeeds regardless of the `X-Hub-Signature` header (or its absence). The `create` action then dispatches to the handler for the event, and the handler's `stacks`/`repository_name` methods derive the affected `Repository` from `full_name = 'org-b/some-repo'`, mutating org-b's stacks/commits/tasks (e.g. queuing `GithubSyncJob`, updating `Status`, etc.) without org-b's secret ever being checked.

Existing guards do not catch this: `drop_unhandled_event` only checks the event type; `ExplicitParameters` schemas (used inside `Handler#initialize`) validate shape/types, not cross-field owner consistency; `Repository` model validations (`owner`/`name` format) only constrain what a *stored* repository's owner/name look like, not that the webhook's claimed owner matches its claimed full_name; there's no `force_github_authentication`/`User#authorized?` check in this controller since webhooks are unauthenticated by design and rely entirely on HMAC verification being organization-consistent.

### Impact Explanation
A payload for one repository's organization can mutate another organization's stack/commit/task state — e.g., a forged `push` event can enqueue `GithubSyncJob` against org-b's stack, or a forged `status`/`check_suite` event can write `Status`/trigger `RefreshCheckRunsJob` for org-b's commits, entirely bypassing org-b's webhook secret. This matches the Critical category "a payload for one repository mutating another's stack, commit, task or team." The attack is repeatable against any org-b repository known to the attacker (repo full name is public information) as long as some org-a exists in the Shipit installation with an absent/weak `webhook_secret`.

### Likelihood Explanation
Preconditions required: at least one organization configured in Shipit (org-a) whose `webhook_secret` is not set (or is weak/guessable) — this is a real, documented fallback behavior in `verify_webhook_signature`, not a hypothetical. Given that, the attacker needs zero secrets: no `GITHUB_TOKEN`, no `webhook_secret`, no session. They only need to know org-b's repository `full_name`, which is public. This is a pure unauthenticated POST to `/webhooks`, fully repeatable, and requires no special GitHub-side privileges (a well-known misconfiguration commonly seen when an org is added to a shared Shipit multi-tenant deployment without a signing secret).

### Recommendation
In `verify_signature` (or in each `Handler`), assert that `payload.dig('repository','owner','login')` matches the owner segment of `payload.dig('repository','full_name')` before processing, rejecting the request (422) on mismatch. Additionally, treat an absent `webhook_secret` for an organization as a hard failure (reject unsigned webhooks) rather than an implicit pass in `GitHubApp#verify_webhook_signature`, or require operators to configure a secret for every registered organization.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (proof sketch)
test "signature check for org-a does not protect org-b's stacks" do
  # org-a has no webhook_secret configured
  Shipit.stubs(:github).with(organization: 'org-a').returns(
    Shipit::GitHubApp.new('org-a', {}) # no webhook_secret => verify_webhook_signature always true
  )

  payload = {
    "repository" => { "owner" => { "login" => "org-a" }, "full_name" => "org-b/some-repo" },
    "after" => "deadbeef"
  }.to_json

  request.headers['X-Github-Event'] = 'push'
  # no X-Hub-Signature header needed, or an arbitrary bogus one

  assert_enqueued_with(job: GithubSyncJob) do
    post :create, body: payload, as: :json
  end
  assert_response :ok
  # Demonstrates: verify_signature only ever consulted org-a's GitHubApp,
  # yet Handler#stacks (Repository.from_github_repo_name('org-b/some-repo').stacks)
  # is the one actually mutated.
end
```
This demonstrates the equality `Shipit.github(organization: repository_owner)` (org-a) != org implied by `Repository.from_github_repo_name(payload.dig('repository','full_name'))` (org-b) still holds unequal after the fix is missing, i.e. the vulnerability is present.
