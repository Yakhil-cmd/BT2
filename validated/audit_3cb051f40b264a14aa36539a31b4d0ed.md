## Analysis

The reachable analog in ocore is the `bounce()` function in `aa_composer.js`, which refunds an AA trigger's funds when the AA's response bounces (errors out). This mirrors the reported bug class: a batch/loop of amounts is processed together, and if a single item's amount is smaller than a required fee, the **entire batch aborts**, causing loss/freezing of all the other, legitimate amounts in the same batch — not just the offending one.

### Title
AA Trigger Refund Silently Drops All Assets When Any Single Asset Amount Is Below Its bounce_fee - (File: aa_composer.js)

### Summary
When an AA trigger causes the AA to bounce (fail), `bounce()` attempts to refund every asset that the trigger sent to the AA, minus each asset's configured `bounce_fees`. The refund loop aborts entirely — losing the refund for *all* assets, not just the offending one — if any single asset amount in the trigger is smaller than that asset's `bounce_fees` entry.

### Finding Description
`bounce()` iterates over every asset the trigger sent (`trigger.outputs`), and for each asset compares `amount` to `bounce_fees[asset]`: [1](#0-0) 

```
var messages = [];
for (var asset in trigger.outputs) {
    var amount = trigger.outputs[asset];
    var fee = bounce_fees[asset] || 0;
    if (fee > amount)
        return finish(null);
    if (fee === amount)
        continue;
    var bounced_amount = amount - fee;
    messages.push({app: 'payment', payload: {asset: asset, outputs: [{address: trigger.address, amount: bounced_amount}]}});
}
if (messages.length === 0)
    return finish(null);
sendUnit(messages);
```

If the trigger sends multiple assets to the AA (e.g. `base` plus one or more non-base assets, which is fully attacker-controlled since the trigger sender chooses what to send), and **any single** asset's amount happens to be less than the corresponding `bounce_fees[asset]`, the function calls `return finish(null)` immediately — before pushing any refund message. This discards the refund for *every* asset already accumulated in `messages`, not only the offending small one. The remaining, larger amounts of other assets that would otherwise have been safely refunded are silently forfeited: no payment message is ever built for them, and `sendUnit` is never called, so the funds are absorbed into the AA balance instead of being returned to the trigger sender.

This is directly analogous to the reported issue: a queue/batch of user-supplied amounts is processed together, and one entry that is smaller than a fee value causes the whole batch operation to fail, trapping/losing the other (larger, otherwise-refundable) entries that preceded or follow it in the same processing pass.

Note that `bounce_fees` for base asset is checked separately beforehand: [2](#0-1) 
but this earlier check only guards the base asset; it does not protect non-base assets from the same failure mode inside the loop.

### Impact Explanation
Any unprivileged user who triggers an AA with multiple asset payments (base + one or more custom assets) risks permanent loss of all sent funds — including large amounts of assets that individually would have qualified for a valid refund — whenever the AA bounces and one of the co-sent assets' amount is below its `bounce_fees` threshold (a value chosen by the AA author at definition time, and which the trigger sender does not need to match/exceed for every asset they attach). This results in concrete AA fund loss/freezing for the trigger sender: the deposited assets remain stuck in the AA's balance rather than being refunded, with no mechanism for the sender to recover them.

### Likelihood Explanation
Likelihood is Medium: it requires (1) an AA definition with non-zero `bounce_fees` for at least one non-base asset (a normal, encouraged configuration to protect AAs from spam), and (2) a trigger sender attaching multiple assets to a single trigger where one asset's amount is below its fee threshold — this can happen accidentally (e.g., dust from a previous partial payment, unit conversion mismatches) or be deliberately induced by any third party who can influence which assets/amounts get bundled into a trigger unit.

### Recommendation
In the `bounce()` loop, do not abort the entire refund pass when a single asset's amount is below its `bounce_fees`. Instead, skip only that specific asset (treat it as forfeited/kept by the AA) and continue building refund messages for all other assets whose amounts exceed their respective fees, then call `sendUnit(messages)` with whatever qualifies. This prevents one small/dust asset amount from causing loss of unrelated, larger refundable amounts.

### Proof of Concept
1. Define an AA with `bounce_fees: { base: 1000, "<ASSET_A>": 100 }`.
2. Post a trigger to the AA that sends `trigger.outputs = { base: 100000, "<ASSET_A>": 50 }` (base amply covers its fee; `ASSET_A` amount 50 < fee 100) and causes the AA to error/bounce (e.g., a formula condition designed to fail).
3. In `bounce()`, the loop first processes (in ECMAScript key order) `base` (fee 1000 ≤ 100000 → pushes a refund message for `bounced_amount = 99000`), then processes `ASSET_A` (fee 100 > amount 50 → `return finish(null)` immediately).
4. Result: no unit is ever sent (`sendUnit` never called), so the 99000-byte refund that had already been computed and queued is discarded along with the ASSET_A dust — the trigger sender loses the entire 100000 bytes (minus what they'd have normally kept via bounce_fees) plus the 50 units of ASSET_A, all of which remain as AA balance instead of returning to the sender.
