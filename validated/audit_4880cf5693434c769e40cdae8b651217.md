### Title
Cross-organization CI status forgery via organization-scoped webhook signature but repository-unscoped status handler - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to verify a webhook against using the attacker-controlled `repository.owner.login` field of the payload [1](#0-0) . Once that org-scoped signature check passes, `Shipit::Webhooks::Handlers::StatusHandler#process` applies the status update by a bare `Commit.where(sha: params.sha)` lookup with **no repository/stack scoping at all** [2](#0-1) , unlike other handlers (e.g. `PushHandler`) which scope through `Handler#stacks`/`repository_name` [3](#0-2) . This breaks the binding "the organization whose secret authenticated the payload = the repository/stack that gets written," and lets an operator of one onboarded GitHub organization forge a CI status for a commit belonging to a totally different organization's stack on the same shared Shipit instance.

### Finding Description
Shipit explicitly supports hosting multiple GitHub organizations on one instance, each with its own `webhook_secret`, `app_id`, and `installation_id`, selected at runtime via `Shipit.github(organization:)` / `Shipit.github_app_config` [4](#0-3) , as documented in "Using Multiple Github Applications" [5](#0-4) .

The webhook signature is not bound to a specific organization or repository at the protocol level; it is simply an HMAC over the raw JSON body, verified using whichever org's secret `repository_owner` (`payload.dig('repository','owner','login')` or `payload.dig('organization','login')`) happens to name: [6](#0-5) 

Because the operator/administrator of `OrgA` (an organization independently onboarded onto the shared Shipit instance, with their own GitHub App and therefore their own legitimately-known `webhook_secret`) can craft *any* JSON body they like as long as `repository.owner.login == "OrgA"`, they can sign an arbitrary payload with their own secret and still control every other field, including `sha`, `state`, and `context`.

`StatusHandler` then processes this payload with a totally unscoped commit lookup: [2](#0-1) 

`Commit.where(sha: params.sha)` searches across **all stacks in the entire database**, not just stacks belonging to `OrgA`. Applying `create_status_from_github!` triggers `add_status`, which fires `deployable_status` hooks and, when the state is `success`, calls `stack.schedule_merges`, which can proceed to continuous deployment: [7](#0-6) [8](#0-7) 

### Impact Explanation
An operator of `OrgA` — who has zero privileges over `OrgB`'s repositories, teams, or GitHub app — can forge a passing/failing CI status for any commit `sha` in `OrgB`'s stacks by guessing/observing the sha (commits/shas are often publicly visible on GitHub) and picking the `context` that matches `OrgB`'s required/blocking status check. This can mark a commit as `deployable?` when its real CI has not passed, enabling an **unauthorized deploy** (or blocking one by marking it as `failure`, a lesser DoS-adjacent effect that is out of scope). This crosses the "an organization that authenticated versus the repository that is written" boundary called out in scope, and lands on the in-scope High-severity bucket ("escalation into authorization... unauthorized deploy").

### Likelihood Explanation
Any tenant organization already onboarded to a shared multi-org Shipit deployment (a documented, supported configuration) can exploit this without any additional credentials beyond their own legitimate `webhook_secret` for their own org. No `ApiClient` token, session, or GitHub App private key for the victim org is required — only knowledge of the target commit's sha and required status context, both of which are frequently public/discoverable.

### Recommendation
Scope `StatusHandler#process` (and any other handler that doesn't already use `Handler#stacks`) to the repository named in the payload, e.g. `stacks.flat_map(&:commits).where(sha: params.sha)`, or otherwise verify that the commit's stack's repository actually belongs to the organization whose secret validated the signature before applying the status.

### Proof of Concept
1. Shipit is configured with multiple GitHub orgs, e.g. `OrgA` and `OrgB`, per `docs/setup.md`'s multi-app scheme.
2. Attacker is the legitimate operator of `OrgA`'s GitHub App and therefore knows `OrgA`'s `webhook_secret`.
3. Attacker crafts:
```json
{
  "repository": { "owner": { "login": "OrgA" } },
  "sha": "<sha of a commit belonging to OrgB's stack>",
  "state": "success",
  "context": "<the required/blocking CI context configured for OrgB's stack>"
}
```
4. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(OrgA_webhook_secret, body)>` and POSTs to `/webhooks` with `X-Github-Event: status`.
5. `verify_signature` resolves `repository_owner == "OrgA"`, verifies against `OrgA`'s secret, and passes [1](#0-0) .
6. `StatusHandler#process` runs `Commit.where(sha: params.sha)`, finds the `OrgB` commit (no org/repo scoping check), and creates a forged `success` status on it, potentially triggering `OrgB`'s continuous deployment.

      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
