### Title
Cross-organization forged commit status injection via unscoped `Commit.where(sha:)` lookup - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
The webhook signature verification in `WebhooksController#verify_signature` selects the GitHub App/organization whose `webhook_secret` is used to validate the HMAC based on the attacker-controlled `repository.owner.login` field of the *same* JSON payload being verified [1](#0-0) . The organization used for the signature check is never re-validated against the actual data the event handler operates on. `StatusHandler#process` uses no organization/repository scoping whatsoever — it looks up commits purely by `sha` across the entire Shipit instance and attaches whatever status the payload carries [2](#0-1) . This breaks the equality "organization authenticated == repository/commit written."

### Finding Description
`WebhooksController#verify_signature` derives the signing organization from the payload itself:
```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [3](#0-2) 
and uses it to fetch the corresponding `GitHubApp` config for signature verification:
```ruby
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
``` [4](#0-3) 

Shipit explicitly supports multiple organizations, each with its own independent `webhook_secret`, as shown in the multi-org secrets example [5](#0-4) . Anyone with legitimate control of a GitHub App configured for *one* organization on a shared Shipit instance therefore knows that organization's `webhook_secret` and can compute a valid `X-Hub-Signature` for **any** payload body they choose, as long as `repository.owner.login` (or `organization.login`) in that payload matches the org they control.

Once the signature passes, `StatusHandler#process` is invoked with the fully attacker-controlled payload and performs no repository/organization check at all:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [2](#0-1) 
Unlike other handlers that at least resolve `params.repository.full_name` to scope the operation to a `Repository`/`Stack` (see `Handler#stacks`/`#repository_name` and the pull-request handlers) [6](#0-5) [7](#0-6) , `StatusHandler` matches purely on the raw `sha` string across the whole install, with no relation to `repository.owner.login` used for signature verification, nor to `repository.full_name`.

### Impact Explanation
An attacker who legitimately controls one organization's GitHub App (and thus its `webhook_secret`) on a shared Shipit instance can forge a signed `status` webhook event that sets `state: success` (and a fabricated `context`) for the `sha` of a commit belonging to a completely different, unrelated stack/organization hosted on the same instance. If that victim stack's `shipit.yml` declares `ci.require` contexts, the forged status can satisfy those requirements and unblock a deploy that should have been gated by real CI results — an unauthorized deploy path, which is explicitly in the accepted High/Critical impact list.

### Likelihood Explanation
Low-to-medium: it requires the attacker to control at least one organization/GitHub App configured on a multi-tenant Shipit instance (a legitimate but limited privilege) and to know or guess a `sha` present in the victim stack (commit SHAs are public on GitHub, and Shipit stacks are typically tied to public/known repos), so this is analogous in severity to the low-likelihood condition described in the report.

### Recommendation
Bind the identity used for signature verification to the identity used by the handler:
- Have `StatusHandler` (and any other handler) resolve the target `Repository`/`Stack` via `params.repository.full_name` first, and only then look up commits scoped to that repository's stacks, mirroring what `Handler#stacks` already does for other handlers.
- Additionally, verify that `repository.owner.login` (used to pick the webhook secret) matches the owner portion of `repository.full_name` before processing, so a payload cannot claim membership in one org for signature purposes while acting on another org's data.

### Proof of Concept
1. Attacker legitimately administers `attacker-org`'s GitHub App on a shared Shipit instance and knows its `webhook_secret`.
2. Attacker learns (via public GitHub) the SHA of a commit `abc123` on `victim-org/victim-repo`, tracked by a Shipit stack requiring `ci/required-context` per its `shipit.yml`.
3. Attacker crafts a `status` event JSON body:
```json
{
  "sha": "abc123",
  "state": "success",
  "context": "ci/required-context",
  "repository": {"owner": {"login": "attacker-org"}, "full_name": "attacker-org/attacker-repo"}
}
```
4. Attacker computes `X-Hub-Signature` using `attacker-org`'s known `webhook_secret` and POSTs it to `/github/webhooks`.
5. `verify_signature` resolves `repository_owner` = `"attacker-org"`, fetches `attacker-org`'s `GitHubApp`, and the HMAC check passes [4](#0-3) .
6. `StatusHandler#process` runs `Commit.where(sha: "abc123")`, finds the commit belonging to `victim-org/victim-repo`'s stack, and creates a fake successful status on it [2](#0-1) , potentially satisfying that stack's `ci.require` gate and enabling an unauthorized deploy.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```
