### Title
Disabled trust check lets indirect (non-corresponding) devices send fully-trusted wallet subjects - ([File: wallet.js])

### Summary
`handleMessageFromHub` in `wallet.js` is supposed to restrict messages coming from "indirect correspondents" — devices that were auto-added as correspondents via `addIndirectCorrespondents` (e.g. cosigners of a shared address introduced by another party) but never explicitly paired/confirmed by the local user — to only a small safelist of subjects. This restriction has been commented out, so any device known only as an indirect (unpaired, synthetic) correspondent can now send arbitrary wallet-protocol subjects that are normally reserved for fully-trusted, explicitly-paired correspondents.

### Finding Description
`device.js`'s hub-message handler distinguishes between fully known/confirmed correspondents and devices that are merely `is_indirect=1` in `correspondent_devices` (added automatically through `addIndirectCorrespondents` when cosigner lists are exchanged for shared/multisig addresses): [1](#0-0) 

The `bIndirectCorrespondent` flag is passed through to `handleMessageFromHub` in `wallet.js`. The intended guard, still visible as a comment, restricted indirect correspondents to only `"cancel_new_wallet"`, `"my_xpubkey"`, and `"new_wallet_address"`: [2](#0-1) 

That check is disabled (`//`), so `bIndirectCorrespondent` is now effectively unused for gating — an indirect correspondent can send any subject the switch statement supports (e.g. `pairing`, `text`, `object`, `removed_paired_device`, `sign`, `arbiter_contract_response`, private-payment related subjects, etc.) with the same trust level as a device the user explicitly paired with.

`addIndirectCorrespondents` inserts a correspondent row purely from data supplied by a peer during a shared-address/cosigner setup flow, without any pairing secret or explicit user confirmation: [3](#0-2) 

This mirrors the Mattermost CVE-2024-39836 bug class (CWE-693 Protection Mechanism Failure): a party that is only "indirectly" known/synthetic (analogous to Mattermost's remote/synthetic shared-channel users) is meant to be restricted from privileged actions, but the enforcement was removed/never wired in, letting the untrusted party act as if fully trusted.

### Impact Explanation
An indirect correspondent — introduced only because it was listed as a cosigner on some shared address, without the local user ever pairing with or vetting that device — can now send messages such as `removed_paired_device`, `arbiter_contract_response`, signature requests, or other wallet-flow subjects that assume the sender is a confirmed, trusted correspondent. Depending on which handlers are reached, this can be leveraged to manipulate wallet state associated with shared/multisig addresses (e.g., contract state transitions, correspondent removal/blackholing, injecting attacker-controlled `peer_addresses` records used later for signing/payment flows) that the disabled check was specifically meant to prevent for untrusted, non-explicitly-paired peers. This is a funds/contract-integrity-adjacent trust boundary failure, not a mere UX issue.

### Likelihood Explanation
Any counterparty in a shared address / multisig / prosaic or arbiter contract setup can cause itself, or a third device it controls, to be added as an indirect correspondent via `addIndirectCorrespondents` (this happens automatically as part of normal cosigner-address setup, requiring no explicit pairing approval from the victim). Once added, that device can immediately send any subject over `hub/message` — the hub-side signature/hash checks in `device.js` (lines 154-189) only prove authenticity of the sender, not the sender's authorization level, so this path is reachable by any unprivileged peer that participates in a shared address setup with the victim.

### Recommendation
Restore and enforce the `bIndirectCorrespondent` allowlist check in `wallet.js`'s `handleMessageFromHub` (or a stricter equivalent), ensuring indirect/unconfirmed correspondents can only send the minimal bootstrap subjects necessary to complete pairing/wallet setup (e.g. `cancel_new_wallet`, `my_xpubkey`, `new_wallet_address`), and reject/ignore all other subjects from such senders until the correspondent is explicitly confirmed/paired.

### Proof of Concept
1. Attacker device A initiates a shared-address/multisig wallet setup with victim device V, listing attacker device B (or A itself with a different identity) as an additional cosigner in the exchanged cosigner list.
2. V's `device.js` message handler calls `addIndirectCorrespondents`, inserting B into `correspondent_devices` with `is_indirect=1` — B was never paired with V and never went through `handlePairingMessage`. [3](#0-2) 
3. B now sends a `hub/message` to V with an arbitrary subject (e.g. `arbiter_contract_response` or `removed_paired_device`) that is normally reserved for confirmed correspondents.
4. Because the disabled check at `wallet.js:92-93` no longer filters by `bIndirectCorrespondent`, V's `handleMessageFromHub` processes the message via the normal `switch(subject)` path as if B were a fully trusted correspondent. [4](#0-3)
