### Title
`provision?` operator-precedence bug lets `prevent_with_label` create review stacks even when `review_stacks_enabled: false` - ([File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb])

### Summary
`provision?` in `OpenedHandler` mixes `&&` and `||` without parentheses grouping `review_stacks_enabled` across all branches, so only the `allow_all` clause is gated by `review_stacks_enabled`. The `prevent_with_label` clause is evaluated independently of `review_stacks_enabled`, so opening an unlabeled PR against a repository with review stacks explicitly disabled but `provisioning_behavior: prevent_with_label` still creates a stack.

### Finding Description
The binding the code is supposed to enforce is: `repository.review_stacks_enabled == true` at the moment `provision?` authorizes stack creation, for every provisioning behavior, not just `allow_all`.

The actual code is: [1](#0-0) 

Because `&&` binds tighter than `||` in Ruby, this parses as:

`(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?)`

Only the first disjunct is gated by `review_stacks_enabled`; the second and third are not. Concretely, if `repository.provisioning_behavior_prevent_with_label?` is true and the PR carries no label, `provision?` returns `true` unconditionally — `review_stacks_enabled` is never consulted for that branch.

Exploit flow: an unprivileged GitHub user opens a pull request (or triggers the webhook payload equivalent) against a repository configured with `provisioning_behavior: prevent_with_label` and `review_stacks_enabled: false`, without applying the provisioning label (the default state for any PR — labels are opt-in). `pull_request_has_provisioning_label?` returns `false` via `pull_request_label_names.include?(repository.provisioning_label_name)`: [2](#0-1) 

`respond_to_pull_request_opened?` then returns `true`, and `process` calls `ReviewStackAdapter#find_or_create!`, creating a `Stack`/`ReviewStack` record for a repository whose operator explicitly disabled review-stack provisioning: [3](#0-2) 

No existing guard prevents this: `params` schema validation only validates payload shape, not authorization logic; `repository.review_stacks_enabled` is read but its result is discarded for two of the three OR-branches due to precedence; there is no separate check gating stack creation on `review_stacks_enabled` before calling `find_or_create!`. The identical bug (same code, same precedence) exists in `ReopenedHandler#unarchive?`: [4](#0-3) 

The existing test suite does not catch this: the only `prevent_with_label` test in `opened_handler_test.rb` uses the default `provisioning_enabled: true`, so it never exercises the `review_stacks_enabled: false` case: [5](#0-4) [6](#0-5) 

### Impact Explanation
An unprivileged party who can open/label a PR against any repository configured with `provisioning_behavior: prevent_with_label` triggers creation of a `Stack`/`ReviewStack` record and drives it into the provisioning queue for a repository whose operator explicitly turned `review_stacks_enabled` off. This is a write (stack creation, and downstream provisioning/deploy task scheduling) that the repository owner did not authorize, matching "an unauthorized deploy... or a payload... mutating another's stack." It is repeatable against any repository using this behavior configuration, and the attacker only needs to control PR metadata (branch name, absence of a label) on a repo they can open PRs against.

### Likelihood Explanation
Preconditions: target repository must have `review_stacks_enabled: false` and `provisioning_behavior: prevent_with_label` — a configuration an operator would reasonably choose believing review stacks are entirely disabled. Attacker cost is trivial: open a PR (or a fork PR) without adding any label; no secrets, tokens, or privileged roles required, matching the stated attacker model exactly. It is fully repeatable per pull request opened.

### Recommendation
Add explicit parentheses so `review_stacks_enabled` gates every disjunct:
```ruby
def provision?
  repository.review_stacks_enabled &&
    (repository.provisioning_behavior_allow_all? ||
     (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
     (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?))
end
```
Apply the identical fix to `ReopenedHandler#unarchive?`.

### Proof of Concept
In `test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb`:
```ruby
test "does not create stacks when review_stacks_enabled is false, even for prevent_with_label with no label" do
  repository = shipit_repositories(:shipit)
  configure_provisioning_behavior(
    repository:,
    provisioning_enabled: false,
    behavior: :prevent_with_label,
    label: "pull-requests-label"
  )
  payload = payload_parsed(:pull_request_opened)
  payload["pull_request"]["labels"] = []

  assert_equal false, repository.review_stacks_enabled
  assert_no_difference -> { Shipit::Stack.count } do
    OpenedHandler.new(payload).process
  end
end
```
Before the fix, this assertion fails: `Shipit::Stack.count` increases by 1 despite `repository.review_stacks_enabled == false`, proving `provision?` authorizes creation without the binding `review_stacks_enabled == true` being satisfied.
