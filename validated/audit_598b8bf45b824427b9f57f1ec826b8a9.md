### Title
Unbounded submodule/tree recursion under a fixed `--sync-timeout` enables persistent sync denial from attacker-pushed repo content - (File: `main.go`)

### Summary
`git-sync`'s core bug class analog to the Putty `_transferERC20sOut`/`_transferERC721sOut`/`_transferFloorsOut` issue is the unbounded work performed inside `configureWorktree()`'s `git submodule update --init [--recursive]` call and the general checkout/fetch pipeline in `SyncRepo()`, all of which must complete inside a single, fixed `--sync-timeout` window. There is no limit on the number or depth of submodules, refs, or files a remote/attacker-controlled repository can contain, exactly mirroring the "no upper bound on loop iterations over externally-controlled data" defect from the report.

### Finding Description
Each sync attempt is wrapped in one fixed-duration context: [1](#0-0) 

That single `ctx` is threaded through `git.SyncRepo(ctx, ...)`, which performs `fetch`, `reset --hard`, and — critically — submodule initialization with no bound on the number/depth of submodules: [2](#0-1) 

The actual git subprocess is executed with `exec.CommandContext(ctx, ...)`, so when the deadline is hit the process is killed and the call returns an error, but only after however much of the (attacker-controlled) recursive submodule tree it managed to process before being killed: [3](#0-2) 

Because `--submodules` defaults to `recursive` and depth/width of the submodule graph in `.gitmodules` is entirely determined by whatever content the attacker can push to (or provide via) the tracked `--ref`, a single push can add an arbitrarily large/deep submodule tree (or simply an enormous number of tracked files) that requires more processing time than `--sync-timeout` allows. This is the direct analog of Putty's unbounded `for` loop over the caller-supplied asset list.

### Impact Explanation
Under this condition every sync attempt fails with `context deadline exceeded`: [4](#0-3) 
If `--max-failures` is a positive bound, the process exits (`os.Exit(1)`), and if it is unset/negative it retries forever without ever completing a sync — in both cases the sidecar can never publish the new (or even the initial) revision, i.e. persistent sync denial matching the report's accepted "orders unexercisable/unwithdrawable" analog (data becomes permanently un-syncable, and if it happens on the very first sync, `setRepoReady()` is never called so the liveness endpoint stays unhealthy). This matches "persistent sync denial," one of the accepted impact categories.

### Likelihood Explanation
This requires only ordinary, unprivileged write access to the tracked repository/ref (push access, or control over an upstream the operator has pointed `--repo`/`--ref` at) — no leaked keys, no malicious operator, no node compromise. The operator does control `--sync-timeout`, and can raise it as a partial mitigation, similar to how Putty's team relied on off-chain (UI/DB) limits rather than an on-chain bound; but git-sync has no equivalent enforced cap on submodule count/depth or tree size at the code level, so a sufficiently large/deep malicious commit can always be crafted to exceed any fixed timeout the operator chooses (especially combined with `--depth`/`--submodules=recursive`, or many small refs/objects that inflate fetch+checkout time). Likelihood is assessed as low-to-medium: it requires deliberate malicious content and depends on the operator's timeout headroom, but there is no code-level ceiling that prevents it, consistent with the original medium-severity judgment.

### Recommendation
- Add explicit, configurable limits on submodule recursion depth/count (or total checked-out object count) independent of `--sync-timeout`, and fail fast with a clear error rather than silently timing out mid-operation.
- Consider separating the timeout budget for `fetch` vs. `submodule update` vs. `checkout` steps so a slow submodule tree cannot consume the entire sync budget silently, and surface partial-progress telemetry so operators can detect repositories that are approaching limits before hitting a hard failure loop.
- Document that `--submodules=recursive` combined with untrusted/branch-following `--ref` content is a potential availability risk, similar to Putty's documented 30-asset UI limit, and provide a `--submodules-max-depth`/`--max-tree-entries`-style flag.

### Proof of Concept
1. Configure `git-sync --repo=<attacker-writable-or-followed-repo> --ref=<tracked-branch> --submodules=recursive --sync-timeout=<operator-chosen value>`.
2. An attacker with push access to the tracked branch (or to any of its transitively recursive submodules) adds a very large number of nested submodules (or a very large tree) and commits/pushes.
3. On the next sync, `configureWorktree()`'s `git submodule update --init --recursive` (main.go:1733-1747) begins processing the new submodule graph inside the fixed `ctx` from the sync loop (main.go:1052-1056).
4. If total processing time exceeds `--sync-timeout`, `exec.CommandContext` kills the git subprocess and `SyncRepo` returns a `context deadline exceeded` error (pkg/cmd/cmd.go:85-87); this repeats every retry, and depending on `--max-failures` either causes the process to exit or to loop indefinitely — the desired ref is never published (persistent sync denial), analogous to the referenced report's unbounded-loop DoS on `exercise()`/`withdraw()`.
