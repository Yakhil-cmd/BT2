### Title
Protocol/matching fee permanently locked in `order_book_exchange` AA with no withdrawal path - (File: test/samples/order_book_exchange.oscript)

### Summary
The order-matching case of the `order_book_exchange` Autonomous Agent deducts a flat 1000-byte fee from both counterparties' tracked balances on every trade execution, but never credits that fee to any address's balance variable. The bytes remain physically inside the AA's on-chain balance, yet the AA's internal accounting (the only mechanism by which funds can ever be paid out via the `withdraw` case) never records them anywhere, so they can never be withdrawn by anyone — including the AA's operator/definer.

### Finding Description
The AA tracks all deposited/owned funds per user in `var['balance_<address>_<asset>']` state variables, and the only way to move bytes/assets out of the AA is the "withdraw" case, which pays `trigger.data.amount` and decrements `var[$key]` accordingly: [1](#0-0) 

In the order-matching case, when two signed orders cross, the AA computes a flat `$fee = 1000` and subtracts it from each trader's `base` balance variable: [2](#0-1) 

This is the exact analog of the reported `Raises.sol::close` bug: an accounting entity (`raise.fees` / here, the `$fee` taken from each trader) is subtracted from the user-facing ledger but is never added to any global/claimable balance (`fees[raise.currency]` / here, a `var['fee_balance_base']` or similar). Since `balance[base]` (the AA's real byte balance) already includes these fees automatically (they were part of the trigger outputs originally deposited by the users via the "silently accept coins" case), but no state variable is ever incremented to reflect that the operator (or anyone) owns this amount, the bytes become permanently untrackable and therefore unwithdrawable through the AA's own logic — since the only spend path (`withdraw`) is gated by `var[$key]`, and no key ever accounts for the collected fee.

### Impact Explanation
Every successful trade match burns 2000 bytes total (1000 from each side) into the AA balance with no path to recover them — not by the users, not by the AA operator. Funds are permanently locked inside the AA. This is a direct "AA fund loss/freezing" outcome as required by the validation rubric: real value denominated in bytes becomes irretrievably stuck in the contract with each trade, growing over time as more orders execute.

### Likelihood Explanation
This is trivially and deterministically reachable by any two AA trigger senders (an unprivileged unit poster) who submit two crossing signed orders via `trigger.data.order1`/`trigger.data.order2`. No special privilege, race condition, or malicious peer/node behavior is required — it happens on every single successful order match, guaranteed by the logic itself.

### Recommendation
Before or when subtracting `$fee` from each trader's balance, credit the same amount to a dedicated, withdrawable ledger entry (e.g., `var['balance_' || definer_address || '_base']` or a distinct `var['fee_balance_base']`), and add a corresponding case (gated to the AA's admin/definer address) allowing that accumulated fee balance to be withdrawn, mirroring the fix pattern of adding `raise.fees` to the global `fees[currency]` mapping before the state transition in the referenced report.

### Proof of Concept
1. Two users each deposit bytes into the AA via the "silently accept coins" case, populating their `var['balance_<address>_base']`.
2. Each submits a signed order and a third caller submits both orders together (`trigger.data.order1`, `trigger.data.order2`) matching them.
3. The AA executes the trade-match branch: `$fee = 1000` is subtracted from `var[$base_key1]` and `var[$base_key2]` for both traders.
4. No `var[]` entry anywhere is incremented by `2*$fee`; querying all state variables shows the sum of all `balance_*` variables is now less than the AA's actual on-chain byte balance by 2000 bytes.
5. There is no case in the AA (no admin/fee-withdrawal branch) that can ever pay out this difference — the fee bytes are permanently stuck in the AA's balance.
