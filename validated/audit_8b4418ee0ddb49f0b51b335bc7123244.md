### Title
Webhook signature verification is bypassed for any GitHub organization without a configured `webhook_secret`, allowing forged `membership` events to grant unprivileged attackers `Shipit.github_teams` authorization - (File: `lib/shipit/github_app.rb`)

### Summary
`Shipit::GitHubApp#verify_webhook_signature` unconditionally returns `true` when the organization's `webhook_secret` is blank [1](#0-0) , and `webhook_secret` is explicitly documented as optional per-organization configuration [2](#0-1) . `WebhooksController#verify_signature` selects the `GitHubApp` instance (and therefore the verification policy) purely from the unauthenticated JSON body's `repository.owner.login` / `organization.login` field [3](#0-2) . As a result, an attacker with no Shipit session, no ApiClient token and no GitHub push/org access can submit an arbitrary, unsigned `membership` webhook naming any organization that has not set a `webhook_secret`, and Shipit will process it as legitimate.

### Finding Description
The equality this design is supposed to preserve is:
`organization whose webhook signature was cryptographically verified == organization whose membership/team data is written`.

The break: when `webhook_secret` is nil/blank for that organization's config, the "verification" step degenerates to an unconditional `true`, so the binding becomes `organization named in the unauthenticated payload == organization whose membership data is written`, with no cryptographic proof required at all.

Concretely:
1. `WebhooksController#create` parses the raw JSON body and dispatches it to registered handlers only after `verify_signature` passes [4](#0-3) .
2. `verify_signature` looks up the `GitHubApp` for `repository_owner`, itself derived from attacker-controlled JSON (`params.dig('repository','owner','login')` or `params.dig('organization','login')`), then calls `verify_webhook_signature` [5](#0-4) [6](#0-5) .
3. `verify_webhook_signature` trusts the request outright whenever `webhook_secret` is not configured for that org: `return true unless webhook_secret` [1](#0-0) .
4. The `membership` event is routed to `MembershipHandler`, which trusts the payload's `team`, `organization`, and `member.login` fields to create/find a `Team` and add a `User` (created on the fly from an arbitrary login) as a member [7](#0-6) .
5. `User#authorized?` — the gate used by `force_github_authentication` on essentially every Shipit page/action — is computed solely from `Team`/`Membership` rows: `Shipit.github_teams.empty? || teams.where(id: Shipit.github_teams.map(&:id)).exists?` [8](#0-7) [9](#0-8) .

So an attacker who merely has (or fabricates) any GitHub login, and who knows/guesses an organization configured on this Shipit instance without a `webhook_secret` (an explicitly supported, documented configuration), can inject a `Membership` row that satisfies `authorized?` for their own `User` record, bypassing the intended "must be a member of one of `Shipit.github_teams`" restriction entirely.

### Impact Explanation
This breaks the binding between "GitHub identity verified via signed webhook" and "authorization granted inside Shipit," directly matching the in-scope High-severity category "escalation into `Shipit.github_teams` authorization." Once `authorized?` returns true, the attacker's session (obtained via a normal, unprivileged GitHub OAuth login that this engine allows for any GitHub account) gains full access to the Shipit UI/API: viewing stack state, triggering deploys/rollbacks/tasks, and creating `ApiClient` tokens — escalating toward the Critical-level "unauthorized deploy" outcome once inside.

### Likelihood Explanation
Exploitation requires no credentials, tokens, or secrets whatsoever — the attacker sends a single unauthenticated HTTP POST to the public `/webhooks` endpoint. The only precondition is that at least one configured GitHub organization on the instance has an unset `webhook_secret`, which is an explicitly documented, supported, "optional" setting [2](#0-1) , not a misconfiguration outside the engine's control. Multi-org test fixtures in this codebase also show `webhook_secret: # nil` as an accepted default [10](#0-9) .

### Recommendation
- Fail closed instead of open in `verify_webhook_signature` when `webhook_secret` is blank — reject the request (or require a `webhook_secret` to be mandatory for orgs that register `membership`/authorization-relevant hooks) rather than treating an absent secret as "trusted."
- At minimum, do not let unsigned `membership` events affect `Team`/`Membership` records that feed into `User#authorized?`; consider requiring the acting `Team` to be fetched/reconciled via an authenticated GitHub API call rather than trusting webhook payload fields directly.

### Proof of Concept
Given a Shipit instance configured with two GitHub orgs, where `OrgWithoutSecret` has no `webhook_secret` set, and `Shipit.github_teams` includes a team belonging to `OrgWithoutSecret`:

1. Attacker signs in through the normal GitHub OAuth flow with their own (unprivileged) GitHub account, creating a `User` with `authorized? == false`.
2. Attacker sends, with no signature header required:
```
POST /webhooks
X-Github-Event: membership
Content-Type: application/json

{
  "action": "added",
  "team": { "id": <id-of-team-in-Shipit.github_teams>, "name": "Deployers", "slug": "deployers", "url": "https://example.com" },
  "organization": { "login": "OrgWithoutSecret" },
  "member": { "login": "<attacker-github-login>" },
  "repository": { "owner": { "login": "OrgWithoutSecret" } }
}
```
3. `verify_webhook_signature` returns `true` (no `webhook_secret` configured for `OrgWithoutSecret`), `MembershipHandler` creates/finds the `Team` and adds the attacker's `User` as a member.
4. Attacker's `User#authorized?` now returns `true`, and `force_github_authentication` grants full access to Shipit stacks/deploys/tasks.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```

```ruby
      if current_user.logged_in? && current_user.requires_fresh_login?

        reset_session
        redirect_to(Shipit::Engine.routes.url_helpers.github_authentication_path(origin: request.original_url))
```
