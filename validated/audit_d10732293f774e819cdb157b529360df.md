### Title
Governance `checkConsistency` validates each KIP-71 base-fee bound vote in isolation, allowing a single epoch to ratify `LowerBoundBaseFee > UpperBoundBaseFee` — (`File: kaiax/gov/headergov/impl/header.go`)

### Summary

The `checkConsistency` function in the header-governance module validates each vote against the **current** (pre-epoch) parameter set. Because both `kip71.lowerboundbasefee` and `kip71.upperboundbasefee` can be voted in the same epoch, and each vote is checked only against the live values (not against other pending votes in the same epoch), the epoch-boundary ratification can commit a state where `LowerBoundBaseFee > UpperBoundBaseFee`. This violates the invariant that the KIP-71 EIP-1559 base-fee mechanism depends on, and no guard at ratification time re-checks the combined result.

### Finding Description

`checkConsistency` in `kaiax/gov/headergov/impl/header.go` handles the two KIP-71 bound parameters as follows:

```go
case gov.Kip71LowerBoundBaseFee:
    params := h.GetParamSet(blockNum)          // reads CURRENT live params
    if vote.Value().(uint64) > params.UpperBoundBaseFee {
        return ErrLowerBoundBaseFee
    }
    return nil
case gov.Kip71UpperBoundBaseFee:
    params := h.GetParamSet(blockNum)          // reads CURRENT live params
    if vote.Value().(uint64) < params.LowerBoundBaseFee {
        return ErrUpperBoundBaseFee
    }
    return nil
``` [1](#0-0) 

Each vote is validated in isolation against the current parameter set. The ratification logic in `getExpectedGovernance` simply collects all votes from the previous epoch and applies the last value per parameter name — it performs no cross-parameter consistency check:

```go
for _, voteBlock := range sortedVoteBlocks {
    vote := prevEpochVotes[voteBlock]
    govs.Add(string(vote.Name()), vote.Value())
}
return headergov.NewGovData(govs)
``` [2](#0-1) 

`VerifyGov` only checks that the ratified governance block exactly matches what `getExpectedGovernance` computed — it does not re-run the cross-parameter invariant check: [3](#0-2) 

The README confirms that for each governance parameter, the last vote in the epoch is ratified, and both `kip71.lowerboundbasefee` and `kip71.upperboundbasefee` are independently votable parameters: [4](#0-3) 

### Impact Explanation

With `LowerBoundBaseFee > UpperBoundBaseFee` committed to the governance history, every subsequent call to `GetParamSet` returns an incoherent KIP-71 configuration. The base-fee adjustment algorithm clamps the base fee to `[Lower, Upper]`; when `Lower > Upper` this range is empty, producing undefined clamping behavior. Concretely:

- All transactions whose `GasFeeCap` satisfies one bound but not the other will be incorrectly accepted or rejected by the tx-pool and state-transition checks.
- The base fee can never settle to a valid value, breaking the fee market for the entire network until a corrective governance vote is ratified (one full epoch later, ~1 week on mainnet).

This is a persistent invalid governance state affecting every block's fee calculation — a protected-state corruption with network-wide impact.

### Likelihood Explanation

In `single` governance mode (used by Kaia Mainnet and Kairos), only the single governing node can vote. That node can cast both votes in the same epoch without any external coordination. In `none` mode, any GC member can cast both votes. The trigger requires no special on-chain condition beyond the governing node (or any GC member in `none` mode) casting two votes in the same epoch — a routine governance operation. No majority-validator collusion is required.

### Recommendation

Re-run the cross-parameter invariant check at ratification time. In `getExpectedGovernance` (or in `VerifyGov`), after assembling the full `govs` map for the epoch, verify that if both `kip71.lowerboundbasefee` and `kip71.upperboundbasefee` are present in the ratified set, the resulting `Lower <= Upper` invariant holds. If it does not, reject the ratification or drop the offending vote. Additionally, `checkConsistency` should check the new value against **pending votes in the same epoch** for the sibling parameter, not only against the current live value.

### Proof of Concept

Setup: `epoch = 1000`, current params: `LowerBoundBaseFee = 25 gwei`, `UpperBoundBaseFee = 750 gwei`.

1. Governing node casts vote at block 100: `kip71.lowerboundbasefee = 500 gwei`.
   - `checkConsistency`: `500 <= 750 (current Upper)` → **passes**.
2. Governing node casts vote at block 200: `kip71.upperboundbasefee = 100 gwei`.
   - `checkConsistency`: `100 >= 25 (current Lower)` → **passes**.
3. At block 1000 (epoch boundary), `getExpectedGovernance` collects both votes and ratifies `{Lower=500, Upper=100}`.
4. `VerifyGov` confirms the ratified block matches the locally computed map → **passes**.
5. From block 2000 onward, `GetParamSet` returns `LowerBoundBaseFee=500 > UpperBoundBaseFee=100`.
6. The KIP-71 base-fee clamp `[500, 100]` is an empty interval; every block's base-fee update produces an incoherent value, breaking the fee market for all subsequent transactions.

func (h *headerGovModule) VerifyGov(header *types.Header) error {
	// (1)
	if header.Number.Uint64()%h.epoch != 0 {
		if len(header.Governance) > 0 {
			logger.Error("governance is not allowed in non-epoch block", "num", header.Number.Uint64())
			return ErrGovInNonEpochBlock
		} else {
			return nil
		}
	}

	// (2), (3)
	expected := h.getExpectedGovernance(header.Number.Uint64())
	if len(header.Governance) == 0 {
		if len(expected.Items()) != 0 {
			return ErrGovVerification
		}

		return nil
	}

	// (4)
	var gb headergov.GovBytes = header.Governance
	actual, err := gb.ToGovData()

	}

	// (5)

		logger.Error("Governance mismatch", "expected", expected, "actual", actual)

	}

func (h *headerGovModule) getExpectedGovernance(blockNum uint64) headergov.GovData {
	prevEpochIdx := calcEpochIdx(blockNum, h.epoch) - 1
	prevEpochVotes := h.getVotesInEpoch(prevEpochIdx)
	govs := make(gov.PartialParamSet)

	sortedVoteBlocks := slices.Collect(maps.Keys(prevEpochVotes))
	slices.Sort(sortedVoteBlocks)

	for _, voteBlock := range sortedVoteBlocks {
		vote := prevEpochVotes[voteBlock]
		govs.Add(string(vote.Name()), vote.Value())
	}

	// assert(len(headergov.NewGovData(govs).Items()) == len(govs))
	return headergov.NewGovData(govs)
}

The ratification condition is determined by the `governance.governancemode` parameter. Mainnet and Kairos both operate in `single` mode. There are two governance modes:

- `none` mode: all members of the GC can vote. For each governance parameter, the last vote in the epoch will be ratified.
- `single` mode: only one member of the GC, stipulated in the parameter `governance.governingnode`, can vote. All valid votes from the governing node in the epoch are ratified in block order. For each governance parameter, the last vote in the epoch will be ratified.

Parameter change ratified at `k*epoch` block takes effect starting from `(k+1)*epoch` block.
