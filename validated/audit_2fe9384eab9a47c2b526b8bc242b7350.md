### Title
`StatusHandler#process` writes commit statuses without scoping to the sending repository - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` looks up commits with `Commit.where(sha: params.sha)` and writes a status to every match, with no filter on the repository/stack that the webhook actually belongs to. Sibling handlers (`PushHandler`, `CheckSuiteHandler`) explicitly scope their writes through the `stacks` helper (which resolves `Repository.from_github_repo_name(repository_name)`), but `StatusHandler` never calls `stacks` or `repository_name` at all, so a legitimately-signed `status` webhook from one repository can mutate `Commit`/`Status` rows belonging to any other stack that happens to share the same commit SHA.

### Finding Description
The broken binding, stated as an equality that should hold but does not:
`commit.stack.repository.full_name == payload['repository']['full_name']` for every `commit` mutated by `StatusHandler#process`.

Trace:
- `Shipit::Webhooks::Handlers::Handler#initialize` parses `payload` into `params` via the `ExplicitParameters` schema declared in `StatusHandler.params` (only `sha`, `state`, `description`, `target_url`, `context`, `created_at`, `branches` — no `repository`). [1](#0-0) 
- `process` does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` — a global, unscoped query across the entire `commits` table, spanning every stack/repository tracked by the Shipit instance. [2](#0-1) 
- The base `Handler` class defines `stacks` and `repository_name` helpers specifically to scope writes to the webhook's own repository (`Repository.from_github_repo_name(payload.dig('repository','full_name'))`), and both `PushHandler#process` and `CheckSuiteHandler#process` use them to filter before touching any commit. [3](#0-2) [4](#0-3) [5](#0-4) 
- `StatusHandler` alone omits this scoping. Signature verification in `GithubHook`/`WebhooksController` only proves the payload was signed for *some* repository — the attacker's own — it does not, and cannot, restrict which `Commit` rows get matched by `Commit.where(sha: ...)` inside the handler.

Exploit flow: An attacker who owns/administers a repository that is a fork of (or shares git history with) a repository tracked as a Shipit stack has identical commit objects (and therefore identical SHA1s) for any commit shared with the upstream. The attacker triggers a genuine, correctly-signed `status` event on their own repository for that shared SHA (e.g., via GitHub's Statuses API or their own CI, no Shipit secret needed since GitHub signs it with the webhook secret configured for their own repo/app installation). Shipit's `StatusHandler` receives this fully legitimate webhook and, because it queries `Commit` globally by `sha`, writes/updates a `Status` (e.g. state `success`) on the *upstream/victim* stack's identical commit as well.

### Impact Explanation
`Commit#create_status_from_github!` funnels into `add_status`, which recomputes `status`, emits `deployable_status` hooks, and calls `stack.schedule_merges` when the new status is `pending` or `success`; `Commit#schedule_continuous_delivery` (invoked on other paths keyed off the same status state) can enqueue `ContinuousDeliveryJob` when `stack.continuous_deployment?` is enabled. An attacker who controls a fork sharing history with a victim's tracked repository can therefore inject a forged "success" status onto the victim's stack for a commit that never passed the victim's real CI, potentially unblocking or triggering an unauthorized deploy — this is a payload for one repository mutating another's commit/stack, matching the Critical category ("a payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy"). The attack is fully repeatable against any pair of stacks in the same Shipit instance that share commit history (a very common real-world pattern: upstream + fork both tracked, or multiple mirrors of the same repo).

### Likelihood Explanation
Preconditions: (1) Shipit tracks at least two repositories/stacks that share commit history (e.g., upstream + a fork, common in open-source or multi-org setups); (2) the attacker administers one of those repositories (their own fork) enough to trigger a real `status` webhook — no Shipit secret, session, or API token is required, since GitHub signs the webhook using the credentials already configured for the attacker's own repository/app installation. This is low-cost and fully within the stated attacker model (owns a repository, can emit webhooks from it). It is repeatable for every shared commit SHA across the fork relationship.

### Recommendation
Scope `StatusHandler#process` to the sending repository the same way `PushHandler`/`CheckSuiteHandler` do: resolve `stacks` (or `Repository.from_github_repo_name(repository_name)`) from the payload's `repository.full_name`, and restrict the `Commit` lookup to `stacks.flat_map(&:commits).where(sha: params.sha)` (or equivalently join through `stack_id`) instead of the unscoped `Commit.where(sha: params.sha)`.

### Proof of Concept
Minitest plan (no live GitHub required):
1. Create `stack_a` for repository `owner/repo-a` and `stack_b` for repository `owner/repo-b`.
2. Create `commit_a` on `stack_a` and `commit_b` on `stack_b`, both with the identical `sha: "deadbeef..."` (simulating shared git history from a fork).
3. Build a `status` payload with `repository.full_name = "owner/repo-a"`, `sha: "deadbeef..."`, `state: "success"`.
4. Call `Shipit::Webhooks::Handlers::StatusHandler.new(payload).process`.
5. Assert `commit_a.statuses.reload.any?` (expected, legitimate) AND assert `commit_b.statuses.reload.any?` (this should be `false` if repository binding were enforced, but is `true` given current code) — proving a status was written to `stack_b`/`repo-b`'s commit purely because the SHA matched, even though the payload's `repository.full_name` referenced only `repo-a`.
6. Additionally assert that `StatusHandler.new(payload.merge('repository' => {'full_name' => 'owner/repo-a'}))` and `StatusHandler.new(payload.merge('repository' => {'full_name' => 'anything-else/unrelated'}))` produce byte-identical mutation results (both hit `commit_a` and `commit_b`), demonstrating `repository` is never consulted by `process`.
