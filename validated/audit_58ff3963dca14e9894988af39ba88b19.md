### Title
`ci/integration` status webhook mutates commits across all repositories/stacks sharing a SHA - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` resolves target commits by bare SHA with no repository or stack scoping, so a `status` webhook legitimately signed for one repository can flip the CI status of a same-SHA commit belonging to an unrelated stack. Combined with a victim stack configured `review_stacks_enabled: true` + `provisioning_behavior: allow_all`, this status flip can drive deploy/merge/block decisions on that victim stack.

### Finding Description
The broken binding: the invariant that should hold is `status.repository == commit.stack.repository` (a `ci/integration` status should only ever affect commits belonging to the repository that authenticated the webhook). Instead the code enforces only `status.sha == commit.sha`: [1](#0-0) 

`Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` performs a global lookup across the entire `commits` table, matching every `Commit` record with that SHA regardless of which `stack`/`repository` it belongs to. `create_status_from_github!` then calls `add_status`, which recomputes `status` and can trigger `stack.schedule_merges` and `Hook.emit(:deployable_status, ...)`: [2](#0-1) 

`WebhooksController#verify_signature` validates the HMAC signature using the GitHub App/organization named in the payload itself (`repository_owner`), which correctly authenticates that the request really came from GitHub for that org — but it says nothing about which `Commit` records the payload is allowed to update: [3](#0-2) 

Exploit flow:
1. Attacker forks/owns a repository (`attacker/foo`) that shares git history with a victim repository, or otherwise obtains a commit whose SHA is identical to a commit already tracked by a victim `Stack` (git SHAs are content-addressed, so this occurs naturally via forks, cherry-picks, or shared upstream commits — no hash collision needed).
2. The victim repository has `review_stacks_enabled: true` and `provisioning_behavior: allow_all`, so any externally opened PR auto-provisions a review stack via `OpenedHandler#process` → `ReviewStackAdapter#find_or_create!`, executing the repo's `shipit.yml`: [4](#0-3) 
3. GitHub legitimately delivers a `status` webhook for `attacker/foo`'s activity (`context: ci/integration`, `state: failure`) for that shared SHA. `verify_signature` succeeds because the webhook truly did come from GitHub for `attacker/foo`.
4. `StatusHandler#process` matches all `Commit` rows with that SHA — including the one in the victim's review stack — and updates each of them, independent of `stack_id`/`repository`.
5. The status flip changes `commit.deployable?`/`blocked?`/`status.state` on the victim stack, which can trigger `stack.schedule_merges`, block deploys, or otherwise alter the ship/merge state of a stack the attacker never authenticated for.

None of the existing guards prevent this: `verify_signature` authenticates the source organization of the webhook, not the set of commits it is permitted to mutate; `ExplicitParameters` only validates payload shape (`sha`, `state`, `context` types), not repository ownership; there is no `stacks`/`repository` scope applied in `StatusHandler` or in `Commit.where`.

### Impact Explanation
A payload correctly authenticated for one repository ("attacker/foo") writes `Status` records and mutates deployability state for `Commit` rows belonging to an unrelated victim `Stack`/`Repository`. This matches the "payload for one repository mutating another's stack/commit" Critical category: it can force an unauthorized deploy (by making a previously blocked commit `deployable?`) or force a block/rollback on the victim stack, and in the `review_stacks_enabled`+`allow_all` configuration, this can gate execution of that stack's `shipit.yml` deploy/build. The attack is repeatable against any repository/stack pair that ever shares a commit SHA (very common due to forking/upstream merges), so the blast radius spans any tenant with cross-repository shared history.

### Likelihood Explanation
Preconditions: attacker needs any repository under a GitHub org configured in Shipit (to receive a validly-signed webhook) and a commit SHA in common with a target stack (trivially achievable by forking a public repo tracked by Shipit, or by having a shared upstream commit). No privileged Shipit role, session, or secret is required — the attacker only needs to make GitHub deliver a normal `status` event for their own repo/commit. This is low-cost and repeatable at will.

### Recommendation
Scope `StatusHandler#process` (and analogously `Commit.where(sha:)` lookups triggered from webhooks) to the repository that authenticated the webhook, e.g. filter via `Commit.joins(:stack).where(sha: params.sha, shipit_stacks: { repository_id: repository.id })`, deriving `repository` from `params.repository.full_name` the same way `PullRequest::OpenedHandler` does, and reject/no-op when the status's repository doesn't match the commit's owning repository.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb`):
1. Create `repository_a` and `repository_b` (different `owner`/`name`).
2. Create `stack_a` on `repository_a` with `review_stacks_enabled: true`, `provisioning_behavior: allow_all`, requiring `ci/integration` in its deploy spec/required statuses.
3. Create `stack_b` on `repository_b` (attacker-controlled) unrelated to `stack_a`.
4. Create a `Commit` with the same `sha` (e.g. `"a" * 40`) on both `stack_a` and `stack_b`.
5. Assert precondition equality: `commit_a.stack.repository != commit_b.stack.repository` while `commit_a.sha == commit_b.sha`.
6. Build a `status` webhook payload with `repository.full_name = repository_b.github_repo_name`, `sha` = shared SHA, `context: "ci/integration"`, `state: "failure"`.
7. Invoke `Shipit::Webhooks::Handlers::StatusHandler.new(payload).process` (or POST through `WebhooksController` with a valid signature for `repository_b`'s org).
8. Assert that `commit_a.reload.status.state` / `commit_a.deployable?` changed (proving cross-repository mutation), even though the webhook only authenticated `repository_b`. Then assert that after applying the recommended fix, `commit_a`'s state is unchanged while `commit_b`'s state reflects the new status.

    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
