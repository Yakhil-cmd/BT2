### Title
Cross-repository commit status forgery via unscoped `Commit.where(sha:)` lookup in `StatusHandler` — ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` only proves that a webhook payload was signed with the `webhook_secret` belonging to the GitHub organization named in that same payload (`repository.owner.login` / `organization.login`). It never checks that the commit or repository the handler subsequently *acts on* actually belongs to that verified organization. `StatusHandler` breaks exactly this binding: it resolves the target `Commit` by a global, unscoped `sha` lookup across the entire Shipit installation, so a "status" webhook validly signed for organization A can write a fabricated CI status onto a commit that lives in organization B's stack.

### Finding Description
Signature verification is organization-scoped: [1](#0-0) 

```
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  ...
``` [2](#0-1) 

`repository_owner` is derived from the unverified payload itself: [3](#0-2) 

This design (documented for the "Using Multiple GitHub Applications" multi-tenant setup) means each org's `webhook_secret` only proves "this payload was sent/signed by GitHub for organization X". It says nothing about which *record* inside the payload (e.g. an arbitrary `sha`) the handler is allowed to mutate.

Other default handlers correctly re-scope the payload to the claimed repository before acting, via `Handler#stacks`, which resolves `Repository.from_github_repo_name(payload.dig('repository','full_name'))`: [4](#0-3) 
`PushHandler` uses this scoped `stacks` relation: [5](#0-4) 

`StatusHandler`, however, ignores the `repository` field entirely and looks up the target `Commit` **globally by `sha`**, with no scoping to any stack/repository/organization: [6](#0-5) 

This breaks the required equality: *organization that authenticated the webhook* == *repository/stack whose data is written*. The verified secret only proves "org A sent this", but the write (`commit.create_status_from_github!`) touches whatever stack happens to contain a commit with the given SHA — regardless of which organization or repository that stack belongs to.

`create_status_from_github!` persists the forged state directly onto the commit's status list: [7](#0-6) 

And `deployable?` — the gate used to decide whether a commit can be shipped — depends directly on that status: [8](#0-7) 

### Impact Explanation
In a multi-organization Shipit installation (explicitly supported per `docs/setup.md`'s "Using Multiple Github Applications" section, each org with its own `webhook_secret`), an attacker who legitimately controls a GitHub organization/App installation on the Shipit instance — and therefore can produce validly HMAC-signed webhooks for *their own* org — can forge a `status` event whose `sha` matches a commit belonging to a **different** organization's stack (git SHAs are public/guessable via the target repo's own commit history, PRs, or CI logs). The forged event will pass `verify_signature` (it's genuinely signed by the attacker's own org secret) and `StatusHandler` will then flip that unrelated commit's CI status to `success`, making an otherwise CI-unverified/malicious commit `deployable?` in the victim stack, enabling an unauthorized deploy. This matches the Critical-impact class of "an unauthorized deploy" via a cross-organization write that the signature scheme was supposed to prevent.

### Likelihood Explanation
Requires only that the attacker legitimately owns one GitHub App installation/org on the shared Shipit instance (a normal, unprivileged setup covered by the multi-org configuration feature) and knows a target commit SHA of another tracked repository (public information for public repos, or discoverable via PR metadata for private ones). No Shipit session, `ApiClient` token, or GitHub write access to the victim repository is needed — only the ability to send an HTTP POST with a signature computed from a secret the attacker already legitimately possesses.

### Recommendation
Scope `StatusHandler` (and any other handler that performs lookups by attacker-supplied identifiers such as `sha`) to the repository/stacks derived from the payload's own `repository.full_name`, consistent with `Handler#stacks`, e.g.:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }
  end
end
```
More generally, `verify_signature` should establish a single verified repository/organization identity that every handler is required to use for scoping — no handler should be allowed to resolve records by attacker-controlled fields (`sha`, IDs, etc.) without intersecting them with the repository that was cryptographically verified for that request.

### Proof of Concept
1. Attacker legitimately installs a Shipit-tracked GitHub App/org "attacker-org" (own `webhook_secret` known to them) — a supported multi-org configuration per `docs/setup.md`.
2. Attacker learns the SHA of an undeployed/failing commit `deadbeef...` on `victim-org/victim-repo`, a stack tracked by the same Shipit instance under a different organization.
3. Attacker crafts a GitHub `status` webhook payload:
```json
{
  "sha": "deadbeef...",
  "state": "success",
  "context": "ci/whatever",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "attacker-org/some-repo" }
}
```
4. Attacker signs the raw body with `attacker-org`'s known `webhook_secret` (`X-Hub-Signature: sha1=...`) and POSTs it to `/github/webhooks`.
5. `WebhooksController#verify_signature` resolves `Shipit.github(organization: 'attacker-org')` and successfully verifies the signature.
6. `StatusHandler#process` executes `Commit.where(sha: 'deadbeef...')` — finding the commit in `victim-org/victim-repo`'s stack — and calls `create_status_from_github!`, marking it `success` there, even though the request has nothing to do with that repository or organization.
7. The victim's now-"successful" commit becomes `deployable?` and can be shipped through Shipit's normal deploy flow.
