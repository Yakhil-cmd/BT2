Confirmed: `here_come_the_walrus` fixture proves `ApiClient` can be legitimately scoped to a specific stack via `stack: shipit` [1](#0-0) , and `BaseController#stacks`/`#stack` correctly enforces that binding by filtering `Stack.where(id: current_api_client.stack_id)` before resolving `params[:stack_id]` [2](#0-1) . `CCMenuController`, however, overrides `#stack` to call `Stack.from_param!(params[:stack_id])` directly, completely bypassing the `current_api_client.stack_id` scoping check [3](#0-2) .

### Title
Stack-scoped ApiClient tokens are not bound to their stack in `CCMenuController#show` - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`CCMenuController` overrides `#authenticate_api_client` to accept `ApiClient.authenticate(params[:token])` from the query string [4](#0-3) , and overrides `#stack` to resolve `params[:stack_id]` via `Stack.from_param!` directly instead of via the inherited stack-scoped `#stacks` method [5](#0-4) . `require_permission :read, :stack` only checks the `read:stack` operation:scope string, never the specific `stack_id` the token is bound to [6](#0-5) . As a result, a token created for (or scoped to) stack A can be replayed with an arbitrary `stack_id` query param for stack B and `show` will render stack B's CI/deploy-state XML.

### Finding Description
Binding claimed: `current_api_client.stack_id == params[:stack_id]` (resolved stack).

Trace:
- `ApiClient` can be legitimately scoped to one stack, e.g. fixture `here_come_the_walrus` has `stack: shipit`, `permissions: ['read:stack']` [1](#0-0) . `ApiClient` model has `belongs_to :stack, optional: true` [7](#0-6) .
- The generic, safe path in `BaseController` enforces the binding: `stacks` returns `Stack.where(id: current_api_client.stack_id)` when `stack_id` is set, and `stack` resolves `params[:stack_id]` only within that pre-filtered scope [2](#0-1) . Under this path, a stack-A-scoped token requesting `stack_id: B` would 404 because `stacks.from_param!` can't find stack B in a relation restricted to stack A's id.
- `CCMenuController` breaks this: it overrides `#stack` to call `Stack.from_param!(params[:stack_id])` directly on the unrestricted `Stack` model, never consulting `current_api_client.stack_id` at all [5](#0-4) .
- `require_permission :read, :stack` (class-level declaration) only invokes `current_api_client.check_permissions!(:read, :stack)`, which is a pure string-membership check against `permissions`, independent of which stack the request targets [6](#0-5) [8](#0-7) .
- `authenticate_api_client` is fully overridden to accept `params[:token]` with no additional checks [4](#0-3) .

Attacker's exact request: `GET /api/stacks/OWNER_B/REPO_B/ENV_B/cc.xml?token=<stack-A-scoped-token>&stack_id=OWNER_B/REPO_B/ENV_B` (or the equivalent route param), i.e. take a valid `here_come_the_walrus`-style token issued/leaked for stack A and swap `stack_id` to stack B. Because `#stack` never checks `current_api_client.stack_id`, `show` renders stack B's `deploys_and_rollbacks.last` build status/name via the `shipit/ccmenu/project.xml` view [9](#0-8) .

Existing guards fail to prevent this because: (1) `check_permissions!` is scope/operation-only, not stack-specific by design and by code; (2) `authenticate_api_client` in this controller does no stack binding; (3) `#stack` is overridden precisely in a way that discards the inherited, stack-scoping implementation that other Api controllers (e.g. `StacksController#stack` uses `stacks.from_param!`) rely on [10](#0-9) .

Additionally, the token minted by `CCMenuUrlController#client` doesn't even set `stack_id` on the `ApiClient` it creates — `find_or_create_by!(creator: current_user, name: 'CCMenu Client')` scopes only by creator+name, never by stack [11](#0-10) , so tokens minted through that specific UI flow are global `read:stack` tokens for that user across all stacks, by apparent design. But the vulnerability is broader and controller-level: even a properly stack-scoped `ApiClient` (as the `here_come_the_walrus` fixture demonstrates is a supported configuration) is not respected by `CCMenuController`, so any leaked/replayed ccmenu token — scoped or not — can read any stack's build state.

### Impact Explanation
Unauthenticated (from the target stack's perspective) read of another stack's deploy/build state: `stack.deploys_and_rollbacks.last` (build success/failure, running status, build label/time, web URL) is exposed via the CCMenu XML feed for any stack reachable by `Stack.from_param!`, to any holder of any valid `read:stack` ccmenu-style token, regardless of the stack that token was intended for. This matches "High - unauthenticated read of stack state" since a token scoped to stack A can read stack B's deploy state, an authorization escalation across stack boundaries. Repeatable for every stack in the installation as long as the attacker holds one valid token.

### Likelihood Explanation
Preconditions: attacker must possess one valid ccmenu-style token (obtained via URL leakage, referrer logs, etc., as described in the question — this token possession itself is out of scope to fabricate but assumed given per the question's threat model). Given that, exploitation costs nothing beyond changing the `stack_id`/path in the URL; no additional secrets, sessions, or GitHub credentials required. Fully repeatable against every stack in the instance.

### Recommendation
In `Api::CCMenuController`, restore the inherited stack-scoping behavior instead of overriding `#stack` with an unscoped `Stack.from_param!` call — use `stacks.from_param!(params[:stack_id])` (i.e. rely on `BaseController#stacks`, which filters by `current_api_client.stack_id` when present) so a stack-scoped token cannot resolve a different stack. Additionally, ensure `CCMenuUrlController#client` binds the created `ApiClient` to the specific `stack`, not merely `creator`+`name`, so each minted ccmenu token is inherently scoped to one stack.

### Proof of Concept
```ruby
# test/controllers/api/ccmenu_controller_test.rb
test "a stack-scoped token cannot read a different stack via query-string replay" do
  stack_a = shipit_stacks(:shipit)
  stack_b = Stack.create!(repository: Repository.create!(owner: 'other', name: 'repo'), environment: 'production', branch: 'main')

  scoped_client = ApiClient.create!(
    creator: shipit_users(:walrus), name: 'Scoped CCMenu', stack: stack_a, permissions: ['read:stack']
  )

  # sanity: token works for its own stack
  get :show, params: { stack_id: stack_a.to_param, token: scoped_client.authentication_token }
  assert_response :ok

  # exploit: same token, different stack_id
  get :show, params: { stack_id: stack_b.to_param, token: scoped_client.authentication_token }
  assert_response :forbidden # or :not_found -- currently renders :ok with stack_b's data
end
```
Assert the equality `current_api_client.stack_id == resolved_stack.id` holds after the request; currently it does not, because `CCMenuController#stack` never checks `current_api_client.stack_id` [5](#0-4) , unlike `BaseController#stack`/`#stacks` [2](#0-1) .
