This confirms the binding break. `WebhooksController#verify_signature` selects the HMAC secret using `repository_owner`, derived from `params.dig('repository', 'owner', 'login')` (falling back to `params.dig('organization', 'login')`), and validates the signature against the **entire raw body** using that org's `webhook_secret`. But `Shipit::Webhooks::Handlers::Handler#repository_name` (used by every handler, e.g. `PushHandler`, `StatusHandler`) resolves the target `Repository`/`Stack` via `payload.dig('repository', 'full_name')` — a *different* field in the same payload.

Because both fields live inside the same signed body, an attacker who legitimately controls a GitHub App/org configured in Shipit (i.e., who knows a valid `webhook_secret` for *their own* org in `Shipit.github(organization: ...)`) can produce a validly-signed payload where `repository.owner.login` names their own org (so `verify_signature` picks the secret they know and passes) while `repository.full_name` names a **victim** repository belonging to a different org/stack entirely. Since Shipit is explicitly designed as multi-tenant (`config/secrets.development.shopify.yml` shows multiple orgs each with their own `webhook_secret`), this cross-tenant mismatch is directly reachable. ### Title
Cross-organization webhook forgery via mismatched signature-organization/repository binding - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` verifies the HMAC signature of an inbound GitHub webhook using the `webhook_secret` of the organization named in `repository.owner.login` (or `organization.login`), but the actual repository/stack acted upon by handlers is resolved independently from `repository.full_name`. These two payload fields are never cross-checked against each other, even though both are covered by the same HMAC.

### Finding Description
`verify_signature` in `app/controllers/shipit/webhooks_controller.rb` computes `repository_owner` from the payload and fetches `Shipit.github(organization: repository_owner)` to obtain that org's `webhook_secret`, then validates `X-Hub-Signature` against the raw body [5](#0-4) . Once verification passes, `create` dispatches the parsed payload to `Shipit::Webhooks.for_event(event)` handlers [6](#0-5) .

Every handler inherits `repository_name` from `Handler`, which reads `payload.dig('repository', 'full_name')` — a field distinct from `repository.owner.login` used for signature routing — to look up the target `Repository`/`Stack` [2](#0-1) . Nothing enforces that `repository.full_name`'s owner matches the `repository.owner.login`/`organization.login` value that selected the verifying secret.

Shipit is built to host multiple independent GitHub organizations, each with its own `webhook_secret` [4](#0-3) . Any party who administers a Shipit-configured org (i.e., knows that org's `webhook_secret`, which they set up themselves in GitHub App settings) can compute a valid `X-Hub-Signature` for an arbitrary JSON body. By setting `repository.owner.login` to their own org (satisfying signature verification) while setting `repository.full_name` to a victim org/repo string, they cause handlers such as `PushHandler` to operate on the victim's `Stack` — e.g. triggering `stack.sync_github(expected_head_sha: params.after)` [7](#0-6)  or injecting a forged commit status via `StatusHandler#process` on any `Commit` matching an attacker-chosen `sha` [8](#0-7) , none of which belong to the attacker's own org.

This is the same class of bug as the referenced Substrate fix: a hook/binding is exercised using state (the "owner" used to select the trust anchor) that diverges from the state the operation actually mutates (the "full_name" that is written), because the two are never reconciled before the privileged action runs.

### Impact Explanation
This allows an attacker who legitimately controls one Shipit-configured GitHub organization to trigger unauthorized deploy-pipeline actions against a *different* organization's stacks — including forcing sync jobs against arbitrary commits/branches and injecting fabricated commit statuses that Shipit's deploy gating (checks/statuses) relies on. This is a cross-repository/cross-tenant write achieved without any credentials belonging to the victim organization, matching the "cross-repository writes" / "unauthorized deploy" impact bar.

### Likelihood Explanation
Exploitability requires only that the attacker administer any one organization onboarded to the same multi-tenant Shipit instance (a legitimate, unprivileged relationship relative to the victim org) and know that org's own `webhook_secret`, something they configure themselves. No access to the victim's secrets, session, or `ApiClient` tokens is needed, making this practically reachable in any deployment hosting multiple tenants.

### Recommendation
In `verify_signature`, or immediately in `create`, enforce that the organization portion of `repository.full_name` (and any other repository identifiers handlers rely on, such as `organization.login`) matches the `repository_owner` used to select the verifying `webhook_secret`, rejecting the request otherwise. Alternatively, have `Handler#repository_name` cross-validate against the verified organization context rather than trusting an independent field in the same unauthenticated-until-verified body.

### Proof of Concept
1. Configure Shipit with two orgs, `attacker-org` and `victim-org`, each with distinct `webhook_secret`s (multi-tenant setup as in `config/secrets.development.shopify.yml`).
2. As the administrator of `attacker-org`, craft a `push` event JSON body: `{"ref": "refs/heads/master", "after": "<attacker-chosen sha>", "repository": {"owner": {"login": "attacker-org"}, "full_name": "victim-org/victim-repo"}}`.
3. Compute `X-Hub-Signature: sha1=<hmac>` using `attacker-org`'s known `webhook_secret` over this exact body.
4. POST to `/webhooks` with header `X-Github-Event: push`. `verify_signature` resolves `repository_owner` = `attacker-org`, fetches `attacker-org`'s secret, and the signature validates successfully.
5. `PushHandler#process` resolves the target stack via `payload.dig('repository', 'full_name')` = `victim-org/victim-repo`, and calls `stack.sync_github(expected_head_sha: params.after)` on the victim's stack — an action the attacker has no legitimate authorization to trigger.
