### Title
Cross-Stack CI-Status Read via CCMenu API Bypasses Per-Stack `ApiClient` Scoping - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::Api::CCMenuController` overrides the `stack` resolver inherited from `Shipit::Api::BaseController` and, in doing so, drops the scoping that restricts a stack-bound `ApiClient` token to only the stack it was issued for. Any token that authorizes `read:stack` can be replayed with a different `stack_id` to read the build/deploy status of stacks it was never authorized for.

### Finding Description
`Shipit::Api::BaseController` enforces the binding "the stack a token authorizes == the stack a request touches" through two cooperating methods: [1](#0-0) 

`stacks` restricts the queryable set to `Stack.where(id: current_api_client.stack_id)` when the authenticated `ApiClient` is scoped to a stack, and `stack` resolves `params[:stack_id]` only within that restricted set.

`Shipit::Api::CCMenuController` inherits `require_permission :read, :stack` but redefines `stack` to bypass this scoping entirely and defines its own `authenticate_api_client`: [2](#0-1) 

Here `stack` resolves directly via `Stack.from_param!(params[:stack_id])` against the entire `Stack` table, ignoring `current_api_client.stack_id`. `require_permission!` only calls `current_api_client.check_permissions!(operation, scope)`: [3](#0-2) 

which checks that `"read:stack"` is present in the client's `permissions` array, but never checks `stack_id` — that check only happens inside the (bypassed) `stacks` method. `ApiClient.authenticate` merely verifies the signed token maps to a persisted `ApiClient` row; it carries no per-request stack constraint of its own: [4](#0-3) 

Tokens scoped to a single stack are a supported, intended feature — e.g. `CCMenuUrlController` mints a `read:stack` client and embeds its token in a CCMenu URL meant to expose only one stack's build status: [5](#0-4) 

and the fixture `here_come_the_walrus` demonstrates a client explicitly scoped to a single stack (`shipit`) with `read:stack` permission: [6](#0-5) 

The stacks controller test even confirms the intended behaviour that such a scoped client "will only see that one stack" when going through the properly-scoped `stacks`-based endpoints: [7](#0-6) 

However, because `CCMenuController#stack` does not use `stacks.from_param!`, presenting that same token with a different `stack_id` value at the CCMenu endpoint (`GET /api/stacks/:stack_id/ccmenu.xml`, mounted via `config/routes.rb`) resolves and renders CI/deploy status for an arbitrary stack outside the token's authorized scope — including stacks belonging to different repositories/environments the client's issuing user may not even have permission to view directly.

### Impact Explanation
This breaks the "stack a token authorizes vs. stack it touches" binding: an `ApiClient` deliberately scoped by an administrator to a single stack (the security boundary the feature exists to enforce) can be used to read build status (`lastBuildStatus`, `lastBuildLabel`, `activity`, `webUrl`) of any other stack in the Shipit instance, including private/internal deployment pipelines the token holder has no legitimate access to. This is an unauthorized read of stack state via a token whose authorization scope is explicitly limited — matching the specified High-impact category "unauthenticated/under-authorized read of stack state, task streams or deploy output."

### Likelihood Explanation
Likelihood is high given normal usage patterns: CCMenu URLs (containing the token in the query string) are designed to be embedded in build-monitor widgets and are often shared more broadly than the underlying Shipit UI credentials (e.g., posted in dashboards, CI radiators, or bookmarked). Any holder of such a URL/token can trivially enumerate other `stack_id` values (which are simply `owner/repo/environment` triples, discoverable or guessable) and swap them into the `stack_id` path parameter to read unrelated stacks' state — no additional exploitation complexity is required.

### Recommendation
Make `CCMenuController#stack` resolve through the same scoping helper as the rest of the API (`stacks.from_param!(params[:stack_id])`) instead of `Stack.from_param!`, so that a stack-scoped `ApiClient` cannot read status for stacks outside its `stack_id`.

### Proof of Concept
1. As an administrator, create/observe a stack-scoped API client, e.g. fixture-equivalent: `ApiClient.create!(creator: user, name: 'CCMenu', permissions: ['read:stack'], stack: stack_a)`.
2. Obtain its `authentication_token` (as would be embedded in the CCMenu URL generated by `Shipit::CCMenuUrlController#fetch`).
3. Issue: `GET /api/stacks/other_owner/other_repo/production/ccmenu.xml?token=<token>` where `other_owner/other_repo/production` is a *different* stack than `stack_a`.
4. Because `CCMenuController#stack` calls `Stack.from_param!` (unscoped) rather than `stacks.from_param!`, the request succeeds (HTTP 200) and returns the CI/deploy status XML for `other_owner/other_repo/production`, even though the token is only supposed to authorize reads of `stack_a`.
