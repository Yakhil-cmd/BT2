### Title
Crafted private-payment chain can trigger an uncaught `throw Error` in transfer-input validation, crashing the whole node - ([File: validation.js])

### Summary
`validation.js`'s payment-input validator contains several `throw Error(...)` statements (instead of soft `callback(err)` returns) in the branch that validates `transfer` inputs of **private, fixed-denomination assets**. This branch trusts that `objValidationState.src_coin` has already been correctly populated with `src_output`, `denomination` and `amount` by the private-payment chain processing code before validation is invoked [1](#0-0) . Because a private payment chain is supplied by an untrusted payment counterparty and is validated by feeding it into the same `validation.validate()` pipeline used for normal units [2](#0-1) , any gap between what the private-payment/indivisible-asset preparation code guarantees and what this code assumes lets a malicious counterparty produce a chain that reaches this code with a missing/malformed `src_coin`. Since these guards are implemented as `throw Error(...)` rather than a handled validation error, the exception is not caught anywhere in the async call chain and propagates as an `uncaughtException`, which the node deliberately re-throws to crash the whole process [3](#0-2) .

### Finding Description
This mirrors the FFmpeg CVE-2020-23906 bug class: a parser/validator trusts internally-produced metadata without robustly re-verifying it against attacker-supplied (crafted) input, so malformed input reaches an unchecked assumption and blows up the whole process rather than being rejected gracefully.

In ocore, private-payment chains for indivisible (fixed-denomination) private assets are received directly from a payment counterparty and validated via `validateAndSavePrivatePaymentChain()` → `indivisibleAsset.validateAndSavePrivatePaymentChain()`, which eventually calls into `validation.validate()`/`validatePaymentInputsAndOutputs()` for the private unit chain [4](#0-3) . Inside `validatePaymentInputsAndOutputs`, when handling a `transfer` input of a private, fixed-denomination asset, the code bypasses the normal DB-backed `SELECT ... FROM units ...` lookup (since the source output can't be found in the DB for a chain being validated before being saved) and instead relies entirely on `objValidationState.src_coin`, which must be pre-populated by the caller:

```
if (objAsset && objAsset.is_private && objAsset.fixed_denominations){
    if (!objValidationState.src_coin)
        throw Error("no src_coin");
    var src_coin = objValidationState.src_coin;
    if (!src_coin.src_output)
        throw Error("no src_output");
    if (!isPositiveInteger(src_coin.denomination))
        throw Error("no denomination in src coin");
    if (!isPositiveInteger(src_coin.amount))
        throw Error("no src coin amount");
    ...
``` [1](#0-0) 

Unlike virtually every other validation failure in this file, which is surfaced through `return callback("...")` (a normal, recoverable validation error), these four checks use `throw Error(...)`. A `throw` inside a callback executed asynchronously (deep inside nested `conn.query()`/`async.series()` callbacks) is not caught by any enclosing `try/catch`, and ultimately surfaces as a Node.js `uncaughtException`. The node's own handler for that event explicitly re-throws to terminate the process:

```
process.on('uncaughtException', (err) => {
    ...
    throw err; // crash the process to avoid ending up in an inconsistent state
});
``` [3](#0-2) 

The trust boundary being crossed is: `src_coin` is supposed to be derived and verified by the indivisible-asset private-chain builder code (`indivisible_asset.js`, which references `src_coin` while assembling the validation state) from data supplied in the private payment chain by the sending counterparty. If a crafted chain (e.g., missing `output` field, mismatched `output_index`, altered denomination/amount ordering, or any other divergence not fully cross-checked before `objValidationState.src_coin` is set) causes that pre-population step to leave `src_coin`, `src_output`, `denomination`, or `amount` unset/invalid, the receiving wallet's validation reaches this branch and throws — crashing the whole node, not just failing the single payment.

### Impact Explanation
This is a full-node denial of service: any user/wallet that receives a maliciously crafted private payment (offer) for a private, fixed-denomination (indivisible) asset can crash the entire recipient process via an unhandled exception, which the process explicitly converts into a hard crash. This affects all pending network activity, not just the one payment, matching the "network unable to confirm new units" / general availability-loss impact class requested. It is reachable by an unprivileged private-payment counterparty, one of the explicitly in-scope attacker roles.

### Likelihood Explanation
Likelihood is Medium: it requires attacker control over the internal composition of a private-payment chain for indivisible private assets so that the caller's pre-population of `src_coin`/`src_output`/`denomination`/`amount` is skipped or made invalid, a narrower surface than plain unit posting but still directly reachable by any wallet accepting private-asset payments from any counterparty without further privilege. Exact exploitability depends on gaps in `indivisible_asset.js`'s chain-building/validation code (not fully inspectable within the available index) between accepting the untrusted chain and calling into `validatePaymentInputsAndOutputs`.

### Recommendation
- Replace the `throw Error(...)` guards for `src_coin`/`src_output`/`denomination`/`amount` in `validation.js` (lines 2415-2424) with normal `return callback("...")` validation errors so malformed private-payment chains are rejected gracefully instead of crashing the process.
- Audit `indivisible_asset.js`'s private-chain processing to ensure `objValidationState.src_coin` is always fully and correctly derived/verified from the chain data before this code is reached, and add defensive checks so that any inconsistency is surfaced as a normal validation failure.
- More generally, review the codebase for other `throw Error(...)` statements inside externally-triggerable async validation paths (units, private payments, AA triggers) and convert genuinely input-dependent conditions to soft errors, reserving `throw` only for provably-internal invariants.

### Proof of Concept
Not independently reproducible from the indexed code alone: exploitation requires crafting a private-payment chain for an indivisible/fixed-denomination private asset such that `indivisible_asset.js`'s pre-population of `objValidationState.src_coin` (invoked from `private_payment.js:validateAndSavePrivatePaymentChain` → `indivisibleAsset.validateAndSavePrivatePaymentChain`) leaves `src_coin`, `src_output`, `denomination`, or `amount` missing/invalid (e.g., by omitting the revealed `output` object or desynchronizing `output_index`/denomination fields in the chain sent to the recipient wallet). When such a chain reaches `validatePaymentInputsAndOutputs`'s `transfer` branch for that asset, one of the `throw Error(...)` statements at `validation.js:2416-2424` fires, is not caught anywhere in the async chain, and is converted by `network.js`'s `uncaughtException` handler into a full process crash.
