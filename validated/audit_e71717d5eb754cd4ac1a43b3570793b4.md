### Title
Stack-scoped API client token authorizes read access to any stack via `Api::CCMenuController` - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
The bug class in the external report is a binding break where an action is *authorized* for one scope (funds at time of unstake request) but *executed* against a different, unverified state (stake ratio at fulfillment). The equivalent binding in this engine is: "a stack a token authorises versus a stack it touches." `Shipit::CCMenuUrlController#fetch` mints an `ApiClient` scoped to a specific `stack_id` with `read:stack` permission, but `Shipit::Api::CCMenuController` never checks that scope when resolving which stack to render, allowing the token to read deploy/build status of any stack.

### Finding Description
`CCMenuUrlController#fetch` creates (or reuses) an `ApiClient` bound to a specific stack: [1](#0-0) 

That token is later consumed by `Shipit::Api::CCMenuController`, which authenticates it via the `token` query param rather than the standard `Basic` auth used elsewhere: [2](#0-1) 

Crucially, the `stack` method used to render the response resolves directly from the request's `stack_id` parameter, bypassing the client's stack scope entirely: [3](#0-2) 

Compare this to the base API controller, where `stack` is deliberately scoped through `stacks`, which filters by `current_api_client.stack_id` when the client is stack-scoped: [4](#0-3) 

The `require_permission :read, :stack` before_action only checks that the string `"read:stack"` is present in `ApiClient#permissions`; it never checks `stack_id`: [5](#0-4) [6](#0-5) 

So the equality that should hold — `token.stack_id == stack_being_rendered.id` — is never enforced in `CCMenuController#show`. An attacker who obtains (or is issued) a legitimate CCMenu token scoped to stack A can substitute any other `stack_id` in the URL to read stack B's deploy state.

### Impact Explanation
This grants unauthenticated (from the target stack's perspective) read access to task/deploy status output for stacks the token was never authorized for: [7](#0-6) 

The XML response leaks `lastBuildStatus`, `activity` (building/sleeping), `lastBuildLabel` (deploy id), and `webUrl` for the arbitrary target stack — this matches the in-scope High-impact category "unauthenticated read of stack state, task streams or deploy output" reachable via a credential whose authorization was meant to be scoped to a single stack.

### Likelihood Explanation
Any holder of a valid `read:stack`-permissioned CCMenu token (a routine, low-privilege artifact meant only for CI dashboard integration, generated automatically for any user visiting stack settings) can trivially change the `stack_id` route segment to target a different stack; no additional secret or race condition is required, unlike the original report's mempool-timing dependency.

### Recommendation
In `Shipit::Api::CCMenuController`, resolve `stack` through the scoped `stacks` collection (as `BaseController#stack` does) instead of `Stack.from_param!(params[:stack_id])` directly, so a stack-scoped `ApiClient#stack_id` is enforced against the requested `stack_id`.

### Proof of Concept
1. As an authenticated Shipit user, visit stack A's settings page, which triggers `CCMenuUrlController#fetch` and creates/returns an `ApiClient` with `permissions: ['read:stack']` and `stack_id: A.id`, plus its `authentication_token`. [8](#0-7) 
2. Take the returned `token` and issue `GET /api/<stack_B_owner>/<stack_B_repo>/<stack_B_env>/ccmenu.xml?token=<token>` (routes wired similarly to `stacks/:stack_id/ccmenu`).
3. `authenticate_api_client` accepts the token (it is a valid signature for a real `ApiClient` row) via `ApiClient.authenticate(params[:token])`. [2](#0-1) 
4. `require_permission :read, :stack` passes because the client has `read:stack` in its permission list, regardless of which stack is in the URL.
5. `stack` resolves `Stack.from_param!(params[:stack_id])` for stack B, and `show` renders stack B's deploy/build status even though the token was scoped only to stack A. [9](#0-8)
