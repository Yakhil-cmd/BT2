Confirmed: `Repository.from_github_repo_name` at [1](#0-0)  looks up the Stack purely by `repository.full_name` from the payload, entirely independent of the `repository.owner.login` field used for signature verification.

### Title
Cross-organization webhook forgery: `repository.owner.login` used for signature verification is decoupled from `repository.full_name` used to select the target Stack - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/push_handler.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/org config (and thus which `webhook_secret`) to check against using `repository_owner`, which is read from the same untrusted, unsigned-at-that-point JSON body (`params.dig('repository','owner','login')`). `PushHandler#process` (via `Handler#stacks`/`#repository_name`) instead resolves the target Stack from a completely different field in the same body, `repository.full_name`. If any organization configured in Shipit has no `webhook_secret` set, `GitHubApp#verify_webhook_signature` returns `true` unconditionally for that org, letting an attacker "verify" the request against that org while asserting an arbitrary `repository.full_name` belonging to a different (victim) organization.

### Finding Description
Broken binding: `organization used to verify signature (params.dig('repository','owner','login'))` == `organization owning the stack whose sync_github is invoked (owner parsed from params.dig('repository','full_name'))`. These are independent, attacker-controlled strings inside the same JSON body, and nothing enforces they refer to the same repository.

Path:
1. `WebhooksController#verify_signature` computes `repository_owner` from `params.dig('repository','owner','login')` (fallback `organization.login`) and calls `Shipit.github(organization: repository_owner)`, then `github_app.verify_webhook_signature(signature, raw_post)`.
2. `GitHubApp#verify_webhook_signature` returns `true` immediately `unless webhook_secret` — i.e., if the org resolved above has no configured secret, any body/signature pair passes, per [2](#0-1) .
3. On success, `WebhooksController#create` parses the full raw body and dispatches it, unmodified, to handlers: [3](#0-2) .
4. `PushHandler#process` resolves stacks via `Handler#stacks`, which calls `Repository.from_github_repo_name(repository_name)` where `repository_name = payload.dig('repository','full_name')`, at [4](#0-3)  and [5](#0-4) .
5. `Repository.from_github_repo_name` splits `full_name` on `/` and does a plain DB lookup with no relation at all to `repository.owner.login`: [1](#0-0) .

Attacker request: POST `/webhooks` with header `X-Github-Event: push`, body:
```json
{
  "repository": {"owner": {"login": "attacker-org"}, "full_name": "victim/repo"},
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>"
}
```
where `attacker-org` is some organization configured in Shipit's `github:` multi-org section without a `webhook_secret` (a supported, documented configuration — every example config in `docs/setup.md` and `config/secrets.*.yml` ships with `webhook_secret: # nil`). No valid `X-Hub-Signature` for `victim`'s secret is required, and the `X-Hub-Signature` header can even contain a bogus/absent value since it's never checked once `webhook_secret` is `nil`.

Existing guards do not catch this:
- `drop_unhandled_event` only checks the event type is handled, not repo ownership.
- `verify_signature` only checks the org derived from the same attacker payload; there's no cross-check that `full_name`'s owner equals `repository.owner.login`.
- `ExplicitParameters` schema for `PushHandler` (`requires :ref`, `requires :after`) does not validate `repository.full_name` against anything.
- `Repository` model validations only constrain the shape of `owner`/`name` strings, not their relationship to the verifying organization.

### Impact Explanation
An unprivileged attacker who merely knows that some organization configured on the target Shipit instance has no `webhook_secret` (a common state per the shipped example configs) can force `stacks.not_archived.where(branch: 'master').find_each { |stack| stack.sync_github(expected_head_sha: params.after) }` to run against a victim organization's real `Stack`, at [6](#0-5) , enqueuing `GithubSyncJob` with `expected_head_sha` fully attacker-controlled — for any repository/stack trackable by that Shipit instance, not just ones belonging to `attacker-org`. This is a genuine cross-tenant authentication-bypass: signature verification for one organization is used to authorize state changes to a different organization's Stack. This matches the Critical category ("a payload for one repository mutating another's stack").

### Likelihood Explanation
Requires only that at least one organization configured in the Shipit instance's `github:` section has no `webhook_secret` set — which is the default/example state shown in every shipped config template (`docs/setup.md`, `config/secrets.*.yml`, `secrets_double_github_app.yml`). No GitHub App private key, `secret_key_base`, session, or API token is needed. The attacker cost is a single crafted HTTP POST; the attack is trivially repeatable against arbitrary repositories/stacks tracked by the instance, limited only by knowing (or guessing) one org name without a secret and the victim's `owner/name`.

### Recommendation
Bind the verifying organization to the repository actually referenced by the payload: derive `repository_owner` and enforce that `payload.dig('repository','full_name')` starts with `"#{repository_owner}/"` before dispatching to handlers, or better, resolve the target `Repository`/`Stack` first and verify the signature using that repository's own configured GitHub App/secret rather than an attacker-suppliable field. Additionally, treat a missing `webhook_secret` as "reject all webhooks for that org" (or require operators to always configure one) rather than "always verified."

### Proof of Concept
minitest under `test/controllers/webhooks_controller_test.rb`:
```ruby
test ":push from an org without a webhook_secret can target a stack in a different org" do
  # Ensure 'attacker-org' is configured with no webhook_secret while victim's Stack lives under a different owner
  victim_stack = shipit_stacks(:shipit) # belongs to repository owner e.g. "shopify"
  request.headers['X-Github-Event'] = 'push'

  forged_payload = {
    'repository' => { 'owner' => { 'login' => 'attacker-org' }, 'full_name' => victim_stack.repository.full_name },
    'ref' => 'refs/heads/master',
    'after' => 'deadbeefdeadbeefdeadbeefdeadbeefdeadbeef'
  }.to_json

  # No X-Hub-Signature needed/valid for attacker-org since it has no webhook_secret configured
  assert_enqueued_with(
    job: GithubSyncJob,
    args: [stack_id: victim_stack.id, expected_head_sha: 'deadbeefdeadbeefdeadbeefdeadbeefdeadbeef']
  ) do
    post :create, body: forged_payload, as: :json
  end
end
```
This asserts `GithubSyncJob` is enqueued for `victim_stack.id` (owned by an organization other than `attacker-org`) with the attacker-chosen `expected_head_sha`, demonstrating the cross-org binding failure.
