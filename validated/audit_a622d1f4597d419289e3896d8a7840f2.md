This matches a real, unmitigated session-fixation gap.### Title
Session fixation on GitHub OAuth login binds `session[:user_id]` to a pre-existing, attacker-controlled session id - ([File: app/controllers/shipit/github_authentication_controller.rb])

### Summary
`GithubAuthenticationController#callback` writes `session[:user_id] = sign_in_github(auth)` into whatever session already exists on the request, without ever rotating the session id (`reset_session`) before or after establishing the authenticated identity. `reset_session` is only called from `logout` and from `force_github_authentication`'s "stale login" branch, never on a fresh successful OAuth callback, so an attacker who pre-plants a session cookie in a victim's browser can have that same session promoted to an authenticated session once the victim completes the real GitHub OAuth flow.

### Finding Description
The broken binding: `session[:user_id] after callback == id of the User row for the GitHub identity the victim authenticated as, AND the session identifier itself must be one the victim's browser generated, not one an attacker chose`. In the actual code: [1](#0-0) 

`callback` only checks that `request.env['omniauth.auth']` is present (line 11) and then sets `session[:user_id]` (line 13) and `session[:authenticated] = true` (line 18) on the *current* session object — the one tied to whatever `rack.session` cookie was sent with the request. No `reset_session` call exists anywhere in this method, and `logout` is the only other place that calls it: [2](#0-1) 

Because the route accepts the callback on both `GET` and `POST` (`config/routes.rb`, lines 70-75), and the controller extends bare `ActionController::Base` with no CSRF protection or session-id rotation hook, an attacker can:
1. Cause a victim to visit the Shipit host first (any page) and note/force a session cookie value, or use a known session-fixation delivery mechanism to plant a session cookie for the victim's browser prior to authentication.
2. Wait for (or induce) the victim to click "Log in with GitHub" and complete the real OAuth exchange with GitHub — the attacker does not need to control or forge this exchange.
3. When the OmniAuth middleware completes and hands control to `callback`, `session[:user_id]` is written into the *same* session record the attacker seeded, because nothing regenerates the session id at this point.
4. The attacker, already holding that session id/cookie, is now authenticated as the victim for the lifetime of that session (`current_user` resolves via `session[:user_id]` in `find_current_user`): [3](#0-2) 

Existing guards do not prevent this: `force_github_authentication` only checks `current_user.logged_in?`/`authorized?`/`requires_fresh_login?` — it never validates that the session id was freshly minted at login time, and only calls `reset_session` for the "stale login" case, not on first successful login. There is no `protect_from_forgery`, `verify_signature`, or CSRF token check in this controller, and none is relevant to session fixation. Nothing in `User#authorized?` or the `stacks` scope addresses session-identity binding.

### Impact Explanation
Successful exploitation gives the attacker a fully authenticated Shipit session as the victim, including whatever GitHub-team authorization (`Shipit.github_teams`) the victim holds, letting them trigger deploys, rollbacks, and manage `api_clients`/repositories as that user — this is a direct authentication bypass (Critical category, matching "session fixation / forced OAuth completion" explicitly called out as High/Critical in the impact list). It is repeatable against any victim the attacker can get to authenticate on a session the attacker seeded, and it is not scoped to a single repository/stack — it grants the attacker the victim's full application-level identity.

### Likelihood Explanation
Preconditions: (1) the attacker must be able to fixate a session cookie in the victim's browser prior to login (a known and generally accepted precondition for session-fixation class bugs — cookie-setting via subdomain, XSS, or a shared/public terminal, or any mechanism that lets an attacker's session id reach the victim's cookie jar); (2) the victim must complete the real OAuth login while that fixed session id is active; (3) no session id rotation must occur in between, which is confirmed true by reading `callback` and `logout` — the only two places `session` is written in this controller. No Shipit secrets, GitHub tokens, or team membership are required by the attacker. The cost is low and the flow is deterministic once the fixation precondition is met.

### Recommendation
Call `reset_session` (or otherwise regenerate the session id, e.g. via `request.session_options[:renew] = true` / `session.merge!` after clearing) inside `GithubAuthenticationController#callback` immediately before setting `session[:user_id]` and `session[:authenticated]`, so that a freshly authenticated session never reuses a pre-existing session id.

```ruby
class GithubAuthenticationControllerTest < ActionDispatch::IntegrationTest
  test "session id is not fixed across OAuth login" do
    # Step 1: attacker (or victim's browser before auth) establishes a session
    get shipit.github_authentication_path
    pre_auth_session_id = cookies["_session_id"] # or whatever the session cookie key is

    # Step 2: victim completes OAuth with a stubbed omniauth.auth
    victim = shipit_users(:walrus)
    OmniAuth.config.mock_auth[:github] = OmniAuth::AuthHash.new(
      extra: { raw_info: victim.attributes },
      credentials: { token: 'victim-token' }
    )
    get shipit.github_authentication_callback_path
    post_auth_session_id = cookies["_session_id"]

    # Assertion 1 (the binding under test): session id must have rotated on login
    assert_not_equal pre_auth_session_id, post_auth_session_id,
      "session id was not regenerated on successful GitHub login (session fixation)"

    # Assertion 2: without rotation, reusing the pre-auth session id (attacker-known)
    # after victim login would resolve current_user to the victim -- demonstrate via
    # asserting session[:user_id] == victim.id while the cookie sent was the
    # attacker-seeded pre_auth_session_id, if rotation is absent.
  end
end
```
This directly tests the equality the vulnerability breaks: `session id before login == session id after login` should be `false`; the current code makes it `true`, which is the root cause enabling fixation.

```ruby
    def callback
```
