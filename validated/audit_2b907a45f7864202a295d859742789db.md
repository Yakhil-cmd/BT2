### Title
Webhook Signature Verified Against `repository.owner.login` While Handlers Act on `repository.full_name`, Enabling Cross-Organization Webhook Forgery in Multi-Tenant Installs - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
Shipit supports hosting multiple GitHub organizations behind a single instance, each with its own GitHub App configuration and `webhook_secret` [1](#0-0) . The webhook signature check selects which organization's secret to verify against using `repository.owner.login` (or `organization.login`) taken from the *unverified* JSON body, then verifies the raw body HMAC using that organization's secret [2](#0-1) . Once verification passes, the actual event handlers determine *which* `Stack`/`Repository` to act on using a different field of the same body, `repository.full_name` [3](#0-2) . Nothing enforces that the organization portion of `repository.full_name` matches the organization whose secret authenticated the request.

### Finding Description
`WebhooksController#verify_signature` picks the GitHub App/secret to validate against solely from the payload:
```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [4](#0-3) 

and
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
  head(422) unless verified
``` [5](#0-4) 

If verification succeeds, `create` dispatches the *whole* JSON body to handlers [6](#0-5) . Handlers such as `PushHandler` resolve the target `Stack` using a *different* field, `repository.full_name`:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [3](#0-2) 
```ruby
def process
  stacks.not_archived.where(branch:).find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
end
``` [7](#0-6) 

Because the HMAC is computed over the whole raw body but the *key* used for verification is chosen from `repository.owner.login`/`organization.login`, and the *target repository* is chosen from an independent field (`repository.full_name`), any actor who legitimately controls one onboarded organization's `webhook_secret` (e.g., an administrator of Org A on a shared, multi-tenant Shipit instance that also hosts Org B) can freely construct an arbitrary payload body, sign it with Org A's secret, but set `repository.owner.login = "OrgA"` (so the correct/known secret is chosen and verification succeeds) while setting `repository.full_name = "OrgB/some-repo"` (the actual write target). `Shipit.github(organization:)`/`verify_webhook_signature` never cross-checks that the org used to select the secret equals the org embedded in the field the handler will act on [8](#0-7) .

This is the direct analog of the report's root cause: a field the code trusts and acts on (`repository.full_name`, the effective "receiver") is never bound to the field actually covered by the authorization check (`repository.owner.login`, the effective "caller"/verified principal) even though both live in the same signed request.

### Impact Explanation
An attacker who is a legitimate, unprivileged administrator/owner of one organization hosted on a shared, multi-tenant Shipit instance can forge webhook events that Shipit will process as belonging to a completely different organization's repository, without ever having credentials or write access to that other organization/repository. For `push` events this triggers `GithubSyncJob`/`Stack#sync_github` for a target `Stack` under another tenant's repository, which drives Shipit's commit sync, CI/status/merge-queue and deploy-readiness state for a repository the attacker does not control — a cross-tenant/cross-repository state write triggered purely by request-body manipulation on an otherwise correctly-signed request. This matches the "cross-repository writes" / "unauthorized deploy" impact tier.

### Likelihood Explanation
Requires only that the Shipit instance is configured to host more than one GitHub organization (documented and tested multi-org support, e.g. `secrets_double_github_app.yml` and `Shipit.github(organization:)`) and that the attacker legitimately possesses the `webhook_secret` for at least one hosted org (their own). No access to `GITHUB_TOKEN`, other tenants' secrets, or Shipit sessions is needed — only knowledge of a webhook secret they are entitled to as an onboarded tenant. This makes it directly reachable by an "unprivileged" attacker relative to the victim organization.

### Recommendation
After computing `repository_owner` for secret selection, cross-validate that the organization used to select the webhook secret matches the organization embedded in every other identity-bearing field the handlers will subsequently use (e.g. `repository.full_name`'s owner segment, `organization.login`). Reject the request (422) on mismatch. Alternatively, bind handlers to resolve the target repository/stack using the same verified `repository_owner` value rather than re-deriving it from `repository.full_name` independently.

### Proof of Concept
1. Configure Shipit with two organizations, `OrgA` and `OrgB`, each with its own `webhook_secret` (as supported by `Shipit.github(organization:)`).
2. As the (unprivileged w.r.t. OrgB) holder of `OrgA`'s `webhook_secret`, craft a `push` event JSON body:
   ```json
   {
     "ref": "refs/heads/master",
     "after": "<attacker-chosen-sha>",
     "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/victim-repo" }
   }
   ```
3. Sign the raw body with `OrgA`'s `webhook_secret` and set header `X-Hub-Signature`.
4. POST to `/webhooks` with `X-Github-Event: push`.
5. `repository_owner` resolves to `OrgA`, `verify_webhook_signature` succeeds against `OrgA`'s secret [5](#0-4) , then `PushHandler` resolves `repository_name` from `repository.full_name` = `OrgB/victim-repo` [9](#0-8) , and triggers `stack.sync_github` for the `OrgB` stack the attacker does not control [7](#0-6) .

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
