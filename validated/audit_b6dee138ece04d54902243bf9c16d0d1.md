### Title
Webhook signature check binds to `repository.owner`/`organization` while event handlers act on `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App/secret used to validate an incoming webhook's HMAC based on `repository.owner.login` (falling back to `organization.login`), but the handlers that actually process the payload and mutate state (e.g. `PushHandler`) resolve the target `Repository`/`Stack` purely from `repository.full_name`. These two fields are never checked for consistency, so the identity that is cryptographically authenticated is not the identity that is written to.

### Finding Description
`verify_signature` computes `repository_owner = params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` and uses it to look up the org-scoped `github_app`/`webhook_secret` via `Shipit.github(organization: repository_owner)`, then verifies the raw body HMAC against that secret. [1](#0-0) 

Once the signature check passes, `create` dispatches the entire, attacker-supplied JSON body to the registered handlers unchanged. [2](#0-1) 

Every handler resolves the repository/stack to act on independently, using `payload.dig('repository', 'full_name')`, not `repository.owner.login`: [3](#0-2) 

`PushHandler`, for example, uses that repository resolution to find stacks and trigger `sync_github`: [4](#0-3) 

`Repository.from_github_repo_name` simply splits the string on `/` and looks the row up by owner/name, with no cross-check against the org that was used to verify the signature: [5](#0-4) 

This is the multi-tenant analog of the reported bug: in the escrow contract, one code path (asset balance) is checked/covered while another related, but distinct, quantity (in-flight amount) that should be bound to the same asset is silently ignored, producing an inconsistent state. Here, the "verified" identity (`repository.owner`/`organization`) and the "acted-upon" identity (`repository.full_name`) are two different fields in the same payload that are supposed to represent the same repository but are never cross-validated. Shipit explicitly supports multiple GitHub Apps/organizations configured with distinct `webhook_secret`s in a single deployment (confirmed by the `secrets_double_github_app.yml` fixture defining `OrgOne`/`OrgTwo` each with independent secrets), so this is a real multi-tenant boundary, not a single-org edge case. [6](#0-5) 

An attacker who legitimately controls a GitHub organization/App configured in the same Shipit instance (e.g. `OrgA`, whose `webhook_secret` they know because they administer that org's GitHub App settings) can craft an arbitrary webhook payload where `repository.owner.login` (or `organization.login`) is set to `"OrgA"` — so `verify_signature` selects and validates against `OrgA`'s secret using an HMAC they can legitimately compute — while `repository.full_name` is set to `"OrgB/some-repo"`, a completely unrelated repository/stack belonging to a different organization hosted on the same Shipit instance. The signature check passes (it only ever inspects `OrgA`), but `PushHandler`/other handlers act on `OrgB`'s repository, letting the attacker trigger `GithubSyncJob`, and other webhook side effects (deployable/merge/commit status updates, PR-driven review-stack provisioning/archival) against a repository they do not own or have write access to. Push events could be spoofed to trigger syncs against `expected_head_sha`, and PR handler flows (`opened`, `labeled`, `closed`) can provision, archive or otherwise mutate review stacks that belong to `OrgB`.

### Impact Explanation
This crosses the "cross-repository writes" boundary explicitly called out as Critical impact: an attacker authenticated only for their own organization's webhook secret can cause writes (sync jobs, stack archival/provisioning, PR/label state changes) against a different organization's repository/stack that they have no legitimate access to, purely by controlling the `repository.full_name` field independently of the field used for signature-org resolution.

### Likelihood Explanation
Requires the attacker to control/administer at least one GitHub organization (or App) already configured in the same multi-tenant Shipit instance, which is a realistic setup for SaaS-style/shared Shipit deployments hosting multiple orgs' stacks (as evidenced by the engine's built-in multi-org `github_apps` configuration support). No GITHUB_TOKEN, `ApiClient` token, or Shipit session is needed — only knowledge of one org's `webhook_secret`, which the attacker is entitled to as that org's GitHub App administrator.

### Recommendation
In `WebhooksController#verify_signature` (or in the shared `Handler` base class), require that the organization used to select the webhook secret matches the owner encoded in `repository.full_name`, rejecting the payload (422) on mismatch. Alternatively, have handlers resolve the target `Repository`/`Stack` using the same `repository_owner` value that was authenticated, rather than independently trusting `repository.full_name`.

### Proof of Concept
1. Attacker administers `OrgA`'s GitHub App in a Shipit instance also hosting `OrgB`'s stacks, and knows `OrgA`'s `webhook_secret`.
2. Attacker crafts a `push` event payload:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>",
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/target-repo" }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC(OrgA_webhook_secret, raw_body)` and POSTs to `/webhooks`.
4. `verify_signature` resolves `repository_owner = "OrgA"`, fetches `Shipit.github(organization: "OrgA")`, and the HMAC validates successfully. [7](#0-6) 
5. `PushHandler#process` resolves stacks via `Repository.from_github_repo_name("OrgB/target-repo")` and enqueues `GithubSyncJob`/`stack.sync_github` for `OrgB`'s stack, even though the request was only authenticated for `OrgA`. [8](#0-7)

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping
      head(:ok) if event == 'ping'
    end

    def event
      request.headers.fetch('X-Github-Event')
    end

    def repository_owner
      # Fallback to the organization sub-object if repository isn't included in the payload
      params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')

module Shipit
  module Webhooks

          requires :ref
          requires :after
