### Title
Unprivileged pull-request labels are merged into the deploy environment without a key allowlist, letting a fork PR clobber `PYTHONPATH` (and any other env var) for `Command#start` - (File: app/models/shipit/review_stack.rb)

### Summary
`ReviewStack#env` takes every pull-request label name, uppercases it, and merges it as `"true"` into the stack's environment hash with no allowlist or blocklist of variable names. Because that hash flows straight into `Command#env`/`Command#unbundled_env`, which is spread onto `PTY.spawn`, an attacker who can label their own PR (which `LabelCapturingHandler` persists verbatim from the webhook payload) can set an arbitrary-named env var such as `PYTHONPATH="true"` for every subsequent deploy/task command run against that review stack.

### Finding Description
The broken binding, stated as an equality, is: for any process spawned for a `ReviewStack`, the invariant should be `Command#env.keys ⊆ SAFE_ALLOWLIST` (i.e. fork-controlled label names must not be able to set arbitrary environment variable names). In the actual code this equality does not hold: `Command#env.keys ⊇ pull_request.labels.map(&:upcase)`.

Trace:
1. An unprivileged fork PR author adds a label to their own PR, e.g. `pythonpath` (any casing, GitHub lowercases label names for matching but the raw `name` string is attacker-chosen).
2. `Shipit::Webhooks::Handlers::PullRequest::LabelCapturingHandler#capture_labels` writes `params.pull_request.labels.map(&:name)` directly into `pull_request.update!(labels: ...)` with no filtering: [1](#0-0) 
3. `Shipit::ReviewStack#env` merges `pull_request.labels.each_with_object({}) { |label_name, labels| labels[label_name.upcase] = "true" }` into the stack env with **no key allowlist**: [2](#0-1) 
4. `TaskCommands#env` (and similarly `DeployCommands`) calls `super.merge(@stack.env)` before merging task-specific vars, so the label-derived keys flow through into the final env hash used to build a `Command`: [3](#0-2) 
5. `Command#unbundled_env` builds the process environment as `BASE_ENV.merge('PATH' => ...).merge(@env.stringify_keys)` — the attacker-controlled `@env` (which includes the uppercased label) is merged **last**, so it overrides any existing/absent `PYTHONPATH` from `BASE_ENV`: [4](#0-3) 
6. `Command#start` spawns the process via `PTY.spawn(unbundled_env, *interpolated_arguments, chdir: @chdir)`, so the forged `PYTHONPATH` reaches the spawned process for every step of the review stack's deploy, including a `deploy.override`/custom step, potentially causing a `python` interpreter invoked in that step to import attacker-supplied modules from a path the attacker controls (e.g. a path checked out from the fork's own repo working directory). [5](#0-4) 

This is confirmed by the existing test suite itself, which documents the label→env merge behavior with `assert_equal env["WIP"], "true"` style assertions and shows no restriction on which keys can be set: [6](#0-5) [7](#0-6) 

None of the standard guards intervene: `verify_signature`/`GitHubApp#verify_webhook_signature` only authenticate that the webhook truly came from GitHub for a repo GitHub already trusts — they do not restrict what a repo owner's own PR labels can contain. The `ExplicitParameters` schema on `LabelCapturingHandler`/`LabeledHandler` only requires `labels` to be an `Array` of objects with a `name: String` — it does not restrict the character set or reserved names (no denylist for `PATH`, `PYTHONPATH`, `LD_PRELOAD`, etc.). `provisioning_behavior=prevent_with_label` only gates whether a review stack is provisioned/archived; it does not sanitize the env-hash-generation path at all — labels still get captured by `LabelCapturingHandler` and merged into `env` by `ReviewStack#env` regardless of `provisioning_behavior`.

### Impact Explanation
An attacker who can only open a PR from a fork and add a label to it (a zero-privilege GitHub action on their own PR) can inject an arbitrary-named environment variable (not just `true`/`false` semantic flags) into every process the Shipit deploy host spawns for that review stack — deploy steps, override steps, task steps, etc. If any step in the review stack's `shipit.yml` (which for review stacks may itself be partially attacker-influenced depending on configuration) invokes an interpreter or tool sensitive to environment-based hijacking (`PYTHONPATH`, `LD_PRELOAD`, `RUBYOPT`, `NODE_OPTIONS`, `BUNDLE_GEMFILE`, etc.), the attacker can achieve code execution in the context of the Shipit deploy host process — Critical severity, matching the "RCE on the deploy host via `Command`/`PTY.spawn`" category. The blast radius is scoped to the review stack the attacker's own PR created/owns, but since the deploy host is shared, arbitrary code execution there compromises the whole Shipit installation (other repos' secrets, `GITHUB_TOKEN`, etc. residing on the same host/process).

### Likelihood Explanation
Preconditions are minimal: the repository must have `review_stacks_enabled` and any `provisioning_behavior` (including `prevent_with_label`, which does not block label capture), and the attacker only needs the ability to open a PR from a fork and label it — actions available to any GitHub user with fork/PR access, no Shipit credentials, no maintainer role, and no secrets. This is essentially a one-request-per-label attack, fully repeatable and requires no timing tricks or race conditions, making it highly feasible.

### Recommendation
In `Shipit::ReviewStack#env`, allowlist which pull-request labels may be surfaced as environment variables (e.g. only labels matching a configured prefix or explicit allowlist maintained by the repo owner), and/or reject/strip label names that collide with reserved/security-sensitive environment variable names (`PATH`, `PYTHONPATH`, `LD_PRELOAD`, `RUBYOPT`, `BUNDLE_*`, `GEM_*`, etc.) before merging. Alternatively, namespace label-derived env vars under a fixed prefix (e.g. `SHIPIT_LABEL_<NAME>`) so they can never collide with interpreter/loader-sensitive variable names, and ensure `Command#unbundled_env` cannot have such prefixed values reach reserved names.

### Proof of Concept
```ruby
# test/models/shipit/review_stack_test.rb (extend existing suite)
test "#env allows a PR label to inject PYTHONPATH into spawned command env" do
  stack = shipit_stacks(:review_stack)
  stack.pull_request.labels = ["pythonpath"]

  env = stack.env
  assert_equal "true", env["PYTHONPATH"]

  command = Shipit::Command.new("python -c 'pass'", env: env, chdir: ".")
  spawned_env = command.unbundled_env
  assert_equal "true", spawned_env["PYTHONPATH"]
  # Binding under test: env.keys should be restricted to a safe allowlist;
  # here PYTHONPATH — a fork-controllable key — reaches the spawned process env,
  # violating the invariant that deploy.override inherits no attacker-controllable key.
end
```
This demonstrates the label-to-`PYTHONPATH` path end-to-end from `ReviewStack#env` through `Command#unbundled_env`, the exact hand-off point before `PTY.spawn`.
