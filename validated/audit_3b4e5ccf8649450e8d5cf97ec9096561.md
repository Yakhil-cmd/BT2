### Title
`handleKLAYTransfer` Permanently Locks Bridged KAIA When `_to` Is a Contract Unable to Receive Native KAIA — (`contracts/service_chain/bridge/BridgeTransferKLAY.sol`)

---

### Summary

`handleKLAYTransfer` in the Kaia service-chain bridge uses a bare `.call.value()` to push native KAIA to the recipient address `_to`. If `_to` is a contract without a payable `receive`/`fallback` function, or one whose fallback reverts, the call returns `ok = false`, the subsequent `require` reverts the entire transaction, and the bridged KAIA is permanently undeliverable. Because the `_to` address is immutably fixed by the source-chain `RequestValueTransfer` event and operators have no mechanism to redirect the transfer, the KAIA is locked in the destination bridge contract forever.

---

### Finding Description

In `BridgeTransferKLAY.sol`, `handleKLAYTransfer` performs the following sequence: [1](#0-0) 

```
_lowerHandleNonceCheck(_requestedNonce);   // guard
_voteValueTransfer(_requestedNonce);        // quorum check
_setHandledRequestTxHash(_requestTxHash);  // mark tx hash
handleNoncesToBlockNums[_requestedNonce] = _requestedBlockNumber;
_updateHandleNonce(_requestedNonce);        // advance lowerHandleNonce
emit HandleValueTransfer(...);

(bool ok, ) = _to.call.value(_value)("");   // ← bare push
require(ok, "handleKLAYTransfer: transfer failed");
```

Because the `require` at line 99 reverts the entire transaction when `ok == false`, all preceding state mutations are also rolled back. The nonce is never consumed, `lowerHandleNonce` never advances past this slot, and the KAIA stays in the bridge. Operators observe the revert and retry — but every retry produces the same outcome because `_to` is taken verbatim from the source-chain event and cannot be changed. [2](#0-1) 

The `_updateHandleNonce` loop in `BridgeTransfer.sol` advances `lowerHandleNonce` only through a contiguous run of handled nonces: [3](#0-2) 

A permanently unhandleable nonce N therefore pins `lowerHandleNonce` at N indefinitely, corrupting the bridge's recovery-block-number tracking for all subsequent nonces.

The Go-layer bridge manager passes `_to` directly from the source-chain event with no substitution path: [4](#0-3) 

A secondary instance of the same class exists in `BridgeFee._payKLAYFeeAndRefundChange`, where a non-payable `feeReceiver` contract blocks every KAIA bridge request: [5](#0-4) 

---

### Impact Explanation

- **Unauthorized permanent lock of bridged KAIA**: A user who specifies a contract `_to` address that cannot receive native KAIA on the destination chain loses the full bridged amount. The KAIA is locked in the destination bridge contract with no withdrawal path.
- **`lowerHandleNonce` corruption**: The stuck nonce prevents the bridge's recovery system (`recoveryBlockNumber`) from advancing correctly, degrading the reliability of the value-transfer recovery mechanism for all subsequent nonces.
- **No operator escape hatch**: `handleKLAYTransfer` accepts `_to` as a parameter supplied by operators, but operators must faithfully reproduce the source-chain event parameters. There is no `handleKLAYTransferTo` override or escrow fallback.

---

### Likelihood Explanation

Any user on the source chain who specifies a contract address as `_to` — intentionally (e.g., a multisig or DAO treasury without a payable fallback) or unintentionally — triggers this condition. Solidity 0.5.6 contracts without an explicit `function () external payable {}` fallback cannot receive KAIA, and many deployed contracts fall into this category. No special privilege is required; the trigger is a normal `requestKLAYTransfer` call from any EOA.

---

### Recommendation

Replace the bare push with an escrow-and-claim pattern analogous to the PartyDAO fix referenced in the external report:

1. **Escrow on failure**: If `_to.call.value(_value)("")` returns `false`, store the amount in a `mapping(address => uint256) public pendingWithdrawals` keyed by `_to` rather than reverting.
2. **Claim function**: Add a `withdrawPending()` function that lets `_to` (or an authorized address) pull the escrowed KAIA to an alternative address.
3. **Advance nonce regardless**: Mark the nonce as handled even when the push fails, so `lowerHandleNonce` continues to advance and the recovery system remains accurate.

Alternatively, wrap the call without `require` and emit a `TransferFailed` event, allowing operators to re-attempt delivery to a user-specified fallback address.

---

### Proof of Concept

1. Deploy a contract `NoReceive` on the destination chain with no payable fallback.
2. On the source chain, call `requestKLAYTransfer(address(NoReceive), value, "")` with sufficient KAIA.
3. Operators observe the `RequestValueTransfer` event and call `handleKLAYTransfer(..., address(NoReceive), value, nonce, ...)` on the destination bridge.
4. `NoReceive` rejects the KAIA push → `ok == false` → `require` reverts.
5. Operators retry indefinitely; every attempt reverts.
6. The source-chain KAIA is permanently locked in the source bridge; the destination bridge's KAIA liquidity is unaffected but the nonce slot is permanently unresolvable.
7. Confirm: `lowerHandleNonce` remains pinned at `nonce`; `recoveryBlockNumber` does not advance past the block of the stuck request. [6](#0-5) [7](#0-6)

    function _updateHandleNonce(uint64 _requestedNonce) internal {
        if (_requestedNonce > upperHandleNonce) {
            upperHandleNonce = _requestedNonce;
        }

        uint64 limit = lowerHandleNonce + 200;
        if (limit > upperHandleNonce) {
            limit = upperHandleNonce;
        }

        uint64 i;
        for (i = lowerHandleNonce; i <= limit && handleNoncesToBlockNums[i] > 0; i++) {
            recoveryBlockNumber = handleNoncesToBlockNums[i];
            delete handleNoncesToBlockNums[i];
            delete closedValueTransferVotes[i];
        }
        lowerHandleNonce = i;
    }
