### Title
Webhook organization-authentication is not bound to the repository actually written by event handlers, enabling cross-tenant forgery of commit statuses - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/handler.rb], [File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/`webhook_secret` to validate an inbound HMAC signature against using the payload's `repository.owner.login` (falling back to `organization.login`), but none of the downstream event handlers verify that this authenticated organization actually corresponds to the repository/stack the handler subsequently mutates. `StatusHandler` in particular does not check any repository field at all: it updates commit statuses purely by SHA, globally, across every stack in the Shipit instance. This breaks the binding "organization that authenticated == repository that is written," the exact class of trust-binding failure called out as in-scope, and mirrors the off-by-reference bug class from the report (a value used to act is not the value that was actually verified).

### Finding Description
`verify_signature` picks the `GitHubApp` (and therefore the `webhook_secret` used for HMAC verification) based on `repository_owner`: [1](#0-0) [2](#0-1) 

In a multi-organization deployment (documented in `docs/setup.md`, "Using Multiple Github Applications"), each organization has its own `webhook_secret`. `Shipit.github(organization:)` looks up the app config keyed by that same owner login: [3](#0-2) 

Once the signature check passes, the raw parsed JSON is dispatched unmodified to every matching handler: [4](#0-3) 

The base `Handler` class exposes a `repository_name` helper that reads a *different* field of the same payload (`repository.full_name`) to scope work to a `Stack`: [5](#0-4) 

Nothing ties `repository_owner` (used to select/verify the signing secret) to `repository.full_name` (used by `stacks`) — they are two independently attacker-controlled JSON fields in the same signed body. Worse, `StatusHandler` doesn't even use `repository_name`/`stacks`; it looks up commits **globally by SHA only**, with no repository or organization scoping whatsoever: [6](#0-5) 

The equality that should hold is:
`organization authenticated by verify_signature (repository_owner) == organization/repository whose commit rows StatusHandler mutates`

Before the attacker's request: only a legitimate GitHub webhook delivery for organization X, signed with X's `webhook_secret`, can create/update `Status` rows for commits belonging to stacks under organization X.

After the attacker's request: any organization configured in Shipit's multi-tenant `github:` secrets (which the attacker legitimately administers, e.g. their own low-privilege organization with its own GitHub App and `webhook_secret` they set up themselves) can send a `status` event, correctly signed with their own secret, containing an arbitrary `sha` value. `verify_signature` authenticates the request against the attacker's own org, but `StatusHandler#process` then applies the payload to `Commit.where(sha: params.sha)` — matching commit rows belonging to *any* stack/organization tracked by the instance, not just the attacker's own.

This status is then used directly by deploy-safety logic: [7](#0-6) [8](#0-7) 

Setting `state: "success"` for a required/blocking `context` on a victim commit clears `blocked?`/raises `deployable?` for that commit in a completely different organization's stack, and also invokes `stack.schedule_merges` for pending/success statuses.

### Impact Explanation
An attacker who legitimately controls one organization/GitHub-App entry in a multi-tenant Shipit install (i.e., holds no privileges on the victim organization or repository, and needs no `ApiClient` token, no GitHub App private key, and no access to the victim's `webhook_secret`) can forge commit-status webhooks for arbitrary other organizations' commits. Because commit status directly gates `deployable?`/`blocked?` and drives `stack.schedule_merges`, this allows marking a required/blocking CI check as `success` on a victim commit that never actually passed CI, satisfying the deploy-safety and merge-queue gating and enabling an **unauthorized deploy/merge** on a stack the attacker has no legitimate access to. This matches the Critical impact category "an unauthorized deploy, rollback or merge."

### Likelihood Explanation
The only prerequisite is administering one organization/App entry in the Shipit multi-tenant `github:` config — something an unprivileged external party can arrange for themselves without any access to the victim's secrets, tokens, or repositories. Commit SHAs are public information (visible via the target repo's commit history/API), so guessing/obtaining a target SHA to forge a status for is trivial. `StatusHandler` performs no repository check at all, so exploitation requires no additional bypass beyond sending a validly-signed webhook for the attacker's own org with a victim SHA and a matching required/blocking `context` string (also discoverable from the target's public `shipit.yml`/status names).

### Recommendation
- In `Handler#stacks`/`repository_name`, and specifically in `StatusHandler#process`, scope commit/status lookups to the repository identified by the verified `repository_owner`/organization (or reject payloads whose `repository.full_name` owner does not match the authenticated organization).
- Pass the authenticated organization (not just the raw parsed payload) from `WebhooksController#create` into `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`, and have each handler assert that any repository-scoped lookup (e.g., `Commit.where(sha:)`) is additionally filtered by `stack.repository.owner == authenticated_organization`.
- Add a regression test asserting that a validly-signed webhook for organization A cannot alter `Status`/`Commit` records belonging to a stack under organization B.

### Proof of Concept
1. Shipit is configured with multiple organizations, each with its own `github.<org>.webhook_secret` (per `docs/setup.md`, "Using Multiple Github Applications"), including `attacker-org` (which the attacker administers) and `victim-org` (unrelated, attacker has no access).
2. Attacker fetches a public commit SHA from `victim-org/victim-repo` and identifies a `context` string it requires from that stack's public `shipit.yml` (`ci.blocking`/`ci.require`).
3. Attacker POSTs to `/webhooks` with `X-Github-Event: status` and a body such as:
   ```json
   { "sha": "<victim commit sha>", "state": "success", "context": "<victim blocking context>",
     "repository": { "owner": { "login": "attacker-org" }, "full_name": "attacker-org/whatever" } }
   ```
   signed with `attacker-org`'s own legitimately-held `webhook_secret` via `X-Hub-Signature`.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: "attacker-org")` and successfully verifies the signature using the attacker's own secret.
5. `StatusHandler#process` executes `Commit.where(sha: params.sha)` — matching the victim commit in `victim-org`'s stack regardless of the `repository` fields — and calls `commit.create_status_from_github!(params)`, creating a `success` status for the blocking `context` on the victim's commit, clearing `blocked?`/enabling `deployable?` and triggering `stack.schedule_merges` for a stack the attacker never had access to.   def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
