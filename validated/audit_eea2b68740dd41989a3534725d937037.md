### Title
Rule engine matches raw literal strings without canonicalization, allowing block rules on file_path/command to be bypassed via equivalent alternate representations - (File: `plugins/hookify/core/rule_engine.py`)

### Summary
`RuleEngine._check_condition` (via `_extract_field` and `_matches_tool`) compares `tool_input`/`tool_name` values as raw, uncanonicalized strings using case-sensitive `equals`/`contains`/`starts_with`/`ends_with` operators or per-pattern `regex_match`. Because no path/command normalization is performed, a semantically identical operation expressed with a different textual representation (case variance, extra path segments, `.`/`..` components, alternate quoting/whitespace in shell commands) will not match the literal pattern a rule author wrote, letting a dangerous Bash/Edit/Write operation slip past an intended `block` rule.

### Finding Description
`RuleEngine._rule_matches` (`plugins/hookify/core/rule_engine.py:96-125`) requires every `Condition` to match via `_check_condition` (`plugins/hookify/core/rule_engine.py:144-180`), which extracts a field value with `_extract_field` (`plugins/hookify/core/rule_engine.py:182-254`) and applies the operator directly: [1](#0-0) 

For `equals`, `contains`, `starts_with`, `ends_with`, the comparison is a strict, case-sensitive Python string comparison against the exact bytes Claude Code places in `tool_input` (e.g. `file_path`, `command`, `new_string`/`content`). Only `regex_match` applies `re.IGNORECASE` via the cached compiler: [2](#0-1) 

No path canonicalization (`os.path.realpath`/`abspath`/`normpath`) or command-syntax normalization is ever performed anywhere in the plugin — confirmed by the absence of such calls in `plugins/hookify/core/rule_engine.py` and `plugins/hookify/core/config_loader.py`. `_extract_field` returns raw values straight from `tool_input`: [3](#0-2) 

Because Claude Code's tool execution (Bash shell, filesystem Write/Edit) resolves paths and shell syntax at the OS/interpreter level, several textual variants resolve to the **same underlying target/operation** but are treated as non-matching by the rule engine:
- Case variation of `file_path` on case-insensitive filesystems (default macOS/Windows) bypasses `equals`/`contains`/`starts_with` rules protecting a specific path.
- Path representations with redundant segments (`./`, `//`, trailing slash) or `..` traversal that resolve to the identical file bypass literal `equals`/`starts_with` checks on `file_path`.
- Shell command text that is logically equivalent but lexically different (alternate quoting, `$IFS` in place of spaces, command substitution, line continuation) evades `contains`/`equals`/most hand-written `regex_match` patterns targeting `command`.
- `_matches_tool` (`plugins/hookify/core/rule_engine.py:127-142`) does exact, case-sensitive membership testing (`tool_name in patterns`) with no alias/casing tolerance, so any layer that could surface a differently-cased or aliased tool name would also bypass the matcher.

Because a malicious repository, issue, or PR can influence what Bash/Edit/Write invocation Claude Code ultimately issues (prompt-injection-style influence over generated commands/paths), an attacker who cannot see or alter the defender's rule file can still craft repository content that nudges Claude Code toward one of these unmatched-but-equivalent representations, causing a `block` rule that the operator believed covered the operation to silently no-op while the underlying dangerous mutation (e.g. writing outside the intended path, or running the blocked command) still executes.

### Impact Explanation
This breaks the core security invariant of hookify: "a matching block rule must reliably deny the protected operation." A rule intended to block writes to a sensitive path or a dangerous shell command can be silently bypassed using an equivalent-but-differently-encoded representation, resulting in unauthorized file mutation or command execution that the operator explicitly tried to prevent — i.e., cross-repo/cross-session/wrong-target mutation with real security impact, consistent with the target impact class in the question.

### Likelihood Explanation
No special privilege is required beyond normal Claude Code operation with hookify rules enabled; the bypass only requires the resulting tool call to use a textually different but operationally equivalent representation of the protected path/command, which is plausible whenever generated commands/paths are influenced by external content (repo files, issue/PR text) or simply vary naturally in casing/quoting. The gap is deterministic and repeatable for any given alternate encoding once identified, since `_check_condition`/`_extract_field`/`_matches_tool` never normalize inputs.

### Recommendation
- For `file_path` fields, canonicalize both the rule pattern and the extracted value (e.g., `os.path.realpath`/`os.path.normcase`) before comparison, or perform matching against the resolved absolute path.
- Make case sensitivity consistent and explicit: either treat all string operators as case-insensitive by default (matching `regex_match`'s `IGNORECASE`) or provide an explicit `case_sensitive` flag on `Condition` and document filesystem case-sensitivity implications.
- For Bash `command` fields, consider normalizing whitespace/quoting or documenting that `block` rules are best-effort literal/regex matches and cannot guarantee semantic equivalence detection; where strong guarantees are required, recommend allowlisting rather than denylisting.
- Extend `_matches_tool` to normalize `tool_name` casing before comparison.

### Proof of Concept
Add unit tests in `plugins/hookify/tests/` exercising `RuleEngine.evaluate_rules` directly:
1. Define a `block` rule with `tool_matcher="Write"` and condition `field="file_path", operator="equals", pattern="/protected/secret.txt"`.
   - Assert blocked for `tool_input={"file_path": "/protected/secret.txt"}`.
   - Assert **also blocked** (currently NOT blocked — bug) for `tool_input={"file_path": "/PROTECTED/secret.txt"}` on a case-insensitive filesystem, and for `tool_input={"file_path": "/protected/./secret.txt"}`.
2. Define a `block` rule with `tool_matcher="Bash"` and condition `field="command", operator="regex_match", pattern=r"rm\s+-rf\s+/"`.
   - Assert blocked for `command="rm -rf /tmp"`.
   - Assert **also blocked** (currently NOT blocked — bug) for `command="rm${IFS}-rf${IFS}/tmp"` or `command="r\\m -rf /tmp"`.

Expected result today: the "equivalent representation" cases pass through `evaluate_rules` returning `{}` (allowed) instead of the blocking response, demonstrating the bypass of the intended `block` rule.
