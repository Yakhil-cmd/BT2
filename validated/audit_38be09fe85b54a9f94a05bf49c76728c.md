### Title
Bridge Operator Can Front-Run User's Fallback KLAY Transfer to Silently Charge Excessive Fees — (File: contracts/service_chain/bridge/BridgeTransferKLAY.sol)

---

### Summary

The service-chain bridge stores `feeOfKLAY` as a single contract-level (global) variable that bridge operators can update at any time. The bridge's Solidity fallback function reads this variable **at execution time** and uses it as both the fee and the fee-limit. A malicious operator can therefore front-run a user's pending fallback call, raise the fee, and silently extract more KLAY than the user intended to pay — with no revert and no refund of the difference.

---

### Finding Description

**Global fee storage (BridgeFee.sol)**

`feeOfKLAY` is a single storage slot shared by every caller:

```solidity
uint256 public feeOfKLAY = 0;          // BridgeFee.sol L30
```

Operators change it with a single on-chain call (subject to the configured `operatorThreshold`, which defaults to 1):

```solidity
function setKLAYFee(uint256 _fee, uint64 _requestNonce)
    external onlyOperators
{
    if (!_voteConfiguration(_requestNonce)) { return; }
    _setKLAYFee(_fee);                  // BridgeTransferKLAY.sol L144-152
}
```

**Fallback reads the fee at execution time**

The fallback function passes `feeOfKLAY` — read at the moment the transaction is mined — as the `_feeLimit` argument:

```solidity
function () external payable {
    _requestKLAYTransfer(msg.sender, feeOfKLAY, new bytes(0));  // L128
}
```

Inside `_requestKLAYTransfer`, the same storage slot is read again as the actual fee charged:

```solidity
function _payKLAYFeeAndRefundChange(uint256 _feeLimit) internal returns(uint256) {
    uint256 fee = feeOfKLAY;                    // BridgeFee.sol L44
    require(_feeLimit >= fee, "insufficient feeLimit");
    // pays `fee` to feeReceiver; refunds (_feeLimit - fee) to sender
    ...
}
```

Because `_feeLimit == feeOfKLAY` in the fallback path, `feeRefund` is always **zero** — the user receives no change regardless of how much the fee was raised.

The emitted transfer value is:

```solidity
emit RequestValueTransfer(..., msg.value.sub(_feeLimit), ...);  // L118
```

So the amount credited on the destination chain is `msg.value − newFee`, not `msg.value − oldFee`.

**No slippage guard exists for the fallback path.** The `requestKLAYTransfer` function does allow a user-controlled `_feeLimit` (`msg.value − _value`), but the fallback — the most common entry point for simple KLAY deposits — does not.

---

### Impact Explanation

A user who sends `1.4 KLAY` via the fallback expecting a `0.4 KLAY` fee and a `1.0 KLAY` cross-chain credit instead receives only `0.6 KLAY` on the destination chain. The `0.4 KLAY` difference is silently transferred to the `feeReceiver`. This is a direct, unauthorized KAIA token loss from the user's perspective, matching the allowed-impact category: *"fee charge … affecting KAIA … or system-managed funds."*

---

### Likelihood Explanation

The attack requires a bridge operator (or the bridge owner, who is an operator by default) to act maliciously. With `operatorThreshold = 1` (the default), a single operator suffices. Even with a higher threshold, a colluding minority of operators — not a chain-wide majority — can execute the attack. Because Kaia is an EVM-compatible chain with a deterministic mempool ordering, a validator-operator can trivially order the `setKLAYFee` transaction before the user's fallback transaction in the same block.

---

### Recommendation

1. **User-supplied max-fee parameter**: Add a `requestKLAYTransferWithMaxFee(address _to, uint256 _maxFee, bytes calldata _extraData) external payable` entry point that reverts if `feeOfKLAY > _maxFee` at execution time, analogous to slippage guards in AMMs.

2. **Snapshot fee at request time**: Record the fee in the `RequestValueTransfer` event and enforce that the charged fee cannot exceed the fee that was current when the request was submitted (requires a nonce-to-fee mapping).

3. **Time-lock fee changes**: Require a minimum delay between a `setKLAYFee` vote passing and the new fee taking effect, preventing same-block front-running.

---

### Proof of Concept

```
State before attack:
  feeOfKLAY = 0.4 KLAY
  feeReceiver = operator-controlled address

Step 1 – User broadcasts fallback call:
  bridge.call{value: 1.4 ether}("")
  // User expects: fee=0.4, cross-chain credit=1.0

Step 2 – Operator front-runs in the same block:
  bridge.setKLAYFee(0.8 ether, currentNonce)
  // feeOfKLAY is now 0.8 KLAY

Step 3 – User's fallback executes:
  _requestKLAYTransfer(msg.sender, feeOfKLAY=0.8, "")
  require(1.4 > 0.8)  ✓ — no revert
  fee = 0.8 KLAY → sent to feeReceiver
  feeRefund = 0.8 - 0.8 = 0  → no refund
  emitted valueOrTokenId = 1.4 - 0.8 = 0.6 KLAY

Result:
  User loses 0.4 KLAY extra (silently, no revert)
  Operator-controlled feeReceiver gains 0.4 KLAY extra
  User receives 0.6 KLAY on destination chain instead of 1.0 KLAY
```

        uint256 fee = feeOfKLAY;

        if (feeReceiver != address(0) && fee > 0) {
            require(_feeLimit >= fee, "insufficient feeLimit");

            (bool ok, ) = feeReceiver.call.value(fee)("");
            require(ok, "transfer fee failed");

            uint256 feeRefund = _feeLimit.sub(fee);
            if (feeRefund > 0) {
                (bool ok, ) = msg.sender.call.value(feeRefund)("");
                require(ok, "refund fee failed");
            }

            return fee;
