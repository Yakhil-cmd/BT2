### Title
`exec.CommandContext` in `runWithStdin` kills only the direct child process, leaving orphaned descendants of hooks/git processes alive past context deadline - (File: pkg/cmd/cmd.go)

### Summary
`runWithStdin` in `pkg/cmd/cmd.go` builds every subprocess (git invocations and `--exechook-command` hooks) with `exec.CommandContext` but never sets `cmd.SysProcAttr` to place the child in its own process group. When the context deadline/cancellation fires, Go's `os/exec` sends the kill signal only to the single tracked child PID, so any grandchildren the hook or git spawns (or a child that reparents/forks before dying) survive independently of the context and are never reaped by git-sync.

### Finding Description
`runWithStdin` (`pkg/cmd/cmd.go:63-94`) constructs the command with `cmd := exec.CommandContext(ctx, command, args...)` and calls `cmd.Run()` at line 81, with no `cmd.SysProcAttr = &syscall.SysProcAttr{Setpgid: true}` and no corresponding `cmd.Cancel`/process-group kill override. This is used both for git operations (via `Runner.Run`) and for `--exechook-command` execution in `pkg/hook/exechook.go`, which wraps calls in `context.WithTimeout` and invokes the runner.

Because no new process group is created, the OS default behavior applies: the exec'd process (git or the hook script) is a normal child in the same process group as git-sync. When `ctx` is canceled after the timeout, Go's `exec.CommandContext` machinery sends `SIGKILL` (default `Cancel`) to exactly the tracked `cmd.Process` — i.e., the PID returned by `fork+exec`, not the whole process group. Any subprocess that the hook script itself forks (e.g., a background job, a long-lived helper, or a git subprocess that spawns another process such as a credential helper or a slow pack/index operation) is not a direct child of the killed PID from git-sync's perspective at the OS signaling layer used here; it is only reachable if the killed parent also forwards the signal, which shell wrappers do not reliably do, especially if the parent is already dead or the child explicitly ignores/blocks propagation.

An attacker who controls repository content/refs that trigger the exechook, or content that makes a git subprocess (invoked by `Runner.Run`) spend long time or spawn a grandchild, can arrange for the hook or a git-invoked helper to fork a process that outlives the direct child once SIGKILL is delivered only to the tracked PID. Since the operator has configured `--exechook-command` (a documented, supported flag) to run a script over which the attacker has partial influence (the script commonly consumes the synced worktree contents), the exploit path requires only unprivileged control over repository content/refs plus the operator's use of a documented flag — no operator misconfiguration beyond using the feature as intended, and no privileged access is required by the attacker.

No compensating control exists in the reviewed code: there is no `SysProcAttr{Setpgid:true}` + group-kill logic, no post-`cmd.Run()` process-tree cleanup, and no explicit orphan reaping. `cmdForLog` is unrelated to the security defect other than confirming the exact argv that is executed (it is used purely for logging/quoting, not for sandboxing).

### Impact Explanation
Surviving orphaned processes can continue to hold open file descriptors/locks on the `--root` worktree and continue consuming CPU/IO indefinitely, since git-sync has no further mechanism to track or terminate them after the context is done. Repeated triggering (e.g., rapid pushes causing repeated hook firings or repeated slow git operations) accumulates orphaned processes, leading to resource exhaustion (CPU/memory/FD/volume lock contention) and a wedged repository state (e.g., stale `index.lock`/worktree locks left by an orphan), which matches the "resource exhaustion" / "denial of service" bug-bounty impact class for a sync sidecar.

### Likelihood Explanation
Requires only that the operator has enabled `--exechook-command` (a documented, standard feature) and that the attacker can influence content processed by that hook or by a git subprocess triggered on their pushed refs — both within the stated unprivileged attacker capability (control of repo content/refs). No non-default insecure flag is needed beyond the intended use of `--exechook-command` (or even without it, a git subprocess that itself spawns a child, e.g., a credential/askpass helper, can suffice). The condition is reproducible deterministically: any child process that forks a grandchild and then blocks/ignores termination of the parent reproduces the orphan every time the context deadline elapses.

### Recommendation
Set `cmd.SysProcAttr = &syscall.SysProcAttr{Setpgid: true}` when constructing the command in `runWithStdin`, and replace the default kill behavior with an explicit `cmd.Cancel` function (or a `context.AfterFunc`) that sends the kill signal to the negative PID (`syscall.Kill(-pgid, syscall.SIGKILL)`) to terminate the entire process group on context cancellation, ensuring no descendant can outlive the context.

### Proof of Concept
Add a unit test in `pkg/cmd/cmd_test.go` that runs a shell script via `runWithStdin` with a short `context.WithTimeout`, where the script backgrounds a grandchild that writes a heartbeat file in a loop and disowns itself (`sh -c 'sleep 100 & disown; wait'`). After the context deadline elapses and `runWithStdin` returns, assert that the heartbeat file stops being updated (i.e., the grandchild PID is no longer running) — under the current implementation the grandchild continues running and the heartbeat keeps updating, demonstrating the orphaned-process leak; after applying the `Setpgid`+group-kill fix, the grandchild is terminated along with the direct child. func runWithStdin(ctx context.Context, log logintf, cwd string, env []string, stdin, command string, args ...string) (string, string, error) {
	cmdStr := cmdForLog(command, args...)
	log.V(5).Info("running command", "cwd", cwd, "cmd", cmdStr)

	cmd := exec.CommandContext(ctx, command, args...)
	if cwd != "" {
		cmd.Dir = cwd
	}
	if len(env) != 0 {
		cmd.Env = env
	}
	outbuf := bytes.NewBuffer(nil)
	errbuf := bytes.NewBuffer(nil)
	cmd.Stdout = outbuf
	cmd.Stderr = errbuf
	cmd.Stdin = bytes.NewBufferString(stdin)

	start := time.Now()
	err := cmd.Run()
	wallTime := time.Since(start)
	stdout := strings.TrimSpace(outbuf.String())
	stderr := strings.TrimSpace(errbuf.String())
	if ctx.Err() == context.DeadlineExceeded {
		return stdout, stderr, fmt.Errorf("Run(%s): %w: { stdout: %q, stderr: %q }", cmdStr, ctx.Err(), stdout, stderr)
	}
	if err != nil {
		return stdout, stderr, fmt.Errorf("Run(%s): %w: { stdout: %q, stderr: %q }", cmdStr, err, stdout, stderr)
	}
	log.V(6).Info("command result", "stdout", stdout, "stderr", stderr, "time", wallTime)

	return stdout, stderr, nil
}

func cmdForLog(command string, args ...string) string {
	if strings.ContainsAny(command, " \t\n") {
		command = fmt.Sprintf("%q", command)
	}
	argsCopy := make([]string, len(args))
	copy(argsCopy, args)
	for i := range args {
		if strings.ContainsAny(args[i], " \t\n") {
			argsCopy[i] = fmt.Sprintf("%q", args[i])
		}
	}
	return command + " " + strings.Join(argsCopy, " ")
}
