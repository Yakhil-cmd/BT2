### Title
Arbitrary environment variable injection into git/deploy subprocesses via unfiltered PR label names in `ReviewStack#env` (e.g. `SSH_ASKPASS`) - (File: app/models/shipit/review_stack.rb)

### Summary
`ReviewStack#env` merges every pull-request label name (uppercased) directly into the stack's environment hash with no allowlist, and that hash is merged unfiltered into `StackCommands#env`, which feeds `Command#unbundled_env` and ultimately `PTY.spawn` for every git subprocess run against a review stack (`fetch`, `fetch_commit`, `fetch_deployed_revision`, `with_temporary_working_directory`). Unlike deploy/task/rollback variables, which are always scrubbed through `EnvironmentVariables#permit` against a fixed whitelist, label-derived keys bypass this control entirely, letting an attacker who can label a PR set sensitive process environment variables such as `SSH_ASKPASS`, `GIT_ASKPASS`, `LD_PRELOAD`, `BUNDLE_GEMFILE`, or `PATH` on the deploy host's git subprocesses.

### Finding Description
The broken binding, stated as an equality that should hold but does not:

`env(reaching PTY.spawn for a ReviewStack's git commands)` should equal `allowlist(EnvironmentVariables#permit(variable_definitions))`, as it does for deploy/task/rollback env (`Stack#build_deploy` → `filter_deploy_envs` → `EnvironmentVariables#permit(deploy_variables)` at [1](#0-0) , `TaskDefinition#filter_envs` at [2](#0-1) , and the raising behavior in `EnvironmentVariables#permit` at [3](#0-2) ).

In reality:
- `ReviewStack#env` builds `super.merge(pull_request.labels.each_with_object({}) { |label_name, labels| labels[label_name.upcase] = "true" })` with **no allowlist call at all**: [4](#0-3) .
- `LabelCapturingHandler#capture_labels` writes `params.pull_request.labels.map(&:name)` straight from the webhook payload into `pull_request.labels`: [5](#0-4) .
- `StackCommands#env` merges the stack's raw env into the base git env: `super.merge(@stack.env)`: [6](#0-5) .
- `StackCommands#fetch_deployed_revision`, `#fetch`, `#fetch_commit`, `#fetched?`, and `#with_temporary_working_directory` all pass this same unfiltered `env` into `Command.new`/`git(...)`: [7](#0-6) .
- `Command#unbundled_env` merges `@env.stringify_keys` last, overriding `BASE_ENV`, and this exact hash is passed to `PTY.spawn`: [8](#0-7) .

Existing guards do not close this gap: `EnvironmentVariables#permit` is only invoked for the deploy/task/rollback "custom variables" feature (`filter_deploy_envs`, `filter_rollback_envs`, `TaskDefinition#filter_envs`), not for `ReviewStack#env`/`StackCommands#env`. This is confirmed intentional-but-unsafe behavior by the existing test suite explicitly asserting labels become raw env entries with no filtering: [9](#0-8) , [10](#0-9) , [11](#0-10) .

Exploit flow: an attacker with permission to apply a label named `ssh_askpass` (case-insensitive) to their PR on a repository with review stacks enabled causes GitHub to emit a `pull_request.labeled` webhook; `LabelCapturingHandler` persists it verbatim; the next `StackCommands#fetch`, `#fetch_commit`, or `FetchDeployedRevisionJob#perform` → `StackCommands#fetch_deployed_revision` builds a `Command`/`git(...)` whose `unbundled_env` contains `SSH_ASKPASS` pointing at an attacker-chosen program name/path, which will be inherited by any `ssh` invoked from that git subprocess (e.g. when the review stack's git remote uses the `ssh://`/`git@` transport and ssh needs to answer a password/passphrase prompt).

### Impact Explanation
If exploited, the git subprocess used to fetch a review stack's revision or maintain its git cache runs with an attacker-named `SSH_ASKPASS` (or other sensitive variable such as `LD_PRELOAD`, `BUNDLE_GEMFILE`, `RUBYOPT`, `PATH`) in its environment. When the git transport invokes `ssh` and a credential prompt occurs, the named program is executed on the Shipit deploy host — Remote Code Execution matching the Critical "RCE on the deploy host via Command/PTY.spawn" category. Because the injected keys are entirely attacker-chosen (any label name, uppercased) and unfiltered, the blast radius extends beyond `SSH_ASKPASS` to any environment variable capable of influencing subprocess behavior for that stack's git and deploy-spec-driven commands. This is repeatable on every PR event for any repository that has review stacks enabled and permits the attacker to label PRs.

### Likelihood Explanation
Preconditions: the target repository must have review stacks enabled (`repository.review_stacks_enabled`), and the attacker must be able to apply a label (GitHub restricts label creation/application to users with triage/write access on the repository, unless label permission is otherwise granted — the specified threat model treats "label their own PR" as an available capability). Given that precondition, the cost is a single API/webhook interaction (adding a label), no Shipit credentials are needed, and the effect recurs on every subsequent fetch/deploy-revision cycle for that stack. The actual RCE trigger additionally depends on the review stack's git remote using an ssh transport that prompts for credentials, which is an additional environment-specific condition not guaranteed by default GitHub HTTPS token-based fetches.

### Recommendation
Apply the same `EnvironmentVariables#permit` allowlist mechanism used for deploy/task/rollback variables to `ReviewStack#env`/`StackCommands#env`: build labels into a namespaced, non-overriding hash (e.g. prefixed like `SHIPIT_LABEL_<NAME>`) and/or explicitly strip or reject any label-derived key that collides with a reserved/sensitive environment variable name (`SSH_ASKPASS`, `GIT_ASKPASS`, `LD_PRELOAD`, `LD_LIBRARY_PATH`, `PATH`, `BUNDLE_GEMFILE`, `RUBYOPT`, etc.) before merging into `Commands#env`/`Command#unbundled_env`.

### Proof of Concept
In `test/lib/shipit/stack_commands_test.rb` (or equivalent):
```ruby
test "#fetch_deployed_revision's Command does not forward attacker-controlled SSH_ASKPASS from PR labels" do
  stack = shipit_stacks(:review_stack)
  stack.pull_request.labels = ["ssh_askpass"]
  # binding under test: StackCommands#env should NOT contain a raw key equal to a sensitive process env var
  commands = Shipit::StackCommands.new(stack)
  refute commands.env.key?("SSH_ASKPASS"),
    "expected SSH_ASKPASS to be filtered/stripped, but it leaked from PR label 'ssh_askpass'"

  # further confirm it would reach the actual git subprocess env
  cmd = Shipit::Command.new("git rev-parse HEAD", env: commands.env, chdir: stack.git_path)
  refute cmd.unbundled_env.key?("SSH_ASKPASS")
end
```
Currently this assertion fails: `commands.env["SSH_ASKPASS"] == "true"` and `cmd.unbundled_env["SSH_ASKPASS"] == "true"`, confirming the unfiltered binding described above.

      else
        @stack.clear_git_cache!
        git_clone(@stack.repo_git_url, @stack.git_path, branch: @stack.branch, env:, chdir: @stack.deploys_path)
      end

    def fetched?(commit)
      if valid_git_repository?(@stack.git_path)
        git('rev-parse', *quiet_git_arg, '--verify', "#{commit.sha}^{commit}", env:, chdir: @stack.git_path)
      else
        # When the stack's git cache is not valid, the commit is
        # NOT fetched. To keep the interface of this method
        # consistent, we must return a Shipit::Command whose #success?
        # method returns false - has a non-zero exit status. We utilize
        # the POSIX 'test' command with no arguments which should
        # always have an exit status of 1.
        Command.new('test', env:, chdir: @stack.deploys_path)
      end
    end

    def fetch_deployed_revision
      with_temporary_working_directory(commit: @stack.commits.reachable.last) do |dir|
        spec = DeploySpec::FileSystem.new(dir, @stack)
        outputs = spec.fetch_deployed_revision_steps!.map do |command_line|
          Command.new(command_line, env:, chdir: dir).run
        end
        outputs.find(&:present?).try(:strip)
      end
    end
