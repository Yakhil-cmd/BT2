### Title
`GIT_SSH` injection via unsanitized pull-request label names reaching `Command#start`/`PTY.spawn` in the `dependencies.override` phase - (File: app/models/shipit/review_stack.rb)

### Summary
`ReviewStack#env` merges every pull-request label name (uppercased) directly into the stack's environment hash with no allowlist, and this hash is merged straight into `TaskCommands#env`, which becomes the actual process environment passed to `Command#start` → `PTY.spawn`. Because `dependencies_steps!` (the `dependencies.override` phase) runs through `Command.new(command_line, env:, ...)` using this unfiltered environment, an attacker who can label their own fork PR (e.g. label `git_ssh`) can set `GIT_SSH` to name an arbitrary program that `git` will invoke for SSH transport during the dependency-install phase.

### Finding Description
The broken binding: the invariant that should hold is `stack.env.keys ⊆ deploy_variables.map(&:name)` for anything reaching `Command#start`, i.e. every environment key delivered to a spawned process must have passed through `EnvironmentVariables#permit`. This does not hold for `ReviewStack`-derived keys.

- `ReviewStack#env` (`app/models/shipit/review_stack.rb:84-93`) does: `super.merge(pull_request.labels.each_with_object({}) { |label_name, labels| labels[label_name.upcase] = "true" })`. There is no allowlist check here — any label name becomes an environment variable key. [1](#0-0) 
- Labels originate from the webhook payload and are persisted verbatim by `LabelCapturingHandler#capture_labels` (`app/models/shipit/webhooks/handlers/pull_request/label_capturing_handler.rb`), which is reachable by any user who can open/label a PR on a repo configured with `provisioning_behavior: allow_with_label`. [2](#0-1) 
- `TaskCommands#env` (`lib/shipit/task_commands.rb:33-48`) does `super.merge(@stack.env).merge(...)`, directly incorporating the unsanitized `ReviewStack#env` hash — there is no call to `filter_deploy_envs`/`EnvironmentVariables#permit` on `@stack.env` at this point. [3](#0-2) 
- `install_dependencies` (the `dependencies.override` phase) builds `Command.new(command_line, env:, chdir: steps_directory)` using exactly this `env`. [4](#0-3) 
- `Command#start` calls `PTY.spawn(unbundled_env, *interpolated_arguments, ...)`, and `unbundled_env` is `BASE_ENV.merge('PATH' => ...).merge(@env.stringify_keys)` — so any key set via `@env` (which includes the attacker's uppercased label) overrides/adds to the process environment used to execute `git` and other dependency-install commands. [5](#0-4) 

Why existing guards fail: `EnvironmentVariables#permit` (`lib/shipit/environment_variables.rb:13-18`) exists and is used to sanitize *explicit user-supplied* env params for deploy/task/rollback triggers (`DeploySpec#filter_deploy_envs`, `#filter_rollback_envs`, `TaskDefinition#filter_envs`) — confirmed by controller tests (`test/controllers/api/deploys_controller_test.rb`, `test/controllers/api/tasks_controller_test.rb`) which show `DANGEROUS_VARIABLE` being rejected. However, this filtering path is never applied to `@stack.env`/`ReviewStack#env`, which is merged into `TaskCommands#env` unconditionally. `dependencies_steps!` reads `dependencies.override` from the fork's own `shipit.yml`, which an unprivileged fork owner fully controls under `allow_with_label`.

### Impact Explanation
An attacker who owns a fork, opens a PR against a repo configured with `provisioning_behavior: allow_with_label`, adds a label such as `git_ssh` (becomes `GIT_SSH=true` — or crafts a label whose uppercase form is a plausible path/command string subject to Shellwords/label content constraints on GitHub), and defines a `dependencies.override` step that invokes `git` (e.g. `git submodule update`, `bundle install` with a git source, etc.) in their fork's `shipit.yml`, can cause `git` to execute an attacker-named program for SSH transport during the review-stack dependency-install phase on the Shipit deploy host. This is Remote Code Execution on the deploy host, matching the Critical severity class described (`Command`/`PTY.spawn` RCE). The blast radius is scoped to the review stack's build (same host, same worker), but the underlying flaw — unsanitized `stack.env` reaching `Command#start` — is a structural violation of the intended env-sanitization invariant.

### Likelihood Explanation
Preconditions: the target repository must have review stacks enabled with `provisioning_behavior: allow_with_label` (a documented, non-default but legitimate configuration), and the fork's `shipit.yml` must define a `dependencies.override` step that shells out to `git` (very common, since dependency installation frequently involves git-based sources). The attacker needs no Shipit credentials — only the ability to open a PR from their own fork and add a label to it, which any GitHub user can do on a public repo accepting PRs. This is a low-cost, repeatable action; the label can be toggled/reused on each new PR.

### Recommendation
In `ReviewStack#env` (or better, in `TaskCommands#env`/`Stack#env`), route pull-request-label-derived environment variables through an explicit allowlist (e.g. `EnvironmentVariables#permit` against a curated, non-shell-sensitive set of label names) before merging, and unconditionally strip/reject any key that overlaps with sensitive process-affecting variables such as `GIT_SSH`, `GIT_SSH_COMMAND`, `LD_PRELOAD`, `BUNDLE_GEMFILE`, `PATH`, etc. Alternatively, namespace label-derived vars with a fixed, safe prefix (e.g. `LABEL_<NAME>`) so they can never collide with security-relevant environment variable names consumed by `git`/`bundler`.

### Proof of Concept
minitest plan (`test/models/shipit/review_stack_test.rb` or `test/lib/shipit/task_commands_test.rb`):
```ruby
test "[allow_with_label] GIT_SSH via PR label reaches dependencies.override Command env" do
  stack = shipit_review_stacks(:some_review_stack) # or build one with provisioning_behavior: allow_with_label
  pull_request = stack.pull_request
  pull_request.update!(labels: ["git_ssh"]) # simulates LabelCapturingHandler#capture_labels persisting webhook labels verbatim

  assert_equal "true", stack.env["GIT_SSH"] # LHS: attacker-controlled label; RHS: value in stack.env — should NOT be equal / GIT_SSH should not exist

  task_commands = TaskCommands.new(shipit_tasks(:review_stack_task))
  commands = task_commands.install_dependencies # dependencies.override phase
  commands.each do |command|
    assert_nil command.env["GIT_SSH"], "GIT_SSH must not leak into dependencies.override Command env"
  end
end
```
This demonstrates the equality `stack.env["GIT_SSH"] == "true"` (attacker-set) propagating unchanged into `command.env["GIT_SSH"]` for the `dependencies.override` step, violating the intended invariant that no fork-controllable key reaches `Command#start`.

    def start(&block)
      return if @started

      @control_block = block
      @out = @pid = nil
      FileUtils.mkdir_p(@chdir)
      begin
        @out, child_in, @pid = PTY.spawn(unbundled_env, *interpolated_arguments, chdir: @chdir)
        child_in.close
      rescue Errno::ENOENT
        raise NotFound, "#{Shellwords.split(interpolated_arguments.first).first}: command not found"
      rescue Errno::EACCES
        raise Denied, "#{Shellwords.split(interpolated_arguments.first).first}: Permission denied"
      end
      @started = true
      self
    end

    def unbundled_env
      BASE_ENV.merge('PATH' => "#{Shipit.shell_paths.join(':')}:#{ENV['PATH']}").merge(@env.stringify_keys)
    end
