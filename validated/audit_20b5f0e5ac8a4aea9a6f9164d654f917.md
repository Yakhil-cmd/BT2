### Title
Webhook signature is verified against an organization derived from unsigned payload fields, decoupled from the repository actually written to - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App / webhook secret to validate the request against using an organization name pulled straight out of the untrusted JSON body, while the event handlers that follow act on a `repository.full_name` field from that same untrusted body to locate the `Repository`/`Stack` to write to. Because the field used to pick the verifying secret (`repository.owner.login` / `organization.login`) is independent of the field used to determine which repository is actually mutated (`repository.full_name`), a party who legitimately controls a GitHub App installation for one organization can forge a payload whose HMAC is valid for their own org while the payload content targets a stack belonging to a different organization/repository.

### Finding Description
`WebhooksController#verify_signature` resolves the app config via: [1](#0-0) 
using `repository_owner`, computed as: [2](#0-1) 

`Shipit.github(organization:)` looks up the webhook secret keyed purely by that organization string: [3](#0-2) 

`verify_webhook_signature` then HMACs the *entire* raw request body against the secret for whichever organization was extracted from `params.dig('repository','owner','login')`: [4](#0-3) 

Once the signature check passes, `create` dispatches the full, attacker-supplied `params` (not scoped to the verified organization) to the registered handlers: [5](#0-4) 

The equality the design implicitly relies on is:

`organization used to select/verify the webhook secret == organization that owns the repository the handlers subsequently write to`

Nothing in `WebhooksController` enforces this. `repository.owner.login` and `repository.full_name` are both attacker-controlled JSON fields inside the same signed blob, but the controller only uses `owner.login` to pick the secret — it never cross-checks that `full_name`'s owner matches `owner.login`. A party that operates their own legitimate GitHub App installation on organization `attacker-org` (and therefore knows/derives the correct HMAC for payloads verified against `attacker-org`'s secret) can construct a JSON body where:
- `repository.owner.login` = `"attacker-org"` (used only for secret selection)
- `repository.full_name` = `"victim-org/victim-repo"` (used by the handlers, e.g. `GithubSyncJob`, `Status` creation, `check_suite` processing, membership/team handlers) to resolve the actual `Repository`/`Stack`/`Commit` records to mutate.

Since the HMAC covers the raw body verbatim and is checked against `attacker-org`'s secret, the signature check passes even though the mutated data belongs to a repository under a different (victim) organization.

### Impact Explanation
This breaks the trust boundary between "who authenticated the webhook" and "what repository is written." A `push` event handled with a forged `full_name` can enqueue `GithubSyncJob` for a stack belonging to `victim-org`, and `status`/`check_suite` handlers can inject fabricated commit statuses/check runs for that repository, all under a webhook signature that only proves control of a *different* organization's secret. This is a cross-repository/cross-organization write achieved without ever compromising the victim's webhook secret, matching the "Critical - cross-repository writes" impact bucket.

### Likelihood Explanation
The attacker precondition is owning a legitimate GitHub App installation (and its webhook secret) for *some* organization onboarded to the same Shipit instance — a low bar for any multi-tenant deployment (the very use case `github_app_config`/`TOP_LEVEL_GH_KEYS` supports). No repository write access, API token, or session is required; only the ability to send an HTTP POST with a correctly-HMAC'd body to `/webhooks`, matching the "unprivileged attacker" model in scope.

### Recommendation
After signature verification, re-derive the trusted organization from the same source used for verification and enforce that every repository-scoped write the handler performs is scoped to `repository.full_name` whose owner matches the verified organization (or, simpler, verify the signature independently per possible org config and require the resolved `Repository`/`Stack.repository.owner` to equal the organization the secret belongs to before any handler runs).

### Proof of Concept
1. Attacker administers a legitimate GitHub App installation on `attacker-org`, with webhook secret `S_attacker` (a normal, permitted configuration in `github_app_config`).
2. Attacker crafts a `push` webhook JSON body:
```json
{
  "repository": {
    "full_name": "victim-org/victim-repo",
    "owner": { "login": "attacker-org" }
  },
  "after": "<sha>",
  "ref": "refs/heads/main"
}
```
3. Attacker computes `sha1=HMAC(S_attacker, body)` and sends it as `X-Hub-Signature`.
4. `WebhooksController#repository_owner` returns `"attacker-org"`; `Shipit.github(organization: "attacker-org")` loads `S_attacker`; `verify_webhook_signature` succeeds.
5. `create` dispatches the full body to `Shipit::Webhooks.for_event('push')`, whose handler resolves the target stack via `repository.full_name` = `"victim-org/victim-repo"`, enqueuing a `GithubSyncJob` (or equivalent write) against the victim's stack — despite the request never having been signed by `victim-org`'s secret.

Note: I was unable to fully inspect `app/models/shipit/webhooks/handlers/push_handler.rb` before running out of tool iterations to confirm the exact field it uses to resolve the `Stack`/`Repository` (it should be verified that it indeed keys off `repository.full_name` rather than a value cross-checked against the verified organization); this should be confirmed in a follow-up session with full file access.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
