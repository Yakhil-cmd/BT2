### Title
Interrupted `publishSymlink` leaves an orphaned `tmp-link` that permanently blocks all future publishes - (File: main.go)

### Summary
`git-sync`'s atomic-publish mechanism (analogous to ZetaChain's "revert" step that is supposed to safely restore state after a failed operation) can be left in an unrecoverable, half-completed state if the second of its two filesystem operations fails or the process is interrupted between them. Unlike ZetaChain's `onRevert`, which aborts the CCTX with no path back to a working state, `publishSymlink` has no self-healing/cleanup step, so the same failure recurs on every subsequent sync attempt, permanently denying legitimate publishes.

### Finding Description
`publishSymlink` performs the atomic symlink flip in two separate steps using a hard-coded temporary name `tmp-link`, with no attempt to clean up or overwrite a pre-existing `tmp-link` before creating a new one: [1](#0-0) 

```go
const tmplink = "tmp-link"
git.log.V(2).Info("creating tmp symlink", "dir", linkDir, "link", tmplink, "target", targetRelative)
if err := os.Symlink(targetRelative, filepath.Join(linkDir.String(), tmplink)); err != nil {
    return fmt.Errorf("error creating symlink: %w", err)
}

git.log.V(2).Info("renaming symlink", "root", linkDir, "oldName", tmplink, "newName", linkFile)
if err := os.Rename(filepath.Join(linkDir.String(), tmplink), git.link.String()); err != nil {
    return fmt.Errorf("error replacing symlink: %w", err)
}
```

If the process crashes, is OOM-killed, or the `os.Rename` call fails (e.g., due to a transient EXDEV/permission/disk-full error, or the target filesystem becoming temporarily read-only) after `os.Symlink` has already succeeded, the `tmp-link` path is left on disk. On the very next sync loop iteration, `publishSymlink` is invoked again and calls `os.Symlink(...)` targeting the same `tmp-link` name. `os.Symlink` unconditionally fails with `EEXIST` if the target path already exists, so every subsequent publish attempt fails identically and permanently, even after the original transient cause (disk full, filesystem hiccup, permission blip) has resolved.

This mirrors the structural flaw in the ZetaChain report: an operation meant to "revert"/re-publish state has a failure branch with no recovery path, and the system latches into a permanently broken state rather than retrying or self-healing.

Compare this to how `createWorktree` explicitly guards against exactly this kind of "wedge" scenario by calling `git.removeWorktree` before creating a new worktree: [2](#0-1) 

`publishSymlink` has no equivalent guard, and callers (`SyncRepo`'s main loop) never attempt to clean up `tmp-link` on the retry path: [3](#0-2) 

### Impact Explanation
This falls under "persistent sync denial." Once the orphaned `tmp-link` exists, `git-sync` can never publish a new revision again — not even after the underlying transient I/O issue is resolved — until an operator manually intervenes to delete the stray file from `--root`'s link directory. In a Kubernetes sidecar deployment, this means the pod will report failures indefinitely (subject to `--max-failures`, potentially causing the container to exit and CrashLoopBackOff, or to keep retrying forever with `--max-failures=-1`), and the application never receives repository updates again despite the git-sync process appearing to be "running."

### Likelihood Explanation
Triggering requires an interruption exactly between the `os.Symlink` and `os.Rename` calls — e.g., a pod eviction/OOM-kill, SIGKILL, or a transient filesystem error on the `os.Rename` step (cross-device link, disk full, permission edge case, or an EXDEV situation when `--root` and `--link` are on different volumes/mounts, which is a realistic Kubernetes configuration with separate `emptyDir` mounts). This is a plausible operational fault rather than something a remote/untrusted git server can directly force deterministically, but it is reachable without any special privileges — any process crash or storage hiccup at the wrong moment suffices, and there is no attacker-controlled ref/commit content needed to hit it, only timing.

### Recommendation
Make `publishSymlink` idempotent and self-healing:
1. Before creating the temporary symlink, remove any pre-existing `tmp-link` (`os.RemoveAll` or `os.Remove` ignoring `ErrNotExist`), the same way `createWorktree` pre-emptively removes a stale worktree directory.
2. Alternatively, use a unique/randomized temp name per attempt (e.g. via `os.MkdirTemp`-style unique suffix) and clean up any orphaned temp links found during `cleanup()`/`removeDirContentsIf`.
3. Ensure `--root` and `--link` directories are documented/enforced to be on the same filesystem to avoid `EXDEV` on `os.Rename`.

### Proof of Concept
1. Start `git-sync` normally so an initial sync/publish succeeds.
2. Simulate an interruption between the two filesystem operations, e.g. by pre-creating the file the code will try to create:
   ```
   ln -s bogus "$ROOT/tmp-link"
   ```
3. Trigger a new sync (e.g., push a new commit to the source repo).
4. Observe `publishSymlink` fails with `error creating symlink: ... file exists` on this and all subsequent sync attempts, even though the underlying repository state and connectivity are healthy — the publish path is permanently wedged until `tmp-link` is manually removed from `--root`.

func (git *repoSync) createWorktree(ctx context.Context, hash string) (worktree, error) {
	// Make a worktree for this exact git hash.
	worktree := git.worktreeFor(hash)

	// Avoid wedge cases where the worktree was created but this function
	// error'd without cleaning up.  The next time thru the sync loop fails to
	// create the worktree and bails out. This manifests as:
	//     "fatal: '/repo/root/nnnn' already exists"
	if err := git.removeWorktree(ctx, worktree); err != nil {
		return "", err
	}

	git.log.V(1).Info("adding worktree", "path", worktree.Path(), "hash", hash)
	_, _, err := git.Run(ctx, git.root, "worktree", "add", "--force", "--detach", worktree.Path().String(), hash, "--no-checkout")
	if err != nil {
		return "", err
	}

	return worktree, nil
}
