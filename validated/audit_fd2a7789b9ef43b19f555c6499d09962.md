### Title
Unauthenticated Initiator in `onERC20Received` / `onERC721Received` Bridge Callbacks Allows Spoofed `_from` to Drain Counterpart Bridge — (`contracts/service_chain/bridge/BridgeTransferERC20.sol`, `contracts/service_chain/bridge/BridgeTransferERC721.sol`)

---

### Summary

`BridgeTransferERC20.onERC20Received` and `BridgeTransferERC721.onERC721Received` are 1-step deposit callbacks that verify `msg.sender` is a registered token but never verify that `_from` is the address that actually initiated the token transfer. Any registered token contract can call these callbacks directly with an arbitrary `_from`, causing the bridge to emit a `RequestValueTransfer` / `RequestValueTransferEncoded` event crediting the wrong originator. The off-chain bridge operator faithfully relays this event to the counterpart bridge, which then transfers or mints bridged assets to the attacker-controlled `_to` address — without the attacker having deposited anything (in lock/unlock mode).

---

### Finding Description

**`onERC20Received`** (the 1-step ERC-20 deposit callback):

```solidity
// BridgeTransferERC20.sol line 111-121
function onERC20Received(
    address _from,   // ← caller-supplied, never verified
    address _to,
    uint256 _value,
    uint256 _feeLimit,
    bytes memory _extraData
)
    public            // ← no access control
{
    _requestERC20Transfer(msg.sender, _from, _to, _value, _feeLimit, _extraData);
}
```

`_requestERC20Transfer` applies `onlyRegisteredToken(msg.sender)` — it checks the *caller* is a registered token, but it never checks that `_from` is the address that actually sent tokens to the bridge. [1](#0-0) 

In lock/unlock mode (`modeMintBurn == false`), `_requestERC20Transfer` does **not** burn or pull any tokens — it only emits the event and increments `requestNonce`:

```solidity
// BridgeTransferERC20.sol line 76-108
function _requestERC20Transfer(...) internal onlyRegisteredToken(_tokenAddress) ... {
    ...
    uint256 fee = _payERC20FeeAndRefundChange(_from, _tokenAddress, _feeLimit);
    // modeMintBurn == false → no burn, no transferFrom
    emit RequestValueTransfer(TokenType.ERC20, _from, _to, ...);
    requestNonce++;
}
``` [2](#0-1) 

The same pattern exists in `BridgeTransferERC721.onERC721Received`:

```solidity
// BridgeTransferERC721.sol line 109-118
function onERC721Received(
    address _from,   // ← caller-supplied, never verified
    uint256 _tokenId,
    address _to,
    bytes memory _extraData
)
    public
{
    _requestERC721Transfer(msg.sender, _from, _to, _tokenId, _extraData);
}
``` [3](#0-2) 

The off-chain bridge operator in `bridge_manager.go` reads the emitted event and blindly passes `ev.GetFrom()` (the spoofed `_from`) to `HandleERC20Transfer` / `HandleERC721Transfer` on the counterpart bridge:

```go
// node/sc/bridge_manager.go line 339
handleTx, err = bi.bridge.HandleERC20Transfer(
    auth, txHash, from, to, ctpartTokenAddr, valueOrTokenId, requestNonce, blkNumber, extraData)
``` [4](#0-3) 

The counterpart bridge's `handleERC20Transfer` then mints or transfers tokens to `_to` without any further verification of the originating deposit:

```solidity
// BridgeTransferERC20.sol line 68-72
if (modeMintBurn) {
    require(ERC20Mintable(_tokenAddress).mint(_to, _value), "handleERC20Transfer: mint failed");
} else {
    IERC20(_tokenAddress).safeTransfer(_to, _value);
}
``` [5](#0-4) 

Additionally, `_payERC20FeeAndRefundChange` transfers fee-refund tokens from the bridge's own balance to the attacker-supplied `_from`:

```solidity
// BridgeFee.sol line 84-86
if (_feeLimit > 0) {
    IERC20(_token).safeTransfer(from, _feeLimit);
}
``` [6](#0-5) 

---

### Impact Explanation

**Lock/unlock mode (most severe):** The attacker's registered token contract calls `onERC20Received(victim_or_attacker_EOA, attacker_EOA, large_value, 0, "")` without transferring any tokens to the bridge. The bridge emits `RequestValueTransfer` with `from = victim, to = attacker_EOA, value = large_value`. The off-chain operator relays this to the counterpart bridge, which transfers `large_value` counterpart tokens from its reserves to `attacker_EOA`. The attacker deposits nothing and receives real bridged assets — a direct unauthorized transfer of bridged funds.

**Mint/burn mode:** The attacker mints tokens to the bridge (they control the token contract), then calls `onERC20Received` to burn them and trigger a mint of `large_value` counterpart tokens to `attacker_EOA` on the other chain.

**Fee-refund theft:** If `_feeLimit > 0` and `feeOfERC20[token] == 0`, the bridge transfers `_feeLimit` tokens from its own balance to the attacker-supplied `_from` address.

The corrupted values are: the `from` field in `RequestValueTransfer` / `RequestValueTransferEncoded` events, the counterpart bridge's token reserves (drained), and the bridge's own token balance (fee refund path).

---

### Likelihood Explanation

The trigger requires `msg.sender` to be a registered token (`onlyRegisteredToken`). Token registration is `onlyOwner` (`BridgeTokens.registerToken`). [7](#0-6)  This makes the attacker a semi-trusted entity: the bridge owner must have registered the token, but the token contract itself is a separate, independently-controlled address. A malicious or compromised registered token contract — or any contract that can trigger a call from a registered token address — can execute this attack without any further privilege. The 1-step deposit design explicitly expects external token contracts to call `onERC20Received`, making this surface reachable in normal operation.

---

### Recommendation

Add an initiator check analogous to the flash-loan fix: verify that `_from` matches the address that actually transferred tokens. The safest fix is to not accept `_from` as a parameter at all and instead derive it from the token transfer itself, or require the token contract to pass `msg.sender` (the actual transferring account) and verify it on-chain. At minimum, add a guard:

```solidity
// In onERC20Received:
function onERC20Received(
    address _from,
    address _to,
    uint256 _value,
    uint256 _feeLimit,
    bytes memory _extraData
) public {
    // Verify the token actually transferred _value + _feeLimit to this bridge
    // before this call, e.g. by checking balance delta, or restrict _from
    // to be verifiable via the token's own transfer record.
    require(_from != address(0), "zero from");
    // Ideally: require that msg.sender (the token) recorded _from as the sender
    _requestERC20Transfer(msg.sender, _from, _to, _value, _feeLimit, _extraData);
}
```

The cleanest fix is to have the token contract pass `msg.sender` as `_from` (as `ERC721ServiceChain.requestValueTransfer` already does correctly at line 46) and enforce this on the bridge side by requiring the token to attest to the sender rather than accepting an arbitrary address. [8](#0-7) 

---

### Proof of Concept

1. Bridge owner deploys bridge in lock/unlock mode (`modeMintBurn = false`) and registers `MaliciousToken` at address `0xMAL`.
2. Counterpart bridge holds 1,000,000 units of `CounterpartToken` in reserve.
3. Attacker (who controls `0xMAL`) calls:
   ```solidity
   // From MaliciousToken contract (msg.sender == 0xMAL, a registered token)
   IBridge(bridgeAddress).onERC20Received(
       address(0xDEAD),   // spoofed _from (victim or any address)
       address(attacker), // _to = attacker's EOA on counterpart chain
       1_000_000,         // _value
       0,                 // _feeLimit
       ""
   );
   ```
   No tokens are transferred to the bridge.
4. Bridge emits `RequestValueTransfer(ERC20, 0xDEAD, attacker, 0xMAL, 1_000_000, nonce, 0, "")`.
5. Off-chain bridge operator (`handleRequestValueTransferEvent`) reads the event and calls `HandleERC20Transfer(txHash, 0xDEAD, attacker, counterpartToken, 1_000_000, nonce, blockNum, "")` on the counterpart bridge.
6. Counterpart bridge executes `IERC20(counterpartToken).safeTransfer(attacker, 1_000_000)`.
7. Attacker receives 1,000,000 counterpart tokens having deposited zero. Counterpart bridge reserves are drained. [1](#0-0) [3](#0-2) [9](#0-8)

// handleRequestValueTransferEvent handles the given request value transfer event.
func (bi *BridgeInfo) handleRequestValueTransferEvent(ev IRequestValueTransferEvent) error {
	var (
		tokenType                         = ev.GetTokenType()
		tokenAddr, from, to, contractAddr = ev.GetTokenAddress(), ev.GetFrom(), ev.GetTo(), ev.GetRaw().Address
		txHash                            = ev.GetRaw().TxHash
		valueOrTokenId                    = ev.GetValueOrTokenId()
		requestNonce, blkNumber           = ev.GetRequestNonce(), ev.GetRaw().BlockNumber
		extraData                         = ev.GetExtraData()
	)

	ctpartTokenAddr := bi.GetCounterPartToken(tokenAddr)
	// TODO-Kaia-Servicechain Add counterpart token address in requestValueTransferEvent
	if tokenType != KAIA && ctpartTokenAddr == (common.Address{}) {
		logger.Warn("Unregistered counter part token address.", "addr", ctpartTokenAddr.Hex())
		ctTokenAddr, err := bi.counterpartBridge.RegisteredTokens(nil, tokenAddr)
		if err != nil {
			return err
		}
		if ctTokenAddr == (common.Address{}) {
			return errors.New("can't get counterpart token from bridge")
		}
		if err := bi.RegisterToken(tokenAddr, ctTokenAddr); err != nil {
			return err
		}
		ctpartTokenAddr = ctTokenAddr
		logger.Info("Register counter part token address.", "addr", ctpartTokenAddr.Hex(), "cpAddr", ctTokenAddr.Hex())
	}

	bridgeAcc := bi.account

	bridgeAcc.Lock()
	defer bridgeAcc.UnLock()

	auth := bridgeAcc.GenerateTransactOpts()

	var handleTx *types.Transaction
	var err error

	switch tokenType {
	case KAIA:
		handleTx, err = bi.bridge.HandleKLAYTransfer(auth, txHash, from, to, valueOrTokenId, requestNonce, blkNumber, extraData)
		if err != nil {
			return err
		}
		handleValueTransferLog(bi.onChildChain, handleVTmethods[KAIA], handleTx.Hash().String(), requestNonce, from, to, valueOrTokenId)
	case ERC20:
		handleTx, err = bi.bridge.HandleERC20Transfer(auth, txHash, from, to, ctpartTokenAddr, valueOrTokenId, requestNonce, blkNumber, extraData)
		if err != nil {
			return err
		}
		handleValueTransferLog(bi.onChildChain, handleVTmethods[ERC20], handleTx.Hash().String(), requestNonce, from, to, valueOrTokenId)
	case ERC721:
		uri := GetURI(ev)
		handleTx, err = bi.bridge.HandleERC721Transfer(auth, txHash, from, to, ctpartTokenAddr, valueOrTokenId, requestNonce, blkNumber, uri, extraData)
		if err != nil {
			return err
		}
		handleValueTransferLog(bi.onChildChain, handleVTmethods[ERC721], handleTx.Hash().String(), requestNonce, from, to, valueOrTokenId)
	default:
		logger.Error("Got Unknown Token Type ReceivedEvent", "bridge", contractAddr, "nonce", requestNonce, "from", from)
		return nil
	}

	bridgeAcc.IncNonce()

	bi.bridgeDB.WriteHandleTxHashFromRequestTxHash(txHash, handleTx.Hash())
	return nil
}
