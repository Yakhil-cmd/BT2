### Title
CCMenu API token authorizes only its bound stack, but `Api::CCMenuController#show` reads whichever stack is named in the URL - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Api::CCMenuController` re-implements stack lookup instead of using `Api::BaseController#stacks`, so the stack an `ApiClient` token is entitled to (its `stack_id` column) is never compared against the `:stack_id` requested in the URL. Any valid `read:stack` token — including the unscoped one minted per-user by `CCMenuUrlController` — can be replayed against `/api/*/ccmenu` for an arbitrary stack path to read that stack's latest deploy/build state.

### Finding Description
`Api::BaseController` is designed so every sub-resource is fetched through a scope-checked accessor: [1](#0-0) [1](#0-0) 

```
def stacks
  @stacks ||= current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all
end

def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```

This is the intended equality that binds the authenticated credential to the resource it may touch: `token.stack_id == requested stack` (or `Stack.all` only for globally-scoped clients).

`Api::CCMenuController`, however, overrides `stack` to bypass that scope entirely: [2](#0-1) 

```
private

def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end

def authenticate_api_client
  @current_api_client = ApiClient.authenticate(params[:token])
  super unless @current_api_client
end
```

Authorization is only checked at the permission-scope level (`require_permission :read, :stack`), which just verifies the string `"read:stack"` is in the client's permission list: [3](#0-2) 

It never checks whether `current_api_client.stack_id` (if set) matches the `stack` being rendered. So the equality that should hold — "the stack a token authorizes" == "the stack it touches" — is broken specifically for this endpoint: any `ApiClient` with `read:stack` permission can be pointed at any `stack_id` path segment and will render that stack's CCMenu XML.

This is compounded by how the primary caller mints these tokens. `CCMenuUrlController#client` creates (or reuses) a single, **unscoped** (`stack: nil`) `ApiClient` per user, regardless of which stack's CCMenu URL was requested: [4](#0-3) 

```
def client
  @client ||= ApiClient.create_with(permissions: %w[read:stack])
                       .find_or_create_by!(creator: current_user, name: 'CCMenu Client')
end
```

Because `stack_id` is never set on this token, `current_api_client.stack_id?` is `false`, so even the (unused, in this controller) `stacks` scope would resolve to `Stack.all`. Combined with the bypass in `CCMenuController#stack`, the token embedded in a single stack's "CCMenu URL" (a URL commonly copy-pasted into CI dashboards / CCMenu-compatible clients, which is a bearer-credential-in-URL by design) in practice grants read access to every stack in the installation, not just the one it was generated for.

### Impact Explanation
This is an unauthenticated (bearer-token-only) read of stack/task state across stacks the token holder was never meant to see — matches the "High: unauthenticated read of stack state, task streams, or deploy output" category. A token/URL generated for (and expected to be scoped to) one stack's build-status widget lets the holder enumerate `/api/<owner>/<repo>/<env>/ccmenu` for every other stack in the Shipit instance and retrieve `deploy.id`, `ended_at`, `running?`/status information for the latest deploy or rollback.

### Likelihood Explanation
No special privilege is required beyond possessing any valid `read:stack` `ApiClient` token — in the default flow this is trivially obtained by any authenticated Shipit user visiting a single stack's settings page (which auto-creates/returns the CCMenu client and URL). No signature or secret needs to be forged; the attacker simply changes the `stack_id` path segment on an otherwise legitimate, already-signed token/URL. This requires no cooperation from other privileged parties and no changes to how the app is mounted.

### Recommendation
Make `Api::CCMenuController#stack` go through the scope-aware `stacks` accessor (i.e., remove the override, or replace `Stack.from_param!` with `stacks.from_param!`) so that a client bound to a specific `stack_id` cannot resolve any other stack. Additionally, consider having `CCMenuUrlController#client` mint a token scoped to the specific stack (`stack: stack`) rather than an unscoped, shared token per user, so a leaked CCMenu URL only discloses the one stack it was generated for.

### Proof of Concept
1. As any authenticated Shipit user, request the CCMenu URL for stack `owner/repoA/production`:
   `GET /ccmenu/owner/repoA/production` → returns `{ "ccmenu_url": ".../api/owner/repoA/production/ccmenu?token=<TOKEN>" }`, where `<TOKEN>` is `ApiClient#authentication_token` for a client with `permissions: ["read:stack"]` and `stack_id: nil` (per `CCMenuUrlController#client`, [5](#0-4) ).
2. Reuse `<TOKEN>` against an unrelated stack the requester should not be able to introspect via this credential:
   `GET /api/owner/repoB/staging/ccmenu?token=<TOKEN>`
3. `Api::CCMenuController#authenticate_api_client` accepts the token (still a valid, signed `ApiClient`), and `#stack` ( [6](#0-5) ) resolves `repoB/staging` directly via `Stack.from_param!`, with no comparison to any stack the token was intended for. The response renders `repoB/staging`'s latest deploy/rollback status even though the token/URL was minted for `repoA/production`.
