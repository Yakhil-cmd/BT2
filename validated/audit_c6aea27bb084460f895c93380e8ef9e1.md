Based on my investigation, `objAuthor.authentifiers[path]` values are validated to be non-empty strings at [1](#0-0) , and merkle-proof strings evaluated via `is_valid_merkle_proof` in formulas are wrapped in try/catch at [2](#0-1) . ### Title
Unhandled exception / invalid state via malformed merkle proof in `'in merkle'` address-definition condition - (File: definition.js)

### Summary
The `'in merkle'` operator in address/asset definitions lets an address owner require an authentifier to be a serialized merkle proof matching a data-feed root. When evaluating this operator, `definition.js` passes the attacker/author-controlled authentifier string directly into `merkle.deserializeMerkleProof()` without validating its structure, and the resulting object is used with no sanity checks on `index`/`siblings`/`root` types before being passed to `dataFeeds.dataFeedExists()`.

### Finding Description
`merkle.deserializeMerkleProof()` blindly splits the serialized proof string on `"-"` and assigns `root`, `index`, `siblings` from whatever the split produces, with no verification that `index` is a valid integer or that `siblings` are well-formed hashes: [3](#0-2) .

In `definition.js`, the `'in merkle'` case in `validateAuthentifiers`'s `evaluate()` function takes `assocAuthentifiers[path]` (the attacker-supplied authentifier string for a signing path, only checked to be a non-empty string of bounded length in `validateAuthor` at [1](#0-0) ) and calls `merkle.deserializeMerkleProof(serialized_proof)` with **no try/catch**, unlike the analogous formula-evaluator code path which wraps the equivalent call in try/catch: [4](#0-3) .

While `verifyMerkleProof()` internally swallows exceptions via its own try/catch [5](#0-4) , a crafted `serialized_proof` (e.g., an unusual string of dashes) can produce a `proof.root` that is not a proper base64 hash string, or a `proof.index` string mismatch, which is then passed on to `dataFeeds.dataFeedExists(arrAddresses, feed_name, '=', proof.root, ...)` at line 1020, and potentially into SQL query parameters and later string operations expecting well-formed hash strings.

I was unable to fully trace whether `dataFeeds.dataFeedExists` performs additional validation on `proof.root` that would prevent a crash, since its implementation was not returned by my searches within the available iterations.

### Impact Explanation
If `dataFeeds.dataFeedExists()` (or any downstream code) throws on the malformed `proof.root` value, the exception is not caught anywhere in the `evaluate()` chain inside `validateAuthentifiers`, propagating up through unit/joint validation. In `network.js`, uncaught exceptions during message/joint handling trigger `process.on('uncaughtException')`, which deliberately re-throws to crash the node process: [6](#0-5) . This mirrors the CVE-2017-9470 bug class: a crafted, unprivileged input (here, a unit whose address definition uses `'in merkle'` and an authentifier of a specially crafted string) reaching an unguarded parsing/deserialization path that can trigger an unhandled exception and crash the process, denying service to the network.

### Likelihood Explanation
Exploitability requires: (1) an address definition containing an `'in merkle'` condition (attacker-controlled, since any unit poster can define arbitrary address definitions), and (2) an authentifier string at the corresponding path crafted to produce a malformed proof object. Because `validateAuthor` only checks the authentifier is a non-empty string under `MAX_AUTHENTIFIER_LENGTH`, an attacker has full control over its content, making the precondition trivially satisfiable by any unit poster.

### Recommendation
Wrap the `merkle.deserializeMerkleProof()` / subsequent processing in the `'in merkle'` case of `definition.js` in a try/catch (mirroring the pattern already used in `formula/evaluation.js`'s `is_valid_merkle_proof` handler), and additionally validate the deserialized proof's `root`, `index`, and `siblings` shape/types before using them, consistent with the defensive checks already applied elsewhere (e.g., `bPostPemCurvesFix` siblings validation at [7](#0-6) ).

### Proof of Concept
1. Attacker creates an address whose definition is `["in merkle", [["SOME_ORACLE_ADDR"], "feed_name", "expected_value"]]`.
2. Attacker posts a unit authored by this address, providing an authentifier string at path `r` that is a crafted, malformed value (e.g., containing unexpected characters or empty segments after splitting on `-`) so that `deserializeMerkleProof` produces a `proof.root`/`proof.index` of unexpected type/shape.
3. During validation, `definition.js`'s `'in merkle'` case calls `merkle.deserializeMerkleProof` and then `dataFeeds.dataFeedExists(..., proof.root, ...)` unguarded; if any downstream code throws on the malformed value, the exception is unhandled, and per `network.js`'s `uncaughtException` handler the node process crashes.

*Note: I could not directly confirm within the available search iterations whether `dataFeeds.dataFeedExists` throws on malformed `proof.root`/`min_mci` values — this is the key remaining uncertainty. Further verification against `data_feeds.js` would be needed to confirm the concrete crash trigger and finalize severity.*

function deserializeMerkleProof(serialized_proof){
	var arr = serialized_proof.split("-");
	var proof = {};
	proof.root = arr.pop();
	proof.index = arr.shift();
	proof.siblings = arr;
	return proof;
}

function verifyMerkleProof(element, proof){
	// Node-as-Leaf issue might matter in some cases
	try {
		var index = proof.index;
		var the_other_sibling = hash(element);
		for (var i = 0; i < proof.siblings.length; i++) {
			// this also works for duplicated trailing nodes
			if (index % 2 === 0)
				the_other_sibling = hash(the_other_sibling + proof.siblings[i]);
			else
				the_other_sibling = hash(proof.siblings[i] + the_other_sibling);
			index = Math.floor(index / 2);
		}
		return (the_other_sibling === proof.root);
	}
	catch (e){
		return false;
	}
