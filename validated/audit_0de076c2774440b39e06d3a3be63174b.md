### Title
Webhook signature is verified against `repository.owner.login`'s org secret while every handler mutates state keyed on the unchecked `repository.full_name` - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which `GithubApp`/`webhook_secret` to validate the HMAC signature against using `params.dig('repository','owner','login')`, but every handler under `app/models/shipit/webhooks/handlers/` (including the shared `Handler` base class) resolves the `Stack`/`Repository`/`Commit`/`Team` to mutate using `params.repository.full_name` (or `payload.dig('repository','full_name')`) with no comparison to `owner.login`. An attacker who controls a GitHub org/repo already integrated with this Shipit instance (and thus knows or can trigger that org's legitimate webhook delivery/secret) can set `repository.full_name` to any other org/repo string in the JSON body while keeping `repository.owner.login` equal to their own org, passing signature verification while causing writes against an arbitrary victim repository's stacks, commits, pull requests, or tasks.

### Finding Description
Binding claimed: `repository.owner.login == repository.full_name.split('/').first` must hold for the org that authenticates the webhook (via `webhook_secret`) to be the same org whose entities get mutated.

Trace:
- `WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-49`) computes `github_app = Shipit.github(organization: repository_owner)` where `repository_owner` (line 59-62) is `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` - fully attacker-controlled JSON, unauthenticated at this point. The chosen `github_app`'s `webhook_secret` is used to HMAC-verify the raw body [1](#0-0) , and `repository_owner` is derived purely from JSON, not any authenticated source [2](#0-1) .
- Once verified, `create` dispatches raw `params` unchanged to every registered handler for the event: `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` [3](#0-2) .
- The base `Handler` class resolves the target `stacks`/`repository_name` solely from `payload.dig('repository', 'full_name')`, never touching `owner.login` [4](#0-3) .
- Every concrete handler examined follows the same pattern - `Shipit::Repository.from_github_repo_name(params.repository.full_name)` - with no re-check of `owner.login`: `AssignedHandler#repository` [5](#0-4) , `ClosedHandler#repository` [6](#0-5) , `EditedHandler#repository` [7](#0-6) , `LabeledHandler#repository` [8](#0-7) , `UnlabeledHandler` (same pattern, truncated) [9](#0-8) , `OpenedHandler#repository` [10](#0-9) , `ReopenedHandler#repository` [11](#0-10) , and `LabelCapturingHandler#repository` [12](#0-11) .

Root cause: the ownership binding is checked once at the transport layer using one field (`owner.login`) but every downstream write authorizes itself against a second, independently attacker-controlled field (`full_name`), and nothing anywhere - not `ExplicitParameters` schemas (which only `requires :full_name, String` with no format/consistency constraint, e.g. `assigned_handler.rb:33-35`), not `Repository` model validations, not the handler base class - re-derives or cross-checks `owner.login` against `full_name`'s owner segment.

Exploit flow: attacker who administers their own GitHub org/repo already registered in this Shipit instance's config (and therefore is a legitimate holder of that org's webhook delivery channel) crafts (or replays with modification, if signature covers only the raw body they fully control as the sender since GitHub signs exactly the body they send from their own repo's webhook settings) a payload where `repository.owner.login = "attacker-org"` (whose secret they know/control) but `repository.full_name = "victim-org/victim-repo"`. `verify_signature` authenticates the request as legitimately from `attacker-org` and passes; the dispatched handler then loads `victim-org/victim-repo`'s `Repository`/`Stack`/`PullRequest`/`Commit` and performs the corresponding write (labels update, stack archive/unarchive, pull request record update, commit status write, etc.) against the victim's resource.

Existing guards do not stop this: `verify_signature` only checks the HMAC against the payload's *declared* owner, not against `full_name`; `drop_unhandled_event` only filters unknown event types; `ExplicitParameters` schemas validate types/presence, not cross-field consistency; `Repository`/`Stack` model validations don't reference the incoming `owner.login` at all.

### Impact Explanation
A payload signed/authenticated as belonging to one GitHub organization can trigger writes (archiving/unarchiving review stacks, updating `PullRequest` records, capturing labels, writing commit `Status`, mutating `Team`/`Membership` via the `membership` event path) against any other organization's `Stack`/`Commit`/`PullRequest`/`Team` records tracked by the same Shipit instance, as long as the attacker can produce a validly-signed webhook for at least one org onboarded to the instance. This is a cross-repository/cross-tenant write vulnerability - Critical per the "payload for one repository mutating another's stack, commit, task or team" category - and is systemic: every handler subclassing `Handler` inherits the same unchecked `full_name`-only resolution, so the flaw is not confined to a single event type.

### Likelihood Explanation
Preconditions: the attacker must be able to produce a signature that validates under `verify_webhook_signature` for at least one org registered in the Shipit instance's `Shipit.github(organization: ...)` config - i.e., they must own/administer a GitHub org/repo that is itself integrated with this Shipit instance (a realistic scenario for any multi-tenant or open-source Shipit deployment where multiple teams/orgs each configure their own webhook secret). Given that, the cost of exploitation is trivial: craft one JSON body with mismatched `owner.login`/`full_name`, no GitHub secrets, sessions, or API tokens required, and the attack is repeatable against any tracked victim repository/stack by simply changing `full_name` per request.

### Recommendation
In `WebhooksController#verify_signature` and/or in `Webhooks::Handlers::Handler`, enforce that `params.dig('repository','owner','login')` (the field used to select the authenticating `webhook_secret`) matches the owner segment parsed from `params.dig('repository','full_name')` before any handler is invoked; reject the request (e.g. `head(422)`) on mismatch. Alternatively, derive the authenticating organization exclusively from the trusted, single source of truth (`full_name`'s owner segment) rather than a separate `owner.login` field, eliminating the two-field divergence entirely.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (conceptual addition)
test "signature verified for owner A must not authorize writes on repository B" do
  victim_stack = shipit_stacks(:shipit) # full_name e.g. "shopify/shipit-engine"
  attacker_org = "attacker-org"

  Shipit.expects(:github).with(organization: attacker_org).returns(
    stub(verify_webhook_signature: true)
  )

  payload = JSON.parse(payload(:pull_request_labeled))
  payload["repository"]["owner"]["login"] = attacker_org       # authenticates as attacker-org
  payload["repository"]["full_name"] = victim_stack.repository.full_name # targets victim's repo

  @request.headers['X-Github-Event'] = 'pull_request'

  assert_no_difference -> { victim_stack.reload.archived? } do
    post :create, body: payload.to_json, as: :json
  end
  # Binding check: assert repository_owner-derived org == full_name owner segment, else reject/no-op
  assert_not_equal payload["repository"]["owner"]["login"],
                    payload["repository"]["full_name"].split("/").first
end
```
A parametrized variant would iterate `Shipit::Webhooks.handlers.values.flatten` (or explicitly enumerate each handler class under `app/models/shipit/webhooks/handlers/`), call `handler.call(payload)` directly with `owner.login` set to a dummy authenticated org and `full_name` set to a real fixture stack's repository, and assert no persisted record (`Stack`, `PullRequest`, `Commit`, `Team`) changes - demonstrating that none of the handlers independently re-validate `owner.login` against `full_name`.
