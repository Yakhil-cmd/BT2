### Title
Silently ignored transfer-result during bounty account migration can leave bounty funds permanently stranded - (File: system-parachains/asset-hubs/asset-hub-polkadot/src/migrations.rs)

### Summary
The Substrate/FRAME analog of the reported Solidity issue ("non-reverting ERC20 `transfer` return value not checked, causing stuck funds") is `MigrateBountyAccountAssets::on_runtime_upgrade`, which calls `Transferer::force_transfer_all_assets(&old, &new)` for every bounty and child-bounty account and discards the returned `Result` with `let _ = ...`, exactly as the original code discarded the `bool` success flag from `ERC20.transfer`.

### Finding Description
`MigrateBountyAccountAssets` iterates all `pallet_multi_asset_bounties::Bounties` and `ChildBounties` keys, computes the old and new sub-account derivations, and calls `Transferer::force_transfer_all_assets(&old, &new)` to move DOT/USDT/USDC balances from the legacy `"mbt"/"mcb"` derived accounts to the new `[u8;3]`-derived accounts: [1](#0-0) [2](#0-1) 

In both loops, the `Result` returned by `force_transfer_all_assets` is bound to `_` and never inspected. If the transfer fails for any reason (e.g. existential-deposit/`Preservation` constraints on one of the assets in `crate::treasury::BountyRelevantAssets`, an account-reap edge case, or any other `DispatchError` the underlying `fungibles`/`Currency` transfer can return), the migration proceeds as if it succeeded: it still books the weight for the operation and moves on to the next bounty, with no event, no error propagation, and no retry mechanism. This is structurally identical to the original bug pattern — the on-chain equivalent of `ERC20.transfer` returning `false` instead of reverting is a `Transfer`-style extrinsic/helper returning `Err(..)` without panicking, and here that `Err` is deliberately swallowed by `let _ = ...` rather than being checked or logged.

Because `pallet_bounties::TransferAllAssets`/`force_transfer_all_assets` is implemented in an external crate not present in this repository's index, I could not directly confirm every condition under which it returns `Err` rather than succeeding unconditionally; this is a limitation of what I could verify from the indexed code.

### Impact Explanation
`MbmMigrations`/`SingleBlockMigrations` migrations in FRAME run exactly once as part of a runtime upgrade (`OnRuntimeUpgrade::on_runtime_upgrade`), so if `force_transfer_all_assets` fails for a given bounty/child-bounty pair, the funds are left at the old, no-longer-tracked sub-account (`"mbt"/"mcb"`-derived) — the comment in the code explicitly states these funds become unreachable by the pallet after the upgrade because the pallet henceforth only reads the new derivation: [3](#0-2) 
There is no built-in retry, alert, or governance recovery path wired into this migration, so a silent partial failure would strand DOT/USDT/USDC funds indefinitely, matching the "High" impact rationale from the original report (stuck funds, but not attacker-exploitable).

### Likelihood Explanation
Low. This code path is not reachable by an unprivileged attacker — it only executes once, automatically, during a scheduled runtime upgrade controlled by the Fellowship/governance, and the failure would need a specific asset/account state (e.g. an account that cannot satisfy existential deposit or asset-sufficiency requirements for one of the `BountyRelevantAssets`) to trigger the silent no-op. This mirrors the "Low likelihood" rating in the original report, which was also premised on an edge-case token/account condition rather than routine operation.

### Recommendation
Do not discard the `Result` from `force_transfer_all_assets`. At minimum, log/emit an event (e.g. via `Self::deposit_event` or `log::error!`) for each bounty/child-bounty whose transfer fails, and/or use `.defensive()` (as done elsewhere in this codebase, e.g. `pallets/ah-ops/src/lib.rs`) so that failures are visible in defensive-mode testing and surfaced for manual remediation rather than being unconditionally ignored: [4](#0-3) 
Consider also making the migration idempotent/retryable (e.g. driven by on-chain storage of "pending" migrations) so a partial failure can be corrected without another full runtime upgrade.

### Proof of Concept
Not applicable as a live exploit — this is not an attacker-triggerable path but a robustness/error-handling gap in a one-shot governance-run migration: [5](#0-4) [6](#0-5) 
If `force_transfer_all_assets` returns `Err(_)` for any `(old, new)` pair (condition not fully verifiable from indexed code, as `pallet_bounties::TransferAllAssets`'s implementation is in an external crate), the corresponding bounty's funds remain at `old` after the upgrade completes, and are no longer reachable through `pallet_multi_asset_bounties` since the pallet only reads the new derivation going forward.
