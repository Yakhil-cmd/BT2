### Title
Webhook signature verification binds to `repository.owner.login`/`organization.login` while event handlers act on the unrelated `repository.full_name` field, allowing a valid multi-org webhook signer to trigger writes on a repository they don't own - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/handler.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/`webhook_secret` to validate the HMAC signature against using `repository_owner`, computed from `params.dig('repository', 'owner', 'login')` (falling back to `params.dig('organization', 'login')`) [1](#0-0) . Once the signature is accepted, the raw JSON body is handed unmodified to every matching `Shipit::Webhooks::Handlers::Handler`, which instead determines the repository to act on from a completely different field, `payload.dig('repository', 'full_name')` [2](#0-1) . Nothing ties `repository.owner.login` to `repository.full_name` before the payload is trusted. In a multi-organization Shipit deployment (`config/secrets.*.yml` supports one `webhook_secret` per organization) [3](#0-2) , an organization admin who legitimately knows their own org's `webhook_secret` (because they configured it in the GitHub App settings) can sign an arbitrary JSON body with that secret while setting `repository.full_name` to a different organization's repository. The signature check in `GitHubApp#verify_webhook_signature` only validates the raw body against the secret picked by `repository_owner` — it has no notion of which repository the body's other fields claim to describe [4](#0-3) .

### Finding Description
The trust binding that should hold is: **the organization whose secret authenticated the request == the repository that gets written to**. Concretely:

- Verification side: `repository_owner` (from `repository.owner.login` or `organization.login`) selects `Shipit.github(organization: repository_owner)`, and the HMAC is checked with that org's `webhook_secret` [5](#0-4) .
- Write side: every handler (`PushHandler`, PR handlers, etc.) resolves the target `Repository`/`stacks` from `repository.full_name` inside the very same JSON body that was just "verified" [2](#0-1) [6](#0-5) [7](#0-6) .

Because the attacker fully controls the raw POST body they sign, `repository.owner.login` and `repository.full_name` need not correspond to the same real-world repository. An org admin for `attacker-org` (a legitimate customer with their own GitHub App installation and `webhook_secret` on this shared Shipit instance) can:
1. Craft a JSON body with `repository.owner.login = "attacker-org"` (or `organization.login = "attacker-org"`) so `verify_signature` selects the org they know the secret for and the HMAC passes.
2. Set `repository.full_name = "victim-org/victim-repo"` in the same body.
3. Sign the body with `attacker-org`'s own `webhook_secret` and POST it to `/github/webhooks`.

`verify_signature` succeeds because it only checks the body against `attacker-org`'s secret, never checking that `repository.full_name` also belongs to `attacker-org` [1](#0-0) . The handler then dispatches purely off `repository.full_name`, so it operates on `victim-org/victim-repo`'s stacks regardless of which org authenticated the request.

### Impact Explanation
This breaks the "organization authenticated vs. repository written" binding called out as an in-scope analog class. With a forged `push` event, `PushHandler#process` calls `stack.sync_github(expected_head_sha: params.after)` on the victim's non-archived stacks matching the forged branch [6](#0-5) , which is the trigger Shipit uses to pick up new commits for deployment consideration — an attacker-controlled organization can force sync/queue activity against a repository/stack it does not own. PR-event handlers (`opened_handler.rb`, `closed_handler.rb`, `labeled_handler.rb`, etc.) similarly resolve `Shipit::Repository.from_github_repo_name(params.repository.full_name)` and then archive/unarchive review stacks or update stored PR state for that victim repository based purely on the forged `full_name` [8](#0-7) [9](#0-8) . This is a cross-repository/cross-organization write performed with credentials belonging to an unrelated tenant, matching the "cross-repository writes" high-severity criterion.

### Likelihood Explanation
Requires the shared Shipit instance to be configured with the multi-organization `github:` secrets schema (each org gets its own installed app + `webhook_secret`), which is a documented, supported configuration [10](#0-9) . Any tenant organization onboarded onto that shared instance inherently knows its own `webhook_secret` (they configured it when creating their GitHub App) and can freely POST crafted bodies to the shared `/github/webhooks` endpoint — no privileged Shipit account or token is required, only being one of the (possibly many) organizations sharing the instance.

### Recommendation
After signature verification, cross-check that the organization used to select the verifying secret (`repository_owner`) is the same organization implied by `repository.full_name` (i.e., `full_name.split('/').first` matches `repository_owner`) before dispatching to handlers, rejecting the request with `422` on mismatch.

### Proof of Concept
1. Configure Shipit with two organizations in `secrets.yml`: `attacker-org` (with `webhook_secret: "attacker-secret"`, known to the attacker) and `victim-org` (any secret, unknown to the attacker), each with a repo/stack registered in Shipit.
2. Attacker builds a JSON push payload:
   ```json
   {
     "ref": "refs/heads/master",
     "after": "<attacker-chosen sha>",
     "repository": {
       "owner": { "login": "attacker-org" },
       "full_name": "victim-org/victim-repo"
     }
   }
   ```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(attacker-secret, body)>` using their known `attacker-secret`.
4. POST to `/github/webhooks` with header `X-Github-Event: push`.
5. `WebhooksController#verify_signature` resolves `repository_owner = "attacker-org"`, fetches `Shipit.github(organization: "attacker-org")`, and the HMAC check passes [5](#0-4) .
6. `PushHandler#process` resolves stacks via `Repository.from_github_repo_name("victim-org/victim-repo")` and calls `sync_github` on victim's stacks despite the request having been authenticated as `attacker-org` [2](#0-1) [6](#0-5) .

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
