### Title
First-depositor share-price manipulation in AA liquidity/share-issuance templates via silent "eat the coins" balance inflation - (File: aa_composer.js, test/samples/uniswap_like_market_maker.oscript)

### Summary
The reported Insure Finance bug is a classic "first depositor" ERC4626/AMM-share inflation issue: shares are minted as `value * supply / totalLiquidity`, and if `totalLiquidity` can be inflated out-of-band relative to `supply` (via a side channel like `transferAttribution`), later depositors get rounded-down (zero) shares while the attacker who controls all shares captures the donated value. The same class of bug is reachable in Obyte's Autonomous Agent (AA) execution model, because `balance[asset]` inside an oscript formula reflects the AA's *raw, on-chain* asset balance, while any "shares outstanding" bookkeeping is a separately maintained state variable that the AA author must keep in sync manually. ocore's own execution engine provides a mechanism that lets funds sit in an AA's balance without any corresponding state update — exactly the "donation" side channel the H-06 report describes.

### Finding Description
In `aa_composer.js`, when a triggered AA case produces no non-empty payment messages after filtering, the engine explicitly documents and implements a "silently eat the coins" behavior: [1](#0-0) 

This means an AA can receive and permanently retain funds (increasing its raw `balance[base]`/`balance[asset]`) in a code path that performs no explicit accounting of those funds into any share/supply state variable, as long as the matching `if` case is satisfied but yields no payment outputs, or all outputs are filtered to zero. The dry-run/AIR path and secondary-trigger balance restoration logic confirm the same "coins absorbed, no messages" semantics is a first-class, reachable outcome of `handleTrigger`, not an edge-case bug: [2](#0-1) 

This engine-level property directly enables the H-06 bug class in any AA that implements pool/LP-share accounting the way the official sample AMM template does. The bundled `uniswap_like_market_maker.oscript` sample (shipped in ocore's own `test/samples`, and validated/parsed by `test/ojson.test.js`) computes the very first liquidity issuance as the AA's entire raw balance rather than the amount actually contributed in the triggering unit: [3](#0-2) 

Specifically:
```
if ($asset_balance == 0 OR $bytes_balance == 0){ // initial deposit
    $issue_amount = balance[base];
    return;
}
...
var['mm_asset_outstanding'] += $issue_amount;
```
`balance[base]` is the AA's *total* raw byte balance at execution time, not `trigger.output[[asset=base]]` (the amount sent in this specific trigger). If an attacker can get bytes/asset into the AA's balance before minting the first `mm_asset` share tokens — via the "eat the coins" no-message path, via a small legitimate first deposit followed by out-of-band donations that don't route through the `invest`/`divest`/`exchange` cases, or via any other case whose `if` matches but leaves `messages` empty after filtering — the attacker (holding 100% of `mm_asset_outstanding` from a nominal deposit) inflates `balance[base]`/`balance[asset]` without inflating `var['mm_asset_outstanding']`. All subsequent depositors then compute their issuance as:
```
$issue_amount = round($investor_share_of_prev_balance * var['mm_asset_outstanding']);
```
where `$investor_share_of_prev_balance = trigger.output[[asset=base]] / $bytes_balance` is now computed against an inflated `$bytes_balance` — an exact structural analog of the reported `(_value * _supply) / _originalLiquidity` rounding-to-zero exploit. A depositor's contribution can round to 0 minted shares while their payment is absorbed into `balance[base]`, which the attacker — holding all of `mm_asset_outstanding` — can withdraw via the `divest` case, capturing the donated funds.

This is not a hypothetical scripting mistake exclusive to app-layer code review; it stems from a genuine engine-level property (`aa_composer.js`'s handling of empty-message responses) that any unprivileged unit poster/AA trigger sender can exploit against any AA (including ocore's own reference implementation) that tracks LP-style share issuance separately from raw AA balance, without additionally guarding against pre-mint donations.

### Impact Explanation
Any AA implementing liquidity-pool/share-token semantics (as ocore's own bundled `uniswap_like_market_maker.oscript` reference template does) is exposed to a fund-theft/fund-freezing vulnerability: a subsequent depositor's payment can be fully absorbed by the AA while receiving zero (rounded-down) shares, and the attacker who minted the initial (nominal) share supply can withdraw the donated value. This constitutes concrete unauthorized fund loss for depositors and AA fund drainage for the attacker's benefit — matching the "AA fund loss" acceptance criterion. Because AAs deployed on Obyte with this pattern are publicly triggerable by any address sending a payment, exploitation requires no privileged access, unlike Ethereum where the underlying report needed a compromised/owner-controlled `transferAttribution` call; the Obyte engine's "eat the coins" semantics is a standard, unprivileged code path.

### Likelihood Explanation
Likelihood is Medium: exploitation requires (a) an AA template that computes first-deposit share issuance from `balance[...]` rather than the current trigger's contribution (present in ocore's own shipped sample), and (b) the attacker being able to route extra funds into the AA's balance without triggering the supply-increment branch (achievable via the documented "no messages after filtering" absorption path, or via depositing an asset/case combination the template doesn't proportionally account for). Since the exact template is a reference/sample AA rather than a mandatory core contract, real-world exposure depends on which third-party AAs copy this pattern, but the underlying engine behavior that enables the donation vector is a fixed, always-available property of `aa_composer.js`.

### Recommendation
- In `aa_composer.js`, consider surfacing a validation warning/lint rule (in `aa_validation.js`) discouraging AA templates whose payment-message filtering can silently absorb trigger funds with zero messages and no explicit state update ("no messages after filtering" path), or require that such cases explicitly acknowledge fund retention.
- For the shipped `uniswap_like_market_maker.oscript` sample (and any documentation referencing it as a safe template), fix the initial-deposit detection to base share issuance strictly on `trigger.output[[asset=base]]` / `trigger.output[[asset=$asset]]` (the actual contribution in the current trigger) rather than the AA's cumulative `balance[...]`, and/or seed `mm_asset_outstanding` with a fixed minimum "virtual" supply so the first depositor's price cannot be set by an arbitrarily small deposit inflated by later donations.
- Document explicitly (in AA developer docs) that `balance[asset]` inside oscript formulas is not equivalent to "total legitimately deposited value" and that AAs must independently defend against under-accounted-for balance inflation, analogous to Uniswap V2's `MINIMUM_LIQUIDITY` lock and OpenZeppelin's ERC4626 inflation-attack mitigations.

### Proof of Concept
1. Deploy an AA using the exact logic of `test/samples/uniswap_like_market_maker.oscript` (or a copy thereof) on the Obyte network.
2. Trigger `{trigger.data.define: true}` to create `$mm_asset`.
3. Attacker sends a trigger matching the "invest" case with a minimal amount, e.g. `trigger.output[[asset=base]] = 100001`, `trigger.output[[asset=$asset]] = 1`. Since `asset_balance == 0` at that point, `$issue_amount = balance[base]` ≈ `100001`, and `var['mm_asset_outstanding'] = 100001`. Attacker now holds all outstanding shares.
4. Attacker (or a colluding unit) sends additional base bytes/`$asset` to the AA address in a trigger that matches a case (or falls through to a case) whose resulting `messages` filters down to empty — invoking the `aa_composer.js` "eat the received coins... state changes are still performed" path (line 1873-1876) — thereby increasing `balance[base]`/`balance[$asset]` without incrementing `var['mm_asset_outstanding']`. (Alternative: repeatedly bounce-fee-only micro triggers that still count toward `balance[base]` per `updateInitialAABalances`/`updateFinalAABalances` bookkeeping.)
5. A legitimate investor now sends a large deposit, e.g. `trigger.output[[asset=base]] = 500000` with matching `$asset` amount. Because `$bytes_balance` (the AA's balance prior to this trigger) has been inflated by step 4 relative to `mm_asset_outstanding`, `$investor_share_of_prev_balance = 500000 / inflated_bytes_balance` is tiny, and `$issue_amount = round($investor_share_of_prev_balance * 100001)` rounds down to 0 (or near 0) minted `mm_asset` shares, while the investor's 500000 bytes remain in the AA's balance.
6. Attacker triggers the "divest" case with their full `mm_asset` holdings (`var['mm_asset_outstanding']` still ≈100001, attacker owns all of it), receiving `round($investor_share * balance[base])` — i.e., the entire inflated balance, including the victim's 500000 bytes — draining the pool exactly as in the original H-06 report.
