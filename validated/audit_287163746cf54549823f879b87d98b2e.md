Based on my investigation, `CCMenuController` breaks the token/stack authorization binding that `Api::BaseController` establishes for every other API endpoint.

### Title
CCMenu API token authorizes reading any stack's build status, not just the stack it was scoped to - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Api::BaseController` scopes an `ApiClient` token to a single stack when `stack_id` is set, and every controller resolves the target stack through the scoped `stacks`/`stack` helpers [1](#0-0) . `Api::CCMenuController` overrides `stack` to query `Stack.from_param!(params[:stack_id])` directly, bypassing the scoping entirely [2](#0-1) . This breaks the equality "stack a token authorizes == stack the token can touch."

### Finding Description
In `Api::BaseController`, the `stacks` helper is the enforcement point for per-token stack scoping: [1](#0-0) 
Every other resource controller (`Api::TasksController`, `Api::CommitsController`, `Api::LocksController`, `Api::StacksController`) resolves its target stack via `stack`/`stacks`, so a token created with a `stack_id` (e.g. via `CCMenuUrlController#client`, which mints a `read:stack`-only `ApiClient` [3](#0-2) ) can only act on that one stack.

`Api::CCMenuController`, however, defines its own `stack` method that queries the full `Stack` relation instead of the scoped `stacks` relation: [2](#0-1) 
It also overrides `authenticate_api_client` to accept the token from a query-string `params[:token]` (for polling tools like CCTray/CCMenu clients) [4](#0-3) , and still enforces only the coarse `read:stack` permission check, not a stack-identity check [5](#0-4) .

Because `check_permissions!` only validates the `operation:scope` string ("read:stack") and never compares the requested `stack_id` param against `current_api_client.stack_id` [6](#0-5) , any holder of a stack-scoped read-only CCMenu token can supply an arbitrary `stack_id` in the URL and read deploy/build status for a stack the token was never scoped to.

### Impact Explanation
This is an unauthorized read of stack/task state across the authorization boundary the token was explicitly restricted to — the "stack a token authorizes" vs "stack it touches" binding named in scope. It discloses deploy status, lock reason, last build outcome, etc. for stacks outside the token's intended scope, which qualifies as "unauthenticated read of stack state" relative to the token's granted scope (High impact tier).

### Likelihood Explanation
Likelihood is high for any deployment that uses the CCMenu integration feature (`CCMenuUrlController`), since these tokens are handed to third-party CI-status tools/URLs and are read-only by design — an attacker who obtains one such URL/token (e.g., from a leaked dashboard bookmark, log, or referrer) can enumerate other stacks by varying `stack_id` in the request without needing any elevated permission.

### Recommendation
Change `Api::CCMenuController#stack` to use the scoped `stacks` helper (`stacks.from_param!(params[:stack_id])`) instead of querying `Stack` directly, so a stack-scoped token cannot read data for stacks outside its `stack_id`.

### Proof of Concept
1. An admin uses the "CCMenu URL" feature for `stack A`, generating a token via `CCMenuUrlController#fetch`, which creates/returns an `ApiClient` with `permissions: ["read:stack"]` (no explicit non-scoped check tying it to `stack A` at the controller level).
2. Using that token, request:
   `GET /api/<stack_B_owner>/<stack_B_name>/<env_B>/ccmenu.xml?token=<token>`
3. `Api::CCMenuController#authenticate_api_client` accepts the token, `check_permissions!(:read, :stack)` passes (token has `read:stack`), and `stack` resolves `Stack.from_param!(params[:stack_id])` for `stack B` directly — bypassing the `stacks` scoping that would normally restrict lookup to the token's own `stack_id`.
4. The response renders `stack B`'s build/deploy status XML, even though the token was only meant to expose `stack A`.
