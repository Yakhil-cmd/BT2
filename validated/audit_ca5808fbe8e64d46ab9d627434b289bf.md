### Title
Fee-on-Transfer ERC20 Undercollateralizes the Service-Chain Bridge — (`contracts/service_chain/bridge/BridgeTransferERC20.sol`)

---

### Summary

`requestERC20Transfer` in `BridgeTransferERC20.sol` calls `safeTransferFrom` for `_value + _feeLimit` and then unconditionally emits `RequestValueTransfer` with the caller-supplied `_value`. It never measures the actual balance change. When a registered ERC20 token silently deducts a transfer fee, the source bridge receives fewer tokens than `_value + _feeLimit`, yet the counterpart bridge is instructed to release the full `_value` to the recipient. Each such transfer permanently undercollateralizes the source bridge by the token's transfer fee, eventually making it unable to honor legitimate withdrawals.

---

### Finding Description

`requestERC20Transfer` performs two sequential operations without any balance-delta check between them:

```solidity
// BridgeTransferERC20.sol line 133-134
IERC20(_tokenAddress).safeTransferFrom(msg.sender, address(this), _value.add(_feeLimit));
_requestERC20Transfer(_tokenAddress, msg.sender, _to, _value, _feeLimit, _extraData);
``` [1](#0-0) 

`safeTransferFrom` only checks that the call did not revert; it does not verify that `address(this).balance` increased by exactly `_value + _feeLimit`. For a fee-on-transfer token with fee rate `t`, the bridge receives `_value + _feeLimit - t`.

Inside `_requestERC20Transfer`, `_payERC20FeeAndRefundChange` disperses the full `_feeLimit` (bridge fee to `feeReceiver` + excess refunded to caller):

```solidity
// BridgeFee.sol line 74-78
IERC20(_token).safeTransfer(feeReceiver, fee);
uint256 feeRefund = _feeLimit.sub(fee);
if (feeRefund > 0) {
    IERC20(_token).safeTransfer(from, feeRefund);
}
``` [2](#0-1) 

After this outflow the bridge retains `_value - t` tokens, but the event is emitted with the original `_value`:

```solidity
// BridgeTransferERC20.sol line 97-106
emit RequestValueTransfer(
    TokenType.ERC20,
    _from, _to, _tokenAddress,
    _value,          // ← caller-supplied, not actual received amount
    requestNonce, fee, _extraData
);
``` [3](#0-2) 

The off-chain bridge relayer reads this event and calls `handleERC20Transfer` on the counterpart bridge with `_value`. In non-mintBurn mode the counterpart bridge executes `safeTransfer(_to, _value)`, releasing the full `_value` to the recipient: [4](#0-3) 

The source bridge is now short `t` tokens per transfer. No guard in the codebase measures the pre/post balance to detect this discrepancy.

---

### Impact Explanation

**Unauthorized asset release from the source bridge.** In non-mintBurn (lock/unlock) mode the source bridge is the sole collateral backing all tokens on the counterpart chain. Each cross-chain transfer with a fee-on-transfer token drains `t` tokens from that collateral without a corresponding reduction in counterpart-chain supply. After `N` transfers the bridge is short `N × t` tokens. When users attempt to bridge back, the source bridge's `safeTransfer` will eventually revert for insufficient balance, permanently locking funds of honest users.

This matches the allowed impact gate: *unauthorized transfer … affecting bridged assets or system-managed funds* and *persistent corruption … that breaks … withdrawals*.

---

### Likelihood Explanation

- **Trigger**: Any unprivileged user who holds a registered fee-on-transfer ERC20 token can call `requestERC20Transfer` directly. No operator role is required.
- **Precondition**: The token must be registered by the bridge owner (`registerToken`). Tokens such as USDT have historically enabled transfer fees; any future fee activation on a registered token silently activates the bug.
- **Detection**: The transaction succeeds and emits a normal-looking `RequestValueTransfer` event; no on-chain revert or anomaly signals the shortfall.

---

### Recommendation

1. **Measure actual received amount** using a pre/post balance check in `requestERC20Transfer`:

```solidity
uint256 before = IERC20(_tokenAddress).balanceOf(address(this));
IERC20(_tokenAddress).safeTransferFrom(msg.sender, address(this), _value.add(_feeLimit));
uint256 actualReceived = IERC20(_tokenAddress).balanceOf(address(this)).sub(before);
require(actualReceived == _value.add(_feeLimit), "fee-on-transfer token not supported");
```

2. **Alternatively**, pass `actualReceived` (minus the fee portion) as the bridged value so the emitted event reflects what the bridge actually holds.

3. **Blocklist fee-on-transfer and rebasing tokens** at the `registerToken` level, or document clearly that only standard ERC20 tokens are supported and enforce this with an integration checklist.

### Proof of Concept

**Setup**: Deploy `BridgeTransferERC20` in non-mintBurn mode. Register a fee-on-transfer ERC20 token (1% fee on every transfer). Set bridge fee = 0, feeLimit = 0.

**Step 1 — Attacker calls `requestERC20Transfer`** with `_value = 1000`, `_feeLimit = 0`:
- `safeTransferFrom` moves `1000` nominal units; token deducts 1% → bridge receives `990`.
- `_payERC20FeeAndRefundChange` does nothing (fee=0, feeLimit=0).
- Bridge balance: `990`.
- `RequestValueTransfer` emitted with `valueOrTokenId = 1000`.

**Step 2 — Relayer observes event**, calls `handleERC20Transfer` on counterpart bridge with `_value = 1000`:
- Counterpart bridge executes `safeTransfer(recipient, 1000)` → recipient receives `1000`.

**Step 3 — Net accounting**:
- Source bridge locked: `990`.
- Counterpart chain minted/released: `1000`.
- Deficit: `10` tokens per transfer.

**Step 4 — Repeat** 100 times → source bridge is short `1000` tokens. The 101st legitimate user who bridges back receives a revert on the source chain's `safeTransfer`, permanently losing their funds.
