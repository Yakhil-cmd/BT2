**Analysis supporting this conclusion:**

The question posits a broken equality between the transcript bytes produced by `blst_p1_affine_compress` in `compute_r_powers_for_verify_kzg_proof_batch` and the canonical encoding produced by `bytes_from_g1` (which wraps `blst_p1_compress`) elsewhere in the codebase.

Tracing the code:
- `bytes_from_g1` in [1](#0-0)  calls `blst_p1_compress(out->bytes, in)` on a Jacobian `g1_t`.
- `compute_r_powers_for_verify_kzg_proof_batch` first converts all `commitments_g1`/`proofs_g1` (Jacobian) to affine form via `blst_p1s_to_affine`, then serializes each with `blst_p1_affine_compress` directly into the transcript buffer: [2](#0-1) .

`blst_p1_compress` and `blst_p1_affine_compress` are both part of blst's public serialization API and are defined to produce byte-identical output for the same group element — `blst_p1_compress` simply converts the Jacobian point to affine internally and then applies the same compression routine that `blst_p1_affine_compress` applies directly. This includes the point-at-infinity encoding (a single set high bit followed by zero bytes) and the case of the generator point, since compression bit-flag logic in blst is independent of whether the input started as Jacobian or affine — the affine coordinates are what get serialized either way. There is no alternate/legacy compression path in blst that diverges for these cases.

Additionally, before any point reaches this transcript code, `bytes_to_kzg_commitment`/`bytes_to_kzg_proof` → `validate_kzg_g1` already decompress-and-validate each point via `blst_p1_uncompress`, accept infinity explicitly, and enforce subgroup membership otherwise: [3](#0-2) . So every `g1_t` fed into `compute_r_powers_for_verify_kzg_proof_batch` (including a submitted G1 generator point) is a validated, canonical point, and converting it Jacobian→affine→compressed via `blst_p1s_to_affine` + `blst_p1_affine_compress` yields exactly the same 48 bytes as `bytes_from_g1` would for that same point.

Since both sides of the claimed equality (`blst_p1_affine_compress` output vs. `bytes_from_g1`/`blst_p1_compress` output) are guaranteed identical by blst's serialization contract for any valid point, including the generator and the point at infinity, there is no divergence to exploit through the Elixir `KZG.verify_blob_kzg_proof_batch` binding or any other path. No forged verdict, no cross-client byte divergence, and no crash is reachable via this described mechanism.

static C_KZG_RET validate_kzg_g1(g1_t *out, const Bytes48 *b) {
    blst_p1_affine p1_affine;

    /* Convert the bytes to a p1 point */
    /* The uncompress routine checks that the point is on the curve */
    if (blst_p1_uncompress(&p1_affine, b->bytes) != BLST_SUCCESS) return C_KZG_BADARGS;
    blst_p1_from_affine(out, &p1_affine);

    /* The point at infinity is accepted! */
    if (blst_p1_is_inf(out)) return C_KZG_OK;
    /* The point must be on the right subgroup */
    if (!blst_p1_in_g1(out)) return C_KZG_BADARGS;

    return C_KZG_OK;
}
