### Title
Cross-repository commit-status forgery via unscoped `sha` lookup in `StatusHandler` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret to validate a webhook against using an organization identifier taken straight out of the *unverified* JSON body (`repository.owner.login` / `organization.login`). [1](#0-0) [2](#0-1)  Once that per-organization check passes, `Shipit::Webhooks::Handlers::StatusHandler#process` never re-checks that the commit it is about to mutate actually belongs to that organization/repository: it resolves the target `Commit` purely by a global `sha` lookup, `Commit.where(sha: params.sha)`. [3](#0-2)  This breaks the equality "organization that authenticated == repository that is written": the signature only proves the payload came from the (correctly configured) app for organization X, but the effect of the handler can be applied to a commit belonging to any other stack/repository tracked by the instance, because `sha` values are not namespaced per repository in this lookup.

### Finding Description
- The base `Handler` class exposes a helper, `repository_name`, that correctly scopes handlers to `payload.dig('repository', 'full_name')`, and most webhook handlers (`PushHandler`, the `PullRequest::*` handlers) use `Repository.from_github_repo_name(...)` before doing anything. [4](#0-3) 
- `StatusHandler`, however, is the one handler that skips this repository binding entirely: it takes `params.sha` and does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }`, with no join/filter on `repository` or `stack`. [5](#0-4) 
- Meanwhile, `verify_signature` picks the secret to validate against using `repository_owner`, itself read from the same untrusted JSON body before verification happens: `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`. [2](#0-1) 
- `verify_webhook_signature` in `GitHubApp` returns `true` unconditionally whenever no `webhook_secret` is configured for that organization: `return true unless webhook_secret`. [6](#0-5)  Setup documentation explicitly marks the webhook secret as "(optional)", so a deployment with one or more configured GitHub Apps lacking a secret is a documented, supported configuration, not a deviation from the docs. [7](#0-6)  The `config/secrets.development.shopify.yml` and `config/secrets.development.example.yml` templates both ship with `webhook_secret: # nil` for illustration/multi-org setups. [8](#0-7) 

Putting these together: an unprivileged external attacker who can reach `POST /webhooks` (no Shipit session, API token, or GitHub credentials required) crafts a `status` event whose `repository`/`organization` fields identify an app configuration with no `webhook_secret` (or one whose secret is somehow known/guessable), thereby satisfying `verify_signature`. The payload's `sha` field, however, is free-form and can name **any commit SHA already tracked in the Shipit database for any stack/repository**, not just repositories under the "authenticated" organization. `StatusHandler` then writes an attacker-chosen `state`/`description`/`target_url` commit status onto that unrelated commit via `Commit#create_status_from_github!`.

### Impact Explanation
Shipit uses commit statuses to compute whether a commit satisfies required checks before it is offered for deploy (`CommitChecks`/`Stack` gating logic referenced from `commit.rb`). By forging a `success` status on an arbitrary commit belonging to a repository/stack the attacker does not control, the attacker can make a commit that never actually passed CI appear deployable to a legitimate, privileged Shipit user, who may then trigger a deploy based on the falsified status. This is a cross-repository write of state that the webhook's authentication boundary is supposed to prevent, and it directly enables an unauthorized deploy of unverified code — matching the required "Critical: unauthorized deploy" / "cross-repository writes" impact bar, without the attacker ever needing a Shipit session, API token, or the target repository's own credentials.

### Likelihood Explanation
Medium. Exploitation requires that at least one configured GitHub App/organization in the Shipit deployment has no `webhook_secret` set (an explicitly documented, optional configuration) or that the attacker otherwise possesses a valid HMAC secret for some organization onboarded to the instance. Multi-organization Shipit deployments (as shown in the shipped example secrets files) are a realistic scenario where operators may leave some entries unsecured. Once that precondition holds, forging the HTTP request itself is trivial (`X-Github-Event: status` header plus a crafted JSON body) and requires no interaction with GitHub at all.

### Recommendation
Scope `StatusHandler#process` (and any other handler that looks up existing records by an identifier taken from the payload) to the repository resolved from the authenticated request, e.g. join through `stacks`/`repository_name` the same way `PushHandler` and the `PullRequest::*` handlers do, rather than performing a global `Commit.where(sha:)` lookup. Additionally, consider making `webhook_secret` mandatory for every configured GitHub App (reject configuration or refuse to process webhooks when it is blank) so `verify_webhook_signature` can never silently return `true`.

### Proof of Concept
1. Shipit is configured with two GitHub Apps: `victim-org` (has a `webhook_secret`, hosts the sensitive stack whose commit the attacker wants to fake-green) and `attacker-org` (no `webhook_secret` configured — a supported/optional configuration per `docs/setup.md`).
2. Attacker sends, without any authentication:
```
POST /webhooks HTTP/1.1
X-Github-Event: status
Content-Type: application/json

{
  "sha": "<sha of a real commit belonging to victim-org's tracked stack>",
  "state": "success",
  "context": "ci/required-check",
  "description": "forged",
  "target_url": "https://attacker.example",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "attacker-org/some-repo" }
}
```
3. `WebhooksController#verify_signature` calls `Shipit.github(organization: "attacker-org")`, whose `verify_webhook_signature` returns `true` because `webhook_secret` is blank for `attacker-org`. [9](#0-8) 
4. `StatusHandler#process` runs `Commit.where(sha: params.sha)`, finds the `victim-org` commit purely by SHA, and calls `create_status_from_github!`, writing the forged "success" status onto it. [3](#0-2) 
5. A legitimate Shipit operator, seeing the (fabricated) green required check, deploys the commit through the normal Shipit UI — an unauthorized deploy enabled entirely by an unauthenticated cross-repository write.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
