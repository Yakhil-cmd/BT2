### Title
`_has_redos_structure()` fails to detect catastrophic-backtracking regexes hidden behind nested groups or `{n,}` quantifiers, allowing a malicious `security-patterns.yaml` to hang the PostToolUse hook - ([File: plugins/security-guidance/hooks/extensibility.py])

### Summary
`_has_redos_structure()` uses two narrow, string-level heuristics (`_REDOS_SHAPES` and `_ALT_UNDER_REP`) that only recognize catastrophic backtracking shapes when the offending quantified group is a *single* paren level with no nested parentheses and is followed directly by a bare `+`/`*`/`?`. An attacker-controlled `security-patterns.yaml` can supply a regex that is still exponential in the standard `re` backtracking engine but structurally evades both checks, e.g. by nesting the vulnerable group one level deeper inside an outer alternation, or by using `{n,}` instead of `+`/`*`. Once accepted by `_validate_pattern`, the regex is stored and later run via `re.search` on every PostToolUse edit in the pattern-check path, causing the hook to hang.

### Finding Description
`_has_redos_structure()` in [1](#0-0)  relies on:
- `_REDOS_SHAPES[0]`: `\([^()]*[+*][^()]*\)[+*?]` — matches a *single* paren group with no nested parens containing a `+`/`*`, immediately followed by `+`/`*`/`?`.
- `_REDOS_SHAPES[1]`: `\(\.\*[^()]*\)[+*]` — wildcard groups under repetition.
- `_ALT_UNDER_REP`: also requires the alternation group to contain no nested parens (`[^()]*`, `[^()|]*`) and to be followed directly by a bare `[+*]`.

Both checks fail closed (return `False`, i.e. "not ReDoS") whenever:
1. **The vulnerable quantified subgroup is nested one level inside another group**, e.g. `(a|(a+))+`. Walking the regex: the outer group cannot match `_REDOS_SHAPES[0]` because its content contains parentheses (violates `[^()]*`), and the inner `(a+)` is not itself directly followed by a quantifier character (it's followed by `)` then the outer `+`), so no substring position satisfies the pattern. `_ALT_UNDER_REP` also fails because branch text scanning disallows parens in the alternatives. Yet `(a|(a+))+` is classic ambiguous-overlap catastrophic backtracking: for an input of many `a`s followed by a non-matching character, the engine explores exponentially many ways to partition the run of `a`s between the `a` and `(a+)` alternatives.
2. **The outer repetition uses a bounded/unbounded `{n,}` quantifier instead of `+`/`*`.** e.g. `(a+){3,}`. `_REDOS_SHAPES[0]` requires the character class `[+*?]` immediately after the closing paren — `{3,}` does not match this class, so the check misses it, even though `{n,}` (unbounded upper bound) is backtracking-equivalent to `+`.

`_validate_pattern` at [2](#0-1)  only rejects a regex if `_has_redos_structure()` returns `True`; otherwise it stores `rule["regex"] = regex` and the rule is merged into the active pattern set via `_load_user_patterns` / `user_patterns()` at [3](#0-2) . Those user patterns are consumed alongside the built-in `SECURITY_PATTERNS` list by the PostToolUse pattern checker (`check_patterns`, referenced in `plugins/security-guidance/hooks/security_reminder_hook.py`), which runs `re.search(pattern['regex'], content)` against edited file content on every tool call. No `_load_user_patterns` cap, timeout, or `re` timeout/step-limit mechanism is documented or visible in `extensibility.py` to bound worst-case match time once a rule is accepted — the module's own docstring states the only defense is the load-time structural heuristic ("Custom regexes are validated at load for catastrophic-backtracking structure and skipped ... if they look ReDoS-prone").

### Impact Explanation
A repository-supplied `.claude/security-patterns.yaml` (project-scoped, discoverable per the precedence rules in [4](#0-3) ) can plant a regex that passes validation but causes `re.search` to backtrack exponentially against ordinary file content matching the pattern's trigger shape (e.g. a long run of `a` characters followed by a non-matching character, plausible in many real source files or easily engineered by the same attacker via a second file). Because `check_patterns` runs synchronously in the PostToolUse hook path that gates every subsequent tool-approval, a hang here stalls or effectively denies the security-reminder enforcement for the remainder of the session — a hook-level denial-of-service against the tool-approval pipeline, not merely a warning-suppression bug.

### Likelihood Explanation
Feasible with a single attacker-controlled file added via a normal PR/branch checkout: no privileged access, no social engineering beyond getting the config file into the repo/checkout, and no dependency on other malicious infrastructure. The bypass patterns identified (`(a|(a+))+`, `(a+){3,}`) are simple, generically constructible, and repeatable — every PostToolUse edit thereafter that causes the regex engine to attempt a match against attacker-shaped content reproduces the hang.

### Recommendation
Do not rely on a purely structural, single-level heuristic to bound worst-case regex runtime. Options:
- Recursively strip/normalize nested groups (or use a proper regex-shape recursion) before applying `_REDOS_SHAPES`/`_ALT_UNDER_REP`, and generalize the trailing-quantifier check to also match `\{\d*,\d*\}` bounds, not just `[+*?]`.
- Better: enforce a runtime budget instead of (or in addition to) static heuristics — run `re.search` for user-supplied patterns under a hard timeout (e.g. via a separate process/thread with `signal.alarm`, or a bounded-backtracking engine such as `re2`/`regex` module with a timeout parameter) and treat a timeout as "skip this rule, debug_log it," never letting a single user pattern block the hook indefinitely.
- Cap total regex evaluation time per `check_patterns` invocation across all user + built-in patterns combined.

### Proof of Concept
Add to the pattern-loading test suite (e.g. a `test_extensibility_redos.py`):
```python
import re, time
from plugins.security_guidance.hooks.extensibility import _has_redos_structure

BYPASS_PATTERNS = [
    r"(a|(a+))+",       # overlap hidden one paren level deep
    r"(a+){3,}",        # bounded quantifier instead of +/*
]

def test_redos_bypass_causes_hang():
    attack_input = "a" * 30 + "!"  # forces full backtrack, then fails
    for regex in BYPASS_PATTERNS:
        assert _has_redos_structure(regex) is False, (
            f"expected heuristic to miss {regex!r} (documenting the bypass)"
        )
        compiled = re.compile(regex)
        start = time.monotonic()
        compiled.search(attack_input)
        elapsed = time.monotonic() - start
        # Invariant: hook-path regex matching must stay sub-second even on
        # adversarial input; this assertion is expected to FAIL, proving DoS.
        assert elapsed < 1.0, f"{regex!r} took {elapsed:.2f}s on {len(attack_input)}-char input"
```
Running this test with increasing `attack_input` lengths (e.g. 20, 25, 30 `a`s) should show exponential growth in `elapsed`, confirming that `_has_redos_structure` accepts patterns that hang `re.search` well past sub-second thresholds, directly on the code path used by `_validate_pattern` → `check_patterns`.

```python
# Catastrophic backtracking: nested quantifiers, overlapping alternations
# under repetition, and wildcard groups under repetition. Static check, not a
# proof — catches the common shapes that hang the hook on every edit.
_REDOS_SHAPES = [
    re.compile(r"\([^()]*[+*][^()]*\)[+*?]"),  # nested quantifier: (a+)*  (a*b)*
    re.compile(r"\(\.\*[^()]*\)[+*]"),         # wildcard group: (.*)*
]
_ALT_UNDER_REP = re.compile(r"\(([^()]*)\|([^()|]*)(?:\|[^()]*)*\)[+*]")


def _has_redos_structure(regex: str) -> bool:
    """Heuristic catastrophic-backtracking check. Not a proof. Catches:
      - nested quantifiers ((a+)*, (a*b)+)
      - wildcard groups under repetition ((.*)*)
      - alternation under repetition where one branch is a prefix of another
        ((a|aa)*, (ab|a)*) — these overlap and explode on non-matching input.
    Does NOT flag non-overlapping alternation ((a|b)*) which is safe."""
    if any(p.search(regex) for p in _REDOS_SHAPES):
        return True
    for m in _ALT_UNDER_REP.finditer(regex):
        branches = [b for b in m.group(0).strip("()*+").split("|") if b]
        for i, a in enumerate(branches):
            for b in branches[i + 1:]:
                # If one branch is a literal prefix of another, the alternation
                # overlaps and the engine backtracks combinatorially.
                if a.startswith(b) or b.startswith(a):
                    return True
    return False
```
