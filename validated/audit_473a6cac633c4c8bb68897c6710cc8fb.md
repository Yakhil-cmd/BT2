### Title
Cross-organization webhook forgery bypasses CI/status gating and can spoof events for repositories not owned by the authenticating organization - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/status_handler.rb`, `app/models/shipit/webhooks/handlers/handler.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/webhook secret to validate the HMAC signature against using an **attacker-controlled** field of the unverified JSON body (`repository.owner.login`, falling back to `organization.login`), then verifies the signature with that org's secret. Once verification passes, the handlers dispatched via `Shipit::Webhooks.for_event` act on **other, independent fields** of the same payload — `repository.full_name` (`Handler#repository_name`) or, in `StatusHandler`, just the raw `sha` with no repository scoping at all — to decide which `Stack`/`Commit` to mutate. Nothing binds "the organization whose secret produced a valid signature" to "the repository/commit that the handler ends up writing to."

### Finding Description
`verify_signature` in `app/controllers/shipit/webhooks_controller.rb:24-49` computes `repository_owner` from the untrusted body and uses it to look up the GitHub App config: [1](#0-0) [2](#0-1) 

`Shipit.github(organization:)` (`lib/shipit.rb:170-181`) picks the `GitHubApp` (and thus the `webhook_secret`) purely from that same untrusted `organization` string in multi-org deployments (`config/secrets.yml`'s `github: <OrgOne>/<OrgTwo>` schema, documented in `docs/setup.md`): [3](#0-2) 

Once the HMAC check passes (using the secret belonging to whatever org string the attacker put in the payload), the whole raw body — including any other field — was written by the attacker, since they know the secret for the org they named. Handlers then locate the target record from a **different, unverified** field:

- `Handler#stacks`/`#repository_name` uses `payload.dig('repository', 'full_name')`, entirely decoupled from the `repository_owner` used for signature routing: [4](#0-3) 

- `StatusHandler#process` is even less scoped — it looks up `Commit` **by `sha` alone**, with no repository/organization check whatsoever: [5](#0-4) 

This reproduces the report's bug class: a field that is acted upon (`repository.full_name` / `sha`) is never covered by the trust decision that was actually verified (`repository.owner.login` used only to pick the signing secret). The analog to the ERC165/`supportsInterface` bug is the same "verify one thing, act on another" pattern: the controller "verifies" org A's signature but the handler mutates data belonging to org B's repository/commit, exactly matching the required binding: *"an organization that authenticated versus the repository that is written."*

### Impact Explanation
Any party who has legitimately installed the Shipit GitHub App on **their own** organization (an unprivileged, self-service action requiring no Shipit account or Shipit privileges) knows that organization's `webhook_secret` and can therefore produce a valid `X-Hub-Signature` for **any** JSON body of their choosing. Because handler dispatch keys off unrelated fields:

- `PushHandler`/`Handler#stacks` — attacker can set `repository.owner.login` to their own org (to pass signature verification) but `repository.full_name` to a victim org/repo tracked by Shipit, triggering `stack.sync_github` on stacks they do not own.
- `StatusHandler` — attacker can forge a commit `status` event with `sha` equal to any commit sha in a victim's tracked repository (commit shas are often publicly known/predictable from public GitHub history) and `state: "success"`/`context`, invoking `Commit#create_status_from_github!` for that commit regardless of which repository it belongs to. Since Shipit's deploy safety gating and `DeploySpec`/`CommitChecks` rely on GitHub `status`/`check_suite` records to decide whether commits are deployable, this allows an attacker with no relationship to the victim repository to inject fabricated passing/failing CI status on victim commits — undermining the CI-gating precondition for deploys and enabling an unauthorized deploy path.
- `PullRequest` handlers (opened/closed/labeled/etc.) similarly resolve target `Repository`/`ReviewStack` via `params.repository.full_name`, independent of the org used for signature verification.

This crosses the required boundary ("escalation into authorization... an unauthorized deploy") because it lets an attacker who only controls their own org's webhook secret manipulate state (commit statuses, review-stack provisioning/archival, sync triggers) belonging to a different, victim organization's repositories that Shipit tracks.

### Likelihood Explanation
Requires a multi-GitHub-App-organization Shipit deployment (`config/secrets.yml` with the per-organization `github:` schema, as documented in `docs/setup.md` and exercised by `test/dummy/config/secrets_double_github_app.yml`), where an attacker legitimately controls the webhook secret for at least one configured organization while Shipit tracks repositories belonging to other organizations. This is a real, documented, supported configuration in this engine, not a hypothetical. The `StatusHandler` case additionally requires knowledge of a target commit sha, which is often obtainable from public repository history.

### Recommendation
Bind the verified signing identity to the data the handler acts upon:
- After selecting the GitHub App/secret via `repository_owner`, re-derive and cross-check that `repository.full_name`'s owner segment matches the same `repository_owner`/organization used to verify the signature, rejecting mismatches before dispatching to handlers.
- In `StatusHandler#process`, scope the `Commit` lookup by the commit's associated stack/repository and verify that repository's owner matches the authenticated organization, instead of matching on `sha` alone.
- More generally, apply the same "verified organization" constraint inside `Handler#stacks`/`#repository_name` so all handlers reject payloads whose target repository does not belong to the organization whose secret validated the signature.

### Proof of Concept
1. Configure Shipit with two GitHub App organizations, `AttackerOrg` and `VictimOrg`, per `docs/setup.md`'s multi-org schema; attacker legitimately installs the Shipit app on `AttackerOrg` and thus knows `AttackerOrg`'s `webhook_secret`.
2. Attacker crafts a `status` webhook JSON body:
```json
{
  "sha": "<known commit sha from VictimOrg/victim-repo>",
  "state": "success",
  "context": "ci/tests",
  "repository": { "owner": { "login": "AttackerOrg" }, "full_name": "AttackerOrg/whatever" }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC(AttackerOrg_webhook_secret, body)` and POSTs to `/github/webhooks` with header `X-Github-Event: status`.
4. `WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-30`) resolves `repository_owner` = `"AttackerOrg"`, fetches `Shipit.github(organization: "AttackerOrg")`, and successfully verifies the signature (it was computed with the correct secret for that org).
5. `StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`) then runs `Commit.where(sha: params.sha)` — matching the `VictimOrg/victim-repo` commit — and calls `create_status_from_github!`, injecting a forged CI status onto a commit in a repository the attacker has no relationship to, despite the signature only proving control of `AttackerOrg`.
