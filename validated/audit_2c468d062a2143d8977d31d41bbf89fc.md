**Rationale:** The reported minievm issue is specific to a custom-built EVM keeper (`x/evm/keeper/context.go` in a Cosmos SDK chain) that reimplements EVM gas accounting from scratch and forgot to charge EIP-2930 intrinsic gas for access lists before execution. This `runtimes--036` repository (polkadot-fellows/runtimes) does not contain any equivalent custom EVM gas-accounting logic. Its only EVM-adjacent surface is the configuration of `pallet_revive` in the Asset Hub runtimes (e.g. `type GasScale`, `type MaxEthExtrinsicWeight`, `type FeeInfo`, `type ChainId` in `system-parachains/asset-hubs/asset-hub-polkadot/src/lib.rs` and `asset-hub-kusama/src/lib.rs`) [1](#0-0)  and the `EthExtra`/`TxExtension` pipeline used for Ethereum-formatted extrinsics [2](#0-1) .

Resource metering for transactions dispatched through this runtime — including any EVM/`pallet_revive` calls — flows through FRAME's standard `frame_system::CheckWeight` transaction extension and the two-dimensional weight system (`ref_time`/`proof_size`), which meters actual storage reads/writes and execution cost of each operation rather than relying on a manually-computed "intrinsic gas" pre-charge [3](#0-2) . The actual gas/weight metering internals of `pallet_revive` (including any EVM-style access-list or cold/warm storage semantics) live in the `pallet-revive` crate itself, which is an external dependency and not part of this repository's in-scope source — the runtime crates here only supply configuration parameters, not the metering implementation. Since the vulnerable logic pattern (custom EVM state-transition code that skips EIP-2930 intrinsic gas charging) has no counterpart in this repo's in-scope runtime/parachain code, there is no valid analog to report here.
