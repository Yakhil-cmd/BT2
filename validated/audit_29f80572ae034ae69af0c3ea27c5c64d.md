### Title
Webhook signature verified against `repository.owner.login`'s app while stack writes are keyed on the unverified `repository.full_name` field, enabling cross-organization webhook forgery - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which `GitHubApp` (and therefore which `webhook_secret`) to validate the HMAC signature against using `repository_owner`, derived from `params.dig('repository', 'owner', 'login')`. However, every webhook handler (`Shipit::Webhooks::Handlers::Handler#stacks`/`#repository_name`) resolves the target `Stack`/`Repository` using a *different* field of the same attacker-supplied JSON body: `payload.dig('repository', 'full_name')`. Nothing binds these two fields together. In a multi-organization Shipit deployment (a documented, supported configuration), an attacker who legitimately controls one configured organization's GitHub App/webhook secret can forge a signature that is valid for "their" organization while setting `repository.full_name` to point at a completely different, victim organization's tracked repository, causing Shipit to act on that victim stack.

### Finding Description
`Shipit.github(organization: repository_owner)` in `lib/shipit.rb` supports per-organization `GitHubApp` configuration, each with its own `webhook_secret`: [1](#0-0) 

The webhook controller uses this per-organization lookup to pick the secret used for HMAC verification: [2](#0-1) [3](#0-2) 

`repository_owner` is entirely attacker-controlled input taken from the unauthenticated JSON body (`params.dig('repository', 'owner', 'login')`, falling back to `params.dig('organization', 'login')`). `verify_webhook_signature` only proves that the raw body was HMAC-signed with *some* configured organization's secret — it says nothing about which repository the rest of the payload actually references: [4](#0-3) 

After the signature check passes, `WebhooksController#create` dispatches the same JSON body to handlers, which resolve the affected `Stack` using a *different* field, `repository.full_name`, with no cross-check against `repository.owner.login`: [5](#0-4) 

For example, `PushHandler` uses `stacks` (i.e. `repository.full_name`) to look up and act on any matching, non-archived `Stack`, entirely independent of which organization's secret was used to authenticate the request: [6](#0-5) 

Concretely: if a Shipit instance is configured (per `docs/setup.md` / `config/secrets.development.example.yml`) with multiple GitHub organizations, each with its own `webhook_secret`, an attacker who administers *any one* of those organizations' GitHub Apps can:
1. Set `repository.owner.login` (or `organization.login`, for org-scoped events) to their own organization "AttackerOrg" so `Shipit.github(organization: "AttackerOrg")` selects the `GitHubApp` whose secret they know.
2. Compute a valid `X-Hub-Signature` HMAC using that known secret over the full raw body.
3. Set `repository.full_name` (and any other payload fields the handler reads, e.g. `sha`, `state`, `ref`, `after`) to reference a repository/stack belonging to a completely different, victim organization tracked by the same Shipit instance.

`verify_signature` passes (their own org's secret matches their own signature), and the handler then acts on the victim's stack because it never checks that `full_name`'s owner matches the verified `repository_owner`.

### Impact Explanation
This breaks the trust binding "organization that authenticated == repository that is written." Concretely reachable handlers that operate on the mismatched `full_name` target include:
- `PushHandler`, which triggers `stack.sync_github(expected_head_sha:)` for arbitrary victim stacks, forcing resyncs and spec cache invalidation using attacker-chosen `after` SHAs.
- Other repository-scoped handlers (status, check_suite) that resolve their target the same way via `Handler#stacks`/`#repository_name`, letting an attacker inject unauthenticated-looking but "signature-valid" webhook events against a repository they do not own or control, on a shared multi-tenant Shipit instance.

This is a cross-tenant integrity issue: it allows a customer/organization with legitimate access to only their own GitHub App configuration on a shared Shipit deployment to inject spoofed events for other organizations' repositories, undermining the very purpose of per-organization webhook secrets and potentially disturbing CI/deploy state (unwarranted syncs, spec cache invalidation, and any other repository-scoped webhook handler that trusts `full_name`) for a stack it should have no authority over.

### Likelihood Explanation
This requires the deployment to be configured with multiple GitHub organizations (a documented, first-class feature — see `docs/setup.md` and `config/secrets.development.example.yml` multi-org example), and requires the attacker to be a legitimate administrator/owner of at least one of those organizations' GitHub App / webhook secret. This is a realistic and unprivileged-with-respect-to-the-victim-org scenario for any Shipit instance shared across multiple orgs/tenants, which is exactly the use case the per-organization config exists to support.

### Recommendation
When resolving the target repository/stack in `Shipit::Webhooks::Handlers::Handler` (and any handler using `payload.dig('repository', ...)`), verify that the organization embedded in `repository.full_name` (or `repository.owner.login`) matches the `repository_owner` value that was actually used to select the `GitHubApp`/secret in `WebhooksController#verify_signature`. Reject (422) any webhook where these two values disagree, ensuring the authenticated organization and the organization whose repository is being written are cryptographically the same.

### Proof of Concept
1. Configure Shipit with two organizations in `secrets.yml`: `victimorg` (secret `S_v`) and `attackerorg` (secret `S_a`), each with a `Stack` tracking a repository under their respective org.
2. As the administrator of `attackerorg`'s GitHub App (who legitimately knows `S_a`), craft a JSON push payload:
   ```json
   {
     "ref": "refs/heads/master",
     "after": "<attacker-chosen sha>",
     "repository": {
       "owner": { "login": "attackerorg" },
       "full_name": "victimorg/victim-repo"
     }
   }
   ```
3. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(S_a, raw_body)>` and POST it to `/webhooks` with `X-Github-Event: push`.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: "attackerorg")` and successfully verifies the signature against `S_a`.
5. `PushHandler` is dispatched with the same payload; `Handler#stacks` resolves `Repository.from_github_repo_name("victimorg/victim-repo")` and calls `stack.sync_github(expected_head_sha: "<attacker-chosen sha>")` on the victim's stack — despite the request never being authenticated by `victimorg`'s webhook secret.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
