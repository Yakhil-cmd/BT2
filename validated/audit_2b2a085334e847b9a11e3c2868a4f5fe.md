Based on the code, the vulnerability described is real and matches an actual configuration weakness present identically in Encointer, Bulletin, Collectives, Coretime (Kusama/Polkadot) and People (Kusama/Polkadot).

### Title
Origin confusion via `AliasOriginRootUsingFilter<AssetHubLocation, Everything>` allows any AssetHub signed account to alias into arbitrary Encointer locations - (File: system-parachains/encointer/src/xcm_config.rs)

### Summary
Encointer's `TrustedAliasers` includes `AliasOriginRootUsingFilter<AssetHubLocation, Everything>`, which allows any XCM whose raw origin equals the bare `AssetHubLocation` (the sibling-chain identity assigned by the XCMP transport, not an account-scoped sub-location) to alias into *any* target `Location` on Encointer. Because AssetHub's `pallet_xcm::Config::SendXcmOrigin` permits any signed account to call `send()` with an attacker-controlled raw `Xcm` program [1](#0-0) , and the outgoing message is forwarded unmodified over XCMP (no per-account `DescendOrigin` is injected by `pallet_xcm::send`), every message from AssetHub arrives at Encointer with the same chain-level origin `AssetHubLocation`, regardless of which internal account triggered it.

### Finding Description
Encointer defines:
```
pub type TrustedAliasers = (
    AliasChildLocation,
    AliasAccountId32FromSiblingSystemChain,
    AliasOriginRootUsingFilter<AssetHubLocation, Everything>,
    AuthorizedAliasers<Runtime>,
);
``` [2](#0-1) 

`AliasOriginRootUsingFilter<Origin, Filter>` allows aliasing whenever the incoming raw origin equals `Origin::get()` and `Filter::contains(target)`. With `Filter = Everything`, any `target` Location qualifies, so once the raw origin is `AssetHubLocation`, the executor accepts an `AliasOrigin(target)` instruction for *any* `target`, including an arbitrary victim `AccountId32` location.

Critically, Encointer's `Barrier` explicitly grants this raw origin **free, unpaid execution rights** via:
```
AllowExplicitUnpaidExecutionFrom<
    (ParentOrParentsPlurality, Equals<AssetHubLocation>, AssetHubPlurality),
    TrustedAliasers,
>,
``` [3](#0-2) 

The raw origin `AssetHubLocation` is set by the XCMP receiving logic based on the sending parachain's channel identity — it is not something embedded per-account inside the message. AssetHub's `pallet_xcm::Config` sets `SendXcmOrigin = EnsureXcmOrigin<RuntimeOrigin, LocalPalletOrSignedOriginToLocation>` with the comment "Any local signed origin can send XCM messages" [1](#0-0) . This `SendXcmOrigin` conversion is only used locally (fee/authorization check on AssetHub); the raw `Xcm` program supplied by the caller is forwarded to `XcmRouter`/XCMP unmodified — there is no compulsory `DescendOrigin` wrapping tying the outgoing message to the sender's specific sub-account. Consequently, a plain signed AssetHub account can submit `pallet_xcm::send(dest=Encointer, message=[AliasOrigin(victim_location), Transact(call=Balances::transfer_all(victim, attacker))])`, and Encointer will process it with raw origin `AssetHubLocation`, pass the `AllowExplicitUnpaidExecutionFrom` barrier for free, alias to `victim_location` via `AliasOriginRootUsingFilter`, and then execute the embedded `Transact` call as the victim.

The doc comment "Allow AssetHub root to alias into anything" [4](#0-3)  conflates "AssetHub-as-a-chain" (any message from that chain) with "AssetHub's privileged/root logic," but the filter only checks the chain-level origin, not any AssetHub-side authorization level.

### Impact Explanation
Any unprivileged AssetHub account can impersonate any account/location on Encointer, enabling arbitrary asset movement (e.g., draining victim balances via `Balances::transfer_all`) or execution of any privileged-looking call that is authorized only by origin, on the victim's behalf.

### Likelihood Explanation
Precondition is only "attacker holds a normal signed AssetHub account," which is trivially satisfiable, and `pallet_xcm::send` is a standard user-facing extrinsic on AssetHub. The exploit is fully repeatable and requires no governance/relayer/leaked-key assumptions — it only depends on the chain-level XCMP origin tagging behavior, which is a routine protocol property.

### Recommendation
Restrict `AliasOriginRootUsingFilter<AssetHubLocation, Everything>` to a narrow, purpose-specific `Filter` (e.g., only migration-related pallet locations or specific known accounts) instead of `Everything`, or gate it behind an explicit AssetHub-side privileged origin marker (e.g., require the message to originate specifically from AssetHub's governance/superuser XCM path rather than any signed account), mirroring the narrower `PolkadotOrEthereumGlobalConsensus`-style filters used elsewhere in the same codebase (e.g., `AliasOriginRootUsingFilter<bridging::to_polkadot::AssetHubPolkadot, PolkadotOrEthereumGlobalConsensus>` in asset-hub-kusama) [5](#0-4) .

### Proof of Concept
xcm-emulator integration test plan:
1. On AssetHub, as a normal signed `attacker` account, call `PolkadotXcm::send` targeting Encointer with a raw `Xcm` program: `AliasOrigin(victim_account_location)` followed by `Transact(call = pallet_balances::Call::transfer_all { dest: attacker, keep_alive: false })`.
2. On Encointer, assert the message is accepted by the `Barrier` (`AllowExplicitUnpaidExecutionFrom` matching `Equals<AssetHubLocation>`) without fee payment.
3. Assert `AliasOrigin` succeeds via `TrustedAliasers::AliasOriginRootUsingFilter<AssetHubLocation, Everything>` and the resulting dispatch origin equals `victim_account`'s origin.
4. Assert `victim_account`'s Encointer balance is transferred to `attacker`, and that this occurred without any entry in `pallet_xcm::AuthorizedAliasers` for `victim_account -> AssetHubLocation`.
