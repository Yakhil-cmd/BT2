### Title
Uncaught exception in `decryptPackage` crashes the wallet/hub process on receipt of a device message encrypted to an unrecognized key - (File: device.js)

### Summary
`device.js`'s `decryptPackage()` throws an `Error` inside a `setTimeout` callback when a received device message's `encrypted_package.dh.recipient_ephemeral_pubkey` does not match the local temporary, previous-temporary, or permanent device key. Because the throw happens asynchronously inside `setTimeout`, it escapes every surrounding `try/catch` in the caller chain and becomes an uncaught exception, crashing the Node.js process. This is directly analogous to CVE-2020-14800's "easily exploitable... network access... complete DOS (crash/hang)" bug class, where a low-privileged remote actor supplies malformed/mismatched cryptographic material to a server-side handler and triggers an unhandled fault that takes down the whole process.

### Finding Description
In `handleJustsaying`, the `hub/message` case performs signature verification on the outer, unencrypted part of `objDeviceMessage` using the sender-supplied `pubkey` field (i.e., the attacker's own device key, which is entirely attacker-controlled and self-consistent) — `ecdsaSig.verify(objectHash.getDeviceMessageHashToSign(objDeviceMessage), objDeviceMessage.signature, objDeviceMessage.pubkey)` [1](#0-0) . This only proves the message was signed by *some* device key, not that the sender is a known correspondent — the "known device" check happens later, after decryption is already attempted [2](#0-1) .

The decryption call is wrapped in try/catch, but that only protects against *synchronous* throws:
```
try {
    var json = decryptPackage(objDeviceMessage.encrypted_package);
}
catch(e){
    return respondWithError("failed to decrypt: " + e);
}
``` [3](#0-2) 

Inside `decryptPackage`, if `dh.recipient_ephemeral_pubkey` doesn't match any of the three known keys (temp, previous temp, permanent), the function logs a message and then schedules a throw via `setTimeout`:
```
else{
    console.log("message encrypted to unknown key");
    setTimeout(function(){
        throw Error("message encrypted to unknown key, device "+my_device_address+...);
    }, 100);
    return null;
}
``` [4](#0-3) 

Because this `throw` executes in a separate macrotask (100ms later), it is outside the call stack of the `try/catch` in `handleJustsaying`, and outside any other `try/catch` in the codebase. Node.js treats it as an uncaught exception, and unless a global `process.on('uncaughtException', ...)` handler is installed and configured to swallow the error and keep the process alive, the process terminates. An attacker only needs to construct an `encrypted_package.dh.recipient_ephemeral_pubkey` value that never matches the victim's current keys (trivial — e.g., a random valid base64 pubkey), self-sign the outer message with their own device keypair, and send it as a `hub/message` addressed to the victim device.

### Impact Explanation
Triggering this path repeatedly allows an attacker who knows (or can address messages to) a victim's device address — including any paired correspondent or an attacker able to reach the message-routing hub logic for that device — to remotely and repeatedly crash the victim's wallet process. This satisfies the "network unable to confirm new units" / node-disagreement style impact bar in that a crashed wallet process cannot process transactions, sign trigger data, or forward private payments while down, and can be crashed again immediately upon restart, producing a persistent denial of service against that device/wallet.

### Likelihood Explanation
Exploitation only requires constructing a self-signed device message with a `dh.recipient_ephemeral_pubkey` that does not match the target's known keys — no cryptographic break, no privileged access, and no race condition is needed. The check for "known correspondent" occurs after decryption is attempted, so even pairing-adjacent or loosely-trusted senders can reach this code path. This makes the bug easily and repeatably triggerable, matching the "easily explo625able" / low-complexity characterization of the CVE analog.

### Recommendation
Do not `throw` inside the `setTimeout` callback. Instead, emit a `nonfatal_error` event (as already hinted by the commented-out line) or otherwise handle the "unknown key" condition without raising an exception that can escape all error boundaries, e.g.:
```
console.log("message encrypted to unknown key");
eventBus.emit('nonfatal_error', "message encrypted to unknown key, device "+my_device_address+", len="+objEncryptedPackage.encrypted_message.length, new Error('unknown key'));
return null;
```
Also ensure `decryptPackage` never throws asynchronously from paths reachable by unauthenticated/unverified senders, and add a top-level safety net (`process.on('uncaughtException')`) that logs and continues rather than terminating the process.

### Proof of Concept
1. Attacker generates a device keypair and self-signs a `hub/message` payload with a valid outer signature (satisfies the check at `device.js:167`).
2. Attacker sets `encrypted_package.dh.recipient_ephemeral_pubkey` to an arbitrary valid-format base64 pubkey that is guaranteed not to equal the victim's current temp/prev-temp/permanent device pubkeys (trivial since these are secret to the victim).
3. Attacker sends this message via the hub addressed to the victim device (`to: victim_device_address`).
4. Victim's `handleJustsaying('hub/message', ...)` passes the outer signature check, then calls `decryptPackage`, which falls into the `else` branch and schedules `setTimeout(() => { throw Error(...) }, 100)`.
5. 100ms later, the thrown error is uncaught by any try/catch and crashes the victim's Node.js process (assuming no global handler intercepts and survives it).
6. Repeat to produce a persistent DoS against the victim's wallet/device process. [5](#0-4)
