### Title
CCMenu endpoint bypasses per-client stack scoping, allowing any authenticated `ApiClient` to read another stack's status - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Api::CCMenuController` overrides `#stack` to call `Stack.from_param!(params[:stack_id])` directly instead of using the scoped lookup (`stacks.from_param!`) used by `BaseController` and `Api::StacksController`. This means any valid `ApiClient` credential - even one whose `stack_id` restricts it to a single stack - can read the CCMenu XML (build/deploy status) of *any* stack by simply changing the `stack_id` param, regardless of the `stack_id` the client was scoped to.

### Finding Description
The binding that must hold for per-client stack scoping to work is: `current_api_client.stack_id == requested stack.id` (or `current_api_client.stack_id?` is false, i.e., unscoped client). `BaseController` enforces this via `#stacks` / `#stack`: [1](#0-0) 
and `Api::StacksController#stack` reuses this scoped helper: [2](#0-1) 

`Api::CCMenuController`, however, overrides `#stack` with an **unscoped** lookup, never referencing `current_api_client.stack_id` at all: [3](#0-2) 

`require_permission :read, :stack` only checks that the client's `permissions` array contains the string `"read:stack"` via `ApiClient#check_permissions!`: [4](#0-3) 
it never checks whether the target stack matches the client's `stack_id`. So a client that was intentionally scoped to Stack A (has `stack_id = A.id` and permission `read:stack`) can call `GET /api/stacks/B/ccmenu.xml?token=<A's token>` and receive Stack B's deploy/build status, because `#stack` in this controller never consults the client's scope.

Regarding the specific mechanism proposed in the question (malformed `params[:token]` plus valid Basic-Auth for a *different* client causing impersonation): this is not itself a distinct bug. `ApiClient.authenticate` on a garbage token simply fails and returns `nil`, causing `super` to run the same Basic-Auth path found in `BaseController#authenticate_api_client`: [5](#0-4) 
This resolves `@current_api_client` to exactly the client whose valid credentials were supplied - there is no cross-client identity confusion. The actual exploitable defect is independent of which credential-supplying mechanism (token param vs. Basic-Auth) is used: it is the unscoped `#stack` lookup in `ccmenu_controller.rb` itself.

### Impact Explanation
Any holder of a legitimately-issued, stack-scoped `ApiClient` token (created by a Shipit operator for one specific stack, e.g. an internal CI badge integration) can enumerate and read the CI/deploy status (branch, latest deploy state, success/failure) of every other stack on the instance, not just their own, via `GET .../ccmenu.xml?stack_id=<other>&token=<their own token>`. This is a cross-tenant information disclosure - matching the "unauthenticated/unauthorized read of stack state" category - repeatable against arbitrary stacks by varying `stack_id`. It does not by itself grant write/deploy capability or expose GitHub credentials.

### Likelihood Explanation
Requires the attacker to already hold a valid `ApiClient` token scoped to some stack with `read:stack` permission (a realistic precondition, since such tokens are commonly issued to CI dashboards/status badges, which are lower-trust integrations by design). No GitHub secrets, session, or team membership needed. The exploit is a single unauthenticated GET request with a query param change - trivial and fully repeatable.

### Recommendation
Change `Api::CCMenuController#stack` to use the same scoped lookup as `BaseController`/`Api::StacksController` (i.e., `stacks.from_param!(params[:stack_id])`) so that a stack-scoped `ApiClient` cannot resolve stacks outside its `stack_id`.

### Proof of Concept
In `test/controllers/api/ccmenu_controller_test.rb` (existing file):
1. Create Stack A and Stack B.
2. Create `ApiClient` C with `stack_id: A.id`, `permissions: ['read:stack']`.
3. `get :show, params: { stack_id: B.to_param, token: C.authentication_token }`.
4. Assert the response is **not** `200` with Stack B's XML (expected: `403`/`404`), but current code returns `200` and renders Stack B's CCMenu XML - demonstrating the scope bypass.
