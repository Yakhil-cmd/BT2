### Title
Webhook signature verification selects the signing organization from an unverified payload field that is decoupled from the repository field handlers act on, enabling cross-organization webhook forgery - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` picks which GitHub App / `webhook_secret` to validate an incoming webhook signature against by reading `repository.owner.login` (or `organization.login`) straight out of the **unverified** JSON body. The downstream event handlers, however, resolve the `Repository` record to mutate using a different field from the very same untrusted body: `repository.full_name`. Because the trust decision (whose secret to check) and the action target (which repository/stack gets written) are bound to two independently-controlled JSON fields, an attacker who legitimately knows one organization's webhook secret can forge a validly-signed webhook whose `repository.full_name` names a repository belonging to a different organization configured on the same Shipit instance.

### Finding Description
`WebhooksController#verify_signature` resolves the signing secret this way: [1](#0-0) 

`repository_owner` reads directly from the request body, before any signature check has occurred: [2](#0-1) 

`Shipit.github(organization: repository_owner)` loads the `GithubApp` config for that organization (each org can have its own `webhook_secret`, as documented and tested in the multi-org secrets fixture): [3](#0-2) 

Once the signature is verified against *that* org's secret, `create` dispatches the same payload to event handlers: [4](#0-3) 

But every handler resolves the target repository from a different JSON field — `repository.full_name` — with no relation enforced to the field used to pick the verifying secret: [5](#0-4) 

`PushHandler` then syncs a stack to an attacker-supplied `after` SHA, and `StatusHandler` writes forged commit statuses, both scoped to whatever repository `repository.full_name` names: [6](#0-5) [7](#0-6) 

**Binding broken:** `organization authenticated (via repository.owner.login / organization.login, used to select the webhook secret) != repository that is written (via repository.full_name, used by handlers)`. Both values originate from the same attacker-supplied HTTP body, and nothing ties them together.

**Before the attack:** signature verification is meant to guarantee "this event genuinely originates from the org whose secret matches, for that org's own repositories."
**After the attacker's crafted request:** signature verification only proves "the request body's `owner.login`/`organization.login` field matches an org whose secret the attacker knows" — while `repository.full_name` (and therefore the actual mutated `Repository`/`Stack`) can point at an entirely different, unrelated organization hosted on the same Shipit instance.

### Impact Explanation
This is exploitable only in the (supported, documented) multi-organization deployment mode, where a single Shipit instance manages several GitHub Apps/orgs, each with its own `webhook_secret`. In that configuration, an attacker who is a legitimate admin/owner of Org A's GitHub App (and therefore knows Org A's `webhook_secret`, which they set themselves when installing the app — not a Shipit-internal secret) can:

1. Set `organization.login` (or `repository.owner.login`) = `"OrgA"` so `verify_signature` selects and successfully checks against Org A's secret.
2. Set `repository.full_name` = `"OrgB/target-repo"`, targeting a repository belonging to a different tenant.

The forged, "verified" webhook is then processed against Org B's stacks:
- Via `PushHandler`, it enqueues `GithubSyncJob` advancing Org B's stack head to an attacker-chosen SHA, feeding Shipit's automatic deploy pipeline with a forged head commit — an unauthorized deploy/rollback vector.
- Via `StatusHandler`, it forges commit statuses on Org B's commits, which can flip merge/deploy gating checks that other automation relies on.

This is a cross-organization write achieved purely through crafted, cross-tenant webhook payloads — matching the Critical "cross-repository writes / unauthorized deploy or merge" class, since the org whose credential is verified is not required to match the repository actually mutated.

### Likelihood Explanation
Requires: (a) the Shipit instance to be configured with more than one GitHub organization/App (each with a distinct `webhook_secret`, a documented and tested configuration), and (b) the attacker to control or know the `webhook_secret` of at least one configured org (which they would, as an admin of their own org's GitHub App installation — not a privileged Shipit credential). Given those preconditions, forging the payload is trivial (compute HMAC over an attacker-chosen body). No Shipit session, API token, or GitHub write access to the victim org is required.

### Recommendation
After selecting the org/secret to verify against (via `repository_owner`), re-validate that the *same* field used for org selection matches the owner of `repository.full_name` (or, better, verify the signature only after resolving the actual target `Repository`/`Stack` and require the resolved repository's known owner to match the org whose secret was used). Reject the webhook if these do not agree.

### Proof of Concept
1. Configure Shipit with two orgs, `OrgA` and `OrgB`, each with distinct `webhook_secret`s (as in `test/dummy/config/secrets_double_github_app.yml`), and a `Stack` for `OrgB/target-repo`.
2. As an attacker who administers `OrgA`'s GitHub App (and thus knows `OrgA`'s webhook secret), build a `push` payload:
   ```json
   {
     "organization": { "login": "OrgA" },
     "repository": { "full_name": "OrgB/target-repo", "owner": { "login": "OrgA" } },
     "ref": "refs/heads/master",
     "after": "<attacker-chosen-sha>"
   }
   ```
3. Compute `X-Hub-Signature: sha1=<hmac>` using `OrgA`'s `webhook_secret`.
4. POST to `/webhooks` with `X-Github-Event: push`.
5. `verify_signature` looks up `Shipit.github(organization: "OrgA")` (from `repository.owner.login`) and the signature passes.
6. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("OrgB/target-repo")` and enqueues `GithubSyncJob` for `OrgB`'s stack with `expected_head_sha` = attacker-chosen SHA, despite the request never being signed by `OrgB`.
