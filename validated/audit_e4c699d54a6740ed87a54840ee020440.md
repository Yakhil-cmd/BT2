### Title
Authenticated denial of service via unhandled crash-on-throw in AA response-unit validation - ([File: aa_composer.js])

### Summary
Consul's CVE-2026-19012 lets a caller with config-entry write permission submit a config-entry that crashes the agent because an edge case in the Enterprise→Community downgrade path is not gracefully handled and instead aborts the process. Ocore has an analogous class of bug in the Autonomous Agent (AA) trigger-execution engine: any unprivileged user can trigger an AA by sending it a payment, and the resulting internally-composed AA response unit is fed back through the general unit validator `validation.validate()`. Several of the validation outcome branches inside `aa_composer.js`'s `validateAndSaveUnit` are treated as "impossible" and simply `throw Error(...)` instead of being handled, and any uncaught exception is deliberately re-thrown by the top-level handler to kill the whole node process.

### Finding Description
`handleTrigger()` composes an AA's response unit from a base/parameterized AA definition and formula-evaluated messages, then calls `validateAndSaveUnit()`, which invokes `validation.validate()`: [1](#0-0) 

Every callback except `ifUnitError` (which is routed to a graceful `bounce()`) throws a bare `Error`:
- `ifJointError` → throw
- `ifTransientError` → throw
- `ifNeedHashTree` → throw
- `ifNeedParentUnits` → throw
- `ifOkUnsigned` → throw
- `ifOk` with `sequence !== 'good'` ("nonserial AA") → throw

These throws happen synchronously inside the async validation callback chain triggered from `handlePrimaryAATrigger`/`handleTrigger`, which itself runs inside `network.js`'s joint-handling/writer pipeline. Any exception that escapes there becomes an `uncaughtException`, and the global handler intentionally re-throws it to crash the process: [2](#0-1) 

`validation.validate()` is a large, evolving general-purpose validator (parents, witnesses, TPS fee, authors, messages, doublespends, oversize fees, version gates, etc.), used for both normal units and, with `objJoint.aa = true`, for internally-generated AA response units. Because the AA composer assumes only `ifOk`/`ifUnitError` are reachable outcomes for its own generated unit, any future/edge-case change in `validate()` semantics (new version gate, new mci-based upgrade check, a corner case in parent/last-ball selection reachable through `pickParents()`, TPS-fee timing, doublespend racing between concurrent secondary AA triggers, etc.) that causes the composed AA unit to fall into `ifJointError`, `ifTransientError`, `ifNeedParentUnits`, `ifNeedHashTree`, or a non-`good` sequence will crash the entire node instead of being handled as a bounce/retry. Since AA execution is fully attacker-reachable — anyone can post a unit paying an AA to trigger it, and any unprivileged AA author can define arbitrary oscript logic that shapes the resulting messages/outputs/assets that feed into this composed unit — this is directly analogous to Consul's "config-entry write permission causes agent to exit unexpectedly."

### Impact Explanation
A crash in `validateAndSaveUnit()` propagates as an uncaught exception, which is intentionally re-thrown by `network.js`'s handler to kill the Node.js process (`throw err; // crash the process to avoid ending up in an inconsistent state`, at [3](#0-2) ). Because this occurs mid-way through `handlePrimaryAATrigger`'s DB transaction and `kvstore` batch, the node may also be left with a stuck/half-committed transaction on restart, compounding the denial-of-service beyond a simple respawn. Because AA triggers are processed automatically by every full node as part of normal DAG stabilization, a single well-crafted trigger (or AA definition combined with a trigger) that reaches one of these throw branches can repeatedly crash every full node in the network as they each independently execute the same AA logic — a systemic denial of service, not just a single-node crash.

### Likelihood Explanation
Reaching one of these throw branches requires finding a specific combination of AA definition and trigger data that pushes the internally-generated response unit into an edge case of `validation.validate()` not anticipated by `aa_composer.js` authors (e.g., a nonserial/doublespend condition among concurrently processed secondary triggers touching the same outputs, or a validator edge case tied to mci-gated feature upgrades). This requires deep knowledge of oscript and the validator internals, similar to the difficulty of hitting HashiCorp's specific downgrade-path edge case. It is plausible for a skilled attacker given ocore's history of adding new mci-gated validation branches, but a concrete unconditional trigger was not confirmed in this review — I could not find a fully worked, minimal PoC that guarantees hitting one of the throw branches from unprivileged input alone.

### Recommendation
Replace the `throw Error(...)` branches in `validateAndSaveUnit()`'s `ifJointError`, `ifTransientError`, `ifNeedHashTree`, `ifNeedParentUnits`, `ifOkUnsigned`, and the "nonserial AA" case with graceful handling (e.g., `bounce()` the trigger, log details, and continue processing other units) rather than crashing the whole process. At minimum, treat these as recoverable errors for the specific trigger/AA pair being processed instead of allowing them to propagate to the global `uncaughtException` handler.

### Proof of Concept
Not available — reaching a specific throw branch (e.g., `ifNeedParentUnits`/`nonserial AA`) requires crafting an AA definition/trigger pair that forces the internally generated response unit into an unanticipated validator branch, which was not fully demonstrated by static analysis alone. The reachability chain (trigger → `handleTrigger` → `validateAndSaveUnit` → `validation.validate` → throw → `uncaughtException` → process crash) is confirmed structurally via the cited code.
