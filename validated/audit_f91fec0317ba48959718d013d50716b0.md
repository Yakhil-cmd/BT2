### Title
Unscoped `Commit.where(sha:)` lookup in `StatusHandler#process` lets an attacker forge CI status and trigger `Stack#schedule_merges` for a victim repository - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` looks up commits by SHA globally, with no scoping to the repository that authenticated the webhook, unlike every other handler in the same directory. A `status` webhook that is legitimately signed for the attacker's own repository can therefore write a forged commit status onto, and trigger `Stack#schedule_merges` for, any `Stack` whose `Commit` shares that SHA — including stacks belonging to repositories the attacker never authenticated against.

### Finding Description
The broken binding: `Stack (schedule_merges invoked on) == Stack ∈ Repository.from_github_repo_name(payload.repository.full_name).stacks`. This binding is enforced in every sibling handler — `PushHandler#process` uses `stacks.not_archived.where(branch:)` [1](#0-0) , `CheckSuiteHandler#process` uses `stacks.where(branch: ...)` [2](#0-1) , and the `PullRequest::*` handlers all resolve `repository = Repository.from_github_repo_name(params.repository.full_name)` before touching any stack [3](#0-2) . The base `Handler#stacks` helper itself implements this scoping via `repository_name` derived from `payload.dig('repository', 'full_name')` [4](#0-3) .

`StatusHandler#process` never calls `stacks` or `Repository.from_github_repo_name`; it does a bare `Commit.where(sha: params.sha)` across the entire `commits` table and calls `create_status_from_github!` on every match: [5](#0-4) . Its `params` schema does not even require a `repository` field [6](#0-5) .

`create_status_from_github!` → `add_status` writes a `Status` row scoped to the *matched commit's* `stack_id` (attacker never chooses this — it's whichever stack owns the matching SHA) with attacker-controlled `state`/`description`/`context`/`target_url`, and then unconditionally runs `stack.schedule_merges if new_status.pending? || new_status.success?`: [7](#0-6) .

`verify_signature` in `WebhooksController` only proves the request was signed with the webhook secret for `repository_owner` (the org owning the *actual* sending repo) [8](#0-7) . It authenticates *who sent the event*, not *which commits the handler is allowed to touch*. Because `StatusHandler` ignores `payload['repository']` entirely, that authentication is disconnected from the resulting write. As stated in the precondition, if a commit SHA that exists in the attacker's own repo (e.g., via a fork, which carries over identical git objects/SHAs from the upstream victim repo) also exists as the `head` of a victim `Stack`'s queued `MergeRequest`, the attacker's own legitimately-signed `status` event for that SHA reaches `Commit.where(sha:)`, matches the victim's `Commit`, and triggers `stack.schedule_merges` for the victim `Stack` — a stack never reachable via the attacker's own `Handler#stacks`.

None of the listed guards close this gap: `verify_signature` is repo/org-authentication only, not SHA-to-repo authorization; the `ExplicitParameters` schema for `StatusHandler` has no `repository` requirement to scope against; `drop_unhandled_event` only checks the event type is registered, not the payload's repository; and `Stack#schedule_merges`/`ProcessMergeRequestsJob` do not re-validate that the triggering status actually originated from the stack's own repository.

### Impact Explanation
Per request, the attacker can (a) write an arbitrary forged `Status` record (state/description/context/target_url) onto a commit belonging to a repository/stack they never authenticated against, and (b) force `ProcessMergeRequestsJob` to run early for that victim stack, advancing merge-queue processing on attacker's timing rather than the victim's real CI cadence. This is a cross-tenant data-mutation bug: "a payload for one repository mutating another's stack/commit," matching the Critical impact category explicitly listed in scope. It is repeatable against any commit SHA that happens to be shared between an attacker-controlled repository and any victim `Stack`'s commits (most easily via a fork of the victim repo), and is not limited to a single victim — any Shipit-tracked repository whose commits are also reachable/forkable by the attacker is affected.

### Likelihood Explanation
The attacker needs: (1) a real GitHub repository that already has a working, correctly-signed Shipit webhook relationship to the target Shipit instance (i.e., the attacker's own org/repo must be one Shipit already trusts — a realistic condition in any multi-tenant Shipit deployment where many orgs/repos are onboarded), and (2) a commit SHA in that repo identical to a SHA that exists in the victim `Stack`'s commit history, which is trivially satisfied for forks of public repositories since git objects/SHAs are preserved across forks. No GitHub credentials, Shipit session, API token, or victim-repo collaborator access are required — only the ability to attach a commit status to a SHA in the attacker's own (authenticated) repository, which any repo owner/collaborator or CI system can do via the standard GitHub Statuses API.

### Recommendation
Scope `StatusHandler#process` the same way as `PushHandler`/`CheckSuiteHandler`: require and use `params.repository.full_name` to resolve the sending `Repository`, and constrain the commit lookup to `stacks.flat_map(&:commits).where(sha: params.sha)` (or equivalent join through the authenticated repository's stacks) instead of the global `Commit.where(sha: params.sha)`.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb
test "#process only updates commits belonging to the webhook-authenticated repository" do
  victim_stack = shipit_stacks(:shipit) # repository != attacker repo
  victim_commit = victim_stack.commits.create!(sha: 'deadbeef' * 5, ...)

  attacker_payload = {
    'sha' => victim_commit.sha,
    'state' => 'success',
    'context' => 'ci/attacker',
    'repository' => { 'full_name' => 'attacker/other-repo' } # different repo than victim_stack.repository
  }

  # Binding under test: Stack (schedule_merges invoked) must be ∈
  # Repository.from_github_repo_name(attacker_payload['repository']['full_name']).stacks
  attacker_repo_stacks = Shipit::Repository.from_github_repo_name('attacker/other-repo')&.stacks || Shipit::Stack.none
  refute_includes attacker_repo_stacks, victim_stack

  Shipit::Stack.any_instance.expects(:schedule_merges).never # expected: not called for out-of-scope stack

  Shipit::Webhooks::Handlers::StatusHandler.call(attacker_payload)

  assert_equal 'success', victim_commit.reload.status.state # FAILS today: write succeeds cross-repo
end
```
This test currently fails: `StatusHandler#process` writes the forged status to `victim_commit` and invokes `schedule_merges` on `victim_stack` even though `victim_stack` is not in `attacker_repo_stacks`.
