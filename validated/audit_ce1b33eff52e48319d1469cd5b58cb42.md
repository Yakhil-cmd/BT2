### Title
Cross-repository commit-status forgery via unscoped `sha` lookup in `StatusHandler#process` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` resolves the target of a GitHub `status` webhook with `Commit.where(sha: params.sha)`, a global lookup across every stack/repository in the Shipit instance, with no check that the commit's owning repository matches the repository that authenticated the webhook. Any attacker who controls a repository already registered with Shipit (and therefore possesses a valid, signed webhook channel for that repo/org) can forge a `status` payload whose `sha`, `context`, and `state` are fully attacker-controlled JSON fields, and have it applied to a commit belonging to a completely different, victim stack.

### Finding Description
The broken binding: the code assumes `commit.stack.github_repo_name == params.dig('repository', 'full_name')` (the status event only applies to the commit's own repository), but this equality is never checked.

Path:
1. `Shipit::WebhooksController#create` (app/controllers/shipit/webhooks_controller.rb:10-15) parses `request.raw_post` and dispatches to handlers for the event type.
2. `verify_signature` (app/controllers/shipit/webhooks_controller.rb:24-49) only validates the HMAC signature against the secret registered for `repository_owner` — the `owner.login` derived from the payload's own `repository`/`organization` object [1](#0-0) . It never checks that `sha`, `context`, or any other field in the JSON body actually belongs to that repository — those fields are simply attacker-supplied JSON, validated only by shape (`ExplicitParameters`), not by ownership.
3. `StatusHandler#process` then does:
```ruby
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
``` [2](#0-1) 
This query is global across the `commits` table (all stacks, all repositories) — it is not scoped by `params.dig('repository', 'full_name')` or by the stack that owns the attacker's authenticated repo.
4. `Commit#create_status_from_github!` writes a `Status` row using the **victim commit's own `stack_id`** (`statuses.replicate_from_github!(stack_id, github_status)`, app/models/shipit/commit.rb:165-169), so the forged status is attributed to the victim's stack even though the attacker's repository authenticated the request.
5. If the victim stack has `blocking_statuses` configured, `Commit#blocked?` (app/models/shipit/commit.rb:231-237) and `Commit#deployable?` (app/models/shipit/commit.rb:227-229) re-evaluate based on the newly-written forged status, flipping deployability/blocking state and triggering `stack.schedule_merges` (app/models/shipit/commit.rb:383) when the forged state is `pending`/`success`.

Exploit: attacker owns/registers repo `attacker/evil` with Shipit (a normal, unprivileged action). They send `POST /webhooks` with header `X-Github-Event: status`, a valid `X-Hub-Signature` computed with `attacker/evil`'s own webhook secret, and a JSON body:
```json
{
  "sha": "<victim commit sha>",
  "state": "success",
  "context": "deploy/production",
  "repository": {"owner": {"login": "attacker"}, "full_name": "attacker/evil"}
}
```
Because `verify_signature` only checks the org (`attacker`) matches the HMAC secret, the request passes. `StatusHandler` then finds the victim's `Commit` row purely by `sha` match and writes a forged `deploy/production: success` status onto it, unblocking (or, by sending `state: error/failure`, blocking) the victim stack's deploy/merge gating.

Existing guards do not catch this: `verify_signature` validates only the signer's own org secret, not field-level repository ownership of `sha`/`context`; `ExplicitParameters` only validates the JSON *shape* (string type of `sha`, `state`, etc.), not cross-tenant scoping; there is no `require_permission!`/`stacks` scope check in this handler.

The one caveat is that the attacker must know a `sha` that already exists in the victim's `commits` table (i.e., the commit was previously synced into Shipit, e.g., from a push/PR). This is commonly public information (Shipit stack pages, GitHub commit history for public repos, PR links), so it is a feasible precondition, not a cryptographic hash-collision requirement — the attacker is choosing an existing, known 40-hex-char value, not brute-forcing SHA1.

### Impact Explanation
A payload authenticated for one repository (`attacker/evil`) mutates state (a `Status` row, and therefore `blocked?`/`deployable?`) belonging to an unrelated victim stack/repository. This matches the "Critical: a payload for one repository mutating another's stack, commit" category. Concretely: forging `deploy/production: success` on a victim stack with `blocking_statuses` requiring that context can unblock/unlock deploys that were being gated by CI, or conversely forging `error`/`failure` can indefinitely block a legitimate deploy — both are unauthorized deploy/merge-gating manipulation with no privilege on the victim stack. The attack is repeatable against any known SHA in any stack in the instance, cross-tenant.

### Likelihood Explanation
Preconditions: (1) attacker owns/administers at least one repository already onboarded to the Shipit instance (a normal, low-privilege action many multi-tenant Shipit deployments allow); (2) attacker knows a SHA belonging to a victim stack's commit (commonly discoverable via public GitHub history or the Shipit UI); (3) victim stack has `blocking_statuses` configured requiring the forged context. Attacker cost is minimal — one signed HTTP POST, fully scriptable and repeatable against arbitrary target SHAs/stacks without further authorization.

### Recommendation
Scope the `Commit` lookup in `StatusHandler#process` (and similarly in other webhook handlers using bare-SHA/global lookups) by the repository that authenticated the webhook, e.g. join through `stack` and filter on `stack.repository.full_name == params.dig('repository', 'full_name')` (or equivalent `owner`/`name`), rejecting/ignoring statuses whose payload repository doesn't match the commit's own stack repository.

### Proof of Concept
```ruby
# test/models/webhooks/status_handler_cross_repo_test.rb
test "status webhook from repo A cannot mutate a commit belonging to repo B's stack" do
  victim_stack = shipit_stacks(:shipit) # e.g. repo "shopify/shipit-engine", blocking_statuses: ['ci/foo']
  victim_stack.update!(cached_deploy_spec: { 'ci' => { 'blocking_statuses' => ['deploy/production'] } })
  victim_commit = victim_stack.commits.create!(sha: '0' * 40, message: 'victim commit')

  # Binding under test: commit.stack.github_repo_name == payload.repository.full_name
  before_blocked = victim_commit.blocked?

  params = ExplicitParameters unused_here = {
    sha: victim_commit.sha,
    state: 'success',
    context: 'deploy/production',
  }

  # Simulate an attacker-owned, validly-signed repository ("attacker/evil") sending this payload
  Shipit::Webhooks::Handlers::StatusHandler.new(status_params).call

  after_blocked = victim_commit.reload.blocked?

  assert_not_equal before_blocked, after_blocked,
    "victim commit's blocked? state changed due to a status forged from a different repository's webhook"
end
```
This demonstrates the equality `commit.stack.github_repo_name == params.dig('repository','full_name')` is never enforced, and a status forged under an unrelated repository's signature mutates the victim stack's `blocked?`/`deployable?` state.
