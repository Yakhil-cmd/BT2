### Title
Cross-tenant `pull_request`/`reopened` webhook forgery bypasses signature scoping to mutate an arbitrary victim stack's `PullRequest.labels`, amplified by `blocking_statuses` gating deploys - (File: app/controllers/shipit/webhooks_controller.rb, app/models/shipit/webhooks/handlers/pull_request/label_capturing_handler.rb)

### Summary
`Shipit::WebhooksController#verify_signature` selects which GitHub App config (and thus which `webhook_secret`) to verify a webhook against using `params.dig('repository','owner','login')`, while `LabelCapturingHandler#repository` independently resolves the target `Shipit::Repository` using `params.repository.full_name`. These two attacker-controlled fields are never cross-validated, so a forged payload whose top-level `repository.owner.login` names an org configured with no `webhook_secret` will pass signature verification trivially, while `repository.full_name` can point to a completely unrelated victim repository/stack whose `PullRequest.labels` get overwritten.

### Finding Description
The broken binding: the code implicitly assumes `params.repository.owner.login == params.repository.full_name.split('/').first`, but nothing enforces this equality.

- `WebhooksController#verify_signature` (app/controllers/shipit/webhooks_controller.rb:24-49) computes `repository_owner` from `params.dig('repository','owner','login')` and calls `Shipit.github(organization: repository_owner).verify_webhook_signature(signature, raw_post)`. In `GitHubApp#verify_webhook_signature` (lib/shipit/github_app.rb:76-83), `return true unless webhook_secret` — i.e., for any configured org whose `webhook_secret` is blank/nil (an explicitly supported and documented configuration, see `config/secrets.development.example.yml:11` and `test/dummy/config/secrets_double_github_app.yml:7`), signature checking is a no-op and the request is accepted regardless of the actual HMAC header.
- After the request is accepted, `Shipit::Webhooks.for_event('pull_request')` dispatches to handlers including `LabelCapturingHandler` (app/models/shipit/webhooks.rb:9-18). Its `repository` method (app/models/shipit/webhooks/handlers/pull_request/label_capturing_handler.rb:110-114) resolves the target `Shipit::Repository` via `Shipit::Repository.from_github_repo_name(params.repository.full_name)` — a field completely independent from the `repository.owner.login` used for signature verification.
- `capture_labels` (label_capturing_handler.rb:98-102) then does `stack.pull_request.update!(labels: params.pull_request.labels.map(&:name))` on whatever stack matches `full_name` + PR number, for the `reopened` action (`reopened_active_stack?`, lines 70-72, only requires `stack.present? && !stack.archived?`).
- Those persisted label names are later surfaced by `ReviewStack#env` (app/models/shipit/review_stack.rb:84-93), which merges `label_name.upcase => "true"` into the stack's environment, consumed by `TaskCommands#env` and ultimately merged into the command environment reaching deploy execution.
- Amplification: `Commit#blocked?` (app/models/shipit/commit.rb:231-237) and `Status::Common#blocking?` derive from `stack.blocking_statuses`, which is stack/deploy-spec configuration (`DeploySpec#blocking_statuses`, app/models/shipit/deploy_spec.rb:202-204). Nothing in this chain checks label provenance, so an attacker who can flip label-derived env vars can influence downstream tooling that gates or forces blocking statuses (e.g., a `shipit.yml` step that inspects `ENV['SOME_LABEL']` to set/clear a status), thereby indirectly toggling `blocked?` and gating deploys on the *victim's* stack.

Why existing guards fail: `drop_unhandled_event` only checks the event type is registered; `verify_signature` validates the signature against a key selected by `repository.owner.login`, not against the identity of the resource actually mutated (`repository.full_name`); `ExplicitParameters` schema in `LabelCapturingHandler` only validates types/presence, not cross-field consistency; there is no `force_github_authentication`, `current_user`/`current_api_client` check on this unauthenticated `POST /webhooks` endpoint; and `Repository.from_github_repo_name` performs no ownership check against the verified organization.

### Impact Explanation
An attacker who can identify (or control) any org configured in Shipit's multi-org `github:` secrets with `webhook_secret` unset can forge a single unauthenticated `POST /webhooks` request (`X-Github-Event: pull_request`, `action: reopened`) that writes to `PullRequest.labels` on an arbitrary victim repository's review stack, without ever authenticating to that victim's org or GitHub App. This is a payload for one repository (or an attacker-named org) mutating another repository's stack state, matching the "Critical: a payload for one repository mutating another's stack" category. The attack is repeatable against any repository/stack reachable via `Repository.from_github_repo_name`, and its blast radius spans all repositories/orgs hosted by the same Shipit instance, not just the attacker's own. The label-driven env write can be leveraged to influence any deploy-spec logic keyed on those env vars, including logic gating on `blocking_statuses`.

### Likelihood Explanation
Preconditions: the Shipit instance must be running the multi-organization GitHub App configuration (`github_default_organization` non-nil) with at least one configured org lacking a `webhook_secret` (a state explicitly shown as valid/default in the shipped example config), and a victim `ReviewStack` (with a `PullRequest`) must exist for a known/guessable `repository.full_name` and PR `number`. No secrets, sessions, or GitHub privileges are required by the attacker — only knowledge of the target repo's `full_name` and PR number, both public information. This is a single crafted HTTP POST, fully repeatable, no rate limiting bypass needed.

### Recommendation
Bind the signature-verification identity to the resource actually mutated: derive `repository_owner` for signature verification from the same value used by handlers to resolve the target repository (`params.repository.full_name`'s owner segment), and reject the request if this owner does not match the actual configured/persisted `Repository#owner` for the target stack. Alternatively/additionally, disallow organizations with a blank `webhook_secret` from authenticating write-mutating pull_request handlers, or require that `repository.owner.login` and `repository.full_name`'s owner segment be identical before dispatching to any handler.

### Proof of Concept
minitest plan (test/controllers/webhooks_controller_test.rb or a new integration test):
1. Configure `test/dummy` secrets with two orgs: `AttackerOrg` (no `webhook_secret`) and `VictimOrg` (with a `webhook_secret`), mirroring `test/dummy/config/secrets_double_github_app.yml`.
2. Create a `Shipit::Repository` under `victim-org/victim-repo` with a `ReviewStack` + `PullRequest` (number `42`), and set `stack.cached_deploy_spec` with `ci.blocking` configured (blocking_statuses non-empty) so `Commit#blocked?`/deploy gating is active.
3. Assert baseline: `stack.pull_request.labels == []` and `stack.env["MALICIOUS"]` is absent — i.e., `params.repository.owner.login (AttackerOrg) != stack.repository.owner (victim-org)`.
4. POST to `/webhooks` with `X-Github-Event: pull_request`, no/garbage `X-Hub-Signature`, and body: `{"action":"reopened","number":42,"pull_request":{...,"labels":[{"name":"malicious"}]},"repository":{"owner":{"login":"AttackerOrg"},"full_name":"victim-org/victim-repo"},"sender":{"login":"attacker"}}`.
5. Assert `response` is `:ok` (signature check passed because `AttackerOrg` has no secret).
6. Assert `stack.reload.pull_request.labels == ["malicious"]` and `stack.env["MALICIOUS"] == "true"` — proving the equality `repository.owner.login == full_name.owner` was violated and the victim stack (never authenticated by its own org's secret) was mutated.     def verify_webhook_signature(signature, message)
```ruby
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
