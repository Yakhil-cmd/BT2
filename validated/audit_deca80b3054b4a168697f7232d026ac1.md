Based on my research, I found a legitimate root-cause analog in the AA (autonomous agent) trigger/bounce mechanism, where private assets sent to an AA can become permanently stuck because neither the AA's own logic nor the automatic bounce mechanism is able to forward a private asset back out.

### Title
AAs permanently trap any private asset sent to them because neither normal payment logic nor the bounce fallback can forward private assets - (File: aa_composer.js)

### Summary
Just as the Salty DAO could only handle SALT and had no path to recover USDS/DAI tokens that ended up in its balance, an ocore AA (autonomous agent) can receive any asset a poster chooses to send in a trigger unit, but `aa_composer.js`'s outgoing-payment pipeline explicitly refuses to construct a payment message for a private asset, and the automatic `bounce()` fallback used when an AA errors out has no special handling for that case either. A trigger that sends a private asset to an AA therefore permanently freezes those coins in the AA's balance, since it is architecturally impossible for the AA (or its bounce path) to ever pay them back out.

### Finding Description
When an AA composes its response messages, `sendUnit()` iterates payment messages and, for any non-base asset, loads the asset's properties and explicitly bails out if the asset is private: `if (objAsset.is_private) // it'll fail validation anyway due to lack of spend_proofs return cb("sending private asset from AA");` [1](#0-0)  This occurs because private-asset payments require off-chain `spend_proofs`/hidden payloads constructed via the wallet's private-payment composer, something an AA (which only produces public, inline payment messages) cannot generate. [2](#0-1) 

When this error is returned, the whole message-composition pipeline calls `bounce(err)` [3](#0-2) . The `bounce()` function is the AA's designated fallback for refunding whatever was sent by the trigger, and it does iterate over every asset in `trigger.outputs`, including private ones, building a payment message to return `bounced_amount` for each asset: [4](#0-3) . However, that bounce message is fed right back into `sendUnit()`, which applies the exact same asset-processing logic quoted above — so any private asset in the bounce message hits the same `"sending private asset from AA"` error and triggers `bounce()` again. Because `bBouncing` is already `true` at that point, the second call to `bounce()` just calls `finish(null)` and gives up silently [5](#0-4) , without ever removing the received private-asset coins from the AA's `aa_balances` entry (that update only happens for outputs that actually get placed in a saved unit, via `updateFinalAABalances`) [6](#0-5) .

The result mirrors the Salty DAO bug precisely at the root-cause level: a contract/AA is credited with an asset it structurally has no way of moving back out, so the balance accretes forever and is permanently unspendable by anyone, including the address owner and any triggering party expecting a refund.

### Impact Explanation
Any base-asset (bytes) sent with the triggering unit to cover bounce fees, plus any private-asset amount sent in the same unit, is credited to the AA's balance immediately in `updateInitialAABalances()` [7](#0-6) , before the AA logic runs. If the AA's own definition happens to reference/forward that private asset (a plausible pattern for any AA meant to be a generic escrow/exchange, similar to the DAO forming POL with multiple tokens), or if it just bounces because the trigger was otherwise invalid, the private-asset coins are irreversibly locked inside the AA's balance with no code path capable of ever paying them out again. This is a permanent, unrecoverable loss of funds for the AA-owning application and the sender, which is the same class of impact (AA fund freezing / permanent loss of a token type the contract cannot handle) called out in the original finding.

### Likelihood Explanation
Triggering this requires only an unprivileged unit poster: any wallet holding a private, divisible/fixed-denomination asset can compose a trigger unit that includes a private-asset payment output to any AA address alongside enough base-asset bounce fee, exactly as regular users do today when interacting with AAs via `sendMultiPayment`/`composeDivisibleAssetPaymentJoint` [8](#0-7) . No special permissions, malicious nodes, or network conditions are needed — the funds get stuck purely due to the AA composer's inability to reconstruct a private payment, which is a deterministic, always-reproducible condition whenever a private asset lands on an AA balance.

### Recommendation
Either (a) reject at validation time any unit that pays a private asset directly to an AA address (similar to the existing `checkAAOutputs`/`checkNotAAs` guardrails for other conditions) [9](#0-8)  so such funds can never enter an AA balance in the first place, or (b) special-case the bounce path so that when a private asset cannot be forwarded, the *entire* trigger (including its base-asset bounce fee) is rejected/failed pre-emptively at validation, preventing the AA from ever taking custody of an asset it cannot release.

### Proof of Concept
1. Create a private, non-transferrable, divisible asset (`is_private: true, auto_destroy: true`) — allowed per `validateAssetDefinition` rules [10](#0-9) .
2. Issue some units of this asset to a wallet address.
3. Send a trigger unit to any deployed AA that includes: (a) enough base asset to cover `bounce_fees.base`, and (b) an output of the private asset to the AA address, using the standard private-payment composer, e.g. `wallet.sendMultiPayment` with `outputs_by_asset` containing the private asset [11](#0-10) .
4. Regardless of whether the AA's own logic tries to forward the asset or simply errors and calls `bounce()`, `aa_composer.js`'s `sendUnit()` will hit `"sending private asset from AA"` for that asset [1](#0-0) , `bounce()` will re-enter and short-circuit via the `bBouncing` flag [5](#0-4) , and the private-asset balance credited in `updateInitialAABalances()` is never debited back out — verifiable by querying `aa_balances` for the AA address/asset after the trigger unit stabilizes, which will show a permanent nonzero balance with no way to withdraw it.
