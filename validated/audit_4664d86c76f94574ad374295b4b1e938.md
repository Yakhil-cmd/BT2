### Title
Cross-organization webhook forgery via mismatch between signature-verification key lookup and repository-write key lookup - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
In a multi-organization Shipit deployment, `WebhooksController#verify_signature` selects the GitHub App / webhook secret to validate a request's HMAC using `repository_owner`, computed from `params.dig('repository','owner','login')` (falling back to `params.dig('organization','login')`). The event handlers, however, resolve *which* `Repository`/`Stack` record to act on using an entirely different field — `payload.dig('repository','full_name')` (`Handler#repository_name`) or `params.repository.full_name` in the PullRequest handlers. Because the same raw, attacker-controlled JSON body is used to compute both values independently, and because `GitHubApp#verify_webhook_signature` treats a blank `webhook_secret` as automatically valid (`return true unless webhook_secret`), an attacker who knows (or can register) an organization configured in `secrets.github` with no `webhook_secret` can craft a signature-verifiable payload whose `repository.owner.login`/`organization.login` matches that unsecured org, while its `repository.full_name` points at a completely different, secured organization's tracked repository.

- Blank-secret bypass in the verifier: [3](#0-2) 

- Repository/stack resolution used by the actual handlers (a *different* payload field than the one used for signature-key lookup): [4](#0-3) [5](#0-4) [6](#0-5) 

- Multi-org configuration is a supported and documented deployment mode (confirmed by the dummy fixture with two orgs, each independently configured, including with `webhook_secret: # nil`): [7](#0-6) [8](#0-7) 

The equality that should hold — "the organization whose secret cryptographically authorized this webhook == the organization owning the repository the handler writes to" — is broken because the two lookups read independent, unauthenticated JSON fields from the same untrusted body. `repository_owner` (used to pick the verifying key) and `repository_name`/`repository.full_name` (used to pick the row to mutate) are never cross-checked against each other, and neither is bound by the HMAC (the HMAC only proves the raw body wasn't altered *if a secret is configured for the org the attacker chose*).

Concretely: for a request to pass `verify_signature`, the attacker only needs `repository.owner.login` (or `organization.login`) to resolve to an app config in `Shipit.github_app_config` that has a blank/absent `webhook_secret` — at which point `verify_webhook_signature` returns `true` unconditionally, regardless of the `X-Hub-Signature` header or body content. Nothing then prevents `repository.full_name` in that same forged body from naming a repository belonging to a *different*, properly-secured organization tracked by the same Shipit instance. The relevant handlers (`OpenedHandler`, `ClosedHandler`, `LabeledHandler`, `UnlabeledHandler`, `ReopenedHandler`, push/status handlers via `Handler#repository_name`) then look up and mutate that repository's stacks/review-stacks — e.g. creating, archiving, unarchiving, or provisioning `ReviewStack`s, and updating `PullRequest`/`Status` records for a repository the attacker never controls in GitHub.

### Impact Explanation
This is a cross-repository/cross-organization write achieved without any GitHub signing secret for the target organization: an unprivileged external attacker (someone who can only send arbitrary HTTP POSTs to the public `/webhooks` endpoint) can create, archive, or unarchive `ReviewStack`s, and manipulate `PullRequest`/commit `Status` data for a repository that belongs to a *different*, secured organization on the same Shipit instance, as long as any other configured organization on that instance has no `webhook_secret` set. Archiving/unarchiving a `ReviewStack` triggers `deprovision`/re-`provision` task flows (see `ReviewStackAdapter#archive!`/`unarchive!`), which is a stack lifecycle action against a repository the attacker does not own — matching the "unauthorized deploy/rollback" class of impact via forged lifecycle triggers.

### Likelihood Explanation
Requires: (1) a multi-org Shipit deployment, and (2) at least one configured organization with a blank `webhook_secret`. Blank secrets are explicitly supported in the codebase (see the dummy multi-org fixture with `webhook_secret: # nil` for both orgs) and the verifier is written to intentionally allow no-secret configs to pass (`return true unless webhook_secret`), so this is not a hypothetical corner case but a directly coded behavior. The main uncertainty is operational: whether real deployments actually run multiple orgs with one lacking a secret. This can't be fully confirmed from the engine code alone since it depends on how the host application populates `secrets.github`.

### Recommendation
Bind the repository/stack resolution to the same identity that was cryptographically verified: after `verify_signature` succeeds, re-derive `repository_owner` from the verified request and enforce that any repository the handler subsequently mutates belongs to that same organization (e.g., compare `Repository#owner` against `repository_owner` before proceeding, or pass the verified organization into the handler and scope `Repository.from_github_repo_name` lookups to it). Additionally, treat a blank `webhook_secret` in a multi-tenant/multi-org configuration as a misconfiguration to reject (or require it) rather than silently trusting all payloads for that organization, since this "bypass-on-blank-secret" behavior directly enables the described binding break.

### Proof of Concept
1. Shipit instance configured with two orgs in `secrets.github`: `OrgA` (has a valid `webhook_secret`, owns tracked repo `orgA/victim-repo`) and `OrgB` (no `webhook_secret` configured).
2. Attacker sends `POST /webhooks` with header `X-Github-Event: pull_request` and no valid `X-Hub-Signature` (or any arbitrary value), with body:
```json
{
  "action": "opened",
  "number": 999,
  "pull_request": { ... "head": {"ref":"evil-branch"} ... },
  "repository": { "owner": {"login": "OrgB"}, "full_name": "orgA/victim-repo" },
  "sender": {"login": "attacker"}
}
```
3. `verify_signature` computes `repository_owner = "OrgB"`, looks up `Shipit.github(organization: "OrgB")`, and because `OrgB`'s `webhook_secret` is blank, `verify_webhook_signature` returns `true` unconditionally — the request passes.
4. `OpenedHandler#process` resolves `repository` via `Shipit::Repository.from_github_repo_name(params.repository.full_name)`, which returns `orgA/victim-repo` (owned by the properly-secured `OrgA`), and creates/provisions a `ReviewStack` for that repository — a mutation on `OrgA`'s repository that the attacker forged using `OrgB`'s (secret-less) identity, entirely bypassing `OrgA`'s webhook secret.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
