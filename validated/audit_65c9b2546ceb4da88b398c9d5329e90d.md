### Title
Cross-organization Team/Membership mutation via `github_id` collision in `MembershipHandler#find_or_create_team!` - (File: `app/models/shipit/webhooks/handlers/membership_handler.rb`)

### Summary
`WebhooksController#verify_signature` selects the `webhook_secret` to validate a `membership` webhook using only the top-level `organization.login` field of the payload [1](#0-0) [2](#0-1) . Once the signature is accepted for that organization, `MembershipHandler#find_or_create_team!` looks up the target `Team` solely by `params.team.id` (GitHub's numeric team id) and mutates its membership, without ever checking that the authenticated organization actually owns that team [3](#0-2) .

### Finding Description
The broken binding: `organization whose webhook_secret verified the request body == organization owning params.team.id`. This should always hold, but the code never enforces it.

- `verify_signature` computes `repository_owner` from `params.dig('repository','owner','login') || params.dig('organization','login')` and uses it to pick the `GitHubApp` (and thus the `webhook_secret`) to verify the HMAC signature: `Shipit.github(organization: repository_owner).verify_webhook_signature(...)` [1](#0-0) . For a `membership` event there is no `repository` key, so this reduces to `params.dig('organization','login')` — a value fully controlled by the sender of the webhook body [2](#0-1) .
- `MembershipHandler` requires `organization.login`, `team.id`, and `member.login` in its schema [4](#0-3) , but `find_or_create_team!` resolves the `Team` exclusively via `Team.find_or_create_by!(github_id: params.team.id)`. If a `Team` row with that `github_id` already exists (e.g., created earlier by a legitimate membership webhook from a different, "victim" organization), the `do |team| ... end` block that sets `team.organization = params.organization.login` never executes, and the pre-existing row (belonging to the victim org) is returned unchanged [3](#0-2) . `process` then calls `team.add_member(member)` or `team.members.delete(member)` on that returned `Team`, mutating `Membership` rows for the victim's team [5](#0-4) .
- This is a real problem specifically in multi-tenant Shipit deployments, which the engine explicitly supports: multiple GitHub organizations can each have their own `GitHubApp` config (`app_id`/`webhook_secret`/etc.) under `secrets.github.<org>` [6](#0-5) , as documented in "Using Multiple Github Applications" [7](#0-6) . An org onboarded as a legitimate tenant (its GitHub App owner correctly knows/controls its own `webhook_secret`) can compute a valid HMAC for a payload whose `organization.login` is its own org name, but whose `team.id` is an arbitrary integer — including the `github_id` of a `Team` belonging to a different tenant org already present in Shipit's database (from that other org's own past legitimate webhooks).
- No other guard exists: `Handler` base class does not scope by organization [8](#0-7) ; `Team` model has no validation binding `github_id` uniqueness to `organization` beyond the DB row itself [9](#0-8) ; `Membership` only validates `user_id` uniqueness scoped to `team_id`, not organization [10](#0-9) .

Exploit flow: attacker (owner/operator of tenant org `attacker-org`, correctly onboarded into this multi-org Shipit instance) sends `POST /webhooks` with `X-Github-Event: membership`, a body `{"action":"added","organization":{"login":"attacker-org"},"team":{"id":<victim_team_github_id>,...},"member":{"login":"attacker-controlled-user"}}`, signed with `attacker-org`'s own `webhook_secret`. `verify_signature` passes (correct secret for `attacker-org`). `MembershipHandler` finds the pre-existing victim `Team` row by `github_id` and adds/removes the attacker-chosen member from it.

### Impact Explanation
An attacker who is a legitimate, authorized tenant of one organization in a multi-org Shipit deployment can add or remove members of a `Team` belonging to a completely different organization/tenant, by referencing that team's known/guessable numeric `github_id`. If any `Shipit.github_teams`/OAuth `teams:` authorization relies on `Team`/`Membership` records populated via this webhook path, this becomes escalation into another org's authorization group (adding themselves as a "member" of a privileged team record) — matching the High severity category ("escalation into `Shipit.github_teams` authorization") or, if that team backs deploy authorization for another org's stacks, the Critical category ("a payload for one repository mutating another's stack ... or team"). The mutation is repeatable per membership webhook sent, is not scoped to any repository, and crosses tenant boundaries entirely inside the engine's own webhook-signature-to-organization binding.

### Likelihood Explanation
Preconditions: (1) Shipit is deployed in the documented multi-organization mode with at least two configured orgs; (2) the attacker legitimately controls one of those orgs' GitHub App/webhook secret (which is normal for a tenant, not a "Shipit operator" privilege over the whole instance); (3) a `Team` row for the target org already exists in Shipit's DB with a known `github_id` (team ids are visible via GitHub's API/UI to anyone who can see the org, or are discoverable/brute-forceable as small sequential integers). Given those, the attack is a single crafted, correctly-signed POST — no GitHub secrets or Shipit operator access are required beyond what the attacker's own tenant org already legitimately has.

### Recommendation
In `MembershipHandler#find_or_create_team!`, after resolving the `Team` by `github_id`, verify `team.organization == params.organization.login` (case-insensitively) before mutating membership, and reject/no-op (or raise) on mismatch. Additionally, consider deriving the authorized organization strictly from the verified webhook's own app-selection input rather than trusting `params.organization.login` unconditionally in `repository_owner`, and enforce a DB-level uniqueness constraint/validation on `(github_id, organization)` for `Team`.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb
test ":membership rejects team whose stored organization differs from authenticated organization" do
  victim_team = shipit_teams(:shopify_developers) # organization: 'shopify', github_id: 1
  @request.headers['X-Github-Event'] = 'membership'

  Shipit.github(organization: 'cyclimse').stubs(:verify_webhook_signature).returns(true)

  body = {
    action: 'added',
    organization: { login: 'cyclimse' },        # attacker-controlled tenant org
    team: { id: victim_team.github_id, name: victim_team.name, slug: victim_team.slug, url: victim_team.api_url },
    member: { login: 'attacker' }
  }

  assert_no_difference -> { victim_team.memberships.count } do
    post :create, body: body.to_json, as: :json
  end

  # Binding check: org that verified signature ('cyclimse') must equal org owning team.id ('shopify')
  refute_equal 'cyclimse', victim_team.reload.organization
end
```
This test currently fails against the existing implementation (the membership is added to `victim_team` despite the signature having been verified for `cyclimse`), demonstrating the broken binding.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
