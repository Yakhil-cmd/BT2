### Title
Membership webhook cross-tenant team mutation via `github_id`-only lookup ignoring signing organization - ([File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`WebhooksController#verify_signature` picks the `GitHubApp`/`webhook_secret` used to validate a `membership` webhook solely from `params.dig('organization','login')` [1](#0-0) , but `MembershipHandler#find_or_create_team!` resolves the target `Team` purely by `params.team.id` (GitHub's numeric team id) and only assigns `organization` when the record does not already exist [2](#0-1) . In a multi-tenant Shipit install, an attacker who legitimately controls a second onboarded organization (and therefore knows *that org's own* `webhook_secret`) can sign a `membership` payload naming their own org while pointing `team.id` at a pre-existing team belonging to a different org, causing that other org's `Team`/`Membership` rows to be mutated.

### Finding Description
Binding that should hold: `org_used_to_verify_signature == org_that_owns_the_mutated_team`, i.e. `Shipit.github(organization: params.organization.login).webhook_secret` must correspond to the `Team#organization` actually being written.

- `repository_owner` in `app/controllers/shipit/webhooks_controller.rb:59-62` falls back to `params.dig('organization','login')` for events (like `membership`) that carry no `repository` key.
- `verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-49`) fetches `Shipit.github(organization: repository_owner)` and validates the HMAC signature using **that organization's own** `webhook_secret` (`lib/shipit/github_app.rb:76-83`), each organization having independently configured secrets via `github_app_config` (`lib/shipit.rb:170-200`).
- On success, `WebhooksController#create` dispatches to `Webhooks::Handlers::MembershipHandler#process` (`app/models/shipit/webhooks/handlers/membership_handler.rb:22-34`).
- `find_or_create_team!` calls `Team.find_or_create_by!(github_id: params.team.id)` — scoped only on `github_id`, a global GitHub identifier not bound to any organization. The block that sets `team.organization = params.organization.login` runs **only when the record is newly created**. If a `Team` with that `github_id` already exists (e.g. belonging to `shopify`, created by a prior legitimate `shopify` membership webhook), it is fetched as-is and its `organization` field is left untouched [2](#0-1) .
- `team.add_member(member)` / `team.members.delete(member)` then mutate that pre-existing team's `Membership` records (`app/models/shipit/team.rb:41-43`), regardless of which organization's secret actually verified the request.

Attacker request: attacker owns/administers `attacker-org` as a second Shipit-configured tenant (knows `secrets.github[:attacker-org][:webhook_secret]` because they set it up when installing the GitHub App for their own org — no Shipit session, API token, or membership in `Shipit.github_teams` required). They POST to `/webhooks` with header `X-Github-Event: membership`, `X-Hub-Signature` computed with `attacker-org`'s secret, and body:
```json
{
  "action": "added",
  "team": {"id": <shopify_team_github_id>, "name": "Developers", "slug": "developers", "url": "https://example.com"},
  "organization": {"login": "attacker-org"},
  "member": {"login": "attacker-controlled-login"}
}
```
`verify_signature` succeeds because it only checks the payload is authentically signed by `attacker-org` — it never checks that `attacker-org` is the organization that owns `team.id`. `find_or_create_team!` then finds the existing `shopify`-owned `Team` (matching by `github_id` only) and adds the attacker's chosen member to it.

Existing guards don't stop this: `drop_unhandled_event` only checks a handler is registered for the event [3](#0-2) ; the `ExplicitParameters` schema on `MembershipHandler` only validates presence/types of `team.id/name/slug/url`, `organization.login`, `member.login` [4](#0-3)  — it never cross-checks `organization.login` against the team's stored `organization`.

### Impact Explanation
This lets a payload signed by one organization mutate another organization's `Team`/`Membership` records — a direct cross-tenant write. Because `Team` rows populate `Shipit.github_teams`, which is used to resolve which teams grant Shipit access/authorization [5](#0-4) , adding an attacker-chosen GitHub login to a victim org's team can potentially affect authorization decisions tied to that team, extending beyond a simple data-integrity issue. The attack is repeatable against any team whose numeric GitHub `github_id` the attacker can learn (team ids are not secret in the way webhook secrets are), across arbitrary organizations configured in the same multi-tenant Shipit instance.

### Likelihood Explanation
Requires: (1) a multi-organization Shipit deployment (`secrets.github` keyed by multiple orgs, i.e. `github_default_organization` is non-nil) [6](#0-5) ; (2) the attacker legitimately controls at least one of the onboarded organizations (and thus its own `webhook_secret`, which they set themselves during GitHub App/webhook setup — not a Shipit or GitHub secret they'd need to steal); (3) the attacker knows the target team's numeric GitHub `github_id` (obtainable via prior webhook deliveries, GitHub API responses, or brute-force since it's a small integer namespace). No Shipit session, API token, or `Shipit.github_teams` membership is needed. This is realistic in any Shipit installation serving multiple organizations/tenants.

### Recommendation
In `MembershipHandler#find_or_create_team!`, scope the lookup by both `github_id` **and** `organization`, and reject/ignore the event (or raise) if a team with that `github_id` already exists under a different organization than `params.organization.login`. E.g.:
```ruby
def find_or_create_team!
  existing = Team.find_by(github_id: params.team.id)
  if existing && existing.organization != params.organization.login
    raise ArgumentError, "team #{params.team.id} does not belong to organization #{params.organization.login}"
  end
  Team.find_or_create_by!(github_id: params.team.id) do |team|
    team.github_team = params.team
    team.organization = params.organization.login
  end
end
```

### Proof of Concept
Add to `test/controllers/webhooks_controller_test.rb` (fixtures: `shipit_teams(:shopify_developers)` belongs to `organization: 'shopify'`):
```ruby
test "membership webhook from a different org cannot mutate another org's team" do
  victim_team = shipit_teams(:shopify_developers)
  attacker_secret = 'attacker-secret'

  Shipit.stubs(:github).with(organization: 'attacker-org').returns(
    Shipit::GitHubApp.new('attacker-org', webhook_secret: attacker_secret)
  )

  payload = {
    action: 'added',
    team: { id: victim_team.github_id, name: victim_team.name, slug: victim_team.slug, url: victim_team.api_url },
    organization: { login: 'attacker-org' },
    member: { login: 'attacker-controlled-login' }
  }.to_json

  signature = 'sha1=' + OpenSSL::HMAC.hexdigest('sha1', attacker_secret, payload)

  @request.headers['X-Github-Event'] = 'membership'
  @request.headers['X-Hub-Signature'] = signature

  assert_no_difference -> { victim_team.reload.members.count } do
    post :create, body: payload, as: :json
  end
  # Currently FAILS: victim_team gains "attacker-controlled-login" as a member
  # even though the request was signed only with attacker-org's secret.
end
```
Assert both sides of the binding: `org_verifying_signature = 'attacker-org'` vs `org_owning_mutated_team = victim_team.organization ('shopify')` — they diverge, and the fix should make the handler reject the mismatch instead of mutating `victim_team`.
