### Title
Cross-repository status forgery via unscoped `Commit.where(sha:)` lookup in `StatusHandler#process` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` resolves the target `Commit` purely by SHA, with no check that the webhook's declared `repository`/organization actually owns that commit's stack. This breaks the intended binding that every `Status` counted by `MergeRequest::StatusChecker` for a given `merge_request.head` must originate from the repository the `merge_request.stack` tracks.

### Finding Description
The broken binding, stated as an equality that must hold but does not: `webhook.repository.full_name == commit.stack.repository.full_name` for every `commit` a `status` webhook is applied to. In the current code this equality is never checked.

Path:
- `Shipit::WebhooksController#verify_signature` only verifies that the raw payload was HMAC-signed with the webhook secret configured for the *organization* named in the payload (`Shipit.github(organization: repository_owner)` / `GitHubApp#verify_webhook_signature`) — see [1](#0-0)  and [2](#0-1) . This proves the request came from *some* repository under that organization's GitHub App installation, not that it came from the specific repository that owns the target commit.
- `StatusHandler#process` then does:
```ruby
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
``` [3](#0-2) 
This is a global, unscoped lookup by `sha` alone — no `stack_id`, no comparison against `params.dig('repository','full_name')`. Other handlers in the same codebase (e.g. `CheckSuiteHandler`) go through a `stacks` helper that scopes by repository before touching commits, e.g. `stacks.where(branch: params.check_suite.head_branch)` [4](#0-3) , showing the established (and here, missing) convention of repository-scoping.
- `Commit#create_status_from_github!` then writes the forged `Status` using the *victim* commit's own `stack_id`, not the attacker's: `statuses.replicate_from_github!(stack_id, github_status)` [5](#0-4) , and `Status.replicate_from_github!` blindly persists `state`, `context`, etc. from the payload [6](#0-5) .
- This forged `Status` row is then picked up by `Shipit::Commit#statuses_and_check_runs` (`statuses + check_runs`) [7](#0-6) , fed into `MergeRequest::StatusChecker` [8](#0-7) , and consumed by `all_status_checks_passed?` / `any_status_checks_failed?` [9](#0-8) , which gate `merge!` [10](#0-9) .

Exploit flow: an attacker who can trigger a genuine, correctly-signed `status` webhook event from any repository covered by the same GitHub App installation (i.e. "a repository they own" as granted in this exercise's threat model) sends `{"sha": "<victim head sha>", "state": "success", ...}` with a `repository`/`organization` field that legitimately passes `verify_signature` for that installation's secret. `StatusHandler` matches the victim's `Commit` purely by `sha` and creates a `success` `Status` under the victim stack, with no verification that the event actually pertains to the victim's repository.

Existing guards do not prevent this: `verify_signature` authenticates the org-level secret, not the repository-to-commit relationship; `drop_unhandled_event` only checks the event type is registered; the `ExplicitParameters` schema on `StatusHandler` only validates payload shape (`sha`, `state`, etc.), not repository identity; there is no `User#authorized?`/`require_permission!` check in the webhook path at all, since this is an unauthenticated webhook endpoint by design, meant to be secured purely by the per-organization signature — which this handler fails to further scope to the correct repository.

### Impact Explanation
A forged, correctly-signed webhook from an unrelated repository under the same GitHub App installation can inject a `success` `Status` for a completely unrelated `Commit`/`MergeRequest`, causing `StatusChecker#success?` to become true even though no legitimate CI ran on that commit for that stack, leading `MergeRequest#merge!` to merge a pull request that should have been blocked. This is a cross-repository payload mutating another stack's/commit's/merge queue state, satisfying "Critical: an unauthorized deploy, rollback or merge" and "a payload for one repository mutating another's stack, commit, task or team." It is repeatable against any commit sha that is reachable by the attacker within the same GitHub App installation.

### Likelihood Explanation
Preconditions: merge queue enabled, `merge_request.pending?`, and the attacker must be able to cause GitHub to deliver a real `status` event (organization-signed) whose `sha` matches the victim's PR head — e.g. by controlling any repository the Shipit GitHub App is installed on, or by having a git commit object with an identical SHA reachable in a repository they control (trivial to arrange when repos share history, e.g. forks, or when multiple Shipit stacks track the same underlying GitHub repository on different branches). No Shipit credentials, session, or webhook secret are required beyond what GitHub itself provides when relaying an event the attacker legitimately triggered in their own scope.

### Recommendation
In `StatusHandler#process`, scope the `Commit` lookup to the repository declared in the webhook payload (matching `params.repository.full_name` / `params.repository.owner.login` against `commit.stack.repository`) before applying the status, mirroring the `stacks`-scoping convention already used by `CheckSuiteHandler` and the `pull_request` handlers. Reject or ignore the event if the commit's stack does not belong to the reporting repository.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (new test)
test ":status from an unrelated repository cannot inject a success status for a victim's commit" do
  victim_stack = shipit_stacks(:shipit) # repo shopify/shipit
  victim_commit = shipit_commits(:first)
  victim_commit.statuses.destroy_all
  victim_commit.statuses.create!(stack: victim_stack, state: 'failure', context: 'ci/travis')

  merge_request = shipit_merge_requests(:shipit_pending) # pending MR whose head == victim_commit
  refute merge_request.send(:all_status_checks_passed?)

  request.headers['X-Github-Event'] = 'status'
  forged_payload = {
    'sha' => victim_commit.sha,
    'state' => 'success',
    'context' => 'attacker/forged',
    'repository' => { 'full_name' => 'attacker-org/unrelated-repo', 'owner' => { 'login' => 'attacker-org' } }
  }.to_json
  Shipit.github(organization: 'attacker-org').stubs(:verify_webhook_signature).returns(true)

  post :create, body: forged_payload, as: :json

  # Equality that should hold but doesn't: the injected Status's implied repo != victim_stack's repo
  injected = victim_commit.statuses.reload.find_by(context: 'attacker/forged')
  assert injected.present?, "forged status was written to victim commit despite belonging to a different repository"
  assert merge_request.send(:all_status_checks_passed?), "StatusChecker#success? became true from a cross-repository forged status"
end
```
This demonstrates the equality `webhook.repository.full_name == commit.stack.repository.full_name` is never enforced, and that a status attributed to `attacker-org/unrelated-repo` is nonetheless applied to `victim_stack`'s commit, flipping `StatusChecker#success?`.

      false
    rescue Octokit::Conflict # shas didn't match, PR was updated.

    end
