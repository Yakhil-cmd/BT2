### Title
Webhook signature verified against `repository.owner.login`'s GitHub App while the write path resolves the target repository from `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
In multi-organization deployments, `Shipit.github(organization: ...)` looks up a per-organization `webhook_secret` from `Rails.application.credentials.github[org]` [1](#0-0) . `WebhooksController#verify_signature` selects which organization's secret to verify the HMAC against using `repository_owner`, computed as `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` [2](#0-1) [3](#0-2) . Once the HMAC over the raw body checks out for that org's secret, the request is dispatched to handlers that resolve the target Repository/Stack using `payload.dig('repository', 'full_name')` — a different field of the same JSON body [4](#0-3) .

### Finding Description
The binding that should hold is: `organization authenticated (used to pick the webhook secret) == organization of the repository actually written to`. Because verification only checks that the raw body is HMAC-signed by *some* configured organization's secret (chosen via `repository_owner`), and the write path independently re-parses `repository.full_name` from the same trusted-once-verified body, the two lookups are logically decoupled data reads of the same payload rather than a single authenticated value. If an operator's GitHub App configuration ever contains multiple organizations (`Shipit.github_organizations` > 1, e.g. shared instance managing several orgs) and any one of those orgs' webhook secrets is compromised or an app is set up per-org with distinct secrets, a request signed with organization A's secret but whose `repository.full_name` points to a stack under organization B would still pass verification, because verification and the eventual write use independent payload fields with no cross-check that they refer to the same organization. This is structurally the same class of bug as the reported race — a value used for a security decision (which secret authenticates the request) diverges from the value used for the state-changing action (which repository is written), because both are read from attacker-controlled input without pinning them to a single verified value.

### Impact Explanation
Successful exploitation causes cross-repository writes: an attacker who holds (or has leaked) the webhook secret for one organization/repository configured on the Shipit instance can drive event handlers (push, status, check_suite, pull_request, membership, etc.) against stacks belonging to a different organization also hosted on that instance, without holding credentials for that second organization. This matches the required Critical impact category of "cross-repository writes."

### Likelihood Explanation
This requires: (1) the Shipit instance configured with multiple organizations under `secrets.github` (supported and documented multi-org schema per `github_app_config`/`github_organizations`) [5](#0-4) , and (2) the attacker possessing a valid webhook secret for at least one configured organization but not the target one. This is a real but narrower precondition than a single-org deployment, so likelihood is Medium — it depends on multi-tenant configuration, which the codebase explicitly supports.

### Recommendation
After `verify_signature` succeeds, assert that the organization whose secret validated the signature equals `repository_owner`/the organization embedded in `repository.full_name` used by `Handler#repository_name`, rejecting (422) any mismatch before dispatching to `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`.

### Proof of Concept
1. Configure Shipit with two organizations, `org-a` and `org-b`, each with its own `webhook_secret` (per `docs/setup.md` multi-org schema).
2. Obtain `org-a`'s webhook secret (e.g., leaked from an `org-a`-side integration).
3. Craft a push payload where `repository.owner.login == "org-a"` (so `verify_signature` picks org-a's app/secret) but `repository.full_name == "org-b/some-stack-repo"`.
4. Sign the raw JSON body with org-a's secret and send it as `X-Hub-Signature`.
5. `verify_signature` succeeds (org-a's secret matches), but `GithubSyncJob`/handlers resolve `Repository.from_github_repo_name("org-b/some-stack-repo")` via `repository_name` [4](#0-3)  and act on org-b's stack, achieving a cross-repository write despite only holding org-a's credentials.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
