### Title
`git.appTokenExpiry` is committed before the credential store succeeds, permanently masking future GitHub App token refresh attempts - ([File: main.go])

### Summary
`RefreshGitHubAppToken` sets `git.appTokenExpiry = tokenResponse.ExpiresAt` before the fetched token is actually persisted via `StoreCredentials`. If `StoreCredentials` subsequently fails, the function returns an error (as if the refresh failed), but the in-memory `appTokenExpiry` field has already been advanced to the new (future) expiry time. This is the same class of bug as the reported GMX issue: a piece of state is updated as though a downstream side effect succeeded, when in fact that side effect (credential persistence) never completed, and the recovery/retry logic later relies on that incorrect state instead of retrying the failed operation.

### Finding Description
In `RefreshGitHubAppToken`, the sequence is: [1](#0-0) 

1. The GitHub App installation token response is decoded.
2. `git.appTokenExpiry` is immediately set to the new token's `ExpiresAt` value.
3. Only afterward is `git.StoreCredentials(ctx, git.repo, username, password)` called to actually write the token into git's credential store via `git credential approve`.

If step 3 fails (e.g., transient `git` subprocess failure, disk/credential-helper cache issue, or context cancellation from `--sync-timeout`), the function returns an error, and the caller in the `refreshCreds` closure propagates that error up through `SyncRepo`: [2](#0-1) 

The overall sync attempt is recorded as a failure, incrementing `failCount` in the main loop: [3](#0-2) 

However, `git.appTokenExpiry` was already mutated to the new, valid-looking expiry time despite the credential never having been stored. On the next sync loop iteration, the guard `if git.appTokenExpiry.Before(time.Now().Add(30 * time.Second))` at main.go:1009 evaluates false (since the field now points ~1 hour into the future, matching typical GitHub App installation token lifetimes), so `RefreshGitHubAppToken` is **not** called again. Git subsequently tries to fetch/authenticate using stale or missing credentials, and continues to fail (401/403) for the entire assumed token lifetime, with no self-healing retry of the credential refresh path — a direct analog of the reported "borrow again despite repay never happening" pattern, where recovery logic assumes a completed side effect that was actually rolled back/never occurred.

### Impact Explanation
This causes persistent sync denial: once a single transient failure occurs in `StoreCredentials` right after a GitHub App token fetch, `git-sync` will keep believing it has a fresh, valid credential for up to the token's full lifetime (commonly up to 1 hour, per GitHub's installation token expiry), even though the credential store was never actually updated. During that window, all fetches against the remote repo will fail authentication, and (depending on `--max-failures`) the process may eventually exit non-zero after exhausting its failure budget — denying the intended continuous synchronization service that `git-sync` is meant to provide as a sidecar.

### Likelihood Explanation
Reaching this requires GitHub App auth to be configured (`--github-app-private-key-file`/`--github-app-application-id`/`--github-app-client-id` and `--github-app-installation-id`) and a failure in the underlying `git credential approve` subprocess call to occur specifically after a successful token fetch (e.g., transient exec failure, disk I/O error on the credential cache, or the sync context timing out via `--sync-timeout` between the HTTP token fetch and the `git` subprocess call). This is a plausible, unprivileged, operationally-triggerable condition (no attacker control of repo content required) rather than a contrived edge case, since `git.Run`/`RunWithStdin` failures are a normal occurrence path already handled (and returned as errors) elsewhere in the codebase.

### Recommendation
Only update `git.appTokenExpiry` after `StoreCredentials` has succeeded, e.g.:
```go
if err := git.StoreCredentials(ctx, git.repo, username, password); err != nil {
    return err
}
git.appTokenExpiry = tokenResponse.ExpiresAt
return nil
```
This ensures the "is the token still valid" state is only advanced once the credential has actually been persisted, so a failed store attempt will cause a retry on the very next sync loop iteration instead of being silently skipped for the remainder of the (incorrectly assumed) token lifetime.

### Proof of Concept
1. Configure `git-sync` with `--github-app-private-key-file`, `--github-app-client-id` (or `--github-app-application-id`), and `--github-app-installation-id` pointing at a valid GitHub App installation.
2. Instrument/patch `StoreCredentials` (or induce a failure, e.g. by making the `git` binary path used for `credential approve` transiently unavailable/erroring only on that specific invocation) so that the call at `main.go:2269` fails exactly once, right after a successful token fetch.
3. Observe that `git.appTokenExpiry` is already set to `tokenResponse.ExpiresAt` (~1 hour in the future) even though `StoreCredentials` failed at main.go:2263-2271.
4. On the next sync loop iteration, confirm via logs/metrics (`metricRefreshGitHubAppTokenCount`) that `RefreshGitHubAppToken` is not invoked again — because `git.appTokenExpiry.Before(time.Now().Add(30*time.Second))` at main.go:1009 is false — while the actual git fetch operations continue to fail due to the missing/stale stored credential, until the (falsely assumed) expiry time is reached or `--max-failures` is exceeded and the process exits.
