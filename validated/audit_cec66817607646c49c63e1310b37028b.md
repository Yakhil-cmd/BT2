Confirmed: this is a real, exploitable trust-binding break in the webhook signature verification path.

### Title
Webhook signature is verified against the organization named in the unverified payload, not the repository actually acted upon - cross-repository/cross-organization webhook forgery ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App's `webhook_secret` to check the `X-Hub-Signature` against by reading `repository.owner.login` (or `organization.login`) straight out of the still-unauthenticated JSON body, then hands the *entire* raw body to that handler's downstream processing, which separately resolves the target `Stack`/`Repository` from `payload.dig('repository', 'full_name')`. Nothing ties the organization whose secret validated the signature to the repository that is ultimately looked up and acted upon.

### Finding Description
`verify_signature` computes: [1](#0-0) 
`repository_owner` is derived from the attacker-controlled payload before any signature check: [2](#0-1) 

`Shipit.github(organization:)` is per-organization in multi-tenant configurations, each with its own `webhook_secret`: [3](#0-2) 

Since the attacker fully controls the raw request body they sign, they can craft a payload whose `repository.owner.login` equals an organization they legitimately control (and thus know the `webhook_secret` for, e.g. their own installed GitHub App / org), producing a valid HMAC with that org's secret. However, every downstream `Handler` resolves the actual target purely from `payload.dig('repository', 'full_name')`, independent of the org used above: [4](#0-3) [5](#0-4) 

Because `repository.full_name` (owner/name used for lookup) is never cross-checked against the `repository.owner.login`/`organization.login` value used for signature verification, an attacker who owns/controls Organization A (and thus knows or controls its `webhook_secret`) can sign a payload where `repository.owner.login = "OrgA"` (satisfying `verify_signature`) but `repository.full_name = "OrgB/some-private-repo"` (a completely different tenant's tracked repository). The signature check passes because it only ever validates against OrgA's secret, yet the `PushHandler`, `LabeledHandler`, `OpenedHandler`, etc. will act on `Repository.from_github_repo_name("OrgB/some-private-repo")`, e.g. triggering `stack.sync_github(...)`: [6](#0-5) 

This breaks the binding: **organization that authenticated (via signature) == repository that is written/acted upon**. The signature only proves "this payload was sent by someone who knows OrgA's webhook secret"; it does not prove anything about the `repository` fields inside that same payload, yet those fields are trusted to select and mutate arbitrary tracked stacks/repositories belonging to any organization configured in `secrets.github`.

### Impact Explanation
An attacker who is a legitimate GitHub App installer/owner for one onboarded organization (or who otherwise obtains that organization's `webhook_secret`) can forge webhook events that are processed as if they originated from a completely different organization/repository tracked by the same Shipit instance. Depending on handler, this can:
- Force `GithubSyncJob` execution / `sync_github` for another org's stacks (state manipulation, spurious CI/status triggers) — `PushHandler`.
- Manipulate review-stack provisioning/archival (`LabeledHandler`, `UnlabeledHandler`, `OpenedHandler`) or pull-request label capture across repositories not owned by the attacker.
- Forge commit `Status` records for arbitrary tracked repositories.

This is a cross-organization/cross-repository write achieved purely by crafting a payload, matching the "cross-repository writes" Critical impact bucket, since the write happens against a repository the attacker does not have credentials for and never authenticated as.

### Likelihood Explanation
Requires the attacker to control (or know) the `webhook_secret` for at least one organization/App installation registered in the multi-tenant `secrets.github` config of the same Shipit instance — a realistic scenario for any Shipit deployment shared across multiple orgs/teams, since each org's admin who installs the App knows its own webhook secret but should have no ability to affect other orgs' stacks. No GitHub write access, Shipit session, or `ApiClient` token is needed — only the ability to POST an arbitrary JSON body with a valid `X-Hub-Signature` computed from a secret the attacker legitimately possesses for their own organization.

### Recommendation
After signature verification succeeds for `repository_owner`, `WebhooksController`/`Handler` must also assert that `payload.dig('repository', 'full_name')`'s owner segment matches `repository_owner` (the same value used to select the verifying secret), rejecting (422) any event where they differ. Equivalently, resolve the target `Repository`/`Stack` using the org that was cryptographically verified rather than trusting the `full_name` field independently.

### Proof of Concept
1. Deploy Shipit with multi-tenant GitHub config (`secrets.github` keyed by org, as in `test/dummy/config/secrets_double_github_app.yml`) tracking `OrgA/repo-a` and `OrgB/repo-b`, each org having its own App/`webhook_secret`.
2. As the administrator of `OrgA` (attacker), know `OrgA`'s `webhook_secret`.
3. Craft a push payload:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>",
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/repo-b" }
}
```
4. Compute `X-Hub-Signature: sha1=<hmac-sha1(OrgA_webhook_secret, body)>` and POST to `/webhooks` with `X-Github-Event: push`.
5. `verify_signature` calls `Shipit.github(organization: "OrgA")` and validates successfully against `OrgA`'s secret.
6. `PushHandler#stacks` resolves via `Repository.from_github_repo_name("OrgB/repo-b")`, and `stack.sync_github` is invoked for `OrgB`'s stack — a write the attacker was never authorized to trigger.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
