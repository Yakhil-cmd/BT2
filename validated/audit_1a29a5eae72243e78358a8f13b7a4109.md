### Title
Webhook Signature Verified Against `repository.owner.login` While Handlers Act on the Independent `repository.full_name` Field, Enabling Cross-Organization Writes - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
In multi-organization Shipit deployments, `WebhooksController#verify_signature` selects which organization's `webhook_secret` to use for HMAC verification based on `repository.owner.login` (or `organization.login`) taken from the *unauthenticated* JSON body. Once the signature check passes, every webhook handler (`PushHandler`, `StatusHandler`, `pull_request` handlers, etc.) resolves the target `Repository`/`Stack` using a *different* field of the same body — `repository.full_name`. Nothing binds these two fields together, so a payload can be signed as belonging to organization A while acting on a repository under organization B.

### Finding Description
`WebhooksController#verify_signature` computes the org used for HMAC verification purely from attacker-supplied JSON: [1](#0-0) [2](#0-1) 

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

`Shipit.github(organization:)` looks up a distinct `webhook_secret` per organization key in `secrets.github` (the documented multi-org configuration schema): [3](#0-2) 

Meanwhile, every event handler resolves the affected repository/stack from the **separate** `repository.full_name` field, completely independent of `repository.owner.login`: [4](#0-3) [5](#0-4) 

Because `verify_webhook_signature` uses `SecureCompare.secure_compare` over the *entire raw body* against the secret for whatever org `repository.owner.login` claims to be, an attacker who legitimately administers (and thus knows the `webhook_secret` for) **any single organization configured on the shared Shipit instance** can craft a payload where:
- `repository.owner.login` = their own org (so the signature is computed/verified with the secret they know), and
- `repository.full_name` = `"victim-org/victim-repo"` (a repository belonging to a completely different, unrelated organization also hosted on the same Shipit instance).

The binding broken is: **organization that authenticated (`repository_owner` → `webhook_secret` selection) ≠ repository that is written (`repository.full_name` → `Repository`/`Stack` resolution)**. GitHub itself always sends these two fields consistent with each other, but nothing in Shipit's engine enforces that consistency — the check is purely structural/positional in the JSON, not cryptographically or logically tied to the acted-upon resource.

### Impact Explanation
This allows an attacker with legitimate control of one organization's GitHub App/webhook configuration on a shared multi-org Shipit instance to forge signed events (`push`, `status`, `check_suite`, `pull_request`, `membership`, etc.) targeting a *different* organization's repositories/stacks that they have no access to. Depending on handler, this can:
- Trigger `PushHandler` → `stack.sync_github` for a victim stack, forcing GitHub sync against attacker-chosen `expected_head_sha`. [6](#0-5) 
- Inject fabricated commit statuses via `StatusHandler#process` → `commit.create_status_from_github!`, which is capable of flipping a commit's aggregate state and can trigger `ProcessMergeRequestsJob`, potentially causing the merge queue to attempt merging a pull request in the victim's repo. [7](#0-6) [8](#0-7) 

This is a cross-organization write into stacks the attacker does not administer, satisfying the "cross-repository writes" / "unauthorized deploy or merge" impact criteria. Severity depends on the merge queue and CI-gating configuration of the victim stack (whether forged statuses alone can satisfy `all_status_checks_passed?` and drive an actual `merge!`).

### Likelihood Explanation
Requires: (1) the Shipit instance to be configured with the documented multi-organization `github:` schema (each org with a distinct `webhook_secret`), and (2) the attacker to legitimately control one of those configured organizations' webhook secret (e.g., as an admin of their own org's GitHub App installation pointed at the shared Shipit instance). This is a realistic scenario for any Shipit deployment shared across multiple organizations/tenants, which the engine explicitly supports and documents. No Shipit session, ApiClient token, or private key is needed — only knowledge of one org's webhook secret, which by design is available to that org's own administrators.

### Recommendation
Cross-validate that `repository.full_name`'s owner segment matches the `repository.owner.login` (or `organization.login`) value used to select the verifying `webhook_secret` before dispatching to handlers, or derive the verifying organization strictly from `repository.full_name`'s owner segment rather than a separately-supplied field. Reject the webhook with `422` if the two are inconsistent.

### Proof of Concept
1. Configure Shipit in multi-org mode with `secrets.github` containing `attacker-org` and `victim-org`, each with its own `webhook_secret`.
2. As an administrator of `attacker-org`'s GitHub App, obtain `attacker-org`'s `webhook_secret`.
3. Craft a `push` event JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "deadbeef",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
4. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(attacker-org_webhook_secret, raw_body)>`.
5. POST to `/webhooks` with `X-Github-Event: push`. `verify_signature` selects `attacker-org`'s app/secret via `repository_owner` (`attacker-org`) and the signature verifies successfully.
6. `PushHandler#process` resolves `stacks` via `repository.full_name` = `victim-org/victim-repo`, and calls `sync_github` on stacks belonging to `victim-org`, which the attacker does not control. [9](#0-8) [4](#0-3)

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
