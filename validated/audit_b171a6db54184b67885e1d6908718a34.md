### Title
Custom `extract_frontmatter` YAML-like parser silently drops `action`/other top-level keys at ambiguous indentation, causing block rules to load as warn-only - ([File: plugins/hookify/core/config_loader.py])

### Summary
`extract_frontmatter` in `plugins/hookify/core/config_loader.py` uses a hand-rolled, line-based parser instead of a real YAML parser. Lines whose indentation is 1 or 2 characters (including tabs counted as 1 char) fall through every branch of the if/elif chain and are silently discarded, so a top-level key such as `action: block` or `enabled: false` placed at that indentation is dropped without any warning, and `Rule.from_dict` then falls back to its default `action = "warn"`.

### Finding Description
The parser loop in `extract_frontmatter` classifies each line into exactly three buckets: [1](#0-0) 

- A line is treated as a top-level key only `if indent == 0 and ':' in line and not line.strip().startswith('-')` [2](#0-1) .
- A line is treated as a list item only if `stripped.startswith('-') and in_list` [3](#0-2) .
- A line is treated as a continuation of a multi-line dict item only if `indent > 2 and in_dict_item and ':' in line` [4](#0-3) .

Any line with `indent` equal to 1 or 2 (e.g., a single leading space/tab, or exactly 2 spaces) that is not a list item matches none of these three branches — there is no `else` clause and no error raised, so the line is silently skipped and the loop continues to the next line. Because `indent` is computed as `len(line) - len(line.lstrip())` [5](#0-4) , tabs and spaces are counted identically (1 unit each), so a single leading tab or a stray space before `action: block` also lands in this dropped-indentation gap.

Concretely, an attacker who can commit/modify a `.claude/hookify.*.local.md` rule file (e.g., via a PR to a repo the victim clones) can cause the block action to disappear in at least these ways:
1. Prepend a single space/tab to a top-level `action: block` line, giving `indent == 1` — fails `indent == 0`, fails list-item check, fails `indent > 2`.
2. Place `action: block` at exactly 2-space indentation nested visually under a `conditions:` list, e.g.:
```
conditions:
  - field: command
    operator: regex_match
    pattern: rm -rf
  action: block
```
Here `  action: block` has `indent == 2`. It is not a top-level key (`indent != 0`), not a list item (doesn't start with `-`), and not a valid dict continuation (`indent > 2` is false at exactly 2) — the key is silently dropped.

In both cases `frontmatter` ends up without an `action` key. `load_rule_file` only checks `if not frontmatter:` (i.e., whether the dict is entirely empty) — it does not validate that expected fields like `action`/`enabled` are present [6](#0-5) . `Rule.from_dict` then applies `action=frontmatter.get('action', 'warn')`, silently defaulting to `"warn"` [7](#0-6) . Downstream, `RuleEngine.evaluate_rules` routes rules by `rule.action == 'block'`; anything else is treated as a warning that does not block the operation [8](#0-7) . The PreToolUse/PostToolUse hooks call `load_rules()` → `load_rule_file()` → `extract_frontmatter()` → `Rule.from_dict()` exactly as described in the question, and always exit 0 regardless of parse outcome [9](#0-8) .

No existing check (allowlist, schema validator, or reference YAML comparison) catches this divergence; the code comments even acknowledge this is a "Simple YAML parser" rather than a spec-compliant one [10](#0-9) .

### Impact Explanation
This breaks the "deny means deny" invariant for hookify block rules: a rule authored/reviewed by the victim as `action: block` (intended to prevent dangerous `Bash`/`Edit`/`Write` operations) can be made to behave as a no-op/warn-only rule purely through a whitespace/indentation change in the committed rule file, with no error surfaced to the user. Since hookify's PreToolUse hook always exits 0 and treats warn-only outcomes as "allow with message" [11](#0-10) , dangerous operations that the victim believes are blocked will actually execute. This matches the scoped impact of "dangerous Bash/Edit operations execute despite an apparent block rule."

### Likelihood Explanation
Preconditions match the stated threat model exactly: an unprivileged attacker only needs to add or modify a file under version-controlled `.claude/hookify.*.local.md` in a repository the victim clones and uses with Claude Code (e.g., via a pull request touching an existing rule file, introducing an innocuous-looking whitespace change). No special privileges, keys, or social engineering beyond a normal PR/commit are required. The trigger is deterministic — any file hitting the indent==1/2 gap reproduces the silent drop every time `load_rules()` runs.

### Recommendation
Replace the custom line-based frontmatter parser with a real YAML parser (e.g., `yaml.safe_load`) for the frontmatter block, or at minimum: normalize indentation (reject/expand tabs, require exact multiples of a fixed indent unit), make the branch logic exhaustive by raising a `ValueError` on any line that fails to match a recognized state rather than silently continuing, and add post-parse validation in `load_rule_file`/`Rule.from_dict` that fails loudly (refuses to load, or defaults to the safest action `block` rather than `warn`) when required keys like `action` are absent from a rule that otherwise defines a `pattern`/`conditions`.

### Proof of Concept
Differential/unit test in `plugins/hookify/core/config_loader.py`'s test area or a new `tests/test_config_loader.py`:
```python
import yaml
from hookify.core.config_loader import extract_frontmatter

CASES = [
    # (description, frontmatter_text)
    ("single-space indent before action", """---
name: block-rm
enabled: true
event: bash
pattern: "rm -rf"
 action: block
---
message
"""),
    ("action nested at indent=2 under list", """---
name: block-rm
enabled: true
event: bash
conditions:
  - field: command
    operator: regex_match
    pattern: rm -rf
  action: block
---
message
"""),
    ("tab indent before action", """---
name: block-rm
enabled: true
event: bash
pattern: "rm -rf"
\taction: block
---
message
"""),
]

def test_action_field_never_silently_dropped():
    for desc, content in CASES:
        fm, _ = extract_frontmatter(content)
        # Reference: strip markers, parse with real YAML
        frontmatter_text = content.split('---', 2)[1]
        ref = yaml.safe_load(frontmatter_text) or {}
        assert fm.get('action') == ref.get('action'), (
            f"[{desc}] custom parser dropped 'action' key: "
            f"got {fm.get('action')!r}, reference expected {ref.get('action')!r}"
        )
```
Expected result (current behavior): the assertion fails for all three cases because `fm.get('action')` is `None`/absent while the reference YAML parser correctly extracts `action: block` — demonstrating the silent divergence. Additionally, an integration test can assert that `Rule.from_dict(fm, msg).action == 'block'` fails (returns `'warn'` default) for these inputs, and that `RuleEngine.evaluate_rules` on a matching `Bash` `rm -rf` command returns an "allow"/warn response instead of `permissionDecision: deny`.

            key, value = line.split(':', 1)
            key = key.strip()
            value = value.strip()

            if not value:
                # Empty value - list or nested structure follows
                current_key = key
                in_list = True
                current_list = []
            else:
                # Simple key-value pair
                value = value.strip('"').strip("'")
                if value.lower() == 'true':
                    value = True
                elif value.lower() == 'false':

                frontmatter[key] = value

        # List item (starts with -)

            # Save previous dict item if any

            # Check if this is an inline dict (key: value on same line)
            if ':' in item_text and ',' in item_text:

                item_dict = {}
                for part in item_text.split(','):
                    if ':' in part:
