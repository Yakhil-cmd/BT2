### Title
`provision?` operator-precedence bug ignores `review_stacks_enabled` for the `allow_with_label`/`prevent_with_label` branches - ([File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb])

### Summary
`OpenedHandler#provision?` intends to gate all provisioning behaviors on `repository.review_stacks_enabled`, but Ruby operator precedence (`&&` binds tighter than `||`) only applies that gate to the `allow_all` branch. Any repository configured with `provisioning_behavior: 'allow_with_label'` (or `prevent_with_label`) will still provision a review stack even when `review_stacks_enabled` is `false`.

### Finding Description
The intended binding is `review_stacks_enabled == true` required for **any** provisioning path. The actual code: [1](#0-0) 

parses as `(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?)` — the second and third disjuncts never reference `review_stacks_enabled` at all. So for a repository with `provisioning_behavior: 'allow_with_label'` and `review_stacks_enabled: false`, opening a PR carrying `repository.provisioning_label_name` makes `provision?` return `true` via `pull_request_has_provisioning_label?`: [2](#0-1) 

`process` then calls `ReviewStackAdapter#find_or_create!` → `create!`, which persists a `ReviewStack`, attaches the pull request, and enqueues it for provisioning (which runs the provisioning task/commands): [3](#0-2) [4](#0-3) 

There is no other guard: `ReviewStackAdapter` performs no `review_stacks_enabled` check itself, `NullRepository` only affects unregistered repos, and no model validation on `ReviewStack`/`Repository` re-checks this flag at creation time. Notably, the sibling `LabeledHandler#respond_to_label_change?` correctly ANDs `repository.review_stacks_enabled` with the whole `(archive? || unarchive?)` expression using parentheses: [5](#0-4) 

confirming that `OpenedHandler#provision?` is missing the equivalent parenthesization/gate, and that this is a real regression rather than intended behavior.

Attack: the attacker owns/maintains a repository already registered in Shipit with `provisioning_behavior: allow_with_label` and `review_stacks_enabled: false` (an operator misconfiguration, or a state reached e.g. by toggling settings), opens a pull request in that repository, and applies the repository's `provisioning_label_name` label to it (or the PR already carries it). The `pull_request.opened` webhook is processed, `provision?` incorrectly returns `true`, and a `ReviewStack` is created and queued for provisioning, causing task/step execution that the operator explicitly disabled via `review_stacks_enabled: false`.

### Impact Explanation
This is an authorization-gate bypass: the operator-controlled kill switch `review_stacks_enabled` is silently ignored for two of the three `provisioning_behavior` modes, letting a labeled pull request trigger `ReviewStack` creation and its downstream provisioning task (command execution via the provisioning queue) against operator intent. It affects only the same repository (not cross-tenant), but it defeats an explicit safety control and results in unauthorized deploy/provisioning execution — matching the Critical category ("unauthorized deploy" / stack creation and step execution not authorized by the operator's configuration). It is fully repeatable for any repository stuck in this configuration combination and for every PR/label event thereafter.

### Likelihood Explanation
Requires a specific but plausible repository configuration: `provisioning_behavior: 'allow_with_label'` (or `prevent_with_label`) together with `review_stacks_enabled: false`. Given that these are two independent settings exposed in the repository settings UI, an operator toggling `review_stacks_enabled` off without also resetting `provisioning_behavior` back to a safe default reaches this state easily. Once there, exploitation costs the attacker nothing beyond opening a PR and applying a label they control on their own repository — no secrets, sessions, or elevated GitHub permissions are needed.

### Recommendation
Parenthesize `provision?` so `review_stacks_enabled` gates the entire expression:
```ruby
def provision?
  repository.review_stacks_enabled &&
    (repository.provisioning_behavior_allow_all? ||
     (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
     (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?))
end
```

### Proof of Concept
In a minitest for `OpenedHandler` (mirroring `test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb`):
1. Build a `Repository` with `provisioning_behavior: 'allow_with_label'`, `review_stacks_enabled: false`, and a known `provisioning_label_name`.
2. Build webhook `params` for `action: 'opened'` whose `pull_request.labels` includes that label name.
3. Instantiate `OpenedHandler.new(params)` and assert `handler.send(:provision?)` is `true` — demonstrating the equality `review_stacks_enabled == false` vs. actual gating `true` diverges.
4. Call `handler.process` and assert `Shipit::ReviewStack.where(environment: "pr#{params.number}").exists?` is `true`, proving a stack was persisted (and enqueued via `Shipit::ReviewStackProvisioningQueue`) despite `review_stacks_enabled: false`.
