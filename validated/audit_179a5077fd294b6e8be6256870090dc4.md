### Title
Webhook signature is verified against the payload's `repository.owner.login`, but every event handler acts on the independent `repository.full_name` field, allowing cross-organization forged webhooks in multi-app deployments - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the HMAC secret to validate a webhook against using `repository_owner`, a value read directly from the untrusted JSON body (`params.dig('repository', 'owner', 'login')` with a fallback to `params.dig('organization', 'login')`). [1](#0-0) [2](#0-1)  Once the signature check passes, the entire raw payload is handed unchanged to every registered handler, and those handlers determine *which repository/stack to mutate* using a completely different field: `payload.dig('repository', 'full_name')`. [3](#0-2) [4](#0-3)  In Shipit's documented multi-organization configuration, each organization has its own `webhook_secret`, so the field used to pick the verification key (`repository.owner.login`) and the field used to pick the write target (`repository.full_name`) are never cross-checked for consistency.

### Finding Description
This is the same root cause pattern as the reported `RiskEngine.getSolvencyTicks` bug: a gate is evaluated over one representation of "where this applies" while the actual effect is applied using a different, unverified representation, letting an attacker satisfy the gate while diverging the effect.

Concretely:
1. `Shipit.github(organization: repository_owner)` looks up the `GitHubApp`/secret keyed by the organization name taken from the payload's `repository.owner.login` (or `organization.login`). [5](#0-4)  In the documented multi-app schema, `Shipit.github_app_config` looks the secret up per-organization key. [6](#0-5) 
2. The HMAC is computed over the raw request body and compared against `X-Hub-Signature` using that organization's secret. [7](#0-6) 
3. On success, `create` parses the same raw body and dispatches it, unmodified, to every handler registered for the event type. [3](#0-2) 
4. Every handler resolves the target repository/stack via `payload.dig('repository', 'full_name')`, not `repository.owner.login`. [4](#0-3)  For example `PushHandler#process` finds stacks purely from `stacks` (derived from `repository.full_name`) and calls `stack.sync_github`. [8](#0-7)  `StatusHandler#process` finds commits purely by SHA (`Commit.where(sha: params.sha)`, with no repository/org scoping at all) and writes a GitHub commit status onto them. [9](#0-8)  `CheckSuiteHandler` similarly resolves `stacks` from `repository.full_name` and schedules check-run refreshes. [10](#0-9) 

Because `repository.owner.login` (used for signature key selection) and `repository.full_name` (used for the actual write) are two independent, attacker-supplied JSON fields inside the same signed payload, nothing forces them to refer to the same repository or organization. An attacker who legitimately controls one configured GitHub organization/app (Org A) — which is the normal, expected way to obtain a validly-signed webhook, since GitHub itself signs the payload with that org's secret when Org A's own repositories fire events — can intercept/replay or, more directly, simply have their own GitHub App/webhook endpoint fire a request that Shipit's controller will accept as long as `X-Hub-Signature` matches Org A's secret, while setting `repository.full_name` inside the JSON body to `OrgB/some-repo`. This is possible because `verify_signature` never re-derives the "owner" from `repository.full_name`, and the HMAC check only proves *a* secret configured somewhere in Shipit matches — it says nothing about which repository's data is truthful.

This exactly matches the analog described in the rules: "an organization that authenticated versus the repository that is written."

### Impact Explanation
- `StatusHandler` writes a CI commit status (`state`, `context`, `target_url`, `description`) onto any commit matching a SHA across the entire Shipit install, without any organization/repository scoping in the query (`Commit.where(sha: params.sha)`). [11](#0-10)  Since commit deployability is gated on required/blocking statuses (`Commit#deployable?`, exercised in `test/models/commits_test.rb`), an attacker who can only authenticate as Org A can forge a "success" status for a commit that belongs to a stack under Org B, defeating Org B's CI gating and enabling an **unauthorized deploy**.
- `PushHandler`/`CheckSuiteHandler` can trigger `GithubSyncJob`/check-run refreshes against Org B's stacks using data supplied entirely by the Org‑A‑signed request, causing cross-repository state changes driven by attacker-controlled content.
- This crosses the "unauthorized deploy" and "cross-repository writes" impact tiers explicitly called out as in-scope.

### Likelihood Explanation
This is only exploitable in the documented multi-GitHub-App deployment configuration (`docs/setup.md`, "Using Multiple Github Applications"), where more than one organization/webhook secret is configured in `secrets.github`. [12](#0-11)  In that configuration, any principal who legitimately controls one onboarded GitHub organization (an ordinary, unprivileged relationship compared to Shipit itself — they only need push/webhook access to their own org's repos, not to Shipit, not a Shipit API token, and not the target org's credentials) can produce a validly-signed request body whose JSON content targets a different organization's stacks. No `ApiClient` token, `webhook_secret` of the victim org, or Shipit session is required — only control of one already-configured tenant's webhook delivery.

### Recommendation
In `WebhooksController#verify_signature`, after computing and validating the signature, additionally validate that the organization used to select the verification secret matches the owner embedded in `repository.full_name` (i.e., re-derive the owner from `full_name` and require it to equal `repository_owner` before dispatching). Equivalently, each `Handler` should scope its repository/stack/commit lookups by the same trusted organization identity used for signature verification, rather than trusting `repository.full_name` (and, for `StatusHandler`, additionally scope `Commit.where(sha:)` by the verified repository) in isolation.

### Proof of Concept
Conceptual PoC (cannot be executed here, no filesystem/terminal access):
1. Configure Shipit with two GitHub Apps, `OrgA` and `OrgB`, each with distinct `webhook_secret`s, per `docs/setup.md`'s multi-app schema.
2. As the administrator of `OrgA` (an ordinary GitHub org owner, not a Shipit operator), construct a JSON body for a `status` event where `repository.owner.login = "OrgA"` but `sha` matches a commit belonging to a stack under `OrgB/some-repo`, and `state = "success"`.
3. Sign the raw body with `OrgA`'s `webhook_secret` (which the attacker legitimately possesses) and send it to `/webhooks` with `X-Github-Event: status` and the resulting `X-Hub-Signature`.
4. `verify_signature` looks up `Shipit.github(organization: "OrgA")`, validates successfully against `OrgA`'s secret. [1](#0-0) 
5. `StatusHandler#process` then writes the forged `success` status onto the `OrgB` commit purely by SHA match, with no relation back to `OrgA`. [9](#0-8)

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently. The top-level keys should be the name of each Github organization, and the following sub-keys are the Github app details for that particular organization.
