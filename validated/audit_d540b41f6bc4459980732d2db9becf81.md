### Title
`OpenedHandler#provision?` (and `ReopenedHandler#unarchive?`) misapply Ruby operator precedence, letting `provisioning_behavior` alone (allow_with_label/prevent_with_label) trigger PR-driven stack provisioning even when `review_stacks_enabled` is `false` - ([File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb])

### Summary
`Repository` is created with schema defaults `review_stacks_enabled: false` and `provisioning_behavior: 'allow_all'`. `OpenedHandler#provision?` and `ReopenedHandler#unarchive?` intend `review_stacks_enabled` to gate all provisioning behaviors, but due to Ruby `&&`/`||` precedence, `review_stacks_enabled` only gates the `allow_all` branch; the `allow_with_label` and `prevent_with_label` branches are evaluated independently of it. Consequently, an operator who sets `provisioning_behavior` to `allow_with_label` or `prevent_with_label` for any reason - without touching `review_stacks_enabled` - unintentionally re-enables PR-triggered stack creation for any repository whose PR label matches (or doesn't match) the configured label.

### Finding Description
The binding the operator relies on is: `review_stacks_enabled == false` implies `provision? == false` for all `provisioning_behavior` values. This is false for two of three enum values.

`app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb:65-70`: [1](#0-0) 
```
def provision?
  repository.review_stacks_enabled &&
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
```

Because `&&` binds tighter than `||` in Ruby, this parses as:
`(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label) || (prevent_with_label? && !has_label)`

`review_stacks_enabled` is ANDed only with the first disjunct. The second and third disjuncts (`allow_with_label`/`prevent_with_label` paths) are entirely independent of `review_stacks_enabled`. `ReopenedHandler#unarchive?` has the identical structure at [2](#0-1) .

This is provably a bug, not intended behavior, because the sibling `LabeledHandler` implements the same gate correctly by ANDing `review_stacks_enabled` across the entire behavior check at the top level: [3](#0-2) 
```
def respond_to_label_change?
  params.action == "labeled" &&
    pull_request_state == "open" &&
    repository.review_stacks_enabled &&
    (archive? || unarchive?)
end
```
Here `review_stacks_enabled` correctly gates the whole `archive?/unarchive?` decision regardless of provisioning_behavior. `OpenedHandler`/`ReopenedHandler` do not follow this pattern - they fold the gate into the boolean expression incorrectly.

Schema defaults confirm the exploitable starting state: `review_stacks_enabled` defaults to `false` and `provisioning_behavior` defaults to `allow_all`, both set in [4](#0-3) . `Repository#provisioning_behavior` is a plain enum with no cross-field validation requiring `review_stacks_enabled` to be true before allowing `allow_with_label`/`prevent_with_label`: [5](#0-4) .

**Exploit flow:** A repository is onboarded normally (`review_stacks_enabled=false`, `provisioning_behavior='allow_all'` - default, no stacks created since `review_stacks_enabled` is false and `allow_all` branch requires it). An operator, testing PR labeling for unrelated reasons, sets `provisioning_behavior = 'allow_with_label'` and a `provisioning_label_name`, without touching `review_stacks_enabled` (they believe it remains the master off-switch). Any GitHub user who can open a pull request against that repository and apply the configured label (an unprivileged action on their own fork/PR) causes `OpenedHandler#provision?` to evaluate true, and `ReviewStackAdapter#find_or_create!` creates and queues a review stack for provisioning - despite `review_stacks_enabled` still being `false`. This triggers the review-stack provisioning task pipeline (`Command`/task execution) for a repository the operator explicitly believed had review stacks disabled.

No existing guard prevents this: `respond_to_pull_request_opened?` only checks `params.action == "opened"` and `provision?` itself (the buggy predicate); there is no separate top-level `review_stacks_enabled` check as in `LabeledHandler`.

### Impact Explanation
This causes provisioning task execution (stack creation → provisioning queue → task/`Command` execution) for a repository configuration the operator explicitly intended to leave disabled. Given `PullRequest::OpenedHandler` runs on the `opened` webhook, any external contributor who can open a PR with a matching/absent label controls whether a review stack (and its associated provisioning task, which runs commands from the repository's `shipit.yml`/config on the deploy host) gets created and run - a repeatable action against every repository whose operator has ever flipped `provisioning_behavior` away from `allow_all` without separately re-verifying/re-disabling review stacks. This matches "Critical: a payload... causing unauthorized... task" execution triggered by an unprivileged PR actor, gated by a control (`review_stacks_enabled`) the operator relies on but which the code fails to honor for two of three enum states.

### Likelihood Explanation
Preconditions: a repository with `review_stacks_enabled=false` (default) whose `provisioning_behavior` has been changed to `allow_with_label` or `prevent_with_label` (a normal, documented operator action visible in the settings UI, not requiring any privileged secret). No other Shipit configuration or attacker credential is needed - the attacker only needs to be able to open a PR and add/omit a label on a repository being tracked by Shipit. This is a plausible and low-cost misconfiguration path (operators reasonably assume `review_stacks_enabled` is an independent kill switch), and the exploit is trivially repeatable per PR.

### Recommendation
Fix operator precedence by explicitly ANDing `review_stacks_enabled` across the entire behavior expression in both `OpenedHandler#provision?` and `ReopenedHandler#unarchive?`, mirroring `LabeledHandler`'s pattern, e.g.:
```ruby
def provision?
  repository.review_stacks_enabled &&
    (repository.provisioning_behavior_allow_all? ||
     (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
     (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?))
end
```
Apply the same wrapping fix to `ReopenedHandler#unarchive?`.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb`):
```ruby
test "does NOT create stacks when review_stacks_enabled is false, even with allow_with_label matching" do
  repository = shipit_repositories(:shipit)
  repository.review_stacks_enabled = false      # default/off - operator's expected master switch
  repository.provisioning_behavior = :allow_with_label
  repository.provisioning_label_name = "pull-requests-label"
  repository.save!

  payload = payload_parsed(:pull_request_opened)
  payload["pull_request"]["labels"] << { "name" => "pull-requests-label" }

  assert_no_difference -> { Shipit::Stack.count } do
    OpenedHandler.new(payload).process
  end
end
```
Binding under test: `repository.review_stacks_enabled == false` should imply `Shipit::Stack.count` unchanged after `OpenedHandler#process`. With current code, `provision?` returns `true` (via the `allow_with_label? && has_label` disjunct, independent of `review_stacks_enabled`), so the `assert_no_difference` fails and a stack is created - demonstrating the vulnerability. After applying the recommended fix, the assertion passes.
