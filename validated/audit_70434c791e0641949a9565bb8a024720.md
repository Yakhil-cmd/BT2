## Title
Unscoped cross-repository status write via `Commit.where(sha:)` in `StatusHandler#process` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

## Summary
`StatusHandler#process` resolves the target commit(s) for an incoming `status` webhook by a bare, global `Commit.where(sha: params.sha)` query with no repository/organization scoping whatsoever, unlike sibling handlers such as `CheckSuiteHandler` which explicitly scope through `stacks.where(branch: ...)` derived from `payload.dig('repository', 'full_name')`. Since a git commit SHA is content/history-derived and is preserved identically across forks and mirrors of a repository, any actor able to trigger a legitimately-signed `status` webhook containing a SHA that also exists as a `Commit` record belonging to an unrelated `Stack` can write a `Status` (e.g. `context: ci/smoke, state: failure`) onto that unrelated stack's commit.

## Finding Description
The broken binding is: **the equality `Status.stack_id == commit.stack.repository` should hold for the repository that authenticated the webhook, but `StatusHandler` never checks it.**

Code path:
- `Shipit::WebhooksController#create` only verifies `X-Hub-Signature` against the GitHub App/secret associated with `repository_owner` (`params.dig('repository','owner','login')`), i.e. at the **organization** level — [1](#0-0) . It does not, and cannot, verify that the SHA in the payload belongs to the specific repository named in `payload['repository']['full_name']`.
- The `status` event is routed to `Shipit::Webhooks::Handlers::StatusHandler` [2](#0-1) .
- `StatusHandler#process` does:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [3](#0-2) 
This query is global across the entire `commits` table — every stack, every repository, every organization tracked by the Shipit instance. It never calls the base `Handler#stacks` helper (which does scope via `Repository.from_github_repo_name(repository_name)`) — [4](#0-3) . Compare this with `CheckSuiteHandler`, which correctly scopes: `stacks.where(branch: params.check_suite.head_branch).each { |stack| stack.commits.where(sha: ...) }` — [5](#0-4) .

`create_status_from_github!` then writes a `Status` row keyed only to `commit.stack_id` (the pre-existing stack the matching `Commit` belongs to), and that write drives real state: `enable_ci_on_stack`, `schedule_continuous_delivery`, and via `Commit#deployable?` (`!locked? && (stack.ignore_ci? || (success? && !blocked?))`) it directly gates deploy eligibility — [6](#0-5) , and blocking behavior via `Commit#blocked?` — [7](#0-6) . `Status.after_create` also fires `enable_ci_on_stack` and `schedule_continuous_delivery` — [8](#0-7) .

Exploit flow: Git commit hashes are preserved verbatim across forks/mirrors that share history. If the attacker's own repository (which they legitimately own, per the stated attacker capabilities) shares a commit SHA with a `Commit` row already tracked for a victim `Stack` (e.g. because the victim's tracked repository history was forked, mirrored, or otherwise reproduced, or because the attacker's own repo's PR/base commit lineage is shared with the tracked stack in the same GitHub organization/App installation), the attacker can, using ordinary GitHub API access to their own repository (setting a commit status requires only write access to *their own* repo), cause GitHub to emit a `status` webhook whose signature validates against the correct organization's app secret (since it is a real, GitHub-originated webhook), with `sha` equal to the shared commit and `context: ci/smoke`, `state: failure`. Because `StatusHandler` performs no per-repository authorization, this status is recorded against the victim's `Commit`/`Stack`, flipping `blocked?`/`deployable?` for the victim's required context. Combined with `review_stacks_enabled: true, allow_all` (per `PullRequest::OpenedHandler#provision?` — [9](#0-8) ), externally-opened PRs auto-provision review stacks that execute the repository's `shipit.yml` deploy/provision logic, so an attacker-forced status flip can trigger or block a deploy/task execution path.

None of the existing guards prevent this: `verify_signature` only authenticates the org, not the specific repository or SHA ownership (`app/controllers/shipit/webhooks_controller.rb:24-49`); `ExplicitParameters` schema in `StatusHandler` only validates types, not repository scope (`status_handler.rb:7-18`); there is no `Repository`/`Stack` scoping check anywhere in the handler.

## Impact Explanation
A `status` payload for one repository/organization can mutate `Status`/deployability state for a `Commit` and `Stack` belonging to a different, unrelated repository that never authenticated that webhook — this is a "payload for one repository mutating another's stack/commit" class finding, matching the Critical impact category (unauthorized deploy/rollback/block via cross-tenant state mutation). The blast radius spans every `Stack`/`Repository` tracked by the same Shipit instance, since the query is entirely global (not even organization-scoped), and is repeatable for any SHA collision the attacker can arrange or that arises naturally from forking/mirroring shared history.

## Likelihood Explanation
This requires: (1) the victim stack requiring `ci/smoke` as a blocking/required status with `review_stacks_enabled: true, allow_all`; (2) a commit SHA shared between an attacker-controlled repository and a `Commit` row tracked by the victim stack — which is trivially achievable for any pre-existing commit inherited via a GitHub fork (fork preserves all upstream SHAs) or for any commit content the attacker can otherwise reproduce; (3) the ability to send a real GitHub-signed `status` webhook for that SHA, which only requires the attacker to have status-write access to *some* repository within an organization whose GitHub App/webhook is registered with the Shipit instance — a routine, low-privilege capability (e.g., posting a status via GitHub's REST API to a repo the attacker owns/controls). No Shipit credentials, sessions, or secrets are needed. This is a low-cost, repeatable attack once the preconditions are met.

## Recommendation
Scope `StatusHandler#process` to the repository that authenticated the webhook, mirroring `CheckSuiteHandler`'s pattern: derive `stacks` via `Repository.from_github_repo_name(payload.dig('repository','full_name'))` and only update `Commit` rows (`stack.commits.where(sha: params.sha)`) that belong to those stacks, rather than querying the global `Commit` table by SHA alone.

## Proof of Concept
Add to `test/models/shipit/webhooks/handlers/status_handler_test.rb` (or equivalent):
```ruby
test "status for a SHA belonging to another repository's stack does not affect that stack" do
  victim_repo   = shipit_repositories(:shipit) # or a distinct fixture repo
  attacker_repo = create_repository(full_name: "attacker/unrelated-repo") # different repository
  victim_stack  = shipit_stacks(:shipit) # requires 'ci/smoke', review_stacks_enabled true, allow_all
  victim_commit = victim_stack.commits.create!(sha: "deadbeef" * 5)

  before_deployable = victim_commit.deployable?
  before_blocked     = victim_commit.blocked?

  payload = {
    "sha" => victim_commit.sha,
    "state" => "failure",
    "context" => "ci/smoke",
    "repository" => { "full_name" => attacker_repo.github_repo_name, "owner" => { "login" => "attacker" } }
  }

  Shipit::Webhooks::Handlers::StatusHandler.new(payload).process

  victim_commit.reload
  # Binding under test: a status authenticated for `attacker_repo` must not change state
  # for a commit belonging to `victim_stack` (different repository).
  assert_equal before_deployable, victim_commit.deployable?, "status from unrelated repo altered victim deployability"
  assert_equal before_blocked, victim_commit.blocked?, "status from unrelated repo altered victim blocked state"
  assert_empty victim_commit.statuses.where(context: "ci/smoke", state: "failure")
end
```
Currently this test fails: `StatusHandler#process`'s bare `Commit.where(sha: params.sha)` matches the victim commit regardless of `payload['repository']`, creating the `ci/smoke failure` `Status` and flipping `deployable?`/`blocked?` for the victim stack.
