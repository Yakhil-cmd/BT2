### Title
Contract hash uses unseparated field concatenation, allowing text/field-boundary confusion in prosaic/arbiter contracts - (File: prosaic_contract.js, arbiter_contract.js)

### Summary
Expat's CVE-2022-25236 root cause is that a namespace-separator character could be smuggled into a field so that two logically distinct pieces of data (prefix/URI) collapse into an ambiguous serialized form, defeating the parser's boundary integrity. ocore's canonical hashing helper (`getSourceString` in `string_utils.js`) defends against exactly this class of bug by using an explicit `STRING_JOIN_CHAR` and rejecting any string/key that embeds it [1](#0-0) . However, two contract-hashing helpers reachable from a paired device (private-payment counterparty) bypass this protection entirely by concatenating attacker-influenced free-text fields with **no separator at all**.

### Finding Description
`prosaic_contract.getHash()` computes the contract identifier as `sha256(title + text + creation_date)` with plain string concatenation and no delimiter between `title` and `text`: [2](#0-1) 

Because `title` and `text` are both free-form strings supplied by the contract creator (a paired device / private counterparty), the field boundary between them is not fixed: `title="AB", text="CD"` and `title="A", text="BCD"` produce the identical string `"ABCD"+creation_date` and therefore the identical hash. This is the same "missing separator → field confusion" defect class as the Expat CVE.

`arbiter_contract.getHashSrc()` has the same defect for contracts created before `exports.NEW_HASH_DATE = '2026-11-01'`, joining `title, text, creation_date, payer_name, arbiter_address, payee_name, amount, asset` with `""` (empty delimiter): [3](#0-2) 
Since today's date (2026-09-15) is before `NEW_HASH_DATE`, this vulnerable no-separator path is the one currently in effect for all newly created arbiter contracts. The newer branch does add a delimiter (`exports.DELIMITER = "[|#|]"`) but only takes effect after 2026-11-01, and even then relies on the delimiter itself never appearing inside `title`/`text`/`party_name` (no check is performed to reject the delimiter substring the way `string_utils.js` rejects `STRING_JOIN_CHAR`).

`getContactsHash()` has an analogous issue joining `payer_contact_info, payer_pairing_code, payee_contact_info, payee_pairing_code` with `"|"` and no escaping/rejection check: [4](#0-3) 

The contract hash is not decorative: it is embedded in an on-chain "data" message as `contract_text_hash` and cross-checked when a signing unit is received (`payload.contract_text_hash !== contract.hash`), and it is also embedded directly into the arbiter dispute-resolution data-feed key `"CONTRACT_" + contract.hash` used inside the shared-address definition: [5](#0-4) [6](#0-5) 
The encrypted contract content (`title`, `text`) sent to the arbiter for dispute resolution is a separate message not itself hash-committed field-by-field, so `contract.hash` is the only cryptographic binding between the on-chain commitment and the actual contract text: [7](#0-6) 

### Impact Explanation
Because the title/text boundary can be shifted, a malicious contract party (the "peer" in a prosaic or arbiter contract, or a colluding cosigner) can craft two different `(title, text)` pairs that hash to the same `contract.hash`/`contract_text_hash`, while keeping `creation_date` (and, for arbiter contracts, `amount`/`asset`/addresses) unchanged. This lets the attacker:
- Present one (innocuous) contract text to a cosigner/dispute arbiter for review/signing while a different text with the same commitment hash is later asserted as "the" agreed contract, undermining the non-repudiation guarantee that `contract_text_hash` is supposed to provide.
- In arbiter disputes, contest which of two colliding contract texts was actually signed, since the on-chain hash cannot distinguish them, potentially causing the arbiter to rule incorrectly and one party to lose the disputed funds locked in the shared address that this contract mechanism secures.

This is a real-value/fund-loss vector reachable purely from a paired-device counterparty crafting `title`/`text` at contract-creation time, without needing any privileged access — matching the required "private-payment counterparty" trust boundary. I rate it Medium: it requires the dispute/verification path to actually be exercised by a human/arbiter and does not directly forge a signature or double-spend an already-stable output, but it does break the cryptographic integrity guarantee the hash is meant to provide for locked funds.

### Likelihood Explanation
Likelihood is Medium: any counterparty to a prosaic or arbiter contract fully controls `title` and `text` and can trivially construct two boundary-shifted variants offline (no cryptographic hash break needed — it's a string-concatenation ambiguity, not a SHA-256 collision). The precondition (before 2026-11-01 for arbiter contracts) currently holds.

### Recommendation
- Change `prosaic_contract.getHash()` and the pre-`NEW_HASH_DATE` branch of `arbiter_contract.getHashSrc()` to serialize fields the same safe way `string_utils.getSourceString`/`getJsonSourceString` do: use a reserved separator/prefix scheme and explicitly reject (or escape) any field value that contains the separator, or better, hash a length-prefixed or JSON-based canonical encoding (`objectHash.getBase64Hash(contract, true)`).
- Apply the same fix to `getContactsHash()`'s `"|"` join.
- Retire/accelerate deprecation of the unseparated legacy hash format rather than gating it on a future date, since it is presently active.

### Proof of Concept
1. Party A creates a prosaic contract offer with `title = "Pay 100"`, `text = "USD to Bob"`.
2. Party A separately (or later) claims the "real" agreed contract was `title = "Pay 100U"`, `text = "SD to Bob"`.
3. Both produce identical `sha256(title+text+creation_date)` values, so both validate against the same `contract.hash`/`contract_text_hash` recorded in the on-chain data message (`prosaic_contract.js:98-100`), and the shared/derived arbiter address and dispute-resolution logic cannot distinguish which text was truly agreed upon, as demonstrated by the concatenation logic at [2](#0-1)  and [8](#0-7) .

function getHashSrc(contract) {
	const payer_name = contract.me_is_payer ? contract.my_party_name : contract.peer_party_name;
	const payee_name = contract.me_is_payer ? contract.peer_party_name : contract.my_party_name;
	const payer_address = contract.me_is_payer ? contract.my_address : contract.peer_address;
	const payee_address = contract.me_is_payer ? contract.peer_address : contract.my_address;
	const src = contract.creation_date > exports.NEW_HASH_DATE
		 ? [contract.title, contract.text, contract.creation_date, payer_address, payer_name || '', contract.arbiter_address, payee_address, payee_name || '', contract.amount, contract.asset || 'null'].join(exports.DELIMITER)
		 : [contract.title, contract.text, contract.creation_date, payer_name || '', contract.arbiter_address, payee_name || '', contract.amount, contract.asset || 'null'].join("");
	return src;
}

function getHash(contract) {
	return crypto.createHash("sha256").update(getHashSrc(contract), "utf8").digest("base64");
