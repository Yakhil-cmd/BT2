### Title
Permanent market freeze via i128 overflow in interest accrual once scaled debt value exceeds `i128::MAX` - ([File: contracts/pool/src/interest.rs](contracts/pool/src/interest.rs), [common/src/rates/simulate.rs](common/src/rates/simulate.rs))

### Summary
Analog of CVE-2021-46389 (integer overflow from arithmetic over inputs whose product exceeds the integer width). XOXNO Lending stores debt as RAY-scaled shares and unscale them during accrual by computing `borrowed_scaled * borrow_index` in i128. When the scaled debt times the borrow index exceeds `i128::MAX`, the accrual step panics with `GenericError::MathOverflow`. Because every pool verb (supply, borrow, withdraw, repay, liquidation settlement, `clean_bad_debt`, `recapitalize`) calls `global_sync` first, one overflow freezes the entire market permanently — an unprivileged supplier/borrower can steer a market to this state, and there is no recovery path.

### Finding Description
`global_sync` runs at the head of every market mutation and applies `accrue_step` per elapsed chunk (`contracts/pool/src/interest.rs:20-53`). The step unscale debt via `scaled_to_original`/`position_value`-style `half_up(borrowed * borrow_index / RAY)` arithmetic, which internally uses `mul_div_half_up` and panics with `GenericError::MathOverflow` when the product or quotient does not fit i128 (`common/src/math/fp_core.rs:108-118`). The intended safeguard is `MAX_BORROW_INDEX_RAY` (`10^36` raw RAY), which caps index growth, and `MAX_COMPOUND_DELTA_MS` chunking, which bounds the per-step exponent — but neither bounds the *value* `borrowed * borrow_index`, which grows linearly with market size. The project's own invariant document concedes this: "Debt-value overflow can still revert accrual before that ceiling is reached" (`docs/reference/invariants.md`, INV-IDX-01). The harness test `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` (`tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:321-356`) demonstrates it: at ~98% utilization on the steep XLM rate curve, a market with ~10^27 raw supply reaches `MathOverflow` in accrual, after which `withdraw` and `repay` both revert with `MATH_OVERFLOW` — the index cap never engages.

### Impact Explanation
Permanent freezing of funds and protocol insolvency impact. Once `borrowed * borrow_index` crosses `i128::MAX`, every entrypoint that accrues first — `withdraw`, `repay`, `borrow`, `supply`, `liquidate`, `clean_bad_debt`, `update_indexes` — panics before touching balances. Supplier principal, unclaimed yield, and any repayable debt in that (hub, token) book are permanently locked; the bad-debt write-down and recapitalize paths cannot run because they too accrue. A single unprivileged borrower maintaining high utilization on a large market is sufficient — no oracle manipulation, governance action, or privileged key is needed; only token capital and elapsed time.

### Likelihood Explanation
Medium. The attacker does not need to trigger the cliff instantly — the index compounds toward it whenever utilization stays high. Whale-scale markets (billions of units at 18 decimals) at sustained ~98% utilization reach the cliff in a few years per the harness test, and the steep `slope3` rate segment accelerates it. The attacker can also keep utilization pinned by borrowing against their own collateral. No special transaction shape beyond ordinary `supply`/`borrow`/`update_indexes` calls is required, and `update_indexes` is permissionless so any party can push the accrual over the edge once the product crosses the boundary.

### Recommendation
Saturate rather than panic at the RAY-value ceiling: have `scaled_to_original`/the accrual step clamp `borrowed * borrow_index` to `i128::MAX` (or to the representable-debt bound implied by `MAX_BORROW_INDEX_RAY`) and continue accrual, so the index cap engages instead of a hard panic. Alternatively, enforce a per-market supply/borrow cap calibrated so `borrowed_max * MAX_BORROW_INDEX_RAY < i128::MAX`, rejecting `supply`/`borrow` amounts that would let the debt value reach the cliff — this turns the overflow into a rejectable precondition while the market is still operable. At minimum, give `repay` a no-accrual escape path (repay-at-cached-index) so borrowers can unwind debt and restore the market to a representable value.

### Proof of Concept
Reproduced by the existing harness test `tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:321-356`:

```rust
let mut t = LendingTest::new()
    .with_market(big("BIG18", 18, xlm_curve()))
    .with_market(col())
    .with_max_utilization_disabled_all_markets()
    .build();
lift_caps(&t, "BIG18", 18);
let principal = BILLION * 10i128.pow(18);
t.supply_raw(BOB, "BIG18", principal);
t.borrow_raw(ALICE, "BIG18", principal / 100 * 98); // ~98% utilization

// Advance time yearly until accrual overflows
loop { t.advance_time(YEAR_SECS); if t.try_update_indexes_for(&["BIG18"]).is_err() { break; } }

// Market is now permanently frozen:
assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
// borrow_index < MAX_BORROW_INDEX_RAY: the index cap never engaged
```

The overflow occurs inside `accrue_step`'s `borrowed * borrow_index` unscale (`mul_div_half_up` → `GenericError::MathOverflow`, `common/src/math/fp_core.rs:108-118`), invoked unconditionally by `global_sync` (`contracts/pool/src/interest.rs:20-53`) before any state mutation.

Caveat: the repo documents this failure mode in `docs/reference/invariants.md` (INV-IDX-01) as a known residual risk rather than a guaranteed invariant; if the audit scope excludes documented limitations, this finding should be treated as informational. The mechanism, reachability, and permanent-freeze impact are nonetheless demonstrated in-repo.
