### Title
Windows reserved-device-name filter bypassable via trailing dots/spaces or non-`.`-delimited suffixes, allowing writes to device paths (CON, PRN, etc.) - ([File: pkg/cmd/release/download/download.go])

### Summary
`isWindowsReservedFilename` normalizes an asset name only by uppercasing and splitting once on `.`, then requires an exact match against a fixed list of DOS device names. Asset names such as `"CON "` (trailing space), `"CON."` (trailing dot), or names using alternate-data-stream syntax (`"CON::$DATA"`) are not exact matches and pass the filter, yet Windows' own path-normalization layer strips trailing dots/spaces from path components (and treats `::$DATA` as a stream on the base file), so the underlying `os.OpenFile` call in `Copy` can still resolve to the `CON` device instead of a regular file.

### Finding Description

which calls: [2](#0-1) 
The normalization `strings.ToUpper(strings.Split(filename, ".")[0])` only handles the simple `NAME.ext` case. It does not:
- Trim trailing whitespace/dots from the base name before comparison (Windows itself strips trailing dots and spaces from path components during resolution in many API paths), so `"CON "` or `"CON."` no longer equal `"CON"` in Go but can still be resolved to the device by the OS.
- Strip NTFS alternate-data-stream suffixes (`":$DATA"`, `"::$DATA"`), so `"CON::$DATA"` is not recognized, though on NTFS this still opens the `CON` device's default stream.
- Handle Unicode confusable/fullwidth characters (e.g., fullwidth "Ｃ" U+FF23), which a naive `ToUpper`/exact-match will not fold to the ASCII device name, though real filesystem-level device name interception in Win32 is based on the DOS device namespace and is unlikely to trigger for genuine Unicode homoglyphs (this vector is weaker/unconfirmed).

Since the flagged names never reach the accepted list, `downloadAsset`/`Copy` proceeds to `os.OpenFile(fp, ...)` with the crafted name, and Windows may then interact with the reserved device instead of creating a normal file, defeating the purpose of the check.

### Impact Explanation
This does not enable arbitrary file write outside the destination directory (no path traversal), so it is not a directory-confinement bypass. The realistic impact is limited to writing to/opening a reserved device path (e.g. `CON`, `PRN`, `NUL`) which can cause the download to hang, error out unexpectedly, or interact with console/printer/null devices — a denial-of-service / unexpected-I/O condition scoped to the `gh release download` command on Windows, consistent with the intent the reserved-name filter was added to prevent.

### Likelihood Explanation
Preconditions: victim runs `gh release download` (or downloads with default patterns) on Windows against a release published by the attacker, containing an asset with a crafted name like `"CON "`, `"CON."`, or `"CON::$DATA"`. This is fully within an unprivileged attacker's control (any GitHub user can create a public release with arbitrary asset filenames, subject to GitHub's own upload-side filename restrictions, which is the main uncertainty — GitHub's asset upload API may itself reject or sanitize trailing dots/spaces in filenames, which would neutralize this bypass; this was not verified in this codebase since it depends on GitHub server-side behavior, not `cli`).

### Recommendation
Trim trailing dots and spaces from the base filename component (and strip NTFS stream suffixes like `:...$DATA`) before the exact-match comparison in `isWindowsReservedFilename`, matching Windows' own path-canonicalization semantics, e.g.:
```go
base := strings.Split(filename, ".")[0]
base = strings.TrimRight(base, " .")
base = strings.SplitN(base, ":", 2)[0] // strip ADS suffix
filename = strings.ToUpper(base)
```
Also consider testing against Unicode-normalized (NFKC) input if fullwidth-character bypass is confirmed to be exploitable on real Windows kernel32 path resolution.

### Proof of Concept
```go
func TestIsWindowsReservedFilename_Bypass(t *testing.T) {
    cases := []struct {
        name     string
        reserved bool
    }{
        {"CON", true},
        {"CON.txt", true},
        {"CON ", true},   // currently false — bypass
        {"CON.", true},   // currently false — bypass
        {"CON::$DATA", true}, // currently false — bypass
    }
    for _, c := range cases {
        got := isWindowsReservedFilename(c.name)
        if got != c.reserved {
            t.Errorf("isWindowsReservedFilename(%q) = %v, want %v", c.name, got, c.reserved)
        }
    }
}
```
Running this against the current implementation shows `"CON "`, `"CON."`, and `"CON::$DATA"` are classified as `false` (not reserved) while behaving as reserved device names under Windows path resolution, confirming the bypass of the intended guard in `isWindowsReservedFilename`. Note: exploitability in practice depends on whether GitHub's release-asset upload API permits filenames with trailing spaces/dots or colons, which could not be verified from this repository alone.

func isWindowsReservedFilename(filename string) bool {
	// Windows terminals should prevent the creation of these files
	// but that behavior is not enforced across terminals. Prevent
	// the user from downloading files with these reserved names as
	// they represent an exploit vector for bad actors.
	// Reserved filenames defined at:
	// https://learn.microsoft.com/en-us/windows/win32/fileio/naming-a-file#win32-file-namespaces
	reservedFilenames := []string{"CON", "PRN", "AUX", "NUL", "COM0",
		"COM1", "COM2", "COM3", "COM4", "COM5",
		"COM6", "COM7", "COM8", "COM9", "COM¹",
		"COM²", "COM³", "LPT0", "LPT1", "LPT2",
		"LPT3", "LPT4", "LPT5", "LPT6", "LPT7",
		"LPT8", "LPT9", "LPT¹", "LPT²", "LPT³"}

	// Normalize type case and remove file type extension from filename.
	filename = strings.ToUpper(strings.Split(filename, ".")[0])

	return slices.Contains(reservedFilenames, filename)
}
