### Title
Cross-tenant Status write via SHA-only lookup in StatusHandler#process bypassing repository scoping - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits purely by `sha` (`Commit.where(sha: params.sha)`) without scoping to the repository named in the verified webhook payload, unlike sibling handlers (e.g. `PushHandler`) that use the base `Handler#stacks` helper tied to `repository_name`. If a `Commit` with the same SHA exists in more than one `Stack`/`Repository` (git SHAs are content-addressed, so identical commit objects — e.g. an empty initial commit or a rebased/cherry-picked commit with identical tree/parent/author/timestamp — can independently exist in unrelated repos), a `status` webhook validly signed for the attacker's own organization/repository will write a `Status` row against the victim's `Commit`/`Stack` as well.

### Finding Description
The broken binding: the code assumes `commit.stack_id == Repository(payload['repository']['full_name']).stacks` for every `commit` mutated, but the actual code establishes no such equality — `Commit.where(sha: params.sha)` can return commits belonging to `stack_id`s unrelated to the authenticated `repository_owner`/`repository.full_name`.

`WebhooksController#verify_signature` authenticates the payload only against the `webhook_secret` of the organization named in `payload.dig('repository','owner','login')` (`repository_owner`), via `Shipit.github(organization: repository_owner).verify_webhook_signature`. This proves the sender controls that org's secret; it says nothing about which `Commit`/`Stack` the `sha` in the body actually belongs to.

`StatusHandler#process` then does:
```ruby
Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }
```
with no filter by `repository_name`/`stacks`, unlike `PushHandler#process`, which correctly scopes via `stacks.not_archived.where(branch:)`. `Commit#create_status_from_github!` calls `statuses.replicate_from_github!(stack_id, github_status)`, writing a `Status` keyed to whatever `stack_id` the matched `Commit` row has — not the stack of the repository that was authenticated.

Attack: an attacker owns `attacker/repo` with a Shipit-configured org (`attacker-org`) and possesses `attacker-org`'s `webhook_secret` legitimately. They craft or discover a commit SHA that is shared between a `Commit` row already tracked for `victim/repo`'s `Stack` (via content-identical commit objects — a realistic occurrence for well-known empty/initial commits, or SHAs that get pushed into their own repo history, e.g. via `git commit --allow-empty` with matching timestamp/author, or copying an existing public commit). They send `POST /webhooks` with `X-Github-Event: status`, `X-Hub-Signature` computed from their own `webhook_secret`, and body `{sha: SHA, state: 'success', context: 'ci/travis', repository: {full_name: 'attacker/repo', owner: {login: 'attacker-org'}}}`. `verify_signature` passes (correctly, for their own org). `StatusHandler#process` then matches and mutates the victim's `Commit` row (`stack_id` belonging to `victim/repo`'s `Stack`), writing a forged `success` status. If the victim's `Stack` merges on green CI (`ci/travis` success) via `MergeMergeRequestsJob`/similar, this can trigger an unauthorized merge or unblock a deploy for a stack the attacker never authenticated against.

Existing guards that fail to prevent this: `verify_signature` only checks org-level HMAC, not per-commit/per-repository ownership; the `ExplicitParameters` schema in `StatusHandler` only validates types of `sha`/`state`/etc., not repository binding; the `Handler#stacks`/`repository_name` scoping mechanism exists in the base class but is simply unused by `StatusHandler`.

### Impact Explanation
A payload authenticated for the attacker's own repository/organization causes a `Status` record to be written against a `Commit` belonging to a different tenant's `Stack`. This is a cross-repository/cross-tenant write, matching the Critical category "a payload for one repository mutating another's stack, commit". Depending on the victim stack's CI/merge configuration, a forged `success` status can unblock deploys (`Commit#deployable?` checks `success? && !blocked?`) or trigger auto-merge jobs, i.e. escalate into an unauthorized deploy/merge. This is repeatable against any repository/stack pair sharing a commit SHA, and requires no privilege beyond controlling one's own GitHub org/repo webhook secret.

### Likelihood Explanation
The precondition (`Commit.where(sha: SHA)` matching rows across two different `Stack`s) requires a duplicate/colliding SHA across two Shipit-tracked repositories, which is not guaranteed on every install but is realistic for repos that share initial commits, vendored history, or subtree/fork relationships common in monorepo migrations — Shipit's own `Commit` model imports commits by SHA per stack without any uniqueness constraint across stacks. The attacker needs only their own webhook secret (which any org owner legitimately has for their own app installation) and knowledge of a shared SHA; no victim secret or session is needed. This is a somewhat narrow-precondition but low-cost, fully repeatable attack once the SHA collision is identified.

### Recommendation
Scope `StatusHandler#process` (and any similar SHA-only handler) to the authenticated repository, e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` or `Commit.where(sha: params.sha, stack_id: stacks.select(:id))`, mirroring the `PushHandler` pattern that uses `Handler#stacks`/`repository_name` to bind the mutation to the repository that was actually authenticated by `verify_signature`.

### Proof of Concept
In `test/controllers/webhooks_controller_test.rb` (or a new test file), add:
```ruby
test ":status only updates commits belonging to the authenticated repository" do
  attacker_repo = Repository.create!(owner: 'attacker-org', name: 'repo')
  attacker_stack = Stack.create!(repository: attacker_repo, environment: 'production')
  victim_commit = shipit_commits(:first) # belongs to a different stack/repository

  request.headers['X-Github-Event'] = 'status'
  body = {
    sha: victim_commit.sha,
    state: 'success',
    context: 'ci/travis',
    repository: { full_name: 'attacker-org/repo', owner: { login: 'attacker-org' } }
  }.to_json

  assert_no_difference -> { victim_commit.statuses.count } do
    post :create, body:, as: :json
  end
end
```
Before the fix, this assertion fails because `StatusHandler#process` writes a `Status` for `victim_commit` even though the payload only authenticates `attacker-org/repo`.
