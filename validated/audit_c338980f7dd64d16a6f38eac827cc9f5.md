### Title
Webhook signature is verified against the claimed organization, but `StatusHandler`/`PushHandler` act on repository data never bound to that verified organization - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/`webhook_secret` to use for HMAC verification based on `repository_owner`, a value taken straight from the untrusted JSON payload (`repository.owner.login` or `organization.login`). Once the signature checks out for that claimed organization, the actual event handlers (`StatusHandler`, `PushHandler`, etc.) determine *what* to mutate using other payload fields (`sha`, `repository.full_name`) that are never cross-checked against the organization whose secret validated the request. In a multi-organization Shipit installation this breaks the binding between "the organization that authenticated" and "the repository/commit that is written."

### Finding Description
`verify_signature` picks the app/secret purely from attacker-supplied data and never re-validates that the resource being acted on actually belongs to that organization: [1](#0-0) [2](#0-1) 

Shipit explicitly supports one `webhook_secret` per GitHub organization (`lib/shipit.rb#github`, `github_app_config`), each organization installing its own GitHub App with its own secret: [3](#0-2) 

`StatusHandler#process`, invoked once the signature is accepted, never scopes by repository/organization at all — it matches purely on `sha` across the entire `Commit` table, i.e. across every stack of every organization hosted by this Shipit instance: [4](#0-3) 

Contrast this with the base `Handler` class and handlers like `PushHandler`, which at least scope to `Repository.from_github_repo_name(repository.full_name)` — but `full_name` is itself an unverified payload field never tied to the organization that authenticated the request: [5](#0-4) [6](#0-5) 

So the equality that should hold — `organization whose webhook_secret validated the request == organization/repository actually mutated` — does not hold anywhere in this flow. Anyone able to produce a validly-signed webhook for *any one* configured organization (e.g. Organization A, a low-trust org that installed the app) can set `sha` to a commit SHA that belongs to a completely different organization's stack (Organization B) and have Shipit process it as genuine, because `StatusHandler` has no repository scoping whatsoever, and `PushHandler`/other handlers only scope by an equally-unverified `full_name` string.

### Impact Explanation
Commit statuses gate merges/deploys in Shipit (`ci.require`, `ci.blocking` contexts documented in `README.md`, and the release/merge-queue status logic in `deploy_spec.rb`'s `release_status_context`). Forging a passing status webhook (`state: "success"`, arbitrary `context`) for a commit SHA belonging to a stack under a different, higher-trust organization lets an attacker who only controls a low-trust organization's webhook secret satisfy required CI checks for that other organization's commit, unblocking an unauthorized deploy or merge-queue merge. This crosses the "unauthorized deploy/merge" High/Critical impact bucket defined in scope.

### Likelihood Explanation
This requires the deployment to use the documented multi-organization `github:` secrets configuration (one webhook secret per org) — a configuration explicitly supported and documented (`docs/setup.md`, `test/dummy/config/secrets_double_github_app.yml`). Any actor who can trigger/replay a legitimately-signed webhook for the org they control (which requires no special Shipit privilege — only a working GitHub App installation for their own, arguably less-trusted organization) can exploit this without any Shipit account, `ApiClient` token, or repository write access, satisfying the "unprivileged attacker" constraint.

### Recommendation
Bind the verified organization to the resource being mutated: after `verify_signature` succeeds, re-derive/verify that `params.dig('repository','full_name')` (and, for `StatusHandler`, the commit's owning stack/repository) belongs to the same organization/owner used to select the webhook secret, and reject the request (422) otherwise. `StatusHandler` in particular must scope its `Commit` lookup by the verified repository/organization rather than matching bare SHAs across the whole installation.

### Proof of Concept
1. Deploy Shipit with the documented multi-org config (`secrets.github.OrgA`, `secrets.github.OrgB`, each with its own `webhook_secret`), as in `test/dummy/config/secrets_double_github_app.yml`.
2. Attacker controls (or has the webhook secret for) `OrgA`'s installed GitHub App — a low-trust org onboarded to the same Shipit instance.
3. Attacker crafts a `status` event payload:
   ```json
   {
     "sha": "<sha_of_a_commit_belonging_to_OrgB/critical-repo>",
     "state": "success",
     "context": "ci/required-check",
     "organization": {"login": "OrgA"},
     "repository": {"owner": {"login": "OrgA"}}
   }
   ```
4. Attacker signs the raw body with `OrgA`'s `webhook_secret` and sets `X-Hub-Signature` accordingly, and `X-Github-Event: status`.
5. `WebhooksController#verify_signature` resolves `Shipit.github(organization: "OrgA")` (via `repository_owner`), verifies successfully with OrgA's secret.
6. `StatusHandler#process` runs `Commit.where(sha: params.sha)` — matching the real commit under `OrgB`'s stack — and calls `create_status_from_github!`, marking that commit's `ci/required-check` as `success` for a repository the attacker never controlled or authenticated against.
7. If OrgB's stack requires that context (`ci.require`) for deploys/merge queue, the forged status unblocks deploy/merge on a repository the attacker has no legitimate access to.

```ruby
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )

    end
```

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
