### Title
Stack-scoped ApiClient token bypasses stack authorization scope in CCMenu endpoint - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Api::CCMenuController` overrides the `stack` accessor used elsewhere in the API to enforce per-token stack scoping, replacing it with an unscoped `Stack.from_param!(params[:stack_id])` lookup. This breaks the binding "the stack a token authorizes == the stack it touches," letting an `ApiClient` restricted to one stack read the build/deploy status of any other stack in the instance.

### Finding Description
Every other stack-scoped API controller resolves the target stack through `Api::BaseController#stacks`, which restricts the query set to the client's authorized stack when the `ApiClient` is scoped: [1](#0-0) 
`Api::StacksController` relies on exactly this scoped helper: [2](#0-1) 

`Api::CCMenuController`, however, defines its own private `stack` method that ignores `current_api_client.stack_id` entirely and resolves the stack straight from the unscoped `Stack` model: [3](#0-2) 

The controller still declares `require_permission :read, :stack`, which only checks that the token carries the string permission `read:stack` in `ApiClient#check_permissions!` — it never checks which stack the token is bound to: [4](#0-3) 

So the equality that should hold is:
`current_api_client.stack_id (the stack the token authorizes) == params[:stack_id] (the stack the request touches)`

For every other stack-scoped API endpoint this is enforced via `stacks.from_param!`. In `CCMenuController` it is not enforced at all: any valid token with the `read:stack` permission — even one created and scoped to a single, specific stack, such as the `here_come_the_walrus` fixture (`stack: shipit`) — can pass an arbitrary `params[:stack_id]` for a completely different stack and successfully render that stack's CCMenu status.

### Impact Explanation
This crosses the "stack a token authorises versus a stack it touches" trust boundary called out as in-scope. The `Api::CCMenuController#show` action discloses the target stack's name, latest deploy/rollback activity, last build status, last build label/time and lock state via `render('shipit/ccmenu/project', ...)`. An attacker holding any single-stack-scoped `ApiClient` token (e.g. obtained legitimately for CI polling of one stack, or via the self-service `CCMenuUrlController#fetch` flow which auto-creates a `read:stack`-scoped `ApiClient` for the current user) can enumerate `stack_id` params to read the build/deploy status of stacks they were never granted access to. This matches the High-severity category "unauthenticated read of stack state, task streams or deploy output" from the perspective of the token's actual grant — the token authenticates the caller but is not confined to the stack it was issued for.

### Likelihood Explanation
Likelihood is high for any deployment that issues stack-scoped `ApiClient`s (this is a supported, encouraged pattern — see `ApiClient#stack` association and the `here_come_the_walrus` fixture, and `CCMenuUrlController` which auto-provisions such tokens). No privileged action is required beyond already possessing one legitimately-scoped token; `stack_id` is a simple, guessable/enumerable path/query parameter (`owner/repo/environment`), and the vulnerable action requires only `read:stack`, the least-privileged permission in the system.

### Recommendation
Make `Api::CCMenuController#stack` route through the scoped `stacks` helper instead of the raw `Stack` model, mirroring every other stack-scoped controller:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
This ensures `current_api_client.stack_id?` scoping (already implemented in `BaseController#stacks`) is applied consistently, so a token can only ever resolve the stack it was actually authorized for.

### Proof of Concept
1. Create two stacks, `stack_a` (owner/repo-a/production) and `stack_b` (owner/repo-b/production).
2. Create an `ApiClient` scoped to `stack_a` only (`stack: stack_a`, `permissions: ['read:stack']`) — this is the standard pattern used by `CCMenuUrlController#fetch`: [5](#0-4) 
3. Using that client's `authentication_token`, issue: `GET /api/stacks/owner/repo-b/production/ccmenu.xml?token=<token>`.
4. Because `Api::CCMenuController#stack` calls `Stack.from_param!(params[:stack_id])` directly (no scoping check against `current_api_client.stack_id`), the request succeeds (`200 OK`) and returns `stack_b`'s CCMenu XML (name, `lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, `webUrl`), even though the token was only ever authorized for `stack_a`.
5. Contrast with `GET /api/stacks/owner/repo-b/production.xml` type endpoints implemented via `Api::BaseController#stacks`, which would return `404`/empty results for an out-of-scope stack, confirming the CCMenu path is the outlier that fails to enforce the token-to-stack binding.
