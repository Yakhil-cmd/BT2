### Title
API `ccmenu` endpoint bypasses per-token stack scoping, letting a stack-restricted `ApiClient` read any stack's build/deploy status - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Shipit::Api::BaseController` restricts an `ApiClient` token to a single stack via `stacks` (`current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all`), and its `stack` helper looks up the requested resource through this scoped relation (`stacks.from_param!(params[:stack_id])`). `Shipit::Api::CCMenuController`, however, overrides `stack` to call `Stack.from_param!(params[:stack_id])` directly, bypassing the `stacks` scope entirely. Any token that passes the `read:stack` permission check can therefore fetch CCMenu status/state for any stack in the installation, not just the one it is bound to.

### Finding Description
The identical bug class described in the onramp report - a resource identifier that is supposed to be uniquely bound/checked against an authorization scope, but the check is skipped in one code path - maps onto how `ApiClient` scoping to a single `stack_id` is enforced.

- `Shipit::ApiClient` supports an optional `stack` association (`belongs_to :stack, optional: true`) that is meant to restrict a token to a single stack: [1](#0-0) 
- `Shipit::Api::BaseController#stacks` enforces that scoping for every other controller: `current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all`, and `#stack` resolves the request through this scoped relation: [2](#0-1) 
- `Shipit::Api::CCMenuController` overrides `stack` to bypass this scope, resolving directly against the global `Stack` table: [3](#0-2) 
- The only authorization gate that remains on this controller is a coarse-grained permission check, not an ownership/scope check: [4](#0-3) 
- Tests only exercise the happy path with the client's own stack (`shipit_stacks(:shipit)`) and never exercise the stack-scoped token case, unlike the equivalent `StacksController` test which explicitly verifies "an api client scoped to a stack will only see that one stack": [5](#0-4) 

This is the analog of the report's binding break: the equality that should hold is `stack a token authorizes == stack the request resolves against`. For every other `Api::BaseController` subclass this equality is enforced through `stacks.from_param!`. In `CCMenuController` it is broken because `stack` resolves through the unscoped `Stack` model.

### Impact Explanation
Any holder of a valid `ApiClient` token that is deliberately restricted to a single stack (e.g., a CI system given `read:stack` for its own stack only, as created via `ccmenu_url_controller.rb`'s `read:stack`-only client: [6](#0-5) ) can instead read the CCMenu build/deploy status of *any* stack in the Shipit instance by supplying a different `stack_id` in the URL. This is an unauthenticated-for-other-stacks read of stack/deploy state (last build status, last build label, last build time, activity, web URL) which the report classifies as "unauthorized read of stack state / deploy output" - matching the High-impact category (unauthenticated read of stack state, task streams or deploy output) in this analysis' scope.

### Likelihood Explanation
Likelihood is Medium: exploitation only requires possession of any valid `ApiClient` token that has `read:stack` permission (even one intentionally scoped to a single stack by an administrator), which is a normal, lower-trust credential distributed to CI or monitoring integrations under the assumption that it is confined to one stack. No privileged account, GitHub credentials, or session hijack is required - only substitution of the `stack_id` URL segment.

### Recommendation
Remove the `stack` override in `Shipit::Api::CCMenuController`, or reimplement it to resolve through the scoped `stacks` method inherited from `BaseController` (i.e., `stacks.from_param!(params[:stack_id])`) so that a stack-restricted `ApiClient` cannot query stacks outside its authorized scope.

### Proof of Concept
1. Admin creates two stacks, `stack-a` and `stack-b`, and issues an `ApiClient` token scoped to `stack-a` only (`api_client.stack = stack_a`, `permissions: ['read:stack']`), analogous to the fixture `here_come_the_walrus` (`app/models/shipit/api_client.rb` `belongs_to :stack, optional: true`).
2. Using that token, request:
   `GET /api/stacks/<stack-b-owner>/<stack-b-repo>/<stack-b-env>/ccmenu`
   as routed in `config/routes.rb`: [7](#0-6) 
3. `CCMenuController#authenticate_api_client` authenticates the token normally, `require_permission :read, :stack` succeeds because the token does have `read:stack` (just scoped to `stack-a`).
4. `CCMenuController#stack` resolves `Stack.from_param!(params[:stack_id])` against `stack-b` directly (ignoring `current_api_client.stack_id`), returning `stack-b`'s CCMenu XML (last build status, label, time, etc.) even though the token is only supposed to see `stack-a`.
