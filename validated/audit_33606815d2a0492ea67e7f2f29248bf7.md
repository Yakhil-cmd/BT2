### Title
`X-Shipit-User` header identity spoofing bypasses `current_api_client.creator` binding - (File: `app/controllers/shipit/api/base_controller.rb`)

### Summary
`Shipit::Api::BaseController#identify_user` resolves `current_user` solely from the attacker-controlled `X-Shipit-User` HTTP header, with no cross-check against `current_api_client.creator` or any session. Any holder of a valid `ApiClient` token that has the permission required for a given write action (e.g. `lock:stack`, `deploy:stack`, `write:hook`) can forge the attributed actor on that action to be an arbitrary existing `User` login.

### Finding Description
The binding that should hold is: `current_user == current_api_client.creator` (the identity attributed to an action must equal the identity that actually authenticated the request). This binding is broken: [1](#0-0) 

`authenticate_api_client` (lines 48-61) only validates the bearer token via `ApiClient.authenticate(token)` and sets `@current_api_client`. `current_user` (lines 65-72) is computed independently from `request.headers['X-Shipit-User']`, looked up in the `users` table by lowercase login, with **no comparison to `current_api_client.creator`**. `require_permission!` (line 82-84) only calls `current_api_client.check_permissions!`, never touching `current_user`. So the two identities — "who is authorized" (`current_api_client`) and "who is attributed" (`current_user`) — are completely decoupled.

Downstream, several controllers use `current_user` purely for attribution while permission is enforced against `current_api_client`:
- `LocksController#create`/`#update` — `stack.lock(params.reason, current_user)` [2](#0-1) 
- `DeploysController#create` — `stack.trigger_deploy(commit, current_user, ...)` [3](#0-2) 
- `RollbacksController#create` — `active_task.abort!(aborted_by: current_user, ...)` / `deploy.trigger_rollback(current_user, ...)` [4](#0-3) 
- `TasksController#trigger`/`#abort` — `stack.trigger_task(params[:task_name], current_user, ...)` / `task.abort!(aborted_by: current_user)` [5](#0-4) 

Exploit flow: attacker holds a valid `ApiClient` token that grants only the specific permission it needs for its intended purpose (e.g. `lock:stack` or `deploy:stack` for an automation integration). Attacker sends `POST /api/stacks/:id/locks` (or `/deploys`, `/rollbacks`, task `trigger`/`abort`) with `Authorization: Basic <token>` and header `X-Shipit-User: <victim-admin-login>`. `identify_user` finds the existing `User` row for `victim-admin-login` and sets `current_user` to it. The lock/deploy/rollback/task record is created with `current_user` (the victim) recorded as the actor, even though the actual authenticated token belongs to the attacker's own `ApiClient`.

No existing guard prevents this: `require_permission!` never inspects `current_user`; `identify_user` performs no comparison to `current_api_client.creator`; there is no session involved in API auth to cross-check against.

### Impact Explanation
Any action attributed via `current_user` (stack locks, deploys, rollbacks, task triggers/aborts) can be stamped with an arbitrary existing user's identity chosen by the attacker, as long as the attacker's own token has permission to perform that operation. This forges accountability/audit trail for privileged actions (who locked/deployed/rolled back a stack), which can mislead incident response, bypass "who did this" accountability controls, and in environments relying on `current_user` for any authorization decisions downstream (e.g. notifications, webhooks, or UI trust) could be leveraged further. This is a genuine authentication/identity-binding bypass matching the "authentication bypass" / cross-tenant-attribution category, though it requires the attacker to already hold a token scoped for the specific write operation being spoofed — it does not grant privilege escalation beyond what the token already permits, only identity forgery for the recorded actor.

### Likelihood Explanation
Preconditions: attacker must already possess a valid `ApiClient` token with the permission needed for the target action (e.g. `lock:stack`, `deploy:stack`, `write:hook`), and a `User` record with the victim's login must exist. Given ApiClient tokens are typically issued per-integration and the header check has zero cost to exploit (a single custom header on any authenticated API call), likelihood is high once any such token is held.

### Recommendation
In `Shipit::Api::BaseController#identify_user`, do not trust `X-Shipit-User` unconditionally. Either remove header-based identity entirely and default `current_user` to `current_api_client.creator`, or require that the resolved user match `current_api_client.creator` (or an explicit allow-list of users the `ApiClient` is permitted to impersonate, if impersonation is an intended feature), rejecting/ignoring the header otherwise.

### Proof of Concept
Minitest plan (`test/controllers/shipit/api/locks_controller_test.rb` or similar existing test file):
```ruby
test "current_user can be spoofed via X-Shipit-User header" do
  attacker_client = shipit_api_clients(:some_client_with_lock_permission) # token owned by attacker's own ApiClient
  victim = shipit_users(:some_admin) # existing user with login e.g. "walro"

  authenticated_post api_stack_locks_path(stack), params: { reason: "forged" },
    headers: { 'X-Shipit-User' => victim.login }

  lock_event = stack.reload.audits.last # or whatever records `locked_by`
  assert_equal victim.id, lock_event.user_id
  refute_equal attacker_client.creator_id, lock_event.user_id
end
```
Assert on both sides of the binding: `current_api_client.creator_id` (the real authenticated identity, equal to `attacker_client.creator_id`) versus the recorded actor id on the created resource (equal to `victim.id`) — demonstrating the two diverge when they should be equal.

      def authenticate_api_client
        @current_api_client = if Shipit.disable_api_authentication
                                UnlimitedApiClient.new
                              else
                                BasicAuth.authenticate(request) do |*parts|
                                  token = parts.select(&:present?).join('--')
                                  ApiClient.authenticate(token)
                                end
                              end
        return if @current_api_client

        headers['WWW-Authenticate'] = 'Basic realm="Authentication token"'
        render(status: :unauthorized, json: { message: 'Bad credentials' })
      end

      attr_reader :current_api_client

      def current_user
        @current_user ||= identify_user || AnonymousUser.new
      end

      def identify_user
        user_login = request.headers['X-Shipit-User'].presence
        User.where('lower(login) = ?', user_login.downcase).first if user_login
      end

      def create
        commit = stack.commits.by_sha(params.sha) || param_error!(:sha, 'Unknown revision')
        param_error!(:force, "Can't rollback a locked stack") if !params.force && stack.locked?
        deploy = stack.deploys.find_by(until_commit: commit) || param_error!(:sha, 'Cant find associated deploy')
        rollback_env = stack.filter_rollback_envs(params.env)

        response = nil
        if !params.force && stack.active_task?
          param_error!(:force, "Can't rollback, deploy in progress")
        elsif stack.active_task?
          active_task = stack.active_task
          active_task.abort!(aborted_by: current_user, rollback_once_aborted_to: deploy, rollback_once_aborted: true)
          response = active_task
        else
          response = deploy.trigger_rollback(current_user, env: rollback_env, force: params.force, lock: params.lock)
        end

        render_resource(response, status: :accepted)
      end
