## Title
Webhook signature is verified against `repository.owner.login`, but events are processed against the unverified `repository.full_name`, allowing cross-organization event forgery in multi-app deployments - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
When Shipit is configured with multiple GitHub Apps (one per organization, as documented in `docs/setup.md` "Using Multiple Github Applications" and exercised by `test/dummy/config/secrets_double_github_app.yml`), `WebhooksController#verify_signature` picks the HMAC secret to validate a webhook against using `repository_owner`, derived from `params.dig('repository', 'owner', 'login')`. Once the signature check passes, the actual event handler (`Shipit::Webhooks::Handlers::Handler#repository_name`) resolves which `Repository`/`Stack` to act on using a *different* field of the same attacker-controlled JSON body: `payload.dig('repository', 'full_name')`. These two fields are never checked for consistency.

### Finding Description
`WebhooksController#verify_signature` selects the webhook secret like this: [1](#0-0) 

`repository_owner` is read straight from the JSON body: [2](#0-1) 

The secret itself is chosen per-organization via `Shipit.github(organization:)` / `github_app_config`, which is exactly the mechanism the multi-org config supports: [3](#0-2) 

Once `verified` is true, `create` dispatches the parsed body unmodified to every registered handler for the event: [4](#0-3) 

All handlers (`PushHandler`, `StatusHandler`, `CheckSuiteHandler`, `PullRequest::*Handler`) resolve the target `Repository`/`Stack` via the base class, using a **different** payload field, `repository.full_name`, which is never cross-checked against `repository.owner.login`: [5](#0-4) 

For example `PushHandler` triggers `stack.sync_github` for whichever stack matches `repository.full_name`: [6](#0-5) 

and `PullRequest::OpenedHandler` similarly resolves the repository via `params.repository.full_name` to auto-provision/act on review stacks: [7](#0-6) 

**Equality broken:** the binding the engine relies on is `organization that authenticated the signature == organization that owns the repository the handler writes to`. Because `repository_owner` (used to pick the HMAC secret) and `repository.full_name` (used to pick the stack that gets written to) are independent, attacker-controlled fields in the same JSON body, this equality is never enforced. An attacker who legitimately controls one configured GitHub App/organization (`OrgB`) — e.g., because they own a repo in `OrgB` and can trigger real webhook deliveries, thus obtaining a validly-signed envelope, or because they administer `OrgB`'s Shipit GitHub App and thus know `OrgB`'s `webhook_secret` — can send a POST to `/webhooks` where:
- `repository.owner.login = "OrgB"` (so `Shipit.github(organization: "OrgB")`'s secret is used and the HMAC check passes), and
- `repository.full_name = "OrgA/some-repo"` (a stack belonging to a wholly different, unrelated organization `OrgA` configured on the same Shipit instance).

The signature check succeeds because it was computed correctly for `OrgB`'s secret over the raw body, and the handler then acts on `OrgA`'s stack using the forged fields (`push`, `after` SHA, `status` sha/state, `check_suite`, or PR `opened` events), none of which are covered or bound by the verification of `repository.owner.login`.

### Impact Explanation
This breaks the deployment-trust binding "organization that authenticated the webhook == repository that is written," which is exactly the class of finding this scan targets. Concretely, an attacker who controls credentials for one configured organization can:
- Force `Stack#sync_github` to run for an unrelated organization's stack with an attacker-chosen `expected_head_sha` (`PushHandler`), affecting deploy/commit tracking state cross-organization.
- Inject fabricated commit statuses (`StatusHandler`) or check-suite refreshes (`CheckSuiteHandler`) against commits in another organization's stacks.
- Trigger unauthorized review-stack provisioning via forged `pull_request` "opened" events (`PullRequest::OpenedHandler`) against another organization's repository.

This is a cross-repository/cross-organization write triggered without any authorization over the target organization, matching the "Critical: cross-repository writes" bar in the rules, since Shipit's job/queue actions (sync, status writes, review-stack provisioning) execute against the victim organization's stacks as a direct consequence of the forged webhook.

### Likelihood Explanation
This only manifests when a Shipit instance is configured with multiple GitHub Apps for multiple organizations sharing one Shipit deployment/webhook endpoint — a configuration explicitly documented and supported (`docs/setup.md`, `TOP_LEVEL_GH_KEYS`, `github_app_config`). In that (documented, first-class) topology, any party holding legitimate credentials/webhook secret for just one of the organizations can exploit this without needing access to the victim organization at all — no privileged Shipit account, API token, or GitHub App private key for the victim org is required. Likelihood is therefore realistic in any multi-tenant Shipit deployment, which is a supported and documented use case, not a misconfiguration.

### Recommendation
In `WebhooksController#verify_signature`, after selecting `github_app` by `repository_owner`, verify that the same organization value is consistent with the repository the payload claims to act on (e.g., assert that `repository.full_name.split('/').first.casecmp(repository_owner) == 0`) before dispatching to handlers, and reject (422) on mismatch. Alternatively, resolve the signing organization strictly from `repository.full_name`'s owner segment rather than from a separately-read `repository.owner.login`/`organization.login` field, so there is a single source of truth for both signature verification and repository resolution.

### Proof of Concept
1. Deploy Shipit with `config/secrets.yml` configured for two organizations, e.g. `OrgA` (webhook_secret_A) and `OrgB` (webhook_secret_B), both installed on the same Shipit instance (per `docs/setup.md`, "Using Multiple Github Applications").
2. As an attacker who controls `OrgB`'s GitHub App configuration (or who can capture one legitimately-signed delivery from `OrgB`), craft a JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker_chosen_sha>",
  "repository": {
    "owner": { "login": "OrgB" },
    "full_name": "OrgA/victim-repo"
  }
}
```
3. Sign the raw body with `webhook_secret_B` using HMAC-SHA1, producing `X-Hub-Signature: sha1=<hmac>`.
4. POST to `/webhooks` with header `X-Github-Event: push` and the above body/signature.
5. `WebhooksController#verify_signature` computes `repository_owner = "OrgB"`, fetches `Shipit.github(organization: "OrgB")`, and successfully verifies the signature (it was signed with `webhook_secret_B`).
6. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("OrgA/victim-repo")` (from `repository.full_name`), matching stacks on `OrgA`, and calls `stack.sync_github(expected_head_sha: "<attacker_chosen_sha>")` — an action against `OrgA`'s stack that the attacker never had signing authority over.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
