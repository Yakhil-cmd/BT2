### Title
Cross-organization team-ID collision in `MembershipHandler#find_or_create_team!` allows forged membership escalation into `Shipit.github_teams` - ([File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`MembershipHandler#process` trusts a webhook-supplied `team.id` and `member.login` unconditionally, calling `Team#add_member` with no GitHub-side verification of real team membership. `Team.find_or_create_by!(github_id: params.team.id)` is looked up **only by the numeric `github_id`**, with no scoping to the organization that signed the webhook, so a legitimate multi-tenant webhook sender for one organization can add itself to a `Team` record belonging to a different, unrelated organization simply by supplying that team's known/guessed numeric `github_id`.

### Finding Description
The broken binding: `Team#members` after `add_member` should equal the set returned by GitHub's real Team Members API for that team's `github_id`, i.e. `Team.find(t).members.pluck(:login) == github.api.team_members(t.github_id).map(&:login)`. This binding is violated because `add_member` performs no verification at all: [1](#0-0) 

and `MembershipHandler#process` looks up the target `Team` purely by the numeric `team.id` from the payload, without checking that the signing organization actually owns that team: [2](#0-1) 

Signature verification (`WebhooksController#verify_signature`) is legitimately organization-scoped: it looks up the `GitHubApp`/secret for `repository_owner` (derived from `organization.login` in a membership payload) and HMAC-verifies against that organization's own `webhook_secret`: [3](#0-2) [4](#0-3) 

In a multi-org Shipit deployment, `Shipit.github(organization:)` resolves a distinct config (and distinct `webhook_secret`) per organization key in `secrets.github`: [5](#0-4) 

This means signature verification only proves the request came from *some* organization that is legitimately onboarded to this Shipit instance with its own known secret — it does **not** prove that the `team.id` in the payload actually belongs to that same organization. `Team.find_or_create_by!(github_id:)` has no `organization` predicate, so if an attacker administers (or is a member/webhook admin of) Org A, which is onboarded to the same multi-tenant Shipit instance, they can send a `membership`/`added` event signed with Org A's own secret but with `team.id` set to the `github_id` of an already-existing `Team` row belonging to Org B (e.g. a team referenced in `Shipit.github_teams` used for authorization). The handler finds Org B's existing `Team` record (because lookup ignores organization) and calls `team.add_member(attacker_user)`, granting membership with zero call to GitHub's Team Members API.

`User#authorized?` then treats this forged membership as legitimate: [6](#0-5)  and `force_github_authentication` grants full application access based on it: [7](#0-6) .

Existing guards (`verify_signature`, `ExplicitParameters` schema, `drop_unhandled_event`) validate payload *shape* and the *sender's own organization identity*, but none of them cross-check that `team.id` belongs to the organization identified by the signature. This is a real gap, root-caused in `app/models/shipit/team.rb#add_member` and `app/models/shipit/webhooks/handlers/membership_handler.rb#find_or_create_team!`.

### Impact Explanation
An attacker who has legitimate control of a webhook for any organization onboarded to a multi-tenant Shipit instance (their own org's webhook secret) can grant themselves membership in an arbitrary other organization's `Team` row, provided they can determine or guess that team's numeric GitHub `github_id` (these are sequential/enumerable integers, and some may already be visible via other Team-creating webhooks or API responses). If that team is part of `Shipit.github_teams`, this is escalation into the authorization set used by `User#authorized?`, granting full application access (viewing stack state, task streams, triggering deploys/rollbacks depending on further authorization checks) without any real GitHub team membership. This matches the "High: escalation into `Shipit.github_teams` authorization" impact category. It is repeatable per attacker-controlled webhook event and is not limited to a single team once the `github_id` is known.

### Likelihood Explanation
This requires the attacker to control (or be an admin of) at least one organization that is legitimately configured in Shipit's multi-tenant `secrets.github` (i.e., they know that organization's own `webhook_secret`) — this is a plausible scenario for shared/multi-tenant Shipit deployments serving multiple GitHub orgs, but does **not** apply to a single-org/single-GitHub-App Shipit deployment where `github_default_organization` is `nil`, since in that mode `Shipit.github(organization: repository_owner)` ignores the organization argument entirely and always verifies against one global secret (which the attacker still doesn't know) — see [8](#0-7) . Given that precondition (multi-tenant config with attacker controlling one onboarded org), the attack is cheap and fully repeatable: a single crafted HTTP POST per target team.

### Recommendation
In `Team.find_or_create_by!`, scope the lookup by both `github_id` AND `organization` (matching the webhook-signing organization), and reject/raise if an existing `Team` record with that `github_id` belongs to a different organization. Additionally, consider validating team membership against the GitHub API (`Shipit.github(organization:).api.team_member?`) before calling `add_member`, rather than trusting the webhook payload unconditionally.

### Proof of Concept
```ruby
# test/models/team_membership_cross_org_test.rb
test "membership webhook cannot add member to a team belonging to a different organization" do
  victim_team = Team.create!(organization: 'shopify', slug: 'developers', name: 'Developers', github_id: 999, api_url: 'https://x')
  attacker = User.create!(login: 'attacker', name: 'Attacker')

  payload = {
    'action' => 'added',
    'team' => { 'id' => 999, 'name' => 'Developers', 'slug' => 'developers', 'url' => 'https://x' },
    'organization' => { 'login' => 'attacker-org' }, # attacker's own onboarded org
    'member' => { 'login' => 'attacker' }
  }

  Shipit::Webhooks::Handlers::MembershipHandler.call(payload)

  refute victim_team.reload.members.include?(attacker),
    "attacker should not gain membership in shopify/developers via attacker-org's webhook"
end
```
Both sides of the binding: expected `victim_team.members` == GitHub API's real team-members list for `github_id: 999` (i.e., excludes `attacker`); actual, with the current code, `victim_team.members` includes `attacker` after the forged event, since `add_member` performs `members.append(member) unless members.include?(member)` with no external verification.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
