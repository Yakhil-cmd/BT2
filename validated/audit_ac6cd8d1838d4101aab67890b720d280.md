### Title
Cross-repository CI status forgery via unscoped commit lookup in `StatusHandler` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` looks up commits to attach a GitHub `status` event to using a global, repository-agnostic query (`Commit.where(sha: params.sha)`), while the webhook's HMAC signature is verified only against the secret of the *organization* that owns the repository named in the payload. Because no code ties the verified organization/repository to the `Commit` rows that actually get mutated, a webhook that is legitimately signed for repository/org **A** can create or update a CI status on a commit that belongs to an entirely different stack/repository **B**, as long as both commits happen to share the same SHA (trivially achievable via forks, since git commit hashes are content-addressed and identical across forks/mirrors of the same history).

### Finding Description
Webhook authenticity is established per-organization in `WebhooksController#verify_signature`, which derives the signing organization from the payload and calls `Shipit.github(organization: repository_owner).verify_webhook_signature(...)`: [1](#0-0) 

The base `Handler` class exposes a `stacks` helper that correctly scopes queries to the repository named in the payload: [2](#0-1) 

Other handlers such as `PushHandler` use this scoping properly: [3](#0-2) 

`StatusHandler`, however, bypasses this scoping entirely and queries the global `Commit` table directly by SHA, with no repository/stack filter at all: [4](#0-3) 

This breaks the binding "organization that authenticated == repository that is written": the signature check only proves the payload was legitimately signed by *some* organization's webhook secret for *its own* repository, but the actual database write (`commit.create_status_from_github!`) can land on any `Commit` record in the entire Shipit installation that happens to carry the same `sha`, regardless of which repository or organization it belongs to.

Git commit SHAs are content-addressed and independent of the remote URL/owner. Any user can fork a public repository that is already tracked as a Shipit stack under a different (victim) organization; the fork will contain identical commit objects with identical SHAs as long as the history is not rewritten. If the attacker also configures their own fork as a Shipit stack (using their own organization's GitHub App/webhook configuration — a normal, unprivileged operation for a repository/org they control), any `status` webhook fired for their own fork (signed with their own org's secret, so `verify_signature` legitimately passes) will be processed by `StatusHandler#process` against every `Commit` row sharing that SHA — including the identical commit tracked under the victim's stack in a different organization.

### Impact Explanation
This is a cross-repository/cross-organization write: an attacker fully controlling only their own (unrelated) organization's webhook feed can inject arbitrary CI status records (`state`, `context`, `description`, `target_url`) onto commits belonging to a victim's stack that they have no access to. Shipit gates deploy eligibility (`required_statuses`, `deployable_status?`, "green CI" checks feeding `Stack#next_commit_to_deploy`) on these `Status` rows attached to `Commit`. By forging a `success` status for a required context (e.g. `ci/build`) on a victim commit, the attacker can make an otherwise-blocked victim commit appear deployable, potentially triggering an unauthorized deploy (directly, or via continuous delivery) for a repository/organization the attacker has no legitimate access to. This satisfies the "cross-repository writes" / "unauthorized deploy" Critical impact category.

### Likelihood Explanation
The prerequisite — forking a public upstream repository that a victim organization already tracks in Shipit, and onboarding that fork as one's own Shipit stack — requires no privileged access to the victim's resources, only ordinary GitHub/Shipit usage of the attacker's own account/org. The SHA collision is not probabilistic; forks of the same history deterministically share identical commit SHAs for unmodified commits, making exploitation reliable rather than merely theoretical.

### Recommendation
Scope the commit lookup in `StatusHandler#process` to the repository identified in the webhook payload, mirroring how `PushHandler` uses `stacks` (derived from `payload.dig('repository', 'full_name')`), e.g.:

```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
end
```

This ensures a status update can only be applied to commits that belong to the repository the authenticated webhook actually originates from.

### Proof of Concept
1. Victim organization `victim-org` tracks `victim-org/app` as a Shipit stack; commit `abc123...` is undeployed and blocked pending a required `ci/build` status.
2. Attacker forks the same repository as `attacker-org/app` (identical git history, so the fork also contains commit `abc123...`), and adds it as a Shipit stack under `attacker-org`'s own GitHub App/webhook configuration.
3. Attacker triggers (or fabricates via their own CI/GitHub API access to their fork) a `status` webhook event for `attacker-org/app` with `sha: "abc123..."`, `state: "success"`, `context: "ci/build"`.
4. `WebhooksController#verify_signature` validates the signature against `attacker-org`'s legitimate webhook secret and passes.
5. `StatusHandler#process` executes `Commit.where(sha: "abc123...")`, which matches the identical commit under `victim-org/app`, and calls `create_status_from_github!`, writing a forged "success" `ci/build` status onto the victim's commit — satisfying the victim stack's required status and enabling deploy eligibility the attacker never had permission to affect.
