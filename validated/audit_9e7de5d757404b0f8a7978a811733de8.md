### Title
Inconsistent "good sequence" filtering between `dataFeedExists()` and `readDataFeedValue()` allows AA data-feed conditions to use non-final (temp-bad) unstable units - (File: data_feeds.js)

### Summary
`data_feeds.js` implements two parallel in-memory scanners over `storage.assocUnstableMessages` that AA/oscript code uses to evaluate data-feed conditions against not-yet-stable AA units: `readDataFeedValue()` (backing the `data_feed[...]` formula expression) and `dataFeedExists()` (backing the `in data feed` / `in_data_feed` boolean condition). One of the two filters excludes units whose `sequence` is not `'good'`; the other does not. This is the same bug class as the phpMyFAQ advisory: two sibling read paths over the same underlying data apply inconsistent visibility/validity filtering, so one path can return content (here, data-feed matches) that the other path correctly withholds.

### Finding Description
In `readDataFeedValue()`, the unstable-AA scan explicitly discards non-good units before considering their `data_feed` messages: [1](#0-0) 

```
for (var unit in storage.assocUnstableMessages) {
    var objUnit = storage.assocUnstableUnits[unit] || storage.assocStableUnits[unit];
    ...
    if (objUnit.sequence !== 'good')
        continue;
    if (objUnit.latest_included_mc_index < min_mci || objUnit.latest_included_mc_index > max_mci)
        continue;
    ...
```

In `dataFeedExists()`, the equivalent unstable-AA scan omits this check entirely: [2](#0-1) 

The loop only filters on `objUnit.bAA`, `latest_included_mc_index` range, and author address — it never checks `objUnit.sequence`. As a result, a unit that is currently marked `temp-bad` (a non-serial/conflicting unit that has not yet been finalized as `good` or `final-bad`) can still have its `data_feed` message payload matched by `dataFeedExists()`, while the same unit would correctly be excluded by `readDataFeedValue()`.

Both functions are reached from the oscript/AA formula evaluator: the `data_feed[...]` formula operator calls `readDataFeedValue()` with the AA context flag as the `unstable_opts` argument, and the `in_data_feed[...]` boolean formula operator calls `dataFeedExists()` with the same AA context flag as `bAA`, enabling the unstable-unit scan specifically during AA trigger/response evaluation: [3](#0-2) 

`dataFeedExists()` with `bAA=false` is also used by `definition.js` for the `'in data feed'` address-definition condition, but that call path is unaffected because it never enables the unstable-scan branch: [4](#0-3) 

The `sequence` field ('good' / 'temp-bad' / 'final-bad') marks non-serial/conflicting units and is precisely the mechanism the codebase uses elsewhere to keep AA logic deterministic before final stabilization (e.g. `readStableOutputs`/`readUnstableOutputsSentByAAs` in `aa_composer.js` and the attestation lookup in `formula/evaluation.js` both filter `sequence='good'`): [5](#0-4) [6](#0-5) 

Because `dataFeedExists()` skips this filter, `in_data_feed[...]` can evaluate `true` based on a data-feed message carried in a `temp-bad` unit — content that `data_feed[...]` would treat as non-existent.

### Impact Explanation
AA response computation must be fully deterministic across all full nodes evaluating the same trigger, because every node independently re-derives the AA's state changes and outputs and must agree on them. `sequence` classification of a not-yet-stable unit ('good' vs 'temp-bad') can transiently differ between nodes or resolve differently depending on propagation/validation order until the unit's mci stabilizes. If an `in_data_feed[...]` condition inside an AA definition (bool oracle gate, branching logic, guard condition, etc.) evaluates differently on different nodes because one node still regards the relevant data-feed-posting unit as `temp-bad` while the underlying data content is nonetheless picked up by `dataFeedExists()`, nodes can compute different AA responses (different bounce/success outcome, different balance/state changes, different output amounts) for the identical trigger. This is a node-disagreement-on-validity condition for AA-generated units, which can lead to consensus splits, AA fund mismanagement (loss/freezing depending on which branch executes), or units accepted as valid by some nodes and rejected by others.

### Likelihood Explanation
Exploitability requires only posting ordinary data-feed and (optionally) conflicting/double-spend units as an unprivileged oracle/poster and having an AA whose definition uses `in_data_feed[...]` to gate behavior on unstable AA data feeds (a documented, supported oscript feature, `bIncludeUnstableAAs`/`all_unstable` unstable-oracle pattern). No special network position or privileged role is needed — any AA author can write such a condition and any user can trigger it while a competing (non-serial) unit from the same oracle address is still unstable, which is a normal occurrence during periods of unstable/competing DAG growth.

### Recommendation
Add the same `objUnit.sequence !== 'good'` guard to the unstable-scan loop in `dataFeedExists()` (data_feeds.js, inside the `for (var unit in storage.assocUnstableMessages)` block) so it matches `readDataFeedValue()`. Alternatively, factor the two scans into a single shared helper (e.g. `getGoodUnstableAAUnits(min_mci, max_mci, arrAddresses)`) used by both `readDataFeedValue()` and `dataFeedExists()`, to prevent this class of drift in the future. Add regression tests that post a `temp-bad` (nonserial, conflicting) unstable AA data-feed unit and assert `in_data_feed[...]` returns the same result as `data_feed[...] == ifnone` for that unit.

### Proof of Concept
Conceptual reproduction (matching the reachable AA/oscript surface):
1. Deploy an AA whose definition contains a condition using `in_data_feed[[oracles=..., feed_name='x', feed_value=1]]` to branch behavior (e.g., pay out vs bounce).
2. From the oracle address, post two conflicting (double-spend/nonserial) units concurrently such that one becomes `sequence='temp-bad'` before stabilization; have the `temp-bad` unit carry a `data_feed` message `{x: 1}`.
3. Trigger the AA while the units are still unstable.
   - `dataFeedExists()` (used by `in_data_feed[...]`) will scan `storage.assocUnstableMessages` without filtering `sequence`, find the `temp-bad` unit's `data_feed` message, and return `true`.
   - `readDataFeedValue()` (used by `data_feed[...]`) filters out the same `temp-bad` unit and would not find the value.
4. On a node where the ordering of arrival caused the *other* conflicting unit to be `temp-bad` instead, the outcome of `in_data_feed[...]` for the trigger evaluated at the same mci can differ, producing divergent AA responses across nodes for an identical trigger — demonstrating the node-disagreement condition. (Exact numeric IDs/timing to force the `temp-bad` race deterministically would need to be worked out in a running testnet/AA dry-run environment; the code-level inconsistency itself is confirmed by direct comparison of the two functions.)
