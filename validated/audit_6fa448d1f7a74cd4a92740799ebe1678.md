### Title
Stack-scoped ApiClient can read CI status of any stack via CCMenuController, bypassing its stack scope binding - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::BaseController` enforces a binding between an `ApiClient`'s `stack_id` scope and the stacks it may touch by resolving the requested stack through a scoped collection: `stacks.from_param!(params[:stack_id])`, where `stacks` is restricted to `Stack.where(id: current_api_client.stack_id)` whenever the client is scoped. [1](#0-0) 

`CCMenuController` overrides this `stack` method to bypass the scoped collection entirely, resolving the stack directly from the global `Stack` relation: [2](#0-1) 

The controller's only authorization gate is `require_permission :read, :stack`, which merely checks that `read:stack` is in the client's `permissions` array via `ApiClient#check_permissions!` — it never compares the permission grant to `current_api_client.stack_id`: [3](#0-2) 

### Finding Description
This mirrors the report's bug class: a permission ("operator"/`read:stack`) is granted, but the check that ties it to a specific object (a specific `lock`/stack) is missing on one code path even though it exists elsewhere in the same trust model. Here, the binding that should hold is:

`current_api_client.stack_id == stack_id_being_served`

For every other API controller (e.g. `TasksController`, `LocksController`, `DeploysController`), this binding is enforced because they call the inherited `stack` method backed by the scoped `stacks` relation. `CCMenuController` redefines `stack` to use `Stack.from_param!(params[:stack_id])` directly, dropping the scoping filter. Consequently, a token that was only ever authorized (`stack_id` set) for Stack A can be replayed with a different `stack_id` param to read CI/build data for Stack B, C, ... any stack in the installation, as long as it carries `read:stack`.

The fixture `here_come_the_walrus` demonstrates that scoped, single-stack tokens are an intended and used pattern in this codebase (`stack: shipit`, `permissions: read:stack`): [4](#0-3) 

and its scoping is verified/relied upon elsewhere, e.g. in the regular stacks index endpoint: [5](#0-4) 

But `CCMenuControllerTest` never exercises the scoped-client case at all — it only authenticates with the unscoped `spy` client, so this scope bypass in `CCMenuController#stack` is not covered by tests. [6](#0-5) 

### Impact Explanation
An attacker holding a legitimately-issued, stack-scoped API token (e.g. one minted narrowly for a single stack's CI status badge, as `CCMenuUrlController` does) can enumerate and read build/deploy status, lock state, and lock reason for every other stack in the Shipit installation, none of which the token was ever authorized to touch. This is an unauthorized read of stack state across repository/stack boundaries using credentials that were deliberately scoped to prevent exactly that — matching the "High: unauthenticated/unauthorized read of stack state" impact class (the credential is authenticated but its authorization boundary is bypassed).

### Likelihood Explanation
High: any holder of a stack-scoped API client credential (a routine, documented artifact — see `CCMenuUrlController#client`) can trivially trigger this by substituting a different `stack_id` in the URL; no additional privileges, secrets, or races are required.

### Recommendation
Remove the `stack` override in `CCMenuController`, or reimplement it to resolve the stack through the scoped `stacks` collection (as `BaseController#stack` does) so that a client's `stack_id` scope is enforced consistently across all API controllers:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```

### Proof of Concept
1. `ApiClient` "here_come_the_walrus" exists with `stack: shipit`, `permissions: [read:stack]` (see fixtures) — a token scoped only to the "shipit" stack.
2. Authenticate as this client and request `GET /api/*stack_id/ccmenu` with `stack_id` set to a *different* stack (e.g. `shipit_canaries` or any other stack the client is not scoped to).
3. Because `CCMenuController#stack` calls `Stack.from_param!(params[:stack_id])` instead of the scoped `stacks.from_param!(...)`, the request succeeds with `200 OK` and returns that other stack's CCMenu XML (name, activity, lastBuildStatus, lock state), even though `current_api_client.stack_id` restricts this client to the "shipit" stack only — confirmed by contrast with `test/controllers/api/stacks_controller_test.rb:217-223`, which shows the same client is correctly restricted to one stack on the standard `stacks#index` endpoint but has no equivalent restriction test/enforcement for `CCMenuController`.
