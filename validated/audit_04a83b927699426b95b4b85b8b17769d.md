### Title
Cross-repository status forgery: `StatusHandler#process` matches commits globally by sha, ignoring the payload's repository - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` resolves target commits with `Commit.where(sha: params.sha)`, with no filter tying the lookup to the repository named in the webhook payload. Any GitHub org/repo that is a legitimate Shipit-connected tenant (and can therefore produce a signature that passes `verify_signature`) can send a `status` event whose `sha` collides with a commit belonging to a completely different stack/repository, and that unrelated commit will receive the forged status.

### Finding Description
The broken binding is: `commit.stack.repository.full_name == payload['repository']['full_name']` — this equality is asserted implicitly by the base `Handler` class (`stacks` helper at `app/models/shipit/webhooks/handlers/handler.rb:32-38` resolves `Repository.from_github_repo_name(repository_name)` from `payload.dig('repository', 'full_name')`), but `StatusHandler` never uses this helper.

Instead: [1](#0-0) 

```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```

This queries `Commit` across *all* stacks/repositories by `sha` alone. `sha` values are only 40-hex-char strings and short/ambiguous shas are already disambiguated elsewhere (`Commit.by_sha`), but nothing prevents two unrelated repositories under different tenants/stacks in the same Shipit instance from having identical commit shas (e.g., empty-tree commits, cherry-picked/rebased identical content, or an attacker deliberately crafting a commit with a colliding sha to a known victim sha via a fork/rewrite of history). Once matched, `commit.create_status_from_github!(params)` (delegating to `Status.replicate_from_github!`) is called with the state from the attacker's own payload for a commit that belongs to a stack the attacker's payload does not name.

`WebhooksController#verify_signature` (app/controllers/shipit/webhooks_controller.rb:24-49) only checks that the signature matches the GitHub App secret associated with `repository_owner` (`params.dig('repository','owner','login')`), i.e., it verifies that the *sender* controls the org named in the payload — it does not verify that the `sha` inside the payload actually belongs to that org's commit history. So an attacker who legitimately owns/administers a Shipit-connected repo (which they are permitted to do per the threat model — "emit webhooks from a repository they own") can pass signature verification for their own org while placing an arbitrary victim sha in the body.

Downstream, `Commit#create_status_from_github!` → `Status.replicate_from_github!` creates a `Status` row tied to the victim commit and the victim's `stack_id` is derived from `commit.stack_id` (`app/models/shipit/commit.rb:165-169`), so `Commit#deployable?` (`app/models/shipit/commit.rb:227-229`) and `UndeployedCommit#deploy_disallowed?` (`app/models/shipit/undeployed_commit.rb:39-41`, `!deployable? || !stack.deployable?`) flip based on this forged status, exposing a false "ready to deploy" state in the dashboard for the victim stack.

None of the existing guards catch this: `drop_unhandled_event` and `check_if_ping` are unrelated; `verify_signature` authenticates the *sender's org*, not the *sha's owning repository*; the `ExplicitParameters` schema on `StatusHandler` (`requires :sha, String; requires :state, String`) only validates types/presence, not repository ownership; and unlike every other handler that scopes work through `Handler#stacks` (bound to `payload.dig('repository','full_name')`), `StatusHandler` bypasses that scoping entirely.

### Impact Explanation
A record (a `Status`) is written for a commit/stack that never authenticated via the attacker's payload — this is a payload for one repository mutating another repository's commit/stack state, matching the "Critical" impact category (an unrelated stack's deploy-readiness state is falsified). The direct consequence is that an operator viewing the victim stack's dashboard sees a false-green "deployable" status and can be induced to trigger an unauthorized deploy of the victim's commit. This is repeatable against any stack/commit sha the attacker can predict or collide with, across tenant boundaries in a shared Shipit instance.

### Likelihood Explanation
Preconditions: the attacker needs at least one repository legitimately connected to the same Shipit instance (satisfying `verify_signature`'s per-org secret check) and needs a commit sha that collides with a targeted victim commit sha. Exact 40-char SHA-1 collision is not practically producible by an attacker, but the code path itself provides zero protection independent of collision difficulty — if the victim stack ever contains a commit whose sha an attacker-controlled repo can also produce (e.g., via cherry-pick, syncing/forking shared upstream history, empty/trivial commits, or shared vendored commits between multiple stacks on the same Shipit instance, a known real-world occurrence), the exploit fires with a single webhook POST. Given multi-tenant self-hosted Shipit deployments frequently host many related/forked repositories, sha collisions across stacks are plausible, not merely theoretical, making this a real, low-cost, repeatable exploitation path for any tenant with a connected repository.

### Recommendation
Scope `StatusHandler#process` the same way other handlers are scoped: resolve the commit only within stacks belonging to the repository named in the payload (using the existing `stacks` helper / `Repository.from_github_repo_name(repository_name)`), e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` or equivalently join `Commit` through `Stack` filtered by the payload's repository, instead of `Commit.where(sha: params.sha)` unscoped by repository.

### Proof of Concept
minitest plan (webhooks_controller_test.rb style, no live GitHub, `GithubHook.any_instance.stubs(:verify_signature).returns(true)` per existing pattern):

1. Create `stack_a` (victim) with repository `victim/repo` and a commit `commit_a` with `sha: "deadbeef...".` Assert baseline: `UndeployedCommit.new(commit_a, index: 0).deploy_disallowed?` is `true` (e.g., commit has a pending/failing status) — left side of binding: `commit_a.stack.repository.full_name == "victim/repo"`.
2. Create `stack_b` (attacker-controlled) with repository `attacker/repo`, no commit with this sha required — only the payload matters.
3. POST a `status` webhook whose JSON body has `repository.full_name = "attacker/repo"` (right side of binding) but `sha = commit_a.sha` and `state: "success"`.
4. Assert `commit_a.statuses.count` increased by 1 and `commit_a.reload.state == "success"`.
5. Assert `UndeployedCommit.new(commit_a.reload, index: 0).deploy_disallowed?` is now `false`, proving the binding `commit_a.stack.repository.full_name == payload.repository.full_name` was violated (`"victim/repo" != "attacker/repo"`) yet the forged status was still applied to `commit_a`.
