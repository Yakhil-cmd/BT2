### Title
Stale delegate grants re-arm when a position NFT returns to its original owner, restoring an untokenized "admin token" after deactivation - (File: contracts/controller/src/storage/account.rs)

### Summary
The external report (CVE-2026-25700) describes a security grant that stays valid after the grantor's status changes. XOXNO Lending has the same shape in its delegate system: a `DelegateGrant` is keyed by `account_id` and stamped with `granted_by`, not with any transfer epoch. Transferring the position NFT deactivates the grant, but the grant is left in storage and silently re-activates if the NFT ever returns to the original owner — provided no intervening owner happened to call `add_delegate` or `remove_delegate` on that account.

### Finding Description
`get_delegates` returns the stored delegate list only when `grant.granted_by == current_owner` (contracts/controller/src/storage/account.rs:176-181). Nothing deletes the grant on NFT transfer — the NFT contract has no hook into the controller, and `get_delegates` merely filters. `is_owner_or_delegate` then authorizes any registered active position manager appearing in that list to act on the account (contracts/controller/src/account.rs:115-140), and delegates "can borrow/withdraw to their chosen recipient within account gates" (docs/explanation/threat-model.md:86-87).

The revocation asymmetry: `remove_delegate` explicitly deletes a stale grant owned by a *different* `granted_by` precisely "preventing those grants from reactivating if the NFT returns to their original owner" (storage/account.rs:224-238, and the test `remove_delegate_purges_stale_grant_preventing_resurrection`). But this purge only runs if an intervening owner bothers to call `remove_delegate` (or overwrites via `add_delegate`). If the interim owner never touches delegates — the common case for a buyer who just holds or flips the NFT — the original owner's grant survives intact in `ControllerKey::Delegates(account_id)` and re-arms the moment `owner_of` again returns `granted_by`.

This mirrors the advisory exactly: the "token" (delegation) was effectively deactivated by the ownership change, but was never invalidated, so it resumes working without any fresh authorization from anyone.

### Impact Explanation
Theft of user funds (Medium severity).

Attack path for a registered position manager `M`:
1. Alice grants `M` as delegate on her funded account, e.g. as part of a managed-strategy arrangement that later ends socially but is never cleaned up because Alice sells/transfers the position NFT to Bob.
2. Bob holds or trades the NFT. He never calls `add_delegate`/`remove_delegate`, so Alice's `DelegateGrant { granted_by: Alice, delegates: [M] }` stays in storage — inactive while Bob owns it.
3. The NFT returns to Alice — she buys back her own account NFT, an OTC deal unwinds, or the position is transferred back for any reason. No delegate write occurs.
4. `M`'s grant is live again (`granted_by == Alice`). `M` calls `borrow(..., to: M)` or `withdraw(..., to: M)` on the account, extracting collateral value up to the LTV/position gates and leaving Alice with the debt.

No re-authorization is ever requested from Alice; the dormant grant is indistinguishable from a fresh one. The controller's own code comments acknowledge resurrection is a hazard worth preventing, but the prevention is opt-in by the intervening owner rather than systematic.

### Likelihood Explanation
Medium-low but credible: it requires (a) a pre-existing grant from the returning owner, (b) at least one ownership round-trip with no delegate writes by intervening owners, and (c) an active position-manager registration for the delegate. Position NFTs are transferable by design (`transfer`, `transfer_from`, `approve`), and round-trips are realistic via marketplaces, custody changes, or unwind of a sale. Interim owners have no on-chain prompt or UI obligation to scrub delegates, and the grant is invisible to them unless they inspect `ControllerKey::Delegates` directly.

### Recommendation
Invalidate delegate grants on any ownership change, not only on explicit `remove_delegate`. Options:
- Stamp grants with a monotonically increasing "ownership epoch" or the NFT transfer count (or `granted_by` plus a ledger-sequence/transfer nonce recorded at grant time), and treat a mismatched epoch as no grant.
- Alternatively, have the controller expose a permissionless `purge_delegates(account_id)` that any caller can invoke when `granted_by != owner_of(account_id)`, replicating the purge inside `remove_delegate` without requiring owner auth — so keepers can clean stale grants before the NFT round-trips.
- Documented minimum: make `transfer`/`transfer_from` callers' risk explicit that delegate state survives.

```text
// Sequence (conceptual, matches test-harness style in
// tests/test-harness/tests/controller/position_nft.rs):

1. t.supply(ALICE, "USDC", 100_000.0);              // funded account
2. t.enable_delegate(ALICE, "M", account_id);       // DelegateGrant{granted_by:ALICE,[M]}
3. t.nft_transfer(ALICE, BOB, account_id);          // grant dormant, NOT deleted
4. // BOB never calls add_delegate / remove_delegate
5. t.nft_transfer(BOB, ALICE, account_id);          // NFT returns to granted_by
6. t.borrow_as_to("M", account_id, "USDC", X, "M"); // SUCCEEDS:
   //   is_owner_or_delegate: M != owner, but
   //   get_position_manager(M).is_active &&
   //   get_delegates(id, ALICE).contains(M)  // grant.granted_by == ALICE again
// M has withdrawn/borrowed account value to itself with no fresh Alice auth.
```

Root cause lines: `get_delegates` filters only on `granted_by == owner` with no epoch check (contracts/controller/src/storage/account.rs:176-181); the only purge path is the optional owner-initiated `remove_delegate`/`add_delegate` (storage/account.rs:226-247, account.rs:242-275); authority is granted via `is_owner_or_delegate` (contracts/controller/src/account.rs:115-127).
