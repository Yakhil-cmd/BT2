### Title
Unauthenticated crash via undefined `payload` dereference on non-inline `temp_data` messages - ([File: storage.js])

### Summary
An unprivileged unit poster can craft a unit containing a `temp_data` message with `payload_location` set to `"none"` (i.e. no `payload` field at all). Unit-level validation only inspects message-specific payload contents (including the `temp_data`-specific checks) when `payload_location === "inline"`; for any other location it just validates the `payload_hash` format and skips to the next message. This lets a syntactically valid, non-inline `temp_data` message with no `payload` object become part of a permanently stable unit. Two downstream code paths that only run for messages tagged `app === "temp_data"` unconditionally execute `delete m.payload.data`, assuming `payload` exists. When `payload` is `undefined`, this throws an uncaught `TypeError`, analogous to the NULL-pointer dereference in the reference CVE (an operation missing a defensive existence check on a caller-influenced object being blindly followed/deleted).

### Finding Description
1. In the per-message structural validation loop, non-inline messages are explicitly allowed to omit `payload`: [1](#0-0) 
Because this loop `continue`s for `payload_location !== "inline"`, the `temp_data`-specific structural checks (which would normally require `data`/`data_length`/`data_hash`) are never applied when the message is non-inline: [2](#0-1) 
So a unit with a message `{ app: "temp_data", payload_location: "none", payload_hash: "<valid base64 hash>" }` and no `payload` field at all passes full unit validation and can become stable.

2. `storage.purgeTempData()`, run periodically by every full node via `setInterval` (hourly) and also opportunistically on devnet time-leaps, iterates all messages of units crossing the purge timeout and blindly does `delete m.payload.data` for any `app === "temp_data"` message, without checking that `payload` exists: [3](#0-2) [4](#0-3) 
`delete undefined.data` throws `TypeError: Cannot convert undefined or null to object`. `purgeTempData` is an `async function` invoked from `setInterval`/`process.nextTick` with no surrounding `try/catch`, so the exception becomes an unhandled promise rejection, crashing the Node.js process on every full node that has ingested the crafted unit once it becomes stable and old enough to be purged.

3. Independently, the oscript/formula `unit[...]` selector performs the identical unchecked delete when any AA evaluates a reference to the crafted unit: [5](#0-4) 
An AA trigger sender can cause any AA whose code contains `unit['<hash>']...` (a supported, documented oscript feature for reading arbitrary stable units) to evaluate against the attacker's crafted unit, crashing AA evaluation for every node computing that AA's response.

### Impact Explanation
Both paths are unauthenticated-process crashes reachable purely from data an ordinary user can get into the DAG (post a normal unit with a `temp_data` message that omits `payload`). This matches the "node unable to confirm new units" / general node-availability criteria: the periodic `purgeTempData` crash affects every full node in the network once the malicious unit stabilizes and ages past `TEMP_DATA_PURGE_TIMEOUT`, and the AA-evaluation crash affects every node computing a response for any AA that reads that unit via `unit[...]`. A process crash (uncaught exception) halts validation/consensus participation for the affected node(s), directly impacting availability, analogous to the referenced kernel NULL-pointer dereference which also caused system crash from an unprivileged path (bounded by `CAP_SYS_ADMIN` there; here bounded only by being able to post a unit).

### Likelihood Explanation
High. No special privileges are needed — just the ability to post a well-formed unit with a `temp_data` message using `payload_location: "none"` (or `"uri"`) and a valid-format `payload_hash`, omitting `payload`. The unit only needs to become stable (normal network operation) to trigger the `purgeTempData` crash on every node after the timeout, or an attacker can immediately craft/trigger an AA that references the unit via `unit['<hash>']` to force the crash sooner.

### Recommendation
- In `storage.js` `purgeTempData()`, guard the delete: only run `delete m.payload.data` when `m.payload` is a non-null object, and treat/report units where a `temp_data` message lacks a `payload` object as anomalous (they should not exist for `payload_location==="none"`/`"uri"` in the first place).
- In `formula/evaluation.js`'s `unit` selector, add the same `m.payload && delete m.payload.data` guard before dereferencing.
- More fundamentally, restrict `payload_location` for `app === "temp_data"` messages to `"inline"` only during validation (temp data by design must be inline to be purged later), rejecting units that declare `temp_data` with `"none"`/`"uri"` locations, closing the root cause rather than only patching the two call sites.
- Wrap `purgeTempData()` invocations with `try/catch`/`.catch()` so a future unforeseen edge case cannot crash the whole process.

### Proof of Concept
1. Compose and broadcast a unit containing a message:
```json
{
  "app": "temp_data",
  "payload_location": "none",
  "payload_hash": "<valid 44-char base64 hash format>"
}
```
with no `payload` field. This passes `validate()` because the early loop (`validation.js:220-233`) only requires `payload` to be absent when `payload_location !== "inline"`, and the `temp_data`-specific checks (`validation.js:1966-2001`) are never reached.
2. Wait for the unit to stabilize and age past `constants.TEMP_DATA_PURGE_TIMEOUT`. On the next hourly `purgeTempData()` run (`storage.js:2548`), the node throws `TypeError: Cannot convert undefined or null to object` inside `storage.js:1109`, crashing the process.
3. Alternatively, deploy/trigger any AA whose oscript evaluates `unit['<hash_of_crafted_unit>']...`; when a trigger causes the AA to evaluate that expression, `formula/evaluation.js:1614` throws the same TypeError, crashing AA-response computation on the evaluating node.
