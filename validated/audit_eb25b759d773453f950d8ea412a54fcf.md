### Title
Unbounded custom-asset dust inputs let an attacker permanently DOS an AA's ability to pay out that asset - (File: aa_composer.js)

### Summary
`aa_composer.js`'s `completePaymentPayload()` picks up *all* unspent outputs of a custom (non-base) asset held by a triggered AA when composing a payment response, with no floor on output size and no cap on the number of inputs collected before checking the total against `MAX_INPUTS_PER_PAYMENT_MESSAGE`. An attacker can pre-fund an AA's address with many dust outputs of an asset the AA is expected to pay out (e.g., its own token), so that any future response that pays this asset (including "send-all" responses) is forced to consume more than `constants.MAX_INPUTS_PER_PAYMENT_MESSAGE` (128) inputs, producing an invalid payment message that will always fail validation. This mirrors the reported `VotingEscrow` bug class: an unprivileged actor pushes entries into a bounded resource that belongs to the victim (there, the delegate array of a user; here, the UTXO set of an AA address), permanently blocking the victim's (the AA's) own future legitimate operation.

### Finding Description
When an AA composes a payment message for a non-base asset, `readStableOutputs`/`readUnstableOutputsSentByAAs` select unspent outputs of that asset belonging to the AA with **no minimum-amount filter**, unlike the base-byte case which explicitly excludes outputs smaller than `FULL_TRANSFER_INPUT_SIZE` ("byte outputs less than 60 bytes ... are ignored to prevent dust attack") [1](#0-0) . `iterateUnspentOutputs` then unconditionally pushes every returned row into `payload.inputs` and keeps accumulating until the accrued amount satisfies the target, with no check against `MAX_INPUTS_PER_PAYMENT_MESSAGE` during collection [2](#0-1) .

Separately, `inputs.js`'s own coin-picking logic for user wallets explicitly reserves against this by limiting the SQL result set to `constants.MAX_INPUTS_PER_PAYMENT_MESSAGE-2` [3](#0-2) , showing the codebase is aware that unlimited input accumulation is dangerous — but the AA response composer path for custom assets has no equivalent limit.

Because units are ultimately checked against `constants.MAX_INPUTS_PER_PAYMENT_MESSAGE = 128` during validation of the payment message [4](#0-3) , if an attacker sends the AA's address hundreds of tiny-amount outputs of the target asset (there is no size floor to filter them out, unlike bytes), any subsequent AA response that must move that asset (particularly a "send-all" response, a common pattern for returning balances) is forced to include all these dust inputs, exceeding the 128-input cap and causing the generated payment message to be invalid.

### Impact Explanation
This is a griefing/DOS vulnerability against the AA and its legitimate users: once the dust is deposited, every trigger that causes the AA to attempt to pay out the polluted asset produces an oversized, invalid payment message. Since the AA cannot manually consolidate its own dust inputs (it has no code path to selectively merge outputs, and the same unbounded-collection bug would recur on any attempted consolidation payment), the asset-handling logic of the AA can become permanently unable to send funds in that asset, freezing user funds routed through the AA and disrupting protocol operation — a concrete AA fund freezing scenario, analogous to the reported "unable to add more delegates" DOS.

### Likelihood Explanation
Likelihood is high for any AA that issues or manages a custom, transferable asset and accepts unsolicited payments to its own address in that asset (a very common AA pattern). Sending payment outputs to an arbitrary address, including an AA address, requires no special privilege — any unit poster can trigger a payment message with many tiny outputs targeting the AA. No cooperation from the AA operator or victim is required.

### Recommendation
Apply the same anti-dust floor already used for base-byte outputs to custom-asset outputs in `readStableOutputs`/`readUnstableOutputsSentByAAs` (e.g., ignore asset outputs below some minimal economically meaningful amount, or cap it relative to the AA's typical payout), and/or enforce a hard limit on the number of inputs collected in `iterateUnspentOutputs` equal to `constants.MAX_INPUTS_PER_PAYMENT_MESSAGE - reserve`, aborting/splitting into multiple payment messages or failing gracefully rather than producing an unconditionally invalid oversized message.

### Proof of Concept
Conceptual PoC (cannot be executed without the wider AA/asset test harness, but the mechanism is directly traceable in code):
1. Define an AA that owns/manages a custom transferable asset `X` and has response logic that pays out `X` from its own balance (including a "send-all" style response).
2. As an attacker, send > 130 payment units, each transferring 1 unit of asset `X` to the AA's address (no minimum-amount filtering applies to non-base assets per `aa_composer.js:1140-1154`).
3. Trigger the AA in a way that causes it to send/return asset `X`.
4. Observe that `completePaymentPayload` in `aa_composer.js` accumulates all of these dust inputs via `iterateUnspentOutputs` (no cap), producing a payment message with `inputs.length > constants.MAX_INPUTS_PER_PAYMENT_MESSAGE`, which will fail unit validation, causing the AA response to bounce or fail on every future attempt to pay asset `X`, permanently denying the AA's ability to distribute that asset.
