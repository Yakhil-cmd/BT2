### Title
CCMenu API client authorizes generic `read:stack` but reads any stack the token is pointed at - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::CCMenuController#stack` bypasses the stack-scoping used by every other API endpoint, letting an unscoped-but-authenticated `read:stack` token retrieve the CI/CD status ("deploy output") of any stack in the installation, not only the stack the token was minted for.

### Finding Description
Every other controller inheriting from `Shipit::Api::BaseController` resolves the target stack through the scoped helper: [1](#0-0) 
`stacks` restricts the queryable set to `current_api_client.stack_id` when the `ApiClient` is scoped to one, and `stack` looks the requested `params[:stack_id]` up only inside that restricted set — this is the binding: **stack a token authorizes == stack it can touch**.

`CCMenuController` overrides `stack` and drops that scoping entirely: [2](#0-1) 
It only enforces `require_permission :read, :stack`, which is nothing more than a check that the permissions array on the `ApiClient` record contains the string `read:stack`: [3](#0-2) 
`check_permissions!` never compares `current_api_client.stack_id` to the requested stack. So the permission check ("authorized for `read:stack`") is decoupled from the actual resource acted upon ("stack whose deploy output is rendered"), which is exactly the deployment-trust binding break the report class targets: `stack a token authorises != stack it touches`.

This is made concretely exploitable because the token minted for the CCMenu use case is created **without any `stack_id`** at all: [4](#0-3) 
The URL embeds a specific `stack_id` in the query string, but the token itself (`client.authentication_token`) carries no stack restriction — the `ApiClient` row has `stack_id: nil`. Anyone in possession of one CCMenu URL/token (these URLs are handed out per-stack for embedding in CI dashboards, badges, IDE plugins, etc., and are not treated as secret in the same way as a full API credential) can replay the token against `api/stacks/:stack_id/ccmenu` for **any** `stack_id` in the Shipit instance and receive that other stack's latest deploy/rollback status, lock state, and build result.

### Impact Explanation
This satisfies the High-severity criterion "unauthenticated read of stack state, task streams or deploy output": a credential legitimately obtained for stack A's CCMenu badge can be used to read stack B's deploy status without ever being granted access to stack B, crossing a repository/stack authorization boundary using a token that was never scoped to that resource.

### Likelihood Explanation
CCMenu URLs are designed to be embedded in third-party tooling (CI status widgets, IDE plugins) and are treated as low-sensitivity, shareable links rather than full authentication secrets, increasing the chance one leaks or is intercepted. Once obtained, exploitation requires only changing the `stack_id` path segment in an HTTP GET request — no privilege escalation, no additional secrets, and no interaction with the victim stack owner is needed.

### Recommendation
Make `CCMenuController#stack` honor the same scoping as `BaseController#stack`/`stacks` (i.e., reuse `stacks.from_param!(params[:stack_id])` instead of `Stack.from_param!`), and/or always create the CCMenu `ApiClient` with `stack_id: stack.id` in `CCMenuUrlController#client` so the token is cryptographically bound to a single stack from creation, matching the "stack a token authorises" to "stack it touches" invariant enforced elsewhere in the API.

### Proof of Concept
1. As an authenticated Shipit user with access only to `stack-A`, visit `stack-A`'s page so `CCMenuUrlController#fetch` mints (or reuses) a `read:stack`-only `ApiClient` (no `stack_id`) and returns a URL such as:
   `https://shipit.example.com/api/stacks/org/stack-A/ccmenu.xml?token=<TOKEN>` [5](#0-4) 
2. Replay the same `<TOKEN>` against a different, unauthorized stack:
   `GET /api/stacks/other-org/private-stack/ccmenu.xml?token=<TOKEN>`
3. `CCMenuController#authenticate_api_client` authenticates the token successfully, `require_permission :read, :stack` passes because the token's permissions array contains `read:stack`, and `stack` resolves `private-stack` directly via `Stack.from_param!` with no ownership check: [6](#0-5) 
4. The response renders `private-stack`'s latest deploy/rollback status, `lock` state and `NoDeploy` fallback — data the requester was never authorized to view.
