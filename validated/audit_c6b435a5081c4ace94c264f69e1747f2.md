## Answer

The external Notional finding hinges on one invariant: a party with signing/authorization power over a value can leave an unchecked field free, so the *content that actually executes* diverges from the content that was implicitly agreed to be valid. The Aptos-native analog I found is in the multisig transaction admission path, where the payload that owners *approved* is not guaranteed to be the payload that actually gets *executed*.

### Title
Multisig transaction execution can diverge from the quorum-approved payload when `abort_if_multisig_payload_mismatch` is disabled - (File: `aptos-move/framework/aptos-framework/sources/multisig_account.move`)

### Summary
`validate_multisig_transaction` (the VM prologue for multisig transactions) only checks the executing owner's supplied `payload` against on-chain state in two situations: (1) when the transaction was created via `create_transaction_with_hash` (only a hash is stored) or (2) when the `abort_if_multisig_payload_mismatch_enabled` feature is turned on and a full payload was stored via `create_transaction`. If a transaction was created with `create_transaction` (full payload, no hash) and the feature flag is off, the payload comparison is completely skipped, so the payload actually submitted at execution time is never bound to what the multisig owners voted on.

### Finding Description
`create_transaction` stores the full approved payload with `payload_hash = None`: [1](#0-0) 

`validate_multisig_transaction`, invoked from the VM as the multisig prologue, only enforces a match between the executor-supplied `payload` and on-chain data under two conditions: [2](#0-1) 

The `payload_hash` branch only fires when the transaction was created with `create_transaction_with_hash`. The second branch — comparing the executor-supplied `payload` against the full `transaction.payload` stored by `create_transaction` — is gated behind `features::abort_if_multisig_payload_mismatch_enabled()`. If that feature is disabled, an owner with enough approvals can call the multisig execute entry point with a `payload`/`executable` that is *different* from the one the other owners voted `approve` on, and the prologue will not reject it.

The actual entry-function/script executed is derived from the caller-supplied `TransactionExecutableRef` and passed into `get_next_transaction_payload` on the Move side and consumed in the VM's `execute_multisig_transaction`: [3](#0-2) 

The same conditional gate is mirrored in the Rust-side prologue call that invokes `validate_multisig_transaction`: [4](#0-3) 

This is the same admission-boundary flaw class as the Notional bug: quorum approval (the analog of "maker signs the order") is supposed to bind a specific payload (the analog of "amount transferred"), but a discretionary/optional field (the executable payload) is left unvalidated unless a separate feature toggle is active, allowing the party executing the transaction to substitute a different payload than was approved.

### Impact Explanation
If reached with the feature disabled, any owner who can gather the approval quorum (or who is the last approver / sole owner in a 1-of-N setup) can execute an entry function/script that was never actually voted on by the other owners, while the on-chain vote record and events (`TransactionExecutionSucceeded`) still reference the sequence number as if the approved payload ran. This breaks the fundamental multisig invariant that the "approval set" binds to a specific payload — the multisig account can be made to sign/execute an attacker-chosen call (e.g., transferring funds, rotating keys, adding a malicious owner) that differs from what was reviewed and approved, which is a high/critical-impact authorization bypass for any multisig relying on `create_transaction` (full on-chain payload, not hash-only) in an environment where `abort_if_multisig_payload_mismatch_enabled` is not turned on.

### Likelihood Explanation
Likelihood depends entirely on whether `abort_if_multisig_payload_mismatch_enabled` is active in the target deployment. I was not able to confirm within the available tool budget whether this feature flag defaults to enabled on mainnet/testnet, or whether it is still in a rollout/opt-in state; this is a materially important open question that determines whether this is presently exploitable or a defense-in-depth gap already closed by the existing feature toggle. The mere existence of the flag as *optional* rather than a hard-coded, unconditional check means that any fork, testnet, private deployment, or state prior to flag activation is exposed, and there is no compile-time or protocol-level guarantee it will always be on.

### Recommendation
Make the payload-match assertion in `validate_multisig_transaction` unconditional (remove the `features::abort_if_multisig_payload_mismatch_enabled()` gate) so that whenever `transaction.payload.is_some()`, the payload supplied at execution time must always equal the payload approved at creation time, regardless of feature-flag state. If backward compatibility requires a rollout window, ensure the flag is enabled and locked/deprecated before any multisig using the affected creation path can be exploited.

### Proof of Concept
1. Owner A calls `create_transaction(owner_A, multisig_addr, payload_X)` (entry function transferring funds to A), storing `payload = Some(payload_X)`, `payload_hash = None`.
2. Owners B, C vote `approve_transaction` for that sequence number based on reviewing `payload_X`.
3. Once quorum is met, instead of submitting `payload_X`, owner A submits a transaction whose `TransactionExecutableRef` encodes a different entry function `payload_Y` (e.g., transferring funds to A's own separate address, or rotating multisig ownership).
4. In an environment where `abort_if_multisig_payload_mismatch_enabled` is disabled, `validate_multisig_transaction`'s payload-match branch is skipped entirely (`features::abort_if_multisig_payload_mismatch_enabled()` short-circuits to false), so no assertion fires.
5. `execute_multisig_transaction` in `aptos_vm.rs` proceeds to execute `payload_Y` under the multisig account's authority, even though only `payload_X` was ever approved by quorum. [5](#0-4) [6](#0-5)

/// Run the prologue for a multisig transaction. This needs to verify that:
/// 1. The multisig tx exists
/// 2. It has received enough approvals to meet the signature threshold of the multisig account
/// 3. If only the payload hash was stored on chain, the provided payload in execution should
/// match that hash.
pub(crate) fn run_multisig_prologue(
    session: &mut SessionExt<impl AptosMoveResolver>,
    module_storage: &impl ModuleStorage,
    txn_data: &TransactionMetadata,
    executable: TransactionExecutableRef,
    multisig_address: AccountAddress,
    features: &Features,
    log_context: &AdapterLogSchema,
    traversal_context: &mut TraversalContext,
) -> Result<(), VMStatus> {
    let unreachable_error = VMStatus::error(StatusCode::UNREACHABLE, None);
    // Note[Orderless]: Earlier the `provided_payload` was being calculated as bcs::to_bytes(MultisigTransactionPayload::EntryFunction(entry_function)).
    // So, converting the executable to this format.
    let provided_payload = match executable {
        TransactionExecutableRef::EntryFunction(entry_function) => bcs::to_bytes(
            &MultisigTransactionPayload::EntryFunction(entry_function.clone()),
        )
        .map_err(|_| unreachable_error.clone())?,
        TransactionExecutableRef::Empty => {
            if features.is_abort_if_multisig_payload_mismatch_enabled() {
                vec![]
            } else {
                bcs::to_bytes::<Vec<u8>>(&vec![]).map_err(|_| unreachable_error.clone())?
            }
        },
        TransactionExecutableRef::Script(script) => {
            if !features.is_multisig_script_enabled() {
                return Err(VMStatus::error(
                    StatusCode::FEATURE_UNDER_GATING,
                    Some("Multisig script payload is not enabled".to_string()),
                ));
            }
            bcs::to_bytes(&MultisigTransactionPayload::Script(script.clone()))
                .map_err(|_| unreachable_error.clone())?
        },
        TransactionExecutableRef::Encrypted => {
            return Err(VMStatus::error(
                StatusCode::FEATURE_UNDER_GATING,
                Some("Encrypted payload not supported for multisig transactions".to_string()),
            ));
        },
    };
