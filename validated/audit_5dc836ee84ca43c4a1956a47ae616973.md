### Title
Cross-repository status injection via unscoped `Commit.where(sha:)` in `StatusHandler#process` amplified by `blocking_statuses` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits globally by SHA with no repository/stack scoping, unlike sibling handlers (`PushHandler`, `CheckSuiteHandler`) which scope through the `stacks` helper derived from the payload's `repository.full_name`. Because `WebhooksController#verify_signature` only validates that the HMAC signature matches the secret for the organization named in the payload (`repository.owner.login`), an attacker who owns/controls any repository can send a fully-authenticated `status` webhook whose `sha` matches a commit that actually belongs to a completely different, victim repository/stack, and inject a status onto it.

### Finding Description
The broken binding: the handler should enforce `commit.stack.repository.full_name == payload.dig('repository', 'full_name')`, but no such check exists.

Trace:
1. `Shipit::WebhooksController#create` dispatches the raw JSON body to `Shipit::Webhooks.for_event('status')`, i.e. `StatusHandler.call(params)` [1](#0-0) .
2. `verify_signature` authenticates the request only against `Shipit.github(organization: repository_owner)`, where `repository_owner` is read straight from the attacker-controlled payload (`params.dig('repository','owner','login')`) [2](#0-1) [3](#0-2) . This only proves the request came from *some* org the attacker controls/owns — it says nothing about which SHA the payload references actually belonging to that org's repo.
3. `StatusHandler#process` then does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` with **no repository/stack scoping at all** [4](#0-3) . Compare this to `CheckSuiteHandler#process`, which correctly scopes lookups through `stacks.where(branch: ...)` where `stacks` is derived from `Repository.from_github_repo_name(repository_name)` (the payload's own `repository.full_name`) [5](#0-4) [6](#0-5) . `PushHandler` similarly scopes via `stacks.not_archived.where(branch:)` [7](#0-6) .
4. Applying the forged status writes a `Status` row on the victim's commit via `Commit#create_status_from_github!`, which is called for every matching commit regardless of stack [8](#0-7) .
5. Amplification: `Commit#blocked?` scans reachable, undeployed commits and treats any commit whose status is `blocking?` (state != success and context is listed in the stack's `blocking_statuses`) as blocking the whole stack [9](#0-8) ; `blocking?` is defined on the status as `!success? && commit.blocking_statuses.include?(context)` [10](#0-9) . Thus injecting a `failure`/`pending` status with a context in the victim stack's `ci.blocking` list (e.g. `ci/kubernetes`) sets `blocked?` true and gates deploys on the victim stack; injecting a `success` status can clear that block. `Commit#deployable?` and `UndeployedCommit#deploy_disallowed?` both depend on this flag [11](#0-10) [12](#0-11) .

Root cause: `StatusHandler` is the only status/CI-related handler that skips the `stacks`/`repository_name` scoping pattern used elsewhere in the same file family, so the commit lookup keys purely on the attacker-supplied `sha` string, which is a value shared across the whole `commits` table irrespective of which repository authenticated the webhook.

Why existing guards don't stop it: `verify_signature` validates org-level HMAC authenticity, not "does this SHA belong to a repo owned by this org" — that binding does not exist anywhere in the code. `ExplicitParameters` schema only enforces types (`sha` is any `String`), not repository ownership. No `Repository`/`Stack` scoping is applied for this handler.

Practical exploitability note: to trigger this, the attacker must know/guess a SHA that is already present as a `Commit` record for the victim's stack (Shipit only stores commits it has synced for tracked stacks). Commit SHAs for actively-tracked branches are effectively public (visible on GitHub, in Shipit's own UI/API for that stack, in PR pages, etc.), so an attacker with read access to the victim repository (even as an outside/anonymous GitHub user) can trivially obtain a target SHA, then forge the status webhook from an org they control.

### Impact Explanation
An attacker who controls any GitHub organization/repository capable of emitting a validly-signed `status` webhook (trivial — they can register their own repo/org with Shipit's webhook infrastructure, or already own one that is registered) can write arbitrary `Status` rows onto commits belonging to any other repository/stack tracked by the same Shipit instance, as long as they know the target SHA. Combined with `blocking_statuses` configuration on the victim stack, this can force `Commit#blocked?`/`deployable?` to flip, blocking or unblocking deploys on a stack the attacker does not own and never authenticated for. This is a cross-repository state-mutation vulnerability ("a payload for one repository mutating another's stack, commit... or an unauthorized deploy/rollback"), matching the Critical impact category. It is repeatable against any stack/commit whose SHA the attacker can observe, and requires no privileges beyond controlling one registered GitHub org/repo webhook secret.

### Likelihood Explanation
Preconditions: (1) attacker's own repo/org has a configured Shipit `GithubHook`/webhook secret they can use to sign requests (attainable by any user who can create a repo/org and register it with the target Shipit instance, or who already has one), (2) victim stack has `blocking_statuses`/`ci.blocking` configured to amplify impact (impact without this config is still a cross-repo status write, but less severe), (3) attacker knows a SHA tracked by the victim stack (trivially obtainable from public GitHub history/PRs or Shipit's own read-accessible stack pages). Cost is low: a single crafted HTTP POST to `/webhooks` with a valid signature for the attacker's own org. Fully repeatable and scriptable against any number of target stacks/SHAs.

### Recommendation
Scope `StatusHandler#process` to the repository that authenticated the webhook, mirroring `PushHandler`/`CheckSuiteHandler`: resolve `stacks` via `Repository.from_github_repo_name(repository_name)` (from the payload's own `repository.full_name`) and only update `Commit` rows belonging to those stacks' repository, e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` or equivalently join through `stack.repository_id` before calling `create_status_from_github!`. Reject/ignore statuses for SHAs not present in a stack that the authenticated repository owns.

### Proof of Concept
Minitest plan (test/models/shipit/webhooks/handlers/status_handler_test.rb or webhooks_controller_test.rb):
1. Seed two stacks in different repositories: `stack_victim` (repository `victim-org/victim-repo`) with `cached_deploy_spec` configuring `ci.blocking: ['ci/kubernetes']`, and `stack_attacker` (repository `attacker-org/attacker-repo`).
2. Create a `Commit` on `stack_victim` with `sha = 'deadbeef...'`, with existing successful statuses so that before the attack `commit.blocked?` is `false` and `stack_victim.commits... deployable?` is `true` — assert this baseline equality: `assert_equal false, commit.blocked?`.
3. Stub `GithubApp#verify_webhook_signature` to return true for `attacker-org` only (simulating attacker's own valid signature) while leaving `victim-org`'s secret unknown/unstubbed.
4. POST `/webhooks` with `X-Github-Event: status`, body `{ "sha": commit.sha, "state": "failure", "context": "ci/kubernetes", "repository": { "full_name": "attacker-org/attacker-repo", "owner": { "login": "attacker-org" } } }`.
5. Assert response is `:ok`, and assert `commit.reload.statuses.exists?(context: 'ci/kubernetes', state: 'failure')` is true even though the payload's `repository.full_name` is `attacker-org/attacker-repo`, not the commit's own `victim-org/victim-repo` — i.e. assert the invariant `commit.stack.repository.full_name == payload['repository']['full_name']` is **false**, yet the status was still written.
6. Assert `commit.reload.blocked?` (or `stack_victim.commits.undeployed.first.deploy_disallowed?`) is now `true`, proving the victim stack's deploy gate was flipped by a payload the victim repository never authenticated.
