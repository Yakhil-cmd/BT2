### Title
Cross-tenant Status forgery via global SHA lookup in `StatusHandler#process` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` resolves target `Commit` rows solely by `Commit.where(sha: params.sha)`, with no scoping to the repository named in the webhook payload. `Commit#create_status_from_github!` then calls `statuses.replicate_from_github!(stack_id, github_status)` using `self.stack_id` — the pre-existing commit's own stack — so a `status` event delivered for a repository the attacker legitimately controls can write a `Status` row against any other stack's commit that happens to share the same SHA.

### Finding Description
The claimed binding is: `stack_id` passed into `Status.replicate_from_github!` == `stack_id` implied by `payload['repository']`. Tracing the code shows this is false.

- `StatusHandler#process` [1](#0-0)  does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` — a global, unscoped query across the entire `commits` table.
- `Commit#create_status_from_github!` [2](#0-1)  forwards `stack_id`, taken from the matched `Commit` record's own `belongs_to :stack` association [3](#0-2) , never from the webhook payload.
- `Status.replicate_from_github!` [4](#0-3)  trusts that `stack_id` verbatim and `find_or_create_by!`s a `Status` row with it.
- The base `Handler` class defines a `repository_name`/`stacks` scoping helper based on `payload.dig('repository', 'full_name')` [5](#0-4) , but `StatusHandler` never calls `stacks` or `repository_name` — it bypasses this scoping entirely.
- `WebhooksController#verify_signature` only authenticates that the request came from GitHub for the org named as `repository_owner` in the payload [6](#0-5) ; it does not restrict which DB rows the handler is allowed to mutate.

Exploit flow: an attacker who controls (or forks) a repository that is itself onboarded as a Shipit stack (e.g., their own account/org with the GitHub App installed) can trigger a genuine, GitHub-signed `status` event for any commit SHA reachable in their own repository's git history. Because forks share commit objects (and thus SHAs) with upstream repositories, any SHA that also exists as a `Commit` row belonging to an unrelated stack (e.g., the upstream repo, or any other repo/stack that happens to contain a commit with byte-identical content) will have its `Status` updated — with attacker-chosen `state`, `description`, `target_url`, and `context` — even though the webhook's `payload['repository']` names only the attacker's own repo.

None of the listed guards prevent this: `verify_signature` only checks origin authenticity for the attacker's own org, `ExplicitParameters` only validates field shapes, and no model validation ties `Status#stack_id` to the requesting repository.

### Impact Explanation
A forged `state: "success"` (or `"failure"`/`"error"`) status can be written against a commit belonging to a stack the attacker has no relationship to, without going through GitHub's actual CI/check process for that repository. Since `Commit#add_status` reacts to status changes by calling `stack.schedule_merges` when the new status is pending or successful [7](#0-6) , and `deployable?`/`schedule_continuous_delivery` gate on status state [8](#0-7) [9](#0-8) , this can unblock continuous-delivery/merge queue processing for a stack the attacker never authenticated against — matching the Critical category "a payload for one repository mutating another's stack, commit, task ... or an unauthorized deploy, rollback or merge." The write is repeatable for any SHA the attacker's own repository history overlaps with a target stack's commits, across arbitrarily many tenants sharing this Shipit instance.

### Likelihood Explanation
Preconditions: the attacker's own repository (or fork) must be a repository whose owning org/account is a recognized GitHub App installation for this Shipit instance (needed only to pass `verify_signature`), and there must exist a commit with a matching SHA already recorded under a different, target stack. The latter is common in practice via forks of public repos tracked by Shipit, shared history between mirrored repos, or cherry-picked/rebased commits with identical content. Cost to the attacker is low: create/push to a repo they control and cause GitHub to emit a `status` webhook (e.g., via the GitHub Statuses/Checks API on their own repo) for a SHA of interest. No secrets, sessions, or privileged roles are required.

### Recommendation
Scope `StatusHandler#process` by the payload's repository, mirroring the base `Handler#stacks` helper (e.g., resolve `stacks = Repository.from_github_repo_name(payload.dig('repository','full_name'))&.stacks`, then restrict the `Commit` lookup to `Commit.where(sha: params.sha, stack_id: stacks.select(:id))`) instead of querying `Commit` globally by `sha` alone.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb (conceptual addition)
test "status webhook for one repository must not mutate a commit belonging to an unrelated stack" do
  target_stack = shipit_stacks(:shipit)
  attacker_stack = create_stack!(repository: create_repository!(owner: 'attacker', name: 'evil-fork'))

  shared_sha = 'a' * 40
  target_commit = target_stack.commits.create!(sha: shared_sha, message: 'shared content')

  payload = {
    'sha' => shared_sha,
    'state' => 'success',
    'repository' => { 'full_name' => attacker_stack.github_repo_name },
  }

  Shipit::Webhooks::Handlers::StatusHandler.call(payload)

  target_commit.reload
  # Binding under test: stack_id written into Status should equal
  # the stack implied by payload['repository'] (attacker_stack.id),
  # NOT target_commit.stack_id (an unrelated, pre-existing stack).
  refute_equal attacker_stack.id, target_commit.statuses.last.stack_id
  assert_equal target_commit.stack_id, target_commit.statuses.last.stack_id # demonstrates the leak
end
```
This demonstrates that `Status#stack_id` after `StatusHandler.call` equals `target_commit.stack_id` (the pre-existing, unrelated commit's stack) rather than any value derivable from `payload['repository']`, confirming the broken binding.
