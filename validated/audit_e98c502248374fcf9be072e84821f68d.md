### Title
Webhook signature verification org selected from `repository.owner.login` does not bind to the `repository.full_name` acted on by handlers, enabling cross-organization/cross-repository webhook forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/webhook secret to validate a delivery against using `repository.owner.login` (or `organization.login`) from the JSON body, but the event handlers that actually act on the payload (e.g. `PushHandler`) resolve the target `Repository`/`Stack` using a *different* field of the same body: `repository.full_name`. Nothing binds these two fields together. In a multi-organization Shipit deployment (Shipit explicitly supports configuring several GitHub Apps/organizations, see `test/dummy/config/secrets_double_github_app.yml`), anyone who legitimately controls one configured organization's webhook secret can forge a delivery that authenticates as "their" org but whose `repository.full_name` names a stack belonging to a different, victim organization's repository.

### Finding Description
`verify_signature` picks the signing organization purely from payload content: [1](#0-0) [2](#0-1) 

Once the HMAC check passes for the org derived from `repository.owner.login`, the raw payload is dispatched unmodified to all registered handlers for the event: [3](#0-2) 

Handlers, however, determine the actual `Repository`/`Stack` to mutate from an independent field, `repository.full_name`, with no cross-check against the organization used for authentication: [4](#0-3) 

`PushHandler#process` uses that repository binding to call `stack.sync_github(expected_head_sha: params.after)` on every matching, non-archived stack for the target branch: [5](#0-4) 

This is exactly the pattern in the Kakarot report: authorization is checked against one identity (`caller_code_address` / here, `repository.owner.login`-derived org secret) while the operation is actually performed against a different, unchecked identity (`caller_address` / here, `repository.full_name`). The binding broken is: `organization that authenticated == repository that is written`, which does not hold.

### Impact Explanation
An entity that legitimately owns/administers a GitHub App configured in Shipit for *one* organization (Org A) — and therefore knows Org A's `webhook_secret` — can forge a `push` (or other) webhook payload where `repository.owner.login` = "Org A" (to pass signature verification against Org A's secret) but `repository.full_name` = "OrgVictim/some-repo" (an unrelated organization/repository also tracked by the same Shipit instance). This lets Org A force `GithubSyncJob`/`sync_github` to run against OrgVictim's stack with an attacker-chosen `expected_head_sha`, i.e. cross-repository/cross-tenant writes to state the attacker has no GitHub-side authorization over. This is a cross-repository-write class impact affecting stack head/commit state outside the attacker's own organization boundary.

### Likelihood Explanation
Exploitability requires only knowledge of one legitimate organization's own webhook secret in a multi-org Shipit deployment (a configuration explicitly supported and documented, see the two-organization fixture `secrets_double_github_app.yml`) plus the ability to send an arbitrary HTTP POST to the public `/webhooks` endpoint — no Shipit session, `ApiClient` token, or GitHub write access to the victim repository is needed. The mismatch is a straightforward, unauthenticated confusion between two unrelated JSON fields.

### Recommendation
Bind the two fields together: after selecting `github_app` via `repository_owner`, require that the same `github_app`'s organization matches the owner encoded in `repository.full_name` (i.e., derive `repository_name`'s owner segment and assert equality with `repository_owner`) before dispatching to handlers, or better, resolve the target `Repository` first and use *its* configured organization to select the verifying webhook secret, rather than trusting an unauthenticated payload field to choose which secret authenticates the message.

### Proof of Concept
1. Shipit is configured (per `secrets_double_github_app.yml`-style setup) with two GitHub Apps: `OrgA` (attacker-administered) and `OrgVictim` (unrelated tenant), each with distinct `webhook_secret`s.
2. Attacker, who administers the `OrgA` GitHub App and therefore knows `OrgA`'s `webhook_secret`, crafts a `push` event payload:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "OrgA" },
    "full_name": "OrgVictim/victim-repo"
  }
}
```
3. Attacker signs the raw JSON body with `OrgA`'s webhook secret and computes `X-Hub-Signature: sha1=<hmac>`.
4. Attacker POSTs to `/webhooks` with `X-Github-Event: push`.
5. `WebhooksController#verify_signature` computes `repository_owner = "OrgA"`, calls `Shipit.github(organization: "OrgA")`, and the HMAC verifies successfully because the attacker used `OrgA`'s real secret [1](#0-0) .
6. `PushHandler.call(params)` is invoked with the full payload; `repository_name` resolves to `"OrgVictim/victim-repo"` [4](#0-3) , and `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` is triggered for every non-archived `master` stack of that victim repository [6](#0-5) , even though the attacker's authenticated identity was only ever `OrgA`.

# frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
