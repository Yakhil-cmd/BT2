## Title
Missing domain separation in `is_valid_signed_package()` / `is_valid_sig()` oscript signature primitives allows cross-AA replay of signed messages - (File: formula/evaluation.js, object_hash.js)

### Summary
The oscript formula primitives `is_valid_signed_package()` and `is_valid_sig()` verify a signature over an arbitrary message/`signed_message` object without binding the hash-to-sign to the verifying AA's own identity (its address, `this_address`) or any other context identifier. This is architecturally identical to the reported `ERC20Distribution`/`ERC20DistributionNative` bug: a signature proof that lacks a domain separator can be lifted from the context it was created for and replayed in a different verifying context, since nothing in the signed payload ties it to that specific verifier.

### Finding Description
`is_valid_signed_package` in the formula evaluator hashes the package with `objectHash.getSignedPackageHashToSign()`: [1](#0-0) 

This hash covers only `signed_message`, `version`, and `last_ball_unit` (with `authentifiers` stripped) — it contains no reference to the address of the AA that is calling `is_valid_signed_package()`, nor to any chain/network identifier: [2](#0-1) 

`is_valid_sig()` is even more permissive — it verifies an arbitrary caller-supplied `message` against an arbitrary `pem_key`, with no context binding at all: [3](#0-2) 

There is no protocol-level enforcement that the signed payload include the verifying AA's own address (`this_address`) or any other domain-specific tag; it is entirely optional and left to the oscript author. The shipped reference sample `test/samples/payment_channels.oscript` demonstrates this is a known-necessary but ad-hoc mitigation: it manually embeds `channel: this_address` and `period` inside the signed message and explicitly checks them before calling `is_valid_signed_package`: [4](#0-3) 

By contrast, `test/samples/order_book_exchange.oscript` — a generic, reusable order-matching AA template — signs orders with fields that carry no binding to the specific AA instance verifying them (`sell_asset`, `buy_asset`, `sell_amount`, `price`, `address`, `last_ball_unit`), and the replay-protection key (`$id1`/`$id2`) is likewise derived only from order content, not from `this_address`: [5](#0-4) 

Consequently, if the same oscript template/bytecode is deployed as two distinct AA instances (distinct addresses, e.g. two separate order-book markets sharing the same code, which is common since AA addresses are just hashes of their oscript definition and any user can deploy an identical copy), a signed order that a trader publishes as `trigger.data.order1` to AA instance #1 is a fully valid, unconsumed signature for AA instance #2 as well, because `is_valid_signed_package` never verifies that the signature was intended for the specific `this_address` doing the check.

### Impact Explanation
An attacker who observes a valid signed order/package in a publicly broadcast unit (trigger data on the DAG is public) can copy it verbatim and submit it as trigger data to a different, independently-deployed instance of the same AA template. Because the per-AA `executed_<id>`/`amount_left_<id>` state only exists in that AA's own state and the id/hash never encodes `this_address`, the copied order will be treated as fresh and tradable there, causing the original signer's funds tracked in that second AA's internal balance ledger to be traded/spent without the signer ever having intended to interact with that AA instance. This results in unauthorized asset movement / unintended trade execution and potential fund loss for the victim address across AA instances they never consented to trade in.

### Likelihood Explanation
Likelihood is elevated because: (1) trigger data for AAs is always public on the DAG, so any attacker can harvest a valid `signed_package`; (2) deploying a byte-for-byte duplicate of a popular AA template under a different address is trivial and permissionless in Obyte; (3) the core primitive gives no warning or built-in protection — only AA authors who happen to think of it (as in the `payment_channels.oscript` sample) add manual binding to `this_address`; templates that omit it (as in `order_book_exchange.oscript`) are silently vulnerable.

### Recommendation
Follow the fix pattern used for the analogous `ERC20Distribution`/`ERC20DistributionNative` issue: bind the signed payload to a domain identifier. Concretely:
- Document and, where feasible, enforce that `signed_message` objects consumed via `is_valid_signed_package()`/`is_valid_sig()` must include the verifying AA's own `this_address` (and any other relevant context such as `period`/nonce) as done in `payment_channels.oscript`.
- Consider extending `getSignedPackageHashToSign()`/`validateSignedMessage()` to optionally take and mix in a caller-supplied domain tag (e.g., the calling AA address) so that oscript authors get built-in cross-AA replay protection instead of relying on manual convention.

### Proof of Concept
1. Deploy `order_book_exchange.oscript` twice as AA_X and AA_Y (identical code, different addresses since AA address = hash of definition plus deployment specifics allow duplicate templates).
2. Trader T deposits funds and signs `order1 = {signed_message: {sell_asset, buy_asset, sell_amount, price, address: T}, last_ball_unit, authors:[...]}` intending it to be matched only within AA_X.
3. T (or anyone observing the public unit containing this order as `trigger.data.order1` sent to AA_X) resubmits the identical `signed_package` object as `trigger.data.order1` to AA_Y, paired with a counter-order.
4. `is_valid_signed_package(trigger.data.order1, $order1.address)` in AA_Y succeeds because the check only verifies the signature against `order1.address`, not against `this_address` of AA_Y, and AA_Y's own `executed_<id>` state is empty, so the trade executes against T's balance in AA_Y — a context T never authorized.

function getSignedPackageHashToSign(signedPackage) {
