### Title
Stale per-block `index-cache` in `market.clar` lets one user's liquidation-triggered `socialize-debt` corrupt zToken valuation for unrelated users in the same block - (File: `local-testing/contracts/market/market.clar`)

### Summary
`market.clar` caches vault `{index, lindex}` per `{timestamp, aid}` to save cross-contract calls within a block [2](#0-1) . This cache is written to persistent map storage, so it is shared across *all transactions in the same block*, not scoped to a single transaction. `socialize-debt` (called from `liquidate` when a borrower has no collateral left) mutates the vault's real `lindex` on-chain, marking down the liquidity index proportionally to the bad-debt loss [1](#0-0) . If an earlier transaction in the same block already primed `index-cache` for that `aid` (e.g., via a normal `borrow`, `repay`, `collateral-add`, or health check that called `accrue-and-cache`), the cache entry is never invalidated or refreshed after `socialize-debt` runs, because the cache key is purely time-based [2](#0-1) , and `liquidate`/other flows re-use `get-cached-indexes`/`accrue-and-cache` results rather than forcing a fresh vault read.

### Finding Description
- Attacker: any user who triggers a liquidation that fully wipes out a borrower's collateral, causing `socialize-debt` to run and mark down the vault's `lindex` at `local-testing/contracts/market/market.clar:1557-1583` (fold over `socialize-debt-asset`).
- Victim: any other unrelated user whose transaction executes later in the *same block* and needs the value of a zToken (e.g., zsBTC) that maps to the same underlying vault (`is-ztoken` -> `vault-id` mapping at `local-testing/contracts/market/market.clar:281-302`).
- Shared state: `index-cache` map, keyed by `{timestamp, aid}` only, populated by `accrue-and-cache` [2](#0-1) .

Sequence:
1. Earlier in block N, a benign transaction (could be the victim's own prior op, or any third party) calls `accrue-and-cache(aid)`, which is a cache MISS, calls `vault-accrue`, and stores the **pre-socialization** `{index, lindex}` in `index-cache` for `{timestamp: T, aid: aid}`.
2. Still in block N, the attacker executes `liquidate` on some borrower whose collateral is fully seized, triggering `socialize-debt` on the underlying vault, which recomputes and lowers the real on-chain `lindex` [3](#0-2) . This state mutation happens in the vault contract's data var, completely bypassing `index-cache` in `market.clar`.
3. Still in block N (timestamp T unchanged), the victim calls e.g. `collateral-add`, `borrow`, or another `liquidate` involving a zToken backed by that same vault. `accrue-and-cache(aid)` is a cache HIT and returns the stale, pre-socialization `lindex`/`index` from step 1 instead of the vault's true post-socialization value [2](#0-1) .
4. The victim's zToken collateral or debt is valued using the wrong index: since a socialization event lowers `lindex` (reducing the true redeemable value backing a zToken), the stale cache overvalues the victim's zToken collateral relative to its real post-loss worth, letting the victim borrow more than truly collateralized, or evade a liquidation, or letting a health check pass when it should fail.

Root cause: the cache invalidation strategy assumes the only state change affecting `{index, lindex}` within a block is time (hence keyed only by timestamp), but `socialize-debt` is a same-block, non-time-based mutation of `lindex` that the cache has no mechanism to observe.

### Impact Explanation
This is a temporary freezing/mispricing of funds for the victim within the affected block: a stranger's liquidation event silently overvalues (or otherwise mis-prices) the victim's zToken collateral/debt for the remainder of the block, letting the victim's operation succeed (extra borrow, avoided liquidation, wrong health check) based on data that no longer reflects the vault's real economic state. It maps to the "temporary freezing of funds" / mispriced-collateral impact class, since positions are evaluated against stale, socialization-affected numbers rather than the true vault state for the rest of the block.

### Likelihood Explanation
Requires: (a) a liquidation that fully wipes a borrower's collateral and triggers `socialize-debt` on a vault whose zToken is also used elsewhere as collateral/debt, and (b) another user transacting against the same asset/aid within the same block, after the cache was already primed. Given liquidations and zToken operations can be intentionally sequenced by a single actor controlling multiple transactions in one block (or coincide naturally in busy blocks), likelihood is non-trivial though it depends on specific ordering, which is somewhat opportunistic rather than fully attacker-controlled without also controlling block ordering (e.g., via a bundling/MEV-adjacent technique, but not requiring MEV/reorg per se — simply submitting both transactions in the same block).

### Recommendation
Invalidate/refresh `index-cache` for `aid` whenever `socialize-debt` (or any operation) mutates the vault's `lindex`/`index` outside of the normal accrue path — e.g., have `vault-socialize-debt` in `market.clar` explicitly `map-delete`/`map-set` the corresponding `index-cache` entry with the fresh post-socialization indexes immediately after the vault call, or eliminate the same-block cross-transaction sharing by re-deriving indexes fresh whenever a socialization event has occurred since the cache entry was written (e.g., track a monotonically increasing "socialization nonce" per aid and include it in the cache key/invalidate on bump).

### Proof of Concept
Not independently executable from static analysis alone; the following on-chain sequence within a single block N demonstrates the flaw based on the code paths cited above:
1. Tx1 (any user): call `market.collateral-add` or `market.borrow` involving zToken `zsBTC` → internally calls `accrue-and-cache(sBTC)` → cache MISS → stores `{index: I0, lindex: L0}` for `{timestamp: T, aid: sBTC}`.
2. Tx2 (attacker/liquidator): call `market.liquidate` on borrower `B` whose sBTC-vault debt position has zero remaining collateral → `socialize-debt-asset` fold invokes `.vault-sbtc socialize-debt scaled-amount` → vault sets `lindex` to `L1 < L0` on-chain [4](#0-3) .
3. Tx3 (victim, same block N): call `market.collateral-add`/`market.borrow` using `zsBTC` collateral → `accrue-and-cache(sBTC)` hits the still-cached `{index: I0, lindex: L0}` from Tx1 instead of the vault's true `{*, L1}` → victim's zsBTC collateral is valued using the stale, higher `L0`, producing an incorrect (overstated) collateral valuation for the rest of block N.

**Note on confidence:** I was not able to fully trace whether any other guard (e.g., an implicit re-accrual forced elsewhere in `liquidate`/`borrow`/`collateral-add` flows, or a possible off-chain sequencer guarantee that liquidations and cache-priming txs cannot coexist in one block) neutralizes this path, nor did I locate an explicit test covering cross-transaction cache staleness after `socialize-debt` in the same block. Given index-size limits on the indexed codebase, I could not review every call site of `accrue-and-cache`/`get-cached-indexes` across `market.clar` (1600+ lines) to confirm there is no additional invalidation step I missed; a full review or a Devin session with complete file access is recommended to validate this end-to-end before treating it as conclusively exploitable.

(define-private (accrue-and-cache (aid uint))
  (let ((cache-key { timestamp: stacks-block-time, aid: aid })
        (cached? (map-get? index-cache cache-key)))

    (match cached?
      ;; cache HIT: return cached value (1 read only)
      cached-indexes (ok cached-indexes)

      ;; cache MISS: accrue and cache (vault-accrue now returns indexes)
      (let ((indexes (try! (vault-accrue aid))))
        ;; store in cache
        (map-set index-cache cache-key indexes)
        (ok indexes)))))
