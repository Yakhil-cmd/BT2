### Title
Attacker-controlled `Merge-Requested-By:` line in a commit message overrides GitHub-attributed commit authorship - ([File: app/models/shipit/user.rb])

### Summary
`Commit.from_github` delegates author resolution to `User.find_or_create_author_from_github_commit`, which regex-matches the free-text commit message for a `Merge-Requested-By: <login>` line and, if present, attributes the commit's `author` to that login instead of the GitHub-reported commit author. Any unprivileged user can embed this line in a commit they push to their own fork; if a maintainer performs an ordinary (non-squash) merge, the original commit object — with the attacker-chosen text intact — becomes part of the tracked branch and is ingested verbatim by `GithubSyncJob`.

### Finding Description
The broken binding: `Commit#author` on a tracked branch should equal `commit.author`/`commit.commit.author` as returned by the GitHub Commits API for that SHA, not a string parsed out of the commit message body written by the same person who authored the patch.

Code path:
- `app/jobs/shipit/github_sync_job.rb` (`append_commit`) calls `Commit.create_from_github!(commit)` for each commit in a push payload.
- `Commit.create_from_github!` → `Commit.from_github` [1](#0-0) .
- `from_github` calls `User.find_or_create_author_from_github_commit(commit)`: [2](#0-1) 

The regex `/^#{MergeRequest::MERGE_REQUEST_FIELD}: ([\w\-.]+)$/` matches against `github_commit.commit.message` — the raw commit message text — with no check that this specific commit is a Shipit-generated merge-queue commit. The `Merge-Requested-By:` convention is intended only for commit messages Shipit itself constructs in `MergeRequest#merge_message` when merging a PR via the merge queue [3](#0-2) , but `find_or_create_author_from_github_commit` applies the same pattern indiscriminately to every commit ingested by `GithubSyncJob`, including ordinary developer commits that were never processed by the merge queue.

Exploit flow: an attacker forks the repository, commits a change with a message body containing a line `Merge-Requested-By: victim-login` (any valid GitHub login, including the attacker's own or an arbitrary third party's), opens a PR, and a maintainer performs a normal merge (not squash) so the original commit object is preserved with its original SHA, author, and message. GitHub then delivers a push webhook for the base branch containing that original commit. `GithubSyncJob` ingests it via `append_commit` → `Commit.create_from_github!` → `Commit.from_github`, which matches the embedded line and calls `find_or_create_by_login!('victim-login')`, setting `Commit#author` to that GitHub user rather than to the commit's real GitHub-reported author.

None of the existing guards prevent this: there is no webhook-signature bypass involved (the push webhook is legitimate and properly signed by GitHub), `identify_merge_request` in `app/models/shipit/commit.rb` only overrides `author` from `merge_request.merge_requested_by` when a matching `MergeRequest` row exists for that PR number [4](#0-3) , but the vulnerable path in `User.find_or_create_author_from_github_commit` runs unconditionally for every ingested commit regardless of whether a `MergeRequest` exists, and is not scoped to commits produced by the merge queue.

### Impact Explanation
The resulting `Commit#author` record is used for the audit trail (UI author display) and, through `TaskCommands#env`, becomes `SHIPIT_USER`, `EMAIL`/committer identity, etc. for tasks associated with that commit (deploys, rollbacks). This lets an unprivileged forker cause Shipit to permanently misattribute a merged commit's authorship to an arbitrary GitHub identity of the attacker's choosing, corrupting the authorization/audit trail for any repository whose maintainers merge such a PR normally. It is repeatable against any stack/repository that ingests push events via `GithubSyncJob`, and the login used can be any existing GitHub account, including privileged maintainers, letting the attacker impersonate someone else in Shipit's records without that person's involvement.

### Likelihood Explanation
Preconditions: the target repository must have `Stack` tracking the branch that receives the commit, and a maintainer must merge the attacker's PR with an ordinary (merge-commit) strategy that preserves the original commit object — a very common default. No Shipit secrets, sessions, or team membership are required; the attacker only needs the ability to push to their own fork and open a PR, which is available to any GitHub user. Squash-merge or rebase-merge strategies that rewrite the commit could alter the message/SHA and change conditions, but many repositories default to real merge commits, making this readily reachable.

### Recommendation
Do not derive `Commit#author` from arbitrary commit-message text for general commit ingestion. Scope the `Merge-Requested-By:` parsing to commits that are actually merge commits produced by the Shipit merge queue (e.g., only apply it when `record.merge_request` is set from `identify_merge_request`, or verify the commit SHA matches a `MergeRequest#merge_commit` created via `MergeRequest#merge!`), and always fall back to the real GitHub-reported `commit.author`/`commit.committer` for any commit that isn't provably a Shipit-authored merge.

### Proof of Concept
Add a minitest to `test/models/commits_test.rb` (or `test/models/users_test.rb`) asserting divergence is rejected:
1. Build a fake `Sawyer::Resource` (or stub) representing a GitHub commit where `commit.author.login == 'attacker'`, `commit.committer.login == 'attacker'`, and `commit.commit.message == "Fix bug\n\nMerge-Requested-By: victim\n"`.
2. Stub `Shipit.github.api.user('victim')` to return a real victim user payload (simulating `find_or_create_by_login!`).
3. Call `Shipit::Commit.from_github(fake_commit)` (with no associated `MergeRequest` in the stack) and assert:
   - `record.author.login` **should** equal `'attacker'` (the real GitHub-reported author),
   - but currently equals `'victim'`, proving the conflation.
4. Additionally assert in `TaskCommands#env` output (or wherever `SHIPIT_USER`/`GIT_COMMITTER_NAME` are built from `commit.author`) that the emitted env reflects the real GitHub author, not the message-derived login — currently it does not, confirming the impact reaches the deploy environment.

    def self.find_or_create_author_from_github_commit(github_commit)
      if (match_info = github_commit.commit.message.match(/^#{MergeRequest::MERGE_REQUEST_FIELD}: ([\w\-.]+)$/))
        begin
          return find_or_create_by_login!(match_info[1])
        rescue Octokit::NotFound
          # Corner case where the merge-requested-by user cannot be found (renamed/deleted).
          # In this case we carry on and search for the commit author
        end
      end
      find_or_create_from_github(github_commit.author.presence || github_commit.commit.author.presence)
    end
