### Title
Webhook signature verification keyed on unsigned-secret organization allows forged `membership` events to grant `Shipit.github_teams` authorization for an unrelated repository - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects *which* GitHub App/organization's `webhook_secret` is used to validate an inbound webhook based on `repository_owner`, a value taken from the same untrusted request body it is about to validate. When any configured organization in a multi-org `secrets.yml` (a documented, supported configuration, see `test/dummy/config/secrets_double_github_app.yml`) has `webhook_secret: nil` (also a documented, explicitly optional setting per `docs/setup.md`), `GithubApp#verify_webhook_signature` unconditionally returns `true` for any payload claiming that organization as `repository.owner.login`/`organization.login` — with **no HMAC check at all**. This breaks the equality "organization whose credential authenticated the request" == "team/organization actually mutated by the handler," because the `MembershipHandler` trusts `params.team` / `params.organization.login` / `params.member.login` straight out of the same forged, unauthenticated body to create/modify a `Team` and its `memberships`, and `Shipit.github_teams` (used by `User#authorized?`) is resolved by team handle, not by any verified GitHub relationship.

### Finding Description
- `WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-30`) computes `repository_owner` from the unauthenticated body (`app/controllers/shipit/webhooks_controller.rb:59-62`) and uses it to look up which `GithubApp` — and therefore which `webhook_secret` — will validate the signature: `github_app = Shipit.github(organization: repository_owner)`.
- `GithubApp#verify_webhook_signature` (`lib/shipit/github_app.rb:76-83`) contains `return true unless webhook_secret`. Since `webhook_secret` is explicitly documented as optional (`docs/setup.md:30`, `config/secrets.development.example.yml:11`, and multi-org example `test/dummy/config/secrets_double_github_app.yml`), any organization configured without a secret makes signature verification a no-op for payloads claiming that organization.
- An unprivileged, unauthenticated attacker can `POST /webhooks` with `X-Github-Event: membership`, `organization.login` set to the no-secret org (satisfying `verify_signature`), and arbitrary `team` and `member.login` fields. `MembershipHandler#process` (`app/models/shipit/webhooks/handlers/membership_handler.rb:22-34`) then creates/finds a `Team` (`find_or_create_team!`, line 38-43) using attacker-supplied `params.team.id`/`name`/`slug`, sets its `organization` from attacker-supplied `params.organization.login`, and calls `team.add_member(member)` where `member` is created via `User.find_or_create_by_login!(params.member.login)` — entirely attacker-controlled.
- `Shipit.github_teams` (`lib/shipit.rb:256-258`) resolves teams by handle (`"#{organization}/#{slug}"`, `app/models/shipit/team.rb:37-39`) purely from the DB record created above, with no re-verification against GitHub. `User#authorized?` (`app/models/shipit/user.rb:80-82`) checks `teams.where(id: Shipit.github_teams.map(&:id)).exists?`. If the attacker crafts a `team.slug`/`team.name`/`organization.login` that collides with a handle in `Shipit.github_teams` (an org/slug combination is public/guessable), and sets `member.login` to their own GitHub login, they gain membership in a `Team` matching `Shipit.github_teams`, satisfying `authorized?` without ever being a real member of that GitHub team.

### Impact Explanation
This is an escalation into `Shipit.github_teams` authorization — a user who is not a member of the required GitHub team(s) can forge unauthenticated membership records that satisfy `current_user.authorized?` (`app/controllers/concerns/shipit/authentication.rb:26`), granting them full application access as an "authorized" Shipit user. This matches the explicitly listed High-severity impact "escalation into `Shipit.github_teams` authorization." From there, an authorized session can trigger deploys/rollbacks/tasks, an unauthorized deploy which is separately listed as Critical impact.

### Likelihood Explanation
Requires: (1) the deployment to configure at least one organization with no `webhook_secret` — an explicitly supported and documented configuration, not a deviation from documented mounting; multi-org configurations with per-org secrets are a first-class feature (`Shipit.github_app_config`, `secrets_double_github_app.yml`). (2) The attacker needs the `Shipit.github_teams` handle (organization + slug), which is often public (GitHub team slugs and org names are frequently discoverable) or guessable from the deployed Shipit instance's org. No credentials, session, or API token are required — the `/webhooks` endpoint is unauthenticated by design (`skip_before_action :verify_authenticity_token`), and `check_if_ping`/`drop_unhandled_event` don't gate membership events.

### Recommendation
- Do not allow `webhook_secret` to be entirely absent for any organization that is also used for `Shipit.github_teams` authorization; require a secret, or fail closed (`return false` instead of `return true`) when no secret is configured in production.
- Never bind webhook trust decisions (which secret validates the request) to fields taken from the same unauthenticated payload being validated; the signature check should not itself depend on attacker-controlled data used to select the verification key.
- In `MembershipHandler`, cross-check that `params.organization.login` matches a `GithubHook::Organization` actually configured with a webhook, and re-validate team membership via the GitHub API (as `Team#refresh_members!` already does) rather than trusting webhook-asserted membership outright for authorization-relevant state.

### Proof of Concept
1. Deploy Shipit with a multi-org `secrets.yml` where org `evil-org` has `webhook_secret: nil` (a documented, optional setting) and org `real-org/deploy-team` is present in `Shipit.github_teams`.
2. As an unauthenticated attacker, `POST /webhooks` with headers `X-Github-Event: membership` and JSON body:
```json
{
  "action": "added",
  "organization": { "login": "real-org" },
  "team": { "id": 999999, "name": "deploy-team", "slug": "deploy-team", "url": "https://api.github.com/teams/999999" },
  "member": { "login": "attacker-github-login" }
}
```
Note: for `verify_signature` to pick a no-secret config, `repository_owner`/`organization.login` must resolve to the no-secret org; if `real-org` itself is the no-secret org this step is direct. Where a distinct no-secret org must be used to bypass verification while still targeting `real-org`'s team, the attacker sets `organization.login` to the no-secret org for the outer routing while the `MembershipHandler`'s own `params.organization.login` is taken from the same field — so the practical exploitation path is strongest when the org lacking a `webhook_secret` is the same org referenced by `Shipit.github_teams`.
3. Since `webhook_secret` is blank for that org, `verify_webhook_signature` returns `true` without checking any signature.
4. `MembershipHandler#process` creates/updates `Team` with `organization: "real-org"`, `slug: "deploy-team"`, and adds `attacker-github-login` as a member.
5. Attacker logs in via GitHub OAuth as `attacker-github-login`; `User#authorized?` now returns `true` because they belong to a `Team` matching `Shipit.github_teams`, granting full unauthorized access to the Shipit instance.     def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

# frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class MembershipHandler < Handler
        params do
          requires :action, String
          requires :team do
            requires :id, Integer
            requires :name, String
            requires :slug, String
            requires :url, String
          end
          requires :organization do
            requires :login, String
          end
          requires :member do
            requires :login, String
          end
        end
        def process
          team = find_or_create_team!
          member = User.find_or_create_by_login!(params.member.login)

          case params.action
          when 'added'
            team.add_member(member)
          when 'removed'
            team.members.delete(member)
          else
            raise ArgumentError, "Don't know how to perform action: `#{action.inspect}`"
          end
        end

        private

        def find_or_create_team!
          Team.find_or_create_by!(github_id: params.team.id) do |team|
            team.github_team = params.team
            team.organization = params.organization.login
          end
        end
      end
    end
  end
end
