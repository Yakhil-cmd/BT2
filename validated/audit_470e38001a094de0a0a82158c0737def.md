## Title
Stack-scoped API tokens can read any stack's CCMenu status, bypassing their `stack_id` restriction - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Api::BaseController` establishes a binding between an `ApiClient`'s authorized stack (`current_api_client.stack_id`) and the stacks it may act on, by scoping the `stacks` relation and resolving `stack` through it. `Api::CCMenuController` overrides `stack` to bypass this scoping entirely, breaking the binding "a stack a token authorises versus a stack it touches," matching the analog bug class from the report (a value acted upon that is never covered by the enforcement mechanism meant to protect it).

### Finding Description
`ApiClient` supports being scoped to a single `stack` via `belongs_to :stack, optional: true` [1](#0-0) . `Api::BaseController` enforces this scoping for every controller that inherits from it:

```ruby
def stacks
  @stacks ||= current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all
end

def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
``` [2](#0-1) 

This means for a scoped client (`stack_id` present), `stack` can only ever resolve to the one stack the client is bound to, no matter what `params[:stack_id]` the caller supplies.

`Api::CCMenuController`, however, overrides `stack` to resolve directly against the global `Stack` model instead of the scoped `stacks` collection:

```ruby
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end
``` [3](#0-2) 

Authorization for this controller is only checked via `require_permission :read, :stack` [4](#0-3) , which in turn calls `ApiClient#check_permissions!`:

```ruby
def check_permissions!(operation, scope)
  required_permission = "#{operation}:#{scope}"
  unless permissions.include?(required_permission)
    raise InsufficientPermission, ...
  end
  true
end
``` [5](#0-4) 

This check only verifies the client has the string permission `read:stack` in its `permissions` array — it never checks whether `params[:stack_id]` matches `current_api_client.stack_id`. Because `CCMenuController#stack` doesn't reuse the scoped `stacks` helper (unlike every other `Api::*` controller, e.g. `Api::StacksController` [6](#0-5)  or `Api::TasksController` which relies on `stack.tasks` from the inherited scoped `stack` [7](#0-6) ), the intended per-stack scoping is not applied here.

Fixture data confirms stack-scoped `ApiClient`s are a supported, real configuration (a client bound to one stack with only `read:stack` permission) [8](#0-7) , and this exact scoped-client pattern is also what `CCMenuUrlController` provisions for embedding in external CI tooling [9](#0-8) .

### Impact Explanation
An attacker holding a valid but stack-scoped API token (e.g., a CCMenu URL token meant to expose only one stack's build status to a CI dashboard) can supply an arbitrary `stack_id` parameter to `Api::CCMenuController#show` and read deploy/build state (`lastBuildStatus`, `lastBuildLabel`, lock status, activity) for any stack in the installation, not just the one the token is bound to. This is an unauthenticated-scope escalation into stack state disclosure across stacks the token was never authorized for — matching the "unauthenticated read of stack state" High-impact category, since the scoping mechanism (`stack_id`) that is meant to gate this read is silently skipped for this endpoint.

### Likelihood Explanation
Any holder of a stack-scoped read-only token (these tokens are specifically designed to be embedded in third-party CCMenu-compatible tooling and thus are more exposed than admin session credentials) can trigger this by simply changing the `stack_id` query parameter. No special privilege beyond possessing one legitimately-scoped token is required.

### Recommendation
Change `Api::CCMenuController#stack` to resolve through the scoped `stacks` collection like every other API controller:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
and remove the private override, relying on the inherited scoped method from `Api::BaseController`.

### Proof of Concept
1. Provision (or have) an `ApiClient` with `stack_id` set to Stack A and permission `read:stack` only (as in the `here_come_the_walrus` fixture, or as created by `CCMenuUrlController`) [8](#0-7) .
2. Authenticate to `GET /api/:stack_id/ccmenu.xml` using that token's `authentication_token` but set `params[:stack_id]` to Stack B (a stack the client is not scoped to) — the existing test route/method matches `GET :show, params: { stack_id: @stack.to_param }` [10](#0-9) .
3. `authenticate_api_client` succeeds because it only validates the token itself [11](#0-10) ; `require_permission :read, :stack` succeeds because the client has that permission string; `stack` resolves Stack B directly via `Stack.from_param!`, bypassing the `stack_id` binding, and returns Stack B's CCMenu XML.
