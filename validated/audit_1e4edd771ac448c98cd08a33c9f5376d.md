## Analysis

This confirms the vulnerability: `Shipit::Api::CCMenuController` (`app/controllers/shipit/api/ccmenu_controller.rb`) overrides the `stack` accessor to resolve `Stack.from_param!(params[:stack_id])` directly against the entire `Stack` table, bypassing the `stacks` scoping helper defined in `BaseController` (`app/controllers/shipit/api/base_controller.rb:74-76`) that restricts lookups to `Stack.where(id: current_api_client.stack_id)` whenever the authenticated `ApiClient` is scoped to a single stack (`ApiClient#stack`, `app/models/shipit/api_client.rb:8`). `require_permission :read, :stack` only checks the string permission `"read:stack"` via `ApiClient#check_permissions!` (`app/models/shipit/api_client.rb:38-45`) — it never checks which `stack_id` the token is bound to.

Because `CCMenuUrlController#client` (`app/controllers/shipit/ccmenu_url_controller.rb:15-18`) provisions/reuses a shared `ApiClient` named `'CCMenu Client'` per user with `permissions: %w[read:stack]` and no `stack:` binding, and because `CCMenuController` doesn't scope by that binding anyway, any token with the generic `read:stack` permission — including one originally minted only to point at one stack's CCMenu URL — can be replayed with a different `stack_id` in the URL to read another stack's deploy/rollback status (`stack.deploys_and_rollbacks.last`), which discloses task/deploy state cross-stack. This is exactly the "a stack a token authorises versus a stack it touches" binding break called out in the rules.

### Title
Stack-scoped API token used to read CCMenu status of unauthorized stacks - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::Api::CCMenuController#stack` resolves the target stack via `Stack.from_param!(params[:stack_id])`, an unscoped lookup, instead of the `stacks.from_param!` helper used everywhere else in `Api::BaseController`. This breaks the binding between the stack an `ApiClient` token is authorized for (`ApiClient#stack_id`) and the stack whose deploy/rollback status is actually returned.

### Finding Description
`Api::BaseController` defines a `stacks` scope: `current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all` (`app/controllers/shipit/api/base_controller.rb:74-76`), and a `stack` helper built on top of it: `stacks.from_param!(params[:stack_id])` (`app/controllers/shipit/api/base_controller.rb:78-80`). This is the mechanism that enforces "this token may only touch the stack it was scoped to." [1](#0-0) 

`CCMenuController` overrides this helper:
```ruby
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end
``` [2](#0-1) 
which queries `Stack` directly, ignoring `current_api_client.stack_id`. The controller's authorization gate is only `require_permission :read, :stack` (`app/controllers/shipit/api/ccmenu_controller.rb:6`), and `ApiClient#check_permissions!` merely checks that the string `"read:stack"` is present in `permissions` — it has no notion of which specific stack the request targets. [3](#0-2) 

Compounding this, `CCMenuUrlController` mints/reuses a single shared `ApiClient` per user with `permissions: %w[read:stack]` and no `stack:` association at all (`find_or_create_by!(creator: current_user, name: 'CCMenu Client')`), so the token is not stack-scoped by construction either. [4](#0-3) 

The equality that should hold is: `stack the ApiClient token authorizes == stack whose data CCMenuController exposes`. Before the request: the token is only ever handed out embedded in a URL for one specific `stack_id`. After an attacker substitutes a different `stack_id` in the query string: the controller still authenticates the token successfully (permission check passes) and now returns data for the substituted stack — the equality is broken, mirroring the `OracleRouter` bug where ETH sent for one price update could be redirected to update a different market because the two operations (fund transfer, then price update) were not bound to each other.

### Impact Explanation
An attacker who obtains any valid CCMenu token (e.g. from a URL shared in chat/CI dashboards, browser history, referer leakage, or by requesting their own legitimately via `CCMenuUrlController#fetch` for a stack they can see) can reuse that same token against `GET /api/:stack_id/cc.xml` for arbitrary other stack identifiers, obtaining unauthenticated read of stack deploy/rollback status (`Task`/`Deploy` state, timing, running/success/failure) for any stack in the installation. This matches the "unauthenticated read of stack state, task streams or deploy output" High-severity criterion in the rules, since the requesting party never proved authorization for the target stack — only for whatever stack the token was originally scoped/intended for.

### Likelihood Explanation
Exploitation requires only possession of any valid `read:stack`-permissioned CCMenu (or similarly generic) token and knowledge/guessing of another stack's `stack_id` parameter (repository owner/name/environment strings, which are often predictable or discoverable via the public `Shipit::Api::StacksController#index`). No privileged session, GitHub credentials, or write access is needed — this is a pure authorization-scoping bug reachable by anyone who has ever been issued a CCMenu URL.

### Recommendation
Change `CCMenuController#stack` (and any other controller that overrides the `BaseController#stack`/`stacks` helpers) to resolve through the scoped `stacks` collection, e.g. `stacks.from_param!(params[:stack_id])`, so it respects `current_api_client.stack_id`. Additionally, consider binding the `ApiClient` created in `CCMenuUrlController#client` to the specific `stack` it is generated for (`stack:` association) rather than sharing one unscoped client per user across all stacks.

### Proof of Concept
1. As User A, visit `/shipit/:owner/:repo/:env` and trigger the CCMenu URL feature, which calls `CCMenuUrlController#fetch` and returns a URL like `https://shipit.example.com/api/owner/repo/env/cc.xml?token=<TOKEN>`.
2. Observe that `client` in `CCMenuUrlController` is a shared, unscoped `ApiClient` with only `permissions: ['read:stack']` — not tied to `owner/repo/env`. [5](#0-4) 
3. Take `<TOKEN>` and request `https://shipit.example.com/api/other-owner/other-repo/other-env/cc.xml?token=<TOKEN>` for a stack User A was never given access to.
4. `Api::CCMenuController#authenticate_api_client` authenticates the token, `require_permission :read, :stack` passes (permission string matches), and `stack` resolves the *other* stack directly via `Stack.from_param!`, returning that stack's deploy/rollback XML status. [6](#0-5)
