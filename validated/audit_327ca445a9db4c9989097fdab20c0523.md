## Finding

### Title
Decryption pipeline never checks ciphertext-to-sender binding, allowing encrypted-payload ciphertexts to be copied into attacker-controlled transactions and admitted to execution - (File: consensus/src/pipeline/decryption_pipeline_builder.rs)

### Summary
The encrypted-transaction feature (`EncryptedPayload`) defines a dedicated integrity check, `EncryptedPayload::verify(sender, signer_auth_keys)` [1](#0-0) , whose entire purpose is to confirm that a ciphertext was encrypted with associated data (`PayloadAssociatedData::V1 { sender, signer_auth_keys }`) tying it to the specific sender/signer set of the transaction that carries it. This function is never called anywhere in the actual decryption/admission path (`decrypt_validator_path` / `do_final_decryption` / `try_into_decrypted`) in `consensus/src/pipeline/decryption_pipeline_builder.rs`.

### Finding Description
`EncryptedInner` stores a `ciphertext`, `payload_hash`, `encryption_epoch`, and an optional `claimed_entry_fun`, all of which are protected only by the outer Ed25519 signature over the `RawTransaction` (via `as_encrypted_variant()` for signing) [2](#0-1) . That outer signature commits the sender to the ciphertext bytes and payload_hash, but the actual admission/decryption pipeline that turns a ciphertext into an executable transaction body only performs two checks in `try_into_decrypted`: that the SHA/crypto hash of the decrypted `DecryptedPlaintext { executable, decryption_nonce }` matches `payload_hash`, and that any `claimed_entry_fun` matches the decrypted executable's module/function [3](#0-2) .

Neither of these checks involves the sender address or the transaction's authenticated signer set. The dedicated binding primitive that was designed for this purpose — `EncryptedPayload::verify(sender, signer_auth_keys)`, which calls `self.ciphertext().verify(&associated_data)` — is defined but is not invoked from `decrypt_validator_path` in the consensus decryption pipeline [4](#0-3) [5](#0-4) . A repo-wide search shows `EncryptedPayload::verify`'s only references are its own definition and its unit tests in `types/src/transaction/encrypted_payload.rs`; it is dead code with respect to the live consensus decryption flow.

The consequence: the threshold-decryption key (`FPTXWeighted::decrypt`) is applied uniformly per-block to every ciphertext present in `EncryptedPayload::Encrypted` regardless of which `RawTransaction.sender` carries it. Because the sender-binding check is never exercised, an adversary observing a victim's encrypted, still-undecrypted transaction in a proposed block (ciphertexts are visible before decryption; only the plaintext is hidden) can copy the victim's `EncryptedInner { ciphertext, payload_hash, encryption_epoch, claimed_entry_fun }` verbatim into a new `RawTransaction` with the attacker's own `sender`, `sequence_number`, `gas_unit_price`, etc., sign it with the attacker's own key, and submit it. Since `try_into_decrypted` validates only `payload_hash`/`claimed_entry_fun` — both of which are copied unchanged along with the ciphertext — the copy decrypts successfully and is admitted into execution exactly as if it were bound to the attacker's transaction, even though the underlying encryption scheme provides an associated-data mechanism (`PayloadAssociatedData`) specifically to prevent this kind of cross-sender ciphertext reuse.

### Impact Explanation
This breaks the intended cryptographic binding between a confidential (encrypted) transaction body and the account/signer identity that is supposed to own it. It is a pre-validation/admission mismatch: a ciphertext that should fail admission (because it was never encrypted with associated data matching the new sender) is instead decrypted and executed, because the one check designed to catch this (`EncryptedPayload::verify`) is not wired into the pipeline. At minimum this permits front-running/duplication of another user's confidential transaction content (an attacker can force execution of another party's private payload attributed to the attacker's own sender/sequence-number binding, e.g. to grief or copy trading intents), and it undermines any correctness guarantee callers might rely on from `EncryptedPayload::verify` existing in the codebase at all. I was not able to fully verify, within the available tool budget, whether the lower-level `Ciphertext`/`FPTXWeighted` primitives independently enforce identity binding as part of decryption itself (i.e., whether `verify()` is a redundant sanity check or the sole enforcement point) — this materially affects real-world exploitability and should be confirmed by inspecting `crates/aptos-batch-encryption/src/shared/ciphertext/*` and `crates/aptos-batch-encryption/src/traits.rs`.

### Likelihood Explanation
Encrypted transactions and their ciphertexts must be broadcast/included in blocks before decryption (that is the entire point of the threshold-encryption mempool design), so an attacker with normal network visibility can observe and copy any pending encrypted ciphertext. Constructing and submitting a new `RawTransaction` with a copied `EncryptedInner` requires no privileged access — only standard transaction submission capability. The missing call is a straightforward code-path gap (absence of a call site), not a subtle cryptographic break, making it highly likely to be reachable by any unprivileged actor if the lower-layer scheme does not independently enforce the same binding.

### Recommendation
Invoke `EncryptedPayload::verify(sender, signer_auth_keys)` (or equivalent associated-data verification) against the actual `RawTransaction.sender` (and secondary/fee-payer signer set, if applicable) as part of `try_into_decrypted`/`decrypt_validator_path`, before or immediately after `do_final_decryption`, and reject with a new `DecryptionFailureReason` (e.g. `SenderBindingMismatch`) on failure. Add a regression test that copies an `EncryptedInner` from one signed transaction into a `RawTransaction` with a different sender and asserts decryption/admission fails.

### Proof of Concept
Conceptual PoC (cannot be executed without the full threshold-encryption test harness):
1. User A builds and submits an encrypted transaction: `EncryptedPayload::Encrypted(EncryptedInner { ciphertext, payload_hash, encryption_epoch, claimed_entry_fun })`, signed with A's key, `sender = A`.
2. Before the block's decryption key is released, attacker B observes A's `SignedTransaction` (ciphertext + payload_hash are plaintext-visible fields of the payload) in the block/mempool.
3. B constructs a new `RawTransaction` with `sender = B`, same `payload = TransactionPayload::EncryptedPayload(EncryptedPayload::Encrypted(<A's EncryptedInner, copied verbatim>))`, and signs it with B's own key.
4. B submits this transaction; it passes normal signature verification (`TransactionAuthenticator::verify`) since it is self-consistently signed by B.
5. In `decrypt_validator_path` → `try_into_decrypted` (`types/src/transaction/encrypted_payload.rs:199-235`), only `payload_hash` and `claimed_entry_fun` are checked against the decrypted plaintext; `EncryptedPayload::verify(sender, signer_auth_keys)` is never called, so B's copied ciphertext decrypts and is admitted for execution under B's sender binding, without ever validating that the ciphertext was actually encrypted for B.

    /// Verify the decrypted plaintext against the stored commitments and, on success,
    /// transition `self` to `Decrypted`. On mismatch, `self` is left as `Encrypted` and the
    /// failure reason is returned so the caller can mark the payload failed.
    pub fn try_into_decrypted(
        &mut self,
        eval_proof: EvalProof,
        plaintext: DecryptedPlaintext,
    ) -> Result<(), DecryptionFailureReason> {
        let Self::Encrypted(original) = self else {
            panic!("try_into_decrypted called on non-Encrypted state");
        };

        if original.payload_hash != CryptoHash::hash(&plaintext) {
            return Err(DecryptionFailureReason::PayloadHashMismatch);
        }

        if let Some(claim) = &original.claimed_entry_fun {
            let TransactionExecutable::EntryFunction(entry_fun) = plaintext.executable() else {
                return Err(DecryptionFailureReason::ClaimedEntryFunctionMismatch);
            };
            if *entry_fun.module() != claim.module {
                return Err(DecryptionFailureReason::ClaimedEntryFunctionMismatch);
            }
            if let Some(claimed_function_id) = &claim.function
                && entry_fun.function() != claimed_function_id.as_ident_str()
            {
                return Err(DecryptionFailureReason::ClaimedEntryFunctionMismatch);
            }
        }

        *self = Self::Decrypted {
            original: original.clone(),
            eval_proof,
            decrypted: plaintext,
        };
        Ok(())
    }
