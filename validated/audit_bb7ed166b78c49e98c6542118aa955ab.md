### Title
Unauthenticated Peer Can Inject Arbitrary StakingInfo During Recovery, Corrupting Reward Distribution — (`datasync/downloader/downloader.go`, `datasync/downloader/queue.go`)

---

### Summary

During a staking-info recovery session (`SyncStakingInfo`), any connected P2P peer can send a `StakingInfoMsg` whose content is written directly to the persistent staking-info database without (a) verifying that the responding peer is the one that was requested, or (b) validating that the content matches the canonical chain state. A malicious peer can therefore overwrite `RewardAddrs`, `StakingAmounts`, and treasury-fund addresses (`KEFAddr`/`KIFAddr`/`KPFAddr`) with arbitrary values, permanently redirecting KAIA block rewards and fund distributions.

---

### Finding Description

**Step 1 – Recovery is initiated.**
`SyncStakingInfo` (admin-level call) sets `d.isStakingInfoRecovery = true`, records the expected block numbers in `d.stakingInfoRecoveryBlocks`, and opens `d.stakingInfoRecoveryCh`. It then calls `conn.peer.RequestStakingInfo(blockHashes)` on the single trusted peer. [1](#0-0) 

**Step 2 – Any peer's response is accepted.**
`handleStakingInfoMsg` in the P2P handler decodes a `StakingInfoMsg` from *any* connected peer and passes it to `DeliverStakingInfos` with that peer's ID. [2](#0-1) 

`DeliverStakingInfos` then unconditionally forwards the payload to the recovery channel **without checking whether the sender is the recovery peer**: [3](#0-2) 

**Step 3 – Content is never validated.**
The recovery goroutine checks only that `stakingInfo.BlockNum` matches the next expected block number. It performs no cryptographic or state-derived check on the actual content (addresses, amounts): [4](#0-3) 

The queue-level `DeliverStakingInfos` also has an explicitly empty validator: [5](#0-4) 

**Step 4 – Fabricated data is persisted.**
`PutStakingInfoToDB` writes the peer-supplied struct directly to the key-value store with no further checks: [6](#0-5) 

The persisted `StakingInfo` fields that control reward distribution are: [7](#0-6) 

---

### Impact Explanation

`StakingInfo` is the authoritative source for every block's reward distribution before the Kaia hardfork. `FinalizeState` calls `GetStakingInfo` → reads from DB → distributes KAIA: [8](#0-7) 

A corrupted `StakingInfo` entry can:

- **Redirect validator rewards**: replacing `RewardAddrs` with attacker-controlled addresses causes all staker KAIA rewards for those blocks to be sent to the attacker.
- **Inflate staking amounts**: inflating `StakingAmounts` for one validator skews the proportional reward split across all stakers.
- **Redirect treasury funds**: replacing `KEFAddr`/`KIFAddr`/`KPFAddr` redirects the KEF/KIF/KPF portions of every block reward to attacker addresses.

The corruption is persistent (written to the DB) and silently affects every block that sources its `StakingInfo` from the poisoned entry.

---

### Likelihood Explanation

- **Trigger**: An admin must first call `SyncStakingInfo`. This is a legitimate recovery operation (e.g., after a node restart with missing staking DB entries). It is not an exotic or rarely-used path — the test `TestStakingInfoSync` confirms it is a supported production flow.
- **Attacker position**: Any peer connected to the node at the time of recovery can send a `StakingInfoMsg`. P2P peers are semi-trusted by design; no special privilege is required beyond being a connected peer.
- **Detection**: The write is silent — no event, no log at warn/error level on success, no on-chain trace. The corruption only becomes visible when rewards are distributed incorrectly.

---

### Recommendation

1. **Check peer identity in `DeliverStakingInfos`**: Before forwarding to `d.stakingInfoRecoveryCh`, verify that `id` matches the recovery peer's ID (`conn.peer` stored at recovery start).

2. **Validate content against canonical state**: After receiving staking info for block `N`, re-derive the expected `StakingInfo` from the local state trie (or at minimum verify a hash commitment) and reject any response that does not match.

3. **Remove the no-op validator**: Replace the `// TODO-Kaia-Snapsync update validation logic` stub in `queue.DeliverStakingInfos` with a real content check tied to the block's state root. [9](#0-8) 

---

### Proof of Concept

```
Setup:
  - Node A (victim) is running with WeightedRandom proposer policy.
  - Node B (trusted recovery peer) and Node C (malicious peer) are both connected to A.

Attack:
1. Admin on Node A calls SyncStakingInfo("B", 0, 86400).
   - d.isStakingInfoRecovery = true
   - d.stakingInfoRecoveryBlocks = [0, 86400, ...]
   - Node A sends StakingInfoRequestMsg to Node B.

2. Node C (malicious, also connected to A) sends a StakingInfoMsg containing:
   P2PStakingInfo{
     BlockNum:     0,                          // matches expected block
     RewardAddrs:  [attacker_address, ...],    // fabricated
     StakingAmounts: [999999999, ...],         // inflated
     KEFAddr:      attacker_address,           // fabricated
   }

3. handleStakingInfoMsg on Node A receives C's message and calls:
   pm.downloader.DeliverStakingInfos("C", fabricatedInfos)

4. DeliverStakingInfos sees d.isStakingInfoRecovery == true and sends
   fabricatedInfos to d.stakingInfoRecoveryCh (no peer ID check).

5. The recovery goroutine checks stakingInfo.BlockNum == 0 ✓ (matches),
   then calls:
   d.stakingModule.PutStakingInfoToDB(0, staking.ToStakingInfo(fabricatedInfo))

6. From this point, every block that sources StakingInfo from block 0
   distributes KAIA rewards to attacker_address instead of legitimate validators.
```

```go
// handleStakingInfoMsg handles staking information response message.
func handleStakingInfoMsg(pm *ProtocolManager, p Peer, msg p2p.Msg) error {
	if pm.chainconfig.Istanbul == nil || pm.chainconfig.Istanbul.ProposerPolicy != uint64(istanbul.WeightedRandom) {
		return errResp(ErrUnsupportedEnginePolicy, "the engine is not istanbul or the policy is not weighted random")
	}

	// A batch of stakingInfos arrived to one of our previous requests
	var stakingInfos []*staking.P2PStakingInfo
	if err := msg.Decode(&stakingInfos); err != nil {
		return errResp(ErrDecode, "msg %v: %v", msg, err)
	}
	// Deliver all to the downloader
	if err := pm.downloader.DeliverStakingInfos(p.GetID(), stakingInfos); err != nil {
		logger.Debug("Failed to deliver staking information", "err", err)
	}
	return nil
```
