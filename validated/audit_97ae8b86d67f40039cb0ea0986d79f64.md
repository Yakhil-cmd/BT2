### Title
Webhook signature verification keys off attacker-controlled `repository.owner.login`, but handlers dispatch on a different unchecked field (`repository.full_name`) - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to validate the HMAC signature against by reading `repository.owner.login` (or `organization.login`) straight out of the untrusted, not-yet-verified JSON body. Every downstream `Webhooks::Handlers::Handler` subclass instead resolves the target `Stack`/`Repository` using a *different* JSON field from the very same body, `repository.full_name`. Nothing enforces that these two attacker-supplied fields describe the same repository, so a valid signature computed with one organization's secret can be replayed to act on a completely different, unrelated repository's stack.

### Finding Description
`verify_signature` does:
```ruby
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
``` [1](#0-0) 
where
```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [2](#0-1) 

This is used purely to pick *which configured GitHub App's `webhook_secret`* is HMAC-compared against `request.raw_post` (Shipit supports multiple GitHub organizations, each with its own App/secret, per `config/secrets.development.example.yml`). Signature verification therefore proves "this body was signed with organization X's secret" - it says nothing about which repository the events inside the body claim to target.

Every handler that later processes the same parsed body, however, resolves its target repository independently via:
```ruby
def repository_name
  payload.dig('repository', 'full_name')
end

def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end
``` [3](#0-2) 

`PushHandler#process` [4](#0-3)  and `PullRequest::ClosedHandler#repository` [5](#0-4)  both act on this attacker-controlled `full_name`, which is never cross-checked against `repository.owner.login`/`organization.login` used for signature routing.

**The broken equality:** *organization that authenticated* (`repository_owner` used to fetch the signing secret) must equal *repository that is written* (`repository.full_name` used by handlers to locate the `Stack`/`Repository` acted upon). Nothing in `verify_signature` or in `Handler#stacks` enforces this. An attacker who legitimately controls one configured GitHub organization/App on a multi-tenant Shipit install (and thus legitimately knows that org's `webhook_secret`, since GitHub App owners see their own webhook secret) can craft a raw JSON body where:
- `repository.owner.login` = "attacker-org" (their own org, used only for signature routing)
- `repository.full_name` = "victim-org/victim-repo" (an unrelated stack hosted on the same Shipit instance)

Sign that body with `attacker-org`'s own known secret and POST it to `/webhooks`. `verify_signature` fetches `Shipit.github(organization: 'attacker-org')`, HMACs successfully, and passes. `create` then re-parses the same `raw_post` and dispatches `Shipit::Webhooks.for_event(event)` handlers using `repository.full_name`, acting on the victim's stack.

### Impact Explanation
Depending on which event/handler is exercised, this crosses into the Critical bucket of "cross-repository writes / an unauthorized deploy, rollback or merge":
- `PullRequest::ClosedHandler#process` calls `review_stack.archive!` on an arbitrary victim repository's review stack [6](#0-5) .
- `PushHandler#process` triggers `stack.sync_github(expected_head_sha:)` on arbitrary not-archived stacks matching an attacker-chosen branch, which can enqueue GitHub sync/continuous-deployment flows for a repository the attacker does not own [4](#0-3) .
- Other handlers (status, check_suite, membership) similarly key off `repository.full_name`/`organization.login` independently of the field used for signature routing, so team membership and commit-status-driven CI/deploy gating for an unrelated repository can be manipulated by an attacker who only controls their own org's webhook secret.

### Likelihood Explanation
This requires the Shipit deployment to be configured in the documented multi-organization mode (`config/secrets.development.example.yml` shows this exact pattern: multiple orgs, each with its own `webhook_secret`, all pointing at the same Shipit host). Any external party who is given ownership/admin of one configured GitHub organization/App on such a shared instance already knows that org's `webhook_secret` (it's shown to them in their own App settings) and can freely craft raw HTTP requests to `/webhooks` without ever needing a Shipit session, an `ApiClient` token, or write access to the victim repository - satisfying the "unprivileged attacker" bar for this multi-tenant scenario.

### Recommendation
Bind signature verification to the same repository identity the handlers actually act on:
- After computing `repository_owner`, also derive the org portion of `repository.full_name` and require they match before selecting/using a `github_app`.
- Alternatively, have `Handler#repository_name`/`#stacks` re-validate that `payload.dig('repository','owner','login')` (the field used for signature routing) is consistent with `payic.dig('repository','full_name')`, rejecting mismatched payloads.
- Longer term, avoid letting untrusted payload content choose which secret verifies its own signature at all; route by a value tied to the request context (e.g., the App/installation ID from a verified source) rather than a field taken from `params` before verification.

### Proof of Concept
1. Deployment configures two orgs in `secrets.yml`: `attacker-org` (attacker is a legitimate App owner there) and `victim-org` (hosts a Shipit-managed stack unrelated to attacker).
2. Attacker builds a `push` (or `pull_request`) JSON body:
   ```json
   {
     "ref": "refs/heads/master",
     "after": "<attacker-controlled sha>",
     "repository": {
       "owner": { "login": "attacker-org" },
       "full_name": "victim-org/victim-repo"
     }
   }
   ```
3. Attacker computes `X-Hub-Signature: sha1=HMAC(attacker-org's webhook_secret, body)` - a secret they legitimately possess.
4. POST to `/webhooks` with header `X-Github-Event: push`.
5. `verify_signature` looks up `Shipit.github(organization: 'attacker-org')`, HMAC succeeds, request proceeds [1](#0-0) .
6. `PushHandler` resolves `Repository.from_github_repo_name('victim-org/victim-repo')` and triggers `sync_github` on the victim's stack even though the signature never proved anything about `victim-org` [3](#0-2) , [4](#0-3) .
