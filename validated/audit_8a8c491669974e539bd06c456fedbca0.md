### Title
Webhook signature-verification key is selected from an unauthenticated payload field, decoupling the authorizing organization from the repository/stack the event actually mutates - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` picks the `GitHubApp`/`webhook_secret` used to validate `X-Hub-Signature` from a field taken out of the *same unverified JSON body* it is about to validate (`repository.owner.login`, falling back to `organization.login`). The handlers that actually act on the payload (`PushHandler`, `StatusHandler`, `CheckSuiteHandler`, `MembershipHandler`) resolve the target `Repository`/`Stack`/`Team` from a *different* field of that same body (`repository.full_name`, `sha`, `organization.login` used for `Team#organization`). In a single-org deployment these two fields always agree, so the bug is latent. In a **multi-org** configuration (`config/secrets.yml` with per-organization `github:` blocks, as documented in `docs/setup.md` and exercised by `test/dummy/config/secrets_double_github_app.yml`), the field used to select which org's `webhook_secret` authenticates the signature is independent of the field used to determine which stack/repository/team is mutated.

### Finding Description [1](#0-0) 

`verify_signature` calls `Shipit.github(organization: repository_owner)`, where `repository_owner` is: [2](#0-1) 

`Shipit.github(organization:)` looks up the `GitHubApp` (and thus `webhook_secret`) keyed by that organization name in a multi-org config: [3](#0-2) 

The handler base class, however, resolves the actually-affected `Repository`/`Stack` from `repository.full_name`, a sibling field independent of `repository.owner.login`: [4](#0-3) 

For the `membership` event, the acted-upon binding is even more direct — `Team#organization` is set straight from `params.organization.login`, a field that is not used at all by `verify_signature` when `repository` is present in the payload: [5](#0-4) 

The equality that is supposed to hold is:
`organization whose webhook_secret authenticated the request == organization/repository the handler subsequently mutates`

Because both sides are read from attacker-controlled JSON with no cryptographic linkage between them (the signature only proves *some* secret matching *an* org name derived from the body was used — it says nothing about which repository/organization fields elsewhere in that same body are legitimate), an operator running Shipit with multiple GitHub App configurations (a supported, documented topology — see `docs/setup.md:181-209` and `test/dummy/config/secrets_double_github_app.yml`) has no engine-level guarantee that a validly-signed webhook from Org A cannot carry a `repository.full_name`/`organization.login` pointing at Org B's stacks/teams.

### Impact Explanation
Exploiting this requires the ability to produce a validly-signed webhook for *some* organization configured on the instance (e.g. by legitimately triggering GitHub events for one's own installed org, or via the org's real webhook delivery). With that signature obtained, an attacker who controls the body of the delivered webhook (not typically possible against real GitHub-originated deliveries, since GitHub itself fills in `repository`/`organization` consistently) could, in principle, cause `PushHandler`/`StatusHandler`/`CheckSuiteHandler`/`MembershipHandler` to act on a `Stack`/`Team` belonging to a *different* organization on the same multi-tenant Shipit instance — triggering `GithubSyncJob` fetches, fabricating commit statuses (`StatusHandler` → `commit.create_status_from_github!`), or adding/removing team memberships (`MembershipHandler`) cross-tenant. This maps to the "escalation into `Shipit.github_teams` authorization" / unauthorized-state-mutation impact category, but only insofar as an attacker already possesses a legitimate signing capability for one org in the multi-tenant deployment — a scenario this engine's own webhook path does nothing to prevent for a *different* tenant's data.

### Likelihood Explanation
Low-to-moderate. This only matters in the multi-org configuration, which is an explicitly supported and documented mode of operation (not a misconfiguration of the host app). It requires the attacker to already be able to get a webhook delivered with a valid signature under *some* org's secret while fully controlling that request's body — GitHub's own webhook delivery mechanism populates `repository`/`organization` consistently from the real event, so the realistic exploitation path depends on an attacker's ability to relay/replay/craft a POST to `/webhooks` with a chosen body and a signature they can compute (i.e., they know one tenant's `webhook_secret`, which happens if they are the admin of their own GitHub App installation feeding this shared Shipit instance).

### Recommendation
Derive the signing-organization exclusively from a value that is *also* the one used downstream to select the mutated resource (e.g., always require `repository.full_name`, and derive the owner from that same field, rather than allowing an independent `organization.login` fallback to select the signing key while `repository.full_name` selects the mutated stack). For `membership`/organization-scoped events, verify the signature using the `organization.login` field the handler itself will use for authorization (`Team#organization`), not a `repository.owner.login` fallback path that can diverge from it. Consider verifying the signature against **every** configured organization's secret (not the one implied by the payload) so the payload cannot influence which secret is authoritative for verification.

### Proof of Concept
1. Deploy Shipit with a multi-org config containing `OrgA` and `OrgB` (as in `test/dummy/config/secrets_double_github_app.yml`).
2. Craft a `membership` webhook JSON body: `{"action":"added","team":{...},"organization":{"login":"OrgB"},"member":{"login":"attacker"},"repository":{"owner":{"login":"OrgA"}}}`.
3. Compute `X-Hub-Signature` with `OrgA`'s `webhook_secret` (known to the attacker as an admin of the App installed for OrgA).
4. `WebhooksController#verify_signature` calls `repository_owner` → `"OrgA"` (from `repository.owner.login`) → verifies successfully against OrgA's secret.
5. `MembershipHandler#process` then executes using `params.organization.login == "OrgB"`, creating/mutating a `Team` scoped to `OrgB` and adding the attacker as a member — despite the signature only proving control of `OrgA`. [6](#0-5) [7](#0-6)

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping

    end

    end

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

# frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class MembershipHandler < Handler
        params do
          requires :action, String
          requires :team do
            requires :id, Integer
            requires :name, String
            requires :slug, String
            requires :url, String
          end
          requires :organization do
            requires :login, String
          end
          requires :member do
            requires :login, String
          end
        end
        def process
          team = find_or_create_team!
          member = User.find_or_create_by_login!(params.member.login)

          case params.action
          when 'added'
            team.add_member(member)
          when 'removed'
            team.members.delete(member)
          else
            raise ArgumentError, "Don't know how to perform action: `#{action.inspect}`"
          end
        end

        private

        def find_or_create_team!
          Team.find_or_create_by!(github_id: params.team.id) do |team|
            team.github_team = params.team
            team.organization = params.organization.login
          end
        end
      end
    end
  end
end
