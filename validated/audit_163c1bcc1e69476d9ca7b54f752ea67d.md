### Title
Webhook signature check authenticates a different GitHub organization than the one whose repository/stack is acted upon - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks which GitHub App/organization secret to validate a webhook's HMAC signature against using `repository.owner.login` from the JSON body, but the code paths that actually act on the payload (e.g. `PushHandler`) key off a *different* field, `repository.full_name`, taken from the same attacker-supplied body. Nothing ties these two fields together, so the "organization that authenticated" and the "repository that is written" can diverge.

### Finding Description
`verify_signature` resolves the GitHub App config to use for HMAC verification purely from the request body: [1](#0-0) [2](#0-1) 

The signature is then checked with `GitHubApp#verify_webhook_signature`, which is a straightforward HMAC comparison keyed by that organization's `webhook_secret`: [3](#0-2) 

Critically, when no `webhook_secret` is configured for an organization — an explicitly documented, optional setting (`webhook_secret: # nil` in the example configs, "(optional)" in `docs/setup.md`) — `verify_webhook_signature` returns `true` unconditionally, i.e. verification is skipped entirely for that organization: [4](#0-3) [5](#0-4) 

Once `verify_signature` passes (either legitimately for that org, or trivially because that org's secret is unset), the handler dispatch uses a *different* JSON field to decide which repository/stack to act on: [6](#0-5) [7](#0-6) 

Because `repository.owner.login` (used to pick the verifying secret) and `repository.full_name` (used to pick the acted-upon `Repository`/`Stack`) are two independent keys inside the same attacker-controlled JSON body, an attacker who can produce a validly-signed payload for *any one* configured organization (including one with no `webhook_secret` set, which requires no secret knowledge at all) can set `repository.full_name` to point at a completely unrelated, victim-owned stack. `PushHandler` will then invoke `stack.sync_github(expected_head_sha: params.after)` on that victim stack, which enqueues `GithubSyncJob` and mutates stack state (appending commits, marking the stack accessible/inaccessible, forcing spec cache refresh) for a repository the attacker does not control: [8](#0-7) 

This is the same class of bug as the referenced finding: the code checks one binding (`isBLSPublicKeyPartOfLSDNetwork` / here, "is this HMAC valid for org X") but the actual guarded action operates on a different, unchecked binding (`isBLSPublicKeyBanned` / here, "is this the correct repository owned by org X").

### Impact Explanation
This breaks the equality that should hold: `organization whose secret verified signature == owner of the repository the handler writes to`. When it doesn't hold, an outside party can trigger cross-repository writes/state changes (stack sync, commit ingestion, accessibility flags, forced deploy-spec cache refresh) on stacks belonging to organizations other than the one they authenticated as — a "cross-repository writes" impact. In the worst case (an org configured without `webhook_secret`, which is a documented, valid, non-privileged configuration state), this requires *no* secret knowledge at all: a fully unauthenticated caller can forge `repository.owner.login` to match the secret-less org while setting `repository.full_name`/`ref`/`after` to target any other stack tracked by the Shipit instance.

### Likelihood Explanation
Likelihood depends on deployment configuration: it is highest in multi-organization Shipit deployments (an explicitly documented supported setup) where at least one configured organization has no `webhook_secret`, or where an attacker otherwise has legitimate access to one configured org's webhook secret. In either case no privileged Shipit session, API token, or repository write access is needed — only the ability to POST to the public `/webhooks` endpoint, which is unauthenticated by design (webhooks are meant to come from GitHub, secured only by the HMAC check this bug weakens).

### Recommendation
Bind the field used to select the verifying secret to the same field used to identify the acted-upon repository/stack. Concretely:
- Verify the signature using the organization actually resolved for the target repository (e.g. derive `repository_owner` from the same `full_name` used downstream, or re-validate that `repository.owner.login == repository.full_name.split('/').first`).
- Do not allow `verify_webhook_signature` to silently return `true` when `webhook_secret` is blank; instead, require an explicit `Shipit.disable_webhook_signature_verification` opt-in flag, or refuse to process webhooks for organizations without a configured secret.

### Proof of Concept
1. Configure Shipit with two organizations, e.g. `orgA` (attacker-controlled, `webhook_secret` unset/nil) and `orgB` (victim, tracked stacks exist for `orgB/victim-repo`).
2. POST to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "orgA" },
    "full_name": "orgB/victim-repo"
  }
}
```
No `X-Hub-Signature` value is required to be valid/known because `Shipit.github(organization: 'orgA').verify_webhook_signature` short-circuits to `true` when `orgA`'s `webhook_secret` is unset.
3. `WebhooksController#create` dispatches to `PushHandler`, which resolves `stacks` via `Repository.from_github_repo_name("orgB/victim-repo")` and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` on the victim's stack, enqueuing `GithubSyncJob` against a repository the attacker never controlled or authenticated for.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
# frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
    end
  end
end
```

```ruby
    def perform(params)
      @stack = Stack.find(params[:stack_id])
      expected_head_sha = params[:expected_head_sha]
      retry_count = params[:retry_count] || 0
      head_before_sync = spec_cache_target
      appended_commits = []

      handle_github_errors do
        new_commits, shared_parent = fetch_missing_commits { stack.github_commits }

        # Retry on Github eventual consistency: webhook indicated new commits but we found none
        if expected_head_sha && new_commits.empty? && !commit_exists?(expected_head_sha) &&
           retry_count < MAX_RETRY_ATTEMPTS
          GithubSyncJob.set(wait: RETRY_DELAY * retry_count).perform_later(params.merge(retry_count: retry_count + 1))
          return
        end

        stack.transaction do
          shared_parent&.detach_children!
          appended_commits = new_commits.map do |gh_commit|
            append_commit(gh_commit)
          end
          stack.lock_reverted_commits! if appended_commits.any?(&:revert?)
        end
      end
      sync_changed_nothing = appended_commits.empty? &&
                             spec_cache_target == head_before_sync &&
                             stack.cached_deploy_spec.present?
      return if sync_changed_nothing && !params[:force_spec_cache]

      CacheDeploySpecJob.perform_later(stack)
    end
```
