### Title
Cross-tenant commit status forgery via unscoped SHA lookup in `StatusHandler#process` enabling unauthorized deploy on another tenant's stack - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` resolves target commits with `Commit.where(sha: params.sha)`, which is not scoped to the repository/organization that authenticated the webhook via `verify_signature`. Any org B with a valid GitHub App installation and `webhook_secret` can post a `status` event for a sha that also exists as a `Commit` row belonging to a completely unrelated stack A (different tenant), causing that commit's status to be written and later evaluated by `Commit#deployable?`/`Stack#trigger_continuous_delivery`, resulting in an unauthorized deploy on stack A.

### Finding Description
Binding claimed broken: `organization(webhook_secret used to verify payload) == organization(repository.owner of Stack A that trigger_continuous_delivery deploys)`. Trace confirms this equality is never checked in code.

- `WebhooksController#verify_signature` derives the verifying org strictly from the *payload's own* `repository.owner.login` (`repository_owner`) and validates the signature against `Shipit.github(organization: repository_owner)`'s `webhook_secret`: [1](#0-0)  This only proves the payload was signed by org B (the sender), it says nothing about which `Commit` rows the handler will touch.
- `StatusHandler#process` then looks up commits purely by SHA, with zero relation to `repository_owner`, `payload['repository']`, or any `Stack`/`Repository` scoping: [2](#0-1)  The base `Handler` class does define a `stacks`/`repository_name` helper scoped to `payload.dig('repository', 'full_name')` [3](#0-2)  but `StatusHandler` does not use it — it queries `Commit` globally.
- `Commit#create_status_from_github!` / `add_status` then writes the forged status onto whatever commit(s) matched the SHA, regardless of which stack/tenant owns them: [4](#0-3) [5](#0-4) 
- `Commit#deployable?` evaluates purely from the attached status/lock state, with no tenant check: [6](#0-5) 
- Continuous delivery is periodically re-evaluated independent of the attacker's request via `Stack.schedule_continuous_delivery`, which enqueues `ContinuousDeliveryJob` for every `continuous_deployment: true` stack: [7](#0-6)  `Stack#trigger_continuous_delivery` then selects `next_commit_to_deploy` → `deployable_commits` → `commit.deployable?`, and if true, calls `trigger_deploy`: [8](#0-7) [9](#0-8) 

Exploit flow: attacker owns/installs a legitimate GitHub App for org B (self-service, unprivileged action) and thereby obtains a valid `webhook_secret` for B. Stack A (a different tenant with `continuous_deployment: true`) has a `Commit` row whose `sha` collides with one reachable in B — trivially true whenever A's repository shares commit history with B (e.g., B is a fork of A's repo, or both share an upstream commit), since raw SHA1 identity across repositories requires no "cracking," only identical git commit objects, which is a normal outcome of forking/cherry-picking. Attacker POSTs `X-Github-Event: status` with `repository.owner.login = B`, signed with B's secret, `sha: <colliding sha>`, `state: success`. `verify_signature` passes (correctly verifies B). `StatusHandler#process` finds and updates the matching `Commit` row that actually belongs to stack A, without checking that A's repository owner equals B. On the next continuous-delivery evaluation cycle, `Commit#deployable?` for that commit now returns true, and `Stack#trigger_continuous_delivery` deploys stack A using status data the attacker fabricated for an entirely different repository.

None of the listed guards close this gap: `verify_signature` verifies sender authenticity but not target-record scoping; `ExplicitParameters` (`ScopedParameters`) only validates the shape of `sha`/`state`, not repository ownership; there is no `require_permission!`/`stacks` scope applied inside `StatusHandler`.

### Impact Explanation
A payload authenticated for repository/org B causes a record write (a `Status`) on a `Commit` belonging to stack A's tenant, and can subsequently cause `Stack#trigger_deploy` to run for stack A — an unauthorized deploy triggered by a party with no relationship to A's tenant. This is a cross-tenant integrity/authorization break: "a payload for one repository mutating another's stack[/commit]" and "an unauthorized deploy," both explicitly in-scope Critical impacts. Blast radius is any stack across the whole Shipit instance with `continuous_deployment: true` whose commit history intersects (via fork/cherry-pick/shared upstream) with a repository the attacker controls — repeatable for every such colliding commit and every polling cycle.

### Likelihood Explanation
Preconditions: (1) attacker must control a repository/org B with a valid GitHub App installation (self-serve, unprivileged) yielding a `webhook_secret`, satisfying `verify_signature`; (2) victim stack A must have `continuous_deployment: true`; (3) a `Commit` row in A's history must have a SHA reachable by the attacker (fork, cherry-pick of a public/shared commit, or shared upstream dependency commit) — no cryptographic collision needed, just identical git object content, which is common for forks and vendored/cherry-picked commits. Attacker cost is low: one crafted HTTP POST to `/webhooks` per attempt, fully repeatable and scriptable, and not dependent on any secret belonging to Shipit or tenant A.

### Recommendation
Scope the `Commit` lookup in `StatusHandler#process` (and any other handler doing global SHA/ID lookups, e.g. check-run/PR handlers) to the repository that authenticated the payload — e.g. join through `Stack`/`Repository` using `payload.dig('repository', 'full_name')` (as `Handler#stacks`/`repository_name` already do) rather than a bare `Commit.where(sha: ...)`, so a webhook can only affect commits belonging to stacks whose repository matches the payload's `repository.full_name`.

### Proof of Concept
Minitest plan (no live GitHub):
1. Create `repository_a` (owner "tenant-a") with `stack_a` (`continuous_deployment: true`), and `commit_a` under `stack_a` with `sha: "deadbeef..." `.
2. Create `repository_b` (owner "tenant-b", attacker-controlled) with a valid stubbed `webhook_secret`/`GithubApp` for org "tenant-b".
3. POST to `/webhooks` with `X-Github-Event: status`, signed using tenant-b's secret, payload: `{ repository: { full_name: "tenant-b/repo", owner: { login: "tenant-b" } }, sha: commit_a.sha, state: "success" }`.
4. Assert response is 200 and `commit_a.reload.status.success?` is now `true` — proving cross-tenant status write despite the signature only authenticating tenant-b.
5. Assert on both sides of the equality: `repository_owner` from the verified payload == `"tenant-b"`, while `commit_a.stack.repository.owner` == `"tenant-a"` — they differ, proving the binding is broken.
6. Call/enqueue `Stack.schedule_continuous_delivery` (or directly invoke `stack_a.trigger_continuous_delivery`) and use `assert_enqueued_with(job: ContinuousDeliveryJob, args: [stack_a])` / perform the job, then assert `Deploy.count` increases for `stack_a`, confirming the forged, cross-tenant status led to an unauthorized deploy.

    def trigger_continuous_delivery
      return if cached_deploy_spec.blank?

      commit = next_commit_to_deploy

      if should_resume_continuous_delivery?(commit)
        continuous_delivery_resumed!
        return
      end

      if should_delay_continuous_delivery?(commit)
        continuous_delivery_delayed!
        return
      end

      begin
        trigger_deploy(commit, Shipit.user, env: cached_deploy_spec.default_deploy_env)
      rescue Task::ConcurrentTaskRunning
      end
    end

    def schedule_merges
      ProcessMergeRequestsJob.perform_later(self)
    end

    def next_commit_to_deploy
      commits_to_deploy = commits.order(id: :asc).newer_than(last_deployed_commit).reachable.preload(:statuses)
      if maximum_commits_per_deploy
        commits_with_max_applied = commits_to_deploy.limit(maximum_commits_per_deploy)
        deployable_commits(commits_with_max_applied) || deployable_commits(commits_to_deploy)
      else
        deployable_commits(commits_to_deploy)
      end
    end
