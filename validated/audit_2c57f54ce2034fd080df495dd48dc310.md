### Title
Flash-balance manipulation of OP-list (witness) vote counting via transient balance injection - ([File: main_chain.js])

### Summary
The vote-weighting mechanism for `op_list` (and other system parameters) in `countVotes()` weighs each voter's vote by that voter's **current** on-chain balance at the exact moment the vote is tallied (when the MCI containing a `system_vote_count` unit becomes stable), not by a balance held over any minimum period. Because `system_vote_count` can be triggered by any ordinary unit poster and balance can be moved into/out of a voting address with ordinary payment units, an attacker can transiently inflate an already-registered voter address's balance immediately before the vote tally executes, capture outsized voting weight for their preferred witness list, and then withdraw the funds right after — a "flash"/JIT manipulation of governance weight analogous to the JIT-liquidity sandwich-fee capture described in the report.

### Finding Description
`countVotes()` in `main_chain.js` computes, for every address that has ever cast a `system_vote` for a subject, a `voter_balances` snapshot built from **currently stable, unspent, good-sequence outputs**: [1](#0-0) 

This balance is computed fresh every time `countVotes` runs — i.e. every time a `system_vote_count` unit for that subject stabilizes: [2](#0-1) 

For the `op_list` subject, the final winning witness set is chosen strictly by summing this instantaneous balance across each voter's most recently cast `op_address` votes and taking the top `COUNT_WITNESSES` by total balance: [3](#0-2) 

Only the *vote's timestamp* is constrained by a lookback window (`since_timestamp`) to decide which historical votes are eligible; the *balance* used to weight an eligible vote is always the balance held right now, with no requirement that the balance existed at the time the vote was cast or for any minimum duration: [4](#0-3) 

The trigger for a vote count, `system_vote_count`, is a message any regular (non-AA) unit author is permitted to attach to a unit, once per unit, without any special privilege: [5](#0-4) 

Consequently, an attacker who has previously cast a cheap `system_vote` for `op_list` from address A (choosing their own preferred witness set) can, at any later time:
1. Send a large amount of bytes to address A (a normal payment unit).
2. Post (or wait for someone else to post) a `system_vote_count` unit for `op_list`.
3. As soon as the MCI containing that unit stabilizes, `countVotes` reads A's now-inflated current balance and counts it fully toward A's chosen OP list.
4. Once the tally is written to `system_vars`, move the funds out of A again (another ordinary payment).

This is structurally the same bug class as the reported `AntiSandwichHook` JIT-liquidity issue: a distribution/decision outcome that is supposed to reflect economically committed stake instead uses a **snapshot of transient, freely and cheaply adjustable state at the exact moment of settlement**, letting an attacker briefly acquire outsized "share" purely to bias the outcome and then discard the position at negligible cost.

### Impact Explanation
The `op_list` vote determines the network's witness set (Order Providers), which underlies main-chain selection, unit stability determination, and thus finality of every transaction on the DAG. An attacker able to bias this vote with only transiently-held funds could:
- Install witnesses they control (or collude with) into the OP list, undermining the assumption that OP selection reflects real, sustained economic stake in the network.
- Use control (or partial control) over the witness list to influence which units become part of the main chain and how quickly units stabilize, creating a path toward network-wide disagreement on validity/stability of units, or degraded ability of the network to reach stable finality on new units if the witness set is captured by an uncooperative/malicious set.

This is a Medium/High severity governance-integrity issue: it does not require any special privilege — only permissionless unit posting (a `system_vote`, a payment, and a `system_vote_count`) — and directly undermines the security assumption that OP list changes require sustained, real economic backing rather than instantaneous, reversible balance.

### Likelihood Explanation
The attack requires no privileged access — only the ability to post units, which is available to any regular ocore participant. Casting an initial `system_vote` is cheap and can be done well in advance. The only real cost is the temporary capital needed to make the target address's balance dominate the total voted balance for the desired outcome, and this capital is fully returned to the attacker immediately after the tally (only network fees are lost). The `since_timestamp` lookback window governs which *votes* are eligible but does nothing to prevent balance itself from being manipulated right before the count executes, so likelihood is driven mainly by the attacker's ability to acquire a large (even momentarily) bytes balance and time a `system_vote_count` unit's stabilization — both of which are attacker-controlled.

### Recommendation
Weight votes by a balance snapshot that cannot be manipulated within a short window before the count, for example:
- Use the voter's balance as of a **fixed historical MCI** (e.g., balance at `last_ball_mci` of the vote-casting unit itself, or balance some fixed number of MCIs prior to the counting MCI) rather than the balance at the instant of tallying.
- Require a minimum holding/aging period for outputs to count toward vote weight (similar to `EMERGENCY_COUNT_MIN_VOTE_AGE` already used for vote timestamps, but applied to the underlying balance/UTXOs rather than to the vote message).
- Alternatively, average balance over a window preceding the count, rather than taking an instantaneous snapshot.

### Proof of Concept
1. Address A casts `system_vote` `{subject: "op_list", value: [attacker-controlled OP set]}` in a low-value unit; this is recorded permanently in `system_votes`/`op_votes` (see `saveSystemVote`, `main_chain.js:1619-1651`).
2. At any later time, attacker sends a large payment of bytes to address A in a normal payment unit and lets it become stable.
3. Attacker (or anyone) posts a unit containing `system_vote_count` for subject `op_list`; per `validation.js:1913-1923` this requires no special privilege.
4. When the MCI containing that unit stabilizes, `countVotes` (`main_chain.js:1737-1913`) computes A's balance via the query at `main_chain.js:1757-1777`, which reflects the just-received large balance, and sums it into A's chosen OP addresses (`main_chain.js:1850-1863`), potentially tipping the top-12 selection in the attacker's favor.
5. After `system_vars.op_list` is updated, attacker moves the funds out of address A in a subsequent payment unit, recovering essentially all capital (minus fees) while having biased the OP list outcome.
