### Title
`TaskCommands#steps` executes attacker-controlled `shipit.yml` steps from a review-stack branch with no re-check of `repository.review_stacks_enabled` at task-execution time - ([File: lib/shipit/task_commands.rb])

### Summary
`TaskCommands#steps` (`lib/shipit/task_commands.rb:29-31`) returns `@task.definition.steps` sourced from `DeploySpec::FileSystem` reading `shipit.yml` off the stack's own `branch`, with no gate on `repository.review_stacks_enabled`. This binding gap is real, but it is only reachable because the review stack can be *created* in the first place while `review_stacks_enabled` is `false`, due to an operator-precedence bug in `respond_to_pull_request_opened?`/`provision?`.

### Finding Description
The claimed binding — "`repository.review_stacks_enabled == true` must hold for any `Command` built from that stack's `shipit.yml` to execute" — is **not enforced anywhere in the reachable code**, confirming half of the question. `TaskCommands#steps` at [1](#0-0)  simply returns `@task.definition.steps`, and `#perform` at [2](#0-1)  turns each into a `Command` with no re-check of `review_stacks_enabled`. `deploy_spec` is built straight from `DeploySpec::FileSystem.new(@task.working_directory, @stack)` [3](#0-2) , and `DeploySpec::FileSystem` loads `shipit.yml`/task definitions purely from files checked out from the stack's `branch`, via `config_file_path`/`load_config`/`task_definitions` [4](#0-3)  and [5](#0-4) . `ReviewStackCommands` is a bare subclass of `StackCommands` with no additional guard [6](#0-5) .

However, whether this is exploitable depends entirely on whether a review stack can exist for a repository with `review_stacks_enabled == false`. Tracing `OpenedHandler`, I found a genuine precedence bug: `provision?` is `repository.review_stacks_enabled && repository.provisioning_behavior_allow_all? || (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) || (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)` [7](#0-6) . Because `&&` binds tighter than `||`, `review_stacks_enabled` is only ANDed into the `allow_all` branch — the `allow_with_label` and `prevent_with_label` branches are **not gated by `review_stacks_enabled` at all**. The same pattern repeats in `ReopenedHandler#unarchive?` [8](#0-7) . So if an operator sets `provisioning_behavior` to `allow_with_label` or `prevent_with_label` while leaving/toggling `review_stacks_enabled` to `false`, an unprivileged PR author from a fork can still trigger stack creation (by adding/omitting the provisioning label), and the resulting review stack fetches `shipit.yml` from the attacker's own branch, whose steps are later executed unconditionally by `TaskCommands#steps`/`Command#start`.

By contrast, `LabeledHandler` (archive/unarchive on label events) *does* correctly AND `review_stacks_enabled` into its top-level guard `respond_to_label_change?` [9](#0-8) , so that path is not affected.

### Impact Explanation
If reached, this results in RCE on the deploy host: attacker-controlled `deploy`/`task` steps from `shipit.yml` are passed to `Command`, which is ultimately spawned via `PTY.spawn` in `lib/shipit/command.rb`. This is scoped to the specific misconfigured repository (one where `provisioning_behavior` is `allow_with_label`/`prevent_with_label` and `review_stacks_enabled` is `false`) — it is not a cross-tenant issue by itself, but within that repository it is fully repeatable for any PR the attacker (or any external contributor) opens, and indefinitely repeatable for every subsequent task/deploy on that stack since `TaskCommands` never re-validates the flag once the stack exists.

### Likelihood Explanation
Exploitability requires a specific, non-default repository configuration: `provisioning_behavior` set to `allow_with_label` or `prevent_with_label` while `review_stacks_enabled` is `false` (or toggled off after being on). This is an unusual, arguably contradictory admin configuration — an operator who unchecks "Dynamically provision stacks for Pull Requests?" would reasonably expect no review stacks to be provisioned regardless of the provisioning-behavior dropdown. The question's proof idea (creating a stack via the precedence bug, then flipping `review_stacks_enabled` off and confirming `TaskCommands` still runs the steps) is consistent with what I found in code, though I was not able to fully verify with a live test run whether any other higher-level gate (e.g., in a controller or job that dispatches tasks) independently blocks this before reaching `TaskCommands`— I did not find one in `app/models/shipit/task.rb` or elsewhere, but the review-stack precedence bug itself (`opened_handler.rb`/`reopened_handler.rb`) is the actual root cause enabling the divergence, not `TaskCommands` in isolation.

### Recommendation
1. Fix operator precedence in `provision?` (`opened_handler.rb`) and `unarchive?` (`reopened_handler.rb`) by parenthesizing so `repository.review_stacks_enabled` gates **all** branches: `repository.review_stacks_enabled && (allow_all? || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?))`.
2. Defense-in-depth: add an explicit `repository.review_stacks_enabled` check inside `TaskCommands#steps`/`#perform` (or in `ReviewStackCommands`) for stacks that are review stacks, so that disabling the flag on a repository immediately halts execution of steps for any existing review stack, regardless of how it was created.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb`-style, plus `test/lib/shipit/task_commands_test.rb`):
1. Create a repository, set `provisioning_behavior: :allow_with_label`, `provisioning_label_name: "deploy-me"`, `review_stacks_enabled: false`.
2. Send a `pull_request` "opened" webhook payload whose `labels` include `"deploy-me"`.
3. Assert: `Shipit::Stack.count` increases by 1 (stack created despite `review_stacks_enabled == false`) — proving `repository.review_stacks_enabled == false` while a review stack now exists (breaking the equality `repository.review_stacks_enabled == true` required for provisioning).
4. On the created stack/task, checkout a `shipit.yml` with an attacker-chosen `deploy: { override: ["echo pwned"] }`.
5. Build `TaskCommands.new(task).steps` (or `#perform`) and assert it returns `["echo pwned"]` / a `Command` wrapping it, with `repository.reload.review_stacks_enabled == false` asserted immediately before, demonstrating the binding "`review_stacks_enabled == true` required for step execution" does not hold.
