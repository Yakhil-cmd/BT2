### Title
Webhook signature is verified against the organization derived from `repository.owner.login`, while every event handler acts on the independent, unchecked `repository.full_name` field — allowing a holder of one organization's webhook secret to write to another organization's repositories/stacks - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` authenticates a webhook delivery by looking up the per-organization `webhook_secret` for whatever value appears in `repository.owner.login` (or `organization.login`) inside the JSON body, and HMAC-validating the raw payload against that secret. Every webhook handler, however, decides *which repository/stack to act on* using a completely different, equally attacker-controlled field of the same JSON body: `repository.full_name`. Nothing ties these two values together, so proving knowledge of Org A's `webhook_secret` only proves the request came from someone who can sign for Org A — it does not prove the payload actually concerns an Org A repository.

Because `repository.owner.login` and `repository.full_name` are two independent, attacker-supplied keys within the same JSON body that the HMAC merely certifies "was produced/known by whoever has Org A's secret," an attacker who legitimately controls a webhook secret for one Shipit-registered organization (Org A) can submit a JSON body where `repository.owner.login = "OrgA"` (so signature verification passes) but `repository.full_name = "OrgB/some-repo"`. Shipit supports and documents multiple independently-configured GitHub organizations sharing one instance (`config/secrets.development.shopify.yml`, CHANGELOG "Support multiple GitHub organisations (#1151)"), so this cross-org condition is a realistic deployment configuration, not a hypothetical.

### Impact Explanation
Once the forged payload passes `verify_signature`, it is dispatched to every handler registered for that event type, and those handlers operate on Org B's actual `Repository`/`Stack` records using attacker-controlled sub-fields of the payload:

- `PullRequest::OpenedHandler` → `ReviewStackAdapter#find_or_create!`, which persists a new `Stack` scoped to Org B's repository using attacker-controlled `pull_request.head.ref` and enqueues it for provisioning: [6](#0-5) 
- `PullRequest::LabeledHandler`/`UnlabeledHandler`/`ReopenedHandler`/`ClosedHandler` can archive, unarchive, or otherwise change the state of Org B's review stacks based on attacker-chosen label/action fields.

Provisioning a review stack runs Org B's `shipit.yml` steps on the shared deploy host against attacker-chosen ref/sha data taken from the forged payload. This is a cross-repository write against a repository the attacker does not administer, and, because provisioning executes shell commands from that repository's own deploy configuration, it can lead to execution against Org B's infrastructure/credentials that the attacker never had rights to touch. This satisfies the "Critical" bar (cross-repository writes / unauthorized deploy, potential RCE on the deploy host) defined by the assignment.

### Likelihood Explanation
Exploitation requires only that the attacker legitimately control the `webhook_secret` of *any* organization configured on the shared Shipit instance (e.g., their own low-privilege org, if the deployment hosts multiple orgs, as explicitly supported and documented). No access to Org B, no `ApiClient` token, and no GitHub App private key for Org B is required — the attacker crafts and POSTs the JSON body directly to `/webhooks` with a valid `X-Hub-Signature` computed from their own org's secret. This is a realistic misconfiguration risk for any multi-tenant Shipit deployment, which the project explicitly advertises support for.

### Recommendation
After signature verification succeeds, `WebhooksController`/`Handler` must additionally assert that the organization used to verify the signature (`repository_owner`) matches the owner segment of `repository.full_name` (and of any other repository identifiers consumed by handlers) before dispatching to handlers, rejecting the event (e.g., `head(422)`) on mismatch.

### Proof of Concept
1. Shipit is configured with two organizations, `OrgA` and `OrgB`, each with its own `webhook_secret` (as supported natively).
2. Attacker administers a webhook for `OrgA` (e.g., they own/administer that low-privilege org) and thus knows `OrgA`'s `webhook_secret`.
3. Attacker crafts a `pull_request` `opened` event JSON body where:
   - `repository.owner.login = "OrgA"`
   - `repository.full_name = "OrgB/victim-repo"`
   - `pull_request.head.ref` = attacker-chosen branch name
4. Attacker computes `X-Hub-Signature` over the raw body using `OrgA`'s `webhook_secret` and POSTs to `/webhooks` with `X-Github-Event: pull_request`.
5. `WebhooksController#verify_signature` resolves `Shipit.github(organization: "OrgA")` and validates successfully.
6. `PullRequest::OpenedHandler` resolves `repository` via `Repository.from_github_repo_name("OrgB/victim-repo")` and, if review stacks are enabled for that repository, creates and provisions a new review stack for `OrgB`'s repository based on the attacker-controlled branch — a write to an organization the attacker never proved control of.

      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
