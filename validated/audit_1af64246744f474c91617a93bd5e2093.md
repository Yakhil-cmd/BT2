This confirms the pattern used by other handlers (`PushHandler#process` scopes work via `stacks`, which resolves `Repository.from_github_repo_name(repository_name)&.stacks`), whereas `StatusHandler#process` bypasses this entirely and queries `Commit.where(sha: params.sha)` globally across all stacks/repositories/orgs.### Title
`StatusHandler` mutates Commit/Status records across arbitrary stacks regardless of which org's webhook signature authenticated the request - (`app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` looks up commits with `Commit.where(sha: params.sha)` with no scoping to the repository/stack that the authenticated organization owns, unlike every other handler which resolves work through `Handler#stacks` (`Repository.from_github_repo_name(repository_name)&.stacks`). Because `Commit` is only unique per `(stack_id, sha)` (not globally), an attacker who can get a valid signature for *any* org configured in Shipit can forge a `status` webhook naming a commit sha that belongs to a completely different repository/org and mutate that unrelated commit's status.

### Finding Description
The claimed identity binding is: `authenticated_org (from repository.owner.login used in verify_signature) == data_owner_org (the org whose Commit/Stack row gets written)`.

Trace:
- `WebhooksController#verify_signature` derives `repository_owner` purely from `params.dig('repository','owner','login')` (attacker-controlled JSON) and calls `Shipit.github(organization: repository_owner)` to pick which `webhook_secret` to verify against [1](#0-0) , [2](#0-1) .
- Once the signature verifies for *that* org, `Shipit::Webhooks.for_event('status')` dispatches the full raw JSON body to `StatusHandler.call(params)` [3](#0-2) [4](#0-3) .
- `StatusHandler` schema only requires `sha`/`state`; it never requires or reads `repository` [5](#0-4) .
- `StatusHandler#process` performs `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` — a global, unscoped lookup [6](#0-5) .
- Contrast with `Handler#stacks`, used by `PushHandler` and others, which resolves work strictly through `Repository.from_github_repo_name(repository_name)&.stacks` [7](#0-6) , [8](#0-7) . `StatusHandler` opts out of this scoping entirely.
- `Commit` uniqueness is enforced only on `(sha, stack_id)`, confirming the same sha can legitimately exist for different stacks/repos/orgs simultaneously [9](#0-8) .

So the two sides of the equality diverge: the org that supplied a valid HMAC (`repository.owner.login` in the request body, used only for secret lookup) has no relationship enforced with the org that actually owns the `Commit` row being written, because `process` never consults `repository_name`/`stacks` at all.

Existing guards do not close this gap:
- `verify_signature` only proves "this body was signed by webhook_secret for org X"; it says nothing about which repository's data the body is permitted to touch.
- `drop_unhandled_event` and the `ExplicitParameters` schema (`requires :sha, :state`) do not require or validate `repository`.
- `Repository`/`Stack` model validations never run here because the vulnerable code path never touches `Repository.from_github_repo_name`.

### Impact Explanation
An attacker who controls (or is a legitimate low-privilege member/webhook of) one org onboarded to a multi-tenant Shipit install can forge a `status` event whose `sha` belongs to a commit in a totally different org/stack, flipping that commit's `state` (e.g., to `success`) via `Commit#create_status_from_github!` → `Status.replicate_from_github!` [10](#0-9) . A fabricated `success` transition triggers `schedule_continuous_delivery` and `ProcessMergeRequestsJob`, which can drive auto-merge/deploy decision logic for the victim stack based on a fake CI signal [11](#0-10) . This is a payload for one repository mutating another repository's Commit/Stack data and potentially triggering an unauthorized deploy decision — matching the Critical category ("a payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy"). It is fully repeatable against any commit sha the attacker knows (commit shas of target repos are frequently public/observable), across any number of unrelated stacks, from a single authenticated org's webhook credential.

### Likelihood Explanation
Requires the attacker to hold valid signing capability for at least one org known to `Shipit.github(organization:)` (their own org in a multi-tenant Shipit install, or trivially satisfied if the installation's `webhook_secret` is left unset, which the docs list as optional) [12](#0-11) . No Shipit session, API token, or maintainer role on the victim repo is needed. The only extra piece of information needed is the target commit's SHA, typically public. This makes the attack cheap and repeatable per request against arbitrary victim stacks in the same Shipit instance.

### Recommendation
Scope `StatusHandler#process` the same way as `PushHandler`/`Handler#stacks`: resolve the repository from the authenticated payload's `repository.full_name`, obtain its `stacks`, and only update commits belonging to those stacks (e.g., `stacks.flat_map(&:commits).where(sha: params.sha)` or add a `belongs_to`-scoped query keyed on the resolved `Repository`/`Stack`), rejecting/no-op if the repository isn't present or doesn't match.

### Proof of Concept
Minitest plan (`test/controllers/webhooks_controller_test.rb`):
1. Set up two stacks/orgs in fixtures: `shipit` (victim, org `shopify`) and a second org e.g. `cyclimse` that the attacker controls and for which `GithubHook`/webhook signature is stubbed to verify (`GithubHook.any_instance.stubs(:verify_signature).returns(true)` as already done in setup, or by using `repository_params` for `cyclimse`).
2. Take `commit = shipit_commits(:first)` (belongs to stack `shipit`, org `shopify`).
3. POST a `status` event with `X-Github-Event: status`, body `{ sha: commit.sha, state: 'success' }.merge(repository: { full_name: 'attacker/cyclimse-repo', owner: { login: 'cyclimse' } })`.
4. Assert `Shipit.github(organization: 'cyclimse')` signature check passes (stubbed as legitimate for attacker's own org) — i.e., the request is authenticated as `cyclimse`, not `shopify`.
5. Assert before: `commit.statuses.count == 0`.
6. Assert after `post :create`: `commit.reload.statuses.count == 1` and `commit.state == 'success'`, proving a payload authenticated by `cyclimse`'s credentials mutated a `shopify`-owned commit — i.e., `authenticated_org ('cyclimse') != data_owner_org ('shopify')` yet the write succeeded.
