### Title
API Client cryptographic authentication does not bind the `X-Shipit-User` actor identity, enabling user impersonation for deploys, rollbacks, task triggers, and locks - (File: app/controllers/shipit/api/base_controller.rb)

### Summary
`Shipit::Api::BaseController` authenticates the *request* via a cryptographically signed `ApiClient` token (`ApiClient.authenticate`), which is verified with `Shipit::SimpleMessageVerifier` and scoped to a specific `stack_id` and `permissions`. However, the identity used to attribute and authorize the *action* — the acting `User` recorded as deploy/task/rollback/lock initiator — is taken from the unauthenticated `X-Shipit-User` request header and is never covered by that signature. Any holder of a valid API token can set this header to impersonate any existing Shipit user (including privileged users) when triggering deploys, rollbacks, tasks, or locks. [1](#0-0) 

### Finding Description
`authenticate_api_client` verifies the `ApiClient` token via HMAC (`Shipit::SimpleMessageVerifier`), establishing which `ApiClient` (and thus which stack scope and `permissions`) is authorized: [2](#0-1) [3](#0-2) 

Separately, `current_user` — the identity attributed to the action performed through this authenticated channel — is derived from `identify_user`, which trusts the plain, unsigned `X-Shipit-User` header and looks up any `User` by login: [4](#0-3) 

This is structurally the same class of bug as the reported issue: a value that is *acted upon* (here, the acting user identity used for authorization/attribution) is never covered by the verification step that establishes trust (here, the signed API token). The equality that should hold is:

`identity authenticated by the verified ApiClient token == identity attributed to the resulting action`

but instead the engine allows:

`identity authenticated by the verified ApiClient token != current_user used for the action (attacker-supplied via X-Shipit-User)`

This attacker-controlled `current_user` then flows directly into privileged operations:
- Task trigger/abort: `stack.trigger_task(params[:task_name], current_user, ...)`, `task.abort!(aborted_by: current_user)` [5](#0-4) 
- Deploy creation: `stack.trigger_deploy(commit, current_user, ...)` [6](#0-5) 
- Rollback / abort-and-rollback: `active_task.abort!(aborted_by: current_user, ...)`, `deploy.trigger_rollback(current_user, ...)` [7](#0-6) 
- Stack lock: `stack.lock(params.reason, current_user)` [8](#0-7) 

The permission check (`require_permission`) only verifies that the *ApiClient* has the operation/scope permission (e.g. `deploy:stack`), not that the impersonated `User` is authorized or even a member of `Shipit.github_teams`: [9](#0-8) [10](#0-9) 

By contrast, the interactive web session path correctly binds the authenticated identity to a signed, server-side session value (`session[:user_id]`) which cannot be forged by the client: [11](#0-10) 

### Impact Explanation
Any legitimate holder of a scoped API token (e.g. a CI system with `deploy:stack` permission on one stack) can forge the `X-Shipit-User` header to attribute deploys, rollbacks, task executions, and lock actions to an arbitrary existing Shipit `User` — including administrators or specific engineers — without that user's consent or knowledge. This breaks audit trails (`SHIPIT_USER` env var, `aborted_by`, commit "merge requested by" attribution) and can be leveraged to trigger an unauthorized deploy/rollback that appears to originate from a trusted identity, satisfying the "unauthorized deploy, rollback" criteria for High/Critical impact.

### Likelihood Explanation
Exploitation requires only a valid `ApiClient` token with permission for the targeted operation (`deploy:stack`, `lock:stack`, etc.) — no special privilege beyond what the token grants is needed to set an arbitrary `X-Shipit-User` value, since `identify_user` performs no validation that the header corresponds to the token holder. Any integration or script possessing a scoped token (which is common for CI systems interacting with Shipit's API) can trivially perform this impersonation.

### Recommendation
Do not derive the acting `User` from an unauthenticated, client-supplied header. Either: (a) bind API clients to a fixed `creator`/actor and use `current_api_client.creator` for attribution instead of `X-Shipit-User`, or (b) if per-request actor attribution is required, require it to be cryptographically bound to the token (e.g., signed alongside the API token or validated against a list of users the token is explicitly permitted to act as), and reject requests where the acting user cannot be verified.

### Proof of Concept
1. Obtain a valid API client token scoped to stack `S` with `deploy:stack` permission (e.g. a CI token intended only to trigger routine deploys).
2. Issue: `POST /api/stacks/S/deploys` with `Authorization: Basic <token>` and header `X-Shipit-User: admin-login`, body `{"sha": "<sha>"}`.
3. Observe in `app/controllers/shipit/api/deploys_controller.rb#create` that `stack.trigger_deploy(commit, current_user, ...)` is invoked with `current_user` resolved to the `admin-login` `User` record purely from the header, per `identify_user` in `app/controllers/shipit/api/base_controller.rb`, producing a deploy record attributed to `admin-login` despite the request never being authenticated as that user.

      def authenticate_api_client
        @current_api_client = if Shipit.disable_api_authentication
                                UnlimitedApiClient.new
                              else
                                BasicAuth.authenticate(request) do |*parts|
                                  token = parts.select(&:present?).join('--')
                                  ApiClient.authenticate(token)
                                end
                              end
        return if @current_api_client

        headers['WWW-Authenticate'] = 'Basic realm="Authentication token"'
        render(status: :unauthorized, json: { message: 'Bad credentials' })
      end

      attr_reader :current_api_client

      def current_user
        @current_user ||= identify_user || AnonymousUser.new
      end

      def identify_user
        user_login = request.headers['X-Shipit-User'].presence
        User.where('lower(login) = ?', user_login.downcase).first if user_login
      end

      def create
        commit = stack.commits.by_sha(params.sha) || param_error!(:sha, 'Unknown revision')
        param_error!(:force, "Can't rollback a locked stack") if !params.force && stack.locked?
        deploy = stack.deploys.find_by(until_commit: commit) || param_error!(:sha, 'Cant find associated deploy')
        rollback_env = stack.filter_rollback_envs(params.env)

        response = nil
        if !params.force && stack.active_task?
          param_error!(:force, "Can't rollback, deploy in progress")
        elsif stack.active_task?
          active_task = stack.active_task
          active_task.abort!(aborted_by: current_user, rollback_once_aborted_to: deploy, rollback_once_aborted: true)
          response = active_task
        else
          response = deploy.trigger_rollback(current_user, env: rollback_env, force: params.force, lock: params.lock)
        end

        render_resource(response, status: :accepted)
      end
