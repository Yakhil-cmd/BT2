### Title
Webhook signature is verified against `repository.owner.login`/`organization.login` while handlers act on the unrelated `repository.full_name`, letting a forged payload trigger syncs/status/check-run updates for any tracked repository - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects the signing secret to validate `X-Hub-Signature` using `repository_owner`, i.e. `params.dig('repository','owner','login')` or the fallback `params.dig('organization','login')`. Every event handler, however, resolves the affected `Stack`/`Commit` using a completely different, unauthenticated field of the same payload: `Handler#repository_name` = `payload.dig('repository', 'full_name')` (used by `PushHandler`, `CheckSuiteHandler` via `stacks`, and indirectly `StatusHandler` via `sha`). Because `owner.login` and `full_name` are never cross-checked, the "organization whose key authenticated the request" and "the repository the handlers act on" are decoupled.

### Finding Description
- `verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-49`) does:
```ruby
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
head(422) unless verified
```
with `repository_owner` defined as:
```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```
- `GithubApp#verify_webhook_signature` (`lib/shipit/github_app.rb:76-83`) is: `return true unless webhook_secret` — if the org resolved by `repository_owner` has **no** `webhook_secret` configured (documented as optional in `docs/setup.md`), verification always succeeds, with zero credential required.
- All handlers derive the target of the action from a different field: `Handler#repository_name` (`app/models/shipit/webhooks/handlers/handler.rb:36-38`) is `payload.dig('repository', 'full_name')`, used by `stacks` (`handler.rb:32-34`), and consumed by `PushHandler#process` (`app/models/shipit/webhooks/handlers/push_handler.rb:12-17`) and `CheckSuiteHandler#process` (`app/models/shipit/webhooks/handlers/check_suite_handler.rb:13-17`). `StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`) matches purely on `sha`, with no repository binding check at all.
- Consequence: a request whose `repository.owner.login`/`organization.login` names an organization configured **without** a webhook secret passes `verify_signature` unconditionally, while the `repository.full_name` (and, for `StatusHandler`, the `sha`) inside the very same JSON body can name a totally different, unrelated, properly-secured stack/repository tracked by this Shipit instance. The handler will act on that unrelated stack.

This is the same defect class as the audited `RedemptionFacet::claimRemainingCollateral()` bug: one field is what gets checked/authenticated (`repository_owner` / the signing key), a different, independently attacker-controlled field is what gets acted upon (`repository.full_name`, or bare `sha` for statuses), and the code never enforces that the two agree.

### Impact Explanation
Concretely, with an internet-reachable `/webhooks` endpoint (mounted per `docs/setup.md`) and at least one configured GitHub organization lacking a `webhook_secret` (an explicitly supported, documented configuration — "Webhook secret (optional)"), an unauthenticated attacker can:
- Send a `push` event with `repository.owner.login` = the unsecured org and `repository.full_name` = `"victim-org/victim-repo"` for any stack this Shipit instance tracks. `PushHandler#process` will call `stack.sync_github(expected_head_sha: params.after)` for the victim stack, enqueuing `GithubSyncJob`, which fetches real commits from GitHub using the app's own credentials and can advance the victim stack's HEAD/lock state, feeding into deploy eligibility for stacks with `continuous_deployment` enabled — an unauthorized deploy trigger.
- Send a `check_suite` event similarly targeting `repository.full_name` of the victim, scheduling check-run refreshes for arbitrary tracked stacks.
- Send a `status` event with an arbitrary `sha` (no repository binding at all) to fabricate a `Status` record on any known commit, which feeds merge-gating logic used by the merge queue.

This crosses a repository/authentication boundary the signature check was meant to enforce, matching the "unauthorized deploy" / "cross-repository writes" impact class, without needing any Shipit session, API token, or knowledge of any org's webhook secret — the attacker only needs to know (or guess) the name of one configured organization that happens to have no secret set, which is a config-dependent but explicitly supported and documented state, not a credential.

### Likelihood Explanation
Requires: (1) the operator has configured at least one GitHub organization without a `webhook_secret` (documented as optional — plausible in multi-org and internal deployments), and (2) the endpoint is internet reachable. Given both, exploitation needs no privilege at all — a single crafted JSON POST to `/webhooks`.

### Recommendation
Bind the signature-verification identity to the same identity acted upon: after selecting `github_app` via `repository_owner`, require that `repository_owner` also equals the owner segment of `repository.full_name` (and, for `StatusHandler`, resolve the repository via the same verified owner rather than trusting a bare `sha`). Do not allow `verify_webhook_signature` to short-circuit to `true` when `webhook_secret` is blank for any organization if other organizations in the same instance are secured — or at minimum reject cross-repository/organization mismatches at the controller level before dispatching to handlers.

### Proof of Concept
1. Configure `config/secrets.yml` in the documented multi-org style (`docs/setup.md:182-209`) with two orgs, where `OrgA` (the attacker-known org) has `webhook_secret:` left blank and `OrgB` (victim) has a strong secret, and Shipit tracks a stack for `OrgB/victim-repo`.
2. POST to `/webhooks` with header `X-Github-Event: push` and any/no `X-Hub-Signature`, and body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker chosen sha existing on victim repo>",
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/victim-repo" }
}
```
3. `verify_signature` resolves `github_app = Shipit.github(organization: "OrgA")`; since `OrgA` has no `webhook_secret`, `verify_webhook_signature` returns `true` unconditionally — no valid signature required.
4. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("OrgB/victim-repo")` and calls `stack.sync_github(expected_head_sha: ...)` on the victim's stack, despite the request never having been authenticated against `OrgB`'s secret.     def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

### Using Multiple Github Applications

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently. The top-level keys should be the name of each Github organization, and the following sub-keys are the Github app details for that particular organization.

For example:

```yml
production:
  github:
    somegithuborg:
      app_id:
      installation_id:
      webhook_secret:
      private_key:
      oauth:
        id:
        secret:
        teams:
    someothergithuborg:
      app_id:
      installation_id:
      webhook_secret:
      private_key:
      oauth:
        id:
        secret:
        teams:
