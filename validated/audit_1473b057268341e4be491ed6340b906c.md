### Title
`flash_position` permanently freezes any token the receiver sends to the controller that the caller did not declare in `collaterals` or `refund_assets` — ([File: contracts/controller/src/strategies/flash_position.rs])

### Summary
The original bug class is: the protocol accepts a user-supplied "destination" parameter and locks/burns the user's tokens, then emits a message whose type the counterparty cannot decode, so the funds are frozen forever. In XOXNO Lending the same shape exists in `Controller::flash_position`: the protocol measures the receiver callback's token receipts strictly by balance delta against a caller-declared asset list. Tokens of any asset that is neither a declared collateral nor a declared refund asset land on the controller but are never deposited, never refunded, and — because every other controller flow measures only deltas against a call-start baseline — can never be claimed or swept by anyone afterward. The transaction commits successfully, so the freeze is silent and permanent.

### Finding Description
`process_flash_position` snapshots controller balances for exactly two caller-controlled lists before invoking the receiver's `execute_flash_position` callback: `collaterals` (`HubAssetKey` + min amounts) and `refund_assets` (plain `Address` list). After the callback returns it:

1. calls `collect_collateral_deposits`, which iterates **only** `collaterals` and deposits each token's positive delta via `process_deposit` (`flash_position.rs:325-352`, line 146);
2. calls `refund_listed_assets`, which iterates **only** `refund_assets` and refunds each token's delta to the caller via `refund_controller_balance_delta` (`flash_position.rs:372-384`, line 148).

Any other token transferred to the controller during the callback is simply ignored. The protocol's own documentation states: "An undeclared token left on the controller is neither deposited nor refunded" (`skills/xoxno-lending-contracts/flash-loans.md:134`). There is no rescue path: `validate_refund_assets` forbids overlap between the two lists (`flash_position.rs:248-255`) but does not forbid the callback sending third-party assets, and the refund mechanic is delta-based (`refund_controller_balance_delta` against `refund_before`), so a subsequent caller declaring that asset in `refund_assets` only receives the delta produced during *their own* callback — the pre-existing stranded balance is never reachable. The repo's own regression test for a sibling instance of this class acknowledges the property: "the controller holds funds no balance-delta measurement can ever claim" (`tests/test-harness/tests/controller/recipient_is_protocol_contract.rs:1-5`). For `borrow`/`withdraw` to the pool or controller the team added a `InvalidFlashloanReceiver` guard, but the flash-position callback still lets arbitrary assets strand on the same contract.

### Impact Explanation
Permanent freezing of funds. An unprivileged `caller` runs `flash_position(caller, account_id, spoke_id, mode, debt, amount, receiver, data, collaterals, refund_assets)` where their receiver contract (or a venue inside `data` that pushes tokens to the controller address) transfers tokens of a listed, supply-eligible asset that the caller omitted from both lists — e.g., a swap that returns two output tokens while only one is declared, or a receiver that over-sends. The position opens (debt minted, declared collateral credited), but the undeclared tokens sit on the controller with no reachable recovery: not depositable retroactively, not refundable, not claimable by any later `refund_assets` delta. As in the source finding, the loss is contingent on the caller's own parameterization of a legitimate path, matching the "sChain-native token to mainnet" misconfiguration shape — user-triggerable permanent freeze of real token value with no administrative recovery entrypoint on the controller.

### Likelihood Explanation
Reachable by any unprivileged caller: `flash_position` only requires `require_authorized_caller` (caller's own auth), an active hub, a flashloanable debt asset, and a wasm receiver distinct from the controller/pool (`flash_position.rs:45-91`). The freeze requires the receiver to send an undeclared asset — a realistic integration mistake, since receivers performing multi-output swaps naturally produce tokens not needed as collateral, and nothing in `validate_refund_assets` or the callback interface warns that non-declared receipts are silently sacrificed rather than reverted. It is self-inflicted rather than attacker-on-victim, which is why severity tracks Medium like the source finding rather than High: the frozen funds are those the caller's own receiver pushed in.

### Recommendation
Mirror the fix pattern the source report suggested (`require(chainHash != MAINNET_HASH)`) by closing the gap before commit: after `refund_listed_assets`, sweep-check that the callback left no balance of *any* listed asset the controller might touch — or, practically, require the receiver to route all outputs through declared lists by reverting when the controller's balance of the debt asset itself is still non-zero after the callback (the borrowed token is not in `collaterals`' snapshot scope beyond its own delta check, and unused forwarded debt left on the controller is also stranded, since refunding it "does not repay the minted debt"). The debt asset is never in `collaterals` and is only refundable if the caller redundantly adds it to `refund_assets` (`validate_refund_assets` does not include the debt asset automatically), so a receiver that returns unspent debt tokens strands them too — add `debt.asset` to `refund_before` implicitly or require a zero post-callback debt-token balance. Alternatively, reject callbacks that change the controller's balance of any asset outside the two declared lists by snapshotting all listed spoke assets.

### Proof of Concept
1. Setup: hub with USDC (debt, `is_flashloanable = true`) and ETH + XLM listed as supply-eligible collateral on the caller's spoke.
2. Attacker/victim `caller` deploys `Receiver` with `execute_flash_position` that: swaps the forwarded USDC into ETH **and** XLM, then transfers both ETH and XLM to the controller.
3. `caller` invokes `Controller::flash_position(caller, 0, spoke_id, PositionMode::Multiply, debt=USDC, amount, receiver, data, collaterals=[(ETH, min)], refund_assets=[])` — XLM is declared in neither list, so it is neither snapshotted nor refunded.
4. The transaction commits: debt is minted, ETH delta is deposited as collateral, risk gates pass. The XLM balance now sits on the controller permanently: no entrypoint credits it to any position, `refund_controller_balance_delta` only ever returns deltas measured *within* a future call, and the controller exposes no sweep. The XLM is frozen exactly as the schain tokens were frozen on `TokenManagerERC20` in the source report.

Uncertainty note: I did not exhaustively verify that no hidden "rescue"/sweep entrypoint exists on the controller; the grep of `contracts/controller/src` showed no such function and the repo's own test comments confirm stranded balances are unclaimable by design.
