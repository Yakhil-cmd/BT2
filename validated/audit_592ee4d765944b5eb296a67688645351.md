## Title
Webhook provenance bypass allows attacker-org's signed membership event to mutate a Team belonging to another organization, granting github_teams authorization - (File: app/models/shipit/webhooks/handlers/membership_handler.rb)

## Summary
`MembershipHandler#find_or_create_team!` and `#process` look up and mutate a `Team` solely by `params.team.id` (the GitHub team's numeric `github_id`), without ever checking that `params.organization.login` (used by `WebhooksController#verify_signature` to select which `GithubApp`/`webhook_secret` verified the request) actually owns that team. Because signature verification is keyed off the *attacker-controlled* `organization.login` field via `Shipit.github(organization: repository_owner)`, an attacker who controls their own configured GitHub App/org can sign a `membership` payload referencing a *different* org's existing `Team#github_id` and add themselves as a member of it.

## Finding Description
The broken binding, stated as an equality that must hold but doesn't:
`organization_that_signed_the_request(params.organization.login) == organization_that_owns(Team.find_by(github_id: params.team.id).organization)`

Trace:
- `WebhooksController#verify_signature` computes `repository_owner` from `params.dig('repository','owner','login') || params.dig('organization','login')` [1](#0-0) . For a `membership` event there is no `repository` key, so `repository_owner` becomes whatever `organization.login` the attacker puts in the JSON body, e.g. `attacker-org`.
- It then does `github_app = Shipit.github(organization: repository_owner)` and verifies the signature against **that** app's `webhook_secret` [2](#0-1) . Since the attacker owns `attacker-org` as one of the two configured GithubApp installs, they know/control that secret and can produce a valid `X-Hub-Signature`.
- Once verified, `Webhooks.for_event('membership')` dispatches to `MembershipHandler#process` [3](#0-2) .
- `find_or_create_team!` resolves the Team purely by `github_id: params.team.id` [4](#0-3) . If a `Team` row with that `github_id` already exists (belonging to a real, different org), `find_or_create_by!` returns the existing record — it never re-checks or validates `params.organization.login` against the existing `team.organization`.
- `process` then calls `User.find_or_create_by_login!(params.member.login)` and, for `action == 'added'`, `team.add_member(member)` [5](#0-4) , `Team#add_member` appends the membership [6](#0-5) .
- `User#authorized?` checks `teams.where(id: Shipit.github_teams.map(&:id)).exists?` [7](#0-6) , so once the Membership row exists, the attacker's user becomes authorized.

None of the listed guards catch this: `verify_signature` only proves the payload was signed by *some* configured org's secret, not that the org matches the team being mutated; `find_or_create_by!` has no ownership check; there is no `require_permission!` or similar call in this controller/handler path.

Attacker request: `POST /webhooks` with `X-Github-Event: membership`, body `{action:'added', team:{id:<existing privileged team's github_id>, name, slug, url}, organization:{login:'attacker-org'}, member:{login:'attacker'}}`, signed with `attacker-org`'s own `webhook_secret`.

## Impact Explanation
The attacker gains membership in a privileged `Shipit::Team` and thus `authorized?` returns true for their `Shipit::User`, escalating into `Shipit.github_teams` authorization — matching the "High: escalation into `Shipit.github_teams` authorization" category. This is repeatable against any team `github_id` the attacker can enumerate/guess (GitHub team ids are often observable or brute-forceable), and is not scoped to a single repository — any team referenced anywhere by `Shipit.github_teams` is a target. Blast radius spans all tenants/stacks that gate actions behind `authorized?`.

## Likelihood Explanation
Requires: (1) Shipit configured with at least two `GithubApp`s (multi-org), one of which the attacker legitimately owns/administers (so they know that app's `webhook_secret`); (2) `Shipit.github_teams` configured with a team whose numeric `github_id` the attacker can discover. Both are plausible in real multi-tenant Shipit deployments (e.g., SaaS-like setups where multiple orgs are onboarded, one of which is attacker-controlled or compromised). Given those preconditions, the attack is a single unauthenticated-relative-to-Shipit HTTP POST, fully repeatable at will, with no rate limiting mentioned as a blocker.

## Recommendation
In `MembershipHandler#find_or_create_team!`, verify that `params.organization.login` matches the `organization` already stored on any existing `Team` with that `github_id` before mutating it (reject/raise if mismatched), and/or have `WebhooksController#verify_signature` cross-check that the signing organization is authorized to emit events about the specific `team.id`/`organization.login` combination rather than trusting the attacker-supplied `organization.login` alone to select the verification key when no `repository` context exists.

## Proof of Concept
Minitest (`test/controllers/webhooks_controller_test.rb`-style) using `ActionDispatch::IntegrationTest`:
1. Configure two `GithubApp`s in `Shipit.app.github` fixture/config: `"real-org"` and `"attacker-org"`, each with distinct `webhook_secret`.
2. Seed a `Team` fixture with `organization: "real-org"`, `github_id: 1234`, included in `Shipit.github_teams`.
3. Build a membership payload `{action:'added', team:{id:1234, name:'x', slug:'x', url:'x'}, organization:{login:'attacker-org'}, member:{login:'attacker'}}`.
4. Sign it with `attacker-org`'s `webhook_secret` and POST to `/webhooks` with `X-Github-Event: membership`.
5. Assert response is `200`/`:ok` (signature accepted).
6. Assert `Shipit::Membership.exists?(user: Shipit::User.find_by(login: 'attacker'), team: Shipit::Team.find_by(github_id: 1234))` is `true`.
7. Assert `Shipit::User.find_by(login: 'attacker').authorized?` is `true`, proving cross-organization escalation: `params.organization.login ("attacker-org") != team.organization ("real-org")` yet the mutation and authorization succeeded.
