### Title
Reward-partitioning clamp to `MAX_FACTOR_OF_REWARD_BLOCKS_IN_EPOCH` allows attacker-inflated delegation counts to produce unboundedly large per-block partitions during epoch-boundary reward distribution - (File: runtime/src/bank/partitioned_epoch_rewards/mod.rs, runtime/src/bank/partitioned_epoch_rewards/distribution.rs)

### Finding Description
`get_reward_distribution_num_blocks` computes the desired number of reward-distribution blocks as `total_stake_accounts.div_ceil(stake_account_stores_per_block)`, but then clamps that number to at most `slots_per_epoch / MAX_FACTOR_OF_REWARD_BLOCKS_IN_EPOCH` (10% of the epoch's slots): [1](#0-0) 

The target chunk size (`stake_account_stores_per_block`, default `MAX_PARTITIONED_REWARDS_PER_BLOCK = 4096`) is only used to *compute the desired number of partitions*, and is not enforced as a hard per-block cap once the clamp kicks in: [2](#0-1) 

At the actual distribution boundary, `hash_rewards_into_partitions` randomly assigns every stake-reward index into one of exactly `num_partitions` buckets via a stake-pubkey hash, with no bound on how many rewards land in a single bucket: [3](#0-2) 

`distribute_partitioned_epoch_rewards` then processes exactly one partition (bucket) per block via `distribute_epoch_rewards_in_partition` / `store_stake_accounts_in_partition`, iterating over every index in that partition's bucket, unconditionally, within a single block: [4](#0-3) [5](#0-4) 

The only guard against unbounded partition-count growth is:
```
assert!(self.epoch_schedule.get_slots_in_epoch(self.epoch) > partition_rewards.partition_indices.len() as u64);
```
This bounds the *number of blocks* (`partition_indices.len()`), not the *size of each partition's inner Vec<usize>* (the per-block work). If an attacker funds and delegates a very large number of low-balance `StakeStateV2::Stake` accounts (each only requiring rent-exempt reserve + `get_minimum_delegation` lamports, which is as small as 1 lamport pre-feature or 1 SOL post-feature-activation), `total_stake_accounts` (`calculate_stake_rewards_and_commissions` processes every delegation in the `Stakes` cache with no upper bound) can be driven arbitrarily large: [6](#0-5) [7](#0-6) 

Once `num_chunks` (desired blocks) exceeds `slots_per_epoch/10`, the clamp caps `num_partitions` at that fixed ceiling regardless of how many total rewards there are, so the average (and worst-case, since hashing is not guaranteed uniform) bucket size grows linearly with `total_stake_accounts / num_partitions` — i.e., unboundedly with attacker-controlled delegation count — while the number of blocks stays fixed. Each such oversized bucket is then processed synchronously within a single 400ms slot in `store_stake_accounts_in_partition`, which loads, mutates, and stores every stake account in the bucket (`self.store_accounts`) and requires acquiring the `stakes_cache` read lock for the whole loop.

### Impact Explanation
This matches the file/function scope ("epoch-boundary work must be bounded") described in the prompt: an unprivileged attacker who is willing to fund enough minimum-delegation stake accounts can cause per-block reward-distribution work (account loads/stores, arithmetic, and lock hold time) to scale with the total delegation count rather than being bounded by the intended `stake_account_stores_per_block` target once the 10%-of-epoch block-count ceiling is hit. This can slow or stall block production for whichever validator is leader during the affected distribution slot(s), for every validator processing that fork (since reward distribution is deterministic/consensus-critical and runs on every node), constituting a network-wide performance degradation ("stalls every validator") rather than a memory-safety panic. The `assert!` in `distribute_partitioned_epoch_rewards` cannot itself be tripped by this pattern because it does not depend on the inner-bucket sizes, so no panic occurs, but the underlying invariant the assert was meant to protect ("epoch-boundary work is bounded") is nonetheless violated in terms of wall-clock cost, since it does not bound the size of the `Vec<usize>` inside each partition.

Category: liveness/performance DoS at the protocol layer, bounded by the economic cost of creating the delegations (rent-exempt reserve + minimum delegation per account), not by a hard protocol-level cap.

### Likelihood Explanation
Feasibility depends heavily on cost: each stake account requires paying the rent-exempt reserve (`StakeStateV2::size_of()` size, several thousand lamports) plus `get_minimum_delegation()` (1 lamport pre-`upgrade_bpf_stake_program_to_v5`, or 1 SOL once that feature activates), per the code in `runtime/src/stake_utils.rs`. Before the v5 feature is active, an attacker can create huge numbers of "dust" stake accounts extremely cheaply (only rent-exempt reserve, no minimum stake requirement of real economic value), making the number of delegations attacker-controllable at very low cost. After the v5 feature activates, the 1-SOL minimum delegation per stake account raises the cost significantly, making this attack much less practical at scale but not architecturally prevented — the per-block work would still scale unboundedly with delegation count if an attacker was willing to spend the SOL. I could not fully verify from the available code index whether the `upgrade_bpf_stake_program_to_v5` feature is active by default on mainnet-beta in this codebase snapshot, nor pin down exact current values of `slots_per_epoch`/`stake_account_stores_per_block` scaling under shorter slot-time regimes referenced in `partitioned_rewards.rs` comments; this affects the precise numeric threshold at which the clamp is hit and should be verified with a live/staging cluster.

### Recommendation
Enforce a genuine hard cap on the number of rewards processed per block (per partition), independent of the block-count ceiling. Options:
- Instead of packing all rewards into a fixed number of "epoch-fraction"-bounded partitions, allow the number of partitions/blocks to grow with `total_stake_accounts` (removing or relaxing the `slots_per_epoch/10` clamp), while adding a separate hard ceiling on the total number of delegations that can exist / receive rewards in a given epoch.
- Alternatively, cap per-partition size explicitly after hashing (e.g., split any partition whose size exceeds `stake_account_stores_per_block` into additional sub-blocks, extending the distribution period as needed rather than silently growing per-block work), and adjust `distribute_end_exclusive`/the `assert!` to account for the true, dynamically determined number of blocks required to keep per-block work bounded.
- Consider adding a protocol-level limit on the total number of `StakeStateV2::Stake` delegations counted for reward purposes, or requiring a non-trivial minimum delegation (already partially addressed by `upgrade_bpf_stake_program_to_v5`'s 1-SOL minimum) to make large-scale dust-delegation flooding economically infeasible.

            // demonstrating unbounded per-block scaling with attacker-controlled

        }

    /// Calculate the number of blocks required to distribute rewards to all stake accounts.
    pub(super) fn get_reward_distribution_num_blocks(
        &self,
        rewards: &PartitionedStakeRewards,
    ) -> u64 {
        let total_stake_accounts = rewards.num_rewards();
        if self.epoch_schedule.warmup && self.epoch < self.first_normal_epoch() {
            1
        } else {
            const MAX_FACTOR_OF_REWARD_BLOCKS_IN_EPOCH: u64 = 10;
            let num_chunks = total_stake_accounts
                .div_ceil(self.partitioned_rewards_stake_account_stores_per_block() as usize)
                as u64;

            // Limit the reward credit interval to 10% of the total number of slots in a epoch
            num_chunks.clamp(
                1,
                (self.epoch_schedule.slots_per_epoch / MAX_FACTOR_OF_REWARD_BLOCKS_IN_EPOCH).max(1),
            )
        }
    }

pub(in crate::bank::partitioned_epoch_rewards) fn hash_rewards_into_partitions(
    stake_rewards: &PartitionedStakeRewards,
    parent_blockhash: &Hash,
    num_partitions: usize,
) -> Vec<Vec<usize>> {
    let hasher = EpochRewardsHasher::new(num_partitions, parent_blockhash);
    let mut indices = vec![vec![]; num_partitions];

    for (i, reward) in stake_rewards.enumerated_rewards_iter() {
        // clone here so the hasher's state is reused on each call to `hash_address_to_partition`.
        // This prevents us from re-hashing the seed each time.
        // The clone is explicit (as opposed to an implicit copy) so it is clear this is intended.
        let partition_index = hasher
            .clone()
            .hash_address_to_partition(&reward.stake_pubkey);
        indices[partition_index].push(i);
    }
    indices
}
