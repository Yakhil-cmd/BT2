### Title
Webhook organization used for HMAC signature verification is decoupled from the repository/commit actually mutated by the event handler - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to validate an inbound webhook against using an attacker-supplied field of the very payload being verified, but several webhook handlers act on data with no re-check that the authenticated organization actually owns the repository/commit being mutated. This breaks the equality that should hold: `organization whose secret authenticated the request == repository/commit written by the handler`.

### Finding Description
`verify_signature` computes the organization to authenticate against directly from the untrusted request body: [1](#0-0) [2](#0-1) 

`repository_owner` reads `repository.owner.login` (or falls back to `organization.login`) straight out of the JSON body that is itself the thing being HMAC-verified. In a Shipit installation configured for multiple GitHub organizations — a first-class, documented configuration (`config/secrets.yml`'s `github:` section keyed by org, each with its own `webhook_secret`) — this means the attacker chooses which org's secret the signature check will run against, simply by setting `repository.owner.login` to an org whose secret they know (e.g., their own org, on which they legitimately administer a GitHub App/webhook). [3](#0-2) 

Once the signature passes (because it was computed with the secret of the org the attacker chose), the actual handler dispatch is driven by *other, unchecked* fields of the same payload. Some handlers do scope to the repository via `Handler#repository_name`/`#stacks` (`payload.dig('repository', 'full_name')`): [4](#0-3) 

But `full_name` is a completely separate field from `owner.login` used for signature selection — nothing ties them together. Worse, `StatusHandler`, which creates commit CI statuses, does not scope to a repository at all: [5](#0-4) 

It performs a global `Commit.where(sha: params.sha)` lookup across the entire Shipit database. Because commit SHAs are public/guessable (visible on the victim's GitHub repository, or on the victim stack's own Shipit UI), an attacker who only controls one org's webhook secret can forge a `status` event, authenticate it against their own org, and have `create_status_from_github!` fire for a commit belonging to a completely unrelated, victim organization's stack — one they have no GitHub or Shipit access to whatsoever.

### Impact Explanation
Commit statuses gate `ci.require`/`ci.blocking` checks that determine whether a commit is `deployable?` and can pass through the deploy/merge-queue flow (documented in `README.md`'s CI section, referencing `ci.require`, `ci.blocking`). By forging a "success" status on an arbitrary victim commit, the attacker can satisfy required-CI gating for a stack they have no legitimate access to, enabling that commit to be deployed or merged — an unauthorized deploy/merge, which is explicitly a Critical-severity outcome per the engine's impact taxonomy. `CheckSuiteHandler` is scoped by `stacks` (repository + branch), reducing but not eliminating similar cross-org exposure for check-run refresh scheduling.

### Likelihood Explanation
Exploitation requires the operator to run Shipit with the documented multi-organization GitHub App configuration and requires the attacker to control (own/administer) at least one of the configured organizations' GitHub Apps — a normal, unprivileged position relative to the *victim* org, and explicitly not requiring any Shipit session, `ApiClient` token, or `GITHUB_TOKEN`. Given multi-org hosting is a first-class supported feature, this is a realistic deployment shape, though the specific StatusHandler global-lookup gap makes it most severe when at least one commit SHA of the victim stack is discoverable (public repos, public Shipit UI).

### Recommendation
Bind the authenticated organization to the object being mutated: after `verify_signature` succeeds, pass the authenticated organization through to each handler and require that the repository/stack/commit being acted upon actually belongs to that organization (e.g., compare `repository.owner.login` against the `Repository`/`Stack` record's own stored owner, not against payload-declared fields) before permitting any writes — especially for `StatusHandler`, which should scope its `Commit` lookup to stacks whose repository owner matches the authenticated organization, mirroring what `Handler#stacks` already does for other handlers.

### Proof of Concept
1. Operate (or have an unprivileged account within) a Shipit instance configured for multiple GitHub orgs, `OrgA` (attacker's own org, secret `S_A` known to attacker) and `OrgB` (victim org, unrelated, tracked by the same Shipit instance).
2. Find a public commit SHA belonging to a stack owned by `OrgB` (e.g., from `OrgB`'s public GitHub repo).
3. Craft a `status` webhook JSON body: `{"repository": {"owner": {"login": "OrgA"}}, "sha": "<OrgB commit sha>", "state": "success", "context": "ci/required"}`.
4. Compute `X-Hub-Signature` as `sha1=HMAC-SHA1(S_A, raw_body)`.
5. POST to `/webhooks` with `X-Github-Event: status`. `verify_signature` resolves `repository_owner` to `"OrgA"`, fetches `Shipit.github(organization: "OrgA")`, and the signature validates successfully against the attacker's own known secret.
6. `StatusHandler#process` runs `Commit.where(sha: params.sha)` and creates a success status on `OrgB`'s commit via `create_status_from_github!`, satisfying `OrgB`'s stack's required CI checks despite the attacker having no access to `OrgB`.
