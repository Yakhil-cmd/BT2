Confirmed: `Shipit.github(organization:)` maps a per-organization config (with its own `webhook_secret`) via `github_app_config(organization)`, and each organization's app config is independently controlled by a Shipit admin who registers each GitHub App/organization in `secrets.github` (`lib/shipit.rb:170-200`). `WebhooksController#verify_signature` picks which org's secret to verify against using `repository_owner`, which is read straight out of the attacker-suppliable JSON body (`params.dig('repository','owner','login') || params.dig('organization','login')`) before the signature has even been checked [1](#0-0) . Once verification passes with *that* organization's secret, the actual write target used by every handler is a *different* field of the same attacker-controlled JSON body: `payload.dig('repository', 'full_name')` [2](#0-1) . Nothing enforces that `repository.owner.login` (used to select/verify the signing secret) equals the owner encoded in `repository.full_name` (used to select the actual `Stack`/`Repository` acted upon). Since a valid signature over the *entire* raw body can be produced by anyone possessing **any one** of the configured organizations' `webhook_secret` (each organization is an independently trusted, but mutually un-privileged-to-each-other, tenant of this multi-org Shipit instance), holder of Org A's secret can freely set `repository.full_name` to `"OrgB/other-repo"` while keeping `repository.owner.login` = `"OrgA"`, producing a fully valid signature that Shipit accepts, then have handlers (e.g. `PushHandler`, `StatusHandler`) act on Org B's stack.

This satisfies the requested analog: "an organization that authenticated versus the repository that is written" — and it does not require an `ApiClient` token, a Shipit session, `api_clients_secret`, or a GitHub App private key; it only requires possession of one legitimately-configured organization's webhook secret (which under this engine's multi-tenant design is not equivalent to "repository write access" or a "privileged account" on the target stack — Org A has no privilege over Org B's repo).

### Title
Webhook signature verification key is selected by `repository.owner.login`, but processing acts on the unverified `repository.full_name` field, enabling cross-organization stack forgery - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` chooses which per-organization `webhook_secret` to validate a GitHub webhook against using the payload's `repository.owner.login` (or `organization.login`) field, but the downstream `Shipit::Webhooks::Handlers::Handler#repository_name` (and every handler built on it) resolves the target `Repository`/`Stack` using the payload's `repository.full_name` field instead. Because the HMAC signature only proves the payload was signed by *some* configured organization's secret — not that the two fields agree — a holder of any one organization's `webhook_secret` can craft a payload whose `owner.login` matches their own org (so it passes verification) while `full_name` points at a completely different organization's repository, letting them inject spoofed push/status/check_suite/pull_request events against a stack they do not own.

### Finding Description
`verify_signature` is invoked as a `before_action` and picks the verifying `GitHubApp`/secret via:
```ruby
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
``` [1](#0-0) 
where
```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [3](#0-2) 

Each organization's configuration (including its own `webhook_secret`) is independently registered by a Shipit admin via `Shipit.github_app_config(organization)` / `secrets.github` [4](#0-3) , meaning distinct organizations connected to the same Shipit instance are mutually un-trusted tenants — one organization's secret should not authorize actions on another organization's repositories.

Once the signature check passes, `create` dispatches the *entire* raw payload to the registered handlers:
```ruby
def create
  params = JSON.parse(request.raw_post)
  Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }
  head(:ok)
end
``` [5](#0-4) 

Every handler resolves its target repository/stack via a *different* field:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [2](#0-1) 

`PushHandler`, `StatusHandler`, `CheckSuiteHandler`, and the `PullRequest::*` handlers all resolve their target repository through `repository.full_name`, e.g.:
```ruby
def process
  stacks.not_archived.where(branch:).find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
end
``` [6](#0-5) 

Because the signature is computed over the raw JSON body as a whole, it only proves the sender knows a *valid webhook secret for some organization* configured on the instance — it does not bind `repository.owner.login` (the key-selection field) to `repository.full_name` (the state-mutation field). An attacker who legitimately controls Org A's GitHub App (and thus knows Org A's `webhook_secret`) can therefore forge a payload where `repository.owner.login == "OrgA"` (so `verify_signature` selects and passes with Org A's secret) but `repository.full_name == "OrgB/target-repo"`, causing the handler layer to look up and mutate `OrgB`'s `Repository`/`Stack` records.

### Impact Explanation
This breaks the trust boundary the multi-organization webhook design is supposed to enforce: possession of one tenant organization's webhook secret should only authorize webhook-driven actions on that organization's own repositories, not on any other configured organization's repositories. Exploiting the mismatch allows:
- Injecting a fake `push` event, causing `stack.sync_github(expected_head_sha: ...)` to run against another organization's stack.
- Injecting fake `status`/`check_suite` events to mark another organization's commits as CI-passing, which can unblock automatic deploys or merge-queue processing for a stack the attacker does not own — an unauthorized deploy/merge on cross-organization state.

This meets the Critical bar of "cross-repository writes" / "unauthorized deploy, rollback or merge," since Org A has no legitimate authority over Org B's repository or stack.

### Likelihood Explanation
Requires the attacker to already control at least one organization's GitHub App/webhook configuration on the shared Shipit instance (a normal, unprivileged-with-respect-to-other-tenants condition in any multi-org deployment) — not a Shipit account, `ApiClient` token, or `api_clients_secret`. Crafting the payload is trivial (arbitrary JSON, HMAC-signed with their own known secret); no interaction with the target organization is required.

### Recommendation
Bind the key-selection field to the mutation field: after selecting `github_app` via `repository_owner`, verify that `repository.full_name`'s owner segment matches `repository_owner` (or, more robustly, verify the signature per-organization only using the exact repository the payload claims to originate from, and reject the payload if `repository.owner.login` and the owner portion of `repository.full_name` diverge) before invoking any handler.

### Proof of Concept
1. Configure Shipit with two organizations, `OrgA` and `OrgB`, each with its own `webhook_secret` (a realistic multi-tenant Shipit deployment) [7](#0-6) .
2. As the (unprivileged w.r.t. OrgB) administrator of `OrgA`'s GitHub App, craft a `push` payload:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha-existing-in-OrgB-repo>",
  "repository": {
    "full_name": "OrgB/target-repo",
    "owner": { "login": "OrgA" }
  }
}
```
3. Compute `X-Hub-Signature` as `sha1=HMAC-SHA1(OrgA_webhook_secret, raw_body)`.
4. POST to `/github/webhooks` with header `X-Github-Event: push`.
5. `verify_signature` computes `repository_owner` = `"OrgA"`, loads `Shipit.github(organization: "OrgA")`, and the signature validates successfully against `OrgA`'s secret [8](#0-7) .
6. `create` dispatches the payload to `PushHandler`, which resolves `stacks` via `repository.full_name` = `"OrgB/target-repo"` [2](#0-1)  and triggers `stack.sync_github` for `OrgB`'s stack — despite the request only ever having been authenticated as originating from `OrgA`.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
