### Title
Non-base assets sent alongside a bouncing AA trigger are permanently absorbed into the AA's balance with no way for the sender to reclaim them - (File: aa_composer.js)

### Summary
An unprivileged unit poster who sends a trigger unit to an Autonomous Agent (AA) that contains both bytes and a custom asset can permanently lose the custom-asset portion if the trigger bounces for any reason. `handleTrigger` composes the bounce response only from the base-asset balance; any other asset received in the same trigger is added to the AA's `aa_balances` accounting but is never returned, and typical AA templates never reference or forward it, so it becomes stuck exactly like the FORT tokens in the referenced `StakingEscrow` report — received but never "accounted for" by any mechanism that could release it.

### Finding Description
`getTrigger()` collects every asset sent to the AA address in the triggering unit into `trigger.outputs`, keyed by asset (`base` and any other asset id): [1](#0-0) 

When a trigger is processed, `updateInitialAABalances` credits **all** of `trigger.outputs` (base and non-base) into `aa_balances` for the AA address before the AA logic even runs: [2](#0-1) 

Immediately afterward, the bounce-fee check only guarantees that the *base* bytes are enough to cover `bounce_fees.base`; for any other asset, insufficient funds are handled by simply calling `bounce()` — the comment explicitly says this is done "ignore silently": [3](#0-2) 

Critically, once `bounce()` fires (whether due to insufficient base bytes, an explicit `bounce()` call in the AA formula, `evaluateAA` failure, "no messages", exceeding `MAX_RESPONSES_PER_PRIMARY_TRIGGER`, or a chained secondary-AA bounce via `revert()`), the response unit that is built to refund the sender only composes a base-asset payment message. This is demonstrated by the existing unit test, where a trigger carrying `40000` base bytes bounces and the refund payment message only ever contains the `base` asset output (`40000 - bounce_fees.base`): [4](#0-3) 

There is no equivalent mechanism that composes a refund payment for a non-base asset that was included in the same trigger. Because the bounce path never runs the AA's own state-var logic (state changes are rolled back via `revert()`/`ROLLBACT TO SAVEPOINT initial_balances`), no state var records that the sender is owed that asset either: [5](#0-4) 

The asset amount, however, was already durably credited into `aa_balances` by `updateInitialAABalances` before the bounce decision was made, so it is now indistinguishable from the AA's own funds. Surveying the shipped/reference AA templates (bouncer, forwarder, ICO, fundraising proxy, payment channels) confirms that none of them account for or forward an asset that arrives on a bounced trigger — they only ever refund/forward the `base` asset in their bounce/fallback branches: [6](#0-5) [7](#0-6) 

This is the same bug class as the `StakingEscrow.release()` issue: funds transferred into the contract/AA are only reachable if some internal accounting/state mechanism explicitly tracks them; the "silent ignore" path leaves received value in the recipient's balance without any tracking, so it can never be released back to the original owner through any code path.

### Impact Explanation
Any user (or a wallet/other AA acting automatically) who sends a unit paying an AA both bytes and a private/public custom asset in the same trigger risks permanent, irrecoverable loss of the asset portion whenever that trigger bounces — which can happen for reasons entirely outside the sender's control (AA hits `MAX_RESPONSES_PER_PRIMARY_TRIGGER`, a chained secondary AA bounces, the AA's formula calls `bounce()` for unrelated reasons, etc.). The lost funds simply become part of the AA's `aa_balance` for that asset with no state variable pointing to the rightful owner, and no AA template in the codebase implements logic to return them. This is a fund-freezing/loss condition reachable by an ordinary unprivileged unit poster, matching the Medium severity of the original report (asset value can become permanently stuck).

### Likelihood Explanation
Likelihood is moderate-to-high: any AA that accepts custom-asset payments (asset exchanges, fundraising proxies, ICOs, DEX-style AAs) is a plausible target, and bounces are a routine, expected outcome of AA processing (insufficient bytes, business-logic bounces, secondary-trigger chain failures). A user does not need to do anything unusual — simply attaching an asset output to a trigger that later bounces for any reason (including reasons unrelated to that asset) is sufficient to trigger the loss.

### Recommendation
When composing the bounce response in `aa_composer.js`, include refund outputs for every non-base asset present in `trigger.outputs` (mirroring the existing base-asset refund logic), or alternatively, make `updateInitialAABalances` defer crediting non-base assets until it's certain that the AA's own accounting will handle them, and refund them automatically when a trigger bounces. At minimum, document explicitly in the AA/oscript documentation that assets sent alongside a bouncing trigger are not automatically refunded, so AA authors implement explicit refund logic — but the root cause is best fixed in the core bounce composition path since it silently swallows value with no user-facing recourse.

### Proof of Concept
1. Define an AA with `bounce_fees: { base: 10000 }` and a simple bounce condition (e.g. `bounce_fees` unmet, or an explicit `bounce()` in `init`).
2. Post a trigger unit that pays the AA `40000` base bytes **and** `1000` units of a custom asset in the same unit, with the AA's condition set up to bounce (as in the existing test at `test/aa.test.js:970-1022`, extended with an asset output).
3. Observe: `updateInitialAABalances` credits both `base` and the custom asset into `aa_balances` for the AA address (aa_composer.js:474-490).
4. Observe: the bounce response composed by `handleTrigger` only contains a `base` payment output (`40000 - 10000`), as shown by the existing test assertion at `test/aa.test.js:1017`; no output refunds the `1000` units of the custom asset.
5. Query `aa_balances` for the AA address/asset after the bounce — the `1000` units remain credited to the AA with no state var or mechanism referencing the original sender, permanently stuck.

function getTrigger(objUnit, receiving_address) {
	var trigger = { address: objUnit.authors[0].address, unit: objUnit.unit, outputs: {} };
	if ("max_aa_responses" in objUnit)
		trigger.max_aa_responses = objUnit.max_aa_responses;
	objUnit.messages.forEach(function (message) {
		if (message.app === 'data' && !trigger.data) // use the first data message, ignore the subsequent ones
			trigger.data = message.payload;
		else if (message.app === 'payment' && message.payload) {
			var payload = message.payload;
			var asset = payload.asset || 'base';
			payload.outputs.forEach(function (output) {
				if (output.address === receiving_address) {
					if (!trigger.outputs[asset])
						trigger.outputs[asset] = 0;
					trigger.outputs[asset] += output.amount; // in case there are several outputs
				}
			});
		}
	});
	if (Object.keys(trigger.outputs).length === 0)
		throw Error("no outputs to " + receiving_address);
	return trigger;
}
