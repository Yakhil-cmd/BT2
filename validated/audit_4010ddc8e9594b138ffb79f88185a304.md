### Title
Unverified `X-Shipit-User` header lets any authenticated API client impersonate any Shipit user for deploys, rollbacks, and locks - ([File: app/controllers/shipit/api/base_controller.rb])

### Summary
`Shipit::Api::BaseController` authenticates requests solely by validating the `ApiClient` bearer token, but derives the *acting user* (`current_user`) from a separate, unsigned request header (`X-Shipit-User`) that is never covered by that authentication check. Any request bearing a valid `ApiClient` token can set `X-Shipit-User` to the login of an arbitrary, more privileged user, and every downstream action attributes itself to that impersonated identity.

### Finding Description
`authenticate_api_client` verifies only the HTTP Basic credentials against `ApiClient.authenticate`, which validates a signed token tied to the `ApiClient` record: [1](#0-0) 

Separately, `current_user` is computed from the `X-Shipit-User` header, looked up by case-insensitive login match, with no relation to and no verification against the credentials that were just authenticated: [2](#0-1) 

This is the same class of bug as the external report: a value that is *acted upon* (here, the `User` identity attributed to a privileged action) is never covered by the binding that was actually verified (the `ApiClient` token signature). The equality that should hold is:

`identity verified by ApiClient.authenticate(token)` == `identity recorded as current_user for the action`

but instead the engine substitutes an attacker-controlled header for the right-hand side, breaking the binding between "the credential that was cryptographically checked" and "the `User` the system believes performed the action."

`current_user` is then passed directly into privileged, stateful operations:
- Triggering a deploy: `stack.trigger_deploy(commit, current_user, ...)` [3](#0-2) 
- Triggering/aborting a rollback: `active_task.abort!(aborted_by: current_user, ...)` and `deploy.trigger_rollback(current_user, ...)` [4](#0-3) 
- Locking/unlocking a stack: `stack.lock(params.reason, current_user)` [5](#0-4) 

Any holder of a valid `ApiClient` token (e.g., a low-trust CI integration issued only `deploy:stack`/`lock:stack` scope) can add `X-Shipit-User: <admin-login>` to make Shipit believe an arbitrary registered user (including admins or team leads) initiated the deploy, rollback, abort, or lock — with no proof of that user's consent or session.

### Impact Explanation
This breaks the binding between the authenticated credential (the `ApiClient` token) and the `User` identity recorded/acted upon for privileged operations, matching the required class of finding ("a GitHub identity versus the `User` bound to the session"). The practical impact is an unauthorized/misattributed deploy or rollback: an attacker who legitimately holds a scoped `ApiClient` token can cause deploys/rollbacks/locks to be performed and recorded under an identity they do not control, without that user's knowledge or authorization, and without any signature or session check tying the header value to the caller.

### Likelihood Explanation
The `X-Shipit-User` header is read from every API request without any authorization check that the authenticated `ApiClient` is actually associated with the named user. Any consumer with a valid, even narrowly-scoped, `ApiClient` token can exploit this trivially by adding one header to any deploy/rollback/lock request; no additional secrets are required.

### Recommendation
Do not trust `X-Shipit-User` as an unauthenticated identity claim. Either bind the acting user to the `ApiClient.creator` (the user who created/owns the token) or require that the `ApiClient` be explicitly scoped/authorized to act on behalf of the named user, validating that link server-side before using it in `current_user`.

### Proof of Concept
1. Obtain (or be issued) a legitimate `ApiClient` token scoped only to `deploy:stack` (e.g., a CI integration token).
2. Send `POST /api/stacks/:id/deploys` with valid Basic Auth for that token and header `X-Shipit-User: admin-login`.
3. Observe the resulting `Deploy` record and its `SHIPIT_USER`/notifications attribute the deploy to `admin-login`, even though `admin-login` never authenticated or approved the request — reachable via [3](#0-2)  and [2](#0-1) .

        @current_api_client = if Shipit.disable_api_authentication

      def create
        commit = stack.commits.by_sha(params.sha) || param_error!(:sha, 'Unknown revision')
        param_error!(:force, "Can't rollback a locked stack") if !params.force && stack.locked?
        deploy = stack.deploys.find_by(until_commit: commit) || param_error!(:sha, 'Cant find associated deploy')
        rollback_env = stack.filter_rollback_envs(params.env)

        response = nil
        if !params.force && stack.active_task?
          param_error!(:force, "Can't rollback, deploy in progress")
        elsif stack.active_task?
          active_task = stack.active_task
          active_task.abort!(aborted_by: current_user, rollback_once_aborted_to: deploy, rollback_once_aborted: true)
          response = active_task
        else
          response = deploy.trigger_rollback(current_user, env: rollback_env, force: params.force, lock: params.lock)
        end

        render_resource(response, status: :accepted)
      end
