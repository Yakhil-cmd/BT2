### Title
Cross-tenant commit status forgery via webhook signature binding mismatch in `StatusHandler` / `Handler` - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/handler.rb`, `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`WebhooksController#verify_signature` selects the `GitHubApp`/secret used to authenticate an inbound webhook using `repository.owner.login` (or `organization.login`) taken from the *same* attacker-controlled JSON body it is about to verify. The handlers that subsequently act on the payload (`Shipit::Webhooks::Handlers::Handler#stacks`, and especially `StatusHandler#process`) do not re-verify that binding — `StatusHandler` in particular ignores `repository` entirely and matches purely on `sha` across the whole installation. This breaks the equality "organization whose credentials authenticated the webhook == repository/commit that is written," analogous to the USDO flash-loan bug where the field an attacker controls (the loan amount / receiver callback) is never covered by the check that is supposed to gate it.

### Finding Description
Signature verification is organization-scoped: [1](#0-0) [2](#0-1) 

`repository_owner` is read straight from the untrusted JSON body (`params.dig('repository','owner','login')`) and used to pick which `GitHubApp` config (and therefore which `webhook_secret`) is used to validate `X-Hub-Signature`: [3](#0-2) 

Crucially, for a top-level (single-org) config, the organization argument is ignored entirely and the single shared secret is used regardless of what `repository.owner.login` says; for a multi-org config (documented and shipped, see `config/secrets.development.example.yml` and `test/dummy/config/secrets_double_github_app.yml`), the config used depends solely on the attacker-supplied `repository.owner.login`. If that org's `webhook_secret` is unset (a supported configuration — the sample files literally comment `webhook_secret: # nil`), verification auto-passes: [4](#0-3) 

Once verification passes, the event handlers determine *what gets written* using unrelated fields of the same payload — not the organization that was used for verification: [5](#0-4) 

`StatusHandler` is the most severe case: it does not scope by repository or organization at all, only by commit `sha`, across the entire Shipit installation: [6](#0-5) 

So the value that gates trust (`repository.owner.login`, used to pick the verifying `GitHubApp`) and the value that determines the blast radius of the write (`sha`, matched globally with no repository check) are two different, independently attacker-supplied fields inside the same unauthenticated JSON body — exactly the "payload field acted on but never covered by the verified signature" binding described in the rules.

### Impact Explanation
An attacker who administers any one organization onboarded to the Shipit instance with no `webhook_secret` configured (a normal, documented, unprivileged setup step — not requiring knowledge of any other org's secret, an `ApiClient` token, or a Shipit session) can send a `status` webhook whose `repository.owner.login` matches their own weak org (causing signature verification to trivially pass) while `sha` names an arbitrary commit belonging to a *different, securely configured* organization/stack tracked by the same Shipit instance. `StatusHandler#process` will happily create a forged commit status for that victim commit via `commit.create_status_from_github!`, because it never checks which repository/org the commit actually belongs to. Forged "success" statuses feed Shipit's deployability/CI-gating and merge-queue logic, allowing an attacker with no access to the victim repository to manufacture the CI signal needed for an unauthorized deploy or auto-merge of a commit in a repository they do not control — a cross-repository write outcome.

### Likelihood Explanation
Multi-organization Shipit deployments are an explicitly documented and supported configuration (`docs/setup.md`, `config/secrets.development.example.yml`). Any org onboarded without a `webhook_secret` (the default/blank value shown in the sample configs) is enough to obtain unconditional signature-verification success for a JSON body the attacker fully controls, at which point the sha-only matching in `StatusHandler` is a straightforward, low-effort way to target arbitrary commits tracked elsewhere in the same instance. No GitHub App private key, `ApiClient` token, or victim repository write access is required.

### Recommendation
- In `WebhooksController#verify_signature`, do not let attacker-controlled payload fields decide which secret verifies the payload's own authenticity when that binding is not cryptographically re-derived from something trusted (e.g., resolve the organization from the installed GitHub App/installation context instead of `repository.owner.login`/`organization.login` taken from the unauthenticated body).
- In every handler (especially `StatusHandler`), scope database lookups by the verified organization/repository, not solely by loosely-typed fields like `sha`; e.g., restrict `Commit.where(sha:)` to commits under repositories owned by the organization that was actually used to verify the signature.
- Require `webhook_secret` to be present for every configured GitHub organization, or otherwise disallow organizations with a blank secret from being used to authenticate cross-tenant events.

### Proof of Concept
1. Configure Shipit with two organizations in `secrets.yml`: `VictimOrg` (proper `webhook_secret`, has a tracked stack/commit `sha=abc123`) and `AttackerOrg` (attacker administers this org's GitHub App installation, leaves `webhook_secret` blank as shown in the shipped example configs).
2. Attacker POSTs to `/webhooks` with header `X-Github-Event: status`, body:
   ```json
   {
     "repository": { "owner": { "login": "AttackerOrg" }, "full_name": "AttackerOrg/whatever" },
     "sha": "abc123",
     "state": "success",
     "context": "ci/required-check"
   }
   ```
   No valid `X-Hub-Signature` needed for `AttackerOrg` because `verify_webhook_signature` returns `true` when `webhook_secret` is blank (`lib/shipit/github_app.rb:76-83`).
3. `WebhooksController#verify_signature` resolves `Shipit.github(organization: 'AttackerOrg')`, verification passes, and `StatusHandler#process` runs `Commit.where(sha: 'abc123')`, matching `VictimOrg`'s commit and creating a forged "success" status on it — despite the request never being signed by `VictimOrg`'s secret.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
