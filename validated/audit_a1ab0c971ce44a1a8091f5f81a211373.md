### Title
Git argument injection via unsanitized `branch` parameter in `CheckoutBranch` - ([File: git/client.go])

### Finding Description
`gitExecuter.CheckoutBranch` in `pkg/cmd/extension/git.go` forwards the `branch` argument directly to `git.Client.CheckoutBranch(ctx, branch)` without any validation. [1](#0-0) 

The underlying `git.Client.CheckoutBranch` builds the argv as `[]string{"checkout", branch}` (per `git/client.go`) and passes it to `Client.Command`, which ultimately shells out to `exec.Command("git", args...)` — there is no `--` separator inserted before the ref argument to force git to treat it as a positional pathspec/ref rather than an option. This means any string the caller passes as `branch` that begins with `-` (e.g. `--orphan`, `-B<newbranch>`) would be interpreted by `git checkout` as a flag rather than a ref name, if such a value ever reaches this call unchecked. In `pkg/cmd/extension/manager.go`, `CheckoutBranch` is invoked with a value derived from repository metadata (e.g. default branch / release ref) during `gh extension upgrade`/`install` flows.

However, the practical exploitability of this pattern is significantly constrained by git's own ref-naming rules (`git check-ref-format`), which explicitly forbid refnames from starting with `-`. Both branches and tags are refs, and GitHub's own ref-creation APIs are backed by git ref validation, so an attacker generally cannot create a real branch or tag whose name begins with a hyphen through normal git/GitHub operations — attempts to `git branch -- --orphan` or push such a ref are rejected server-side. This materially reduces the likelihood of an attacker being able to plant a hostile `branch` value that reaches this specific call path via legitimate default-branch or tag-name metadata.

### Impact Explanation
If a malicious ref name could be supplied, `git checkout` interpreting `branch` as a flag (e.g., `--orphan`) could alter local repository state (e.g., create an orphan branch, discard tracked changes) which is a real "unintended git behavior" impact as scoped. It does not itself achieve code execution but could corrupt local extension state and set up downstream confusion. This matches a moderate "unintended repository state change" impact class rather than direct remote code execution.

### Likelihood Explanation
Low-to-moderate. The precondition — a repo/tag ref name beginning with `-` reaching this code path — is blocked by git's built-in `check-ref-format` restrction on refnames starting with a hyphen, which GitHub enforces when refs (branches/tags) are created via git or the GitHub API. An attacker would need to find an alternate injection point that bypasses git's own ref creation (not identified in the codebase during this review) to actually deliver a hyphen-prefixed value to `CheckoutBranch`.

### Recommendation
As defense-in-depth, regardless of ref-naming restrictions, `Client.CheckoutBranch` (and other ref-consuming git subcommands such as `Clone`, `Fetch`, `Pull`) should insert an explicit `--` separator before user/metadata-derived ref arguments, e.g. `args := []string{"checkout", "--", branch}`, to guarantee git never interprets such values as options even if some other future code path supplies unsanitized input.

### Proof of Concept
Unit test outline for `git/client_test.go`:
```go
func TestClient_CheckoutBranch_RejectsOptionLikeRef(t *testing.T) {
    cs, restore := run.Stub()
    defer restore(t)
    cs.Register(`git checkout -- --orphan`, 0, "") // expect '--' separator present

    client := &Client{GitPath: "path/to/git"}
    err := client.CheckoutBranch(context.Background(), "--orphan")
    assert.NoError(t, err)
}
```
Currently, this assertion would fail because the constructed command is `git checkout --orphan` (no `--`), which git would interpret as the `--orphan` option, and no test in `git/client_test.go` verifies the presence of an option-terminator before ref arguments in `CheckoutBranch`, `Fetch`, `Pull`, or `Clone`.
