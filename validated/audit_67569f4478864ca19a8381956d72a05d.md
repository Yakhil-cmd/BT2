### Title
Incomplete regex-metacharacter escaping in `has_only()` allows a trigger sender to defeat an AA's character-whitelist validation - (File: formula/evaluation.js)

### Summary
The oscript builtin `has_only(str, charset)` is implemented by building a JavaScript `RegExp` character class (`^[...]*$`) directly from the attacker-influenceable `charset` argument. The sanitization applied to `charset` before it is embedded in the regex only rejects a trailing unescaped backslash and escapes literal `]`; it does not neutralize `^` (negation inside a character class) or the `-` range operator. Both operands of `has_only` are ordinary formula expressions, so either argument (including the "whitelist" argument) can be derived from `trigger.data`, i.e. attacker-controlled by whoever sends the trigger unit to the AA.

### Finding Description
`has_only` is parsed generically as `"has_only" "(" expr "," expr ")"` [1](#0-0) , so nothing in the grammar or in `formula/validation.js`'s handling of `has_only` restricts the second argument to a literal string — it is evaluated like any other expression [2](#0-1) .

At evaluation time, the implementation does:
```
if (sub.match(/\\]/) || sub[sub.length - 1] === '\\')
    return setFatalError("invalid character group: " + sub, { arr }, false, cb);
sub = sub.replace(/]/g, '\\]'); // don't allow to close the group early
var bMatches = new RegExp("^[" + sub + "]*$").test(str);
``` [3](#0-2) 

This only guards against a bare `]` prematurely closing the character class and a dangling `\`. It does not:
- Strip or reject a leading `^` in `sub`, which inside `[...]` negates the whole set (`[^...]` means "match anything except these chars"), silently inverting the semantics of the whitelist check.
- Guard against `-` being used to build unintended wide character ranges (e.g. combining fixed and attacker-supplied fragments to form `"0-\uFFFF"`), which can make the "whitelist" match virtually any input.

If an AA author builds a dynamic allow-list this way (a natural oscript pattern — concatenating a fixed prefix/suffix with a piece of `trigger.data`, or reading part of the charset from a previously stored state variable that itself was seeded from trigger data), a malicious trigger sender who controls a substring that ends up inside `sub` can inject `^` or a range-forming `-` to flip or defeat the intended validation, while the AA logic continues to believe the checked string was properly restricted to “safe” characters.

### Impact Explanation
Any AA that relies on `has_only()` as a security gate before trusting a string (e.g., to prevent embedding delimiters/newlines into fields used for state-variable keys, cross-AA messages, data feeds, or address/asset comparisons) can have that gate silently inverted or neutralized. Depending on how the AA subsequently uses the "validated" string, this can lead to state corruption (colliding or malformed state-variable names), unintended branching in the AA's control flow, or unauthorized manipulation of AA-held funds if the sanitized value gates a payout/authorization decision — i.e., AA fund loss or freezing, consistent with the impact categories in scope.

### Likelihood Explanation
Exploitation requires an AA definition where the `charset` argument to `has_only` is not a hard-coded string authored entirely by the AA developer but is, in whole or in part, built from trigger-controlled input or state that a trigger sender can influence over successive triggers. This is a realistic but not universal oscript pattern (dynamic/extensible whitelists), so likelihood is moderate and dependent on specific AA design rather than being universally exploitable against arbitrary AAs.

### Recommendation
In the `has_only` handler in `formula/evaluation.js`, properly neutralize all regex metacharacters that are meaningful inside a character class before constructing the `RegExp`: escape/strip a leading `^`, and escape `-` (or explicitly validate that `sub` only contains literal characters, not raw range syntax) in addition to the existing `]`/trailing-`\` checks, so the resulting behavior always matches "characters literally present in `sub`" regardless of `sub`'s content.

### Proof of Concept
1. Deploy an AA that uses a dynamically composed whitelist, e.g.:
   `require(has_only(trigger.data.name, "a-z0-9" || trigger.data.extra));`
   intending `extra` to only add a few additional literal safe characters.
2. Trigger sender posts a unit with `data.extra = "^"` (or a value producing an unintended range such as `"-\uFFFF"`).
3. The resulting regex becomes `^[a-z0-9^]*$` (harmless) or, with a crafted range, `^[a-z0-9- ... ]*$` matching far more than intended — depending on placement, an attacker can construct payloads where `has_only` returns `true` for `trigger.data.name` values containing characters the AA author intended to reject (e.g. delimiters, control characters), because negation/range injection was not filtered out in `formula/evaluation.js:2037-2049` before being embedded into `new RegExp("^[" + sub + "]*$")`.
