### Title
Cross-Organization Webhook Forgery via Organization/Repository Field Mismatch - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
In a multi-organization Shipit deployment (the documented configuration format shown in `config/secrets.development.shopify.yml`, where multiple GitHub orgs each have their own `webhook_secret`), the field used to select *which organization's secret verifies* an inbound webhook's HMAC signature is different from the field used to determine *which repository/stack the event actually mutates*. This is the same class of bug as the reported "front-run deposit" issue: a value that gates a privileged action (the deposit amount checked at submission vs. the fee applied at execution) is not the same value that is actually acted upon, letting an attacker who controls one side of the binding manipulate the other.

### Finding Description
`Shipit::WebhooksController#verify_signature` selects the GitHub App/webhook secret to validate the signature using only the attacker-supplied JSON body: [1](#0-0) 

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [2](#0-1) 

The HMAC only proves that the request body is unmodified and was generated by *some* org's webhook secret — the org identified by `repository.owner.login`, itself taken from that same unauthenticated body. However, the actual event handlers that mutate application state (sync commits, record CI statuses, update check-runs, etc.) look up the target `Repository`/`Stack` using a *different* field: `repository.full_name`: [3](#0-2) 

```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
```

`PushHandler` (and, by the shared `Handler` base class, other repository-scoped handlers) use exactly this `repository_name`/`stacks` binding to decide which stack receives `sync_github`, statuses, or check-run updates: [4](#0-3) 

Nothing in the pipeline verifies that `repository.owner.login` (used to pick the verifying secret) is consistent with the owner portion embedded in `repository.full_name` (used to pick the mutated repository). Because the entire JSON body is attacker-controlled prior to signing, and the signature only certifies "signed by organization X's secret", an attacker who legitimately controls a GitHub App installation on their *own* organization (e.g., "attacker-org", onboarded to the same shared multi-tenant Shipit instance as documented) knows that org's `webhook_secret` and can compute a valid HMAC for any body. They can then set `repository.owner.login = "attacker-org"` (satisfying the signature check) while setting `repository.full_name = "victim-org/victim-repo"` (which resolves via `Repository.from_github_repo_name` to a completely different tenant's `Stack`).

This breaks the equality the deployment trust model depends on:
`organization whose secret authenticated the request == organization owning the repository being written`

### Impact Explanation
A forged, validly-signed webhook can target any repository/stack tracked by the same Shipit instance, not just the attacker's own. Concretely this allows an attacker to:
- Forge `status`/`check_suite` events reporting `success` for an arbitrary commit SHA on a victim stack, defeating `ci.require`/`blocking` checks that gate `Commit#deployable?` and `MergeRequest#all_status_checks_passed?` — enabling an unauthorized deploy or an unauthorized PR merge on a repository the attacker does not control.
- Forge `push` events that drive `Stack#sync_github(expected_head_sha:)`, potentially causing the victim stack to record an attacker-chosen commit as the new HEAD to track for continuous deployment.

This matches the required High/Critical bar: "escalation ... or an unauthorized deploy, rollback or merge" and reads/writes across the repository/organization boundary the signature is supposed to enforce.

### Likelihood Explanation
Exploitation requires only:
1. The host Shipit instance to be configured for multiple GitHub organizations (an explicitly documented and supported configuration — see `config/secrets.development.shopify.yml`).
2. The attacker to control (or install) a GitHub App/organization entry on that same shared instance — a low bar in shared/internal-tools deployments where many teams' orgs are onboarded to one Shipit instance, and does not require any of the excluded privileges (no Shipit session, no `ApiClient` token, no victim repo write access, no TLS interception).

No race condition or timing dependency is needed — the attacker fully controls and can replay the crafted payload at will, computing a correct signature offline using their own known secret.

### Recommendation
`verify_signature` and the downstream handlers must be bound to the *same* verified identity. Concretely:
- After verifying the signature with the secret keyed by `repository_owner`, re-derive/require that `repository.full_name`'s owner segment (and/or `organization.login` for org-level events) exactly matches the `repository_owner` that authenticated the request, rejecting (422) on mismatch.
- Alternatively, resolve the `GitHubApp`/secret independently for the event's declared `repository.full_name` owner, and refuse to process the event if the resolved app for the "full_name" owner doesn't match the one whose secret validated the HMAC.

### Proof of Concept
Assume a shared instance configured per `config/secrets.development.shopify.yml` with orgs `attacker-org` (secret known to attacker, who installed the App there) and `victim-org` (a genuine tracked stack).

1. Attacker builds a `status` webhook payload:
```json
{
  "sha": "<victim-target-sha>",
  "state": "success",
  "context": "ci/required",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" }
}
```
2. Attacker computes `X-Hub-Signature: sha1=HMAC(attacker-org-webhook-secret, raw_body)`.
3. `WebhooksController#verify_signature` calls `Shipit.github(organization: "attacker-org")`, which succeeds (attacker's own secret matches).
4. `Shipit::Webhooks.for_event('status')` dispatches to the status handler, which resolves the repository via `payload.dig('repository','full_name') == "victim-org/victim-repo"`, locating and mutating the real victim `Stack`'s commit status — despite the request never being signed by `victim-org`'s webhook secret.

Note: I was unable to fully inspect `app/models/shipit/webhooks/handlers/status_handler.rb`, `check_suite_handler.rb`, `lib/shipit.rb#github`, and `app/models/shipit/repository.rb#from_github_repo_name` in this session (index truncation cut off before I could pull their full bodies), so I could not confirm line-by-line that every repository-scoped handler exclusively uses `full_name` with zero cross-check against `repository.owner.login`. The `Handler` base class and `PushHandler` I did inspect confirm the pattern; a Devin session with full repository access should verify `status_handler.rb`/`check_suite_handler.rb` and `lib/shipit.rb` to confirm the identical `full_name`-based lookup and finalize the fix.

# frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
    end
  end
end
