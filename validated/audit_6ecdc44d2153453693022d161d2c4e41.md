### Title
Webhook signature is verified against the organization implied by `repository.owner.login`, but every event handler resolves the target repository/stack from the unrelated `repository.full_name` field, allowing an app-installer for *any* configured GitHub organization to write status/CI/sync events onto stacks belonging to a *different* organization - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects which organization's `webhook_secret` to check the HMAC against using `repository_owner`, a value taken from `params.dig('repository', 'owner', 'login')` (or `organization.login`). [1](#0-0) [2](#0-1)  Once the signature is accepted, every handler (`PushHandler`, `StatusHandler`, `CheckSuiteHandler`, etc.) resolves the *actual* repository/stack to mutate from a completely different field, `repository.full_name`, via `Handler#repository_name`/`#stacks`. [3](#0-2)  Nothing ties `repository.owner.login` to `repository.full_name` - Shipit never checks that the organization whose secret authenticated the request is the owner of the repository the payload claims to describe.

### Finding Description
In a multi-organization deployment (documented in `docs/setup.md`, "Using Multiple Github Applications"), each organization gets its own `github` config block with its own `app_id`, `installation_id`, and `webhook_secret`, all independently controlled by whoever installs/administers the GitHub App for that org. [4](#0-3)  `Shipit.github(organization:)` looks up the correct `GitHubApp` (and thus the correct `webhook_secret`) purely from the `organization` string that `WebhooksController` extracts from the incoming payload. [5](#0-4) 

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [6](#0-5) 

`verify_webhook_signature` only checks that the raw body matches an HMAC computed with that organization's `webhook_secret` - it never checks that the body's `repository.owner.login` actually corresponds to `repository.full_name`: [7](#0-6) 

```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  algorithm, signature = signature.split("=", 2)
  return false unless algorithm == 'sha1'
  SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
end
```

Because the attacker crafts and signs the entire raw HTTP body themselves (they know their own org's `webhook_secret`, since they administer that GitHub App installation), they control every field in the JSON, including `repository.owner.login`/`organization.login` (used only to *pick the key*) and `repository.full_name` (used to *pick the target*). These can be set independently: `repository.owner.login = "attacker-org"` (so `Shipit.github(organization: "attacker-org")` returns the attacker's own known secret and the HMAC check passes) while `repository.full_name = "victim-org/some-repo"` (so `Repository.from_github_repo_name` resolves to a stack that belongs to a totally unrelated, victim organization). [8](#0-7)  Every handler trusts `repository.full_name` blindly:

```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [3](#0-2) 

This breaks exactly the trust binding the analog targets: *the organization that authenticated the webhook* (`repository.owner.login`, checked against a specific org's `webhook_secret`) is not the same as *the repository that gets written* (`repository.full_name`, used unchecked by every handler).

### Impact Explanation
An attacker who legitimately administers the GitHub App installation for one configured organization (a completely unprivileged party with respect to any other organization or to Shipit itself) can forge webhook deliveries that are accepted as authentic and applied against stacks owned by any *other* organization configured on the same Shipit instance:
- `StatusHandler` writes arbitrary CI `Status` rows (`state: "success"`) onto any commit `sha` in the victim's stacks, which can satisfy `deployable?`/status checks and enable an unauthorized deploy through continuous delivery. [9](#0-8) 
- `CheckSuiteHandler` and `PushHandler` can trigger sync/refresh jobs (`schedule_refresh_check_runs!`, `sync_github`) against victim stacks on demand. [10](#0-9) [11](#0-10) 

Forged, org-crossing writes of CI status that gate deploys map to the "unauthorized deploy" / "cross-repository writes" Critical-impact bucket described in scope.

### Likelihood Explanation
Requires only that the Shipit instance is configured with more than one GitHub organization (an explicitly documented, supported configuration) and that the attacker controls (as an app installer/admin, not a Shipit-privileged account) the GitHub App/webhook secret for at least one of those organizations - no `ApiClient` token, `Shipit` session, or GitHub App private key for the *victim* org is needed. This is a realistic, moderate-likelihood scenario for any multi-tenant Shipit deployment.

### Recommendation
In `WebhooksController#verify_signature`, after verifying the HMAC, cross-check that `repository.owner.login` (the org whose secret validated the request) matches the owner encoded in `repository.full_name` (and `organization.login` where present) before dispatching to handlers; reject with `422` on mismatch. Alternatively, derive the organization used for handler dispatch/lookup from the same verified field used for signature selection, rather than trusting `repository.full_name` independently.

### Proof of Concept
Configuration: two orgs, `attacker-org` and `victim-org`, each with distinct `webhook_secret`s (per `docs/setup.md`, "Using Multiple Github Applications").

1. Attacker computes `sig = HMAC-SHA1(attacker_org_webhook_secret, body)` for a crafted payload:
```json
{
  "sha": "<victim commit sha>",
  "state": "success",
  "context": "ci/tests",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" }
}
```
2. POST to `/webhooks` with header `X-Github-Event: status` and `X-Hub-Signature: sha1=<sig>`.
3. `verify_signature` calls `Shipit.github(organization: "attacker-org")` (from `repository.owner.login`), succeeds because the attacker knows that secret. [1](#0-0) 
4. `StatusHandler#process` runs against `Commit.where(sha: params.sha)`, matching the victim's commit (looked up globally, not scoped by the verified org), and records a forged successful status for it. [9](#0-8) 

Note: I could not fully trace whether `commit.create_status_from_github!` or downstream deploy-eligibility logic (`Stack#deployable?` and continuous delivery gating) applies any additional owner/organization cross-check beyond commit `sha` matching, since the relevant methods (`Commit#create_status_from_github!`, `Stack` deployability checks) were not retrieved in full during this session; this should be confirmed by a background agent with full file access before treating the deploy-unlock impact as certain, though the cross-organization write of `Status`/triggering of `sync_github`/`schedule_refresh_check_runs!` on an unrelated org's stack is confirmed by the code shown above.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end
