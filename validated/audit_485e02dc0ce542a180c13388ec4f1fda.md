### Title
Webhook signature is verified against the organization named in an unauthenticated field while the event is applied to whatever repository/team the same unauthenticated payload names - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks *which* organization's `webhook_secret` to check the HMAC against by reading an unauthenticated field of the incoming JSON body (`repository.owner.login` / `organization.login`), then verifies the raw body against that org's secret. Every downstream handler, however, resolves the actual repository/team to mutate using a *different* unauthenticated field of the very same body (`repository.full_name`, `team.id`, `organization.login`). Nothing ties "the org whose secret produced a valid signature" to "the repository/team the handler actually writes to." This mirrors the reported bug class: code assumes a field it doesn't fully validate is inert/consistent with the field it trusts, when in fact the two can diverge.

### Finding Description
`repository_owner` is computed from raw, unverified JSON before any cryptographic check occurs: [1](#0-0) 

That value selects the `GitHubApp`/`webhook_secret` used to verify the HMAC over the whole raw body: [2](#0-1) 

`verify_webhook_signature` only proves that the request came from someone in possession of *that selected organization's* `webhook_secret` — it says nothing about which repository/team the payload targets: [3](#0-2) 

Once the signature check passes, `Handler#stacks`/`#repository_name` resolve the target purely from `repository.full_name`, a sibling field of the same JSON body that was never cryptographically bound to the org used above: [4](#0-3) 

The same pattern repeats in every pull-request handler (`repository.full_name` drives `Repository.from_github_repo_name`) and, most impactfully, in `MembershipHandler`, which creates/updates a `Team` and adds/removes members based on `params.team` and `params.organization.login` taken from the same unauthenticated body: [5](#0-4) 

`Team` membership feeds directly into `Shipit.github_teams`, which is the OAuth authorization gate for the whole application: [6](#0-5) 

Because Shipit supports multiple GitHub organizations sharing a single instance (`github_app_config`/`TOP_LEVEL_GH_KEYS`), an attacker who legitimately controls (or has leaked) the `webhook_secret` for **one** onboarded organization (Org A) — which is not a privileged Shipit account, `ApiClient` token, or GitHub App private key — can compute a valid `X-Hub-Signature` over a forged JSON body whose `repository.owner.login`/`organization.login` says "Org A" (so the correct secret is picked and verification passes) while `repository.full_name`, `team`, or `member.login` reference a completely different organization/repository/team (Org B) that Shipit also serves: [7](#0-6) 

The binding broken: **organization that authenticated the request (`repository_owner` ⇒ `webhook_secret` used) ≠ repository/team the handler actually writes to (`repository.full_name`/`team`/`member` used by the handler)**. This is the direct analog of the report's core flaw: trusting one field's implied semantics ("Call doesn't move value") while a sibling field of the same message actually determines the real effect ("value moves regardless of kind").

### Impact Explanation
Via the `membership` event, an attacker holding a valid webhook secret for any one org configured on the instance can add an arbitrary GitHub login as a member of any `Team` record (including teams tied to a *different* organization's `oauth.teams` authorization list), escalating into `Shipit.github_teams` authorization — meeting the High-severity bar defined by the rules ("escalation into `Shipit.github_teams` authorization"). Via `push`/`pull_request`/`status`/`check_suite` events, the same technique lets the attacker trigger `sync_github`, review-stack provisioning/deprovisioning, and status writes against stacks belonging to repositories they do not own, i.e. actions cross-bound to a repository never authenticated by the presented signature.

### Likelihood Explanation
Requires only that the instance is configured for multiple organizations (a documented, supported configuration — see `secrets.development.shopify.yml` / `docs/setup.md` multi-org example) and that the attacker controls a legitimate webhook secret for at least one of those organizations (something an org owner/admin of their own GitHub org can set without any Shipit privilege). No Shipit session, `ApiClient` token, or GitHub App key is needed — only crafting a JSON body with mismatched `repository.owner.login`/`organization.login` vs. `repository.full_name`/`team`, which is trivial once one secret is known.

### Recommendation
Bind the field used to select the verification secret to the field(s) used by every handler to determine the mutation target, e.g.: require that `repository.owner.login` (or `organization.login`) used to pick the `webhook_secret` equals the owner segment of `repository.full_name` before dispatching, and reject the payload otherwise; alternatively, dispatch handlers only within the resolved organization scope, not by decoupled field lookups. `MembershipHandler` should further validate that `params.organization.login` matches the organization whose `webhook_secret` verified the request before creating/mutating a `Team`.

### Proof of Concept
1. Instance is configured with two orgs, `orgA` and `orgB`, each with its own `webhook_secret` (per `docs/setup.md` multi-org schema, `lib/shipit.rb:170-200`).
2. Attacker is a member/owner of `orgA` on GitHub (or otherwise knows/has been shown `orgA`'s `webhook_secret`) and configures a webhook from `orgA` (or crafts a raw POST) with body:
```json
{
  "action": "added",
  "team": {"id": 999, "name": "OrgB Admins", "slug": "orgb-admins", "url": "https://api.github.com/orgs/orgB/teams/orgb-admins"},
  "organization": {"login": "orgB"},
  "member": {"login": "attacker-controlled-login"},
  "repository": {"owner": {"login": "orgA"}, "full_name": "orgB/some-repo"}
}
```
3. `WebhooksController#repository_owner` reads `repository.owner.login` = `"orgA"` → `verify_signature` uses `orgA`'s `webhook_secret` (`app/controllers/shipit/webhooks_controller.rb:59-62`, `lib/shipit/github_app.rb:76-83`), which the attacker computed correctly.
4. Signature passes; `MembershipHandler#process` is invoked with the full unauthenticated body, creates/updates `Team` for `orgB` and adds the attacker's login as a member (`app/models/shipit/webhooks/handlers/membership_handler.rb:22-43`), even though the signature never proved authorization for `orgB`.
5. If `orgB/orgb-admins` maps to an entry in `secrets.github.orgB.oauth.teams`, the attacker's added login now satisfies `Shipit.github_teams` authorization for `orgB`'s Shipit instance/oauth gate (`lib/shipit.rb:256-258`).

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
