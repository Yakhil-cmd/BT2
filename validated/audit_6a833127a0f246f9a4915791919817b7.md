### Title
`StatusHandler` applies attacker-forged GitHub statuses to commits in any stack sharing the same SHA, because it performs zero repository scoping - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` runs `Commit.where(sha: params.sha).each { |c| c.create_status_from_github!(params) }` with no filter on repository or stack. The webhook's signature is verified against the org/repo the attacker names in `repository_owner` (with a fallback from `repository.owner.login` to `organization.login`), which is entirely decoupled from which commits get mutated, since the handler never reads `repository.full_name` at all.

### Finding Description
The broken binding is: *the entity that authenticates a `status` webhook (`repository_owner` used in `Shipit.github(organization: repository_owner)`, in `app/controllers/shipit/webhooks_controller.rb:25,59-62`) MUST equal the entity whose data is mutated by the handler*. That binding does not hold.

- `WebhooksController#verify_signature` resolves `repository_owner` as `params.dig('repository','owner','login') || params.dig('organization','login')` [1](#0-0)  and uses it solely to pick which `GitHubApp`/webhook secret verifies the HMAC signature [2](#0-1) .
- `StatusHandler#params` never requires or reads `repository` at all — only `sha`, `state`, `description`, `target_url`, `context`, `created_at`, `branches` [3](#0-2) .
- `process` looks up commits purely `by sha`, globally, across every stack in the database, and calls `create_status_from_github!` on each match [4](#0-3) .

So an attacker who controls **their own** GitHub repository configured in the same Shipit instance (owns/knows its `webhook_secret`) can send a `status` webhook that passes signature verification (since verification is keyed off `repository_owner`, which the attacker fully controls and which matches their own org), while the resulting status is written against **any** `Commit` record in the database whose `sha` matches — including commits belonging to a victim's stack, if that sha happens to also exist there (e.g., shared commits from forks, cherry-picks, rebases onto a common base, or simply a commit sha the attacker read from the victim's public GitHub history and replayed).

This directly produces a write for a repository that did not authenticate it: `Status.replicate_from_github!(stack_id, github_status)` creates a `Shipit::Status` row tied to the *victim's* `stack_id` (taken from `commit.stack_id`, not from the authenticated webhook) [5](#0-4) [6](#0-5) .

`Commit#add_status` then evaluates deployability transitions and, if the new status makes the commit `pending?` or `success?`, calls `stack.schedule_merges` and (via `Status#schedule_continuous_delivery`) `commit.schedule_continuous_delivery` [7](#0-6) [8](#0-7) . `schedule_continuous_delivery` enqueues `ContinuousDeliveryJob` if `deployable? && stack.continuous_deployment? && stack.deployable?` [9](#0-8) , and the job then calls `stack.trigger_continuous_delivery` [10](#0-9) , which executes an actual deploy task using the stack's configured deploy identity/credentials (bot_login or otherwise).

None of the existing guards prevent this: `verify_signature` only checks HMAC validity for whichever org the attacker names, it never cross-checks that the org owns the commits being mutated; `ExplicitParameters` (`params do ... end` in `StatusHandler`) only validates the shape of `sha`/`state`/etc., not repository ownership; there is no `stack_id`/`repository_id` filter anywhere in the query.

### Impact Explanation
An attacker who legitimately owns any repository connected to the same Shipit instance (or even just knows a `webhook_secret` for a lenient/fallback org path) can forge `success` statuses for arbitrary commits in a victim's stack simply by replaying that commit's SHA (public information on GitHub) in a `status` payload signed with their own webhook secret. Because status changes can flip `deployable?` to true and trigger `ContinuousDeliveryJob` → `stack.trigger_continuous_delivery`, this can cause an **unauthorized deploy** of attacker-influenced or unreviewed code in the victim's repository, executed under the victim stack's configured deploy identity (e.g., the `bot_login` service account and its `GITHUB_TOKEN`/deploy credentials). This is a cross-tenant impact (Repo A's authenticated webhook mutates Repo B's stack state and can trigger Repo B's deploy pipeline), matching the "Critical: unauthorized deploy" and "payload for one repository mutating another's stack" categories.

### Likelihood Explanation
Preconditions: the attacker must control at least one repository/organization registered in the target Shipit instance (to have a valid `webhook_secret` to sign with), and the victim stack must have a commit whose SHA also appears in a commit reachable by the attacker (fork relationship, shared base commit, cherry-pick, or an attacker simply pushing/faking a commit with a colliding message but real SHA taken from the victim's public commit history — no SHA collision needed, just identical SHA value copied verbatim, since `Commit.where(sha:)` matches by exact SHA string). This is a low-cost, fully repeatable attack: one crafted POST per target commit, no GitHub or Shipit privileged secrets needed beyond the attacker's own webhook secret for their own registered repo.

### Recommendation
Scope `StatusHandler#process` (and any other handler with a similar pattern) to only mutate commits belonging to the stack(s) whose `repository.full_name`/`owner/name` matches the one that was actually cryptographically authenticated in `WebhooksController#verify_signature`. Concretely, thread the verified repository identity (not the attacker-suppliable `repository_owner`/`organization.login` fallback alone, but the full `owner/repo` pair) into the handler context, and change `Commit.where(sha: params.sha)` to `Commit.where(sha: params.sha, stack: Stack.where(repository: matching_repository))`, or require `repository.full_name` in `StatusHandler#params` and use it to scope the query.

### Proof of Concept
1. In `test/models/shipit/webhooks/handlers/status_handler_test.rb` (or wherever handler tests live), set up:
   - `attacker_repo` / `attacker_stack` with a known `webhook_secret` (`org: 'attacker-org'`).
   - `victim_repo` / `victim_stack` configured with `bot_login` set, `continuous_deployment: true`, and a `Commit` with `sha: 'deadbeef...'` currently in `pending`/unknown state, with `stack.deployable?` conditions otherwise satisfied.
2. Also create a `Commit` with the identical `sha` under `attacker_stack` (simulating a shared/forked commit).
3. POST to `/webhooks` with `X-Github-Event: status`, a body containing `{"sha": "deadbeef...", "state": "success", "repository": {"owner": {"login": "attacker-org"}}}` (no victim repo reference at all), signed with `attacker`'s `webhook_secret`.
4. Assert:
   - LHS of the invariant: `repository_owner` resolved by the controller == `"attacker-org"`.
   - RHS: a `Shipit::Status` row with `state: "success"` now exists with `stack_id == victim_stack.id` (`Shipit::Status.where(stack_id: victim_stack.id, state: 'success').exists?` is `true`), proving the victim stack was mutated by a webhook that never authenticated as the victim's repository.
   - Additionally assert `ContinuousDeliveryJob` was enqueued for `victim_stack` (`assert_enqueued_with(job: Shipit::ContinuousDeliveryJob, args: [victim_stack])`), demonstrating the unauthorized-deploy trigger path.

    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
