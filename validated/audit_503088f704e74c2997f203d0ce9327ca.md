Based on my investigation, I could not gather enough verified evidence to produce a supportable, submission-ready vulnerability analog for CVE-2019-3785, and I ran out of tool-call budget before fully confirming a critical fact. I'll lay out what I found and where the uncertainty lies.

## What the CVE's invariant maps to

The CVE's core pattern is: a capability granted for a narrow purpose (read access) is not properly scoped, and the same signed credential ends up usable for a broader purpose (write access) — i.e., an authorization check that is supposed to deny a class of actions fails to actually deny all of them.

The closest structural analog in this codebase is `pallet-proxy`'s `InstanceFilter<RuntimeCall>` implementations, specifically the `ProxyType::NonTransfer` variant, which is documented as "can execute any call that does not transfer funds or assets" but is implemented as a **deny-list**, meaning it fails open: any call family not explicitly listed is allowed [1](#0-0) .

## Evidence this exact bug class already existed and was fixed

This is not a hypothetical — the identical bug class was found and patched in this repo for `asset-hub-westend-runtime` and `pallet-staking-async-parachain-runtime`:

- `prdoc/pr_12771.prdoc` documents that `ForeignAssets`, `PoolAssets`, `AssetConversion`, `Psm`, `PolkadotXcm`, `Revive`, and `Indices::transfer`/`force_transfer` were all reachable through a `NonTransfer` proxy despite moving the delegator's funds or assets [2](#0-1) .
- `prdoc/pr_12922.prdoc` documents the same class of omission (missing `ForeignAssets`/`PoolAssets`) in the `staking-async` parachain runtime [3](#0-2) .
- Regression tests were added specifically to prevent recurrence, e.g. `non_transfer_proxy_rejects_value_moving_calls` and `non_transfer_proxy_is_not_a_superset_of_governance` [4](#0-3) [5](#0-4) .

This matters because `pallet-proxy::do_proxy` uses exactly this filter to gate what a delegate can execute on behalf of the real account [6](#0-5) , and `add_proxy`/`remove_proxy` escalation is separately guarded by `is_superset`, which was also found broken for the `Governance` proxy type in the same class of bug.

## The unresolved lead I could not verify

`asset-hub-rococo-runtime`'s `ProxyType::NonTransfer` filter still only denies `Balances`, `Assets`, `NftFractionalization`, `Nfts`, and `Uniques` [7](#0-6)  — it does **not** contain the additional denials (`ForeignAssets`, `PoolAssets`, `AssetConversion`, `PolkadotXcm`, `Revive`, `Indices::transfer`) that were added to `asset-hub-westend` in `pr_12771`. This raises the question of whether `asset-hub-rococo` has the same unpatched deny-list gap.

However, I exhausted my tool-call budget before I could confirm the critical prerequisite fact: **whether `asset-hub-rococo-runtime`'s `construct_runtime!` actually wires in pallets like `ForeignAssets`, `PoolAssets`, `AssetConversion`, `PolkadotXcm`, `Revive`, or a value-moving `Indices::transfer` as reachable `RuntimeCall` variants at all.** My grep for these pallet names in that file returned 117 matches, but I could not distinguish genuine `RuntimeCall::X` construct_runtime entries from unrelated occurrences (imports, config types, comments) within the remaining iteration budget.

Additionally, even if confirmed, Rococo and Westend are both public testnets, not live production value-bearing networks, so eligibility under a live Parity bounty program (which typically requires reproduction on a covered, value-bearing network/version) is itself unverified and doubtful for a testnet-only Asset Hub instance.

## Conclusion

I cannot respectfully issue the strict vulnerability report format requested, because I have unresolved uncertainty on:
1. Whether `asset-hub-rococo` actually has the value-moving pallets in question wired into its `RuntimeCall` enum (unconfirmed due to tool budget).
2. Whether a testnet-only Asset Hub instance is in scope for any live bounty program.

Given the instructions to not speculate or guess, and that I cannot confirm reachability and eligibility, I am not able to certify a supportable finding. If you'd like, a follow-up session with additional investigation could confirm the `construct_runtime!` pallet list for `asset-hub-rococo` and settle whether this deny-list gap is real and reachable.

fn non_transfer_proxy_rejects_value_moving_calls() {

	// Collected rather than asserted one by one, so a regression reports every call that slipped
	// through instead of only the first.
