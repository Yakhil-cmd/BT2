### Title
Missing oracle-count cap in `data_feed`/`in_data_feed` AA formula validation allows unbounded per-unit computation - ([File: formula/validation.js])

### Summary
`formula/validation.js`'s `validateDataFeed()` — the function that computes the fixed "complexity" cost charged for a `data_feed`/`in_data_feed` operation inside an AA — does not cap the number of oracle addresses that can be packed into the `oracles` parameter, and the line that would have scaled complexity with the address count is commented out. [1](#0-0) 

### Finding Description
`validateDataFeed(params)` only rejects an empty `oracles` string; it never bounds `addresses.length`, and the complexity contribution for extra addresses is disabled:
```
var addresses = value.split(':');
if (addresses.length === 0) return {error: 'empty oracle list', complexity};
//	complexity += addresses.length;
if (!addresses.every(ValidationUtils.isValidAddress)) return {error: 'oracle address not valid', complexity};
``` [2](#0-1) 

This is the validator used for the `data_feed` and `in_data_feed` oscript operators evaluated during AA definition/getter validation, so the declared `complexity` (which gates `MAX_COMPLEXITY`/`MAX_OPS` for a whole unit) stays constant (1) no matter how many `:`-separated oracle addresses are supplied.

At evaluation time, `evaluate()`'s `data_feed`/`in_data_feed` cases split the same `oracles` string into `arrAddresses` with no re-check of its size, and pass it straight into `dataFeeds.readDataFeedValue`/`dataFeeds.dataFeedExists`. [3](#0-2) [4](#0-3) 

Both `readDataFeedValue` and `dataFeedExists` then iterate the full, attacker-supplied address list with `async.eachSeries`, and for each address `dataFeedByAddressExists`/`readDataFeedByAddress` opens a fresh LevelDB key-range stream lookup: [5](#0-4) [6](#0-5) [7](#0-6) 

By contrast, the non-AA (bounced-message/light) helper `readDataFeedValueByParams` explicitly caps the oracle list at 10 addresses before doing the same lookup: [8](#0-7) 

No such cap exists on the AA-formula path, so an AA author can define a getter/trigger-handler formula containing `oracles='ADDR1:ADDR2:...:ADDRn'` with an arbitrarily large `n` (bounded only by the overall string/unit size limits, which are orders of magnitude larger than 10), and every full node that validates/executes any unit triggering that AA must perform `n` separate DB range-scans per `data_feed`/`in_data_feed` call, while the complexity/op budget charged for it never reflects `n`.

### Impact Explanation
This is directly analogous to the reported Pyth issue: the actual resource cost of an external/expensive operation scales with an attacker-controlled list length (`idList.length` in Pyth vs. the oracle address count here), but the code that is supposed to bound/account for that cost (the `value`/gas computation in Pyth, the `complexity` charge here) ignores the list length. Because AA `complexity`/`count_ops` accounting is the mechanism that keeps a single unit's AA-triggered execution bounded and reproducible across all full nodes, decoupling the real DB-scan cost from the charged complexity lets a malicious AA author (an unprivileged "asset issuer"/AA definition author) craft an AA whose trigger execution is far more expensive than its declared complexity permits. Nodes validating/executing units that trigger such an AA (e.g., during stabilization when `markMcIndexStable`→`addDataFeeds` and AA responses are computed) incur disproportionate, unbounded I/O work, which can slow or stall processing of new units on the network — the network-cannot-confirm-new-units impact class.

### Likelihood Explanation
Likelihood is high: any user can post an AA definition unit containing an oscript formula with `data_feed[[oracles='A1:A2:...:An', feed_name=...]]` or `in_data_feed[[...]]`, then send a trigger unit to that AA. No special privileges are required, and the malformed complexity accounting is not caught anywhere else in `formula/validation.js` (the analogous, correctly-bounded check exists only in the separate `readDataFeedValueByParams` helper in `data_feeds.js`, not in the AA-formula path).

### Recommendation
Restore/enable the complexity scaling with `addresses.length` in `validateDataFeed()` (uncomment and tune the `complexity += addresses.length;` line), and additionally enforce an explicit maximum oracle-address count (mirroring the `oracles.length > 10` cap used in `readDataFeedValueByParams`) in both `validateDataFeed()` and at evaluation time in `formula/evaluation.js`'s `data_feed`/`in_data_feed` cases before invoking `dataFeeds.readDataFeedValue`/`dataFeeds.dataFeedExists`.

### Proof of Concept
1. Define an AA (or plain address definition, if `in data feed` is reachable there too) whose getter/trigger-handling formula contains:
   `data_feed[[oracles='ADDR1:ADDR2:...:ADDR200', feed_name='X']]`
   using 200 distinct valid Obyte addresses joined by `:`.
2. Submit this AA definition unit; `validateDataFeed()` accepts it because it only checks non-emptiness and per-address validity, charging complexity = 1 regardless of the 200 addresses. [2](#0-1) 
3. Post a trigger unit to the AA. During evaluation, `getDataFeed`/`in_data_feed` splits the 200 addresses and calls `dataFeeds.readDataFeedValue`/`dataFeeds.dataFeedExists`, which run 200 sequential LevelDB range-stream lookups per call. [5](#0-4) [7](#0-6) 
4. Repeating the `data_feed[[...]]` expression multiple times within the complexity budget (since each call's declared complexity is only 1) multiplies the real per-unit DB work far beyond what `MAX_COMPLEXITY`/`MAX_OPS` intend to bound, unlike the capped, non-AA `readDataFeedValueByParams` path. [8](#0-7)
