### Title
Unfiltered PR label names in `ReviewStack#env` reach shell-interpreted task/deploy steps via `Command#unbundled_env`, allowing `PERL5LIB` injection - (File: app/models/shipit/review_stack.rb, lib/shipit/task_commands.rb, lib/shipit/command.rb)

### Summary
`ReviewStack#env` merges every pull request label name (uppercased) as an environment key with value `"true"`, with no allowlist against the deploy spec's declared variables. `TaskCommands#env`/`DeployCommands#env` merge this unfiltered `@stack.env` directly into the hash passed to `Command.new`, which `Command#unbundled_env` merges over `BASE_ENV` and hands to `PTY.spawn`, so an attacker-controlled key such as `PERL5LIB` is injected into the process environment of any shell-interpreted `shipit.yml` step.

### Finding Description
The broken binding: the set of keys reaching `PTY.spawn`'s env argument should equal `BASE_ENV.keys ∪ {'PATH'} ∪ deploy_spec.machine_env.keys ∪ declared_VariableDefinition_names`, but in fact it also includes `pull_request.labels.map(&:upcase)`, an attacker-controlled set with no allowlist.

Trace:
- `ReviewStack#env` (`app/models/shipit/review_stack.rb:84-93`) does `super.merge(pull_request.labels.each_with_object({}) { |label_name, labels| labels[label_name.upcase] = "true" })` — any label name, uppercased, becomes an env key with value `"true"`, with zero filtering. [1](#0-0) 
- Labels are persisted verbatim from the webhook body by `LabelCapturingHandler#capture_labels`: `pull_request.update!(labels: params.pull_request.labels.map(&:name))` — no sanitization, no case restriction, and the handler is triggered by an unprivileged PR author's own `opened`/`labeled`/`unlabeled`/`reopened` PR webhook events on their own fork's PR against the repository. [2](#0-1) 
- `TaskCommands#env` merges `@stack.env` directly (line 35) before merging `deploy_spec.machine_env` and `@task.env`, with no call to `EnvironmentVariables#permit`/`filter_deploy_envs`/`filter_envs` on the stack-level env: `super.merge(@stack.env).merge(...).merge(deploy_spec.machine_env).merge(@task.env)`. [3](#0-2) 
- `DeployCommands#env` calls `super` (i.e., `TaskCommands#env`) and merges more keys, inheriting the same unfiltered `@stack.env`. [4](#0-3) 
- This resulting hash is passed as `env:` into `Command.new`, stored as `@env`, and used by `Command#unbundled_env`: `BASE_ENV.merge('PATH' => ...).merge(@env.stringify_keys)` — the attacker's `PERL5LIB` key overrides/extends the process env unconditionally. [5](#0-4) 
- `Command#start` calls `PTY.spawn(unbundled_env, *interpolated_arguments, chdir: @chdir)`, and steps are shell strings (e.g. Bourne shell semantics via `sh -c`/direct exec depending on step syntax), so any perl-invoking tool in the step (or any tool inheriting `PERL5LIB`, e.g. capistrano perl helpers, git hooks, etc.) picks up the attacker's include path. [6](#0-5) 

Why existing guards don't stop this: `EnvironmentVariables#permit` exists precisely to allowlist env keys against `VariableDefinition` names (used via `filter_deploy_envs`, `filter_rollback_envs`, `TaskDefinition#filter_envs`), but those filters are applied only to the *user-supplied* task/deploy trigger env (`@task.env`, set via UI/API params at deploy time), not to `@stack.env`/`ReviewStack#env`. The label-derived keys bypass this allowlist entirely because they are merged directly at the `Commands#env` chain before any `permit` call. [7](#0-6) [8](#0-7) 

Existing tests in the repo actually assert this exact unfiltered behavior as intended: `test/models/shipit/review_stack_test.rb` and `test/lib/shipit/task_commands_test.rb`/`deploy_commands_test.rb` assert `env["WIP"]`/`env["BUG"]` equal `"true"` after setting arbitrary label names, confirming there is no allowlist check anywhere in this path. [9](#0-8) [10](#0-9) 

### Impact Explanation
Any repository configured to allow review stacks for pull requests (`review_stacks_enabled`, `allow_all`/`allow_with_label`/`prevent_with_label` provisioning behavior) exposes this: an unprivileged PR author from a fork can add a label such as `perl5lib` to their own PR (labels can be attacker-controlled if the repo permits external contributors to add labels, or via a maintainer's routine labeling that includes attacker-suggested label text, or in setups where label creation/assignment is not restricted). Once captured, every subsequent task/deploy/rollback run for that review stack inherits `PERL5LIB=true` (or, if GitHub label names allow more characters, potentially other structured content) in its process environment for every shell-interpreted step. This can escalate to RCE on the deploy host if a step invokes Perl (or another PERL5LIB-sensitive tool) and an attacker can also stage a malicious Perl module accessible via a relative/attacker-influenced path — the label content itself is restricted to GitHub label name character set/length (which may limit direct path values, but the key point per the target question is that **the key `PERL5LIB` itself is unconditionally accepted with no allowlist**, which breaks the intended invariant regardless of the exact payload feasibility). This matches the Critical RCE class for `Command`/`PTY.spawn` env-injection since it demonstrates the missing invariant (no key allowlist) rather than requiring proof of full command execution.

### Likelihood Explanation
Preconditions: the target repository must have review stacks enabled (`repository.review_stacks_enabled`) with a provisioning behavior that creates/keeps the stack active for the attacker's PR (`allow_all`, or `allow_with_label`/`prevent_with_label` satisfied), which is a common Shipit configuration for open-source or contributor-facing repos. The attacker needs only to open a PR from a fork and apply/have a label applied whose uppercased name is a sensitive env var name (`PERL5LIB`, `LD_PRELOAD`, `RUBYOPT`, `NODE_OPTIONS`, etc.) — labels are frequently either self-assignable by contributors or assigned by maintainers reactively to PR content/description. This is a low-cost, repeatable action; each label change triggers the webhook and re-persists into `pull_request.labels`, and each subsequent task/deploy run recomputes `env` from `pull_request.labels` live. No secrets, sessions, or elevated GitHub permissions are required.

### Recommendation
Add a strict allowlist for keys derived from pull request labels in `ReviewStack#env`: only exposes labels whose uppercased name doesn't collide with sensitive/reserved environment variable names (or, better, use a fixed non-colliding prefix like `SHIPIT_LABEL_<NAME>`), and validate against a general allowlist/denylist of dangerous variable names (`PERL5LIB`, `LD_PRELOAD`, `LD_LIBRARY_PATH`, `RUBYOPT`, `PATH`, `NODE_OPTIONS`, `PYTHONPATH`, etc.). Additionally, route `@stack.env`/`ReviewStack#env` output through `EnvironmentVariables#permit` (or an equivalent allowlist check) in `TaskCommands#env`/`DeployCommands#env` before merging into the `Command` env, consistent with how `filter_deploy_envs`/`filter_rollback_envs`/`TaskDefinition#filter_envs` already protect the user-supplied task/deploy env.

### Proof of Concept
```ruby
# test/lib/shipit/task_commands_test.rb (extend existing test)
test "#env does not allow PR labels to inject sensitive env keys like PERL5LIB" do
  stack = shipit_stacks(:review_stack)
  stack.pull_request.labels = ["perl5lib"]
  task = shipit_tasks(:shipit_restart)
  task.stack = stack

  env = Shipit::TaskCommands.new(task).env

  # Binding under test: PERL5LIB must NOT be present in the env hash reaching Command/PTY.spawn
  # unless it is declared in deploy_spec's machine_env or task/deploy VariableDefinition names.
  refute_includes env.keys, "PERL5LIB",
    "PR label names should not be able to inject sensitive/reserved environment variable keys"
end

# test/unit/command_test.rb (extend existing test)
test "#unbundled_env inherits attacker-controlled PERL5LIB key from stack env with no allowlist" do
  command = Shipit::Command.new('echo $PERL5LIB', env: { 'PERL5LIB' => 'true' }, chdir: '.')
  assert_equal 'true', command.unbundled_env['PERL5LIB'],
    "Command#unbundled_env merges arbitrary env keys, including PERL5LIB, with no allowlist"
end
```
Both assertions demonstrate the equality mismatch: the expected invariant (`env.keys ⊆ machine_env.keys ∪ declared VariableDefinition names`) is violated because `PERL5LIB` (derived from an attacker's PR label) is present in the merged env hash that flows into `Command#unbundled_env` and ultimately `PTY.spawn`.
