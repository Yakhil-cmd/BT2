### Title
Webhook signature verification authenticates the organization named in `repository.owner.login`/`organization.login`, while event handlers act on the completely independent `repository.full_name` field, letting a forged payload attribute cross-organization writes (e.g. forged commit `Status`) to a victim stack - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret to check the HMAC signature against using `repository_owner`, derived from `params.dig('repository','owner','login')` (falling back to `organization.login`) [1](#0-0) [2](#0-1) . Once the signature check passes, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` dispatches the entire raw payload to handlers [3](#0-2) . Every handler resolves the target `Stack`/`Repository` from a *different* JSON field, `payload.dig('repository', 'full_name')`, via `Handler#stacks`/`#repository_name` [4](#0-3) . Nothing binds `repository.owner.login` (used to pick the trusted secret) to `repository.full_name` (used to pick the repository whose data gets mutated) — exactly the same class of bug as the referenced report, where the entity that is checked/authorized (`_current`/DAO check) is not the same entity that is actually mutated (the deleted mapping), enabling a value used for authorization to diverge from the value acted upon.

### Finding Description
`GithubApp#verify_webhook_signature` returns `true` unconditionally whenever the resolved organization has no `webhook_secret` configured: `return true unless webhook_secret` [5](#0-4) . Any Shipit deployment onboarding more than one GitHub organization (a documented, supported configuration) can therefore have at least one organization with signature checking effectively disabled, or an organization whose secret the attacker legitimately controls because it is their own onboarded org.

The attacker crafts a webhook body where `repository.owner.login` (or `organization.login`) names the org that is either unauthenticated (no secret) or one the attacker controls, but `repository.full_name` names a completely different, victim organization's repository that also has a `Stack` in the same Shipit instance. `verify_signature` authenticates only the first identity, then hands the untouched payload to handlers that key off the second, unrelated identity [4](#0-3) .

The existing test suite confirms handlers resolve the target purely from `repository_params` merged into arbitrary event bodies, independent of whatever the webhook signature check validated: the `:state` test merges `repository_params` (`{owner: {login: 'shopify'}}`) into a synthetic payload to create a `Status` for an existing commit under that repository's stacks [6](#0-5) , and `Handler#repository_name` is the sole lookup key used to find the `stacks` collection that every handler (push, status, check_suite, pull_request, membership) operates on [4](#0-3) .

### Impact Explanation
A `push` event forged this way causes `PushHandler#process` to call `stack.sync_github(expected_head_sha:)` on a victim's stack [7](#0-6) , forcing resyncs on an arbitrary schedule. More seriously, a forged `status` (or `check_suite`) event lets the attacker create a `Status` record for an arbitrary commit SHA and arbitrary state/context on the victim's stack — exactly what `ci.require` in `shipit.yml` relies on to gate deploys. Falsely marking a required CI context as `success` for a real commit in a repository the attacker has no access to can let that commit pass Shipit's CI safety gate, enabling an unauthorized deploy of code that never actually passed CI. This satisfies the "unauthorized deploy" / cross-repository-write impact tier.

### Likelihood Explanation
Exploitability depends only on: (1) the Shipit instance being configured with more than one GitHub organization (a normal multi-tenant setup), and (2) at least one onboarded organization either lacking a `webhook_secret` or being one the attacker legitimately administers (e.g., their own sandbox org onboarded to the same instance). No GitHub write access to the victim repository, no Shipit session, and no privileged token are required — only the ability to POST to the public `/webhooks` endpoint, which is unauthenticated by design (that's the whole point of `verify_signature`). This is a plausible, code-provable analog of the frontrun/binding-break class in the reference report.

### Recommendation
Bind the identity used for signature verification to the identity used for repository resolution: derive `repository_owner` for secret selection from the *same* `repository.full_name` that handlers use (e.g., split the owner out of `full_name` rather than trusting a separate `owner.login`/`organization.login` field), or explicitly re-verify after parsing that `repository.owner.login` matches the owner segment of `repository.full_name` before dispatching to handlers. Additionally, require every configured organization to have a non-blank `webhook_secret`, removing the unconditional `return true unless webhook_secret` bypass in `GithubApp#verify_webhook_signature`.

### Proof of Concept
1. Shipit instance is configured with two organizations: `attacker-org` (attacker-controlled, or has no `webhook_secret` set) and `victim-org` (has a real `Stack` tracking `victim-org/app`).
2. Attacker POSTs to `/webhooks` with header `X-Github-Event: status` and body:
   ```json
   {
     "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/app" },
     "sha": "<real commit sha in victim-org/app tracked by Shipit>",
     "state": "success",
     "context": "<ci context required by victim-org/app's shipit.yml ci.require>"
   }
   ```
   signed (or unsigned, if `attacker-org` has no secret) with `attacker-org`'s webhook secret.
3. `WebhooksController#verify_signature` resolves `repository_owner` = `"attacker-org"`, calls `Shipit.github(organization: "attacker-org")`, and the signature check passes [1](#0-0) .
4. The `status` handler runs `Handler#stacks`, which looks up `Repository.from_github_repo_name("victim-org/app")` and creates a `Status` for the given SHA on the victim's stack [4](#0-3) .
5. If that context is required by `victim-org/app`'s `ci.require`, the targeted commit now appears deployable in Shipit despite the attacker having no access to `victim-org`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
