This confirms the multi-organization design: `Shipit.github(organization:)` supports multiple GitHub Apps/organizations, each with its own `webhook_secret`, keyed under `secrets.github` (see `github_app_config`) [1](#0-0) . `WebhooksController#verify_signature` selects which app's secret to verify against using `repository_owner`, which is read directly from the untrusted payload (`params.dig('repository', 'owner', 'login')`) [2](#0-1) . Once verified, `create` re-parses the same raw body and dispatches it to handlers [3](#0-2) , but every handler resolves the target `Repository`/`Stack` purely from `payload.dig('repository', 'full_name')` [4](#0-3) , e.g. in `PushHandler` [5](#0-4)  or `PullRequest::OpenedHandler` [6](#0-5) . Nothing cross-checks that `repository.full_name`'s owner matches the `repository_owner`/organization whose secret validated the signature.

### Title
Webhook signature is bound to the payload's `repository.owner.login`, but repository writes are keyed only on `repository.full_name`, allowing cross-organization webhook forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
In multi-organization Shipit deployments, each GitHub organization can have its own GitHub App configuration and `webhook_secret` (`Shipit.github(organization:)`). The engine selects *which* secret to verify a webhook against using an attacker-controlled field of the same unauthenticated payload (`repository.owner.login`), then dispatches the identical payload to handlers that resolve the affected `Stack`/`Repository`/`Commit` solely by `repository.full_name`. The binding "organization whose secret authenticated the request" ≠ "repository that gets written to" is never enforced.

### Finding Description
`verify_signature` computes `repository_owner` from the JSON body itself and uses it to pick the `GitHubApp` (and thus the `webhook_secret`) used to validate `X-Hub-Signature`: [7](#0-6) [8](#0-7) 

The signature verification itself (`GitHubApp#verify_webhook_signature`) only proves that whoever produced the payload knows the secret associated with the organization named in `repository.owner.login` inside that same payload — it does not prove anything about `repository.full_name`, which is a separate, independently attacker-controlled field of the payload used later by every handler to select the affected records: [4](#0-3) 

Handlers such as `PushHandler` (`sync_github`), `StatusHandler` (creates commit statuses matched by SHA across *all* stacks, not scoped by repository at all), and the `PullRequest::*` handlers (archive/unarchive review stacks, update PR metadata) all trust `repository.full_name`/`sha` from the payload without any relation to the `repository_owner` used to authenticate: [5](#0-4) [9](#0-8) [10](#0-9) 

An attacker who controls (or is a member of) an organization "attacker-org" that is configured in this Shipit instance with its own `webhook_secret` can craft a payload where `repository.owner.login` = `"attacker-org"` (so the signature check passes with the attacker's own known secret) while `repository.full_name` = `"victim-org/some-tracked-repo"`. `verify_signature` will validate successfully because the HMAC is computed and checked against `attacker-org`'s secret, which the attacker legitimately knows; the handler then acts on `victim-org/some-tracked-repo` because it never re-checks the owner.

### Impact Explanation
This lets an actor who legitimately controls one configured GitHub organization/app in a multi-tenant Shipit deployment forge webhook events (push, pull_request, status, check_suite) against stacks belonging to a *different* organization it has no access to. Depending on handler, this can trigger unauthorized `sync_github` calls, archive/unarchive of review stacks, injection of fake commit statuses (`StatusHandler` matches purely by `sha` across the whole database, with no repository scoping at all), or fabricated PR state changes — i.e., writes into another organization's stack state driven by a forged, cross-repository webhook. This matches the "cross-repository writes" high-impact criterion, since the authenticated organization boundary does not match the repository being written.

### Likelihood Explanation
Requires the instance to be configured with more than one GitHub organization/app (the `github_organizations`/`github_app_config` multi-tenant schema in `lib/shipit.rb`), and requires the attacker to control at least one such organization's webhook secret (e.g., because they administer that org's GitHub App settings) — a real but non-default configuration. Given that assumption is met, exploitation only requires a single crafted HTTP POST with mismatched `repository.owner.login` vs `repository.full_name`; no other privilege is required.

### Recommendation
After `verify_signature` succeeds, re-derive `repository_owner` from the same trusted value used for verification and enforce that every handler's resolved `Repository`/`Stack` belongs to that same organization (e.g., compare `repository.full_name.split('/').first` against `repository_owner` before dispatching, or pass the verified organization into `Handler#call` and have `stacks`/`repository_name` scope by it) rather than trusting `full_name` alone.

### Proof of Concept
1. Deploy Shipit with two configured GitHub organizations: `attacker-org` (attacker controls the GitHub App / knows its `webhook_secret`) and `victim-org` (has a tracked repository/stack, e.g. `victim-org/app`).
2. Attacker crafts a JSON payload for the `push` event: `{"repository": {"owner": {"login": "attacker-org"}, "full_name": "victim-org/app"}, "ref": "refs/heads/master", "after": "<attacker chosen sha>"}`.
3. Attacker computes `X-Hub-Signature` using `attacker-org`'s `webhook_secret` over the raw body, per `Hook::DeliverySigner`/`GitHubApp#verify_webhook_signature` logic.
4. POST to `/webhooks` with `X-Github-Event: push`. `verify_signature` resolves `repository_owner` = `"attacker-org"`, loads `attacker-org`'s app, and successfully verifies the signature.
5. `create` dispatches the same payload to `Shipit::Webhooks::Handlers::PushHandler`, which resolves stacks via `Repository.from_github_repo_name("victim-org/app")` and calls `sync_github(expected_head_sha: ...)` on `victim-org`'s stacks — a write triggered by a request never authenticated against `victim-org`.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

      verified = github_app.verify_webhook_signature(
