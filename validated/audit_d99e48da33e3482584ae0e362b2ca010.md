### Title
Denial of Service via ID/parameter mismatch in duplicate-detection query for divisible private payments - (File: private_payment.js)

### Summary
The Synapse advisory (CVE-2020-26257) is a "trust the routing/identifying parameter without cross-checking it against the content" bug: a room id supplied out-of-band did not have to match the room id embedded in the signed event, letting a peer inject malformed data that later breaks processing for everyone. The closest analog reachable by an unprivileged actor in this codebase (a private-payment counterparty / paired device, not a p2p/hub attacker) is in `private_payment.js`'s duplicate-check query for divisible private-payment chains, which identifies "the same output" using `unit + asset + message_index` only, without the `output_index` that uniquely identifies which of possibly several outputs in that message it refers to.

### Finding Description
`validateAndSavePrivatePaymentChain` in [1](#0-0)  builds a lookup query to detect whether a private payment chain has already been saved:

```
var sql = "SELECT address, denomination, amount, blinding FROM outputs WHERE unit=? AND asset=? AND message_index=?";
...
if (objAsset.fixed_denominations){
    ... sql += " AND output_index=?"; params.push(headElement.output_index);
}
```
For divisible assets (`fixed_denominations` false), the `output_index` filter is deliberately omitted, on the assumption that a `unit+asset+message_index` triple can match at most one stored row: `if (rows.length > 1) throw Error(...)`.

That assumption is false whenever the referenced payment message legitimately has more than one output for the same asset (a normal payment plus its own change output, both created and inserted by [2](#0-1) , which inserts one `outputs` row per `output_index` for every element of `payload.outputs`). Once such a multi-output divisible private payment has been saved once, the very same `unit+asset+message_index` identifier used for the duplicate check will now match more than one row in the `outputs` table.

### Impact Explanation
Any private-payment counterparty or paired device that re-sends (or the hub/network layer that re-delivers, e.g. after `ifQueued`/reconnect, resends via `network.requestUnfinishedPastUnitsOfPrivateChains` or forwarding in [3](#0-2) ) an already-processed multi-output divisible private-payment chain will cause the wallet to hit the `rows.length > 1` branch and `throw Error(...)` synchronously inside a `conn.query` callback in `private_payment.js`. This throw is not wrapped in a try/catch anywhere in the call chain (`validateAndSavePrivatePaymentChain` → `wallet.handlePrivatePaymentChains` → `network.handleOnlinePrivatePayment`), so it propagates as an uncaught exception, crashing the receiving Node.js process. Since receiving private payments is a core wallet function reachable from any correspondent device, this is a concrete "node unable to process/confirm" condition — a wallet-level denial of service triggerable by an ordinary counterparty simply by resending a payment it already legitimately sent, not requiring any malicious peer/hub/network-level behavior.

### Likelihood Explanation
Re-delivery of the same private-payment chain is a normal occurrence in this protocol (network retries, hub redelivery, users manually resharing a payment, or an attacker deliberately resending). All that's needed is a divisible private asset payment whose message contains more than one output (an extremely common case: any payment with a change output). No privileged access, race condition, or special crafting beyond a standard duplicate resend is required, making this readily reproducible.

### Recommendation
Include `output_index` in the duplicate-detection `WHERE` clause for divisible assets as well (mirroring what is done for `fixed_denominations` assets), so the lookup uniquely identifies the specific output row being checked, and/or replace `rows.length > 1 → throw Error` with a graceful check per-`output_index` (e.g., iterate `rows` filtering by `output_index === headElement.output_index` or by matching against `payload.outputs[i]` for each `i`) instead of assuming uniqueness on an under-specified key.

### Proof of Concept
1. Attacker/counterparty Alice sends Bob a divisible private-asset payment chain whose `payload.outputs` array has two entries (e.g., payment output + change output) for the same `unit`/`asset`/`message_index`, processed successfully once via `wallet.handlePrivatePaymentChains` → `private_payment.validateAndSavePrivatePaymentChain` → `divisible_asset.validateAndSaveDivisiblePrivatePayment`, which inserts two rows into `outputs` (one per `output_index`) as shown in [4](#0-3) .
2. Alice (or the hub, or a retry) resends the exact same chain (`arrPrivateElements`) to Bob a second time.
3. `validateAndSavePrivatePaymentChain` in [5](#0-4)  runs the duplicate-check `SELECT ... WHERE unit=? AND asset=? AND message_index=?` (no `output_index` filter for divisible assets) and now retrieves 2 rows.
4. The code hits `if (rows.length > 1) throw Error("more than one output "+sql+' '+params.join(', '))` at [6](#0-5) , an uncaught synchronous throw inside the async DB callback, crashing Bob's wallet process.

### Note on investigation limits
I was unable to fully inspect `network.js` (the file appeared largely empty/truncated in the index, likely due to index size limits) to confirm the exact absence of a surrounding try/catch at the `handleOnlinePrivatePayment` call site and the precise redelivery triggers (hub retry vs. counterparty resend vs. `requestUnfinishedPastUnitsOfPrivateChains`). If you need certainty on those redelivery paths and the top-level exception handling, a full Devin session with direct file access would be needed to confirm there is no global uncaught-exception guard that would only log rather than crash.
