### Title
Private-payment forwarding ignores actual delivery status, allowing a private-asset spend to be publicly committed before the recipient ever receives proof of the transfer - (File: wallet_general.js)

### Summary
`sendPrivatePayments()` in `wallet_general.js` forwards a private-asset chain to a device but discards the real success/failure outcome of that send. It only reacts to `onSaved` (the message being queued locally), while `ifOk`/`ifError` — the actual delivery outcome — are wired to no-ops. This mirrors the FootiumEscrow bug class: a critical transfer status (ERC20 `transfer()` return value there, device-message delivery status here) is ignored, and downstream business logic (committing/broadcasting the unit that publicly spends the private asset) proceeds as if the transfer had succeeded.

### Finding Description
`sendPrivatePayments` calls `device.sendMessageToDevice` with callbacks that swallow the real outcome: [1](#0-0) 

`device.sendMessageToDevice` → `sendMessageToHub` → `reliablySendPreparedMessageToHub` inserts the encrypted package into the local `outbox` table and, when an `onSaved` callback is supplied (as `sendPrivatePayments` does), immediately calls `onSaved()` and then `ifOk()` — **before any actual network delivery attempt**. The real delivery is deferred to a background `resendStalledMessages` call: [2](#0-1) 

This `onSaved` signal is used as the completion gate for the `sendToRecipients` step of the private-asset pre-commit flow in `wallet.js`: [3](#0-2) 

Once `sendToRecipients`/`sendToCosigners` report completion via `cb`, the outer `async.series` in `getSavingCallbacks` (indivisible/divisible asset modules) proceeds to `writer.saveJoint` and `composer.postJointToLightVendorIfNecessaryAndSave`, i.e. the unit that publicly spends the private-asset output is written and broadcast: [4](#0-3) 

Because `sendPrivatePayments`'s `ifError`/`ifOk` handlers are empty functions, any subsequent failure to actually deliver the encrypted private chain (stale/incorrect hub info, wrong pubkey, unreachable correspondent, hub rejecting `hub/deliver`, etc., all surfaced by `handleError` in `sendPreparedMessageToConnectedHub`) is never observed or acted upon by the pre-commit logic: [5](#0-4) 

The end result: the check "did the transfer of the private chain actually succeed" is skipped, exactly like the audited `transferERC20` not checking `erc20Contract.transfer`'s boolean return.

### Impact Explanation
For private assets, the spendable proof of ownership is the private payment chain (blinded outputs/blinding factors), not the (public) unit alone. If the local queuing succeeds but the actual encrypted delivery to the recipient's device/hub permanently fails (and is silently ignored due to the no-op `ifError`), the sender's unit is nonetheless saved and broadcast, publicly consuming/spending the private-asset output. The recipient, having never received the chain, cannot construct the corresponding spend proof to claim/forward the asset. This causes an asset-transfer inconsistency/fund loss for the recipient side of a private payment, while the payer-side output is already irreversibly spent — the same class of "funds moved on one side, but the other party's claim wasn't validated" failure described in the source report.

### Likelihood Explanation
This path is reachable by any wallet user sending a private asset (a normal wallet feature, not requiring special privileges), any time the recipient's correspondent/hub record is stale or the hub temporarily rejects delivery for reasons other than the queuing itself. Because the completion signal used by the pre-commit logic is `onSaved` (a pure local DB write) rather than confirmed delivery, and both `ifOk`/`ifError` for the actual send are no-ops, no error is ever surfaced to the sending flow, making the divergence between "publicly spent" and "recipient has proof" silent and undetectable by the caller.

### Recommendation
`sendPrivatePayments` (and similar forwarding helpers relying on `onSaved`) should treat `onSaved` only as "queued," and should wire real `ifOk`/`ifError` handling so that pre-commit logic either (a) waits for confirmed delivery before allowing the joint to be saved/broadcast, or (b) explicitly accepts the "eventual, retried" delivery model but tracks/surfaces failures (e.g., persistent errors from `handleError` in `device.js`) so the wallet can react (retry, alert user, or avoid committing the spend) rather than silently discarding them.

### Proof of Concept
1. Send a private asset via `walletGeneral.sendPrivatePayments` from `wallet.js`'s `preCommitCb` (path taken whenever `objAsset.is_private` is true).
2. `device.sendMessageToDevice` inserts the encrypted package into `outbox` and immediately fires `onSaved()`/`ifOk()` per `reliablySendPreparedMessageToHub` (device.js:590-597) — regardless of whether the recipient's hub info is valid or the hub is reachable.
3. `sendToRecipients`'s `cb2` (bound to `onSaved`) fires immediately, `async.series([sendToRecipients, sendToCosigners], cb)` completes, and `onSuccessfulPrecommit`/`saveAndUnlock` proceed to `writer.saveJoint` and broadcast the unit (indivisible_asset.js:908-960).
4. In the background, `resendStalledMessages` attempts real delivery via `sendPreparedMessageToConnectedHub`; if it fails for a reason such as wrong `pubkey`/wrong `hub` in `correspondent_devices`, `handleError` is invoked (device.js:624-666) but this error is never routed back to `sendPrivatePayments`'s `ifError:function(){}` consumer, so the sender/wallet never learns the private chain was not delivered even though the unit spending that private-asset output has already been saved and broadcast.

function sendPrivatePayments(device_address, arrChains, bForwarded, conn, onSaved){
	var body = {chains: arrChains};
	if (bForwarded)
		body.forwarded = true;
	device.sendMessageToDevice(device_address, "private_payments", body, {
		ifOk: function(){},
		ifError: function(){},
		onSaved: onSaved
	}, conn);
}
