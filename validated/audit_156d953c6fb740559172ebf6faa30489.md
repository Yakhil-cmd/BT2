### Title
Griefing/DoS via pre-funding a deterministic AA address before its "initial deposit" balance check activates - (File: `storage.js::insertAADefinitions`, `aa_composer.js::updateInitialAABalances`)

### Summary
Obyte allows anyone to derive the deterministic address of a not-yet-registered Autonomous Agent (AA) — `address = chash160(definition)` — and to send coins to that address before the AA is ever defined on-chain. When the AA is later defined (e.g. by a factory/parent AA, a common "AA-defined-AA" pattern), all outputs previously sent to that address, including ones sent by an attacker in advance, are swept into the new AA's `aa_balances` in one aggregate SUM. Application logic that relies on `balance[asset] == 0` to detect a pristine/first-deposit state (a documented, intended AA pattern in this codebase) can therefore be permanently bypassed or corrupted by an attacker who pre-funds the predictable address with dust, exactly mirroring the Blackhole `GenesisPoolManager`/`PairFactory` griefing pattern (public deterministic target + permissionless funding + naive zero-balance check).

### Finding Description
An AA address is fully deterministic: `objectHash.getChash160(arrDefinition)` [1](#0-0) . This is used explicitly in the "AA defines a new AA" pattern, where a parent/factory AA's own public source code contains a fixed child-AA template, letting anyone compute `child_aa_address` off-chain in advance [2](#0-1) .

Because any base32 address can receive bytes/assets before it is ever "defined," an attacker can send a small amount to this precomputed address ahead of time. When the defining unit is later processed, `storage.js::insertAADefinitions` aggregates **all** prior undefined-address outputs (not just the ones from the parent AA's own payment) into the new `aa_balances` row: [3](#0-2) 

This balance is what `aa_composer.js::updateInitialAABalances` reads as the AA's starting balance for every subsequent trigger [4](#0-3) .

The intended usage pattern in this codebase explicitly relies on the assumption that balance equals zero only for the very first deposit, as shown in the shipped Uniswap-like market-maker sample: [5](#0-4) 

If an attacker front-runs the pool's activation by sending 1 unit of `base` and/or of the paired asset to the precomputed AA address, `$asset_balance == 0 OR $bytes_balance == 0` will never be true again — the "initial deposit" branch is permanently skipped, exactly as `IERC20(pairAddress).balanceOf(...) == 0` is permanently false in the Blackhole report once an attacker pre-funds the pair. All subsequent legitimate deposits are evaluated against a corrupted, attacker-controlled tiny ratio, either bouncing them (DoS) or letting the attacker manipulate the effective price/ratio (fund loss/griefing) for the first genuine depositor.

### Impact Explanation
This breaks the same class of invariant as the referenced Medium-severity finding: a check meant to gate "is this genuinely the first/empty state" is defeated by permissionless pre-funding of a publicly predictable target address. Consequences for an AA using this pattern:
- Denial of Service: legitimate initial deposits permanently bounce (e.g., division by an attacker-chosen dust ratio, or explicit `bounce('wrong ratio of amounts...')`) [6](#0-5) .
- Griefing/fund loss: the attacker sets an extreme, favorable initial price ratio with negligible cost (a few bytes), diluting or extracting value from legitimate depositors' subsequent shares.
This qualifies as AA fund loss/freezing under the accepted impact categories, reachable purely by an unprivileged unit poster sending a plain payment to a predictable address.

### Likelihood Explanation
Any address, defined or not, can receive coins in Obyte at any time — this is normal, expected behavior of the DAG, not a bug in isolation. What makes exploitation practical is that (a) AA/child-AA definitions are public (on-chain oscript source), so `chash160(definition)` is computable by anyone before the AA is activated, and (b) this "balance == 0 means first deposit" check is a documented, endorsed pattern shipped in this repo's own sample scripts, meaning real deployed AAs are likely to use it. The attack costs only the minimum bounce-fee-sized dust transfer and requires no special access or timing precision (unlike a strict mempool front-run, the attacker can pre-fund at their leisure any time before the pool AA is activated).

### Recommendation
AA authors using a "balance was zero, so this is the first deposit" pattern should not rely solely on raw `balance[asset]`. Recommendations for the ocore framework level:
- Document explicitly (and warn via `aa_validation`/AA authoring guidelines) that `balance[...]` at AA activation may already include pre-existing "donations" sent to the not-yet-defined address, since `insertAADefinitions` back-fills all matching prior outputs.
- Consider tracking and exposing to AA formulas a distinct, protocol-maintained state flag such as "has this AA ever completed a deposit/received-any-trigger" (already partially possible via `var[...]` state, but the framework could offer a first-class `is_first_trigger`-style primitive) instead of encouraging balance-based heuristics, which are trivially griefable.
- At minimum, flag/lint the `balance[asset]==0` idiom for LP/market-maker style AAs during `aa_validation.validateAADefinition` as a known-risky pattern.

### Proof of Concept
1. Deploy (or observe) a factory AA whose `init` formula defines a fixed child AA template and computes `$child_aa_address = chash160($child_aa)` — this is a supported, tested pattern [2](#0-1) , and the child AA itself follows the market-maker "initial deposit" idiom [7](#0-6) .
2. Attacker independently computes `child_aa_address = chash160(child_aa_definition)` from the factory's public oscript source, without waiting for any transaction.
3. Attacker posts a payment unit sending 1 byte and 1 unit of the paired asset to `child_aa_address`, long before the factory AA is triggered to formally define/activate it.
4. When the factory AA eventually posts the `definition` message activating `child_aa_address`, `storage.js::insertAADefinitions` sums all pre-existing unspent outputs at that address (including the attacker's dust) into `aa_balances` [8](#0-7) .
5. The legitimate first depositor's trigger now computes `$asset_balance` and `$bytes_balance` as nonzero (due to attacker dust), skipping the intended "initial deposit" branch and instead computing a ratio based on the attacker's near-zero values, causing the deposit to bounce or be priced at an extreme, attacker-favorable ratio.
