### Title
Stack-Scoped ApiClient Tokens Bypass Stack Authorization in CCMenu API - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::Api::CCMenuController` reimplements stack resolution instead of using the shared, scope-aware `stack` helper from `Shipit::Api::BaseController`. This lets an `ApiClient` token that is authorized for only one stack read build/deploy status for **any** stack in the installation, breaking the equality that should hold: `stack a token authorizes == stack a token touches`.

### Finding Description
`BaseController` defines a scoping helper that all other API controllers rely on: [1](#0-0) 
`stacks` restricts the queryable set to `current_api_client.stack_id` when the client is stack-scoped, and `stack` resolves `params[:stack_id]` only within that restricted relation.

`CCMenuController`, however, overrides both authentication and the `stack` resolution method: [2](#0-1) 
Instead of calling `stacks.from_param!(params[:stack_id])`, it calls `Stack.from_param!(params[:stack_id])` directly against the unscoped `Stack` model, discarding the `current_api_client.stack_id` restriction entirely. The only check performed is `require_permission :read, :stack`: [3](#0-2) 
which only validates that the token carries the `read:stack` permission string — it never validates that the requested `stack_id` matches the token's authorized stack, as evidenced by `ApiClient#check_permissions!`: [4](#0-3) 

An `ApiClient` can be created scoped to a single stack (see fixture `here_come_the_walrus`, which has `stack: shipit` and `permissions: read:stack`): [5](#0-4) 
Such a token is intended, per the scoping mechanism in `BaseController#stacks`, to only ever "touch" its assigned stack. The route is publicly reachable and even accepts the token as a URL query parameter, lowering the bar for exposure: [6](#0-5) 

This is the direct structural analog of the reported bug class: a credential/binding intended to scope an actor's authority (preferred fee type tied to a specific `campaignCreator`; here, an `ApiClient` token tied to a specific `stack_id`) is checked in one place (`check_permissions!`/`setPreferredFeeType`'s missing creator check) but not enforced at the point where the target object is actually resolved and acted upon (`stack` resolution in `CCMenuController` vs. the deployed distributor's `campaignCreator`).

### Impact Explanation
This meets the "High" bar defined in scope: "unauthenticated read of stack state, task streams or deploy output." A token deliberately restricted to Stack A (e.g., issued to a low-trust integration such as a CI badge/status widget) can be used to read the deploy/build status (`lastBuildStatus`, `lastBuildLabel`, `activity`, `webUrl`, etc.) of any other stack in the Shipit installation, including private or sensitive repositories/stacks that were never meant to be exposed to the holder of that token. This is a cross-stack information disclosure crossing an authorization boundary the application explicitly modeled (`ApiClient#stack_id`).

### Likelihood Explanation
High likelihood: no privileged access, GitHub App credentials, or additional secrets are needed beyond possession of any valid stack-scoped `read:stack` `ApiClient` token — which by design is meant to be a low-privilege, narrowly-scoped credential (e.g., handed to third-party CI dashboards). The attacker only needs to know or guess another stack's `owner/repo/environment` identifier (used in `Stack.from_param!`), which is often predictable/public (GitHub org/repo names). The endpoint even supports token-in-query-string authentication, making it trivial to invoke from a browser or curl.

### Recommendation
Change `CCMenuController#stack` to reuse the inherited, scope-aware resolution instead of querying `Stack` directly:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
removing the private `stack` override entirely so it falls back to `BaseController#stack`/`#stacks`, ensuring stack-scoped tokens can never resolve a stack outside their authorized `stack_id`.

### Proof of Concept
1. Create (or use) an `ApiClient` scoped to `shipit_stacks(:shipit)` with `permissions: ['read:stack']` (matches fixture `here_come_the_walrus`): [5](#0-4) 
2. As this restricted client, request the CCMenu status for a *different* stack that the client was never granted access to:
```
GET /api/stacks/other-owner/other-repo/other-environment/ccmenu?token=<here_come_the_walrus_token>
```
3. Because `CCMenuController#stack` calls `Stack.from_param!` on the unscoped `Stack` model rather than `stacks.from_param!` (the client-restricted relation used everywhere else, e.g. `Shipit::Api::BaseController#stack` at lines 78-80), the request succeeds with `200 OK` and renders the target stack's build status XML, even though `current_api_client.stack_id` does not match the requested stack. Compare with `Shipit::Api::StacksController`, which correctly uses the inherited scoped `stack`/`stacks` helpers and would return `404 Not Found` for the same cross-stack request, as implied by the scoping test pattern: [7](#0-6)
