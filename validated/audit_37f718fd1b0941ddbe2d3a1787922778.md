### Title
AA fund freezing via unbounded dust-output accumulation for custom-asset payments - ([File: aa_composer.js])

### Summary
In `aa_composer.js`'s `sendUnit` / `completePaymentPayload`, when an AA composes a payment message denominated in a custom (non-base) asset, it fetches ALL unspent outputs of that asset sent to the AA's address and iterates over them with no dust floor, unlike bytes/base payments which explicitly filter out dust (outputs smaller than `FULL_TRANSFER_INPUT_SIZE`) "to prevent dust attack: spamming the AA with very small outputs so that the AA spends all its money for fees when it tries to respond" [1](#0-0) . For base payments the query enforces `amount>=FULL_TRANSFER_INPUT_SIZE`, but for asset payments the same query has no such minimum: `"...asset"+(asset ? "="+conn.escape(asset) : " IS NULL AND amount>=" + FULL_TRANSFER_INPUT_SIZE)+"..."` [2](#0-1) .

### Finding Description
`iterateUnspentOutputs` loops over every row returned by `readStableOutputs`/`readUnstableOutputsSentByAAs` and pushes each as a payment input until `target_amount` is reached [3](#0-2) . Because the asset-branch query has no minimum-amount filter, an attacker can send an unbounded number of dust-sized outputs of a custom asset to an AA's address. When the AA later needs to compose a response payment in that asset (e.g., paying out a balance, forwarding tokens, or issuing an asset payment), it must consume many of these dust outputs to accumulate enough value, appending one input per dust output.

Critically, this bypasses the normal payment size limits: `validatePaymentInputsAndOutputs` explicitly exempts AA-authored payments from the `MAX_INPUTS_PER_PAYMENT_MESSAGE` check — `if (payload.outputs.length > constants.MAX_INPUTS_PER_PAYMENT_MESSAGE && !objValidationState.bAA)` [4](#0-3) . So there is no protocol-level cap forcing the AA to reject an oversized input list the way a normal user payment would be capped at `constants.MAX_INPUTS_PER_PAYMENT_MESSAGE` (128) [5](#0-4) .

The comment at line 1144 explicitly acknowledges the dust-attack class for bytes but the mitigation (amount floor) was only applied to the base-asset branch of the query, leaving the general-asset branch unprotected [6](#0-5) .

### Impact Explanation
An attacker who wants to disable an AA's ability to spend/forward a specific custom asset can flood the AA's address with a large number of tiny-amount outputs of that asset. Because these are all pulled in without a dust floor and without any input-count cap for AA-composed units, the AA is forced to build a payment message with an unbounded number of inputs when it needs to move that asset. This can push the resulting unit past practical/size limits, cause repeated processing overhead each time the AA tries to respond, and effectively prevent the AA from ever successfully composing a valid response involving that asset — freezing the AA's asset funds/functionality, analogous to the referenced dust-deposit refund-DOS bug class. This matches the accepted impact category of "AA fund loss or freezing."

### Likelihood Explanation
Likelihood is Medium: sending many small-amount transfers of an asset to a known AA address is inexpensive for an attacker (only bytes fees for creating many payment units are required, and asset amounts can be arbitrarily small as long as they are positive integers, per `isPositiveInteger(output.amount)` in payment output validation [7](#0-6) ). The AA needs to actually be triggered to spend that asset for the effect to manifest, so the attack targets specific AAs that hold/manage custom assets and reads/writes that asset balance in response to triggers — a fairly common AA pattern (e.g., token-handling AAs, DEXes, bonding curves).

### Recommendation
Apply the same dust-amount floor used for base/byte outputs to the asset branch of the queries in `readStableOutputs` and `readUnstableOutputsSentByAAs`, or otherwise cap/limit the number of unspent outputs consumed per payment composition (e.g., add `LIMIT constants.MAX_INPUTS_PER_PAYMENT_MESSAGE` and reintroduce the outputs-length check for AA-composed payments, or coalesce dust before it can be spent). Alternatively, remove the `!objValidationState.bAA` exemption from the `MAX_INPUTS_PER_PAYMENT_MESSAGE`/`MAX_OUTPUTS_PER_PAYMENT_MESSAGE` checks so AA-composed transactions are bound by the same anti-spam limits as user transactions, and have the AA gracefully bounce (or split across multiple response units) rather than fail outright when funds are fragmented across too many dust outputs.

### Proof of Concept
1. Attacker identifies a custom-asset-handling AA address `A` that will later need to send/forward asset `X` from its balance (e.g., a DEX or vault AA).
2. Attacker (or colluding accounts) issue thousands of tiny (e.g., amount = 1) transfer payments of asset `X` to address `A`, each in a separate unit, well below the byte-equivalent `FULL_TRANSFER_INPUT_SIZE` floor that is enforced only for the base asset.
3. Attacker triggers the AA in a way that requires it to compose an outgoing payment denominated in asset `X` reaching some `target_amount`.
4. `completePaymentPayload`'s `readStableOutputs`/`readUnstableOutputsSentByAAs` return all the dust outputs (no amount filter for non-base assets) [2](#0-1) ; `iterateUnspentOutputs` appends one input per dust row until `target_amount` is reached [3](#0-2) .
5. Because AA-composed payments are exempt from `MAX_INPUTS_PER_PAYMENT_MESSAGE` [8](#0-7) , the resulting response unit can contain an excessive number of inputs, causing composition/processing failures or repeated bounce behavior whenever the AA attempts to spend asset `X`, freezing that portion of its functionality.
