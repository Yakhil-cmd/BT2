### Title
Balance-based "first deposit" detection in AA templates allows share-price manipulation via unprivileged front-running deposits - (File: test/samples/uniswap_like_market_maker.oscript)

### Summary
The bug-class described in the WithdrawProxy report — inferring a critical state transition ("is it safe/first to accept redemptions") from a mutable `totalAssets()`-style balance check instead of an explicit, tamper-proof flag — has a direct analog in Obyte's Autonomous Agent (AA) programming model. The `balance[asset]` oscript primitive returns the AA's live balance, which includes coins received in the very same trigger and any coins ever sent to the AA address by any unprivileged party. The reference AA implementation for a market-maker/liquidity-pool pattern shipped with ocore uses exactly this primitive to decide whether an "initial deposit" (i.e., no prior share issuance) is occurring, and this same anti-pattern is echoed in other bundled examples (crowdfunding/51%-attack game) that use `balance[base]` to gate payouts and share pricing.

### Finding Description
In `test/samples/uniswap_like_market_maker.oscript:33-48`, the "invest in MM" branch determines whether this is the pool's first deposit purely by checking live balances: [1](#0-0) 
```
if: `{$mm_asset AND trigger.output[[asset=base]] > 1e5 AND trigger.output[[asset=$asset]] > 0}`,
init: `{
    $asset_balance = balance[$asset] - trigger.output[[asset=$asset]];
    $bytes_balance = balance[base] - trigger.output[[asset=base]];
    if ($asset_balance == 0 OR $bytes_balance == 0){ // initial deposit
        $issue_amount = balance[base];
        return;
    }
    ...
```
`balance[]` is resolved from `objValidationState.assocBalances`, which for the AA's own address is seeded with its current on-chain balance and then immediately incremented with the current trigger's outputs before any state logic runs, as implemented in `aa_composer.js`'s `updateInitialAABalances`: [2](#0-1) 
This means the balance used to gate "initial deposit" pricing is not an explicit, protected counter — it is simply whatever coins currently sit at the AA's address, exactly analogous to `WithdrawProxy.totalAssets()` being derived from the raw WETH balance of the contract rather than an explicit `withdrawReserveReceived` flag.

Because any address can post a trigger (a payment message) to an AA address at any time — this is the unprivileged "AA trigger sender" role explicitly reachable in ocore — an attacker can pre-seed the pool's `$asset` and `base` balances with a tiny "donation" before the legitimate first depositor's transaction lands. This corrupts the `$current_ratio`/`$issue_amount` calculations in the non-initial-deposit branch, or forces the legitimate depositor into the manipulated "initial deposit" branch with a distorted `balance[base]`, letting the attacker mint a disproportionate share of `$mm_asset` for a nominal cost and later redeem it against the real depositor's contributed value via the "divest MM shares" branch: [3](#0-2) 

The same anti-pattern (deriving payout/threshold logic from `balance[base]` rather than an internal, explicitly-updated accounting variable) also appears in the bundled 51%-attack-game and ICO samples, where `var['total'] = balance[base]` is used to size payouts: [4](#0-3) [5](#0-4) 
An attacker sending extra bytes directly to these AA addresses before the "finish"/"milestone" trigger inflates `var['total']`, and thus the payouts computed as a share of it, at the expense of legitimate contributors' proportional claims.

### Impact Explanation
Any unprivileged AA trigger sender can donate a small, unaccounted amount of the base asset or a custom asset directly to an AA that uses this `balance[]`-based accounting pattern, and thereby manipulate share-issuance ratios or payout totals. This is a fund-loss/fund-theft primitive for any AA built following ocore's own documented reference pattern: attackers can mint outsized shares for negligible cost and redeem them against honest depositors' funds, i.e., unauthorized value extraction analogous to the WithdrawProxy exploit (undervalued share redemption/oversized share issuance from balance manipulation).

### Likelihood Explanation
Triggering the exploit requires only posting a normal payment-carrying unit (a trigger) to the target AA address before the legitimate depositor's unit — something any wallet holder can do trivially and cheaply (a dust amount plus bounce fee). Because ocore explicitly exposes `balance[]` as a first-class, encouraged construct for AA authors (used across the shipped samples), and because AA balances are updated with received trigger outputs before any conditional logic runs (`aa_composer.js` `updateInitialAABalances`), the precondition for the attack is always present for any AA copying this pattern.

### Recommendation
- In ocore's AA documentation/samples, replace balance-derived state checks (`balance[asset]==0`, `var['total']=balance[base]`) used to gate critical pricing/payout logic with an explicit, monotonically-tracked state variable (e.g., `var['mm_asset_outstanding']` already tracked in the same script) that is updated only through the AA's own controlled state-transition messages, never inferred from the raw wallet balance.
- Where `balance[]` must be used for accounting, compute deltas against a stored "last known accounted balance" state var and reconcile/quarantine any unaccounted surplus (donations) instead of implicitly folding it into share-price or payout formulas.
- Add explicit guidance/warnings in ocore's AA-authoring documentation (and ideally a validation lint in `aa_validation.js`) flagging `balance[...]` usage in `if`/pricing formulas that are not reconciled against an explicit running total, since this is a recurring anti-pattern across the bundled reference AAs.

### Proof of Concept
1. Deploy the AA from `test/samples/uniswap_like_market_maker.oscript` and define `$mm_asset` via the "define" trigger.
2. Attacker posts a trigger sending a dust amount of `base` bytes (> bounce fee) and a dust amount of `$asset` directly to the AA address, without waiting for `$mm_asset_outstanding` to be initialized — this seeds `balance[base]` and `balance[$asset]` while `var['mm_asset_outstanding']` is still unset/zero.
3. Attacker's own trigger then satisfies the "invest in MM" branch's `$asset_balance == 0 OR $bytes_balance == 0` condition (or, depending on ordering, corrupts `$current_ratio` for the next depositor), causing `$issue_amount = balance[base]` to mint the attacker a large `$mm_asset` allocation for a small `base` contribution.
4. Legitimate depositor's subsequent, larger contribution is priced against the attacker-corrupted `$asset_balance`/`$bytes_balance` ratio, under-minting their fair share of `$mm_asset`.
5. Attacker calls the "divest MM shares" branch to redeem their disproportionate `$mm_asset` for a share of the pool's true (legitimate-depositor-funded) `balance[$asset]` and `balance[base]`, extracting value contributed by the legitimate depositor.
