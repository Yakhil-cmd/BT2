### Title
CCMenu API bypasses stack-scoped ApiClient authorization, allowing cross-stack read of build/deploy status - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::CCMenuController` overrides the stack-lookup method used by every other API controller and, in doing so, drops the per-stack authorization scoping that `ApiClient` records are meant to enforce. A `read:stack` token that was intentionally created scoped to a single stack can be replayed against `CCMenuController#show` with an arbitrary `stack_id` to read another stack's build/deploy status.

### Finding Description
`Shipit::Api::BaseController` implements stack access as two cooperating methods: [1](#0-0) 

`stacks` restricts the visible `Stack` relation to `current_api_client.stack_id` when the client is scoped, and `stack` resolves the requested `stack_id` param *through that restricted relation* via `stacks.from_param!`. Every other API controller (`StacksController`, `TasksController`, etc.) relies on this inherited `stack`/`stacks` pair, so a token created with `stack_id` set can only ever resolve to its own stack.

`CCMenuController`, however, redefines `stack` to bypass `stacks` entirely: [2](#0-1) 

It still declares `require_permission :read, :stack` [3](#0-2)  and `check_permissions!` only checks that the token has the generic `"read:stack"` string in its `permissions` array — it never checks the token's `stack_id` binding: [4](#0-3) 

So the equality that should hold is:
`{stack authorized by ApiClient#stack_id} == {stack resolved and rendered by CCMenuController#show}`

Before the request: for a stack-scoped `read:stack` token, `stacks` (base controller logic) would equal `Stack.where(id: token.stack_id)`. After the request (CCMenu path): `stack` is resolved as `Stack.from_param!(params[:stack_id])`, i.e. `Stack.all`, completely independent of `token.stack_id`. Any `stack_id` supplied in the URL is honored, breaking the binding.

### Impact Explanation
An attacker in possession of a `read:stack`-scoped API token for stack A (e.g., a CCMenu token deliberately restricted to one project, or any token an administrator scoped to a single stack via `stack_id`) can call `GET /api/stacks/:stack_id/ccmenu.xml?token=<token>` with a different `stack_id` and receive that other stack's CCMenu XML — including `lastBuildStatus`, `lastBuildLabel`, `webUrl`, activity/lock state, i.e. an unauthorized read of stack state/deploy status for a stack the token was never granted access to (see `app/views/shipit/ccmenu/project` fields exercised in `test/controllers/api/ccmenu_controller_test.rb` lines 33-51). This matches the "unauthenticated/unauthorized read of stack state, task streams or deploy output" High-severity category, because the credential-to-resource binding (`ApiClient.stack_id` ↔ accessed `Stack`) is broken.

### Likelihood Explanation
Exploitation requires only possession of any valid `read:stack` API token — no further privilege, session, or GitHub credential is needed, and the request is a single unauthenticated (from Shipit's perspective) GET with a token query param, matching how `CCMenuUrlController` already issues such tokens over URLs (which are inherently more likely to leak/be shared, e.g. pasted into a CI dashboard). The only uncertainty is how commonly operators create genuinely stack-scoped `ApiClient` records (the stock admin UI in `ApiClientsController#create_params` doesn't expose `stack_id` in the form), but the model attribute and the base-controller enforcement logic clearly exist for this purpose, and any token created with a `stack_id` (via console, seed data, or other integration) is unconditionally exposed to this bypass.

### Recommendation
Make `CCMenuController#stack` reuse the same scoped lookup as the rest of the API surface:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
and delete the private override entirely, relying on `BaseController#stack`/`#stacks`. Alternatively, have `check_permissions!`/`require_permission` also verify `current_api_client.stack_id.nil? || current_api_client.stack_id == stack.id` before serving any per-stack API response.

### Proof of Concept
1. Create (e.g., via Rails console) `ApiClient stack_id: <StackA.id>, permissions: ["read:stack"]`, and obtain its `authentication_token`.
2. Request `GET /api/stacks/<StackB_param>/ccmenu.xml?token=<tokenA>` where `StackB` is a different, unrelated stack.
3. Observe the response renders `StackB`'s CCMenu project XML (name, lastBuildStatus, lastBuildLabel, webUrl, activity) — as demonstrated by the assertions in `test/controllers/api/ccmenu_controller_test.rb` (lines 20-45) which pass regardless of the token's `stack_id`, because `CCMenuController#stack` never consults it.
