### Title
`timestamp` in oscript AAs / address definitions is the author-chosen `last_ball_unit`'s timestamp, not true wall-clock inclusion time, allowing deadline/expiry checks to be bypassed - (File: `formula/evaluation.js`, `definition.js`, `validation.js`)

### Summary
Oscript's `timestamp` keyword — used by AA authors and address-definition authors to implement deadlines, vesting windows, sale-end times, and other time-gated logic — does not reflect the actual wall-clock time at which the unit is processed. It is set to `objValidationState.last_ball_timestamp`, i.e. the timestamp of whichever `last_ball_unit` the unit's author chose to reference when composing the unit. Because an unprivileged unit poster/AA trigger sender controls which stable ball to reference as `last_ball_unit` (subject only to the DAG-inclusion/non-retreat constraints in `validateParents`), they have some latitude to make `timestamp` appear earlier than the real submission time. This is the same root-cause pattern as the reported Balancer `deadline` bug: a value that is supposed to be an independent, off-chain-agreed checkpoint is instead derived from a value the transaction submitter effectively controls, defeating the intended time-boundary protection.

### Finding Description
`timestamp` in oscript formulas simply returns the validation state's `last_ball_timestamp`: [1](#0-0) 

The same value backs the `timestamp` relational operator used in address definitions: [2](#0-1) 

`last_ball_timestamp` is not "now" — it is populated from the timestamp of whatever `last_ball_unit` field the unit's author put in the unit, as long as it satisfies the DAG constraints (must not retreat vs. parents' last ball, and must be included/ancestor of the chosen parents): [3](#0-2) [4](#0-3) 

The reference wallet composer (`parent_composer.js`) always tries to pick the *most recent* stable ball as `last_ball_unit`: [5](#0-4) 

but nothing in `validation.js` forces this — an unprivileged unit author can hand-craft (or use a custom composer for) a unit that attaches to older, still-unstable/free parts of the DAG and references an older stable `last_ball_unit`, as long as the non-retreat and inclusion checks above hold. In that case, `timestamp` returned to the oscript formula (both for AA `if`/`init`/`state` formulas and for address-definition `timestamp` conditions) will reflect that older, attacker-chosen point in time rather than the true time the unit is actually confirmed on the network.

This is exactly the anti-pattern in the reported issue: a time boundary meant to be an absolute, externally-fixed checkpoint is instead derived from a value the caller effectively selects when constructing their transaction, making a deadline/expiry comparison ineffective. Multiple shipped oscript sample templates rely on `timestamp` for exactly this kind of access control, e.g. an ICO close/expiry check: [6](#0-5) 
and a challenge-period/timelock pattern: [7](#0-6) 

### Impact Explanation
Any AA (or address definition) that gates behavior with a `timestamp <` / `timestamp >=` style deadline — sale windows, contribution deadlines, vesting/release timelocks, challenge/dispute periods — can potentially be manipulated by a trigger sender who selects an older `last_ball_unit` to make the AA believe less time has elapsed than actually has. This can let a user squeeze a trigger into a window that should already be closed (e.g., contributing to a token sale after `$expiry_ts`, or forging eligibility for a time-bounded refund/claim), leading to unauthorized fund movement/allocation within an AA (fund loss or unfair distribution to a party who should not have been eligible after the deadline passed) — i.e. concrete AA fund-loss/misallocation impact.

### Likelihood Explanation
Exploitation requires an attacker to run a custom unit composer (not the stock wallet) that intentionally selects an older stable `last_ball_unit`/older parent set instead of the freshest one used by the reference composer. The achievable backward drift is bounded by the non-retreat/inclusion checks in `validateParents` (the chosen `last_ball_mci` must lie between the parents' own last-ball mci and their `latest_included_mc_index`), so it is not unlimited, but it is not zero either, and any AA/address-definition author relying on `timestamp` for precise deadline enforcement is exposed to some degree of timestamp skew controlled by the trigger sender rather than the network.

### Recommendation
- Avoid treating oscript `timestamp` as a trustworthy "current wall-clock time" for security-critical deadline/expiry logic; document clearly that it is the timestamp of the unit's own `last_ball_unit`, chosen by the unit's author.
- Where deadlines matter, consider enforcing a maximum allowed skew between `last_ball_timestamp` and other, harder-to-manipulate signals (e.g., `mci` deltas against the current stable MCI, or a minimum bound requiring `last_ball_mci` to be close to the network's actual current stable MCI at the time of processing), rather than relying purely on non-retreat/inclusion constraints.
- Consider tightening `validateParents` so that `last_ball_unit` must be within a small MCI window of the actual best-known stable MCI at the time of broadcast/processing, closing the gap an attacker can exploit to skew `timestamp`.

### Proof of Concept
1. Deploy an AA (or address definition) with a case such as `if: "{ timestamp < $sale_end_ts AND trigger.output[[asset=base]] >= X }"` implementing a sale window, similar to `test/samples/ico_with_milestones.oscript`'s expiry pattern.
2. Wait until the real wall-clock time has passed `$sale_end_ts`.
3. Using a custom composer (not the stock wallet's `parent_composer.pickParentUnitsAndLastBall`, which always picks the freshest stable ball), construct and sign a trigger unit whose `parent_units` attach to an older, still valid/unstable branch of the DAG and whose `last_ball_unit`/`last_ball` reference a stable ball whose `timestamp` is still `< $sale_end_ts`, while satisfying `validateParents`'s non-retreat (`last ball mci must not retreat`) and inclusion (`last ball unit ... not included in parents`) checks.
4. Broadcast the unit; once it is validated and included, the AA formula evaluates `timestamp` against the old `last_ball_timestamp`, so `timestamp < $sale_end_ts` is still true even though the sale should already be closed in real time, allowing the late contribution/claim to succeed.
