This confirms the vulnerability. The base `Handler` class provides a `stacks` helper that properly scopes lookups to the repository named in the webhook payload via `Repository.from_github_repo_name(repository_name)&.stacks`, and `PushHandler#process` [1](#0-0)  correctly uses this scoped `stacks` collection. `StatusHandler#process`, however, bypasses this repository-scoping entirely and looks up commits globally by `sha` alone: [2](#0-1) .

### Title
Cross-repository Status forgery via unscoped `Commit.where(sha:)` lookup enables unauthorized deploy trigger - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` resolves target commits purely by `sha` across the entire database, without checking that the webhook's `repository.full_name` matches the stack/repository owning that commit. Because Git commit SHAs are content-addressed and identical across forks/copies of shared history, an attacker who legitimately controls their own GitHub repository (tracked as an unrelated Shipit stack) can fire a real, validly-signed status webhook for a SHA that also exists in a victim's stack, injecting a fabricated `success` status that can unlock `Stack#trigger_continuous_delivery` for the victim's stack.

### Finding Description
The broken binding: "the repository that produced this status webhook" == "the repository/stack that the resulting `Status` record is attributed to and that could deploy off of it" — this fails. All other handlers (e.g. `PushHandler`) resolve the acting stack via `stacks`, which is `Repository.from_github_repo_name(payload.dig('repository','full_name'))&.stacks` [3](#0-2) , tying the mutation to the reporting repository. `StatusHandler`, instead, does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [2](#0-1) , which matches **any** `Commit` row in the database with that SHA, regardless of which repository/stack it belongs to, and `create_status_from_github!` stores the status against that commit's own pre-existing `stack_id` [4](#0-3) .

`verify_signature` only authenticates *which organization* sent the webhook (via `repository.owner.login` selecting the correct `github_app`/`webhook_secret`) [5](#0-4)  — it never checks that the named repository actually owns the commit being mutated. Since Git commit SHA1s are computed from tree/parent/author/committer/message content, not from the hosting repository, a commit that is part of the victim's shared history (e.g., because the attacker forked the victim's public repo, or copied/cherry-picked an exact commit object into a repo they control) will have an identical SHA in both repositories. GitHub's Statuses API permits setting a status on any commit object present in a repository's object store, including ones reachable only through fork ancestry, so the attacker can trigger a genuine, correctly-HMAC-signed `status` webhook from **their own** repository/org for that shared SHA, with an arbitrary `state`/`context`/`description` of their choosing.

That real, validly signed webhook is delivered to Shipit; `StatusHandler#process` finds the victim's `Commit` row (same SHA, different stack) and calls `commit.create_status_from_github!(params)`, creating a `Status` in the victim's stack context. This flips `Commit#deployable?` (`!locked? && (stack.ignore_ci? || (success? && !blocked?))`) [6](#0-5)  and triggers the `schedule_continuous_delivery` chain: `Status#schedule_continuous_delivery` → `Commit#schedule_continuous_delivery` → `ContinuousDeliveryJob` → `Stack#trigger_continuous_delivery` → `Stack#trigger_deploy(commit, Shipit.user, env: cached_deploy_spec.default_deploy_env)` [7](#0-6) , which ultimately spawns the deploy `Task`/`Command` with the victim stack's own scoped `GITHUB_TOKEN`.

### Impact Explanation
An unprivileged attacker who merely owns/controls an unrelated repository tracked by the same multi-tenant Shipit instance can write a `Status` record into, and potentially trigger an unauthorized deploy for, a completely different tenant's stack, without ever needing that tenant's webhook secret, session, or API token. This matches the "payload for one repository mutating another's stack, commit, task, or unauthorized deploy" Critical category. The GITHUB_TOKEN itself is never exposed to the attacker (it stays in the victim's own `Command` environment), but the attacker succeeds in causing the victim's own credentialed deploy process to run for a commit approval that never legitimately passed victim's own CI gating, and did not originate from a webhook authenticated for victim's repository. This is repeatable against any Shipit stack whose commit history shares any SHA with a repository the attacker controls (trivial via forking public repos), and scales across all stacks/tenants hosted on the same Shipit instance.

### Likelihood Explanation
Preconditions: (1) the target Shipit instance hosts multiple tenants/orgs (as documented, multi-org `github:` config is a supported setup) with the attacker holding a legitimate, unprivileged account/repo on at least one of them; (2) the victim's repository has public (or otherwise attacker-accessible) history so the attacker can obtain an exact commit object to place into a repo they control (fork, or push of a copied commit object); (3) the shared commit must be reachable as `next_commit_to_deploy` for the victim stack (i.e., not yet deployed, not blocked by other required statuses if the DeploySpec has more than one required check) — attacker can read the victim's `shipit.yml` (public) to learn the exact required context name to forge. Attacker cost is low: fork the repo, push/create the shared commit, call GitHub's create-status API on their own fork for that SHA. No secrets, sessions, or privileged roles are required, satisfying the stated threat model.

### Recommendation
Scope `StatusHandler#process` the same way `PushHandler` does: resolve the reporting repository via `Repository.from_github_repo_name(payload.dig('repository','full_name'))` and restrict the `Commit` lookup to `sha` **and** that repository's stacks (e.g., `stacks.flat_map(&:commits).where(sha: params.sha)` or equivalently join `Commit` to `Stack`/`Repository` and filter by the matching repository), rejecting/ignoring any commit whose owning stack's repository does not match the webhook's `repository.full_name`.

### Proof of Concept
Minitest plan (no live GitHub):
1. Create two stacks fixtures backed by two different `Repository` records (`victim/prod` and `attacker/fork`), each with a `Commit` row sharing the identical `sha` value (simulating shared fork history), where the victim commit is `next_commit_to_deploy`-eligible pending a specific required status context (e.g., `ci/travis`).
2. POST to `/webhooks` with `X-Github-Event: status`, a JSON body `{"sha": SHARED_SHA, "state": "success", "context": "ci/travis", "repository": {"full_name": "attacker/fork", "owner": {"login": "attacker"}}}`, and a signature computed with `attacker`'s configured `webhook_secret` (stub `Shipit.github(organization: 'attacker').verify_webhook_signature` to return `true`, matching existing test patterns like `GithubHook.any_instance.stubs(:verify_signature).returns(true)`).
3. Assert: `assert_difference('victim_commit.statuses.count', 1) { post :create, body:, as: :json }` and `assert_equal victim_stack.id, victim_commit.reload.statuses.last.stack_id` — i.e., a `Status` was written into the victim's stack from a webhook whose `repository.full_name` was `attacker/fork`, proving `repository.full_name` (attacker's repo) != `commit.stack.repository.full_name` (victim's repo) yet the write succeeded.
4. Extend by stubbing `Command#start`/`PTY.spawn` and asserting `ContinuousDeliveryJob.perform_now(victim_stack)` results in a deploy `Task` created/spawned for `victim_stack`, confirming the forged cross-repo status reached `Stack#trigger_deploy`.
