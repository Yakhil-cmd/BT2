### Title
Cross-organization commit status forgery via webhook secret confusion between the authenticated GitHub organization and the commit/stack actually written - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`WebhooksController#verify_signature` authenticates an inbound webhook against the `webhook_secret` belonging to whatever organization appears in `params.dig('repository','owner','login')` (or `organization.login`) [1](#0-0) , using `repository_owner` purely as a lookup key for which app config to verify with [2](#0-1) . Once verified, the entire raw payload is handed to the event handler, and `Shipit::Webhooks::Handlers::StatusHandler` looks up and mutates commits **solely by SHA**, with no re-validation that the commit's owning repository/organization matches the organization whose secret authenticated the request: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [3](#0-2) . The handler's `params` block doesn't even require a `repository` field [4](#0-3) .

### Finding Description
This is a direct analog of the reported bug class: a value that was verified/authenticated (the organization tied to the `X-Hub-Signature`) is not the same value that is subsequently used to select which resource gets written (the commit/stack, selected by a bare SHA match with no owner check). Just as `quoteExactOutput` verified a `USDC` amount but the calling code acted as if it had verified a `USDs` amount, `verify_signature` cryptographically verifies "this payload came from organization X" but `StatusHandler#process` acts on "any commit anywhere in the database whose SHA matches," regardless of which organization/repository that commit belongs to.

Concretely:
1. Shipit supports hosting stacks for multiple independent GitHub organizations, each with its own registered `github.<org>.webhook_secret` [5](#0-4) .
2. An attacker who controls one such registered organization ("Org A") can compute a valid `X-Hub-Signature` over an arbitrary JSON body using Org A's `webhook_secret`.
3. `verify_signature` only checks that the signature is valid for the organization named in the payload's `repository.owner.login`/`organization.login` field — it never checks that this organization actually owns the commit, repo, or stack that will be mutated [6](#0-5) .
4. The attacker crafts a `status` event payload: `repository.owner.login = "org-a"` (so the HMAC checks out against Org A's secret) while `sha` is set to a commit SHA belonging to a stack under a completely different organization ("Org B") that also happens to be hosted on the same Shipit instance.
5. `StatusHandler` finds `Commit.where(sha: params.sha)` — this is a global, unscoped lookup — and calls `commit.create_status_from_github!(params)`, injecting an attacker-chosen `state` (e.g. `"success"`) and `context` for Org B's commit [7](#0-6) .
6. This status feeds directly into `Commit#deployable?`, `Status::Group`, and `stack.schedule_merges`, which govern whether a commit is considered CI-passing and eligible for deploy/merge [8](#0-7) [9](#0-8) .

The binding broken, stated as an equality that the code implicitly assumes but never enforces:
`organization authenticated by webhook signature == organization owning the repository/commit being written`

### Impact Explanation
By forging a fake "success" CI status for a commit in a repository/organization the attacker does not control, the attacker can make a commit appear deployable in Org B's stack (`deployable?` becomes true when `success? && !blocked?`), enabling continuous delivery (`schedule_continuous_delivery`) or a manual deploy of a commit that never actually passed real CI — i.e., an unauthorized deploy driven by a cross-organization/cross-repository write into another tenant's commit-status state. This matches the "High" impact bar: escalation into deploy authorization state via cross-repository writes triggered by an unprivileged party who merely controls a different, unrelated organization's webhook secret on the same multi-tenant Shipit instance.

### Likelihood Explanation
Exploitability requires only that: (a) the Shipit instance hosts multiple GitHub organizations (an explicitly documented, supported configuration [5](#0-4) ), and (b) the attacker controls (or has compromised) one of those organizations enough to have a `webhook_secret` provisioned for it — which is a normal, low-privilege configuration step for onboarding any org to Shipit, not a Shipit-specific privileged credential. No `ApiClient` token, no Shipit account, and no access to the target organization is needed; only knowledge/possession of the attacker's *own* org's webhook secret and knowledge of a target commit SHA (SHAs are not secret — visible via GitHub, PRs, CI, etc.).

### Recommendation
Scope the `status` (and any similar SHA-only) handler lookup to the repository indicated by the payload, and cross-check that this repository's owning organization matches the organization used in `verify_signature`. Concretely: require the `repository.full_name` field in `StatusHandler::params`, resolve commits via `Repository.from_github_repo_name(...).stacks.commits.where(sha: ...)` (mirroring `Handler#stacks`/`#repository_name` used by other handlers) instead of a bare, unscoped `Commit.where(sha:)`, and additionally assert `payload.dig('repository','owner','login') == repository_owner` before dispatching to handlers so a payload can never claim one organization for signing and reference another organization's resources.

### Proof of Concept
1. Configure Shipit for two orgs: `org-a` (attacker-controlled, `webhook_secret = SECRET_A`) and `org-b` (victim, with a stack tracking commit `abc123...` that is currently pending/failing CI).
2. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(SECRET_A, body)` over:
```json
{
  "sha": "abc123...",            // victim Org B's commit
  "state": "success",
  "context": "ci/attacker-forged",
  "repository": { "owner": { "login": "org-a" } }
}
```
3. POST to `/github/webhooks` with header `X-Github-Event: status` and the computed signature.
4. `verify_signature` resolves `Shipit.github(organization: "org-a")` and validates successfully using `SECRET_A` [1](#0-0) .
5. `StatusHandler#process` finds the commit by SHA globally and applies the forged "success" status to Org B's commit [3](#0-2) , potentially flipping `deployable?` to `true` for a stack the attacker never had access to.

      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",

      ].join(' '))
    end

    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
