### Title
Scoped `ApiClient` tokens can read the CI/deploy status of any stack via `CCMenuController` - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::CCMenuController#stack` overrides the stack-scoping logic inherited from `Shipit::Api::BaseController`, looking the target stack up directly from the URL parameter instead of restricting it to the stack the authenticated `ApiClient` is authorized for. This breaks the binding `current_api_client.stack_id == stack actually read`, letting a token scoped to one stack read the CCMenu (build/deploy) status of any other stack.

### Finding Description
`BaseController` enforces per-token stack scoping centrally: [1](#0-0) 

`stacks` restricts the queryable set to `current_api_client.stack_id` when the client is scoped, and `stack` resolves the requested `stack_id` param only within that authorized set — this is the mechanism that binds "stack a token authorizes" to "stack a request may touch."

`CCMenuController`, however, defines its own `stack` method that ignores this scoping entirely: [2](#0-1) 

It resolves `Stack.from_param!(params[:stack_id])` directly from the global `Stack` relation, with no reference to `current_api_client.stack_id`. The only authorization check that runs is `require_permission :read, :stack`, which is a generic permission-string check, not a check that the resolved record matches the client's assigned stack: [3](#0-2) 

Since `ApiClient` supports being scoped to a single stack (`belongs_to :stack, optional: true`), and other endpoints (e.g. `stacks#index`) correctly enforce that scope, `CCMenuController` is inconsistent: a token minted with `stack_id` set to Stack A and `permissions: ['read:stack']` will still be accepted for `GET /api/stacks/:stack_id/ccmenu` where `:stack_id` refers to Stack B, C, etc.

The route is reachable with just the permission `read:stack` and either Basic Auth or a `token` query parameter: [4](#0-3) [5](#0-4) 

### Impact Explanation
A scoped `ApiClient` (e.g. minted by `CCMenuUrlController` for a specific stack, or any narrowly-scoped credential issued to a limited-trust integration) can be replayed against arbitrary `stack_id` values to read the last build status, build label, activity, and lock state of stacks it was never granted access to. This is an unauthorized cross-stack read of deploy/task state, matching the "unauthenticated/unauthorized read of stack state, task streams or deploy output" High-severity category — the equality `current_api_client.stack_id == params[:stack_id]` that every other API endpoint enforces is silently dropped for this one action.

### Likelihood Explanation
Any holder of a valid, narrowly-scoped `ApiClient` token with `read:stack` permission can trigger this by simply changing the `stack_id` in the URL of the CCMenu endpoint — no additional privilege, secret, or session is required beyond the token itself, which is exactly the class of credential this endpoint is meant to restrict.

### Recommendation
Remove the local `stack` override in `CCMenuController` (or reimplement it using the inherited `stacks` scope) so lookups go through `stacks.from_param!(params[:stack_id])`, ensuring the resolved stack is always constrained by `current_api_client.stack_id` when the client is scoped.

### Proof of Concept
1. Create an `ApiClient` scoped to Stack A: `ApiClient.create!(creator: user, name: 'x', stack: stack_a, permissions: ['read:stack'])`.
2. As an attacker holding only this token, send `GET /api/stacks/<stack_b_owner>/<stack_b_repo>/<stack_b_branch>/ccmenu?token=<token>` for unrelated Stack B.
3. Compare with `app/controllers/shipit/api/base_controller.rb:74-80` `stacks`/`stack`: request succeeds and returns Stack B's CCMenu XML (`lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, `activity`) because `CCMenuController#stack` (`app/controllers/shipit/api/ccmenu_controller.rb:29-31`) never filters by `current_api_client.stack_id`, whereas the equivalent index/show actions elsewhere would have returned only Stack A or a 404/403.
