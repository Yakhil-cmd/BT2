### Title
`StatusHandler#process` writes commit statuses without repository scoping, allowing cross-repository status forgery - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` looks up commits solely by `Commit.where(sha: params.sha)`, with no scoping to the `repository` in the webhook payload, unlike `PullRequest::OpenedHandler`, which resolves `repository = Shipit::Repository.from_github_repo_name(params.repository.full_name) || NullRepository.new` before acting. Because GitHub's Statuses API lets any repository owner set a commit status for an arbitrary SHA (the SHA is not required to be a commit that exists in the poster's own repository history), an attacker who owns any repository with the Shipit GitHub App installed can create a status for a victim's commit SHA, and Shipit will apply it to the victim's `Commit`/`Stack` because `StatusHandler` never checks which repository the SHA belongs to.

### Finding Description
The claimed broken binding, stated as an equality: `params.repository.full_name` (from the webhook payload) SHOULD equal `commit.stack.repository.github_repo_name` (the repository owning the matched `Commit`) before `create_status_from_github!` is invoked — but `StatusHandler#process` never establishes or checks this equality.

Code path:
- `app/controllers/shipit/webhooks_controller.rb#create` dispatches the parsed JSON payload to `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` after `verify_signature`, which validates the HMAC signature using `Shipit.github(organization: repository_owner)` — i.e., the webhook secret tied to the **attacker's own** organization/app installation (`repository_owner = params.dig('repository', 'owner', 'login')`). This confirms the payload is authentic for the attacker's *own* repo, not the victim's. [1](#0-0) 
- `StatusHandler#process` then does:
```ruby
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
```
with no call to `repository_name`/`stacks`, unlike the base `Handler` class which defines but never uses this scoping inside `StatusHandler`. [2](#0-1) [3](#0-2) 

Contrast with `PullRequest::OpenedHandler`, which explicitly resolves and scopes to the repository named in the payload before taking any action, and falls back to a `NullRepository` (no-op) if the named repository doesn't match a registered `Shipit::Repository`: [4](#0-3) 

`Commit#sha` has a composite index on `(stack_id, sha)` (per `db/migrate/20170524104615_index_commits_on_stack_id_and_sha.rb`), meaning the schema itself expects SHA to be looked up per-stack, but `StatusHandler` ignores this and queries by SHA alone across all stacks/repositories in the installation. `Commit#create_status_from_github!` then calls `add_status`, which writes a `Status` record, may emit `Hook.emit(:commit_status/:deployable_status, stack, ...)`, and can trigger `stack.schedule_merges` — all against the victim's `stack`, not the attacker's. [5](#0-4) [6](#0-5) 

Attacker action: the attacker owns a GitHub repository/organization with the Shipit GitHub App installed (this is the same "unprivileged" precondition needed for the `pull_request` control case — they can open PRs and emit webhooks from a repo they own). Using their own valid GitHub credentials, they call GitHub's `POST /repos/{attacker}/{repo}/statuses/{victim_sha}` where `victim_sha` is a SHA belonging to a commit already imported into a different Shipit `Stack` (e.g., learned from a public repo, PR, or CI page). GitHub delivers a legitimately signed `status` webhook to Shipit, signed with the attacker's own installation secret, with `payload.repository.full_name = attacker/repo` and `payload.sha = victim_sha`. `verify_signature` passes because it validates against the attacker's own org. `StatusHandler` then matches `Commit.where(sha: victim_sha)` — hitting the victim's commit — and writes a status onto it.

Existing guards fail to prevent this:
- `verify_signature` only proves the *sender* legitimately controls the named `repository_owner`; it says nothing about whether the `sha` in the body belongs to that repository. [7](#0-6) 
- `ExplicitParameters` schema in `StatusHandler` only validates types/presence of `sha`, `state`, etc., not repository ownership of the sha. [8](#0-7) 
- `Handler#stacks`/`repository_name` scoping exists in the base class but is dead code with respect to `StatusHandler`, which never calls it. [9](#0-8) 

### Impact Explanation
An attacker who owns any repository connected to the Shipit installation can inject arbitrary commit statuses (`success`, `failure`, `pending`, with attacker-controlled `description`/`target_url`/`context`) onto commits belonging to *any other* stack/repository in the same Shipit instance, as long as they know or can guess a target SHA. Because `deployable?` depends on `status.success?` [10](#0-9) , and `schedule_continuous_delivery` fires when a commit becomes deployable and the stack has continuous deployment enabled [11](#0-10) , forging a "success" status for a victim's pending/blocked commit can trigger an unauthorized deploy of a stack the attacker does not control. This matches the Critical category: "a payload for one repository mutating another's stack, commit, task or team" and "an unauthorized deploy." The blast radius spans every stack/tenant hosted by the same Shipit instance, and the attack is fully repeatable against arbitrary SHAs/repositories without additional privilege.

### Likelihood Explanation
Preconditions: the attacker needs (a) their own GitHub repository with the Shipit GitHub App installed (a normal, unprivileged onboarding step available to "any GitHub user"), and (b) knowledge of a target commit SHA in another repository tracked by the same Shipit instance (trivially obtainable from any public repo, PR, or CI status page). No Shipit session, API token, or secret is required — the webhook signature is validated against the attacker's own legitimate installation. This is a low-cost, highly repeatable attack requiring only a single GitHub API call per forged status.

### Recommendation
Scope `StatusHandler#process` to the repository named in the payload, mirroring the `PullRequest` handlers' pattern, e.g.:
```ruby
def process
  Commit.where(sha: params.sha, stack: stacks).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
using the existing `Handler#stacks`/`repository_name` helper so that only commits belonging to stacks under the repository named in the authenticated payload can be updated.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb`), no live GitHub:

```ruby
test "status webhook does not update commit statuses belonging to another repository" do
  org_a_stack = shipit_stacks(:shipit) # repository X/Y
  org_b_stack = create_stack_for_repository('org-b/other-repo')
  victim_commit = org_b_stack.commits.create!(sha: 'deadbeef' * 5, ...)

  payload = {
    'sha' => victim_commit.sha,
    'state' => 'success',
    'repository' => { 'full_name' => 'org-a/attacker-repo' } # attacker's own repo
  }

  before = victim_commit.reload.status.state
  Shipit::Webhooks::Handlers::StatusHandler.call(payload)

  # equality check both sides:
  assert_equal before, victim_commit.reload.status.state,
    "status for org-b's commit must not change from an org-a-scoped payload"
end

test "pull_request webhook for org A does not affect org B's stack (control case)" do
  org_b_repo = create_repository('org-b/other-repo', review_stacks_enabled: true)
  payload = pull_request_opened_payload(repository_full_name: 'org-a/attacker-repo', ...)

  assert_no_difference -> { org_b_repo.review_stacks.count } do
    Shipit::Webhooks::Handlers::PullRequest::OpenedHandler.call(payload)
  end
end
```
The first test demonstrates the missing binding (`params.repository.full_name` vs. the matched commit's actual stack repository) causes a cross-repository write; the second confirms the equivalent `pull_request` path correctly rejects the same cross-repo attempt via its own `repository` resolution.

    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
