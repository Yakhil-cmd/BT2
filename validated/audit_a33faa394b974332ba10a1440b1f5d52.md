### Title
Merkle tree leaf/internal-node hash collision ("node-as-leaf") allows forging inclusion proofs in `is_valid_merkle_proof` and the `in merkle` authentifier - ([File: merkle.js])

### Summary
`merkle.js` computes both leaf hashes and internal-node hashes with the exact same `sha256`-then-base64 function and no domain separation between "this is a leaf" and "this is an internal node made of two child hashes." This is the same root cause flagged in the external report (pre-hash data structurally indistinguishable from an internal node), and ocore's own code even contains a comment acknowledging the risk without fixing it. This Merkle implementation backs two attacker-reachable primitives: the oscript function `is_valid_merkle_proof` (usable in AA trigger-data validation) and the `in merkle` address-definition authentifier.

### Finding Description
`getMerkleRoot`/`getMerkleProof` build the tree as:
- leaf hash: `hash(element)`
- internal node hash: `hash(hash(left) + hash(right))` [1](#0-0) 

`verifyMerkleProof` walks the supplied siblings from `element` up to `root` using the same `hash()` at every step, and the code explicitly notes the "Node-as-Leaf issue": [2](#0-1) 

Because leaf hashing and internal-node hashing share the identical hash function and there is no leading tag/prefix (e.g. `0x00`/`0x01`) to separate the two domains, anyone who knows two adjacent hash values `H_a`, `H_b` inside a real tree can construct a forged "leaf" whose raw content is the literal concatenation `H_a + H_b`. `hash(H_a + H_b)` computed as a leaf hash is identical to the internal-node hash `hash(H_a + H_b)` that was originally computed from real children `H_a`/`H_b`. Re-using the remaining sibling path from that internal node up to the root produces a proof that `verifyMerkleProof` (and therefore `is_valid_merkle_proof`) accepts for an element that was never part of the original data set — a classic second-preimage / node-reinterpretation attack, exactly the bug class in the report.

This routine is reachable from two unprivileged, attacker-controlled entry points:

1. **oscript formula `is_valid_merkle_proof`** — both the `element` and the `proof` arguments are evaluated from arbitrary oscript expressions, which in an AA context typically come straight from `trigger.data`, fully controlled by the AA trigger sender: [3](#0-2) [4](#0-3) 

2. **`in merkle` address-definition authentifier** — a unit poster supplies `serialized_proof` as an authentifier value, which is deserialized and checked with `merkle.verifyMerkleProof`; if it verifies, the code trusts `proof.root` and checks it against a data feed value: [5](#0-4) 

If an AA author (or address-definition author) uses either of these primitives to gate fund release/asset transfer/whitelist checks against a previously published Merkle root (e.g., an allow-list root stored in AA state vars, or a root posted via a data feed), an attacker who can reconstruct or observe the internal structure of that tree (the underlying element set is very often public — whitelists, snapshot data, etc.) can synthesize a proof for a fabricated "element" that was never part of the original set, as long as that fabricated element happens to equal the concatenation of two real sibling hash values in the tree.

### Impact Explanation
Any AA logic (or address definition) that relies on `is_valid_merkle_proof`/`in merkle` to authorize a payment, mint/whitelist an asset, or unlock funds for whoever proves membership of a specific value in a Merkle set can be bypassed: an attacker forges a valid-looking proof for an unauthorized/fabricated leaf value, resulting in unauthorized fund release from an AA or unauthorized satisfaction of an address's spending condition — i.e., unauthorized spending / AA fund loss, matching the High severity of the analogous report.

### Likelihood Explanation
Exploitation requires the attacker to know (or reconstruct) the full leaf set of the target Merkle tree so it can compute matching internal-node hash pairs — a condition frequently true in practice since such data sets (whitelists, distribution lists, oracle-fed data) are usually published or derivable off-chain by design. No special privilege beyond posting a normal unit/AA trigger is needed, and the vulnerable code path (`merkle.js`'s undifferentiated hash function) is unconditionally reachable from both `is_valid_merkle_proof` in oscript and the `in merkle` authentifier.

### Recommendation
Add domain separation to `merkle.js` so leaf hashes and internal-node hashes cannot collide, e.g. prefix leaf hashing with a distinct tag (`hash("\x00"+element)`) and internal-node hashing with a different tag (`hash("\x01"+left+right)`), and apply this consistently across `getMerkleRoot`, `getMerkleProof`, and `verifyMerkleProof`. This is a hard-fork-relevant change since it alters serialized proof semantics and existing/expected Merkle roots — it must be gated behind a protocol upgrade MCI similar to other consensus-affecting formula behavior changes already present in `formula/evaluation.js` (e.g. `bPostPemCurvesFix`).

### Proof of Concept
Using ocore's own `merkle.js` semantics:
1. Build a 4-leaf tree over public elements `A, B, C, D`:
   - `H_A = hash(A)`, `H_B = hash(B)`, `H_C = hash(C)`, `H_D = hash(D)`
   - `L = hash(H_A + H_B)`, `R = hash(H_C + H_D)`
   - `root = hash(L + R)`
2. Attacker, knowing `H_A` and `H_B` (derivable from the public `A`, `B`), crafts a forged element `X = H_A + H_B` (raw string concatenation, not one of `A..D`).
3. Attacker submits `proof = { index: 0, siblings: [R], root: root }` together with `element = X` to `is_valid_merkle_proof(X, proof)` (via AA `trigger.data`) or as the `serialized_proof` authentifier for an `in merkle` clause.
4. `verifyMerkleProof` computes `hash(X) = hash(H_A+H_B) = L`, then `hash(L + R) = root`, returning `true` — confirming `X` as a "member" of the tree even though `X` was never one of the original leaves `A, B, C, D`, per the logic in [2](#0-1) .

function hash(str){
	return crypto.createHash("sha256").update(str, "utf8").digest("base64");
}

function getMerkleRoot(arrElements){
	var arrHashes = arrElements.map(hash);
	while (arrHashes.length > 1){
		var arrOverHashes = []; // hashes over hashes
		for (var i=0; i<arrHashes.length; i+=2){
			var hash2_index = (i+1 < arrHashes.length) ? (i+1) : i; // for odd number of hashes
			arrOverHashes.push(hash(arrHashes[i] + arrHashes[hash2_index]));
		}
		arrHashes = arrOverHashes;
	}
	return arrHashes[0];
}

function verifyMerkleProof(element, proof){
	// Node-as-Leaf issue might matter in some cases
	try {
		var index = proof.index;
		var the_other_sibling = hash(element);
		for (var i = 0; i < proof.siblings.length; i++) {
			// this also works for duplicated trailing nodes
			if (index % 2 === 0)
				the_other_sibling = hash(the_other_sibling + proof.siblings[i]);
			else
				the_other_sibling = hash(proof.siblings[i] + the_other_sibling);
			index = Math.floor(index / 2);
		}
		return (the_other_sibling === proof.root);
	}
	catch (e){
		return false;
	}
}
