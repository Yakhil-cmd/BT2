### Title
Missing cosigner authorization check in wallet "sign" message handler enables unauthorized signing requests on locally-controlled addresses - (File: wallet.js)

### Summary
`handleMessageFromHub`'s `"sign"` case in `wallet.js` accepts a request from any paired correspondent device to co-sign a transaction on any address the requester claims that node hosts. When `findAddress` resolves the address locally (`ifLocal`), the code explicitly skips verifying that the sending device (`from_address`) is actually a legitimate cosigner of that address before proceeding to hash and emit a `"signing_request"` event that can lead to a signature being produced. This mirrors CVE-2017-14140's root cause: an operation is performed against a target (a process/an address) without validating that the caller is actually authorized to act on that target.

### Finding Description
In the `"sign"` case, after validating the shape of the request and confirming that `body.address` is present among the `objUnit.authors`, the code calls `findAddress(body.address, body.signing_path, ...)`. In the `ifLocal` branch, a check that would confirm the sender is a genuine cosigner of the address is present only as a comment: [1](#0-0) 

```

    ifError: callbacks.ifError,
    ifLocal: function(objAddress){
        // the commented check would make multilateral signing impossible

        //    if (sender_rows.length !== 1)
        //        return callbacks.ifError("sender is not cosigner of this address");
```

Nothing else in the `ifLocal` branch validates that `from_address` (the actual sender of the request, verified only at the transport/pairing layer) is one of the legitimate cosigners recorded for `body.address` in `wallet_signing_paths`/`shared_address_signing_paths`/`extended_pubkeys`. The only checks performed are on the *shape* of the attacker-supplied `unsigned_unit` (that `body.address` appears among its authors, that payload hashes match, etc.), all of which the attacker fully controls since they construct the unit themselves. [2](#0-1) 

As a result, `callbacks.ifOk()` is invoked unconditionally, and the code proceeds to compute the unit hash and emit `eventBus.emit("signing_request", objAddress, body.address, objUnit, assocPrivatePayloads, from_address, body.signing_path)`, which is the public API surface that any signer implementation (interactive wallet UI or automated/headless wallet) listens on to actually produce the missing signature. [3](#0-2) 

Notably, the parallel `ifRemote` branch (used when the target address's key lives on another device and the current node is only a proxy) *does* perform this check: [4](#0-3) 
```
ifRemote: function(device_address, other_device_addresses){
    if (device_address === from_address)
        return callbacks.ifError("looping signing request for address "+body.address+", path "+body.signing_path);
    if (!other_device_addresses.includes(from_address))
        return callbacks.ifError("you are not listed as a cosigner for this address "+body.address);
```
This confirms the omission in `ifLocal` is an inconsistency/gap rather than an intentional universal design choice — the codebase itself demonstrates the proper check pattern in a sibling branch, yet fails to apply the analogous check when the target key is hosted locally.

### Impact Explanation
Any device paired with a wallet (a "correspondent," not necessarily a genuine multisig cosigner of a particular address) can send a forged `"sign"` request for any address that the target wallet locally hosts, including ordinary single-sig payment addresses and multisig addresses the sender is not actually part of. Because the address-vs-cosigner relationship is never validated, the wallet cannot distinguish a legitimate multilateral-signing partner from an unrelated, untrusted correspondent probing/soliciting a signature on an attacker-crafted transaction. Any listener that acts on the `"signing_request"` event without independently re-validating the requester's legitimacy as cosigner (which the emitted event does not itself provide) can be induced to produce a partial or full valid signature over an attacker-chosen transaction, enabling unauthorized spending of funds from the targeted address, particularly acute for automated/non-interactive wallet signers.

### Likelihood Explanation
The `"sign"` message subject is directly reachable from any paired device via `handleMessageFromHub`, requiring no on-chain footprint or special privileges beyond an existing device pairing — a normal, low-barrier prerequisite for wallet correspondents. The attacker fully controls the `unsigned_unit` content and only needs to know a target address that the victim's wallet hosts (frequently discoverable, e.g., previously used payment addresses).

### Recommendation
Restore and enforce the cosigner check in the `ifLocal` branch of the `"sign"` case: before proceeding to hash/emit the signing request, verify that `from_address` is registered as an authorized cosigner device for `body.address` (via `wallet_signing_paths` for wallet-owned addresses and `shared_address_signing_paths` for shared addresses), mirroring the check already implemented in the `ifRemote` branch. If multilateral (non-cosigner) signing scenarios are still required, gate them behind an explicit, narrower authorization mechanism (e.g., matching the address's actual definition membership) instead of removing the check entirely.

### Proof of Concept
1. Attacker device pairs with victim's wallet as an ordinary correspondent (no shared address relationship required).
2. Attacker learns/guesses one of the victim's locally-hosted payment addresses `A` (single-sig or a multisig address the attacker is not part of).
3. Attacker crafts an `unsigned_unit` whose `authors` include address `A` and whose payment message spends `A`'s funds to an attacker-controlled address, then sends a `"sign"` device message: `{address: A, signing_path: "r", unsigned_unit: <forged unit>}`.
4. Victim's `handleMessageFromHub` resolves `A` via `findAddress` to `ifLocal` (since `A` is locally hosted) and, lacking any cosigner check, calls `callbacks.ifOk()` and emits `"signing_request"` for `A` with the attacker-forged unit.
5. Any signer logic subscribed to `"signing_request"` that trusts this event to represent a legitimate cosigning request (e.g., automated/headless signer, or a user who is not shown enough context to detect the request did not originate from a true cosigner) produces the requested signature, yielding an unauthorized, signed spend from `A`.
