This confirms the exploit path. The controller verifies the signature using `repository_owner` derived from `params.dig('repository', 'owner', 'login')` [1](#0-0) , while the actual repository/stack mutated by the handler is looked up from an entirely separate field, `params.repository.full_name`, via `Shipit::Repository.from_github_repo_name` [2](#0-1) . Nothing enforces that `repository.owner.login` is consistent with `repository.full_name` in the same JSON body — the attacker fully controls both fields independently.

Critically, `GitHubApp#verify_webhook_signature` returns `true` unconditionally when no `webhook_secret` is configured for that organization, before even inspecting the signature header or algorithm: [3](#0-2) . Since `webhook_secret` is documented as optional per-organization [4](#0-3) , an attacker can target any organization configured without a secret (setting `repository.owner.login` to that org to sail through `verify_signature`), while setting `repository.full_name` to an entirely different, real tracked repository belonging to another tenant/org. The `LabeledHandler` then archives or unarchives that other org's `ReviewStack` based on the label content the attacker fully controls [5](#0-4) , and `ReviewStackAdapter#archive!`/`unarchive!` perform real deprovisioning/provisioning actions [6](#0-5) .

Note this is broader than the "sha1 vs sha256" framing in the question implies: the actual root cause is that a no-secret org bypasses verification entirely (no signature check happens at all, regardless of algorithm), combined with the verification org and the mutated-record org being read from two different, attacker-controlled fields of the same payload.

### Title
Signature verification checks a different repository field than the one the handler mutates, allowing cross-tenant `ReviewStack` archive/unarchive - (File: app/controllers/shipit/webhooks_controller.rb, app/models/shipit/webhooks/handlers/pull_request/labeled_handler.rb)

### Summary
`WebhooksController#verify_signature` derives the signing organization from `params.dig('repository', 'owner', 'login')`, while `Shipit::Webhooks::Handlers::Handler`/`LabeledHandler` resolve the repository to mutate from the independent `params.repository.full_name` field of the same attacker-controlled JSON body. When any organization is configured in Shipit without a `webhook_secret` (a documented, supported configuration), `GitHubApp#verify_webhook_signature` short-circuits to `true` for any signature (or lack thereof), letting an attacker forge a payload whose `repository.owner.login` names the no-secret org while `repository.full_name` names a real tracked repository belonging to a different, unrelated organization, causing `LabeledHandler` to archive/unarchive that other org's review stack.

### Finding Description
The broken binding is: *the organization whose `webhook_secret` verified the request* MUST equal *the organization owning the repository/stack the handler writes to*. In code:

- Verification org: `repository_owner = params.dig('repository', 'owner', 'login')` used in `Shipit.github(organization: repository_owner)` and `github_app.verify_webhook_signature(...)` [1](#0-0) , [7](#0-6) .
- Mutated org: `Shipit::Repository.from_github_repo_name(params.repository.full_name)` inside `LabeledHandler#repository` [2](#0-1) , and the same field is used generically in `Handler#repository_name`/`#stacks` [8](#0-7) .

Nothing ties these two lookups together or validates that `repository.owner.login` is a prefix of `repository.full_name`. The attacker fully controls the raw JSON body (`request.raw_post`), so these two fields can point at two different organizations.

Root cause in `GitHubApp#verify_webhook_signature`: `return true unless webhook_secret` [3](#0-2)  — if the org named by `repository.owner.login` has no secret configured (an explicitly supported/optional configuration per `docs/setup.md` and `config/secrets.development.example.yml`), verification passes unconditionally, without even inspecting the `X-Hub-Signature` header content or algorithm.

Exploit flow:
1. Shipit operator has configured at least one organization without a `webhook_secret` (supported by design).
2. Attacker POSTs to `/webhooks` with `X-Github-Event: pull_request`, body `action: "labeled"`, `repository.owner.login: "<no-secret-org>"`, but `repository.full_name: "<victim-org>/<real-tracked-repo>"`, and a `pull_request` object with attacker-chosen `labels`.
3. `verify_signature` calls `Shipit.github(organization: "<no-secret-org>")` and `verify_webhook_signature` returns `true` immediately, no signature required.
4. `WebhooksController#create` re-parses the body and dispatches to `LabeledHandler`, which resolves `repository` via `params.repository.full_name` — the victim org's real repository — and calls `stack.archive!`/`unarchive!` on that org's `ReviewStack` [9](#0-8) .

Existing guards do not close this gap: `drop_unhandled_event` only filters unrecognized event types [10](#0-9) ; the `ExplicitParameters` schema in `LabeledHandler.params` validates types/presence but not cross-field consistency between `repository.full_name` and any owner field [11](#0-10) ; and `verify_signature`'s `rescue Shipit::GithubOrganizationUnknown` only guards against the org key not existing at all, not against a mismatched-but-known org.

### Impact Explanation
An unauthenticated attacker can cause `Shipit::ReviewStack#archive!`/`#unarchive!` to run against any tracked repository's review stack in a multi-org Shipit deployment, as long as at least one configured organization has no `webhook_secret`. `archive!` calls `stack.remove_from_provisioning_queue` and `stack.deprovision`; `unarchive!` re-queues provisioning [6](#0-5)  — real infrastructure state changes on a repository/organization the attacker never authenticated against. This is repeatable against any repository tracked by Shipit and matches the "payload for one repository mutating another's stack" Critical category.

### Likelihood Explanation
Preconditions: (1) Shipit must be configured with multiple GitHub organizations, and (2) at least one of them must have no `webhook_secret` set — both explicitly supported/documented configurations, not misconfigurations from this engine's perspective [12](#0-11) . Given that, attacker cost is a single unauthenticated HTTP POST with a hand-crafted JSON body; no GitHub account, session, or secret is required. Fully repeatable against any repository with `review_stacks_enabled` and an open PR number the attacker guesses or observes.

### Recommendation
Derive the repository/organization used by every handler from the same value verified by `verify_signature` (e.g., pass the verified `repository_owner`/org context into `Handler#call` and require `Repository#owner`/organization to match it), or reject requests where `repository.full_name`'s owner segment does not match `repository.owner.login`. Additionally, do not implicitly trust a payload merely because the named organization has no `webhook_secret` — require explicit opt-in or bind the "no secret" bypass to the same org actually referenced by `repository.full_name`.

### Proof of Concept
Minitest (`ActionDispatch::IntegrationTest` or `ActionController::TestCase` analogous to `test/controllers/webhooks_controller_test.rb`):
1. Configure `Shipit.github(organization: 'org-no-secret')` with no `webhook_secret`.
2. Create a real tracked `Shipit::Repository`/`Stack` owned by `victim-org/victim-repo` with `review_stacks_enabled` and provisioning-label behavior configured, plus an existing unarchived `ReviewStack` for PR number 42.
3. POST `/webhooks` with `X-Github-Event: pull_request`, no `X-Hub-Signature` (or an arbitrary bogus one), and body: `{"action":"labeled","number":42,"pull_request":{...,"state":"open","labels":[{"name":"<provisioning_label>"}]},"repository":{"owner":{"login":"org-no-secret"},"full_name":"victim-org/victim-repo"},"sender":{"login":"attacker"}}`.
4. Assert response is `:ok` (not `422`).
5. Assert `victim_stack.reload.archived?` (or `unarchived?`) changed as dictated by the attacker-controlled label — proving a record owned by `victim-org`, never authenticated by any secret, was mutated using verification that only checked `org-no-secret`.
