## Analysis

This confirms the binding break: `WebhooksController#verify_signature` selects **which organization's `webhook_secret`** to verify the HMAC against using a field taken directly from the *unverified* JSON body — `repository_owner`, which is `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` — before the signature has been checked. [1](#0-0) [2](#0-1) 

Separately, once the signature check passes, the handlers that actually act on the payload (e.g. `PushHandler`) resolve the target `Stack`/`Repository` using a **different** field: `payload.dig('repository', 'full_name')` via `Handler#repository_name` / `#stacks`. [3](#0-2) [4](#0-3) 

The HMAC in `verify_webhook_signature` is computed over the entire raw body, so the signature does bind the *whole payload's bytes* to the secret used. [5](#0-4)  This means an attacker who legitimately controls one GitHub organization's App/webhook installed on this Shipit instance (i.e., knows that organization's `webhook_secret`) can freely construct the JSON body themselves, since nothing but the signature constrains its content. They can set `repository.owner.login`/`organization.login` to their own org (so `Shipit.github(organization: repository_owner)` picks their own known secret) while setting `repository.full_name` to a **different, victim organization's repository** that is registered as a Shipit `Stack`. Because Shipit never validates that `repository.owner.login` is consistent with `repository.full_name`'s owner, and because Ruby/JSON payload construction is fully attacker-controlled (not actually generated by GitHub), the signature check ends up authenticating "the organization named in the payload" rather than "the organization that owns the repository being acted on."

I was not able to fully trace how `Shipit.github(organization:)` resolves configuration keys (multi-tenant `config/secrets.yml` orgs) to confirm whether this instance would realistically have two independent orgs/secrets configured, and I could not verify inside this session whether GithubSyncJob further re-validates ownership against GitHub's API before acting (which could mitigate real-world exploitability). This is worth further investigation, but based on the code read, the trust boundary the report is checking (`payload field acted on but never covered by the verified signature` / `organization that authenticated versus the repository that is written`) is present at `app/controllers/shipit/webhooks_controller.rb:59-62` vs `app/models/shipit/webhooks/handlers/handler.rb:36-38`.

### Title
Webhook signature is verified against the org named in the (unverified) payload, not the org that owns the repository being acted on - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` picks the GitHub App/`webhook_secret` to check against using `repository_owner`, a value read straight out of the untrusted JSON body, before the signature is validated. The actual event-processing code path (`Handler#repository_name`) instead trusts `repository.full_name` to find the target `Stack`. Because these two payload fields are never checked for consistency, and the HMAC signature only proves "the payload was signed by *some* org's secret," a party who knows one tenant org's `webhook_secret` can forge a payload naming their own org for the signature check while pointing `repository.full_name` at a stack belonging to a different org configured on the same Shipit instance.

### Finding Description
`verify_signature` derives `repository_owner` from the raw, unauthenticated JSON body (`params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`), fetches that org's `GitHubApp` config via `Shipit.github(organization: repository_owner)`, and checks the `X-Hub-Signature` header against that org's `webhook_secret`. [1](#0-0) 

If the signature validates, `create` dispatches the full, attacker-supplied `params` to `Shipit::Webhooks.for_event(event)` handlers, unconstrained by which org's secret was used. [6](#0-5) 

`Handler#stacks` / `#repository_name` then resolves the target repository purely from `payload.dig('repository', 'full_name')`, with no re-check that this repo belongs to the org whose secret signed the request. [3](#0-2) 

This is structurally the same class of bug as H-5: a verification routine (`_verifyLendingPoolIsActive`/here, "verify signature belongs to org X") is bound to one field, while the operation actually performed (renew protection for pool Y / here, act on repository Z) is driven by a different, unchecked field of the same request. The equality that should hold — "org whose secret verified the request == org owning the repo being written to" — is not enforced.

### Impact Explanation
On a multi-tenant Shipit deployment (multiple GitHub orgs each with their own App/`webhook_secret` in `config/secrets.yml`, as documented for the double-github-app setup), a user who administers/owns one tenant org's GitHub App can forge webhook deliveries claiming to originate from a different org's repository. Depending on which handler runs (`push`, `pull_request`, `status`, `check_suite`), this can trigger unauthorized `sync_github`, alter deploy/merge state, spoof CI `status`/`check_suite` results feeding into deploy gating for a repository the attacker does not own — i.e., cross-repository/cross-tenant writes and influence over another org's deploy pipeline using credentials that were never meant to authorize that org's stacks.

### Likelihood Explanation
Requires the attacker to control (or have compromised) a legitimate `webhook_secret` for at least one org configured on the shared Shipit instance — a reasonable bar for a multi-tenant deployment (Shipit explicitly documents supporting multiple GitHub orgs sharing one instance). No repository write access, no Shipit login, and no `ApiClient` token are needed; only the ability to send an HTTP POST to `/webhooks` with a self-signed body.

### Recommendation
In `verify_signature`, after determining the org from `repository_owner`, re-verify that `repository.full_name`'s owner segment matches `repository_owner` (and matches `organization.login` if present) before dispatching to handlers; reject mismatches with 422. More robustly, resolve the target `Stack`/`Repository` first, look up which org it belongs to, and verify the signature using that org's secret rather than trusting an org name asserted inside the unauthenticated payload.

### Proof of Concept
1. Attacker owns/administers GitHub org `attacker-org`, which is configured in this Shipit instance with `webhook_secret = S_attacker`; `victim-org/victim-repo` is a separate Stack in the same instance under a different org's secret.
2. Attacker crafts a `push` webhook JSON body: `{"ref":"refs/heads/main","after":"<sha>","repository":{"full_name":"victim-org/victim-repo","owner":{"login":"attacker-org"}}}`.
3. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(S_attacker, body)` and POSTs to `/webhooks` with `X-Github-Event: push`.
4. `verify_signature` computes `repository_owner = "attacker-org"`, loads `attacker-org`'s `webhook_secret` (`S_attacker`), and the signature matches → passes. [1](#0-0) 
5. `PushHandler#process` resolves `stacks` from `repository.full_name = "victim-org/victim-repo"` and calls `stack.sync_github(...)` on the victim's stack — an action never authorized by that stack's own org secret. [4](#0-3) [3](#0-2)

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
