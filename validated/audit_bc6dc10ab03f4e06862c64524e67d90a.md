### Title
Cross-tenant Status forgery via unscoped SHA lookup in StatusHandler#process enables unauthorized continuous deployment - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` resolves the target commit(s) for an incoming `status` webhook purely by `sha`, with no filter on `repository`/`stack`, while `WebhooksController#verify_signature` only checks that the payload's signature matches the webhook secret configured for the `repository.owner.login` present in the same attacker-controlled payload. An attacker who controls a repository with a webhook secret bound to their own org (or who can otherwise produce a validly-signed payload for their own org) can forge a `success` status for any commit SHA, and if that SHA also exists as a `Shipit::Commit` row belonging to a victim's `Stack` (e.g. via a fork sharing upstream history, or any SHA collision across tracked repositories), the forged status is written to the victim's commit and can trigger `Stack#trigger_continuous_delivery`.

### Finding Description
The intended binding is: `verified_org(repository_owner_in_payload) == owner_of_stack_that_processes_the_status`. `WebhooksController#verify_signature` selects the `GithubApp` (and thus the HMAC secret) using `repository_owner`, taken straight from the JSON body (`params.dig('repository','owner','login')`), and only proves the payload was signed for *that* org. [1](#0-0) [2](#0-1) 

However, once past `verify_signature`, `StatusHandler#process` performs no repository/stack-scoped lookup at all — it queries `Commit.where(sha: params.sha)` across the entire database and calls `create_status_from_github!` on every match, regardless of which org the signature was verified for: [3](#0-2) 

So the equality is broken: the org that signed the payload need not be the org that owns the `Stack` whose `Commit` gets the new `Status`. Any repository (with any SHA that happens to collide with a commit tracked by another `Stack` — trivially true for forks, which retain identical SHAs for shared history) can inject a status into that other `Stack`'s commit.

Creating the `Status` triggers `Status#schedule_continuous_delivery`, which schedules delivery for the victim commit's stack: [4](#0-3) [5](#0-4) 

`ContinuousDeliveryJob#perform` then calls `stack.trigger_continuous_delivery` if `continuous_deployment?` is on and the stack isn't occupied: [6](#0-5) 

`Stack#trigger_continuous_delivery` selects `next_commit_to_deploy`, which walks undeployed commits and picks the first `deployable?` one: [7](#0-6) [8](#0-7) 

`Commit#deployable?` returns true once the commit has a `success` status and isn't `locked?`/`blocked?`: [9](#0-8) 

None of the existing guards prevent this: `verify_signature` validates the signature against the *attacker's own* org secret (which they legitimately possess for their own onboarded repository/org), not against the org that owns the commit being mutated; `StatusHandler`'s `ExplicitParameters` schema only validates types (`sha`, `state`, etc.), not repository ownership; and there is no `stack_id`/`repository_id` filter anywhere in the `Commit.where(sha: params.sha)` lookup.

### Impact Explanation
An attacker who legitimately controls one Shipit-tracked repository/org (and therefore its webhook secret) can forge a signed `status` webhook naming any SHA. If that SHA is shared with a commit tracked under a different `Stack` (any organization/tenant), the forged `success` status is written to the victim's `Commit`, and — with continuous deployment enabled and the commit otherwise unblocked — this can autonomously trigger `Stack#trigger_deploy` on the victim stack, i.e. an unauthorized deploy of a repository the attacker never authenticated against. This is a cross-tenant record write (a `Status` row created for a repository/stack that never authorized it) escalating to an unauthorized deploy, matching the Critical category ("a payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy").

### Likelihood Explanation
Requires: (1) the victim `Stack` to have `continuous_deployment` enabled and `ignore_ci?` false; (2) a `Commit` SHA collision between the attacker's own signed-payload repository and the victim's tracked repository — trivially achievable via a public fork (forks preserve upstream commit SHAs for all inherited history) or any repo sharing ancestry with the victim; (3) the victim commit not already `locked?`/`blocked?`. The attacker only needs control of one legitimately onboarded repository/org in the same Shipit instance (a low bar in any multi-tenant deployment) and no additional secrets, tokens, or privileges. The attack is repeatable against any repository sharing SHAs with the attacker's own.

### Recommendation
Scope `StatusHandler#process` (and `Commit.where(sha:...)`) by the repository identified in the verified webhook payload, e.g. resolve only commits belonging to `Stack`s whose `repository` matches `repository_owner`/`repository_full_name` from the same payload that was signature-verified, instead of a bare global SHA lookup.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (conceptual addition)
test ":status from one repo's verified webhook mutates a commit belonging to a different stack" do
  victim_stack = shipit_stacks(:shipit) # owned by "shopify"
  victim_commit = shipit_commits(:first)
  victim_commit.update!(sha: "deadbeef" * 5) # shared/forked sha

  attacker_owned_repo_payload = {
    'sha' => victim_commit.sha,
    'state' => 'success',
    'repository' => { 'owner' => { 'login' => 'attacker-org' } }
  }

  Shipit.github(organization: 'attacker-org').stubs(:verify_webhook_signature).returns(true)

  request.headers['X-Github-Event'] = 'status'
  assert_difference '-> { victim_commit.statuses.count }', 1 do
    post :create, body: attacker_owned_repo_payload.to_json, as: :json
  end

  assert_equal 'success', victim_commit.reload.state

  ContinuousDeliveryJob.expects(:perform_later).with(victim_stack) # or assert directly on stack.trigger_deploy
end
```
This demonstrates the binding failure: the webhook was signature-verified only for `attacker-org`, yet `victim_stack`'s commit (`shipit_commits(:first)`, owned by `shopify`) received the forged status and became eligible for `trigger_continuous_delivery`.

    def trigger_continuous_delivery
      return if cached_deploy_spec.blank?

      commit = next_commit_to_deploy

      if should_resume_continuous_delivery?(commit)
        continuous_delivery_resumed!
        return
      end

      if should_delay_continuous_delivery?(commit)
        continuous_delivery_delayed!
        return
      end

      begin
        trigger_deploy(commit, Shipit.user, env: cached_deploy_spec.default_deploy_env)
      rescue Task::ConcurrentTaskRunning
      end
    end

    def schedule_merges
      ProcessMergeRequestsJob.perform_later(self)
    end

    def next_commit_to_deploy
      commits_to_deploy = commits.order(id: :asc).newer_than(last_deployed_commit).reachable.preload(:statuses)
      if maximum_commits_per_deploy
        commits_with_max_applied = commits_to_deploy.limit(maximum_commits_per_deploy)
        deployable_commits(commits_with_max_applied) || deployable_commits(commits_to_deploy)
      else
        deployable_commits(commits_to_deploy)
      end
    end
