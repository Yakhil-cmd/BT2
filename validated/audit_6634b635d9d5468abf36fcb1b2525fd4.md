### Title
Webhook signature verification is bound to `repository.owner.login`, while all event handlers dispatch on `repository.full_name` — allows cross-organization webhook forgery ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret to validate the HMAC signature against using the attacker-controlled `repository.owner.login` (or `organization.login`) field of the JSON body itself, before the signature has actually been checked. Every event handler, however, resolves the target `Stack`/`Repository` to act on using a *different* field of the same body: `repository.full_name`. Because `verify_webhook_signature` returns `true` unconditionally when the selected organization has no `webhook_secret` configured (a state explicitly documented as "optional"), an attacker can pick an organization with no secret to satisfy signature verification while pointing `repository.full_name` at a completely different, unrelated organization's repository/stack.

Once past `verify_signature`, `WebhooksController#create` dispatches to handlers with the *entire* raw payload: [4](#0-3) 

Every handler (`PushHandler`, `StatusHandler`, `CheckSuiteHandler`, etc.) resolves which `Repository`/`Stack` to act on using `repository.full_name` — a field never consulted during signature verification: [5](#0-4) [6](#0-5) 

The binding that breaks: the organization that *authenticated* the request (`repository.owner.login`, used only to pick which secret to validate against) is never checked for equality against the organization embedded in the repository that is actually *written to* (`repository.full_name`, used to look up the `Stack`). Both fields live in the same untrusted JSON body and are only trustworthy as a pair if the signature genuinely binds the whole payload to a secret the attacker doesn't know. When the chosen org has no secret, that binding disappears completely, but the code still processes the (now-fabricated) `repository.full_name` as if it were authenticated.

This is a direct structural analog of the reported bug class: a payload field (`repository.full_name`) is acted upon by the business logic (stack lookup / mutation) while the field actually covered by the verification path (`repository.owner.login`) is a different one — exactly the "organization that authenticated versus the repository that is written" binding called out in scope.

### Impact Explanation
Any organization onboarded onto the shared Shipit instance without a configured `webhook_secret` (explicitly supported/documented as optional) becomes a skeleton key: an unauthenticated, unprivileged attacker who knows that org's login can send a completely unsigned/arbitrarily-signed POST to `/webhooks` with `repository.owner.login` set to that org (to pass `verify_signature`) and `repository.full_name` set to any other tracked repository (belonging to a different, properly-secured organization) in the deployment. This lets the attacker:
- Force `PushHandler` to enqueue `GithubSyncJob` for a victim stack with an attacker-chosen `expected_head_sha`.
- Forge `status` events (`StatusHandler`) creating `Status` records with attacker-chosen `state`/`context`/`sha` against a victim stack's commits — which, combined with `continuous_deployment`, can trigger an unauthorized deploy.
- Trigger `check_suite` refresh (`CheckSuiteHandler`) against arbitrary repositories.

This crosses the "an unauthorized deploy" / cross-repository-write boundary called out as in-scope Critical impact, without requiring any credential, webhook secret, or privileged account for the *target* organization.

### Likelihood Explanation
Likelihood depends on at least one organization configured on the shared Shipit instance lacking a `webhook_secret` — a state the project's own setup docs and example config present as normal/optional, not exceptional (`docs/setup.md`, `config/secrets.development.example.yml`, `config/secrets.development.shopify.yml`). Multi-organization deployments are an explicitly documented, supported configuration (`docs/setup.md` "Using Multiple Github Applications"), which is exactly the scenario where this cross-organization binding failure is exploitable.

### Recommendation
After successfully verifying the signature for the organization derived from `repository.owner.login`/`organization.login`, cross-check that the `repository.full_name` (or `organization.login` for org-scoped events) used by the downstream handler actually belongs to the same authenticated organization before dispatching to handlers. Alternatively, resolve the `Stack`/`Repository` by an owner value that is itself verified as consistent with the signing organization, and reject the request (422) on mismatch. Do not allow `verify_webhook_signature`'s unconditional `true` for orgs without a secret to implicitly authorize payloads whose acted-upon repository belongs to a different organization.

### Proof of Concept
Assume the Shipit instance is configured with two organizations, `victim-org` (has a `webhook_secret`, hosts a tracked stack `victim-org/prod-app`) and `unsecured-org` (has `webhook_secret: nil`, as permitted by `docs/setup.md`).

```
POST /webhooks
X-Github-Event: push
X-Hub-Signature: sha1=anything-or-omitted

{
  "ref": "refs/heads/main",
  "after": "deadbeefdeadbeefdeadbeefdeadbeefdeadbeef",
  "repository": {
    "owner": { "login": "unsecured-org" },
    "full_name": "victim-org/prod-app"
  }
}
```

`WebhooksController#verify_signature` resolves `repository_owner => "unsecured-org"`, calls `Shipit.github(organization: "unsecured-org").verify_webhook_signature(...)`, which returns `true` unconditionally because that org has no `webhook_secret` (`lib/shipit/github_app.rb:76-77`). The request proceeds; `PushHandler#process` resolves the target repository via `payload.dig('repository', 'full_name') == "victim-org/prod-app"` (`app/models/shipit/webhooks/handlers/handler.rb:36-38`), matching and enqueuing `GithubSyncJob` against `victim-org`'s stack — despite the request never being validated against `victim-org`'s actual webhook secret.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
