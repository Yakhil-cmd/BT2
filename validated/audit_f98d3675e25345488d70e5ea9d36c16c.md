### Title
Unhandled exception in `isChashValid()` on malformed address/chash allows a crafted unit to crash validating nodes - ([File: chash.js])

### Summary
`ValidationUtils.isValidAddress()` / `isValidChash()` validates every author address, `definition_chash`, `changed_address`, `attestor` address, asset address, etc. found in a unit by calling `chash.isChashValid()` [1](#0-0) . `isChashValid()` only wraps the base32/base64 *decode* step in try/catch; the subsequent bit-manipulation functions (`buffer2bin`, `separateIntoCleanDataAndChecksum`) are called unprotected and can `throw` on unexpected input, exactly like the length-driven, insufficiently-validated buffer walk that caused the heap-overflow read in ClamAV's ARJ parser (CVE-2020-3327: attacker supplies a crafted length/structure that the parser trusts and walks past the buffer it decoded).

### Finding Description
`isChashValid()` in [2](#0-1)  is:
```
function isChashValid(encoded){
	var encoded_len = encoded.length;
	if (encoded_len !== 32 && encoded_len !== 48)
		throw Error("wrong encoded length: "+encoded_len);
	try{
		var chash = (encoded_len === 32) ? base32.decode(encoded) : Buffer.from(encoded, 'base64');
	}
	catch(e){
		console.log(e);
		return false;
	}
	var binChash = buffer2bin(chash);
	var separated = separateIntoCleanDataAndChecksum(binChash);
	...
}
```
Only the decode call is inside `try/catch`. `separateIntoCleanDataAndChecksum()` [3](#0-2)  explicitly `throw`s `Error("bad length=...")` whenever the bit-length of the decoded buffer is not exactly 160 or 288 bits (line 53). The function assumes the third-party `thirty-two` base32 decoder always returns exactly 20 bytes for a 32-character string; if it returns any other length (e.g. because of non-canonical padding, mixed case, or characters the library tolerates/strips instead of rejecting), `buffer2bin` produces a bit string whose length is not 160, and `separateIntoCleanDataAndChecksum` throws an *uncaught* exception straight out of `isChashValid`.

This function is reached synchronously, without any surrounding try/catch, from `ValidationUtils.isValidChash()` → `isValidAddress()` / `isValidAddressAnyCase()` [1](#0-0) , which in turn is called throughout `validation.js` and `definition.js` while validating every author address, `definition_chash`, `payload.address`, `seen address`, `attested` address, asset addresses, etc. contained in an **externally-posted unit** — e.g. `isValidAddress(payload.definition_chash)` in `address_definition_change` handling [4](#0-3) , or `isValidAddress(other_address)`/`isValidAddress(changed_address)` in definition evaluation [5](#0-4) . None of these call sites wrap the `isValidAddress` call in a try/catch — the whole validation chain assumes it is a pure boolean predicate.

### Impact Explanation
If `isChashValid` throws instead of returning `false`, a synchronous, uncaught JS exception propagates out of the unit-validation pipeline that every full node runs when processing an untrusted, newly received/posted unit (`network.js` → `validation.js` → `definition.js` → `validation_utils.js` → `chash.js`). An uncaught exception raised synchronously deep in this call stack is not guaranteed to be caught by any surrounding `try/catch` (validation.js only wraps specific narrow blocks, not the whole recursive definition-evaluation graph), so it can propagate to the top of the call stack and crash the Node.js process, exactly analogous to ClamAV's scanner process crashing on a single crafted file. Because *every* full node that receives the malicious unit performs the same validation, an attacker can craft one address/chash string and broadcast/post it in a unit to crash multiple/most nodes on the network simultaneously — a network-wide denial of service ("a network unable to confirm new units"), which meets the required impact bar.

### Likelihood Explanation
Reachability requires only posting a normal unit (author address, `address_definition_change` payload, `attested`/`seen address`/`seen definition change` operand, or asset-related chash field) containing a 32- or 48-character string engineered to decode via `base32.decode`/`Buffer.from(...,'base64')` into a buffer whose length is not exactly 20/36 bytes while still passing the outer length check (`encoded.length===32`). Whether the bundled `thirty-two` base32 implementation can actually be coerced into emitting a non-canonical byte count for a 32-character input (e.g. via non-alphabet characters that it silently drops/pads rather than rejects) is the one point that needs empirical confirmation against the exact installed version of the `thirty-two` package; this could not be verified further from source alone in this pass. If confirmable, exploitation requires no privileges beyond the ability to post any unit or address-carrying message, matching the "unprivileged unit poster" reachability bar.

### Recommendation
- Wrap the entire body of `isChashValid()` (not just the decode step) in try/catch and return `false` on any exception, so malformed decoded lengths are treated as an invalid chash rather than causing an unhandled throw.
- Additionally/alternatively, explicitly assert `chash.length === encoded_len===32 ? 20 : 36` immediately after decoding, before calling `buffer2bin`/`separateIntoCleanDataAndChecksum`, and return `false` if the assertion fails.
- Audit all synchronous call sites of `isValidAddress`/`isValidChash` in `validation.js`/`definition.js` to confirm no unhandled exception from this path can escape the per-unit validation try/catch and crash the node process.

### Proof of Concept
1. Craft a unit (e.g. as an `address_definition_change` message) whose `payload.definition_chash` field is a 32-character string composed of valid base32 alphabet characters arranged so that the underlying `thirty-two` decoder returns a Buffer whose length, once converted with `buffer2bin`, is not exactly 160 bits (this requires confirming the exact edge-case behavior of the installed `thirty-two` version — e.g. strings with trailing padding-only characters or mixed case that the library tolerates atypically).
2. Post/broadcast this unit to a full node.
3. Node calls `validation.js` → `isValidAddress(payload.definition_chash)` → `chash.isValidChash` → `isChashValid`, which throws inside `separateIntoCleanDataAndChecksum` uncaught, crashing the node's validation process.
4. Repeat against multiple full nodes with the same crafted unit to cause a broader network denial of service.

function separateIntoCleanDataAndChecksum(bin){
	var len = bin.length;
	var arrOffsets;
	if (len === 160)
		arrOffsets = arrOffsets160;
	else if (len === 288)
		arrOffsets = arrOffsets288;
	else
		throw Error("bad length="+len+", bin = "+bin);
	var arrFrags = [];
	var arrChecksumBits = [];
	var start = 0;
	for (var i=0; i<arrOffsets.length; i++){
		arrFrags.push(bin.substring(start, arrOffsets[i]));
		arrChecksumBits.push(bin.substr(arrOffsets[i], 1));
		start = arrOffsets[i]+1;
	}
	// add last frag
	if (start < bin.length)
		arrFrags.push(bin.substring(start));
	var binCleanData = arrFrags.join("");
	var binChecksum = arrChecksumBits.join("");
	return {clean_data: binCleanData, checksum: binChecksum};
}
