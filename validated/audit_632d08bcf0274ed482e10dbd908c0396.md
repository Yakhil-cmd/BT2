### Title
Stack-scoped `ApiClient` token bypasses its `stack_id` binding via `Api::CCMenuController` - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Shipit::ApiClient` supports scoping a token to a single stack via `belongs_to :stack, optional: true` and `stack_id`, enforced through `Api::BaseController#stacks`/`#stack`. `Api::CCMenuController` overrides `#stack` to bypass that scoping, allowing a token issued for one stack to read data from any stack.

### Finding Description
`Shipit::ApiClient` has a `stack_id` column that is meant to bind a token to a single stack: `belongs_to :stack, optional: true` [1](#0-0) . The base API controller enforces this binding by scoping lookups through `stacks`, which restricts to `Stack.where(id: current_api_client.stack_id)` when the client is stack-scoped, and by resolving the requested stack only from within that scope: `stacks.from_param!(params[:stack_id])` [2](#0-1) .

`Api::CCMenuController`, however, defines its own `stack` method that ignores this scoping entirely and resolves the stack from the global `Stack` relation instead:
```
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end
``` [3](#0-2) 

The controller's only authorization gate is `require_permission :read, :stack`, which merely checks that the token carries the `read:stack` permission string via `ApiClient#check_permissions!` [4](#0-3) . `check_permissions!` never consults `stack_id`, and `require_permission` only guards permission scope, not stack scope [5](#0-4) .

This breaks the equality that should hold for stack-scoped tokens:
`stack the token authorises == stack the token touches`

For a client with `stack_id` set, `stacks` (the authorized set) is `Stack.where(id: current_api_client.stack_id)`, but `CCMenuController#stack` (the stack actually touched) is any `Stack.from_param!(params[:stack_id])` in the whole table — an attacker-controlled `stack_id` URL/query parameter, not constrained by the token's own `stack_id`.

### Impact Explanation
An `ApiClient` holding only `read:stack` permission, scoped to a single stack, can use the `/api/stacks/:stack_id/ccmenu.xml` endpoint (and the `?token=` query-string auth path it exposes via `authenticate_api_client` override) to read `deploys_and_rollbacks` status (name, build status, lock state, last build label/time) of **any** stack in the installation, not just the stack it was authorized for. This is an unauthenticated-scope-bypass read of task/stack state belonging to other repositories/environments than the token was issued for — an authorization boundary crossing consistent with "escalation into unauthenticated read of stack state" for stacks outside the token's granted scope.

### Likelihood Explanation
Any holder of a valid, narrowly-scoped `ApiClient` token (e.g. a CCMenu integration token meant for one stack) can trigger this by simply substituting a different `stack_id` in the request path/params — no additional secrets, GitHub access, or privilege escalation is required beyond possessing that one legitimate scoped token. `ApiClient` tokens are routinely distributed to third-party CI/monitoring tools, making this a low-effort, high-likelihood scope-confusion bug.

### Recommendation
Remove the `CCMenuController#stack` override, or reimplement it using the scoped `stacks` relation (`stacks.from_param!(params[:stack_id])`) so that stack-scoped `ApiClient` tokens cannot resolve stacks outside their authorized `stack_id`, matching the behavior enforced by `Api::BaseController`.

### Proof of Concept
1. As an admin, create/imagine an `ApiClient` record with `stack_id` set to Stack A's id and `permissions: ['read:stack']` (the model supports this scoping via `belongs_to :stack`).
2. Using that client's `authentication_token`, request `GET /api/stacks/:stack_B_id/ccmenu.xml?token=<token>` where `stack_B_id` is a different stack than the one the token is scoped to.
3. Because `Api::CCMenuController#stack` calls `Stack.from_param!(params[:stack_id])` directly instead of `stacks.from_param!(...)`, `require_permission :read, :stack` only checks the permission string (`read:stack`) and passes, and the response renders Stack B's CCMenu status (`show` action) despite the token being scoped only to Stack A. [6](#0-5)
