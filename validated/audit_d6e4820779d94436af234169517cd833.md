### Title
Uncaught exception in `merkle.deserializeMerkleProof` on malformed `in merkle` authentifier crashes/derails unit validation - (File: merkle.js)

### Summary
`merkle.deserializeMerkleProof` in [1](#0-0)  parses an attacker-controlled string by naive `split("-")`, `pop()`, and `shift()` operations with no format/length validation, analogous to the unchecked ZIP-entry parsing in zziplib's `zzip_mem_entry_new` (CVE-2017-5978) that crashed on crafted input. In ocore, the equivalent "crafted file" is the `serialized_proof` string supplied as the authentifier for an `in merkle` address-definition clause, which is directly attacker-controlled by anyone posting a unit that spends from/authenticates such an address.

### Finding Description
When an address definition contains an `in merkle` clause, `validateAuthentifiers` in `definition.js` retrieves the corresponding authentifier value and feeds it straight to the parser: [2](#0-1) 

`assocAuthentifiers[path]` is the raw authentifier string an author signs a unit with — fully attacker-controlled content, not validated for structure before being handed to `merkle.deserializeMerkleProof`. That function does: [1](#0-0) 

There is no bounds/format checking: it blindly assumes the delimited string has at least a root and index segment. This call in `definition.js` is **not** wrapped in a try/catch, unlike the equivalent call site in `formula/evaluation.js`'s `is_valid_merkle_proof`, which does wrap the deserialize+verify calls in `try { ... } catch (e) { res = false; }` ( [3](#0-2) ). By contrast, `verifyMerkleProof` itself is wrapped in try/catch ( [4](#0-3) ), but `deserializeMerkleProof` in the `definition.js` validation path is called outside any try/catch, so any exception it raises (e.g., if `serialized_proof` is not actually a string, or is empty/malformed such that `.split` on a non-string throws a TypeError) propagates up through `evaluate`/`validateAuthentifiers` uncaught.

I was unable to fully confirm, within the available tool budget, whether an earlier type-check in `definition.js`/`validation.js` guarantees `assocAuthentifiers[path]` is always a string before reaching this code (my search for such a check via `grep_search` for `authentifiers[` and `MAX_AUTHENTIFIER_LENGTH` in `definition.js` returned matches whose content I did not get to inspect before running out of iterations). This is the key open question: if authentifier values are validated as generic strings/objects without format constraints for the `in merkle` case specifically, then a crafted (non-conforming) value could reach `deserializeMerkleProof` and throw synchronously inside a validation callback chain.

### Impact Explanation
If an uncaught exception is thrown synchronously inside the `evaluate` callback chain used by `validateAuthentifiers`/`validateDefinition` while validating a unit's authentifiers, this can crash or hang the validating process depending on how the exception propagates through the async control flow, since much of this code assumes all failure modes are communicated via the `cb`/`cb2` callback rather than thrown exceptions. A crash during unit validation on a full node is a node-availability/DoS impact; more concerning, if the exception's propagation differs between two independently-implemented or differently-behaving nodes (e.g., one catches it via a wrapping try/catch somewhere else in the stack and treats the unit as invalid, another crashes or treats it differently), this could cause node disagreement on unit validity — a stated in-scope impact.

### Likelihood Explanation
Reaching this code requires only that some address (that the attacker can author for, e.g. a shared/multisig address they participate in, or their own address) has a definition containing an `in merkle` clause and that the attacker supplies the corresponding authentifier value when posting a unit. Since authentifiers are attacker-supplied signature-like values, likelihood of reaching the parser with attacker-chosen content is high; likelihood that the specific missing validation (non-string / malformed authentifier value) is actually reachable past prior checks is uncertain without confirming the referenced validation code in `definition.js`.

### Recommendation
Wrap the `merkle.deserializeMerkleProof` call site in `definition.js`'s `in merkle` handling in a try/catch (mirroring the pattern already used at the `is_valid_merkle_proof` call site in `formula/evaluation.js`), and/or harden `deserializeMerkleProof` itself to validate that `serialized_proof` is a non-empty string with the expected `index-sibling-...-root` structure before parsing, returning a controlled error instead of throwing.

### Proof of Concept
Not independently verified due to inability to confirm, within the available investigation, whether a non-string or malformed value can reach `assocAuthentifiers[path]` before `merkle.deserializeMerkleProof` is called in `definition.js`. Conceptually: author a unit whose address definition includes `["in merkle", [[oracleAddr], "feed", "element"]]`, and supply an authentifier at the corresponding signing path that is not a valid `index-siblings-root` string (e.g., an empty string, an object, or a string producing `pop()`/`shift()` on unexpected structure); if this reaches `deserializeMerkleProof` unguarded, it would throw synchronously and propagate uncaught through the validation callback chain.

function deserializeMerkleProof(serialized_proof){
	var arr = serialized_proof.split("-");
	var proof = {};
	proof.root = arr.pop();
	proof.index = arr.shift();
	proof.siblings = arr;
	return proof;
}

function verifyMerkleProof(element, proof){
	// Node-as-Leaf issue might matter in some cases
	try {
		var index = proof.index;
		var the_other_sibling = hash(element);
		for (var i = 0; i < proof.siblings.length; i++) {
			// this also works for duplicated trailing nodes
			if (index % 2 === 0)
				the_other_sibling = hash(the_other_sibling + proof.siblings[i]);
			else
				the_other_sibling = hash(proof.siblings[i] + the_other_sibling);
			index = Math.floor(index / 2);
		}
		return (the_other_sibling === proof.root);
	}
	catch (e){
		return false;
	}
