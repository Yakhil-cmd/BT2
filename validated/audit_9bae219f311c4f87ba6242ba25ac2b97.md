This inconsistency is exploitable because `signed_message.js`'s `validateSignedMessage()` sets `bNoReferences: !bNetworkAware` and, in the non-network-aware branch (no `last_ball_unit` supplied), hardcodes `last_ball_timestamp` to `0` while still allowing `timestamp`/`mci`/`age` conditions to be evaluated against that state:

### Title
Signed-message `timestamp`/`mci`/`age` definition checks bypassed via zero-timestamp when `last_ball_unit` omitted - (File: signed_message.js)

### Summary
`is_valid_signed_package()` (oscript/AA) and any code path calling `signed_message.validateSignedMessage()` allow an attestation/signed-message object to omit the optional `last_ball_unit` field, which forces `last_ball_timestamp = 0` and does not block address-definition conditions that reference on-chain state (`mci`, `age`, `timestamp`), unlike the analogous `has`/`seen`/`in merkle` ops which are explicitly disabled via `bNoReferences`.

### Finding Description
`validateSignedMessage(conn, objSignedMessage, address, mci, handleResult)` determines `bNetworkAware = ("last_ball_unit" in objSignedMessage)` [2](#0-1) . When the signed package omits `last_ball_unit` (non-network-aware), the code takes the definition and calls back with a hardcoded, attacker-independent-of-reality timestamp:
```
cb(objAuthor.definition, (mci >= constants.pemCurvesFixMci) ? mci : -1, 0);
``` [3](#0-2) 
This `last_ball_timestamp = 0` (and possibly `last_ball_mci = -1`) is stored into `objValidationState` together with `bNoReferences: !bNetworkAware` [4](#0-3) , and is then passed into `Definition.validateAuthentifiers()`.

Inside the definition evaluator, `bNoReferences` is explicitly checked for `has`, `has one`, `seen`, `has equal`, `has one equal`, and `in merkle` (`return cb("no references allowed in address definition")`) [5](#0-4) , but the `mci`/`age`/`timestamp` case has **no such guard** [6](#0-5) . The actual evaluation logic in `validateAuthentifiers` compares the definition's declared relation/threshold directly against `objValidationState.last_ball_timestamp`/`last_ball_mci` [7](#0-6) , with no special-case rejection when references are disallowed.

Consequently, if an address definition embeds a time-bound condition such as `["timestamp", ["<", DEADLINE]]` or `["timestamp", [">", NOT_BEFORE]]` (used, e.g., to time-lock or expire an off-chain-issued signed attestation/oracle package), an attacker who controls the signed-message JSON (e.g. supplied as `trigger.data` to an AA calling `is_valid_signed_package(...)` in `formula/evaluation.js`) can simply omit `last_ball_unit`. This forces `last_ball_timestamp` to `0`, which trivially satisfies any `<` upper-bound check (`0 < DEADLINE` is always true) regardless of the real current time, silently bypassing the intended expiry/time-window enforcement. The `is_valid_signed_package` implementation confirms `last_ball_unit` is fully optional and, when absent, calls `validateSignedMessage` without any additional restriction on which ops are permitted in the embedded definition [8](#0-7) .

### Impact Explanation
An AA (or any oscript definition validated via `is_valid_signed_package`) that relies on `timestamp`/`mci`/`age` conditions inside an attacker-supplied signed package's definition to enforce freshness, expiry, or time-locked authorization can be tricked into treating an expired/premature/replayed attestation as valid. Since `is_valid_signed_package` is invoked from AA formulas on trigger data supplied by any unprivileged unit poster, this can lead to AA fund loss or unauthorized release of funds gated by a time-window check that the AA author believed was enforced by the definition engine (consistent with "AA fund loss or freezing" impact class).

### Likelihood Explanation
Exploitation requires no special privileges: any unit poster/trigger sender can construct a `signed_package` object without a `last_ball_unit` field and submit it as AA trigger data to any AA that calls `is_valid_signed_package` with a definition using `timestamp`/`mci`/`age`. The attacker fully controls the (address, definition) pair used inside the package as long as `getChash160(definition) === address` holds, which is trivial to satisfy by generating a fresh definition/address together, and the `<` relation makes the bypass to zero timestamp value trivially satisfiable.

### Recommendation
In `definition.js`, add the same `if (objValidationState.bNoReferences) return cb("no references allowed in address definition")` guard to the `case 'mci': case 'age': case 'timestamp':` block as is already applied to `has`/`seen`/`in merkle`, so that non-network-aware signed messages cannot use on-chain-state-dependent conditions at all.

### Proof of Concept
1. Address owner defines address `A` with definition `["and", [["sig", {"pubkey": PK}], ["timestamp", ["<", 1700000000]]]]`, intending signatures under this address to be valid only before the deadline `1700000000`.
2. An AA accepts external attestations via `is_valid_signed_package(trigger.data.package, trigger.data.address)`.
3. After the deadline has passed, attacker crafts a `signed_package` object `{signed_message: ..., authors: [{address: A, definition: [...], authentifiers: {...}}]}` **without** a `last_ball_unit` field, signed with the still-known private key for `A`.
4. `validateSignedMessage` takes the `bNetworkAware=false` path, setting `last_ball_timestamp = 0`; the `timestamp < 1700000000` check in the definition evaluates `0 < 1700000000 = true`, and `is_valid_signed_package` returns `true` even though real time is long past the deadline, letting the attacker trigger AA logic intended to be time-restricted.
