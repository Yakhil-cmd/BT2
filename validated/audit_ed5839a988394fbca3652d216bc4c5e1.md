### Title
Single unattestable/blocked payee address can permanently freeze funds and block payouts to all other AA beneficiaries in a batched payment — (File: `aa_composer.js`, `validation.js`)

### Summary
Autonomous Agents (AAs) build response units where a single `payment` message may pay out to many different addresses in one atomic unit. If the asset used is `spender_attested` (or has a `transfer_condition`), the entire unit — and therefore *every* payee in that message, not just the offending one — fails validation and the whole trigger is bounced if even one output address does not satisfy the condition. This mirrors the Astaria `LienToken` bug: a single adversarial "payee" who deliberately keeps their receiving address unable to satisfy a payment precondition can force the whole settlement to fail, freezing funds owed to honest counterparties and blocking the AA's distribution logic indefinitely.

### Finding Description
When an AA formula produces `payment` messages, `aa_composer.js` assembles the outputs and asks `storage.loadAssetWithListOfAttestedAuthors` to fetch attestor info for the asset, but it never filters output addresses for eligibility before composing the unit: [1](#0-0) 

The composed unit is then run through full protocol validation via `validateAndSaveUnit`: [2](#0-1) 

If validation fails (`ifUnitError`), the error propagates back up and the AA bounces the *entire* trigger: [3](#0-2) 

The actual failure condition is enforced in `validatePaymentInputsAndOutputs`: for a `spender_attested` asset, **all** output addresses in the payment message must be attested, and if even one isn't, the whole payment message (and thus the whole unit) is rejected with `"some output addresses are not attested"`. The same all-or-nothing effect applies to a `transfer_condition` that one address can fail to satisfy: [4](#0-3) 

Because AA execution is atomic — either the whole response unit (with all its payment outputs and state changes) is accepted, or the whole trigger is bounced — a single malicious/blocked payee embedded among many legitimate payees in the same payment message can force perpetual bounce. `bounce()` only refunds the *original trigger sender*, not the other intended beneficiaries, and restores/reverts all pending state changes for that call, including in chains of secondary AAs: [5](#0-4) [6](#0-5) 

This is the direct analog of the Astaria bug: there, one adversarial "payee" (a lien holder who transferred the bearer token to a blocklisted address) caused every attempted repayment/auction-settlement push-payment to that address to revert, which (because settlement logic bundled everyone in the same transaction) blocked payments to/for all other honest lenders and let the liquidator seize collateral for free. In ocore, the equivalent is a single unattestable/condition-failing address embedded in a multi-recipient AA payout, which blocks the entire batched settlement/distribution for all other participants and locks the AA's balance.

### Impact Explanation
- Funds held by the AA meant for honest counterparties become permanently stuck: every attempt to execute the payout trigger bounces because of the one bad address, so no honest payee is ever paid (AA fund freezing).
- Any protocol built as an AA-based pooled distribution, auction settlement, dividend/lending payout, or liquidation-clearing mechanism using a `spender_attested` or `transfer_condition`-gated asset is vulnerable: a single participant who registers themselves (or is registered via user-supplied trigger data) as a payee with an address that fails the attestation/transfer condition can indefinitely block distribution to everyone sharing that batched payment.
- Because AA code is immutable once deployed, there is no in-protocol remedy once such a state is reached other than the AA never completing that payout path again.
- This matches the accepted impact categories: AA fund loss/freezing and a fundamentally correct-but-unusable protocol state (analogous to a stuck liquidation auction).

### Likelihood Explanation
Any AA developer that batches multiple beneficiaries into one `payment` message when working with a `spender_attested` or `transfer_condition`-restricted asset is exposed. An attacker only needs to:
1. Become one of the tracked payees in the AA's state (a normal, permission-less interaction most AAs allow), and
2. Use/keep an address that is not attested by the asset's attestor(s), or crafts a `transfer_condition` failure (e.g., relying on a condition that references `this/other address`, `seen address`, or similar attacker-influenceable state).

No special privilege, hub, or peer collusion is required — this is reachable purely by an ordinary AA trigger sender interacting with a public AA, matching the "unprivileged... AA trigger sender" reachability requirement.

### Recommendation
- Avoid bundling payouts to multiple, mutually-independent beneficiaries in a single atomic `payment` message/unit when the asset enforces `spender_attested` or a `transfer_condition`; instead, have each beneficiary pull their own payout via a separate trigger/response so one bad address cannot block others.
- When state-tracking payee addresses supplied by users, validate attestation/transfer-condition eligibility for the address at registration time (using an appropriate data feed / getter) rather than deferring the failure to distribution time, so a bad registration is rejected immediately instead of poisoning the batched payout permanently.
- Consider allowing partial execution or per-recipient isolation semantics for message-level payment validation failures instead of failing the entire unit, though this would be a broader protocol-level change.

### Proof of Concept
1. Define asset `X` with `spender_attested: true`, `attestors: [AttestorAddr]`.
2. Deploy AA `Vault` that lets any address register itself with `data.action = 'register'`, storing `var['payee_' + trigger.data.address] = 1`, and exposes a `distribute` trigger that, in a single `payment` message for asset `X`, builds `outputs` from all registered `payee_*` state vars, e.g.:
```
{
  app: 'payment',
  payload: {
    asset: '<X>',
    outputs: [ {address: payee1, amount: a1}, {address: payee2, amount: a2}, ... ]
  }
}
```
(built via `outputs.push(...)` in the formula for each stored payee — supported per `aa_composer.js` lines 1312–1344 above).
3. Attacker registers themselves with an address that is not, and will never be, attested by `AttestorAddr` for asset `X`.
4. Anyone (including honest depositors) triggers `distribute`. `validatePaymentInputsAndOutputs` rejects the unit because the attacker's output address is unattested (`validation.js` lines 2630–2641), the AA's `validateAndSaveUnit` receives `ifUnitError`, and `bounce()` is invoked (`aa_composer.js` lines 1405–1411, 909–945), reverting all state changes and refunding only the trigger sender.
5. Every subsequent `distribute` attempt bounces identically as long as the attacker's payee entry remains, permanently freezing asset `X` held by `Vault` for all honest participants.
