### Title
TPS-fee snapshot (`storage.updateTpsFees`) is skipped for a stabilized MCI when it produces no AA triggers - (File: `writer.js`)

### Summary
The external report's bug class is: a state-recording function required by spec to run on every relevant event (`_snapshot()` on every transfer/mint/burn) is only conditionally invoked, so downstream readers of that state operate on stale/missing data. The same pattern exists in `writer.js`'s post-stabilization pipeline: `storage.updateTpsFees()`, which is supposed to record the TPS-fee-relevant state for every MCI that becomes stable at/after `constants.v4UpgradeMci`, is only called inside the `if (bStabilizedAATriggers && !err)` branch, i.e. only when the newly-stabilized MCI happens to also have AA triggers to execute.

### Finding Description
In `writer.js`, after `saveJoint` commits a unit, the code branches on whether the just-stabilized MCI triggered AA execution: [1](#0-0) 

The `updateTpsFees` call for `arrStabilizedMcis` is nested entirely inside `if (bStabilizedAATriggers && !err)`. If a unit stabilizes an MCI (`arrStabilizedMcis.length > 0`) but that MCI has no AA triggers (`bStabilizedAATriggers === false`), this call is skipped for that MCI.

The subsequent block that tries to "stabilize more MCIs" does not fix this gap — it calls `main_chain.advanceMcStability` again to find *further* MCIs to stabilize and only updates TPS fees for those newly found MCIs, not for the MCI that was already stabilized and skipped above: [2](#0-1) 

So the MCI whose stabilization did not produce AA triggers never gets its `updateTpsFees` call executed by any code path in this function, exactly mirroring the reported class of bug: a state update required "on every relevant event" (here: every MCI stabilization at/after v4UpgradeMci) is called only under an unrelated side condition (whether AA triggers exist), not unconditionally.

### Impact Explanation
`updateTpsFees` maintains the per-address TPS-fee balances/state (`tps_fees_balances`, `storage.systemVars`-adjacent bookkeeping) that the AA/oscript layer and unit validation rely on to compute `oversize_fee`/tps fees for subsequent units and AA responses (seen referenced via `storage.getOversizeFee` and byte-balance checks in `aa_composer.js`). If this snapshot/update is skipped for an MCI, subsequent fee computations and balance checks for that time window are performed against stale tps-fee state. Depending on how nodes later reconcile this (or fail to), this can produce disagreement between nodes on unit/AA validity (different nodes running the pipeline at different times may or may not hit the same code path), incorrect fee charges to AA responses (potential AA fund loss/freezing via wrongly computed `oversize_fee`), or a node getting stuck unable to correctly account for TPS fees going forward — all without any privileged actor being required, since MCI stabilization (and whether it produces AA triggers) is driven purely by ordinary unit posting.

### Likelihood Explanation
This is a normal, frequently-hit code path (not attacker-controlled beyond posting ordinary units) — MCI stabilization events without direct AA triggers are common on ocore's DAG. Any MCI stabilizing at or above `v4UpgradeMci` without an AA trigger unit reaching quorum is enough to hit the skip; no privileged access or malicious peer/node is needed to reach it.

### Recommendation
Move the `storage.updateTpsFees(conn, arrStabilizedMcis)` call out of the `bStabilizedAATriggers` conditional so it runs unconditionally whenever `arrStabilizedMcis.length > 0 && arrStabilizedMcis[0] >= constants.v4UpgradeMci`, regardless of whether AA triggers were produced, matching the same unconditional-update pattern recommended in the external report (perform the required state update on every relevant event, not only when an unrelated condition happens to be true).

### Proof of Concept
Not independently verified end-to-end (could not inspect the full body of `storage.updateTpsFees` or downstream fee-consumption code within the available tool budget) — I could only confirm, via `writer.js:720-770`, that the call is structurally gated behind `bStabilizedAATriggers` and that the "stabilize more MCIs" fallback loop does not retroactively cover the MCI that was skipped. A concrete PoC would require constructing two units where the first stabilizes MCI N with `bStabilizedAATriggers=false` (no AA outputs in that MCI) at `mci >= v4UpgradeMci`, then observing that `tps_fees_balances`/`storage.systemVars` are never updated for MCI N, while a later AA trigger's fee computation (`storage.getOversizeFee`) uses the stale/missing value — this should be validated with a running Devin session against the actual `storage.updateTpsFees` implementation before treating severity as confirmed.
