### Title
Webhook GitHub-App/secret selection is decoupled from the repository actually acted upon, allowing cross-organization/cross-repository webhook forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App configuration (and therefore which HMAC `webhook_secret`) to verify the inbound signature against based on a field read out of the *unverified* JSON body (`repository.owner.login` / `organization.login`). Once the signature check passes, every event handler (`PushHandler`, `PullRequest::*Handler`, etc.) resolves the target `Stack`/`Repository` using a *different* field from the same body — `repository.full_name` — which is never cross-checked against the owner/organization used to select the verification secret.

### Finding Description
`repository_owner` is computed purely from `params` (parsed from `request.raw_post`) before any cryptographic check occurs: [1](#0-0) [2](#0-1) 

This value is used only to pick *which* `GitHubApp` instance (i.e., which organization's `webhook_secret`) performs the HMAC comparison: [3](#0-2) [4](#0-3) 

Shipit explicitly supports multiple, independently-configured GitHub Apps/organizations, each with its own `webhook_secret`, exactly to keep organizations' webhook traffic isolated from each other: [5](#0-4) [6](#0-5) 

However, once the signature is confirmed valid *for whichever organization `repository_owner` names*, the event handler that actually executes state changes resolves the target repository/stack using a **separate, independent field** in the same JSON body — `repository.full_name` — with no re-validation that this repository belongs to the organization whose secret was used to authenticate the request: [7](#0-6) [8](#0-7) [9](#0-8) 

Because the HMAC is computed over the *entire raw body*, and the attacker fully controls the body they submit (including both `repository.owner.login`/`organization.login` and `repository.full_name`), anyone who legitimately possesses (or knows) the `webhook_secret` for **any one** organization configured in Shipit (e.g., their own tracked org, for which they are a repo/org admin and thus already know or can view the configured webhook secret) can construct a payload where:
- `repository.owner.login` (or `organization.login`) = their own organization (so `Shipit.github(organization:)` picks their own `GitHubApp`/secret for verification), and
- `repository.full_name` = a *different* organization/repository's full name (the actual target victim stack tracked by the same Shipit instance).

They sign this crafted body with the secret they legitimately possess and POST it to the shared `/github/webhooks` endpoint. `verify_signature` succeeds because it validates the exact bytes against the exact secret the attacker used — the mismatch between the "authenticating organization" and the "repository that gets written" is never checked anywhere in the pipeline. The dispatched handler then acts on the victim's `Stack`/`Repository`, e.g. `PushHandler#process` calls `stack.sync_github(expected_head_sha: params.after)` for stacks under the *forged* `repository.full_name`, and PR handlers can archive/unarchive review stacks, capture labels, or trigger provisioning of review stacks belonging to a repository the attacker was never granted webhook access to.

This is precisely the analog required by the rules: **an organization that authenticated versus the repository that is written** — the two are never bound together.

### Impact Explanation
This breaks repository-level trust isolation between organizations/tenants hosted on a single multi-org Shipit deployment. An attacker who controls (or has visibility of) the webhook secret for one tracked organization can forge GitHub events attributed to a completely different organization's repository, causing Shipit to perform state-changing operations (triggering GitHub syncs, archiving/unarchiving review stacks, provisioning/deprovisioning review stacks, updating cached PR state) against that victim repository's stacks without ever holding push or webhook access to it. This is a cross-repository write achieved purely by exploiting the disconnect between the field used for authentication routing and the field used for authorization/target-resolution, matching the required "cross-repository writes" impact class.

### Likelihood Explanation
Exploitability requires the attacker to know a `webhook_secret` for at least one organization configured in the multi-org `github:` block — a secret they can obtain if they administer the GitHub App installation / webhook settings for any org tracked by the same Shipit instance (a realistic scenario for shared internal Shipit deployments serving multiple teams/orgs). No compromise of GitHub, no `ApiClient` token, no `GITHUB_TOKEN`, and no direct access to the victim organization is required — only the ability to craft and POST an HTTP request with a valid HMAC for a secret the attacker legitimately possesses.

### Recommendation
After signature verification succeeds, re-derive `repository_owner` (or repository full name) from the verified payload and assert it belongs to the same organization whose `GitHubApp`/secret was used for verification (e.g., compare `payload.dig('repository','full_name').split('/').first` against the `organization` param used in `Shipit.github(organization:)`) before dispatching to any handler. Reject the request if they diverge.

### Proof of Concept
1. Deploy Shipit with two organizations configured, `OrgAttacker` and `OrgVictim`, each with distinct `webhook_secret`s (per `docs/setup.md` multi-org format), both organizations having stacks tracked by the same Shipit instance.
2. Attacker, who administers `OrgAttacker`'s GitHub App/webhook configuration, knows `OrgAttacker`'s `webhook_secret`.
3. Attacker crafts a `push` event JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>",
  "organization": {"login": "OrgAttacker"},
  "repository": {"full_name": "OrgVictim/victim-repo", "owner": {"login": "OrgAttacker"}}
}
```
4. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(OrgAttacker_webhook_secret, raw_body)>` and POSTs it to `/github/webhooks` with `X-Github-Event: push`.
5. `WebhooksController#verify_signature` calls `Shipit.github(organization: 'OrgAttacker')` (from `repository.owner.login`), validates the signature successfully against `OrgAttacker`'s secret.
6. `PushHandler#process` resolves stacks via `Repository.from_github_repo_name('OrgVictim/victim-repo')` and calls `stack.sync_github(expected_head_sha: <attacker-chosen sha>)` on `OrgVictim`'s stack — an operation the attacker was never authorized to trigger, forged entirely with credentials belonging to a different organization.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end
```
