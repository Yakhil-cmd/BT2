### Title
Webhook signature verification binds to an attacker-chosen organization while push/status handlers act on an unrelated, unvalidated repository — enabling cross-tenant unauthorized deploys/merges - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
The Party `PartyGovernance` bug is a TOCTOU where the value checked (voting power at proposal time) is not the value used at accept time, letting an attacker manipulate the unchecked field. Shipit's webhook pipeline has an analogous binding break: `WebhooksController#verify_signature` authenticates the webhook against the GitHub organization named by `repository.owner.login`, but the event handlers that mutate application state key off a *different*, unvalidated field of the same attacker-supplied JSON body (`repository.full_name`, or in the case of `StatusHandler`, no repository field at all). Nothing enforces `repository.owner.login == repository.full_name.split('/').first`.

### Finding Description
`WebhooksController#verify_signature` selects which GitHub App/webhook secret to validate against using a field taken straight from the unauthenticated JSON body: [1](#0-0) [2](#0-1) 

`Shipit.github(organization:)` resolves this to a specific per-organization config (Shipit supports one GitHub App per organization, each with its own optional `webhook_secret`): [3](#0-2) 

Signature verification itself is a plain HMAC compare over the raw body using that organization's secret: [4](#0-3) 

Note `return true unless webhook_secret` — per the docs, `webhook_secret` is *optional* per organization, so verification is a no-op for any org that hasn't configured one: [5](#0-4) 

Once the request is accepted, the actual event handlers determine which `Stack`/`Repository`/`Commit` to mutate from a **different** field of the same untrusted body — `repository.full_name` — which is never cross-checked against `repository.owner.login` used for signing: [6](#0-5) [7](#0-6) 

`StatusHandler` is even more permissive: it doesn't scope by repository at all, only by commit SHA, globally across every stack in the Shipit instance: [8](#0-7) 

The equality that must hold but does not:
`organization_that_authenticated_the_signature (repository.owner.login) == organization/repository whose Stack/Commit state is written (repository.full_name / global sha lookup)`.

### Impact Explanation
On a multi-tenant Shipit deployment (documented and tested feature — `Shipit.github_organizations`, `test/dummy/config/secrets_double_github_app.yml`), any org whose GitHub App is configured with an empty/optional `webhook_secret`, or whose secret is known to a tenant admin who legitimately controls that org's app but not others, can forge a webhook body where `repository.owner.login` names the (unprotected/known-secret) org while `repository.full_name` (push) or `sha` (status, unscoped) targets a completely different organization's stack/commit:
- A forged `push` event lets the attacker call `stack.sync_github(expected_head_sha: ...)` for a stack belonging to another org, injecting arbitrary attacker-chosen commit SHAs into that stack's history.
- A forged `status` event lets the attacker post fabricated "success" CI statuses onto any commit SHA in the database, regardless of which org/repo it belongs to, because `StatusHandler` never checks `repository` at all.

Combined, these can make a commit appear green/deployable in another organization's stack, resulting in an unauthorized deploy/merge of attacker-controlled code — matching the Critical/High impact criteria ("cross-repository writes, or an unauthorized deploy, rollback or merge").

### Likelihood Explanation
Requires only unauthenticated POST access to `/webhooks` (no Shipit session, no `ApiClient` token) plus knowledge of one org's webhook secret, which by design may be blank (`webhook_secret: # nil`, called out as "optional" in `docs/setup.md`). Any tenant that omits the secret, or whose secret is known to a non-privileged party (e.g., a former employee, a contractor who set up their org's app, or a leak scoped to one tenant), gets a write path into every other tenant's stacks tracked on the same Shipit instance. This is realistic specifically because Shipit is designed to host multiple independent GitHub organizations behind one instance.

### Recommendation
Bind repository/organization identity once, at verification time, and require every downstream handler to use that same verified value instead of re-reading it from the untrusted payload:
- In `verify_signature`, after computing `repository_owner`, store it (e.g. `request.env['shipit.verified_organization']`) and pass it explicitly into `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params, verified_organization) }`.
- In `Handler#repository_name`/`#stacks`, require the resolved `Repository`'s organization/owner to equal the verified organization; reject (422) on mismatch.
- In `StatusHandler#process`, scope `Commit.where(sha:)` by the commit's stack's repository owner matching the verified organization.
- Consider making `webhook_secret` mandatory (not optional) for any multi-organization configuration, since its absence disables authentication for that org's namespace entirely.

### Proof of Concept
1. Deploy Shipit with two organizations configured, `OrgA` (webhook secret left blank, per documented optional support) and `OrgB` (has a real stack `OrgB/private-repo` tracked with real commits).
2. Attacker crafts a `push` webhook body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "OrgA" },
    "full_name": "OrgB/private-repo"
  }
}
```
3. POST to `/webhooks` with header `X-Github-Event: push` and no valid `X-Hub-Signature` (or one trivially computed since `OrgA` has no `webhook_secret`).
4. `verify_signature` resolves `Shipit.github(organization: "OrgA")`, whose `verify_webhook_signature` returns `true` immediately because `webhook_secret` is blank — the request is accepted.
5. `PushHandler#process` resolves `stacks` via `repository.full_name = "OrgB/private-repo"`, and calls `stack.sync_github(expected_head_sha: params.after)` on `OrgB`'s real stack — a write the attacker has no legitimate access to.
6. A similarly crafted `status` webhook (any `X-Github-Event: status`, again authenticated as `OrgA`) with `sha` set to a real commit SHA belonging to `OrgB`'s stack lets the attacker call `Commit#create_status_from_github!` and inject a fabricated "success" status onto that commit, with no repository check at all in `StatusHandler`.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
