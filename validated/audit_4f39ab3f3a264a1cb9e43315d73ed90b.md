## Analog Vulnerability Found

Found a direct structural analog to the GMX liquidation slippage bug in Cumulus's XCM fee-swapping infrastructure. Both bugs share the identical root cause: a credit/asset swap through an AMM-style pool executed with **no minimum-output (slippage) protection**, which can be manipulated by an attacker who controls or can influence pool reserves within the same execution window.

### Title
`SwapFirstAssetTrader::refund_weight` swaps XCM fee surplus back to the user's asset with no slippage protection - ([File: cumulus/primitives/utility/src/lib.rs])

### Summary
`SwapFirstAssetTrader`, a `WeightTrader` used by XCM executors on chains that let users pay XCM execution fees in a non-native asset via `pallet_asset_conversion`, swaps the user's asset into the `Target` fee asset in `buy_weight` (protected, using `swap_tokens_for_exact_tokens` with an exact `fee` amount) but swaps the **unused surplus back** to the user's original asset in `refund_weight` using `SwapCredit::swap_exact_tokens_for_tokens` with `amount_out_min = None`. This mirrors exactly the audited GMX issue: a swap through an AMM pool ("pnl token to collateral token") executed with zero/no slippage protection.

`None` is passed as `amount_out_min`. Tracing into `pallet_asset_conversion`, `SwapCredit::swap_exact_tokens_for_tokens` forwards to `do_swap_exact_credit_tokens_for_tokens`, where the `amount_out_min` check is entirely skipped when it is `None`: [2](#0-1) 

The swap therefore executes at whatever price the pool currently reflects, no matter how unfavorable, exactly the missing-guard pattern described in the GMX report ("this liquidation order is created with 0 slippage param... pool can receive less amount after liquidation").

By contrast, the earlier `buy_weight` swap in the very same trader *does* pass an exact `fee` target via `swap_tokens_for_exact_tokens`, and every other public entry point of `pallet_asset_conversion` (`swap_exact_tokens_for_tokens`/`swap_tokens_for_exact_tokens` dispatchables, and their `SwapCredit`/`Swap` trait counterparts used elsewhere, e.g. in `pallet-asset-conversion-tx-payment`'s `SwapAssetAdapter`) either enforce a caller-supplied `amount_out_min`/`amount_in_max`, or use the "exact-out" variant which is inherently bounded. `refund_weight` is the sole caller in the reviewed code that opts out of this protection.

**Attack surface / reachability:** Any account can submit XCM with a `BuyExecution` (using a fee asset different from `Target`) that overpays weight, followed by instructions/`Transact` calls that move the price of the `swap_asset`/`Target` pool (e.g., by executing large swaps against the very same pool via `pallet_asset_conversion` dispatchables reachable from `Transact`, or by executing another leg of the same XCM program before `RefundSurplus`), and finally trigger the automatic/explicit refund. `buy_weight` and `refund_weight` execute within the same XCM message processing; no privileged role, governance, or malicious peer is required — only ordinary signed extrinsics/XCM instructions available to any user.

### Impact Explanation
Because the refund swap has no floor on the amount received, an attacker who moves the pool's reserves between `buy_weight` and `refund_weight` (self-sandwich within one XCM message, or opportunistically racing a pending message) can cause the refund to convert the surplus `Target` asset back to the original asset at an arbitrarily bad rate. The difference in value is captured by whoever holds the counter-side of the pool at that moment (the attacker, if they also hold/control liquidity or execute an offsetting trade), i.e., value is extracted from the fee payer's legitimate refund. This is a direct value-extraction / loss-of-funds vector rooted in a missing slippage check on a swap through a shared AMM pool — the same class of bug as the GMX report (pool/participant receives less than it should due to absent slippage protection on a triggered swap).

### Likelihood Explanation
Requires: (1) a runtime that configures `SwapFirstAssetTrader` as (part of) its `WeightTrader` for XCM fee payment with `pallet_asset_conversion` swaps, and (2) an attacker able to move the relevant pool's price within the window between `buy_weight` and `refund_weight` of the same XCM message (or race a subsequent price-moving trade before the refund executes, if refund is not strictly atomic with buy). Both AMM price manipulation and XCM message construction are unprivileged, ordinary user actions, making this readily reachable wherever the trader is wired into a live runtime; no forged proofs, no governance, no validator/collator collusion needed.

### Recommendation
Pass a caller/derived minimum-acceptable-output to the refund swap instead of `None`, e.g. quote the expected `refund_swap_asset` amount via `QuotePrice::quote_price_exact_tokens_for_tokens` (already used elsewhere in this same file for `quote_weight`) before calling `swap_exact_tokens_for_tokens`, and reject/keep-as-fee if the realized output falls below an acceptable bound (mirroring how `buy_weight` already bounds its own swap via the exact-amount variant).

### Proof of Concept
No test harness exists that reproduces a live sandwich against `pallet_asset_conversion` + `SwapFirstAssetTrader` end-to-end in this codebase; the finding is based on direct code tracing of the missing `amount_out_min` argument (`None`) through `pallet_asset_conversion::do_swap_exact_credit_tokens_for_tokens`, confirmed by inspecting the corresponding guard (`ensure!(amount_out_min.map_or(true, |a| amount_out >= a), ...)`) which is trivially satisfied when `None`. A full PoC would require constructing an XCM integration test (per `cumulus/primitives/utility/src/tests.rs` harness) that: creates a pool, calls `buy_weight`, executes an intermediate swap that shifts reserves, then calls `refund_weight`, and asserts the refunded amount is below the price-implied fair amount — this was not executed in this investigation.
