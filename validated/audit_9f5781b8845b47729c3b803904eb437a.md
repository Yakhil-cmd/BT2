### Title
`StatusHandler#process` writes commit statuses by bare SHA with no repository scoping, letting one repo's `status` webhook flip another stack's commit state - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` looks up commits solely by `Commit.where(sha: params.sha)` and calls `commit.create_status_from_github!(params)` on every match, with no filter tying the update to the repository/organization that authenticated the webhook. Because git commit SHAs are content-addressed, any two repositories that share history (e.g. an attacker forking a victim's public repo) will have `Commit` rows with identical `sha` values in different stacks, so a validly-signed `status` webhook from the attacker's own repo/org will also mutate the victim stack's commit status.

### Finding Description
The broken binding, stated as an equality that should hold but doesn't: `commit.stack.github_repo_name == payload.dig('repository', 'full_name')` for every `Commit` touched by `StatusHandler#process`. In practice `StatusHandler#process` never checks this at all: [1](#0-0) 

Contrast this with the base `Handler` class, which *does* provide a repository-scoping helper (`stacks`, built from `Repository.from_github_repo_name(repository_name)`), but `StatusHandler` never calls it: [2](#0-1) 

`WebhooksController#verify_signature` only proves that the request was signed by *some* GitHub organization's webhook secret — the one named by `repository_owner`, itself read straight out of the untrusted JSON payload before the signature is checked — it does not bind the signature to a specific repository or to the specific `Commit` rows that will be mutated: [3](#0-2) 

`Commit#create_status_from_github!` and `Status.replicate_from_github!` then write unconditionally using `stack_id` derived from whichever `Commit` row matched the bare SHA — again with no cross-check against the webhook's originating repository: [4](#0-3) [5](#0-4) 

Exploit flow: attacker forks (or otherwise obtains) a public repository that shares commit history/SHAs with a Shipit-tracked victim stack (a very common situation for open-source repos, monorepo forks, or repos mirrored under a different name/org). Attacker's own GitHub App installation (their own org) legitimately signs a `status` webhook (`context: "ci/smoke"`, `state: "success"`, `sha: <shared-sha>`) which passes `verify_signature` because it's checked against the attacker's own org secret, not the victim's. `StatusHandler#process` then finds **every** `Commit` row across the whole Shipit instance with that SHA — including the victim's — and writes a `success` status onto it, which can flip `Commit#deployable?`/`blocked?` and trigger `stack.schedule_merges`, i.e. an unauthorized ship/block decision on the victim stack.

None of the existing guards prevent this: `verify_signature` validates organization-level HMAC, not per-repository binding; `drop_unhandled_event` and the `ExplicitParameters` schema only validate payload shape/fields, not repository ownership; there is no `stacks`/`Repository.from_github_repo_name` scoping used in `StatusHandler`, unlike other handlers that use it (e.g. pull_request handlers).

### Impact Explanation
An attacker who controls a repository whose commit history intersects a victim's tracked repository (via fork or shared history) can inject `success`/`failure`/`error` CI statuses onto the victim's `Commit` records, without ever authenticating to or being a maintainer of the victim's repository. This can force a required-context ("ci/smoke") to be satisfied and unblock `deployable?`/auto-merge (`stack.schedule_merges`) or, conversely, inject a `failure`/blocking status to block deploys. This is a payload for one repository mutating another's `Commit`/`Status` state — matching the Critical "cross-tenant/cross-repository state manipulation" category. It is repeatable against any repository sharing SHAs with an attacker-controlled repo.

### Likelihood Explanation
Preconditions: the attacker needs (a) a GitHub repository/org they control with a working GitHub App/webhook installation recognized by `Shipit.github(organization: ...)`, and (b) commit-SHA overlap with the victim's tracked repository (trivially achievable by forking a public victim repo, since forks retain identical SHAs for shared commits). No Shipit session, API token, or webhook secret for the victim's org is required — only a legitimately signed webhook from the attacker's own org. This is low-cost and repeatable per request.

### Recommendation
Scope `StatusHandler#process` (and any other webhook handler that looks up `Commit`/`Stack` records by bare identifiers) to the repository that authenticated the webhook, e.g. restrict the lookup to `Commit.joins(:stack).merge(stacks)` using the `stacks`/`repository_name` helper already defined in the base `Handler`, so a status can only ever update commits belonging to stacks whose `github_repo_name` matches `payload.dig('repository', 'full_name')`.

### Proof of Concept
minitest plan (no live GitHub required):
1. Create two `Stack`/`Repository` fixtures, `victim_repo` (`owner/victim`) and `attacker_repo` (`owner-attacker/fork`), each with a `Commit` row sharing the identical `sha` value (simulating a forked shared commit).
2. Set `victim_stack.required_statuses` (or equivalent) to include `ci/smoke`, and assert `victim_commit.deployable?` is `false` before the exploit (`assert_equal victim_commit.stack.github_repo_name, "owner/victim"` vs the webhook's `repository.full_name == "owner-attacker/fork"` — the equality that should gate the write but doesn't).
3. Stub `verify_signature`/`GithubHook#verify_signature` to return true (as in `test/controllers/webhooks_controller_test.rb`), and POST to `/webhooks` with `X-Github-Event: status` and a payload `{ sha: <shared_sha>, state: "success", context: "ci/smoke", repository: { full_name: "owner-attacker/fork", owner: { login: "owner-attacker" } } }`.
4. Assert `victim_commit.reload.deployable?` is now `true` (or that `victim_commit.statuses.count` increased) even though the payload's `repository.full_name` never matched `victim_stack.github_repo_name` — proving the cross-repository write.

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```
