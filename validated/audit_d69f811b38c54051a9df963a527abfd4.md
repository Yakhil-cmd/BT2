## Analog Found: cross‑repository forged commit status via `Shipit::Webhooks::Handlers::StatusHandler`

### Title
Webhook organization-signature scope does not match write scope: forged `status` events update commits belonging to any repository/stack - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` authenticates an incoming GitHub webhook against the `webhook_secret` configured for one specific GitHub *organization*, derived from `repository_owner` in the payload [1](#0-0) . All other handlers (`PushHandler`, `CheckSuiteHandler`) scope their side effects to the `stacks` collection returned by `Handler#stacks`, which is derived from `payload.dig('repository', 'full_name')` and thus tied to the repository that was actually verified [2](#0-1) . `StatusHandler`, however, never calls `stacks`/`repository_name` at all — it looks up commits **globally by sha** across the entire installation:

```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [3](#0-2) 

### Finding Description
The binding that should hold is: `organization authenticated by HMAC signature == repository/stack whose commit is written`. `verify_signature` only proves the payload was signed by the org identified by `repository_owner` (`params.dig('repository','owner','login')`) [4](#0-3) . Nothing in `StatusHandler` re-checks that the `sha` supplied in the (attacker-controlled) JSON body actually belongs to a commit that is part of that same repository. Any commit sha tracked by *any* stack on the Shipit instance can be targeted, because `Commit.where(sha: params.sha)` is a global, unscoped lookup, and `commit.create_status_from_github!` blindly writes a new `CommitStatus` using attacker-supplied `state`, `context`, `description`, and `target_url` [5](#0-4) .

Concretely: an attacker who is able to configure a legitimate GitHub webhook on *any single repository* belonging to *any* GitHub organization for which Shipit has a configured `webhook_secret` (a value that is necessarily shared org-wide, since `Shipit.github(organization: X)` keys the secret by organization, not by repo) can compute a valid `X-Hub-Signature` for an arbitrary payload. They can then send a `status` event whose `sha` is the sha of a commit belonging to a completely different, unrelated repository/stack (even one they have no access to at all), and Shipit will create a fabricated commit status for it.

### Impact Explanation
Commit statuses directly drive deploy/merge safety logic: `Commit#deployable?`/`add_status` schedules merges when a status becomes `success`/`pending` [6](#0-5) , and `MergeRequest#all_status_checks_passed?` / `any_status_checks_failed?` rely on exactly these statuses to gate automatic merging via `StatusChecker` [7](#0-6) . By forging a `success` status for a required CI context on a commit in a repository the attacker doesn't control, the attacker can make `ProcessMergeRequestsJob` merge a pull request that never actually passed CI [8](#0-7) , i.e., an unauthorized merge — one of the explicitly listed Critical impacts.

### Likelihood Explanation
Requires only: (a) the attacker can register a webhook (thus learn/set the shared `webhook_secret`) on some repository under a GitHub org Shipit trusts — a much lower bar than repository write access to the *targeted* stack's repo — and (b) knowledge of the target commit sha, which is public information for any commit visible on GitHub (PRs, pushes, etc.). No Shipit session, `ApiClient` token, or GitHub App private key is needed; only the ability to compute a valid HMAC using a secret the attacker legitimately possesses for an unrelated repo.

### Recommendation
Make `StatusHandler` scope its commit lookup the same way `PushHandler`/`CheckSuiteHandler` do, i.e., restrict to commits belonging to the `stacks` derived from `payload.dig('repository', 'full_name')` rather than a bare `Commit.where(sha: ...)` global lookup.

### Proof of Concept
1. Attacker has webhook-admin rights on `orgX/some-unrelated-repo` and knows `webhook_secret` configured for `orgX` in Shipit.
2. Attacker computes `sha256`/`sha1` HMAC of a crafted JSON body over the shared secret:
```json
{
  "sha": "<known sha of a commit belonging to orgX/target-repo, a stack the attacker cannot write to>",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "orgX" } }
}
```
3. POST to `/webhooks` with `X-Github-Event: status` and the computed `X-Hub-Signature`. `verify_signature` succeeds because the org (`orgX`) matches [1](#0-0) .
4. `StatusHandler#process` finds the commit by sha (belonging to `orgX/target-repo`) and creates the forged success status, regardless of which repository actually signed the request [3](#0-2) .
5. If that status satisfies `merge.require` for a pending merge request on `target-repo`, `ProcessMergeRequestsJob` merges the PR automatically.
