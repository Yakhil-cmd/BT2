### Title
AA logic that depends on a remote AA's getter (`remote_aa.$getter()`) can be permanently DoSed by an author-controlled remote AA address, freezing funds already held by the calling AA - (File: `formula/evaluation.js`)

### Summary
Autonomous Agents (AAs) can call getter functions defined in another AA's `getters` formula via the `remote_func_call`/`remote_func` oscript construct, evaluated by `callGetter()` in [1](#0-0) . This is architecturally analogous to the reported bug: a "vault-like" AA that needs to compute something (e.g., an exchange rate, fee, or eligibility check) by calling into a separate, independently deployed/controlled AA address, just like the ZeroLend vault's `updateInterestRates()` calling into a pool-supplied `interestRateStrategyAddress`. If the address used for the remote call is controllable by an untrusted party (the AA's author who chose it, or a state var that an admin-style trigger can repoint), and the remote AA's getter unconditionally calls `bounce()`, every trigger that needs that getter's result will bounce forever, freezing any funds that have already accumulated in the calling AA's balance (they can never be paid out because the payout logic never gets past the failing remote call).

### Finding Description
`callGetter()` in [2](#0-1)  loads and evaluates the remote AA's `getters` formula and then evaluates the specific getter call; any failure (including explicit `bounce()`, as in `formula/evaluation.js:2669-2677`) results in `cb(err.formattedError || ...)`, which is propagated back to the caller through `remote_func_call`'s handler: [3](#0-2) 

There, any `err` from `callGetter` is converted directly into `setFatalError(err, ...)` for the **calling** AA, with no mechanism to catch or recover from the failure — oscript has no `try`/`catch` construct (confirmed absent from the grammar/evaluator). A fatal error inside `handleTrigger()` leads straight to `bounce()`, as demonstrated by the existing test `'calling a remote function that fails'`: [4](#0-3) 

Because AA definitions are immutable once posted, and remote AA addresses used in `remote_func_call` are typically either hardcoded at AA-authoring time or stored in a state var that some other trigger writes, whichever address ends up being called is fully at the mercy of whoever controls that address/AA (the "pool"/strategy side in H-6's terminology). If that controlling party deploys or points to a remote AA whose getter always `bounce()`s (e.g. `getters: "{ $f = ($x) => bounce('dos'); }"`), then any AA relying on this getter to gate or compute a required value for a withdrawal/payout message will bounce on every subsequent trigger. Since AAs cannot "roll back" a bad remote address by themselves (immutability), and the calling AA's balance already holds funds contributed by other, unrelated users (analogous to "vault depositors"), those funds become permanently unreachable through that code path — exactly the "always-revert dependency locks unrelated depositors' funds" pattern described in H-6.

### Impact Explanation
Funds held in the balance of an AA that structurally depends on a remote getter call for its payout/withdrawal logic can become permanently locked if the remote AA (controlled by a different, potentially adversarial party) is made to always bounce. This is a fund-freezing/AA fund-loss scenario reachable purely by an AA author picking (or a privileged trigger repointing) an address for `remote_func_call`, with no way for the affected AA or its users to recover funds through that path, matching the accepted High-severity classification of the original report (any party-vs-party fund freezing counts, per Sherlock's "two sets of actors" rule referenced in the discussion).

### Likelihood Explanation
The remote-getter-call feature (`remote_func_call`/`$aa.$getter()`) is a documented, commonly-used oscript feature for composing AAs (e.g. library/pricing/oracle-style AAs), so any protocol AA built with a dependency on an externally-controlled remote AA getter for critical logic is exposed. The only precondition is that the remote AA's controller is untrusted relative to the depositors of the calling AA — a realistic scenario for permissionless AA ecosystems (analogous to permissionless pool deployment in the original report).

### Recommendation
- Design vault/aggregator-style AAs so that failure of a remote getter call degrades gracefully (e.g., falling back to a cached/default value or a separate escape-hatch payout path) instead of making the entire trigger — including payout of unrelated already-deposited funds — depend on the remote call succeeding.
- Where possible, avoid letting an untrusted/external party fully control the remote AA address used in a `remote_func_call`; if configurable, gate updates to it via a value that cannot be flipped back and forth freely, or allow the AA's *other* stakeholders (e.g., existing depositors) a fallback withdrawal mechanism independent of that remote call.
- Document this risk clearly for AA developers so that "trusted" cross-AA composition (calling into another author's AA as a dependency) is not treated as risk-free by default.

### Proof of Concept
Based on the existing test pattern in `test/aa_composer.test.js:1625-1647`, define:
```
remote_aa (malicious/adversarial, controlled by party B):
  getters: { $f = ($x) => bounce("dos"); }

vault_aa (holds deposits from party A's users, controlled/authored referencing remote_aa):
  init: { $ret = <remote_aa_address>.$f(trigger.data.x); }
  messages: [ { app: 'payment', payload: { asset: 'base', outputs: [...pay out to withdrawer...] } } ]
```
Every trigger sent to `vault_aa` that reaches the `$f()` call bounces (as shown by `arrResponses[0].bounced === true` in the existing test), so any bytes already sitting in `vault_aa`'s balance from prior deposits can never be paid out through that trigger path, mirroring the vault-depositor fund-lock described in H-6.
