### Title
Cross-repository Status forgery flips victim `Stack#ignore_ci` via unscoped `Commit.where(sha:)` lookup - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits by SHA alone with no repository scoping, unlike other handlers (e.g. `PushHandler`) that filter through `stacks` (which is derived from `Repository.from_github_repo_name(repository_name)`). Because git commit SHAs are content-addressed and identical across forks/mirrors of the same history, an attacker who owns any repository sharing commit history with a victim's repository can send a validly-signed `status` webhook for their own repo and have Shipit apply the status — and the `enable_ci!` side effect — to the victim's unrelated `Stack`.

### Finding Description
The claimed binding, stated as an equality, is:

`Stack(enable_ci! invoked) == Stack.find_by(repository: payload['repository']['full_name'])`

Tracing the code shows this does **not** hold for the `status` event:

- `app/models/shipit/webhooks/handlers/handler.rb:32-38` defines the `stacks` helper that other handlers use to scope any DB lookup to `Repository.from_github_repo_name(repository_name)` (the repository named in the verified payload). `PushHandler#process` (`app/models/shipit/webhooks/handlers/push_handler.rb:12-17`) correctly uses `stacks.not_archived.where(branch:)`.
- `StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`) instead does:
  ```ruby
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
  ```
  This queries `Commit` globally by `sha`, across **all** stacks in the installation, completely bypassing the `stacks`/`repository_name` scoping helper that exists specifically to bind webhook payloads to the repository that was cryptographically verified.
- `Commit#create_status_from_github!` → `statuses.replicate_from_github!(stack_id, github_status)` (`app/models/shipit/commit.rb:165-169`, `app/models/shipit/status.rb:23-33`) creates the `Status` using the **found commit's own** `stack_id`, not any stack derived from the payload's `repository` field.
- `Status` has `after_create :enable_ci_on_stack` → `commit.stack.enable_ci!` (`app/models/shipit/status.rb:18,38-40`), which runs unconditionally on whatever stack owns the matched commit.

`WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-49`) only checks that the payload signature is valid for `repository_owner` — it authenticates *that the sender controls the named repository*, but does nothing to constrain which `Commit`/`Stack` records the handler is allowed to touch. `drop_unhandled_event` and the `ExplicitParameters` schema (`requires :sha`, `requires :state`) likewise do not enforce repository/stack binding.

Because git SHA1s are computed purely from commit content (tree, parent, author/committer, message, timestamps), an attacker who forks a victim's public/shared repository (or otherwise shares commit history with it, e.g. via a mirrored/forked Shipit-tracked repo) will have `Commit` rows with **identical SHAs** in both the attacker's stack and the victim's stack. Sending a signed `status` webhook from the attacker-owned repository referencing one of those shared SHAs causes `StatusHandler` to match the `Commit` row belonging to the victim's stack too, and mutate it.

**Attacker's exact request:** a `status` webhook (`X-Github-Event: status`) signed with the attacker's own repository's/app's valid webhook secret (which the attacker legitimately has since it's their own repo), with `sha` set to a commit SHA shared with the victim's tracked repository, `state` set to any value, `repository.full_name` set to the attacker's own repo.

**Exploit flow:**
1. Attacker forks/owns a repo whose history overlaps with a victim's Shipit-tracked repo (shared commit SHAs).
2. Attacker triggers (or self-sends) a `status` webhook on their own repo for that shared SHA — a fully legitimate, correctly signed webhook for their own repository.
3. `StatusHandler#process` matches **all** `Commit` rows with that SHA, including the victim stack's row.
4. A new `Status` is inserted against the victim's `Commit`/`Stack`.
5. `after_create :enable_ci_on_stack` fires, calling `victim_stack.enable_ci!`, flipping `ignore_ci` to `false` on the victim's stack even though the webhook never referenced the victim's repository.

### Impact Explanation
This is a payload for one repository mutating another repository's `Stack` configuration — matching the Critical category "a payload for one repository mutating another's stack, commit, task or team." Concretely, an attacker can flip `ignore_ci` on a victim stack from `true` to `false` (removing an operator's explicit "bypass CI" configuration) purely as a side effect of a webhook the attacker legitimately sent for their own repository. It also spuriously creates `Status` rows and can trigger `schedule_continuous_delivery`/hook emission (`Status#schedule_continuous_delivery`, `after_commit :broadcast_update`) on the victim's commit, potentially influencing merge/deploy automation (`ProcessMergeRequestsJob`) for a stack the attacker does not own or control. This is repeatable against any victim repository whose commit history intersects (via fork, mirror, or cherry-pick) with a repository the attacker controls.

### Likelihood Explanation
Preconditions: the victim stack must currently have `ignore_ci: true`, and the victim's tracked repository must share at least one commit SHA with a repository the attacker owns or controls webhooks for (trivially true for public forks, which is a extremely common Shipit deployment pattern — many organizations track both `upstream` and fork repos, or a repo and its mirror). The attacker needs no Shipit credentials, no GitHub team membership, and no access to the victim's repository or secrets — only the ability to own/administer a repository that shares history with the target and to trigger a `status` webhook on it (self-hostable or via any CI integration on their own fork). This is low-cost and repeatable at will.

### Recommendation
Scope `StatusHandler#process` to the repository named in the verified webhook payload, mirroring `PushHandler`/other handlers, e.g.:
```ruby
def process
  stacks.find_each do |stack|
    stack.commits.find_by(sha: params.sha)&.create_status_from_github!(params)
  end
end
```
so only commits belonging to stacks whose `Repository` matches `payload['repository']['full_name']` can be mutated by a given webhook.

### Proof of Concept
Minitest under `test/models/shipit/webhooks/handlers/status_handler_test.rb` (conceptual, no live GitHub needed):
```ruby
test "status webhook only affects commits belonging to the payload's repository" do
  victim_stack = shipit_stacks(:shipit)
  victim_stack.update!(ignore_ci: true)
  attacker_stack = shipit_stacks(:cyclimse) # different repository

  shared_sha = 'deadbeef' * 5
  victim_commit = victim_stack.commits.create!(sha: shared_sha, author: shipit_users(:walrus), committer: shipit_users(:walrus), authored_at: Time.now, committed_at: Time.now)
  attacker_commit = attacker_stack.commits.create!(sha: shared_sha, author: shipit_users(:walrus), committer: shipit_users(:walrus), authored_at: Time.now, committed_at: Time.now)

  payload = {
    'sha' => shared_sha,
    'state' => 'success',
    'context' => 'ci/attacker',
    'repository' => { 'full_name' => attacker_stack.repository.full_name },
  }

  Shipit::Webhooks::Handlers::StatusHandler.call(payload)

  victim_stack.reload
  refute victim_stack.ignore_ci, "victim stack's ignore_ci flipped from a webhook naming a different repository"
end
```
Currently this assertion fails: `enable_ci_on_stack` fires for both `victim_commit` and `attacker_commit` because `StatusHandler` matches on SHA alone, so `victim_stack.ignore_ci` becomes `false` even though the payload's `repository.full_name` never matched `victim_stack.repository`.
