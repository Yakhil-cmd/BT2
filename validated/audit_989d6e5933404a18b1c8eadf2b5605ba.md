### Title
Null value in `trigger.data` crashes full nodes during AA response composition via unchecked `typeof value === 'object'` dereference - (File: `aa_composer.js`)

### Summary
The `replace()` function that substitutes formulas inside an Autonomous Agent (AA) response template treats any value for which `typeof value === 'object'` as a genuine object and immediately dereferences `value.if` / `value.init` on it. In JavaScript `typeof null === 'object'`, so if a `null` value (a perfectly legal JSON value) ends up as a message-template value at this point, the code throws an uncaught `TypeError`. Because `network.js` installs a global `uncaughtException` handler that deliberately re-throws to crash the process, this single unhandled type turns into a full node crash — the exact analog of the TensorFlow advisory, where a type that lacked kernel/type support led to a `nullptr` dereference and a segfault/DoS.

### Finding Description
`trigger.data` / `params` are wrapped into a `wrappedObject` **without any recursive type sanitization**: [1](#0-0) 

so nested `null` values present in the attacker-controlled JSON `data` message payload of the triggering unit survive unchanged inside the wrapped object.

When an AA response template returns this wrapped object as a formula result (a common, documented pattern — see `test/samples/sending_prepared_objects_through_trigger_data.oscript`, which forwards `trigger.data.*` sub-objects directly into `payload`), the top-level evaluator unwraps it back into a plain JS object, preserving any nested `null`: [2](#0-1) 

`aa_composer.js`'s `replace()` then assigns this raw (possibly `null`-containing) object into the message tree: [3](#0-2) 

and later recurses into that object's own keys to keep substituting formulas: [4](#0-3) 

For the child key whose value is exactly `null`, the recursive `replace(obj, name, ...)` call hits the object-with-`if`/`init` check **before** any object-emptiness/array check: [5](#0-4) 

`typeof null === 'object'` evaluates to `true`, so the engine executes `typeof value.if`, which throws `TypeError: Cannot read properties of null (reading 'if')`. This exception is raised synchronously inside a deeply nested `async.eachSeries` callback and is never caught by any `try/catch` in the call chain (`handleTrigger` → `evaluateAA` → `replace` → ... ). It propagates to Node's event loop and is caught only by the global handler: [6](#0-5) 

which explicitly re-throws to crash the process ("crash the process to avoid ending up in an inconsistent state"). Notably, other type-dispatch helpers elsewhere in the codebase (`string_utils.js`, `object_length.js`) explicitly special-case and reject `null` before reaching a `switch(typeof ...)`, showing the project is aware `null` needs distinct handling — but this specific dispatcher in `aa_composer.js` forgot to guard against it, exactly mirroring the missing-type-support root cause in the TensorFlow advisory.

### Impact Explanation
AA execution is deterministic and mandatory for consensus — every full node that processes the unit triggering this AA must independently execute the identical `handleTrigger`/`replace` code path to agree on the AA's response unit and state changes. Since the crash is triggered by data embedded in the unit itself (not by network timing or peer behavior), **all full nodes** that attempt to validate/process this unit will hit the identical uncaught exception and crash simultaneously. This meets the required bar of "a network unable to confirm new units": a single crafted unit can be used to repeatedly bring down full nodes attempting to catch up or validate main-chain progress through the offending AA trigger, until node operators patch the flaw.

### Likelihood Explanation
Reachable from a single, unprivileged, attacker-composed unit: any address can send a payment + `data` message to an AA whose response template forwards `trigger.data` (or a sub-object of it) into a message payload — a pattern explicitly present in the codebase's own test fixtures (`test/samples/sending_prepared_objects_through_trigger_data.oscript`). The attacker only needs to include a `null` field inside the forwarded JSON sub-object of the `data` message. No special privileges, AA author cooperation beyond using this common "forward trigger data" idiom, or race conditions are required.

### Recommendation
In `aa_composer.js`'s `replace()` function, explicitly exclude `null` before treating a value as a candidate for the `if`/`init` object check, e.g. change the condition to `typeof value === 'object' && value !== null && (typeof value.if === 'string' || typeof value.init === 'string')`. Additionally, sanitize/reject `null` recursively when wrapping `trigger.data`/`params`/state-var objects into `wrappedObject` (mirroring the explicit `null` rejection already implemented in `string_utils.js`/`object_length.js`), so that `null` can never surface as a message-template value during AA response composition.

### Proof of Concept
1. Deploy an AA whose definition includes a message such as:
```
{
  app: 'data',
  payload: `{trigger.data.sub}`
}
```
(this pattern is already used in `test/samples/sending_prepared_objects_through_trigger_data.oscript`).
2. Send a unit that triggers this AA with a `data` message payload:
```json
{ "sub": { "a": null } }
```
3. When the network processes this unit, every full node executing the AA's `handleTrigger`/`replace` reaches the nested key `a` with `value === null`, hits the `typeof value === 'object' && (typeof value.if === 'string' || typeof value.init === 'string')` check in `aa_composer.js`, dereferences `value.if` on `null`, throws an uncaught `TypeError`, and crashes via the `process.on('uncaughtException', ...)` handler in `network.js`.
