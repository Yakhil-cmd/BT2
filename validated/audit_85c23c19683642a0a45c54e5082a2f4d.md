### Title
Cross-repository commit status contamination via unscoped SHA lookup in `StatusHandler#process` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` resolves the target `Commit` by `sha` alone, with no scoping to the repository/organization that the verified webhook signature belongs to. Because `commits` are unique per `(sha, stack_id)` pair rather than globally per `sha`, a validly-signed status webhook from one organization's repository can flip the CI status of a `Commit` row belonging to a completely different stack/organization whenever that stack happens to hold a commit with the same SHA (the common case being a fork sharing git history with the victim's repo). This lets an attacker who controls an org onboarded into Shipit alter `deployable?`/`active?` computations on a victim stack they do not own, corrupting `Stack#next_expected_commit_to_deploy` and what `trigger_continuous_delivery` picks up next.

### Finding Description
The broken binding: the code assumes `repository_owner_of(webhook) == stack.repository.owner_of(commit)`, i.e. that a signed status webhook for organization `X` can only affect commits that belong to a stack owned by `X`. This is false.

Path:
- `WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-49`) only verifies that the payload's `repository.owner.login` maps to a *known, configured* Shipit GitHub App/org and that the HMAC signature matches that org's `webhook_secret`. It never associates the request with a specific `Stack` or `Commit`.
- `StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`) then does:
```ruby
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
``` [1](#0-0) 
This query is global across the entire `commits` table — it is not scoped by `stack_id`, `repository_owner`, or anything tied to the webhook that was just verified.
- The schema confirms `Commit` rows are unique on `(sha, stack_id)`, not on `sha` alone:
```ruby
t.index ["sha", "stack_id"], name: "index_commits_on_sha_and_stack_id", unique: true
``` [2](#0-1) 
So it is entirely legitimate for two different `Stack`s (different repositories, potentially different organizations/orgs configured in `Shipit.github`) to each have a `Commit` row with the identical `sha` — this happens naturally whenever one repo is a fork of the other and shares unmodified ancestor commits (git commit SHA is a pure hash of tree+parents+author+message+timestamp, which forking preserves exactly).
- `Commit#create_status_from_github!` → `#add_status` (`app/models/shipit/commit.rb:366-386`) creates a `Status`, recomputes `commit.status`, and fires `deployable_status`/`commit_status` hooks and `stack.schedule_merges`, all scoped to whichever stack that particular `Commit` row belongs to — which may be the victim's stack, not the attacker's.
- Once the commit's status flips to `success`, `Commit#deployable?` (transitively via `Status`) changes, altering `Stack#next_expected_commit_to_deploy` (`app/models/shipit/stack.rb:332-342`) and `UndeployedCommit#expected_to_be_deployed?` (`app/models/shipit/undeployed_commit.rb:47-53`), both of which key off `commit.active?` / `commit.deployable?` without any check that the update that produced those values came from the same organization/repository that owns the stack.
- When the victim's currently-active `Task` completes, `Stack#trigger_continuous_delivery` (`app/models/shipit/stack.rb:210-229`) calls `next_commit_to_deploy`, which is influenced by the exact same `deployable?`/status state that the attacker's cross-repo webhook just mutated.

Why existing guards fail: `verify_signature` authenticates *which organization sent the webhook*, but never authenticates *which stack's commit the webhook is allowed to mutate*. `drop_unhandled_event` and the `ExplicitParameters` schema on `StatusHandler` only validate shape (`sha`, `state`, etc.), not ownership. There is no `require_permission!`, `stacks` scope, or repository-ownership check anywhere between the verified webhook and the `Commit.where(sha:)` lookup.

Attacker's exact request: the attacker needs an organization/repository that is itself a legitimately Shipit-tracked stack (so that `Shipit.github(organization: attacker_org)` resolves and the attacker's real GitHub-generated, correctly-signed `status` webhook passes `verify_signature`). They fork the victim's public repository (ordinary GitHub action, preserving identical SHAs for shared history) and get that fork onboarded as its own Shipit stack. GitHub itself will emit a genuinely signed `status` webhook to `POST /webhooks` for commits on the fork, including ancestor commits shared with the victim's repo. Because `StatusHandler#process` is unscoped, that status update also lands on the victim stack's `Commit` row with the same sha.

### Impact Explanation
A `status` payload correctly signed for organization/repository A mutates a `Commit`/`Status` record belonging to stack/repository B, which the attacker does not own or control. This can flip `deployable?`/`state` for a commit in the victim's stack, changing `Stack#next_expected_commit_to_deploy` and therefore which commit `trigger_continuous_delivery` deploys next once the active task completes — an unauthorized/attacker-influenced deployment decision on a stack the attacker has no legitimate access to. This matches the "payload for one repository mutating another's stack/commit" Critical category. The blast radius spans any pair of stacks whose commit histories share SHAs (forks, mirrors, monorepo splits), and is repeatable for every status the attacker's own repository (or its CI) emits.

### Likelihood Explanation
Preconditions are real but non-trivial: the attacker's own organization must already be a Shipit-tracked/configured GitHub App organization (this is an onboarding precondition, not a secret-dependent one — anyone who can get a repo onboarded into the same Shipit instance, e.g. in multi-tenant/open deployments, or any org already permitted by the operator, qualifies). The victim's stack must contain a commit whose SHA is shared with the attacker's repo — trivially true for forks of the same upstream history, common for open-source or internally-forked repos tracked by the same Shipit instance. No secrets, sessions, or elevated GitHub permissions are required beyond the attacker's legitimate control of their own onboarded repository — GitHub itself will generate and correctly sign the webhook.

### Recommendation
Scope the `StatusHandler` (and any other sha-based lookup used to mutate commit state from a webhook) to the repository that authenticated the request, not just the sha:
- Pass the verified `repository_owner`/`repository.full_name` from the webhook payload into `StatusHandler#process` and restrict the `Commit` lookup to stacks whose `Repository` matches that owner/name, e.g. `Commit.joins(stack: :repository).where(sha: params.sha, shipit_repositories: { owner: repository_owner, name: repository_name })`.
- Alternatively/additionally, scope by `stack_id` derived from the payload's repository rather than a bare global `sha` scan.

### Proof of Concept
Add to `test/models/webhooks/handlers/status_handler_test.rb` (or a new test file):
```ruby
test "a status webhook for one repository does not mutate a commit belonging to a different stack that happens to share the same sha" do
  victim_stack = shipit_stacks(:shipit)               # continuous_deployment: true, has an active task fixture
  attacker_stack = shipit_stacks(:some_other_org_stack) # different repository/org

  shared_sha = "deadbeef" * 5
  victim_commit = victim_stack.commits.create!(sha: shared_sha, message: "shared", author: shipit_users(:walrus), committer: shipit_users(:walrus), authored_at: Time.now, committed_at: Time.now)
  attacker_commit = attacker_stack.commits.create!(sha: shared_sha, message: "shared", author: shipit_users(:walrus), committer: shipit_users(:walrus), authored_at: Time.now, committed_at: Time.now)

  before = victim_stack.next_expected_commit_to_deploy

  Shipit::Webhooks::Handlers::StatusHandler.new.call(
    "sha" => shared_sha,
    "state" => "success",
    "repository" => { "owner" => { "login" => attacker_stack.repository.owner }, "full_name" => attacker_stack.repository.name }
  )

  after = victim_stack.reload.next_expected_commit_to_deploy

  assert_not_equal before, after, "attacker-owned repository's status webhook altered the victim stack's next expected commit"
  refute_predicate victim_commit.reload.statuses, :empty? # victim commit got a status it never legitimately received
end
```
Assert on both sides of the equality: `before` (victim's `next_expected_commit_to_deploy` prior to the foreign webhook) vs `after` (post-webhook), demonstrating the divergence caused solely by an attacker-controlled, differently-owned repository's webhook.
