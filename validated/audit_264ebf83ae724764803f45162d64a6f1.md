### Title
Session fixation on the GitHub OAuth callback allows forced authentication as a victim - (File: `app/controllers/shipit/github_authentication_controller.rb`)

### Summary
The BarnBridge report describes a bug class where a value the protocol trusts (the fee amount) is derived without validating the boundary condition that protects it, letting an attacker repeatedly exploit the gap. The Shipit analog is a **session-identity binding gap**: the GitHub identity returned by the OmniAuth callback is written into `session[:user_id]` without first rotating the session id, so a pre-existing (attacker-fixated) session id becomes authenticated as the victim once the victim completes GitHub OAuth. The binding that should hold — "the session id used post-login" == "a session id newly issued at login time" — is broken.

### Finding Description
`GithubAuthenticationController#callback` is a public, unauthenticated endpoint (it is excluded from `Shipit::Authentication`'s `force_github_authentication` filter since it lives outside that concern, and it is reachable by anyone hitting `/github/auth/github/callback`): [1](#0-0) 

The controller sets `session[:user_id]` and `session[:authenticated] = true` directly from the OmniAuth result, with no call to `reset_session` (that call only exists in `#logout`): [2](#0-1) 

`current_user` elsewhere in the engine is derived purely from `session[:user_id]`: [3](#0-2) 

Because the Rails session cookie id is not regenerated at the moment of authentication, an attacker who can plant a known session id in a victim's browser (classic session fixation — e.g., via a subdomain cookie, a response-header injection elsewhere, or any mechanism that lets an attacker set a cookie value in the victim's browser for this application's domain) can:
1. Establish a session id of the attacker's choosing in the victim's browser (unauthenticated state).
2. Wait for/induce the victim to complete the real GitHub OAuth flow on that same browser/session.
3. Because `sign_in_github` writes `session[:user_id]` into the *existing* session rather than a freshly rotated one, the attacker's known session id is now bound to the victim's authenticated `User` record.
4. The attacker can then present that same session id in their own request and be treated as the victim by every session-based controller/action in the engine (deploys, merges, task triggers, API-client creation, etc.), because `current_user` only trusts `session[:user_id]`.

This directly parallels the requested binding class: "a GitHub identity versus the `User` bound to the session" — the equality that should be enforced ("session id at login" = "a session id minted for that login") is never established.

### Impact Explanation
This is a session fixation vulnerability leading to authentication bypass: an unprivileged attacker who can fixate a session id can end up fully authenticated as any victim who completes GitHub OAuth on that session, without ever needing valid GitHub credentials, an API token, or repository write access. Once authenticated as the victim, the attacker inherits all of the victim's privileges in the engine (triggering deploys/rollbacks, creating `ApiClient`s with `Shipit.github_teams`-gated permissions, approving merges, etc.), matching the "authentication bypass" / "escalation into `Shipit.github_teams` authorization" impact tiers called out in the rules.

### Likelihood Explanation
Exploitation requires the classic session-fixation precondition (the attacker must be able to set a session cookie value in the victim's browser before the victim authenticates), which is a real-world, commonly exploitable scenario for applications that don't rotate session ids at login — this is exactly why Rails/OWASP guidance requires calling `reset_session` (or `session.clear` + regeneration) immediately before or after setting authentication state. No repository access, GitHub App keys, or API tokens are needed by the attacker themselves.

### Recommendation
Call `reset_session` in `GithubAuthenticationController#callback` immediately before establishing the new authenticated session (i.e., before assigning `session[:user_id]` and `session[:authenticated]`), mirroring what is already done in `#logout`. This forces a new session id to be issued at the moment of authentication, severing any pre-existing (potentially attacker-controlled) session identifier from the newly authenticated identity.

### Proof of Concept
1. Attacker obtains/fixates a session cookie for the Shipit host in the victim's browser (session id `S`), while unauthenticated.
2. Victim, using the same browser/cookie jar, navigates to `/github/auth/github` and completes the real GitHub OAuth flow.
3. `GithubAuthenticationController#callback` executes `session[:user_id] = sign_in_github(auth)` on session `S` without rotating it — see [4](#0-3)  — binding the victim's `User` to session id `S`.
4. Attacker, who already knows session id `S`, sends any subsequent request (e.g., `POST /:stack/deploys`) using that same session id and is treated as the victim by `current_user` ( [3](#0-2) ), performing privileged actions as the victim.

```ruby
# frozen_string_literal: true

module Shipit
  class GithubAuthenticationController < ActionController::Base
    include Shipit::Engine.routes.url_helpers

    def callback
      return_url = request.env['omniauth.origin'] || root_path
      auth = request.env['omniauth.auth']

      return render('failed', layout: false) if auth.blank?

      session[:user_id] = sign_in_github(auth)

      # We need to set this so that the /events and /sidekiq endpoint
      # which leverage `UserRequiredMiddleware` will recognize the user
      # is authenticated.
      session[:authenticated] = true

      redirect_to(return_url)
    end

    def logout
      reset_session
      redirect_to(root_path)
    end

    private

    def sign_in_github(auth)
      user = User.find_or_create_from_github(auth.extra.raw_info)
      user.update(github_access_token: auth.credentials.token)
      user.id
    end
  end
```
