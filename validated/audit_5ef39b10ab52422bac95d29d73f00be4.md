### Title
Malicious strategy venue can attach an arbitrary victim token transfer to the signed authorization tree - ([File: contracts/controller/src/strategies/swap.rs])

### Summary
`swap_collateral` accepts opaque route bytes and invokes the configured router while the account owner’s authorization is active [1](#0-0) . The route can name an attacker-controlled venue, and the venue is invoked below the caller’s authorization context [2](#0-1) . If that venue calls `token.transfer(victim, attacker, amount)`, Soroban simulation records the transfer as a child authorization; a phished victim who signs that tree loses the unrelated wallet tokens [3](#0-2) .

### Finding Description
The controller requires the caller to own or delegate the account, but places no restriction on the route payload beyond requiring it to be non-empty [1](#0-0) . `swap_tokens` authorizes only the controller’s exact input transfer to the router, then calls `execute_strategy` with the caller-supplied payload [4](#0-3) .

The router decodes attacker-controlled asset and pool addresses from the payload and invokes the selected venue-specific hop [5](#0-4) [2](#0-1) . Venue dispatch does not validate that the pool address belongs to an allowlist [6](#0-5) .

A malicious venue can therefore execute arbitrary contract code during the signed strategy call. If it invokes a token contract’s `transfer(from = victim, to = attacker, amount)`, the token requires the victim’s authorization [7](#0-6) . An honest simulation attaches that transfer under the victim’s `swap_collateral` authorization, and enforcing mode permits it once the victim signs the resulting tree [8](#0-7) .

### Impact Explanation
An attacker can steal arbitrary tokens from the victim’s wallet, including tokens never supplied to the lending protocol. The theft is not limited to the swap input, the account collateral, or the router’s measured output [9](#0-8) . The harness demonstrates the complete loss of a 77,770-unit unrelated wallet balance while the routed swap itself pays a fair output [10](#0-9) [11](#0-10) .

### Likelihood Explanation
The attacker cannot submit the theft without the victim’s signature because the token transfer must be present in the signed authorization tree [12](#0-11) . The practical path is phishing or a malicious route-generation service that causes the victim to sign a simulated authorization tree containing the hidden transfer. Because the venue address comes from opaque route bytes and is not allowlisted, a malicious venue can be introduced without protocol privileges [13](#0-12) [14](#0-13) .

### Recommendation
Restrict routes to governance-reviewed venue and pool addresses, or have the controller/router reject routes whose simulation produces any caller-authorization child other than the expected input transfer. At minimum, transaction-building clients must reject any signed authorization tree containing extra `token.transfer` children before asking the user to sign [9](#0-8) .

### Proof of Concept
1. Alice creates a lending account and supplies USDC collateral [15](#0-14) .
2. The attacker deploys a malicious pool contract whose `swap` function calls `USDC_UNRELATED_TOKEN.transfer(alice, attacker, balance)` [16](#0-15) .
3. The attacker gives Alice a `swap_collateral` route naming that pool as the hop address. The router accepts it because pool addresses come from the payload’s unrestricted address registry [2](#0-1) .
4. Alice simulates `swap_collateral(caller=alice, account_id, current=USDC, amount, new=ETH, swap=malicious_route)`. The route executes the malicious pool while Alice’s root authorization is active [17](#0-16) .
5. The simulation returns an authorization tree containing an additional child `token.transfer(alice, attacker, alice_balance)` [18](#0-17) .
6. If Alice signs that tree, the malicious token transfer succeeds and the attacker receives the unrelated wallet tokens [8](#0-7) .

pub(crate) fn dispatch_hop(
    env: &Env,
    router: &Address,
    hop: &SwapHop,
    amount_in: i128,
    tokens_cache: &mut Map<Address, Vec<Address>>,
) -> i128 {
    let ctx = HopContext::new(env, router, hop, amount_in);
    let before_in = ctx.input_balance();
    let before_out = ctx.output_balance();

    match hop.venue {
        SwapVenue::Soroswap => soroswap::swap(&ctx),
        SwapVenue::Aquarius => aquarius::swap(&ctx, tokens_cache),
        SwapVenue::Phoenix => phoenix::swap(&ctx),
        SwapVenue::Sushi => sushi::swap(&ctx),
        SwapVenue::CometDex => comet::swap(&ctx),
    };

**File:** docs/explanation/threat-model.md (L154-165)
```markdown
That bound covers the controller's own grant only. The router calls the pool
and token addresses its payload names and keeps no allowlist of them, so a
route can put third-party code on the call stack below the caller's
authorization. A token transfer that such code makes from the caller is
recorded by an honest simulation as a child of the caller's authorization
entry, and it executes if the caller signs that tree. The loss is then the
caller's wallet, not the routed amount, and neither the payload minimum nor the
final risk gate bounds it. An honest swap strategy gives the caller no child
entry, and a direct router swap gives exactly one input transfer. A client must
decode the route it signs and refuse an authorization tree with any other
child. The direct `execute_strategy` path has the same exposure for every swap
user.
```
