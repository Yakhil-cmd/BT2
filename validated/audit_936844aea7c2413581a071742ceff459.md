## Title
Scoped ApiClient tokens bypass their stack restriction on the CCMenu API endpoint - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Shipit::Api::CCMenuController` overrides the shared, scope-respecting `stack` lookup from `BaseController` with an unscoped one, so an `ApiClient` token that is restricted to a single stack can be used to read the CI status of *any* stack in the Shipit instance.

### Finding Description
`Shipit::Api::BaseController` defines the trust binding "a token authorizes only the stack(s) it is scoped to": [1](#0-0) 

`stacks` restricts the queryable set to `Stack.where(id: current_api_client.stack_id)` whenever the authenticated `ApiClient` is scoped to a stack (`stack_id?` true), and `stack` is derived from that restricted relation. This is the mechanism that enforces the equality: `{stacks reachable by client} == {stacks the client is authorized for}`.

`CCMenuController`, however, redefines `stack` to bypass this scoping entirely: [2](#0-1) 

It calls `Stack.from_param!(params[:stack_id])` directly on the `Stack` model, not through the client-scoped `stacks` relation. The controller does enforce `require_permission :read, :stack` via `ApiClient#check_permissions!`, but that check only validates that the token carries the `read:stack` *permission string* — it does not verify which specific stack the permission applies to: [3](#0-2) 

Consequently, for any `ApiClient` created with a `stack_id` (e.g. the `CCMenu Client` created automatically by `CCMenuUrlController` for the current viewer of one specific stack), the resulting authentication token — while intended to authorize CCMenu access to that one stack only — will authenticate successfully against `CCMenuController#show` for an arbitrary `stack_id` parameter in the URL, since `stack` no longer filters by `current_api_client.stack_id`. [4](#0-3) 

This breaks the equality "stack a token authorizes == stack the request actually touches": before the bug, `stack ∈ {current_api_client.stack_id}`; after hitting `CCMenuController#show` with a different `stack_id` param, `stack` can be any stack in the installation.

### Impact Explanation
This is a High-severity issue: it is an unauthenticated-scope escalation allowing unauthorized read of stack state/task output (last deploy status, lock state, etc.) for any stack, using a token that was only ever meant to be scoped (and distributed, e.g. embedded in a CCMenu client URL) for a single stack. Any holder of one stack's CCMenu token (which is exposed via `ccmenu_url` and often embedded unencrypted in third-party CI dashboard tools) can enumerate and read build/deploy status of every other stack managed by the Shipit instance.

### Likelihood Explanation
High likelihood: CCMenu tokens are generated automatically and shared broadly (embedded in URLs consumed by external CCMenu-compatible clients), so they are more likely to leak or be reused outside their intended single-stack scope than a general API token. No special privilege beyond possessing one scoped CCMenu token is required — this is purely an unprivileged-attacker path since the attacker only needs a token issued for *some* stack, not the target stack.

### Recommendation
Change `CCMenuController#stack` to look up the stack through the scoped `stacks` relation (inherited from `BaseController`) instead of calling `Stack.from_param!` directly, e.g. `@stack ||= stacks.from_param!(params[:stack_id])`, so that `current_api_client.stack_id` scoping is enforced consistently across all API controllers.

### Proof of Concept
1. Create (or have Shipit auto-create via `CCMenuUrlController#fetch`) an `ApiClient` scoped to `stack_id: A` with `permissions: ['read:stack']`, and obtain its `authentication_token`.
2. As an attacker in possession of that token (e.g. found via a leaked CCMenu URL for stack A), issue: `GET /api/stacks/<owner>/<repo-of-stack-B>/<env-of-stack-B>/ccmenu.xml?token=<tokenForStackA>`.
3. `authenticate_api_client` (overridden in `CCMenuController`) succeeds via `ApiClient.authenticate(params[:token])`.
4. `require_permission :read, :stack` passes because the token does carry the `read:stack` permission string.
5. `stack` resolves via `Stack.from_param!(params[:stack_id])` to stack B, unrelated to the token's `stack_id`, and its CI status is rendered — despite the token being provisioned only for stack A.
