### Title
CCMenu client token is stack-agnostic and `Api::CCMenuController#stack` bypasses client stack-scoping - (File: app/controllers/shipit/ccmenu_url_controller.rb, app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::CCMenuUrlController#fetch` mints (or reuses) an `ApiClient` named `'CCMenu Client'` scoped only by `creator`, with a global `read:stack` permission and no `stack_id` set, then embeds a target stack in the URL *path* only for readability while the token itself authorizes nothing stack-specific. `Api::CCMenuController#stack` further overrides the `stack` accessor from `Api::BaseController` to query the *unscoped* `Stack` model instead of the client-scoped `stacks` relation, so even if a client's `stack_id` were ever set, it would not be enforced on this endpoint.

### Finding Description
The claimed binding, stated as an equality that must hold, is:

`client.stack_id == stack.id` (the ApiClient authorizing the request must equal the stack being requested)

Tracing the code:

- `CCMenuUrlController#fetch` builds `client` via:
`ApiClient.create_with(permissions: %w[read:stack]).find_or_create_by!(creator: current_user, name: 'CCMenu Client')` [1](#0-0) 
No `stack:` attribute is ever assigned, so `client.stack_id` is `nil` for every stack the user has ever requested a CCMenu URL for — the same single `ApiClient` record (and thus the same `authentication_token`) is returned regardless of which `stack_id` was passed in `params`. [2](#0-1) 

- `ApiClient#check_permissions!` only checks the flat string `"#{operation}:#{scope}"` (e.g. `"read:stack"`) against `permissions`; it never compares against a specific stack instance: [3](#0-2) 

- `Api::BaseController` *does* have a mechanism intended to scope clients to a single stack (`stacks` returns `Stack.where(id: current_api_client.stack_id)` when `stack_id?` is true, else `Stack.all`), and its `stack` method uses that scoped relation: [4](#0-3) 

- However, `Api::CCMenuController` overrides `stack` to bypass this scoping entirely, querying the raw `Stack` model: [5](#0-4) 

So both the token minting side (never sets `stack_id`) and the token consuming side (`Api::CCMenuController#stack` ignores `current_api_client.stack_id` even when set) fail to enforce the equality. `client.stack_id` is always `nil` and is never compared to the requested `stack.id` — the two sides of the binding are never evaluated together, so a token minted while viewing Stack A's CCMenu URL is functionally valid for any stack whose `to_param` is substituted into the URL path.

Attack: an operator with legitimate `read:stack` access to Stack A calls `GET /stacks/A/ccmenu_url`, receiving `.../ccmenu.xml?token=<t>` with path `stack_id=A`. Any third party who observes this URL (CI dashboard, access log, browser history) can request `.../stacks/B/ccmenu.xml?token=<t>` for arbitrary Stack B; `Api::CCMenuController#authenticate_api_client` calls `ApiClient.authenticate(params[:token])`, which succeeds (same client id, same HMAC), `require_permission :read, :stack` passes (permission is not stack-scoped), and `stack = Stack.from_param!(params[:stack_id])` resolves to Stack B with no ownership check.

Existing guards do not prevent this: `require_permission!` only checks the operation:scope string; `Stack.from_param!` performs no tenant/owner filtering; `Api::BaseController#stacks`'s scoping-by-`current_api_client.stack_id` is dead code for this controller because `CCMenuController#stack` shadows it and, additionally, the client never has `stack_id` set in the first place.

### Impact Explanation
An attacker who merely observes a shared/leaked CCMenu URL for one stack can read the build/deploy status (`ccmenu.xml`, includes latest deploy/rollback state) of any other stack in the Shipit instance by substituting the path segment, with no additional credential, repeatable indefinitely against arbitrary stacks. This is an authorization-scope bypass enabling unauthenticated (relative to the target stack) read of stack state across tenants/repositories, matching the High severity category "escalation... or unauthenticated read of stack state, task streams or deploy output."

### Likelihood Explanation
No special Shipit or repository configuration is required beyond the CCMenu feature being enabled (default). The only precondition is that a legitimate CCMenu URL for any stack becomes observable to a third party — a well-documented low-cost scenario (CI status pages, shared dashboards, browser history, forwarded links) already assumed in the question's preconditions. The attack requires no GitHub credentials, no Shipit session, and no privileged role — simple URL string substitution.

### Recommendation
Bind the minted `ApiClient` to the specific stack it was generated for (`ApiClient.create_with(permissions: %w[read:stack], stack: stack)` in `CCMenuUrlController#fetch`, uniquely keyed per stack rather than reused via `find_or_create_by!(creator:, name:)` alone), and remove the `stack` override in `Api::CCMenuController` so it uses the inherited `stacks`/`stack` from `Api::BaseController`, which enforces `current_api_client.stack_id` against the requested `stack_id`.

### Proof of Concept
Minitest plan (`test/controllers/ccmenu_controller_test.rb` style, adapted conceptually):
1. Sign in as a user with `read:stack` access to `stack_a`; `POST/GET /stacks/:stack_a_id/ccmenu_url`; capture returned `ccmenu_url`, parse `token` query param.
2. Assert `GET` to `stack_a`'s `ccmenu.xml?token=<token>` returns `200`.
3. Build a second URL replacing only the `stack_id` path segment with `stack_b.to_param`, keeping the same `token`.
4. Assert `GET` to that rewritten URL against `stack_b`'s `ccmenu.xml` also returns `200` and renders `stack_b`'s status — proving `client.stack_id` (nil) is never compared to `stack_b.id`, violating the claimed binding.
