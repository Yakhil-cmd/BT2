### Title
Webhook signature verification is keyed off `repository.owner.login`, but event handlers act on the independent `repository.full_name` field, allowing signature-bypass on any organization to forge events against a different, unrelated repository - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which `GitHubApp` (and thus which `webhook_secret`) is used to validate an inbound webhook by reading `params.dig('repository', 'owner', 'login')` (falling back to `organization.login`). Once verification passes, the entire raw payload is handed to `Shipit::Webhooks.for_event(event)` handlers, which determine the actual repository/stack to act on using a *different* field: `payload.dig('repository', 'full_name')`. These two payload fields are never cross-checked, and `GitHubApp#verify_webhook_signature` trivially returns `true` whenever the organization used for verification has no `webhook_secret` configured. This lets an attacker "authenticate" against a low-value/unconfigured organization while the payload actually targets and mutates state for a completely different repository.

### Finding Description
`verify_signature` picks the signing organization from the attacker-controlled JSON body: [1](#0-0) [2](#0-1) 

`GitHubApp#verify_webhook_signature` unconditionally passes when the selected organization has no secret configured: [3](#0-2) 

Shipit explicitly supports per-organization GitHub App configs, each with its own optional `webhook_secret` (documented as nullable, `webhook_secret: # nil`): [4](#0-3) [5](#0-4) 

After `verify_signature` succeeds (using whatever organization the attacker named in `repository.owner.login`), the full, unmodified `params` is dispatched to handlers via `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`: [6](#0-5) 

Every handler, however, resolves the target `Repository`/`Stack` from an entirely different, unrelated JSON field, `repository.full_name`, never `repository.owner.login`: [7](#0-6) 

For example `PushHandler` uses this to fetch the stacks and immediately triggers a sync against the real, unrelated stack: [8](#0-7) 

This mirrors the smart-contract bug class in the report: two code paths cover different subsets of the same logical operation (there, `_nativeReserve` was checked in one variant but not the other; here, "which org authenticated the request" is checked against `repository.owner.login`, while "which repository is written to" is taken from `repository.full_name`). The equality that should hold — `organization that authenticated == organization owning the repository being acted on` — is never enforced, so an attacker can supply a payload where these two fields point to different organizations.

### Impact Explanation
An unauthenticated, unprivileged network attacker (no Shipit session, `ApiClient` token, or knowledge of any real `webhook_secret` is required) can:
1. Configure/guess an organization slug that is present in Shipit's multi-org `github:` config but has no `webhook_secret` set (a supported, documented configuration state), or otherwise cause `repository.owner.login` to resolve to such an org.
2. Craft a webhook body where `repository.owner.login`/`organization.login` = that no-secret org, but `repository.full_name` = the real target org/repository that *does* have a secret and is actually deployed via Shipit.
3. Send this to `/webhooks` with an `X-Github-Event: push` header and an arbitrary/garbage `X-Hub-Signature`. `verify_signature` looks up the no-secret org's `GitHubApp`, and `verify_webhook_signature` returns `true` unconditionally because `webhook_secret` is blank.
4. `PushHandler` then resolves stacks via `repository.full_name` (the real target) and invokes `stack.sync_github(expected_head_sha: params.after)`, which enqueues `GithubSyncJob`. This causes Shipit to fetch and record new commits against the real stack and can enqueue `CacheDeploySpecJob`, potentially advancing continuous-delivery state for a stack the attacker was never authorized to trigger events for.

This breaks the "organization that authenticated versus the repository that is written" trust binding called out in the rules, and results in unauthorized triggering of deploy-pipeline machinery (commit ingestion / continuous delivery advancement) on a repository/stack the attacker has no legitimate signature for — satisfying the "unauthorized deploy" critical-impact category.

### Likelihood Explanation
Likelihood is elevated by the fact that per-organization `webhook_secret` is explicitly optional in Shipit's supported multi-org configuration (as shown in the example secrets files and setup docs), so any Shipit deployment onboarding multiple GitHub organizations is likely to have at least one org where the operator has not yet set a secret (e.g., newly added org, staging org, or an org intentionally left public). No credentials, GitHub App private key, or webhook secret of the *target* org are required, only knowledge that some other configured org lacks one — information that can often be inferred (e.g., trial-and-error with `X-Hub-Signature` mismatches, or via server logs like `WebhookController#verify_signature` which even logs the organization derived).

### Recommendation
Bind webhook signature verification and event dispatch to the *same* organization: after computing the effective organization used to verify the signature, require that `payload.dig('repository', 'full_name')`'s owner matches that organization (reject/422 otherwise) rather than deriving the verifying organization from one payload field and the acted-upon repository from another, unrelated field. Additionally, do not allow `verify_webhook_signature` to silently pass when `webhook_secret` is unset in production; require a configured `webhook_secret` for every organization, or fail closed if it is missing.

### Proof of Concept
1. Configure Shipit with two GitHub orgs in `config/secrets.yml`: `no-secret-org` (no `webhook_secret` set) and `real-org` (has `webhook_secret` set, and hosts a Shipit stack `real-org/target-repo/production`).
2. POST to `/webhooks` with:
   - Header `X-Github-Event: push`
   - Header `X-Hub-Signature: sha1=deadbeef` (arbitrary/invalid)
   - Body:
     ```json
     {
       "ref": "refs/heads/master",
       "after": "<attacker-chosen-sha-that-exists-on-github>",
       "repository": {
         "owner": { "login": "no-secret-org" },
         "full_name": "real-org/target-repo"
       }
     }
     ```
3. `WebhooksController#repository_owner` resolves to `no-secret-org`; `Shipit.github(organization: 'no-secret-org').verify_webhook_signature` returns `true` because that org has no `webhook_secret` configured — despite the bogus signature.
4. `Shipit::Webhooks.for_event('push')` dispatches to `PushHandler`, which resolves the target repository/stack from `repository.full_name` = `real-org/target-repo`, and calls `stack.sync_github(expected_head_sha: ...)`, enqueuing `GithubSyncJob` for the real stack — all without ever presenting a valid signature for `real-org`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
