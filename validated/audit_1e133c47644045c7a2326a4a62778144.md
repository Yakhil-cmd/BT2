**Analysis:**

In `rotate_encryption_key_raw` / `rotate_encryption_key`, the `owner: &signer` parameter is not attacker-controlled data — it is a native VM-constructed `signer` reference bound to whichever account address was cryptographically authenticated for that transaction (via the transaction authenticator, verified before Move execution even starts). An attacker cannot supply an arbitrary address for the `&signer` parameter; `signer::address_of(owner)` always returns the attacker's own authenticated account address, never a victim's.

Tracing the call:
- `rotate_encryption_key` calls `borrow_confidential_store_mut(signer::address_of(owner), asset_type)`, which always resolves to the caller's own `ConfidentialStore` [1](#0-0) .
- `assert_valid_key_rotation_proof` builds the sigma-protocol session via `sigma_protocol_key_rotation::new_session(owner, asset_type)`, which derives the domain separator/statement binding from the same `owner` signer [2](#0-1) .
- The Fiat-Shamir domain separator for verification is built from `self` (the session, which encodes `sender = signer::address_of(&sender)`), chain ID, and protocol ID [3](#0-2) .

There is no code path where an attacker's proof data, `asset_type` object, or any entry-function argument can override or rebind which address `owner`/`sender` resolves to — that binding is fixed by the Move VM's signer-construction mechanism, which itself derives from the transaction's authenticated sender (enforced upstream at the authenticator/VM-validator layer, outside application Move code). Forging a proof "for" a victim's `ConfidentialStore` while signing as the attacker would require either (a) controlling the victim's decryption key (a leaked-key precondition, explicitly out of scope) or (b) breaking the VM's signer-address binding itself, which is not something achievable via crafted entry-function arguments in `confidential_asset.move`.

Since the described exploit requires the transaction's own signer to bind to an address other than the authenticated sender — something the Move VM's signer semantics prevent by construction — this does not constitute a valid admission-boundary vulnerability under the review's decision standard.
