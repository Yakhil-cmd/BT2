### Title
`in_data_feed`/`in data feed` inside AAs accepts data feeds from non-`good`-sequence (final-bad/double-spent) units - ([File: data_feeds.js])

### Summary
`data_feeds.js#dataFeedExists()` is the function that evaluates `in_data_feed[...]` (formula/evaluation.js) and `["in data feed", ...]` address-definition conditions (definition.js) when called from AA context (`bAA=true`). Unlike its sibling `readDataFeedValue()`, which is used to evaluate `data_feed[[...]]` value reads, `dataFeedExists()`'s in-memory scan of `storage.assocUnstableMessages` never checks `objUnit.sequence === 'good'` before treating a candidate unit's `data_feed` message as proof that the condition is satisfied.

### Finding Description
`readDataFeedValue()` explicitly filters out non-good-sequence units: [1](#0-0) 
```
217: if (!objUnit.bAA && !bIncludeAllUnstable) continue;
219: if (objUnit.sequence !== 'good') continue;
```

`dataFeedExists()`, which implements the boolean "does a data feed satisfying condition X exist" check used by `in_data_feed` (an AA formula construct) and `["in data feed", ...]` (an address-definition/oscript construct), performs the same unstable-unit scan but has no equivalent `sequence !== 'good'` guard: [2](#0-1) 

This is called with `bAA=true` from AA formula evaluation: [3](#0-2) 

and from address-definition evaluation with `bAA` propagated from the validation state (which is `true` while executing inside an AA): [4](#0-3) 

In Obyte's DAG, a unit can be temporarily included in `storage.assocUnstableMessages`/`assocUnstableUnits` while still unstable, and can later be marked `sequence = 'final-bad'` (e.g., because it double-spends an input, conflicts with an earlier-ordered unit, or is otherwise voided) once its ordering relative to the main chain is determined - such a unit's messages are permanently excluded from consensus effect once it goes final-bad, yet its `data_feed` message stays in `assocUnstableMessages` until it is fully evicted from cache. `dataFeedExists()` will still treat that message as "found" for any AA that queries `in_data_feed[[...]]`, or for any oscript/address definition using `["in data feed", ...]` while executing under an AA context. This is directly analogous to `CollateralToken.settleAuction()` trusting that a privileged event occurred without checking that the referenced state (a successful/valid transaction) actually took place — here, the code trusts that a `data_feed` message came from a valid/serial unit without checking `sequence`.

### Impact Explanation
An oscript/AA author can build financial logic (fund release, dispute resolution, oracle-gated payments, arbiter-style contracts) around `in_data_feed[[oracles=..., feed_name=..., feed_value ...]]`. Any address (an unprivileged "oracle" poster, or a malicious actor colluding with/spoofing an oracle) can post a unit containing a matching `data_feed` message and immediately double-spend one of its own inputs in a conflicting unit, causing the original unit to eventually resolve to `sequence = 'final-bad'`. Before that resolution completes/evicts from `assocUnstableMessages`, or if the AA's trigger is evaluated against the unstable snapshot at a point where the bad unit is still present, `in_data_feed` will incorrectly report `true`, letting an AA release funds, resolve a dispute, or otherwise change state based on a condition that never actually held under consensus rules. This can lead to unauthorized AA fund loss/release (an "AA fund loss" impact category), potentially exploitable by any user able to post a unit and its double-spend, without needing the AA owner's cooperation.

### Likelihood Explanation
Reaching this path only requires: (1) an AA definition (or private/prosaic address definition executed by an AA) using `in_data_feed`/`["in data feed", ...]`, which is a documented, commonly used oscript primitive for oracle-gated conditions; and (2) posting one unit with the matching `data_feed` payload and a conflicting double-spend unit — both are actions available to any ordinary wallet/unit poster, requiring no special privileges, matching the "AA trigger sender / asset issuer / oscript evaluation" unprivileged actor classes allowed by the rules. The main uncertainty is the precise timing window in which the final-bad unit remains present in `assocUnstableMessages` relative to when AAs evaluate triggers, and it could not be fully verified from the indexed portion of `storage.js` how quickly `assocUnstableMessages` entries for final-bad units are purged; that timing detail would need confirmation via a live/test-node reproduction.

### Recommendation
Add the same `if (objUnit.sequence !== 'good') continue;` guard to the `bAA` branch of `dataFeedExists()` in `data_feeds.js`, mirroring the check already present in `readDataFeedValue()`, so that `in_data_feed` and `["in data feed", ...]` conditions evaluated inside AAs only ever consider messages from units with confirmed `sequence === 'good'`.

### Proof of Concept
Conceptual reproduction (exact timing needs confirmation on a running node/testkit):
1. Deploy an AA whose logic includes `in_data_feed[[oracles="ORACLE_ADDR", feed_name="X", feed_value="Y"]]` gating a payment/state change.
2. From `ORACLE_ADDR`, post unit U1 with `data_feed` message `{X: "Y"}`, spending some output O.
3. Before U1 stabilizes, from the same address (or a colluding address), post a conflicting unit U2 that double-spends output O, causing U1 to eventually be marked `sequence: 'final-bad'` by the DAG's conflict-resolution rules.
4. While U1 is still present in `storage.assocUnstableMessages` (post-inclusion, pre-eviction) but already resolved to non-good sequence, trigger the AA. Because `dataFeedExists()` never checks `objUnit.sequence`, the AA's `in_data_feed` check returns `true` and the AA executes the gated logic even though U1 is not a valid/final unit — compare against `readDataFeedValue()` behavior for the same scenario, which correctly excludes U1 via its `sequence !== 'good'` check.
