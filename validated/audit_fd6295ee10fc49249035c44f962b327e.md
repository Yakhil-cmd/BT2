The reported issue describes inherent behavior of constant-product AMM liquidity math (LP tokens computed via `sqrt(amount1 * amount2) - MINIMUM_LIQUIDITY`), which naturally produces different raw LP-token magnitudes for token pairs with different decimal precisions. This is the same design used by Uniswap V2 and is intentional/expected: LP token supply is meaningful only *within* a given pool, not comparable in absolute magnitude across different pools with different decimal assets.

The Polkadot SDK analog is `pallet-asset-conversion`'s `calc_lp_amount_for_zero_supply`, which computes the initial LP mint the same way as Uniswap V2: [1](#0-0) 

and is invoked from `do_add_liquidity` when `total_supply.is_zero()`: [2](#0-1) 

This mirrors the reported pattern exactly (sqrt of product minus a minimum-liquidity constant, no decimal normalization), as confirmed by the pallet's own test expectations (`sqrt(10_000 * 10_000) - MintMinLiquidity(100) = 9_900`): [3](#0-2) 

There is no invariant being violated here:
- LP token amounts for a given pool are only meaningful relative to that pool's own reserves and total supply; the pallet never claims cross-pool LP-token comparability, and no downstream logic (fee sharing, redemption via `mul_div` in `do_remove_liquidity`) depends on cross-pool LP amount consistency — it always uses `total_supply` and reserves specific to that pool: [4](#0-3) .
- Redemption correctly returns each LP holder their proportional share of that specific pool's reserves regardless of the absolute LP token magnitude, so no value is misallocated or stolen.
- There's no attacker-controlled entry point that exploits this to steal funds, mint unbacked value, or manipulate another user's position — every liquidity provider's redemption value is still proportional to their share of that specific pool.

Since the underlying "bug" is a well-known and accepted characteristic of constant-product AMMs (not unique to the original Solidity contract), and the FRAME pallet's math and safety invariants (minimum liquidity, proportional redemption, overflow checks via `HigherPrecisionBalance`) are intact, this does not constitute a demonstrable, reachable vulnerability under the required scan criteria (no theft, unbacked issuance, unauthorized dispatch, or integrity break).

		pub(super) fn calc_lp_amount_for_zero_supply(
			amount1: &T::Balance,
			amount2: &T::Balance,
		) -> Result<T::Balance, Error<T>> {
			let amount1 = T::HigherPrecisionBalance::from(*amount1);
			let amount2 = T::HigherPrecisionBalance::from(*amount2);

			let result = amount1
				.checked_mul(&amount2)
				.ok_or(Error::<T>::Overflow)?
				.integer_sqrt()
				.checked_sub(&T::MintMinLiquidity::get().into())
				.ok_or(Error::<T>::InsufficientLiquidityMinted)?;

			result.try_into().map_err(|_| Error::<T>::Overflow)
		}
