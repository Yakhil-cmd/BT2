### Title
Cross-tenant webhook forgery via `repository.owner.login` / `repository.full_name` split lets an attacker without any secret mutate another org's `PullRequest` record - (File: `app/controllers/shipit/webhooks_controller.rb`, `lib/shipit/github_app.rb`, `app/models/shipit/webhooks/handlers/pull_request/edited_handler.rb`)

### Summary
`WebhooksController#verify_signature` selects the GitHub App/secret to validate the HMAC using `repository.owner.login` (via `repository_owner`), while `EditedHandler` resolves the repository/stack it mutates using an entirely different field, `repository.full_name`. Nothing binds these two values together, so an attacker can name an org that has no `webhook_secret` configured in `repository.owner.login` (which causes `verify_webhook_signature` to return `true` unconditionally) while pointing `repository.full_name` at a different, victim-configured org/repo whose `PullRequest` record then gets overwritten with attacker-controlled data.

### Finding Description
The intended invariant is: **the org that authenticates the webhook == the org whose repository/stack is mutated by the handler**, i.e. `repository_owner == owner(params.repository.full_name)`. This binding is never checked.

- `WebhooksController#verify_signature` computes `github_app = Shipit.github(organization: repository_owner)` and calls `github_app.verify_webhook_signature(...)`, where `repository_owner` reads `params.dig('repository','owner','login')` (falling back to `organization.login`). [1](#0-0) [2](#0-1) 

- `GitHubApp#verify_webhook_signature` returns `true` unconditionally when the selected org has no `webhook_secret` configured: `return true unless webhook_secret`. [3](#0-2) 

- `EditedHandler#process` (and its sibling handlers) locate and mutate the `PullRequest` using `params.repository.full_name`, completely independent of `repository_owner`/the org that was used to verify the signature: [4](#0-3) 

Exploit flow:
1. Attacker registers/controls a GitHub org `attacker-org` that is either unconfigured in `Shipit.github_organizations` or configured with no `webhook_secret`.
2. Attacker sends `POST /webhooks` with header `X-Github-Event: pull_request`, body `action: "edited"`, `repository.owner.login: "attacker-org"`, but `repository.full_name: "victim-org/victim-repo"` (a real, secret-protected stack on the target Shipit instance), and any `number`/`pull_request` payload matching an existing PR record on the victim stack.
3. `verify_signature` resolves `Shipit.github(organization: "attacker-org")`; since that org has no secret, `verify_webhook_signature` returns `true` regardless of the (attacker-supplied, arbitrary) `X-Hub-Signature` header — no secret of any kind is needed.
4. `EditedHandler#process` then resolves `repository` via `Repository.from_github_repo_name("victim-org/victim-repo")`, finds the matching `PullRequest` scoped to that repository's stacks, and calls `pull_request.update(github_pull_request: params.pull_request)` — writing attacker-controlled JSON (title, labels, head sha/ref, assignees, additions/deletions, etc.) into the victim's persisted `PullRequest` record.

No existing guard prevents this: `drop_unhandled_event` only checks the event type is handled; `ExplicitParameters` only validates presence/type of fields, not cross-field consistency; there is no code anywhere that compares `repository_owner` to the owner embedded in `repository.full_name`.

Regarding the bot_login/auto-deploy amplification claim in the question: I could not verify within the available exploration that `EditedHandler`'s `pull_request.update(github_pull_request: ...)` call itself triggers an auto-deploy, merge, or rollback as the configured bot identity — that would require tracing `PullRequest` model callbacks/observers and any deploy-trigger logic, which I was not able to confirm from the files inspected. The confirmed, demonstrable impact is limited to: **an attacker with zero secrets for `victim-org` can force a write into `victim-org`'s persisted `PullRequest` record**, which matches the "payload for one repository mutating another's stack" Critical category on its own, independent of whether it cascades into an automatic deploy.

### Impact Explanation
An unprivileged attacker (no Shipit session, no API token, no webhook secret for the victim org) can forge a `pull_request` webhook that is accepted as valid by the victim's Shipit instance and causes a database write (`PullRequest#update`) against a stack belonging to a completely different, secret-protected organization. This is a cross-tenant integrity violation: the record written was never authenticated by its own owner's secret. The attack is repeatable against any `victim-org/victim-repo` combination as long as the attacker can name any org with no configured `webhook_secret` (including an org with no Shipit config entry at all, which also hits the same `return true unless webhook_secret` path via the default/no-op app) as `repository.owner.login`.

### Likelihood Explanation
Preconditions are minimal and cheap: the attacker needs no credentials, no repository access, and no knowledge of any secret — only knowledge of a target `owner/repo` full name that exists as a Shipit-managed repository, and the ability to send an unauthenticated HTTP POST. This is trivially repeatable and scriptable.

### Recommendation
Enforce that the organization used to select the webhook-verification secret matches the organization embedded in `repository.full_name` (and any other repo-identifying fields used by handlers) before dispatching to handlers — e.g., derive `repository_owner` strictly from `repository.full_name.split('/').first` (never from `repository.owner.login`), and reject the request if `repository.owner.login` and `repository.full_name`'s owner disagree. Additionally, treat "no configured `webhook_secret` for an org" as verification failure rather than automatic success, or restrict webhook processing to orgs explicitly present in `Shipit.github_organizations`.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (illustrative)
test "pull_request edited event with mismatched owner/full_name mutates victim stack's PullRequest" do
  victim_repo = shipit_repositories(:shipit) # owner: "shopify", name: "shipit-engine" e.g.
  victim_stack = victim_repo.stacks.first
  victim_pr = victim_stack.pull_requests.create!(number: 42, github_pull_request: { "title" => "original" })

  payload = {
    action: "edited",
    number: 42,
    pull_request: {
      id: 1, number: 42, url: "http://example", title: "PWNED",
      state: "open", additions: 1, deletions: 1,
      head: { sha: "a" * 40, ref: "attacker-branch" },
      user: { login: "attacker" }, assignees: [], labels: []
    },
    repository: { full_name: victim_repo.github_repo_name, owner: { login: "attacker-org-with-no-secret" } },
    sender: { login: "attacker" }
  }.to_json

  post shipit.webhooks_path, params: payload,
       headers: { 'X-Github-Event' => 'pull_request', 'X-Hub-Signature' => 'sha1=deadbeef',
                  'Content-Type' => 'application/json' }

  assert_response :ok
  victim_pr.reload
  assert_equal "PWNED", victim_pr.github_pull_request["title"] # written without victim's secret
end
```
Assertions on both sides of the binding:
- Before: `repository_owner` ("attacker-org-with-no-secret") ≠ owner of `victim_repo.github_repo_name` ("shopify"/etc.) — verification passed anyway because `webhook_secret` for `repository_owner` is absent.
- After: `victim_pr.github_pull_request["title"]` changed to attacker-controlled value, proving the victim's `Stack`/`PullRequest` was mutated by a request that was never authenticated with the victim org's secret.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
