### Title
Unverified `organization.login` in `membership` webhook lets an attacker seed a `Team` row that `Shipit.github_teams` later trusts for authorization - ([File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`WebhooksController#repository_owner` falls back to `params.dig('organization','login')` when no `repository` key is present, and this attacker-chosen string is used both to pick the `GitHubApp` (and therefore the `webhook_secret`) used for HMAC verification and, unverified, is persisted onto the new `Team` record by `MembershipHandler#find_or_create_team!`. Where a multi-organization Shipit deployment has an org configured without a `webhook_secret`, signature verification is vacuously true for any org name matching that config entry, letting an attacker create a `Team` row whose `organization`/`slug` match an entry in `Shipit.github_teams`, which is later trusted by `Team.find_or_create_by_handle` without re-validating against real GitHub data.

### Finding Description
Binding claimed broken: `organization.login` (used to select the `GitHubApp` and its `webhook_secret` in `verify_signature`) == `organization` value durably written onto `Team` by `team.organization = params.organization.login`.

- `repository_owner` returns `params.dig('repository','owner','login') || params.dig('organization','login')`, so for a `membership` event (which has no `repository` key) the attacker fully controls the value used to select the GitHub app config: ` [1](#0-0) `.
- `verify_signature` calls `Shipit.github(organization: repository_owner)` then `github_app.verify_webhook_signature(...)`: ` [2](#0-1) `.
- `verify_webhook_signature` returns `true` unconditionally when the resolved `GitHubApp`'s `webhook_secret` is blank: ` [3](#0-2) `.
- `Shipit.github` only ignores the `organization` argument (using the single top-level `secrets.github` config) when `github_default_organization` is `nil`, i.e. single-org mode; in multi-org mode it does `github_app_config(organization)` keyed strictly on the attacker-supplied org string, raising `GithubOrganizationUnknown` (→ HTTP 422) if that org isn't configured: ` [4](#0-3) `. So the attacker must name an org that is actually configured in `secrets.github`, but if that org entry has no `webhook_secret`, verification is bypassed entirely with no forgery needed.
- `MembershipHandler#find_or_create_team!` then does `Team.find_or_create_by!(github_id: params.team.id) { |team| team.github_team = params.team; team.organization = params.organization.login }`: ` [5](#0-4) `. `github_team=` also sets `slug` from the payload: ` [6](#0-5) `. If `github_id` doesn't already exist, this creates a brand-new `Team` row with attacker-chosen `organization`, `slug`, `name`, `api_url`, all taken verbatim from the unverified payload.
- `MembershipHandler#process` immediately calls `team.add_member(member)` for `action: 'added'`, adding the attacker's own GitHub login (also unverified, just `User.find_or_create_by_login!(params.member.login)`) as a member of this newly-created team: ` [7](#0-6) `.
- Separately, `Shipit.github_teams` (used by `User#authorized?`) resolves each configured `oauth_teams` handle via `Team.find_or_create_by_handle(handle)`, which does `find_by(organization:, slug:) || fetch_and_create_from_github(...)`: ` [8](#0-7) `, ` [9](#0-8) `. This lookup is purely by `organization`+`slug` string match against the `teams` table — it does not re-verify against GitHub if a row already exists. If the attacker's forged `Team` row (with matching `organization`/`slug`) is created before Shipit resolves that `oauth_teams` handle for the first time, the attacker's forged row — with the attacker already added as a member — becomes the "real" authorization team.
- `User#authorized?` then does `teams.where(id: Shipit.github_teams.map(&:id)).exists?`: ` [10](#0-9) `, so the attacker (now a member of the forged `Team`) is treated as authorized.

Existing guards do not stop this: `drop_unhandled_event`/`check_if_ping` don't apply to `membership`; the `ExplicitParameters` schema in `MembershipHandler` only validates types/presence, not the identity of `organization.login` against a trusted source; `verify_signature`'s only protection is the `webhook_secret` check, which is bypassed by design when that config key is absent for the targeted org.

Note: if `github_id` in the payload collides with an *existing* `Team` row, `find_or_create_by!` finds the existing record and the block (which sets `organization`) is **not** executed — so an attacker cannot overwrite an existing, already-verified team's `organization` this way. The exploitable path is specifically creating a **new** row whose `organization`+`slug` match a not-yet-resolved `Shipit.github_teams` entry.

### Impact Explanation
If exploited, an attacker becomes a member of a `Team` that `Shipit.github_teams` trusts for authorization, i.e. escalation into `Shipit.github_teams` authorization — matching the "High" impact category (escalation into `Shipit.github_teams` authorization). This affects any tenant/org whose `oauth_teams` handle hasn't yet been materialized as a `Team` row in the database, and repeats for as many `oauth_teams`/orgs as are similarly race-able. It does not directly grant RCE but grants a durable, DB-persisted authorization foothold usable in subsequent authenticated Shipit actions gated by `User#authorized?`.

### Likelihood Explanation
This requires a specific multi-organization Shipit deployment (`github_default_organization` non-nil, i.e. `secrets.github` keyed by multiple org names) with at least one configured org entry lacking a `webhook_secret`, and requires the attacker to know/guess that org's exact login string plus a target `oauth_teams` org/slug pair, and to win a race against the first legitimate resolution of `Shipit.github_teams` (which is memoized per-process once computed). This is a non-trivial but plausible operator-configuration-dependent scenario; it requires no secrets from the attacker, only knowledge of a public org/team slug and the fact that one configured org's webhook secret is unset — a genuine (if narrow) production misconfiguration surface enabled by `verify_webhook_signature`'s `return true unless webhook_secret` behavior.

### Recommendation
- In `verify_webhook_signature`, fail closed instead of vacuously succeeding when `webhook_secret` is blank for a resolved organization (`lib/shipit/github_app.rb`).
- In `MembershipHandler#find_or_create_team!` and `Team.find_or_create_by_handle`, do not trust webhook-derived `organization`/`slug`/`github_id` to create new authorization-relevant `Team` rows without cross-checking against a live GitHub API call (as `fetch_and_create_from_github` already does for the `oauth_teams` bootstrap path), or restrict `Team` creation via `membership` webhooks to organizations that have a verified `webhook_secret`.

### Proof of Concept
minitest sketch under `test/controllers/webhooks_controller_test.rb` and `test/models/shipit/team_test.rb` (not written here per scope, but the assertions needed):
1. Configure `secrets.github` in multi-org mode with two orgs: `secure-org` (has `webhook_secret`) and `unsecured-org` (no `webhook_secret`).
2. POST a `membership` event to `/webhooks` with `X-Github-Event: membership`, no `X-Hub-Signature` needed, body: `{"action":"added","team":{"id":<unused_id>,"name":"Deployers","slug":"deployers","url":"..."},"organization":{"login":"unsecured-org"},"member":{"login":"attacker"}}`.
3. Assert response is `200 OK` (verification bypassed) and assert `Shipit::Team.find_by(github_id: <unused_id>).organization == "unsecured-org"` and `.slug == "deployers"` — i.e. the unverified payload value was durably persisted as claimed by the binding.
4. Configure `Shipit.oauth_teams` (or the relevant org's `oauth.teams`) to include `"unsecured-org/deployers"` and assert `Shipit.github_teams` resolves to this attacker-seeded `Team` (via `find_by(organization:, slug:)`) rather than fetching from GitHub, and that `User.find_by(login: "attacker").authorized?` returns `true`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
