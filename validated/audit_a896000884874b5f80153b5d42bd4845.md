This is a confirmed finding: `Shipit::Api::CCMenuController` resolves the target stack directly from the URL parameter without ever checking it against the scope of the authenticated `ApiClient`, unlike the sibling `Shipit::Api::StacksController` (and `BaseController#stacks`) which restrict lookups to `current_api_client.stack_id` when the client is stack-scoped.

### Title
Stack-scoped API tokens can read any stack's build/deploy status via the CCMenu endpoint - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`BaseController#stacks` correctly enforces that a stack-scoped `ApiClient` can only see the stack it was minted for: `current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all` [1](#0-0) . However, `Shipit::Api::CCMenuController` overrides the `stack` accessor to bypass this scoping entirely and resolve the stack straight from the request parameter: `def stack; @stack ||= Stack.from_param!(params[:stack_id]); end` [2](#0-1) , while only enforcing the generic, non-scoped permission check `require_permission :read, :stack` [3](#0-2) .

### Finding Description
`ApiClient` records can be scoped to a single stack via `belongs_to :stack, optional: true` [4](#0-3) , and `check_permissions!` only validates the coarse `operation:scope` string (e.g. `read:stack`), never the specific stack id: `unless permissions.include?(required_permission); raise InsufficientPermission ...` [5](#0-4) . The intended enforcement of "this token may only touch its own stack" lives entirely in `BaseController#stacks`/`#stack` (`stacks.from_param!(params[:stack_id])`) [6](#0-5) , and is correctly used by `Api::StacksController#show` via `stacks.from_param!(params[:id])` [7](#0-6) .

`CCMenuController` breaks this binding: it authenticates the client (any client that authenticates and holds the `read:stack` permission string, regardless of which stack it was created for) and then fetches `Stack.from_param!(params[:stack_id])` unscoped [2](#0-1) . This mirrors the reported bug class exactly: "a stack a token authorises versus a stack it touches" — the token is authorized (by permission bit) for `read:stack` in the abstract, but the `stack_id` it is bound to at creation is never checked against the `stack_id` param it actually acts on.

This is concretely reachable because CCMenu tokens are routinely created and handed out per-stack for third-party CI dashboard tools: `CCMenuUrlController#client` creates `ApiClient.create_with(permissions: %w[read:stack]).find_or_create_by!(creator: current_user, name: 'CCMenu Client')` [8](#0-7) , and the resulting token is embedded directly in a URL served back to the browser: `uri.query = { 'token' => client.authentication_token }.to_query` [9](#0-8) . Because that URL/token is designed to be pasted into external, less-trusted CCMenu-compatible tooling, it is treated as low-privilege and stack-specific by design — but the controller doesn't actually restrict it to that stack.

### Impact Explanation
Holding one legitimately-issued, stack-scoped CCMenu token (`read:stack` permission, `stack_id` set to stack A) is sufficient to read the latest deploy/rollback status, exit code, and duration of **any** stack in the Shipit instance by simply changing `stack_id` in the request path, since `ApiClient.authenticate(params[:token])` succeeds and `require_permission :read, :stack` only checks the permission bit, not the bound `stack_id` [10](#0-9) . This matches the "High - unauthenticated/unauthorized read of stack state, task streams or deploy output" impact bucket, since it grants cross-stack read access to deploy status information using a credential that was only ever authorized for one specific stack.

### Likelihood Explanation
High. No special privilege is required beyond possessing any single stack-scoped CCMenu token — which is explicitly designed to be shared with low-trust, external tooling (`ccmenu_url_controller.rb`). The attack is a trivial parameter substitution (`stack_id` in the URL) requiring no additional credentials, signature forgery, or session access.

### Recommendation
In `CCMenuController#stack`, resolve the stack through the scoped `stacks` collection (as `Api::StacksController` and `BaseController` do) instead of the unscoped `Stack.from_param!`, e.g.:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
so that `current_api_client.stack_id?`-scoped clients are rejected (via `stacks.from_param!` raising a not-found) when requesting a `stack_id` outside their bound stack.

### Proof of Concept
1. As a legitimate stack owner, visit stack A's CCMenu URL page; the app creates (or reuses) an `ApiClient` scoped to stack A with `permissions: ['read:stack']` and returns a URL containing `token=<A's token>` [8](#0-7) .
2. Take that token and issue: `GET /api/stacks/<stack-B-id>/ccmenu.xml?token=<A's token>` where stack B is any other stack on the instance.
3. `CCMenuController#authenticate_api_client` authenticates the token successfully (`ApiClient.authenticate(params[:token])`) [11](#0-10) , `require_permission :read, :stack` passes because the token has `read:stack` in its permission list, and `stack` resolves stack B unconditionally via `Stack.from_param!(params[:stack_id])` [2](#0-1) , returning stack B's deploy/rollback status even though the token was only ever bound to stack A.
