### Title
Flawed share-minting logic in the reference Uniswap-like AA pattern lets a trigger sender dilute/steal pool shares from other depositors - (File: test/samples/uniswap_like_market_maker.oscript)

### Summary
The `uniswap_like_market_maker.oscript` sample shipped in ocore (used as the canonical reference pattern for building a pooled-liquidity AA and validated by `test/ojson.test.js`) mints `mm_asset` shares using a check that can be satisfied by a partial, rather than a true, empty-pool state. This mirrors the classic "inflation attack" bug class described in the report: a naive share-minting formula that fails to correctly account for pre-existing pool value lets one depositor mint shares that do not correspond to their real contribution, at the expense of other depositors' claims on `balance[base]`/`balance[$asset]`.

### Finding Description
In the "invest in MM" case, share issuance is computed as: [1](#0-0) 

```
$asset_balance = balance[$asset] - trigger.output[[asset=$asset]];
$bytes_balance = balance[base] - trigger.output[[asset=base]];
if ($asset_balance == 0 OR $bytes_balance == 0){ // initial deposit
    $issue_amount = balance[base];
    return;
}
```

The condition uses `OR` instead of `AND`, and the "initial deposit" branch sets `$issue_amount` equal to the *entire post-deposit* `balance[base]`, without reference to the existing `mm_asset_outstanding` shares or to the value already held in `$asset`. This branch is meant to fire only when the pool is genuinely empty (both reserves are zero, i.e. no shares are outstanding), but it also fires whenever *either* side of the pool has been driven to zero while the other side still holds real value — a state reachable through the normal, legitimate "exchange" cases: [2](#0-1) 

Once `mm_asset_outstanding` exists but `$bytes_balance` (or `$asset_balance`) has been traded down to zero, a subsequent "investor" can trigger the initial-deposit branch again, minting new shares equal to just the freshly deposited bytes while ignoring the value already owned by existing shareholders in the other asset: [3](#0-2) 

`var['mm_asset_outstanding'] += $issue_amount;` simply adds the newly minted, mispriced shares to the total supply. Because "divest MM shares" pays out a proportional share of *both* `balance[$asset]` and `balance[base]` based on `mm_asset_amount / var['mm_asset_outstanding']`: [4](#0-3) 

the attacker's disproportionately large new share count entitles them to redeem more of the pool's pre-existing reserve than their actual deposit was worth, diluting/stealing value from earlier depositors — the same fund-loss outcome described in the `StakePet` inflation-attack report, just triggered by a share-accounting edge case instead of a direct balance donation.

### Impact Explanation
Any address able to send a trigger to an AA deployed from this reference pattern (an ordinary AA trigger sender) can manipulate the pool into a one-sided-reserve state via normal trades, then re-enter through the flawed "initial deposit" branch to mint shares that do not reflect the pool's true value. Subsequent redemption lets the attacker claim assets contributed by other depositors, resulting in concrete AA fund loss for legitimate liquidity providers — matching the High severity of the original inflation-attack finding.

### Likelihood Explanation
Because this oscript is shipped in the repository as the documented example for building pooled/AMM-style AAs, any developer following it verbatim in production reproduces the flaw. Reaching the required "one side of the pool is zero while the other still holds value" state only requires ordinary use of the already-implemented "exchange bytes to asset" / "exchange asset to bytes" cases, so no privileged access is needed — only a series of ordinary triggers from an unprivileged AA trigger sender.

### Recommendation
- Use `AND` instead of `OR` so the "initial deposit" branch only fires when both `$asset_balance == 0` and `$bytes_balance == 0`, i.e., when `var['mm_asset_outstanding']` is also zero/unset.
- Explicitly guard the branch with `!var['mm_asset_outstanding']` rather than inferring "no shares" purely from a single reserve reaching zero.
- Never mint shares proportional to raw `balance[base]`; always compute new shares relative to the pool's total value (including both reserves) and existing `mm_asset_outstanding`, as already done correctly in the non-initial branch.

### Proof of Concept
1. AA author deploys an AA using this exact `uniswap_like_market_maker.oscript` pattern; user Alice performs the legitimate initial deposit, receiving `mm_asset` shares equal to her deposited bytes, with the pool holding both `base` and `$asset`.
2. Attacker repeatedly uses the "exchange asset to bytes" case (`trigger.output[[asset=$asset]] > 0`) to buy up all of the pool's `base` reserve with `$asset`, driving `balance[base]` (net of this trigger's own output) down to 0 while `$asset` reserve remains valuable and `var['mm_asset_outstanding']` is still non-zero (Alice's shares still outstanding).
3. Attacker then calls "invest in MM" with `trigger.output[[asset=base]] > 1e5` and `trigger.output[[asset=$asset]] > 0`; since `$bytes_balance == 0` (post-drain state), the `OR` condition is satisfied and the code executes the "initial deposit" branch, setting `$issue_amount = balance[base]` (the attacker's own new deposit) and adding it on top of Alice's still-existing shares — without regard to the sizeable `$asset` reserve Alice's shares are entitled to.
4. Attacker calls "divest MM shares," redeeming their newly minted shares for a proportional cut of `balance[$asset]` and `balance[base]`, extracting value that rightfully belonged to Alice's original deposit.
