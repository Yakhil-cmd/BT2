### Title
Cross-repository forged commit statuses via `StatusHandler` bypassing per-organization webhook trust boundary - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to validate an inbound webhook against by reading the *unverified* `repository.owner.login` field straight out of the JSON payload, then validates the HMAC using that organization's own secret. Once the signature check passes, `Shipit::Webhooks::Handlers::StatusHandler#process` acts on the commit `sha` from the same payload with **no repository/organization scoping at all**, unlike sibling handlers (e.g. `PushHandler`) which restrict effects to `stacks` derived from the payload's `repository.full_name`. This breaks the binding "organization that authenticated == repository that is written": an attacker who legitimately controls (or knows) the `webhook_secret` for *any one* configured GitHub organization/app in a multi-org Shipit deployment can forge a `status` event that is authenticated against their own org's secret, but whose `sha` targets a commit belonging to an entirely different repository/stack, injecting an arbitrary CI status for it.

### Finding Description
Signature verification in `app/controllers/shipit/webhooks_controller.rb` is performed like this: [1](#0-0) 

The organization used to select the correct `webhook_secret` (`repository_owner`) is taken directly from the untrusted JSON body: [2](#0-1) 

Shipit explicitly supports multiple independent GitHub Apps/organizations, each with its own `webhook_secret`, all funneled through the same `WebhooksController#create` endpoint: [3](#0-2) [4](#0-3) 

So the HMAC only proves "this request was signed with organization X's webhook secret" — it says nothing about which repository the payload's other fields (like `sha`) may reference. Handlers are expected to further scope their side effects to the repository named in the payload, exactly as `Handler#stacks`/`#repository_name` does: [5](#0-4) 

and as `PushHandler` correctly does: [6](#0-5) 

However, `StatusHandler` never consults `stacks`/`repository_name` at all — it looks up commits globally by `sha` across the entire Shipit instance and writes a status onto every match: [7](#0-6) 

Because git commit SHAs are content hashes, not secrets (they are visible in GitHub UI, PR diffs, CI logs, and often shared across forks/mirrors that are tracked as separate Shipit `Stack`s pointing at different `Repository`/organization records), a payload signed and authenticated as belonging to organization X can carry a `sha` that actually belongs to a `Commit` row tied to a stack under organization Y. `StatusHandler` will happily write a forged status (`state`, `context`, `description`, `target_url`) onto that commit, even though nothing about organization Y's repository was ever verified by the signature that authorized the request.

This is the binding-break called out by the rules: "an organization that authenticated versus the repository that is written."

### Impact Explanation
Commit statuses drive deploy-gating logic in Shipit (CI requirements for deployability, merge-queue merges, and continuous-deployment auto-triggering are all keyed off `Commit` status records populated by this exact handler). An attacker who is a legitimate (unprivileged w.r.t. other tenants) integrator on one configured GitHub organization — i.e., they only have the webhook secret for their own org's installed GitHub App, not for the target org/repo — can forge a "success" status for a commit belonging to a stack in a different organization/repository tracked by the same Shipit instance. If that stack has `continuous_deployment` enabled or CI-gated merges, the forged status can unblock an automatic deploy or a merge-queue merge for a repository/org the attacker has no legitimate access to, which is an unauthorized deploy/merge — the kind of cross-tenant, cross-repository write called out as High/Critical impact.

### Likelihood Explanation
Medium: it requires (a) a Shipit deployment configured with multiple GitHub organizations/apps (an explicitly documented and supported configuration), (b) the attacker already possessing a valid `webhook_secret` for at least one of those organizations (their own installed app — not a privileged secret for the victim org), and (c) the attacker knowing or guessing a target commit SHA belonging to another tracked repository (readily discoverable since SHAs are public in GitHub UI/PRs/CI logs, and could also be enumerated via any stack's commit history pages if Shipit itself exposes them).

### Recommendation
`StatusHandler` (and any other handler that does not currently use `Handler#stacks`) should scope its `Commit` lookup to commits belonging to the repository named in the same payload (`payload.dig('repository', 'full_name')`), matching the pattern already used by `PushHandler`. Additionally, `WebhooksController#verify_signature` should not allow the org used for authentication to silently diverge from the org actually acted upon by handlers — at minimum, handlers must independently re-derive and enforce the repository scope from the verified payload rather than trusting a global, unscoped side effect.

### Proof of Concept
1. Configure Shipit with two organizations, `OrgA` and `OrgB`, each with a distinct `webhook_secret` (per `docs/setup.md`'s multi-org config schema).
2. Attacker has legitimate access to `OrgA`'s GitHub App and therefore knows `OrgA`'s `webhook_secret`.
3. Attacker learns a commit SHA `deadbeef...` that Shipit has tracked as a `Commit` belonging to a stack under `OrgB` (e.g., from GitHub UI, a public PR, or CI logs).
4. Attacker POSTs to `/github/webhooks` with header `X-Github-Event: status`, body:
```json
{
  "sha": "deadbeef...",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgA/some-repo" }
}
```
5. `WebhooksController#verify_signature` resolves `repository_owner` = `OrgA`, computes HMAC with `OrgA`'s secret (which the attacker knows), and the signature validates.
6. `StatusHandler#process` runs `Commit.where(sha: 'deadbeef...')`, finds the `Commit` under `OrgB`'s stack, and calls `create_status_from_github!`, writing a forged "success" status onto it — despite the request never being authenticated by anything belonging to `OrgB`. [8](#0-7) [9](#0-8)

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

# frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class StatusHandler < Handler
        params do
          requires :sha, String
          requires :state, String
          accepts :description, String
          accepts :target_url, String
          accepts :context, String
          accepts :created_at, String

          accepts :branches, Array do
            requires :name, String
          end
        end

        def process
          Commit.where(sha: params.sha).each do |commit|
            commit.create_status_from_github!(params)
          end
        end
      end
    end
  end
