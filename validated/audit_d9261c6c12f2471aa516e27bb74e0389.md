### Title
Cross-repository Status/CI forgery via unscoped `Commit.where(sha:)` lookup in `StatusHandler` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` resolves the target commit purely by SHA (`Commit.where(sha: params.sha)`) with no filter on the repository that the verified webhook payload names, unlike the base `Handler` class which exposes a `stacks`/`repository_name` scoping helper specifically for this purpose. Because the GitHub webhook signature is verified per-organization (`Shipit.github(organization: repository_owner)`) rather than per-repository, any repository owner within that organization can post a validly-signed status webhook naming their own repository while supplying a `sha` belonging to a different (victim) stack's commit, causing Shipit to attach a forged `Status` (state/description/target_url/context) to that victim commit.

### Finding Description
The binding the question assumes is:
`stack.updated_at touched by Status insert == stack owning payload['repository']['full_name']`.

Tracing the code shows this binding is **not enforced**:

- `WebhooksController#verify_signature` only checks the HMAC signature against the webhook secret configured for `repository_owner` (the organization named in the payload), via `Shipit.github(organization: repository_owner).verify_webhook_signature(...)` [1](#0-0) . This proves the request came from *some* repo/app installation belonging to that organization — not that it came from the specific repository the payload claims, and not that the sha it names belongs to that repository.
- `Handler` defines `stacks`/`repository_name` helpers explicitly meant to scope processing to the repository named in the payload [2](#0-1) , but `StatusHandler#process` does not use them at all:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [3](#0-2) 
This is a global, cross-stack lookup by `sha` alone — any `Commit` row in the entire database matching that SHA (regardless of which stack/repository it belongs to) receives the forged status.
- `Commit#create_status_from_github!` then creates a real `Status` record scoped to that commit's actual `stack_id`: `statuses.replicate_from_github!(stack_id, github_status)` [4](#0-3) .
- `Status` declares `deferred_touch commit: :updated_at` [5](#0-4) , and `Commit` declares `deferred_touch stack: :updated_at` [6](#0-5) , so the touch chain reaches the victim stack exactly as the question describes — confirming the timestamp propagation.

Exploit flow: the attacker owns/administers a repository within the same GitHub organization/App installation as the victim's Shipit-tracked stack (satisfying "emit webhooks from a repository they own" — the webhook secret is per-organization/app-installation, not per-repository). SHA1 git commit hashes are content-derived and public; the attacker fetches the victim's public commit SHA and crafts a `status` webhook payload naming their own repository in `repository.full_name` but with `sha` set to the victim's commit SHA and an arbitrary `state`/`description`/`context`. GitHub (or the attacker directly posting to `/webhooks` with a correctly HMAC-signed body using the org's webhook secret they legitimately received for their own repo) signs it. `verify_signature` passes because it only checks the organization-level secret. `StatusHandler` then finds the victim's `Commit` by SHA regardless of repository and writes a forged `Status` onto it.

This is not merely a covert timestamp channel: `Commit#add_status` reacts to the forged status by potentially calling `stack.schedule_merges` and scheduling `ContinuousDeliveryJob` when the forged state is `success`/`pending` [7](#0-6) , and `deployable?` depends on `success?` [8](#0-7) . A forged "success" status can therefore make an otherwise-blocked victim commit deployable and trigger continuous delivery on a stack the attacker never authenticated against — this is a payload for one repository mutating another repository's stack/commit state, and potentially triggering an unauthorized deploy.

None of the listed guards prevent this: `verify_signature` checks only the org-level HMAC, not repository identity; `drop_unhandled_event` only filters unknown event types; the `ExplicitParameters` schema (`params do requires :sha ... end`) only validates payload shape, not repository ownership of the SHA; there is no `require_permission!`/`stacks` scoping applied in `StatusHandler#process`.

### Impact Explanation
An attacker who controls any repository within an organization sharing Shipit's webhook secret for that org can write arbitrary `Status` rows (state, description, target_url, context) onto commits belonging to a completely different, victim stack in the same org, without ever authenticating against that victim's repository. Consequences: (1) covert/forced staleness of `updated_at` as described in the question, and more importantly (2) forged CI state that can flip `deployable?`/`blocked?` outcomes and trigger `ContinuousDeliveryJob`/`schedule_merges` on the victim stack — i.e., a payload for one repository mutating another repository's stack/commit and potentially causing an unauthorized deploy. This matches the Critical category "a payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy." The attack is repeatable against any commit SHA the attacker can learn (all public commit SHAs are known) as long as both repos share an org/app-installation webhook secret.

### Likelihood Explanation
Preconditions: the attacker must own/administer a repository within the same GitHub organization (or App installation) as the victim stack, since `verify_webhook_signature` is keyed by `repository_owner` (the organization), not by individual repository — this is a realistic setup for any multi-repo GitHub organization using a single GitHub App/webhook secret, which is the default Shipit GitHub App model. The attacker needs no Shipit session, API token, or GitHub App secret of their own beyond what GitHub itself provides them for their own repository's webhook delivery, and needs only the victim's public commit SHA. Crafting and posting the forged payload to `/webhooks` requires only standard HTTP tooling once they have webhook delivery access for their own repo (or intercept/replicate a legitimately-signed delivery, which is standard GitHub App behavior, not a secret leak). This is a low-cost, repeatable attack.

### Recommendation
Scope `StatusHandler#process` (and any other handler resolving records solely by attacker-influenced identifiers like `sha`) to the repository named in the verified payload, using the existing `stacks`/`repository_name` helper: e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` or equivalent, so a commit is only updated if it belongs to a stack whose repository matches `payload['repository']['full_name']`. More broadly, webhook signature verification should be strengthened to also validate that the named `repository.full_name` in the payload actually corresponds to the installation/organization that produced the signature, rather than trusting organization-level secrets to authorize repository-scoped writes.

### Proof of Concept
```ruby
# test/models/webhooks/handlers/status_handler_test.rb (conceptual, no live GitHub)
test "cross-repo status webhook mutates an unrelated victim stack's commit/stack" do
  victim_stack = shipit_stacks(:shipit)
  victim_commit = victim_stack.commits.create!(sha: 'a' * 40, message: 'victim commit')
  attacker_repo_payload = {
    'sha' => victim_commit.sha,
    'state' => 'success',
    'repository' => { 'full_name' => 'attacker-org/attacker-repo', 'owner' => { 'login' => 'attacker-org' } }
  }

  before = victim_stack.updated_at

  Shipit::Webhooks::Handlers::StatusHandler.call(attacker_repo_payload)

  victim_stack.reload
  assert_not_equal before, victim_stack.updated_at
  assert victim_commit.statuses.exists?(state: 'success'),
         "forged status from an unrelated repository was written onto the victim commit"
end
```
This demonstrates that `payload['repository']['full_name']` (attacker's own repo) never matches `victim_stack`'s repository, yet the victim stack's `updated_at` changes and a real `Status` row is written — confirming the claimed binding is broken.
