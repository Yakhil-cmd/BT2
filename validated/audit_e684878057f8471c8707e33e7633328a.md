### Title
Cross-Repository Webhook Confusion via Organization/Repository Binding Mismatch - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App configuration (and thus which HMAC secret) to verify a webhook against using `repository_owner`, taken from `params.dig('repository', 'owner', 'login')` [1](#0-0) , while the field that actually determines which `Stack`/`Repository` the event is applied to is `repository_name = payload.dig('repository', 'full_name')`, read independently inside `Handler#stacks` [2](#0-1) . Both fields live in the same attacker-supplied JSON body and are never cross-checked against each other, breaking the equality "organization authenticated == repository written."

### Finding Description
The controller resolves the signing organization purely from `repository.owner.login` (or `organization.login`) and fetches that organization's `GitHubApp` instance via `Shipit.github(organization: repository_owner)` [3](#0-2) . `GitHubApp#verify_webhook_signature` explicitly returns `true` without checking any HMAC when that organization's configured `webhook_secret` is blank: `return true unless webhook_secret` [4](#0-3) . `webhook_secret` is documented as optional per-organization configuration ("If you've set a webhook secret during the App creating, you should copy it here") [5](#0-4) , and Shipit natively supports multiple GitHub App configs for multiple organizations, as shown by the dedicated multi-app fixture `test/dummy/config/secrets_double_github_app.yml`.

Once signature verification passes for the "owner" organization, `WebhooksController#create` dispatches the parsed JSON to the handler unconditionally: `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` [6](#0-5) . Inside `PushHandler`, the actual `Stack`s that get mutated are resolved from `repository.full_name` — a completely separate field from the one used for signature selection — via `Repository.from_github_repo_name(repository_name)&.stacks` [2](#0-1) , then `stack.sync_github(expected_head_sha: params.after)` is invoked on every matching stack [7](#0-6) .

Because nothing enforces `repository.owner.login == repository.full_name.split('/').first`, an attacker who knows (or guesses) that some organization configured in the Shipit instance has no `webhook_secret` set can spoof `repository.owner.login` to that organization while setting `repository.full_name` to a victim organization's repository. The signature check trivially passes (no secret to verify against), yet the event is applied to the victim's stacks.

### Impact Explanation
This allows an unauthenticated, unprivileged attacker (holding no webhook secret, GitHub token, or repository access) to inject forged `push` events attributing an arbitrary `after` SHA to a victim organization's stack, function through `Stack#sync_github`, and — where continuous deployment is enabled — trigger deployment of an attacker-chosen (but already-existing) commit SHA without ever proving push access to that repository. This falls under the "unauthorized deploy/rollback" Critical impact category, since it bypasses the repository-ownership boundary the signature check is meant to enforce.

### Likelihood Explanation
Exploitability depends on at least one organization configured in the Shipit instance's multi-org GitHub App setup lacking a `webhook_secret` (a supported and documented configuration, not a hardening violation of the engine's mounting contract). In single-tenant deployments with one required secret this path is not exploitable, since the attacker still needs to forge a valid HMAC over the raw body with an unknown secret. The vulnerability is therefore concrete but conditioned on multi-organization deployments where at least one org's app config omits a webhook secret — a state the engine's own code explicitly tolerates (`return true unless webhook_secret`).

### Recommendation
Cross-validate that `repository.owner.login` (used to select the verifying `GitHubApp`) matches the owner portion of `repository.full_name` (used to select the target `Stack`) before dispatching to handlers, and/or require a `webhook_secret` for every configured organization, rejecting webhook delivery for any organization lacking one instead of auto-passing signature verification.

### Proof of Concept
Given a Shipit instance configured with two GitHub App organizations — `org-no-secret` (no `webhook_secret`) and `victim-org` (has stacks and a secret the attacker doesn't know) — the attacker POSTs to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "repository": {
    "owner": { "login": "org-no-secret" },
    "full_name": "victim-org/victim-repo"
  },
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-existing-sha>"
}
```
`repository_owner` resolves to `org-no-secret`, whose `GitHubApp#verify_webhook_signature` returns `true` unconditionally [8](#0-7) . `PushHandler` then resolves stacks from `victim-org/victim-repo` [9](#0-8)  and calls `sync_github(expected_head_sha: "<attacker-chosen-existing-sha>")` on every matching victim stack [7](#0-6) .

      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
