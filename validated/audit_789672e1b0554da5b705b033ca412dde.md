### Title
Cross-repository status forgery causes unauthorized continuous deployment - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`, `app/models/shipit/stack.rb`)

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` looks up commits to attach a GitHub status to purely by `sha`, with no check that the webhook's `repository` matches the commit's own stack/repository. Combined with `Stack#trigger_continuous_delivery` → `next_commit_to_deploy` → `deployable?`, a status event that is validly signed for one repository (Repo A) but whose `sha` collides with a commit that also exists under a different stack (Repo B) can flip Repo B's commit to `deployable?` and trigger an unauthorized deploy with `Shipit.user` as the actor.

### Finding Description
The broken binding: the code implicitly assumes `commit.stack == webhook.repository`, but nothing enforces `params.dig('repository','full_name') == commit.stack.repository.full_name`.

Path:
1. `Shipit::WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-38`) only validates the HMAC signature against the secret for `repository_owner` (`params.dig('repository','owner','login')`). It never checks that the sha inside the payload actually belongs to that repository.
2. `Shipit::Webhooks::Handlers::StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`) does:
   ```ruby
   Commit.where(sha: params.sha).each do |commit|
     commit.create_status_from_github!(params)
   end
   ```
   This is a *global* lookup by `sha` across the entire `commits` table, not scoped to the stack/repository named in the webhook payload. The unique index on `commits` is `(sha, stack_id)` (`db/migrate/20170524104615_index_commits_on_stack_id_and_sha.rb`), which explicitly permits the *same* sha to exist under multiple different `stack_id`s (multiple stacks/repos can contain a commit with an identical sha).
3. `Commit#create_status_from_github!` → `#add_status` (`app/models/shipit/commit.rb:365-386`) updates commit status and, on a state transition to non-pending, emits `deployable_status` and calls `stack.schedule_merges`, which eventually triggers `ContinuousDeliveryJob` → `Stack#trigger_continuous_delivery`.
4. `Stack#trigger_continuous_delivery` (`app/models/shipit/stack.rb:210-229`) calls `next_commit_to_deploy`, which relies on `Commit#deployable?`/status state that was just set by the forged webhook, and if satisfied calls `trigger_deploy(commit, Shipit.user, env: cached_deploy_spec.default_deploy_env)` — creating a real `Deploy` and eventually invoking `Command#start` with the app's own `GITHUB_TOKEN`/`GIT_ASKPASS` against Repo B's deploy host.

Root cause: status ingestion trusts `sha` alone as the join key to commits, with no cross-check against the webhook's own repository/stack, even though `sha` is not guaranteed unique across stacks (by design, per the composite index).

Existing guards do not prevent this: `verify_signature` authenticates the *organization* of the incoming payload, not that the referenced `sha` belongs to a commit under that same repository; `drop_unhandled_event` and `ExplicitParameters` schema in `StatusHandler` only validate the type of `sha`/`state`, not repository scoping.

### Impact Explanation
An attacker who controls a commit-sha collision (e.g., by replicating an existing public commit's exact object bytes into a repository they control, achievable because git commit hashes are computable/reproducible when tree/parent/author/committer/message/timestamps are copied) can cause a `Status` record — and consequently a `deployable_status` transition — to be created for a commit belonging to an entirely different stack/repository than the one that authenticated the webhook. If that target stack has `continuous_deployment: true`, this results in `Deploy.count` increasing for that stack, with `Shipit.user` (not any real operator of that repo) as the deploying user, and a real `Command#start` invocation using that stack's own `git_url`/env against its deploy host. This is a cross-tenant authorization bypass and unauthorized deploy — Critical severity per the stated impact categories ("a payload for one repository mutating another's stack, commit, task... an unauthorized deploy").

### Likelihood Explanation
I was **not able to fully verify** within available tool budget whether this Shipit instance's webhook-signature scheme is single-organization-secret (one secret shared by all repos owned by that org, in which case the attacker only needs *any* other repo in the same org to exploit this) or fully per-repository. I confirmed `Shipit.github(organization: repository_owner)` and `verify_webhook_signature` are keyed by `repository_owner`/organization (`app/controllers/shipit/webhooks_controller.rb:25-30`), not by individual repository, which supports the "any repo in the same org" exploitation path, but I could not inspect `lib/shipit/github_app.rb`'s `verify_webhook_signature` implementation in this session to confirm whether it uses a single shared secret across all repos of that org/installation or something more granular. This materially affects likelihood: if it's org-scoped, exploitation only requires the attacker to control (or push a colliding commit into) any one other repository within the same GitHub org/installation as the victim stack — a moderate-cost, plausible scenario in shared-org GitHub App setups. If it is genuinely per-repo-secret with no sharing, the attacker would need to compromise/own the specific target org's app installation, which is out of scope for an unprivileged attacker.

### Recommendation
Scope the `StatusHandler#process` (and equivalent `CheckSuiteHandler`, `push`, etc. status-touching handlers) lookup to commits whose `stack.repository` matches the webhook's `params.dig('repository', 'full_name')` (and owner), e.g.:
```ruby
def process
  Commit.joins(:stack).merge(Stack.for_repository(params.dig('repository','full_name'))).where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
This closes the gap where a sha collision across repositories can inject a status onto an unrelated stack.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (conceptual addition)
test "a status webhook for repo A cannot mark repo B's colliding-sha commit deployable and trigger CD" do
  GithubHook.any_instance.stubs(:verify_signature).returns(true)

  repo_b_stack = shipit_stacks(:shipit) # continuous_deployment: true
  repo_b_commit = repo_b_stack.commits.create!(sha: 'deadbeef' * 5, ...)

  # payload claims to be for a totally different repository ("attacker/repo-a")
  # but carries the same sha as repo_b_commit
  payload = {
    'sha' => repo_b_commit.sha,
    'state' => 'success',
    'context' => 'ci/travis',
    'branches' => [{ 'name' => 'master' }],
    'repository' => { 'full_name' => 'attacker/repo-a', 'owner' => { 'login' => 'attacker' } }
  }.to_json

  request.headers['X-Github-Event'] = 'status'

  Command.any_instance.expects(:start).never # should NOT deploy repo B off repo A's webhook

  assert_no_difference -> { Deploy.where(stack_id: repo_b_stack.id).count } do
    post :create, body: payload, as: :json
  end
end
```
This test currently would **fail** (i.e., demonstrate the bug) against the unpatched `StatusHandler#process`, because `Commit.where(sha: params.sha)` matches `repo_b_commit` regardless of the `repository` field in the payload, allowing the status/CD chain to fire for `repo_b_stack`.
