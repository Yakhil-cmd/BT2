### Title
AA Trigger Sender Can Manipulate the `timestamp` Keyword by Choosing an Old `last_ball`, Bypassing Time-Locked AA Logic - (File: `formula/evaluation.js`)

### Summary
The `timestamp` keyword available to oscript/AA formulas does not reflect real wall-clock time at the moment of trigger evaluation; it is set to `objValidationState.last_ball_timestamp`, i.e., the timestamp of whatever `last_ball_unit` the trigger unit's author chose to reference when composing the unit.

### Finding Description
When an AA formula evaluates `timestamp`, the evaluator simply returns `objValidationState.last_ball_timestamp`: [1](#0-0) 

That value is populated during unit validation from the `last_ball_unit` referenced by the *unit itself* (chosen by whoever composed the triggering unit, i.e., an ordinary AA trigger sender), not from `Date.now()`: [2](#0-1) 

The only constraint on how "stale" this referenced `last_ball` may be is a non-retreat check relative to the sender's own parent units — the composer/validator only requires that the chosen `last_ball_mci` not be lower than the maximum `last_ball_mci` already included by the parent units: [3](#0-2) 

Nothing enforces that the referenced `last_ball` is the most recent available stable unit, or that its timestamp is close to real time, beyond this weak monotonicity constraint. Meanwhile the AA `mci`/`timestamp` keywords are explicitly documented and used by AA developers as deadline/maturity/expiry gates in real contract templates shipped in this repo, e.g.:
- Futures contract: `if (timestamp < 1556668800) bounce('wait for maturity date');` and blackswan gating `... AND timestamp < 1556668800` [4](#0-3) [5](#0-4) 
- Option contract: outcome resolution gated by `timestamp > 1556668800` [6](#0-5) 
- ICO with milestones: `trigger.data.finish AND (trigger.address == $control_address OR timestamp > $expiry_ts)` [7](#0-6) 

This is the structural analog of the reported "`block.timestamp` as swap deadline" issue: in both cases, a party who controls how a transaction/unit references the chain's time source (miner picking `block.timestamp`; here, the AA trigger *sender* picking which stable `last_ball` unit to reference) can steer the effective "current time" seen by contract logic within the tolerance the protocol permits, in order to satisfy or defeat a time-based condition that should reflect the real current moment.

Unlike the Solidity report (where the deadline only bounds transaction inclusion time and manipulation range is a few seconds of miner discretion), here the discretion is potentially much larger: a sender can choose an older-but-still-valid `last_ball_unit` (as long as it does not retreat below what their own parent units already commit to), giving them a wider window to pick a `timestamp` value that is convenient for satisfying/evading a deadline check (e.g., sneaking in before an expiry, or claiming a maturity/blackswan condition was already met when real time had not yet reached it, or vice versa delaying to a favorable oracle/data_feed reading window combined with `timestamp` gating).

### Impact Explanation
AA templates that gate fund release, milestone payments, contract maturity, or "blackswan"/outcome resolution on `timestamp` comparisons can be triggered earlier or later than the contract author intended by a trigger sender who deliberately selects an unfavorable-for-others but still protocol-valid `last_ball`. This can lead to premature release of escrowed/milestone funds, premature or delayed contract settlement combined with stale oracle data windows, or bypass of "wait until maturity" guards — i.e., concrete AA fund loss/incorrect settlement, which is the class of impact this analog scan requires (AA fund loss or freezing).

### Likelihood Explanation
Any address can freely construct and post a trigger unit; choosing which valid `last_ball_unit` to reference is a normal, permitted step of unit composition available to every ordinary user via `composer.js`/`parent_composer.js`, not a privileged or malicious-node action. Any AA that uses `timestamp` for a deadline/expiry/maturity check (a documented and commonly used pattern, as shown by the sample contracts bundled with the codebase) is potentially exposed. The main uncertainty is the practically achievable "staleness" window in a live, busy DAG (which likely bounds how old a still-non-retreating `last_ball` can be) — this was not fully verified from the accessible code paths and would need empirical/network-level analysis to quantify precisely.

### Recommendation
- For AA formulas, avoid relying solely on `timestamp` (last-ball-derived) for security-critical deadline/maturity logic; consider also bounding by `mci` proximity to `number_of_responses`/current known MC height, or requiring the referenced `last_ball_mci` to be within a small delta of the most recent stable MCI.
- Consider tightening the last-ball selection constraint in `validateParents` (`validation.js`) so that a unit's `last_ball_mci` cannot lag far behind the best known stable MCI, reducing the sender's freedom to pick a favorable historical timestamp.
- Document explicitly for AA authors that `timestamp` is attacker-influenceable (bounded by the DAG's non-retreat rule) and should not be treated as a trustworthy, tamper-proof wall-clock value for tight deadline enforcement.

### Proof of Concept
1. Author deploys an AA modeled on the shipped `futures_contract.oscript` sample, which bounces if `timestamp < maturity_ts` before allowing settlement using an oracle price feed valid only after maturity: [5](#0-4) .
2. As maturity approaches, an attacker composes their settlement-triggering unit but deliberately references an older, still-valid `last_ball_unit` whose stored `timestamp` is just before the maturity threshold, satisfying `validateParents`'s only constraint that `last_ball_mci` not retreat below what the attacker's own parent units already reference: [3](#0-2) .
3. During evaluation, `objValidationState.last_ball_timestamp` is set from that chosen (stale) `last_ball_unit`'s timestamp: [2](#0-1) , and the AA's `timestamp` keyword resolves to that value: [1](#0-0) .
4. The AA incorrectly believes maturity has not been reached (or has been reached, depending on which side is exploited) relative to real time, allowing the attacker to force an outcome (e.g., blocking rightful settlement, or forcing premature blackswan/expiry resolution) that a truthful wall-clock timestamp would have prevented.
