Confirmed: `select` is never used server-side to constrain the actual submitted value. It's only stored/serialized for UI rendering.

### Title
`select`-restricted deploy/task variables accept arbitrary values because only the variable *name* is whitelisted, not the value - ([File: lib/shipit/environment_variables.rb])

### Summary
`VariableDefinition#select` is meant to constrain a `shipit.yml`-declared deploy/task variable to a fixed set of values (rendered as a `<select>` in the UI), analogous to the reported `maxReferralEarningTime` bug where a value-setting function lacked a bound check that another function implicitly relied upon. In this engine, the actual server-side enforcement (`EnvironmentVariables#permit`) only checks that the submitted **key** is in the whitelist of variable *names* — it never checks the submitted **value** against `VariableDefinition#select`. This breaks the binding "value permitted by the declared `shipit.yml` variable constraints == value spawned into the deploy/task shell environment."

### Finding Description
`Shipit::EnvironmentVariables#permit` filters the incoming env hash purely by key: [1](#0-0) 

`VariableDefinition` parses `select` from `shipit.yml` but stores it only for display purposes (`to_h`), never using it to validate a submitted value: [2](#0-1) 

`TaskDefinition#filter_envs` and the deploy/rollback equivalent call `EnvironmentVariables.with(env).permit(variables)`, which — as shown above — only cross-checks names: [3](#0-2) 

Controller-side, `TasksController#task_params` also only restricts by variable **name** via strong parameters (`params.require(:task).permit(env: @definition.variables.map(&:name))`), placing no restriction on the value: [4](#0-3) 

The permitted env hash then flows unchanged into the environment of the spawned shell command via `TaskCommands#env` and ultimately `Command#unbundled_env`, which merges it directly into the process environment used for `PTY.spawn`: [5](#0-4) [6](#0-5) 

The README documents `select` as though it were an enforced constraint ("will turn the input into a `<select>` of values"), reinforcing that operators/deploy-script authors reasonably expect the server to reject any value outside the declared set — but no such server-side check exists.

### Impact Explanation
This does not on its own grant unauthorized deploy/rollback/merge access — the request still requires a valid Shipit session with permission to trigger a task/deploy on the stack (an authenticated, authorized user). Given that a legitimate but low-trust user (e.g., someone permitted only to run a specific whitelisted task with a constrained `select` variable, such as choosing a "region" or a "safe" mode flag) can instead submit an arbitrary string for that variable name, the deploy scripts (which are executed with the app's `chdir` and inherit `GITHUB_TOKEN`/other secrets already present in the process environment per `Command#unbundled_env`/`BASE_ENV`) will receive attacker-controlled, unvalidated input where the `shipit.yml` author assumed a closed set of safe values. Depending on how the `deploy`/`rollback`/`task` shell steps use that variable (e.g., interpolated into a shell command via `$VARNAME`), this can enable command injection / arbitrary shell execution on the deploy host, which is the same trust-boundary violation class as "an environment key permitted versus an environment key spawned" called out in the rules. Whether this reaches RCE depends entirely on how the specific `shipit.yml` step consumes the variable, so the severity is conditional rather than guaranteed for every stack, but the missing validation is a genuine root-cause gap in this engine's own code (not a documented-vs-undocumented mounting issue).

### Likelihood Explanation
Likelihood is Low/Medium: it requires (a) an authenticated user with existing permission to trigger the specific task/deploy on the stack, and (b) a `shipit.yml` configuration that uses a `select` variable and interpolates it unsafely into a shell command — this is a realistic but not universal pattern based on the documented feature (`README.md` "rollback.variables.select" example). It does not require any privileged token, TLS interception, or social engineering beyond normal task-triggering access already granted to the user.

### Recommendation
Enforce `VariableDefinition#select` server-side: reject (or clamp) any submitted variable value that is not a member of the declared `select` list, in `EnvironmentVariables#permit` (or in `VariableDefinition` itself), raising `NotPermitted` (or an equivalent error) just as is currently done for unknown variable names. This restores the intended binding between the value set declared/approved in `shipit.yml` and the value that is actually spawned into the task/deploy environment.

### Proof of Concept
1. Configure a stack's `shipit.yml` with a task/deploy variable using `select`, e.g. as documented:
```yaml
rollback:
  variables:
    - name: REGION
      title: Run a rollback in a given region
      select: [east, west, north]
```
and have a step that interpolates it, e.g. `./deploy_to_region.sh $REGION`.
2. As a user authorized to trigger this task, submit a request with `task[env][REGION]=; rm -rf /` (or any shell metacharacter payload) via `TasksController#create` / the deploy/rollback equivalent.
3. Trace the value through `task_params` (only filters by name) → `TaskDefinition#filter_envs` → `EnvironmentVariables#permit` (only checks key membership) → `TaskCommands#env` → `Command#unbundled_env` → `PTY.spawn`. At no point is `REGION`'s value checked against `["east", "west", "north"]`, so the malicious value reaches the shell environment unfiltered. [7](#0-6) [2](#0-1)

# frozen_string_literal: true

module Shipit
  class EnvironmentVariables
    NotPermitted = Class.new(StandardError)

    class << self
      def with(env)
        EnvironmentVariables.new(env)
      end
    end

    def permit(variable_definitions)
      return {} unless @env
      raise "A whitelist is required to sanitize environment variables" unless variable_definitions

      sanitize_env_vars(variable_definitions)
    end

    def interpolate(argument)
      return argument unless @env

      argument.gsub(/(\$\w+)/) do |variable|
        variable.sub!('$', '')
        Shellwords.escape(@env.fetch(variable) { ENV[variable] })
      end
    end

    private

    def initialize(env)
      @env = env
    end

    def sanitize_env_vars(variable_definitions)
      allowed_variables = variable_definitions.map(&:name)

      allowed, disallowed = @env.partition { |k, _| allowed_variables.include?(k) }.map(&:to_h)

      error_message = "Variables #{disallowed.keys.to_sentence} have not been whitelisted"
      raise NotPermitted, error_message unless disallowed.empty?

      allowed
    end
  end
end

# frozen_string_literal: true

module Shipit
  class VariableDefinition
    attr_reader :name, :title, :default, :select

    def initialize(attributes)
      @name = attributes.fetch('name')
      @title = attributes['title']
      @default = attributes['default'].to_s
      @default_provided = attributes.key?('default')
      @select = attributes['select'].presence
    end

    def default_provided?
      @default_provided
    end

    def to_h
      {
        'name' => @name,
        'title' => @title,
        'default' => @default,
        'select' => @select
      }
    end
  end
