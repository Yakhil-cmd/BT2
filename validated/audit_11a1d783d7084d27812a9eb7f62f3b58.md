### Title
Webhook signature is verified against the payload's `organization`/`repository.owner` field while event handlers act on the payload's independent `repository.full_name` field, breaking the "organization authenticated == repository written" binding - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App configuration (and therefore which `webhook_secret`) to verify the HMAC signature against by reading `repository_owner`, which is derived directly from the JSON body itself rather than from any pre-established, trusted association between a GitHub App installation and the stacks it is allowed to update.

### Finding Description
`repository_owner` is computed purely from attacker-supplied payload content: [1](#0-0) 

This value is used to pick the `github_app` whose secret is used to validate the signature: [2](#0-1) 

Once the signature check passes, `create` dispatches the full, attacker-controlled JSON body to the registered event handlers unmodified: [3](#0-2) 

The handlers (e.g. the push/status/check_suite handlers under `app/models/shipit/webhooks/handlers/`) resolve the target `Stack`/`Repository` to act on using the `repository.full_name` field of the same payload — a field that is completely independent of `repository.owner.login`/`organization.login` used for signature-secret selection. Nothing in `verify_signature` establishes that the organization whose secret validated the signature is the same organization that owns the repository being mutated by `full_name`.

Concretely: an attacker who legitimately owns/administers an organization "OrgA" that is configured in Shipit (and therefore possesses OrgA's real `webhook_secret`) can craft a payload where `organization.login` (or `repository.owner.login`) = `"OrgA"` — so `verify_signature` correctly validates the HMAC using OrgA's secret — while `repository.full_name` is set to `"OrgB/some-repo"`, a completely different repository/stack tracked by the same Shipit instance under a different organization. Because the signature only proves "this body was signed with OrgA's secret," not "this body only refers to OrgA's repositories," the handler layer will process the event as if it legitimately originated from OrgB, since it relies on `repository.full_name` to find the stack to update.

This is exactly the kind of binding break called out in the rules: *"an organization that authenticated versus the repository that is written."*

### Impact Explanation
Depending on the event type dispatched (`push`, `status`, `check_suite`, `pull_request`, `membership`, etc.), this allows an attacker who controls one legitimate, Shipit-registered GitHub organization to inject forged webhook events that manipulate the state of a **different** organization's stacks — e.g., forging commit statuses, triggering `GithubSyncJob`s, or manipulating check-run/PR/review-stack state for repositories they have no legitimate access to. Because these events feed directly into deploy-eligibility logic (commit statuses gating whether a commit is deployable), this can influence unauthorized deploy/rollback decisions on stacks belonging to a different repository/organization — a cross-repository write of trust-relevant state through the app's own webhook trust boundary.

### Likelihood Explanation
Requires an attacker to control one legitimate Shipit-registered GitHub organization (and its webhook secret) — no elevated Shipit account, `ApiClient` token, or repository push access on the *target* repo is needed. Given multi-tenant Shipit deployments commonly configure several organizations under `Shipit.github(organization: ...)` (as seen in `config/secrets.development.shopify.yml`), this is a realistic misuse pattern for any environment hosting more than one organization.

### Recommendation
Bind the authenticated organization to the repository being acted upon: after signature verification succeeds for `repository_owner`, reject (or additionally verify) any payload whose `repository.full_name` organization segment does not match the `repository_owner`/GitHub App organization that validated the signature, before handlers are allowed to resolve/mutate a `Stack`.

### Proof of Concept
1. Shipit is configured with two organizations, `OrgA` and `OrgB`, each with a distinct `webhook_secret` (as in `config/secrets.development.shopify.yml`).
2. Attacker administers `OrgA` and thus knows `OrgA`'s real webhook secret (a legitimate, unprivileged position with respect to `OrgB`).
3. Attacker crafts a JSON payload for a `status` (or `push`) event:
   ```json
   {
     "organization": { "login": "OrgA" },
     "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/target-repo" },
     "sha": "<commit sha on OrgB/target-repo>",
     "state": "success"
   }
   ```
4. Attacker computes `X-Hub-Signature` using `OrgA`'s webhook secret over this exact body and POSTs it to `/github/webhooks`.
5. `WebhooksController#verify_signature` resolves `repository_owner` to `"OrgA"` [1](#0-0) , fetches `OrgA`'s `github_app`, and `verify_webhook_signature` succeeds since the body was legitimately signed with `OrgA`'s secret [2](#0-1) .
6. `create` then dispatches the parsed payload to `Shipit::Webhooks.for_event('status')`, whose handler resolves the target commit/stack via `repository.full_name = "OrgB/target-repo"`, updating status for a repository never authenticated by the signing organization [3](#0-2) .
