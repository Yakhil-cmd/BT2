### Title
Reachable invariant-violation crash via non-scalar `max_remote_complexity` in AA remote function calls - (File: formula/evaluation.js)

### Summary
`checkMaxRemoteComplexity()` in `formula/evaluation.js` asserts that a remote-AA-call's `max_remote_complexity` value must be either a string or a `Decimal`, and `throw`s a bare `Error` for any other type. The oscript grammar for the `P#X.func()` remote-call syntax allows `X` (the complexity bound) to be an arbitrary `local_var`, whose value can be assigned to any oscript type (array, dictionary/object, boolean, etc.) before use. If an attacker crafts an AA definition/trigger formula that assigns a non-scalar value to the variable used as the remote-complexity operand, the synchronous `throw Error("unknown type of max_remote_complexity: " + ...)` fires deep inside an async callback chain, outside any `try/catch` that could turn it into a normal validation error. This is conceptually the same bug class as CVE-2021-46344: an internal "should never happen" invariant/assertion is reachable from attacker-controlled, syntactically-valid input, and firing it does not produce a graceful error — it crashes the process.

### Finding Description
The oscript grammar defines the "call getter on a remote AA with max complexity budget" syntax as: [1](#0-0) 

The third symbol accepted is `(%number|%addressValue|local_var)`, meaning the complexity bound can be supplied via a local variable that was previously assigned any expression result (array, dictionary, boolean, etc.), not just a number or address.

At evaluation time, `checkMaxRemoteComplexity()` evaluates that operand and only special-cases `string` and `Decimal`: [2](#0-1) 

The final branch is an unconditional `throw Error("unknown type of max_remote_complexity: " + max_remote_complexity)` rather than routing the problem through the normal error-callback (`cb(err)`) path used everywhere else in this file for user-facing validation failures (compare to `setFatalError()` used elsewhere, e.g. `formula/evaluation.js:134-150`). Because this throw happens inside a callback fired from `evaluate(max_remote_complexity, ...)` (an async/immediate-based evaluator, see `formula/evaluation.js:126-157`), it executes outside the call stack of any `try { … } catch` block that wraps the top-level formula parse/evaluate call (compare `formula/parse_ojson.js:56-77` and `aa_composer.js` usages), so it becomes a genuine uncaught exception.

The process explicitly treats uncaught exceptions as fatal for full nodes: [3](#0-2) 

AA triggers (and AA definitions containing getters) are evaluated by every full node that processes the DAG, either during live validation (`aa_composer.handleTrigger`/`evaluateAA`, e.g. `aa_composer.js:589-615`) or during dry-run/estimation (`aa_composer.js:152-213`, `network.js:1271-1281`). Any node that evaluates such a formula—whether the AA author who defines it or any node validating/estimating a unit that triggers it—will hit the same uncaught throw and crash.

### Impact Explanation
This is a denial-of-service against full nodes, analogous to the JerryScript assertion-failure crash: a syntactically valid, spec-permitted oscript construct reaches an internal invariant check that is not designed to handle attacker-supplied values, and violating it terminates the process instead of returning a validation error. Any AA author can post such a definition, and any user (or the AA itself in response to any trigger) can cause it to be evaluated, crashing every full node — including hubs and witnesses — that processes the corresponding unit. This can halt confirmation of new units on affected nodes until manually restarted, satisfying the "network unable to confirm new units" impact bar.

### Likelihood Explanation
Likelihood is high for any full node operator who chooses/needs to process the specific AA: the syntax (`local_var` as the complexity operand of `P#X.func()`) is explicitly permitted by the grammar, requires no privileged access, and the offending value only needs to be assigned to a variable of a non-string/non-Decimal type (e.g., an array or dictionary) before being used as the complexity bound — an ordinary oscript pattern (`$x = [1,2]; …; P#$x.getter()` is grammatically invalid directly, but the same effect is reachable by first assigning the array/dictionary result to the variable used in that position). Any unprivileged user can post the AA definition and send/trigger a payment that exercises the vulnerable code path.

### Recommendation
In `checkMaxRemoteComplexity()`, replace the final `throw Error(...)` with a normal error callback (`return cb("bad type of max_remote_complexity")` or route through `setFatalError`) so malformed/unexpected types produce a formula-evaluation error instead of an uncaught exception. More broadly, audit other `throw Error(...)` "assert-style" statements inside `formula/evaluation.js`'s async evaluation callbacks (there are ~49 such throws in this file alone) for reachability from attacker-controlled AA formulas, and convert any reachable ones to graceful `cb(err)`-based failures.

### Proof of Concept
1. Deploy (or have any user deploy) an AA whose bound `formula` uses the remote-call-with-complexity-limit syntax where the complexity operand is a local variable assigned a non-scalar value, e.g. (schematically, exact escaping/typing per oscript grammar needs verification in a live test environment):
```
{
  messages: [{
    app: 'state',
    state: "{
      $limit = [1];              // array, not number/string/Decimal
      $x = SOME_REMOTE_AA#$limit.some_getter();
    }"
  }]
}
```
2. Trigger the AA (any unprivileged unit poster can send a payment to it).
3. When `checkMaxRemoteComplexity()` evaluates `$limit` and finds it is neither a `string` nor a `Decimal`, it throws synchronously inside an async callback; this propagates as an uncaught exception.
4. `network.js`'s `process.on('uncaughtException', …)` handler re-throws to crash the process on every full node that validates/estimates the triggering unit.

Note: I was not able to retrieve, within the available tool budget, the exact `case 'remote_func_call'` block in `formula/evaluation.js` that invokes `checkMaxRemoteComplexity`, nor a fully worked-out concrete oscript snippet that type-checks under the grammar to produce a non-string/non-Decimal value in that exact operand position. The grammar and the vulnerable function itself are confirmed by direct citation above; the precise minimal PoC formula should be validated by a developer with access to run the parser/evaluator against candidate inputs.

	function checkMaxRemoteComplexity(remote_aa, func_name, max_remote_complexity, cb) {
		if (max_remote_complexity === null)
			return cb();
		evaluate(max_remote_complexity, max_remote_complexity => {
			if (fatal_error)
				return cb(fatal_error);
			if (typeof max_remote_complexity === 'string') {
				storage.readAADefinition(conn, remote_aa, mci, arrDefinition => {
					if (!arrDefinition)
						return cb("no such remote AA: " + remote_aa);
					const base_aa = arrDefinition[1].base_aa;
					if (max_remote_complexity !== base_aa)
						return cb(max_remote_complexity + " is not base AA for remote AA " + remote_aa);
					cb();
				});
			}
			else if (Decimal.isDecimal(max_remote_complexity)) {
				max_remote_complexity = max_remote_complexity.toNumber();
				storage.readAAGetterProps(conn, remote_aa, func_name, mci, props => {
					if (!props)
						return cb("no such getter: " + remote_aa + "." + func_name);
					if (typeof props.complexity !== 'number')
						throw Error("bad complexity of " + remote_aa + "." + func_name + ": " + props.complexity);
					if (props.complexity > max_remote_complexity)
						return cb("getter " + remote_aa + "." + func_name + " has complexity " + props.complexity + " while called with max remote complexity " + max_remote_complexity);
					cb();
				});
			}
			else
				throw Error("unknown type of max_remote_complexity: " + max_remote_complexity);
		});
	}
