### Title
Congestion control forward-limit accounting checks a clamped gas value but deducts the full unclamped gas, allowing the "allowed shard" trickle bypass on fully-congested receivers - (File: `runtime/runtime/src/congestion_control.rs`)

### Summary
`ReceiptSink::try_forward` decides whether to forward a buffered receipt to another shard by comparing a possibly-clamped `admission_gas` value against the remaining `forward_limit.gas` budget, but then debits the *unclamped* `gas` value from that same budget. This mirrors the TurboSafe `less()` bug class: the value used for the accounting check/decrement is different from the value actually consumed/forwarded, producing a permanent desync between the tracked budget and the real amount sent.

The admission check uses `admission_gas`, which is clamped to at most `allowed_shard_outgoing_gas` (the tiny "trickle" amount a shard is allowed to send to a fully-congested receiver, per [2](#0-1) ). However, the actual debit against `forward_limit.gas` uses the full, unclamped `gas` (the receipt's real attached gas, which can be as large as `max_total_prepaid_gas`, hundreds of Tgas). Since the check passes as long as `forward_limit.gas >= admission_gas` (a small threshold), a single receipt carrying far more gas than `admission_gas` can still be forwarded in full; the excess is silently absorbed via `saturating_sub`, which can only clamp the budget down to zero rather than reflecting the receipt actually exceeded it.

This is structurally identical to the `TurboSafe.less()` issue: the value used to validate/track a capped resource (`admission_gas`) differs from the value that is actually consumed and forwarded (`gas`), causing the tracked accounting (`forward_limit.gas`) to diverge from the real resource flow (how much gas is actually sent to the fully congested shard).

`outgoing_gas_limit` in `CongestionControl` (see [3](#0-2)  and its "red traffic light" branch) sets `forward_limit.gas` to exactly `allowed_shard_outgoing_gas` for the one allowed shard when the receiver is fully congested - this is explicitly documented as "the absolute minimum of new workload a congested shard has to accept every round" (`allowed_shard_outgoing_gas` doc comment, [2](#0-1) ), which is supposed to guarantee deadlock-freedom without overloading the congested shard. The clamp/deduct mismatch defeats this guarantee: a single outgoing receipt with attached gas well above `allowed_shard_outgoing_gas` can still pass the (clamped) admission check and be forwarded in full to a fully-congested shard.

### Impact Explanation
The mismatch allows a fully-congested shard (a "red light" receiver, meant to only accept a minimal, bounded trickle of gas per round to guarantee progress) to instead receive a receipt with arbitrarily large attached gas, up to the protocol's per-receipt gas maximum. This undermines the core purpose of the congestion-control backpressure mechanism (deadlock-avoidance while bounding load on congested shards), and can cause the state-tracked `forward_limit.gas` for that link to diverge from the real amount of gas actually sent - a state/resource accounting divergence in the congestion/bandwidth-limit subsystem explicitly in scope. This does not directly mint or steal tokens, but it is a concrete instance of the reported bug class: internal accounting (a "cap"-like counter) being updated with a different, clamped value than the value that governs the actual resource transfer, defeating the invariant the cap exists to enforce.

### Likelihood Explanation
This path is reachable purely through normal receipt/transaction execution: any account can create action receipts with large attached gas destined for a shard that becomes fully congested; congestion state (`shard_accepts_transactions`, `outgoing_gas_limit`) is derived deterministically from prior chunk state, so an attacker aiming to spam a specific shard until it becomes fully congested, then have an outstanding oversized buffered receipt land as the "allowed shard" receipt, is a plausible and unprivileged scenario. It requires no validator or node-level privilege, only ordinary transaction submission and patience for congestion to build up.

### Recommendation
In `try_forward`, use the same clamped value for both the admission check and the deduction (or explicitly cap the *forwarded* gas as well as the check), i.e.:
```rust
let effective_gas = admission_gas; // or gas.min(forward_limit.gas)
if forward_limit.gas >= effective_gas && forward_limit.size >= size {
    ...
    forward_limit.gas = forward_limit.gas.saturating_sub(effective_gas);
    ...
}
```
Alternatively, deduct the receipt's actual `gas` but require `forward_limit.gas >= gas` (i.e., do not clamp the *check*, only clamp intended semantics elsewhere), so the check and the deduction always agree.

### Proof of Concept
Not independently executed; based on static code review of `try_forward` (`runtime/runtime/src/congestion_control.rs` lines 397-462). A concrete PoC would need to: (1) drive a target shard's congestion info to "fully congested" (`congestion_level() >= 1.0`) so `outgoing_gas_limit` returns `allowed_shard_outgoing_gas` for the allowed sender shard, initializing `forward_limit.gas = allowed_shard_outgoing_gas`; (2) have a buffered outgoing receipt on the allowed sender shard with attached `gas` much larger than `allowed_shard_outgoing_gas`; (3) run `ReceiptSink::try_forward` (via normal chunk application) and observe the receipt is forwarded in full despite `gas > allowed_shard_outgoing_gas`, and that `forward_limit.gas` saturates to zero rather than reflecting the true (negative) balance. I was not able to verify runtime behavior or execute this scenario within the available tools, nor fully review the git history/intent behind the `ClampOutgoingGasAdmission` protocol feature flag (in `core/primitives-core/src/version.rs`) that introduced this clamp - it's possible this asymmetry is a known, intentional trade-off; this should be confirmed against the feature's design notes/PR before treating it as a defect.

    /// How much gas another shard can send to us in the next block.
    pub fn outgoing_gas_limit(&self, sender_shard: ShardId) -> Gas {
        let congestion = self.congestion_level();

        if Self::is_fully_congested(congestion) {
            // Red traffic light: reduce to minimum speed
            if sender_shard == ShardId::from(self.info.allowed_shard()) {
                self.config.allowed_shard_outgoing_gas
            } else {
                Gas::ZERO
            }
        } else {
            mix_gas(self.config.max_outgoing_gas, self.config.min_outgoing_gas, congestion)
        }
    }
