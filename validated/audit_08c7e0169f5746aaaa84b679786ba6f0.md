### Title
Webhook signature verification is bound to `repository.owner.login`, but event handlers act on `repository.full_name` — signature-authorized organization ≠ repository that gets written - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
This mirrors the referenced bug class (two supposedly-linked values silently diverging because no equality check enforces them to match, letting an attacker substitute a "cheap"/attacker-controlled value for the trusted one). In `VE3DRewardPool`, `stakingToken` and `rewardToken` were never checked for equality, letting reward payouts drain principal. In `Shipit::WebhooksController`, the field used to select **which organization's secret authenticates the request** and the field used to select **which repository/stack the request acts on** come from the same JSON body but are never checked against each other.

### Finding Description
`Shipit::WebhooksController#verify_signature` picks the GitHub org to authenticate against from the payload itself: [1](#0-0) [2](#0-1) 

`repository_owner` is `params.dig('repository', 'owner', 'login')`, and `Shipit.github(organization: repository_owner)` looks up that org's per-org config (multi-org mode, keyed by org name): [3](#0-2) 

`verify_webhook_signature` for that org's `GitHubApp` explicitly **skips verification entirely** if that org has no `webhook_secret` configured: [4](#0-3) 

Once verification passes (or is trivially skipped for a secret-less org), `WebhooksController#create` dispatches the **same raw payload** to handlers: [5](#0-4) 

But every repository-scoped handler resolves the target repository/stack from a *different* field of that payload — `repository.full_name` — not `repository.owner.login`: [6](#0-5) 

`Repository.from_github_repo_name` splits `full_name` on `/` and looks the repo up directly, independent of whatever org authenticated the request: [7](#0-6) 

`PushHandler` and `StatusHandler` then act on whatever stacks/commits that lookup returns: [8](#0-7) [9](#0-8) 

**The broken equality**: `Shipit.github(organization: repository_owner).verify_webhook_signature(...)` (authenticating org) is never checked to equal the owner embedded in `repository.full_name` (the repository actually written to). Nothing in `WebhooksController` or `Handler` cross-validates these two fields of the same payload.

### Impact Explanation
In a multi-org Shipit deployment (`Shipit.github_default_organization` present, per-org `github:` config keyed by org name), any org onboarded into Shipit whose config has a blank/unset `webhook_secret`, or whose secret the attacker legitimately knows (because they administer that org's own GitHub webhook settings), lets the attacker forge a payload where `repository.owner.login` (or `organization.login`) names the weak/known org while `repository.full_name` names a completely different, victim organization's repository. Because signature verification only binds to the former and handlers only act on the latter, this causes:
- Unauthorized triggering of `GithubSyncJob` / deploy pipeline sync for a victim stack via `PushHandler` (cross-repository write / unauthorized deploy pipeline activity).
- Forged commit statuses (`Commit#create_status_from_github!`) written against a victim repository's commits via `StatusHandler`.
- Forged `pull_request` events causing review-stack archival/creation against a victim repository, since those handlers also resolve `Repository.from_github_repo_name(params.repository.full_name)` independent of the verifying org.

This satisfies the "cross-repository writes" / "unauthorized deploy" impact bar, contingent on the deployment running multi-org Shipit with at least one weak/attacker-known org secret — analogous to the original finding being contingent on an admin misconfiguration.

### Likelihood Explanation
Requires: (1) the host app running Shipit in the documented multi-org configuration, and (2) at least one onboarded org with no `webhook_secret` set, or one whose secret the attacker controls as a normal (non-privileged-to-victim) GitHub org admin. Both are realistic operational states in a documented, supported configuration mode rather than a hypothetical misconfiguration only privileged actors could reach.

### Recommendation
In `Shipit::WebhooksController#verify_signature`, after determining the authenticating organization, also derive the owner from `repository.full_name` (or the same `repository.owner.login`/`organization.login` value used everywhere else) and reject the request (422) if it doesn't match. Equivalently, in `Handler#repository_name`, require that the resolved repository's owner equals the organization that successfully verified the signature for this request, closing the gap between "org that authenticated" and "repository that is written."

### Proof of Concept
1. Shipit is deployed in multi-org mode with orgs `weak-org` (no `webhook_secret` configured) and `victim-org` (a real onboarded Shipit customer, with `webhook_secret` set).
2. Attacker (who only knows/controls `weak-org`) POSTs to `/webhooks` with `X-Github-Event: push` and body:
```json
{
  "ref": "refs/heads/main",
  "after": "deadbeef",
  "repository": { "owner": { "login": "weak-org" }, "full_name": "victim-org/victim-repo" }
}
```
3. `verify_signature` computes `repository_owner = "weak-org"`, loads `Shipit.github(organization: "weak-org")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` unconditionally — no `X-Hub-Signature` needed at all.
4. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("victim-org/victim-repo")` and enqueues `sync_github` for `victim-org`'s stack, despite the request never being authenticated against `victim-org`'s secret.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
