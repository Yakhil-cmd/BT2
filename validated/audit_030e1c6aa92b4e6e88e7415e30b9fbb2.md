### Title
Bridge Operator Can Drain or Mint Arbitrary ERC20/ERC721 Tokens via Unvalidated `_tokenAddress` in `handleERC20Transfer` / `handleERC721Transfer` — (`File: contracts/service_chain/bridge/BridgeTransferERC20.sol`, `contracts/service_chain/bridge/BridgeTransferERC721.sol`)

---

### Summary

`handleERC20Transfer` and `handleERC721Transfer` accept a caller-supplied `_tokenAddress` with no registered-token whitelist check. The default operator threshold is **1**, so a single registered bridge operator can fabricate a handle call targeting any ERC20/ERC721 token the bridge holds (lock mode) or any token for which the bridge has minter rights (mintBurn mode), draining or inflating bridged assets without a corresponding cross-chain request.

---

### Finding Description

`_requestERC20Transfer` (the deposit path) enforces `onlyRegisteredToken(_tokenAddress)`:

```solidity
function _requestERC20Transfer(...)
    internal
    onlyRegisteredToken(_tokenAddress)   // ← whitelist enforced
    onlyUnlockedToken(_tokenAddress)
``` [1](#0-0) 

`handleERC20Transfer` (the withdrawal path) has **no such check**:

```solidity
function handleERC20Transfer(
    bytes32 _requestTxHash,
    address _from,
    address _to,
    address _tokenAddress,   // ← fully attacker-controlled, never validated
    uint256 _value,
    uint64 _requestedNonce,
    ...
)
    public
    onlyOperators
``` [2](#0-1) 

After the vote passes it unconditionally calls:

```solidity
if (modeMintBurn) {
    require(ERC20Mintable(_tokenAddress).mint(_to, _value), ...);
} else {
    IERC20(_tokenAddress).safeTransfer(_to, _value);
}
``` [3](#0-2) 

The same pattern exists in `handleERC721Transfer`:

```solidity
if (modeMintBurn) {
    require(ERC721MetadataMintable(_tokenAddress).mintWithTokenURI(_to, _tokenId, _tokenURI), ...);
} else {
    IERC721(_tokenAddress).transferFrom(address(this), _to, _tokenId);
}
``` [4](#0-3) 

The `BridgeOperator` constructor hard-codes the default threshold to **1** for all vote types:

```solidity
constructor() internal {
    for (uint8 i = 0; i < uint8(VoteType.Max); i++) {
        operatorThresholds[uint8(i)] = 1;
    }
    operators[msg.sender] = true;
    operatorList.push(msg.sender);
}
``` [5](#0-4) 

With threshold = 1, `_voteValueTransfer` returns `true` on the very first operator call, immediately executing the transfer:

```solidity
bytes32 voteKey = keccak256(msg.data);
if (_voteCommon(VoteType.ValueTransfer, _requestNonce, voteKey)) {
    closedValueTransferVotes[_requestNonce] = true;
    return true;
}
``` [6](#0-5) 

The only other guard is `_lowerHandleNonceCheck`, which only requires `_requestedNonce >= lowerHandleNonce` — it does not verify that the nonce corresponds to any real cross-chain request:

```solidity
function _lowerHandleNonceCheck(uint64 _requestedNonce) internal {
    require(lowerHandleNonce <= _requestedNonce, "removed vote");
}
``` [7](#0-6) 

---

### Impact Explanation

**Lock mode (`modeMintBurn = false`):** The bridge holds ERC20/ERC721 tokens deposited by users. An operator can call `handleERC20Transfer` with any `_tokenAddress` the bridge holds (registered or not — e.g., tokens accidentally sent to the bridge, or tokens from a deregistered pair), any `_to` (attacker-controlled), and any `_value` up to the bridge's balance. The bridge will execute `safeTransfer`, draining those tokens to the attacker.

**MintBurn mode (`modeMintBurn = true`):** The bridge holds minter rights on registered tokens. An operator can call `handleERC20Transfer` with any `_tokenAddress` for which the bridge is a minter, minting an arbitrary `_value` to any `_to`. This inflates the token supply without a corresponding lock on the counterpart chain, breaking the 1:1 bridge invariant.

Both paths constitute **unauthorized transfer or mint of bridged assets** — a direct match to the allowed impact gate.

---

### Likelihood Explanation

- The default threshold is 1, so **a single registered operator** is sufficient; no collusion is required.
- The bridge owner registers operators; operators are semi-trusted (not fully privileged). A compromised or malicious operator key is the only precondition.
- The `_requestTxHash` parameter is a free `bytes32` — the operator can supply any value, bypassing the "already handled" check for any nonce not yet consumed.
- The attack is a single on-chain transaction with no observable preparation.

---

### Recommendation

Add an `onlyRegisteredToken(_tokenAddress)` modifier (already present in `BridgeTokens`) to both `handleERC20Transfer` and `handleERC721Transfer`, mirroring the guard already applied to the deposit path `_requestERC20Transfer`:

```solidity
function handleERC20Transfer(
    ...
    address _tokenAddress,
    ...
)
    public
    onlyOperators
    onlyRegisteredToken(_tokenAddress)   // add this
```

Additionally, consider raising the default `operatorThresholds` above 1 for production deployments, or enforcing a minimum threshold in `setOperatorThreshold`.

---

### Proof of Concept

Preconditions:
- Bridge deployed in lock mode (`modeMintBurn = false`).
- `tokenA` is a registered token; the bridge holds 1000 `tokenA`.
- `tokenB` is **not** registered but the bridge also holds 500 `tokenB` (e.g., sent by a user by mistake).
- Attacker is a registered operator (threshold = 1).

```solidity
// Attacker calls directly — no real cross-chain request exists
bridge.handleERC20Transfer(
    bytes32(uint256(0xdeadbeef)),  // fabricated requestTxHash
    address(0),                    // _from: irrelevant
    attacker,                      // _to: attacker's address
    address(tokenB),               // _tokenAddress: unregistered token
    500e18,                        // _value: full balance
    0,                             // _requestedNonce: first unused nonce
    1,                             // _requestedBlockNumber: any
    ""                             // _extraData
);
// Result: bridge transfers 500 tokenB to attacker
// No corresponding lock event on the counterpart chain
```

The same call works for `tokenA` (a registered token), draining the bridge's registered holdings as well, since `handleERC20Transfer` never checks registration for either case.
