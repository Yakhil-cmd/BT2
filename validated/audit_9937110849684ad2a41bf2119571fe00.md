Based on my investigation, the closest analog to this bug class in ocore is the `spender_attested` asset attestor mechanism, which uses the *current* attestor list rather than the list in effect when the funds were received—structurally similar to the EigenLayer bug where a privileged party can revoke a whitelist entry and permanently strand previously-deposited funds with no path to exit.

### Title
Spend of `spender_attested` asset funds becomes permanently stuck when the holder's address is dropped from the current asset attestor list - (File: `validation.js`, `storage.js`)

### Summary
For assets defined with `spender_attested: true`, `validatePayment` in `validation.js` requires that the spending address currently appear in the asset's attestor list, evaluated at validation time (last stable MCI), not at the time the address received its balance. If the asset definer/attestor-list-updater removes an address from the attestor list after that address already holds balance, the address's funds become permanently unspendable, with no other exit mechanism, mirroring the EigenLayer report's pattern of a privileged whitelist revocation stranding already-held funds.

### Finding Description
`validatePayment` loads the asset and its live list of attested authors via `storage.loadAssetWithListOfAttestedAuthors`, then enforces: [1](#0-0) 

The attestor list itself is resolved to the *latest* stable `asset_attestors` update as of `last_ball_mci`, i.e., whatever the current attestor set is — not the set that applied when the address received its output: [2](#0-1) 

Attestor list updates are posted on-chain via `asset_attestors` messages and are gated only by whatever conditions `validateAttestorListUpdate` imposes (typically controlled by the asset definer). Once a new attestor list unit becomes stable and no longer includes a given address, any subsequent attempt by that address to spend its existing balance in that asset fails validation with `"none of the authors is attested"`, even though the balance was legitimately acquired while the address was attested. There is no fallback path (e.g., "spend once with the old attestor snapshot" or "withdraw regardless of current attestation") — the check is purely against the present state of the attestor list.

This is structurally the same defect as the EigenLayer report: a party with unilateral control over a whitelist/allowlist (there: `strategyIsWhitelistedForDeposit`; here: the asset's current attestor list) can change that list in a way that blocks an operation (there: further deposits; here: any further spend) for holders whose exit depends on being on the list, permanently freezing funds already held by affected parties who were compliant when they acquired the funds.

### Impact Explanation
Holders of a `spender_attested` asset who are later removed from the attestor list lose the ability to move or exchange their existing balance entirely — not just future receipts. Because payment validation always uses the current attestor list rather than a snapshot tied to the output, there is no way for such a holder to withdraw, redeem, or transfer funds elsewhere; the tokens are permanently frozen at the protocol level for as long as (or forever if) the address remains off the list. This is a fund-freezing condition reachable by any unprivileged holder who depended on attestor status previously granted, triggered solely by an ordinary on-chain `asset_attestors` message from the definer/updater.

### Likelihood Explanation
Any asset creator can define an asset with `spender_attested: true` and later post updated `asset_attestors` messages that drop previously attested addresses — this is a normal, expected operational action for compliance-oriented assets (e.g., regulatory attestation revocation), not an edge case requiring an external protocol failure. Consequently the scenario is readily reachable in practice for any asset using this feature, whenever the attestor-list controller performs a routine list update that removes a currently-holding address.

### Recommendation
Decouple spend eligibility from the *current* attestor list for outputs that were received while the spender was attested. Options include: (a) recording attestation status at the time the output is created and permitting spends based on that snapshot, or (b) providing an explicit unconditional withdrawal/exit path for holders who lose attestation, so that balance already acquired legitimately cannot become permanently unspendable due to a later, unilateral attestor-list update.

### Proof of Concept
1. Definer creates asset `A` with `spender_attested: true` and posts an initial `asset_attestors` unit listing address `X`.
2. Address `X` receives a payment output in asset `A` while attested, per the standard payment/validation flow in `validatePayment` (`validation.js` — case `payment`).
3. Definer later posts a new `asset_attestors` unit for asset `A` that no longer includes `X` (only requires whatever authorization `validateAttestorListUpdate` imposes, typically the definer's signature).
4. Once this new attestor-list unit is stable, `storage.readAsset`'s `addAttestorsIfNecessary` resolves the attestor list to this latest unit [3](#0-2) .
5. `X` attempts to spend its previously received balance of asset `A`. `validatePayment` rejects the unit with `"none of the authors is attested"` because `objAsset.arrAttestedAddresses` no longer contains `X` [1](#0-0) .
6. `X`'s balance in asset `A` is now permanently unspendable with no protocol-level recourse.
