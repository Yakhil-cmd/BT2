### Title
Argument injection into `git branch` via unsanitized default branch name in `gh repo sync` - ([File: pkg/cmd/repo/sync/git.go])

### Summary
`gitExecuter.CreateBranch` (and to a lesser extent the `--set-upstream-to` call within it) passes the branch name returned by `api.RepoDefaultBranch` directly as a positional argument to `git branch` without a `--` separator or leading-dash validation. A source repository whose default branch name begins with `-` (e.g. `-D`, `-M`, `-f`) causes `git branch` to interpret the branch name as an option flag instead of a branch name, altering the intended local git-branch operation on the victim's machine.

### Finding Description
`syncLocalRepo` in `pkg/cmd/repo/sync/sync.go:128-140` fetches `opts.Branch` from `api.RepoDefaultBranch(apiClient, srcRepo)` whenever `--branch` is not supplied, taking the value verbatim from the GitHub API response for the attacker's own (or attacker-influenced) source repository. This value flows into `executeLocalRepoSync` (`pkg/cmd/repo/sync/sync.go:221-272`), which—for a branch that does not yet exist locally—calls: [1](#0-0) 

`gitExecuter.CreateBranch` then builds the git invocation: [2](#0-1) 

The first `git.Command(ctx, "branch", branch, ref)` call places `branch` as a raw positional argument immediately after the `branch` subcommand, with no `--` separator and no check that `branch` does not start with `-`. `git.Client.Command` forwards these arguments straight into `exec.CommandContext` (`git/client.go:77-99`) without a shell, so this is not shell injection, but git's own CLI parser will treat a leading-dash value as an option to `git branch` rather than as a branch name (e.g. `-D`/`-M`/`-f`), changing the semantics of the command (delete/rename/force-create) instead of creating the intended branch. The subsequent `--set-upstream-to` call has the same weakness for its trailing `branch` argument.

In contrast, `UpdateBranch` (used when the branch already exists locally) is not vulnerable, because `branch` is embedded inside a formatted string, `fmt.Sprintf("refs/heads/%s", branch)`, which can never begin with `-`: [3](#0-2) 

Git's `check-ref-format` rules do not forbid a ref/branch name from starting with `-` at the low level (the "no ambiguity with options" restriction is enforced only by the `git branch`/`git tag` porcelain argument parser, which can be bypassed with `--`). This means a ref literally named e.g. `refs/heads/-D` can be created by an attacker on their own repository/fork using a raw ref-update push (bypassing the CLI's own guard), and such a ref can subsequently be selected as the repository's default branch via GitHub, so `api.RepoDefaultBranch` returns the dash-prefixed string unfiltered.

### Impact Explanation
This is scoped local ref manipulation on the victim's clone: depending on which git-branch flag the attacker's branch name maps to, the affected `git branch` invocation can be turned into an unintended delete (`-D`), force-rename (`-M`), or force-create/reset (`-f`) operation instead of creating the intended synced branch. The arguments that would be "deleted"/"renamed"/"reset" are limited to the hardcoded literal `FETCH_HEAD`/current-branch context supplied by the code, not arbitrary attacker-chosen targets, so the blast radius is constrained to local branch bookkeeping corruption rather than arbitrary file write or code execution. This matches the "unintended git-branch flag execution / local ref manipulation" impact class called out in the question, not a code-execution or credential-exfiltration class.

### Likelihood Explanation
Exploitation requires: (1) the victim to run `gh repo sync` (or the local no-arg form) against a repository whose default branch name is attacker-controlled, and (2) the attacker to have already set that repo's (their own fork's or upstream's) default branch to a dash-prefixed ref, which requires bypassing `git branch`'s own CLI guard via a raw ref-update push. This is feasible without any special privileges since it's the attacker's own repository, but it is a somewhat unusual, deliberate setup rather than an incidental configuration, so likelihood is moderate rather than high.

### Recommendation
In `pkg/cmd/repo/sync/git.go`, insert a `--` separator before the branch-name positional argument in every `git branch`/`git update-ref` invocation that accepts an attacker-influenced branch name (e.g. `g.client.Command(ctx, "branch", "--", branch, ref)` and `g.client.Command(ctx, "branch", "--set-upstream-to", upstream, "--", branch)`), or validate that `opts.Branch` does not begin with `-` before it reaches any git subprocess call, rejecting/erroring out otherwise.

### Proof of Concept
Go test using a `gitClient`/`git.Command` stub:
```go
func TestCreateBranch_DashPrefixedName(t *testing.T) {
    cs, restore := run.Stub()
    defer restore(t)
    cs.Register(`git branch -D FETCH_HEAD`, 0, "") // demonstrates "-D" is parsed as delete flag, not branch name

    g := &gitExecuter{client: &git.Client{ /* stubbed commandContext */ }}
    err := g.CreateBranch("-D", "FETCH_HEAD", "origin/-D")
    // Assert the underlying command executed was `git branch -D FETCH_HEAD`
    // (i.e. no "--" separator was inserted), proving "-D" is consumed as an
    // option rather than as a literal branch name argument.
}
```
Expected assertion: the recorded command line is `git branch -D FETCH_HEAD` (interpreted by real git as a force-delete of branch `FETCH_HEAD`), not a branch-creation of a branch literally named `-D`—demonstrating the missing `--` separator/validation before `git.Command.Run`/`Output`.

func (g *gitExecuter) CreateBranch(branch, ref, upstream string) error {
	ctx := context.Background()
	cmd, err := g.client.Command(ctx, "branch", branch, ref)
	if err != nil {
		return err
	}

		return err

		return err
