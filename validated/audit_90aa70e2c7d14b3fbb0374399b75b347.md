### Title
`OpenedHandler#provision?` ignores `review_stacks_enabled` for `allow_with_label`/`prevent_with_label` due to operator precedence - ([File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb])

### Summary
`OpenedHandler#provision?` is written as `A && B || C || D`, and Ruby's `&&`/`||` precedence makes this `(A && B) || C || D`, not `A && (B || C || D)`. As a result, when `provisioning_behavior` is `prevent_with_label` (or `allow_with_label`), `repository.review_stacks_enabled` is never consulted, so an attacker's unlabeled PR triggers `ReviewStack` creation and provisioning even on repositories where review stacks were never enabled.

### Finding Description
The intended binding is: **stack provisioning should require `repository.review_stacks_enabled == true` in all cases** — that binding is broken.

Actual code:
```ruby
def provision?
  repository.review_stacks_enabled &&
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
``` [1](#0-0) 

Because `&&` binds tighter than `||`, this evaluates as:
```
(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label) || (prevent_with_label? && !has_label)
```
The last two disjuncts never reference `review_stacks_enabled`. Any repository record with `provisioning_behavior == 'prevent_with_label'` (or `allow_with_label`) will provision stacks for matching PRs regardless of the `review_stacks_enabled` flag.

Call path: `Webhooks::HandlerController` dispatches a validated `opened` event to `OpenedHandler#process`, which calls `respond_to_pull_request_opened?` → `provision?` [2](#0-1) . If true, `ReviewStackAdapter#find_or_create!` builds a `ReviewStack` from attacker-controlled `pull_request.head.ref` and PR number, and queues it via `ReviewStackProvisioningQueue.add(stack)` [3](#0-2) , which eventually leads to provisioning tasks running deployment commands for the attacker's branch.

Note: unlike the question's premise, the migration sets the DB-level default for `provisioning_behavior` to `allow_all`, not `prevent_with_label` [4](#0-3) , so `prevent_with_label` is not literally the factory default — it is a value an operator must explicitly select in the settings UI [5](#0-4) . This does not change the core finding: whenever an operator sets `provisioning_behavior` to `prevent_with_label` or `allow_with_label` while leaving `review_stacks_enabled` false (its DB default) [6](#0-5) , the gate is bypassed.

Existing tests do not catch this because `configure_provisioning_behavior` defaults `provisioning_enabled: true` in every `prevent_with_label`/`allow_with_label` test case, so the `review_stacks_enabled: false` + `prevent_with_label` combination is never exercised [7](#0-6) [8](#0-7) . No other guard (signature verification, `ExplicitParameters` schema, controller auth) checks `review_stacks_enabled`; the parameter schema only validates payload shape [9](#0-8) .

The same bug pattern (`A && B || C`) is also present in `ReopenedHandler#unarchive?` [10](#0-9) , compounding the impact for the `reopened` event.

### Impact Explanation
Any unprivileged GitHub user who can open a PR against a repository with `provisioning_behavior` set to `allow_with_label` or `prevent_with_label` and `review_stacks_enabled == false` can force Shipit to create a `ReviewStack` and enqueue provisioning for their own branch/environment, even though the operator never enabled dynamic PR provisioning for that repository. Provisioning executes deploy tasks derived from attacker-controlled `pull_request.head.ref`, which can lead to arbitrary task/command execution scoped to that repository — matching "an unauthorized deploy" / command running that should not, Critical per the rubric. It is repeatable against every repository configured this way and does not require any secret or privileged role.

### Likelihood Explanation
Requires only that an operator has explicitly chosen `allow_with_label` or `prevent_with_label` for `provisioning_behavior` while `review_stacks_enabled` remains false (its column default) [11](#0-10) . This is a plausible, non-exotic configuration (e.g., an operator preparing label-gated provisioning before flipping the master toggle on). No secrets, sessions, or team membership are needed — just opening a PR (or omitting a label) from any account with push access to a fork, which is available to any GitHub user.

### Recommendation
Add explicit parentheses so `review_stacks_enabled` gates every branch:
```ruby
def provision?
  repository.review_stacks_enabled &&
    (repository.provisioning_behavior_allow_all? ||
     (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
     (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?))
end
```
Apply the same fix to `ReopenedHandler#unarchive?`.

### Proof of Concept
Minitest plan (add to `test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb`):
```ruby
test "does not create stacks when review_stacks_enabled is false, even with prevent_with_label" do
  repository = shipit_repositories(:shipit)
  configure_provisioning_behavior(
    repository:,
    provisioning_enabled: false,   # binding under test: review_stacks_enabled == false
    behavior: :prevent_with_label,
    label: "pull-requests-label"
  )
  payload = payload_parsed(:pull_request_opened)
  payload["pull_request"]["labels"] = []  # no label -> prevent_with_label branch fires

  assert_no_difference -> { Shipit::Stack.count } do
    OpenedHandler.new(payload).process
  end
end
```
Before the fix: `repository.review_stacks_enabled` is `false` while `provision?` returns `true` (stack is created) — the two sides of the intended equality (`review_stacks_enabled == true` required for provisioning) diverge, and the assertion fails (stack count increases). After applying the parenthesization fix, `provision?` returns `false` and the assertion passes.
