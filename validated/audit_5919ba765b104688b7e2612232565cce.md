### Title
Webhook signature is verified against the payload's own `repository.owner.login`/`organization.login` while handlers act on the payload's `repository.full_name`, allowing cross-organization forgery of push/status/check_suite events - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which organization's webhook secret to verify the HMAC signature against by reading `repository.owner.login` (or `organization.login`) straight out of the attacker-supplied, unsigned-at-that-point JSON body. Once verification passes, `WebhooksController#create` hands the *entire same payload* to the registered handlers, which independently derive the target `Repository`/`Stack` from `repository.full_name` in `Handler#repository_name`. Nothing ties the organization whose secret validated the signature to the repository the handlers actually mutate.

### Finding Description
`verify_signature` does:
```ruby
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
``` [2](#0-1) 
where `repository_owner` is taken from the same body being verified: [3](#0-2) 

`Shipit.github(organization:)` looks up a distinct `GitHubApp` (and thus a distinct `webhook_secret`) per organization key in `secrets.github`, as shown by the multi-org fixture with independent `OrgOne`/`OrgTwo` webhook secrets: [1](#0-0) [4](#0-3) 

After the signature check passes, `create` re-uses the identical payload for the handlers: [5](#0-4) 

Every handler resolves the target `Repository`/`Stack` from `repository.full_name`, a completely different field than the one used for signature-organization selection: [6](#0-5) 

So an attacker who legitimately controls a webhook secret for **their own** onboarded organization (`OrgA`) — a routine, unprivileged capability in a multi-tenant Shipit deployment where each customer org configures its own GitHub App/webhook secret — can craft a payload where `repository.owner.login` (or `organization.login`) is set to `OrgA` (so the signature check picks and validates against `OrgA`'s known secret) while `repository.full_name` is set to `OrgB/some-repo`, a completely unrelated organization/repository also tracked by the same Shipit instance. The signature will verify successfully (it's HMAC'd with `OrgA`'s secret over the exact bytes sent, and the attacker controls those bytes), yet the handlers will act on `OrgB`'s stack.

Concretely:
- `PushHandler#process` calls `stack.sync_github(expected_head_sha: params.after)` on any not-archived stack of the resolved repository matching the pushed branch. [7](#0-6) 
- `StatusHandler#process` writes arbitrary CI status (`state`, `context`, `description`, `target_url`) onto any existing commit matching `sha` — sha is not scoped to the resolved repository at all, so forged "green" CI can be attached to any commit shared/globally matching that sha. [8](#0-7) 
- `CheckSuiteHandler#process` similarly schedules check-run refreshes for `OrgB`'s stacks based on attacker-chosen `head_sha`/`head_branch`. [9](#0-8) 

Because stacks can be configured for `continuous_deployment` (auto-deploy when required statuses turn green), injecting forged "success" statuses via `StatusHandler` into `OrgB`'s commits can trigger an unauthorized deploy of `OrgB`'s stack, entirely from a signature that was only ever proven valid for `OrgA`.

### Impact Explanation
This breaks the equality: `organization whose signature validated == organization whose repository/stack is written`. An attacker who is a legitimate, unprivileged customer of the Shipit instance for their own organization (`OrgA`) can forge webhook events attributed to any other organization's repository (`OrgB`) hosted on the same instance, causing cross-repository writes (forged commit statuses, forced sync jobs, forced check-run refresh) and potentially an unauthorized deploy if `OrgB`'s stack has continuous deployment enabled and is gated on the forged CI status. This matches the Critical impact bucket: cross-repository writes / unauthorized deploy.

### Likelihood Explanation
Requires only that the Shipit instance host more than one organization's GitHub App/webhook configuration (a documented, supported configuration per `secrets_double_github_app.yml`), and that the attacker be a legitimate owner/admin of any one of those onboarded organizations (able to compute a valid signature with their own org's webhook secret, e.g. via a controlled test webhook delivery or a compromised low-privilege integration). No Shipit `ApiClient` token, GitHub App private key, or Shipit account is required — only the ability to send an HTTP POST with a body whose HMAC-SHA1 matches a secret the attacker legitimately possesses for their own org.

### Recommendation
Verify the webhook signature using an identifier of the organization/installation that is cryptographically bound to the delivery (e.g. the GitHub App installation ID or `X-GitHub-Hook-Installation-Target-ID` header resolved server-side to the expected org), not a field read out of the same JSON body being verified. Additionally, after selecting the organization from a trusted source, re-validate that every repository referenced in the payload (`repository.full_name`, and any repository implied by `sha`/`stacks` lookups in handlers) actually belongs to that same organization before any handler mutates state.

### Proof of Concept
1. Configure a Shipit instance in multi-org mode with two organizations, `OrgA` and `OrgB`, each with its own `webhook_secret` (as in `test/dummy/config/secrets_double_github_app.yml`), and a stack/repository tracked for each.
2. As a legitimate admin of `OrgA`, obtain/know `OrgA`'s `webhook_secret` (normal operational knowledge for setting up the GitHub App webhook).
3. Craft a `status` event JSON payload with `sha` set to a known commit hash belonging to `OrgB`'s repository, `state: "success"`, and `repository.owner.login` (or `organization.login`) set to `"OrgA"`.
4. Compute `X-Hub-Signature: sha1=HMAC-SHA1(OrgA_webhook_secret, raw_body)` and POST it to `/webhooks` with `X-Github-Event: status`.
5. `WebhooksController#verify_signature` resolves `Shipit.github(organization: "OrgA")` and successfully verifies the signature against `OrgA`'s secret.
6. `StatusHandler#process` then finds the commit by `sha` (belonging to `OrgB`) and calls `commit.create_status_from_github!(params)`, writing a forged "success" status — potentially unblocking `OrgB`'s continuous deployment gate — despite the request never being signed by anything associated with `OrgB`.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?

    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)

  end
