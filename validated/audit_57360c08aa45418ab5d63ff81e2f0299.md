### Title
`flash_position` measures declared collateral by bare asset address, so duplicate `(hub, asset)` legs share one measured deposit and mint double-counted supply - (File: contracts/controller/src/strategies/flash_position.rs)

### Summary
The bug class in the report is an insufficient fix: a hostname whitelist entry (`localhost6`) that an attacker can make resolve to a different target than intended. The analog here is a collateral declaration keyed by a coarser identifier than the accounting it feeds. `flash_position` snapshots and measures callback receipts per token `asset` address, but the books it credits are per `(hub_id, asset)`. The same token is listed in multiple hubs (e.g., the same USDC SAC address as `USDC@hub1` and `USDC_HUB2@hub2`), so a caller can declare two collateral legs with the same asset and different `hub_id`s. One physical deposit of `X` then satisfies both declared minimums and is credited as supply into two separate market books, minting `2X` of collateral against minted flash debt.

### Finding Description
In `process_flash_position`, the callback baselines are taken per asset address, not per `HubAssetKey`:

```rust
let collateral_before = snapshot_balances(
    env,
    &controller,
    collaterals.iter().map(|(hub_asset, _)| hub_asset.asset),
);
``` [1](#0-0) 

The collateral/refund snapshots are `Map`s keyed on the bare `Address`. After the receiver callback, the controller measures each declared collateral's balance delta, requires every declared minimum, and deposits positive deltas per leg (`INV-STRAT-04`: "measures callback receipts against those minima, deposits positive receipts"). [2](#0-1) 

There is a dedup guard for `debt_caps` in Blend migration (`require_unique_debt_assets` rejects repeated debt assets), but no equivalent check was found for the `collaterals` list in `flash_position` — the only use of the declared assets before the callback is `extra_assets` price prefetching, where duplicates are harmless. [3](#0-2) [4](#0-3) 

Because hub markets keep separate books over one physical balance, the same token address legitimately appears in two hubs (USDC is listed as `hub_id 1` and `hub_id 2` with the identical asset address). [5](#0-4) 

Note: I was unable to fully verify the post-callback deposit loop (whether each `(hub_asset, min)` leg reads the shared per-asset delta and credits it independently). The finding depends on that; if the deposit leg re-measures or rejects duplicate assets elsewhere, the exploit collapses.

### Impact Explanation
An attacker calls `flash_position` with `debt = (ETH@hub1, amount)` and `collaterals = [(USDC@hub1, X), (USDC@hub2, X)]`. The receiver returns `X` USDC once; both legs read the same `+X` delta, both minimums pass, and the account is credited `X` supply in each hub book — `2X` total collateral backing `amount` of real debt. The position then passes the final LTV/health/collateral-floor gates on phantom collateral, and the attacker can withdraw or borrow real pool funds against the duplicated leg in a second hub market. This is theft of user funds / protocol insolvency reachable by any unprivileged caller via `controller::flash_position`. [6](#0-5) 

### Likelihood Explanation
Fully permissionless: `flash_position` requires only `caller.require_auth`, a Wasm receiver (the attacker's own contract), a flash-loan-enabled debt market, and declared collateral minimums that are nonnegative with at least one positive. A duplicate-asset declaration requires no special market state beyond a token listed in two hubs, which is already the mainnet configuration for USDC. The receiver needs only to transfer the single collateral amount back to the controller during `execute_flash_position`. [7](#0-6) 

### Recommendation
Reject duplicate asset addresses (or duplicate `HubAssetKey`s that share an asset) in the `collaterals` list at request validation, analogous to `require_unique_debt_assets` for `debt_caps`. Alternatively, snapshot and measure per `HubAssetKey` by requiring the receiver to return collateral through per-leg distinct transfers — but since the token is physically identical across hubs, keying the measurement map by `HubAssetKey` alone is insufficient; dedup on the bare asset address is the correct fix, since one balance delta cannot honestly fund two legs.

### Proof of Concept
1. Attacker deploys a Wasm `FlashPositionReceiver` that, inside `execute_flash_position`, transfers exactly `X` USDC to the controller.
2. Attacker calls `controller.flash_position(caller, account_id=0, spoke_id, Multiply, debt=(ETH@hub1, D), receiver=self, data, collaterals=[(USDC@hub1, X), (USDC@hub2, X)], refunds=[])`.
3. `snapshot_balances` records one USDC baseline; the callback adds `X`; both legs observe the same `+X` delta and meet their minimums.
4. The controller deposits `X` of supply into the hub-1 USDC book and `X` into the hub-2 USDC book, while the account carries `D` of ETH debt minted without an origination fee.
5. The final risk gates evaluate `2X` of collateral against `D` of debt; with `2X·LTV ≥ D` the call succeeds. The attacker then withdraws/borrows against the duplicated collateral, leaving the protocol undercollateralized.

### INV-STRAT-04 — Flash position retains debt and supply

Flash position mints debt without an origination fee and never automatically
repays returned debt tokens. Every declared collateral minimum must be
non-negative, with at least one positive minimum. The controller measures
callback receipts against those minima, deposits positive receipts and
remeasures the pool's receipt.

Before and after account finalization, the borrowed market must retain positive
scaled debt and the account must retain supply. Returned debt becomes
collateral if declared, returns to the caller if refund-listed, or remains
uncredited if in neither list. Refunds cover only positive callback balance
changes.
```

## Flash position

`flash_position` creates or reuses a `Multiply`, `Long`, or `Short` account,
mints debt, transfers the measured receipt to the receiver, and invokes:

```rust
fn execute_flash_position(
    env: Env,
    initiator: Address,
    account_id: u64,
    asset: Address,
    amount: i128,
    fee: i128,
    amount_received: i128,
    controller: Address,
    data: Bytes,
);
```

The controller passes `fee` as `0`. The callback does not repay or approve
debt. It transfers purchased collateral from the receiver to the controller.
After return, the controller:

1. measures each declared collateral balance delta
2. requires every minimum and at least one positive deposit
3. deposits positive declared deltas on `account_id`
4. refunds positive deltas for declared refund assets to the caller
5. requires debt and collateral to remain open
6. runs LTV, health-factor, and minimum borrow collateral checks

An undeclared token left on the controller is neither deposited nor refunded.
Refunding unused debt tokens does not repay the minted debt.
```
