### Title
Webhook `repository.owner.login` used to select the signing organization while handlers act on `repository.full_name`, allowing forged CI status/push/check-suite events to reach any tracked stack — (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` picks which GitHub App/organization secret to verify the incoming payload against using `params.dig('repository','owner','login')`, while the event handlers that actually mutate state key off a *different* attacker-controlled field, `payload.dig('repository','full_name')`, or (in the case of `StatusHandler`) don't scope by repository at all. Because `webhook_secret` is explicitly documented as optional per organization, any organization configured without a secret becomes a skeleton key: a forged payload can declare that unprotected organization as `repository.owner.login` to pass signature verification, while the handler logic that follows resolves the real target using `full_name` (or a global commit-sha lookup), letting the payload affect repositories/commits that have nothing to do with the "authenticated" organization.

### Finding Description
Signature verification: [1](#0-0) 

The organization used to look up the secret comes straight from the attacker-supplied JSON body (`repository_owner`), not from any authenticated context: [2](#0-1) 

`GitHubApp#verify_webhook_signature` trivially returns `true` when no secret is configured for that organization: [3](#0-2)  This is a documented, supported configuration — the setup guide marks `webhook_secret` as "(optional)": [4](#0-3)  and the multi-org example config shows independent `webhook_secret` entries per organization: [5](#0-4) 

Once signature verification passes, the payload is dispatched to handlers keyed by `X-Github-Event`: [6](#0-5) 

The base `Handler` resolves the target `Stack` using `repository.full_name` — a field independent of the `repository.owner.login` value used for signature/organization selection: [7](#0-6) 

`StatusHandler` goes further and doesn't scope by repository at all — it matches purely by commit SHA across the entire install: [8](#0-7) 

`PushHandler` and `CheckSuiteHandler` similarly act on stacks resolved from `full_name`/branch, independent of the org that was actually "authenticated": [9](#0-8) [10](#0-9) 

**Binding broken:** `organization authenticated by verify_signature (repository.owner.login → org's webhook_secret)` ≠ `repository/commit actually written by the handler (repository.full_name, or global commit sha for StatusHandler)`. This is the direct analog of the report's unchecked-recovery bug: a value that passes an authentication/verification step is silently substituted for a different, unverified value that drives the security-relevant action.

### Impact Explanation
If any organization configured in Shipit's multi-org setup has no `webhook_secret` set (an explicitly supported/optional configuration), an unauthenticated attacker can craft a webhook body that:
- declares `repository.owner.login` = the org with no secret (so `verify_signature` trivially passes), and
- declares `repository.full_name` = the actual owner/repo of a *different, protected* stack, or
- for `status` events, simply sets an arbitrary `sha` that matches any tracked `Commit` in the whole installation, with no repository field consulted by `StatusHandler` at all.

This lets the attacker forge a passing CI status (`state: success`) for any commit Shipit knows about, which is used to gate CI-based deploy checks, merge queue promotion, and continuous deployment — enabling an unauthorized deploy or merge. It can also forge `push`/`check_suite` events to trigger `stack.sync_github`/check-run refresh cycles against stacks unrelated to the "authenticated" organization. This satisfies the required Critical impact category of "an unauthorized deploy, rollback, or merge."

### Likelihood Explanation
Requires only that the Shipit deployment has at least one configured GitHub organization without a `webhook_secret` — a state the project's own setup docs present as a normal, optional configuration, not a misconfiguration outside the documented deployment model. No credentials, GitHub App private key, session, or `ApiClient` token are needed; the `/webhooks` endpoint is intentionally unauthenticated aside from the HMAC check that this flaw defeats. `StatusHandler`'s complete lack of repository scoping means the sha-based forgery works regardless of the multi-org edge case, as long as any org lacks a secret.

### Recommendation
- Verify the webhook signature using the organization actually referenced by the data the handler will act on (i.e., derive both from the same, single field, and reject payloads where `repository.owner.login` doesn't match the owner segment of `repository.full_name`).
- Scope `StatusHandler` (and any other handler) to the repository/organization that was authenticated, not merely to a global commit SHA.
- Treat a missing/blank `webhook_secret` for any configured organization as a hard failure (reject the webhook) rather than an automatic pass, or require operators to set a shared minimum secret policy across all configured organizations.

### Proof of Concept
1. Configure Shipit with two organizations in `secrets.yml`: `org-with-secret` (has stacks, `webhook_secret` set) and `org-without-secret` (any org name resolvable by `Shipit.github`, `webhook_secret` left blank per docs' "optional" guidance).
2. POST to `/webhooks` with header `X-Github-Event: status` and body:
```json
{
  "repository": { "owner": { "login": "org-without-secret" }, "full_name": "org-without-secret/whatever" },
  "sha": "<sha-of-a-real-commit-tracked-under-org-with-secret>",
  "state": "success",
  "context": "ci/forged"
}
```
No `X-Hub-Signature` needs to be valid because `verify_webhook_signature` short-circuits to `true` when `org-without-secret` has no secret configured — see [11](#0-10) .
3. `StatusHandler#process` runs `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` — see [8](#0-7)  — which writes a forged "success" status onto the targeted commit regardless of which organization it actually belongs to, potentially unblocking a deploy/merge gated on CI status.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
