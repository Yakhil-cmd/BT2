## Title
`agave_precompiles::secp256k1::verify` accepts malleable ECDSA signatures (missing EIP-2 low-S check) - (File: `precompiles/src/secp256k1.rs`)

## Summary
The `secp256k1_program` precompile validates ECDSA/secp256k1 signatures over an Ethereum-style keccak-hashed message and recovers the eth address, but it never enforces the canonical/low-S requirement that Ethereum's EIP-2 mandates. This is the exact same class of bug described in the external report: any transaction sender can flip `s -> -s (mod n)` and the corresponding recovery id, producing a second, distinct-but-equally-valid signature encoding for the same message and signer.

## Finding Description
`verify()` parses the signature with `libsecp256k1::Signature::parse_standard_slice` and recovers the public key/eth address without any check that `s` is in the lower half of the curve order (the standard EIP-2 style check performed e.g. by `sig.normalize_s()` before recovery). [1](#0-0) 

The codebase's own test explicitly documents that this is malleable: it flips `s` and the recovery id and shows `verify()` accepts *both* signature encodings for the same message/eth_address. [2](#0-1) [3](#0-2) 

This is the closest structural analog to the reported `static_validate_system_transaction`/EIP-2 issue: both cases are ECDSA secp256k1 signature verification paths that omit the canonical-S check that Ethereum requires. By contrast, Agave's other signature-verification paths are ed25519-based and are either explicitly hardened against malleability (`verify_strict` in the ed25519 precompile and in gossip `CrdsValue::verify_with_cache`), or use a different verification mechanism not directly comparable to EIP-2: [4](#0-3) [5](#0-4) 

## Impact Explanation
The precompile itself does not move funds or mint tokens by itself — it is a pure signature-verification/attestation primitive used by on-chain programs (bridges, oracles, multisig/relayer schemes) that consume the `secp256k1_program` instruction to authenticate an externally-signed (often Ethereum-style) message and then take some privileged action keyed by that message hash or signature. Because a single signature can be presented in two distinct valid byte-encodings (differing `s`/recovery id), any downstream program that uses the raw signature bytes (or a hash of them) as a nonce/replay-protection key, an idempotency key, or a unique transaction identifier can be tricked into treating the same authorized action as two different, both-valid submissions. This maps to the report's "malicious sender can include a second valid-but-different-looking signed payload" class of issue and can enable replay of an authorized action or double-processing in any program built on top of this precompile that relies on signature bytes for deduplication.

## Likelihood Explanation
High/trivial to reach: any account can submit a transaction containing a `secp256k1_program` instruction with an attacker-chosen signature encoding; libsecp256k1 signature negation (`s = -s`) plus recovery-id XOR 1 is a one-line, deterministic transformation requiring no additional cryptographic work, exactly as demonstrated in the repository's own `test_malleability` test. No special privileges, leader position, or network manipulation is required — a single unprivileged transaction sender can produce a malleable signature for any message they already have a valid signature for.

## Recommendation
Enforce EIP-2 style canonicalization in `agave_precompiles::secp256k1::verify` before recovery: reject (or normalize) any signature whose `s` value is not in the lower half of the secp256k1 curve order, e.g. call `signature.normalize_s()` and fail (or use the normalized form consistently) prior to computing `libsecp256k1::recover`. This should be done at `precompiles/src/secp256k1.rs:65-68`, mirroring the fix pattern shown in the external report's `validation.rs` example.

## Proof of Concept
The repository's existing unit test already constitutes a working PoC: it signs `b"hello"`, flips `s` and the recovery id to derive `alt_signature`, and demonstrates that `agave_precompiles::secp256k1::verify` accepts an instruction containing *both* the original and the flipped signature for the same eth address and message with no error.
