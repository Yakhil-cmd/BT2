### Title
AA payment composer does not pre-check `spender_attested`/`transfer_condition` before sending or bouncing asset payments, allowing funds sent to an AA to become permanently stuck when the trigger/output address is not attested for the asset - (File: aa_composer.js)

### Summary
`Bracket.sol`'s bug is that orders can be created with a recipient that a blacklist-gated token will refuse to receive, and the same lack-of-validation later blocks `cancelOrder`'s refund path, freezing funds and filling the pending-orders queue. Obyte's autonomous-agent (AA) engine has an analogous "gated asset" concept — assets can be defined with `spender_attested` (output address must be attested by trusted attestors) and `transfer_condition`/`issue_condition` (arbitrary oscript conditions) — enforced in `validatePaymentInputsAndOutputs` in `validation.js`. However, the AA payment composer in `aa_composer.js` does not check these conditions before building and attempting to save a payment message, relying on the generic validator to reject the unit and only then triggers a `bounce()`.

### Finding Description
When an AA sends payment messages (`sendUnit` in `aa_composer.js`), for non-base assets it loads asset info via `storage.loadAssetWithListOfAttestedAuthors` and only special-cases `fixed_denominations` (skip) and `is_private` (fail) before calling `completePaymentPayload` and ultimately `validateAndSaveUnit`: [1](#0-0) 

It never checks `objAsset.spender_attested` or `objAsset.transfer_condition` against the destination addresses at composition time. The actual enforcement only happens later, deep in `validation.js`, at unit-save time: [2](#0-1) 

If that validation fails, `validateAndSaveUnit`'s callback calls `bounce(err)`: [3](#0-2) 

The `bounce()` function itself composes a refund payment that sends the *same asset* back to `trigger.address` and re-invokes `sendUnit(messages)`: [4](#0-3) 

Crucially, `bounce()` guards re-entrancy with `bBouncing`: if this refund unit *also* fails validation (e.g., because `trigger.address` itself is not attested for the asset, or fails the asset's `transfer_condition`), `bounce()` is invoked a second time, and since `bBouncing` is already `true`, it short-circuits to `finish(null)`: [5](#0-4) 

`finish(null)` treats this as a normal successful (non-bounced) completion with no response unit — the AA silently keeps/consumes the received asset balance with no output message and no way for the sender to reclaim it: [6](#0-5) 

This mirrors the root cause in the Sherlock report: the protocol composes a transfer to/for an address without validating that a refund/cancellation path to that same address is actually possible, and the downstream "cancel" (here: bounce) logic then fails for the same reason the forward transfer would have failed.

### Impact Explanation
Funds sent by a trigger unit to an AA in a `spender_attested`/`transfer_condition`-gated asset can become permanently locked at the AA address with no way to bounce them back, if:
- the trigger's own address (`trigger.address`) is not on the attestor's attested list (or otherwise fails the asset's `transfer_condition`), and
- the AA's response logic would (successfully or on error) attempt to pay out or bounce that asset back to `trigger.address`.

Because the composer does not pre-validate the destination against the asset's gating rules, an AA operating on a gated asset can silently swallow user deposits instead of returning them, and — combined with attacker-chosen trigger addresses/timing — can be intentionally triggered to freeze AA-held asset balances. This is a fund-freezing/loss condition affecting AA fund custody, matching the "Medium/High: AA fund loss or freezing" acceptance criterion.

### Likelihood Explanation
Requires an asset definition with `spender_attested: true` (or a `transfer_condition`) to exist and be used with an AA that forwards/bounces that asset back to the trigger address — a legitimate and documented AA/asset combination, not a contrived edge case. Any AA developer building on top of "permissioned"/attested assets (a supported first-class ocore feature) is exposed; a user (or the AA developer's own logic) triggering with an unattested/disqualified address is sufficient to reach the bug, requiring no privileged access — matching the required unprivileged AA-trigger-sender reachability.

### Recommendation
Before composing a payment message for a non-base asset in `sendUnit`/`bounce` in `aa_composer.js`, validate the destination address(es) against `objAsset.spender_attested` (via `storage.filterAttestedAddresses`) and `objAsset.transfer_condition` (via `Definition.evaluateAssetCondition`), the same checks already performed in `validation.js`'s `validatePaymentInputsAndOutputs`. If a payout or bounce destination fails these checks, treat it explicitly (e.g., bounce with a clear error before wasting a second composition attempt, or fall back to `finish(null)` only after logging/exposing that the asset is stuck) rather than silently discovering the failure at `validateAndSaveUnit` and potentially reaching the double-bounce dead end that swallows the funds with no recorded response payment.

### Proof of Concept
Conceptual reproduction (could not be executed in this read-only session; recommend validating on a Devin session with test harness):
1. Definer publishes an asset `A` with `spender_attested: true` and attestor `X`.
2. Deploy an AA whose `messages` include, on trigger, sending asset `A` back to `trigger.address` (e.g., a pass-through/swap-style AA), and rely on `bounce()` for any failure path.
3. An address `U` that is *not* attested by `X` sends asset `A` to the AA as a trigger (this is possible because the payment into the AA only requires the AA's own address to be attested as the payment's output, not the sender `U`).
4. AA logic runs; suppose it hits an internal condition causing `bounce(err)` — `bounce()` tries to refund asset `A` to `trigger.address` = `U`.
5. `sendUnit` composes this refund payment without checking `spender_attested`; `validateAndSaveUnit` rejects it with `"some output addresses are not attested"`.
6. `bounce()` is re-entered, `bBouncing` is already `true`, so it calls `finish(null)` — the AA response is recorded as non-bounced with no response unit, and asset `A` balance credited to the AA is not returned to `U`, effectively frozen at the AA address. [1](#0-0) [4](#0-3) [2](#0-1) [6](#0-5)
