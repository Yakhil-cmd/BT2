### Title
Signature verification org can diverge from the mutated stack's org, letting a forged `pull_request:unlabeled` webhook write another repository's `PullRequest#labels` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects the GitHub App/secret to check against using `repository_owner`, which is parsed from `params.dig('repository','owner','login')` [1](#0-0) . `LabelCapturingHandler` (and all other `pull_request` handlers) instead resolve the target repository/stack from `params.repository.full_name` [2](#0-1) . Nothing enforces that these two attacker-supplied fields agree, so an attacker can pass signature verification under an org with no `webhook_secret` while pointing the payload's `repository.full_name` at a completely different, victim-owned repository/stack.

### Finding Description
The broken binding is the implicit assumption:
`params.dig('repository','owner','login') == owner_portion(params.repository.full_name)`

Both sides of this equality are independently attacker-controlled JSON fields inside the same POST body, and no code enforces they match:

- `verify_signature` computes `repository_owner` purely from `params['repository']['owner']['login']` (falling back to `params['organization']['login']`) and uses it only to select which `GitHubApp`/secret to check the signature against: `Shipit.github(organization: repository_owner)` → `github_app.verify_webhook_signature(...)` [3](#0-2) .
- `GitHubApp#verify_webhook_signature` returns `true` unconditionally when `@webhook_secret` is blank/unset for that organization [4](#0-3) .
- The handler that actually mutates state, `LabelCapturingHandler`, resolves `repository` via `Shipit::Repository.from_github_repo_name(params.repository.full_name)` — a completely separate field from `repository.owner.login` used in step 1 [5](#0-4) , then loads the target `ReviewStack` by PR-derived environment `"pr#{params.number}"` within that repository's `review_stacks` scope [6](#0-5) , and finally calls `pull_request.update!(labels: params.pull_request.labels.map(&:name))` [7](#0-6) .

Exploit flow: attacker registers/controls a GitHub org, e.g. `attacker-org`, that is configured in Shipit's `github` secrets section with no `webhook_secret` (or targets any org the operator forgot to set a secret for) [8](#0-7) . Attacker sends `POST /webhooks` with header `X-Github-Event: pull_request`, body:
```json
{
  "action": "unlabeled",
  "number": 1,
  "repository": { "owner": {"login": "attacker-org"}, "full_name": "victim-org/victim-repo" },
  "pull_request": { ..., "labels": [{"name": "forced_up"}], "state": "open", "head": {...}, "user": {...}, "assignees": [] },
  "sender": {"login": "attacker"}
}
```
`verify_signature` looks up `Shipit.github(organization: "attacker-org")`, whose `webhook_secret` is unset, so `verify_webhook_signature` returns `true` regardless of the `X-Hub-Signature` header content (attacker doesn't even need a valid HMAC) [9](#0-8) . The request passes and `LabelCapturingHandler` (and any other `pull_request` handler present) then runs against `victim-org/victim-repo`'s review stack for PR #1, persisting attacker-chosen labels onto that stack's `PullRequest` record.

Downstream amplification: `ReviewStack#env` merges the persisted `pull_request.labels` as uppercased boolean env keys on top of the stack's normal environment [10](#0-9) , and the test suite confirms label names become `env["WIP"]`, `env["BUG"]`, etc. [11](#0-10) . Deploy gating relies on `Commit#blocked?`, which checks whether any status in `stack.blocking_statuses` is `blocking?` (i.e., non-success and configured as blocking) among undeployed commits [12](#0-11)  and [13](#0-12) . If a stack's deploy pipeline or `shipit.yml`-driven checks read the injected env vars (a "forced status" scenario driven by these env keys, as referenced by the question), an attacker-controlled label from an unrelated repository/org can flip state on the victim stack that gates deploys.

None of the existing guards stop this: `drop_unhandled_event` only checks the event type is registered, `ExplicitParameters` only validates shape/types (not cross-field consistency), and `verify_signature`'s org selection is fully decoupled from the org/repo actually mutated by the handler.

### Impact Explanation
An unauthenticated attacker can write to `PullRequest#labels` on a review stack belonging to a repository/organization they do not own or control, as long as: (a) the payload's `repository.owner.login` names any org with no configured `webhook_secret` (a value the attacker fully controls in the JSON body and doesn't need to actually own), and (b) the payload's `repository.full_name` names the victim's actual `owner/repo`, matching an existing `PullRequest#number`. This is a cross-tenant/cross-repository state write — one repo's (attacker's chosen, secret-less) forged payload mutates another, unrelated repository's stack record — matching the Critical "payload for one repository mutating another's stack" category. The attack is fully repeatable against any repository/stack in the Shipit instance and is not limited to a single victim.

### Likelihood Explanation
Preconditions: at least one org configured in Shipit's `github` secrets with `webhook_secret` unset (explicitly documented as "optional" in `docs/setup.md`) [14](#0-13) , and a target stack/PR combination that exists (`Repository.from_github_repo_name` + PR number → `environment: "pr#{number}"`). Attacker cost is a single unauthenticated HTTP POST with a crafted JSON body; no valid GitHub signature, session, API token, or team membership is required. This is trivially repeatable and scriptable against any repo/PR number pair.

### Recommendation
Bind signature verification to the same repository identity the handlers act on: derive `repository_owner` from `params.repository.full_name`'s owner segment (or require it to match `params.dig('repository','owner','login')` and reject mismatches), and reject webhooks where the two disagree before dispatching to handlers. Additionally, consider making `webhook_secret` mandatory for all configured organizations so `verify_webhook_signature` never silently returns `true`.

### Proof of Concept
Minitest (`test/controllers/webhooks_controller_test.rb`-style):
```ruby
test "forged pull_request:unlabeled from a no-secret org mutates a victim stack's PullRequest" do
  # Victim: configured normally, has blocking_statuses set and an open review stack for PR #1
  victim_stack = shipit_stacks(:review_stack) # repo "victim-org/victim-repo"
  victim_stack.pull_request.update!(labels: [])

  # Attacker-chosen org with no webhook_secret configured
  Shipit.stubs(:github).with(organization: "attacker-org").returns(
    Shipit::GitHubApp.new("attacker-org", {}) # no webhook_secret => verify_webhook_signature always true
  )

  request.headers["X-Github-Event"] = "pull_request"
  body = {
    action: "unlabeled",
    number: 1,
    repository: { owner: { login: "attacker-org" }, full_name: "victim-org/victim-repo" },
    pull_request: {
      id: 1, number: 1, url: "x", title: "x", state: "open",
      additions: 0, deletions: 0,
      head: { sha: "a"*40, ref: "attacker-branch" },
      user: { login: "attacker" }, assignees: [],
      labels: [{ name: "forced_up" }]
    },
    sender: { login: "attacker" }
  }.to_json

  post :create, body:, as: :json

  assert_equal ["forced_up"], victim_stack.pull_request.reload.labels
  # Binding check: signature-checked org ("attacker-org") != mutated repo's owner ("victim-org")
  refute_equal "attacker-org", "victim-org"
end
```
This demonstrates the equality `signature_org == mutated_repo_owner` is false yet the mutation still occurs, confirming the vulnerability.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

### Using Multiple Github Applications

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently. The top-level keys should be the name of each Github organization, and the following sub-keys are the Github app details for that particular organization.
