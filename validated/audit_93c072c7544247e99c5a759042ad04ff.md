### Title
Cross-organization team membership mutation via globally-scoped `github_id` lookup in `MembershipHandler#process` - ([File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`MembershipHandler#process` resolves the `Team` record solely by the webhook's `team.id` (GitHub's globally unique team identifier) and never checks that the organization that actually signed the webhook (`params.organization.login`) matches the `organization` already recorded on that `Team`. In a multi-organization Shipit deployment, an attacker who controls a legitimately-configured, unrelated GitHub organization can send a validly-signed `membership` webhook naming a foreign team's numeric `github_id`, causing Shipit to mutate that foreign team's roster (e.g., remove a real maintainer) as if the request had come from the team's own organization.

### Finding Description
The broken binding, stated as an equality that must hold but is never checked: `params.organization.login == team.organization` before `team.add_member(member)` / `team.members.delete(member)` is executed.

Trace:
- `WebhooksController#verify_signature` selects the GitHub App/secret via `Shipit.github(organization: repository_owner)`, where `repository_owner` falls back to `params.dig('organization', 'login')` for organization-level events like `membership` [1](#0-0) [2](#0-1) . This correctly proves the request was signed by *some* organization onboarded into Shipit — specifically the attacker's own organization — but it never ties that organization to the team being mutated.
- `MembershipHandler#process` then looks up (or creates) the `Team` purely by the numeric `github_id` supplied in the payload, and resolves the target `User` purely by login, with no comparison to the organization that just passed signature verification [3](#0-2) .
- `find_or_create_team!` uses `Team.find_or_create_by!(github_id: params.team.id)`; the `organization:` assignment only happens inside the creation block, so if a `Team` row with that `github_id` already exists (created earlier from a legitimate event from the real owning organization), the existing row is returned unchanged and the `organization` field is never re-validated against the current request's organization [4](#0-3) .
- `team.members.delete(member)` / `team.add_member(member)` then operate on that resolved `Team`/`User` pair unconditionally [5](#0-4) [6](#0-5) .

Exploit flow: Shipit is configured (via `secrets.github`) with multiple organizations, each with its own `webhook_secret`, resolved through `Shipit.github_app_config` [7](#0-6) . The attacker legitimately administers one such onboarded organization ("attacker-org") and thus legitimately possesses that organization's webhook secret — no Shipit secret is stolen. The attacker crafts a `membership` webhook, signs it with the attacker-org secret, and sets:
- `action: 'removed'`
- `team: { id: <victim team's real GitHub team ID>, name, slug, url }`
- `organization: { login: 'attacker-org' }`
- `member: { login: '<real maintainer's public GitHub login>' }`

`verify_signature` succeeds (the signature genuinely matches attacker-org's secret and attacker-org's own webhook), so the request is accepted as authentic — but authentic only for attacker-org, not for the victim team's real owning organization. `MembershipHandler#process` then deletes the real maintainer's membership in the victim team, entirely driven by a payload the victim organization never sent or observed.

Existing guards fail here because `verify_signature` answers "was this signed by *some* trusted org?" not "was this signed by the org that owns *this specific team*?" — no code path enforces the latter equality.

### Impact Explanation
A request from one organization's legitimately-configured webhook can delete (or add) team memberships belonging to a completely different organization's team, as long as the attacker knows/guesses the target team's numeric GitHub `id`. This is an authorization downgrade / denial of legitimate access for a real privileged Shipit user (a maintainer loses `Shipit::Membership`, and thus any team-derived privileges such as `Shipit.github_teams` authorization), and is repeatable against any team whose `github_id` the attacker can obtain, across any organization sharing the same Shipit instance. This matches the "payload for one repository/organization mutating another organization's team" Critical category.

### Likelihood Explanation
Requires Shipit be configured for multiple organizations (the per-org `secrets.github` schema) and the attacker to legitimately control one of those onboarded organizations — a normal multi-tenant Shipit deployment scenario, not a secret leak. The attacker also needs the numeric GitHub `team.id` of the target team, which is not secret-key material but must be known/guessed; it can be observed from prior webhook deliveries, GitHub API responses, or team URLs the attacker has any visibility into. Given these two mild preconditions, the attack is a single crafted HTTP POST and fully repeatable/idempotent (further `removed` events keep the maintainer locked out).

### Recommendation
In `MembershipHandler#process`, verify that `params.organization.login` (case-insensitively) matches the `Team`'s stored `organization` before performing any `add_member`/`delete`; reject or no-op the event when they differ. Additionally, `find_or_create_team!` should scope its lookup by both `github_id` and `organization`, refusing to reuse/attach a team row owned by a different organization than the one that just passed webhook verification.

### Proof of Concept
```ruby
test ":membership from a foreign organization cannot mutate another organization's team" do
  victim_team = shipit_teams(:shopify_developers) # organization: 'shopify'
  maintainer = shipit_users(:walrus)
  victim_team.add_member(maintainer)
  assert_includes maintainer.teams, victim_team

  @request.headers['X-Github-Event'] = 'membership'
  forged_payload = {
    action: 'removed',
    team: { id: victim_team.github_id, name: victim_team.name, slug: victim_team.slug, url: victim_team.api_url },
    organization: { login: 'attacker-org' }, # a different, attacker-controlled org onboarded in Shipit
    member: { login: maintainer.login }
  }.to_json

  # signed with attacker-org's own legitimately configured webhook_secret
  signature = 'sha1=' + OpenSSL::HMAC.hexdigest('sha1', attacker_org_webhook_secret, forged_payload)
  @request.headers['X-Hub-Signature'] = signature

  post :create, body: forged_payload, as: :json
  assert_response :ok

  maintainer.reload
  refute_includes maintainer.teams, victim_team # BROKEN BINDING: params.organization.login ('attacker-org') != victim_team.organization ('shopify'), yet mutation succeeded
end
```

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
