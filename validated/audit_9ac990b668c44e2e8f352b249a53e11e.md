### Title
`Api::CCMenuController#stack` ignores API-client stack scoping, allowing a stack-scoped token to read any stack's build status - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
### Finding Description
`ApiClient` supports scoping a token to a single stack via its optional `belongs_to :stack` association [1](#0-0) . `Api::BaseController` is designed to enforce this binding by scoping the `stacks` relation to `current_api_client.stack_id` whenever the client is stack-scoped, and by deriving `stack` from that scoped relation with `stacks.from_param!(params[:stack_id])`: `stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all` [2](#0-1) . `check_permissions!` on `ApiClient` only checks that a permission string like `read:stack` exists in the token's `permissions` array — it never checks the token's `stack_id` against the requested resource [3](#0-2) .

`Api::CCMenuController` overrides `stack` and bypasses the scoped `stacks` helper entirely, resolving the target stack directly from the global `Stack` collection: `@stack ||= Stack.from_param!(params[:stack_id])` [4](#0-3) . It only requires the generic `:read, :stack` permission and authenticates the client from a `token` query parameter [5](#0-4) . This breaks the binding "stack a token authorizes == stack it touches": a token that was authorized (and possibly deliberately restricted via `ApiClient#stack_id`) for stack A can be replayed against `show?stack_id=<B>` to read stack B's data.

### Impact Explanation
The `show` action renders `deploy.running?`, `deploy.ended_at`/`started_at`/`created_at`, `deploy.id`, and `stack.merge_status` for the resolved stack in `app/views/shipit/ccmenu/project.xml.builder` [6](#0-5) . Any holder of a valid, stack-scoped, `read:stack`-permission API token (e.g. a CI-status widget token meant to be limited to one project) can enumerate `stack_id` params and obtain unauthenticated read of another stack's deploy/build state — matching the "unauthenticated read of stack state" High-severity class, since access controls that should confine the token to its assigned stack are not enforced for this endpoint.

### Likelihood Explanation
Any party who legitimately possesses one working CCMenu/API token (even one intentionally scoped to a single, low-sensitivity stack) can trigger this simply by changing the `stack_id` query parameter — no additional secrets, sessions, or privileged access are required beyond the token itself, which is the intended, unprivileged use case for this endpoint (CI status badges).

### Recommendation
Have `Api::CCMenuController#stack` reuse the base controller's scoped `stacks` relation (`stacks.from_param!(params[:stack_id])`) instead of querying `Stack` directly, so that a stack-scoped `ApiClient` cannot resolve any stack outside its authorized `stack_id`.

### Proof of Concept
1. Create an `ApiClient` with `permissions: ['read:stack']` and `stack_id` set to Stack A's id; obtain its `authentication_token`.
2. Request `GET /api/1/ccmenu/<stack_A_id>.xml?token=<token>` — succeeds as intended.
3. Request `GET /api/1/ccmenu/<stack_B_id>.xml?token=<token>` where B is a different stack the token was never authorized for. Because `CCMenuController#stack` calls `Stack.from_param!(params[:stack_id])` on the unscoped `Stack` relation rather than `stacks.from_param!`, `check_permissions!(:read, :stack)` only checks the string permission and passes, and the response renders Stack B's `merge_status`, `activity` (running/sleeping), and latest deploy timing/id — data the token was never scoped to access.
