### Title
Webhook signature verification keys off an unverified `repository.owner.login`/`organization.login` field that can diverge from the repository the event handlers actually act on - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to validate the HMAC signature against by reading `repository.owner.login` (or falling back to `organization.login`) directly out of the **unverified** JSON body, before the signature has been checked. [1](#0-0) [2](#0-1) 

Shipit is explicitly designed to support multiple GitHub organizations, each configured with its own independent `webhook_secret`, `app_id`, and `installation_id`. [3](#0-2) 

Once the signature check passes, `create` dispatches the **entire raw payload** (including whatever `repository.full_name` / `repository.owner.login` fields the attacker put in it) to the registered handlers (`push`, `status`, `check_suite`, `membership`, etc.), which resolve the target `Stack`/`Repository`/`Commit` from those same payload fields. [4](#0-3) 

### Finding Description
This is a direct structural analog of H-9: a lookup key used to select the "authorization context" is taken from a payload field that is never itself covered/pinned by the trust check applied against it, allowing the verified identity (here: "which org's secret validated this HMAC") to diverge from the effectively-written resource (here: "which repository/stack the handler mutates").

The binding that should hold is:
`organization whose webhook_secret validated the signature == organization that owns the repository the handlers act upon`

Concretely:
1. `verify_signature` computes `repository_owner` from `params.dig('repository','owner','login') || params.dig('organization','login')` — fields inside the raw, not-yet-authenticated body. [2](#0-1) 
2. It uses that value to fetch `Shipit.github(organization: repository_owner)` and verify the HMAC with *that organization's* `webhook_secret`. [1](#0-0) 
3. HMAC-SHA1 only proves that "the body was signed by someone who knows Org A's `webhook_secret`" — it says nothing about which repository the body *describes*. Since the same field (`repository.owner.login`) is read once for secret-selection and independently re-read later by each handler for target resolution, nothing forces the two reads to agree with the actual target repository that the secret is scoped to protect.
4. A user who legitimately owns/administers a repository under Org A (and therefore, through normal GitHub webhook delivery, can obtain a validly-signed payload/secret for Org A) can submit a forged payload where `repository.owner.login = "OrgA"` (so the signature-selection step picks Org A's `webhook_secret`, which the attacker can compute against because they can generate real, validly-signed deliveries for their own Org A repo) while `repository.full_name`, `commit sha`, `branches`, or `team`/`member` fields reference a completely different stack/organization (`OrgB/victim-repo`) hosted on the same multi-tenant Shipit instance.
5. Since the signature only proves knowledge of Org A's secret, not that the body pertains to Org A's repositories, the request passes `verify_signature` and is handed to handlers that write state (queue `GithubSyncJob`, create commit `Status`, enqueue `RefreshCheckRunsJob`, create `Team`/`User` membership records) for `OrgB/victim-repo`, a repository the attacker has no relationship to.

This is the same class of bug as the Sherlock finding: the code establishes trust ("this HMAC came from Org A") but then acts on a different, unauthenticated dimension of the same payload ("target repository/org") that the trust check never actually pinned down — exactly like `_listing` staying keyed to the old owner/price while `ProtectedListings` moves on with a different accounting of the same token.

### Impact Explanation
If proven exploitable end-to-end, this would let an attacker who only controls a repository under one organization (Org A) forge webhook-driven writes against a different organization's stack (Org B) on a shared Shipit deployment — e.g., forcing a spurious `GithubSyncJob`/`CacheDeploySpecJob` run, injecting a fabricated commit `Status`, or creating bogus `Team`/`User` records tied to `membership` events for a repository/org they do not control. This falls into cross-repository/cross-organization writes without the corresponding GitHub authorization, which maps to the Critical impact bucket ("cross-repository writes").

### Likelihood Explanation
This requires: (a) a Shipit deployment configured to serve multiple GitHub organizations with independent `webhook_secret`s (an explicitly supported and documented configuration, per `secrets_double_github_app.yml`), and (b) the attacker controlling a repository/webhook under at least one of those organizations to obtain a validly-signed body. This is a real but non-trivial precondition — I could not fully trace every downstream handler (`push_handler.rb`, `status_handler.rb`, `check_suite_handler.rb`, `membership_handler.rb`) within the remaining budget to confirm each one resolves its target purely from payload fields with no secondary check against `repository_owner`/an installation-bound Repository record, so I cannot state with certainty that no handler performs an additional consistency check. This should be verified directly in `app/models/shipit/webhooks/handlers/*.rb` and `app/models/shipit/hook.rb`/`Repository.from_github_repo_name` before treating this as fully confirmed.

### Recommendation
After the raw body is parsed, re-derive the organization/repository strictly from the same value used to select the verification secret, and reject (422) any request where a resolved `Stack`/`Repository`'s owner does not match the organization whose secret validated the signature. Concretely, in `WebhooksController`, once `Shipit::Repository.from_github_repo_name(params.dig('repository','full_name'))` (or equivalent) is resolved, assert its `owner` matches `repository_owner` used in `verify_signature`, and have each handler consume that pre-validated `Repository`/`Stack` object rather than independently re-reading `full_name`/`owner.login` out of the raw payload.

### Proof of Concept
Conceptual (not runnable without a live multi-org Shipit deployment and knowledge of Org A's `webhook_secret`, which an attacker legitimately possesses through their own Org A repo's webhook deliveries):

```
POST /webhooks HTTP/1.1
X-Github-Event: push
X-Hub-Signature: sha1=<HMAC-SHA1(body, OrgA_webhook_secret)>

{
  "repository": {
    "owner": {"login": "OrgA"},          // used by verify_signature to pick OrgA's secret
    "full_name": "OrgB/victim-repo"       // used by PushHandler to resolve the actual Stack
  },
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>"
}
```

`verify_signature` computes `repository_owner = "OrgA"`, fetches `Shipit.github(organization: "OrgA")`, and validates the signature successfully (attacker knows `OrgA_webhook_secret`). The `push` handler then acts on `OrgB/victim-repo`, a repository the attacker never proved control over. Full confirmation requires reading `app/models/shipit/webhooks/handlers/push_handler.rb` and related handlers to confirm the exact resolution path from `full_name` to `Stack`, which was not fully traced in this analysis due to tool-call limits.
