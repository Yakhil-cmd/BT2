### Title
Cross-repository CI status corruption via unscoped SHA lookup in `Shipit::Webhooks::Handlers::StatusHandler#process` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` resolves the target `Commit` purely by `sha`, with no scoping to the `repository` named in the incoming GitHub `status` webhook payload. Any two `Stack`/`Repository` records that happen to track a commit sharing the same `sha` (e.g. forks with common ancestor commits, or repos imported into more than one Shipit `Stack`) will both be mutated by a single webhook, even though the webhook payload identifies only one repository.

### Finding Description
The broken binding, stated as an equality that should hold but does not: `params.dig('repository','full_name') == commit.stack.repository.full_name` for every `Commit` row updated by the handler. The code never enforces this.

Path:
- `Shipit::WebhooksController#create` dispatches the parsed payload to `Shipit::Webhooks.for_event(event)` handlers after `verify_signature`, which only checks the HMAC using the org derived from `repository.owner.login` [1](#0-0) . It never uses `repository.full_name` to constrain which `Commit`/`Stack` rows can be touched.
- `StatusHandler#process` executes `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [2](#0-1) . The `params` schema only requires `:sha` and `:state` (plus optional description/target_url/context/created_at/branches) — no repository field is required or checked against the matched commit's stack [3](#0-2) .
- `Commit#create_status_from_github!` unconditionally records the attacker-supplied `state` (`success`, `failure`, `error`, `pending`) into `statuses` via `add_status`, which recomputes `Commit#status`, potentially flips `deployable?`/`blocked?`, and triggers `Hook.emit(:deployable_status, ...)` and `stack.schedule_merges` [4](#0-3) [5](#0-4) .

Why guards fail: `verify_signature` authenticates that the request legitimately originates from the GitHub organization named in the payload's `repository.owner.login` — it proves *who sent it*, not *which Shipit Stack/Commit rows may be affected*. Because `StatusHandler` never re-derives the target `Stack` from `params.repository` and cross-checks it against the `Commit#stack` the query matched, a validly-signed webhook for repository/org A can still mutate a `Commit` belonging to Stack B whenever both stacks contain a row with the identical `sha` (common in forked repositories imported as separate Shipit `Stack`s, sharing history/commits with the upstream or a sibling fork).

Attacker request: attacker (an admin of their own onboarded fork/org, able to sign requests for that org) sends `POST /webhooks` with `X-Github-Event: status` and body `{"sha": "<shared-ancestor-sha>", "state": "success"|"failure", "repository": {"owner": {"login": "attacker-org"}}}`. If a `Commit` with that same `sha` also belongs to a different `Stack` (e.g. an upstream/fork sibling), that commit's CI polarity is updated too.

### Impact Explanation
For every `Commit` row sharing the attacker-known `sha` across `Stack`s, the attacker can flip `deployable?`/`blocked?` state:
- `state: success` can make a previously blocked/pending commit `deployable?` in a victim stack, potentially unblocking or accelerating an unauthorized deploy through `schedule_continuous_delivery`/`stack.schedule_merges`.
- `state: failure`/`error` can grief a victim's currently green commit into `blocked?`, denying deploys for a stack the attacker does not control.

This is a cross-tenant write to another repository's `Commit`/`Stack` state from a payload the victim never authenticated, matching the Critical category "a payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy, rollback or merge." Blast radius is limited to `Stack`s that happen to share a commit `sha` with the attacker's repository (commonly true for forks/mirrors of the same upstream history), and is repeatable per shared sha for as many webhook posts as the attacker wishes.

### Likelihood Explanation
Preconditions: two `Stack`/`Repository` fixtures whose commit histories overlap (fork relationship, shared upstream base commits, or a monorepo mirrored into multiple `Stack`s) so that a `Commit.sha` collision naturally exists — this does not require breaking SHA-1, only ordinary shared git history, which is a realistic Shipit deployment pattern (forks of the same project both onboarded to Shipit). Attacker cost: must be able to send a validly-signed webhook for at least one org/repo they administer (per the rules, this is granted as "emit webhooks from a repository they own"). No Shipit session, API token, or operator role is required. This is straightforward and repeatable against any pair of stacks sharing a commit sha.

### Recommendation
In `StatusHandler#process` (and analogously in other SHA-keyed webhook handlers), scope the `Commit` lookup by the repository named in the payload, e.g. resolve the target `Stack`/`Repository` from `params.dig('repository','full_name')` first, then constrain `Commit.where(sha: params.sha, stack_id: matching_stack_ids)`, discarding matches whose `stack.repository.full_name` doesn't equal the payload's `repository.full_name`.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb
require 'test_helper'

module Shipit
  module Webhooks
    module Handlers
      class StatusHandlerCrossRepoTest < ActiveSupport::TestCase
        setup do
          @stack_a = shipit_stacks(:shipit)          # repository A
          @stack_b = Shipit::Stack.create!(repository: Shipit::Repository.create!(owner: 'other-org', name: 'other-repo'), environment: 'production')
          @shared_sha = '2adaad1ad30c235d3a6e7981dfc1742f7ecb1e85'

          @commit_a = @stack_a.commits.create!(sha: @shared_sha, message: 'shared ancestor')
          @commit_b = @stack_b.commits.create!(sha: @shared_sha, message: 'shared ancestor (fork)')
        end

        %w[success failure error pending].each do |state|
          test "status webhook for repo A with state=#{state} also mutates commit in unrelated stack B" do
            # Binding under test: params.repository.full_name == commit.stack.repository.full_name
            # Before: neither commit has a status matching `state`
            refute_equal state, @commit_a.reload.state
            refute_equal state, @commit_b.reload.state

            payload = {
              sha: @shared_sha,
              state:,
              repository: { full_name: @stack_a.repository.full_name, owner: { login: @stack_a.repository.owner } }
            }.with_indifferent_access

            StatusHandler.new.process_test_entrypoint(payload) # invoke handler logic directly

            # After: both commits changed, even though payload named only stack_a's repository
            assert_equal state, @commit_a.reload.state
            assert_equal state, @commit_b.reload.state, "cross-repository mutation: stack B commit changed from a webhook naming stack A's repository"
          end
        end
      end
    end
  end
end
```
Note: the handler's `process` is invoked via `ExplicitParameters`-wrapped `params`; the PoC should call through `Shipit::Webhooks.for_event('status').each { |h| h.call(payload) }` or directly build the `params` object as done in existing handler tests, asserting `@commit_b.reload.state == state` while `payload['repository']['full_name']` only ever names `@stack_a.repository.full_name`.

      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }

      if previous_status.simple_state != new_status.simple_state
