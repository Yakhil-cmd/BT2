### Title
Unscoped `Commit.where(sha:)` lookup in `StatusHandler#process` lets a status webhook from any authenticated repository mutate commit rows belonging to a different stack - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` resolves the target commit(s) purely by `sha`, with no constraint on the repository that the webhook signature actually authenticated. Because SHA-1 is content-addressable and reproducible cross-repository (an attacker who knows/reconstructs a victim commit's exact object content can create an object with the identical SHA in their own, attacker-owned repository), an attacker can trigger a validly-signed webhook from their own repo that writes a GitHub status onto a `Shipit::Commit` row belonging to a completely different stack.

### Finding Description
The broken invariant, stated as an equality that should hold but doesn't: `commit.stack.repository == payload.repository` should always be true for every commit mutated by a status webhook, but the code enforces no such check.

`Shipit::WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-49`) only verifies that the payload was signed by the GitHub App/webhook secret belonging to `repository_owner` extracted from the payload itself — i.e., it proves "this payload was legitimately sent by GitHub for *some* repo the attacker owns/controls," not that the payload's `sha` belongs to that repo.

`StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`):
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
This queries `Commit` with no `stack_id`/repository scoping — any `Shipit::Commit` row across any stack/repository in the Shipit instance whose `sha` matches is updated.

Exploit flow:
1. Attacker owns/controls a GitHub repository (or organization) that has a Shipit-configured GitHub App/webhook installed — satisfying `verify_signature`.
2. Attacker learns (or reproduces) the exact SHA-1 of a commit that also exists in a victim's Shipit stack (public repos routinely expose full commit metadata; reproducing an identical git commit object — same tree, parents, author/committer, timestamps, message — under a different remote yields an identical SHA1, a known cross-repo SHA-sharing technique).
3. Attacker pushes/creates that identical commit under their own repo, then triggers (or GitHub naturally sends) a `status` event for `context: deploy/production`, `sha: <shared sha>`, `state: success` from their own repo.
4. `verify_signature` succeeds because the signature is valid for the attacker's own organization/app.
5. `StatusHandler#process` finds the victim's `Commit` row (same SHA, different `stack_id`) and calls `commit.create_status_from_github!(params)`, writing a status onto it.
6. In `Shipit::Commit#add_status` (`app/models/shipit/commit.rb:366-386`), a state transition to success calls `stack.schedule_merges if new_status.pending? || new_status.success?`. If the victim stack has `merge_queue_enabled: true` and this commit is the head of a pending `MergeRequest` requiring `deploy/production`, the merge queue evaluation (`MergeRequest#all_status_checks_passed?` / `StatusChecker`, `app/models/shipit/merge_request.rb:193-206`) may now see the required status as satisfied, allowing `MergeRequest#merge!` (`app/models/shipit/merge_request.rb:164-191`) to fire — merging/deploying code the victim never approved via that status context.

None of the existing guards catch this: `verify_signature` authenticates the *sender's own org*, not the *SHA's owning stack*; `drop_unhandled_event` and the `ExplicitParameters` schema only validate payload shape; there is no `Repository`/`stack_id` check anywhere in `StatusHandler` or `Commit.create_status_from_github!`.

### Impact Explanation
A payload authenticated for repository A can flip CI state (and potentially trigger a merge/ship or block) on a commit belonging to stack B, entirely across tenant/repository boundaries. This matches the "Critical" category: a payload for one repository mutating another's stack/commit, and — when `merge_queue_enabled` is true and the forged context is the required one — an unauthorized merge (`MergeRequest#merge!`) or deploy gating decision on the victim stack. This is repeatable against any stack/commit whose SHA the attacker can reproduce or is shared (e.g., commits cherry-picked/merged identically across mirrors, forks, or template repos), and the blast radius spans all stacks in the Shipit instance since `Commit` is queried globally.

### Likelihood Explanation
Preconditions: attacker needs (a) any GitHub repo/org with a Shipit-registered webhook/App (cheap — public repos, personal orgs, or open-source forks commonly qualify), and (b) a commit whose SHA-1 collides with (is identical to) a commit that also exists in the victim's stack. Reproducing an identical SHA-1 for a *known* commit (not a hash collision attack, but exact object recreation) is feasible for public/shared history (mirrors, template repos, cross-forked commits, or simply commits that get replicated verbatim across repos as part of normal workflows such as vendoring/subtree merges). This is more constrained than "any arbitrary sha" but is a realistic and low-cost precondition for many real deployments (monorepo mirrors, org-wide template commits, shared release commits). Given the precondition is met, the attack is fully repeatable and requires no privileged access.

### Recommendation
Scope the commit lookup in `StatusHandler#process` to the repository that authenticated the webhook, e.g. join on `Stack -> Repository` and filter by the payload's `repository.full_name` (or `repository_owner`/`repository_id`) in addition to `sha`, mirroring the same repository binding enforced by `verify_signature`. Apply the same repository-scoping fix to any other handler (e.g. `CheckRunHandler`) that resolves commits solely by bare SHA.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb` conceptually):
1. Create `stack_a` (attacker's authenticated repo) and `stack_b` (victim, `merge_queue_enabled: true`, deploy spec requiring `deploy/production`).
2. Create `commit_b` under `stack_b` with `sha: "deadbeef..."` and no prior successful `deploy/production` status; create a pending `MergeRequest` on `stack_b` whose `head` is `commit_b`.
3. Create `commit_a` under `stack_a` with the **same** `sha: "deadbeef..."` (simulating a reproduced/shared commit object).
4. Build a `status` webhook payload: `{ sha: "deadbeef...", state: "success", context: "deploy/production", repository: { full_name: stack_a.repository.full_name, owner: { login: stack_a.repository.owner } } }`.
5. Call `Shipit::Webhooks::Handlers::StatusHandler.call(payload)` (bypassing/stubbing `verify_signature` as already-passed, since it only checks `stack_a`'s org).
6. Assert: `commit_b.reload.status.success?` is `true` even though the webhook never authenticated for `stack_b`'s repository — i.e., `commit_b.stack.repository != payload.repository` yet `commit_b`'s state changed.
7. Assert the side effect: `stack_b.merge_requests.find(mr.id).reload.merge_status` progresses (e.g. to `pending`/eligible-to-merge) or that `Stack#schedule_merges` was invoked for `stack_b`, demonstrating the merge-queue amplification from an unrelated repository's webhook.     def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)

        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
