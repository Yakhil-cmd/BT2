### Title
Webhook signature verification is bound to `repository.owner.login`, but the event is actually applied to `repository.full_name` / commit `sha`, allowing cross-organization webhook forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
In a multi-GitHub-App Shipit deployment, `WebhooksController#verify_signature` selects the HMAC secret to validate a webhook using `repository.owner.login` (or `organization.login`) from the JSON body, while the handlers that actually act on the payload (`Handlers::Handler#repository_name`, `PushHandler`, `StatusHandler`, etc.) use unrelated fields of the same attacker-controlled body (`repository.full_name`, `sha`) with no cross-check that they belong to the organization whose secret validated the request. This breaks the intended binding: `organization that authenticated == repository that is written`.

### Finding Description
`WebhooksController#verify_signature` picks the GitHub App/secret to validate against using only the owner login: [1](#0-0) [2](#0-1) 

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(...)
  head(422) unless verified
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

`Shipit.github(organization:)` looks up per-organization webhook secrets from `secrets.github` when the "multiple GitHub Applications" schema is used, as documented and tested: [3](#0-2) [4](#0-3) 

`verify_webhook_signature` HMACs the *entire raw body* with the secret belonging to that one organization: [5](#0-4) 

Once the signature check passes, the same raw JSON body is dispatched to handlers, which independently extract the repository to act on from a *different* field of the same body: [6](#0-5) 

```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
```

`PushHandler` uses this `stacks` scope to trigger `sync_github` for any matching stack: [7](#0-6) . `StatusHandler` goes further and doesn't even filter by repository at all — it matches purely on commit SHA across the whole install: [8](#0-7) 

Because signature verification and payload-consumption use two different, independently attacker-supplied fields (`repository.owner.login` vs. `repository.full_name` / bare `sha`) with no assertion that they are consistent, an attacker who possesses a valid webhook secret for *any one* organization configured on the Shipit instance (e.g., because they administer a GitHub App/organization that is legitimately onboarded to that Shipit instance) can forge a POST to `/webhooks` where:
- `repository.owner.login` = the organization whose secret they hold (so `verify_signature` passes), and
- `repository.full_name` (or `sha`, for `status` events) = a repository/commit belonging to a *different* organization/stack on the same Shipit instance.

The equality that should hold — "the organization whose secret authenticated the request" == "the repository/stack the handler operates on" — is never enforced.

### Impact Explanation
This crosses a genuine trust boundary between tenants of a single Shipit deployment (documented multi-org support). With a forged `push` webhook, an attacker can enqueue `GithubSyncJob`/`sync_github` for stacks in a repository they do not control, forcing resynchronization against an attacker-chosen `expected_head_sha`, which can drive out-of-band deploy behavior. With a forged `status` webhook, an attacker can inject a fabricated CI status (`state`, `context`, `target_url`, `description`) onto any commit in the system merely by knowing its SHA, which can be used to make deploy/merge gating checks (that rely on `Commit#create_status_from_github!`) appear green when they should not — enabling an unauthorized deploy path. This satisfies the "unauthorized deploy" bar.

### Likelihood Explanation
Requires an attacker to already hold a valid `webhook_secret` for at least one organization configured on the shared Shipit instance — this is a real but non-trivial precondition (multi-tenant Shipit installs with GitHub Apps across independently-trusted organizations). Given that precondition, the forgery itself is trivial: a single unauthenticated HTTP POST to `/webhooks` with a crafted JSON body and a correctly computed HMAC using the known secret. No GitHub session, API token, or `ApiClient` credential is needed.

### Recommendation
After `verify_signature` succeeds, assert that the organization used to select the verifying secret matches the organization actually referenced by the fields the handlers will consume (e.g., ensure `repository.full_name.split('/').first.casecmp?(repository_owner)` before dispatching to handlers), and have `StatusHandler` scope by repository (not just bare SHA) so cross-organization commit collisions cannot leak/forge statuses.

### Proof of Concept
1. Configure Shipit with two GitHub Apps, `OrgA` and `OrgB`, each with its own `webhook_secret` (as in the documented multi-org schema, cf. `test/dummy/config/secrets_double_github_app.yml`).
2. As an attacker who legitimately controls/knows `OrgA`'s `webhook_secret`, craft a `push` event JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>",
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/victim-repo" }
}
```
3. Compute `X-Hub-Signature: sha1=<hmac-sha1(OrgA_webhook_secret, body)>` and `X-Github-Event: push`, then POST to `/webhooks`.
4. `verify_signature` resolves `repository_owner` = `"OrgA"`, verifies successfully against `OrgA`'s secret.
5. `PushHandler#process` resolves `stacks` via `repository_name` = `"OrgB/victim-repo"`, and calls `sync_github(expected_head_sha: "<attacker-chosen-sha>")` on `OrgB`'s stacks, despite the request never being authenticated by `OrgB`'s credentials.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
