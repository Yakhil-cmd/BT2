## Analysis

I traced the report's core issue — instantaneous, on-chain pool state used as a price oracle without slippage/TWAP protection — to a real, concrete analog in `pallet-asset-conversion-tx-payment`. The `SwapAssetAdapter::withdraw_fee` function reads the pool's live spot price via `S::quote_price_tokens_for_exact_tokens` and immediately uses it to withdraw the exact fee amount, with **no user-supplied maximum-fee cap** to bound the price used, exactly analogous to Arrakis's uncapped reliance on `slot0`. [1](#0-0) [2](#0-1) 

### Title
`ChargeAssetTxPayment`/`SwapAssetAdapter` charges transaction fees using an unbounded spot pool price, exposing users to sandwich manipulation - ([File: substrate/frame/transaction-payment/asset-conversion-tx-payment/src/payment.rs])

### Summary
`pallet-asset-conversion-tx-payment`'s `SwapAssetAdapter::withdraw_fee` quotes the amount of a user-chosen fee-asset needed to cover the native-denominated transaction fee by calling `AssetConversion::quote_price_tokens_for_exact_tokens`, which reads the pool's current (spot) reserve balances via `get_reserves`. There is no maximum-fee parameter the signer can supply to cap the acceptable price, unlike the underlying `SwapCredit::swap_tokens_for_exact_tokens`/`amount_in_max` mechanism available elsewhere in the pallet.

### Finding Description
`get_reserves` returns the pool account's current token balances directly — an instantaneous, single-block-observable value with no time-weighting, identical in nature to Uniswap V3's `slot0`: [2](#0-1) 

`quote_price_tokens_for_exact_tokens` derives its quote directly from these live reserves: [3](#0-2) 

`SwapAssetAdapter::withdraw_fee` (used by `ChargeAssetTxPayment`) calls this quote function with the exact `fee` amount and no slippage bound, then withdraws precisely that computed amount from the signer: [4](#0-3) 

Crucially, this withdrawal happens in `TransactionExtension::prepare`, which executes at actual block-inclusion time (not at pool-validation time), so the price used is whatever the pool reflects at that instant in the block: [5](#0-4) 

The `ChargeAssetTxPayment` extension itself only carries `tip` and `asset_id` — no `max_fee`/slippage cap that the signer could use to protect themselves: [6](#0-5) 

An attacker who can get a large swap on the fee-paying pool included in the same block immediately before a victim's fee-paying extrinsic (e.g., via same-account sequential-nonce ordering guarantees, or MEV-style priority/tip front-running of a pending transaction they observe) can transiently skew the pool's reserve ratio. The victim's `withdraw_fee` then quotes and withdraws a fee-asset amount computed off that skewed ratio — silently overcharging the victim — after which the attacker can swap back to restore the pool, extracting the created slippage/LP-fee value. This directly mirrors the reported class: a critical monetary computation is driven by unprotected, attacker-movable spot AMM state.

### Impact Explanation
Each affected transaction can be forced to pay a fee-asset amount larger than fair market value, bounded by how far the attacker can move the specific pool within the block and by the size of the victim's transaction fee. This is a loss-of-funds bug for the fee payer, but the magnitude is inherently bounded by per-transaction fee size (typically small relative to a user's holdings), unlike theft of arbitrary user balances. This aligns most closely with a Medium-severity finding: real, demonstrable value extraction, but scoped to transaction-fee amounts rather than unbounded asset theft.

### Likelihood Explanation
Any chain that enables `pallet-asset-conversion-tx-payment` with `SwapAssetAdapter` and permits users to pay fees in a non-native asset backed by a `pallet-asset-conversion` pool is exposed. No privileged role is required — only the ability to place a swap transaction adjacent to (before) the victim's fee-paying transaction in the same block, achievable through generic transaction-pool prioritization/tip mechanics or same-account nonce ordering, without any validator/collator collusion.

### Recommendation
Add a signer-supplied maximum acceptable fee-asset amount (analogous to `amount_in_max` in `SwapCredit::swap_tokens_for_exact_tokens`) to `ChargeAssetTxPayment`/`OnChargeAssetTransaction::withdraw_fee`, and fail validation if the spot-quoted amount exceeds it. Alternatively, source the quote from a time-weighted or bounded-deviation price rather than the raw, single-block `get_reserves` balances.

### Proof of Concept
Guard checked: `SwapAssetAdapter::withdraw_fee` in `substrate/frame/transaction-payment/asset-conversion-tx-payment/src/payment.rs:142-157` performs no bound/slippage check against the caller-approved maximum before calling `F::withdraw(asset_id, who, asset_fee, ...)` — `asset_fee` is taken as-is from the unbounded spot quote.

Deployment evidence: `pallet_asset_conversion_tx_payment::Config` is wired with `SwapAssetAdapter` in production runtime configs, e.g. Penpal testing parachain: [7](#0-6) 

A minimal FRAME integration reproduction (extending the pallet's own test harness in `substrate/frame/transaction-payment/asset-conversion-tx-payment/src/tests.rs`) would:
1. `setup_lp(asset_id, balance_factor)` to create the fee-asset pool.
2. Record `quote_price_tokens_for_exact_tokens` for a fixed `fee_in_native` (baseline fee-asset cost).
3. Simulate an attacker swap (`AssetConversion::swap_exact_tokens_for_tokens`) against the same pool to skew reserves.
4. Re-run `ChargeAssetTxPayment::validate_and_prepare` for the victim and assert the withdrawn `fee_in_asset` is strictly larger than the pre-manipulation baseline, with no error/rejection despite the price having moved arbitrarily.
5. Swap back to restore the pool, and confirm the attacker recovers the shifted value (net of LP fee), demonstrating extractable value at the victim's expense.

This reproduction was not executed as part of this analysis (no test run was performed); it is provided as the exact scaffold needed using the existing test harness (`setup_lp`, `ChargeAssetTxPayment::validate_and_prepare` calls already present in `tests.rs`) to confirm the described unbounded-fee-quote behavior deterministically.

		pub fn quote_price_tokens_for_exact_tokens(
			asset1: T::AssetKind,
			asset2: T::AssetKind,
			amount: T::Balance,
			include_fee: bool,
		) -> Option<T::Balance> {
			// Swaps reject zero amounts, match that behavior.
			if amount.is_zero() {
				return None;
			}
			let pool_account = T::PoolLocator::pool_address(&asset1, &asset2).ok()?;

			let (balance1, balance2) = Self::get_reserves(asset1.clone(), asset2.clone()).ok()?;

			if balance1.is_zero() {
				return None;
			}

			// Swap withdrawals from pools use `keep_alive=true` (Preserve). Use the same
			// preservation level to determine the actual withdrawable amount.
			let max_output =
				T::Assets::reducible_balance(asset2.clone(), &pool_account, Preserve, Polite);
			if amount > max_output {
				return None;
			}

			if include_fee {
				let fee = Self::pool_fee_for(&asset1, &asset2).ok()?;
				Self::get_amount_in(fee, &amount, &balance1, &balance2).ok()
			} else {
				Self::quote(&amount, &balance2, &balance1).ok()
			}
		}
