### Title
Cross-repository Status forgery via global `sha` lookup in `StatusHandler#process` - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` resolves target `Commit` rows solely by `Commit.where(sha: params.sha)`, without any comparison to the webhook's `repository` field, even though `Handler#repository_name`/`Handler#stacks` exist precisely to bind a payload to its owning repository. Any commit sha collision (a common occurrence with forked/cherry-picked/shared history) lets an attacker's own legitimately-signed webhook write a `Status` onto a `Commit` belonging to an unrelated `Stack`.

### Finding Description
The broken binding is: `params.repository.full_name == commit.stack.repository.full_name` is never checked, whereas it should be enforced before `commit.create_status_from_github!(params)` is called.

Code path:
- `WebhooksController#create` parses the JSON body and dispatches to `Shipit::Webhooks.for_event('status')`, which is `[Handlers::StatusHandler]` [1](#0-0) [2](#0-1) .
- `verify_signature` only checks that the HMAC signature matches the GitHub App secret for `repository_owner` derived from the payload; it does not verify that the named repository/owner has any relationship with the commit being updated, nor does it check that the *sha* belongs to that repository [3](#0-2) . This guard authenticates "a message legitimately came from GitHub for org X," not "this sha belongs to org X's repository."
- `Handler#initialize` parses params via the `ExplicitParameters` schema defined in `StatusHandler`, which never declares `repository` as an accepted/required key [4](#0-3) .
- `Handler#repository_name`/`Handler#stacks` exist in the base class exactly to scope a payload to a repository's stacks [5](#0-4) , but `StatusHandler#process` never calls `stacks` or `repository_name`; it queries `Commit` globally by `sha` alone and mutates whatever rows match: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [6](#0-5) .
- `Commit belongs_to :stack` [7](#0-6) , so distinct `Stack`/repository records can each hold a `Commit` row with an identical `sha` (e.g., a fork or cherry-pick that preserves the original commit hash). `create_status_from_github!` then calls `add_status`, which can flip `deployable?`/blocking status and trigger `stack.schedule_merges` and `ContinuousDeliveryJob.perform_later(stack)` for the *victim's* stack [8](#0-7) [9](#0-8) [10](#0-9) .

Attack: the attacker owns a repository/org with the Shipit GitHub App installed (or any org whose webhook secret they legitimately control). They push/fork a commit whose sha matches (or is later cherry-picked to be identical to) a commit that already exists in the victim's Shipit-tracked stack (a routine occurrence for forks and cherry-picks, since git SHAs are content-addressed and independent of the repository they live in). The attacker then causes their own CI/webhook to emit a `status` event for that sha — a fully genuine, correctly-signed webhook from their own repository. `verify_signature` passes because the signature is validated only against the attacker's own organization/app secret, not against any repository/sha ownership check. `StatusHandler#process` finds the victim's `Commit` row purely by `sha` and writes an attacker-controlled `Status` (state/description/target_url/context) onto it, potentially unblocking the victim stack's deploy pipeline.

### Impact Explanation
An attacker can inject a forged commit status (e.g., `state: "success"`, arbitrary `context`) onto a `Commit` belonging to a `Stack`/repository they do not own and never authenticated for, because the handler performs no repository binding check at all. Since `create_status_from_github!` recomputes `deployable?`/`blocking?` and can schedule merges and continuous deployment jobs for the victim's stack, this can result in an unauthorized deploy being triggered on the victim's stack, or blocking-status manipulation that stalls/unblocks victim deploys. This matches the Critical category: "a payload for one repository mutating another's stack, commit, task, or team" and potentially "an unauthorized deploy."

### Likelihood Explanation
The attacker needs no Shipit credentials — only a repository they control with a legitimately configured/installed webhook (satisfying `verify_signature`), and a commit sha that collides with a commit already tracked in a victim `Stack`. Sha collisions across repositories are a routine, low-cost occurrence in real-world git workflows (forks, cherry-picks, shared submodules/monorepos), making this readily repeatable and requiring no cryptographic collision — only reuse of an existing, unmodified commit object.

### Recommendation
In `StatusHandler#process`, scope the `Commit` lookup by the handler's own `stacks`/`repository_name` binding (as the base `Handler` class already provides), e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` or join through `Stack` filtered by `Repository.from_github_repo_name(repository_name)`, and require `repository` in the `ExplicitParameters` schema so a payload lacking a resolvable repository is rejected outright.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb`):
1. Create two `Stack`s belonging to different `Repository` records (`victim_repo`, `attacker_repo`).
2. Create `Commit` `victim_commit` with `sha: "abc123"` under `victim_stack`.
3. Build a `status` webhook payload with `repository.full_name = attacker_repo.github_repo_name`, `sha: "abc123"`, `state: "success"`.
4. Call `Shipit::Webhooks::Handlers::StatusHandler.call(payload)`.
5. Assert: before the call, `victim_commit.statuses.count == 0`; after the call, `victim_commit.reload.statuses.count == 1` and the new `Status#state == "success"`, even though `payload['repository']['full_name'] != victim_repo.github_repo_name` — demonstrating the binding `params.repository.full_name == commit.stack.repository.full_name` is never enforced.

    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
