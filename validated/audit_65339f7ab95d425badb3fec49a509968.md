### Title
Cross-organization webhook forgery lets any configured GitHub org spoof pushes for another org's stacks - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects the HMAC secret to validate a webhook using the `repository.owner.login` field of the JSON body, but the webhook dispatch pipeline (`Shipit::Webhooks::Handlers::Handler#repository_name`) resolves the actual `Repository`/`Stack` to mutate using the unrelated `repository.full_name` field of the same body. Because Shipit supports multiple independently configured GitHub organizations, each with its own `webhook_secret` known to that org's own administrator, an org admin who legitimately knows their own org's secret can forge a webhook whose signing identity (`repository.owner.login`) is their own org, while the acted-upon target (`repository.full_name`) points at a stack belonging to a completely different, unrelated organization/repository.

### Finding Description
`verify_signature` picks the GitHub App/secret to validate against from the attacker-controlled JSON payload itself: [1](#0-0) [2](#0-1) 

Once the signature check passes, the raw body is re-parsed and passed as-is to the registered handlers: [3](#0-2) 

`Shipit::Webhooks::Handlers::Handler` — the base class used by `PushHandler` and other handlers — resolves the target `Repository`/`Stack` using a *different* field of the same body, `repository.full_name`, with no cross-check against the field (`repository.owner.login`) that was used to pick the verification secret: [4](#0-3) 

`PushHandler#process` uses this handler-scoped `stacks` and directly forces a sync using the attacker-supplied `after` SHA: [5](#0-4) 

Shipit explicitly supports multiple independently-configured GitHub organizations, each with a distinct `webhook_secret` that is generated and known by that org's own GitHub App administrator: [6](#0-5) [7](#0-6) 

The signature check itself is a straightforward HMAC compare against whatever secret was resolved for the org named in the payload: [8](#0-7) 

This breaks the binding: `organization that authenticated (repository.owner.login, verified via HMAC)` ≠ `repository that is written (repository.full_name, used to locate the Stack that is mutated)`. Nothing in the code enforces that these two fields describe the same repository/organization.

### Impact Explanation
An administrator of any GitHub organization that is configured on a shared/multi-tenant Shipit instance (a documented, supported deployment topology) can:
1. Know their own org's `webhook_secret` (they configured it themselves when setting up their GitHub App).
2. Send a raw HTTP POST directly to the Shipit webhooks endpoint (bypassing GitHub) with a JSON body where `repository.owner.login` = their own org (so `verify_signature` looks up and validates against their own known secret) but `repository.full_name` = `victim-org/victim-repo`.
3. Compute a valid `X-Hub-Signature` using their own known secret.
4. Have `PushHandler` (or other handlers keyed on `repository.full_name`, e.g. pull_request handlers) locate and mutate a `Stack` belonging to `victim-org/victim-repo`, forcing `sync_github` with an attacker-chosen `expected_head_sha`.

This is a cross-repository write performed by an org that never authenticated as, or was authorized for, the victim repository — matching the report's underlying bug class (a field acted upon that is never bound to the field actually verified). Depending on the victim stack's continuous-delivery configuration, a forced sync to an attacker-chosen SHA can also trigger downstream deploy automation.

### Likelihood Explanation
Requires only administrative control of any one GitHub org/App configured on the same shared Shipit instance (a normal, supported multi-org configuration per `docs/setup.md`), and the ability to send an arbitrary HTTP request with a correctly computed HMAC using a secret the attacker legitimately possesses. No access to the victim's repository, GitHub token, session, or API client is needed — this is directly reachable by any org-level admin who is otherwise fully unprivileged with respect to the target org/repo.

### Recommendation
Bind the field used to select the verification secret to the field used to resolve the mutated resource. Concretely:
- After signature verification, re-derive the acting organization from the same trusted field (`repository.owner.login` / `organization.login`) that selected the secret, and reject (or scope) any request where `repository.full_name`'s owner does not match that verified organization.
- Alternatively, verify the webhook using a secret scoped by `repository.full_name`'s owner rather than a separately-supplied `repository.owner.login`/`organization.login`, so the value used for verification is identical to the value used to locate the target Stack.

### Proof of Concept
1. Configure Shipit with two orgs, `org-a` and `org-b`, each with distinct `webhook_secret`s (per `docs/setup.md` multi-org config).
2. As an administrator of `org-a` (who knows `org-a`'s webhook_secret because they configured it), craft:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "org-a" },
    "full_name": "org-b/victim-repo"
  }
}
```
3. Compute `X-Hub-Signature: sha1=<hmac(org-a-secret, body)>` and `X-Github-Event: push`, POST to `/github_hooks` (Shipit's webhook endpoint).
4. `verify_signature` resolves `Shipit.github(organization: "org-a")` and validates the HMAC successfully (attacker knows this secret).
5. `PushHandler#process` resolves `Repository.from_github_repo_name("org-b/victim-repo")` and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` on a stack the attacker does not own, demonstrating the cross-organization/cross-repository write.

### Using Multiple Github Applications

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently. The top-level keys should be the name of each Github organization, and the following sub-keys are the Github app details for that particular organization.

    someothergithuborg:

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
