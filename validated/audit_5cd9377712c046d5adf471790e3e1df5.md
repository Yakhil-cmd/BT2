## Title
CCMenu API endpoint bypasses per-stack ApiClient scoping, allowing a stack-scoped token to read deploy status of any stack - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Shipit::Api::CCMenuController` overrides the `stack` finder inherited from `Shipit::Api::BaseController` with an unscoped lookup, breaking the binding between the stack(s) an `ApiClient` token is authorized for and the stack it can actually read.

### Finding Description
`Shipit::Api::BaseController` enforces stack-level authorization by scoping the `stack` resolution to the client's own `stack_id` when the token is stack-scoped: [1](#0-0) 

That is: `stack == stacks.from_param!(params[:stack_id])`, where `stacks` is restricted to `Stack.where(id: current_api_client.stack_id)` for scoped clients. This is the intended equality: *the stack a token authorizes == the stack a request can touch*.

`CCMenuController` however redefines `stack` to bypass that scoping entirely, resolving directly against the full `Stack` table regardless of the authenticated client's `stack_id`: [2](#0-1) 

The controller only enforces the permission name via `require_permission :read, :stack`, which checks the client's `permissions` array but never checks which stack the client is bound to: [3](#0-2) 

The `stack_id` scoping feature is real and tested elsewhere (e.g. `Shipit::Api::BaseController#stacks`, covered by "an api client scoped to a stack will only see that one stack" in `test/controllers/api/stacks_controller_test.rb:217-223`), confirming that stack-scoped tokens are a supported trust boundary that `CCMenuController` fails to respect.

CCMenu tokens are explicitly designed for external, low-trust distribution: `CCMenuUrlController` mints a `read:stack` token and embeds it directly in a URL meant to be pasted into third-party CI dashboards/CCTray clients: [4](#0-3) 

Before vs after the attack:
- **Before**: An ApiClient token scoped to `stack_id = A` can only satisfy `stacks.from_param!` for stack A on every other API endpoint (deploys, tasks, hooks, lock, etc.).
- **After**: The same token, presented to `GET /stacks/*stack_id/ccmenu?token=...`, resolves `stack` via unscoped `Stack.from_param!(params[:stack_id])`, and can retrieve deploy/build status for any stack `B` in the installation — a stack it was never authorized for.

### Impact Explanation
This escalates the authorization scope of a `read:stack`-permissioned, stack-bound token into an unauthenticated-for-that-stack read of another stack's deploy/build state (last deploy status, running/failure state, deploy id) — matching the "escalation into ... unauthenticated read of stack state ... or deploy output" High-impact bucket. Because CCMenu tokens are intended for wide, low-trust distribution (embedded in CI dashboard configs), any leak of one such token exposes the status of every stack in the Shipit instance, not just the one it was scoped to.

### Likelihood Explanation
Any holder of a legitimately-scoped, low-privilege CCMenu/`read:stack` token — which by design is meant to be pasted into external tooling and is not treated as highly sensitive — can trivially exploit this by changing the `stack_id` segment of the URL. No additional privilege, session, or GitHub credential is required beyond the token itself.

### Recommendation
Remove the `stack` override in `CCMenuController` (or reimplement it using the scoped `stacks` relation from `BaseController`) so `stack` is always resolved via `stacks.from_param!(params[:stack_id])`, ensuring the stack a CCMenu token can display is bound by the same `stack_id` scope enforced everywhere else in the API.

### Proof of Concept
1. Create (or obtain) an `ApiClient` with `permissions: ['read:stack']` and `stack_id` set to Stack A (e.g., via the "Create CCMenu URL" flow scoped to A, or an admin-issued scoped token).
2. Call `GET /stacks/<owner>/<repoA>/<envA>/ccmenu?token=<tokenA>` → succeeds as expected.
3. Call `GET /stacks/<owner>/<repoB>/<envB>/ccmenu?token=<tokenA>` for an unrelated Stack B → the request still succeeds (200, deploy/build status of B returned), even though `tokenA` is scoped only to Stack A, because `CCMenuController#stack` uses `Stack.from_param!` instead of the scoped `stacks.from_param!`.

require 'uri'

module Shipit
  class CCMenuUrlController < ShipitController
    def fetch
      uri = URI(api_stack_ccmenu_url(stack_id: stack.to_param))
      uri.query = { 'token' => client.authentication_token }.to_query
      render(json: { ccmenu_url: uri.to_s })
    end

    private

    def client
      @client ||= ApiClient.create_with(permissions: %w[read:stack])
                           .find_or_create_by!(creator: current_user, name: 'CCMenu Client')
    end

    def stack
      @stack ||= Stack.from_param!(params[:stack_id])
    end
  end
