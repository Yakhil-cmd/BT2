## Title
Merkle tree leaf/internal-node hash collision in `merkle.js` allows forged inclusion proofs for `in merkle` address definitions and `is_valid_merkle_proof` AA formula - (File: `merkle.js`)

### Summary
`ocore`'s merkle tree implementation hashes leaves and internal nodes with the exact same, unprefixed hash function: `hash(x) = sha256(x)`. A leaf hash is `hash(element)` and an internal node hash is `hash(child1_hash + child2_hash)`. Because there is no domain separation between "hashing a raw leaf value" and "hashing a pair of child hashes," a raw string equal to the concatenation of two sibling hashes will produce exactly the same digest as the corresponding internal node. This is the classic CVE-2012-2459-style merkle "node-as-leaf" collision - the same bug class flagged in the referenced report for `FootiumPrizeDistributor::claimEthPrize`, but present here in `verifyMerkleProof`.

The code itself contains a developer acknowledgment of this exact risk ("Node-as-Leaf issue might matter in some cases") directly above `verifyMerkleProof`, but no domain-separation prefix (e.g. `0x00` for leaves / `0x01` for nodes, as used in RFC 6962) was ever added: [3](#0-2) 

This primitive is reachable by unprivileged actors in two places:

1. **Address definition authentifier `in merkle`** - evaluated for any unit whose signing address uses this definition rule. `assocAuthentifiers[path]` (the serialized proof) is supplied by the unit author/poster, and `element` (`args[2]`) is fixed by the address definition, checked against a data-feed-posted root: [4](#0-3) 

2. **`is_valid_merkle_proof` formula function**, usable inside any AA's `getters`/trigger-processing formulas, where both `element` and `proof` are attacker-influenced expressions evaluated from the trigger data supplied by the AA trigger sender: [5](#0-4) 

Both paths funnel into the same `merkle.verifyMerkleProof` primitive that lacks leaf/node domain separation, so any address definition or AA formula that establishes semantic meaning to "any element whose value happens to equal the concatenation of two sibling hashes in the tree" is vulnerable to accepting a fabricated intermediate-node value as if it were a genuine leaf that was included in the original data set.

### Impact Explanation
If a fixed target `element` used in an `in merkle` address definition, or a target passed to `is_valid_merkle_proof` inside AA logic, happens to coincide with the concatenation of two sibling hashes from a real, oracle-posted merkle tree (root published via a data feed), an attacker can construct a valid-looking merkle proof for that colliding value using only the already-public sibling hashes from the tree structure, and get the AA/definition to treat it as legitimate proof of set membership. Depending on how the AA/definition uses this check (e.g., gating fund release, authorizing an address as a valid signer, or accepting an oracle-attested value), this could lead to unauthorized spending of AA funds or bypass of an address authentification rule. This mirrors the underlying Solidity finding's impact class (spending funds contingent on a merkle proof that should not have validated).

### Likelihood Explanation
Exactly as characterized in the source report: a spontaneous collision between a fixed application-defined `element` and the concatenation of two arbitrary sibling hashes is extremely unlikely in general (comparable to a random 256-bit collision), so this is a low-probability/high-impact structural weakness rather than a directly exploitable bug in the common case. It becomes materially more likely in any scenario where the tree structure or target value is attacker-influenced or predictable (e.g., the tree is small, or the "element" being checked is derived from other on-chain data an attacker can also influence), which is plausible given `is_valid_merkle_proof` accepts fully attacker-controlled `element`/`proof` expressions from AA trigger data.

### Recommendation
Add domain separation to `merkle.js`'s hashing scheme, e.g. prefix leaf hashing with a distinct byte/tag different from the prefix used when hashing two child hashes together (as done in RFC 6962), so that `hash(leaf, element)` can never collide with `hash(node, child1+child2)`. Apply the fix consistently across `getMerkleRoot`, `getMerkleProof`, and `verifyMerkleProof` in `merkle.js` and ensure serialized/deserialized proofs remain backward-compatible or are versioned appropriately given this is used both in on-chain-verified formulas (`is_valid_merkle_proof`) and address definitions (`in merkle`).

### Proof of Concept
1. An oracle posts a data feed value `R` that is the merkle root of elements `[e1, e2, e3, e4, ...]`, computed via `getMerkleRoot` in `merkle.js`.
2. Compute `h1 = hash(e1)`, `h2 = hash(e2)` (the actual sibling hashes at the leaf level, both derivable from public tree data or a previously obtained legitimate proof).
3. Construct `fake_element = h1 + h2` (raw string concatenation). By construction, `hash(fake_element) === hash(h1 + h2)`, which is exactly the internal node hash that `e1`/`e2` roll up into.
4. Build a proof object reusing the remaining siblings from `e1`'s original path (skipping the first level) with `index` set to the parent's index, and `root: R`.
5. Call `merkle.verifyMerkleProof(fake_element, proof)` (directly, or via `is_valid_merkle_proof(fake_element, proof)` in an AA formula, or via the `in merkle` address definition if `fake_element` happens to equal the definition's fixed `element` argument) - verification succeeds and returns `true`, even though `fake_element` was never an original leaf inserted by the oracle. function hash(str){
	return crypto.createHash("sha256").update(str, "utf8").digest("base64");

function getMerkleRoot(arrElements){
	var arrHashes = arrElements.map(hash);
	while (arrHashes.length > 1){
		var arrOverHashes = []; // hashes over hashes
		for (var i=0; i<arrHashes.length; i+=2){
			var hash2_index = (i+1 < arrHashes.length) ? (i+1) : i; // for odd number of hashes
			arrOverHashes.push(hash(arrHashes[i] + arrHashes[hash2_index]));
		}
		arrHashes = arrOverHashes;
	}
	return arrHashes[0];

function verifyMerkleProof(element, proof){
	// Node-as-Leaf issue might matter in some cases
	try {
		var index = proof.index;
		var the_other_sibling = hash(element);
		for (var i = 0; i < proof.siblings.length; i++) {
			// this also works for duplicated trailing nodes
			if (index % 2 === 0)
				the_other_sibling = hash(the_other_sibling + proof.siblings[i]);
			else
				the_other_sibling = hash(proof.siblings[i] + the_other_sibling);
			index = Math.floor(index / 2);
		}
		return (the_other_sibling === proof.root);
	}
	catch (e){
		return false;
	}
}
