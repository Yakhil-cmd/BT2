## Finding [1](#0-0) 

### Title
Stack-scoped `ApiClient` token can read CI/build status for any stack via `Api::CCMenuController` - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::Api::BaseController` scopes which stacks an `ApiClient` may act on by intersecting the requested stack with `current_api_client.stack_id`, but `Api::CCMenuController` overrides the `stack` resolver to bypass this scoping entirely and load the requested stack unconditionally via `Stack.from_param!`, breaking the binding between "the stack the token is authorised for" and "the stack the endpoint touches."

### Finding Description
`Shipit::Api::BaseController` implements the intended authorization binding as: [2](#0-1) 

`stacks` restricts the queryable set to `Stack.where(id: current_api_client.stack_id)` whenever the `ApiClient` has a `stack_id` set (i.e., it is a stack-scoped token), and `stack` resolves `params[:stack_id]` only from within that restricted scope. Every other API controller (e.g. `LocksController`, `StacksController`) relies on this shared `stack`/`stacks` helper, so the `stack_id` binding on the `ApiClient` record is enforced consistently.

`Api::CCMenuController`, however, redefines `stack` to resolve directly against the unscoped `Stack` model:
```ruby
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end
``` [3](#0-2) 

The controller still gates access with `require_permission :read, :stack`, but that check only inspects the `ApiClient#permissions` string array via `check_permissions!`: [4](#0-3) 

It never consults `current_api_client.stack_id`. As a result, the equality that should hold — `stack_touched == stack_authorised (current_api_client.stack_id)` when the client is stack-scoped — is broken: `stack_touched = Stack.from_param!(params[:stack_id])` for an arbitrary attacker-chosen `stack_id`, independent of which stack the token was actually issued/scoped for.

This is the direct analog of the Yearn `maxLoss` bug class: the vault's real withdrawal path silently drops the caller-specified safety parameter, letting a legitimate operation touch more (loss) than what was authorised; here, the CCMenu read path silently drops the caller-specific stack scope, letting a legitimately-issued, narrowly-scoped token touch more (any stack) than what was authorised.

### Impact Explanation
An `ApiClient` token that was deliberately created with `stack_id` set (the mechanism by which an operator hands out a credential limited to a single stack's data, per `test/controllers/api/stacks_controller_test.rb`'s `"an api client scoped to a stack will only see that one stack"`) can be replayed against `Api::CCMenuController#show` with a different `stack_id`/`to_param` and successfully retrieve that other stack's build/deploy status (`lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, lock state, etc.), because the controller path never checks `stack_id` at all. This is an unauthenticated-relative-to-scope read of stack state/deploy output across stack boundaries by a credential that was never authorised to see it, matching the "High" impact category of unauthorized read of stack state or deploy output across an authorization boundary.

### Likelihood Explanation
Exploitation only requires possessing any stack-scoped `ApiClient` token (the exact class of credential the system is designed to hand out with reduced scope) and knowing/guessing another stack's `to_param` (owner/repo/env/branch, which is not secret and is often predictable/enumerable). No additional privilege, secret, or session is required beyond the token itself, and the vulnerable code path (`app/controllers/shipit/api/ccmenu_controller.rb#stack`) is reachable on every request to that controller.

### Recommendation
Remove the `stack` override in `Api::CCMenuController` (or reintroduce the `stack_id` scoping) so it resolves through the shared, scope-aware `stacks`/`stack` helpers in `BaseController`, i.e. `stacks.from_param!(params[:stack_id])`, ensuring stack-scoped tokens can never resolve a stack outside `current_api_client.stack_id`.

### Proof of Concept
1. An operator creates a stack-scoped `ApiClient` for Stack A: `ApiClient.create!(creator: user, name: 'ci', stack: stack_a, permissions: ['read:stack'])`, obtaining `client.authentication_token`.
2. Attacker (holder of this Stack-A-scoped token) sends `GET /ccmenu/*stack_b_param?token=<token>` (or Basic Auth) where `stack_b_param` identifies unrelated Stack B.
3. `authenticate_api_client` in `CCMenuController` succeeds via `ApiClient.authenticate(params[:token])`. `require_permission :read, :stack` passes because the token has `read:stack` in `permissions`.
4. `stack` resolves `Stack.from_param!(params[:stack_id])` directly against Stack B, ignoring that `current_api_client.stack_id == stack_a.id`.
5. The response renders Stack B's CCMenu XML (`lastBuildStatus`, `lastBuildLabel`, lock status, etc.), a stack the token was never authorised to view.
