### Title
Cross-repository Status webhook forgery via global `sha` lookup - (File: app/models/shipit/webhooks/handlers/status_handler.rb, app/models/shipit/status.rb)

### Summary
`StatusHandler#process` resolves the target `Commit` purely by `sha`, with no check that the webhook's `repository.full_name`/owner matches the repository of the stack that owns the matched commit. Combined with `Status.replicate_from_github!` accepting whatever `stack_id` the matched `Commit` happens to carry, an attacker who owns any repository sharing a commit SHA with a victim's tracked commit (e.g. a fork containing the pre-fork commit history) can post an attacker-signed webhook for their own repository and mutate the victim stack's commit state, firing `commit_status`/`deployable_status` hooks that downstream systems trust as the victim's CI signal.

### Finding Description
The broken binding is: `commit.stack.repository.full_name` (the actual owner of the row being mutated) must equal `params.dig('repository','full_name')` / `repository_owner` (the repository that was cryptographically verified by `verify_signature`) — but no such equality is ever checked.

Trace:
1. `WebhooksController#verify_signature` computes `github_app = Shipit.github(organization: repository_owner)` where `repository_owner` is read straight from the attacker-supplied payload (`params.dig('repository','owner','login')`) [1](#0-0) [2](#0-1) . This only proves the request was signed by *some* organization the attacker legitimately controls (their own fork/org's webhook secret) — it proves nothing about the commit or stack the payload claims to describe.
2. `StatusHandler#process` then does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` with zero scoping to the verified repository/owner [3](#0-2) .
3. `Commit#create_status_from_github!` calls `add_status { statuses.replicate_from_github!(stack_id, github_status) }`, where `stack_id` is the *matched commit's own* `stack_id`, not anything from the payload [4](#0-3) .
4. `Status.replicate_from_github!` blindly creates/finds the `Status` row for that `stack_id` using attacker-controlled `state`/`description`/`target_url`/`context` [5](#0-4) .
5. `Commit#add_status` compares old vs new status and fires `Hook.emit(:commit_status, stack, ...)` and, on meaningful transitions (e.g. success/pending → failure), `Hook.emit(:deployable_status, stack, ...)` scoped to the victim's real `stack` object [6](#0-5) .

Exploit: attacker forks the victim's public repository (forks share commit objects/SHAs for history that predates divergence, or the attacker can otherwise obtain a repo containing an identical commit — same tree/parents/author/committer/message — to reproduce the SHA). Attacker POSTs (or triggers via GitHub's Statuses API on their own fork) a `status` event with `state: "failure"`, `sha: <victim's currently-deploying commit sha>`, and `repository.owner.login` set to their own account/org. `verify_signature` validates against the attacker's own legitimately-configured webhook secret and passes. `StatusHandler` then finds the victim's `Commit` row purely by `sha` (ignoring that it belongs to a different, unrelated repository/stack) and forges a `failure` status against it, firing `deploy_status`/`commit_status` hooks scoped to the victim's stack.

Existing guards do not stop this: `verify_signature` authenticates the *sender's own organization*, not the *target repository/stack of the payload's content*; `drop_unhandled_event` only filters unknown event types; there is no `ExplicitParameters` validation tying `params.sha` to `params.repository`; no model validation on `Status`/`Commit` enforces repository ownership consistency for the `sha` lookup.

### Impact Explanation
An unprivileged attacker who controls any repository sharing a commit SHA with a tracked victim commit (trivially achievable by forking a public repo, no Shipit or GitHub secrets needed beyond their own repo's webhook signing which is theirs by construction) can write a `Shipit::Status` record for the victim's stack/commit and trigger `Hook.emit(:commit_status, ...)`/`Hook.emit(:deployable_status, ...)` scoped to that victim stack — a record written and a webhook fired "from" a repository that never authenticated the event. This can flip a currently deploying/success commit to `failure`, denying legitimate continuous-delivery/merge flows and misleading any downstream system (e.g. merge automation, deploy gating) that treats these hooks as trustworthy CI signal from the victim's own repository. This matches the "payload for one repository mutating another's stack/commit" Critical impact category.

### Likelihood Explanation
Preconditions: victim stack has a commit tracked with a SHA the attacker can reproduce (straightforward via forking a public repo, since forks retain identical commit objects/SHAs for shared history), and the Shipit-configured GitHub App/webhook secret setup allows the attacker to register/verify webhooks for their own repository (a normal, unprivileged capability of any GitHub user with a repo). No Shipit session, API token, or GitHub App private key is needed. The attack is fully repeatable against any commit SHA the attacker can reproduce and works uniformly across tenants tracked by the same Shipit instance.

### Recommendation
Scope the `Commit` lookup in `StatusHandler#process` (and analogous handlers) to commits whose `stack.repository` matches the verified webhook's `repository.full_name`/owner, e.g. `Commit.joins(stack: :repository).where(sha: params.sha, shipit_repositories: { full_name: params.repository.full_name })`, so a status can only ever mutate commits belonging to stacks tracking the exact repository that was cryptographically verified.

### Proof of Concept
Add a minitest to `test/controllers/webhooks_controller_test.rb` (or `test/models/commits_test.rb`) asserting the binding:
```ruby
test ":status from an unrelated repository must not mutate a commit belonging to a different tracked stack" do
  victim_commit = shipit_commits(:first) # belongs to shipit_stacks(:shipit), repo "shopify/shipit-engine"
  attacker_repository_owner = "attacker-org" # different from victim_commit.stack.repository.owner

  GithubHook.any_instance.stubs(:verify_signature).returns(true)
  request.headers['X-Github-Event'] = 'status'

  payload = {
    'sha' => victim_commit.sha,
    'state' => 'failure',
    'context' => 'ci/travis',
    'repository' => { 'full_name' => 'attacker-org/attacker-fork', 'owner' => { 'login' => attacker_repository_owner } }
  }.to_json

  # Equality that should hold but does not: victim_commit.stack.repository.full_name != payload repository.full_name
  refute_equal victim_commit.stack.repository.full_name, JSON.parse(payload)['repository']['full_name']

  assert_no_difference '-> { victim_commit.reload.statuses.count }' do
    post :create, body: payload, as: :json
  end
end
```
This currently fails (the status IS created and hooks scoped to the victim stack fire), demonstrating the missing binding between the verified webhook repository and the mutated commit's actual stack/repository.
