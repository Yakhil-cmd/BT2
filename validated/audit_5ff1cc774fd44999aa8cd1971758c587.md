## Title
Webhook signature check can be a no-op per-organization, letting an unauthenticated attacker forge `membership`/`push`/`status` events for any tracked repository - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which `GitHubApp` (and therefore which `webhook_secret`) to validate a webhook against using an attacker-controlled field of the unauthenticated request body, and `GitHubApp#verify_webhook_signature` treats a blank `webhook_secret` as "verified". Because `webhook_secret` is documented and shipped as optional/blank in every configuration template, an attacker can pick an organization identifier that resolves to a blank-secret `GitHubApp` and have the signature check pass unconditionally, then have the event handled against any repository/team named elsewhere in the same payload.

### Finding Description
`verify_signature` computes the org used for verification from body fields the attacker fully controls: [1](#0-0) [2](#0-1) 

`repository_owner` is read from `params.dig('repository','owner','login')` or, if absent, `params.dig('organization','login')` — both attacker-supplied JSON fields, not authenticated in any way before this point.

`Shipit.github(organization: repository_owner)` resolves to a distinct `GitHubApp` per configured organization: [3](#0-2) 

`GitHubApp#verify_webhook_signature` short-circuits to `true` whenever that org's `webhook_secret` is blank: [4](#0-3) 

`webhook_secret` is explicitly optional in every shipped configuration template (`# nil`), including the multi-org example: [5](#0-4) [6](#0-5) 
and documentation frames it as optional ("If you've set a webhook secret ... copy it here"). [7](#0-6) 

Once verification is bypassed (or trivially satisfied for a blank-secret org), the actual event handlers derive the target repository from a *different* body field, `repository.full_name`, with no relation to whichever org string was used to pick the app/secret: [8](#0-7) 

For the `membership` event specifically, the handler trusts `organization.login` and `team.id`/`member.login` from the same unauthenticated payload to add an arbitrary GitHub user to an arbitrary `Team`: [9](#0-8) 

Membership in a `Team` referenced by `Shipit.github_teams` is exactly what `User#authorized?` checks to grant access to the whole application: [10](#0-9) 

**Binding broken:** organization authenticated (the org whose blank/guessable `webhook_secret` gated the HMAC check) ≠ repository/team actually written (`repository.full_name` / `team.id` / `member.login` freely chosen elsewhere in the same unauthenticated payload). Before the attacker's request, both sides are constrained to the same GitHub-issued, HMAC-signed event; after it, the "authenticated org" side is a no-op (or a forgeable org string) while the "written" side is entirely attacker-chosen.

### Impact Explanation
This breaks a core Shipit trust boundary: `POST /webhooks` is meant to be reachable only by GitHub, gated by an HMAC computed with a per-app secret. If any configured `GitHubApp` (a routine, documented state) has a blank `webhook_secret`, the check degrades to accepting any signature for that org, and the attacker can then direct the resulting handler at any other tracked repository/team by simply filling in different values elsewhere in the JSON body. Concretely this allows an unauthenticated attacker to:
- Add their own GitHub identity to a `Team` referenced by `Shipit.github_teams` via a forged `membership` event, escalating to authorized access to the whole Shipit UI/API (Critical — escalation into `Shipit.github_teams` authorization, per [10](#0-9) ).
- Inject forged `push`, `status`, `check_suite`, or `pull_request` events for any tracked stack/repository, manipulating commit statuses, review-stack lifecycle, or triggering `GithubSyncJob` against arbitrary repositories tracked by Shipit (High — unauthenticated manipulation of stack/task state).

### Likelihood Explanation
The precondition — at least one configured GitHub App/org with no `webhook_secret` — is not an edge case: it is the literal default shown in every shipped secrets template in this repo, and the setup docs describe the secret as something you copy in only "if you've set" one, i.e. optional. `/webhooks` requires no session, no API token, and no prior access; the request is a single unauthenticated HTTP POST with a crafted JSON body and mismatched `organization`/`repository` fields.

### Recommendation
- Require a non-blank `webhook_secret` for every configured GitHub organization; refuse to boot (or refuse all webhook requests) for an org whose secret is unset instead of returning `true` from `verify_webhook_signature`.
- Verify the signature using the target organization actually referenced by `repository.full_name` (or refuse ambiguous payloads where `organization.login`/`repository.owner.login` and the repository's owning org disagree) rather than trusting an unauthenticated field to select the verification key.
- Consider re-deriving the org used for verification strictly from `Repository.from_github_repo_name(payload.dig('repository','full_name'))` so the "authenticated" and "written" identifiers are always the same value.

### Proof of Concept
1. Configure Shipit with multiple orgs where at least one, e.g. `blankorg`, has `webhook_secret` unset (the shipped default).
2. POST to `/webhooks` with header `X-Github-Event: membership` and body:
```json
{
  "action": "added",
  "organization": { "login": "blankorg" },
  "team": { "id": 1, "name": "Deployers", "slug": "deployers", "url": "https://example.com" },
  "member": { "login": "attacker-github-login" }
}
```
No `X-Hub-Signature` (or any garbage value) is required, since `blankorg`'s `webhook_secret` is blank and `verify_webhook_signature` returns `true` unconditionally (`app/controllers/shipit/webhooks_controller.rb:24-30`, `lib/shipit/github_app.rb:76-83`).
3. `MembershipHandler#process` creates/loads the real GitHub user `attacker-github-login` (via GitHub API lookup) and adds them to the `Team` matching `team.id` = 1 (`app/models/shipit/webhooks/handlers/membership_handler.rb:22-43`).
4. If that `Team` is one of `Shipit.github_teams`, `attacker-github-login` logging in via OAuth now passes `User#authorized?` and gains full application access.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

        def process
          team = find_or_create_team!
          member = User.find_or_create_by_login!(params.member.login)

          case params.action
          when 'added'
            team.add_member(member)
          when 'removed'

          end
        end

          end
        end
