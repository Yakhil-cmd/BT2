### Title
Webhook signature verification key is selected from an unauthenticated payload field that is decoupled from the repository the handlers act on - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` chooses which GitHub App/`webhook_secret` to validate a webhook against using `repository_owner`, a value taken straight from the unauthenticated JSON body (`params.dig('repository','owner','login')` or `organization.login`). All webhook event handlers, however, resolve the actual `Repository`/`Stack` to act on using a *different* field of the same unauthenticated body: `payload.dig('repository','full_name')`. Because these two fields are never cross-checked, and because `GitHubApp#verify_webhook_signature` short-circuits to `true` when the resolved organization has no configured `webhook_secret`, an attacker can pick an organization with no secret configured to trivially pass verification, while pointing `repository.full_name` at a stack belonging to a *different, secured* organization.

### Finding Description
In a multi-org Shipit deployment (`github:` keyed by organization, as documented in `docs/setup.md:182-209`), `Shipit.github(organization:)` looks up per-org config via `github_app_config(organization)` (`lib/shipit.rb:170-200`). The controller passes the attacker-supplied `repository_owner` directly to it: [1](#0-0) [2](#0-1) 

`verify_webhook_signature` treats an unset secret as automatic success rather than a hard failure: [3](#0-2) 

Every webhook handler then resolves the repository/stack to operate on from a *separate* field of the same untrusted payload, with no linkage back to the organization that was actually used for signature verification: [4](#0-3) 

For example `PushHandler` triggers a GitHub sync (and potentially downstream auto-deploy) for whatever stack `Repository.from_github_repo_name` resolves to: [5](#0-4) 

and PR handlers archive/unarchive/provision review stacks based on the same decoupled `full_name`: [6](#0-5) 

The equality that is supposed to hold is:
`organization that authenticated the request == organization owning the repository that handlers act on`

This breaks because both sides are attacker-controlled fields of the same unsigned-or-partially-signed JSON body, and the engine never asserts `repository.owner.login == repository.full_name.split('/').first`, nor does it require every configured organization to have a non-blank `webhook_secret`.

### Impact Explanation
If a Shipit instance has multiple GitHub organizations configured and even one of them has no `webhook_secret` set (shown as the literal default/example value `webhook_secret: # nil` across `docs/setup.md`, `config/secrets.development.shopify.yml`, and `test/dummy/config/secrets_double_github_app.yml`), an attacker who knows nothing about any secret can:
- Set `repository.owner.login` (or `organization.login`) to the org with no secret → `verify_webhook_signature` returns `true` unconditionally.
- Set `repository.full_name` to `secured-org/target-repo`, a stack belonging to a fully-secured organization.

This forges arbitrary `push`, `pull_request` (`opened`/`closed`/`reopened`/`labeled`/`unlabeled`), `status`, `check_suite`, and `membership` events against any stack in the installation, regardless of which org it actually belongs to. Concretely this can trigger `Stack#sync_github` on arbitrary stacks (`PushHandler`), potentially seeding an auto-deploy pipeline with attacker-influenced commit state, and archive/unarchive/provision review stacks and their associated infrastructure (`ReviewStackAdapter#archive!`/`unarchive!`) — an unauthorized deploy/provisioning action against a repository the attacker never authenticated for.

### Likelihood Explanation
Likelihood is elevated by the fact that the vulnerable condition (one organization configured without a `webhook_secret`) is exactly what the shipped documentation and fixture files show as an acceptable/default configuration for multi-org setups, making it plausible that real deployments run with at least one org lacking a secret while others are hardened. No credentials, tokens, or session are required — only knowledge of one org's login name that lacks a secret, which is often discoverable (e.g., it may be the org actually running Shipit).

### Recommendation
- Require and enforce a non-blank `webhook_secret` for every configured organization; treat a missing secret as a hard configuration error rather than an automatic pass in `GitHubApp#verify_webhook_signature`.
- After signature verification, assert that the organization used to select the verifying `GitHubApp` matches the owner of `repository.full_name` (or `organization.login`) actually used by the handlers, rejecting the webhook if they diverge.
- Consider deriving the repository/stack solely from the same trusted field used for authentication, rather than trusting two independent fields of the same unauthenticated payload.

### Proof of Concept
1. Configure Shipit with two organizations: `OpenOrg` (no `webhook_secret`) and `SecuredOrg` (with a strong `webhook_secret`), each with stacks/repositories tracked.
2. Send a POST to `/github/webhooks` (mounted webhook endpoint) with header `X-Github-Event: push` and body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "OpenOrg" },
    "full_name": "SecuredOrg/critical-repo"
  }
}
```
No `X-Hub-Signature` needs to be valid for `SecuredOrg`; `repository_owner` resolves to `OpenOrg`, whose missing secret makes `verify_webhook_signature` return `true` for any signature/body.
3. `PushHandler` resolves `Repository.from_github_repo_name('SecuredOrg/critical-repo')` and calls `stack.sync_github(expected_head_sha: '<attacker-chosen-sha>')` on the secured org's stack, despite the request never being validated against `SecuredOrg`'s secret.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
