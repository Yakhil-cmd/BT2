### Title
Unbounded dust-output consumption in AA asset payments bypasses the anti-dust-attack protection and the input-count cap - ([File: aa_composer.js])

### Summary
`aa_composer.js`'s `sendUnit()`/`completePaymentPayload()` logic that funds AA-generated payment messages contains an explicit anti-dust-attack mitigation for base-currency (bytes) outputs, but the same mitigation is missing for custom (non-base) assets. Combined with the fact that AA-generated units are exempt from the `MAX_INPUTS_PER_PAYMENT_MESSAGE` cap, an attacker can cheaply flood an AA address with an unbounded number of tiny-amount asset outputs that the AA is forced to fully consume whenever it composes a response payment in that asset, causing fee-draining/DoS of the AA analogous to the reported "flood with worthless entries that a critical automated process must exhaustively process" bug class.

### Finding Description
When an AA composes an outgoing payment, `completePaymentPayload()` collects unspent outputs belonging to the AA's address to use as payment inputs via `readStableOutputs()` and `readUnstableOutputsSentByAAs()`: [1](#0-0) 

The comment explicitly states the purpose of the `amount>=FULL_TRANSFER_INPUT_SIZE` (60-byte) filter: *"byte outputs less than 60 bytes (which are net negative) are ignored to prevent dust attack: spamming the AA with very small outputs so that the AA spends all its money for fees when it tries to respond."* However, that minimum-amount filter is applied only in the `!asset` (base-currency) branch of the SQL condition:

```
WHERE address=? AND asset"+(asset ? "="+conn.escape(asset) : " IS NULL AND amount>=" + FULL_TRANSFER_INPUT_SIZE)+" AND is_spent=0 ...
``` [2](#0-1) 

For any non-base asset, the condition is simply `asset=?`, with **no minimum amount check at all** — every unspent output in that asset, no matter how tiny, is eligible to be pulled in as an input. The same gap exists in `readUnstableOutputsSentByAAs()`: [3](#0-2) 

`iterateUnspentOutputs()` then walks through all returned rows one at a time, pushing each into `payload.inputs` until the target amount is reached: [4](#0-3) 

Normally, a huge number of payment inputs would be rejected by validation via `constants.MAX_INPUTS_PER_PAYMENT_MESSAGE`, but this check is explicitly skipped for AA-generated units: [5](#0-4) 

Because asset issuance/transfer is comparatively cheap (a normal payment message, subject only to standard payload/size fees — no economic floor tied to the recipient AA's ability to process it), an attacker can send the AA's address a large number of 1-unit (or otherwise minimal) outputs of a given asset. The next time the AA needs to spend/forward that asset (e.g., responding to a legitimate user, refunding, or paying out), `readStableOutputs`/`readUnstableOutputsSentByAAs` will return and consume all of these dust outputs (since there is no floor to exclude them and no cap to limit how many get pulled in), producing an oversized response unit that pays a correspondingly large size/oversize fee — potentially exceeding the value the AA is trying to pay out, and possibly failing to be composed/broadcast at all if the resulting unit becomes too large.

### Impact Explanation
This directly threatens AA funds and availability, matching "AA fund loss or freezing":
- **Fund loss**: The AA is forced to pay commission on a response unit containing hundreds/thousands of tiny inputs, draining its bytes balance on fees rather than legitimate operations, exactly as described in the original dust-attack comment the developers already anticipated — but only mitigated for the base asset.
- **DoS/freezing of AA asset functionality**: Because the input-count cap (`MAX_INPUTS_PER_PAYMENT_MESSAGE`) does not apply to AA units, there is no ceiling stopping the number of dust inputs pulled in; a sufficiently large dust flood can make legitimate asset payouts from that AA unit-size-infeasible or economically unviable, effectively freezing the AA's ability to move that asset.

### Likelihood Explanation
Any address (an ordinary unprivileged unit poster) can issue an asset and/or send arbitrarily many minimal-amount outputs of any transferable asset to a target AA address using standard, unprivileged `payment` messages — no special permission, definition control, or high value is required, only enough bytes to cover the payload/commission fees of many small units. Given the existing comment shows the team was already aware of exactly this attack pattern for the base asset, the omission for custom assets is a straightforward, easily reachable gap.

### Recommendation
- Apply an equivalent minimum-amount ("net negative"/dust) floor to non-base-asset outputs in `readStableOutputs()` and `readUnstableOutputsSentByAAs()`, e.g., ignore asset outputs whose amount is below the marginal cost of including them as an input (analogous to `FULL_TRANSFER_INPUT_SIZE` for bytes, but denominated appropriately for the asset or measured in bytes-equivalent fee impact).
- Enforce `MAX_INPUTS_PER_PAYMENT_MESSAGE` (or an asset-specific bound) for AA-generated payment messages as well, rather than exempting `objValidationState.bAA`, or otherwise cap the number of dust inputs consumed per response.

### Proof of Concept
1. Attacker issues (or already holds) a transferable custom asset `X`.
2. Attacker sends the target AA address a large number (e.g., thousands) of `payment` messages/outputs in asset `X`, each with amount = 1 (or any value low enough to be a net loss once included as an input).
3. These outputs each land in the `outputs` table with `address = AA_address`, `asset = X`, `is_spent = 0`.
4. When the AA is later triggered to send a payment in asset `X` (e.g., forwarding a user's balance), `completePaymentPayload()` calls `readStableOutputs()`/`readUnstableOutputsSentByAAs()`, which returns **all** unspent `X` outputs at the AA's address because no minimum-amount filter applies to non-base assets (`aa_composer.js:1149`, `1167`).
5. `iterateUnspentOutputs()` pushes every one of them into `payload.inputs`, and because `MAX_INPUTS_PER_PAYMENT_MESSAGE` is bypassed for AA units (`validation.js:2137`), the resulting response unit balloons in size, paying disproportionate size/oversize fees (or failing outright), draining/freezing the AA's bytes balance and/or its ability to process asset `X` payouts.
