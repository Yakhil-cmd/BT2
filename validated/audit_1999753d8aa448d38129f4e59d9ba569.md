### Title
AA `data_feed[[...]]` oracle reads return no staleness/timestamp information, letting Autonomous Agents use arbitrarily stale prices in financial calculations - (File: `formula/evaluation.js`, `data_feeds.js`)

### Summary
The `data_feed`/`in_data_feed` oscript primitives that Autonomous Agents (AAs) use to read externally-posted oracle prices return only the last posted value (and optionally the posting unit), with no built-in age/staleness check. An AA author who uses `data_feed[[...]]` directly in an exchange-rate, redemption, or collateral calculation (a documented and even officially-bundled pattern, see `futures_contract.oscript`) has no protocol-level guarantee that the value was posted recently. If the oracle address posts infrequently (analogous to the low-liquidity Balancer pool in the referenced report), the AA will silently use a stale price for real fund transfers, exactly the "infrequently-updated oracle" failure mode described in the external report.

### Finding Description
`data_feed[[oracles=..., feed_name=..., min_mci=...]]` is implemented by `getDataFeed()`/`readDataFeedValue()`, which walks backward through `data_feeds` (or `dfv`) keys and simply returns the **most recent** matching value at or below the current `max_mci` and at or above the optional `min_mci`: [1](#0-0) [2](#0-1) 

The returned `objResult` only carries `{ value, unit, mci }`. The formula language exposes `value` (default) or `unit` (`what='unit'`), but never a timestamp or "how old" indicator tied directly to the query result: [3](#0-2) 

`min_mci` only sets a *lower bound* on how old a feed can be (i.e., "not older than mci X"); there is no companion mechanism to require the feed be *newer* than some point (no "max age" / "freshness" guard) baked into the `data_feed` operator itself. An AA author wanting freshness enforcement would have to separately request `what='unit'`, then perform an additional `unit[...]` lookup to read that unit's `timestamp`, and then compare it to `timestamp` in the same formula — a non-trivial, opt-in pattern that is not used in the codebase's own bundled example contracts.

This is demonstrated by the bundled `futures_contract.oscript` sample, which is part of the project's own reference/test contracts and directly consumes `data_feed[[oracles=..., feed_name='GBYTE_USD_MA_2019_04_30']]` to compute a payout ratio (`$bytes_per_usd_asset = min(50/$exchange_rate/2, 1)`) used to determine real payment amounts, with zero freshness check on the exchange rate value itself: [4](#0-3) 

Likewise `uniswap_like_market_maker.oscript` computes issuance/redemption ratios directly from AA balances rather than an oracle, but the general pattern in the ecosystem — using `data_feed` output directly as the price for minting/redeeming assets — is exactly the pattern vulnerable to a stale-oracle problem, since `readDataFeedValue`/`readDataFeedByAddress` provide no signal to the calling formula about how long ago the price was posted relative to `timestamp`: [5](#0-4) 

### Impact Explanation
Any AA that treats `data_feed[[...]]` output as an up-to-date price for computing amounts to mint, redeem, or pay out (a documented, supported usage pattern in ocore, exactly like `CrvDepositorWrapper` treating a Balancer TWAP as up-to-date) can execute real payments/asset issuance based on a price that is significantly out of date if the oracle address posts infrequently or is temporarily unavailable. This can lead to:
- Loss of AA funds when users redeem/mint at a favorable-to-them but stale rate before the oracle catches up (fund loss for other AA participants).
- Ability for a user (or the oracle operator, or anyone who can predict/observe an upcoming price move) to time their trigger unit to exploit the stale price window, extracting value from the AA's balance — a direct analogue of the sandwich/slippage exploitation the report describes for `CrvDepositorWrapper`.

Because AA execution results are deterministic and consensus-critical, this isn't merely a UX bug: an AA author unaware of this gap will ship a contract that leaks funds under adverse but foreseeable oracle-posting conditions, which matches Medium severity in the original report (fund loss risk without any protocol-level safety net).

### Likelihood Explanation
Likelihood is meaningful because: (1) the `data_feed` primitive is a first-class, widely-advertised AA feature intended precisely for price/exchange-rate use cases; (2) the project's own bundled sample AAs (`futures_contract.oscript`) demonstrate the vulnerable pattern of consuming `data_feed` value directly in payout math without any freshness check; (3) nothing in `readDataFeedValue`/`dataFeedExists`/`getDataFeed` warns, errors, or otherwise signals staleness by default — an AA author must proactively implement freshness checks themselves via an extra `unit[...]` lookup, which is easy to omit, especially since the official example doesn't do it either.

### Recommendation
- Extend `readDataFeedValue`/`getDataFeed` to optionally return (or make trivially queryable) the timestamp of the unit that posted the value, so formula authors can enforce `timestamp - data_feed_timestamp < max_age` in one step, without needing a second `unit[...]` round trip.
- Update AA documentation and the bundled sample contracts (`futures_contract.oscript` and similar) to demonstrate the recommended freshness-check pattern, since currently the official examples themselves omit it.
- Consider adding an explicit `max_age`/`min_timestamp` parameter to the `data_feed[[...]]` operator (symmetric to the existing `min_mci`) so freshness enforcement becomes a first-class, low-complexity option for AA authors.

### Proof of Concept
1. Deploy an AA modeled on `futures_contract.oscript`'s exchange logic, using `data_feed[[oracles='<oracle>', feed_name='PRICE']]` directly to compute a payout amount, e.g. `$bytes = round($usd_asset_amount / data_feed[[oracles='<oracle>', feed_name='PRICE']])`.
2. The oracle posts a price update infrequently (e.g., once every few hours), exactly as `readDataFeedValue` will keep returning that last posted value indefinitely until a new one is posted — see the unconditional "most recent" selection logic in `readDataFeedByAddress`: [6](#0-5) 
3. Real market price of the underlying moves significantly while the on-chain feed value is unchanged (oracle hasn't posted).
4. A user submits a trigger unit exploiting the stale price to redeem/mint at a rate favorable to them, extracting value from the AA's balance, with no protocol mechanism to reject the transaction for staleness.
