### Title
Asset definer can unilaterally rewrite the attestor list at any time, permanently freezing already-issued attested-asset holdings without a grace period - (File: `validation.js`)

### Summary
For assets with `spender_attested=true`, the asset definer can replace the entire attestor list at any time via an `asset_attestors` message, with no restriction requiring already-attested holders to remain attested or any waiting/grace period. Because every payment spending or transferring such an asset requires the owner address to be present in the *current* attestor list, a definer who drops an address from the list instantly and permanently blocks that address from ever moving the balance it legitimately holds — mirroring the reported bug class where a privileged party (`issuer`) can unilaterally close/alter state and strand other users' pending claims/funds with no cooldown.

### Finding Description
`validateAttestorListUpdate` only checks that the message is single-authored by the asset's `definer_address` and that the new attestor list is well-formed (`checkAttestorList`); it performs no comparison with the previous list and imposes no delay before the new list takes effect: [1](#0-0) 

`checkAttestorList` merely validates address format, sort order, and count — it never requires previously attested holders to remain in the list: [2](#0-1) 

Once the definer posts a new `asset_attestors` unit that becomes stable, `storage.readAsset`/`filterAttestedAddresses` resolve `arrAttestedAddresses` strictly from the *latest* stable attestor-list unit for the asset, with no reference to what the list was when the holder acquired the asset: [3](#0-2) [4](#0-3) 

Every payment that spends an output of a `spender_attested` asset — for both issuance and ordinary transfers — is gated on the *current* attestor list membership of the owner address: [5](#0-4) [6](#0-5) 

For private, fixed-denomination assets the same check is enforced from the pre-populated `src_coin` state: [7](#0-6) 

So a legitimate holder who received units of the asset while attested can be excluded from any subsequent attestor list at the sole discretion of the definer, and from that point on every unit spending that output will be rejected by `validatePaymentInputsAndOutputs`/`validatePayment` with "owner address is not attested" — there is no way for the holder to remediate other than the definer reinstating them.

### Impact Explanation
Any address holding a `spender_attested` asset is only one `asset_attestors` message away from having its entire balance of that asset permanently frozen — the funds cannot be spent, transferred, or redeemed, and there is no on-chain mechanism (grace period, appeal, or holder consent) to prevent or reverse it. This is directly analogous to the reported bug class: a privileged, single-signature actor (the "issuer"/definer) can unilaterally alter shared state in a way that blocks other parties from completing an already-pending action (claiming/spending funds they are entitled to), without any cooldown protecting participants who acted in good faith before the change.

### Likelihood Explanation
The action requires only a single, ordinary, validly-signed unit from the asset's definer address (`asset_attestors` app) — no special privileges beyond being the definer, no cooperation from other network participants, and no waiting period. Any asset issued with `spender_attested=true` is exposed to this at any time after issuance, making this trivially reachable in normal operation of the protocol as implemented.

### Recommendation
Require that addresses which already hold a confirmed balance of the asset (or that were attested when they received their balance) either be retained in any subsequent attestor list, or provide the community/holder some enforced transition/grace period before a removal takes effect (e.g., a minimum look-back window during which the old list, or a union of old+new list, is still honored for spending purposes) so a definer cannot instantly and unilaterally strand existing legitimate holders' funds.

### Proof of Concept
1. Definer `D` issues asset `A` with `spender_attested: true` and initial attestor list `[X]`. [8](#0-7) 
2. Address `X` receives a transfer of asset `A` from `D` (allowed because `X` is attested) — validated per [6](#0-5) .
3. `D` posts an `asset_attestors` unit for asset `A` with a new list `[Y]` that excludes `X`. This passes validation because nothing checks the previous list or existing holders: [1](#0-0) 
4. Once that unit is stable, `storage.readAsset` resolves `arrAttestorAddresses = [Y]` for asset `A`: [3](#0-2) 
5. `X` attempts to spend its previously received output of asset `A`. `validatePaymentInputsAndOutputs` rejects the unit with "owner address is not attested" because `X` is no longer in `arrAttestedAddresses`: [6](#0-5) 
`X`'s balance of asset `A` is now permanently unspendable unless `D` chooses to re-add `X` to the attestor list.

function validateAttestorListUpdate(conn, payload, objUnit, objValidationState, callback){
	if (objUnit.authors.length !== 1)
		return callback("attestor list must be single-authored");
	if (!isNonemptyObject(payload))
		return callback("attestor update must be a non-empty object");
	if (hasFieldsExcept(payload, ['asset', 'attestors']))
		return callback("foreign fields in attestor list update");
	storage.readAsset(conn, payload.asset, objValidationState.last_ball_mci, false, function(err, objAsset){
		if (err)
			return callback(err);
		if (!objAsset.spender_attested)
			return callback("this asset does not require attestors");
		if (objUnit.authors[0].address !== objAsset.definer_address)
			return callback("attestor list can be edited only by definer");
		err = checkAttestorList(payload.attestors);
		if (err)
			return callback(err);
		callback();
	});
}

function checkAttestorList(arrAttestors){
	if (!isNonemptyArray(arrAttestors))
		return "attestors not defined";
	if (arrAttestors.length > constants.MAX_ATTESTORS_PER_ASSET)
		return "too many attestors";
	var prev="";
	for (var i=0; i<arrAttestors.length; i++){
		if (!isValidAddress(arrAttestors[i]))
			return "invalid attestor address: "+JSON.stringify(arrAttestors[i]);
		if (arrAttestors[i] <= prev)
			return "attestors not sorted";
		prev = arrAttestors[i];
	}
	return null;
}
