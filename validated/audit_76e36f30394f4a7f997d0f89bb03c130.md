### Title
Splitting stake across multiple signer-keys distorts the largest-remainder apportionment, letting one entity capture more PoX-5 reward slots than its stake share, denying legitimate signers - (File: stackslib/src/chainstate/nakamoto/signer_set.rs)

### Summary
`pox_5_make_signer_set` aggregates locked uSTX **by signing key**, not by staking principal, and distributes weight (reward-slot/signing power) with a two-stage largest-remainder scheme: a "base" `floor(stacked_amt / threshold)` weight, followed by a single leftover slot awarded to the entries with the highest fractional remainder [1](#0-0) . Because each distinct `signer_key` is treated as an independent entry in this leftover-round competition, an entity that controls many signer keys (splitting its own aggregate stake across them, e.g. via multiple `register-for-bond`/stacking calls) can flood the top of the remainder ranking with many maximal-remainder fragments and deterministically win multiple leftover slots that a single, consolidated entry would only have a probabilistic chance of winning once. This is the same bug class as the Kairos `ClaimFacet.sol` issue — splitting one position into many small "provisions" to game a per-unit minimum/remainder allocation at the expense of other, larger, legitimate participants.

### Finding Description
The apportionment algorithm is:
1. Aggregate `amount_ustx` per `signer_key` [2](#0-1) .
2. Compute `threshold = ceil(total_ustx_locked / reward_slots)` and give each signer `base weight = stacked_amt / threshold` [3](#0-2) .
3. Distribute the remaining `leftover = reward_slots - sum(base weights)` slots one at a time to the entries with the largest `remainder = stacked_amt % threshold`, ties broken by ascending signing key [4](#0-3) .

Crucially, step 3 grants **at most one extra slot per distinct signing-key entry**, and the entry list is keyed by `signer_key`, not by the controlling stacker/principal. Splitting a given aggregate amount `A` across `K` distinct signer keys — each held just below `threshold` (maximizing `remainder`) — turns one "ticket" in the leftover lottery into `K` maximal-remainder tickets. If `K <= leftover`, the entity is now guaranteed to sweep up to `K` leftover slots outright, displacing other honest signers whose single, larger stake produces a smaller, non-maximal remainder and who therefore lose every tie/rank comparison against the attacker's manufactured maximal-remainder fragments.

This breaks the intended equality that "signing weight ∝ locked stake": for the same aggregate locked amount, a split entity can obtain strictly more total weight (and correspondingly more of the fixed pool of `reward_slots`) than a single-key entity with identical stake, at the expense of other signers who are pushed out of the leftover round despite holding equal or larger stakes.

### Impact Explanation
Reward-slot weight in PoX-5 directly determines Nakamoto block-signing voting power (`total_signing_weight`, `weight_threshold` used for block approval) [5](#0-4) . Gaining disproportionate weight relative to locked stake is explicitly called out in scope as a High-impact category ("signing weight or reward slots exceeding locked value"). An attacker who over-represents their signing weight relative to actual locked STX can disproportionately influence Nakamoto consensus signing while diluting honest signers' fair share of slots, without locking any additional value.

### Likelihood Explanation
The precondition is simply that an entity control multiple distinct signer keypairs (trivial — a signer key is a self-chosen public key) and split their stacking/bond registrations across them rather than using one key, and that the resulting per-key remainders be high enough to dominate the leftover-slot ranking (achievable by staking amounts just under the reward threshold in each key). No privileged role or another party's key is required — only ordinary, permissionless stacking operations. Whether this is exploitable in practice depends on the exact competitive stake distribution in a given cycle (larger `leftover` counts and more signers with small/mid remainders make it more effective).

### Recommendation
Aggregate not only by `signer_key` but constrain or attribute the leftover-round competition per controlling stacker/bond participant (e.g., aggregate by underlying stacker principal before computing remainders, or cap the number of leftover slots any one derived signer identity may win), similar to how the Kairos fix eliminated the exploit by restricting the number of provisions per loan to one. At minimum, the largest-remainder round should not allow an unbounded number of attacker-controlled fragments to each compete independently for the fixed pool of leftover slots.

### Proof of Concept
Illustrative numbers using the exact algorithm in `pox_5_make_signer_set` [6](#0-5) , with `reward_slots = 4`:

- Two honest signers, H1 and H2, each stake 100 uSTX with a single signer key.
- Attacker (total stake 100 uSTX, same as one honest signer) splits into 3 signer keys: 34, 33, 33.

Total locked = 100+100+34+33+33 = 300 → `threshold = ceil(300/4) = 75`.

Base weights: H1 = floor(100/75)=1 (remainder 25), H2 = 1 (remainder 25); attacker's three entries: floor(34/75)=0 (rem 34), floor(33/75)=0 (rem 33), floor(33/75)=0 (rem 33). Sum of base weights = 2, so `leftover = 4 - 2 = 2`.

Sorted by remainder descending: 34 (attacker), 33 (attacker), 33 (attacker), 25 (H1), 25 (H2). The top 2 (`leftover=2`) entries — both attacker fragments — win the extra slot. Final weights: H1=1, H2=1, attacker(34)=1, attacker(33-winner)=1, attacker(other 33)=0 (dropped).

Result: attacker's total weight = 2 out of 4 total slots (50%) despite contributing only 100/300 = 33% of locked stake, and both honest signers — who tied at remainder 25 and would have split the tie-break fairly against a single consolidated attacker entry — are shut out of the leftover round entirely because the attacker's split fragments outrank them. A single, non-split attacker entry of 100 uSTX would only tie with H1/H2 at remainder 25 and win at most 1 extra slot (expected weight ≈1.33, not a guaranteed 2).

                }

                    error!(

                        "error" => err_str
                    );
                    return Err(ChainstateError::PoxNoRewardCycle);
                }
            };

            total_ustx_locked += entry.amount_ustx;

            signer_set
                .entry(entry.signer_key)
                .and_modify(|existing_entry| *existing_entry += entry.amount_ustx)
                .or_insert_with(|| entry.amount_ustx);
        }

        // Allocate `reward_slots` weight across signers in proportion to stake using the
        // a largest-remainder method:
        //
        // The threshold is `ceil(total / reward_slots)`.
        //
        // Flooring each signer's `stacked / threshold` assigns a base weight where the sum is `<= reward_slots`
        // (the ceil makes `total/threshold <= reward_slots`).
        //
        // This leaves some unassigned ("leftover") slots, which are handed out one-per-signer
        //  in descending fractional-remainder order (ties broken by pubkey-sort order).
        //
        // This avoids degenerate modes of the floor-and-drop scheme: when more than
        // `reward_slots` distinct signers hold roughly equal stake, every base weight floors to
        // 0, and without the leftover round the entire signer set could be dropped.
        let reward_slots = u128::from(pox_constants.reward_slots());
        let threshold = std::cmp::max(1, total_ustx_locked.div_ceil(reward_slots));

        struct Apportionment {
            signing_key: [u8; SIGNERS_PK_LEN],
            stacked_amt: u128,
            weight: u128,
            remainder: u128,
        }

        let mut apportioned: Vec<Apportionment> = signer_set
            .into_iter()
            .map(|(signing_key, stacked_amt)| Apportionment {
                signing_key,
                stacked_amt,
                weight: stacked_amt / threshold,
                remainder: stacked_amt % threshold,
            })
            .collect();

        // Guaranteed `<= reward_slots` by the ceil quota, so leftover does not underflow.
        let assigned: u128 = apportioned.iter().map(|entry| entry.weight).sum();
        let mut leftover = reward_slots.saturating_sub(assigned);

        if leftover > 0 {
            // Largest fractional remainder wins the next slot; ties broken by signing_key
            // ascending so the apportionment is deterministic (and matches the final sort).
            apportioned.sort_by(|a, b| {
                b.remainder
                    .cmp(&a.remainder)
                    .then_with(|| a.signing_key.cmp(&b.signing_key))
            });
            for entry in apportioned.iter_mut() {
                if leftover == 0 {
                    break;
                }
                entry.weight += 1;
                leftover -= 1;
            }
        }
