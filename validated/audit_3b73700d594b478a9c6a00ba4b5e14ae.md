### Title
Tokens received by the controller or pool outside credited accounting are permanently locked — no release path exists - ([File: contracts/controller/src/payments.rs])

### Summary
The kernel bug class is an acquired resource (a `memremap()` mapping) that is never released because no `memunmap()` counterpart exists. The analog in XOXNO Lending is token balances acquired by the controller (or pool) outside the credited-accounting paths: the code deliberately preserves pre-existing contract balances and refunds only balance *deltas*, yet no entrypoint — privileged or otherwise — ever releases a pre-existing balance. Any token that reaches the controller address without going through a measured receive/refund leg is permanently frozen.

### Finding Description
`claim_revenue_for_asset` in `contracts/controller/src/markets.rs:179-196` snapshots the controller's balance before pulling revenue from the pool, then forwards only `balance_delta_since(...)` — the measured increase — to the accumulator. Pre-existing controller balances are explicitly left untouched; the harness test `claim_revenue_forwards_the_measured_amount_and_leaves_controller_dust_intact` asserts `controller_after == controller_before` even when the controller holds stray dust.

The same pattern governs refunds: `refund_controller_balance_delta` in `contracts/controller/src/payments.rs:41-52` computes `excess = balance_delta_since(controller, balance_before)` and returns only the delta to the payer, preserving whatever balance the controller already held.

On the pool side, `repay`/`recapitalize` only `credit_cash` the accounted amount (`contracts/pool/src/ops/repay.rs:57`), and `transfer_out` can only release up to credited cash. A direct token transfer to the pool inflates its SAC balance above `cash` with no mechanism to skim or credit the difference.

Like the kernel driver's missing `memunmap`, there is no counterpart entrypoint: no `sweep`, `rescue`, `skim`, or admin withdrawal exists on the controller or pool ABI to release a balance that was never credited. Tokens delivered by direct transfer (an explicitly in-scope path), fee-on-transfer shortfalls, or tokens pushed during flash-receiver / swap callbacks that the measured-delta logic intentionally ignores become permanently unspendable.

### Impact Explanation
Permanent freezing of funds: tokens that land on the controller or pool outside the credited-accounting legs can never be moved again. For the pool, donated/stray tokens are not revenue shares and cannot be claimed via `claim_revenue` (which is capped by `min(cash, floor(revenue_value))`); for the controller, every settlement function operates on deltas against the pre-existing balance, so the pre-existing balance itself is unreachable. The freeze is indefinite for the life of the contract — matching the kernel leak's "resource held for the lifetime of the device" severity rationale (CVSS 5.5, availability impact).

### Likelihood Explanation
Medium. Any unprivileged address can create the condition with a plain `token.transfer` to the controller or pool address, and stray balances also arise organically: flash receiver callbacks or swap-route legs that over-deliver to the controller leave residue that `refund_controller_balance_delta` is explicitly designed not to touch. The affected value is bounded by what users/miscredited flows actually strand, so it is a real but bounded permanent loss rather than a drain of accounted funds.

### Recommendation
Add a `sweep(asset, to)` entrypoint — owner- or governance-gated — that releases controller/pool token balances in excess of accounted obligations (for the pool: `balance − cash`; for the controller: the full balance, since no legitimate flow requires a persistent controller balance). Alternatively, treat stray pool balance as claimable revenue by crediting the surplus into revenue shares.

### Proof of Concept
1. Any account calls `token.transfer(user, controller, amount)` on a market asset, or a flash-position receiver callback transfers extra tokens to the controller.
2. The controller balance now exceeds zero; `claim_revenue_for_asset` snapshots `before` including this dust and forwards only the pool-delivered delta, leaving the dust behind (asserted by the harness test).
3. No controller or pool entrypoint accepts `(asset, recipient, amount)` to move a pre-existing balance; every outbound path (`transfer_out`, `refund_controller_balance_delta`, revenue forward) is bounded by credited cash or by a measured delta.
4. The transferred tokens are permanently frozen — the acquired resource is never released, the direct analog of `memremap()` without `memunmap()`.

Note: I verified the delta-preservation behavior in `payments.rs`, `markets.rs`, and `repay.rs`, and the harness test confirms stranded controller dust is intentional; I did not enumerate every `pub fn` in `contracts/controller/src/lib.rs`, so the conclusion that no sweep entrypoint exists is based on the absence of any rescue/skim semantics in the settlement code paths and tests reviewed.
