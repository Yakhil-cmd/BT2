### Title
Webhook `status` event trusts only the signing organization, not the target repository, enabling cross-repository commit-status writes - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` authenticates a webhook solely against the GitHub organization derived from `repository.owner.login` in the payload, using that organization's `webhook_secret` to validate the HMAC. [1](#0-0)  Once the signature is accepted, the handler for the `status` event, `Handlers::StatusHandler`, looks up commits **globally by SHA only**, with no scoping to the repository or organization that was actually authenticated: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }`. [2](#0-1)  This breaks the equality `organization authenticated == repository written`: the signature only proves the request came from a specific org's GitHub App/webhook config, but the write (a commit status upsert) is applied to any `Commit` record in the entire Shipit instance whose SHA matches, regardless of which repository/stack owns that commit.

By contrast, `Handlers::PushHandler` correctly scopes writes to `stacks` (implicitly filtered to the authenticated repository) before acting. [3](#0-2)  `StatusHandler` has no equivalent scoping.

### Finding Description
`verify_signature` resolves `Shipit.github(organization: repository_owner)` and validates the signature against that organization's secret only; it never re-checks that the specific `repository.full_name` in the payload is one the org is actually authorized/expected to represent for the resulting write. [4](#0-3) 

For the `status` event, the handler ignores the `repository` field of the payload entirely for scoping purposes and only uses `params.sha` (and `state`) to find matching `Commit` rows across the whole database: [5](#0-4) . Since `Commit` records belong to `Stack`s that belong to different `Repository` records, any commit SHA that happens to exist in more than one tracked repository (e.g., a fork sharing history/base commits with the upstream repository, or a repository that was renamed/re-added and re-uses old commit rows) will have its CI status overwritten by a webhook signed for a completely different, unrelated organization/repository.

### Impact Explanation
This is a cross-repository write: an attacker who controls (or has push/webhook access to) *any* GitHub organization/repository that Shipit has configured with a valid `webhook_secret` can forge a `status` webhook naming an arbitrary commit SHA and state (e.g., `success`), and have it applied to a `Commit` belonging to a completely different, unrelated stack/repository if that SHA happens to collide (via shared git history, forks, or reused commit objects). This can fabricate a passing CI status on a victim repository's commit, potentially satisfying `release_status_context` / `required_statuses` deploy gating (`DeploySpec#release_status_context`) and enabling an unauthorized deploy of that commit. This matches the "cross-repository writes" / "unauthorized deploy" Critical impact category.

### Likelihood Explanation
Likelihood requires the attacker to control (or otherwise have legitimate delivery access to) a GitHub organization/repo already configured in Shipit with its own `webhook_secret`/GitHub App installation — this is plausible in multi-tenant or monorepo-adjacent Shipit deployments where many orgs/repos are onboarded, and is explicitly an "unprivileged-attacker" scenario relative to the *victim* repository (the attacker never needs write access to the victim repo, a Shipit session, or an `ApiClient` token — only control of their own onboarded org's webhook delivery). The main constraint is the SHA-collision precondition (shared history between the attacker's repo and the victim's repo), which is realistic for forked/mirrored repositories commonly tracked side-by-side in the same Shipit instance.

### Recommendation
Scope the `status` handler's `Commit` lookup by the authenticated repository (e.g., join through `Stack`/`Repository` matching `params.repository.full_name`, the same value used to select `Shipit.github(organization:)`) instead of a global `Commit.where(sha:)`, mirroring the scoping already done in `PushHandler`.

### Proof of Concept
1. Onboard/attacker-controlled org `attacker-org/repo-fork` is configured in Shipit with a legitimate `webhook_secret` (any org Shipit trusts).
2. `attacker-org/repo-fork` shares a common ancestor commit `SHA_X` with the victim repository `victim-org/app` (e.g., it's a fork or was created from the same initial commit), and `SHA_X` is tracked as a `Commit` in `victim-org/app`'s stack.
3. Attacker sends a `status` webhook to Shipit signed with `attacker-org`'s secret: `{"sha": "SHA_X", "state": "success", "repository": {"owner": {"login": "attacker-org"}}}`.
4. `WebhooksController#verify_signature` validates the signature against `attacker-org`'s secret and passes. [1](#0-0) 
5. `StatusHandler#process` runs `Commit.where(sha: "SHA_X")`, which matches the commit in `victim-org/app`'s stack (unrelated to `attacker-org`), and calls `create_status_from_github!`, marking it as `success` in the victim's stack — potentially unblocking a deploy gated on that status. [2](#0-1)

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping
      head(:ok) if event == 'ping'
    end

    def event
      request.headers.fetch('X-Github-Event')
    end

    def repository_owner
      # Fallback to the organization sub-object if repository isn't included in the payload
      params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')

# frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class StatusHandler < Handler
        params do
          requires :sha, String
          requires :state, String
          accepts :description, String
          accepts :target_url, String
          accepts :context, String
          accepts :created_at, String

          accepts :branches, Array do
            requires :name, String
          end
        end

        def process
          Commit.where(sha: params.sha).each do |commit|
            commit.create_status_from_github!(params)
          end
        end
      end
    end
  end
