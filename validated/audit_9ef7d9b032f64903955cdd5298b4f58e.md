### Title
`Api::CCMenuController` Bypasses Per-Stack `ApiClient` Scoping, Allowing Cross-Stack Read Access - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::Api::CCMenuController` overrides the `stack` accessor used by `Api::BaseController` and looks up the stack directly from `params[:stack_id]` via `Stack.from_param!`, instead of going through the `stacks` scope that filters by `current_api_client.stack_id`. This breaks the binding: `current_api_client.stack_id` (the stack a token authorizes) == `params[:stack_id]` (the stack the token actually touches).

### Finding Description
`Api::BaseController#stacks` is designed to scope every request to only the stack(s) an `ApiClient` is authorized for: [1](#0-0) 
When `current_api_client.stack_id?` is true, only that one `Stack` is reachable; `stack` then calls `stacks.from_param!(params[:stack_id])`, which raises/404s if the requested stack doesn't match the scope.

`Api::CCMenuController`, however, redefines both `authenticate_api_client` (to allow query-string `token` auth, appropriate for CCTray clients) and `stack` — but the redefined `stack` method bypasses the scoped `stacks` relation entirely: [2](#0-1) 

`require_permission :read, :stack` only checks that the `ApiClient.permissions` array contains `read:stack`; it never validates `stack_id` against the requested resource: [3](#0-2) 

As a result, any `ApiClient` token that carries `read:stack` permission — including one explicitly scoped to a single stack via `stack_id` (as demonstrated by the "an api client scoped to a stack will only see that one stack" behavior enforced elsewhere in `StacksController`) — can be replayed with a different `stack_id` query parameter against `Api::CCMenuController#show` to read build status, activity, and last build info for **any** stack in the installation, not just the one it was authorized for.

### Impact Explanation
This is an unauthenticated (relative to the intended scope) cross-stack information disclosure: a token minted for reading one repository/stack's deploy status can be used to read deploy status, lock state, and build outcome for every stack managed by the Shipit instance, since `Stack.from_param!` is unscoped. This matches the "unauthenticated read of stack state" High-impact category — the credential the attacker legitimately holds (a stack-scoped `read:stack` token) is escalated into a global read primitive, breaking the authorization boundary the rest of the API (`StacksController`, `CommitsController`, `LocksController`, etc.) correctly enforces through `stacks.from_param!`.

### Likelihood Explanation
Any party holding a legitimately-issued, stack-scoped `ApiClient` token (e.g. a CI integration or a CCMenu URL handed to a specific team for a specific stack) can trivially exploit this by changing the `stack_id` in the request URL — no additional credentials, signatures, or privileged access required. The `token` query-string authentication path in `CCMenuController#authenticate_api_client` makes this even easier to exploit outside of Basic-Auth headers.

### Recommendation
Remove the custom `stack` override in `Api::CCMenuController`, or reimplement it to reuse the scoped `stacks` relation from `Api::BaseController`, e.g.:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
This restores the invariant that `current_api_client.stack_id` (if set) must match the stack being read.

### Proof of Concept
1. Create (or observe) a stack-scoped `ApiClient` with `permissions: ['read:stack']` and `stack_id` set to `Stack A`'s id (this is the normal "CCMenu Client" pattern created per-user by `CCMenuUrlController#client`, or any admin-scoped API client — see `app/controllers/shipit/ccmenu_url_controller.rb` lines 15-18 and `test/controllers/api/stacks_controller_test.rb` line 217 confirming scoped clients exist and are meant to see only their stack).
2. Using that client's `authentication_token`, issue:
   `GET /api/stacks/:stackB_id/ccmenu?token=<tokenScopedToStackA>`
   where `:stackB_id` is a **different** stack the token was never authorized for.
3. Because `Api::CCMenuController#stack` calls `Stack.from_param!(params[:stack_id])` directly rather than `stacks.from_param!`, the request succeeds and returns Stack B's `deploys_and_rollbacks`, lock status, and last build info — data the token holder was never granted access to.

Note: I was not able to fully confirm from the index whether `stack_id`-scoped `ApiClient` records are commonly created for CCMenu tokens specifically (the `CCMenuUrlController#client` method as currently written does not set `stack_id`), so the most concrete exploitation path is any other stack-scoped `read:stack` token (created via `Api::ApiClientsController`) being replayed against the CCMenu endpoint. A Devin session with full repository access could verify all call sites that mint stack-scoped tokens to strengthen this PoC.
