### Title
Task-defined `variables` in `shipit.yml` can shadow and override `GITHUB_TOKEN` in the task execution environment - ([File: lib/shipit/task_commands.rb#env])

### Summary
`TaskCommands#env` merges `@task.env` (built from the task's `shipit.yml`-declared `variables`) as the very last step, after `base_env` (which sets the real `GITHUB_TOKEN`). Because `TaskDefinition#filter_envs` only restricts submitted variables to the *names* declared in `shipit.yml` and does not reserve/blacklist infrastructure keys like `GITHUB_TOKEN`, a task definition that declares a variable literally named `GITHUB_TOKEN` allows its value to win the final merge and replace the genuine token used for git operations.

### Finding Description
The claimed binding is:
`TaskCommands.new(task).env['GITHUB_TOKEN'] == Commands#base_env['GITHUB_TOKEN']` (i.e., `Shipit.github(...).token`).

Tracing `lib/shipit/task_commands.rb`:
```ruby
def env
  super
    .merge(@stack.env)
    .merge(...)
    .merge(deploy_spec.machine_env)
    .merge(@task.env)
end
``` [1](#0-0) 

`super` resolves to `Commands#env`, which returns `base_env`, containing the real token:
```ruby
def base_env
  @base_env ||= begin
    env = Shipit.env.merge('GITHUB_DOMAIN' => github.domain, 'GITHUB_TOKEN' => github.token)
    ...
``` [2](#0-1) 

`@task.env` is the final merge, so any key it contains overrides everything preceding it, including `GITHUB_TOKEN`.

`TaskDefinition#filter_envs` (used to build `@task.env` from caller-supplied/default values) only permits keys that are declared as `variables` in `shipit.yml`:
```ruby
def filter_envs(env)
  EnvironmentVariables.with(env).permit(variables)
end

def variables_with_defaults
  @variables_with_defaults ||= variables.select(&:default_provided?)
end
``` [3](#0-2) 

There is no reserved-name check preventing a `shipit.yml` author from declaring a variable named `GITHUB_TOKEN`. Since review stacks load `shipit.yml` from the PR's own branch/fork, an attacker who owns a repository/fork and opens a PR controls this file entirely, satisfying the attacker model (unprivileged GitHub user who can push to their own fork/branch).

Exploit flow:
1. Attacker adds to their fork's `shipit.yml` a custom task with `variables: [{name: "GITHUB_TOKEN", default: "clobbered"}]`.
2. Attacker triggers the review-stack task via UI/API (or via a webhook-driven review stack flow).
3. `TaskDefinition#filter_envs`/`variables_with_defaults` produce `@task.env['GITHUB_TOKEN'] = "clobbered"` (or a caller-supplied value if the UI/API allows overriding variable values with defaults).
4. `TaskCommands#env` merges `@task.env` last, so `env['GITHUB_TOKEN']` becomes `"clobbered"` instead of the real token.
5. This env hash is passed to `Command`/`PTY.spawn` for git operations (clone/fetch/push), corrupting or replacing the credential used for those operations.

None of the standard guards intercept this: `filter_envs` filters by variable *name membership* only, not by a reserved-word blocklist; there's no model validation on `TaskDefinition`/`VariableDefinition` name to reject infrastructure env-var names.

### Impact Explanation
The task's execution environment used for git/network operations against GitHub has its `GITHUB_TOKEN` value overridden by attacker-controlled content declared in a repository-owned `shipit.yml`. This can corrupt git authentication for that task's git operations (clone/fetch/push) or, if a step in the task echoes environment variables (a common debug/step pattern), lead to secret confusion/exposure in task output. This affects the review stack tied to the attacker's own branch/fork; the blast radius is scoped to that stack's execution but represents an unauthorized credential-shadowing vector that matches the "exfiltration of GITHUB_TOKEN / deploy-time secrets" or "unauthorized deploy" Critical impact category.

### Likelihood Explanation
Preconditions are low-cost and fully within an unprivileged attacker's control: they need only push a `shipit.yml` with a task defining a `variables` entry named `GITHUB_TOKEN` to their own fork/branch and trigger the task through the review-stack task UI/API, which is standard, expected review-stack functionality (shipit.yml is read from the PR's own branch). No Shipit secrets, session, or maintainer privilege is required.

### Recommendation
In `TaskDefinition#filter_envs` (or `VariableDefinition`), reject/reserve infrastructure-critical environment variable names (`GITHUB_TOKEN`, `GITHUB_DOMAIN`, `GIT_ASKPASS`, etc.) so they cannot be declared as task variables, and/or change the merge order in `TaskCommands#env` so `base_env`'s security-critical keys are re-applied/merged last (or merged with `Hash#merge` using a block that refuses to let `@task.env` override reserved keys).

### Proof of Concept
```ruby
# test/unit/task_commands_test.rb (illustrative, no live GitHub)
test "task-declared GITHUB_TOKEN variable cannot override the real github token" do
  task_definition = Shipit::TaskDefinition.new(
    'custom_task',
    'action' => 'custom_task',
    'steps' => ['echo hi'],
    'variables' => [{ 'name' => 'GITHUB_TOKEN', 'default' => 'clobbered' }]
  )
  task = shipit_tasks(:shipit_deploy) # or a Task built with the above definition
  task.stubs(:definition).returns(task_definition)
  task.stubs(:env).returns(task_definition.filter_envs('GITHUB_TOKEN' => 'clobbered'))

  commands = Shipit::TaskCommands.new(task)

  assert_equal Shipit.github(organization: task.stack.repository.owner).token, commands.env['GITHUB_TOKEN']
  refute_equal 'clobbered', commands.env['GITHUB_TOKEN']
end
```
This asserts the two sides of the claimed binding directly against `TaskCommands#env`'s output.
