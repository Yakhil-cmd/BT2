### Title
Broken Access Control in device "sign" request handling allows any correspondent device to trigger signing of arbitrary units for wallet-controlled addresses — ([File: wallet.js])

### Summary
The external report describes a broken-access-control flaw where a privileged setup endpoint was left reachable without an authorization check, letting any unauthenticated caller retrieve sensitive credential material. The closest reachable analog in ocore is in the paired-device "sign" message handler in `wallet.js`, where the check that verifies the requesting device is actually a registered cosigner for the target address has been deliberately commented out, so the access-control gate that should restrict who may request a signature over a given address is missing.

### Finding Description
In `wallet.js` `handleMessageFromHub`, the `"sign"` subject handler is reachable from any device that has successfully completed device pairing (a normal, low-privilege, unauthenticated-relative-to-wallet-funds action) via the hub message pipeline (`device.js` `handleJustsaying` "hub/message" → `eventBus.emit("handle_message_from_hub", ...)`). [1](#0-0) 

After validating the unsigned unit structure, the code calls `findAddress(...)` and, in the `ifLocal` branch — which is taken whenever the requested `body.address` is an address that this device actually controls locally — it immediately calls `callbacks.ifOk()` and emits the `"signing_request"` event that ultimately drives the actual signing flow. The commented-out code shows that the intended check ("sender is not cosigner of this address") — a query against `extended_pubkeys WHERE wallet=? AND device_address=?` — has been disabled: [2](#0-1) 

By contrast, the `ifRemote` branch of the very same handler *does* enforce that the sender must be a listed cosigner (`other_device_addresses.includes(from_address)`), confirming that this authorization check is the intended security control and that its absence in `ifLocal` is a broken-access-control gap rather than by design: [3](#0-2) 

Because the local branch skips this ownership/cosigner check, **any device that is a correspondent of the wallet's device (paired at any point, even for an unrelated purpose such as a merchant/bot pairing) can send a `"sign"` request naming any of the wallet's own addresses**, and the wallet will treat it as a legitimate signing request and proceed to the confirmation/signing pipeline (`eventBus.emit("signing_request", ...)`), instead of rejecting it outright as an unauthorized request from a non-cosigner.

### Impact Explanation
For interactive wallets, `"signing_request"` is expected to trigger a UI confirmation dialog before any private key operation occurs, which mitigates the impact somewhat but still exposes users to social-engineering / confirmation-fatigue attacks where they are tricked into approving transactions requested by devices they never intended to grant signing authority to for that address. For headless/bot wallets — which are commonly used for exchanges, gateways, and automated payment services and are supposed to auto-sign requests coming only from cosigners of a specific multisig arrangement — the missing check means an unrelated, merely-paired correspondent device can originate signing requests for addresses it has no legitimate right to co-sign, directly enabling unauthorized creation of signed spending transactions from wallet-controlled funds. This matches the "concrete unauthorized spending" impact bar, since the broken check is precisely the authorization gate meant to prevent non-cosigners from getting the wallet to produce signatures over arbitrary attacker-supplied units for wallet addresses.

### Likelihood Explanation
Likelihood is high for any deployment using headless wallet automation (bots, exchanges, gateways) because: (1) pairing with a new device is a normal, low-friction, self-service action; (2) once paired, the correspondent is trusted for the `"sign"` subject with no further per-address authorization check on the local-signing path; (3) the attack requires no special network position or vulnerability chaining — just a device pairing and a single crafted `"sign"` message naming any address the target device controls.

### Recommendation
Restore (and generalize, if multilateral signing must be supported) the disabled cosigner check in the `ifLocal` branch of the `"sign"` handler in `wallet.js`: before emitting `"signing_request"` or invoking `network.handleOnlineJoint`, verify that `from_address` is a legitimate cosigner of `body.address` (e.g., present in `extended_pubkeys`, `shared_address_signing_paths`, or an equivalent multi-signer definition, depending on how the address was constructed) rather than merely being *any* known correspondent device. If multilateral signing (different addresses each owned by different peers, all under the same message) is a required use case, the check should validate that `from_address` is authorized to request a signature for that specific unit/context (e.g., is itself a party to the same contract/definition), not skip verification entirely.

### Proof of Concept
1. Attacker device pairs with the victim's headless wallet using any pairing code (a normal, unprivileged operation), becoming a `correspondent_devices` entry.
2. Attacker sends a device `"sign"` message to the victim: `{address: <victim's own wallet address>, signing_path: "r", unsigned_unit: {...attacker-crafted payment spending victim's funds...}}`.
3. In `wallet.js`, `findAddress` resolves `ifLocal` because the address genuinely belongs to the victim's wallet.
4. The disabled check that would normally reject the request (`"sender is not cosigner of this address"`) never runs, so `callbacks.ifOk()` fires and `"signing_request"` is emitted for the attacker-supplied unit.
5. On a headless/bot deployment where `"signing_request"` is wired to auto-sign (no interactive confirmation), the wallet computes and returns/broadcasts a valid signature over the attacker's unit, resulting in unauthorized spending from the victim's address.
