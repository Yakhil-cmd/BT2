### Title
`liquidate-multi` batch isolation is broken by `unwrap-panic` traps inside `call-liquidate`, letting one malformed position abort an entire liquidation batch - ([File: mainnet/contracts/market/v0-4-market.clar])

### Summary
`liquidate-multi` is documented and designed to isolate failures per-position: "Failed liquidations return error codes but don't revert entire batch" [1](#0-0) . It implements this by `(ok (map call-liquidate positions))`, expecting each `liquidate` call to fail gracefully via `try!`/`(err ...)` responses that `map` simply collects into a list [2](#0-1) . However, several helper functions invoked transitively from `liquidate` use `unwrap-panic` instead of `try!`/`unwrap!`, e.g. `process-debt-asset`'s `(unwrap-panic (find-asset debt-aid assets))` [3](#0-2) , `process-collateral-asset`'s `(unwrap-panic (price-resolve oracle-data))` for disabled collateral [4](#0-3) , and `(unwrap-panic (get-cached-indexes asset-id))` used repeatedly in `scale-debt-for-liquidation` and the remaining-debt calculation [5](#0-4) . `unwrap-panic` in Clarity is a hard runtime trap: it does not produce a catchable error, it aborts the **entire enclosing transaction** atomically. Because `map` runs all `call-liquidate` invocations inside a single transaction, one position that hits any of these traps rolls back the state changes (debt removal, collateral seizure, bad-debt socialization) already performed for every other position processed earlier in the same `map` call.

### Finding Description
The comment and API contract of `liquidate-multi` promise per-position isolation so that a liquidator can safely batch several unrelated positions and rely on partial success [6](#0-5) . This contract only holds if every failure path inside `liquidate` returns through `try!`/`unwrap!` (producing a `(response ... uint)` error that `try!` can propagate up as an ordinary `err`). But `process-debt-asset`, `process-collateral-asset`, and `scale-debt-for-liquidation` use `unwrap-panic`, which is the Clarity analog of an unrecovered panic: it is not converted into a normal error and is not caught anywhere in the `liquidate` → `call-liquidate` → `map` call chain. A single position whose `debt-aid` is absent from `assets` (e.g., a debt asset outside the currently enabled/priced asset list for that egroup) or whose disabled-collateral oracle resolution fails will trap, and Clarity semantics discard the whole transaction rather than just the array element — exactly the same failure class as the IoTeX bug where a panic unwound past the intended per-action isolation and discarded the surrounding batch/draft instead of just the offending action.

### Impact Explanation
Because `liquidate-multi` exists specifically "to prevent front-running attacks that prevent bad debt socialization" by bundling multiple liquidations atomically [7](#0-6) , a landmine position placed in the batch by one principal (e.g., a borrower whose account is deliberately or incidentally left with a debt asset outside the enabled mask, or with a disabled collateral asset whose oracle currently fails/staleness-reverts) causes the whole batch transaction to trap and roll back. Other unhealthy positions bundled in the same call — belonging to unrelated borrowers who were legitimately due for liquidation and, per the code comment, for coordinated bad-debt socialization — are silently protected from liquidation for that attempt, and any liquidation/socialization work already computed in that same transaction is discarded. This creates a freezing/denial condition on liquidation and bad-debt socialization that the batch API was explicitly built to guarantee, falling under temporary freezing of protocol remediation function (bad-debt socialization), which can compound into protocol insolvency risk if repeated to block liquidations of accounts accruing bad debt.

### Likelihood Explanation
Likelihood is moderate-to-low: it requires either (a) a borrower's own account entering a state where their debt/collateral asset is absent from the currently resolved `assets` list for their egroup or its disabled-collateral price resolution reverts, and (b) that borrower being included in a `liquidate-multi` batch together with other positions. This can occur without any privileged action, purely through combinations of egroup/mask state and oracle availability that are already reachable in normal protocol operation, but it depends on state/oracle conditions outside the caller's/attacker's direct control, making it more of a reliability/DoS hazard than a directly exploitable theft. I was not able to fully verify from the available index whether `find-asset debt-aid assets` can return `none` under legitimate operational conditions (e.g., is it guaranteed by `get-egroup`/mask invariants that every asset with nonzero debt is always present in `assets`?) — this would need confirmation via a Devin session with full repo access, since the wiki-indexed excerpts do not show the complete invariant proof for `get-assets`/`find-asset`.

### Recommendation
Replace the `unwrap-panic` calls inside `process-debt-asset`, `process-collateral-asset`, and `scale-debt-for-liquidation` (and any other helper reachable from `liquidate`) with `unwrap!`/`try!` patterns that return a proper `(err ...)` response. Then wrap `call-liquidate`'s invocation of `liquidate` in `liquidate-multi` with an explicit catch (e.g., via `match`) so that any error response — rather than an uncatchable trap — is what determines per-position isolation, matching the documented "failed liquidations return error codes but don't revert entire batch" contract.

### Proof of Concept
1. Borrower `B` has a position whose obligation record still references a debt asset `X` that is not currently present in the `assets` list returned by `get-assets` for `B`'s current egroup mask (e.g., due to a mask/egroup transition edge case, or `X`'s oracle price being unresolvable so it is dropped from the enabled list at valuation time).
2. Liquidator submits `liquidate-multi` with `positions = [liquidate(B, ...), liquidate(A, ...)]` where `A` is a genuinely healthy-to-liquidate, unrelated borrower.
3. `map call-liquidate positions` first (or in any order within the same tx) processes `B`; inside `liquidate` → `process-debt-asset`, `(unwrap-panic (find-asset debt-aid assets))` traps because `X` (debt-aid) is not in `assets`.
4. The Clarity VM aborts the whole `liquidate-multi` transaction; `A`'s liquidation (and any state changes already applied to the market/vault for `A`) is rolled back even though `A`'s liquidation was independently valid.
5. Net effect: no positions are liquidated in that transaction, contradicting the API's documented partial-success guarantee, and any coordinated bad-debt-socialization intent for `A` is defeated by `B`'s unrelated, uncaught trap.
