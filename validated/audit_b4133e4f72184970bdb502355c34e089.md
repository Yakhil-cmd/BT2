### Title
Cross-organization/cross-repository commit-status forgery via unscoped `StatusHandler` breaks the org-authenticated-vs-repository-written binding, enabling unauthorized merges/deploys - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`WebhooksController#verify_signature` authenticates an inbound GitHub webhook using the `webhook_secret` of the **organization** derived from `repository.owner.login` (or the `organization.login` fallback), i.e. `Shipit.github(organization: repository_owner)`. However, `Shipit::Webhooks::Handlers::StatusHandler`, which processes `status` events, never checks which repository/organization the payload claims to be for. It matches purely by commit SHA across the *entire* installation: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }`. Any Shipit deployment that authenticates webhooks for more than one GitHub organization (a supported, documented configuration, see `config/secrets.development.shopify.yml`) allows a party who legitimately controls one organization's GitHub App webhook secret to forge a signed `status` event that updates the CI status of a commit belonging to a completely different organization's stack, because the signing organization is never checked against the commit's actual stack/repository.

### Finding Description
The equality that should hold is:

`organization authenticated by HMAC (repository_owner used in verify_webhook_signature)` == `organization/repository whose commit status is mutated`

In `app/controllers/shipit/webhooks_controller.rb`:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) [2](#0-1) 

This selects which organization's `webhook_secret` validates the request's HMAC signature — it is attacker-suppliable JSON (`repository.owner.login` / `organization.login`), and it is only used to pick the *verifying* secret, never propagated to the event handler.

`StatusHandler`, which processes the `status` event, ignores `repository` entirely and updates any commit matching the SHA anywhere in the database:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [3](#0-2) 

Compare this to the base `Handler` class, which does define a `repository_name`/`stacks` scoping helper based on `payload.dig('repository', 'full_name')`, but `StatusHandler` does not use it: [4](#0-3) 

`create_status_from_github!` creates a `Status` record, which triggers side effects regardless of which org "authenticated" the request:
```ruby
after_create :enable_ci_on_stack
after_commit :schedule_continuous_delivery, :broadcast_update, on: :create
``` [5](#0-4) 

And in `Commit#add_status`:
```ruby
stack.schedule_merges if new_status.pending? || new_status.success?
``` [6](#0-5) 

`schedule_continuous_delivery` eventually calls `Stack#trigger_continuous_delivery`, which can call `trigger_deploy` and actually start a deployment: [7](#0-6) [8](#0-7) 

`schedule_merges` enqueues `ProcessMergeRequestsJob`, part of the Merge Queue that can merge a pull request once CI is reported green — this analog directly parallels the report's "successful action on an entity the signature never actually bound to": the SafeTransferLib report shows a successful transfer despite the token not existing; here, a webhook is treated as authentic for a repository/commit it was never cryptographically tied to, because the org used to verify the signature and the commit acted upon are two unrelated payload fields.

Multi-organization configuration is a supported, documented deployment mode (each org has its own independently generated `webhook_secret`), as shown in `config/secrets.development.shopify.yml`: [9](#0-8) 

### Impact Explanation
Any actor who legitimately controls the GitHub App webhook secret of *one* organization configured on a shared Shipit instance can forge a `status` webhook that is verified as authentic (because verification only checks that org's HMAC secret), but which mutates commit status for a commit belonging to a *different* organization's stack anywhere in the Shipit installation (the handler does zero repository binding, matching purely by SHA). Since a successful/pending status can (a) trigger `ContinuousDeliveryJob`, resulting in an unauthorized deploy of a real stack, and (b) enqueue `ProcessMergeRequestsJob`, contributing toward an unauthorized merge in the merge queue, this crosses the "unauthorized deploy... or merge" Critical-impact bar defined in scope, without requiring any Shipit session, API token, or privileged account on the *victim* organization/repository — only knowledge of the target commit SHA (public information) and the attacker's own (unrelated) org's webhook secret.

### Likelihood Explanation
This requires a multi-tenant Shipit deployment (multiple GitHub organizations configured with their own webhook secrets), which is an explicit, supported, documented configuration pattern in this codebase. Any organization admin/app-installer who can view or set their own org's GitHub App webhook secret (a routine, low-privilege operational task, not requiring victim-repo access) can exploit this deterministically and repeatedly against any known commit SHA in any other stack tracked by the shared instance.

### Recommendation
`StatusHandler` (and any other handler that trusts `sha`/`repository` fields without cross-checking) must scope its lookup to commits/stacks belonging to the same organization/repository that was authenticated by `verify_signature`, e.g. by threading the verified `repository_owner`/`repository.full_name` into the handler and requiring `Commit.joins(stack: :repository).where(sha: params.sha, repositories: { owner: verified_owner })`, rather than a bare `Commit.where(sha:)` across the entire installation. More generally, the org/repo identity used to select the verifying webhook secret should be enforced as an invariant everywhere a webhook payload subsequently acts on a specific stack/commit/repository.

### Proof of Concept
1. Shipit is configured (per `config/secrets.*.yml`) with two organizations, e.g. `attacker-org` (webhook secret known to the attacker, who legitimately administers that org's GitHub App) and `victim-org` (a stack unrelated to the attacker).
2. Attacker crafts a `status` webhook JSON body:
```json
{
  "sha": "<sha-of-a-commit-in-victim-org-stack>",
  "state": "success",
  "context": "ci/forged",
  "repository": { "owner": { "login": "attacker-org" } }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<hmac-sha1(attacker-org's webhook_secret, body)>` and POSTs to `/webhooks` with `X-Github-Event: status`.
4. `WebhooksController#verify_signature` resolves `repository_owner` = `"attacker-org"`, fetches `Shipit.github(organization: "attacker-org")`, and validates the signature successfully because the attacker used the correct (their own) secret. [1](#0-0) 
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)`, matches the victim's commit (which belongs to a stack under `victim-org`, never checked), and creates a `success` `Status` on it. [3](#0-2) 
6. If `victim-org`'s stack has `continuous_deployment: true`, `ContinuousDeliveryJob` is scheduled and can trigger a real deploy; if the commit is part of an open PR, `ProcessMergeRequestsJob` is enqueued and can contribute to an unauthorized merge — all without the attacker ever authenticating against `victim-org`.
