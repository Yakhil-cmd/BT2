### Title
AA bounce logic can discard all trigger funds instead of returning them, when just one of several sent assets fails to cover its own bounce fee - ([File: aa_composer.js])

### Summary
`handleTrigger`'s internal `bounce()` function is supposed to return unused/rejected funds (base bytes plus any other assets) back to the trigger sender when a primary AA trigger is bounced. Instead, when a trigger sends multiple assets/currencies together (e.g. base bytes plus a token) and **any single asset** among them doesn't cover its own `bounce_fees[asset]`, the function aborts the entire refund process via `return finish(null)` and returns **nothing** — not even the assets/bytes that were otherwise sufficient to be refunded.

### Finding Description
`handleTrigger` builds `trigger.outputs` from every payment message the trigger unit sent to the AA address, keyed by asset (`base` or asset hash), aggregating all assets sent in one trigger unit. [1](#0-0) 

Before evaluating the AA, it pre-checks that every asset sent has enough amount to cover its configured `bounce_fees[asset]`; if not, it calls `bounce('received ' + asset + ' is not enough to cover bounce fees')`. [2](#0-1) 

Inside `bounce()`, the function iterates over **all** assets present in `trigger.outputs` to build refund messages for each of them:
```js
for (var asset in trigger.outputs) {
    var amount = trigger.outputs[asset];
    var fee = bounce_fees[asset] || 0;
    if (fee > amount)
        return finish(null);
    if (fee === amount)
        continue;
    var bounced_amount = amount - fee;
    messages.push({app: 'payment', payload: {asset: asset, outputs: [{address: trigger.address, amount: bounced_amount}]}});
}
if (messages.length === 0)
    return finish(null);
sendUnit(messages);
``` [3](#0-2) 

The bug: `if (fee > amount) return finish(null);` unconditionally aborts the **whole** refund attempt for **every** asset in `trigger.outputs`, not just the offending one. This is exactly the same `fee > amount` condition that triggered the call to `bounce()` in the first place (line 1856: `bounce_fees[asset] && trigger.outputs[asset] < bounce_fees[asset]`). So whenever a trigger sends two or more assets together and even one small/dust asset amount fails to cover its bounce fee, the entire loop bails out before any `sendUnit(messages)` call, and `finish(null)` is invoked with no response unit at all — meaning the base bytes and any other, fully-sufficient asset sent by the trigger sender are silently absorbed into the AA's balance and never refunded.

This mirrors the reported `BountyCore.receiveFunds` pattern: a function that conditionally handles one "kind" of payment (there: `_tokenAddress`, here: `asset`) fails to properly handle/return the other kind of value sent alongside it, resulting in permanent loss of the sender's funds with no revert and no refund.

### Impact Explanation
An AA trigger sender who legitimately sends a large base-byte payment (sufficient bytes to cover `bounce_fees.base`) together with even a tiny amount of some other asset that doesn't reach that asset's `bounce_fees[asset]` threshold will have **all** funds sent in that unit permanently absorbed by the AA with no bounce/refund response, even though the AA logic never executed and the trigger was fully rejected. This is a direct, unauthorized fund loss for an unprivileged AA trigger sender, matching "AA fund loss" impact criteria.

### Likelihood Explanation
This is trivially reachable by any address that sends a trigger unit containing more than one asset (a common, encouraged usage pattern — e.g., paying bytes plus a custom token to an AA in one unit) where the AA defines `bounce_fees` for that asset and the amount sent for that asset happens to fall short of the fee (dust amount, accidental wrong amount, or malicious third-party output added to the same unit). No special privilege or AA cooperation is required — it is purely a client-facing/trigger-sending mistake with a network-level guaranteed loss.

### Recommendation
Fix the loop in `bounce()` so that an asset failing to cover its own bounce fee only excludes that asset's refund message rather than aborting the refund for all other assets in `trigger.outputs`. For example, replace `if (fee > amount) return finish(null);` with `continue;` (skip refunding that particular asset while still refunding the others), or reconsider absorbing only the insufficient asset while still generating the bounce unit for the rest.

### Proof of Concept
1. Deploy an AA with `bounce_fees: { base: 10000, 'ASSET_X': 5000 }` and a message body that will error/bounce for some unrelated reason (or that intentionally triggers `bounce()` via the pre-check).
2. Send a trigger unit containing:
   - a `payment` message with `asset: 'base'`, output amount `50000` to the AA (well above `bounce_fees.base`)
   - a second `payment` message with `asset: 'ASSET_X'`, output amount `100` to the AA (below `bounce_fees['ASSET_X']`)
3. `getTrigger()` aggregates `trigger.outputs = { base: 50000, ASSET_X: 100 }` [4](#0-3) .
4. The pre-check at line 1855-1858 detects `trigger.outputs['ASSET_X'] (100) < bounce_fees['ASSET_X'] (5000)` and calls `bounce('received ASSET_X is not enough to cover bounce fees')` [5](#0-4) .
5. Inside `bounce()`, the loop reaches `asset = 'ASSET_X'`, computes `fee (5000) > amount (100)`, and calls `return finish(null)` — aborting the loop entirely before the `base` asset (which had plenty of margin) is ever added to the refund `messages` array [6](#0-5) .
6. Result: `finish(null)` produces no response unit; the sender's 50000 bytes are never returned and become part of the AA's balance with no trace of a refund, while the AA never actually accepted/ran the trigger logic.
