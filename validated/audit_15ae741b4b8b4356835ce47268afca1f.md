### Title
MembershipHandler ignores the signing organization, letting one org's validly-signed webhook add members to another org's Team - (File: app/models/shipit/webhooks/handlers/membership_handler.rb)

### Summary
`MembershipHandler#find_or_create_team!` resolves the target `Team` purely by the attacker-supplied `params.team.id`, with no check that it belongs to the `organization.login` whose signature was verified. This lets an attacker who legitimately administers *any* GitHub organization onboarded into a multi-tenant Shipit instance (and thus knows that org's own `webhook_secret`) send a `membership` `added` webhook naming a `team.id` that belongs to a different, unrelated organization (e.g. one listed in `Shipit.github_teams`), causing Shipit to add an attacker-controlled user to that team's `memberships`.

### Finding Description
The broken binding: `Team row matched by find_or_create_by!(github_id: params.team.id).organization == params.organization.login (the org whose signature was verified)`. This does not hold — `find_or_create_team!` performs `Team.find_or_create_by!(github_id: params.team.id) { |team| team.organization = params.organization.login }` (app/models/shipit/webhooks/handlers/membership_handler.rb:38-43); the block only runs on *creation*, so if a `Team` row with that `github_id` already exists (created earlier for a different organization, e.g. "shopify"), it is returned as-is and `team.organization` is never checked or updated [1](#0-0) .

`WebhooksController#verify_signature` only verifies that the signature matches `Shipit.github(organization: repository_owner)`, where `repository_owner` is derived from the payload's own `organization.login` for membership events [2](#0-1) [3](#0-2) . It never cross-checks that the `team.id` embedded in the payload actually belongs to that same organization on GitHub's side. So a validly-signed request from Org B ("attacker-org") can name any `team.id` value, including one already recorded for Org A ("shopify").

Exploit flow: attacker administers "attacker-org", which is a separate GitHub organization already onboarded into the same Shipit instance (so it has its own `webhook_secret` configured in Shipit's secrets, known to the attacker as the org admin who set up that webhook). They POST to `/webhooks` a `membership` event: `{"action":"added","team":{"id":<shopify_team_github_id>,...},"organization":{"login":"attacker-org"},"member":{"login":"attacker"}}` signed with attacker-org's webhook secret. `verify_signature` resolves and validates against `Shipit.github(organization: "attacker-org")` and passes. `MembershipHandler#process` then calls `find_or_create_team!`, which matches the *existing* Team row (github_id equal to the target team, organization = "shopify") because lookup is by `github_id` only, and calls `team.add_member(User.find_or_create_by_login!('attacker'))`, inserting a `Membership` row for the attacker into that Shopify team [4](#0-3) [5](#0-4) .

Existing guards do not prevent this: `verify_signature` authenticates only that the request came from the claimed organization, not that the claimed `team.id` is owned by that organization; there is no model validation on `Team` or `Membership` tying `github_id` to `organization`, and the `teams` unique index is only on `(organization, slug)`, not on `github_id` [6](#0-5) [7](#0-6) . If that Team happens to be one entry in `Shipit.github_teams` (`@github_teams ||= github.oauth_teams.map { |t| Team.find_or_create_by_handle(t) }`), the attacker becomes a member of a team Shipit uses for authorization checks [8](#0-7) .

### Impact Explanation
The attacker gains membership in an arbitrary pre-existing `Team` record — including one configured in `Shipit.github_teams` for global application authorization — without GitHub ever reporting that membership for that team, and without any call to `Shipit.github(organization: 'shopify')`. This is repeatable against any Team github_id the attacker can discover or brute-force, is not scoped to a single repository/stack, and constitutes cross-tenant mutation: a payload correctly authenticated for Org B mutates data belonging to Org A. This matches the High severity category "escalation into `Shipit.github_teams` authorization."

### Likelihood Explanation
This requires: (1) a multi-tenant Shipit deployment configuring more than one GitHub organization, each with its own `webhook_secret`; (2) the attacker legitimately administering at least one of those onboarded organizations (thus knowing its own configured `webhook_secret`); (3) knowledge or brute-forceable discovery of the numeric `github_id` of the target team (team IDs are sequential and not secret — visible via GitHub's API/UI to team members, or guessable). Given those preconditions, the attack is a single unauthenticated-relative-to-target-org HTTP POST, fully repeatable, and does not require access to the target org's secrets at all. In a single-org deployment (only "shopify" configured) this specific path is not reachable, since the attacker would have no other org's `webhook_secret` to sign with.

### Recommendation
In `MembershipHandler#find_or_create_team!`, scope the lookup by both `github_id` and `organization` (e.g. `Team.find_or_create_by!(github_id: params.team.id, organization: params.organization.login)`), and reject/raise if an existing Team with that `github_id` has a different `organization` than the one whose signature was verified, rather than silently reusing the record.

```ruby
test ":membership from a different org cannot add members to another org's team" do
  # shipit_teams(:shopify_developers) has organization: 'shopify', github_id: 1
  target_team = shipit_teams(:shopify_developers)

  # Configure/stub a second organization "attacker-org" with its own webhook_secret
  Shipit.stubs(:github).with(organization: 'attacker-org').returns(
    stub(verify_webhook_signature: true)
  )

  request.headers['X-Github-Event'] = 'membership'
  payload = {
    action: 'added',
    team: { id: target_team.github_id, name: target_team.name, slug: target_team.slug, url: target_team.api_url },
    organization: { login: 'attacker-org' }, # signature verified against attacker-org, NOT shopify
    member: { login: 'attacker' }
  }

  assert_no_difference -> { Membership.where(team: target_team).count } do
    post :create, body: payload.to_json, as: :json
  end
  # Currently this assertion FAILS: Membership.count increases by 1 for target_team,
  # proving cross-organization team mutation via a validly-signed but unrelated org's webhook,
  # with no call to Shipit.github(organization: 'shopify').
end
```
