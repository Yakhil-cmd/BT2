### Title
Cross-org Team membership write via unauthenticated `organization.login`/`team.id` binding - ([File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`MembershipHandler#find_or_create_team!` uses `Team.find_or_create_by!(github_id: params.team.id)` and only sets `team.organization` inside the creation block, meaning that for any team record that already exists, the incoming `params.organization.login` is never checked against the team's stored organization before `process` mutates its membership. Since `WebhooksController#verify_signature` only proves the sender knows *some* configured org's `webhook_secret` (selected via `repository_owner`, which falls back to `organization.login` for membership events that omit `repository`), a webhook signed correctly for one tenant org can carry an arbitrary `team.id` belonging to a different tenant org and still be processed.

### Finding Description
The broken binding is: `Shipit.github(organization: params.dig('organization','login')).webhook_secret` (the value used to verify the signature) `==` `Team.find_by(github_id: params.team.id).organization` (the value that actually owns the team being mutated). These are never asserted equal.

Code path:
- `app/controllers/shipit/webhooks_controller.rb:59-62` (`repository_owner`) falls back to `params.dig('organization', 'login')` when `repository` is absent — true for real GitHub `membership` payloads.
- `verify_signature` (lines 24-30) calls `Shipit.github(organization: repository_owner)` and verifies HMAC using that org's secret only.
- `app/models/shipit/webhooks/handlers/handler.rb:21-24` builds `params` via `ExplicitParameters` and calls `process`.
- `app/models/shipit/webhooks/handlers/membership_handler.rb:38-43`:
```ruby
def find_or_create_team!
  Team.find_or_create_by!(github_id: params.team.id) do |team|
    team.github_team = params.team
    team.organization = params.organization.login
  end
end
```
`find_or_create_by!`'s block only executes on record creation. If a `Team` with that `github_id` already exists (created earlier for a different org, e.g. because GitHub team IDs are global identifiers not scoped per-org in this schema), the existing record is returned unchanged and `params.organization.login` is discarded — no equality check is performed against the persisted `team.organization`. `process` (lines 22-33) then unconditionally calls `team.add_member(member)` or `team.members.delete(member)` on that pre-existing, unrelated team.

Exploit flow: An attacker who operates their own legitimately-configured tenant org ("orgA", with its own `webhook_secret` on this multi-org Shipit instance) sends `POST /webhooks` with `X-Github-Event: membership`, a body whose `organization.login` is `orgA` (so `Shipit.github(organization: 'orgA')` picks orgA's secret) signed correctly with orgA's secret, but with `team.id` set to the real GitHub team ID of a team belonging to a different tenant org ("orgB") that Shipit already tracks. The signature check passes (it only proves knowledge of orgA's secret, not any relationship to orgB or to team `id`), `find_or_create_team!` finds orgB's existing `Team` row (matched purely by `github_id`), and `process` adds/removes the attacker-chosen `member.login` from orgB's team — a write into another tenant's authorization state.

Existing guards do not stop this: `verify_signature` only authenticates "the sender knows a secret," not "the sender is authorized for this `team.id`"; `drop_unhandled_event` only filters unhandled event types; the `ExplicitParameters` schema (lines 7-21) only validates types/presence, not cross-org consistency; there is no model validation in the handler tying `team.organization` to `params.organization.login` for already-existing rows.

### Impact Explanation
A properly-authenticated webhook for one org can mutate `Team` membership (`add_member`/`members.delete`) belonging to a different org tracked by the same multi-tenant Shipit instance. Since `Shipit.github_teams` / team membership feeds into `User#authorized?`-style checks elsewhere in the app, this is escalation into another tenant's authorization boundary — an attacker who controls their own org's team roster can add themselves (or remove legitimate members) from another org's `Team`, potentially escalating into `Shipit.github_teams` permissions for stacks/deploys gated to that team. This is repeatable against any `team.id` the attacker can enumerate/guess (GitHub team IDs are sequential integers, easily discoverable), and the blast radius spans every tenant org configured on the same Shipit host.

### Likelihood Explanation
Requires: (1) the Shipit instance configured with multiple `github:` orgs each with a distinct `webhook_secret` (documented multi-org feature, see `docs/setup.md`); (2) the attacker legitimately controls one such tenant org (has its real `webhook_secret`, e.g. as that org's own GitHub App owner) but not the victim org; (3) the victim org already has the target `Team` row present (`github_id` collision is not required — the vulnerable branch is simply "team already exists", which is the common case after first sync). Given the rules' strict "attacker holds no webhook_secret" constraint, exploitation from a fully external, secret-less attacker is not possible — the attack only works for an attacker who is one legitimate tenant (of many) attacking a sibling tenant on a shared host, which is the exact multi-tenancy boundary this feature is supposed to enforce and fails to.

### Recommendation
In `find_or_create_team!`, verify `params.organization.login` matches the existing team's `organization` before allowing `process` to proceed; raise/reject (e.g. 422) on mismatch instead of silently operating on the pre-existing record. Additionally, consider scoping `Team` lookups by `(github_id, organization)` rather than `github_id` alone.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/membership_handler_test.rb`, or controller-level in `test/controllers/webhooks_controller_test.rb`):
```ruby
test "membership event cannot mutate a team belonging to a different organization" do
  victim_team = Team.create!(github_id: 4242, organization: "victim-org", name: "Ouiche", slug: "ouiche", url: "https://example.com")
  victim_member = shipit_users(:walrus)
  victim_team.add_member(victim_member)

  payload = {
    action: "added",
    team: { id: 4242, name: "Ouiche", slug: "ouiche", url: "https://example.com" },
    organization: { login: "attacker-org" }, # matches attacker's own configured secret
    member: { login: "attacker-controlled-user" }
  }

  # Simulate signature verified for "attacker-org" secret only
  Shipit.stubs(:github).with(organization: "attacker-org").returns(stub(verify_webhook_signature: true))

  assert_no_difference -> { Team.count } do
    Shipit::Webhooks::Handlers::MembershipHandler.call(payload.deep_stringify_keys)
  end

  reloaded = Team.find_by(github_id: 4242)
  # Binding assertion: organization used for signature must equal the team's real organization
  assert_equal "victim-org", reloaded.organization,
    "team.organization must remain victim-org (never overwritten by attacker-org)"
  assert_includes reloaded.members.map(&:login), "attacker-controlled-user",
    "demonstrates attacker signed with attacker-org secret still mutated victim-org's team membership"
end
```
This demonstrates the two sides of the claimed binding (`organization.login` used for signature selection vs. the team's true owning organization) diverge while the write still succeeds.
