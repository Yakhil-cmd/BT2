### Title
XCM `ERC20Transactor` trusts the ERC20 boolean return value instead of verifying actual balance delta, permitting fee-on-transfer/short-transfer tokens to desynchronize XCM holding accounting - (File: cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs)

### Summary
`ERC20Transactor::withdraw_asset_with_surplus` and `deposit_asset_with_surplus` move ERC20 tokens by calling `IERC20::transferCall` via `pallet_revive::Pallet::<T>::bare_call` and treat a decoded `true` return as proof that exactly `amount` moved. Neither function checks the checking-account's or beneficiary's actual balance before/after the call.

### Finding Description
`withdraw_asset_with_surplus` ( [1](#0-0) ) calls `transfer(checking_address, amount)` from the user's account and, if the contract returns `true`, unconditionally credits the XCM holding register with `Erc20Credit(amount)` — the *requested* amount, not the amount actually received by the checking account. `deposit_asset_with_surplus` ( [2](#0-1) ) does the symmetric thing when paying a beneficiary out of the checking account.

The asset is matched purely structurally: `ERC20Matcher` accepts any local `AccountKey20` location ( [3](#0-2) ), so any contract deployed via `pallet-revive` can act as the "ERC20" for this transactor — there is no vetting step enforced in code. This is the exact bug class from the report: the code assumes `transferCall` returning `true` implies the destination balance increased by `amount`, which the ERC20 standard does not guarantee (fee-on-transfer, rebasing, or otherwise non-standard tokens can return `true` while moving less).

Consequence: `AssetsInHolding` inside the XCM executor will hold more "ERC20" units than the checking account actually possesses. That imbalanced holding can subsequently be deposited to a beneficiary via `deposit_asset_with_surplus`, which again just calls `transfer` for the nominal `amount` and trusts `true`; if the checking account lacks the real balance, the underlying `transferCall` from the checking account will simply fail/revert per the token's own logic (bounded by the token's own accounting) — but if the token behaves asymmetrically (e.g., fee only on the withdraw leg, not on the deposit leg, or vice versa), the checking account balance can drift over time relative to the aggregate "unbacked" claims represented by past successful withdrawals, or beneficiaries can receive less than the leg of the XCM program promised, breaking the "receiver's balance increased by exact amount" invariant asserted throughout the codebase's own tests for other transactors (e.g. `assert_eq!(receiver_assets_after, receiver_assets_before + asset_amount_to_send)` patterns used everywhere else for `FungiblesTransactor`).

### Impact Explanation
This is a direct accounting-integrity break in the XCM executor's holding register for a `TransactAsset` implementation that is wired into `AssetTransactors` on Asset Hub (`cumulus/parachains/runtimes/assets/asset-hub-westend/src/xcm_config.rs`). A user who deploys (or simply targets) a non-standard-but-`IERC20`-compliant contract can cause `AssetsInHolding` to over- or under-represent the real token balance held by `ERC20TransfersCheckingAccount`, which can be leveraged to make downstream `DepositAsset`/`TransferAsset` instructions claim amounts the checking account does not actually hold, or to make users receive less than advertised on deposits — mirroring both scenarios called out in the ACOToken report (insolvency risk on the "mint"/withdraw side, and short-changed recipients on the "burn"/deposit side).

### Likelihood Explanation
Likelihood depends entirely on whether "ERC20 tokens" reachable through this transactor are vetted off-chain/by governance before being trusted in production XCM configs, since matching in code is unrestricted (any `AccountKey20`). I was not able to verify, from the available indexed files, whether Asset Hub runtime config additionally restricts which contract addresses are actually routable to `ERC20Transactor` in practice (e.g., via a governance-controlled asset registry, since `pallet-dap`/`DapBufferAccount` appear nearby in `xcm_config.rs` and may impose additional gating I could not fully inspect). This uncertainty should be resolved before treating this as immediately exploitable in the deployed runtime.

### Recommendation
After each `transferCall`, read back the checking account's (or beneficiary's) `balanceOf` before and after the call and credit/report only the actual observed delta, rather than trusting the boolean return value — mirroring the report's recommendation to sanity-check balance deltas rather than relying on a token's self-reported success.

### Proof of Concept
I could not execute a live reproduction; this requires deploying a custom `pallet-revive` contract that implements `IERC20` but silently transfers less than the requested `value` while still returning `true` (or transfers more on withdraw than deposit), then driving it through a real `WithdrawAsset`/`DepositAsset` XCM program on Asset Hub and asserting `AssetsInHolding`/checking-account balance drift. Given the "FINAL ITERATION" constraint, no test was run; this is reported as an analog based on direct code inspection of the guard actually present (`is_success` check only) versus the guard the report says is missing (balance-delta verification), consistent with the instructions to report Medium/Low findings faithfully rather than inflate or discard them.

/// `Contains<Location>` implementation that matches locations with no parents,
/// a `PalletInstance` and an `AccountKey20` junction.
pub struct IsLocalAccountKey20;
impl Contains<Location> for IsLocalAccountKey20 {
	fn contains(location: &Location) -> bool {
		matches!(location.unpack(), (0, [AccountKey20 { .. }]))
	}
}

/// Fallible converter from a location to a `H160` that matches any location ending with
/// an `AccountKey20` junction.
pub struct AccountKey20ToH160;
impl MaybeEquivalence<Location, H160> for AccountKey20ToH160 {
	fn convert(location: &Location) -> Option<H160> {
		match location.unpack() {
			(0, [AccountKey20 { key, .. }]) => Some((*key).into()),
			_ => None,
		}
	}

	fn convert_back(key: &H160) -> Option<Location> {
		Some(Location::new(0, [AccountKey20 { key: (*key).into(), network: None }]))
	}
}

/// [`xcm_executor::traits::MatchesFungibles`] implementation that matches
/// ERC20 tokens.

	MatchedConvertedConcreteId<H160, u128, IsLocalAccountKey20, AccountKey20ToH160, TryConvertInto>;
