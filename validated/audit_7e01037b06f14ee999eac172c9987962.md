### Title
Permanent freeze of crowdloan reserve deposit via a dust `RcCrowdloanContribution` entry that can never be withdrawn - (File: pallets/ah-ops/src/lib.rs)

### Summary
`Pallet::do_unreserve_crowdloan_reserve` gates the release of a crowdloan's reserve deposit on `contributions_withdrawn`, which requires the `RcCrowdloanContribution` map for `(block, para_id)` to be fully empty. If any single contributor's entry has a `contribution` amount that cannot be transferred out of the pot (e.g. it is below the existential deposit and the contributor's account does not otherwise exist on Asset Hub), `do_withdraw_crowdloan_contribution` will fail every time it is called, the map entry is never removed, and the depositor's reserve can never be unreserved.

### Finding Description
`do_withdraw_crowdloan_contribution` first removes the storage entry with `RcCrowdloanContribution::<T>::take((block, para_id, &depositor))` and only afterwards attempts the actual funds transfer from the pot to the depositor: [1](#0-0) 

If the transfer fails (mapped to `Error::<T>::FailedToWithdrawCrowdloanContribution`), the dispatchable returns `Err`, and FRAME's transactional dispatch wrapper rolls back all storage writes performed during that call — including the earlier `take()`. The entry therefore survives in `RcCrowdloanContribution` unchanged, and any subsequent retry of `withdraw_crowdloan_contribution` for the same `(block, para_id, depositor)` key hits the exact same failure condition, since the transferred `contribution` amount never changes.

`do_unreserve_crowdloan_reserve` checks that all contributions have been withdrawn before releasing the depositor's reserve: [2](#0-1) 

`contributions_withdrawn` simply checks whether `RcCrowdloanContribution::iter_prefix((block, para_id))` is empty. A single stuck entry keeps this permanently non-empty, so `ensure!(Self::contributions_withdrawn(...), Error::<T>::ContributionsRemaining)` will fail forever for that crowdloan, and `RcCrowdloanReserve::take(...)` is never reached — the reserve deposit stays locked indefinitely.

The transfer in `do_withdraw_crowdloan_contribution` uses `Preservation::Expendable` on the sender (`pot`) side, which is intentional (it allows the pot account to be fully drained/reaped on the last withdrawal). The realistic failure mode is on the receiver side: if the contributor's `contribution` amount is a "dust" amount below the existential deposit and the depositor's account does not otherwise exist/hold a balance on Asset Hub, `FungibleMutate::transfer` fails with a below-minimum/dust error, which is caught and mapped to `Error::<T>::FailedToWithdrawCrowdloanContribution`.

Because `RcCrowdloanContribution` entries originate from real, user-initiated crowdloan contributions made on the Relay Chain prior to migration (carried over verbatim by the migration process), an attacker only needs to make an ordinary dust contribution to a crowdloan they do not control the deposit for. Nothing in the withdrawal path can recover or purge such an entry through any permissionless call; the reserve deposit tied to that `(block, para_id)` combination is stuck.

### Impact Explanation
The crowdloan creator's `RcCrowdloanReserve` deposit (normally 500 DOT-class amount) can be permanently frozen by an unrelated, unprivileged contributor who made a dust contribution that fails ED checks on withdrawal. This is a real fund-freeze: no permissionless extrinsic in the pallet can clear the stale `RcCrowdloanContribution` entry or otherwise unblock `unreserve_crowdloan_reserve` for that depositor.

### Likelihood Explanation
This requires only a normal, valid crowdloan contribution of a sufficiently small amount (below Asset Hub's existential deposit) from an account with no other balance on Asset Hub — an easily reachable, low-cost action by any contributor. It is fully repeatable/deterministic: the failure condition (dust amount, no existing receiver account) does not change across retries or block progression, so the freeze is permanent once triggered.

### Recommendation
Do not remove the `RcCrowdloanContribution` entry before confirming the transfer succeeds (i.e., perform the transfer first, or wrap removal and transfer so failure leaves a clearly-flagged, separately recoverable entry), and add a permissionless/governance-safe path to force-resolve dust entries that can never be transferred (e.g., top up the receiving account with ED from the pot before transferring the dust, or explicitly special-case zero/sub-ED contributions in `contributions_withdrawn`/withdrawal logic so they don't block the aggregate check).

### Proof of Concept
Rust unit test in `pallets/ah-ops/src/tests.rs` (or an analogous new test):
1. Set up a pot account with reserved lease deposit and one `RcCrowdloanContribution` entry with a `contribution` amount below the configured existential deposit, for a contributor account that has zero balance on chain.
2. Insert a `RcCrowdloanReserve` entry for a distinct depositor account for the same `(block, para_id)`.
3. Call `Pallet::withdraw_crowdloan_contribution` for the dust contributor; assert it returns `Err(Error::FailedToWithdrawCrowdloanContribution)` and assert `RcCrowdloanContribution::get((block, para_id, &dust_contributor))` is still `Some(..)` (unchanged, proving no permanent removal happened despite the error).
4. Advance blocks arbitrarily and repeat step 3 multiple times, asserting it always fails identically.
5. Call `Pallet::unreserve_crowdloan_reserve` for the depositor; assert it always returns `Err(Error::ContributionsRemaining)` regardless of block number, proving the reserve deposit is permanently frozen.

			block: BlockNumberFor<T>,
			depositor: T::AccountId,
			para_id: ParaId,
		) -> Result<(), Error<T>> {
			ensure!(block <= T::RcBlockNumberProvider::current_block_number(), Error::<T>::NotYet);
			let (pot, contribution) =
				RcCrowdloanContribution::<T>::take((block, para_id, &depositor))
					.ok_or(Error::<T>::NoCrowdloanContribution)?;

			// Maybe this is the first one to withdraw and we need to unreserve it from the pot
			match Self::do_unreserve_lease_deposit(block, pot.clone(), para_id) {
				Ok(()) => (),
				Err(Error::<T>::NoLeaseReserve) => (), // fine
				Err(e) => return Err(e),
			}

			// Ideally this does not fail. But if it does, then we keep it for manual inspection.
			let transferred = <<T as Config>::Currency as FungibleMutate<_>>::transfer(
				&pot,
				&depositor,
				contribution,
				Preservation::Expendable,
			)
			.defensive()
			.map_err(|_| Error::<T>::FailedToWithdrawCrowdloanContribution)?;
			defensive_assert!(transferred == contribution);

			<<T as Config>::Currency as Currency<_>>::reactivate(transferred);

			Ok(())
		}

		pub fn do_unreserve_crowdloan_reserve(
			block: BlockNumberFor<T>,
			depositor: T::AccountId,
			para_id: ParaId,
		) -> Result<(), Error<T>> {
			ensure!(block <= T::RcBlockNumberProvider::current_block_number(), Error::<T>::NotYet);
			ensure!(
				Self::contributions_withdrawn(block, para_id),
				Error::<T>::ContributionsRemaining
			);
			let amount = RcCrowdloanReserve::<T>::take((block, para_id, &depositor))
				.ok_or(Error::<T>::NoCrowdloanReserve)?;

			let remaining = <T as Config>::Currency::unreserve(&depositor, amount);
			if remaining > 0 {
				defensive!("Should be able to unreserve all");
				Self::deposit_event(Event::CrowdloanUnreserveRemaining {
					depositor,
					remaining,
					para_id,
				});
			}

			Ok(())
		}

		fn contributions_withdrawn(block: BlockNumberFor<T>, para_id: ParaId) -> bool {
			let mut contrib_iter = RcCrowdloanContribution::<T>::iter_prefix((block, para_id));
			contrib_iter.next().is_none()
		}
