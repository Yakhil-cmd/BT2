### Title
Cross-organization webhook forgery due to mismatched authentication/authorization bindings in `WebhooksController#verify_signature` and `Webhooks::Handlers::Handler#repository_name` - (File: app/controllers/shipit/webhooks_controller.rb, app/models/shipit/webhooks/handlers/handler.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/`webhook_secret` to validate a webhook signature against based on an attacker-controlled field extracted from the payload (`repository.owner.login` or `organization.login`), but the downstream event handlers act on a completely different, independently-controlled field (`repository.full_name`) to locate the target `Stack`/`Repository`/`Commit`. Because the HMAC signature only proves knowledge of *some* org's `webhook_secret`, not that the payload's target repository belongs to that org, an attacker who legitimately controls one GitHub organization configured on a multi-org Shipit instance can forge webhook events (push, status, check_suite) that are cryptographically "valid" for their own org but semantically target a victim org's stack.

### Finding Description
Shipit supports configuring multiple GitHub organizations, each with its own `webhook_secret`: [1](#0-0) 

`WebhooksController#verify_signature` picks the `github_app` (and thus the `webhook_secret` used for HMAC verification) using a payload field the attacker fully controls: [2](#0-1) 

`GitHubApp#verify_webhook_signature` only checks that the raw body was signed with *the secret belonging to the organization named in the payload itself* — it does not tie the signature to any specific repository: [3](#0-2) 

Once the signature check passes, `WebhooksController#create` dispatches the parsed body to event handlers unmodified: [4](#0-3) 

Every handler resolves its target `Stack`/`Repository` via `Handler#repository_name`, which reads a *different* JSON field (`repository.full_name`) than the one used for signature-org-selection (`repository.owner.login` / `organization.login`): [5](#0-4) 

Nothing enforces that `repository.owner.login` (used to pick the verifying secret) is consistent with `repository.full_name` (used to pick the acted-upon repository). This is the broken binding: `organization authenticated == repository written`. An attacker who is a legitimate admin of "attacker-org" (a real org installed on the shared Shipit instance) knows a real `webhook_secret` for that org. They can craft a JSON body such as:
```json
{
  "organization": {"login": "attacker-org"},
  "repository": {"owner": {"login": "attacker-org"}, "full_name": "victim-org/victim-repo"},
  "sha": "<victim commit sha>",
  "state": "success"
}
```
Sign it with `attacker-org`'s real `webhook_secret`, and POST to `/webhooks`. `verify_signature` resolves `repository_owner` to `"attacker-org"`, fetches `Shipit.github(organization: "attacker-org")`, and the signature check succeeds because it was genuinely signed with that org's secret. `StatusHandler` (or `PushHandler`/`CheckSuiteHandler`) then acts on `repository.full_name = "victim-org/victim-repo"`: [6](#0-5) [7](#0-6) 

### Impact Explanation
This lets an attacker who controls only one org on a shared/multi-org Shipit deployment inject forged GitHub events (fake commit statuses, forced sync triggers, forced check-run refresh requests) against a completely different, victim organization's repositories/stacks that they have no legitimate access to. Forged `status` events in particular write a `Status` record on the victim's `Commit` via `Commit#create_status_from_github!`, which can be used to spoof passing CI/required-status checks that gate deploy eligibility, escalating to an unauthorized deploy — matching the Critical impact bar ("an unauthorized deploy"). This is a genuine cross-repository/cross-tenant write, crossing the "organization authenticated vs. repository written" trust boundary described in the rules, and requires no privileged Shipit account, API token, or access to the victim's secrets — only legitimate control of one org configured on the shared instance.

### Likelihood Explanation
Exploitability requires the Shipit instance to be configured with more than one GitHub organization (a documented, supported configuration per `docs/setup.md` and `config/secrets.development.shopify.yml`), and the attacker must be an admin/owner of one of those organizations (able to obtain or set that org's `webhook_secret`) while not being authorized on the victim org. In shared/hosted Shipit deployments serving multiple independent teams/orgs, this is a realistic scenario, since Shipit's webhook secret model is inherently per-organization while its authorization model for acting on payload data is per-repository-field with no cross-check.

### Recommendation
Bind the two fields together: after signature verification, require that the organization actually authenticated (used to select the `webhook_secret`) matches the owner segment of `repository.full_name` that the handler will act upon, e.g. verify `payload.dig('repository', 'owner', 'login') == payload.dig('repository', 'full_name')&.split('/')&.first` before dispatch, or have handlers derive the repository strictly from the already-verified `repository_owner`/org context rather than trusting an independent `full_name` field from the same untrusted JSON body.

### Proof of Concept
1. Configure Shipit with two orgs, `attacker-org` (secret `S_A`) and `victim-org` (secret `S_V`), as supported by `config/secrets.development.shopify.yml`.
2. As an admin of `attacker-org`, obtain `S_A` (a legitimate webhook secret you own).
3. Build payload:
```json
{"organization":{"login":"attacker-org"},"repository":{"owner":{"login":"attacker-org"},"full_name":"victim-org/victim-repo"},"sha":"<victim_commit_sha>","state":"success","context":"ci/required-check"}
```
4. Compute `X-Hub-Signature: sha1=HMAC_SHA1(S_A, raw_body)` per `GitHubApp#verify_webhook_signature` (lib/shipit/github_app.rb:76-83).
5. `POST /webhooks` with header `X-Github-Event: status` and the signed body.
6. `WebhooksController#verify_signature` resolves `repository_owner` to `attacker-org`, loads `Shipit.github(organization: 'attacker-org')`, and validates successfully using `S_A`.
7. `StatusHandler.process` runs against `Commit.where(sha: params.sha)` resolved through `victim-org/victim-repo`, creating a forged success status on the victim's commit despite the attacker never having credentials for `victim-org`.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping

    end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
    end
  end
end
