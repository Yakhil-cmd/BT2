### Title
Atomic dual-token `collect_creator_fee`/`collect_creator_fee_permissionless` transfer permanently freezes both tokens' creator fees if the creator's fixed-destination ATA for either token becomes untransferable - ([File: programs/cp-swap/src/instructions/collect_creator_fee.rs], [File: programs/cp-swap/src/instructions/collect_creator_fee_permissionless.rs])

### Summary
`collect_creator_fee` and `collect_creator_fee_permissionless` transfer accrued `creator_fees_token_0` and `creator_fees_token_1` atomically to two ATAs whose owner is fixed to `pool_state.pool_creator`. There is no way to redirect either transfer to an alternate destination. If either underlying token/mint makes the creator's ATA untransferable (e.g. Token-2022 mint with a transfer hook / default frozen state extension, or an SPL-style deny-list wrapper mint), the whole instruction reverts, and since the fee counters are zeroed only after both transfers succeed, both token_0 and token_1 creator fees remain stuck in the vaults indefinitely, with no recovery path.

### Finding Description
`collect_creator_fee` performs two sequential CPI transfers via `transfer_from_pool_vault_to_user`, one for each token, before zeroing `pool_state.creator_fees_token_0` and `creator_fees_token_1`: [3](#0-2) 

The destination accounts `creator_token_0`/`creator_token_1` are Anchor-derived ATAs whose authority is hard-coded to `creator` (which itself is constrained to `pool_state.pool_creator`): [4](#0-3) 

The same pattern exists in the permissionless variant, where the ATA authority is fixed to the immutable `pool_creator` field read from pool state: [5](#0-4) [6](#0-5) 

Neither instruction exposes a parameter to choose an alternate recipient — unlike `collect_protocol_fee`/`collect_fund_fee`, whose `recipient_token_*_account`s are freely-supplied accounts controlled by the admin caller: [7](#0-6) 

`pool_creator` is permanently fixed at pool creation time to whichever address calls `initialize`/`initialize_with_permission`, and cannot be changed afterward: [2](#0-1) [1](#0-0) 

Because the program accepts arbitrary token mints for `token_0_mint`/`token_1_mint` (via `mint::token_program = token_0_program`/`token_1_program`, allowing either legacy SPL Token or Token-2022) and Token-2022 mints can carry transfer hooks, permanent-delegate, or default-account-state extensions, the transfer CPI for one leg can be made to revert unconditionally against the creator's ATA (e.g., the hook program denies transfers to that specific owner, or a default-frozen account state extension freezes newly created creator ATAs). Since `swap_base_input`/`swap_base_output` continuously accrue `creator_fees_token_0`/`creator_fees_token_1` on every swap when `enable_creator_fee` is set, these balances keep growing inside the pool vaults with no way to ever extract them once one leg is permanently blocked — the same "all-or-nothing forced-recipient" pattern as the referenced Maia `redeemDeposit` bug, but here it is the pool creator's earned fees (funds that rightfully belong to the pool creator, sitting in the shared vault) that become permanently locked, and the locking of one token's fee additionally blocks the unrelated token's fee from ever being collected.

### Impact Explanation
This causes permanent freezing of the pool creator's accrued fee funds for **both** token_0 and token_1, not just the one that becomes untransferable, because the instruction transfers both legs atomically and only clears the accounting after success. Since fee accrual is continuous (every swap adds to `creator_fees_token_0`/`creator_fees_token_1`), the frozen amount grows unbounded over the pool's lifetime with no admin override or alternate-recipient mechanism to recover it. This meets the "permanent freezing of user funds" bar.

### Likelihood Explanation
The program explicitly supports Token-2022 mints (`token_0_program`/`token_1_program` as `TokenInterface`) throughout `initialize`, `initialize_with_permission`, `collect_creator_fee`, and `collect_creator_fee_permissionless`, and Token-2022 transfer hooks / default account states are a standard, commonly-used extension in production token deployments today. A pool creator using (or being targeted through) such a mint, or any token with issuer-side denylist/freeze capability on one of the two pool assets, will trigger this permanently — no attacker action beyond normal pool usage over time is required, only the mint's built-in feature being exercised against the creator's fixed ATA.

### Recommendation
Decouple the two token transfers so a failure on one leg does not block the other and does not prevent the fee accounting from being appropriately updated. Alternatively, allow the creator (or a permissioned override) to specify an arbitrary destination token account (as already done for `collect_protocol_fee`/`collect_fund_fee`), or independently collect/track token_0 and token_1 creator fees in two separate instructions/counters so one CPI failure does not lock the other token's fees.

### Proof of Concept
1. `initialize` (or `initialize_with_permission`) a pool where `token_1_mint` is a Token-2022 mint that either (a) has a transfer-hook program that reverts any transfer whose destination owner equals a chosen "creator" pubkey, or (b) uses the default-account-state extension so newly created ATAs start frozen.
2. Perform swaps via `swap_base_input`/`swap_base_output` so `creator_fees_token_0` and `creator_fees_token_1` both accrue in `pool_state`. [8](#0-7) 
3. Call `collect_creator_fee` (or `collect_creator_fee_permissionless`). The transfer to `creator_token_0` succeeds, but the transfer to `creator_token_1` reverts due to the hook/frozen state, causing the whole instruction, including the already-succeeded token_0 transfer's on-chain effects being rolled back (Solana transaction atomicity), to fail. `pool_state.creator_fees_token_0`/`creator_fees_token_1` are never zeroed since that only happens after both transfers succeed.
4. Every subsequent call to `collect_creator_fee`/`collect_creator_fee_permissionless` fails identically; both `creator_fees_token_0` and `creator_fees_token_1` remain stuck in `token_0_vault`/`token_1_vault` permanently, growing with every future swap, with no instruction available to redirect or force-extract them.

```rust
pub fn collect_creator_fee(ctx: Context<CollectCreatorFee>) -> Result<()> {
    let mut pool_state = ctx.accounts.pool_state.load_mut()?;
    let creator_fees_token_0 = pool_state.creator_fees_token_0;
    let creator_fees_token_1 = pool_state.creator_fees_token_1;
    if creator_fees_token_0 == 0 && creator_fees_token_1 == 0 {
        return err!(ErrorCode::NoFeeCollect);
    }

    let signer_seeds: &[&[u8]] = &[crate::AUTH_SEED.as_bytes(), &[ctx.bumps.authority]];

    transfer_from_pool_vault_to_user(
        ctx.accounts.authority.to_account_info(),
        ctx.accounts.token_0_vault.to_account_info(),
        ctx.accounts.creator_token_0.to_account_info(),
        ctx.accounts.vault_0_mint.to_account_info(),
        ctx.accounts.token_0_program.to_account_info(),
        creator_fees_token_0,
        ctx.accounts.vault_0_mint.decimals,
        &[signer_seeds],
    )?;

    transfer_from_pool_vault_to_user(
        ctx.accounts.authority.to_account_info(),
        ctx.accounts.token_1_vault.to_account_info(),
        ctx.accounts.creator_token_1.to_account_info(),
        ctx.accounts.vault_1_mint.to_account_info(),
        ctx.accounts.token_1_program.to_account_info(),
        creator_fees_token_1,
        ctx.accounts.vault_1_mint.decimals,
        &[signer_seeds],
    )?;

    pool_state.creator_fees_token_0 = 0;
    pool_state.creator_fees_token_1 = 0;
```

```rust
    pub fn swap_base_input(
        input_amount: u128,
        input_vault_amount: u128,
        output_vault_amount: u128,
        trade_fee_rate: u64,
        creator_fee_rate: u64,
        protocol_fee_rate: u64,
        fund_fee_rate: u64,
        is_creator_fee_on_input: bool,
    ) -> Option<SwapResult> {
        let mut creator_fee = 0;
        let trade_fee: u128;

        let input_amount_less_fees = if is_creator_fee_on_input {
            let total_fee = Fees::trading_fee(input_amount, trade_fee_rate + creator_fee_rate)?;
            creator_fee = Fees::split_creator_fee(total_fee, trade_fee_rate, creator_fee_rate)?;
            trade_fee = total_fee - creator_fee;
            input_amount.checked_sub(total_fee)?
        } else {
            trade_fee = Fees::trading_fee(input_amount, trade_fee_rate)?;
            input_amount.checked_sub(trade_fee)?
        };
        let protocol_fee = Fees::protocol_fee(trade_fee, protocol_fee_rate)?;
        let fund_fee = Fees::fund_fee(trade_fee, fund_fee_rate)?;

        let output_amount_swapped = ConstantProductCurve::swap_base_input_without_fees(
            input_amount_less_fees,
            input_vault_amount,
            output_vault_amount,
        );

        let output_amount = if is_creator_fee_on_input {
            output_amount_swapped
        } else {
            creator_fee = Fees::creator_fee(output_amount_swapped, creator_fee_rate)?;
            output_amount_swapped.checked_sub(creator_fee)?
        };
```
