### Title
Direct-payment balance manipulation ("donation attack") on AA `balance[asset]` allows griefing/fund-mispricing of AAs that price shares from live balance - ([File: formula/evaluation.js])

### Summary
Analogous to the Blueberry `IchiVaultSpell` bug (whale inflates `vaultToken.balanceOf(spell)` by direct transfer, breaking the max-position check for all strategies sharing the vault), an Obyte AA that prices deposits/shares using the `balance[asset]` oscript operator reads the AA's *live, on-chain* balance rather than an internally tracked accounting variable. Any address can increase that live balance by sending a payment to the AA that does not need to satisfy any specific "if" case, because incoming coins are credited to `aa_balances` for every unit received, independent of whether a `case` matched. This lets a third party manipulate the balance that legitimate users' triggers use for ratio/share/price computations, causing either a griefing bounce (DoS) for legitimate depositors or a mispriced deposit/withdrawal (fund loss for later depositors), the exact bug class described in the report ("a whale can grief strategies that use the same vault/pool by inflating the balance the contract relies on").

### Finding Description
The `balance[asset]` (and `balance[address][asset]`) oscript operator is evaluated in `formula/evaluation.js`'s `readBalance()` helper: [1](#0-0) 

It directly reads the `aa_balances` table for the address, which is the AA's *actual* cumulative on-chain balance, updated by `updateFinalAABalances()`/`updateInitialAABalances()` in `aa_composer.js` for **every** payment unit that credits the AA address, regardless of whether the accompanying trigger matched any specific business-logic `case`: [2](#0-1) 

Multiple official example AAs shipped with ocore (used as reference patterns for AA authors) rely on this raw `balance[...]` value to compute investment/exchange ratios and share issuance, e.g. the bundled "Uniswap-like market maker" sample: [3](#0-2) [4](#0-3) 

Here `$asset_balance = balance[$asset] - trigger.output[[asset=$asset]]` and `$bytes_balance = balance[base] - trigger.output[[asset=base]]` are used as the "previous pool balance" to compute the expected deposit ratio (`$current_ratio`) or swap price (`$p = $asset_balance * $bytes_balance`). Because `balance[...]` reflects the AA's total live balance and not a value the AA itself maintains and validates through its own case logic, any party can inflate (or, via a self-triggered withdrawal path, manipulate) that balance ahead of a victim's transaction:
- By sending a payment that does not match any of the AA's specific `if` conditions (e.g., an amount below the `1e5` threshold, or additional funds attached to an otherwise-matching trigger of a different case), the extra coins are still credited into `aa_balances` (per `updateFinalAABalances`) even though no state-var accounting entry is created for them.
- The very next legitimate investor's trigger computes `$expected_asset_amount` or `$new_asset_balance`/`$new_bytes_balance` from this polluted `balance[...]`, producing a mismatch that triggers `bounce('wrong ratio of amounts...')` (griefing/DoS) or, in the exchange cases, a skewed price that benefits the attacker at the expense of the counterparty (fund mispricing), mirroring the Solidity `balanceOf()`-donation attack class.

This is architecturally identical to the reported bug: `balanceOf(spell)`/`totalVaultToken` in the Solidity contract is replaced here by `balance[asset]`/`balance[base]` in oscript, and both are "trust the live balance of the contract" patterns that any unrelated payer can pollute.

### Impact Explanation
- Griefing/DoS: legitimate depositors' `invest`/`exchange` triggers can be forced to `bounce`, since the ratio check compares against a manipulated `balance[...]`, denying service to all users of an AA/pool that uses this pattern — analogous to the "EXCEED_MAX_POS" DoS in the original report.
- Fund mispricing: for pool/AMM-style AAs (as in the sample) an attacker who pollutes the balance immediately before a victim's swap/invest can skew `$p`, `$new_asset_balance`, or `$issue_amount`, extracting value from or diluting the victim — an AA fund-loss vector for the counterparty.
- Because this affects any AA built on the officially recommended `balance[asset]` pattern, the blast radius is every deployed AA copying this idiom (pools/market-makers/vaults sharing this accounting style), not a single contract instance.

### Likelihood Explanation
High reachability: any address can send a plain payment to a public AA address; no privileged role, hub cooperation, or node compromise is required. The only constraint is crafting a payment whose trigger doesn't match the AA's specific business `case` (e.g., an amount just under the AA's own threshold, or arriving in the same unit as an unrelated trigger data field), which is straightforward and fully within an ordinary user's/whale's capability — exactly the "single posted unit" trigger vector explicitly in scope.

### Recommendation
- AAs should never use the raw `balance[asset]`/`balance[base]` operator as the sole source of truth for pricing/ratio/share computations. Instead, maintain and validate every credited deposit through an internally tracked state variable (e.g., `var['pool_asset_balance']`, `var['pool_bytes_balance']`) that is only updated inside the AA's own case logic, mirroring the "Recommendation" in the original report ("instead of using balanceOf, record the balance within the contract").
- Documentation/samples distributed with ocore (e.g. `test/samples/uniswap_like_market_maker.oscript`) should be updated to track internal balances rather than reading live `balance[...]`, since these samples are used as reference implementations by AA authors and currently propagate this unsafe pattern.
- Consider adding a catch-all case (as some other samples already do, e.g. `test/samples/a_bank_without_percent.oscript`, `test/samples/sell_asset_for_bytes.oscript`) that explicitly records any non-matching incoming payment into tracked state so `balance[...]` and the tracked accounting never diverge, or bounces unmatched payments so they can't remain to pollute the balance used elsewhere.

### Proof of Concept
1. Deploy an AA using the "invest"/"exchange" pattern from `test/samples/uniswap_like_market_maker.oscript` (lines 33-48, 102-122), which computes `$asset_balance = balance[$asset] - trigger.output[[asset=$asset]]` and `$bytes_balance = balance[base] - trigger.output[[asset=base]]`.
2. Attacker sends a payment of the pool's non-base asset to the AA address with an amount/trigger data that satisfies neither the `invest` (`trigger.output[[asset=base]] > 1e5 AND trigger.output[[asset=$asset]] > 0`) nor `exchange` cases exactly — e.g. attach it together with a `trigger.data.define` no-op case, or send it in a unit whose base-asset output is below `1e5` so only the asset-only transfer lands with no matching case, causing it to bounce with only the bounce fee retained but, for assets not listed in `bounce_fees`, the deposited asset remains credited to `aa_balances` per `updateFinalAABalances` (`aa_composer.js` lines 543-586) since bounce-fee retention is evaluated per-asset only if `bounce_fees[asset]` is configured (`aa_composer.js` line ~1856).
3. Victim then sends a legitimate `invest` trigger. Because `balance[$asset]` now includes the attacker's unaccounted deposit, `$current_ratio` and thus `$expected_asset_amount` no longer match the victim's intended contribution, causing `bounce('wrong ratio of amounts, expected ...')` — denial of service — or, in the swap cases, a skewed `$amount` that misprices the trade in the attacker's favor.
