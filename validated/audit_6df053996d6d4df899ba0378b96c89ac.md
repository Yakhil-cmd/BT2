### Title
Team membership webhook resolves teams by global `github_id` with no organization binding, enabling cross-organization team-membership escalation - ([File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`MembershipHandler#find_or_create_team!` resolves the target `Team` solely via `Team.find_or_create_by!(github_id: params.team.id)`, ignoring the `organization` field for existing records, while webhook authentication (`verify_signature`) is performed per-organization using that organization's own (optional) `webhook_secret`. Because the team lookup key is not scoped to the authenticating organization, a webhook accepted under one organization's identity can mutate a `Team` record that actually belongs to a different organization, as long as the attacker knows that team's numeric `github_id`.

### Finding Description
The binding that should hold is: `authenticated_organization(payload) == team.organization` for any `Team` row mutated by a `membership` webhook. In `find_or_create_team!` (`app/models/shipit/webhooks/handlers/membership_handler.rb:38-43`), the lookup is:

```ruby
Team.find_or_create_by!(github_id: params.team.id) do |team|
  team.github_team = params.team
  team.organization = params.organization.login
end
```

The block only runs on *creation*; if a `Team` row with that `github_id` already exists (e.g. created earlier through a legitimate webhook for org B), it is returned unmodified regardless of what `params.organization.login` says. The `teams` table has no unique/foreign constraint tying `github_id` to `organization` [1](#0-0) , and the `Team` model itself performs no cross-check between the two [2](#0-1) .

Authentication happens one layer up, in `WebhooksController#verify_signature`, which resolves the signing app **per organization name found in the payload** and skips verification entirely when that organization has no `webhook_secret` configured:

```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
``` [3](#0-2) [4](#0-3) 

So the guard only proves "this payload's `organization.login` was validated (or that org has no secret configured)" — it never proves anything about the `team.id`/`team.organization` pair embedded further inside the same payload. `ExplicitParameters` only enforces types (`requires :id, Integer`), not any relationship between `team.id` and `organization.login` [5](#0-4) .

Exploit flow: in a multi-organization Shipit deployment (`secrets.github` keyed by org, per `Shipit.github_app_config`) [6](#0-5) , if any configured organization A has no `webhook_secret` set, an attacker can POST a forged `membership` webhook with `X-Github-Event: membership`, `organization.login: "A"` (any signature accepted, since `verify_webhook_signature` short-circuits `true`), but `team.id` set to the numeric `github_id` of an existing `Team` that actually belongs to a different, properly-secured organization B (e.g. one of `Shipit.github_teams`). `find_or_create_team!` finds team B's row by `github_id` alone, `add_member` is called, and the attacker's chosen `User` is inserted into `team.members` for organization B's team — with zero Octokit calls and zero verification tied to organization B.

### Impact Explanation
This allows an unprivileged attacker to insert an arbitrary GitHub login into the membership of any `Shipit::Team` already known to Shipit (including teams listed in `Shipit.github_teams`, which gate OAuth authorization) [7](#0-6) , provided they can authenticate as *some* other, weaker organization in the same multi-tenant Shipit instance. Because `Shipit.github_teams` is used to restrict application access, this is an escalation into `Shipit.github_teams` authorization, matching the High severity bucket in the rules. It is repeatable against any team whose numeric `github_id` the attacker learns, and blast radius spans all organizations sharing one Shipit deployment (a payload authenticated for org A mutating org B's team).

### Likelihood Explanation
The exploit requires two preconditions I could not fully verify from the indexed code:
1. A multi-organization Shipit deployment where at least one configured GitHub organization has no `webhook_secret` set (this is possible per the config schema in `lib/shipit/github_app.rb`, but I found no evidence in `docs/setup.md` on whether operators are told this field is mandatory — I could not retrieve that file's content before running out of iterations).
2. The attacker must discover the victim team's numeric `github_id`. I found no route/serializer in this engine that exposes `Team#github_id` (only `User#github_id` appears in serializers) [8](#0-7) , so the specific claim that "/repositories or /stacks pages leak team handles" giving the numeric `github_id` is not substantiated by this engine's own code — team *handles* (org/slug) are distinct from the numeric `github_id`, and I found no in-engine leak of the latter.

Given point 2 is unconfirmed, likelihood is lower than "Critical/trivial," but the underlying code defect (missing organization scoping on `Team.find_or_create_by!`) is real and independent of how the `github_id` is obtained (it could be learned via GitHub's own API for the target org's teams, sequential/small integer guessing, or leaked logs).

### Recommendation
Scope the team lookup by both `github_id` and `organization`, and reject (or explicitly reconcile) any webhook where an existing team's stored `organization` does not match `params.organization.login`, e.g.:
```ruby
def find_or_create_team!
  team = Team.find_by(github_id: params.team.id)
  raise ArgumentError, "organization mismatch" if team && team.organization != params.organization.login

  Team.find_or_create_by!(github_id: params.team.id, organization: params.organization.login) do |t|
    t.github_team = params.team
  end
end
```
Additionally, make `webhook_secret` mandatory for every configured organization (fail startup/config validation if absent) so `verify_webhook_signature` never silently returns `true`.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
