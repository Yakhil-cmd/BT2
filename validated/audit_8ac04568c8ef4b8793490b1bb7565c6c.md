### Title
`OpenedHandler#provision?` operator-precedence bug bypasses `review_stacks_enabled` gate for the `prevent_with_label` provisioning behavior - (File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb)

### Summary
`OpenedHandler#provision?` combines `repository.review_stacks_enabled` with the three provisioning-behavior branches using `&&`/`||` without parentheses grouping the enable flag across all branches. Because Ruby's `&&` binds tighter than `||`, `review_stacks_enabled` only gates the `allow_all?` branch; the `allow_with_label?` and `prevent_with_label?` branches are evaluated independently of it, so a repository with review stacks disabled but `provisioning_behavior = 'prevent_with_label'` will still auto-provision a `ReviewStack` for any unlabeled PR.

### Finding Description
The intended binding is: `provision? == true` **iff** `repository.review_stacks_enabled == true` AND one of the three behavior conditions holds. The actual code at [2](#0-1)  is:

```ruby
def provision?
  repository.review_stacks_enabled &&
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
```

Due to operator precedence this parses as:
`(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label) || (prevent_with_label? && !has_label)`

so `review_stacks_enabled` is scoped only to the first disjunct. With `provisioning_behavior == 'prevent_with_label'` and `review_stacks_enabled == false`, the third disjunct `(prevent_with_label? && !has_label)` evaluates to `true` whenever the PR has no provisioning label — completely independent of the enable flag.

Exploit flow: attacker opens a PR (`action: "opened"`) against a target repository configured with `provisioning_behavior = 'prevent_with_label'` and `review_stacks_enabled = false`, without adding the provisioning label. `respond_to_pull_request_opened?` at [3](#0-2)  calls `provision?`, which returns `true`; `process` then calls `Shipit::Webhooks::Handlers::PullRequest::ReviewStackAdapter.new(params, scope: repository.review_stacks).find_or_create!` at [4](#0-3) , which creates a `ReviewStack` from `stack_attributes` (using the attacker-controlled `params.pull_request.head.ref` as `branch`) and enqueues it via `Shipit::ReviewStackProvisioningQueue.add(stack)` at [5](#0-4) , triggering provisioning of a stack pointed at the attacker's fork/branch for a repository that never opted into review stacks.

`review_stacks_enabled` and `provisioning_behavior` are independently settable via `RepositoriesController#update_params` ( [1](#0-0) ), so this configuration combination is directly reachable through the settings UI, not merely theoretical. No signature verification, authentication check, or model validation constrains this logic — the divergence is purely in `provision?`'s boolean expression.

### Impact Explanation
For any repository where an operator has enabled `prevent_with_label` provisioning behavior but has not (yet) enabled review stacks, an unprivileged attacker who can open a pull request against that repository can force creation and provisioning of a `ReviewStack` bound to their own fork/branch, bypassing the `review_stacks_enabled` opt-in gate entirely. This is repeatable per-PR and across any repository sharing this configuration state, matching the "unauthorized deploy/provisioning" and "record written for a repository that did not authenticate it" Critical impact category.

### Likelihood Explanation
Requires only: `repository.provisioning_behavior == 'prevent_with_label'` and `repository.review_stacks_enabled == false` — a legitimate, reachable configuration state via the repository settings form — plus the attacker opening a PR without a label (the default, no-action case). No secrets, tokens, or elevated privileges are needed; the attacker only needs GitHub PR-opening ability against the target repo (or its fork-PR flow) and the webhook delivering normally to the Shipit host.

### Recommendation
Parenthesize `review_stacks_enabled` across all three disjuncts, e.g.:

```ruby
def provision?
  repository.review_stacks_enabled &&
    (repository.provisioning_behavior_allow_all? ||
     (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
     (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?))
end
```

### Proof of Concept
In `test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb`, add a test:
1. Build a `repository` fixture/record with `review_stacks_enabled: false` and `provisioning_behavior: 'prevent_with_label'`.
2. Construct webhook params for `action: "opened"` with `pull_request.labels` empty (no provisioning label).
3. Assert `repository.review_stacks_enabled == false` (left side of binding) before invoking the handler.
4. Invoke `Shipit::Webhooks::Handlers::PullRequest::OpenedHandler.new(params).process` (or equivalent handler entry point).
5. Assert `repository.review_stacks.count == 0` — i.e., assert the right side (whether a `ReviewStack` was actually created) equals the left side (`review_stacks_enabled`). The test currently fails because a `ReviewStack` is created despite `review_stacks_enabled == false`, demonstrating the divergence.
