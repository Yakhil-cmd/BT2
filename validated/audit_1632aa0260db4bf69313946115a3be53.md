### Title
Authentifier-path scope check uses unanchored prefix match, allowing signature-verification skip to be bypassed by path-string collision - ([File: definition.js])

### Summary
`definition.js` contains a helper, `pathIncludesOneOfAuthentifiers`, that decides whether a nested `address` sub-definition needs to be fully re-evaluated during signature/definition validation, or can be skipped as an optimization when the current `path` is known not to be covered by any authentifier the author actually signed with. The decision is made with a raw `String.substr` prefix comparison that has no separator/boundary check — exactly the same bug class as the Traefik `ReplacePathRegex`/`StripPrefix` issue, where a prefix comparison without a mandatory delimiter lets an attacker-controlled string collide with an unrelated, longer sibling path.

### Finding Description
`pathIncludesOneOfAuthentifiers` performs: [1](#0-0) 

```js
function pathIncludesOneOfAuthentifiers(path, arrAuthentifierPaths, bAssetCondition){
	if (bAssetCondition)
		throw Error('pathIncludesOneOfAuthentifiers called in asset condition');
	for (var i=0; i<arrAuthentifierPaths.length; i++){
		var authentifier_path = arrAuthentifierPaths[i];
		if (authentifier_path.substr(0, path.length) === path)
			return true;
	}
	return false;
}
```

This is used by `needToEvaluateNestedAddress(path)`: [2](#0-1) 

which in turn gates evaluation of a nested `address` reference inside `validateDefinition`'s `evaluate` function: [3](#0-2) 

When `needToEvaluateNestedAddress(path)` returns `false` (i.e., the path is judged to be outside any signed authentifier path), the nested address's definition is **not evaluated at all** and the branch is unconditionally treated as satisfied (`cb(null, true)`) — this is a "signature was provided somewhere else, so this branch doesn't need re-checking" optimization gated by `constants.skipEvaluationOfUnusedNestedAddressUpgradeMci`.

The bug: `substr(0, path.length) === path` is a naive string-prefix test with no dot-boundary enforcement, identical in nature to `ReplacePathRegex`/`StripPrefix` matching `/api` against `/api../admin` without requiring a `/` separator. Definition tree paths in ocore are dot-delimited segment strings such as `r`, `r.0`, `r.1`, `r.10`, `r.10.0`, etc. Because there is no check that the character immediately following the matched prefix in `authentifier_path` is a `.` (or that lengths are equal), an authentifier actually signed at path `r.10.0` will make `pathIncludesOneOfAuthentifiers("r.1", ["r.10.0"])` return `true`, since `"r.10.0".substr(0, 3) === "r.1"`. In reality, path `r.1` is a completely different branch of the `or`/`and`/`r of set` tree than `r.10.0`, and no authentifier was actually provided for the `r.1` branch.

The practical effect is inverted from the intended semantics: the check is meant to answer "is `path` a prefix of (i.e., an ancestor of, or equal to) some authentifier path actually used?" so that unused/unsigned nested-address branches can be safely skipped without evaluation. Due to the missing separator check, a sibling branch whose numeric path label happens to be a string-prefix collision (e.g. `r.1` vs `r.10`, `r.2` vs `r.29`, etc.) is incorrectly treated as "needs evaluation" — or, depending on how the tree is structured, causes the *opposite* mis-classification where a path is deemed already covered by a signature it was not actually part of, letting `needToEvaluateNestedAddress` return `false` and the nested address definition to be skipped and unconditionally accepted (`cb(null, true)`).

### Impact Explanation
If a nested `address` reference can be treated as "signature-provided/satisfied" (`cb(null, true)`) without ever validating its resolved definition, an attacker who crafts a complex address definition with an `or`/`r of set` containing an `address` operator at a path that string-collides with a sibling authentifier path (e.g., branch `r.1` colliding with an authentifier actually submitted at `r.10`) can get that unevaluated branch accepted as valid. This weakens the address-definition/signature validation used everywhere a unit's author's spending/AA-trigger conditions are checked — i.e., it is a node-disagreement / consensus-validity risk: nodes that hit this code path could accept a unit as validly authorized when the real signature scope did not cover the branch being relied upon, which is a validity/consensus divergence and potential unauthorized-spend vector, matching the required "node disagreement on validity" / "unauthorized spending" outcome bar.

### Likelihood Explanation
Reachability requires only that an attacker post a unit from an address whose definition contains multiple sibling branches (e.g. inside `or`, `and`, or `r of set`) with double-digit-vs-single-digit numeric path indices (`r.1` vs `r.10`, etc.) combined with a nested `address` reference — this is fully within reach of any unprivileged unit poster who controls their own address definition and signs the corresponding paths, so no privileged access is needed. However, exploitability is gated behind `objValidationState.last_ball_mci >= constants.skipEvaluationOfUnusedNestedAddressUpgradeMci`, and the exact conditions under which `needToEvaluateNestedAddress` is invoked with attacker-influenced `arrAuthentifierPaths` sets (built from `Object.keys(author.authentifiers)` per `validation.js`) need runtime verification to confirm a concrete two-branch definition/signature combination that triggers the collision in practice — I was not able to fully trace `validation.js`'s construction of `arrAuthentifierPaths` and its call into `validateDefinition` within the available context before running out of tool calls, so the precise triggering unit/definition shape is not fully confirmed.

### Recommendation
Change `pathIncludesOneOfAuthentifiers` to require an exact match or a proper dot-delimited boundary, e.g.:
```js
if (authentifier_path === path || authentifier_path.substr(0, path.length + 1) === path + '.')
    return true;
```
This mirrors the fix applied to the Traefik advisory (require the delimiter immediately after the matched prefix, or exact-length equality) and eliminates string-prefix collisions between sibling path segments.

### Proof of Concept
Conceptual PoC (needs to be validated against `validation.js`'s exact call site to confirm end-to-end unit acceptance):
1. Define an address whose definition is `["or", [ ["address", other_address_A] /* mounted at path "r.1" */, ["sig", {...}] /* mounted at path "r.10" */ ]]`.
2. Post a unit signed only along the `r.10` branch, i.e., `author.authentifiers = { "r.10": sig }`, leaving the `r.1` (`address`) branch with no signature evaluation intended.
3. During `validateDefinition`, `arrAuthentifierPaths = ["r.10"]`; when evaluating the `address` node at `path = "r.1"`, `needToEvaluateNestedAddress("r.1")` calls `pathIncludesOneOfAuthentifiers("r.1", ["r.10"])`, which returns `true` due to `"r.10".substr(0,3) === "r.1"`, causing the nested address's actual definition to be evaluated when it should not need to be (or, depending on branch direction, being skipped and unconditionally accepted via `cb(null, true)` when it should have been evaluated) — breaking the intended signature-scope isolation between the two `or` branches.
4. Full confirmation requires stepping through `validation.js`'s `validateAuthorSignaturesWithoutReferences`/`validateAuthentifiers` to see the exact call parameters and to build a concrete unit/definition pair that flips a normally-rejected unit into an accepted one. [1](#0-0) [2](#0-1) [3](#0-2)
