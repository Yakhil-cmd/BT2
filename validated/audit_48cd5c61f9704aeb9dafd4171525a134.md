### Title
Clickjacking via `response.headers['X-Frame-Options'] = 'ALLOWALL'` enables unauthorized merge-queue enqueue/dequeue using the victim's session - ([File: app/controllers/shipit/merge_status_controller.rb])

### Summary
`MergeStatusController#show` unconditionally sets `X-Frame-Options: ALLOWALL`, allowing the merge-status widget (which contains live, session-bound forms for `enqueue`/`dequeue`) to be embedded in an attacker-controlled cross-origin iframe. A classic UI-redress/clickjacking overlay can trick an already-authenticated victim into clicking the framed "Add to merge queue" / "Remove from merge queue" button, causing their browser to submit a genuine, CSRF-token-valid request to the `enqueue`/`dequeue` endpoints without their intent.

### Finding Description
The claimed binding is: `X-Frame-Options prevents cross-origin framing == true`. In this controller it is explicitly false for the `:show` action: [1](#0-0) 

`show` is also exempted from Shipit's login-redirect gate (`skip_authentication only: %i[check show]`), so it renders content (including merge-queue action buttons) for any visitor whose session is already `logged_in?`: [2](#0-1) 

The rendered partial embeds real, CSRF-protected forms pointing at the state-changing `enqueue`/`dequeue` routes, submitted via `remote: true` (AJAX) with the real page's authenticity token: [3](#0-2) 

`enqueue`/`dequeue` are NOT in the `skip_authentication` list, so they still require `force_github_authentication`, but that check only verifies the requester `current_user.logged_in?` and `authorized?` (member of `Shipit.github_teams`) — there is no additional per-stack authorization/consent check: [4](#0-3) [5](#0-4) 

`protect_from_forgery with: :exception` (inherited from `ShipitController`) blocks *forged* cross-origin requests, but does nothing against clickjacking: the request submitted is not forged, it is the genuine same-origin form from the genuine iframe, carrying the genuine CSRF token, only the user's click is being hijacked via UI redress. [6](#0-5) 

Attack flow: attacker crafts a page containing `<iframe src="https://shipit.example.com/merge_status?referrer=https://github.com/<owner>/<repo>/pull/<n>&branch=<branch>">` (or `stack_id=...`), overlays decoy UI so the real "Add/Remove from merge queue" button sits under a lure ("Click to continue"), and gets a victim who is already logged into Shipit to click. The click submits the framed page's real AJAX form to `/enqueue`/`/dequeue` with the victim's session cookie and valid CSRF token, invoking `MergeRequest.request_merge!(stack, params[:number], current_user)` or `merge_request.cancel!` under the victim's identity, without the victim intending or even seeing that action. This is repeatable against any stack/PR the attacker can address via `referrer`/`branch`/`stack_id` params.

### Impact Explanation
The attacker causes a logged-in Shipit team member to unknowingly add or remove a pull request from a repository's merge queue (`MergeRequest.request_merge!` / `merge_request.cancel!`), an action credited to the victim's identity but never consented to. This is a state-carrying, authenticated write performed against the victim's real session, matching the spirit of "unauthorized merge" activity (queuing/dequeuing being the entry point to the actual merge pipeline). It does not grant the attacker any new authorization beyond what the victim already has (no team-membership escalation, no credential exfiltration), and is scoped to whichever stack/PR the attacker addresses per request — repeatable but bounded to targets where a valid team-member victim can be lured.

### Likelihood Explanation
Preconditions: victim must already have an active, `logged_in?` Shipit session (per the question's premise) and be a member of `Shipit.github_teams`; the attacker needs only to know or guess a `referrer` GitHub PR URL or `stack_id`/`branch` and host an arbitrary iframe/overlay page — no Shipit or GitHub secret is required. This is inexpensive and fully attacker-controlled once the framing precondition (a real, logged-in victim) is met, and it is repeatable against any number of stacks/PRs one request at a time.

### Recommendation
Remove the explicit `response.headers['X-Frame-Options'] = 'ALLOWALL'` override in `MergeStatusController#show` (or restrict it, e.g. `ALLOW-FROM` a fixed trusted origin / a `Content-Security-Policy: frame-ancestors` allowlist of the known embedding surface such as the GitHub PR page origin) so the merge-queue action buttons cannot be embedded and clickjacked from arbitrary third-party origins. If cross-origin embedding is a required product feature (e.g., embedding in GitHub's PR page via a browser extension), scope the CSP `frame-ancestors`/`X-Frame-Options` to that specific trusted origin only, and consider adding a client-side framing-busting/double confirmation on `enqueue`/`dequeue` actions.

### Proof of Concept
```ruby
# test/controllers/shipit/merge_status_controller_test.rb (add to existing test file)
test '#show explicitly disables frame protection' do
  stack = shipit_stacks(:shipit)
  session[:user_id] = shipit_users(:walrus).id
  get :show, params: { stack_id: stack.to_param }
  assert_equal 'ALLOWALL', response.headers['X-Frame-Options']
end

test 'clickjacked enqueue request succeeds using only the framed page state' do
  stack = shipit_stacks(:shipit)
  pr = shipit_merge_requests(:pending) # or a fixture representing a waiting/available PR
  session[:user_id] = shipit_users(:walrus).id

  # Simulate the attacker's iframe load of the framable, no-consent page
  get :show, params: { stack_id: stack.to_param, referrer: "https://github.com/#{stack.repository.owner}/#{stack.repository.name}/pull/#{pr.number}" }
  assert_equal 'ALLOWALL', response.headers['X-Frame-Options']

  # Simulate the victim's hijacked click submitting the real embedded form
  put :enqueue, params: { stack_id: stack.to_param, number: pr.number }
  assert_response :success
  assert pr.reload.waiting?, 'PR was enqueued via a request the victim never intentionally authorized on this page'
end
```

    def enqueue
      MergeRequest.request_merge!(stack, params[:number], current_user)
      render(stack_status, layout: !request.xhr?)
    end

    def dequeue
      if (merge_request = stack.merge_requests.find_by_number(params[:number])) && merge_request.waiting?
        merge_request.cancel!
      end
      render(stack_status, layout: !request.xhr?)
    end
