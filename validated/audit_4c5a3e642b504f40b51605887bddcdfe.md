### Title
Address Definitions Referencing External Addresses via `['address', ...]` Can Be Permanently Bricked by the Referenced Address Owner - (File: `definition.js`)

### Summary
Ocore address definitions support an `['address', 'BASE32']` operator that lets an address's spending condition depend on the *current* definition of another, independently-controlled address. Because that other address's owner can change their own definition at any time (via `address_definition_change`), and because the outer address's chash is immutable once created, a referenced address owner can unilaterally turn the outer address into a definition that can never again pass validation — permanently freezing any funds sitting at (or later sent to) that address, with no "uninstall" or emergency-override path, mirroring the Alchemy plugin-hook bricking bug class.

### Finding Description
`definition.js` implements the `'address'` opcode twice: once in `validateDefinition` (structural validation, `definition.js:269-304`) and once in `validateAuthentifiers` (actual signature evaluation, `definition.js:774-800`). In both places, the inner definition is fetched dynamically via `storage.readDefinitionByAddress(conn, other_address, objValidationState.last_ball_mci, …)` and then recursively evaluated: [1](#0-0) [2](#0-1) 

The function `validateAuthentifiers` explicitly documents that this dynamic re-resolution is dangerous: [3](#0-2) 

That comment states plainly: "redefinition of a referenced address might introduce loops that will drive complexity to infinity," yet no mitigation exists beyond the generic complexity/op-count limits enforced inside `evaluate`: [4](#0-3) 

Because:
1. An address's identity (`address` = `chash160(definition)`) is immutable — once other parties have started depending on it via `['address', X]`, that reference can never be removed from the *outer* definition.
2. The referenced address owner fully controls their own definition and can change it freely and repeatedly via `address_definition_change` (validated generically in `validateInlinePayload`, `validation.js:1719-1745`) — this is normal, permission-less behavior for any address owner, exactly analogous to a plugin author who can register new hooks post-installation.
3. If the new inner definition is crafted to exceed `MAX_COMPLEXITY`/`MAX_OPS`, or to contain an unsatisfiable/looping structure, every future `evaluate()` call over the outer definition will return an error (`"complexity exceeded…"`, `"number of ops exceeded…"`) and authentifier validation will never succeed again.
4. Since signature/authentifier checking is mandatory for spending, the outer address becomes permanently unable to authorize any future unit — its balance is frozen forever, with no way for the outer address's controller(s) to "uninstall" the malicious dependency, just as a malicious plugin's always-reverting hooks block `uninstallPlugin` in the reported Alchemy bug.

This is squarely within the "address definitions and authentifiers" scope of reachable analogs, and the attacker is simply an ordinary, unprivileged co-signer/other address owner referenced by `['address', ...]` — not a malicious node, peer, or hub.

### Impact Explanation
Shared/multisig addresses (`wallet_defined_by_addresses.js`) and any custom address definition that embeds `['address', other_address]` inherit the liveness of the referenced address's definition. A referenced party — who may be a co-signer of a multisig wallet, or any address whose owner was trusted to keep a benign definition when the outer address was created — can, after the outer address has already received funds, redefine themselves to a maliciously complex/looping definition. This permanently freezes all base-currency and asset balances held at the outer address, since neither AA logic nor manual `address_definition_change` recovery is possible (the address's chash can't change, and it can't authorize a definition-change message without passing authentifier validation itself). This is a concrete "AA/address fund loss or freezing" impact.

### Likelihood Explanation
The construct is a documented, ordinary oscript feature (`['address', X]`), not a bug requiring the referenced party to do anything out-of-protocol — any address owner can trigger this today via a completely normal `address_definition_change` message. The barrier to exploitation is only that some other address must have chosen to reference the attacker's address in an `['address', X]` clause when originally composing its own definition (e.g., in a shared address setup, or any nested-condition design pattern). Given ocore's own code comments acknowledge this exact risk, it is a realistic, low-effort griefing/DoS vector for anyone who is (or convinces others to make them) a referenced party in a composite address definition.

### Recommendation
- Consider capping/pinning the referenced inner definition at the time the outer address is created (e.g., snapshot/freeze the resolved definition instead of re-resolving dynamically at every validation), or
- Require that outer definitions referencing external addresses include an escape/override branch (e.g., a time-locked fallback signer) so that funds are not unconditionally hostage to the referenced address's future definition changes, and
- Add a stricter complexity/loop-detection budget specifically when resolving nested `['address', X]` references, and document to wallet UIs that composing addresses with `['address', X]` on externally controlled addresses carries a freeze risk when the referenced party changes their definition maliciously.

### Proof of Concept
1. Alice and Bob agree to create a 2-of-2-like address `S` whose definition includes `['and', [['sig', {pubkey: Alice}], ['address', Bob_address]]]` (or equivalent nested construct), where `Bob_address`'s current definition is `['sig', {pubkey: BobKey}]`.
2. Alice sends funds to `S`.
3. Bob issues an `address_definition_change` on `Bob_address`, changing its definition to a deeply nested/self-referential definition engineered to push `evaluate()`'s `complexity`/`count_ops` past `constants.MAX_COMPLEXITY`/`MAX_OPS` (see `definition.js:103-111`), while the new definition still resolves fine for spending Bob's own funds directly (so Bob suffers no loss).
4. From this point on, any attempt to spend from `S` re-resolves `['address', Bob_address]` per `definition.js:774-800`, which recurses into Bob's new bloated/looping definition and fails validation with `"complexity exceeded"`/`"number of ops exceeded"`.
5. `S`'s balance is now permanently frozen: Alice cannot spend without Bob's cooperation (by design), but Bob can never restore spendability either, because `S`'s chash is immutable and always re-evaluates the *current* (attacker-controlled) definition of `Bob_address`.
