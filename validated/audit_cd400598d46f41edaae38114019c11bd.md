### Title
Webhook signature verified against `repository.owner.login`/`organization.login` while handlers act on `repository.full_name` - cross-organization forged webhooks in multi-org Shipit deployments ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
When Shipit is configured with multiple GitHub organizations (as documented in `docs/setup.md`, each with its own `webhook_secret`), the HMAC signature check selects which organization's secret to verify against using `repository.owner.login` (or `organization.login`) from the untrusted, not-yet-verified JSON body. The event handlers that actually act on the payload (finding the `Stack`/`Repository` and triggering deploys, syncs, status updates, membership changes, etc.) instead use `repository.full_name` from that same body. These two fields are never cross-checked, so a party who legitimately possesses the webhook secret for **one** configured organization can forge a signed payload that names a **different** organization's repository in `repository.full_name`, and the handler will act on it.

### Finding Description
`WebhooksController#verify_signature` selects the `GitHubApp`/secret to verify against using data taken straight from the unverified request body: [1](#0-0) [2](#0-1) 

Once `verify_webhook_signature` returns true for the org identified by `repository_owner`, the controller dispatches the raw parsed payload — unchanged — to the registered handlers: [3](#0-2) 

The base `Handler` class, used by all handlers (`PushHandler`, `StatusHandler`, `CheckSuiteHandler`, `MembershipHandler`, `PullRequest::*Handler`), resolves the target `Stack`/`Repository` using a **different** field of the same payload — `repository.full_name` — not `repository.owner.login`: [4](#0-3) 

Because Shipit supports multiple GitHub Apps/organizations each with independent `webhook_secret`s (`lib/shipit/github_app.rb` initializes `@webhook_secret` per-org config, and `docs/setup.md` documents the multi-org `github:` config format), the field used to pick *which* secret validates the signature (`repository.owner.login`) is decoupled from the field used to determine *which repository/stack is acted upon* (`repository.full_name`). Nothing in `verify_signature` or in `Handler#repository_name` enforces that these two values refer to the same organization.

This is exactly the "organization that authenticated versus the repository that is written" trust-binding break called out in scope: the equality `repository_owner (signed by) == repository.full_name's owner (acted on)` is never enforced.

### Impact Explanation
In a multi-organization Shipit deployment, anyone who holds the webhook secret for organization A (e.g., an admin of a GitHub App installed for org A, or anyone who can read/leak that one secret) can craft an HTTP POST to `/webhooks` with:
- `repository.owner.login` (or `organization.login`) = `"org-a"` — so `Shipit.github(organization: "org-a")` is selected and the HMAC is computed/verified with org A's secret, which the attacker controls/knows.
- `repository.full_name` = `"org-b/victim-repo"` — an entirely different, victim organization's repository that Shipit also tracks.

Because the signature check passes (it only validates that org A's secret signed the bytes, and says nothing about which repository the payload claims to describe), the event is dispatched to handlers that will act on org B's repository/stack: e.g. `PushHandler` will call `stack.sync_github(expected_head_sha: params.after)` for org B's stacks matching the forged branch/`after` sha, `StatusHandler`/`CheckSuiteHandler` can inject fabricated CI status/check-run state, and `MembershipHandler` can create/remove team memberships. This is an unauthorized cross-repository/cross-organization action triggered with a credential (webhook secret) scoped to a different tenant, matching the "cross-repository writes / unauthorized deploy" high-severity impact bucket in scope.

### Likelihood Explanation
This requires: (1) Shipit configured for multiple GitHub organizations (a documented, supported configuration in `docs/setup.md`), and (2) the attacker possessing the webhook secret for at least one of those organizations (which is a much lower bar than possessing org B's secret or any Shipit session/API token — webhook secrets are set at GitHub App creation and are often shared more broadly, e.g. with less-trusted org admins, CI infra, or third parties who only need to send events for their own org). Given that condition, forging the cross-org payload is trivial (just set two independent JSON fields and compute one HMAC). No Shipit session, `ApiClient` token, or repository write access to org B is needed.

### Recommendation
After signature verification, ensure the verified organization matches the organization implied by `repository.full_name` (or `organization.login`) actually used to resolve the target `Stack`. Concretely, in `WebhooksController`/`Handler`, derive the owning organization consistently from a single field, and reject (422) any payload where `repository.owner.login` (the field used to pick the verifying secret) does not match the owner segment of `repository.full_name` (the field used to resolve the target repository).

### Proof of Concept
1. Configure Shipit with two GitHub Apps/orgs, `org-a` (secret `SECRET_A`, known to attacker) and `org-b` (contains a tracked `Stack` for `org-b/victim-repo`).
2. Attacker builds a `push` payload:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "org-a" },
    "full_name": "org-b/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(SECRET_A, raw_body)>` and sends the POST to `/webhooks` with `X-Github-Event: push`.
4. `WebhooksController#verify_signature` computes `repository_owner = "org-a"` [2](#0-1)  selects org A's `GitHubApp`, verifies the HMAC successfully with `SECRET_A`, and lets the request through.
5. `PushHandler` (via `Handler#stacks`/`#repository_name`) resolves `Repository.from_github_repo_name("org-b/victim-repo")` [4](#0-3)  and triggers `stack.sync_github(expected_head_sha: params.after)` [5](#0-4)  for org B's stack — an action authorized only by org A's credential.
