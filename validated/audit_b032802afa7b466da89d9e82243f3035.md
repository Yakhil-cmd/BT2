## Title
Webhook signature verification key selected from unauthenticated `repository.owner.login` field diverges from the `repository.full_name` field the handlers act on, allowing signature-check bypass and cross-repository writes - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks which GitHub App/webhook secret to verify the signature against by reading `repository.owner.login` (or `organization.login`) directly out of the **unauthenticated** JSON body, before any signature has been validated. The actual repository/stack that the event is later applied to is resolved independently, by the handler base class, from `repository.full_name` in that same unauthenticated body. Because these are two independently attacker-controlled fields inside one JSON payload, an attacker can pick an "owner" that maps to a configured organization with no `webhook_secret` set (which is documented and supported, e.g. `test/dummy/config/secrets_double_github_app.yml`), causing signature verification to be trivially satisfied, while still targeting `repository.full_name` of an arbitrary victim repository/stack that is deployed under a different, properly-secured organization.

### Finding Description
- `verify_signature` selects the signing key using data that has not yet been authenticated: [1](#0-0) 
- The `repository_owner` used for that key lookup is read straight from the JSON body: [2](#0-1) 
- `Shipit.github(organization: ...)` resolves a `GitHubApp` per configured organization key, and multi-org configuration is an explicitly supported feature where some orgs may have `webhook_secret: nil`: [3](#0-2) 
- `GitHubApp#verify_webhook_signature` unconditionally treats a blank `webhook_secret` as "verified": [4](#0-3) 
- After this "verification" step, the actual business logic (`Handler` base class used by `PushHandler`, `StatusHandler`, etc.) determines which `Stack`/`Repository` to act on using a *different* field of the same unauthenticated JSON body — `repository.full_name` — with no consistency check against `repository.owner.login`: [5](#0-4) [6](#0-5) 

This breaks the trust binding: `organization authenticated (via repository.owner.login and its webhook_secret) == repository actually written (via repository.full_name)`. Nothing enforces that `full_name`'s owner segment matches the `owner.login` that was used to select/validate the signature. An attacker who knows (or guesses) that any configured organization lacks a `webhook_secret` (this is an out-of-the-box supported, documented state — see `docs/setup.md` "Webhook secret (optional)" and the multi-org example configs) can submit a forged, unsigned event payload naming that org as `repository.owner.login` while setting `repository.full_name` to any victim `owner/repo` tracked by Shipit, e.g., to fire `push` events that trigger `GithubSyncJob`/`sync_github` for that victim stack, or `status`/`check_suite` events that mutate commit statuses/checks used to gate deploys.

### Impact Explanation
This crosses the "unauthorized deploy/write" boundary called out in scope: an unprivileged, unauthenticated remote attacker (anyone who can POST to `/webhooks`) can inject events that are processed as if legitimately signed by GitHub for an arbitrary tracked repository, as long as at least one configured GitHub organization in the deployment has no webhook secret configured (a state the engine explicitly supports and ships example configs for). This can influence deploy-gating state (commit statuses, check suites) and trigger repository sync jobs for repositories/stacks the attacker does not control, i.e., cross-repository interference without any credential. This maps to High/Critical impact per the rubric ("unauthorized deploy... cross-repository writes").

### Likelihood Explanation
Requires: (1) the target Shipit instance configured with multiple GitHub organizations (a documented, supported deployment mode) where at least one organization has no `webhook_secret` set, and (2) the attacker knowing/guessing that org's name. Both webhook secret configuration and multi-org names could be discoverable/guessable or simply absent by default (the single-org default template also leaves `webhook_secret` optional/blank). Likelihood is moderate — it depends on operator configuration, but the vulnerable pattern (deriving trust-selection key from the same untrusted body that supplies the target-selection key, with no cross-check) is present in the code regardless of configuration, and is entirely attacker-triggerable with a single unauthenticated HTTP POST.

### Recommendation
- Do not derive the signing-organization from unauthenticated payload content when multiple orgs/secrets are configured; instead require a strong per-org webhook secret whenever multi-org config is used, and reject requests where no secret is configured for the resolved org (fail closed instead of `return true unless webhook_secret`).
- After signature verification succeeds, explicitly verify that the `owner.login` used to select/verify the secret matches the owner segment of `repository.full_name` (or `organization.login`) before dispatching to handlers, rejecting mismatches.
- Consider making `webhook_secret` mandatory (validation at boot) for any organization entry in `Shipit.github`.

### Proof of Concept
Given a deployment with:
```yaml
github:
  OrgOne:
    webhook_secret: # nil (unset)
    ...
  OrgTwo:
    webhook_secret: "s3cr3t"
    ...
```
and a Shipit stack tracking `OrgTwo/victim-repo`, an attacker sends:
```
POST /webhooks
X-Github-Event: push
X-Hub-Signature: sha1=0000000000000000000000000000000000000000

{
  "ref": "refs/heads/main",
  "after": "deadbeefdeadbeefdeadbeefdeadbeefdeadbeef",
  "repository": {
    "owner": { "login": "OrgOne" },
    "full_name": "OrgTwo/victim-repo"
  }
}
```
- `verify_signature` resolves `github_app = Shipit.github(organization: "OrgOne")` [1](#0-0) , and since `OrgOne` has no `webhook_secret`, `verify_webhook_signature` returns `true` regardless of the bogus signature [4](#0-3) .
- `create` then parses `params` and dispatches to `PushHandler`, which resolves the target stack via `repository.full_name` = `"OrgTwo/victim-repo"` [7](#0-6) [6](#0-5) , enqueuing a `GithubSyncJob`/triggering sync for the victim stack under `OrgTwo`, despite never presenting a valid `OrgTwo` signature.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
