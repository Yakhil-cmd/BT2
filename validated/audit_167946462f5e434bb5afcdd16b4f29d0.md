### Title
Unauthenticated live subscription to task/deploy output stream via mounted Pubsubstub engine bypassing Shipit's authentication filter chain - (File: config/routes.rb)

### Summary
`Pubsubstub::StreamAction` is mounted directly as a Rack application at `/events` [1](#0-0)  instead of being routed through a Shipit controller. Because it is a `mount`, not a controller action, none of `ShipitController`'s `before_action` authentication filters (`force_github_authentication`) ever execute for requests to `/events`, letting any unauthenticated client subscribe to any pubsub channel it can name or guess, including channels carrying live task/deploy output.

### Finding Description
The binding that should hold is: `AuthEnforced(request path served by Shipit::Engine) == true` for every path under the engine that exposes stack/task state, because `ShipitController` (and the `Shipit::Authentication` concern it includes) is the mechanism that enforces this for all controller-backed routes such as `stacks#show`, `tasks#show`, `api/outputs#show`, etc.

`mount Pubsubstub::StreamAction.new, at: "/events"` breaks this binding: a `mount` point is dispatched to directly as its own Rack endpoint and never instantiates `ShipitController`, so `force_github_authentication`/`authorized?` never run for it [1](#0-0) . The result is `AuthEnforced(/events) == false` while `AuthEnforced(everything else) == true` — the divergence the question describes.

Task/deploy output that is normally gated behind the authenticated `api/outputs` or `tasks#tail`/`show` controllers is streamed live to pubsub channels (`Task#write`/`chunk_output` push to Redis and, via the `Shipit.pubsub`/Pubsubstub integration wired in `lib/shipit/engine.rb` and `Shipit::Stack`, republished as SSE events) [2](#0-1) . Any client that can reach `/events` and supply/guess a valid channel name (stack or task identifiers, whose format `stack_id_format` is a public regex in `routes.rb`) receives that stream with zero authentication.

I could not fully verify from the indexed code the exact channel-naming scheme used to publish to Pubsubstub (the calls appear in `app/models/shipit/stack.rb`, but the file's channel-construction lines were not retrievable through search/read in this session), so the precise guessability of channel names (e.g., whether they include unguessable secrets like task UUIDs vs. predictable `stack:owner/repo/env` strings) is not fully confirmed here.

### Impact Explanation
An unauthenticated attacker who reaches the Shipit host can perform unauthenticated reads of stack/task state and deploy/task streaming output for any stack whose channel identifier they can derive — this matches the "High: unauthenticated read of stack state, task streams or deploy output" impact category defined in the rules. The blast radius spans every stack hosted by the instance, since the mount point is global and not scoped per-tenant; repeatability is unlimited (any number of GET/SSE subscribe requests). Whether secrets (e.g., `GITHUB_TOKEN`-derived values) actually appear in `chunk_output` depends on what commands/build steps echo to stdout, which is deployment-specific and not verifiable from this engine's code alone — so the guaranteed impact is confidently "High" (output/state disclosure), with escalation to "Critical" only if a given deploy script happens to echo secrets.

### Likelihood Explanation
No credentials, sessions, or GitHub privileges are required — the only precondition is network access to the Shipit host and knowledge/guessing of a valid pubsub channel name, whose format is derivable from the public `stack_id_format` regex in `routes.rb`. This is trivially repeatable and requires no interaction with GitHub. The only uncertainty affecting exploitability is the exact channel-naming scheme (whether it embeds anything non-guessable), which limits full certainty of this proof but does not change the underlying architectural bypass: the mount is provably unauthenticated regardless of channel secrecy.

### Recommendation
Do not `mount` `Pubsubstub::StreamAction` directly on the engine's route set outside the controller filter chain. Instead, wrap `/events` in a thin controller action (or a Rack middleware invoked after authentication) that runs `force_github_authentication`/`authorized?` (and, ideally, validates the requested channel belongs to a stack the current user is authorized to view) before delegating to `Pubsubstub::StreamAction`. Alternatively, generate per-subscription signed/expiring tokens (scoped to the stack the authenticated user is viewing) that `StreamAction` validates before allowing a channel subscription.

### Proof of Concept
```ruby
# test/integration/unauthenticated_events_stream_test.rb (proof-of-concept plan, not present in scope but describes the assertion)
test "GET /events without a session can subscribe to a stack's channel" do
  stack = shipit_stacks(:shipit)
  channel = "stack:#{stack.to_param}" # or whatever Stack's actual pubsub channel format is

  # No sign_in, no cookies, no Authorization header
  get "/events", params: { channel: channel }, headers: { "Accept" => "text/event-stream" }

  assert_response :success
  # Publish a task chunk on the same channel from a background job
  # and assert the SSE body eventually contains that chunk's content,
  # proving delivery without any authentication check having run.
end
```
Both sides of the equality to assert: `ShipitController#force_github_authentication` is invoked for `stacks#show`/`api/outputs#show` (verifiable by asserting a 302/401 without a session) but is never invoked for `/events` (verifiable by asserting `200`/stream success without a session) — demonstrating the divergence directly.
