### Title
Unvalidated route venues can steal unrelated wallet tokens through the caller’s authorization tree - (File: `contracts/swap-aggregator/src/execute/mod.rs`)

### Summary
A route can name an arbitrary pool contract address, and the router invokes that address during execution. Because the venue call occurs inside the `sender.require_auth()` invocation, a malicious venue can request additional token transfers from the sender; those requests are recorded as children of the caller’s signed authorization tree and execute if signed. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
`execute_strategy` decodes caller-supplied `swap_xdr`, resolves token and pool addresses from its `assets` registry, and authorizes the sender before executing the route. [4](#0-3)  Program validation checks opcode structure and registry bounds, but does not verify that a pool address is a known or trusted venue implementation. [5](#0-4)  Execution then constructs a hop from the supplied pool address and dispatches it to a venue adapter. [6](#0-5) 

The venue adapter invokes the supplied contract. For example, the Soroswap adapter calls `get_reserves`, transfers the measured input to the supplied address, and invokes its `swap` function. [7](#0-6)  During that call, malicious venue code can invoke an unrelated token’s `transfer(sender, attacker, amount)`. Soroban records that nested authorization request under the root authorization for the user’s strategy call; if the user signs the simulated tree, the unrelated transfer succeeds. [8](#0-7) [9](#0-8) 

The same exposure applies through controller strategy entrypoints such as `swap_collateral(caller, account_id, current, amount, new, swap)`, where `swap` is caller-controlled route bytes. [10](#0-9)  The controller authorizes one exact input-token transfer to the configured router, but that restriction only limits the controller’s own authorization; it does not isolate the user’s root authorization from code executed by the route. [11](#0-10) [9](#0-8) 

### Impact Explanation
A malicious route can steal arbitrary tokens held by the caller, including assets unrelated to the strategy and assets never listed by the lending protocol. The theft amount is bounded only by the victim’s wallet balances and the malicious payload encoded in the signed route. [8](#0-7)  The route can still return sufficient output to satisfy `total_min_out`, the controller’s measured-output check, and final account risk checks, so none of those controls bounds the separate wallet transfer. [12](#0-11) [13](#0-12) 

### Likelihood Explanation
Exploitation requires the victim to submit and sign a malicious route. This is realistic when routes are generated or relayed by an attacker-controlled interface, quote, or payload provider, and the wallet approves the simulated authorization tree without identifying the unexpected child token transfer. [9](#0-8)  An unprivileged attacker needs only a deployed contract implementing the expected venue ABI and a route whose `assets` registry names that contract as the pool. [14](#0-13) [7](#0-6) 

### Recommendation
Do not execute arbitrary pool addresses selected solely by route input. Bind each venue opcode to a governance-approved pool registry or otherwise validate that the supplied pool is a known trusted implementation before invoking it. [2](#0-1)  If arbitrary pool routing must remain supported, treat the route and its complete simulated authorization tree as part of the signing boundary and require clients to reject any child invocation other than the expected input transfer; however, client-side inspection does not provide an on-chain invariant against a user signing a poisoned tree. [9](#0-8) 

### Proof of Concept
1. The attacker deploys a contract exposing the selected venue’s pool ABI, such as `get_reserves` and `swap` for a Soroswap opcode.
2. The malicious `swap` implementation invokes `unrelated_token.transfer(victim, attacker, victim_balance)` before returning normally.
3. The attacker creates a `StrategyPayload` whose `assets` registry includes the malicious contract in the instruction’s `idx_a` pool slot and the expected input/output tokens in `idx_b` and `idx_c`.
4. The victim invokes either:
   - `Router::execute_strategy(sender = victim, total_in, swap_xdr)`, or
   - `Controller::swap_collateral(caller = victim, account_id, current, amount, new, swap_xdr)`.
5. Simulation records the rogue token transfer as a child of the victim’s authorization entry. If the victim signs that tree, the malicious pool transfers the unrelated wallet token to the attacker while the route can still satisfy its minimum output and account checks. [3](#0-2)

    /// Validates every instruction's opcode, mode, and indices before execution begins,
    /// including the `Prev` chain, same-token swaps, and split-weight bounds.
    fn validate(&self, env: &Env, assets_len: u32, amounts_len: u32, weight_count: u32) {
        for i in 0..self.op_count {
            let record = self.raw(i);
            let Some(opcode) = Opcode::from_u8(record[field::OPCODE]) else {
                panic_with_error!(env, Error::InvalidRouteXdr);
            };
            let mode = Mode::from_u8(record[field::MODE]);
            let (idx_a, idx_b, idx_c) = (
                record[field::POOL] as u32,
                record[field::TOKEN_IN] as u32,
                record[field::TOKEN_OUT] as u32,
            );

            // `Prev` is a purely structural link: the predecessor must exist,
            // must have a single output, and that output must be this
            // instruction's input.
            if mode == Mode::Prev {
                if i == 0 {
                    panic_with_error!(env, Error::BrokenTokenChain);
                }
                let previous = self.raw(i - 1);
                let produced = match Opcode::from_u8(previous[field::OPCODE]) {
                    // A swap produces its `token_out`, a mint its share token.
                    Some(Opcode::Swap(_)) => previous[field::TOKEN_OUT],
                    Some(Opcode::Mint) => previous[field::TOKEN_IN],
                    // A burn releases every constituent at once.
                    _ => panic_with_error!(env, Error::BrokenTokenChain),
                };
                if idx_b != produced as u32 {
                    panic_with_error!(env, Error::BrokenTokenChain);
                }
            }
            match mode {
                Mode::Fixed(idx) if idx as u32 >= amounts_len => {
                    panic_with_error!(env, Error::InvalidRouteXdr)
                }
                Mode::Ppm(idx) if idx as u32 >= weight_count => {
                    panic_with_error!(env, Error::InvalidRouteXdr)
                }
                _ => {}
            }

            if idx_a >= assets_len || idx_b >= assets_len {
                panic_with_error!(env, Error::InvalidRouteXdr);
            }
            match opcode {
                Opcode::Swap(_) => {
                    if idx_c >= assets_len {
                        panic_with_error!(env, Error::InvalidRouteXdr);
                    }
                    if idx_b == idx_c {
                        panic_with_error!(env, Error::SameToken);
                    }
                }
