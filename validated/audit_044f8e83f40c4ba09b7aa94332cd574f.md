### Title
Missing cosigner-authorization check in the "sign" message handler allows any paired device to request signing of arbitrary transactions/messages against addresses it does not own — (File: `wallet.js`)

### Summary
`handleMessageFromHub`'s `"sign"` case resolves the target address via `findAddress()` and, when the address is *local* (i.e. the signing key lives on the receiving device), immediately proceeds to fire a `signing_request` and validate/broadcast the caller-supplied unit — without verifying that the sender (`from_address`) is actually a cosigner/member of the wallet or shared address that owns `body.address`. The authorization check that would enforce this was deliberately commented out.

By contrast, the `ifRemote` branch of the very same handler *does* enforce that the requesting sender must be a recognized cosigner before it will forward the request: [2](#0-1) 

```
ifRemote: function(device_address, other_device_addresses){
    if (device_address === from_address)
        return callbacks.ifError("looping signing request for address "+body.address+", path "+body.signing_path);
    if (!other_device_addresses.includes(from_address))
        return callbacks.ifError("you are not listed as a cosigner for this address "+body.address);
```

This asymmetry means: for addresses whose signing key is hosted on the *receiving* device, **any paired correspondent** (an entity that has merely completed device pairing — not necessarily a wallet cosigner) can send a `"sign"` message referencing that device's own address and cause it to:
- process and validate an attacker-supplied `unsigned_unit` (including arbitrary payment inputs/outputs, private payloads, or a `signed_message`),
- emit a `signing_request` event carrying the attacker-controlled unit/message to the device's wallet application, and
- ultimately reach `network.handleOnlineJoint`, all gated only by whatever the downstream UI decides to do with `signing_request`.

`findAddress` traverses `my_addresses`, `wallet_signing_paths`, and `shared_address_signing_paths` [3](#0-2) , so this reaches every locally-hosted signing path, including shared/multisig addresses where the device is one of several members — not just the device’s own private single-sig wallet.

### Impact Explanation
This is a missing-authorization defect analogous to the ChromaDB issue: an entity that is authenticated at the transport layer (a paired device) but has no legitimate relationship to the specific resource (the target address/wallet) is allowed to drive privileged, resource-scoped operations against it. Concretely this lets an unrelated paired peer:
- feed a victim device attacker-chosen payment data (inputs/outputs, private payloads) framed as something to sign for one of its own addresses, laundering it through the wallet’s normal signing/confirmation pipeline as if it originated from a legitimate cosigner request,
- request signature over an arbitrary `signed_message` bound to the victim's address, which can be replayed as an authenticator elsewhere (e.g., arbiter-contract acceptance, which is validated purely by checking a signed message against `objContract.peer_address`, see `wallet.js:932`), and
- do this for shared/multisig addresses as well, since `findAddress` recurses into `shared_address_signing_paths` without re-checking sender membership at the local branch.

### Likelihood Explanation
Reachable by any device that has completed pairing with the victim (a normal, low-privilege relationship established via a pairing code/URI) — no wallet or shared-address membership is required, only knowledge of the target `address` and a valid `r`-prefixed `signing_path`, both of which are frequently shared/observable in normal correspondent interactions (contracts, chats, shared address setup). The check that would prevent this was consciously disabled rather than never implemented, so the gap is a persistent, exploitable path rather than an edge case.

### Recommendation
Restore an authorization check in the `ifLocal` branch of the `"sign"` handler that verifies `from_address` is a legitimate cosigner/member for `body.address` (via `wallet_signing_paths` for wallet addresses and `shared_address_signing_paths`/member relationship for shared addresses) before proceeding to validate or emit `signing_request` for caller-supplied data. If multilateral signing (case 2 in the code comment) requires allowing non-cosigner senders, that use case should be distinguished explicitly (e.g., via a separate message type or an authenticated claim tied to being an author of the same unit) rather than universally disabling the ownership check for all local addresses.

### Proof of Concept
1. Device B pairs with Device A (ordinary correspondent pairing, no shared wallet).
2. Device B learns one of Device A's addresses, `addrA` (e.g., from a prior chat/contract), and signing path `r`.
3. Device B sends a `"sign"` message to A's hub: `{address: addrA, signing_path: "r", unsigned_unit: {...attacker-crafted authors/messages...}}`.
4. On Device A, `handleMessageFromHub` resolves `addrA` via `findAddress` to `ifLocal` (since A hosts the key), and — because the cosigner check is commented out — proceeds directly to `callbacks.ifOk()` and emits `eventBus.emit("signing_request", ...)` with B's attacker-controlled unit, without ever verifying B has any relationship to `addrA` or its wallet.
