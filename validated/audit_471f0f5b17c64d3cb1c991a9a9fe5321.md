### Title
Confused-deputy webhook status forgery via organization/repository signature-binding mismatch - (File: app/controllers/shipit/webhooks_controller.rb, app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/`webhook_secret` to verify a webhook against based on `repository.owner.login` (or `organization.login`) taken from the *unverified* JSON body, but the handlers that subsequently act on the payload (e.g. `StatusHandler`) never re-check that the entity whose secret authenticated the request is the same entity whose data is mutated. This breaks the binding: `organization authenticated == repository/commit written`.

### Finding Description
`WebhooksController#verify_signature` looks up the GitHub App config to use for HMAC verification purely from attacker-supplied payload fields: [1](#0-0) [2](#0-1) 

Shipit explicitly supports configuring multiple independent GitHub Apps for different organizations, each with its own (optional) `webhook_secret`: [3](#0-2) 

`Shipit::GithubApp#verify_webhook_signature` trivially returns `true` when no secret is configured for the resolved organization: [4](#0-3) 

After signature verification, event handlers do not reuse the verified `repository_owner`; instead the base `Handler` resolves the target repository purely from `payload['repository']['full_name']`, an independent field of the same untrusted JSON: [5](#0-4) 

`StatusHandler#process` goes further and doesn't even scope by repository at all — it matches commits globally by `sha` and writes CI status state straight from the payload with no cross-check against GitHub: [6](#0-5) 

**Attack:** In a multi-org Shipit instance, an attacker who can produce a valid signature for *any* configured org `A` (trivial if org `A` has no `webhook_secret` set — an explicitly supported/"optional" configuration per `docs/setup.md`) crafts a `status` webhook where `repository.owner.login` = `A` (so `verify_signature` passes using `A`'s app), but omits/mismatches the real repository binding, letting `StatusHandler` match any `Commit` row in the database by `sha` alone — including commits belonging to stacks tracked under a completely different, properly-secured organization `B`. The forged `state: "success"` status is written to that commit via `commit.create_status_from_github!`.

### Impact Explanation
Commit status/CI state feeds directly into `Commit#deployable?`/`deploy_disallowed?`, which gate the deploy button and safety checks shown to fund/stack managers. Forging a green status for a commit under org `B`, while only having authenticated as (or as an unsecured) org `A`, lets an unprivileged webhook sender make an otherwise CI-failing or unverified commit appear deployable, enabling an unauthorized deploy decision by a legitimate operator who trusts the (forged) green status — matching the "unauthorized deploy" critical-impact category.

### Likelihood Explanation
Requires: (1) a Shipit instance configured with multiple GitHub organizations (an explicitly documented and supported configuration), and (2) at least one configured org with no/weak `webhook_secret` (the example config ships `webhook_secret: # nil` and docs mark the secret as "optional"), which is a realistic operational state during onboarding or for low-trust orgs. Given that, no privileged credential (no `ApiClient` token, no session, no GitHub App key) is needed to hit `/webhooks` and forge the event.

### Recommendation
Bind the resolved `repository_owner` used for signature verification to the actual `repository.full_name` used by handlers (reject if `repository.full_name.split('/').first != repository_owner`), and scope `StatusHandler`/other handlers' commit/stack lookups by the repository that was actually authenticated, not merely by an unscoped `sha` match.

### Proof of Concept
1. Configure Shipit with two orgs in `secrets.yml`: `orgA` (no `webhook_secret`) and `orgB` (real, secret webhook_secret, hosts the target stack/commit).
2. POST to `/webhooks` with header `X-Github-Event: status`, no/blank `X-Hub-Signature`, and body:
```json
{
  "repository": { "owner": { "login": "orgA" }, "full_name": "orgA/throwaway-repo" },
  "sha": "<sha of a real commit belonging to orgB's tracked stack>",
  "state": "success"
}
```
3. `verify_signature` resolves `Shipit.github(organization: "orgA")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` unconditionally.
4. `StatusHandler#process` runs `Commit.where(sha: params.sha)` — matching the targeted commit regardless of `orgA`/`orgB` mismatch — and calls `create_status_from_github!`, writing a forged "success" status onto orgB's commit.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
