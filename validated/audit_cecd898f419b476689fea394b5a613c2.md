## Finding: Webhook signature is verified against an attacker-chosen organization, while the event is dispatched against an attacker-chosen `repository.full_name` — (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/handler.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/`webhook_secret` to validate the HMAC against using `repository.owner.login` taken straight from the unauthenticated JSON body [1](#0-0) , using the helper `repository_owner` [2](#0-1) . Every event handler, however, resolves *which stack/repository the event acts on* using a different, independently-controlled field, `payload.dig('repository', 'full_name')` [3](#0-2) . Nothing ties these two fields together, so the "organization whose secret authenticated the request" and "the repository the request is allowed to act on" are never proven equal.

### Finding Description
The trust binding that should hold is:
`organization verified via HMAC(repository.owner.login) == owner(repository.full_name) acted on by the handler`

In a Shipit instance configured for multiple GitHub organizations (a documented, ordinary configuration — see `docs/setup.md` "Using Multiple Github Applications"), each organization has its own independent `webhook_secret` in `secrets.yml`. Anyone who administers a GitHub App/webhook for *their own* organization "attacker-org" (the intended, low-privilege use case: they own their org's app, not Shipit's) knows that org's `webhook_secret`.

Because `WebhooksController#create` accepts POST bodies from anyone (it is a public endpoint, not gated by an `ApiClient` token) [4](#0-3) , an attacker can craft an arbitrary JSON body where:
- `repository.owner.login` (or `organization.login`) = `"attacker-org"` — selects the secret they know.
- `repository.full_name` = `"victim-org/victim-repo"` — the repository actually processed by the handler.

`verify_signature` calls `Shipit.github(organization: "attacker-org")` and validates the signature successfully because the attacker computed the HMAC with their own known secret over the whole raw body, including the forged `full_name` field [5](#0-4) . The request then proceeds to `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` [6](#0-5) .

For example, `PushHandler` resolves stacks via `Repository.from_github_repo_name(repository_name)` where `repository_name` is the forged `repository.full_name`, and then calls `stack.sync_github(expected_head_sha: params.after)` on the victim's real stack [7](#0-6) ; `Repository.from_github_repo_name` does a straight DB lookup with no verification of who signed the request [8](#0-7) .

### Impact Explanation
This is a cross-repository write: an unprivileged attacker who only controls their own organization's GitHub App webhook secret can forge webhook events targeting any other repository/stack configured on the same shared Shipit instance, triggering handler-side side effects (e.g. `GithubSyncJob` enqueuing and DB writes via `stack.sync_github`) for repositories/organizations they have no relationship to. Other handlers keyed the same way (e.g. status/check_suite/pull_request family, all inheriting `Handler#repository_name`) are equally exposed; some of these mutate commit status/state used by Shipit's deploy-safety and continuous-delivery gating, which could enable an unauthorized deploy if a forged event satisfies a required check for a victim commit — I could not fully trace the continuous-delivery gating code in this session to confirm this secondary path, so it should be verified separately.

### Likelihood Explanation
Requires only: (1) a Shipit deployment configured for multiple GitHub organizations (documented supported configuration), and (2) the attacker administering their own low-privilege organization's GitHub App on that instance — no access to the victim's org, no Shipit account, no `ApiClient` token, and no access to the victim's `webhook_secret`. The webhook endpoint is unauthenticated by design (relies solely on HMAC), and the two fields used for secret-selection vs. routing are never cross-checked, so exploitation only requires crafting a JSON body and computing an HMAC with a secret the attacker already legitimately possesses.

### Recommendation
After determining `repository_owner` in `verify_signature`, re-derive the owner from `repository.full_name` (and/or `organization.login`) and reject the request (422) unless they match the verified organization. Equivalently, thread the verified organization through to `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params, verified_organization: repository_owner) }` and have `Handler#repository_name`/`Repository.from_github_repo_name` refuse to resolve a repository whose owner differs from the organization whose secret validated the signature.

### Proof of Concept
1. On a Shipit instance configured with multiple GitHub orgs (`attacker-org` and `victim-org`, each with distinct `webhook_secret`s), the attacker — who legitimately administers `attacker-org`'s GitHub App — knows `attacker-org`'s `webhook_secret`.
2. Attacker builds a JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(attacker-org's webhook_secret, raw_body)`.
4. Attacker sends `POST /github/webhooks` with headers `X-Github-Event: push` and the computed signature.
5. `verify_signature` selects `Shipit.github(organization: "attacker-org")`, verification succeeds (`app/controllers/shipit/webhooks_controller.rb:24-30`).
6. `PushHandler` resolves `Repository.from_github_repo_name("victim-org/victim-repo")` and calls `sync_github` on the victim's stack (`app/models/shipit/webhooks/handlers/push_handler.rb:12-17`, `app/models/shipit/webhooks/handlers/handler.rb:32-38`) — an action the attacker was never authorized to trigger for `victim-org`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
