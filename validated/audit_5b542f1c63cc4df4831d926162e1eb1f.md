### Title
Cross-tenant commit status mutation via unscoped `Commit.where(sha:)` in `StatusHandler#process` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits solely by `sha`, with no `stack_id`/repository scoping, then calls `create_status_from_github!` on every match. Because Git SHAs are not globally unique to a repository (identical squash/no-op/vendor-bump/merge-base commits can exist verbatim across unrelated repositories tracked by different Shipit stacks), a single signed webhook from one repository can mutate commit statuses belonging to other, unrelated stacks/tenants.

### Finding Description
The intended binding is: `{Commit rows mutated by a status webhook}` == `{Commit rows belonging to Repository/Stack that authenticated that webhook}`. In code, that equality is never enforced.

Path: `Shipit::WebhooksController#create` parses the raw JSON body and dispatches to `Shipit::Webhooks.for_event(event)` handlers after `verify_signature` [1](#0-0) . `verify_signature` resolves `Shipit.github(organization: repository_owner)` from `params.dig('repository','owner','login')` and validates the HMAC signature against that organization's webhook secret [2](#0-1) . This proves the payload came from GitHub for *some* repository owned by that org — it does not constrain which `sha` values the handler is allowed to touch, and it says nothing about other orgs' stacks.

`StatusHandler#process` then executes:
```ruby
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
``` [3](#0-2) 

This query has no `stack_id` or repository filter at all. Note that `Handler` (the base class) already defines a `stacks` helper that scopes lookups to `Repository.from_github_repo_name(repository_name)&.stacks` [4](#0-3) , demonstrating that repository-scoped lookup is the established pattern elsewhere in this codebase — `StatusHandler` simply does not use it.

`Commit#create_status_from_github!` then writes a `Status` record and, via `add_status`, can emit `Hook.emit(:commit_status, ...)` / `Hook.emit(:deployable_status, ...)` and call `stack.schedule_merges` for whichever stack the matched commit belongs to [5](#0-4) [6](#0-5) . Since `deployable?`/`blocked?`/continuous delivery scheduling depend on commit status [7](#0-6) [8](#0-7) , an attacker-controlled status webhook can flip deploy-blocking state on stacks it has no relationship to.

Attack: attacker owns/administers repository A (part of org X, so they can install a webhook and GitHub will validly sign a `status` event for org X's secret). They pick a `sha` that is known (via public GitHub search/mirroring) to also exist as an identical commit in unrelated Shipit-tracked stacks B (org Y) and C (org Z) — e.g. a shared open-source merge base, a squashed no-op commit, or a vendored dependency bump. They trigger (or forge, within their own repo's legitimate signing capability) a `status` webhook with that `sha` and `state: success` (or `failure`). `verify_signature` passes because the signature matches org X's secret for a payload whose `repository.owner.login` is X. `StatusHandler` then matches `Commit.where(sha: <that sha>)` across all stacks, including B's and C's `Commit` rows, and writes new `Status` rows and triggers hooks/merge scheduling for those unrelated stacks.

None of the existing guards prevent this: `verify_signature` authenticates *who sent* the webhook and for which org's secret, not *which stack's data may be touched*; `drop_unhandled_event` only filters event types; the `ExplicitParameters` schema in `StatusHandler.params` only validates the payload shape (`sha`, `state`, etc.), not repository ownership [9](#0-8) ; there is no `require_permission!`/`User#authorized?` check in the webhook path at all since this is an unauthenticated machine-to-machine endpoint.

### Impact Explanation
A single unprivileged POST (signed only for the attacker's own org) causes writes (`Status` records, `Hook.emit(:commit_status/:deployable_status)`, `stack.schedule_merges`) against `Commit`/`Stack` rows belonging to arbitrary unrelated repositories, provided a colliding SHA exists — this is a cross-tenant record mutation from a payload authenticated for a different repository, matching the "payload for one repository mutating another's stack, commit ... " Critical category. Blast radius is every stack that happens to share the SHA (potentially many, given common merge-base/vendor-bump commits), all mutated simultaneously by one request.

### Likelihood Explanation
Preconditions: attacker needs a repository within some GitHub org that is onboarded to this Shipit instance (so `verify_signature` succeeds for a known org secret) and needs a SHA value that also exists verbatim in another tracked stack's commit history — feasible in practice for squash-merge no-op commits, common upstream merge bases in forks, or automated dependency-bump commits that are frequently identical byte-for-byte across many repos. No secrets, sessions, or elevated roles are required beyond controlling one already-onboarded repository/webhook. This is fully repeatable against any repository sharing a colliding SHA, at attacker's discretion.

### Recommendation
Scope the lookup to the repository that authenticated the webhook, mirroring the `stacks` helper already present in `Handler`: e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` or `Commit.where(sha: params.sha, stack_id: stacks.select(:id))` instead of unscoped `Commit.where(sha: params.sha)`.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb
test "status webhook only updates commits belonging to the authenticated repository" do
  stack_a = shipit_stacks(:shipit) # repo org/A
  stack_b = create(:stack, repository: create(:repository, owner: 'unrelated-org', name: 'B'))
  stack_c = create(:stack, repository: create(:repository, owner: 'another-org', name: 'C'))

  shared_sha = '0123456789abcdef0123456789abcdef01234567'
  commit_a = create(:commit, stack: stack_a, sha: shared_sha)
  commit_b = create(:commit, stack: stack_b, sha: shared_sha)
  commit_c = create(:commit, stack: stack_c, sha: shared_sha)

  payload = {
    'repository' => { 'full_name' => stack_a.github_repo_name, 'owner' => { 'login' => stack_a.repository.owner } },
    'sha' => shared_sha,
    'state' => 'success',
    'context' => 'ci',
  }

  Shipit::Webhooks::Handlers::StatusHandler.call(payload)

  assert commit_a.reload.statuses.any?, "expected authenticated repo's commit to be updated"
  # Broken binding under current code: these also get mutated despite belonging to unrelated repos/orgs
  assert commit_b.reload.statuses.none?, "commit for unrelated stack B must NOT be mutated"
  assert commit_c.reload.statuses.none?, "commit for unrelated stack C must NOT be mutated"
end
```
Under the current implementation this test fails on the `commit_b`/`commit_c` assertions, demonstrating the unscoped cross-tenant write.

    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
