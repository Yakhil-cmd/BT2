### Title
Api::CCMenuController#stack bypasses ApiClient stack_id scoping - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Api::CCMenuController` overrides the `stack` lookup method to resolve `params[:stack_id]` directly via `Stack.from_param!`, instead of using `Api::BaseController#stack`/`#stacks`, which is the only place that enforces `current_api_client.stack_id == resolved_stack.id`. As a result, any token explicitly scoped by an operator to a single stack can be used to read CCMenu status XML for any other stack.

### Finding Description
The intended binding is: for any token with `current_api_client.stack_id` set (not nil), every stack-scoped read must satisfy `current_api_client.stack_id == stack.id`. `Api::BaseController` implements this correctly: [2](#0-1) 

`stacks` restricts the queryable set to `Stack.where(id: current_api_client.stack_id)` when the client has a `stack_id`, and `stack` resolves `params[:stack_id]` against that restricted set with `from_param!`, raising `RecordNotFound` (→ 404) if the id doesn't match.

However, `Api::CCMenuController` defines its own private `stack` method that shadows the base one and never consults `current_api_client` at all: [3](#0-2) 

`require_permission :read, :stack` only calls `current_api_client.check_permissions!('read', 'stack')`, which checks the string `"read:stack"` is present in the token's `permissions` array — it carries no notion of *which* stack, so it does not catch this: [4](#0-3) 

Attacker/operator flow: an operator scopes a token to Stack A by creating an `ApiClient` with `stack: stack_a` via the normal `/api_clients` flow (any flow that sets `stack_id` on the record, not just `CCMenuUrlController`). The holder of that token then sends `GET /api/stacks/<stack_b-owner>/<stack_b-name>/<stack_b-env>/ccmenu?token=<token>` (or with the token via HTTP Basic auth, per `authenticate_api_client` override at lines 33-36). `CCMenuController#stack` resolves Stack B unconditionally, `show` renders Stack B's latest deploy status.

Existing guards that fail to prevent this: `require_permission!` (only checks the permission string, not stack identity); `authenticate_api_client` (only verifies the token signature/existence, not stack scope); there is no `ExplicitParameters` schema or model validation involved for `stack_id`. The one enforcement point (`BaseController#stacks`) is simply never called by this controller.

### Impact Explanation
An attacker holding a token deliberately scoped to Stack A can read build/deploy status (lock state, last build status/label/time, web URL) for any other stack in the Shipit instance, including stacks belonging to entirely different repositories/tenants. This is an unauthenticated-for-that-resource read of stack state — matching the High severity category ("unauthenticated read of stack state"). It's trivially repeatable against arbitrary `stack_id` path values with a single GET request per stack, and it directly defeats the administrative intent of scoped tokens (least privilege), which is the entire security property `stack_id` scoping exists to provide.

### Likelihood Explanation
Preconditions are minimal and normal: any Shipit deployment where an operator issues a stack-scoped `ApiClient` (a documented, standard configuration) is affected. The attacker only needs possession of one such legitimately-scoped token (e.g., one distributed to a CI dashboard or CCMenu tray app for Stack A) and knowledge/guessing of another stack's owner/name/environment path segment (stack path components are often predictable or discoverable). No secrets, sessions, or elevated roles are needed beyond the token itself. The exploit is a single unauthenticated-style HTTP GET, fully repeatable.

### Recommendation
Remove the private `stack` override in `Api::CCMenuController` (and the duplicate logic) so it inherits `Api::BaseController#stack`, which resolves against the `stacks` scope (`Stack.where(id: current_api_client.stack_id)` when applicable). This restores the `current_api_client.stack_id == stack.id` binding for this endpoint, returning 404 for out-of-scope stacks.
