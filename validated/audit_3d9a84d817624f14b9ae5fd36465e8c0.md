### Title
Webhook signature verification is scoped to an attacker-controlled organization field, while the acted-upon repository/stack comes from a different, unverified payload field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks *which* GitHub App's `webhook_secret` to validate the incoming HMAC against by reading the organization name straight out of the untrusted JSON payload (`repository.owner.login` or `organization.login`), then hands the *entire raw payload* — including a separate `repository.full_name` field — to the event handlers, which use that field to resolve the `Stack`/`Repository` to act on. The field used to select the trust anchor for verification and the field used to decide what gets written/synced are not the same, and there is no check binding them together.

### Finding Description
`Shipit::WebhooksController#verify_signature` does: [1](#0-0) 
selecting `github_app = Shipit.github(organization: repository_owner)`, where: [2](#0-1) 
`repository_owner` is read directly from the JSON body (`params.dig('repository','owner','login')` or `params.dig('organization','login')`) — fields fully controlled by whoever sends the request, before any signature has been checked.

`Shipit.github(organization:)` resolves a distinct `GitHubApp` (and thus a distinct `webhook_secret`) per configured organization, as supported by the documented multi-tenant "Using Multiple Github Applications" setup: [3](#0-2) 

Crucially, `GitHubApp#verify_webhook_signature` treats a blank/unconfigured secret as automatically verified: [4](#0-3) 
`return true unless webhook_secret`. The setup docs explicitly mark the webhook secret as optional per organization: [5](#0-4) 

Once `verify_signature` passes, `#create` dispatches the raw parsed payload to handlers without re-checking any relationship between the organization that was used to select/verify the secret and the actual `repository.full_name` the handler will act on: [6](#0-5) 

Handlers such as `PushHandler`, `StatusHandler`, and the base `Handler#stacks`/`repository_name` resolve the target purely from `payload.dig('repository', 'full_name')`: [7](#0-6) [8](#0-7) 

This is the exact analog of the reported `VaultFactory`/`Controller` bug: the equality that should hold is
`organization whose secret verified the request == organization that owns the repository being written to`,
but nothing in the code enforces `repository.full_name`'s owner segment to match `repository_owner`/the organization resolved for verification. `VaultFactory.changeController` set a `controller` without checking `controller.vaultFactory() == address(this)`; here, `verify_signature` accepts a payload based on one organization's key while the handlers write to whatever repository the same payload names, with no cross-check.

### Impact Explanation
In a multi-org Shipit deployment (the documented "Using Multiple Github Applications" configuration), any tenant organization whose GitHub App has no `webhook_secret` configured (an explicitly supported/optional setting) — or any tenant that knows its own organization's secret — can send a forged webhook whose `repository.owner.login`/`organization.login` names *that* organization (satisfying/bypassing verification) while `repository.full_name` names a **different** organization's repository that also has a Stack configured in the same Shipit instance. Because handler logic keys purely off `repository.full_name`, this lets that party:
- Trigger `GithubSyncJob` for another tenant's stack via a forged `push` event (`PushHandler`), potentially cascading into an unauthorized deploy for `continuous_deployment`-enabled stacks.
- Post arbitrary commit `status` records for another tenant's commits (`StatusHandler`).
- Trigger `RefreshCheckRunsJob`/other cross-repo actions for stacks they do not own.

This falls under "an unauthorized deploy" / cross-tenant-write impact, matching the High/Critical impact categories for this scan (unauthorized deploy, cross-repository writes).

### Likelihood Explanation
Requires a multi-organization Shipit deployment where at least one configured organization has no `webhook_secret` (explicitly documented as optional) or is controlled by a different, less-trusted party than the target stack's owner. This is a real, documented configuration path (`docs/setup.md` "Using Multiple Github Applications"), not a purely theoretical single-org scenario. Single-organization deployments where the sole configured `webhook_secret` is always set are not exploitable this way, so likelihood depends on operator configuration choices, but the code contains no defense-in-depth check even when secrets are configured for every org.

### Recommendation
After successfully verifying the webhook signature against the organization resolved from the payload, re-validate that the acted-upon field(s) — `repository.full_name`'s owner (or `organization.login` for org-level events) — match the organization that was used to select/verify the webhook secret, mirroring the same-entity check pattern the report recommends adopting from `VaultFactory.createNewMarket`. Additionally, consider making `webhook_secret` mandatory (or refusing organizations without one when more than one GitHub App/organization is configured) instead of silently treating an absent secret as "verified."

### Proof of Concept
1. Configure Shipit with two organizations per the multi-app setup (`OrgA` with no `webhook_secret`, `OrgB` with a Stack for `OrgB/target-repo`).
2. Send a POST to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "OrgA" },
    "full_name": "OrgB/target-repo"
  }
}
```
3. `verify_signature` resolves `repository_owner` = `"OrgA"`, selects `OrgA`'s `GitHubApp`, and since `OrgA.webhook_secret` is blank, `verify_webhook_signature` returns `true` unconditionally — no valid signature is needed at all.
4. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("OrgB/target-repo")` and calls `stack.sync_github(expected_head_sha: "<attacker-chosen sha>")`, queuing a `GithubSyncJob` for a stack the attacker does not own, purely from the two mismatched fields in one forged payload.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
