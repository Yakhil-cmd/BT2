### Title
Route-controlled venue can escalate the caller's root authorization into an unrelated wallet-token transfer - (File: contracts/controller/src/strategies/swap.rs)

### Summary

`swap_collateral` and the other controller strategy entrypoints forward caller-supplied route bytes to the configured swap router without constraining the pool contracts that the route can name. The controller only authorizes its own exact input transfer to the router, but the caller's root `require_auth` remains the authorization context for nested contract calls. A malicious venue contract reached through a valid route can therefore request `token.transfer(victim, attacker, amount)` for an unrelated wallet token. Simulation records that transfer as a child of the victim's controller authorization; if the resulting authorization tree is signed, the unrelated transfer executes.

### Finding Description

`swap_collateral` authenticates the account owner or delegate, withdraws the selected collateral, and forwards the supplied swap payload to `withdraw_and_swap_from_supply`. [1](#0-0) 

The swap helper creates only a controller-scoped invoker authorization for `token_in.transfer(controller, router, amount_in)` and then invokes `execute_strategy(controller, amount_in, swap)`. [2](#0-1) 

The router authenticates `sender`—the controller in this path—and decodes the caller-provided program, whose asset registry supplies each hop's `pool`, `token_in`, and `token_out` addresses. [3](#0-2) [4](#0-3) 

The venue dispatcher does not check that `hop.pool` belongs to an allowlist; it dispatches the supplied address to the selected venue adapter. [5](#0-4)  For example, the Sushi adapter invokes `token0`, `token1`, `get_oracle_hints`, and finally `swap` on that payload-controlled address. [6](#0-5) 

Because these are ordinary nested contract calls, malicious venue code can call an unrelated token's `transfer(victim, attacker, amount)`. The Soroban authorization model attaches that requested invocation to the victim's existing authorization tree rather than limiting it to the controller's exact router grant. The repository's focused test demonstrates that simulation records such a rogue transfer beneath `swap_collateral`, that an honest root-only tree rejects it, and that signing the simulated poisoned tree permits it. [7](#0-6) [8](#0-7) 

This is analogous to forwarding first-proxy credentials to a second proxy: the caller authenticated the lending operation and intended to expose only the routed collateral flow, while an untrusted second destination can request an additional spend of unrelated wallet assets under that same authorization context.

### Impact Explanation

A successful route can transfer arbitrary amounts of any token held by the caller, including tokens never supplied to or listed by the lending protocol. The malicious venue can still provide a positive output and satisfy the router's measured-spend checks, allowing the lending operation itself to complete normally while the unrelated wallet-token transfer succeeds. [9](#0-8) 

This is theft of user funds. The demonstrated test transfers the caller's entire unrelated wallet balance to an attacker while the requested collateral swap also completes. [10](#0-9) 

### Likelihood Explanation

The attack requires the victim to execute a route containing an attacker-controlled venue and to sign the authorization tree produced by simulation. No privileged role, leaked key, upgrade, oracle manipulation, or protocol parameter change is required. [11](#0-10) 

The requirement that the poisoned child invocation appear in the signed tree limits exploitability, since an honest client can detect and reject it. However, the child is nested under a legitimate `swap_collateral` invocation and may be non-obvious to clients that present only the top-level operation or expected input transfer. [12](#0-11) 

### Recommendation

Restrict strategy hops to governance-approved venue contract addresses, or bind each supported venue type to a separately validated pool registry. The route decoder should treat `pool` as a venue identity rather than accepting an arbitrary contract address from the generic asset registry. [13](#0-12) 

Additionally, expose an explicit authorization-tree policy for strategy transactions: a legitimate controller strategy should never contain a caller token-transfer child unrelated to the requested input pull. Clients should reject any simulated `swap_collateral`, `swap_debt`, `multiply`, or `repay_debt_with_collateral` authorization tree containing such a child. [14](#0-13) 

### Proof of Concept

1. The attacker deploys a contract implementing the selected venue's pool ABI. For the Sushi path, it returns the route's `token_in` and `token_out` from `token0`/`token1`, returns acceptable oracle hints, and implements `swap`. [6](#0-5) 

2. In `swap`, the malicious contract calls `token::Client::new(unrelated_token).transfer(victim, attacker, victim_balance)`. It then performs enough token movement to satisfy the router's exact-input-spend and positive-output checks. [9](#0-8) 

3. The attacker encodes a strategy route whose hop names the malicious contract as `pool`, with valid distinct input and output tokens and a positive `min_out`. The victim invokes `swap_collateral(caller=victim, account_id, current, amount, new, swap)` with those route bytes. [15](#0-14) 

4. During execution, the controller authorizes only its own exact input transfer to the configured router, then invokes the router with the opaque route bytes. [11](#0-10) 

5. Simulation records the malicious pool's unrelated `transfer(victim, attacker, amount)` as a child invocation beneath the victim's `swap_collateral` authorization. [16](#0-15) 

6. If the victim signs that tree, the malicious transfer succeeds alongside the otherwise valid collateral swap. The repository test demonstrates the full balance moving to the attacker while the swapped collateral is deposited. [17](#0-16)

#[test]
fn simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry() {
    let s = Scene::new();
    let route = s.route_through_pool_stealing(WALLET_BALANCE);

    // `simulateTransaction` runs recording mode with non-root auth disabled.
    s.t.env.mock_all_auths();
    s.try_swap(&route)
        .expect("recording mode accepts the route");
    let recorded = s.t.env.auths();
    std::println!("recorded auth tree = {recorded:#?}");

    let stolen_transfer = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.wallet_token.clone(),
            symbol_short!("transfer"),
            (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),
        )),
        sub_invocations: std::vec![],
    };
    let poisoned_root = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.t.controller.clone(),
            Symbol::new(&s.t.env, "swap_collateral"),
            s.swap_args(&route),
        )),
        sub_invocations: std::vec![stolen_transfer],
    };
    assert_eq!(recorded, std::vec![(s.alice.clone(), poisoned_root)]);

    assert_eq!(s.wallet(&s.alice), 0);
    assert_eq!(s.wallet(&s.attacker), WALLET_BALANCE);
    assert_eq!(s.t.supply_balance_raw(ALICE, "ETH"), FAIR_OUT_ETH);
}

#[test]
fn enforced_auth_moves_the_wallet_token_only_when_the_signed_tree_lists_the_rogue_transfer() {
    let s = Scene::new();

    // Control: a pool that touches nothing passes with the honest root-only tree.
    let benign = s.route_through_pool_stealing(0);
    s.try_swap_with_signed_tree(&benign, &[])
        .expect("the honest tree authorizes an honest route");
    assert_eq!(s.wallet(&s.alice), WALLET_BALANCE);

    // Rogue pool, honest tree: the host refuses the transfer and the whole call rolls back.
    s.t.env.mock_all_auths_allowing_non_root_auth();
    let rogue = s.route_through_pool_stealing(WALLET_BALANCE);
    let usdc_before = s.t.supply_balance_raw(ALICE, "USDC");
    let refused = s
        .try_swap_with_signed_tree(&rogue, &[])
        .expect_err("a transfer outside the signed tree is unauthorized");
    std::println!("rogue transfer under the honest tree = {refused:?}");
    assert!(
        refused.is_type(ScErrorType::Auth) || refused.is_type(ScErrorType::Context),
        "expected a host auth failure, got {refused:?}"
    );
    assert!(s
        .diagnostics()
        .contains("Unauthorized function call for address"));
    assert_eq!(s.wallet(&s.alice), WALLET_BALANCE);
    assert_eq!(s.wallet(&s.attacker), 0);
    assert_eq!(s.t.supply_balance_raw(ALICE, "USDC"), usdc_before);

    // Same route, with the tree that simulation returned.
    let stolen_transfer = MockAuthInvoke {
        contract: &s.wallet_token,
        fn_name: "transfer",
        args: (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),
        sub_invokes: &[],
    };
    s.try_swap_with_signed_tree(&rogue, core::slice::from_ref(&stolen_transfer))
        .expect("the poisoned tree authorizes the rogue transfer");
    assert_eq!(s.wallet(&s.alice), 0);
    assert_eq!(s.wallet(&s.attacker), WALLET_BALANCE);
}
