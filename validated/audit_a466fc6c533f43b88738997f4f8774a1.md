Confirmed multi-org config is a supported, documented deployment shape (`test/dummy/config/secrets_double_github_app.yml` shows `github: {OrgOne: {webhook_secret: ...}, OrgTwo: {webhook_secret: ...}}`), and `Shipit.github(organization:)` in `lib/shipit.rb` looks up a **separate app/secret per organization**. This confirms the binding-mismatch analog is reachable in-scope.

### Title
Webhook signature is verified against the org derived from `repository.owner.login`, while stack-mutating handlers act on the org/repo derived from the unauthenticated `repository.full_name` field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to use for HMAC verification based on `params.dig('repository','owner','login')` (or `organization.login`), then verifies the whole raw body against that org's secret [1](#0-0) , using `repository_owner` purely as a lookup key [2](#0-1) . However, once the signature is accepted, every stack-mutating handler (`PushHandler`, `Handler#stacks`, and all `PullRequest::*Handler`s) resolves the repository to act on from a **different** field in the same payload: `repository.full_name`, via `Repository.from_github_repo_name` [3](#0-2) [4](#0-3) . `Repository.from_github_repo_name` simply splits the string on `/` and looks up any locally-registered repository by owner/name, with no cross-check against the organization whose secret was actually used to authenticate the request [5](#0-4) .

### Finding Description
The trust binding that should hold is: **organization whose secret validated the signature == organization owning the repository the handler mutates**. Nothing in the code enforces this equality.

- `verify_signature` computes `repository_owner` only to pick a `GitHubApp` config/secret: `Shipit.github(organization: repository_owner)` [6](#0-5) .
- `Shipit.github` looks up per-organization config (`github_app_config(organization)`), each with its own independent `webhook_secret` in supported multi-org deployments [7](#0-6) .
- After verification, `Webhooks.for_event(event).each { |handler| handler.call(params) }` passes the **entire raw parsed payload** to handlers [8](#0-7) , and handlers never re-read `repository.owner.login`; they only use `repository.full_name` to find the target `Repository`/`Stack` [3](#0-2) .
- Because `repository.owner.login` and `repository.full_name` are two independent, attacker-writable JSON fields inside the same HTTP body, an attacker who knows (or can obtain, e.g., by being a legitimate maintainer with webhook access on one, low-value repo in "OrgA") the `webhook_secret` for OrgA can craft a payload where `repository.owner.login = "OrgA"` (so the HMAC verifies against OrgA's secret) but `repository.full_name = "OrgB/high-value-repo"`. The signature check passes because it only validates the byte-for-byte HMAC of the raw body against OrgA's secret; it never validates that the *content* of the body is internally consistent or that OrgB's stacks may legitimately be triggered by an OrgA credential.
- This forged payload reaches handlers such as `PushHandler`, which will call `stack.sync_github(expected_head_sha: params.after)` for any stack under `OrgB/high-value-repo` matching the forged branch/SHA [9](#0-8) , or PR handlers which can archive/unarchive review stacks belonging to a completely different, non-owned repository [10](#0-9) .

This is the direct analog of the smart-contract bug class: the code checks one identity/address (`repository_owner`, used as the access-control key to select the trusted secret) but then acts on a different, unvalidated identity/address (`repository.full_name`) taken from the same untrusted input, exactly matching the "organization that authenticated versus the repository that is written" binding called out in scope.

### Impact Explanation
This breaks the equality `organization(secret used for HMAC) == organization(repository/stack acted upon)`, enabling a party who only possesses one organization's webhook secret to trigger `GithubSyncJob`, and archive/unarchive/label-driven review-stack lifecycle actions, against stacks belonging to an entirely different, unrelated organization/repository registered in the same Shipit instance. This is a cross-repository/cross-organization write triggered by webhook events using another org's trust material, matching the in-scope "cross-repository writes" Critical impact category.

### Likelihood Explanation
Exploitability depends entirely on the attacker already possessing (or being able to register) at least one organization's `webhook_secret` in a multi-tenant Shipit deployment — a configuration this engine explicitly documents and ships fixtures for (`test/dummy/config/secrets_double_github_app.yml`). Given that webhook secrets are typically per-GitHub-App/organization and often shared by less-privileged repo/org admins (not full Shipit operators), this is a realistic scenario for any Shipit instance serving more than one organization, without requiring a Shipit session, API token, or the GitHub App private key.

### Recommendation
In `WebhooksController`/`Shipit::Webhooks::Handlers::Handler`, after verifying the signature for `repository_owner`, re-derive and enforce that the organization portion of `repository.full_name` (and `organization.login` when present) matches the `repository_owner` used to select the verifying secret before dispatching to handlers. Reject (422) any payload where these values diverge.

### Proof of Concept
1. Attacker has legitimate access to configure/read the webhook secret for `OrgA` (e.g., is an admin of some trivial repo under `OrgA` registered in the shared Shipit instance).
2. Attacker crafts a `push` webhook JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker chosen sha for OrgB/high-value-repo>",
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/high-value-repo" }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(OrgA_webhook_secret, body)` and POSTs to `/github/webhooks`.
4. `verify_signature` resolves `Shipit.github(organization: "OrgA")` and confirms the HMAC — request passes [1](#0-0) .
5. `PushHandler#process` looks up stacks via `repository.full_name = "OrgB/high-value-repo"` [3](#0-2)  and triggers `stack.sync_github(expected_head_sha: ...)` for `OrgB`'s stack, even though only `OrgA`'s secret was used to authenticate the request [9](#0-8) .

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
