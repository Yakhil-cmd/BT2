### Title
TOCTOU race in multisig wallet rejection allows deletion of an already-approved wallet - ([File: wallet_defined_by_keys.js])

### Summary
`deleteWallet()` in `wallet_defined_by_keys.js` reads a cosigner's `approval_date` in one query, then — if it was `NULL` — deletes the `wallets`, `extended_pubkeys`, and `wallet_signing_paths` rows in a separate, later batch of queries with no surrounding transaction/lock. Between the read and the delete, an incoming `my_xpubkey`/approval message for the same wallet can be processed concurrently (via `addDeviceXPubKey` → `checkAndFullyApproveWallet` → `checkAndFinalizeWallet`), setting `approval_date`/`full_approval_date`/`ready_date` on the very rows that are about to be deleted. This mirrors the lnd `pruneLinkNode`/`MarkChanFullyClosed` bug: a check ("no approval yet") and the destructive action ("delete wallet") happen in separate, non-atomic operations, so the invariant "wallet exists iff not yet approved/finalized" can be violated.

### Finding Description [1](#0-0) 
`deleteWallet` is invoked "from network, without user interaction" when a cosigner declines wallet creation:
- Query 1: `SELECT approval_date FROM extended_pubkeys WHERE wallet=? AND device_address=?`
- If `approval_date` is falsy, it proceeds to a second `SELECT device_address FROM extended_pubkeys WHERE wallet=?`, then issues a batch of `DELETE FROM extended_pubkeys/wallets/wallet_signing_paths` queries via `async.series`.

Meanwhile, `addDeviceXPubKey` (also "called from network, without user interaction") can run concurrently for the same wallet and rejecting device_address: [2](#0-1) 
It sets `extended_pubkeys.approval_date` for that device and immediately triggers `checkAndFullyApproveWallet`, which can set `wallets.full_approval_date` and `wallet_signing_paths`/`wallets.ready_date` via `checkAndFinalizeWallet`: [3](#0-2) [4](#0-3) 

None of these operations are wrapped in a single atomic transaction or protected by a mutex lock (unlike other write paths in this codebase that use `mutex.lock`/`db.executeInTransaction`), so the read-then-delete in `deleteWallet` and the concurrent read-then-update in `addDeviceXPubKey`/`checkAndFullyApproveWallet` can interleave: the `SELECT approval_date` in `deleteWallet` observes `NULL`, then before the `DELETE` statements run, the approval/finalization path commits its updates, and the wallet is deleted anyway.

### Impact Explanation
A wallet the local device and other cosigners just finished approving (and possibly marked `ready_date`, i.e. usable for a shared multisig address) can be wiped from the `wallets`, `extended_pubkeys`, and `wallet_signing_paths` tables purely due to timing of two device messages. This causes loss of the local record of a completed multisig wallet definition — including derived-address/signing-path bookkeping — while other cosigners (and any already-issued/expected shared address) still believe the wallet is valid and fully approved, leading to inconsistent wallet state across devices and effective loss of access to that wallet's addresses/signing data on the affected device (fund-management/availability impact for a shared wallet). This is triggered by an ordinary paired device message pair (`create_new_wallet`/`my_xpubkey` approvals racing with a rejection message), which is within the "paired device" reachable class allowed by scope.

### Likelihood Explanation
Requires two race conditions to line up: a cosigner sending a rejection (or a duplicate/retransmitted rejection) roughly at the same time another cosigner's `my_xpubkey` message completes approval for the same wallet. Message delivery timing between paired devices (including retries/duplicate delivery, which the P2P layer does not strictly prevent) makes this plausible but not trivially reproducible on demand; it depends on network/message scheduling rather than attacker-controlled single-shot input.

### Recommendation
Wrap the check-and-delete in `deleteWallet` and the check-and-update logic in `addDeviceXPubKey`/`checkAndFullyApproveWallet`/`checkAndFinalizeWallet` in a single atomic transaction (`db.executeInTransaction`) guarded by a `mutex.lock(['wallet-' + wallet])`, and re-verify (inside that same transaction) that `approval_date`/`full_approval_date` is still unset immediately before executing the `DELETE` statements, analogous to the double-check fix applied to `pruneLinkNode` in the referenced lnd commit.

### Proof of Concept
1. Two devices are cosigners of a not-yet-approved multisig wallet `W` (one entry in `extended_pubkeys` has `approval_date = NULL` for device `D`).
2. Device `D` sends `cancel_new_wallet` for `W`; the hub/local node begins processing `deleteWallet(W, D, ...)`, which executes the `SELECT approval_date ... WHERE wallet=W AND device_address=D` and finds it `NULL`.
3. Concurrently, the same device `D` (or a duplicate/retried in-flight message) also delivers `my_xpubkey` for `W`, invoking `addDeviceXPubKey` → sets `approval_date` for `D`, and — if all other cosigners already approved — `checkAndFullyApproveWallet` sets `full_approval_date`/finalizes the wallet before `deleteWallet`'s `DELETE` statements run.
4. `deleteWallet` proceeds to delete `wallets`, `extended_pubkeys`, and `wallet_signing_paths` rows for `W`, wiping the just-finalized wallet despite the invariant that a fully approved/finalized wallet should never be deleted.

Note: I was unable to trace the exact network-layer dispatch code in `wallet.js` that routes incoming `cancel_new_wallet`/`my_xpubkey` messages to `deleteWallet`/`addDeviceXPubKey` due to index/search limitations on that file's full contents; a Devin session with full file access would be needed to confirm there is no higher-level per-wallet mutex serializing these two message handlers before concluding the race is unmitigated end-to-end.

function checkAndFinalizeWallet(wallet, onDone){
	db.query("SELECT member_ready_date FROM wallets LEFT JOIN extended_pubkeys USING(wallet) WHERE wallets.wallet=?", [wallet], function(rows){
		if (rows.length === 0){ // wallet not created yet or already deleted

			return onDone ? onDone() : null;

			return onDone ? onDone() : null;
		db.query("UPDATE wallets SET ready_date="+db.getNow()+" WHERE wallet=? AND ready_date IS NULL", [wallet], function(){
			if (onDone)
				onDone();
			eventBus.emit('wallet_completed', wallet);
		});
	});
}

function checkAndFullyApproveWallet(wallet, onDone){
	db.query("SELECT approval_date FROM wallets LEFT JOIN extended_pubkeys USING(wallet) WHERE wallets.wallet=?", [wallet], function(rows){
		if (rows.length === 0) // wallet not created yet
			return onDone ? onDone() : null;
		if (rows.some(function(row){ return !row.approval_date; }))
			return onDone ? onDone() : null;
		db.query("UPDATE wallets SET full_approval_date="+db.getNow()+" WHERE wallet=? AND full_approval_date IS NULL", [wallet], function(){
			db.query(
				"UPDATE extended_pubkeys SET member_ready_date="+db.getNow()+" WHERE wallet=? AND device_address=?", 
				[wallet, device.getMyDeviceAddress()], 
				function(){
					db.query(
						"SELECT device_address FROM extended_pubkeys WHERE wallet=? AND device_address!=?", 
						[wallet, device.getMyDeviceAddress()], 
						function(rows){
							// let other members know that I've collected all necessary xpubkeys and ready to use this wallet
							rows.forEach(function(row){
								sendNotificationThatWalletFullyApproved(row.device_address, wallet);
							});
							checkAndFinalizeWallet(wallet, onDone);
						}
					);
				}
			);
		});
	});
}

function deleteWallet(wallet, rejector_device_address, onDone){
	db.query("SELECT approval_date FROM extended_pubkeys WHERE wallet=? AND device_address=?", [wallet, rejector_device_address], function(rows){
		if (rows.length === 0) // you are not a member device
			return onDone();
		if (rows[0].approval_date) // you've already approved this wallet, you can't change your mind
			return onDone();
		db.query("SELECT device_address FROM extended_pubkeys WHERE wallet=?", [wallet], function(rows){
			var arrMemberAddresses = rows.map(function(row){ return row.device_address; });
			var arrQueries = [];
			db.addQuery(arrQueries, "DELETE FROM extended_pubkeys WHERE wallet=?", [wallet]);
			db.addQuery(arrQueries, "DELETE FROM wallet_signing_paths WHERE wallet=?", [wallet]);
			db.addQuery(arrQueries, "DELETE FROM wallets WHERE wallet=?", [wallet]);
			// delete unused indirect correspondents
			db.addQuery(
				arrQueries, 
				"DELETE FROM correspondent_devices WHERE is_indirect=1 AND device_address IN(?) AND NOT EXISTS ( \n\
					SELECT * FROM extended_pubkeys WHERE extended_pubkeys.device_address=correspondent_devices.device_address \n\
				)", 
				[arrMemberAddresses]
			);
			async.series(arrQueries, function(){
				eventBus.emit('wallet_declined', wallet, rejector_device_address);
				onDone();
			});
		});
	});
}

function addDeviceXPubKey(wallet, device_address, xPubKey, onDone){
	db.query(
		"INSERT "+db.getIgnore()+" INTO extended_pubkeys (wallet, device_address) VALUES(?,?)",
		[wallet, device_address],
		function(){
			db.query(
				"UPDATE extended_pubkeys SET extended_pubkey=?, approval_date="+db.getNow()+" WHERE wallet=? AND device_address=?", 
				[xPubKey, wallet, device_address],
				function(){
					eventBus.emit('wallet_approved', wallet, device_address);
					checkAndFullyApproveWallet(wallet, onDone);
				}
			);
		}
	);
}
