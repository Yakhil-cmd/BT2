### Title
Stale stored account owner lets a seller retain spending authority after the position NFT is transferred - (File: contracts/controller/src/account.rs)

### Summary
The controller's account-spending gate, `require_owner_or_delegate`, compares the caller against `account.owner`, a field written once at account creation, while the actual source of truth for account ownership is the position NFT (`storage::account_owner` reads the live NFT `owner_of`). Because `position-nft::transfer` / `transfer_from` are stock OpenZeppelin `NonFungibleToken` methods that cannot call back into the controller to re-stamp `account.owner`, transferring the NFT leaves the stored owner pointing at the seller. The seller (and any still-active delegates granted by the seller) can then keep calling `withdraw`, `borrow`, `swap_collateral`, `repay_debt_with_collateral`, `swap_debt`, `multiply` and `flash_position` on the sold account.

### Finding Description
Analog to CVE-2025-41232 (a security annotation the framework fails to locate on certain methods, silently bypassing authorization): here the ownership "annotation" — `account.owner` — is present but describes an outdated owner on the post-transfer path, so the check enforces authority for the wrong principal.

- `create_account_with` sets `account.owner = owner` at mint time and nothing in the account record is ever re-written on NFT transfer (`contracts/controller/src/account.rs:64-70`).
- `require_owner_or_delegate` / `is_owner_or_delegate` resolve authority against that stored field and the delegate set keyed by it (`account.rs:115-140`).
- In contrast, `require_account_owner` deliberately reads the live NFT owner via `storage::account_owner` (`account.rs:143-148`), confirming the codebase knows NFT ownership, not the stored field, is authoritative.
- The NFT's `transfer`, `transfer_from`, `approve` and `approve_for_all` are pinned stock `contracttrait` methods (`scripts/permissionless_entrypoints.txt:103-114`, `scripts/check_access_control.py:135-154`); they perform only `from.require_auth`/`spender.require_auth` and a stock `Base::update`, so no controller write can resync `account.owner`. The declared justification even acknowledges delegation transfer semantics ("delegate grants from the previous owner go inactive"), which is not enforced on the `require_owner_or_delegate` path: delegates remain keyed under the stale `account.owner`, so `is_owner_or_delegate` still returns true for the seller and the seller's registered-manager delegates.
- Reachable mutating entrypoints gated only by this stale check include `process_withdraw` (`positions/supply.rs:150`), `process_borrow` (`positions/debt.rs:43`), `process_swap_debt` (`strategies/swap_debt.rs:48`), `process_repay_debt_with_collateral` (`strategies/repay_debt_with_collateral.rs:51`), and the `AccountGuard::Migrate`/`AccountGuard::Multiply` arms in `load_or_create_account` (`account.rs:101-109`).

### Impact Explanation
Theft of user funds. A seller lists or transfers the position NFT; the buyer receives the NFT and is recognized by `require_account_owner` as owner, but `withdraw`/`borrow` still accept the seller as `account.owner`. The seller (or a still-active delegate the buyer cannot revoke via `remove_delegate`, since that path requires `require_account_owner` on the *new* owner while delegates live under the old owner's key — note `remove_delegate` would revert for the buyer because delegates were stored under `old_owner`, leaving them permanently active) calls `controller::withdraw(account_id, withdrawals, to=Some(seller))`, draining all collateral within solvency limits, or `borrow` to push the account to the brink and leave the buyer with debt. Conversely, the legitimate buyer fails `require_owner_or_delegate` and cannot withdraw at all — permanent freezing of funds even absent malice.

### Likelihood Explanation
Any unprivileged address can trigger this with a single `position-nft::transfer`/`transfer_from` call — an explicitly in-scope entrypoint. No governance action, leaked key, or special market state is required; every account created via `supply`/`multiply`/`flash_position` carries the stale-owner latent condition from mint.

### Recommendation
Resolve authority from the live NFT owner on every spending path: have `require_owner_or_delegate`/`is_owner_or_delegate` call `storage::account_owner` (or `PositionNftClient::owner_of`) instead of the stored `account.owner`, and key the delegate set by the resolved live owner (or by `account_id` alone). Alternatively, delete `account.owner` from the stored `Account` struct entirely so no divergent copy can exist.

### Proof of Concept
1. Alice calls `controller::supply(0, spoke_id, [(usdc, 1000e7)])`; `load_or_create_account` mints NFT `account_id=N` with `account.owner = alice` and credits supply.
2. Alice sells the position: `position_nft.transfer(alice, bob, N)` — a stock method, passes `alice.require_auth`, emits no controller write.
3. Alice calls `controller::withdraw(N, [(usdc, 1000e7)], Some(alice))`. `process_withdraw` calls `require_owner_or_delegate(env, N, alice, &account.owner)`; `account.owner` still equals `alice`, so the check passes, the pool pays Alice, and solvency is re-proven against an account Alice no longer owns.
4. Bob's matching `withdraw` reverts at the same check because `account.owner != bob`, despite `PositionNftClient::owner_of(N) == bob` and `require_account_owner` recognizing Bob.

Caveat: if an unindexed helper re-stamps `account.owner` on transfer this collapses, but NFT transfer is a pinned stock OZ method that cannot invoke the controller, and no such sync path appears in the controller sources reviewed.
