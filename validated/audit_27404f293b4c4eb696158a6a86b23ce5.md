### Title
`pallet-asset-rewards` `reward_per_token` truncates to zero under attacker-forced frequent checkpointing, permanently starving stakers of rewards - (File: `substrate/frame/asset-rewards/src/lib.rs`)

### Summary
The Synthetix-style reward accumulator in `pallet-asset-rewards` computes `reward_per_token` increments using integer division scaled by a small constant `PRECISION_SCALING_FACTOR = 4096` [1](#0-0) . Because any signed account can permissionlessly trigger a pool-wide checkpoint update via `stake` (even with a trivial amount) [2](#0-1) , an attacker can force `update_pool_rewards` to run every block, splitting the natural multi-block reward accrual into many single-block floor-divisions. Due to the subadditivity of integer floor division, this can drive the "elapsed reward" fraction to `0` on every call when `reward_rate_per_block * 1 * 4096 < total_tokens_staked`, permanently blocking `reward_per_token_stored` from ever advancing for as long as the attacker keeps checkpointing every block — an exact structural analog of the BathBuddy `getReward`/`rewardPerToken` DoS.

### Finding Description
The reward math is:
```rust
Ok(pool_info.reward_per_token_stored.ensure_add(
    pool_info
        .reward_rate_per_block
        .ensure_mul(rewardable_blocks_elapsed.into())?
        .ensure_mul(PRECISION_SCALING_FACTOR.into())?
        .ensure_div(pool_info.total_tokens_staked)?,
)?)
``` [3](#0-2) 

`update_pool_rewards` persists `last_update_block = current_block` and `reward_per_token_stored = reward_per_token` every time it is invoked [4](#0-3) , and this is invoked from `stake`, `unstake`, and `harvest_rewards`, all of which are ordinary signed extrinsics operating on pool-global state (`Pools::<T>`) rather than per-caller isolated state [5](#0-4) [6](#0-5) .

`stake` has no minimum-amount check before calling `Self::update_pool_and_staker_rewards` and mutating the shared `pool_info` [2](#0-1) ; an attacker who is already a staker (or who stakes a minimal amount once) can call `stake(pool_id, 1)` in every block. Each call computes `rewardable_blocks_elapsed = 1`, so the pending increment is `floor(reward_rate_per_block * 1 * 4096 / total_tokens_staked)`. If `total_tokens_staked > reward_rate_per_block * 4096`, this per-block increment is `0`, and `reward_per_token_stored` never advances — exactly mirroring the BathBuddy issue where frequent `getReward` calls reset `lastUpdateTime` and drive `rewardPerToken`'s per-call delta to zero via rounding, blocking legitimate small (or here, any) stakers' `derive_rewards` from ever increasing:
```rust
Ok(staker_info
    .amount
    .ensure_mul(reward_per_token.ensure_sub(staker_info.reward_per_token_paid)?)?
    .ensure_div(PRECISION_SCALING_FACTOR.into())?
    .ensure_add(staker_info.rewards)?)
``` [7](#0-6) 

Without attacker interference, the same total elapsed blocks would eventually be checkpointed in a single call with a larger numerator, producing a non-zero floor result once enough blocks accumulate. By forcing single-block checkpoints, the attacker converts what should be one eventual non-zero floor division into many always-zero floor divisions, indefinitely starving `reward_per_token_stored` growth for every staker in the pool, not just small ones — a strictly stronger DoS than the original report because `PRECISION_SCALING_FACTOR` here is only `4096` rather than a high-precision `1e18`-style scaling used elsewhere in the codebase (e.g. nomination-pools' `FixedU128`), making the zero-rounding condition trivially reachable for realistically-sized pools.

### Impact Explanation
This is a genuine functional-DoS on reward distribution: legitimate stakers who call `harvest_rewards` (permitted for `caller == staker` at any time, or by anyone after `expiry_block`) will see `reward_per_token` computed by `reward_per_token()` never grow while the attacker checkpoints every block, so `derive_rewards` returns the same (or negligibly increasing) value indefinitely. Reward assets remain locked in the pool account, unclaimed, degrading the pallet's core function for as long as the attacker sustains one cheap `stake` extrinsic per block. This matches the classification and mechanics of the referenced BathBuddy High/Medium finding: no funds are stolen, but reward distribution functionality can be blocked for an indefinite period.

### Likelihood Explanation
The precondition (`total_tokens_staked * base_unit > reward_rate_per_block * 4096`) is easily satisfied for any pool with a modest total stake or a low-to-moderate `reward_rate_per_block`, which is a normal, non-privileged, admin-set configuration [8](#0-7) . The attacker needs no privileged role — only enough of the staked asset to call `stake` with a minimal, non-zero amount, and the willingness to submit one low-value extrinsic per block (or per few blocks) for the attack's duration. This is a real, unprivileged, permissionless-entry-point issue, not a theoretical concern.

### Recommendation
Avoid re-checkpointing more granularly than the accumulator's precision supports. Options: (1) increase `PRECISION_SCALING_FACTOR` to a much larger fixed-point base (e.g. `1e12`/`1e18`-scale, as used elsewhere in the codebase such as nomination-pools' `FixedU128` reward counter) so a single block's worth of reward cannot legitimately round to zero for realistic stake/rate ratios; (2) track fractional remainder/dust across checkpoints instead of discarding it on each call, so repeated checkpointing cannot lose more precision cumulatively than a single deferred checkpoint would; (3) rate-limit or decouple the pool-wide checkpoint update from unrelated low-value `stake` calls (e.g. require a minimum stake amount, or make checkpointing depend on elapsed blocks rather than call frequency).

### Proof of Concept
Not executed against a live network; this is a code-level derivation from the referenced source lines showing the reachable griefing condition. No test harness run was performed for this analysis — the claim rests on tracing `stake` → `update_pool_and_staker_rewards` → `update_pool_rewards`/`reward_per_token` and the floor-division arithmetic shown above. A concrete integration reproduction would set up a pool with `total_tokens_staked` large relative to `reward_rate_per_block * 4096`, have the attacker call `stake(pool_id, 1)` every block for N blocks, and assert that `Pools::<T>::get(pool_id).reward_per_token_stored` remains `0` (or far below the value it would reach with a single N-block-elapsed checkpoint), while a victim's `PoolStakers` `rewards` stays at `0` via `harvest_rewards`. This reproduction step was not executed in this session; a Devin session with repository access would be needed to write and run the FRAME test asserting the described precision-loss/zero-rounding condition.

		pub fn stake(origin: OriginFor<T>, pool_id: PoolId, amount: T::Balance) -> DispatchResult {
			let staker = ensure_signed(origin)?;

			// Always start by updating staker and pool rewards.
			let pool_info = Pools::<T>::get(pool_id).ok_or(Error::<T>::NonExistentPool)?;
			let staker_info = PoolStakers::<T>::get(pool_id, &staker).unwrap_or_default();
			let (mut pool_info, mut staker_info) =
				Self::update_pool_and_staker_rewards(&pool_info, &staker_info)?;

			T::AssetsFreezer::increase_frozen(
				pool_info.staked_asset_id.clone(),
				&FreezeReason::Staked.into(),
				&staker,
				amount,
			)?;

			// Update Pools.
			pool_info.total_tokens_staked.ensure_add_assign(amount)?;

			Pools::<T>::insert(pool_id, pool_info);

			// Update PoolStakers.
			staker_info.amount.ensure_add_assign(amount)?;
			PoolStakers::<T>::insert(pool_id, &staker, staker_info);

			// Emit event.
			Self::deposit_event(Event::Staked { staker, pool_id, amount });

			Ok(())
		}

		/// Derives the current reward per token for this pool.
		pub(super) fn reward_per_token(
			pool_info: &PoolInfoFor<T>,
		) -> Result<T::Balance, DispatchError> {
			if pool_info.total_tokens_staked.is_zero() {
				return Ok(pool_info.reward_per_token_stored);
			}

			let rewardable_blocks_elapsed: u32 =
				match Self::last_block_reward_applicable(pool_info.expiry_block)
					.ensure_sub(pool_info.last_update_block)?
					.try_into()
				{
					Ok(b) => b,
					Err(_) => return Err(Error::<T>::BlockNumberConversionError.into()),
				};

			Ok(pool_info.reward_per_token_stored.ensure_add(
				pool_info
					.reward_rate_per_block
					.ensure_mul(rewardable_blocks_elapsed.into())?
					.ensure_mul(PRECISION_SCALING_FACTOR.into())?
					.ensure_div(pool_info.total_tokens_staked)?,
			)?)
		}

	fn create_pool(
		creator: &T::AccountId,
		staked_asset_id: T::AssetId,
		reward_asset_id: T::AssetId,
		reward_rate_per_block: T::Balance,
		expiry: DispatchTime<BlockNumberFor<T>>,
		admin: &T::AccountId,
	) -> Result<PoolId, DispatchError> {
		// Ensure the assets exist.
		ensure!(T::Assets::asset_exists(staked_asset_id.clone()), Error::<T>::NonExistentAsset);
		ensure!(T::Assets::asset_exists(reward_asset_id.clone()), Error::<T>::NonExistentAsset);

		// Check the expiry block.
		let now = T::BlockNumberProvider::current_block_number();
		let expiry_block = expiry.evaluate(now);
		ensure!(expiry_block > now, Error::<T>::ExpiryBlockMustBeInTheFuture);

		let pool_id = NextPoolId::<T>::try_mutate(|id| -> Result<PoolId, DispatchError> {
			let current_id = *id;
			*id = id.ensure_add(1)?;
			Ok(current_id)
		})?;

		let footprint = Self::pool_creation_footprint();
		let cost = T::Consideration::new(creator, footprint)?;
		PoolCost::<T>::insert(pool_id, (creator.clone(), cost));

		// Create the pool.
		let pool = PoolInfoFor::<T> {
			staked_asset_id: staked_asset_id.clone(),
			reward_asset_id: reward_asset_id.clone(),
			reward_rate_per_block,
			total_tokens_staked: 0u32.into(),
			reward_per_token_stored: 0u32.into(),
			last_update_block: 0u32.into(),
			expiry_block,
			admin: admin.clone(),
			account: Self::pool_account_id(&pool_id),
		};

		// Insert it into storage.
		Pools::<T>::insert(pool_id, pool);

		// Emit created event.
		Self::deposit_event(Event::PoolCreated {
			creator: creator.clone(),
			pool_id,
			staked_asset_id,
			reward_asset_id,
			reward_rate_per_block,
			expiry_block,
			admin: admin.clone(),
		});

		Ok(pool_id)
	}
