### Title
Cross-organization membership webhook lets an attacker's own org strip a `Membership` row for a team belonging to a different organization - ([File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`MembershipHandler#process` deletes a `Membership` based solely on `params.team.id` and `params.member.login`, without ever checking that the organization whose secret verified the webhook (`params.organization.login`, used by `WebhooksController#verify_signature`) matches the `organization` column already stored on the `Team` record. An attacker who legitimately controls a webhook for their own (different) GitHub organization configured in Shipit can therefore send a validly-signed `membership`/`removed` event that deletes a `Membership` row belonging to a completely unrelated team/organization.

### Finding Description
The intended binding is: `webhook_verified_organization == team.organization` before mutating that team's memberships. In practice:

- `WebhooksController#verify_signature` computes `repository_owner` from the payload's `organization.login` (or `repository.owner.login`) and calls `Shipit.github(organization: repository_owner)` to fetch that organization's configured `webhook_secret`, then HMAC-verifies the raw body against it [1](#0-0) , [2](#0-1) . This only proves the request was signed by whatever organization the attacker put in the payload's `organization.login` field, i.e., the attacker's *own* organization (whose secret they legitimately know because they configured that org's webhook).
- `MembershipHandler#find_or_create_team!` looks a `Team` up **only by `github_id`** taken from `params.team.id`; the `organization` attribute is only ever set inside the `find_or_create_by!` block, i.e. only when the row is first created, and is never re-checked against `params.organization.login` on subsequent calls: [3](#0-2) .
- `process` then does `team.members.delete(member)` for `action == 'removed'` unconditionally: [4](#0-3) .

Because the team is resolved purely by the numeric GitHub team id (globally unique but not organization-scoped in this lookup) and `member` is resolved purely by login via `User.find_or_create_by_login!`, nothing ties the deletion to the organization that actually signed the request. An attacker who: (1) is an owner/admin of some organization `orgA` that is a recognized organization in Shipit's config (has its own `webhook_secret`, distinct from `Shipit.github_teams`), and (2) knows or can discover the numeric GitHub `team.id` of a victim team in a different org `orgB` (already synced into Shipit as a `Team` row with `organization: "orgB"`) and the victim's GitHub `login`, can send:

```
POST /webhooks
X-Github-Event: membership
X-Hub-Signature: sha1=<HMAC using orgA's real webhook_secret over the raw body below>
{
  "action": "removed",
  "team": { "id": <orgB team's github_id>, "name": "...", "slug": "...", "url": "..." },
  "organization": { "login": "orgA" },
  "member": { "login": "victim" }
}
```

`verify_signature` succeeds because it only checks the signature against `orgA`'s secret (matching the payload's `organization.login`), and `drop_unhandled_event`/`ExplicitParameters` schema only validate presence/types, not organization consistency. `find_or_create_team!` then finds the pre-existing `orgB` team by `github_id` (ignoring that the verified signer was `orgA`), and `team.members.delete(member)` removes the victim's `Membership` row for that team.

### Impact Explanation
This directly mutates Shipit's authorization state (`Membership` rows are the basis of `User#authorized?`, which checks membership against `Shipit.github_teams`) [5](#0-4) . If the targeted team is one of `Shipit.github_teams`, this deauthorizes a legitimate operator from Shipit entirely, with no corresponding change on GitHub's side — a genuine cross-tenant authorization-state corruption caused by an org that has no relationship to the victim's team or organization. This matches the "escalation into `Shipit.github_teams` authorization" High-severity category (here used destructively, to strip rather than grant, but it is an unauthorized authorization-state mutation across tenants). The attack is repeatable for any `(team github_id, member login)` pair as long as the attacker's own org remains a Shipit-recognized organization with a known webhook secret.

### Likelihood Explanation
Preconditions: the attacker's organization must be configured in Shipit as a known GitHub organization (so `Shipit.github(organization: "orgA")` resolves and has a `webhook_secret`) — this is a low bar since Shipit commonly serves many internal orgs, only some of which back `Shipit.github_teams`. The attacker also needs the numeric GitHub `team.id` of the victim team, which is not a secret (exposed via GitHub API/team URLs) and the victim's GitHub login (public). No Shipit credentials, session, API token, or GitHub App private key are required — only control of a legitimate webhook the attacker's own org already has configured to point at the Shipit instance. This is feasible and repeatable.

### Recommendation
In `MembershipHandler#find_or_create_team!`, scope the lookup by both `github_id` and `organization`, and reject/no-op processing when an existing `Team` row's `organization` does not equal `params.organization.login`. E.g., `Team.find_or_create_by!(github_id: params.team.id, organization: params.organization.login)`, and additionally verify that `WebhooksController`'s already-verified organization (the one whose secret validated the signature) equals `params.organization.login` before trusting it, so a signed-but-mismatched payload cannot mutate a different org's `Team`.

### Proof of Concept
Minitest (webhooks controller / handler level), no live GitHub:

```ruby
test "membership 'removed' webhook signed by org A cannot delete a Membership for a Team owned by org B" do
  org_a_secret = "org-a-secret"
  team = shipit_teams(:some_team) # organization: "orgB", github_id: 4242
  victim = shipit_users(:walrus)
  team.add_member(victim)
  assert Membership.exists?(team_id: team.id, user_id: victim.id)

  payload = {
    action: 'removed',
    team: { id: team.github_id, name: team.name, slug: team.slug, url: team.api_url },
    organization: { login: 'orgA' }, # attacker's own org, distinct from team.organization ("orgB")
    member: { login: victim.login }
  }.to_json

  signature = "sha1=" + OpenSSL::HMAC.hexdigest('sha1', org_a_secret, payload)

  # stub Shipit.github(organization: 'orgA').verify_webhook_signature to succeed using org_a_secret
  post shipit.github_webhooks_path,
       params: payload,
       headers: { 'X-Github-Event' => 'membership', 'X-Hub-Signature' => signature },
       as: :json

  # Assert the binding is broken: verified org ('orgA') != team.organization ('orgB'),
  # yet the Membership was still deleted.
  refute_equal 'orgA', team.reload.organization
  refute Membership.exists?(team_id: team.id, user_id: victim.id)
end
``` [6](#0-5)
