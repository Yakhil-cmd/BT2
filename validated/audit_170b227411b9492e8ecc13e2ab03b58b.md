## Title
A single malicious/broken submodule entry in `.gitmodules` can permanently block publishing of new commits for all consumers of a git-sync instance - (File: `main.go`, function `configureWorktree`)

### Summary
`git-sync`'s `configureWorktree` runs a single `git submodule update --init` (optionally `--recursive`) invocation to resolve every submodule referenced by the synced commit, analogous to `MultiRewards.getRewardForUser()` iterating over every reward token in one loop. Just as one malicious/paused reward token can revert the whole reward-claim loop and DoS all users, a single bad/unreachable/malformed submodule entry committed to the tracked ref causes the whole `git submodule update` command to fail, which aborts `SyncRepo` and prevents the new hash from ever being published via the atomic symlink.

### Finding Description
In `configureWorktree`, after checking out the target hash, git-sync unconditionally updates all submodules declared for that commit: [1](#0-0) 

This call is made once per sync, over the *entire* submodule set for the commit — there is no per-submodule isolation or "skip failing entries" logic, mirroring the reward-token loop pattern in the reference report. If an attacker who can influence the content of the synced ref (e.g., a merged PR, a pushed branch that git-sync tracks, or a compromised upstream) adds or edits a submodule entry to point at an unreachable, malformed, or intentionally slow/hanging URL, the single `git submodule update --init` command fails (or hangs until `--sync-timeout`), and `configureWorktree` returns an error: [2](#0-1) 

That error propagates out of `SyncRepo`, so the new worktree is never configured and the symlink is never updated: [3](#0-2) 

Because `git.SyncRepo` already advanced local refs via `git reset --soft remoteHash` before the submodule step, and the remote ref stays at the same (bad) hash on every subsequent poll, the failure recurs identically on every sync cycle: [4](#0-3) 

The outer loop only counts consecutive failures and exits the process after `--max-failures` (or restarts under Kubernetes), but it never manages to sync past the malicious commit, so the symlink remains pinned at the last good hash indefinitely — a persistent, repo-content-triggered denial of new updates for every consumer reading `--link`.

### Impact Explanation
**High** for future updates: once a malicious/broken submodule reference reaches the tracked ref, the local mirror can never advance past it. All consumers of the git-sync sidecar (e.g., all pods mounting the shared volume) are denied any new configuration/content until an operator manually intervenes (fixes the ref or reconfigures `--submodules off`), effectively the same "all reward tokens blocked for all users in the vault" pattern from the reference report, translated to "all consumers blocked from new sync in this git-sync instance."

### Likelihood Explanation
**Low-to-Medium**, gated by whether an attacker can get a commit onto the ref git-sync tracks (e.g., open-source repos with external contributors, compromised upstream, or an insufficiently protected branch). This is analogous to the report's "Low" likelihood tied to governance whitelisting — here the analogous control is repository push/merge access control.

### Recommendation
- Treat submodule update failures the same way `git-sync` already treats fetch/checkout sanity failures: fall back to a bounded retry/backoff without repeatedly resetting `origin` state, and surface a clear, actionable error distinguishing "bad submodule in synced ref" from transient network errors.
- Consider adding an option to skip/ignore unreachable or disallowed submodules (e.g., restrict allowed submodule URLs to an allow-list, similar to the report's "stringent whitelist" recommendation) rather than failing the entire checkout.
- Bound submodule update time strictly via `--sync-timeout` (already partially enforced by the wrapping `ctx`) and ensure failures don't leave the repo in a state that requires manual cleanup.

### Proof of Concept
1. Attacker (or compromised upstream contributor) pushes a commit to the branch/ref git-sync tracks that adds/modifies `.gitmodules` to reference a submodule URL that is unreachable, requires interactive auth, or triggers an unsupported/malicious transport.
2. git-sync's next `SyncRepo` fetches the new commit (`remoteHash` changes), creates a new worktree, and calls `configureWorktree`, which invokes `git submodule update --init` at `main.go:1744`.
3. The submodule command fails (non-zero exit / times out), `configureWorktree` returns an error, `SyncRepo` aborts before `publishSymlink`, and the symlink continues pointing at the old worktree.
4. On every subsequent poll cycle, the same `remoteHash` is fetched and the same submodule failure recurs, so the symlink never advances — all consumers relying on `--link` for updated content are permanently denied new syncs until manual operator intervention.
