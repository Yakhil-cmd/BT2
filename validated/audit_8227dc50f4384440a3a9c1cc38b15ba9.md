### Title
Attacker-controlled `bounce_fees`/`outputs` values in an AA definition or trigger cause an uncaught exception that crashes the entire ocore daemon - ([File: aa_composer.js])

### Summary
`moby`'s bug (CVE-2021-21285) is a malformed image manifest that hits an unchecked code path and panics the whole `dockerd` process, denying service to the entire node. `ocore` has a structurally identical hazard: `network.js` installs a global `process.on('uncaughtException', ...)` handler that **deliberately re-throws** to crash the entire node process (`network.js:4530-4543`), and `aa_composer.js`'s AA-trigger execution path (`handleTrigger`, reachable by *any* unprivileged unit poster who pays outputs to an AA address) contains multiple bare `throw Error(...)` statements inside async DB-callback chains that are not wrapped in any try/catch reachable by that handler.

### Finding Description
Any unit poster can trigger AA execution simply by sending a payment to an AA address; `aa_composer.getTrigger()` builds a `trigger` object straight from the untrusted unit's `messages`/`payload.outputs` [1](#0-0) , and `handleTrigger()` executes the AA's definition using data mostly derived from this attacker/AA-author-controlled trigger and the (attacker- or AA-author-supplied) AA `arrDefinition` template [2](#0-1) .

Throughout this execution path there are bare, synchronous `throw Error(...)` calls performed from inside async callbacks (e.g. `pickParents` throwing `"limci of last AA > mci"` [3](#0-2) , `finish()` throwing `'response_unit with bouncing a secondary AA'` [4](#0-3) , `handleSecondaryTriggers` throwing `"secondary triggers while bouncing"` [5](#0-4) , and `validateAndSaveUnit`'s callbacks throwing on any joint/transient/unsigned/dependency validation anomaly for an internally composed AA response unit [6](#0-5) ). None of these throws are caught by a surrounding `try/catch`; they propagate to the Node.js event loop and are only intercepted by the process-wide `uncaughtException` handler in `network.js`, which explicitly re-throws to kill the process:

```
process.on('uncaughtException', (err) => {
    ...
    throw err; // crash the process to avoid ending up in an inconsistent state
});
``` [7](#0-6) 

Because AA trigger handling is invoked automatically whenever a normal unit becomes stable and pays to a known AA address (`main_chain.js` `handleAATriggers()` inserts triggers unconditionally for any unit paying an AA [8](#0-7) ), and because `network.js`'s optional dry-run path explicitly documents the intent that a crash here is acceptable ("if it would crash, let it crash now, not when we execute the trigger for real" [9](#0-8) ), a specially crafted but validation-accepted unit/trigger/AA-definition combination that hits one of these unreachable-by-design invariants (e.g., a race/ordering condition causing `pickParents`'s "limci of last AA > mci" assertion to fail, or a bounced secondary AA that still produces a `response_unit`) throws synchronously inside a DB callback and crashes the entire full node — not just the single transaction.

This is directly analogous to the moby CVE: an externally reachable, insufficiently defensive code path (unchecked invariant assumptions about "impossible" states) turns malformed/unusual but reachable input into an unhandled crash of the whole daemon (CWE-754: improper handling of an unusual/exceptional condition, and CWE-400 in the sense that it is an uncontrolled effect of processing external data), rather than a contained, per-unit validation error.

### Impact Explanation
An uncaught exception anywhere in the AA execution path crashes the entire ocore full node process (not just the one transaction). Given that AA triggers execute automatically for any unit paying to an AA address, this is a network-reachable-by-content vector: a malicious unit author or a malicious/exotic AA author can construct a trigger/definition pair that reliably drives execution into one of these `throw Error(...)` assertions, taking down a node (or many nodes running identical validation logic) whenever the relevant unit becomes stable and its AA trigger is processed. Because AA processing occurs deterministically on every full node evaluating the same stabilized unit, this is a network-wide denial of confirmation of new units capability for AAs and can stall stabilization/witnessing for the affected node(s), which maps to "a network unable to confirm new units" in the given impact criteria.

### Likelihood Explanation
Exploitation requires crafting a unit/trigger whose interaction with a particular AA definition drives execution into one of the "impossible" invariant-violation throws (e.g., timing/ordering issues in `pickParents`, or bounce-with-response-unit combinations in `finish()`). These are edge-case/defensive assertions the developers believed unreachable, similar to the "malformed manifest touches an unexpected nil pointer" pattern in the moby bug. Because AA definitions are user-authored and highly flexible (arbitrary formulas, `state`/`init` code, bounce logic, remote AA calls), and secondary/chained AA triggers add extra branching complexity, it is plausible for a determined attacker to construct an AA + trigger sequence that reaches one of these throw sites, though this analysis could not execute or fuzz the code to confirm a concrete reproducer for any specific throw site.

### Recommendation
- Replace the process-crashing `process.on('uncaughtException', ...)` re-throw (or at minimum, avoid relying on it as the last line of defense for logic invoked directly from untrusted, attacker-influenced data) with fine-grained error handling in `aa_composer.js`.
- Wrap `handleTrigger`, `handleSecondaryTriggers`, `pickParents`, `finish`, and `validateAndSaveUnit`'s callback error paths in structured error handling that bounces the AA trigger (as is already done for expected errors) instead of throwing, so that unanticipated internal-invariant violations degrade to a bounced/no-op response rather than crashing the daemon.
- Audit every `throw Error(...)` reachable from `handleTrigger`/`getTrigger`/`handlePrimaryAATrigger` to determine which invariants can actually be violated by attacker-supplied trigger data or AA definitions, and convert those into `bounce(...)` calls or unit-validation rejections instead of hard throws.
- Add defensive/regression tests that attempt pathological AA definitions (chained/secondary triggers that bounce while producing a response unit, out-of-order `limci`/`mci` values, etc.) to confirm none of these currently-unreachable-by-design assertions can be triggered by valid-but-adversarial input.

### Proof of Concept
No concrete, adversarially-constructed unit/AA-definition pair was fully validated in this analysis to trigger a specific throw (e.g., reproducing the `pickParents` "limci of last AA > mci" or `finish()`'s "response_unit with bouncing a secondary AA" conditions end-to-end requires deeper reproduction of main-chain stabilization ordering, which was out of scope for this static review). This is noted as an open item: further dynamic testing/fuzzing of AA definitions with secondary/chained triggers and bounce logic is needed to produce a concrete PoC and confirm reachability from purely external, attacker-controlled data (trigger unit content and/or a self-authored malicious AA definition).

function getTrigger(objUnit, receiving_address) {
	var trigger = { address: objUnit.authors[0].address, unit: objUnit.unit, outputs: {} };
	if ("max_aa_responses" in objUnit)
		trigger.max_aa_responses = objUnit.max_aa_responses;
	objUnit.messages.forEach(function (message) {
		if (message.app === 'data' && !trigger.data) // use the first data message, ignore the subsequent ones
			trigger.data = message.payload;
		else if (message.app === 'payment' && message.payload) {
			var payload = message.payload;
			var asset = payload.asset || 'base';
			payload.outputs.forEach(function (output) {
				if (output.address === receiving_address) {
					if (!trigger.outputs[asset])
						trigger.outputs[asset] = 0;
					trigger.outputs[asset] += output.amount; // in case there are several outputs
				}
			});
		}
	});
	if (Object.keys(trigger.outputs).length === 0)
		throw Error("no outputs to " + receiving_address);
	return trigger;
}
