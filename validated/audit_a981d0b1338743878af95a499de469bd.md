### Title
Webhook `X-Hub-Signature` is verified against the organization derived from `repository.owner.login`, but handlers act on the unrelated `repository.full_name` / global `sha` fields — cross-repository status/commit writes - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to verify the incoming payload against using `repository_owner`, i.e. `params.dig('repository','owner','login')` (or `organization.login`). Once the signature check passes, the payload is handed unmodified to `Shipit::Webhooks.for_event(event)` handlers, which act on a *different* field of the same payload — `repository.full_name` in `Handler#repository_name`, or, worse, no repository scoping at all in `StatusHandler`, which does `Commit.where(sha: params.sha)` across the entire instance. The equality the engine implicitly relies on — "organization whose secret authenticated the request" == "repository that gets written to" — is never enforced.

### Finding Description
`WebhooksController#verify_signature` resolves the signing organization purely from attacker-supplied JSON fields: [1](#0-0) [2](#0-1) 

`lib/shipit/github_app.rb#verify_webhook_signature` then HMACs the *raw body* with that organization's configured `webhook_secret`: [3](#0-2) 

This means: any party that legitimately controls one Shipit-configured GitHub organization/App (and therefore knows that org's `webhook_secret`, e.g. because they administer that org's GitHub App installation) can sign an arbitrary JSON body themselves, as long as `repository.owner.login` (or `organization.login`) in that body equals their own org's login. Nothing forces the rest of the payload — in particular `repository.full_name` or `sha` — to belong to that same organization/repository.

Downstream, `Handler#repository_name` reads a **different** field (`repository.full_name`) to resolve the `Stack`/`Repository` to write to: [4](#0-3) 

`PushHandler#process` uses that mismatched resolution to trigger `stack.sync_github`, and `CheckSuiteHandler` similarly scopes only through `Handler#stacks`, which is derived from `repository.full_name`: [5](#0-4) [6](#0-5) 

The most severe instance is `StatusHandler`, which does not even use `repository_name`/`stacks` scoping — it matches purely on commit `sha`, globally, across every stack/repository tracked by the Shipit instance: [7](#0-6) 

Since `sha` values are 40-hex-character but not secret (visible on any public GitHub repo, in PR URLs, CI logs, etc.), an attacker who administers Org A's GitHub App integration with Shipit can sign a `status` webhook body where `repository.owner.login = "OrgA"` (so `verify_signature` passes using Org A's secret) while the `sha` field names a commit that actually belongs to Org B's stack. `StatusHandler#process` will then create/update a `Status` on that unrelated commit with an attacker-chosen `state`, `context`, `description`, and `target_url`.

### Impact Explanation
Commit "deployability" gates in this engine are driven by commit statuses. The API deploy endpoint explicitly checks `commit.deployable?` when `require_ci` is requested: [8](#0-7) 

By forging a `success` status for a victim stack's commit (using nothing but knowledge of a public commit SHA and possession of a webhook secret for an entirely unrelated organization configured on the same Shipit instance), an attacker can flip a commit that never actually passed CI into a "deployable" state. Combined with `continuous_deployment` or a subsequent legitimate deploy trigger with `require_ci: true`, this results in an **unauthorized deploy** of a commit that was never vetted by real CI — the specific "cross-repository writes / unauthorized deploy" impact bucket. It also breaks the exact binding called out in scope: "an organization that authenticated versus the repository that is written."

### Likelihood Explanation
This requires the attacker to control at least one organization/GitHub App entry already configured in this Shipit deployment's `github:` secrets (a realistic scenario for any multi-tenant Shipit instance serving several orgs/teams), plus knowledge of a target commit SHA in another tracked repository, which is generally public information. No repository write access, no `ApiClient` token, and no privileged Shipit account are required — only the webhook secret for one's *own* configured org, which is a credential the engine hands out per-organization by design. This is a realistic, low-friction path for an insider-of-one-tenant to affect other tenants sharing the same Shipit deployment.

### Recommendation
When verifying and dispatching a webhook, bind the verified organization to the repository actually mutated: after `verify_signature` succeeds for organization `O`, every field the handler consults to select a `Repository`/`Stack`/`Commit` (`repository.full_name`, and in `StatusHandler`, the commit's owning repository) must be checked to belong to `O` before any write occurs. Concretely, `StatusHandler` should scope `Commit.where(sha: params.sha)` through `stacks`/`repository_name` (as `PushHandler`/`CheckSuiteHandler` already partially do) so that only commits under the repository named in the payload — and matching the authenticated organization — can be updated.

### Proof of Concept
1. Shipit is configured with two organizations, `orgA` and `orgB`, each with its own `webhook_secret` (as shown in `config/secrets.development.shopify.yml`).
2. Attacker administers `orgA`'s GitHub App/webhook config and thus knows `orgA`'s `webhook_secret`.
3. Attacker crafts a `status` event JSON body:
   ```json
   {
     "repository": { "owner": { "login": "orgA" }, "full_name": "orgA/irrelevant" },
     "sha": "<public sha of a commit in orgB's tracked stack>",
     "state": "success",
     "context": "ci/required-check",
     "description": "forged",
     "target_url": "https://example.com"
   }
   ```
4. Attacker computes `X-Hub-Signature: sha1=HMAC(orgA_webhook_secret, body)` and POSTs to `/webhooks` with `X-Github-Event: status`.
5. `WebhooksController#verify_signature` resolves `repository_owner => "orgA"`, fetches `orgA`'s app, and the signature verifies successfully.
6. `StatusHandler#process` executes `Commit.where(sha: params.sha)` — matching the `orgB` commit — and calls `create_status_from_github!`, writing a forged "success" status onto a commit the attacker never had permission to touch.
7. A subsequent deploy request with `require_ci: true` against `orgB`'s stack for that commit now passes the `commit.deployable?` check it should have failed.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
