### Title
`create1` address prediction under `pallet-revive` dry-run diverges from the actual deployment address, permanently orphaning pre-funded counterfactual deployments - ([File: substrate/frame/revive/src/exec.rs])

### Summary
`pallet-revive`'s CREATE1 address-derivation logic subtracts 1 from the caller's on-chain nonce whenever `origin_is_caller` is true, on the assumption that the nonce was already incremented pre-dispatch by a real signed extrinsic. This assumption does not hold for dry-run/simulation execution paths (e.g. `eth_call`/runtime-API instantiate calls used to predict a deployment address before submitting the real transaction), where the nonce has not been pre-incremented. A `prdoc` in this repository (`prdoc/stable2506/pr_8504.prdoc`) documents this exact bug and claims a fix that adds an `ExecContext`-aware branch, but no `ExecContext` symbol exists anywhere in `substrate/frame/revive/src/exec.rs` (or the rest of the crate) — the described fix was never actually landed in code, even though the prdoc bump (`pallet-revive: major`) suggests it shipped.

### Finding Description
The address-prediction logic lives in `Stack::new_frame` in `substrate/frame/revive/src/exec.rs`: [1](#0-0) 

```rust
FrameArgs::Instantiate { sender, executable, salt, input_data } => {
    let deployer = T::AddressMapper::to_address(&sender);
    let account_nonce = <System<T>>::account_nonce(&sender);
    let address = if let Some(salt) = salt {
        address::create2(&deployer, executable.code(), input_data, salt)
    } else {
        use sp_runtime::Saturating;
        address::create1(
            &deployer,
            // the Nonce from the origin has been incremented pre-dispatch, so we
            // need to subtract 1 to get the nonce at the time of the call.
            if origin_is_caller {
                account_nonce.saturating_sub(1u32.into()).saturated_into()
            } else {
                account_nonce.saturated_into()
            },
        )
    };
```

The comment explicitly states the `-1` adjustment is only correct when the extrinsic pipeline has already incremented the nonce pre-dispatch — which is true for a *real, submitted transaction*, but not true when the very same code path is invoked through a dry-run/simulation entry point (Ethereum JSON-RPC `eth_call`/`eth_estimateGas`, or the runtime-API `instantiate`/`call` used to preview a CREATE1 deployment). In dry-run contexts the nonce read from `System::account_nonce` is the *current* nonce, not "current + 1", so subtracting 1 yields a nonce one lower than what the *actual* transaction will use once it increments the nonce pre-dispatch and runs the real deployment. This directly parallels the reported analog bug class: a value used to derive/predict a deterministic address (`troveManagerImpl` in the Prisma report; the account nonce here) is not consistently the same at "prediction time" and at "actual deployment time," causing the exposed address-prediction function to return an address that does not match reality.

`prdoc/stable2506/pr_8504.prdoc` (present in this repo) documents this exact defect and describes a fix that checks `matches!(exec_context, ExecContext::Transaction)` before subtracting 1, and bumps `pallet-revive` as a `major` change: [2](#0-1) 

A repository-wide search for `ExecContext` returns matches **only inside this prdoc file** — the symbol does not exist in `substrate/frame/revive/src/exec.rs` or anywhere else in the crate. The `Stack::new` / `new_frame` code path (`substrate/frame/revive/src/exec.rs` lines 1015-1214) still relies purely on `origin_is_caller`, with no `ExecContext`/dry-run branch guarding the `-1` subtraction: [3](#0-2) 

This is a discrepancy between the documented/claimed fix and the actual shipped source in this codebase snapshot — the bug the prdoc claims to have fixed appears to remain present in the code.

### Impact Explanation
A dry-run instantiate (no salt, i.e. CREATE1 semantics) called by any unprivileged user through the standard eth-RPC or runtime-API simulate path returns a predicted deployment address computed with `nonce - 1`. If a user or tooling relies on this address to pre-fund a counterfactual deployment (a very common pattern: fund an address before code lands there, e.g. via a factory or wallet pre-computation flow), the actual on-chain transaction — when later submitted — increments the nonce pre-dispatch and deploys the contract at `nonce` (one higher than the value the dry run used), landing at a *different* address than the one that was pre-funded. Funds sent to the mispredicted address are not recoverable because no contract is ever deployed there (its nonce slot was already skipped by the real deployment). This matches the "irreversible freezing" impact class the assessment explicitly weights as high severity.

### Likelihood Explanation
- No privileged role, governance, or malicious actor is required — this is triggered by ordinary use of the standard read-only simulate/dry-run RPC/runtime-API surface that `pallet-revive` exposes for previewing a CREATE1 deployment before submission, which is exactly the intended purpose of such dry-run calls (predict-then-fund workflows are common in EVM-compatible tooling).
- The divergence is deterministic and 100% reproducible any time a dry-run instantiate without salt is performed on an account whose nonce will be incremented before the real transaction executes — i.e., every normal case.
- Confidence is limited by the fact that I could not fully trace the exact RPC/runtime-API entry point that sets `origin_is_caller = true` for a genuine dry-run invocation (the `is_dry_run` flag threading through `ExecConfig` in `substrate/frame/revive/src/exec.rs` and `substrate/frame/revive/src/primitives.rs` was located, but the full call graph from `eth_call`/`instantiate` runtime API down into `Stack::new`/`new_frame` was not completely walked in the time available). The prdoc itself, however, is direct evidence that Parity engineers identified and attempted to fix precisely this issue for precisely this reason ("users can rely on the address returned by a dry run to match the actual address... when the transaction is submitted"), which corroborates the reachability and real-world relevance of the bug.

### Recommendation
Verify whether `substrate/frame/revive/src/exec.rs`'s `new_frame`/`Stack::new` actually receives and threads an `ExecContext`-like flag (transaction vs. dry-run) into the nonce adjustment for `address::create1`, matching what `prdoc/stable2506/pr_8504.prdoc` describes. If it is absent, land the fix described in that prdoc: only subtract 1 from `account_nonce` when the call is executing as part of a genuine, dispatched transaction (i.e., the nonce was actually pre-incremented), and use the raw current nonce for all dry-run/simulation paths, so that a previewed CREATE1 address always matches the address of the eventual real deployment.

doc:
- audience: Runtime Dev
  description: |-
    ## Description

    When dry-running a contract deployment through the runtime API, the returned address does not match the actual address that will be used when the transaction is submitted. This inconsistency occurs because the address derivation logic doesn't properly account for the difference between transaction execution and dry-run execution contexts.

    The issue stems from the `create1` address derivation logic in `exec.rs`:

    ```rust
    address::create1(
        &deployer,
        // the Nonce from the origin has been incremented pre-dispatch, so we
        // need to subtract 1 to get the nonce at the time of the call.
        if origin_is_caller {
            account_nonce.saturating_sub(1u32.into()).saturated_into()
        } else {
            account_nonce.saturated_into()
        },
    )
    ```

    The code correctly subtracts 1 from the account nonce during a transaction execution (because the nonce is incremented pre-dispatch), but doesn't account for execution context - whether it's a real transaction or a dry run through the RPC.

    ## Review Notes

    This PR adds a new condition to check for the `ExecContext` when calculating the nonce for address derivation:

    ```rust
    address::create1(
        &deployer,
        // the Nonce from the origin has been incremented pre-dispatch, so we
        // need to subtract 1 to get the nonce at the time of the call.
        if origin_is_caller && matches!(exec_context, ExecContext::Transaction) {
            account_nonce.saturating_sub(1u32.into()).saturated_into()
        } else {
            account_nonce.saturated_into()
        },
    )
    ```

    A new test `nonce_not_incremented_in_dry_run()` has been added to verify the behavior.

    ## Before Fix

    - Dry-run contract deployment returns address derived with nonce N
    - Actual transaction deployment creates contract at address derived with nonce N-1
    - Result: Inconsistent addresses between simulation and actual execution

    ## After Fix

    - Dry-run and actual transaction deployments both create contracts at the same address
    - Result: Consistent contract addresses regardless of execution context
    - Added test case to verify nonce handling in different execution contexts

    This fix ensures that users can rely on the address returned by a dry run to match the actual address that will be used when the transaction is submitted.
