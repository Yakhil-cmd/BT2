### Title
Webhook authenticity check silently degrades to "always verified" for any organization missing a `webhook_secret`, letting an unauthenticated attacker forge `membership` events and grant themselves `Shipit.github_teams` authorization - ([File: lib/shipit/github_app.rb])

### Summary
`WebhooksController#verify_signature` selects which organization's GitHub App config to use for HMAC verification directly from unauthenticated JSON in the request body, and `GitHubApp#verify_webhook_signature` treats a missing `webhook_secret` as automatic success. Because `webhook_secret` is documented as optional per organization, an attacker can target any configured organization that has none set, bypass signature verification entirely, and drive privileged webhook handlers (e.g. `membership`) with fully attacker-controlled payload content.

### Finding Description
`WebhooksController#verify_signature` derives the organization used for authentication from the payload itself, before any signature has been validated: [1](#0-0) [2](#0-1) 

That organization name is used to fetch a `GitHubApp` instance holding a per-organization `webhook_secret`: [3](#0-2) 

`GitHubApp#verify_webhook_signature` returns `true` unconditionally whenever that organization's `webhook_secret` is blank, regardless of the `X-Hub-Signature` header supplied (or omitted): [4](#0-3) 

The setup docs explicitly describe `webhook_secret` as optional per app/organization: [5](#0-4) 

The binding that is expected to hold is: **organization that cryptographically authenticated the request == organization whose data the handlers mutate**. When an organization has no `webhook_secret` configured, that binding collapses to **organization named in an unauthenticated JSON field == organization whose data the handlers mutate**, i.e. no authentication at all for that organization's traffic.

Downstream, handlers trust the payload unconditionally once `verify_signature` passes. The `membership` handler creates/attaches `Team`, `User`, and `Membership` records purely from payload fields: [6](#0-5) [7](#0-6) 

`Membership` records are exactly what `User#authorized?` checks to gate access to the whole Shipit application: [8](#0-7) [9](#0-8) 

### Impact Explanation
An unauthenticated, unprivileged attacker who knows (or discovers) the handle of an organization configured in `secrets.github` without a `webhook_secret` can POST a forged `membership` event claiming that organization, adding any GitHub login (including one the attacker controls) as a member of a `Team` that is part of `Shipit.github_teams`. After a normal OAuth login with that GitHub account, `current_user.authorized?` becomes `true` via the forged `Membership`, granting access to the Shipit web UI and its deploy/rollback/merge actions. This is an escalation into `Shipit.github_teams` authorization, which is explicitly listed as a High-impact outcome. The same forged-signature path also lets the attacker drive `push`/`status`/`pull_request` handlers for that organization with entirely fabricated repository/commit/status data.

### Likelihood Explanation
This does not require a session, `ApiClient` token, `webhook_secret`, or repository write access - the `/webhooks` endpoint is unauthenticated by design (it's how GitHub reaches Shipit) and the only gate is `verify_signature`. The attack only requires that at least one organization configured in the deployment lacks a `webhook_secret`, which the project's own setup documentation treats as an acceptable, supported configuration rather than a misconfiguration to avoid. In an installation with multiple organizations, forgetting/omitting the secret on any one of them exposes this bypass for that organization's namespace while other organizations may be properly secured, making the flaw easy to overlook.

### Recommendation
Do not let `verify_webhook_signature` treat an absent `webhook_secret` as a pass; require a `webhook_secret` to be configured for every organization Shipit tracks, or fail closed (reject the request) when it's missing rather than returning `true`. Additionally, avoid deriving the trust-establishing organization from unauthenticated payload fields prior to verification - verify against all known organization secrets (or a global secret) rather than a self-reported org, and re-validate that the verified organization matches the org referenced by the event data used by handlers.

### Proof of Concept
1. Deploy Shipit with two organizations configured under `secrets.github`, where `orgA` has a `webhook_secret` set and `orgB` does not (a valid configuration per `docs/setup.md`).
2. As an unauthenticated attacker, POST to `/webhooks` with header `X-Github-Event: membership` and no valid `X-Hub-Signature`, body:
```json
{
  "action": "added",
  "team": { "id": <id-of-a-team-in-Shipit.github_teams>, "slug": "developers", "name": "Developers", "url": "https://example.com" },
  "organization": { "login": "orgB" },
  "member": { "login": "attacker-controlled-login" }
}
```
3. `verify_signature` resolves `repository_owner` to `"orgB"` (`app/controllers/shipit/webhooks_controller.rb:61`), fetches `orgB`'s `GitHubApp`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` (`lib/shipit/github_app.rb:76-77`) - no valid signature was required.
4. The `membership` handler creates a `Membership` linking `attacker-controlled-login`'s `User` to the authorized `Team`, exactly as demonstrated by `test/controllers/webhooks_controller_test.rb:159-165`.
5. The attacker signs in to Shipit via normal GitHub OAuth as `attacker-controlled-login`; `User#authorized?` now returns `true` due to the forged `Membership`, granting access gated by `force_github_authentication`.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
