### Title
Webhook signature is verified against `repository.owner.login`'s GitHub App secret, but every event handler acts on the unrelated `repository.full_name` field, letting any organization's installed app forge writes against another organization's stacks - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the `GitHubApp` (and therefore the HMAC `webhook_secret`) used to authenticate the inbound webhook based on `repository_owner`, which is read from the same untrusted JSON body as everything else: `params.dig('repository', 'owner', 'login')` (falling back to `params.dig('organization', 'login')`). [1](#0-0) [2](#0-1) 

Once the signature check passes, the entire raw `params` hash is dispatched unmodified to every registered handler for the event: [3](#0-2) 

Handlers never re-derive or cross-check the organization used for authentication. Instead, `Handler#repository_name` reads a *different* field of the same payload, `repository.full_name`, to look up the target `Repository`/`Stack`: [4](#0-3) 

`PushHandler` and `CheckSuiteHandler` then act on stacks resolved purely from that `full_name`: [5](#0-4) [6](#0-5) 

### Finding Description
This is a direct analog of the `0x07` binding-break class described in the report: one code path validates field A (`repository.owner.login`) while a sibling/parallel code path acts on field B (`repository.full_name`) from the very same attacker-supplied payload, with no equality check tying them together.

The binding that should hold is:
`organization whose GitHub App secret authenticated the webhook == owner of the repository the handler mutates state for`

Concretely:
- Shipit supports multiple independently-configured GitHub Apps, one per organization, each with its own `webhook_secret` (see `docs/setup.md` and `test/dummy/config/secrets_double_github_app.yml`, which configures `OrgOne`/`OrgTwo` each with a distinct app/secret).
- `verify_signature` picks the app/secret solely by `repository.owner.login` (or `organization.login`) from the JSON body, and validates the raw body against that org's `webhook_secret` via `GitHubApp#verify_webhook_signature`. [7](#0-6) 
- The `full_name` field used for the actual write path (`Repository.from_github_repo_name(repository_name)`) is never compared against `repository_owner`. An attacker who legitimately owns/administers a GitHub App installation on **their own** organization ("attacker-org") knows that organization's `webhook_secret` (it is visible to the app owner in the GitHub App settings and is exactly what they'd configure in Shipit's `config/secrets.yml` entry for that org). They can therefore compute a valid `X-Hub-Signature` for a payload where `repository.owner.login = "attacker-org"` (so the signature check passes against attacker-org's key) while `repository.full_name = "victim-org/victim-repo"` (an org/repo they do not control, but which is registered as a Shipit stack).
- The `PushHandler`/`CheckSuiteHandler` will resolve stacks via `Repository.from_github_repo_name("victim-org/victim-repo")` and act on them — e.g. enqueue `GithubSyncJob`/`stack.sync_github` or `schedule_refresh_check_runs!` — even though the request was never signed by victim-org's app.

### Impact Explanation
This breaks the intended per-organization trust boundary that the multi-tenant GitHub App / `webhook_secret` model is meant to enforce: signature verification is supposed to prove "this event genuinely originates from GitHub for organization X," but the code that consumes the event trusts an unrelated field to decide *which* organization's stacks to touch. This lets any org onboarded onto the same Shipit instance forge cross-organization events against stacks it doesn't own, matching the rule's explicit criterion "an organization that authenticated versus the repository that is written." Depending on downstream handler behavior this can trigger unauthorized syncs/check-run refreshes against another tenant's stack.

### Likelihood Explanation
Requires only that Shipit is configured with more than one organization's GitHub App (a documented, supported configuration — see `test/dummy/config/secrets_double_github_app.yml`) and that the attacker controls one such organization/app (which they can legitimately install themselves). No privileged Shipit credentials, `ApiClient` token, or GitHub write access to the victim repo is required — only knowledge of their own app's `webhook_secret`, which they inherently have.

### Recommendation
In `WebhooksController#verify_signature`/`create`, after resolving `repository_owner` for signature verification, enforce that every handler operates only on repositories/organizations matching that verified `repository_owner`, e.g. by having `Handler#repository_name` (or the controller) assert `payload.dig('repository', 'owner', 'login') == repository_owner` (or the `organization.login` fallback) before dispatching, and reject the event otherwise.

### Proof of Concept
1. Configure Shipit with two orgs, `attacker-org` and `victim-org`, each with its own GitHub App and `webhook_secret` (as in `test/dummy/config/secrets_double_github_app.yml`).
2. Attacker owns the `attacker-org` GitHub App and therefore knows `attacker-org`'s `webhook_secret`.
3. Attacker crafts a `push` (or `check_suite`) webhook JSON body:
   ```json
   {
     "ref": "refs/heads/master",
     "after": "<attacker-chosen-sha>",
     "repository": {
       "owner": { "login": "attacker-org" },
       "full_name": "victim-org/victim-repo"
     }
   }
   ```
4. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(attacker-org_webhook_secret, body)>` and POSTs to `/webhooks` with header `X-Github-Event: push`.
5. `verify_signature` calls `Shipit.github(organization: "attacker-org")` (from `repository.owner.login`) and validates successfully against `attacker-org`'s secret. [1](#0-0) 
6. `PushHandler#process` resolves stacks via `Repository.from_github_repo_name("victim-org/victim-repo")` (from `repository.full_name`) and invokes `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` on the victim's stack — despite the request never being signed by `victim-org`'s app. [5](#0-4) [4](#0-3) 

Note: I was unable to fully trace `Stack#sync_github` / `GithubSyncJob` and `Commit#create_status_from_github!` execution details (which GitHub credentials they use internally and whether `sync_github`'s `expected_head_sha` can drive an unauthorized deploy vs. merely a resync) before running out of tool iterations, so the exact downstream severity (e.g., whether this can be escalated to an actual unauthorized deploy/rollback) is not fully confirmed and would need further verification of `app/models/shipit/stack.rb` and `app/jobs/shipit/github_sync_job.rb`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
