### Title
Cross-repository forgery of commit statuses via unscoped `StatusHandler` breaks the organization-authenticated vs. repository-written binding — ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` authenticates an inbound webhook by selecting a GitHub App/secret keyed on the *organization* named in the payload (`repository.owner.login` or `organization.login`) and verifying the HMAC signature against that secret [1](#0-0) . This proves only that the sender knows *some* organization's configured `webhook_secret` on this multi-tenant Shipit instance — it says nothing about which repository's data the payload is allowed to affect. Most webhook handlers re-derive and check the target repository from the signed `repository.full_name` field before mutating anything [2](#0-1) , but `Shipit::Webhooks::Handlers::StatusHandler` does not: it resolves the target `Commit` purely by `sha`, globally, across every repository/stack hosted by the instance [3](#0-2) .

### Finding Description
The binding that should hold is:

`organization authenticated by verify_signature == organization owning the repository/stack whose data is written by the handler`

For `push`, `check_suite`, and the `pull_request` family of handlers, this binding is preserved because they scope their side effects through `Repository.from_github_repo_name(params.repository.full_name)` or the equivalent `stacks` helper, which is itself derived from the signed `repository.full_name` field [2](#0-1) [4](#0-3) [5](#0-4) .

`StatusHandler` breaks this binding. Its `params` block only requires `sha`, `state`, and optional descriptive fields — it never requires or reads `repository` at all [6](#0-5) . Its `process` method queries `Commit.where(sha: params.sha)` with no `Stack`/`Repository` scoping whatsoever, and writes a status onto every matching commit found anywhere in the database [3](#0-2) .

Concretely:
1. An attacker who legitimately administers *any* GitHub organization/repository onboarded to this Shipit instance controls the `webhook_secret` for that org (they set it when configuring the webhook, per `docs/setup.md`'s multi-app instructions and `test/dummy/config/secrets_double_github_app.yml`) [7](#0-6) .
2. `verify_signature` only checks that the signature is valid for the org named in the attacker's own payload (`repository.owner.login` set to the attacker's org) — it uses `Shipit.github(organization: repository_owner)` to pick which secret to check against [8](#0-7) .
3. Because the attacker computes the HMAC themselves with their own known secret, they can freely choose every other field in the JSON body, including a `sha` value belonging to a commit in a *victim* stack from a completely different organization.
4. `StatusHandler` ignores the `repository` context and matches purely on `sha`, so it happily creates/updates a `Status` on the victim's commit using data the attacker fully controls (`state`, `description`, `context`, `target_url`) [3](#0-2) .

No hash collision is required: the attacker only needs to know the target commit's SHA (visible on GitHub/PR pages or in the Shipit UI) and send it as a string in the forged `status` payload.

### Impact Explanation
A forged `success` status on a victim commit directly affects `Commit#deployable?`, which is `!locked? && (stack.ignore_ci? || (success? && !blocked?))` [9](#0-8) . Marking a previously failing/pending commit as `success` can:
- Make the commit pass `require_ci` checks in `Api::DeploysController#create`, enabling a human operator to trigger a deploy of a commit that never actually passed CI [10](#0-9) .
- Feed into `schedule_continuous_delivery`, which auto-triggers a deploy once a commit becomes `deployable?` under continuous deployment [11](#0-10) .
- Unblock `blocked?` for a subsequent commit by faking a passing status for an earlier blocking commit [12](#0-11) .

This maps to the "unauthorized deploy" impact bucket: an attacker with no access to the victim's organization or repository can cause the victim's Shipit instance to deploy or auto-deploy a commit that was never actually verified as CI-passing.

### Likelihood Explanation
High. Any tenant of a multi-organization Shipit deployment (a routine, documented configuration — see `docs/setup.md` "Using Multiple Github Applications") who legitimately controls one organization's webhook secret can exploit this with a single crafted HTTP POST; no privileged access to the victim org, no signing-key compromise, and no race condition are required. The only "secret" the attacker needs is one they are entitled to configure themselves.

### Recommendation
Scope `StatusHandler` (and any other handler that currently lacks it) to the signed `repository.full_name`/`repository.owner.login` fields before touching any `Commit`, mirroring the pattern used by `PushHandler`/`CheckSuiteHandler`/the `PullRequest` handlers, e.g. restrict the `Commit.where(sha: params.sha)` lookup to commits whose `stack.repository` matches `Repository.from_github_repo_name(payload.dig('repository','full_name'))`, and require `repository.full_name` in the handler's `params` block so it is enforced/validated like the other handlers.

### Proof of Concept
1. Attacker legitimately owns org `AttackerOrg`, configured on the shared Shipit instance with `webhook_secret = S`.
2. Attacker learns the SHA of a commit `deadbeef...` belonging to `victim-org/victim-repo`, tracked by a `Stack` on the same instance.
3. Attacker POSTs to `/webhooks` with header `X-Github-Event: status`, body:
```json
{
  "sha": "deadbeef...",
  "state": "success",
  "context": "ci/forged",
  "repository": { "owner": { "login": "AttackerOrg" }, "full_name": "AttackerOrg/anything" }
}
```
4. Attacker signs the raw body with secret `S` and sets `X-Hub-Signature` accordingly.
5. `WebhooksController#verify_signature` resolves `repository_owner => "AttackerOrg"`, fetches `Shipit.github(organization: "AttackerOrg")`, and verifies successfully since the attacker used the correct secret `S` [8](#0-7) .
6. `StatusHandler#process` runs `Commit.where(sha: "deadbeef...")`, finds the victim's commit (owned by an unrelated org), and calls `commit.create_status_from_github!(params)`, writing a forged `success` status onto it [3](#0-2) .
7. The victim's commit now shows as `deployable?`/CI-green, potentially triggering an unauthorized deploy via continuous delivery or a human-approved `require_ci` deploy.

      verified = github_app.verify_webhook_signature(
