## Title
Attacker-controlled PR labels can override `Shipit.env`/`Stack#env` keys (e.g. `GITHUB_TOKEN`, `GITHUB_DOMAIN`, custom operator secrets) in the merged task environment - ([File: app/models/shipit/review_stack.rb])

## Summary
`ReviewStack#env` merges upcased PR label names directly into the stack env hash returned to `TaskCommands#env`, which then merges that hash on top of `super` (which itself already contains `Shipit.env` plus `GITHUB_DOMAIN`/`GITHUB_TOKEN` from `Commands#base_env`) before applying a small fixed set of hardcoded keys. Any key not in that fixed hardcoded list, and not re-set by `deploy_spec.machine_env` or `@task.env`, can be permanently overridden by a label whose upcased name matches it.

## Finding Description
The claimed binding — "for every key K in `Shipit.env`'s output, K must not be re-definable by `pull_request.labels`" — is **broken**, but only for keys outside the specific hardcoded set.

Trace:
- `Shipit::TaskCommands#env` (`lib/shipit/task_commands.rb:33-48`) builds env as: `super` → `.merge(@stack.env)` → `.merge({SHIPIT_USER, EMAIL, BUNDLE_PATH, SHIPIT_LINK, TASK_ID, IGNORED_SAFETIES, GIT_COMMITTER_NAME, GIT_COMMITTER_EMAIL})` → `.merge(deploy_spec.machine_env)` → `.merge(@task.env)`. [1](#0-0) 
- `super` resolves to `Commands#env` → `base_env`, which is `Shipit.env.merge('GITHUB_DOMAIN' => ..., 'GITHUB_TOKEN' => ...)`. [2](#0-1) 
- For a `ReviewStack`, `@stack.env` is overridden to be `super.merge(pull_request.labels.each_with_object({}){|l,h| h[l.upcase]="true"})` — i.e. `Stack#env`'s fixed keys (`ENVIRONMENT`, `LAST_DEPLOYED_SHA`, `GITHUB_REPO_OWNER`, `GITHUB_REPO_NAME`, `DEPLOY_URL`, `BRANCH`) merged with attacker-controlled upcased label names. [3](#0-2) [4](#0-3) 
- This `@stack.env` (containing the label-derived keys) is merged into `TaskCommands#env` at line 35, i.e. directly on top of `super` (which carries `Shipit.env`, `GITHUB_DOMAIN`, `GITHUB_TOKEN`). Only the 8 hardcoded literal keys (line 37-44) are guaranteed to win over a label of the same name. Any other key present in `Shipit.env`/`base_env` — including `GITHUB_TOKEN`, `GITHUB_DOMAIN`, or any operator-defined custom key in `Shipit.env` — is only restored afterward if `deploy_spec.machine_env` or `@task.env` happen to redefine it. Neither of those is guaranteed to do so generically, since `deploy_spec.machine_env` is repository-defined (from the repo's own `shipit.yml`, not from Shipit's own env layer) and `@task.env` is task-specific, filtered variables, not a mirror of `Shipit.env`.

This confirms the binding stated in the question: a label named e.g. `GITHUB_TOKEN` or any custom `Shipit.env` key survives into the final env used to build `Command`s for that task's steps, unless the deploy spec's `machine_env` or task env happens to redefine that exact key. The only keys *guaranteed* to be protected are the 8 hardcoded ones in `TaskCommands#env` (`SHIPIT_USER`, `EMAIL`, `BUNDLE_PATH`, `SHIPIT_LINK`, `TASK_ID`, `IGNORED_SAFETIES`, `GIT_COMMITTER_NAME`, `GIT_COMMITTER_EMAIL`).

However, I was unable to fully confirm two things within available context/tools:
1. The exact contents of `Shipit.env` (`lib/shipit.rb`) — I could not retrieve its definition/default value in this session, so I cannot confirm whether it contains any secret-bearing keys by default in this repo, or whether it's operator-configurable to contain such keys.
2. Whether PR labels reaching `pull_request.labels` are trust-gated by webhook signature verification (`verify_signature`/`GitHubApp#verify_webhook_signature`) before being persisted — meaning the attacker would need actual label-edit permission on the PR (typically requiring write access to the repository, which is stated as available to the attacker for "their own" repo per the threat model), not a forged webhook. I was not able to inspect `PullRequest#labels=`/the labeled-event handler code in this session to fully confirm the exact attacker path (webhook signature checks, `label_capturing_handler`), so the "attacker controls labels without any repo permission" precondition is not independently verified here.

## Impact Explanation
If exploitable as described, an attacker who can label a pull request belonging to a `ReviewStack`-eligible repository can override any `Shipit.env` key (including `GITHUB_TOKEN`/`GITHUB_DOMAIN` from `base_env`, or any operator-configured secret path/key not in the fixed hardcoded list) for that stack's tasks, as long as the deploy spec's `machine_env`/`task.env` doesn't happen to redefine it. This could corrupt or redirect build/deploy behavior (e.g., point at a different `GITHUB_DOMAIN`/token value, or override an operator's custom `Shipit.env` variable used by deploy scripts), potentially enabling downstream command misbehavior depending on what the repository's own build scripts do with that variable — this is a cross-cutting environment-override issue scoped to the specific `ReviewStack`/PR being labeled, not automatically to other repositories' stacks.

## Likelihood Explanation
Requires: (1) the target repository must use `Shipit::ReviewStack` (review-app feature), (2) the attacker must be able to attach a label to the PR that becomes the review stack's `pull_request`, and (3) the overridden key must not be one of the 8 hardcoded keys, and must not be re-set by `deploy_spec.machine_env`/`@task.env`. Whether label-setting is truly available to an unprivileged attacker (vs. requiring write/triage access on GitHub) was not independently confirmed in this session.

## Recommendation
In `ReviewStack#env` / `TaskCommands#env`, ensure label-derived keys cannot shadow any reserved/system key: either merge `pull_request.labels` env first (before `super`/`Shipit.env`) so later merges always win, or explicitly filter label names against a denylist/allowlist (e.g., only accept label names not colliding with `Stack#env`, `Shipit.env`, or `base_env` keys) before upcasing them into the env hash.

## Proof of Concept
Not provided — full confirmation of the exact attacker-reachable path (label-write authorization and `Shipit.env` contents) could not be completed within this session's tool budget; a live Devin session with full repo access would be needed to write and validate a minitest reproduction (stub `Shipit.env` with a marker key, add a matching label to a `PullRequest`, assert `TaskCommands.new(task).env[marker_key]` is unaffected).
