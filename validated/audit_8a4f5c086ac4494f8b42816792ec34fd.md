### Title
Missing upper-bound validation on `commission_bps` in `update_commission_bps` allows commission > 100% - (File: `programs/vote/src/vote_state/mod.rs`)

### Summary
The `update_commission_bps` function, which implements SIMD-0291's basis-points commission update, accepts a raw `u16` `commission_bps` value from the authorized withdrawer and stores it directly into vote state without ever checking that it does not exceed `10_000` (100% in basis points). This is the same bug class as the external report: a fee/commission-setting function with no upper-bound check against its full-scale value (`BPS`), which can push a value-splitting calculation out of its valid range.

### Finding Description
`update_commission_bps` only verifies that the `BlockRevenue` kind is gated by a feature flag and that the authorized withdrawer signed; it never validates the numeric range of `commission_bps` before storing it: [1](#0-0) 

Compare this with the legacy `update_commission` path, which uses a `u8` (naturally bounded to 0-255 and conventionally interpreted as a 0-100 percentage), whereas the new bps field is a `u16` that can hold values up to `65_535` — more than six times the valid `10_000` bps (100%) ceiling: [2](#0-1) 

The `VoteInstruction::UpdateCommissionBps` handler in the processor simply forwards the caller-supplied value without validation, gated only by feature flags for whether the instruction/kind is enabled at all — not by any bounds check on the value itself: [3](#0-2) 

Because commission-in-bps is meant to represent a fraction of rewards (validator share out of `10_000`), any downstream reward-splitting arithmetic that computes `validator_share = rewards * commission_bps / 10_000` and `delegator_share = rewards - validator_share` implicitly assumes `commission_bps <= 10_000`. Allowing an authorized withdrawer to set `commission_bps` above `10_000` breaks that invariant analogous to the reported `feeTake_ <= BPS` omission.

### Impact Explanation
If `commission_bps` is stored above `10_000`, any reward-distribution logic keyed off this value that computes `validator_share` as a fraction of total rewards and then derives the delegator remainder via subtraction could produce a validator share exceeding total rewards, causing either an arithmetic underflow/panic in the reward-distribution path (a potential halt of that computation) or a miscalculated (over)payment to the validator relative to delegators (misattributed rewards). This matches the "misattributed or duplicated rewards" / "epoch-boundary halt" impact categories.

### Likelihood Explanation
The path is reachable by any account that holds the vote account's authorized-withdrawer key (an unprivileged, non-operator-role capability from the protocol's perspective — any wallet can be designated as authorized withdrawer), requiring only a single signed `UpdateCommissionBps` instruction once the relevant feature (`commission_rate_in_basis_points` + `delay_commission_updates`) is active: [4](#0-3) 
No epoch-timing restriction or other gate limits how large a value can be set, unlike the legacy percentage-based commission which is bounded by the `u8` type.

### Recommendation
Add an explicit range check in `update_commission_bps` (and/or in the instruction processor) rejecting `commission_bps > 10_000` with `InstructionError::InvalidInstructionData` before calling `vote_state.set_inflation_rewards_commission_bps` / `set_block_revenue_commission_bps`, mirroring the recommended `require(feeTake_ <= BPS)` check from the external report.

### Proof of Concept
1. Create/activate a vote account on a cluster with `commission_rate_in_basis_points` and `delay_commission_updates` features enabled, using `VoteStateV4`.
2. As the authorized withdrawer, submit `VoteInstruction::UpdateCommissionBps { commission_bps: 60_000, kind: CommissionKind::InflationRewards }`.
3. Observe that `update_commission_bps` accepts and stores `60_000` (600%) with no error, as shown by the unrestrained call path in [5](#0-4) .
4. Any subsequent reward computation relying on `commission_bps <= 10_000` will operate on an out-of-range fraction, producing incorrect share calculations or an arithmetic panic.

/// Update the vote account's commission
pub fn update_commission<S: std::hash::BuildHasher>(
    vote_account: &mut BorrowedInstructionAccount,
    target_version: VoteStateTargetVersion,
    commission: u8,
    signers: &HashSet<Pubkey, S>,
    epoch_schedule: &EpochSchedule,
    clock: &Clock,
    disable_commission_update_rule: bool,
) -> Result<(), InstructionError> {
    let vote_state_result = get_vote_state_handler_checked(vote_account, target_version);
    let enforce_commission_update_rule = !disable_commission_update_rule
        && match vote_state_result.as_ref() {
            Ok(decoded_vote_state) => commission > decoded_vote_state.commission(),
            Err(_) => true,
        };

    if enforce_commission_update_rule && !is_commission_update_allowed(clock.slot, epoch_schedule) {
        return Err(VoteError::CommissionUpdateTooLate.into());
    }

    let mut vote_state = vote_state_result?;

    // current authorized withdrawer must say "yay"
    verify_authorized_signer(vote_state.authorized_withdrawer(), signers)?;

    vote_state.set_commission(commission);

    vote_state.set_vote_account_state(vote_account)
}

/// Update the vote account's commission in basis points (SIMD-0291, SIMD-0123).
pub fn update_commission_bps<S: std::hash::BuildHasher>(
    vote_account: &mut BorrowedInstructionAccount,
    target_version: VoteStateTargetVersion,
    commission_bps: u16,
    kind: CommissionKind,
    signers: &HashSet<Pubkey, S>,
    block_revenue_sharing_enabled: bool,
) -> Result<(), InstructionError> {
    // Per SIMD-0291: BlockRevenue returns InvalidInstructionData unless
    // SIMD-0123 (block_revenue_sharing) is enabled.
    if matches!(kind, CommissionKind::BlockRevenue) && !block_revenue_sharing_enabled {
        return Err(InstructionError::InvalidInstructionData);
    }

    let mut vote_state = get_vote_state_handler_checked(vote_account, target_version)?;

    // No commission update rule, per SIMD-0249 and SIMD-0291.

    // Require authorized withdrawer to sign.
    verify_authorized_signer(vote_state.authorized_withdrawer(), signers)?;

    match kind {
        CommissionKind::InflationRewards => {
            vote_state.set_inflation_rewards_commission_bps(commission_bps);
        }
        CommissionKind::BlockRevenue => {
            vote_state.set_block_revenue_commission_bps(commission_bps);
        }
    }

    vote_state.set_vote_account_state(vote_account)
}
