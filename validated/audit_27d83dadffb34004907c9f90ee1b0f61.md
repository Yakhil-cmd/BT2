### Title
`DepositDelegatorRewards` allows any signer to grief vote-account withdrawals/closures via unauthorized `pending_delegator_rewards` inflation - (File: `programs/vote/src/vote_state/mod.rs`)

### Summary
The `VoteInstruction::DepositDelegatorRewards` instruction (SIMD-0123) can be invoked by *any* transaction signer with as little as a few lamports, targeting *any* vote account, with no requirement that the caller hold any authority over that vote account. This lets an unprivileged attacker unilaterally increment a victim vote account's `pending_delegator_rewards` field immediately before a legitimate `Withdraw` transaction lands, causing that withdrawal (sized against the pre-attack state) to revert with `InsufficientFunds` — mirroring the Timeswap `pay()` DOS where an attacker front-runs with a negligible amount to force an arithmetic check to fail on the victim's transaction.

### Finding Description
`deposit_delegator_rewards` in `programs/vote/src/vote_state/mod.rs:940-993` only requires that the *sender* account (the lamport source) sign the transaction: [1](#0-0) 
It performs no check that the caller is the vote account's authorized withdrawer, staker, or voter — it validates only that the target account deserializes as an initialized `VoteStateV4`, then unconditionally CPIs a System transfer from the (unrelated) signer into the vote account and bumps `pending_delegator_rewards` by the deposited amount: [2](#0-1) 

The `withdraw` function later reads `pending_delegator_rewards` and uses it as a hard floor/blocker for withdrawals: [3](#0-2) 

Specifically:
- If the withdrawer attempts to fully close the account (`remaining_balance == 0`), the instruction fails with `InstructionError::InsufficientFunds` whenever `pending_delegator_rewards > 0`.
- If the withdrawer attempts a partial withdrawal, the required `min_balance` is `rent_exempt_minimum + pending_delegator_rewards`; the withdrawer's max-safe amount (typically computed off-chain, e.g. via `check_remaining_balance` in `cli/src/vote.rs`) is invalidated if an attacker deposits even 1 lamport of `pending_delegator_rewards` between quote-time and execution-time.

Because `DepositDelegatorRewards` has no relationship requirement to the vote account's authorities, an attacker can watch the mempool for a withdrawer's `Withdraw` transaction (which encodes a specific `lamports` amount computed against the *current* `pending_delegator_rewards`), and front-run it with a trivial `DepositDelegatorRewards { deposit: 1 }` targeting the same vote account. This raises `pending_delegator_rewards` just enough that the victim's precomputed withdrawal amount now violates the `remaining_balance >= min_balance` (or `== 0`) invariant, causing the legitimate withdraw to revert. The attacker can repeat this indefinitely at near-zero cost (the deposited lamports are not lost — they land in the vote account and simply reappear as `pending_delegator_rewards`, which is only fully cleared via epoch-based reward distribution in `runtime/src/bank/partitioned_epoch_rewards/calculation.rs` / `runtime/src/bank/fee_distribution.rs`, an event outside the attacker's or victim's direct control that occurs at most once per epoch), giving the attacker a durable griefing lever similar to the Timeswap "repay 1 wei" attack.

### Impact Explanation
This is a griefing / availability issue rather than a fund-theft or consensus bug: the withdraw authority's transaction repeatedly reverts, wasting fees and delaying legitimate withdrawal/closure of the vote account, and an attacker can specifically target the "close account" path (`remaining_balance == 0`) to make full closure of a vote account effectively impossible for the duration of the attack window (bounded by the next epoch's reward distribution, which the attacker can re-grief afterward). No stake, rewards, or lamports are stolen; this is a targeted availability degradation, analogous in class (though lower severity, given SOL's bounded decimal precision and the requirement to re-attack after each epoch) to the original Timeswap medium-severity finding.

### Likelihood Explanation
The instruction is fully permissionless from the perspective of the target vote account (only the unrelated *source* account must sign), reachable from a single submitted transaction, and requires no special privilege, precompile, or leader cooperation — any user can construct and repeatedly submit `DepositDelegatorRewards` instructions against any vote account of interest at the cost of only the lamports deposited (which are not burned, minimizing attacker cost). This makes exploitation straightforward and cheap, though its impact is limited to temporary DOS of a specific withdrawal/close operation rather than a stronger security guarantee violation.

### Recommendation
Require an authorization or intent check before mutating a third-party vote account's `pending_delegator_rewards`, or decouple the `withdraw` size-safety check from a value that can be unilaterally inflated by unrelated parties — e.g., allow the withdrawer to specify "withdraw remaining minus current pending rewards" atomically, add a maximum per-transaction/per-slot cap on unsolicited deposits, or require the withdraw authority's co-signature/allow-list for `DepositDelegatorRewards` targets. At minimum, document and mitigate the front-running window in the CLI/RPC tooling (e.g., recompute `pending_delegator_rewards` immediately before submission and retry with updated bounds).

### Proof of Concept
1. Attacker observes (or predicts) that a vote account's authorized withdrawer is about to submit `VoteInstruction::Withdraw(lamports)` sized to close the account (targeting `remaining_balance == 0`), based on the vote account's current `pending_delegator_rewards == 0`.
2. Attacker submits `VoteInstruction::DepositDelegatorRewards { deposit: 1 }` for that same vote account, signing only with their own unrelated funded keypair as the source account (see accounts layout in `programs/vote/src/vote_processor.rs:391-408`, requiring only `check_number_of_instruction_accounts(2)` and the source signer).
3. If the attacker's transaction lands first, `pending_delegator_rewards` becomes `1`.
4. The victim's `Withdraw(lamports)` transaction, which assumed `pending_delegator_rewards == 0`, now hits: [4](#0-3) 
and fails with `InstructionError::InsufficientFunds`.
5. Attacker repeats step 2 before every subsequent retry by the withdrawer, indefinitely delaying the close/withdraw until an epoch boundary triggers a reward-distribution event that clears `pending_delegator_rewards` — after which the attacker can immediately re-deposit and repeat.

        .get_lamports()
        .checked_sub(lamports)

    // Always zero until SIMD-0123 is activated.
    let pending_delegator_rewards = vote_state.pending_delegator_rewards();

    if remaining_balance == 0 {
        // SIMD-0123: vote account cannot be closed if
        // pending_delegator_rewards > 0.
        if pending_delegator_rewards > 0 {
            return Err(InstructionError::InsufficientFunds);
        }

        let reject_active_vote_account_close = vote_state
            .epoch_credits()
            .last()
            .map(|(last_epoch_with_credits, _, _)| {
                let current_epoch = clock.epoch;
                // if current_epoch - last_epoch_with_credits < 2 then the validator has received credits
                // either in the current epoch or the previous epoch. If it's >= 2 then it has been at least
                // one full epoch since the validator has received credits.
                current_epoch.saturating_sub(*last_epoch_with_credits) < 2
            })
            .unwrap_or(false);

        if reject_active_vote_account_close {
            return Err(VoteError::ActiveVoteAccountClose.into());
        } else {
            // Deinitialize upon zero-balance
            VoteStateHandler::deinitialize_vote_account_state(&mut vote_account, target_version)?;
        }
    } else {
        // SIMD-0123: withdrawable balance when pending_delegator_rewards > 0
        // is lamports - pending_delegator_rewards - rent_exempt_minimum.
        let min_rent_exempt_balance = rent_sysvar.minimum_balance(vote_account.get_data().len());
        let min_balance = min_rent_exempt_balance
            .checked_add(pending_delegator_rewards)
            .ok_or(InstructionError::ArithmeticOverflow)?;
        if remaining_balance < min_balance {
            return Err(InstructionError::InsufficientFunds);
