### Title
Attacker-controlled PR label overrides `PATH` in deploy commands via `ReviewStack#env` — (File: `app/models/shipit/review_stack.rb`)

### Summary
`Shipit::ReviewStack#env` merges every pull-request label name (upcased, hardcoded value `"true"`) into the stack's environment hash without any allow-list, and this hash flows unfiltered through `TaskCommands#env` into `Command#unbundled_env`, where it is merged *after* the safe `Shipit.shell_paths`-derived `PATH`. An attacker who can label their own fork's PR (e.g., with a label literally named `PATH`) can therefore clobber the `PATH` environment variable used by `PTY.spawn` for that review stack's deploy/task commands. Because the attacker also fully controls the checked-out working directory content (their own PR branch), this can be leveraged into arbitrary binary resolution when unqualified commands are invoked during deploy/task execution.

### Finding Description
The broken binding: `Command#unbundled_env`'s key set is expected to satisfy `PATH == "#{Shipit.shell_paths.join(':')}:#{ENV['PATH']}"`, but this equality does **not hold** whenever `@env` (the hash passed via `env:`) contains a `'PATH'` key, because:

```ruby
# lib/shipit/command.rb
def unbundled_env
  BASE_ENV.merge('PATH' => "#{Shipit.shell_paths.join(':')}:#{ENV['PATH']}").merge(@env.stringify_keys)
end
``` [1](#0-0) 

the caller-supplied `@env` is merged **last**, so any `'PATH'` key in it wins.

The untrusted `PATH` key originates in `ReviewStack#env`:
```ruby
def env
  return super unless pull_request.present?
  super.merge(
    pull_request.labels.each_with_object({}) { |label_name, labels| labels[label_name.upcase] = "true" }
  )
end
``` [2](#0-1) 

`pull_request.labels` is persisted straight from the GitHub webhook payload by `LabelCapturingHandler#capture_labels` (`pull_request.update!(labels: params.pull_request.labels.map(&:name))`) with no name whitelist — any label name a repo collaborator can attach to the PR (including on their own fork's PR, subject to the repo's label set) becomes an upcased env key. [3](#0-2) 

This hash is merged, unfiltered, into `TaskCommands#env`:
```ruby
def env
  super
    .merge(@stack.env)          # <- attacker-controlled PATH from labels enters here
    .merge('SHIPIT_USER' => ..., ...)
    .merge(deploy_spec.machine_env)
    .merge(@task.env)
end
``` [4](#0-3) 

and that full hash is passed as `env:` directly to `Command.new` in `perform`/`install_dependencies`, which run the deploy/task scripts (unlike `Commands#git`, whose git-plumbing calls use a separate minimal `base_env`). [5](#0-4) 

Note that `EnvironmentVariables#permit`/`VariableDefinition` whitelisting (`filter_deploy_envs`, `filter_envs`) exists and is applied to the *user-supplied* `env` parameter for API-triggered deploys (`Stack#build_deploy`), but it is **never** applied to the composite hash returned by `TaskCommands#env`/`ReviewStack#env` that is actually handed to `Command`. That whitelist therefore does not protect this path. [6](#0-5) [7](#0-6) 

This exact behavior (labels flowing unfiltered into env, including for `TaskCommands`) is already asserted by existing tests, confirming the code path is reachable and intended to work this way for arbitrary label names: [8](#0-7) [9](#0-8) 

### Impact Explanation
If an attacker names a label `PATH`, the final `Command#env` for that review stack's tasks/deploys will contain `'PATH' => 'true'` instead of the safe `"#{Shipit.shell_paths}:#{ENV['PATH']}"` value. Because the attacker also controls the checked-out repository content for their PR branch (chdir for the running command), a relative `PATH="true"` opens the door to binary-resolution hijacking if the attacker places an executable of the same basename as an invoked command (e.g., `bundle`, `rake`, custom deploy script names) inside a directory literally named `true` in their fork. Subsequent `git`/deploy commands invoked through `PTY.spawn` for that stack would then resolve to the attacker-controlled binary — RCE on the deploy host, scoped to whatever repository/stack their PR belongs to. The value is fixed to the string `"true"` (not arbitrary attacker text), which limits (but does not eliminate) exploitability to this relative-path-hijack scenario, since the attacker cannot inject an absolute malicious path directly.

### Likelihood Explanation
Preconditions: the target repository must have review stacks enabled and reachable via a webhook-created `ReviewStack` with an associated `PullRequest`; the attacker needs only the ability to open/label a PR against that repository (label addition on your own PR is typically unprivileged for external contributors on public repos, subject to the repo's label configuration). No Shipit credentials are required — `LabelCapturingHandler` relies on the webhook payload's `pull_request.labels`, gated by normal webhook signature verification only, not by content trust of label names. However, review stacks are created with `continuous_deployment: false` by default, so the corrupted `PATH` only takes effect the next time a task/deploy actually runs for that review stack (triggered by a maintainer or automation), and the follow-on RCE additionally requires the attacker to place a matching malicious binary under a `true`-named directory in their branch and requires an unqualified/relative command lookup to occur. This raises the practical bar from "trivial to trigger" to "requires an actual task run on the review stack plus a crafted working-tree layout."

### Recommendation
- In `Command#unbundled_env`, protect reserved/security-sensitive keys (at minimum `PATH`) from being overridden by caller-supplied `env`, e.g. compute `PATH` after merging `@env`, or explicitly strip `PATH` (and other dangerous keys like `GIT_ASKPASS`, `BUNDLE_*`) from any untrusted env sources before merge.
- In `ReviewStack#env`, do not let PR label names become arbitrary env key names; either prefix them (e.g., `LABEL_<NAME>`) or restrict to a fixed allow-list of expected label keys, and explicitly filter out reserved variable names (`PATH`, `GIT_*`, `GITHUB_*`, `BUNDLE_*`, etc.).
- Apply `EnvironmentVariables#permit` (or an equivalent explicit deny-list) to the full composite env produced by `TaskCommands#env`/`ReviewStack#env`, not only to the caller-supplied deploy `env` parameter.

### Proof of Concept
```ruby
# test/models/shipit/review_stack_test.rb (new test)
test "#env does not allow pull request labels to override PATH" do
  stack = shipit_stacks(:review_stack)
  stack.pull_request.labels = ["PATH"]

  safe_path = "#{Shipit.shell_paths.join(':')}:#{ENV['PATH']}"
  command_env = Shipit::TaskCommands.new(shipit_tasks(:shipit_restart).tap { |t| t.stack = stack }).env
  command = Shipit::Command.new('true', env: command_env, chdir: '.')

  # demonstrates the broken binding: unbundled_env['PATH'] should equal safe_path but instead
  # equals the attacker-controlled label value.
  assert_equal 'true', command.unbundled_env['PATH']
  refute_equal safe_path, command.unbundled_env['PATH']
end
```
This test constructs the exact call chain `ReviewStack#env -> TaskCommands#env -> Command#unbundled_env`, and asserts the two sides of the claimed binding (`unbundled_env['PATH']` vs. the `Shipit.shell_paths`-derived value) diverge, confirming the finding.
