### Title
Asset holders can be permanently frozen out of spending `spender_attested` asset coins when the definer updates the attestor list - ([File: storage.js])

### Summary
For assets with `spender_attested: true`, spend-time validation in `validation.js` checks whether the *current, latest* attestor list still attests to the spender/output addresses, rather than the attestor list that was valid when the coins were originally issued or received. Because the asset definer can freely republish a new `asset_attestors` list at any time (`validateAttestorListUpdate`), and `storage.readAsset` always resolves to the single most recent attestor-list unit, a coin holder who legitimately received/held the asset while properly attested can become permanently unable to spend those coins the moment the definer swaps the attestor set — mirroring the reported bug class where a check re-applied at a later "withdrawal" step uses list state that changed after the user's position/request was already established.

### Finding Description
When an asset is created with `spender_attested = true`, every payment of that asset re-derives the currently valid attestor list and re-checks attestation at validation time:

- `storage.readAsset` fetches only the single most-recent attestor list unit for the asset (`ORDER BY level DESC LIMIT 1`), discarding any older attestor list that may have been in effect when a holder's coins were received: [1](#0-0) 

- `filterAttestedAddresses` then checks the `attestations` table against `objAsset.arrAttestorAddresses` — i.e., the *current* attestor set — and additionally requires the attestation to be newer than the address's last definition change: [2](#0-1) 

- On every spend, `validatePayment` requires the author (spender) addresses to be in `arrAttestedAddresses` computed from this current list: [3](#0-2) 

- Likewise, receiving further coins of the asset requires all output addresses to currently be attested: [4](#0-3) 

- The asset definer can change the attestor list at will via an `asset_attestors` message, subject only to being the definer — no protection is given to holders whose coins were issued/attested under a prior list: [5](#0-4) 

Because coin ownership on the DAG cannot be "rolled back" or reissued once recorded, if the definer republishes a different attestor set (dropping the attestor who originally attested a given holder, or simply replacing all attestors), any address whose attestation depended on the old list immediately fails the spend-time check in `validatePayment`, permanently freezing that holder's balance of the asset — with no way to become spendable again unless the definer happens to restore an attestor who re-attests them. This is structurally identical to the reported issue: a gating check (`onlyAllowedProviders`/attestor whitelist) is evaluated at the *action* (withdraw/spend) time using list state that can diverge from the state when the user's holding was legitimately established, instead of pinning it to that trusted qualifying event.

### Impact Explanation
An unprivileged asset holder can have their entire balance of a `spender_attested` asset permanently frozen (unable to spend or transfer) purely due to a definer-side attestor-list update that has nothing to do with the holder's own conduct. This is a fund-freezing bug affecting ordinary token holders reachable through normal DAG usage (posting a payment unit), not an operator/administrator themselves.

### Likelihood Explanation
Any asset issuer using `spender_attested` and later rotating its attestor set (e.g., replacing a compromised or discontinued attestation provider, or adding new attestors while dropping old ones) will trigger this for every holder who was only ever attested by the removed attestor(s). This is a normal, expected asset-management operation (not requiring any special/rare conditions), making the freeze likely to occur in ordinary asset lifecycle management rather than only in edge cases.

### Recommendation
Anchor the attestation requirement used for spending to the attestor list (and attestation) that was valid at the time the specific coin/output was created (or at least allow validation against any historically valid, still-unrevoked attestation chain), rather than always requiring current attestation against the single latest attestor list. Alternatively, only apply the spender-attested check for the *receiving* transfer, not for subsequent spends of coins already accepted into the DAG under valid attestation, similar to removing `onlyAllowedProviders` from `withdrawAvailableCollateral()` in the original report so that a state change occurring after a fund position is established cannot retroactively block access to it.

### Proof of Concept
1. Definer creates asset `A` with `spender_attested: true` and attestor list `[Attestor1]`.
2. `Attestor1` attests holder `H`; `H` receives a payment of asset `A` (passes the output-attestation check in `validatePaymentInputsAndOutputs`, lines 2630-2641).
3. Definer later publishes an `asset_attestors` message changing the list to `[Attestor2]` (allowed unconditionally by `validateAttestorListUpdate`, lines 2829-2847).
4. `H` attempts to spend the previously received coins. `validatePayment` (lines 2115-2122) calls `loadAssetWithListOfAttestedAuthors` → `readAsset` (lines 1917-1946), which now resolves the attestor list to `[Attestor2]` only.
5. `filterAttestedAddresses` (lines 1959-1974) finds no attestation of `H` by `Attestor2`, so `arrAttestedAddresses` is empty, and the payment is rejected with `"none of the authors is attested"`.
6. `H`'s coins remain permanently unspendable unless `Attestor2` (or whichever attestor the definer currently trusts) independently chooses to attest `H` again — an outcome outside `H`'s control.

function validateAttestorListUpdate(conn, payload, objUnit, objValidationState, callback){
	if (objUnit.authors.length !== 1)
		return callback("attestor list must be single-authored");
	if (!isNonemptyObject(payload))
		return callback("attestor update must be a non-empty object");
	if (hasFieldsExcept(payload, ['asset', 'attestors']))
		return callback("foreign fields in attestor list update");
	storage.readAsset(conn, payload.asset, objValidationState.last_ball_mci, false, function(err, objAsset){
		if (err)
			return callback(err);
		if (!objAsset.spender_attested)
			return callback("this asset does not require attestors");
		if (objUnit.authors[0].address !== objAsset.definer_address)
			return callback("attestor list can be edited only by definer");
		err = checkAttestorList(payload.attestors);
		if (err)
			return callback(err);
		callback();
	});
