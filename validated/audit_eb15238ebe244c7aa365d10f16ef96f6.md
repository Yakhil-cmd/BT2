### Title
Cross-repository CI status forgery via unscoped `Commit.where(sha:)` lookup enables unauthorized PR merges - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits purely `by sha` with no scoping to the stack/repository named in the verified webhook payload, so a `status` webhook signed for repository A can write a `Status` record onto a `Commit` row that belongs to a completely different stack/repository B, as long as both share an identical git commit sha (trivially achievable, e.g. via an empty-tree commit). If that commit is the `head` of a pending `MergeRequest` in stack B, this forged status can satisfy `MergeRequest::StatusChecker#success?` and cause `ProcessMergeRequestsJob` to call `merge_request.merge!`, merging a PR in tenant B's repository using only a webhook against tenant A's repository.

### Finding Description
The broken binding: `Commit#stack.repository.full_name == verified_webhook.payload['repository']['full_name']` — this is never checked.

Path:
- `WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-49`) only verifies that the signature matches the GitHub App secret for `repository_owner` (the org in the payload). It authenticates *who sent the webhook*, not *which commit rows the payload is allowed to mutate*.
- `StatusHandler#process` then does:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
`app/models/shipit/webhooks/handlers/status_handler.rb:20-24` — this is a global, unscoped `Commit` lookup by `sha` only, with no `stack_id`/repository filter tying it back to `params['repository']['full_name']`.
- The `Commit` table's uniqueness/index is `(stack_id, sha)` (`db/migrate/20170524104615_index_commits_on_stack_id_and_sha.rb`), not a global unique index on `sha`. This confirms the schema explicitly allows multiple `Commit` rows across different stacks to share the same sha — a designed possibility that `StatusHandler` fails to account for.
- `Commit#create_status_from_github!` (`app/models/shipit/commit.rb:165-169`) writes a `Status` row scoped to `commit.stack_id`, i.e. whatever stack happens to own the colliding `Commit` row — not the stack that owns the webhook's named repository.
- If that commit is a `MergeRequest#head` in stack B, `MergeRequest#all_status_checks_passed?` (`app/models/shipit/merge_request.rb:193-197`) reads `head.statuses_and_check_runs` from the DB, which now includes the attacker-forged status.
- `ProcessMergeRequestsJob#perform` (`app/jobs/shipit/process_merge_requests_job.rb:21-30`) calls `merge_request.refresh!` (re-fetches real GitHub statuses for stack B's actual sha) then checks `all_status_checks_passed?` and calls `merge_request.merge!` → `stack.github_api.merge_pull_request` (`app/models/shipit/merge_request.rb:164-176`), an authenticated GitHub mutation performed with tenant B's own installation credentials.

Exploit flow: Attacker (owner of repo A, unprivileged w.r.t. Shipit/repo B) crafts a commit in repo A whose sha collides with the head sha S of a pending MergeRequest in repo B (e.g., both are the well-known empty-tree sha, or the attacker can construct any commit whose content/tree/parents/timestamps hash identically — full SHA-1 collision is not required if the required CI context in B is simply *missing* rather than actively failing, since `StatusChecker` treats a present matching-context success as satisfying "missing" checks; identical hex sha is required for the row match itself, which is realistic for the empty-tree commit or any commit two repos happen to construct identically). Attacker then triggers/POSTs a `status` event from repo A (a repository they legitimately own and can sign webhooks for) with `sha: S`, `state: "success"`, `context: <required-context-name-for-stack-B>`. This is validly signed by GitHub for repo A's org. `StatusHandler#process` finds *all* `Commit` rows with sha `S` — including the one in stack B — and attaches the forged success `Status` to it.

Existing guards fail because: `verify_signature` only checks that the sending org matches the payload's declared org — it never cross-checks that the *content* of the payload (sha ownership) belongs to that org's repositories; `drop_unhandled_event`/`ExplicitParameters` only validate the payload's shape, not the sha's provenance; and there is no `stacks.where(repository: ...)`/`Repository` join in `StatusHandler#process` the way e.g. `CheckSuiteHandler` scopes by `stacks.where(branch: ...)` before touching commits — `StatusHandler` is the outlier that skips this scoping entirely.

### Impact Explanation
A successful exploit results in `merge_request.merge!` calling `stack.github_api.merge_pull_request` for stack B using stack B's own GitHub App credentials, i.e., an unauthorized merge into a repository the attacker does not control, triggered solely by a webhook the attacker legitimately sent for a repository they do own. This matches the Critical category "a payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy, rollback or merge." The attack is repeatable against any stack whose merge-request head sha can be made to collide with a sha the attacker controls in their own repo, and is not limited to a single victim repository — any tenant using merge queues (`merge_queue_enabled`) is exposed. Blast radius spans arbitrary Shipit tenants sharing the same Shipit instance.

### Likelihood Explanation
Preconditions: victim stack B must have `merge_queue_enabled` / merge-request gating configured, and have a `MergeRequest` currently `pending` whose head sha is exactly reproducible by an attacker in a repo they own (trivial for content-identical commits, e.g. empty-tree or any commit whose tree+parents+author/committer timestamps match — attacker needs no secrets, only the ability to open a PR and construct a commit, and to have GitHub deliver a `status` webhook for their own repo, which requires no privileges beyond owning that repo). No Shipit session, API token, or GitHub App key is needed. This is fully attacker-cost-free beyond crafting a matching commit and is repeatable against any target sha the attacker can predict or race.

### Recommendation
Scope the commit lookup in `StatusHandler#process` to the stack(s) identified by the webhook's own `repository.full_name`/`owner`+`name`, analogous to how `CheckSuiteHandler` scopes via `stacks.where(...)`. E.g., resolve `stacks = Stack.joins(:repository).where(repositories: { owner: params.repository.owner.login, name: params.repository.name })` (or equivalent identification available in the handler's context) and restrict `Commit.where(sha: params.sha, stack: stacks)` before calling `create_status_from_github!`, ensuring a status webhook can only affect commits belonging to the stack(s) whose repository matches the verified webhook payload.

      end

      true

      false
    rescue Octokit::Conflict # shas didn't match, PR was updated.

    end

    def perform(stack)
      merge_requests = stack.merge_requests.to_be_merged.to_a
      merge_requests.each do |merge_request|
        merge_request.refresh!
        merge_request.reject_unless_mergeable!
        merge_request.cancel! if merge_request.closed?
        merge_request.revalidate! if merge_request.need_revalidation?
      end

      return false unless stack.allows_merges?

      merge_requests.select(&:pending?).each do |merge_request|
        merge_request.refresh!
        next unless merge_request.all_status_checks_passed?

        begin
          merge_request.merge!
        rescue MergeRequest::NotReady
          ProcessMergeRequestsJob.set(wait: 10.seconds).perform_later(stack)
          return false
        end
      end
    end
