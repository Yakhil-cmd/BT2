## Finding

The webhook signature check in `WebhooksController` selects which organization's `webhook_secret` to verify against using an **unauthenticated, attacker-controlled** field, while the handlers that act on the payload use a **different** field to decide which stack/commit/repository to mutate. Because both fields live inside the same JSON body and are never cross-checked, a party who legitimately owns one organization's webhook secret on a multi-tenant Shipit install can forge events for a completely different organization's repositories. [1](#0-0) 

`repository_owner` (used to pick the HMAC secret) is read from `params.dig('repository', 'owner', 'login')`, falling back to `params.dig('organization', 'login')`. This selects `github_app = Shipit.github(organization: repository_owner)` and verifies `X-Hub-Signature` against **that org's** `webhook_secret`. [2](#0-1) 

Meanwhile, the handlers resolve the target *independently* of that field:
- `StatusHandler` looks up commits **globally by sha**, with no repository/org scoping at all: [3](#0-2) 
- Other handlers (`PushHandler`, `CheckSuiteHandler`, PR handlers) resolve the stack via `payload.dig('repository', 'full_name')`, a sibling field of `repository.owner.login` inside the same `"repository"` object: [4](#0-3) 

Nothing enforces that `repository.owner.login` (what the signature was checked against) matches the owner encoded in `repository.full_name` (what is actually written) or the stack found by `sha`. A tenant who legitimately controls Org A's GitHub App (and therefore knows Org A's own `webhook_secret`, which they configured themselves as documented in `docs/setup.md`) can sign a payload with `repository.owner.login: "orgA"` while setting `repository.full_name` (or, for `StatusHandler`, simply a real `sha` of a commit belonging to a stack in a completely different tenant, Org B) that targets Org B's data.

The most damaging path is `StatusHandler`: a forged, successfully-"verified" (via Org A's secret) commit-status webhook can attach a fabricated `success` CI status to a real, public commit sha belonging to Org B's stack: [3](#0-2) 

That forged status is exactly what `MergeRequest` uses to decide CI has passed and to auto-merge the pull request through Shipit's own GitHub App credentials: [5](#0-4) [6](#0-5) 

`merge!` calls `stack.github_api.merge_pull_request` — Shipit's privileged app token performing a write on a repository the forging tenant does not own — an unauthorized merge into a foreign organization's repository, satisfying the "unauthorized merge" / cross-repository write impact.

### Title
Webhook signature verified against attacker-selectable organization enables cross-tenant forged CI statuses and unauthorized merges - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` picks the HMAC secret to validate a webhook using `repository.owner.login`/`organization.login`, fields taken straight from the unauthenticated JSON body, while the handlers that actually mutate state (especially `StatusHandler`, which matches commits globally by `sha` with no scoping at all) do not verify that the signed organization matches the repository/commit being acted upon.

### Finding Description
On a Shipit install configured for multiple GitHub organizations/App configs (`Shipit.github(organization: ...)`), each org has its own `webhook_secret`. `verify_signature` in `app/controllers/shipit/webhooks_controller.rb` (lines 24-49) derives the org whose secret is used to verify `X-Hub-Signature` from `repository_owner`, which is read at line 59-62 straight from the JSON payload (`repository.owner.login` or `organization.login`) — a value fully controlled by whoever sends the HTTP request.

The handler that actually consumes the trusted payload, `Shipit::Webhooks::Handlers::StatusHandler` (`app/models/shipit/webhooks/handlers/status_handler.rb`), applies the status update to `Commit.where(sha: params.sha)` with no repository or organization filter whatsoever. Other handlers key off `repository.full_name`, a sibling field to `repository.owner.login` inside the same JSON object, so the two are never required to be consistent.

Because signature verification only proves the request was signed with *some* configured org's secret — not necessarily the secret of the org that owns the repository/commit named elsewhere in the same payload — any tenant who legitimately knows their own org's `webhook_secret` can forge a fully "verified" webhook that carries data belonging to a different org's stack.

### Impact Explanation
Using their own valid webhook secret, a low-privileged tenant can inject a fabricated passing CI status onto a real commit sha of another organization's stack via `StatusHandler`. `MergeRequest#all_status_checks_passed?`/`merge!` treat that forged status as legitimate CI, causing Shipit's GitHub App credentials to call `merge_pull_request` and merge a pull request the attacker does not control, in a repository they were never authorized to touch. This is an unauthorized cross-repository merge performed with the app's own `GITHUB_TOKEN`, matching the Critical/High impact bar (unauthorized merge / cross-repository write). The same confusion can also feed forged CI signals into deploy-gating checks (`ci.require`), enabling unauthorized deploys to proceed.

### Likelihood Explanation
Exploitability requires only that the attacker already possesses a legitimately configured webhook secret for *any* one organization onboarded to the shared Shipit instance (a normal, low-privilege tenant capability, not the target's secret), plus knowledge of a target commit's sha, which is public GitHub information. No session, ApiClient token, or the victim organization's own secret is required — this crosses the credential/organization boundary defined by the report's binding-break rule.

### Recommendation
Bind webhook verification to the resource being mutated, not to an attacker-chosen field: after selecting `github_app` by `repository_owner`, re-derive/validate that the resolved repository/commit/stack actually belongs to that same verified organization before applying handler side effects. In particular, scope `StatusHandler`'s `Commit.where(sha: ...)` lookup to commits/stacks whose repository owner matches the verified `repository_owner`, and add an explicit consistency check between `repository.owner.login` and the owner encoded in `repository.full_name` for all handlers.

### Proof of Concept
1. Attacker is a legitimate tenant admin of `org-attacker` on a shared Shipit instance and knows `org-attacker`'s configured `webhook_secret`.
2. Attacker learns (from GitHub, publicly) the `sha` of a commit belonging to `org-victim/some-repo`, which is tracked as a stack in the same Shipit instance.
3. Attacker POSTs to `/webhooks` with header `X-Github-Event: status` and body:
```json
{
  "sha": "<victim-commit-sha>",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "org-attacker" } }
}
```
   signing `X-Hub-Signature` with `org-attacker`'s webhook secret.
4. `verify_signature` resolves `Shipit.github(organization: "org-attacker")` and successfully verifies the signature (`app/controllers/shipit/webhooks_controller.rb` lines 24-30).
5. `StatusHandler#process` writes a `success` status onto the victim's real commit, globally matched by `sha` with no org check (`app/models/shipit/webhooks/handlers/status_handler.rb` lines 20-24).
6. If the victim's pull request was pending merge, `MergeRequest#all_status_checks_passed?` now reports success and `merge!` calls `stack.github_api.merge_pull_request`, merging the PR using Shipit's own GitHub App token (`app/models/shipit/merge_request.rb` lines 164-191).

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
