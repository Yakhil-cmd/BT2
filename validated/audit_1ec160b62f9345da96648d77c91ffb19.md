### Title
Cross-organization webhook forgery — signed org (`repository.owner.login`) not bound to targeted repository (`repository.full_name`) allows cross-tenant stack mutation - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` validates the HMAC signature against the GitHub App configured for `params.dig('repository', 'owner', 'login')`, while every `pull_request` handler (including `LabelCapturingHandler`) resolves the target `Shipit::Repository`/stack via the independently-attacker-controlled `params.repository.full_name` field. Nothing enforces that these two fields refer to the same organization, so an attacker who owns a throwaway GitHub org registered in Shipit can sign a payload with their own known `webhook_secret` while pointing `repository.full_name` at a victim's repository, causing the handler to mutate the victim's stack/pull_request state.

### Finding Description
The intended binding is: `organization verifying the signature (params.repository.owner.login) == organization owning the repository whose stack is mutated (owner segment of params.repository.full_name)`.

Tracing the code:
- `verify_signature` computes `repository_owner = params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` and calls `Shipit.github(organization: repository_owner).verify_webhook_signature(...)`. [1](#0-0) [2](#0-1) 
- If the attacker's own org is configured in Shipit (multi-org `github:` section), and they set `repository.owner.login` to their own org, `verify_webhook_signature` succeeds using the attacker's own known secret. [3](#0-2) 
- The handler then resolves the target repository purely from `params.repository.full_name`, a separate JSON field the attacker also fully controls: `Shipit::Repository.from_github_repo_name(params.repository.full_name)`. [4](#0-3) 
- Nowhere is `repository.owner.login` cross-checked against the owner segment of `repository.full_name`; `Repository.from_github_repo_name` simply splits the string on `/` and does a lookup. [5](#0-4) 
- Given the resolved (victim) repository, `LabelCapturingHandler#capture_labels` writes attacker-supplied label names to the victim's `stack.pull_request` as long as the stack is present and not archived: `pull_request.update!(labels: params.pull_request.labels.map(&:name))`. [6](#0-5) [7](#0-6) 

Correction to the question's specific framing: `LabelCapturingHandler` has no `handle` method and never calls `archive!`/`unarchive!` — `process` only calls `capture_labels` then returns `stack`. [8](#0-7)  The `archive?`/`unarchive?` decision + `handle` method that actually toggles archive state based on the provisioning label exists in the sibling `LabeledHandler` (and `UnlabeledHandler`), which shares the exact same cross-org repository-resolution pattern (`Repository.from_github_repo_name(params.repository.full_name)`): [9](#0-8) [10](#0-9) 

Existing guards fail because: `verify_signature` only proves the requester controls a valid `webhook_secret` for *some* configured org (the one named in `repository.owner.login`); it never proves that org owns the repository named in `repository.full_name`. `drop_unhandled_event`, `check_if_ping`, and the `ExplicitParameters` schema only validate presence/types of fields, not cross-field consistency. [11](#0-10) 

### Impact Explanation
An attacker who registers/controls a throwaway GitHub org configured in Shipit's multi-org `github:` secrets (a legitimate, low-privilege setup any Shipit operator's onboarding process allows) can forge a `pull_request` webhook where `repository.owner.login` = their own org (satisfies signature check) but `repository.full_name` = victim's org/repo. This causes:
- `LabelCapturingHandler` to overwrite `pull_request.labels` on a victim's active (non-archived) review-stack pull request — an unauthorized write to a record belonging to a repository the attacker never authenticated as.
- Sibling handlers `LabeledHandler`/`UnlabeledHandler`, using the identical binding-break, to actually call `stack.archive!`/`stack.unarchive!` on the victim's review stack based on the attacker-supplied provisioning label, matching the "payload for one repository mutating another's stack" Critical category.

This is repeatable against any repository/stack whose `full_name` the attacker can guess or knows, as long as the victim's repository uses review stacks (`review_stacks_enabled`). The blast radius spans all tenants sharing the same Shipit instance across configured GitHub orgs.

### Likelihood Explanation
Preconditions: the attacker must control at least one GitHub org configured in the target Shipit instance's `github:` secrets (own repo integration is a normal, low-privilege setup, not a Shipit operator role), the victim repository must have `review_stacks_enabled` and a matching `provisioning_label_name`/behavior configured, and the attacker needs to know or guess the victim's `owner/repo` full name (public information). Cost is a single crafted HTTP POST to `/webhooks` with a valid signature computed from the attacker's own secret. This is fully repeatable and does not require any GitHub or Shipit secret belonging to the victim.

### Recommendation
In `WebhooksController#verify_signature` (or in `Handler#initialize`), enforce that the owner segment of `params.repository.full_name` equals `params.dig('repository', 'owner', 'login')` (or `params.dig('organization', 'login')`) before dispatching to any handler; reject the request (422) on mismatch. Additionally, `Repository.from_github_repo_name` lookups in every `pull_request` handler should be scoped to the verified/signing organization rather than trusting the raw `full_name` string unconditionally.

### Proof of Concept
Minitest plan (`test/controllers/webhooks_controller_test.rb` style, or `test/models/shipit/webhooks/handlers/pull_request/label_capturing_handler_test.rb` style):
1. Configure two orgs in `Shipit.github` config: `attacker-org` (with a known `webhook_secret`) and `victim-org` (repository `victim-org/victim-repo` with an active, non-archived review stack and existing `pull_request` labels `[]`).
2. Build a `pull_request` `labeled` payload where `payload['repository']['owner']['login'] = 'attacker-org'` and `payload['repository']['full_name'] = 'victim-org/victim-repo'`, with `pull_request.labels` set to arbitrary attacker-chosen names (or the victim's `provisioning_label_name` for the `LabeledHandler` variant).
3. Compute `X-Hub-Signature` using `attacker-org`'s known `webhook_secret` over the raw JSON body.
4. `POST /webhooks` with that body/signature/`X-Github-Event: pull_request` header.
5. Assert response is `200 OK` (signature accepted) and assert `victim_stack.reload.pull_request.labels` now equals the attacker-supplied labels (binding broken: `repository.owner.login ('attacker-org') != full_name owner ('victim-org')` yet the write succeeded) — for the archive-toggle variant, assert `victim_stack.reload.archived?` flips per the attacker-supplied provisioning label via `LabeledHandler`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
