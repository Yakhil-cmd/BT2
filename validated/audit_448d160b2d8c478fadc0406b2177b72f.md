### Title
Unbounded recursive submodule checkout enables permanent sync denial via attacker-controlled repo content - (File: main.go)

### Summary
`git-sync`'s worktree configuration step runs `git submodule update --init --recursive` with no cap on the number or depth of submodules, and no minimum-cost/maximum-cost gate before doing so. A repository owner (or anyone who can push to a synced ref, including via a submodule URL under attacker control) can commit an arbitrarily large or deeply-nested submodule tree "for free" (one commit), while `git-sync` must pay the full, unbounded cost of resolving and cloning that tree on every single sync attempt, bounded only by `--sync-timeout` (120s default). This mirrors the referenced bug class: cheap, unrestricted creation of "small" state (many submodules) versus an expensive, bounded remediation step (full recursive checkout) that the honest party (git-sync/the consumer) must repeatedly and unprofitably retry — and can never complete, resulting in permanent denial of sync rather than "bad debt."

### Finding Description
In `configureWorktree`, after resetting the worktree to the target hash, git-sync unconditionally runs a recursive submodule update whenever `--submodules` is not `off`: [1](#0-0) 

This command is executed inside the sync loop under a single `context.WithTimeout(ctx, *flSyncTimeout)` (default 120s): [2](#0-1) [3](#0-2) 

There is no limit on submodule count, nesting depth, or total transfer size enforced anywhere before invoking `submodule update --init --recursive`; the only bound is the overall `--sync-timeout` for the whole sync attempt (fetch + worktree create + submodule recursion). An attacker with write access to the synced repository (or to any nested submodule URL reachable from it) can add many submodules and/or deeply nested submodule chains in a single, cheap commit. On the git-sync side, each sync attempt must walk and clone the entire submodule graph, which is asymmetrically expensive and can be made to exceed `--sync-timeout` on every attempt.

When a sync attempt times out, it's counted as a failure: [4](#0-3) 
and `--max-failures` (default `0`, i.e., abort after the very first failure) causes the process to `os.Exit(1)`: [5](#0-4) [6](#0-5) 

Because the underlying cause (the oversized/deeply nested submodule graph in the target commit) does not change between restarts, this produces a crash-loop / permanent inability to complete a sync — the same "unprofitable to remediate" pattern as the original finding, translated from "unliquidatable positions" to "unsyncable commits."

### Impact Explanation
This qualifies as **persistent sync denial**, one of the accepted impacts: once an attacker lands such a commit/ref on the branch git-sync tracks, every subsequent sync attempt fails the same way, the container repeatedly restarts or hangs, and the consumer sidecar contract (the symlink is never updated to a newer, safe hash) is permanently broken until an operator manually intervenes (e.g., changing `--ref`, increasing `--sync-timeout` drastically, or disabling submodules). Unlike a single slow fetch, this is trivially and cheaply repeatable/amplifiable by the attacker (nested submodules multiply cost combinatorially) while git-sync has no per-submodule accounting or backpressure to detect and bypass the pathological input.

### Likelihood Explanation
Likelihood is moderate and depends on the threat model: it requires push/commit access to the tracked repository or control over a submodule URL that the tracked repository references (both are within the "attacker-pushed commit" reachability the validation scope allows). No special git-sync flags beyond the default `--submodules=recursive` (which is git-sync's default) are required. The complexity of the attack is low — adding recursive submodules is a normal, one-time git operation.

### Recommendation
- Enforce a configurable limit on submodule recursion depth and/or total submodule count before running `submodule update --init --recursive` (e.g., inspect `.gitmodules` and abort/skip with a clear error if limits are exceeded, rather than blocking the whole sync).
- Decouple the submodule update timeout from the overall `--sync-timeout`, and make it independently configurable (similar to `--pre-publish-exechook-timeout`) so a pathological submodule graph fails fast and is logged distinctly rather than being lumped into generic sync failures.
- Consider treating repeated submodule-stage failures differently from fetch/worktree failures for `--max-failures` accounting, and document the risk of `--submodules=recursive` with untrusted upstream content.

### Proof of Concept
1. Attacker with write access to the repo referenced by `--repo` (or to a submodule URL it points to) adds a large number of submodules, or a submodule chain nested many levels deep, in a single commit and pushes it to the ref git-sync tracks.
2. `git-sync`, running with default flags (`--submodules=recursive`, `--sync-timeout=120s`, `--max-failures=0`), fetches the new hash, creates a worktree, and calls `configureWorktree`, which invokes `git submodule update --init --recursive` [7](#0-6) .
3. The recursive submodule resolution/clone exceeds 120s due to the graph size/depth crafted by the attacker; `SyncRepo` returns a context-deadline error, which is counted as a failure [4](#0-3) .
4. With the default `--max-failures=0`, git-sync immediately exits with status 1 [6](#0-5) ; in Kubernetes this causes a crash-loop of the sidecar, and since the offending commit remains at `HEAD`/`--ref`, every restart repeats the same failure indefinitely — a persistent, attacker-triggered denial of sync.
