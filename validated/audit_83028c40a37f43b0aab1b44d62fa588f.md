## Analysis: Missing Authorization Analog Found

The GitLab bug lets an authenticated user manipulate a *namespace identifier* in an API request to reach settings belonging to a namespace they don't control, because the server trusted the supplied identifier without checking that the caller actually owns/controls it. The equivalent pattern in `ocore` is `handleNewSharedAddress()` in `wallet_defined_by_addresses.js`, which accepts a peer-supplied mapping between a shared-address signing path and a `device_address` (the "identifier" that determines who is authorized to receive future private-payment forwards and cosigning requests for that path) without ever verifying that the claimed `device_address` is actually the device that controls the corresponding member address.

### Title
Missing Authorization in Shared-Address Signer Registration Allows Device-Address Hijacking of Cosigner Routing - (File: `wallet_defined_by_addresses.js`)

### Summary
`handleNewSharedAddress()` validates that the shared address's c-hash matches its definition and that each `signers[path].address` matches the address embedded in that definition path, but it never checks that the `device_address` supplied for a given signing path is legitimately paired with / controls that member address. This value is persisted verbatim into `shared_address_signing_paths.device_address`, which is later trusted as the destination for private-payment forwarding and multisig co-signing requests.

### Finding Description
A `new_shared_address` network message is handled with no ownership check on the sender: [1](#0-0) 

`handleNewSharedAddress` only checks that (a) the definition hashes to the claimed address, and (b) each declared signer address matches the address literal embedded at that path of the definition: [2](#0-1) 

Crucially, `signerInfo.device_address` — the field that decides who is authorized to receive cosigning/forwarding traffic for that signing path — is accepted with no verification that this device is actually paired with, or controls, `signerInfo.address`. The pair is stored directly: [3](#0-2) 

Compare this with sibling handlers in the same file that *do* perform such an ownership check before trusting sender-supplied claims, e.g. `arbiter_contract_shared`/`arbiter_contract_update`, which verify the sender's device_address against `my_addresses`/`wallet_signing_paths`: [4](#0-3) [5](#0-4) 

No equivalent check exists for `new_shared_address`/`handleNewSharedAddress`.

Once the bogus `device_address` is stored in `shared_address_signing_paths`, it is used as the authoritative routing target in at least two security-relevant flows:

1. **Private payment forwarding** — `forwardPrivateChainsToOtherMembersOfAddresses` / `readAllControlAddresses` read `device_address` straight from `shared_address_signing_paths` to decide who receives the private payment chain (amounts, blinding factors, spend proofs) for a shared address member: [6](#0-5) [7](#0-6) 

2. **Multisig co-signing routing** — `findAddress()` resolves a shared address's signing path to a `device_address` from `shared_address_signing_paths` and forwards signing requests (`ifRemote`) to whatever device is registered there: [8](#0-7) [9](#0-8) 

### Impact Explanation
A malicious paired correspondent who is (or claims to be) a co-participant in constructing a shared/multisig address can send a crafted `new_shared_address` message in which the signing path belonging to a legitimate cosigner ("Bob") is annotated with the attacker's own `device_address` instead of Bob's. Because the address literal still matches the real definition (the c-hash check passes) and there is no cross-check against actual pairing/ownership of that address, the victim's node persists this mapping. From that point on:
- Private payment chains destined for Bob (including blinding factors and amounts of shared-address outputs) are forwarded to the attacker instead, leaking sensitive private-payment data belonging to a counterparty.
- Signing requests requiring Bob's cosignature are routed to the attacker's device instead of Bob's, so the attacker can either capture the unsigned transaction (information disclosure of pending payments/outputs) or simply never respond, permanently freezing any output that requires Bob's cosignature on that multisig/shared address — an availability/fund-freezing impact.

This mirrors the GitLab flaw's root cause: an authenticated actor supplies an identifier (there: namespace id; here: device_address for a signing path) that the server trusts without verifying it actually belongs to the claimed principal, letting the attacker redirect access/routing that should be restricted to the rightful owner.

### Likelihood Explanation
Any device that is paired with the victim (a normal, low-privilege correspondent relationship established via pairing codes) can send this message directly, or simply be part of the group participating in the shared-address creation handshake, and the fabricated field passes all existing validation (c-hash match, address-per-path match). No special node/hub privileges are required, only an existing paired-device relationship, which is the standard trust level assumed for "wallet and contract message handling" in this ecosystem.

### Recommendation
In `handleNewSharedAddress` (and by extension `addNewSharedAddress`), validate that for every signing path whose `address` is not one of *my own* addresses, the claimed `device_address` is actually a correspondent that has been established/paired for that specific address (e.g., cross-check against `peer_addresses` or an existing prior handshake confirming the peer controls that address), analogous to the ownership checks already performed for `arbiter_contract_shared`/`arbiter_contract_update`. Reject or flag the shared-address registration if the `device_address` cannot be attributed to the address owner.

### Proof of Concept
1. Alice and Bob agree (out of band, via a legitimate definition template) to create a 2-of-2 shared address; Mallory is a device paired with Alice (unrelated correspondent relationship).
2. Mallory sends Alice a `new_shared_address` message whose `definition` is the genuine multisig definition (containing Bob's real address at Bob's path) and whose `signers` map sets `signers[bobPath] = {address: BOB_ADDR, device_address: MALLORY_DEVICE}` while `signers[alicePath] = {address: ALICE_ADDR, device_address: ALICE_DEVICE}`.
3. `handleNewSharedAddress` verifies `objectHash.getChash160(definition) === address` (passes, genuine definition) and `assocDefinitionAddresses[bobPath] === BOB_ADDR` (passes, matches embedded literal) — it never checks that `MALLORY_DEVICE` is paired with/controls `BOB_ADDR`.
4. `addNewSharedAddress` inserts `(shared_address, BOB_ADDR, bobPath, ..., MALLORY_DEVICE)` into `shared_address_signing_paths`.
5. Any subsequent payment to the shared address triggers `forwardPrivateChainsToOtherMembersOfAddresses`, which sends the private payment chain (amounts/blinding) to `MALLORY_DEVICE` instead of Bob; any spend from the shared address triggers `findAddress`'s `ifRemote` path, sending the co-signing request to `MALLORY_DEVICE`, who can withhold cooperation indefinitely, freezing the funds.

function handleNewSharedAddress(body, callbacks){
	if (!ValidationUtils.isArrayOfLength(body.definition, 2))
		return callbacks.ifError("invalid definition");
	if (typeof body.signers !== "object" || Object.keys(body.signers).length === 0)
		return callbacks.ifError("invalid signers");
	try {
		var addr = objectHash.getChash160(body.definition);
	}
	catch (e) {
		return callbacks.ifError("invalid definition: " + e);
	}
	if (body.address !== addr)
		return callbacks.ifError("definition doesn't match its c-hash");
	for (var signing_path in body.signers){
		var signerInfo = body.signers[signing_path];
		if (signerInfo.address && signerInfo.address !== 'secret' && !ValidationUtils.isValidAddress(signerInfo.address))
			return callbacks.ifError("invalid member address: " + JSON.stringify(signerInfo.address));
	}
	const assocDefinitionAddresses = extractAddressPathsFromDefinition(body.definition);
	for (let signing_path in body.signers) {
		const signerInfo = body.signers[signing_path];
		if (assocDefinitionAddresses[signing_path] !== signerInfo.address)
			return callbacks.ifError("signer address at path " + signing_path + " doesn't match definition");
	}
	for (let def_path in assocDefinitionAddresses) {
		if (!body.signers[def_path])
			return callbacks.ifError("no signer for definition address at path " + def_path);
	}
	determineIfIncludesMeAndRewriteDeviceAddress(body.signers, function(err){
		if (err)
			return callbacks.ifError(err);
		validateAddressDefinition(body.definition, function(err){
			if (err)
				return callbacks.ifError(err);
			addNewSharedAddress(body.address, body.definition, body.signers, body.forwarded, callbacks.ifOk);
		});
	});
}

function readAllControlAddresses(conn, arrAddresses, handleLists){
	conn = conn || db;
	conn.query(
		"SELECT DISTINCT address, shared_address_signing_paths.device_address, (correspondent_devices.device_address IS NOT NULL) AS have_correspondent \n\
		FROM shared_address_signing_paths LEFT JOIN correspondent_devices USING(device_address) WHERE shared_address IN(?)", 
		[arrAddresses], 
		function(rows){
			if (rows.length === 0)
				return handleLists([], []);
			var arrControlAddresses = rows.map(function(row){ return row.address; });
			var arrControlDeviceAddresses = rows.filter(function(row){ return row.have_correspondent; }).map(function(row){ return row.device_address; });
			readAllControlAddresses(conn, arrControlAddresses, function(arrControlAddresses2, arrControlDeviceAddresses2){
				handleLists(_.union(arrControlAddresses, arrControlAddresses2), _.union(arrControlDeviceAddresses, arrControlDeviceAddresses2));
			});
		}
	);
}
