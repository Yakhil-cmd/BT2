### Title
Hookify PreToolUse hook fails open (allows the tool call) whenever a data-shape mismatch in a rule/tool_input triggers an exception, silently bypassing configured `block` rules - ([File: plugins/hookify/hooks/pretooluse.py])

### Summary
The reported Mosaic bug is a class of vulnerability where a security/recovery-critical function assumes a fixed data shape from a generic dispatcher, but a specific implementation uses a different shape; the resulting exception aborts the entire protective mechanism, harming the party the mechanism was meant to protect. The closest reachable analog in this repository is the `hookify` plugin's `PreToolUse` hook: it evaluates user-authored rules against tool-call data whose shape is only loosely validated, and any exception raised by a shape mismatch causes the hook to unconditionally *allow* the tool call instead of enforcing the configured `block` decision.

### Finding Description
`hookify`'s `PreToolUse` hook is a user-configured access-control gate: rules defined in `.claude/hookify.*.local.md` can set `action: block` to prevent dangerous `Bash`/`Write`/`Edit`/`MultiEdit` operations [1](#0-0) .

The rule engine's `_extract_field` handles the `MultiEdit` tool by assuming every element of `tool_input['edits']` is a dict and calling `.get()` on it directly, with no type validation: [2](#0-1) 

There is no shape validation for `tool_input` anywhere along the call chain `evaluate_rules → _rule_matches → _check_condition → _extract_field` [3](#0-2) . If `edits` contains a non-dict element (e.g., a string, `None`, or a nested list — which can occur from a malformed/partial tool call, a hook-input mutation by another `PreToolUse` hook's `updatedInput`, or any producer that doesn't perfectly match the expected schema), `e.get(...)` raises `AttributeError`, which propagates all the way out of `evaluate_rules` uncaught.

The top-level hook entry point wraps the entire evaluation in a single broad `except Exception` that, by explicit design, always exits `0` (i.e., "allow") no matter what went wrong: [4](#0-3) 

Because the only way this hook communicates a `deny` decision to the CLI is by successfully returning `{"hookSpecificOutput": {"permissionDecision": "deny", ...}}` from `evaluate_rules` (see `rule_engine.py` lines 72–79), any exception thrown before that return point means the `deny` decision is never produced — the hook always reports success with no blocking output, which Claude Code's hook loader treats as "no opinion / allow." This mirrors the root cause of the reported issue: a structural/shape mismatch between what a generic caller assumes (dict-shaped `edits` entries) and what a specific code path actually receives, causing the protective mechanism itself to fail — except here the failure mode is "fail open" (silently approve) rather than "fail closed" (revert), which is a more severe consequence for a security control.

### Impact Explanation
A user who has configured `hookify` to block dangerous operations (e.g., `rm -rf`, writes to `.env`, edits to CI/CD configs) can have that protection silently bypassed whenever the specific tool call's `tool_input` doesn't match the exact shape `_extract_field` expects. This is a genuine access-control/tool-authorization bypass: the configured deny rule never fires, and the dangerous `Bash`/`Edit`/`MultiEdit` call proceeds as if no rule existed, with the user only seeing a generic `"Hookify error: ..."` system message rather than the intended block. Since the exception can be triggered indirectly by tool-input shapes the agent/model produces (or by another hook's `updatedInput` mutating the input into an unexpected shape), an unprivileged, agent-driven code path can defeat a user-configured security control without any explicit "escape" action.

### Likelihood Explanation
This requires no special privilege — any `MultiEdit` tool call whose `edits` array contains a non-dict element (or any other tool_input path where `_extract_field`/`_check_condition` make unchecked type assumptions) triggers it. Malformed/edge-case tool inputs are plausible in agentic flows (partial JSON, hook-modified `updatedInput`, or a buggy/adversarial MCP-produced arguments), and the `finally: sys.exit(0)` guarantees the failure is always silent and always resolves to "allow," making the bypass reliable once the shape mismatch is hit.

### Recommendation
- In `rule_engine.py`, validate the type of each element before calling `.get()` (e.g., `e.get('new_string', '') if isinstance(e, dict) else ''`), and apply the same defensive typing to every other `_extract_field`/`_check_condition` branch that assumes a specific `tool_input` shape.
- In `pretooluse.py`, do not treat "hook execution failed" as equivalent to "operation approved." At minimum, distinguish infrastructure failures (missing rules, I/O errors) from evaluation failures that occur *after* a rule has already matched a `block` action, and fail closed (`deny`, or at least `ask`) in the latter case, or persist a clear, unmissable warning that a configured protection did not run.
- Add schema validation for the hook input JSON (`tool_input`) at the top of `main()` before dispatching to the rule engine, so malformed shapes are caught and reported explicitly rather than causing an unhandled exception deep in the evaluation logic.

### Proof of Concept
1. Configure a blocking rule, e.g. `.claude/hookify.block-rm.local.md`:
```
---
name: block-rm
enabled: true
event: file
action: block
tool_matcher: MultiEdit
conditions:
  - field: content, operator: contains, pattern: "rm -rf"
---
Blocked dangerous edit.
```
2. Have the agent (or a hook that rewrites `tool_input` via `updatedInput`) issue a `MultiEdit` call whose `edits` field contains a non-dict element, e.g.:
```json
{
  "tool_name": "MultiEdit",
  "tool_input": {
    "file_path": "script.sh",
    "edits": ["not-a-dict-entry", {"old_string": "x", "new_string": "rm -rf /"}]
  }
}
```
3. `_extract_field` (plugins/hookify/core/rule_engine.py:252) executes `e.get('new_string', '')` on the string element `"not-a-dict-entry"`, raising `AttributeError: 'str' object has no attribute 'get'`.
4. This exception propagates out of `evaluate_rules` into `main()`'s `except Exception` block (plugins/hookify/hooks/pretooluse.py:61-70), which prints a generic error message and, via the `finally: sys.exit(0)`, reports success/allow.
5. The `block` rule never fires; the `MultiEdit` call (containing the "rm -rf /" edit that should have been blocked) proceeds unblocked.

    def evaluate_rules(self, rules: List[Rule], input_data: Dict[str, Any]) -> Dict[str, Any]:
        """Evaluate all rules and return combined results.

        Checks all rules and accumulates matches. Blocking rules take priority
        over warning rules. All matching rule messages are combined.

        Args:
            rules: List of Rule objects to evaluate
            input_data: Hook input JSON (tool_name, tool_input, etc.)

        Returns:
            Response dict with systemMessage, hookSpecificOutput, etc.
            Empty dict {} if no rules match.
        """
        hook_event = input_data.get('hook_event_name', '')
        blocking_rules = []
        warning_rules = []

        for rule in rules:
            if self._rule_matches(rule, input_data):
                if rule.action == 'block':
                    blocking_rules.append(rule)
                else:
                    warning_rules.append(rule)

        # If any blocking rules matched, block the operation
        if blocking_rules:
            messages = [f"**[{r.name}]**\n{r.message}" for r in blocking_rules]
            combined_message = "\n\n".join(messages)

            # Use appropriate blocking format based on event type
            if hook_event == 'Stop':
                return {
                    "decision": "block",
                    "reason": combined_message,
                    "systemMessage": combined_message
                }
            elif hook_event in ['PreToolUse', 'PostToolUse']:
                return {
                    "hookSpecificOutput": {
                        "hookEventName": hook_event,
                        "permissionDecision": "deny"
                    },
                    "systemMessage": combined_message
                }
            else:
                # For other events, just show message
                return {
                    "systemMessage": combined_message
                }

        # If only warnings, show them but allow operation
        if warning_rules:
            messages = [f"**[{r.name}]**\n{r.message}" for r in warning_rules]
            return {
                "systemMessage": "\n\n".join(messages)
            }

        # No matches - allow operation
        return {}

    def _rule_matches(self, rule: Rule, input_data: Dict[str, Any]) -> bool:
        """Check if rule matches input data.

        Args:
            rule: Rule to evaluate
            input_data: Hook input data

        Returns:
            True if rule matches, False otherwise
        """
        # Extract tool information
        tool_name = input_data.get('tool_name', '')
        tool_input = input_data.get('tool_input', {})

        # Check tool matcher if specified
        if rule.tool_matcher:
            if not self._matches_tool(rule.tool_matcher, tool_name):
                return False

        # If no conditions, don't match
        # (Rules must have at least one condition to be valid)
        if not rule.conditions:
            return False

        # All conditions must match
        for condition in rule.conditions:
            if not self._check_condition(condition, tool_name, tool_input, input_data):
                return False

        return True

def main():
    """Main entry point for PreToolUse hook."""
    try:
        # Read input from stdin
        input_data = json.load(sys.stdin)

        # Determine event type for filtering
        # For PreToolUse, we use tool_name to determine "bash" vs "file" event
        tool_name = input_data.get('tool_name', '')

        event = None
        if tool_name == 'Bash':
            event = 'bash'
        elif tool_name in ['Edit', 'Write', 'MultiEdit']:
            event = 'file'

        # Load rules
        rules = load_rules(event=event)

        # Evaluate rules
        engine = RuleEngine()
        result = engine.evaluate_rules(rules, input_data)

        # Always output JSON (even if empty)
        print(json.dumps(result), file=sys.stdout)

    except Exception as e:
        # On any error, allow the operation and log
        error_output = {
            "systemMessage": f"Hookify error: {str(e)}"
        }
        print(json.dumps(error_output), file=sys.stdout)

    finally:
        # ALWAYS exit 0 - never block operations due to hook errors
        sys.exit(0)
