### Title
Malicious repo content (e.g. large/deeply-nested submodule trees) causes unbounded, unbacked-off resync work leading to persistent sync denial - (File: main.go)

### Summary
`git-sync`'s sync loop fetches and recursively updates submodules on every attempted update `(main.go` `configureWorktree`, `SyncRepo`), with `--submodules=recursive` as the default and no per-submodule depth limiting unless the repo author opts in via `.gitmodules`. An attacker who can push content to the synced ref (branch/tag) — the untrusted-repo-content analog to a "malicious smart contract" — can add a very large or deeply nested submodule chain. Every sync attempt re-runs the expensive `git submodule update --init --recursive` step until it succeeds, and there is no backoff or work-shedding when a sync repeatedly times out, so the same expensive operation repeats every `--period` indefinitely. [1](#0-0) 

### Finding Description
`configureWorktree` always performs a submodule checkout after the worktree hash changes, and submodule recursion depth is only bounded by the top-level `--depth` flag, which is passed to `git submodule update` but does not prevent a malicious/large submodule tree (many submodules, deep nesting, or huge submodule payload) from making the update slow: [1](#0-0) 

In `SyncRepo`, `configureWorktree` is invoked inside the `changed || git.syncCount == 0` branch, meaning as long as the sync has not yet completed successfully (`changed` stays true because `currentHash` never converges to `remoteHash`), this heavy step is retried in full on every loop iteration: [2](#0-1) 

The outer sync loop applies a fixed `--sync-timeout` per attempt (default 120s per README) and, on failure, simply logs and retries after the fixed `--period` (default 10s) with no exponential backoff, and no cap on submodule/recursive work performed before the timeout fires: [3](#0-2) [4](#0-3) 

Because `--submodules` defaults to `recursive` (not `off` or `shallow`) and depth is optional, a repository maintainer/attacker with commit access to the tracked ref can add a submodule chain (many submodules and/or deep nesting and/or large blobs) that makes each `git submodule update --init --recursive` invocation consume disproportionate CPU/network/time relative to the size of the actual content change — directly analogous to the wasmvm advisory's "malicious contract [triggers] disproportionate compute relative to its cost," which slows down block production. Here it slows down (or with `--sync-timeout` exceeded, indefinitely blocks) the sync loop, denying publication of any subsequent updates to the `--link` target that all consumer containers depend on.

### Impact Explanation
This causes persistent sync denial: once such a commit lands on the tracked ref, every sync attempt (every `--period`) repeats the expensive/slow submodule recursion, either consuming excessive CPU/network resources indefinitely or exceeding `--sync-timeout` and failing repeatedly. Since `--submodules=recursive` is the default and no complexity/size limit exists, downstream consumers relying on the symlink (`--link`) never receive updates once such a commit is fetched, and the sidecar consumes resources on every retry cycle without bound (no backoff, `--max-failures` unlimited by default based on code flow). This matches the "persistent sync denial" impact criterion.

### Likelihood Explanation
Requires only that the attacker be able to introduce a commit that is fetched by the ref/branch git-sync tracks (e.g. a merged PR, a compromised or malicious contributor with write access to a low-privilege branch, or a webhook-triggered ref update) — no privileged access to the git-sync deployment or credentials is needed. This is a moderate-likelihood scenario in CI/CD or GitOps pipelines where git-sync tracks a branch that receives contributions from less-trusted parties, similar in spirit to the "no privileged party required" precondition in the wasmvm advisory (a permissionless/lower-trust contract deployer analog is a lower-trust committer).

### Recommendation
- Bound submodule recursion cost independent of the top-level `--depth`: enforce or default a submodule depth/shallow mode, and/or set a submodule-count/size sanity limit before running `git submodule update --recursive`.
- Track consecutive timeouts/failures per-ref and apply exponential backoff (already tracked via `failCount`, but currently only used for `--max-failures` abort, not backoff of `--period`).
- Consider capping the total work done in `configureWorktree` under `--sync-timeout` more granularly (e.g., timing budget split between checkout and submodule update) so partial completion doesn't repeatedly redo already-expensive steps.
- Document that `--submodules=recursive` (the default) has no depth/size safety limit and recommend `--submodules=shallow` or `--depth` combined with `.gitmodules` shallow settings for untrusted or externally-contributed repos.

### Proof of Concept
1. Set up a repo tracked by `git-sync` with `--submodules=recursive` (default) and no `--depth`.
2. As a low-privileged contributor with merge/push rights to the tracked branch, add a submodule chain: e.g., submodule A referencing submodule B referencing submodule C, each with a large history/blob, nested several levels deep (mirroring the `submodule_sync_default`/`submodule_sync_depth` e2e patterns already in the test suite, but scaled up in size/depth) — see the recursive submodule test harness for the mechanics of adding nested submodules: [5](#0-4) .
3. Commit and push this change to the tracked ref.
4. Observe that `git-sync`'s `SyncRepo` → `configureWorktree` → `git submodule update --init --recursive` step takes disproportionately long relative to the actual file change, and if it exceeds `--sync-timeout`, the sync fails and retries every `--period` indefinitely without backoff, per the loop logic at: [6](#0-5) , ` [4](#0-3) ` — resulting in the `--link` symlink never being updated and continuous resource consumption on every cycle.

Note: I could not fully verify the exact default/behavior of `--max-failures` (whether unlimited by default) from the indexed snippets alone; a background agent with full file access should confirm `flMaxFailures`'s default value in `main.go` to precisely characterize whether the process eventually exits (bounded DoS) or retries forever (unbounded DoS).

function e2e::submodule_sync_default() {
    # Init submodule repo
    local submodule_repo_name="sub"
    local submodule="$WORK/$submodule_repo_name"
    mkdir "$submodule"

    git -C "$submodule" init -q -b "$MAIN_BRANCH"
    echo "submodule" > "$submodule/submodule.file"
    git -C "$submodule" add submodule.file
    git -C "$submodule" commit -aqm "init submodule.file"

    # Init nested submodule repo
    local nested_submodule_repo_name="nested-sub"
    local nested_submodule="$WORK/$nested_submodule_repo_name"
    mkdir "$nested_submodule"

    git -C "$nested_submodule" init -q -b "$MAIN_BRANCH"
    echo "nested-submodule" > "$nested_submodule/nested-submodule.file"
    git -C "$nested_submodule" add nested-submodule.file
    git -C "$nested_submodule" commit -aqm "init nested-submodule.file"

    # Add submodule
    git -C "$REPO" -c protocol.file.allow=always submodule add -q file://$submodule "$submodule_repo_name"
    git -C "$REPO" commit -aqm "add submodule"

    GIT_SYNC \
        --period=100ms \
        --repo="file://$REPO" \
        --root="$ROOT" \
        --link="link" \
        &
    wait_for_sync "${MAXWAIT}"
    assert_link_exists "$ROOT/link"
    assert_file_exists "$ROOT/link/file"
    assert_file_exists "$ROOT/link/$submodule_repo_name/submodule.file"
    assert_file_eq "$ROOT/link/$submodule_repo_name/submodule.file" "submodule"
    assert_metric_eq "${METRIC_GOOD_SYNC_COUNT}" 1

    # Make change in submodule repo
    echo "${FUNCNAME[0]} 2" > "$submodule/submodule.file"
    git -C "$submodule" commit -qam "${FUNCNAME[0]} 2"
    git -C "$REPO" -c protocol.file.allow=always submodule update --recursive --remote > /dev/null 2>&1
    git -C "$REPO" commit -qam "${FUNCNAME[0]} 2"
    wait_for_sync "${MAXWAIT}"
    assert_link_exists "$ROOT/link"
    assert_file_exists "$ROOT/link/file"
    assert_file_exists "$ROOT/link/$submodule_repo_name/submodule.file"
    assert_file_eq "$ROOT/link/$submodule_repo_name/submodule.file" "${FUNCNAME[0]} 2"
    assert_metric_eq "${METRIC_GOOD_SYNC_COUNT}" 2

    # Move backward in submodule repo
    git -C "$submodule" reset -q --hard HEAD^
    git -C "$REPO" -c protocol.file.allow=always submodule update --recursive --remote > /dev/null 2>&1
