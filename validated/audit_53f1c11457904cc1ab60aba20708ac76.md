### Title
Global, repository-unscoped `Commit` lookup in `StatusHandler#process` lets any authenticated GitHub org forge a CI status for another tenant's commit and trigger an unauthorized PR merge - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` looks up commits by `sha` alone, with no scoping to the repository that emitted the webhook, so a `status` event legitimately signed by an attacker's own GitHub organization can create a `Status` row on any other tenant's `Commit` that happens to share the same sha. If that commit is a pending, merge-queue-enabled `MergeRequest#head`, this drives `ProcessMergeRequestsJob` to call `merge_request.merge!`, which merges the victim's PR using the victim's own `stack.github_api` credentials.

### Finding Description
The broken binding is: **the repository/organization that authenticated the webhook (`repository_owner` used in `WebhooksController#verify_signature`) must equal the repository owning the `Commit`/`MergeRequest` that gets mutated** — this equality does not hold.

- `WebhooksController#verify_signature` only proves the payload was signed by *some* configured GitHub org (`Shipit.github(organization: repository_owner)`), using that org's own `webhook_secret`: [1](#0-0) . It never validates that the org matches the repository whose commit is going to be updated — it only guards against forged signatures for the *declared* `repository_owner`, which the attacker legitimately controls since they own that org/repo.
- The base `Handler#stacks` helper correctly scopes lookups by `repository_name` from the payload: `Repository.from_github_repo_name(repository_name)&.stacks`, as seen in `app/models/shipit/webhooks/handlers/handler.rb` lines 32-38. However, `StatusHandler#process` bypasses this scoping entirely and queries commits globally: [2](#0-1) . `Commit.where(sha: params.sha)` matches every `Commit` record across every stack/repository in the installation that shares that sha, regardless of which repository the webhook payload/signature claims to be from.
- `Commit#create_status_from_github!` then calls `statuses.replicate_from_github!(stack_id, github_status)` using **the matched commit's own real `stack_id`** (`app/models/shipit/commit.rb` lines 165-169, `app/models/shipit/status.rb` lines 23-33) — so the forged status is attached to the victim's real stack, appearing indistinguishable from a legitimate CI signal for that stack.
- `Status#schedule_continuous_delivery`/commit state transition (per `test/models/commits_test.rb` lines 763-777) enqueues `ProcessMergeRequestsJob` for the victim's stack once state becomes `pending`/`success`.
- `ProcessMergeRequestsJob#perform` then calls `merge_request.refresh!` and, if `all_status_checks_passed?` (backed by `StatusChecker` over `head.statuses_and_check_runs`), calls `merge_request.merge!`, which invokes `stack.github_api.merge_pull_request` for the **victim's** stack: [3](#0-2)  and [4](#0-3) .

**Exploit flow:**
1. Attacker owns a GitHub org/repo (`evil/repo`) registered with a Shipit installation (or one where their org key is otherwise configured), giving GitHub a legitimate HMAC signature for `evil/repo`'s `status` events.
2. Attacker copies a public commit sha `X` (the head of a pending, merge-queue-enabled victim PR in `victim/prod`) as the head of a PR opened in `evil/repo`.
3. Attacker's own CI (fully attacker-controlled) posts a `success` status for sha `X` to GitHub, which GitHub relays to Shipit's `/webhooks` signed with `evil`'s webhook secret.
4. `verify_signature` passes because the signature is valid for `evil`'s org — it only proves authenticity of `evil`, not relevance to `victim/prod`.
5. `StatusHandler#process` finds **every** `Commit` with `sha == X`, including `victim/prod`'s `MergeRequest#head`, and writes a `success` `Status` there, scoped to `victim/prod`'s `stack_id`.
6. This flips the victim commit's status to `success`, enqueuing `ProcessMergeRequestsJob` for `victim/prod`'s stack, which then calls `merge_request.merge!` using `victim/prod`'s real GitHub credentials.

Existing guards do not stop this: `verify_signature` binds only to the *claimed* organization in the payload, not the target commit's actual stack; `drop_unhandled_event` and the `ExplicitParameters` schema only validate the presence/shape of `sha`/`state`, not repository identity; and `StatusHandler` doesn't reuse the `stacks`/`repository_name` scoping the base `Handler` class provides for exactly this purpose.

### Impact Explanation
This allows an unprivileged GitHub user (owner of any repo enrolled with any configured Shipit GitHub organization) to trigger an **unauthorized merge of a pull request in a completely unrelated victim repository/stack**, using the victim's own GitHub App credentials (`stack.github_api`). This is a cross-tenant integrity break: one repository's webhook payload mutates another repository's `Commit`/`MergeRequest`/`Stack` state and triggers a privileged GitHub API call (`merge_pull_request`) against the victim. This matches the Critical category: "a payload for one repository mutating another's stack, commit, task or team" and "an unauthorized deploy, rollback or merge." It is repeatable against any sha collision the attacker can engineer against any pending, merge-queue-enabled PR sha in any tenant stack served by the same Shipit instance.

### Likelihood Explanation
Preconditions: the target `merge_request` must be `pending` with merge queue enabled and no other blocking status (per `reject_unless_mergeable!`/`all_status_checks_passed?`); the attacker needs an org/repo already recognized by `Shipit.github(organization:)` (any tenant repo onboarded to the same Shipit instance, which is the normal multi-tenant use case for this engine) so that GitHub will sign the status webhook for them. No Shipit session, API token, or secret is required — only ability to open a PR and receive a real GitHub `status` webhook for a sha they choose, which the attacker fully controls by copying a public commit as their fork's PR head. Cost is low and the exploit is deterministic and repeatable per matching sha.

### Recommendation
Scope `StatusHandler#process` (and any other handler that queries by sha alone) to the repository declared in the payload, mirroring the pattern used in `Handler#stacks`, e.g., restrict the `Commit.where(sha: params.sha)` lookup to commits belonging to `stacks` (derived from `repository_name`) rather than a global sha match across all tenants.

### Proof of Concept
minitest plan (no live GitHub, via existing webhook/job test patterns):
1. Fixtures: create two stacks, `victim_stack` (repository `victim/prod`) and `evil_stack` (repository `evil/repo`), both with configured `GitHubApp`/webhook secrets so `verify_signature` succeeds for `evil`'s org.
2. Create `commit = victim_stack.commits.create!(sha: 'sharedsha123...', ...)` and `merge_request = victim_stack.merge_requests.create!(head: commit, state: 'pending', ...)` with merge queue enabled and no blocking statuses.
3. Simulate the attacker's webhook: POST to `/webhooks` with `X-Github-Event: status`, body `{ "sha" => "sharedsha123...", "state" => "success", "repository" => { "full_name" => "evil/repo", "owner" => { "login" => "evil" } } }`, with a signature valid for `evil`'s configured secret (stub `Shipit.github(organization: 'evil').verify_webhook_signature` to return true, matching existing test patterns in `test/controllers/webhooks_controller_test.rb`).
4. Assertion 1 (binding violated): `assert_difference('commit.statuses.count', 1) { post :create, body: ..., as: :json }` — proving a `Status` was written to `victim/prod`'s commit from a payload authenticated only for `evil/repo` (i.e. `repository_owner == 'evil'` while `commit.stack.repository.full_name == 'victim/prod'`, an inequality that should have blocked the write).
5. Assertion 2 (impact): `assert_enqueued_with(job: ProcessMergeRequestsJob, args: [victim_stack])` around step 3.
6. Run the enqueued `ProcessMergeRequestsJob#perform(victim_stack)` with `Shipit.github.api.expects(:merge_pull_request).with(victim_stack.github_repo_name, merge_request.number, anything, has_entries(sha: 'sharedsha123...'))` (mocha), and assert it is called — proving an attacker-controlled, `evil`-signed status caused `victim/prod`'s PR to merge via `victim_stack`'s own GitHub credentials.

    def perform(stack)
      merge_requests = stack.merge_requests.to_be_merged.to_a
      merge_requests.each do |merge_request|
        merge_request.refresh!
        merge_request.reject_unless_mergeable!
        merge_request.cancel! if merge_request.closed?
        merge_request.revalidate! if merge_request.need_revalidation?
      end

      return false unless stack.allows_merges?

      merge_requests.select(&:pending?).each do |merge_request|
        merge_request.refresh!
        next unless merge_request.all_status_checks_passed?

        begin
          merge_request.merge!
        rescue MergeRequest::NotReady
          ProcessMergeRequestsJob.set(wait: 10.seconds).perform_later(stack)
          return false
        end
      end
    end

    def merge!
      raise InvalidTransition unless pending?

      raise NotReady if not_mergeable_yet?

      stack.github_api.merge_pull_request(
        stack.github_repo_name,
        number,
        merge_message,
        sha: head.sha,
        commit_message: 'Merged by Shipit',
        merge_method: stack.merge_method
      )
      begin
        if stack.github_api.pull_requests(stack.github_repo_name, base: branch).empty?
          stack.github_api.delete_branch(stack.github_repo_name, branch)
        end
      rescue Octokit::UnprocessableEntity
        # branch was already deleted somehow
      end
      complete!
      true
    rescue Octokit::MethodNotAllowed # merge conflict
      reject!('merge_conflict')
      false
    rescue Octokit::Conflict # shas didn't match, PR was updated.
      raise NotReady
    end

    def all_status_checks_passed?
      return false unless head

      StatusChecker.new(head, head.statuses_and_check_runs, stack.cached_deploy_spec).success?
    end
