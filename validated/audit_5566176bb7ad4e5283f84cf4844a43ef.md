### Title
Permissionless `claim_revenue` reverts permanently when the pool owner or accumulator cannot receive the asset, freezing accrued protocol revenue - (File: contracts/pool/src/ops/revenue.rs)

### Summary
The Notional report's class is "a supposedly permissionless settlement path pushes tokens to an address that may not be allowed to receive them, so the flow reverts and blocks further actions." XOXNO Lending has the same shape in its revenue sweep: the permissionless `claim_revenue` endpoint pushes pool cash to the pool's Ownable owner (the controller) and then pushes the measured receipt on to the governance-configured accumulator. If either hop targets an address that cannot receive the token (classic-asset trustline deauthorized by the issuer, issuer allowlist gating like the LQV RWA asset, or a receiver contract that rejects), the whole call reverts and protocol revenue can never be swept while that condition holds.

### Finding Description
`claim_revenue` is explicitly permissionless: "Keeper maintenance: sweeps accrued protocol revenue to the governance-configured accumulator. The caller picks the timing, never the recipient" (`scripts/permissionless_entrypoints.txt:75`), and `Controller::claim_revenue` only requires `caller.require_auth` (`contracts/controller/src/lib.rs:374-380`).

The path has two unconditional push legs:

1. `markets::claim_revenue_for_asset` calls `pool_claim_revenue_call`, which invokes `pool.claim_revenue` (`contracts/controller/src/markets.rs:184`, `contracts/controller/src/external/pool.rs:120-126`).
2. In the pool, `ops::revenue::apply` burns claimable revenue shares, then pushes cash to `ownable::get_owner(env)` — the controller — via `cache.transfer_out(&owner, ...)` (`contracts/pool/src/ops/revenue.rs:22-31`). This is the only payout "whose recipient the pool chooses" (`certora/pool/spec/guard_rules.rs:467-469`).
3. Back in the controller, the measured receipt is forwarded with `transfer_amount_measured(..., &accumulator, received, ...)` (`contracts/controller/src/markets.rs:188-196`).

Both hops are synchronous `token.transfer` calls inside the same transaction. Stellar classic assets exposed through the SAC can refuse receipt: under `AUTHORIZATION_REQUIRED`/`AUTH_REVOCABLE` the issuer can deauthorize a balance, and issuer-allowlisted assets (the repo's own LQV RWA fixture reverts un-allowlisted receivers with `ACCOUNT_NOT_ALLOWED`, `tests/test-harness/tests/controller/liqvid_rwa_collateral.rs:502-525`) reject unauthorized destinations outright. If the controller's balance for that asset is deauthorized, leg 2 reverts inside `pool.claim_revenue` after `burn_claimable_revenue`/guards already ran — the revert rolls back the burn, so revenue stays booked but unsweepable. If the accumulator's balance is deauthorized or lacks a trustline, leg 3 reverts with the same result. There is no catch-and-hold, no alternate recipient argument, and no admin bypass path inside the call; unlike liquidation, which offers `SeizeMode::Credit` as a non-custodial fallback (`common/src/types/controller.rs:226-243`), `claim_revenue` has exactly one delivery route.

### Impact Explanation
Accrued protocol revenue becomes un-claimable for as long as the receiving hop cannot accept the token: every `claim_revenue` call for that `(hub_id, asset)` reverts. Revenue shares continue to sit inside `total supplied` (`Cache::accrue_revenue` increases both `revenue` and `supplied`, `contracts/pool/src/cache/shares.rs:36-39`), so the yield is frozen rather than lost, but no caller — keeper or admin via the same endpoint — can recover it without a governance `set_accumulator` change (or issuer re-authorization). This is a temporary freezing of unclaimed yield triggered by an external token-issuer action the protocol cannot prevent — precisely the impact accepted in the original report.

### Likelihood Explanation
The trigger is an external issuer event (clawback/deauthorization on the controller or accumulator balance, or an allowlisted RWA-style asset whose issuer has not admitted the accumulator) rather than an attacker action, so likelihood is low-to-moderate. It is, however, a realistic condition for exactly the asset types the protocol courts (USDC-class clawback-enabled Stellar assets and issuer-gated RWAs are supported, as the LQV tests show), and a single deauthorization on one hop is sufficient — there is no redundancy in the delivery path.

### Recommendation
Make the revenue sweep tolerant of an unreceivable destination, mirroring the report's recommendation to let settlement bypass the failing transfer:

- In `ops::revenue::apply`, wrap the outbound `transfer_out` in `try_transfer` semantics (or gate it behind a receivability precheck) so a failed payout leaves revenue shares unburned but does not revert the accounting — or alternatively keep the funds claimable while returning `actual_amount = 0` and emitting a distinct "claim deferred" event.
- In `markets::claim_revenue_for_asset`, measure the controller receipt as today, but if the forward to `accumulator` fails, retain the tokens at the controller and record a pending accumulator balance that a later `set_accumulator` or retry call can sweep, instead of reverting the whole claim.
- Equivalently, allow `claim_revenue` to accept an explicit fallback receiver authorized by governance, so an issuer-deauthorized accumulator does not wedge the sweep.

### Proof of Concept
1. Governance configures `set_accumulator(A)` where `A` is a classic Stellar account.
2. Users supply and borrow an issuer-controlled asset (e.g., USDC or the allowlisted LQV unit); time advances so `get_revenue` is positive.
3. The asset issuer revokes authorization on `A`'s trustline (or `A` never established one / is not allowlisted).
4. Any keeper calls `controller.claim_revenue(caller, [(hub_id, asset)])`. `pool.claim_revenue` → `transfer_out(owner)` → controller → `transfer_amount_measured(accumulator)`; the final SAC `transfer` panics on the deauthorized/missing trustline (or `ACCOUNT_NOT_ALLOWED` for an allowlisted asset), reverting the entire transaction including `burn_claimable_revenue`.
5. Repeat indefinitely: `get_revenue` stays positive, the sweep always reverts, and the yield cannot be collected until governance replaces the accumulator — matching the blacklisted-account settlement block of the source report.
