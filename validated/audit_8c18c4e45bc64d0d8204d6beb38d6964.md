### Title
Webhook signature verified against organization derived from a payload field that is decoupled from the repository field used to select the write target - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks which GitHub App / webhook secret to validate the HMAC against using `repository_owner`, a value read out of the attacker-suppliable JSON body (`repository.owner.login`, falling back to `organization.login`). The signature only proves "this body was signed with organisation X's secret" - it does not bind that assurance to the separate `repository.full_name` field that `PushHandler` (and other handlers) later use to look up the `Repository`/`Stack` to write into. In a multi-organization Shipit deployment (`Shipit.github_app_config`, one `webhook_secret` per org key under `secrets.github`), anyone who legitimately possesses the webhook secret for their own onboarded organization can forge a body where `repository.owner.login`/`organization.login` names their own org (so verification passes with their own secret) while `repository.full_name` names a different, victim organization's repository, causing Shipit to sync/write commits into that victim stack.

### Finding Description
`verify_signature` in `app/controllers/shipit/webhooks_controller.rb` does:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```
`Shipit.github(organization:)` (in `lib/shipit.rb`) resolves per-organization config via `github_app_config(organization)`, which indexes `secrets.github` by the org key and returns that org's own `webhook_secret`. `GitHubApp#verify_webhook_signature` (in `lib/shipit/github_app.rb`) only confirms the raw body's HMAC matches the secret configured for whatever organization key `repository_owner` names - it says nothing about which repository the event content actually concerns.

Downstream, `Shipit::Webhooks.for_event('push')` dispatches to `PushHandler`, which reads `params.dig('repository','full_name')` (and similar keys) to locate the `Repository`/`Stack` and enqueue `GithubSyncJob`, which then fetches commits and writes them into that stack (`app/jobs/shipit/github_sync_job.rb`). `repository.owner.login` and `repository.full_name` are two independent JSON keys inside the same signed body; nothing enforces `full_name` starts with `owner.login`, and the signature itself provides no such guarantee - it merely proves the whole body was produced/known by whoever holds the secret keyed by whatever `repository_owner` says.

The trust equality that should hold is:
`organization whose secret authenticated the payload == organization owning the repository the payload's content is applied to`

Because both sides of that equality are independently attacker-controlled fields inside the same POST body, an org admin who only holds the webhook secret for their own, legitimately-registered organization (a low-privilege, expected credential in a multi-tenant Shipit install; not a Shipit session, `ApiClient` token, or GitHub App private key) can set `repository.owner.login`/`organization.login` = their own org (to pick their own secret and pass `verify_webhook_signature`), sign the body with that secret, and set `repository.full_name` = `victim-org/victim-repo`, causing cross-organization/cross-repository writes (spurious commits appended to, and sync forced on, a stack the attacker has no authorization over).

### Impact Explanation
This crosses a repository/authentication boundary that the engine is supposed to enforce per-organization: a party authorized only for organization A's webhook channel can inject events that get applied to organization B's `Repository`/`Stack` records (commit history sync, `mark_as_accessible!`/`mark_as_inaccessible!` state, potential deploy triggering off newly-synced commits via continuous delivery). This matches the "Critical: cross-repository writes" impact bucket, since the write target repository is decoupled from the authenticated organization.

### Likelihood Explanation
Requires a specific deployment mode: multiple GitHub organizations configured under `secrets.github` (the `github_app_config` per-org schema), each with its own `webhook_secret`, and the attacker being a legitimate holder of one org's webhook secret. This is a normal operating configuration for shared/multi-tenant Shipit installs (explicitly supported per `lib/shipit.rb`'s `github_default_organization`/`github_app_config`), so the precondition is realistic but not universal (single-org installs using the top-level `webhook_secret` key are unaffected, since there `organization` is effectively ignored/`nil`).

### Recommendation
After `verify_webhook_signature` succeeds, re-derive the organization to act on strictly from a field that is provably the same one the secret was selected from (or reject the payload if `repository.full_name`'s owner segment / `repository.owner.login` disagree with the `organization` used to pick the secret). Concretely, validate `repository.full_name.split('/').first == repository_owner` (or equivalent) before dispatching to handlers, or select the verifying GitHub App using an org identifier that cannot be independently varied from the field handlers use to resolve the target repository.

### Proof of Concept
1. Shipit is configured with two organizations under `secrets.github`: `org-a` (attacker-controlled, attacker knows `webhook_secret_a`) and `org-b` (victim, repository `org-b/victim-repo`).
2. Attacker crafts a `push` webhook JSON body:
```json
{
  "repository": { "owner": { "login": "org-a" }, "full_name": "org-b/victim-repo" },
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>"
}
```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(webhook_secret_a, body)>` and POSTs to `/github/webhooks` with `X-Github-Event: push`.
4. `verify_signature` computes `repository_owner` = `"org-a"`, resolves `Shipit.github(organization: "org-a")`, and `verify_webhook_signature` succeeds since the attacker signed with `org-a`'s real secret.
5. `create` then dispatches to `PushHandler`, which reads `repository.full_name` = `org-b/victim-repo` to find the `Repository`/`Stack`, enqueuing `GithubSyncJob` against the victim's stack - an unauthorized cross-repository action originating from a party who only holds `org-a`'s webhook secret.   def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

    def perform(params)
      @stack = Stack.find(params[:stack_id])
      expected_head_sha = params[:expected_head_sha]
      retry_count = params[:retry_count] || 0
      head_before_sync = spec_cache_target
      appended_commits = []

      handle_github_errors do
        new_commits, shared_parent = fetch_missing_commits { stack.github_commits }

        # Retry on Github eventual consistency: webhook indicated new commits but we found none
        if expected_head_sha && new_commits.empty? && !commit_exists?(expected_head_sha) &&
           retry_count < MAX_RETRY_ATTEMPTS
          GithubSyncJob.set(wait: RETRY_DELAY * retry_count).perform_later(params.merge(retry_count: retry_count + 1))
          return
        end

        stack.transaction do
          shared_parent&.detach_children!
          appended_commits = new_commits.map do |gh_commit|
            append_commit(gh_commit)
          end
          stack.lock_reverted_commits! if appended_commits.any?(&:revert?)
        end
      end
      sync_changed_nothing = appended_commits.empty? &&
                             spec_cache_target == head_before_sync &&
                             stack.cached_deploy_spec.present?
      return if sync_changed_nothing && !params[:force_spec_cache]

      CacheDeploySpecJob.perform_later(stack)
    end
