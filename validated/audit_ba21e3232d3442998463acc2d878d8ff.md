### Title
Webhook signature is bound to the payload's `repository.owner.login` (or `organization.login`) while every event handler acts on the independently-attacker-controlled `repository.full_name`, allowing cross-organization/cross-repository writes - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App (and therefore which `webhook_secret`) to validate a webhook against using a field read straight out of the unauthenticated JSON body — `repository.owner.login` (falling back to `organization.login`). Once the HMAC check passes, the entire raw payload — including a completely independent field, `repository.full_name` — is handed unmodified to every `Shipit::Webhooks::Handlers::Handler` subclass, which uses `repository.full_name` (not `repository.owner.login`) to resolve the target `Repository`/`Stack` to act on. Because the two fields are never cross-checked, a party who legitimately knows the `webhook_secret` for *one* configured GitHub organization in a multi-tenant Shipit deployment can forge a signed payload whose `repository.owner.login` matches their own org (so it verifies) but whose `repository.full_name` points at a different organization's repository, causing Shipit to sync/act on a stack it should never be authorized to touch.

### Finding Description
`Shipit.github_organizations` / `Shipit.github_app_config` (`lib/shipit.rb:190-200`) explicitly support multiple GitHub organizations being configured in the same Shipit instance, each with its own `webhook_secret`. [1](#0-0) 

`WebhooksController#verify_signature` picks the app/secret to check against using `repository_owner`, which is read directly from the untrusted JSON body: [2](#0-1) [3](#0-2) 

`GitHubApp#verify_webhook_signature` only verifies that the whole raw body was HMAC-signed with *that organization's* secret; it does not verify that the body's `repository.full_name` actually belongs to the organization used to select the secret: [4](#0-3) 

Once verified, the full parsed payload is forwarded unmodified to the matching handler(s): [5](#0-4) 

Every handler resolves its target repository/stack from `payload.dig('repository', 'full_name')` — a field that plays no role in signature verification: [6](#0-5) 

`PushHandler`, for example, uses that repository-scoped `stacks` collection to trigger a sync against `expected_head_sha` taken straight from the payload: [7](#0-6) 

Because the HMAC covers the raw body as a whole, an attacker who is *not* an operator of any configured organization cannot forge a valid signature. However, anyone who legitimately controls the GitHub App / webhook settings for **any one** of the organizations configured in this Shipit instance (call it Org B) knows Org B's `webhook_secret`. That is a normal, low-privilege capability for a tenant admin in a multi-org Shipit install — not a Shipit session, `ApiClient` token, or repository write access on the *target* repository. With Org B's own secret, that party can construct an arbitrary JSON body containing:
- `repository.owner.login` / `organization.login` = `"OrgB"` (so `verify_signature` selects Org B's app/secret and the HMAC computed with `webhook_secret_B` validates), and
- `repository.full_name` = `"OrgA/some-other-repo"` (any repository tracked by this Shipit instance, belonging to a completely different organization/tenant).

The controller accepts this as an authentic webhook for Org B, but the handler dispatches it against Org A's stack, because the field used to authenticate ("who signed this") and the field used to authorize the write ("what repository does this act on") are disjoint.

### Impact Explanation
This breaks the binding "the organization that authenticated == the repository that is written," letting a low-privilege tenant (owner of one configured GitHub org's webhook secret) trigger unauthorized cross-organization/cross-repository actions — e.g., forcing `PushHandler` to invoke `stack.sync_github(expected_head_sha:)` (`app/models/shipit/webhooks/handlers/push_handler.rb:16`) on a stack belonging to a repository/org they have no legitimate relationship to, or driving `StatusHandler`/`CheckSuiteHandler`/`membership`/pull-request handlers against another tenant's stacks. This is a cross-repository write across trust boundaries that the multi-org webhook_secret design is meant to enforce.

### Likelihood Explanation
Requires only knowledge of one legitimately-configured organization's `webhook_secret` in a multi-tenant Shipit deployment (a routine credential for that org's own GitHub App admin) plus the ability to POST directly to the public `/webhooks` endpoint with a crafted body and correctly computed `X-Hub-Signature` — no access to the target organization's secret, GitHub App, or repository is needed.

### Recommendation
Bind the field used to select the verifying `webhook_secret` to the same field(s) used by handlers to resolve the target repository, and reject the payload if `repository.full_name`'s owner does not match the organization whose secret validated the signature (e.g., re-derive/require `repository.owner.login == repository.full_name.split('/').first`, and validate this consistency in `verify_signature` before dispatching to handlers).

### Proof of Concept
1. Shipit instance configured with two organizations, `OrgA` and `OrgB`, each with its own `webhook_secret` (per `lib/shipit.rb#github_app_config`).
2. Attacker controls Org B's GitHub App settings and therefore knows `webhook_secret_B`.
3. Attacker crafts JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": { "owner": { "login": "OrgB" }, "full_name": "OrgA/target-repo" }
}
```
4. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(webhook_secret_B, body)>` and sends it with `X-Github-Event: push` to `/webhooks`.
5. `verify_signature` resolves `repository_owner` = `"OrgB"`, loads Org B's `GitHubApp`, and `verify_webhook_signature` succeeds because the attacker used the correct `webhook_secret_B`. [2](#0-1) 
6. `PushHandler` resolves `stacks` via `Repository.from_github_repo_name("OrgA/target-repo")` and calls `stack.sync_github(expected_head_sha: <attacker-chosen-sha>)` on Org A's stack, even though the request was only authenticated as coming from Org B. [6](#0-5) [7](#0-6)

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
