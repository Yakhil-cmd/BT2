### Title
Cross-organization commit status forgery — `StatusHandler` writes CI state without verifying the authenticated organization owns the target repository - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` looks up commits globally by `sha` and applies the incoming CI status without ever confirming that the commit's `Stack`/`Repository` belongs to the GitHub organization whose webhook secret was used to authenticate the request. This breaks the required binding: *organization that authenticated (via HMAC verified against that org's `webhook_secret`) == repository that is written (the `Stack`/`Commit` state actually mutated)*.

### Finding Description
Webhook authentication in `WebhooksController#verify_signature` selects the signing organization purely from the untrusted payload (`repository_owner`, i.e. `params.dig('repository','owner','login')`) and verifies the HMAC against that organization's configured `webhook_secret`: [1](#0-0) [2](#0-1) 

This design is only safe if the *handler* subsequently re-scopes any mutation to the repository/organization that was actually verified. Compare the two handlers for `push`/`check_suite` versus `status`:

- `PushHandler` and `CheckSuiteHandler` scope their side effects through `stacks`, which is derived from `Repository.from_github_repo_name(repository_name)` (the `repository.full_name` field of the *same* payload that was authenticated): [3](#0-2) [4](#0-3) [5](#0-4) 

- `StatusHandler`, however, ignores repository scoping entirely and updates **any** `Commit` row in the whole database whose `sha` matches the payload's `sha`, regardless of which stack/repository/organization that commit belongs to: [6](#0-5) 

`Commit#create_status_from_github!` (via `Status.replicate_from_github!`/`add_status`) persists the new CI state and, when the status transitions to `success`/`pending`, schedules merges and continuous delivery for the commit's stack: [7](#0-6) 

Because Shipit explicitly supports multiple GitHub App installations (multiple organizations) sharing one Shipit instance, each with its own `webhook_secret` (documented feature): [8](#0-7) 

...an event that is genuinely, correctly signed for **Organization B**'s app installation is processed by `StatusHandler` without checking that the `sha` in the payload actually belongs to a commit tracked under Organization B's repositories. If a commit `sha` in Organization A's tracked `Stack` happens to also exist as a commit reachable from a repository in Organization B (e.g. Organization B forked/mirrored a public repo of Organization A, sharing git history/objects and therefore identical SHA-1 commit ids), Organization B can trigger a legitimate GitHub Status API call on their own copy of that commit. GitHub will deliver a webhook correctly signed with **Organization B's** secret, but `StatusHandler` will apply the status to the `Commit` row belonging to **Organization A's** `Stack`.

### Impact Explanation
This is an authentication/authorization binding violation: the entity that GitHub (and thus Shipit's HMAC check) authenticated as the source of the event is not the entity whose state is mutated. The practical effect is that a lower-trust, differently-authenticated organization can inject arbitrary CI status (including `success`) for a commit belonging to another organization's stack. Since `add_status` schedules `ContinuousDeliveryJob`/merge processing on success/pending transitions, this can result in an **unauthorized deploy** being triggered for a stack the attacker's organization does not own — matching the report's "Critical: unauthorized deploy" impact bar.

### Likelihood Explanation
Exploitability depends on the deployment running the documented multi-organization configuration and on the attacker's organization sharing at least one identical commit SHA with the victim's tracked repository (most realistically achievable via forking a public upstream repository, which preserves SHA-1 identity for shared history). This is a real, in-scope configuration supported by the engine, but it requires (a) the multi-org feature being used and (b) a shared/forked commit history, so likelihood is moderate rather than trivial for arbitrary unrelated repositories.

### Recommendation
Scope `StatusHandler#process` the same way `PushHandler`/`CheckSuiteHandler` do: restrict the `Commit` lookup to `stacks` derived from `Repository.from_github_repo_name(payload.dig('repository','full_name'))` (i.e., use the `stacks`/`repository_name` helpers already defined on `Handler`), for example:
```ruby
def process
  stacks.flat_map(&:commits).select { |c| c.sha == params.sha }.each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
or equivalently join through `Commit.joins(:stack).merge(stacks).where(sha: params.sha)`, ensuring the commit's stack's repository matches the repository/organization that was actually authenticated for this webhook delivery.

### Proof of Concept
1. Shipit instance is configured with the documented multi-org `github` section in `secrets.yml`, tracking a `Stack` for `org-a/app` (public repo) and also having a GitHub App installed for `org-b` (attacker-controlled organization), per `docs/setup.md` "Using Multiple GitHub Applications".
2. Attacker (owner of `org-b`) forks the public `org-a/app` repository into `org-b/app-fork`; shared ancestor commits retain identical SHA-1 ids, e.g. `abc123...`, which is also the `sha` of a commit tracked in Shipit's `org-a/app` `Stack`.
3. Attacker calls the GitHub Statuses API on their own fork: `POST /repos/org-b/app-fork/statuses/abc123...` with `state: success`.
4. GitHub delivers a `status` webhook to Shipit, correctly signed with `org-b`'s `webhook_secret`. `WebhooksController#verify_signature` succeeds because it only checks `org-b`'s signature against `org-b`'s secret — this is legitimately valid.
5. `StatusHandler#process` executes `Commit.where(sha: 'abc123...')`, which matches the `Commit` row belonging to `org-a/app`'s `Stack` (not `org-b`'s), and calls `create_status_from_github!`, setting that commit's CI state to `success`.
6. If `org-a`'s stack has continuous delivery enabled, `add_status` schedules `ContinuousDeliveryJob`, resulting in an unauthorized deploy of `org-a`'s stack triggered entirely by `org-b`.

If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently.
