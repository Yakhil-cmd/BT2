### Title
Cross-repository commit-status forgery via unscoped SHA lookup in `StatusHandler` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` resolves the target `Commit` purely by SHA, with no check that the SHA belongs to the repository named in the webhook payload that was actually authenticated. This breaks the binding: *organization authenticated == repository written*. Any GitHub organization onboarded to a multi-tenant Shipit instance can forge a webhook whose signature is valid for its own org, but whose effect (writing a commit status) lands on a `Commit` belonging to a completely different stack/repository, as long as the two repositories happen to share a commit SHA.

### Finding Description
`WebhooksController#verify_signature` selects the app/secret to validate against using the organization derived from the payload, then verifies the HMAC over the raw body: [1](#0-0) 

Once the signature check passes, `WebhooksController#create` dispatches the *entire unfiltered payload* to the matching handler: [2](#0-1) 

The base `Handler` class exposes a `stacks` helper that correctly scopes lookups to the repository named in the payload: [3](#0-2) 

`PushHandler` and `CheckSuiteHandler` both use this `stacks` scoping before touching any records: [4](#0-3) [5](#0-4) 

`StatusHandler`, however, ignores `payload['repository']` entirely and looks up commits globally by SHA across every stack in the database: [6](#0-5) 

Because a webhook's org (and therefore which secret authenticates it) is derived only from `repository.owner.login`/`organization.login` in the same untrusted payload that is later used (or, for `StatusHandler`, *not* used) to scope the write, the equality that should hold — "the organization whose secret validated this payload" == "the repository that gets a commit status written" — is never enforced for `status` events. Since git commit SHAs are content-addressed, any actor who can produce (e.g., via a mirror/fork containing byte-identical commit content) or otherwise control a commit with the same SHA as one tracked by an unrelated stack, and who has enough access to trigger a `status` webhook from *any* org configured in Shipit's multi-tenant `github:` secrets (see `docs/setup.md` "Using Multiple Github Applications"), can inject a forged CI status onto that unrelated stack's commit.

### Impact Explanation
A forged commit status can satisfy `ci.require` gating in `shipit.yml`, letting an attacker who controls or has push access to a different, unrelated repository monitored by the same Shipit instance mark a commit in a target stack as CI-passing without ever having write access to the target repository. This can lead to an unauthorized deploy being unblocked — matching the "unauthorized deploy" high-impact category, since Shipit's core safety mechanism (CI check requirements) is bypassed by a cross-repository status write that the target repository's own maintainers never triggered.

### Likelihood Explanation
Exploitation requires: (1) the attacker to have write/CI-trigger access to *some* repository whose organization is configured in the same Shipit instance's multi-org `github:` secrets (a realistic setup per `docs/setup.md`), and (2) a commit SHA collision between the attacker-controlled repo and the target stack's repo — achievable deliberately by mirroring/forking the exact target commit content into an attacker-controlled repository and then posting a status against it via the normal GitHub API. This is more constrained than a trivial exploit, but does not require any Shipit session, API token, or the target repository's own webhook secret — only an unrelated, lower-privileged GitHub identity already trusted by the same Shipit deployment.

### Recommendation
Scope `StatusHandler#process` to the repository asserted in the webhook payload, mirroring `PushHandler`/`CheckSuiteHandler`:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
end
```
This ensures the organization that authenticated the webhook can only write commit statuses for commits belonging to stacks tied to the repository named in that same authenticated payload.

### Proof of Concept
1. Configure Shipit with two organizations, `TargetOrg` (hosts the protected stack) and `AttackerOrg` (attacker has push access), per the multi-org setup in `docs/setup.md`.
2. Attacker mirrors/forks the exact commit (identical tree/parents/message → identical SHA) from `TargetOrg/target-repo` into `AttackerOrg/evil-repo`.
3. Attacker uses the GitHub API (which they legitimately control for their own repo) to create a `success` commit status on that SHA in `AttackerOrg/evil-repo`.
4. GitHub sends a `status` webhook to Shipit, signed with `AttackerOrg`'s legitimate `webhook_secret`; `WebhooksController#verify_signature` passes. [1](#0-0) 
5. `StatusHandler#process` matches `Commit.where(sha: params.sha)` and finds the commit belonging to `TargetOrg/target-repo`'s stack, writing the forged `success` status onto it. [6](#0-5) 
6. If `TargetOrg/target-repo`'s `shipit.yml` requires that CI context, the target stack now shows as deployable/passing based on a status the attacker forged from an unrelated repository.
