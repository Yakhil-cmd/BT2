### Title
Webhook signature verification selects the trust boundary (GitHub org / secret) from an attacker-controlled payload field, letting a forged event for one (secret-less) organization write to a stack owned by a different organization - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks *which* `GithubApp` (and therefore which webhook secret) to validate the incoming signature against by reading `repository.owner.login` / `organization.login` straight out of the *unauthenticated* JSON body. The very same untrusted body is then handed unchanged to `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`, whose handlers act on a *different* field of that body - `repository.full_name` - to decide which `Stack`/repository to mutate. The equality the code implicitly assumes, `organization authenticated == repository written`, does not hold: the organization used to pick/verify the secret and the repository that ends up being written to are independently attacker-controlled fields of one forged request.

### Finding Description
`verify_signature` does:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
  head(422) unless verified
  ...
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) 

`repository_owner` is read from the raw, unauthenticated request body before any signature check occurs, so an attacker fully controls which `GithubApp` config is used for verification. `GithubApp#verify_webhook_signature` only compares the HMAC signature to the secret configured *for that organization*, and critically:
```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
``` [2](#0-1) 

If *any* organization configured on the instance has no `webhook_secret` set, verification is unconditionally bypassed for a payload claiming to be from that organization. This is not a theoretical edge case: the documented/default configuration explicitly ships with `webhook_secret: # nil`, both in the setup guide and in the development example secrets: [3](#0-2) 
and the multi-org test fixture demonstrates the same pattern for a second, real organization (`OrgTwo`) sitting alongside a properly-secured one (`OrgOne`): [4](#0-3) 

Once `verify_signature` passes (because it resolved and checked against the secret-less/attacker-known organization's `GithubApp`), the controller dispatches the *entire unmodified payload* to the registered handlers:
```ruby
def create
  params = JSON.parse(request.raw_post)
  Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }
  head(:ok)
end
``` [5](#0-4) 

Handlers such as the push handler resolve the target `Stack` from `params['repository']['full_name']` (not from `repository_owner`) and enqueue jobs against it, e.g. `GithubSyncJob` with the stack id and the attacker-supplied head SHA: [6](#0-5) 

Because `repository_owner` (used to select/validate the signing secret) and `repository.full_name` (used to select the stack that is actually mutated) are two independent fields of the same attacker-supplied JSON body, an attacker can:
1. Set `repository.owner.login` (or `organization.login`) to an organization configured on the instance with `webhook_secret` blank/nil - this makes `verify_signature` pass unconditionally, with no signature required at all.
2. Set `repository.full_name` (and other repo fields used by handlers) to point at a *different*, unrelated, and properly secured stack/organization tracked by the same Shipit instance.

The request is processed as a legitimate event for that second, unrelated repository - triggering `GithubSyncJob` for an attacker-chosen commit SHA, or manipulating PR-related state (labels, merge/close events, review-stack adapters) for that victim stack - despite never having produced a valid signature for that victim organization/repository.

### Impact Explanation
This breaks the binding between "the organization whose credentials authenticated the webhook" and "the repository that is actually written to" by Shipit. On any Shipit instance hosting more than one GitHub organization/app where at least one has no webhook secret configured (a state explicitly presented as valid/default in the docs and fixtures), an unauthenticated remote attacker can forge push/pull_request/status/etc. events for a completely different, secured stack. Depending on the target stack's configuration (e.g. `continuous_deployment: true`), this can result in unauthorized syncs, merges, or deploy-triggering state changes on a repository the attacker never had legitimate access to - satisfying the Critical impact bar of "an unauthorized deploy, rollback or merge" / "cross-repository writes".

### Likelihood Explanation
Likelihood is high wherever an operator follows the documented default (`webhook_secret: # nil`) for even one organization while other organizations on the same instance are properly secured - a very plausible real-world misconfiguration given it is the example/default value shown in `config/secrets.development.example.yml` and mirrored in the multi-org test fixture. No credentials, session, or API token are required; only knowledge that an organization with a blank secret is configured (which can often be inferred/guessed, e.g. a test/staging org) and knowledge of the victim stack's `owner/repo` full name, which is generally public.

### Recommendation
Do not let an untrusted, unauthenticated field of the payload determine both (a) which secret is used for verification and (b) which resource is mutated. Concretely:
- Reject webhooks for any organization that has no `webhook_secret` configured instead of returning `true` unconditionally in `GithubApp#verify_webhook_signature`.
- After signature verification succeeds for `repository_owner`, re-validate that the repository/stack the handlers are about to act on (`repository.full_name`) actually belongs to that same verified organization before dispatching to handlers.
- Consider requiring `webhook_secret` to be present for every configured organization at boot/initialization time and failing fast otherwise.

### Proof of Concept
1. Configure Shipit with two organizations, e.g. as in `test/dummy/config/secrets_double_github_app.yml`: `OrgOne` with a real `webhook_secret`, and `OrgTwo` with `webhook_secret: nil` (matches the documented default in `config/secrets.development.example.yml`). `OrgOne` owns the real target stack `OrgOne/victim-repo`, tracked and continuously deployed by Shipit.
2. As an attacker with no credentials, POST to `/github/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "repository": { "owner": { "login": "OrgTwo" }, "full_name": "OrgOne/victim-repo" },
  "after": "<attacker-chosen-sha>",
  "ref": "refs/heads/master"
}
```
No `X-Hub-Signature` header is required (or any arbitrary value), because `repository_owner` resolves to `OrgTwo`, whose `GithubApp#verify_webhook_signature` returns `true` unconditionally (`webhook_secret` is nil).
3. `WebhooksController#create` proceeds to call the push handler with this payload; the handler resolves the target stack from `repository.full_name` = `OrgOne/victim-repo` and enqueues `GithubSyncJob` for that stack with the attacker-chosen SHA, exactly as demonstrated by the legitimate-flow test at `test/controllers/webhooks_controller_test.rb:23-32`, but here reached via a forged, unsigned request that was only "verified" against an unrelated organization's (missing) secret.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
