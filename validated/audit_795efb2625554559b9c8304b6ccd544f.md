### Title
Sustained high-utilization accrual overflows the RAY asset value and permanently freezes the market - (File: contracts/pool/src/cache/scale.rs)

### Summary
The CVE-2017-5980 class is "crafted input drives the program into an unconditional crash." The XOXNO Lending analog is an unconditional `MathOverflow` panic inside interest accrual: once the RAY-scaled borrowed value `scaled_debt * borrow_index` exceeds `i128::MAX`, `scaled_to_original` panics on every subsequent call. Because every market verb accrues first, the market is permanently bricked — no repay, withdraw, liquidate, or `clean_bad_debt` can ever execute again, and all supplied funds are frozen forever. The repository's own test demonstrates this cliff is reachable before the borrow-index cap engages.

### Finding Description
`Cache::calculate_utilization` (and every other accrual consumer) calls `scaled_to_original(&self.env, self.borrowed, self.borrow_index)` at `contracts/pool/src/cache/scale.rs:23`, which computes `scaled * index / RAY` via `mul_div_half_up` in `common/src/math/fp_core.rs:108-118`. `mul_div_half_up` raises `GenericError::MathOverflow` when the result does not fit `i128` (`fp_core.rs:116-117`, `to_i128` at `fp_core.rs:300-303`).

`global_sync` in `contracts/pool/src/interest.rs:20-33` runs this accrual (via `accrue_chunk` → `accrue_step`, `interest.rs:39-53`) before every state-changing pool op, so utilization/index recomputation is on the critical path of `supply`, `withdraw`, `borrow`, `repay`, `liquidate`, `clean_bad_debt`, `flash_loan`, and `update_indexes`.

The harness test `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` (`tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:321-361`) proves the exploit end-to-end:

- A supplier deposits ~10²⁷ units of an 18-decimal token (`BILLION * 10^18`, line 329).
- A borrower takes ~98% utilization against collateral (line 333).
- On the steep segment of the XLM-style rate curve, iterated `update_indexes` calls eventually panic inside `scaled_to_original` with `MATH_OVERFLOW` while `borrow_index < MAX_BORROW_INDEX_RAY` — i.e., the value ceiling is hit *before* the index cap can clamp growth (lines 343-353).
- After the cliff, `withdraw` and `repay` both revert with `MATH_OVERFLOW` because they accrue first (lines 355-356). The panic is unrecoverable: accrual is recomputed from stored state on every call, so the overflow condition never clears.

This maps cleanly onto the CVE class: the crash is not a one-off transaction revert (fail-closed DoS) but a permanent state where the contract can never complete its own accounting again.

### Impact Explanation
Permanent freezing of funds. Every supplier's deposits and every borrower's collateral in that market become unrecoverable: withdraw, repay, liquidate, `clean_bad_debt`, and `recapitalize` all route through accrual and panic. Protocol revenue shares embedded in `supplied` are likewise frozen. This satisfies the "permanent freezing of funds" / "contract unable to operate" impact criteria.

### Likelihood Explanation
Reachable by a single unprivileged address pair using only `supply` and `borrow`: supply a very large principal in a high-decimal market, borrow to high utilization, then let time (or repeated permissionless `update_indexes` calls) advance accrual until the RAY product overflows. It requires whale-scale capital or a market with large existing supply and a steep high-utilization rate segment, and enough elapsed accrual for the index to multiply the value past `i128::MAX` (~1.7×10³⁸ raw, i.e. ~170× index growth on a 10²⁷ base). Any third party can also trigger the freeze permissionlessly via `update_indexes` once the threshold is crossed. Medium severity: high impact, gated by capital scale and time.

### Recommendation
Cap growth before the RAY value overflows rather than only capping the index:

- In `accrue_step`/index update, clamp the *borrowed/supplied scaled shares or the index increment* so that `scaled * index` cannot exceed `i128::MAX`; enforce the existing `MAX_BORROW_INDEX_RAY` ceiling by checking the resulting scaled value, not just the index.
- Alternatively, saturate `scaled_to_original`-style unscaling used inside accrual (a `mul_div_*_saturating` variant exists in `fp_core.rs:180-201`) and book the excess as bad debt, so accrual degrades gracefully instead of panicking.
- Add a regression test asserting the index/value cap engages before `scaled_to_original` can overflow, covering the `interest.rs`/`scale.rs` path.

### Proof of Concept
The repo's own test is the PoC (`tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:321-361`):

```rust
let mut t = LendingTest::new()
    .with_market(big("BIG18", 18, xlm_curve()))
    .with_market(col())
    .with_max_utilization_disabled_all_markets()
    .build();
lift_caps(&t, "BIG18", 18);
lift_caps(&t, "COL", 7);
let principal = BILLION * 10i128.pow(18);
t.supply_raw(BOB, "BIG18", principal);          // attacker seeds huge supply
let debt = principal / 100 * 98;
t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
t.borrow_raw(ALICE, "BIG18", debt);             // ~98% utilization

loop {
    t.advance_time(YEAR_SECS);
    if let Err(e) = t.try_update_indexes_for(&["BIG18"]) { break e; }
}
// update_indexes now fails with MathOverflow while borrow_index < cap;
// withdraw and repay both revert permanently:
assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
```

Crash chain: `update_indexes` → `global_sync` (`interest.rs:20`) → `accrue_step`/utilization → `scaled_to_original` (`scale.rs:23`) → `mul_div_half_up` → `MathOverflow` (`fp_core.rs:117`). Since accrual re-runs from persisted state on every invocation, the panic is deterministic and permanent for all market verbs.
