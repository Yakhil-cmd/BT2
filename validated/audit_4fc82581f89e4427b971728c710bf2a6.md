### Title
Cross-organization webhook forgery via mismatched signature-key/target-repository binding — ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App / webhook secret to validate the HMAC signature against using `repository.owner.login` (falling back to `organization.login`), while the actual handlers that mutate state (e.g. `PushHandler`, and any handler inheriting `Handler#stacks`) resolve the `Repository`/`Stack` to act on using a *different* field from the same JSON body: `repository.full_name`. Nothing in the codebase enforces that these two fields agree.

### Finding Description
`verify_signature` computes the signing organization like this: [1](#0-0) 

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) 

The HMAC secret used for verification is looked up solely by `repository.owner.login`. Once verification passes, the raw params are dispatched unchanged to every registered handler: [2](#0-1) 

Handlers, however, do not consult `repository.owner.login` at all. `Handler#stacks`/`#repository_name` resolves the target `Repository` using `repository.full_name`: [3](#0-2) 

and `PushHandler#process` acts on whatever stacks are returned for that repository, syncing them to an attacker-supplied `after` SHA: [4](#0-3) 

This is a classic "verify field A, act on field B" bug: the signature only proves *someone possessing the webhook secret registered for the organization named in `repository.owner.login`* sent the payload — it says nothing about which repository (`repository.full_name`) is actually operated on. Shipit explicitly supports **multiple GitHub App configurations keyed by organization** in `config/secrets.yml` (confirmed by the `github: { OrgOne: {...}, OrgTwo: {...} }` structure) and raises `Shipit::GithubOrganizationUnknown` when an org has no config, showing multi-tenant hosting of several organizations from one Shipit instance is a first-class, documented use case: [5](#0-4) [6](#0-5) 

Given a multi-org deployment, an actor who is a legitimate GitHub App/webhook administrator for **Organization A** (and therefore knows/can produce a valid signature keyed to Org A's `webhook_secret`) can craft a webhook payload where `repository.owner.login = "OrgA"` (so it validates against Org A's secret) but `repository.full_name = "OrgB/target-repo"` (a repository actually belonging to a *different* tenant, Org B, on the same Shipit instance). The signature check passes because it only checks the raw body against Org A's secret; the handler then locates and mutates Org B's `Stack` because it trusts `repository.full_name` unconditionally.

### Impact Explanation
This breaks the trust boundary "the organization that authenticated the webhook == the repository whose state is written," which is one of the deployment-trust bindings this analysis targets. Concretely, with a forged `push` event an attacker (privileged only within their own tenant, Org A) can:
- Force `Stack#sync_github` to run against Org B's stack with an attacker-chosen `expected_head_sha`, corrupting/advancing commit state that later deploy/rollback logic in Org B relies on — a cross-repository/cross-tenant write.
- Similarly abuse `status`, `check_suite`, or `pull_request` handlers (all of which also resolve their target repository via `payload.dig('repository', 'full_name')` through the shared `Handler` base class) to inject fabricated CI/check statuses onto Org B's commits, potentially causing an unauthorized deploy to be triggered on Org B if deploy gating relies on commit `deployable?`/status checks.

This qualifies as a cross-repository write / potential unauthorized deploy trigger against a tenant the attacker has no legitimate access to, satisfying the Critical impact bar for cross-tenant writes.

### Likelihood Explanation
Exploitation requires the attacker to already control (or be an authorized admin of) a GitHub App installation/webhook secret for at least one organization hosted on the same multi-tenant Shipit instance — a realistic scenario for shared/hosted Shipit deployments serving several organizations, since the engine explicitly supports per-organization GitHub App configuration. No access to Org B's secrets, `ApiClient` tokens, or `GITHUB_TOKEN` is required. This is not a purely theoretical scenario given the shipped multi-org config format, but it is contingent on a specific deployment topology (multiple orgs configured on one instance), so likelihood is Medium rather than trivially universal.

### Recommendation
In `WebhooksController#verify_signature` / the shared `Handler` base class, require that `repository.owner.login` (the field used to select the signing key) matches the organization implied by `repository.full_name` (the field used to select the write target) before dispatching to handlers — reject the webhook (422) on mismatch. Alternatively, resolve the target `Repository`/`Stack` using the same organization value that was cryptographically verified, rather than trusting an independent, unauthenticated-relative-to-that-binding field from the payload body.

### Proof of Concept
1. Shipit instance hosts two orgs, `OrgA` and `OrgB`, each with its own `webhook_secret` in `config/secrets.yml` (as in `test/dummy/config/secrets_double_github_app.yml`).
2. Attacker is a legitimate admin of the GitHub App installed on `OrgA` and thus knows/derives `OrgA`'s `webhook_secret`.
3. Attacker crafts a `push` event JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "OrgA" },
    "full_name": "OrgB/target-repo"
  }
}
```
4. Attacker computes `X-Hub-Signature: sha1=<hmac(OrgA_webhook_secret, body)>` and POSTs to `/webhooks` with `X-Github-Event: push`.
5. `verify_signature` resolves `repository_owner` → `"OrgA"`, fetches `OrgA`'s `GithubApp`, and the HMAC validates successfully.
6. `PushHandler#process` resolves the target repository via `repository.full_name` → `OrgB/target-repo`, finds `OrgB`'s `Stack`, and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` — mutating a stack the attacker has no authorization over.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping
      head(:ok) if event == 'ping'
    end

    def event
      request.headers.fetch('X-Github-Event')
    end

    def repository_owner
      # Fallback to the organization sub-object if repository isn't included in the payload
      params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
    end
