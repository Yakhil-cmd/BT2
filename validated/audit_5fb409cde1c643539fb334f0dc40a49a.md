### Title
Unverified `X-Shipit-User` header lets any holder of a scoped API token spoof deploy/task/lock/merge authorship - (File: app/controllers/shipit/api/base_controller.rb)

### Summary
`Api::BaseController#identify_user` derives `current_user` purely from the client-supplied `X-Shipit-User` request header, looking the user up by login with no cryptographic binding to the authenticated `ApiClient`. This mirrors the FRAX report's root cause: a value that influences a privileged calculation/attribution (there, spot price feeding `minVeFXSForMaxBoost`; here, the acting-user identity feeding stack actions) is read from attacker-controlled input that is never verified against the credential that was actually authenticated.

### Finding Description
`authenticate_api_client` verifies only the bearer token (`ApiClient.authenticate`) via `BasicAuth`/`SimpleMessageVerifier`, establishing `@current_api_client`. Separately, `current_user` is computed independently: [1](#0-0) 

`identify_user` trusts `request.headers['X-Shipit-User']` and does a case-insensitive login lookup, with no check that this login corresponds to the creator of the presented `ApiClient`, nor any signature/ownership proof: [2](#0-1) 

This `current_user` is then passed as the acting principal into privileged operations: triggering deploys, custom tasks, locking/unlocking stacks, and merge requests: [3](#0-2) [4](#0-3) [5](#0-4) 

The binding that is broken is: **the GitHub/Shipit identity claimed in the request payload (`X-Shipit-User`) ≠ the `User` actually bound to the authenticated session/token**. The `ApiClient` token authenticates *that a caller is permitted to perform `operation:scope`*, but nowhere does the engine verify that the caller is entitled to act *as* the specific `User` named in the header. Any party holding a valid `ApiClient` token with `deploy:stack`/`lock:stack`/`write:hook` etc. permission for a given stack can set `X-Shipit-User` to any existing login (e.g., an admin or a `Shipit.github_teams` member) and have all resulting audit trail, `deploy.user`, `task.user`, `lock_author`, and `merge_requested_by` attributed to that spoofed identity.

### Impact Explanation
This does not, by itself, exfiltrate a `github_access_token` or grant new permissions beyond what the `ApiClient` token already carries — deploy/task execution still runs with `Shipit.github.api` credentials, not the impersonated user's token (`TaskCommands#env` only uses `@task.user&.name`/`&.email` for git-committer metadata, and `github_api` fallbacks to `Shipit.github.api` unless the impersonated user happens to have a `github_access_token` set, in which case attribution-dependent GitHub API calls, e.g. `CommitDeployment#create_deployment_on_github`, could run under that specific user's token: `stack.github_api`/`task.author`). This creates an identity/audit-trail-forgery condition and a limited path where an already-token-holding caller can cause GitHub-side actions (deployments, deployment statuses) to be attributed to and executed under an arbitrary other Shipit user's linked GitHub identity/token, without any additional privilege check tying the header value to the authenticated client.

### Likelihood Explanation
Exploitation requires only possession of any valid `ApiClient` token scoped to the target stack with the relevant `operation:scope` permission (e.g. `deploy:stack`) — no GitHub write access, no webhook secret, and no session are needed. Given that `ApiClient` tokens are commonly distributed to CI systems and are less tightly controlled than admin GitHub team membership, this is a plausible escalation path from "low-privilege automation token" to "impersonate any registered Shipit user for attribution and, when that user has a linked `github_access_token`, for GitHub-side API actions."

### Recommendation
Do not derive `current_user` from an unauthenticated header. Bind the acting user to the `ApiClient` itself (e.g., `ApiClient#creator`) or require the `X-Shipit-User` claim to be cryptographically tied to the token (e.g., signed alongside the token, or restricted to `ApiClient`s explicitly delegated to a given user), and reject the header when the `ApiClient` has no such delegation.

### Proof of Concept
1. Obtain (or be issued) a legitimate `ApiClient` token scoped to `stack-A` with permission `deploy:stack` (e.g. a CI integration token).
2. `POST /api/stacks/:stack_id/deploys` with `Authorization: Basic <token>` and header `X-Shipit-User: admin-login` (any existing privileged Shipit user's login), per [3](#0-2)  and `identify_user` at [2](#0-1) .
3. The resulting `Deploy` is created with `user_id` = the admin's id; if that admin user has a `github_access_token`, subsequent GitHub-facing actions tied to the deploy (deployment/status creation) may execute under the admin's GitHub identity, and all UI/audit attribution shows the admin as having triggered the deploy — despite the admin never authenticating this request.
