### Title
Cross-repository status webhook confusion via unscoped sha lookup allows attacker to fake CI success and unlock a victim's merge - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits solely by `sha` across the entire database, with no scoping to the repository named in the webhook payload, even though the base `Handler` class already provides a `stacks` helper scoped by `repository_name` that this handler never uses. Because a valid webhook signature only proves the request originated from *some* repository the attacker controls (verified against that repository's own `webhook_secret`), an attacker who can produce a commit with a colliding `sha` in their own repo can post a `success` status that gets attached, via `Status.replicate_from_github!(commit.stack_id, ...)`, to a completely unrelated victim stack's commit, letting `MergeRequest#all_status_checks_passed?` return true and `merge!` proceed.

### Finding Description
The broken binding, stated explicitly: the webhook's authenticated origin, `repository_owner`/`repository.full_name` as verified by `GitHubApp#verify_webhook_signature` against **that repository's own `webhook_secret`**, must equal `Shipit::Commit#stack.repository.full_name` for every `Shipit::Commit` row that the handler mutates in response to that webhook. It does not:

- `WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-49`) computes `repository_owner` from `params.dig('repository', 'owner', 'login')` and verifies the HMAC signature using `Shipit.github(organization: repository_owner)`'s app secret. This proves the payload was signed by *the attacker's own repository's* webhook secret — nothing more. It never checks that `repository.full_name` matches any particular Shipit stack. [1](#0-0) 

- `StatusHandler#process` then ignores the payload's repository entirely and matches by `sha` alone across **all** stacks in the installation: [2](#0-1) 
Contrast this with the sibling `Handler` base class, which does provide repository-scoped access via `stacks` (`Repository.from_github_repo_name(repository_name)&.stacks`), but `StatusHandler` never calls it. [3](#0-2) 

- For every matched `Commit` (regardless of which stack/repository it belongs to), `create_status_from_github!` writes a `Status` keyed on that commit's **own** `stack_id`, not on the webhook's originating repository: [4](#0-3) [5](#0-4) 

- `MergeRequest#all_status_checks_passed?`/`any_status_checks_failed?`/`any_status_checks_missing?` then consume whatever `Status` rows exist on `head` (the victim's commit), with no check that those statuses were ever reported by the victim's own repository: [6](#0-5) 

**Exploit flow:** Attacker forks/owns repo `attacker/evil`. Attacker crafts a commit with sha identical to the victim's open PR head (feasible since sha is a hash of tree, parent, author/committer identity and timestamps, all attacker-controllable when constructing an equivalent commit — e.g. an empty/no-op commit with matching tree and parent hash and forged timestamps) and pushes/references it in their own repo. Attacker sends `POST /webhooks` with `X-Github-Event: status`, `repository.full_name = attacker/evil`, `repository.owner.login = attacker`, `sha = <victim's head sha>`, `state: success`, signed with `attacker`'s own legitimate webhook secret (their own GitHub App/org's secret, which they possess). `verify_signature` passes because the signature is valid for `attacker`'s org. `StatusHandler#process` runs `Commit.where(sha: params.sha)`, which matches the victim's `Commit` row (same sha, different stack), and calls `commit.create_status_from_github!(params)`, writing a `success` `Status` scoped to the **victim's stack_id**. `MergeRequest#all_status_checks_passed?` for the victim's pending merge request now returns true, `reject_unless_mergeable!` no longer rejects on `ci_missing`/`ci_failing`, and `merge!` calls `stack.github_api.merge_pull_request` against the victim's real GitHub repository, merging the victim's PR.

None of the listed guards prevent this: `verify_signature` only authenticates the sender as *a* repository owner, not as the *specific* repository whose commit is being mutated; `drop_unhandled_event` and the `ExplicitParameters` schema only validate payload shape (`sha`/`state` presence), not repository scoping; `force_github_authentication`/`User#authorized?`/`require_permission!` are irrelevant since webhooks bypass session auth entirely; model validations on `Repository`/`Stack` don't constrain `Status.stack_id` at write time beyond FK existence.

### Impact Explanation
This is a payload for one repository (attacker's) mutating another's stack/commit data (victim's `Status` rows), directly enabling an unauthorized merge of a pending `MergeRequest` — the attacker can flip a victim stack's CI-gate state to "passing" and cause `stack.github_api.merge_pull_request` to execute against the victim's actual GitHub repository. This matches the Critical category: "a payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy, rollback or merge." It is repeatable against any victim stack/PR where the attacker can reproduce (or otherwise learn/collide) the head commit's sha, and requires no privileges on the victim's repository, team membership, or any Shipit secret.

### Likelihood Explanation
Preconditions: the attacker needs (1) their own GitHub repository/org onboarded to the same Shipit installation (to have a valid, self-controlled `webhook_secret` for signing), and (2) a commit sha that collides with the victim's PR head sha. Reproducing an *identical* sha across unrelated repositories generally requires either exact duplication of tree/parent/author/committer/timestamp (feasible if attacker can observe the victim's commit metadata and replicate it exactly, e.g. cherry-picking/duplicating a public commit into their own repo — perfectly legal git operation, not a hash break) or a sha1 collision (out of scope for feasibility discussion but not required — simple duplication of an existing public commit is sufficient and costs nothing). Given GitHub commits are frequently public (open-source PRs), an attacker can trivially git fetch the victim's exact commit object and push it into their own repo, yielding an identical sha with zero cryptographic effort. This makes the attack highly feasible and repeatable at will.

### Recommendation
Scope `StatusHandler#process` (and any other sha-keyed handler) to the repository named in the webhook payload, mirroring the `stacks` helper already defined in `Shipit::Webhooks::Handlers::Handler`:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
end
```
This ensures a `Status` is only ever written for a commit belonging to a stack whose repository matches the webhook's authenticated origin, restoring the equality `commit.stack.repository.full_name == payload['repository']['full_name']` before any `Status` row is created.

### Proof of Concept
Minitest under `test/models/webhooks/handlers/status_handler_test.rb` (or extend `test/controllers/webhooks_controller_test.rb`):

```ruby
test "status webhook from an unrelated repository must not create a Status for a commit belonging to a different stack" do
  victim_stack = shipit_stacks(:shipit)
  attacker_stack = shipit_stacks(:cyclimse) # a different repo/org fixture

  colliding_sha = 'a' * 40
  victim_commit = victim_stack.commits.create!(sha: colliding_sha, ...)
  # NOTE: attacker_stack has no commit with this sha; only the victim does.

  payload = {
    'sha' => colliding_sha,
    'state' => 'success',
    'context' => 'ci/attacker',
    'repository' => { 'full_name' => attacker_stack.repo_name, 'owner' => { 'login' => attacker_stack.repo_owner } },
  }

  Shipit::Webhooks::Handlers::StatusHandler.call(payload)

  # Assert the victim commit's stack_id was NOT used to create a Status,
  # i.e. no Status exists tying the victim's stack to a status that
  # only the attacker's (unrelated) webhook secret ever signed.
  assert_empty victim_commit.reload.statuses

  merge_request = shipit_merge_requests(:shipit_pending)
  merge_request.update!(head: victim_commit)
  assert_not merge_request.all_status_checks_passed?

  Shipit::GithubApi.any_instance.expects(:merge_pull_request).never
  assert_raises(Shipit::MergeRequest::NotReady) { merge_request.merge! }
end
```
This test currently **fails** (the Status gets created against `victim_commit`/`victim_stack`, `all_status_checks_passed?` becomes true, and `merge!` would proceed) demonstrating the vulnerability; after applying the recommended fix (scoping by `stacks`), the test passes.
