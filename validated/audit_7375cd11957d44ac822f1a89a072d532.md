### Title
Unhandled `throw Error` on attacker-controlled AA/private-payment validation paths causes daemon crash - (File: `validation.js`)

### Summary
CVE-2016-9131 is a DoS where a malformed (but externally-supplied) response triggers an internal assertion that BIND treats as fatal, crashing the daemon. The ocore codebase has an analogous pattern: several validation callback paths that are reachable from data an unprivileged party controls (a posted unit's author, an AA trigger, or a private-payment chain sent by a payment counterparty) end in a bare `throw Error(...)` instead of an error callback. Because these are synchronous/async throws inside deeply nested callbacks (not wrapped in a caller-level `try/catch` that funnels to `ifUnitError`/`ifJointError`), they propagate up to Node's `uncaughtException` handler in `network.js`, which explicitly re-throws to crash the process: [1](#0-0) 

### Finding Description
`validation.js`'s `validateAuthor` function, when validating an AA-authored unit (i.e., an AA response unit produced while processing an attacker-supplied trigger), does: [2](#0-1) 

If `storage.readAADefinition` cannot find a definition for the AA address at the given `aa_mci` — which can occur due to attacker-influenced conditions such as a trigger causing an AA to be invoked at an MCI/state where its definition lookup is inconsistent, or a crafted trigger driving the AA composer into an unexpected address — the code does not return a callback error but instead `throw Error(...)`. This throw occurs inside an asynchronous callback (`storage.readAADefinition(..., function (arrDefinition) {...})`), so it cannot be caught by the synchronous `try/catch` wrapping `validate()` in `validation.js` (lines 131-138, 235-242, etc., which only guard synchronous code). It propagates to the top of the event loop and crashes the process via the `uncaughtException` handler: [1](#0-0) 

The same unhandled-throw pattern recurs throughout unit/joint validation and AA execution when "should never happen" invariants are violated, e.g.:
- `checkForDoublespends` throws `"conflicting "+type+" spent from another address?"` and `"double spending "+type+" without double spending address?"` when database state derived from attacker-supplied units doesn't match expectations: [3](#0-2) 
- The AA composer's `validateAndSaveUnit` throws on `ifJointError`, `ifTransientError`, `ifNeedHashTree`, `ifNeedParentUnits`, and non-good sequence when saving a self-generated AA response, all conditions that can be forced by carefully crafted trigger data driving the AA into producing a unit that fails its own validation: [4](#0-3) 
- Private/indivisible and divisible asset private-payment handling mirrors this: a private-payment counterparty (an unprivileged party who is allowed to send a private payment chain to a wallet) triggers `getSavingCallbacks`, whose `ifJointError`, `ifTransientError`, and `ifNeedHashTree` handlers are all bare `throw Error(...)`: [5](#0-4) [6](#0-5) 

Unlike `network.js`'s `handleJoint`, which carefully converts validation outcomes for externally-received joints into non-fatal callback paths (`ifUnitError`, `ifJointError` handled gracefully, with only devnet-specific `throw`s), these AA/private-payment code paths were written assuming the unit is "self-generated" and therefore "can't fail," making the `throw` an intentional invariant check. However, because AA response composition and private-payment chain acceptance are both driven by attacker-controlled inputs (a trigger unit's data/formula, or a crafted private payment chain sent directly to a wallet), the "impossible" state can be forced, turning an invariant-violation safety check into a remotely triggerable crash — directly analogous to BIND's "malformed response causes assertion failure and daemon exit."

### Impact Explanation
A successful trigger reaches `process.on('uncaughtException')` in `network.js`, which deliberately re-throws to terminate the process: [1](#0-0) 
This crashes the full node (hub, witness, or wallet backend), producing a network-wide denial of service if repeatable, and can be triggered without any special privilege — merely by posting a unit/trigger or sending a private payment chain that forces the underlying AA/asset code down one of the affected "impossible" branches. This satisfies "a network unable to confirm new units" if targeted at witnesses/hubs performing AA execution or private-payment relaying.

### Likelihood Explanation
Likelihood is moderate: the throw conditions are guarded by earlier validation checks intended to make them unreachable in normal operation, so exploitation requires finding a specific combination of trigger/oscript state, MCI timing, or private-chain payload that defeats those earlier checks (analogous to the specific malformed-RTYPE-ANY condition needed for CVE-2016-9131). No source access is required beyond normal ocore network/wallet protocol usage, and the attack surface (AA triggers, private payment chains) is explicitly reachable by unprivileged actors per the task's scope.

### Recommendation
Replace the bare `throw Error(...)` calls in `validateAuthor` (validation.js:1171), `checkForDoublespends` (validation.js:1673, 1688, 1692), `aa_composer.js`'s `validateAndSaveUnit` (aa_composer.js:1804-1833), and the private-payment `getSavingCallbacks` in `divisible_asset.js`/`indivisible_asset.js` with graceful error propagation (e.g., abort the specific AA execution/bounce the trigger, or reject the private payment chain) instead of crashing the whole process. Reserve process-crashing `throw` only for conditions that are truly unreachable regardless of external input, and add regression tests exercising the edge cases that reach these branches.

### Proof of Concept
Concretely reproducing this requires constructing a trigger/AA state or private-payment chain that reaches one of the flagged branches (e.g., an AA response whose author address has no definition at `aa_mci`, or a private payment chain whose double-spend record address doesn't match any author). Because I do not have runtime access to craft/execute such a trigger against a live node, I cannot supply a working exploit script; the analysis above is based on static code review of the reachable, unhandled-throw paths cited. Confirming exploitability precisely (i.e., which malformed trigger/private-payment input defeats the preceding validation checks) would require dynamic testing in a Devin session with full repository and execution access.
