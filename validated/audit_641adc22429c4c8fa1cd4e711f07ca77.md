### Title
Second-preimage / node-as-leaf forgery in `merkle.js` allows an `["in merkle", ...]` authentifier or `is_valid_merkle_proof()` formula check to accept a forged, non-member "element" - (File: `merkle.js`)

### Summary
`merkle.js` implements the Merkle tree used by ocore's `["in merkle", ...]` address/AA-definition authentifier and the `is_valid_merkle_proof()` oscript formula function. Leaf hashing and internal-node hashing use the exact same hash function applied to plain string concatenation, with no domain separation between leaves and internal nodes and no length-prefixing of the concatenated hash strings. This is the same class of bug as the OpenZeppelin/Footium report: an attacker can present a fabricated "element" equal to the concatenation of two real internal-node hashes and a truncated proof, and `verifyMerkleProof` will accept it as if that string were a genuine leaf of the tree.

### Finding Description
`getMerkleRoot`/`getMerkleProof` build the tree as: [1](#0-0) 

Leaves are hashed with `hash(element)` while internal nodes are hashed with `hash(arrHashes[i] + arrHashes[hash2_index])` — i.e. `sha256(hashA + hashB)` where `hashA`/`hashB` are themselves base64-encoded sha256 digests. There is no tag/prefix distinguishing "this is a leaf hash" from "this is an internal node hash", and no length delimiter between the two concatenated hash strings.

`verifyMerkleProof` mirrors this: it starts from `hash(element)` and then repeatedly does `hash(the_other_sibling + proof.siblings[i])` (or the reverse), finally comparing to `proof.root`: [2](#0-1) 

The code even contains a developer comment flagging this exact risk: `// Node-as-Leaf issue might matter in some cases` at the top of `verifyMerkleProof`, but no mitigation was implemented.

Because leaf-hash = `sha256(element)` and node-hash = `sha256(h1 + h2)` use the identical hash function and no distinguishing structure, an attacker who knows two adjacent hash values `h1`, `h2` from anywhere in a *published* tree can set `element = h1 + h2` (the literal 88-character base64 concatenation) and provide the remaining ancestor siblings as `proof.siblings`, `proof.index` set appropriately. `verifyMerkleProof` will compute `hash(element) === hash(h1+h2)`, which equals the real parent node's hash, and the verification will proceed up to the true published `root` and succeed — even though `element` (`h1+h2`) was never one of the original `arrElements` fed into `getMerkleRoot`.

This directly reaches two ocore surfaces controllable by unprivileged actors:
1. `["in merkle", [addresses, feed_name, element, min_mci]]` — an authentifier condition inside an address (or AA-controlled) definition. The condition is satisfied if `merkle.verifyMerkleProof(element, proof)` returns true and the resulting `proof.root` matches a value the named oracle previously posted as a `data_feed`: [3](#0-2) 
Both `element` (embedded in the definition, which for AA-authored spending conditions is attacker-controlled at address-creation time) and `serialized_proof` (an attacker-supplied authentifier when spending) feed into `verifyMerkleProof` with no leaf/node domain separation.

2. `is_valid_merkle_proof(element, proof)` in the oscript formula language, usable inside Autonomous Agents, where both `element` and `proof` can come straight from AA trigger data: [4](#0-3) 

If an oracle publishes a Merkle root (e.g., a whitelist, KYC list, allowed-club list, etc.) as a data feed value, and the tree structure/intermediate hashes are knowable (which is typical, since Merkle proofs are meant to be publicly verifiable and any prior valid proof already reveals sibling hashes along a path), an attacker can synthesize a forged "element" equal to two sibling hash strings concatenated and produce a valid proof for it against the real, oracle-published root — without that string ever having been a genuine tree member.

### Impact Explanation
Where `["in merkle", ...]` or `is_valid_merkle_proof()` is used to gate spending conditions in an address definition or AA logic (e.g., "only addresses/values present in an oracle-signed whitelist Merkle tree may spend/trigger a payout"), this bug lets an attacker satisfy the authentifier with a value that was never actually included in the whitelisted set, as long as they can derive a valid `h1+h2` pair from tree structure known to them (from previously published proofs, leaked tree data, or a tree whose internal nodes are otherwise learnable). This can result in unauthorized spending from an address/AA that relies on `in merkle`/`is_valid_merkle_proof` to restrict participants, matching the "unauthorized spending" / "AA fund loss" impact classes.

### Likelihood Explanation
Exploitability requires knowledge of at least one adjacent pair of hash values (leaf-hashes or internal-node hashes) inside the referenced tree along with an oracle-published root that the tree feeds into via `dataFeeds.dataFeedExists`. Because Merkle trees are generally intended to be publicly auditable (siblings are revealed to any legitimate holder of a proof), and because both `element` and the `proof` are attacker-suppliable at the "in merkle" authentifier or the AA-trigger `is_valid_merkle_proof` call site, this is realistically reachable by any unprivileged unit poster/AA trigger sender who has visibility into the tree contents used by the oracle/AA design. This mirrors exactly the reachability profile of the referenced Footium/OpenZeppelin issue.

### Recommendation
Add domain separation between leaf and internal-node hashing in `merkle.js`, e.g. prefix leaf hashes with a distinct tag (`hash("leaf:" + element)`) and internal-node hashes with another (`hash("node:" + h1 + h2)`), and/or length-prefix/delimit the two concatenated hash values so a leaf input can never be reinterpreted as the concatenation of two internal-node hashes. Apply this consistently in `getMerkleRoot`, `getMerkleProof`, and `verifyMerkleProof` in `merkle.js`, and bump/guard the format so existing proofs relying on the old scheme are not silently reinterpreted.

### Proof of Concept
1. Suppose an oracle publishes Merkle root `R` for `feed_name` covering a whitelist tree, and (as is normal for Merkle-proof systems) the sibling hash values along some proof path are learnable/public — e.g., the tree owner or another whitelisted party has already revealed a valid proof containing sibling hashes `h1` and `h2` that combine as `hash(h1 + h2) = h_parent`, which lies somewhere on the path to `R`.
2. Construct `forged_element = h1 + h2` (verbatim string concatenation) and `forged_proof = { index: <index of h_parent in tree>, siblings: [<the remaining siblings from h_parent up to R>], root: R }`.
3. Call `merkle.verifyMerkleProof(forged_element, forged_proof)`; internally `hash(forged_element) === hash(h1+h2) === h_parent`, and the remaining hashing chain reproduces `R`, so the function returns `true`, per [2](#0-1) .
4. Use `forged_element` and `serializeMerkleProof(forged_proof)` as the `element`/authentifier value in an `["in merkle", [oracle_address], "feed_name", forged_element]` condition (per [3](#0-2) ) or as arguments to `is_valid_merkle_proof(forged_element, forged_proof)` in an AA formula (per [4](#0-3) ), satisfying a spending/trigger condition that was intended to require genuine list membership.

function hash(str){
	return crypto.createHash("sha256").update(str, "utf8").digest("base64");
}

function getMerkleRoot(arrElements){
	var arrHashes = arrElements.map(hash);
	while (arrHashes.length > 1){
		var arrOverHashes = []; // hashes over hashes
		for (var i=0; i<arrHashes.length; i+=2){
			var hash2_index = (i+1 < arrHashes.length) ? (i+1) : i; // for odd number of hashes
			arrOverHashes.push(hash(arrHashes[i] + arrHashes[hash2_index]));
		}
		arrHashes = arrOverHashes;
	}
	return arrHashes[0];
}

function verifyMerkleProof(element, proof){
	// Node-as-Leaf issue might matter in some cases
	try {
		var index = proof.index;
		var the_other_sibling = hash(element);
		for (var i = 0; i < proof.siblings.length; i++) {
			// this also works for duplicated trailing nodes
			if (index % 2 === 0)
				the_other_sibling = hash(the_other_sibling + proof.siblings[i]);
			else
				the_other_sibling = hash(proof.siblings[i] + the_other_sibling);
			index = Math.floor(index / 2);
		}
		return (the_other_sibling === proof.root);
	}
	catch (e){
		return false;
	}
}
