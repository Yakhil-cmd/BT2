### Title
`add_tip`/`register_token` tip-asset-to-Ether swap uses zero slippage protection, allowing burn of fewer wei than fair value in volatile conditions - (File: bridges/snowbridge/pallets/system-frontend/src/lib.rs)

### Summary
`pallet-snowbridge-system-frontend`'s `add_tip` and `register_token` extrinsics let any signed caller swap an arbitrary tip/fee asset into Ether via `pallet_asset_conversion::Swap::swap_exact_tokens_for_tokens`, then burn the resulting Ether amount for teleport to Ethereum as a relayer reward/tip. The swap call passes `None` as `amount_out_min`, i.e. no minimum-output/slippage protection, structurally the same pattern as the referenced Napier/Kelp report where `RSETH_DEPOSIT_POOL.depositETH` was called with a hardcoded `0` minimum.

### Finding Description
`Pallet::add_tip` is a plain signed extrinsic (`ensure_signed(origin)?`) reachable by any account with a balance of some asset accepted by the on-chain AMM pool: [1](#0-0) 

It calls `swap_fee_asset_and_burn`, which for any fee asset other than Ether itself, delegates to `swap_and_burn`: [2](#0-1) 

`swap_and_burn` performs the actual AMM swap: [3](#0-2) 

The `amount_out_min` argument to `T::Swap::swap_exact_tokens_for_tokens` is hardcoded to `None` (comment: "No minimum amount required"). This is functionally the "zero slippage" bug from the report: the underlying AMM (`pallet-asset-conversion`) does support and enforce a minimum-output check when a `Some(min)` is supplied — see `do_swap_exact_tokens_for_tokens`, which rejects the swap via `Error::<T>::ProvidedMinimumNotSufficientForSwap` if `amount_out < amount_out_min`: [4](#0-3) 

But `system-frontend` deliberately bypasses this protection by passing `None`, so whatever the AMM pool state happens to return — including a heavily depressed rate due to pool imbalance, a large prior trade in the same block/extrinsic-batch, or multi-hop path manipulation — is accepted unconditionally and burned as the "amount of Ether teleported" for the tip/reward.

Because `swap_path` and `tip_amount`/`fee_asset` are taken directly from the caller-controlled `asset: Asset` parameter of `add_tip` (and `fee_asset: Asset` of `register_token`), and the resulting `ether_gained` is what gets committed on-chain as `AddTip { sender, message_id, amount }` (dispatched cross-chain to BridgeHub and ultimately used to set the relayer reward for that message), an attacker or just adverse market conditions can cause a caller to receive (and the protocol to commit) a materially lower Ether-denominated reward than the nominal tip they paid, with no recourse — the extrinsic still succeeds.

### Impact Explanation
This does not cause unbacked issuance or theft of other users' funds; the caller only spends their own tip asset. However it violates the "no execution without price guarantee" invariant that the underlying `pallet-asset-conversion` explicitly supports (`amount_out_min`) and that Snowbridge's own fee/reward economics assume a faithful ETH-denominated conversion. Concretely:
- A user calling `add_tip` in a moment of low pool liquidity/high volatility (e.g., right after a large trade in the same pool, or via pool manipulation within the same block using other `pallet-asset-conversion` calls) can have their tip asset converted into far less Ether than fair value, and that lower amount is what gets recorded as the relayer reward on BridgeHub — directly analogous to the report's "less rsETH minted than intended" outcome, just here it is "less Ether tipped than intended."
- Because the swap is composable within a single transaction (an attacker can queue `swap_exact_tokens_for_tokens`/`add_liquidity`/`remove_liquidity` calls immediately before/after in the same block, or via a batch), the price impact is not merely passive market drift but can be actively engineered by any account with capital, since the pool is a standard constant-product AMM with public swap/liquidity extrinsics and no privileged role is required.
- Impact is bounded to the caller's own tip funds (no cross-account theft), so this is best characterized as Medium: a real accepted-extrinsic invariant violation with demonstrable economic loss to the specific user/reward economics, not a Critical/High unbacked-issuance or theft bug.

### Likelihood Explanation
Likelihood is moderate-to-high in practice: `add_tip` is fully permissionless (any signed account, no governance/privileged prerequisite), and AMM pools generally have finite liquidity, so slippage during ordinary demand spikes or via same-block sandwiching (self-inflicted or third-party, since XCM/AssetConversion calls are all public extrinsics) is a normal, expected occurrence for constant-product pools — no bridging exploit, forged proof, or malicious relayer/collator is required, matching the report's model exactly (the caller/attacker has no privileged role).

### Recommendation
Add a configurable minimum-output parameter to `add_tip`/`register_token` (or compute one on-chain via `QuotePrice`/`quote_price_exact_tokens_for_tokens` with a bounded tolerance), and pass `Some(min_ether_out)` into `T::Swap::swap_exact_tokens_for_tokens` inside `swap_and_burn`, rejecting the extrinsic if the AMM cannot honor it, mirroring the slippage protection already implemented and enforced by `pallet_asset_conversion::do_swap_exact_tokens_for_tokens`.

### Proof of Concept
No local Rust/FRAME integration reproduction was executed in this session (tool budget exhausted before running a test harness). The evidence above is based on static code inspection only:
- Confirmed `add_tip` is a permissionless signed extrinsic with no privileged prerequisite: [1](#0-0) 
- Confirmed the hardcoded `None` slippage parameter passed to the swap call: [5](#0-4) 
- Confirmed the underlying `pallet-asset-conversion` does support and enforce a real minimum-output check when supplied, proving the omission is a deliberate/available-but-unused guard rather than an inherent AMM limitation: [4](#0-3)  and the existing test demonstrating the guard's effect when engaged: [6](#0-5) 

A concrete PoC would need to: (1) set up a `pallet-asset-conversion` pool with a tip asset/Ether pair in the `snowbridge-pallet-system-frontend` mock runtime, (2) drain/skew the pool via a large prior `swap_exact_tokens_for_tokens` or `remove_liquidity` call in the same block, (3) call `add_tip` with a tip amount that would receive materially less Ether than the pre-skew quote, and (4) assert the extrinsic still succeeds and that `ether_gained` (visible via the `AddTip` call built in `build_add_tip_call`) is below the fair-value quote — this reproduction was not executed here and its exact numeric magnitude of loss is unverified.

		/// Swaps a specified tip asset to Ether and then burns the resulting ether for
		/// teleportation. Returns the amount of Ether gained if successful, or a DispatchError if
		/// any step fails.
		fn swap_and_burn(
			origin: Location,
			tip_asset_location: Location,
			ether_location: Location,
			tip_amount: u128,
		) -> Result<u128, DispatchError> {
			// Swap tip asset to ether
			let swap_path = vec![tip_asset_location.clone(), ether_location.clone()];
			let who = T::AccountIdConverter::convert_location(&origin)
				.ok_or(Error::<T>::LocationConversionFailed)?;

			let ether_gained = T::Swap::swap_exact_tokens_for_tokens(
				who.clone(),
				swap_path,
				tip_amount,
				None, // No minimum amount required
				who,
				true,
			)?;

			// Burn the ether
			let ether_asset = Asset::from((ether_location.clone(), ether_gained));

			burn_for_teleport::<T::AssetTransactor>(&origin, &ether_asset)
				.map_err(|_| Error::<T>::BurnError)?;

			Ok(ether_gained)
		}

		fn swap_fee_asset_and_burn(
			origin: Location,
			fee_asset: Asset,
		) -> Result<u128, DispatchError> {
			let ether_location = T::EthereumLocation::get();
			let (fee_asset_location, fee_amount) = match fee_asset {
				Asset { id: AssetId(ref loc), fun: Fungible(amount) } => (loc, amount),
				_ => {
					tracing::debug!(target: LOG_TARGET, ?fee_asset, "error matching fee asset");
					return Err(Error::<T>::UnsupportedAsset.into());
				},
			};
			if fee_amount == 0 {
				return Ok(0);
			}

			let ether_gained = if *fee_asset_location != ether_location {
				Self::swap_and_burn(
					origin.clone(),
					fee_asset_location.clone(),
					ether_location,
					fee_amount,
				)
				.inspect_err(|&e| {
					tracing::debug!(target: LOG_TARGET, ?e, "error swapping asset");
				})?
			} else {
				burn_for_teleport::<T::AssetTransactor>(&origin, &fee_asset)
					.map_err(|_| Error::<T>::BurnError)?;
				fee_amount
			};
			Ok(ether_gained)
		}
