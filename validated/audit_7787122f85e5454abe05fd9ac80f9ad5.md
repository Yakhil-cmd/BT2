## Title
Stack-scoped API tokens can read the CCMenu status of any stack, bypassing the token's `stack_id` binding - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

## Summary
`Shipit::Api::CCMenuController` overrides the `stack` resolver used by `BaseController` and, in doing so, drops the scoping that binds a stack-restricted `ApiClient` token to the single stack it was issued for. Any valid token — even one explicitly created to read only one stack (e.g. via the CCMenu URL flow) — can be replayed against `/api/stacks/:stack_id/ccmenu` for any other stack in the installation, since the permission check only verifies the `read:stack` permission flag and never re-validates `stack_id` against the requested stack.

## Finding Description
`Shipit::Api::BaseController` establishes the authorization binding "token authorises stack X" == "stack acted upon is X" via the `stacks` helper: [1](#0-0) 

`current_api_client.stack_id?` is true when the `ApiClient` was created scoped to a single stack (as opposed to `UnlimitedApiClient`, which always returns `false` and is only used when API auth is globally disabled): [2](#0-1) 

Every other controller that reads/writes a specific stack (e.g. `StacksController`) resolves the target stack through this scoped `stacks` relation: [3](#0-2) 

`CCMenuController`, however, defines its own `stack` method that queries `Stack.from_param!` directly against the unscoped `Stack` model, completely bypassing `current_api_client.stack_id`: [4](#0-3) 

The only authorization check that remains is `require_permission :read, :stack`, which merely checks that the client's `permissions` array contains `read:stack` — it says nothing about *which* stack: [5](#0-4) [6](#0-5) [7](#0-6) 

This is exactly the class of bug in the report: an authorization scope carried on the credential (here, the `stack_id` the token is bound to) is checked in the "normal" code path but silently dropped in one code path that re-derives the resource from raw request input instead of from the already-scoped relation. The equality that should hold is:

`current_api_client.stack_id (if scoped) == stack.id (being acted upon)`

but for `CCMenuController#show`, the right-hand side is derived from `params[:stack_id]` against the global `Stack` table, so the equality is never enforced.

Making the exposure concrete: `CCMenuUrlController` is the documented, unprivileged-relative-to-other-stacks way this token type is minted — it creates (or reuses) a `read:stack`-only, stack-scoped `ApiClient` named "CCMenu Client" per user and hands back a URL containing the signed token: [8](#0-7) 

That token is meant to expose CI-status (CCMenu/CCTray XML) for one stack only (e.g. for use in a build-status widget/menubar app), yet because `CCMenuController#stack` ignores `stack_id?`, the same token can be used to poll `/api/stacks/<any-other-stack>/ccmenu` and read that other stack's last build/deploy status, name, activity, and lock state — data belonging to a stack the token was never authorized for.

## Impact Explanation
This matches the High-severity category "unauthenticated/unauthorized read of stack state" in scope: a credential that a user believes is scoped to a single (possibly less-sensitive) stack's CI status can be used to enumerate/read build and deploy status of every stack in the Shipit installation, including stacks the token holder may have no other access to. It is a genuine authorization-scope-bypass rather than a data-exposure bug limited to CI status semantics, because the whole point of `ApiClient#stack_id` is per-stack least privilege for tokens (this is the mechanism `CCMenuUrlController` explicitly relies on to mint narrowly-scoped tokens for embedding in URLs/widgets).

## Likelihood Explanation
Any holder of a legitimately-issued, stack-scoped `read:stack` token (which by design is meant to be embedded/shared, e.g. pasted into CI dashboard tools, since `CCMenuUrlController#fetch` returns the token in a plain URL) can trivially exploit this by changing the `stack_id` in the request path — no additional privileges, secrets, or session are required beyond possessing that one token. This is a simple parameter substitution, requiring no race condition, no signature forgery, and no elevated access.

## Recommendation
Remove the `stack` override in `CCMenuController` (or reintroduce the scoping) so that it resolves the stack through the inherited, scope-aware `stacks` relation from `BaseController`, e.g.:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
This restores the invariant that `current_api_client.stack_id`, when set, must equal the `id` of the stack being read, consistent with every other stack-scoped API controller.

## Proof of Concept
1. As an authenticated user, call `GET /stacks/:owner/:repo/:env/ccmenu_url` (routed to `CCMenuUrlController#fetch`) to obtain a `ccmenu_url` containing a `token` for a `read:stack`-only `ApiClient` scoped to `stack_id = A`. [9](#0-8) 
2. Take that `token` and issue `GET /api/stacks/B/ccmenu` for a *different* stack `B` that the token was never scoped to, using the same token via HTTP Basic auth (as `ApiClient.authenticate` decodes it) or the `token` query param supported by `CCMenuController#authenticate_api_client`: [10](#0-9) 
3. The request succeeds and returns stack `B`'s CCMenu XML (name, last build status, activity, web URL) because `CCMenuController#stack` resolves `B` via unscoped `Stack.from_param!`, never checking that the token's `stack_id` is `A`: [11](#0-10)

require 'uri'

module Shipit
  class CCMenuUrlController < ShipitController
    def fetch
      uri = URI(api_stack_ccmenu_url(stack_id: stack.to_param))
      uri.query = { 'token' => client.authentication_token }.to_query
      render(json: { ccmenu_url: uri.to_s })
    end

    private

    def client
      @client ||= ApiClient.create_with(permissions: %w[read:stack])
                           .find_or_create_by!(creator: current_user, name: 'CCMenu Client')
    end

    def stack
      @stack ||= Stack.from_param!(params[:stack_id])
    end
  end
end
