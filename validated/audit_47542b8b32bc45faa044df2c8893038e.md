### Title
Tokens transferred directly to the Pool contract are permanently locked — `cash` accounting never credits them and no skim/rescue path exists - (File: contracts/pool/src/cache/cash.rs)

### Summary
The `FeeReceiver` bug class — a contract that can receive tokens but has no function to retrieve them — maps directly onto the XOXNO Lending `pool` contract. The pool holds the physical token balance for every market, but all outbound transfers (`withdraw`, `borrow`, `claim_revenue`, `recapitalize` refunds, seize/transfer legs) are gated by the internally tracked `cash` reserve, which is only mutated through `credit_cash`/`debit_cash` inside pool ops. Any tokens pushed to the pool address via a plain `token.transfer` — explicitly listed as a reachable unprivileged path — raise the real balance without raising `cash`, and no function exists to sweep the difference. The surplus is trapped permanently.

### Finding Description
`Cache::transfer_out` is the only outbound token primitive in the pool, and it is only invoked after `debit_cash(amount)` succeeds, which itself requires `self.cash >= amount` via `require_reserves` (`contracts/pool/src/cache/cash.rs:32-53`). `cash` is a storage-accounted field credited only by `credit_cash` inside pool operations such as `supply`/`repay` settlement (`contracts/pool/src/cache/cash.rs:24-30`). A direct `token::Client::transfer(sender, pool_address, amount)` increases the pool's real token balance but touches no storage, so:

- `require_reserves` still sees the same `cash`, so no withdrawal, borrow, claim, or flash leg can be sized against the donated tokens.
- `claim_revenue` is capped by `min(cash, floor(revenue_value))` (`Cache::burn_claimable_revenue`, `contracts/pool/src/cache/shares.rs:54-56`), so protocol revenue cannot absorb them either.
- `interest.rs`/index accrual operates on share state (`supplied`, `revenue`, `borrowed`), not token balances, so the extra balance is invisible to every code path.

A repo-wide search for `skim`, `rescue`, `recover`, `sweep`, `excess` in `contracts/**` finds no pool-side recovery function — the only matches are in `swap-aggregator` (out of scope) and governance timelock internals. Unlike `FeeReceiver`, where the fix was simply "add a withdraw function," here the tokens are locked *twice*: there is no withdraw, and the accounting layer structurally ignores them.

The controller has the same shape at a secondary level: `refund_controller_balance_delta` refunds only the post-snapshot delta and explicitly "preserv[es] the pre-existing balance" (`contracts/controller/src/payments.rs:39-51`), and `claim_revenue_for_asset` forwards only the measured delta (`contracts/controller/src/markets.rs:182-196`), so a pre-existing stray controller balance is likewise stranded. The pool is the stronger instance because stranded tokens there are not merely idle — they can never be paid out at all.

### Impact Explanation
Permanent freezing of funds, an accepted impact class. Any unprivileged address that transfers a market asset directly to the pool contract — a plausible mistake given the pool is the canonical holder of market tokens and users interact with it indirectly through the controller — loses those tokens irreversibly. The tokens remain in the pool's balance but are unreachable by every entrypoint, including the owner-gated ones, because payout capacity is derived exclusively from the `cash` ledger entry. There is no governance rescue, no skim, and no emergency withdraw in the pool ABI (`contracts/pool/src/lib.rs` exposes only `transfer_out` consumers, all cash-gated). Impact is bounded by the amount sent (per-incident), not a protocol-wide drain.

### Likelihood Explanation
Requires an external trigger (a direct transfer to the pool or controller address) rather than a profitable exploit, so the likelihood is moderate rather than high. However, the exposure is continuous: the pool address is discoverable, Stellar token transfers are one-call operations, and integrations or users may reasonably assume tokens sent to the pool back the market (as they do in many pool designs that measure balance deltas). Once sent, the loss is irreversible — no privileged or unprivileged path can ever unlock them. Medium severity.

### Recommendation
Add an owner-gated `skim`/`rescue` function on the pool that computes `token.balance(pool) - cash` and transfers the surplus to a configured recipient (e.g., the accumulator/owner), restricted to amounts strictly above accounted `cash` so it can never touch user-backed reserves. Apply the same treatment on the controller for stranded pre-existing balances. Alternatively — and more robustly — have `supply`/`repay` measure the balance delta received rather than trusting declared amounts, and document that direct transfers are donations absorbed into `cash` (crediting them to `cash` or `revenue` would at least keep them claimable rather than burned forever).

### Proof of Concept
```rust
// Soroban test sketch, pool-only
let t = TestSetup::new();
let client = t.client();
let tok = token::Client::new(&t.env, &t.asset);

client.supply(&t.sup(0, 50_000_000_000i128));           // cash = 50_000_000_000

// Unprivileged user pushes tokens straight to the pool contract.
let rando = Address::generate(&t.env);
token::StellarAssetClient::new(&t.env, &t.asset).mint(&rando, &1_000_000_000);
tok.transfer(&rando, &t.pool, &1_000_000_000);          // pool balance = 51_000_000_000

// Accounting cash is unchanged: no entrypoint can pay out the extra 1_000_000_000.
assert_eq!(t.state_snapshot().cash, 50_000_000_000);
assert_eq!(tok.balance(&t.pool), 51_000_000_000);

// Full supplier withdraw drains exactly `cash` worth of backing;
// claim_revenue is capped by min(cash, revenue_value) -> cannot reach the surplus.
// No skim/rescue/rescue_token exists in the pool ABI.
// The 1_000_000_000 is locked in the pool address forever.
```

Root cause support: `Cache::debit_cash` + `require_reserves` gate every outbound transfer on stored `cash` (`contracts/pool/src/cache/cash.rs:15-41`), `transfer_out` never consults the actual token balance (`contracts/pool/src/cache/cash.rs:46-53`), `burn_claimable_revenue` caps claims at `self.cash` (`contracts/pool/src/cache/shares.rs:54-56`), and the controller refunds/forwards only measured deltas, preserving stranded balances (`contracts/controller/src/payments.rs:41-51`, `contracts/controller/src/markets.rs:182-196`).
