### Title
Cross-stack read authorization bypass via unscoped `stack` lookup in CCMenu API - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::CCMenuController` accepts any valid `ApiClient` token and independently re-resolves the target `Stack` from the request's `stack_id` param using an **unscoped** lookup, instead of the stack-scoped lookup used everywhere else in the API. This breaks the binding "the stack(s) an `ApiClient` token authorizes == the stack it actually touches," letting the holder of a stack-scoped, `read:stack`-only token read deploy/build state for any stack in the installation, not just the one the token was issued for.

### Finding Description
`Shipit::Api::BaseController` enforces per-token stack scoping through two cooperating methods: [1](#0-0) 

`stacks` restricts the visible set to `current_api_client.stack_id` when the client is scoped, and `stack` resolves the requested record only from within that restricted set. Every other API controller (`Api::StacksController`, etc.) inherits this `stack` method and therefore respects the token's stack scope.

`Api::CCMenuController`, however, overrides `stack` to bypass the scoped `stacks` collection entirely: [2](#0-1) 

It authenticates the caller purely from `params[:token]` (`ApiClient.authenticate(params[:token])`) and then calls `Stack.from_param!(params[:stack_id])` directly on the unscoped `Stack` relation. The only authorization check performed is `require_permission :read, :stack`, which — via `ApiClient#check_permissions!` — only checks that `"read:stack"` is present in the client's `permissions` array; it never checks that `params[:stack_id]` matches `current_api_client.stack_id`: [3](#0-2) 

So the equality the rest of the API enforces —
`stacks visible to token == Stack.where(id: current_api_client.stack_id)` (when scoped)
— is silently replaced in this one controller by
`stacks visible to token == Stack.from_param!(any stack_id in the URL)`.

Any `ApiClient` record with `permissions` including `read:stack` (regardless of whether `stack_id` is set, i.e. regardless of whether it was meant to be scoped to a single stack) can be used against `GET /api/stacks/:stack_id/ccmenu?token=...` for an arbitrary `:stack_id` to fetch that stack's latest deploy/rollback status.

### Impact Explanation
This is an unauthenticated (session-less, token-only) read of stack/deploy state across stack boundaries — a client explicitly minted/scoped for one stack (e.g., a CCMenu build-status widget URL meant to expose only that stack, generated in `Shipit::CCMenuUrlController#client`) can be replayed with a different `stack_id` to read another stack's latest deploy id, completion time, and running status. This matches the "unauthenticated read of stack state ... or deploy output" High-impact category, since possession of any single valid `read:stack` token becomes sufficient to enumerate deploy state for every stack in the installation instead of the one it was authorized for.

### Likelihood Explanation
Likelihood is Medium/High for anyone who already possesses a legitimate `read:stack`-scoped `ApiClient` token (e.g., a CCMenu URL shared with an external CI dashboard, or any integration holding a stack-scoped API token) — the identifier is a public API endpoint and `stack_id` is a normal user-supplied route/query parameter, requiring no privileged action beyond swapping it.

### Recommendation
Change `Api::CCMenuController#stack` to reuse the inherited, scope-respecting lookup instead of hitting `Stack` directly:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
i.e., remove the private `stack` override so the controller falls back to `Api::BaseController#stack`/`#stacks`, ensuring the stack requested is always constrained to `current_api_client.stack_id` when the token is scoped.

### Proof of Concept
1. Create/obtain an `ApiClient` scoped to Stack A with permission `read:stack` only (e.g., via the standard "CCMenu Client" flow in `Shipit::CCMenuUrlController`, or any integration token limited to Stack A).
2. Take that token's `authentication_token` and call:
   `GET /api/stacks/<stack-B-param>/ccmenu?token=<token>`
   where Stack B is a completely unrelated stack the token was never scoped/authorized for.
3. Because `Api::CCMenuController#stack` calls `Stack.from_param!(params[:stack_id])` directly (`app/controllers/shipit/api/ccmenu_controller.rb:29-31`) instead of the scoped `stacks.from_param!` used elsewhere, the request succeeds and returns Stack B's latest deploy/rollback XML status, despite the token only being authorized for Stack A.
