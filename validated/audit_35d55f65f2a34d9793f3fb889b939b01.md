### Title
`ReopenedHandler#unarchive?` reproduces the `&&`/`||` precedence defect from `OpenedHandler#provision?`, letting an attacker re-provision an archived `ReviewStack` on a repository with `review_stacks_enabled = false` - ([File: app/models/shipit/webhooks/handlers/pull_request/reopened_handler.rb])

### Summary
`Shipit::Webhooks::Handlers::PullRequest::ReopenedHandler#unarchive?` uses the exact same boolean expression as `OpenedHandler#provision?`, where Ruby operator precedence causes `repository.review_stacks_enabled` to only gate the `provisioning_behavior_allow_all?` branch, not the `allow_with_label?`/`prevent_with_label?` branches. As a result, reopening a PR on a repository configured with `review_stacks_enabled: false` and `provisioning_behavior: :prevent_with_label` (no label present) still returns `true`, causing the engine to unarchive and re-enqueue the stack for provisioning.

### Finding Description
The claimed binding is: `repository.review_stacks_enabled` (as read at reopen-time in `ReopenedHandler#unarchive?`) == the sole gate controlling whether `stack.unarchive!` and `Shipit::ReviewStackProvisioningQueue.add(stack)` execute.

The actual code is: [1](#0-0) 

Due to Ruby's `&&` binding tighter than `||`, this parses as:
`(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?)`

`review_stacks_enabled` is not distributed over all three disjuncts, so it has no effect at all when `provisioning_behavior` is `:allow_with_label` or `:prevent_with_label`. With `review_stacks_enabled: false`, `provisioning_behavior: :prevent_with_label`, and no provisioning label on the PR, the third disjunct `(true && true)` makes the whole expression `true`, identical to the pre-existing defect already present in `OpenedHandler#provision?`: [2](#0-1) 

`process` then calls `stack.unarchive!` (via the `ReviewStackAdapter`), which re-enqueues the stack for provisioning and clears `archived_since`/`lock_reason`: [3](#0-2) [4](#0-3) [5](#0-4) 

Attacker request: any GitHub user reopens a previously-closed PR (or a repository owner triggers the `pull_request` `reopened` webhook event, e.g. via GitHub Actions or the API on a repo they control) against a Shipit-connected repository whose Shipit configuration has `review_stacks_enabled: false` and `provisioning_behavior: :prevent_with_label`, without applying the provisioning label. `ReopenedHandler#process` unarchives the stack and re-adds it to `ReviewStackProvisioningQueue`, from which the background worker will call `stack.provision` and re-run the deploy spec's provisioning/`shipit.yml` steps for that PR's branch — even though the repository owner explicitly disabled review stacks.

No existing guard intercepts this: `respond_to_pull_request_reopened?` only checks `params.action == "reopened"` and delegates to the flawed `unarchive?`; no additional authorization, signature, or `review_stacks_enabled`-scoped check exists downstream before `unarchive!`/`ReviewStackProvisioningQueue.add` run.

### Impact Explanation
Re-provisioning an archived `ReviewStack` re-triggers deploy-spec-driven provisioning execution (via `stack.provisioner.provision?`/`stack.provision` in `ReviewStackProvisioningQueue#provision`) for a repository that has `review_stacks_enabled = false`, i.e., for a repository whose owner explicitly opted out of automated review-stack execution. This is an unauthorized re-provisioning/deploy of attacker-influenced content (branch head, `shipit.yml`), matching the "unauthorized deploy" Critical category. The blast radius is scoped to repositories/stacks that were previously provisioned (so a `ReviewStack` record already exists and is archived) and later had `review_stacks_enabled` toggled to `false` or configured with `prevent_with_label`/`allow_with_label` behaviors; it does not cross tenant boundaries into unrelated repositories, since `repository` and `stack` are looked up from the webhook's own `params.repository.full_name`.

### Likelihood Explanation
Preconditions: a `ReviewStack` must already exist and be archived (i.e., the PR was opened/provisioned in the past, then closed), and the repository must currently be configured with `review_stacks_enabled: false` combined with `provisioning_behavior: :prevent_with_label` (no label) or `:allow_with_label` (with label). Any GitHub user with push access to a PR branch on that repository — no Shipit credentials required — can reopen a PR to trigger this. This is a repeatable, low-cost, purely webhook-driven exploit against any Shipit-connected repository matching this configuration.

### Recommendation
Fix the operator precedence identically in both handlers by parenthesizing the enable check so it applies to all branches:
```ruby
def unarchive?
  repository.review_stacks_enabled &&
    (repository.provisioning_behavior_allow_all? ||
     (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
     (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?))
end
```
Apply the same fix to `OpenedHandler#provision?`.

### Proof of Concept
minitest (`test/models/shipit/webhooks/handlers/pull_request/reopened_handler_test.rb`):
1. Create a `Repository` with `review_stacks_enabled: false` and `provisioning_behavior: :prevent_with_label`.
2. Create an archived `ReviewStack` for that repository at `environment: "pr#{number}"`.
3. Build webhook params for `action: "reopened"` with no `labels`.
4. Assert equality-before: `repository.review_stacks_enabled` is `false` while `ReopenedHandler#send(:unarchive?)` returns `true` (the divergence).
5. Call `ReopenedHandler.new(params).process` and assert `stack.reload.archived?` is `false` and that `Shipit::ReviewStackProvisioningQueue.queued_stacks` includes the stack — demonstrating unauthorized re-provisioning despite `review_stacks_enabled: false`.
