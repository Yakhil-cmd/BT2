### Title
Attacker `Split`/`Deactivate` between epoch-boundary reward calculation and validator restart makes `recalculate_stake_rewards` diverge from the frozen original calculation, causing cross-node reward state and bank-hash divergence - ([File: runtime/src/bank/partitioned_epoch_rewards/calculation.rs])

### Summary
`recalculate_stake_rewards` recomputes stake rewards for the still-undistributed portion of an active `EpochRewards` sysvar using the *current* `StakesCache` after a snapshot restore, whereas a non-restarted node simply keeps and pays out the reward list frozen at the epoch boundary. Because per-account effective stake is derived from the delegation's mutable `stake` field with no historical memory, an attacker who `Split`s or `Deactivate`s their own already-computed stake account between the original calculation and a validator's restart causes that restarted validator to compute a different `stake_reward`/`inflation` amount than validators that never restarted, even though both processed the identical block sequence.

### Finding Description
At the epoch boundary, `Bank::compute_new_epoch_caches_and_rewards` (`runtime/src/bank.rs:1750-1814`) computes the full `PartitionedStakeRewards` set once and stores it via `set_epoch_reward_status_calculation`/`set_epoch_reward_status_distribution`. This frozen `Arc<PartitionedStakeRewards>` is simply carried forward, unmodified, on every subsequent `Bank::new_from_parent` call for the rest of the distribution phase — it is never recomputed for a live (non-restarted) validator.

If a validator restarts from a snapshot while `EpochRewards.active == true`, `initialize_after_snapshot_restore` (`runtime/src/bank.rs:6061-6085`) calls `recalculate_partitioned_rewards_if_active`, which calls `recalculate_stake_rewards` (`runtime/src/bank/partitioned_epoch_rewards/calculation.rs:1038-1095`). This function rebuilds stake rewards **from scratch** using:
- `point_value` taken from the fixed sysvar (`total_rewards`/`total_points`), and
- `stake_delegations` taken from `self.stakes_cache.stakes()` — the **current, mutable** state of the bank at the (later) restart slot.

The actual numeric reward for each delegation flows through `calculate_stake_rewards_and_commissions` → `redeem_delegation_rewards`/`calculate_stake_rewards` (`runtime/src/inflation_rewards/mod.rs`) and `calculate_alpenglow_points`/`calculate_points_for_tower` (`runtime/src/inflation_rewards/points.rs`), all of which derive the per-account "effective stake" for the (past) `rewarded_epoch` via `delegation_effective_stake`/`delegation_activation_status` (`runtime/src/stake_delegation.rs:9-39`), which dispatch to `Delegation::stake_v2`/`stake_activating_and_deactivating_v2`. For an already fully-activated delegation, these functions return the effective stake as simply the delegation's *current* `stake` field — there is no per-epoch historical snapshot of the stake amount. Consequently, if the attacker calls `Split` (which immediately reduces the source account's `Delegation.stake` while preserving `activation_epoch`) or `Deactivate` (which sets `deactivation_epoch`) on their own stake account any time between the original epoch-boundary computation and a validator's restart+recalculation, the *same* historical `rewarded_epoch` now evaluates to a different effective stake for that account.

A non-restarted validator never re-evaluates this — it just pays out the number computed and frozen at the epoch boundary block. A validator that restarts mid-distribution recomputes using the mutated delegation and gets a numerically different `stake_reward`, `commission_bps`, or (for `Deactivate`) potentially a different eligibility outcome for the currently-undistributed partitions. `build_partitioned_stake_rewards`/`compare_stake_rewards` in the test suite show that developers expect recalculated and originally-computed rewards for undistributed partitions to be byte-identical (`test_recalculate_stake_rewards`, `test_recalculate_partitioned_rewards`, `runtime/src/bank/partitioned_epoch_rewards/calculation.rs:2417-2675`), but none of these tests exercise an attacker mutating the stake account between calculation and recalculation — the newly-added guard test (`test_recalculate_alpenglow_rewards_after_partial_distribution_uses_original_denominator`, lines 2678-2798) only protects the *denominator* (`RewardEpochDelegatedStakes`) against drift, not the per-account *numerator* (`Delegation.stake` itself), leaving this path unguarded.

Since `distribute_partitioned_epoch_rewards` credits stake accounts with exactly the recomputed/frozen amount, a discrepancy directly changes account lamport balances and thus the resulting bank hash for that slot, producing consensus-breaking divergence between validators that restarted mid-distribution and those that did not, despite identical replayed transaction history.

### Impact Explanation
This falls under cross-node state divergence / epoch-boundary halt: validators that restart during the reward-distribution window can credit a different lamport amount to an attacker-influenced stake account than validators that stayed up, producing differing bank hashes for the same slot and block sequence. That is a duplicate-block/bank-hash-mismatch class issue that can halt or fork the cluster at epoch boundaries — the most severe category listed in the prompt's scoped impact.

### Likelihood Explanation
The attacker needs only to own a delegated stake account with a pending, not-yet-distributed reward and submit an ordinary `Split` or `Deactivate` stake instruction (fully within normal unprivileged capability) in any block after the epoch-boundary reward calculation but before some validator happens to restart (a routine, frequent operational event — snapshot-based restarts, crash recovery, or fast-boot from a downloaded snapshot). No fork-switch manipulation or validator control is required; the trigger event (restart) is explicitly called out as in-scope ("recalculation is triggered by normal restart flow"). This is realistically triggerable by any staker with routine restart cadence across a diverse validator set.

### Recommendation
`recalculate_stake_rewards` should not re-derive per-account reward amounts from the live, mutable `StakesCache`. Instead, either:
1. Persist/snapshot the frozen `PartitionedStakeRewards` (or enough state to deterministically reconstruct it, e.g. a snapshot of `Delegation.stake`/`activation_epoch`/`deactivation_epoch` as of the epoch-boundary block) so recalculation reproduces exactly the original values, or
2. Explicitly snapshot the epoch-boundary `Delegation` values used for reward math (analogous to how `RewardEpochDelegatedStakes` already snapshots the denominator) and feed those frozen per-account values into `calculate_stake_rewards_and_commissions` during recalculation instead of the current `stakes_cache.stakes()` delegations.

### Proof of Concept
Rust integration test plan (extending the existing test harness in `runtime/src/bank/partitioned_epoch_rewards/calculation.rs`):
1. Build a `RewardBank` with tower (non-AG) rewards active, at least 2 delegations, distributed over 2+ blocks (reuse `create_reward_bank_with_specific_stakes`).
2. Advance to the epoch boundary; capture `all_stake_rewards` from `EpochRewardStatus::Active(EpochRewardPhase::Calculation)` — this is `expected_stake_rewards`.
3. Before distributing all partitions, have the "attacker" stake account (one whose reward is still undistributed) submit a `Split` instruction reducing its `Delegation.stake`, applied via a normal `Bank::new_from_parent` transaction execution (not direct store mutation).
4. Call `bank.recalculate_stake_rewards(&epoch_rewards_sysvar, &thread_pool)` to simulate a validator restart at this slot.
5. Assert that `recalculated_rewards` for the attacker's stake_pubkey differs from `expected_stake_rewards` for the same pubkey/partition (`inflation.stake_reward` or eligibility differs), while a control validator that never restarted still holds the untouched `expected_stake_rewards` in its in-memory `epoch_reward_status`.
6. Assert this produces different lamport credits when each variant runs `distribute_partitioned_epoch_rewards`, demonstrating a bank-state (and thus bank-hash) divergence between the "restarted" and "non-restarted" code paths for the identical block/transaction sequence.     pub(in crate::bank) fn recalculate_partitioned_rewards_if_active<F, TP>(

        thread_pool_builder: F,

        F: FnOnce() -> TP,

    {

            let (stake_rewards, partition_indices) =

            self.set_epoch_reward_status_distribution(
                epoch_rewards_sysvar.distribution_starting_block_height,
                stake_rewards,
                partition_indices,
            );
        }
    }

    /// Returns a vector of partitioned stake rewards. StakeRewards are
    /// recalculated from an active EpochRewards sysvar, vote accounts from
    /// EpochStakes, and stake accounts from StakesCache.
    fn recalculate_stake_rewards(
        &self,
        epoch_rewards_sysvar: &EpochRewards,
        thread_pool: &ThreadPool,
    ) -> (Arc<PartitionedStakeRewards>, Vec<Vec<usize>>) {
        assert!(epoch_rewards_sysvar.active);
        // If rewards are active, the rewarded epoch is always the immediately
        // preceding epoch.
        let rewarded_epoch = self.epoch().saturating_sub(1);

        let point_value = PointValue {
            rewards: epoch_rewards_sysvar.total_rewards,
            points: epoch_rewards_sysvar.total_points,
        };

        let stakes = self.stakes_cache.stakes();
        let EpochRewardCalculateParamInfo {
            stake_history,
            stake_delegations,
            cached_vote_accounts,
        } = self.get_epoch_params_for_recalculation(rewarded_epoch, &stakes);
        let ag_epoch_type = AlpenglowEpochType::get(self, rewarded_epoch, || {
            RewardEpochDelegatedStakes::get(self)
        });

        // On recalculation, only the `StakeRewardCalculation::stake_rewards`
        // field is relevant. It is assumed that reward commission accounts have
        // already been calculated and delivered, while
        // `StakeRewardCalculation::total_rewards` only reflects rewards that
        // have not yet been distributed.
        //
        // NOTE: the `RewardCommissionAccounts` will NOT have a correct
        // post_lamport amount if the commission account is NOT the vote account,
        // because the commission account is loaded from the current bank, and
        // not the start of the epoch. We don't have a snapshot of all commission
        // accounts from the start of the epoch. For this reason, the
        // `RewardCommissionAccounts` calculated in this function call should
        // NOT be used ever.
        let (_, StakeRewardCalculation { stake_rewards, .. }) = self
            .calculate_stake_rewards_and_commissions(
                &stake_history,
                stake_delegations,
                cached_vote_accounts,
                rewarded_epoch,
                point_value,
                &ag_epoch_type,
                thread_pool,
                null_tracer(),
                &mut RewardsMetrics::default(), // This is required, but not reporting anything at the moment
            );
        drop(stakes);
        let partition_indices = hash_rewards_into_partitions(
            &stake_rewards,
            &epoch_rewards_sysvar.parent_blockhash,
            epoch_rewards_sysvar.num_partitions as usize,
        );
        (stake_rewards, partition_indices)
    }

    fn initialize_after_snapshot_restore<F, TP>(&mut self, rewards_thread_pool_builder: F)
    where
        F: FnOnce() -> TP,
        TP: std::borrow::Borrow<ThreadPool>,
    {
        self.transaction_processor =
            TransactionBatchProcessor::new_uninitialized(self.slot, self.epoch);

                .set_execution_cost(compute_budget.to_cost());

        self.stakes_cache.refresh_delegated_stakes(

            self.use_fixed_point_stake_math(),
        );

        self.recalculate_partitioned_rewards_if_active(rewards_thread_pool_builder);

        self.transaction_processor
            .fill_missing_sysvar_cache_entries(self);

pub(crate) fn delegation_effective_stake<T: StakeHistoryGetEntry>(
