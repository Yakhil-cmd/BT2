### Title
Asset "friendly name" registered via `asset_metadata` is not globally unique and can be spoofed by any address, enabling GALA-style "false top-up" confusion between a legitimate asset and a look-alike asset - ([File: wallet.js])

### Summary
The Gala Games incident relied on the coexistence of two on-chain tokens that shared the same human-readable symbol (`GALA`) but had different underlying contract addresses; an exchange that identified deposits by the display symbol rather than the canonical contract address credited a worthless "old GALA" deposit as the real, currently-traded token. Obyte/ocore has a structurally analogous surface: the protocol's canonical, immutable asset identifier is the defining unit's hash (`payload.asset` = unit hash), but a separate, informal "friendly name" for the asset is published and cached via the `asset_metadata` mechanism [1](#0-0) . This name is not globally unique — it is only unique per `(name, registry_address)` pair — and any unprivileged address can act as a self-declared "registry" for any asset it likes.

### Finding Description
Asset metadata is populated from a plain `data` message posted by any address; the wallet code only checks that the message's author matches the `registry_address` the requester already believed in, not that the `registry_address`/name pair is authoritative or unique across the whole registry namespace: [2](#0-1) 

`fetchAssetMetadata` accepts a `name` field for an asset id and stores it keyed by `(asset, registry_address)`. Because `UNIQUE byNameRegistry(name, registry_address)` only prevents the *same* registry from reusing a name, any number of distinct addresses can register metadata claiming the very same display name (`"GALA"`, `"USDT"`, etc.) for completely different, unrelated `asset` unit hashes: [1](#0-0) 

Since anyone can post an `asset` definition message with arbitrary `cap`/`is_transferrable`/etc. (asset definition validation imposes no privilege check, just structural rules) [3](#0-2) , an attacker can:
1. Define a brand-new, worthless asset A2 that looks superficially similar to a well-known asset A1 (e.g., same cap, same transferability flags).
2. Publish a `data` message (self-declared registry) naming A2 with the exact same display name as A1, e.g. `"GALA"`.
3. Send A2 to a downstream integrator (exchange, bot, custodial service) that displays/matches deposited assets by the `name` field returned from `readAssetMetadata`/`hub/get_asset_metadata` rather than by the canonical asset id (unit hash): [4](#0-3) [5](#0-4) 

If the receiving system's crediting logic keys off `name` (or off metadata without pinning a known-good `registry_address`), it will treat the deposit of the worthless look-alike asset A2 as if it were the legitimate, actively-traded asset A1 — the same confusion mechanism ("false top-up" via ambiguous token identity) exploited in the Gala Games incident, just realized through ocore's optional friendly-name layer instead of a re-deployed ERC-20 contract.

### Impact Explanation
Any wallet, hub-backed service, or exchange integration built on ocore that surfaces or matches deposited assets by the cached `name`/`suffix` metadata (a documented, intended feature of `asset_metadata`) rather than by the immutable asset unit hash can be tricked into crediting a victim's account for a decoy asset while believing it received the real one. This is a concrete path to unauthorized crediting / fund loss for any operator relying on this convenience field, matching the Medium-severity "false top-up" bug class from the report.

### Likelihood Explanation
Reachable by a fully unprivileged unit poster: defining a new asset requires no special permission beyond single-authorship [6](#0-5) , and registering a display name for it as a self-declared registry requires only posting a `data` message, which any address can do at any time [2](#0-1) . No hub/witness/AA cooperation or special key is needed.

### Recommendation
- Never rely on `asset_metadata.name`/`suffix` alone for identity or crediting decisions; always key operational/financial logic on the canonical asset id (unit hash).
- When displaying or accepting a name-based match, require pinning to a specific, pre-vetted `registry_address` rather than accepting any self-declared registry, and clearly surface `registry_address`/`suffix` to end users so colliding names are distinguishable.
- Consider enforcing global uniqueness of `name` (not just per-registry) or, at minimum, flag/warn when multiple registries claim the same name for different asset ids.

### Proof of Concept
1. Attacker posts an `asset` definition unit A2 with parameters mimicking a target asset A1 (same `cap`, `is_transferrable`, etc.) — accepted by `validateAssetDefinition` with no privilege check.
2. Attacker posts a `data` message from address `R` with payload `{asset: A2, name: "GALA", decimals: 5}`; because `R` is also the message author, `fetchAssetMetadata`'s consistency check (`objJoint.unit.authors[0].address !== registry_address`) passes trivially [7](#0-6) .
3. This is stored in `asset_metadata` keyed by `(A2, R)`, coexisting with a legitimate `(A1, R_legit)` entry for a different but identically-named `"GALA"` asset, since the uniqueness constraint is per-registry, not global [1](#0-0) .
4. Attacker sends A2 tokens to a service that looks up `readAssetMetadata`/`hub/get_asset_metadata` by asset id and displays/credits based on the returned `name` field without verifying `registry_address` against a trusted allow-list, causing the service to treat the worthless A2 deposit as the real "GALA" (A1), enabling withdrawal of real funds — mirroring the reported incident.

CREATE TABLE asset_metadata (
	asset CHAR(44) CHARACTER SET latin1 COLLATE latin1_bin NOT NULL PRIMARY KEY,
	metadata_unit CHAR(44) CHARACTER SET latin1 COLLATE latin1_bin NOT NULL,
	registry_address CHAR(32) NULL,
	suffix VARCHAR(20) NULL, -- added only if the same name is registered by different registries for different assets, equal to registry name
	name VARCHAR(20) NULL,
	decimals TINYINT NULL,
	creation_date TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
	UNIQUE byNameRegistry(name, registry_address),
	FOREIGN KEY (asset) REFERENCES assets(unit),
	FOREIGN KEY (metadata_unit) REFERENCES units(unit)
