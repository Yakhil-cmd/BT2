### Title
Commit author spoofing via forged `Merge-Requested-By:` trailer in synced commit messages - (File: app/models/shipit/user.rb)

### Summary
`Shipit::User.find_or_create_author_from_github_commit` trusts a `Merge-Requested-By: <login>` line inside the raw commit message to determine `Commit#author`, instead of relying on `github_commit.author`/`github_commit.commit.author`. Since any commit reaching a tracked branch is synced through `PushHandler` → `GithubSyncJob` → `Commit.from_github` with no validation that the trailer was written by Shipit itself, an attacker can plant this trailer in a commit message and have Shipit misattribute authorship to an arbitrary victim GitHub login once that commit lands on the tracked branch.

### Finding Description
The broken binding is: `Shipit::Commit#author.login == (the GitHub identity that actually authored/pushed the commit)`. In practice, `Commit#author` is set from whatever `find_or_create_author_from_github_commit` returns [3](#0-2) , and that method prioritizes a regex match on the free-text commit message over the actual GitHub author metadata:

```ruby
def self.find_or_create_author_from_github_commit(github_commit)
  if (match_info = github_commit.commit.message.match(/^#{MergeRequest::MERGE_REQUEST_FIELD}: ([\w\-.]+)$/))
    begin
      return find_or_create_by_login!(match_info[1])
    rescue Octokit::NotFound
    end
  end
  find_or_create_from_github(github_commit.author.presence || github_commit.commit.author.presence)
end
``` [4](#0-3) 

`MERGE_REQUEST_FIELD` (`Merge-Requested-By`) is intended to be written only by Shipit's own merge-queue flow, via `MergeRequest#merge_message`, when a Shipit user requests a merge through the app's merge queue [5](#0-4) . However, nothing enforces that this string only ever originates from Shipit — it is a literal substring of the commit message that GitHub stores verbatim, and Git commit messages are entirely attacker-controlled.

Exploit flow:
1. An unprivileged attacker forks the repo and opens a PR containing a commit whose message body includes a line exactly matching `Merge-Requested-By: <victim-login>` (e.g., a trusted maintainer's login), disguised within an otherwise innocuous-looking commit message.
2. A maintainer reviews and merges the PR normally (via GitHub's merge/rebase, preserving the original commit message) — this is an ordinary, expected maintainer action, not a bypass of any Shipit guard.
3. GitHub emits a `push` webhook for the target branch. `PushHandler` matches the tracked stack by `branch` and enqueues `GithubSyncJob` [1](#0-0) .
4. `GithubSyncJob#perform` fetches the new commit(s) and calls `stack.commits.create_from_github!(gh_commit)` [6](#0-5) .
5. `Commit.from_github` calls `find_or_create_author_from_github_commit`, which matches the forged trailer and calls `find_or_create_by_login!("<victim-login>")`, setting `Commit#author` to the victim regardless of the true committer/pusher identity in `github_commit.author`.

No existing guard intercepts this: webhook signature verification (`verify_signature`) only authenticates that the payload came from GitHub for the given repository — it does nothing to validate the *content* of a commit message inside that payload. There is no server-side check anywhere in the sync path that the `Merge-Requested-By` trailer was actually produced by `MergeRequest#merge!`/`merge_message`, and the existing test `self.find_or_create_author_from_github_commit handles missing users on github` in `test/models/users_test.rb` demonstrates the exact mechanism operates on arbitrary attacker-supplied message text [7](#0-6) .

### Impact Explanation
This breaks the deploy audit trail: `TaskCommands#env` derives `SHIPIT_USER`/`SHIPIT_EMAIL` from `@task.author`, and commit authorship feeds into UI/audit displays and potentially author-based logic elsewhere in the app. An attacker can make it appear that a trusted maintainer authored a malicious or unwanted commit that later gets deployed, undermining accountability for "who wrote this code" — a Critical-category identity-spoofing impact in the deploy audit trail as scoped by the question. The attack is repeatable against any tracked stack/repository the attacker can get a PR merged into, and does not require any Shipit credentials, only that their PR (with the crafted message) is merged upstream through the normal contribution flow.

### Likelihood Explanation
Preconditions: the attacker needs their commit message (containing the trailer) to survive into the tracked branch's history unmodified — this happens whenever a maintainer merges via merge-commit or rebase-merge (which preserve original commit messages); it would be defeated only if the repo enforces squash-merge with edited messages. No Shipit secrets, API tokens, or team membership are required. The cost is trivial (a single crafted commit message); the only "gate" is a maintainer's ordinary merge action, which is a routine, expected event in any active repository, making this readily repeatable.

### Recommendation
Remove or restrict the message-based trailer mechanism as an authorship signal from arbitrary GitHub-sourced commits: only trust `Merge-Requested-By` when Shipit is the entity that produced the merge (e.g., verify the commit was created by `MergeRequest#merge!` and matches the stored `merge_requested_by` on the corresponding `MergeRequest` record) rather than re-parsing free-text commit messages ingested from any push.

    def perform(params)
      @stack = Stack.find(params[:stack_id])
      expected_head_sha = params[:expected_head_sha]
      retry_count = params[:retry_count] || 0
      head_before_sync = spec_cache_target
      appended_commits = []

      handle_github_errors do
        new_commits, shared_parent = fetch_missing_commits { stack.github_commits }

        # Retry on Github eventual consistency: webhook indicated new commits but we found none
        if expected_head_sha && new_commits.empty? && !commit_exists?(expected_head_sha) &&
           retry_count < MAX_RETRY_ATTEMPTS
          GithubSyncJob.set(wait: RETRY_DELAY * retry_count).perform_later(params.merge(retry_count: retry_count + 1))
          return
        end

        stack.transaction do
          shared_parent&.detach_children!
          appended_commits = new_commits.map do |gh_commit|
            append_commit(gh_commit)
          end
          stack.lock_reverted_commits! if appended_commits.any?(&:revert?)
        end
      end
      sync_changed_nothing = appended_commits.empty? &&
                             spec_cache_target == head_before_sync &&
                             stack.cached_deploy_spec.present?
      return if sync_changed_nothing && !params[:force_spec_cache]

      CacheDeploySpecJob.perform_later(stack)
    end

    def append_commit(gh_commit)
      stack.commits.create_from_github!(gh_commit)
    end
