### Title
Webhook GitHub App selection for signature verification is derived from the unverified payload, decoupling the authenticating organization from the repository/stack that gets written - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks which `GitHubApp` (and therefore which `webhook_secret`) to use for HMAC verification based on a value read directly out of the still-unauthenticated JSON body, not out of any cryptographically-bound field. Everything downstream (`Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`) then acts on the *same* attacker-supplied `params` hash, including whichever repository/stack fields the handler uses to decide what to create, update, or sync. There is no check anywhere in this flow that the organization whose secret validated the signature is the same organization/repository that the handler subsequently mutates.

### Finding Description
`before_action :check_if_ping, :drop_unhandled_event, :verify_signature` runs `verify_signature` before the body has been authenticated in any way: [1](#0-0) 

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
end
```

`repository_owner` is computed purely from the JSON body the attacker controls: [2](#0-1) 

```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

So the *choice of which secret to check the signature against* is itself derived from unauthenticated attacker input, not from something Shipit already trusts (e.g. a URL path scoped to a specific stack/org, or a value it independently looks up). `GitHubApp#verify_webhook_signature` also trivially returns `true` when no `webhook_secret` is configured for that organization: [3](#0-2) 

Once `verify_signature` passes (because the attacker picked an organization/App config whose secret they know, or one with no secret configured at all), the controller hands the *entire* raw `params` — including any other embedded `repository`/`full_name`/`organization` fields — to the registered handlers: [4](#0-3) 

Nothing re-derives or re-checks that the repository the handler subsequently reads/writes (to locate a `Stack`, create `Commit`/`Status` records, enqueue `GithubSyncJob`, etc.) is the same repository/organization whose `webhook_secret` was used to authenticate the request. This is the exact binding break called out in the analog rules: **the organization that authenticated the webhook is not provably the same as the repository/stack that ends up being written.**

### Impact Explanation
An attacker with control over a GitHub App/webhook integration for *any* organization known to Shipit's `secrets.github` (or any organization for which no `webhook_secret` is configured) can craft a payload where the "authenticating" fields (used only to pick which secret is checked) point at their own org, while other repository-identifying fields in the same JSON body point at a victim stack. Since handlers act on the full unrestricted `params`, this allows forged webhook events (pushes, statuses, check_suite, membership, etc.) to be attributed to and processed against a repository/stack the attacker does not control — i.e., a cross-repository write driven by a signature that was never actually validated against that repository's own secret. This satisfies the "cross-repository writes" high/critical impact bar.

### Likelihood Explanation
Exploiting this only requires the attacker to control (or already have credentials for) at least one GitHub App/organization configured in the same Shipit instance's `secrets.github`, or to target an organization that has no `webhook_secret` configured (in which case `verify_webhook_signature` returns `true` unconditionally). No repository write access, session, or `ApiClient` token is required — only the ability to send an HTTP POST to the public `/webhooks` endpoint with a crafted body, which is by design unauthenticated until `verify_signature` runs.

### Recommendation
Do not select the verification secret from unauthenticated fields of the payload. Bind the endpoint (or verification) to a specific, previously-established organization/installation identity (e.g. use the GitHub App installation ID from the verified webhook delivery, or scope the route per-organization) and, after signature verification, re-validate that every repository/stack the handler subsequently touches actually belongs to the organization that produced a valid signature, rejecting or ignoring events with inconsistent repository/organization data.

### Proof of Concept
1. Attacker owns/controls a GitHub App entry configured under `secrets.github` for org `attacker-org` (or targets an org with no `webhook_secret` set).
2. Attacker crafts a JSON payload for a handled event (e.g. `push`) with:
   - `repository.owner.login = "attacker-org"` (or an org with a blank `webhook_secret`)
   - Other repository-identifying fields used later by the event handler (e.g. `repository.full_name`, `repository.name`) set to `"victim-org/victim-repo"`.
3. Attacker computes/obtains a valid `X-Hub-Signature` for `attacker-org`'s (possibly blank) `webhook_secret` and POSTs to `/webhooks` with `X-Github-Event: push`.
4. `verify_signature` calls `Shipit.github(organization: "attacker-org")` and succeeds (real secret match, or automatic `true` for blank secret).
5. `Shipit::Webhooks.for_event('push')` handlers then execute using the full `params`, operating against whatever stack/repository the handler resolves from `repository.full_name`/`repository.name` — i.e., `victim-org/victim-repo` — even though that repository's own webhook secret was never checked.

*Caveat: I was unable to inspect the concrete handler implementations under `lib/shipit/webhooks/**` (the directory returned empty in this session) to confirm exactly which field each individual handler (push/status/check_suite/etc.) uses to resolve the target `Stack`. The controller-level binding break (`verify_signature` keying off unauthenticated payload data, followed by unrestricted handler execution over the same payload) is confirmed directly from `app/controllers/shipit/webhooks_controller.rb` and `lib/shipit/github_app.rb`, but full end-to-end confirmation of the downstream write path would benefit from reviewing the handler classes directly — a Devin session with full repository access could verify this quickly.*

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
