### Title
Unscoped `Commit.where(sha:)` lookup in `StatusHandler#process` lets a status webhook from one repository mutate commit status on another repository's stack - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits purely by `sha`, with no scoping to the repository/stack that actually sent the webhook, unlike every other handler which uses the base `Handler#stacks` helper (`Repository.from_github_repo_name(repository_name)`). Since two different Shipit-registered repositories can legitimately share a commit sha (e.g. forks sharing ancestor history, or any repo containing byte-identical commit content), a validly-signed status webhook from an attacker-controlled repository can create/replace a `Status` on a `Commit` row that belongs to a victim's stack, which feeds directly into `Stack#next_expected_commit_to_deploy` and `UndeployedCommit#expected_to_be_deployed?` and can trigger `ContinuousDeliveryJob`.

### Finding Description
The claimed binding is: `payload.dig('repository','full_name')` (the repository the signature in `verify_signature` was checked against, and that the attacker legitimately controls) == `commit.stack.repository` for every `Commit` mutated by the handler. Tracing the code shows this equality does **not** hold:

- `WebhooksController#verify_signature` (app/controllers/shipit/webhooks_controller.rb:24-49) verifies the HMAC signature using `Shipit.github(organization: repository_owner)`, where `repository_owner` is taken from the payload's own `repository.owner.login`. This only proves the webhook genuinely came from GitHub for the org/repo named in the payload — it says nothing about which `Commit` rows in Shipit's DB should be affected.
- The base `Handler` class provides a `stacks` helper that correctly scopes to the sending repository: `Repository.from_github_repo_name(repository_name)&.stacks` (app/models/shipit/webhooks/handlers/handler.rb:32-38), where `repository_name` comes from the same payload. Other handlers use this to restrict effects to the right repository.
- `StatusHandler#process` (app/models/shipit/webhooks/handlers/status_handler.rb:20-24) instead does:
```ruby
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
```
This ignores `stacks`/`repository_name` entirely and matches **any** `Commit` row across **any** stack/repository that has the same `sha`, then calls `commit.create_status_from_github!(params)` which writes a `Status` scoped to `commit.stack_id` (app/models/shipit/commit.rb:165-169), i.e. it writes into whichever stack that `Commit` row happens to belong to — not necessarily the sender's stack.
- `create_status_from_github!` → `add_status` recomputes `status`, and via `Commit#deployable?`/`schedule_continuous_delivery` (app/models/shipit/commit.rb:227-229, 281-287) can enqueue `ContinuousDeliveryJob`, and downstream `Stack#next_expected_commit_to_deploy` / `UndeployedCommit#expected_to_be_deployed?` (app/models/shipit/undeployed_commit.rb:47-53) will treat later victim commits as expected-to-deploy based on a status this handler wrote using attacker-controlled webhook content, for a commit the attacker's own CI never validated in the victim's repo context.

Exploit flow: attacker registers/administers a repository in Shipit (e.g. a fork of the victim's repo, or any repo whose history intersects the victim's, sharing at least one commit sha with the victim's undeployed commits — trivially true for forks, which share all ancestor SHAs). Attacker sets a commit status (via GitHub's Status API, a completely legitimate action on their own repo) on that shared sha. GitHub delivers a correctly-signed webhook naming the attacker's repository. `verify_signature` passes (it's genuinely from GitHub for the attacker's org). `StatusHandler#process` then updates the `Status` for **every** `Commit` record with that sha, including the one that belongs to the victim's stack, without ever checking `repository_name` against that commit's stack.

None of the existing guards catch this: `verify_signature` only authenticates "this payload really came from GitHub for org X," `drop_unhandled_event` only checks the event type is registered, and the `ExplicitParameters` schema only validates the shape of `sha`/`state`/etc. — none of them scope the DB write to the sending repository. This is exactly the class of guard the `stacks` helper exists for, and `StatusHandler` simply doesn't use it.

### Impact Explanation
A forged/attacker-triggered success status on a shared sha causes Shipit to write a `Status` row against a victim stack's `Commit`, altering `deployable?`/`status` for that commit and shifting `Stack#next_expected_commit_to_deploy`, which marks subsequent legitimate victim commits `expected_to_be_deployed? == true` even though the victim's own required CI never reported success on them. With `continuous_deployment` enabled, `ContinuousDeliveryJob` can act on this and deploy commits without the victim's actual CI signal — this is "a payload for one repository mutating another's stack, commit ... or an unauthorized deploy," matching the **Critical** severity category. The attack is repeatable against any victim repository that shares any commit sha with an attacker-administered repository (most commonly via forks, which is a broad and common configuration), and works per-sha/per-commit, so an attacker can chain multiple shared ancestor commits to walk the `next_expected_commit_to_deploy` pointer forward.

### Likelihood Explanation
Preconditions: (1) the victim stack has `continuous_deployment` enabled and multiple undeployed commits; (2) at least one commit sha is shared between the victim's stack and a repository the attacker administers (trivial for forks — all shared history has identical SHAs); (3) the attacker's repository/org is already integrated with Shipit's GitHub App so their own legitimately-signed status webhooks are delivered (this is the normal, unprivileged self-service flow of adding a stack for a repo you own/admin — no victim or operator secrets needed). Attacker cost is low: fork the victim repo (or otherwise produce a byte-identical commit), register it in Shipit, and set a commit status via the standard GitHub Status API on the shared sha. This is fully repeatable and requires no secrets, sessions, or elevated GitHub permissions on the victim's repository.

### Recommendation
Scope `StatusHandler#process` to the sending repository the same way other handlers do: use `stacks` (or otherwise join through `Repository.from_github_repo_name(payload.dig('repository','full_name'))`) and restrict the `Commit` lookup to `Commit.where(sha: params.sha, stack_id: stacks.ids)` (or iterate `stacks.flat_map { |s| s.commits.where(sha: params.sha) }`) before calling `create_status_from_github!`, so a status from repository A can never write into a `Commit` belonging to repository B's stack.

### Proof of Concept
Minitest plan (test/models/shipit/webhooks/handlers/status_handler_test.rb or similar), no live GitHub:

```ruby
test "a status webhook naming repository A must not mutate a commit belonging to repository B's stack, even if shas collide" do
  victim_stack = shipit_stacks(:shipit)
  attacker_repo_name = "attacker/attacker-repo"
  shared_sha = "deadbeef" * 5  # 40 hex chars

  victim_commit = victim_stack.commits.create!(sha: shared_sha, message: "victim commit")

  # Binding under test (BEFORE):
  # payload.repository.full_name == "attacker/attacker-repo"  (attacker's own repo)
  # victim_commit.stack.repository.full_name == victim repo (different repo)
  # => these must be different, and no status should exist yet
  assert_nil victim_commit.reload.statuses.last

  payload = {
    'repository' => { 'full_name' => attacker_repo_name, 'owner' => { 'login' => 'attacker' } },
    'sha' => shared_sha,
    'state' => 'success',
    'context' => 'ci/attacker',
  }

  Shipit::Webhooks::Handlers::StatusHandler.call(payload)

  # Binding under test (AFTER): the write must not have crossed into victim_commit's stack.
  assert_nil victim_commit.reload.statuses.last,
    "expected no status written to victim's commit from a webhook naming a different repository"
end
```

A second test should assert the corollary against `UndeployedCommit#expected_to_be_deployed?`: build an `undeployed_commits` list for the victim stack with `continuous_deployment: true`, call `StatusHandler.call(payload)` with the attacker's repository name and the shared sha, then assert that `expected_to_be_deployed?` flips to `true` for a later victim commit despite the victim's own CI never having posted a success status — demonstrating the ordering/gating bypass described in the question.
