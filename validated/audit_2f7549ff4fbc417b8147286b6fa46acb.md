### Title
`OpenedHandler#provision?` operator-precedence bug lets `prevent_with_label` PRs provision review stacks even when `review_stacks_enabled` is `false` - ([File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb])

### Summary
`OpenedHandler#provision?` combines its clauses with `&&`/`||` without parentheses grouping the `review_stacks_enabled` check across all three provisioning-behavior branches. Because `&&` binds tighter than `||` in Ruby, the `prevent_with_label` clause `(repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)` is evaluated independently of `repository.review_stacks_enabled`, so an attacker opening an unlabeled PR against a repo configured with `provisioning_behavior: prevent_with_label` can trigger `ReviewStackAdapter#create!` even when `review_stacks_enabled` is `false`.

### Finding Description
The intended binding is: `provision? == true` only when `repository.review_stacks_enabled == true` AND one of the behavior clauses matches. The actual code is: [1](#0-0) 

```ruby
def provision?
  repository.review_stacks_enabled &&
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
```

Ruby's `&&` has higher precedence than `||`, so this parses as:

```
(review_stacks_enabled && allow_all?) ||
(allow_with_label? && has_label?) ||
(prevent_with_label? && !has_label?)
```

`review_stacks_enabled` is ANDed only into the first disjunct (`allow_all?`). The second and third disjuncts (`allow_with_label?` and `prevent_with_label?`) are entirely independent of `review_stacks_enabled`. Given the equality `repository.review_stacks_enabled == false` and `repository.provisioning_behavior == "prevent_with_label"`, and a PR opened with no matching label, evaluate the third term: `prevent_with_label? (true) && !has_label? (true) == true`. The whole `provision?` expression therefore returns `true` despite `review_stacks_enabled == false` — the two sides of the intended binding diverge.

Reachable path: `params.action == "opened"` is attacker-controlled via a normal GitHub `pull_request` `opened` webhook payload (repository owner/maintainer can configure `provisioning_behavior` to `prevent_with_label` while leaving `review_stacks_enabled` off; this is a plausible/legal configuration state since the two fields are independent enum/boolean columns with no model validation tying them together — no `validates` cross-field check exists in `Shipit::Repository`). `respond_to_pull_request_opened?` calls `provision?`, which returns `true`, and `process` calls: [2](#0-1) 

This invokes `ReviewStackAdapter#find_or_create!` → `create!`, which persists a new `Shipit::ReviewStack` record from attacker-supplied `params.pull_request.head.ref` and enqueues it via `Shipit::ReviewStackProvisioningQueue.add(stack)`: [3](#0-2) 

Provisioning queue processing subsequently runs the deploy-spec/provisioning tasks against the attacker's branch, which is the standard review-stack RCE surface (arbitrary `shipit.yml` steps executed via `Command`/`PTY.spawn`) — this part of the pipeline is outside `OpenedHandler` but is the documented consequence of a stack being created and queued for provisioning.

None of the listed guards intercept this: `verify_signature`/webhook signature verification only authenticates that the payload came from GitHub for *some* repository the attacker can trigger (via their own fork/PR), not that provisioning is authorized; `ExplicitParameters` schema only validates payload shape; there is no `require_permission!`/`User#authorized?` check in this webhook-driven flow; and no model validation in `Shipit::Repository` enforces `review_stacks_enabled == true` whenever `provisioning_behavior` is set to `prevent_with_label`.

### Impact Explanation
An attacker who can open a PR (fork PR or PR from a branch on a repo already onboarded to Shipit with `provisioning_behavior = prevent_with_label`) causes a `Shipit::ReviewStack` (and associated `Shipit::PullRequest`) to be created and queued for provisioning even though the operator explicitly disabled review stacks (`review_stacks_enabled = false`). This is a write to a persistent record and an unauthorized triggering of the provisioning pipeline that the `review_stacks_enabled` flag is supposed to gate off entirely — matching "a command running that should not, a record written for a repository that did not authenticate it" and the Critical category (unauthorized provisioning/deploy pipeline execution leading toward RCE via attacker-controlled `shipit.yml`/branch content once provisioning tasks run). It is repeatable for any repository matching this specific configuration (`review_stacks_enabled: false`, `provisioning_behavior: prevent_with_label`) and repeatable per PR/branch name (`environment: "pr#{number}"`), but it is scoped only to repositories with that specific configuration combination — it does not cross-contaminate unrelated repositories' stacks.

### Likelihood Explanation
Preconditions: the target repository must have `review_stacks_enabled: false` combined with `provisioning_behavior: prevent_with_label`. This is an unusual but not prevented configuration — the two settings are independent database columns/enum with no cross-field validation, so it can arise e.g. when an operator toggles `review_stacks_enabled` off after having set the behavior, or misconfigures it during setup. Attacker cost is trivial: open a PR with no matching provisioning label against such a repo. No secrets, sessions, or elevated GitHub permissions are required — any GitHub user able to open a PR (including via a fork) triggers this. The bug is 100% deterministic given the configuration and is fully repeatable.

### Recommendation
Add explicit parentheses so `review_stacks_enabled` gates all three disjuncts:

```ruby
def provision?
  repository.review_stacks_enabled &&
    (repository.provisioning_behavior_allow_all? ||
     (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
     (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?))
end
```

### Proof of Concept
Minitest plan (in `test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb`, using the existing `configure_provisioning_behavior` helper):

```ruby
test "does not create stacks when review_stacks_enabled is false, even with prevent_with_label and no label" do
  repository = shipit_repositories(:shipit)
  configure_provisioning_behavior(
    repository:,
    provisioning_enabled: false,      # review_stacks_enabled = false
    behavior: :prevent_with_label,
    label: "pull-requests-label"
  )
  payload = payload_parsed(:pull_request_opened)
  payload["pull_request"]["labels"] = []   # no label present

  assert_no_difference -> { Shipit::Stack.count } do
    OpenedHandler.new(payload).process
  end
end
```

Assert both sides of the binding: `repository.review_stacks_enabled == false` (set explicitly) vs. observed effect `Shipit::Stack.count` unchanged (expected) — running this test against current code demonstrates the assertion fails (a stack IS created), proving `provision?` returns `true` when it should return `false`.
