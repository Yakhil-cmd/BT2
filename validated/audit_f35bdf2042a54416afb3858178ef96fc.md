### Title
Cross-organization webhook forgery via mismatched `repository.owner.login`/`organization.login` (used for signature verification) vs `repository.full_name` (used to locate the target Stack) - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to verify a request against using `repository_owner`, which is read from the same untrusted JSON body it is about to validate: `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`. Once the HMAC check passes, `create` hands the *entire* raw payload to `Shipit::Webhooks.for_event(event)` handlers, which locate the target `Repository`/`Stack` using a different field of the same payload: `payload.dig('repository', 'full_name')` (`app/models/shipit/webhooks/handlers/handler.rb:36-38`, also used directly by handlers such as `PullRequest::OpenedHandler#repository`). Nothing enforces that `repository.owner.login` and `repository.full_name`'s owner segment refer to the same organization, so a party who legitimately controls one organization's webhook secret (e.g., an org admin/maintainer for whom the Shipit GitHub App is installed) can sign a payload whose `owner.login`/`organization.login` matches their own org (so it authenticates), while `repository.full_name` names a completely different, victim organization's repository that Shipit tracks.

### Finding Description
`verify_signature` in `app/controllers/shipit/webhooks_controller.rb:24-49` does:
```ruby
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
```
`GitHubApp#verify_webhook_signature` (`lib/shipit/github_app.rb:76-83`) performs a standard HMAC-SHA1 comparison of the *raw body* against the secret configured for `repository_owner`'s organization (`Shipit.github_app_config`, `lib/shipit.rb:196-200`). This proves only that the sender knows the webhook secret for whichever organization `repository_owner` names — it says nothing about which repository the payload's business fields describe.

`repository_owner` itself is derived from the payload under verification:
```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```
Once `verified` is true, `create` dispatches the untouched `params` to every registered handler for the event (`app/controllers/shipit/webhooks_controller.rb:10-15`). Handlers resolve the affected `Repository`/`Stack` from a *different* field:
```ruby
def repository_name
  payload.dig('repository', 'full_name')
end
```
(`app/models/shipit/webhooks/handlers/handler.rb:36-38`), and specific handlers (e.g. `PullRequest::OpenedHandler#repository`, `app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb:50-54`) do the same via `params.repository.full_name`.

The binding being broken is: *the organization whose secret authenticated the request* (`repository.owner.login` / `organization.login`) **≠** *the repository whose Stack is actually written to* (`repository.full_name`). Both values live in the same attacker-controllable JSON body; the signature covers the raw bytes of that body as a whole but the controller never checks that these two fields are mutually consistent before trusting `full_name` in the write path.

### Impact Explanation
An entity that controls a webhook secret for organization A (a normal, lower-trust position: e.g. any org where the Shipit GitHub App/webhook is installed, or anyone able to trigger a legitimately signed delivery for org A) can construct a request that:
- Sets `organization.login` / `repository.owner.login` to `"org-a"` so `verify_signature` fetches and validates against org A's real secret and passes.
- Sets `repository.full_name` to `"org-b/victim-repo"`, an unrelated tracked repository belonging to a different, victim organization/GitHub App boundary.

This drives handlers such as pull-request/push/commit-status/membership handlers to mutate state (create review stacks, alter commit status, add/remove team members, trigger merge/deploy-adjacent bookkeeping) on `org-b`'s Stack, i.e., a cross-organization write that should require org B's own webhook secret. This matches the "unauthorized... cross-repository writes" impact category (an organization that authenticated versus the repository that is written).

### Likelihood Explanation
Exploitation requires possession of a valid webhook secret for at least one organization connected to the Shipit instance — a bar far lower than compromising the target organization or its GitHub App installation. Any multi-tenant Shipit deployment configuring more than one `github.<org>` app config (`lib/shipit.rb:190-200`, `docs/setup.md`) is exposed. The request itself is a normal unauthenticated HTTP POST to `/webhooks` with a correctly-signed body — no session, API token, or GitHub write access to the victim repo is needed.

### Recommendation
Do not use payload-derived fields to select the verification key without also enforcing that the same fields the handlers use to route/mutate state are consistent with it. Concretely, after verifying the signature, assert that `repository.full_name`'s owner segment equals the `repository_owner`/`organization.login` used to select the webhook secret, and reject (422) on mismatch. Alternatively, resolve the target repository/stack using the same authenticated owner value the signature was checked against rather than trusting `full_name` independently.

### Proof of Concept
1. Configure two organizations in `secrets.github`, `org-a` and `org-b`, each with a distinct `webhook_secret`, per `lib/shipit.rb:170-200`. Org B tracks a repository `org-b/victim-repo` with an existing Stack.
2. As a party who legitimately knows/controls org A's webhook secret (e.g., an org-A maintainer with the Shipit GitHub App installed there), craft a `pull_request` (or similar) webhook JSON body where:
   - `organization.login` = `"org-a"` and `repository.owner.login` = `"org-a"`
   - `repository.full_name` = `"org-b/victim-repo"`
3. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(org-a's webhook_secret, raw_body)>` and POST to the Shipit `/webhooks` endpoint with `X-Github-Event: pull_request`.
4. `WebhooksController#verify_signature` fetches org A's `GitHubApp`, verifies the HMAC over the body, and passes (`app/controllers/shipit/webhooks_controller.rb:24-38`).
5. `create` dispatches to `Shipit::Webhooks::Handlers::PullRequest::OpenedHandler`, which resolves `Shipit::Repository.from_github_repo_name("org-b/victim-repo")` (`app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb:50-54`) and provisions/mutates a review stack on org B's repository — a write performed under authentication that only proved control of org A's secret.     def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
