### Title
Premature chained division in liquidation's bad-debt-socialization trigger can prematurely socialize debt onto vault suppliers - (File: `local-testing/contracts/market/market.clar` / `mainnet/contracts/market/v0-4-market.clar`, function `liquidate`)

### Summary
The `liquidate` function decides whether to trigger bad-debt socialization (`no-collateral-left`) based on `other-debt-repayable`, a value computed through four sequential, independently-truncating division steps instead of a single fused fraction. This is the same "divide-then-multiply, repeatedly" pattern flagged in the external report (`GaugeController::_calculateReward`), except here the truncated result gates a state transition that writes down vault assets for every depositor in the affected vault, not just the liquidator's own payout.

### Finding Description
In `liquidate`, once the targeted collateral asset is (partially) seized, the contract must decide if the borrower's *other* collateral (in a different asset) could still cover the remaining debt. This is computed as: [1](#0-0) 

```
(other-coll-usd (if (> total-collateral-usd target-coll-full-usd) (- total-collateral-usd target-coll-full-usd) u0))
(other-debt-repayable
  (if (> other-coll-usd u0)
    (let ((other-adj (div-bps-down other-coll-usd (+ BPS liq-penalty-max)))
          (other-tokens (mul-div-down other-adj (pow u10 debt-decimals) debt-price))
          (other-borrow-idx (get index (unwrap-panic (get-cached-indexes debt-aid))))
          (other-scaled (mul-div-down other-tokens INDEX-PRECISION other-borrow-idx)))
      (mul-div-up other-scaled other-borrow-idx INDEX-PRECISION))
    u0))
```

This chains three floor-divisions (`div-bps-down`, then two `mul-div-down`) before a single ceiling correction (`mul-div-up`), exactly mirroring the reported anti-pattern of computing intermediate ratios (`gaugeShare`, `typeShare`) and truncating each before the final multiplication. Each intermediate floor operation discards fractional value that a single combined `(A*B*D)/(C*E)` computation would have preserved, so `other-debt-repayable` can be truncated to `u0` even when the borrower's remaining collateral, evaluated without intermediate truncation, would still be worth a non-zero amount of repayable debt.

`other-debt-repayable` directly controls `no-collateral-left`: [2](#0-1) 

which, when true, triggers `socialize-debt-asset` over the borrower's remaining debt list, calling `vault-socialize-debt` and writing down the vault's `lindex`/`assets`/`total-borrowed` state that is shared by every LP in the vault: [3](#0-2) [4](#0-3) 

`vault-socialize-debt`'s `new-lindex` write-down is shared state consumed by every LP's `convert-to-assets`, so a premature (incorrectly triggered) socialization directly reduces the redeemable value for depositors who did not participate in or cause the liquidation.

### Impact Explanation
The attacker here is any liquidator (unprivileged principal) calling `liquidate`. The victims are the vault's LP depositors (a different, unprivileged set of principals) whose shared `lindex`/`assets` state is written down. Without the bug, the borrower's remaining collateral value in the other asset would (mathematically) still be enough to be recorded as recoverable, and `no-collateral-left` should remain `false`, leaving debt on the books to be recovered by a later liquidation of the other collateral asset. With the chained-division truncation flipping `other-debt-repayable` to `u0`, the position's remaining debt is written off via `socialize-debt-asset` immediately, permanently transferring that shortfall onto the vault's LP suppliers — a loss they did not need to bear had the exact fraction been preserved. This is a socialization charged to all suppliers of the vault, landing on the "protocol insolvency / theft of user funds" impact category since real recoverable value is discarded and replaced by writing down every depositor's claim.

### Likelihood Explanation
This path executes on every partial liquidation where a borrower holds debt collateralized by more than one asset and the liquidated asset does not fully cover the max-debt-usd bound — a routine, permissionless liquidation flow, not requiring privileged access or unusual preconditions. The truncation is most impactful when the "other" collateral's USD value is close to (but should be above) the rounding boundary introduced by the extra division steps, which is a realistic dust/near-threshold scenario in live markets with volatile prices and small remaining balances.

### Recommendation
Combine the four-step computation of `other-debt-repayable` (and the structurally identical `remaining-debt-to-repay` block a few lines above it) into a single fused-fraction calculation that only rounds once (up, matching the "amount owed" rounding direction), e.g.:
```
other-debt-repayable = ceil( other-coll-usd * 10^debt-decimals * INDEX-PRECISION / ((BPS+liq-penalty-max) * debt-price * other-borrow-idx) ) * other-borrow-idx / INDEX-PRECISION
```
or restructure so only the final division rounds, consistent with the report's recommended fix of deferring all division until the last multiplication step.

### Proof of Concept
Because the exact truncation magnitude depends on live oracle prices/decimals/`borrow-idx`, exact reproduction requires a test harness with controlled fixture values (as in the original report's Hardhat test). Conceptually:
1. Set up a borrower with two collateral assets, A (being liquidated) and B (remaining).
2. Choose collateral B's USD value and `liq-penalty-max`/`debt-price`/`debt-decimals` such that the exact fraction `other-coll-usd * BPS * 10^debt-decimals / ((BPS+liq-penalty-max) * debt-price)` is a small positive non-integer (e.g., 0.6 scaled units) — i.e., mathematically representing recoverable debt.
3. Show that computing this via the contract's three chained `div-bps-down`/`mul-div-down` floor operations yields `0` at the intermediate `other-tokens`/`other-scaled` stage, causing `other-debt-repayable` to resolve to `u0`, versus a fused single-division computation that would round the same true value up to `1` (a non-zero repayable amount).
4. Confirm that with `other-debt-repayable = u0`, `no-collateral-left` becomes `true` and `socialize-debt-asset` is invoked, writing down the vault's `lindex`, whereas the mathematically correct (fused) computation should have left the debt outstanding for a subsequent liquidation instead of socializing it onto LPs.

I was not able to execute this against the live test suite in this session to produce concrete numeric deltas (analogous to the report's "3,474 token" figure); this should be validated with a Clarinet/Vitest simulation using the project's existing liquidation test fixtures before treating the magnitude as confirmed.
