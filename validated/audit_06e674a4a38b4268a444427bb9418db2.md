### Title
Cross-tenant status forgery via unscoped `Commit.where(sha:)` in `StatusHandler#process` — ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` looks up commits solely by SHA with no repository/stack scoping, unlike every other webhook handler which uses `Handler#stacks` (scoped via `Repository.from_github_repo_name(repository_name)`). Because `verify_signature` in `WebhooksController` validates the signature using the `webhook_secret` of the organization named in the *payload's own* `repository.owner.login`, an attacker who controls (or registers) any GitHub organization known to Shipit can send a validly-signed `status` webhook whose `sha` and `context` target a completely unrelated victim stack's commit, flipping that commit's status and unblocking `deployable?`/`schedule_merges`.

### Finding Description
The broken binding: `verify_signature` authenticates that "the payload's claimed `repository.owner.login` organization signed this request" — call this `signer_org == payload.repository.owner.login`. It does **not** and cannot bind "the mutated `Commit` row belongs to a stack owned by `signer_org`." Every other handler restores that missing binding by scoping lookups through `Handler#stacks`, which resolves `Repository.from_github_repo_name(repository_name)` — i.e., it only touches records belonging to the repository named in the very payload that was verified [1](#0-0) .

`StatusHandler#process`, by contrast, does:
```ruby
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
``` [2](#0-1) 

This query is global across all tenants/stacks — `params.sha` and `params.context` are attacker-supplied strings from the payload of the *signing* organization's webhook, but the `Commit` rows matched can belong to **any** stack in the Shipit instance, including ones owned by a completely different GitHub organization, as long as the SHA happens to match (SHAs are 40-hex public values visible on GitHub, and commits can collide across forks/mirrors, or an attacker can simply mirror/cherry-pick a victim's exact commit into their own throwaway repo to guarantee the SHA is known and even present in their own git history).

Exploit flow:
1. Attacker creates/controls org `attacker-org` in GitHub, and this org is configured in Shipit (or has no `webhook_secret` set, making `verify_webhook_signature` trivially return `true` per `GitHubApp#verify_webhook_signature` — `return true unless webhook_secret`) [3](#0-2) .
2. Attacker POSTs to `/webhooks` a `status` event with `repository.owner.login: "attacker-org"` (so `verify_signature` uses attacker's own — possibly absent — secret) [4](#0-3) , but with `sha` set to a victim commit's SHA and `context` matching the victim stack's configured blocking status check, `state: "success"`.
3. `WebhooksController#create` dispatches to `StatusHandler.call(params)` [5](#0-4) .
4. `StatusHandler#process` finds the victim's `Commit` row purely by `sha` match and calls `create_status_from_github!(params)` on it, with no check that this commit belongs to a stack under `attacker-org` [2](#0-1) .
5. This updates/creates a `Status` on the victim commit which can flip `simple_state` to `success`, and downstream logic in `Commit`/`Stack` (`add_status`, `schedule_merges`, `deployable?`) can now treat the victim commit as deployable/mergeable.

Existing guards fail here specifically because: `verify_signature` only proves who sent the request, not which records the payload is permitted to touch; and `Handler#stacks` — the mechanism that would normally re-establish that binding for every other handler — is not used by `StatusHandler` at all.

### Impact Explanation
An attacker-controlled organization can forge a passing (or failing) CI status for an arbitrary victim stack's commit purely by knowing its SHA (public on GitHub) and the blocking status context name (visible in the victim's public CI config/`shipit.yml`). If the status flip makes `deployable?` true, this can unblock `Deploy` creation or `Stack#schedule_merges`, i.e., an unauthorized deploy/merge on a tenant the attacker never authenticated against. This is a cross-tenant, payload-for-one-repository-mutates-another's-commit vulnerability — Critical severity per the stated impact categories (unauthorized deploy/merge, one repository's payload mutating another's stack/commit).

### Likelihood Explanation
Preconditions: attacker needs (a) any Shipit-registered GitHub org they control (trivial — self-serve GitHub org creation, or use of an org lacking `webhook_secret` per the sibling bypass finding), (b) a victim commit SHA (public), (c) a victim blocking-status context name (typically discoverable in public CI config). No Shipit session, API token, or GitHub App secret is required. This is fully repeatable against any stack/commit in the instance and does not require the attacker to compromise or spoof the victim's own webhook secret.

### Recommendation
Scope `StatusHandler#process` to only touch commits belonging to stacks associated with the repository named in the verified payload, matching the pattern used by all other handlers, e.g.:
```ruby
def process
  stacks.flat_map(&:commits).where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
or equivalently restrict via `Commit.where(sha: params.sha, stack_id: stacks.select(:id))`, using the existing `Handler#stacks` helper so the binding between the verifying organization/repository and the mutated record is restored.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb`):
1. Create `stack_a` under `repository_a` (owner `org-a`, no/placeholder `webhook_secret`) and `stack_b` under `repository_b` (owner `org-b`), each with its own `Commit` fixture sharing the identical `sha` value (simulate SHA collision/mirrored commit).
2. Configure `stack_b`'s blocking status context, e.g. `context: "ci/travis"`.
3. Build a `status` webhook payload with `repository.full_name` / `owner.login` set to `org-a`, `sha` equal to the shared SHA, `context: "ci/travis"`, `state: "success"`.
4. Call `Shipit::Webhooks::Handlers::StatusHandler.call(payload)` directly (bypassing HTTP signature layer, which is covered by the sibling bypass finding).
5. Assert:
   - Before: `stack_b.commits.find_by(sha: shared_sha).state` (or `simple_state`) is not `"success"`, and `stack_b.deployable?` is `false`.
   - After calling the handler: `stack_b.commits.find_by(sha: shared_sha).reload.state == "success"`.
   - Assert `ProcessMergeRequestsJob` (or `stack.schedule_merges`) is enqueued/invoked for `stack_b`, even though the payload only ever named `org-a`/`repository_a`.
   - Assert `stack_a`'s commit remains unaffected/as expected, isolating that the mutation occurred cross-tenant.
