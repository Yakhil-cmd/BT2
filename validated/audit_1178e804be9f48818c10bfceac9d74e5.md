### Title
CCMenu API endpoint bypasses `ApiClient#stack_id` scoping, allowing a stack-scoped token to read any stack's deploy status - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Api::CCMenuController` overrides `BaseController#stack` with a version that resolves the stack directly from the `stack_id` URL parameter instead of going through the `stack_id`-scoped `stacks` relation. This breaks the equality that a `read:stack` permission check is supposed to enforce: `ApiClient#stack_id` (the stack the token is authorized for) ≠ the stack the request actually touches (`params[:stack_id]`).

### Finding Description
`ApiClient` records can carry an optional `stack_id`, meant to scope a token to a single stack [1](#0-0) . `Api::BaseController` implements this scoping via `stacks`/`stack`:

```ruby
def stacks
  @stacks ||= current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all
end

def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
``` [2](#0-1) 

`require_permission` only calls `ApiClient#check_permissions!(operation, scope)`, which merely checks that the required permission string (e.g. `read:stack`) is present in the client's `permissions` array — it never compares the requested stack to `current_api_client.stack_id` [3](#0-2) . The stack-id binding is therefore enforced solely by the `stacks` scoping in `BaseController#stack`.

`Api::CCMenuController` (used to serve the public CCMenu/CCTray XML feed) authenticates via a bare URL token instead of Basic Auth, and re-defines `stack` to bypass that scoping entirely:

```ruby
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end

def authenticate_api_client
  @current_api_client = ApiClient.authenticate(params[:token])
  super unless @current_api_client
end
``` [4](#0-3) 

This tokens is generated by `CCMenuUrlController`, which creates (or reuses) an `ApiClient` scoped to a single stack with only the `read:stack` permission, and embeds it as a plain query-string `token` intended for third-party CI dashboard software:

```ruby
def client
  @client ||= ApiClient.create_with(permissions: %w[read:stack])
                       .find_or_create_by!(creator: current_user, name: 'CCMenu Client')
end
``` [5](#0-4) 

Because the request is unauthenticated by a Shipit session and only needs a valid token plus the `read:stack` permission (which every CCMenu client has), and because `CCMenuController#stack` never checks `current_api_client.stack_id` against `params[:stack_id]`, holding any one CCMenu token is sufficient to enumerate and read the deploy status (`Api::CCMenuController#show` → `stack.deploys_and_rollbacks.last`) of **every** stack in the Shipit instance, not just the one the token was minted for.

**Binding broken:** `ApiClient#stack_id` (stack the token authorizes) ≠ `stack` (the stack the `CCMenuController#show` action actually touches).

- Before: a CCMenu token for stack A can only ever resolve `stack` to stack A, because `BaseController#stack` filters through `stacks` (`Stack.where(id: current_api_client.stack_id)`).
- After (in `CCMenuController`): `stack` is resolved via `Stack.from_param!(params[:stack_id])`, unconditionally, for any `stack_id` supplied in the URL — regardless of the authenticated client's `stack_id`.

### Impact Explanation
This is an unauthenticated (no Shipit session, no GitHub team membership check, no Basic Auth) read of another stack's deploy/task state — explicitly listed as a High-impact class in scope ("unauthenticated read of stack state, task streams, or deploy output"). Since CCMenu tokens are designed to be embedded in third-party, less-trusted CI dashboard tooling (hence the plain URL-token auth scheme rather than session/Basic Auth), any party who obtains one such token (e.g. via a leaked dashboard config, browser history, proxy logs, or simply being a legitimate low-privilege user of one stack) can use it to read deploy status of stacks they were never granted access to.

### Likelihood Explanation
Likelihood is high for anyone who already possesses a valid CCMenu token for any stack (which is the intended, low-friction distribution mechanism for this feature — it's meant to be pasted into external tools). No other credential, session, or elevated permission is required; only changing the `stack_id` request parameter is needed.

### Recommendation
- Short term: change `Api::CCMenuController#stack` to reuse the scoped `stacks` relation from `BaseController` (i.e. `stacks.from_param!(params[:stack_id])`) instead of `Stack.from_param!(params[:stack_id])`, so the `ApiClient#stack_id` scope is enforced the same way it is for every other API controller.
- Long term: add a test asserting that a CCMenu (or any stack-scoped `ApiClient`) token cannot fetch data for a stack other than the one it was scoped to, and audit all controllers that override `BaseController#stack`/`#stacks` for the same bypass pattern.

### Proof of Concept
1. As a legitimate low-privilege Shipit user with access to Stack A only, visit `CCMenuUrlController#fetch` for Stack A to obtain a `ccmenu_url` containing `token=<T>`, where `T` authenticates an `ApiClient` with `stack_id = A.id` and `permissions = ["read:stack"]`.
2. Using token `T`, issue a request to the CCMenu API endpoint but substitute a different stack's `to_param` in the `stack_id` route segment, e.g.:
   `GET /api/stacks/other-owner/other-repo/production/ccmenu.xml?token=T`
3. `CCMenuController#authenticate_api_client` succeeds (token `T` is valid), `require_permission :read, :stack` succeeds (`T` has `read:stack`), and `CCMenuController#stack` resolves via `Stack.from_param!("other-owner/other-repo/production")` — returning Stack B regardless of `T`'s `stack_id` scope.
4. The response renders Stack B's latest deploy/rollback status (`id`, `ended_at`, `running?`) via `shipit/ccmenu/project.xml.builder`, disclosing deploy state for a stack token `T` was never authorized to access.
