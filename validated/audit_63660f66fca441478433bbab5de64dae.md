### Title
Membership webhooks are trusted without a verified signature when `webhook_secret` is unset, letting an unprivileged attacker forge team-membership grants into `Shipit.github_teams` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` delegates trust in an inbound webhook entirely to `GitHubApp#verify_webhook_signature`, which **returns `true` unconditionally whenever no `webhook_secret` is configured** for the resolved organization [1](#0-0) . `webhook_secret` is documented and shipped as an *optional* setting in every secrets template (`# nil`) [2](#0-1) [3](#0-2) . When that binding ("payload accepted" ⇔ "payload cryptographically verified as from GitHub") is broken, the `membership` webhook handler will process a completely forged payload and grant arbitrary GitHub logins membership in a `Team`, which is the exact object `User#authorized?` checks against to gate the entire application [4](#0-3) .

### Finding Description
`WebhooksController` verifies signatures like this:
```
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
head(422) unless verified
``` [5](#0-4) 

`verify_webhook_signature` is:
```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
``` [1](#0-0) 

So the "verified" boolean the controller trusts is decoupled from any actual GitHub signature whenever `webhook_secret` is blank/nil — a state explicitly presented as valid/optional in every shipped secrets template, including the multi-org template [6](#0-5)  and the `test/dummy` multi-org fixture [7](#0-6) .

Once "verified", the `membership` event is dispatched to `MembershipHandler`, registered by default [8](#0-7) :
```ruby
def process
  team = find_or_create_team!
  member = User.find_or_create_by_login!(params.member.login)
  case params.action
  when 'added'
    team.add_member(member)
  ...
``` [9](#0-8) 

`Team#add_member` simply appends the (attacker-chosen) user to the team's memberships with no further GitHub-side re-verification [10](#0-9) , and `User#authorized?` — the single gate used by `Authentication#force_github_authentication` to decide whether *any* logged-in GitHub identity may use Shipit — is purely a DB membership check against `Shipit.github_teams` [4](#0-3) [11](#0-10) .

**The binding broken:** *"organization/event that authenticated" (should equal a signature verified with a real GitHub-issued HMAC secret) vs. "team membership that is written and later trusted for authorization."* When `webhook_secret` is absent, the left side of that equality is vacuously true for any POST body an attacker crafts, while the right side (DB membership → `authorized?`) is exactly what gates deploys, rollbacks, and merges application-wide.

### Impact Explanation
This lets an unauthenticated, unprivileged internet attacker who merely knows (or guesses) an organization name configured in Shipit send a forged `membership` webhook to `/webhooks` and add any GitHub login — including their own — to a `Team` matching one of `Shipit.github_teams`. After that, the attacker completes the normal (legitimate) GitHub OAuth login flow with that same login and is granted `authorized?` access to the whole Shipit instance: triggering deploys, rollbacks, merges, and viewing/streaming all task output — i.e., escalation into `Shipit.github_teams` authorization, one of the explicitly listed High-severity impacts.

### Likelihood Explanation
Requires no credential, no repository write access, no `webhook_secret`, and no privileged account — only network reachability to the mounted `/webhooks` endpoint and knowledge of a configured organization login (often discoverable from the Shipit UI itself, which shows repository owners). This directly parallels the reported bug class: a security control (signature/encryption) that is optional in shipped configuration and fails open rather than closed, so operators following the documented, default-supported setup remain exposed.

### Recommendation
Do not fail open when `webhook_secret` is unset. Either make `webhook_secret` mandatory for any organization capable of driving trust-affecting handlers such as `membership`, or reject/ignore trust-affecting events entirely when no secret is configured, logging a hard error instead of returning `true` from `verify_webhook_signature`. Additionally, consider re-verifying team membership against the GitHub API (as `Team#refresh_members!` already does) before trusting webhook-driven `add_member` calls, rather than trusting the webhook body in isolation.

### Proof of Concept
1. Deploy Shipit using the documented/shipped configuration with `github.<org>.webhook_secret` left blank (as in `config/secrets.development.example.yml` / `docs/setup.md`'s optional field).
2. As an unauthenticated attacker, POST to `/webhooks` with header `X-Github-Event: membership` and body:
```json
{
  "action": "added",
  "team": {"id": 999999, "name": "pwn", "slug": "pwn", "url": "https://example.com"},
  "organization": {"login": "<configured-org>"},
  "repository": {"owner": {"login": "<configured-org>"}},
  "member": {"login": "attacker-github-login"}
}
```
No `X-Hub-Signature` header is required to pass verification because `verify_webhook_signature` short-circuits to `true` when `webhook_secret` is blank [12](#0-11) .
3. `MembershipHandler#process` creates the `Team` and adds `attacker-github-login` as a member [9](#0-8) . If `Shipit.github_teams` happens to match this team (or the attacker chooses the `team.id`/`organization` of an already-authorized team), the attacker's `User` record now satisfies `authorized?` [4](#0-3) .
4. Attacker completes the legitimate GitHub OAuth flow (`GithubAuthenticationController#callback`) with the same GitHub login; `force_github_authentication` now grants full access [11](#0-10) .

Note: I could not fully confirm from the index how `Shipit.github_teams` resolves `team.id`/`organization` matching in every multi-org configuration (`Team.find_or_create_by_handle` vs. the webhook-created `Team.find_or_create_by!(github_id: ...)` path) — an operator with a background Devin session and full repository access should verify the exact `github_id`/`organization` values needed to collide with a real `Shipit.github_teams` entry in their deployment.
