### Title
Webhook signature verification is keyed on `repository.owner.login`, but the repository written to is resolved from the independently-attacker-controlled `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization config (and therefore which `webhook_secret`) to check against using `repository_owner`, a field read directly out of the unauthenticated JSON body. All webhook `Handler` subclasses, however, resolve the `Stack`/`Repository` they act on using a *different* field from the same body: `repository.full_name`. Nothing ties these two fields together, so an attacker can pick an organization slot for signature verification that has no `webhook_secret` configured while pointing the actual mutation at any other repository/stack in the installation.

### Finding Description
`verify_signature` in `app/controllers/shipit/webhooks_controller.rb` computes the org used for the signature check like this: [1](#0-0) [1](#0-0) [2](#0-1) 

`Shipit.github(organization:)` resolves per-organization config using `github_app_config`, and `GitHubApp#verify_webhook_signature` unconditionally returns `true` when that organization has no `webhook_secret` configured: [3](#0-2) [4](#0-3) 

This multi-organization configuration (a map of org name to `{app_id, webhook_secret, private_key, ...}`) is a first-class, production feature of the engine (`github_app_config`, `github_organizations`, `TOP_LEVEL_GH_KEYS`), not a test-only construct.

Once `verify_signature` passes, `create` dispatches the raw parsed JSON to every registered `Handler` for the event: [5](#0-4) 

But every `Handler` determines the repository/stack to act on from a *different* field of the same payload: [6](#0-5) 

There is no code anywhere that checks `repository.owner.login` (used to select the verifying org) against `repository.full_name`'s owner segment (used to select the acted-upon repository). Both fields originate from the same attacker-controlled JSON body.

**Equality that should hold but doesn't:** `organization authenticated by verify_signature (repository.owner.login)` == `organization that owns the repository actually written to (repository.full_name)`.

**Attack:** if any organization configured in `Shipit.github_organizations` has a blank `webhook_secret` (a supported and, per `docs/setup.md`, explicitly optional field), an attacker with no credentials can send a POST to `/webhooks` with:
- `X-Github-Event: push` (or `status`, `check_suite`, `membership`, `pull_request`)
- `repository.owner.login` = the org with no secret (so `verify_webhook_signature` returns `true` regardless of the `X-Hub-Signature` header)
- `repository.full_name` = `<victim-org>/<victim-repo>`, an entirely different, secret-protected repository

`verify_signature` passes (no secret to check against), and the dispatched handler (e.g. `PushHandler`) resolves and mutates the *victim* stack because it only looks at `repository.full_name`: [7](#0-6) 

For `push`, this enqueues `GithubSyncJob`/`stack.sync_github` for the victim stack using an attacker-chosen `expected_head_sha`, potentially triggering continuous-delivery deploys on a stack the attacker has no relationship to.

### Impact Explanation
This breaks a deployment-trust binding without any credential: the org whose signature secret is (or isn't) checked is not the org whose repository/stack is mutated. Depending on which handler is invoked, an attacker can forge push/status/membership/check_suite events against any repository configured in the Shipit instance, causing unauthorized commit ingestion and downstream continuous-delivery deploy triggers, forged commit statuses, or spurious team/user creation — all without possessing any GitHub credential, session, or API token. This aligns with "High - unauthenticated write of stack state" / can escalate to an unauthorized deploy trigger when combined with continuous deployment settings.

### Likelihood Explanation
Requires only that the Shipit deployment use the multi-organization GitHub App config with at least one organization lacking a `webhook_secret` (a supported, documented configuration in `docs/setup.md`/`lib/shipit.rb`). Given that, exploitation needs a single unauthenticated HTTP POST with a crafted JSON body — no signature, session, or token required.

### Recommendation
Bind the org used to verify the signature to the same identifier used by handlers to resolve the target repository: derive both `repository_owner` and `repository_name` from `repository.full_name` consistently, or verify that `repository.owner.login`/`organization.login` matches the owner segment of `repository.full_name` before dispatching. Additionally, consider refusing verification success (`verified = true`) when `webhook_secret` is blank, or scoping any secret-less org strictly so it cannot serve as an authentication bypass for events referencing other organizations' repositories.

### Proof of Concept
1. Configure Shipit with two orgs: `victim-org` (has `webhook_secret`) and `attacker-org` (no `webhook_secret`), both valid entries under `secrets.github`.
2. POST to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-controlled-sha>",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
No valid `X-Hub-Signature` is required because `Shipit.github(organization: "attacker-org").verify_webhook_signature` returns `true` unconditionally (blank secret), per `app/controllers/shipit/webhooks_controller.rb:24-30` and `lib/shipit/github_app.rb:76-83`.
3. `create` dispatches to `PushHandler`, which resolves `Repository.from_github_repo_name("victim-org/victim-repo")` via `app/models/shipit/webhooks/handlers/handler.rb:32-38`, and triggers `stack.sync_github(expected_head_sha: "<attacker-controlled-sha>")` on the victim's stack — a write the attacker was never authenticated to make.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
