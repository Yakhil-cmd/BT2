### Title
Unvalidated swap routes can inject unauthorized wallet token transfers into a signed controller authorization tree - ([File: contracts/controller/src/strategies/swap.rs](contracts/controller/src/strategies/swap.rs))

### Summary
XOXNO Lending lets an account owner submit an opaque route through `swap_collateral`, but the controller’s narrow input-transfer authorization does not prevent route-invoked pool code from requesting unrelated token transfers under the caller’s authorization. [1](#0-0)  A victim who signs the poisoned simulation tree can lose unrelated wallet tokens even though the requested collateral swap itself settles normally. [2](#0-1) 

### Finding Description
`swap_collateral` authenticates `caller` and requires ownership or delegation for `account_id`, but treats `swap` as unvalidated opaque payload. [3](#0-2)  The controller invokes the configured router and authorizes only its own exact input-token transfer to that router. [4](#0-3)  Route execution resolves pool and token addresses from payload-supplied registries, with no controller-side venue allowlist. [5](#0-4)  A payload-named pool can therefore execute attacker-controlled contract code during the swap. [6](#0-5)  If that code calls `unrelated_token.transfer(victim, attacker, amount)`, Soroban records the nested transfer as a child of the victim’s authorization entry. [7](#0-6)  Signing the returned tree authorizes that unrelated transfer, and the swap can still return enough output to satisfy settlement and final account checks. [2](#0-1) 

### Impact Explanation
This enables theft of arbitrary unrelated tokens held by the victim’s wallet, beyond the collateral amount intentionally supplied to the strategy. [8](#0-7)  The loss is not bounded by `amount_in`, route `min_out`, or post-swap account solvency because those controls measure only the strategy’s input and output assets. [9](#0-8) 

### Likelihood Explanation
An unprivileged attacker can deploy a compatible malicious pool, construct a route naming it, and induce a victim to submit `swap_collateral` or an equivalent route-bearing strategy call. [10](#0-9)  Exploitation requires the victim to sign an authorization tree containing the extra transfer, which makes phishing or a compromised route-generation path necessary but does not require privileged access, leaked keys, oracle manipulation, or a protocol upgrade. [11](#0-10) 

### Recommendation
Bind swap routes to governance-approved pool, venue, and token addresses before execution rather than allowing the opaque payload to select arbitrary contracts. [5](#0-4)  Until venue allowlisting is enforced, clients should decode the simulated authorization tree and reject any controller strategy tree containing token-transfer children unrelated to the declared route. [12](#0-11) 

### Proof of Concept
1. Deploy a pool implementing the selected venue ABI whose `swap` implementation calls `victim_token.transfer(victim, attacker, amount)` and then returns enough route output token to satisfy the measured-output check. [13](#0-12) 
2. Construct a route whose payload registries name that malicious pool while keeping a valid listed input and output market. [14](#0-13) 
3. Have the victim invoke `swap_collateral(victim, account_id, current_asset, amount, new_asset, route)` on the controller. [15](#0-14) 
4. Simulation records the unrelated wallet-token transfer beneath the victim’s authorization root. [7](#0-6) 
5. If the victim signs that tree, the unrelated wallet balance moves to the attacker while the requested collateral swap succeeds. [2](#0-1)

**File:** docs/explanation/threat-model.md (L154-164)
```markdown
That bound covers the controller's own grant only. The router calls the pool
and token addresses its payload names and keeps no allowlist of them, so a
route can put third-party code on the call stack below the caller's
authorization. A token transfer that such code makes from the caller is
recorded by an honest simulation as a child of the caller's authorization
entry, and it executes if the caller signs that tree. The loss is then the
caller's wallet, not the routed amount, and neither the payload minimum nor the
final risk gate bounds it. An honest swap strategy gives the caller no child
entry, and a direct router swap gives exactly one input transfer. A client must
decode the route it signs and refuse an authorization tree with any other
child. The direct `execute_strategy` path has the same exposure for every swap
```
