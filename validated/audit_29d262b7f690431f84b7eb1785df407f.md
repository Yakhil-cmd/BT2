### Title
Cross-repository Status forgery via global sha lookup in `StatusHandler#process` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` looks up commits by `Commit.where(sha: params.sha)` across the entire `commits` table instead of scoping to the stacks that belong to the webhook's verified `repository.full_name`, unlike `PushHandler` which correctly scopes via `stacks`. Because `sha` is only unique per `(stack_id, sha)` and not globally, a webhook legitimately signed for one repository can write a `Status` (via `Status.replicate_from_github!`) onto a `Commit`/`Stack` belonging to a completely unrelated repository/organization that happens to share that sha (e.g. a fork of the victim repo).

### Finding Description
Binding claimed to hold: `stack_id` passed to `Status.replicate_from_github!` == the stack referenced by the verified webhook's `repository.full_name`.

Trace:
- `WebhooksController#create` parses the payload and dispatches to `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` [1](#0-0) .
- `verify_signature` only checks that the payload signature matches the GitHub App configured for `repository_owner` (`params.dig('repository','owner','login')`) — it proves the payload really came from GitHub for *that* owner/repo, nothing more [2](#0-1) .
- The base `Handler` class exposes a `stacks` helper that correctly scopes to `Repository.from_github_repo_name(repository_name)&.stacks`, i.e. only stacks that belong to the verified repository [3](#0-2) . `PushHandler` uses exactly this scope: `stacks.not_archived.where(branch:).find_each { ... }` [4](#0-3) .
- `StatusHandler#process`, however, **never calls `stacks`**. It does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [5](#0-4) . This is a global, unscoped query across every stack/repository/organization tracked by the Shipit instance.
- `commit.create_status_from_github!` then calls `statuses.replicate_from_github!(stack_id, github_status)` where `stack_id` is simply `commit.stack_id` of whatever row matched — not derived from the webhook's `repository.full_name` at all [6](#0-5) .
- `Status.replicate_from_github!` performs `find_or_create_by!(stack_id:, state:, description:, target_url:, context:, created_at:)` with no additional authorization or repository check [7](#0-6) .
- The schema only enforces uniqueness/indexing on the composite `(stack_id, sha)` (`db/migrate/20170524104615_index_commits_on_stack_id_and_sha.rb`), confirming `sha` is not unique across the whole `commits` table — different stacks can legitimately hold `Commit` rows with an identical `sha` (e.g., two Shipit stacks tracking a repo and its fork, which share git history/object hashes up to the fork point, or any two repos that happen to contain byte-identical commit objects).

Attacker path: attacker forks (or otherwise obtains write access to) a repository whose history overlaps with a victim's Shipit-tracked repository, so some commit sha `X` exists both as a `Commit` row for the victim stack and (if the attacker's own repo/fork is also tracked as a Shipit stack, e.g. via review-stack/self-service provisioning) for the attacker's own stack. The attacker then triggers a real GitHub `status` event on their own repository (e.g., via the GitHub API using their own token, no Shipit secret needed) with `sha = X`. GitHub signs and delivers this webhook legitimately; `verify_signature` passes because it's genuinely from GitHub for the attacker's own repo/org. `StatusHandler#process` then updates/creates a `Status` for **every** `Commit` row in the database with `sha = X`, including the victim's unrelated stack, using state/description/context/target_url fully controlled by the attacker.

Existing guards (`verify_signature`, `drop_unhandled_event`, `ExplicitParameters` schema) validate only that the payload's *sender* and *shape* are legitimate for the attacker's own repository — none of them enforce that the `Commit` rows touched by `process` belong to stacks under that same `repository.full_name`. The `stacks` scope exists in the base `Handler` precisely for this purpose but `StatusHandler` bypasses it.

### Impact Explanation
An attacker who controls any repository (even a throwaway fork) whose commit history overlaps with a Shipit-tracked target can inject arbitrary CI/status data (`state`, `description`, `context`, `target_url`) onto a commit belonging to a different stack/organization they do not control. Since `Status#state` (`success`/`failure`/etc.) feeds `Commit#status`/`deployable_status`, and those states drive `continuous_delivery` scheduling (`schedule_continuous_delivery`) and merge-request processing (`ProcessMergeRequestsJob`) as seen in the commit model, forging a `success` status can unblock/trigger an unauthorized continuous deployment or auto-merge of a commit in a repository/stack the attacker does not own — a payload for one repository mutating another's stack/commit, matching the "Critical" impact category. This is repeatable against any pair of repositories sharing a commit sha (most easily, any fork relationship) and is not limited to a single victim.

### Likelihood Explanation
Preconditions: the attacker needs (a) a repository they control that is registered with Shipit as a stack (or that shares commit shas with one — most simply via forking a tracked repo, though gaining a Shipit stack registration for their own repo may require additional setup depending on installation policy) and (b) knowledge/observation of a shared sha (trivial if they forked the victim repo, since shared history commits carry identical shas). Given those, the attacker cost is a single real GitHub API call to set a commit status on their own repository — no Shipit secrets, sessions, or tokens are required, and GitHub itself produces the correctly signed webhook. This is fully repeatable and requires no privileged Shipit role.

### Recommendation
Scope `StatusHandler#process` (and any other handler that queries `Commit` by `sha` without going through `stacks`) to only the stacks derived from the verified `repository.full_name`, e.g. `Commit.where(sha: params.sha, stack_id: stacks.select(:id))` or iterate `stacks.each { |stack| stack.commits.find_by(sha: params.sha)&.create_status_from_github!(params) }`, mirroring the pattern already used in `PushHandler`.

### Proof of Concept
Minitest plan (model/webhook-level, no live GitHub required):

```ruby
test "StatusHandler must not update commits belonging to a different repository/stack" do
  victim_stack = shipit_stacks(:shipit)               # tracks "shopify/shipit-engine"
  attacker_stack = shipit_stacks(:cyclimse)            # tracks a different repo, e.g. attacker's fork

  shared_sha = "deadbeefcafebabe0000000000000000000000"
  victim_commit = victim_stack.commits.create!(sha: shared_sha, author: shipit_users(:walrus),
                                                committer: shipit_users(:walrus),
                                                authored_at: Time.now, committed_at: Time.now,
                                                message: "shared commit")
  attacker_commit = attacker_stack.commits.create!(sha: shared_sha, author: shipit_users(:walrus),
                                                    committer: shipit_users(:walrus),
                                                    authored_at: Time.now, committed_at: Time.now,
                                                    message: "shared commit")

  payload = {
    'sha' => shared_sha,
    'state' => 'success',
    'description' => 'forged by attacker',
    'context' => 'ci/attacker',
    'branches' => [{ 'name' => attacker_stack.branch }],
    'repository' => { 'full_name' => attacker_stack.repository.github_repo_name }
  }

  Shipit::Webhooks::Handlers::StatusHandler.call(payload)

  # Expected (safe) behavior: only attacker_commit gets the forged status
  assert_equal 'success', attacker_commit.reload.status.state
  refute_equal 'success', victim_commit.reload.status.state   # FAILS today: victim_commit also gets updated
end
```

This demonstrates that a webhook verifiably signed and scoped to the attacker's own repository (`payload['repository']['full_name']`) nonetheless writes a `Status` row against `victim_commit`/`victim_stack`, violating the claimed binding between `stack_id` and the verified `repository.full_name`.
