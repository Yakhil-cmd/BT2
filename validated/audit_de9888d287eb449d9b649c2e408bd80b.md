### Title
Unauthenticated P2P Staking Info Injection via No-op Validation in FastSync/SnapSync Corrupts KEFAddr/KIFAddr for Pre-Kaia Epochs — (`datasync/downloader/queue.go`, `datasync/downloader/downloader.go`)

### Summary

During FastSync/SnapSync, staking info delivered by a sync peer is accepted with zero validation. A malicious peer can supply fabricated `P2PStakingInfo` (with attacker-chosen `KEFAddr`/`KIFAddr`) for pre-Kaia-hardfork staking update blocks. This fabricated data is written directly to the persistent DB via `PutStakingInfoToDB`. Because `GetStakingInfo` for pre-Kaia blocks returns the DB value on first hit without re-deriving from the state trie, the corruption is durable and will be used for all reward distribution calls that reference those source block numbers.

### Finding Description

**Step 1 — Staking info is scheduled for download with no content commitment.**

In `newFetchResult`, a staking info fetch is queued for any header at a staking update interval before the Kaia hardfork: [1](#0-0) 

The block header hash does not commit to the staking info content. The staking info is a separate P2P payload.

**Step 2 — Delivery validation is a no-op.**

`DeliverStakingInfos` in `queue.go` has an explicit TODO and returns `nil` unconditionally: [2](#0-1) 

Any `P2PStakingInfo` payload — including one with attacker-chosen `KEFAddr`/`KIFAddr`/`CouncilNodeAddrs` — is accepted and placed into the `fetchResult`.

**Step 3 — `commitPivotBlock` writes the unvalidated staking info to DB.** [3](#0-2) 

The same pattern exists in `commitFastSyncData` for pre-pivot blocks: [4](#0-3) 

There is no comparison against the state trie rooted at `result.Header.Root`.

**Step 4 — `GetStakingInfo` returns the DB value without re-deriving from state.** [5](#0-4) 

Once the corrupted entry is in DB, every subsequent call to `GetStakingInfo` for that source block number returns the fabricated value. The state-derivation path (lines 65–73) is never reached.

**Step 5 — `PostInsertBlock` propagates the corrupted value.** [6](#0-5) 

For each new pre-Kaia block inserted, `GetStakingInfo` is called, hits the corrupted DB entry, and caches it — cementing the fabricated `KEFAddr`/`KIFAddr` in the in-memory cache as well.

### Impact Explanation

The corrupted `KEFAddr` and `KIFAddr` fields in `StakingInfo` are used by the reward module to determine where ecosystem fund distributions (KEF, KIF) are sent. An attacker who controls a sync peer can redirect these distributions to attacker-controlled addresses for all pre-Kaia-hardfork epochs whose source block numbers were corrupted during sync. The corruption is persistent across node restarts because it lives in the key-value DB.

The impact is bounded to pre-Kaia-hardfork epochs: after the Kaia hardfork, `GetStakingInfo` derives from state and does not consult the DB, so post-Kaia reward distribution is unaffected.

### Likelihood Explanation

- Any node that connects to a malicious peer and initiates FastSync or SnapSync is vulnerable.
- The attacker only needs to run a standard Kaia node that serves valid headers (obtained from the real network) but returns fabricated staking info in response to `StakingInfoRequestMsg`.
- No validator keys, governance privileges, or majority collusion are required.
- The attack is silent — no error is logged for the missing validation.

### Recommendation

Replace the no-op `validate` function in `DeliverStakingInfos` with a check that re-derives the staking info from the synced state trie at the corresponding block root and compares it against the peer-supplied value. Alternatively, after FastSync completes and the state trie is available, re-derive and overwrite all staking info DB entries from the canonical state before marking sync as done.

### Proof of Concept

1. Run a malicious Kaia peer that serves valid headers/bodies/receipts from the real chain but intercepts `StakingInfoRequestMsg` and responds with a `P2PStakingInfo` where `KEFAddr` and `KIFAddr` are set to attacker-controlled addresses.
2. Connect a victim node in FastSync mode to this peer.
3. After sync completes, call `kaia_getStakingInfo` for any pre-Kaia staking update block number.
4. Observe that the returned `KEFAddr`/`KIFAddr` match the attacker-supplied values, not the values encoded in the AddressBook contract at that block's state root.
5. Confirm that reward distribution for those epochs uses the fabricated addresses.
