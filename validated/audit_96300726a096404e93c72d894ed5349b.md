### Title
Webhook signature verification is keyed to the attacker-controlled `repository.owner.login`/`organization.login` field, not the `repository.full_name` the event actually acts on, allowing an org with no `webhook_secret` to forge events for a different, secured org - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks *which* GitHub App/org config (and therefore which HMAC secret) to validate a webhook against based on an attacker-controlled field of the unauthenticated payload (`repository.owner.login`, falling back to `organization.login`). The event is then dispatched to handlers that resolve the target `Stack`/`Repository` independently, from `repository.full_name` in the same payload. In a multi-org deployment where one configured organization has no `webhook_secret` set, `verify_webhook_signature` is a no-op for that organization (`return true unless webhook_secret`), letting an unprivileged caller "authenticate" as that org while writing/acting on a completely different organization's repository/stack.

`PushHandler`, `StatusHandler`, and the pull-request handlers all key off this `repository.full_name`/`repository`-derived scope, independent of `repository_owner`: [8](#0-7) [9](#0-8) 

**Broken binding (as equality):** `organization authenticated by verify_signature` should equal `organization that owns the repository the handlers write to`. Instead, `repository_owner` (used only to pick a verification key) and `repository.full_name`'s owner (used to select the actual stack acted on) are two independently attacker-supplied fields of the same unauthenticated JSON body, with no cross-check that they match.

**Before the attacker's request:** an operator has configured Shipit for two GitHub orgs — e.g. `secured-org` (has `webhook_secret` set, hosts production stacks) and `legacy-org` (no `webhook_secret` configured, as the sample config demonstrates is a valid state). Both orgs' data lives in the same Shipit instance and DB.

**After the attacker's request:** an unauthenticated attacker POSTs to `/webhooks` with `X-Github-Event: push`, body `{"repository": {"owner": {"login": "legacy-org"}, "full_name": "secured-org/production-repo"}, "ref": "refs/heads/main", "after": "<attacker-chosen sha>"}`. `repository_owner` resolves to `legacy-org`; `Shipit.github(organization: "legacy-org")` has `webhook_secret` blank, so `verify_webhook_signature` returns `true` unconditionally, bypassing signature verification entirely (no `X-Hub-Signature` value is even required). `create` then dispatches to `PushHandler`, which resolves `Repository.from_github_repo_name("secured-org/production-repo")` and calls `stack.sync_github(expected_head_sha: params.after)` on the secured org's real stack — a forged, unauthenticated event acting on a repository never protected by `legacy-org`'s (non-existent) secret.

### Impact Explanation
This is an authentication bypass: the per-organization signature check can be defeated simply by naming, in the request body, any configured organization that has no `webhook_secret`, while directing the actual effect (`repository.full_name`) at a different, secured organization's stack. This lets an unauthenticated, unprivileged caller inject forged GitHub events (`push`, `status`, `check_suite`, `pull_request`, etc.) for repositories/stacks belonging to organizations that *do* have webhook protection configured. Depending on which handler fires, this can forge commit statuses feeding `Commit#deployable?` (`app/models/shipit/commit.rb:227-229`) and trigger `stack.schedule_merges`/continuous delivery, or force out-of-band `sync_github` calls on protected stacks — i.e., manipulation of deploy-gating state and potentially an unauthorized ship for a repository the attacker has no legitimate write access to. This satisfies the "authentication bypass" / "unauthorized deploy" criteria.

### Likelihood Explanation
Requires the target Shipit instance to be configured for more than one GitHub organization (the multi-org config schema is a first-class, documented feature — `github_default_organization`, `github_app_config`, `TOP_LEVEL_GH_KEYS` in `lib/shipit.rb`), and at least one configured org lacking a `webhook_secret`. Given the sample config file in this repo itself ships with `webhook_secret: # nil` for every org, this is a realistic operational state, not a hypothetical misconfiguration exclusive to test environments. No credentials, session, or prior access are required by the attacker — only knowledge that a second, low-privilege org name is configured (discoverable, e.g., via OAuth login flows, error messages, or simply guessing common org slugs).

### Recommendation
Bind the signature-verification org to the same identity the handlers use for repository resolution: verify the payload against the org actually implied by `repository.full_name` (not a separately-controllable `repository.owner.login`/`organization.login` field chosen ahead of full validation), and reject/require a secret for every configured org rather than silently returning `true` when `webhook_secret` is blank. At minimum, cross-check that `repository_owner` used for verification matches the owner segment of `repository.full_name` before dispatching to handlers, and treat "no webhook_secret configured for an org" as a hard misconfiguration (fail closed) rather than an implicit bypass.

### Proof of Concept
Given a Shipit deployment configured with two orgs where `legacy-org` has no `webhook_secret` and `secured-org` does (mirroring `config/secrets.development.shopify.yml`'s pattern):

```
POST /webhooks HTTP/1.1
X-Github-Event: push
Content-Type: application/json

{
  "repository": { "owner": { "login": "legacy-org" }, "full_name": "secured-org/production-repo" },
  "ref": "refs/heads/main",
  "after": "deadbeefdeadbeefdeadbeefdeadbeefdeadbeef"
}
```
- `repository_owner` → `"legacy-org"` (`app/controllers/shipit/webhooks_controller.rb:59-61`).
- `Shipit.github(organization: "legacy-org").verify_webhook_signature(...)` returns `true` immediately since `webhook_secret` is blank (`lib/shipit/github_app.rb:76-77`), no `X-Hub-Signature` header needed.
- `PushHandler.call(params)` resolves `Repository.from_github_repo_name("secured-org/production-repo")` and invokes `stack.sync_github(expected_head_sha: "deadbeef...")` on the `secured-org` stack (`app/models/shipit/webhooks/handlers/push_handler.rb:12-16`, `app/models/shipit/webhooks/handlers/handler.rb:32-38`) — despite the attacker never possessing `secured-org`'s `webhook_secret`.

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
    end
  end
end
