## Finding

### Title
Premature in-memory `is_stable` flag update before the corresponding DB write/commit completes - ([File: main_chain.js])

### Summary
`markMcIndexStable()` in `main_chain.js` sets the in-memory stability flag and populates the process-wide unit-props cache (`storage.assocStableUnits`, `storage.assocStableUnitsByMci`) *before* the corresponding `UPDATE units SET is_stable=1 ...` query is even issued, and long before the enclosing DB transaction is committed and the `kvstore` batch is flushed to disk. [1](#0-0) 

This mirrors the CVE-2025-38429 bug class: the "pointer" that signals availability of fully-written data (here, the `is_stable` flag and the cached unit properties that many code paths trust as ground truth) is advanced before the actual persisted buffer (the SQL row and the kv-store `ball`/joint payload written later in the same function, e.g. in `addBalls()`) is durably written.

### Finding Description
`storage.readUnitProps()` deliberately checks the in-memory cache first, without touching the database, whenever a unit is considered stable: [2](#0-1) 

Because `markMcIndexStable()` populates `assocStableUnits[unit]` and flips `o.is_stable = 1` synchronously at the very top of the function — well before the `UPDATE units SET is_stable=1...` query callback fires, and well before `handleNonserialUnits()`, `propagateFinalBad()`, `addBalls()` (which writes the ball/skiplist/joint payload to the kv-store batch) and the final `batch.write()` + `COMMIT` in `stabilizeMci()`/`advanceMcStability()` complete — any code that consults the cache during this window observes a unit as "stable" while its persisted representation (SQL row, `sequence` finalization for non-good units, ball/skiplist entries in the kv-store batch) is still incomplete or not yet committed: [3](#0-2) 

The whole sequence (memory update → SQL updates → non-serial unit sequence resolution → ball/skiplist persistence → AA trigger insertion → batch write → SQL commit) is long and multi-step, and several sub-steps (`handleNonserialUnits`, `propagateFinalBad`, `saveUnstablePayloads`) perform further asynchronous DB work and can throw on unexpected conditions. If any exception surfaces after the in-memory flag has already been flipped but before the transaction commits, the in-memory cache remains permanently marked "stable"/finalized while the underlying SQL transaction can be rolled back or left uncommitted, producing a lasting divergence between what the process believes is stable (used by AA balance computation, output-picking, and light/watcher notifications) and what is actually durable on disk.

### Impact Explanation
`is_stable` (and the cached `sequence`, ball, and data-feed state derived from it) is the primary signal used throughout the codebase to treat units/outputs as final: AA trigger processing reads `storage.assocStableUnits` to resolve unit props (`aa_composer.js` `handlePrimaryAATrigger` at line 104), balances and outputs pickers rely on unit finality, and light/watcher notification (`network.js` `notifyWatchersAboutStableJoints`) is emitted from this same event. A memory/disk divergence here can cause the node to act on a stability decision that was never durably committed, which in the AA/balance-consuming paths translates to funds being treated as available/spendable, or state considered final, when the persisted ledger disagrees — i.e., node disagreement on validity/stability of a supposedly-stable unit.

### Likelihood Explanation
Reaching `markMcIndexStable()` requires no special privilege — it fires automatically whenever a normal unit poster's unit advances main-chain stability, which happens continuously as part of ordinary DAG growth. The multi-step, multi-async-callback body of the function (spanning `handleNonserialUnits`, `propagateFinalBad`, `addBalls`, `saveUnstablePayloads`) gives a wide window between the premature in-memory update and the final commit in which a transient DB error, a thrown assertion (e.g., the `throw Error` calls scattered through this path), or process restart can leave the cache and the database permanently inconsistent.

### Recommendation
Defer all in-memory cache mutations (`o.is_stable = 1`, population of `storage.assocStableUnits`/`assocStableUnitsByMci`, deletion from `assocUnstableUnits`) in `markMcIndexStable()` until after the corresponding SQL updates and the kv-store batch write have been confirmed committed (i.e., move the cache mutation to the point right before/after `COMMIT` in `stabilizeMci()`/`advanceMcStability()`), mirroring the upstream kernel fix of writing the buffer before advancing the pointer that signals its availability.

### Proof of Concept
Not directly demonstrable without triggering a mid-function exception in a live network; the root cause is architectural — visible directly from the code ordering in [4](#0-3)  compared with the cache-first read in [5](#0-4) .

function markMcIndexStable(conn, batch, mci, onDone){
	if (!onDone)
		return new Promise(resolve => markMcIndexStable(conn, batch, mci, resolve));
	profiler.start();
	let count_aa_triggers;
	var arrStabilizedUnits = [];
	if (mci > 0)
		storage.assocStableUnitsByMci[mci] = [];
	for (var unit in storage.assocUnstableUnits){
		var o = storage.assocUnstableUnits[unit];
		if (o.main_chain_index === mci && o.is_stable === 0){
			o.is_stable = 1;
			storage.assocStableUnits[unit] = o;
			storage.assocStableUnitsByMci[mci].push(o);
			arrStabilizedUnits.push(unit);
		}
	}
	arrStabilizedUnits.forEach(function(unit){
		delete storage.assocUnstableUnits[unit];
	});
	conn.query(
		"UPDATE units SET is_stable=1 WHERE is_stable=0 AND main_chain_index=?", 
		[mci], 
		function(){
			// next op
			handleNonserialUnits();
		}
	);
