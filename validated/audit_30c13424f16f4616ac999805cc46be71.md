### Title
Signature-verification organization is decoupled from the acted-upon repository, allowing cross-organization push/status spoofing - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
The webhook signature-verification step selects which GitHub App/`webhook_secret` to validate against based on `repository.owner.login` taken from the untrusted request body, while every event handler resolves the target `Repository`/`Stack` from a different field of the same untrusted body: `repository.full_name`. These two fields are never checked for consistency, so a signature that is valid for organization A's webhook secret can be replayed with a payload whose `repository.full_name` points at a completely different organization's repository.

### Finding Description
`WebhooksController#verify_signature` picks the `GitHubApp` (and thus the `webhook_secret` used for HMAC verification) using: [1](#0-0) [2](#0-1) 

i.e. `repository_owner` is read from `params.dig('repository', 'owner', 'login')` (or `organization.login`) inside the JSON body itself, and `Shipit.github(organization: repository_owner)` resolves the per-organization config (relevant when the "Using Multiple GitHub Applications" setup, documented in `docs/setup.md`, is in use with distinct `webhook_secret`s per org).

Once signature verification passes, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` dispatches the same raw payload to handlers such as `PushHandler`, which resolve the affected repository/stack via `Handler#repository_name`: [3](#0-2) 

`repository_name` comes from `payload.dig('repository', 'full_name')` — a completely different JSON field from the one used to select the signing secret. Nothing ties `repository.owner.login` to `repository.full_name`.

This breaks the equality: `organization authenticated (repository.owner.login) == repository written (repository.full_name)`. Before the attack, both fields naturally match for legitimate GitHub-issued webhooks. An attacker who administers their own GitHub App/organization on the same Shipit instance (and therefore legitimately knows their own org's `webhook_secret`) can craft a payload where `repository.owner.login` is their own org (so the signature computed with their known secret passes verification) while `repository.full_name` is set to `victim-org/victim-repo`, a stack belonging to a different organization on the same Shipit instance.

### Impact Explanation
`PushHandler#process` uses `params.after` (the attacker-controlled "expected head SHA") to invoke `stack.sync_github(expected_head_sha: params.after)` on the victim's stack: [4](#0-3) 

This lets an attacker who is only authorized for their own GitHub organization's webhook trigger sync/state-changing webhook events (`push`, `status`, `check_suite`, `pull_request`, `membership`, etc., per `Shipit::Webhooks.for_event`) against stacks belonging to organizations they have no access to, purely by knowing a signing secret that legitimately belongs to a different, unrelated organization configured on the same multi-tenant Shipit instance. Depending on which handler is targeted this can force sync of an attacker-chosen "expected head sha", or manipulate commit statuses/deployable status for a foreign repository — an authentication/authorization boundary crossing that reaches into deploy-relevant state for repositories the attacker does not control. This matches the High/Critical class of "escalation into GitHub authorization" / "unauthorized deploy or state change" called out in scope.

### Likelihood Explanation
Requires the Shipit instance to be configured for multiple GitHub organizations (explicitly documented and supported in `docs/setup.md`, "Using Multiple Github Applications") and the attacker to be an admin of (or otherwise possess the webhook secret for) at least one of those organizations' GitHub Apps — a realistic scenario for shared/multi-tenant Shipit deployments where different teams/orgs each configure their own GitHub App. No GitHub write access to the victim repository, no Shipit session, and no victim API token are required.

### Recommendation
After parsing the payload, verify that `repository.owner.login` (or `organization.login`) matches the owner segment of `repository.full_name` before dispatching to handlers, or better, always derive the signing organization and the acted-upon repository from the same, single trusted field. Reject the webhook if these are inconsistent.

### Proof of Concept
1. Configure Shipit with two GitHub orgs, `attacker-org` and `victim-org`, each with its own `webhook_secret` (per `docs/setup.md` multi-org setup). Attacker administers `attacker-org`'s GitHub App and knows its `webhook_secret`.
2. Attacker crafts a JSON body:
```json
{
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  },
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>"
}
```
3. Attacker computes `X-Hub-Signature: sha1=<hmac>` using `attacker-org`'s known `webhook_secret` over the raw body.
4. POST to `/github/webhooks` with `X-Github-Event: push`. `verify_signature` resolves `Shipit.github(organization: 'attacker-org')` and successfully verifies the signature.
5. `PushHandler` resolves `repository_name` = `victim-org/victim-repo`, finds the corresponding `Stack`, and calls `stack.sync_github(expected_head_sha: '<attacker-chosen-sha>')` — a state-changing action on a stack the attacker has no authorization over.

Note: I was unable to fully inspect `Stack#sync_github` and `GithubSyncJob` contents within the tool budget to confirm the exact downstream consequence (e.g., whether `expected_head_sha` can force a deploy of an arbitrary/rolled-back commit); this should be verified in a follow-up review of `app/models/shipit/stack.rb` and `app/jobs/shipit/github_sync_job.rb`.
