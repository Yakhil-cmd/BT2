This is a genuine analog: multi-org GitHub App deployments authenticate the *organization* named by the webhook payload's `repository.owner.login`, but the *repository processed* by every registered handler is derived independently from `payload.dig('repository', 'full_name')` — with no check that this repository actually belongs to the org whose secret validated the signature.

### Title
Webhook signature verification binds to `repository.owner.login`, but handlers act on `repository.full_name`, allowing cross-organization webhook forgery in multi-org deployments - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
When Shipit is configured with multiple GitHub Apps (one per organization, as documented in `docs/setup.md`), `WebhooksController#verify_signature` selects the HMAC secret to verify against using `repository_owner`, derived from the payload's `repository.owner.login` (or `organization.login`) field. Once the signature check passes, `create` dispatches the *entire raw payload* to all registered handlers, which independently extract the repository to act on from `payload.dig('repository', 'full_name')`. Nothing ties the two together, so a payload can be signed with organization A's secret while carrying `repository.full_name` pointing at organization B's repository.

### Finding Description
`verify_signature` computes the signing key from one field: [1](#0-0) [2](#0-1) 

`Shipit.github(organization:)` resolves per-organization config (app id, webhook secret, etc.) via `github_app_config`, explicitly designed for the case where "a Github application can only authenticate to the Github organization it's installed in" (multi-org setups documented in `docs/setup.md:182-209`, config example in `test/dummy/config/secrets_double_github_app.yml`): [3](#0-2) 

Once `head(422)` is *not* triggered (signature valid for org A), `create` fans the payload out to every handler for the event, and each handler resolves its own target repository from the payload body, not from anything validated during signature verification: [4](#0-3) [5](#0-4) 

This is structurally the same class of bug as the reported issue: the `Deployer` binds trust to one value (a nonce) but the executed action (Safe creation) is keyed on parameters an attacker can also control/collide, breaking the intended "nonce belongs to daoAddress" binding. Here, the binding "webhook_secret used == organization that owns the repository being written" is broken: the secret is chosen from `repository.owner.login`, but the repository actually acted upon (queried for commits, pushed statuses, etc., depending on registered handler) is taken from `repository.full_name`, a sibling field in the same attacker-controlled JSON body that is never cross-checked against `repository.owner.login`.

Equality that should hold and doesn't:
`organization authenticated by verify_webhook_signature == owner(repository acted upon by handler)`

Concretely: if Shipit is installed with GitHub Apps for orgs `A` and `B` (a supported, documented configuration), and the attacker holds/derives `A`'s webhook secret (e.g. because they administer a repository/webhook delivery under org `A`, which is a much lower bar than needing push access to org `B`), they can sign an arbitrary payload with `A`'s secret while setting `repository.full_name` to `B/some-repo` and `repository.owner.login` to `A` (to pick the correct secret) — or, if the handler code reads `organization.login` instead per the fallback, they can even control that independently since `repository_owner` prefers `repository.owner.login` with a fallback to `organization.login`, and handlers use `repository.full_name` exclusively, so these fields need not agree at all.

### Impact Explanation
Depending on which webhook handler is targeted, this allows an attacker who compromises or controls one org's webhook secret to inject forged GitHub events (push, status, check_suite, membership, pull_request, etc.) against stacks belonging to a *different, unrelated organization's* repository registered in the same Shipit instance. For example, forged `status`/`check_suite` events can flip CI state used to gate deploys (`ci.require`/`ci.blocking`), and forged `push` events can trigger `GithubSyncJob` for a foreign repository. This crosses a repository/organization trust boundary that the multi-org GitHub App feature was specifically designed to keep separate, matching the "cross-repository writes" / "unauthorized deploy" impact bucket.

### Likelihood Explanation
Requires: (1) Shipit configured with the multi-org GitHub Apps feature, and (2) attacker possession of one organization's webhook secret (e.g., leaked secret for a smaller/less-guarded org, or an org the attacker legitimately administers) while targeting a different, more sensitive org's repository configured in the same instance. This is a realistic deployment pattern per the documented multi-org setup, but it is conditioned on webhook-secret compromise for at least one org, which somewhat limits likelihood versus a fully unauthenticated bypass.

### Recommendation
In `WebhooksController`, after verifying the signature against the organization-specific secret, re-derive the repository/organization from the payload and assert that `repository.owner.login` (or `organization.login`) used to select the signing secret matches the owner of `repository.full_name` used by handlers, rejecting the request (422) on mismatch. Alternatively, pass the already-validated organization into `Shipit::Webhooks.for_event(...).each { |handler| handler.call(params, organization:) }` and have `Handler#stacks`/`#repository_name` enforce that the resolved repository's owner equals the validated organization before doing any work.

### Proof of Concept
1. Configure Shipit with two GitHub Apps, e.g. `OrgOne` and `OrgTwo` (per `test/dummy/config/secrets_double_github_app.yml`), each with its own `webhook_secret`, both installed on the same Shipit instance with stacks for repos owned by each org respectively.
2. As an attacker who knows/controls `OrgOne`'s webhook secret (e.g., you administer a repo under `OrgOne` and can read its App webhook config, or the secret leaked), craft a `push` (or `status`, `check_suite`) JSON payload where `repository.owner.login = "OrgOne"` but `repository.full_name = "OrgTwo/victim-repo"`.
3. Sign the raw body with `OrgOne`'s `webhook_secret` using `sha1=` + HMAC-SHA1, and POST it to `/github/webhooks` with header `X-Github-Event: push`.
4. `verify_signature` computes `repository_owner` as `"OrgOne"`, fetches `OrgOne`'s `GitHubApp`, and the signature validates successfully.
5. `create` dispatches the parsed payload to `Shipit::Webhooks.for_event('push')`; the push handler resolves `stacks` via `Repository.from_github_repo_name("OrgTwo/victim-repo")` and enqueues `GithubSyncJob` for a stack that belongs to `OrgTwo`, despite the request never being authenticated by `OrgTwo`'s secret.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
