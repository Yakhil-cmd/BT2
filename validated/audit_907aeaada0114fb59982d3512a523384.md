### Title
Unlocked concurrent read of `storage.assocUnstableUnits` / stability advancement during catch-up races with unit purging - ([File: network.js])

### Summary
`tryToAdvanceStabilityPointForCatchupAATrigger()` in `network.js` reads the shared in-memory cache `storage.assocUnstableUnits` and later invokes `main_chain.determineIfStableInLaterUnitsAndUpdateStableMcFlag()` — which mutates main-chain/stability state — entirely **without acquiring the `["write"]` or `["handleJoint"]` mutex** that every other path touching this cache (validation, `writer.saveJoint`, `joint_storage.purgeUncoveredNonserialJoints`, `storage.forgetUnit`) uses. [1](#0-0) 

### Finding Description
This mirrors the CVE-2021-47461 bug class: an operation reads/uses a shared, concurrently-managed structure (there, `mm`; here, `storage.assocUnstableUnits` and the stability/main-chain state) without first establishing exclusive/safe access, while a concurrent "cleanup" path (there, `exit_mmap()`; here, `writer.saveJoint` → `main_chain.advanceMcStability`, or `joint_storage.purgeUncoveredNonserialJointsUnderLock` → `storage.forgetUnit`) can mutate or remove the very same entries.

Concretely:
- `tryToAdvanceStabilityPointForCatchupAATrigger` is invoked from the `ifTransientError` handler of `handleJoint` when catching up and error is `"possible AA"` [2](#0-1) . Note this call happens *after* `unlock()` has already been scheduled via `process.nextTick(unlock)` [3](#0-2)  — i.e., the `handleJoint` mutex is being released concurrently with (or just before) this function running.
- Inside the function, `parent_unit` is selected by scanning `storage.assocUnstableUnits` without any lock [4](#0-3) .
- It then takes its *own* DB connection and calls `main_chain.determineIfStableInLaterUnitsAndUpdateStableMcFlag(conn, parent_unit, arrFreeUnits, false)` under `BEGIN`/`COMMIT` on that connection alone — again with no `mutex.lock(["write"])` [5](#0-4) .
- Meanwhile, the legitimate/expected callers of the stability machinery (`writer.js` `saveJoint`, `main_chain.advanceMcStability`) and the cache-purging paths run only under the `["write"]` lock, and `validation.js`'s stability-related logic executes under the `["handleJoint"]`/author-address locks [6](#0-5) . `joint_storage.purgeUncoveredNonserialJoints` explicitly takes the `["write"]` lock before mutating `assocUnstableUnits` via `storage.forgetUnit` [7](#0-6) .
- Because `tryToAdvanceStabilityPointForCatchupAATrigger` bypasses all of these locks, a concurrently running `saveJoint`/`advanceMcStability` (processing a different, real new unit while catching up) can simultaneously advance the main chain, insert/stabilize units, run AA triggers, and update `assocUnstableUnits`/`assocStableUnits`, while this function is mid-way through its own unlocked read of the cache and unlocked stability-advancement transaction on `parent_unit`. Both code paths write to `is_stable`/main-chain-index state and to the `assocUnstableUnits`/`assocStableUnits` caches that are asserted to be exact mirrors of DB content elsewhere (see the consistency check in `storage.readUnitProps`, which `throw`s if cache and DB disagree) [8](#0-7) .

### Impact Explanation
If two unlocked/locked stability-advancement operations interleave on the same node, the node's cached view of which units are stable/on-main-chain (`assocUnstableUnits`, `assocStableUnits`) can diverge from the DB-committed state, or `parent_unit`'s properties can be read/acted upon after another writer has already stabilized/forgotten it. `storage.readUnitProps` treats such cache/DB divergence as a fatal invariant violation and throws `"different props of ..."` [9](#0-8) , crashing the node process. A crash-inducing, remotely-triggerable race during catch-up on a full node is a concrete "node unable to confirm new units" / "node disagreement on validity or stability" outcome, matching the required impact classes.

### Likelihood Explanation
This path is only reachable while `bCatchingUp` is true and a peer sends a unit that triggers `"possible AA"` transient-error handling with a matching hash-tree ball — i.e., during normal catch-up from any connected peer, not requiring a malicious peer (a plain new unit arriving during catch-up is sufficient) [2](#0-1) . Because Node.js's single-threaded event loop still interleaves async DB callbacks, and this function explicitly runs in parallel with the main write/validation pipeline without any of the locks those pipelines rely on, the race window exists on every catch-up cycle where multiple units are in flight, which is common. The severity is limited by the fact that it manifests as a hard crash (fail-safe rather than silent fund loss), consistent with a Medium rating.

### Recommendation
Wrap `tryToAdvanceStabilityPointForCatchupAATrigger`'s read of `storage.assocUnstableUnits` and its call to `main_chain.determineIfStableInLaterUnitsAndUpdateStableMcFlag` inside `mutex.lock(["write"])` (the same lock used by `writer.saveJoint`/`main_chain.advanceMcStability` and by `joint_storage.purgeUncoveredNonserialJoints`), so that stability advancement and cache mutation are always serialized against the rest of the write path, analogous to using `mmget_not_zero()`-style safe-reference acquisition before touching a concurrently-managed resource.

### Proof of Concept
Not directly reproducible as a standalone script without a live two-node catch-up scenario and precise timing control; conceptually:
1. Node A is catching up (`bCatchingUp = true`).
2. Peer sends unit U2 whose ball matches a hash-tree ball, causing `ifTransientError("possible AA")` and invoking `tryToAdvanceStabilityPointForCatchupAATrigger(U2_joint)` unlocked [2](#0-1) .
3. Concurrently, a second unit U3 (a normal new joint, not necessarily malicious) is being validated/saved via `handleJoint` → `writer.saveJoint` → `main_chain.advanceMcStability`, which holds the `["write"]` lock and mutates `assocUnstableUnits`/`assocStableUnits`.
4. If step 2's read of `assocUnstableUnits[parent_unit]` and its subsequent `determineIfStableInLaterUnitsAndUpdateStableMcFlag` transaction interleave with step 3's cache/DB mutation, the invariant check in `storage.readUnitProps` (`different props of ...`) can trip on a subsequent read of the same unit, crashing the node [10](#0-9) .

// try to advance the stability point to an unstable on-MC parent, which might stabilize the actual AA trigger and let the retransmitted unit through
async function tryToAdvanceStabilityPointForCatchupAATrigger(objJoint){
	const objUnit = objJoint.unit;
	const unit = objUnit.unit;
	const ball = objJoint.ball;
	if (!ball || storage.assocHashTreeUnitsByBall[ball] !== unit)
		return;
	// the parent might not be known to us yet, hence not in assocUnstableUnits
	const parent_unit = objUnit.parent_units.find(parent_unit => {
		const props = storage.assocUnstableUnits[parent_unit];
		return props && props.is_on_main_chain && !props.is_stable;
	});
	if (!parent_unit)
		return;
	const arrFreeUnits = main_chain.getFreeUnits();
	console.log(`possible AA trigger for unit ${unit}: trying to advance the stability point to its MC parent ${parent_unit} using free units ${arrFreeUnits.join(', ')}`);
	// use a dedicated connection so that interleaving writes from other tasks don't interfere with this check
	const conn = await db.takeConnectionFromPool();
	await conn.query("BEGIN");
	const bStable = await main_chain.determineIfStableInLaterUnitsAndUpdateStableMcFlag(conn, parent_unit, arrFreeUnits, false);
	console.log(`AA parent ${parent_unit} stable in free units ${arrFreeUnits.join(', ')}? ${bStable}`);
	await conn.query("COMMIT");
	conn.release();
}
