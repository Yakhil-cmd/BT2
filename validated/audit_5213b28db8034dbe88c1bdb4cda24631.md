### Title
Webhook Signature Selects Organization Secret by Unverified Field While Handlers Act on a Different Unverified Field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
When Shipit is configured with multiple GitHub Apps/organizations (the documented multi-org setup), `WebhooksController#verify_signature` selects *which* organization's `webhook_secret` to validate the HMAC signature against by reading an unauthenticated field from the same untrusted request body (`repository.owner.login`/`organization.login`), while the downstream event handlers act on a *different* field of that same body (`repository.full_name`) to resolve the target `Repository`/`Stack`. Because these are two independent fields inside one JSON payload, and only the org named in the first field determines which secret is used to check the HMAC, an attacker who knows (or controls) the webhook secret for **any one** organization configured in the Shipit instance can forge a payload that authenticates as that organization but names a completely different organization/repository as the target to act upon.

### Finding Description
`verify_signature` computes `repository_owner` straight from the JSON body: [1](#0-0) 

and uses it only to pick which `GitHubApp`/secret to validate against: [2](#0-1) 

`Shipit.github(organization:)` maps this attacker-supplied organization name directly to a distinct secret configuration entry: [3](#0-2) 

The HMAC check itself only proves the raw body was signed with the secret belonging to the *organization named in `repository.owner.login`* — it does not bind that organization to the *repository that will actually be operated on*. That target repository is read from a **different** field, `repository.full_name`, by the base webhook `Handler` and specific handlers (e.g. `PushHandler`) to look up the `Repository`/`Stack`: [4](#0-3) [5](#0-4) 

`Repository.from_github_repo_name` resolves purely by owner/name string match against records already stored for any onboarded organization: [6](#0-5) 

**Broken binding (as an equality):** `organization authenticated (repository.owner.login used to pick the HMAC secret) == repository being written (repository.full_name used by the handler to select the Stack)`. Nothing enforces this equality. Docs confirm the supported multi-org topology where each org has its own independent `webhook_secret`: [7](#0-6) 

**Before the attack:** for an org `AttackerOrg` with a known/leaked `webhook_secret`, a legitimate webhook body has `repository.owner.login == "AttackerOrg"` and `repository.full_name == "AttackerOrg/some-repo"`, matching, and signature verification uses `AttackerOrg`'s secret correctly.

**After the attack:** attacker crafts `{"repository": {"owner": {"login": "AttackerOrg"}, "full_name": "VictimOrg/critical-repo"}, "ref": "refs/heads/master", "after": "<attacker-chosen sha>"}`, computes the HMAC using `AttackerOrg`'s known secret, and sends it with `X-Github-Event: push`. `verify_signature` looks up `AttackerOrg`'s config via `repository_owner` (`"AttackerOrg"`), validates the signature successfully, and the request proceeds. `PushHandler` then resolves `VictimOrg/critical-repo` via `repository.full_name` and triggers `stack.sync_github(expected_head_sha:)` for a Stack the attacker does not control.

### Impact Explanation
This can trigger an unauthorized sync/deploy trigger (`GithubSyncJob`) against another organization's Stack hosted on the same Shipit instance, purely by knowing the webhook secret of one org configured on that Shipit instance — a materially lower privilege than having push/admin access to the victim org's repository. This maps to "unauthorized deploy" territory (push events feed `sync_github`, which is a precursor to auto-deploy pipelines depending on stack configuration), qualifying as Critical/High per the listed impact criteria (unauthorized deploy / cross-repository writes analog).

### Likelihood Explanation
Requires only knowledge of one organization's `webhook_secret` value (which, per `docs/setup.md`, multiple independent GitHub App admins may hold in a shared multi-tenant Shipit deployment) — not any Shipit session, API token, or GitHub repository write access to the victim org. This is a realistic configuration (explicitly documented as supported) and the crafted payload requires no elevated access beyond that one secret.

### Recommendation
Bind the verified organization to the acted-upon repository: after signature verification, require `repository.owner.login` (or `organization.login`) to equal the owner portion of `repository.full_name` before dispatching to any handler, and reject the webhook otherwise. Alternatively, verify the signature against secrets for all configured organizations and only accept if the organization whose secret validated the signature matches the repository being targeted.

### Proof of Concept
1. Configure Shipit with two orgs, `AttackerOrg` (secret `S1`) and `VictimOrg` (secret `S2`), each with existing `Stack`s (per `docs/setup.md` multi-org format).
2. Attacker builds payload:
```json
{
  "ref": "refs/heads/master",
  "after": "deadbeefdeadbeefdeadbeefdeadbeefdeadbeef",
  "repository": { "owner": { "login": "AttackerOrg" }, "full_name": "VictimOrg/critical-repo" }
}
```
3. Compute `X-Hub-Signature: sha1=<hmac_sha1(S1, raw_body)>`.
4. POST to `/webhooks` with header `X-Github-Event: push`.
5. `WebhooksController#verify_signature` computes `repository_owner = "AttackerOrg"`, fetches `Shipit.github(organization: "AttackerOrg")`, and successfully validates the signature using `S1` (which the attacker legitimately possesses).
6. `PushHandler#process` resolves the target via `payload.dig('repository','full_name') == "VictimOrg/critical-repo"`, finds `VictimOrg`'s `Stack`, and calls `stack.sync_github(expected_head_sha: "deadbeef...")` — executed despite the attacker never having proven any relationship to `VictimOrg`.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

### Using Multiple Github Applications

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently. The top-level keys should be the name of each Github organization, and the following sub-keys are the Github app details for that particular organization.

For example:

```yml
production:
  github:
    somegithuborg:
      app_id:
      installation_id:
      webhook_secret:
      private_key:
      oauth:
        id:
        secret:
        teams:
    someothergithuborg:
      app_id:
      installation_id:
      webhook_secret:
      private_key:
      oauth:
        id:
        secret:
        teams:
```
