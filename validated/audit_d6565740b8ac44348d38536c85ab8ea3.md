None of the filesystem-path-construction code in the codebase is reachable from an attacker-controlled entry point as required by the analysis criteria. The instances found are all node-local, operator-controlled configuration/tooling paths, not paths built from remote/unprivileged input:

- `cumulus/client/consensus/aura/src/lib.rs` `export_pov_to_path` builds file names from `block_hash`/`block_number`, which are node-local values, not attacker-supplied strings, and the destination directory is an operator-configured CLI flag [1](#0-0) .
- `polkadot/node/service/src/workers.rs` resolves PVF worker binary paths from local filesystem locations and CLI-supplied `given_workers_path`, not from any extrinsic, XCM message, or proof payload [2](#0-1) .
- `substrate/client/hop/src/pool.rs` constructs paths from hash values and fixed directory constants, not user input [3](#0-2) .

The CVE-2009-4013 pattern requires attacker-controlled field names or values in a control file to be used directly in path construction. No such pattern exists in the Polkadot SDK runtime extrinsic dispatch, contract execution, or XCM message handling paths.
