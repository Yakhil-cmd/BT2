**Rationale:**

CVE-2021-29922 is a defect in Rust's standard library IPv4 string parser (`library/std/src/net/parser.rs`) that treated leading zeros in octets as octal, fixed upstream in Rust 1.53 (rust-lang/rust#83652). This is a toolchain/dependency-level issue, not application logic that Polkadot SDK authors wrote.

Searching the codebase for IP-address parsing and IP-based access control turned up only usages of Rust's `std::net::IpAddr::from_str` / `SocketAddr::parse` and the external `ip_network` crate, e.g.:
- RPC proxy-header IP extraction and CORS/rate-limit whitelisting in `substrate/client/rpc-servers/src/utils.rs` [1](#0-0) 
- RPC endpoint listen address / whitelisted-IP CLI parsing in `substrate/client/cli/src/params/rpc_params.rs` [2](#0-1) 
- Multiaddr `/ip4/.../ip6/...` protocol parsing in `substrate/client/network/types/src/multiaddr/protocol.rs`, which stores `Ipv4Addr`/`Ipv6Addr` typed values rather than re-implementing octet parsing [3](#0-2) 

None of these implement a custom IPv4/IPv6 octet parser; they all delegate directly to the Rust standard library's `FromStr` implementation for `IpAddr`/`Ipv4Addr`/`SocketAddr`, which has been fixed since Rust 1.53 in any toolchain capable of building this codebase's current edition/dependencies. There is no FRAME pallet, XCM executor, or contracts/revive code path that parses attacker-supplied IP address strings as part of consensus-critical access control reachable via a signed extrinsic, XCM message, or contract call — all IP parsing found is client/node-side networking and RPC-server configuration, which is not reachable by an unprivileged extrinsic-signing attacker as required by the scan's entry-point criteria.

Per the scan's exclusion rules, dependency-only/toolchain-only issues without a demonstrable Polkadot SDK application-logic analog reachable through a real user entry point are not reportable.
