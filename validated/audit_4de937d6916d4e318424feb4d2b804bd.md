### Title
AA-received `cosigned_by_definer` assets become permanently frozen because AA response/bounce units are always single-authored - ([File: aa_composer.js])

### Summary
Every AA response unit, including the built-in bounce/refund unit, is authored solely by the AA address itself. Asset validation requires that any payment of an asset with `cosigned_by_definer:true` be co-signed by the asset's definer as one of the unit's authors. Since an AA can never add a second author/signature to its own generated units, an AA can never legally forward, spend, or bounce back such an asset once it has received it. This is the ocore-native analog of the BGT report: a token whose transfer requires an "approved sender" causes downstream transfer/refund logic to fail and strands the funds in the receiving contract with no recovery path.

### Finding Description
Any asset can be defined with `cosigned_by_definer: true`, requiring the definer address to be present among `arrAuthorAddresses` for every transfer of that asset: [1](#0-0) 
This check is unconditionally applied in `validatePaymentInputsAndOutputs`/`validatePayment`, with no special carve-out for AA-authored units.

Separately, `aa_validation.js` only forbids an AA from *defining* an asset with `cosigned_by_definer !== false` for assets the AA itself issues: [2](#0-1) 
This restriction only applies to assets created via an `asset` message inside the AA's own template - it does nothing to stop a third party from defining an unrelated asset with `cosigned_by_definer:true` and later sending that asset into any existing AA as ordinary trigger-payment output.

When an AA composes any outgoing unit (a normal response payment or the automatic bounce/refund payment), the resulting unit always has exactly one author - the AA itself: [3](#0-2) 
There is no mechanism for the AA to add the definer as a co-author, since AA execution is fully deterministic and non-interactive.

The built-in bounce mechanism, triggered whenever the AA's response formula fails or bounces for any reason, tries to refund every non-base asset the trigger sent, including a `cosigned_by_definer` asset, back to `trigger.address`: [4](#0-3) 
That refund message goes through the same `sendUnit` → `validateAndSaveUnit` pipeline, which will fail the `cosigned_by_definer` check in `validation.js` since the response unit only has the AA as author. This causes `bounce(err)` to be invoked a second time: [5](#0-4) 
Because `bBouncing` is already `true` on the second call, the function immediately returns `finish(null)` - no unit is created, no error is surfaced to the trigger sender, and none of the trigger's assets (including the base currency that was meant to be refunded) are returned. The original trigger unit that funded the AA is already stable on the DAG, so the funds are permanently recorded as part of the AA's balance with no code path that can ever release them.

### Impact Explanation
This is a protocol-level "AA fund loss/freezing" bug: any user who sends a `cosigned_by_definer` asset (plus bytes) to any AA on the network - whether by mistake, by a malicious asset issuer intentionally probing AAs, or simply through an AA path that naturally bounces - causes that asset (and any bytes bundled in the same trigger) to become irrecoverably stuck in the AA's balance. No error, refund, or response unit is ever produced, silently violating the fundamental guarantee that a bounced AA trigger returns the sender's funds.

### Likelihood Explanation
Likelihood is Medium: the attacker (or an ordinary user) must (1) define an asset with `cosigned_by_definer:true` - a single unprivileged `asset` message any address can post, and (2) cause a trigger to that AA to bounce while carrying that asset (e.g. sending too little base currency, invalid trigger data, or any condition the target AA already bounces on). Both steps are fully reachable by an unprivileged asset issuer / AA trigger sender with no special access.

### Recommendation
Either forbid AAs (and the AA response/bounce pipeline) from ever accepting `cosigned_by_definer` assets as valid trigger inputs, or have `validatePaymentInputsAndOutputs`/`aa_composer.js` treat delivery of such an asset to an AA address as invalid at the trigger-validation stage (reject the trigger unit rather than silently swallowing the funds after acceptance). Alternatively, exempt AA-authored bounce/refund payments from the `cosigned_by_definer` requirement, since the AA cannot ever satisfy it, and ensure `bounce()` still creates a base-currency-only refund unit even when an asset-inclusive refund message fails validation, instead of aborting entirely via `finish(null)`.

### Proof of Concept
1. Attacker posts an `asset` definition unit with `cosigned_by_definer:true`, `is_transferrable:true`, definer = attacker's own address `D`.
2. Attacker sends a trigger unit to any existing AA `X` (not co-authored by `D`... which is guaranteed since the AA can never co-author), including in the trigger's outputs: some bytes and an amount of the `cosigned_by_definer` asset, crafted so the AA's response logic bounces (e.g., insufficient bytes for the AA's intended action, or malformed `trigger.data`).
3. `handleTrigger` in `aa_composer.js` evaluates the AA template, hits an error/no-messages condition, and calls `bounce(error)`.
4. `bounce()` builds a refund message for the asset (`{app:'payment', payload:{asset: <asset>, outputs:[{address: trigger.address, amount: ...}]}}`) and calls `sendUnit(messages)`.
5. `sendUnit` reaches `validateAndSaveUnit`, which invokes `validatePayment` → fails at `validation.js:2112-2113` because the response unit's sole author is AA `X`, not definer `D`.
6. `validateAndSaveUnit`'s error triggers `bounce(err)` again; `bBouncing` is already `true`, so `finish(null)` is returned immediately.
7. No response unit is created, no funds (neither the asset nor the accompanying bytes) are ever returned to the attacker/trigger sender; they remain permanently attributed to AA `X`'s balance, unreachable by any subsequent AA logic that isn't specifically aware of this asset.
