### Title
Webhook signature verification key is selected using an attacker-controlled organization field that is decoupled from the repository/team actually mutated by the event handler - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` picks the HMAC secret to validate `X-Hub-Signature` against based on `repository_owner`, a value read straight out of the *unverified* JSON body (`params.dig('repository','owner','login')` or `params.dig('organization','login')`). The event handlers that subsequently mutate state resolve their target independently from other fields of that same unverified body (`repository.full_name`, `organization.login`/`team`), so the organization whose secret is checked and the resource that is actually written are not provably the same entity.

### Finding Description
`verify_signature` does:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) 

`repository_owner` is taken from the raw, unauthenticated request body before any signature has been checked, and it is used purely to pick *which* configured GitHub App's `webhook_secret` to HMAC against:
```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
``` [2](#0-1) 

Note `verify_webhook_signature` trivially returns `true` when the resolved app has no `webhook_secret` configured (`webhook_secret: # nil` is shown as a valid, common config in the docs and example secrets files) [3](#0-2) . In a multi-organization deployment (`github: {org1: {...}, org2: {...}}`), `Shipit.github(organization: repository_owner)` resolves to a distinct `GitHubApp` instance per organization key [4](#0-3) .

Once signature verification passes (or is trivially skipped because the *chosen* organization has no secret), the actual handler dispatch is:
```ruby
def create
  params = JSON.parse(request.raw_post)
  Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }
  head(:ok)
end
```
The handler resolves its target repository from a *different* field of the same untrusted payload:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [5](#0-4) 

and `Repository.from_github_repo_name` splits `owner/name` straight from that field with no cross-check against `repository_owner`/`organization.login` used for the signature lookup:
```ruby
def self.from_github_repo_name(github_repo_name)
  repo_owner, repo_name = github_repo_name.downcase.split('/')
  find_by(owner: repo_owner, name: repo_name)
end
``` [6](#0-5) 

For the `membership` event, the binding break is even more sensitive: `MembershipHandler` creates/looks up a `Team` and adds/removes a `User` from it purely from unauthenticated payload fields (`params.organization.login`, `params.team.id`, `params.member.login`), and team membership is exactly what `User#authorized?` checks against `Shipit.github_teams` to gate access to the whole app:
```ruby
def process
  team = find_or_create_team!
  member = User.find_or_create_by_login!(params.member.login)
  case params.action
  when 'added' then team.add_member(member)
  when 'removed' then team.members.delete(member)
  ...
end
``` [7](#0-6) 
```ruby
def authorized?
  @authorized ||= Shipit.github_teams.empty? || teams.where(id: Shipit.github_teams.map(&:id)).exists?
end
``` [8](#0-7) 

The binding that should hold is: *organization whose `webhook_secret` authenticates the request* == *organization/repository the handler mutates*. Because both sides of that equality are read from the same unauthenticated JSON body but from independent keys (`repository.owner.login`/`organization.login` for auth-selection vs. `repository.full_name`/`organization.login`+`team.id` for the mutation target), an attacker who controls only the payload of an organization configured with a blank/missing `webhook_secret` can make `verify_signature` succeed for "their" org while the handler acts on a `Repository`/`Team` belonging to a *different*, secret-protected organization in the same multi-org deployment.

### Impact Explanation
If an operator runs Shipit in multi-organization mode (`config/secrets.yml` with a `github:` hash keyed by multiple orgs, as documented in `config/secrets.development.example.yml`) and any one configured organization has no `webhook_secret` set (a state the example config explicitly allows via `webhook_secret: # nil`), an unauthenticated attacker can:
- Trigger `PushHandler`/`CheckSuiteHandler`/`StatusHandler` side effects (`stack.sync_github`, commit status writes) against repositories that belong to a *different*, secret-protected organization, by setting `repository.owner.login` to the org with no secret while setting `repository.full_name` to `secured-org/real-repo`.
- More critically, forge a `membership` webhook to add an arbitrary GitHub login into a `Team` whose `github_id`/`organization` matches one of `Shipit.github_teams`, which is the exact authorization gate in `Shipit::Authentication#force_github_authentication` → `User#authorized?`. This is a direct escalation into `Shipit.github_teams` authorization, letting the attacker grant themselves (or any account) access to a Shipit instance without possessing any org's real webhook secret.

This matches the accepted High-severity class: "escalation into `Shipit.github_teams` authorization."

### Likelihood Explanation
Requires: (1) a multi-organization Shipit deployment, and (2) at least one configured organization lacking a `webhook_secret`. Both conditions are explicitly presented as supported, ordinary configuration in the engine's own example secrets files and setup docs, so this is a realistic, not merely theoretical, misconfiguration surface that the engine's own signature-selection logic makes exploitable rather than a defense-in-depth failure purely on the operator's side — the code path (`repository_owner` picking the verification key independently of what the handler later writes) is what turns a "missing secret on one org" into a cross-organization forgery, rather than only affecting that one unsecured org's own data.

### Recommendation
Do not let the payload determine which secret validates itself. Verify the signature against the union of all configured organizations' secrets (or, better, require every configured organization to have a non-blank `webhook_secret`, and reject requests where no configured secret validates the raw body). Additionally, after signature verification, re-derive the acting organization from the *same* trusted field used for verification and assert it matches the organization implied by `repository.full_name` / `team.organization` before dispatching to handlers, so a payload cannot authenticate as org A while mutating org B's `Repository` or `Team` records.

### Proof of Concept
Given `secrets.yml`:
```yaml
github:
  secure-org:
    webhook_secret: real-secret
  open-org:
    webhook_secret:   # left blank/nil by mistake
```
1. Attacker POSTs to `/github_webhooks` (webhook endpoint) with header `X-Github-Event: membership` and body:
```json
{
  "action": "added",
  "team": { "id": 999, "name": "Deployers", "slug": "deployers", "url": "https://x" },
  "organization": { "login": "open-org" },
  "member": { "login": "attacker-handle" }
}
```
with no valid `X-Hub-Signature` header (or any garbage value).
2. `WebhooksController#verify_signature` computes `repository_owner` = `"open-org"`, resolves `Shipit.github(organization: "open-org")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` unconditionally [9](#0-8) , and the request is accepted.
3. `MembershipHandler#process` runs, calling `find_or_create_team!` with `github_id: 999`. If `999` happens to coincide with (or the attacker iterates/guesses) the `github_id` of a `Team` referenced in `Shipit.github_teams` for the operator's actual authorization policy, `team.add_member(User.find_or_create_by_login!("attacker-handle"))` grants that login membership in an authorization-gating team [10](#0-9) .
4. Attacker then completes normal GitHub OAuth login as `attacker-handle`; `User#authorized?` now returns true because `teams` includes a `Shipit.github_teams` entry, bypassing the organization-team authorization check entirely without ever knowing `secure-org`'s or any org's real `webhook_secret` [8](#0-7) [11](#0-10) .

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
