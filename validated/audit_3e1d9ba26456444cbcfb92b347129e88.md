### Title
Cross-repository forged commit status via unscoped `Commit.where(sha:)` lookup in `StatusHandler` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`WebhooksController#verify_signature` authenticates an inbound `status` webhook against the `webhook_secret` belonging to the GitHub organization named in the payload's `repository.owner.login` (or `organization.login`) field. This establishes the binding `authenticated_org(payload) == owner_of(repository_in_payload)`. However, `Shipit::Webhooks::Handlers::StatusHandler#process` never re-checks the `repository` field: it looks up commits with `Commit.where(sha: params.sha)` across the **entire database**, unscoped to any stack or repository. Because `sha` is not globally unique in the schema (it is indexed per `stack_id`, not uniquely), any two stacks that share commit history (forks, mirrors, or upstream/downstream repos) can contain rows with an identical `sha`. An attacker who merely owns a repository configured in the same Shipit instance can trigger a genuinely GitHub-signed `status` event for a commit SHA that also exists in a victim stack, and have Shipit apply the forged status to the victim's commit.

### Finding Description
Signature verification is performed once, keyed off attacker-controlled payload data, and only binds "this payload is authentic for organization X": [1](#0-0) [2](#0-1) 

That binding is never enforced again when the event is actually applied. The generic `Handler` base class defines a repository-scoped `stacks` helper based on `repository.full_name`: [3](#0-2) 

`CheckSuiteHandler` correctly uses this scoping (`stacks.where(branch: ...)`): [4](#0-3) 

But `StatusHandler` bypasses this scoping entirely and queries commits globally by SHA, with no `repository` field required or used in its parameter schema: [5](#0-4) 

The `sha` column is indexed together with `stack_id` (not as a globally unique key), confirmed by the migration name `index_commits_on_stack_id_and_sha`, meaning the schema explicitly anticipates multiple stacks holding commit rows with the same SHA (e.g., forks/mirrors of the same upstream history). `Commit#create_status_from_github!` then persists whatever status the attacker sent, without any additional ownership check: [6](#0-5) 

**Binding broken:** `authenticated_org(payload) == owner_of(repository_written)`. The webhook signature only proves the sender controls the org named in the payload; the handler instead writes to any commit sharing the SHA, regardless of which org/stack that commit actually belongs to.

### Impact Explanation
An attacker who controls (or forks) a repository tracked by any Stack in the Shipit instance can:
1. Configure/own a repo (e.g., a public fork of the victim's repository) that shares commit history/SHAs with a victim stack's tracked repository.
2. Cause GitHub to deliver a genuinely-signed `status` webhook for their own org (this requires no secret knowledge — GitHub signs it with the legitimate `webhook_secret` for the attacker's own org/app installation) for a shared commit SHA, with an attacker-chosen `state` (e.g., `success`), `context`, and `description`.
3. `WebhooksController#verify_signature` accepts it because it is a real, correctly-signed webhook for the attacker's own organization.
4. `StatusHandler#process` matches the commit by SHA across the entire DB and writes a forged `success` status onto the victim's commit row via `create_status_from_github!`.

If the victim stack's deploy/merge gating depends on commit statuses (CI status checks consumed for `deployable?`/merge-queue decisions), this allows an unprivileged outsider to inject a fabricated passing status onto a commit they do not control, potentially enabling an unauthorized deploy or merge in a repository/stack they have no write access to — a cross-repository write via confused-deputy signature scoping, matching the "authenticated organization vs. repository written" trust-binding class from the report.

### Likelihood Explanation
Exploitability depends on the attacker being able to produce or predict a commit SHA collision with a target stack — trivially achievable via a public fork sharing pre-fork commit history, or any downstream/upstream mirror relationship, both very common setups for open-source or internally-mirrored repositories monitored by the same Shipit instance. No secrets, tokens, or privileged accounts are required — only a normal GitHub account with push access to any repo whose org is configured/installed for this Shipit instance.

### Recommendation
Scope `StatusHandler#process` (and any other handler doing unscoped lookups) to the repository asserted in the payload, exactly like `CheckSuiteHandler` does via `stacks`/`repository_name`, e.g. `stacks.commits.where(sha: params.sha)`, so that the organization authenticated by `verify_signature` and the stack/repository actually written to are provably the same entity. Require and validate the `repository.full_name` field in `StatusHandler`'s parameter schema and reject events where it does not resolve to a repository from which the signature-selected organization is authoritative.

### Proof of Concept
1. Attacker forks/mirrors a public repository that is also tracked as a Stack (`victim-org/app`) in the target Shipit instance, creating `attacker-org/app-fork` which shares historical commit SHAs.
2. Attacker's own GitHub App/organization (`attacker-org`) is a separate, legitimately configured organization in this multi-org Shipit deployment (or attacker simply has a repo under an org already installed on Shipit).
3. Any GitHub event that causes a `status` webhook to fire for `attacker-org/app-fork` at a shared commit SHA (e.g., via CI configured on the attacker's fork, or by directly using the GitHub Status API on their own repo/commit) is delivered to `/webhooks`, signed with `attacker-org`'s real `webhook_secret`.
4. `WebhooksController#verify_signature` passes because the signature is valid for `attacker-org`.
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)` and matches the row belonging to `victim-org/app`'s stack (same SHA, different stack), calling `create_status_from_github!` with attacker-supplied `state: 'success'`, `context`, and `description`.
6. The victim stack's commit now shows a forged passing status it never legitimately received, usable to satisfy deploy/merge gating that depends on commit status checks.
