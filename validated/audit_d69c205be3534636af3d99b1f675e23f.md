### Title
Cross-tenant status forgery via unscoped `Commit.where(sha:)` in StatusHandler#process - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits to attach a GitHub `status` webhook to using only `Commit.where(sha: params.sha)`, with no filter on the repository/stack that the webhook signature actually authenticated. Any `Commit` row in any stack sharing that sha receives the forged status, which can flip `MergeRequest#all_status_checks_passed?` to true for a victim stack whose merge request head commit happens to share a sha with a commit visible in an attacker-controlled repository.

### Finding Description
The broken binding: `commit.stack_id` (the stack that gets the new `Status` row) must equal `repository_owner`/`params.dig('repository','full_name')` (the repository whose webhook signature was actually verified) — this does not hold.

Code path:
- `WebhooksController#verify_signature` verifies the payload's HMAC against `Shipit.github(organization: repository_owner)`, i.e. it only proves the payload was signed with the secret belonging to *the organization named in the payload* [1](#0-0) . It never binds the sha inside the payload to that organization/repository.
- `StatusHandler#process` then does:
```
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
```
with no scoping by stack or repository at all [2](#0-1) .
- `Commit#create_status_from_github!` writes the status using the *matched commit's own* `stack_id`, not any stack derived from the webhook payload: `statuses.replicate_from_github!(stack_id, github_status)` [3](#0-2) , and `Status.replicate_from_github!` persists `context`/`state` verbatim from the untrusted payload [4](#0-3) .
- `Commit` rows are not deduplicated globally by sha; each is `belongs_to :stack` and created per-stack via `stack.commits.by_sha` / `stack.commits.create_from_github!` [5](#0-4) [6](#0-5) . So two different stacks can legitimately hold `Commit` rows with an identical sha (e.g. a shared upstream/base commit that exists verbatim in both a victim repo's history and an attacker-controlled fork/repo), yet `StatusHandler` treats them as one target.
- `MergeRequest#all_status_checks_passed?` then trusts whatever `Status` rows exist on `head` regardless of which repository produced them: `StatusChecker.new(head, head.statuses_and_check_runs, stack.cached_deploy_spec).success?` [7](#0-6) .

Attacker flow: the attacker owns a repository with a Shipit webhook already configured (their own stack in the same multi-tenant Shipit instance, or a fork sharing history with the victim repo). They push/trigger a commit `status` event with `context` equal to the victim's `merge_request_required_statuses` entry (e.g. `ci/circle`) and `state: success`, on a sha that is also present as `head` (or an ancestor commit) of a `Commit` row belonging to the victim's stack. The webhook signature check passes because it only validates the attacker's own organization's secret, not any relationship to the victim's repository or sha. `StatusHandler#process`'s unscoped `Commit.where(sha:)` then writes a matching `Status` onto the victim's commit, and `all_status_checks_passed?` can flip to true, enabling `MergeRequest#merge!` to proceed against the victim's repository.

No existing guard stops this: `verify_signature` only checks org-level HMAC, not sha ownership; `drop_unhandled_event` and the `ExplicitParameters` schema for `StatusHandler` only validate shape (`sha`, `state`, `context` types), not cross-repo scoping [8](#0-7) ; there is no `Repository`/stack membership check anywhere in this handler.

### Impact Explanation
A successful forged status causes `MergeRequest#all_status_checks_passed?` to become true for a merge request that never received the real CI signal from its own repository, allowing `MergeRequest#merge!` to invoke `stack.github_api.merge_pull_request` against the victim repository/branch [9](#0-8) . This is an unauthorized merge into a repository that never authenticated the satisfying check — matching the Critical category "a payload for one repository mutating another's stack/commit/task/team, or an unauthorized deploy/rollback/merge." It is repeatable against any stack whose merge-queue required-status context is known (often public, e.g. `ci/circle`) and whose merge request head/ancestor sha collides with a commit visible to the attacker.

### Likelihood Explanation
Requires: (1) the attacker to control a repository with a valid, already-configured Shipit webhook (their own stack/org, or a shared-history fork of the victim repo), (2) knowledge of the victim's exact required status context string from `deploy_spec.merge_request_required_statuses` (commonly documented/public CI names), and (3) a sha shared between a commit in the attacker's reachable repository and a `Commit` row already persisted for the victim's stack (base/ancestor commits shared via forks or shared upstream history are a realistic, non-cryptographic way to obtain this — no SHA1 collision break is required, only ordinary git history sharing). Given these are plausible in real multi-tenant Shipit deployments where many teams/orgs share this instance and repos fork from common upstreams, likelihood is Medium, gated mainly by knowing the required-status context and the coincidence of a shared commit being present in the victim stack's tracked commit set.

### Recommendation
Scope `StatusHandler#process` (and `Commit#create_status_from_github!`/`Status.replicate_from_github!`) by the repository asserted in the verified webhook payload, not merely by sha: e.g. filter `Commit.where(sha: params.sha)` down to commits whose `stack.repository.full_name` (or `github_repo_name`) matches `params.repository.full_name`, rejecting/ignoring statuses for commits belonging to a different repository than the one whose signature was verified.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb (conceptual)
test "status webhook can forge a required status for an unrelated stack sharing a commit sha" do
  victim_stack = shipit_stacks(:shipit)
  attacker_stack = shipit_stacks(:cyclimse) # a different repo/stack in the same instance

  shared_sha = "deadbeef" * 5

  victim_commit = victim_stack.commits.create!(sha: shared_sha, author: shipit_users(:walrus),
    committer: shipit_users(:walrus), authored_at: Time.now, committed_at: Time.now)
  attacker_commit = attacker_stack.commits.create!(sha: shared_sha, author: shipit_users(:walrus),
    committer: shipit_users(:walrus), authored_at: Time.now, committed_at: Time.now)

  merge_request = shipit_merge_requests(:shipit_pending) # belongs to victim_stack
  merge_request.update!(head: victim_commit)
  victim_stack.cached_deploy_spec.stubs(:merge_request_required_statuses).returns(['ci/circle'])

  refute merge_request.all_status_checks_passed?

  # Attacker-signed webhook (their own org secret), payload references only sha, not repo scoping
  params = Shipit::Webhooks::Handlers::StatusHandler::Params.new(
    sha: shared_sha, state: 'success', context: 'ci/circle', created_at: Time.now.to_s
  )
  Shipit::Webhooks::Handlers::StatusHandler.new(params).process

  assert victim_commit.reload.statuses.exists?(context: 'ci/circle', state: 'success')
  assert merge_request.reload.all_status_checks_passed?, "forged status from attacker repo satisfied victim's required check"
end
```
This demonstrates `commit_row_for(victim_stack, shared_sha).stack_id == attacker_stack.id`'s absence of check: the write lands on `victim_commit` purely because `Commit.where(sha:)` is unscoped, satisfying `merge_request.all_status_checks_passed?` without any status ever having been produced for the victim's own repository.
