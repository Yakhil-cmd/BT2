### Title
CCMenu API endpoint bypasses per-stack ApiClient scoping, allowing cross-stack status reads - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::Api::BaseController` enforces that a stack-scoped `ApiClient` (one created with a specific `stack_id`) can only resolve stacks through the `stacks` relation, which is filtered to that single stack. `Shipit::Api::CCMenuController` overrides the `stack` accessor to bypass that relation entirely, breaking the binding between "the stack a token authorizes" and "the stack the endpoint actually returns."

### Finding Description
In `app/controllers/shipit/api/base_controller.rb`, the scoping is implemented as: [1](#0-0) 

`stacks` restricts the queryable set to `Stack.where(id: current_api_client.stack_id)` when the client is scoped (`stack_id?`), and `stack` resolves `params[:stack_id]` only within that restricted relation. This is the mechanism that is supposed to guarantee "the stack a token authorizes == the stack it can touch."

`Api::CCMenuController` does not use this mechanism. It defines its own `stack` method that queries the global `Stack` model directly: [2](#0-1) 

`require_permission :read, :stack` (declared at line 6 of the same file) only checks that the `ApiClient` has the `read:stack` permission bit via `ApiClient#check_permissions!`; it performs no per-stack scope check: [3](#0-2) 

So any `ApiClient` that (a) has the `read:stack` permission and (b) is scoped to a specific `stack_id` — a supported configuration exercised by the `here_come_the_walrus` fixture — can call `GET /api/:stack_id/cc.xml?token=...` with an *arbitrary* `stack_id` and successfully render that other stack's CCMenu status, because `CCMenuController#stack` never consults `current_api_client.stack_id`.

Concretely:
- Equality that should hold: `token.authorized_stack == stack_rendered_by_endpoint`.
- Before the attack: a legitimate stack-scoped token (e.g. distributed via `CCMenuUrlController#fetch`, see below) is only expected to read the one stack it was minted for.
- After the attack: the same token, presented with a different `stack_id` parameter, reads an unrelated stack's build/deploy state — the binding is broken.

This is exactly analogous to the reported `split_off_older_than` bug class: a boundary/scope check is computed (`stacks` / `stack_id`) but the code path that actually returns data (`CCMenuController#stack`) uses the *other* side of the split (the unfiltered `Stack` relation) instead of the intended scoped one.

### Impact Explanation
This allows an attacker holding any single-stack-scoped, `read:stack`-permissioned API token to read the build/deploy status of stacks it was never granted access to — i.e., unauthorized read of stack state across stack/security boundaries. Per the rules this is a High-impact finding ("escalation into authorization scope... unauthenticated/unauthorized read of stack state, task streams or deploy output"). The exposed data (via `app/views/shipit/ccmenu/project` template) includes stack name, last build label/sha, lock/failure status and web URL for the targeted stack — none of which the token holder is supposed to be able to see.

### Likelihood Explanation
Likelihood is high for anyone who already legitimately holds one scoped `ApiClient` token (a normal, unprivileged capability — CCMenu tokens are explicitly designed to be embedded in third-party dashboard tools, i.e., handed to lower-trust consumers). No additional privilege, write access, or session is required — only substituting the `stack_id` route/query parameter is needed.

### Recommendation
Make `Api::CCMenuController#stack` resolve stacks through the inherited, scoped `stacks` relation (i.e., `stacks.from_param!(params[:stack_id])`) instead of `Stack.from_param!`, so per-token stack scoping is enforced consistently across all API controllers.

### Proof of Concept
1. As an authorized Shipit user, create (or have the app create via `CCMenuUrlController#fetch`) an `ApiClient` scoped to Stack A with `permissions: ['read:stack']` and `stack_id: A.id` (mirrors fixture `here_come_the_walrus`, scoped to stack `shipit`, in [4](#0-3) ).
2. Obtain that client's `authentication_token`.
3. Send `GET /api/<Stack-B-param>/cc.xml?token=<token>` where Stack B is any other stack in the installation.
4. Observe a `200 OK` response rendering Stack B's build/deploy status (name, lastBuildStatus, lastBuildLabel, webUrl), even though the token is only supposed to authorize Stack A — because `CCMenuController#stack` ( [5](#0-4) ) never applies the `current_api_client.stack_id` restriction that `BaseController#stacks` ( [6](#0-5) ) would normally enforce.
