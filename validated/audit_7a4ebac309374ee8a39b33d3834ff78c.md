### Title
Unauthenticated GitHub webhook event forgery leading to unauthorized deploys when `webhook_secret` is unset - ([File: lib/shipit/github_app.rb])

### Summary
`GitHubApp#verify_webhook_signature` treats an absent `webhook_secret` as "signature always valid," so `WebhooksController#verify_signature` performs no cryptographic check at all in that configuration. Since `webhook_secret` is optional/`nil` in every shipped configuration template, and the controller derives which app config (and hence which secret) to check against directly from the unauthenticated payload, an unprivileged network attacker can post arbitrary, unsigned JSON bodies to `/github/webhooks` and have them fully trusted and acted upon by `push`, `status`, `check_suite`, and `membership` handlers — including forcing `GithubSyncJob`/`sync_github` on arbitrary stacks, which can trigger continuous deployment.

### Finding Description
`WebhooksController#verify_signature` resolves the org from the raw JSON body and asks that org's `GitHubApp` instance to verify the `X-Hub-Signature` header against the raw payload: [1](#0-0) [1](#0-0) 

```
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
```

`repository_owner` is read straight out of the untrusted JSON payload: [2](#0-1) 

The actual signature check is: [3](#0-2) 

```
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
```

If the resolved organization's `webhook_secret` is not configured, this method unconditionally returns `true`, regardless of the (possibly absent or garbage) `X-Hub-Signature` header, so the "verified" binding between "GitHub-authenticated organization" and "the payload the app is about to act on" collapses entirely.

`webhook_secret` being unset is not an edge case — it is the value shipped in every configuration template and doc example, e.g.: [4](#0-3) [5](#0-4) 

Once past `verify_signature`, the raw JSON is dispatched by declared event handlers with no further authentication: [6](#0-5) 

For example, `PushHandler` uses attacker-supplied `ref`/`after` to force `sync_github` on any matching stack: [7](#0-6) 

And `ContinuousDeliveryJob` will deploy a stack automatically once it observes a new synced/green commit if continuous deployment is enabled: [8](#0-7) 

`StatusHandler` similarly lets an attacker write arbitrary CI status onto any known commit sha, which can gate/trigger continuous deployment: [9](#0-8) 

`MembershipHandler` lets an attacker create/modify `Team` and `User` records and toggle membership, since `Shipit.github_teams` gates authorization (`authorized?` in `app/models/shipit/user.rb` lines 80-82) based on `Membership` records that this unauthenticated handler can freely rewrite.

### Impact Explanation
This breaks the binding "GitHub organization that authenticated the webhook" == "repository/commit/state that is actually acted on by handlers." With no real signature check, any unprivileged network client can:
- Force out-of-band `GithubSyncJob`/`trigger_continuous_delivery` runs, leading to **unauthorized deploys** of arbitrary synced commits (Critical, matches "unauthorized deploy" in the accepted impact list).
- Forge commit statuses via `StatusHandler`, manipulating deploy/merge gating logic (`Commit#create_status_from_github!`).
- Forge `membership` events to add/remove arbitrary GitHub logins from `Team`s used by `Shipit.github_teams` authorization, potentially escalating a GitHub identity into `Shipit.github_teams` authorization (High, explicitly listed).

### Likelihood Explanation
High for any deployment run with the documented/default configuration (no `webhook_secret` set) — which is the norm across every shipped `secrets*.yml`/`secrets*.json` template in this repo. No credentials, tokens, or prior access are required; the attacker only needs the public webhook URL and knowledge of a configured organization login (visible in error responses / configuration, or guessable), which is used only to select which `GitHubApp` instance to call — the signature check itself is a no-op when unconfigured.

### Recommendation
- Do not treat a missing `webhook_secret` as "verification passed." Either require `webhook_secret` to be present for every configured organization (fail closed at boot/config-load time), or explicitly reject requests when no secret is configured instead of returning `true`.
- Avoid deriving the trust boundary (`repository_owner`) purely from unauthenticated payload content before any cryptographic verification has occurred; validate signature first against a secret bound to routing/config, not to attacker-controlled JSON.

### Proof of Concept
1. Deploy Shipit with a config matching the shipped templates (`webhook_secret` unset for the target org), e.g. `config/secrets.development.example.yml`.
2. As an anonymous attacker, `POST /github/webhooks` with header `X-Github-Event: push`, no valid `X-Hub-Signature` (or any garbage value), and body:
```json
{ "ref": "refs/heads/master", "after": "<arbitrary_sha_known_to_exist_in_repo>", "repository": {"owner": {"login": "<target-org>"}, "full_name": "target-org/target-repo"} }
```
3. `verify_signature` calls `verify_webhook_signature(garbage, raw_post)`, which returns `true` because `webhook_secret` is `nil` for `target-org`.
4. `PushHandler#process` runs unauthenticated, invoking `stack.sync_github(expected_head_sha: ...)` on every non-archived stack on that branch, potentially cascading into `ContinuousDeliveryJob#perform` and an unauthorized deploy.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
