## Confirmed: cross-organization webhook forgery in `Shipit::WebhooksController#verify_signature`

Excellent — the `StatusHandler#process` finding confirms the exploit path: `Commit.where(sha: params.sha)` matches **globally by SHA across all stacks/repositories**, with no re-check that the commit's owning repository/organization matches the organization whose secret verified the request signature.

### Title
Cross-organization webhook forgery via `repository.owner.login` / `repository.full_name` mismatch bypasses per-organization webhook signing - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which organization's HMAC secret to validate against using `repository_owner`, taken from the same JSON body the attacker fully controls (`params.dig('repository','owner','login')` or `params.dig('organization','login')`), then verifies the *entire raw body* against that org's secret. Downstream `Handler` subclasses (e.g. `StatusHandler`, `PushHandler`, membership/pull-request handlers) act on a *different* field of that same body — `repository.full_name`, or, in `StatusHandler`, on `params.sha` with no repository scoping at all. Because Shipit natively supports multiple configured GitHub organizations (`docs/setup.md` "Using Multiple Github Applications", `lib/shipit.rb#github`), an actor who legitimately administers **one** configured organization's GitHub App (and thus knows/controls that org's `webhook_secret`) can hand-craft a raw payload, sign it with their own org's secret, but populate `repository.full_name` (or simply `sha`) so that the handlers mutate state belonging to a **different**, unrelated organization's stacks.

### Finding Description
- `WebhooksController#verify_signature` computes `repository_owner` from the untrusted JSON body and looks up `Shipit.github(organization: repository_owner)` to obtain the HMAC secret used to check `X-Hub-Signature` against `request.raw_post`. [1](#0-0) [2](#0-1) 
- Multiple organizations are supported as independently configured GitHub Apps, each with its own `webhook_secret`, looked up via `Shipit.github_app_config(organization)`. [3](#0-2) 
- Once signature verification passes, event handlers derive scope from a *different* field of the same attacker-supplied body: `Handler#repository_name` reads `payload.dig('repository', 'full_name')`, entirely independent of `repository.owner.login` used for org selection. [4](#0-3) 
- `StatusHandler#process` doesn't even check `repository` — it matches `Commit.where(sha: params.sha)` **globally**, across every stack in the instance, and calls `commit.create_status_from_github!(params)` for every match. [5](#0-4) 
- `Status#enable_ci_on_stack` and `after_commit :schedule_continuous_delivery` mean a forged status is not inert — it flips CI state and can trigger continuous deployment. [6](#0-5) 
- Deploy gating is driven purely by recorded `Status` rows: `Commit#deployable?` requires `success? && !blocked?`, and `Status::Group` picks the "significant" status from whatever `Status` rows exist for that commit — regardless of which org's webhook actually created them. [7](#0-6) [8](#0-7) 

**Binding broken (equality that should hold but doesn't):**
`organization used to select the HMAC secret that authenticated the request` **≠** `organization/repository whose commits/stacks are actually mutated by the handler`.

Concretely: `repository_owner` (from `params.repository.owner.login`, used in `verify_signature`) is never cross-checked against `repository_name`/`sha` scope used inside the handlers that run afterwards on the very same trusted body.

### Impact Explanation
A holder of a legitimate `webhook_secret` for **one** configured GitHub organization (org admin who installed/owns that org's GitHub App — no Shipit repository write access, no `ApiClient` token, no session needed) can:
- POST directly to `/github/webhooks` with a body they construct themselves, sign it with their own org's known secret, and set `sha`/`repository.full_name` to target a commit/stack belonging to a **completely unrelated organization** tracked by the same Shipit instance.
- Inject a fabricated `success` `Status` for any known commit SHA in another org's stack, satisfying `Commit#deployable?` and triggering `schedule_continuous_delivery` — an **unauthorized deploy** of another organization's repository, which is explicitly a Critical-tier impact under the rules ("exfiltration... or an unauthorized deploy, rollback or merge").
- Similarly abuse `PushHandler`/`CheckSuiteHandler`/membership/pull-request handlers scoped by `repository.full_name` to trigger resyncs, archive review stacks, or manipulate team membership tied to a different org, since none of those handlers re-verify that `repository.full_name`'s owner matches the org whose secret authenticated the request.

### Likelihood Explanation
Requires only that the Shipit deployment is configured for multiple GitHub organizations (a documented, supported configuration) and that the attacker legitimately controls a GitHub App/webhook secret for at least one of them — a realistic scenario for any multi-tenant or multi-team Shipit install, and explicitly not one of the excluded "requires Shipit session/ApiClient/repo write access" categories, since GitHub App administration of one's own org is orthogonal to Shipit-side privileges or to the victim organization.

### Recommendation
In `WebhooksController`/`Handler`, after signature verification, assert that the organization derived for signature selection (`repository_owner`) matches the organization portion of every repository-scoped field the handler subsequently acts on (`repository.full_name`'s owner). For `StatusHandler` specifically, scope `Commit.where(sha:)` to commits whose `stack.repository`'s organization equals the verified `repository_owner`, rather than matching by SHA globally.

### Proof of Concept
1. Shipit configured with two orgs: `orgone` (attacker-administered GitHub App, secret known to attacker) and `orgtwo` (victim org's stacks, e.g. `orgtwo/critical-repo`).
2. Attacker crafts a `status` webhook JSON body:
```json
{
  "sha": "<victim-commit-sha-in-orgtwo>",
  "state": "success",
  "context": "ci/circleci",
  "repository": { "owner": { "login": "orgone" } }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(orgone_webhook_secret, raw_body)>` and POSTs to `/github/webhooks` with `X-Github-Event: status`.
4. `verify_signature` resolves `repository_owner` = `"orgone"`, fetches `orgone`'s `GitHubApp`, and successfully verifies the signature (attacker legitimately knows this secret). [1](#0-0) 
5. `StatusHandler#process` runs unconditionally against `Commit.where(sha: params.sha)`, finds the victim commit belonging to `orgtwo/critical-repo`, and creates a forged `success` status for it. [5](#0-4) 
6. The forged status makes the commit `deployable?` and can trigger `schedule_continuous_delivery`, resulting in an unauthorized deploy of `orgtwo`'s stack — despite the attacker having no relationship with `orgtwo` whatsoever.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
