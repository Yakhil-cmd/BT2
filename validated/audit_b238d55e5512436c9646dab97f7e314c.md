### Title
`is_valid_signed_package()` verifies a user's signature over generic, domain-less data, enabling cross-AA replay of off-chain signed messages - (File: formula/evaluation.js)

### Summary
Obyte AAs can verify off-chain, user-signed data via `is_valid_signed_package(signed_package, address)`. The hash that the user actually signs (`getSignedPackageHashToSign`) covers only the free-form `signed_message` payload plus generic envelope fields (`authors`, `last_ball_unit`, `version`) — it contains no binding to the specific AA (`this_address`) that will consume it. Exactly like the Futureswap `instantWithdraw` bug, where the signed struct lacked any Futureswap-specific data, an ocore user's signature over a `signed_message` intended for one AA can be replayed against a different AA that expects a structurally identical `signed_message`, because nothing in the signed hash commits it to a particular AA instance.

### Finding Description
`getSignedPackageHashToSign` computes the hash to sign purely from the caller-supplied envelope: [1](#0-0) 

`is_valid_signed_package` in the formula evaluator only checks (a) that the envelope's shape is valid, (b) that `last_ball_unit` is stable, and (c) that the given `address` is one of the signers via `signed_message.validateSignedMessage`. It never mixes in `this_address` (the invoking AA's own address) or any other AA-specific domain tag into the data being verified: [2](#0-1) 

`validateSignedMessage` itself only confirms the address/definition/authentifier match the generic `unit_hash_to_sign = getSignedPackageHashToSign(...)`; it has no concept of "for which AA" the package was intended: [3](#0-2) 

Because the primitive is domain-agnostic, safety against replay depends entirely on the AA author manually embedding a self-referential tag (e.g. `this_address`) inside `signed_message` and checking it. The shipped `payments_channels.oscript` sample does this correctly: [4](#0-3) 

But the shipped `order_book_exchange.oscript` sample — which is exactly the kind of generic trading/message schema (`sell_asset`, `buy_asset`, `sell_amount`, `price`, `address`) that could exist verbatim on another exchange AA — performs **no** such check; it verifies `is_valid_signed_package(trigger.data.order1, $order1.address)` without ever confirming the order was meant for `this_address`: [5](#0-4) 

This mirrors the Futureswap report precisely: the user's signed struct (`{token, amount, userInteractionNumber}` there; `{sell_asset, buy_asset, sell_amount, price, address}` here) carries no platform/contract-specific discriminator, so a signature crafted for AA #1 can be replayed verbatim against any other AA #2 sharing the same `signed_message` schema and signer address/definition, as long as `last_ball_unit` is still stable and unused nonce/order-id checks (which are also AA-specific and not enforced by `is_valid_signed_package`) don't happen to collide.

### Impact Explanation
An unprivileged AA trigger sender can take a legitimately-signed `signed_package` a user produced for one AA (e.g., an order-book exchange, an escrow, a lottery) and post it as trigger data to a *different* AA that also calls `is_valid_signed_package` on a compatible schema. If that second AA doesn't defensively bind the message to `this_address` (as `order_book_exchange.oscript` does not), the second AA will treat the signature as valid authorization even though the user never intended to interact with it. Depending on what the target AA does with the "authenticated" `signed_message` fields (state changes, balance debits/credits, order execution), this can cause unauthorized state changes or fund loss/freezing within that AA — a Medium/High severity griefing-to-fund-loss vector reachable purely by an unprivileged AA trigger sender, matching the "AA fund loss" acceptance criterion.

### Likelihood Explanation
Likelihood is moderate: it requires two different AAs to define semantically similar `signed_message` schemas and for at least one of them to omit the self-referential domain check, exactly as the sample code demonstrates (`payments_channels.oscript` does the check; `order_book_exchange.oscript` does not). Given that `is_valid_signed_package` is documented as a general building block and one of the two official sample AAs already omits the domain binding, it is realistic that third-party AA authors will replicate the same insecure pattern, especially since the API gives no warning or built-in protection against this class of replay.

### Recommendation
Harden the primitive itself (defense in depth), analogous to the Futureswap fix of binding the signature to the `Registry` contract address:
- Have `is_valid_signed_package(signed_package, address)` (or an additional variant) optionally require/verify that `signed_message` contains a field equal to `this_address`, or automatically mix `this_address` into the hash that is checked, so a signature is cryptographically bound to the AA that will consume it.
- At minimum, update documentation and the reference sample AAs (`order_book_exchange.oscript`) to consistently demonstrate embedding and checking `this_address` (or another unique per-AA/per-purpose domain tag) inside every `signed_message`, the way `payments_channels.oscript` already does, so third-party AA developers copy the safe pattern rather than the unsafe one.

### Proof of Concept
1. User signs an order for AA "Exchange A" using `signed_message = {address, sell_asset:'X', buy_asset:'Y', sell_amount, price}` following `order_book_exchange.oscript`'s schema, producing `signed_package` per `getSignedPackageHashToSign`. [1](#0-0) 
2. An unrelated party deploys "Exchange B" with an AA that also accepts orders in this same shape and similarly calls `is_valid_signed_package(trigger.data.order, order.signed_message.address)` without checking `this_address`.
3. The unrelated party (or the user by mistake) posts a trigger unit to Exchange B containing the exact same `signed_package` originally produced for Exchange A.
4. `is_valid_signed_package` returns `true` for Exchange B because the check only validates the signer's authentifier over the generic envelope — it never confirms the package was destined for Exchange B specifically: [6](#0-5) 
5. Exchange B executes the "order" against its own order book/state using a signature the user never intended for it, potentially moving/crediting funds the user did not authorize for that specific AA.

function getSignedPackageHashToSign(signedPackage) {
	var unsignedPackage = _.cloneDeep(signedPackage);
	for (var i=0; i<unsignedPackage.authors.length; i++)
		delete unsignedPackage.authors[i].authentifiers;
	var sourceString = (typeof signedPackage.version === 'undefined' || signedPackage.version === constants.versionWithoutTimestamp) ? getSourceString(unsignedPackage) : getJsonSourceString(unsignedPackage);
	return crypto.createHash("sha256").update(sourceString, "utf8").digest();
}
