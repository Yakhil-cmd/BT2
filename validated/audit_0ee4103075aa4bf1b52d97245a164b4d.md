### Title
Cross-organization team membership mutation via `MembershipHandler#find_or_create_team!` looking up teams by `github_id` alone, without binding to the verified webhook organization - (File: app/models/shipit/webhooks/handlers/membership_handler.rb)

### Summary
`WebhooksController#verify_signature` only verifies that the request's signature matches the GitHub App configured for the organization named in the payload (`repository_owner`, falling back to `organization.login` for org-scoped events like `membership`). It never verifies that the `team.id` in the payload actually belongs to that same organization. `MembershipHandler#find_or_create_team!` then looks up/mutates a `Team` purely by the global `github_id`, so a webhook cryptographically valid for OrgOne can add or remove members on a `Team` row that actually belongs to OrgTwo.

### Finding Description
The broken binding, stated as an equality that should hold but does not:
`Shipit.github(organization: X).verify_webhook_signature(...) == true` should imply `X == organization_owning(Team.find_by(github_id: params.team.id))`. In this exploit, `X = "OrgOne"` (attacker-controlled, from `params['organization']['login']`) while the targeted `Team` record's true owning organization is `"OrgTwo"`.

Code path:
- `WebhooksController#verify_signature` computes `repository_owner` as `params.dig('repository','owner','login') || params.dig('organization','login')` [1](#0-0)  and calls `Shipit.github(organization: repository_owner).verify_webhook_signature(...)` [2](#0-1) . GitHub's real `membership` webhook payload has no top-level `repository` key, so `repository_owner` resolves to the attacker-supplied `organization.login` field.
- `MembershipHandler#find_or_create_team!` looks the team up solely by `github_id`, an attribute with no scoping to the verified organization: `Team.find_or_create_by!(github_id: params.team.id) { |team| team.github_team = params.team; team.organization = params.organization.login }` [3](#0-2) . If a `Team` row with that `github_id` already exists (created earlier by a legitimate OrgTwo membership event), `find_or_create_by!` returns the existing record and the block (which would at least re-assert `organization`) is skipped entirely.
- `#process` then calls `team.add_member(member)` or `team.members.delete(member)` on that pre-existing OrgTwo `Team` object [4](#0-3) , mutating OrgTwo's membership data using a request that was only ever authenticated as belonging to OrgOne.

Root cause: `github_id` is a global lookup key with no per-organization scoping anywhere in `Shipit::Team`, and neither `verify_signature` nor `MembershipHandler` cross-checks `params.organization.login` (the value the signature was verified against) with the organization actually owning the targeted `Team` row. `Shipit.github_app_config`/`Shipit.github` correctly separate secrets per organization [5](#0-4) , so the per-organization secret separation is real and does work as designed — the gap is purely that the handler's data write is not scoped by the organization the signature was verified for.

Attacker's exact request: a `POST /webhooks` with header `X-Github-Event: membership`, a valid `X-Hub-Signature` computed with OrgOne's real `webhook_secret` (which the attacker, as an admin/owner of OrgOne, legitimately possesses), and a JSON body `{"action":"added","organization":{"login":"OrgOne"},"team":{"id":<OrgTwo's real team github_id>,"name":...,"slug":...,"url":...},"member":{"login":"<attacker-controlled-or-target-login>"}}`. `verify_signature` calls `Shipit.github(organization: "OrgOne")` and succeeds; `find_or_create_team!` resolves the pre-existing OrgTwo `Team` by `github_id` and the handler mutates its membership.

Existing guards do not stop this: `verify_signature` only checks the HMAC against the org named in the payload, `drop_unhandled_event` and the `ExplicitParameters` schema only validate shape/types (they require `team.id` be an `Integer`, not that it belong to any particular org), and there is no model validation in `Shipit::Team` binding `github_id` to `organization`.

### Impact Explanation
An attacker who legitimately administers one onboarded GitHub organization (OrgOne) in a multi-org Shipit deployment can add or remove arbitrary users from another tenant's (OrgTwo's) `Shipit::Team`, which is used elsewhere for authorization gating (e.g., `Shipit.github_teams` / team-based permission checks) [6](#0-5) . This is a direct cross-tenant write matching the documented Critical category "a payload for one repository [org] mutating another's ... team." It is repeatable against any `Team` `github_id` the attacker can discover, for both `added` and `removed` actions, and does not require compromising any Shipit-side secret.

### Likelihood Explanation
Requires: (1) a genuinely multi-org Shipit deployment using `github_organizations`/`github:` per-org secrets schema (as in `test/dummy/config/secrets_double_github_app.yml`), (2) attacker legitimately controls at least one onboarded org (OrgOne) and can trigger/sign its own webhooks, (3) attacker knows or can discover the numeric GitHub `team.id` (github_id) of a target team in OrgTwo (team IDs are visible via GitHub's API/UI to org members and are not secret in the way tokens are), and (4) the target `Shipit::Team` row for OrgTwo already exists in Shipit's DB (typical after any prior real membership sync for that team). Given these are realistic conditions for the documented multi-org use case, likelihood is moderate-to-high for any deployment actually using multiple orgs.

### Recommendation
In `MembershipHandler#find_or_create_team!`, scope the lookup/creation by both `github_id` and `organization` (using the organization value that `verify_signature` actually authenticated), and reject/no-op if an existing `Team` with that `github_id` has a different `organization` than the one the webhook was verified for. Additionally, consider adding a uniqueness/consistency validation on `Shipit::Team` for `(github_id, organization)` and having `WebhooksController` pass the verified organization down to handlers so they can assert it against payload-derived organization ownership before mutating any record.

### Proof of Concept
Minitest plan (extending `test/controllers/webhooks_controller_test.rb` conventions), no live GitHub calls:
1. Load `test/dummy/config/secrets_double_github_app.yml` config via `Shipit.stubs(:secrets)` as done in `test/unit/shipit_test.rb`.
2. Create a `Shipit::Team` fixture/row with `github_id: 999, organization: 'orgtwo', slug: 'orgtwo-team'`.
3. Build a membership payload: `{ action: 'added', team: { id: 999, name: 'Org Two Team', slug: 'orgtwo-team', url: 'https://example.com' }, organization: { login: 'OrgOne' }, member: { login: 'attacker-friend' } }`.
4. Compute `signature = 'sha1=' + OpenSSL::HMAC.hexdigest('sha1', <OrgOne's configured webhook_secret>, payload.to_json)`.
5. `POST :create` with `X-Github-Event: membership` and `X-Hub-Signature: signature`.
6. Assert response is `:ok` (signature verified against OrgOne's secret).
7. Assert `Shipit::Team.find_by(github_id: 999).organization == 'orgtwo'` (unchanged, proving the OrgTwo team, not an OrgOne team, was targeted) and assert `Shipit::Team.find(999_team.id).members.map(&:login)` now includes `'attacker-friend'` — i.e., the equality `X (OrgOne, verified) == organization_owning(mutated team) (orgtwo)` is false, yet the write succeeded.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
