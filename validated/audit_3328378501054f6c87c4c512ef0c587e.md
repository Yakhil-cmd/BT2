### Title
Cross-organization commit-status/CI forgery via webhook signature scoped to sender org but write scoped globally by SHA - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App whose `webhook_secret` is used to authenticate an inbound webhook based on a payload-controlled field (`repository.owner.login`, falling back to `organization.login`), i.e. the identity that is *cryptographically verified* is "whichever organization's key matches this payload." However, `StatusHandler` (and `CheckSuiteHandler`) then act on that payload using only a bare `sha`/branch lookup that is **not** scoped to the verified organization/repository at all. This breaks the intended binding `organization_that_signed == repository_that_is_written`, analogous to the zAuction bug where the verified identifier (`saleId`/`auctionId`) was not bound to the correct counterpart (`seller`/`bidder`).

### Finding Description
Signature verification is performed in [1](#0-0) , and the organization used to select the verification key is derived purely from the JSON payload: [2](#0-1) 

Once verified, the raw JSON `params` are dispatched to event handlers without any re-binding of the handler's target records to that same `repository_owner`/organization: [3](#0-2) 

Most handlers correctly scope their side effects to the repository named in the payload via `Handler#stacks`, which filters by `repository.full_name`: [4](#0-3) 

But `StatusHandler#process` does **not** use `stacks`/`repository_name` scoping at all — it looks up **any** `Commit` across the entire installation (all stacks, all repositories, all organizations) matching the attacker-supplied `sha` and writes a CI status to it: [5](#0-4) 

`create_status_from_github!` then updates the commit's aggregate status and, critically, can trigger continuous deployment: [6](#0-5) [7](#0-6) 

**The binding that should hold:** `organization whose webhook_secret signed the request == organization/repository owning the commit that gets its CI status mutated`.

**What actually happens:** the signature is checked against the org named in `repository.owner.login`/`organization.login` of the payload, but the status write in `StatusHandler` is keyed solely by `sha` — a value with no cryptographic tie to the org that was authenticated. In a multi-tenant Shipit deployment (as the engine explicitly supports — see `config/secrets.*.yml` listing multiple GitHub orgs, each with its own `webhook_secret`), an attacker who controls (or has push access to) any one configured organization's repository can:
1. Send a legitimately-signed webhook for their own org (`repository.owner.login = attacker-org`, which passes `verify_signature`).
2. Set `sha` in the payload to the SHA of a real commit belonging to an unrelated stack in a different, victim organization (git SHAs are public information, obtainable from the victim repo's commit history/API).
3. `StatusHandler` finds that `Commit` (matched by SHA regardless of `stack_id`/repository) and calls `create_status_from_github!` with an attacker-chosen `state` (e.g. `"success"`), `context`, `description`.

If the victim stack has `continuous_deployment: true` and `ignore_ci`/required statuses configured such that this forged status satisfies `deployable?`, `schedule_continuous_delivery` fires `ContinuousDeliveryJob`, causing an **unauthorized deploy on a stack the attacker's organization never authenticated against**.

### Impact Explanation
This is a cross-organization write and can escalate to an unauthorized deploy — matching the Critical severity bucket ("cross-repository writes, or an unauthorized deploy, rollback or merge"). The write crosses a trust boundary that the webhook signature is specifically meant to enforce (per-organization isolation via distinct `webhook_secret`s), yet the actual mutation target is chosen with no reference to that boundary.

### Likelihood Explanation
Requires the attacker to control (or have push access enabling GitHub-generated status webhooks for) at least one organization/repository configured in the same multi-tenant Shipit instance, and to know the target commit's SHA (public via GitHub). No `webhook_secret` of the *victim* org, no Shipit session, and no `ApiClient` token is needed — only the attacker's own legitimately-configured org's webhook credentials, which is a materially lower bar than compromising the victim's secrets. Likelihood is moderate: it depends on the deployment hosting multiple independent/untrusted organizations behind one Shipit instance and on the victim stack having `continuous_deployment` enabled with CI-gated deploys.

### Recommendation
Scope `StatusHandler#process` (and any other handler performing writes) to the repository/organization named in the same payload envelope that was cryptographically verified, i.e. restrict the query to `stacks` (as `Handler#stacks` already does via `repository.full_name`) rather than a bare, unscoped `Commit.where(sha: params.sha)`. Concretely: filter to commits within `stacks.flat_map(&:commits)` (or an equivalent stack-scoped query) before creating the status, ensuring the organization that signed the webhook is the same one whose commit is mutated.

### Proof of Concept
1. Configure Shipit with two orgs in `secrets.yml`: `attacker-org` (attacker has admin/push access) and `victim-org` (target stack, `continuous_deployment: true`, deployable when CI passes).
2. Attacker obtains the SHA of an undeployed commit `C` in `victim-org/repo` (public via GitHub UI/API).
3. Attacker triggers (or crafts, using their own repo's legitimate GitHub App webhook delivery mechanism/replay) a `status` event where:
   - `repository.owner.login` = `attacker-org` (so `X-Hub-Signature` verifies against `attacker-org`'s `webhook_secret`)
   - `sha` = `C`, `state` = `"success"`, `context` = required CI context for victim stack
4. `WebhooksController#verify_signature` passes (valid signature for `attacker-org`).
5. `StatusHandler#process` executes `Commit.where(sha: C)`, finds commit `C` belonging to `victim-org`'s stack (no owner check), and calls `create_status_from_github!`.
6. If this satisfies `Commit#deployable?` and `Stack#deployable?`, `schedule_continuous_delivery` enqueues `ContinuousDeliveryJob`, deploying commit `C` on the victim stack — a deploy never authorized by `victim-org`'s signature.

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```
