### Title
`deregisterOperator` Lacks Threshold Guard, Permanently Locking Bridged KLAY/Tokens When Active Operators Fall Below Quorum — (`contracts/service_chain/bridge/BridgeOperator.sol`)

---

### Summary

`BridgeOperator.deregisterOperator` allows the bridge owner to remove operators without verifying that the remaining operator count still satisfies `operatorThresholds[ValueTransfer]`. When the active operator count drops below the threshold, pending `handleKLAYTransfer` / `handleERC20Transfer` votes can never reach quorum. KLAY and tokens already locked in the bridge by users via `requestKLAYTransfer` / `requestERC20Transfer` have no user-accessible refund path and become permanently irrecoverable once the stuck nonces fall outside the 200-nonce handle window.

---

### Finding Description

`setOperatorThreshold` correctly enforces a forward guard:

```solidity
require(operatorList.length >= _threshold, "bigger than num of operators");
``` [1](#0-0) 

But the symmetric reverse guard is absent from `deregisterOperator`:

```solidity
function deregisterOperator(address _operator)
external
onlyOwner
{
    require(operators[_operator]);
    delete operators[_operator];
    // removes from operatorList (swap-and-pop)
    emit OperatorDeregistered(_operator);
}
``` [2](#0-1) 

The code comment itself acknowledges a related but distinct issue (stale votes), yet does not address the threshold-underflow case: [3](#0-2) 

`_voteValueTransfer` executes a transfer only when `voteCounts[voteKey] >= operatorThresholds[ValueTransfer]`: [4](#0-3) 

If `operatorList.length` is reduced below `operatorThresholds[ValueTransfer]`, this condition can never be satisfied. `handleKLAYTransfer` is also gated by `onlyOperators`, so no new votes can be cast by non-operators either: [5](#0-4) 

The handle-nonce window advances by at most 200 slots. Once a stuck nonce falls outside the window, `_lowerHandleNonceCheck` will permanently reject it even if the threshold is later corrected. There is no `cancelTransfer`, `refund`, or owner-withdrawal function in the bridge contracts; the only egress for locked KLAY is through a successful `handleKLAYTransfer` execution.

The extreme case — deregistering all operators — additionally breaks `setOperatorThreshold` itself, because that function requires `operatorList.length >= _threshold`, and with zero operators no valid threshold ≥ 1 can be set: [6](#0-5) 

---

### Impact Explanation

KLAY and ERC-20/ERC-721 tokens deposited by users into the service-chain bridge via `requestKLAYTransfer` / `requestERC20Transfer` are locked in the bridge contract. If the owner deregisters operators such that `operatorList.length < operatorThresholds[ValueTransfer]`, those pending transfers can never be executed. Once the stuck request nonces age past the 200-slot handle window, they become permanently unprocessable even after a threshold correction. This is an unauthorized, irreversible loss of bridged assets — KLAY and bridged tokens — held in a system-managed contract.

---

### Likelihood Explanation

The bridge owner is a semi-trusted administrator expected to perform routine operator rotation (e.g., replacing a compromised key). A single misordered operation — deregistering the old operator before registering the replacement, or deregistering while threshold equals the current operator count — silently drops the active count below quorum. No on-chain warning or revert prevents this. The scenario requires only one privileged but non-colluding actor making a sequencing mistake, which is a realistic operational error.

---

### Recommendation

Add a post-deregistration threshold check inside `deregisterOperator`:

```solidity
function deregisterOperator(address _operator) external onlyOwner {
    require(operators[_operator]);
    delete operators[_operator];

    for (uint i = 0; i < operatorList.length; i++) {
        if (operatorList[i] == _operator) {
            operatorList[i] = operatorList[operatorList.length - 1];
            operatorList.length--;
            break;
        }
    }

    // Guard: remaining operators must still satisfy every vote threshold
    for (uint8 vt = 0; vt < uint8(VoteType.Max); vt++) {
        require(
            operatorList.length >= operatorThresholds[vt],
            "deregister would break threshold"
        );
    }

    emit OperatorDeregistered(_operator);
}
```

This mirrors the existing guard in `setOperatorThreshold` and ensures the bridge can never enter a state where pending value-transfer votes are permanently unresolvable.

---

### Proof of Concept

1. Deploy `Bridge` (lock-mode). Owner is the sole operator; threshold = 1.
2. Register operators `op1` and `op2`; call `setOperatorThreshold(ValueTransfer, 3)` (3 operators, threshold = 3). ✓
3. User calls `requestKLAYTransfer{value: 1 ether}(user, 1 ether, "")` on the child bridge. 1 KLAY is now locked in the contract.
4. `op1` calls `handleKLAYTransfer(...)` on the parent bridge — 1 vote, threshold not met, returns without executing.
5. Owner calls `deregisterOperator(op2)` — succeeds with no revert. Now 2 operators remain, threshold = 3.
6. Owner calls `deregisterOperator(op1)` — succeeds. Now 1 operator remains, threshold = 3.
7. The sole remaining operator calls `handleKLAYTransfer(...)` — 1 vote, `voteCounts < 3`, never executes.
8. Owner attempts `setOperatorThreshold(ValueTransfer, 1)` — succeeds (1 ≥ 1), but the nonce from step 4 already has 2 stale votes from deregistered operators recorded in `votes` storage; the `closedValueTransferVotes` flag is not set; however, the `_lowerHandleNonceCheck` window advances as later nonces are processed, eventually expiring the stuck nonce.
9. The 1 KLAY from step 3 is permanently locked with no withdrawal path. [2](#0-1) [7](#0-6)
