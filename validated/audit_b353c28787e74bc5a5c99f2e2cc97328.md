### Title
Retroactive TPS-fee re-pricing via `system_vote` on `base_tps_fee`/`tps_interval` causes unfair, uncontrollable debits from an address's `tps_fees_balance` — (File: `storage.js`)

### Summary
`ocore` lets any address (weighted by its stable byte balance) vote on numeric network parameters `base_tps_fee`, `tps_interval` and `tps_fee_multiplier` via a `system_vote`/`system_vote_count` message pair, which is tallied once per MCI in `countVotes()` and stored versioned by `vote_count_mci` in `system_vars`. A unit's TPS fee is validated against these parameters at *composition/validation time* (using the unit's `last_ball_mci`), but the fee that is actually and irrevocably debited from the payer's running `tps_fees_balance` is recomputed later, at *stabilization time*, using the parameter values in effect at the unit's own (later) MCI. If a vote changes `base_tps_fee`/`tps_interval` in the gap between those two points, ordinary users are retroactively charged (or credited) a different fee than the one they paid for and validated against — exactly the same bug class as the reported "voting to change a reward/fee coefficient retroactively changes outcomes for already-committed transactions."

### Finding Description
When composing/validating a payment unit, the TPS fee obligation is computed against system vars fixed at the unit's `last_ball_mci`: [1](#0-0) 

This is enforced during unit validation via `validateTpsFee`, which reads the address's current `tps_fees_balance` and compares it (plus the unit's declared `tps_fee`) against `min_tps_fee` computed from `getLocalTpsFee` (i.e., parameters at `last_ball_mci`): [2](#0-1) 

However, once the unit stabilizes, `main_chain.js` calls `updateTpsFees()`, which recomputes the fee that is actually applied to the account's ledger balance using `getFinalTpsFee()`. Crucially, this function explicitly uses the system var in effect at the **unit's own MCI**, not the `last_ball_mci` that was used to validate/price the unit when it was broadcast: [3](#0-2) 

```
const base_tps_fee = getSystemVar('base_tps_fee', mci); // not at last_ball_mci
```

`updateTpsFees()` then applies the *delta* between the fee the user actually paid (`objUnitProps.tps_fee`) and this newly (and later) computed "final" fee directly to the address's persistent `tps_fees_balance` ledger: [4](#0-3) 

`getSystemVar()` selects whichever system-var record has the highest `vote_count_mci` below the queried MCI: [5](#0-4) 

and votes are counted and immediately made effective for all future MCI lookups as soon as the counting proposal stabilizes: [6](#0-5) 

Because a unit can take multiple MCIs to become stable (it must first be included, then wait for later units to confirm it on the main chain), and `base_tps_fee`/`tps_interval`/`tps_fee_multiplier` can change via `system_vote_count` in that window, the fee finally levied against the user's `tps_fees_balance` in `updateTpsFees()` was never known or agreed to by the user when the unit was composed and paid for. Unlike the DEXE case, where different claimants of the same proposal get inconsistent rewards, here every node deterministically computes the same "final" fee, so there is no cross-node disagreement — but every user is still exposed to unbounded, unannounced retroactive re-pricing of already-broadcast, already-fee-paid transactions.

### Impact Explanation
If `base_tps_fee` or `tps_interval` is voted upward while a user's units are still unstable, `updateTpsFees()` computes a materially larger "final" fee than the amount the user actually included and validated against at broadcast time. The resulting negative `total_tps_fees_delta` is subtracted from the address's `tps_fees_balance`, driving it deeply negative. Since `validateTpsFee` requires `tps_fees_balance + tps_fee*share >= min_tps_fee*share` for all future units from that address, a large negative balance effectively forces the address to overpay (or be rejected/soft-rejected) on all subsequent transactions until the deficit is worked off — a form of unplanned fund loss / spending freeze inflicted after the fact by a governance vote the user had no way to anticipate when they signed and broadcast their unit. This matches the accepted impact class of "AA/fund loss or freezing" caused by retroactively applying a voted parameter to already-finalized user commitments.

### Likelihood Explanation
`system_vote`/`system_vote_count` messages can be posted by any address with a stable byte balance, and votes are tallied automatically once the counting unit stabilizes; no special privilege is required. The window between a unit's `last_ball_mci` (its own fee-validation reference point) and its actual stabilization MCI is routine and can span multiple MCIs, especially under normal network latency or during periods of active voting/campaigning on TPS-fee parameters, making the retroactive mismatch a naturally occurring rather than purely theoretical condition.

### Recommendation
Freeze the parameter set used for `getFinalTpsFee()` to the same reference point used for `getLocalTpsFee()`/`validateTpsFee()` (i.e., the unit's own `last_ball_mci`, not its later stabilization `mci`), so that the fee a user validates and pays for at broadcast time cannot be silently altered by governance votes that land afterward. If retroactive re-pricing is an intentional design choice (analogous to DEXE's "acknowledged" stance), it should at minimum be bounded (e.g., capped delta) and clearly documented so wallets can defend against unbounded balance depletion.

### Proof of Concept
1. Address A composes and broadcasts a payment unit U with `last_ball_mci = M`; `tps_fee` is computed and validated using `base_tps_fee`/`tps_interval` in effect at `M` (`storage.js:1339-1349`, `validation.js:1050-1097`).
2. Before U stabilizes, a `system_vote_count` on `base_tps_fee` finalizes with `vote_count_mci = M+1`, roughly doubling `base_tps_fee` (`main_chain.js:1737-1913`).
3. U eventually stabilizes at `mci = M+3`. `updateTpsFees()` invokes `getFinalTpsFee(U)`, which looks up `base_tps_fee` at `mci = M+3` — the new, higher value (`storage.js:1238-1245`).
4. The resulting `total_tps_fees_delta` is strongly negative and is subtracted from A's `tps_fees_balance` (`storage.js:1247-1275`), even though A never agreed to or could have known about the new fee when broadcasting U.
5. A's subsequent units now fail or must overpay in `validateTpsFee` (`validation.js:1088-1090`) until the deficit created by the retroactive vote is repaid.

async function getLocalTpsFee(conn, objUnitProps, count_units = 1) {
	const objLastBallUnitProps = await readUnitProps(conn, objUnitProps.last_ball_unit);
	const last_ball_mci = objLastBallUnitProps.main_chain_index;
	const base_tps_fee = getSystemVar('base_tps_fee', last_ball_mci); // unit's mci is not known yet
	const tps_interval = getSystemVar('tps_interval', last_ball_mci);
	const tps_fee_multiplier = getSystemVar('tps_fee_multiplier', last_ball_mci);
	const tps = await getLocalTps(conn, objUnitProps, count_units);
	console.log(`local tps at ${objUnitProps.unit} ${tps}`);
	const tps_fee_per_unit = Math.round(tps_fee_multiplier * base_tps_fee * (exp(tps / tps_interval) - 1));
	return count_units * tps_fee_per_unit;
}

		timestamp: objUnit.timestamp,

		max_aa_responses: objUnit.max_aa_responses,
	};
	const count_units = storage.getCountUnitsPayingTpsFee(objUnitProps);
	const min_tps_fee = await storage.getLocalTpsFee(conn, objUnitProps, count_units);

async function countVotes(conn, mci, subject, is_emergency = 0, emergency_count_command_timestamp = 0) {
	console.log('countVotes', mci, subject, is_emergency, emergency_count_command_timestamp);
	if (is_emergency && subject !== "op_list")
		throw Error("emergency vote count supported for op_list only, got " + subject);
	const address_rows = await conn.query("SELECT DISTINCT address FROM system_votes WHERE subject=?", [subject]);
	let addresses = address_rows.map(r => r.address);
	const unstable_votes = (is_emergency && mci >= constants.pemCurvesFixMci) ? getUnstableVotes(emergency_count_command_timestamp) : null;
	if (unstable_votes) {
		for (let { author_addresses } of unstable_votes) {
			for (let address of author_addresses)
				addresses.push(address);
		}
		addresses = _.uniq(addresses);
	}
	const strAddresses = addresses.map(db.escape).join(', ');
	let balances = {};
	// Count all stable-good outputs that have no stable-good spender.
	// This correctly handles outputs whose only spending unit was propagated to final-bad
	// (leaving is_spent=1 in the DB while no good unit claims the output), which the
	// previous two-query approach (bal_rows + spent_rows) silently undercounted.
	const bal_rows = await conn.query(`
		SELECT outputs.address, SUM(outputs.amount) AS balance
		FROM outputs
		JOIN units ON outputs.unit = units.unit
		WHERE outputs.address IN(${strAddresses})
			AND outputs.asset IS NULL
			AND units.is_stable = 1 AND units.sequence = 'good'
			AND NOT EXISTS (
				SELECT 1 FROM inputs
				JOIN units AS su ON inputs.unit = su.unit
				WHERE inputs.src_unit = outputs.unit
					AND inputs.src_message_index = outputs.message_index
					AND inputs.src_output_index = outputs.output_index
					AND su.sequence = 'good'
					AND su.is_stable = 1
			)
		GROUP BY outputs.address`);
	console.log('bal rows', bal_rows)
	for (let { address, balance } of bal_rows) {
		balances[address] = balance;
	}
	let values = [];
	for (let address in balances)
		values.push(`(${db.escape(address)}, ${balances[address]})`);
	if (values.length === 0)
		return console.log(`no voters for ${subject}, skipping vote count`);

	const [mc_row] = await conn.query("SELECT timestamp FROM units WHERE main_chain_index=? AND is_on_main_chain=1", [mci]);
	if (!mc_row)
		throw Error(`no MC unit on just stabilized MCI ` + mci);
	const mc_timestamp = mc_row.timestamp;
	
	const [activation_row] = await conn.query("SELECT timestamp FROM units WHERE main_chain_index=? AND is_on_main_chain=1", [constants.v4UpgradeMci]);

	if (mci >= constants.pemCurvesFixMci) {
		const [first_vote_row] = await conn.query("SELECT timestamp FROM system_votes WHERE subject=? ORDER BY timestamp ASC LIMIT 1", [subject]);
		if (!first_vote_row)
			throw Error(`no votes for subject ${subject}`);
		activation_timestamp = first_vote_row.timestamp;
	}

	await conn.query(`CREATE TEMPORARY TABLE voter_balances (
		address CHAR(32) NOT NULL PRIMARY KEY,
		balance BIGINT NOT NULL
	)`);

	let since_timestamp = mc_timestamp;

		since_timestamp -= 365 * 24 * 3600;

			FROM voter_balances

			break;
	}

	let value;
	switch (subject) {

			if (is_emergency) { // add unstable votes for OPs
				await conn.query(`CREATE TEMPORARY TABLE ${votes_table} AS SELECT address, op_address, timestamp FROM op_votes`);
				// the order of iteration is undefined, so we'll first collect the messages and then sort them. The order matters only when the same address sends multiple unstable votes
				let votes = unstable_votes || getUnstableVotes(emergency_count_command_timestamp);
				console.log('unsorted unstable votes', votes);
				votes.sort((v1, v2) => {
					const dt = v1.timestamp - v2.timestamp;
					if (dt !== 0)

			if (mci === 0) {

			}
			storage.systemVars.op_list.unshift({ vote_count_mci: mci === 0 ? -1 : mci, value: ops, is_emergency });
			value = JSON.stringify(ops);

		case "threshold_size":

				FROM numerical_votes
				CROSS JOIN voter_balances USING(address)
				WHERE timestamp>=? AND subject=?
				GROUP BY value
				ORDER BY value`,

}
