Confirmed: `labels` has no format validation — any string from `pull_request.labels.map(&:name)` (raw GitHub label names) is stored as-is [1](#0-0) [2](#0-1) , and `ReviewStack#env` uppercases every label name into an environment-variable key with no allowlist filtering [3](#0-2) .

### Title
Unfiltered PR label names become arbitrary environment variable keys (e.g. `RUBYLIB`) injected into `TaskCommands#install_dependencies` process env - (File: app/models/shipit/review_stack.rb)

### Summary
`ReviewStack#env` merges every pull request label, uppercased, directly as an environment variable key with the value `"true"`, with no allowlist. `TaskCommands#install_dependencies` builds its `Command` using this unfiltered `env`, so a PR label literally named `rubylib` becomes `RUBYLIB=true` in the spawned process's environment for the `bundle install`/`ruby` dependency step.

### Finding Description
The broken binding: `Command#env` used for `install_dependencies` should equal `EnvironmentVariables.with(candidate_env).permit(allowed_variable_definitions)` (an allowlisted set), but instead it equals `TaskCommands#env` = `Commands#env.merge(@stack.env).merge(...).merge(deploy_spec.machine_env).merge(@task.env)`, where `@stack.env` for a `ReviewStack` includes `pull_request.labels.each_with_object({}) { |label_name, labels| labels[label_name.upcase] = "true" }` with no key restriction whatsoever [3](#0-2) .

Path: an attacker opens a PR from their own fork/repo against a repository with `provisioning_behavior = allow_all` and adds a label such as `rubylib` (case-insensitive, GitHub allows arbitrary label text). `Shipit::Webhooks::Handlers::PullRequest::LabelCapturingHandler#capture_labels` (for `labeled`/`opened`/`reopened`/`unlabeled` actions) writes `params.pull_request.labels.map(&:name)` straight into `PullRequest#labels` with no sanitization [4](#0-3) ; `PullRequest#github_pull_request=` does the same for the initial sync [2](#0-1) . The `PullRequest#labels` column itself has no format validator, just a serializer [1](#0-0) .

When a task/deploy runs, `TaskCommands#install_dependencies` builds `Command.new(command_line, env:, chdir: steps_directory)` using this unfiltered `env` for each dependency step (`bundle install`, etc.) [5](#0-4) . `Command#unbundled_env` then does `BASE_ENV.merge('PATH' => ...).merge(@env.stringify_keys)`, so the attacker-controlled key/value pair overrides/adds directly into the environment handed to `PTY.spawn` [6](#0-5) . Ruby (invoked via `bundle`/`ruby`) honors `RUBYLIB` to prepend load paths, so any `require` executed during the dependency install step (or later steps, since the same tainted `env` flows through `perform` too) can load attacker-supplied code if the attacker can also place a file at a path they control (e.g. within the checked-out working directory of their own fork, which is exactly what gets checked out for this build).

Why existing guards don't help: The only sanitization mechanism in the codebase, `EnvironmentVariables#permit`, is applied solely to human/API-triggered deploy/task custom variables (`filter_deploy_envs`, `filter_rollback_envs`, `Task#env`/`TaskDefinition#filter_envs`) [7](#0-6) [8](#0-7) , confirmed by controller tests that reject unwhitelisted keys via `deploy_params`/`env` params [9](#0-8) . It is never applied to `Stack#env`/`ReviewStack#env`, which is merged unfiltered into `TaskCommands#env` and used directly by `install_dependencies` and `perform`. There is no key-name validation on `provisioning_behavior=allow_all`, which is precisely the mode intended to let PRs auto-provision without any maintainer review or label gating.

### Impact Explanation
Any label name an unprivileged PR author chooses becomes an environment variable in the process that installs dependencies (and later runs all deploy/task steps) on the Shipit deploy host, for the review stack tied to their own PR. `RUBYLIB` (or `BUNDLE_GEMFILE`, `GEM_PATH`, `LD_PRELOAD`-style loader variables honored by the language toolchain, `PATH` override attempts, etc.) can redirect `require`/gem resolution to attacker-supplied code checked out from the attacker's own fork, resulting in arbitrary code execution on the Shipit deploy host — Critical, matching the RCE-via-`Command`/`PTY.spawn` class. This is repeatable on every PR/label event for any repository configured with `allow_all` review stacks, and is scoped to that repository's stack process (not cross-tenant by itself, but RCE on the shared deploy host is a full compromise regardless of stack boundaries).

### Likelihood Explanation
Preconditions: the target repository must have `ReviewStack` provisioning enabled with `provisioning_behavior = allow_all` (a documented, supported configuration for fully automated review stacks), and the repo's `dependencies` step must invoke `ruby`/`bundle` (default `bundle install` autodetected when a `Gemfile` is present) [10](#0-9) . Attacker cost is trivial: open a PR from a fork and add a label — no Shipit credentials, no webhook secret, no team membership needed. Fully repeatable per PR/label event.

### Recommendation
Do not use raw pull request label names as environment variable keys. Either (a) namespace/prefix label-derived variables (e.g. `LABEL_<name>`) so they can never collide with sensitive interpreter/loader variable names, and/or (b) apply an explicit allowlist (similar to `EnvironmentVariables#permit`) to `Stack#env`/`ReviewStack#env` before merging into `TaskCommands#env`, rejecting or dropping any key that collides with known loader/toolchain environment variables (`RUBYLIB`, `LD_PRELOAD`, `BUNDLE_GEMFILE`, `PATH`, `GEM_PATH`, etc.), and/or (c) restrict label-derived keys to a hardcoded prefix and validate label name characters.

### Proof of Concept
minitest plan (`allow_all`):
```ruby
test "TaskCommands#install_dependencies env is polluted by PR label names" do
  stack = shipit_stacks(:review_stack) # ReviewStack with allow_all
  stack.pull_request.update!(labels: ["rubylib"]) # attacker-controlled via webhook label name

  task = shipit_tasks(:shipit_restart)
  task.stack = stack

  command = Shipit::TaskCommands.new(task).install_dependencies.first

  assert_equal "true", command.env["RUBYLIB"]
end
```
This mirrors the existing assertions in `test/lib/shipit/task_commands_test.rb` (`env["WIP"]`, `env["BUG"]`) [11](#0-10)  and `test/models/shipit/review_stack_test.rb` [12](#0-11) , proving the same unfiltered merge path reaches `install_dependencies`'s `Command#env`, which feeds `PTY.spawn` via `Command#unbundled_env` [6](#0-5) .
