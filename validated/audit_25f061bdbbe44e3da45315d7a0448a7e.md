### Title
Uncaught exception in chash validation crashes full node on malformed attestor/address input - ([File: chash.js])

### Summary
`chash.isChashValid()` in [1](#0-0)  can throw an uncaught `Error` when fed a 32-character string whose bytes, after base32 decoding, do not add up to exactly 160 bits. This mirrors the `multihash::from_slice` bug class in the report: a function whose signature/usage implies a safe boolean/Result-style check (`isChashValid`/`isValidChash`) can instead panic (throw) on malformed input that the caller does not expect to throw.

### Finding Description
`isChashValid(encoded)` only wraps the `base32.decode(encoded)` / `Buffer.from(encoded,'base64')` call in a `try/catch` [2](#0-1) . Everything downstream — `buffer2bin(chash)`, and especially `separateIntoCleanDataAndChecksum(binChash)` — is **not** covered by that `try/catch`: [3](#0-2) 

`separateIntoCleanDataAndChecksum` explicitly throws when the decoded bit-length isn't exactly 160 or 288: [4](#0-3) 

The guard that is supposed to prevent invalid-alphabet input from ever reaching `isChashValid` is the regex check in `isValidAddress`: [5](#0-4) 

However, `isValidAddressAnyCase` calls the underlying `isValidChash`/`isChashValid` path **without** that charset regex: [6](#0-5) 

`isValidChash` itself only checks the *length* of the string (`isStringOfLength(str, len)`), not its character set, before calling `chash.isChashValid(str)`: [7](#0-6) 

This is the same class of bug as CVE-2020-35909: a decode/validate routine that looks like it safely returns a boolean/error but can instead throw on attacker-controlled malformed input, because the function's internal `try/catch` doesn't cover every code path that can raise an exception on bad input.

### Impact Explanation
If an uncaught exception is thrown synchronously anywhere inside the (largely synchronous, callback-driven) unit-validation call chain in `validation.js`, it is not converted into an `ifUnitError`/`ifJointError` callback — it propagates as a genuine JS exception. `network.js` installs a global `uncaughtException` handler that explicitly **re-throws to crash the process**: [8](#0-7) 

So any code path that reaches `isValidAddressAnyCase` (or any other call into `isValidChash`/`chash.isChashValid` that bypasses the `[A-Z2-7]{32}` regex) with a 32-character string of unexpected characters can crash the validating full node process when processing an incoming unit, AA trigger, or private-payment/device message that contains such a field — a single unprivileged unit poster can trigger a node-wide crash/DoS, i.e. "a network unable to confirm new units" if this is reachable broadly, or at minimum a node-disagreement/availability issue for any node hitting this code path.

### Likelihood Explanation
Medium: the bug is real (`separateIntoCleanDataAndChecksum` throwing outside the `try/catch` in `isChashValid` is a concrete, provable coding defect), and `isValidAddressAnyCase` is confirmed to exist and be referenced from `validation.js` (1 match found), but I was **not able to fully confirm within tool budget** the exact call site in `validation.js`/`definition.js` where `isValidAddressAnyCase` (as opposed to the regex-guarded `isValidAddress`) is invoked on unit-supplied data, nor whether that specific call site lacks an enclosing `try/catch`. This detail is necessary to be certain the throw is reachable end-to-end from a single posted unit without being intercepted. I recommend a background Devin session with full repo/grep access to pin down every caller of `isValidAddressAnyCase`/`isValidChash` and verify whether any of those calls (a) receive attacker-controlled 32-character strings that are not regex-filtered first, and (b) are not wrapped in a `try/catch` at the call site or in an ancestor synchronous frame before returning to the event loop.

### Recommendation
- Move the `try/catch` in `chash.isChashValid()` (chash.js:152-171) to cover the entire function body, not just the initial decode step, so any internal `Error` (e.g., "bad length=...") is converted to a `return false` instead of propagating.
- Add the same base32/base64 charset pre-check used in `isValidAddress` to `isValidAddressAnyCase` and any other caller of `isValidChash`, or make `isValidChash` itself charset-safe.
- Audit all call sites of `isValidChash`/`isValidAddressAnyCase` to ensure none receive unsanitized, attacker-controlled strings without either a preceding charset filter or a surrounding `try/catch`.

### Proof of Concept
Conceptually: an attacker crafts a unit (or AA trigger/private-payment/device message) containing a 32-character field that is validated via `isValidAddressAnyCase` (bypassing the `[A-Z2-7]{32}` filter used by `isValidAddress`) — e.g., a string containing lowercase letters or digits outside `2-7` that the `thirty-two` base32 decoder still decodes (without throwing) into a byte buffer whose bit length is not 160. When this string reaches `chash.isChashValid()`, `separateIntoCleanDataAndChecksum()` throws `Error("bad length=...")`, which is not caught anywhere in the chain, propagates up through `validation.js`, and is ultimately caught by the `process.on('uncaughtException', ...)` handler in `network.js:4530-4543`, which re-throws and crashes the node process handling that unit.

I could not empirically execute this PoC or confirm the precise unvalidated call site of `isValidAddressAnyCase` reachable from network input due to tool/search limits in this session — I recommend a Devin session with full source access to trace every caller of `isValidChash`/`isValidAddressAnyCase` to confirm the exact reachable, uncaught-exception path before treating this as fully confirmed exploitable.
