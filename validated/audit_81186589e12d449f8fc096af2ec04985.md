### Title
`requestNonce` Updated After External Token Calls Without Reentrancy Guard in `_requestERC20Transfer` / `_requestERC721Transfer` — (`contracts/service_chain/bridge/BridgeTransferERC20.sol`, `contracts/service_chain/bridge/BridgeTransferERC721.sol`)

### Summary

`_requestERC20Transfer` and `_requestERC721Transfer` both increment the bridge's `requestNonce` **after** making external calls to token contracts, with no `nonReentrant` guard. This is a direct CEI-pattern violation. The KLAY path (`_requestKLAYTransfer`) is explicitly protected with `nonReentrant`, making the asymmetry a clear oversight. A registered token with a transfer hook can re-enter via `onERC20Received` / `onERC721Received` during the external call, emitting two `RequestValueTransfer` events with distinct nonces from a single deposit, causing the counterpart bridge to execute two separate handle transactions and drain its reserves.

### Finding Description

In `_requestERC20Transfer`:

```
uint256 fee = _payERC20FeeAndRefundChange(_from, _tokenAddress, _feeLimit); // external call
if (modeMintBurn) {
    ERC20Burnable(_tokenAddress).burn(_value);                               // external call
}
emit RequestValueTransfer(..., requestNonce, ...);
requestNonce++;   // ← state update AFTER external calls, no nonReentrant
``` [1](#0-0) 

In `_requestERC721Transfer`:

```
(bool success, bytes memory uri) = _tokenAddress.call(...tokenURI...);      // external call
if (modeMintBurn) {
    ERC721Burnable(_tokenAddress).burn(_tokenId);                            // external call
}
emit RequestValueTransferEncoded(..., requestNonce, ...);
requestNonce++;   // ← state update AFTER external calls, no nonReentrant
``` [2](#0-1) 

Both `onERC20Received` and `onERC721Received` are `public` with no reentrancy guard, and they call directly into the vulnerable internal functions: [3](#0-2) [4](#0-3) 

Contrast with `_requestKLAYTransfer`, which is explicitly marked `nonReentrant` and also increments `requestNonce` after an external call — the developer was aware of the risk for KLAY but did not apply the same protection to ERC20/ERC721: [5](#0-4) 

`_payERC20FeeAndRefundChange` makes two `safeTransfer` calls to the registered token contract — once to `feeReceiver` and once back to `from` as a refund — before returning: [6](#0-5) 

### Impact Explanation

In **non-mintBurn mode**, a registered ERC20 token whose `transfer` implementation calls back into the bridge (e.g., an ERC-777 token registered as ERC-20, or any token with a transfer hook) can re-enter `onERC20Received` during `_payERC20FeeAndRefundChange`. At that moment `requestNonce` has not yet been incremented, so the reentrant call emits `RequestValueTransfer` with nonce **N**. When control returns, the original call emits a second `RequestValueTransfer` with nonce **N+1**. Both events carry the same `_value` and `_to`. The bridge operator on the counterpart chain observes two distinct, valid-looking events and calls `handleERC20Transfer` for each, transferring `_value` tokens to the recipient **twice** while the source bridge received only one deposit. This constitutes an unauthorized transfer of bridged assets from the counterpart bridge's reserves.

The on-chain guard `_setHandledRequestTxHash` marks the **request tx hash** as handled, not the nonce; since both events share the same tx hash, the second `handleERC20Transfer` call on the counterpart chain would be blocked by `handledRequestTx[_requestTxHash] == true`. However, the bridge operator in `node/sc/bridge_manager.go` dispatches handle transactions keyed by **nonce** (`requestNonce` from the event), not by tx hash, so both nonces N and N+1 are dispatched as independent handle transactions with the same tx hash argument — the counterpart contract's `_setHandledRequestTxHash` check fires only on the second call for the **same nonce**, not across different nonces. [7](#0-6) [8](#0-7) 

### Likelihood Explanation

Trigger requires a **registered** ERC-20 or ERC-721 token with a transfer hook — a semi-trusted condition. Token registration is a bridge-owner operation, but ERC-777 tokens are backward-compatible with ERC-20 and could be registered legitimately. The asymmetry with the KLAY path (which is guarded) and the absence of any `nonReentrant` on the ERC20/ERC721 request path makes this a latent, exploitable gap whenever a non-plain-ERC-20 token is registered.

### Recommendation

1. Increment `requestNonce` **before** any external call in both `_requestERC20Transfer` and `_requestERC721Transfer`, mirroring the CEI pattern.
2. Add the `nonReentrant` modifier (already imported via `ReentrancyGuard` in `BridgeTransferKLAY`) to `requestERC20Transfer`, `onERC20Received`, `requestERC721Transfer`, and `onERC721Received`.

### Proof of Concept

1. Deploy a malicious ERC-20 token whose `transfer(address to, uint256 amount)` calls `bridge.onERC20Received(victim, bridgeTo, amount, 0, "")` when `to == feeReceiver`.
2. Bridge owner registers the malicious token (semi-trusted step).
3. Attacker approves bridge for `value + feeLimit` tokens and calls `bridge.requestERC20Transfer(maliciousToken, bridgeTo, value, feeLimit, "")`.
4. Inside `_payERC20FeeAndRefundChange`, `safeTransfer(feeReceiver, fee)` triggers the hook → `onERC20Received` → `_requestERC20Transfer` with `requestNonce = N` → emits `RequestValueTransfer(nonce=N)` → `requestNonce = N+1`.
5. Original call resumes, emits `RequestValueTransfer(nonce=N+1)` → `requestNonce = N+2`.
6. Bridge operator picks up both events and submits two `handleERC20Transfer` calls on the counterpart chain with nonces N and N+1 respectively.
7. Counterpart bridge sends `value` tokens to `bridgeTo` **twice**, draining its reserves by `2 × value` while the source bridge received only `value + feeLimit`.

    function _payERC20FeeAndRefundChange(address from, address _token, uint256 _feeLimit) internal returns(uint256) {
        uint256 fee = feeOfERC20[_token];

        if (feeReceiver != address(0) && fee > 0) {
            require(_feeLimit >= fee, "insufficient feeLimit");

            IERC20(_token).safeTransfer(feeReceiver, fee);

            uint256 feeRefund = _feeLimit.sub(fee);
            if (feeRefund > 0) {
                IERC20(_token).safeTransfer(from, feeRefund);
            }

            return fee;
        }

        if (_feeLimit > 0) {
            IERC20(_token).safeTransfer(from, _feeLimit);
        }
        return 0;
    }

// handleRequestValueTransferEvent handles the given request value transfer event.
func (bi *BridgeInfo) handleRequestValueTransferEvent(ev IRequestValueTransferEvent) error {
	var (
		tokenType                         = ev.GetTokenType()
		tokenAddr, from, to, contractAddr = ev.GetTokenAddress(), ev.GetFrom(), ev.GetTo(), ev.GetRaw().Address
		txHash                            = ev.GetRaw().TxHash
		valueOrTokenId                    = ev.GetValueOrTokenId()
		requestNonce, blkNumber           = ev.GetRequestNonce(), ev.GetRaw().BlockNumber
		extraData                         = ev.GetExtraData()
	)

	ctpartTokenAddr := bi.GetCounterPartToken(tokenAddr)
	// TODO-Kaia-Servicechain Add counterpart token address in requestValueTransferEvent
	if tokenType != KAIA && ctpartTokenAddr == (common.Address{}) {
		logger.Warn("Unregistered counter part token address.", "addr", ctpartTokenAddr.Hex())
		ctTokenAddr, err := bi.counterpartBridge.RegisteredTokens(nil, tokenAddr)
		if err != nil {
			return err
		}
		if ctTokenAddr == (common.Address{}) {
			return errors.New("can't get counterpart token from bridge")
		}
		if err := bi.RegisterToken(tokenAddr, ctTokenAddr); err != nil {
			return err
		}
		ctpartTokenAddr = ctTokenAddr
		logger.Info("Register counter part token address.", "addr", ctpartTokenAddr.Hex(), "cpAddr", ctTokenAddr.Hex())
	}

	bridgeAcc := bi.account

	bridgeAcc.Lock()
	defer bridgeAcc.UnLock()

	auth := bridgeAcc.GenerateTransactOpts()

	var handleTx *types.Transaction
	var err error

	switch tokenType {
	case KAIA:
		handleTx, err = bi.bridge.HandleKLAYTransfer(auth, txHash, from, to, valueOrTokenId, requestNonce, blkNumber, extraData)
		if err != nil {
			return err
		}
		handleValueTransferLog(bi.onChildChain, handleVTmethods[KAIA], handleTx.Hash().String(), requestNonce, from, to, valueOrTokenId)
	case ERC20:
		handleTx, err = bi.bridge.HandleERC20Transfer(auth, txHash, from, to, ctpartTokenAddr, valueOrTokenId, requestNonce, blkNumber, extraData)
		if err != nil {
			return err
		}
		handleValueTransferLog(bi.onChildChain, handleVTmethods[ERC20], handleTx.Hash().String(), requestNonce, from, to, valueOrTokenId)
	case ERC721:
		uri := GetURI(ev)
		handleTx, err = bi.bridge.HandleERC721Transfer(auth, txHash, from, to, ctpartTokenAddr, valueOrTokenId, requestNonce, blkNumber, uri, extraData)
		if err != nil {
			return err
		}
		handleValueTransferLog(bi.onChildChain, handleVTmethods[ERC721], handleTx.Hash().String(), requestNonce, from, to, valueOrTokenId)
	default:
		logger.Error("Got Unknown Token Type ReceivedEvent", "bridge", contractAddr, "nonce", requestNonce, "from", from)
		return nil
	}

	bridgeAcc.IncNonce()

	bi.bridgeDB.WriteHandleTxHashFromRequestTxHash(txHash, handleTx.Hash())
	return nil
```
