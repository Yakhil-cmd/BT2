### Title
Webhook signature is verified against the organization derived from `repository.owner.login` while the actual write target is `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App (and therefore which `webhook_secret`) to validate the inbound HMAC signature against based on `repository_owner`, a value read straight out of the unauthenticated request body. All subsequent event handlers, however, resolve the repository/stack to act on using a *different* field of the same body: `repository.full_name`. Because the field that gates the cryptographic check (`repository.owner.login`) and the field that drives the actual write (`repository.full_name`) are never bound together, and are never cross-validated against each other, a payload can be crafted so it authenticates as one organization while acting on a stack belonging to another.

### Finding Description
`verify_signature` picks the `GithubApp` instance – and thus the HMAC secret used to verify `X-Hub-Signature` – purely from the payload: [1](#0-0) 

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

`Shipit.github(organization:)` resolves per-org config from `secrets.github`, and each org's webhook secret is optional ("Webhook secret (optional): Fill it with some randomly generated string" - `docs/setup.md`). `GitHubApp#verify_webhook_signature` explicitly bypasses HMAC checking entirely when no secret is configured for that organization: [2](#0-1) 

```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
```

Once the request passes `verify_signature`, `WebhooksController#create` dispatches the *entire raw JSON body* – unmodified – to the registered handlers: [3](#0-2) 

Every handler resolves the target stacks using `repository.full_name`, a field that was never inspected or bound during signature verification: [4](#0-3) 

```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
```

`PushHandler#process`, driven by `repository_name` derived from `full_name`, directly triggers a sync of the deployed head to an attacker-chosen `after` SHA for any matching, non-archived stack: [5](#0-4) 

The break in the trust binding is:
`org used to select webhook_secret (repository.owner.login)` ≠ `repository whose stacks are mutated (repository.full_name)`

Before the fix (bug class analog): both fields describe the same GitHub `repository` object in a legitimate delivery, so they always match, and the signature check is implicitly trusted as authorizing the repository being acted on. But the controller never enforces that `repository.owner.login` actually corresponds to the owner encoded in `repository.full_name` — nothing computes/validates `full_name.split('/').first == owner.login`. An attacker who can obtain (or is legitimately handed) a validly-signed webhook body for *any* one organization onboarded to this Shipit instance — including one whose `webhook_secret` is left blank per the documented "optional" setting, or one they administer themselves — can reuse/replay that valid signature/secret while substituting `repository.full_name` to point at a completely different, victim organization's repository/stack.

### Impact Explanation
This crosses the exact boundary called out as in-scope: "an organization that authenticated versus the repository that is written." Concretely, it allows:
- Forged `push` events causing `Stack#sync_github` to run against a stack belonging to a different, unrelated GitHub organization/repository than the one whose credentials/secret were actually used to authenticate the request — an unauthorized write into another repository's deploy state.
- Forged `status`/`check_suite` events that spoof CI/status data for arbitrary commits by sha, independent of which org authenticated, potentially unblocking merge/deploy gating that depends on those statuses (`app/models/shipit/webhooks/handlers/status_handler.rb`, `check_suite_handler.rb`).

This matches the "cross-repository writes" / "unauthorized deploy" High-severity impact class defined in scope, since it lets a request authenticated for org A mutate stack/commit state that belongs to org B, potentially manipulating the state Shipit uses to gate deploys (last-known head SHA, CI status).

### Likelihood Explanation
Likelihood is bounded by two factors that must be verified operationally (not fully confirmable from static code alone): (1) whether any onboarded organization in this specific deployment's `secrets.yml` has a blank `webhook_secret` (explicitly documented as optional), which would make forging any payload trivial without needing any secret at all; and (2) even where secrets are set, since the same App/webhook secret is often shared across an org's own installation, anyone with legitimate access to trigger real webhook deliveries for that one org (e.g., a low-privilege contributor able to push/open PRs in an org that's onboarded) can capture a validly-signed delivery and is only prevented from tampering with `repository.full_name` by HMAC coverage — which the code does enforce for the raw body. The primary concrete, code-provable gap is the "no secret configured" case, which is a real, code-reachable, unprivileged bypass with no other precondition.

### Recommendation
Bind the two fields together: after selecting the `github_app` used for verification, explicitly assert that `repository.full_name`'s owner segment equals `repository_owner` (the same value used to select the signing key), rejecting the request otherwise. Additionally, do not silently return `true` from `verify_webhook_signature` when `webhook_secret` is blank for multi-org configurations — either require a secret for every org or fail closed. This closes the gap where the authenticated organization and the mutated repository can diverge.

### Proof of Concept
1. Configure (or observe an existing) multi-org Shipit deployment where org `attacker-org` has no `webhook_secret` set (a documented "optional" field), while org `victim-org` hosts a monitored stack.
2. POST to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. `verify_signature` resolves `Shipit.github(organization: "attacker-org")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` unconditionally regardless of the (even absent) `X-Hub-Signature` header.
4. `PushHandler#process` resolves `stacks` via `payload.dig('repository', 'full_name')` = `"victim-org/victim-repo"`, and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` on the victim's stack — a write performed under no organization's actual cryptographic authorization.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
# frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
    end
  end
```
