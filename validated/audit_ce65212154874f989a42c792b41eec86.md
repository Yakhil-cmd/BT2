### Title
Cross-organization Team collision via `MembershipHandler#find_or_create_team!` grants membership on a Team belonging to another organization - ([File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`WebhooksController#repository_owner` falls back to `params.dig('organization', 'login')` when no `repository` key is present, so a `membership` webhook is authenticated solely against the organization the attacker names and controls. `MembershipHandler#find_or_create_team!` then does `Team.find_or_create_by!(github_id: params.team.id)`, which — on the "find" branch — returns any pre-existing `Team` row matching that `github_id` without ever checking that its `organization` column equals the verified `params.organization.login`. This lets an attacker with a self-configured GitHub organization/app add an arbitrary login as a member of a `Team` record that actually belongs to a different organization.

### Finding Description
Binding under test: `verified_organization (params.organization.login, checked in WebhooksController#verify_signature) == team.organization (the Team row mutated by MembershipHandler)`.

Trace:
- `app/controllers/shipit/webhooks_controller.rb:59-62` — `repository_owner` returns `params.dig('repository','owner','login') || params.dig('organization','login')`. A `membership` event payload has no `repository` key, so `repository_owner` resolves to the attacker-supplied `organization.login`.
- `verify_signature` (lines 24-30) calls `Shipit.github(organization: repository_owner)` and verifies the HMAC signature using **that organization's own configured `webhook_secret`**. If the attacker has set up their own GitHub org (`attacker-org`) as a configured organization in Shipit (a legitimate, attacker-controlled tenant), they know that org's `webhook_secret` and can produce a valid signature for a payload whose `organization.login` is `"attacker-org"`. The signature check is thus scoped to "this request is really from attacker-org," not to "this request may only touch attacker-org's own data."
- `app/models/shipit/webhooks/handlers/membership_handler.rb:38-43`:
```ruby
def find_or_create_team!
  Team.find_or_create_by!(github_id: params.team.id) do |team|
    team.github_team = params.team
    team.organization = params.organization.login
  end
end
```
`find_or_create_by!` first performs a `find_by(github_id: params.team.id)`. If a row already exists (e.g., a legitimate `Team` fixture/record with `organization: "victim-org", github_id: 42`), that row is returned as-is — the block (which sets `organization`) only runs on creation, so the existing `organization` field is **never re-validated or checked** against `params.organization.login`.
- Back in `process` (lines 22-33), `team.add_member(User.find_or_create_by_login!(params.member.login))` is then called on that returned (victim) team, appending the attacker-controlled `member.login` as a member of `victim-org`'s team.

No other guard intervenes: `verify_signature` only authenticates that the payload came from the org named in it; it does not bind the payload's `team.id` to that org, and `ExplicitParameters` (`params do ... end`) only validates types/presence, not cross-record ownership. `Team#organization` is used elsewhere (e.g., `github_hooks` association, `Shipit.github_teams` authorization checks) as the trust boundary for which org a team belongs to, but that field is bypassed here on the find path.

Exploit flow:
1. Attacker registers/configures their own GitHub organization `attacker-org` in Shipit (this is legitimate self-service configuration, not a stolen secret) and obtains its `webhook_secret`.
2. Attacker learns/guesses a target `Team.github_id` that already exists in Shipit for `victim-org` (team IDs are visible via GitHub's public API for the victim's real team, or via any Shipit UI/API exposing team info).
3. Attacker crafts a `membership` event JSON: `{"action":"added","team":{"id":<victim_team_github_id>,...},"organization":{"login":"attacker-org"},"member":{"login":"attacker-controlled-login"}}`, signs it with `attacker-org`'s `webhook_secret`, and POSTs to `/webhooks` with `X-Github-Event: membership`.
4. `verify_signature` succeeds because the signature is valid for `attacker-org`.
5. `find_or_create_team!` finds the existing `victim-org` `Team` row by `github_id` and returns it unchanged.
6. `team.add_member(...)` adds the attacker's chosen login as a member of the victim org's team.

### Impact Explanation
This is a real authentication/authorization-boundary bypass: an attacker who authenticates as `attacker-org` can write a `Membership` record binding an arbitrary GitHub login to a `Team` belonging to `victim-org`. If that team is referenced by `Shipit.github_teams` (used for authorization elsewhere in the engine per `lib/shipit.rb` and `app/models/shipit/user.rb`), the attacker (or a user they control) gains membership-based authorization they should not have — matching the High severity category "escalation into `Shipit.github_teams` authorization." It is repeatable against any `Team.github_id` the attacker can enumerate, for any target organization, as long as the attacker controls one webhook-registered organization of their own.

### Likelihood Explanation
Preconditions: (1) Shipit must be configured to accept webhooks from multiple organizations (multi-tenant `Shipit.github(organization:)` lookup, which is the documented normal deployment model), and the attacker must control/register one such organization with its own `webhook_secret`. (2) The attacker needs to know a target `Team`'s `github_id` (GitHub team IDs are numeric and often discoverable/enumerable, or knowable if the attacker was previously in that org). (3) A `Team` row for the victim org must already exist in Shipit's database (created by a prior legitimate `membership` webhook for the real team). Given these are plausible in any multi-org deployment, the attack is feasible and cheap: one crafted HTTP POST per exploitation attempt, fully repeatable.

### Recommendation
In `find_or_create_team!`, do not blindly trust the found record on `github_id` collision — verify `team.organization == params.organization.login` before returning it (or on the found branch, e.g. `Team.find_by(github_id: params.team.id)` and raise/ignore if `team.organization != params.organization.login`, only falling back to create when no team exists). Alternatively, scope the `find_or_create_by!` lookup to `github_id: params.team.id, organization: params.organization.login` so cross-organization collisions can never be found/reused.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/membership_handler_test.rb
test "does not add a member to a team belonging to a different organization when github_id collides" do
  victim_team = Shipit::Team.create!(
    github_id: 424242,
    organization: 'victim-org',
    slug: 'core',
    name: 'Core',
    api_url: 'https://example.com/victim-org/core'
  )

  payload = {
    'action' => 'added',
    'team' => { 'id' => 424242, 'name' => 'Core', 'slug' => 'core', 'url' => 'https://example.com/victim-org/core' },
    'organization' => { 'login' => 'attacker-org' },
    'member' => { 'login' => 'attacker-controlled-login' },
  }

  Shipit::Webhooks::Handlers::MembershipHandler.new.call(payload)

  attacker_user = Shipit::User.find_by(login: 'attacker-controlled-login')
  # Binding check: the organization that authenticated the request ("attacker-org")
  # must not equal the organization owning the mutated team ("victim-org"), yet
  # membership was still granted -- proving the missing check.
  assert_equal 'victim-org', victim_team.reload.organization
  assert_includes victim_team.members, attacker_user
end
```
