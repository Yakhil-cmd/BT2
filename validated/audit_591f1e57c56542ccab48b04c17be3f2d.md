Based on my investigation, I found a genuine analog in the encoding scheme used for AA data-feed lookups.

### Title
Hardcoded 32-bit `0xFFFFFFFF` Width Assumption in `encodeMci`/`getMciFromDataFeedKey` Allows Data-Feed Key Corruption via Unbounded `min_mci` in `data_feed()` Oscript Calls - (File: `string_utils.js`)

### Summary
`string_utils.encodeMci()` reverses an MCI for lexicographic sorting by subtracting it from the hardcoded constant `0xFFFFFFFF` (32-bit width), exactly mirroring the reported bug class: an offset/width constant is hardcoded assuming values never exceed a fixed bit-width, and the function silently produces corrupted output rather than rejecting out-of-range input when that assumption is violated.

### Finding Description
`encodeMci` and its inverse `getMciFromDataFeedKey` are defined as: [1](#0-0) 

These functions assume `mci` always fits within 32 bits. `readDataFeedValueByParams` (invoked from AA formula evaluation for the `data_feed()` oscript function) takes `min_mci` directly from AA-trigger-controlled `params` and only validates that it is a non-negative integer, with no upper bound check: [2](#0-1) 

This `min_mci` is then fed into `encodeMci` to build LevelDB range-query keys for the data-feed store: [3](#0-2) [4](#0-3) 

If `min_mci` (or `max_mci`, wherever attacker-influenced) exceeds `0xFFFFFFFF` (4294967295), `0xFFFFFFFF - mci` becomes negative, and `.toString(16).padStart(8,'0')` no longer yields a fixed-width, correctly-ordered hex string — exactly the same failure mode as `phaseId()` silently truncating/misinterpreting round IDs wider than the hardcoded 64-bit `PHASE_OFFSET`.

### Impact Explanation
A corrupted or malformed reversed-MCI key changes the LevelDB range boundaries (`gte`/`lte`) used to look up oracle data-feed values for an AA trigger. This can cause the data-feed value returned to an AA (or the "not found" result) to no longer correspond to the intended MCI window, since the reported issue's impact category is about bypassing checks that are supposed to gate correct behavior — here the check is "return a value only within `[min_mci, max_mci]`". Since AAs commonly gate fund transfers, price-based payouts, or timelocks on `data_feed()` results, a wrong or bypassed range check could lead to AA fund loss or incorrect state transitions if a bogus/wrong-window value is used in financial logic.

### Likelihood Explanation
Exploitability requires an AA-author-crafted `data_feed()` call with an extreme `min_mci` (e.g., `Number.MAX_SAFE_INTEGER` or any value > 4294967295), which is straightforward for any AA author to construct in an AA's oscript definition; `isNonnegativeInteger` does not clamp the magnitude. However, I could not fully verify, given tool-call limits, whether an equivalent upper-bound check exists elsewhere in `formula/validation.js` or `formula/evaluation.js` before `min_mci` reaches `data_feeds.js` — this is a real uncertainty in my analysis and should be confirmed by inspecting `formula/evaluation.js`'s `data_feed` case in full and `formula/validation.js`'s bounds checks. If such a check exists there and clamps `min_mci` to `< 2^32`, the practical severity of this analog drops substantially.

### Recommendation
Add an explicit upper-bound check on `min_mci`/`max_mci` in `data_feeds.js`'s `readDataFeedValueByParams` (and any other entry point relying on `encodeMci`), rejecting values outside the actually-representable range (`0` to `0xFFFFFFFF`), or migrate `encodeMci`/`getMciFromDataFeedKey` to a wider fixed-width scheme (e.g., using `BigInt`/48-bit or 64-bit hex padding) that matches realistic future MCI growth headroom, and add unit tests asserting correct rejection/ordering at and beyond the boundary.

### Proof of Concept
Conceptually:
1. An AA author defines a trigger-time `data_feed({ oracles: [...], feed_name: 'X', min_mci: 999999999999 })` — a value that easily passes `ValidationUtils.isNonnegativeInteger`.
2. `readDataFeedValueByParams` forwards this to `readDataFeedValue` → `readDataFeedByAddress`, which calls `string_utils.encodeMci(min_mci)`.
3. `0xFFFFFFFF - 999999999999` is a large negative number; `.toString(16)` produces a signed hex string of variable, non-fixed width, breaking the assumed lexicographic key layout used for the LevelDB `gte`/`lte` range bounds.
4. The resulting range query against the `df\n<address>\n<feed_name>\n...` key space no longer correctly bounds by MCI, potentially returning a value outside the intended window or none at all, feeding an incorrect result into AA logic that trusts the MCI-bounded lookup.

I was not able to execute this against a live node in this environment to confirm the exact corrupted string output and its practical query effect — this should be verified with a targeted unit test analogous to the existing `test/string_utils.test.js` `encodeMci`/`getMciFromDataFeedKey` tests, extended to boundary/overflow values.

function encodeMci(mci){
	return (0xFFFFFFFF - mci).toString(16).padStart(8, '0'); // reverse order for more efficient sorting as we always need the latest

function getMciFromDataFeedKey(key){
	var arrParts = key.split('\n');
	var strReversedMci = arrParts[arrParts.length-1];
	var reversed_mci = parseInt(strReversedMci, 16);
	var mci = 0xFFFFFFFF - reversed_mci;
	return mci;
}
