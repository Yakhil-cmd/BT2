### Title
Bridge `handle*Transfer` Functions Bypass `isRunning` and Token-Lock Guards, Allowing Asset Drain After Emergency Stop — (`contracts/service_chain/bridge/BridgeTransferKLAY.sol`, `BridgeTransferERC20.sol`, `BridgeTransferERC721.sol`)

---

### Summary

The Kaia service-chain bridge has an asymmetric protection model: the **request** path enforces `isRunning` and per-asset lock checks, but the **handle** path (which actually moves assets out of the bridge) enforces neither. When the bridge owner invokes the emergency stop (`start(false)`, `lockKLAY()`, or `lockToken()`), bridge operators can still call `handleKLAYTransfer`, `handleERC20Transfer`, and `handleERC721Transfer` to transfer KLAY and bridged tokens out of the bridge contract.

---

### Finding Description

**Request path — checks present:**

`_requestKLAYTransfer` applies the `unlockedKLAY` modifier and `require(isRunning, "stopped bridge")`: [1](#0-0) 

`_requestERC20Transfer` applies `onlyUnlockedToken(_tokenAddress)` and `require(isRunning, "stopped bridge")`: [2](#0-1) 

`_requestERC721Transfer` applies `onlyUnlockedToken(_tokenAddress)` and `require(isRunning, "stopped bridge")`: [3](#0-2) 

**Handle path — checks absent:**

`handleKLAYTransfer` carries only `onlyOperators` and `nonReentrant`; no `isRunning` or `isLockedKLAY` check. It unconditionally sends `_value` KLAY to `_to`: [4](#0-3) 

`handleERC20Transfer` carries only `onlyOperators`; no `isRunning` or `onlyUnlockedToken` check. It mints or transfers `_value` tokens to `_to`: [5](#0-4) 

`handleERC721Transfer` carries only `onlyOperators`; no `isRunning` or `onlyUnlockedToken` check. It mints or transfers the NFT to `_to`: [6](#0-5) 

The `isRunning` flag and the lock flags are defined and toggled in the base contracts: [7](#0-6) [8](#0-7) 

The off-chain relayer (`BridgeInfo.handleRequestValueTransferEvent`) calls all three handle functions unconditionally — it does not query `isRunning` or any lock state before submitting the on-chain transaction: [9](#0-8) 

---

### Impact Explanation

When the bridge owner calls `start(false)` or `lockKLAY()` / `lockToken()` to halt the bridge (e.g., because the counterpart chain is compromised and emitting fraudulent `RequestValueTransfer` events), the automated relayer continues to observe those events and submit `handleKLAYTransfer` / `handleERC20Transfer` / `handleERC721Transfer` transactions. Because the handle functions contain no `isRunning` or lock guard, those transactions succeed and KLAY or bridged ERC-20/ERC-721 tokens are transferred out of the bridge to attacker-controlled addresses.

The corrupted value is the bridge's KLAY balance and/or ERC-20/ERC-721 token holdings — a direct unauthorized transfer of bridged assets.

---

### Likelihood Explanation

The relayer is an automated process (`processingPendingRequestEvents`) that does not inspect the destination bridge's `isRunning` flag before calling handle functions. Any scenario that causes the bridge owner to stop the bridge while the relayer is still running (source-chain exploit, operator key compromise, or simply a race condition between the stop transaction and in-flight relayer submissions) triggers the bypass. The operators are semi-trusted but the relayer code contains no defensive check, making accidental exploitation realistic.

---

### Recommendation

Add `require(isRunning, "stopped bridge")` to all three handle functions. For KLAY, also add the `unlockedKLAY` modifier; for ERC-20 and ERC-721, add `onlyUnlockedToken(_tokenAddress)`. This mirrors the protection already present on the request path and gives the bridge owner a complete, atomic emergency stop:

```solidity
// BridgeTransferKLAY.sol
function handleKLAYTransfer(...) public onlyOperators unlockedKLAY nonReentrant {
    require(isRunning, "stopped bridge");
    ...
}

// BridgeTransferERC20.sol
function handleERC20Transfer(...) public onlyOperators onlyUnlockedToken(_tokenAddress) {
    require(isRunning, "stopped bridge");
    ...
}

// BridgeTransferERC721.sol
function handleERC721Transfer(...) public onlyOperators onlyUnlockedToken(_tokenAddress) {
    require(isRunning, "stopped bridge");
    ...
}
```

---

### Proof of Concept

1. Deploy the bridge with KLAY balance (e.g., 1000 KLAY via `chargeWithoutEvent`).
2. Register an operator account.
3. Call `bridge.start(false)` from the owner — bridge is now stopped.
4. Verify: `bridge.requestKLAYTransfer(...)` reverts with `"stopped bridge"`. ✓
5. Call `bridge.handleKLAYTransfer(txHash, attacker, attacker, 1000 ether, 0, 1, "0x")` from the operator account.
6. Observe: the call **succeeds** and 1000 KLAY is transferred to `attacker`, despite `isRunning == false`.

The same sequence applies with `lockKLAY()` instead of `start(false)`, and with `handleERC20Transfer` / `handleERC721Transfer` after `lockToken()`.

// handleRequestValueTransferEvent handles the given request value transfer event.
func (bi *BridgeInfo) handleRequestValueTransferEvent(ev IRequestValueTransferEvent) error {
	var (
		tokenType                         = ev.GetTokenType()
		tokenAddr, from, to, contractAddr = ev.GetTokenAddress(), ev.GetFrom(), ev.GetTo(), ev.GetRaw().Address
		txHash                            = ev.GetRaw().TxHash
		valueOrTokenId                    = ev.GetValueOrTokenId()
		requestNonce, blkNumber           = ev.GetRequestNonce(), ev.GetRaw().BlockNumber
		extraData                         = ev.GetExtraData()
	)

	ctpartTokenAddr := bi.GetCounterPartToken(tokenAddr)
	// TODO-Kaia-Servicechain Add counterpart token address in requestValueTransferEvent
	if tokenType != KAIA && ctpartTokenAddr == (common.Address{}) {
		logger.Warn("Unregistered counter part token address.", "addr", ctpartTokenAddr.Hex())
		ctTokenAddr, err := bi.counterpartBridge.RegisteredTokens(nil, tokenAddr)
		if err != nil {
			return err
		}
		if ctTokenAddr == (common.Address{}) {
			return errors.New("can't get counterpart token from bridge")
		}
		if err := bi.RegisterToken(tokenAddr, ctTokenAddr); err != nil {
			return err
		}
		ctpartTokenAddr = ctTokenAddr
		logger.Info("Register counter part token address.", "addr", ctpartTokenAddr.Hex(), "cpAddr", ctTokenAddr.Hex())
	}

	bridgeAcc := bi.account

	bridgeAcc.Lock()
	defer bridgeAcc.UnLock()

	auth := bridgeAcc.GenerateTransactOpts()

	var handleTx *types.Transaction
	var err error

	switch tokenType {
	case KAIA:
		handleTx, err = bi.bridge.HandleKLAYTransfer(auth, txHash, from, to, valueOrTokenId, requestNonce, blkNumber, extraData)
		if err != nil {
			return err
		}
		handleValueTransferLog(bi.onChildChain, handleVTmethods[KAIA], handleTx.Hash().String(), requestNonce, from, to, valueOrTokenId)
	case ERC20:
		handleTx, err = bi.bridge.HandleERC20Transfer(auth, txHash, from, to, ctpartTokenAddr, valueOrTokenId, requestNonce, blkNumber, extraData)
		if err != nil {
			return err
		}
		handleValueTransferLog(bi.onChildChain, handleVTmethods[ERC20], handleTx.Hash().String(), requestNonce, from, to, valueOrTokenId)
	case ERC721:
		uri := GetURI(ev)
		handleTx, err = bi.bridge.HandleERC721Transfer(auth, txHash, from, to, ctpartTokenAddr, valueOrTokenId, requestNonce, blkNumber, uri, extraData)
		if err != nil {
			return err
		}
		handleValueTransferLog(bi.onChildChain, handleVTmethods[ERC721], handleTx.Hash().String(), requestNonce, from, to, valueOrTokenId)
	default:
		logger.Error("Got Unknown Token Type ReceivedEvent", "bridge", contractAddr, "nonce", requestNonce, "from", from)
		return nil
	}

	bridgeAcc.IncNonce()

	bi.bridgeDB.WriteHandleTxHashFromRequestTxHash(txHash, handleTx.Hash())
	return nil
