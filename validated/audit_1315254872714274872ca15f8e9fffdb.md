### Title
Webhook signature is verified against an attacker-chosen organization while handlers act on an unverified `repository.full_name` from the same payload - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which `GitHubApp` (and thus which `webhook_secret`) is used to authenticate an inbound webhook based on a field it extracts from the *unverified* JSON body itself, then, once "verified", `WebhooksController#create` dispatches the *entire same body* to handlers that key off a *different* field of that body to decide which `Stack`/`Repository` to mutate. The organization whose secret authenticated the request is never checked against the repository the handlers actually act on.

### Finding Description
`verify_signature` computes the organization to authenticate against directly from attacker-controlled JSON, with a fallback path: [1](#0-0) [2](#0-1) 

```ruby
def repository_owner
  # Fallback to the organization sub-object if repository isn't included in the payload
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

`Shipit.github(organization: repository_owner)` looks up a per-organization `GitHubApp`/`webhook_secret` in multi-org deployments: [3](#0-2) 

Signature verification simply HMACs the raw body with that organization's secret — and if that organization's `webhook_secret` is blank/unset (documented as optional, `webhook_secret: # nil` is the shipped default), verification is skipped entirely: [4](#0-3) 

Once "verified", the controller forwards the *whole* raw payload to every registered handler for the event: [5](#0-4) 

But every handler resolves the repository/stack to mutate purely from `repository.full_name` in that same payload — a field completely independent from `repository_owner`/`organization.login` used for signature selection: [6](#0-5) [7](#0-6) [8](#0-7) 

The invariant that should hold is:
`organization_whose_secret_authenticated_the_request == owner_of(repository.full_name)_that_handlers_mutate`

Before an attack (genuine GitHub webhooks), GitHub itself sets `organization.login`/`repository.owner.login` and `repository.full_name` consistently to the same repo/org, so the equality holds implicitly. There is no code that actually enforces it — the invariant is coincidental, exactly analogous to how `MagicLpAggregator.latestAnswer()` coincidentally produced correct answers only because both tokens happened to share 18 decimals, while nothing in the code actually enforced that constraint.

After the attack: this repository is explicitly documented to support multiple independent GitHub organizations sharing one Shipit instance, each with its own (optionally blank) `webhook_secret`: [9](#0-8) [10](#0-9) 

An unprivileged remote attacker (no Shipit session, no `ApiClient` token, no GitHub App key) can POST directly to `/webhooks` with a crafted body where:
- `organization.login` (or `repository.owner.login`) = an org whose `webhook_secret` is blank/unset (a supported, documented configuration) or an org the attacker otherwise knows the secret for, so `verify_signature` passes trivially, and
- `repository.full_name` = any *other* tracked repository/org's full name, e.g. `"victim-org/victim-repo"`.

`verify_signature` authenticates against the harmless/blank-secret organization, but every downstream handler (`PushHandler`, `StatusHandler`, `CheckSuiteHandler`, `PullRequest::*Handler`) acts on `repository.full_name`, i.e. on the victim organization's stacks — an organization the attacker was never authenticated for.

### Impact Explanation
This breaks the "organization authenticated vs. repository written" binding required by the rules. Concretely, a fully unauthenticated request can:
- Forge `push` events to trigger `stack.sync_github` on arbitrary tracked stacks (cross-repository writes) via `PushHandler#process` [11](#0-10) .
- Forge `status`/`check_suite` events to create fake passing CI `Status`/CheckRun records for arbitrary commits in unrelated repositories, which can satisfy merge-queue/continuous-deployment gating checks and lead to unauthorized deploys.
- Forge `pull_request` events to open/close/archive review stacks belonging to a different, unrelated organization.

This is a cross-repository-write / unauthorized-deploy-class issue reachable by any unprivileged remote party, matching the Critical impact bucket.

### Likelihood Explanation
Any Shipit instance that (a) tracks more than one GitHub organization/repository (a documented, supported configuration) or (b) has any organization configured with a blank `webhook_secret` (the documented default) is exploitable with a single unauthenticated HTTP request; no credentials, session, or GitHub access are required.

### Recommendation
After picking the `GitHubApp`/secret used for HMAC verification in `verify_signature`, re-derive the repository owner from `repository.full_name` (the field handlers actually use) and require it to match the organization that was authenticated, rejecting the webhook (422) on mismatch. Do not allow `organization.login` to silently satisfy verification for a `repository.full_name` belonging to a different organization.

### Proof of Concept
1. Configure Shipit with two organizations, e.g. as in `test/dummy/config/secrets_double_github_app.yml`, where `OrgTwo.webhook_secret` is blank/nil (documented-supported: "Webhook secret (optional)").
2. Craft a POST to `/webhooks` with header `X-Github-Event: push` and JSON body:
```json
{
  "organization": { "login": "OrgTwo" },
  "repository": { "full_name": "OrgOne/victim-repo" },
  "ref": "refs/heads/main",
  "after": "<attacker chosen sha>"
}
```
(no `repository.owner.login` key, so `repository_owner` falls back to `organization.login` = `"OrgTwo"`).
3. `verify_signature` calls `Shipit.github(organization: "OrgTwo")`; since `OrgTwo.webhook_secret` is blank, `verify_webhook_signature` returns `true` unconditionally — no valid `X-Hub-Signature` header is even required.
4. `WebhooksController#create` dispatches the parsed body to `PushHandler`, which resolves `stacks` via `payload.dig('repository', 'full_name')` = `"OrgOne/victim-repo"`, and calls `stack.sync_github(expected_head_sha: ...)` on `OrgOne`'s stack — an organization never checked during authentication.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

### Using Multiple Github Applications

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently. The top-level keys should be the name of each Github organization, and the following sub-keys are the Github app details for that particular organization.

    someothergithuborg:

      installation_id:
      webhook_secret:
