### Title
Cross-organization forged commit status / stack sync via webhook signature not bound to the acted-upon repository or commit - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/status_handler.rb`, `app/models/shipit/webhooks/handlers/handler.rb`)

### Summary
`WebhooksController#verify_signature` verifies the HMAC signature of an inbound GitHub webhook using the GitHub App/organization secret selected by `repository_owner`, a value read straight out of the attacker-controlled JSON body (`params.dig('repository','owner','login')`). Once the signature check passes, the actual handlers that mutate state (`Shipit::Webhooks::Handlers::StatusHandler`, `Shipit::Webhooks::Handlers::Handler#stacks`/`PushHandler`) act on *different* fields of that same attacker-controlled body — `sha` (matched globally with zero repository scoping) and `repository.full_name` respectively — without re-checking that those fields belong to the organization whose secret produced the signature. This is the same class of bug as the reported `Spoke.requestCallback()` issue: the entity that is cryptographically authenticated (the organization owning the webhook secret) is not the entity that is ultimately written to (an arbitrary repository/commit belonging to any org tracked by the Shipit instance).

### Finding Description
`app/controllers/shipit/webhooks_controller.rb`:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) 

The signature is checked against the webhook secret of whatever organization the attacker names in `repository.owner.login` inside the raw JSON body they control. Because the HTTP request is a direct POST to `/github/webhooks` (not a value GitHub itself enforces to be internally consistent), nothing prevents the attacker from putting one organization's login in `repository.owner.login` (to select the secret they know) while putting a *different* organization/repository's identifiers in the fields the handlers actually act on.

Once past signature verification, `Shipit::Webhooks.for_event(event)` handlers run on the full, attacker-controlled `params` [2](#0-1) :

- `StatusHandler#process` resolves target records purely by commit SHA, with no repository/organization scoping at all:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [3](#0-2) 
`sha` is a global, cross-tenant lookup key across every `Commit` row in the whole Shipit instance, regardless of which repository/organization it belongs to.

- `Handler#stacks`/`Handler#repository_name` (used by `PushHandler`) resolves the repository from `payload.dig('repository', 'full_name')` — a field independent of `repository.owner.login` used in signature verification:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [4](#0-3) 

Root cause equality: the verified organization (`repository_owner` used to pick the HMAC secret) is **not equal to** the repository/commit acted upon (`repository.full_name` / `sha`), and no code path enforces that equality. `Repository.from_github_repo_name` merely splits the attacker-supplied string on `/` and does a DB lookup [5](#0-4) , with no cross-check against `repository_owner`.

### Impact Explanation
An attacker who administers (or otherwise knows the webhook secret of) **any single GitHub organization/repository that is registered as a Shipit stack** — a low-privilege, self-service action since anyone can add their own repo as a stack and configure its own GitHub App/webhook secret — can forge signed webhook deliveries to Shipit's shared webhook endpoint that are attributed to their own org for authentication purposes, but whose payload content targets a completely different, victim-owned repository or commit:

- Via a forged `status` event: set `sha` to any commit SHA tracked by any other stack in the Shipit instance and `state: "success"` with an arbitrary `context`. `StatusHandler` will call `commit.create_status_from_github!(params)` on that victim commit with no ownership check, injecting a fabricated passing CI status. Since `Commit#deployable?` and `Stack#schedule_continuous_delivery`/`Status::Group` gate deploy eligibility on `success?`/required statuses [6](#0-5)  and continuous delivery is scheduled automatically when a commit becomes deployable [7](#0-6) , this can be used to satisfy required CI checks (`ci.require`) and trigger an **unauthorized deploy** on a victim stack that has continuous deployment enabled — a Critical impact per the rules.
- Via a forged `push` event: set `repository.full_name` to a victim repository, causing `PushHandler` to enqueue `GithubSyncJob` (`stack.sync_github(expected_head_sha: ...)`) on the victim's stack using the attacker's own webhook signature.

This breaks the binding "an organization that authenticated versus the repository that is written," exactly matching the analog class called out in the rules.

### Likelihood Explanation
Likelihood is high for any Shipit deployment that supports more than one GitHub organization/App (multi-tenant use, or any environment where users can self-register stacks/orgs with their own webhook secret, as implied by `Shipit.github(organization:)` resolving per-org config). The attacker only needs write access to one low-value/self-controlled repository and its associated webhook secret — no `ApiClient` token, no GitHub App private key, no privileged Shipit account, and no repository write access to the victim repo are required, matching the "unprivileged-attacker" threat model in scope.

### Recommendation
After verifying the HMAC signature, enforce that every field the handler subsequently acts on (`repository.full_name` for `PushHandler`/other repo-scoped handlers, and the owning repository of any `Commit` matched by `sha` in `StatusHandler`) belongs to the same organization (`repository_owner`) whose secret produced a valid signature. Concretely:
- In `Handler#stacks`, verify `Repository.from_github_repo_name(repository_name)&.owner == payload.dig('repository','owner','login')` (or otherwise thread the authenticated organization into every handler and assert equality before acting).
- In `StatusHandler#process`, scope the `Commit.where(sha: ...)` lookup to commits whose `stack.repository.owner` matches the authenticated `repository_owner`, rejecting/ignoring commits belonging to other organizations.

### Proof of Concept
1. Register/administer GitHub org `attacker-org` and its own repo as a Shipit stack; obtain its webhook secret (self-configured, no privilege needed).
2. Note a commit SHA `SHA_VICTIM` belonging to an unrelated stack `victim-org/victim-repo` tracked by the same Shipit instance (e.g., visible via Shipit's public commit/task pages).
3. Craft a `status` event JSON body:
```json
{
  "sha": "SHA_VICTIM",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "attacker-org/attacker-repo" }
}
```
4. Compute `X-Hub-Signature: sha1=<hmac(attacker-org secret, body)>` and POST it to `/github/webhooks` with `X-Github-Event: status`.
5. `WebhooksController#verify_signature` resolves `repository_owner => "attacker-org"`, fetches `attacker-org`'s app, and successfully verifies the signature.
6. `StatusHandler.call(params)` runs `Commit.where(sha: "SHA_VICTIM")` — matching the victim's commit — and calls `create_status_from_github!`, injecting a fabricated "success" status onto the victim stack's commit, independent of the victim organization's actual webhook secret or CI results.
