### Title
Private assets sent to an Autonomous Agent (AA) address become permanently unspendable, freezing the sender's funds forever - ([File: aa_composer.js])

### Summary
Any unprivileged asset issuer or unit poster can create a private (hidden) asset and pay it to any AA address. Once received, the funds can never be moved out of the AA, because the AA-generated response units are structurally forbidden from carrying private-asset payment payloads. This permanently locks the value inside the AA with no recovery path, mirroring the reported class of bug ("payable contract, no way to withdraw funds").

### Finding Description
Ocore's Autonomous Agents receive coins via ordinary or private payment outputs sent to the AA's deterministic address. When an AA composes its response unit, the payment-message builder in `sendUnit()`/`completePaymentPayload()` explicitly rejects any attempt to build an outgoing payment for a private asset: [1](#0-0) 

The comment on this line ("it'll fail validation anyway due to lack of spend_proofs") points to the deeper, protocol-level restriction: AA-authored units are not permitted to carry `spend_proofs` at all, which are mandatory for spending any private-asset output: [2](#0-1) 

Since private assets can only be spent by presenting valid `spend_proofs` chained from the private payment history (see `validatePayment`/`is_private` handling in `validation.js`), and an AA is categorically barred from including `spend_proofs` in any message it authors, an AA address can never construct a valid outgoing transfer of a private asset it received. Unlike a normal wallet address (controlled by a private key and free to sign any withdrawal), an AA address's only spending path is through the deterministic `handleTrigger`/`sendUnit` logic in `aa_composer.js`, which unconditionally refuses this operation. There is no admin, owner, or definer override for AAs — the AA's spending logic is fixed by its `oscript` definition and by the composer's protocol-level restrictions, so no future trigger, however crafted, can retrieve the private-asset balance. The dedicated `aa_balances` bootstrap query even explicitly excludes private outputs from being counted as AA balance in the first place, confirming these funds are treated as unreachable by design: [3](#0-2) 

Any unprivileged user (an asset issuer defining `is_private: true`, and any counterparty transacting in that asset) can trigger this simply by directing a private payment chain to an AA address as part of ordinary use of the asset — no special network or hub privileges are required.

### Impact Explanation
Coins/tokens of a private asset sent to any AA address are irrecoverably lost. This is a direct, permanent AA fund freezing condition reachable by an ordinary counterparty in a private payment, with no way for the AA definer, the sender, or any future trigger to recover the value. For AAs that are designed to accept diverse assets (e.g., generic "accept any payment" AAs, exchanges, or marketplaces), this results in silent, unrecoverable loss of user funds whenever a private asset is used, satisfying the "AA fund loss or freezing" impact bar.

### Likelihood Explanation
Likelihood is high in practice for any AA that does not explicitly reject non-base/unlisted assets, since private assets are an ordinary, first-class asset type in Obyte (`is_private: true` in the `asset` message), and any user can issue one and pay it to any address, including AA addresses, without any special conditions. No cooperation from the AA owner, network operators, or hubs is required — a single private-asset holder acting alone can lock funds into an AA.

### Recommendation
- Reject payments of private assets to AA addresses at protocol validation time (e.g., extend `checkNotAAs`-style checks in `validation.js` to forbid `is_private` asset payment outputs whose destination address is a known AA, similar to how bounce-fee checks already inspect AA outputs in `aa_addresses.js`), so senders get an explicit, early failure instead of silently losing funds.
- Alternatively, document this behavior prominently and have wallets warn/block private-asset payments to AA addresses (analogous to the existing `checkAAOutputs` bounce-fee warning in `aa_addresses.js`), preventing accidental fund loss without requiring a consensus change.

### Proof of Concept
1. Issue a new private (`is_private: true`) divisible or indivisible asset via a normal `asset` definition message — any unprivileged user can do this.
2. Compose and send a private payment of this asset to any existing AA's address (a normal wallet-level operation using `divisible_asset.js`/`indivisible_asset.js` private payment composition, exactly as one would pay any other address).
3. The private payment chain validates and is saved normally (private payments are validated the same way regardless of recipient type; see `validatePayment` in `validation.js`), crediting an output at the AA's address.
4. Trigger the AA (or wait for its next execution) and attempt, in the AA's `oscript`, to send this asset back out via a `payment` message with `asset` set to the private asset.
5. Observe that `sendUnit()` in `aa_composer.js` fails the message with `"sending private asset from AA"`, and even if attempted, `validateMessage()` in `validation.js` would reject `spend_proofs` in any AA-authored message with `"spend proofs in AA"`. The private asset value at the AA's address is now permanently unspendable.
