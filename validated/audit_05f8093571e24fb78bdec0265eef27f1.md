### Title
Cross-tenant status forgery via unscoped `Commit.where(sha:)` in `StatusHandler#process` enables unauthorized PR merge - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits purely by `sha` across the entire `commits` table, without checking that the SHA belongs to the repository named in the verified webhook payload. Because `Commit` SHAs are content-addressed and identical across repositories/forks, an attacker who owns any repository (or org) that Shipit is configured to receive webhooks from can emit a legitimately-signed `status` event for a SHA that also exists in a victim stack's pending merge request, causing `MergeRequest#all_status_checks_passed?` to return true and `ProcessMergeRequestsJob` to call `merge!`, merging the victim's PR using the victim org's `GITHUB_TOKEN`.

### Finding Description
The broken binding is: `payload.dig('repository', 'full_name')` (the repository whose signature was verified) **should equal** `commit.stack.repository.full_name` (the repository owning the `Commit` record being mutated), but `StatusHandler#process` never enforces this equality: [1](#0-0) 

Contrast this with the `Handler` base class, which provides a `stacks` helper explicitly scoped by `repository_name` for exactly this purpose [2](#0-1)  — `StatusHandler` simply does not use it, instead running `Commit.where(sha: params.sha)` unscoped by stack/repository.

`WebhooksController#verify_signature` only checks that the request is a validly-signed webhook for whatever organization the payload claims to be from — it uses `repository_owner` taken from the attacker-controlled payload to select which app/secret to verify against, then checks the signature against that org's own webhook secret [3](#0-2) . This correctly authenticates that "this event genuinely came from GitHub for repository R," but R is the attacker's own repository, not the victim's. Nothing downstream re-checks that the commit being updated actually belongs to R.

Exploit flow:
1. Attacker owns/administers a GitHub repository/org where the Shipit GitHub App/webhook is installed (their own tenant).
2. Attacker obtains (e.g., via fork) a commit object that is byte-identical, and therefore SHA-identical, to `merge_request.head.sha` of a victim's pending merge request in another stack.
3. Attacker uses their own repo's admin/CI access to `POST` a commit status (e.g. via GitHub API `statuses` endpoint on their own repo, for a SHA they control) with a passing state and the context name required by the victim stack's required statuses.
4. GitHub emits a `status` webhook, signed with the attacker's own repository/org's valid webhook signature, to Shipit's `/webhooks` endpoint.
5. `WebhooksController#verify_signature` succeeds (correctly signed for the attacker's own org).
6. `StatusHandler#process` runs `Commit.where(sha: params.sha)`, which matches the **victim's** `Commit` row (same SHA, different stack), and calls `commit.create_status_from_github!(params)`, writing the forged passing status into the victim commit's `statuses` [4](#0-3) .
7. `add_status` schedules merges for the victim's stack because the new status is `success?` [5](#0-4) , enqueuing `ProcessMergeRequestsJob` for the victim stack.
8. `ProcessMergeRequestsJob#perform` calls `merge_request.refresh!` then `merge_request.all_status_checks_passed?`, which now evaluates true because the forged status satisfies `StatusChecker` [6](#0-5) [7](#0-6) .
9. `merge_request.merge!` calls `stack.github_api.merge_pull_request` using the victim stack/org's own GitHub credentials [8](#0-7) , merging a PR the attacker does not own using credentials the attacker never had.

None of the existing guards prevent this: signature verification authenticates the *sender's own* repository, not the *target* of the mutation; `ExplicitParameters` only validates payload shape (`sha`, `state`, etc.), not tenant ownership; and `StatusHandler` never consults `Repository.from_github_repo_name(repository_name)` the way other handlers do.

### Impact Explanation
A single forged (but legitimately GitHub-signed, from the attacker's own tenant) `status` webhook can cause Shipit to execute an unauthorized merge of a pull request in a victim's repository, using the victim org's `GITHUB_TOKEN`/GitHub App installation credentials. This is a cross-tenant confused-deputy: a payload authenticated for repository A mutates and triggers a privileged action (`merge_pull_request`) on repository B's stack. This is repeatable against any stack with a pending merge-queue entry whose head SHA the attacker can reproduce, and the blast radius spans all tenants sharing the Shipit deployment. This matches the "Critical" category: "a payload for one repository mutating another's stack, commit, task or team, or an unauthorized... merge."

### Likelihood Explanation
Preconditions: (1) Shipit is deployed as multi-tenant (multiple orgs/repos configured), (2) the attacker controls at least one repository/org onboarded to the same Shipit instance (a realistic, low-privilege precondition for any public/multi-tenant Shipit deployment), (3) the attacker can reproduce or otherwise obtain a commit object with an identical SHA to the victim's `merge_request.head` (straightforward via forking a public victim repo and pushing/re-pointing that same commit into their own repository, since git SHAs are content-addressed), and (4) a victim stack has a `pending` merge request whose head currently lacks a passing required status. Attacker cost is low: no secrets, sessions, or GitHub App keys are needed — only ordinary GitHub API access to their own repository to set a status, which they legitimately have.

### Recommendation
In `Shipit::Webhooks::Handlers::StatusHandler#process`, scope the commit lookup to the repository asserted (and cryptographically bound) in the webhook payload, e.g. restrict to `stacks.flat_map(&:commits).where(sha: params.sha)` or equivalently join through `Commit.where(sha: params.sha, stack_id: stacks.select(:id))`, using the `stacks` helper already provided by `Shipit::Webhooks::Handlers::Handler` (`app/models/shipit/webhooks/handlers/handler.rb`), instead of the current unscoped `Commit.where(sha: params.sha)`.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb (conceptual)
test "status event for repo A does not update commits belonging to repo B's stack" do
  victim_stack = shipit_stacks(:shipit)  # repo B
  attacker_stack = create_stack_for_other_repo # repo A, attacker-owned

  shared_sha = "deadbeef" * 5
  victim_commit = victim_stack.commits.create!(sha: shared_sha, message: "shared content")
  merge_request = victim_stack.merge_requests.create!(number: 42, merge_status: "pending", head: victim_commit)

  payload = {
    'sha' => shared_sha,
    'state' => 'success',
    'context' => 'ci/required',
    'repository' => { 'full_name' => attacker_stack.repo_name, 'owner' => { 'login' => attacker_stack.repo_owner } }
  }

  Shipit::ProcessMergeRequestsJob.expects(:perform_later).with(victim_stack).never

  Shipit::Webhooks::Handlers::StatusHandler.call(payload)

  victim_commit.reload
  assert_not victim_commit.statuses.exists?(context: 'ci/required', state: 'success'),
             "forged status from attacker's repository must not be written onto victim commit"
  assert_not merge_request.reload.all_status_checks_passed?
end
```
Assert on both sides of the binding: `payload.dig('repository','full_name')` (attacker's repo) must not equal, and must not be able to mutate, `victim_commit.stack.repository.full_name`; the test demonstrates that today it does.
