### Title
Webhook signature is verified against the org derived from `repository.owner.login`, but the repository/stack that is written to is looked up from the independent, attacker-controlled `repository.full_name` field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
This is the same "interface/field mismatch" bug class as the report's `IYuzuILPV2`/`IPSM` findings — a value the code trusts (a parameter/field) diverges from the value actually used to act. In `shipit-engine`, `WebhooksController#verify_signature` selects the GitHub App / webhook secret to validate the HMAC using `repository_owner`, but `Shipit::Webhooks::Handlers::Handler#repository_name` (and every push/pull-request handler) resolves the repository/stack that gets mutated using the sibling `repository.full_name` field from the same JSON body. These two fields are never checked for consistency.

### Finding Description
`WebhooksController#verify_signature` computes the expected signing secret this way: [1](#0-0) [2](#0-1) 

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
  head(422) unless verified
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```
`Shipit.github(organization:)` looks up a per-organization `webhook_secret` from `secrets.github` (documented multi-org config in `docs/setup.md`), so in a multi-tenant Shipit install every onboarded GitHub organization has its own independent webhook secret. [3](#0-2) 

Once the signature check passes, the raw JSON body is dispatched to handlers, all of which resolve the repository to act on via `repository.full_name` — a completely different field of the same body: [4](#0-3) [5](#0-4) 

`Repository.from_github_repo_name` simply splits `"owner/name"` from that field and does a DB lookup, independent of `owner.login`: [6](#0-5) 

The binding that should hold is:
`organization used to select/verify the webhook secret == organization that owns the repository being written to (full_name's owner segment)`

Nothing enforces this equality. An attacker who legitimately controls (or has obtained) the webhook secret for **any one** organization onboarded to the shared Shipit instance (e.g., their own org, which they administer and for which they can freely view/rotate the webhook secret in GitHub App settings) can craft an arbitrary JSON body where:
- `repository.owner.login` = their own organization (so `Shipit.github(organization: repository_owner)` selects the secret they know, and they can compute a valid `X-Hub-Signature` for the whole raw body), while
- `repository.full_name` = `"<victim-org>/<victim-repo>"` (a repository belonging to a different onboarded organization on the same Shipit instance).

Because HMAC verification only proves "this body was signed by *some* known secret," and the secret is selected using a field from the same forgeable body, the check does not bind the signature to the specific repository being acted upon. The `push` handler will then call `stack.sync_github(expected_head_sha: params.after)` on stacks belonging to the victim organization's repository, and other PR-based handlers (`OpenedHandler`, `LabeledHandler`, `ClosedHandler`, etc.) will create/archive/unarchive `ReviewStack`s or manipulate `PullRequest` records tied to the victim's repository — all triggered by a payload the attacker fully controls and validly signed with their own org's secret.

### Impact Explanation
This crosses an authentication boundary this engine is supposed to enforce per-organization: the whole reason multi-org config exists (each org gets its own `webhook_secret`) is so that org A cannot forge events for org B's repositories. This mismatch defeats that isolation, letting an attacker with only their own onboarded organization's webhook secret trigger unauthorized deploy-adjacent actions (`sync_github`, review-stack creation/archival, pull-request label/close/reopen state changes, task provisioning) against another tenant's repository/stack. This matches the "cross-repository writes" / "unauthorized deploy" class of impact called out in scope.

### Likelihood Explanation
Exploitation only requires knowledge of one legitimate, already-provisioned organization's webhook secret in a multi-org Shipit deployment (a low bar for an org admin who is by definition "unprivileged" with respect to other tenants) and the ability to POST a forged JSON body with mismatched `owner.login` / `full_name` fields to the shared webhook endpoint — no GitHub App private key, session, or `ApiClient` token is needed.

### Recommendation
Bind the HMAC verification result to the exact repository being acted upon: after selecting the app/secret via `repository_owner`, re-validate that the resolved `GitHub App`'s organization matches the owner segment of `repository.full_name` (or, better, look the target `Repository`/its owning `Shipit.github` instance up first and verify the signature using that repository's own configured secret) before dispatching to any handler.

### Proof of Concept
1. Attacker administers `org-attacker`, onboarded to a shared Shipit instance, and knows `org-attacker`'s `webhook_secret` (visible/rotatable in their own GitHub App settings).
2. Attacker crafts a `push` payload:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "org-attacker" },
    "full_name": "org-victim/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<hmac(org-attacker secret, body)>` and POSTs to `/github/webhooks`.
4. `verify_signature` calls `Shipit.github(organization: "org-attacker")` and the HMAC check passes.
5. `PushHandler#process` calls `stacks` → `Handler#repository_name` → `payload.dig('repository','full_name')` = `"org-victim/victim-repo"`, and finds/mutates `org-victim`'s stacks via `stack.sync_github(...)`, even though the signature was never validated against anything owned by `org-victim`.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
