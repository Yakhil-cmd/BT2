### Title
CCMenu token issued without `stack_id`, granting cross-stack read access - ([File: app/controllers/shipit/ccmenu_url_controller.rb])

### Summary
`CCMenuUrlController#client` creates the "CCMenu Client" `ApiClient` via `find_or_create_by!(creator: current_user, name: 'CCMenu Client')` without ever assigning `stack_id`. Because `ApiClient#stack_id` is left `nil`, the token embedded in the returned `ccmenu_url` is not scoped to the stack it was requested for, and `Api::BaseController#stacks` treats a client with no `stack_id` as authorized for `Stack.all`.

### Finding Description
The claimed binding is `ApiClient#stack_id == stack.id` where `stack` is `Stack.from_param!(params[:stack_id])` [1](#0-0) . Tracing the code: `client` is built with `ApiClient.create_with(permissions: %w[read:stack]).find_or_create_by!(creator: current_user, name: 'CCMenu Client')` — no `stack:` attribute is passed, and `ApiClient` defines `belongs_to :stack, optional: true`, so `stack_id` defaults to `nil` [2](#0-1) . The generated token (`client.authentication_token`) is embedded in the URL returned to the browser for stack A.

That same token, when replayed against `Api::CCMenuController#show` (or any other `Api::BaseController` subclass endpoint), is authenticated via `ApiClient.authenticate(params[:token])` and then scoped via the `stacks` helper: `current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all` [3](#0-2) . Since `stack_id` is `nil`, `stack_id?` is `false`, so the scope resolves to `Stack.all` — i.e., the token is valid for **every** stack in the installation, not just the one whose CCMenu URL was requested. `Api::CCMenuController` only requires the generic `read:stack` permission and resolves `stack` via `Stack.from_param!(params[:stack_id])` directly (bypassing even the `stacks` scoping helper in this particular controller) [4](#0-3) , so no per-stack check narrows access at all.

Additionally, `find_or_create_by!` keys the lookup only on `creator` + `name = 'CCMenu Client'`, so a single client record is reused across every stack the same user later requests a CCMenu URL for — reinforcing that the token was never intended to be single-stack-scoped, and none of the existing guards (`require_permission!`, `stacks` scope, model validations) restrict it, because `require_permission!` only checks the `read:stack` permission string, not stack identity, and the `stacks` scope explicitly falls back to "all stacks" when `stack_id` is blank.

Attacker flow: a user who is a collaborator on stack A visits `/ccmenu/:owner/:repo/:env` (routed to `CCMenuUrlController#fetch`) and receives a `ccmenu_url` containing an `ApiClient` token. That token authenticates against `Api::CCMenuController#show` for any `stack_id` path parameter, including stacks the user has no access to, returning that stack's latest deploy XML (`stack.deploys_and_rollbacks.last`).

### Impact Explanation
The attacker obtains a persistent API token (reused per-user across requests, since `find_or_create_by!` returns the same row) that grants `read:stack` access to **every stack in the Shipit installation**, not just the one they legitimately have access to. This is an unauthorized cross-tenant read of stack/deploy state — matching the High-severity category "unauthenticated read of stack state, task streams or deploy output" (the attacker is not credentialed for the target stack, only for their own). The blast radius is every stack hosted by the Shipit instance, and the token remains valid indefinitely (tokens are HMAC-signed IDs with no expiry, `SimpleMessageVerifier`), so it is fully repeatable against arbitrary stacks by simply changing the `stack_id` route segment on `GET /api/stacks/*stack_id/ccmenu`.

### Likelihood Explanation
Preconditions are minimal: the attacker only needs enough access to view the settings/CCMenu page of one stack they legitimately collaborate on (a standard, unprivileged capability) to trigger creation of the token. No GitHub secrets, webhook signatures, or Shipit operator role are required. The attack is a single authenticated GET to obtain the token, followed by unauthenticated (token-only) GETs to `Api::CCMenuController#show` for arbitrary stack path segments. This is trivially reproducible and low-cost.

### Recommendation
Scope the CCMenu `ApiClient` to the requested stack, e.g. `ApiClient.create_with(permissions: %w[read:stack], stack:).find_or_create_by!(creator: current_user, name: "CCMenu Client (#{stack.to_param})")` (or otherwise include `stack_id` in both the `create_with` attributes and the `find_or_create_by!` lookup key so each stack gets its own token), ensuring `client.stack_id == stack.id` before the token is issued.

### Proof of Concept
```ruby
# test/controllers/ccmenu_url_controller_test.rb (conceptual addition)
test "ccmenu token is not scoped to the requested stack" do
  user = shipit_users(:walrus)
  stack_a = shipit_stacks(:shipit)
  stack_b = shipit_stacks(:cyclimse) # a different stack the user has no business accessing

  session[:user_id] = user.id
  get :fetch, params: { stack_id: stack_a.to_param }
  assert_response :ok

  client = ApiClient.find_by(creator: user, name: 'CCMenu Client')
  assert_nil client.stack_id # BROKEN BINDING: expected client.stack_id == stack_a.id

  token = client.authentication_token
  get :show, params: { stack_id: stack_b.to_param, token: }, controller: Api::CCMenuController
  assert_response :ok # token issued for stack_a grants read access to stack_b
end
```
This demonstrates the equality `client.stack_id == stack_a.id` fails (`nil != stack_a.id`), and the resulting token authorizes reads against an unrelated `stack_b`.
