### Title
Authorization bypass via unsigned webhook impersonation when a configured GitHub organization has no `webhook_secret` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks which GitHub App/organization config to use for HMAC verification from unauthenticated payload fields, then delegates the entire, unscoped payload to event handlers. `GitHubApp#verify_webhook_signature` treats a *missing* `webhook_secret` as an automatic pass. Because Shipit supports multiple configured organizations (see `secrets.development.shopify.yml`) and the `webhook_secret` key is documented as optional, an attacker who knows nothing about any real secret can select an organization with no secret configured to make signature verification trivially succeed, while still supplying arbitrary payload content (team id, member login, repository full name) that is processed against the full, cross-organization Shipit database. This breaks the intended binding "organization that authenticated" (the org whose secret gated the request) versus "the object that is written" (the team/repository/stack actually mutated), enabling escalation into `Shipit.github_teams` authorization.

### Finding Description
The webhook entry point performs verification like this: [1](#0-0) 

`repository_owner` is read straight out of the unverified JSON body: [2](#0-1) 

The organization thereby selected determines which `GitHubApp` instance verifies the signature: [3](#0-2) 

Notice `return true unless webhook_secret` — if the selected organization's config has no `webhook_secret` set (a documented, supported configuration, see below), *any* signature (or none) passes verification, regardless of the actual `X-Hub-Signature` header content.

Optional nature of `webhook_secret` is documented and even shown blank in the sample multi-org secrets file: [4](#0-3) [5](#0-4) 

Once `verify_signature` passes (trivially, due to the blank-secret organization), `create` dispatches the entire payload — including fields unrelated to `repository_owner` — to registered handlers without any re-validation that the payload's other identifying fields (e.g. `team.id`, `repository.full_name`) belong to the same organization used for verification: [6](#0-5) 

The `membership` handler is a concrete, high-impact sink: it creates/updates a `User` from the attacker-chosen `login` (via a live GitHub API lookup for that login, so it resolves to a real, potentially unrelated GitHub account) and adds that user to whatever `Team` the payload's `team.id` references — with no scoping to the verifying organization: [7](#0-6) [8](#0-7) 

Membership in a `Team` that matches `Shipit.github_teams` directly grants authorization inside Shipit, because authorization is a plain local-table membership check, not a live GitHub verification: [9](#0-8) 

`Shipit.github_teams` is derived from `oauth_teams`/`Team.find_or_create_by_handle`, and is used by `Authentication#force_github_authentication` to gate access to the entire application: [10](#0-9) 

**Binding broken:** organization authenticated (the org whose, possibly absent, `webhook_secret` gated the request) ≠ team/repository actually written (any team/repository referenced elsewhere in the same payload). Nothing ties the two together beyond the attacker-controlled `repository_owner`/`organization.login` value used purely to pick a verifier.

### Impact Explanation
This crosses the explicit High-severity bar: "escalation into `Shipit.github_teams` authorization." A completely unprivileged network attacker — with no Shipit session, no `ApiClient` token, no `webhook_secret`, and no GitHub App credentials — can add an arbitrary (real) GitHub login to any locally-tracked `Team` that gates access via `Shipit.github_teams`. If that GitHub login is one the attacker controls (or can create), the attacker subsequently authenticates through the normal OAuth flow and is granted `authorized?` status, gaining full access to Shipit's UI/API (viewing stack state, task streams/deploy output, and further actions), all stemming purely from data in an unsigned webhook.

### Likelihood Explanation
Exploitability hinges on a documented, legitimate configuration: `github.webhook_secret` is presented in the docs and example secrets file as optional/blank-able, and Shipit natively supports multiple concurrently configured organizations (`secrets.github` with per-org sub-keys). Any deployment that configures more than one organization and leaves the secret blank for even one of them (e.g., during initial setup, a low-traffic secondary org, or a dev/staging org config accidentally reused) exposes the flaw for all organizations' teams, not just the unsecured one — because the handler code performs no re-check of consistency between the verifying org and the payload's other identifiers. Likelihood is "medium" in the sense it requires this specific but realistic and doc-encouraged misconfiguration; it does not require compromising any secret, session, or credential.

### Recommendation
- In `GitHubApp#verify_webhook_signature`, do not treat a blank `webhook_secret` as automatic success; require a Signature/secret or explicitly and loudly opt out per-organization, and never let a blank-secret organization validate payloads referencing other organizations.
- In `WebhooksController`, after signature verification, enforce that all organization-identifying fields in the payload (e.g. `repository.owner.login`, `organization.login`, and any team/org fields consumed by handlers) match the organization whose secret verified the request.
- In `MembershipHandler` (and other handlers), verify that `params.organization.login` (or equivalent) matches the `Team#organization` being mutated before adding/removing membership.

### Proof of Concept
1. Configure Shipit with two organizations, e.g. `secure-org` (has `webhook_secret` set) and `open-org` (no `webhook_secret`, as shown in `config/secrets.development.shopify.yml`), both mapped via `Shipit.github_teams`/`Team` records that gate authorization.
2. Attacker (no session, no secret, no token) sends:
   ```
   POST /webhooks
   X-Github-Event: membership
   Content-Type: application/json

   {
     "action": "added",
     "organization": { "login": "open-org" },
     "team": { "id": <github_id of secure-org's authorized Team>, "name": "developers", "slug": "developers", "url": "https://api.github.com/..." },
     "member": { "login": "attacker-github-handle" }
   }
   ```
3. `verify_signature` resolves `repository_owner` → `"open-org"` (via `params.dig('organization','login')`), loads `open-org`'s `GitHubApp`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` unconditionally — no valid `X-Hub-Signature` is required.
4. `MembershipHandler#process` runs: `Team.find_or_create_by!(github_id: <secure-org's team id>)` matches the existing authorized team (from `secure-org`), `User.find_or_create_by_login!("attacker-github-handle")` fetches/creates that user via the live GitHub API, and `team.add_member(member)` adds them.
5. If "attacker-github-handle" is an account the attacker controls, they log in via Shipit's normal GitHub OAuth flow; `current_user.authorized?` now returns `true` because of the forged `Membership` row, granting full access gated by `Shipit.github_teams`.

Note: I could not fully verify from the index whether any additional per-route or Rack-level webhook secret enforcement exists outside the files reviewed (e.g., load balancer/App-level GitHub App signature enforcement configured by the host app), since such configuration would live outside this engine's own code; the analysis is based strictly on the in-scope `app/**`/`lib/shipit/**` code paths.

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e

        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
        def process
          team = find_or_create_team!
          member = User.find_or_create_by_login!(params.member.login)

          case params.action
          when 'added'
            team.add_member(member)
          when 'removed'

        end

          Team.find_or_create_by!(github_id: params.team.id) do |team|

          end
        end
```
