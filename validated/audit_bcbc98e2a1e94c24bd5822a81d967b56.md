### Title
Webhook signature is verified against the org derived from `repository.owner.login`, but the write path resolves the target Stack from the unrelated `repository.full_name` field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/webhook secret to check the HMAC signature against using one payload field (`repository.owner.login`, falling back to `organization.login`), while every event handler (`PushHandler`, `StatusHandler`, `CheckSuiteHandler`, etc.) resolves the `Stack`/`Repository` to act on from a *different*, unauthenticated payload field: `repository.full_name`. Nothing ties these two fields together, so the "organization whose secret authenticated the request" and "the repository that is actually written to" are never checked for equality.

### Finding Description
`verify_signature` computes the org used for signature verification purely from attacker-controlled JSON: [1](#0-0) [2](#0-1) 

```
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

`Shipit.github(organization: repository_owner)` picks the `GithubApp` config for that org (which, per the multi-org config format, carries its own independent `webhook_secret`, e.g. `test/dummy/config/secrets_double_github_app.yml`) and calls `verify_webhook_signature`: [3](#0-2) 

Crucially, `verify_webhook_signature` **always returns `true` when no `webhook_secret` is configured for that org** — a documented, supported, "optional" configuration (`docs/setup.md` line 30: "Webhook secret (optional)"; `config/secrets.development.example.yml` ships `webhook_secret: # nil`).

Once `verify_signature` passes (either because the secret truly matches, or — more importantly — because the org picked via `repository.owner.login`/`organization.login` simply has no secret configured), the request body is dispatched unchanged to the handlers: [4](#0-3) 

Every handler then resolves the target `Stack` using a completely different field of the same payload, `repository.full_name`, via the shared `Handler#stacks`/`#repository_name` helpers: [5](#0-4) 

For example `PushHandler` triggers a GitHub sync for any stack matching `repository.full_name` + branch: [6](#0-5) 

`StatusHandler` writes commit statuses for any commit matching `sha`, with no repository/org check at all beyond the SHA: [7](#0-6) 

`CheckSuiteHandler` schedules check-run refreshes for the matching stack/branch/sha, again derived from `repository.full_name` via `stacks`: [8](#0-7) 

**Break of the trust binding:** the equality that should hold is
`organization whose webhook_secret authenticated the request == organization that owns the repository/stack being mutated`.
Because `repository_owner` (used for signature selection) and `repository_name`/`sha` (used for the actual DB write) come from independent, attacker-controlled JSON fields in the *same* unauthenticated POST body, an attacker who can satisfy verification for **any** configured organization (trivially, one with no `webhook_secret` set, which the docs treat as a normal/optional configuration) can supply a `repository.full_name`/`sha` belonging to a completely unrelated, victim stack hosted on the same Shipit instance and have it processed as if it came from GitHub for that repository.

### Impact Explanation
This is an authentication-bypass class issue for cross-repository writes: an attacker with no GitHub credentials for the victim repository can, on any Shipit instance configured with multiple GitHub orgs (a supported and documented setup) where at least one configured org lacks a `webhook_secret`, forge:
- a `push` event that triggers `GithubSyncJob`/`sync_github` for an arbitrary victim stack,
- a `status` event that writes fabricated commit statuses onto arbitrary commits (by SHA guess/observation) across any stack,
- a `check_suite` event that forces check-run refreshes on a victim stack/branch.

Depending on the victim stack's continuous-delivery configuration, a forged `status` update (turning CI red/green) combined with a forged sync can influence whether commits become eligible for continuous deployment, i.e., can indirectly affect an unauthorized deploy decision. At minimum this is unauthenticated cross-repository state mutation on the deploy platform.

### Likelihood Explanation
Requires only an unauthenticated HTTP POST to `/webhooks` (`config/routes.rb` mounts `WebhooksController`), with the repository-owner field pointing at any org configured in `secrets.yml` without a `webhook_secret` (a state the project's own docs and example configs present as normal/optional), while the `repository.full_name`/`sha` fields target a different, victim stack registered on the same instance. No repository write access, API token, or session is needed — exactly the class of unprivileged-attacker analog in scope.

### Recommendation
- Require the resolved `Repository`/`Stack` for a webhook event (via `repository.full_name`) to belong to the same organization used for signature verification (`repository.owner.login`/`organization.login`), rejecting the event if they mismatch.
- Stop treating "no `webhook_secret` configured" as automatic pass-through; either require a secret for every configured org or scope such orgs' webhooks to no-op/read-only handlers.
- Consider deriving the org used to select stacks directly from the `Repository` record found (its stored owner) and cross-checking it against `repository_owner` before dispatching to handlers.

### Proof of Concept
1. Shipit instance is configured with two GitHub orgs, `OrgOne` (has a real `webhook_secret`) and `OrgNoSecret` (leaves `webhook_secret` empty), as shown supported by `test/dummy/config/secrets_double_github_app.yml`/`docs/setup.md`.
2. `OrgOne/victim-repo` is registered in Shipit as a `Stack` with an active continuous-delivery pipeline.
3. Attacker sends:
```
POST /webhooks
X-Github-Event: push
X-Hub-Signature: sha1=anything   # or omitted

{
  "repository": { "owner": { "login": "OrgNoSecret" }, "full_name": "OrgOne/victim-repo" },
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha already known to exist in victim-repo>"
}
```
4. `verify_signature` calls `Shipit.github(organization: "OrgNoSecret")`; because that org has no `webhook_secret`, `verify_webhook_signature` returns `true` regardless of the (bogus) signature header (`lib/shipit/github_app.rb:76-83`).
5. `PushHandler#process` resolves `stacks` from `repository.full_name` = `"OrgOne/victim-repo"` (`app/models/shipit/webhooks/handlers/handler.rb:32-38`) and calls `stack.sync_github(expected_head_sha: ...)` on the real victim stack, even though the request was never authenticated by `OrgOne`'s secret.

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e

        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
