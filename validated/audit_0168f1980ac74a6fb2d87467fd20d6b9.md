### Title
Unauthenticated user-impersonation via `X-Shipit-User` header breaks the API-token-vs-acting-user binding - (File: app/controllers/shipit/api/base_controller.rb)

### Summary
The Shipit API authenticates the *caller* by validating an `ApiClient` token (HTTP Basic auth), but it separately derives the *acting user* attributed to every privileged action (deploy author, rollback/task "aborted_by", lock owner, git committer identity, etc.) from a plain, unauthenticated request header, `X-Shipit-User`. Any request that is capable of presenting a valid `ApiClient` token can set this header to the login of any existing `Shipit::User` and have all resulting actions recorded and executed as that user, with no verification that the request actually originates from that user's GitHub identity or browser session.

### Finding Description
`Shipit::Api::BaseController#current_user` resolves the acting user purely from the `X-Shipit-User` header: [1](#0-0) 

```ruby
def current_user
  @current_user ||= identify_user || AnonymousUser.new
end

def identify_user
  user_login = request.headers['X-Shipit-User'].presence
  User.where('lower(login) = ?', user_login.downcase).first if user_login
end
```

Authentication of the *request* itself is handled separately and independently by `authenticate_api_client`, which only validates the `ApiClient` bearer/basic-auth token: [2](#0-1) 

There is no cryptographic or session-based binding tying the `ApiClient` token to the `X-Shipit-User` value — the header is attacker-controlled free text checked only against `User.login`, with no possession-of-identity check (no GitHub token check, no session cookie, no per-user secret). This is exactly the deployment-trust binding break described in the rules: "a GitHub identity versus the `User` bound to the session" — here, the acting `User` is bound to an arbitrary header value instead of any verified identity, while the API-level authorization (`ApiClient` permissions) covers only the *stack-scope* operation, never the *identity* claimed for accountability and git-authorship purposes.

`current_user` returned by this method is then used, unauthenticated, as the acting principal for consequential actions:
- Triggering a deploy: [3](#0-2) 
- Triggering/aborting a task: [4](#0-3) 
- Triggering a rollback or aborting an active task: [5](#0-4) 
- Locking a stack: [6](#0-5) 

The impersonated user is subsequently baked into deploy provenance data used for git authorship and audit trails (`GIT_COMMITTER_NAME`, `GIT_COMMITTER_EMAIL`, `SHIPIT_USER`, task `author`, lock `author`) via `TaskCommands#env`: [7](#0-6) 

Existing tests confirm this is treated purely as a claim, not a verified identity: [8](#0-7) 

```ruby
test "#create use the claimed user as author" do
  request.headers['X-Shipit-User'] = @user.login
  post :create, params: { stack_id: @stack.to_param, sha: @commit.sha }
  deploy = Deploy.last
  assert_equal @user, deploy.user
end
```
The test name itself ("the claimed user") acknowledges the value is unverified.

### Impact Explanation
Any party in possession of a valid `ApiClient` token scoped to `deploy:stack`/`lock:stack` permissions for a given stack can, without any credential belonging to a specific human user, attribute deploys, rollbacks, task aborts, and stack locks to any other `Shipit::User` in the system (e.g., an admin, a team lead, or a user whose approval carries special weight in downstream tooling that inspects `deploy.user`/git committer). This corresponds to the "unauthorized deploy, rollback" Critical-impact category and the "escalation ... authorization" High-impact category defined in scope, because the accountability/authorization model that assumes deploy actions map 1:1 to a specific verified human is bypassed — the `User` object bound to the action is decoupled from any GitHub-identity or session verification, unlike the browser-based flow in `Shipit::Authentication` which does bind `current_user` to `session[:user_id]` set only via the OAuth callback (`GithubAuthenticationController#sign_in_github`).

### Likelihood Explanation
Exploitation requires only a valid `ApiClient` token with the relevant stack permission (`deploy:stack`, `lock:stack`, etc.) — no possession of any specific user's session, GitHub OAuth token, or private key is needed to impersonate that user for accountability purposes. Any integration, CI system, or teammate holding an `ApiClient` token intended for automation can trivially set the header to impersonate a human user. This is a straightforward, low-complexity misuse of a documented but unauthenticated header (`X-Shipit-User` is described in `README.md`/API docs as identifying the acting user), making likelihood high wherever `ApiClient` tokens are shared beyond the specific individual they are meant to represent.

### Recommendation
Do not derive the acting/accountable `User` from a bare, unauthenticated header. Options:
- Bind `X-Shipit-User` enforcement to the `ApiClient` itself (e.g., require the `ApiClient#creator` to match, or restrict which logins a given client is allowed to claim, configured at token-issuance time).
- Require a separately signed/verified assertion of user identity (e.g., a per-user API token or session-bound value) rather than a free-text header compared against `User.login`.
- At minimum, gate use of `X-Shipit-User` behind an additional permission scope so that only trusted, narrowly-issued `ApiClient`s can act on behalf of arbitrary users, and audit/log every such impersonation distinctly from self-attributed actions.

### Proof of Concept
1. Obtain (or be issued) any `ApiClient` token with `deploy:stack` permission on a target stack (e.g., a low-trust CI integration token).
2. Send a deploy request with an arbitrary victim's login in the header:
```
POST /api/stacks/org/repo/production/deploys
Authorization: Basic <base64(api_client_token)>
X-Shipit-User: victim-admin-login
Content-Type: application/json

{"sha": "<commit_sha>"}
```
3. `Shipit::Api::BaseController#identify_user` resolves `current_user` to the `User` record for `victim-admin-login` purely from the header value.
4. `Api::DeploysController#create` calls `stack.trigger_deploy(commit, current_user, ...)`, creating a `Deploy` whose `user` is the victim, and whose resulting git commits/env (`GIT_COMMITTER_NAME`, `GIT_COMMITTER_EMAIL`, `SHIPIT_USER`) are attributed to the victim — confirmed by the existing test `test/controllers/api/deploys_controller_test.rb:49-61`, which demonstrates this exact behavior is currently by design and unauthenticated.

      def create
        commit = stack.commits.by_sha(params.sha) || param_error!(:sha, 'Unknown revision')
        param_error!(:force, "Can't rollback a locked stack") if !params.force && stack.locked?
        deploy = stack.deploys.find_by(until_commit: commit) || param_error!(:sha, 'Cant find associated deploy')
        rollback_env = stack.filter_rollback_envs(params.env)

        response = nil
        if !params.force && stack.active_task?
          param_error!(:force, "Can't rollback, deploy in progress")
        elsif stack.active_task?
          active_task = stack.active_task
          active_task.abort!(aborted_by: current_user, rollback_once_aborted_to: deploy, rollback_once_aborted: true)
          response = active_task
        else
          response = deploy.trigger_rollback(current_user, env: rollback_env, force: params.force, lock: params.lock)
        end

        render_resource(response, status: :accepted)
      end
