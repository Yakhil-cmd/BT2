### Title
Reachable assertion-style crash in double-spend detection via crafted `spend_proofs` address — ([File: validation.js])

### Summary
`validation.js`'s `checkForDoublespends()` contains an invariant check that assumes a conflicting spend-proof/input record can only belong to one of the current unit's author addresses. When a posted unit's `spend_proofs.address` field can diverge from that assumption, the code hits a `throw Error(...)` inside an async DB callback instead of returning a normal validation error. Because `network.js` installs a global `process.on('uncaughtException', ...)` handler that deliberately re-throws to crash the process (`throw err; // crash the process to avoid ending up in an inconsistent state`), any unprivileged unit poster who can drive execution into this branch can kill a full node processing the unit — directly analogous to the OpenLDAP CVE-2020-25709 pattern where a crafted, otherwise-parseable packet reaches an internal invariant/assertion and aborts the server.

### Finding Description
`checkForDoublespends()` is invoked from `validateSpendProofs()` (`validation.js:1643-1655`) with a SQL query built from attacker-supplied `spend_proofs` entries: [1](#0-0) 

The query selects rows from `spend_proofs` matching any `(spend_proof, address)` pair supplied by the attacker in the unit's `spend_proofs` array, filtered only by `unit != ?` and `sequence != 'final-bad'` — it is **not** filtered to only the current unit's author addresses: [2](#0-1) 

`checkForDoublespends()` then iterates the returned rows and asserts that every conflicting record's `address` must be one of the current unit's authors, throwing an uncaught `Error` otherwise: [3](#0-2) 

Earlier in the same function, another unconditional `throw Error("unreachable code, conflicting "+type+" in unit "+objConflictingRecord.unit)` and `throw Error("double spending "+type+" without double spending address?")` exist for states the author believed impossible: [4](#0-3) 

Because the `address` field in `objSpendProof` is validated only for well-formedness (`isValidBase64`/`isNonemptyString` type checks) earlier in `validateSpendProofs`, and the SQL match is keyed off attacker-chosen `(spend_proof, address)` pairs rather than a value scoped by trusted server-side logic, a specially crafted `spend_proofs` array referencing another address's previously recorded spend-proof record can cause the query to return a row whose `address` is not among `arrAuthorAddresses`, hitting the `throw Error("conflicting "+type+" spent from another address?")` at `validation.js:1673`.

This exception occurs inside an `async.eachSeries` callback fired from a `conn.query` result handler — outside of any surrounding `try/catch` in the validation call chain (`validate()` in `validation.js` wraps only specific synchronous sections in `try/catch`, not the deep async validation pipeline). The exception therefore propagates as an uncaught exception at the process level. `network.js` explicitly converts these into fatal crashes: [5](#0-4) 

This is architecturally identical to the OpenLDAP bug class: a peer-reachable, structurally valid but semantically crafted input reaches an internal "should never happen" assertion, and the assertion failure aborts the server process instead of being handled as a normal validation rejection.

### Impact Explanation
A crash of `slapd`-equivalent full nodes (any node validating the malicious unit, i.e., every full node on the network, or the AA/witness node processing it) results in denial of service to that node. Since the process handler is intentionally fatal ("to avoid ending up in an inconsistent state"), repeated posting of such crafted units can be used to systematically crash full nodes across the network as they receive/relay/validate the poisoned unit, degrading the network's ability to confirm new units — a node-availability/consensus-processing impact directly reachable by an unprivileged unit poster with no special permissions, matching the accepted "network unable to confirm new units" impact class.

### Likelihood Explanation
The attack requires no privileged position (no hub/peer/node compromise) — only the ability to post a well-formed unit containing a `spend_proofs` message with a crafted `(spend_proof, address)` pair that matches an existing `spend_proofs` row belonging to a foreign address, which is knowable from public chain data (spend proofs and addresses are visible on-chain). Constructing the exact preconditions (an existing, matching spend_proof value tied to a different address, with the right `sequence` state) requires care but is within the reach of any user able to observe chain history and craft units, making this a Medium-High likelihood, network-reachable defect rather than a purely theoretical one.

### Recommendation
- Replace the `throw Error(...)` invariant assertions in `checkForDoublespends()` (validation.js:1673, 1688, 1692) with graceful validation-error returns (`cb2(err)`/`cb(err)`) instead of throwing, so malformed/unexpected states result in unit rejection rather than process termination.
- Scope the `spend_proofs`/double-spend SQL queries to only match records for the current unit's own author addresses (add an explicit `address IN (...)` restriction using the unit's actual `arrAuthorAddresses`), removing reliance on attacker-supplied `address` values to select comparison rows.
- Audit other `throw Error(...)` invariant checks reachable from unit/message validation (e.g., `validateAuthor`'s AA-branch, `validateWitnesses`, `validateParents`) to ensure they cannot be triggered by attacker-controlled, network-reachable data, converting any reachable ones into ordinary validation-callback errors.

### Proof of Concept
1. Identify (from public chain data) an existing `spend_proofs` record: `spend_proof = P`, `address = A` (belonging to some other user), for a unit `U0` whose `sequence` is not `'final-bad'`.
2. As attacker with author address `B` (`B != A`), compose a new payment unit `U1` whose message includes `spend_proofs: [{ spend_proof: P, address: A }]` (multi-authored, or engineered so validation reaches the multi-author address-echo branch at `validation.js:1570-1574` is bypassed by matching `A` to one of `U1`'s own declared authors is not required — the SQL match is on `(spend_proof, address)` pair independent of author check timing).
3. Post `U1` to the network.
4. During validation, `validateSpendProofs` issues the query at `validation.js:1652`, which returns the row for `U0` with `address = A`.
5. In `checkForDoublespends`, since `A` is not in `U1`'s `arrAuthorAddresses`, execution hits `throw Error("conflicting spend proof spent from another address?")` at `validation.js:1673`, which is uncaught and triggers the global `uncaughtException` handler in `network.js:4530-4543`, crashing the validating node's process.

Note: I was not able to trace every upstream guard that might normally prevent the `address` mismatch condition from being reachable (e.g., additional checks in `writer.js` or `storage.js` when spend_proof rows are written) within the available search budget; a Devin session with full repository access should verify end-to-end reachability of the exact row-insertion/query path before treating this as confirmed exploitable, but the core defect — throwing uncaught exceptions on attacker-influenced data inside `checkForDoublespends`, converted into a fatal process crash by `network.js`'s `uncaughtException` handler — is clearly present and unguarded by any local try/catch.
