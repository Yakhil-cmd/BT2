### Title
Webhook organization-to-repository binding is not signature-enforced, allowing forged CI/push events for arbitrary tracked repositories - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects *which* GitHub App secret to check against by reading `repository.owner.login` (or `organization.login`) straight out of the untrusted, unauthenticated JSON body, and `GithubApp#verify_webhook_signature` fails open (`return true unless webhook_secret`) whenever that resolved app config has no `webhook_secret` set — a state that ships as the default in every example config in this repo. The field used to pick the "authorizing organization" is never cryptographically bound to the field(s) the rest of the pipeline actually writes against (e.g. `repository.full_name`, `sha`, `state`), so an attacker can pick an org with no configured secret to short-circuit verification while asserting webhook data for a completely different, tracked repository.

### Finding Description
`verify_signature` derives the org used to select a signing secret from the body itself: [1](#0-0) [2](#0-1) 

The actual check is delegated to `GithubApp#verify_webhook_signature`, which explicitly no-ops when the resolved app config has no secret configured: [3](#0-2) 

Every shipped example configuration — single-org and multi-org — ships `webhook_secret` unset by default, which is documented as optional ("If you've set a webhook secret during the App creation, you should copy it here"): [4](#0-3) [5](#0-4) 

Once `verify_signature` passes (which requires nothing more than naming an org that has no secret configured), the controller hands the entire unverified JSON body to the event handlers, keyed only by the `X-Github-Event` header: [6](#0-5) 

Nothing re-derives or re-checks that the `repository.owner.login`/`organization.login` used to pick the (unset) secret matches the `repository.full_name`, `sha`, or other fields the downstream handlers act on — these are independent JSON keys with no cross-field validation, unlike a real GitHub-issued payload where they are naturally consistent. Test fixtures confirm handlers act on `sha`, `state`, `branches`, and merged `repository_params` fields taken directly from the body to create `Status` records and enqueue jobs such as `GithubSyncJob`/`RefreshCheckRunsJob` against whatever stack/repository those fields name: [7](#0-6) [8](#0-7) 

This breaks the intended equality: **organization whose secret authenticated the request == organization/repository the handler actually writes state for**. Because the "authenticating organization" field is attacker-chosen and can trivially be a no-secret org while the "acted-upon repository" field names an unrelated, tracked repository, the signature check provides no real authorization boundary in the (documented, default) no-secret configuration.

### Impact Explanation
An unprivileged attacker with no GitHub credentials, no `ApiClient` token, and no knowledge of any `webhook_secret` can POST forged `status`, `check_suite`, or `push` events for any repository Shipit tracks, as long as the deployment (or any one org in a multi-org deployment) has no `webhook_secret` configured — the documented default. Forged `status`/`check_suite` events fabricate green CI state for a commit; combined with Shipit's continuous-deployment feature (`resource :continuous_delivery_schedule` and stacks' `continuous_deployment` flag), this can trigger an unauthorized deploy of a commit that never actually passed CI. This lands in the "High/Critical" bucket defined by the rules: unauthorized deploy via falsified check/status state.

### Likelihood Explanation
High for any deployment that has not explicitly set a `webhook_secret` — which is the state shipped by every example config in this repository and explicitly called out in the docs as optional. No credentials, tokens, or privileged access are required; only network access to the public `/webhooks` endpoint documented by the engine.

### Recommendation
- Require `webhook_secret` to be present for any configured GitHub organization; refuse to boot (or reject all webhooks) instead of silently returning `true` in `GithubApp#verify_webhook_signature` when it's blank.
- Cross-validate that `repository.full_name`'s owner segment matches the `repository.owner.login`/`organization.login` used to select the verifying secret before dispatching to handlers.
- After signature verification, re-derive the target `Repository`/`Stack` strictly from the same organization identity that was cryptographically verified, not from an independently-controlled field in the body.

### Proof of Concept
1. Deploy Shipit with the default/example secrets config (`webhook_secret` unset for the org named in the payload), as shipped in `config/secrets.development.example.yml`.
2. POST to `/webhooks` with header `X-Github-Event: status`, and body:
```json
{
  "repository": { "owner": { "login": "no-secret-org" }, "full_name": "victim-org/victim-repo" },
  "sha": "<victim commit sha>",
  "state": "success",
  "branches": [{ "name": "main" }]
}
```
3. `verify_signature` resolves `Shipit.github(organization: "no-secret-org")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` unconditionally regardless of the (missing/invalid) `X-Hub-Signature` header.
4. The `status` handler processes the payload and records a fabricated "success" `Status` against `victim-org/victim-repo`'s commit, as shown by the equivalent code path exercised in `test/controllers/webhooks_controller_test.rb:42-59`, potentially enabling an unauthorized continuous deployment for a stack that never actually passed CI.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
