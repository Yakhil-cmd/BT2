Confirmed: the `deposit` function has no `ERR-OUTPUT-ZERO` guard on `inkind` (share amount), unlike `redeem` which explicitly asserts `(> inkind u0)`. This asymmetry is the root cause enabling the analog below.

### Title
Deposit into a vault with zeroed `total-assets` after bad-debt socialization mints zero shares, donating the depositor's underlying to existing shareholders - ([File: mainnet/contracts/vault/v0-vault-usdc.clar])

### Summary
Any Zest lending vault (`v0-vault-usdc.clar`, `v0-vault-usdh.clar`, `v0-vault-stx.clar`, `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`) can reach a state where `total-assets` is driven to `u0` by `socialize-debt` while `zft` `total-supply` remains non-zero — exactly the precondition described in the external M-8 report (`totalSTokenUnderlying == 0`, `totalSupply != 0`). Unlike the referenced Carapace bug, the Zest vaults' `convert-to-shares-preview` does not divide-by-zero/revert in this state; instead it silently returns `u0` shares for any deposit amount. Because `deposit` lacks a zero-shares guard, a victim who deposits while the vault is in this state pays real underlying tokens into the pool, receives zero `zft` shares, yet the underlying they deposited increases `var-get assets`, i.e. it inflates the exchange rate for every pre-existing shareholder. This is a direct, unrecoverable transfer of the depositor's principal to other unprivileged shareholders.

### Finding Description
`socialize-debt` in each vault clamps `assets` to zero when bad debt exceeds current assets, without burning any outstanding `zft` shares: [1](#0-0) 

This can leave `total-assets-preview` (`ta`) at `u0` while `total-supply-preview` (`ts`) is non-zero — the same "zero assets, non-zero supply" state as the referenced report. The vault's conversion helper explicitly handles this state without reverting: [2](#0-1) 
When `ts != 0` and `ta == 0`, `convert-to-shares-preview` returns `u0` for any positive deposit `amount`.

`deposit` then proceeds without any check that `inkind` (shares to mint) is greater than zero: [3](#0-2) 
The only zero-check is on `amount` (`ERR-AMOUNT-ZERO`) and the slippage check `(>= inkind min-out)`, which trivially passes for a default `min-out` of `u0`. The underlying is received and `assets` is increased by the full deposited `amount`, but `ft-mint?` mints `u0` shares to the depositor. Contrast this with `redeem`, which explicitly guards against a zero output: [4](#0-3) 

The shared state is `var-get assets` and `zft` `total-supply` — the exchange-rate numerator/denominator used by every shareholder. The victim (the depositor) unknowingly donates their principal, which then benefits all pre-existing `zft` holders (including any attacker who front-runs or holds shares before triggering/observing the zero-asset state), since their fixed share count now maps to a strictly larger `assets` value.

### Impact Explanation
This is a direct theft of user funds at rest: a victim depositing into the affected vault while it is in the zero-`total-assets`/non-zero-`total-supply` state loses their entire deposited principal to other shareholders, with no recourse (shares minted = 0, no revert, no error). This falls under the Critical impact class ("direct theft of user funds at rest ... other than unclaimed yield").

### Likelihood Explanation
The precondition (`socialize-debt` reducing `assets` to zero while shares remain outstanding) requires bad debt from a liquidation that consumes all seized collateral value and is socialized across the shareholder pool — a state the protocol's own `bad-debt-socialized` logic in `v0-4-market.clar` is designed to produce and print as an event, making it publicly observable. Since `zft` transfers/liquidity make partial repayment unlikely to fully restore `assets` to a healthy positive-per-share ratio instantly, and no invariant check prevents deposits during this window, any user (or an attacker deliberately front-running/monitoring emitted `bad-debt-socialized`/`socialize-debt` events and then either being an existing shareholder or inducing a victim to deposit) can realize this loss transfer. Likelihood is Medium: it requires an actual bad-debt event (not attacker-triggerable at will without incurring their own losses as borrower) but is fully mechanical once that state occurs and is silent (no revert) so a victim depositor would not be warned.

### Recommendation
Add an explicit zero-output guard in `deposit`, mirroring `redeem`'s `ERR-OUTPUT-ZERO` check, e.g. `(asserts! (> inkind u0) ERR-OUTPUT-ZERO)`. Additionally, seed and permanently lock a minimum non-zero `assets` balance (as already done via `MINIMUM-LIQUIDITY` sent to `NULL-ADDRESS` at `initialize`) that `socialize-debt` must never be able to fully deplete, e.g. by capping `principal-reduction` such that `assets` cannot fall below the `MINIMUM-LIQUIDITY` floor, preserving a non-zero exchange-rate denominator at all times.

### Proof of Concept
1. Vault `v0-vault-usdc` has shareholders A, B holding `zft` totaling `total-supply = 1_000_000` (any positive value), with `assets = 1_000_000`.
2. A large borrower's position becomes massively underwater and is liquidated via `liquidate` in `v0-4-market.clar`; all collateral is seized and insufficient to cover debt, triggering `bad-debt-socialized` and a call into the vault's `socialize-debt`. [1](#0-0) 
3. `socialize-debt` reduces `assets` all the way to `u0` (clamped by `(if (> current-assets principal-reduction) (- current-assets principal-reduction) u0)`), while `zft` `total-supply` remains `1_000_000` (no shares burned).
4. Victim `V` calls `deposit(amount: 500_000, min-out: 0, recipient: V)`.
   - `convert-to-shares-preview(500_000)`: `ts = 1_000_000 != u0`, `ta = 0`, so returns `u0`.
5. Deposit proceeds: `(asserts! (>= inkind min-out) ERR-SLIPPAGE)` → `(>= 0 0)` passes; `receive-underlying` pulls `500_000` USDC from `V`; `ft-mint? zft 0 V` mints zero shares to `V`; `assets` is set to `500_000`. [3](#0-2) 
6. Result: `V` has paid `500_000` USDC and received `0` `zft` shares. `total-assets` is now `500_000` while `V` owns none of it; shareholders `A` and `B` (whose combined `zft` still totals `1_000_000`) can now redeem for a share of the recovered `500_000` `assets`, i.e. `V`'s deposit was fully transferred to `A` and `B`.

(define-public (socialize-debt (scaled-amount uint))
  (let ((scaled-principal (var-get principal-scaled))
        (borrowed (var-get total-borrowed))
        (idx (var-get index))
        (current-assets (var-get assets))
        (current-lindex (var-get lindex))
        (old-total-assets (total-assets))
        (debt-reduction (mul-div-down scaled-amount idx INDEX-PRECISION))
        (principal-reduction (if (> scaled-principal u0)
                                (mul-div-down scaled-amount borrowed scaled-principal)
                                u0))
        ;; Write down lindex proportionally to loss in total-assets
        (new-lindex (if (and (> old-total-assets u0) (> old-total-assets debt-reduction))
                       (mul-div-down current-lindex (- old-total-assets debt-reduction) old-total-assets)
                       u0)))

    (try! (check-caller-auth))
    (asserts! (> scaled-amount u0) ERR-AMOUNT-ZERO)

    (var-set lindex new-lindex)
    (var-set principal-scaled (if (> scaled-principal scaled-amount) (- scaled-principal scaled-amount) u0))
    (var-set total-borrowed (if (> borrowed principal-reduction) (- borrowed principal-reduction) u0))
    (var-set assets (if (> current-assets principal-reduction) (- current-assets principal-reduction) u0))

  (asserts! (> inkind u0) ERR-OUTPUT-ZERO)
