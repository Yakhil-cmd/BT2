### Title
Whale-scale market at sustained high utilization permanently freezes a hub/spoke book — accrual value overflow panics before the borrow-index cap engages - ([File: contracts/pool/src/interest.rs])

### Summary
CVE-2024-20977 is a low-privileged, repeatable-crash DoS class. Its analog in XOXNO Lending is a permanent panic in pool accrual: debt value (`borrowed_shares * borrow_index` in RAY) can overflow `i128`/the RAY domain **before** the borrow index reaches `MAX_BORROW_INDEX_RAY` (10^36). Because `global_sync` accrues first inside every mutating pool verb, once the overflow threshold is crossed the market is unrecoverable: `supply`, `withdraw`, `borrow`, `repay`, `liquidate`, `clean_bad_debt`, `claim_revenue`, and `recapitalize` all revert with `MATH_OVERFLOW` — forever, since no path exists to shrink `borrowed` or roll back the index without first accruing.

### Finding Description
`contracts/pool/src/interest.rs` `global_sync` runs `accrue_chunk` on every state-changing call via `cache.needs_accrual()` (`contracts/pool/src/interest.rs:20-33`). Each chunk calls `accrue_step`, which internally computes `scaled_to_original(borrowed, borrow_index)` — a RAY multiply that panics with `GenericError` math overflow when `borrowed_shares * index` exceeds `i128::MAX`. `update_borrow_index` caps the *index* at 10^36 (`common/src/rates/index.rs:13-19`), but the *value* `borrowed * index` hits the i128 ceiling well before the index cap does on a large book.

The protocol's own documentation acknowledges the cliff: `docs/reference/formulas.md` lines 432-437 state "Value overflow can occur before the index ceiling and block repayment/withdrawal because those operations accrue first," and that "No dedicated ceiling alarm is emitted." The harness test `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` (`tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:320-361`) demonstrates it end-to-end: after the accrual panic, `try_withdraw_raw` and `try_repay` both revert with `MATH_OVERFLOW`, and `last.borrow_index < MAX_BORROW_INDEX_RAY` proves the cap never engaged.

Reachability is fully unprivileged: the admitted cap maximum is `i128::MAX / 10^(27-d)` (~170 billion whole tokens, `docs/reference/formulas.md:429`), and cap→scaled conversion saturates rather than traps, so any governance-set cap near that bound (or an effectively unenforced saturated cap per line 411-413) lets a single whale `supply`/`borrow` a book large enough that accrual eventually overflows.

### Impact Explanation
Permanent freezing of all funds in the affected (hub, token) book: suppliers cannot withdraw, borrowers cannot repay, liquidators cannot liquidate, and `recapitalize`/`clean_bad_debt` cannot run because every path accrues first. The pool's physical token balance is stranded. This is "permanent freezing of funds," an accepted impact class, and unlike the MySQL crash there is no restart — the state is unrecoverable.

### Likelihood Explanation
Medium. It requires no privileged role, no oracle manipulation, and no leaked key — only capital at whale scale and sustained high utilization so the borrow index compounds. The fuzz and harness fixtures show it takes years of accrual at ~98% utilization on a steep rate curve, so it is a slow-burn rather than instant attack; however, once crossed it is irreversible and there is no monitoring or alarm (explicitly documented), so nothing intervenes before the cliff.

### Recommendation
- Clamp or skip accrual when `scaled_to_original(borrowed, borrow_index)` would overflow: e.g., in `accrue_step`, stop growing the index once the debt value is at the RAY-domain ceiling (accrual produces no new interest anyway past that point), instead of panicking.
- Alternatively, make `global_sync` trap only the *accrual* for the affected market while still allowing `repay`/`liquidate`/`clean_bad_debt` to operate on the frozen index, so debt can be unwound.
- Enforce caps strictly (fail closed instead of `calculate_scaled_cap` saturating to `i128::MAX`) so governance cannot silently admit books whose future accrual does not fit the RAY domain.

### Proof of Concept
See `tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:320-361`: supply `10^9 * 10^18` units of an 18-decimal asset, borrow ~98% of it against large collateral, advance time in yearly steps until `update_indexes` returns `MATH_OVERFLOW`; then `withdraw(1)` and `repay` both fail with the same error while `borrow_index < MAX_BORROW_INDEX_RAY`. Reproduction path for a single unprivileged address:

```text
controller.supply(attacker, BIG18_hub_asset, ~cap, position)
controller.supply(attacker, COL_hub_asset, collateral, position)
controller.borrow(attacker, BIG18_hub_asset, ~98% of book, position)
... wait / repeat controller.update_indexes(caller, [BIG18]) ...
// once scaled_to_original overflows:
controller.update_indexes(...) -> panic MATH_OVERFLOW
controller.repay / withdraw / liquidate / recapitalize -> all panic MATH_OVERFLOW
```
