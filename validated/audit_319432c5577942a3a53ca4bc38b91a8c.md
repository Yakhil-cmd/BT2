### Title
`OpenedHandler#provision?` operator-precedence bug bypasses `review_stacks_enabled` for `allow_with_label`/`prevent_with_label` behaviors - ([File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb])

### Summary
`OpenedHandler#provision?` is written as `repository.review_stacks_enabled && repository.provisioning_behavior_allow_all? || (allow_with_label? && has_label) || (prevent_with_label? && !has_label)`. Because Ruby's `&&` binds tighter than `||`, `review_stacks_enabled` only gates the `allow_all` clause, not the `allow_with_label` or `prevent_with_label` clauses, so a repository with `review_stacks_enabled: false` and `provisioning_behavior: 'prevent_with_label'` (or `allow_with_label`) still provisions a `ReviewStack` on an unlabeled (or labeled) opened pull request.

### Finding Description
The claimed broken binding is: `repository.review_stacks_enabled (false) == the gating condition actually enforced by #provision? for the prevent_with_label/allow_with_label branches`. Tracing the code: [1](#0-0) 

`respond_to_pull_request_opened?` calls `provision?`, which is:
```
repository.review_stacks_enabled &&
  repository.provisioning_behavior_allow_all? ||
  (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
  (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
```
Due to Ruby operator precedence, this parses as:
`(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label) || (prevent_with_label? && !has_label)`

For a repository with `review_stacks_enabled: false` and `provisioning_behavior: 'prevent_with_label'`, and a PR with no matching label, the third disjunct `(prevent_with_label? && !has_label)` evaluates to `true` — independent of `review_stacks_enabled`. The same applies to `allow_with_label?` when the PR carries the label. `process` then unconditionally calls `ReviewStackAdapter#find_or_create!`, which calls `create!`, creating a `Shipit::ReviewStack` row, a `PullRequest` association, and enqueuing the stack via `Shipit::ReviewStackProvisioningQueue.add(stack)`. [2](#0-1) [3](#0-2) 

No other guard in the request path (`ExplicitParameters` schema, `verify_signature`, `drop_unhandled_event`) checks `review_stacks_enabled` — that flag is only consulted inside `provision?`, and the operator-precedence bug neutralizes it for two of the three provisioning-behavior branches. The existing test suite's `prevent_with_label` coverage (`test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb`, lines 159-172) uses the default `provisioning_enabled: true`, so this specific `review_stacks_enabled: false` + `prevent_with_label` combination is not exercised by any existing test, confirming the gap is unaddressed in-repo.

An attacker (any GitHub user able to open a PR from a fork) simply opens a PR against the target repository without adding the configured provisioning label (for `prevent_with_label`) or with the label (for `allow_with_label`); the webhook's `pull_request`/`opened` payload flows unauthenticated-signature-checked but otherwise attacker-controlled data (`head.ref`, `labels`) directly into `stack_attributes` (`branch: params.pull_request.head.ref`), causing stack creation regardless of the repository owner's intent to disable review stacks entirely.

### Impact Explanation
The immediate effect is an unauthorized `Shipit::ReviewStack` row and a queued provisioning entry for a repository whose owner explicitly disabled review stacks (`review_stacks_enabled: false`). Because `ReviewStackProvisioningQueue#work` later calls `stack.provision` on queued stacks, this can lead to real provisioning/build task execution against the attacker's fork branch (`branch: params.pull_request.head.ref`) — i.e., an unauthorized deploy-like action was triggered on infrastructure the operator believed was protected by disabling review stacks. This stays within the target repository (not cross-tenant), but it is a genuine authorization bypass of a configured control, repeatable against any repository configured with `allow_with_label` or `prevent_with_label` and `review_stacks_enabled: false`, by any external user who can open a PR against that repo.

### Likelihood Explanation
Preconditions are realistic and match common configuration (`review_stacks_enabled: false` combined with a leftover/non-default `provisioning_behavior` value such as `prevent_with_label`). No secrets, tokens, or privileged roles are required — only the ability to open a pull request against the target repository (or from a fork, depending on repository settings) with a webhook delivered to the Shipit host. This is low-cost and repeatable for any repository in this misconfigured state.

### Recommendation
Fix the operator precedence in `provision?` by explicitly parenthesizing the `review_stacks_enabled` guard so it applies to all three branches, e.g.:
```ruby
def provision?
  repository.review_stacks_enabled &&
    (
      repository.provisioning_behavior_allow_all? ||
      (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
      (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
    )
end
```

### Proof of Concept
In `test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb`, add:
```ruby
test "does not create stacks when review_stacks_enabled is false, even for prevent_with_label" do
  repository = shipit_repositories(:shipit)
  configure_provisioning_behavior(
    repository:,
    provisioning_enabled: false,
    behavior: :prevent_with_label,
    label: "pull-requests-label"
  )
  payload = payload_parsed(:pull_request_opened)
  payload["pull_request"]["labels"] = []

  assert_no_difference -> { Shipit::Stack.count } do
    OpenedHandler.new(payload).process
  end
end
```
Assert `repository.review_stacks_enabled` (false) on one side against `Shipit::ReviewStack.exists?(environment: "pr#{payload['number']}")` (currently true due to the bug) on the other; the test currently fails, demonstrating the divergence.
