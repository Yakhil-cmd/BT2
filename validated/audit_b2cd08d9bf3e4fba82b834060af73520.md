### Title
Webhook signature verified against `repository.owner.login`/`organization.login` while handlers dispatch on the separate, unverified `repository.full_name` field, allowing cross-repository event forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App/webhook secret to validate the HMAC signature using `repository_owner`, computed as `params.dig('repository', 'owner', 'login')` (falling back to `params.dig('organization', 'login')`). Once the signature check passes, `create` dispatches the raw, unmodified `params` hash to `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`. Every handler (e.g. `PushHandler`, and the shared `Handler#stacks`/`Handler#repository_name`) determines *which* `Repository`/`Stack` to act on using a **different** field of the same payload: `payload.dig('repository', 'full_name')`. Nothing ties `repository.owner.login` (the field used to pick the signing secret) to `repository.full_name` (the field used to select the target Stack). ### Finding Description
This engine supports multi-tenant configuration: `Shipit.github(organization: owner)` resolves a distinct `GithubApp`/webhook secret per GitHub organization onboarded to the same Shipit instance, and `Repository#github_app` looks it up by the repository's own `owner`. [6](#0-5) 

The binding that should hold is: **the organization whose secret validated the signature == the organization that owns the repository whose stacks get acted upon.** Instead, the code only enforces: *the organization named in `repository.owner.login` (or `organization.login`) validated the signature*, while the *actual write target* is resolved independently from `repository.full_name`, a sibling field in the identical unsigned-content-but-differently-parsed JSON body. Because the whole raw body is what's HMAC-signed, an attacker who legitimately controls **their own** onboarded organization (OrgA, with its own genuine `webhook_secret`) can construct a payload where:
- `repository.owner.login` (and/or `organization.login`) = `"OrgA"` → selects OrgA's secret for `verify_webhook_signature`
- `repository.full_name` = `"OrgB/victim-repo"` → selects an unrelated stack belonging to OrgB, tracked by the same Shipit instance

They sign this crafted JSON with OrgA's real webhook secret (which they legitimately possess as OrgA's GitHub App administrator) and POST it to the shared `WebhooksController#create` endpoint. `verify_signature` succeeds because it correctly validates the signature against OrgA's secret using `repository_owner == "OrgA"`. `create` then dispatches the same payload to handlers, which look at `repository.full_name == "OrgB/victim-repo"` and act on `OrgB`'s `Stack`.

For the `push` event, this reaches `PushHandler#process`, which finds all non-archived stacks in `OrgB/victim-repo` matching the pushed branch and calls `stack.sync_github(expected_head_sha: params.after)` — an attacker-controlled SHA — for every matching stack, entirely outside of `OrgB`'s authorization boundary. Depending on `continuous_deployment` settings, `sync_github` can enqueue deploy scheduling for a commit chosen by the attacker.

### Impact Explanation
This breaks the cross-repository trust boundary the signature check is meant to enforce: an entity that is only authorized (has only proven possession of a secret) for OrgA is able to make the application act as if a webhook for OrgB's repository was received, forging `expected_head_sha` and triggering downstream `Stack#sync_github`/continuous-deployment side effects on repositories/stacks it does not own. This is a cross-repository write in effect (forged sync state driving deploy pipeline decisions) achieved purely by controlling one legitimate-but-unrelated GitHub App installation on the same multi-tenant Shipit instance — satisfying the "cross-repository writes" / "unauthorized deploy" bar without needing the victim's `webhook_secret`, `api_clients_secret`, or any session/token.

### Likelihood Explanation
Requires only that the attacker administers (or compromises) one organization's GitHub App/webhook integration on a multi-tenant Shipit deployment that also serves other organizations' stacks — a realistic operating model for shipit-engine (a shared deploy tool typically installed once and used by many teams/orgs within a company). No access to the victim's secrets, sessions, or GitHub credentials is needed; the attacker only crafts one payload field (`repository.full_name`) independently of the field that selects the signing key (`repository.owner.login`/`organization.login`).

### Recommendation
After signature verification, re-derive the repository/organization strictly from the same field used to select the verification key (or verify that `repository.full_name`'s owner segment matches `repository.owner.login`/`organization.login` used in `verify_signature`) before dispatching to handlers, and have handlers consume that authenticated owner rather than trusting `repository.full_name` independently.

### Proof of Concept
1. Attacker administers GitHub App/organization `OrgA` on the shared Shipit instance and knows `OrgA`'s configured `webhook_secret`.
2. Attacker crafts a `push` event JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>",
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/victim-repo" }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<hmac-sha1(OrgA_webhook_secret, body)>` and POSTs to `/webhooks` with `X-Github-Event: push`.
4. `WebhooksController#verify_signature` computes `repository_owner = "OrgA"`, fetches OrgA's `GithubApp`, and the HMAC matches → passes. [7](#0-6) 
5. `create` calls `PushHandler.call(params)`; `Handler#stacks` resolves `Repository.from_github_repo_name("OrgB/victim-repo")` and `PushHandler#process` invokes `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` on OrgB's stacks. [5](#0-4)

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified
