### Title
Webhook signature verification org is decoupled from the repository the event actually writes to, allowing cross-org webhook forgery - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to validate the request against using `repository_owner`, a value read directly from the untrusted, attacker-supplied JSON body (`params.dig('repository', 'owner', 'login')`). The webhook handlers, however, resolve the actual `Repository`/`Stack` to act on using a different field of the same untrusted body: `payload.dig('repository', 'full_name')` (`Handler#repository_name`). These two fields are never checked for consistency, so the "organization whose secret authenticated the request" and "the repository that the event is applied to" are two independent, attacker-controlled values instead of one verified binding.

### Finding Description
`verify_signature` in [1](#0-0)  does:
```ruby
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
```
where `repository_owner` is derived purely from the payload itself: [2](#0-1) .

`Shipit.github(organization:)` looks up per-organization GitHub App config (multi-org support is a real, documented/tested feature — see `lib/shipit.rb` `github_app_config`/`github_organizations`, and the `secrets_double_github_app.yml` fixture defining `OrgOne` and `OrgTwo`) [3](#0-2) .

`GitHubApp#verify_webhook_signature` trivially returns `true` for an organization whose config has no `webhook_secret` set:
```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
``` [4](#0-3) 

Meanwhile, the event handler that actually performs the mutation resolves the target repository/stack from a *different* field of the same payload:
```ruby
def repository_name
  payload.dig('repository', 'full_name')
end
``` [5](#0-4) 

Because `repository.owner.login` (used to pick the verifying org/secret) and `repository.full_name` (used to pick the acted-upon repository) are independent JSON keys inside one attacker-controlled request body, an attacker can set them inconsistently: point `owner.login` at an organization whose `webhook_secret` is unset (verification trivially succeeds) while pointing `full_name` at a *different*, secret-protected organization's real repository. The signature check that "authenticates" the request is bound to the wrong organization relative to the repository actually written to — exactly the "organization that authenticated versus the repository that is written" equality break called out in the rules.

This is reachable by `PushHandler` (queues `GithubSyncJob`, `sync_github`) [6](#0-5) , and by the `status` handler which writes `Status` records tied to commit SHAs that feed continuous-delivery gating (`required_statuses`/`blocking_statuses` in `app/models/shipit/deploy_spec.rb`), as well as PR handlers that archive/unarchive review stacks based on `repository.full_name` lookups (e.g. `ClosedHandler`, `LabeledHandler`) [7](#0-6) .

### Impact Explanation
An attacker with no Shipit credentials, no `webhook_secret`, and no GitHub App key for the protected organization can forge webhook events (push, status, pull_request, membership) that are processed as if legitimately delivered for a specific protected repository, as long as any other organization configured in the same Shipit instance lacks a `webhook_secret`. Concretely:
- Forged `status` events can inject arbitrary commit statuses on the protected repo's commits; if those statuses satisfy `required_statuses`/`blocking_statuses` used to gate continuous delivery, this can enable an **unauthorized deploy** to proceed (Critical bucket: "an unauthorized deploy, rollback or merge").
- Forged `push` events can force `GithubSyncJob`/`sync_github` execution against the protected stack.
- Forged `pull_request`/`membership` events can archive/unarchive review stacks or alter team/user membership state tied to the protected org's repository.

This is a genuine confused-deputy/credential-scoping flaw: the verification decision and the resource-mutation decision consult two different, independently-forgeable fields of the same unauthenticated payload.

### Likelihood Explanation
Requires a Shipit deployment configured with more than one GitHub organization (a documented, supported configuration, evidenced by `secrets_double_github_app.yml`), where at least one configured organization has no `webhook_secret` set (also an explicitly supported/tested configuration state — `webhook_secret: # nil` in that same fixture, and `return true unless webhook_secret` in `github_app.rb`). Given multi-tenant Shipit installs onboarding new GitHub orgs incrementally, having at least one org temporarily or permanently without a webhook secret is realistic. No attacker-held secret, session, or API token is needed — only knowledge of the org names and a target repository's `full_name`, both of which are typically public information.

### Recommendation
Bind the signature-verifying organization to the resource actually mutated: derive the "verifying organization" from the same canonical field used by handlers (`repository.full_name`'s owner segment) rather than trusting `repository.owner.login`/`organization.login` independently, or explicitly assert `repository.owner.login == repository.full_name.split('/').first` before dispatching. Additionally, do not allow `verify_webhook_signature` to silently pass (`return true unless webhook_secret`) for a specific organization lookup path — require every configured GitHub App entry to define a `webhook_secret`, and fail closed (422) if a configured organization is missing one, rather than treating "no secret" as "no verification needed."

### Proof of Concept
1. Configure Shipit with two organizations, mirroring `test/dummy/config/secrets_double_github_app.yml`: `OrgOne` has a `webhook_secret` set; `OrgTwo` has `webhook_secret: nil`.
2. Ensure a real, tracked repository exists under `OrgOne`, e.g. `OrgOne/protected-repo`.
3. As an unauthenticated attacker, POST to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha-already-known-or-guessed>",
  "repository": {
    "owner": { "login": "OrgTwo" },
    "full_name": "OrgOne/protected-repo"
  }
}
```
No `X-Hub-Signature` header (or any arbitrary value) is required because `repository_owner` resolves to `OrgTwo`, whose `verify_webhook_signature` returns `true` unconditionally (`return true unless webhook_secret`).
4. `verify_signature` passes; `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name('OrgOne/protected-repo')` and triggers `sync_github`/`GithubSyncJob` for the protected stack — despite the request never being validated against `OrgOne`'s actual `webhook_secret`.
5. The same technique applies to the `status` event/handler to inject forged commit statuses on `OrgOne/protected-repo` commits, potentially unblocking continuous-delivery gating checks.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
