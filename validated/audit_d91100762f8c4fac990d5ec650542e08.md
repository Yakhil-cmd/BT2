## Title
Signature replay across AA (contract) instances via `is_valid_signed_package`/`validateSignedMessage` lacking recipient-address binding - (File: signed_message.js, object_hash.js, formula/evaluation.js)

### Summary
The oscript primitive `is_valid_signed_package()`, used by Autonomous Agents (AAs) to verify off-chain signed messages (oracle feeds, payment-channel updates, order signatures, etc.), delegates to `signed_message.validateSignedMessage()`. The hash that is actually signed — computed by `objectHash.getSignedPackageHashToSign()` — is derived only from the `signed_message` payload, `authors` (addresses/definitions), `last_ball_unit`, `timestamp` and `version`. It never includes the AA address that is performing the verification (`this_address`), nor any other unique per-deployment identifier. This is structurally identical to the eth-bridge finding: none of the signature schemes bind the signature to the specific "contract instance" (here, the specific AA address) that is supposed to consume it.

### Finding Description
`is_valid_signed_package(signed_package, address)` evaluates the given `address` only to identify which author in the package must have produced the signature — it is the *signer's* address, not the *verifying AA's* address: [1](#0-0) 

The actual bytes that get hashed and signed come from `getSignedPackageHashToSign`, which clones the package, strips `authentifiers`, and hashes the remaining `signed_message`/`last_ball_unit`/`version`/`authors` fields — with no reference at all to which AA (contract instance) is meant to accept the package: [2](#0-1) 

`validateSignedMessage` itself only checks that (a) the JSON is well-formed, (b) the claimed `address`'s definition matches, and (c) the authentifier verifies against `unit_hash_to_sign = getSignedPackageHashToSign(objSignedMessage)` — again with no binding to the calling AA's address: [3](#0-2) 

Because there is no platform-enforced domain separator (equivalent to `thisContractAddress`/`chainID` in the Solidity report), any AA that wants to prevent a signed package intended for one AA instance from being replayed against a different instance (e.g. two deployments of the same AA template, or a decoy/cloned AA sharing the same trusted signer address) must manually embed `this_address` (or another unique identifier) inside the `signed_message` payload and check it in oscript. The codebase's own test data shows this is exactly the pattern developers are expected to remember to add: [4](#0-3) 

If an AA author omits this manual check (a very plausible omission, since nothing in `is_valid_signed_package` or `validateSignedMessage` enforces it, and the failure mode is silent), a signature produced by a legitimate signer for AA instance A (e.g., a price attestation, an order confirmation, or a payment-channel closing balance) can be replayed verbatim against a different AA instance B that happens to trust the same signer address — for example two deployments from the same AA template, or a malicious AA deployed by an attacker who reuses a legitimate template and tricks the same set of oracle/counterparty addresses into signing for it once.

### Impact Explanation
An attacker who deploys a cloned/similar AA (any user can define and instantiate AAs on ocore) and gets a legitimate signer (oracle, payment-channel counterparty, order originator) to produce one signed package can replay that exact package into their attacker-controlled AA instance if that AA's oscript, or the victim AA's oscript, does not itself verify a unique identifier bound to the specific instance. This can lead to unauthorized fund release from an AA (e.g., a stale/foreign payment-channel closing signature accepted as authorization to pay out balances), or a peer/order signature intended for one exchange-style AA validated by an unrelated AA — i.e., concrete AA fund loss, matching the "Medium/High" severity bar requested.

### Likelihood Explanation
Exploitability depends entirely on whether individual AA authors add manual domain-separation fields (`this_address`, asset id, etc.) to the signed message and verify them — the platform does not enforce this by default. Since the primitive's hash function (`getSignedPackageHashToSign`) is used identically across all AAs without any built-in address binding, any AA template that is copy/deployed multiple times (a common pattern for exchange, payment-channel, or oracle-consuming AAs) is at risk if the template's author didn't add such a check, making this a realistic and repeatable bug class rather than a one-off implementation slip.

### Recommendation
- Short term: document prominently (and provide linter/checklist guidance) that any oscript using `is_valid_signed_package`/`validateSignedMessage` must include `this_address` (and ideally an application-specific domain tag) inside the signed message and verify it, exactly as done in the reference payment-channel example.
- Long term: consider adding an optional built-in domain-separation field to `getSignedPackageHashToSign` (e.g., automatically mixing in the verifying AA's address when `is_valid_signed_package` is invoked from an AA context) so that replay across differing verifying addresses is prevented by default rather than relying on every app author remembering to do it manually.

### Proof of Concept
1. Deploy AA `Channel_A` from a public payment-channel-style template that calls `is_valid_signed_package(trigger.data.sentByPeer, $peerAddress)` but omits (or a developer forgets) the `signed_message.channel != this_address` check shown in the reference test.
2. Alice and Bob operate `Channel_A`; Bob signs `{amount_spent: 100, period: 1}` (no channel/address binding) to close their channel, sending the signed package to Alice.
3ロ Eve deploys `Channel_B` from the identical template, with Bob also listed as an authorized cosigner/peer address (e.g., by social-engineering Bob into believing it's the same channel, or because Bob's address is reused across MPC-style multi-channel setups).
4. Eve submits the same signed package (`trigger.data.sentByPeer`) that Bob signed for `Channel_A` as a trigger to `Channel_B`. Since `getSignedPackageHashToSign` and `validateSignedMessage` never reference `this_address`, the signature verifies successfully in `Channel_B`, letting Eve claim funds/state transitions in `Channel_B` intended only for `Channel_A`. function getSignedPackageHashToSign(signedPackage) {
	var unsignedPackage = _.cloneDeep(signedPackage);
	for (var i=0; i<unsignedPackage.authors.length; i++)
		delete unsignedPackage.authors[i].authentifiers;
	var sourceString = (typeof signedPackage.version === 'undefined' || signedPackage.version === constants.versionWithoutTimestamp) ? getSourceString(unsignedPackage) : getJsonSourceString(unsignedPackage);
	return crypto.createHash("sha256").update(sourceString, "utf8").digest();
}
