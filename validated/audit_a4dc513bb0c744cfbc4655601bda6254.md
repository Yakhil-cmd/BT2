### Title
Uncaught `throw` in payment-input validation crashes node on crafted double-spend unit - (File: `validation.js`)

### Summary
CVE-2017-10688 is a LibTIFF assertion abort reachable via crafted, attacker-controlled input, causing a remote DoS crash. The analogous bug class in ocore is a hard `throw Error(...)` (instead of the standard `cb(error)` rejection pattern) inside an asynchronous DB-callback in the payment-input validation path, reachable from a single unprivileged unit posted by any peer or light client. Because the throw happens inside a `conn.query` callback rather than in the synchronous validation call stack, it is not caught by the `try/catch` wrappers used elsewhere in `validate()`, and can propagate as an uncaught exception, crashing the node process handling the unit.

### Finding Description
`validatePaymentInputsAndOutputs` in `validation.js` processes payment inputs of type `"transfer"` by querying the source output and validating that it can legally be spent: [1](#0-0) 

Two of the branches inside this `conn.query` result callback use `throw Error(...)` rather than `return cb(error)`:
- `if (rows.length > 1) throw Error("more than 1 src output");`
- `if (src_output.sequence === 'temp-bad') throw Error("spending a stable temp-bad output " + input.unit);`

Every other rejection path in this same function (and throughout `validation.js`) uses the callback-based error propagation (`return cb("...")`), which is safely handled by the `async.series` error handler in `validate()`: [2](#0-1) 

That error handler only catches synchronous throws or errors passed via `cb(err)`; it cannot catch an exception thrown asynchronously inside a `conn.query` callback fired later on the event loop. Such an exception bypasses `commit_fn`/`unlock()`/`callbacks.ifUnitError()` entirely and becomes an uncaught exception at the process level. The nearby throws for the private/fixed-denomination branch (`"no src_coin"`, `"no src_output"`, `"no denomination in src coin"`, `"no src coin amount"`) share the same anti-pattern: [3](#0-2) 

The unit-validation entry point `validate()` is reached directly from `handlePostedJoint`/`handleJoint`, i.e., from any peer or light client submitting an ordinary unit — no privileges required: [4](#0-3) [5](#0-4) 

The `"spending a stable temp-bad output"` condition is reachable whenever an attacker constructs a payment input that references a unit/output already marked `sequence='temp-bad'` in the local `outputs`/`units` tables and whose `main_chain_index` is at or before `last_ball_mci` (i.e., stable in the referencing unit's parents) — an attacker-crafted double-spend scenario that any node will eventually see when a conflicting pair of spends is broadcast and one loses the double-spend race, then a further unit tries to spend the losing (temp-bad) output.

### Impact Explanation
An uncaught exception thrown from within an async DB callback is not caught by any surrounding `try/catch` in the synchronous call stack of `validate()`, and Node.js's default behavior for an uncaught exception is to terminate the process unless a global `process.on('uncaughtException', ...)` handler intervenes. If no handler recovers gracefully for this specific code path, a single crafted unit (or a pair of conflicting units engineered by the attacker) can crash the full node, hub, or light-vendor process that attempts to validate it — a remote, unauthenticated denial of service. This matches the "network unable to confirm new units" impact bucket: repeated submission of such units to multiple nodes could disrupt network-wide validation/confirmation.

### Likelihood Explanation
Likelihood is moderate: the attacker does not need any special privilege, key, or protocol violation — they only need to get two conflicting spends of the same output accepted such that one is marked `temp-bad` and stable, then submit a further transfer input referencing that same output. This is a normal (if adversarial) double-spend sequence achievable by any wallet/unit poster, making the trigger condition realistically reachable without hub/peer compromise.

### Recommendation
Replace the `throw Error(...)` statements inside the async `conn.query` callback (and the private/fixed-denomination src_coin checks) in `validatePaymentInputsAndOutputs` with `return cb(...)` calls so that these conditions are reported through the standard `ifUnitError`/`ifJointError` validation-failure path instead of throwing inside an asynchronous callback. This ensures the offending unit is cleanly rejected and the process/connection is not put at risk of crashing on attacker-supplied input.

### Proof of Concept
1. Broadcast two conflicting units, `U1` and `U2`, that spend the same source output `O`.
2. Let the network/local node resolve the double-spend such that `U2`'s payment is marked `sequence='temp-bad'` in the `units`/`outputs` tables, and this state becomes stable (`main_chain_index <= last_ball_mci` relative to later units).
3. Construct and broadcast a further unit `U3` whose payment input of type `"transfer"` references the `temp-bad`, stable output produced by `U2` (`input.unit = U2`, matching `message_index`/`output_index`).
4. When any node validates `U3`, execution reaches `validatePaymentInputsAndOutputs` → the `conn.query` callback in `validation.js:2443-2461`, sees `bStableInParents === true` and `src_output.sequence === 'temp-bad'`, and executes `throw Error("spending a stable temp-bad output " + input.unit)` inside the async callback, outside any catching `try` used by `validate()`'s `async.series` handler, resulting in an uncaught exception on the validating node.
