### Title
Clickjacking of merge-queue actions via `X-Frame-Options: ALLOWALL` in `MergeStatusController#show` - (File: app/controllers/shipit/merge_status_controller.rb)

### Summary
`Shipit::MergeStatusController#show` unconditionally sets `response.headers['X-Frame-Options'] = 'ALLOWALL'` and never sets a `Content-Security-Policy: frame-ancestors` header, allowing the fully-rendered merge-status page (including the `enqueue_merge_request`/`dequeue_merge_request` forms) to be embedded in an iframe on any attacker-controlled origin. A logged-in operator lured into visiting the malicious page can be tricked into clicking an invisible overlay positioned over the "Add to merge queue" button, causing their real, cookie-authenticated, CSRF-token-valid browser to submit the merge-queue PUT request without any deliberate intent to do so.

### Finding Description
The broken binding is: `human clicked "Add to merge queue"` == `victim's browser submitted PUT enqueue_merge_request with victim's session cookies and CSRF token`. Rails' `protect_from_forgery with: :exception` [1](#0-0)  and `force_github_authentication`/`current_user.authorized?` [2](#0-1)  only verify that the *request* originates from an authenticated, authorized session with a valid same-origin CSRF token — they do not, and cannot, verify that the *human* actually intended to trigger that request. Because `show` explicitly disables framing protection (`ALLOWALL`) and sets no `frame-ancestors` CSP [3](#0-2) , an attacker can embed the real, fully-authenticated page (with correct CSRF token embedded via the layout) inside a cross-origin iframe and clickjack the genuine `enqueue_merge_request_path` form [4](#0-3) , producing a real, validly-authenticated, CSRF-token-correct PUT that Shipit's `MergeRequest.request_merge!` will happily process [5](#0-4) . The two sides of the equality diverge: the server sees "authorized session submitted request," but the human never intended the click — CSRF and authorization checks pass while consent is forged via UI redress, exactly the scenario the question describes.

### Impact Explanation
A successful clickjack forces an authenticated Shipit operator's browser to add (or, with a second click on `dequeue`, remove) a specific pull request to/from the merge queue of a stack the attacker chooses (the attacker controls the `stack_id`/`referrer` query params used to select the target stack via `Stack.from_param!` or the referrer-parsed repo/branch lookup [6](#0-5) ). This is a forced, state-changing action ("an unauthorized ... merge") performed as a legitimately authorized user without their consent, and it is repeatable against any stack/PR the attacker names in the iframe URL as long as they can lure a logged-in operator to the page, matching the described severity of forcing merge-queue mutation via consent bypass rather than credential theft.

### Likelihood Explanation
The precondition is a normal, common one: any Shipit operator with an active browser session visiting an attacker page. No secrets, tokens, or GitHub privileges are required — the attacker only needs the victim's browser to load an iframe pointing at a public, unauthenticated-by-header (`skip_authentication only: %i[check show]`) `show` endpoint [7](#0-6) . The attack cost is a single crafted HTML page plus a lure (phishing link, malicious ad, etc.), and it is trivially repeatable against arbitrary stacks/PRs by varying the `referrer`/`stack_id` parameters.

### Recommendation
Do not set `X-Frame-Options: ALLOWALL` (or, if embedding is a genuine product requirement for specific trusted origins such as `github.com`, restrict via `Content-Security-Policy: frame-ancestors https://github.com` and drop the header for the general case), and/or require a fresh, explicit user interaction (e.g., a confirmation step not satisfiable via a single overlay click) before performing the state-changing enqueue/dequeue actions.

### Proof of Concept
Add a minitest integration test to `test/controllers/merge_status_controller_test.rb` (existing suite location) asserting:
1. `GET merge_status_path(...)` response always has `response.headers['X-Frame-Options'] == 'ALLOWALL'` and no `Content-Security-Policy` header containing `frame-ancestors`.
2. With a stubbed session (`session[:user_id]` set to an authorized user), `PUT enqueue_merge_request_path(stack, pull_request_number)` with a valid CSRF token succeeds (`response).must_be :successful?` and `MergeRequest.find_by(number: ...)` transitions to `waiting?`) with no additional interactive confirmation step required — demonstrating that a framed, single click is sufficient to mutate merge-queue state.
