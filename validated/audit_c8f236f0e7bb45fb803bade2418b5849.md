### Title
Stack-scoped ApiClient token bypasses its own authorized-stack binding in `CCMenuController#stack` - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::CCMenuController` authorizes an `ApiClient` token to read `:stack` data, but resolves the target `Stack` by directly calling `Stack.from_param!(params[:stack_id])` instead of using the scoped `stacks` helper that every other API controller relies on. This breaks the intended binding "stack a token authorizes == stack it actually touches," letting a stack-scoped, read-only CCMenu token read the CI/deploy status of any stack in the installation.

### Finding Description
The base API controller establishes the invariant that a stack-scoped `ApiClient` (one with `stack_id` set) may only operate on that single stack: `stacks` filters `Stack.all` down to `Stack.where(id: current_api_client.stack_id)` when `stack_id?` is true, and the shared `stack` accessor resolves `params[:stack_id]` through this scoped relation via `stacks.from_param!(params[:stack_id])`. [1](#0-0) 

`CCMenuController` overrides this `stack` method and drops the scoping entirely, resolving the stack straight from the global `Stack` model: [2](#0-1) 

The controller still declares `require_permission :read, :stack`, which only calls `current_api_client.check_permissions!('read', 'stack')` — a check against the client's `permissions` array, not against which specific stack the client is bound to: [3](#0-2) [4](#0-3) 

Because `ApiClient` objects can be created scoped to a single stack (e.g. by the `CCMenuUrlController`, which mints a token with `permissions: %w[read:stack]` tied implicitly to no `stack_id` restriction elsewhere, or by any user via the `api_clients` UI with a `stack_id`), the `require_permission` check passes for *any* stack as long as the token carries `read:stack`, while the actual stack object used to render the response is taken from the unscoped `Stack.from_param!` call driven entirely by attacker-supplied `params[:stack_id]`.

Also note `CCMenuController` supports authenticating via a bare `?token=` query parameter (rather than only HTTP Basic auth), which is how the CCMenu-generating flow (`CCMenuUrlController`) intentionally works — tokens end up embedded in plain URLs: [5](#0-4) [6](#0-5) 

The equality this breaks is:
`stack(s) authorized for ApiClient token == stack(s) actually rendered by CCMenuController#show`

Before the flaw: for a stack-scoped `ApiClient`, `stacks` == `Stack.where(id: current_api_client.stack_id)`, so any controller using `stack ||= stacks.from_param!(...)` only ever touches the authorized stack.
After: `CCMenuController#stack` == `Stack.from_param!(params[:stack_id])`, unconditionally, independent of `current_api_client.stack_id`.

### Impact Explanation
This meets the High-severity bar of "unauthenticated/unauthorized read of stack state, task streams, or deploy output" analogously to the scope-authorization escalation criterion: a token intentionally minted and distributed for exactly one stack's CI status (this is the pattern CCMenu URLs are built for — a lightweight, unauthenticated-feeling, embeddable per-stack status badge/token) can be replayed with a different `stack_id` to read the deploy/status of stacks the token was never meant to authorize, disclosing stack names, last build status/label, and whether the stack is locked (`lastBuildStatus 'Failure'` on lock) for arbitrary stacks in the same Shipit install.

### Likelihood Explanation
Exploitation requires nothing beyond possession of one valid, even narrowly-scoped, `read:stack` token — which is by design distributed relatively casually (embedded in a CCMenu URL query string, as `CCMenuUrlController` demonstrates) and not the private webhook/App secrets excluded by scope rules. Any holder of such a token can simply swap the `stack_id` path segment on the same authenticated request to probe or read other stacks' status. No additional privilege, session, or GitHub credential is required beyond the single token already granted to the caller.

### Recommendation
Remove `CCMenuController`'s private `stack` override, or reimplement it using the scoped `stacks` relation (`stacks.from_param!(params[:stack_id])`) exactly as `BaseController#stack` does, so that stack-scoped `ApiClient` tokens can only ever resolve their bound stack.

### Proof of Concept
1. As a user with access to Stack A, request a CCMenu URL: `GET /ccmenu/*stack_a` (via `CCMenuUrlController#fetch`), which creates (or reuses) an `ApiClient` with `permissions: ['read:stack']` and returns a URL like `.../api/stacks/*stack_a/ccmenu?token=<TOKEN>`. [7](#0-6) 
2. Take `<TOKEN>` and issue: `GET /api/stacks/*stack_b/ccmenu?token=<TOKEN>` for an unrelated Stack B that the token was never generated for.
3. `authenticate_api_client` in `CCMenuController` accepts the token via `ApiClient.authenticate(params[:token])`, `require_permission :read, :stack` only checks the token's global `permissions` list (passes), and `stack` resolves `Stack.from_param!(params[:stack_id])` — i.e., Stack B directly, unscoped — returning Stack B's CI/deploy status XML instead of rejecting the request. [8](#0-7)
