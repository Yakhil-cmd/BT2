### Title
Staking Reward Silently Burned When Validator's `CLPoolAddr` Equals `RewardAddr` in `assignStakingRewards` / `assignStakingRewardsFlex` — (File: `kaiax/reward/impl/getter.go`)

---

### Summary

In `assignStakingRewards` and `assignStakingRewardsFlex`, when a validator's consensus-liquidity pool address (`CLPoolAddr`) equals their AddressBook reward address (`RewardAddr`), a direct map assignment overwrites the first allocation with the second. The `cnAmount` portion of the staking reward is silently dropped — never credited to any address — while the `remaining` counter is decremented by the full `reward`, so the lost amount is also not redirected to the proposer. The result is that `cnAmount` of KAIA is permanently unaccounted for in every block where this condition holds.

---

### Finding Description

`assignStakingRewards` (Prague path, lines 521–525) and `assignStakingRewardsFlex` (Prague path, lines 474–480) both contain the following pattern:

```go
// kaiax/reward/impl/getter.go  lines 521-525
if isPrague && cn.CLStakingInfo != nil {
    cnAmount, clAmount := cn.Split(reward)
    alloc[cn.RewardAddr] = cnAmount                    // (1) write cnAmount
    alloc[cn.CLStakingInfo.CLPoolAddr] = clAmount      // (2) overwrites (1) if addrs equal
}
```

`alloc` is a plain `map[common.Address]*big.Int`. When `cn.RewardAddr == cn.CLStakingInfo.CLPoolAddr`, assignment (2) silently replaces assignment (1). The entry for that address ends up holding only `clAmount`; `cnAmount` is gone.

Immediately after, `remaining` is decremented by the full `reward = cnAmount + clAmount`:

```go
// line 529
remaining.Sub(remaining, reward)
```

So `remaining` (which becomes `kip82Remainder` and is added to the proposer) is also reduced by the full `reward`, not just `clAmount`. The proposer does **not** receive the lost `cnAmount` either.

The identical overwrite exists in `assignStakingRewardsFlex` at lines 474–480.

The downstream `FinalizeState` loop credits only what is in `spec.Rewards`:

```go
// kaiax/reward/impl/blockstate.go  lines 53-55
for addr, amount := range spec.Rewards {
    state.AddBalance(addr, amount)
}
```

`cnAmount` is absent from `spec.Rewards`, so it is never minted to any account.

---

### Impact Explanation

For every block in which a validator has `CLPoolAddr == RewardAddr`:

- The validator's staking reward is `clAmount` instead of the correct `cnAmount + clAmount`.
- `cnAmount` is permanently unaccounted for — it is neither credited to the validator, nor to the proposer, nor to any fund.
- The `spec.Rewards` sum is less than `spec.Minted + spec.TotalFee − spec.BurntFee` by exactly `cnAmount`, breaking the conservation invariant verified by `sanityCheckRewardSpec` (test-only) but not enforced in production by `spec.Validate()`.
- This constitutes an incorrect reward distribution and an effective unauthorized burn of KAIA that should have been distributed.

---

### Likelihood Explanation

The `CLPoolAddr` is registered in the CLRegistry system contract by the validator; the `RewardAddr` is registered in the AddressBook contract by the same validator. No on-chain or off-chain guard in the repository prevents a validator from setting `CLPoolAddr == RewardAddr`. The `parseCallResult` and `parsePermissionlessCallResult` functions that build `StakingInfo` perform no such equality check. The `consolidateNodes` function likewise has no guard. Any validator (or a governance actor who controls both registrations) can trigger this condition.

---

### Recommendation

Replace the direct map assignments with accumulating additions, mirroring the `IncRecipient` pattern used everywhere else in the reward spec:

```go
// assignStakingRewards — Prague path
if isPrague && cn.CLStakingInfo != nil {
    cnAmount, clAmount := cn.Split(reward)
    if alloc[cn.RewardAddr] == nil {
        alloc[cn.RewardAddr] = new(big.Int)
    }
    alloc[cn.RewardAddr].Add(alloc[cn.RewardAddr], cnAmount)

    if alloc[cn.CLStakingInfo.CLPoolAddr] == nil {
        alloc[cn.CLStakingInfo.CLPoolAddr] = new(big.Int)
    }
    alloc[cn.CLStakingInfo.CLPoolAddr].Add(alloc[cn.CLStakingInfo.CLPoolAddr], clAmount)
}
```

Apply the same fix to `assignStakingRewardsFlex`. Additionally, add a test case where `CLPoolAddr == RewardAddr` and assert that the full `reward` is credited to that address.

---

### Proof of Concept

**Setup (Prague / Kore hardfork active, deferred fees):**

- One validator: `RewardAddr = 0xAAA`, `StakingAmount = 10_000_000 KAIA`
- Same validator's CL: `CLPoolAddr = 0xAAA` (same address), `CLStakingAmount = 5_000_000 KAIA`
- `MinimumStake = 5_000_000 KAIA`
- `stakersReward = 1_000_000 kei`

**Trace through `assignStakingRewards`:**

1. `cnTotalStakingAmount = 10_000_000 + 5_000_000 = 15_000_000`
2. `totalExcessInt = 15_000_000 − 5_000_000 = 10_000_000`
3. `reward = (10_000_000 × 1_000_000) / 10_000_000 = 1_000_000 kei`
4. `cn.Split(1_000_000)` → `cnAmount = 666_666 kei` (10M/15M), `clAmount = 333_333 kei` (5M/15M)
5. `alloc[0xAAA] = 666_666` → then `alloc[0xAAA] = 333_333` (overwrite)
6. `remaining -= 1_000_000` (full reward, not just clAmount)

**Result:** `0xAAA` receives `333_333 kei`; `666_666 kei` is never credited anywhere. `remaining = 0`, so the proposer receives no compensation for the lost amount. The block's total credited rewards are `666_666 kei` short of the expected `1_000_000 kei`. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4)
