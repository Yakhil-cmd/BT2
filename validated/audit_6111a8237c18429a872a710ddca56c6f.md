### Title
RAY-valued market totals overflow `i128`, permanently freezing all pool operations - ([File: common/src/rates/scaling.rs](common/src/rates/scaling.rs))

### Summary
A market whose scaled borrow or supply balance grows large enough can make `scaled_amount * index / RAY` exceed `i128::MAX`, after which every operation that performs interest accrual panics with `MathOverflow`. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
`accrue_step` begins by converting total borrowed and supplied shares into RAY-denominated balances through `scaled_to_original`, which calls `Ray::mul`. [4](#0-3) [1](#0-0) 

`Ray::mul` delegates to `mul_div_half_up`, whose widened `I256` path is only overflow-safe for intermediates; it still returns `None` when the final RAY result does not fit `i128`, causing `MathOverflow`. [5](#0-4) [6](#0-5) 

The overflow can occur before either index reaches `MAX_BORROW_INDEX_RAY` or `MAX_SUPPLY_INDEX_RAY`, because the vulnerable product is market shares multiplied by the index rather than the index itself. [7](#0-6) [8](#0-7) 

Every mutating market operation invokes `global_sync` before applying the requested mutation, so the panic repeats before `repay`, `withdraw`, `liquidate`, `clean_bad_debt`, and further `supply` or `borrow` processing can make progress. [3](#0-2) [9](#0-8) [10](#0-9) 

The public controller paths needed to create the condition are `supply` and `borrow`, while `repay`, `withdraw`, `liquidate`, and `update_indexes` remain permissionless or caller-authorized but cannot bypass the accrual panic. [11](#0-10) [12](#0-11) 

### Impact Explanation
This is permanent freezing of user funds and protocol insolvency risk: depositors cannot withdraw, borrowers cannot repay, and liquidators cannot progress because the same accrual panic precedes each remediation path. [3](#0-2) [13](#0-12) 

The existing integration test explicitly demonstrates that `update_indexes`, `withdraw`, and `repay` all fail with `MATH_OVERFLOW` after the market crosses the RAY-value ceiling while its borrow index remains below the configured index cap. [14](#0-13) 

### Likelihood Explanation
The attack requires an exceptionally large market position and enough elapsed accrual for `scaled_amount * index / RAY` to exceed approximately `1.70e38`, so it is not an immediate low-capital exploit. [15](#0-14) 

The condition is nevertheless reachable through ordinary unprivileged `supply`, `borrow`, and index-update flows, and the repository reproduces it with a one-billion-token, 18-decimal market at sustained 98% utilization. [16](#0-15) [17](#0-16) 

### Recommendation
Represent aggregate borrowed and supplied values in `I256`, or use capped/saturating aggregate-value calculations during accrual, so the market remains operable when a nominal RAY value exceeds `i128::MAX`. [18](#0-17) [19](#0-18) 

Additionally enforce market supply and borrow caps against the worst-case future index multiplication, or add an explicit terminal accrual state that permits repayment, withdrawal, liquidation, and bad-debt cleanup after the numeric ceiling is reached. [7](#0-6) [20](#0-19) 

### Proof of Concept
1. Create or select an 18-decimal market capable of holding approximately `1_000_000_000` whole tokens, then call `supply` with `1e27` base units so the position is approximately `1e36` RAY shares. [21](#0-20) [22](#0-21) 
2. Provide sufficient collateral in another market and call `borrow` for approximately 98% of the first market's supplied amount, keeping utilization high. [23](#0-22) [24](#0-23) 
3. Let time advance in bounded accrual chunks and invoke `update_indexes`; each step multiplies the large aggregate share balance by the growing borrow or supply index through `scaled_to_original`. [3](#0-2) [25](#0-24) [1](#0-0) 
4. Once the index exceeds roughly `170` for `1e36` shares, the RAY-valued balance exceeds `i128::MAX`; the repository test observes `MATH_OVERFLOW` on `update_indexes` before `MAX_BORROW_INDEX_RAY` is reached. [26](#0-25) 
5. Subsequent `withdraw` and `repay` calls hit the same mandatory accrual and also fail with `MATH_OVERFLOW`, leaving the market permanently frozen. [3](#0-2) [13](#0-12)

```rust
pub(crate) fn global_sync(env: &Env, cache: &mut Cache) {
    if !cache.needs_accrual() {
        return;
    }

    let mut remaining = cache.elapsed_ms();
    while let Some(nonzero) = NonZeroU64::new(remaining) {
        let chunk = nonzero.get().min(MAX_COMPOUND_DELTA_MS);
        accrue_chunk(env, cache, chunk);
        remaining = remaining.saturating_sub(chunk);
    }

    cache.mark_accrued();
```

```rust
/// Computes `x * y / d` rounded half up. Returns `None` if `x < 0`, `y < 0`, `d <= 0`, or the
/// result does not fit in `i128`.
pub fn try_mul_div_half_up(env: &Env, x: i128, y: i128, d: i128) -> Option<i128> {
    if x < 0 || y < 0 || d <= 0 {
        return None;
    }
    let half = d / 2;

    // Fast path: the biased product fits `i128`, so the whole computation is
    // native. `x * y + half` is non-negative here, so `/` is the floor the
    // widened path would produce.
    if let Some(biased) = x
        .checked_mul(y)
        .and_then(|product| product.checked_add(half))
    {
        return Some(biased / d);
    }

    let (x256, y256, d256) = to_i256_operands(env, x, y, d);
    x256.mul(&y256)
        .add(&I256::from_i128(env, half))
        .div(&d256)
        .to_i128()
}
```

```rust
/// The cliff. A billion whole tokens is `1e36` raw ray; the value ceiling is
/// `i128::MAX`, 170 times that. At the XLM curve's steep segment the index
/// grows past 170x in a few years, and the next accrual panics inside
/// `scaled_to_original`. Every verb accrues first, so the market freezes:
/// no repay, no withdraw, no liquidation. The index cap never engages.
#[test]
fn a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap() {
    let mut t = LendingTest::new()
        .with_market(big("BIG18", 18, xlm_curve()))
        .with_market(col())
        .with_max_utilization_disabled_all_markets()
        .build();
    lift_caps(&t, "BIG18", 18);
    lift_caps(&t, "COL", 7);
    let principal = BILLION * 10i128.pow(18);
    t.supply_raw(BOB, "BIG18", principal);
    let debt = principal / 100 * 98;
    t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
    t.borrow_raw(ALICE, "BIG18", debt);

    let mut years = 0u32;
    let failure = loop {
        years += 1;
        assert!(
            years <= 40,
            "no cliff within 40 years; the bound in docs/reference/formulas.md is wrong"
        );
        t.advance_time(YEAR_SECS);
        if let Err(e) = t.try_update_indexes_for(&["BIG18"]) {
            break e;
        }

    assert_contract_error(failed, errors::MATH_OVERFLOW);
    let last = book(&t, "BIG18");

        last.borrow_index < MAX_BORROW_INDEX_RAY,
        "the index cap did not engage before the value overflow"

    assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
```

```markdown
| Deposit conversion at the supply-index floor | About 170.14 million whole tokens before scaled-share overflow |

The token-to-RAY maximum is also the admitted cap maximum. Accrued position
values and market totals must independently fit the RAY domain; valid caps and
bounded indexes do not guarantee that future accrual fits. Value overflow can
occur before the index ceiling and block repayment/withdrawal because those
operations accrue first. At the borrow-index ceiling, further accrual produces
no borrower interest. No dedicated ceiling alarm is emitted.
```
