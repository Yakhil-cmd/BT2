### Title
Cross-tenant assignee metadata forgery via webhook signature/resource binding mismatch - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects the HMAC-verifying GitHub App/org config using `params.dig('repository', 'owner', 'login')` (or `organization.login`), while `Shipit::Webhooks::Handlers::PullRequest::AssignedHandler` resolves the affected `Repository`/`Stack`/`PullRequest` using the independent field `params.repository.full_name`. Since both fields are attacker-supplied JSON in a raw POST body, they are never cross-checked, letting a forged event "verified" against one (secret-less) org's config mutate assignment metadata on a `PullRequest` belonging to a completely different org's `Stack`.

### Finding Description
The intended binding is: `repository_owner` (the org whose secret validated the request) `==` owner(`params.repository.full_name`) (the org whose data gets mutated).

- `verify_signature` computes `repository_owner = params.dig('repository','owner','login') || params.dig('organization','login')` and calls `Shipit.github(organization: repository_owner)`, then `github_app.verify_webhook_signature(signature, raw_post)`. [1](#0-0) 
- `GitHubApp#verify_webhook_signature` returns `true` unconditionally `unless webhook_secret` is configured for that org. [2](#0-1) 
- Multi-org configs commonly leave `webhook_secret` unset per org, as shown in the shipped example config. [3](#0-2) 
- `AssignedHandler#process` never looks at `repository.owner.login`; it resolves the target repository purely from `params.repository.full_name` via `Repository.from_github_repo_name`, joins to `stacks`/`repositories`, finds the matching `PullRequest` by `number`, and calls `pull_request.update(github_pull_request: params.pull_request)`, which rewrites `assignees` (backed by `PullRequestAssignment` rows). [4](#0-3) 
- `Repository.from_github_repo_name` simply splits the attacker-controlled string on `/` and does a `find_by(owner:, name:)` lookup — no relationship to the org used for signature verification. [5](#0-4) 

Exploit flow: attacker crafts a raw JSON body with `repository.owner.login` (or top-level `organization.login`) set to `attacker-org` — any org name configured in Shipit whose `webhook_secret` is blank/unset — while setting `repository.full_name` to `victim-org/victim-repo` and `action: "assigned"`/`assignee.login` to an arbitrary GitHub login. POSTs to `/webhooks` with header `X-Github-Event: pull_request`. `verify_signature` looks up `attacker-org`'s config, finds no `webhook_secret`, and returns `true` for any signature (even a missing/garbage one, since `verify_webhook_signature` short-circuits before ever inspecting the value). The handler then updates the real `victim-org/victim-repo` `PullRequest`'s assignees using attacker-chosen logins.

No existing guard prevents this: `drop_unhandled_event` only checks the event type; `ExplicitParameters` schema in `AssignedHandler` validates types/presence, not cross-field consistency between `repository.owner.login` and `repository.full_name`; there is no `require_permission!`/`stacks` scope check for webhook processing (this is unauthenticated infrastructure by design, secured only by the HMAC signature, which is bypassed here); `force_github_authentication` and `User#authorized?` are unrelated to webhook ingestion.

### Impact Explanation
An attacker can write arbitrary `PullRequestAssignment` rows (and trigger the associated hooks) on any victim `PullRequest`/`Stack`/repository known to the Shipit instance, provided any org registered in Shipit's config has an empty `webhook_secret`. This is a payload "verified" under one tenant mutating another tenant's stack/PR state — squarely a cross-tenant authentication-bypass/forgery, Critical per the stated impact categories. It is fully repeatable against any existing `PullRequest` number for any repository with a matching `Stack`, and the same signature-selection flaw (`repository_owner` vs. `repository.full_name`/`.number`) equally affects every other handler in `Shipit::Webhooks.default_handlers` (push, closed, reopened, edited, labeled, etc.), widening the blast radius beyond just assignee metadata. [6](#0-5) 

### Likelihood Explanation
The only precondition is operational, not code-level: at least one organization entry in Shipit's `github` secrets config lacking a `webhook_secret`. This is a state the codebase itself documents/ships as an example (`config/secrets.development.shopify.yml`), and nothing in `GitHubApp`/`Shipit.github_app_config` warns or blocks operation when `webhook_secret` is blank — `verify_webhook_signature` treats blank secret as "always trust." The attacker needs no Shipit session, API token, or GitHub org membership — only knowledge of one configured org name with no secret and the ability to POST arbitrary JSON, which matches the defined unprivileged-attacker capability set. Cost is a single crafted HTTP request, fully repeatable and scriptable against arbitrary target repositories/PR numbers.

### Recommendation
Cross-validate the org used for signature verification against the resource being mutated: derive `repository_owner` and reject/ignore the event (respond 422) if it does not match the owner portion of `params.repository.full_name` (and any `organization.login` present). Additionally, treat a blank/missing `webhook_secret` for a configured org as a hard misconfiguration (fail closed, e.g., raise/log and reject at boot or per-request) rather than silently trusting all payloads for that org.

### Proof of Concept
Add to `test/controllers/webhooks_controller_test.rb` (or a new test) using multi-org secrets fixtures with an org lacking `webhook_secret`:

```ruby
test "assigned webhook signed by a secret-less org cannot mutate another org's PullRequest" do
  pull_request = shipit_pull_requests(:review_stack_review) # belongs to victim stack/repo
  pull_request.assignees.clear
  original_assignee_ids = pull_request.assignees.pluck(:id)

  payload = payload_parsed(:pull_request_assigned)
  payload["action"] = "assigned"
  payload["number"] = pull_request.number
  payload["pull_request"]["number"] = pull_request.number
  # Attacker-controlled divergence: verifying org != owning org of the mutated PullRequest
  payload["repository"]["owner"] = { "login" => "attacker-org-with-no-secret" } # configured, webhook_secret: nil
  payload["repository"]["full_name"] = pull_request.stack.repository.github_repo_name # victim org/repo
  payload["pull_request"]["assignees"] = [{ "login" => "arbitrary-forged-login" }]

  @request.headers['X-Github-Event'] = 'pull_request'
  @request.headers['X-Hub-Signature'] = 'sha1=deadbeef' # irrelevant, secret-less org always verifies true

  post :create, body: payload.to_json, as: :json

  assert_equal original_assignee_ids, pull_request.reload.assignees.pluck(:id),
    "Victim PullRequest assignees must not change from a payload verified by an unrelated, secret-less org"
end
```
Assert on both sides of the binding: `repository_owner` used in `verify_signature` (`"attacker-org-with-no-secret"`) versus `pull_request.stack.repository.github_repo_name`'s owner (the real, victim owner) — before the fix these diverge and the mutation still succeeds; after the fix the request must be rejected (422) and `pull_request.assignees` must remain unchanged.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
