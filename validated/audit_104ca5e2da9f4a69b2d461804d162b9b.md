### Title
Webhook status forgery across organizations bypasses signature scoping and enables unauthorized deploy gating - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
The reported bug class is: a security check is performed at a coarse granularity (all addresses in a shared map) while the code that actually acts operates without regard to that granularity, letting unrelated/unverified data slip through. The same class of flaw exists in Shipit's webhook pipeline: the HMAC signature is verified against the organization implied by `repository.owner.login` in the payload, but the event handler that mutates state (`StatusHandler`) never re-checks that binding — it looks up commits **globally by SHA**, with no scoping to the organization/repository whose secret was actually used to authenticate the request.

### Finding Description
`WebhooksController#verify_signature` derives the organization to authenticate against purely from attacker-controlled JSON, then looks up that organization's `GitHubApp` and webhook secret to check the signature: [1](#0-0) [2](#0-1) 

Crucially, `verify_webhook_signature` treats an organization with no configured `webhook_secret` as always valid, unconditionally: [3](#0-2) 

Once the request passes `verify_signature`, `WebhooksController#create` dispatches the full attacker-controlled `params` to the registered handler for the event, with no additional binding to the organization that was authenticated: [4](#0-3) 

`StatusHandler`, the handler for GitHub `status` events, then acts on the payload with **no repository scoping at all** — it resolves the target purely by commit SHA against the entire `commits` table and writes a GitHub-reported status onto whatever commit matches: [5](#0-4) 

This breaks the binding: *organization authenticated by signature verification* ≠ *repository/commit whose status is actually written*. `repository_owner` (used only to select which secret verifies the signature) is never propagated into, or checked against, the object the handler mutates.

### Impact Explanation
Shipit uses recorded commit statuses to gate deploys/merges — statuses (including "blocking statuses") determine whether a commit is eligible to ship. If an attacker can get any organization/repository tracked by Shipit into a state where its `webhook_secret` is unset (a supported, documented-as-optional configuration per the `.presence` check), the attacker can send an unauthenticated POST to `/webhooks` with `X-Github-Event: status`, set `repository.owner.login` to that unsecured organization (satisfying `verify_signature`, which returns `true` unconditionally for it), while setting `sha` to a real commit belonging to a completely different, secured stack, and `state: "success"` with a `context` matching a required blocking-status check. Because `StatusHandler` resolves commits with an unscoped `Commit.where(sha: params.sha)`, this forged status is attached to the victim commit regardless of which organization was "authenticated." This can clear a blocking-status gate and enable an unauthorized deploy of that commit — matching the "unauthorized deploy" impact class.

### Likelihood Explanation
The precondition (an org/repository without a webhook secret) is directly supported by the code's own optional-secret design (`@webhook_secret = @config[:webhook_secret].presence`) rather than misconfiguration outside the engine's control, and no session, API token, or GitHub credential is required to exploit it — only knowledge/discovery of which tracked organization has no secret set, which is externally probeable by observing 200 vs 422 responses to crafted requests.

### Recommendation
Bind the authenticated organization to the object the handler is permitted to mutate: after `verify_signature` succeeds, pass the verified `repository_owner`/organization into the handler and require `StatusHandler` (and other handlers) to scope lookups by repository (e.g., join through `Repository.from_github_repo_name` and its `owner`) rather than a bare global `Commit.where(sha:)`. Additionally, consider treating a missing `webhook_secret` as a configuration warning rather than an implicit "verification passed" for events whose payload references cross-organization data.

### Proof of Concept
1. Identify (or arrange, via the engine's own optional-secret support) an organization `unsecured-org` tracked by Shipit with no `webhook_secret` configured.
2. POST to `/webhooks` with header `X-Github-Event: status`, body:
```json
{
  "sha": "<victim-commit-sha-in-another-org's-stack>",
  "state": "success",
  "context": "<required-blocking-context>",
  "repository": { "owner": { "login": "unsecured-org" } }
}
```
3. `verify_signature` resolves `Shipit.github(organization: "unsecured-org")`; `verify_webhook_signature` returns `true` unconditionally since no secret is set.
4. `StatusHandler#process` runs `Commit.where(sha: params.sha)`, finds the victim commit (belonging to a different, secured organization/stack), and calls `create_status_from_github!`, recording a forged "success" status that can satisfy a blocking-status deploy gate.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
