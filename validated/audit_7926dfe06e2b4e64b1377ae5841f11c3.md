### Title
`deregisterOperator()` Does Not Enforce Threshold Invariant, Permanently Locking All Bridge Assets — (`contracts/service_chain/bridge/BridgeOperator.sol`)

---

### Summary

`BridgeOperator.deregisterOperator()` removes an operator from `operatorList` without verifying that the remaining operator count still satisfies `operatorThresholds`. When `operatorList.length` drops below the current threshold for either `VoteType.ValueTransfer` or `VoteType.Configuration`, the vote-count condition `voteCounts[voteKey] >= operatorThresholds[uint8(_voteType)]` can never be satisfied, permanently freezing all KLAY, ERC20, and ERC721 assets held by the bridge.

---

### Finding Description

`setOperatorThreshold()` correctly guards against an impossible threshold:

```solidity
require(operatorList.length >= _threshold, "bigger than num of operators");
``` [1](#0-0) 

But `deregisterOperator()` performs no symmetric check before shrinking `operatorList`:

```solidity
function deregisterOperator(address _operator) external onlyOwner {
    require(operators[_operator]);
    delete operators[_operator];
    for (uint i = 0; i < operatorList.length; i++) {
       if (operatorList[i] == _operator) {
           operatorList[i] = operatorList[operatorList.length-1];
           operatorList.length--;   // ← no threshold guard
           break;
       }
    }
    emit OperatorDeregistered(_operator);
}
``` [2](#0-1) 

After the removal, `_voteCommon()` increments `voteCounts[voteKey]` to at most `operatorList.length` (the new, smaller count), but the threshold has not changed:

```solidity
if (vote.voteCounts[_voteKey] >= operatorThresholds[uint8(_voteType)]) {
    return true;
}
return false;
``` [3](#0-2) 

When `operatorList.length < threshold`, this condition is permanently `false`. `_voteValueTransfer()` therefore always returns `false`, and every `handle*Transfer` function silently returns without executing the asset transfer:

```solidity
if (!_voteValueTransfer(_requestedNonce)) {
    return;   // ← silent no-op; assets never released
}
``` [4](#0-3) 

The same early-return pattern exists in `handleERC20Transfer` and `handleERC721Transfer`: [5](#0-4) 

---

### Impact Explanation

All KLAY, ERC20, and ERC721 tokens held by the bridge contract become permanently unrecoverable. There is no administrative escape hatch: `setOperatorThreshold()` cannot lower the threshold below 1 (`require(_threshold > 0)`), and it cannot raise the operator count without `registerOperator()` — but even after re-registering, any in-flight nonces whose `closedValueTransferVotes[nonce]` is still `false` remain stuck because the vote data is not reset. The bridge's `chargeWithoutEvent()` and `requestKLAYTransfer()` paths continue to accept deposits, silently growing the locked balance.

This matches the allowed impact gate: **unauthorized lock of KLAY and bridged assets** caused by a broken invariant in a system-contract (service-chain bridge) function reachable by a semi-trusted caller (bridge owner).

---

### Likelihood Explanation

The bridge owner is a semi-trusted role, not an external attacker. However, the scenario is operationally realistic:

- A bridge operator key is compromised; the owner deregisters it to stop the attacker.
- The bridge was configured with threshold = number of operators (a common "all must agree" setup).
- After deregistration, `operatorList.length < threshold`, and the bridge is permanently deadlocked.

No majority-validator collusion or external service compromise is required. A single `onlyOwner` transaction suffices.

---

### Recommendation

Add a post-removal threshold check inside `deregisterOperator()`:

```solidity
function deregisterOperator(address _operator) external onlyOwner {
    require(operators[_operator]);
    delete operators[_operator];
    for (uint i = 0; i < operatorList.length; i++) {
       if (operatorList[i] == _operator) {
           operatorList[i] = operatorList[operatorList.length-1];
           operatorList.length--;
           break;
       }
    }
    // Guard: remaining operators must still satisfy every threshold.
    for (uint8 vt = 0; vt < uint8(VoteType.Max); vt++) {
        require(
            operatorList.length >= operatorThresholds[vt],
            "deregisterOperator: would break threshold"
        );
    }
    emit OperatorDeregistered(_operator);
}
```

This mirrors the invariant already enforced by `setOperatorThreshold()` and prevents the state where `operatorList.length < threshold`.

---

### Proof of Concept

1. Deploy `Bridge` (non-mintBurn mode) and fund it with 10 KLAY.
2. Register `op1` as a second operator (`registerOperator(op1)`).
3. Set `ValueTransfer` threshold to 2 (`setOperatorThreshold(VoteType.ValueTransfer, 2)`).
4. Deregister `op1` (`deregisterOperator(op1)`). Now `operatorList.length == 1`, threshold == 2.
5. As the remaining operator (owner), call `handleKLAYTransfer(txHash, from, recipient, 10 ether, nonce=0, blockNum, "")`.
6. Observe: the transaction succeeds (no revert) but `recipient` receives 0 KLAY. The `HandleValueTransfer` event is never emitted. The 10 KLAY remains locked in the contract forever.
7. Confirm: `closedValueTransferVotes[0]` is `false` — the vote never closed. No operator can ever accumulate enough votes to reach threshold 2 with only 1 operator registered. [2](#0-1) [6](#0-5) [7](#0-6)
