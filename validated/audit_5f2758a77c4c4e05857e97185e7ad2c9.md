### Title
Missing BlockNum Validation in `queue.DeliverStakingInfos` Allows Malicious P2P Peer to Corrupt Staking Info DB at Arbitrary Epoch — (`datasync/downloader/queue.go`)

### Summary

During fast-sync, a malicious P2P peer can respond to a staking info request for header N with a `P2PStakingInfo` whose `BlockNum` field is set to a different epoch M. Because the `validate` function in `queue.DeliverStakingInfos` is explicitly a no-op (marked `TODO`), and because `commitFastSyncData` uses `result.StakingInfo.BlockNum` (the attacker-controlled field) as the DB write key rather than `result.Header.Number.Uint64()`, the forged staking info is persisted at epoch M, overwriting any legitimate entry there.

### Finding Description

**Step 1 — Entry point:** A malicious P2P peer sends a `StakingInfoMsg` response. `handleStakingInfoMsg` in `node/cn/handler.go` decodes it without any field-level validation and forwards it to the downloader: [1](#0-0) 

**Step 2 — Queue delivery with no-op validation:** `queue.DeliverStakingInfos` in `queue.go` defines a `validate` function that is explicitly a `TODO` and always returns `nil`. The `reconstruct` function blindly stores the attacker-supplied `P2PStakingInfo` (including its `BlockNum` field) into the `fetchResult` slot for the requested header: [2](#0-1) 

**Step 3 — Positional binding, not content binding:** The generic `deliver` function iterates over `request.Headers` and calls `reconstruct(accepted, res)` where `res` is the result cache slot for `header.Number`. The staking info at position `index` in the response list is placed into the slot for the header at position `index` in the request — but the `BlockNum` field inside the `P2PStakingInfo` is never checked against `header.Number`: [3](#0-2) 

**Step 4 — DB write uses attacker-controlled `BlockNum`:** In `commitFastSyncData`, the key passed to `PutStakingInfoToDB` is `result.StakingInfo.BlockNum` — the field the attacker controls — not `result.Header.Number.Uint64()`: [4](#0-3) 

The same pattern exists in `commitPivotBlock`: [5](#0-4) 

**Contrast with the recovery path:** `SyncStakingInfo` does validate `BlockNum` against the expected block before writing, but this guard is absent from the fast-sync path: [6](#0-5) 

**DB schema:** `WriteStakingInfo` uses `BlockNum` directly as the DB key, so writing at the wrong key permanently corrupts the entry for that epoch: [7](#0-6) 

### Impact Explanation

The staking info DB is the authoritative source for reward distribution before the Kaia hardfork. `GetStakingInfo` reads from this DB and uses `CouncilRewardAddrs` to determine which addresses receive block rewards: [8](#0-7) 

An attacker who corrupts epoch M's staking info with forged `CouncilRewardAddrs` causes all block rewards for every block in epoch M to be distributed to attacker-controlled addresses. This is an unauthorized redirect of KAIA block rewards — a direct financial impact on validators.

### Likelihood Explanation

- The attacker only needs to be a connected P2P peer while the victim node is fast-syncing (a common bootstrap scenario).
- No privileged access, governance keys, or validator collusion is required.
- The `TODO` comment in the validate function confirms this was a known gap left unimplemented. [9](#0-8) 

### Recommendation

In `queue.DeliverStakingInfos`, replace the no-op `validate` function with a check that `stakingInfoList[index].BlockNum == header.Number.Uint64()`. Additionally, in `commitFastSyncData` and `commitPivotBlock`, use `result.Header.Number.Uint64()` as the DB key rather than `result.StakingInfo.BlockNum`.

### Proof of Concept

1. Victim node starts fast-sync. The queue schedules staking info fetches for headers at blocks `86400` and `172800` (staking interval boundaries).
2. Attacker peer receives a `GetStakingInfo` request containing the hash of header `172800`.
3. Attacker responds with a `P2PStakingInfo{BlockNum: 86400, CouncilRewardAddrs: [attacker_addr, ...]}`.
4. `queue.DeliverStakingInfos` accepts it (validate is a no-op), places it in the `fetchResult` for header `172800`.
5. `commitFastSyncData` calls `PutStakingInfoToDB(86400, forgedInfo)`.
6. `WriteStakingInfo(db, 86400, forgedInfo)` overwrites the legitimate epoch-86400 entry.
7. All subsequent blocks in epoch 86400 distribute rewards to `attacker_addr`.
