### Title
Cross-organization webhook forgery via mismatched signature-selection identity and payload-consumed identity - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
In a multi-GitHub-org Shipit deployment, `WebhooksController#verify_signature` selects which `webhook_secret` to verify a request against using `repository_owner`, a value read directly out of the *unverified* JSON body [1](#0-0) . Once the HMAC check passes, every downstream `Shipit::Webhooks::Handlers::Handler` subclass resolves the target `Repository`/`Stack` using a *different* field of the same payload, `payload.dig('repository', 'full_name')` [2](#0-1) . Because the signature is computed by the attacker themselves (they legitimately possess one organization's `webhook_secret`), nothing binds the "organization whose secret authenticated the request" to the "repository/stack the payload is applied to." An operator of Org A's GitHub App can therefore forge an authentic-looking webhook that is verified against Org A's secret while its `repository.full_name`/`sha`/`team` fields target Org B's stacks, commits, or teams in the same Shipit instance.

### Finding Description
`verify_signature` does:
```ruby
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
``` [3](#0-2) 
`repository_owner` is taken from `params.dig('repository', 'owner', 'login')` (or `organization.login`), i.e. attacker-controlled JSON, evaluated *before* the signature is checked [1](#0-0) . `Shipit.github(organization:)` looks up the per-organization config/secret from `secrets.github` keyed by that string [4](#0-3) , a configuration shape explicitly supported for multiple orgs (`config/secrets.development.shopify.yml` shows `somegithuborg`/`someothergithuborg` each with its own `webhook_secret`).

`verify_webhook_signature` itself only checks `HMAC(secret, raw_post) == signature`; it does not check that the payload's `repository`/`organization` fields are internally consistent with the org whose secret was selected [5](#0-4) .

The signature only proves the sender possesses *some* configured org's secret and that they signed *this exact byte string* — it does not restrict which org/repo/team fields may appear inside that byte string. Once verification passes, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` runs unconditionally on the full parsed body [6](#0-5) , and every handler picks its target purely from `repository.full_name` (push, pull_request family) [7](#0-6) , from `sha` alone with no repository scoping at all (`status`) [8](#0-7) , or from `organization.login`/`team` (membership, which mutates `Shipit.github_teams`-linked `Team`/`Membership` records) [9](#0-8) .

The binding that is broken is:
`organization authenticated by verify_signature (repository.owner.login) == repository acted on by the handler (repository.full_name / sha / organization.login in MembershipHandler)`

Before the attacker's request: for legitimate GitHub-originated traffic these two identities always agree, because GitHub signs the payload with the secret of the org that actually owns the repository in the payload.
After the attacker's request: the attacker, holding Org A's secret, crafts a payload whose `repository.owner.login = "OrgA"` (so `Shipit.github(organization: "OrgA")` resolves the secret they know) but whose `repository.full_name = "OrgB/target-repo"`, `sha = "<OrgB commit>"`, or `organization.login = "OrgB"`/`team` (for membership events). They compute a valid HMAC-SHA1 over this exact body using Org A's secret and submit it with `X-Hub-Signature`. `verify_signature` passes because the HMAC matches Org A's secret over the exact bytes sent. The handler then acts on Org B data.

### Impact Explanation
This crosses the "organization that authenticated versus the repository that is written" boundary called out explicitly in scope. Concretely, with only a legitimately-obtained secret for one configured org, an attacker can, against any other org configured in the same instance:
- Forge `status` events to mark arbitrary commits as `success`/`failure` on any `Commit` row matching a `sha` they choose, independent of which repo it belongs to, since `StatusHandler` does no repository check at all — this can flip `deployable_status`/`commit_status` used to gate deploys [8](#0-7) .
- Trigger `GithubSyncJob`/`sync_github` on push events for stacks under other organizations by choosing a `full_name` that resolves to those repositories [10](#0-9) .
- Create/modify `Team`/`Membership` records tied to another organization via forged `membership` events, escalating into `Shipit.github_teams`-based authorization used to gate stack access [9](#0-8) , and archive/unarchive review stacks or update pull-request state cross-org via the `pull_request/*` handlers which likewise trust `payload['repository']['full_name']` in isolation from the authenticating identity.

This matches the High-impact category: "escalation into `Shipit.github_teams` authorization" and "unauthenticated read/unauthorized deploy-adjacent state change," and can chain into unauthorized deploys by faking green CI status.

### Likelihood Explanation
Requires the Shipit instance to be configured with more than one GitHub organization (a documented, first-class configuration mode, see `github_app_config`/`github_organizations` in `lib/shipit.rb`), and requires the attacker to know one org's `webhook_secret` — realistic for someone with admin access to their own org's GitHub App settings, which is not privileged access to the Shipit application, the target org, or a `GITHUB_TOKEN`. No Shipit session, API token, or GitHub write access to the victim org is needed; only knowledge of a secret for a *different*, unprivileged org sharing the same Shipit instance.

### Recommendation
Bind the authenticating identity to the acted-upon identity before dispatch:
- In `WebhooksController#verify_signature` / `#create`, after resolving `github_app` for `repository_owner`, verify that the payload's `repository.full_name` (and, for membership events, `organization.login`) actually belongs to the organization whose secret matched — e.g. compare the owner segment of `full_name` against `repository_owner`, or resolve the target `Repository`/organization first and require that its configured GitHub App is the one that produced a valid signature.
- Alternatively, do not select the verification secret from unauthenticated payload content at all; instead verify against every configured org's secret and require that the org that verifies is the same org that owns the target repository being mutated.

### Proof of Concept
Given a multi-org config:
```yaml
github:
  orga:
    webhook_secret: "orga-secret"
  orgb:
    webhook_secret: "orgb-secret"
```
Attacker (knows only `orga-secret`) sends:
```json
POST /webhooks
X-Github-Event: status
X-Hub-Signature: sha1=<HMAC-SHA1("orga-secret", body)>

{
  "sha": "<sha of a commit belonging to OrgB's tracked repo>",
  "state": "success",
  "context": "ci/tests",
  "repository": { "owner": { "login": "orga" }, "full_name": "orgb/target-repo" }
}
```
`verify_signature` resolves `Shipit.github(organization: "orga")`, computes `HMAC-SHA1("orga-secret", body)`, which the attacker already produced correctly, so verification passes [3](#0-2) . `StatusHandler#process` then finds `Commit.where(sha: params.sha)` — matching OrgB's commit — and calls `create_status_from_github!`, forging a `success` status on an OrgB commit despite the attacker never holding OrgB's `webhook_secret` [8](#0-7) .

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
