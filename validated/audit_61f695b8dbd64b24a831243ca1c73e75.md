### Title
Decompression Bomb via Unbounded ZIP Extraction in Private Textcoin/Payment File Handling - (File: wallet.js)

### Summary
`handlePrivatePaymentFile()` in `wallet.js` decompresses an attacker-controlled ZIP archive (a "textcoin"/private-payment file received from a payment counterparty) using JSZip. The only protection against a decompression bomb is a size check performed on an **internal, undocumented JSZip property** (`entry._data.uncompressedSize`), and that check is only executed `if (entry._data)` is truthy. If that internal property is absent/falsy for a given entry (which is not guaranteed by JSZip's public API and can vary based on how the archive is constructed), the size guard is silently skipped and the code proceeds straight to `entry.async("string")`, which performs the actual DEFLATE inflate with no upper bound on the resulting decompressed size — the same root-cause pattern as the OpenBao advisory (unbounded copy of decompressed data, with the integrity/size check only reliably happening after or dependent on data that the attacker controls). [1](#0-0) 

### Finding Description
`handlePrivatePaymentFile(fullPath, content, cb)` receives a ZIP file — either read from local storage/QR scan (`fullPath`) or passed directly as `content` — that is created by whoever sent the textcoin/private payment (a private-payment counterparty), i.e., untrusted, attacker-controlled input: [2](#0-1) 

The code loads the ZIP via `zip.loadAsync(data)`, retrieves the `private_textcoin` entry, and attempts to bound the decompressed size:
```
if (entry._data && entry._data.uncompressedSize > 100 * 1024 * 1024)
    return cb("private_textcoin entry is too large");
entry.async("string").then(function(data) { ... })
``` [3](#0-2) 

This check relies on `entry._data`, an internal JSZip implementation detail that is not part of JSZip's documented public API and is not guaranteed to be populated for every entry/compression method. When `entry._data` is falsy, the `if` condition short-circuits and the size check is **never performed at all** — the code falls straight through to `entry.async("string")`, which streams the DEFLATE-compressed bytes through zlib inflate with no byte-count cap, analogous to OpenBao's unbounded `io.Copy` of decompressed tar data. An attacker who crafts the ZIP so that this internal metadata field is absent (or otherwise not what the code expects) can embed a `private_textcoin` entry that decompresses to an arbitrarily large size, causing the recipient's process to exhaust memory while calling `entry.async("string")` and building the resulting string/JSON. [4](#0-3) 

Even when `entry._data.uncompressedSize` is present and enforced, this is still a self-reported size taken from the local file header of the attacker-supplied archive; the real protection is that JSZip won't lie about output length for standard DEFLATE, but the code explicitly gates the check behind an internal property whose presence is implementation-dependent, making the safeguard unreliable rather than a hard limit enforced independent of attacker input.

This function is reachable by any private-payment counterparty: sending someone a textcoin or private-payment file/mnemonic that the victim's wallet opens via `handlePrivatePaymentFile` (called by `receiveTextCoin`/QR-scan/file-share flows) triggers this code path without any prior trust relationship. [5](#0-4) 

### Impact Explanation
A malicious private-payment counterparty can cause the victim wallet process to attempt decompressing an unbounded/very large payload into memory (via `entry.async("string")`), leading to memory exhaustion and process crash/hang — a denial of service against the wallet that is receiving or claiming the textcoin/private payment. This does not by itself enable double-spend or fund theft, but it fits the "AA fund loss or freezing / network unable to confirm new units" class loosely only insofar as it denies the victim wallet's ability to process transactions while under attack; more precisely it is a resource-exhaustion DoS triggered by attacker-supplied compressed data, matching the OpenBao bug class (decompression bomb via unbounded copy/inflate with the size check being unreliable/bypassable).

### Likelihood Explanation
Likelihood is moderate: it requires the attacker to control the ZIP structure sent to the victim (which they fully do, since they generate the textcoin/private-payment file) and to construct an entry where JSZip's internal `_data.uncompressedSize` is not populated as expected by this check. Because `_data` is an internal, non-public field, its presence/shape can vary across JSZip versions or non-standard/malformed-but-still-parseable ZIP structures, making a bypass plausible but requiring some JSZip-internals-specific crafting to confirm reliably.

### Recommendation
- Do not rely on JSZip's internal `_data.uncompressedSize` property for security-relevant size enforcement. Use documented, deterministic size tracking instead.
- Enforce the maximum decompressed size independent of any per-entry metadata reported by the archive itself, e.g., by streaming the entry through `entry.internalStream("string")` (or equivalent) and counting bytes as they are produced, aborting once the 100 MB threshold (or a tighter limit) is exceeded — instead of calling `entry.async(...)` unconditionally when the guard is skipped.
- Fail closed: if the size cannot be determined ahead of decompression, still cap the decompression using a streaming/byte-counting approach rather than skipping the check entirely.
- Additionally bound the ZIP archive's own file size before parsing, as an extra layer of defense.

### Proof of Concept
1. Attacker crafts a ZIP archive containing an entry named `private_textcoin` using a compression scheme/JSZip artifact-construction technique that leaves `entry._data` falsy/undefined after `zip.loadAsync(data)` (e.g., by directly serializing a ZIP with a custom local-file-header/compression method not fully populating JSZip's internal metadata, or a specially structured entry that JSZip parses lazily).
2. Inside that entry, attacker places a compressed payload that inflates to several GB (a classic zip-bomb ratio, e.g., overlapping/duplicated compressed blocks).
3. Attacker sends this file to the victim as a textcoin/private-payment (via mnemonic link/file share), reaching `handlePrivatePaymentFile`.
4. `entry._data` is falsy ⇒ the `if (entry._data && entry._data.uncompressedSize > 100 * 1024 * 1024)` check is skipped.
5. `entry.async("string")` is called and decompresses the entire bomb into memory with no limit, exhausting the victim wallet's memory/CPU and causing a crash or unresponsiveness (DoS). [1](#0-0)
