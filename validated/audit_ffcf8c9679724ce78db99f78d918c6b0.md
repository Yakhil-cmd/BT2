### Title
Cross-tenant Membership write via unvalidated `member.login`/`team.id` trust in `MembershipHandler` - (File: app/models/shipit/webhooks/handlers/membership_handler.rb)

### Summary
`MembershipHandler#process` resolves `params.member.login` through `User.find_or_create_by_login!` and `params.team.id` through `Team.find_or_create_by!(github_id:)`, then calls `team.add_member(member)` / `team.members.delete(member)` purely on the strength of these payload fields. Neither the `User` row nor the `Team` row lookup is scoped to the organization that authenticated the webhook, so any org allowed to emit a signed `membership` event can attach (or detach) an arbitrary, pre-existing, globally-shared `Shipit::User` to/from any `Team`, including one that legitimately belongs to a different organization/tenant.

### Finding Description
The broken binding: `User row mutated by User.find_or_create_by_login!(params.member.login)` should equal `the GitHub identity that params.organization.login (the org verified by verify_signature) has actual authority to attest team membership for` — but this equality is never checked anywhere in the code path.

Trace:
- `WebhooksController#verify_signature` (app/controllers/shipit/webhooks_controller.rb:24-49) only checks that the request HMAC matches the `webhook_secret` configured for `repository_owner` (here, `params.dig('organization','login')` since a membership payload has no `repository` key, per `repository_owner` at line 59-61). It proves the request was signed by *some* configured org's secret; it says nothing about the truthfulness of the JSON body's content.
- `MembershipHandler#process` (app/models/shipit/webhooks/handlers/membership_handler.rb:22-34) then:
  - `team = find_or_create_team!` → `Team.find_or_create_by!(github_id: params.team.id)` (lines 38-42). This filters **only on `github_id`**, not on `organization`. The `teams` table's only unique index is `(organization, slug)` [1](#0-0) ; `github_id` is not unique, so if the attacker names a `team.id` that already matches a `Team` row created for a different organization, `find_or_create_by!` returns that pre-existing, foreign team.
  - `member = User.find_or_create_by_login!(params.member.login)` (app/models/shipit/user.rb:22-28) matches purely by `login`, a global, cross-tenant identifier with no unique constraint enforced beyond app logic [2](#0-1) . If a `User` with that login already exists (e.g., from a legitimate prior OAuth login via `GithubAuthenticationController#sign_in_github`), it is reused unmodified.
  - `team.add_member(member)` (app/models/shipit/team.rb:41-43) or `team.members.delete(member)` then writes/removes a `Membership` row linking that pre-existing user to that (possibly foreign) team, with no re-verification against GitHub that the named login is actually a member of the emitting organization's team.

Given the question's stated precondition — the attacker can get a correctly-signed `membership` webhook accepted, either through a signature-verification gap or through an org they legitimately administer within Shipit's multi-org config (`Shipit.github_app_config`, `TOP_LEVEL_GH_KEYS`, lib/shipit.rb:170-200) — the handler itself performs no additional authorization check binding the payload's `member.login`/`team.id` to that org's actual authority. `verify_signature`, `drop_unhandled_event`, and the `ExplicitParameters` schema in `MembershipHandler.params` (lines 7-21) only validate shape/type of the fields, not their truthfulness relative to the emitting org.

### Impact Explanation
An org/attacker who can get one signed `membership` webhook accepted can:
- Attach any existing Shipit `User` (identified only by GitHub login, e.g., an operator who previously logged in) to a `Team` under the attacker's control, or
- If the attacker guesses/knows a `github_id` already used by a `Team` belonging to a different organization, mutate that foreign organization's `Team`'s `Membership` list directly (add or, via `action: 'removed'`, strip an existing member) — a payload from one org mutating another org's team state, matching the explicitly listed Critical category ("a payload for one repository mutating another's ... team"). Because `User#authorized?` (app/models/shipit/user.rb:80-82) is computed from `teams.where(id: Shipit.github_teams...)`, mutating team membership can affect (grant or, via `removed`, revoke) that user's authorization outcome depending on which team/github_id is targeted. The action is repeatable against any login/team-id combination the attacker chooses, with each webhook POST an independent write.

### Likelihood Explanation
Requires the attacker to have some accepted channel for a signed `membership` webhook (either a signature-verification gap, as referenced in the prompt, or genuine administration of an org onboarded into Shipit's multi-org `secrets.github` config). Given that channel, no further secrets or privileges are needed: `team.id`, `member.login`, and `organization.login` are all attacker-supplied JSON fields with no cross-check against GitHub's real state, and `Team` lookup by `github_id` is not organization-scoped in the schema or in `find_or_create_team!`.

### Recommendation
- Scope `Team.find_or_create_by!` by both `github_id` **and** `organization` (matching the payload's authenticated `organization.login`), and add/enforce a DB uniqueness constraint reflecting that scope.
- Before calling `team.add_member`/`team.members.delete`, verify (e.g., via a live GitHub API call using the emitting org's installation credentials) that `params.member.login` is actually a member of `params.organization.login`, or at minimum verify that `params.team.id`'s reported organization matches `params.organization.login`.
- Consider not trusting `member.login` blindly for pre-existing global `User` rows without confirming the requesting org's install actually has visibility/authority over that GitHub identity.

### Proof of Concept
```ruby
# test/models/webhooks/handlers/membership_handler_test.rb
require 'test_helper'

module Shipit
  module Webhooks
    module Handlers
      class MembershipHandlerCrossTenantTest < ActiveSupport::TestCase
        test "membership webhook from unrelated org attaches an existing user to an attacker-controlled team" do
          victim = shipit_users(:walrus) # pre-existing user, login: 'walrus', simulating prior legit login
          attacker_team_payload = {
            'action' => 'added',
            'team' => { 'id' => 999_888, 'name' => 'Attacker Team', 'slug' => 'attacker-team', 'url' => 'https://example.com' },
            'organization' => { 'login' => 'attacker-org' }, # unrelated org, no authority over 'walrus'
            'member' => { 'login' => victim.login }
          }

          assert_difference -> { Membership.count }, 1 do
            MembershipHandler.call(attacker_team_payload)
          end

          team = Team.find_by(github_id: 999_888)
          assert team.members.include?(victim),
                 "Expected 'attacker-org' payload to be unable to bind victim's account " \
                 "to a team it has no authority over, but Membership was created"
        end
      end
    end
  end
end
```
This demonstrates that `find_or_create_by_login!` matches the pre-existing `User` row purely by login, and `team.add_member` creates a `Membership` linking it to a team declared by an org that has no verified relationship with that user — the equality `User row mutated` == `identity the emitting org has authority over` fails both before and after the call.
