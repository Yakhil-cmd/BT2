Confirmed root cause. `internal/skills/discovery/discovery.go`'s `FetchBlob` function requests a git blob by SHA via `GET /repos/{owner}/{repo}/git/blobs/{sha}` and decodes the base64 `content` field, but never recomputes the git blob hash (`sha1("blob " + len + "\0" + content)`) and compares it against the requested `sha` or the `resp.SHA` returned in the JSON body.### Title
Skills installer trusts blob content by SHA without verifying the response's `sha` matches the requested blob hash - ([File: internal/skills/discovery/discovery.go])

### Summary
`gh skills install`/`update`/`preview` resolve a skill's files by walking a git tree (`walkTree`) to collect `{path, sha}` pairs, then fetch each file's content individually via `FetchBlob(client, host, owner, repo, sha)`, which calls `GET /repos/{owner}/{repo}/git/blobs/{sha}`. The handler decodes `resp.Content` and returns it, but never checks that `resp.SHA` equals the requested `sha`, nor recomputes the git blob hash (`sha1("blob "+len+"\0"+content)`) to confirm the returned bytes actually correspond to the identifier that was requested. This is the same missing-verification pattern flagged in the Monero report: content is fetched by an identifying hash and consumed without confirming the hash-to-content binding, trusting solely on the serving host's word.

### Finding Description [1](#0-0) 

`FetchBlob` issues `client.REST(host, "GET", .../git/blobs/{sha}, nil, &resp)` where `resp` contains `SHA`, `Content`, `Encoding`. It validates only that `Encoding == "base64"` and then base64-decodes and returns the content — there is no comparison of `resp.SHA` (or a locally recomputed digest) to the `sha` parameter that was passed in.

This function is the sole content-fetching primitive used by:
- `installer.installSkill` [2](#0-1)  which calls `discovery.DiscoverSkillFiles` to enumerate `{path, sha}` and then `discovery.FetchBlob(opts.Client, opts.Host, opts.Owner, opts.Repo, file.SHA)` for each, writing the *unverified* bytes verbatim to disk via `os.WriteFile(destPath, []byte(content), 0o644)`.
- `pkg/cmd/skills/preview/preview.go` and `pkg/cmd/skills/search/search.go`, which call `FetchBlob` to render file/description content in the terminal.
- `pkg/cmd/skills/update/update.go`, which drives `installer.Install` for in-place skill updates that get atomically swapped into the live skill directory (`updateSkillInPlace` → `swapDirectoryContents`).

The root cause mirrors the Monero pattern exactly: an identifier obtained from one trusted step (the tree listing) is used to request content from a second call, and the response is consumed without confirming that the returned payload is actually bound to that identifier. If the API host that `gh` talks to for a given skill install (a configurable `--host`, e.g. a GitHub Enterprise Server instance or any host the tool is pointed at) returns a blob body whose `sha`/content pair doesn't match what was asked for, `FetchBlob` has no way to detect it, and callers proceed as if the content is authentic to the requested SHA.

### Impact Explanation
Because `installSkill` writes `FetchBlob`'s output verbatim to disk and injects it into `SKILL.md` files that are subsequently loaded/executed by AI-agent skill runners, a host that lies about the blob content bound to a requested SHA can smuggle attacker-controlled instructions/scripts into an installed skill while the discovery/tree-walk metadata (paths, tree SHA, "resolved to" messaging shown to the user) appears consistent and legitimate. `gh skills update` uses the same path to write into an already-trusted, live skill directory via an atomic swap, so a compromised or malicious host can silently replace previously-installed skill content during a routine update, without any cryptographic step ever comparing the fetched bytes against the tree-declared SHA.

### Likelihood Explanation
Exploitation requires the `gh skills install/update/preview` commands to be pointed at a host that does not honestly enforce content-addressing for git blob objects (i.e., a malicious or compromised endpoint reachable via `--host`, custom GHES enterprise config, or any endpoint substitutable for `api.Client`'s target host) — this is the same "attacker-controlled host during a normal gh command" trust boundary called out as valid in the Monero analog, not a MITM of an otherwise-honest github.com endpoint. No user interaction beyond running a normal `gh skills install`/`update` command against that host is required, and the flaw is present on every call path that uses `FetchBlob`.

### Recommendation
In `FetchBlob` (`internal/skills/discovery/discovery.go`), after decoding the base64 content:
1. Verify `resp.SHA == sha` (the requested identifier) and reject mismatches.
2. Additionally recompute the canonical git blob SHA-1 (`sha1("blob " + len(content) + "\0" + content)`) over the decoded bytes and compare it to the requested `sha`, matching the defense-in-depth pattern used by `check_tx_proof`'s `tx_hash != txid` guard in the Monero report. Fail the fetch (returning an error) on any mismatch rather than silently proceeding.

### Proof of Concept
Not independently executed (no live/attacker-controlled GHES host was available to test against); this assessment is based on static code review. A PoC harness would:
1. Stand up a mock HTTP server implementing the `git/trees` and `git/blobs` REST endpoints used by `internal/skills/discovery`.
2. Configure `gh skills install <owner>/<repo> --host <mock-host>` (or the internal `api.Client` pointed at that host in a unit test, analogous to the existing `httpmock.Registry`-based tests such as `TestFetchBlob` in `internal/skills/discovery/discovery_test.go`).
3. Have the tree endpoint return a legitimate-looking `{path: "SKILL.md", sha: "abc123"}` entry, but have the blob endpoint for `git/blobs/abc123` return `{"sha": "abc123", "encoding": "base64", "content": base64("malicious content")}` where the base64 content does not actually hash (via git blob SHA-1) to `abc123`.
4. Observe that `FetchBlob`/`installSkill` accepts and writes the mismatched content to disk without error, confirming the missing verification, exactly as `installer_test.go`'s `TestInstallSkill` stubs currently do not assert any SHA-content binding check. [3](#0-2)

// FetchBlob retrieves the content of a blob by SHA. The blob is base64-encoded
// inside the JSON response and decoded here, so it is returned as
// iostreams.Untrusted and callers must choose sanitized display or raw
// round-tripping.
func FetchBlob(client *api.Client, host, owner, repo, sha string) (iostreams.Untrusted, error) {
	apiPath, err := safeurl.JoinPath("repos", owner, repo, "git", "blobs", sha)
	if err != nil {
		return iostreams.Untrusted{}, err
	}
	var resp struct {
		SHA      string `json:"sha"`
		Content  string `json:"content"`
		Encoding string `json:"encoding"`
	}
	if err := client.REST(host, "GET", apiPath.String(), nil, &resp); err != nil {
		return iostreams.Untrusted{}, fmt.Errorf("could not fetch blob: %w", err)
	}

	if resp.Encoding != "base64" {
		return iostreams.Untrusted{}, fmt.Errorf("unexpected blob encoding: %s", resp.Encoding)
	}

	// GitHub API returns base64 with embedded newlines; use the StdEncoding
	// decoder via a reader to handle them transparently.
	decoded, err := io.ReadAll(base64.NewDecoder(base64.StdEncoding, strings.NewReader(resp.Content)))
	if err != nil {
		return iostreams.Untrusted{}, fmt.Errorf("could not decode blob content: %w", err)
	}

	return iostreams.NewUntrustedBytes(decoded), nil
}
