### Title
Webhook payload's unverified `repository.full_name` lets an attacker route a validly-signed (or unsigned) event from one configured GitHub organization into another organization's stack - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the `GitHubApp`/webhook secret to check against using `repository_owner`, which is read from `params.dig('repository','owner','login')`, but the payload actually processed by the event handlers (e.g. `PushHandler`, `PullRequest::*Handler`) looks up the target `Repository`/`Stack` using a *different* field, `payload.dig('repository','full_name')`, without ever checking that this matches the organization that was authenticated. This is the same class of bug as the reported `_updateRates` issue: one field/index is used to authorize, a different field/index from the same untrusted structure is used to act.

### Finding Description
`verify_signature` computes the org used for HMAC verification like this: [1](#0-0) [2](#0-1) 

The `github_app` returned by `Shipit.github(organization: repository_owner)` supplies the `webhook_secret` used to verify `X-Hub-Signature`: [3](#0-2) 

Critically, `verify_webhook_signature` returns `true` unconditionally when no `webhook_secret` is configured for that organization (`return true unless webhook_secret`). Shipit explicitly supports multi-organization configurations where each org has its own independent `webhook_secret` (some potentially left blank, as shown in the test fixture where both `OrgOne` and `OrgTwo` have `webhook_secret: # nil`): [4](#0-3) 

Once `verify_signature` passes (either because the correct secret was used, or trivially because the org keyed by `repository.owner.login` has no secret configured), the controller feeds the *entire, unfiltered* payload to every registered handler for the event: [5](#0-4) 

The handlers, however, never look at `repository.owner.login` (the field that was authenticated). They resolve the target repository/stack purely from `repository.full_name`: [6](#0-5) [7](#0-6) [8](#0-7) 

**The broken binding, as an equality:**
`organization used to select/verify the webhook signature (params['repository']['owner']['login'])` MUST equal `organization implied by the repository actually mutated (params['repository']['full_name'].split('/').first)` — but nothing in the code enforces this. An attacker who can produce a payload that is accepted for *organization A* (either because A's `webhook_secret` is blank/unset, or because the attacker otherwise obtains A's secret through a channel unrelated to org B) can set `repository.full_name` to `"OrgB/some-tracked-repo"` and have the handler act on Org B's stack, even though only Org A's (weaker or absent) authentication was actually checked.

### Impact Explanation
This crosses an authentication boundary between two independently-configured GitHub organizations sharing one Shipit installation, one of the deployment-trust bindings explicitly called out in scope ("an organization that authenticated versus the repository that is written"). Concretely, with a zero/weak-secret organization present in the deployment, an unprivileged attacker can:
- Forge `push` events causing `GithubSyncJob` to run against another organization's tracked stack (`PushHandler#process` → `stack.sync_github`).
- Forge `pull_request` `opened`/`reopened`/`labeled` events to create or unarchive a `ReviewStack` for another organization's repository, which triggers automatic provisioning (checkout + deploy commands) of attacker-controlled branch/PR content — an unauthorized deploy on the deploy host.
- Forge `status`/`check_suite` events to poison commit statuses or trigger `RefreshCheckRunsJob` for a repository they don't control.

This matches the in-scope "High"/"Critical" impact classes: unauthorized deploy, and unauthenticated write into another organization's stack/task state.

### Likelihood Explanation
Exploitability is conditioned on the deployment having at least one configured GitHub organization with a blank/unset `webhook_secret` (a state the codebase itself supports and whose test fixtures demonstrate as a valid configuration), which then acts as a skeleton key for the `repository_owner`-selection logic. Given that condition, no session, `ApiClient` token, GitHub App private key, or repository write access is needed — only knowledge of the target Shipit instance's public webhook endpoint and of an existing tracked repository's `full_name`. I was not able to fully confirm from the index whether every real-world deployment always configures a non-blank `webhook_secret` for all organizations (this is operator-configuration dependent, not enforced in code), so likelihood is contingent on that operational detail rather than proven universally exploitable.

### Recommendation
After parsing and before dispatching to handlers, verify that `params.dig('repository','owner','login')` (or `params.dig('organization','login')`) matches the organization implied by `params.dig('repository','full_name')`, and reject the event if they diverge. Additionally, consider making `webhook_secret` mandatory per configured organization (raise at boot/config-validation time rather than silently trusting unsigned payloads via `return true unless webhook_secret`).

### Proof of Concept
1. Configure Shipit with two organizations per `docs/setup.md`'s "Using Multiple Github Applications" section: `OrgWeak` (no `webhook_secret` set) and `OrgVictim` (has a tracked repository/stack and a real `webhook_secret`).
2. Send a POST to `/webhooks` with header `X-Github-Event: pull_request`, no valid `X-Hub-Signature` (or any garbage signature — irrelevant since `OrgWeak` skips verification), and a JSON body where:
   - `repository.owner.login = "OrgWeak"` (drives `WebhooksController#repository_owner`, so `verify_webhook_signature` short-circuits to `true`)
   - `repository.full_name = "OrgVictim/tracked-repo"`, `action = "opened"`, plus a crafted `pull_request` object pointing at an attacker-controlled branch/head SHA.
3. `PullRequest::OpenedHandler` resolves the repository via `Shipit::Repository.from_github_repo_name("OrgVictim/tracked-repo")` and creates/unarchives a `ReviewStack`, queuing provisioning of the attacker's branch — without `OrgVictim`'s webhook secret ever having been checked.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
