### Title
Unbounded synchronous scan of all unstable units in `in_data_feed`/AA data-feed lookups enables an AA-trigger-driven hang - ([File: data_feeds.js])

### Summary
`dataFeeds.dataFeedExists()` (used by the oscript `in_data_feed` operator, and by the `has`/`sum`/`in data feed` opcodes in address definitions) iterates `storage.assocUnstableMessages` with a synchronous `for...in` loop whenever it is invoked from AA formula evaluation (`bAA=true`). Because this operator can be embedded in an AA's oscript that runs for every trigger unit an unprivileged sender posts, and the formula evaluator only bounds "complexity"/"count_ops" (an abstract op counter), not the actual cost of each op, a single triggering unit can force the node to repeatedly scan the full in-memory set of currently-unstable DAG units synchronously on the Node.js main thread.

### Finding Description
`data_feeds.js` `dataFeedExists()`:
```
for (var unit in storage.assocUnstableMessages) {
    var objUnit = storage.assocUnstableUnits[unit] || storage.assocStableUnits[unit];
    ...
    storage.assocUnstableMessages[unit].forEach(function (message) { ... });
}
``` [1](#0-0) 

This function is reached from the oscript `in_data_feed` operator in `formula/evaluation.js`, which is directly reachable by any AA trigger sender because AA formulas execute this operator during the response to an incoming trigger unit (an unprivileged, attacker-controlled event):
```
case 'in_data_feed':
    ...
    dataFeeds.dataFeedExists(arrAddresses, feed_name, relation, value, min_mci, mci, bAA, cb);
``` [2](#0-1) 

The oscript validator (`formula/validation.js`) enforces `count_ops`/`complexity` limits (`MAX_OPS`, `MAX_COMPLEXITY`) on the *number* of oscript operations in a formula, but it has no accounting for the *real* cost of a single `in_data_feed`/`data_feed` evaluation, which is proportional to the size of `storage.assocUnstableMessages` (i.e., to the number of not-yet-stable units currently tracked in memory by the node). Every other place in the interpreter that does variable-cost work (array/dictionary literals, string cloning, remote-AA calls, etc.) has an explicit size or complexity charge tied to the cost (`isTooBigObj`, `arrPairs.length > 5`, `count_ops += (max_remote_complexity+1)*...`, etc.) — see e.g. `formula/validation.js` `search_param_list` bound (`arrPairs.length > 5`) [3](#0-2) . The `in_data_feed`/`data_feed` opcodes have no such proportional charge: `formula/validation.js` treats `data_feed`/`in_data_feed` complexity via `validateDataFeed`/`validateDataFeedExists`, which only validate the shape of parameters, not runtime cost relative to network size.

Because the `count_ops` budget (`MAX_OPS`) allows many opcodes per formula/getter call, and AAs can call remote getters and nested functions, an attacker can construct an AA (or trigger an already-deployed AA) whose formula calls `in_data_feed[...]` many times (bounded only by `MAX_OPS`, not by the true cost), each call performing an O(N) synchronous scan over all currently unstable units held in `storage.assocUnstableMessages`. During periods of high network load (many units posted but not yet stable — the intended/expected operating condition the DAG is designed to tolerate), N can be large, and the scan is synchronous JavaScript object iteration with no `setImmediate`/yield points (unlike the interpreter's own defensive `count % 100 === 0 → setImmediate` pattern used elsewhere to avoid blocking, see `formula/evaluation.js` lines 126-129 [4](#0-3) ). This blocks the Node.js event loop for the duration of the AA response computation for that trigger, which is executed as part of ordinary consensus/validation processing (every full node/AA-watcher processes every trigger to determine the AA's response).

### Impact Explanation
A single crafted trigger unit sent to an AA that uses `in_data_feed` (or a maliciously-published AA definition that itself uses this operator, which any unprivileged AA author can create) can force every node executing that AA to synchronously scan the full unstable-unit set multiple times per trigger. Under network conditions with many pending/unstable units, this results in prolonged event-loop blocking on nodes computing AA responses, which delays or stalls processing of all other units/AA triggers in the same time window — a localized hang/DoS analogous to the MySQL optimizer hang in CVE-2019-2834 (unbounded internal work triggered by an unprivileged, otherwise well-formed request). This does not appear to allow double-spend, inflation, or fund theft directly, but can cause the network's AA-processing nodes to become temporarily unresponsive, delaying confirmation of new units.

### Likelihood Explanation
Medium. Exploitability requires: (1) an AA definition using `in_data_feed`/`data_feed` reachable multiple times within one trigger's execution (easily achievable via loops/`map`/`reduce`/recursive-function patterns bounded only by `MAX_OPS`/`MAX_COMPLEXITY`, not real cost), and (2) a DAG state with a non-trivial number of unstable units, which is a normal, externally-influenceable condition (an attacker can also flood the network with units to inflate `assocUnstableMessages` size before firing the trigger). No special privileges beyond posting units/triggers are needed.

### Recommendation
Add a real-cost accounting for `data_feed`/`in_data_feed` proportional to `storage.assocUnstableMessages` size (or cap the number of these opcodes usable per AA execution independent of the generic `count_ops` budget), and/or replace the synchronous `for...in` scan with a bounded/indexed lookup structure (e.g., a per-address index of unstable data-feed messages) so a single evaluation is O(matching messages) rather than O(all unstable units in the network). Additionally, consider yielding to the event loop periodically inside `dataFeedExists`'s unstable-scan branch, consistent with the `setImmediate` pattern already used elsewhere in the formula evaluator.

### Proof of Concept
Conceptual (cannot be executed without live infra):
1. Deploy an AA whose response formula contains a loop or repeated calls invoking `in_data_feed[[oracles=..., feed_name=..., feed_value>0]]` enough times to approach `MAX_OPS` (each call is one "op" for validation purposes, but each performs a full O(N) scan of `storage.assocUnstableMessages`).
2. Flood the network with unstable units (unprivileged unit posting) to grow `storage.assocUnstableMessages` to a large size N.
3. Send a single trigger unit to the AA.
4. Nodes processing this trigger perform `MAX_OPS`-bounded-count × O(N) synchronous work in `dataFeedExists`, blocking their event loop for the duration, delaying processing of concurrent units/triggers.

Note: I was not able to execute this in a live environment to measure actual timing impact, nor confirm the exact value of `MAX_OPS`/`MAX_COMPLEXITY` (the `constants.js` grep matched but content wasn't returned within available context) or the typical/maximum size of `storage.assocUnstableMessages` under real network conditions — these would need to be verified in a running Devin session with the full repo and test network to confirm exploitability magnitude.
