### Title
Webhook signature is verified against the wrong organization's secret while handlers act on the `repository.full_name` from the same forged payload - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App configuration (and thus which `webhook_secret`) to validate the `X-Hub-Signature` against by reading `repository.owner.login` (or `organization.login`) out of the **unauthenticated** request body itself. All downstream webhook handlers, however, resolve the repository/stack to act on using a different field from that same unauthenticated body: `repository.full_name`. Because the field used to pick the verification secret is not the field used to determine the object being mutated, an attacker who knows (or can obtain) the `webhook_secret` for *any one* organization configured on the Shipit instance can forge a signature that the controller will happily accept while pointing `repository.full_name` at a completely different (victim) repository/organization's stack.

### Finding Description
`verify_signature` computes the organization used for verification purely from body content: [1](#0-0) [2](#0-1) 

`Shipit.github(organization: repository_owner)` looks up the `GithubApp`/secret keyed by that owner login, and `verify_webhook_signature` HMACs the raw body against that org's `webhook_secret`: [3](#0-2) 

Once verification passes, `create` hands the *entire parsed body* to every registered handler for the event, unmodified: [4](#0-3) 

Handlers, however, do not use `repository.owner.login` to decide what to act on — they use `repository.full_name`: [5](#0-4) 

For example, `PushHandler` resolves stacks purely from that `repository_name` lookup and then triggers a GitHub sync against the matched stack's branch: [6](#0-5) 

This is exactly the "organization that authenticated versus the repository that is written" binding break: the equality the code implicitly assumes is `repository.owner.login == owner-of(repository.full_name)`, but nothing enforces it. An attacker who controls (or has compromised) the `webhook_secret` of *any* organization/app configured in `config/secrets.yml` (e.g., a low-value test org) can sign a payload with `repository.owner.login` set to that org while setting `repository.full_name` to a victim's `owner/repo` tracked by a different, unrelated GitHub App. `verify_webhook_signature` only checks the signature against the attacker-controlled org's secret and returns `true`, then the push/status/check_suite handlers act on the victim repository's `Stack` because they trust `repository.full_name` unconditionally.

Additionally, when an org has no `webhook_secret` configured at all, `verify_webhook_signature` short-circuits to `true` unconditionally: [7](#0-6) 

so an attacker can simply set `repository.owner.login` to any org that has a blank `webhook_secret` (a legitimate, permitted deployment configuration per `docs/setup.md`) and bypass signature verification entirely for a request whose `repository.full_name` points at a fully signed/protected victim repo.

### Impact Explanation
This breaks the trust boundary between "which organization cryptographically vouched for this webhook" and "which repository/stack gets acted upon." Depending on handler, this allows an attacker with no privileged access to the victim's GitHub org to:
- Force `PushHandler` to enqueue `GithubSyncJob` against a victim stack with an attacker-chosen `expected_head_sha`, effectively triggering unauthorized syncs/deploys tied to a forged ref.
- Inject `StatusHandler`/`check_suite` events for a victim commit, influencing merge/deploy gating decisions (`deployable_status`) that Shipit trusts as coming from GitHub for that commit.

This crosses the "unauthorized deploy/rollback" and "escalation into authorization decisions" categories called out as valid impact, since the confused-organization binding lets an attacker manipulate state belonging to a repository they were never authorized to send events for.

### Likelihood Explanation
Requires only knowledge of a `webhook_secret` for *some* org configured on the instance (or exploitation of an org configured with no secret, which `docs/setup.md` explicitly allows), plus knowledge of the victim's `repository.full_name` and any expected commit SHAs — no privileged Shipit session, API token, or GitHub write access to the victim repo is needed. Multi-tenant Shipit deployments (multiple orgs in `config/secrets.yml`) are the realistic exposure case.

### Recommendation
Bind the verification identity to the same field the handlers act on. Concretely, `verify_signature` should derive the app/secret to check against using `repository.full_name`'s owner (or otherwise verify that `repository.owner.login` matches the owner segment of `repository.full_name`) before accepting the signature, and reject payloads where these disagree. Do not allow an org with a blank `webhook_secret` to implicitly authorize webhooks for a different, unrelated repository's stack.

### Proof of Concept
1. Suppose Shipit is configured with two GitHub Apps: `victim-org` (has a real `webhook_secret`) and `attacker-org` (attacker knows/owns this org's app and its `webhook_secret`, or it is configured with a blank secret per the sample config in `config/secrets.development.shopify.yml`).
2. Attacker crafts a `push` webhook JSON body:
   ```json
   {
     "ref": "refs/heads/main",
     "after": "<attacker-chosen-sha>",
     "repository": {
       "owner": { "login": "attacker-org" },
       "full_name": "victim-org/victim-repo"
     }
   }
   ```
3. Attacker signs the raw body with `attacker-org`'s `webhook_secret` (or sends no valid HMAC at all if `attacker-org` has no secret configured) and sets `X-Hub-Signature` accordingly.
4. `verify_signature` calls `Shipit.github(organization: 'attacker-org')` and passes verification using `attacker-org`'s secret/lack thereof — [1](#0-0)  — even though the payload targets `victim-org/victim-repo`.
5. `create` forwards the same body to `PushHandler`, which resolves the stack via `repository.full_name == "victim-org/victim-repo"` — [5](#0-4)  — and enqueues `GithubSyncJob` against the victim's stack with the attacker-supplied `after` SHA, without ever having been authenticated by `victim-org`'s GitHub App.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
