### Title
Cross-organization webhook forgery via organization/repository binding confusion in signature verification - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App's `webhook_secret` to validate an incoming webhook's HMAC signature against using one field of the untrusted JSON body (`repository.owner.login` / `organization.login`), while the handlers that actually mutate state use a *different* field of the same untrusted body (`repository.full_name`) to resolve the `Repository`/`Stack` to act on. Because Shipit explicitly supports hosting multiple GitHub App organizations on one instance (see `test/dummy/config/secrets_double_github_app.yml`), an attacker who legitimately administers a GitHub App installation for one configured organization can sign a forged payload with their own known `webhook_secret`, while claiming a different organization's repository in `repository.full_name`, causing the engine to act on a repository/stack it does not own.

### Finding Description
`verify_signature` computes which secret to use from the payload itself, before that payload has been proven authentic: [1](#0-0) [2](#0-1) 

`repository_owner` is read straight out of the attacker-supplied JSON (`params.dig('repository', 'owner', 'login')`), and `Shipit.github(organization: repository_owner)` looks up the `GithubApp`/secret configured for that organization name. The signature is only checked against that org's secret — nothing ties `repository.owner.login` to the actual target of the event.

Every event handler, however, resolves the repository/stack to mutate from a separate field of the same untrusted body: [3](#0-2) 

e.g. `PushHandler#process` finds stacks for `repository_name` (`repository.full_name`) and triggers `stack.sync_github`: [4](#0-3) 

Nothing in the request pipeline asserts that the organization portion of `repository.full_name` matches `repository.owner.login`/the org whose secret validated the HMAC. Since this engine is designed to serve multiple GitHub organizations from a single deployment (documented via `secrets_double_github_app.yml`'s `OrgOne`/`OrgTwo` configuration), an attacker who is an admin of their own org's GitHub App installation (`OrgTwo`) knows `OrgTwo`'s `webhook_secret` (they can generate it/see it themselves as the app owner) but not `OrgOne`'s (the victim). They can craft a raw JSON payload with `repository.owner.login = "OrgTwo"` (so the org-secret lookup succeeds and the HMAC validates), yet set `repository.full_name = "OrgOne/victim-repo"`. The signature check passes because it only validates against `OrgTwo`'s secret and the raw body; the handler then acts on `OrgOne/victim-repo`, entirely bypassing the boundary between organizations that the webhook signing scheme is meant to enforce.

This is the RCE-report's bug class ("attacker-controlled field used to build a trusted operation without matching the field actually verified") mapped onto Shipit's own trust boundary: **the organization whose secret authenticated the request ≠ the repository the handler writes to**, both being independently attacker-supplied fields of the same JSON body.

### Impact Explanation
This crosses the "organization that authenticated versus the repository that is written" binding called out in scope, and produces a documented Critical/High impact: cross-repository writes. Depending on the event type this can:
- Force a `GithubSyncJob`/`stack.sync_github` on a victim org's stack (`push` event), potentially advancing `undeployed_commits_count`, altering cached commit/CI state.
- Create, archive/unarchive Review Stacks belonging to a victim organization (`pull_request` opened/closed/reopened handlers), i.e. an unauthorized provisioning/deprovisioning action, without ever holding credentials for the victim org.
- Write commit statuses for a victim's commits (`status` handler), influencing deployability checks used to gate real deploys.

This directly matches the listed High-impact category ("cross-repository writes") only achievable if a Shipit instance hosts multiple GitHub organizations, which is an explicitly supported and documented configuration, not a misconfiguration outside scope.

### Likelihood Explanation
Requires: (1) the Shipit deployment to be multi-tenant/multi-org (a supported configuration per `secrets_double_github_app.yml`), and (2) the attacker to control a GitHub App installation for at least one of the configured organizations (i.e., be an unprivileged outsider to the victim org but a legitimate admin of their own, separate org on the same instance). No GitHub App private key, no Shipit session, and no `ApiClient` token for the victim org is needed — only the attacker's own webhook secret, which they legitimately possess. This satisfies the "unprivileged attacker" requirement relative to the victim organization.

### Recommendation
Bind signature verification to the same repository identity used by handlers: derive the organization key from `repository.full_name`'s owner segment (or, better, verify against every configured organization's secret and cross-check that the matching organization equals the owner encoded in `repository.full_name`) before dispatching to any handler. Reject requests where `repository.owner.login` and the owner portion of `repository.full_name` disagree.

### Proof of Concept
1. Configure Shipit with two GitHub App organizations, `OrgOne` (victim, secret unknown to attacker) and `OrgTwo` (attacker's own org/app, secret known to attacker), as in `test/dummy/config/secrets_double_github_app.yml`.
2. Attacker crafts a `push` webhook JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "deadbeefdeadbeefdeadbeefdeadbeefdeadbeef",
  "repository": {
    "owner": { "login": "OrgTwo" },
    "full_name": "OrgOne/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<hmac_sha1(OrgTwo_webhook_secret, raw_body)>` using their own known `OrgTwo` secret.
4. POST to `/webhooks` with header `X-Github-Event: push`. `verify_signature` calls `Shipit.github(organization: "OrgTwo")`, validates successfully against the attacker's own secret [1](#0-0) .
5. `PushHandler#process` resolves stacks via `repository.full_name = "OrgOne/victim-repo"` [3](#0-2)  and enqueues `GithubSyncJob`/`sync_github` for the victim's stack, an action the attacker was never authorized to trigger.

  module Webhooks

        params do
          requires :ref
          requires :after
        end
