### Title
Webhook signature verification is scoped to the wrong field — organization used to select the HMAC secret is disconnected from the repository/commit actually mutated ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects *which* GitHub App/organization's `webhook_secret` to check the `X-Hub-Signature` against using `repository_owner`, taken from the attacker-supplied JSON body (`repository.owner.login`, falling back to `organization.login`). Once the signature checks out against that organization's secret, the entire raw payload — including fields the verification step never inspected — is handed unmodified to the registered webhook handlers, which key their side effects off *different* fields of the same JSON body (`repository.full_name` for `Repository.from_github_repo_name`, or nothing at all for `StatusHandler`). In a multi-organization Shipit deployment (the documented `github: { org1: {...}, org2: {...} }` schema), this breaks the intended binding "organization that authenticated == repository that is written."

### Finding Description
`Shipit.github(organization: repository_owner)` in `lib/shipit.rb` (`github_app_config`) looks up per-organization credentials (`app_id`, `webhook_secret`, etc.) using the organization name pulled straight out of the untrusted JSON body: [1](#0-0) [2](#0-1) [3](#0-2) 

The signature verification (`verify_webhook_signature`) only proves the raw body was HMAC-signed with *some* organization's `webhook_secret` — it says nothing about which repository inside that body is legitimate for that organization: [4](#0-3) 

After verification, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` hands the full, attacker-controlled JSON straight to handlers: [5](#0-4) 

Handlers resolve the target repository from `repository.full_name`, a field the verification step never checked for consistency with `repository.owner.login`: [6](#0-5) 

`Shipit::Webhooks::Handlers::StatusHandler` is the worst case: it doesn't even scope by repository — it looks up commits **globally by SHA** across the entire Shipit instance: [7](#0-6) 

A `status` webhook drives `Commit#create_status_from_github!` → `add_status`, which can transition a commit to `success` and trigger `stack.schedule_merges` (part of the auto-merge/continuous-delivery pipeline): [8](#0-7) [9](#0-8) 

### Impact Explanation
In a Shipit deployment configured for multiple GitHub organizations (documented in `docs/setup.md`/`config/secrets.development.example.yml`), an attacker who administers a GitHub App/webhook for **one** low-trust organization (OrgA, whose `webhook_secret` they legitimately know) can:
1. Sign an arbitrary JSON body with OrgA's `webhook_secret`.
2. Set `X-Github-Event: status`, `sha` = the head SHA of a commit belonging to a **different**, higher-trust organization's stack (OrgB), and `state: success`.
3. `repository_owner` resolves to OrgA (verification passes), but `StatusHandler` never checks repository ownership at all and updates the status of the OrgB commit globally by SHA.

This can flip a commit's status to `success`, satisfying CI gating and triggering `schedule_merges`/continuous delivery for a stack the attacker does not control — an unauthorized/forged CI signal feeding into an unauthorized deploy or merge decision. This matches the report's "Critical: unauthorized deploy" impact class. The same organization/repository disconnect also affects `push`, `pull_request`, and `check_suite` handlers, which rely solely on `repository.full_name` with no cross-check against the verified `repository.owner.login`, though those are additionally gated by `Repository.from_github_repo_name` matching an existing repository record.

### Likelihood Explanation
This requires (a) a multi-organization Shipit configuration and (b) the attacker controlling a legitimate webhook secret for at least one configured organization — a realistic scenario for a shared/self-service Shipit instance serving many GitHub orgs with differing trust levels, since organization admins configure their own GitHub App webhook secrets independently of each other. No Shipit session, `ApiClient` token, or GitHub write access to the target org/repo is required — only the ability to sign an HTTP POST to `/webhooks` with a secret the attacker already legitimately possesses for an unrelated organization.

### Recommendation
Verify that `repository.full_name`'s owner matches the organization whose secret was used to verify the signature (i.e., re-derive `repository_owner` used for verification and pass it through so each handler can assert `repository.owner.login == verified_organization`). At minimum, `StatusHandler` (and any other handler that queries records without scoping by repository) should scope its lookup to the repository resolved from the verified organization, not merely by global SHA.

### Proof of Concept
1. Configure Shipit with two organizations, e.g. `secrets.github = { orga: {webhook_secret: "s1", ...}, orgb: {webhook_secret: "s2", ...} }`.
2. Attacker administers a GitHub App under `orga` and knows `s1`.
3. Attacker crafts payload:
```json
{
  "sha": "<head sha of a commit in an orgb-owned stack>",
  "state": "success",
  "repository": { "owner": { "login": "orga" } }
}
```
4. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(s1, body)` and POSTs to `/webhooks` with `X-Github-Event: status`.
5. `verify_signature` resolves `repository_owner` = `"orga"`, fetches `orga`'s `GitHubApp`, and the signature validates against `s1`.
6. `StatusHandler#process` runs `Commit.where(sha: params.sha)` — matching the `orgb` commit regardless of the signing organization — and calls `create_status_from_github!`, marking it `success` and potentially triggering `stack.schedule_merges` for the `orgb` stack.

Note: I could not find a `test/` fixture reproducing this exact cross-organization payload in the indexed code, so this scenario is derived from static analysis of `webhooks_controller.rb`, `handler.rb`, and `status_handler.rb` rather than an executed proof; a Devin session with full repo/test access would be needed to build and run a concrete regression test confirming the cross-org status write.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

      already_deployed = deployed?
