### Title
Cross-repo status forgery via global sha-only matching in `StatusHandler#process` binds attacker CI results to victim stacks - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` resolves target commits purely by `sha` across the entire `commits` table, ignoring the webhook payload's own `repository` field entirely. Any legitimately-signed GitHub `status` webhook — even one originating from a completely unrelated repository the attacker controls — will be applied to every `Commit` row sharing that sha, using each matched commit's *own* `stack_id`, not the stack the webhook actually came from.

### Finding Description
The broken binding: the question claims `deploy_spec used to judge status == deploy_spec of repo that actually posted status`. Trace confirms this is violated because commit lookup never checks repository identity: [1](#0-0) 

`params` (built from the `ExplicitParameters` schema) only requires `sha`, `state`, and optionally `context`/`branches` — there is no `repository` requirement or comparison against the matched commit's stack: [2](#0-1) 

For every `Commit` row that shares the sha, `create_status_from_github!` is called, which persists the status using that specific commit's own `stack_id`, taken from the `Commit` record (i.e. the victim's stack), not from the webhook payload: [3](#0-2) 

`Status.replicate_from_github!` simply writes `state`, `description`, `context`, `target_url` and `created_at` from whatever `github_status` was passed, with `stack_id` supplied by the caller — it performs no validation that the status's context/repo is consistent with the stack that consumed it: [4](#0-3) 

`WebhooksController#verify_signature` only proves the payload came from GitHub for the organization named in the payload's own `repository.owner` — it says nothing about which `Commit`/`Stack` the status content is allowed to attach to: [5](#0-4) 

Exploit flow: the victim's stack (`Stack V`) requires context `ci/travis` via `merge_request_required_statuses` sourced from `stack.cached_deploy_spec`: [6](#0-5) 

`MergeRequest#all_status_checks_passed?` builds a `StatusChecker` from `head.statuses_and_check_runs` and the victim stack's own deploy spec, then simply matches by context string, with no verification of which repository actually posted the underlying `Status`: [7](#0-6) [8](#0-7) 

If a commit with the victim PR head's exact sha also exists as a `Commit` row tied to a stack the attacker's own repository posts webhooks for (e.g. a Shipit-tracked fork, or any repo sharing that exact git commit object — git commit hashes are content-addressed and fully reproducible by anyone who can read the public commit metadata/diff), the attacker can trigger their own legitimate CI to post a `success` status with context `ci/travis` for that sha. GitHub signs and delivers this webhook honestly for the attacker's own installation, passing `verify_signature`. `StatusHandler#process` then matches the sha globally and writes a `Status` bound to `stack_id = V` (the victim's stack), satisfying `merge_request_required_statuses` for a PR that never actually ran the victim's own CI.

None of the existing guards intercept this: `verify_signature` checks webhook authenticity for the *sending* repository/org only, not the identity of the commits it is allowed to annotate; `drop_unhandled_event` and the `ExplicitParameters` schema only validate presence/shape of fields, not repository binding; there is no `stacks`/`Repository` scoping applied in `Commit.where(sha: params.sha)`.

### Impact Explanation
A status write intended for one repository's CI is silently bound to a different stack's commit record, which is exactly the "payload for one repository mutating another's stack" Critical category: it can satisfy `merge_request_required_statuses`/`all_status_checks_passed?` and gate (or directly enable) merging a victim PR that did not pass the victim repository's actual CI. This is repeatable for any sha that coincides between an attacker-controlled, Shipit-tracked repository and a victim stack's tracked commit, and the blast radius spans any two stacks sharing commit history under the same Shipit instance (e.g., forks, mirrors, monorepo splits).

### Likelihood Explanation
Exploitability requires: (1) the exact commit sha of the victim PR head to also be reachable/postable-to from a Shipit-tracked repository the attacker controls (achievable for forks of public repos, since git commit objects are portable/reproducible), and (2) that repository to be one for which GitHub will deliver a signed `status` webhook Shipit accepts (i.e., tracked by the same Shipit/GitHub App instance). This is a real but non-trivial precondition — it is most directly exploitable in fork-based or monorepo-split Shipit deployments where multiple stacks are configured against related git histories, but the core code defect (no repository-binding check in `StatusHandler#process`) is unconditional and does not depend on secrets.

### Recommendation
In `StatusHandler#process`, restrict the `Commit` lookup to commits whose `stack.github_repo_name` (or `Repository`) matches the webhook payload's `repository.full_name`, e.g. `Commit.joins(:stack).where(sha: params.sha, shipit_stacks: { ... repo match ... })`, and reject/ignore statuses whose payload repository doesn't correspond to the target commit's stack before calling `create_status_from_github!`.

### Proof of Concept
```ruby
# test/models/webhooks/handlers/status_handler_test.rb (conceptual)
test "status webhook cannot bind a status originating from another repository to a victim stack" do
  victim_stack = shipit_stacks(:shipit)                 # requires 'ci/travis'
  victim_stack.cached_deploy_spec.stubs(:merge_request_required_statuses).returns(['ci/travis'])
  attacker_stack = shipit_stacks(:cyclimse)              # unrelated repo/stack

  shared_sha = 'deadbeefcafef00d'
  victim_commit = victim_stack.commits.create!(sha: shared_sha, ...)
  merge_request = shipit_merge_requests(:some_pr)        # belongs to victim_stack, head: victim_commit

  refute merge_request.reload.all_status_checks_passed?

  # forged/legit webhook actually signed for attacker_stack's repo, but same sha
  params = Webhooks::Handlers::StatusHandler.const_get(:Params).new(
    sha: shared_sha, state: 'success', context: 'ci/travis'
  )
  Webhooks::Handlers::StatusHandler.new(attacker_repo_payload_with(sha: shared_sha)).process

  assert merge_request.reload.all_status_checks_passed?, "victim MergeRequest gating flipped by attacker-originated status"
end
```
Both sides of the equality diverge: `Status.stack_id == victim_stack.id` (written) vs. the actual originating repository/stack of the CI run == `attacker_stack`, yet `merge_request.all_status_checks_passed?` reads `stack.cached_deploy_spec` (victim's) as satisfied by attacker-sourced data.
