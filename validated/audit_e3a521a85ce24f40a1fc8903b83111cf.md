### Title
Fork PR labels inject unfiltered `ENV`/arbitrary env vars into ReviewStack deploy commands enabling shell-startup-file RCE - (File: app/models/shipit/review_stack.rb, lib/shipit/command.rb)

### Summary
`ReviewStack#env` merges every PR label, upcased, directly into the stack's environment hash with no whitelist, unlike every other env-var ingestion path in the codebase which routes through `EnvironmentVariables#permit`. Because PR labels can be self-applied by the PR author on their own fork/PR, and provisioning of the corresponding `ReviewStack` happens automatically when `provisioning_behavior` is `allow_all`, an unprivileged contributor can set a label like `env` and have `ENV=true` injected unfiltered into the environment merged into every deploy `Command`, ultimately reaching `PTY.spawn` via `Command#unbundled_env`.

### Finding Description
The broken binding: for a `ReviewStack`, the invariant should be `stack.env.keys ⊆ deploy_variables.map(&:name) ∪ fixed_task_keys` (i.e., every key reaching the spawned process env is either a fixed Shipit-controlled key or explicitly whitelisted via `deploy.variables` in `shipit.yml`). Instead:

`ReviewStack#env` at [1](#0-0)  does:
```
super.merge(pull_request.labels.each_with_object({}) { |label_name, labels| labels[label_name.upcase] = "true" })
```
This merges every GitHub label name (upcased) as a key with no call to `EnvironmentVariables.permit`, unlike `DeploySpec#filter_deploy_envs`/`filter_rollback_envs` [2](#0-1)  which whitelist deploy/rollback envs against `deploy.variables`/`rollback.variables`, and unlike `EnvironmentVariables#permit` in general [3](#0-2) .

This `stack.env` (containing the attacker-controlled `ENV` key) is merged into `TaskCommands#env`:
```
super.merge(@stack.env).merge({...fixed keys...}).merge(deploy_spec.machine_env).merge(@task.env)
``` [4](#0-3)  — note `@stack.env` is merged early and is not subsequently overwritten by any fixed key named `ENV`, so it survives to the final env hash.

That hash is passed as `env:` into `Command.new`, stored in `@env`, and then combined in `Command#unbundled_env`:
```
BASE_ENV.merge('PATH' => ...).merge(@env.stringify_keys)
``` [5](#0-4)  — `@env` (attacker-controlled) is merged **last**, overriding anything in `BASE_ENV`. This is fed straight into `PTY.spawn(unbundled_env, *interpolated_arguments, chdir: @chdir)` at [6](#0-5) , which spawns the actual deploy-step shell process.

Exploit flow:
1. Attacker opens a PR from their own fork against a repository configured with `review_stacks_enabled=true` and `provisioning_behavior=allow_all`.
2. `Shipit::Webhooks::Handlers::PullRequest::OpenedHandler` creates a `ReviewStack` for this PR unconditionally under `allow_all` (confirmed by existing tests, e.g. "creates stacks for repos that allow_all").
3. Attacker (as the PR owner) adds a label named `env` to their own PR via the GitHub API/UI (labeling one's own PR requires only "read" access on public repos or write access on the fork, which every PR author-on-their-own-fork setup permits for public repos accepting PRs) — or the label could also come from any `shipit.yml` env-independent config if applicable, but the direct path is via label.
4. `ReviewStack#env` produces `{'ENV' => 'true', ...}` unfiltered.
5. When the review stack deploys (or any task runs), `TaskCommands#env` includes `'ENV' => 'true'`, and `Command#unbundled_env` places `ENV=true` into the spawned process's environment.
6. If `ENV=true` is not directly useful, the same code path allows setting `ENV=/tmp/attacker_controlled_path` (a label named e.g. `env` only yields `"true"` as value — labels only control the *key*, not an arbitrary value, since the merge always sets the value to the literal string `"true"`). This means the practical exploit is limited to setting `ENV=true`/`RUBYOPT=true`/etc. — i.e., attacker controls **which env var names get set to `"true"`**, not arbitrary values, unless the value itself can also be attacker-set through another vector (e.g., `shipit.yml`'s `deploy.variables` combined with a task-triggering user-supplied env, which IS filtered by `EnvironmentVariables#permit`).

Because the value is fixed to the string `"true"`, this specific path cannot make `ENV` point to an attacker-authored shell script path (which requires attacker control of the *value*, not just the key). Achieving `ENV=/path/to/malicious/file` for shell-sourcing RCE would require a different vector where the attacker also controls the *value* unfiltered — this is not demonstrated by `ReviewStack#env`. No other unfiltered fork-controllable value-setting path into the deploy-time env hash was found: `deploy_spec.machine_env` sources from `shipit.yml`'s `machine.environment` block [7](#0-6) , but the target repository's `shipit.yml` used to build the cached deploy spec is fetched from the base repository/branch definitions rather than proven in this trace to be sourced from the fork's untrusted branch without any check — this could not be fully confirmed within the scope of the search performed and would need direct inspection of `DeploySpec::FileSystem` fetch/checkout logic and `ReviewStack`'s branch/commit resolution to confirm whether `machine_env` is actually attacker-fork-controlled for review stacks specifically.

### Impact Explanation
Confirmed: an unprivileged PR author can force an arbitrary key of their choosing (via a self-applied label) into the environment of every `Command` spawned for their `ReviewStack`'s tasks/deploys, with the value hard-coded to `"true"`. This can pollute/override well-known environment variables that other tooling might treat specially with a boolean-truthy value (e.g., toggling debug/verbose behavior variables, disabling `CI` checks that gate on absence of a var, or overriding flags a deploy script checks with `if [ -n "$VAR" ]`), but does **not** allow arbitrary command execution via `ENV`/`BASH_ENV` sourcing because the attacker cannot control the *value* (i.e., cannot supply a path to a malicious script) through this label mechanism — only the *key name*. This falls short of the Critical RCE claim in the question as stated, since RCE via shell startup-file sourcing requires attacker-controlled file *content and path*, not just the variable name.

### Likelihood Explanation
Requires `review_stacks_enabled=true` and `provisioning_behavior=allow_all` (or `allow_with_label`/`prevent_with_label` combined with the attacker controlling their own label) on the target repository — a maintainer-chosen, documented setting [8](#0-7) . Attacker cost is minimal (open a PR, add a label to their own PR), fully repeatable per PR/stack, but the value-injection is restricted to the literal `"true"` string, capping impact well below arbitrary code execution.

### Recommendation
Whitelist PR-label-derived environment variable names in `ReviewStack#env` against an explicit allowlist (analogous to `DeploySpec#filter_deploy_envs`/`EnvironmentVariables#permit`), reject reserved/dangerous names (`ENV`, `BASH_ENV`, `PATH`, `LD_PRELOAD`, `RUBYOPT`, etc.) outright, and ensure `Command#unbundled_env` filters `@env` through a similar reserved-name denylist before merging over `BASE_ENV`, regardless of the value's origin.

### Proof of Concept
```ruby
# test/models/shipit/review_stack_test.rb (proof sketch)
test "PR labels unfiltered env leaks into stack.env and Command#unbundled_env" do
  repository = shipit_repositories(:shipit)
  repository.update!(review_stacks_enabled: true, provisioning_behavior: :allow_all)

  stack = ReviewStack.create!(branch: "feature", environment: "pr999", repository:)
  pr = stack.create_pull_request!(github_pull_request: { labels: [{ name: "env" }] })

  assert_equal "true", stack.env["ENV"]

  command = Command.new("echo hi", env: stack.env, chdir: ".")
  assert_equal "true", command.unbundled_env["ENV"]
end
```
This confirms the binding is broken (`stack.env["ENV"]` should not exist / should be filtered, but is present and reaches `Command#unbundled_env`), while noting the exploit is limited to fixed-value injection, not arbitrary-value RCE via shell startup file sourcing as claimed.
