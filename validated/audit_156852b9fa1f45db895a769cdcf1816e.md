### Title
Shared/multi-device address definition templates allow a hidden single-key spending branch that silently overrides intended n-of-n cosigning, with no warning to the approving device - (File: wallet_defined_by_addresses.js)

### Summary
When a device proposes creation of a shared (multi-signature) address via `create_new_shared_address`, the recipient device validates the proposed `address_definition_template` with `validateAddressDefinitionTemplate()`, which relies on `getMemberDeviceAddressesBySigningPaths()` to enumerate the "member devices" that must cosign. This enumerator only understands `or`, `and`, `r of set`, `weighted and`, `address`, and `definition template` ops. Any other valid definition op (e.g. `sig` or `hash` with a hard-coded, attacker-controlled pubkey) embedded inside an `or` branch is silently skipped — neither recorded as a member nor rejected — while `Definition.validateDefinition()` still accepts it as a perfectly legal spending condition. As a result, a template that looks like an "n-of-n" or "all members required" shared address can actually contain a hidden `or` branch that lets the proposer (or anyone holding a hard-coded key) spend unilaterally, and the approving user/device is never warned about this extra, unauthorized spending path.

### Finding Description
`getMemberDeviceAddressesBySigningPaths()` in [1](#0-0)  walks the proposed definition template recursively but its `switch` only has cases for `or`, `and`, `r of set`, `weighted and`, and `address` (throwing only for `definition template`). Any other op (most notably `sig`/`hash` with a literal, non-`$address@`-prefixed pubkey) simply falls through with no case matched — no error, no recorded signer.

`validateAddressDefinitionTemplate()` at [2](#0-1)  then only checks that the *enumerated* `arrDeviceAddresses` has at least two entries, includes "my" device, and includes the sender's device — it never checks that every leaf of the definition is accounted for as a known device, nor that there is no alternate `or` branch bypassing the cosigning requirement. It does call `Definition.validateDefinition()` on a filled fake template, but that only confirms the definition is *structurally valid* (i.e., syntactically legal spending conditions) — it says nothing about whether the definition matches the cosigning semantics the user believes they are approving.

Consequently, a malicious peer can send a `create_new_shared_address` message (handled in `wallet.js`, which calls `validateAddressDefinitionTemplate` and then emits the `create_new_shared_address` event for UI confirmation) with a template such as:
```
['or', [
  ['address', '$address@DEVICE_A'],
  ['address', '$address@DEVICE_B'],
  ['sig', {pubkey: '<attacker-controlled pubkey, base64>'}]
]]
```
This passes `validateAddressDefinitionTemplate` because `arrDeviceAddresses = [DEVICE_A, DEVICE_B]` satisfies "at least 2 members, includes me, includes sender," and `Definition.validateDefinition` accepts the whole `or` expression as valid. The UI dialog triggered by `eventBus.emit("create_new_shared_address", ...)` (see the comment at [3](#0-2)  in `wallet.js`) shows only the raw template/paths intended for cosigner assignment — it never surfaces that a third, always-available single-signature branch exists that bypasses the intended 2-party requirement. The same enumeration gap exists in the single-signature multi-device wallet path via `getDeviceAddressesBySigningPaths()`/`validateWalletDefinitionTemplate()` in [4](#0-3) , which likewise only records `sig`/`hash` args matching the `$pubkey@device_address` convention and silently ignores any other literal-keyed branch.

This mirrors the XWiki analog precisely: an untrusted party (peer device) crafts a definition object; the victim, with the ability/authority to fund an address (the analog of "programming right"), unknowingly approves it because the validation and UI path give no warning about the embedded privilege-granting branch.

### Impact Explanation
Once the victim approves and funds the resulting shared address (believing it requires cosigning from `DEVICE_A` and `DEVICE_B`), the attacker who embedded the hard-coded `sig`/`hash` branch can spend all funds sent to that address unilaterally, at any time, without any cooperation from the other cosigners. This is a direct unauthorized-spending / fund-theft vulnerability: the enforced trust model of a multi-party address is silently subverted by a single malicious proposer.

### Likelihood Explanation
Exploitation requires only that the attacker be a correspondent device able to send a `create_new_shared_address` (or wallet-definition-template) offer — a routine cosigning proposal in normal peer-to-peer wallet interactions, requiring no special network position or privileged role. The victim's decision to accept is based on a UI dialog populated from data that has already passed validation, so the flawed template appears legitimate and safe.

### Recommendation
Harden `getMemberDeviceAddressesBySigningPaths()` (and the analogous `getDeviceAddressesBySigningPaths()` in `wallet_defined_by_keys.js`) so that every leaf of the definition tree is exhaustively classified: any `sig`/`hash`/other terminal op that does not resolve to a known, expected device/member must cause validation to fail (`throw`/`return error`) rather than being silently skipped. Additionally, `validateAddressDefinitionTemplate`/`validateWalletDefinitionTemplate` should positively verify that *all* signing paths reachable in the definition are attributable to an enumerated member device, rather than only checking that a minimum count of expected members is present.

### Proof of Concept
1. Device B (attacker) sends Device A a `create_new_shared_address` message with `address_definition_template`:
```json
["or", [
  ["address", "$address@DEVICE_A"],
  ["address", "$address@DEVICE_B"],
  ["sig", {"pubkey": "<attacker_pubkey_base64>"}]
]]
```
2. Device A calls `validateAddressDefinitionTemplate`, which computes `assocMemberDeviceAddressesBySigningPaths = {DEVICE_A, DEVICE_B}` (2 members, includes self and sender) and passes `Definition.validateDefinition` since the `or` structure is syntactically valid.
3. Device A's UI shows a "create shared address" confirmation without indicating the extra unconditional `sig` branch; the user approves.
4. Funds are sent to the resulting shared address.
5. The attacker, holding the private key for `attacker_pubkey`, spends the funds alone via the third `or` branch, without any involvement from Device A or Device B.

function getMemberDeviceAddressesBySigningPaths(arrAddressDefinitionTemplate){
	function evaluate(arr, path){
		var op = arr[0];
		var args = arr[1];
		if (!args)
			return;
		switch (op){
			case 'or':
			case 'and':
				for (var i=0; i<args.length; i++)
					evaluate(args[i], path + '.' + i);
				break;
			case 'r of set':
				if (!ValidationUtils.isNonemptyArray(args.set))
					return;
				for (var i=0; i<args.set.length; i++)
					evaluate(args.set[i], path + '.' + i);
				break;
			case 'weighted and':
				if (!ValidationUtils.isNonemptyArray(args.set))
					return;
				for (var i=0; i<args.set.length; i++)
					evaluate(args.set[i].value, path + '.' + i);
				break;
			case 'address':
				var address = args;
				var prefix = '$address@';
				if (!ValidationUtils.isNonemptyString(address) || address.substr(0, prefix.length) !== prefix)
					return;
				var device_address = address.substr(prefix.length);
				assocMemberDeviceAddressesBySigningPaths[path] = device_address;
				break;
			case 'definition template':
				throw Error(op+" not supported yet");
			// all other ops cannot reference device address
		}
	}
	var assocMemberDeviceAddressesBySigningPaths = {};
	evaluate(arrAddressDefinitionTemplate, 'r');
	return assocMemberDeviceAddressesBySigningPaths;
}

function validateAddressDefinitionTemplate(arrDefinitionTemplate, from_address, handleResult){

		var assocMemberDeviceAddressesBySigningPaths = getMemberDeviceAddressesBySigningPaths(arrDefinitionTemplate);
	}
	catch (e) {
		return handleResult("failed to get member device addresses of new shared address: " + e.toString());
	}
	var arrDeviceAddresses = _.uniq(_.values(assocMemberDeviceAddressesBySigningPaths));
	if (arrDeviceAddresses.length < 2)
		return handleResult("less than 2 member devices");
	if (arrDeviceAddresses.indexOf(device.getMyDeviceAddress()) === - 1)
		return handleResult("my device address not mentioned in the definition");
	if (arrDeviceAddresses.indexOf(from_address) === - 1)
		return handleResult("sender device address not mentioned in the definition");

	// to fill the template for validation, assign my device address (without leading 0) to all member devices 
	// (we need just any valid address with a definition)

		params['address@'+device_address] = fake_address;

		var arrFakeDefinition = Definition.replaceInTemplate(arrDefinitionTemplate, params);

		return handleResult(e.toString());

			return handleResult(err);
		handleResult(null, assocMemberDeviceAddressesBySigningPaths);
	});
