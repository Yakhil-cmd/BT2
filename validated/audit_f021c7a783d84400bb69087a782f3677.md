## Title
Stack‑scoped API client can read the deploy/rollback status of any stack via the CCMenu endpoint - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Shipit::Api::CCMenuController` overrides the `stack` resolution helper to look up the stack directly from `Stack.from_param!(params[:stack_id])` instead of using the scoped `stacks.from_param!` helper defined in the base controller. This breaks the binding "a stack a token authorises versus a stack it touches": an `ApiClient` that is restricted to a single `stack_id` can still be presented with an arbitrary `stack_id` in the URL and receive that other stack's latest deploy/rollback status.

### Finding Description
`Shipit::Api::BaseController` scopes stack lookups to the authenticated API client when the client is bound to a specific stack: [1](#0-0) 

Every other resource controller (e.g. `Api::StacksController#stack`) reuses this scoped helper: [2](#0-1) 

However, `Api::CCMenuController` defines its own `stack` method that bypasses the client-scoped `stacks` relation entirely and resolves the stack unconditionally from all stacks: [3](#0-2) 

The controller still enforces `require_permission :read, :stack`, but that check only verifies the *permission* string is present on the client (`ApiClient#check_permissions!`), not that the requested stack matches the client's authorized `stack_id`: [4](#0-3) 

This is exactly the same bug class as the report: a security-relevant conditional (settle-escalation logic gated only on `_pledgesAgainstDispute`, ignoring `_pledgesForDispute`) omits a check that should also cover the sibling case. Here, the sibling case is the client's `stack_id` scope, which every other controller enforces via `stacks.from_param!` but `CCMenuController` silently drops in favor of unscoped `Stack.from_param!`.

### Impact Explanation
A caller holding a valid `ApiClient` token that was intentionally restricted to one stack (fixture example: `here_come_the_walrus`, scoped to the `shipit` stack with only `read:stack` permission) can request `/api/stacks/:stack_id/ccmenu` for any other stack's `to_param` and receive that stack's name, activity, last build status/label/time and web URL — data the token issuer never authorized that client to see. This is an authenticated-but-unauthorized cross-stack read of deploy status, matching the in-scope "High" impact category of unauthenticated read of stack state / deploy output relative to the token's actual authorization scope.

### Likelihood Explanation
Any party in possession of a stack-scoped `ApiClient` authentication token (the normal, lowest-privilege token type CCMenu clients are created with, see `CCMenuUrlController#client`) can trigger this by simply changing the `stack_id` path parameter — no additional secret, session, or privileged access is required beyond the token itself, which is the credential this endpoint is designed to accept. [5](#0-4) 

### Recommendation
- Short term: change `Api::CCMenuController#stack` to reuse the client-scoped lookup (`stacks.from_param!(params[:stack_id])`) exactly as `Api::StacksController` and other resource controllers do, so a stack-restricted `ApiClient` cannot resolve stacks outside its `stack_id`.
- Long term: add a regression test authenticating with a stack-scoped `ApiClient` (e.g. `here_come_the_walrus`) and asserting that requesting the CCMenu endpoint for a *different* stack returns 404/forbidden rather than the other stack's data.

### Proof of Concept
1. Create/obtain a stack-scoped `ApiClient` token restricted to Stack A (`permissions: [read:stack]`, `stack: A`), e.g. via `CCMenuUrlController#fetch` on Stack A which creates such a client.
2. Call `GET /api/stacks/:B_id/ccmenu?token=<token>` where `B` is a different stack the client was never authorized for.
3. Observe `Api::CCMenuController#stack` resolves `Stack.from_param!(params[:stack_id])` unconditionally, `require_permission :read, :stack` passes (the client does have the `read:stack` permission string), and the response renders Stack B's `deploys_and_rollbacks.last` status — data outside the token's authorized scope.
