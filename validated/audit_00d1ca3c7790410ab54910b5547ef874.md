### Title
`ERC20Transactor` credits the XCM holding register with the requested amount without verifying the ERC20 contract actually transferred that amount, allowing fee-on-transfer/non-standard ERC20 tokens to desynchronize on-chain accounting from the real token balance held in the checking account - (File: cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs)

### Summary
The external report flags `_pullTokenInputAndPayProtocolFee()` in an EVM AMM for crediting itself with a `saleAmount` of ERC20 tokens after `safeTransferFrom()` without checking the actual balance delta, which breaks under fee-on-transfer or non-standard tokens. The Polkadot SDK's `ERC20Transactor` (used by Asset Hub Westend's XCM executor to bridge ERC20 tokens deployed via `pallet-revive` into the XCM asset model) has the same class of defect: it calls the ERC20 contract's `transfer()` function and, if the call succeeds and returns `true`, unconditionally credits the XCM holding register (or treats the deposit as fully completed) with the exact `amount` requested by the XCM program - it never re-reads the ERC20 `balanceOf` of the checking account before/after to confirm that amount was actually moved.

### Finding Description
`ERC20Transactor::withdraw_asset_with_surplus` (`cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs:150-216`) builds an `IERC20::transferCall { to: checking_address, value: amount }` and executes it via `pallet_revive::Pallet::<T>::bare_call`. On success it does: [1](#0-0) 
i.e. it only checks that the call didn't revert and that the ABI-decoded boolean return value is `true`; it then mints an `AssetsInHolding::new_from_fungible_credit(what.id.clone(), Box::new(Erc20Credit(amount)))` for the full requested `amount` - the *intended* transfer amount, not anything measured from the contract's state.

`deposit_asset_with_surplus` (same file, lines 225-306) mirrors this: it calls `transfer()` from the checking account to the beneficiary for `amount`, and if the return decodes to `true`, it reports success for the full `amount`, again with no `balanceOf` check before/after.

This is architecturally identical to the reported bug: both trust the return value / non-reverting nature of an external ERC20-style `transfer`/`transferFrom` call as proof that exactly `amount` tokens moved, rather than verifying the real balance delta. An ERC20 contract that:
- takes a fee on transfer (burns or redirects part of the amount), or
- returns `true` while moving less than `value` (many non-standard/deflationary tokens do this), or
- has reentrant/hooked logic that alters balances unexpectedly during the call,

will cause the `ERC20Transactor`'s internal XCM accounting (`AssetsInHolding`) to diverge from the real ERC20 balance actually held by `ERC20TransfersCheckingAccount`.

Any user can deploy an arbitrary ERC20 contract via `pallet-revive` on Asset Hub (no privileged role required), then reference it as an XCM asset using its `AccountKey20` location - this is exactly how the feature is designed to be used, confirmed by the `withdraw_and_deposit_erc20s` test and the `ERC20Matcher`/`IsLocalAccountKey20` matching logic wired into `AssetTransactors` in `xcm_config.rs`: [2](#0-1) 
A signed user can submit `pallet_xcm::execute` with a program that does `WithdrawAsset` (their fee-on-transfer ERC20) → `DepositAsset` to a beneficiary, exactly as exercised by the existing test: [3](#0-2) 
If the deployed contract's `transfer` takes, say, a 10% fee, `withdraw_asset_with_surplus` will still credit the holding register with the full pre-fee `amount`, and the subsequent `deposit_asset_with_surplus` will then attempt to move that same (unbacked) `amount` out of the checking account to the beneficiary. Over repeated calls, the checking account's actual ERC20 balance can be depleted faster than the XCM program's accounting assumes, or a beneficiary can receive more "credited" holding value than was ever actually deposited into the checking account, corrupting the invariant that the checking account's real ERC20 balance backs all outstanding XCM-tracked ERC20 credits for that asset.

### Impact Explanation
This is a genuine accounting-integrity break specific to Asset Hub's new ERC20-XCM bridge (introduced per `prdoc/stable2506/pr_7762.prdoc`). The severity is bounded because:
- It only affects ERC20 contracts that are non-standard (fee-on-transfer, rebasing, or return-value-lying tokens) - well-formed ERC20s (which don't take fees and return true only on full transfer) are unaffected.
- The Sudorandom Labs/Spearbit acknowledgment on the *original* EVM report explicitly treats fee-on-transfer tokens as "undefined behavior... beyond scope," and this is the same posture the Polkadot SDK code implicitly takes for the `ERC20Transactor` (no listing/allowlist restrictions were found for which ERC20 contracts may be referenced).
- Exploitation would primarily let an attacker create internal-accounting/holding-register value that is not backed 1:1 by the checking account's real ERC20 balance, which could manifest as loss of funds for other users of the same checking account/asset once the discrepancy is deposited/withdrawn elsewhere, but requires the attacker to control (or find) a non-standard ERC20 contract usable for this purpose.

Given the acknowledged/accepted-risk precedent on the analogous EVM report and the narrow non-standard-token precondition, this most plausibly maps to a Medium-severity finding, consistent with the original report's own severity rating.

### Likelihood Explanation
Likelihood is Medium: the entry path (deploy a contract via `pallet-revive`, then reference it via XCM's `AccountKey20` asset id in a self-service `pallet_xcm::execute` or reserve/local transfer) is fully user-accessible with no privileged role, matching a real, wired code path (`AssetTransactors` includes `ERC20Transactor` on Asset Hub Westend). However, actually causing measurable loss requires the attacker (or another party) to use a non-standard ERC20 contract as the bridged asset, and requires a second party's funds/checking-account balance to be at stake for the discrepancy to translate into loss rather than just self-inflicted accounting noise.

### Recommendation
In `ERC20Transactor::withdraw_asset_with_surplus` and `deposit_asset_with_surplus`, read the ERC20 `balanceOf` of the checking account (and/or the source/beneficiary) immediately before and after the `bare_call` to `transfer`, and use the measured balance delta - not the requested `amount` - to determine the actual `AssetsInHolding` credit/debit and reported success. Alternatively, restrict which contracts can be onboarded as XCM-tradable ERC20 assets to those that have been vetted not to charge fees on transfer or misreport return values (allowlisting), similar to the recommendation given in the original report to vet token addresses before listing.

### Proof of Concept
No new PoC was executed; a full local FRAME/pallet-revive integration test could not be run in this session. The existing repository test `withdraw_and_deposit_erc20s` (`cumulus/parachains/runtimes/assets/asset-hub-westend/tests/tests.rs:1871-1935`) already demonstrates the exact code path (deploy an ERC20 via `pallet-revive`, `withdraw_asset`/`deposit_asset` through `ERC20Transactor`) using a compliant `MyToken` fixture; a deterministic reproduction of this finding would replace that fixture with a minimal fee-on-transfer Solidity ERC20 (`transfer` that moves `value * 90%` to `to` and burns/redirects the rest, but still returns `true`), then assert that `Revive::balance(erc20_address, &beneficiary)` (or the checking account's ERC20 balance) diverges from the `erc20_transfer_amount` credited in the XCM holding register - this is a straightforward code-level derivation from the two functions cited above, not something independently executed in this session. 	fn withdraw_asset_with_surplus(
		what: &Asset,
		who: &Location,
		_context: Option<&XcmContext>,
	) -> Result<(AssetsInHolding, Weight), XcmError> {
		tracing::trace!(
			target: "xcm::transactor::erc20::withdraw",
			?what, ?who,
		);
		let (asset_id, amount) = Matcher::matches_fungibles(what)?;
		let who = AccountIdConverter::convert_location(who)
			.ok_or(MatchError::AccountIdConversionFailed)?;
		// We need to map the 32 byte checking account to a 20 byte account.
		let checking_account_eth = T::AddressMapper::to_address(&TransfersCheckingAccount::get());
		let checking_address = Address::from(Into::<[u8; 20]>::into(checking_account_eth));
		let weight_limit = WeightLimit::get();
		// To withdraw, we actually transfer to the checking account.
		// We do this using the solidity ERC20 interface.
		let data =
			IERC20::transferCall { to: checking_address, value: EU256::from(amount) }.abi_encode();
		let ContractResult { result, weight_consumed, storage_deposit, .. } =
			pallet_revive::Pallet::<T>::bare_call(
				OriginFor::<T>::signed(who.clone()),
				asset_id,
				U256::zero(),
				TransactionLimits::WeightAndDeposit {
					weight_limit,
					deposit_limit: StorageDepositLimit::get(),
				},
				data,
				&ExecConfig::new_substrate_tx(),
			);
		// We need to return this surplus for the executor to allow refunding it.
		let surplus = weight_limit.saturating_sub(weight_consumed);
		tracing::trace!(target: "xcm::transactor::erc20::withdraw", ?weight_consumed, ?surplus, ?storage_deposit);
		if let Ok(return_value) = result {
			tracing::trace!(target: "xcm::transactor::erc20::withdraw", ?return_value, "Return value by withdraw_asset");
			if return_value.did_revert() {
				tracing::debug!(target: "xcm::transactor::erc20::withdraw", "ERC20 contract reverted");
				Err(XcmError::FailedToTransactAsset("ERC20 contract reverted"))
			} else {
				let is_success = IERC20::transferCall::abi_decode_returns_validate(&return_value.data).map_err(|error| {
					tracing::debug!(target: "xcm::transactor::erc20::withdraw", ?error, "ERC20 contract result couldn't decode");
					XcmError::FailedToTransactAsset("ERC20 contract result couldn't decode")
				})?;
				if is_success {
					tracing::trace!(target: "xcm::transactor::erc20::withdraw", "ERC20 contract was successful");
					Ok((
						AssetsInHolding::new_from_fungible_credit(
							what.id.clone(),
							Box::new(Erc20Credit(amount)),
						),
						surplus,
					))
				} else {
					tracing::debug!(target: "xcm::transactor::erc20::withdraw", "contract transfer failed");
					Err(XcmError::FailedToTransactAsset("ERC20 contract transfer failed"))
				}
			}
		} else {
			tracing::debug!(target: "xcm::transactor::erc20::withdraw", ?result, "Error");
			// This error could've been duplicate smart contract, out of gas, etc.
			// If the issue is gas, there's nothing the user can change in the XCM
			// that will make this work since there's a hardcoded gas limit.
			Err(XcmError::FailedToTransactAsset("ERC20 contract execution errored"))
		}
	}

	/// Deposits assets from holding to a beneficiary account via ERC20 transfer.
	///
	/// Note: This implementation only handles a single fungible asset at a time. The
	/// `AssetsInHolding` parameter is required by the `TransactAsset` trait, but callers
	/// should ensure only one asset is passed. If multiple assets are present, only the
	/// first fungible asset will be deposited and the rest will be silently ignored.
	/// The `defensive_assert!` helps catch misuse during development.
	fn deposit_asset_with_surplus(
		what: AssetsInHolding,
		who: &Location,
		_context: Option<&XcmContext>,
	) -> Result<Weight, (AssetsInHolding, XcmError)> {
		tracing::trace!(
			target: "xcm::transactor::erc20::deposit",
			?what, ?who,
		);
		defensive_assert!(what.len() == 1, "Trying to deposit more than one asset!");
		// Check we handle this asset.
		let maybe = what
			.fungible_assets_iter()
			.next()
			.and_then(|asset| Matcher::matches_fungibles(&asset).ok());
		let (asset_contract_id, amount) = match maybe {
			Some(inner) => inner,
			None => return Err((what, MatchError::AssetNotHandled.into())),
		};
		let who = match AccountIdConverter::convert_location(who) {
			Some(inner) => inner,
			None => return Err((what, MatchError::AccountIdConversionFailed.into())),
		};
		// We need to map the 32 byte beneficiary account to a 20 byte account.
		let eth_address = T::AddressMapper::to_address(&who);
		let address = Address::from(Into::<[u8; 20]>::into(eth_address));
		// To deposit, we actually transfer from the checking account to the beneficiary.
		// We do this using the solidity ERC20 interface.
		let data = IERC20::transferCall { to: address, value: EU256::from(amount) }.abi_encode();
		let weight_limit = WeightLimit::get();
		let ContractResult { result, weight_consumed, storage_deposit, .. } =
			pallet_revive::Pallet::<T>::bare_call(
				OriginFor::<T>::signed(TransfersCheckingAccount::get()),
				asset_contract_id,
				U256::zero(),
				TransactionLimits::WeightAndDeposit {
					weight_limit,
					deposit_limit: StorageDepositLimit::get(),
				},
				data,
				&ExecConfig::new_substrate_tx(),
			);
		// We need to return this surplus for the executor to allow refunding it.
		let surplus = weight_limit.saturating_sub(weight_consumed);
		tracing::trace!(target: "xcm::transactor::erc20::deposit", ?weight_consumed, ?surplus, ?storage_deposit);
		if let Ok(return_value) = result {
			tracing::trace!(target: "xcm::transactor::erc20::deposit", ?return_value, "Return value");
			if return_value.did_revert() {
				tracing::debug!(target: "xcm::transactor::erc20::deposit", "Contract reverted");
				Err((what, XcmError::FailedToTransactAsset("ERC20 contract reverted")))
			} else {
				match IERC20::transferCall::abi_decode_returns_validate(&return_value.data) {
					Ok(true) => {
						tracing::trace!(target: "xcm::transactor::erc20::deposit", "ERC20 contract was successful");
						Ok(surplus)
					},
					Ok(false) => {
						tracing::debug!(target: "xcm::transactor::erc20::deposit", "contract transfer failed");
						Err((
							what,
							XcmError::FailedToTransactAsset("ERC20 contract transfer failed"),
						))
					},
					Err(error) => {
						tracing::debug!(target: "xcm::transactor::erc20::deposit", ?error, "ERC20 contract result couldn't decode");
						Err((
							what,
							XcmError::FailedToTransactAsset(
								"ERC20 contract result couldn't decode",
							),
						))
					},
				}
			}
		} else {
			tracing::debug!(target: "xcm::transactor::erc20::deposit", ?result, "Error");
			// This error could've been duplicate smart contract, out of gas, etc.
			// If the issue is gas, there's nothing the user can change in the XCM
			// that will make this work since there's a hardcoded gas limit.
			Err((what, XcmError::FailedToTransactAsset("ERC20 contract execution errored")))
		}
	}
