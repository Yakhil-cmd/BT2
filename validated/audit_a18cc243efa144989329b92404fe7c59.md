### Title
`StatusHandler#process` looks up commits by SHA only (no repository scoping), letting a status webhook authenticated with attacker-owned repo A's `webhook_secret` create a `Status` and enqueue `ContinuousDeliveryJob` for victim stack B - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`PushHandler` and other handlers scope their target via `stacks` (derived from `payload.dig('repository', 'full_name')`), but `Shipit::Webhooks::Handlers::StatusHandler#process` instead does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [1](#0-0)  - a global, cross-repository/cross-stack lookup with no `stacks`/`repository_name` filter at all, unlike the base `Handler#stacks` helper meant for this purpose [2](#0-1) . Since `Status` creation triggers `after_commit :schedule_continuous_delivery`, which delegates to `commit.schedule_continuous_delivery` and can enqueue `ContinuousDeliveryJob.perform_later(stack)` for whatever stack owns the matched commit [3](#0-2) [4](#0-3) , a webhook verified only against repository A's secret can write data and enqueue a real evaluation job for stack B if any commit in Shipit's database happens to share that SHA.

### Finding Description
The broken binding: the organization/repository whose `webhook_secret` authorized the request (`repository_owner` from `params.dig('repository','owner','login')`, verified in `WebhooksController#verify_signature` against `Shipit.github(organization: repository_owner)`) must equal the organization/stack that is mutated and whose `ContinuousDeliveryJob` gets enqueued [5](#0-4) . It does not: `StatusHandler#process` never consults `repository_name`/`stacks` before acting, only `params.sha` [6](#0-5) .

Path: attacker owns repo A with a registered `GithubHook`/`webhook_secret` for repo A. Attacker POSTs to `/webhooks` with `X-Github-Event: status` and a body whose top-level `repository.owner.login` is attacker's own org (so `verify_signature` succeeds against A's secret) but whose `sha` field matches a commit SHA that exists in the `commits` table under victim stack B (e.g., a widely-shared base commit, a well-known open-source commit, a commit cherry-picked/rebased across forks, or a SHA the attacker learns from public GitHub activity on B's actual repo). `Commit.where(sha: params.sha)` is global and finds the commit row(s) regardless of which stack/repository they belong to, then calls `commit.create_status_from_github!(params)` on each match, creating a `Shipit::Status` row scoped to `commit.stack_id` = victim stack B's id [7](#0-6) . That `Status#create` fires `after_commit :schedule_continuous_delivery`, which calls `commit.schedule_continuous_delivery`; if stack B has `continuous_deployment?` true and the commit is `deployable?` and stack is `deployable?`, `ContinuousDeliveryJob.set(wait: RECENT_COMMIT_THRESHOLD).perform_later(stack)` is enqueued for stack B [4](#0-3) .

Why existing guards fail: `verify_signature` only checks that the *body's declared* `repository.owner.login`/`organization.login` matches a valid GitHub org's secret - it authenticates "a request from org A", not "a request about stack B" [5](#0-4) . `ExplicitParameters` schema for `StatusHandler` only validates types/presence of `sha`, `state`, etc., not repository ownership [8](#0-7) . `drop_unhandled_event` only checks event name is registered. There is no equivalent of the `stacks` scoping that `PushHandler` correctly applies via `Repository.from_github_repo_name(repository_name)` [9](#0-8) .

### Impact Explanation
This lets an attacker write a `Status` row for a stack/repository they never authenticated against, and proactively enqueue `ContinuousDeliveryJob` for that victim stack, which - if the stack has `continuous_deployment: true` and the commit is otherwise deployable - triggers `Stack#trigger_continuous_delivery` and ultimately `trigger_deploy`, i.e., an unauthorized deploy trigger cycle for a repository outside the attacker's authorization scope. This matches "a payload for one repository mutating another's stack/commit" and "an unauthorized deploy" impact categories. The blast radius is bounded by SHA-collision feasibility: the attack requires a commit SHA that already exists as a `Commit` row for stack B in Shipit's DB (Git SHAs are effectively impossible to forge/collide, so the attacker needs the *actual* SHA of a real commit tracked on stack B, e.g. by observing B's public repository activity, GitHub UI, or existing Shipit UI, not merely guessing). Given that constraint, it is repeatable against any known commit on any stack whose SHA the attacker can learn, and could be automated across many known SHAs.

### Likelihood Explanation
Preconditions: (1) attacker must control/own a GitHub repository with a Shipit `GithubHook` registered (any user can create such a repo/webhook against their own org if Shipit onboarding allows self-service hook registration, or the attacker just needs valid signature for *some* organization Shipit trusts - note the webhook secret must correspond to an org Shipit already recognizes via `Shipit.github(organization: repository_owner)`, meaning the attacker needs an org where they legitimately have a `webhook_secret`, i.e., their own tracked repo A); (2) attacker must know an actual SHA of a commit that exists in stack B's `commits` table (feasible via public GitHub history, Shipit's own public stack pages if readable, or coincidence of shared commits between forks/mirrors); (3) stack B must have `continuous_deployment` enabled and be otherwise `deployable?` for the job to have real deploy effect (absent that, only the spurious `Status` row and job enqueue happen, with `ContinuousDeliveryJob#perform` itself being a no-op due to `trigger_continuous_delivery`'s guard). Attacker cost is a single crafted HTTP POST to `/webhooks`, fully repeatable and scriptable.

### Recommendation
Scope `StatusHandler#process` by the payload's repository, mirroring the base `stacks` helper: resolve the stack(s) via `Repository.from_github_repo_name(repository_name)` (or equivalent) and constrain `Commit.where(sha: params.sha, stack_id: stacks.select(:id))` before calling `create_status_from_github!`, so a webhook can only affect commits belonging to the repository asserted (and signature-verified) in that same payload.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb (conceptual)
test "status webhook from repo A does not enqueue ContinuousDeliveryJob for stack B sharing a commit sha" do
  stack_b = shipit_stacks(:cyclimse) # victim stack, continuous_deployment: true
  stack_b.update!(continuous_deployment: true)
  shared_sha = "deadbeef" * 5
  commit_b = stack_b.commits.create!(sha: shared_sha, message: "m", authored_at: Time.now, committed_at: Time.now)

  payload = {
    "sha" => shared_sha,
    "state" => "success",
    "branches" => [{ "name" => stack_b.branch }],
    "repository" => { "full_name" => "attacker/repo-a", "owner" => { "login" => "attacker-org" } }
  }

  # Only asserts attacker-org's webhook_secret verified the request (simulated by stubbing verify_webhook_signature true)
  assert_no_enqueued_jobs only: ContinuousDeliveryJob do
    Shipit::Webhooks::Handlers::StatusHandler.call(payload)
  end
  # currently FAILS: ContinuousDeliveryJob IS enqueued for stack_b despite the payload asserting repo "attacker/repo-a"
end
```
Binding to check: `repository_owner` used in `verify_signature` (= `"attacker-org"`) vs. `stack_b.repository.owner` (`≠ "attacker-org"`) - they diverge, yet `ContinuousDeliveryJob.perform_later(stack_b)` is still enqueued, proving the authorization/action binding is broken.
