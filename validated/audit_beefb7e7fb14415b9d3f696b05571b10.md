### Title
Webhook signature is verified against the wrong organisation's secret, allowing cross-organisation status/push forgery - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organisation's `webhook_secret` to use for HMAC verification based on a field (`repository.owner.login`, falling back to `organization.login`) taken from the very same unauthenticated JSON body it is trying to validate. The handlers that actually act on the payload (`PushHandler`, `StatusHandler`, `CheckSuiteHandler`, etc.) instead resolve the target `Repository`/`Stack` from a *different* field of the same body: `repository.full_name`. Because these two fields are never cross-checked, an attacker who controls one organisation configured on a multi-org Shipit instance (and therefore legitimately knows that organisation's `webhook_secret`) can forge a signature that Shipit accepts, while pointing `repository.full_name` at a repository belonging to a completely different organisation on the same install.

### Finding Description
In `verify_signature`, the org used to fetch the signing secret is derived from attacker-controlled JSON, before the signature has been proven authentic for that data: [1](#0-0) [2](#0-1) 

`Shipit.github(organization:)` looks up per-organisation config (`webhook_secret`, `private_key`, etc.) using exactly that attacker-supplied `organization` value: [3](#0-2) 

Shipit explicitly supports hosting multiple GitHub organisations from one instance, each with its own `webhook_secret` (documented and fixture-backed): [4](#0-3) [5](#0-4) 

Once the signature check passes, `WebhooksController#create` dispatches the same raw payload to the event handler: [6](#0-5) 

The base `Handler` resolves the target repository/stack for the event from `payload.dig('repository', 'full_name')` — a completely separate field from the one used to pick the verifying secret: [7](#0-6) [8](#0-7) 

`PushHandler` uses this repository resolution to trigger a `GithubSyncJob` for every non-archived stack on the matched repo: [9](#0-8) 

`StatusHandler` writes an arbitrary CI status (`state`, `context`, `description`, `target_url`) onto any `Commit` row matching an attacker-chosen `sha`, with no repository-affinity check on the commit at all: [10](#0-9) 

The equality the design intends to hold is:
`organisation whose webhook_secret authenticated the request == organisation that owns the repository the handler acts on`

The bug breaks this into two independent, attacker-controlled inputs from the same unauthenticated JSON body:
- Before: `repository.owner.login` (secret selection) is implicitly trusted to equal `repository.full_name`'s owner (repository selection), because in a legitimate GitHub-originated webhook these two always describe the same repo.
- After: an attacker who administers OrgA (a real org configured on the Shipit instance, so they legitimately possess OrgA's `webhook_secret`) can sign a payload with OrgA's secret while setting `repository.full_name = "OrgB/victim-repo"`, `repository.owner.login = "OrgA"`. The signature check passes (real OrgA secret, real OrgA HMAC), but the handler acts on OrgB's repository/commits.

### Impact Explanation
This lets an unprivileged outsider (someone with push/webhook access to only their own, unrelated GitHub org hosted on the same Shipit instance) forge webhook events against any other organisation's stacks without ever knowing that organisation's `webhook_secret`:
- Via `StatusHandler`, they can write a fabricated `success` CI status onto any commit SHA of a victim repository, which can satisfy `ci.require` gating and enable an unauthorized deploy of a commit whose CI never actually passed — this maps to the "unauthorized deploy" Critical impact bucket.
- Via `PushHandler`, they can force `GithubSyncJob` execution against a victim stack's branch on demand.

This is a direct analog of the reported bug class: a check is performed against one field (`sqrtPriceLimitD18`-gated spend / here, `repository.owner.login`), while the actual effect is driven by a different, uncovered field (actual ETH spent / here, `repository.full_name`), so the enforced binding never actually holds.

### Likelihood Explanation
Requires only that the Shipit deployment be configured for multiple GitHub organisations (a documented, supported configuration) and that the attacker controls (owns/administers) at least one of those organisations well enough to know its `webhook_secret` and send a webhook to the shared `/webhooks` endpoint — no Shipit account, `ApiClient` token, or victim-org secret is needed.

### Recommendation
After selecting the GitHub App/secret by `repository_owner`/`organization.login`, verify that this same value matches the owner segment of `repository.full_name` (and of `organization.login` when present) before dispatching to handlers; reject the webhook if they disagree.

### Proof of Concept
1. Shipit is configured with two orgs, `OrgA` and `OrgB`, each with distinct `webhook_secret`s (per `docs/setup.md` multi-org config).
2. Attacker administers a GitHub App installed on `OrgA` and therefore knows `OrgA`'s `webhook_secret`.
3. Attacker crafts a `status` (or `push`) event JSON body with:
   - `organization.login` / `repository.owner.login` = `"OrgA"`
   - `repository.full_name` = `"OrgB/victim-repo"`
   - `sha` = a real commit SHA of an OrgB stack, `state` = `"success"`
4. Attacker computes `X-Hub-Signature: sha1=HMAC(OrgA_webhook_secret, body)` and POSTs to `/webhooks`.
5. `WebhooksController#verify_signature` calls `Shipit.github(organization: "OrgA")` and the signature verifies successfully.
6. `Webhooks.for_event('status').each { |handler| handler.call(params) }` runs `StatusHandler#process`, which finds `Commit.where(sha: ...)` — a commit belonging to `OrgB`'s repository — and writes the forged status via `commit.create_status_from_github!(params)`, with no cross-check that `OrgA` should not be permitted to attest CI state for `OrgB`'s commits.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

module Shipit
  module Webhooks
    module Handlers
      class StatusHandler < Handler
        params do
          requires :sha, String
          requires :state, String
          accepts :description, String
          accepts :target_url, String
          accepts :context, String
          accepts :created_at, String

          accepts :branches, Array do
            requires :name, String
          end
        end

        def process
          Commit.where(sha: params.sha).each do |commit|
            commit.create_status_from_github!(params)
          end
        end
      end
