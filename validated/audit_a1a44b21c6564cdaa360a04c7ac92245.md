### Title
Cross-repository CI status forgery via unscoped `Commit.where(sha:)` lookup in `StatusHandler#process` — ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` looks up commits to attach a forged status to using only the raw `sha` string, with **no scoping to the repository that sent the webhook**. Unlike every other handler in the codebase, it never calls `Repository.from_github_repo_name(params.repository.full_name)` to constrain the lookup, so a status event legitimately signed for repository A can write a `Status` record onto a `Commit` belonging to an unrelated stack/repository B whenever the two share the same SHA1 (e.g. via a public fork). This directly satisfies `Commit#deployable?`, which never consults `release_status` or repository identity, and schedules `Stack#trigger_continuous_delivery` for the victim stack.

### Finding Description
Broken binding, stated explicitly: the intended invariant is `commit.stack.repository.full_name == payload['repository']['full_name']` for every `Status` written by a webhook. The actual code enforces no such equality.

Path:
- `WebhooksController#create` dispatches the parsed JSON to `Shipit::Webhooks.for_event('status')`, i.e. `StatusHandler.call(params)` [1](#0-0)  after `verify_signature`, which validates the HMAC against `Shipit.github(organization: repository_owner)` — a signature check that is per-organization, not per-repository [2](#0-1) .
- `StatusHandler`'s `params` schema requires only `sha`, `state`, `description`, `target_url`, `context`, `created_at`, `branches` — it does not require/parse a `repository` block at all, and `process` does:
```
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
``` [3](#0-2) 
This is a global, unscoped lookup across **every stack in the installation** that happens to have a commit row with that SHA. Contrast this with every other handler (`PushHandler`, `PullRequest::OpenedHandler`, `ClosedHandler`, `LabeledHandler`, etc.), which all resolve `repository = Shipit::Repository.from_github_repo_name(params.repository.full_name)` before touching any model, and with the base `Handler#stacks` helper that does the same scoping [4](#0-3) [5](#0-4) .

- `Commit#create_status_from_github!` writes a `Status` row scoped to `stack_id` (the commit's own stack, whichever stack happened to match the sha) via `statuses.replicate_from_github!` [6](#0-5) , and `Status` fires `after_commit :schedule_continuous_delivery` on create [7](#0-6) .
- `Commit#deployable?` is exactly `!locked? && (stack.ignore_ci? || (success? && !blocked?))` — no term for `release_status?`, `last_release_status`, or repository identity [8](#0-7) . `create_release_status!` is a completely separate code path guarded by `stack.release_status?` and is never invoked here [9](#0-8) . This confirms the question's framing: the forged CI status alone, with zero interaction with `release_statuses`, flips `deployable?` to `true`.

Exploit flow: attacker forks (or otherwise obtains write access to) a public repository whose commits share SHA1s with a victim stack tracked by Shipit (forking preserves commit hashes by git's content-addressing). The attacker triggers GitHub to send a `status` webhook for their own repo/commit (e.g. via `POST /repos/{attacker}/{fork}/statuses/{sha}` on a SHA that also exists in the victim's history) with `state: success`. GitHub signs this webhook legitimately for the attacker's own organization, so `verify_signature` passes. `StatusHandler#process` then finds **every** `Commit` row across the entire database matching that SHA — including the victim's — and creates a `success` `Status` on it, regardless of which repository actually owns that commit's stack.

Existing guards (`verify_signature`, `drop_unhandled_event`, `ExplicitParameters` schema, model validations) do not catch this because they operate at the transport/organization layer, not at the model-lookup layer where the missing repository scope actually lives.

### Impact Explanation
A forged/legitimate-but-misdirected `success` status is written directly onto a victim commit that the attacker never had CI access to, satisfying `Commit#deployable?` for that stack. Combined with `Status#schedule_continuous_delivery` → `Stack#trigger_continuous_delivery`, this can trigger an **unauthorized deploy** on a stack/repository the attacker does not control, matching the Critical category "a payload for one repository mutating another's stack, commit, task" and "an unauthorized deploy". This is repeatable against any victim stack whose commit SHAs the attacker can reproduce (public repos, or any repo the attacker can fork/clone), and the blast radius spans every stack in the Shipit instance since the lookup is entirely global.

### Likelihood Explanation
Preconditions: the attacker needs (a) a repository they control that is webhook-emitting into the same Shipit instance (satisfied per the given threat model — "emit webhooks from a repository they own"), and (b) a target commit SHA that is shared between their own repo and the victim's tracked stack — trivially achieved by forking a public victim repository, since git SHAs are content-derived and identical between origin and fork. No secrets, sessions, or privileged roles are required. Cost is a single GitHub API call or webhook trigger from an owned repository; the attack is fully repeatable against any repository whose commits can be reproduced by the attacker.

### Recommendation
Scope the commit lookup in `StatusHandler#process` to the repository named in the webhook payload, mirroring every other handler: parse `requires :repository { requires :full_name, String }` in the `params` block, resolve `repository = Shipit::Repository.from_github_repo_name(params.repository.full_name)`, and restrict the query to `repository.stacks.flat_map(&:commits).where(sha: params.sha)` (or join through `stacks: { repository_id: repository.id }`) before calling `create_status_from_github!`.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb
require 'test_helper'

module Shipit
  module Webhooks
    module Handlers
      class StatusHandlerCrossRepoTest < ActiveSupport::TestCase
        test "status webhook from repo A must not create a Status for a commit owned by repo B" do
          victim_repo  = shipit_repositories(:cyclimse) # some stack unrelated to attacker
          victim_stack = victim_repo.stacks.first
          shared_sha   = 'a' * 40
          victim_commit = victim_stack.commits.create!(sha: shared_sha, message: 'victim commit',
                                                         author: Shipit::AnonymousUser.new,
                                                         committer: Shipit::AnonymousUser.new,
                                                         authored_at: Time.now, committed_at: Time.now)

          forged_payload = {
            'sha' => shared_sha,
            'state' => 'success',
            'context' => 'ci/attacker',
            'repository' => { 'full_name' => 'attacker/unrelated-fork' } # attacker's own repo
          }

          assert_no_difference -> { victim_commit.statuses.count } do
            StatusHandler.call(forged_payload)
          end

          victim_commit.reload
          refute_predicate victim_commit, :deployable?
        end
      end
    end
  end
end
```
This test asserts the binding `commit.stack.repository.full_name == payload['repository']['full_name']` holds before a `Status` is written. On the current code, the `assert_no_difference` fails (a `Status` **is** created for the victim commit because the lookup is unscoped), and `victim_commit.deployable?` becomes `true` purely from the forged status, with `victim_commit.release_statuses` left empty throughout — demonstrating the standalone bypass and the missing repository-scope guard.
