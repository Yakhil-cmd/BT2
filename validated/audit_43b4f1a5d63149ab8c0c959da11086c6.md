### Title
Webhook `repository.owner.login` used to select the signing organization is decoupled from `repository.full_name` used to select the target Stack, allowing organization/repository binding confusion - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` authenticates an inbound webhook by looking up a GitHub App/secret keyed on `repository.owner.login` (or `organization.login`) taken from the JSON body, while the handler that actually acts on the webhook (`Handler#stacks`) resolves the target `Repository`/`Stack` using an entirely separate field, `repository.full_name`, from the same body. [1](#0-0) [2](#0-1) [3](#0-2)  Nothing ties the value used to pick the "authenticating organization" to the value used to pick the "repository being written to," which is exactly the Putty-style trust-binding gap described in the report (a field acted on but never actually covered by the verification the code believes it performed).

### Finding Description
`verify_signature` fetches the GitHub App configuration for `repository_owner` and calls `verify_webhook_signature`: [1](#0-0) . `GithubApp#verify_webhook_signature` explicitly short-circuits to `true` when no `webhook_secret` is configured for that organization: [4](#0-3) . The webhook secret is documented as optional per-organization configuration (`docs/setup.md`), so a multi-organization Shipit deployment (a feature explicitly added, see CHANGELOG "Support multiple GitHub organisations") can legitimately have one organization configured without a secret.

Once `verify_signature` passes (either via a real secret match or via the no-secret bypass), the actual event dispatch never re-checks that the verified organization matches the repository being acted upon. `Handler#stacks` independently derives the target `Repository` from `payload.dig('repository', 'full_name')`: [3](#0-2) , and `PushHandler#process` uses that resolved `stacks` collection to call `stack.sync_github(expected_head_sha: params.after)` on every matching, non-archived stack: [5](#0-4) .

Because the JSON body is entirely attacker-authored, an attacker can set `repository.owner.login`/`organization.login` to an organization whose webhook secret check they can satisfy (e.g., an organization the Shipit operator configured without a secret, satisfying `return true unless webhook_secret`), while setting `repository.full_name` to any other organization/repository that already has a `Stack` configured in the same Shipit instance. The signature check "authenticates" the first field; the action is performed against the second, unrelated field. This is the direct analog of the Putty bug: the value that is actually acted upon (`repository.full_name`, i.e., which `Stack` gets synced) is never covered by the check that the code relies on for trust (`repository_owner`'s secret).

### Impact Explanation
An unprivileged, unauthenticated network attacker can force a `GithubSyncJob`/`sync_github` call (and the resulting commit sync / continuous-deployment trigger path) against any `Stack` in the instance, as long as the Shipit deployment has at least one configured organization without a webhook secret (a state the documentation presents as a normal, optional configuration). This crosses a repository trust boundary: the organization whose credentials were "verified" is not the organization whose repository/stack is acted upon, enabling cross-repository/cross-organization webhook forgery and potentially forcing an out-of-band commit sync (and, if `continuous_deployment` is enabled on the targeted stack, an unauthorized deploy trigger) without ever holding a Shipit session, API token, or the target organization's webhook secret.

### Likelihood Explanation
Likelihood depends on operational configuration: it requires at least one organization in the Shipit instance to have no `webhook_secret` set, which the setup documentation presents as optional and therefore plausible in real deployments. Given that condition, exploitation requires only an unauthenticated POST to `/webhooks` with a crafted JSON body — no credentials, tokens, or secrets of any kind are needed by the attacker.

### Recommendation
Bind the two identities together before acting: after resolving the `Repository`/`Stack` from `repository.full_name`, verify that its `owner`/organization matches the organization whose secret validated the signature (`repository_owner`), and reject the webhook if they differ. Additionally, reconsider allowing any configured organization to omit a `webhook_secret`, since that organization becomes a skeleton key for signature verification across the whole multi-organization instance.

### Proof of Concept
1. Deploy Shipit configured for two organizations, `org-safe` (webhook secret configured) and `org-open` (no webhook secret configured, per the documented "optional" setting).
2. Attacker POSTs to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker chosen sha>",
  "repository": { "full_name": "org-safe/private-repo", "owner": { "login": "org-open" } }
}
```
3. `WebhooksController#verify_signature` computes `repository_owner = "org-open"`, fetches `Shipit.github(organization: "org-open")`, and since it has no `webhook_secret`, `verify_webhook_signature` returns `true` unconditionally regardless of the (even absent) `X-Hub-Signature` header. [6](#0-5) 
4. `PushHandler` then resolves stacks via `repository.full_name = "org-safe/private-repo"` and calls `sync_github` on that stack, which the attacker never authenticated against. [3](#0-2) [5](#0-4) 

Note: I was unable to fully trace `Stack#sync_github`'s downstream behavior (whether it immediately triggers a deploy when `continuous_deployment` is enabled, or only updates commit records ahead of the periodic `schedule_continuous_delivery` cron) within the remaining investigation budget, so the precise severity of the downstream effect (forced early sync vs. an actual unauthorized deploy) could not be fully confirmed from the indexed code and should be verified directly against `app/models/shipit/stack.rb`'s `sync_github` implementation.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
