Confirmed: `Status#schedule_continuous_delivery` at [1](#0-0)  fires on every created `Status` record, meaning a forged commit status can advance continuous delivery for any commit whose SHA it matches, regardless of which stack/org it belongs to.

### Title
Webhook signature verification keys the trusted GitHub App on `repository.owner.login`, but handlers act on unrelated payload fields (`repository.full_name`, unscoped `sha`), letting a low-trust org's blank/absent webhook secret authorize writes against any other stack - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which `GitHubApp` (and thus which `webhook_secret`) to validate an inbound webhook against purely from an attacker-controlled JSON field, `repository.owner.login` (or `organization.login`) [2](#0-1) , [3](#0-2) . `GitHubApp#verify_webhook_signature` returns `true` unconditionally whenever that org's configured `webhook_secret` is blank: `return true unless webhook_secret` [4](#0-3) . The webhook secret is documented as *optional* per app/org [5](#0-4) , so a multi-org Shipit deployment can legitimately have one organization configured without a secret while others have one.

Once `verify_signature` passes, `WebhooksController#create` dispatches the raw JSON to handlers [6](#0-5) , which resolve their target using **different** payload fields than the one used for authentication: `Handler#repository_name` reads `payload.dig('repository', 'full_name')` [7](#0-6) , and `StatusHandler#process` doesn't even scope by repository — it matches `Commit.where(sha: params.sha)` across the entire instance [8](#0-7) .

### Finding Description
The equality that should hold but is never checked is:
`organization_that_authenticated(repository.owner.login) == organization_owning(repository.full_name / commit.sha)`

Concretely, in a multi-org deployment (`docs/setup.md` "Using Multiple Github Applications" [9](#0-8) ), suppose org `victim-org` has a `webhook_secret` set, while org `low-trust-org` (also installed/configured, e.g. for a sandbox or secondary team) has none. An attacker with no knowledge of any secret can:

1. Craft a POST to `/webhooks` with `X-Github-Event: push` (or `status`), and a JSON body where `repository.owner.login = "low-trust-org"` (selects the app with blank secret) but `repository.full_name = "victim-org/production-app"` (targets a real tracked repository/stack), or for the `status` event, simply set `sha` to a known commit SHA belonging to `victim-org`'s stack.
2. `verify_signature` calls `Shipit.github(organization: "low-trust-org")`, whose `verify_webhook_signature` returns `true` regardless of the `X-Hub-Signature` header, because `webhook_secret` is blank for that org [4](#0-3) .
3. `create` then invokes `PushHandler`/`StatusHandler` with the full, attacker-controlled payload — these never re-check that `repository.full_name`/`sha` actually belongs to `low-trust-org` [10](#0-9) , [8](#0-7) .
4. For the `status` handler, `Commit#create_status_from_github!` creates a `Status`, whose `after_commit` callback `schedule_continuous_delivery` unconditionally fires for that commit [1](#0-0) , potentially advancing continuous deployment of `victim-org`'s stack using a forged "success" status the attacker was never entitled to send.

This is the same class of bug as the report: a security-critical binding (which credential authorizes which action) is established once (per-org secret check) but never re-validated against the field the code actually acts on (repository/commit ownership), so a stale/absent trust anchor on one path silently authorizes actions on an unrelated, more privileged path.

### Impact Explanation
This crosses the "unauthorized deploy" / cross-repository-write bar in the rules: an attacker with zero valid credentials can inject synthetic CI status or push-sync events for a stack belonging to a different, higher-trust GitHub organization than the one whose (weak/absent) secret gated the request, by exploiting the mismatch between the `verify_signature` selection key and the handler's action key.

### Likelihood Explanation
Requires: (a) the operator running a multi-org Shipit configuration (documented, supported feature) where at least one configured org has no `webhook_secret` (documented as optional), and (b) knowledge of the target repository's `full_name` or a tracked commit SHA (public information visible in the target's GitHub repo/PRs). No secret, session, or API token is needed. Likelihood is moderate — contingent on that specific but documented and plausible multi-tenant configuration pattern.

### Recommendation
Bind the authentication decision to the same identity the handler acts on: resolve the target `Repository`/`Stack` first from `repository.full_name`, determine which organization actually owns it in Shipit's own records, and verify the webhook signature using that organization's configured app/secret — never let an attacker-supplied `repository.owner.login` field pick an unrelated, weaker-secret app. Additionally, never treat a blank `webhook_secret` as automatic pass-through in multi-org configurations; require an explicit secret per configured organization, or scope `StatusHandler`'s `Commit.where(sha:)` lookup by the repository asserted in the same verified payload.

### Proof of Concept
1. Configure two orgs in `config/secrets.yml`: `victim-org` (with a real `webhook_secret`) and `attacker-controlled-org` (webhook_secret left blank, as permitted by `docs/setup.md`).
2. As an unauthenticated attacker, POST to `/webhooks` with header `X-Github-Event: status` and no valid `X-Hub-Signature`, body:
```json
{
  "sha": "<victim-org tracked commit sha>",
  "state": "success",
  "repository": { "owner": { "login": "attacker-controlled-org" }, "full_name": "attacker-controlled-org/whatever" }
}
```
3. `verify_signature` looks up `Shipit.github(organization: "attacker-controlled-org")`; since its `webhook_secret` is blank, `verify_webhook_signature` returns `true` [4](#0-3)  and the request is accepted with `head(:ok)`.
4. `StatusHandler#process` runs `Commit.where(sha: params.sha)` — matching `victim-org`'s commit regardless of the `repository` fields — and creates a `success` `Status`, triggering `schedule_continuous_delivery` [8](#0-7) , [1](#0-0) .

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
