### Title
Webhook signature bypass via unauthenticated organization selection allows forged GitHub webhooks against any configured repository - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App / webhook secret used to validate a request based on `repository_owner`, a value read straight out of the unauthenticated JSON payload, and `GitHubApp#verify_webhook_signature` unconditionally trusts any request when that app's `webhook_secret` is unset. Because the field used to pick "which org's secret validates this request" is different from the field the event handlers use to pick "which repository/stack gets acted on," an attacker can pick an organization with no configured `webhook_secret` to skip verification entirely, then set `repository.full_name` to any other repository/organization configured in the same Shipit instance to drive real state changes (sync commits, post commit statuses, etc.) for that other repo.

### Finding Description
`verify_signature` computes the app used for verification from attacker-controlled JSON: [1](#0-0) [2](#0-1) 

`repository_owner` is taken from `params.dig('repository', 'owner', 'login')` (or `organization.login`) — both fully attacker-supplied fields, not covered by any signature yet at the time they are read.

`GitHubApp#verify_webhook_signature` treats an absent `webhook_secret` as "always valid": [3](#0-2) 

`Shipit.github_app_config` resolves per-organization config for multi-org installs by simply downcasing and looking up the organization key supplied by the caller (i.e., ultimately by the attacker via `repository_owner`): [4](#0-3) 

Every documented multi-org example ships with `webhook_secret: # nil`, i.e. optional per-org secrets: [5](#0-4) [6](#0-5) 

Once verification is bypassed, the actual event handlers select the target `Stack`/`Repository` using a *different* payload field, `repository.full_name`, with no cross-check against `repository.owner.login`/`organization.login` used above: [7](#0-6) 

This is the exact binding break called out in scope: "an organization that authenticated versus the repository that is written." The organization whose (absent) secret was checked is not required to be the same organization/repository the handler subsequently mutates.

### Impact Explanation
An attacker who knows (or brute-force-guesses) that any one organization configured in a multi-GitHub-App Shipit deployment has no `webhook_secret` set can send a completely unsigned/unauthenticated `POST /webhooks` request that:
- sets `repository.owner.login` (or `organization.login`) to that unsecured org so `verify_webhook_signature` returns `true` unconditionally, and
- sets `repository.full_name` to any *other* repository tracked by that same Shipit instance (e.g. a highly privileged production repo secured with a real secret).

The forged event is then processed as authentic for the target repository: e.g. a forged `push` event queues `Stack#sync_github`/`GithubSyncJob`, and a forged `status` event lets the attacker mark arbitrary commits as passing CI via `Commit#create_status_from_github!`. Since Shipit's continuous-deployment/merge-queue logic and required-status checks in `shipit.yml` rely on these `Commit::Status` rows being trustworthy GitHub-origin data, an attacker can use this to defeat CI gating and trigger an unauthorized deploy or merge on a repository they have no legitimate access to — meeting the "unauthorized deploy" / "cross-repository writes" bar for High/Critical impact.

### Likelihood Explanation
Likelihood depends on the operator running the multi-organization GitHub App configuration (`github: <org>: ...` schema) documented in `docs/setup.md`, and at least one configured organization having an unset `webhook_secret`, which the shipped example configs treat as the default ("Optional")/nil. In that (common, documented) configuration, exploitation requires no credentials at all — just knowledge of the org name and standard JSON crafting — making it trivially reachable by an unprivileged, unauthenticated attacker who can reach `/webhooks`.

### Recommendation
- Require `webhook_secret` to be present for every configured organization (fail closed instead of `return true unless webhook_secret`), or at minimum never allow an unsigned request to affect a *different* organization's data.
- Bind the organization used for signature verification to the same value used to resolve the target repository/stack, and reject requests where `repository.full_name`'s owner does not match the verified organization.
- Consider validating using GitHub's `X-Hub-Signature-256` and rejecting `sha1`-only signatures as an additional hardening step (not itself the primary bug here, but related).

### Proof of Concept
1. Deploy Shipit with the multi-org GitHub App schema, e.g. `OrgA` (no `webhook_secret` set) and `OrgB` (has `webhook_secret`, tracks a real Shipit stack/repository).
2. Send:
```
POST /webhooks
X-Github-Event: status
Content-Type: application/json

{
  "sha": "<sha of a real commit on OrgB/important-repo>",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/important-repo" }
}
```
No `X-Hub-Signature` header is required to pass validation, because `WebhooksController#verify_signature` resolves `Shipit.github(organization: "OrgA")`, and `GitHubApp#verify_webhook_signature` returns `true` unconditionally since OrgA has no `webhook_secret`.
3. `StatusHandler#process` looks up `Commit.where(sha: params.sha)` — a commit belonging to `OrgB/important-repo` (resolved independently by `full_name` in `Handler#repository_name`) — and creates a passing status for it, potentially satisfying `ci.require` and enabling an unauthorized deploy/merge on `OrgB`'s stack.

```ruby
      verified = github_app.verify_webhook_signature(
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
