### Title
Cross-organization webhook forgery via signature/repository binding mismatch - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects the GitHub App / `webhook_secret` used to HMAC-verify an incoming webhook based on `repository.owner.login` (or `organization.login`) taken from the **unverified** JSON body, then verifies the signature against that secret. Every downstream `Shipit::Webhooks::Handlers::Handler` subclass, however, resolves the repository/stack to act on using a *different, independently attacker-controlled* field of the same unverified body: `payload.dig('repository', 'full_name')`. Nothing ties these two fields together, so a valid signature computed with organization A's secret can be replayed with a `repository.full_name` pointing at organization B's repository.

### Finding Description
The controller flow is:
1. `repository_owner` is read straight from the JSON body before any verification: [1](#0-0) 
2. That value selects which multi-tenant GitHub App config (and therefore which `webhook_secret`) is used to verify the HMAC over the raw body: [2](#0-1) 
3. Once the signature check passes, the handler for the event is invoked with the full (still attacker-authored) JSON body: [3](#0-2) 
4. Every handler picks the stack/repository to mutate using `repository.full_name`, a field completely independent of the `repository.owner.login`/`organization.login` field that was used to choose the verifying secret: [4](#0-3) 

The engine's own multi-tenant config format confirms per-organization `webhook_secret`s are expected and each organization's admin supplies/knows their own secret: [5](#0-4) 

The bug class is an exact analog of the reported weak Fiat-Shamir issue: the "challenge" (HMAC verification) is bound to one piece of data (`repository.owner.login`), while the actual state-changing computation (`PushHandler#process`, `MembershipHandler#process`, `StatusHandler#process`, etc.) is driven by an entirely different, unauthenticated field (`repository.full_name`, `organization.login` used again unchecked inside `MembershipHandler`, `sha`/`state` in `StatusHandler`). The binding "the organization that authenticated == the repository that is written" is broken:

- Before the PR (current code): `verify(secret[owner_A]) == true` says nothing about `full_name`, so `full_name` can be `orgB/anything`.
- Equality that should hold but doesn't: `repository_owner used to pick secret == owner(repository.full_name used by handler)`.

Any organization onboarded to a shared/multi-tenant Shipit instance (i.e., any org whose admin legitimately knows their own `webhook_secret`, as documented in `docs/setup.md`) can therefore forge webhooks that are accepted as authentic for **any other organization's repository** hosted on the same Shipit instance, by simply setting `repository.full_name` (and, for `MembershipHandler`, `organization.login`/`team.*`) to point at the victim org while keeping `repository.owner.login` set to their own org so the correct (self-known) secret is used for the HMAC.

### Impact Explanation
This crosses the "cross-repository writes" / unauthenticated-write boundary called out as Critical impact:
- `PushHandler` triggers `stack.sync_github(expected_head_sha:)` for any stack matched by `full_name`, letting the forging org drive commit sync for a victim org's stack.
- `MembershipHandler` creates/mutates `Team` and `Membership` records (`Team.add_member`) tied to `Shipit.github_teams`, which directly feeds `User#authorized?` — i.e. an attacker-forged `membership` webhook can grant an attacker-controlled GitHub user membership in a `Team` object that the deployment treats as an authorization team, escalating into `Shipit.github_teams` authorization for a completely unrelated organization.
- `StatusHandler` and other handlers can write commit statuses onto any commit by `sha`, independent of which org "authenticated."

This satisfies both the Critical bar (cross-repository writes / unauthorized deploy prerequisite via forced sync) and the High bar (escalation into `Shipit.github_teams` authorization).

### Likelihood Explanation
Requires only that the attacker's own organization is legitimately onboarded to the same multi-tenant Shipit deployment (a normal, documented configuration, not a privileged Shipit account, API token, or GitHub org write access to the victim). The attacker needs no access to the victim organization at all — only knowledge of their own org's `webhook_secret`, which they configured themselves per `docs/setup.md`. No GitHub App private key, `api_clients_secret`, or Shipit session is needed, keeping this within scope as an unprivileged-attacker analog.

### Recommendation
After signature verification, re-derive and cross-check that the organization/owner used to select the verifying secret matches the owner embedded in every field the handlers subsequently trust (`repository.full_name`, `organization.login`, `team.organization`, etc.), rejecting the webhook if they diverge. Alternatively, bind the webhook secret lookup and the repository resolution to the same canonical, single source of truth (e.g., resolve the `Repository`/`Stack` record first via a trusted mapping keyed by the verified organization, rather than trusting `full_name` verbatim from the payload).

### Proof of Concept
1. Organization `orgA` is a legitimate tenant on a shared Shipit instance and knows its own `webhook_secret` (`SECRET_A`), as configured in `config/secrets.yml` per `docs/setup.md`.
2. Attacker (any member of `orgA` able to compute HMACs, e.g., by replaying `orgA`'s real GitHub webhook deliveries or simply knowing `SECRET_A`) crafts a `push` event body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "orgA" },
    "full_name": "orgB/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(SECRET_A, raw_body)` and POSTs to `/webhooks` with `X-Github-Event: push`.
4. `WebhooksController#verify_signature` extracts `repository_owner == "orgA"`, loads `Shipit.github(organization: "orgA")`, and the signature verifies successfully because it was computed with `SECRET_A`.
5. `Shipit::Webhooks.for_event('push')` invokes `PushHandler.call(params)`, which resolves `stacks` via `Repository.from_github_repo_name("orgB/victim-repo")` — a repository belonging to a completely different, victim organization — and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")`, all despite the signature only proving control of `orgA`'s secret.

I was unable to fully trace `Stack#sync_github`/`Repository#from_github_repo_name` and `Repository#github_api` implementations within the tool budget to confirm the exact downstream GitHub API credential used during sync (this would clarify whether it uses `orgA`'s or `orgB`'s GitHub App token), but the write to `orgB`'s `Stack`/`Commit` records via `PushHandler`/`StatusHandler`/`MembershipHandler` is directly demonstrated by the code cited above regardless of which token is used for the follow-up GitHub API call.
