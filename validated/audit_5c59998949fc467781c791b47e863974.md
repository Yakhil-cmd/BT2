### Title
Missing arbiter/party distinctness check allows self-dealing arbiter to steal escrowed funds in arbiter contracts - (File: arbiter_contract.js, wallet.js)

### Summary
`ocore`'s arbiter-contract feature (`arbiter_contract.js`, wired through `wallet.js`) is structurally the same trust pattern flagged in the external report: a third role (`arbiter`) is implicitly trusted to be independent of the two contracting parties (`my_address`/`peer_address`), and is allowed to unilaterally decide who receives the escrowed funds via a signed data-feed message, analogous to the operator's `AssetTransferResult`. Nowhere in contract creation, offer handling, or shared-address derivation is it verified that `arbiter_address` differs from `my_address` and `peer_address`, so one of the contracting parties can act as their own arbiter (or collude with an arbiter address they control) and award themselves the escrowed funds regardless of the real outcome of the deal.

### Finding Description
When a contract is created, `createAndSend` stores `arbiter_address`, `my_address`, and `peer_address` with no relationship check between them [1](#0-0) . The offer is transmitted to the peer and validated in `wallet.js`'s `arbiter_contract_offer` handler, which validates only that each address is independently well-formed (`ValidationUtils.isValidAddress`) and that the hash matches — it never checks that `arbiter_address` is distinct from `my_address`/`peer_address` [2](#0-1) .

The shared (escrow) address definition built in `deriveSharedAddress` grants the funds to whichever address the arbiter names in a `CONTRACT_<hash>` data-feed value, gated only by `["in data feed", [[contract.arbiter_address], "CONTRACT_" + contract.hash, "=", offeror_address/acceptor_address]]` [3](#0-2) . This is functionally identical to the external report's `AssetTransferResult` mechanism: a single address is trusted to "vouch" for the outcome, and the protocol enforces no independence between that address and the transacting parties.

`parseWinnerFromUnit`, used to interpret the arbiter's ruling, only checks that the authoring address of the resolution unit equals `contract.arbiter_address` and that the named winner is one of `my_address`/`peer_address` — it does not (and structurally cannot) detect that the "arbiter" is actually one of the disputants [4](#0-3) .

### Impact Explanation
If a contract is created with `arbiter_address` set equal to (or controlled by) one of the two contracting parties, that party can post a self-authored data-feed message naming themselves as `winner`. The escrow logic in `complete()`/`deriveSharedAddress` will then pay out the full escrowed amount to that address via `sendMultiPayment`, using the arbiter-authorized branch of the shared-address definition [5](#0-4) . This is unauthorized spending: the honest counterparty's funds sitting in the shared address can be taken by a self-dealing "arbiter," exactly mirroring the reported operator-as-buyer/operator-colluding-with-buyer fraud pattern, but here realized as arbiter-as-party/arbiter-colluding-with-party.

### Likelihood Explanation
Nothing in the codebase — neither the JS wallet-side validation (`arbiter_contract_offer` handler) nor the shared-address definition builder — prevents `arbiter_address` from coinciding with `my_address` or `peer_address`. An attacker acting as one of the two contract parties only needs to propose (or accept, with a colluding counterparty) a contract where the "arbiter" field is under their own control; this requires no privileged access, only normal paired-device contract negotiation, which is exactly the "paired device" attack surface allowed by scope.

### Recommendation
Add explicit checks, both when a contract offer is created/accepted (`createAndSend`, and the `arbiter_contract_offer`/`arbiter_contract_shared` handlers in `wallet.js`) and when the shared address definition is derived (`deriveSharedAddress`), that `arbiter_address !== my_address && arbiter_address !== peer_address`, rejecting any contract where the arbiter coincides with either party. Additionally, since the wallet cannot verify that an independent, non-colluding entity controls `arbiter_address`, consider requiring the arbstore/arbiter registry lookup (`arbiters.getArbstoreInfo`) to fail or warn if the arbiter address is associated with either contracting party's known addresses.

### Proof of Concept
1. Attacker A wants to defraud counterparty B in an arbiter contract.
2. A crafts a contract offer via `createAndSend`/`arbiter_contract_offer` with `my_address = A`, `peer_address = B`, and `arbiter_address = A2`, where `A2` is a second address fully controlled by A (or A convinces/colludes so that the "arbiter" role is effectively under A's control).
3. B validates only the format and hash of the offer (`ValidationUtils.isValidAddress`, hash match) — see `wallet.js` lines 617–654 — and, absent any distinctness check, accepts and funds the shared address as designed by `deriveSharedAddress`.
4. After the shared address is funded, A opens or does not even need a real dispute; A composes and posts a `data_feed` unit from `A2` (the "arbiter") setting `CONTRACT_<hash> = A`, satisfying the `"in data feed"` branch of the escrow definition [6](#0-5) .
5. `parseWinnerFromUnit` accepts this as a valid arbiter ruling because the authoring address matches `contract.arbiter_address` [4](#0-3) , and `complete()` releases the full amount to A [5](#0-4) , resulting in unauthorized loss of B's escrowed funds.

function parseWinnerFromUnit(contract, objUnit) {
	if (objUnit.authors[0].address !== contract.arbiter_address) {
		return;
	}
	var key = "CONTRACT_" + contract.hash;
	var winner;
	objUnit.messages.forEach(function(message){
		if (message.app !== "data_feed" || !message.payload || !message.payload[key]) {
			return;
		}
		winner = message.payload[key];
	});
	if (!winner || (winner !== contract.my_address && winner !== contract.peer_address)) {
		return;
	}
	return winner;
}
