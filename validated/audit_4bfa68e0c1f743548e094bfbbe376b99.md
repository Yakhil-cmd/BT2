### Title
Unhandled exception / crash from unsanitized C-hash decoding in `isValidAddressAnyCase` - (File: chash.js)

### Summary
`chash.js` implements the C-hash (address) checksum verification used throughout ocore to validate 32-character base32 addresses. The routine `isChashValid()` decodes an attacker-supplied string and then feeds the decoded bytes into bit-level parsing functions (`buffer2bin`, `separateIntoCleanDataAndChecksum`) that assume an exact bit length (160 or 288) and `throw` an uncaught `Error` otherwise. Only the `base32.decode`/`Buffer.from` call is wrapped in `try/catch`; the subsequent length-dependent parsing is not protected. [1](#0-0) 

### Finding Description
`isChashValid(encoded)` only validates the *string* length (32 or 48 chars) before decoding: [2](#0-1) 

For 32-character input it calls `base32.decode(encoded)` (the `thirty-two` package), which does not strictly validate that every character belongs to the RFC4648 base32 alphabet `[A-Z2-7]`; malformed/foreign characters can still be decoded without throwing, yielding a `Buffer` whose bit-length once passed through `buffer2bin()` is not exactly 160 bits.

`separateIntoCleanDataAndChecksum()` explicitly `throw`s an `Error` if the resulting binary string length is anything other than 160 or 288: [3](#0-2) 

This exception is raised *outside* the `try/catch` block in `isChashValid`, so it propagates up as an unhandled synchronous exception to whatever caller invoked chash/address validation.

The normal, most-used entry point `isValidAddress()` mitigates this by pre-filtering the string with a strict regex before calling into chash: [4](#0-3) 

However, `isValidAddressAnyCase()` calls `isValidChash()` → `chash.isChashValid()` directly, with **no character-set regex guard**, only a length check: [5](#0-4) 

This mirrors the CVE-2021-39926 bug class: a length/format field from untrusted data is checked for gross size but not fully validated before being handed to lower-level parsing code that makes strict internal assumptions and crashes (buffer/length mismatch) instead of gracefully rejecting malformed input.

### Impact Explanation
If `isValidAddressAnyCase` (or any other caller that skips the `[A-Z2-7]{32}` regex before calling `chash.isChashValid`) is reached with attacker-controlled 32-character data embedded in a posted unit, AA trigger, or device message, an uncaught `Error` is thrown synchronously inside the unit/trigger validation code path. Because ocore's validation pipeline is not designed to catch arbitrary synchronous throws from deep helper functions in all call sites, this can crash the Node.js process handling validation, denying service to the node and preventing it from processing/confirming new units — consistent with the "network unable to confirm new units" impact category.

### Likelihood Explanation
Exploitability depends on whether an unprivileged sender can supply a 32-character string containing characters outside `[A-Z2-7]` (e.g., lowercase letters, digits `0/1/8/9`, or other symbols) to a code path that calls `isValidAddressAnyCase`/`isValidChash` without the stricter regex pre-check used by `isValidAddress`. This was not fully confirmed within available tool calls — I could not enumerate all call sites of `isValidAddressAnyCase` in this session to prove an unprivileged-reachable path (e.g., via unit authors, AA definitions, attestation payloads, or device messages). This is the main open question for confirming full exploitability.

### Recommendation
- Wrap the entire body of `isChashValid()` (not just the decode step) in `try/catch`, returning `false` on any parsing error instead of allowing exceptions to propagate.
- Add the same `[A-Z2-7]{32}`/valid-base64 character-set validation used in `isValidAddress()` to `isValidAddressAnyCase()` (and any other direct caller of `chash.isChashValid`) before invoking `chash.js` routines.
- Audit all call sites of `isValidAddressAnyCase` and `chash.isChashValid` to confirm none are reachable with fully attacker-controlled strings from posted units, AA triggers, or device messages without prior sanitization.

### Proof of Concept
Conceptual PoC (pending confirmation of a reachable unprivileged call site):
```js
const chash = require('./chash.js');
// 32-char string, valid length, but containing bytes that base32-decode
// into a buffer whose bit-length isn't exactly 160 after buffer2bin()
chash.isChashValid('AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA1'); // '1' is outside A-Z2-7
// -> throws uncaught Error("bad length=...") from separateIntoCleanDataAndChecksum,
//    not caught by isChashValid's try/catch (which only wraps the decode call)
```
If this string reaches `validation_utils.isValidAddressAnyCase()` from a unit/trigger/device-message field that a remote unprivileged peer controls, the resulting uncaught exception can crash the validating process.
