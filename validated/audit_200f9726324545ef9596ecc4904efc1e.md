### Title
Cross-repository status forgery via unscoped SHA lookup in `StatusHandler#process` enables forged merge-gate satisfaction and unauthorized `merge_pull_request` calls - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` resolves the target `Commit` for an incoming `status` webhook purely by SHA, with no check that the webhook's `repository` matches the `Stack`/repository the matched `Commit` belongs to. Because git commit SHAs are content-addressed and therefore reproducible by anyone who can see the public commit content, an attacker who controls an unrelated repository monitored by the same Shipit installation can get GitHub to deliver a validly-signed `status` webhook whose `sha` collides with a victim stack's pending `MergeRequest#head`, injecting a forged "success" status that satisfies `merge.require` and triggers a real `merge_pull_request` call against the victim repository.

### Finding Description
The broken binding, stated as an equality that the code never enforces:

`payload["repository"]["full_name"] (the repo that authored/owns the status) == commit.stack.repository.full_name (the repo whose merge gate is being evaluated)`

Trace:
- `WebhooksController#verify_signature` only checks the HMAC signature against the GitHub App config keyed by `repository_owner` (the organization derived from the payload) — [1](#0-0) . This proves the webhook came from *some* repo GitHub delivered for that org/app installation; it does **not** bind the specific repository to any particular `Commit`/`Stack`.
- `StatusHandler#process` then does a **global**, unscoped lookup:
  `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [2](#0-1) . It never checks `commit.stack.repository` against `params.repository`.
- `Commit#create_status_from_github!` writes the status through `add_status`/`statuses.replicate_from_github!`, attaching it to whatever `Commit` row matched the SHA regardless of which repo's webhook produced it [3](#0-2) .
- Since git commit objects are content-addressed (same tree/blob content + same parent/author/committer/message/timestamps ⇒ same SHA1), an attacker who fully controls an unrelated repository that Shipit also tracks can reconstruct a commit object with an identical SHA to the victim `MergeRequest#head` (all inputs — tree, parents, author, committer, dates, message — are public via the GitHub API for the victim's public PR). They then call GitHub's standard "create status" API on their own repo/SHA with `context: 'ci/integration', state: 'success'`. GitHub signs and delivers this webhook validly (it is a completely legitimate event for the attacker's own, Shipit-monitored repository).
- On the next `ProcessMergeRequestsJob` run, `MergeRequest#all_status_checks_passed?` calls `StatusChecker.new(head, head.statuses_and_check_runs, stack.cached_deploy_spec).success?` [4](#0-3) , which now finds the forged `ci/integration` success status (required per `Shipit::DeploySpec#merge_request_required_statuses`) and the gate passes.
- `MergeRequest#merge!` then unconditionally calls `stack.github_api.merge_pull_request(stack.github_repo_name, number, ..., sha: head.sha, ...)` [5](#0-4) , an authenticated GitHub API call made with the victim stack's/org's `GITHUB_TOKEN`, merging the victim's PR based purely on the forged status.

Existing guards do not prevent this: `verify_signature` validates only that the payload came from a real GitHub delivery for the claimed org (an org-scoped HMAC, not a repo-scoped one), and nothing downstream re-checks `params.repository` against the `Stack`/`Repository` owning the matched `Commit`.

### Impact Explanation
An attacker who owns/administers any Shipit-tracked repository within reach of the same GitHub App installation can, from outside the victim stack entirely, inject arbitrary CI-status contexts (`state: success`) onto any `Commit` row that happens to share a SHA — including a victim repository's pending merge-request head. This directly bypasses the CI status gate (`merge.require`) enforced by `Shipit::DeploySpec#merge_request_required_statuses` / `MergeRequest::StatusChecker`, and results in Shipit executing a real, authenticated `merge_pull_request` call against the victim repository using that repository's own `GITHUB_TOKEN`. This is a cross-repository payload mutating another repository's stack/commit/merge state and causing an unauthorized merge — matching the Critical category ("a payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy, rollback or merge"). It is repeatable against any tracked stack whose pending commit SHA the attacker can reproduce, and the blast radius spans every stack served by the same GitHub App/org installation.

### Likelihood Explanation
Preconditions: victim stack requires at least one named status context in `shipit.yml` (`merge.require`); attacker needs push/admin rights on a *different* repository that is also tracked/monitored by the same Shipit installation (a normal, low-privilege developer capability, not requiring maintainer rights on the victim repo); attacker must be able to reconstruct a commit object with an identical SHA to the victim's PR head, which is mechanically straightforward since all inputs to a git commit hash (tree, parents, author/committer, timestamps, message) are public for any public PR. No secrets (`webhook_secret`, `GITHUB_TOKEN`, `api_clients_secret`) are required. This is feasible with a scripted `git commit-tree`/API call and repeatable per pending merge request.

### Recommendation
Scope the `status`/`check_suite` webhook handlers by the repository asserted in the payload, not merely by SHA: resolve the `Stack`/`Repository` from `params.repository.full_name` first, and only update `Commit` records that belong to `Stack`s matching that repository (e.g. `stack.commits.where(sha: params.sha)` instead of the global `Commit.where(sha: params.sha)` in `app/models/shipit/webhooks/handlers/status_handler.rb`). Apply the same repository-scoping check anywhere else statuses/check runs are attached to commits purely by SHA.

### Proof of Concept
Minitest plan (controller/model level, no live GitHub):
1. In `test/controllers/webhooks_controller_test.rb`, create two `Stack` fixtures for two different repositories (`victim/prod` and `attacker/unrelated`), each with a `Commit` sharing the **same** `sha` value (simulating the content-addressed collision — trivial to set up directly at the fixture/test level).
2. Stub `GithubHook.any_instance` / `Shipit.github(organization: ...)`'s `verify_webhook_signature` to return `true` (representing a validly-signed webhook from the attacker's own org/repo — never claiming the victim's org).
3. POST to `/webhooks` with `X-Github-Event: status`, body `{ sha: <shared_sha>, state: 'success', context: 'ci/integration', repository: { full_name: 'attacker/unrelated', owner: { login: 'attacker-org' } } }`.
4. Assert: `victim_commit.reload.statuses.where(context: 'ci/integration', state: 'success').exists?` is `true` — proving cross-repository status contamination (the equality `payload.repository.full_name == commit.stack.repository.full_name` is false, yet the write still occurred).
5. In `test/models/merge_request_test.rb`, build a pending `MergeRequest` on `victim/prod` whose `head` is the shared-SHA commit, stub `stack.github_api.merge_pull_request` and `.expects(:merge_pull_request)`; after step 3's forged status write, call `merge_request.reload.all_status_checks_passed?` and assert `true`, then call `merge_request.merge!` and assert `merge_pull_request` was invoked, with no real CI status ever posted against `victim/prod`.
