### Title
Webhook authenticity check is bound to `repository.owner.login`, not to the `repository.full_name` the webhook handlers act on - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App configuration (and therefore which `webhook_secret`) to verify the inbound signature against using `repository_owner`, a value taken from the same untrusted JSON body it is trying to authenticate. The actual object that gets mutated — the `Stack`/`Repository` record — is resolved later by the webhook handlers using a *different* field from the same body, `repository.full_name`. These two fields are never required to agree, so the "authenticated organization" and the "repository actually written to" are two independent bindings that an attacker can pull apart in any multi-organization Shipit deployment.

### Finding Description
`verify_signature` derives the signing organization purely from attacker-controlled JSON: [1](#0-0) [2](#0-1) 

`Shipit.github(organization: repository_owner)` returns a `GithubApp` instance scoped to that organization, and `verify_webhook_signature` is defined so that if that organization has no `webhook_secret` configured, verification is skipped entirely: [3](#0-2) 

Shipit explicitly supports multiple GitHub App/organization configurations at once (evidenced by the dummy multi-app fixture used in tests), so it is normal for a deployment to have several organizations configured, each with its own (or absent) `webhook_secret`: [4](#0-3) 

Once the request passes (or bypasses) this per-`repository_owner` check, `create` hands the *entire* JSON body to the registered handlers unchanged: [5](#0-4) 

Every handler resolves the target repository not from `repository_owner`/`organization.login` (the field the signature check trusted) but from `repository.full_name`: [6](#0-5) [7](#0-6) 

For example, `PushHandler` uses `stacks` (i.e. the repository resolved from `repository.full_name`) to enqueue a sync of whatever branch/SHA is in the payload: [8](#0-7) 

**The broken equality:** the engine implicitly assumes
`organization_whose_secret_verified_the_request == organization_that_owns_the_repository_being_mutated`,
but nothing enforces this. An attacker who knows (or can find, e.g. by triggering a 422 with a wrong signature and observing behavior, or by simply targeting an org that was configured without a webhook secret for convenience/testing) that organization `org-A` has `webhook_secret: null`, can send `X-Github-Event: push` with:
```json
{ "repository": { "owner": {"login": "org-A"}, "full_name": "org-B/secured-repo" }, "ref": "refs/heads/main", "after": "<attacker-chosen sha>" }
```
`repository_owner` resolves to `org-A"`, whose `verify_webhook_signature` returns `true` unconditionally (no secret configured), so the request passes the before_action. `create` then runs `PushHandler`, which looks up `Repository.from_github_repo_name("org-B/secured-repo")` — a repository that lives under a completely different, secret-protected organization — and enqueues a sync/deploy-triggering job for it using the attacker-supplied `after` SHA and `ref`.

### Impact Explanation
This lets an unprivileged attacker forge trusted GitHub events (push, status, check_suite, membership, pull_request, etc.) against any repository/stack tracked by Shipit, as long as *any one* configured organization in the same deployment lacks (or the attacker can otherwise defeat) a webhook secret — without needing that organization's real secret, a Shipit session, or an API token. Depending on the handler reached this enables triggering `GithubSyncJob` with attacker-chosen SHAs, forging commit statuses that gate deploys, or manipulating team/user membership — i.e., an unauthorized write/state change on a stack that belongs to a different, properly-secured GitHub organization. This matches the "unauthorized deploy/write" class of Critical/High impact defined in scope.

### Likelihood Explanation
Requires only that the Shipit deployment configures more than one GitHub organization (a documented, supported feature) and that at least one of them has no `webhook_secret` set — a realistic operational scenario during onboarding of a new org/testing, and indistinguishable from a properly-secured single-purpose deployment from the outside. No credentials, GitHub App keys, or Shipit accounts are required; the attacker only needs the public route `/github/webhooks` and knowledge of the target `full_name`.

### Recommendation
Do not let the value used to select the verifying `webhook_secret` diverge from the value the handlers act on. Concretely:
- Verify the webhook signature using the same repository identity (`repository.full_name`, or the owner derived from it) that handlers subsequently use to resolve the `Repository`/`Stack`, not a separately-dug `repository.owner.login`/`organization.login` field.
- Reject (422) any webhook where the configured GitHub App for the resolved repository has no `webhook_secret`, rather than silently treating "no secret configured" as "verification passed" in `GithubApp#verify_webhook_signature`.
- Consider requiring `webhook_secret` to be mandatory for every configured organization at boot, failing fast if any is missing.

### Proof of Concept
1. Configure Shipit with two orgs, e.g. `org-A` (no `webhook_secret`) and `org-B` (`webhook_secret` set, and it owns `secured-repo` tracked by Shipit).
2. POST to `/github/webhooks` with header `X-Github-Event: push` and any/garbage `X-Hub-Signature`, body:
```json
{
  "repository": {"owner": {"login": "org-A"}, "full_name": "org-B/secured-repo"},
  "ref": "refs/heads/main",
  "after": "deadbeefdeadbeefdeadbeefdeadbeefdeadbeef"
}
```
3. `verify_signature` calls `Shipit.github(organization: "org-A")`, whose `webhook_secret` is nil, so `verify_webhook_signature` returns `true` and the request is accepted.
4. `create` runs `PushHandler`, which resolves `Repository.from_github_repo_name("org-B/secured-repo")` and enqueues `stack.sync_github(expected_head_sha: "deadbeef...")` for `org-B`'s stack — despite the request never being validated with `org-B`'s secret.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
