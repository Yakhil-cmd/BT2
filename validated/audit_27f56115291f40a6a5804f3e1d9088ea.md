### Title
Unvalidated swap route lets route-selected contract inject unauthorized token transfers - (File: contracts/controller/src/strategies/swap.rs)

### Summary
Controller strategy entrypoints accept an opaque caller-supplied `swap` payload and invoke the configured router without constraining which contracts that payload may cause to execute. During `swap_collateral`, a malicious pool or venue embedded in the route can issue a token `transfer` from the account owner's wallet to an attacker. Soroban records that transfer as a child of the owner's `swap_collateral` authorization, so a poisoned signed authorization tree executes the unrelated transfer.

### Finding Description
`swap_collateral` authorizes the caller as the account owner or active delegate and passes the caller-controlled `swap` bytes into `withdraw_and_swap_from_supply`. [1](#0-0) 

The common swap implementation does not decode, parse, or allowlist the payload's destination contracts. It authorizes only the intended input-token transfer from the controller to the configured router, then invokes `router.execute_strategy(controller, amount_in, swap)` with the opaque payload. [2](#0-1) 

The authorization entry covers one exact `token.transfer(controller, router, amount_in)` invocation and has no declared sub-invocations. [3](#0-2)  However, because the router executes contracts named by the route, a malicious venue can make an unrelated token call beneath the user's top-level authorization. The protocol's test harness demonstrates this behavior: a route-selected `RogueHopPool` calls `transfer(alice, attacker, WALLET_BALANCE)`, simulation records that transfer under Alice's `swap_collateral` authorization entry, and the wallet balance moves to the attacker. [4](#0-3) 

The enforcing-auth test confirms that the transfer succeeds when the signed tree returned by simulation contains the rogue child invocation. [5](#0-4) 

### Impact Explanation
An attacker can steal arbitrary SEP-41 token balances from a user who submits or signs a poisoned route. The stolen amount is not limited to `from_amount`, collateral value, route output, or protocol-held funds: the malicious venue can name another token contract and transfer any wallet balance covered by the poisoned authorization tree. [6](#0-5) 

The same authorization-tree exposure applies to the other controller strategy entrypoints that submit a caller-provided route through `swap_tokens_or_passthrough`, including `swap_debt` and `repay_debt_with_collateral`. [7](#0-6) [8](#0-7) 

### Likelihood Explanation
Exploitation requires the victim to submit a poisoned route and sign the authorization tree produced by simulation. An attacker cannot directly invoke `swap_collateral` on a foreign account because `require_owner_or_delegate` restricts the account to its owner or an active delegate. [9](#0-8) 

The payload remains attacker-controlled once that authorization requirement is met. A malicious quote, route source, compromised frontend, or crafted transaction can include a route-selected contract whose code performs the unrelated token transfer. The controller's own checks measure only the input and output balances around the router call and do not prevent unrelated transfers under the user's authorization tree. [10](#0-9) 

The required behavior is demonstrated by an executable test rather than inferred: simulation records the theft as a child invocation, and enforcing mode succeeds when that child is included in the signed tree. [11](#0-10) [5](#0-4) 

### Recommendation
Constrain route execution to governance-approved venue contracts, or use a route representation whose pool addresses are selected only from a verified registry rather than from arbitrary caller-supplied bytes. The router call should be unable to introduce unrelated sub-invocations beneath the user's authorization entry.

At the controller boundary, decode and validate the route's venue addresses before granting authorization, reject unallowlisted venues, and reject payloads that can execute arbitrary callbacks or token contracts. Clients should additionally compare the simulated authorization tree with the expected route and reject any child invocation other than the intended input-token transfer.

### Proof of Concept
1. Alice supplies collateral and owns `account_id`.
2. An attacker deploys `RogueHopPool`, configured with `(alice, wallet_token, attacker, WALLET_BALANCE)`. Its `swap` function executes `token.transfer(alice, attacker, WALLET_BALANCE)` on an unrelated token contract. [12](#0-11) 
3. Alice calls `swap_collateral(alice, account_id, USDC, 50_000_000_000, ETH, route)`, where `route` names the rogue contract while still returning a fair `ETH` output.
4. The controller invokes the configured router with Alice's opaque `swap` payload after authorizing only the intended controller-to-router input transfer. [13](#0-12) 
5. During route execution, the rogue contract invokes the unrelated token transfer. Simulation attaches that transfer as a child of Alice's `swap_collateral` authorization. [14](#0-13) 
6. If Alice signs the simulated tree, the unrelated wallet token is transferred to the attacker while the nominal collateral swap still completes. [5](#0-4)

/// Authorizes, on behalf of the current contract, one `transfer(from, to, amount)`
/// call on `token_addr` made deeper in the next contract call (for example by
/// the pool). The entry allows no further sub-invocations.
pub fn authorize_transfer_as_current(
    env: &Env,
    token_addr: &Address,
    from: &Address,
    to: &Address,
    amount: i128,
) {
    let entry = InvokerContractAuthEntry::Contract(SubContractInvocation {
        context: ContractContext {
            contract: token_addr.clone(),
            fn_name: symbol_short!("transfer"),
            args: (from.clone(), to.clone(), amount).into_val(env),
        },
        sub_invocations: Vec::new(env),
    });
    env.authorize_as_current_contract(vec![env, entry]);

#[test]
fn simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry() {
    let s = Scene::new();
    let route = s.route_through_pool_stealing(WALLET_BALANCE);

    // `simulateTransaction` runs recording mode with non-root auth disabled.
    s.t.env.mock_all_auths();
    s.try_swap(&route)
        .expect("recording mode accepts the route");
    let recorded = s.t.env.auths();
    std::println!("recorded auth tree = {recorded:#?}");

    let stolen_transfer = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.wallet_token.clone(),
            symbol_short!("transfer"),
            (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),
        )),
        sub_invocations: std::vec![],
    };
    let poisoned_root = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.t.controller.clone(),
            Symbol::new(&s.t.env, "swap_collateral"),
            s.swap_args(&route),
        )),
        sub_invocations: std::vec![stolen_transfer],
    };
    assert_eq!(recorded, std::vec![(s.alice.clone(), poisoned_root)]);

    assert_eq!(s.wallet(&s.alice), 0);
    assert_eq!(s.wallet(&s.attacker), WALLET_BALANCE);
    assert_eq!(s.t.supply_balance_raw(ALICE, "ETH"), FAIR_OUT_ETH);
}
