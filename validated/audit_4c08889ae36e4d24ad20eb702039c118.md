### Title
Stale `VotesData` Mapping Entries Persist After `deregisterOperator`, Allowing Deregistered Operator's Vote to Execute Bridge Value Transfers — (`File: contracts/service_chain/bridge/BridgeOperator.sol`)

---

### Summary

`BridgeOperator.deregisterOperator()` removes an operator from `operators[_operator]` but cannot clear the internal mappings inside the `VotesData` struct (`voted` and `voteCounts`) stored in the nested `votes` mapping. These stale entries persist for every pending nonce. When a new operator is registered and votes on the same nonce, the deregistered operator's stale `voteCounts` contribution is still counted, allowing the threshold to be met with fewer active operators than required. This is the direct Kaia analog of the external "struct-with-mapping deletion" bug class.

---

### Finding Description

`BridgeOperator` stores per-nonce vote state in a nested mapping:

```solidity
mapping(uint8 => mapping(uint64 => VotesData)) private votes;
```

where `VotesData` is:

```solidity
struct VotesData {
    address[] voters;
    mapping(address => bytes32) voted;      // operator → voteKey
    bytes32[] voteKeys;
    mapping(bytes32 => uint8) voteCounts;   // voteKey → count
}
```

`deregisterOperator` only executes:

```solidity
delete operators[_operator];
``` [1](#0-0) 

It does **not** iterate over pending nonces to zero out `votes[voteType][nonce].voted[_operator]` or decrement the corresponding `voteCounts` entry. Solidity cannot delete mappings nested inside structs by deleting the struct; the storage slots remain at their last-written values.

The code itself acknowledges this in a comment:

```
// Note that outstanding votes by the deregistered operator are not revoked.
// ...
// In this case the request was executed with A's vote after A is deregistered.
``` [2](#0-1) 

The `_voteCommon` function reads `vote.voted[msg.sender]` and `vote.voteCounts[key]` directly from storage without any check that the voter was an operator at the time of the original vote:

```solidity
VotesData storage vote = votes[uint8(_voteType)][_nonce];
bytes32 oldVoteKeyOfVoter = vote.voted[msg.sender];
...
vote.voteCounts[_voteKey]++;
if (vote.voteCounts[_voteKey] >= operatorThresholds[uint8(_voteType)]) {
    return true;
}
``` [3](#0-2) 

**Re-registration corruption path (direct analog to external bug):**

When operator A is deregistered and then re-registered, and A votes on nonce N with the same calldata as before:
- `oldVoteKeyOfVoter = voted[A] = K` (stale, non-zero)
- `voteCounts[K]--` → 0 (was 1, A's prior contribution)
- `voted[A] = K` (same key)
- `voteCounts[K] == 0` → K is pushed to `voteKeys` **again** (duplicate entry)
- `voteCounts[K]++` → 1

This corrupts the `voteKeys` array with a duplicate entry and resets the count, creating inconsistent internal state for that nonce.

---

### Impact Explanation

The primary impact is on **bridge value transfers** (`handleKLAYTransfer`, `handleERC20Transfer`, `handleERC721Transfer`): [4](#0-3) 

**Concrete attack scenario (threshold bypass):**

1. Operators A and B; `operatorThresholds[ValueTransfer] = 2`
2. Operator A votes on nonce N (any pending bridge request) → `voteCounts[K] = 1`
3. Owner deregisters A (e.g., A is compromised) — `voteCounts[K]` remains 1 in storage
4. Owner registers new operator C
5. C votes on nonce N with identical calldata → `voteCounts[K]++` → 2 ≥ threshold → `closedValueTransferVotes[N] = true` → `_to.call.value(_value)("")` executes

The transfer is executed with only **one active operator's vote** (C's), while the threshold nominally requires two. A's vote persists despite deregistration, contributing the second count. If A was deregistered because A was compromised and had voted for a fraudulent transfer (wrong `_to`, inflated `_value`), C's vote on the same nonce completes the fraudulent transfer.

The corrupted value is: `voteCounts[K]` = 2 when only 1 active operator voted, causing `_to.call.value(_value)("")` to execute an unauthorized KAIA transfer from the bridge contract.

---

### Likelihood Explanation

- Operator rotation (deregister + register) is a normal operational action on service-chain bridges.
- The stale vote persists indefinitely for every nonce the deregistered operator voted on.
- Any new operator who votes on the same nonce (which is the normal duty of a bridge operator) will unknowingly complete the transfer using the deregistered operator's stale count.
- No special attacker capability is required beyond being a registered bridge operator.

---

### Recommendation

1. **Clear stale vote state on deregistration**: In `deregisterOperator`, iterate over all pending nonces and zero out `votes[voteType][nonce].voted[_operator]`, decrementing the corresponding `voteCounts` entry. Because the nonce space is unbounded, maintain a separate list of active nonces.

2. **Blacklist deregistered operators** (as the external report recommended): Prevent re-registration of a previously deregistered address, or track a deregistration block number and reject votes cast before that block.

3. **Minimum fix**: After `delete operators[_operator]`, emit an event and require operators to re-cast votes on any nonce where the deregistered operator had voted, by resetting `closedValueTransferVotes` state or incrementing a "generation" counter checked in `_voteCommon`.

---

### Proof of Concept

```
Setup:
  - Bridge deployed with operator A (owner) and operator B
  - operatorThresholds[ValueTransfer] = 2
  - A pending bridge request exists: nonce=5, to=attacker, value=1000 KAIA

Step 1: Attacker-controlled operator A calls handleKLAYTransfer(txHash, from, attacker, 1000, 5, blockNum, "")
  → votes[0][5].voted[A] = K = keccak256(calldata)
  → votes[0][5].voteCounts[K] = 1
  → closedValueTransferVotes[5] = false  (threshold not met)

Step 2: Owner calls deregisterOperator(A)
  → operators[A] = false
  → votes[0][5].voted[A] = K  ← STILL SET (mapping not cleared)
  → votes[0][5].voteCounts[K] = 1  ← STILL 1

Step 3: Owner calls registerOperator(C)  (C is a new trusted operator)

Step 4: C calls handleKLAYTransfer(txHash, from, attacker, 1000, 5, blockNum, "")
  → _voteCommon: votes[0][5].voteCounts[K]++ → 2
  → 2 >= operatorThresholds[0] (= 2) → returns true
  → closedValueTransferVotes[5] = true
  → attacker.call.value(1000)("")  ← EXECUTED

Result: 1000 KAIA transferred to attacker using A's stale vote,
        even though A was deregistered before C voted.
        Only 1 active operator (C) voted, but threshold of 2 was met
        via A's persisted storage entry.
```

The corrupted storage value is `votes[0][5].voteCounts[K] = 2` when only one active operator contributed, causing `handleKLAYTransfer` to execute an unauthorized KAIA transfer from the bridge.

    function _voteCommon(VoteType _voteType, uint64 _nonce, bytes32 _voteKey)
        private
        returns(bool)
    {
        VotesData storage vote = votes[uint8(_voteType)][_nonce];

        // If the same voter voted again, revoke previous vote.
        bytes32 oldVoteKeyOfVoter = vote.voted[msg.sender];
        if (oldVoteKeyOfVoter == bytes32(0)) {
            vote.voters.push(msg.sender);
        } else {
            vote.voteCounts[oldVoteKeyOfVoter]--;
        }

        // Either the current voter has voted before or not, update the vote data.
        vote.voted[msg.sender] = _voteKey;

        if (vote.voteCounts[_voteKey] == 0) {
            vote.voteKeys.push(_voteKey);
        }
        vote.voteCounts[_voteKey]++;

        if (vote.voteCounts[_voteKey] >= operatorThresholds[uint8(_voteType)]) {
            return true;
        }
        return false;
    }

    function deregisterOperator(address _operator)
    external
    onlyOwner
    {
        require(operators[_operator]);
        delete operators[_operator];

        for (uint i = 0; i < operatorList.length; i++) {
           if (operatorList[i] == _operator) {
               operatorList[i] = operatorList[operatorList.length-1];
               operatorList.length--;
               break;
           }
        }
        emit OperatorDeregistered(_operator);
    }
