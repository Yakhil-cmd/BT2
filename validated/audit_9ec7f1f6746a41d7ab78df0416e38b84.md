### Title
Stack-scoped ApiClient tokens bypass their stack binding in `Api::CCMenuController#stack` - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Api::CCMenuController` re-implements `#stack` using `Stack.from_param!(params[:stack_id])` instead of the base controller's `stacks.from_param!(params[:stack_id])`, dropping the scoping by `current_api_client.stack_id`. A CCMenu token that was created for (and should only be authorized to read) one stack can be used to read the CI/build status of any other stack in the installation.

### Finding Description
`Api::BaseController#stacks` correctly restricts the queryable set of stacks to `Stack.where(id: current_api_client.stack_id)` whenever the authenticated `ApiClient` is stack-scoped, and `#stack` resolves the request parameter within that restricted relation [1](#0-0) . This is the intended trust binding: *stack the token authorizes == stack the request touches*.

`Api::CCMenuController`, however, overrides `#stack` to resolve `params[:stack_id]` against the entire `Stack` table, ignoring `current_api_client.stack_id`:
```ruby
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end
``` [5](#0-4) 

The only authorization gate left is `require_permission :read, :stack`, which merely checks the client's `permissions` array contains the literal string `"read:stack"` — it is not aware of which stack is being requested [3](#0-2) . Any client holding `read:stack` (including a token deliberately minted and scoped to a single, low-sensitivity stack, e.g. via `CCMenuUrlController#client`, which is exactly this kind of stack-agnostic-permission/stack-scoped client at [6](#0-5) ) can therefore substitute an arbitrary `stack_id` in the URL and read another stack's build/deploy state.

Fixture evidence confirms stack-scoped clients are a first-class, exercised concept in this codebase: `here_come_the_walrus` is created with `stack: shipit` and only `read:stack` permission [7](#0-6) , and is asserted elsewhere to be restricted to that one stack when listing stacks — but this scoping guarantee is never exercised/enforced for the CCMenu endpoint.

### Impact Explanation
This is an unauthenticated-read-scope-escalation: an attacker who legitimately holds (or otherwise obtains) a stack-scoped CCMenu token authorized only for stack A can supply a different `stack_id` and obtain the last deploy/build status (success/failure, name, etc.) of stack B, which the token was never authorized to access. This matches the "High" impact class of unauthenticated/unauthorized read of stack state via a broken deployment-trust binding (token-authorized stack vs. stack actually touched).

### Likelihood Explanation
Likely to be triggered: the CCMenu route is intentionally exposed with token-based authentication designed for third-party CI dashboard tools (`CCMenuUrlController` explicitly mints such tokens), so tokens of this kind are expected to exist and be used externally. Exploitation only requires substituting the `stack_id` route/query parameter — no additional secret or session is needed once a client already possesses any valid `read:stack` token.

### Recommendation
Make `Api::CCMenuController#stack` reuse the scoped `stacks` relation from `BaseController` (i.e., `stacks.from_param!(params[:stack_id])`) instead of querying `Stack` directly, so that stack-scoped API clients cannot read information about stacks outside their authorized `stack_id`. Add regression tests asserting that a stack-scoped `ApiClient` token receives a 404/403 when requesting `Api::CCMenuController#show` for a stack other than the one it is bound to.

### Proof of Concept
1. As an admin, create (or observe) a stack-scoped `ApiClient` bound to `stack_id = A` with `permissions: ['read:stack']` (as done automatically by `CCMenuUrlController#fetch` for stack A).
2. Obtain that client's `authentication_token` (e.g., via the generated CCMenu URL for stack A, which is designed to be shared with third-party tools).
3. Send `GET /api/stacks/:B/ccmenu.xml?token=<token>` where `B` is a different stack's identifier.
4. Observe that `Api::CCMenuController#stack` returns stack `B` (via `Stack.from_param!`) rather than raising/404, and the response renders stack `B`'s deploy status — even though the token is only supposed to be authorized for stack `A`.
