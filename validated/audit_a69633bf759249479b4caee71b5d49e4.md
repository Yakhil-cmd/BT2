### Title
Old Bridge Owner Retains Operator Privileges After `transferOwnership`, Enabling Unauthorized Bridge Asset Draining — (`contracts/service_chain/bridge/BridgeOperator.sol`)

---

### Summary

`BridgeOperator.sol` registers the deployer as an operator in its constructor. When ownership is later transferred via the inherited `Ownable.transferOwnership`, only the `_owner` storage variable is updated — the previous owner's entry in `operators` and `operatorList` is never cleared. The previous owner therefore retains the ability to call `handleKLAYTransfer`, `handleERC20Transfer`, and `handleERC721Transfer` as a registered operator, and can unilaterally execute bridge value transfers (threshold defaults to 1) after the sale or handover of the bridge.

---

### Finding Description

**Constructor registers deployer as operator:** [1](#0-0) 

```solidity
constructor() internal {
    for (uint8 i = 0; i < uint8(VoteType.Max); i++) {
        operatorThresholds[uint8(i)] = 1;   // default threshold = 1
    }
    operators[msg.sender] = true;
    operatorList.push(msg.sender);
}
```

**`transferOwnership` (inherited from `Ownable`) only updates `_owner`; it never touches `operators` or `operatorList`:** [2](#0-1) 

```solidity
function transferOwnership(address newOwner) public onlyOwner {
    _transferOwnership(newOwner);
}
function _transferOwnership(address newOwner) internal {
    require(newOwner != address(0), ...);
    emit OwnershipTransferred(_owner, newOwner);
    _owner = newOwner;   // operators mapping untouched
}
```

**`deregisterOperator` is `onlyOwner`** — the new owner *can* remove the old owner, but there is no automatic cleanup, and the new owner may not know this step is required: [3](#0-2) 

**`handleKLAYTransfer` and `handleERC20Transfer` are gated only by `onlyOperators`**, which checks `operators[msg.sender]` — a mapping that still contains the old owner: [4](#0-3) [5](#0-4) 

**The `onlyOperators` modifier:** [6](#0-5) 

```solidity
modifier onlyOperators() {
    require(operators[msg.sender], "msg.sender is not an operator");
    _;
}
```

Because `operators[oldOwner]` is never set to `false` by `transferOwnership`, the old owner passes this check indefinitely.

---

### Impact Explanation

With the default threshold of 1, the old owner can call `handleKLAYTransfer`, `handleERC20Transfer`, or `handleERC721Transfer` unilaterally after the bridge has been sold or handed over. Each call mints or transfers tokens/KLAY to an arbitrary `_to` address chosen by the caller:

- `handleERC20Transfer` → `IERC20(_tokenAddress).safeTransfer(_to, _value)` or `ERC20Mintable.mint(_to, _value)`
- `handleKLAYTransfer` → `_to.call.value(_value)("")`
- `handleERC721Transfer` → analogous token transfer

This allows the previous owner to drain all KLAY, ERC20, and ERC721 assets held or mintable by the bridge contract after the ownership transfer.

---

### Likelihood Explanation

The scenario is a natural consequence of bridge ownership transfer (e.g., selling the bridge to a new operator, handing it to a DAO, or upgrading governance). The new owner is not prompted to deregister the old owner, and the contract provides no warning. The old owner may exploit this window immediately after the transfer. The default threshold of 1 means no collusion is required — the old owner acts alone.

---

### Recommendation

Override `transferOwnership` in `BridgeOperator` to atomically remove the outgoing owner from `operators`/`operatorList` and add the incoming owner:

```solidity
function transferOwnership(address newOwner) public onlyOwner {
    // Remove old owner from operator set
    if (operators[owner()]) {
        delete operators[owner()];
        for (uint i = 0; i < operatorList.length; i++) {
            if (operatorList[i] == owner()) {
                operatorList[i] = operatorList[operatorList.length - 1];
                operatorList.length--;
                break;
            }
        }
    }
    // Add new owner as operator if not already registered
    if (!operators[newOwner]) {
        operators[newOwner] = true;
        operatorList.push(newOwner);
    }
    super.transferOwnership(newOwner);
}
```

Alternatively, require explicit operator management after ownership transfer and document the mandatory deregistration step prominently.

---

### Proof of Concept

```
1. Alice deploys Bridge (Alice = _owner, operators[Alice] = true, threshold = 1)
2. Alice calls transferOwnership(Bob)
   → _owner = Bob
   → operators[Alice] = true  ← NOT cleared
   → operators[Bob] = false   ← NOT set
3. Alice calls handleKLAYTransfer(txHash, victim, alice, 100 ether, nonce, blockNum, "")
   → onlyOperators passes (operators[Alice] == true)
   → _voteValueTransfer reaches threshold (1 vote needed, 1 cast)
   → bridge sends 100 KLAY to Alice
4. Alice repeats for every ERC20/ERC721 token held by the bridge
```

Bob (new owner) can stop this only by calling `deregisterOperator(Alice)`, but there is no mechanism to alert Bob that this step is necessary, and the exploit can occur in the same block as the ownership transfer.
