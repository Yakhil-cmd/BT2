### Title
Borrower can push utilization to the configured ceiling and permanently block all ordinary withdrawals — (File: contracts/pool/src/guards.rs)

### Summary
`require_utilization_below_max` in `contracts/pool/src/guards.rs:19-34` rejects any post-operation state where `ceil(debt_value) / floor(supply_value) > params.max_utilization`. This guard is enforced on ordinary withdrawals (`contracts/pool/src/ops/withdraw.rs:111-119`) and revenue claims (`contracts/pool/src/ops/revenue.rs:44`), but not on accrual or liquidation withdrawals. An unprivileged borrower can call `borrow` to push utilization exactly to the ceiling (the check admits `<=` at `borrow.rs:78` via the same guard), after which every ordinary `withdraw` reverts with `UtilizationAboveMax`, because burning supply shares strictly raises utilization. Interest accrual then pushes utilization above the ceiling on its own (documented in `docs/reference/invariants.md` INV-ACCT-08), making the freeze self-sustaining.

### Finding Description
The bug class from the external report — a hard revert whenever a computed value exceeds a cap, letting an attacker drive that value past the cap to DoS an operation — maps directly onto the max-utilization gate:

- `borrow`/`mint_debt` enforces `require_utilization_below_max` *after* minting debt (`borrow.rs:78`), with `borrowed.div_ceil(supplied) <= max_utilization` — equality is admitted.
- `withdraw` enforces the same guard *after* burning supply shares (`withdraw.rs:114-117`). Since withdrawal only decreases `supplied` while `borrowed` stays constant, post-withdraw utilization is always ≥ pre-withdraw utilization.
- Therefore, once utilization ≥ `max_utilization`, the assert `borrowed.div_ceil(supplied) <= max_utilization` fails for every ordinary withdrawal of any size — a complete DoS of `withdraw`, which is exactly the "rewards never reach the gauge" shape translated to supplier exits.
- Accrual compounds debt without running the guard, so utilization drifts strictly above the ceiling over time; the attacker does not even need to hit equality precisely.
- `require_supply_for_debt` adds a second permanent-revert edge: a supplier burning the last supply shares while debt exists reverts with `PoolInsolvent` (`guards.rs:69-73`), so full exits are blocked whenever debt is outstanding and a withdrawal would zero `supplied`.

The attacker only needs standard `borrow` via the controller — collateral-backed debt is an accepted cost, and liquidation does not release the block for other suppliers because liquidation withdrawals skip the gate but ordinary ones never regain a below-ceiling state unless debt is repaid.

### Impact Explanation
Temporary freezing of funds: all suppliers in the affected (hub, token) market are unable to withdraw any amount through the unprivileged `withdraw` path while utilization sits at or above `max_utilization`. Protocol revenue claims via `claim_revenue` also revert (`revenue.rs:44`), freezing unclaimed yield. The freeze lifts only if borrowers repay, liquidation reduces debt, or governance changes parameters — none of which suppliers control.

### Likelihood Explanation
Reachable by a single unprivileged address: supply collateral, then `borrow` the target market up to the liquidation-buffer/cap limits so that `div_ceil(borrowed, supplied)` lands at `max_utilization`. The admission of equality makes the ceiling itself sufficient; accrual does the rest. The attack requires collateral and that `max_utilization < 1.0` is configured for the market — a normal configuration, not a bad-parameter edge, since the guard is meaningless when unset. Borrow caps may limit debt size, so this is most effective in markets where the borrow cap is high relative to supply.

### Recommendation
Do not re-check the max-utilization gate on exits that cannot lower utilization, or gate withdrawals on the pre-withdraw utilization instead of the post-withdraw value — a withdrawal from an already-over-ceiling market should be allowed since it can only worsen a ratio the protocol already tolerates (and exits are how suppliers exit a risky market anyway). Alternatively, exempt full/partial withdrawals from `require_utilization_below_max` entirely, as is already done for liquidation withdrawals (`withdraw.rs:114`), since a supplier leaving does not create new risk.

### Proof of Concept
1. Market (hub H, USDC) is configured with `max_utilization < RAY` (e.g., 0.95). Alice supplies 1000 USDC; the market is below the ceiling.
2. Attacker supplies collateral (e.g., ETH) and calls controller `borrow` for USDC sized so `ceil(debt_value) / floor(supply_value) == 0.95` — admitted by `mint_debt` since the guard uses `<=` (`guards.rs:31`).
3. Attacker waits one accrual chunk (or repays nothing); `update_indexes` raises `borrow_index`, pushing the ratio above 0.95 (`INV-ACCT-08` confirms accrual can exceed the ceiling).
4. Alice calls `withdraw`. `accounting` burns her shares, then `gate_and_debit` calls `require_utilization_below_max` — post-burn `supplied` is smaller, so `div_ceil` is even larger — revert `UtilizationAboveMax`.
5. Every ordinary withdrawal of any size reverts identically; `claim_revenue` also reverts (`revenue.rs:44`). Funds are frozen until the attacker (or liquidations/bad-debt) reduce debt below the ceiling.
