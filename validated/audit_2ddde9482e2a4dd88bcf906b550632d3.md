### Title
Unauthenticated Webhook Forgery via Uninitialized `webhook_secret` Bypasses Signature Verification, Enabling `Shipit.github_teams` Authorization Bypass - ([File: lib/shipit/github_app.rb])

### Summary
`GitHubApp#verify_webhook_signature` treats an unset `webhook_secret` as automatically "verified," exactly mirroring the reported `Fishing` bug class: a security-critical parameter (`stakeDuration` / `webhook_secret`) defaults to a falsy/uninitialized value, and the code path that is supposed to enforce a guarantee (waiting duration / cryptographic signature) silently no-ops instead of rejecting the request. Combined with the fact that the *organization* used to select this (possibly unset) secret is itself taken from the unauthenticated JSON payload, an attacker can forge arbitrary GitHub webhook events — including `membership` events that write `Team`/`Membership` records used directly by `User#authorized?`, the gate for `Shipit.github_teams` authorization.

### Finding Description
`WebhooksController#verify_signature` resolves which `GitHubApp` (and therefore which `webhook_secret`) to use for verification from `repository_owner`, a value read straight out of the untrusted JSON body before any signature has been checked: [1](#0-0) [2](#0-1) 

`GitHubApp#verify_webhook_signature` then performs the actual check: [3](#0-2) 

Line 77, `return true unless webhook_secret`, is the uninitialized-guard analog of the `Fishing` contract's missing `stakeDuration` check: if the config for the selected organization has no `webhook_secret` set — which is the exact value shown in the shipped example configs — signature verification is unconditionally satisfied, with **no binding whatsoever to the raw request body or the `X-Hub-Signature` header**. [4](#0-3) 

This is not a hypothetical misconfiguration edge case: the "Using Multiple GitHub Applications" pattern that Shipit documents explicitly allows each organization in `secrets.yml` to have its own independent `webhook_secret`, and any one of those (e.g., a low-value or newly-added org) being left blank collapses signature enforcement for *any* webhook payload whose `repository.owner.login` (or `organization.login`) is set to that org's name — because that field, not a verified identity, is what selects the (empty) secret. [5](#0-4) 

Once `verify_signature` "passes," `WebhooksController#create` dispatches the entire attacker-controlled JSON body to registered handlers for the claimed `X-Github-Event` type: [6](#0-5) 

Among the default handlers is the `membership` handler, which creates `Team` and `Membership` records purely from payload data (verified in the test suite, which shows a forged `membership` webhook creating a `Team`, and adding/removing arbitrary `Membership` records by GitHub login): [7](#0-6) 

These `Team`/`Membership` records are exactly what gates deploy authorization: `User#authorized?` checks whether the current session's `User` belongs to any team in `Shipit.github_teams`: [8](#0-7) 

and this check is the sole authorization gate enforced on every controller in the app via `force_github_authentication`: [9](#0-8) 

The equality that should hold is:
`organization whose secret cryptographically authenticated the request == organization/repository whose state (teams, memberships, repositories, statuses) the handler is permitted to mutate`

Because the organization used to *select the verification secret* is attacker-supplied and decoupled from the payload fields the handlers actually *write* (team slug, member login, repository full_name), that equality is broken — just as in the `Fishing` bug the `stakeDuration` guard never covered the field (`hero.stakeAt` comparison) it was meant to gate.

### Impact Explanation
An unauthenticated network attacker who can reach the mounted webhooks endpoint and who knows (or guesses) the name of any GitHub organization configured in `secrets.yml` with an empty `webhook_secret` can:
- Forge a `membership` webhook to add their own real GitHub login as a member of a `Team` matching one of `Shipit.github_teams`, thereby satisfying `User#authorized?` on their next legitimate OAuth login — an **authentication/authorization bypass** into the entire Shipit instance (deploy triggering, task execution, stack management), which the rules explicitly flag as a High/Critical target ("escalation into `Shipit.github_teams` authorization").
- Forge `push`, `status`, or `check_suite` events naming any tracked repository to desynchronize CI/commit status state that gates deploy safety checks (`ci.require`), or trigger `GithubSyncJob` against arbitrary stacks.

### Likelihood Explanation
Likelihood is moderate-to-high in any deployment using the documented multi-organization GitHub App configuration, since `webhook_secret` is shown blank in every shipped example (`config/secrets.development.example.yml`, `test/dummy/config/secrets_double_github_app.yml`, `docs/setup.md`), making it plausible that at least one organization in a real fleet is left unset — and the code performs no validation forcing it to be non-blank before accepting requests as verified, exactly analogous to `Fishing.stakeMany()` never checking that `stakeDuration` had been initialized.

### Recommendation
- Fail closed instead of open in `GitHubApp#verify_webhook_signature`: reject (return `false`) when `webhook_secret` is blank rather than returning `true`, or refuse to boot/register a webhook endpoint for organizations with no configured secret.
- Decouple organization-for-verification selection from any single unauthenticated payload field, or re-validate after verification that the organization used for signature checking matches the repository/organization actually mutated by the handler.
- Add a startup/config validation step (similar to the recommended `if ($.stakeDuration == 0) revert RewardsNotSet();` in the referenced report) that refuses to start the engine, or explicitly disables the corresponding handlers, when any configured GitHub org lacks a `webhook_secret`.

### Proof of Concept
1. Configure Shipit with two GitHub orgs per the documented multi-org schema: `TrustedOrg` (real `webhook_secret` set) and `EmptyOrg` (no `webhook_secret`, matching the shipped example configs).
2. As an unauthenticated attacker, POST to the webhooks endpoint with header `X-Github-Event: membership`, no valid `X-Hub-Signature`, and a body of the form:
```json
{
  "action": "added",
  "team": { "id": 48, "name": "Shopify Developers", "slug": "developers" },
  "organization": { "login": "EmptyOrg" },
  "member": { "login": "attacker-github-login" }
}
```
3. `repository_owner` resolves to `"EmptyOrg"`; `Shipit.github(organization: "EmptyOrg")` config has no `webhook_secret`; `verify_webhook_signature` returns `true` unconditionally regardless of the (absent/garbage) `X-Hub-Signature` header.
4. The `membership` handler processes the forged payload and creates/updates a `Membership` linking a `User` with login `attacker-github-login` to the `Team` matching `Shipit.github_teams` (as demonstrated by the existing test coverage of this handler behavior).
5. `attacker-github-login` subsequently signs in via the real GitHub OAuth flow; `User#authorized?` now returns `true` because the forged `Membership` row satisfies `teams.where(id: Shipit.github_teams.map(&:id)).exists?`, granting full access to the Shipit instance without ever being a genuine member of the required GitHub team.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
    def force_github_authentication
      if current_user.logged_in? && current_user.requires_fresh_login?
        Rails.logger.warn("User #{current_user.id} requires a fresh login, logging out...")
        reset_session
        redirect_to(Shipit::Engine.routes.url_helpers.github_authentication_path(origin: request.original_url))
      elsif Shipit.authentication_disabled? || current_user.logged_in?
        unless current_user.authorized?
          team_handles = Shipit.github_teams.map(&:handle)
          team_list = team_handles.to_sentence(two_words_connector: ' or ', last_word_connector: ', or ')
          render(plain: "You must be a member of #{team_list} to access this application.", status: :forbidden)
        end
      else
        redirect_to(Shipit::Engine.routes.url_helpers.github_authentication_path(origin: request.original_url))
      end
    end
```
