### Title
`StatusHandler#process` mutates commits across all repositories via unscoped `Commit.where(sha:)` - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` looks up commits by SHA alone across the entire database, without scoping to the repository named in the webhook payload. Since git commit SHAs are content-addressed and repository-independent (identical commits in a fork share the same SHA as the upstream repo), an attacker who controls any GitHub App/org with its own valid `webhook_secret` can send a correctly-signed `status` webhook for their own repository that mutates a commit's status in a completely unrelated victim stack.

### Finding Description
The binding that must hold is: **the organization whose `webhook_secret` verified this webhook delivery == the organization/repository that owns the `Commit` record being mutated**. `StatusHandler` breaks this equality.

Path:
1. `WebhooksController#verify_signature` resolves `Shipit.github(organization: repository_owner)` using `repository_owner` taken from the attacker's own payload (`params.dig('repository', 'owner', 'login')`), and verifies the signature against that org's `webhook_secret`. [1](#0-0) . This correctly proves the request came from the attacker's own app/org — it says nothing about which `Commit` rows may be touched.
2. `WebhooksController#create` dispatches unconditionally to `Shipit::Webhooks.for_event('status')`, which resolves to `Handlers::StatusHandler` by default. [2](#0-1) [3](#0-2) 
3. `StatusHandler#process` executes `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` — a global, unscoped lookup with no reference to `payload.dig('repository', 'full_name')`. [4](#0-3) 

Compare this to the base `Handler#stacks` helper used correctly by `PushHandler` and `CheckSuiteHandler`, which scopes lookups through `Repository.from_github_repo_name(repository_name)` where `repository_name` is `payload.dig('repository', 'full_name')` — i.e., the repository asserted in the *same signed payload* used for verification. [5](#0-4)  `StatusHandler` never calls `stacks` or checks `repository_name`/`stack_id`, so any commit anywhere in the Shipit install with a matching SHA is mutated regardless of which repository/org it belongs to.

Exploit: an attacker registers their own GitHub App/org in Shipit (or otherwise controls a repo with its own `webhook_secret`), forks or otherwise obtains a repository containing a commit object identical (same SHA1) to one tracked by a victim's Shipit stack — trivial for public repos via fork, since SHA1 is content-addressed and independent of the remote. The attacker POSTs `X-Github-Event: status` to `/webhooks` with `repository.owner.login` = their own org (so `verify_signature` passes using their own secret) and `sha` = the shared commit SHA, `state` = `success` (or any state/description/context/target_url of choice). `StatusHandler` finds the victim's `Commit` row by that SHA and calls `create_status_from_github!`, writing a forged `Status` for the victim's stack — potentially flipping CI to green and enabling `deployable_status`/CI gating for that commit. [6](#0-5) 

Existing guards (`verify_signature`, `drop_unhandled_event`, `ExplicitParameters` schema) only validate the shape/signature of the request, not the repository-scoping of the effect; none of them check that the matched `Commit`'s `stack`/`repository` corresponds to the signing org.

### Impact Explanation
This is a cross-tenant "payload for one repository mutating another's ... commit" scenario, explicitly listed as Critical. An attacker with no privileges on the victim's stack can forge a `Status` (and thus CI signal) for the victim's commit, potentially unblocking automatic deploys or manipulating status checks that gate merges/deploys. This is repeatable against any commit whose SHA the attacker can reproduce (trivial for any public/forked repository) and is not limited to a single victim — every Shipit-tracked stack across every tenant that has ever ingested that commit SHA is affected.

### Likelihood Explanation
Preconditions are attacker-attainable without any Shipit privileges: only a self-controlled GitHub App/org configured in Shipit with its own `webhook_secret` (which the attacker fully controls) and knowledge of a target commit SHA (obtainable by forking a public repo, since SHA1 hashes are identical across forks/mirrors). No Shipit session, API token, or GitHub secret of the victim is required. The attack is a single unauthenticated-relative-to-victim HTTP POST and fully repeatable.

### Recommendation
Scope `StatusHandler#process` to the repository asserted in the signed payload, mirroring `PushHandler`/`CheckSuiteHandler`: resolve `stacks` via `Repository.from_github_repo_name(payload.dig('repository', 'full_name'))` and restrict the `Commit` lookup to `stacks.flat_map(&:commits).where(sha: params.sha)` (or equivalent `Commit.where(sha: params.sha, stack: stacks)`), rejecting/ignoring commits that don't belong to a stack of the repository that authenticated the webhook.

### Proof of Concept
In `test/controllers/webhooks_controller_test.rb` style (minitest, `ActionController::TestCase`):
```ruby
test ":status from an attacker-controlled org mutates a commit belonging to a different stack" do
  victim_stack = shipit_stacks(:shipit) # belongs to repository "shopify/shipit-engine" or similar
  victim_commit = shipit_commits(:first)
  victim_repo_full_name = victim_stack.repository.full_name

  # Attacker's own org/app config, distinct from victim's org, with attacker's own webhook_secret
  attacker_org = 'attacker-org'
  GithubHook.any_instance.stubs(:verify_signature).returns(true) # only stands in for attacker's own valid signature

  request.headers['X-Github-Event'] = 'status'
  body = {
    'sha' => victim_commit.sha,             # SHA collides because attacker forked the victim repo
    'state' => 'success',
    'context' => 'attacker/forged',
    'repository' => { 'owner' => { 'login' => attacker_org }, 'full_name' => "#{attacker_org}/forked-repo" }
  }.to_json

  assert_difference '-> { victim_commit.statuses.count }', 1 do
    post :create, body:, as: :json
  end

  status = victim_commit.statuses.last
  assert_equal 'success', status.state
  assert_equal 'attacker/forged', status.context
  # Binding check: signing org (attacker_org) != owning org (victim_repo_full_name), yet mutation succeeded
  refute_equal attacker_org, victim_repo_full_name.split('/').first
end
```
This demonstrates that despite the signature belonging solely to `attacker_org`'s app config, the mutation lands on `victim_commit`, which belongs to a stack owned by a different repository/org — confirming the vulnerability is entirely within `StatusHandler#process`'s unscoped `Commit.where(sha:)` lookup.

      verified = github_app.verify_webhook_signature(

      )
