### Title
Poseidon Syscall Charges Compute Units by Input Count Instead of Input Byte-Length, Enabling Unmetered CPU Amplification - ([File: syscalls/src/lib.rs])

### Summary
`SyscallPoseidon` (`syscalls/src/lib.rs:2453-2521`) charges compute units using `poseidon_cost(vals_len)` — a function of the *number* of input sequences only — while the actual work performed by `poseidon::hashv` scales with the *total byte length* of all the `VmSlice<u8>` inputs the caller supplies. This is structurally identical to the LiquidJS `replace_first` bug: the accounting metric (count) is decoupled from the actual resource consumed (bytes processed), allowing a caller to pay a small, fixed charge while forcing disproportionately large CPU work.

### Finding Description
`SyscallPoseidon::rust` in `syscalls/src/lib.rs:2453-2521` limits the number of input sequences to 12 (`vals_len > 12` check, lines 2467-2474) and then computes the compute-unit cost via:
```rust
let Some(cost) = execution_cost.poseidon_cost(vals_len) else { ... };
invoke_context.compute_meter.consume_checked(cost.to_owned())?;
```
`poseidon_cost` (`program-runtime/src/execution_budget.rs:265-293`) is a pure quadratic function of `nr_inputs` (`61*n^2 + 542`), with **no dependence on the byte length of any input**. After charging this fixed, count-based cost, the code translates each `VmSlice<u8>` via `translate_slice::<VmSlice<u8>>` and `translate_vm_slice` (lines 2499-2504) and passes the resulting byte slices — whose lengths are entirely attacker-controlled and can be as large as any mapped memory region (e.g., account data buffers, which can be up to 10 MB each) — into `poseidon::hashv(parameters, endianness, inputs.as_slice())` at line 2506.

For comparison, the generic `SyscallHash` (SHA-256/Keccak/Blake3, `syscalls/src/lib.rs:2718-2789`) correctly charges `hash_byte_cost.saturating_mul(val.len() / 2)` **per input slice** in addition to the base cost (lines 2767-2778), i.e. cost scales with actual bytes hashed. `SyscallPoseidon` has no equivalent per-byte charge — the `$&`-style amplification here is: metering keyed to the wrong dimension (count of "slices" instead of size of data), exactly mirroring how LiquidJS's `memoryLimit.use(str.length)` metered only the *input* dimension while `$&` expansion multiplied the *output* dimension unaccounted.

An attacker-controlled BPF program can build up to 12 `VmSlice<u8>` entries whose `ptr`/`len` point into large, already-mapped memory regions (e.g., account data buffers loaded for the instruction, which the SVM permits up to `MAX_LOADED_ACCOUNTS_DATA_SIZE_BYTES`), and pass them to `sol_poseidon`. The syscall charges a fixed ~9,226 CU (`61*12^2+542`) regardless of whether each of the 12 slices is a few bytes or several megabytes, while the underlying Poseidon hash implementation processes every byte of every slice to produce field elements for the permutation.

### Impact Explanation
This breaks the fundamental invariant of Agave's compute-budget model: CU consumption must track real CPU work so that a leader can bound per-transaction/per-block execution time by the compute budget. Because Poseidon's real cost scales with total input bytes but the charged cost does not, a transaction can consume orders of magnitude more wall-clock CPU time in `poseidon::hashv` than its CU charge reflects. Since block packing, leader scheduling, and cost-model block limits (`cost-model/src/block_cost_limits.rs`) all assume CU consumption ∝ execution time, an attacker can craft transactions that are "cheap" by the cost model yet execute for far longer than budgeted, degrading leader throughput and potentially causing slot deadline misses — a compute-budget/cost-accounting bypass reachable directly by an unprivileged transaction sender through a BPF program invoking `sol_poseidon`.

### Likelihood Explanation
High likelihood of reachability: any unprivileged user can deploy or invoke a BPF program that calls the `sol_poseidon` syscall with attacker-chosen `VmSlice<u8>` lengths pointing at loaded account data. No special privileges, precompile access, or leader cooperation are required — this is a standard syscall available in every SBF program via `sol_poseidon`/`solana_program_runtime` bindings included in the repo (`programs/sbf/c/inc/sol/poseidon.h`, `programs/sbf/c/src/poseidon/poseidon.c`). The only constraint is the number of input sequences (≤12) and the size of accounts loaded into the transaction, both of which are attacker-controllable up to protocol limits.

### Recommendation
Modify `SVMTransactionExecutionCost::poseidon_cost` (or its call site in `SyscallPoseidon::rust`) to incorporate the total byte length of all input slices, analogous to `SyscallHash`'s `hash_byte_cost.saturating_mul(val.len()/...)` per-slice charge, and charge that additional cost *before* invoking `poseidon::hashv`. This should be benchmarked against `light-poseidon` cost-per-byte, not just cost-per-sequence-count, and applied atomically with the existing quadratic base cost so total CU charged is monotonic in both input count and input size.

### Proof of Concept
Conceptual (cannot execute without full BPF toolchain, but derivable from code paths cited):
1. Load an account with several MB of writable data (feasible within `MAX_LOADED_ACCOUNTS_DATA_SIZE_BYTES`).
2. In an SBF program, construct up to 12 `SolBytes`/`VmSlice<u8>` entries whose `addr`/`len` point into that account's large data buffer (each slice several hundred KB to a few MB).
3. Call `sol_poseidon(POSEIDON_PARAMETERS_BN254_X5, endianness, inputs, 12, result)`.
4. Observe: compute meter is only debited `61*12^2+542 = 9,226` CUs (`program-runtime/src/execution_budget.rs:285-293`), independent of slice sizes, while `poseidon::hashv` (`syscalls/src/lib.rs:2506`) processes the full multi-megabyte payload — exactly mirroring the LiquidJS PoC pattern of "small charged metric, large actual work."

*Note: I was unable to directly inspect the `poseidon::hashv` implementation internals (the `poseidon` crate source was not indexed) to confirm the exact big-O relationship between input byte length and hashing time, though the syscall's own translation logic (`translate_vm_slice`) confirms each input slice's byte length is fully attacker-controlled and unbounded by the cost function. This limits full certainty on the precise CPU-time multiplier achievable, but the core finding — that CU charge is decoupled from input byte size — is directly supported by the cited code.*
