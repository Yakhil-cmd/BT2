### Title
CCMenu endpoint bypasses ApiClient stack scoping, letting a stack-scoped token read any stack's build/deploy status - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
The external report's bug class is "a value used to authorize an action is not the same value that is actually acted upon" (minimum-transfer-amount check bypassed by chaining small, individually-valid operations to move funds outside the intended scope). The equivalent binding in shipit-engine is: **the `Stack` a stack-scoped `ApiClient` token is authorized for must equal the `Stack` that a request actually touches.** This binding is enforced in `Shipit::Api::BaseController`, but the CCMenu endpoint re-implements stack lookup without honoring it.

### Finding Description
`Shipit::Api::BaseController` defines the canonical scoping rule for API tokens: [1](#0-0) 

`stacks` restricts the queryable set to `current_api_client.stack_id` when the token is scoped to a specific stack, and `stack` resolves the requested `:stack_id` param **through that restricted relation** (`stacks.from_param!`). Every controller inheriting this behavior normally cannot access a stack outside the token's `stack_id`, as verified by the test "an api client scoped to a stack will only see that one stack": [2](#0-1) 

`Shipit::Api::CCMenuController`, however, overrides `stack` to bypass this scoping entirely, resolving the stack directly from the global `Stack` table instead of the token-scoped relation: [3](#0-2) 

It only checks that the token carries the `read:stack` permission string via `require_permission :read, :stack`, which validates the *permission*, not the *scope*: [4](#0-3) 

The permission check and the scope check are two independent bindings in this codebase (`check_permissions!` vs. `stacks`/`stack`); `CCMenuController` implements the former but skips the latter. A concrete stack-scoped client exists in the fixtures/tests (`here_come_the_walrus`, `stack: shipit`, `permissions: [read:stack]`), demonstrating this is a supported, intentional restriction pattern that the app expects to be honored across all API surfaces: [5](#0-4) 

### Impact Explanation
An attacker holding any valid `ApiClient` token restricted to `read:stack` on Stack A (for example, a token minted for a specific team/stack integration) can query `GET /api/stacks/:stack_id/cc.xml` (`CCMenuController#show`) with an arbitrary `:stack_id` belonging to a different, unauthorized stack, and receive that stack's latest deploy/rollback status (`stack.deploys_and_rollbacks.last`). This is an unauthenticated-for-that-resource read of stack/deploy state across a trust boundary the token was explicitly scoped not to cross — matching the "High: unauthorized read of stack state / deploy output" impact bucket, since the token's authorization equality (`token.stack_id == requested_stack.id`) is broken by design in this one controller.

### Likelihood Explanation
Any holder of a legitimately-issued, narrowly-scoped `read:stack` `ApiClient` token (a realistic, supported configuration per the fixtures and tests) can exploit this with a single unauthenticated-parameter GET request — no privilege escalation, secret leakage, or additional access is required beyond possessing one valid scoped token and knowing/guessing another stack's `to_param` (owner/name/environment), which is often discoverable (e.g., from the Shipit UI, repo name, or public CI badges).

### Recommendation
Change `Shipit::Api::CCMenuController#stack` to resolve the stack through the token-scoped `stacks` relation (i.e., `stacks.from_param!(params[:stack_id])`) instead of the unscoped `Stack.from_param!`, consistent with the rest of `Shipit::Api::BaseController`'s subclasses. Add a regression test asserting that a stack-scoped `ApiClient` token receives a 404/403 when requesting `cc.xml` for a stack outside its `stack_id`.

### Proof of Concept
1. As an authorized Shipit user, mint (or have an admin mint) an `ApiClient` scoped to Stack A only: `ApiClient.create!(creator: user, name: "x", stack: stack_a, permissions: ["read:stack"])`.
2. Using that client's `authentication_token`, request:
   `GET /api/stacks/<stack_b_param>/cc.xml?token=<token>`
   where `stack_b_param` identifies a different stack (`owner/repo/environment`) the token was never granted access to.
3. Observe that `Shipit::Api::CCMenuController#stack` resolves `stack_b` successfully (via unscoped `Stack.from_param!`) and returns `stack_b`'s latest deploy/rollback status in the XML response, even though `require_permission :read, :stack` only validated the permission string and `current_api_client.stack_id` is `stack_a.id`, not `stack_b.id`.

*Note: I could not fully verify the exact fields rendered in the `shipit/ccmenu/project` view template (it lives under `app/views/**`, which is excluded from the indexed scope per the rules), so the precise contents of the leaked XML (e.g., whether it includes deploy URLs or just status) is inferred from the `show` action's use of `stack.deploys_and_rollbacks.last` rather than confirmed from the template itself.*

```ruby
# frozen_string_literal: true

module Shipit
  module Api
    class CCMenuController < BaseController
      require_permission :read, :stack

      class NoDeploy
        def id
          0
        end

        def ended_at
          Time.now.utc
        end

        def running?
          false
        end
      end

      def show
        latest_deploy = stack.deploys_and_rollbacks.last || NoDeploy.new
        render('shipit/ccmenu/project', formats: [:xml], locals: { stack:, deploy: latest_deploy })
      end

      private

      def stack
        @stack ||= Stack.from_param!(params[:stack_id])
      end

      def authenticate_api_client
        @current_api_client = ApiClient.authenticate(params[:token])
        super unless @current_api_client
      end
    end
```
