### Title
`OpenedHandler#provision?` operator-precedence bug bypasses `review_stacks_enabled` for `allow_with_label`/`prevent_with_label` repos - ([File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb])

### Summary
`OpenedHandler#provision?` combines `review_stacks_enabled` with the three provisioning-behavior branches using `&&`/`||` in a way that Ruby parses as `(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?)`. This means `review_stacks_enabled` only gates the `allow_all` branch; when a repository is configured with `allow_with_label` or `prevent_with_label`, an attacker-controlled PR satisfying the label condition causes `provision?` to return `true` even if the operator has set `review_stacks_enabled = false`.

### Finding Description
The claimed binding is: `repository.review_stacks_enabled == true` must hold for `Shipit::ReviewStackAdapter#create!` to be invoked for that repository. The code that is supposed to enforce this is: [1](#0-0) 

Due to Ruby's `&&`/`||` precedence, this is actually evaluated as `(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?)`. Only the first disjunct is gated by `review_stacks_enabled`; the other two are independent of it. So for a repository configured with `provisioning_behavior_allow_with_label?` (or `prevent_with_label?`), `review_stacks_enabled` has no effect on `provision?` at all.

Call path: `respond_to_pull_request_opened?` → `provision?` → true → `process` calls `Shipit::Webhooks::Handlers::PullRequest::ReviewStackAdapter.new(params, scope: repository.review_stacks).find_or_create!`, which calls `create!`, which does `scope.create!(stack_attributes)` and `build_pull_request.update!(github_pull_request: params.pull_request)` inside a transaction, then enqueues the stack for provisioning: [2](#0-1) [3](#0-2) 

The attacker's action is simply opening a pull request against the repository they can PR into, with a label matching `provisioning_label_name` (for `allow_with_label`) or without it (for `prevent_with_label`, the default state with no label). No forged signature, session, or token is needed — this is a logic bug reachable through the normal, correctly-authenticated webhook flow (webhook signature verification is not bypassed and is irrelevant to this bug).

The existing test suite does not catch this: `test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb` tests `allow_with_label`/`prevent_with_label` behaviors only with `provisioning_enabled: true` (the default of the `configure_provisioning_behavior` helper) — [4](#0-3)  and [5](#0-4) . The only test that sets `provisioning_enabled: false` uses `behavior: :allow_all` [6](#0-5) , which happens to be the one branch that is correctly gated, so the bug went untested.

### Impact Explanation
When an operator disables review stacks (`review_stacks_enabled = false`) on a repository configured with `allow_with_label` or `prevent_with_label`, the intended control is bypassed: a `Shipit::Stack`/`Shipit::ReviewStack` row and a `Shipit::PullRequest` row (carrying attacker-controlled `title`, `user.login`, branch ref, etc.) are created for that repository, and the stack is queued via `Shipit::ReviewStackProvisioningQueue.add(stack)` [7](#0-6) . Once queued, `ReviewStackProvisioningQueue#work` will call `stack.provision` if `stack.provisioner.provision?` [8](#0-7) , which can lead to real infrastructure provisioning/deployment for a repository the operator explicitly turned off. This is scoped to the single repository whose `full_name` matches the webhook payload (not a cross-tenant write into an unrelated repository's data), but it is an unauthorized write and unauthorized triggering of the provisioning/deploy pipeline against that repository's explicit configuration — an authorization-bypass condition rather than a cross-tenant one.

### Likelihood Explanation
Preconditions: the repository must be registered in Shipit and have `provisioning_behavior` set to `allow_with_label` or `prevent_with_label` while `review_stacks_enabled` is `false` — a plausible/realistic misconfiguration (e.g., an operator temporarily disabling review stacks without also resetting the behavior, or never realizing that disabling review stacks doesn't actually disable it for non-`allow_all` behaviors). No secrets, tokens, or elevated GitHub permissions are required — any user who can open a PR (or push a label, for `allow_with_label`) against the target repo can trigger it. This is fully repeatable, deterministic, and requires zero attacker sophistication once the misconfiguration precondition holds.

### Recommendation
Add explicit parentheses so `review_stacks_enabled` gates all three branches:
```ruby
def provision?
  repository.review_stacks_enabled && (
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
  )
end
```

### Proof of Concept
minitest in `test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb` style (illustrative, since `test/**` is out of scope for remediation but is the correct verification vehicle):

```ruby
test "does not create stacks when review_stacks_enabled is false, even with allow_with_label + label present" do
  repository = shipit_repositories(:shipit)
  configure_provisioning_behavior(
    repository:,
    provisioning_enabled: false,
    behavior: :allow_with_label,
    label: "pull-requests-label"
  )
  payload = payload_parsed(:pull_request_opened)
  payload["pull_request"]["labels"] << { "name" => "pull-requests-label" }

  assert_no_difference -> { Shipit::Stack.count } do
    assert_no_difference -> { Shipit::PullRequest.count } do
      OpenedHandler.new(payload).process
    end
  end
end
```
Before the fix: `Shipit::Stack.count` and `Shipit::PullRequest.count` both increase (bug reproduced). After applying the recommended fix, both assertions pass, confirming `review_stacks_enabled == false` correctly blocks `create!` regardless of `provisioning_behavior`.
