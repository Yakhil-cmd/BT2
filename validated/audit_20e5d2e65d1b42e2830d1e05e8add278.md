### Title
First-to-register wins ownership race in the AA "registry" pattern - ([File: test/samples/things_registry_and_marketplace.oscript])

### Summary
The `createProject` bug in the referenced Solidity report lets any address permissionlessly become "owner" of a resource simply by being the first to call a public function with a chosen identifier, allowing a front‑runner to seize ownership (and later, sale proceeds) of a resource someone else intended to register. The same "first writer of an unclaimed key wins ownership" pattern exists in ocore's canonical Autonomous Agent (AA) registry/marketplace example, which ships in the repo as a reference design for how AAs should manage ownership state via `var[]`.

### Finding Description
`test/samples/things_registry_and_marketplace.oscript` implements a generic "register a thing and later sell it" AA. Registration is guarded only by checking that the state variable is not already set: [1](#0-0) 

```

    if: `{trigger.data.register AND $id}`,
    init: `{
        if (var['owner_' || $id])
            bounce('thing ' || $id || ' already registered');
        ...
    }`,
    messages: [
        {
            app: 'state',
            state: `{
                var['owner_' || $id] = trigger.address;
                ...
```

Any AA trigger sender who knows (or predicts) the `$id` a legitimate user is about to register can broadcast their own `register` trigger for the same `$id` before the legitimate trigger unit becomes stable. Because AA trigger units are broadcast as regular DAG units — visible to all peers immediately, well before they are ordered/stabilized on the main chain — an attacker monitoring the network can see the target `$id` in the pending unit's `data` payload and race to get a competing trigger processed with an earlier position in the DAG order, exactly analogous to a mempool front-run in Ethereum. Whoever's `register` trigger is evaluated first by the AA engine (order determined by unit/MC ordering, not by who submitted first) claims `var['owner_' || $id] = trigger.address`, and the AA has no mechanism to verify that the registrant is entitled to that `$id`.

Once the attacker owns the id, they control the subsequent `sell`/`buy`/`withdraw_from_sale` cases and can, e.g., immediately list the item for sale and receive payment from a buyer who believes they are dealing with the legitimate registrant: [2](#0-1) 

### Impact Explanation
An attacker can permanently seize ownership of any not-yet-registered `$id` in an AA built on this pattern, then sell the (illegitimate) "thing" to a buyer for real payment via the `buy` case, which forwards `trigger.output[[asset=base]]` to the fraudulent `$owner`. This is a direct fund-loss/fraud vector for the AA's users: legitimate registrants lose the resource they intended to register, and buyers can pay an attacker who has no rightful claim to the registered `$id`. This mirrors the "become owner of the collection and withdraw paymentToken" impact described in the original report.

### Likelihood Explanation
Likelihood is high whenever the `$id` is predictable or observable ahead of finality (e.g., sequential ids, well-known real-world identifiers, or ids visible in the attacker's own mempool/DAG view of the pending trigger unit). Because AA triggers are ordinary public units, their `data` payload (including the `id` and `register`/`sell` flags) is visible to any full node the moment the unit is broadcast, long before the unit is included and made stable, giving an attacker a window to construct and broadcast a competing registration unit with the same identifier.

### Recommendation
Any AA using this "claim an id on first write" pattern should not rely purely on unauthenticated identifiers:
- Require the registrant to prove control over the underlying resource, e.g., via a commit-reveal scheme (commit `hash(id, secret)` first, reveal later) so the actual `id` is not exposed until the committer's claim is already locked in.
- Alternatively, scope ids to the registrant's own address (e.g., `id = trigger.address || '_' || user_supplied_suffix`) so no other address can collide with it.
- Where the resource has an off-chain owner (e.g., a real-world object with an embedded key), require a signature/attestation tied to that resource before allowing registration, as the original report's OpenZeppelin `ECDSA`-based mitigation suggests.

### Proof of Concept
1. Alice wants to register `id = "rare-collectible-42"` in an AA deployed from `things_registry_and_marketplace.oscript` and broadcasts a trigger unit `{data: {register: true, id: "rare-collectible-42"}}`.
2. Before Alice's unit stabilizes, attacker Bob observes the pending unit's payload (public on the DAG) and broadcasts his own trigger unit `{data: {register: true, id: "rare-collectible-42", sell: true, price: 1}}` referencing parents chosen to be ordered ahead of Alice's unit.
3. If Bob's unit ends up processed first (`var['owner_rare-collectible-42']` unset when his `init` block runs), the AA sets `var['owner_rare-collectible-42'] = Bob`, and Alice's later trigger is bounced with `"already registered"`.
4. Bob immediately lists the item for sale; an unsuspecting buyer sends payment to the AA and it is forwarded to Bob per the `buy` case, even though Bob never legitimately owned/registered the resource Alice intended to claim.
