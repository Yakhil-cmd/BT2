### Title
`review_stacks_enabled` bypass via operator precedence in `OpenedHandler#provision?` - (File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb)

### Summary
`OpenedHandler#provision?` combines a review-stacks master switch with per-behavior label logic using `&&`/`||`, but Ruby operator precedence only applies `repository.review_stacks_enabled` to the `provisioning_behavior_allow_all?` clause. The `provisioning_behavior_allow_with_label?` and `provisioning_behavior_prevent_with_label?` clauses are evaluated independently of `review_stacks_enabled`, so a repository owner who disables review stacks (`review_stacks_enabled == false`) but leaves `provisioning_behavior` set to `prevent_with_label` (or `allow_with_label`) will still have review stacks auto-created from unlabeled (or labeled) pull requests.

### Finding Description
The binding that should hold is: `repository.review_stacks_enabled == true` must be true before `ReviewStack.create!` is ever reached for any provisioning behavior.

The actual code:
```ruby
def provision?
  repository.review_stacks_enabled &&
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
``` [1](#0-0) 

Due to `&&` binding tighter than `||`, this parses as:
`(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?)`

So `review_stacks_enabled` only gates the `allow_all` path. For `provisioning_behavior == 'prevent_with_label'`, the third disjunct `(prevent_with_label? && !has_label?)` is evaluated with no reference to `review_stacks_enabled` at all — if it's true, the whole `||` expression is true regardless of the first clause's value.

`respond_to_pull_request_opened?` calls `provision?` directly [2](#0-1) , and `process` uses that result to gate `ReviewStackAdapter#find_or_create!` [3](#0-2) , which calls `create!`, building a `ReviewStack` with `branch: params.pull_request.head.ref` and enqueuing it for provisioning [4](#0-3) .

Neither `Repository` nor `NullRepository` re-check `review_stacks_enabled` anywhere else in this path [5](#0-4) , and the `Repository#review_stacks` association places no additional constraint. Nothing in webhook signature verification, `ExplicitParameters`, or model validations addresses this — those controls authenticate the webhook and validate schema shape, not the provisioning policy logic.

Attacker's exact request: open a pull request (from a fork, as any GitHub user with permission to open PRs against the target repo) with no labels, against a repository configured with `review_stacks_enabled: false` and `provisioning_behavior: 'prevent_with_label'`. GitHub emits a `pull_request` "opened" webhook; `OpenedHandler#process` runs `provision?`, which evaluates true, and a `ReviewStack` is created and queued for provisioning even though the repository owner disabled review stacks entirely.

### Impact Explanation
The immediate effect is unauthorized creation of a `Shipit::ReviewStack` record and enqueueing it via `ReviewStackProvisioningQueue.add`, which subsequently triggers `stack.provisioner.provision?` / `stack.provision` [6](#0-5) . This is scoped to the repository the PR was opened against (not cross-tenant — the attacker cannot target a different repository's stacks), but it is a bypass of an explicit owner-configured control (`review_stacks_enabled = false`), causing infrastructure provisioning workflows to run that the repository owner intended to be fully disabled. This is repeatable for any pull request opened against any repository misconfigured with `review_stacks_enabled: false` + `provisioning_behavior: prevent_with_label` (or `allow_with_label`), by any user able to open a PR (including from a fork) or relabel it.

### Likelihood Explanation
Requires the repository to be configured with `review_stacks_enabled: false` and `provisioning_behavior` set to `allow_with_label` or `prevent_with_label` — i.e., an operator who explicitly disabled review stacks but left the provisioning-behavior field in a non-default state (this combination is plausible: `review_stacks_enabled` may be flipped off after having previously configured a label policy). No secrets or elevated privileges are needed; only the ability to open a pull request (or add/remove its label) against the repository, which is standard GitHub contributor capability. Fully feasible and repeatable with zero cost per exploit attempt.

### Recommendation
Parenthesize the `provision?` boolean expression so `review_stacks_enabled` gates all clauses:
```ruby
def provision?
  repository.review_stacks_enabled? && (
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
  )
end
```
Apply the same audit/fix to `LabeledHandler`, `UnlabeledHandler`, and `ReopenedHandler`, which share similar `review_stacks_enabled`/`provisioning_behavior` conditionals per the earlier grep results.

### Proof of Concept
Add a minitest to `test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb`:
```ruby
test "does not create stacks when review_stacks_enabled is false, even with prevent_with_label" do
  repository = shipit_repositories(:shipit)
  configure_provisioning_behavior(
    repository:,
    provisioning_enabled: false,
    behavior: :prevent_with_label,
    label: "pull-requests-label"
  )
  payload = payload_parsed(:pull_request_opened)
  payload["pull_request"]["labels"] = []

  assert_no_difference -> { Shipit::ReviewStack.count } do
    OpenedHandler.new(payload).process
  end
end
```
Binding assertion before fix: `repository.review_stacks_enabled == false` while `Shipit::ReviewStack.count` still increases (assertion fails, proving the bug). After applying the recommended fix, `review_stacks_enabled == false` implies no `ReviewStack` row is created, and the test passes.
