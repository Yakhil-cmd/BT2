### Title
Unchecked scaled-value overflow permanently freezes all market operations - ([File: common/src/rates/scaling.rs](common/src/rates/scaling.rs))

### Summary

A market can reach a state where merely unscaling its aggregate debt or supply during interest accrual overflows `i128`. Because every state-changing pool operation accrues interest before applying the requested action, that overflow permanently blocks withdrawals, repayments, liquidations, recapitalization, and subsequent index updates for the market.

Severity: **Medium**.

### Finding Description

`accrue_step` converts aggregate debt and supply shares to their live values before calculating utilization:

```rust
let borrowed_original = scaled_to_original(env, borrowed, borrow_index);
let supplied_original = scaled_to_original(env, supplied, supply_index);
let util = utilization(env, borrowed_original, supplied_original);
```

`scaled_to_original` performs checked fixed-point multiplication and panics with `MathOverflow` when `scaled * index / RAY` exceeds `i128::MAX`. [1](#0-0) [2](#0-1) 

The borrow-index ceiling does not prevent this state. The ceiling is applied only inside `update_borrow_index`, after `accrue_step` has already unscaled both aggregates for utilization. [3](#0-2)  Once either aggregate's scaled value exceeds `i128::MAX`, the next accrual panics before the index can be capped.

Every ordinary pool operation loads the market through `synced_market`, which unconditionally calls `interest::global_sync` before the operation-specific logic. [4](#0-3)  `global_sync` invokes `accrue_step` for each elapsed interval. [5](#0-4) [6](#0-5) 

This also removes the recovery path: `recapitalize` calls `ops::renewed_market`, which itself performs `synced_market` and therefore panics during accrual before any cash can be credited. [7](#0-6) [8](#0-7) 

The existing long-horizon test demonstrates the concrete cliff: one billion whole units of an 18-decimal asset at 98% utilization eventually causes `update_indexes` to fail with `MathOverflow`, after which both withdrawal and repayment fail with the same error while the borrow index remains below its configured cap. [9](#0-8) 

### Impact Explanation

All user funds associated with the affected market become permanently unavailable:

- suppliers cannot withdraw;
- borrowers cannot repay;
- liquidators cannot process unhealthy positions;
- revenue cannot be claimed;
- bad debt cannot be cleaned;
- `recapitalize` cannot add cash because it accrues first.

This is not a temporary fail-closed condition: the persisted `last_timestamp` remains behind the current ledger timestamp, so every subsequent transaction reaches the same overflowing accrual expression. [4](#0-3) [7](#0-6) 

The qualifying impact is **permanent freezing of funds** and a market that can no longer operate.

### Likelihood Explanation

Triggering the condition requires a very large market balance and sustained debt utilization over multiple years, so it is not a low-cost griefing primitive. [10](#0-9) 

Nevertheless, no privileged operation is required after the market exists. A single sufficiently funded account can:

1. supply the borrowable asset;
2. supply collateral;
3. borrow most of the supplied asset;
4. leave the position until aggregate scaled value crosses the `i128` boundary;
5. call permissionless `update_indexes`.

`update_indexes` only requires caller authorization and forwards the supplied `Vec<HubAssetKey>` to the pool. [11](#0-10) [12](#0-11) 

Because the threshold is an arithmetic property of the live market rather than attacker-controlled malformed input, ordinary organic growth can also reach it even without a deliberate attack.

### Recommendation

Do not compute utilization by first materializing complete unscaled aggregates in `i128`.

At minimum, calculate utilization using a widened or reduced expression such as comparing debt and supply through `I256`, or algebraically cancel shared scale factors before conversion. Index capping should also occur before any checked multiplication whose result can exceed `i128`.

Accrual should additionally be failure-isolated from remediation paths. In particular, `recapitalize`, repayment, withdrawal, liquidation, and bad-debt cleanup need a path that can proceed or use saturated valuation when aggregate accrual arithmetic exceeds the representable range.

### Proof of Concept

A single funded account can reproduce the existing harness scenario conceptually:

```text
1. supply(
     caller = attacker,
     account_id = A,
     deposits = [
       (HubAssetKey { hub_id: H, asset: BIG18 },
        1_000_000_000 * 10^18)
     ]
   )

2. supply(
     caller = attacker,
     account_id = A,
     deposits = [
       (HubAssetKey { hub_id: H, asset: collateral_asset },
        sufficient_collateral)
     ]
   )

3. borrow(
     caller = attacker,
     account_id = A,
     borrows = [
       (HubAssetKey { hub_id: H, asset: BIG18 },
        980_000_000 * 10^18)
     ],
     to = attacker
   )

4. Wait until BIG18's aggregate scaled debt or supply value exceeds i128::MAX.

5. update_indexes(
     caller = attacker,
     assets = [HubAssetKey { hub_id: H, asset: BIG18 }]
   )
```

The repository test uses the same market shape: `1_000_000_000 * 10^18` supplied base units and 98% of that amount borrowed. [13](#0-12) 

When accrual next runs, `scaled_to_original(borrowed, borrow_index)` or `scaled_to_original(supplied, supply_index)` panics before utilization or index capping can complete. [3](#0-2)  The test confirms `MathOverflow`, an uncapped borrow index, and subsequent withdrawal and repayment failures. [14](#0-13)

```rust
pub(crate) fn global_sync(env: &Env, cache: &mut Cache) {
    if !cache.needs_accrual() {
        return;
    }

    let mut remaining = cache.elapsed_ms();
    while let Some(nonzero) = NonZeroU64::new(remaining) {
        let chunk = nonzero.get().min(MAX_COMPOUND_DELTA_MS);
        accrue_chunk(env, cache, chunk);
        remaining = remaining.saturating_sub(chunk);
    }

    cache.mark_accrued();
```

```rust
/// The cliff. A billion whole tokens is `1e36` raw ray; the value ceiling is
/// `i128::MAX`, 170 times that. At the XLM curve's steep segment the index
/// grows past 170x in a few years, and the next accrual panics inside
/// `scaled_to_original`. Every verb accrues first, so the market freezes:
/// no repay, no withdraw, no liquidation. The index cap never engages.
#[test]
fn a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap() {
    let mut t = LendingTest::new()
        .with_market(big("BIG18", 18, xlm_curve()))
        .with_market(col())
        .with_max_utilization_disabled_all_markets()
        .build();
    lift_caps(&t, "BIG18", 18);
    lift_caps(&t, "COL", 7);
    let principal = BILLION * 10i128.pow(18);
    t.supply_raw(BOB, "BIG18", principal);
    let debt = principal / 100 * 98;
    t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
    t.borrow_raw(ALICE, "BIG18", debt);

    let mut years = 0u32;
    let failure = loop {
        years += 1;
        assert!(
            years <= 40,
            "no cliff within 40 years; the bound in docs/reference/formulas.md is wrong"
        );
        t.advance_time(YEAR_SECS);
        if let Err(e) = t.try_update_indexes_for(&["BIG18"]) {
            break e;
        }
    };
    let failed: Result<(), soroban_sdk::Error> = Err(failure);
    assert_contract_error(failed, errors::MATH_OVERFLOW);
    let last = book(&t, "BIG18");
    assert!(
        last.borrow_index < MAX_BORROW_INDEX_RAY,
        "the index cap did not engage before the value overflow"
    );
    // The market is frozen: exits and repayments accrue first and hit the same panic.
    assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
    assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
```
