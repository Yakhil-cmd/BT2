## Title
Wallet-contract cross-contract callback can be permanently gas-griefed by an attacker-controlled contract, leaving `has_in_flight_tx` stuck and the account's Eth-transaction execution locked forever - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The `WalletContract` used to emulate Ethereum-style transactions on NEAR serializes all execution through an `in-flight` flag, `has_in_flight_tx`, which is only cleared inside asynchronous callback methods (`address_check_callback`, `nep_141_storage_balance_callback`, `rlp_execute_callback`, `ban_relayer`) after they successfully run [1](#0-0) . If any of these callbacks runs out of the fixed gas budget it was given while processing attacker-influenced response data, the callback aborts, no state change (including the flag reset) is persisted, and the account becomes permanently stuck with `has_in_flight_tx = true`, blocking all future `rlp_execute` calls. This is directly analogous to the `settleContract()` bug: an external, callee-controlled call whose response is processed inside gas-limited logic can be weaponized to force an out-of-gas abort that blocks the victim's ability to finalize/continue their transaction.

### Finding Description
`rlp_execute` refuses to start a new transaction while `has_in_flight_tx` is `true` [2](#0-1) . The flag is set to `true` right before returning a promise chain, and is only reset to `false` at the top of a callback that is `.then()`-chained onto that promise [3](#0-2) .

For the emulated ERC-20 transfer path, the intermediate step calls the target token contract's `storage_balance_of` and processes the result inside `nep_141_storage_balance_callback`, deserializing the attacker-controlled response with `serde_json::from_slice` [4](#0-3) . The gas budget for this callback is fixed and computed ahead of time as `NEP_141_STORAGE_BALANCE_CALLBACK_GAS.saturating_add(action.gas())` [5](#0-4) , where `NEP_141_STORAGE_BALANCE_CALLBACK_GAS` is only ~15 Tgas [6](#0-5) . The same pattern exists for `address_check_callback`, which deserializes the address registrar's response with the same fixed extra budget `ADDRESS_CHECK_CALLBACK_GAS` [7](#0-6) .

Per nearcore's execution model, if a function call exhausts its attached/prepaid gas mid-execution, it aborts with `GasExceeded`/`Exceeded the prepaid gas` and **no state changes are persisted** for that call [8](#0-7) . This is exactly the underlying mechanism exploited in the Solidity report (an out-of-gas revert nullifying a state transition the victim depends on). Because `self.has_in_flight_tx = false;` is the very first state write inside the callback body, if the subsequent `serde_json::from_slice` deserialization of a maliciously crafted, gas-expensive response consumes all remaining gas before the function returns, the entire receipt aborts and the flag reset is rolled back — leaving `has_in_flight_tx` at its prior value of `true` forever, since no further receipt in the promise chain will execute to reset it.

The token/registrar contract that is called is outside the wallet-contract's control and can be built to return a payload engineered to maximize `serde_json` parsing cost (e.g., deeply nested or malformed JSON) within the small amount of gas it is allotted for its own execution (`NEP_141_STORAGE_BALANCE_OF_GAS` / `REGISTRAR_LOOKUP_GAS`, 5 Tgas each) [9](#0-8) , forcing the wallet's fixed-gas callback to run out of gas while parsing it.

### Impact Explanation
Once triggered, the affected eth-wallet-contract account can never again process `rlp_execute` because `has_in_flight_tx` is stuck `true` and there is no public/private recovery method to reset it [10](#0-9) . This permanently denies the account owner the ability to submit any further emulated Ethereum transactions through this contract instance — the same class of "victim locked out of exercising their rights" impact described in the ERC721 `settleContract()` report, transposed to NEAR's async receipt/callback and gas-accounting model.

### Likelihood Explanation
Reaching this requires only that the wallet owner (or a relayer acting on their signed transaction) interacts with an ERC-20-emulated token contract or the address registrar that is adversarial or compromised, both of which are ordinary unprivileged contract accounts reachable by a normal `FunctionCall` action/receipt — no validator or network-layer privilege is needed. The trigger is a single crafted response payload from that external contract during normal callback processing.

### Recommendation
- Do not couple clearing of `has_in_flight_tx` to the same gas-limited execution that also performs untrusted deserialization; reset the flag independently of parse success/failure, or perform response validation in a way that is bounded in cost regardless of response size (e.g., cap response length before deserializing, or move the flag reset to occur even on the abort path via a scheduled follow-up receipt).
- Ensure callback gas budgets (`ADDRESS_CHECK_CALLBACK_GAS`, `NEP_141_STORAGE_BALANCE_CALLBACK_GAS`) are sized independently of attacker-controlled response size, and bound the size of data accepted from external calls before deserialization (analogous to the ERC-721 receiver "try/catch" fix suggested in the source report, but adapted to guarantee state finalization regardless of downstream gas exhaustion).

### Proof of Concept
1. Deploy a malicious NEP-141-like contract as the `target`/`token_id` for an emulated ERC-20 transfer, or compromise/spoof the address registrar contract.
2. Have that contract's `storage_balance_of` (or `lookup`) method return a JSON payload deliberately engineered to be maximally expensive to parse with `serde_json::from_slice` relative to the small extra gas margin (`NEP_141_STORAGE_BALANCE_CALLBACK_GAS`/`ADDRESS_CHECK_CALLBACK_GAS`, ~10-15 Tgas) available to the wallet's callback [4](#0-3) .
3. Submit (or relay) an `rlp_execute` transaction targeting this contract; the wallet sets `has_in_flight_tx = true` and schedules the callback [11](#0-10) .
4. The callback aborts with `GasExceeded` while deserializing the malicious response; per nearcore semantics no state changes persist [8](#0-7) , so `has_in_flight_tx` remains `true`.
5. Any subsequent call to `rlp_execute` on this wallet account now immediately returns `"transaction already in progress"` indefinitely, with no available recovery method [10](#0-9) .

### Gas in Contract Calls

A function call has a fixed gas cost to be initiated. Then the execution itself
draws gas from the `attached_gas`, sometimes also called `prepaid_gas`, until it
reaches zero, at which point the function call aborts with a `GasExceeded`
error. No changes are persisted on chain.
