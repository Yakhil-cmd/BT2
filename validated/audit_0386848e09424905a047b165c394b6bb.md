## Analysis

The Sherlock H-4 bug class is: a shared, mutable reward pool is divided among multiple claimants proportionally to their stake, but the per-claimant share is computed from the *current* value of that shared pool at claim time rather than a value fixed/cached for the period being paid out — so as the pool value changes (via cliffs, other claims, or new deposits), claimants processed at different times receive inconsistent, and in aggregate over/under-distributed shares.

Agave's SIMD-0123 "block revenue sharing" path contains the same structural pattern. [1](#0-0) 

`deposit_delegator_rewards` lets any signer permissionlessly add to `pending_delegator_rewards` on a vote account via a simple `checked_add`, making it a cumulative, ever-growing pool rather than a per-epoch snapshot value: [2](#0-1) 

At each epoch's reward calculation, `calculate_block_reward` divides the vote account's **current** `pending_delegator_rewards()` value among every delegator proportional to `stake / total_active_stake`: [3](#0-2) 

This is invoked once per stake delegation inside `calculate_stake_rewards_and_commissions`, using the same `pending_delegator_rewards` read for every stake in that pass: [4](#0-3) 

Critically, `recalculate_stake_rewards` — invoked whenever a bank is created while an epoch-reward distribution is still `Active` (e.g. bank warps/forks mid-distribution) — **re-derives** `cached_vote_accounts`/`pending_delegator_rewards` from current state and recomputes `block_reward` for the *same rewarded_epoch* a second (or Nth) time: [5](#0-4) 

The developers' own comment on `calculate_block_reward` acknowledges the exact symptom described in the Sherlock finding — that recalculation can make "individual rewards look greater than the pending rewards" because the divisor (`total_active_stake`) is frozen from `RewardEpochDelegatedStakes`, but the pool value (`pending_delegator_rewards`) being divided is read fresh/live each time, and it is merely clamped rather than reconciled: [6](#0-5) 

I could not locate, within the files retrieved, any code path that decrements/reserves `pending_delegator_rewards` on the vote account atomically with the reward calculation pass (only `block_reward_lamports_distributed`/`block_reward_lamports_burned` capitalization counters are tracked during distribution) — I was unable to fully trace whether or where the vote account's `pending_delegator_rewards` field itself is debited during `distribute_epoch_rewards_in_partition`/`distribute_reward_commissions`, so I cannot conclusively confirm whether double-distribution across epochs occurs versus only the cross-recalculation inconsistency documented by the clamp comment. This is a genuine gap in verification, not a claim to hide.

### Title
Block-revenue-sharing reward calculation divides a live, mutable `pending_delegator_rewards` pool instead of a value fixed per rewarded epoch, causing inconsistent/duplicated reward attribution across recalculations - (File: runtime/src/bank/partitioned_epoch_rewards/calculation.rs)

### Summary
`calculate_block_reward` computes each delegator's share of SIMD-0123 block revenue by dividing the vote account's *current* `pending_delegator_rewards` balance by each stake's fraction of `total_active_stake`, and this calculation can run multiple times for the same `rewarded_epoch` via `recalculate_stake_rewards` whenever a bank is created mid-distribution. Because `pending_delegator_rewards` is a cumulative counter that anyone can add to via `DepositDelegatorRewards`, and is read live rather than snapshotted per rewarded-epoch, the divisor pool used to compute each delegator's share can differ between the original calculation and later recalculations for the exact same epoch's payout.

### Finding Description
`pending_delegator_rewards` on a `VoteStateV4` account is a running total incremented via `deposit_delegator_rewards`/`add_pending_delegator_rewards`, with no per-epoch reset or reservation mechanism visible in the reviewed code. [2](#0-1) 

`calculate_block_reward` reads this live value and divides it pro-rata across delegated stake using a fixed `total_active_stake` snapshot (`RewardEpochDelegatedStakes`), but an unfixed reward pool (`pending_delegator_rewards`): [7](#0-6) 

This same function is called both during the original reward calculation at the epoch boundary (`calculate_rewards_for_partitioning` → `calculate_validator_rewards` → `calculate_stake_rewards_and_commissions`) and again during `recalculate_stake_rewards`, which is triggered on every bank creation while an `EpochRewardStatus` is `Active` (i.e., mid multi-block distribution): [8](#0-7) [5](#0-4) 

Between the original calculation and a subsequent recalculation, `pending_delegator_rewards` on the vote account can change (new deposits arrive, or is spent) while `total_active_stake` stays fixed to the rewarded epoch. The result is that stakes rewarded during the first calculation pass and stakes rewarded during a later recalculation pass for the *same rewarded_epoch* can be computed against different pool sizes — exactly the "uses the current value instead of the value at accrual time" root cause identified in the CVX/AURA report, just applied to Agave's block-revenue-sharing delegator pool instead of a Convex/Aura cliff-based emission schedule. The code's own clamp (`.min(pending_delegator_rewards)`) and comment acknowledge that "individual rewards look greater than the pending rewards" can occur during recalculation, i.e., the mismatch is a known, unhandled edge rather than a theoretical concern.

### Impact Explanation
If the pool grows between the initial calculation and a recalculation (e.g., a new `DepositDelegatorRewards` lands in between), stakes rewarded in the later pass receive a share computed from an inflated pool relative to what earlier-processed stakes for the same epoch received — misattributing block-revenue rewards across delegators of the same validator and epoch. If the pool shrinks, some legitimately-earned rewards are clamped away and effectively lost. Either direction constitutes misattributed or lost lamport rewards for delegators, matching the accepted impact classes (misattributed/duplicated rewards, or loss of legitimately-owed rewards).

### Likelihood Explanation
This requires: (1) a validator/vote account participating in SIMD-0123 block revenue sharing with a delegator pool (`pending_delegator_rewards` > 0), and (2) a bank being created while that epoch's reward distribution is still `Active` and a deposit (or other pool-value shift) occurring in between the initial calculation and the recalculation. Bank warps/forks during the multi-block partitioned distribution window are a normal, expected occurrence (not an attacker-controlled edge case), and `DepositDelegatorRewards` is a permissionless instruction any account can call at any time, so the preconditions are readily reachable during ordinary network operation rather than requiring an adversarial actor.

### Recommendation
Snapshot the exact `pending_delegator_rewards` amount to be distributed for a given `rewarded_epoch` once, at the initial reward-calculation pass, and reuse that fixed value for any subsequent recalculation of the same epoch's rewards (analogous to how `total_active_stake`/`RewardEpochDelegatedStakes` is already frozen). Ensure the vote account's `pending_delegator_rewards` is decremented atomically as the corresponding portion is distributed, so that the same lamports cannot be counted toward more than one calculation pass or more than one epoch's payout.

### Proof of Concept
Conceptual sequence (not independently executed, based on code review):
1. Vote account V has delegated stakes A (60%) and B (40%) for `rewarded_epoch=E`. `pending_delegator_rewards = 100`.
2. Epoch boundary triggers `calculate_rewards_for_partitioning`; `calculate_block_reward` computes A's share as 60, B's as 40, matching the current pool of 100. [7](#0-6) 
3. Before A's/B's stake-reward partitions are fully distributed, another bank is created (fork/warp) while `EpochRewardStatus::Active`, triggering `recalculate_partitioned_rewards_if_active` → `recalculate_stake_rewards` for the same `rewarded_epoch=E`. [8](#0-7) 
4. In between steps 2 and 3, someone calls `DepositDelegatorRewards` adding 50 more lamports, so `pending_delegator_rewards` is now 150 when read during recalculation. [1](#0-0) 
5. Recalculation now computes A's share as 90, B's as 60 (150 total) for the *same* epoch E, rather than reusing the originally-computed 60/40 split — inflating the total amount attributed to epoch E's block reward beyond the 100 lamports that were actually earned for that period, or, in the reverse scenario (pool spent down), clamping rewards below what was legitimately computed initially.

pub fn deposit_delegator_rewards<S: std::hash::BuildHasher>(
    invoke_context: &mut InvokeContext,
    vote_account_index: IndexOfAccount,
    sender_account_index: IndexOfAccount,
    deposit: u64,
    signers: &HashSet<Pubkey, S>,
) -> Result<(), InstructionError> {
    let transaction_context = &invoke_context.transaction_context;
    let instruction_context = transaction_context.get_current_instruction_context()?;

    let vote_address = *instruction_context.get_key_of_instruction_account(vote_account_index)?;
    let source_address =
        *instruction_context.get_key_of_instruction_account(sender_account_index)?;

    // Source account must sign the transfer.
    verify_authorized_signer(&source_address, signers)?;

    // SIMD-0123 states we must validate the vote account deserializes to a v4
    // *before* attempting CPI, then update the `pending_delegator_rewards`
    // field *last*.
    // We can deserialize it, and hold onto the deserialized payload in-memory.
    // This way, we can drop the account borrow but avoid re-deserializing
    // later, since we know only lamports will change.
    let mut vote_state = {
        let vote_account =
            instruction_context.try_borrow_instruction_account(vote_account_index)?;

        // Can't use `get_vote_state_handler_checked`, since it will convert
        // the underlying vote state to v4.
        // SIMD-0123 requires an *initialized v4*.
        let versioned = VoteStateVersions::deserialize(vote_account.get_data())?;
        if let VoteStateVersions::V4(vote_state_v4) = versioned {
            Ok(VoteStateHandler::new_v4(*vote_state_v4))
        } else {
            Err(InstructionError::InvalidAccountData)
        }
    }?;

    // CPI to System: Transfer from sender to vote account.
    invoke_context.native_invoke_signed(
        system_instruction::transfer(&source_address, &vote_address, deposit),
        &[],
    )?;

    // Update `pending_delegator_rewards`.
    let transaction_context = &invoke_context.transaction_context;
    let instruction_context = transaction_context.get_current_instruction_context()?;
    let mut vote_account =
        instruction_context.try_borrow_instruction_account(vote_account_index)?;

    vote_state.add_pending_delegator_rewards(deposit)?;
    vote_state.set_vote_account_state(&mut vote_account)
}

/// Calculates block reward for a stake account based on SIMD-0123
fn calculate_block_reward(
    rewarded_epoch: Epoch,
    delegation: &Delegation,
    stake_history: &StakeHistory,
    distribution_epoch_vote_accounts: &VoteAccounts,
    ag_epoch_type: &AlpenglowEpochType,
    new_warmup_cooldown_rate_epoch: Option<Epoch>,
    use_fixed_point_stake_math: bool,
) -> u64 {
    let vote_pubkey = delegation.voter_pubkey;
    let Some(vote_account) = distribution_epoch_vote_accounts.get(&vote_pubkey) else {
        debug!("could not find vote account {vote_pubkey} in cache");
        return 0;
    };
    let vote_state = vote_account.vote_state_view();
    let pending_delegator_rewards = vote_state.pending_delegator_rewards();
    // NOTE: during recalculation, `distribution_epoch_vote_accounts` already
    // includes updated stake activation values from after the new epoch
    // calculation, so we need to use `RewardEpochDelegatedStakes` for the exact
    // values at the end of the reward epoch.
    let (AlpenglowEpochType::Alpenglow {
        reward_epoch_delegated_stakes,
        ..
    }
    | AlpenglowEpochType::MigrationEpoch {
        reward_epoch_delegated_stakes,
        ..
    }) = ag_epoch_type
    else {
        debug!("Alpenglow must be enabled for block reward calculation");
        return 0;
    };
    let total_active_stake = reward_epoch_delegated_stakes
        .delegated_stakes
        .get(&vote_pubkey)
        .copied()
        .unwrap_or(0);
    if total_active_stake == 0 {
        0
    } else {
        let stake = delegation_effective_stake(
            delegation,
            rewarded_epoch,
            stake_history,
            new_warmup_cooldown_rate_epoch,
            use_fixed_point_stake_math,
        );
        // During recalculation, if stake account has already received rewards,
        // it's possible to have `stake > total_active_stake`. If
        // `pending_delegator_rewards` is a huge number, we could potentially
        // overflow a `u64`. We can also have individual rewards look greater
        // than the pending rewards. This is harmless in practice, but we
        // clamp it just to be safe
        (pending_delegator_rewards as u128 * stake as u128 / total_active_stake as u128)
            .try_into()
            .unwrap_or(u64::MAX)
            .min(pending_delegator_rewards)
    }
}

    /// If rewards are still active, recalculates partitioned stake rewards and
    /// updates Bank::epoch_reward_status. This method assumes that reward
    /// commissions have already been calculated and delivered, and *only*
    /// recalculates stake rewards
    pub(in crate::bank) fn recalculate_partitioned_rewards_if_active<F, TP>(
        &mut self,
        thread_pool_builder: F,
    ) where
        F: FnOnce() -> TP,
        TP: std::borrow::Borrow<ThreadPool>,
    {
        let epoch_rewards_sysvar = self.get_epoch_rewards_sysvar();
        if epoch_rewards_sysvar.active {
            let thread_pool = thread_pool_builder();
            let (stake_rewards, partition_indices) =
                self.recalculate_stake_rewards(&epoch_rewards_sysvar, thread_pool.borrow());
            self.set_epoch_reward_status_distribution(
                epoch_rewards_sysvar.distribution_starting_block_height,
                stake_rewards,
                partition_indices,
            );
        }
    }

    fn recalculate_stake_rewards(
        &self,
        epoch_rewards_sysvar: &EpochRewards,
        thread_pool: &ThreadPool,
    ) -> (Arc<PartitionedStakeRewards>, Vec<Vec<usize>>) {
        assert!(epoch_rewards_sysvar.active);
        // If rewards are active, the rewarded epoch is always the immediately
        // preceding epoch.
        let rewarded_epoch = self.epoch().saturating_sub(1);

        let point_value = PointValue {
            rewards: epoch_rewards_sysvar.total_rewards,
            points: epoch_rewards_sysvar.total_points,
        };

        let stakes = self.stakes_cache.stakes();
        let EpochRewardCalculateParamInfo {
            stake_history,
            stake_delegations,
            cached_vote_accounts,
        } = self.get_epoch_params_for_recalculation(rewarded_epoch, &stakes);
        let ag_epoch_type = AlpenglowEpochType::get(self, rewarded_epoch, || {
            RewardEpochDelegatedStakes::get(self)
        });

        // On recalculation, only the `StakeRewardCalculation::stake_rewards`
        // field is relevant. It is assumed that reward commission accounts have
        // already been calculated and delivered, while
        // `StakeRewardCalculation::total_rewards` only reflects rewards that
        // have not yet been distributed.
        //
        // NOTE: the `RewardCommissionAccounts` will NOT have a correct
        // post_lamport amount if the commission account is NOT the vote account,
        // because the commission account is loaded from the current bank, and
        // not the start of the epoch. We don't have a snapshot of all commission
        // accounts from the start of the epoch. For this reason, the
        // `RewardCommissionAccounts` calculated in this function call should
        // NOT be used ever.
        let (_, StakeRewardCalculation { stake_rewards, .. }) = self
            .calculate_stake_rewards_and_commissions(
                &stake_history,
                stake_delegations,
                cached_vote_accounts,
                rewarded_epoch,
                point_value,
                &ag_epoch_type,
                thread_pool,
                null_tracer(),

            );
