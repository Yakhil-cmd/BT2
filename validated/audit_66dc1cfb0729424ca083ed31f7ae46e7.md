### Title
Webhook signature verified against the payload's `repository.owner.login` organization, but handlers resolve the target repository/stack from the unverified `repository.full_name` field, allowing cross-organization writes - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/`webhook_secret` to validate the `X-Hub-Signature` against based on `repository_owner`, computed as `params.dig('repository', 'owner', 'login')` (falling back to `params.dig('organization', 'login')`). [1](#0-0) [2](#0-1)  However, every event handler resolves the actual repository/stack to act on using a different field, `payload.dig('repository', 'full_name')`, via `Handler#repository_name` / `Repository.from_github_repo_name`. [3](#0-2) [4](#0-3)  Nothing ties `repository.owner.login` (the field whose org determines which `webhook_secret` verifies the HMAC) to `repository.full_name` (the field the write actually targets).

### Finding Description
In a multi-organization Shipit deployment, `Shipit.github_app_config` looks up a distinct `webhook_secret` per configured GitHub organization key. [5](#0-4)  The controller's `verify_signature` uses `repository_owner` purely to pick *which* org's secret to check the signature with: `Shipit.github(organization: repository_owner)` then `verify_webhook_signature(header, raw_post)`. [6](#0-5) 

Once the signature check passes, `WebhooksController#create` dispatches the full, unmodified JSON payload to handlers. [7](#0-6)  All handlers (`PushHandler`, `PullRequest::OpenedHandler`, `PullRequest::ClosedHandler`, `PullRequest::LabeledHandler`, `PullRequest::UnlabeledHandler`, etc.) derive the target `Repository`/`Stack` from `payload.dig('repository', 'full_name')` — not from `repository.owner.login`. [3](#0-2) [8](#0-7) [9](#0-8)  `Repository.from_github_repo_name` splits `full_name` on `/` and looks up by `owner`/`name` columns with no relation to which webhook secret validated the request. [4](#0-3) 

This breaks the intended binding: `verified_signing_org (repository.owner.login) == acted_upon_repository_org (repository.full_name)`. An attacker who controls a GitHub organization "OrgA" (and therefore legitimately knows OrgA's `webhook_secret`, since that secret is configured when OrgA's admin sets up the GitHub App integration) can send a request whose HMAC is computed over a JSON body where `repository.owner.login = "OrgA"` (so the signature verifies against OrgA's registered secret) but `repository.full_name = "VictimOrg/victim-repo"` (a completely different, unrelated tenant's repository hosted on the same Shipit instance). Because `Repository.from_github_repo_name` and `Handler#repository_name` only look at `full_name`, the handler will act on `VictimOrg/victim-repo`'s stacks even though the signature was never validated against `VictimOrg`'s secret.

Concretely: for the `push` event, `PushHandler#process` calls `stack.sync_github(expected_head_sha: params.after)` on every non-archived stack of the victim repository matching the pushed branch. [10](#0-9)  This forces the victim's Shipit stack to resync to an attacker-chosen `after` SHA, i.e., an attacker-controlled commit becomes recognized as the pending/deployable head for a repository the attacker does not own or have write access to — a cross-organization write into a tenant the attacker was never authorized to touch.

### Impact Explanation
This is a cross-repository/cross-tenant write: an unprivileged attacker who only controls their own GitHub organization's webhook secret can force state changes (which SHA is synced/deployable) on a victim organization's stack that lives on the same shared Shipit instance, entirely bypassing the per-organization webhook secret isolation that `Shipit.github(organization:)` is meant to enforce. This matches the Critical-tier "cross-repository writes" impact category, since the compromised binding is exactly "organization that authenticated versus the repository that is written."

### Likelihood Explanation
Likelihood is Medium: exploitation requires (a) the target Shipit deployment hosting multiple GitHub organizations/tenants under the same instance with the multi-org secrets schema (`config.github.<org>.webhook_secret`), and (b) the attacker controlling at least one such onboarded organization (which they can do without any special privilege beyond being able to register/administer their own GitHub App installation against the shared Shipit instance). No GitHub write access to the victim repo, no Shipit session, and no `ApiClient` token are required — only knowledge of the attacker's own org's `webhook_secret`, which the attacker legitimately possesses.

### Recommendation
Bind the field used for authorization/dispatch to the field whose organization was cryptographically verified. Concretely, after `verify_signature` succeeds, validate that the payload's `repository.full_name` (and `organization.login`/`repository.owner.login` used elsewhere) is owned by the exact organization that the signature was checked against, rejecting (422) any request where these disagree. Alternatively, have `Handler#repository_name`/`Repository.from_github_repo_name` scope lookups to the verified `repository_owner`, refusing to resolve/act on a repository whose owner differs from the organization whose secret validated the signature.

### Proof of Concept
1. Shipit instance is configured with two orgs in `secrets.github`: `orga` (attacker-controlled, secret known to attacker) and `victimorg` (unrelated tenant), per the multi-org schema in `lib/shipit.rb#github_app_config`. [5](#0-4) 
2. Attacker crafts a `push` webhook JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker_chosen_sha>",
  "repository": {
    "owner": { "login": "orga" },
    "full_name": "victimorg/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC(orga_webhook_secret, raw_body)` and sends `POST /github/webhooks` with `X-Github-Event: push`.
4. `verify_signature` calls `Shipit.github(organization: "orga")` (from `repository.owner.login`) and successfully verifies the signature against `orga`'s secret. [6](#0-5) 
5. `PushHandler#process` (via `Handler#repository_name` reading `payload.dig('repository','full_name')`) resolves `victimorg/victim-repo` and calls `stack.sync_github(expected_head_sha: "<attacker_chosen_sha>")` on its stacks, even though the request was never signed with `victimorg`'s secret. [10](#0-9) [3](#0-2)
