### Title
Pull-request label names are merged unsanitized into deploy process environment, enabling `GEM_HOME` injection - ([File: app/models/shipit/review_stack.rb])

### Summary
`ReviewStack#env` merges every pull-request label name (uppercased) into the stack's environment hash with no allowlist, and that hash is merged directly into every task/deploy command's environment via `TaskCommands#env`, which is passed straight to `Command#start` → `PTY.spawn`. Unlike the deploy-form/API-supplied `env`, which is filtered by `DeploySpec#filter_deploy_envs`/`EnvironmentVariables#permit` against `deploy.variables`, the stack-derived label environment bypasses that whitelist entirely.

### Finding Description
The broken binding is: **every key reaching `Command#unbundled_env` for a task/deploy execution should be a member of `deploy_variables` (the `deploy.variables` allowlist) ∪ Shipit's own fixed keys**, i.e. `env_reaching_PTY_spawn.keys ⊆ (deploy_variables.map(&:name) ∪ FIXED_KEYS)`. This does not hold for review-stack executions.

`ReviewStack#env` takes every label on the associated pull request and uppercases it into a hash value of `"true"`, with no filtering of the key name: [1](#0-0) 

That `env` method is what `Stack#env` resolves to for a `ReviewStack` instance (polymorphic override), and it is unconditionally merged into every task/deploy/install_dependencies command's environment in `TaskCommands#env`: [2](#0-1) 

Note line 35, `.merge(@stack.env)` — this is separate from `.merge(@task.env)` on line 47. Only `@task.env` (the user/API-supplied deploy variables) is ever passed through `DeploySpec#filter_deploy_envs`/`EnvironmentVariables#permit`, which raises `NotPermitted` for any key not in `deploy_variables`: [3](#0-2) [4](#0-3) 

`@stack.env` (containing the attacker-uppercased label keys) never passes through this filter — it is merged in raw. `TaskCommands#perform` and `#install_dependencies` build every deploy step's `Command` with this merged `env`: [5](#0-4) 

Finally, `Command#start` spawns the process with `unbundled_env`, which layers `@env` (attacker-controlled, stringified) on top of `BASE_ENV`/`PATH`, with no key restriction: [6](#0-5) 

So a fork PR labeled `gem_home` produces `env['GEM_HOME'] = 'true'`... but more importantly any label text is used verbatim as an environment variable *name* after uppercasing — an attacker names a label e.g. `gem_home` (GitHub allows arbitrary label names including those matching env var syntax), which becomes key `GEM_HOME` in the process environment for every `bundle`/gem-invoking command run during dependency installation or deploy steps of the review stack, redirecting Ruby's gem resolution to a location the PR branch also populates (e.g. via `machine.directory` or checked-out repo paths under `deploy.dependencies`). Existing guards (`filter_deploy_envs`, `EnvironmentVariables#permit`) are architecturally scoped only to the user/API-triggered `env:` parameter on `Deploy`/`Task` records (`Stack#build_deploy`, `Stack#trigger_task`), not to `Stack#env`/`ReviewStack#env`, so they do not intercept this path.

### Impact Explanation
This allows a PR author (via label naming, granted as in-scope attacker capability by the rules) to inject arbitrary environment variable names/values into every command executed for their review stack, including dependency-installation and deploy steps run as the Shipit worker/deploy-host user. `GEM_HOME` (or `RUBYOPT`, `BUNDLE_GEMFILE`, `LD_PRELOAD`-style keys, etc., all reachable via the same unfiltered path) can redirect gem/library resolution to attacker-supplied code checked out from the fork branch, achieving code execution as the Shipit deploy-host process — Critical RCE. This is scoped to whichever repository/stack has review stacks (`provision_pr_stacks`) enabled and is not isolated per PR-author privilege; it affects the specific ReviewStack being provisioned/deployed but the pattern is repeatable per PR and per repository configured this way.

### Likelihood Explanation
Preconditions: the target repository must have review stacks enabled (`provision_pr_stacks`/`allow_all` provisioning behavior) so that `ReviewStack` instances and their `pull_request` association exist; the attacker must be able to open a PR and have a label with an attacker-chosen name attached to it (granted by the rules as an in-scope capability). No Shipit session, API token, or GitHub secret is required. Cost is low — labeling a PR and letting the review-stack deploy pipeline run.

### Recommendation
Do not merge raw pull-request label names into the process environment. Either drop `ReviewStack#env`'s label-merging entirely, or pass label-derived keys through the same `EnvironmentVariables#permit`/`deploy_variables` allowlist used for `filter_deploy_envs`/`filter_task_envs` before merging into `TaskCommands#env`, and explicitly reject any key colliding with sensitive/interpreted variable names (`GEM_HOME`, `BUNDLE_*`, `RUBYOPT`, `LD_PRELOAD`, `PATH`, etc.).

### Proof of Concept
```ruby
# test/models/shipit/review_stack_env_test.rb (illustrative)
test "GEM_HOME injected via uppercased PR label reaches spawned deploy command env" do
  stack = shipit_stacks(:review_stack) # or build a ReviewStack fixture
  pull_request = stack.pull_request
  pull_request.update!(labels: ['gem_home']) # attacker-controlled label name

  env = stack.env
  assert_equal 'true', env['GEM_HOME'], "expected label-derived key to appear unfiltered in stack.env"

  task_commands = Shipit::TaskCommandsSubclassFor(stack) # e.g. DeployCommands.new(deploy)
  built_env = task_commands.send(:env) # or public env
  assert_equal 'true', built_env['GEM_HOME'], "expected GEM_HOME to survive into TaskCommands#env unfiltered"

  command = Shipit::Command.new('bundle install', env: built_env, chdir: Dir.tmpdir)
  assert_equal 'true', command.unbundled_env['GEM_HOME'], "GEM_HOME reaches PTY.spawn env, confirming injection"
end
```
This demonstrates the equality `env_reaching_PTY_spawn['GEM_HOME'] == 'true'` holds after label injection, while it should be excluded because `GEM_HOME` is not part of any `deploy.variables` allowlist and was never passed through `EnvironmentVariables#permit`.

    def start(&block)
      return if @started

      @control_block = block
      @out = @pid = nil
      FileUtils.mkdir_p(@chdir)
      begin
        @out, child_in, @pid = PTY.spawn(unbundled_env, *interpolated_arguments, chdir: @chdir)
        child_in.close
      rescue Errno::ENOENT
        raise NotFound, "#{Shellwords.split(interpolated_arguments.first).first}: command not found"
      rescue Errno::EACCES
        raise Denied, "#{Shellwords.split(interpolated_arguments.first).first}: Permission denied"
      end
      @started = true
      self
    end

    def unbundled_env
      BASE_ENV.merge('PATH' => "#{Shipit.shell_paths.join(':')}:#{ENV['PATH']}").merge(@env.stringify_keys)
    end
