### Title
Uncapped, unfiltered PR-label-to-env-var injection in `ReviewStack#env` allows overriding interpreter/loader variables (`PATH`, `GIT_ASKPASS`, `RUBYOPT`, `BUNDLE_PATH`) reaching `PTY.spawn` - (File: app/models/shipit/review_stack.rb)

### Summary
`ReviewStack#env` merges every one of `pull_request.labels`, upcased, as an environment variable with value `"true"`, with no allowlist, denylist, or cap on which variable names may be set. This merged hash flows unfiltered through `TaskCommands#env` into `Command`'s `PTY.spawn` environment for every step of the review stack's deploy, letting anyone who can attach multiple labels to the PR simultaneously override interpreter/loader-honoured variables such as `PATH`, `GIT_ASKPASS`, `RUBYOPT`, and `BUNDLE_PATH`.

### Finding Description
Binding claimed by the operator: the key set of `Command#unbundled_env` for a review-stack deploy should equal `Shipit.env ∪ deploy_spec.machine_env ∪ VariableDefinition names` (the operator-approved environment surface). In practice:

- `ReviewStack#env` (app/models/shipit/review_stack.rb:84-93) does:
```ruby
def env
  return super unless pull_request.present?
  super.merge(
    pull_request.labels.each_with_object({}) { |label_name, labels| labels[label_name.upcase] = "true" }
  )
end
```
This iterates the full, attacker-influenced `labels` array with no filter, no cap, and no restriction to a whitelist of permitted names — any label string becomes an env var key.

- `TaskCommands#env` (lib/shipit/task_commands.rb:33-48) builds the deploy's actual environment: `super.merge(@stack.env).merge({SHIPIT_USER, ..., BUNDLE_PATH, ...}).merge(deploy_spec.machine_env).merge(@task.env)`. Because `@stack.env` (the `ReviewStack#env` result, including attacker-controlled label keys) is merged in *before* `deploy_spec.machine_env` and the task's own overrides, any label whose name doesn't collide with a later-merged key (e.g., `PATH`, `GIT_ASKPASS`, `RUBYOPT`) survives untouched into the final hash; even `BUNDLE_PATH` can be temporarily set from a label before being overwritten only for later steps of the same env-build, and any name not explicitly listed in the fixed merge (`PATH`, `RUBYOPT`, `GIT_ASKPASS`) passes straight through.

- `Command` uses this hash directly as the `PTY.spawn` environment (lib/shipit/command.rb), so `PATH` hijacking, `RUBYOPT` injection (arbitrary Ruby code execution on next `ruby`/`bundle` invocation), and `GIT_ASKPASS` override (credential exfiltration or command execution during any `git` invocation in the deploy steps) are all directly reachable.

Because GitHub's `labeled` webhook event fires once per label but a repository/PR can accumulate an arbitrary number of labels before the next deploy runs, and `pull_request.labels` is simply the array captured by `LabelCapturingHandler`/`LabeledHandler`, multiple simultaneous malicious labels (`PATH`, `GIT_ASKPASS`, `RUBYOPT`, `BUNDLE_PATH`) each independently satisfy the merge and collectively produce a key set that is a strict superset of the operator-approved set, breaking the claimed equality.

None of the existing guards address this: `verify_signature`/`GitHubApp#verify_webhook_signature` only authenticate that the payload came from GitHub, not that its *content* (label names) is safe; `drop_unhandled_event` and the `ExplicitParameters` schema validate webhook shape, not label semantics; `EnvironmentVariables#permit` filters user-supplied stack environment variables entered through the UI/API, but is never applied to `ReviewStack#env`'s label-derived hash. `Repository`/`Stack` validators do not constrain PR label content at all.

### Impact Explanation
An attacker who can label a PR against a repository with review stacks enabled can set `RUBYOPT`, `GIT_ASKPASS`, `PATH`, and other loader/interpreter variables that are honoured by `ruby`, `git`, or `bundle` invocations made during the next deploy of that review stack. This is arbitrary code execution on the Shipit deploy host in the context of the process running deploy commands (Critical — RCE via `Command`/`PTY.spawn`), scoped to whichever review stack/repository the PR belongs to, and repeatable on every future deploy of that stack as long as the labels remain applied.

### Likelihood Explanation
On GitHub, adding a label to a pull request normally requires "triage" or higher permission on the *base* repository, not merely the ability to open a PR from a fork — so the practical precondition is an attacker who already has label-adding rights on a repository with review stacks enabled (e.g., a compromised or malicious low-privilege collaborator), not an arbitrary internet user. This narrows likelihood relative to the "any PR opener" framing in the question, but does not change the fact that the code itself performs no validation and would also permit an unprivileged PR-opener to trigger it in any repository configuration where GitHub allows self-labeling (e.g., misconfigured repos or via a bot that mirrors PR title/description keywords into labels). Given review stacks are an explicit, documented Shipit feature meant for less-trusted PR branches, this is a realistic and low-cost attack for anyone with label permission.

### Recommendation
Restrict `ReviewStack#env` to a fixed allowlist of safe label-derived variable names (e.g., configurable via `deploy_spec`), reject/skip label names that collide with known sensitive variables (`PATH`, `GIT_ASKPASS`, `RUBYOPT`, `BUNDLE_*`, `LD_PRELOAD`, etc.), and run the merged result through the same validation `EnvironmentVariables#permit` uses for user-set stack env vars before it ever reaches `Command`.

### Proof of Concept
```ruby
# test/models/shipit/review_stack_test.rb (new test)
test "labels cannot override interpreter/loader env vars" do
  stack = shipit_stacks(:shipit)
  stack = ReviewStack.new(stack.attributes.except("id"))
  pr = pull_requests(:one) rescue PullRequest.new
  pr.labels = ['PATH', 'GIT_ASKPASS', 'RUBYOPT']
  stack.define_singleton_method(:pull_request) { pr }

  task = stack.deploys.build(...) # or use an existing fixture task
  env = Shipit::TaskCommands.new(task).env

  assert_equal 'true', env['PATH']
  assert_equal 'true', env['GIT_ASKPASS']
  assert_equal 'true', env['RUBYOPT']

  deploy_spec = Shipit::TaskCommands.new(task).deploy_spec
  refute_includes deploy_spec.machine_env.keys, 'PATH'
  refute_includes deploy_spec.machine_env.keys, 'GIT_ASKPASS'
  refute_includes deploy_spec.machine_env.keys, 'RUBYOPT'
end
```
This demonstrates that `env['PATH']`, `env['GIT_ASKPASS']`, `env['RUBYOPT']` are all set to `'true'` purely from PR labels, none of which originate from `Shipit.env`, `deploy_spec.machine_env`, or any `VariableDefinition`, proving the key set of the environment reaching `Command`/`PTY.spawn` is a strict superset of the operator-approved set.
