### Title
CCMenuController bypasses ApiClient stack-scope restriction, allowing a stack-scoped token to read the build status of any other stack - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Shipit::Api::CCMenuController` overrides the base `stack` accessor with an unscoped lookup, breaking the binding that an `ApiClient` token restricted to one stack (`ApiClient#stack_id`) may only touch that stack. Any valid API token — including one deliberately scoped to a single stack — can be replayed against the CCMenu endpoint for an arbitrary `stack_id` and will successfully return that other stack's build/deploy status.

### Finding Description
`Shipit::Api::BaseController` establishes the authorization binding "stack a token authorizes == stack a request touches" through `stacks`/`stack`: [1](#0-0) 

`current_api_client.stack_id?` gates the queryable `Stack` relation to the single stack the client was scoped to when created (see the `here_come_the_walrus` fixture, `stack: shipit`): [2](#0-1) 

Every other API controller relies on this scoped `stack`/`stacks` helper (e.g. `StacksController#stack` calls `stacks.from_param!`): [3](#0-2) 

`CCMenuController`, however, redefines `stack` to bypass the scoped collection entirely and resolve directly against the global `Stack` table: [4](#0-3) 

The only guard left is `require_permission :read, :stack`, which is enforced by `ApiClient#check_permissions!`: [5](#0-4) 

That check only verifies the string `"read:stack"` is present in the token's permission list — it never inspects `current_api_client.stack_id`, so it cannot detect that the requested `stack_id` param differs from the stack the token was issued for.

Equality that should hold: `current_api_client.stack_id (if present) == stack.id used in the response`.
Equality actually enforced by `CCMenuController#show`: none — `stack` is resolved from `Stack.from_param!(params[:stack_id])` unconditionally, independent of `current_api_client.stack_id`.

### Impact Explanation
This crosses the "stack a token authorizes versus a stack it touches" trust boundary called out for this engine. A stack-scoped, read-only `ApiClient` token — the kind explicitly meant to be handed out narrowly (e.g. via `CCMenuUrlController`, which mints exactly such a `read:stack`-only client per stack) — can be replayed with a different `stack_id` to read another stack's deploy state (`lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, `activity`, `webUrl`) that the token was never authorized to see: [6](#0-5) 

This matches the in-scope High-severity bucket "unauthenticated read of stack state ... or deploy output" via an authorization-scope escape rather than session compromise.

### Likelihood Explanation
Any holder of a legitimately-scoped `read:stack` token (these tokens are routinely distributed to CI dashboards/CCMenu clients, as shown by `CCMenuUrlController`) can trigger this by simply changing the `stack_id` path segment of the request URL — no additional privilege, secret, or race condition is required.

### Recommendation
Make `CCMenuController#stack` use the scoped `stacks` collection from `BaseController` instead of `Stack.from_param!` directly, e.g.:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
so that a stack-scoped `ApiClient` can never resolve a stack outside `current_api_client.stack_id`.

### Proof of Concept
1. Create (or reuse) an `ApiClient` scoped to stack A with permission `read:stack` only (analogous to fixture `here_come_the_walrus`, scoped to `shipit`).
2. Using that client's `authentication_token`, issue:
   `GET /api/stacks/<owner>/<other-repo>/<other-env>/ccmenu?token=<token>` where the path targets stack B, a stack the token was never scoped to.
3. `CCMenuController#stack` resolves stack B via `Stack.from_param!`, bypassing the `current_api_client.stack_id` restriction; `check_permissions!(:read, :stack)` passes because the token does have the generic `read:stack` permission string.
4. The response renders stack B's `lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, `activity`, and `webUrl` — data the token's issuer never intended to expose, confirming cross-stack authorization bypass.
