### Title
Unscoped `Commit.where(sha:...)` lookup in `StatusHandler#process` lets an attacker's own webhook flip commit state and trigger deploys on a victim's stack - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` looks up commits purely by `sha`, with no scoping to the repository/stack that the webhook's signature actually authenticated. Since GitHub commit SHAs are content-addressed and can be trivially reproduced (e.g. the well-known empty-tree SHA, or any SHA an attacker can also craft/push in their own repo), an attacker can send a legitimately-signed status webhook for their own repository naming a SHA that also exists as a `Commit` row belonging to an unrelated victim `Stack`, causing that victim commit's status/state and thus its `deployable?`/continuous-deployment eligibility to be mutated.

### Finding Description
The broken binding, stated explicitly: the request is authenticated for `repository == attacker_repo` (via `WebhooksController#verify_signature`, which resolves `Shipit.github(organization: repository_owner)` from `payload['repository']['owner']['login']`), but the record that gets mutated is selected only by `sha`, independent of `repository`. The intended invariant should be `commit.stack.repository == attacker_repo`; the actual code enforces no such constraint.

Path:
- `WebhooksController#verify_signature` [1](#0-0)  verifies the signature against the GitHub App keyed by the *attacker's own* `repository_owner` — this only proves the payload originated from GitHub for the attacker's org/repo, it says nothing about which `Stack`/`Commit` rows may be touched.
- `StatusHandler#process` then does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` with no repository filter at all [2](#0-1) .
- Notably, the base `Handler` class already provides a repository-scoped helper, `stacks`, built from `Repository.from_github_repo_name(repository_name)` [3](#0-2) , but `StatusHandler` does not use it — it queries `Commit` globally instead of through the payload's own repository/stack.
- `create_status_from_github!` calls `add_status`, which replicates the GitHub status and recomputes `status`/state, and can call `stack.schedule_merges` [4](#0-3) [5](#0-4) .
- `Commit#deployable?` becomes true once state flips to success (`!locked? && (stack.ignore_ci? || (success? && !blocked?))`) [6](#0-5) .
- `schedule_continuous_delivery`, triggered `after_commit` on creation and also reachable through the same status-flip path, enqueues `ContinuousDeliveryJob` for the victim `stack` when `deployable? && stack.continuous_deployment? && stack.deployable?` [7](#0-6) .

Because `Commit` rows are looked up globally by `sha` with no `stack_id`/repository filter, any two stacks (victim's and attacker's) that happen to share a commit SHA — trivially achievable using deterministic Git objects like the empty-tree SHA, or by an attacker forking/rebasing to reproduce a specific known SHA — let the attacker's authenticated webhook mutate the victim's commit's state. None of the listed guards (`verify_signature`, `drop_unhandled_event`, `ExplicitParameters`) constrain the query to the authenticated repository; they only validate the shape/signature of the *attacker's own* payload, not which rows the handler may touch.

### Impact Explanation
An attacker with no privileges on the victim's repository, stack, or Shipit installation can write to a victim `Commit` row (state/status) belonging to a different tenant purely by owning a repo that shares a SHA with the victim's pending commit, and can cause an unauthorized deploy to be scheduled on the victim's `Stack` via `ContinuousDeliveryJob`. This matches the Critical category "a payload for one repository mutating another's stack, commit, task or team" / "an unauthorized deploy". This is repeatable against any victim stack whose `next_commit_to_deploy` SHA an attacker can predict or reproduce (well-known empty-tree/empty-blob SHAs, or any SHA disclosed publicly e.g. via the victim's own public commit history/PRs), and it is cross-tenant since the write is not scoped to the authenticating repository at all.

### Likelihood Explanation
Preconditions: the victim stack must have `continuous_deployment: true` and a pending/unsuccessful `Commit` whose SHA the attacker can also produce/name via their own repository and webhook. The empty-tree SHA (`4b825dc642cb6eb9a060e54bf8d69288fbee4904`) is deterministic and identical across all Git repositories, so this precondition is easy to satisfy for any freshly-initialized or otherwise-colliding branch tip. Attacker cost is low: create a repo, push an empty-tree commit to a branch, send `POST /webhooks` with a `status` event for that SHA and `state: success`, signed with the attacker's own legitimate `webhook_secret`/GitHub App secret for their own repo — no victim secrets are needed. The attack is repeatable per victim commit/SHA collision.

### Recommendation
Scope the commit lookup in `StatusHandler#process` to the stacks/repositories legitimately associated with the webhook's payload, e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` or equivalently filter `Commit.where(sha: params.sha)` by `stack_id: stacks.pluck(:id)` (mirroring the `stacks` helper already defined in `Handler`), so a status event can only affect commits belonging to the repository that was actually authenticated for that webhook.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb`):
1. Create `victim_stack` for repo `victim/repo` with `continuous_deployment: true`; create `victim_commit` with `sha: "4b825dc642cb6eb9a060e54bf8d69288fbee4904"` and an initial pending/failing status so `deployable?` is false.
2. Create `attacker_stack`/`Repository` for `attacker/repo` (or simply an unrelated repository payload) tracked or not by Shipit.
3. Stub `ContinuousDeliveryJob` enqueue (or stub the GitHub-authenticating pieces) and build a `status` webhook payload: `{ 'sha' => victim_commit.sha, 'state' => 'success', 'repository' => { 'full_name' => 'attacker/repo', 'owner' => { 'login' => 'attacker' } }, ... }`.
4. Assert before: `victim_commit.reload.deployable?` == `false`, and `Deploy.count` unaffected.
5. Call `Shipit::Webhooks::Handlers::StatusHandler.call(payload)` (bypassing/stubbing signature verification as the attacker's own app would legitimately pass it).
6. Assert after: `victim_commit.reload.success?` == `true` and `victim_commit.deployable?` == `true`, and (`assert_difference -> { Deploy.count }` or assert `ContinuousDeliveryJob` enqueued for `victim_stack`) demonstrating the attacker's webhook for `attacker/repo` mutated and triggered deployment logic for `victim/repo`'s stack — violating the intended `commit.stack.repository == authenticated_repository` binding.

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }

      end

      if previous_status.simple_state != new_status.simple_state

      end
      new_status
    end
