Webhook Signature is Verified Against the Wrong Organization, Allowing Cross-Organization Forgery of Push/Status Events - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects the HMAC secret to validate a GitHub webhook using `repository_owner`, a value taken from the `repository.owner.login` (or `organization.login`) field of the *same untrusted JSON body* it is about to validate [1](#0-0) . Once the signature check passes, the raw payload is dispatched to handlers that resolve the actual repository/commit to act on using a *different* field of the same body — `repository.full_name` (used by `Handler#stacks`) or `sha` alone (used by `StatusHandler`) — with no re-verification that these fields belong to the organization whose secret validated the request [2](#0-1) [3](#0-2) .

### Finding Description
In a multi-tenant Shipit deployment (explicitly documented and supported: `config/secrets.yml` can hold a separate GitHub App/`webhook_secret` per organization) [4](#0-3) , the equality that must hold for the trust boundary to be sound is:

`organization that authenticated the request (repository.owner.login)` == `organization/repository that is actually written to (repository.full_name / sha lookup)`

`verify_signature` only enforces the left-hand side — it looks up `Shipit.github(organization: repository_owner)` and checks the `X-Hub-Signature` HMAC against that organization's `webhook_secret` [1](#0-0) , computed via `GitHubApp#verify_webhook_signature` [5](#0-4) . It never checks that the resolved organization matches the repository the payload will actually mutate.

The `create` action then forwards the entire parsed body to registered handlers regardless of which organization "owns" the fields being consumed [6](#0-5) . `Handler#stacks` resolves the target `Stack`(s) purely from `payload.dig('repository', 'full_name')` [2](#0-1) , and `StatusHandler#process` resolves target commits purely by matching `sha` across the whole `Commit` table, with no repository/organization scoping at all [3](#0-2) .

Because a Shipit administrator can be an "unprivileged attacker" with respect to *other* orgs on the same instance — they legitimately know their own GitHub App's `webhook_secret` for "Org A" (they created it) — they can craft and self-sign a JSON body where:
- `repository.owner.login` = `"org-a"` (so `verify_signature` picks Org A's secret, which the attacker knows and can compute a valid HMAC for), and
- `repository.full_name` = `"org-b/victim-repo"` (a repository belonging to a completely different, unrelated organization "Org B" also tracked by the same Shipit instance), or for the `status` event, simply a `sha` that happens to match a commit tracked in Org B's repo.

The controller will accept the request (signature is valid for Org A), and the handler will act on Org B's stack/commit.

### Impact Explanation
This breaks the "organization that authenticated versus the repository that is written" binding and results in cross-repository/cross-organization writes: an attacker with legitimate access to only their own organization's GitHub App can forge:
- `push` events that make `PushHandler` invoke `stack.sync_github(expected_head_sha:)` for a victim organization's stack (`app/models/shipit/webhooks/handlers/push_handler.rb:12-17`), and
- `status` events that make `StatusHandler` create a fabricated `Commit::Status` on a victim's commit (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`), which can flip a commit's simple state to `success`, triggering `stack.schedule_merges` and `ProcessMergeRequestsJob`, i.e., influencing/triggering merges and continuous-delivery pipelines the attacker does not own [7](#0-6) .

This meets the "unauthorized deploy, rollback or merge" / "cross-repository writes" criterion without requiring a Shipit session, ApiClient token, repository write access on GitHub, or the victim's credentials — only requiring the attacker's own, self-controlled GitHub App webhook secret for a different org hosted on the same Shipit instance.

### Likelihood Explanation
Requires a Shipit instance configured with multiple GitHub organizations (an explicitly documented, supported configuration) and requires the attacker to be a legitimate GitHub App owner/admin for at least one of those organizations — a realistic scenario for shared/hosted Shipit deployments serving multiple teams or external partner orgs. No insider access to the victim org is needed.

### Recommendation
After verifying the HMAC signature, cross-check that the organization used to select the `webhook_secret` (`repository.owner.login` / `organization.login`) matches the owner segment of `repository.full_name` (and any other repository identifiers consumed by handlers) before dispatching to handlers. Additionally, `StatusHandler` should scope its `Commit.where(sha:)` lookup to the repository identified in the verified payload rather than matching `sha` globally across all tracked stacks.

### Proof of Concept
1. Configure (as in production) Shipit with two orgs, "org-a" (attacker-controlled GitHub App, known `webhook_secret`) and "org-b" (victim, tracked by the same Shipit instance).
2. Attacker crafts a `push` webhook JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>",
  "repository": { "owner": { "login": "org-a" }, "full_name": "org-b/victim-repo" }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(org-a's webhook_secret, body)>` and POSTs to `/webhooks` with `X-Github-Event: push`.
4. `verify_signature` resolves `repository_owner` = `"org-a"`, fetches Org A's `GitHubApp`, and the signature validates successfully (`app/controllers/shipit/webhooks_controller.rb:24-30`).
5. `PushHandler` resolves stacks via `payload.dig('repository', 'full_name')` = `"org-b/victim-repo"` (`app/models/shipit/webhooks/handlers/handler.rb:36-38`) and calls `stack.sync_github(expected_head_sha: "<attacker-chosen sha>")` on Org B's stack — despite the attacker having no relationship to Org B.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
