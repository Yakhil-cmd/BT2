### Title
Definer-controlled attestor list update can permanently freeze already-attested coin holders' funds - ([File: validation.js])

### Summary
For `spender_attested` assets, the current (latest) attestor list is re-checked every time an address's output is spent, rather than the attestor status at the time the output was received. Because the asset definer can freely update the attestor list at any time via an `asset_attestors` message, removing an address (or an attestor) from the list retroactively makes previously-received, previously-valid funds permanently unspendable, with no recourse for the holder. This mirrors the reported analog: a privileged, mutable whitelist that gates a critical validation path, and once toggled, a legitimate on-chain state (held funds / a liquidatable debt) becomes permanently unenforceable/unusable.

### Finding Description
An asset can be defined with `spender_attested: true`. The definer publishes and can update the list of attestors at will via the `asset_attestors` app, validated by `validateAttestorListUpdate` and `checkAttestorList`: [1](#0-0) 

The list of currently attested addresses is computed dynamically for the `last_ball_mci` of whichever unit is being validated, based on the **latest** attestor-list unit and the **latest** attestation for each address: [2](#0-1) [3](#0-2) 

Crucially, when an existing output of a `spender_attested` asset is later spent (as a `transfer` input), the validator re-checks whether the **owner address is currently attested** — not whether it was attested when the coins were received: [4](#0-3) 

The same re-check applies to private, fixed-denomination coins spent from `objValidationState.src_coin`: [5](#0-4) 

Because the attestor list (and the attestation records built on top of it) are entirely mutable at the definer's discretion, and because spend-time validation always uses the attestation status as of the **spending unit's** `last_ball_mci` (not the receiving unit's), a definer can:
1. Attest address A, allowing A to receive/hold the asset.
2. Later publish a new `asset_attestors` message that drops A from the attestor list, or have an attestor revoke A's attestation.
3. From that point forward, any attempt by A to spend the funds it legitimately holds will fail validation with `"owner address is not attested"`, permanently freezing those funds unless/until A is re-attested — which is entirely at the definer's/attestors' discretion.

This is structurally identical to the reported bug class: a privileged whitelist (`whitelistedERC1155` / attestor list) is checked live at the time of a security-critical action (liquidation / fund spend) rather than pinned to the state at the time the position/holding was created, so a later revocation permanently blocks the affected party from exercising their rights over already-existing, previously-valid on-chain state.

### Impact Explanation
Any holder of a `spender_attested` asset (public or private) can have their funds permanently frozen the moment the definer edits the attestor list (or an attestor revokes attestation) to exclude their address, even though the funds were legitimately acquired while attested. There is no way for the affected holder to unilaterally recover the funds — this is a definer-triggered denial-of-spend / fund freeze impacting an unprivileged counterparty (any address that received such an asset). This satisfies the "AA/asset fund loss or freezing" acceptance criterion.

### Likelihood Explanation
This requires the asset's definer (a privileged actor per the asset's own design) to publish an `asset_attestors` update, which is a normal, unrestricted action explicitly allowed at any time by `validateAttestorListUpdate` (only requiring single-authorship and being the definer). No special conditions or races are needed — any definer of a `spender_attested` asset can trigger this against any current holder at any time.

### Recommendation
Decouple spend-time attestation checks from receive-time checks: pin the attestation requirement to the state of the attestor list at the time the output was created (similar to how `denomination` and other output properties are fixed at creation), or provide a grace/appeal mechanism so that funds received while properly attested cannot be frozen retroactively by later attestor-list changes. At minimum, document this as an inherent risk of `spender_attested` assets so wallets/users are aware that already-held balances can become unspendable due to a definer's unilateral action.

### Proof of Concept
1. Asset definer creates asset X with `spender_attested: true` and publishes an initial attestor list including attestor `T`.
2. `T` attests address `A`. `A` receives a payment output of asset X (validated fine since `A` is in `arrAttestedAddresses` at that time, per `loadAssetWithListOfAttestedAuthors` → `filterAttestedAddresses`, storage.js:1959-1992).
3. Definer publishes a new `asset_attestors` message removing `T` (or `T` never re-attests `A`, or attestations are otherwise altered) — validated and accepted per `validateAttestorListUpdate`, validation.js:2829-2848.
4. `A` attempts to spend the previously received output. `validatePaymentInputsAndOutputs` re-evaluates `objAsset.arrAttestedAddresses` for the current `last_ball_mci` and finds `A` no longer attested, hitting `return cb("owner address is not attested")` at validation.js:2506 (or 2432 for private fixed-denomination coins).
5. `A`'s previously legitimate balance of asset X is now permanently unspendable, with no mechanism to force re-attestation.

function validateAttestorListUpdate(conn, payload, objUnit, objValidationState, callback){
	if (objUnit.authors.length !== 1)
		return callback("attestor list must be single-authored");
	if (!isNonemptyObject(payload))
		return callback("attestor update must be a non-empty object");
	if (hasFieldsExcept(payload, ['asset', 'attestors']))
		return callback("foreign fields in attestor list update");
	storage.readAsset(conn, payload.asset, objValidationState.last_ball_mci, false, function(err, objAsset){
		if (err)
			return callback(err);
		if (!objAsset.spender_attested)
			return callback("this asset does not require attestors");
		if (objUnit.authors[0].address !== objAsset.definer_address)
			return callback("attestor list can be edited only by definer");
		err = checkAttestorList(payload.attestors);
		if (err)
			return callback(err);
		callback();
	});
}

// filter only those addresses that are attested (doesn't work for light clients)
function filterAttestedAddresses(conn, objAsset, last_ball_mci, arrAddresses, handleAttestedAddresses){
	conn.query(
		"SELECT DISTINCT address FROM attestations CROSS JOIN units USING(unit) \n\
		WHERE attestor_address IN(?) AND address IN(?) AND main_chain_index<=? AND is_stable=1 AND sequence='good' \n\
			AND main_chain_index>IFNULL( \n\
				(SELECT main_chain_index FROM address_definition_changes JOIN units USING(unit) \n\
				WHERE address_definition_changes.address=attestations.address AND main_chain_index<=? AND is_stable=1 AND sequence='good' ORDER BY main_chain_index DESC LIMIT 1), \n\
			0)",
		[objAsset.arrAttestorAddresses, arrAddresses, last_ball_mci, last_ball_mci],
		function(addr_rows){
			var arrAttestedAddresses = addr_rows.map(function(addr_row){ return addr_row.address; });
			handleAttestedAddresses(arrAttestedAddresses);
		}
	);
}

// note that light clients cannot check attestations
function loadAssetWithListOfAttestedAuthors(conn, asset, last_ball_mci, arrAuthorAddresses, bAcceptUnconfirmedAA, handleAsset){
	if (arguments.length === 5) {
		handleAsset = bAcceptUnconfirmedAA;
		bAcceptUnconfirmedAA = false;
	}
	readAsset(conn, asset, last_ball_mci, bAcceptUnconfirmedAA, function(err, objAsset){
		if (err)
			return handleAsset(err);
		if (!objAsset.spender_attested)
			return handleAsset(null, objAsset);
		filterAttestedAddresses(conn, objAsset, last_ball_mci, arrAuthorAddresses, function(arrAttestedAddresses){
			objAsset.arrAttestedAddresses = arrAttestedAddresses;
			handleAsset(null, objAsset);
		});
	});
}
