### Title
Malicious asset `transfer_condition`/`is_transferrable`/`spender_attested` restrictions permanently freeze AA funds because the whole response unit is bounced atomically - ([File: aa_composer.js])

### Summary
Any unprivileged user can define a public Obyte asset with attacker-controlled `transfer_condition` (e.g. one that is always false), `is_transferrable:false`, or `spender_attested` restrictions, and attach that asset as a payment together with a trigger to any AA. When the AA later composes a single response unit that bundles a payout of that "poisoned" asset together with legitimate bytes/assets to a claimant, the entire unit fails atomic validation and is bounced, so none of the bundled payments (including otherwise-valid ones) go through, exactly mirroring the "broken ERC20 in a for-loop" freezing pattern from the reference report.

### Finding Description
Obyte's asset model lets anyone define an asset with a `transfer_condition` (an arbitrary oscript boolean expression) and other restrictive flags (`is_transferrable`, `spender_attested`, `cosigned_by_definer`, `issued_by_definer_only`). These are validated as part of `validateAssetDefinition` in `validation.js` and stored per-asset (`writer.js`, asset tables). Critically, a *public* asset may still carry a `transfer_condition`; only private assets are barred from having one (`validation.js:2800`, `noPrivateAssetsWithConditionsUpgradeMci`). Nothing prevents an attacker from defining an asset whose `transfer_condition` always evaluates to false, or one with `is_transferrable:false` and no relation to the definer, and then sending that asset (with a normal trigger payment) to any target AA — AAs cannot refuse or filter what assets accompany a trigger. [1](#0-0) [2](#0-1) 

When the AA composes its response, `sendUnit` in `aa_composer.js` builds ALL outgoing payment messages (base bytes plus every asset the AA is paying out) into one single `objUnit`, and validates/saves that unit atomically: [3](#0-2) [4](#0-3) 

The final `validateAndSaveUnit(objUnit, ...)` call validates every message/payment of that unit together; if `validatePaymentInputsAndOutputs` rejects the poisoned asset's output (because `transfer_condition` evaluates false, `is_transferrable` is false and the output pattern doesn't match the definer exception, or `spender_attested` filters out the recipient), the whole callback returns an error and the AA calls `bounce(err)` for the entire response, not just for that one asset's message: [5](#0-4) 

This is structurally identical to the reported ClaimManagerV1 bug: a single `for`-loop transfer failure (there, a broken ERC20; here, a poisoned/restricted Obyte asset) causes the entire payout transaction to revert/bounce, blocking delivery of everything bundled with it — including base bytes and other perfectly valid assets that were meant to reach the claimant in the same response.

### Impact Explanation
Any AA design that batches multiple asset payouts to a single recipient in one response unit (a very natural pattern, since AAs must produce one unit per trigger and `mergeMessagesAndOutputs`/`sendUnit` process all queued payment messages together) is exposed: an attacker who is only an ordinary depositor/asset issuer can permanently deny the release of that AA's held funds to the legitimate claimant by ensuring a restrictively-conditioned asset is part of the payout set. Because the condition (`transfer_condition`) is attacker-defined and can be made unsatisfiable forever, the freeze is permanent — the AA can never construct a valid response unit that includes that asset, so if the AA's payout logic path requires including it (e.g., "forward everything currently held to the closer"), the claimant's legitimate bytes/assets stay locked in the AA indefinitely. This matches the required impact bar: AA fund loss/freezing.

### Likelihood Explanation
Likelihood is bounded by AA design: this requires an AA that (a) accepts deposits of arbitrary/unwhitelisted assets from any sender attached to a trigger, and (b) later bundles a payout of "everything held" (or of all assets deposited by/for a party) into one atomic unit rather than isolating per-asset payout attempts. This is a common and natural pattern for bounty/vault/escrow-style AAs (directly analogous to the audited `AtomicBountyV1`/`DepositManager` design), and nothing in ocore prevents an attacker from crafting and depositing such a poisoned asset, since asset definition and deposit-to-AA are both fully permissionless operations reachable by an ordinary user.

### Recommendation
- AA authors should never bundle third-party-deposited, unvetted assets into the same atomic response unit as a guaranteed payout; instead send each asset's payout in its own isolated response/trigger, or maintain a per-asset "claimable" ledger evaluated lazily per claim rather than iterating and paying all held assets in one unit.
- Where possible, whitelist accepted assets (reject/ignore deposits of assets with `transfer_condition`, `is_transferrable:false`, or `spender_attested` set, unless explicitly vetted) at the application/oscript layer, since ocore itself provides no such protection to AAs.
- Consider documenting/warning in AA developer guidance that a single failed asset payment inside a composed response unit bounces the entire unit, and that this can be weaponized by depositing intentionally-unspendable assets.

### Proof of Concept
1. Attacker defines a public asset `X` via an `asset` message with `transfer_condition: ['formula', 'false']` (or any condition guaranteed to fail) and normal `is_private:false`, satisfying `validateAssetDefinition` (`validation.js:2725-2827`).
2. Attacker sends a trigger to a target AA that is designed to pool deposits and later pay out "all held assets" to a beneficiary (e.g., a bounty/vault AA), attaching asset `X` as part of the trigger's payment.
3. AA state accumulates `X` as part of its balance/state tracking for that beneficiary/claim.
4. When the beneficiary later triggers the payout, the AA's oscript emits a payment message for `X` together with base bytes/other assets in the same response.
5. In `aa_composer.js`'s `sendUnit`, all messages are merged into one `objUnit` and passed to `validateAndSaveUnit`; validation reaches `validatePaymentInputsAndOutputs`, which evaluates `X`'s `transfer_condition` via `Definition.evaluateAssetCondition` and returns `"transfer or issue condition not satisfied"` (`validation.js:2643-2659`).
6. This error propagates back to `sendUnit`'s final callback, which calls `bounce(err)` for the entire unit (`aa_composer.js:1405-1411`), discarding the whole payout — including the base bytes and any other valid assets that were supposed to reach the beneficiary.
7. Because `X`'s condition is permanently unsatisfiable and remains part of the AA's tracked balance for that claim, every subsequent attempt to release the beneficiary's funds bounces the same way, freezing the funds indefinitely.
