### Title
Cross-repository `Status` forgery via unscoped sha lookup in `StatusHandler#process` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` matches incoming `status` webhook payloads to commits using a global `Commit.where(sha: params.sha)` query with no repository/stack scoping, unlike every other webhook handler (`PushHandler`, `CheckSuiteHandler`, PR handlers) which all restrict matching to `stacks` derived from the payload's `repository.full_name`. Because `verify_signature` only authenticates that the sender legitimately controls *some* repository/org known to Shipit (via `repository_owner`), an attacker who owns any tracked repository can send a genuinely-signed `status` webhook naming a sha that collides with a commit belonging to a completely unrelated victim stack, and have `create_status_from_github!` write an attacker-controlled `Status` (state/description/context/target_url) onto that victim commit. This is a strictly stronger and more critical bug than the DeferredTouch side-effect the question asks about, and it fully explains why the `updated_at` touch happens: the touch is a direct, expected consequence of an unauthorized `Status` write that itself should never have been reachable.

### Finding Description
The binding that should hold is: `Repository.from_github_repo_name(payload.dig('repository','full_name')) == commit.stack.repository` for any commit whose `Status` is created/mutated by a webhook. In `Handler` base class, every subclass except `StatusHandler` enforces this via the `stacks` helper, e.g. `PushHandler#process` calls `stacks.not_archived.where(branch:).find_each { ... }` and `CheckSuiteHandler#process` calls `stacks.where(branch: ...).each { |stack| stack.commits.where(sha: ...) }` — both restrict candidate commits to the authenticated repository's own stacks. [4](#0-3) 

`StatusHandler#process`, however, does:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [1](#0-0) 

This ignores `repository_name`/`stacks` entirely and matches by sha across the *entire database*, regardless of which repository authenticated the request. `create_status_from_github!` then calls `add_status { statuses.replicate_from_github!(stack_id, github_status) }`, creating a real `Status` row scoped to the victim's own `stack_id`. [6](#0-5) [7](#0-6) 

Signature verification does not close this gap: `WebhooksController#verify_signature` only checks `Shipit.github(organization: repository_owner)` — i.e., that the signature matches the webhook secret configured for *some* organization Shipit knows about (the attacker's own, if they own/control a repo under a tracked org/app installation). It never checks that `repository.full_name` corresponds to the stack owning the matched commit. [5](#0-4) 

Exploit flow: attacker pushes a commit to their own tracked repository/fork whose sha collides (or, more practically, an attacker who already knows/observes a victim commit sha from a public GitHub repo can directly craft a raw HTTP POST to `/webhooks` with `X-Github-Event: status`, a `sha` equal to the victim's commit sha, and a signature computed with their own webhook secret if a per-org `webhook_secret` is configured for their org) — this reaches `StatusHandler#process`, matches `Commit.where(sha: params.sha)` against the victim's commit (owned by a different stack/repository), and creates a forged `Status` on it. `Status#after_create :enable_ci_on_stack`, `schedule_continuous_delivery`, and the `deferred_touch commit: :updated_at` all then fire on the victim's `Commit` and `Stack` as an unavoidable side effect of this unauthorized write. [8](#0-7) 

### Impact Explanation
This allows a payload signed for one repository to mutate another repository's stack/commit state — writing an arbitrary CI status (`state`, `description`, `context`, `target_url`) onto a victim commit not owned by the attacker's authenticated repository. Depending on the victim stack's `required_statuses`/`blocking_statuses`/`soft_failing_statuses` configuration, this can flip `commit.state` to `success`, enabling `stack.schedule_merges` and continuous delivery (`schedule_continuous_delivery`) for a stack the attacker does not own, in addition to touching `commit.updated_at`/`stack.updated_at` via `DeferredTouch`. This matches the in-scope Critical category "a payload for one repository mutating another's stack, commit, task or team," and is repeatable against any commit sha the attacker can guess or observe, for any commit in the Shipit database.

### Likelihood Explanation
The precondition is a sha collision between the attacker-controlled repository and the victim's tracked commit — feasible in practice by an attacker who owns/controls a repository under a GitHub org/app that Shipit already trusts (satisfying `verify_signature`), and who can name/predict a target sha (e.g., forcing their own commit to have a chosen sha is not required if the attacker can observe or guess a live, public victim sha and directly forge the raw webhook POST, since `Commit.where(sha:)` doesn't require the sha to originate from the attacker's own repo at all — only the HMAC signature must validate against a webhook secret for the org named in the payload's `repository.owner.login`, which is entirely attacker-suppliable JSON). No Shipit session, API token, or GitHub App private key is required — only knowledge of a webhook secret for one already-onboarded organization, which the attacker could have if they are simply a regular collaborator/contributor able to trigger real webhooks from a repo under that org.

### Recommendation
Scope `StatusHandler#process` the same way as `PushHandler`/`CheckSuiteHandler`: restrict the commit lookup to `stacks` (i.e., `Repository.from_github_repo_name(repository_name).stacks.commits.where(sha: params.sha)`), so a `status` webhook can only mutate commits that belong to stacks under the authenticated payload's own repository.

require 'test_helper'

module Shipit
  module Webhooks
    module Handlers
      class StatusHandlerCrossRepoTest < ActiveSupport::TestCase

          attacker_stack = shipit_stacks(:cyclimse)       # unrelated repo/org

            'context' => 'forged',

          assert_no_difference -> { victim_commit.statuses.count } do
            Shipit::Webhooks::Handlers::StatusHandler.call(payload)
          end
