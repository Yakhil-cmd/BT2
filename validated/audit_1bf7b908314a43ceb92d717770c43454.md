### Title
Cross-organization webhook signature bypass via divergent `repository.owner.login` vs `repository.full_name` fields - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects the `GitHubApp` (and thus the HMAC secret) to verify against using `repository.owner.login` (or `organization.login`), while every downstream pull-request handler resolves the actual target `Repository` using the unrelated `repository.full_name` field. Since the raw POST body is fully attacker-controlled at this unauthenticated endpoint, an attacker can name a no-secret org as `repository.owner.login` (bypassing HMAC entirely) while pointing `repository.full_name` at a secret-protected org's real, tracked repository, causing `OpenedHandler` to create a `ReviewStack` for that protected repository without ever presenting a valid signature.

### Finding Description
Binding required for the signature check to be meaningful: `params.dig('repository','owner','login') == params.dig('repository','full_name').split('/').first`. This equality is **never enforced** — both values are read independently from the same attacker-supplied JSON body with no cross-validation.

Code path:
- `WebhooksController#verify_signature` picks the app config purely off `repository_owner`: [1](#0-0)  and [2](#0-1) .
- `GitHubApp#verify_webhook_signature` returns `true` unconditionally when that org's config has no `webhook_secret`: [3](#0-2) .
- If verification passes, `Shipit::Webhooks.for_event('pull_request')` dispatches to `OpenedHandler`, whose `#repository` method resolves the target repo purely from `params.repository.full_name`, completely independent of `repository_owner`: [4](#0-3) .
- `Repository.from_github_repo_name` just splits `full_name` on `/` and does a DB lookup by owner/name, with no reference back to the signature-checked organization: [5](#0-4) .
- The base `Handler` class exhibits the identical pattern (`repository_name` derived from `payload.dig('repository','full_name')`, unrelated to whatever org authenticated the request): [6](#0-5) .

Root cause: in a genuine GitHub webhook, `repository.owner.login` and `repository.full_name` always agree because both are derived from the same GitHub-side repository object. This assumption is baked into the code but is not actually checked, and it fails as soon as the request does not come from GitHub — which is exactly the threat model here, since `POST /webhooks` has no other authentication and the signature is the *only* thing meant to prove GitHub authorship. Multi-org configuration where some orgs have no `webhook_secret` is an explicitly documented and supported setup: [7](#0-6) .

Attacker's exact request: `POST /webhooks` with header `X-Github-Event: pull_request`, no (or garbage) `X-Hub-Signature`, and JSON body:
```json
{
  "action": "opened",
  "number": 2,
  "pull_request": { ...valid ExplicitParameters-required fields... },
  "repository": { "owner": { "login": "someothergithuborg" }, "full_name": "somegithuborg/protected-repo" },
  "sender": { "login": "attacker" }
}
```
where `someothergithuborg` is a Shipit-configured org with `webhook_secret: nil` and `somegithuborg/protected-repo` is a real, tracked `Shipit::Repository` belonging to the secret-protected org.

Exploit flow: `verify_signature` calls `Shipit.github(organization: 'someothergithuborg')`, whose `verify_webhook_signature` short-circuits to `true` (no secret configured) — no HMAC ever checked. The request proceeds to `create`, `OpenedHandler` runs, resolves `repository` via `full_name` = `somegithuborg/protected-repo`, and (if that repository has review stacks enabled with an appropriate provisioning behavior) creates a `ReviewStack` — a write against the secret-protected org's repository triggered by a payload that never validated against that org's secret.

None of the existing guards stop this: `drop_unhandled_event` only filters unknown event types (pull_request is handled); `ExplicitParameters` schemas in `OpenedHandler` only validate presence/types of fields, not that `repository.owner.login` matches `repository.full_name`'s owner; `force_github_authentication`/`User#authorized?`/`require_permission!` are session/API-token controls not applicable to this public webhook endpoint; `Repository` model validations only constrain owner/name character format, not provenance.

### Impact Explanation
An unauthenticated attacker can trigger authenticated-org-only side effects (creation of a `ReviewStack`/`Stack` record, PR/user records, provisioning jobs) against **any repository belonging to any org that has a webhook_secret configured**, as long as the Shipit instance also has at least one other configured org without a `webhook_secret`. This is a cross-tenant authentication bypass: a payload naming one org (unsecured) is used to mutate state scoped to a completely different org (secured), matching the Critical category "a payload for one repository mutating another's stack" and "authentication bypass (forged webhook … accepted)". It is fully repeatable — every request forges the same divergence and can target any tracked repository in the secured org, and pull_request-based handlers (`ClosedHandler`, `LabeledHandler`, `UnlabeledHandler`, `ReopenedHandler`, `EditedHandler`, `AssignedHandler`) share the identical `full_name`-based resolution pattern, widening blast radius beyond just `OpenedHandler`.

### Likelihood Explanation
Preconditions: Shipit must be configured with the documented multi-org `github:` schema (per `docs/setup.md`) where at least one configured organization has `webhook_secret` unset/blank, and the target repository (in a *different*, secret-protected org) must already be tracked by Shipit with review stacks enabled. This is a plausible but not universal operator configuration — it requires more than one org to be onboarded, one of which is left without a secret (e.g., during initial setup, as the shipped example config shows `webhook_secret:` blank for both sample orgs). No attacker credentials of any kind are required beyond internet access to the Shipit host and knowledge of a tracked repo's `full_name`, which is typically public information. Cost to the attacker is a single crafted HTTP POST.

### Recommendation
Bind the signature-verifying organization to the same repository object used by the handlers: derive the app/config used for HMAC verification from `repository.full_name`'s owner (or, better, verify the signature using a mechanism independent of any payload-supplied identifier — e.g. verify against *all* configured webhook secrets, or require a stable per-installation identifier), and explicitly reject requests where `repository.owner.login` does not match the owner segment of `repository.full_name`. Additionally, disallow (or warn loudly against) `webhook_secret: nil` for any organization once multi-org mode is enabled, since it makes that org a signature-bypass proxy for the entire instance.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (conceptual addition)
test "cross-org webhook forgery bypasses HMAC check for a different org's repository" do
  # Config: two orgs — "unsecured" (no webhook_secret) and "secured" (webhook_secret set)
  Shipit.stubs(:github_app_config).with("unsecured").returns({})
  Shipit.stubs(:github_app_config).with("secured").returns({ webhook_secret: "supersecret" })

  secured_repo = shipit_repositories(:shipit) # owner: "secured", tracked, review_stacks_enabled: true

  payload = payload_parsed(:pull_request_opened)
  payload["repository"]["owner"]["login"] = "unsecured"
  payload["repository"]["full_name"] = secured_repo.full_name

  @request.headers['X-Github-Event'] = 'pull_request'
  # No X-Hub-Signature header at all

  assert_difference -> { Shipit::Stack.count }, 1 do
    post :create, body: payload.to_json, as: :json
  end
  assert_response :ok
end
```
Assertions on both sides of the binding: `payload["repository"]["owner"]["login"] == "unsecured"` (used by `verify_signature` → `Shipit.github(organization: "unsecured")` → `verify_webhook_signature` returns `true` unconditionally) while `payload["repository"]["full_name"].split("/").first == "secured"` (used by `OpenedHandler#repository` → `Repository.from_github_repo_name` → resolves the secured org's real repository) — the two values differ, proving the binding is broken, yet the request succeeds (`head :ok`) and a `Stack` is created for the secured repository despite zero HMAC validation.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently.
