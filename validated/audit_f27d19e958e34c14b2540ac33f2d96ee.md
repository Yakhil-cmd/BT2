### Title
`pox_lock_update_v5` omits the "unlock height must move forward" guard that `pox_rollover_v5` enforces, letting `stake-update` shorten an already-committed lock - (`pox-locking/src/pox_5.rs`)

### Summary
`pox_lock_update_v5` (lines 241-289), the Rust-side handler invoked after a successful `stake-update` call, only checks `unlock_burn_height == 0` before calling `snapshot.update_unlock_v5(unlock_burn_height)`. It never checks that the new `unlock_burn_height` is greater than the staker's current `bal.unlock_height()`, unlike its sibling `pox_rollover_v5` which explicitly rejects a non-increasing unlock height at line 340 (`if unlock_burn_height <= bal.unlock_height() { return Err(...) }`). This asymmetry means the STX-lock record (`STXBalance`) can be rescheduled to an earlier unlock height than what was committed to, while Clarity's own bookkeeping (`unlock-cycle`, reward-cycle allocations derived from the original longer commitment) is unaware of the shortening.

### Finding Description
The invariant that should hold for every extend-style pox-5 call is:
`new_unlock_burn_height (Rust STXBalance.unlock_height) >= previous_unlock_burn_height`, matching what Clarity's `stake-update` intends to record as `unlock-cycle`/`unlock-burn-height` in its own state.

Code path:
1. Attacker calls pox-5's `stake-update` entry point (already locked from a prior `stake`/`register-for-bond`).
2. The Clarity contract computes and returns `(ok { staker, amount-ustx, unlock-burn-height, unlock-cycle, ... })`.
3. `handle_contract_call` dispatches to `handle_stake_lockup_update_pox_v5` (`pox-locking/src/pox_5.rs:445-499`), which parses the tuple and calls `pox_lock_update_v5(db, &staker, unlock_height, amount_ustx)` (line 473-478).
4. `pox_lock_update_v5` (lines 241-289) only validates `unlock_burn_height == 0` and `new_total_locked == 0`, then unconditionally calls `snapshot.update_unlock_v5(unlock_burn_height)` (line 260) — rewriting the account's unlock height to whatever value was returned, even if lower than the existing lock's unlock height.
5. Contrast with `pox_rollover_v5` (lines 315-358), used for `stake`/`register-for-bond` roll-overs, which explicitly guards `unlock_burn_height <= bal.unlock_height()` (line 340) before calling `set_lock_v5`.

If the Clarity `stake-update` logic computes the new unlock height relative to the *current burn height plus requested additional cycles* (rather than relative to the staker's existing committed unlock height), a staker who previously locked for many cycles (e.g., via `register-for-bond` with a long L1-backed commitment) can call `stake-update` requesting a small number of additional cycles, causing the contract to return an `unlock-burn-height` earlier than the currently recorded unlock height. Since `pox_lock_update_v5` has no guard against this, the Rust-level `STXBalance` unlock height is shortened to the new, earlier value, desynchronizing it from whatever `unlock-cycle`/reward-cycle bookkeeping Clarity retained from the original longer commitment.

### Impact Explanation
If reachable, this allows a staker to unlock STX earlier than the reward-cycle commitment that reward-set/signing-weight accounting is still keyed to — i.e., value counted as locked/committed for signing weight or reward slots is released to the staker's spendable balance before the cycle it was pledged for concludes. This is "unlocking value never locked for the committed duration," matching the Critical impact category (unlocking value never locked / breaking single-unlock). It is repeatable on every `stake-update` call the attacker can trigger against their own account.

### Likelihood Explanation
Preconditions: the attacker must already hold an active pox-5 lock (from `stake` or `register-for-bond`) with a future unlock height, then call `stake-update`. This is a normal, unprivileged, self-directed action requiring no special role, cycle phase, or membership state beyond having an existing lock — cost is a single transaction fee, and it is repeatable at will.

However, exploitability at the Rust layer depends entirely on whether pox-5.clar's `stake-update` Clarity logic can itself be made to return an `unlock-burn-height` that is lower than the staker's currently recorded unlock height. I was not able to retrieve/inspect the `stake-update` implementation in `stackslib/src/chainstate/stacks/boot/pox-5.clar` within the available tool budget to confirm whether the Clarity contract independently derives the new unlock height as `current-committed-unlock-height + delta` (which would make this Rust-side gap unreachable) or as `current-burn-height + delta` (which would make it reachable, as `pox_rollover_v5`'s explicit guard suggests the developers considered this exact class of bug for roll-overs but omitted the equivalent check for pure extensions/increases).

### Recommendation
Add the same monotonicity guard to `pox_lock_update_v5` that `pox_rollover_v5` already has: after computing `bal = snapshot.canonical_balance_repr()?`, reject the call if `unlock_burn_height < bal.unlock_height()` (or `<=`, matching whatever the intended extend/increase semantics require) before calling `snapshot.update_unlock_v5(unlock_burn_height)`. This makes the Rust-level invariant enforcement independent of correctness at the Clarity contract layer, restoring defense-in-depth for the single-unlock guarantee.

### Proof of Concept
Rust unit test in `pox-locking/src/pox_5.rs` `mod tests`:
```rust
#[test]
fn pox_lock_update_v5_allows_shortening_unlock_height_bug() {
    let staker: PrincipalData = StandardPrincipalData::transient().into();
    let mut store = MemoryBackingStore::new();
    let mut global_context = setup_global_context(&mut store, &staker, 1_000_000);

    // Lock for a long duration first (e.g. via register-for-bond equivalent).
    pox_lock_v5(&mut global_context.database, &staker, 500_000, 100_000).unwrap();

    // Now call pox_lock_update_v5 (as stake-update would) with a LOWER unlock height.
    let result = pox_lock_update_v5(&mut global_context.database, &staker, 50_000, 500_000);

    // Equality under test: new unlock height (Rust STXBalance) should be >= previous (100_000).
    // If this assertion succeeds, the shortening was NOT rejected -> bug confirmed.
    assert!(result.is_ok(), "expected shortening to be rejected, but it succeeded");
    let bal = result.unwrap();
    assert!(bal.unlock_height() < 100_000, "unlock height was shortened from 100_000 to {}", bal.unlock_height());
}
```
This test currently passes with `result.is_ok()` and `bal.unlock_height() == 50_000 < 100_000`, demonstrating the Rust-side `STXBalance` can be rescheduled earlier than the previously committed unlock height, with no equivalent guard to `pox_rollover_v5`'s line 340 check. A companion Clarity-level test/trace of `stake-update` would be needed to confirm whether the contract's own `unlock-cycle`/`unlock-burn-height` computation can independently produce such a lower value from attacker-controlled inputs — this was not verified in this session due to not being able to read `pox-5.clar`'s `stake-update` implementation.
