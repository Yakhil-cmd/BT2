### Title
Cross-repository CI status forgery via unscoped SHA lookup in `StatusHandler#process` unblocks victim stack deploys - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` looks up commits to update purely by `sha`, with no scoping to the repository that signed the incoming webhook, unlike its sibling handlers `PushHandler` and `CheckSuiteHandler` which explicitly scope through `stacks` (derived from `payload['repository']['full_name']`). Because git commit SHAs are content-addressed and identical across forks/shared history, an attacker who controls any repository wired into Shipit (their own fork of, or a repo sharing ancestry with, the victim's repo) can generate a real, correctly-signed GitHub status webhook that Shipit will apply to a completely different, victim-owned `Shipit::Commit` row, flipping its blocking status and unblocking the victim's deploy chain via `Commit#blocked?`/`#deployable?`.

### Finding Description
The binding the system needs, but does not enforce, is:

`repository authenticated by webhook signature (payload['repository']['owner']['login']) == repository that owns the Shipit::Commit row being mutated by the status update`

Tracing the path:

1. `Shipit::WebhooksController#verify_signature` only verifies the HMAC of the raw body against `Shipit.github(organization: repository_owner).webhook_secret`, where `repository_owner` is read straight from the attacker-controlled `payload['repository']['owner']['login']` field [1](#0-0) . This proves only that the request came from GitHub for *some* org Shipit knows about — it says nothing about which `Commit`/`Stack` the payload's `sha` is allowed to touch.
2. `Handler#stacks` exists precisely to scope handling to the repository named in the payload, via `Repository.from_github_repo_name(repository_name)&.stacks` [2](#0-1) , and both `PushHandler#process` and `CheckSuiteHandler#process` correctly use this scope before touching any commit [3](#0-2) [4](#0-3) .
3. `StatusHandler#process`, however, ignores `stacks` entirely and queries the global `Commit` table by `sha` alone: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [5](#0-4) . Any `Shipit::Commit` row in any stack, belonging to any tenant, sharing that SHA gets the status applied.
4. `Commit#create_status_from_github!` creates a `Status` record via `Status.replicate_from_github!` and calls `add_status`, updating the commit's cached status/state [6](#0-5) , [7](#0-6) .
5. This directly changes the result of `Commit#blocked?` — `stack.commits.reachable.newer_than(stack.last_deployed_commit).older_than(self).any?(&:blocking?)` — and therefore `Commit#deployable?` for later commits in the victim's stack [8](#0-7) .

Exploit flow: since git SHAs are content hashes, a commit that exists in the victim's tracked repository can also exist, with the identical SHA, in a fork or any other repository sharing that commit's ancestry (e.g., an attacker forks the victim's public repo and never rewrites history). If the attacker's fork/repo is itself wired to Shipit (or to any GitHub App/org whose webhook secret Shipit knows), the attacker — who has ordinary push/write access to their own repo — can call the real GitHub API `POST /repos/{attacker}/{repo}/statuses/{sha}` with `state: success` for that shared SHA. GitHub delivers a webhook to Shipit's `/webhooks` endpoint, correctly signed with the secret associated with the attacker's own organization/app installation (a normal, unprivileged, self-service action). `verify_signature` passes because it only checks the attacker's own org's secret against the attacker's own payload — it never cross-checks that this org actually owns the `sha` being referenced. `StatusHandler#process` then finds and mutates the victim's `Commit` row for that same SHA in an entirely different stack.

Existing guards do not catch this: `verify_signature` authenticates the org, not the SHA-to-repository mapping; `drop_unhandled_event` and the `ExplicitParameters` schema only validate shape, not ownership; there is no `require_permission!`/`User#authorized?` check in the unauthenticated webhook path (by design, since GitHub itself is the caller) and no model-level check tying `Status`/`Commit` update to the `repository` named in the payload.

### Impact Explanation
An attacker fully controlling only their own GitHub repository can create or manipulate a `Status` record on a `Shipit::Commit` belonging to a victim's stack in a different tenant, changing `Commit#blocked?`/`#deployable?` results. This can unblock a deploy chain the victim never approved (a payload from one repository mutating another repository's commit/stack state, leading to an unauthorized deploy) — matching the Critical category "a payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy." It is repeatable against any victim stack whose tracked commits share a SHA with a repository the attacker can trigger real GitHub statuses on (most straightforwardly, forks of the same repo, or any repo sharing history/cherry-picks).

### Likelihood Explanation
Preconditions: the victim stack must have `blocking_statuses`/CI blocking configured and an older undeployed commit currently in a blocking state, per the question's premise. The attacker needs: (a) a GitHub repository they control that is wired to a Shipit-known GitHub App/org (so their own webhook signature verifies), and (b) a commit SHA shared between their repo and the victim's tracked repo — trivially achievable by forking the victim's public repository, since fork history shares identical commit objects/SHAs until diverged. No Shipit credentials, sessions, or GitHub secrets are required; the only actions used (`git fork`, `POST .../statuses/{sha}` on their own repo) are ordinary unprivileged GitHub operations. This is feasible and repeatable per targeted SHA/stack.

### Recommendation
Scope `StatusHandler#process` to the requesting repository, mirroring `PushHandler`/`CheckSuiteHandler`: resolve commits only within `stacks` (i.e., `stacks.flat_map(&:commits).where(sha: params.sha)` or equivalent), so a status webhook can only mutate commits belonging to stacks whose `Repository` matches `payload['repository']['full_name']`, rather than a global `Commit.where(sha: ...)` lookup.

### Proof of Concept
Minitest plan (`test/models/webhooks/handlers/status_handler_test.rb` or extending `test/controllers/webhooks_controller_test.rb`):
1. Seed two distinct stacks/repositories: `victim_stack` (fixture-based, e.g. modeled on `shipit_commits(:soc_second)`/`(:soc_third)` with `blocking_statuses` configured and `soc_second` currently in a `failure`/blocking state older than undeployed `soc_third`), and `attacker_stack` pointing to a different `Repository` (e.g. `attacker/repo`).
2. Create a `Commit` row in `attacker_stack` with the same `sha` as `victim_stack`'s blocking commit (`soc_second.sha`).
3. Assert baseline: `assert_equal false, soc_third.deployable?` (blocked because `soc_second.blocking?` is true).
4. Post a `status` webhook via `WebhooksController#create` with `repository.owner.login` set to the attacker's org (stubbing/mocking `verify_webhook_signature` to return true for that org only, simulating a legitimately-signed request for the attacker's own repo), `sha: soc_second.sha`, `state: 'success'`.
5. Assert the equality that should hold but doesn't: `assert_not_equal payload_repository_owner, victim_stack.repository.owner` while still observing `soc_second.reload.state == 'success'` and `assert_equal true, soc_third.reload.deployable?` — proving a webhook authenticated for the attacker's repository mutated and unblocked the victim's stack.
