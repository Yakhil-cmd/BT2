## Title
Cross-organization webhook forgery due to signature-verification/target binding mismatch - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App secret to validate the request's `X-Hub-Signature` against based on `params.dig('repository', 'owner', 'login')` (or the fallback `organization.login`) — a field fully controlled by the payload body itself. Once the signature check passes for that "authenticating" organization, the resulting handler (`PushHandler`, `StatusHandler`, `CheckSuiteHandler`, etc.) resolves the actual target repository/stack from a *different* field, `params.dig('repository', 'full_name')` (`app/models/shipit/webhooks/handlers/handler.rb`), which is never cross-checked against the organization that produced a valid signature.

### Finding Description
`Shipit` supports multi-tenant configuration where each GitHub organization has its own GitHub App and `webhook_secret` [1](#0-0) . `Shipit.github(organization:)` looks up per-organization config and instantiates a `GitHub App` scoped to that org [2](#0-1) .

In `WebhooksController`, the org used to select the verification secret is taken directly from the untrusted JSON body: [3](#0-2) [4](#0-3) 

`verify_webhook_signature` then simply HMACs the *entire* raw body against the secret belonging to whatever organization the attacker claimed in `repository.owner.login`: [5](#0-4) 

Once verification succeeds, event handlers ignore `repository.owner.login` entirely and instead resolve the target stack(s) using `repository.full_name`: [6](#0-5) [7](#0-6) [8](#0-7) [9](#0-8) 

`Repository.from_github_repo_name` splits this attacker-controlled `full_name` on `/` and looks up any repository by owner/name in the whole instance, with no relationship enforced to the organization that authenticated the request: [10](#0-9) 

**Binding broken:** the organization that authenticated the webhook (`repository.owner.login`, used only to pick the HMAC secret) ≠ the repository that is actually written to / acted upon (`repository.full_name`, used by every handler to resolve stacks/commits). Because HMAC-SHA1 covers the raw bytes of the whole JSON body but the controller never re-derives or pins the org from the same field the handlers trust, an attacker holding a valid webhook secret for Org A (e.g., because they are a legitimate admin who installed Shipit for their own Org A) can forge a signed payload where `repository.owner.login = "org-a"` (so it validates against Org A's secret) while `repository.full_name = "org-b/some-repo"` (an unrelated organization's repository/stack hosted on the same Shipit instance). The `push`/`status`/`check_suite` handlers act on Org B's stack using data entirely supplied by the Org A attacker, e.g.:
- Forging a `push` event causes `stack.sync_github(expected_head_sha:)` to run against Org B's stack with an attacker-chosen `after` SHA [11](#0-10) .
- Forging a `status` event lets the attacker create arbitrary CI statuses (`state`, `context`, `description`) on any commit SHA already known in Org B's stack [8](#0-7) , which can flip `deployable?`/safety checks feeding continuous delivery (`ContinuousDeliveryJob` deploys automatically once `stack.continuous_deployment?` and no blocking checks) [12](#0-11) .

### Impact Explanation
This crosses an authentication boundary the same way the reported ArkProject bug crosses an escrow-ownership boundary: the entity that is cryptographically authenticated (Org A, via its own webhook secret) is not the entity whose state is mutated (Org B's stack/commit/status). On an instance hosting multiple GitHub organizations (the documented multi-app configuration), this allows one organization's legitimate webhook-secret holder to inject forged CI status/push data into another organization's stack, which can influence `continuous_deployment` and safety-gated deploys — matching the "unauthorized deploy" High/Critical impact bucket.

### Likelihood Explanation
Requires the instance to be configured with multiple GitHub organizations (documented, supported feature) and requires the attacker to control a legitimate webhook secret for at least one of those organizations (obtainable by anyone who is a legitimate GitHub App owner for their own org on the shared instance, not by a fully external unprivileged party against a single-org deployment). Likelihood is therefore moderate and scoped to multi-tenant deployments, but no repository write access, session, or `ApiClient` token is needed — only knowledge of one organization's `webhook_secret`, which the attacker is entitled to know as an app installer for their own org.

### Recommendation
After signature verification succeeds for organization `X`, re-validate that `params.dig('repository', 'owner', 'login')` (or `organization.login`) used for verification is the same value the handlers use to resolve the target repository/stack, or better, resolve the target `Repository`/`Stack` first and confirm it belongs to the same `owner` as the organization whose secret validated the signature, rejecting the webhook otherwise.

### Proof of Concept
1. Instance configured with two orgs, `org-a` and `org-b`, each with its own `github.webhook_secret` (per `docs/setup.md` "Using Multiple Github Applications").
2. Attacker is a legitimate installer/admin of the `org-a` GitHub App and thus knows `org-a`'s `webhook_secret`.
3. Attacker crafts a JSON body for the `status` (or `push`) event:
```json
{
  "repository": { "owner": { "login": "org-a" }, "full_name": "org-b/target-repo" },
  "sha": "<commit sha known in org-b's stack>",
  "state": "success",
  "context": "ci/attacker"
}
```
4. Attacker computes `X-Hub-Signature: sha1=HMAC_SHA1(org_a_webhook_secret, raw_body)` and POSTs to `/github/webhooks`.
5. `verify_signature` calls `Shipit.github(organization: "org-a")` and validates successfully against `org-a`'s secret [3](#0-2) .
6. `StatusHandler#process` looks up `Commit.where(sha: params.sha)` — matching commits belonging to `org-b`'s stacks — and creates a forged status on them [8](#0-7) , with no check that `org-b` is the org that authenticated the request.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?

    @github[organization] ||= GitHubApp.new(organization, config)

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
