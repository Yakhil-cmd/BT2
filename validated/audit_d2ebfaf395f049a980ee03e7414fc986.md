### Title
Stale signer-key grants remain valid after rotation, allowing a compromised/old signer key to resume authority in `pox-5.clar` - ([File: stackslib/src/chainstate/stacks/boot/pox-5.clar])

### Summary
`pox-5.clar`'s signer-key grant/registration model is directly analogous to the reported bug class: a credential ("session") that should be invalidated when a new credential is issued (a "password change") is instead left valid indefinitely unless a separate, explicit revocation call is made. In `pox-5.clar`, rotating a signer's key from key `A` to key `B` via `register-signer` does **not** invalidate the grant previously issued for key `A`. Anyone who still holds key `A` (e.g. a leaked/weak/compromised key) can re-establish it as the active signer for that `signer-manager`, exactly mirroring "attacker continues accessing the account using the old session" after a password change.

### Finding Description
`register-signer` in `pox-5.clar` only checks that the presented key has an active grant, and then overwrites the `signers` map entry: [1](#0-0) 

`verify-signer-key-grant` checks a per-key grant record, and `grant-signer-key` records single-use anti-replay of the `(signer-key, signer-manager, auth-id)` tuple but never revokes the *previous* key's grant when a new one is issued: [2](#0-1) 

The project's own property-test suite documents this exact behavior as intentional-but-dangerous: rotating to a new key does not revoke the grant tied to the old key. [3](#0-2) [4](#0-3) 

There is a separate `revoke-signer-grant` entry point, confirming that revocation is an *opt-in*, manual action rather than something that happens automatically on rotation: [5](#0-4) 

The equality this breaks: "the signer currently entitled to sign/represent a `signer-manager` in `pox-5` must be exactly the most-recently-authorized key holder." Because old grants stay live, a previously-authorized (and possibly compromised) key holder can still satisfy `verify-signer-key-grant` and re-invoke `register-signer`, re-installing themselves as the active `signers` entry for that manager — reasserting stacking-signer authority the operator believed had been revoked by rotating to a new key.

### Impact Explanation
If a signer's private key is compromised (weak generation, leak, phishing — the direct analog of "weak password"), the operator's remediation of rotating to a new key does not close the exposure: the attacker's old grant remains usable to re-register as the signer, letting them resume acting with the signing weight/authority associated with that `signer-manager` for future reward cycles. This is "a stacking action the staker/signer never authorised" (the *rotated-away* key regaining control), which the rules classify as High impact.

### Likelihood Explanation
Exploitation requires: (1) an attacker who has obtained an old signer private key, and (2) the ability to trigger `register-signer` through the `signer-manager` contract with that old key. Whether (2) is reachable depends on the specific `signer-manager` implementation's caller-authorization for its `register-self`/rotation entrypoint — pox-5.clar itself does not gate this, delegating that responsibility entirely to the signer-manager contract. The reference/test signer-manager contracts in this repo (`test-pox-5-signer.clar`) impose no restriction on `register-self`'s caller, so a permissively-written signer-manager is directly vulnerable; a well-guarded one (`signer-manager.clar` with `authorize-admin`) mitigates the caller-side risk but still leaves the underlying pox-5 grant model stale-by-design.

### Recommendation
- In `pox-5.clar`, have `register-signer` (or `grant-signer-key`) automatically invalidate/remove any previously active grant for the same `signer-manager` when a new key is granted/registered, rather than requiring a separate manual `revoke-signer-grant` call.
- Alternatively, track only a single "current" grant per `signer-manager` (instead of a set of independently-live grants), so that granting/registering a new key is inherently exclusive with the old one.
- Emit an explicit revocation event whenever a key is superseded so downstream consumers/signer-managers can detect and react to old-key compromise windows.

### Proof of Concept
1. Signer manager `M` registers signer key `A` via `grant-signer-key` + `register-signer` (grant for `A` becomes active, `signers[M] = A`).
2. Key `A`'s private key leaks/is guessed.
3. `M` "changes password" by rotating: grants and registers new key `B` (`signers[M] = B`); per `RotateSignerKey.ts`, the grant for `A` is **not** revoked and remains in the active-grants set.
4. Attacker, still holding `A`, drives (or is permitted by a permissive signer-manager to drive) another call to `register-signer` with `signer-key = A`. `verify-signer-key-grant` succeeds because `A`'s grant was never revoked, and `signers[M]` is overwritten back to `A`.
5. The attacker's compromised key `A` is now the active signer for `M` again, despite the operator's rotation to `B` — the compromise was never actually closed, mirroring the "old session still works after password change" scenario from the report.
