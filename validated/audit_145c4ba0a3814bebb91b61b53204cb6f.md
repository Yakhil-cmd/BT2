### Title
`status` webhook resolves commits by bare SHA across all repositories, letting a cross-repo `ci/kubernetes` success flip a victim stack's deployability and trigger `ContinuousDeliveryJob` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` calls `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github! }` with no filter tying the lookup to the repository that authenticated the webhook. Every other handler in the base `Handler` class scopes lookups through `stacks` (derived from `payload.dig('repository', 'full_name')`), but `StatusHandler` bypasses that and queries the global `Commit` table by SHA alone, so a status payload legitimately signed for repository A can mutate a `Commit` row belonging to a completely different stack/repository B if the two share the same commit SHA.

### Finding Description
The broken binding is: **the status's authenticated repository (`payload.dig('repository','full_name')`, verified via `Shipit.github(organization: repository_owner)` in `WebhooksController#verify_signature`) MUST equal the repository owning the `Commit` row being mutated** (`commit.stack.repository`). In `StatusHandler#process`: [1](#0-0) 

the code never checks `repository_name` or restricts to `stacks` (the helper defined in the base class specifically for that purpose): [2](#0-1) 

Instead it does a bare `Commit.where(sha: params.sha)`, matching any `Commit` row in the entire installation with that SHA, then calls `create_status_from_github!` on each match, which appends a `Status` and re-evaluates deployability: [3](#0-2) [4](#0-3) 

If the newly-appended status flips `deployable?` to true and the owning stack has `continuous_deployment?` enabled, `schedule_continuous_delivery` (an `after_commit` callback fired on creation of the `Commit`, but the relevant recompute path for status changes is the deployable check inside `add_status`/`schedule_merges`) enqueues auto-deploy machinery: [5](#0-4) 

Because git commit SHAs are content-addressed (hash of tree, parent, author/committer, timestamps, message), an attacker who can observe a target commit's exact metadata (trivial for any public commit) can construct a byte-identical commit object and push/reference it from a repository they control, producing an identical SHA. They can then have a CI system (or a script with push access to that repo) post a `context: ci/kubernetes`, `state: success` status for that SHA. GitHub signs the webhook using the **attacker's own repository/organization's** secret, so `WebhooksController#verify_signature` passes legitimately — the signature check only proves "this payload really came from repository A," it says nothing about which `Commit` rows the handler is permitted to touch. `StatusHandler#process` then updates the victim's `Commit` row (belonging to stack B) as if the status originated from stack B's own CI.

Existing guards fail here because:
- `verify_signature` only authenticates the *sender repository*, not the *scope of mutation* — that's the handler's job, and `StatusHandler` doesn't do it.
- `ExplicitParameters` in `StatusHandler` validates types (`sha`, `state`, `context` are strings) but has no repository field/constraint at all.
- The base `Handler#stacks` scoping mechanism exists precisely to prevent this class of bug, but `StatusHandler` doesn't use it.

### Impact Explanation
An attacker who controls (or has push access to) any repository integrated with Shipit — even an unrelated, low-privilege one — can, without ever authenticating to Shipit or possessing any Shipit secret, force a status flip on a `Commit` belonging to a **different** stack/repository, provided a SHA collision (constructed via identical git object content) exists. On a victim stack with `continuous_deployment` enabled requiring `ci/kubernetes`, turning that commit's status to `success` can make it `deployable?` and trigger `ContinuousDeliveryJob`, i.e., an **unauthorized deploy of attacker-influenced content** without the victim's own CI ever reporting success. This is a payload for one repository mutating another's stack/commit state, matching the Critical impact category ("a payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy").

### Likelihood Explanation
Preconditions: (1) attacker needs push/webhook-posting capability on *some* repository already onboarded to the same Shipit instance (registered in `Shipit.github_teams`/github app config so `verify_signature` succeeds for their org) — this need not be the victim's own repo; (2) attacker must produce a commit object with a SHA identical to an existing `Commit` row for the victim stack, which requires reproducing the exact tree/parent/author/committer/timestamp/message of that specific commit — feasible for any commit whose metadata is public (e.g., open-source victim repo) but not a generic "any SHA" attack; (3) victim stack must have `continuous_deployment` enabled and be otherwise deployable (`stack.deployable?`). Given these, the exploit is repeatable per matching SHA and does not require any Shipit credential, session, or API token — only ordinary GitHub push/webhook capability on an unrelated onboarded repo.

### Recommendation
Scope `StatusHandler#process` to the repository that authenticated the webhook, mirroring the base `Handler#stacks` helper, e.g.:

```ruby
def process
  Commit.where(sha: params.sha, stack_id: stacks.select(:id)).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```

so status updates only ever apply to commits belonging to stacks of the repository named in `payload['repository']['full_name']`.

### Proof of Concept
minitest plan (no live GitHub):

```ruby
test "status handler does not update commits belonging to a different repository" do
  repo_a = shipit_repositories(:shipit) # attacker-controlled repo, onboarded
  repo_b = create_repository(name: 'victim') # victim's onboarded repo
  stack_b = create_stack(repository: repo_b, continuous_deployment: true)
  same_sha = 'a' * 40
  commit_b = create_commit(stack: stack_b, sha: same_sha)

  payload = {
    'sha' => same_sha,
    'state' => 'success',
    'context' => 'ci/kubernetes',
    'repository' => { 'full_name' => repo_a.full_name } # attacker's own repo, correctly signed
  }

  before_deployable = commit_b.reload.deployable?
  Shipit::Webhooks::Handlers::StatusHandler.call(payload)
  after_deployable = commit_b.reload.deployable?

  assert_equal before_deployable, after_deployable,
    "victim stack's commit deployability must not change from a status authenticated for a different repository"
end
```

Given the current implementation, `after_deployable` flips (or a `Status` row for `stack_b`'s commit is created) despite the payload's `repository.full_name` being `repo_a`, demonstrating the cross-repository write.
