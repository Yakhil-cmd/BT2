### Title
Missing null-guard on `definition` message payload causes unhandled TypeError / node crash - (File: network.js)

### Summary
`network.js`'s `getAllAuthorsAndOutputAddresses()` dereferences `message.payload.definition[1]` for `app === 'definition'` messages without first checking that `payload` exists, unlike the sibling `payment` branch which explicitly guards with `payload &&`. This mirrors the CVE-2016-10129 bug class: a parser/handler that dereferences a field assuming it is always present, crashing on a malformed/degenerate input (there, an empty Git packet line; here, a message whose payload is absent).

### Finding Description
In `getAllAuthorsAndOutputAddresses`, each message in a unit is inspected: [1](#0-0) 

The `payment` branch is defensively coded (`message.app === "payment" && payload`), but the `else if` branch for `definition` messages accesses `payload.definition[1].base_aa` with no equivalent `payload &&` guard. If `payload` is `undefined` or `null` for a `definition`-app message, this throws a `TypeError` (`Cannot read properties of undefined`), an uncaught exception in the unit-processing path that runs on every full node for every accepted unit/joint.

`payload` can legitimately be absent for a message when `payload_location` is `"none"` or `"uri"` — this is a normal, general-purpose feature of the protocol enforced generically in `validate()`: [2](#0-1) 

That loop only forbids `payload` from being present when `payload_location !== "inline"`; it does not restrict which `app` values are allowed to use non-inline payload locations. Unless there is a `definition`-specific validation rule elsewhere in `validation.js` that explicitly forces `payload_location === "inline"` for `app: "definition"` messages (I was not able to locate and confirm such a rule within the available search results — the visible per-app switch in `validateInlinePayload` only handles `profile`, `data`, `temp_data`, `definition_template`, `attestation`, `asset`, `asset_attestors`, `payment`, `poll`, `vote`, `data_feed`, none of which is literally `definition`), a unit containing a message `{ app: "definition", payload_location: "none" }` (no `payload` field) could pass general structural validation while still reaching `getAllAuthorsAndOutputAddresses` later, since that function is invoked whenever a unit is processed/broadcast after being saved.

### Impact Explanation
An uncaught `TypeError` thrown deep inside unit-processing code (not wrapped in a try/catch at this call site) can crash or destabilize the Node.js process on every full node that processes the malicious unit, since `getAllAuthorsAndOutputAddresses` is invoked as part of standard joint/notification handling for every unit entering the DAG. If reachable widely across nodes, this is a network-wide denial of service that prevents nodes from continuing to process/confirm new units — directly matching the "network unable to confirm new units" impact bar.

### Likelihood Explanation
The trigger requires only posting an ordinary unit containing a `definition`-app message with `payload_location` set to `"none"` or `"uri"` (omitting `payload`), an action any unprivileged unit poster can attempt. The likelihood is contingent on confirming that no earlier, `definition`-specific validation rule rejects non-inline payload location for this app — I could not fully verify this due to not locating the exact `case "definition"` validation block content in `validation.js` within the tool-call budget available. This is the key open uncertainty for this finding; if such a rule already forces `payload_location === "inline"` for `definition` messages, this specific code path would be unreachable via untrusted input, and the missing guard would be a latent/dead-code defensive gap rather than an exploitable one.

### Recommendation
- Add the same defensive `payload &&` guard to the `definition` branch as already used for `payment`:
  ```js
  else if (message.app === 'definition' && payload && payload.definition && payload.definition[1] && payload.definition[1].base_aa)
  ```
- Independently, confirm/enforce in `validation.js` that `app: "definition"` messages must always use `payload_location: "inline"` (since the definition content must be publicly derivable), rejecting any unit that tries to use `"none"`/`"uri"` for this app.
- Wrap unit-processing entry points (e.g., around `getAllAuthorsAndOutputAddresses` and similar consumers of `objUnit.messages`) with defensive try/catch so a single malformed unit cannot crash the whole node process, providing defense-in-depth against similar oversights elsewhere.
