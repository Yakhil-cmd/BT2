Found the actual analog: ocore has a built-in **`in merkle`** address-definition primitive that is structurally identical to `TrufMigrator.migrate()`. It lets an address's spending authority be gated on proving that some `element` is part of a Merkle tree whose root was posted by an oracle via a data feed. Just like `TrufMigrator`, the "root" (here, the data-feed value) is fully mutable by the posting address at any time, with no history/versioning kept — so a change of root can invalidate previously-valid, still-unclaimed proofs and, more importantly, leaves stale-root usage ambiguous depending on which data-feed version the validator picks.

### Title
Mutable oracle-controlled Merkle root in `in merkle` definitions can strand or desynchronize authorized spenders - (File: `definition.js`)

### Summary
The `in merkle` authentifier condition authorizes spending by proving an `element` belongs to a Merkle tree whose root is read from a **data feed** (`dataFeeds.dataFeedExists`), not from an immutable definition field. Any address controlling the oracle can post a new data-feed value (a new Merkle root) at any time, silently invalidating all previously valid proofs for addresses relying on the old root, with no compensating mechanism to migrate committed claims — mirroring the `TrufMigrator.setMerkleRoot` root-change hazard from the audit report.

### Finding Description
`validateDefinition` accepts `in merkle` with `[arrAddresses, feed_name, element, min_mci]` [1](#0-0) , and at authentication time `validateAuthentifiers` verifies the supplied Merkle proof against **whatever root currently satisfies the data feed lookup** via `dataFeeds.dataFeedExists(arrAddresses, feed_name, '=', proof.root, min_mci, objValidationState.last_ball_mci, false, cb2)` [2](#0-1) . Unlike `TrufMigrator.migratedAmount`, ocore's `in merkle` has no state at all to track which users already validated against which root — but the underlying vulnerable pattern (owner/oracle-controlled root with `onlyOwner`/`setDataFeed` style updates and no way to reconcile pre-change proofs) is present: the data feed value can be updated by its posting address without restriction, exactly as `setMerkleRoot` had no restrictions in the reported bug [3](#0-2) .

Because the check accepts `main_chain_index<=? AND main_chain_index>=?` (i.e. it will match **any** historical value of the feed within `[min_mci, last_ball_mci]`, not only the latest), an address whose definition uses `in merkle` can continue to spend using an **old, superseded** root as long as `min_mci` is small enough, while a second address that was defined to require the new root at a higher `min_mci` cannot use the old one. This means the "meaning" of authorization silently depends on the range of MCIs supplied in the definition, and once an oracle rotates roots (analogous to `setMerkleRoot`), any address whose `min_mci` was pinned to expect a particular root generation can become permanently unable to produce a satisfying proof if the new tree does not include their `element`, with the address's spending authority frozen — the same "funds/authorization frozen after a root change" outcome as the reported Sherlock finding, but at the definition/authentifier layer instead of an AA state-variable layer.

### Impact Explanation
If an oracle (which could itself be an AA or a compromised/careless posting address) rotates the Merkle root feed used by `in merkle` conditions (e.g., to update an allow-list or a claim set), any address whose authorization depends on the old tree loses spending authority for outputs/assets protected by that definition, freezing funds. Conversely, because `dataFeedExists`/`readDataFeedValue` can match older feed postings when `min_mci` is unrestricted, spending authorization can persist against a root the oracle believed retired, creating inconsistent enforcement across addresses — a node-disagreement/authorization-integrity risk rather than a simple usability bug.

### Likelihood Explanation
Any AA or address owner using `in merkle` in a real definition (whitelists, claim/airdrop-style spending conditions, etc.) is exposed the moment the oracle rotates its Merkle root — this requires only a single ordinary data-feed-posting unit, no special privilege beyond being the named oracle address, matching the "unprivileged sender reachable" bar (the oracle role here is analogous to a project owner posting merkle roots, exactly as in the original report).

### Recommendation
For `in merkle`, either (a) always resolve to the **latest** data-feed value at authentication time (drop or clamp the historical `min_mci`/`max_mci` window so an old-but-still-matching root can't be reused after rotation), and/or (b) document/require oracle-side protocols that only ever add leaves (append-only Merkle trees) rather than fully replacing the tree, so previously valid elements remain provable after a root update. This mirrors the original recommendation to refactor `TrufMigrator` to support incremental/leftover claims instead of a hard `amount <= previous` cutoff.

### Proof of Concept
1. Oracle address `O` posts data feed `feed_name = R1` (Merkle root of set `{A, B}`), and address `X` is defined with `["in merkle", [["O"], "feed_name", "A", 0]]`.
2. `X` can spend by proving `A ∈ R1` — `validateAuthentifiers` verifies via `merkle.verifyMerkleProof` and `dataFeeds.dataFeedExists` [4](#0-3) .
3. Oracle `O` posts a new data feed value `feed_name = R2` (Merkle root of a new set that no longer contains `A`, e.g. `{C, D}`), with no restriction on how often/when this can happen [5](#0-4) .
4. `X` can no longer produce a proof of `A` against `R2` and is permanently unable to spend from that address/asset condition unless the oracle republishes a tree containing `A` again — the same "root rotated, prior claimant locked out" scenario as `TrufMigrator`.

	var bLimitedPrecision = (max_mci < constants.aa2UpgradeMci);
	if (bAA) {
		var bFound = false;
		function relationSatisfied(v1, v2) {
			switch (relation) {
				case '<': return (v1 < v2);
				case '<=': return (v1 <= v2);
				case '>': return (v1 > v2);
				case '>=': return (v1 >= v2);
				default: throw Error("unknown relation: " + relation);
			}
		}
		function valueIsNumber() {
			if (typeof value === 'string') {
				const float = string_utils.toNumber(value, bLimitedPrecision);
				return float !== null;
			}
			return true;
		}
		for (var unit in storage.assocUnstableMessages) {
			var objUnit = storage.assocUnstableUnits[unit] || storage.assocStableUnits[unit];
			if (!objUnit)
				throw Error("unstable unit " + unit + " not in assoc");
			if (!objUnit.bAA)
				continue;
			if (objUnit.latest_included_mc_index < min_mci || objUnit.latest_included_mc_index > max_mci)
				continue;
			if (_.intersection(arrAddresses, objUnit.author_addresses).length === 0)
				continue;
			storage.assocUnstableMessages[unit].forEach(function (message) {
				if (message.app !== 'data_feed')
					return;
				var payload = message.payload;
				if (!ValidationUtils.hasOwnProperty(payload, feed_name))
					return;
				var feed_value = payload[feed_name];
				if (relation === '=') {
					if (value === feed_value || value.toString() === feed_value.toString())
						bFound = true;
					return;
				}
				if (relation === '!=') {
					// search only within the same type, otherwise 'abc' != 123 but we don't want to say that they are not equal, because they are incomparable
					if (valueIsNumber()) {
						if (value.toString() !== feed_value.toString())
							bFound = true;
					}
					else {
						if (value !== feed_value)
							bFound = true;
					}
					return;
				}
				if (typeof value === 'number' && typeof feed_value === 'number') {
					if (relationSatisfied(feed_value, value))
						bFound = true;
					return;
				}
				var f_value = (typeof value === 'string') ? string_utils.toNumber(value, bLimitedPrecision) : value;
				var f_feed_value = (typeof feed_value === 'string') ? string_utils.toNumber(feed_value, bLimitedPrecision) : feed_value;
				if (f_value === null && f_feed_value === null) { // both are strings that don't look like numbers
					if (relationSatisfied(feed_value, value))
						bFound = true;
					return;
				}
				if (f_value !== null && f_feed_value !== null) { // both are either numbers or strings that look like numbers
					if (relationSatisfied(f_feed_value, f_value))
						bFound = true;
					return;
				}
				if (typeof value === 'string' && typeof feed_value === 'string') { // only one string looks like a number
					if (relationSatisfied(feed_value, value))
						bFound = true;
					return;
				}
				// else they are incomparable e.g. 'abc' > 123
			});
			if (bFound)
				break;
		}
		if (bFound)
			return handleResult(true);
	}
	async.eachSeries(

			dataFeedByAddressExists(address, feed_name, relation, value, min_mci, max_mci, cb);
		},
		function(bFound){
			console.log('data feed by '+arrAddresses+' '+feed_name+relation+value+': '+bFound+', df took '+(Date.now()-start_time)+'ms');
			handleResult(!!bFound);
		}
	);
