### Title
Stack-scoped API tokens can read the build status of any stack via the CCMenu endpoint - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::CCMenuController` overrides the `stack` lookup helper inherited from `Shipit::Api::BaseController` in a way that bypasses the per-`ApiClient` stack scoping, letting a token that is only supposed to authorize reads on one stack read the CCMenu (build status) data of every other stack.

### Finding Description
`Shipit::Api::BaseController` restricts which stacks an `ApiClient` may see via the `stacks` helper: [1](#0-0) [1](#0-0) 
This means `current_api_client.stack_id?` is used to bind the token to a single, specific `Stack`; every other controller obtains the stack object through `stacks.from_param!(...)`, which enforces this binding.

`CCMenuController`, however, defines its own private `stack` method that ignores this scoping entirely and resolves the stack directly from the unscoped `Stack` relation: [2](#0-1) 

The controller's only authorization check is `require_permission :read, :stack`, which calls `ApiClient#check_permissions!`: [3](#0-2) 
This only checks that the string `"read:stack"` is present in the client's `permissions` array — it never checks that the requested `stack_id` matches the `stack_id` the client is bound to. Because `CCMenuController#stack` builds the `Stack` object from `Stack.from_param!(params[:stack_id])` rather than from the client-scoped `stacks` relation, any valid, non-revoked token with `read:stack` permission can supply an arbitrary `stack_id` and receive that stack's CCMenu payload, even if the token was created scoped to a completely different stack.

This is exactly the kind of scenario the "CCMenu Client" token is meant to prevent: `CCMenuUrlController` mints a per-stack, `read:stack`-only token intended to only reveal one stack's status: [4](#0-3) 

The equality that should hold but is broken is:
`stack a token authorizes` (`current_api_client.stack_id`) ≠ `stack the request actually touches` (`params[:stack_id]` resolved unscoped in `CCMenuController#stack`).

### Impact Explanation
An attacker who obtains (or is legitimately issued) a CCMenu token scoped to stack A can pass any other `stack_id` to `GET /api/stacks/:stack_id/ccmenu.xml?token=...` and read build/lock status, last deploy id, and status of any stack in the Shipit instance — including private/production stacks they have no authorization for. This is an unauthorized cross-stack read of stack state, matching the "High" impact category (unauthenticated/unauthorized read of stack state).

### Likelihood Explanation
Likelihood is Medium-High: exploitation requires only a single valid, low-privilege `read:stack`-scoped token (these tokens are routinely distributed to CI dashboards/build-status widgets via `CCMenuUrlController#fetch`, and the URL/token is often embedded in externally visible CI tooling configuration). No special privilege beyond possessing one legitimately-scoped token is required to pivot to reading every other stack.

### Recommendation
Change `CCMenuController#stack` to reuse the inherited, client-scoped lookup (`stacks.from_param!(params[:stack_id])`) instead of the unscoped `Stack.from_param!(params[:stack_id])`, so the `stack_id` implied by the token (`current_api_client.stack_id`) is enforced consistently with every other API controller.

### Proof of Concept
1. Create (or obtain) a Stack A and visit its CCMenu URL page so `CCMenuUrlController#fetch` mints a `read:stack`-scoped `ApiClient` bound to Stack A, returning a token `T`.
2. Send `GET /api/stacks/<stack-B-id>/ccmenu.xml?token=T` where Stack B is a different, unrelated stack.
3. `CCMenuController#authenticate_api_client` authenticates `T` successfully (it's a valid client with `read:stack`), and `require_permission :read, :stack` passes because it only checks the permission string, not the stack binding.
4. `CCMenuController#stack` resolves Stack B directly via `Stack.from_param!(params[:stack_id])`, bypassing the `current_api_client.stack_id` restriction, and the response renders Stack B's build status/lock state — data the token was never authorized to access. [5](#0-4)
