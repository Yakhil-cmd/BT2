### Title
Cross-tenant status forgery in `Shipit::Webhooks::Handlers::StatusHandler` triggers unauthorized `ContinuousDeliveryJob` for a foreign stack - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` resolves the target commit purely by `sha` with no repository scoping, and `WebhooksController#verify_signature` derives the signing key from the attacker-supplied `repository.owner.login` in the payload rather than from the commit/stack actually being mutated. When the organization owning that attacker-named repository has no `webhook_secret` configured, `GitHubApp#verify_webhook_signature` returns `true` unconditionally, letting an unauthenticated request forge a `status` event for any SHA, including one that happens to also exist in a different tenant's stack, and drive that stack into `Commit#schedule_continuous_delivery` → `ContinuousDeliveryJob.perform_later(stack)`.

### Finding Description
The claimed binding is: **the actor authorizing continuous delivery on stack A == an identity with write access to repository A**. Tracing the code shows this binding is not enforced anywhere in the `status` webhook path:

- `WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-49`) computes `repository_owner` from `params.dig('repository','owner','login')` — fully attacker-controlled JSON in the POST body — and does `Shipit.github(organization: repository_owner)` then `github_app.verify_webhook_signature(signature, raw_post)`.
- `GitHubApp#verify_webhook_signature` (`lib/shipit/github_app.rb:76-83`) contains `return true unless webhook_secret`. If the organization resolved from the attacker-chosen `repository.owner.login` has no `webhook_secret` configured (a valid, documented configuration state — see `config/secrets.development.shopify.yml:9` and `test/dummy/config/secrets_double_github_app.yml:7`), **any unsigned request passes verification**, with no signature at all required.
- `StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`) then does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }`. This lookup is **global across all stacks/repositories** — it does not filter by `stack_id`, `repository`, or any tenant-scoping field tied to the `repository_owner` used for signature verification.
- `Commit#create_status_from_github!` → `Status#schedule_continuous_delivery` (`app/models/shipit/status.rb:19,42-44`) → `Commit#schedule_continuous_delivery` (`app/models/shipit/commit.rb:281-287`), which checks only `deployable? && stack.continuous_deployment? && stack.deployable?` and enqueues `ContinuousDeliveryJob.perform_later(stack)` for **stack A** (the stack owning the matched commit), completely independent of which organization's webhook_secret validated the request.

Exploit flow: attacker (who owns repo B, or any repo under an org with no configured `webhook_secret`) finds/knows a SHA that also exists as a commit on stack A (SHAs are 40-hex Git object ids, and in practice this requires either a coincidental shared commit — e.g., a shared base branch/fork lineage, cherry-pick, or a monorepo split into multiple Shipit stacks — or an org configured without a secret). Attacker sends `POST /webhooks` with header `X-Github-Event: status`, body `{"repository":{"owner":{"login":"<org-without-secret>"}}, "sha":"<stackA_commit_sha>", "state":"success", ...}`. `verify_signature` accepts it unconditionally for that org. `StatusHandler` finds the commit on stack A by SHA alone and writes a `success` status, which — if stack A has `continuous_deployment?` enabled — schedules `ContinuousDeliveryJob` for stack A.

Existing guards fail because: `drop_unhandled_event` doesn't examine payload contents; `ExplicitParameters` schema for `StatusHandler` only validates types of `sha`/`state`, not repository ownership; there is no `require_permission!`/`stacks` scope check in this webhook path (webhooks are inherently unauthenticated by session/API-token design and rely entirely on the HMAC signature, which fails open when `webhook_secret` is blank).

### Impact Explanation
A forged webhook can write a `Status` record for a commit belonging to a stack whose owning repository the attacker never authenticated against, and if that stack has continuous deployment enabled, it results in `ContinuousDeliveryJob` being enqueued and (per `Stack#trigger_continuous_delivery`) an actual `Deploy` being triggered for stack A's already-merged commit — a payload/webhook nominally tied to repository B mutating stack/commit/deploy state belonging to repository A. This matches the Critical impact category: "a payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy." It is repeatable against any stack/commit combination sharing a SHA, and the blast radius spans all tenants of a shared Shipit instance whenever at least one configured GitHub organization lacks a `webhook_secret`.

### Likelihood Explanation
Exploitability strictly depends on: (1) at least one org registered in `Shipit.secrets.github` having no `webhook_secret` set — a configuration the code explicitly supports and treats as "no verification needed" rather than "reject"; and (2) a SHA collision/overlap between the attacker's named repository and a real commit on the target stack A, which is plausible in monorepo-to-multiple-stacks setups, forks, or shared history, but is not guaranteed in general. Given precondition (1), attacker cost is a single unauthenticated HTTP POST, fully repeatable and scriptable. Given precondition (1) absent (every org has a properly configured non-blank `webhook_secret`), the forged request is rejected at `verify_signature` and the vulnerability does not materialize — the root cause specifically is the `return true unless webhook_secret` fail-open behavior combined with the missing repository-scoping in the commit lookup.

### Recommendation
1. In `GitHubApp#verify_webhook_signature`, do not fail open when `webhook_secret` is blank; require an explicitly configured secret for any organization accepting webhooks, or reject in production if unset.
2. In `Shipit::Webhooks::Handlers::StatusHandler#process`, scope the `Commit` lookup by the repository identified in the payload (e.g., join through `Stack#repository`/`github_repo_name` and only update commits belonging to stacks whose repository matches `params.dig('repository','full_name')`), not by bare `sha` alone.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (new test)
test "forged status for org without webhook_secret cannot trigger CD on an unrelated stack" do
  stack_a = shipit_stacks(:shipit)
  commit  = stack_a.commits.last
  stack_a.update!(continuous_deployment: true)
  Shipit::Stack.any_instance.stubs(:continuous_deployment?).returns(true)

  # Simulate an org with no webhook_secret configured
  Shipit.stubs(:github).with(organization: 'attacker-org').returns(
    Shipit::GitHubApp.new('attacker-org', {}) # webhook_secret nil -> verify returns true
  )

  request.headers['X-Github-Event'] = 'status'
  body = {
    sha: commit.sha,
    state: 'success',
    repository: { owner: { login: 'attacker-org' }, full_name: 'attacker/unrelated-repo' }
  }.to_json

  Shipit::ContinuousDeliveryJob.expects(:perform_later).with(stack_a).never
  # This assertion is expected to FAIL against current code, proving the bug:
  # replace .never with .once to demonstrate the forged trigger actually fires.
  post :create, body:, as: :json
  assert_response :ok
end
```
This test demonstrates that `verify_signature` accepts the request (no signature header needed because `webhook_secret` is blank for `attacker-org`), and `StatusHandler` matches `commit` purely by `sha`, calling `commit.create_status_from_github!`, which cascades into `ContinuousDeliveryJob.perform_later(stack_a)` for a stack the "attacker-org" repository never owned or authenticated against.     def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
