### Title
Webhook signature is verified against the organization derived from `repository.owner.login`/`organization.login`, but handlers act on the unrelated `repository.full_name` field, letting any onboarded organization spoof events for another organization's stacks - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`Shipit::WebhooksController#verify_signature` selects which GitHub App/organization config (and therefore which `webhook_secret`) to use for HMAC verification based on `repository_owner`, computed from the payload itself. Every `Shipit::Webhooks::Handlers::Handler` subclass (e.g. `PushHandler`) independently resolves the `Stack`/`Repository` to act on from a *different* field of the same payload, `repository.full_name`. Because the whole raw body is attacker-supplied JSON (not a genuine GitHub-generated payload), nothing forces these two fields to refer to the same repository/organization.

### Finding Description
`verify_signature` picks the app config like this: [1](#0-0) [2](#0-1) 

`repository_owner` reads `repository.owner.login`, falling back to `organization.login` — both attacker-controlled fields in the raw POST body. `Shipit.github(organization: repository_owner)` then looks up the org-specific `webhook_secret` used to HMAC-verify the *entire* raw body: [3](#0-2) 

Separately, every handler resolves the actual `Stack`/`Repository` to operate on from `repository.full_name`, a sibling field in the same JSON body: [4](#0-3) [5](#0-4) 

Because HMAC verification only proves "this body was signed with organization X's secret", not "organization X owns the repository named inside this body", an attacker who legitimately administers **any** GitHub organization onboarded into a shared/multi-tenant Shipit instance (and therefore knows that organization's own `webhook_secret`, since they configured/received it when installing the GitHub App/webhook for their own org) can craft an arbitrary JSON body where `repository.owner.login` = their own org (so the secret they know is selected and the signature check passes) while `repository.full_name` = `victim-org/victim-repo`, a completely unrelated stack tracked by the same Shipit instance. The handler layer will then process the forged event (e.g. `push`, `status`, `check_suite`, `deployable_status`) against the victim stack, which they have no GitHub or Shipit permission over.

This is the structural analog of the audited bug: the value the trust decision is computed from (`repository_owner` → secret selection) is not the same value later trusted for the privileged action (`repository.full_name` → which stack is mutated), i.e. "an organization that authenticated versus the repository that is written" binding is broken.

### Impact Explanation
Depending on which event/handler is hit, an attacker who only controls an unrelated onboarded organization can:
- Force `Stack#sync_github` to run for a victim stack via `push`, pulling/registering forged commits (`PushHandler`).
- Inject forged CI/commit statuses (`status`/`check_suite`/`deployable_status` events) into a victim's commit history, potentially satisfying `ci.require` checks and enabling continuous-delivery auto-deploys of a commit that never actually passed CI.
- Manipulate team/membership records tied to the wrong organization via `membership` events.

Given Shipit's continuous-deployment feature can automatically trigger deploys once CI/deployable-status conditions are met, spoofed status events crossing organization boundaries can escalate to an unauthorized deploy, satisfying the "cross-repository writes / unauthorized deploy" impact bar.

### Likelihood Explanation
This requires the Shipit deployment to be multi-tenant (multiple GitHub organizations configured with distinct `webhook_secret`s in `Shipit.github_configs`/app config) and the attacker to be an administrator of at least one of those organizations (i.e., they legitimately know their own org's webhook secret) but have no access to the victim organization's repositories or Shipit stacks. This is a realistic operating mode for shared Shipit instances but does not apply to single-tenant deployments where only one organization is configured. Likelihood is therefore Medium — it requires a specific but supported and undocumented-as-unsafe deployment configuration, not any additional privileged Shipit credential.

### Recommendation
After verifying the HMAC signature, re-validate that the repository named in the payload (`repository.full_name`) actually belongs to the organization whose secret validated the signature (`repository_owner`), rejecting the webhook with 422 if they diverge. Alternatively, resolve the `Stack`/`Repository` using the same `repository_owner`-derived organization used for signature verification rather than trusting `repository.full_name` independently.

### Proof of Concept
1. Deploy Shipit configured for two organizations, `attacker-org` (attacker legitimately installed the GitHub App / webhook and knows `webhook_secret_A`) and `victim-org` (tracks stack `victim-org/victim-repo`, secret unknown to attacker).
2. Attacker crafts a `push` event body:
```json
{
  "ref": "refs/heads/master",
  "after": "deadbeef...",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<hmac(webhook_secret_A, body)>` using their own known secret.
4. POST to `/webhooks` with header `X-Github-Event: push`.
5. `verify_signature` resolves `repository_owner` = `"attacker-org"`, loads `webhook_secret_A`, and the HMAC check passes. [6](#0-5) 
6. `PushHandler#process` resolves stacks from `repository.full_name = "victim-org/victim-repo"` and triggers `sync_github` on the victim's stack, which the attacker never authenticated against. [5](#0-4)

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
