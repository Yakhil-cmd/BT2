### Title
Webhook signature verified against the organization named in the payload while handlers act on a different `repository.full_name` field, allowing cross-organization event spoofing - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/webhook secret to use for HMAC verification from an **untrusted** field in the request body (`repository.owner.login` / `organization.login`), then verifies the signature against the **whole** raw body with that secret. Every webhook `Handler` subsequently determines which `Repository`/`Stack` the event applies to using a **different** field of the same body, `repository.full_name` (`Handler#repository_name`). Nothing ties the field used to pick/verify the secret to the field used to select the target repository, so a payload can validly authenticate as "organization A" while acting on "organization B's" repository.

### Finding Description [1](#0-0) 
`verify_signature` calls `Shipit.github(organization: repository_owner)` and verifies `X-Hub-Signature` against that org's `webhook_secret`. [2](#0-1) 
`repository_owner` is read straight out of the JSON body being verified: `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`. [3](#0-2) 
Every handler resolves the affected stacks/repository via `repository_name = payload.dig('repository', 'full_name')` — a sibling but independent field of the same payload.

Shipit supports multi-organization deployments where each configured organization has its own `webhook_secret` (see `config/secrets.development.example.yml` and `docs/setup.md`, "Use this configuration schema if you are configuring multiple Github applications for different Github organizations"). In that configuration, an attacker who legitimately administers **one** configured organization ("attacker-org", knows its `webhook_secret`) can POST directly to `/webhooks` with a crafted JSON body where:
- `repository.owner.login` = `"attacker-org"` (so `Shipit.github(organization: ...)` resolves attacker-org's config and the HMAC check succeeds, since the attacker computes the signature themselves using their own known secret over their own crafted body), and
- `repository.full_name` = `"victim-org/victim-repo"` (an unrelated organization/repository also configured in the same Shipit instance).

The signature check equality that should hold is: `organization authenticated by webhook_secret == organization whose repository is mutated by the handler`. This binding is broken because `verify_signature` authenticates the payload against the org named in the (attacker-controlled) `repository_owner` field, while `Handler#repository_name`/`stacks` act on the independently attacker-controlled `repository.full_name` field, with no cross-validation between the two.

### Impact Explanation
This lets an attacker who controls only their own (unprivileged, relative to the victim) organization's webhook credentials forge GitHub events against a victim organization's stacks in the same Shipit instance:
- `PushHandler` (`app/models/shipit/webhooks/handlers/push_handler.rb:12-17`) invokes `stack.sync_github(expected_head_sha: params.after)` for any matching branch/stack under the spoofed `full_name`, forcing a sync to an attacker-chosen head sha.
- `StatusHandler` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`) calls `commit.create_status_from_github!(params)` for any `Commit` matching the attacker-supplied `sha`, letting the attacker inject a fabricated "success" CI status on a specific commit in the victim repo — potentially unblocking a merge/deploy gated on that status, i.e., an unauthorized deploy.
- Other handlers (`check_suite`, `pull_request/*`, `membership`) are reachable the same way against the victim's data.

This crosses an organizational/repository trust boundary (cross-repository writes / potential unauthorized deploy) using only credentials the attacker legitimately possesses for their own, unrelated organization — matching the "Critical" impact bar (cross-repository writes / unauthorized deploy).

### Likelihood Explanation
Requires: (1) the Shipit deployment configured with multiple GitHub organizations (documented, supported configuration), and (2) the attacker being a legitimate administrator/webhook-secret holder for at least one of those configured organizations, but with no privileges on the victim organization. Given multi-tenant Shipit deployments are an explicitly documented use case, this is a realistic configuration, not a hypothetical one.

### Recommendation
In `WebhooksController`, after determining `repository_owner` for secret selection, verify that it is consistent with the owner segment of `repository.full_name` (and/or `organization.login`) before dispatching to handlers — reject the request if they disagree. Alternatively, bind handlers strictly to the same `repository_owner` value that was authenticated, rather than re-deriving `repository_name` independently from the body in `Handler#repository_name`.

### Proof of Concept
1. Configure Shipit with two organizations, each with its own `webhook_secret`, e.g.:
```yaml
github:
  attacker-org:
    webhook_secret: "attacker-known-secret"
  victim-org:
    webhook_secret: "victim-secret-not-known-to-attacker"
```
2. Attacker crafts a `status` (or `push`) webhook JSON body:
```json
{
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" },
  "sha": "<victim commit sha>",
  "state": "success",
  "context": "ci/required-check"
}
```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(body, "attacker-known-secret")>` themselves (they know their own org's secret) and sets `X-Github-Event: status`.
4. `WebhooksController#verify_signature` resolves `repository_owner` = `"attacker-org"` from the body, fetches `attacker-org`'s config, and successfully verifies the signature (`app/controllers/shipit/webhooks_controller.rb:24-30`).
5. `Shipit::Webhooks.for_event('status')` dispatches to `StatusHandler`, which resolves the target `Commit` purely from `params.sha` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`), unrelated to the `attacker-org` used for authentication, and creates a forged "success" status on the victim's commit.
