## Finding Confirmed

I traced this fork's custom encrypted-transaction feature and found that the signature scheme does not bind to the actual encrypted payload contents, allowing pre-decryption substitution of the ciphertext/claims without invalidating the sender's (or fee-payer's/secondary signers') signature.

### Title
Signature does not bind to encrypted payload contents, allowing ciphertext/claim substitution before decryption - (File: `types/src/transaction/mod.rs`, `types/src/transaction/authenticator.rs`, `types/src/transaction/encrypted_payload.rs`)

### Summary
For the `TransactionPayload::EncryptedPayload` variant, signing and signature verification are computed over `as_encrypted_variant()`, which replaces the real payload with a bare `TransactionExecutable::Encrypted` placeholder before hashing/signing [1](#0-0) . Neither the ciphertext, `payload_hash`, `encryption_epoch`, `claimed_entry_fun`, nor `TransactionExtraConfig` (which carries `multisig_address` and `replay_protection_nonce`) are part of what the sender/fee-payer/secondary signers actually sign. `TransactionAuthenticator::verify` explicitly converts back to this placeholder form before checking signatures [2](#0-1) .

### Finding Description
The only integrity check tying the ciphertext to a specific decrypted result is `EncryptedPayload::try_into_decrypted`, which checks `payload_hash == CryptoHash::hash(&plaintext)` and, if present, `claimed_entry_fun` [3](#0-2) . Since `payload_hash`, `claimed_entry_fun`, `extra_config`, and the ciphertext itself are outside the signed message, an attacker who intercepts a signed-but-still-encrypted transaction (state `EncryptedPayload::Encrypted`) can replace the ciphertext, `payload_hash`, `encryption_epoch`, and `extra_config` (including `multisig_address` / `replay_protection_nonce`) with values of their choosing, re-serialize, and the transaction's Ed25519/multi-agent/fee-payer signature will still verify, because verification only reconstructs the fixed `Encrypted` placeholder for the message that was actually signed.

This is directly confirmed by the repository's own test suite: `simulate_decryption` mutates a signed transaction's `ciphertext`, `extra_config`, `payload_hash`, and `encryption_epoch` to entirely different values (post-signing) and `signed_txn.verify_signature()` still succeeds — for the plain Ed25519, fee-payer, multi-agent, and single-sender authenticator paths alike [4](#0-3) . The test comment even states the reason: "Signature should still verify because `as_encrypted_variant()` converts back."

### Impact Explanation
This breaks the transaction-admission invariant that a signature must bind to the exact content that will be executed under the sender's/fee-payer's authority. Because `extra_config.multisig_address` and `replay_protection_nonce`, along with the ciphertext and its claimed target module/function, are unsigned, a network participant that observes an encrypted transaction before its ciphertext is consumed by consensus decryption can rebind it to:
- a different `multisig_address` (redirecting execution to a different multisig account than the signer intended), or
- a different `replay_protection_nonce` (affecting replay-protection binding for orderless/nonce-based transactions), or
- an entirely different ciphertext/`payload_hash` (since `try_into_decrypted`'s hash check only validates internal consistency of the substituted ciphertext against its own substituted `payload_hash`, not against what the signer originally committed to).

The sender/fee-payer's cryptographic authorization is therefore decoupled from the actual instructions being admitted and executed, satisfying the "Pre-validation mismatch that causes a transaction which should fail admission to execute and commit" and "Authenticator ... accepting the wrong signing material" impact categories.

### Likelihood Explanation
The vulnerability requires only network-level or mempool-level access to an encrypted, not-yet-decrypted transaction (no privileged role, no leaked keys) — any relayer, validator, or observer with visibility into transactions prior to the consensus decryption step (`consensus/src/pipeline/decryption_pipeline_builder.rs`) can perform the substitution. The repo's own regression tests independently demonstrate the exact primitive (signature validity survives ciphertext/hash/config mutation), so this is not speculative.

### Recommendation
Include a binding commitment to the actual encrypted payload contents (ciphertext, `payload_hash`, `encryption_epoch`, `claimed_entry_fun`, and `TransactionExtraConfig`) inside the data that is actually signed — e.g., by hashing these fields into the `TransactionExecutable::Encrypted` variant used during signing (instead of using a content-free placeholder), so that `as_encrypted_variant()` cannot silently discard attacker-controllable fields. Add an explicit test that signs an encrypted payload, mutates the ciphertext/hash/extra_config, and asserts signature verification **fails**.

### Proof of Concept
The existing test `verify_ed25519_encrypted_payload_after_decryption` (and its fee-payer/multi-agent/single-sender variants) is itself the proof of concept: it signs a `RawTransaction` containing `TransactionPayload::EncryptedPayload(EncryptedPayload::Encrypted(..))`, verifies the signature, then calls `simulate_decryption` to replace the `ciphertext`, `extra_config`, `payload_hash`, and `encryption_epoch` with unrelated freshly-generated values, and shows `signed_txn.verify_signature()` still succeeds [5](#0-4) . Substituting these fields is equivalent to an attacker swapping in an entirely different encrypted instruction set/target/multisig account after the sender signed, without needing the sender's private key.

    /// from Encrypted to Decrypted.
    fn simulate_decryption(
        signed_txn: &mut SignedTransaction,
        ciphertext: Ciphertext,
        extra_config: TransactionExtraConfig,
        payload_hash: HashValue,
        encryption_epoch: u64,
    ) {

                    encryption_epoch,
                    claimed_entry_fun: None,
                },
                eval_proof: EvalProof::random(),
                decrypted: DecryptedPlaintext::new(TransactionExecutable::Empty, [42; 16]),
            });
    }

    /// Verify the decrypted plaintext against the stored commitments and, on success,
    /// transition `self` to `Decrypted`. On mismatch, `self` is left as `Encrypted` and the
    /// failure reason is returned so the caller can mark the payload failed.
    pub fn try_into_decrypted(
        &mut self,
        eval_proof: EvalProof,
        plaintext: DecryptedPlaintext,
    ) -> Result<(), DecryptionFailureReason> {
        let Self::Encrypted(original) = self else {
            panic!("try_into_decrypted called on non-Encrypted state");
        };

        if original.payload_hash != CryptoHash::hash(&plaintext) {
            return Err(DecryptionFailureReason::PayloadHashMismatch);
        }

        if let Some(claim) = &original.claimed_entry_fun {
            let TransactionExecutable::EntryFunction(entry_fun) = plaintext.executable() else {
                return Err(DecryptionFailureReason::ClaimedEntryFunctionMismatch);
            };
            if *entry_fun.module() != claim.module {
                return Err(DecryptionFailureReason::ClaimedEntryFunctionMismatch);
            }
            if let Some(claimed_function_id) = &claim.function
                && entry_fun.function() != claimed_function_id.as_ident_str()
            {
                return Err(DecryptionFailureReason::ClaimedEntryFunctionMismatch);
            }
        }
