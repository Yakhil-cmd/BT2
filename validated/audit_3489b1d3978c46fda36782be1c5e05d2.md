## Finding: AA-level `is_valid_signed_package` / `is_valid_sig` primitives verify signatures but provide no built-in replay/consumption protection

### Title
Off-chain signed authorizations validated by `is_valid_signed_package`/`is_valid_sig` in AA oscript are not bound to any nonce or consumption mechanism, enabling signature replay - (File: `formula/evaluation.js`, `signed_message.js`, `object_hash.js`)

### Summary
Obyte's AA (Autonomous Agent) formula language exposes `is_valid_signed_package()` and `is_valid_sig()` as building blocks that let an AA accept an off-chain, ECDSA-signed message as authorization for an on-chain action (payment, entitlement, session-style delegation), exactly the same pattern as the `ResourceLockValidator.validateUserOp()` bug in the external report. Just like that module, these ocore primitives verify only that *a* valid signature exists over the supplied data — they never check or record whether this exact signed payload was already consumed. Any AA that uses this primitive as its sole authorization gate (a usage pattern the codebase itself demonstrates and encourages) is exploitable by replaying the identical signed package in a new trigger unit.

### Finding Description
`is_valid_signed_package` is handled in the formula evaluator: [1](#0-0) 

It calls `signed_message.validateSignedMessage()`, which validates structure, checks `last_ball_unit` stability, and then verifies the ECDSA signature via `Definition.validateAuthentifiers()` using a hash computed purely from the fields the caller chose to include: [2](#0-1) 

The hash-to-sign itself, `getSignedPackageHashToSign()`, is derived only from the `signed_message`/`authors`/`last_ball_unit`/`version` fields explicitly placed in the package — nothing forces uniqueness, a nonce, or a binding to a specific AA address, trigger unit, or execution: [3](#0-2) 

`is_valid_sig()` is even more minimal — it verifies a raw signature over an arbitrary message/PEM key with no state tracking at all: [4](#0-3) 

Crucially, unlike a normal DAG unit signature (which is inherently single-use because the unit itself, once posted, can never be reposted — the DAG naturally prevents unit replay), a `signed_message`/PEM-signed payload embedded inside `trigger.data` has no such natural uniqueness. Once an AA trigger unit containing a `signed_package` is posted (which it must be, publicly, to invoke the AA), any unprivileged party can read that public data and re-submit the identical `trigger.data.signed_package` in a brand-new trigger unit. `is_valid_signed_package`/`is_valid_sig` will validate it as "true" again, because ocore performs no consumption bookkeping of previously-seen signed messages — this bookkeeping, if desired, is entirely left to the AA author to implement manually via state vars keyed on a hash of the signed message.

This mirrors the report's root cause precisely: `ResourceLockValidator.validateUserOp()` checked the Merkle proof and ECDSA signature over the `ResourceLock`/`callData` but never marked that authorization as spent, so the attacker replayed the same signature with a fresh EntryPoint nonce. Here, `is_valid_signed_package`/`is_valid_sig` checks the signature over arbitrary attacker-supplied data but never marks that signed data as spent, so it can be replayed inside a fresh trigger unit (which plays the same role as the fresh EntryPoint nonce in the original bug — a new, valid "envelope" carrying the stale authorization).

The test suite and documentation demonstrate this pattern is the intended, encouraged use of the primitive (e.g., signing arbitrary application-level messages like orders): [5](#0-4) 

### Impact Explanation
Any AA that relies on `is_valid_signed_package`/`is_valid_sig` as the authorization check for a stateful, value-affecting action (fund release, discount/whitelist grant, delegated/session-key-style spending — the same category of use case as `ResourceLockValidator`) is exposed to unlimited replay of a single off-chain authorization by any unprivileged AA trigger sender, once that authorization has appeared in any public unit. This can cause repeated unauthorized payouts from the AA's balance (AA fund loss/drain) or repeated redemption of a one-time entitlement, unless the AA author independently reimplements nonce/consumption tracking in oscript state vars — protection that ocore's own primitive does not provide or enforce, and does not warn about at the framework level.

### Likelihood Explanation
High for AAs that adopt this documented, natural-looking primitive for meta-transaction/session-key/delegated-authorization patterns without separately hand-rolling a nonce-consumption check in their own oscript state (`var[...]`). The attack requires no privileged access: any address able to observe a previously posted trigger unit (which is inherently public on the DAG) and post a new trigger unit can replay it.

### Recommendation
- Document explicitly, next to `is_valid_signed_package`/`is_valid_sig`, that these functions provide signature validity only and **not** replay protection, and that AA authors must independently record consumption (e.g., `var[hash(signed_message)] = true` and reject if already set).
- Consider offering a built-in helper/pattern in the formula language for "single-use signed package" semantics (e.g., an opcode that atomically checks-and-marks a signed package/nonce as consumed in AA state), analogous to how `spend_proofs` provides built-in double-spend protection for asset transfers elsewhere in ocore.
- Audit existing/community AAs that use `is_valid_signed_package`/`is_valid_sig` for authorization to confirm they implement their own nonce tracking.

### Proof of Concept
1. Alice signs an off-chain message authorizing a payout, e.g. `{signed_message: {action:"withdraw", amount:100}, authors:[{address: Alice, definition:["sig",{pubkey}], authentifiers:{r: sig}}]}`, intended to let an AA `AA1` release 100 bytes to Alice once.
2. Alice's wallet posts a trigger unit `U1` to `AA1` with `trigger.data.signed_package` set to this package. `AA1`'s oscript checks `is_valid_signed_package(trigger.data.signed_package, Alice)` and, on success, pays out 100 bytes — but does not store a hash of the consumed package in state vars.
3. Any observer (including Alice herself, or any unprivileged third party who can read `U1` from the public DAG) copies the exact `signed_package` object from `U1` into a brand-new trigger unit `U2` sent to `AA1`.
4. `is_valid_signed_package` in `formula/evaluation.js` (lines 1653–1701) re-validates it successfully via `signed_message.validateSignedMessage` (`signed_message.js` lines 255–289), because nothing checks whether this package was already used — `AA1` pays out another 100 bytes.
5. Steps 3–4 can be repeated indefinitely, draining `AA1`'s balance, exactly analogous to resubmitting the same `callData`/signature with a new EntryPoint nonce in the original `ResourceLockValidator` report.

function getSignedPackageHashToSign(signedPackage) {
	var unsignedPackage = _.cloneDeep(signedPackage);
	for (var i=0; i<unsignedPackage.authors.length; i++)
		delete unsignedPackage.authors[i].authentifiers;
	var sourceString = (typeof signedPackage.version === 'undefined' || signedPackage.version === constants.versionWithoutTimestamp) ? getSourceString(unsignedPackage) : getJsonSourceString(unsignedPackage);
	return crypto.createHash("sha256").update(sourceString, "utf8").digest();
}
