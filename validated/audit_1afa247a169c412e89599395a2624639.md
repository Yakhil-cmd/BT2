### Title
Permissionless accrual panics on the RAY value ceiling and permanently freezes a market — withdrawals, repayments, and liquidations all revert — ([File: contracts/pool/src/cache/scale.rs])

### Summary
The kernel bug is a defensive assertion (`WARN_ON_ONCE`) reachable from unprivileged userspace: an attacker can trip a "should not happen" check that turns into a system-wide denial of service under `panic_on_warn`. The analog in XOXNO Lending is the defensive checked-math panic inside pool accrual: a market's RAY-scaled debt value can be driven past the `i128` ceiling, after which the checked multiply inside `scaled_to_original` panics on every subsequent accrual. Because every state-changing verb accrues first, the panic — triggered by the permissionless `update_indexes` entrypoint — permanently freezes the market.

### Finding Description
Interest accrual in the pool converts scaled borrow shares to original amounts via `scaled_to_original` in `common/src/rates/scaling.rs` (used by `contracts/pool/src/cache/scale.rs`), which performs checked multiplication and panics with `GenericError::MathOverflow` on overflow (same pattern as `credit_cash`/`debit_cash` in `contracts/pool/src/cache/cash.rs:24-41` and `now_ms` in `contracts/pool/src/time.rs:15-19`). A documented bounds gap exists: the `MAX_BORROW_INDEX_RAY` cap is meant to bound index growth, but the ceiling on the *value* — `scaled_amount * borrow_index` — is higher and is hit first.

The integration test `tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:316-361` demonstrates the full path:

- A whale supplies ~1e9·10^18 units of an 18-decimal market on the XLM rate curve and a borrower takes ~98% utilization.
- `borrow_index` compounds past ~170x before the index cap engages.
- The next `update_indexes` call panics inside `scaled_to_original` with `MATH_OVERFLOW`; the test asserts `last.borrow_index < MAX_BORROW_INDEX_RAY` — the index cap never fires.
- The same test asserts `try_withdraw_raw` and `try_repay` both revert with `MATH_OVERFLOW`, and notes liquidation accrues first and hits the same panic.

`update_indexes` is a permissionless controller entrypoint, so once the market state reaches the ceiling any unprivileged address triggers the panic, and — critically — there is no way to unwind it: accrual runs before every operation, so repay, withdraw, liquidate, clean_bad_debt, and recapitalize all revert on the same overflow. The defensive check is reachable from userspace exactly like the cgroup `WARN_ON_ONCE`: a limit the code assumed unreachable is reachable, and tripping it is fatal rather than recoverable.

### Impact Explanation
Permanent freezing of funds for every supplier and borrower in the affected market. Suppliers cannot withdraw (`withdraw` accrues first), borrowers cannot repay, liquidators cannot close positions, and bad-debt cleanup/recapitalization also revert because they route through `ops::renewed_market` accrual (`contracts/pool/src/ops/recapitalize.rs:50`). All tokens held by the market are bricked indefinitely since no code path can reduce `scaled_amount` or rewind `borrow_index` without first performing the overflowing accrual.

### Likelihood Explanation
Low-to-moderate. It requires a whale-scale market (the test uses ~10^27 raw units) sustained near maximum utilization on a steep rate curve for decades of ledger time — an attacker cannot compress Soroban ledger time, and the principal is economically significant. However, no privileged action is needed to trigger the freeze once conditions exist (`update_indexes` is unprivileged), the conditions arise organically in a large high-utilization market rather than requiring an attack, and the characterization test explicitly shows the documented safety bound in `docs/reference/formulas.md` is wrong — the value ceiling is reached before the intended index cap. Severity: Medium, consistent with the source report.

### Recommendation
Bound the product, not just the index. Options:

- Enforce a cap on `scaled_amount * borrow_index` (or the original-units debt total) inside accrual, clamping like `MAX_BORROW_INDEX_RAY` does, instead of letting `scaled_to_original` overflow.
- Make accrual saturate at the cap rather than panic, so `update_indexes`, `repay`, `withdraw`, and `liquidate` remain executable at the ceiling.
- Alternatively, allow repay/withdraw to settle against the last committed index without re-accruing when accrual itself overflows, so users retain an exit path.

### Proof of Concept
The existing harness test is the PoC (`tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:316-361`):

```rust
t.supply_raw(BOB, "BIG18", BILLION * 10i128.pow(18));
t.borrow_raw(ALICE, "BIG18", principal / 100 * 98); // ~98% utilization

loop {
    t.advance_time(YEAR_SECS);
    if let Err(e) = t.try_update_indexes_for(&["BIG18"]) { break e; } // MATH_OVERFLOW
}

// Market permanently frozen:
assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
assert!(book(&t, "BIG18").borrow_index < MAX_BORROW_INDEX_RAY); // cap never engaged
```

An unprivileged attacker path: supply and borrow (or rely on an existing large high-utilization market), let interest accrue, then call the permissionless `controller.update_indexes` — the panic is reproducible on every subsequent call by anyone, permanently.
