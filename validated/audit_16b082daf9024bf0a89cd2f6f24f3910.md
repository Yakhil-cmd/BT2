### Title
Cross-organization commit status forgery via unscoped `sha` lookup in webhook `status` handler - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`Shipit::Webhooks::Handlers::StatusHandler` updates commit CI status by looking up commits **globally by `sha`**, without any check that the commit belongs to the repository/organization whose GitHub App installation actually signed the incoming webhook. This breaks the binding "organization that authenticated" == "repository that is written", allowing an attacker who controls any org where Shipit's GitHub App is installed to forge a passing CI status on a commit belonging to a completely different, unrelated stack/repository, as long as the SHA values collide (trivially achievable by forking the target repository).

### Finding Description
`WebhooksController#verify_signature` selects the GitHub App configuration to validate the HMAC signature based on `repository_owner`, derived from the webhook payload itself (`params.dig('repository','owner','login')`) [1](#0-0) . This only proves that *some* organization with a configured webhook secret sent the request — it does not, by itself, constrain which repository/commit records the payload is allowed to mutate.

`Shipit::Webhooks::Handlers::Handler` provides a `stacks` helper that correctly scopes lookups to the repository named in the payload: [2](#0-1) 
`PushHandler` uses this scoping (`stacks.not_archived.where(branch:)`) [3](#0-2) .

However, `StatusHandler` does not use this scoping mechanism at all. It queries `Commit` globally by `sha` across the entire installation and applies the incoming status to every match: [4](#0-3) 
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```

Because a Git commit SHA is a content-addressed hash of its tree, parents, author, message and timestamps, forking a target public repository into an attacker-controlled organization (with Shipit's GitHub App installed there, as is normal/expected for any org onboarded to Shipit — see the multi-org fixture at `test/dummy/config/secrets_double_github_app.yml`) reproduces byte-identical SHAs for shared commits. The attacker can then push a legitimate, signature-valid `status` webhook from their own org that references one of these shared SHAs, and `StatusHandler` will happily attach that status to the commit record belonging to the victim's stack — even though the victim's repository/organization never sent that webhook.

### Impact Explanation
Commit statuses gate deploy safety in Shipit (`ci.require`), and continuous deployment / merge-queue behavior consult these statuses to decide whether a commit is safe to ship. A forged "success" status injected via a cross-organization sha collision can satisfy `ci.require` checks it never actually passed, resulting in an **unauthorized deploy** of a commit whose real CI never validated it. This matches the Critical impact bucket ("an unauthorized deploy, rollback or merge").

### Likelihood Explanation
Exploitation requires no session, ApiClient token, webhook secret theft, or GitHub App private key — only that the attacker controls (or forks into) an organization where Shipit's GitHub App is installed with its own legitimately-issued webhook secret, which is the normal onboarding path for any Shipit customer/org. Producing a matching SHA is deterministic for any commit the attacker can reproduce by forking the target repository, making this practically exploitable rather than merely theoretical.

### Recommendation
Scope `StatusHandler#process` (and any other handler resolving records purely by SHA) through the same repository-derived `stacks`/`Repository.from_github_repo_name(repository_name)` mechanism used by `PushHandler`, so that a status update can only be applied to commits belonging to the repository named in — and cryptographically bound to — the verified webhook payload, e.g.:
```ruby
def process
  stacks.flat_map(&:commits).select { |c| c.sha == params.sha }.each do |commit|
    commit.create_status_from_github!(params)
  end
end
```

### Proof of Concept
1. Fork the victim's public repository (`victim-org/app`) into an attacker-controlled organization (`attacker-org/app-fork`) so that at least one commit SHA is shared between both histories.
2. Install/configure Shipit's GitHub App on `attacker-org` (normal onboarding, no privileged access to `victim-org` needed) and note its legitimately issued webhook secret.
3. Send a `status` event to `/webhooks` signed with `attacker-org`'s webhook secret:
   ```json
   {
     "sha": "<shared-sha>",
     "state": "success",
     "context": "ci/required-check",
     "repository": { "owner": { "login": "attacker-org" }, "full_name": "attacker-org/app-fork" }
   }
   ```
4. `WebhooksController#verify_signature` validates successfully (correct secret for `attacker-org`).
5. `StatusHandler#process` runs `Commit.where(sha: "<shared-sha>")`, matches the commit belonging to `victim-org/app`'s stack, and creates a forged "success" status for it, satisfying `ci.require` on a stack the attacker has no relationship to.
