### Title
Borrow-index accrual overflows before its cap and permanently freezes an entire market - ([File: common/src/rates/simulate.rs](common/src/rates/simulate.rs))

### Summary
`accrue_step` converts the stored scaled debt to its current original value before the borrow-index ceiling can stabilize the market. On a sufficiently large, highly utilized market, time-driven index growth eventually makes `borrowed * borrow_index` exceed `i128::MAX`. The resulting `GenericError::MathOverflow` aborts every accrual-dependent operation, including repayment, withdrawal, liquidation, and `update_indexes`, permanently freezing funds in that market.

### Finding Description
Every pool accrual starts by computing:

- `borrowed_original = scaled_to_original(env, borrowed, borrow_index)` in `common/src/rates/simulate.rs:60`
- `scaled_to_original` evaluates `scaled.mul(env, index)` in `common/src/rates/scaling.rs:14-16`
- `Ray::mul` calls `mul_div_half_up` in `common/src/math/fp.rs:50-52`
- `mul_div_half_up` panics with `MathOverflow` when the exact quotient does not fit `i128` in `common/src/math/fp_core.rs:108-118`

The borrow index itself is intended to be bounded by `MAX_BORROW_INDEX_RAY` in `common/src/rates/index.rs:13-18`, but that clamp is applied only after the vulnerable value conversion has already occurred. An attacker who creates a sufficiently large supply/borrow position through normal `supply` and `borrow` operations can therefore push the market into a state where ordinary ledger time advances the index until `borrowed * borrow_index / RAY` exceeds `i128::MAX`, even though `borrow_index` remains below its configured cap.

This is analogous to the upstream parsing flaw because a valid attacker-established state reaches a fatal arithmetic path rather than a recoverable domain-specific result. The existing harness test `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` demonstrates the exact sequence: supply a billion-token 18-decimal market, borrow 98%, advance time until `update_indexes` returns `MathOverflow`, then observe that both `withdraw` and `repay` fail with the same error (`tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:316-356`).

### Impact Explanation
Permanent freezing of user funds and market insolvency handling:

- Suppliers cannot withdraw because `withdraw` accrues first.
- Borrowers cannot repay because `repay` accrues first.
- Liquidators cannot close unhealthy positions because liquidation also needs current indexes.
- Anyone calling `update_indexes` receives the same `MathOverflow`.
- Bad-debt cleanup and later market operations cannot recover the market because they also depend on the failed accrual path.

The affected market becomes unable to operate while user deposits and debt remain recorded.

### Likelihood Explanation
Medium. The trigger does not require privileged calls, malformed transaction data, leaked keys, oracle manipulation, or contract internals. It requires an unprivileged account able to supply and borrow a very large amount of a high-decimal asset, then sustain high utilization long enough for index growth to cross the value-overflow boundary. The harness proves the state is reachable through normal `supply` and `borrow` calls, although the required capital scale and elapsed period reduce practical likelihood.

### Recommendation
Do not unconditionally multiply `borrowed` by the old borrow index before applying the borrow-index cap. Make the accrual ordering overflow-aware:

- Check whether `interest_factor` advances `borrow_index` beyond `MAX_BORROW_INDEX_RAY` and clamp it before unscaling debt.
- At the cap, treat indexed debt as capped state rather than evaluating the overflowing full-value product.
- Alternatively, use saturating or widened-value accounting for `borrowed_original` and `supplied_original` during utilization/rate calculations, while keeping actual settlement amounts checked.
- Add regression coverage asserting `update_indexes`, `withdraw`, `repay`, and liquidation remain callable when index growth reaches `MAX_BORROW_INDEX_RAY` on a whale-scale market.

### Proof of Concept
The repository’s existing integration test provides the PoC:

```rust
let mut t = LendingTest::new()
    .with_market(big("BIG18", 18, xlm_curve()))
    .with_market(col())
    .with_max_utilization_disabled_all_markets()
    .build();

lift_caps(&t, "BIG18", 18);
lift_caps(&t, "COL", 7);

let principal = BILLION * 10i128.pow(18);
t.supply_raw(BOB, "BIG18", principal);

let debt = principal / 100 * 98;
t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
t.borrow_raw(ALICE, "BIG18", debt);

loop {
    t.advance_time(YEAR_SECS);
    if let Err(e) = t.try_update_indexes_for(&["BIG18"]) {
        assert_contract_error(Err(e), errors::MATH_OVERFLOW);
        break;
    }
}

assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
```

This corresponds to `tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:321-356`. The test also verifies that `borrow_index < MAX_BORROW_INDEX_RAY` when the failure occurs, proving the overflow happens before the configured index ceiling can prevent the freeze.
