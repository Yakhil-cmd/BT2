### Title
Stale `["seen definition change", [address, definition_chash]]` condition never expires, letting a superseded key set permanently satisfy address/asset spend conditions - (File: definition.js)

### Summary
The C4 MIMO finding shows that when an authorization system tracks "ownership" as a historical fact instead of the *current* state, a party that is no longer the true owner can keep unauthorized access, and a new owner can silently lose it. `ocore`'s definition-evaluation opcode `seen definition change` has the same structural flaw: it queries whether an address *ever* changed its definition to a given `definition_chash`, without checking whether that `definition_chash` is the address's *current* (most recent) definition.

### Finding Description
`evaluate()` in `definition.js` implements the `seen definition change` operator by querying `address_definition_changes` for any historical row matching `address` and `definition_chash`, stable and good, before `last_ball_mci` — with no requirement that this be the *latest* change for that address: [1](#0-0) 

Compare this with the correctly "current-state-aware" `attested` opcode, which explicitly restricts attestations to those posted *after* the address's most recent definition change (`main_chain_index > IFNULL(last address_definition_changes.main_chain_index, 0)`) via `storage.filterAttestedAddresses`: [2](#0-1) 

No equivalent recency filter exists for `seen definition change`. Consequently, once an address `A` at any point in its history executes `address_definition_change` to `definition_chash` `D`, any oscript/asset condition of the form `["seen definition change", ["A", "D"]]` will evaluate to `true` forever after — even if `A` subsequently changes its definition again to `E`, `F`, etc., completely revoking `D`'s signers from any control over `A`. The message type and its acceptance are defined here: [3](#0-2) 
and written permanently to `address_definition_changes`: [4](#0-3) 

This mirrors the MIMO bug precisely: the authoritative "current owner" of address `A` is whatever definition is active now (tracked correctly by `readDefinitionChashByAddress`/`readDefinitionByAddress`), but `seen definition change` gives any *former* definition holder a permanent, un-revocable backdoor if it is referenced in a spend/authorization condition — exactly like the stale `owner` variable in MIMOProxy that never got cleared when Registry (the real ownership source) moved on.

### Impact Explanation
This op can be embedded directly in:
- an address definition (multisig/AND/OR conditions used to authorize spending funds from a normal or shared address), or
- an asset's `issue_condition` / `transfer_condition` (validated via `Definition.evaluateAssetCondition` in `validatePaymentInputsAndOutputs`): [5](#0-4) 

A realistic pattern is a "recovery" or "backup key" clause: `["or", [["sig", {pubkey: current}], ["seen definition change", ["this address", RECOVERY_CHASH]]]]`. If the address owner ever transitioned through `RECOVERY_CHASH` (e.g., during a legitimate key rotation, a compromise-triggered recovery that was later reverted, or simply an intermediate step in a multi-stage rotation) and later moves to a completely different, uncompromised definition, the old `RECOVERY_CHASH` signers can still satisfy the OR-branch and spend funds — unauthorized spending that the current, legitimate definition never sanctioned. Since any single unposted unit or asset condition author fully controls the content of their own address definition or asset condition, this is directly reachable by an unprivileged address/asset definer and results in concrete unauthorized spending of funds that the network will validate as fully "good" (all nodes evaluate the same historical fact and agree it's true), so there's no fork/disagreement risk — just silent loss of funds for whoever relied on this op believing it reflected current control.

### Likelihood Explanation
Any wallet, dApp, or AA author who uses `seen definition change` to build a "was recovery/rotation performed" clause in a spend condition is exposed. Given that this is a documented public oscript primitive (used for definition-change-triggered spend logic, e.g., time-locked recovery flows), and that key rotation for legitimate reasons is a normal, expected user action, the likelihood of a real address unintentionally satisfying this stale condition — or an attacker deliberately engineering a throwaway definition-change to "unlock" the clause forever — is realistic rather than hypothetical.

### Recommendation
Restrict `seen definition change` evaluation to only match if the referenced `definition_chash` is (or was) active during a contiguous window ending at the current definition, or — simplest and most robust — require that the matched `address_definition_changes` row be the **most recent** stable/good change for that address at or before `last_ball_mci` (i.e., add `AND NOT EXISTS (SELECT 1 FROM address_definition_changes adc2 JOIN units u2 USING(unit) WHERE adc2.address=address_definition_changes.address AND u2.main_chain_index>address_definition_changes... AND u2.main_chain_index<=? AND u2.is_stable=1 AND u2.sequence='good')`), mirroring the recency check already used for `attested`/`filterAttestedAddresses`. Document clearly that `seen definition change` reflects only the *current* definition state, not full history, or introduce a separate, explicitly historical opcode name if backward compatibility with existing "seen" semantics is required (with a protocol upgrade guarded by `last_ball_mci` similar to `anyDefinitionChangeUpgradeMci`).

### Proof of Concept
1. Address `A` is defined with:
   `["or", [ ["sig", {pubkey: pub_current}], ["seen definition change", ["this address", chash_of_R]] ]]`
   where `R = ["sig", {pubkey: pub_recovery}]`.
2. Owner legitimately rotates `A`'s definition to `R` via `address_definition_change` (composed via `composeDefinitionChangeJoint` in `composer.js`, lines 85-87) for some operational reason, then rotates again to a brand-new, uncompromised definition `S` (unrelated to `R`).
3. Because `address_definition_changes` now contains a stable, good row `(address=A, definition_chash=chash_of_R)`, any future unit spending from `A` and satisfying `["seen definition change", ["A", chash_of_R]]` in `evaluate()` (`definition.js` lines 835-853) will pass validation in `validateAuthentifiers`, regardless of the fact that `A`'s active definition is now `S`.
4. Holder of the old `pub_recovery` key (or anyone who colludes to include such a clause when defining the address) can post a payment from `A` signed only with `pub_recovery`, and it will validate as fully "good" everywhere, resulting in unauthorized spend of `A`'s balance.
