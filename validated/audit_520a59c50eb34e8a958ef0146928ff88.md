### Title
Ambiguous `trigger.address` vs `trigger.initial_address` terminology in AA oscript enables owner-check bypass in chained AA calls - (File: aa_composer.js, formula/evaluation.js)

### Summary
Autonomous Agents (AAs) in oscript expose two distinct "sender" concepts that are easy to confuse: `trigger.address` and `trigger.initial_address`. `trigger.address` is the immediate caller of the current AA invocation (which can be another AA when the trigger is a secondary/chained trigger), while `trigger.initial_address` is preserved unchanged through the whole chain and always refers to the original human/wallet address that started the transaction. This mirrors the SecuritizeVault report's core issue: two different "owner"/"caller" concepts exist side by side, and if an AA author uses the wrong one for an access-control or ownership check, permissions intended for one entity end up being granted to (or checked against) a different entity.

### Finding Description
`getTrigger()` sets `trigger.address` to `objUnit.authors[0].address` — the immediate sender of the unit that triggered this particular AA invocation. [1](#0-0) 

For a primary trigger, `trigger.initial_address` is set equal to `trigger.address`: [2](#0-1) 

But when an AA forwards funds/messages to another AA (a secondary/chained trigger), `handleSecondaryTriggers` builds a fresh `child_trigger` via `getTrigger(objUnit, row.address)`, so `child_trigger.address` becomes the **sending AA's own address**, not the original human caller — only `initial_address`/`initial_unit` are explicitly propagated forward: [3](#0-2) 

Both values are exposed to oscript formulas as separate, similarly-named primitives (`trigger.address`, `trigger.initial_address`), evaluated independently with no warning that they can diverge: [4](#0-3) 

The distinction is validated/gated identically in the formula validator (both allowed anywhere an AA can use triggers), reinforcing that oscript treats them as two interchangeable-looking "who is calling me" primitives with no syntactic or semantic hint about which one is safe to use for authorization: [5](#0-4) 

An AA author writing an "owner-only" check such as `if (trigger.address != $owner) bounce(...)` is implicitly assuming `trigger.address` always equals the human wallet that initiated the top-level transaction. This assumption silently breaks the moment the AA is called as part of a chain (i.e., when another AA — possibly attacker-controlled or attacker-triggered — forwards a payment to it), because at that point `trigger.address` is the calling AA's address, and only `trigger.initial_address` still reflects the original human caller. Conversely, an author who intends to check "who is currently interacting with me" (which should legitimately change per hop) but mistakenly uses `trigger.initial_address` will authorize based on the wrong, stale address throughout an entire multi-hop chain.

### Impact Explanation
Because ocore explicitly supports and encourages chained/secondary AA triggers (an AA can send a payment to another AA within the same primary trigger, automatically invoking it), any AA whose access-control/ownership logic conflates `trigger.address` with `trigger.initial_address` is exploitable by a malicious or naively-designed intermediary AA in the call chain:
- If an owner check uses `trigger.address` expecting it to be the human owner, an attacker can deploy an intermediary AA that forwards a payment on the owner's behalf (or that itself impersonates the "caller") so that the vulnerable AA's owner check evaluates against the intermediary AA's address instead of the true owner — this can lead to funds being redirected, state variables representing ownership/collateral being overwritten by an unauthorized address, or protected operations (e.g., withdrawals, price/param changes) being executed by an unintended party.
- Conversely, using `trigger.initial_address` where per-hop caller identity is required can cause an AA to authorize actions for the wrong address across a multi-step chain, again enabling unauthorized state changes or fund misdirection.

This directly maps to the report's "AA fund loss or freezing" / unauthorized access-control outcome category, and is reachable purely by a normal AA trigger sender (or trigger-chain author) with no special privilege — matching the report's requirement that only unprivileged reachable paths qualify.

### Likelihood Explanation
AA authors write oscript using natural, English-like syntax (`trigger.address` reads intuitively as "the address that triggered me"), with no compiler warning distinguishing it from `trigger.initial_address`. The official test suite itself demonstrates both fields being used almost interchangeably across chained-AA scenarios (`test/aa_composer.test.js`), confirming that developers must be deeply aware of the chain semantics to choose correctly: [6](#0-5) [7](#0-6) 

Given that AA composability (one AA calling another) is a core, encouraged design pattern in ocore, and that "owner"/"who sent this" checks are extremely common in AA code (e.g., marketplace/registry patterns like `test/samples/things_registry_and_marketplace.oscript` compare `trigger.address` against a stored owner), the likelihood of an AA author picking the wrong primitive — and of that AA later being called through an intermediary — is realistic and not merely hypothetical: [8](#0-7) 

### Recommendation
- Document explicitly, next to both `trigger.address` and `trigger.initial_address` definitions, which one should be used for authorization/ownership checks and which one changes per hop; add this guidance directly to the oscript language reference and to `formula/evaluation.js`/`formula/grammars/oscript.ne` comments.
- Consider introducing clearer, less confusable naming (e.g. `trigger.caller` vs `trigger.original_sender`) or a dedicated getter such as `is_original_caller()` that AA authors can use for ownership checks without needing to reason about chain semantics.
- Add AA validation/linting warnings (in `formula/validation.js`) when `trigger.address` is used in a comparison against a variable/state var that looks like a stored "owner" without corroborating logic, to nudge authors toward the safer `trigger.initial_address` (or vice versa depending on intended semantics), similar to how other risky patterns are already flagged during AA validation.

### Proof of Concept
Given an AA that intends to restrict a sensitive operation to its recorded owner:
```
{
  init: `{
    $owner = var['owner'];
  }`,
  messages: [
    {
      if: `{trigger.address == $owner}`,   // BUG: should arguably use trigger.initial_address
      app: 'state',
      state: `{
        var['owner'] = trigger.data.new_owner;  // sensitive: change ownership
      }`
    }
  ]
}
```
1. The legitimate owner `O` normally calls this AA directly, so `trigger.address == O` and the check passes as intended.
2. An attacker deploys an intermediary AA `M` that, upon receiving any payment, forwards it on to the victim AA together with attacker-controlled `data`. Per `getTrigger`, when `M`'s payment triggers the victim AA as a secondary trigger, `trigger.address` for that invocation is `M`'s own address, not the original caller: [3](#0-2) 
3. If the victim AA's owner address `$owner` was ever set to (or can be tricked into equaling) `M`'s address — for example, because a previous chain of triggers set `var['owner']` using `trigger.address` instead of `trigger.initial_address` when the true owner first interacted via an intermediary — then any subsequent call through `M` will satisfy `trigger.address == $owner`, letting the attacker execute the sensitive branch even though `trigger.initial_address` (the real originating human wallet) differs.
4. This class of confusion is exactly demonstrated by the difference between `who` (set to `trigger.address`) and `initial` (set to `trigger.initial_address`) diverging across a chain in the existing test: [9](#0-8)

function getTrigger(objUnit, receiving_address) {
	var trigger = { address: objUnit.authors[0].address, unit: objUnit.unit, outputs: {} };
	if ("max_aa_responses" in objUnit)
		trigger.max_aa_responses = objUnit.max_aa_responses;
	objUnit.messages.forEach(function (message) {
		if (message.app === 'data' && !trigger.data) // use the first data message, ignore the subsequent ones
			trigger.data = message.payload;
		else if (message.app === 'payment' && message.payload) {
			var payload = message.payload;
			var asset = payload.asset || 'base';
			payload.outputs.forEach(function (output) {
				if (output.address === receiving_address) {
					if (!trigger.outputs[asset])
						trigger.outputs[asset] = 0;
					trigger.outputs[asset] += output.amount; // in case there are several outputs
				}
			});
		}
	});
	if (Object.keys(trigger.outputs).length === 0)
		throw Error("no outputs to " + receiving_address);
	return trigger;
}
