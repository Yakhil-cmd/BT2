### Title
Unbounded Memory Allocation via Oversized `private_payments` Chain Array from a Private-Payment Counterparty - (File: wallet.js)

### Summary
`handlePrivatePaymentChains()` in `wallet.js` accepts a `chains` array from a device-message peer (a private-payment counterparty or paired device) without any bound on the number of chains, the number of elements per chain, or the size of each element's `payload` (inputs/outputs). This is analogous to the Mattermost PSD bug: an attacker-controlled structural size field is used to drive allocation/processing work (repeated `cloneDeep`, `JSON.stringify`, recursive hashing) before any real validation limits the size, leading to memory exhaustion.

### Finding Description
`handlePrivatePaymentChains(ws, body, from_address, callbacks)` [1](#0-0)  only checks that `body.chains` is a non-empty array and that each chain element is a non-empty object with the expected string/array fields present — it never checks:
- the number of chains in `arrChains`,
- the number of elements in each chain `c`,
- the number of `inputs`/`outputs` in each element's `payload`.

Right after this shape-only check, the code computes `objectHash.getBase64Hash(arrChains)` over the *entire* attacker-supplied structure [2](#0-1) , which recursively walks and hashes every field of every element of every chain. It then proceeds to iterate all chains with `async.eachSeries`, calling `network.handleOnlinePrivatePayment()` [3](#0-2) , which in turn calls `JSON.stringify(arrPrivateElements)` per chain to persist it in `unhandled_private_payments` [4](#0-3) .

Additionally, `handleOnlinePrivatePayment` performs no size limit either — it only validates that `arrPrivateElements` is non-empty and that `unit`/`message_index`/`output_index` are well-formed [5](#0-4) . Compare this to the tight, explicit bounds enforced for unit-level payment messages during normal unit validation (`MAX_INPUTS_PER_PAYMENT_MESSAGE`, `MAX_OUTPUTS_PER_PAYMENT_MESSAGE`, `MAX_MESSAGES_PER_UNIT`, `MAX_SPEND_PROOFS_PER_MESSAGE`, etc.) [6](#0-5)  — none of these constants are applied to the private-payment "chains" message type, which arrives via the device-message channel (peer-to-peer or through a hub) rather than as a DAG unit subject to `validation.js`'s object-size/nesting checks (`isTooDeeplyNestedOrHasTooManyNodes`, `objectLength.getTotalPayloadSize`, `MAX_UNIT_LENGTH`) [7](#0-6) .

Because this is device-message content (not a DAG unit), it bypasses `validation.js`'s size gate entirely (`MAX_UNIT_LENGTH`, `isTooDeeplyNestedOrHasTooManyNodes`) that protects ordinary unit posting. An attacker who is a paired device / private-payment counterparty (an "unpaired" role explicitly in-scope: "private-payment counterparty ... paired device") can send a single `private_payments` message with a huge `chains` array, each containing many elements, each with large `inputs`/`outputs` arrays, causing:
- expensive recursive hashing over the whole structure,
- repeated `_.cloneDeep()` allocations while building/saving each chain (`buildPrivateElementsChain`, `validateAndSavePrivatePaymentChain`) [8](#0-7) ,
- large `JSON.stringify` buffers stored per chain,
before any of the individual-chain content validation in `indivisible_asset.js`/`divisible_asset.js` can reject the malformed/oversized structure.

### Impact Explanation
A single malicious message from a paired device or private-payment counterparty can force the receiving wallet/hub-connected node to allocate large amounts of memory (deep clones, JSON serialization, recursive hashing) proportional to attacker-chosen array sizes, with no upstream size cap analogous to `MAX_UNIT_LENGTH`/`MAX_INPUTS_PER_PAYMENT_MESSAGE`. This can exhaust process memory and crash or degrade the victim's wallet/hub process — a denial-of-service condition matching the CVE's bug class (memory exhaustion from unbounded allocation driven by attacker-supplied size fields), reachable by an authenticated (paired) peer without needing operator privileges.

### Likelihood Explanation
Likelihood is moderate-to-high: reaching this code only requires being a paired device or a counterparty who can send a `private_payments` device message (a normal part of the private-asset payment protocol), which matches the in-scope reachable classes ("private-payment counterparty" / "paired device"). No unit needs to be posted to the DAG and no witness/consensus gating applies — the vulnerable code executes on receipt of the message itself.

### Recommendation
Add explicit bounds to `handlePrivatePaymentChains()` and `handleOnlinePrivatePayment()` before any hashing/cloning/stringifying work is performed:
- cap `arrChains.length` (e.g., a small constant),
- cap the number of elements per chain,
- cap `payload.inputs.length` / `payload.outputs.length` per element (reuse `constants.MAX_INPUTS_PER_PAYMENT_MESSAGE` / `MAX_OUTPUTS_PER_PAYMENT_MESSAGE` or a dedicated constant),
- reject the whole message immediately if any bound is exceeded, before calling `objectHash.getBase64Hash(arrChains)` or any `cloneDeep`/`JSON.stringify` on the structure.

### Proof of Concept
1. Pair with (or act as) a legitimate private-payment counterparty device.
2. Send a `private_payments` device message whose `body.chains` is an array containing a very large number of chain arrays, each chain containing an element whose `payload.inputs`/`payload.outputs` arrays each contain tens of thousands of well-formed-looking objects (to pass the shallow `isNonemptyObject`/`isNonemptyArray` checks in the validity predicate at `wallet.js:959-972`).
3. On receipt, `wallet.js`'s `handlePrivatePaymentChains` will call `objectHash.getBase64Hash(arrChains)` over the whole payload and then iterate every chain, calling `JSON.stringify` on each in `network.js`'s `handleOnlinePrivatePayment`/`savePrivatePayment`, causing large heap allocations proportional to the attacker-chosen array sizes, with no size cap enforced anywhere in this path.

Note: I could not directly confirm whether the underlying websocket layer enforces a `maxPayload`/frame-size limit that would cap the overall message size before it reaches `wallet.js` — this would materially affect exploitability and should be verified in a live session (e.g., by inspecting how `ws`/network.js configures the WebSocket server/client). No such constant was found in the indexed portions of `network.js`.

function handleOnlinePrivatePayment(ws, arrPrivateElements, bViaHub, callbacks){
	if (!ValidationUtils.isNonemptyArray(arrPrivateElements))
		return callbacks.ifError("private_payment content must be non-empty array");

		return callbacks.ifError("invalid message_index");
	if (!(ValidationUtils.isNonnegativeInteger(output_index) || output_index === -1))
		return callbacks.ifError("invalid output_index");
