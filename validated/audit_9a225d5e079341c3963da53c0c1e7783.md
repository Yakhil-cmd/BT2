### Title
Webhook authentication silently degrades to "always verified" when `webhook_secret` is unset, allowing unauthenticated forgery of GitHub events - (File: `lib/shipit/github_app.rb`)

### Summary
`GitHubApp#verify_webhook_signature` returns `true` whenever no `webhook_secret` has been configured for the target organization, instead of failing closed. Since `docs/setup.md` explicitly documents `webhook_secret` as **optional**, an installation that follows the documented setup without a secret will accept and process arbitrary, unsigned `POST /webhooks` requests, letting an unprivileged network attacker forge GitHub events (`push`, `status`, `membership`, `check_suite`) processed by `WebhooksController`.

### Finding Description
This is the same bug class as the reported `WarpSync.getFinalizationReward` issue: a value that is only "safe" under an implicit precondition is used without validating that precondition, silently producing an erroneous (here: overly permissive) result. [1](#0-0) 

```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
```

`webhook_secret` is populated straight from `secrets.yml`/credentials, and `docs/setup.md` explicitly labels it `(optional)`: [2](#0-1) 

The precondition the author intended ("we can only cryptographically verify a webhook if a secret is configured") is never asserted; instead of rejecting unverifiable requests, the code treats the *absence* of a secret as proof of authenticity (`verified = true`). This is invoked unconditionally in the controller's `before_action`: [3](#0-2) 

The binding broken is: **"organization that authenticated" (GitHub, via HMAC) vs. "repository/event that is written"** — with no secret configured, nothing authenticates the caller as GitHub at all, yet the payload is processed exactly as if it had been verified. Downstream handlers act on fully attacker-controlled JSON:
- `Handlers::MembershipHandler` adds/removes arbitrary GitHub logins to/from `Team`s that gate `Shipit.github_teams` authorization [4](#0-3) 
- `Handlers::StatusHandler` creates arbitrary commit `Status` records used by `MergeRequest#all_status_checks_passed?` to gate the automated merge queue [5](#0-4) [6](#0-5) 
- `push` events trigger `GithubSyncJob` for arbitrary repos already known to Shipit.

### Impact Explanation
- Forging `status` events lets an attacker mark a pull request's required checks as `success`, which `ProcessMergeRequestsJob` then auto-merges via `MergeRequest#merge!` — an **unauthorized merge**, one of the explicitly listed Critical impacts. [7](#0-6) 
- Forging `membership` events lets an attacker add themselves (or any known GitHub login) into a `Team` backing `Shipit.github_teams`, directly escalating into the application's authorization boundary — a listed High impact. [8](#0-7) 

### Likelihood Explanation
No credentials, session, API token, or private key are required — only that the operator followed the documented, optional-secret setup path. Any deployment that has not set `github.webhook_secret` (shown as blank/`nil` in the shipped example configs and explicitly called "(optional)" in `docs/setup.md`) is exploitable by any network-reachable, unauthenticated attacker who can reach `/webhooks`.

### Recommendation
Fail closed instead of failing open: reject the webhook (`head 422/401`) whenever no `webhook_secret` is configured, or make `webhook_secret` mandatory for the GitHub App configuration and refuse to boot/serve `/webhooks` without it. At minimum, log loudly and refuse to treat `verified = true` as a substitute for actual signature verification.

### Proof of Concept
1. Deploy Shipit following `docs/setup.md` without setting `github.webhook_secret` (an explicitly documented, supported configuration).
2. As an unauthenticated attacker, send:
```
POST /webhooks HTTP/1.1
X-Github-Event: membership
Content-Type: application/json

{"action":"added","team":{"id":1,"name":"x","slug":"x","url":"https://x"},
 "organization":{"login":"<org>"},"member":{"login":"attacker-controlled-login"}}
```
No `X-Hub-Signature` header is required — `verify_webhook_signature` returns `true` because `webhook_secret` is blank [9](#0-8) , so `MembershipHandler#process` runs and adds the target user to the team, potentially satisfying `Shipit.github_teams` membership checks. [4](#0-3) 
3. Similarly, POST a forged `status` event for a commit's SHA with `state: success` for all required contexts to make `MergeRequest#all_status_checks_passed?` return true, causing the background merge queue to merge the PR without genuine CI having run.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

    end
