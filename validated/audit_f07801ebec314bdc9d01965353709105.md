### Title
Arbstore Fee Not Enforced or Paid for Arbiter Contracts on Private and Indivisible Assets - (File: arbiter_contract.js)

### Summary
`arbiter_contract.js` computes the ArbStore's service `cut` and only embeds it in the shared-address spending condition — and only pays it out on completion — when the contract's asset is a *public, divisible* asset. For private assets and fixed-denomination (indivisible) assets, the cut computation is silently skipped both in the definition (`deriveSharedAddress`) and in the payout logic (`complete`), so the ArbStore never receives its commission even though `arbstoreInfo.cut > 0`. This mirrors the reported bug class: a fee is computed/expected but is never actually transferred to the fee recipient.

### Finding Description
In `deriveSharedAddress` [1](#0-0) , the shared-address definition is built differently depending on `isPrivate` and `isFixedDen`:

- For **private assets**, the branch that installs the `["and",[...]]` clauses uses only `in data feed ... CONTRACT_DONE_` release conditions [2](#0-1) . There is no `hasArbStoreCut` handling at all in this branch — the ArbStore's cut is never encoded into the spending condition, regardless of whether `arbstoreInfo.cut > 0`.
- For **public, non-fixed-denomination assets**, the `has output` conditions correctly reduce the peer's expected amount by the cut and add a `has output ... arbstoreInfo.address` clause when `hasArbStoreCut` is true [3](#0-2) .
- The `!isFixedDen && hasArbStoreCut` guard means indivisible assets also never get an ArbStore-cut clause [4](#0-3) .

Correspondingly, in `complete()` [5](#0-4) , the peer/ArbStore amount split is only computed and paid when the asset is public and non-fixed-denomination, i.e. inside `require("./wallet_defined_by_addresses.js").readSharedAddressDefinition(...)` block guarded by `!(assetInfo && (assetInfo.fixed_denominations || assetInfo.is_private))` [6](#0-5) . For private assets, `complete()` only posts a `data_feed` "CONTRACT_DONE_" release message and never builds any `asset_outputs`/`base_outputs` splitting funds to `objContract.arbstore_address` [7](#0-6) . For the "refund" path (and implicitly indivisible assets that fall through to the `else` branch), the full `objContract.amount` goes to `objContract.peer_address` with no cut deducted [8](#0-7) .

The ArbStore's `cut` value is fetched from an external ArbStore server (`arbiters.getArbstoreInfo`) [9](#0-8)  and represents a fee the arbiter/ArbStore is entitled to for providing dispute-resolution services. As with the reported `ElytraDepositPoolV1` bug, the fee percentage is computed (`arbstoreInfo.cut`) but the actual transfer of that fee to the fee recipient (`arbstoreInfo.address`) is silently dropped for a whole class of assets (private and fixed-denomination), creating inconsistent fee handling between asset types.

### Impact Explanation
Any user (offeror/acceptor of an arbiter contract) using a private or fixed-denomination asset can complete a contract without the ArbStore ever receiving its service cut, even though the ArbStore's info advertises `cut > 0`. This is a fund-loss condition for the arbiter/ArbStore fee recipient, and it is inconsistently enforced compared to public divisible assets — a party could deliberately choose a private or NFT-style asset for contracts specifically to avoid paying the arbiter's fee while still consuming arbitration services. Impact is Medium: it does not cause double-spends or DAG-level consensus issues (this is client-side wallet logic, not enforced by protocol validation), but it results in guaranteed, silent loss of expected fee revenue for a legitimate off-chain participant.

### Likelihood Explanation
Likelihood is Medium: any contract created with a private asset (common for privacy-sensitive payments) or a fixed-denomination/indivisible asset will trigger this path automatically — no special conditions or attacker sophistication are required. The bug reproduces deterministically whenever `assetInfo.is_private` or `assetInfo.fixed_denominations` is true and `arbstoreInfo.cut > 0`.

### Recommendation
Extend the cut-splitting logic in `deriveSharedAddress` to also apply to private and fixed-denomination assets (e.g., by encoding the cut condition using `in data feed` release keyed by amount, or by requiring a corresponding `CONTRACT_DONE_` payment split in the private-asset payment chain), and update `complete()` so that, for private/indivisible assets, the payout logic explicitly computes and transfers `arbstoreInfo.cut * objContract.amount` to `objContract.arbstore_address`, consistent with the public-divisible-asset code path.

### Proof of Concept
1. Two parties create an arbiter contract with a private asset (`assetInfo.is_private = true`) via an arbiter whose ArbStore reports `cut = 0.05` (5%).
2. `deriveSharedAddress` builds the shared address definition without any ArbStore-cut clause (lines 485-493), because the `isPrivate` branch never inspects `hasArbStoreCut`.
3. The payer funds the shared address with the full `objContract.amount`.
4. On `complete()`, since `assetInfo.is_private` is true, execution takes the `data_feed`-only branch (lines 728-744) and never builds `asset_outputs` that pay `arbstoreInfo.address` — the peer receives the full `objContract.amount`, and the ArbStore receives nothing, despite having a nonzero `cut`.
5. Repeating the same scenario with a public divisible asset correctly withholds and pays the cut to `arbstoreInfo.address` (lines 752-773), confirming the inconsistency between asset types.

function getArbstoreInfo(arbiter_address, cb) {
	if (!cb)
		return new Promise(function(resolve, reject){
			getArbstoreInfo(arbiter_address, function(err, info){
				if (err) return reject(err);
				resolve(info);
			});
		});
	if (arbStoreInfos[arbiter_address]) return cb(null, arbStoreInfos[arbiter_address]);
	device.requestFromHub("hub/get_arbstore_url", arbiter_address, function(err, url){
		if (err) {
			return cb(err);
		}
		if (!validationUtils.isNonemptyString(url))
			return cb("invalid url received from hub");
		requestInfoFromArbStore(url+'/api/get_info', function(err, info){
			if (err)
				return cb(err);
			if (!validationUtils.isNonemptyObject(info))
				return cb("invalid info received from arbstore");
			const cut = parseFloat(info.cut);
			if (!info.address || !validationUtils.isValidAddress(info.address) || isNaN(cut) || cut < 0 || cut >= 1) {
				return cb("malformed info received from ArbStore");
			}
			info.url = url;
			arbStoreInfos[arbiter_address] = info;
			cb(null, info);
		});
	});
}
