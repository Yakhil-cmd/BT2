### Title
Webhook signature verification keys on `repository.owner.login`/`organization.login` while every event handler acts on the unrelated `repository.full_name` field — signed-org identity ≠ repository written - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App/organization whose `webhook_secret` is used to validate `X-Hub-Signature` based on `params.dig('repository','owner','login')` (falling back to `params.dig('organization','login')`). Every webhook handler, however, resolves which `Repository`/`Stack` to mutate using a completely different payload field, `payload.dig('repository','full_name')` in `Shipit::Webhooks::Handlers::Handler#repository_name`. Because HMAC validation only proves "this body was signed with organization X's secret," not "the `repository.full_name` inside this body actually belongs to organization X," an attacker who legitimately controls their own onboarded GitHub organization (and therefore its `webhook_secret`) can forge a correctly-signed payload whose `owner.login` is their own org but whose `repository.full_name` names any other repository/stack tracked by the same Shipit instance.

### Finding Description
- Signature check: [1](#0-0) , with `repository_owner` derived from [2](#0-1) .
- Action/write target: [3](#0-2) , used by handlers such as `PushHandler` (`stacks.not_archived.where(branch:).find_each { |stack| stack.sync_github(...) }`) [4](#0-3)  and `CheckSuiteHandler` (`stacks.where(branch: ...).each(&:schedule_refresh_check_runs!)`) [5](#0-4) .
- `StatusHandler` is even more permissive: it never scopes by `repository` at all, it looks up `Commit.where(sha: params.sha)` across the entire database and calls `commit.create_status_from_github!(params)` [6](#0-5) , meaning a signed-but-unrelated payload can inject commit-status/CI state for any commit sha that happens to exist on any tracked stack, as long as the sha matches.

The equality that should hold is: **organization whose secret authenticated the request == organization/repository the handler is permitted to mutate**. Because `verify_signature` and `Handler#repository_name` read two independent, attacker-controlled JSON fields from the same unsigned-vs-signed body, this binding is not enforced — the HMAC covers the raw bytes, but nothing ties the specific `repository.full_name` value to the `repository.owner.login`/`organization.login` value used for key selection. Since the raw JSON is entirely attacker-authored (before signing with their own secret), they can freely set `repository.owner.login` = their own org (to pick a secret they know) and `repository.full_name` = a victim's tracked repository (to pick the target).

### Impact Explanation
An attacker who is a legitimate, unprivileged customer/organization onboarded to a shared Shipit instance (i.e., they have their own GitHub org + webhook secret configured in `Shipit.github_apps`/config, which is the normal, documented mounting of this engine — not a privileged Shipit account) can:
- Forge `push` events for another tenant's tracked stack, forcing `sync_github` with an attacker-chosen `expected_head_sha`, effectively injecting arbitrary commit metadata into a stack they don't own.
- Forge `status` events to mark an arbitrary commit sha (on any tracked repository) as CI-passing/failing via `Commit#create_status_from_github!`, which can influence deploy safety gating (`deployable?`/required/blocking status checks) for stacks the attacker does not have write access to — this can contribute to an unauthorized deploy being permitted.
- Forge `check_suite` events to trigger check-run refresh for arbitrary tracked branches/commits.

This crosses the "unauthorized deploy" / "cross-repository writes" impact bar because the binding broken is exactly "GitHub org authenticated via signature" vs "repository actually written," matching the required analog class.

### Likelihood Explanation
Requires the attacker to control at least one legitimately onboarded GitHub organization/webhook secret on the shared Shipit instance (not a privileged Shipit session, `ApiClient` token, or the app's own GitHub App key) — a low bar for any multi-tenant deployment of this engine as documented. No repository write access, TLS interception, or social engineering is needed; only crafting a raw JSON POST to the public `/github/webhooks`-style endpoint with a valid HMAC computed from a secret the attacker legitimately possesses.

### Recommendation
Do not select the verification key from an unauthenticated field that differs from the field used to resolve the target repository. Either:
1. Verify the signature using a secret bound to the repository actually referenced by `repository.full_name` (not `repository.owner.login`/`organization.login`), or
2. After verifying, re-validate that every field the handler acts on (`repository.full_name`, commit `sha` provenance, etc.) belongs to the organization whose secret validated the signature, rejecting/dropping events where `repository.full_name`'s owner segment does not match `repository_owner`.
3. For `StatusHandler`, scope the `Commit.where(sha: ...)` lookup by the repository resolved from the verified organization, not globally by sha.

### Proof of Concept
1. Attacker owns GitHub org `attacker-org` with a Shipit-configured `webhook_secret` (`S_attacker`), a normal customer setup.
2. Attacker crafts a JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "deadbeef...attacker-chosen-sha",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(S_attacker, body)` and POSTs to the webhooks endpoint with `X-Github-Event: push`.
4. `verify_signature` resolves `repository_owner` = `"attacker-org"` [2](#0-1) , fetches `Shipit.github(organization: "attacker-org")`, and validates successfully because the attacker signed with their own real secret [1](#0-0) .
5. `PushHandler#process` resolves the target stack via `repository.full_name` = `"victim-org/victim-repo"` [3](#0-2)  and calls `stack.sync_github(expected_head_sha: "deadbeef...")` on the victim's stack [4](#0-3) , despite the request never being signed by `victim-org`.
