### Title
`has_only()` oscript function mishandles character-class regex construction, allowing a whitelist validation bypass via negated character class - (File: formula/evaluation.js)

### Summary
The oscript function `has_only(str, chars)` is meant to let an Autonomous Agent (AA) author whitelist-validate a string against a fixed set of allowed characters. The implementation builds a regular expression by naively embedding the attacker-influenced `chars` argument inside a `[...]` character class without rejecting the regex negation meta-character `^` or otherwise safely escaping the class contents. Analogous to CVE-2019-15845 (Ruby `File.fnmatch` mishandling special characters in path-matching patterns, letting attacker input silently defeat the intended match semantics), a value beginning with `^` inverts the meaning of the character class instead of being treated as a literal character to allow, turning a restrictive whitelist check into a check that matches virtually any input.

### Finding Description
`has_only` is implemented in `formula/evaluation.js` inside the shared `evaluate()` switch used by both AA formulas and address/asset definitions: [1](#0-0) 

The code only guards against two things: an escaped `]` (`sub.match(/\\]/)`) and a trailing unescaped backslash. It does not reject or escape a leading `^`, nor does it prevent `-` from creating unintended ranges. Both `str_expr` and `sub_expr` are arbitrary, fully dynamic oscript expressions — nothing in `formula/validation.js` requires `sub_expr` to be a compile-time literal: [2](#0-1) 

Because `sub` can be built (directly or indirectly, e.g. via string concatenation with `trigger.data.*`) from data supplied by an unprivileged AA trigger sender, an attacker who influences the `chars` argument can pass a value starting with `^`. The resulting expression `new RegExp("^[" + sub + "]*$")` becomes something like `^[^]*$`, and in JavaScript `[^]` (an empty negated character class) matches *any* character, including newlines. The whitelist check `has_only(str, sub)` then returns `true` for arbitrary `str`, completely defeating the intended restriction, regardless of what characters the AA author's logic assumed were being enforced.

This mirrors the CVE's bug class exactly: a matching/validation primitive that is supposed to enforce "only these characters/paths are allowed" can be tricked with a crafted pattern into accepting inputs it should reject.

### Impact Explanation
Any AA that relies on `has_only()` to sanitize or whitelist-validate trigger-supplied strings before using them in security-relevant logic (e.g., validating a symbol/ticker/key that is later used to index state variables, construct data-feed names, build addresses, or gate a payout path) can have that validation silently bypassed by an attacker who can influence the character-set argument (even partially, through string concatenation with `trigger.data`). Depending on how the AA uses the "sanitized" value downstream, this can lead to state corruption, collision of keys/namespaces meant to be kept distinct, or bypass of a guard that was meant to prevent malicious values from reaching a fund-moving branch of the bounce/AA logic — i.e., AA fund loss or freezing, consistent with the Medium severity of the underlying CVE analog.

### Likelihood Explanation
Exploitation requires only sending a normal AA trigger with attacker-chosen `data` fields to an AA whose oscript formula passes any trigger-influenced value into the `chars` argument of `has_only`. No privileged access, no malicious peer/hub, and no network-level behavior is required — a single posted trigger unit is sufficient to test/exploit the bug against any AA using this pattern for input sanitization.

### Recommendation
Harden the `has_only` implementation in `formula/evaluation.js`:
- Reject (fatal error) if `sub` begins with `^`, or always neutralize it by escaping (e.g., prefix with `\` inside the class, since `\^` is a literal caret in a JS character class) rather than passing it through unescaped.
- Escape all other regex metacharacters that have special meaning inside `[...]` (notably `-` used for ranges, and `\` sequences) unless explicitly intended as a supported feature, and document/test the supported subset precisely.
- Alternatively, avoid dynamic regex construction entirely and implement `has_only` via direct character-set membership testing (e.g., build a `Set` of allowed literal characters, or a whitelist of supported escape shorthands like `\w`, `\d`, `\s`) so there is no possibility of the pattern altering match semantics.

### Proof of Concept
An oscript formula executed by any AA that whitelists a trigger-controlled value using `has_only`:
```
$chars = trigger.data.chars; // attacker controls this via trigger.data
$ok = has_only(trigger.data.value, $chars);
if ($ok) {
    // AA logic assumes trigger.data.value only contains vetted characters
    ...
}
```
Attacker sends a trigger with:
```
{ "chars": "^", "value": "'; DROP everything :: arbitrary/malicious/string\n$$$" }
```
Because `sub` = `"^"`, the constructed pattern is `^[^]*$`, which matches any string (including special characters, newlines, etc.), so `has_only` returns `true` even though `value` contains none of the characters the AA author intended to allow, defeating the whitelist check at: [3](#0-2)
