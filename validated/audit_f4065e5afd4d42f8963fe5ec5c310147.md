### Title
Webhook signature check is fully bypassed on GitHub Apps configured without a `webhook_secret`, letting an unauthenticated attacker forge events (membership/push/status) that act on unrelated organizations, repositories, and `Shipit.github_teams` authorization - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/secret to validate against using an **unverified** field from the incoming JSON body (`repository.owner.login` / `organization.login`), then hands the same unverified body to event handlers that act on *different* payload fields (`repository.full_name`, top-level `organization.login`, `team.id`, `member.login`). When the selected app has no `webhook_secret` configured — a state the setup docs explicitly call "optional" — `GitHubApp#verify_webhook_signature` returns `true` unconditionally, so the signature check is a no-op for that request. This breaks the binding "organization that authenticated == organization/repository that is written": an attacker who only needs an unauthenticated HTTP POST can pick which (unsecured) org's checks to satisfy while making the payload act on any other org/repo/team, including teams in `Shipit.github_teams`.

### Finding Description
`verify_signature` looks up the app to validate against from attacker-controlled JSON, before any verification occurs: [1](#0-0) [2](#0-1) 

`GitHubApp#verify_webhook_signature` silently authorizes the request when no secret is configured for that org: [3](#0-2) 

`Shipit.github` resolves configuration purely from the (attacker-supplied) `organization` argument, with no cross-check that this value matches anything else in the payload: [4](#0-3) 

Once "verified" (trivially, if no secret is set), the same raw payload is dispatched to handlers that key off *other* fields entirely, never re-checked against `repository_owner`:
- `MembershipHandler` trusts `params.team.id`, `params.organization.login`, and `params.member.login` to add an arbitrary GitHub user to an arbitrary (existing) `Team`: [5](#0-4) 
- `PushHandler`/`StatusHandler`/PR handlers key off `repository.full_name` via `Handler#repository_name`/`Repository.from_github_repo_name`, independent of the `repository_owner` used for signature selection: [6](#0-5) 

Because `Team.find_or_create_by!(github_id: params.team.id)` will find (not create) a pre-existing team when `team.id` matches a real, already-provisioned `Shipit.github_teams` team, an attacker who forges a `membership` event with that team's real `github_id` and their own GitHub login gets `team.add_member(member)` executed: [7](#0-6) 

`User#authorized?` is computed purely from team membership recorded in the database, so once the forged membership is persisted, a subsequent legitimate OAuth login by that same GitHub account passes the authorization gate: [8](#0-7) [9](#0-8) 

### Impact Explanation
This escalates directly into `Shipit.github_teams` authorization (explicit High-impact category): a fully unauthenticated network attacker can grant their own real GitHub account membership in whichever team gates access to a private Shipit instance, then simply complete the normal OAuth login flow to gain authenticated access. The same primitive also lets the attacker forge `push`/`status`/`pull_request` events for arbitrary stacks (triggering `GithubSyncJob`, fabricating commit statuses, or manipulating review-stack provisioning) regardless of which organization actually owns those stacks, since the org used to "verify" the request and the org/repo actually acted upon are never required to match.

### Likelihood Explanation
Any Shipit deployment that follows the documented setup (webhook secret marked "optional" in `docs/setup.md`) and leaves `webhook_secret` unset for any configured GitHub App is directly exploitable with a single unauthenticated `POST /webhooks` request — no credentials, tokens, or GitHub write access are needed. Even where secrets are set, the selection-vs-action field mismatch is structural, so any future/alternate deployment gap in secret coverage (e.g., a newly onboarded org) reopens the same hole.

### Recommendation
- Verify the HMAC signature using the specific GitHub App config resolved from a value that is itself bound to the request's authenticated source (e.g., require and fail-closed on a missing `webhook_secret` rather than treating it as "verified").
- After signature verification succeeds, re-derive and enforce that the organization used to select the verifying secret matches every organization/repository field the handler subsequently acts on (`repository.full_name`'s owner, `organization.login`, team ownership) before executing side effects like `team.add_member`, `Stack#sync_github`, or `Commit#create_status_from_github!`.

### Proof of Concept
1. Deploy Shipit with the documented, "optional" `webhook_secret` left blank for the GitHub App configured for `repository_owner: victim-org` (or use the single-app config path, where `webhook_secret` blank disables the check globally).
2. As an anonymous attacker, `POST /webhooks` with header `X-Github-Event: membership` and a JSON body such as:
```json
{
  "action": "added",
  "team": { "id": <real github_id of a Shipit.github_teams team>, "name": "Deployers", "slug": "deployers", "url": "https://github.com" },
  "organization": { "login": "victim-org" },
  "member": { "login": "attacker-github-login" }
}
```
No `X-Hub-Signature` needs to be valid since `verify_webhook_signature` returns `true` when `webhook_secret` is blank.
3. `WebhooksController#create` dispatches to `MembershipHandler#process`, which creates/fetches the attacker's `User` via `User.find_or_create_by_login!('attacker-github-login')` and calls `team.add_member(member)` on the real authorized team.
4. Attacker completes the normal `/github/auth/github` OAuth login with their own GitHub account; `find_or_create_from_github` matches the same `github_id`, and `User#authorized?` now returns `true` because of the forged membership row, granting full access to the private Shipit instance.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
