### Title
Commit CI-status forgery across repositories breaks the binding between the GitHub organization that signed the webhook and the repository/stack whose commit status is mutated - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` selects a GitHub App/webhook secret using the *organization* named in the payload (`repository.owner.login`, falling back to `organization.login`), and accepts the request once the HMAC matches that org's secret. However, `Shipit::Webhooks::Handlers::StatusHandler#process` never checks which repository/organization the payload claims to be from: it resolves the commit purely via `Commit.where(sha: params.sha)`, globally across every stack tracked by the Shipit instance. This breaks the binding: `organization whose webhook secret validated the signature == repository/stack whose commit status gets written`.

### Finding Description
- `WebhooksController#verify_signature` picks the GitHub App config for HMAC verification using `repository_owner`, itself read straight out of the untrusted JSON body (`params.dig('repository', 'owner', 'login')`), and then calls `Shipit.github(organization: repository_owner).verify_webhook_signature(...)`. [1](#0-0) [2](#0-1) 
- Shipit explicitly supports multiple independent GitHub Apps/organizations, each with its own `webhook_secret`, as shown by the dual-org fixture config. [3](#0-2) 
- Once the signature check passes (proving only that *some* configured org's secret produced this HMAC over the full raw body), the event is dispatched to handlers with the raw, already-verified payload: `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`. [4](#0-3) 
- The base `Handler` class resolves the acted-upon repository via `payload.dig('repository', 'full_name')` for handlers that use `stacks`. [5](#0-4) 
- Critically, `StatusHandler` (handling the `status` webhook event) does **not** use `stacks`/`repository_name` at all. It resolves the target purely by commit SHA, with no repository or organization filter whatsoever: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }`. [6](#0-5) 
- Because git commit SHAs are computed from tree content and are identical across forks/mirrors that share history, any commit that exists in more than one repository tracked by the same Shipit instance (e.g. a fork of a tracked upstream repo, or two stacks pointing at related repos) can have its Shipit-tracked commit's CI status set by a `status` webhook that is genuinely signed by GitHub for a *different* repository/organization than the one whose commit is mutated.
- The written status feeds directly into deploy/merge automation: `Commit#add_status` (invoked by `create_status_from_github!`) calls `stack.schedule_merges` on `pending`/`success` transitions and updates `deployable_status`. [7](#0-6)  Tests confirm that a `success` status transition on continuous-deployment-enabled stacks directly enqueues a `Deploy`. [8](#0-7) 

Before the attacker's request: the commit's real CI status reflects genuine CI results for the tracked repository/organization X, and the webhook signature scheme intends `organization(secret used to sign) == organization(repository that gets its state changed)`.
After the attacker's request: a webhook validly signed with organization Y's webhook secret (Y ≠ X, e.g. attacker's own fork/org) is processed by `StatusHandler`, and because resolution is by bare SHA with no repository/org check, the commit belonging to organization X's stack is mutated with attacker-chosen `state`/`description`/`target_url`/`context` — i.e., `organization(signature) ≠ repository(write)`.

### Impact Explanation
Forging a `success` CI status on a commit that is not actually green can unblock `allows_merges?`/`merge_status` gating and, on stacks with `continuous_deployment` enabled, directly trigger an automatic `Deploy` of a commit that never passed real CI for the target repository/stack. This is an unauthorized-deploy class impact achieved purely through a cross-repository binding failure in webhook processing, without needing an `ApiClient` token, a Shipit session, or write access to the target repository itself.

### Likelihood Explanation
The attacker only needs: (1) a commit whose content/history is shared between a repository they control (e.g. a fork) and a repository Shipit tracks under a different organization/app, and (2) the ability to post a real commit status to their own repo (which GitHub will legitimately sign and deliver as a `status` event using their own org's registered webhook secret). No secret leakage, no forged signature, and no access to the victim repository or its GitHub App is required — only ordinary, unprivileged GitHub usage (forking a public repo and setting a status on it via the standard commits/statuses API) that Shipit's own configuration model (multi-org support with independent webhook secrets) explicitly allows to reach a shared instance.

### Recommendation
In `StatusHandler` (and any other handler that doesn't use the base `stacks` scoping), constrain the lookup to commits belonging to stacks whose `repository.owner`/`full_name` matches the `repository_owner`/`repository.full_name` that was actually used to select and verify the webhook signature, e.g. `stacks.joins(:repository).merge(Commit.where(sha: params.sha))`, and reject/ignore events where the payload's declared repository does not match any stack under the authenticated organization.

### Proof of Concept
1. Attacker forks a public upstream repository that Shipit tracks (stack `A`, owned by GitHub org `OrgX`, whose GitHub App has `webhook_secret_X`). The fork lives under the attacker's own org/account `OrgY`, with its own `webhook_secret_Y` configured in Shipit (multi-org setup as in `secrets_double_github_app.yml`).
2. Because it's a fork, commit `abc123...` exists identically (same SHA) in both `OrgX/upstream` (tracked, real CI pending/failing) and `OrgY/fork`.
3. Attacker uses the GitHub Statuses API on their own fork `OrgY/fork` to post `state: success` for `sha: abc123...`. GitHub genuinely signs and delivers this `status` webhook to Shipit using `webhook_secret_Y`.
4. `WebhooksController#verify_signature` reads `repository.owner.login == "OrgY"`, loads `webhook_secret_Y`, and the HMAC validates — request is accepted. [1](#0-0) 
5. `StatusHandler#process` runs `Commit.where(sha: "abc123...")`, matches the `Commit` row belonging to stack `A` (`OrgX/upstream`), and calls `create_status_from_github!`, marking it `success` regardless of real CI state for `OrgX`. [6](#0-5) 
6. If stack `A` has `continuous_deployment` enabled, this triggers an automatic `Deploy` of `abc123...` on `OrgX/upstream`'s infrastructure. [8](#0-7)

    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
