## Title
Dust-remaining-collateral rounding lets a liquidator seize a borrower's entire collateral balance while only being required to repay debt for the "dust" fraction - (File: `mainnet/contracts/market/v0-4-market.clar`, function `liquidate`)

## Summary
In `liquidate`, after computing a proportional collateral seizure (`coll-final-raw`), the contract checks whether the *remaining* (unseized) collateral is worth enough to repay any further debt (`remaining-debt-to-repay`). If that "remaining debt" rounds down to `u0` (a dust amount of leftover collateral), the code discards the proportionally-computed `coll-final-raw` and instead sets `coll-final` to the borrower's **entire** collateral balance (`user-coll-balance`), while `debt-to-repay` (computed earlier from `coll-final-raw`/`debt-final`) is left unchanged and can be far smaller than what would be required to buy the full collateral balance at the penalty rate.

## Finding Description
The relevant computation is: [1](#0-0) 

`debt-to-repay` and `coll-final-raw` are derived consistently from the same proportional liquidation math (`process-debt-asset` → `process-collateral-asset` → `calc-final-liquidation-amounts` → `scale-debt-for-liquidation`): [2](#0-1) 

But then the code overrides the seized-collateral amount based on a *separate, unrelated* "dust check" on the leftover collateral, not on the actual value backing `debt-to-repay`: [3](#0-2) 

The logic: compute `coll-remaining = user-coll-balance - coll-final-raw`. If `coll-remaining > 0`, convert that *remaining* collateral value to a hypothetical debt-token amount (`remaining-debt-to-repay`) using `div-bps-down`/`mul-div-down`/`mul-div-up` rounding. Because of integer-division rounding (`mul-div-down` truncation, `INDEX-PRECISION` scaling, and rebasing through `mul-div-up`), it is possible for a genuinely non-zero `coll-remaining` to compute to `remaining-debt-to-repay == u0` (i.e., the dust remainder "looks like" it is worth 0 debt tokens after rounding). When this happens, `coll-final` is unconditionally set to `user-coll-balance` — the borrower's *full* collateral balance for that asset — while `debt-to-repay` and `debt-final-usd`/`scaled-to-remove` (the debt actually removed from the borrower's ledger and the tokens actually pulled from the liquidator via `vault-system-repay`) remain the smaller, proportionally-calculated values from `coll-final-raw`.

The subsequent execution then acts on these mismatched numbers: [4](#0-3) 

`vault-system-repay` only pulls `debt-to-repay` tokens from the liquidator, and `debt-remove-scaled` only clears `scaled-to-remove` scaled debt from the borrower — both computed from the smaller `coll-final-raw`-based path — yet `collateral-remove` is invoked with `coll-final = user-coll-balance`, sweeping the borrower's *entire* collateral position of that asset to the liquidator (or an arbitrary `collateral-receiver`).

This is precisely the reported bug class: a downstream execution step consumes an amount (`coll-final`) that was silently replaced with a value inconsistent with the amount that was actually priced/paid for (`debt-to-repay`), rather than the amount actually computed for the trade — mirroring `StandardPolicyERC1155`'s hardcoded `1` replacing `order.amount` in the transfer step while the price still reflects the full order.

## Impact Explanation
The liquidator (attacker/unprivileged principal) can repay only a small, rounding-crafted amount of debt yet receive the borrower's (victim, unprivileged principal) entire collateral balance for that asset — collateral far exceeding the bonus-adjusted value of the debt actually repaid. This is a direct seizure exceeding its intended bound: the borrower is stripped of collateral without a commensurate reduction in debt liability beyond what was paid for, and the liquidator captures the excess value. This is theft of a user's funds at rest (collateral) via a bug in the protocol's own liquidation accounting — a Critical-severity impact (direct theft of user funds), independent of any oracle manipulation or DAO compromise.

## Likelihood Explanation
Triggering this requires driving `remaining-debt-to-repay` to exactly `u0` via the chained rounding of `div-bps-down` → `mul-div-down` (twice) → `mul-div-up`, which happens whenever `coll-remaining`'s USD value, after the liquidation-penalty divisor and debt-token/scaled-debt conversions, truncates to zero. A liquidator who controls `debt-amount` (and thus `debt-to-repay`/`coll-final-raw` indirectly through the earlier capping logic) can iteratively choose `debt-amount` such that the leftover collateral lands in this dust window, especially for low-decimal or low-price debt assets where truncation to zero is easy to hit. This makes the condition realistically reachable by any liquidator against any near-full-liquidation borrower, not just an edge case requiring privileged access.

## Recommendation
Never let `coll-final` exceed the collateral value actually purchased by `debt-to-repay`. If the leftover `coll-remaining` is judged to be "dust" (unliquidatable due to rounding), it should either: (a) be left with the borrower rather than swept to the liquidator, or (b) be swept only if `debt-to-repay`/`scaled-to-remove` is correspondingly increased to fully consume the borrower's remaining debt for that asset (i.e., treat this as a full/final liquidation of the position, not a partial one priced at the smaller amount). The `coll-final` override must be derived from — and bounded by — the same proportional pricing used for `debt-to-repay`, never independently substituted with `user-coll-balance`.

## Proof of Concept
1. Borrower has a position with debt-asset D (low decimals, e.g., a stablecoin with 6 decimals) and collateral-asset C, positioned in the partial/full liquidation LTV band.
2. Liquidator calls `liquidate` with a `debt-amount` chosen (via off-chain simulation) such that the resulting `coll-final-raw` leaves a `coll-remaining` whose USD value, once divided by `(BPS + liq-penalty-max)` and converted through `mul-div-down`/`mul-div-up` with `INDEX-PRECISION` and the current `borrow-index`, rounds down to `remaining-debt-to-repay = u0`.
3. Because `remaining-debt-to-repay == u0`, `coll-final` is set to `user-coll-balance` at line 1509 (local-testing) / line 1486 (mainnet `v0-4-market.clar`), while `debt-to-repay` remains the smaller value from `scale-debt-for-liquidation`.
4. `vault-system-repay` charges the liquidator only `debt-to-repay` tokens; `collateral-remove` transfers the borrower's entire `user-coll-balance` of asset C to the liquidator/`collateral-receiver`.
5. The borrower loses their full collateral balance in asset C for a fraction of the expected repayment, and the liquidator profits the difference — reproducible deterministically given the described rounding path, without needing any oracle manipulation, DAO action, or leaked keys.

;; Converts to scaled units, caps at current debt, calculates final collateral
;; Returns: { scaled-to-remove: uint, debt-to-repay: uint, coll-final: uint }
(define-private (scale-debt-for-liquidation
  (debt-final uint)
  (coll-actual uint)
  (curr-scaled uint)
  (asset-id uint))
  (let (;; convert debt amount to scaled units for storage
        (borrow-index (get index (unwrap-panic (get-cached-indexes asset-id))))
        (scaled-debt (mul-div-down debt-final INDEX-PRECISION borrow-index))
        ;; cap at current debt (prevent over-repayment)
        (scaled-to-remove (if (> scaled-debt curr-scaled) curr-scaled scaled-debt))
        (debt-to-repay (mul-div-up scaled-to-remove borrow-index INDEX-PRECISION))
        ;; If debt was capped, scale collateral proportionally
        (coll-final (if (< scaled-to-remove scaled-debt)
                        (mul-div-down coll-actual scaled-to-remove scaled-debt)
                        coll-actual)))
    {
      scaled-to-remove: scaled-to-remove,
      debt-to-repay: debt-to-repay,
      coll-final: coll-final
