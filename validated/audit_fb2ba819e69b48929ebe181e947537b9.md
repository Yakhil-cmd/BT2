### Title
Unbounded loop over attestor addresses in the `attested` address-definition op allows spam/DoS on every spend from the address - (File: `definition.js`)

### Summary
The dForce report describes an unbounded loop, driven entirely by attacker-controlled array length, that is re-executed on every subsequent action touching the position (transfer/redeem/borrow/liquidate), with no per-item cost accounting. `ocore`'s address-definition evaluator has close structural analog: the `attested` op accepts an attacker-supplied list of attestor addresses (`arrAttestors`) and validates every entry in a `for` loop, but — unlike the sibling `in data feed` / `in merkle` ops in the very same function — it never charges any `complexity`/`count_ops` for the size of that array. This op is evaluated (and its DB-backed authentication logic re-run) on **every unit signed by the address**, i.e., on every spend, making the cost recurring rather than one-time.

### Finding Description
`Definition.validateDefinition()` in `definition.js` walks an address/asset definition tree and increments `complexity`/`count_ops` once per node, enforcing `constants.MAX_COMPLEXITY` / `constants.MAX_OPS` as global anti-spam limits: [1](#0-0) 

For the `in data feed` and `in merkle` ops, the code explicitly compensates for the size of the `arrAddresses` array by adding `arrAddresses.length-1` to `complexity`, so a large oracle-address list is charged proportionally to its size and will trip `MAX_COMPLEXITY`: [2](#0-1) [3](#0-2) 

The `attested` op, however, loops over an attacker-controlled `arrAttestors` array with **no equivalent complexity charge**: [4](#0-3) 

Compare this to the sibling function `checkAttestorList()`, used only for the `asset_attestors` app message, which does explicitly cap the list size with `constants.MAX_ATTESTORS_PER_ASSET`: [5](#0-4) 

No such cap exists for the `attested` op's `arrAttestors` array inside an address definition (or an asset issue/transfer condition, since `bAssetCondition` is explicitly allowed for this op except when referencing `'this address'`): [6](#0-5) 

At authentication time (`validateAuthentifiers`), the same op is evaluated again, this time invoking a DB lookup keyed on the full `arrAttestors` list via `storage.filterAttestedAddresses`: [7](#0-6) 

Because address definitions are cached and re-validated whenever the address is used as an author (a full re-walk of the definition tree, per the comment in the code: "we need to re-validate the definition every time... in case a referenced address was redefined"), this large, uncomplexity-charged loop and its associated `IN (...)` query are repeated on **every unit spent from that address**, not just once at definition-creation time: [8](#0-7) 

This exactly mirrors the dForce bug-class: a per-position/per-entry loop, sized by attacker-controlled input, whose cost is not adequately capped, and which is re-executed on every subsequent transaction touching the affected account — inflating validation cost for any node (and any counterparty who must validate the unit) each time the address spends.

### Impact Explanation
An attacker can create an address whose definition contains an `attested` clause with an oversized `arrAttestors` array (bounded only by the overall unit-size limit `MAX_UNIT_LENGTH`, not by any per-op cap). Every unit later signed by this address — and every unit any full/light node must validate that references it (e.g. spending its outputs, or a wallet co-signer service processing signing requests) — forces:
1. An O(n) address-validity loop over `arrAttestors` with no complexity accounting, so it does **not** get rejected via `MAX_COMPLEXITY`/`MAX_OPS` the way comparable ops (`in data feed`, `in merkle`) would.
2. A DB query (`storage.filterAttestedAddresses`) parameterized by the full attestor list, executed on the hot validation path for that address, every single time it is used.

This raises the CPU/DB cost of validating units for a given address well beyond what the anti-spam complexity budget intends, and it recurs indefinitely for the lifetime of the address (unlike a one-time definition-validation cost). It does not directly cause loss of funds, but it degrades node validation performance and can be used to make transactions from/against the crafted address disproportionately expensive to validate compared to their declared "complexity", undermining the complexity-based anti-DoS design that the rest of `validateDefinition` relies on.

### Likelihood Explanation
Reachable by any unprivileged unit poster: defining an address (or an asset issue/transfer condition) with an `attested` clause is a standard, permitted feature and requires no special privilege — only sufficient bytes to pay for a larger-than-usual (but still valid) unit. The inconsistency between `attested` and the neighboring `in data feed`/`in merkle` ops (which do charge complexity per array element) indicates this is an overlooked gap rather than an intentional design choice, increasing confidence that it is an unintended, exploitable oversight.

### Recommendation
- Charge `complexity` (and/or `count_ops`) proportionally to `arrAttestors.length` in the `attested` case of `validateDefinition`, mirroring the treatment already applied to `in data feed` and `in merkle`.
- Additionally, apply an explicit hard cap (e.g., reuse `constants.MAX_ATTESTORS_PER_ASSET` or a dedicated constant) on the number of attestor addresses allowed inside an `attested` op in address/asset definitions, consistent with the existing cap enforced for `asset_attestors` messages via `checkAttestorList`.
- Audit all other definition ops for similar array-driven loops (e.g., any future op accepting attacker-sized arrays) to ensure each has both a complexity charge and, where relevant, a hard size cap, so the complexity budget actually bounds real validation cost.

### Proof of Concept
1. Attacker crafts a new address whose definition is:
   `['attested', ['this address', [addr_1, addr_2, ..., addr_N]]]` (combined with a `sig` branch to satisfy the "each branch must have a signature" rule), where `N` is chosen as large as the overall unit-size limit (`constants.MAX_UNIT_LENGTH`) allows for the definition payload.
2. Because the `attested` case (`definition.js` lines 370–388) does not add complexity per attestor (unlike `in data feed`/`in merkle`), this passes `validateDefinition`'s `MAX_COMPLEXITY`/`MAX_OPS` checks despite containing thousands of addresses.
3. The attacker funds the address and later spends from it. Each such spend causes `validateAuthentifiers` to re-evaluate the `attested` op (`definition.js` lines 904–915), iterating/querying against the full `arrAttestors` list via `storage.filterAttestedAddresses`, and this happens on every future unit involving that address as an author — imposing a disproportionate, recurring validation cost on every node in the network relative to the complexity budget the definition nominally consumed.
