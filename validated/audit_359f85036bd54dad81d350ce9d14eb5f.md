Confirmed root cause: `PushHandler#stacks` (and every other webhook handler inheriting from `Shipit::Webhooks::Handlers::Handler`) resolves the target `Repository`/`Stack` from `payload.dig('repository', 'full_name')` [1](#0-0) , while `WebhooksController#verify_signature` selects which GitHub App/secret to authenticate the request against using a *different* field, `repository.owner.login` (or `organization.login`) [2](#0-1) . These two fields are never checked for consistency against each other or against the actual signed content's origin.

### Title
Webhook org used to select signing key differs from the repository field the handler acts on, permitting cross-organization stack writes - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/handler.rb`)

### Summary
`verify_signature` picks the `GithubApp`/webhook secret to validate a webhook with by reading `repository.owner.login` from the *unverified* JSON body [3](#0-2) . Once the HMAC checks out for whatever org that field names, `Handler#stacks` looks up the Stack to mutate using an entirely separate field, `repository.full_name` [1](#0-0) . Nothing enforces `repository.full_name`'s owner segment to match `repository.owner.login`/`organization.login`. This is the same class of bug as the report: a value that gates the trust decision (`minAnswer`/`maxAnswer` bound, here "the org whose secret was used to sign") is not the same value that the downstream logic actually acts on (`_answer` bound to real price, here "the repository actually written to").

### Finding Description
In a Shipit deployment configured with multiple GitHub Apps/orgs (a documented, supported configuration — see `test/dummy/config/secrets_double_github_app.yml` and `config/secrets.development.example.yml`'s multi-org example) [4](#0-3) , each org has its own `webhook_secret`. `Shipit.github(organization: repository_owner)` is invoked with `repository_owner` taken straight from the attacker-controlled JSON body before the HMAC signature is validated [5](#0-4) . The signature is verified over the raw request body using that org's secret [6](#0-5) .

Because the body itself is attacker-supplied JSON (not a real GitHub-relayed payload with cross-checked fields), nothing stops the attacker from crafting a payload where `repository.owner.login` == `OrgB` (whose secret the attacker legitimately possesses, e.g. because they administer OrgB's own GitHub App/webhook) while `repository.full_name` == `"OrgA/some-other-repo"` — a completely different, unrelated repository under a different org that the attacker does not control. `verify_signature` will validate successfully (it's checking a real, correctly-signed-with-OrgB's-secret body), and then `PushHandler`/`StatusHandler`/`CheckSuiteHandler`/etc. will resolve `stacks` via `Repository.from_github_repo_name("OrgA/some-other-repo")` and act on it — e.g. enqueue `GithubSyncJob`, mutate `Commit#statuses`, refresh check runs — for a stack the attacker has no authorization over.

### Impact Explanation
This lets a party who legitimately controls one configured GitHub App/org's webhook secret (unprivileged with respect to any *other* configured org) forge webhook events that are accepted as authentic for stacks belonging to a different organization. Depending on which webhook event/handler is targeted this can trigger unauthorized `GithubSyncJob` runs, spoofed commit statuses (`StatusHandler`), or spoofed check-run refreshes — actions on a stack/repository that were never authorized by the actual owning organization's GitHub App. This satisfies the "cross-repository writes" / "unauthorized deploy-adjacent action" impact class: the binding broken is *"organization whose signature authenticated the request" == "organization/repository the payload's `full_name` field actually causes handlers to write to"*, which does not hold.

### Likelihood Explanation
Requires the deployment to be configured with more than one GitHub App/org (a documented, supported configuration) and requires the attacker to already possess a valid webhook secret for at least one configured org (e.g. their own org's Shipit-integrated GitHub App). Given that constraint, forging the cross-org payload is trivial — a single crafted JSON body and a correctly computed HMAC using their own known secret. No GitHub write access, Shipit session, or `ApiClient` token is required, only knowledge of one configured webhook secret, which is a materially weaker credential than what's needed elsewhere in the engine.

### Recommendation
Bind the field used to select the verifying secret to the same field used for resolving the target repository. E.g., verify the signature generically first against all configured orgs (or key the lookup off the same `repository.full_name`-derived owner used by `Handler#repository_name`), and reject if the org that successfully verifies the signature does not match the owner segment of `repository.full_name` that the handler will act upon.

### Proof of Concept
1. Deploy Shipit with two configured GitHub orgs, `OrgA` (owns stack `OrgA/prod-app`) and `OrgB` (attacker administers `OrgB`'s GitHub App and therefore knows `OrgB`'s `webhook_secret`).
2. Attacker crafts a `push` event JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "deadbeef",
  "repository": {
    "owner": { "login": "OrgB" },
    "full_name": "OrgA/prod-app"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(OrgB_webhook_secret, body)>` and POSTs to `/webhooks`.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: "OrgB")`, verifies successfully against `OrgB`'s secret [7](#0-6) .
5. `PushHandler#process` → `stacks` resolves `Repository.from_github_repo_name("OrgA/prod-app")` [1](#0-0)  and calls `stack.sync_github(expected_head_sha: "deadbeef")` on `OrgA`'s stack, despite the attacker never having proven any relationship to `OrgA`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
