### Title
CCMenu-minted `ApiClient` has no `stack_id`, granting `read:stack` across *all* stacks - (File: app/controllers/shipit/ccmenu_url_controller.rb)

### Summary
`CCMenuUrlController#fetch` mints an `ApiClient` with `read:stack` permission but never assigns `stack_id`, and it deduplicates purely on `creator`+`name`, so the same client is reused for every stack a user requests a CCMenu URL for. `Api::BaseController#stacks` treats an absent `stack_id` as "unrestricted", so the resulting token can be replayed against `Api::TasksController#index`/`#show` for any stack in the installation, not just the one it was generated for.

### Finding Description
Binding claimed to hold: `current_api_client.stack_id == stack.id` for any action gated only by `require_permission :read, :stack`.

Trace:
- `CCMenuUrlController#fetch` builds the client via
`ApiClient.create_with(permissions: %w[read:stack]).find_or_create_by!(creator: current_user, name: 'CCMenu Client')` [1](#0-0)  — no `stack:`/`stack_id:` attribute is ever set, and the lookup key (`creator`, `name`) is stack-independent, so the very same `ApiClient` row (and thus the same `authentication_token`) is returned/reused for every stack the user calls `fetch` on.
- `Api::BaseController#stacks` resolves the client's authorized stack set as:
`current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all` [2](#0-1) . Because `stack_id` is `nil`, `stack_id?` is `false`, so the guard resolves to `Stack.all` instead of restricting to the originating stack.
- `Api::TasksController` only gates via `require_permission :read, :stack` for `index`/`show` [3](#0-2) , which calls `require_permission!` → `current_api_client.check_permissions!(:read, :stack)` [4](#0-3) , `check_permissions!` only checks the `permissions` array, never `stack_id` [5](#0-4) . The actual stack scoping for the request happens through `stack` → `stacks.from_param!(params[:stack_id])` [6](#0-5) , which is exactly the `stacks` method broadened to `Stack.all` above.

So the equality the question asks about does not hold before the request even starts: `current_api_client.stack_id` is `nil`, not the ID of the stack the CCMenu URL was generated for. The permission model conflates "no stack restriction configured on this client" with "any stack", which is only safe for clients explicitly created without a stack (e.g. admin/service tokens), but `CCMenuUrlController` unintentionally mints such an unrestricted token while presenting it to the user as scoped to one specific stack/build-radiator URL.

Attacker flow: A user authorized to view Stack A's CCMenu URL calls `GET /stacks/:owner/:repo/:env/ccmenu.json` (routed to `fetch`), obtaining a token bound to an `ApiClient` with `stack_id: nil`. That token is then replayed via HTTP Basic-Auth against `GET /api/stacks/:other_owner/:other_repo/:other_env/tasks` (`Api::TasksController#index`) or `#show`, for a stack the user was never authorized on. `require_permission!(:read, :stack)` passes because the permissions array contains `read:stack`; `stacks` resolves to `Stack.all` because `stack_id` is nil; `stack.tasks` returns the unrelated stack's tasks.

No existing guard prevents this: `require_permission!` never compares `stack_id`; the `stacks` helper's `nil`-means-`Stack.all` fallback is the actual root cause and is not overridden anywhere in `TasksController`.

### Impact Explanation
The reused, stack-unbound CCMenu token allows an attacker who already has (or transiently had) legitimate read access to one stack to read task lists and task detail/output metadata for every other stack hosted on the same Shipit instance, including stacks belonging to unrelated repositories/teams/organizations they are not authorized on. This is a cross-tenant confidentiality break — unauthorized read of stack state/task data for repositories the token holder never authenticated against — matching the High-severity category ("unauthenticated/escalated read of stack state, task streams or deploy output"). It is repeatable indefinitely: the token is a long-lived signed ID (`ApiClient.authentication_token`), not a one-time credential, and works against arbitrary `stack_id` values in the URL with no additional secrets.

### Likelihood Explanation
Preconditions: the attacker only needs to be a Shipit user permitted to view/generate the CCMenu URL for at least one stack (a normal, low-privilege capability many CI-integration users have) and to know or enumerate another stack's `owner/repo/environment` path. No GitHub secrets, `api_clients_secret`, or admin role is required. The attack cost is a single authenticated request to mint the token plus one Basic-Auth request per victim stack — trivially feasible and fully repeatable.

### Recommendation
Set `stack: stack` (or `stack_id: stack.id`) when creating/finding the CCMenu `ApiClient` in `CCMenuUrlController#client`, and include the stack in the `find_or_create_by!` lookup keys so a distinct, stack-bound client/token is minted per stack. Additionally, treat `stack_id` as a hard restriction in `Api::BaseController#stacks`/`require_permission!` — if `stack_id` is set, require it to equal `params[:stack_id]`'s resolved stack for every `:stack`-scoped permission check, rather than only using it to build a lookup scope.

### Proof of Concept
```ruby
test "a ccmenu token for stack A cannot read stack B's tasks" do
  stack_a = shipit_stacks(:shipit)
  stack_b = shipit_stacks(:cyclimse) # a different stack/repo
  user = shipit_users(:walrus)

  # mint token for stack A via CCMenuUrlController#fetch
  session[:user_id] = user.id
  get :fetch, params: { stack_id: stack_a.to_param }
  token = ApiClient.last.authentication_token
  client = ApiClient.last

  assert_nil client.stack_id # binding is already broken here: not bound to stack_a.id

  # replay against TasksController#index for stack B
  @request.env['HTTP_AUTHORIZATION'] = ActionController::HttpAuthentication::Basic.encode_credentials(token, '')
  get :index, params: { stack_id: stack_b.to_param } # Api::TasksController

  assert_response :ok
  # FAIL expected: attacker should get :forbidden/:not_found, but gets stack_b's tasks
  refute_empty JSON.parse(response.body)
end
```
This demonstrates `current_api_client.stack_id` (`nil`) diverging from `stack.id` (`stack_b.id`) while `require_permission :read, :stack` still passes.
