## Analog Finding

### Title
Zero `issue_amount` in `aa_composer.js` `issueAsset()` can produce an invalid `type=issue` input, breaking AA-generated payment messages - (File: aa_composer.js)

### Summary
The reported bug pattern is: an internally-computed amount that can be legitimately `0` is passed unguarded into logic that requires a strictly positive value, causing failure. `BaseLSTAdapter.prefundedDeposits()` computes `stakeAmount` that can be `0` and passes it to `_stake()`, which reverts because the external minter rejects zero. The equivalent computed-amount pattern exists in ocore's AA payment-composition code, where `issue_amount` for a self-issued, uncapped asset can become `0` and is fed into a `type: "issue"` input that ocore's own `validatePaymentInputsAndOutputs()` requires to be strictly positive.

### Finding Description
When an AA composes an outgoing payment message for a non-base asset it owns, `sendUnit()`'s inner `completePaymentPayload()` first tries to satisfy `target_amount` from the AA's own unspent outputs via `iterateUnspentOutputs()`. It only sets `bFound = true` when either:
- `total_amount === target_amount && payload.outputs.length > 0`, or
- `change_amount > 0` [1](#0-0) 

If `payload.outputs.length === 0` (no outputs pending yet, e.g. only implicit change/fee coverage is needed) and the accumulated `total_amount` lands *exactly* equal to `target_amount`, neither branch fires, so `bFound` stays `false` even though funds are sufficient. Once stable and unstable-AA outputs are exhausted without setting `bFound`, `issueAsset()` is invoked as a fallback: [2](#0-1) 

Inside `issueAsset()`, for an uncapped asset (`objAsset.cap` falsy), the issue amount is computed as:

```js
var issue_amount = objAsset.cap || (target_amount - total_amount);
``` [3](#0-2) 

Since `total_amount === target_amount` in this edge case, `issue_amount` evaluates to `0`, and `addIssueInput()` unconditionally pushes `{ type: "issue", amount: 0, serial_number }` into `payload.inputs`: [4](#0-3) 

Notably, the near-identical wallet-side composer function for the same purpose (`issueAsset()` in `inputs.js`) explicitly guards against this exact zero case with a `|| 1` fallback and an accompanying comment:

```js
var issue_amount = objAsset.cap || (required_amount - total_amount) || 1; // 1 currency unit in case required_amount = total_amount
``` [5](#0-4) 

The AA-composer equivalent lacks this guard, meaning the same class of edge case that ocore developers already recognized and patched in the wallet composer is unaddressed in the AA composer.

A `type: "issue"` input with `amount: 0` violates ocore's own core validation, which requires issue amounts to be strictly positive: [6](#0-5) 

### Impact Explanation
If the AA-generated unit is subsequently checked against `validatePaymentInputsAndOutputs` (as any unit destined for the DAG must be), a zero-amount issue input renders that unit invalid ("amount must be positive"). Since AA response-unit composition is expected to always produce a unit that will pass core validation, hitting this edge case breaks the AA's ability to complete its trigger response for the affected uncapped self-issued asset under this specific balance condition — a Denial-of-Service against that AA's payment/issuance path, forcing it into an unexpected failure/bounce state rather than the successful payment it was supposed to construct. This impacts any AA author or user of an AA that self-issues an uncapped asset when the AA's held balance for that asset lands exactly on the required send amount with no explicit change/output entries yet queued.

### Likelihood Explanation
This requires a specific but reachable state: an AA sending an uncapped, self-issued asset where its currently-owned unspent outputs sum to exactly the payment's `target_amount` while `payload.outputs.length === 0` at that point in the iteration. This is a state the AA author does not fully control moment-to-moment (it depends on prior AA responses/change outputs), making it a plausible but not trivially triggerable edge case — consistent with the Medium severity of the original report, which likewise depended on `availableETH` landing at a value producing `stakeAmount == 0`.

### Recommendation
Add the same `|| 1` (or an explicit check that forces `issue_amount` to be at least 1) fallback in `aa_composer.js`'s `issueAsset()`, matching the guard already present in `inputs.js`:

```js
var issue_amount = objAsset.cap || (target_amount - total_amount) || 1;
```

Alternatively, fix the root cause by adjusting the `bFound` condition in `iterateUnspentOutputs()` to also treat `total_amount === target_amount` as found regardless of `payload.outputs.length`, avoiding an unnecessary call to `issueAsset()` altogether.

### Proof of Concept
Conceptual reproduction (not executed, since the exact trigger requires precise unspent-output states):
1. Deploy an AA that defines an uncapped, `issued_by_definer_only` asset and, in a later trigger case, sends a payment message in that asset without pre-populating `payload.outputs` (relying purely on inputs/change accounting), where `target_amount` is set to a value that exactly matches the AA's currently owned unspent output total for that asset (no dust/change is left over).
2. Trigger this AA response path when the AA has no unspent outputs of that asset (`total_amount` starts at 0) and `target_amount` also computes to 0 for the branch requiring an issue, OR trigger the path via secondary triggers/complex multi-message flows so that the loop in `iterateUnspentOutputs` exits with `total_amount === target_amount` and `payload.outputs.length === 0`.
3. `issueAsset()` is called, computes `issue_amount = target_amount - total_amount = 0`, and pushes a `type:"issue", amount:0` input.
4. The generated unit fails `validatePaymentInputsAndOutputs`'s `isPositiveInteger(input.amount)` check for issue inputs, causing the AA's payment message construction/execution to fail unexpectedly for this trigger.
