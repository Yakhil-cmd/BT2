### Title
Uncaught exception in `definition template` authentifier evaluation crashes validation instead of failing gracefully - (File: definition.js)

### Summary
This is the ocore analog of the reported "safe transfer to ERC-721/fallback contract" bug class: a secondary/fallback code path assumes a specific return format from an external construct (in the Solidity report, an ABI-encoded `bytes4` selector from a receiver's fallback function; here, a `params` object satisfying the variable names referenced by a `definition_template` unit), and when that assumption is violated, the code throws instead of gracefully failing. In ocore, this throw happens inside an asynchronous DB-query callback in `Definition.validateAuthentifiers()`'s `definition template` handler, so it cannot be caught by any surrounding try/catch, resulting in an uncaught exception during unit validation.

### Finding Description
`Definition.js` implements the `'definition template'` address-definition operator, which lets an address's spending condition reference a previously posted `definition_template` unit and fill it in with caller-supplied `params`: [1](#0-0) 

```
case 'definition template':
    // ['definition template', ['unit', {param1: 'value1'}]]
    var unit = args[0];
    var params = args[1];
    conn.query(
        "SELECT payload FROM messages JOIN units USING(unit) \n\
        WHERE unit=? AND app='definition_template' AND main_chain_index<=? AND +sequence='good' AND is_stable=1",
        [unit, objValidationState.last_ball_mci],
        function(rows){
            if (rows.length !== 1)
                throw Error("not 1 template");
            var template = rows[0].payload;
            var arrTemplate = JSON.parse(template);
            var arrFilledTemplate = replaceInTemplate(arrTemplate, params);
            evaluate(arrFilledTemplate, path, cb2);
        }
    );
    break;
```

`replaceInTemplate()` walks the stored template and, for every string that starts with `$`, requires the corresponding key to exist in the caller-supplied `params`: [2](#0-1) 

```
function replaceInTemplate(arrTemplate, params){
	function replaceInVar(x){
		switch (typeof x){
			...
			case 'string':
				if (x.charAt(0) !== '$')
					return x;
				var name = x.substring(1);
				if (!ValidationUtils.hasOwnProperty(params, name))
					throw new NoVarException("variable "+name+" not specified, template "+JSON.stringify(arrTemplate)+", params "+JSON.stringify(params));
				return params[name];
			...
			default:
				throw Error("unknown type");
		}
	}
	return replaceInVar(_.cloneDeep(arrTemplate));
}

function NoVarException(error){
	this.error = error;
	this.toString = function(){
		return this.error;
	};
}
```

Just like the Solidity report where `_doSafeTransferAcceptanceCheck` assumes the fallback call's success implies a decodable `bytes4` response and blows up when it doesn't, here the code assumes that `params` supplied by the unit author always satisfies every `$name` reference inside the referenced (attacker/author-controlled-lookup) template, and that the template itself only contains the expected JS types (`number`, `boolean`, `string`, `object`). Neither assumption is validated before use: if a key is missing, `NoVarException` is thrown; if the template contains an unexpected type (e.g., due to a template with nested arrays/objects producing `undefined`, or any type not covered by the switch), a generic `Error("unknown type")` is thrown.

Critically, both throws occur **inside the `conn.query` callback**, i.e., in an asynchronous context. Unlike other branches of `validateAuthentifiers`/`validateDefinition` that wrap risky operations in `try { ... } catch (e) { return cb2(false); }` (e.g. the `'address'` case at [3](#0-2) ), the `'definition template'` branch has no `try/catch` around `replaceInTemplate`/`evaluate`. An exception thrown here cannot be caught by `validateAuthentifiers`'s caller (`validateAuthor` in `validation.js`), because the throw happens on a different tick of the event loop than the original synchronous call. This produces a genuine uncaught exception.

### Impact Explanation
Any unprivileged party can post a unit whose author uses an address definition containing `['definition template', [unit_of_existing_template, params]]`, where `params` deliberately omits a variable name referenced by the template (or the template itself contains a value type outside the switch's four cases, e.g. `undefined`/`null`). When any full node subsequently validates a unit signed by this address (including the original posting unit itself, or any other unit spending from that address), `Definition.validateAuthentifiers` will throw an uncaught exception from inside the DB-query callback. Because this is a genuine Node.js uncaught exception in an async callback, it is not caught by `validateAuthor`'s or `validation.validate`'s error-handling logic and can crash the node process (or at minimum leave the mutex/connection state corrupted), preventing that node from validating further units — i.e., disagreement/inability to confirm new units, matching the "network unable to confirm new units" impact category.

### Likelihood Explanation
Likelihood is high for any full node that processes DAG history containing such a unit: the trigger condition (author-controlled `params` not matching the template's `$name` references) is entirely within the control of the unit's author and requires no special privileges — only that a `definition_template` unit already exists on the DAG (which is a normal, permissionless `definition_template` app message) and that the attacker crafts an address using it with mismatched params. This authentifier-evaluation code path is exercised every time such an address signs any unit, so the crash is deterministic and repeatable across all nodes that see the unit.

### Recommendation
Wrap the `replaceInTemplate`/`evaluate` call in the `'definition template'` branch of `validateAuthentifiers` in a `try/catch`, mirroring the pattern already used elsewhere in the same function (e.g. the `'address'`/`ifDefinitionNotFound` branch), and resolve `cb2(false)` (or propagate a proper validation error) instead of allowing exceptions such as `NoVarException`/`Error("unknown type")` to escape the async callback:

```js
conn.query(..., function(rows){
    try {
        if (rows.length !== 1)
            throw Error("not 1 template");
        var template = rows[0].payload;
        var arrTemplate = JSON.parse(template);
        var arrFilledTemplate = replaceInTemplate(arrTemplate, params);
    }
    catch (e) {
        return cb2(false);
    }
    evaluate(arrFilledTemplate, path, cb2);
});
```
Additionally, `replaceInTemplate` should be reviewed to ensure `NoVarException` and the generic `"unknown type"` error can never be thrown from a context that is not guarded by a synchronous try/catch, applying the same principle as the safe-transfer fix in the external report: never assume a fallback/fill-in path succeeds with the expected shape without validating first and handling the failure gracefully rather than throwing.

### Proof of Concept
1. Post a `definition_template` unit `T` defining a template array containing `"$missing_var"` at some position, e.g. `['sig', {pubkey: '$missing_var'}]`.
2. Create an address definition `D = ['definition template', [T, {other_var: 'value'}]]` (note: `other_var` does not satisfy `$missing_var`).
3. Post/attempt to spend from an address using definition `D` (or from a unit that references `D` inline for signature checking).
4. During `Definition.validateAuthentifiers`, evaluation reaches the `'definition template'` case, calls `replaceInTemplate(arrTemplate, params)`, which throws `NoVarException("variable missing_var not specified...")` from inside the `conn.query` callback.
5. Because there is no try/catch around this call, the exception is uncaught in the async callback and surfaces as an uncaught exception at the process level instead of a graceful `cb(err)`/`cb2(false)`, unlike the analogous `'address'` case which is defensively wrapped.

function replaceInTemplate(arrTemplate, params){
	function replaceInVar(x){
		switch (typeof x){
			case 'number':
			case 'boolean':
				return x;
			case 'string':
				// searching for pattern "$name"
				if (x.charAt(0) !== '$')
					return x;
				var name = x.substring(1);
				if (!ValidationUtils.hasOwnProperty(params, name))
					throw new NoVarException("variable "+name+" not specified, template "+JSON.stringify(arrTemplate)+", params "+JSON.stringify(params));
				return params[name]; // may change type if params[name] is not a string
			case 'object':
				if (Array.isArray(x))
					for (var i=0; i<x.length; i++)
						x[i] = replaceInVar(x[i]);
				else
					for (var key in x)
						assignField(x, key, replaceInVar(x[key]));
				return x;
			default:
				throw Error("unknown type");
		}
	}
	return replaceInVar(_.cloneDeep(arrTemplate));
}

function NoVarException(error){
	this.error = error;
	this.toString = function(){
		return this.error;
	};
}
