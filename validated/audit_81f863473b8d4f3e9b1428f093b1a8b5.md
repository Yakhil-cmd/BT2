### Title
Webhook signature is verified against `repository.owner.login`, but handlers act on the independently-controlled `repository.full_name` field, enabling cross-organization/cross-repository webhook forgery - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App / `webhook_secret` to validate a delivery against using `repository_owner`, which is read from `params.dig('repository', 'owner', 'login')`. Every event handler, however, determines *which repository/stacks to mutate* using a completely different JSON field, `payload.dig('repository', 'full_name')` (`Handler#repository_name`). These two fields are never checked for consistency, so an attacker who legitimately owns/administers **any** GitHub organization configured in Shipit's multi-org `github:` secrets block (and therefore knows that organization's own `webhook_secret`) can compute a valid HMAC over an arbitrary payload and set `repository.full_name` to a **different** organization's `owner/repo`, causing Shipit to apply the webhook to stacks it does not actually own.

### Finding Description
- `app/controllers/shipit/webhooks_controller.rb` line 25-29 and 59-61: signature verification picks the GitHub App config via `repository_owner`, which resolves to `params.dig('repository', 'owner', 'login')`. [1](#0-0) [2](#0-1) 
- `app/models/shipit/webhooks/handlers/handler.rb`: the base handler resolves the target repository/stacks using `payload.dig('repository', 'full_name')`, a sibling field of `repository.owner.login` inside the same JSON body, unrelated to the field used for authentication. [3](#0-2) 
- Concrete handlers act purely on this untethered `full_name`-derived scope: `PushHandler#process` triggers `stack.sync_github(expected_head_sha: params.after)` for every non-archived stack matching the branch. [4](#0-3) 
- `StatusHandler#process` writes a commit status to **any** commit row matching `params.sha` globally (`Commit.where(sha: params.sha)`), with no repository scoping at all beyond what a forged `full_name` implied. [5](#0-4) 

Because HMAC covers the whole raw body, an attacker cannot forge a payload *without* knowing some org's `webhook_secret` — but the multi-org configuration documented in `config/secrets.development.shopify.yml` is explicitly designed to let each organization onboard its own GitHub App with its own independent `webhook_secret`, meaning knowledge of one org's own webhook secret is not a "privileged" credential relative to Shipit as a whole — it is the normal, low-privilege trust level of "an org that installed the Shipit GitHub App for its own repos." That org admin never needs write access to, or any credential belonging to, the victim organization/repository whose stacks get mutated. [6](#0-5) 

The equality that should hold and is broken:
`repository_owner` (org whose secret authenticated the delivery) `==` owner component of `repository.full_name` (repo whose stacks are actually written to).

Note that `MembershipHandler` is *not* affected the same way, because for that event `repository_owner` falls back to `params.dig('organization','login')`, which is the exact same field the handler subsequently uses (`params.organization.login`) — auth and action are bound to the same value there. [2](#0-1) [7](#0-6) 

### Impact Explanation
This is a cross-repository write: an attacker who legitimately controls only their own organization's Shipit GitHub App installation can:
- Force `sync_github` (push handler) against any other organization's stacks that share a matching branch name, causing Shipit to fetch/record an attacker-chosen `expected_head_sha` for a repository they don't own.
- Inject a forged commit status (`create_status_from_github!`) for any commit SHA present in Shipit's `commits` table across all repositories (`Commit.where(sha: params.sha)` is not scoped by repository at all), which can flip a required CI check to "success" and enable an unauthorized deploy of a repository the attacker has no access to.

Both outcomes match the "cross-repository writes" / "unauthorized deploy" Critical impact bucket, since they subvert the org-to-repo binding that the webhook signature is supposed to enforce.

### Likelihood Explanation
Requires only that Shipit be configured for more than one GitHub organization (the multi-org configuration is a documented, supported deployment pattern) and that the attacker be an administrator of any one of those onboarded, otherwise-unprivileged organizations — no access to Shipit itself, no `ApiClient` token, and no credentials belonging to the victim organization are needed. This is a moderate-likelihood, architecture-level flaw rather than a one-off bug.

### Recommendation
Bind the field used to authenticate the delivery to the field used to select the mutated resource: after `verify_signature` succeeds, derive `repository_name`/stack scoping from the exact same trusted field (`organization.login`/`repository.owner.login`) used to pick the webhook secret, and reject any event where `repository.full_name`'s owner component does not match `repository_owner`.

### Proof of Concept
1. Attacker administers GitHub organization `orgA`, which is configured in Shipit's `github:` secrets as `somegithuborg` with a known `webhook_secret_A` (a normal, low-privilege setup step for onboarding their own org).
2. Attacker crafts a `push` webhook JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "orgA" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(webhook_secret_A, body)>` and POSTs to `/webhooks` with `X-Github-Event: push`.
4. `WebhooksController#verify_signature` resolves `repository_owner` = `"orgA"`, fetches `Shipit.github(organization: "orgA")`, and successfully verifies the signature (attacker legitimately knows `webhook_secret_A`). [1](#0-0) 
5. `PushHandler` is invoked; `Handler#repository_name` reads `payload.dig('repository','full_name')` = `"victim-org/victim-repo"`, and `stacks` resolves to that victim repository's stacks — completely disjoint from the `orgA` identity that passed signature verification. [3](#0-2) [4](#0-3)
