### Title
Webhook signature verification selects the signing organization from `repository.owner.login`, but the payload fields actually acted upon (`repository.full_name`, `sha`) are never bound to that organization - allowing cross-tenant status/push forgery - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`Shipit::WebhooksController#verify_signature` picks *which* GitHub App/organization secret to use for HMAC verification based on `params.dig('repository', 'owner', 'login')` (or `organization.login`), then verifies the raw body against that org's `webhook_secret`. Once verification passes, the handlers (`PushHandler`, `StatusHandler`, etc.) act on *other, unbound* fields of the same JSON body - `repository.full_name` for `PushHandler`, and just `sha` (with no repository scoping at all) for `StatusHandler`. Nothing ties the org whose secret validated the signature to the repository/commit that is actually written to.

### Finding Description [1](#0-0) 

`verify_signature` resolves the signing organization purely from `repository.owner.login`:
```
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```
and verifies `X-Hub-Signature` against `Shipit.github(organization: repository_owner).webhook_secret`. This only proves "whoever holds the secret for `repository_owner` sent this exact byte string" - it says nothing about the other fields inside that same byte string.

Downstream, `Shipit::Webhooks::Handlers::Handler#repository_name` and `#stacks` resolve the target using an *independent* field: [2](#0-1) 
```
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
```
`PushHandler#process` then calls `stack.sync_github(expected_head_sha: params.after)` for every matching stack, using attacker-controlled `after`/`ref`. [3](#0-2) 

Even more directly, `StatusHandler#process` doesn't consult the repository at all - it looks up commits *globally* by `sha` and materializes a CI status from unvalidated fields: [4](#0-3) 
```
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```

Equality that should hold but doesn't: `organization_that_authenticated(repository.owner.login) == organization_that_is_written_to(repository.full_name / sha lookup)`. The controller only checks that the *bytes* of the payload were signed by *some* configured organization's secret; it never checks that `repository.owner.login` matches the owner embedded in `repository.full_name`, nor that the `sha` referenced belongs to a commit/stack owned by that organization at all.

In a Shipit deployment that hosts multiple organizations (multi-tenant `Shipit.github` config, as documented in `docs/setup.md` and exercised by `test/dummy/config/secrets_double_github_app.yml`), any organization admin who legitimately controls a GitHub App / webhook secret for **their own** onboarded org can POST a hand-crafted JSON body directly to `/github/webhooks` (bypassing real GitHub) with:
- `repository.owner.login` = their own org (so the correct, known secret is selected and HMAC verification passes), and
- `repository.full_name` = a victim org/repo tracked in the same Shipit instance, and/or
- `sha` = any commit sha that exists in any stack, with `state: "success"`.

Because the signature only covers "did this org's secret produce this HMAC," and the handlers key off unrelated fields, the forged webhook is accepted and acted on for the victim's stack.

### Impact Explanation
This crosses the "organization that authenticated versus the repository that is written" trust boundary explicitly called out as in-scope. Concretely:
- `StatusHandler` lets the attacker fabricate a `success` CI status for an arbitrary commit sha on any tracked repository (there is no repository filter at all in `Commit.where(sha: params.sha)`), which can satisfy `deployable?`/status-check requirements and cause `continuous_deployment` stacks to auto-deploy a commit that never actually passed real CI/tests - an **unauthorized deploy**.
- `PushHandler` lets the attacker trigger `GithubSyncJob`/`stack.sync_github` for a victim stack with an attacker-chosen `expected_head_sha`, forcing Shipit to treat an arbitrary sha as the head of a branch it tracks for a repository the attacker does not control.

Both map to the required High/Critical impact bucket ("unauthorized deploy" / cross-repository write) without needing any Shipit session, `ApiClient` token, GitHub App private key, or repository write access on the victim's repository - only a legitimate webhook secret for *some* other org already onboarded to the same Shipit instance.

### Likelihood Explanation
Requires a multi-organization Shipit deployment (a supported, documented configuration - see `docs/setup.md` and `secrets_double_github_app.yml`) where the attacker is a legitimate owner/admin of one onboarded org (and thus knows/controls that org's webhook secret) but not of the victim org. This is a realistic "shared instance" scenario (e.g., a company-wide Shipit install used by many teams/orgs) and requires no interception, no privileged Shipit account, and no compromise of the victim - only crafting a raw HTTP POST with a valid HMAC for the attacker's own org.

### Recommendation
Bind the organization used for signature verification to the same field(s) the handlers act on: verify that `repository.owner.login` (used to select the secret) matches the owner parsed out of `repository.full_name`, and scope `StatusHandler`'s `Commit.where(sha: ...)` lookup to commits belonging to stacks/repositories owned by the verified `repository_owner`. Reject the webhook if these do not match.

### Proof of Concept
1. Shipit instance configured with two organizations, `attacker-org` (attacker is the GitHub App/org admin, knows `webhook_secret_A`) and `victim-org` (has a stack with `continuous_deployment: true` and a commit `deadbeef` awaiting a passing "ci/travis" status).
2. Attacker computes `sha1=` HMAC of a crafted JSON body using `webhook_secret_A`:
```json
{
  "sha": "deadbeef",
  "state": "success",
  "context": "ci/travis",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" }
}
```
3. POST this body to `/github/webhooks` with header `X-Github-Event: status` and the computed `X-Hub-Signature`.
4. `verify_signature` resolves `repository_owner` = `attacker-org`, validates the HMAC against `webhook_secret_A` successfully.
5. `StatusHandler#process` runs `Commit.where(sha: 'deadbeef')` (no ownership check) and creates a `success` status for `victim-org`'s commit, potentially satisfying `deployable?` and triggering `ContinuousDeliveryJob`/`trigger_continuous_delivery` for `victim-org`'s stack - an unauthorized deploy of a commit that never received a real passing CI status from GitHub.

      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(

        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([

    rescue Shipit::GithubOrganizationUnknown => e

        "status=#{status}"
      ].join(' '))
    end
