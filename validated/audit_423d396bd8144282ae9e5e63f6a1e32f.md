### Title
Uncaught-exception DoS via unvalidated `authentifiers` type in `in merkle` address-definition condition - (File: definition.js)

### Summary
`definition.js`'s `validateAuthentifiers()` evaluates the `in merkle` opcode by taking the attacker-supplied per-path authentifier value straight out of `assocAuthentifiers[path]` and passing it to `merkle.deserializeMerkleProof()` without verifying that it is a string, unlike the sibling `hash` opcode handler which explicitly checks `typeof assocAuthentifiers[path] !== 'string'` before use. This is the same bug class as CVE-2025-63650 (`mk_ptr_to_buf` in monkey doing pointer/buffer arithmetic on attacker data without a bounds/type check): a value coming straight from a network-supplied unit is fed into a parsing routine that assumes a particular shape, and an unexpected shape can crash the process (denial of service) rather than being rejected as invalid input.

### Finding Description
In `definition.js`, the `evaluate()` function used by `validateAuthentifiers()` handles `case 'in merkle'`: [1](#0-0) 

The only guard is a truthiness check (`!assocAuthentifiers[path]`), which passes for any non-falsy value — including a number, boolean `true`, or object — not just strings. Compare this to the adjacent `hash` opcode handler, which explicitly requires `typeof assocAuthentifiers[path] === 'string'`: [2](#0-1) 

`merkle.deserializeMerkleProof()` assumes a string and calls `.split("-")` on it directly with no type check and no surrounding `try/catch`: [3](#0-2) 
```
function deserializeMerkleProof(serialized_proof){
	var arr = serialized_proof.split("-");
	...
}
```
If `assocAuthentifiers[path]` is, e.g., a JSON number or object (both are valid JSON values that can appear at an authentifier path since `authentifiers` values are arbitrary JSON taken from the posted unit), `serialized_proof.split` throws a `TypeError: serialized_proof.split is not a function`. This call happens inside the `evaluate()` callback chain invoked from `validateAuthentifiers()`, which itself is invoked deep in `validateAuthor`/unit validation — none of the wrapping code paths in this branch install a `try/catch` around the `deserializeMerkleProof` call (unlike the `address` case a few lines above at lines 774–800 in `definition.js`, and unlike the `is_valid_merkle_proof` oscript evaluator in `formula/evaluation.js`, lines 1785–1804, which does wrap similar deserialization/verification in `try/catch`). An uncaught exception thrown synchronously inside validation logic that is not caught anywhere up the call stack will propagate as an uncaught exception; per `network.js`'s global handler, uncaught exceptions are treated as fatal and the process is deliberately crashed: [4](#0-3) 

### Impact Explanation
Any unprivileged unit author can define (or already control) an address whose definition contains an `in merkle` condition at some authentifier path, then post a unit whose `authentifiers` object supplies a non-string (e.g., a number or object) value at that path. When another node validates that unit, `validateAuthentifiers()` reaches the `in merkle` branch, calls `merkle.deserializeMerkleProof()` on the non-string value, and throws an uncaught `TypeError`. Given ocore's global `uncaughtException` handler intentionally re-throws to crash the process, this results in remote, unauthenticated denial-of-service against any full node (and potentially all validating nodes network-wide if the same crafted unit propagates), matching the "network unable to confirm new units" impact class for a High-severity finding, directly analogous to the OOB/DoS bug class in the reported CVE.

### Likelihood Explanation
Likelihood is high for any address whose definition includes an `in merkle` clause: constructing a matching unit with an `authentifiers` field whose value at the relevant path is a non-string JSON value (e.g., a plain number) requires no special privileges, keys, or race conditions — it is a single crafted unit sent by any ordinary user. The `in merkle` clause itself is a legitimate/uncommon oscript address-definition primitive but is a first-class supported opcode, and definitions with it can be authored and even self-referenced (definition + authentifiers can appear in the same unit).

### Recommendation
Add an explicit type check before calling `merkle.deserializeMerkleProof()` in the `in merkle` branch of `definition.js`, mirroring the `hash` branch: reject (`cb2(false)`) unless `typeof assocAuthentifiers[path] === 'string'`. Additionally, harden `merkle.deserializeMerkleProof()` itself to validate its input type/format and wrap the call site in `try/catch` returning `false` on failure, consistent with how `formula/evaluation.js`'s `is_valid_merkle_proof` handler already treats parsing/verification failures as a graceful `false` rather than letting exceptions propagate.

### Proof of Concept
1. Attacker creates address `A` with definition `['in merkle', [[oracle_address], 'feed', 'expected_value']]` at authentifier path `r`.
2. Attacker posts a unit authored by `A` with `authentifiers: { r: 12345 }` (a JSON number instead of the expected serialized-proof string).
3. During validation, `validateAuthentifiers()` reaches `case 'in merkle'`; `!assocAuthentifiers['r']` is `false` (12345 is truthy), so execution proceeds to `merkle.deserializeMerkleProof(12345)`.
4. `deserializeMerkleProof` executes `12345.split("-")`, throwing `TypeError: 12345.split is not a function`.
5. The exception is uncaught within the validation call chain and reaches the global `process.on('uncaughtException', ...)` handler in `network.js`, which re-throws to crash the node process — denial of service.
