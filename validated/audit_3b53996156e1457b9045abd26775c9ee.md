### Title
Single Stuck Bridge Request Permanently DoS-es All Subsequent Value Transfers — (`File: node/sc/bridge_manager.go`)

---

### Summary

`processingPendingRequestEvents()` in `node/sc/bridge_manager.go` processes the bridge's pending request queue sequentially. When `handleRequestValueTransferEvent()` fails for any single event at queue index `idx`, the function re-queues **all** events from `idx` onward — including the failing one — and returns. Because the failing event is always re-inserted at the front of the queue, it will be retried on every subsequent tick and will fail again, permanently blocking every bridge request that was submitted after it.

---

### Finding Description

`processingPendingRequestEvents()` iterates over the ready event slice and calls `handleRequestValueTransferEvent()` for each entry: [1](#0-0) 

On failure the entire tail of the slice — starting at the failing index — is re-inserted into `pendingRequestEvent`: [2](#0-1) 

`handleRequestValueTransferEvent()` calls the Go binding `bi.bridge.HandleKLAYTransfer(...)` (or the ERC20/ERC721 equivalents), which internally calls `Transact()`. `Transact()` performs gas estimation before submitting; if the simulated call reverts, it returns an error immediately — no transaction is ever sent. [3](#0-2) 

The on-chain `handleKLAYTransfer` performs the KLAY send **after** updating nonce state, and reverts the whole call if the send fails: [4](#0-3) 

Likewise, `handleERC20Transfer` in lock/unlock mode calls `safeTransfer` after updating nonce state, which reverts if the token's transfer logic fails (e.g., blacklisting): [5](#0-4) 

Because the failing event is always re-queued at the head, every subsequent call to `processingPendingRequestEvents()` — triggered either by a new event or by the one-second ticker in `bi.loop()` — hits the same failing event first and returns early, leaving all higher-nonce requests permanently unprocessed. [6](#0-5) 

The value-transfer recovery path (`vt_recovery.go`) re-fetches events whose nonce is `>= lowerHandleNonce`. Because the on-chain `lowerHandleNonce` never advances past the stuck nonce (the transaction always reverts), the recovery path re-injects the same failing event on every recovery cycle, providing no escape. [7](#0-6) 

---

### Impact Explanation

Any user who can submit a `RequestValueTransfer` event on the source bridge can permanently halt all cross-chain value transfers for every other user. The corrupted state is the bridge operator's in-memory `pendingRequestEvent` queue: the stuck event occupies the lowest nonce slot, and `processingPendingRequestEvents()` never advances past it. All KLAY, ERC20, and ERC721 bridge requests submitted after the malicious one are frozen indefinitely. Bridged assets on the destination chain remain locked in the bridge contract with no mechanism for users to retrieve them.

---

### Likelihood Explanation

The trigger requires only a standard, permissionless `requestKLAYTransfer` call on the child-chain bridge, directing the transfer to a contract address on the parent chain that has no payable fallback. Any user can deploy such a contract and submit the request. No special privilege, no majority-validator collusion, and no compromised key is required. The cost is a single transaction on the child chain.

---

### Recommendation

1. **Skip unprocessable events instead of re-queuing them at the head.** In `processingPendingRequestEvents()`, on error, log the failure and `continue` to the next event rather than re-inserting `ReadyEvent[idx:]` and returning. Separately track failed nonces so the recovery path can report them.

2. **Add a privileged "skip nonce" function** callable by the bridge owner/operator that advances `lowerHandleNonce` past a stuck nonce on the on-chain contract, mirroring the recommendation in the referenced report.

3. **Validate the recipient before queuing.** In `_requestKLAYTransfer`, consider rejecting transfers to contract addresses that cannot receive KLAY (e.g., by checking `extcodesize`), or at minimum document that such requests will permanently stall the bridge.

---

### Proof of Concept

**Setup:**

1. Deploy the service-chain bridge pair (child + parent).
2. On the parent chain, deploy a contract `Blocker` with no payable fallback:
   ```solidity
   contract Blocker { }  // rejects all KLAY sends
   ```

**Attack:**

3. On the child chain, call:
   ```solidity
   childBridge.requestKLAYTransfer{value: 1 ether}(address(Blocker), 1 ether - fee, "");
   // emits RequestValueTransfer with requestNonce = N
   ```
4. Submit a legitimate transfer immediately after:
   ```solidity
   childBridge.requestKLAYTransfer{value: 1 ether}(alice, 1 ether - fee, "");
   // emits RequestValueTransfer with requestNonce = N+1
   ```

**Observation:**

5. The bridge operator's `processingPendingRequestEvents()` dequeues nonce N first and calls `bi.bridge.HandleKLAYTransfer(...)`. Gas estimation simulates `Blocker.call.value(1 ether)("")`, which reverts. The binding returns an error.
6. `ReadyEvent[N:]` (containing both nonce N and N+1) is re-inserted into `pendingRequestEvent`.
7. On the next tick (≤1 second), step 5 repeats. Alice's transfer at nonce N+1 is never reached.
8. The on-chain `lowerHandleNonce` remains at 0 (or whatever it was before N). The recovery path re-fetches nonce N on every cycle and re-injects it, perpetuating the loop.

**Result:** Alice's KLAY is locked in the child bridge contract with no path to settlement.
