### Title
Webhook organization used for signature verification is decoupled from the repository the handlers act on, allowing cross-tenant forged webhooks - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/`webhook_secret` to validate an inbound webhook's HMAC against using the `repository_owner` field parsed straight out of the (unverified) JSON body. The event handlers that actually perform the state-changing work (creating review stacks, syncing branches, merging pull requests, etc.) key off a *different* field of the same body — `repository.full_name`. Nothing binds these two fields together, so a signature that is valid for organization A can be replayed with a body claiming to describe a repository belonging to organization B.

### Finding Description
`verify_signature` computes the organization used to pick the verifying `GithubApp` purely from attacker-supplied payload content: [1](#0-0) [2](#0-1) 

The signature check itself, `GitHubApp#verify_webhook_signature`, HMACs the *entire* raw body against the secret configured for whichever organization `repository_owner` happened to resolve to: [3](#0-2) 

Crucially, this only proves the request was signed by *some* configured organization's secret — it says nothing about whether the repository referenced elsewhere in the same body actually belongs to that organization. Downstream, every handler resolves the target `Repository`/`Stack` from a completely independent field, `repository.full_name`: [4](#0-3) 

For example `PushHandler` uses this to find stacks and immediately triggers a sync: [5](#0-4) 

and `PullRequest::OpenedHandler` uses `params.repository.full_name` to resolve the repository and then provisions/adapts review stacks: [6](#0-5) 

Shipit supports multiple GitHub organizations configured simultaneously, each with its own `webhook_secret`, exactly the scenario documented in `config/secrets.development.shopify.yml` and `docs/setup.md`. An operator (or anyone who can register/administer their own low-privilege organization pointed at the same Shipit instance — an ordinary, unprivileged setup action, not requiring any of the excluded credentials) legitimately knows the `webhook_secret` for their own organization. Because the webhook endpoint is a plain HTTP POST target (`WebhooksController#create`), nothing requires the request to actually originate from GitHub's servers; the attacker can POST directly: [7](#0-6) 

By setting `repository.owner.login` (or `organization.login`) to their own, legitimately-controlled organization while setting `repository.full_name` to a victim organization's tracked repository, the attacker produces a body whose HMAC — computed over the *whole* raw body — validates successfully against their own known secret, yet whose `repository.full_name` is trusted unconditionally by every handler to select the object being written to.

This mirrors the reported bug class exactly: a field that is acted upon (`repository.full_name`, analogous to the pool/gauge being voted on) is never covered by the check that is actually performed (`repository_owner`-keyed signature verification, analogous to the missing `isAlive[_gauge]` check before `_vote()` commits state). The verification binds "which secret validated this HTTP request" to "which org authenticated," but the code equates that with "which repository may be written to," which is a distinct, unchecked equality.

### Impact Explanation
An attacker who legitimately controls a benign/throwaway GitHub App+organization registered on the same Shipit instance can forge webhook events (`push`, `pull_request`, `status`, `check_suite`, etc.) that are processed as if they originated from any other organization's repositories tracked by that Shipit instance. Depending on which handler fires this can: force unwanted `stack.sync_github` syncs, fabricate `pull_request` merged/closed events driving review-stack provisioning/archival logic, or fabricate CI `status`/`check_suite` payloads that influence deploy-readiness gating (`ci.require`/`ci.blocking` statuses used to decide `deployable?`). Combined with `continuous_deployment`, this can result in an unauthorized deploy being triggered for a victim stack — falling under the accepted "unauthorized deploy" impact class.

### Likelihood Explanation
Likelihood is Medium: it requires the attacker to control at least one organization/GitHub App configured on the target Shipit instance (a normal, unprivileged onboarding action in multi-tenant Shipit deployments, not requiring any of the excluded credentials such as `webhook_secret` for the *victim* org, `api_clients_secret`, or repository write access to the victim repo), and requires that Shipit be configured for more than one organization (a documented, supported configuration per `docs/setup.md` and `config/secrets.development.shopify.yml`).

### Recommendation
After signature verification succeeds, re-derive the organization strictly from `repository.full_name` (or `organization.login` for org-scoped events) and confirm it matches the organization whose secret validated the signature (i.e., `repository_owner`). Reject the webhook if these diverge, so that the entity acted upon by handlers is always the same entity that was cryptographically authenticated.

### Proof of Concept
1. Configure Shipit with two organizations, e.g. `attacker-org` and `victim-org`, each with its own GitHub App and `webhook_secret` (multi-org config as shown in `config/secrets.development.shopify.yml`).
2. Attacker computes `sha1=HMAC(webhook_secret_of_attacker_org, body)` for a crafted JSON body:
   ```json
   {
     "ref": "refs/heads/main",
     "after": "<attacker-chosen sha already known to exist on victim repo>",
     "repository": { "full_name": "victim-org/victim-repo", "owner": { "login": "attacker-org" } }
   }
   ```
3. POST this body directly to `/github/webhooks` with header `X-Github-Event: push` and `X-Hub-Signature: sha1=<computed>`.
4. `verify_signature` resolves `repository_owner` to `"attacker-org"`, fetches `attacker-org`'s `GithubApp`, and validates the signature successfully (it was computed with that org's own secret) — see `app/controllers/shipit/webhooks_controller.rb:24-30,59-62` and `lib/shipit/github_app.rb:76-83`.
5. `Shipit::Webhooks.for_event('push')` dispatches to `PushHandler`, which resolves stacks via `payload.dig('repository','full_name')` = `"victim-org/victim-repo"` (`app/models/shipit/webhooks/handlers/handler.rb:36-38`) and calls `stack.sync_github(expected_head_sha: ...)` on the victim's stack (`app/models/shipit/webhooks/handlers/push_handler.rb:12-17`), even though the request was never authenticated for `victim-org`.

Note: I could not fully trace the exact downstream effect of a forged `pull_request` "closed"/merged event through `MergeRequest`/`merge_status` logic within the remaining investigation time (e.g., `closed_handler.rb`, `merge_request.rb`), so the strongest concretely-traced consequence I can assert with certainty is the forced `GithubSyncJob`/`sync_github` call and review-stack provisioning shown above; whether this chain can be extended all the way to an unauthorized deploy trigger via `continuous_deployment` would need further tracing of `Stack#sync_github` and `ContinuousDeliveryJob` before concluding Critical severity with full confidence.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
