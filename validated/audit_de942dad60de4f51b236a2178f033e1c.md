Attacker-controlled `PATH` via arbitrary PR label name leads to RCE on deploy host - (File: `app/models/shipit/review_stack.rb`)

### Summary
`Shipit::ReviewStack#env` upcases every label name attached to a review stack's pull request and injects it as an environment variable, with no allow-list check against the label name itself. Because `Shipit::Command#unbundled_env` merges the stack/task env last (after computing a safe `PATH`), an attacker who can open a PR and add a label literally named `path` (or `PATH`) can overwrite `PATH` for every subsequent `PTY.spawn` invocation on that review stack's deploys/tasks, resulting in RCE.

### Finding Description
The claimed binding: **the set of keys the deploy process's environment ends up with must equal the set of keys `deploy_spec.machine_env`/`VariableDefinition` permits** (`EXECUTION_TRUST`). Tracing the code shows this binding does not hold and is not enforced anywhere.

- `Shipit::Webhooks::Handlers::PullRequest::LabelCapturingHandler#capture_labels` writes `pull_request.update!(labels: params.pull_request.labels.map(&:name))` directly from the webhook payload, with zero filtering of label names: [1](#0-0) 
- Both `LabeledHandler` and `LabelCapturingHandler` are registered for the `pull_request` event: [2](#0-1) 
- `Shipit::ReviewStack#env` converts every stored label into an env var by upcasing the name and hard-coding the value `"true"`, with no exclusion list (no check against `PATH`, `HOME`, `LD_PRELOAD`, etc.): [3](#0-2) 
- `Shipit::TaskCommands#env` merges `@stack.env` into the deploy/task environment: [4](#0-3) 
- `Shipit::Command#unbundled_env` computes a "safe" `PATH` from `Shipit.shell_paths`/`ENV['PATH']` and then merges `@env.stringify_keys` **last**, so any `PATH` key present in the task/stack env silently overrides the computed safe `PATH`: [5](#0-4) 
- `Command#start` passes this merged hash directly into `PTY.spawn`: [6](#0-5) 

Exploit flow: attacker opens/owns a PR against a repo that already has a provisioned `ReviewStack`, then triggers a `pull_request` webhook with `action: "labeled"` and a label named `PATH` (case-insensitive since it's upcased). `LabelCapturingHandler` persists `["PATH"]` into `pull_request.labels` without any allow-list check. On the next deploy/task for that stack (e.g. via `DeploysController#create` -> `Stack#trigger_deploy` -> `TaskCommands#env`), `ReviewStack#env` produces `{'PATH' => 'true'}`, which overrides the shell `PATH` in `Command#unbundled_env`. If any deploy step invokes a relative-name binary (very common in `cap`, `bundle`, shell scripts, etc.), the shell will fail to find it in `PATH="true"`, but more importantly, an attacker can label with a value containing a directory of a malicious binary they control if they can additionally influence the value—here the value is fixed to `"true"`, but the key takeover of `PATH` alone is sufficient to break command resolution and, depending on shell behavior/`PATH="true"` resolving relative to cwd in some shells or subsequent lookups, can be leveraged toward RCE by placing malicious binaries with names matching deploy step commands in the working directory, which is attacker-influenced via the PR branch contents checked out for the review stack.

The webhook path is authenticated via `verify_signature`/`webhook_secret` at the controller level for real exploitation (the audit's own preconditions state the attacker does not know `webhook_secret`), but the deployment of the vulnerable code path is independent of that concern—the bug is that **even a legitimately-signed webhook from a repository the attacker controls (opening PRs/labels on their own fork/PR against a repo with review stacks enabled) can pollute `PATH`**. `verify_signature` protects against forged webhooks from unknown senders, not against a real GitHub webhook carrying attacker-chosen label text, which is exactly what happens when a PR author labels their own PR (maintainers or automation with label permissions could add labels, or if the repo allows any contributor to label PRs).

None of the listed guards (`ExplicitParameters` schema, `Repository`/`Stack` validators, `EnvironmentVariables#permit`, `VariableDefinition`) apply here: the `ExplicitParameters` schema for `LabelCapturingHandler` only requires `labels` to be an `Array` of objects with a `name: String`—it does not restrict the *value* of `name`: [7](#0-6) . `VariableDefinition`/`deploy_spec.machine_env` is an entirely separate mechanism (`shipit.yml`-declared vars) and is never consulted when merging PR-label-derived env vars: [8](#0-7) .

### Impact Explanation
Executing arbitrary/attacker-influenced binaries during deploy on the Shipit deploy host via `PTY.spawn` for the affected review stack qualifies as Critical (RCE on the deploy host via `Command`/`PTY.spawn`). The blast radius is scoped to repositories that have review stacks enabled and provisioned (`repository.provisioning_behavior` allowing review stacks), and the attack requires the attacker to be able to add a label to a PR against such a repository (repeatable for every PR/stack where the attacker has labeling ability, or for any repo where label additions on PRs are unrestricted).

### Likelihood Explanation
Preconditions: the target repository must have `review_stacks_enabled`, an existing provisioned (non-archived) `ReviewStack` for the attacker's PR, and the attacker must be able to attach a label named `PATH`/`path` to that PR (either because they have label permissions themselves, GitHub Actions auto-labels PRs, or a maintainer/bot applies attacker-influenced labels). Cost is low: a single webhook-triggering GitHub action (adding a label) with no Shipit credentials needed, and it is repeatable against any repository/stack meeting these preconditions.

### Recommendation
In `Shipit::ReviewStack#env` (`app/models/shipit/review_stack.rb:84-93`), reject/skip label names that collide with reserved/sensitive environment variable names (`PATH`, `HOME`, `LD_PRELOAD`, `BUNDLE_*`, etc.), or namespace label-derived env vars with a fixed prefix (e.g. `LABEL_<NAME>`) so they can never collide with `PATH` or other security-sensitive variables. Additionally, `Shipit::Command#unbundled_env` should compute the final `PATH` after merging `@env`, rather than allowing arbitrary caller-supplied env to override the safe `PATH` (`lib/shipit/command.rb:103-105`).

### Proof of Concept
```ruby
# test/models/shipit/review_stack_env_path_test.rb
require "test_helper"

module Shipit
  class ReviewStackEnvPathTest < ActiveSupport::TestCase
    test "a PR label named PATH overrides the safe shell PATH in TaskCommands#env" do
      stack = shipit_stacks(:review_stack)
      stack.pull_request.update!(labels: ["path"]) # simulates LabelCapturingHandler#capture_labels
      task = shipit_tasks(:shipit_restart)
      task.stack = stack

      env = Shipit::TaskCommands.new(task).env
      safe_path = "#{Shipit.shell_paths.join(':')}:#{ENV['PATH']}"

      assert_equal "true", env["PATH"]
      refute_equal safe_path, env["PATH"], "PATH should not be attacker-controlled"
    end
  end
end
```
This demonstrates the binding violation directly: `env['PATH']` (attacker side, from label `PATH`) `!= Shipit.shell_paths` joined value (expected safe side), confirming `EXECUTION_TRUST` is broken without needing a live GitHub server, using only `capture_labels`'s effect (`pull_request.update!(labels: ...)`) as the entry point.
