### Title
AA funds in a `spender_attested` asset can be frozen by the asset's definer at will - ([File: validation.js])

### Summary
Ocore's asset framework lets any asset definer make an asset's usability contingent on an externally-controlled, mutable attestor whitelist (`spender_attested` + `asset_attestors`). If an Autonomous Agent accepts or holds such a foreign asset as part of its logic (e.g. as collateral, a stability token, or a share/LP token, similar to how USSD accepted external tokens like WBGL/WBTC), the asset's definer can unilaterally revoke the AA's attested status at any time, effectively "pausing" that asset for the AA and freezing/blocking any of the AA's payment logic that depends on moving funds in that asset.

### Finding Description
Asset definitions carry a `spender_attested` flag; when true, an address must be present in the asset's live attestor list to be a valid input or output address for that asset [1](#0-0) . This attestor list is not fixed at asset creation — it is stored in a separate `asset_attestors` table and can be replaced at any later time by a new `asset_attestors` unit [2](#0-1) .

Validation of that update message enforces only that the sender be the original asset definer, with no cooldown, no timelock, no notice, and no restriction preventing removal of previously-attested addresses: [3](#0-2) 

During ordinary payment validation, if an asset requires attestation, both the payment author (for issues) and every output address must appear in the *current* attestor list, computed fresh against the current DAG state: [4](#0-3) [5](#0-4) 

Because the attestor list can be rewritten by the definer at any moment (a single-authored `asset_attestors` message, validated independently of any cooperation from holders), any address that was attested when it acquired the asset can later be de-attested, after which:
- it can no longer be a valid output address to receive the asset (blocking transfers *into* the address, e.g. blocking users from sending it to an AA), and
- more importantly, it can no longer be a valid output address for *outgoing* payments either, since `arrOutputAddresses` (which include change/destination outputs of the AA's own spend) are checked against `arrAttestedAddresses` for every payment of that asset.

If an AA's own address is de-attested, or all addresses the AA needs to pay out to are de-attested, the AA's held balance of that asset becomes unspendable through normal payment messages: `aa_composer.js`'s `sendDummyUnit`/response logic composes ordinary `payment` messages that go through the same `validatePaymentInputsAndOutputs` checks, so a bounced/blocked payment due to failed attestation freezes the AA's funds in that asset just like WBGL/WBTC being paused froze USSD's rebalancing mechanism [6](#0-5) .

### Impact Explanation
Any AA that integrates a `spender_attested` asset issued by a third party (e.g. as collateral, LP shares, or a stable-value token, mirroring the "WBGL/WBTC as collateral" scenario in the source report) is exposed to a single external actor — the asset's definer — being able to freeze that AA's holdings or block its stability/rebalancing operations in that asset at will, with no on-chain restriction preventing it. This is a direct AA fund-freezing vector reachable purely by posting standard `asset_attestors` units, matching the "AA fund loss or freezing" impact category.

### Likelihood Explanation
Likelihood depends on the AA's design: it is not exploitable against the base asset or against `is_transferrable`/non-attested assets, but for any AA that is designed to hold or process a `spender_attested` foreign asset, the asset's definer needs only to post one ordinary `asset_attestors` unit to trigger the freeze — no special privileges beyond being the original asset issuer, no complex conditions, and it is fully reachable through normal unit posting.

### Recommendation
- AAs should avoid conditioning on continued attested status of externally issued `spender_attested` assets for critical balances, or should treat such assets as trusted only if the definer is also trusted/immutable.
- Consider documenting/flagging in AA tooling or wallet UX that `spender_attested` assets carry a standing freeze risk, since attestor lists are mutable indefinitely by the definer with no protocol-level safeguard (e.g., no minimum grace period, no way to lock the list).
- For asset designs meant to be trustlessly held by AAs, prefer assets without `spender_attested`/mutable conditions, or require `attestors` to be fixed at asset creation (immutable) rather than updatable via `asset_attestors`.

### Proof of Concept
1. Definer creates asset X with `spender_attested: true`, `attestors: [AA_addr, alice]` [7](#0-6) .
2. AA is designed (e.g., a stability/market-maker AA) to hold and pay out asset X to users as part of its stability mechanism, similar to `test/samples/uniswap_like_market_maker.oscript` patterns that pay assets on divestment [8](#0-7) .
3. Users send asset X to the AA; AA holds balance in `aa_balances` for asset X.
4. Definer posts an `asset_attestors` unit removing `AA_addr` (and/or all its user counterparties) from the attestor list — this is accepted because only the definer's authorization is required [9](#0-8) .
5. Any subsequent AA response that tries to pay out asset X now fails `validatePaymentInputsAndOutputs`'s attestation check ("some output addresses are not attested") and the AA response bounces, permanently freezing the AA's asset-X balance until/unless the definer chooses to re-attest.

function validateAttestorListUpdate(conn, payload, objUnit, objValidationState, callback){
	if (objUnit.authors.length !== 1)
		return callback("attestor list must be single-authored");
	if (!isNonemptyObject(payload))
		return callback("attestor update must be a non-empty object");
	if (hasFieldsExcept(payload, ['asset', 'attestors']))
		return callback("foreign fields in attestor list update");
	storage.readAsset(conn, payload.asset, objValidationState.last_ball_mci, false, function(err, objAsset){
		if (err)
			return callback(err);
		if (!objAsset.spender_attested)
			return callback("this asset does not require attestors");
		if (objUnit.authors[0].address !== objAsset.definer_address)
			return callback("attestor list can be edited only by definer");
		err = checkAttestorList(payload.attestors);
		if (err)
			return callback(err);
		callback();
	});
}
