### Title
Unallowlisted swap routes can attach unauthorized wallet transfers to a user's signed authorization tree - ([File: contracts/controller/src/strategies/swap.rs])

### Summary
XOXNO strategy operations let user-supplied route bytes place arbitrary third-party contracts below the caller's authorization. A malicious venue invoked by that route can add a token transfer from the caller's wallet to the authorization tree, so signing the operation can transfer unrelated wallet assets to an attacker even though the routed swap itself settles correctly.

### Finding Description
`swap_collateral` requires authorization and verifies that the caller owns or delegates the target account, but it accepts attacker-controlled `swap` bytes and passes them into `withdraw_and_swap_from_supply`. [1](#0-0) 

That helper withdraws the caller's collateral into controller custody and calls `swap_tokens_or_passthrough`, which reaches `swap_tokens` for different token addresses. [2](#0-1) 

`swap_tokens` loads the configured router, authorizes only the exact controller-to-router input transfer, invokes `execute_strategy` with the user-controlled route bytes, and then only checks controller input spending and positive output. [3](#0-2) 

Those controller-side accounting checks do not prevent code reached through the route from requesting an additional `token.transfer(caller, attacker, amount)` beneath the caller's signed invocation. The threat model explicitly documents that routes have no venue allowlist and that a malicious child invocation executes if the caller signs the recorded authorization tree. [4](#0-3) 

The harness demonstrates the resulting auth-tree poisoning through `swap_collateral`: simulation records a transfer of the caller's unrelated wallet token to the attacker, and successful authorization leaves the caller's wallet empty while the protocol-side swap still completes. [5](#0-4) 

### Impact Explanation
An attacker can steal arbitrary tokens from a victim's wallet by getting the victim to submit a poisoned route. The stolen amount is not limited to the collateral being swapped or the protocol's routed amount because the malicious venue can request a separate transfer for another token held by the caller. The final risk checks still pass because the swap can pay a nominally valid output while the malicious wallet transfer occurs as a separate authorized child call. [4](#0-3) 

### Likelihood Explanation
An unprivileged attacker can deploy the malicious venue and construct route bytes for reachable caller-authorized operations such as `swap_collateral`, `swap_debt`, `multiply`, or `repay_debt_with_collateral`. Exploitation requires the victim to submit and sign a transaction containing the malicious route and its expanded authorization tree. This is analogous to an open redirect: the user expects a legitimate operation, while the attacker-controlled destination diverts authority to an unauthorized asset transfer. [6](#0-5) 

### Recommendation
Do not allow arbitrary route-controlled contracts to execute under a caller's authorization tree. Restrict routes to governance-approved venues and token contracts, or execute route hops under a constrained authorization boundary that cannot attach additional calls to the user's authorization. At minimum, clients should simulate and reject any authorization tree containing children other than the expected input transfer, but protocol-side route allowlisting provides a stronger boundary. [4](#0-3) 

### Proof of Concept
1. Victim supplies USDC and holds an unrelated token in the same wallet.
2. Attacker deploys a route venue whose `swap` function calls `token::Client::transfer(victim, attacker, wallet_balance)` for that unrelated token.
3. Attacker provides `swap` bytes for `swap_collateral(caller=victim, account_id=victim_account, current=USDC_market, amount=swap_amount, new=ETH_market, swap=poisoned_route)`.
4. `process_swap_collateral` passes the poisoned route through the withdrawal and swap path. [7](#0-6) 
5. `swap_tokens` invokes the configured router with the supplied route and authorizes only the expected controller input transfer. [6](#0-5) 
6. The router calls the attacker's venue, whose transfer is recorded as a child of the victim's `swap_collateral` authorization.
7. The victim signs the simulated tree; the malicious venue transfers the unrelated wallet balance to the attacker while the router still returns the declared output. The production controller then observes positive output and completes account finalization. [5](#0-4)

That bound covers the controller's own grant only. The router calls the pool
and token addresses its payload names and keeps no allowlist of them, so a
route can put third-party code on the call stack below the caller's
authorization. A token transfer that such code makes from the caller is
recorded by an honest simulation as a child of the caller's authorization
entry, and it executes if the caller signs that tree. The loss is then the
caller's wallet, not the routed amount, and neither the payload minimum nor the
final risk gate bounds it. An honest swap strategy gives the caller no child
entry, and a direct router swap gives exactly one input transfer. A client must

#[test]
fn simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry() {
    let s = Scene::new();
    let route = s.route_through_pool_stealing(WALLET_BALANCE);

    // `simulateTransaction` runs recording mode with non-root auth disabled.
    s.t.env.mock_all_auths();
    s.try_swap(&route)
        .expect("recording mode accepts the route");
    let recorded = s.t.env.auths();
    std::println!("recorded auth tree = {recorded:#?}");

    let stolen_transfer = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.wallet_token.clone(),
            symbol_short!("transfer"),
            (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),
        )),
        sub_invocations: std::vec![],
    };
    let poisoned_root = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.t.controller.clone(),
            Symbol::new(&s.t.env, "swap_collateral"),
            s.swap_args(&route),
        )),
        sub_invocations: std::vec![stolen_transfer],
    };
    assert_eq!(recorded, std::vec![(s.alice.clone(), poisoned_root)]);

    assert_eq!(s.wallet(&s.alice), 0);
    assert_eq!(s.wallet(&s.attacker), WALLET_BALANCE);
    assert_eq!(s.t.supply_balance_raw(ALICE, "ETH"), FAIR_OUT_ETH);
