### Title
`Api::CCMenuController#stack` bypasses ApiClient stack scoping, letting a stack-scoped token read any stack's status - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::ApiClient` supports scoping a token to a single stack via `stack_id` (`belongs_to :stack, optional: true`), and `Api::BaseController#stacks`/`#stack` enforces that scope for every other API endpoint. `Api::CCMenuController` overrides `#stack` with an unscoped `Stack.from_param!(params[:stack_id])`, breaking the equality "stack a token authorises == stack the request touches" for this one endpoint.

### Finding Description
`ApiClient` permissions are checked only by permission name (`read:stack`, etc.), not by stack; the actual isolation between multiple tenants/stacks sharing one Shipit instance is enforced by scoping the visible `Stack` relation to `current_api_client.stack_id` when present: [1](#0-0) 

This is exercised and relied upon elsewhere in the API (e.g. `Api::StacksController#index`), and is explicitly tested as a security boundary: [2](#0-1) 

`Api::CCMenuController`, however, authenticates the client with the same token mechanism but resolves `stack` directly from the request parameter, without going through the scoped `stacks` relation: [3](#0-2) 

`require_permission :read, :stack` only calls `ApiClient#check_permissions!`, which merely checks that the token's `permissions` array contains `read:stack` - it never compares the token's `stack_id` to the requested stack: [4](#0-3) 

So for `Api::CCMenuController` specifically, the binding "stack the token authorizes" (its `stack_id` column) diverges from "stack the request actually touches" (`params[:stack_id]` resolved unscoped via `Stack.from_param!`).

Root cause: `stack` is redefined in `Api::CCMenuController` (lines 29-31) instead of delegating to `Api::BaseController#stack`/`#stacks` (lines 74-80), which is the only place enforcing the per-client stack scope.

### Impact Explanation
An `ApiClient` legitimately scoped to one stack (e.g. the CCMenu client auto-created by `CCMenuUrlController#client`, or any admin-provisioned token with a `stack_id` set) can be used to fetch CI/deploy status (`lastBuildStatus`, `lastBuildLabel`, activity, lock state) for **any** stack on the instance by changing `stack_id` in the URL, even though the token was only supposed to read that one stack's state. This matches the "High - unauthorized read of stack state" impact bucket: cross-stack disclosure of deployment/build status that the token holder was not authorized to see. It does not grant write/deploy access (the endpoint is read-only and `check_permissions!` still requires `read:stack`), so impact is limited to unauthorized read, not RCE/credential exfiltration.

### Likelihood Explanation
Likelihood is moderate: exploitation requires possession of a valid, stack-scoped `ApiClient` token (e.g. a leaked CCMenu URL, which by design embeds the token in a query string and is commonly shared in CI dashboards, browser history, or chat - a much lower bar than requiring `webhook_secret`/GitHub App private key/admin session). No other privilege is required; the attacker simply changes the `stack_id` segment of an otherwise-valid, authenticated CCMenu request.

### Recommendation
Make `Api::CCMenuController#stack` reuse the scoped lookup from `Api::BaseController` (i.e. `stacks.from_param!(params[:stack_id])`) instead of `Stack.from_param!(params[:stack_id])`, so a client's `stack_id` restriction is enforced consistently across all API endpoints, including CCMenu.

### Proof of Concept
1. As a legitimate user, create a CCMenu URL for stack A: `GET /ccmenu/*stack_A` → returns a URL containing `token=<TOKEN_A>`, where `TOKEN_A` authenticates an `ApiClient` with `stack_id = A.id` and `permissions = ['read:stack']`. [5](#0-4) 
2. As an attacker who obtains `TOKEN_A` (e.g. from a shared/leaked CCMenu dashboard URL), issue: `GET /api/stacks/*stack_B/ccmenu?token=TOKEN_A` for an unrelated stack B that `TOKEN_A` was never scoped to.
3. `authenticate_api_client` in `Api::CCMenuController` accepts `TOKEN_A` via `ApiClient.authenticate(params[:token])`; `require_permission :read, :stack` passes because `TOKEN_A.permissions` includes `read:stack` (checked without regard to stack). `stack` resolves via `Stack.from_param!(params[:stack_id])` to stack B, unscoped.
4. The response renders stack B's build/deploy status (`shipit/ccmenu/project`), even though `TOKEN_A.stack_id == A.id`, demonstrating the token authorized only stack A but was able to touch stack B.

# frozen_string_literal: true

module Shipit
  module Api
    class CCMenuController < BaseController
      require_permission :read, :stack

      class NoDeploy
        def id
          0
        end

        def ended_at
          Time.now.utc
        end

        def running?
          false
        end
      end

      def show
        latest_deploy = stack.deploys_and_rollbacks.last || NoDeploy.new
        render('shipit/ccmenu/project', formats: [:xml], locals: { stack:, deploy: latest_deploy })
      end

      private

      def stack
        @stack ||= Stack.from_param!(params[:stack_id])
      end

      def authenticate_api_client
        @current_api_client = ApiClient.authenticate(params[:token])
        super unless @current_api_client
      end
    end
  end
end

require 'uri'

module Shipit
  class CCMenuUrlController < ShipitController
    def fetch
      uri = URI(api_stack_ccmenu_url(stack_id: stack.to_param))
      uri.query = { 'token' => client.authentication_token }.to_query
      render(json: { ccmenu_url: uri.to_s })
    end

    private

    def client
      @client ||= ApiClient.create_with(permissions: %w[read:stack])
                           .find_or_create_by!(creator: current_user, name: 'CCMenu Client')
    end

    def stack
      @stack ||= Stack.from_param!(params[:stack_id])
    end
  end
end
