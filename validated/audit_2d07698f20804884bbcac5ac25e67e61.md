### Title
Webhook signature is verified against `repository.owner.login`, but repository lookup for all event handlers uses `repository.full_name` — allowing cross-organization forged events - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App / webhook secret to check the HMAC against using `repository.owner.login` (or `organization.login`) from the *attacker-supplied* JSON body, then verifies the HMAC of the *entire* raw body against that secret. [1](#0-0) [2](#0-1) 

Every event handler, however, resolves the target `Repository`/`Stack` using a *different* field of the same payload: `repository.full_name`, split into owner/name and looked up independently of `repository.owner.login`. [3](#0-2) [4](#0-3) 

Because the attacker crafts the full JSON body themselves and signs it with their own legitimately-configured org's webhook secret, they can set `repository.owner.login` to their own org (so `verify_signature` picks their own valid secret and the HMAC matches) while setting `repository.full_name` to an arbitrary, unrelated `owner/repo` that Shipit tracks. The signature check never verifies that `full_name`'s owner equals `owner.login`.

### Finding Description
`verify_signature` does:
```ruby
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
```
where `repository_owner` is `params.dig('repository','owner','login') || params.dig('organization','login')`. [5](#0-4) 

`Shipit.github(organization:)` picks the `webhook_secret` configured for that organization key, and `verify_webhook_signature` computes `HMAC-SHA1(webhook_secret, raw_post)` and compares it to `X-Hub-Signature`. [6](#0-5) [7](#0-6) 

This is a correct HMAC of the whole body — but the whole body, including `repository.full_name`, is entirely attacker-controlled content in a self-signed request: an attacker who legitimately administers their own GitHub App/org integration on this Shipit instance (and therefore knows/controls that org's `webhook_secret`) can build any JSON payload, put `repository.owner.login = "their-org"` and `repository.full_name = "victim-org/victim-repo"`, and produce a valid signature themselves — because they know the secret used to verify it.

All downstream handlers key off `full_name`, not `owner.login`:
- `Handler#stacks` / `Handler#repository_name` uses `payload.dig('repository','full_name')`. [3](#0-2) 
- `Repository.from_github_repo_name` splits `full_name` on `/` with no cross-check against `owner.login`. [4](#0-3) 
- `PushHandler#process` uses `stacks` (i.e., `full_name`-resolved) to call `stack.sync_github`. [8](#0-7) 
- Pull-request handlers (`ClosedHandler`, `ReopenedHandler`, `LabeledHandler`, `OpenedHandler`, etc.) resolve `repository` via `Repository.from_github_repo_name(params.repository.full_name)` and then archive/unarchive/create review stacks based on payload content alone. [9](#0-8) [10](#0-9) 
- `ReviewStackAdapter#archive!`/`#unarchive!`/`#create!` act directly on the resolved stack (deprovision, archive, unarchive, create a new review stack) using only payload-derived data (`params.sender.login`, `params.pull_request.head.ref`, etc.), no re-fetch/validation against GitHub. [11](#0-10) [12](#0-11) 

**The broken binding, as an equality:**
`organization_authenticated_by_signature (repository.owner.login → webhook_secret)` == `organization_of_repository_written (repository.full_name → Stack/Repository lookup)`

Before the attack, this equality naturally holds for legitimate GitHub-originated webhooks (GitHub always sets `owner.login` consistent with `full_name`, and signs with the org's real secret). After the attacker's crafted request, `repository.owner.login = "attacker-org"` (used to pick a secret the attacker knows) while `repository.full_name = "victim-org/victim-repo"` (used to pick the actual target). The equality is violated, and the request still passes `verify_signature` because the signature is checked against attacker-known content, not against any invariant linking the two fields.

### Impact Explanation
This grants an attacker who controls **any** single organization/GitHub App integration configured in this multi-org Shipit deployment the ability to forge arbitrary webhook events (`push`, `pull_request`, `status`, `check_suite`, `membership`, etc.) targeting **any other organization's stacks** tracked by the same instance, without any actual push/PR access to the victim repository. Concretely this allows:
- Archiving/deprovisioning a victim's review stack (`pull_request` `closed` event) — an unauthorized destructive action on infrastructure the attacker has no access to.
- Creating rogue review stacks under a victim repository's namespace with attacker-controlled branch/PR metadata (`opened`/`reopened` handlers), which are later provisioned/deployed by CI processes trusting Shipit state.
- Forcing sync jobs (`push` handler) against arbitrary victim stacks.
- Injecting fabricated `status`/`check_suite` results for arbitrary commits, potentially affecting CI-gated deploy eligibility for stacks Shipit tracks under other organizations.

This crosses the "cross-repository writes" / "unauthorized deploy, rollback or merge" trust boundary described in the scope rules: an org that is authenticated (via signature) is treated as authorized to write state for any repository named in the payload, regardless of actual ownership.

### Likelihood Explanation
Requires only that the attacker already has a legitimately configured GitHub App/org entry in this Shipit instance's `secrets.github` (a normal, low-privilege situation for any tenant of a multi-tenant Shipit deployment) — no GitHub App private key, no `webhook_secret` leak, no repository write access to the victim repo is needed, satisfying the "unprivileged attacker" bar. The only skill needed is constructing an HTTP POST with a custom JSON body and computing an HMAC with a secret the attacker already legitimately possesses.

### Recommendation
In `WebhooksController#verify_signature` (or in each `Handler`), cross-validate that `repository.owner.login` (the field used to select the signing secret) matches the owner segment of `repository.full_name` before dispatching to handlers; reject the request (422) on mismatch. More robustly, resolve the target `Stack`/`Repository` using the same trusted field that was used to select the webhook secret, rather than trusting a second, independently-controlled field (`full_name`) for authorization-relevant lookups.

### Proof of Concept
1. Attacker legitimately administers `attacker-org`'s GitHub App/webhook integration on the shared Shipit instance, and thus knows `attacker-org`'s `webhook_secret`.
2. Attacker crafts a `pull_request` `closed` webhook payload:
```json
{
  "action": "closed",
  "number": 1,
  "pull_request": { "...": "..." , "head": {"sha": "...", "ref": "..."} },
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" },
  "sender": { "login": "attacker" }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(attacker-org's webhook_secret, raw_body)>` and POSTs it to `/github/webhooks`.
4. `verify_signature` resolves `Shipit.github(organization: "attacker-org")` (attacker's own app), verifies the HMAC successfully (because attacker computed it with the correct secret for that lookup), and the request passes. [1](#0-0) 
5. `Shipit::Webhooks.for_event('pull_request')` dispatches to `ClosedHandler`, which resolves `repository` via `Repository.from_github_repo_name("victim-org/victim-repo")` and calls `review_stack.archive!`, archiving/deprovisioning the victim's review stack — despite the attacker having no relationship to `victim-org`. [13](#0-12) [14](#0-13) 

Note: I was unable to execute this end-to-end against a running instance (no runtime/browser access here); the analysis is based on static code review of the cited files. If further confirmation is needed (e.g., confirming `check_suite_handler.rb`/`status_handler.rb`/`membership_handler.rb` follow the identical `full_name`-only lookup pattern), a Devin session with repository access would be needed to trace those handlers in full.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
          def archive!(*args, &block)
            if stack.blank?
              Rails.logger.info(
                "Processing #{action} event for #{repo_name} PR #{pr_number} but no Stack exists. Ignoring."
              )
              return true
            end
            return if stack.archived?

            stack.remove_from_provisioning_queue
            stack.deprovision
            stack.archive!(user, *args, &block)
          end

          def unarchive!(*args, &block)
            if stack.blank?
              Rails.logger.info(
                "Processing #{action} event for #{repo_name} PR #{pr_number} but no ReviewStack exists. Creating."
              )
              return create!
            end
            return unless stack.archived?

            stack.transaction do
              Shipit::ReviewStackProvisioningQueue.add(stack)
              stack.unarchive!(*args, &block)
            end
          end
```
