`Shipit::Webhooks::Handlers::StatusHandler#process` matches commits by SHA across all repositories, letting one repo's signed status webhook mutate an unrelated stack's `ignore_ci` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` looks up commits with `Commit.where(sha: params.sha)` with no repository scoping, unlike sibling handlers (`PushHandler`, `CheckSuiteHandler`) which resolve stacks via `stacks` (derived from `payload.dig('repository', 'full_name')`) before touching any record. Any `Commit` row anywhere in the database sharing that SHA gets `create_status_from_github!` called on it, which fires `Status#after_create :enable_ci_on_stack` → `Stack#enable_ci!`, flipping `ignore_ci` on whatever stack owns that commit — regardless of which repository's webhook secret actually signed the request.

### Finding Description
The binding the code should enforce is: `commit.stack.repository.full_name == payload['repository']['full_name']` (the stack whose state is mutated must be the stack owning the repository that authenticated the request). This binding is never checked.

Call path:
- `WebhooksController#create` dispatches the parsed JSON body to `Shipit::Webhooks.for_event('status')` → `StatusHandler.call(params)` [1](#0-0) .
- `verify_signature` only checks that the payload was signed by *some* org's secret, chosen from `repository_owner` inside the same attacker-controlled JSON body: `Shipit.github(organization: repository_owner)` [2](#0-1) . It authenticates "this request came from GitHub for org X," not "this request may mutate stacks belonging to repo Y."
- `StatusHandler#process` then does: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [3](#0-2) . It never filters by `stacks`/`repository_name`, unlike `PushHandler#process` (`stacks.not_archived.where(branch:)...`) [4](#0-3)  and `CheckSuiteHandler#process` (`stacks.where(branch: ...)`) [5](#0-4) , both of which resolve `stacks` from `payload.dig('repository', 'full_name')` [6](#0-5) .
- `Commit#create_status_from_github!` calls `statuses.replicate_from_github!(stack_id, github_status)` using the *found* commit's own `stack_id` [7](#0-6) , not any stack tied to the authenticated repository.
- `Status#after_create :enable_ci_on_stack` unconditionally calls `commit.stack.enable_ci!` [8](#0-7) , flipping `ignore_ci` on that commit's stack.

Exploit flow: if any `Commit` row for a completely different stack shares a SHA with a commit the attacker can legitimately post a GitHub status against (e.g., a shared/forked commit history, or any two stacks in the codebase that end up importing an identical commit SHA — a real and common situation for forks/mirrors/monorepo templates), a validly-signed status webhook from the attacker's own repository will still resolve and mutate the *other* stack's `Commit`/`Status`/`ignore_ci` state, because the lookup is `Commit.where(sha:)` with no repository predicate. `verify_signature` and `ExplicitParameters` schema validate the request's authenticity and shape, but neither of them nor `process` verifies that the resolved `Commit`/`Stack` actually belongs to the repository that signed the request — so the divergence is real and unguarded.

### Impact Explanation
A payload legitimately signed for repository A can create a `Status` on, and toggle `ignore_ci` for, a `Stack` belonging to unrelated repository B, purely because `Commit.where(sha:)` is unscoped. This is a cross-repository mutation of stack configuration/state, matching the Critical category "a payload for one repository mutating another's stack, commit, task or team." The blast radius is any stack in the installation whose `Commit` table happens to contain a SHA also reachable via a status the attacker can legitimately push from their own authenticated repo.

### Likelihood Explanation
The attacker still needs (a) a repository under an org for which they can generate a validly-signed webhook (their own repo, if Shipit's GitHub App is installed there), and (b) a SHA collision between one of their own repo's commits/status targets and a `Commit` row already imported into a different, unrelated stack. Requirement (b) is the limiting factor for arbitrary victim targeting — SHA-1 preimage forgery against a specific target hash is not practically achievable — but SHA collisions across repositories/stacks are realistic in common Shipit deployments (forks, mirrors, shared history, multiple stacks tracking the same repository), and the missing repository check is unconditionally present regardless of how the SHA collision arises. The bug (missing scoping in `StatusHandler#process` versus its siblings) is deterministic and trivially reproducible in a test using two fixture stacks with commits sharing a SHA.

### Recommendation
Scope `StatusHandler#process` the same way `PushHandler`/`CheckSuiteHandler` do: resolve `stacks` from `payload.dig('repository', 'full_name')` and restrict the commit lookup to `stacks.flat_map(&:commits).where(sha: params.sha)` (or equivalently `Commit.where(sha: params.sha, stack_id: stacks.select(:id))`), so a status can only affect commits belonging to the stack(s) of the repository that authenticated the webhook.

### Proof of Concept
minitest plan (model/controller level, no live GitHub):
1. Create two stacks, A (repository `orgA/repoA`) and B (repository `orgB/repoB`), each with `ignore_ci: true` and no CI hook.
2. Create `Commit` rows for both stacks sharing the identical `sha` value (e.g. `"deadbeef" * 5`), one on stack A (`commit_a`) and one on stack B (`commit_b`).
3. Stub `GithubHook.any_instance.stubs(:verify_signature).returns(true)` (as in `test/controllers/webhooks_controller_test.rb`).
4. POST to `/webhooks` with `X-Github-Event: status`, body `{ sha: <shared sha>, state: 'success', repository: { full_name: 'orgA/repoA', owner: { login: 'orgA' } } }`.
5. Assert:
   - Before: `stack_a.ignore_ci == true` and `stack_b.ignore_ci == true`.
   - After: `stack_a.reload.ignore_ci == false` (expected, same repo).
   - After: `stack_b.reload.ignore_ci == false` (unexpected — proves the binding "stack whose CI mode is toggled == stack of the authenticated repository" is broken, since the request never named `orgB/repoB`).
