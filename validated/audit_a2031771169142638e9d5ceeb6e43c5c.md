### Title
Webhook signature verification binds to the org named in `repository.owner.login`, but handlers act on repositories/commits identified by unrelated payload fields — ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App configuration (and thus which `webhook_secret`) to validate an inbound webhook's HMAC signature against, based on `repository_owner`, derived from the payload's `repository.owner.login` (or `organization.login`) field. Once the signature check passes, the individual event handlers (`Shipit::Webhooks::Handlers::*`) determine which Shipit `Repository`/`Stack`/`Commit` row to mutate using a *different* payload field — `repository.full_name` for most handlers, and for `StatusHandler`, no repository field at all, only a global `sha` lookup. Because the signature only certifies that the raw request body was HMAC-signed with a given org's secret, and nothing cross-checks that the "owner" field used for authentication matches the "full_name"/`sha` fields used for the write, an attacker who legitimately controls one organization's webhook secret (a normal, documented multi-tenant Shipit configuration) can forge a payload that authenticates as their own org while writing/mutating state that belongs to a completely different repository/stack.

### Finding Description
`verify_signature` computes the authenticating organization purely from attacker-suppliable JSON, not from any GitHub-verified identity: [1](#0-0) [2](#0-1) 

The signature is verified against the `webhook_secret` configured for that organization only: [3](#0-2) 

This is legitimate and secure *as long as* the "owner" used to pick the secret is the same repository the payload subsequently acts on. However, the base `Handler` class (used by `PushHandler`, `CheckSuiteHandler`, pull-request handlers, etc.) resolves the target repository from an entirely different field, `repository.full_name`, with no cross-check against `repository.owner.login`: [4](#0-3) 

Worse, `StatusHandler` does not scope to a repository at all — it looks up commits globally by `sha`: [5](#0-4) 

So the binding that should hold is:

`organization_that_authenticated (repository.owner.login used to pick webhook_secret) == organization_that_is_written (repository.full_name / commit.sha used by the handler)`

Nothing in the engine enforces this equality. An attacker who is a legitimate admin of "OrgA" in a multi-organization Shipit deployment (a supported, documented configuration — see `docs/setup.md` "Using Multiple Github Applications") possesses OrgA's `webhook_secret` and can craft an arbitrary raw JSON body, sign it with that secret, and set:
- `repository.owner.login = "OrgA"` (or `organization.login = "OrgA"`) so `verify_signature` selects and passes OrgA's secret, and
- `repository.full_name = "OrgB/victim-repo"` (for push/check_suite/pull_request events), or an arbitrary/known commit `sha` belonging to `OrgB` (for status events)

`Repository.from_github_repo_name`/`Commit.where(sha:)` will resolve to OrgB's actual `Stack`/`Commit` records: [6](#0-5) 

### Impact Explanation
- Via `StatusHandler`, an attacker authenticated only as their own organization can inject an arbitrary CI `state`/`context`/`description` onto any known commit `sha` in an unrelated stack they do not control: [7](#0-6)  This can force a required status check to "success" on a victim repository's commit, which Shipit's merge queue and continuous-deployment logic rely on to gate merges and deploys — an unauthorized merge/deploy.
- Via `PushHandler`, the attacker can trigger `stack.sync_github(expected_head_sha: ...)` for a victim stack under a repository/org they don't own: [8](#0-7) 
- Via `CheckSuiteHandler`, the attacker can force `schedule_refresh_check_runs!` on a victim's commits: [9](#0-8) 

This satisfies the Critical/High impact bar: cross-repository writes and the ability to influence an unauthorized deploy/merge decision, achieved purely by exploiting a trust-binding gap in the engine's own webhook dispatch code, not by stealing any victim credential.

### Likelihood Explanation
Likelihood is realistic in any deployment using the documented multi-organization GitHub App configuration (`github: <org>: webhook_secret: ...` per org), which is an intended, supported feature, not a misconfiguration. Any org onboarded to a shared Shipit instance inherently knows its own webhook secret and can freely construct raw POSTs to the shared `/github/webhooks` endpoint (there is no per-repository binding check), making this trivially reachable by any org tenant without needing further privileges.

### Recommendation
In `WebhooksController#verify_signature` (or in `Handler`), require and enforce that the organization used to select/verify the webhook secret (`repository.owner.login` / `organization.login`) matches the owner encoded in `repository.full_name` (and, for `StatusHandler`, scope `Commit` lookups to a `Stack`/`Repository` derived from a verified `repository.full_name`, rejecting events without one). Reject requests where these two identities diverge before dispatching to any handler.

### Proof of Concept
1. Deploy Shipit with two organizations configured, `OrgA` and `OrgB`, each with its own `webhook_secret` (per `docs/setup.md` multi-org example).
2. As an OrgA admin (knows OrgA's `webhook_secret`), craft a `status` event JSON body:
   ```json
   {
     "sha": "<known commit sha belonging to an OrgB stack>",
     "state": "success",
     "context": "ci/required-check",
     "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/victim-repo" }
   }
   ```
3. Compute `X-Hub-Signature: sha1=<hmac-sha1(OrgA_webhook_secret, body)>` and POST to `/github/webhooks`.
4. `WebhooksController#verify_signature` resolves `repository_owner` = `"OrgA"`, fetches OrgA's app, and the signature validates successfully.
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)` — matching the OrgB commit — and calls `create_status_from_github!`, writing a forged "success" status onto a commit in a repository/organization the attacker never authenticated for.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
