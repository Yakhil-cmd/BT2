### Title
Cross-repository commit status forgery via unscoped `sha` lookup in `StatusHandler` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`Shipit::WebhooksController#verify_signature` authenticates a webhook against the GitHub App/organization derived from the payload's own `repository.owner.login` field [1](#0-0) , but `StatusHandler#process` never checks that the `repository` named in that same payload actually owns the commit it mutates — it looks the commit up globally by `sha` alone [2](#0-1) . This is exactly the same class of bug as the reported issue: a trust boundary (which entity is authorized to act) is enforced at one layer (signature → organization) while the actual mutation is performed against a completely different, unchecked scope (any commit, in any repository/stack, matching an attacker-chosen `sha` string).

### Finding Description
- `WebhooksController#verify_signature` selects the `GitHubApp`/`webhook_secret` to validate against using `repository_owner`, itself read straight out of the untrusted payload (`params.dig('repository', 'owner', 'login')`) [3](#0-2) . This only proves the request was signed by *some* organization's registered GitHub App — it says nothing about which repository/stack should be affected.
- `StatusHandler` (invoked for every `status` event) declares no requirement on `repository` at all in its parameter schema, only `sha` and `state` [4](#0-3) .
- `process` resolves the target purely via `Commit.where(sha: params.sha)`, iterating over every matching `Commit` row across the entire installation and calling `commit.create_status_from_github!(params)` on each — with no filter tying the commit back to the `repository` field that was used to select/verify the signing secret [2](#0-1) . Contrast with `PushHandler`, which does scope its effect through `stacks` (derived from `Handler#repository_name`, i.e. `payload.dig('repository', 'full_name')`) [5](#0-4) [6](#0-5) .

**Binding broken (as an equality):**
`organization that authenticated the request` (via `repository_owner` used in `verify_signature`) ≠ `repository/stack whose commit is actually written` (any repo globally, selected only by `sha`).

Before the attacker's action: the signature only authorizes writes for the sending organization's own commits.
After: the same authorized signature lets `StatusHandler` write a status onto a commit belonging to *any* other tracked repository/stack, because the write path never re-checks the repository binding that the signature verification relied on.

### Impact Explanation
GitHub allows any actor with `repo:status` write access on a repository (including a low-privilege, throwaway repo an attacker controls and has legitimately onboarded into Shipit) to create a commit status for an **arbitrary 40-hex-character `sha` string** via `POST /repos/:owner/:repo/statuses/:sha` — GitHub does not require that SHA to exist in that repository. This produces a genuinely, validly signed `status` webhook (signed with the attacker's own org's `webhook_secret`), but with `sha` set to a real commit hash belonging to a different, more sensitive stack (commit hashes are public information visible via `git log`/API). Because `StatusHandler` resolves commits globally by `sha`, this forged, "success" status gets attached to that unrelated commit. If that target stack's deploy pipeline gates readiness/merges on the presence of a specific status context (a common Shipit pattern), the attacker can satisfy that gate and trigger an unauthorized deploy on a repository/stack they have no access to — matching the Critical "unauthorized deploy" impact class.

### Likelihood Explanation
High. No privileged Shipit session, API token, or GitHub App credentials are required — only ordinary commit-status write access to any single repository already connected to the Shipit instance (which can be a low-value/onboarding repo). The commit SHA of the target stack's HEAD is typically public. The forged webhook is a completely standard, correctly-signed GitHub `status` event; nothing about it looks anomalous to `verify_signature`.

### Recommendation
Scope `StatusHandler#process` to the repository named in the payload before touching any `Commit`, mirroring what `Handler#repository_name`/`#stacks` already provide for `PushHandler`: require `repository.full_name` in the handler's `params` schema and filter `Commit.where(sha: params.sha, stack: stacks)` (or equivalent join through the commit's stack/repository) instead of an unscoped global `sha` lookup.

### Proof of Concept
1. Attacker onboards/controls `attacker-org/throwaway-repo` in the Shipit instance (has a registered GitHub App/`webhook_secret` for `attacker-org`).
2. Attacker looks up the current HEAD `sha` of `victim-org/critical-repo` (public git history) that is tracked as a Shipit stack requiring a `ci/tests` status to be deployable.
3. Attacker calls GitHub's API: `POST /repos/attacker-org/throwaway-repo/statuses/<victim_sha>` with `{state: "success", context: "ci/tests"}`.
4. GitHub delivers a genuinely signed `status` webhook (signed with `attacker-org`'s `webhook_secret`) to Shipit.
5. `WebhooksController#verify_signature` succeeds because it validates against `attacker-org`'s own secret — the org it derived from the payload's own `repository.owner.login`.
6. `StatusHandler#process` runs `Commit.where(sha: victim_sha)`, finds the commit belonging to `victim-org/critical-repo`, and calls `create_status_from_github!`, marking the required `ci/tests` check as `success` on a commit the attacker never had access to — potentially unlocking an unauthorized deploy on `critical-repo`.
