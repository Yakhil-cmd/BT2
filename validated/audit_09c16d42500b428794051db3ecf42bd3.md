### Title
Membership webhook authenticated for one organization can mutate any other organization's Team by github_id - ([File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`MembershipHandler` finds/mutates a `Team` purely by `github_id` from the payload without ever checking that the payload's `organization.login` matches the organization that already owns that `Team` row. Because `WebhooksController#verify_signature` derives `repository_owner` from `params.dig('organization', 'login')` for this event type, an attacker only needs to name an organization that (a) is configured in Shipit but (b) has no `webhook_secret` set (in which case `GitHubApp#verify_webhook_signature` returns `true` unconditionally), then supply any victim `team.id` to add/remove members on that team.

### Finding Description
The binding that should hold is: `organization authenticated by verify_signature (params.organization.login)` == `organization that owns the Team row being mutated (Team#organization for github_id == params.team.id)`.

Trace:
- `WebhooksController#verify_signature` computes `repository_owner` as `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` [1](#0-0)  and then does `Shipit.github(organization: repository_owner).verify_webhook_signature(...)` [2](#0-1) . The `membership` payload schema requires only `organization.login`, never a `repository` key [3](#0-2) , so `repository_owner` is exactly `params.organization.login` — fully attacker-controlled.
- `GitHubApp#verify_webhook_signature` returns `true` unconditionally when no `webhook_secret` is configured for that organization: `return true unless webhook_secret` [4](#0-3) .
- `MembershipHandler#process` then calls `find_or_create_team!`, which does `Team.find_or_create_by!(github_id: params.team.id)` [5](#0-4)  — looked up solely by `github_id`, with no check that `team.organization == params.organization.login` for an already-existing row. `process` then mutates `team.members` via `add_member`/`members.delete` based on `params.action` [6](#0-5) .

Attack: attacker controls (or is a member of) some GitHub organization `A` that is configured in Shipit (e.g., via `Shipit.github_teams`/app config) but for which the operator forgot to set a `webhook_secret`. Attacker POSTs `X-Github-Event: membership` to `/webhooks` with `organization.login = "A"` and `team.id = <victim Team B's github_id>` (guessable/observable via Shipit's UI, API, or GitHub's public team pages) and `action: "added"`/`"removed"` plus any `member.login`. `verify_signature` authenticates against org `A`'s (secret-less) config and passes; the handler then finds Team B (belonging to org `B`) purely by `github_id` and mutates its `members`, i.e., a payload "authenticated" for org A mutates org B's Team.

Existing guards do not stop this: `drop_unhandled_event` only checks the event has a registered handler; the `ExplicitParameters` schema only validates types, not cross-organization consistency; there is no `require_permission!`/`stacks` scope check in this webhook path at all, since it's meant to be authenticated purely by HMAC signature — and that signature check is keyed off attacker-chosen org data with no secret required for a misconfigured org.

### Impact Explanation
A single crafted, unauthenticated HTTP POST (assuming any Shipit-configured org lacks a `webhook_secret`) lets the attacker add or remove arbitrary GitHub users from any `Team` row in Shipit by guessing/observing its `github_id`, regardless of which organization actually owns that team. Team membership in Shipit governs `Shipit.github_teams` authorization checks elsewhere in the app (`User#authorized?`/`require_permission!`), so this is a path to escalate a chosen user (including an attacker-controlled account) into a privileged Shipit team, or to remove legitimate members, across organizational boundaries — this is a cross-tenant authorization mutation, matching "escalation into `Shipit.github_teams` authorization" (High) or, if it enables further privileged actions (merges/deploys gated by that team), potentially Critical. Repeatable against every `Team` github_id the attacker can enumerate.

### Likelihood Explanation
Requires: (1) the Shipit deployment to have at least one configured organization without a `webhook_secret` (a real, documented misconfiguration risk, not a hypothetical secret leak), and (2) knowledge of a victim team's numeric `github_id`, which is often discoverable via the GitHub API/team page or via Shipit's own team-related endpoints. No Shipit session, API token, or GitHub App secret is needed. Cost is a single crafted HTTP request; feasibility depends entirely on the secretless-org precondition, which is an operator misconfiguration rather than a universal default (Shipit expects a `webhook_secret` per org via `config/secrets.yml`).

### Recommendation
In `MembershipHandler#find_or_create_team!`, verify that an existing `Team` (found by `github_id`) belongs to `params.organization.login` before mutating it, and reject/raise if it doesn't. Additionally, `WebhooksController#verify_signature` should not silently pass (`return true unless webhook_secret`) for any organization; either require a webhook secret for all configured organizations or reject webhooks for organizations with no secret.

### Proof of Concept
minitest plan (`test/models/shipit/webhooks/handlers/membership_handler_test.rb`):
1. Create `team_b = Shipit::Team.create!(organization: 'org-b', github_id: 555, slug: 'ops', ...)` and an existing member.
2. Build a membership payload: `{ action: 'added', team: { id: 555, name: 'Ops', slug: 'ops', url: '...' }, organization: { login: 'org-a' }, member: { login: 'attacker-user' } }` — note `organization.login` ("org-a") differs from `team_b.organization` ("org-b").
3. Call `Shipit::Webhooks::Handlers::MembershipHandler.new.call(payload)` (bypassing/stubbing signature verification to simulate the secretless-org path, or directly assert the handler-level defect since `verify_signature` is a separate controller concern).
4. Assert before: `team_b.members.map(&:login)` does not include `'attacker-user'`.
5. Assert after: `team_b.reload.members.map(&:login)` includes `'attacker-user'`, proving `Team.find_or_create_by!(github_id: 555)` mutated `team_b` despite the payload's `organization.login` being `'org-a'`, not `'org-b'` — demonstrating the broken binding `params.organization.login != team.organization` yet the write still occurred.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
