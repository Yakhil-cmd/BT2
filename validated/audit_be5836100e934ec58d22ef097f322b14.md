### Title
CCMenu token minted without `stack_id` grants `read:stack` on every stack - ([File: app/controllers/shipit/ccmenu_url_controller.rb])

### Summary
`CCMenuUrlController#client` creates an `ApiClient` with `permissions: %w[read:stack]` via `find_or_create_by!(creator: current_user, name: 'CCMenu Client')` but never sets `stack:` on it, so the resulting record's `stack_id` is `nil`. Since `Api::BaseController#stacks` treats `stack_id.nil?` as "unscoped" and returns `Stack.all`, the token embedded in a CCMenu URL that looks scoped to one stack actually authorizes `read:stack` against every stack in the installation.

### Finding Description
The intended binding is: for a CCMenu URL requested for `stack` (id `S`), the minted `ApiClient` should satisfy `api_client.stack_id == S`. Instead: [1](#0-0) 

creates/finds an `ApiClient` keyed only on `creator` and `name`, with no `stack:` attribute, so `api_client.stack_id` is `nil`. `ApiClient` does support scoping (`belongs_to :stack, optional: true`, see [2](#0-1) ), but this controller never uses it.

Downstream, `Api::BaseController#stacks` decides scope purely from `current_api_client.stack_id?`: [3](#0-2) 

Because `stack_id` is `nil`, `stack_id?` is `false`, so `stacks` resolves to `Stack.all` rather than `Stack.where(id: stack_id)`. Any `Api::*Controller` action that relies on `stacks`/`stack` (e.g. `Api::StacksController#show`, `Api::CCMenuController#show`) will therefore authorize the token against any stack, not just the one the CCMenu URL was generated for.

The controller's own authorization for generating the URL is also weak: `CCMenuUrlController#stack` does `Stack.from_param!(params[:stack_id])` with no permission check on whether `current_user` is a maintainer/collaborator of that stack's repository — so this issue compounds an existing "any logged-in Shipit user can hit `/stacks/:stack_id/ccmenu_url` for any stack" behavior with "the token that comes back is not even scoped to that stack." No guard (`require_permission`, `stacks` scoping, or `ApiClient` validation) prevents this divergence, because `ApiClient` permits `stack: nil` (`belongs_to :stack, optional: true`) and no validation forces a `stack` to be present when created from this flow.

Exploit flow: an authenticated Shipit user visits `GET /stacks/stackA/ccmenu_url`, receives a URL containing `token=<t>`. That same `t` authenticates a request to `GET /api/stacks/stackB` (or `Api::CCMenuController#show` for stackB) with `read:stack` permission satisfied, returning stackB's data even though the user has no relationship to stackB.

### Impact Explanation
An authenticated user gains persistent, repeatable `read:stack` access to every stack in the Shipit instance via a single generated token, rather than the one stack the UI implies. This is unauthorized cross-tenant read of stack state (deploy status, environment info exposed by `read:stack`-gated endpoints) for every stack/repository managed by the instance — matching "High: escalation ... unauthenticated/unauthorized read of stack state" (here effectively cross-stack read for any authenticated but otherwise unprivileged user). The token is durable (an `ApiClient` record, reusable indefinitely, one per `(creator, name)` pair) and works against arbitrary stacks without further authorization checks.

### Likelihood Explanation
Preconditions: attacker only needs a normal authenticated Shipit session (any `current_user`) — no stack membership, no maintainer role, no API credentials. The route `/stacks/:stack_id/ccmenu_url` is reachable by any logged-in user for any `stack_id` since `CCMenuUrlController#stack` does not scope by permission. Attacker cost is a single GET request; the result token is reusable against any other stack indefinitely. This is fully feasible with no GitHub secrets or elevated role required.

### Recommendation
Scope the `ApiClient` to the requested stack when creating/finding it, e.g. `ApiClient.create_with(permissions: %w[read:stack], stack: stack).find_or_create_by!(creator: current_user, stack: stack, name: 'CCMenu Client')`, and additionally enforce that `current_user` is authorized to view `stack` before minting/returning any token in `CCMenuUrlController#fetch`.

### Proof of Concept
Minitest plan (no live GitHub needed):
1. Create two stacks, `stack_a` and `stack_b`, and a plain authenticated `user` with no special role.
2. Sign in as `user`; `get :fetch, params: { stack_id: stack_a.to_param }` on `CCMenuUrlController`. Extract `token` from the returned `ccmenu_url` query string.
3. Load the created `ApiClient` and assert `api_client.stack_id.nil?` is `true` (before-side of the binding: `stack_id == nil`, expected `stack_id == stack_a.id`).
4. Using HTTP basic auth with `token` as credentials, call `Api::StacksController#show` (or `Api::CCMenuController#show`) for `stack_b`.
5. Assert the response status is `200` (current broken behavior) rather than the expected `403`/`404` that would result if `stacks` were properly scoped to `stack_a` only, proving the token grants `read:stack` on `stack_b` despite being requested for `stack_a`.
