### Title
`remote_proxy` charges a fixed, proof-size-independent weight while `sp_trie` proof-DB construction and traversal cost scales with attacker-supplied `Vec<Vec<u8>>` size - ([File: pallets/remote-proxy/src/lib.rs])

### Summary
`Pallet::remote_proxy`/`do_remote_proxy` accept a `RemoteProxyProof::RelayChain { proof: Vec<Vec<u8>>, .. }` and, once the supplied `block` matches any entry in the bounded `BlockToRoot` ring, unconditionally build an in-memory trie DB from the entire proof and run `sp_trie::read_trie_value` before any validity check on the proof content occurs. The dispatch weight charged for this call is a single fixed constant (`WeightInfoOf::<T,I>::remote_proxy()`) benchmarked against a tiny, well-formed proof, and is not scaled by `proof.len()` or the total byte size of the supplied nodes, so the declared/charged weight does not bound the actual CPU cost an attacker can force.

### Finding Description
In `do_remote_proxy`, the flow is: [1](#0-0) 

1. `roots.binary_search_by(...)` on `BlockToRoot::<T, I>` must succeed, i.e. the attacker must reference a `block` that is currently present in the bounded ring (any of the up-to-`MaxStorageRootsToKeep` entries, not necessarily the "oldest" one — using the latest known block works just as well and is trivially obtainable via RPC). If it fails, the call returns `Error::UnknownProofAnchorBlock` cheaply, *before* any trie work.
2. Once a valid anchor is found, `sp_trie::StorageProof::new(proof).into_memory_db::<RemoteHasherOf<T, I>>()` is called on the **entire, attacker-controlled** `Vec<Vec<u8>>` — every supplied "node" is hashed and inserted into the memory DB, regardless of whether it lies on the actual path to `key`. This cost is proportional to the total size of `proof`, which the pallet does not bound beyond whatever the runtime's generic extrinsic/block-length limits allow.
3. `sp_trie::read_trie_value` is then run, and only afterwards does the code map failure to `Error::InvalidProof`.

The `#[pallet::weight]` annotation on `remote_proxy` is: [2](#0-1) 

This only adds `WeightInfoOf::<T, I>::remote_proxy()` (a fixed constant), a fixed DB read/write weight, and the *inner call's* declared weight (`di.call_weight`) — nothing scales with `proof.len()` or the encoded size of the proof vector. The benchmark that produces this fixed constant uses `T::RemoteProxy::create_remote_proxy_proof`, which produces one small, well-formed proof: [3](#0-2) 

and the resulting generated weight for asset-hub-kusama is a small fixed number derived from a 105-byte measured proof: [4](#0-3) 

So the weight system treats every `remote_proxy` call as costing the same ~18μs of CPU regardless of whether the submitted proof is 105 bytes or several megabytes of garbage nodes. Because `RemoteProxyProof` is a plain call argument (not itself weight-scaled), an attacker only needs: (a) a signed account, (b) knowledge of any currently-valid `(block, root)` pair from `BlockToRoot` (obtainable via public RPC/storage query — no privileged access), and (c) an oversized `Vec<Vec<u8>>` filled with arbitrary bytes shaped as SCALE-decodable `Vec<u8>` entries. There is no minimum-node-validity check, no cap on `proof.len()`, and no per-byte weight component before the expensive hashing/traversal step.

### Impact Explanation
Multiple `remote_proxy` extrinsics, each declared to cost only the fixed low benchmarked weight but each carrying a maximally-sized garbage proof (bounded only by the runtime's max extrinsic/block length), can be included in a single block up to the parachain's declared weight limit while their actual CPU time (hashing/inserting all supplied nodes into the memory trie DB) is far higher than what was charged. This creates a mismatch between charged weight and actual execution time, allowing an attacker to push real block execution time beyond the assumed weight budget, degrading block production/execution time and congesting the parachain's processing of legitimate extrinsics (including legitimate `remote_proxy` calls) within the affected block(s). This is a transient weight-accounting/DoS issue, not a permanent halt or funds-loss issue.

### Likelihood Explanation
Feasible and repeatable: the attacker needs only a signed account (no special privileges), a valid `(block, root)` pair readable from public chain state (`BlockToRoot` storage, or equivalently the latest relay-chain block known to the parachain), and can construct arbitrarily large syntactically-valid `Vec<Vec<u8>>` payloads without needing any real trie data. The call fails only at the end with `Error::InvalidProof`/`ProxyDefinitionDecodingFailed`, after the costly hashing step has already run, so failure does not save the wasted work. This can be repeated every block as long as the parachain continues producing new anchor blocks (attacker simply re-queries the newest valid block each time), so the DoS is sustainable, not merely a one-off exploit against a race window.

### Recommendation
- Make the declared weight for `remote_proxy`/`remote_proxy_with_registered_proof` scale with the size of the supplied proof (e.g., add a per-node/per-byte weight component derived from `proof.iter().map(|n| n.len()).sum()`), consistent with how `sp_trie`'s proof-DB construction cost scales.
- Alternatively/additionally, enforce an explicit maximum node count and/or maximum total byte size for `RemoteProxyProof::RelayChain::proof` at decode time (e.g., via a `Config`-bound `MaxProofSize`/`MaxProofNodes`), rejecting oversized proofs before doing any trie work.
- Consider validating/bounding node count against the storage proof format expectations (e.g., cross-check with `sp_trie::verify_trie_proof` semantics that reject unused/redundant nodes early) rather than blindly building a full memory DB from all supplied bytes.

### Proof of Concept
Rust benchmark/fuzz-style integration test in `pallets/remote-proxy/src/tests.rs`:
```rust
#[test]
fn oversized_garbage_proof_costs_far_more_than_declared_weight() {
    new_test_ext().execute_with(|| {
        // Seed BlockToRoot with a real, currently-valid anchor.
        let (real_proof, block_number, storage_root) =
            <Test as Config>::RemoteProxy::create_remote_proxy_proof(&caller, &real);
        BlockToRoot::<Test, ()>::set(BoundedVec::truncate_from(vec![(block_number, storage_root)]));

        // Build a maximally-sized garbage proof (e.g. near max extrinsic/block length)
        // reusing the *same* valid block_number so binary_search succeeds and the
        // cheap UnknownProofAnchorBlock short-circuit is bypassed.
        let garbage_proof = RemoteProxyProof::RelayChain {
            proof: (0..N_NODES).map(|_| vec![0xAB; NODE_SIZE]).collect(),
            block: block_number,
        };

        let declared = <Test as Config>::WeightInfo::remote_proxy();

        let start = std::time::Instant::now();
        let result = RemoteProxy::do_remote_proxy(
            caller.clone(), real.clone(), None, cheap_call.clone(), garbage_proof,
        );
        let elapsed = start.elapsed();

        assert_eq!(result, Err(Error::<Test>::InvalidProof.into()));
        // Assert that actual measured time grossly exceeds the time budget implied
        // by `declared` weight (converted via a reference weight-to-time ratio),
        // demonstrating the weight-to-execution-time mismatch.
        assert!(elapsed_far_exceeds_budget(elapsed, declared));
    });
}
```
Expected assertion: the call still fails with `Error::InvalidProof`, but measured execution time (proof-DB construction + traversal) scales with `N_NODES * NODE_SIZE` while `WeightInfoOf::remote_proxy()` remains constant — proving the charged weight does not bound actual execution cost.
