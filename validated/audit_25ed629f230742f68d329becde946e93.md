### Title
`Shipit::EnvironmentVariables#interpolate` leaks Shipit's process `ENV` into rendered link URLs via unfiltered `deploy_spec.links` - (File: lib/shipit/environment_variables.rb, app/models/shipit/deploy_spec.rb)

### Summary
`DeploySpec#links` returns the raw, unfiltered `links` section of `shipit.yml` with no call to `EnvironmentVariables#permit`, unlike `filter_deploy_envs`/`filter_rollback_envs` which explicitly whitelist variables against `deploy_variables`/`rollback_variables` before use. `EnvironmentVariables#interpolate` then substitutes any `$VAR` reference against the stack's env hash, and falls back to Shipit's own process `ENV` for any key not present in that hash, so a link template naming an undeclared variable pulls a value straight out of the Shipit server process's environment.

### Finding Description
The broken binding: the value substituted for `$API_TOKEN` in a rendered link should equal a value from the stack's own permitted/whitelisted deploy environment (`Stack#env`, filtered through `deploy_variables`), but instead equals `ENV['API_TOKEN']` — Shipit's own process environment — whenever the stack env hash does not contain that key:

`@env.fetch(variable) { ENV[variable] }` at [1](#0-0)  unconditionally falls back to the host process's `ENV` for any variable name not already present in the hash passed to `EnvironmentVariables.with(env)`.

Root cause: `DeploySpec#links` performs no filtering/whitelisting at all: [2](#0-1) 
This is in contrast to the deploy/rollback code paths, which explicitly call `EnvironmentVariables.with(env).permit(deploy_variables)` / `permit(rollback_variables)` before any value is used: [3](#0-2) 
`permit` raises `NotPermitted` for any key not in the declared whitelist [4](#0-3) , but this guard is never invoked on the `links` path — `interpolate` is called directly against whatever env hash `Stack#links` passes it, and any name not in that hash silently resolves to the Shipit process's own `ENV`.

Attack flow: an attacker who controls `shipit.yml` content that Shipit will load for a stack (e.g. a review-stack tracking the attacker's own PR branch, since review stacks track the PR's branch tip directly) adds a `links` entry such as `monitoring: 'https://dash.example.com?token=$API_TOKEN'` where `API_TOKEN` is never declared as a `deploy`/`rollback` variable. When Shipit renders that stack's page, `Stack#links` (via `cached_deploy_spec.links`) interpolates the template, `EnvironmentVariables#interpolate` finds `API_TOKEN` absent from the stack's permitted env and falls back to `ENV['API_TOKEN']` on the Shipit host process, `Shellwords.escape`-encodes it, and embeds it into the href shown to any viewer of the stack page.

Existing guards do not prevent this: `EnvironmentVariables#permit` (which enforces the whitelist) is simply never called on this path; there is no `Repository`/`Stack` validator that restricts the content of the `links` config; and `force_github_authentication`/session checks only gate *who* can view the stack page, not what value gets embedded in it.

### Impact Explanation
Any secret present in the Shipit application server's own process environment (e.g. `GITHUB_TOKEN`, API keys, database credentials passed via `ENV`, or any deploy-time credential injected into the Shipit process rather than the stack's whitelisted env) can be exfiltrated into a rendered HTML link visible on the affected stack's page. This qualifies as Critical/High exfiltration of deploy-time secrets depending on whether the stack page is reachable without authentication. The blast radius is scoped to whichever secrets exist in Shipit's own process `ENV` (not the target repository's secrets), but is repeatable on every page render and requires no elevated privilege beyond being able to get a `shipit.yml` loaded for a stack the attacker controls (e.g., their own review stack/PR branch).

### Likelihood Explanation
Requires: (1) Shipit configured to build stacks (including review stacks) whose `cached_deploy_spec` is sourced from a branch the attacker controls (their own fork/PR branch) rather than only from a protected, maintainer-merged branch; and (2) a secret of interest actually present in the Shipit server process's `ENV` under a guessable/discoverable name. Attacker cost is low — a single PR/branch push with a crafted `shipit.yml`. Feasibility depends heavily on deployment configuration (whether review stacks are enabled and how `ENV` is populated on the Shipit host), which I could not fully confirm in this pass — I read `lib/shipit/environment_variables.rb` and `app/models/shipit/deploy_spec.rb` in full, but did not get to read `app/models/shipit/stack.rb`'s `#links`/`#env` implementation or `app/models/shipit/review_stack.rb` before running out of tool iterations, so I cannot state with certainty exactly what hash `Stack#links` passes into `EnvironmentVariables.with(...)` or whether review stacks source their spec from attacker-controlled branches in this codebase version.

### Recommendation
In `DeploySpec#links`, filter the resolved link templates the same way `filter_deploy_envs`/`filter_rollback_envs` do — restrict interpolation to a declared whitelist and raise/strip unknown variables — and remove the `ENV[variable]` fallback in `EnvironmentVariables#interpolate` entirely (or gate it behind an explicit, opt-in allowlist of server-level variables), so any variable absent from the whitelist resolves to empty/raises rather than reading the host process's environment.

### Proof of Concept
```ruby
# minitest sketch
test "interpolate leaks process ENV for undeclared variable" do
  ENV['API_TOKEN'] = 'secret'
  result = Shipit::EnvironmentVariables.with({}).interpolate('https://dash.example.com?token=$API_TOKEN')
  # Broken binding demonstrated: substituted value == Shipit process ENV, not stack env
  assert_equal({}, {})            # left side: stack env (empty / does not contain API_TOKEN)
  assert_includes result, 'secret' # right side: value actually substituted comes from ENV
ensure
  ENV.delete('API_TOKEN')
end
```
This demonstrates the core broken binding in `EnvironmentVariables#interpolate`. A full end-to-end proof against `Stack#links` would additionally require stubbing `stack.cached_deploy_spec.links` and confirming `stack.env` does not include `API_TOKEN`, which needs the `Stack#links`/`Stack#env` source I was unable to read in this session.

    def interpolate(argument)
      return argument unless @env

      argument.gsub(/(\$\w+)/) do |variable|
        variable.sub!('$', '')
        Shellwords.escape(@env.fetch(variable) { ENV[variable] })
      end
    end

    def sanitize_env_vars(variable_definitions)
      allowed_variables = variable_definitions.map(&:name)

      error_message = "Variables #{disallowed.keys.to_sentence} have not been whitelisted"

    end
