### Title
Uncaught exception in `isChashValid` on malformed base32/base64 c-hash input causes unhandled crash during unit validation - ([File: chash.js])

### Summary
`chash.isChashValid()` (`chash.js:152-171`), reached via `validation_utils.isValidChash` / `isValidAddress` / `isValidAddressAnyCase` (`validation_utils.js:52-62`), decodes attacker-supplied address/definition-chash strings and then calls `separateIntoCleanDataAndChecksum()` (`chash.js:45-68`) with **no exception guard**, while the actual base32/base64 decode a few lines above **is** wrapped in try/catch. If the decoded buffer does not resolve to exactly 160 or 288 bits (an "unusual size" relative to what the checksum-mixing algorithm assumes — directly analogous to libtiff's Predictor code assuming a tile size consistent with subsampling and blowing up when it isn't), `separateIntoCleanDataAndChecksum` throws `Error("bad length=...")`, and that throw is **not caught anywhere in the call chain**, unlike the sibling decode step.

### Finding Description
`isChashValid(encoded)`:
```js
try{
    var chash = (encoded_len === 32) ? base32.decode(encoded) : Buffer.from(encoded, 'base64');
}
catch(e){
    console.log(e);
    return false;
}
var binChash = buffer2bin(chash);
var separated = separateIntoCleanDataAndChecksum(binChash);   // <-- throws, NOT caught
``` [1](#0-0) 

`separateIntoCleanDataAndChecksum` explicitly throws when the bit-length of the decoded buffer is anything other than exactly 160 or 288 bits:
```js
function separateIntoCleanDataAndChecksum(bin){
    var len = bin.length;
    var arrOffsets;
    if (len === 160) arrOffsets = arrOffsets160;
    else if (len === 288) arrOffsets = arrOffsets288;
    else throw Error("bad length="+len+", bin = "+bin);
``` [2](#0-1) 

This is invoked transitively from `isValidChash`, which is the basis for `isValidAddress`/`isValidAddressAnyCase`:
```js

    return (isStringOfLength(str, len) && chash.isChashValid(str));
}

    return isValidChash(address, 32);
}
function isValidAddress(address){

``` [3](#0-2) 

`isValidAddress`/`isValidAddressAnyCase` are called pervasively during unit/message/AA validation — e.g. on every payment output address in `validatePaymentInputsAndOutputs`:
```js
const isValidAddressWithCase = objValidationState.last_ball_mci >= constants.timestampUpgradeMci ? ValidationUtils.isValidAddress : ValidationUtils.isValidAddressAnyCase;
...

    return callback("output address " + JSON.stringify(output.address) + " invalid");
``` [4](#0-3) 

as well as for author addresses, address-definition-change payloads, data-feed oracle addresses in `definition.js`, spend-proof addresses, device addresses (`isValidDeviceAddress`), and wallet/AA message handling. Any of these is a network-reachable path where an unprivileged unit poster, AA trigger sender, or device-message sender controls the string being validated.

For `isValidAddress`, the 32-character regex `[A-Z2-7]{32}` restricts input to the canonical base32 alphabet, and 32 base32 characters normally decode to exactly 20 bytes (160 bits), so in the common address-validation path a length mismatch is unlikely with a well-behaved base32 decoder. However, `isValidAddressAnyCase` (used for pre-`timestampUpgradeMci` units and as a fallback) and any use of `isValidChash` directly do **not** enforce that regex, so any 32-character string (including non-canonical characters accepted or mis-decoded by the third-party `thirty-two` decoder, e.g. non-canonical padding/case handling quirks) can reach `base32.decode` and potentially produce a buffer whose bit-length isn't a clean multiple matching 160/288, triggering the uncaught throw deep inside consensus-critical validation code. This mirrors the CVE-2016-9535 root cause pattern: a routine assumes a fixed/derived size relationship (tile size vs. subsampling; decoded-buffer bit-length vs. 160/288) that untrusted input can violate, and the failure mode is an unguarded fault instead of a checked validation error.

### Impact Explanation
If reachable with `isValidAddressAnyCase` (still used for units before `constants.timestampUpgradeMci`, and in `isChashValid`'s callers used by `definition.js` and `wallet_defined_by_addresses.js`), an uncaught `Error` thrown from deep within synchronous validation code that is not wrapped by a try/catch at the calling `validate()`/`validateMessage()` level would propagate as an unhandled exception. In Node.js, an unhandled synchronous exception thrown inside a callback-driven request path typically crashes the process (unless a global `uncaughtException` handler exists), which would deny an ocore node's ability to validate/confirm any further units — directly matching the "network unable to confirm new units" acceptance criterion.

### Likelihood Explanation
Medium. The direct `isValidAddress` path (32-char regex `[A-Z2-7]`) makes hitting a length-mismatch in the common case unlikely because base32 of a fixed 32-character canonical string is deterministic (20 bytes). The likelihood is higher for legacy paths using `isValidAddressAnyCase` (pre-`timestampUpgradeMci`, still reachable on mainnet history/replay and via `chash.js`'s use in `definition.js`'s inner-address evaluation) and any code invoking `isValidChash` directly without the regex, where malformed/non-canonical-but-still-32/48-character strings could reach the unguarded throw. I could not fully verify, without executing the third-party `thirty-two` base32 decoder, whether a crafted 32-character string can actually decode to a non-160-bit buffer; this uncertainty is the main gap in confidently rating this Critical rather than Medium.

### Recommendation
Wrap the call to `separateIntoCleanDataAndChecksum` (and `mixChecksumIntoCleanData`, which has an analogous unguarded throw) inside the same try/catch that already guards the decode step in `isChashValid`, returning `false` on any exception instead of allowing it to propagate. Additionally, audit all call sites of `isValidAddressAnyCase`/`isValidChash` to ensure they enforce a strict alphabet/length precondition before calling into `chash.js`, consistent with `isValidAddress`.

### Proof of Concept
Conceptual PoC (exact byte-level malicious base32 string that decodes to a non-160-bit buffer was not verified with the actual `thirty-two` library due to lack of execution environment):
1. An unprivileged party crafts a unit/AA-trigger message containing a 32-character (for `isValidAddressAnyCase`, any 32-char string; for `isValidChash` direct callers, any string of the target length) value used as an `address`/`definition_chash`, chosen so that decoding via `base32.decode` (or `Buffer.from(x,'base64')` for the 288-bit case) yields a buffer whose length in bits is not exactly 160 or 288.
2. This value is passed to `isValidChash`/`isChashValid` during normal validation of the posted unit (e.g., in `validatePaymentInputsAndOutputs`'s `isValidAddressWithCase(output.address)` check, or `definition.js`'s `'address'`/`'in merkle'` oracle address checks).
3. `base32.decode`/`Buffer.from` succeeds (no exception), so the guarding try/catch does not trigger; `buffer2bin` produces a bitstring whose length is not 160/288.
4. `separateIntoCleanDataAndChecksum` throws `Error("bad length=...")`, which is not caught anywhere up the call stack, crashing the validating process.
