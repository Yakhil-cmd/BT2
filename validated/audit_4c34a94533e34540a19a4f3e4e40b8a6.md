### Title
Webhook signature verification binds to `repository.owner.login` while all handlers act on `repository.full_name`, allowing cross-organization webhook forgery - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to use for HMAC validation based on `repository.owner.login` (or `organization.login`) taken from the untrusted JSON body, while every webhook `Handler` subsequently resolves the repository/stack to mutate using a *different* field of the same body, `repository.full_name`. Since Shipit supports multiple independently-configured GitHub organizations/apps (each with its own `webhook_secret`), an attacker who legitimately controls the webhook secret for one onboarded organization can forge a signed payload whose `repository.full_name` points at a repository belonging to an entirely different organization tracked by the same Shipit instance.

### Finding Description
Signature verification is performed in `verify_signature`: [1](#0-0) [2](#0-1) 

`repository_owner` is read straight from attacker-controlled JSON (`params.dig('repository','owner','login')` / `organization.login`) and used to pick the GitHub App/secret via `Shipit.github(organization: repository_owner)`.

Shipit explicitly supports a multi-organization credential schema where each organization has its own independent `webhook_secret`: [3](#0-2) 

Once the signature check passes (using the secret belonging to whatever organization `repository.owner.login` claims to be), the request body is dispatched to handlers via `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`: [4](#0-3) 

Every handler resolves the repository/stack to act on using a *different* JSON field, `repository.full_name`, via the shared `Handler` base class: [5](#0-4) 

Because the HMAC signature only proves "this body was signed with organization X's secret," and `verify_signature` never checks that `repository.owner.login` (the value used to pick the secret) is consistent with `repository.full_name` (the value used to identify which repository/stack is actually written to), an attacker who is a legitimate administrator of Organization X (and therefore knows/controls X's `webhook_secret`, e.g. by configuring X's GitHub App webhook themselves) can craft an arbitrary JSON body with `repository.owner.login = "X"` (to pass the signature check against X's secret) but `repository.full_name = "victim-org/victim-repo"` (a repository tracked under a completely unrelated organization/tenant in the same Shipit install), sign it with X's secret, and POST it directly to `/webhooks`.

This breaks the binding: **organization authenticated by the signature check (`repository.owner.login` → X's `webhook_secret`) ≠ repository actually written to by the handlers (`repository.full_name` → victim-org/victim-repo)**.

### Impact Explanation
With a forged, signature-valid webhook for an unrelated tracked repository, an attacker can invoke any webhook handler against that victim repository's stacks, including the `status` handler, which creates a `Status` record for an attacker-chosen commit SHA with an attacker-chosen state (e.g., forging a `success` CI status), as demonstrated by the existing test path for `:state` events: [6](#0-5) 

Since Shipit uses recorded commit `Status` records to gate deployability/mergeability of commits, an attacker can fake passing CI checks on a victim organization's repository they otherwise have no write or webhook access to, enabling an **unauthorized deploy** of a commit that never actually passed the real CI pipeline — this crosses the organizational trust boundary the signature check is meant to enforce.

### Likelihood Explanation
This requires the attacker to be a legitimate administrator of at least one organization/GitHub App already onboarded into the same multi-tenant Shipit instance (so they know that organization's real `webhook_secret`), and for the target victim repository to be tracked by the same instance. This is a realistic scenario for any multi-tenant/shared Shipit deployment serving several organizations, which is an explicitly supported configuration (`github_organizations`, `github_app_config`). No repository write access, GitHub App private key, or session/API token is required — only control of one onboarded org's webhook configuration.

### Recommendation
In `WebhooksController#verify_signature`, after selecting the GitHub App by `repository_owner`, additionally verify that `repository.full_name`'s owner segment matches `repository_owner` (and, ideally, that the resolved `Repository`/`Stack` actually belongs to that same GitHub organization) before dispatching to handlers. Reject the webhook if the two identifiers disagree.

### Proof of Concept
1. Attacker administers GitHub organization `attacker-org`, which is legitimately configured in Shipit's multi-tenant `secrets.github` config with webhook secret `S`.
2. Attacker crafts a JSON body:
```json
{
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" },
  "sha": "<victim commit sha>",
  "state": "success",
  "context": "ci/forged",
  "target_url": "https://attacker.example/fake"
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(S, body)` and sends `POST /webhooks` with header `X-Github-Event: status`.
4. `verify_signature` resolves `repository_owner = "attacker-org"`, loads `Shipit.github(organization: "attacker-org")`, and the HMAC check passes because it was signed with `S`.
5. The `status` handler (per `Handler#repository_name` using `repository.full_name`) resolves stacks under `victim-org/victim-repo` and creates a forged `success` Status for the victim's commit, independent of the fact that the signature was only proven valid for `attacker-org`.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
