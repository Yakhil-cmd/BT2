### Title
Unscoped `Commit.where(sha:)` lookup in the `status` webhook handler lets an org whose webhook signature is verified inject CI statuses onto commits belonging to a different repository/stack - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
The Chainlink report's bug class is "the value that is cryptographically/authoritatively verified is not the value actually acted upon." The corresponding binding in Shipit is: *the GitHub organization whose webhook signature is verified* must equal *the repository/stack whose data is written* when a webhook is processed. `Shipit::Webhooks::Handlers::StatusHandler` breaks this binding: it resolves the target `Commit` purely by `sha`, globally across the whole `commits` table, with no repository/stack scoping tied to the organization that was authenticated for the request.

### Finding Description
`WebhooksController#verify_signature` authenticates a webhook by looking up the `GitHubApp` for `repository_owner` (`params.dig('repository','owner','login')` or `params.dig('organization','login')`) and verifying the HMAC signature with that organization's `webhook_secret`: [1](#0-0) 

Once verification succeeds, `create` dispatches the raw JSON payload to the handlers registered for the event, with no further scoping applied by the controller: [2](#0-1) 

For the `status` event, `StatusHandler#process` looks up commits *only by `sha`*, with no join/filter on repository or stack: [3](#0-2) 

Compare this to `Handler#stacks`, which shows the pattern other handlers use to correctly scope by `repository.full_name` via `Repository.from_github_repo_name`: [4](#0-3) 

`StatusHandler` does not use this pattern at all - it never consults `payload['repository']`. So the equality that should hold - *organization authenticated by signature* == *organization/stack whose commit is mutated* - is never enforced. Any organization/repository that has a valid, Shipit-configured GitHub App (and therefore a valid webhook secret it legitimately owns, e.g., its own test org in a multi-org Shipit deployment) can send a `status` webhook whose payload contains an arbitrary `sha`, `state`, `description`, `target_url`, and `context` for any commit SHA already tracked by Shipit, in any other stack/repository, and Shipit will apply it via `Commit#create_status_from_github!`: [5](#0-4) 

This status feeds directly into deploy-gating logic: `Commit#deployable?` requires `success?` (derived from `status`, which aggregates `statuses_and_check_runs`), and a newly-"successful" status also triggers `stack.schedule_merges` and continuous-delivery scheduling: [6](#0-5) [7](#0-6) 

### Impact Explanation
Git commit SHAs are not secrets - they are visible in GitHub UI, PR links, CI logs, and often in Shipit's own public-ish task/commit views. Any attacker who controls a Shipit-recognized GitHub organization/app (a low-privilege position - they only need to be an admin of their own org with a Shipit GitHub App installed, a normal supported multi-org deployment per `docs/setup.md`'s "Using Multiple Github Applications" section) can forge a legitimately-signed `status` webhook for their own org while setting `sha` to a target commit belonging to a completely different tracked stack/repository. Because `StatusHandler` performs no repository scoping, the forged "success" status is written to the victim commit, which can flip `Commit#deployable?` to true and trigger `schedule_merges`/continuous delivery for a repository the attacker never authenticated against. This is a cross-repository/cross-tenant write that can lead to an unauthorized deploy or merge decision, satisfying the "Critical: cross-repository writes / unauthorized deploy" impact bar.

### Likelihood Explanation
Likelihood is highest in the documented multi-organization configuration (distinct `webhook_secret` per org), which is an officially supported and expected Shipit deployment mode. The attacker needs: (1) control of one Shipit-configured GitHub org/app (satisfied by being a legitimate but unprivileged tenant of that Shipit instance), and (2) knowledge of a target commit SHA (public information). No access to another org's `webhook_secret`, `GITHUB_TOKEN`, or a Shipit session/API token is required.

### Recommendation
Scope the `status` handler's lookup to the repository identified in the webhook payload, mirroring the pattern used by `Handler#stacks`/`Repository.from_github_repo_name`, e.g., restrict `Commit.where(sha: params.sha)` to `commit.stack.repository == Repository.from_github_repo_name(payload.dig('repository','full_name'))`, and additionally verify that the resolved repository's owning organization matches the organization that was authenticated in `WebhooksController#verify_signature` before any commit mutation occurs.

### Proof of Concept
1. Configure Shipit with two GitHub Apps/organizations, `OrgA` (attacker-controlled) and `OrgB` (victim), each with its own `webhook_secret`, per the multi-org setup in `docs/setup.md`.
2. Attacker discovers the SHA of an unmerged/failing commit in `OrgB/victim-repo` that Shipit already tracks (e.g., from GitHub's public commit page).
3. Attacker sends a `status` event to `/webhooks`, with `X-Github-Event: status`, a body containing `{"sha": "<victim-sha>", "state": "success", "repository": {"owner": {"login": "OrgA"}}, ...}`, and `X-Hub-Signature` computed with `OrgA`'s known `webhook_secret`.
4. `WebhooksController#verify_signature` resolves `repository_owner` as `"OrgA"`, fetches `OrgA`'s `GitHubApp`, and successfully verifies the signature (attacker knows this secret).
5. `Shipit::Webhooks.for_event('status')` dispatches to `StatusHandler`, which executes `Commit.where(sha: params.sha)` - matching the victim's commit in `OrgB/victim-repo` - and calls `create_status_from_github!`, marking it `success` regardless of which org the request was verified against.
