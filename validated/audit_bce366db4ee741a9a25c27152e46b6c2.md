### Title
RAY-domain overflow during interest accrual permanently freezes a high-utilization market - (File: common/src/rates/simulate.rs)

### Summary
A sufficiently large borrowed or supplied share balance can overflow the `i128` RAY domain when multiplied by a later interest index, even though the index itself remains below `MAX_BORROW_INDEX_RAY`. Every market mutation runs `interest::global_sync` before processing, so once `scaled_to_original` overflows, repayment, withdrawal, liquidation, and explicit index updates all revert with `MathOverflow`. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
`accrue_step` begins by unscaling total debt and supply through `scaled_to_original`, which computes `scaled * index / RAY` and returns `MathOverflow` when the resulting value cannot fit in `i128`. [1](#0-0) [4](#0-3) [5](#0-4) 

`update_borrow_index` caps only the index at `MAX_BORROW_INDEX_RAY`; it does not bound the product of the stored scaled balance and the index. [6](#0-5)  Consequently, a book near `1e36` RAY can reach the `i128::MAX` value boundary after roughly a 170× index increase, long before the index reaches its `1e36` ceiling. [3](#0-2) [7](#0-6) 

An unprivileged caller can build this condition through `Controller::supply` and `Controller::borrow`, retain approximately 98% utilization, and later invoke `update_indexes` after enough interest has accumulated. [8](#0-7) [9](#0-8)  The existing harness demonstrates a market whose subsequent `update_indexes`, `withdraw`, and `repay` calls all fail with `MATH_OVERFLOW` while the stored borrow index remains below its cap. [10](#0-9) 

### Impact Explanation
The result is permanent freezing of all funds associated with the affected market: suppliers cannot withdraw, borrowers cannot repay, liquidators cannot process the debt, and ordinary accrual cannot advance the market. [2](#0-1) [11](#0-10) [12](#0-11) 

This is not ordinary fail-closed input validation because the previously admitted market state becomes unprocessable, and even risk-reducing repayment and liquidation paths share the same overflowing accrual prerequisite. [2](#0-1) [13](#0-12)  Administrative parameter replacement also accrues under the old model first, so it does not provide a non-upgrade recovery path. [14](#0-13) 

### Likelihood Explanation
Severity is Medium because exploitation requires an exceptionally large, admitted token book and sustained high utilization for the index to cross the share-value boundary. [9](#0-8)  Nevertheless, neither condition is privileged: an attacker with enough inventory can provide the market liquidity and collateral through the public controller entrypoints, and any user can later trigger accrual. [8](#0-7) [15](#0-14) 

The cap is checked only against the index, so valid stored share balances and valid index growth can combine into an unrepresentable total value. [6](#0-5)  The project’s numeric documentation explicitly states that accrued market values can overflow before the index ceiling and then block repayment and withdrawal. [16](#0-15) 

### Recommendation
Enforce a market-level invariant that `borrowed * borrow_index / RAY` and `supplied * supply_index / RAY` remain representable, rather than bounding only the indexes. [6](#0-5) [1](#0-0)  Entry guards should reject additional supply or debt when projected accrual can exceed the RAY-domain ceiling before the configured index cap. [17](#0-16) 

Accrual also needs a bounded-value path that caps utilization input or index progression before `scaled_to_original` panics, allowing repayment and liquidation to continue. [18](#0-17)  Finally, add an explicit post-overflow rescue path or tested recovery procedure, because the present harness shows that ordinary exit and repayment calls remain unusable after the overflow. [10](#0-9) 

### Proof of Concept
The existing test constructs an 18-decimal market, supplies `1_000_000_000 * 10^18` base units, borrows 98%, advances ledger time, and observes `MATH_OVERFLOW` before the borrow-index cap. [19](#0-18) 

```rust
let principal = BILLION * 10i128.pow(18);
t.supply_raw(BOB, "BIG18", principal);
t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
t.borrow_raw(ALICE, "BIG18", principal / 100 * 98);

// Advance ledger time until scaled_value * borrow_index / RAY
// exceeds i128::MAX.
assert_contract_error(
    t.try_update_indexes_for(&["BIG18"]),
    errors::MATH_OVERFLOW,
);
assert_contract_error(
    t.try_withdraw_raw(BOB, "BIG18", 1),
    errors::MATH_OVERFLOW,
);
assert_contract_error(
    t.try_repay(ALICE, "BIG18", 1.0),
    errors::MATH_OVERFLOW,
);
```

The test additionally verifies that the borrow index remains below `MAX_BORROW_INDEX_RAY`, proving that the overflow occurs in share-value reconstruction rather than from exceeding the configured index ceiling. [20](#0-19)

/// Applies `interest_factor` to `old_index` to produce the new borrow index,
/// capped at `MAX_BORROW_INDEX_RAY`.
pub fn update_borrow_index(env: &Env, old_index: Ray, interest_factor: Ray) -> Ray {
    let new_index = old_index.mul(env, interest_factor);
    if new_index.raw() > MAX_BORROW_INDEX_RAY {
        return Ray::from(MAX_BORROW_INDEX_RAY);
    }
    new_index
}

pub(crate) fn global_sync(env: &Env, cache: &mut Cache) {
    if !cache.needs_accrual() {
        return;
    }

    let mut remaining = cache.elapsed_ms();
    while let Some(nonzero) = NonZeroU64::new(remaining) {
        let chunk = nonzero.get().min(MAX_COMPOUND_DELTA_MS);
        accrue_chunk(env, cache, chunk);
        remaining = remaining.saturating_sub(chunk);
    }

    cache.mark_accrued();
}
