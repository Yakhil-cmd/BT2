## Title
Cross-organization webhook signature confusion allows unauthenticated escalation into `Shipit.github_teams` authorization - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` picks *which* GitHub App/webhook secret to validate an inbound webhook against by reading an untrusted field out of the very payload it hasn't verified yet (`repository.owner.login` / `organization.login`). In a Shipit installation configured with multiple GitHub organizations (a documented, supported setup, see `docs/setup.md` "Using Multiple Github Applications"), this lets an attacker choose to "authenticate" as any organization whose `webhook_secret` is blank/unset, while the payload body still acts on a **different** team/organization's data. This is the same class of bug as the reported finding: a value is checked against one binding ("is this signature valid for org X") but a different, unguarded value from the same untrusted input ("which team/org do we actually mutate") is what the code acts upon.

### Finding Description
`Shipit.github(organization:)` resolves a distinct `GitHubApp` (and thus a distinct `webhook_secret`) per configured organization [1](#0-0) . `WebhooksController#verify_signature` selects that organization straight from the JSON body:

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(...)
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [2](#0-1) 

`GitHubApp#verify_webhook_signature` returns `true` unconditionally when that organization has no `webhook_secret` configured:
```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
``` [3](#0-2) 

The docs and example secrets files show `webhook_secret` as an optional field left blank (`webhook_secret: # nil`) per organization [4](#0-3) [5](#0-4) .

Once verification "passes" (because the picked organization has no secret), the request body is handed unmodified to the event handlers, which trust *other* fields from the same body to decide what to mutate. `MembershipHandler` looks a team up purely by the numeric GitHub `team.id` supplied in the payload — independent of which organization's secret was used to authenticate the request — and adds an arbitrary (attacker-supplied) GitHub login to it:
```ruby
def process
  team = find_or_create_team!
  member = User.find_or_create_by_login!(params.member.login)
  case params.action
  when 'added'
    team.add_member(member)
  ...
def find_or_create_team!
  Team.find_or_create_by!(github_id: params.team.id) do |team|
    team.github_team = params.team
    team.organization = params.organization.login
  end
end
``` [6](#0-5) 

That `Team` row is the same object referenced by `Shipit.github_teams`, which gates access to the whole app:
```ruby
def authorized?
  @authorized ||= Shipit.github_teams.empty? || teams.where(id: Shipit.github_teams.map(&:id)).exists?
end
``` [7](#0-6) 

The equality that should be, but is not, enforced is:
`organization whose webhook secret authenticated the request == organization/team the payload is permitted to mutate`.
Because `repository_owner`/`organization.login` is attacker-controlled and only used to *pick a lax verifier*, while `team.id`/`organization.login` used by the handler is a completely separate, unguarded field from the same body, an attacker can authenticate as "the org with no secret" and still write to another org's team membership data.

### Impact Explanation
An unauthenticated, unprivileged external actor who only knows that a shared Shipit instance manages multiple GitHub organizations (a supported, documented configuration) and that at least one of them has no `webhook_secret` configured, can:
1. POST directly to `/webhooks` with `X-Github-Event: membership`, `repository.owner.login`/`organization.login` set to the org with no secret (any/garbage `X-Hub-Signature` accepted).
2. Set `team.id` to the numeric GitHub id of a *different* organization's privileged team (e.g., the one referenced in `oauth.teams`/`Shipit.github_teams`), and `member.login` to their own GitHub username.
3. `MembershipHandler` adds their GitHub account to that `Team` record.
4. `User#authorized?` now returns true for that attacker once they complete the normal GitHub OAuth login, granting them full access to stacks, deploys, and API clients that should be restricted to `Shipit.github_teams` members.

This is an escalation into `Shipit.github_teams` authorization — explicitly listed as a High-severity impact in scope, achieved with no session, no `ApiClient` token, and no repository write access.

### Likelihood Explanation
Requires only: (a) the target installation to use the multi-organization GitHub App config (a first-class, documented feature), and (b) at least one configured organization to have no `webhook_secret`. Given `webhook_secret` is presented as optional in setup docs and example configs, this is a realistic misconfiguration, not a contrived edge case. No credentials, tokens, or prior access are needed to send the forged webhook.

### Recommendation
Do not let the payload itself choose which secret verifies it. Bind the verified organization to the effect of the handler:
- Verify the signature using a secret tied to the actual resource being modified (e.g., the destination stack/team's known organization), not a value read from the unverified body, or
- Reject/require a non-blank `webhook_secret` for every configured organization, and additionally re-check, inside each handler, that `params.organization.login` / the team's `organization` matches the organization whose secret validated the request before mutating cross-cutting state like team membership.

### Proof of Concept
Given a shared Shipit config:
```yaml
github:
  OrgNoSecret:
    app_id: ...
    webhook_secret: # blank
  OrgAdmins:
    app_id: ...
    webhook_secret: real-secret
    oauth:
      teams:
        - OrgAdmins/admins   # Team.github_id = 999 (already known/synced)
```
Attacker sends, with no valid signature:
```
POST /webhooks
X-Github-Event: membership
X-Hub-Signature: sha1=deadbeef

{
  "action": "added",
  "team": { "id": 999, "name": "admins", "slug": "admins", "url": "https://github.com/x" },
  "organization": { "login": "OrgNoSecret" },
  "member": { "login": "attacker-handle" }
}
```
`verify_signature` calls `Shipit.github(organization: 'OrgNoSecret')`, whose `verify_webhook_signature` returns `true` unconditionally (blank secret) [8](#0-7) , so the request passes. `MembershipHandler` then finds `Team` with `github_id: 999` (the `OrgAdmins/admins` team) and adds `attacker-handle` as a member [9](#0-8) . After logging in via GitHub OAuth, `attacker-handle`'s `User#authorized?` now returns `true`, granting full access to the Shipit instance.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
