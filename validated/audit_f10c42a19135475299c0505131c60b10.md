### Title
CCMenuController#stack bypasses stack_id scoping, allowing an ApiClient token scoped to stack A to read stack B's CCMenu status - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::CCMenuController#stack` (app/controllers/shipit/api/ccmenu_controller.rb:29-31) calls `Stack.from_param!(params[:stack_id])` directly instead of using the inherited, scoped `stacks.from_param!` from `BaseController` (app/controllers/shipit/api/base_controller.rb:74-79). This means the binding `current_api_client.stack_id == stack.id`, which is enforced everywhere else via the `stacks` scope, is never checked here, so any valid ApiClient token with `read:stack` can fetch the CCMenu XML for any stack, not just the one it was issued for.

### Finding Description
The intended binding is: `current_api_client.stack_id.nil? || current_api_client.stack_id == stack.id`. This is enforced in `BaseController#stacks` (app/controllers/shipit/api/base_controller.rb:74-76): `current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all`, and `BaseController#stack` (line 78-80) resolves the requested `params[:stack_id]` only within that scoped relation, so `from_param!` raises `ActiveRecord::RecordNotFound` if the client's `stack_id` doesn't match the requested stack.

`CCMenuController` overrides `#stack` (app/controllers/shipit/api/ccmenu_controller.rb:29-31) to bypass this scope entirely:
```ruby
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end
```
This resolves against the entire `Stack` table, ignoring `current_api_client.stack_id`. `authenticate_api_client` (lines 33-36) only calls `ApiClient.authenticate(params[:token])`, which just verifies the signed client id (`ApiClient.authenticate`, app/models/shipit/api_client.rb:24-27) — it performs no stack-scoping check either. The only other guard, `require_permission :read, :stack` (line 6), calls `check_permissions!` (app/models/shipit/api_client.rb:38-45), which only checks that `"read:stack"` is in the client's `permissions` array — it never compares `stack_id` to the requested stack.

Attacker flow: Attacker previously obtained a `token` for an ApiClient scoped to stack A (`ApiClient#stack_id == A.id`, permission `read:stack`) — e.g., via the CCMenu URL exposed on stack A's settings page (`CCMenuUrlController#fetch`, app/controllers/shipit/ccmenu_url_controller.rb:7-11). Attacker sends `GET /stacks/<stack_B_param>/ccmenu?token=<tokenA>`. `authenticate_api_client` accepts the token (valid signature, unrelated to stack B). `#stack` resolves stack B directly from `Stack.from_param!`, ignoring that `current_api_client.stack_id == A.id != B.id`. `show` renders stack B's `deploys_and_rollbacks.last` and project data. The before/after equality: before the request, `current_api_client.stack_id (A) == stack.id (B)` is false; after rendering, the code never re-checks this and returns 200 with stack B's data anyway — the divergence is never closed.

### Impact Explanation
An attacker holding any single-stack-scoped CCMenu/API token can read the build/deploy status (latest deploy/rollback id, ended_at, running state, project name) of any other stack in the Shipit instance, including stacks belonging to unrelated repositories/tenants. This is a cross-tenant unauthorized read of stack/deploy state, repeatable for every stack id the attacker can guess or enumerate, matching the "High - unauthenticated/unauthorized read of stack state" impact category (the attacker is authenticated as *some* client but not authorized for the target stack, which is the exact escalation being probed here).

### Likelihood Explanation
Preconditions are modest: the attacker only needs to have obtained one legitimate CCMenu token for any stack (e.g., leaked ccmenu_url, or a stack they briefly had settings access to per `CCMenuUrlController`). No GitHub secrets, session, or elevated Shipit role are required — the request is a single unauthenticated GET with a query-string token, and stack ids are sequential/guessable via `Stack.from_param!` (typically slug or numeric id). This makes exploitation cheap and fully repeatable against arbitrary stacks.

### Recommendation
Change `CCMenuController#stack` to use the same scoped resolution as `BaseController`, e.g.:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
removing the private `stack` override entirely so it inherits `BaseController#stacks`/`#stack`, restoring the `current_api_client.stack_id` scoping check.

### Proof of Concept
Minitest controller test plan (`test/controllers/api/ccmenu_controller_test.rb` scope, illustrative):
```ruby
test "ccmenu#show scoped client can not read another stack's status" do
  stack_a = shipit_stacks(:shipit)
  stack_b = shipit_stacks(:cyclimse) # a different repository/tenant
  client_a = ApiClient.create!(creator: shipit_users(:walrus), name: 'A', permissions: %w[read:stack], stack: stack_a)

  assert_not_equal client_a.stack_id, stack_b.id # binding is false before request

  get :show, params: { stack_id: stack_b.to_param, token: client_a.authentication_token }

  assert_response :not_found # expected: request must fail since client_a.stack_id != stack_b.id
  # Current (vulnerable) behavior: assert_response :ok and response.body includes stack_b's project data
end
```
This demonstrates the equality `current_api_client.stack_id == stack.id` is false yet the controller currently returns `:ok` with stack B's CCMenu XML, confirming the cross-tenant read. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3)
