### Title
`status_handler.rb` mutates commits/stacks across organizations because `Commit.where(sha:)` is unscoped by repository - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` looks up commits purely by `sha`, with no join or filter on the repository/stack that the incoming webhook actually belongs to. Signature verification only proves the payload was signed by the `webhook_secret` of the organization named in the payload's own `repository.owner.login`; it says nothing about which commit rows the handler is allowed to touch. If a sha collides across two independently tracked repositories (shared history, or by simply naming an arbitrary/nonexistent sha when creating a GitHub status on your own repo), an authenticated-for-Org1 webhook mutates Org2's commit/stack state.

### Finding Description
The intended binding is: `organization_that_signed(payload) == organization_owning(Commit.where(sha: params.sha))`. In code, `WebhooksController#verify_signature` derives the signing organization strictly from the payload body (`repository_owner`) and validates the signature against `Shipit.github(organization: repository_owner).verify_webhook_signature`: [1](#0-0) [2](#0-1) 

That verification only proves "this body was signed with Org1's secret" - it never constrains which `Commit` rows the handler may act on. `StatusHandler#process` then runs an unscoped, global lookup: [3](#0-2) 

`Commit#create_status_from_github!` operates using the commit's own `stack` (whichever stack it actually belongs to, e.g. Org2's), not the organization that signed the webhook: [4](#0-3) [5](#0-4) 

Exploit flow: an attacker who owns/administers a repository under Org1 (with a legitimately configured Shipit webhook and real `webhook_secret`) can call GitHub's `POST /repos/Org1/repo/statuses/:sha` API with an arbitrary `sha` string - GitHub does not require that sha to exist in Org1's repository. GitHub then delivers a `status` webhook signed with Org1's real secret, but with `sha` set to a value that happens to also exist as a `Commit` row under Org2's stack (e.g., a shared upstream commit, or the git empty-tree sha `4b825dc642cb6eb9a060e54bf8d69288fbee4904`, which is identical across every git repository). `verify_signature` correctly validates the signature (it is genuinely Org1's signature over Org1's payload), so the request passes `drop_unhandled_event`/`verify_signature`. `StatusHandler#process` then finds the row in `Commit` table with that sha - which is Org2's commit - and calls `create_status_from_github!` on it, writing a new `Status` record and changing that commit's computed status/state, potentially triggering `stack.schedule_merges` or continuous-delivery evaluation on Org2's stack, entirely without ever touching Org2's `webhook_secret`.

None of the existing guards catch this: `verify_signature` validates the org tied to the payload's own repository field, not the org owning the target commit row; `drop_unhandled_event` only filters by event type; `ExplicitParameters` schema for `StatusHandler` only validates types/shape of `sha`/`state`/etc., not repository ownership; there is no `repository.full_name` check anywhere in `status_handler.rb` correlating the payload's repo to the matched `Commit`'s stack/repo.

### Impact Explanation
A payload authenticated for Organization X can create/replace GitHub-status records and flip the computed CI/deploy state on a `Commit` belonging to Organization Y's stack, without ever presenting Y's `webhook_secret`. This can influence `stack.schedule_merges`, continuous-deployment eligibility (`schedule_continuous_delivery`), and downstream deploy/merge automation - i.e., a payload for one repository mutating another organization's stack/commit, which matches the Critical impact category ("a payload for one repository mutating another's stack, commit, task or team"). This is repeatable against any sha the attacker can predict or induce to collide (trivially the empty-tree sha, or any commit shared via forking from a common upstream/monorepo split), and can be fired for every status webhook received by any org configured on the Shipit instance.

### Likelihood Explanation
Preconditions: attacker needs to control (or have push/status-creation access to) at least one repository already registered/tracked by any Shipit-configured GitHub organization, and needs a `Commit` row to exist elsewhere with a colliding sha. Colliding shas are realistic in common scenarios (shared upstream history between forks, monorepo splits, or the universally identical empty-tree sha present in literally every git repo, which is trivially reachable if any tracked stack ever ingested that commit e.g. via an initial empty commit). Creating a GitHub commit status via the API against an arbitrary sha string requires only standard write/status permission on one's own repo - no Shipit secret, session, or API token is needed, satisfying the stated unprivileged-attacker model. Cost is a single authenticated GitHub API call; the resulting webhook is delivered and processed automatically by Shipit.

### Recommendation
Scope the `Commit` lookup in `StatusHandler#process` by the stack/repository derived from the webhook payload (`repository.full_name` / `repository.owner.login`), not by sha alone - e.g. join through `Stack` to ensure the resolved commit's stack repository matches the payload's `repository.full_name`, discarding any match where they differ. Apply the same repository-scoping check generically wherever webhook handlers resolve records purely by GitHub-supplied identifiers (sha, PR number, etc.) to prevent cross-tenant record resolution.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb (conceptual)
test "a status webhook signed for org1 must not mutate a commit belonging to org2's stack" do
  Shipit.stubs(:github).with(organization: 'org1').returns(github_app_with_secret('org1-secret'))
  Shipit.stubs(:github).with(organization: 'org2').returns(github_app_with_secret('org2-secret'))

  stack_org2 = shipit_stacks(:shipit) # belongs to org2
  colliding_sha = '4b825dc642cb6eb9a060e54bf8d69288fbee4904' # empty tree sha
  commit_org2 = stack_org2.commits.create!(sha: colliding_sha, message: 'org2 commit')

  payload = {
    'sha' => colliding_sha,
    'state' => 'success',
    'repository' => { 'owner' => { 'login' => 'org1' }, 'full_name' => 'org1/some-repo' }
  }
  body = payload.to_json
  signature = 'sha1=' + OpenSSL::HMAC.hexdigest('sha1', 'org1-secret', body)

  # side of equality: organization that signed == org1
  # side of equality: organization owning commit row == org2
  assert_not_equal 'org1', stack_org2.repository.owner # sanity: different orgs

  post shipit.github_webhooks_path,
       params: body,
       headers: { 'X-Hub-Signature' => signature, 'X-Github-Event' => 'status', 'Content-Type' => 'application/json' }

  assert_response :ok
  commit_org2.reload
  # BUG: org2's commit was mutated by a webhook that only org1's secret verified
  assert_equal 'success', commit_org2.status.state
end
```
This demonstrates the two sides of the provenance equality (signing org = org1, mutated-row org = org2) diverge, confirming the cross-organization state mutation.
