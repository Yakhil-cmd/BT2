This confirms multi-tenant support: `Shipit.github(organization:)` looks up a per-organization config (with its own `webhook_secret`) via `Shipit.github_app_config(organization)`, keyed strictly by the organization name string.

Now I have what's needed to write up the analog.### Title
Webhook signature is verified against the organization named in `repository.owner.login`, but the resulting stacks are looked up from the independently-forgeable `repository.full_name`, letting an attacker with one legitimate Shipit organization forge writes into stacks owned by any other organization - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks the HMAC secret to validate a webhook against by reading `repository.owner.login` (or `organization.login`) out of the **unauthenticated** JSON body, before the signature has been checked. `Shipit::Webhooks::Handlers::Handler#stacks`, executed after verification succeeds, independently re-reads `repository.full_name` from that same still-attacker-controlled body to decide which `Repository`/`Stack` records to act on. Because these two fields are read separately and nothing enforces that `full_name`'s owner segment matches `owner.login`, a value that authenticates against organization A's registered secret can be paired with a `full_name` claiming to belong to organization B, breaking the "organization that authenticated == repository being written" invariant — the same class of binding break as the mantra report's "gas paid == gas that should be spent" mismatch.

### Finding Description
The verification step in `app/controllers/shipit/webhooks_controller.rb`:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```
`Shipit.github(organization:)` resolves a **per-organization** webhook secret via `Shipit.github_app_config(organization)` (`lib/shipit.rb`), which is exactly what multi-tenant Shipit installations use to host several independent GitHub organizations with independent app credentials/secrets.

The signature is computed over `request.raw_post` (the whole body) using the secret picked from `repository.owner.login`. That check only proves the body was signed by *some* org's secret keyed by that login — it does not constrain any other field inside that same body.

After verification, `create` dispatches to handlers (e.g. `PushHandler`, `StatusHandler`) which derive the target repository independently:
```ruby
# app/models/shipit/webhooks/handlers/handler.rb
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
```
`Repository.from_github_repo_name` splits `"owner/name"` on `/` and looks up any repository by that owner/name pair — with no relationship at all to `repository_owner` used earlier for signature selection.

Because the JSON body is a single object entirely crafted by whoever holds a valid secret for *any one* onboarded organization, that attacker can set:
```json
{
  "repository": {
    "owner": { "login": "attacker-org" },   // used only to select attacker-org's secret for verify_webhook_signature
    "full_name": "victim-org/victim-repo"    // used to select the actual Stacks acted upon
  },
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>"
}
```
Signing this body with `attacker-org`'s real webhook secret makes `verify_signature` pass (it only checks the HMAC against `attacker-org`'s secret, which the attacker legitimately possesses because they are a properly onboarded/installed GitHub App user for `attacker-org`), yet `PushHandler#process` will operate on stacks belonging to `victim-org/victim-repo`:
```ruby
# app/models/shipit/webhooks/handlers/push_handler.rb
def process
  stacks.not_archived.where(branch:).find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
end
```
`sync_github(expected_head_sha:)` triggers `GithubSyncJob`, which fetches and records commits/state for the victim stack based on attacker-supplied `after` sha, and (depending on stack configuration/continuous-delivery settings) can advance the victim stack's known head and drive subsequent deploy scheduling — all without ever proving authorization from `victim-org`.

### Impact Explanation
This crosses an authentication boundary that the report class explicitly calls out: "an organization that authenticated versus the repository that is written." An attacker who is a legitimate GitHub App/webhook holder for their own onboarded organization (`attacker-org`) — a low-privilege, unprivileged-relative-to-other-tenants position — can forge webhook events attributed to an unrelated organization's repository (`victim-org/victim-repo`), causing Shipit to record fabricated commit/status/sync state and potentially trigger continuous-delivery deploy scheduling for stacks they have no legitimate relationship with. This matches the High-impact bucket: "unauthenticated read of stack state" is exceeded here — this is an unauthenticated **write** of stack state (synced commits, statuses) for a repository the attacker does not control, and depending on continuous delivery configuration this can cascade into "an unauthorized deploy."

### Likelihood Explanation
Likelihood is High in any Shipit deployment supporting multiple organizations (the multi-org `github_app_config` schema exists precisely for this), since:
- The only prerequisite is legitimate control of one organization's own webhook secret (from being onboarded normally as any tenant) — no privileged Shipit account, GitHub App private key, or repository write access to the victim is required.
- The mismatch is structural: `repository_owner` and `repository_name` are read independently from the same attacker-authored payload with no cross-check anywhere in `WebhooksController` or `Handler`.
- Any handler that derives `stacks` from `repository_name` (push, status, check_suite, deployable/merge status, pull_request) is affected identically.

### Recommendation
After `verify_signature` succeeds, bind the verified organization to the events actually processed: derive `repository_name`'s owner from the same value used for verification (`repository_owner`), and reject/short-circuit if `payload.dig('repository', 'owner', 'login')` does not case-insensitively match the owner segment of `payload.dig('repository', 'full_name')`. Alternatively, pass the verified `repository_owner` explicitly into each `Handler` and have `Repository.from_github_repo_name` require the owner segment to equal it, rather than trusting `full_name` outright.

### Proof of Concept
1. Onboard `attacker-org` in Shipit's multi-org `secrets.github` config (legitimately, as any tenant would) and obtain its `webhook_secret`.
2. Craft a push webhook payload:
```json
{
  "ref": "refs/heads/main",
  "after": "deadbeefdeadbeefdeadbeefdeadbeefdeadbeef",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. Compute `X-Hub-Signature: sha1=<hmac_sha1(attacker-org secret, body)>` and POST it to `/webhooks` with `X-Github-Event: push`.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: 'attacker-org')` and successfully verifies the signature using `attacker-org`'s secret (`app/controllers/shipit/webhooks_controller.rb`).

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
