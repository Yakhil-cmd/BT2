### Title
Status webhook writes CI status onto a Commit owned by a different repository's stack due to unscoped `Commit.where(sha:)` lookup - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` looks up commits solely by `sha` with no filter on the repository/stack that the webhook payload claims to be for, while every sibling handler (`PushHandler`, `CheckSuiteHandler`, all `PullRequest::*Handler`s) uses the base `Handler#stacks` helper which scopes lookups through `Repository.from_github_repo_name(repository_name)`. Because `sha` is a public, attacker-readable value and the only binding enforced before this code runs is that the payload's `X-Hub-Signature` matches the webhook secret for `payload['repository']['owner']['login']` (the attacker's own org), an attacker who owns a GitHub App/webhook for their own repo can forge a `status` event carrying a victim's commit sha and have Shipit write a `Status` row onto the victim's commit/stack.

### Finding Description
The binding that should hold is: `repository that authenticated the payload (params.dig('repository','owner','login'), verified in WebhooksController#verify_signature via Shipit.github(organization: repository_owner).verify_webhook_signature)` == `repository/stack owning the Commit record that gets mutated by commit.create_status_from_github!(params)`.

Trace:
- `Shipit::WebhooksController#create` (`app/controllers/shipit/webhooks_controller.rb:10-15`) parses the raw JSON body and dispatches to `Shipit::Webhooks.for_event(event)` handlers, with only `verify_signature` (line 24-49) gating the request. `verify_signature` resolves `Shipit.github(organization: repository_owner)` where `repository_owner` (line 59-62) is read straight from the attacker-controlled payload (`params.dig('repository','owner','login')`), then verifies HMAC using that org's own webhook secret — which the attacker legitimately possesses for their own GitHub App/org. This only proves "this payload was sent by whoever owns `attacker-org`"; it says nothing about which `sha` is safe to trust.
- `Shipit::Webhooks::Handlers::Handler` (`app/models/shipit/webhooks/handlers/handler.rb`) defines a `stacks` helper (line 32-34) and `repository_name` (line 36-38) that scope operations to `Repository.from_github_repo_name(payload.dig('repository','full_name'))`. Every other handler I inspected (`PushHandler`, `CheckSuiteHandler`, the `PullRequest::*` handlers) uses this scoping so that a payload can only ever mutate stacks belonging to the repository named in that same payload.
- `StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`) does not use `stacks`/`repository_name` at all. It runs `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` — a global, cross-tenant query against the entire `commits` table.
- `Commit#create_status_from_github!` (`app/models/shipit/commit.rb:165-169`) then calls `statuses.replicate_from_github!(stack_id, github_status)`, writing a `Status` (state/description/target_url/context) associated with that commit's actual `stack_id`, regardless of which org's secret authenticated the request.

Exploit: attacker registers/controls `attacker-org` (or any repo they legitimately own) with Shipit, obtaining a valid webhook secret for that org. They observe a public commit sha belonging to `victim-org/victim-repo` (commit shas are not secret — visible via GitHub UI/API, PR links, CI logs, etc.), then POST to `/webhooks` with header `X-Github-Event: status`, a body where `repository.owner.login = "attacker-org"` (so `verify_signature` succeeds using the attacker's own secret) but `sha` set to the victim's commit sha, `state`/`description`/`target_url` of their choosing. `StatusHandler` finds the `Commit` row for that sha (which belongs to the victim's `Stack`) and writes a forged status onto it — e.g. flipping it to `success` to force merge-gating/continuous-deployment (`Commit#schedule_continuous_delivery`, `add_status` in `commit.rb:366-386`) to fire, or to `failure`/`error` to block the victim's deploys.

Existing guards do not stop this: `verify_signature` only checks the signature against the org named in the payload (which the attacker legitimately controls), not against the org that actually owns the target commit; `drop_unhandled_event`, `ExplicitParameters` schema (`requires :sha, :state`, etc.) and `force_github_authentication` are irrelevant here since this is an unauthenticated webhook endpoint by design, gated only by signature. Nothing in `StatusHandler` cross-checks `payload['repository']['full_name']` against the found `Commit`'s `stack.repository`.

### Impact Explanation
A payload authenticated under attacker-org's webhook secret writes a `Status` row that changes CI/merge-gating signal (`state`, `description`, `target_url`, `context`) for a `Commit` belonging to an arbitrary victim `Stack`/`Repository`. This can spoof a passing status to trigger `deployable?`/`schedule_continuous_delivery` (potentially enabling continuous deployment of an unvetted commit) or spoof a failing status to block legitimate deploys/merges of the victim's stack — a cross-tenant payload-to-stack mutation, matching the "payload for one repository mutating another's stack/commit" Critical category. It is repeatable against any commit sha the attacker can discover (which is trivial for public repos, and even for private repos if the sha leaks via any channel), across arbitrarily many victim stacks, at will.

### Likelihood Explanation
Preconditions are low-cost and fully attacker-controlled: the attacker only needs a GitHub App/webhook already configured for one of their own orgs/repos in Shipit (a normal, unprivileged onboarding action), and the target victim commit sha, which is not a secret and is routinely public. No victim secrets, sessions, or elevated Shipit roles are required. The attack is a single crafted HTTP POST, trivially scriptable and repeatable.

### Recommendation
Scope `StatusHandler#process` the same way as the other handlers: resolve the payload's own repository (`repository_name`/`stacks` from the base `Handler`) and restrict the `Commit` lookup to commits under that repository's stacks, e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` or joining through `Stack`/`Repository` so a commit is only mutated if it belongs to a stack whose repository matches `payload['repository']['full_name']`.

### Proof of Concept
Minitest plan (`test/controllers/webhooks_controller_test.rb` style, no live GitHub):
1. Create two `Shipit::Stack`/`Shipit::Repository` fixtures: `victim_stack` owned by `victim-org/victim-repo`, and an `attacker_stack`/`Repository` owned by `attacker-org/attacker-repo` with its own webhook secret configured via `Shipit.github(organization: 'attacker-org')`.
2. Create a `Shipit::Commit` under `victim_stack` with `sha: 'deadbeef...'` and no existing status.
3. Build a `status` webhook JSON payload: `{"sha": "deadbeef...", "state": "success", "repository": {"full_name": "attacker-org/attacker-repo", "owner": {"login": "attacker-org"}}}`.
4. Sign the payload with attacker-org's webhook secret and POST it to `/webhooks` with `X-Github-Event: status`.
5. Assert response is `200`.
6. Assert `victim_commit.reload.statuses.last.state == 'success'` (or whatever state was injected) — proving a payload signed for `attacker-org` mutated a `Commit` belonging to `victim-org`'s stack.
7. Contrast/control assertion: before the fix, `victim_commit.stack` (`victim_stack`) is untouched by anything derived from `payload['repository']['full_name']` ("attacker-org/attacker-repo" != "victim-org/victim-repo"), demonstrating the broken equality `payload repository == commit's owning repository`.     def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping
      head(:ok) if event == 'ping'
    end

    def event
      request.headers.fetch('X-Github-Event')
    end

    def repository_owner
      # Fallback to the organization sub-object if repository isn't included in the payload
      params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
    end

    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
