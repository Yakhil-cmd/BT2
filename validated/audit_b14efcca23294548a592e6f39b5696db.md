This maps well to a valid analog. The `max_receipt_size` cap exists in the runtime config and is checked in `validate_receipt` at receipt creation time, but this check happens too early: it validates the receipt's size at construction, before later mutations (`output_data_receivers` appended via `promise_return`, or `value_return` wrapping into a data receipt) can push the actual persisted/forwarded receipt size above the configured `max_receipt_size` cap. This is the exact "cap exists but isn't enforced at the point that matters" bug class from the report, applied to a state/bandwidth accounting limit instead of a token supply cap.

### Title
`max_receipt_size` cap is checked before receipt mutation, allowing oversized receipts into state and congestion accounting - ([File: runtime/runtime/src/verifier.rs])

### Summary
The receipt-size cap `max_receipt_size` is enforced by `validate_receipt` at the time a receipt is first constructed, but `output_data_receivers` (via `promise_return`) and value-return wrapping into a `DataReceipt` can later add bytes to that same receipt after the size check has passed, producing receipts that exceed the protocol's configured limit.

### Finding Description
`validate_receipt` computes `borsh::object_length(receipt)` and rejects it if greater than `limit_config.max_receipt_size`, but only when `mode == ValidateReceiptMode::NewReceipt` [1](#0-0) . The `ValidateReceiptMode::ExistingReceipt` variant is explicitly documented as needed because "there is a bug which allows to create receipts that are above the size limit," referencing near/nearcore#12606 [2](#0-1) .

The root cause is that a promise's receipt can be validated for size at creation, and then have its `output_data_receivers` field populated afterward via `promise_return`, or have a large `value_return` wrapped into a subsequent `DataReceipt`, both of which happen after the size gate has already passed, so the final persisted/forwarded receipt is never re-checked against `max_receipt_size`. This is confirmed by test comments and code in `test-loop-tests/src/tests/max_receipt_size.rs`: `test_max_receipt_size_promise_return` and `test_max_receipt_size_value_return` are documented as "should be rejected, but currently isn't because of a bug" [3](#0-2) [4](#0-3) .

Downstream, `try_forward` in the congestion/bandwidth accounting path has an explicit workaround acknowledging that oversized receipts exist and clamps their accounted size to `max_receipt_size` to avoid them getting permanently stuck in state, rather than rejecting them [5](#0-4) . This is functionally identical to the `OmoVault` bug class: a cap (`supplyCap` / `max_receipt_size`) exists and has a setter/config, but the enforcement point in the code path that actually matters (before the value is durably recorded/forwarded) is missing or bypassed, letting the tracked quantity exceed the configured limit.

### Impact Explanation
Receipts above `max_receipt_size` defeat the purpose of the size limit, which exists specifically to bound the size of `ChunkStateWitness` (target ~17 MiB total) [6](#0-5) . Uncontrolled oversized receipts can inflate state witness size beyond the bounds validators expect, increasing bandwidth/storage/proof overhead in the receipt pipeline and creating class of "receipts getting stuck" in the congestion/bandwidth-buffer accounting that the `try_forward` comment explicitly calls out as a risk being worked around [7](#0-6) .

### Likelihood Explanation
This is reachable by any unprivileged contract deployer/caller: a contract using `promise_return` to swap the returned promise for a bigger one, or returning a large value from a callback, can trigger the bug without any special privileges, as demonstrated by the reproducing test cases [8](#0-7) [9](#0-8) .

### Recommendation
Re-validate (or re-derive) the final receipt size against `limit_config.max_receipt_size` after all mutations that can add bytes (`output_data_receivers` assignment from `promise_return`, and `DataReceipt` construction from `value_return`) are applied, immediately before the receipt is persisted or queued for forwarding, so `ValidateReceiptMode::NewReceipt` checks cannot be bypassed by post-construction mutation. The `try_forward` size-clamping workaround in `congestion_control.rs` should be removed once the receipt can no longer be created oversized.

### Proof of Concept
`test_max_receipt_size_promise_return` and `test_max_receipt_size_value_return` in `test-loop-tests/src/tests/max_receipt_size.rs` reproduce the issue: a contract call constructs a receipt at exactly `max_receipt_size`, passes the `ReceiptSizeExceeded` check, and then has `output_data_receivers` (or a large returned value wrapped as a `DataReceipt`) appended afterward, producing a receipt whose real size exceeds `max_receipt_size` without triggering `ReceiptValidationError::ReceiptSizeExceeded` [10](#0-9) [11](#0-10) .

```markdown
## State witness size limits

Some limits were introduced to keep the size of `ChunkStateWitness` reasonable.
`ChunkStateWitness` contains all the incoming transactions and receipts that will be processed during chunk application and in theory a single receipt could be tens of megabytes in size. Distributing a `ChunkStateWitness` this large would be troublesome, so we limit the size and number of transactions, receipts, etc. The limits aim to keep the total uncompressed size of `ChunkStateWitness` under 17MiB.

There are two types of size limits:

* Hard limit - the size must be below this limit, anything else is considered invalid
* Soft limit - things are added until the limit is exceeded, after that things stop being added. The last added thing is allowed to slightly exceed the limit.

The limits are:

* `max_transaction_size = 1.5 MiB`
  * All transactions must be below 1.5 MiB, otherwise they'll be considered invalid and rejected.
  * Previously was 4MiB, now reduced to 1.5MiB
* `max_receipt_size - 4 MiB`:
  * All receipts must be below 4 MiB, otherwise they'll be considered invalid and rejected.
  * Previously there was no limit on receipt size. Set to 4MiB, might be reduced to 1.5MiB in the future to match the transaction limit.
```
