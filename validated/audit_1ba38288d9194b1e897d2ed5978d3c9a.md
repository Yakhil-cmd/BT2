### Title
Webhook signature verification checks the wrong organization, allowing cross-repository event forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
The reported bug class is a broken binding between the entity that is verified and the entity that is acted upon (`potCreator` learns the random value before the check that is supposed to be unpredictable resolves, so the verified value and the used value diverge). The same class of bug exists in Shipit's webhook pipeline: the field used to select and verify the HMAC signature (`repository.owner.login`) is not the field used to determine which stack/repository the event is applied to (`repository.full_name`). Since both fields live inside the same attacker-suppliable JSON body, an entity that only controls credentials for one organization onboarded to a shared Shipit instance can forge a webhook body that verifies against its own organization's secret while acting on a completely different organization's repository.

### Finding Description
`WebhooksController#verify_signature` selects which GitHub App/organization secret to verify against using the `repository.owner.login` (or `organization.login`) field of the untrusted JSON body, and then verifies the HMAC of the *entire raw body* with that secret: [1](#0-0) [2](#0-1) 

Once the signature check passes, the event is dispatched to handlers (e.g. `PushHandler`) via `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`: [3](#0-2) 

Every handler resolves the target stack(s) not from `repository.owner.login` (the field that was authenticated) but from `repository.full_name` inside the same payload: [4](#0-3) 

`PushHandler#process` then invokes `stack.sync_github(expected_head_sha: params.after)` for every matching, non-archived stack on the target branch: [5](#0-4) 

Because the HMAC only proves "this body was signed with organization X's webhook secret," not "the repository named inside this body belongs to organization X," an attacker who knows any one organization's webhook secret (e.g. because they control their own org/GitHub App that is also configured on the same shared Shipit instance) can craft a JSON body where `repository.owner.login` is their own org (so signature verification picks and passes against their own known secret) while `repository.full_name` names a victim's repository/stack tracked by the same instance. This breaks the equality that the report's bug class is about: **organization authenticated == repository acted upon** is assumed but never enforced.

### Impact Explanation
This lets an attacker who is not authorized on the victim repository trigger webhook-driven side effects against that repository's stacks purely by holding valid credentials for an unrelated organization on the same Shipit deployment. Depending on which webhook event is replayed with a forged `repository.full_name`, this can force out-of-band GitHub syncs (`sync_github`), and more broadly reaches any handler under `app/models/shipit/webhooks/handlers/**` that trusts `repository.full_name` after a signature check keyed on `repository.owner.login`/`organization.login` — this includes status, merge, and pull-request handlers that influence deployability and merge state of a stack the attacker does not control. This is a cross-organization/cross-repository write primitive gated only by possession of a webhook secret unrelated to the victim, matching the "authenticated organization vs. repository written" trust boundary called out as in-scope.

### Likelihood Explanation
Exploitability depends entirely on the deployment topology: it requires a multi-tenant Shipit instance where more than one organization's GitHub App/webhook secret is configured (`Shipit.github(organization: ...)`), and the attacker controls (or can obtain) the secret for at least one such organization without needing any credential belonging to the victim organization or repository. This is a realistic configuration for a shared Shipit install serving multiple GitHub orgs.

### Recommendation
After signature verification, re-validate that `repository.owner.login` (the organization used to select/verify the secret) matches the owner encoded in `repository.full_name` before dispatching to handlers, and have handlers reject payloads where these two fields disagree, rather than trusting `full_name` unconditionally in `Handler#repository_name`.

### Proof of Concept
1. Attacker controls organization `attacker-org`, which has its own GitHub App installed on the shared Shipit instance with webhook secret `S_attacker` (known to the attacker as they configured that GitHub App).
2. Victim organization `victim-org/victim-repo` has a stack tracked on the same Shipit instance.
3. Attacker POSTs to `/webhooks` a JSON body:
   ```json
   {
     "ref": "refs/heads/main",
     "after": "<attacker-chosen sha>",
     "repository": {
       "owner": { "login": "attacker-org" },
       "full_name": "victim-org/victim-repo"
     }
   }
   ```
   with header `X-Github-Event: push` and `X-Hub-Signature` computed as `sha1=HMAC(S_attacker, body)`.
4. `verify_signature` calls `Shipit.github(organization: "attacker-org")` (from `repository.owner.login`), verifies the HMAC against `S_attacker`, and passes.
5. `PushHandler#process` resolves stacks via `Repository.from_github_repo_name("victim-org/victim-repo")` and calls `sync_github(expected_head_sha: "<attacker-chosen sha>")` on the victim's stack — an action the attacker was never authorized to trigger.
