### Title
Missing Cosigner-Authorization Check on Device `"sign"` Request Handler Allows Any Paired Correspondent to Trigger Signing Requests for Arbitrary Local Wallet Addresses - ([File: wallet.js])

### Summary
The device-message handler for the `"sign"` subject in `handleMessageFromHub` (wallet.js) accepts a signing request from **any** paired correspondent device and, for addresses that are locally hosted (`ifLocal`), immediately proceeds to trigger the signing flow without verifying that the requesting device (`from_address`) is actually an authorized cosigner of the target `body.address`. This mirrors the Devtron pattern of accepting attacker-supplied identifiers (there: project/env/app; here: `address`/`signing_path`/`unsigned_unit`) and returning/acting on privileged data without an object-level authorization check tying the caller to the resource.

### Finding Description
In `wallet.js`, the `"sign"` case parses and validates the *shape* of the incoming request (valid address, signing path regex, well-formed unit, payload-hash consistency, etc.) but performs no check that the sender of the message (`from_address`) is entitled to request a signature on `body.address` via `body.signing_path`: [1](#0-0) [2](#0-1) 

Specifically:
```

The comment itself documents that the authorization check (verifying the sender is a genuine cosigner via `extended_pubkeys`/wallet membership) was deliberately disabled. By contrast, the `ifRemote` branch of the very same handler *does* perform an equivalent check:
```
ifRemote: function(device_address, other_device_addresses){
    if (device_address === from_address)
        return callbacks.ifError("looping signing request for address "+body.address+", path "+body.signing_path);
    if (!other_device_addresses.includes(from_address))
        return callbacks.ifError("you are not listed as a cosigner for this address "+body.address);
``` [4](#0-3) 

This asymmetry means: for any address that is locally hosted on the victim device (`ifLocal`), the missing-check path is reached, and the handler goes straight to constructing/queuing a signing request and firing the `"signing_request"` event with attacker-supplied `objUnit` content: [5](#0-4) 

`findAddress` only confirms that `body.address` belongs to one of the victim's own wallets/approved shared addresses — it does not verify the caller's relationship to that address at all: [6](#0-5) 

The only remaining gate is `handleJustsaying`'s check that the message comes from a *known correspondent* (any paired contact, not necessarily a cosigner of the target address) or a whitelisted non-correspondent subject: [7](#0-6) 

### Impact Explanation
Any device that is merely paired as a correspondent (a normal chat contact, not necessarily a cosigner of the target multisig/shared address) can send a crafted `"sign"` device message naming any of the victim's local addresses and an arbitrary `unsigned_unit`. The victim's wallet will accept the request (bypassing the intended cosigner-authorization check) and surface a signing confirmation dialog populated with attacker-controlled transaction data via the `"signing_request"` event, rather than rejecting the request outright as "sender is not cosigner of this address." This expands the attack surface for social-engineering-driven unauthorized signing/spending on shared/multisig addresses to any paired contact instead of being restricted to legitimate cosigners, directly analogous to the Devtron flaw where an authenticated-but-unauthorized caller could act on arbitrary resource identifiers because the ownership/authorization check was missing.

### Likelihood Explanation
Exploitation only requires that the attacker's device be an existing correspondent of the victim (a common, low-friction pairing relationship in Obyte's wallet/chat model), and that the victim hosts the targeted address locally (`ifLocal`). No cryptographic material needs to be compromised to reach the vulnerable code path — the missing check is unconditional for local addresses. The remaining barrier to fund loss is UI confirmation by the victim, which is exactly the kind of authorization boundary this check was meant to reinforce before ever reaching the user.

### Recommendation
Restore (or replace with an equivalent, multilateral-signing-compatible) authorization check in the `ifLocal` branch of the `"sign"` handler, verifying that `from_address` is a legitimate cosigner/member device for `body.address` (e.g., via `extended_pubkeys`/wallet membership or `shared_address_signing_paths`) before emitting `"signing_request"`, mirroring the check already present in the `ifRemote` branch.

### Proof of Concept
1. Attacker device A pairs with victim device V as an ordinary correspondent (no shared/multisig address involvement required).
2. V hosts local address `ADDR` belonging to a wallet (single-sig or as one cosigner of a shared address) that is fully approved (`full_approval_date` set).
3. A sends a `hub/message`-wrapped device message to V with `subject: "sign"`, `body: { address: ADDR, signing_path: "r", unsigned_unit: <attacker-crafted transaction> }`.
4. In `handleMessageFromHub`, the `"sign"` case validates only the message's structural fields, then calls `findAddress(ADDR, "r", {...})`, which resolves to `ifLocal` because `ADDR` is hosted on V.
5. Because the cosigner check is commented out, `callbacks.ifOk()` is called and the `"signing_request"` event is emitted with A's crafted unit — with no error such as "sender is not cosigner of this address," even though A has no relation to `ADDR`. [8](#0-7)
