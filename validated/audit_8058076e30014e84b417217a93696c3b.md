### Title
Attacker-controlled swap route invokes arbitrary pool/token contracts beneath the caller's signed authorization, draining the caller's wallet - (File: contracts/controller/src/strategies/swap.rs)

### Summary
CVE-2018-10472 is a "trusted resolver follows an untrusted pointer" bug: Xen resolved a guest-supplied backing-file path and gave the guest read access to arbitrary dom0 files. The analog in XOXNO Lending is the strategy swap path: `swap_debt`, `swap_collateral`, `repay_debt_with_collateral`, and `multiply` accept fully caller-supplied `swap: Bytes` route payloads, and the router invokes whatever pool and token addresses the payload names — with no on-chain allowlist. Code inside a named hop can issue a `token.transfer(caller, attacker, x)` that Soroban attaches as a child of the caller's own authorization entry, so a signed route steals wallet funds unrelated to the swap.

### Finding Description
`swap_tokens` snapshots balances, authorizes only the exact input transfer to the configured router, and executes `router.execute_strategy(&controller, &amount_in, swap)` with the attacker-controlled payload [1](#0-0) . The threat model confirms the router "calls the pool and token addresses its payload names and keeps no allowlist of them, so a route can put third-party code on the call stack below the caller's authorization," and that such a transfer "executes if the caller signs that tree. The loss is then the caller's wallet, not the routed amount, and neither the payload minimum nor the final risk gate bounds it" [2](#0-1) . The harness test `rogue_hop_pool_transfer_joins_caller_auth_tree.rs` demonstrates this end-to-end through `swap_collateral`: a `RogueHopPool` named in the route calls `token::Client::transfer(victim, attacker, WALLET_BALANCE)` inside its `swap` hop, simulation records it as a child of Alice's `swap_collateral` entry, and her wallet is drained while the strategy itself settles "fairly" [3](#0-2) [4](#0-3) . Like the CVE's backing-file path, the `assets`/pool registry inside `swap` bytes is an unvalidated external pointer resolved by trusted code under the victim's authority.

### Impact Explanation
Theft of user funds: any token balance held by the signing address — including assets the protocol never lists — can be transferred out in the same transaction, unbounded by `amount_in`, `total_min_out`, or the final health-factor gate. The exposure applies to every `swap_collateral`/`swap_debt`/`repay_debt_with_collateral`/`multiply` caller and to direct `execute_strategy` users.

### Likelihood Explanation
Exploitation requires the victim to sign a route whose authorization tree contains the malicious child invocation; an attacker must get a poisoned `swap` payload in front of a signer (malicious quote, compromised route builder, or phishing a delegate/strategy contract). Soroban wallets can display the auth tree, and the docs shift detection to the client ("a client must decode the route it signs and refuse an authorization tree with any other child"), but no contract-side enforcement exists, so a signer relying only on route economics loses funds. Medium: real theft, conditioned on signature of the poisoned tree.

### Recommendation
Constrain the trusted-resolver surface on-chain rather than relying on client-side route decoding:
- Maintain a governance-managed venue/pool allowlist in the router and reject hops naming unlisted pools or token addresses outside the declared `token_in`/`token_out` path.
- Alternatively, wrap the route execution in a context where the caller's authorization cannot be inherited by payload-named contracts (e.g., have the router pull input from the controller, never `sender`, so hop contracts run below the router's authority only).
- Document and enforce that delegates/strategy contracts must reject routes whose decoded registry contains unexpected addresses.

### Proof of Concept
See `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs`: the test registers `UnlistedPoolRouter` as the swap aggregator, builds a `RoutedSwap` whose `hop_pool` is an attacker-deployed `RogueHopPool` storing `(victim=alice, wallet_token, to=attacker, amount=WALLET_BALANCE)`, and calls `ctrl.try_swap_collateral(alice, account_id, USDC, 5_000 USDC, ETH, route)`. The hop executes `token.transfer(alice, attacker, WALLET_BALANCE)` [5](#0-4) ; the recorded authorization tree contains the stolen transfer as a child of Alice's `swap_collateral` entry, `wallet(alice) == 0`, `wallet(attacker) == WALLET_BALANCE`, and the strategy still credits `FAIR_OUT_ETH` so all controller checks pass [6](#0-5) .

#[test]
fn simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry() {
    let s = Scene::new();
    let route = s.route_through_pool_stealing(WALLET_BALANCE);

    // `simulateTransaction` runs recording mode with non-root auth disabled.
    s.t.env.mock_all_auths();
    s.try_swap(&route)
        .expect("recording mode accepts the route");
    let recorded = s.t.env.auths();
    std::println!("recorded auth tree = {recorded:#?}");

    let stolen_transfer = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.wallet_token.clone(),
            symbol_short!("transfer"),
            (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),
        )),
        sub_invocations: std::vec![],
    };
    let poisoned_root = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.t.controller.clone(),
            Symbol::new(&s.t.env, "swap_collateral"),
            s.swap_args(&route),
        )),
        sub_invocations: std::vec![stolen_transfer],
    };
    assert_eq!(recorded, std::vec![(s.alice.clone(), poisoned_root)]);

    assert_eq!(s.wallet(&s.alice), 0);
    assert_eq!(s.wallet(&s.attacker), WALLET_BALANCE);
    assert_eq!(s.t.supply_balance_raw(ALICE, "ETH"), FAIR_OUT_ETH);
}
