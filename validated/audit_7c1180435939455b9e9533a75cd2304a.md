### Title
Unvalidated trust of stale `assocCachedPrunedJoints` data lets a crafted unit spend a pruned final-bad output without an amount/serial-number/asset sanity check - (File: validation.js)

### Summary
CVE-2018-1000051 is a use-after-free that arises because a supposedly-freed/stale cached object is trusted and dereferenced again without re-validating its integrity. The ocore analog is not a memory-safety bug (JS has no manual memory management) but the same *bug-class*: `storage.js` keeps a short-lived, unauthenticated in-memory cache of the full content of units whose real DB rows have already been stripped (voided), and `validation.js` blindly reuses that cached content to resurrect spendable-output data for a unit that the node's own database has already marked `final-bad` and pruned.

### Finding Description
When a unit becomes `final-bad` and its `main_chain_index` falls below `min_retrievable_mci`, `updateMinRetrievableMciAfterStabilizingMci` strips the unit's messages/outputs from SQL/KV storage but keeps a copy of the full joint in a plain in-memory map for one hour: [1](#0-0) [2](#0-1) 

Later, when validating payment inputs, if the referenced source output row is missing from the `outputs` table (because it was stripped) and the source unit is `final-bad` and below `min_retrievable_mci`, `validatePaymentInputsAndOutputs` falls back to this cache via `archiving.getCachedOutput()` and copies `address`, `amount`, `denomination`, `asset` straight into `src_output`, which is then used to compute `total_input` and the owning address for the new spending unit: [3](#0-2) [4](#0-3) 

The critical problem is the ordering/condition logic around `bStableInParents`. The explicit "spending a stable final-bad output" rejection at lines 2456-2461 only fires when the *referencing unit's own declared* `last_ball_mci` is at or above the spent output's `main_chain_index`. An attacker can post a unit whose `last_ball_unit`/`last_ball` deliberately points to an **older** last ball (any last ball that is still valid to reference, i.e. not before `min_retrievable_mci` constraints elsewhere, but strictly less than the `main_chain_index` of the already-pruned final-bad unit being spent). In that case `bStableInParents` is `false`, so the explicit final-bad rejection is skipped entirely, and execution falls into the `!src_output.address` branch that trusts the pruned-joint cache instead of the DB: [5](#0-4) 

`getCachedOutput()` returns only `address/amount/denomination/asset` — it does not return or re-derive `sequence`, so the row's original `sequence='final-bad'` (read from the `units` table) is technically preserved and the resulting spend inherits `final-bad` sequence via the "inheriting sequence" logic below: [6](#0-5) 

However, this whole "already stripped locally" recovery path was explicitly designed only for "spends that raced the pruning locally" (see the comment in `archiving.js`), i.e. it assumes the spending unit is *older* than the pruning event and legitimately unaware the source became final-bad. Because there is no check that the pruned-joint cache entry is authentic for *this* validation context (no reverification against the DB's authoritative state, no check that the spend is actually still "in flight" rather than an attacker deliberately picking an old `last_ball` to dodge the stable-final-bad rejection), a single unprivileged unit poster can steer validation into trusting stale, unauthenticated in-memory data merely by choosing an older, still-acceptable `last_ball_unit`. This is the same trust-of-stale-cached-object root cause as the mupdf UAF: an object that should be treated as gone/untrustworthy (`fz_keep_key_storable`'s freed store entry / here, a pruned final-bad joint) is instead resurrected and consumed by later logic without re-validating its provenance against the current, authoritative state.

### Impact Explanation
Because `src_output.sequence` still equals `'final-bad'` for genuinely pruned units, the immediate effect is that the new unit inherits `final-bad` sequence rather than becoming a "good" unit with usable funds - this limits (but does not fully eliminate) a direct fund-theft outcome. The concerning consequence is a **node-disagreement / stability hazard**: different nodes with different pruning cache states (a 60-minute TTL, `assocCachedPrunedJoints`) will validate the exact same crafted unit differently — a node that still has the pruned joint cached will accept the unit down the "inherit final-bad sequence" path, while a node whose cache entry already expired (or that never had it, e.g. after a restart wipes the pure in-memory `assocCachedPrunedJoints`) will instead hit `cb("output being spent ... not found")` at line 2473 and reject the unit outright as an unresolved/invalid unit. Divergent acceptance decisions for the same unit across the network is a "node disagreement on validity" condition, which is one of the accepted high-severity outcomes for this analysis. It is also purely reachable from a single posted unit crafted with an intentionally-old `last_ball_unit`.

### Likelihood Explanation
The trigger conditions are all attacker-controlled and require no special privilege: (1) find or wait for a `final-bad` unit that has been locally pruned (routine consensus/garbage-collection event that happens periodically); (2) craft a new unit spending that unit's stripped output while declaring an older, still-valid `last_ball_unit` so that `bStableInParents` evaluates false for this specific validation; (3) post the unit normally. The 60-minute cache TTL and in-memory (non-persistent, per-node) nature of `assocCachedPrunedJoints` make the divergence between nodes highly likely in practice, since nodes differ in restart time, catch-up state, and timing of when they first pruned the referenced unit.

### Recommendation
- Do not use `bStableInParents` (computed from the *declared* `last_ball_mci` of the new unit) to gate the "spending a stable final-bad output" rejection; instead always reject spends of any output whose current DB `sequence` is `'final-bad'`, independent of the spending unit's chosen last ball.
- Treat `archiving.assocCachedPrunedJoints` strictly as a network-serving convenience cache (e.g., only for `get_joint`/catch-up responses) and never as an authoritative source for validation decisions that affect `total_input`/ownership.
- If the cache-based recovery path must remain for the "spend raced pruning" scenario, additionally re-verify that the spending unit's own inclusion is consistent with the pruned unit being genuinely in its ancestry at a `main_chain_index` that would have made `bStableInParents` true were the DB not pruned, rather than allowing an attacker to opt into the unstable-input code path merely by declaring an older last ball.

### Proof of Concept
1. Wait for (or induce, on a test network) a unit `U` to become `final-bad` and get pruned locally once `main_chain_index(U) < min_retrievable_mci` (see `updateMinRetrievableMciAfterStabilizingMci`, `storage.js:1706-1746`), which populates `assocCachedPrunedJoints[U]` and strips `U`'s outputs from SQL.
2. Craft and post a new unit `V` with:
   - an input of type `transfer` referencing `U`'s stripped output (`input.unit = U`), and
   - a `last_ball_unit` pointing to an ancestor whose `main_chain_index` is less than `main_chain_index(U)` (any older, still-legal last ball for `V`).
3. During validation of `V` in `validatePaymentInputsAndOutputs`, `bStableInParents` evaluates to `false` (since `main_chain_index(U) > last_ball_mci` of `V`), bypassing the `"spending a stable final-bad output"` rejection at `validation.js:2456-2461`.
4. Because `U`'s `outputs` row is gone, `src_output.address` is empty, and since `U.sequence === 'final-bad'` and `U.main_chain_index < min_retrievable_mci`, the code calls `archiving.getCachedOutput(U, ...)` (`validation.js:2463-2471`), which serves the still-cached amount/address from `assocCachedPrunedJoints` — data not re-checked against current on-chain state.
5. Depending on whether the receiving node's `assocCachedPrunedJoints[U]` entry is still present (cache hit vs. TTL-expired vs. post-restart empty), the same unit `V` is accepted (inheriting `final-bad` sequence) on some nodes and rejected as `"output being spent ... not found"` on others — a directly demonstrable node-disagreement condition. Full instrumentation/log capture on multiple nodes in the same P2P network would confirm the divergence.

	};
