### Title
MultiEdit `new_text`/`content` extraction crashes on malformed `edits` entries, causing hookify's blanket exception handler to fail-open and allow blocked file writes - ([File: plugins/hookify/core/rule_engine.py])

### Summary
`RuleEngine._extract_field` builds the `new_text`/`content` value for `MultiEdit` via `' '.join(e.get('new_string', '') for e in edits)` [1](#0-0)  without validating that each `edits` entry is a dict whose `new_string` is a string. A single malformed entry (a non-dict item, or a `new_string` that is itself a list/dict) raises `AttributeError`/`TypeError` inside rule evaluation, which propagates out of `evaluate_rules` uncaught by the engine. Both hook entry points (`pretooluse.py`, and presumably `posttooluse.py`) wrap the whole evaluation in a blanket `try/except Exception` that, on *any* error, prints a systemMessage and **always allows the operation** (`sys.exit(0)` in the `finally` block, no deny decision) [2](#0-1) . This lets a MultiEdit call carrying malicious content bypass a configured `block` rule that targets `new_text`/`content` via `regex_match`.

### Finding Description
The vulnerable extraction path is:

```
elif tool_name == 'MultiEdit':
    ...
    elif field in ['new_text', 'content']:
        edits = tool_input.get('edits', [])
        return ' '.join(e.get('new_string', '') for e in edits)
``` [3](#0-2) 

If `edits` contains an entry that is not a dict (e.g. a string, `None`, or nested list), `e.get(...)` raises `AttributeError`. If an entry is a dict but its `new_string` value is a nested structure (list/dict) rather than a string, `str.join()` raises `TypeError: sequence item N: expected str instance, ... found`. Either exception bubbles up through `_extract_field` → `_check_condition` → `_rule_matches` → `evaluate_rules` unguarded — there is no try/except anywhere in `rule_engine.py` around this logic.

The hook script that calls `evaluate_rules` treats *all* exceptions identically to "no rules matched": it catches the exception, emits an informational `systemMessage`, and still exits `0` without ever returning a `deny` `hookSpecificOutput` [2](#0-1) . This means a `PreToolUse` block rule intended to stop a dangerous MultiEdit (e.g., a rule matching secret-looking strings written into a tracked file) is silently defeated: the crash converts an intended `deny` into an unconditional `allow`, and the actual MultiEdit tool call still proceeds through Claude Code's normal execution and writes the file.

Because `tool_input` for `MultiEdit` is attacker-influenceable content (e.g., produced by the model acting on prompt-injected instructions embedded in repository files, issue/PR text, or MCP/tool output that gets copied into the `edits` array), an attacker does not need direct control of the hook — only the ability to get such a malformed `edits` structure into a MultiEdit call that also carries the malicious payload elsewhere (or even within the same malformed entry, since it never gets checked against the pattern once the exception fires).

A secondary, non-crashing evasion also exists: because entries are joined with a literal space (`' '.join(...)`), an attacker can fragment a contiguous secret string across two `new_string` values (e.g. `"SECR"` and `"ET_KEY=xxx"`), producing `"SECR ET_KEY=xxx"` for matching purposes while the actual file content written by the real MultiEdit tool remains contiguous `"SECRET_KEY=xxx"`, breaking any `regex_match`/`contains` pattern that expects contiguity.

### Impact Explanation
This is a workspace/file-write authorization bypass: a `block`-action rule configured to prevent dangerous file mutations (e.g., writing secrets or malicious code into a tracked file) via `regex_match` on `new_text` can be evaded solely by structuring the `MultiEdit` `tool_input` in an unusual (malformed or fragmented) way. The dangerous edit proceeds unblocked because the hook fails open on the internal exception, matching the bounty category of unauthorized file mutation / hook enforcement bypass.

### Likelihood Explanation
Exploitability only requires the ability to influence the `edits` array of a `MultiEdit` tool call — reachable whenever the model incorporates untrusted content (repo files, PR/issue text, MCP tool responses) into tool-call construction, a realistic and repeatable condition since no legitimate schema validation of `edits` entries occurs before rule evaluation. The crash is deterministic given a malformed entry, and the fail-open behavior in the hook wrapper is unconditional for any exception type.

### Recommendation
- In `_extract_field`, defensively validate each `edits` entry: skip or coerce non-dict entries and non-string `new_string` values instead of letting `.get`/`.join` raise.
- Change the hook's exception handling to fail-closed (or at least surface a clear warning and deny) when rule evaluation itself errors on a security-relevant tool (`Edit`/`Write`/`MultiEdit`), rather than unconditionally allowing the operation on any exception [2](#0-1) .
- Concatenate MultiEdit `new_string` values without an artificial space separator (or use an unlikely-to-occur delimiter and normalize before matching) to avoid enabling contiguous-payload fragmentation evasion.

### Proof of Concept
Unit test in `rule_engine.py`'s test style / pytest:

```python
def test_multiedit_malformed_entry_crashes_and_hook_fails_open():
    from hookify.core.config_loader import Condition, Rule
    from hookify.core.rule_engine import RuleEngine

    rule = Rule(
        name="block-secret-write",
        enabled=True,
        event="file",
        tool_matcher="MultiEdit",
        conditions=[Condition(field="new_text", operator="regex_match", pattern=r"SECRET_KEY=")],
        action="block",
        message="Blocked secret write",
    )
    engine = RuleEngine()

    # Baseline: contiguous single-Edit-equivalent content triggers block
    baseline_input = {
        "tool_name": "MultiEdit",
        "tool_input": {"file_path": "app/config.py",
                        "edits": [{"old_string": "", "new_string": "SECRET_KEY=abc123"}]},
    }
    assert engine.evaluate_rules([rule], baseline_input) != {}

    # Malformed entry: new_string is a nested list -> str.join raises TypeError,
    # which is NOT caught inside rule_engine.py.
    malicious_input = {
        "tool_name": "MultiEdit",
        "tool_input": {"file_path": "app/config.py",
                        "edits": [{"old_string": "", "new_string": ["SECRET_KEY=abc123"]}]},
    }
    import pytest
    with pytest.raises(TypeError):
        engine.evaluate_rules([rule], malicious_input)
```
