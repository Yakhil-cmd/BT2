Based on my investigation, I found a concrete analog in `indivisible_asset.js`'s private-payment validation logic, in the function `validatePrivatePayment` (this handles private (indivisible) asset payment chains delivered as device messages between wallets, exactly the class of surface named in scope: "private payment chains" / "wallet and contract message handling").

### Title
Missing bounds check on attacker-controlled `output_index` when indexing `partially_revealed_payload.outputs[]` in indivisible private payment validation - (File: indivisible_asset.js)

### Summary
`validatePrivatePayment()` in `indivisible_asset.js` builds the "our_output" reference by indexing the payload's `outputs` array with `objPrivateElement.output_index`, an attacker-supplied field from a private-payment chain element received over the wallet device-messaging channel, without first checking that `output_index` is within the bounds of `payload.outputs`.

### Finding Description
Earlier in the same function, `objPrivateElement.output_index` is validated only for the *previous* element's output (`prev_hidden_output = objPrevPrivateElement.payload.outputs[input.output_index]`, guarded by `if (!prev_hidden_output) return callbacks.ifError(...)`), [1](#0-0) . However, later in the same function, when building `our_output`, the code does:
```
var our_output = partially_revealed_payload.outputs[objPrivateElement.output_index];
our_output.address = objPrivateElement.output.address;
our_output.blinding = objPrivateElement.output.blinding;
``` [2](#0-1) 
There is no check that `objPrivateElement.output_index` is a valid index into `partially_revealed_payload.outputs` (i.e., `< outputs.length`) before this access — unlike the analogous, correctly-guarded access to `prev_hidden_output` a few lines above it in the same function. If `output_index` is out of range, `our_output` is `undefined`, and the subsequent property assignment `our_output.address = ...` throws a `TypeError` (accessing a property of `undefined`).

This mirrors the CVE-2026-23180 pattern exactly: an index taken from unvalidated external input (there, the IRQ status register; here, an attacker-supplied private-payment element) is used to index into an array without a bounds check, even though a **consistent, existing validation pattern for a sibling field in the same function** demonstrates the fix was known and applied elsewhere but omitted here.

Earlier in the call chain, `objPrivateElement.output_index` is checked only for `isNonnegativeInteger`, not for being within array bounds, [3](#0-2) . This one check is insufficient to prevent access beyond the end of `payload.outputs`.

### Impact Explanation
Private payment chains are processed via `validateAndSavePrivatePaymentChain` / `validatePrivatePayment`, invoked when a wallet receives a private-asset payment chain from a counterparty over the private/device-messaging channel [4](#0-3) . A malicious private-payment counterparty can craft a payload where `output_index` exceeds `payload.outputs.length`, causing an uncaught `TypeError` inside the wallet process handling the payment. Because this code path executes without a try/catch boundary that gracefully converts the exception into an `ifError` callback, the exception propagates up and can crash the wallet/light-client process that is validating and attempting to save the private payment, denying that wallet the ability to receive/process the payment (funds effectively become unusable/stuck for that recipient flow) and potentially crashing the node process handling AA / wallet private payment reception.

### Likelihood Explanation
Likelihood is high for any private-payment counterparty (a normal, unprivileged actor in a private payment negotiation) since crafting `output_index` values outside of the bounds of `outputs` requires no special privileges — it is a simple integer field in the JSON payload of a private-payment chain element sent directly by the paying party to the receiving wallet.

### Recommendation
Add a bounds check on `objPrivateElement.output_index` against `partially_revealed_payload.outputs.length` (and validate that the corresponding element is a non-empty object), consistent with the existing check performed for `prev_hidden_output` earlier in the same function, before dereferencing `our_output`.

### Proof of Concept
A malicious private-payment counterparty constructs a private-payment chain element (`objPrivateElement`) with:
- `payload.outputs`: an array of length 1 (or 2)
- `output_index`: e.g., `5` (out of range)
- All other fields (`asset`, `denomination`, `output`, `output.address`, `output.blinding`, spend proof, etc.) crafted to pass the earlier checks in `validatePrivatePayment` (`isNonemptyObject(objPrivateElement.output)`, `isNonemptyString(blinding)`, hash checks, etc., which only validate the `output` object itself, not that `output_index` is in range of `outputs`) [5](#0-4) .

When the victim wallet processes this chain via `validateAndSavePrivatePaymentChain` → `validateAndSaveIndivisiblePrivatePayment`-style flow and reaches:
```
var our_output = partially_revealed_payload.outputs[objPrivateElement.output_index]; // undefined
our_output.address = ...; // TypeError: Cannot set properties of undefined
``` [6](#0-5) 
the process throws, uncaught by the surrounding `async.series`/callback error-handling path, crashing/denying the wallet's ability to process the private payment.

**Note on uncertainty**: I was not able to fully trace whether an outer try/catch (e.g., in the wallet's message-receiving event handler) ultimately catches this specific `TypeError` before it can crash the process, since that boundary lives in wallet/device-message dispatch code I did not have time to fully inspect in this pass. If such a catch exists, the impact would be reduced to a stuck/failed private-payment validation for that wallet rather than a full crash. This should be verified by a full Devin agent session with complete file access, as the index may also be exceeded due to size limits on file retrieval in this ask-only investigation.
