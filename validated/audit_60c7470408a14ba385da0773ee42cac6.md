### Title
Missing Staking Info Validation in Fast-Sync Allows Malicious Peer to Corrupt Validator/Reward DB — (`datasync/downloader/queue.go`)

---

### Summary

During fast-sync, `queue.DeliverStakingInfos` accepts `P2PStakingInfo` from a P2P peer using a `validate` function that unconditionally returns `nil` (marked `TODO-Kaia-Snapsync`). There is no cryptographic binding between the received staking info and the corresponding block header. A malicious peer can inject entirely fabricated `CouncilNodeAddrs`, `CouncilRewardAddrs`, and `CouncilStakingAmounts`, which are durably written to the staking info DB via `PutStakingInfoToDB`. This corrupted data is subsequently used for reward distribution and validator-set selection.

---

### Finding Description

**Entry point — `DeliverStakingInfos` validate func:** [1](#0-0) 

The `validate` closure always returns `nil`:

```go
validate := func(index int, header *types.Header) error {
    // TODO-Kaia-Snapsync update validation logic
    return nil
}
```

Compare this to `DeliverBodies`, which checks `types.DeriveTransactionsRoot(...) != header.TxHash`, and `DeliverReceipts`, which checks `types.DeriveReceiptsRoot(...) != header.ReceiptHash`: [2](#0-1) [3](#0-2) 

Staking info has no equivalent commitment in the block header, so no such check exists — but the validate function is also not even attempting a block-number consistency check (e.g., `stakingInfoList[index].BlockNum != header.Number.Uint64()`).

**Storage path — `PutStakingInfoToDB`:**

After `deliver()` calls `reconstruct`, the `fetchResult.StakingInfo` is set to the peer-supplied value. Downstream, `commitFastSyncData` calls `PutStakingInfoToDB`, which writes directly to the chain KV store with no further validation: [4](#0-3) 

**`P2PStakingInfo` fields that can be fabricated:** [5](#0-4) 

All fields — `CouncilNodeAddrs`, `CouncilRewardAddrs`, `CouncilStakingAmounts`, `KEFAddr`, `KIFAddr` — are fully attacker-controlled.

**Scheduling condition — only pre-Kaia fork blocks at staking update intervals:** [6](#0-5) 

Staking info is only fetched for blocks where `header.Number % stakingUpdateInterval == 0` and `!IsKaiaFork`. These are exactly the blocks whose staking info governs validator selection and reward distribution for subsequent epochs.

---

### Impact Explanation

A fast-syncing node that stores corrupted staking info will subsequently use it for:
- **Reward distribution**: `CouncilRewardAddrs` determines which addresses receive block rewards. Fabricated addresses redirect rewards to attacker-controlled accounts.
- **Validator-set selection**: `CouncilNodeAddrs` and `CouncilStakingAmounts` determine the weighted-random proposer selection. Fabricated amounts can skew or fully control proposer selection for the affected epoch.
- **KEF/KIF fund routing**: `KEFAddr`/`KIFAddr` control ecosystem fund destinations.

The corruption is **durable** — written to the chain KV store and read back via `GetStakingInfoFromDB` during normal operation after sync completes.

---

### Likelihood Explanation

The P2P network is permissionless. Any node can connect as a peer to a fast-syncing node. The syncing node sends `RequestStakingInfo` to whichever peer it has reserved for the staking info fetch. A malicious peer that wins the reservation (or is the only peer with the data) can respond with fabricated data. No authentication, signature, or cryptographic commitment prevents this.

---

### Recommendation

1. **Immediate**: Add a `BlockNum` consistency check in the `validate` closure: reject any `P2PStakingInfo` where `stakingInfoList[index].BlockNum != header.Number.Uint64()`.
2. **Structural**: Derive a deterministic commitment (e.g., hash of the canonical staking info fields) and include it in the block header's extra data or a system-contract storage root, so it can be verified against the already-validated header chain — analogous to how receipts are verified via `ReceiptHash`.
3. **Short-term mitigation**: After fast-sync completes, re-derive staking info from the synced state trie for all stored staking update blocks and overwrite any peer-supplied values.

---

### Proof of Concept

In a fast-sync integration test:
1. Spin up a syncing node and a malicious peer.
2. Have the malicious peer respond to `RequestStakingInfo` for block `N` (a staking update interval block) with a `P2PStakingInfo` where all `CouncilRewardAddrs` are zeroed and `CouncilStakingAmounts` are all `0`.
3. Assert that `GetStakingInfoFromDB(N)` on the syncing node returns the zeroed data.
4. Trigger reward distribution logic referencing block `N`'s staking info and assert rewards are sent to zero addresses (i.e., burned/lost) rather than legitimate validators.

The `validate` func at line 956–958 will return `nil` unconditionally, `reconstruct` will store the fabricated `P2PStakingInfo`, and `PutStakingInfoToDB` will persist it without any further check. [7](#0-6)
