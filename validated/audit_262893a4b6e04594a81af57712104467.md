### Title
Cross-tenant webhook forgery via mismatched "authenticated organization" vs "repository/commit written" - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/`webhook_secret` to validate the HMAC signature against using a field pulled from the attacker-supplied JSON body (`repository.owner.login`, falling back to `organization.login`), but the actual event handlers that mutate state (`PushHandler`, `StatusHandler`, `MembershipHandler`, `PullRequest::*Handler`, `CheckSuiteHandler`) key off a *different* attacker-supplied field in the same body (`repository.full_name`, or in `StatusHandler`'s case, no repository scoping at all — just `sha`). Nothing binds these two fields together server-side, so the "organization whose secret authenticated the request" is not guaranteed to equal the "repository/commit the handler acts on." This is the same bug class as the TOB report: an invariant ("the phase checked" / here, "the org verified") is not actually enforced along the code path that performs the state-changing action ("the phase acted on" / here, "the repo or commit written").

### Finding Description
`verify_signature` computes:
```ruby
# app/controllers/shipit/webhooks_controller.rb:24-30
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) 

This binds the HMAC check to a *specific* configured `Shipit::GitHubApp`/`webhook_secret` for the organization named in `repository.owner.login`, per the multi-tenant config schema documented in `docs/setup.md` and exercised in `test/dummy/config/secrets_double_github_app.yml` (each org has its own `webhook_secret`). [2](#0-1) [3](#0-2) 

However, once signature verification passes, `create` dispatches the *entire raw payload* to handlers:
```ruby
def create
  params = JSON.parse(request.raw_post)
  Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }
  head(:ok)
end
``` [4](#0-3) 

Handlers determine *which* `Repository`/`Stack` to mutate using `repository.full_name`, an independent field of the same JSON body:
```ruby
def repository_name
  payload.dig('repository', 'full_name')
end
``` [5](#0-4) 

Nothing in the controller or `Handler` base class checks that `repository.owner.login` (used to pick the verifying secret) matches the owner embedded in `repository.full_name` (used to pick the target `Repository`). Because a tenant organization legitimately possesses its own `webhook_secret` (it configured it when creating its GitHub App, per `docs/setup.md` step "Webhook secret … keep it in clear on the side"), that tenant can sign an arbitrary JSON body with its own secret while setting `repository.full_name` to point at a repository belonging to a *different* tenant configured on the same Shipit instance.

The impact is worst in `StatusHandler`, which doesn't even use `repository` for scoping — it matches purely on commit SHA across the entire installation:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [6](#0-5) 
This lets a tenant with a valid (its own) webhook secret write a GitHub commit-status record (`state: success`, arbitrary `context`/`target_url`/`description`) against any commit SHA tracked anywhere in the instance, not just its own repositories — commit statuses gate merge-queue/deploy readiness logic elsewhere in the app (`app/models/shipit/commit.rb`, `app/models/shipit/status/group.rb`, `app/models/shipit/commit_checks.rb`, `app/models/shipit/deploy_spec.rb`).

`PushHandler` similarly triggers `stack.sync_github(expected_head_sha:)` for any stack matching `repository.full_name`+branch, regardless of who authenticated the request: [7](#0-6) 

### Impact Explanation
This breaks the binding "organization that authenticated == repository/commit that is written." A tenant that legitimately controls one GitHub App (webhook secret) integrated into a shared/multi-org Shipit deployment can forge webhook payloads that are correctly signed (with their own key) but reference another tenant's repository or an arbitrary commit SHA. Consequences:
- Forcing a `GithubSyncJob`/deploy-readiness sync on another organization's stack.
- Injecting a fabricated "success" commit status onto any commit across the whole instance, which can be used to satisfy merge-queue/CI-gating checks and lead to an unauthorized merge/deploy for a repository the attacker does not own.
- Triggering `RefreshCheckRunsJob` / review-stack archive/unarchive actions on another org's repository via `check_suite`/`pull_request` handlers, since those also key only on `repository.full_name`.

This matches the "unauthorized deploy, rollback or merge" / "cross-repository writes" Critical/High impact bar, since it lets an unprivileged-relative-to-Org-B attacker (who only administers Org A's own GitHub App) write into Org B's data model without ever needing Org B's secret, session, or GitHub credentials.

### Likelihood Explanation
Requires that the Shipit deployment be configured for multiple GitHub organizations (the documented, supported "Using Multiple Github Applications" mode), and that the attacker administers one of the onboarded orgs (hence legitimately knows its own `webhook_secret`). Given multi-tenant configuration is a first-class, documented feature of this engine, and no additional secrets/tokens/session are needed beyond the attacker's own org's webhook secret (which they control by design), likelihood is moderate-to-high in any deployment that onboards more than one GitHub organization.

### Recommendation
- After signature verification succeeds for a given `repository_owner`, re-derive the "authorized organization" and enforce that every organization-scoped field used later (the owner embedded in `repository.full_name`, `organization.login`, etc.) matches the organization whose secret validated the signature — reject the request otherwise.
- In `StatusHandler`, scope the `Commit.where(sha:)` lookup to commits whose stack's repository belongs to the verified organization, not a bare SHA match across the whole database.
- Apply the same repository-ownership binding check inside `Handler#stacks`/`#repository_name` so every handler enforces it uniformly, rather than leaving it to each handler to (not) re-derive scoping correctly.

### Proof of Concept
1. Deploy Shipit configured with two GitHub orgs (`OrgA`, `OrgB`), each with its own `webhook_secret`, per `test/dummy/config/secrets_double_github_app.yml`.
2. As the administrator of `OrgA` (attacker, "Eve"), compute a valid HMAC-SHA1 signature over a crafted JSON body using `OrgA`'s own `webhook_secret`:
```json
{
  "sha": "<victim-commit-sha-in-OrgB-repo>",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/victim-repo" }
}
```
3. POST this body to `/webhooks` with header `X-Github-Event: status` and `X-Hub-Signature: sha1=<computed-with-OrgA-secret>`.
4. `verify_signature` looks up `repository_owner` = `"OrgA"`, fetches `Shipit.github(organization: "OrgA")`, and successfully verifies the signature (since Eve signed it with her own key).
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)` — matching the victim commit in `OrgB`'s repository regardless of the verified org — and calls `create_status_from_github!`, injecting a fabricated "success" status that can satisfy merge/deploy gating for a repository Eve does not own.
