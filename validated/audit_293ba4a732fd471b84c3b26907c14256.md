## Analog Found: CCMenu API token authorizes only one stack in intent, but is not scoped to any stack in practice — token can read *any* stack's status - ([File: app/controllers/shipit/ccmenu_url_controller.rb])

### Summary
The bug class in the report is: a control (min/max price selection) that is supposed to bind two different operations (deposit vs. withdrawal) to different values is instead collapsed into one shared value, letting an attacker use a credential/action in a context it was never meant to authorize. The equivalent binding in `shipit-engine` is: **the stack a CCMenu `ApiClient` token is generated for** (the `stack_id` embedded in the URL the user requested) versus **the stack the resulting token is actually authorized to touch** (`ApiClient#stack_id`, which controls `Api::BaseController#stacks` scoping). These two are supposed to be equal but are not.

### Finding Description
`CCMenuUrlController#fetch` builds a per-stack CCMenu URL and a companion API token: [1](#0-0) 

The token is minted by:
```ruby
def client
  @client ||= ApiClient.create_with(permissions: %w[read:stack])
                       .find_or_create_by!(creator: current_user, name: 'CCMenu Client')
end
```
Note that `stack:` is never passed to `create_with`/`find_or_create_by!`, so the created `ApiClient` record has `stack_id == nil`. `ApiClient` is `belongs_to :stack, optional: true`, so this is a legal, "global" client, not scoped to the stack that appears in `stack_id` in the URL. [2](#0-1) 

Because `find_or_create_by!` matches on `creator:` and `name:` only, this is effectively a **single shared token per user** across every stack for which that user ever requests a CCMenu URL — the URL's `stack_id` param is baked into the returned URL, but the underlying `ApiClient` credential is identical and reusable regardless of which stack it was generated for.

On the read side, `Api::BaseController#stacks` is supposed to enforce the binding "a token can only read the stack(s) it is authorized for":
```ruby
def stacks
  @stacks ||= current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all
end
``` [3](#0-2) 

Since `stack_id?` is false for the CCMenu client, this scoping resolves to `Stack.all` — i.e. no scoping at all. On top of that, `Api::CCMenuController` doesn't even use the (already ineffective) `stacks` scoping — it overrides `stack` to look up **any** stack directly by param, completely independent of the authenticated client:
```ruby
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end
``` [4](#0-3) 

The only check performed is `require_permission :read, :stack`, which only verifies that the token has the *permission bit* `read:stack` — it never verifies that the token's `stack_id` matches the `stack_id` in the request: [5](#0-4) [6](#0-5) 

So the equality that should hold — `stack authorized when token was minted == stack touched when token is used` — is broken: **any** CCMenu token, once obtained, can be replayed against **any** `stack_id` in the whole Shipit instance to read that stack's latest deploy/status (`Api::CCMenuController#show`, rendering `shipit/ccmenu/project.xml.builder`), regardless of which stack the user originally requested the URL for.

### Impact Explanation
This crosses the "High" bar defined by the rules: **unauthenticated read of stack state**. CCMenu URLs are explicitly designed to be handed out to third-party CI dashboard tools (CCTray/CCMenu clients) — i.e., outside Shipit's authenticated session boundary, over the network, often to less-trusted consumers than the Shipit web UI itself. A leaked/observed CCMenu URL for one (possibly low-sensitivity) stack lets the holder enumerate `stack_id` and read deploy/build status for every stack in the deployment, including stacks the user issuing the original CCMenu URL never intended to expose and which they themselves may have no access to (since `current_user` at mint-time is not re-checked against arbitrary stacks at read-time — the token is a bearer credential, decoupled from the requesting user's own stack permissions at read time).

### Likelihood Explanation
High likelihood: no special privilege is needed beyond being any authenticated Shipit user able to hit `CCMenuUrlController#fetch` for at least one stack (a normal, low-privilege feature exposed in the stack settings UI), and no attacker-side cryptographic work is required — the token is a legitimately issued, correctly signed `ApiClient` bearer token; it is simply *not scoped* the way the design (per-stack CCMenu URL) implies. Any code that reads a leaked CCMenu URL from logs, browser history, third-party CI dashboard configuration, etc. gets this over-broad read.

### Recommendation
When minting the CCMenu `ApiClient`, scope it to the specific stack (`stack:` must be set, and the lookup key should include the stack so that different stacks get different clients), e.g. `ApiClient.create_with(permissions: %w[read:stack], stack:).find_or_create_by!(creator: current_user, stack:, name: 'CCMenu Client')`. Additionally, `Api::CCMenuController#stack` should use the scoped `stacks` lookup (as `Api::BaseController` intends) instead of an unscoped `Stack.from_param!`, so that a `stack_id`-scoped token cannot be replayed against other stacks even if the scoping logic elsewhere is later reintroduced correctly.

### Proof of Concept
1. As user A, request a CCMenu URL for `stack_id = "org/repoA/production"` via `GET /ccmenu_url?stack_id=org/repoA/production`. This creates `ApiClient` (`creator: A`, `name: 'CCMenu Client'`, `permissions: ['read:stack']`, `stack_id: nil`) and returns `https://shipit/api/stacks/org/repoA/production/ccmenu.xml?token=<TOKEN>`.
2. Take `<TOKEN>` and request `https://shipit/api/stacks/org/repoB/staging/ccmenu.xml?token=<TOKEN>` for an unrelated stack `org/repoB/staging` that user A was never granted CCMenu access to (or does not even have read access to via web UI).
3. `Api::CCMenuController#authenticate_api_client` accepts the token via `ApiClient.authenticate(params[:token])`. `require_permission :read, :stack` passes because the token has `read:stack`. `stack` resolves via `Stack.from_param!(params[:stack_id])`, unscoped, returning `repoB/staging`.
4. The response renders `repoB/staging`'s latest deploy/status — data the token was never scoped to expose.
