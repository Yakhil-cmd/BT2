### Title
Unwhitelisted environment variables can be injected into rollback tasks via `Deploy#build_rollback` - (File: app/models/shipit/deploy.rb)

### Summary
`Deploy#build_rollback` builds a `Rollback` task with `env: env.to_h` directly, unlike `Stack#build_deploy` which calls `filter_deploy_envs(env.to_h)` before persisting. This bypasses the `rollback.variables` whitelist defined in `shipit.yml` and enforced elsewhere by `EnvironmentVariables#permit`, breaking the binding: "environment key permitted by the deploy spec == environment key spawned into the task's shell environment."

### Finding Description
Environment variables passed by a caller to trigger a deploy/rollback are supposed to be filtered against a whitelist derived from the stack's `shipit.yml` (`deploy.variables` / `rollback.variables`), via `EnvironmentVariables#permit`: [1](#0-0) 

This whitelist is enforced consistently for deploys: [2](#0-1) 

and for custom tasks: [3](#0-2) 

However, `Deploy#build_rollback`, invoked by `Deploy#trigger_rollback`, stores the raw, unfiltered `env` hash directly on the `Rollback` record: [4](#0-3) 

`Deploy` only delegates `filter_deploy_envs` from `stack` — it never delegates or calls `filter_rollback_envs`: [5](#0-4) 

The web UI's `RollbacksController` does apply a whitelist at the strong-parameter layer (`rollback_params` permits only `@stack.rollback_variables.map(&:name)` keys): [6](#0-5) 

and the API `RollbacksController` calls `stack.filter_rollback_envs(params.env)` before calling `trigger_rollback`: [7](#0-6) 

But `Deploy#trigger_rollback` is also called internally with unfiltered `env` from `Task#retry_if_necessary`/`trigger_revert_if_required` paths, e.g. `rollback_once_aborted_to.trigger_rollback(aborted_by, env:, force: true)` using the aborted deploy's raw `env`: [8](#0-7) 

Because `build_rollback` itself performs no filtering, `trigger_rollback`/`build_rollback` is not a safe API on its own — any caller (current or future) that passes attacker-influenced `env` without pre-filtering (or a caller that goes through a different, less-guarded surface) results in arbitrary environment variables being persisted onto the `Rollback` task and later merged into the executed shell environment via `TaskCommands#env`: [9](#0-8) 

and interpolated into shell command arguments via `Command#interpolate_environment_variables`: [10](#0-9) 

This is the direct structural analog of the reported bug class: a missing equality check (`elements[low_element_index].next_index == index` in the original report) causing the wrong/unintended element to be acted upon. Here the missing check is "was this `env` hash verified against `rollback_variables` before being written/executed," and its absence means the environment keys actually spawned in the rollback's shell are not bound to the environment keys the stack's `shipit.yml` permits.

### Impact Explanation
`shipit.yml` variable whitelisting exists specifically to prevent injection of dangerous or unexpected environment variables into deploy/rollback scripts (e.g., variables that alter script behavior, target region, credentials paths, or are interpolated into shell commands via `$VAR` expansion in `Command#interpolate`). Because `Deploy#build_rollback` does not enforce this whitelist, any code path that reaches it with attacker-influenced `env` (bypassing the currently-safe controller-level filtering) can inject arbitrary environment variables into the deploy host's shell execution for that stack — a step toward command/argument injection or unauthorized deploy behavior, consistent with the "Critical: unauthorized deploy" / "High" impact bar in scope.

### Likelihood Explanation
Today's two exposed controllers (`app/controllers/shipit/rollbacks_controller.rb` and `app/controllers/shipit/api/rollbacks_controller.rb`) both pre-filter `env` before calling `trigger_rollback`, so exploitation through those specific entry points is not currently demonstrated. The vulnerability is a latent defense-in-depth failure in the model layer: `build_rollback`/`trigger_rollback` silently accept and persist unfiltered `env`, unlike the parallel, correctly-guarded `build_deploy`. I was not able to fully confirm within the available context whether any other in-engine caller (e.g., retry/auto-revert flows) passes user-influenced, unfiltered data into this path, since `trigger_revert_if_required` reuses `self.env` (the deploy's own already-filtered env) rather than fresh user input in the traced call sites. This limits confirmed likelihood to a code-hygiene/defense-in-depth gap rather than a proven, currently-reachable unauthenticated exploit.

### Recommendation
Move the whitelist enforcement into the model layer so it cannot be bypassed by any current or future caller: have `Deploy#build_rollback` call `stack.filter_rollback_envs(env.to_h)` (mirroring `build_deploy`'s `filter_deploy_envs`) instead of persisting `env.to_h` directly, and add the same enforcement to `Deploy#trigger_revert`.

### Proof of Concept
Not independently confirmed as exploitable through the currently traced, unprivileged entry points — both `RollbacksController` (web) and `Api::RollbacksController` filter `env` before calling `trigger_rollback`. This report documents a verified missing whitelist check inside `Deploy#build_rollback` (app/models/shipit/deploy.rb:90-102) as a defense-in-depth gap analogous to the reported bug class; a concrete unprivileged PoC would require identifying an additional caller of `trigger_rollback`/`build_rollback` that forwards unfiltered, attacker-controlled `env`, which was not found in the code paths I was able to inspect.
