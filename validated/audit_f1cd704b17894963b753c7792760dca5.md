### Title
Cross-organization webhook forgery via `repository.owner.login`/`repository.full_name` binding mismatch - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App (and thus which `webhook_secret`) to use for HMAC verification based on `repository_owner`, derived from the payload's `repository.owner.login` (or `organization.login`). However, every event handler that actually performs writes (finds/creates repositories, stacks, review stacks, syncs commits, etc.) uses a *different* field from the same payload — `repository.full_name` — with no check that its owner segment matches the organization whose secret validated the signature.

### Finding Description
In `app/controllers/shipit/webhooks_controller.rb`, the signature check is: [1](#0-0) 

`repository_owner` is computed from the payload: [2](#0-1) 

`Shipit.github(organization: repository_owner)` looks up a `GitHubApp` whose config (and `webhook_secret`) is keyed by that organization name, as configured in multi-org setups such as `test/dummy/config/secrets_double_github_app.yml`, and each `GitHubApp` instance carries its own `@webhook_secret` used in `verify_webhook_signature`: [3](#0-2) 

Once the signature is accepted, `create` dispatches the *entire raw payload* to handlers: [4](#0-3) 

But the base `Handler` class (used by `PushHandler`, all `PullRequest::*Handler`s, etc.) resolves the target repository/stacks using `repository.full_name`, an entirely separate JSON field that is never cross-checked against `repository.owner.login`: [5](#0-4) 

`Repository.from_github_repo_name` simply splits the `owner/name` string from `full_name` and looks it up directly: [6](#0-5) 

This is exactly the pattern the bug class targets: **the organization authenticated by the signature check (`repository.owner.login`) is not the same entity as the repository that is actually written to (`repository.full_name`)**. In a multi-organization Shipit deployment (explicitly supported — see `secrets.development.shopify.yml`, `secrets_double_github_app.yml`), each onboarded organization has its own GitHub App and thus its own `webhook_secret`, known to that organization's own administrators (they configure it when creating their GitHub App per `docs/setup.md`). Because the controller derives the *verification* organization strictly from `repository.owner.login`/`organization.login`, while the *effect* is driven by the unrelated `repository.full_name` field in the same JSON body, an org admin who legitimately knows their own org's `webhook_secret` can craft a request that:
- Sets `repository.owner.login` (or `organization.login`) to their own org, so the signature is computed/verified correctly with their known secret.
- Sets `repository.full_name` to `"other-org/some-repo"`, so the handler processed acts on a stack/repository belonging to a different, unrelated organization onboarded to the same Shipit instance.

For example, with a forged `push` event the `PushHandler` will call `stack.sync_github` on stacks under the victim organization's repository (equality broken: `organization_verified_by_signature != organization_that_owns_repository.full_name_acted_on`), causing cross-repository writes/syncs, and a forged `pull_request` `closed`/`reopened` event can archive/unarchive review stacks belonging to a different org's repository.

### Impact Explanation
This allows an attacker who only has legitimate credentials for their *own* onboarded organization on a shared, multi-org Shipit deployment to trigger writes against a *different* organization's repositories/stacks (archiving/unarchiving review stacks, triggering syncs) — a cross-repository write, which is explicitly listed as a Critical impact category.

### Likelihood Explanation
Requires a multi-organization Shipit deployment (a documented, first-class configuration in this engine) where the attacker is one of the onboarded orgs with a known `webhook_secret` for their own App, and crafts a webhook request with mismatched `repository.owner.login` vs `repository.full_name`. No repository write access, GitHub App private key, or Shipit session is needed — only the attacker's own organization webhook secret, which is not privileged with respect to other tenants.

### Recommendation
After the signature is verified against the app selected for `repository_owner`, validate that `params.dig('repository', 'full_name')` (and any other repository-owner-bearing fields used by handlers) has an owner segment equal to `repository_owner`; reject the request otherwise.

### Proof of Concept
1. Deploy Shipit configured with two organizations, `OrgA` and `OrgB`, each with its own GitHub App/`webhook_secret` (as in `test/dummy/config/secrets_double_github_app.yml`).
2. As an administrator of `OrgA` (who knows `OrgA`'s `webhook_secret` from creating that org's GitHub App), craft a `push` webhook payload:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-controlled sha>",
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/victim-repo" }
}
```
3. Compute `X-Hub-Signature` as `sha1=` HMAC-SHA1 of the raw body using `OrgA`'s `webhook_secret`.
4. POST to `/webhooks` with header `X-Github-Event: push`. `verify_signature` resolves `repository_owner` = `"OrgA"`, fetches `OrgA`'s app, and the signature validates.
5. `PushHandler#process` resolves stacks via `Repository.from_github_repo_name("OrgB/victim-repo")` and calls `stack.sync_github`, causing the app to act on `OrgB`'s repository despite authenticating as `OrgA`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
