### Title
`ERC20Transactor::withdraw_asset_with_surplus` credits the full requested `amount` to XCM holding regardless of what the checking account actually received, allowing fee-on-transfer / deflationary ERC20 tokens to mint unbacked XCM credit - ([File: cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs])

### Summary
`pallet-revive`-backed ERC20 tokens can be used as XCM-transactable assets via `ERC20Transactor` (wired into AssetHub's `AssetTransactors` as `cumulus/parachains/runtimes/assets/asset-hub-westend/src/xcm_config.rs:222-246`). Its `withdraw_asset_with_surplus` moves tokens by calling the ERC20 contract's `transfer()` to a fixed `TransfersCheckingAccount`, and on a `true` return unconditionally credits `AssetsInHolding` with the full `amount` requested, never verifying the checking account's actual balance delta. For a deflationary/fee-on-transfer ERC20 that deducts a fee inside `_update`/`transfer()` while still returning `true`, this produces XCM holding credit that is not fully backed by what the checking account actually received - the same class of "trusted nominal amount vs. actual received amount" bug flagged in the Basin `Well.sol` report.

### Finding Description
`ERC20Transactor::withdraw_asset_with_surplus` [1](#0-0)  takes the caller-controlled `amount` (from the XCM `withdraw_asset` instruction, matched via `Matcher::matches_fungibles`) and calls the target ERC20 contract's `transfer(checking_address, amount)`.

The result is only checked for revert and for the boolean return value of `transfer`, never for the actual balance change of the checking account: [2](#0-1)  On `is_success == true`, it does:
```
Ok((AssetsInHolding::new_from_fungible_credit(what.id.clone(), Box::new(Erc20Credit(amount))), surplus))
```
i.e. it credits the *requested* `amount`, not the amount actually deposited into `checking_address`'s ERC20 balance.

`Erc20Credit` is explicitly documented as an unchecked/unsafe imbalance type: [3](#0-2)  "This type implements the necessary imbalance accounting traits but does not perform runtime-level balance enforcement... the actual balance constraints are enforced by the ERC20 smart contract itself rather than the runtime." This assumption holds only for standard ERC20 tokens where `transfer(to, amount)` moves exactly `amount` (or fails). It does not hold for fee-on-transfer/deflationary ERC20 tokens - contracts whose `_update`/`transfer` logic deducts a fee and delivers less than `amount` to the recipient while still returning `true` on success (the same "exclusive feeOnTransfer" token category referenced in the source report).

`can_check_in`/`can_check_out` are disabled ("We don't support teleports"), so there is no independent teleport-accounting check that could catch a mismatch here; the only invariant the design relies on is "checking account ERC20 balance == sum of outstanding XCM credit for that asset," and that invariant is exactly what a fee-on-transfer token breaks, because `withdraw_asset_with_surplus` never re-reads the checking account's balance to confirm it increased by `amount`.

The symmetric `deposit_asset_with_surplus` [4](#0-3)  has the analogous gap on the other side (transfers from checking account to beneficiary, again trusting `amount` rather than measuring delivered balance), but that direction only shortchanges the recipient rather than inflating outstanding claims on the reserve.

### Impact Explanation
Every `withdraw_asset` of a fee-on-transfer ERC20 through this transactor creates `AssetsInHolding` credit equal to the nominal `amount`, while the checking account's real ERC20 balance only increases by `amount - fee`. XCM execution can then deposit/forward that over-credited holding to any beneficiary (including a different account or, if paired with a reserve-transfer style XCM program, to another chain), effectively manufacturing value that is not backed by the checking account's actual ERC20 balance. Repeating this drains the checking account's real backing relative to the outstanding credit the runtime believes exists for that asset - the same "reserve accounting divorced from real transfer amount" root cause as the original Basin `skim`/`sync` bug, and it matches the report's "unbacked issuance" pattern that this scan explicitly treats as high-priority. Severity is Medium: it requires a specific token type (fee-on-transfer/deflationary ERC20) to be deployed and used through the XCM path, but no privileged role, governance action, or protocol-level trust is needed - any user can deploy such a contract via `pallet-revive` and drive XCM `withdraw_asset`/`deposit_asset` against it.

### Likelihood Explanation
Likelihood is Medium-Low in practice: it requires (a) an ERC20 contract with fee-on-transfer semantics deployed under `pallet-revive`, and (b) that contract being routed through `ERC20Transactor` via XCM `execute`/local program (as demonstrated by the existing `withdraw_and_deposit_erc20s` test pattern in `cumulus/parachains/runtimes/assets/asset-hub-westend/tests/tests.rs:1871-1936`, which shows this exact call path is reachable by a signed, unprivileged account). No governance, collator, or relayer trust is required - only deploying and interacting with an attacker-controlled contract, which is exactly the "no privileged role" attacker model required by this scan.

### Recommendation
In `withdraw_asset_with_surplus`, read the checking account's ERC20 balance before and after the `transfer` call (or use `balanceOf` deltas) and credit `AssetsInHolding` with the actually-received delta rather than the nominal `amount`. Symmetrically, in `deposit_asset_with_surplus`, verify the beneficiary's balance increased by the expected amount before treating the holding as fully consumed, or explicitly document/enforce that only non-fee-on-transfer ERC20s may be used with this transactor (e.g., via an allow-list/matcher check) if delta-based accounting is not feasible.

### Proof of Concept
Not independently executed in this session (index/tool-only environment; no Rust/FRAME test harness was run). Reasoning is based on static code inspection: the code path `withdraw_asset_with_surplus` → `IERC20::transferCall` → unconditional `Erc20Credit(amount)` credit contains no balance-delta verification, and the analogous XCM `execute` reachability for this transactor is directly demonstrated by the existing repository test `withdraw_and_deposit_erc20s` (`cumulus/parachains/runtimes/assets/asset-hub-westend/tests/tests.rs:1871-1936`), which exercises the exact same `withdraw_asset`/`deposit_asset` XCM instructions against a `pallet-revive` ERC20 contract from a signed, unprivileged account. A full reproduction would require: (1) writing a minimal fee-on-transfer Solidity fixture (deduct e.g. 2% on `transfer`, still return `true`), (2) instantiating it via `pallet-revive` as in the existing test, (3) executing the same XCM withdraw/deposit program, and (4) asserting `checking_account` ERC20 balance delta < credited `AssetsInHolding` amount. This last step was not executed and remains unverified; flagging as a supported analog based on code-level evidence rather than a confirmed live run.

/// A minimal imbalance tracking type that holds an ERC20 token amount.
///
/// This type implements the necessary imbalance accounting traits but does not perform
/// runtime-level balance enforcement. It's used to track ERC20 token amounts within XCM
/// asset holdings, where the actual balance constraints are enforced by the ERC20 smart
/// contract itself rather than the runtime.
struct Erc20Credit(u128);
impl UnsafeConstructorDestructor<u128> for Erc20Credit {
	fn unsafe_clone(&self) -> Box<dyn ImbalanceAccounting<u128>> {
		Box::new(Erc20Credit(self.0))
	}
	fn forget_imbalance(&mut self) -> u128 {
		let amount = self.0;
		self.0 = 0;
		amount
	}
}

impl UnsafeManualAccounting<u128> for Erc20Credit {
	fn saturating_subsume(&mut self, mut other: Box<dyn ImbalanceAccounting<u128>>) {
		let amount = other.forget_imbalance();
		self.0 = self.0.saturating_add(amount);
	}
}

impl ImbalanceAccounting<u128> for Erc20Credit {
	fn amount(&self) -> u128 {
		self.0
	}
	fn saturating_take(&mut self, amount: u128) -> Box<dyn ImbalanceAccounting<u128>> {
		let new = self.0.min(amount);
		self.0 = self.0 - new;
		Box::new(Erc20Credit(new))
	}
}

	fn deposit_asset_with_surplus(
		what: AssetsInHolding,
		who: &Location,
		_context: Option<&XcmContext>,
	) -> Result<Weight, (AssetsInHolding, XcmError)> {
		tracing::trace!(
			target: "xcm::transactor::erc20::deposit",
			?what, ?who,
		);
		defensive_assert!(what.len() == 1, "Trying to deposit more than one asset!");
		// Check we handle this asset.
		let maybe = what
			.fungible_assets_iter()
			.next()
			.and_then(|asset| Matcher::matches_fungibles(&asset).ok());
		let (asset_contract_id, amount) = match maybe {
			Some(inner) => inner,
			None => return Err((what, MatchError::AssetNotHandled.into())),
		};
		let who = match AccountIdConverter::convert_location(who) {
			Some(inner) => inner,
			None => return Err((what, MatchError::AccountIdConversionFailed.into())),
		};
		// We need to map the 32 byte beneficiary account to a 20 byte account.
		let eth_address = T::AddressMapper::to_address(&who);
		let address = Address::from(Into::<[u8; 20]>::into(eth_address));
		// To deposit, we actually transfer from the checking account to the beneficiary.
		// We do this using the solidity ERC20 interface.
		let data = IERC20::transferCall { to: address, value: EU256::from(amount) }.abi_encode();
		let weight_limit = WeightLimit::get();
		let ContractResult { result, weight_consumed, storage_deposit, .. } =
			pallet_revive::Pallet::<T>::bare_call(
				OriginFor::<T>::signed(TransfersCheckingAccount::get()),
				asset_contract_id,
				U256::zero(),
				TransactionLimits::WeightAndDeposit {
					weight_limit,
					deposit_limit: StorageDepositLimit::get(),
				},
				data,
				&ExecConfig::new_substrate_tx(),
			);
