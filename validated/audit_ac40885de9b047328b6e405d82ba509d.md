### Title
Unvalidated route bytes let a malicious swap venue drain the caller's wallet through the recorded auth tree in `swap_collateral` / `swap_debt` / `repay_debt_with_collateral` / `multiply` - (File: contracts/controller/src/strategies/swap.rs)

### Summary
The controller's strategy entrypoints accept caller-supplied `swap: Bytes` and forward them verbatim to the configured swap aggregator with no canonicalization or containment check on the venues encoded inside — the exact analog of the PocketFlow `os.path.join` wrapper: a thin pass-through of an untrusted path-like input to a powerful sink. Because Soroban `require_auth` propagates across nested contract calls, a hop venue embedded in the route can require the caller's authorization for an arbitrary `token::transfer`, which the transaction recorder folds into the auth tree the user signs for the `swap_collateral` invocation — draining unrelated wallet tokens.

### Finding Description
`Controller::swap_collateral`, `swap_debt`, `multiply`, and `repay_debt_with_collateral` all take an opaque `swap: Bytes` argument and reach `swap_tokens` in `contracts/controller/src/strategies/swap.rs:13-55`. That function only asserts `!swap.is_empty()`, reads `router_addr` from storage, authorizes the exact input transfer to the router, and calls `router.execute_strategy(&controller, &amount_in, swap)` — the route payload is never decoded or validated by the controller (`swap.rs:22-38`). The repository's own test `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs:111-227` demonstrates the exploit primitive: a `RogueHopPool` registered as a route hop calls `alice.require_auth()` + `token::transfer(alice, attacker, amount)` on a token unrelated to the swap; under recording mode this nested auth is recorded as a child of Alice's `swap_collateral` root, and `assert_eq!(s.wallet(&s.alice), 0)` confirms the theft of `WALLET_BALANCE`. The bug class is the missing "containment check": there is no allowlist or invariant binding the venues inside `swap` to the declared `token_in`/`token_out` pair at the controller layer, so an arbitrary "path" through attacker contracts executes inside the user's authorization scope.

### Impact Explanation
Theft of user funds. Any user who submits a strategy transaction with route bytes they did not build byte-by-byte (the documented flow is to paste server-returned `routeXdr` per `skills/xoxno-swap-aggregator/composition.md:53-60`) can have their entire balance in any token drained to an attacker address, as long as they sign the recorded auth tree. The stolen assets are unrelated wallet tokens — not swap inputs — so protocol slippage guards (`RouterOverspend`, `NoSwapOutput`, `SlippageExceeded`) do not bound the loss. A single unprivileged attacker only needs to get a crafted `routeXdr` in front of a victim (malicious quote service, compromised frontend, phishing bot) — matching the report's UI:R / AC:H profile.

### Likelihood Explanation
Requires user interaction (victim signs the poisoned tree) and an attacker-controlled route reaching the victim, analogous to the report's high attack complexity — hence Medium rather than High. The venue injection itself is trivially reachable by any unprivileged address: nothing in `swap_tokens`, `swap_tokens_or_passthrough`, `process_swap_collateral`, or `process_swap_debt` restricts hop addresses, and the in-repo PoC executes end-to-end. The auth tree is generated by simulation, so wallets that auto-sign recorded auth or users who do not audit sub-invocations sign the malicious `transfer` without realizing it.

### Recommendation
Constrain the "path" at the controller boundary:
- Decode `swap` and enforce that every hop venue is a known/allowlisted pool type, or pin venue addresses to a governance-managed allowlist before calling `execute_strategy`.
- Alternatively, wrap the router call so the user's `require_auth` scope cannot leak into venue code — e.g., perform strategy swaps from the controller's own balance after pulling input, so only the controller's auth (not the caller's) is exercised inside the route.
- At minimum, surface the decoded route venues in the `swap_collateral`/`swap_debt` arguments or events so wallets can display which contracts will execute under the user's signature.

### Proof of Concept
See `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs:111-227`. `route_through_pool_stealing(WALLET_BALANCE)` encodes a `RogueSwap` whose `hop_pool` is a `RogueHopPool` carrying `(alice, wallet_token, attacker, amount)`; when Alice calls `swap_collateral(usdc_market, SWAP_IN_USDC, eth_market, route)`, the hop transfers `WALLET_BALANCE` of an unrelated wallet token from Alice to `attacker` using her recorded authorization, while the swap itself still returns a fair `FAIR_OUT_ETH` output — all slippage/output checks pass and the theft is invisible to the controller's balance deltas.
