### Title
Webhook signature is verified against `repository.owner.login`, but the repository/commit that is actually written to is resolved from the attacker-controlled `repository.full_name` field — allowing cross-repository status forgery - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/handler.rb])

### Summary
`WebhooksController#verify_signature` authenticates an inbound webhook by looking up the GitHub App/secret for `repository_owner` (derived from `params.dig('repository','owner','login')`) and HMAC-verifying the raw payload against that org's `webhook_secret`. The `Handler` base class that actually performs the write, however, resolves the target `Repository`/`Stack` from a *different* field of the very same payload: `payload.dig('repository', 'full_name')`. Nothing ties `full_name`'s owner segment to `owner.login`, so an attacker with legitimate webhook-signing capability for any one repository (i.e., anyone who can configure a GitHub webhook on any org/repo tracked by this Shipit instance, which is a normal, low-privilege repo-admin capability, not a Shipit credential) can produce a validly-signed payload whose `repository.full_name` points at a completely different, victim repository.

### Finding Description
Verification and write use two different bindings inside the same JSON object, mirroring the `TitlesGraph` bug class where a value that is checked (edge/state) and the value that is actually persisted diverge:

- Verification binding: `repository.owner.login` → picks the GitHub App/secret used to compute/compare the HMAC signature. [1](#0-0) [2](#0-1) 

- Write binding: `repository.full_name` → resolves the `Repository`/`Stack` that handlers act on. [3](#0-2) [4](#0-3) 

`StatusHandler#process` uses the attacker-supplied `sha`/`state` to create a commit status for whatever `Commit` matches that `sha`, scoped only by the `stacks`/`Repository` resolved via `full_name`: [5](#0-4) 

`PushHandler#process` similarly triggers `stack.sync_github` for whatever stacks belong to the `full_name`-resolved repository: [6](#0-5) 

Because `verify_webhook_signature` only checks that the raw payload bytes match the HMAC for the secret belonging to `repository.owner.login`, an attacker who controls a repository whose owner org is tracked by this Shipit instance (e.g., they added/administer a webhook on their own low-value repo) can send a request where:
- `repository.owner.login = "attacker-org"` (so the correct, known secret is used and signature check passes), and
- `repository.full_name = "victim-org/victim-repo"` (so the handler resolves and mutates the victim's `Repository`/`Stack`).

The signature check equality that should hold is:
`verified-org-that-signed == org-that-owns-the-repo-being-written`
but the code only enforces:
`verified-org-that-signed == params['repository']['owner']['login']`
while writing to:
`Repository.from_github_repo_name(params['repository']['full_name'])`
These two fields are never cross-checked for consistency.

### Impact Explanation
Via `status` events, an attacker can forge a `success` `commit_status` for an arbitrary commit `sha` in a victim repository/stack they don't own, as long as they can guess/know that sha (commits/shas are often public via the same public GitHub repo). Since commit deployability in Shipit gates on commit statuses, this allows an unauthenticated third party (from Shipit's perspective — they hold no Shipit session, `ApiClient` token, or the victim's `webhook_secret`) to mark an otherwise-non-deployable commit as deployable, enabling an unauthorized deploy of that commit through the normal Shipit UI/API by any legitimate stack operator, or via `push` events to force out-of-band `sync_github` calls against a victim's stacks. This is a cross-repository write crossing an authentication boundary (org A's signature authorizing writes to org B's data), matching the "unauthorized deploy" / "cross-repository writes" impact bucket.

### Likelihood Explanation
Requires only the ability to register/administer a webhook on any repository/org that this Shipit instance already trusts (a normal, unprivileged GitHub repo-admin action, not a Shipit credential), plus knowledge of a target commit sha in the victim repo (commonly public). No Shipit session, `ApiClient` token, or the victim webhook secret is needed, satisfying the "unprivileged attacker" bar. The main uncertainty (unverifiable from the indexed source alone) is the exact per-organization GitHub App/webhook_secret provisioning topology configured by `Shipit.github(organization:)` in `lib/shipit.rb`, which determines how many distinct attacker-controllable "trusted" orgs exist in a given deployment; I was not able to fully inspect `lib/shipit.rb`'s app registry contents within the tool budget.

### Recommendation
In `WebhooksController#verify_signature` (or in `Shipit::Webhooks::Handlers::Handler`), assert that `params.dig('repository', 'owner', 'login')` matches the owner segment of `params.dig('repository', 'full_name')` before verifying/acting, and reject the request (422/404) on mismatch. Prefer deriving the repository lookup key from the same normalized owner/name pair that was used for signature verification rather than trusting `full_name` independently.

### Proof of Concept
1. Attacker administers `attacker-org/attacker-repo`, which is a tracked Shipit `Repository`; they know `webhook_secret` for `attacker-org` (they configured it themselves in GitHub's webhook UI).
2. Attacker crafts a `status` event payload:
```json
{
  "sha": "<victim-repo-commit-sha>",
  "state": "success",
  "repository": {
    "full_name": "victim-org/victim-repo",
    "owner": { "login": "attacker-org" }
  }
}
```
3. Attacker computes `X-Hub-Signature` using the known `attacker-org` webhook secret over the raw JSON body.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: "attacker-org")` and successfully verifies the signature. [1](#0-0) 
5. `StatusHandler#process` looks up `Commit.where(sha: params.sha)` — a commit that belongs to `victim-org/victim-repo` — and calls `create_status_from_github!`, marking it as `success` despite the request never being signed with `victim-org`'s secret. [5](#0-4)
