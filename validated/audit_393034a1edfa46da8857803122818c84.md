### Title
`snowbridge-pallet-system-frontend::add_tip`/`register_token` swap tip asset for Ether with no slippage protection, allowing loss of the entire tip - (File: bridges/snowbridge/pallets/system-frontend/src/lib.rs)

### Summary
`Pallet::add_tip` and `Pallet::register_token` in `snowbridge-pallet-system-frontend` let any signed account convert an arbitrary fee/tip asset into Ether via `Pallet::swap_and_burn`, which calls `T::Swap::swap_exact_tokens_for_tokens` with `amount_out_min = None` [1](#0-0) . This is the same missing-slippage-check pattern described in the FeeCollector.claimFees report: a swap is performed on behalf of the user/attacker with no minimum-output guarantee, so a delayed transaction or AMM price movement between submission and execution can consume the full input while returning a near-zero output.

### Finding Description
`add_tip` is a public, signed extrinsic [2](#0-1) . It forwards the caller-supplied `asset` (attacker-controlled asset id and amount) to `swap_fee_asset_and_burn`, which — when the asset isn't already Ether — calls `swap_and_burn`:

```
let ether_gained = T::Swap::swap_exact_tokens_for_tokens(
    who.clone(),
    swap_path,
    tip_amount,
    None, // No minimum amount required
    who,
    true,
)?;
``` [3](#0-2) 

The `Swap` trait (implemented in production by `pallet-asset-conversion::Pallet<T>`) explicitly supports an `amount_out_min: Option<Balance>` parameter designed to bound slippage [4](#0-3) , and the pallet enforces it when `Some` is supplied via `ProvidedMinimumNotSufficientForSwap` [5](#0-4) . `system-frontend` deliberately opts out of this protection by hard-coding `None`, meaning the swap always succeeds regardless of the resulting output amount, no matter how unfavorable the AMM price has become since the user constructed the extrinsic.

The withdrawn tip asset amount is fixed by the caller (`tip_amount`/`fee_amount`), but the resulting `ether_gained` — which is burned for teleportation and reported to BridgeHub as the tip/reward value via `EthereumSystemCall::AddTip`/`RegisterToken` — is whatever the pool returns at execution time [6](#0-5) . There is no check that `ether_gained` is close to the amount quoted/expected by the user.

### Impact Explanation
An honest user calling `add_tip` (or `register_token` from a non-root origin) to pay a relayer tip in some asset X can have their entire `tip_amount` of X withdrawn and swapped for Ether, but if the X/Ether pool has moved (e.g., due to normal market activity, a delayed inclusion, or an attacker front-running the swap by trading against the same pool before the victim's transaction lands), the amount of Ether actually burned/registered can be a small fraction of what was quoted. The user permanently loses the difference: their asset is consumed, the swap "succeeds" (no error, since no minimum is enforced), and they receive materially less relayer-reward value than intended. Because the reward is used to incentivize message relaying on Ethereum, an unexpectedly low resulting tip can also cause the tip to fail to attract a relayer, indirectly degrading bridge message delivery guarantees for that message. This is a direct, deterministic loss-of-funds bug reachable by any signed, unprivileged account with no special permission — matching the High severity classification of the source report.

### Likelihood Explanation
Likelihood is high: `add_tip` is meant to be called by ordinary users on a live, public parachain frontend for Snowbridge (BridgeHub-facing). No governance or privileged role is required — `ensure_signed(origin)` is the only origin check [7](#0-6) . Any delay between signing and inclusion (normal network latency, mempool reordering, or a deliberate front-run trade against the same AMM pool by an unprivileged third party) is sufficient to trigger loss; no forged proofs, malicious validators, or governance control are needed.

### Recommendation
Add a `min_ether_out` (or equivalent minimum-output) parameter to `add_tip` and `register_token`, threaded through `swap_fee_asset_and_burn`/`swap_and_burn` into `T::Swap::swap_exact_tokens_for_tokens` as `Some(min_ether_out)` instead of hard-coded `None`, so the extrinsic fails atomically (reverting the withdrawal) if the AMM cannot deliver at least the caller-specified minimum. Alternatively, expose a quote-then-swap pattern (using `QuotePrice`/`quote_price_exact_tokens_for_tokens`) so callers/wallets can compute and supply a safe minimum, consistent with how `pallet-asset-conversion`'s own dispatchables already require `amount_out_min` for direct swaps.

### Proof of Concept
No live PoC was executed. Failed/absent guard identified by static review: `swap_and_burn` at `bridges/snowbridge/pallets/system-frontend/src/lib.rs:301-308` unconditionally passes `None` for `amount_out_min` into the `Swap` trait's `swap_exact_tokens_for_tokens`, which is the only slippage-protection mechanism the trait exposes (confirmed via `substrate/frame/asset-conversion/src/swap.rs:43-50` and `substrate/frame/asset-conversion/src/tests.rs:1565-1613`, which shows the pool DOES enforce this bound when `Some(amount_out_min)` is supplied via `Error::<T>::ProvidedMinimumNotSufficientForSwap`). The test harness for `system-frontend` (`bridges/snowbridge/pallets/system-frontend/src/mock.rs`) uses a `SwapExecutor` mock rather than the real `pallet-asset-conversion`, so I could not run an integration reproduction of the loss inside this environment/session (no terminal access in ask-only mode); constructing a minimal integration test would require wiring `pallet-asset-conversion` as `T::Swap` in the mock runtime, seeding a pool, calling `add_tip` with a value that, if the pool price moves before "execution" (e.g. by another account swapping against the same pool between `validate` and `dispatch`), demonstrates `ether_gained` dropping arbitrarily low while the full input asset is debited. This construction and its expected/actual state assertions were not executed and are provided as the concrete reproduction plan for a background engineer.

		fn swap_fee_asset_and_burn(
			origin: Location,
			fee_asset: Asset,
		) -> Result<u128, DispatchError> {
			let ether_location = T::EthereumLocation::get();
			let (fee_asset_location, fee_amount) = match fee_asset {
				Asset { id: AssetId(ref loc), fun: Fungible(amount) } => (loc, amount),
				_ => {
					tracing::debug!(target: LOG_TARGET, ?fee_asset, "error matching fee asset");
					return Err(Error::<T>::UnsupportedAsset.into());
				},
			};
			if fee_amount == 0 {
				return Ok(0);
			}

			let ether_gained = if *fee_asset_location != ether_location {
				Self::swap_and_burn(
					origin.clone(),
					fee_asset_location.clone(),
					ether_location,
					fee_amount,
				)
				.inspect_err(|&e| {
					tracing::debug!(target: LOG_TARGET, ?e, "error swapping asset");
				})?
			} else {
				burn_for_teleport::<T::AssetTransactor>(&origin, &fee_asset)
					.map_err(|_| Error::<T>::BurnError)?;
				fee_amount
			};
			Ok(ether_gained)
		}
