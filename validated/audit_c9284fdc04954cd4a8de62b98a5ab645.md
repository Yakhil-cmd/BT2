### Title
`StatusHandler#process` writes status rows keyed only by `sha`, with no binding to the webhook-verified repository owner - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`Shipit::WebhooksController#verify_signature` authenticates only that the payload was signed by the GitHub App/organization identified by `repository_owner` (`params.dig('repository','owner','login')`), but `StatusHandler#process` never re-checks that binding when writing data: it resolves target `Commit` rows via a global, cross-tenant `Commit.where(sha: params.sha)` query. Any organization with a validly configured Shipit webhook secret can therefore write a `Status` onto a `Commit` belonging to a completely different organization's `Stack`, as long as the two commits share the same git `sha`.

### Finding Description
The claimed binding is:
`verify_signature`'s authenticated owner `O = params.dig('repository','owner','login')` (used at [1](#0-0) ) MUST equal `Stack#repository.owner` for every `Commit` row mutated by `handler.call(params)` ( [2](#0-1) ).

Tracing the code:
- `verify_signature` fetches `Shipit.github(organization: repository_owner)` and verifies the HMAC signature against that org's app secret, then proceeds if valid; it never scopes anything further and puts nothing about the owner into `params` for the handler to consult. [3](#0-2) 
- `create` dispatches the full parsed JSON `params` to every registered handler for the event via `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`. [2](#0-1) 
- The base `Handler` class provides a `stacks` helper that correctly scopes lookups to the repository named in the payload: `Repository.from_github_repo_name(repository_name)&.stacks || Stack.none`, where `repository_name = payload.dig('repository','full_name')`. [4](#0-3) 
- `CheckSuiteHandler#process` uses this scoped helper correctly: `stacks.where(branch: params.check_suite.head_branch).each { |stack| stack.commits.where(sha: ...) ... }`, so writes are confined to stacks under the verified repository. [5](#0-4) 
- `StatusHandler#process`, by contrast, bypasses `stacks` entirely and queries the global `Commit` table by `sha` alone: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }`. [6](#0-5) 

Because git commit SHAs are content-addressed, any two repositories that share the same commit content (e.g. a fork of an upstream repo, or a copy/re-push of a public commit) will have identical SHAs. An attacker who owns and controls org A's repository (and hence org A's Shipit webhook secret, which is legitimately theirs) can:
1. Identify or reproduce a commit SHA that also exists in org B's `Stack` (e.g., by forking org B's public upstream repo, or by cherry-picking/copying an existing public commit into their own repo).
2. Send a signed `status` webhook (`POST /webhooks`, `X-Github-Event: status`) to Shipit, correctly signed with org A's own webhook secret, containing that shared `sha`, plus attacker-chosen `state`, `context`, `description`, `target_url`.
3. `verify_signature` succeeds because the signature is valid for org A. `StatusHandler#process` then matches `Commit.where(sha: params.sha)` across **all** stacks/repositories, including org B's commit row, and calls `commit.create_status_from_github!(params)` on it, writing an attacker-controlled status onto org B's commit.

None of the existing guards prevent this: `verify_signature` only checks the signature belongs to *some* org, not that the org matches the target commit's stack; `drop_unhandled_event` only checks the event type is registered; the `ExplicitParameters` schema for `StatusHandler` only validates the shape of `sha`/`state`/`context` etc., not their tenant scope; there is no `force_github_authentication`/`require_permission!` check in this webhook path at all (webhooks are unauthenticated by session/API-client design, relying solely on signature-to-repository binding, which `StatusHandler` drops).

### Impact Explanation
A successful request causes Shipit to persist a `Status` record (via `Commit#create_status_from_github!`) on a `Commit` belonging to a stack/repository the attacker does not own and never authenticated against, with attacker-controlled `state`, `context`, `description`, and `target_url`. This can flip a commit's aggregate `state` (e.g. from `pending`/`failure` to `success`), which per `Commit#add_status`/`#schedule_continuous_delivery` can trigger `ContinuousDeliveryJob`, merges via `stack.schedule_merges`, and hooks (`deployable_status`), i.e. influencing deploy/merge decisions for a stack belonging to a different tenant. This matches "a payload for one repository mutating another's stack, commit, task or team" and "an unauthorized deploy, rollback or merge" under Critical impact. It is repeatable against any organization for which the attacker can produce/observe a shared-SHA commit, and the blast radius spans every `Stack` in the Shipit instance since the query is global and unscoped by repository.

### Likelihood Explanation
The attacker needs: (1) a repository registered in Shipit that they control and for which they can receive/derive a valid webhook secret (trivially available to any GitHub org/user who sets up their own Shipit-monitored repo — this is exactly the "unprivileged" actor described, since they only need ownership of their *own* repo), and (2) a commit SHA that coincides with a commit already tracked in a victim stack — realistically achievable via forking a public upstream repository that a victim also tracks, or copying a known public commit. No GitHub App private key, `api_clients_secret`, or victim secrets are needed. The attack is a single crafted HTTP POST to `/webhooks`, fully repeatable, and requires no interaction with the victim.

### Recommendation
Scope `StatusHandler#process` the same way `CheckSuiteHandler` does: resolve target commits only within `stacks` derived from `payload.dig('repository','full_name')` (or otherwise from the verified `repository_owner`), e.g. `stacks.flat_map { |stack| stack.commits.where(sha: params.sha) }.each { |commit| commit.create_status_from_github!(params) }`, instead of querying `Commit` globally by `sha` alone.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb` or controller-level test):
1. Create `repo_a = shipit_repositories(create with owner "org-a")`, `stack_a = repo_a.stacks.create!(...)`.
2. Create `repo_b = shipit_repositories(create with owner "org-b")`, `stack_b = repo_b.stacks.create!(...)`, and `commit_b = stack_b.commits.create!(sha: "deadbeef"*5, ...)`.
3. Build a `status` payload: `{ "sha" => commit_b.sha, "state" => "success", "context" => "ci/attacker", "repository" => { "full_name" => repo_a.full_name, "owner" => { "login" => "org-a" } } }`.
4. Assert the binding before: `commit_b.stack.repository.owner != payload["repository"]["owner"]["login"]` (i.e., `"org-b" != "org-a"`).
5. Call `Shipit::Webhooks::Handlers::StatusHandler.call(payload)` directly (equivalent to what `WebhooksController#create` does after `verify_signature` passes for org-a's own signature — signature verification is orthogonal and can be stubbed/bypassed at the controller level to isolate the row-level check, or tested end-to-end with `Shipit.github(organization: "org-a")` stubbed to accept the signature).
6. Assert after: `commit_b.reload.status.context == "ci/attacker"` and `commit_b.statuses.last.stack_id == stack_b.id`, proving org A's signed payload mutated org B's `Commit`/`Status` despite `repository_owner` ("org-a") never equaling `commit_b.stack.repository.owner` ("org-b").

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```
