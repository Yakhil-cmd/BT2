### Title
Membership webhook authorization scope not bound to authenticating organization, allowing cross-organization `Shipit.github_teams` membership escalation - (File: `app/models/shipit/webhooks/handlers/membership_handler.rb`)

### Summary
`Shipit.github_teams` is the binding that determines who is authorized to use a Shipit deployment (`app/controllers/concerns/shipit/authentication.rb`, `current_user.authorized?`). Membership in those teams is populated exclusively through GitHub `membership` webhook events. The `verify_signature` step in `app/controllers/shipit/webhooks_controller.rb` authenticates a webhook payload against the webhook secret of a *single* organization, but `MembershipHandler` uses a different, unverified field (`team.id`) to decide which `Team` record — and therefore which authorization scope — the requested membership change applies to, without cross-checking that this team actually belongs to the organization whose secret validated the request.

### Finding Description
`WebhooksController#verify_signature` selects which organization's `webhook_secret` to HMAC-verify the raw payload against, based on an unverified field read out of the JSON body itself: [1](#0-0) [2](#0-1) 

For a `membership` event, `repository_owner` resolves from `params.dig('organization', 'login')`. Once the signature checks out for *that* organization's secret, the entire payload is treated as trusted for every handler — including `params.team.id`, a bare integer that is never cross-checked against `params.organization.login`.

`MembershipHandler#find_or_create_team!` looks the `Team` up (or creates it) **solely by `github_id`**: [3](#0-2) 
The `organization` attribute is only set at creation time; on every subsequent call the lookup is `Team.find_or_create_by!(github_id: params.team.id)` with no verification that `params.organization.login` still matches the `organization` already stored on that `Team` row. `process` then unconditionally adds or removes the attacker-supplied `member.login` from that team: [4](#0-3) 

`Shipit.github_teams` — the authorization gate for the whole app — is built from `Team` rows resolved by handle (`organization/slug`), and a user is `authorized?` if they belong to any `Team` whose `id` is in that set: [5](#0-4) [6](#0-5) [7](#0-6) 

**The broken binding, stated as an equality that should hold but doesn't:**
`organization that authenticated the webhook (repository_owner used to pick webhook_secret)` == `organization that owns the Team record whose membership is mutated (params.team.id)`.

Before the attack: a `Team` row for the authorized org's team (e.g. `myorg/deployers`, `github_id = 555`) already exists in the DB from legitimate prior `membership` webhooks, and is part of `Shipit.github_teams`.

After the attack: an actor who only knows/controls webhook credentials for an unrelated, unprivileged organization (`attacker-org`, its own `webhook_secret`) can POST directly to the public `/github/webhooks` endpoint (no Shipit session, no `ApiClient` token needed — `WebhooksController` only requires a valid HMAC for *some* configured org) with:
```json
{
  "action": "added",
  "organization": { "login": "attacker-org" },
  "team": { "id": 555, "name": "x", "slug": "x", "url": "x" },
  "member": { "login": "attacker-github-login" }
}
```
signed with `attacker-org`'s `webhook_secret`. `verify_signature` passes because it only checks the `attacker-org` secret against `repository_owner = "attacker-org"`. `MembershipHandler` then finds the *existing* `Team(github_id: 555)` — the real, privileged `myorg/deployers` team — and calls `team.add_member(User.find_or_create_by_login!("attacker-github-login"))`, granting the attacker's GitHub identity membership in the privileged team.

### Impact Explanation
Once membership is added, `current_user.authorized?` (`app/models/shipit/user.rb:80-82`) is satisfied for the attacker's own GitHub account the next time they log in via `GithubAuthenticationController`, bypassing the `Shipit.github_teams` gate entirely — this is explicitly listed as a High-impact escalation ("escalation into `Shipit.github_teams` authorization"). Because Shipit authorization is typically the only guard in front of deploy/rollback/merge actions across all stacks, this can cascade to unauthorized deploys.

### Likelihood Explanation
Requires only knowledge of one organization's `webhook_secret` — a credential of the *lowest*-privilege org configured on a shared/multi-tenant Shipit instance (a normal, legitimately onboarded but unprivileged team) — and no Shipit account, session, or API token. The only non-trivial requirement is knowing the numeric GitHub `team.id` (`github_id`) of the target privileged team; this is a real, stable GitHub-assigned integer, not a secret, and can be small/sequential or discoverable through normal GitHub API access an attacker may have to public organizations, so it should be treated as guessable/discoverable rather than protected.

### Recommendation
In `MembershipHandler#find_or_create_team!`, verify that `params.organization.login` matches the `organization` already stored on any existing `Team(github_id: ...)` record before mutating membership, and reject/ignore the event otherwise. More generally, `WebhooksController#verify_signature` should ensure every payload field consumed by handlers to select the target resource (team, repository, stack) is scoped to the same organization whose secret validated the request, not merely to whichever organization login happens to appear in the payload.

### Proof of Concept
1. Attacker is a member of (or otherwise possesses the `webhook_secret` for) `attacker-org`, an organization already configured in Shipit's `secrets.github`, but has no membership in the privileged team backing `Shipit.github_teams`.
2. Obtain the numeric `github_id` of the target privileged team (e.g., `myorg/deployers`), already present as a `Team` row in Shipit's DB from prior legitimate webhook traffic.
3. Craft a JSON body:
   ```json
   {"action":"added","organization":{"login":"attacker-org"},"team":{"id":<privileged_team_github_id>,"name":"x","slug":"x","url":"x"},"member":{"login":"<attacker_github_login>"}}
   ```
4. Compute `X-Hub-Signature: sha1=<hmac-sha1(attacker-org_webhook_secret, body)>`.
5. `POST /github/webhooks` with header `X-Github-Event: membership` and the above body/signature.
6. `WebhooksController#verify_signature` succeeds (signature valid for `attacker-org`). `MembershipHandler` runs, finds the existing privileged `Team` by `github_id`, and adds the attacker's GitHub login as a member.
7. Attacker logs into Shipit via GitHub OAuth; `current_user.authorized?` now returns true due to the forged team membership.

Note: I could not fully verify from the indexed code how discoverable/guessable a target `Team.github_id` is in a given deployment (this depends on target org visibility and whether the attacker has any legitimate access to enumerate its teams via the GitHub API), so likelihood may vary by deployment; this uncertainty is flagged rather than assumed away.
