### Title
Webhook signature verification is keyed on the payload's organization field while the repository actually acted upon is a different, unchecked field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App configuration (and thus which `webhook_secret`) to verify the HMAC signature against using an attacker-controlled field in the JSON body (`repository.owner.login` or `organization.login`), but the handlers that actually act on the payload (`Shipit::Webhooks::Handlers::Handler#repository_name`) resolve the target `Repository`/`Stack` from a completely different, independently-controlled field: `payload.dig('repository', 'full_name')`. Nothing ties these two fields together.

### Finding Description
`verify_signature` computes the organization to verify against like this: [1](#0-0) [2](#0-1) 

Crucially, if the resolved organization has no `webhook_secret` configured, `verify_webhook_signature` unconditionally returns `true`, accepting **any** body regardless of the `X-Hub-Signature` header: [3](#0-2) 

`webhook_secret` is explicitly documented as *optional* per organization, so a multi-org Shipit deployment can legitimately have some organizations configured without a secret: [4](#0-3) [5](#0-4) 

Meanwhile, every webhook handler resolves the target repository/stack independently, from an entirely different JSON field that is never cross-checked against the field used for signature verification: [6](#0-5) 

This breaks the equality that should hold: `organization authenticated by verify_signature` == `organization owning the repository that handlers act on`. An attacker who controls (or merely knows the name of) any organization configured in the same Shipit instance without a `webhook_secret` can craft an arbitrary, unsigned/any-signature POST to `/webhooks` where `repository.owner.login` (or top-level `organization.login`) names the unsecured org (satisfying `verify_signature`), while `repository.full_name` names a completely different, secured target repository/stack that the handler will operate on.

The `push` handler is the most consequential: it looks up `stacks` for the (attacker-chosen) `repository.full_name`, filters by `branch` from `params.ref`, and calls `stack.sync_github(expected_head_sha: params.after)` for every matching, non-archived stack, with `after` (the target SHA) fully attacker-controlled: [7](#0-6) 

Because `sync_github` re-syncs commit/CI state and, for stacks with `continuous_deployment: true`, can drive the stack toward deploying whatever commit is now considered "head", this lets an attacker who only controls an unrelated, secret-less GitHub organization spoof pushes against a target repository/stack belonging to a different, properly-secured organization, without ever presenting a valid signature for that organization's secret.

The `membership` handler is similarly reachable and independently dangerous: it creates/mutates `Team` and `User` records and adds arbitrary GitHub logins as team members based purely on payload content, again gated only by the org-selection logic in `verify_signature`: [8](#0-7) 

Since `Shipit.github_teams` membership drives authorization (`User#authorized?`), and `Team.add_member` is invoked from an attacker-influenced webhook that only needed to defeat verification for an unrelated, secret-less org, this crosses directly into the documented High-impact category: "escalation into `Shipit.github_teams` authorization." [9](#0-8) 

### Impact Explanation
This crosses two of the listed impact categories:
- **Unauthorized deploy/rollback trigger**: spoofed `push` events against a target stack's `repository.full_name`/branch can force re-sync and, for continuously-deployed stacks, drive a deploy of an attacker-chosen commit, without a valid signature for the target organization.
- **Escalation into `Shipit.github_teams` authorization**: spoofed `membership` events can add an arbitrary GitHub login to a `Team` that is part of `Shipit.github_teams`, granting that user (once they authenticate via OAuth) `authorized?` access to the whole Shipit instance.

Both impacts are achievable purely by defeating verification for one unsecured organization while acting on a repository/team belonging to a different, secured organization — no `ApiClient` token, session, or GitHub write access to the target repository is required.

### Likelihood Explanation
Likelihood depends on the specific deployment having at least one configured GitHub organization without a `webhook_secret`, which the project's own documentation calls out as an *optional* setting, and which the shipped example secrets file sets to `nil` by default. Any Shipit instance following the "multiple GitHub organizations" configuration pattern with even one org left unsecured (a very plausible operational lapse given the explicit "optional" framing) is exposed. The `/webhooks` endpoint requires no authentication of any kind beyond this per-organization HMAC check, so the attacker only needs the ability to send an arbitrary HTTP POST.

### Recommendation
Bind the identity used for signature verification to the identity used for repository/stack/team resolution:
- After computing `repository_owner`/`organization.login` for `verify_signature`, require that the same value match the owner segment of `repository.full_name` (and the `organization.login` used by `MembershipHandler`) before dispatching to handlers.
- Alternatively, resolve the target `Repository`/`Stack`/`Team` first, and pick the GitHub App config to verify against based on that resolved entity's known owner (from the database), not from attacker-supplied payload fields — never let the same untrusted payload dictate both "which secret to check" and "what to act on."
- Do not allow `verify_webhook_signature` to silently succeed (`return true unless webhook_secret`) for a configuration where other organizations in the same instance are secured; either require all organizations to configure a `webhook_secret` or fail closed when the owner cannot be cross-validated against the repository being acted upon.

### Proof of Concept
1. Configure Shipit for two orgs: `org-open` (no `webhook_secret`) and `org-secure` (has `webhook_secret` set), each per the multi-org config format in `docs/setup.md`.
2. `org-secure` owns a stack tracking `org-secure/target-repo` on branch `main`, with `continuous_deployment: true`.
3. Attacker (with no access to `org-secure` or its webhook secret) POSTs to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "full_name": "org-secure/target-repo",
    "owner": { "login": "org-open" }
  }
}
```
with any (or garbage) `X-Hub-Signature` header.
4. `verify_signature` resolves `repository_owner` = `"org-open"`, calls `Shipit.github(organization: "org-open")`, whose `verify_webhook_signature` returns `true` unconditionally because `org-open` has no `webhook_secret` — request passes.
5. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("org-secure/target-repo")`, matching the real `org-secure` stack, and calls `sync_github(expected_head_sha: "<attacker-chosen-sha>")`, causing the secured stack to sync/deploy based on attacker-controlled input, despite the request never having a valid signature for `org-secure`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
