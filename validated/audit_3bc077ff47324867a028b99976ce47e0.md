### Title
`reward_per_token` division by `total_tokens_staked` can round to zero, permanently freezing reward accrual for stakers with disproportionately large stake - ([File: substrate/frame/asset-rewards/src/lib.rs])

### Summary
`pallet-asset-rewards`'s `reward_per_token` computes a per-token reward increment by multiplying `reward_rate_per_block * blocks_elapsed * PRECISION_SCALING_FACTOR` and dividing by `total_tokens_staked`, exactly mirroring the reported bug pattern: a rate multiplied by an elapsed-time factor, divided by a large attacker-influenced denominator, using integer division that can floor to `0`.

### Finding Description
`reward_per_token` is:
```rust
Ok(pool_info.reward_per_token_stored.ensure_add(
    pool_info
        .reward_rate_per_block
        .ensure_mul(rewardable_blocks_elapsed.into())?
        .ensure_mul(PRECISION_SCALING_FACTOR.into())?
        .ensure_div(pool_info.total_tokens_staked)?,
)?)
``` [1](#0-0) 

`PRECISION_SCALING_FACTOR` is a small fixed constant (`4096`) meant to preserve precision [2](#0-1) , but exactly like the report's fixed `interval` value that doesn't scale with the attacker-controlled `borrowedAmountFromPool`, this fixed multiplier does not scale with `total_tokens_staked`, which is directly attacker-controlled: `stake` is a permissionless, signed extrinsic that lets any account increase `pool_info.total_tokens_staked` arbitrarily [3](#0-2) .

If an attacker stakes a very large amount relative to `reward_rate_per_block`, the numerator (`reward_rate_per_block * blocks_elapsed * 4096`) can become smaller than `total_tokens_staked`, causing `ensure_div` to floor to `0` for however many blocks elapse between calls to `reward_per_token`. Since `reward_per_token_stored` is only ever updated additively via this same rounding-prone division [4](#0-3) , and staker rewards are derived from the delta between `reward_per_token` and `staker_info.reward_per_token_paid` [5](#0-4) , this rounding-to-zero is not a one-off truncation of a fraction of a token (as intended by the design) — it can zero out reward accrual entirely for extended periods, harming all other stakers in the pool, not just the attacker.

This differs from the resolved report's exact numeric scenario, but the root cause (fixed-precision multiplier vs. attacker-scalable divisor, integer division truncating to zero) is structurally the same class of bug.

### Impact Explanation
Honest stakers earn zero or near-zero rewards for as long as the attacker maintains an outsized stake relative to `reward_rate_per_block * PRECISION_SCALING_FACTOR`, since `reward_per_token_stored` fails to increase across those blocks. Because `Pools`/`PoolStakers` storage retains no record of "missed" reward-per-token beyond `reward_per_token_stored`, this loss is not merely a rounding of a fraction of a wei-equivalent — it is a sustained freezing/dilution of the entire pool's promised reward distribution, degrading token-economics guarantees for the pallet's reward mechanism. This would be a Medium/Low-severity griefing/precision issue in FRAME terms (no unbacked issuance, no unauthorized dispatch, no fund theft by the attacker), constrained by the fact that the attacker must self-fund a large stake (economic cost) and the effect is temporary/reversible once staking ratio or reward rate changes.

### Likelihood Explanation
Likelihood is low-to-moderate in practice: `stake` is fully permissionless for any signed account with the staked asset [6](#0-5) , so no privileged role is required, satisfying the "real user entry point" requirement. However, triggering meaningful, sustained rounding to zero requires the reward rate to be small and/or blocks between updates to be few relative to `total_tokens_staked / PRECISION_SCALING_FACTOR`, i.e., pool parameters chosen by the (trusted) admin at `create_pool` largely determine exposure. `PRECISION_SCALING_FACTOR` (4096) already provides some headroom compared to the "interval = 1" case in the original report, meaning many realistic reward-rate/stake configurations would not trigger the zero-rounding, but no minimum-quotient or "never zero if diff > 0" guard analogous to `converted_fee_is_never_zero_if_input_fee_is_not` (seen elsewhere in transaction-payment) exists here to hard-prevent it [7](#0-6) .

### Recommendation
Increase `PRECISION_SCALING_FACTOR` (or use a wider intermediate type such as `u128`/fixed-point `FixedU128`) so that `reward_rate_per_block * blocks_elapsed * PRECISION_SCALING_FACTOR` cannot be driven below `total_tokens_staked` for realistic staking ranges, and/or add an explicit check/rounding-up strategy in `reward_per_token` similar to `MultiplyRational`/`Rounding` utilities already present in `sp_arithmetic` [8](#0-7)  to guarantee a nonzero increment whenever `reward_rate_per_block` and elapsed blocks are nonzero.

pub trait MultiplyRational: Sized {
	fn multiply_rational(self, n: Self, d: Self, r: Rounding) -> Option<Self>;
}

macro_rules! impl_rrm {
	($ulow:ty, $uhi:ty) => {
		impl MultiplyRational for $ulow {
			fn multiply_rational(self, n: Self, d: Self, r: Rounding) -> Option<Self> {
				if d.is_zero() {
					return None;
				}

				let sn = (self as $uhi) * (n as $uhi);
				let mut result = sn / (d as $uhi);
				let remainder = (sn % (d as $uhi)) as $ulow;
				if match r {
					Rounding::Up => remainder > 0,
					// cannot be `(d + 1) / 2` since `d` might be `max_value` and overflow.
					Rounding::NearestPrefUp => remainder >= d / 2 + d % 2,
					Rounding::NearestPrefDown => remainder > d / 2,
					Rounding::Down => false,
				} {
					result = match result.checked_add(1) {
						Some(v) => v,
						None => return None,
					};
				}
				if result > (<$ulow>::max_value() as $uhi) {
					None
				} else {
					Some(result as $ulow)
				}
			}
		}
