Based on extensive searching, I could not find a genuine analog to this bug in the Polkadot SDK codebase.

**Why no analog was found:**

The Sherlock/Cooler bug is a direct consequence of Solidity's implicit storage reference semantics: `Loan storage loan = loans[loanID];` binds a *storage pointer*, so `delete loans[loanID]` (which zeroes the underlying storage slot) causes a subsequent read of `loan.lender` to yield `address(0)`, and that stale/zeroed value is then used as the transfer destination.

Rust/FRAME storage access does not have this hazard by construction: `StorageMap::get()`/`take()` returns an owned value (a copy), and pallets consistently bind the recipient field to a local `let` binding *before* removing/mutating the storage entry, so no code path can accidentally re-read a zeroed struct after deletion. I verified this pattern across every "claim/close and delete storage, then pay out" style extrinsic that structurally resembles `Cooler::repay()`:

- `pallet_bounties::claim_bounty` — `curator` and `beneficiary` are destructured from the `bounty.status` enum and used for `T::Currency::transfer` calls, then `*maybe_bounty = None` is set only *after* the transfers, using the already-extracted `curator`/`beneficiary` locals, not a post-removal storage read. [1](#0-0) 
- `pallet_child_bounties::claim_child_bounty` — same pattern: `curator`/`beneficiary` bound from the matched status, transfers executed, and only then `*maybe_child_bounty = None`.
