### Title
Instantaneous utilization can be manipulated to permanently distort the shared debt/liquidity index applied to all borrowers and depositors - (File: `mainnet/contracts/vault/v0-vault-usdc.clar` and equivalent per-asset vaults)

### Summary
Each vault's borrow-interest and liquidity-interest indices (`index`, `lindex`) are shared state consumed by every depositor and borrower. They are updated lazily via `accrue`, which computes the rate to apply over the **entire elapsed time** since `last-update` using only the **instantaneous** utilization read at the moment `accrue` executes. This lets any unprivileged caller who can momentarily move utilization (e.g., via a large borrow/repay or deposit/withdraw sequence, optionally funded by a flashloan) apply a spot-manipulated rate to a long, un-accrued time window, permanently ratcheting the shared index for the entire user base — before reversing their own position and paying only gas/opportunity cost.

### Finding Description
`utilization()`/`interest-rate()` compute a purely instantaneous ratio from `get-available-assets()` and `total-debt()`: [1](#0-0) 

That instantaneous `interest-rate` is then compounded not for an instant, but over the full elapsed `time-delta` since the last time `accrue` ran (`stacks-block-time - last-update`), which can span an arbitrary number of blocks if no one has interacted with the vault: [2](#0-1) 

`accrue` writes the result directly into the global `index`/`lindex` variables that every user's debt (`scaled-principal * index`) and share value are computed from, and it is invoked as the first step of every state-changing borrower/lender action (`system-borrow`, `system-repay`, etc.): [3](#0-2) 

Because the rate applied to the whole elapsed window is sampled at a single instant rather than averaged/TWAP'd over that window, an attacker can:
1. Wait until a meaningful amount of time has passed since `last-update` (interest-rate compounding period is large).
2. Spike (or depress) `utilization()` momentarily — e.g., by borrowing a large amount against available liquidity (capital can come from a flashloan, used only to fund the position) or by depositing/withdrawing to change `get-available-assets()`.
3. Trigger `accrue()` (any borrow/repay call does this automatically) so the abnormal instantaneous rate gets compounded over the full stale `time-delta` and permanently written to `index`/`lindex`.
4. Reverse their own position immediately after, having paid only the interest that accrued during their own tiny window, while every other borrower's outstanding debt (`scaled-principal * index`) and every depositor's share value are now computed against the manipulated index.

This is a shared-state (index) priming attack: one caller's transient action determines a value that is later consumed uniformly by all other, unrelated users' debt and asset accounting — it is not the attacker's own economics being affected, but every other position-holder's.

### Impact Explanation
Existing borrowers can be forced to owe more debt than they should (their `scaled-principal` gets multiplied by an inflated `index` computed from a manipulated instantaneous rate applied over a long stale window they had no part in), and existing depositors' `lindex`-based yield can likewise be distorted up or down. Since the index directly encodes accrued interest for the whole user base, this is a form of value transfer between unrelated users mediated entirely through a shared cache — a temporary/permanent misallocation of accrued yield (interest owed/earned), landing in the "theft/freezing of unclaimed yield" impact category.

### Likelihood Explanation
Requires the attacker to have enough capital (or to use a flashloan purely as capital, which is in-scope per the rules) to move utilization meaningfully, and to time the attack after a period of inactivity so the elapsed `time-delta` is large enough for the distortion to be material. No privileged role is needed — `system-borrow`/`system-repay` are reachable by any account with `check-caller-auth` (market-routed), and `accrue` is triggered automatically on every borrow/repay.

### Recommendation
Use a time-weighted / averaged utilization (or checkpoint the rate more frequently, e.g., cap the maximum single-compounding interval, or accrue in smaller sub-intervals using multiple rate snapshots) rather than applying one instantaneous spot rate to an unbounded elapsed window. Alternatively, bound how much a single caller's action can move `utilization()` within one block/transaction before it is used for accrual, or accrue interest before allowing large utilization-moving actions to take effect for that block.

### Proof of Concept
Conceptual reproduction (mirrors the structure of the original PoC against `next-index`/`accrue` instead of `RAACMinter.emissionRate`):
1. Deploy/observe a vault where `last-update` is stale (e.g., simulate many blocks passing with `stacks-block-time` advanced, no intervening `accrue` calls).
2. Attacker calls `system-borrow` with a large `amount` (optionally financed via flashloan) to spike `utilization()` right up to the top of the rate curve.
3. In the same call, `accrue()` fires as part of `system-borrow`, computing `next-index`/`next-liquidity-index` using the spiked `interest-rate()` compounded over the full stale `time-delta`, and commits it via `var-set index next` / `var-set lindex nliq`.
4. Attacker immediately calls `system-repay` to unwind their borrow.
5. Compare any other borrower's `total-debt` (via `debt-preview`/`total-debt`, which uses the now-updated `index`) before vs. after the attacker's two transactions: it increases by more than the interest that should have accrued at the vault's "normal"/average utilization over that period, at no material cost to the attacker beyond gas and brief exposure.

Note: I was unable to fully inspect `get-available-assets`, `deposit`/`withdraw` implementations, and the flashloan-permission gating (`flashloan-permissions` map, `check-caller-auth`) before the tool budget was exhausted, so the exact capital requirements and any secondary guardrails (e.g., fee-exempt flags, deposit/withdraw pause states) that might partially mitigate this could not be fully confirmed.

(define-private (next-index)
  (let ((states (var-get pause-states))
        (idx (var-get index)))
    (if (get accrue states)
        idx
        (let (
            (rate (interest-rate))
            (time-delta (- stacks-block-time (var-get last-update)))
            (multiplier (if (is-eq time-delta u0)
                          INDEX-PRECISION
                          (calc-multiplier-delta rate time-delta true))))
          (calc-index-next idx multiplier)))))
