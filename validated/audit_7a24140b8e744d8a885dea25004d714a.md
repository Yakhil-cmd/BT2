### Title
Loss of headers commission if no eligible child stabilizes within one main-chain index of its parent - (File: headers_commission.js)

### Summary
`calcHeadersCommissions` in `headers_commission.js` searches for the "winning" child unit that earns a parent unit's `headers_commission` only among children that are marked `sequence='good'` **and** stabilize at the same or next main-chain index (MCI) as the parent. When this restricted candidate set is empty, the code silently skips the parent unit instead of retrying later or refunding/redistributing the commission — the funds are effectively burned, unlike the analogous "return unused incentives to inflation" expectation described in the referenced report.

### Finding Description
`calcHeadersCommissions` builds, for every stable "good" parent unit, the list of eligible "child" candidates that can win the parent's `headers_commission`: [1](#0-0) 

```js
var filter_func = function(child){
    return (child.sequence === 'good' && child.parent_units && child.parent_units.indexOf(parent.unit) > -1);
};
var arrSameMciChildren = storage.assocStableUnitsByMci[parent.main_chain_index].filter(filter_func);
var arrNextMciChildren = storage.assocStableUnitsByMci[parent.main_chain_index+1].filter(filter_func);
var arrCandidateChildren = arrSameMciChildren.concat(arrNextMciChildren);
if (arrCandidateChildren.length === 0)
    return; // all eligible children are final-bad, nobody gets the hc
```

This is the exact analog of the reported bug: the "total weight" here is the count of eligible ("good") children within the ±1 MCI window of the parent. If that "weight" is zero — e.g. all of the parent's children within this window happen to be marked `final-bad` (non-serial, e.g. due to a double-spend conflict, per `main_chain.js` `handleNonserialUnits`/`propagateFinalBad`) while the actual serial ("good") descendant of the parent stabilizes at an MCI more than 1 away — the function simply `return`s without ever recording an entry for `assocChildrenInfosRAM[parent.unit]`/`assocChildrenInfos[payer_unit]`. Consequently: [2](#0-1) 

```js
var assocWonAmounts = {}; // amounts won, indexed by child unit who won the hc, and payer unit
for (var payer_unit in assocChildrenInfos){
    ...
}
var arrWinnerUnits = Object.keys(assocWonAmounts);
if (arrWinnerUnits.length === 0)
    return cb();
```

The parent's `headers_commission` never gets a corresponding row inserted into `headers_commission_contributions`/`headers_commission_outputs`, so it is not credited to any address, not refunded to any pool, and not retried on a later `calcHeadersCommissions` pass, since `max_spendable_mci` is advanced monotonically once the batch that included this `since_mc_index+1` window finishes: [3](#0-2) 

The developers' own comment confirms this is a known, accepted loss for the genesis-unit edge case only ("hack for genesis unit where we lose hc"), but the general `arrCandidateChildren.length === 0` branch applies to any parent unit in the DAG, not just genesis, and there the comment ("nobody gets the hc") documents the same unconditional loss without any special-casing or refund path.

### Impact Explanation
`headers_commission` is byte funds paid by the parent unit's author, meant to always end up with exactly one recipient (the winning child's author(s) or its `earned_headers_commission_recipients`). When the eligible-candidate set is empty, those bytes are permanently removed from circulation without being credited to any address or accounted for anywhere else (no burn tracking, no return to a shared pool) — a direct, uncompensated loss of value for the parent unit's author, analogous to the reported "loss of incentives" (funds that should be conserved simply vanish) rather than a controlled fund-conservation design (e.g., refund to inflation as in the external report).

### Likelihood Explanation
This path is reachable by an ordinary unit poster: any user can create a parent unit with two or more children units and cause one of the double-spending descendants to be finalized as `final-bad` via the normal non-serial resolution logic (`main_chain.js` `handleNonserialUnits`, `propagateFinalBad`). If none of the "good" descendants directly referencing the parent stabilize within the parent's MCI or MCI+1 (which can occur under normal DAG growth patterns, not solely adversarial ones, whenever the surviving serial descendant of a parent needs more than one extra main-chain index to stabilize), the candidate list becomes empty and the commission is lost. This does not require any privileged role, malicious peer/node behavior, or network-level attack — it is a consequence of standard commission accounting under normal DAG conditions.

### Recommendation
When `arrCandidateChildren.length === 0` for a parent unit, do not silently skip it. Instead, either:
- widen the search window (retry at later MCIs, tracking parents whose HC hasn't been distributed yet) until a "good" child is found and can win the commission, or
- explicitly account for the amount (e.g., insert a self-refund output to the parent's own author, or a dedicated "unclaimed headers commission" pool) rather than dropping the parent unit from `assocChildrenInfos` entirely, and record which parent's HC has already been resolved so it isn't processed twice once a later fix runs.

### Proof of Concept
1. Post unit `P` (a parent) with `headers_commission > 0`.
2. Post two children `C1` and `C2` of `P` that double-spend the same output, both referencing `P` as a parent.
3. Let the network resolve `C1` as the sole serial ("good") descendant while `C2` becomes `final-bad` per `main_chain.js` nonserial handling.
4. Arrange for `C1`'s own stabilization (its own `main_chain_index`, not `P`'s) to occur more than 1 index after `P.main_chain_index` (e.g., due to it not being directly on the main chain but confirmed via a witnessed-level path that takes longer to stabilize).
5. When `calcHeadersCommissions` runs for `since_mc_index = P.main_chain_index`, `storage.assocStableUnitsByMci[P.main_chain_index]` and `storage.assocStableUnitsByMci[P.main_chain_index+1]` contain no `good` child of `P` (`C2` is `final-bad`, `C1` is not yet at that MCI), so `arrCandidateChildren.length === 0` and the function returns without ever crediting `P.headers_commission` to any address — confirmed by inspecting `headers_commission_outputs` afterward, which will never contain a row for `P`'s commission.
