## Title
Signature verification keyed on `repository.owner.login` while write target is resolved from a different payload field `repository.full_name`, breaking the `authenticated organization == written repository` binding - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects the GitHub App (and thus the webhook secret used for HMAC verification) using `repository_owner`, derived from `params.dig('repository', 'owner', 'login')` [1](#0-0) [2](#0-1) . Once the signature passes, `create` re-parses the same raw body and dispatches it to handlers [3](#0-2) . Every handler, however, resolves the target `Repository`/`Stack` to write to using a *different* JSON field, `repository.full_name`, via `Handler#repository_name` / `Handler#stacks` [4](#0-3) , and per-handler code such as `OpenedHandler#repository` [5](#0-4) .

### Finding Description
The equality this code implicitly relies on is:

`organization that authenticated the signature (repository.owner.login)` == `repository that gets written to (repository.full_name)`

Both values come from the same attacker-controlled JSON body, and nothing in `verify_signature` or in `Handler` cross-checks that `repository.full_name` actually belongs to `repository.owner.login`/the org whose secret validated the signature. `repository.full_name` is a free-form string (e.g. `"otherorg/other-repo"`) that is not required to share the `owner.login` value used for HMAC selection.

This mirrors the report's root cause pattern: a value used to gate/authorize an action (`initId`/signature-checked org) is decoupled from the value actually acted upon (`_openPositions` mutation / repository actually written), because the implementation trusts one field for authorization and a different field for the effect.

Practically, in a single-organization Shipit deployment (the common case, `Shipit.github` configured without the multi-org hash) `Shipit.github(organization: repository_owner)` always returns the same singleton `GithubApp`/secret regardless of `repository_owner`'s value [6](#0-5) , so the binding is not org-scoped there and this specific analog is not exploitable. The multi-tenant configuration (`somegithuborg`/`someothergithuborg` in `config/secrets.yml`) is where `verify_webhook_signature` is actually selected per-organization [7](#0-6) , but I could not fully trace `Shipit.github(organization:)`'s org-lookup/`GithubOrganizationUnknown` resolution logic from the index to confirm whether it is keyed strictly by `owner.login` and whether cross-org secrets are truly isolated per repository at this layer, versus being globally shared for all installs on one App. That resolution logic (in `lib/shipit.rb` or `lib/shipit/github_app.rb`, config parsing) was not returned in full by the search and would need direct inspection in a full checkout.

### Impact Explanation
If confirmed reachable in a multi-organization Shipit installation, an entity holding a valid `webhook_secret` for OrgA (which is not "privileged" relative to OrgB — the org boundary is exactly what Shipit's multi-org config is meant to enforce) could sign a payload whose `repository.owner.login` is OrgA (to pass `verify_signature`) but whose `repository.full_name` claims a repository under OrgB, causing handlers to create commits, PR-driven review stacks, or check-run/status updates against OrgB's `Stack` records. That would be a cross-repository/cross-tenant write performed by a party never authenticated against OrgB, matching the "cross-repository writes" Critical impact category.

### Likelihood Explanation
Low-to-uncertain. It requires (a) a multi-org Shipit deployment, and (b) confirmation that `Shipit.github(organization:)`'s per-org secret map is keyed only by the unauthenticated `owner.login` field without any additional binding to `full_name`, which I could not fully verify from the indexed code (the org-config resolution and `GithubOrganizationUnknown` raising logic were not returned in full). In the default single-org configuration this is not exploitable at all, since one shared secret is used regardless of the claimed owner.

### Recommendation
In `Handler#repository_name`/`#stacks` and in each handler's `repository` resolution, assert that the owner segment of `repository.full_name` matches `payload.dig('repository', 'owner', 'login')` (the same field used for signature-secret selection), and reject the webhook otherwise. Alternatively, verify the signature using the `full_name`-derived owner rather than a separately-read `owner.login`/`organization.login` field, so a single field consistently governs both authentication and the write target.

### Proof of Concept
Conceptual (not verified end-to-end due to inability to inspect the multi-org secret-selection internals):
1. Attacker possesses/derives OrgA's `webhook_secret` (a valid, but org-scoped, credential — not a global privilege).
2. Attacker POSTs to `/webhooks` a `pull_request` `opened` event with `repository.owner.login = "orgA"` and `repository.full_name = "orgB/target-repo"`, HMAC-signed with OrgA's secret.
3. `WebhooksController#verify_signature` computes `Shipit.github(organization: "orgA")` and validates the signature successfully [1](#0-0) .
4. `Shipit::Webhooks::Handlers::PullRequest::OpenedHandler#repository` looks up `Shipit::Repository.from_github_repo_name("orgB/target-repo")` [5](#0-4)  and, if review stacks are enabled, provisions/creates review-stack state for OrgB's repository — despite OrgB never having authenticated this request.

Given the uncertainty around whether the multi-org secret map is truly keyed in a way that allows this cross-org mismatch (I could not confirm this from the available index), I present this as the closest structural analog to the report's "value used for authorization decoupled from value used for the effect" pattern, but flag that full verification requires reading the complete `Shipit.github`/organization-config resolution code, which a Devin session with full repository access could confirm.

```markdown
## Creating the GitHub App

Shipit needs a GitHub App to authenticate users, receive Webhooks and access the API.

You can create a new one for your organization at `https://github.com/organizations/<your-org>/settings/apps/new`, or [https://github.com/settings/apps/new](https://github.com/settings/apps/new) for a regular user.

  - Homepage URL: The URL where Shipit will be deployed, e.g. `https://example.com`.
  - User authorization callback URL: It must be set to `<homepage>/github/auth/github/callback`, e.g. `https://example.com/github/auth/github/callback`.
  - Setup URL: Leave it empty.
  - Webhook URL: It must be set to `<homepage>/webhooks`, e.g. `https://example.com/webhooks`.
  - Webhook secret (optional): Fill it with some randomly generated string, and *keep it in clear on the side, you'll need it later*.
```
