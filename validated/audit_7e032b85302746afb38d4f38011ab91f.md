### Title
Unbounded scan of all unstable messages in `dataFeedExists()`/`readDataFeedValue()` enables AA-trigger DoS via unstable `data_feed` flooding - (File: `data_feeds.js`)

### Summary
`dataFeedExists()` and `readDataFeedValue()` in `data_feeds.js` support an "unstable" oracle-lookup mode (`bAA`/`unstable_opts`) used when an AA's oscript formula checks a `data_feed` condition against not-yet-stable oracle data. In this mode, both functions iterate over `storage.assocUnstableMessages` — the in-memory map of **every currently-unstable message on the whole DAG**, not just messages from the requested oracle addresses — filtering only after entering the loop. [1](#0-0) [2](#0-1) 

This mirrors the `processFees()` bug class: an unbounded loop over a collection that is filled by ordinary, low-privilege actions (posting units) and later traversed in full during a routine operation, with no cap on the collection size.

### Finding Description
`storage.assocUnstableMessages` accumulates a message entry for every unstable unit's message until the unit becomes stable. Any address can post units cheaply with a `data_feed` app-message (`aa_validation.js` allows `data_feed` payloads with only per-field length checks, no cap on the *number* of such units kept unstable at once): [3](#0-2) 

When any AA whose oscript uses `data_feed[...]` with `unstable_opts` (a documented, normal oscript feature for reading in-flight oracle values) is triggered, `dataFeedExists`/`readDataFeedValue` walk the **entire** `storage.assocUnstableMessages` map: [4](#0-3) [5](#0-4) 

For each unstable unit encountered, the code does a `_.intersection` against `arrAddresses` and, for matching authors, an inner `forEach` over that unit's messages. Since stability can lag (deliberately, e.g., under high load, low-witness-diversity conditions, or simply by an attacker continuously posting cheap `data_feed` units before they get included past the stability point), an unprivileged unit poster can grow `storage.assocUnstableMessages` arbitrarily large. There is no limit analogous to `MAX_MESSAGES_PER_UNIT` or `MAX_OUTPUTS_PER_PAYMENT_MESSAGE` bounding the *total* number of unstable messages scanned here — the loop cost is O(total unstable messages network-wide), fully attacker-controllable and unbounded, exactly like the unbounded `_heldFeesOf[_projectId]` loop in the referenced report.

### Impact Explanation
Every node performing validation/execution of any AA trigger that hits this code path (i.e., any AA using `data_feed[...]` with the unstable-lookup option, a normal, intentionally-supported oscript feature) must pay this unbounded cost. As an attacker inflates the unstable-message set, AA trigger processing time for such AAs grows without bound, degrading to the point where:
- AA response computation for the primary trigger can stall or be delayed enough to affect timely stabilization, freezing normal use of any AA relying on real-time/unstable oracle reads (a fund-freezing/DoS effect on affected AAs), and
- because this scan happens deterministically inside `handleTrigger`'s formula evaluation, all full nodes pay the same growing cost each time it recurs, degrading overall network throughput for unit/AA processing, comparable to the "network unable to confirm new units" impact class.

### Likelihood Explanation
Likelihood is moderate-to-high: any address can post ordinary `data_feed` messages at low cost, no special privilege or economic barrier prevents accumulating many unstable data_feed messages simultaneously (only normal per-message/per-unit size fees apply), and the vulnerable read path (`unstable_opts`) is a documented, commonly-used oscript feature for AAs that need low-latency oracle data, so triggering the expensive path does not require an unusual contract.

### Recommendation
Bound the cost of the unstable lookup, e.g.:
- Maintain a per-`(address, feed_name)` index of unstable data-feed messages instead of scanning the flat `storage.assocUnstableMessages` map, or
- Cap the number of unstable messages/units considered (skip/short-circuit once a configurable limit is exceeded and treat as "not found" or require stabilization), or
- Track and enforce a hard cap on how many unstable `data_feed` messages any single address (or the network) may have outstanding at once, so the loop bound stays constant instead of growing with attacker-controlled input.

### Proof of Concept
1. Attacker repeatedly posts many low-fee units containing a `data_feed` app-message (each unit valid per `aa_validation.js`'s per-message checks), keeping them unstable for as long as possible (e.g., by posting from many addresses/timing to avoid quick stabilization).
2. `storage.assocUnstableMessages` grows to contain a large number of entries network-wide.
3. Any user sends a payment triggering an AA whose oscript formula contains `data_feed[[oracles=...]]` evaluated with `unstable_opts` set (a supported, ordinary usage pattern), causing `dataFeedExists`/`readDataFeedValue` to be invoked.
4. The `for (var unit in storage.assocUnstableMessages)` loop in `data_feeds.js` (lines 34-43, 211-224) iterates over the full, attacker-inflated set on every node that must validate/execute this trigger, increasing processing time proportional to the attacker-controlled unstable-message count, with no upper bound.
