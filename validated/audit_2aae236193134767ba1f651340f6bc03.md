### Title
Webhook signature verification is scoped by `repository.owner.login` while event handlers act on `repository.full_name`, allowing a webhook sender in one configured GitHub organization to trigger sync jobs against stacks belonging to a different organization - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/webhook secret to validate a delivery against using the organization derived from `repository.owner.login` (or `organization.login`) in the JSON body. [1](#0-0) [2](#0-1)  However, the actual event handlers (`Shipit::Webhooks::Handlers::Handler#repository_name` used by `PushHandler`) select which `Repository`/`Stack` to act on using a *different* field of the same payload: `repository.full_name`. [3](#0-2) [4](#0-3)  Because these two fields are never checked for consistency, a valid signature computed with organization A's webhook secret can carry a `repository.full_name` pointing at a repository owned by organization B, causing Shipit to sync organization B's stack based on attacker-supplied `ref`/`after` values.

### Finding Description
Shipit explicitly supports hosting multiple, independently-owned GitHub organizations in a single instance via the multi-org `github:` config schema, each with its own `app_id`, `private_key`, and `webhook_secret`. [5](#0-4)  `Shipit.github(organization:)` looks up the app/secret for the named organization independently for each org key. [6](#0-5) 

The binding that should hold is:
`organization used to verify the HMAC signature == organization that owns the repository the handler subsequently writes to`

In `verify_signature`, the "authenticating organization" is derived solely from `repository.owner.login`/`organization.login`:
```
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [2](#0-1) 

Once verification passes, `create` dispatches the entire raw JSON body to the registered handler(s), unmodified: `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`. [7](#0-6)  `PushHandler` (and every other `Handler` subclass) then derives the "repository to write to" from a completely separate JSON key, `repository.full_name`:
```
def repository_name
  payload.dig('repository', 'full_name')
end
``` [8](#0-7)  and uses it to look up real `Stack` records and call `stack.sync_github(expected_head_sha: params.after)` for every non-archived stack on the matching branch. [9](#0-8) 

There is nothing that requires `repository.owner.login == repository.full_name.split('/').first`. An attacker who legitimately controls their own GitHub organization "OrgA" (installed as its own tenant on this same Shipit instance, with its own known `webhook_secret`) can:
1. Construct a JSON body: `{"repository": {"owner": {"login": "OrgA"}, "full_name": "OrgB/victim-repo"}, "ref": "refs/heads/master", "after": "<attacker-chosen sha>"}`.
2. Sign it with OrgA's `webhook_secret` (`sha1=HMAC(OrgA_secret, body)`), which the attacker legitimately possesses because they administer OrgA's own GitHub App.
3. POST it to the shared `/webhooks` endpoint.

`verify_signature` resolves `repository_owner` → `"OrgA"`, fetches `Shipit.github(organization: "OrgA")`, and validates the signature against OrgA's secret — which succeeds, since the attacker signed it correctly. [1](#0-0)  The request is never checked against "does this signing organization actually own the repository named in the payload?" `PushHandler` then resolves `Repository.from_github_repo_name("OrgB/victim-repo")` — a repository under a completely different, unrelated organization — and enqueues `stack.sync_github(expected_head_sha:)` using the attacker's forged `ref`/`after` values. [9](#0-8)  This is dispatched via `GithubSyncJob`, which fetches commits from GitHub for the target stack and, if the SHA cannot be found on retry, appends commits and can trigger deploy-spec caching / commit ingestion for that stack. [10](#0-9) 

This mirrors the reported bug class exactly: a value that is checked/authenticated (the signing organization) is not the same value that is subsequently trusted and acted upon (the repository actually written to) — an unchecked binding between two logically-linked fields.

### Impact Explanation
This lets a party who administers one tenant organization on a shared, multi-org Shipit deployment forge webhook events that are cryptographically valid (for their own org) but are processed as if they originated from, and pertain to, a completely different organization's repository. This is a cross-organization/cross-repository write: it can force sync jobs, commit ingestion, and deploy-spec cache refresh for a `Stack` the attacker does not own or have permission over, using attacker-controlled branch/SHA values embedded in the forged payload, without possessing any Shipit user session, `ApiClient` token, or the victim organization's webhook secret. Depending on downstream trust of `sync_github`'s ingested commit data (deploy spec caching, commit-based approval/merge automation), this can influence deploy behavior for a repository the attacker has no legitimate access to — matching the "cross-repository writes" / "unauthorized deploy" impact class.

### Likelihood Explanation
Requires the Shipit instance to be configured for multiple organizations (a documented, supported configuration [5](#0-4) ) and requires the attacker to control (own the GitHub App for) at least one of those organizations — a realistic scenario for any Shipit deployment shared across several teams/orgs, none of which needs to be privileged relative to Shipit itself.

### Recommendation
In `WebhooksController#verify_signature` (or in `Shipit::Webhooks::Handlers::Handler`), enforce that the organization used to select/verify the webhook secret matches the owner embedded in `repository.full_name` (and/or `organization.login` for org-level events) before dispatching to handlers — reject the request (422) on mismatch instead of trusting `full_name` unconditionally.

### Proof of Concept
1. Configure Shipit with two organizations, `OrgA` and `OrgB`, each with distinct `webhook_secret`s (as supported per `docs/setup.md`), and a `Stack`/`Repository` `OrgB/victim-repo` tracked in Shipit.
2. As an attacker who owns `OrgA`'s GitHub App (and thus its `webhook_secret`), craft:
```json
{"repository": {"owner": {"login": "OrgA"}, "full_name": "OrgB/victim-repo"}, "ref": "refs/heads/master", "after": "<attacker-chosen sha>"}
```
3. Compute `sha1=HMAC-SHA1(OrgA_webhook_secret, body)` and set headers `X-Github-Event: push`, `X-Hub-Signature: sha1=<hmac>`.
4. POST to `/webhooks`. `verify_signature` validates successfully against `OrgA`'s secret (`app/controllers/shipit/webhooks_controller.rb:24-30`), then `PushHandler` resolves and syncs `OrgB/victim-repo`'s stack (`app/models/shipit/webhooks/handlers/push_handler.rb:12-17`), which is not owned or signed for by `OrgA`.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

    def perform(params)
      @stack = Stack.find(params[:stack_id])
      expected_head_sha = params[:expected_head_sha]
      retry_count = params[:retry_count] || 0
      head_before_sync = spec_cache_target
      appended_commits = []

      handle_github_errors do
        new_commits, shared_parent = fetch_missing_commits { stack.github_commits }

        # Retry on Github eventual consistency: webhook indicated new commits but we found none
        if expected_head_sha && new_commits.empty? && !commit_exists?(expected_head_sha) &&
           retry_count < MAX_RETRY_ATTEMPTS
          GithubSyncJob.set(wait: RETRY_DELAY * retry_count).perform_later(params.merge(retry_count: retry_count + 1))
          return
        end

        stack.transaction do
          shared_parent&.detach_children!
          appended_commits = new_commits.map do |gh_commit|
            append_commit(gh_commit)
          end
          stack.lock_reverted_commits! if appended_commits.any?(&:revert?)
        end
      end
      sync_changed_nothing = appended_commits.empty? &&
                             spec_cache_target == head_before_sync &&
                             stack.cached_deploy_spec.present?
      return if sync_changed_nothing && !params[:force_spec_cache]

      CacheDeploySpecJob.perform_later(stack)
    end
