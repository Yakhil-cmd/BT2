This confirms the vulnerability path. `Handler#stacks` looks up the repository purely via `payload.dig('repository', 'full_name')` [1](#0-0)  completely independent from the `repository_owner` field used by `WebhooksController#verify_signature` to select which `GitHubApp`/secret validates the signature [2](#0-1) , and `GitHubApp#verify_webhook_signature` bypasses verification entirely when no `webhook_secret` is configured for that organization [3](#0-2) .### Title
Webhook signature verification key is selected from an unauthenticated field, decoupling the authenticated organization from the repository whose stacks are written - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks which `GithubApp` (and therefore which `webhook_secret`) to use for HMAC verification based on `params.dig('repository','owner','login')` (falling back to `params.dig('organization','login')`), a value taken directly from the unauthenticated JSON body itself. The event handlers, however, resolve which `Repository`/`Stack` to act on using a *different* unauthenticated field from the same body: `payload.dig('repository','full_name')`. Nothing binds these two fields together, and nothing binds the field used to pick the verification key to the field used to select the target repository whose state gets mutated.

### Finding Description
`verify_signature` computes:
```ruby
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
``` [4](#0-3) 
with
```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [5](#0-4) 

The chosen `GithubApp`'s secret is then used by `verify_webhook_signature`, which explicitly bypasses verification entirely when no secret is configured for that organization:
```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
``` [3](#0-2) 
`docs/setup.md` explicitly documents `webhook_secret` as *optional* per configured organization, and the sample multi-org secrets fixture shows organizations configured with `webhook_secret: # nil` [6](#0-5) .

Meanwhile, once a payload passes `verify_signature`, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` [7](#0-6)  dispatches to handlers whose base class resolves the target repository from a **different** field of the same untrusted body:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [1](#0-0) 
`Repository.from_github_repo_name` performs a global, unscoped lookup by owner/name parsed out of this field: `find_by(owner: repo_owner, name: repo_name)` [8](#0-7) , with no relation to `repository_owner`/the app whose secret validated the request.

This breaks the deployment-trust binding: **organization authenticated (`repository_owner`, used to select the verifying secret) ≠ repository written (`repository.full_name`, used to select the `Stack`/`Repository` acted upon)**.

Concretely: `PushHandler#process` calls `stack.sync_github(expected_head_sha: params.after)` on every matching, non-archived stack of the resolved repository [9](#0-8) , and `StatusHandler#process` updates commit statuses for any `Commit` matching an attacker-supplied `sha` [10](#0-9)  — both driven entirely by `repository.full_name`/`sha` fields never covered by the signature-selection logic.

### Impact Explanation
If the Shipit deployment is configured with more than one GitHub organization (a documented, supported configuration — see `docs/setup.md` "Using Multiple GitHub Applications" and the `secrets_double_github_app.yml` fixture) and any one of those organizations has no `webhook_secret` set (explicitly documented as optional), an attacker who can reach the `/webhooks` endpoint can:
1. Set `repository.owner.login` (or `organization.login`) to the org with no configured secret, so `verify_signature` selects a `GithubApp` whose `verify_webhook_signature` unconditionally returns `true`.
2. Set `repository.full_name` to an entirely different, victim organization/repository that Shipit also tracks.
3. The `push`/`status`/`check_suite` handler then acts on the victim repository's stacks/commits — e.g., triggering `stack.sync_github`, or writing forged commit statuses — with no cryptographic binding to the victim organization at all.

This constitutes cross-repository writes/state manipulation on stacks belonging to an organization the attacker never authenticated against, matching the "High/Critical: cross-repository writes" impact class.

### Likelihood Explanation
Likelihood depends on the deployment having multiple configured GitHub organizations with at least one lacking a `webhook_secret`. This is not a hypothetical misconfiguration — the project's own setup documentation calls the webhook secret "optional" and the shipped multi-org test fixture demonstrates orgs configured with a `nil` secret, indicating this is a realistic, supported configuration pattern rather than an edge case outside the documented deployment model.

### Recommendation
Bind the field used to select the verification secret to the same field used to resolve the acted-upon repository, and reject the payload if they diverge (i.e., derive both from `repository.full_name` consistently, not two separately-trusted sub-fields). Additionally, require `webhook_secret` to be present for every configured organization (fail closed instead of `return true unless webhook_secret`), and consider re-verifying, inside each handler, that the resolved `Repository#owner` matches the organization whose secret validated the request.

### Proof of Concept
Given a Shipit deployment configured for two GitHub orgs, e.g. as in `test/dummy/config/secrets_double_github_app.yml` [6](#0-5) , where `OrgA` has `webhook_secret: nil` and `OrgB` is a tracked victim organization with real stacks in Shipit:

```
POST /webhooks
X-Github-Event: push
X-Hub-Signature: sha1=0000000000000000000000000000000000000000   # arbitrary, unverified

{
  "ref": "refs/heads/main",
  "after": "<attacker-controlled sha>",
  "repository": {
    "owner": { "login": "OrgA" },        // selects OrgA's GithubApp -> no webhook_secret -> verify_webhook_signature returns true
    "full_name": "OrgB/victim-repo"       // resolves Repository/Stack actually acted upon
  }
}
```
`verify_signature` passes because `Shipit.github(organization: "OrgA").verify_webhook_signature` short-circuits to `true` [11](#0-10) . `PushHandler` then resolves `Repository.from_github_repo_name("OrgB/victim-repo")` via `payload.dig('repository','full_name')` [1](#0-0)  and calls `sync_github(expected_head_sha: ...)` on OrgB's stacks, with no signature ever validated against OrgB's actual webhook secret.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
