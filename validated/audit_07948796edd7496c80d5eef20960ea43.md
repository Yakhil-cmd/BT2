### Title
`StatusHandler#process` matches `Commit.where(sha:)` globally across all stacks/repositories, letting one verified webhook mutate unrelated tenants' commits - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` runs `Commit.where(sha: params.sha)` with no `stack_id`/repository scope, unlike the sibling `CheckSuiteHandler`, which explicitly scopes through `stacks.where(branch: ...)` derived from the webhook's own `repository.full_name`. Any commit row anywhere in the database sharing that sha gets `create_status_from_github!` called on it, regardless of which repository/org's webhook secret was used to verify the request.

### Finding Description
Binding claimed: for a single verified webhook, `Stack rows touched == stacks owned by the org whose webhook_secret verified the request` (expected 1 org's stacks). Actual binding in code: [1](#0-0) 
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```

This query is unfiltered by `repository_name`/`stack_id`, so it matches every `Commit` row in the whole install sharing that sha, across every stack/repository/org — not just the org that owns the repo named in `payload['repository']['full_name']`.

Contrast with `CheckSuiteHandler`, which correctly scopes via the base `Handler#stacks` helper: [2](#0-1) [3](#0-2) 

`verify_signature` only proves the request was signed with `webhook_secret` for `repository_owner` from the payload — it says nothing about which commits the payload is authorized to touch: [4](#0-3) 

Attacker path: per the threat model, the attacker legitimately owns a GitHub repository connected to Shipit and can "emit webhooks from a repository they own." GitHub will genuinely sign and deliver a `status` event for that repository. `params.sha` in that payload is the commit sha field from the request body. Because git commit hashes are deterministic content hashes (tree, parent, author/committer, timestamps, message), an attacker who can predict or reproduce those exact fields (e.g., copying an identical initial/vendored/license commit, or any commit whose full metadata is knowable/replayable) can create a commit in their own repo that has the *same sha* as a commit already recorded in a victim's unrelated `Stack`. When their own CI/GitHub then posts a `status` webhook for that sha (correctly signed with *their own org's* webhook_secret), `StatusHandler#process` will match and mutate the `Commit` row in the victim stack, calling `commit.create_status_from_github!(params)` on it — this can flip CI state (e.g. to `success`), trigger `ProcessMergeRequestsJob`, and influence deployability/merge behavior for a stack the attacker never authenticated against.

No existing guard prevents this: `verify_signature` checks org-level HMAC only, `drop_unhandled_event`/`check_if_ping` are unrelated, `ExplicitParameters` only validates the shape of `sha`/`state`/etc, not ownership, and there is no `stacks`/`repository_name` scoping applied in `StatusHandler#process` itself.

### Impact Explanation
A payload legitimately signed for org/repo A can flip CI status on `Commit` rows belonging to any other stack/org B, C, … whose stored commit sha happens to match. This can mark a victim's commit as `success`, enabling deploy/merge decisions (`ProcessMergeRequestsJob` is enqueued on relevant state transitions, per `test/models/commits_test.rb:763-777`), i.e. "a payload for one repository mutating another's stack, commit ... or an unauthorized deploy, rollback or merge" — matching the Critical impact category. It is repeatable for every matching sha and scales with however many stacks/commits happen to contain that sha.

### Likelihood Explanation
Preconditions: attacker needs (a) their own GitHub repo already connected/onboarded to Shipit (allowed per the threat model — they can "emit webhooks from a repository they own"), and (b) a commit whose sha collides with a targeted commit in a victim stack. True SHA-1 preimage crafting against an *arbitrary chosen* victim sha is not shown to be feasible here — this report does not demonstrate a concrete method to reliably produce a colliding sha against a specific victim commit (that would require either a genuine hash collision, or a real content match, such as duplicating a byte-identical commit, e.g. shared vendored files/forks/mirrors, which is plausible but not universal). This limits practical likelihood versus the strict "arbitrary victim, arbitrary sha" framing in the question, but the underlying query is unambiguously unscoped and the described PoC pattern (seeding 3 stacks with a shared, attacker-known sha and firing one webhook) is directly reproducible in tests without needing to break SHA-1.

### Recommendation
Scope `StatusHandler#process` to only the commits belonging to stacks tied to the webhook's own `repository.full_name`, mirroring `CheckSuiteHandler`'s use of the `stacks` helper, e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` or `Commit.where(sha: params.sha, stack_id: stacks.select(:id))`, rather than a bare `Commit.where(sha: ...)`.

### Proof of Concept
Minitest plan under `test/controllers/webhooks_controller_test.rb` (or `test/models/shipit/webhooks/handlers/status_handler_test.rb`):
1. Create 3 `Stack`s belonging to 3 different `Repository`/org fixtures (`repo-a`, `repo-b`, `repo-c`).
2. Create a `Commit` with the identical sha `SHARED_SHA` under each of the 3 stacks (`commit_a`, `commit_b`, `commit_c`).
3. Build a valid `status` webhook payload for `repo-a` only, with `sha: SHARED_SHA`, signed with `repo-a`'s configured `webhook_secret`.
4. POST it to `/webhooks`.
5. Assert `commit_a.reload.statuses.count`, `commit_b.reload.statuses.count`, and `commit_c.reload.statuses.count` — binding equality expected: only `commit_a`'s statuses should change (`== 1` stack touched); actual: all three change (`== 3`), demonstrating the cross-tenant mutation.
