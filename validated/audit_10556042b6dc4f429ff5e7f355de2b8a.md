The premise of this question is false: the reward-distribution partition count is explicitly bounded and does not scale unboundedly with the number of attacker-created stake accounts.

`Bank::get_reward_distribution_num_blocks` computes `num_chunks` from the total stake-reward count divided by `partitioned_rewards_stake_account_stores_per_block()`, but then clamps the result to `(epoch_schedule.slots_per_epoch / MAX_FACTOR_OF_REWARD_BLOCKS_IN_EPOCH).max(1)`, i.e., at most 10% of the epoch's slots, regardless of how large the stake-reward count is. [1](#0-0) 

This value becomes `num_partitions`, which is stored in the `EpochRewards` sysvar via `create_epoch_rewards_sysvar` in `begin_partitioned_rewards`, and is what ultimately surfaces as `num_reward_partitions` in block metadata. [2](#0-1) 

The existing unit test `test_get_reward_distribution_num_blocks_cap` directly demonstrates this bound: increasing `num_stakes` well beyond the per-block capacity (4x, 5x the per-block store count) still caps the result at 3 blocks (10% of a 32-slot epoch), never growing further. [3](#0-2) 

Additionally, `distribute_partitioned_epoch_rewards` asserts `epoch_schedule.get_slots_in_epoch(self.epoch) > partition_rewards.partition_indices.len()`, which would panic (not silently corrupt state) if partition count ever exceeded the epoch's slot count — a further defense-in-depth check, though the clamp already prevents this from being reachable via attacker-controlled stake account count. [4](#0-3) 

Since `num_reward_partitions`/`num_partitions` reported in `UiConfirmedBlock`/`EncodedConfirmedBlock` (transaction-status-client-types) is sourced directly from this bounded sysvar value (via `get_rewards_and_num_partitions`), it cannot diverge from — or exceed — the protocol-enforced bound regardless of how many minimum-delegation stake accounts an attacker creates. There is no unbounded "actual partition count enforced by the scheduler" versus a differently-computed reported value; both derive from the same clamped calculation. [5](#0-4)

    pub(super) fn get_reward_distribution_num_blocks(
        &self,
        rewards: &PartitionedStakeRewards,
    ) -> u64 {
        let total_stake_accounts = rewards.num_rewards();
        if self.epoch_schedule.warmup && self.epoch < self.first_normal_epoch() {
            1
        } else {
            const MAX_FACTOR_OF_REWARD_BLOCKS_IN_EPOCH: u64 = 10;

                1,

        }
