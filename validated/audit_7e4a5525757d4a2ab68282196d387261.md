### Title
SSRF via attacker-controlled ArbStore URL in arbiter contract handling - (File: arbiters.js, arbiter_contract.js)

### Summary
When a paired device sends an `arbiter_contract_offer` message naming itself (or a colluding address) as `arbiter_address`, the receiving wallet only validates that the address is well-formed, not that it belongs to a trustworthy, publicly reachable arbitration service. Later wallet-driven flows (`arbiters.getInfo`/`getArbstoreInfo`, `arbiter_contract.getArbstoreAddresses`, `appeal`, `getAppealFee`) resolve a URL for that `arbiter_address` via the hub and then issue outbound `http.get`/`https.get`/`http.request` calls to that URL with no validation of scheme, host, or destination (no protection against `localhost`, link-local, or private-network addresses). This mirrors the txtdot `/proxy` SSRF class: the server (here, the victim's ocore node) is induced to make arbitrary HTTP requests to attacker-influenced targets, in this case also carrying private contract data (title, text, parties, amount) in the POST body.

### Finding Description
The `arbiter_contract_offer` handler in `wallet.js` only checks address format for `arbiter_address`: [5](#0-4) 
It never verifies that the address is a known, legitimate arbiter or restricts the location that will eventually be contacted on the victim's behalf.

Once a contract referencing that `arbiter_address` exists, wallet code resolves and fetches from an ArbStore URL tied to the arbiter:
- `arbiters.requestInfoFromArbStore` performs a raw `http.get(url, ...)` with only a "non-empty string" check on `url`: [6](#0-5) 
- `arbiter_contract.getArbstoreAddresses`/`appeal`/`getAppealFee` call `httpRequest(url, ...)`, which parses the URL and issues an `http.request` POST carrying the full contract payload (title, text, addresses, amount, asset) with no allow-listing of destination host/scheme: [2](#0-1) [3](#0-2) 

Because `arbiter_address` is fully attacker-chosen in the offer sent by a paired device, and the URL bound to it is fetched with no destination restriction, an attacker acting as arbiter (or colluding with the registered arbiter) can steer the victim node's outbound HTTP requests to arbitrary hosts, including internal-network or loopback addresses reachable only from the victim's node. This is functionally the same bug class as the reported txtdot `/proxy` SSRF: user-influenced target + unrestrained outbound fetch by the server/node.

### Impact Explanation
- The victim node performs GET/POST requests to attacker-influenced targets, enabling internal network reconnaissance/pivoting from wherever the ocore node runs (SSRF).
- Sensitive contract details (parties' addresses, amount, asset, title, text, pairing codes in the appeal flow) are POSTed to the attacker-controlled or attacker-redirected endpoint, causing confidentiality loss for the private contract negotiation.
- If the node runs alongside other local services (common in wallet/hub deployment topologies), this can be leveraged to probe or interact with those services using the node's network position.

### Likelihood Explanation
Likelihood is high for an unprivileged, paired counterparty: creating an arbiter contract offer and naming an arbitrary `arbiter_address`/associated URL requires no special privilege beyond normal device pairing and contract flows already supported in the wallet UI, and no additional validation of the destination is performed before the outbound request is made.

### Recommendation
Validate and restrict outbound ArbStore URLs before use in `arbiters.js`/`arbiter_contract.js`:
- Enforce `https://` scheme only.
- Resolve and reject destinations that resolve to private/loopback/link-local IP ranges (RFC1918, 127.0.0.0/8, 169.254.0.0/16, ::1, fc00::/7, etc.), similar to standard SSRF mitigations.
- Consider requiring ArbStore URLs to be pinned/allow-listed rather than resolved ad hoc per arbiter address, and avoid sending full private contract content until the endpoint's identity has been confirmed.

### Proof of Concept
1. Attacker device pairs with victim and sends an `arbiter_contract_offer` naming `arbiter_address` as an address the attacker controls (or colludes with) on the hub, where the corresponding `hub/get_arbstore_url` resolves to `http://127.0.0.1:PORT/...` or an internal-network host.
2. Victim's wallet accepts/processes the contract; later flows (`arbiters.getInfo`, `getArbstoreInfo`, or dispute `appeal`/`getAppealFee`) call `device.requestFromHub("hub/get_arbstore_url", arbiter_address, ...)` then `requestInfoFromArbStore`/`httpRequest` in `arbiters.js`/`arbiter_contract.js`.
3. The victim node issues an HTTP GET/POST to the attacker-supplied internal URL, including private contract fields in the POST body for the appeal/dispute path, demonstrating SSRF plus data exfiltration to an attacker-influenced destination.

function requestInfoFromArbStore(url, cb){
	http.get(url, function(resp){
		var data = '';
		resp.on('data', function(chunk){
			data += chunk;
		});
		resp.on('end', function(){
			try {
				cb(null, JSON.parse(data));
			} catch(ex) {
				cb(ex);
			}
		});
	}).on("error", cb);
}

					contract_hash: hash,
					my_pairing_code: objContract.my_pairing_code,
					my_address: objContract.my_address,

function httpRequest(host, path, data, cb) {
	var reqParams = Object.assign(url.parse(host),
		{
			path: path,
			method: "POST",
			headers: {
				"Content-Type": "application/json",
				"Content-Length": (new TextEncoder().encode(data)).length
			}
		}
	);
	var req = http.request(
		reqParams,
		function(resp){
			var data = "";
			resp.on("data", function(chunk){
				data += chunk;
			});
			resp.on("end", function(){
				try {
					data = JSON.parse(data);
					if (data.error) {
						return cb(data.error);
					}
					cb(null, data);
				} catch (e) {
					cb(e);
				}
			});
		}).on("error", cb);
	req.write(data);
	req.end();
}
