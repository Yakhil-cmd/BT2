### Title
`is_valid_signed_package()` / signed-message hashing lacks domain separation, enabling replay of off-chain signatures across AAs and contexts - (File: `formula/evaluation.js`, `signed_message.js`, `object_hash.js`)

### Summary
Ocore's oscript primitive `is_valid_signed_package()` (and the underlying `signed_message.validateSignedMessage()`/`objectHash.getSignedPackageHashToSign()`) verifies an off-chain ECDSA signature over a `signed_message` object, but the hash that is actually signed does not bind the identity of the verifying Autonomous Agent (the "recipient" of the signed package), any purpose/domain tag, or a nonce. This mirrors the reported `CrosschainMerkleDistributor.claimBySignature()` flaw: the signed payload is under-specified, so the same signature can be valid input to more than one verification context.

### Finding Description
`is_valid_signed_package(signed_package_expr, address_expr)` in `formula/evaluation.js` only checks that the object was signed by `address_expr` (the counterparty's address) and, if present, that `last_ball_unit` is stable: [1](#0-0) 

The actual hash that gets signed/verified is produced by `signed_message.validateSignedMessage()`, which computes:
```
unit_hash_to_sign: objectHash.getSignedPackageHashToSign(objSignedMessage)
``` [2](#0-1) 

and the set of top-level fields the signer/verifier controls is restricted to `signed_message`, `authors`, `last_ball_unit`, `timestamp`, `version`: [3](#0-2) 

Nowhere in this pipeline is the identity of the AA/contract consuming the signed package (i.e., `this_address` of the AA calling `is_valid_signed_package`), an application/purpose tag, or a nonce mixed into the signed hash. The only content-level protection against replay is whatever fields the AA author manually puts inside `signed_message` itself and manually checks in oscript.

This is demonstrated by the repository's own sample AA, `test/samples/payment_channels.oscript`, which — because the primitive doesn't provide binding — the author is forced to manually embed and check a `channel` field equal to `this_address` to prevent a signature meant for one channel/contract instance from being replayed against another: [4](#0-3) 

If any AA author (or a wallet library composing signed packages via `composer.js`/`getUnitHashToSign`/`getSignedPackageHashToSign`) omits this manual binding — exactly as `CrosschainMerkleDistributor` omitted binding the consuming contract address into `_signed` — a beneficiary's signature can be replayed:
- across two different AAs that both expect signed packages from the same signer address with the same `signed_message` shape (e.g. two independently deployed instances of a template AA, or a "claim"/"vesting"-style AA deployed twice), or
- across two different code branches/purposes within the same AA that reuse the same signer/message shape (e.g. an approval message intended for one action reused to authorize a different action).

Because oscript AAs are user-deployable and their bytecode/definition is fully attacker/author controlled, an "AA author" role can build (intentionally or by oversight) a signature scheme that is unsafe under replay, and any trigger sender in possession of a previously-published signed package (signed packages are typically embedded in trigger data, which is publicly visible on the DAG) can resubmit it to a second AA/context.

### Impact Explanation
Where an AA design uses `is_valid_signed_package`/`is_valid_sig` as an authorization gate for fund movement (payment channel closes, claims, off-chain approvals, order fills), missing domain separation lets an attacker replay a legitimately obtained signature into an unintended AA instance or unintended state, causing unauthorized fund release/double-spend of AA-held funds. This matches "AA fund loss" impact criteria: it is not a defect in the reported library's business logic (the sample already defends against it), but the primitive itself provides no默认 protection, so any AA that doesn't add its own domain tag is exploitable in the same way as `CrosschainMerkleDistributor`.

### Likelihood Explanation
Medium. Exploitation requires: (1) an AA design that verifies signed packages from the same signer address in more than one context/instance without embedding a unique identifier bound to that context, and (2) the attacker obtaining a previously published signed package (readily available since triggers/messages are public on the DAG). This is a realistic and recurring pattern for template AAs deployed multiple times (payment channels, order books, vesting/claim AAs) by non-security-expert authors, analogous to how the original Solidity report found two sibling contracts (`CrosschainContinuousVestingMerkle` / `CrosschainTrancheVestingMerkle`) sharing an insufficiently-scoped signature scheme.

### Recommendation
- Document and, where feasible, enforce that `getSignedPackageHashToSign` / the `signed_message` schema include a mandatory domain-separation field bound to the consuming AA's `this_address` (or an explicit `purpose`/`aa` tag and nonce), similar to EIP-712 domain separators.
- Update `is_valid_signed_package()` (and its formula validator in `formula/validation.js`) to optionally require and check a `contract`/`aa` field in `signed_message` equal to `this_address`, so AA authors get this protection without having to remember to add it manually as in `payment_channels.oscript`.
- Audit template/sample AAs (`payment_channels.oscript`, `order_book_exchange.oscript`) and any produced from them to confirm they always bind `this_address` (or an equivalent unique identifier) plus a nonce/period into the signed message before trusting `is_valid_signed_package`.

### Proof of Concept
1. Deploy two instances of a template AA (e.g., two independent payment-channel AAs, `AA1` and `AA2`) that both use `is_valid_signed_package(trigger.data.sentByPeer, $peerAddress)` to authorize a state transition, but — unlike the shipped sample — do **not** check `signed_message.channel == this_address`.
2. Peer B signs a `signed_message` such as `{ period: 1, amount_spent: 100 }` for use with `AA1`.
3. Because `getSignedPackageHashToSign` only hashes `signed_message`/`authors`/`last_ball_unit`/`version` (`signed_message.js` lines 130-137, 264-272) and not `AA1`'s address, the exact same signed package validates successfully when submitted as a trigger to `AA2` (`formula/evaluation.js` lines 1666-1699), letting the counterparty replay the authorization and drain funds from `AA2` that were never intended to be spent under that signature.
