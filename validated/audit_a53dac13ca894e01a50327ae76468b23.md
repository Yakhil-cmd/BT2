### Title
Webhook Signature Verified Against `repository.owner.login`/`organization.login` While the Repository Actually Mutated Is Selected From The Unverified `repository.full_name` Field - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/handler.rb`)

### Summary
`WebhooksController#verify_signature` selects which `GithubApp`/`webhook_secret` to use for HMAC verification based on `repository_owner` (`params.dig('repository','owner','login')` or `params.dig('organization','login')`), while every `Handler` subclass resolves the `Stack`/`Repository` to actually mutate from a different field, `payload.dig('repository','full_name')`. Because Shipit supports multiple GitHub organizations each with its own, independently-configured (and explicitly documented as *optional*) `webhook_secret`, an attacker can pick which secret protects the request while the object actually written to is controlled by a separate field in the same JSON body.

### Finding Description
`verify_signature` in [1](#0-0)  looks up the `GithubApp` via `Shipit.github(organization: repository_owner)`, and `repository_owner` reads `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` [2](#0-1) . `Shipit.github` resolves per-organization config via `github_app_config(organization)`, and each organization entry in `secrets.github` carries its own, independently settable `webhook_secret` [3](#0-2) . The setup docs explicitly mark the webhook secret as *optional* per GitHub App: "Webhook secret (optional): Fill it with some randomly generated string..." [4](#0-3) , and `verify_webhook_signature` short-circuits to `true` whenever that organization's `webhook_secret` is blank: `return true unless webhook_secret` [5](#0-4) .

Once the signature check passes, `Handler#stacks`/`Handler#repository_name` never consult `repository_owner` again — they resolve the target repository purely from `payload.dig('repository', 'full_name')`: `Repository.from_github_repo_name(repository_name)&.stacks` [6](#0-5) . `PushHandler#process` then walks every matching, non-archived stack and calls `stack.sync_github(expected_head_sha: params.after)` [7](#0-6) .

This is the same class of bug as the AMM `initialize()` finding: the trust check binds to one identity (`_governance`/`repository_owner`) while a *different* piece of state (`syncDeps`'s registry-derived values/`repository.full_name`) is what actually gets acted upon, with nothing enforcing that the two agree. Concretely, the equality that should hold but doesn't is:

`organization used to select/verify the webhook secret (repository.owner.login) == owner of the repository actually mutated (repository.full_name's owner segment)`

Before the attacker's request: for legitimate GitHub-originated webhooks these two always match because GitHub itself fills both fields from the same event. After the attacker's crafted request: `repository.owner.login` (or `organization.login`) is set to any organization configured in Shipit that has **no `webhook_secret` set** (a state the docs themselves invite by calling the secret "optional"), so `verify_webhook_signature` returns `true` unconditionally without any secret at all — while `repository.full_name` is set to `victim-org/victim-repo`, a fully configured, secret-protected repository with real stacks. `check_if_ping`/`drop_unhandled_event` do not re-validate this relationship, and no code anywhere compares `repository_owner` to the owner segment of `repository_name`.

### Impact Explanation
An unauthenticated attacker (no Shipit session, no `ApiClient` token, no GitHub App private key, no knowledge of any `webhook_secret`) can forge `push`, `status`, `check_suite`, `membership`, or `pull_request` events for any repository configured in Shipit as long as any other organization in the same Shipit instance lacks a `webhook_secret`. Via `push`, this drives `Stack#sync_github`, which is what ultimately triggers `GithubSyncJob` and can lead to deploys being triggered against forged head SHAs for stacks the attacker does not control — an unauthorized deploy/rollback path, matching the "unauthorized deploy" Critical impact category. `membership` events can also create/delete `Team`/`Membership`/`User` records tied to `Shipit.github_teams` authorization, escalating into the High-severity "escalation into `Shipit.github_teams` authorization" category, since Team/Membership handlers likewise trust `payload` fields without cross-checking against the organization the signature was actually verified against.

### Likelihood Explanation
Requires only that the Shipit deployment be configured with multiple GitHub organizations (a documented, supported configuration via `secrets.github` per-org keys) and that at least one configured organization omit its "optional" `webhook_secret` — a realistic operational mistake explicitly permitted by the setup documentation. Given that precondition, exploitation requires nothing beyond sending a single unauthenticated HTTP POST to `/webhooks` with crafted JSON; no credentials, tokens, or cryptographic breaks are needed.

### Recommendation
Do not let `repository_owner` (used to pick the verification secret) diverge from the object the handler subsequently mutates. Either: (1) require every configured organization to have a non-blank `webhook_secret` (removing the `return true unless webhook_secret` bypass in `GithubApp#verify_webhook_signature`), and/or (2) after signature verification, assert that the resolved `repository_owner` matches the owner segment of `payload.dig('repository','full_name')` (and of `Repository#full_name` for the stack ultimately resolved) before any handler is invoked, rejecting the request otherwise.

### Proof of Concept
1. Shipit instance is configured with two GitHub orgs in `secrets.github`: `victim-org` (has stacks, `webhook_secret: "s3cr3t"`) and `scratch-org` (installed for testing, `webhook_secret` left unset — allowed by docs).
2. Attacker sends `POST /webhooks` with header `X-Github-Event: push` and body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>",
  "organization": { "login": "scratch-org" },
  "repository": { "owner": { "login": "scratch-org" }, "full_name": "victim-org/victim-repo" }
}
```
No `X-Hub-Signature` header (or any arbitrary value) is required.
3. `verify_signature` computes `repository_owner == "scratch-org"`, loads `Shipit.github(organization: "scratch-org")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` unconditionally [8](#0-7) .
4. `PushHandler` resolves stacks via `repository_name = payload.dig('repository','full_name')` = `"victim-org/victim-repo"` [9](#0-8)  and calls `stack.sync_github(expected_head_sha: ...)` for every matching branch/stack under `victim-org/victim-repo` [7](#0-6) , with zero authentication tying the attacker to `victim-org`.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
