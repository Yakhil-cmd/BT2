## Confirmed vulnerability

### Title
Webhook signature verification uses `repository.owner.login` while every handler resolves the target repository from the unauthenticated `repository.full_name` field, allowing signature-secret confusion across organizations - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App's `webhook_secret` to validate the HMAC signature against using `repository_owner`, derived from `params.dig('repository', 'owner', 'login')`. But the actual work performed by every webhook handler (`PushHandler`, `StatusHandler`, `CheckSuiteHandler`, `PullRequest::*Handler`) resolves the target `Repository`/`Stack` from a *different* field of the same attacker-controlled JSON body: `payload.dig('repository', 'full_name')` in `Handler#repository_name`. These two fields are never cross-checked against each other, so the field that gated signature verification is not the field that determines what gets written.

### Finding Description
`verify_signature` in `app/controllers/shipit/webhooks_controller.rb` computes: [1](#0-0) [2](#0-1) 

using `repository_owner = params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` to pick which per-organization `GitHubApp`/`webhook_secret` (`Shipit.github(organization: repository_owner)`) validates `X-Hub-Signature`.

Meanwhile, every event handler (base class `Handler#stacks`/`repository_name`) determines the `Repository`/`Stack` to act on using a completely separate field of the same payload: [3](#0-2) 

Shipit explicitly supports multiple GitHub organizations, each with its own independently configured `webhook_secret` (which, per `docs/setup.md` and the test fixture `secrets_double_github_app.yml`, is optional/nilable per org): [4](#0-3) [5](#0-4) 

And `GitHubApp#verify_webhook_signature` explicitly treats a blank secret as "always verified": [6](#0-5) 

Given this, an attacker who can trigger a delivery attributable to (or crafted for) an organization `OrgA` whose GitHub App is configured with **no** `webhook_secret` (`return true unless webhook_secret`), or who otherwise knows `OrgA`'s secret, can send a POST to `/webhooks` where:
- `repository.owner.login = "OrgA"` (or `organization.login = "OrgA"`) — satisfies `verify_signature`, which resolves and validates against `OrgA`'s (blank/known) secret.
- `repository.full_name = "OrgB/victim-repo"` — the field actually consumed by `Handler#repository_name` to look up the `Repository`/`Stack` that gets acted upon.

Because the field bound by the signature check (`repository.owner.login`) is never the same field consumed by the handler logic (`repository.full_name`), the "organization authenticated" and "repository written" bindings diverge, breaking the required equality: **organization the signature authenticated == repository the handler mutates**.

### Impact Explanation
This lets an unprivileged external attacker forge webhook events (`push`, `status`, `check_suite`, `pull_request`, `membership`) that are processed as if they legitimately originated from `OrgB`, while only having to satisfy `OrgA`'s (potentially blank) signing secret. Concretely:
- `PushHandler` enqueues `GithubSyncJob` for `OrgB`'s stacks based on attacker-supplied `after` (target SHA), which can trigger deploy-relevant state changes / spurious syncs for repositories the attacker has no access to.
- `StatusHandler` writes fabricated commit statuses (`create_status_from_github!`) onto `OrgB` commits, which can be leveraged to unblock/allow deploys that rely on required statuses (`deployable_status`), i.e., contributes to an **unauthorized deploy**.
- `MembershipHandler`/`Team` webhooks can create/modify `Team`/`Membership` records tied to an org whose name the attacker fully controls in the payload, independent of the org whose secret authenticated the request.

This crosses the "unauthorized deploy" / "cross-repository writes" impact bar defined in scope, since the org used to authenticate the request is not cryptographically bound to the repository whose state is mutated.

### Likelihood Explanation
Likelihood is high specifically in the documented and tested multi-organization configuration (`docs/setup.md` "Using Multiple Github Applications", and `test/dummy/config/secrets_double_github_app.yml`/`secrets.development.shopify.yml` show `webhook_secret` as commonly left blank per org). Any Shipit deployment managing more than one GitHub organization, where at least one org's App is configured without a webhook secret (a supported and exampled configuration) or whose secret the attacker can obtain independently (e.g. a public/open-source org they also administer), is exploitable without any credential, session, or repository-write access to the victim org — only network access to the public `/webhooks` endpoint.

### Recommendation
Bind the field used to select/validate the signing secret to the same field used to resolve the target repository. Concretely, `Handler#repository_name` (and any other handler resolving repositories/orgs from the payload) should re-derive the organization from `repository.full_name` (or explicitly re-validate that `repository.owner.login`/`organization.login` matches the owner segment of `repository.full_name`) before trusting it, and `WebhooksController` should reject payloads where these fields disagree. More robustly, verify the signature using the specific `GithubHook`/App config associated with the resolved `Repository` record (looked up from `full_name`) rather than trusting an unauthenticated field to pick the verification key in the first place.

### Proof of Concept
1. Configure Shipit with two orgs: `OrgA` (webhook_secret left blank, per the documented/supported multi-org config) and `OrgB` (real secret, real stacks Shipit manages).
2. POST to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "ref": "refs/heads/master",
  "after": "deadbeef",
  "repository": {
    "owner": { "login": "OrgA" },
    "full_name": "OrgB/victim-repo"
  }
}
```
No `X-Hub-Signature` header is required to pass, or any arbitrary value works, because `verify_signature` resolves `Shipit.github(organization: "OrgA")` whose `verify_webhook_signature` short-circuits to `true` (`return true unless webhook_secret`) per [7](#0-6) .
3. `WebhooksController#create` dispatches to `PushHandler`, whose `Handler#repository_name` reads `full_name` = `"OrgB/victim-repo"` [8](#0-7) , resolving `OrgB`'s real `Stack` and enqueuing `stack.sync_github(expected_head_sha: "deadbeef")` — a state-changing action on `OrgB`'s stack triggered by a request that was only ever validated against `OrgA`'s credentials.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
