### Title
Permissionless "emergency" OP-list vote recount can be triggered from non-final, node-local mempool state, causing witness-list divergence between nodes - ([File: main_chain.js])

### Summary
Similar to `consolidatePendingState()` in the PolygonZkEVM report, ocore has an "emergency" recovery path — the emergency `op_list` vote recount — that is reachable and triggerable by any ordinary unit poster, without the safeguards that would be expected for a mechanism meant to run only in an exceptional, carefully-bounded situation. Instead of relying purely on finalized/stable data, the emergency computation reads from each node's local, still-unstable mempool state, which is not guaranteed to be identical across nodes.

### Finding Description
Any unit can carry a `system_vote_count` message for subject `op_list`. Whenever such a unit is written with `sequence === 'good'`, `writer.js` unconditionally schedules `main_chain.applyEmergencyOpListChange()`: [1](#0-0) 

`applyEmergencyOpListChange()` only checks a timestamp-based staleness condition (time since last stable unit) before invoking `countVotes(..., is_emergency=1, ...)`: [2](#0-1) 

Inside `countVotes`, when `is_emergency` is set, the vote tally is augmented with **unstable** (not-yet-final) votes pulled from `storage.assocUnstableMessages` / `storage.assocUnstableUnits` via `getUnstableVotes()`: [3](#0-2) [4](#0-3) 

The result is written with `REPLACE INTO system_vars ... is_emergency=1`, directly overriding the current `op_list`/witness list value used by the network: [5](#0-4) 

Because `assocUnstableUnits`/`assocUnstableMessages` reflect each node's own local view of unconfirmed units (which can differ node-to-node depending on arrival order, propagation delay, and provisional `sequence`/`level` values that are not yet final), two honest nodes can compute different sets of `unstable_votes` at the moment the emergency trigger unit is processed, and thus derive different `op_list` values for the very same `vote_count_mci`. This mirrors the report's core problem: a recovery/cleanup-style operation (`consolidatePendingState`/emergency vote count) that any unprivileged actor can trigger, running without adequate consistency guarantees, while a supposedly "emergency-only" state is in effect.

### Impact Explanation
Since `op_list` determines the effective witness set used for main-chain stability and unit validation, nodes disagreeing on the emergency-computed `op_list` can diverge on which units/balls are valid or stable, i.e., a consensus split ("node disagreement on validity or stability" per the impact rubric). This can also let an attacker deliberately race the trigger while the mempool state differs between nodes (e.g., unstable votes at the boundary of `EMERGENCY_COUNT_MIN_VOTE_AGE`) to try to push different witness lists onto different parts of the network.

### Likelihood Explanation
Triggering the message costs only posting a normal unit containing a `system_vote_count` message with payload `op_list` — reachable by any unprivileged unit poster once the staleness/timeout condition (`EMERGENCY_OP_LIST_CHANGE_TIMEOUT`) is met, i.e., whenever the chain has been stalled long enough for the emergency path to be legitimately usable. The non-determinism itself requires the network to already be near the edge of the emergency-eligible window (chain stalled), which is exactly the adverse condition the mechanism is meant to safely resolve, making the scenario plausible rather than purely theoretical.

### Recommendation
Base the emergency vote recount exclusively on finalized/stable data (or deterministically-ordered, unit-hash-anchored data available identically to all nodes), rather than each node's locally-observed `assocUnstableUnits`/`assocUnstableMessages`. If unstable votes must be included, gate their inclusion by fields that are guaranteed identical pre-finality across all honest nodes (e.g., derived strictly from parent-included units that are already common ancestors), and add an explicit consistency check (e.g., requiring the applying node to confirm the computed `op_list` against a quorum-signed statement) before performing the `REPLACE INTO system_vars` that overrides the active witness list.

### Proof of Concept
1. Let the main chain stall past `EMERGENCY_OP_LIST_CHANGE_TIMEOUT` (main_chain.js:1939).
2. Two nodes, A and B, have received a slightly different set of unstable `system_vote` units for `op_list` (e.g., B received one extra vote that hasn't propagated to A yet, or the vote is exactly at the `EMERGENCY_COUNT_MIN_VOTE_AGE` boundary so it's included on one node and excluded on the other, main_chain.js:1915-1933).
3. An unprivileged user posts a unit containing a `system_vote_count` message for `op_list`.
4. Both A and B independently call `applyEmergencyOpListChange` → `countVotes(..., is_emergency=1, ...)`; because their `getUnstableVotes()` results differ, they compute different `ops` arrays and each `REPLACE`s its own `system_vars.op_list` for the same `vote_count_mci` (main_chain.js:1860-1870, 1908-1912).
5. A and B now use different witness lists, leading to divergent validation/stability decisions for subsequent units.

function getUnstableVotes(emergency_count_command_timestamp) {
	let votes = [];
	for (let unit in storage.assocUnstableMessages) {
		for (let m of storage.assocUnstableMessages[unit]) {
			if (m.app === 'system_vote' && m.payload.subject === 'op_list') {
				const { timestamp, author_addresses, sequence, level } = storage.assocUnstableUnits[unit];
				if (sequence !== 'good')
					continue;
				if (emergency_count_command_timestamp - timestamp < constants.EMERGENCY_COUNT_MIN_VOTE_AGE) {
					console.log('unstable vote from', author_addresses, 'is too young');
					continue;
				}
				const arrOPs = m.payload.value;
				votes.push({ timestamp, level, author_addresses, arrOPs });
			}
		}
	}
	return votes;
}

async function applyEmergencyOpListChange(conn, emergency_count_command_timestamp, cb) {
	// last stable unit
	const [{ timestamp, main_chain_index }] = await conn.query("SELECT timestamp, main_chain_index FROM units WHERE is_stable=1 AND is_on_main_chain=1 ORDER BY main_chain_index DESC LIMIT 1");
	if (emergency_count_command_timestamp < timestamp + constants.EMERGENCY_OP_LIST_CHANGE_TIMEOUT) {
		console.log(`too early to apply emergency OP list change yet`);
		return cb();
	}
	console.log(`applying emergency vote count after being stuck at mci ${main_chain_index}`);
	await countVotes(conn, main_chain_index - 1, 'op_list', 1, emergency_count_command_timestamp);
	cb();
}
