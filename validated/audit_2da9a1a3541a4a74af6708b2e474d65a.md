### Title
Webhook signature verification is keyed by an attacker-controlled `repository.owner.login` field that is independent of the `repository.full_name` used to route the event, letting a request "verified" against one (secret-less) GitHub organization write a forged `Status` to a commit belonging to any other repository - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects which GitHub App's `webhook_secret` to check the request against using `repository_owner`, a value read straight out of the unverified/attacker-controlled JSON body. `GitHubApp#verify_webhook_signature` treats a missing `webhook_secret` for that organization as automatic success. Meanwhile, the actual event handlers (e.g. `StatusHandler`) look up their target purely from other fields of the same body (`sha`, `repository.full_name`) with no re-check that they belong to the organization that was "verified." Because nothing binds the organization used for verification to the repository/commit actually written to, an attacker can pick a configured organization that has no `webhook_secret` to trivially pass verification, then supply a `sha`/`repository.full_name` pointing at a completely different, properly-configured organization's stack.

### Finding Description
`WebhooksController#verify_signature` derives the verification target like this: [1](#0-0) 

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
``` [2](#0-1) 

```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

`repository_owner` is read directly from `JSON.parse(request.raw_post)` — the exact payload whose authenticity is being decided — before any signature has actually been validated.

`GitHubApp#verify_webhook_signature` fails open when the selected organization has no configured secret: [3](#0-2) 

```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
```

Shipit explicitly supports multi-organization deployments where each org's GitHub App config, including `webhook_secret`, is independent: [4](#0-3) 

and the shipped example/dev configuration templates default `webhook_secret` to nil/unset for one or more configured orgs: [5](#0-4) [6](#0-5) 

Once `verify_signature` passes (because the org it picked has no secret), `create` dispatches to the event handler using the same attacker-controlled body: [7](#0-6) 

The `status` handler resolves its target purely by commit SHA, with no organization/repository binding check at all: [8](#0-7) 

```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```

Other handlers (push, pull_request, etc.) similarly key off `repository.full_name`: [9](#0-8) 

None of these re-derive or re-check the value that `verify_signature` used (`repository.owner.login`) against the field they act on (`sha` / `repository.full_name`). These are two independently attacker-suppliable fields inside the same forged JSON body.

The broken binding, stated as an equality that the code fails to enforce:
`organization authenticated by verify_signature (repository.owner.login)` == `repository/commit actually written by the handler (sha / repository.full_name)`.

Before the attack: a legitimate webhook for org X is only accepted if signed with X's secret, and only ever writes to X's own repositories/commits (the two sides of the equality coincide naturally because GitHub itself fills in both fields consistently).

After the attack: an attacker with no GitHub App credentials, no `webhook_secret`, no Shipit session, and no `ApiClient` token sets `repository.owner.login` to an org configured in the same Shipit instance with `webhook_secret` unset (satisfying `return true unless webhook_secret` and thus passing "verification" unconditionally), while setting `sha` (and, for other handlers, `repository.full_name`) to point at a commit/repository belonging to an entirely different, properly secured organization. `StatusHandler` then writes a forged `Status` to that victim commit.

### Impact Explanation
This is an authentication-bypass / cross-repository write: an unauthenticated, unprivileged network attacker can inject arbitrary GitHub event data (forged commit statuses at minimum, and potentially push/pull_request-driven side effects for other handlers) into any stack tracked by the Shipit instance, as long as the instance has at least one configured organization without a `webhook_secret` — a state explicitly produced by the project's own example/dev configuration files. Forged `Status` records land on the victim's commit; since Shipit's CI/status gating (`ci.require`) is what blocks a deploy button/API call from being usable, this can be used to defeat a deploy-readiness gate on a stack the attacker has no access to, without ever presenting a valid GitHub webhook signature for that stack's organization.

### Likelihood Explanation
High. No credentials of any kind are required. Any Shipit deployment configured for more than one GitHub organization (a documented, supported setup) is vulnerable if any one of the configured organizations lacks a `webhook_secret` — a state that is the literal default in the project's own example and test configuration files. The attacker only needs to know: (1) a valid commit SHA of the victim repository (trivially obtained from GitHub's public API or UI) and (2) the org key for the secret-less organization (visible in `Shipit.github_organizations`/config, often guessable or discoverable).

### Recommendation
Do not select the verification secret from the same unverified payload that is later trusted for routing. Concretely:
- Bind the organization/repository used to look up the signing secret to the same value used by the downstream handler, and reject the request if they mismatch after canonicalization.
- Do not allow `GitHubApp#verify_webhook_signature` to silently succeed when `webhook_secret` is blank in a multi-organization configuration; require every configured organization to have a `webhook_secret` (or explicitly whitelist single-org "no secret" mode only when exactly one organization is configured).
- Have handlers like `StatusHandler` scope their `Commit`/`Repository` lookup to the organization that was actually verified, not merely to a globally-unique field such as `sha`.

### Proof of Concept
1. Deploy Shipit with a multi-organization config where `OrgA` has a real `webhook_secret` and `OrgB` has none (mirrors the shipped `test/dummy/config/secrets_double_github_app.yml` / `config/secrets.development.shopify.yml` templates).
2. Identify a commit SHA belonging to a stack under `OrgA/victim-repo` that Shipit tracks (e.g. via GitHub's public commits API).
3. Send, without any signature/secret knowledge:
```
POST /github/webhooks
X-Github-Event: status
Content-Type: application/json

{
  "repository": { "owner": { "login": "OrgB" }, "full_name": "OrgB/anything" },
  "sha": "<victim-sha-from-OrgA/victim-repo>",
  "state": "success",
  "context": "<ci-context-required-by-OrgA-victim-repo's-shipit.yml>",
  "target_url": "https://attacker.example/fake",
  "description": "forged",
  "created_at": "2026-09-01T00:00:00Z"
}
```
4. `verify_signature` resolves `repository_owner` = `"OrgB"`, calls `Shipit.github(organization: "OrgB")`, and `verify_webhook_signature` returns `true` because `OrgB.webhook_secret` is blank — no `X-Hub-Signature` header is even required.
5. `create` dispatches to `StatusHandler#process`, which finds the victim `Commit` purely by `sha` (independent of `OrgB`) and calls `commit.create_status_from_github!(params)`, writing a forged "success" status onto the `OrgA/victim-repo` commit — demonstrating the cross-organization write achieved with zero credentials tied to `OrgA`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

**File:** lib/shipit.rb (L170-200)
```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
