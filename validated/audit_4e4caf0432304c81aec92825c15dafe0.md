## Analysis

The Sherlock report's root cause is: a user-facing function accepts a caller-controlled destination account without validating it against the chain's "null"/unrecoverable address, permanently locking transferred assets.

The Polkadot SDK analog is in `pallet-revive`'s EVM-compatible precompiles for `pallet-assets` (ERC20) and `pallet-asset-conversion` (DEX). These precompiles accept a Solidity `address` parameter that gets mapped to a native `AccountId` via `AddressMapper::to_account_id`. When the supplied `H160` address has no explicit mapping (as is always the case for `address(0)`), the mapper deterministically returns a stateless *fallback account* — for `AccountId32Mapper` this is `[0x00;20] ++ [0xEE;12]` for the zero address [1](#0-0) . This fallback account is not derived from any real public key, so in practice nobody controls the private key needed to spend from it — it functions exactly like Ethereum's `address(0)` burn sink.

Neither the ERC20 `transfer` precompile nor the asset-conversion `addLiquidity` precompile check the destination/recipient address for the zero value before minting/crediting the fallback account:

- ERC20 `transfer`: `dest` is derived directly from `call.to` and used in `do_transfer` with no zero-address guard [2](#0-1) .
- Asset-conversion `addLiquidity`: `mint_to` is derived directly from `call.mintTo` and passed to `MutateLiquidity::add_liquidity`, which mints LP tokens to it, with no zero-address guard [3](#0-2) .

Both entry points are reachable by any signed account via a normal `bare_call`/EVM transaction to the precompile address — no privileged role is required, matching the pattern demonstrated in existing tests [4](#0-3) .

### Title
Missing zero-address (`address(0)`) validation on recipient/`mintTo` parameters in pallet-assets ERC20 and pallet-asset-conversion precompiles permanently locks transferred/minted funds - ([File: substrate/frame/assets/precompiles/src/lib.rs], [File: substrate/frame/asset-conversion/precompiles/src/lib.rs])

### Summary
The Solidity-ABI precompiles exposed by `pallet-assets` (`ERC20::transfer`/`transferFrom`) and `pallet-asset-conversion` (`addLiquidity`) accept an attacker/user-supplied `address` destination that is converted to a native `AccountId` through `AddressMapper::to_account_id` without ever checking whether the supplied address is `address(0)`. Since an unmapped `H160` (which is always true for the zero address, as nobody can register a real key that maps to it) resolves to a deterministic, cryptographically unreachable "fallback account" [5](#0-4) , any asset transfer or LP-token mint routed to `address(0)` becomes permanently unrecoverable.

### Finding Description
`AccountId32Mapper::to_account_id` looks up `OriginalAccount` for a stateful mapping and, absent one, falls back to a purely deterministic derivation: the first 20 bytes of the H160 padded with a constant `0xEE` suffix [1](#0-0) . For `address(0)` this yields the fixed account `[0x00;20] ++ [0xEE;12]`. Because `AccountId32` values are ordinarily derived from public keys via cryptographic hashing, no legitimate keypair can be found whose hash collides with this specific padded value, so this account is unspendable in practice, functionally the Substrate analog of Ethereum's `address(0)`.

The `ERC20::transfer` precompile maps `call.to` straight into `do_transfer`'s destination with no validation [2](#0-1) . The `pallet-asset-conversion` `addLiquidity` precompile similarly maps `call.mintTo` straight into `MutateLiquidity::add_liquidity`'s `mint_to` parameter, which is used to mint LP tokens with no validation [3](#0-2) ; the underlying pallet's `do_add_liquidity` implementation also performs no beneficiary check before calling `T::PoolAssets::mint_into(pool.lp_token.clone(), mint_to, lp_token_amount)` [6](#0-5) .

Both call paths are reachable by any signed account through an ordinary `bare_call`/EVM-style transaction to the precompile address, exactly as exercised in the existing test suite [4](#0-3) . No governance, root, or privileged origin is required.

### Impact Explanation
If a user, integrating wallet, or contract mistakenly (or due to an upstream bug) supplies `address(0)` as the `to`/`mintTo` recipient, the transferred assets or newly-minted LP tokens are credited to an account that is provably unspendable by any real actor, resulting in a permanent, irreversible loss of user funds. This matches the impact class of the referenced report (funds locked at `address(0)`), rated Medium there.

### Likelihood Explanation
Likelihood is Medium: this requires user/integration error (accidentally passing an all-zero/default address, e.g. because it is the default value of an `address` variable in Solidity before assignment, or a bug in calling code), not any privileged capability, malicious validator, or governance action. The scenario mirrors common Solidity foot-guns since these precompiles intentionally emulate ERC20/DEX ABI semantics for EVM-compatible tooling that is prone to exactly this class of mistake.

### Recommendation
In both `ERC20::transfer`/`transferFrom` (`substrate/frame/assets/precompiles/src/lib.rs`) and `IAssetConversion::addLiquidity`/`removeLiquidity` (`substrate/frame/asset-conversion/precompiles/src/lib.rs`), reject `H160::zero()` (and any other well-known unspendable fallback pattern) as a destination/`mintTo`/`withdrawTo` parameter before invoking the underlying pallet mutation, reverting with a clear "invalid recipient" error, analogous to OpenZeppelin's `ERC20InvalidReceiver` check [7](#0-6) .

### Proof of Concept
Deployment/reachability evidence: the precompile test harness demonstrates ordinary signed-account calls reaching `ERC20::transfer` via `bare_call` [4](#0-3)  and `addLiquidity` via the analogous precompile in `substrate/frame/asset-conversion/precompiles/src/tests.rs`. No test in the repository asserts rejection of `H160::zero()`/`address(0)` for either `to` or `mintTo`; the fallback-mapping test (`test_system_precompile_unmapped_account`) confirms that `H160::zero()` deterministically maps to a live, storage-writable fallback `AccountId` rather than being rejected [8](#0-7) . A minimal reproduction (not executed here, but derivable from the existing harness) would: fund an account, mint an asset, call `ERC20::transferCall{ to: H160::zero(), value }` through `bare_call`, and observe the balance credited to the `[0;20]++[0xEE;12]` fallback account with no subsequent way to move it out, since no real keypair can produce that `AccountId32`.

		let account_bytes: &mut [u8; 32] = account_id.as_mut();
