### Title
Out-of-bounds Buffer read in PEM public key parsing reachable from `is_valid_sig`/`vrf_verify` oscript functions - (File: `signature.js`)

### Summary
`signature.validateAndFormatPemPubKey()` is directly reachable from AA/oscript formulas via the `is_valid_sig` and `vrf_verify` functions, which accept an attacker-controlled PEM key string as part of an AA trigger unit or an AA's own logic evaluated against attacker-supplied data. The PEM-parsing code indexes into a `Buffer` derived from base64-decoded, attacker-controlled input without first verifying the buffer is long enough to contain the fields being read, analogous to the CVE-2021-44962 pattern of reading past the bounds of attacker-supplied file/content data without a length check.

### Finding Description
`validateAndFormatPemPubKey()` decodes the PEM body into `contentAloneBuffer` and then reads several successive byte offsets to parse a minimal DER structure: [1](#0-0) 

The length check `contentAloneB64.length > 736` bounds the *maximum* size but does not guarantee a *minimum* size, and none of the subsequent branches verify that `contentAloneBuffer` actually has enough bytes at indices 0–6 before reading `contentAloneBuffer[1]`, `[2]`, `[3]`, `[4]`, `[5]` depending on the branch taken: [2](#0-1) 

Because `Buffer` indexing past its length silently returns `undefined` in Node.js rather than throwing, a short, attacker-crafted base64 payload (e.g. just `"MA=="` decoding to a 1-byte buffer `[0x30]`) causes `contentAloneBuffer[1]` and subsequent reads to be `undefined`. This flows into arithmetic/comparisons (`identifiersStart * 2 + identifiersLength * 2`) producing `NaN`, and into `contentAloneHex.slice(...)` with `NaN` bounds, silently yielding unexpected/incorrect strings instead of a clean rejection — the JS analog of the C++ OOB read: the code trusts attacker-supplied length/offset bytes to index into buffer memory it never validated is present.

A related, more severe instance of the same root cause exists in `verifyMessageWithSecp256k1PemPubKey()`, called from the same `is_valid_sig` path when `bPostPemCurvesFix` is active and the DER encodes the secp256k1 OID: [3](#0-2) [4](#0-3) 

Here `der[1]` is read to decide `algIdStart` before confirming `der.length` is sufficient, and `der.slice(bitStringIdx + 3, bitStringIdx + 68)` is taken from attacker-controlled DER bytes; if `der` is short, `.slice()` silently returns a truncated (possibly empty) buffer, and the subsequent `pubkey.length !== 65` check is the only backstop. While the `.length` checks here mostly turn genuinely malformed input into `false`, the pattern throughout this file is "read attacker-controlled byte offsets from a buffer without confirming the buffer is long enough first," matching the reported bug class (OOB read of attacker-supplied binary parsed by an unprivileged, single-message code path).

This code is reachable by any unprivileged actor who can:
- author or trigger an Autonomous Agent invoking `is_valid_sig(msg, pem_key, sig)` or `vrf_verify(seed, proof, pem_key)` where `pem_key` is derived from trigger data (`trigger.data.*`), as shown in the evaluation dispatcher: [5](#0-4) [6](#0-5) 

### Impact Explanation
The observable effect in JavaScript differs from the native C/C++ CVE: instead of leaking adjacent process memory, out-of-range `Buffer` indexing returns `undefined`/empty results, which get silently coerced into `NaN` or empty strings during arithmetic/slicing. In the worst case this can cause the PEM validation logic to take an unintended branch (e.g., mis-classify `typeIdentifiersHex`, mis-slice buffer content) which could make `validateAndFormatPemPubKey` incorrectly accept/reject a key, or produce differing behavior across different Node.js versions/engines. Because `is_valid_sig`/`vrf_verify` results feed directly into AA state-var/fund-release decisions, any indeterminism or engine-dependent parsing divergence here risks **node disagreement on AA response validity** if some validating nodes compute a different boolean result than others for the same malformed PEM key — this is the concrete AA-consensus-safety analog to the "information disclosure" impact of the original CVE.

### Likelihood Explanation
`is_valid_sig` and `vrf_verify` are ordinary oscript primitives usable in any AA definition, and the `pem_key` argument can be fully attacker-controlled when derived from `trigger.data`, so triggering the vulnerable code path requires only posting a unit that calls an AA with a short/malformed base64 string as the PEM key argument — no elevated privilege needed.

### Recommendation
Add explicit minimum-length assertions on `contentAloneBuffer` in `validateAndFormatPemPubKey()` before dereferencing indices `[1]`–`[5]` (e.g., require `contentAloneBuffer.length >= identifiersStart + identifiersLength + 8` before proceeding), and add an explicit `der.length` minimum check in `verifyMessageWithSecp256k1PemPubKey()` before reading `der[1]` and before computing `algIdStart`, rejecting with a clear error rather than allowing `undefined`/`NaN` to propagate through parsing logic.

### Proof of Concept
1. Deploy an AA containing `is_valid_sig({trigger.data.msg}, {trigger.data.key}, {trigger.data.sig})`.
2. Send a trigger unit with `data.key` set to a PEM-formatted string whose base64 body decodes to fewer than ~6 bytes (e.g., `-----BEGIN PUBLIC KEY-----\nMA==\n-----END PUBLIC KEY-----`).
3. Observe that `validateAndFormatPemPubKey()` reads `contentAloneBuffer[1]`..`[5]` on a 1-byte buffer, producing `undefined`/`NaN`-driven branch decisions instead of a clean, deterministic rejection at the `contentAloneBuffer[0] != 0x30` check boundary, matching the pattern in [7](#0-6) .

function verifyMessageWithSecp256k1PemPubKey(message, signature, der) {
	try {
		// Locate the BIT STRING for an uncompressed public key: 03 42 00 04 <32 X> <32 Y>
		var bitStringIdx = der.indexOf(Buffer.from([0x03, 0x42, 0x00]));
		if (bitStringIdx === -1) return false;
		var pubkey = der.slice(bitStringIdx + 3, bitStringIdx + 68); // 65 bytes: 04 + 32 + 32
		if (pubkey.length !== 65 || pubkey[0] !== 0x04) return false;

		var encoding = ValidationUtils.isValidHexadecimal(signature) ? 'hex' : 'base64';
		var sigBytes = Buffer.from(signature, encoding);
		var rawCompact = sigBytes.length === 64 ? sigBytes : Buffer.from(ecdsa.signatureImport(sigBytes));
		var compactSig = Buffer.from(ecdsa.signatureNormalize(rawCompact));

		var msgBuf = Buffer.isBuffer(message) ? message : Buffer.from(message);
		var hash = crypto.createHash('sha256').update(msgBuf).digest();
		return ecdsa.ecdsaVerify(compactSig, hash, pubkey);
	} catch(e) {
		console.log('secp256k1 pem verify exception: ' + e);
		return false;
	}
}
