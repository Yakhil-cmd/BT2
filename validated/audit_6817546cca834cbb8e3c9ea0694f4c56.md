### Title
CCMenu API token stack-scope bypass allows cross-stack disclosure of deploy/task state - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Shipit::ApiClient` supports an optional `stack_id` scope that is supposed to bind a token to a single `Stack`, enforced by `Shipit::Api::BaseController#stacks`/`#stack`. `Shipit::Api::CCMenuController` overrides `#stack` and looks the target stack up directly from all stacks by `params[:stack_id]`, never consulting the scoped `stacks` relation. This breaks the binding "stack a token authorizes = stack it touches," letting a token scoped to one stack read CCMenu deploy state for any other stack.

### Finding Description
`ApiClient` optionally `belongs_to :stack` [1](#0-0) , and permission checks in `check_permissions!` only validate the `operation:scope` string (e.g. `read:stack`), never the specific stack id [2](#0-1) . The actual per-stack authorization boundary is enforced centrally in `Shipit::Api::BaseController`:

```ruby
def stacks
  @stacks ||= current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all
end

def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
``` [3](#0-2) 

Every other controller that needs a stack (e.g. `DeploysController`, `RollbacksController`, `LocksController`, `StacksController`) inherits `#stack`/`#stacks` unmodified and is therefore restricted to `current_api_client.stack_id` when the token is scoped [4](#0-3) [5](#0-4) .

`CCMenuController`, however, redefines `#stack` to bypass that scoping entirely:

```ruby
require_permission :read, :stack

def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end
``` [6](#0-5) 

`require_permission :read, :stack` only calls `current_api_client.check_permissions!(:read, :stack)`, which checks the token has the `read:stack` string in its `permissions` array — it does not check `current_api_client.stack_id` at all [7](#0-6) . Because `#stack` here queries `Stack.from_param!` unscoped, any `stack_id` param supplied by the caller resolves against the entire `Stack` table, independent of which stack (if any) the presented token was bound to.

This mirrors the ERC1404 bug class: the "membership"/authorization check (`read:stack` permission, analogous to checking only the receiving address) is validated, but the binding that should restrict which specific stack the token may touch (analogous to also checking the sending address) is silently dropped in this one controller.

### Impact Explanation
A token created with `stack_id` set (limiting it to a single stack) is meant to only disclose state for that stack. Via `CCMenuController#show`, that same token can be replayed with any other `stack_id` in the URL and will successfully render `deploys_and_rollbacks.last` (deploy status, timing, running state) for stacks the token was never authorized to see. This is an unauthenticated-scope escalation exposing task/deploy state across stacks and repositories the token holder should not have access to, matching the "High" impact class: unauthorized read of stack state/deploy output.

### Likelihood Explanation
Any holder of a stack-scoped `read:stack` API token (e.g. a CCMenu URL generated for one stack via `CCMenuUrlController`, which itself creates a `read:stack` client [8](#0-7) ) can exploit this by simply changing the `stack_id` in the request path — no additional privileges, signature forgery, or credentials are required beyond the token itself.

### Recommendation
Make `CCMenuController#stack` use the inherited scoped `stacks` relation (i.e. remove the controller-local override, or change it to `stacks.from_param!(params[:stack_id])`) so that stack-scoped tokens are restricted exactly as they are in every other API controller.

### Proof of Concept
1. Admin generates a CCMenu URL for `stack_id=42`, producing an `ApiClient` token `T` with `permissions: ["read:stack"]`.
2. Attacker (or the token holder) requests `GET /api/stacks/:other_stack_id/ccmenu.xml?token=T` where `other_stack_id` belongs to a different, unrelated stack.
3. `authenticate_api_client` accepts `T` via `ApiClient.authenticate(params[:token])` [9](#0-8) .
4. `require_permission :read, :stack` passes because `T` has `read:stack` in its permission list, regardless of `stack_id`.
5. `stack` resolves `Stack.from_param!(other_stack_id)` directly, bypassing the `current_api_client.stack_id` filter, and the controller renders deploy/rollback state for the unauthorized stack.
