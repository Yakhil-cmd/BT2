### Title
CCMenu API Endpoint Ignores Api Client Stack Scope, Allowing A Stack-Scoped Token To Read Any Stack's Build Status - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
The `Api::CCMenuController#stack` method resolves the requested stack directly from `params[:stack_id]` via `Stack.from_param!`, bypassing the `ApiClient`'s stack scope that the rest of the API enforces through `BaseController#stacks`. This breaks the binding `current_api_client.stack_id == stack acted upon`, letting a token that was only ever authorized to read one specific stack's CI status read the CI status of any stack in the Shipit instance.

### Finding Description
`Shipit::ApiClient` supports being scoped to a single stack via its `stack_id` column, and the generic API path enforces this scope centrally: [1](#0-0) 

```ruby
def stacks
  @stacks ||= current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all
end

def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```

Any other `Api::*Controller` that calls the inherited `stack` helper is correctly limited to the stack the client was scoped to. However, `Api::CCMenuController` (mounted at `/*stack_id/ccmenu.xml` and authenticated by a `token` query parameter rather than Basic Auth) overrides this helper: [2](#0-1) 

```ruby
private

def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end

def authenticate_api_client
  @current_api_client = ApiClient.authenticate(params[:token])
  super unless @current_api_client
end
```

This override resolves `Stack.from_param!(params[:stack_id])` against the entire `Stack` table, completely ignoring `current_api_client.stack_id`. The only authorization check performed is the generic permission check `require_permission :read, :stack` [3](#0-2) , which only validates that the token carries the `read:stack` *permission string*, not that it is scoped to *this* stack.

This scoping mechanism exists specifically to create narrowly-authorized tokens: `CCMenuUrlController#client` creates (or reuses) a per-user, per-stack `ApiClient` with `read:stack` permission and binds it to one `stack`: [4](#0-3) 

```ruby
def client
  @client ||= ApiClient.create_with(permissions: %w[read:stack])
                       .find_or_create_by!(creator: current_user, name: 'CCMenu Client')
end
```

The signed `authentication_token` embeds only the `ApiClient` row id (`self.class.message_verifier.generate(id)` in `app/models/shipit/api_client.rb` lines 34-36) and does not itself carry or enforce the stack scoping; the scoping is supposed to be enforced by the controller's `stacks`/`stack` lookup, exactly the enforcement that `CCMenuController` skips.

### Impact Explanation
This is the direct structural analog of the reported bug class: a credential's binding to a specific resource (org that authenticated vs. repo written / stack a token authorizes vs. stack it touches) is not carried through to the value actually acted upon. Here, an `ApiClient` token that is only supposed to authorize reading one stack's CI state (as generated for a CCMenu integration URL shared with a specific team/stack) can instead be used to read the build/deploy status (`lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, lock status, etc.) of every stack managed by the Shipit instance, simply by changing the `stack_id` path segment while reusing the leaked/observed token. This is an unauthenticated-scope escalation: read access to stack state/deploy output beyond what the token was provisioned for, satisfying the "unauthenticated read of stack state, task streams or deploy output" High-impact category, since the token no longer confines the reader to the stack it was minted for.

### Likelihood Explanation
The `token` value is embedded directly in a URL (`ccmenu_url`) that is designed to be shared with third-party CI status tools/dashboards (per `CCMenuUrlController`/`Api::CCMenuController` naming and test `test/controllers/api/ccmenu_controller_test.rb`), so it is more likely than a typical API credential to be exposed to intermediaries, logs, or copy-pasted between systems. Exploiting the flaw requires no privileges beyond possessing any single valid CCMenu token (which is by design meant to be low-privilege and narrowly scoped); the attacker only needs to substitute the `stack_id` in the URL. This is a low-effort, high-confidence exploitation path once a token for any stack is obtained.

### Recommendation
Make `Api::CCMenuController#stack` honor the same stack-scoping used elsewhere by resolving through the inherited scoped `stacks` collection (i.e., `stacks.from_param!(params[:stack_id])`) instead of `Stack.from_param!(params[:stack_id])`, so that a stack-scoped `ApiClient` cannot be used to query stacks outside its `stack_id`.

### Proof of Concept
1. As a legitimate Shipit user, visit `/ccmenu/<stack_a>` (or trigger `CCMenuUrlController#fetch`) to obtain a CCMenu URL such as `https://shipit.example.com/api/<stack_a>/ccmenu.xml?token=<TOKEN>`, where `TOKEN` authenticates an `ApiClient` created with `stack_id = stack_a.id` and permissions `['read:stack']`.
2. An attacker who observes/obtains `TOKEN` (e.g., from a shared CI dashboard config, logs, or a proxy) sends: `GET /api/<stack_b>/ccmenu.xml?token=<TOKEN>` for an arbitrary other stack `stack_b`.
3. Because `Api::CCMenuController#stack` calls `Stack.from_param!(params[:stack_id])` directly (bypassing `current_api_client.stack_id` scoping enforced in `Api::BaseController#stacks`), the request succeeds and returns `stack_b`'s build/deploy status and lock state, even though `TOKEN` was only authorized for `stack_a`.
