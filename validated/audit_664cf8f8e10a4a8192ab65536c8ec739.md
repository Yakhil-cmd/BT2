### Title
Arity-based overload of `validateSignedMessage()` silently drops address-authentication, mirroring Netty's trust-manager-wrapper bypass - (File: signed_message.js)

### Summary
`signed_message.js`'s `validateSignedMessage()` decides which of three call signatures was used purely by inspecting `arguments`/parameter truthiness, exactly like Netty's `X509TrustManagerWrapper`, which silently drops the hostname-carrying `SSLEngine` argument when it detects a "compatible" but weaker call shape. Here, when the function is invoked without an explicit `address` (the 2‑arg legacy form used by `validateSignedMessageSync`), the code no longer verifies that the signature belongs to the specific counterparty address the caller expects — it just accepts whichever author happens to be first in the array.

### Finding Description
`validateSignedMessage(conn, objSignedMessage, address, mci, handleResult)` re-detects its own calling convention at runtime: [1](#0-0) 

If `address` is not supplied, the function does not fail closed; instead it falls into the branch that treats the message as single-author and unconditionally accepts `authors[0]` as "the" verified author, without ever confirming that this author is the specific address the caller intended to check: [2](#0-1) 

The comment directly above the 2-arg wrapper openly acknowledges the resulting weakness: [3](#0-2) 

This is structurally identical to the Netty bug class: a wrapper/overload that is supposed to preserve a strong identity check (hostname in Netty; specific signer address here) silently discards that check when invoked through what looks like a compatible but reduced-argument interface, and nothing downstream re-adds the missing verification.

### Impact Explanation
Any code path that validates a signed package/private message via the argument-elided form (`validateSignedMessageSync` or the 2/3-arg forms of `validateSignedMessage`) ends up confirming only that *some* valid signature exists on the message and that the definition hash matches its own address, but not that the signer is the specific counterparty address the calling logic (e.g. an AA `is_valid_signed_package` check, an arbiter/prosaic contract, or a paired-device signed message flow) expected. An attacker who can supply their own validly-signed message (trivial — they sign with their own key) could have it accepted in place of a message that was supposed to come from a particular payment-channel peer or contract counterparty, enabling forged approvals, fraud-proof bypass, or unauthorized state transitions in code that relies on the address check being performed as part of `validateSignedMessage`.

### Likelihood Explanation
Exploitability depends entirely on whether any caller in the AA/oscript/contract/device-message surface actually invokes `validateSignedMessage` or `validateSignedMessageSync` without passing an explicit `address` while still relying on the result to imply "signed by counterparty X." The AA formula path (`is_valid_signed_package` in `formula/evaluation.js`) does pass a concrete `evaluated_address` and mci, so that specific call site is safe. `wallet.js`, `arbiter_contract.js`, and `prosaic_contract.js` also reference signed-message validation, but I was not able to fully inspect their exact call signatures before running out of tool budget, so I cannot confirm with certainty that any of them use the weaker, address-less form in a context reachable by an unprivileged private-payment counterparty or paired device. This uncertainty materially affects the severity of the finding.

### Recommendation
Remove the implicit arity-based redispatch in `validateSignedMessage()`. Require callers to always pass an explicit `address` (or an explicit `null` meaning "no specific author required", chosen deliberately rather than inferred from missing arguments), and audit every caller (`wallet.js`, `arbiter_contract.js`, `prosaic_contract.js`, `validateSignedMessageSync`) to ensure they supply the address whenever the result is used to authenticate a specific counterparty.

### Proof of Concept
Given the confirmed but not-fully-traced reachability of the vulnerable code path (see Likelihood Explanation), a concrete end-to-end PoC cannot be constructed without further inspection of `wallet.js`/`arbiter_contract.js`/`prosaic_contract.js` call sites, which was not completed within the available tool budget.
