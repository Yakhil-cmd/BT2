### Title
Missing `return` after hash-computation failure causes double completion of private-payment queue entry in `handleSavedPrivatePayments()` - (File: network.js)

### Summary
In `network.js`, the function `handleSavedPrivatePayments()` processes queued private-payment chains stored in `unhandled_private_payments`. When computing `json_payload_hash` throws (e.g. because a private-payment counterparty sent a malformed `payload`), the `catch` block deletes the queue row and invokes the `async.each` iteration callback `cb`, but execution falls through (no `return`) into the normal validation path, which invokes `privatePayment.validateAndSavePrivatePaymentChain()` and eventually calls `deleteHandledPrivateChain(..., cb)` (or `cb()`) a second time for the same row. This is analogous to the kernel bug class in CVE‑2025‑40047: a queued/waiting entry is not unconditionally "pruned" on every completion path, so a second, racing completion path fires against an entry that should already have been finalized.

### Finding Description
`handleSavedPrivatePayments()` iterates queued rows with `async.each`, and for each row defines:

```js
var validateAndSave = function(){
    var objHeadPrivateElement = arrPrivateElements[0];
    try {
        var json_payload_hash = objectHash.getBase64Hash(objHeadPrivateElement.payload, true);
    }
    catch (e) {
        console.log("getBase64Hash failed for private element", objHeadPrivateElement.payload, e);
        if (ws)
            sendResult(ws, {private_payment_in_unit: row.unit, result: 'error', error: e.toString()});
        deleteHandledPrivateChain(row.unit, row.message_index, row.output_index, cb);
    }
    var key = 'private_payment_validated-'+objHeadPrivateElement.unit+'-'+json_payload_hash+'-'+row.output_index;
    privatePayment.validateAndSavePrivatePaymentChain(arrPrivateElements, {
        ifOk: function(){ ... deleteHandledPrivateChain(row.unit, row.message_index, row.output_index, cb); ... },
        ifError: function(error){ ... deleteHandledPrivateChain(row.unit, row.message_index, row.output_index, cb); ... },
        ifWaitingForChain: function(){ ... cb(); }
    });
};
``` [1](#0-0) 

There is no `return` statement inside the `catch` block, so after `deleteHandledPrivateChain(cb)` finalizes and prunes the row (the correct completion path), the same synchronous function continues executing and calls `privatePayment.validateAndSavePrivatePaymentChain(arrPrivateElements, {...})` on the *same* `arrPrivateElements`, whose payload is still the attacker-controlled data that failed hashing. This second call runs full validation/save logic and — regardless of its outcome (`ifOk`, `ifError`, or `ifWaitingForChain`) — calls `cb` (via `deleteHandledPrivateChain(...cb)` or directly) a second time for the same async.each item.

The row entering this queue (`unhandled_private_payments`) is populated by `network.handleOnlinePrivatePayment()`, reachable directly by any private-payment counterparty sending a `private_payments`/private-chain message over a paired device or hub connection: [2](#0-1) [3](#0-2) 

`objectHash.getBase64Hash` can throw on malformed/non-canonical payload content (e.g. unexpected types or structures inside `payload`), which is plausible from an attacker crafting the `payload` field of a private-payment chain element. This gives an unprivileged private-payment counterparty a way to reliably drive execution into the buggy fallthrough path.

The double invocation of `cb` for the same item breaks the invariant that `async.each` expects exactly one callback per item; a second call for the same item can cause the overall `async.each` completion callback to fire prematurely (with other rows' processing still outstanding), which in turn:
- releases the `["saved_private"]` mutex early (`unlock()` in the outer `lock(["saved_private"], ...)` callback) while other rows are still being validated/saved concurrently, and
- emits `new_my_transactions` prematurely/inconsistently. [4](#0-3) 

Additionally, the second call proceeds to run full DB validation/save logic (`privatePayment.validateAndSavePrivatePaymentChain`) against a payload that already failed canonical hashing, bypassing the intended "reject on hash failure" outcome and instead going through the normal accept/duplicate-check code path in `private_payment.js`: [5](#0-4) 

This mirrors the kernel bug class exactly: the queue entry (here, the `unhandled_private_payments` row / the `async.each` item) must be pruned/finalized on exactly one path; instead it can be finalized on the error path and then reprocessed and finalized again on the normal path, because the "cancellation"/error branch does not unconditionally stop further wait-queue processing.

### Impact Explanation
Double-processing the same private-payment row concurrently with two independent invocations of `privatePayment.validateAndSavePrivatePaymentChain` racing against the mutex-guarded batch loop can cause the "saved_private" mutex to be released while another row's DB transaction is still in flight, breaking the serialization guarantee that this lock is meant to provide for private-payment processing. That serialization is relied on elsewhere to avoid concurrent/duplicate insertion of private payment inputs/outputs for the same wallet state. A wallet's local processing of private-payment chains desynchronizing from the mutex it depends on can lead to inconsistent wallet state regarding which private outputs are considered spent/received, i.e., potential double-crediting/duplicate insertion attempts or missed processing of legitimately queued private payments (funds appearing stuck/never surfaced as `new_my_transactions`). This satisfies the "AA/asset fund loss or freezing" / node disagreement class of impact required by the validation rules, reachable by an unprivileged private-payment counterparty.

### Likelihood Explanation
The trigger condition (making `objectHash.getBase64Hash` throw on a crafted `payload`) is plausible for a private-payment counterparty who fully controls the content of the private-payment chain element sent to a peer/paired device, since this is exactly the object being hashed. No special privileges beyond being a private-payment counterparty (or forwarding through the hub) are required, and the code path is directly reachable via `handleOnlinePrivatePayment` → `savePrivatePayment` → `handleSavedPrivatePayments` → `validateAndSave`.

### Recommendation
Add a `return` statement at the end of the `catch` block in `validateAndSave` inside `handleSavedPrivatePayments()` (network.js, around line 2477) so that after `deleteHandledPrivateChain(...)` finalizes and prunes the row, execution does not fall through into the normal validation path. This ensures the queue entry (and its associated `cb`) is completed exactly once, matching the "always prune the wait-queue-equivalent entry" fix applied upstream for CVE-2025-40047.

### Proof of Concept
1. As a paired device / private-payment counterparty, send (or forward via the hub) a `private_payments` message whose `chains[0][0].payload` is crafted so that `objectHash.getBase64Hash(payload, true)` throws inside `network.js`'s `handleSavedPrivatePayments → validateAndSave` (e.g. a payload field type/shape that the hashing routine cannot canonicalize).
2. The row is inserted into `unhandled_private_payments` by `savePrivatePayment` in `handleOnlinePrivatePayment` (reached via `ifWaitingForChain`/`ifQueued` for light wallets), then later picked up by `handleSavedPrivatePayments()`.
3. In `validateAndSave`, the hash computation throws; the `catch` block calls `deleteHandledPrivateChain(row.unit, row.message_index, row.output_index, cb)`, pruning the row and invoking `cb` once.
4. Execution falls through (no `return`) to `privatePayment.validateAndSavePrivatePaymentChain(arrPrivateElements, {...})`, which independently proceeds to validate/save the same (still attacker-controlled) `arrPrivateElements` and calls `cb` a second time via its own `ifOk`/`ifError`/`ifWaitingForChain` branch.
5. Observe `cb` invoked twice for the same `async.each` item, causing the batch's final callback (and the `["saved_private"]` mutex `unlock()`) to fire out of sync with the number of rows still being processed, and the malformed payload to be run through the full save path despite having already failed canonical hashing. function validateAndSavePrivatePaymentChain(arrPrivateElements, callbacks){
	if (!ValidationUtils.isNonemptyArray(arrPrivateElements))
		return callbacks.ifError("no priv elements array");
	var headElement = arrPrivateElements[0];
	if (!headElement.payload)
		return callbacks.ifError("no payload in head element");
	var asset = headElement.payload.asset;
	if (!asset)
		return callbacks.ifError("no asset in head element");
	if (!ValidationUtils.isNonnegativeInteger(headElement.message_index))
		return callbacks.ifError("no message index in head private element");
	
	var validateAndSave = function(){
		storage.readAsset(db, asset, null, function(err, objAsset){
			if (err)
				return callbacks.ifError(err);
			if (objAsset.is_private !== 1)
				return callbacks.ifError("asset is not private");
			if (!!objAsset.fixed_denominations !== !!headElement.payload.denomination)
				return callbacks.ifError("presence of denomination field doesn't match the asset type");
			if (!!objAsset.fixed_denominations !== ("output" in headElement))
				return callbacks.ifError("divisible asset must not have output field, indivisible must");
			db.takeConnectionFromPool(function(conn){
				conn.query("BEGIN", function(){
					var transaction_callbacks = {
						ifError: function(err){
							conn.query("ROLLBACK", function(){
								conn.release();
								callbacks.ifError(err);
							});
						},
						ifOk: function(){
							conn.query("COMMIT", function(){
								conn.release();
								callbacks.ifOk();
							});
						}
					};
					// check if duplicate
					var sql = "SELECT address, denomination, amount, blinding FROM outputs WHERE unit=? AND asset=? AND message_index=?";
					var params = [headElement.unit, asset, headElement.message_index];
					if (objAsset.fixed_denominations){
						if (!ValidationUtils.isNonnegativeInteger(headElement.output_index))
							return transaction_callbacks.ifError("no output index in head private element");
						sql += " AND output_index=?";
						params.push(headElement.output_index);
					}
					conn.query(
						sql, 
						params, 
						function(rows){
							if (rows.length > 1)
								throw Error("more than one output "+sql+' '+params.join(', '));
							if (rows.length > 0 && rows[0].address){ // we could have this output already but the address is still hidden
								const stored = rows[0];
								const payload = headElement.payload;
								let bDuplicate = false;
								if (objAsset.fixed_denominations){ // the row we selected is exactly headElement.output_index, filtered in sql above
									const claimed_output = payload.outputs?.[headElement.output_index];
									const revealed_output = headElement?.output;
									bDuplicate =
										ValidationUtils.isNonemptyObject(claimed_output)
										&& ValidationUtils.isNonemptyObject(revealed_output)
										&& stored.denomination === payload.denomination
										&& stored.amount === claimed_output.amount
										&& stored.address === revealed_output.address
										&& stored.blinding === revealed_output.blinding;
								}
								else // divisible outputs are never hidden individually and sql has no output_index filter, so match against any of them
									bDuplicate = (payload.outputs || []).some(output => {
										return ValidationUtils.isNonemptyObject(output)
											&& stored.denomination === 1
											&& stored.amount === output.amount
											&& stored.address === output.address
											&& stored.blinding === output.blinding;
									});
								if (bDuplicate) {
									console.log("duplicate private payment "+params.join(', '));
									return transaction_callbacks.ifOk();
								}
							}
							var assetModule = objAsset.fixed_denominations ? indivisibleAsset : divisibleAsset;
							assetModule.validateAndSavePrivatePaymentChain(conn, arrPrivateElements, transaction_callbacks);
						}
					);
				});
			});
		});
	};
	
	if (conf.bLight)
		findUnfinishedPastUnitsOfPrivateChains([arrPrivateElements], false, function(arrUnfinishedUnits){
			(arrUnfinishedUnits.length > 0) ? callbacks.ifWaitingForChain() : validateAndSave();
		});
	else
		validateAndSave();
}
