### Title
Reused/stale Bitcoin L1-lockup proof lets a staker claim `register-for-bond` sBTC collateral credit that isn't actually locked - (File: `stackslib/src/chainstate/stacks/boot/pox-5.clar`)

### Summary
`register-for-bond`'s L1 path (`verify-l1-lockups` / `validate-l1-lockup`) accepts a Bitcoin merkle-inclusion proof of a timelock output as evidence that `sats-total` sats are currently locked as bond collateral, but it only de-duplicates outpoints *within a single call's output list* — there is no persistent, cross-call registry of already-credited L1 outpoints. This mirrors the reported bug class (a validator accepting a "proof" as evidence of a commitment without checking it hasn't already been consumed/counted), letting `amount-sats` recorded in `protocol-bond-memberships` diverge from BTC actually locked.

### Finding Description
`register-for-bond` computes `sats-total` from `verify-l1-lockups`, which folds over the caller-supplied list of Bitcoin outputs via `validate-l1-lockup`, tracking `seen-outpoints` only as a fresh, empty list for that single invocation: [1](#0-0) 

The per-output dedup guard exists solely to stop a single call from citing the same outpoint multiple times to inflate `sum`, as confirmed by the integration-test docstring: "the per-output dedup inside `validate-l1-lockup` trips before the post-fold sum check ... the honest single-output proof still registers (guards against too-aggressive dedup)." [2](#0-1) 

Crucially, `register-for-bond` never persists which Bitcoin outpoints have already been counted as collateral across separate transactions/bonds. The state that is mutated is only `protocol-bond-memberships`, `protocol-bonds-total-staked`, and the signer/bond cycle share maps — none of which is keyed by the underlying BTC outpoint: [3](#0-2) 

Because Clarity/the node can only verify Bitcoin-header-anchored merkle inclusion of a transaction (i.e., that the timelock output was *created*), not whether that UTXO has since been spent/unlocked on Bitcoin, the same historical lockup transaction can be re-submitted as proof in a later `register-for-bond` call once eligible again (e.g., after a prior bond using it ends and the staker rolls into a new bond, or after any earlier registration referencing it is torn down) even if the BTC was already withdrawn on L1. `sats-total` is used directly to size `protocol-bond-memberships`, `protocol-bonds-total-staked`, and `add-staker-to-bond-cycles`, all of which drive bond-reward sizing (`bondTargetYieldPerCalculation`) and `claim-rewards` payouts in sBTC: [4](#0-3) 

This breaks the equality "sBTC/STX bond rewards paid ∝ sats actually locked on Bitcoin at claim time" — a staker can be credited (and later paid bond rewards) for a lockup that is not truly locked, because the same proof of a Bitcoin output's *existence* is treated as ongoing proof of custody with no persistent replay protection outside a single call.

### Impact Explanation
If exploitable, this allows sats to be double-counted as bond collateral across separate `register-for-bond` calls without new BTC actually being locked, inflating a staker's/signer's bond share and thus their claimable sBTC rewards beyond what is backed by real locked BTC — matching the "Critical: sats credited by an L1 proof that were never locked on Bitcoin" / "double-counting a commitment" category.

### Likelihood Explanation
Requires only an ordinary staker replaying a previously-used, node-verifiable Bitcoin merkle proof in a subsequent `register-for-bond` call (e.g., after their prior bond membership using that outpoint has rolled over/ended, per the code paths at lines 764-815 that permit non-overlapping re-registration). No admin, miner, or other user's key is needed. I was not able to fully confirm the absence of a global outpoint-used map elsewhere in the contract within the scanned excerpts (search coverage was limited by index/tool budget), so likelihood should be validated by inspecting the complete `pox-5.clar` map/data-var declarations for any `l1-outpoints-used`-style map before treating this as confirmed-exploitable.

### Recommendation
Persist a durable map (e.g., `{tx-id, output-index} -> bool`) of L1 outpoints already credited toward bond collateral, checked and set in `validate-l1-lockup`/`verify-l1-lockups` across all calls (not just within one fold), so the same Bitcoin lockup output can never back more than one live bond-collateral credit.

### Proof of Concept
1. Staker A calls `register-for-bond` for bond 0 with a valid L1 lockup proof for outpoint `O` (sats `S`), receiving bond membership with `amount-sats: S`. [5](#0-4) 
2. Bond 0 ends; staker A's `protocol-bond-memberships` overlap check permits rolling into bond 6 (non-overlapping) per `bond-overlaps-new-position?`. [6](#0-5) 
3. Staker A calls `register-for-bond` for bond 6, resubmitting the *same* Bitcoin header/merkle proof for outpoint `O` (still verifiable as historically included, regardless of whether the BTC was ever unlocked/spent on L1). `verify-l1-lockups`'s `seen-outpoints` is freshly initialized for this new call, so it passes. [1](#0-0) 
4. Bond 6 membership is created crediting `amount-sats: S` again, and bond-reward calculations (`calculateRewards`/`claim-rewards`) pay out sBTC proportional to `S` sats for bond 6 as well — sats that may no longer be locked on Bitcoin, double-counting the same underlying BTC collateral.
