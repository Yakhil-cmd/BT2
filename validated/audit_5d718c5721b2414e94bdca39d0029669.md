### Title
Handlers select `Repository`/`Stack` by `repository.full_name` while `WebhooksController#verify_signature` authenticates the payload against `repository.owner.login`, allowing a self-service org owner to mutate another organization's stacks - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the `GitHubApp` (and thus the `webhook_secret` used for HMAC verification) using `params.dig('repository','owner','login')`, but every webhook `Handler` subsequently resolves the target `Repository`/`Stack` using the independent `params.dig('repository','full_name')` field, with no check that the two agree. Because both fields live in the same attacker-suppliable JSON body, an attacker who owns a legitimate org (and therefore legitimately knows that org's `webhook_secret`) can sign an arbitrary payload whose `repository.owner.login` is their own org (passing signature verification) while `repository.full_name` names a *different*, victim-owned repository.

### Finding Description
The broken binding is: `Shipit.github(organization: repository_owner)` (verified org) MUST equal the organization that owns the `Repository`/`Stack` mutated by `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`. This is never enforced.

- `verify_signature` computes `repository_owner` from `params.dig('repository','owner','login')` and validates the raw POST body's HMAC against that org's `webhook_secret`: [1](#0-0) [2](#0-1) 

- Every handler (base `Handler#stacks`, `PullRequest::OpenedHandler#repository`, `ClosedHandler#repository`, `ReopenedHandler#repository`, `LabelCapturingHandler#repository`, `ReviewStackAdapter`) resolves the repository purely from `payload.dig('repository','full_name')` / `params.repository.full_name`, never cross-checking it against `repository_owner`: [3](#0-2) [4](#0-3) [5](#0-4) [6](#0-5) [7](#0-6) 

- `Repository.from_github_repo_name` performs a global, un-scoped lookup by `owner`/`name` parsed straight out of `full_name`, with no relation to which org's secret validated the request: [8](#0-7) 

Attacker flow: the attacker configures their own GitHub App/webhook on `attacker-org` (self-service, legitimate), thereby legitimately knowing `attacker-org`'s `webhook_secret`. They then send a direct `POST /webhooks` (not necessarily via GitHub) with headers `X-Github-Event: pull_request` and `X-Hub-Signature` computed over a **crafted raw body** using `attacker-org`'s known secret. In that body they set `repository.owner.login = "attacker-org"` (so `verify_signature` looks up and validates against `attacker-org`'s app/secret and succeeds) but `repository.full_name = "victim-org/victim-repo"` (an existing `Repository` belonging to a different, victim organization). `verify_webhook_signature` only checks the HMAC of the raw body against `attacker-org`'s secret and does not inspect `full_name`: [9](#0-8) 

The handler then resolves `Shipit::Repository.from_github_repo_name("victim-org/victim-repo")`, which returns the real victim `Repository`, and mutates its `review_stacks`/`Stack` (create, archive, unarchive, or overwrite pull-request labels) - e.g. `ReviewStackAdapter#create!`/`#archive!`/`#unarchive!`: [10](#0-9) [11](#0-10) 

No existing guard catches this: `verify_signature` never re-derives or compares the resolved `Repository#owner` to `repository_owner`; `drop_unhandled_event` only filters by event type; `ExplicitParameters` schemas (see `OpenedHandler.params`) only validate types/presence of `full_name`, not consistency with `owner.login`; and `Repository.from_github_repo_name` has no organization-scoping parameter at all.

### Impact Explanation
An attacker who legitimately controls one organization's GitHub App/webhook secret can forge webhook payloads that create, archive, unarchive, or relabel review stacks belonging to *any other organization* whose repository is registered in the same Shipit instance - a payload authenticated for one tenant mutating another tenant's records. This matches the "payload for one repository mutating another's stack" Critical category. It is fully repeatable against any repository the attacker can enumerate (e.g., via Shipit's public stack listing or guessed `owner/name`), and works for every `pull_request`-based handler (`opened`, `closed`, `reopened`, label add/remove) as well as any other handler using `Handler#stacks`/`repository_name` (push, status, check_suite). This constitutes a cross-tenant integrity break across the whole webhook surface, not a single endpoint.

### Likelihood Explanation
Preconditions: Shipit must be configured in multi-organization mode (`config/secrets*.yml` with per-org `webhook_secret`, as documented and tested via `test/dummy/config/secrets_double_github_app.yml`), and at least one victim repository/stack must already exist in the shared Shipit database. Attacker cost is low: they only need to register their own GitHub App/webhook on any org (self-service, no privilege needed) to obtain a valid `webhook_secret`, then can POST directly to the `/webhooks` endpoint with a fully attacker-crafted JSON body and a correctly computed HMAC - no GitHub-side action or victim cooperation is required. This is trivially repeatable and scriptable.

### Recommendation
In `WebhooksController#verify_signature` (or immediately before dispatch in `#create`), after determining `repository_owner` from the payload, also parse the owner segment out of `params.dig('repository','full_name')` and reject the request (`head 422`) unless the two agree case-insensitively. Additionally/alternatively, harden `Handler` (and `Repository.from_github_repo_name`) to accept and enforce an expected organization, and have `WebhooksController#create` pass the verified `repository_owner` down to `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params, expected_owner: repository_owner) }`, with handlers scoping `Repository.where(owner: expected_owner)` instead of a global lookup.

### Proof of Concept
Minitest plan (`test/controllers/webhooks_controller_test.rb`), using the existing double-org fixture (`test/dummy/config/secrets_double_github_app.yml`, orgs `OrgOne`/`OrgTwo`):

1. Configure `Shipit.stubs(:secrets)` with the double-org config so `OrgOne` and `OrgTwo` each have distinct `webhook_secret`s.
2. Create a `Repository`/`Stack` fixture owned by `OrgTwo` (e.g., `owner: "orgtwo", name: "victim-repo"`).
3. Build a `pull_request` "opened" payload where `payload['repository']['owner']['login'] = "OrgOne"` and `payload['repository']['full_name'] = "orgtwo/victim-repo"`, plus a valid `pull_request.head.ref`.
4. Compute `X-Hub-Signature` as `"sha1=" + OpenSSL::HMAC.hexdigest('sha1', OrgOne_webhook_secret, payload.to_json)`.
5. `POST :create` with that body/signature and `X-Github-Event: pull_request`.
6. Assert the equality that should hold: `resolved_repository.owner == "OrgOne"` (the verified/authenticating org) — and show it currently fails, i.e. `Shipit::Repository.from_github_repo_name("orgtwo/victim-repo").owner == "orgtwo"`, not `"orgone"`.
7. Assert `assert_difference -> { Shipit::ReviewStack.where(repository: orgtwo_repository).count }` increases by 1 (or that `stack.reload.archived?`/`unarchive!` fired) even though the request was authenticated solely with `OrgOne`'s secret — demonstrating the cross-tenant write with no rejection (current behavior returns `:ok` and performs the mutation; the fix should instead return `:unprocessable_entity`/`422` and perform no mutation).

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
