### Title
Webhook `status` events processed against commits by SHA only, with no repository/stack scoping, allowing repo B's webhook to mutate stack A's commit status - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` looks up commits solely by `Commit.where(sha: params.sha)` with no filter on the repository that the webhook signature verified. Since GitHub `status` webhook signatures are verified per-organization based only on the payload's own `repository.owner.login` (repo B), a webhook whose body only names repo B can still update the status of, and fire `Hook.emit(:commit_status, ...)` for, any `Commit` row across the whole database that happens to share that SHA — including one that belongs to a completely different stack/repository (A).

### Finding Description
The binding that should hold is:
`organization_that_verified_the_webhook_signature (owner of repository named in payload, i.e. repo B) == organization_owning_the_stack/commit_that_gets_mutated (owner of stack A)`

Tracing the path:
1. `WebhooksController#verify_signature` resolves `github_app = Shipit.github(organization: repository_owner)` where `repository_owner` is read straight from the untrusted payload (`params.dig('repository','owner','login')`), then verifies the HMAC using that org's (B's) `webhook_secret`. [1](#0-0) 
2. Once verified, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` dispatches the raw payload without re-checking that the payload's repository owns any resource the handler is about to touch. [2](#0-1) 
3. `StatusHandler#process` does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` — there is no join/filter against `Repository.from_github_repo_name(payload.repository.full_name)` or the handler's own `stacks` helper (which other handlers such as `ClosedHandler`/`ReopenedHandler` *do* use). [3](#0-2) 
4. `Commit#create_status_from_github!` calls `add_status`, which replicates the status, reloads, and if the aggregated status changed, calls `Hook.emit(:commit_status, stack, ...)` using `commit.stack` — i.e., stack A, the victim, regardless of which org's secret authorized the write. [4](#0-3) [5](#0-4) 
5. Because `add_status` also triggers `stack.schedule_merges` when state becomes `pending`/`success`, and `Commit#schedule_continuous_delivery`/`deployable?` factor in `blocking_statuses`/status state, flipping the aggregated status on stack A's commit can unblock `Stack#trigger_continuous_delivery` downstream. [6](#0-5) [7](#0-6) 

Attacker request: an attacker who owns repo B (any GitHub org they control, configured in Shipit with its own `webhook_secret`) creates a commit whose SHA equals an existing commit's SHA in victim stack A (trivial: git SHA1s are content-addressed and independent of the hosting repository, so pushing a commit with identical tree/parent/author/committer/timestamps/message reproduces the same SHA in a different repo — no cryptographic collision required). The attacker then sends `POST /webhooks` with `X-Github-Event: status`, a body whose `repository.full_name`/`repository.owner.login` is repo B, and `sha` set to the shared value, signed with B's own `webhook_secret`. `verify_signature` passes because it only checks B's secret against B's payload. `StatusHandler#process` then updates *every* `Commit` row with that SHA, including stack A's, and fires `Hook.emit(:commit_status, stack_A, ...)`.

None of the existing guards catch this: `verify_signature` only proves possession of B's `webhook_secret`, not authority over any particular commit/stack; `drop_unhandled_event` and the `ExplicitParameters` schema only validate payload shape; there is no `Repository`/`stacks` scoping check inside `StatusHandler`.

### Impact Explanation
An attacker who controls or can push to any repository configured in Shipit (repo B) can forge a `success`/`pending`/`failure` CI status onto an unrelated victim stack's commit (stack A) purely by reproducing the same commit SHA and sending a webhook signed with their own repository's secret. This can flip a commit from blocked to deployable, enabling `stack.schedule_merges` and `Commit#schedule_continuous_delivery` → `Stack#trigger_continuous_delivery`, i.e., a payload for one repository mutating another's commit/stack state and potentially causing an unauthorized deploy. This matches "Critical: a payload for one repository mutating another's stack/commit... or an unauthorized deploy."

### Likelihood Explanation
Preconditions: attacker needs any repository onboarded into Shipit as their own (a common, low-privilege configuration — many Shipit deployments allow many teams/orgs to self-register repos), and the target commit's exact tree/parent/author/committer/timestamp/message to reproduce an identical SHA (achievable via fork/cherry-pick/patch replication, a standard git operation, not a hash collision attack). No Shipit session, API token, or the victim's `webhook_secret` is required. This is realistically repeatable against any stack whose commits' content an attacker can replicate in their own repo.

### Recommendation
Scope `StatusHandler#process` (and any other handler resolving records purely by SHA) to only touch commits whose `stack.repository` matches `Repository.from_github_repo_name(payload.dig('repository','full_name'))`, e.g. `Commit.where(sha: params.sha, stack: stacks... )` using the handler's existing `stacks` helper, mirroring what `ClosedHandler`/`ReopenedHandler` already do.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb`-style):
```ruby
repo_a = Repository.create!(owner: 'victim-org', name: 'repo-a')
repo_b = Repository.create!(owner: 'attacker-org', name: 'repo-b')
stack_a = Stack.create!(repository: repo_a, environment: 'production')
shared_sha = 'a' * 40
commit_a = stack_a.commits.create!(sha: shared_sha, message: 'shared content commit')

payload = {
  'sha' => shared_sha,
  'state' => 'success',
  'context' => 'ci/test',
  'repository' => { 'full_name' => 'attacker-org/repo-b', 'owner' => { 'login' => 'attacker-org' } }
}

Hook.expects(:emit).with(:commit_status, stack_a, has_entries(commit: commit_a)).once

assert_difference -> { commit_a.statuses.count }, 1 do
  Shipit::Webhooks::Handlers::StatusHandler.call(payload)
end
```
Assert both sides of the binding: `payload['repository']['owner']['login'] == 'attacker-org'` while `commit_a.stack.repository.owner == 'victim-org'`, and yet the status/write and `Hook.emit(:commit_status, stack_a, ...)` still occur — proving the divergence.

    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
