### Title
Webhook signature is verified against the organization named in the payload, not the repository the payload actually mutates - allowing cross-organization webhook forgery - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/webhook secret to validate a webhook against using an organization value pulled out of the very payload being verified, and never re-checks that this organization is the one that actually owns the repository the event handlers subsequently act on. In a Shipit deployment configured with multiple GitHub Apps/organizations (a supported configuration, see `test/dummy/config/secrets_double_github_app.yml`), an attacker who legitimately controls one onboarded organization's GitHub App secret can forge a webhook whose `repository.owner.login` matches their own org (so it passes HMAC verification with a secret they legitimately know) while other payload fields (e.g. `repository.full_name`, PR/commit/status data) reference a different, victim organization's stack. This breaks the binding "organization authenticated == repository written."

### Finding Description
`verify_signature` computes the verifying organization purely from attacker-controlled payload content: [1](#0-0) [2](#0-1) 

`repository_owner` is derived from `params.dig('repository', 'owner', 'login')` (falling back to `organization.login`), and this value is used only to pick which `GitHubApp` instance (and thus which `webhook_secret`) to HMAC-verify the raw body against: [3](#0-2) 

Once `verify_signature` succeeds, `create` re-parses the whole raw body and dispatches it to event handlers (`push`, `status`, `check_suite`, `pull_request`, etc.) unmodified: [4](#0-3) 

These handlers use other fields inside the same payload (repository full name, commit SHAs, PR data) to locate and mutate the actual `Stack`/`Commit`/`Repository` records — fields that are never checked for consistency with the `repository.owner.login` value that was used to select the verifying secret. Shipit explicitly supports multiple independently configured GitHub Apps/organizations sharing one instance: [5](#0-4) [6](#0-5) 

Because the webhook secret is looked up by an org name embedded inside the very JSON body being signed, and no code path cross-validates that `repository.owner.login` equals the actual owner of the repository/stack that gets modified (e.g. `repository.full_name`), a user who administers Organization A's GitHub App (and thus legitimately knows Organization A's `webhook_secret`) can:
1. Build a JSON body where `repository.owner.login = "OrgA"` but `repository.full_name = "victim-org/victim-repo"` (and any other event-specific fields targeting a stack under `victim-org`).
2. Compute a valid `X-Hub-Signature` HMAC using Organization A's own secret over that exact body.
3. POST it to `/webhooks`. `verify_signature` resolves `Shipit.github(organization: "OrgA")` and successfully verifies the signature (correct secret, correct raw body) even though the payload's operative content targets `victim-org`'s stack.
4. `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` then processes the forged event (e.g. a `status` event forging a green CI status on a victim commit, or a `push`/`pull_request` event manipulating a victim stack's merge-queue/PR state) using the payload's repository fields, not the organization used for authentication.

This is analogous to the reported loan-creation bug's core failure mode: a field that is *checked* (organization/`loanId` ownership at verification time) is different from the field the system actually *acts upon* (repository/loan record actually mutated), letting an authenticated-but-wrong-scope actor manipulate another party's state.

### Impact Explanation
If exploitable, this allows a user who legitimately administers one onboarded GitHub organization/App on a shared Shipit instance to forge signed-looking webhook events (status, push, pull_request, check_suite) that are processed against a different organization's stack. Depending on the handler reached, this could forge a green commit/CI status that bypasses `ci.require` gating and leads to an unauthorized deploy, or manipulate merge-queue/PR state for a repository the attacker does not control — matching the Critical "unauthorized deploy" impact bucket.

### Likelihood Explanation
Exploitability strictly depends on: (a) the Shipit instance being configured with more than one GitHub App/organization (an explicitly supported and documented configuration), and (b) attacker control over one onboarded org's GitHub App/webhook secret while targeting another onboarded org's stack. I was not able to fully trace the individual event handlers (`push_handler.rb`, `status_handler.rb`, `pull_request/*_handler.rb`) in the time available to confirm that none of them independently re-validate that `repository.owner.login` matches the repository/stack being mutated — this is the main remaining uncertainty. If any handler does perform that cross-check (e.g. by re-deriving the owning organization from the resolved `Stack`/`Repository` record and comparing it to the authenticated org before mutating anything), the practical exploitability would be significantly reduced or eliminated.

### Recommendation
In `verify_signature`, after successfully authenticating the payload against the organization derived from it, re-derive the target `Repository`/`Stack` strictly from trusted, already-persisted association data (not from further unchecked payload fields), and reject the event if the resolved repository's organization does not match the organization whose secret validated the signature. Alternatively, verify the signature independently against every configured GitHub App/secret and require that the winning secret's organization equals the organization owning the repository named in `repository.full_name` before dispatching to handlers.

### Proof of Concept
1. Configure Shipit with two organizations, `OrgA` and `victim-org`, each with its own GitHub App and `webhook_secret` (as supported per `test/dummy/config/secrets_double_github_app.yml`).
2. As the administrator of `OrgA`'s GitHub App (attacker), craft a JSON body such as:
```json
{
  "repository": { "owner": { "login": "OrgA" }, "full_name": "victim-org/victim-repo" },
  "sha": "<victim commit sha>",
  "state": "success",
  "context": "ci/required-check"
}
```
3. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(OrgA_webhook_secret, body)>`.
4. `POST /webhooks` with header `X-Github-Event: status` and the above body/signature.
5. `verify_signature` resolves `Shipit.github(organization: "OrgA")` and validates successfully (correct secret for the exact bytes sent).
6. The `status` handler is invoked with the parsed body, which contains a SHA belonging to `victim-org/victim-repo` — a forged CI status is recorded on a commit outside the organization that authenticated the request, potentially unblocking a gated deploy that requires `ci/required-check` to be green.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
