### Title
Asset spender-attestation check grants permanent access from a single historical attestation, ignoring later revocation - ([File: storage.js])

### Summary
GitLab CVE-2023-0805 allowed a banned group member to retain access to a public group's projects because the ban was not re-checked at the resource-access layer — access was granted based on stale membership state instead of current status. ocore's `spender_attested` asset-restriction mechanism has the same class of flaw: an address is treated as "attested" (and therefore allowed to hold/spend a restricted asset) if it can find **any** historical attestation unit ever posted by a currently-trusted attestor, rather than the attestor's **current/latest** judgement on that address.

### Finding Description
Assets can be created with `spender_attested: true`, which restricts issuance/transfer to addresses that have been vetted by one of the asset's trusted attestors, as recorded in the `asset_attestors` table [1](#0-0) .

When validating a payment against such an asset, `validatePayment` loads the asset together with the list of currently-attested authors/output-addresses via `storage.loadAssetWithListOfAttestedAuthors`, then rejects the unit if the address is not in `objAsset.arrAttestedAddresses`: [2](#0-1) 
and for output addresses: [3](#0-2) 

The actual "is this address attested" check is performed by `filterAttestedAddresses` in `storage.js`: [4](#0-3) 

This query returns an address as attested if **any** row exists in the `attestations` table with `attestor_address IN (current trusted attestor list)` for that address, stable and sequence `good`, and posted after the address's most recent `address_definition_change`. It does **not**:
- limit to the attestor's *latest* attestation for that address, or
- check any "revoked"/"banned" semantics in the attestation `profile` payload.

Contrast this with the AA/oscript `attestation` evaluation primitive, which explicitly orders by `main_chain_index DESC ... LIMIT 1` to pick the *latest* attestation for a given `address`/`field` combination [5](#0-4) . The core-level asset spend-authorization path has no equivalent "take the latest state" logic — it is a pure existence check over the whole attestation history.

Attestation itself has no `revoke` message type; the only way for an attestor to signal that an address's status changed is to publish a new `attestation` unit (e.g., with a `banned: true`/`kyc: false` field) [6](#0-5) , and this is stored as an additional independent row in the `attestations`/`attested_fields` tables [7](#0-6) . Because `filterAttestedAddresses` only checks for *existence* of a qualifying row and never inspects the attested `profile`/field values, the old (now superseded/"banned") attestation row still satisfies the `WHERE` clause. The address therefore remains permanently "attested" for that asset for as long as: (1) the original attestor stays in the asset's trusted-attestor list, and (2) the address's definition (signing keys) is not changed.

The only way to actually cut off access is for the asset definer to remove the attestor entirely from `asset_attestors` via an `asset_attestors` update message — but that de-authorizes *every* address the attestor ever attested, not just the specific banned address, which is not a workable per-user revocation mechanism.

### Impact Explanation
For any asset issued with `spender_attested: true` (a common pattern for regulated/KYC-gated tokens on Obyte), an attestor's attempt to revoke a specific address's clearance (by posting a superseding attestation) has **no effect on core validation**. The originally-attested address can continue to issue, hold, and transfer the restricted asset indefinitely — i.e., unauthorized continued access to asset transfer rights after the issuer/attestor intended to ban it, directly mirroring the "banned member keeps access" class of bug. This can lead to continued spending/transfer of a regulated asset by a party the issuer explicitly intended to exclude, undermining the asset's core compliance guarantee (the entire point of `spender_attested`).

### Likelihood Explanation
High likelihood of occurrence in practice: any legitimate asset issuer using `spender_attested` for compliance purposes and later needing to revoke a specific address (fraud, KYC failure, sanctions, etc.) will hit this exact limitation, since posting a new attestation is the documented/intended mechanism for updating attestation state, but core validation never reads the latest value — it only checks historical existence. No malicious network behavior is required; it is a normal application-level flow that silently fails to enforce revocation.

### Recommendation
Change `filterAttestedAddresses` (and `loadAssetWithListOfAttestedAuthors`) to select only the *most recent* qualifying attestation per (attestor, address) pair (analogous to the `ORDER BY main_chain_index DESC ... LIMIT 1` pattern already used in `formula/evaluation.js`), and define/document a reserved field (e.g., a boolean `revoked`/`banned` field or an explicit `attestation revocation` semantics) that asset-spend validation checks against. Alternatively, introduce a first-class revocation message type so that core validation logic — not just application-level convention — enforces the attestor's latest decision.

### Proof of Concept
1. Define asset `X` with `spender_attested: true` and `attestors: [A]`.
2. Attestor `A` posts `attestation` unit `U1`: `{address: V, profile: {kyc: true}}`. `filterAttestedAddresses` now returns `V` as attested; `V` can issue/transfer asset `X`.
3. Attestor `A` later posts `attestation` unit `U2` (after detecting fraud): `{address: V, profile: {kyc: false, banned: true}}`, intending to revoke `V`'s clearance.
4. `V` posts a new payment message spending/transferring asset `X`. `validatePayment` → `loadAssetWithListOfAttestedAuthors` → `filterAttestedAddresses` still finds row `U1` (attestor `A` ∈ trusted list, `address = V`, stable, sequence good, after `V`'s last definition change) and returns `V` as attested — `U2`'s revoked status is never consulted.
5. The unit validates and is accepted by the network: `V` retains full spend authority over asset `X` despite the attestor's explicit revocation.

Note: this analysis is based on the indexed subset of `storage.js`, `validation.js`, `writer.js`, and `formula/evaluation.js`; if there is additional application-level or wallet-side enforcement of "latest attestation" for `spender_attested` assets elsewhere in the codebase that wasn't surfaced by search, it should be checked in a full Devin session with complete file access.

function filterAttestedAddresses(conn, objAsset, last_ball_mci, arrAddresses, handleAttestedAddresses){
	conn.query(
		"SELECT DISTINCT address FROM attestations CROSS JOIN units USING(unit) \n\
		WHERE attestor_address IN(?) AND address IN(?) AND main_chain_index<=? AND is_stable=1 AND sequence='good' \n\
			AND main_chain_index>IFNULL( \n\
				(SELECT main_chain_index FROM address_definition_changes JOIN units USING(unit) \n\
				WHERE address_definition_changes.address=attestations.address AND main_chain_index<=? AND is_stable=1 AND sequence='good' ORDER BY main_chain_index DESC LIMIT 1), \n\
			0)",
		[objAsset.arrAttestorAddresses, arrAddresses, last_ball_mci, last_ball_mci],
		function(addr_rows){
			var arrAttestedAddresses = addr_rows.map(function(addr_row){ return addr_row.address; });
			handleAttestedAddresses(arrAttestedAddresses);
		}
	);
}
