### Title
Webhook signature is verified against the payload's `repository.owner.login`, but event handlers act on the unrelated `repository.full_name` field, letting an org onboarded to a multi-tenant Shipit instance forge events for another org's repository - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects which GitHub App/webhook secret to use for HMAC verification based on `params.dig('repository', 'owner', 'login')` (falling back to `params.dig('organization', 'login')`), then verifies the raw body against that org's `webhook_secret`. [1](#0-0) [2](#0-1)  Once verified, `Shipit::Webhooks::Handlers::Handler#repository_name` (used by every handler to look up the `Repository`/`Stack` to act on) reads a *different* field of the same payload: `payload.dig('repository', 'full_name')`. [3](#0-2)  Nothing ties `repository.owner.login` to the owner segment of `repository.full_name`; `Repository.from_github_repo_name` simply splits `full_name` on `/` and looks up any repository record by owner/name with no relation to which org's secret validated the request. [4](#0-3) 

### Finding Description
Shipit supports multi-tenant GitHub App configuration, keyed by organization, each with its own independent `webhook_secret` (as illustrated in the sample multi-org secrets file). [5](#0-4)  `Shipit.github(organization:)` looks up the per-organization config and instantiates a `GitHubApp` scoped to that org's secret. [6](#0-5) 

The equality the engine implicitly (and incorrectly) assumes is:
`org whose webhook_secret validated the signature == owner segment of repository.full_name that handlers act on`

Before the attack: for a legitimate GitHub-originated webhook, `repository.owner.login` and the owner portion of `repository.full_name` are always the same value, because GitHub itself populates both fields from the same source repository. The binding holds only because GitHub is trusted to keep the payload internally consistent.

After the attack: an attacker who administers **any** organization onboarded to the same Shipit instance (e.g., they set up their own GitHub App/webhook secret entry for `attacker-org`, which is a legitimate, unprivileged customer of the shared instance with respect to other tenants) can send a POST to `/webhooks` with:
- `X-Hub-Signature` computed with `attacker-org`'s own known `webhook_secret`
- a raw JSON body where `repository.owner.login = "attacker-org"` (so `verify_signature` picks `attacker-org`'s app and the HMAC checks out) but `repository.full_name = "victim-org/victim-repo"`.

`verify_signature` passes because it only ever inspects `owner.login`. [7](#0-6)  The request then reaches `Shipit::WebhooksController#create`, which dispatches to every registered handler for the event with the full parsed payload. [8](#0-7)  Handlers such as `PushHandler`, the `PullRequest::*` handlers, `StatusHandler`, `CheckSuiteHandler`, etc. all resolve their target `Repository`/`Stack` via `repository_name = payload.dig('repository', 'full_name')`, i.e. `victim-org/victim-repo`, and act on it - e.g. `PushHandler#process` calls `stack.sync_github(expected_head_sha: params.after)` for the victim's stacks, and matches on `stacks.not_archived.where(branch:)`. [9](#0-8)  `PullRequest::OpenedHandler`/`ClosedHandler`/`ReopenedHandler` similarly resolve `Repository.from_github_repo_name(params.repository.full_name)` and create/archive/unarchive review stacks belonging to the victim repo. [10](#0-9) [11](#0-10) 

The root cause is that `verify_signature`'s trust decision is bound to one payload field (`repository.owner.login`, or the `organization.login` fallback) while every consumer of the payload is bound to a different, independently-attacker-controlled field (`repository.full_name`), and the controller never asserts these are consistent.

### Impact Explanation
This breaks a cross-tenant trust boundary in a multi-organization Shipit deployment. A tenant that only has legitimate control over its own org's webhook secret can forge webhook events that Shipit will process as if they came from a completely different, victim organization's repository. Concretely this can:
- Trigger `GithubSyncJob`/`sync_github` on victim stacks with attacker-chosen `expected_head_sha`, corrupting the commit history Shipit believes is deployable for the victim, which can influence subsequent (real, human-approved) deploy/rollback decisions.
- Force-close, reopen, or archive/unarchive the victim's `ReviewStack`s and `PullRequest` records via the PR handlers, disrupting or manipulating the merge queue/CI status tracked for repos the attacker has no access to.
- Inject/forge commit `status`/`check_suite` results for the victim repository via `StatusHandler`/`CheckSuiteHandler`, which can gate or unblock deploys and merges based on falsified CI state.

This qualifies as cross-repository, cross-tenant unauthorized write access to another organization's deploy/merge state, matching the "cross-repository writes" / "unauthorized deploy, rollback or merge" impact tier, without requiring any Shipit session, API token, or the victim org's own secret.

### Likelihood Explanation
Exploitability requires only that the attacker control (or be an admin of) one organization already configured as a tenant on the shared Shipit instance — a realistic, documented deployment model (multiple `github:` entries each with their own `webhook_secret`, as shown in the repo's own sample secrets file). No access to the victim's secret, GitHub App, or Shipit session is needed; the attacker only crafts the JSON body and signs it with their own known secret before POSTing to the shared `/webhooks` endpoint.

### Recommendation
In `WebhooksController#verify_signature` (or immediately after, before dispatch), assert that the resolved `github_app`'s organization matches the owner segment of `payload.dig('repository', 'full_name')` (and/or `organization.login`) before invoking handlers; reject with `422` on mismatch. Alternatively, have `Shipit::Webhooks::Handlers::Handler#repository_name` reuse the same field (`repository.owner.login`) that was used for signature selection instead of independently trusting `repository.full_name`.

### Proof of Concept
1. Shipit instance is configured with two tenants: `attacker-org` and `victim-org`, each with its own GitHub App/`webhook_secret` in `secrets.github`.
2. Attacker computes `sha1=HMAC(attacker-org_webhook_secret, body)` for a crafted push payload body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker chosen sha>",
  "repository": {
    "full_name": "victim-org/victim-repo",
    "owner": { "login": "attacker-org" }
  }
}
```
3. POST to `/webhooks` with header `X-Github-Event: push` and `X-Hub-Signature: sha1=<computed>`.
4. `verify_signature` calls `Shipit.github(organization: "attacker-org")` (from `repository_owner`) and verifies successfully against the attacker's own secret. [1](#0-0) 
5. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("victim-org/victim-repo")` and calls `sync_github(expected_head_sha: "<attacker chosen sha>")` on `victim-org`'s stacks, despite the attacker having no relationship to `victim-org` whatsoever. [9](#0-8) [3](#0-2)
