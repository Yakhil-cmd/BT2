### Title
Cross-organization team membership grant via unscoped `github_id` lookup in `MembershipHandler#find_or_create_team!` - ([File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`MembershipHandler#find_or_create_team!` looks up an existing `Team` solely by `params.team.id` (`github_id`), with no check that the payload's `organization.login` matches the team's actual `organization`. Because webhook signature verification is keyed per-organization off attacker-controlled `organization.login` (via `repository_owner` fallback in `WebhooksController#repository_owner`), an attacker who owns a legitimately-configured GitHub organization can sign a forged `membership` `action: added` payload with a guessed `team.id` belonging to a real, unrelated team, causing `team.add_member(member)` to add the attacker's GitHub user to that real team's `memberships`.

### Finding Description
The broken binding: `signed_organization.login (attacker-org, attacker's own secret) == team.organization (bound to the target github_id in Shipit::Team)` should never be assumed true, but the code treats them as if they were.

Path: `WebhooksController#verify_signature` calls `Shipit.github(organization: repository_owner)` where `repository_owner` falls back to `params.dig('organization', 'login')` for membership events [1](#0-0) . This means the webhook is verified against the webhook secret configured for whatever organization login the attacker puts in the payload's `organization.login` field. If the attacker controls (or is a legitimate customer of) a configured GitHub App/organization ("attacker-org"), they can produce a validly-signed payload for that org name while fully controlling the JSON body, including `team.id`, `team.name`, `team.slug`, `member.login`, since these are just JSON fields, not verified against GitHub itself [2](#0-1) .

Once past signature verification, `MembershipHandler#process` calls `find_or_create_team!`, which does `Team.find_or_create_by!(github_id: params.team.id)` [3](#0-2) . The lookup key is only `github_id` — the `organization` field is only assigned inside the `find_or_create_by!` block, which only executes on **creation**, not when an existing record is found. So if a real `Team` already exists (created earlier via a legitimate webhook from the real organization) with `github_id` equal to the attacker's guessed integer, `find_or_create_by!` returns that pre-existing real `Team` object untouched — the attacker's forged `organization.login` never overwrites or is checked against `team.organization`.

`process` then does `team.add_member(member)` where `member` is `User.find_or_create_by_login!(params.member.login)` — i.e., the attacker's own GitHub login [4](#0-3) . `Team#add_member` unconditionally appends the member if not already present [5](#0-4) , writing a `Membership` row binding the attacker's `User` to the real `Team`.

If that `Team` is one of the entries in `Shipit.github_teams`, this directly grants `User#authorized?` (`teams.where(id: Shipit.github_teams.map(&:id)).exists?`) [6](#0-5) , escalating the attacker into the app's authorization group without ever being a real member of the target GitHub org/team.

No existing guard prevents this: `verify_signature` only proves the payload was signed by *some* configured organization's secret, not that the `team`/`organization` referenced in the body actually belongs to that organization; `find_or_create_team!` has no `organization:` scoping in its lookup; `ExplicitParameters` only validates types/presence, not cross-consistency between `organization.login` and the `team` object.

Regarding the response-code oracle claimed in the question: both the "hit" (existing team match) and "miss" (new team created) paths return `head(:ok)` (200) from `WebhooksController#create` regardless of outcome — `add_member` and the `find_or_create_by!` creation branch both succeed silently, so the HTTP status itself does not differentiate a hit from a miss. This detail in the question is not accurate as a literal oracle, but it does not change the underlying vulnerability: the core exploit (blind brute-forcing team `github_id`s, each attempt returning 200 either way, until one lands on a real team and grants persistent membership) is still valid and does not require the response code to succeed — the attacker can detect success out-of-band (e.g., checking their own resulting authorization/team memberships in Shipit's UI/API) once granted.

### Impact Explanation
A successful guess causes a `Membership` record to be created binding an attacker-controlled `User` to a real `Team` that the attacker does not belong to on GitHub. If that team is configured in `Shipit.github_teams`, the attacker becomes `authorized?` in Shipit, which is used for deploy/stack authorization gates elsewhere in the app. This is a genuine authorization-bypass into `Shipit.github_teams`, matching the High severity category ("escalation into `Shipit.github_teams` authorization"). It is repeatable across any organization the attacker can get validly signed (their own configured org) against any numeric `github_id` in existence, and the membership persists until manually removed.

### Likelihood Explanation
Preconditions: the attacker must own/control a GitHub organization that is already configured in Shipit's `github_apps`/`secrets` (i.e., has a valid `webhook_secret` for that org) — this is the same precondition required by the sibling cross-org binding issue. GitHub team IDs are global sequential integers, making them guessable/brute-forceable in a modest range. Given that precondition, the attack costs only crafting arbitrary HTTP POSTs with a correctly computed HMAC-SHA1 signature using the attacker's own known secret — no other secret material is required. This is feasible and fully repeatable.

### Recommendation
Scope the team lookup by both `github_id` and the verified organization, e.g. `Team.find_or_create_by!(github_id: params.team.id, organization: params.organization.login)`, or explicitly reject the event if an existing `Team` with that `github_id` has a different `organization` than the payload. More fundamentally, `WebhooksController#verify_signature` should validate that the organization used to select the webhook secret actually matches every organization-scoped resource referenced inside the payload it authorizes.

### Proof of Concept
Minitest plan (webhooks controller / membership handler test):
1. Seed `Shipit.github_teams`-eligible `Team` with `github_id: 555`, `organization: 'real-org'`, `slug: 'real-team'`.
2. Configure a second organization `'attacker-org'` in `secrets.test` with its own `webhook_secret`.
3. Build a `membership` payload: `{ action: 'added', team: { id: 555, name: 'x', slug: 'x', url: 'x' }, organization: { login: 'attacker-org' }, member: { login: 'attacker-user' } }`.
4. Sign it with `attacker-org`'s webhook secret, POST to `/webhooks` with `X-Github-Event: membership`.
5. Assert response is 200 (`head :ok`).
6. Assert `Shipit::Team.find_by(github_id: 555).organization == 'real-org'` (unchanged — confirms found not created).
7. Assert `Shipit::Team.find_by(github_id: 555).members.exists?(login: 'attacker-user')` is `true` — proving cross-org membership grant.
8. Assert `Shipit::User.find_by(login: 'attacker-user').authorized?` is `true` if that team is in `Shipit.github_teams`.

Binding checked before/after: `params.organization.login ('attacker-org') != Shipit::Team#organization ('real-org')` before the request, and this inequality is never checked by `find_or_create_team!`, yet the membership write still succeeds — confirming the vulnerability.
