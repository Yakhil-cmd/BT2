I searched for analogous "permissive filter takes precedence over restrictive filter" patterns across FRAME's origin filtering (`RuntimeOrigin::add_filter`/`filter_call`), XCM barrier combinators (`DenyThenTry`, `AllowExplicitUnpaidExecutionFrom`), `pallet-proxy`'s `InstanceFilter`, and `pallet-safe-mode`'s `is_allowed`/`WhitelistedCalls`. In every case examined, filters compose with AND semantics or are structured so a more permissive component cannot silently override a more restrictive one:

- `RuntimeOrigin::filter_call` combines filters via `f(call) && filter(call)` in `add_filter`, and only `Root` bypasses filtering entirely — there's no `allow_all`-style flag that supersedes a narrower filter unintentionally. [1](#0-0) 
- XCM's `DenyThenTry<Deny, Allow>` always evaluates `Deny::deny_execution` first and returns an error before ever reaching `Allow`, so an `AllowAll` cannot bypass an active deny rule. [2](#0-1) 
- `pallet-proxy`'s `do_proxy` layers an additional origin filter restricting privilege escalation on top of `ProxyType::filter`, rather than allowing a broader proxy type to implicitly bypass a narrower one. [3](#0-2) 
- `pallet-safe-mode`'s `is_allowed` only exempts the `SafeMode` pallet's own calls; when entered, everything else is checked against `WhitelistedCalls`, with no separate "allow all" toggle that could silently override this restriction. [4](#0-3) 

I found no reachable, unprivileged user entry point where a broad "allow all" configuration option is documented/intended to be combined with a narrower restriction (like the JupyterHub `allow_all` + `identity_provider` case) but ends up silently taking precedence due to an ordering/precedence regression. This bug class (a config-composition precedence flaw) does not have a demonstrable analog with exact file:line evidence and a working boundary reproduction in this codebase.
