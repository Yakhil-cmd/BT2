### Title
Unbounded memory allocation via snappy decompression bomb in bundle fetch - ([File: pkg/cmd/attestation/api/client.go])

### Summary
`(*LiveClient).getBundle` reads the entire `BundleURL` response body with `io.ReadAll` and then calls `snappy.Decode(out, body)` with no size limits at either step. Because the attacker fully controls the bytes served from `BundleURL` (their own attestation bundle blob), they can craft a highly compressible snappy stream whose header declares an enormous decoded length, causing the client to allocate an oversized buffer and consume excessive memory/CPU when a victim runs an attestation-fetching `gh` command against that content.

### Finding Description
The relevant code path is: [1](#0-0) 

`resp.Body` is read fully into memory via `io.ReadAll` with no `io.LimitReader` or `Content-Length` cap, and the resulting bytes are handed directly to `snappy.Decode(out, body)` with `out` set to `nil`, letting the snappy decoder allocate a buffer sized according to the length header embedded in the attacker-supplied compressed stream. There is no validation of the declared/decoded length against a sane maximum before or after this call, and no context/goroutine-level memory or time budget is enforced around the decompression. `fetchBundleFromAttestations` invokes `getBundle` in a goroutine per attestation via `errgroup.Group`, so a response with multiple malicious attestations can multiply the effect: [2](#0-1) .

`BundleURL` originates from the GitHub attestations API response field `bundle_url` ( [3](#0-2) ), and the question's precondition states the attacker controls the bytes served from that URL (i.e., they control the content of the attestation bundle stored on their own repository's artifact). Nothing in `getBundle` or in `safeurl` mitigates payload size or decompressed size — `safeurl` only validates/normalizes the URL/host, not response body size.

### Impact Explanation
This is a denial-of-service condition against the victim's local `gh` process: a crafted small snappy payload with an inflated decoded-length header can force a large memory allocation (and copy-expansion CPU work) inside `snappy.Decode`, potentially exhausting memory or causing the `gh` process to be OOM-killed or hang while verifying attestations for an attacker-controlled artifact/repo. This matches the "denial of service on victim host" impact class described in the question — it is a local process-level DoS triggered by content the victim fetches when running standard `gh attestation verify`-style commands against attacker-published content.

### Likelihood Explanation
Feasible and repeatable: any attacker who can publish a repository/artifact with an attestation whose bundle blob is a crafted snappy stream can trigger this whenever a victim runs `gh` to fetch/verify that attestation. No privileged access, MITM, or social engineering is required — only that the victim inspects attacker-published attestations, which is the intended use case for `gh attestation verify`.

### Recommendation
- Wrap `resp.Body` in `io.LimitReader` with a reasonable maximum bundle size before `io.ReadAll`, and treat truncation/oversized bodies as an error.
- Avoid calling `snappy.Decode` with an unbounded implicit allocation: use `snappy.DecodedLen(body)` to check the claimed decoded size against a hard cap (e.g., a few MB, consistent with expected sigstore bundle sizes) before allocating `out` and calling `snappy.Decode(out, body)`.
- Apply the same cap check uniformly regardless of concurrency (each goroutine in `fetchBundleFromAttestations` should respect the same limit) to avoid multiplicative memory pressure from multiple attestations in a single response.

### Proof of Concept
Go test using `httpmock`/a local test server:
1. Start an `httptest.Server` that responds to `GET /bundle` with a crafted snappy stream: a snappy block header (varint) declaring a decoded length of e.g. `4 GiB`, followed by minimal encoded data (a single large "copy" op referencing a small literal, as permitted by the snappy format) — a classic small-input/large-output decompression bomb.
2. Construct a `LiveClient` with `externalHttpClient` pointed at this test server, and call `c.getBundle(safeurl.NewImmutableSafeURL(testServer.URL + "/bundle"))`.
3. Assert that memory usage (`runtime.MemStats.Alloc` before/after) spikes far beyond the compressed payload size, or that the call fails only after excessive allocation/time, demonstrating no size-cap enforcement exists prior to `snappy.Decode`.
4. Compare against expected behavior after the fix: `getBundle` should return an error quickly (e.g., "bundle exceeds maximum allowed size") without attempting the large allocation, verified via the same memory/time measurement showing bounded resource use.

func (c *LiveClient) fetchBundleFromAttestations(attestations []*Attestation) ([]*Attestation, error) {
	fetched := make([]*Attestation, len(attestations))
	g := errgroup.Group{}
	for i, a := range attestations {
		g.Go(func() error {
			if a.Bundle == nil && a.BundleURL == "" {
				return fmt.Errorf("attestation has no bundle or bundle URL")
			}

			// for now, we fall back to the bundle field if the bundle URL is empty
			if a.BundleURL == "" {
				c.logger.VerbosePrintf("Bundle URL is empty. Falling back to bundle field\n\n")
				fetched[i] = &Attestation{
					Bundle: a.Bundle,
				}
				return nil
			}

			// otherwise fetch the bundle with the provided URL
			b, err := c.getBundle(safeurl.NewImmutableSafeURL(a.BundleURL))
			if err != nil {
				return fmt.Errorf("failed to fetch bundle with URL: %w", err)
			}
			fetched[i] = &Attestation{
				Bundle: b,
			}

			return nil
		})
	}
