### Title
Address definition changes can be silently bundled inside multi-message shared-address signing requests, enabling unnoticed takeover of a multisig address - ([File: wallet.js])

### Summary
Core ocore has no restriction preventing an `address_definition_change` message from being combined with other, innocuous-looking messages (e.g. a `payment`) inside the same unit. When a shared/multisig address must be co-signed by multiple devices, the wallet's cosigning confirmation logic in `getSigner().sign` only inspects the unit for prosaic/arbiter-contract-specific patterns to decide which popup to show; it never singles out or specially warns about the presence of a definition-change message. This mirrors the reported Governor/Timelock issue: a sensitive, control-changing operation can be smuggled inside a batch that the reviewing party (the other cosigner) approves without noticing, permanently altering who controls the shared address.

### Finding Description
`validateInlinePayload`'s handling of `address_definition_change` only enforces that there is at most one such message per address in a unit; it imposes no restriction that prevents it from being combined with arbitrary other messages such as a normal payment: [1](#0-0) 

When a device needs another cosigner's signature for a shared address, the wallet computes the signature confirmation UX purely from heuristics about prosaic/arbiter-contract deposit amounts; there is no branch that inspects `objUnsignedUnit.messages` for an `address_definition_change` app and forces a distinct, mandatory, explicit warning before signing: [2](#0-1) 

The generic fallback simply emits `confirm_on_other_devices`, treating a unit that redefines control of the shared address exactly the same as an everyday payment cosigning request: [3](#0-2) 

Once such a unit is fully signed under the *current* definition and becomes stable, `address_definition_change` immediately and irrevocably changes the authentication rules for future spends from that address: [4](#0-3) [5](#0-4) 

A malicious cosigner of a jointly-controlled/shared address (e.g., one party of a 2-of-2 shared address created for an escrow, arbiter contract, or any custom multisig application) can construct a unit that:
1. Contains a normal-looking payment message (e.g., paying a merchant, or depositing into the shared address) that the innocent cosigner expects to review casually.
2. Also contains an `address_definition_change` message that redefines the shared address's definition (e.g., to a `sig` definition using only the attacker's key, or lowering an `r of set` multisig threshold to 1).

Because the wallet code does not flag or block this combination and does not force a dedicated, unmissable prompt for definition changes distinct from ordinary payments, the innocent cosigner may sign the bundle believing they are only approving a payment. This is directly analogous to Eve's proposal in the Timelock report: a dangerous administrative action (redefining who controls the address) hidden inside an otherwise unremarkable batch that the reviewer approves without noticing.

### Impact Explanation
If the innocent cosigner signs, the shared address's definition is permanently changed. The attacker gains unilateral (or disproportionate) control over all current and future funds and any assets held by that shared address, resulting in unauthorized spending / permanent loss of the honest party's control of jointly-owned funds - a concrete fund-loss/unauthorized-spending outcome, analogous to the admin takeover in the original report.

### Likelihood Explanation
Exploitation requires the attacker to already be a legitimate cosigner of a shared/multisig address (a role reachable by any counterparty in escrow, prosaic contracts, arbiter contracts, or manually created shared addresses) and for the counterparty to review the signing request without independently decoding and checking every message. Since the wallet's own confirmation logic makes no special distinction for `address_definition_change`, the honest party has no client-provided safeguard flagging this specific danger, making the social-engineering step plausible in real usage (e.g., presented as a routine deposit/settlement transaction).

### Recommendation
- At the core validation layer, forbid an `address_definition_change` message from being combined with any other message type in the same unit (mirroring the short-term Timelock fix of disallowing `setPendingAdmin` inside a general proposal), or at minimum require it to be the sole message when the address is a multi-signer/shared address.
- In `wallet.js`'s `getSigner().sign` cosigning flow, add an explicit, dedicated, non-suppressible confirmation (separate from `confirm_on_other_devices`) whenever `objUnsignedUnit.messages` contains an `address_definition_change`, clearly displaying the old vs. new definition to the cosigner before any signature is requested.

### Proof of Concept
1. Alice and Bob create a 2-of-2 shared address `S` via `wallet_defined_by_addresses.createNewSharedAddress`.
2. Bob (attacker) composes a unit with two messages targeting `S`: (a) a normal `payment` message paying some address (framed as "settling the escrow"), and (b) an `address_definition_change` message setting `S`'s new definition to `['sig', {pubkey: Bob_pubkey}]`.
3. Bob requests Alice's signature via the `sign` device message (`wallet.js`, case `"sign"`).
4. Alice's client, per `getSigner().sign`, does not recognize the `address_definition_change` message as special and only shows a generic `confirm_on_other_devices` prompt (or none of the contract-specific prompts apply).
5. Alice signs, believing she is only approving a routine payment.
6. The unit stabilizes; `writer.js` records the new `definition_chash` for `S` in `address_definition_changes`, and `storage.readDefinitionChashByAddress` now returns Bob's sole-signature definition.
7. Bob now unilaterally controls all funds at `S` going forward, having effectively taken over the shared address the same way Eve took over the Timelock admin role.

function readDefinitionChashByAddress(conn, address, max_mci, handle){
	if (!handle)
		return new Promise(resolve => readDefinitionChashByAddress(conn, address, max_mci, resolve));
	if (max_mci == null || max_mci == undefined)
		max_mci = MAX_INT32;
	// try to find last definition change, otherwise definition_chash=address
	conn.query(
		"SELECT definition_chash FROM address_definition_changes CROSS JOIN units USING(unit) \n\
		WHERE address=? AND is_stable=1 AND sequence='good' AND main_chain_index<=? ORDER BY main_chain_index DESC, level DESC LIMIT 1", 
		[address, max_mci], 
		function(rows){
			var definition_chash = (rows.length > 0) ? rows[0].definition_chash : address;
			handle(definition_chash);
	});
}
