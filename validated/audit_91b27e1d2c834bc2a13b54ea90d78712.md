### Title
Unscoped `Commit.where(sha:)` lookup in `StatusHandler#process` lets a webhook authenticated for one repository write GitHub status records onto commits belonging to any other stack sharing the same SHA - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` looks up commits purely by `params.sha`, with no filter on the repository that authenticated the webhook, unlike every other handler in the same namespace (e.g. `PullRequest::ClosedHandler`, `PullRequest::EditedHandler`) which explicitly scope their lookups via `Repository.from_github_repo_name(params.repository.full_name)`. Because the `commits` table is only indexed/scoped per `stack_id` (not globally unique per SHA), any two stacks — including stacks backed by entirely different GitHub repositories/orgs — can contain a `Commit` row with an identical `sha` (e.g. a fork, a mirrored/mono-repo commit, or any commit whose content the attacker can reproduce). A webhook that GitHub-authenticates for repository A therefore writes a status onto repository B's commit as well.

### Finding Description
The broken binding is: `webhook.repository_owner/full_name == commit.stack.repository.full_name` for every commit mutated by the handler. `StatusHandler#process` breaks this:

```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [1](#0-0) 

`Commit.where(sha: params.sha)` is a table-wide query with no join/filter on `stack_id`/repository, unlike the base `Handler#stacks` helper (`Repository.from_github_repo_name(repository_name)&.stacks`) that other handlers use to scope their side effects: [2](#0-1) 

`WebhooksController#verify_signature` only authenticates that the payload's signature matches the GitHub App/org secret for `repository_owner` in the payload; it says nothing about which commit SHAs that org/repo is allowed to write status against: [3](#0-2) 

Because `db/migrate/20170524104615_index_commits_on_stack_id_and_sha.rb` scopes SHA uniqueness to `stack_id`, the same SHA can legitimately exist as separate `Commit` records under unrelated stacks (forks, mirrors, or any commit whose exact tree/parents/author/committer/date the attacker reproduces). `create_status_from_github!` then calls `add_status`, which recomputes `status`, and `Commit#blocked?`/`#deployable?` derive directly from the stack's `blocking_statuses`/status state: [4](#0-3)  and toggling status also triggers `stack.schedule_merges` and `ContinuousDeliveryJob`: [5](#0-4) 

Attack: the attacker owns/controls a GitHub repository (or organization) whose webhook the app trusts for that repo (this is the normal case — any repo added to Shipit, or any repo under an org configured in `Shipit.github`), pushes/produces a commit whose SHA matches a commit already present in the victim's stack (fork of victim repo, or reproducing identical git-object content), then sends a `status` webhook with `context: ci/smoke`, `state: failure` for that SHA. Because `verify_signature` only checks the org secret for the attacker's own repository — which validly passes — the request is accepted, and `StatusHandler` writes the failing status onto every `Commit` row with that SHA, including the victim's, flipping `blocked?`/`deployable?` for the victim stack.

### Impact Explanation
A payload authenticated for the attacker's own repository mutates commit/status state belonging to a different stack/repository that never authenticated it. If the victim stack has `blocking_statuses` configured, the injected `failure` status can flip `Commit#blocked?` to true, blocking deploys/merges for legitimate, already-green commits (denial of shipping), or — depending on state ordering and prior statuses — clear a stale failing state and unblock a deploy path prematurely. This is a cross-tenant state write against `Shipit::Status`/`Commit` records not owned by the attacker's authenticated repository, matching the Critical category "a payload for one repository mutating another's stack, commit ... record."

### Likelihood Explanation
Preconditions: attacker needs a GitHub repository (their own, or any public repo) wired into the same Shipit instance (or any org configured under `Shipit.github`) so their webhook signature validates, plus a commit whose SHA coincides with one tracked in a victim stack (trivially achievable via forking the victim repo — forked commits keep identical SHAs — or any repo mirroring/rebasing onto the same upstream history) and a victim stack configured with `blocking_statuses`. This requires no privileged Shipit role, no session, no API token — only the ability to add a repository to Shipit's webhook config (or exploit a repo already tracked) and send an HTTP POST. It is repeatable against any victim stack sharing commit history with an attacker-reachable repository.

### Recommendation
Scope `StatusHandler#process` to the repository that authenticated the webhook, e.g. use the base `Handler#stacks` helper (`Repository.from_github_repo_name(payload.dig('repository','full_name'))&.stacks`) and restrict `Commit.where(sha: params.sha, stack: stacks)` (or join through `stack.repository`) before calling `create_status_from_github!`, mirroring the pattern already used in `PullRequest::ClosedHandler`/`EditedHandler`.

### Proof of Concept
minitest plan (add to `test/models/webhooks/handlers/status_handler_test.rb` or similar):
1. Create two stacks `stack_a` (repository `attacker/repo`) and `stack_b` (repository `victim/repo`), `stack_b` configured with `blocking_statuses: ['ci/smoke']` (via stubbed `DeploySpec`).
2. Create `Commit` rows with the identical `sha: 'deadbeef...'` under both `stack_a` and `stack_b`, with `stack_b`'s commit currently `success?`/deployable (`blocked?` == false).
3. Build a `status` webhook payload for `repository: attacker/repo`, `sha: 'deadbeef...'`, `context: 'ci/smoke'`, `state: 'failure'`.
4. Assert before: `stack_b.commits.find_by(sha: sha).blocked?` == false, `deployable?` == true.
5. Invoke `Shipit::Webhooks::Handlers::StatusHandler.call(payload)` (or POST to `/webhooks` with a valid signature for `attacker/repo`).
6. Assert after: `stack_b.commits.find_by(sha: sha).blocked?` == true (or `deployable?` flips), proving the attacker-authenticated payload for `attacker/repo` mutated `stack_b`'s commit state despite never authenticating for `victim/repo`.
