### Title
Webhook signature is verified against `repository.owner.login`, but the acted-upon commit/repository is taken from unrelated payload fields — allowing cross-repository status forgery and unauthorized merges - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` authenticates a webhook by looking up the GitHub App/organization to use for HMAC verification from `repository.owner.login` (or `organization.login`), then verifies the raw payload against that org's `webhook_secret`. However, the handlers that actually mutate state (`StatusHandler`, `Handler#repository_name`) read *different* fields from the same JSON body (`sha`, and `repository.full_name`) to decide what to write, without ever checking that those fields belong to the same organization/repository that was used to authenticate the request. This breaks the equality "organization that authenticated the webhook == repository/commit that is written," letting a request validly signed by one (weakly secured or secret-less) organization write state — including fabricated CI "success" statuses — for commits belonging to a completely different, unrelated repository tracked by the same Shipit instance.

### Finding Description
`verify_signature` derives the signing organization purely from payload content: [1](#0-0) [2](#0-1) 

`GitHubApp#verify_webhook_signature` explicitly treats a missing `webhook_secret` as "always verified": [3](#0-2) 

Shipit natively supports multiple organizations configured under one instance, each with its own (optional) `webhook_secret`: [4](#0-3) 

Once `verify_signature` passes (using the org derived from `repository.owner.login`/`organization.login`), the actual handlers never re-check that binding:

- `StatusHandler#process` looks up commits **globally by sha**, with no repository/organization scoping at all: [5](#0-4) 

- Other handlers (`PushHandler`, `PullRequest` handlers) scope by `repository.full_name`, a field independent from `repository.owner.login`/`organization.login` used for signature verification: [6](#0-5) [7](#0-6) 

The status a `StatusHandler` writes is later trusted, unauthenticated with GitHub, to gate the merge queue: [8](#0-7) [9](#0-8) 

And `MergeRequest#merge!` performs a real, authenticated GitHub write using Shipit's own credentials once `all_status_checks_passed?` returns true: [10](#0-9) 

**Binding broken (as an equality):**
`organization authenticated by verify_signature (repository.owner.login / organization.login)` **≠** `repository/commit actually written to (sha / repository.full_name used by handlers)`.

Because nothing enforces that the org used to pick the HMAC secret matches the repository/commit the handler subsequently mutates, a payload can be legitimately signed under Org A's secret (or under an org whose `webhook_secret` is unset, which is a fully supported configuration that returns `true` unconditionally) while claiming a `sha`/`full_name` belonging to Org B's tracked repository.

### Impact Explanation
This crosses the "unauthorized deploy/rollback/merge" and "cross-repository writes" impact bar (Critical): an attacker who can get any one signed webhook accepted (trivially satisfied for any org configured with no `webhook_secret`, which the codebase explicitly treats as valid) can:
1. Inject a fabricated `state: 'success'` status for any known commit `sha` belonging to a totally different, unrelated tracked repository via `StatusHandler`, which is not scoped by organization or repository at all.
2. That forged status is stored as a local `Status` and consumed by `MergeRequest#all_status_checks_passed?`/`reject_unless_mergeable!` without any re-verification against GitHub's actual check state.
3. When `ProcessMergeRequestsJob` runs, `MergeRequest#merge!` performs a real GitHub API merge (`stack.github_api.merge_pull_request`) using Shipit's own GitHub App/OAuth credentials, causing an unauthorized merge of a pull request that never actually passed CI, in a repository/organization the attacker had no legitimate authorization over.

### Likelihood Explanation
Likelihood depends on deployment configuration: any organization tracked by the Shipit instance whose `webhook_secret` is left unset (a documented, supported, non-default-enforced option) gives an unprivileged internet attacker unconditional signature bypass for that organization's identity, which is sufficient to reach the unscoped `StatusHandler` write path against every other tracked repository's commits. Because commit SHAs are generally public (visible on GitHub, in Shipit's own UI/API, or via CI logs), guessing/obtaining a target `sha` is not a meaningful barrier.

### Recommendation
- In `StatusHandler#process` (and any handler that doesn't already do so), scope the lookup to `Repository.from_github_repo_name(payload.dig('repository', 'full_name'))`'s stacks/commits rather than a bare, cross-tenant `Commit.where(sha: ...)`.
- In `WebhooksController#verify_signature` / `Handler`, assert that the organization/owner used to select the webhook secret is identical to the owner implied by `repository.full_name` before dispatching to handlers, rejecting mismatches with `422`.
- Consider making `webhook_secret` mandatory (removing the `return true unless webhook_secret` bypass in `GitHubApp#verify_webhook_signature`) so an unconfigured secret fails closed instead of open.

### Proof of Concept
Given a Shipit instance tracking `org-a/repo1` (with `webhook_secret: nil`) and `org-b/repo2` (properly secured), an attacker can:
```
POST /webhooks
X-Github-Event: status
X-Hub-Signature: sha1=anything   # accepted because org-a has no webhook_secret configured
Body:
{
  "sha": "<known commit sha belonging to org-b/repo2's pending PR head>",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "org-a" }, "full_name": "org-a/repo1" }
}
```
- `verify_signature` resolves `repository_owner = "org-a"`, calls `Shipit.github(organization: "org-a")`, and `verify_webhook_signature` returns `true` unconditionally since `org-a`'s `webhook_secret` is blank.
- `StatusHandler#process` runs `Commit.where(sha: params.sha)`, which matches the commit in `org-b/repo2` (no repository scoping), and calls `commit.create_status_from_github!(params)` marking it `success`.
- On the next `ProcessMergeRequestsJob` run, `org-b/repo2`'s pending merge request now reports `all_status_checks_passed?` as true and is merged via `stack.github_api.merge_pull_request` using Shipit's real GitHub credentials — an unauthorized merge into a repository the attacker never had access to.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
    def perform(stack)
      merge_requests = stack.merge_requests.to_be_merged.to_a
      merge_requests.each do |merge_request|
        merge_request.refresh!
        merge_request.reject_unless_mergeable!
        merge_request.cancel! if merge_request.closed?
        merge_request.revalidate! if merge_request.need_revalidation?
      end

      return false unless stack.allows_merges?

      merge_requests.select(&:pending?).each do |merge_request|
        merge_request.refresh!
        next unless merge_request.all_status_checks_passed?

        begin
          merge_request.merge!
        rescue MergeRequest::NotReady
          ProcessMergeRequestsJob.set(wait: 10.seconds).perform_later(stack)
          return false
        end
      end
```
