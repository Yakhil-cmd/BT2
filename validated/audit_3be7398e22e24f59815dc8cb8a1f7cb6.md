### Title
Stack-scoped API client tokens bypass their `stack_id` restriction in the CCMenu endpoint - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Shipit::Api::CCMenuController` overrides the base `stack` accessor with an unscoped lookup, so an `ApiClient` token that is authorized (via `stack_id`) for only one stack can be used to read the build/deploy status of any other stack in the installation, breaking the "stack a token authorizes" vs "stack it touches" binding.

### Finding Description
`ApiClient` records can be scoped to a single stack via `belongs_to :stack, optional: true` / `stack_id` [1](#0-0) . `Api::BaseController` enforces this scoping through its `stacks`/`stack` helpers, which restrict lookups to `Stack.where(id: current_api_client.stack_id)` whenever the authenticated client has a `stack_id` set: [2](#0-1) 

Every other API resource controller (e.g. `Api::CommitsController`, `Api::StacksController#show`) relies on this scoped `stack` helper, which is confirmed by the test "an api client scoped to a stack will only see that one stack" [3](#0-2) .

However, `Api::CCMenuController` redefines `stack` to bypass this scoping entirely, performing an unscoped `Stack.from_param!(params[:stack_id])` lookup instead of using the scoped `stacks` relation: [4](#0-3) 

The controller only checks the coarse `read:stack` permission via `require_permission :read, :stack` [5](#0-4) , and `check_permissions!` only validates that the operation/scope string is in the client's `permissions` array — it never checks `stack_id` [6](#0-5) . As a result, any token with `read:stack` permission — even one created specifically for a single stack (e.g. the CCMenu client auto-created per-stack in `CCMenuUrlController`, which grants `read:stack` [7](#0-6) ) — can query `GET /api/stacks/*stack_id/ccmenu` for **any** `stack_id`, not just the one it was scoped to.

The binding broken: `current_api_client.stack_id` (the stack the token authorizes) ≠ the `stack_id` param the controller actually renders data for.

### Impact Explanation
This is a scope-escalation vulnerability: a token that a user intentionally provisioned/handed out for exposure of a single stack's build status (e.g. embedded into a CI dashboard widget, shared with a third party, or leaked) can be replayed against the `/api/stacks/*stack_id/ccmenu` endpoint for arbitrary stacks in the Shipit installation, exposing their name, last build status, last build label/time, lock state, and deploy/rollback history — cross-stack unauthorized read of stack state. This matches the "High" impact category (unauthenticated/unauthorized read of stack state) since the compromise of a narrowly-scoped credential grants broad read access far beyond its intended authorization boundary.

### Likelihood Explanation
Exploitation only requires possession of any valid `ApiClient` token with `read:stack` permission (regardless of its intended `stack_id` scope) and knowledge/guessing of another stack's `owner/repo/environment` path — no additional privilege is required, and the request is a simple unauthenticated-style GET once the caller has any valid basic-auth token. This is straightforward to exploit for anyone who has legitimately obtained a scoped, low-privilege CCMenu token (these are routinely distributed to external CI-status widgets).

### Recommendation
Change `Api::CCMenuController#stack` to reuse the scoped `stacks` helper from `BaseController` (i.e. `stacks.from_param!(params[:stack_id])`) instead of the unscoped `Stack.from_param!`, so that clients with a `stack_id` restriction cannot query stacks outside their authorized scope.

### Proof of Concept
1. Create (or obtain) an `ApiClient` scoped to `stack_id = A` with `permissions: ["read:stack"]` (e.g., via `CCMenuUrlController#fetch` for stack A, which auto-creates such a client) [7](#0-6) .
2. Using that token's `authentication_token` as HTTP Basic auth, send:
   `GET /api/stacks/<owner>/<other-repo>/<other-environment>/ccmenu`
   for a *different* stack B that the client was never authorized for.
3. `authenticate_api_client` succeeds (valid token) and `require_permission :read, :stack` passes because the client has `read:stack` in `permissions` [6](#0-5) .
4. `CCMenuController#stack` resolves stack B via the unscoped `Stack.from_param!(params[:stack_id])` [8](#0-7) , and the controller renders stack B's CCMenu XML (name, last build status/label/time, lock state) even though the token was never granted access to stack B.
