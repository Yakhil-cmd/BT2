### Title
Webhook Signature Verification Is Keyed to `repository.owner.login`, Not to the `repository.full_name` the Handlers Actually Act On - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/webhook secret to use for HMAC verification based on `repository.owner.login` (or `organization.login`) taken from the raw, attacker-supplied payload. Once verification passes, the webhook body is handed unchanged to the event handlers, which resolve the actual `Repository`/`Stack` to write to using a completely different field of the same payload — `repository.full_name`. No code ever asserts that these two fields refer to the same repository/organization, exactly mirroring the Solana `handle_spl` bug where the whitelist check is bound to `mint_account` while the actual transfer is bound to `from`/`token_program`.

### Finding Description
Signature/organization selection: [1](#0-0) [2](#0-1) 

The organization whose secret is used for verification is `repository_owner`, computed purely from the JSON body (`params.dig('repository','owner','login')` or `params.dig('organization','login')`) — a value fully controlled by whoever is sending the HTTP POST.

Signature check itself trusts the caller unconditionally when no secret is configured for that resolved organization: [3](#0-2) 

Once `verify_signature` passes (which it always does for any org resolved to a `GitHubApp` instance with `webhook_secret` blank/nil), `create` dispatches the entire payload to the handlers: [4](#0-3) 

The handlers, however, determine which `Repository`/`Stack` to act on using a *different* field, `repository.full_name`, with no cross-check against `repository.owner.login`/`organization.login` used above: [5](#0-4) 

`Repository.from_github_repo_name` simply splits `full_name` on `/` and looks the record up directly: [6](#0-5) 

For push events, the resolved stacks are synced with an attacker-supplied `after` SHA: [7](#0-6) 

**Broken binding:** `organization authenticated` (`repository.owner.login`/`organization.login`, used to pick the `GitHubApp`/secret in `verify_signature`) must equal `repository written` (`repository.full_name`, used by `Handler#repository_name`/`Repository.from_github_repo_name` to select the `Stack` that is mutated). The engine never enforces this equality.

### Impact Explanation
If any onboarded GitHub organization in `Shipit.github` config has no `webhook_secret` set (the config schema explicitly allows this — see `webhook_secret: nil` in `test/dummy/config/secrets.yml` and the optional wording in `docs/setup.md`), `verify_webhook_signature` returns `true` unconditionally for a payload whose `repository.owner.login`/`organization.login` names that org — regardless of the actual signature header. An attacker can then set `repository.full_name` to any *other* onboarded repository (e.g., under a fully-secured organization) in the same payload. The handler layer resolves and mutates the `Stack` for that unrelated `full_name`, e.g. enqueuing `GithubSyncJob` with an attacker-chosen commit SHA (`push_handler.rb:16`), which can advance/lock/deploy state for a repository the attacker was never authenticated against — a cross-repository write triggered without any credential tied to the victim repository's organization.

### Likelihood Explanation
Requires only: (1) a Shipit deployment onboarding more than one GitHub org (documented multi-org setup) where at least one org's `webhook_secret` is left unset, and (2) a single unauthenticated HTTP POST to the public `/webhooks` endpoint with a crafted JSON body. No GitHub session, API token, or secret knowledge of any kind is needed — the attacker exploits the absence of a secret to bypass verification while the write target is dictated by an unrelated payload field.

### Recommendation
After `verify_signature` succeeds, assert that `repository.full_name.split('/').first` (or the derived `Repository#owner`) equals the `repository_owner`/organization actually used to select the verifying `GitHubApp`, rejecting the request (422) if they diverge. Additionally, consider requiring `webhook_secret` to be present for every configured organization rather than silently trusting unsigned payloads when it's absent.

### Proof of Concept
1. Configure Shipit with two orgs in `github:` — `org-a` (properly configured with a secret, owning `org-a/victim-repo` as an onboarded Stack) and `org-b` (onboarded but with `webhook_secret` left blank).
2. POST to the webhooks endpoint:
```
X-Github-Event: push
Body: {
  "repository": {"owner": {"login": "org-b"}, "full_name": "org-a/victim-repo"},
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>"
}
```
3. `verify_signature` resolves `repository_owner` = `org-b`, loads its `GitHubApp` (no secret), and `verify_webhook_signature` returns `true` regardless of any (or no) `X-Hub-Signature` header.
4. `PushHandler` resolves stacks via `Repository.from_github_repo_name("org-a/victim-repo")` and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")`, mutating `org-a`'s stack with no authentication tied to `org-a` at all.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
