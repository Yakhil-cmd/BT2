I found a strong analog to the ERC20 unchecked-transfer-return-value bug in `pallet-child-bounties` and `pallet-bounties`: the FRAME `Currency::transfer` result is discarded via `debug_assert!`, which compiles to a no-op in production (non-debug-assertions) builds. This lets the pallet mark a bounty as fully paid/removed even though the underlying transfer actually failed.

### Title
Child-bounty (and bounty) payout marked as claimed while the underlying `Currency::transfer` silently fails due to `debug_assert!` being compiled out in production - ([File: substrate/frame/child-bounties/src/lib.rs])

### Summary
`claim_child_bounty` (callable by any signed account) computes a `payout` to the beneficiary and performs `T::Currency::transfer(&child_bounty_account, beneficiary, payout, AllowDeath)`, but only checks the result with `debug_assert!(payout_transfer_result.is_ok())` [1](#0-0) . `debug_assert!` is compiled to a no-op in release/production WASM runtimes, so in a real deployed chain the return value of the transfer is never actually checked. Immediately afterward the code unconditionally deposits the `Claimed` event with the full `payout` amount and removes the child bounty from storage [2](#0-1) , exactly mirroring the reported ERC20 pattern: the "claimed" state is recorded even though the actual token movement did not happen. The sibling function `claim_bounty` in `pallet-bounties` has the identical pattern [3](#0-2) .

### Finding Description
`Currency::transfer` (`fungible::Mutate::transfer`) fails with `TokenError::BelowMinimum` when the destination account does not yet exist and the transferred amount is below `ExistentialDeposit` — this is confirmed by the balances pallet's own tests: `assert_noop!(Balances::transfer_allow_death(Some(1).into(), 5, 9), TokenError::BelowMinimum)` when account `5` doesn't exist and 9 < ED=10 [4](#0-3) .

In `claim_child_bounty`, `payout = balance.saturating_sub(curator_fee)` [5](#0-4) . The `curator_fee` value is set arbitrarily by the parent curator when proposing the child-bounty curator (the only constraint is `fee <= value`), so `payout` can be made arbitrarily small — even below `ExistentialDeposit` — while the bounty's total `value` still satisfies `ChildBountyValueMinimum`. If the `beneficiary` account has never held a balance (a perfectly normal condition — the beneficiary is just whoever the curator names in `award_child_bounty`), the payout transfer returns `Err(TokenError::BelowMinimum)`.

Because the check is `debug_assert!` rather than a propagated `?`, this error is discarded in any release-mode runtime (the default for real chains). Execution falls through to:
1. Emit `Event::Claimed { beneficiary, payout, .. }` — telling on-chain observers the beneficiary was paid.
2. Decrement `ParentChildBounties`.
3. Remove the child-bounty description and `*maybe_child_bounty = None`, permanently deleting the only record that tracked this payout.

The funds remain sitting in the deterministic `child_bounty_account_id(parent_bounty_id, child_bounty_id)`, but once the child bounty record is deleted there is no remaining extrinsic path to recover or re-route them (the only closer, `close_child_bounty`, requires the child bounty to still exist in storage).

The entry point `claim_child_bounty` is a normal permissionless signed extrinsic — "the dispatch origin ... may be any signed origin" [6](#0-5)  — so no privileged role, governance, or stolen keys are required to trigger the state-corruption; any signed account can call it once the child bounty reaches `PendingPayout`.

### Impact Explanation
This is an integrity break, not merely a display bug: on-chain state (`Claimed` event, removal of the bounty record) asserts a payout occurred when it did not, and the beneficiary's funds become permanently stuck/unspendable through the pallet, matching "irreversible freezing" of user funds — the same broken-accounting-invariant class flagged as Medium in the reported ERC20 issue, but here it manifests as outright fund loss since there is no re-claim mechanism once the storage entry is deleted (unlike the ERC20 report where at least a `totalERC20Claimed` counter could theoretically be corrected via merkle-root regeneration).

### Likelihood Explanation
This does not require any adversarial input crafting beyond normal bounty administration: a curator who assigns a large `fee` relative to `value` (a routine operation, with the only guard being `fee <= value`), combined with a beneficiary address that hasn't been funded yet (also routine — beneficiaries are frequently fresh accounts), reliably triggers the condition. Any signed account can then call `claim_child_bounty` to realize the bug. No governance, no malicious validator/collator, and no privileged origin is needed.

### Recommendation
Replace both `debug_assert!(...is_ok())` checks in `claim_child_bounty` (and the analogous checks in `pallet-bounties::claim_bounty`) with proper error propagation, e.g. `T::Currency::transfer(...)?;`, so the whole `try_mutate_exists` closure reverts on transfer failure instead of silently completing. Alternatively, ensure the destination account is pre-funded to the ED (or use `Preservation::Preserve` with an explicit `ensure!` on the ED requirement) before finalizing the claim, so the failure is surfaced to the caller rather than swallowed.

### Proof of Concept
Deployment/observation evidence supporting the guard failure:
- `debug_assert!` no-op in release builds is standard Rust/Substrate behavior; the runtime is always compiled without `debug-assertions` for production chains.
- Confirmed failure mode of `Currency::transfer` into a fresh, sub-ED account: `substrate/frame/balances/src/tests/dispatchable_tests.rs:31-44` reproduces `TokenError::BelowMinimum` for exactly this scenario in the existing test harness.
- Code path evidence: `substrate/frame/child-bounties/src/lib.rs:714-765` shows the unchecked transfer immediately followed by unconditional event emission and storage removal.

Background: Both functions call `T::Currency::transfer(...)` to pay out the curator fee and beneficiary payout, but only validate the result with `debug_assert!(result.is_ok())`. Since `debug_assert!` compiles to a no-op in release/production builds (the default for real chains), any transfer failure (e.g. `TokenError::BelowMinimum` when paying a sub-existential-deposit amount to a brand-new beneficiary account) is silently ignored. Execution continues to emit the `Claimed`/`BountyClaimed` event claiming the payout succeeded, and to remove the bounty/child-bounty record from storage — permanently losing track of the un-transferred funds, which remain stuck in the bounty's deterministic sub-account with no remaining code path to reclaim them.

1. Sets a low `ExistentialDeposit` in the test mock.
2. Creates a parent bounty and child bounty whose curator `fee` is close enough to `value` that `payout = value - fee` is below the existential deposit.
3. Awards the child bounty to a beneficiary account with zero balance (never funded/does not exist in storage).
4. Calls `claim_child_bounty` (or `claim_bounty`) and asserts that the beneficiary's balance is NOT increased (transfer silently failed), while the `Claimed`/`BountyClaimed` event was still emitted and the bounty record was removed from storage — demonstrating the invariant break.

Then fix the root cause: replace the `debug_assert!(fee_transfer_result.is_ok())` / `debug_assert!(payout_transfer_result.is_ok())` (and the equivalent checks in pallet-bounties' `claim_bounty` and the `impl_close_child_bounty`/`close_bounty` transfer results, if similarly discarded) with proper error propagation using `?` inside the `try_mutate_exists` closures, so that a failed transfer aborts and reverts the whole claim (no event emitted, no storage removed) instead of silently completing. Add regression tests verifying that on transfer failure, the extrinsic returns an error, the child-bounty/bounty record is NOT removed, and no `Claimed`/`BountyClaimed` event is emitted, allowing the claim to be retried later (e.g. once the beneficiary account is funded or the payout amount is adjusted).
