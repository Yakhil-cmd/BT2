### Title
Webhook signature verified against the sender's own GitHub organization while `StatusHandler`/`PushHandler` act on globally-scoped identifiers, allowing cross-organization commit-status/sync forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which organization's `webhook_secret` to check against using a field taken from the *unverified* JSON body (`repository.owner.login`, falling back to `organization.login`), then HMAC-verifies the raw payload with that organization's secret [1](#0-0) [2](#0-1) . Once verified, the actual event handlers act on *different* fields of the same payload without re-checking they belong to the organization whose secret validated the request. `StatusHandler#process` looks up commits purely by `sha` with no repository/organization scoping at all [3](#0-2) , and `PushHandler#process` matches stacks purely by `branch` name across `stacks` (no owner/organization filter) [4](#0-3) .

This is the direct analog of the FeeBuyback bug: `submit()` verifies nothing about `msg.value` (the value actually transferred) while acting on the separately-supplied `amount`. Here, the signature verifies that "this organization's app sent something," but the handlers act on `sha`/`branch` values that are never bound to that same organization/repository.

### Finding Description
Shipit explicitly supports hosting multiple independent GitHub organizations from one instance, each with its own `webhook_secret`, configured under distinct top-level keys in `secrets.github` [5](#0-4) [6](#0-5) . `Shipit.github(organization:)` looks up the app/secret purely by the organization name supplied by the caller [7](#0-6) .

In `WebhooksController#verify_signature`, that `organization` argument is `repository_owner`, computed straight from the untrusted JSON body [2](#0-1) . Because the admin of "OrgA" (a legitimately configured, but otherwise unprivileged, GitHub organization on this Shipit instance) knows OrgA's own `webhook_secret` (they configured it when creating their GitHub App/webhook per `docs/setup.md`), they can compute a valid HMAC signature for an arbitrary payload as long as `repository.owner.login` (or `organization.login`) says `"OrgA"`. The signature check equality is: *"organization whose secret validated the signature" == "OrgA"*, but the code that executes never re-asserts *"repository the handler acts on" == "OrgA/*"*.

Concretely:
- `StatusHandler#process` runs `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` — no scoping by repository or organization anywhere in the handler [3](#0-2) . Any commit SHA present in the Shipit database — including ones belonging to a completely different organization's stack — can have a forged CI status ("success"/"failure"/etc.) attached, as long as the signature was valid for *some* configured organization.
- `PushHandler#process` matches `stacks.not_archived.where(branch:)` without filtering by repository/owner, then triggers `stack.sync_github` [4](#0-3) , so a same-named branch on an unrelated repository/stack can be force-synced.

The `PullRequest` handlers do call `Shipit::Repository.from_github_repo_name(params.repository.full_name)` [8](#0-7) , so they are scoped to whatever `full_name` the attacker supplies — but that `full_name` is likewise never checked against `repository_owner`/the signing organization, so an attacker signing with OrgA's secret can still target a repository under `full_name: "OrgB/other-repo"`.

### Impact Explanation
This breaks the "organization that authenticated vs. repository/commit that is written" binding named in the acceptance rules. Forged `status` webhooks that mark a commit as passing CI directly attack Shipit's deploy-safety gating: Shipit's `DeploySpec`/`Status::Group` machinery treats GitHub commit statuses as a required gate before allowing a commit to be deployed [9](#0-8) . Being able to inject an arbitrary "success" status onto any commit SHA tracked by any stack on the instance — regardless of which organization actually owns that commit — can enable an unauthorized deploy (bypassing required checks) for a repository the attacker does not control. This satisfies the Critical/High impact bar ("an unauthorized deploy").

### Likelihood Explanation
Requires only that the Shipit deployment (a) hosts more than one GitHub organization (documented, supported feature) and (b) that the attacker controls/knows the `webhook_secret` for at least one of those organizations (e.g., they are the admin of their own onboarded org's GitHub App/webhook — not a privileged Shipit account, `ApiClient` token, or `api_clients_secret`). No repository write access or Shipit session is required — only an HTTP POST to the public `/webhooks` endpoint with a valid signature for their own org. This is a realistic configuration for any Shipit instance serving multiple tenants/organizations.

### Recommendation
After `verify_signature` establishes which organization's secret validated the payload, every handler must re-derive the target repository/commit scope from the payload and assert it belongs to that same organization before acting — e.g., pass the verified `organization` (or a `Repository` scoped to it) into `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params, organization: verified_organization) }`, and have `StatusHandler` filter `Commit.joins(stack: :repository).where(sha: params.sha, shipit_repositories: { owner: verified_organization })`, and have `PushHandler` filter stacks by `repository.owner == verified_organization` as well. More generally, require `params.dig('repository','owner','login')` (or `organization.login`) used for signature selection to be equal to the value acted upon downstream (repository full_name / commit's owning repository) before any handler runs.

### Proof of Concept
1. Configure Shipit (per `docs/setup.md`, "Using Multiple Github Applications") with two orgs: `OrgA` (attacker-administered) and `OrgVictim` (has a stack tracking commit `deadbeef...` awaiting a required CI status).
2. Attacker, using OrgA's own `webhook_secret` (which they legitimately possess as OrgA's GitHub App owner), computes `X-Hub-Signature` for a `status` event payload:
   ```json
   {
     "repository": {"owner": {"login": "OrgA"}, "full_name": "OrgA/anything"},
     "sha": "deadbeef... (OrgVictim's commit)",
     "state": "success",
     "context": "ci/required-check"
   }
   ```
3. POST to `/webhooks` with `X-Github-Event: status` and the computed signature.
4. `verify_signature` calls `Shipit.github(organization: "OrgA")` and validates successfully against OrgA's secret [1](#0-0) .
5. `StatusHandler#process` runs `Commit.where(sha: "deadbeef...")`, finds OrgVictim's commit (no organization filter), and creates a forged "success" status on it [3](#0-2) , potentially satisfying OrgVictim's deploy gating and enabling an unauthorized deploy.

Note: I was not able to inspect `Commit#create_status_from_github!` or the exact deploy-gating logic in `Shipit::DeploySpec`/`Status::Group` in full within this session (only grep hits, not full file contents), so the precise mechanics of how a forged status feeds into the "safe to deploy" decision should be confirmed by a maintainer/agent with full file access before treating this as fully proven end-to-end.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
