### Title
Unchecked RAY value overflow during accrual permanently freezes a large market - (File: common/src/rates/simulate.rs)

### Summary

`accrue_step` converts aggregate scaled debt and supply into RAY-valued originals before calculating utilization. Both conversions use `scaled_to_original`, which multiplies the scaled `Ray` amount by its index and panics with `MathOverflow` when the result exceeds `i128`. The configured `MAX_BORROW_INDEX_RAY` bound only limits the index itself; it does not ensure `borrowed * borrow_index` or `supplied * supply_index` remains representable. Once either aggregate crosses the `i128` boundary, every subsequent market operation that accrues first reverts, including repayment, withdrawal, liquidation, and recapitalization.

### Finding Description

Every pool market mutation loads a synced cache. `ops::synced_market` loads persistent state and calls `interest::global_sync` before any operation-specific logic. [1](#0-0)  The explicit index-keeper path also calls `global_sync` for each requested market. [2](#0-1) 

Each accrual chunk calls `accrue_step`. Before calculating utilization, the function executes:

```rust
let borrowed_original = scaled_to_original(env, borrowed, borrow_index);
let supplied_original = scaled_to_original(env, supplied, supply_index);
``` [3](#0-2) 

`scaled_to_original` performs `scaled.mul(index)`. [4](#0-3)  `Ray::mul` delegates to `mul_div_half_up`, whose widened result is converted back to `i128` and panics if it does not fit. [5](#0-4) [6](#0-5) 

The problem is that the ceiling applies to `borrow_index`, not to the product `borrowed * borrow_index`. A large but valid market can therefore remain below the index ceiling while its aggregate RAY value exceeds `i128::MAX`. Because the failed calculation occurs before indexes or `last_timestamp` are committed, the call reverts and leaves the stale timestamp unchanged; the same overflowing starting values are used on every later attempt.

### Impact Explanation

This permanently freezes all funds in the affected hub asset market.

The impacted paths include:

- `withdraw`: `accounting` calls `ops::load_leg`, which syncs the market before resolving and burning shares. [7](#0-6) 
- `repay`: `accounting` calls `ops::load_leg` before resolving and burning debt. [8](#0-7) 
- Liquidation seizure: `seize_positions` calls `ops::synced_market` before writing down bad debt or crediting seized supply. [9](#0-8) 
- `recapitalize`: `accounting` calls `ops::renewed_market`, which also accrues before the backing calculation. [10](#0-9) 
- `update_indexes`: the keeper call directly runs `global_sync`. [2](#0-1) 

As a result, suppliers cannot withdraw, borrowers cannot reduce or close debt, liquidators cannot progress a distressed account, and recapitalization cannot restore the market. This satisfies permanent freezing of user funds and can leave the market unable to operate.

### Likelihood Explanation

The attack path is capital-intensive and depends on a market being admitted with caps large enough to hold an aggregate near the `i128` RAY-value limit. No privileged action is required after such a market exists: an unprivileged account can create the position through normal `supply` and `borrow`, and any caller can submit `update_indexes` once ledger time advances.

The failure is deterministic once:

```text
scaled debt shares × borrow index > i128::MAX
```

or:

```text
scaled supply shares × supply index > i128::MAX
```

The protocol’s own regression test reproduces the condition with a billion-token, 18-decimal market at sustained high utilization and confirms that `update_indexes`, `withdraw`, and `repay` all fail with `MathOverflow` while the borrow index remains below `MAX_BORROW_INDEX_RAY`. [11](#0-10) 

### Recommendation

Prevent aggregate value overflow instead of allowing accrual to trap irreversibly. Options include:

1. Compute utilization directly from scaled balances without materializing the full `i128` product, using a saturating or wider-domain utilization calculation.
2. Saturate the aggregate value used only for utilization while retaining checked math for actual settlement amounts.
3. Enforce an aggregate scaled-share cap that guarantees `scaled * MAX_*_INDEX / RAY` always fits in `i128`.
4. Add a liveness escape that permits repayment and withdrawal when index accrual overflows, without allowing new borrows.

The chosen mitigation must preserve liquidation access and avoid blocking repayment or withdrawal paths.

### Proof of Concept

The repository already contains an executable reproduction:

```text
tests/test-harness/tests/controller/large_positions_and_long_horizons.rs
test: a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap
```

Conceptual transaction sequence:

1. Create or select an 18-decimal market whose caps admit approximately `1_000_000_000 * 10^18` base units.
2. Supplier calls controller `supply` with the full amount.
3. Borrower supplies sufficient collateral in another market and calls controller `borrow` for approximately 98% of the supplied liquidity.
4. Leave the market untouched while utilization remains high.
5. Any caller invokes controller `update_indexes` for the affected `HubAssetKey`.
6. `global_sync` reaches `accrue_step`, where `scaled_to_original(borrowed, borrow_index)` or `scaled_to_original(supplied, supply_index)` exceeds `i128` and panics with `MathOverflow`.
7. Subsequent `update_indexes`, `withdraw`, `repay`, liquidation seizure, and `recapitalize` calls repeat the same accrual and fail before reaching their operation-specific logic.

The regression test asserts that the index cap has not engaged when the overflow occurs and that both `withdraw` and `repay` fail afterward. [12](#0-11)

pub fn try_mul_div_half_up(env: &Env, x: i128, y: i128, d: i128) -> Option<i128> {
    if x < 0 || y < 0 || d <= 0 {
        return None;
    }
    let half = d / 2;

    // Fast path: the biased product fits `i128`, so the whole computation is
    // native. `x * y + half` is non-negative here, so `/` is the floor the
    // widened path would produce.
    if let Some(biased) = x
        .checked_mul(y)
        .and_then(|product| product.checked_add(half))
    {
        return Some(biased / d);
    }

    let (x256, y256, d256) = to_i256_operands(env, x, y, d);
    x256.mul(&y256)
        .add(&I256::from_i128(env, half))
        .div(&d256)
        .to_i128()
}

/// The cliff. A billion whole tokens is `1e36` raw ray; the value ceiling is
/// `i128::MAX`, 170 times that. At the XLM curve's steep segment the index
/// grows past 170x in a few years, and the next accrual panics inside
/// `scaled_to_original`. Every verb accrues first, so the market freezes:
/// no repay, no withdraw, no liquidation. The index cap never engages.
#[test]
fn a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap() {
    let mut t = LendingTest::new()
        .with_market(big("BIG18", 18, xlm_curve()))
        .with_market(col())
        .with_max_utilization_disabled_all_markets()
        .build();
    lift_caps(&t, "BIG18", 18);
    lift_caps(&t, "COL", 7);
    let principal = BILLION * 10i128.pow(18);
    t.supply_raw(BOB, "BIG18", principal);
    let debt = principal / 100 * 98;
    t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
    t.borrow_raw(ALICE, "BIG18", debt);

    let mut years = 0u32;
    let failure = loop {
        years += 1;
        assert!(
            years <= 40,
            "no cliff within 40 years; the bound in docs/reference/formulas.md is wrong"
        );
        t.advance_time(YEAR_SECS);
        if let Err(e) = t.try_update_indexes_for(&["BIG18"]) {
            break e;
        }
    };
    let failed: Result<(), soroban_sdk::Error> = Err(failure);
    assert_contract_error(failed, errors::MATH_OVERFLOW);
    let last = book(&t, "BIG18");
    assert!(
        last.borrow_index < MAX_BORROW_INDEX_RAY,
        "the index cap did not engage before the value overflow"
    );
    // The market is frozen: exits and repayments accrue first and hit the same panic.
    assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
    assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
