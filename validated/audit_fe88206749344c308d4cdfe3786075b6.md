### Title
Stack-scoped API tokens can read build/deploy status of any stack via the CCMenu endpoint - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::ApiClient` tokens can be scoped to a single `stack` (`belongs_to :stack, optional: true`, `app/models/shipit/api_client.rb:8`), and `Shipit::Api::BaseController` is designed to enforce this scope by restricting all stack lookups to `current_api_client.stack_id` through the `stacks`/`stack` helper methods (`app/controllers/shipit/api/base_controller.rb:74-80`). `Shipit::Api::CCMenuController`, however, overrides `stack` to call `Stack.from_param!(params[:stack_id])` directly, entirely skipping the `current_api_client.stack_id` restriction (`app/controllers/shipit/api/ccmenu_controller.rb:29-31`).

### Finding Description
The binding that should hold is: `stack a token authorizes == stack a request touches`. Before the flaw is exploited, this holds for every other API controller that relies on the inherited `stack`/`stacks` helpers, e.g. `Shipit::Api::LocksController` (`app/controllers/shipit/api/locks_controller.rb`), which never overrides `stack`, so a token scoped via `ApiClient#stack_id` can only ever resolve to that one `Stack`.

`CCMenuController` breaks this binding: `authenticate_api_client` is overridden to read the token from `params[:token]` (`app/controllers/shipit/api/ccmenu_controller.rb:33-36`) so it can be embedded in a URL used by CI dashboard tools (see `Shipit::CcmenuUrlController#client`, `app/controllers/shipit/ccmenu_url_controller.rb:15-18`, which creates tokens scoped to one specific stack for this exact purpose). Once authenticated, `require_permission :read, :stack` (`app/controllers/shipit/api/ccmenu_controller.rb:6`) only checks that the token carries the `read:stack` permission string — it never checks which stack the token is bound to. The actual `Stack` object rendered is fetched by the overridden `stack` method, which ignores `current_api_client.stack_id` and resolves any `params[:stack_id]` via the unscoped `Stack.from_param!` (`app/models/shipit/stack.rb`).

As a result, a CCMenu token that was minted and is legitimately used for `Stack` A can be replayed by anyone who intercepts or is handed the URL against any other `Stack` B by simply changing the `stack_id` in the request path/params.

### Impact Explanation
This is an unauthenticated-boundary-crossing read: a low-privilege, single-stack-scoped credential (deliberately designed to be embedded in third-party CI dashboard URLs, i.e., a lower-trust context) allows unrestricted read of build/deploy status (`name`, `activity`, `lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, `webUrl`, lock status) for every stack in the Shipit instance. This matches the "High" impact class: unauthenticated read of stack state/deploy output, achieved by escalating a stack-scoped token beyond its intended authorization boundary.

### Likelihood Explanation
CCMenu tokens are explicitly designed to be shared/embedded in external CI status tools and dashboards (see `CcmenuUrlController`), so they are more likely to leak or be intentionally shared with less-trusted parties than a full API token. Any holder of one legitimate CCMenu URL can trivially enumerate or guess other `stack_id`/`to_param` values and read their status — no additional secrets, sessions, or privileges are required beyond possessing one valid scoped token.

### Recommendation
In `Shipit::Api::CCMenuController`, replace the direct `Stack.from_param!(params[:stack_id])` lookup with the scoped helper from `BaseController` (i.e., `stacks.from_param!(params[:stack_id])`), so that a token whose `ApiClient#stack_id` is set can only ever resolve to that stack, consistent with every other API controller.

### Proof of Concept
1. Create two stacks, `A` and `B`.
2. Via `Shipit::CcmenuUrlController#fetch`, obtain a CCMenu URL scoped to stack `A` (token generated by `ApiClient.create_with(permissions: %w[read:stack])... stack: A`).
3. Send `GET /api/stacks/B/ccmenu.xml?token=<A's token>` (substituting stack `B`'s `to_param` for `stack_id`).
4. Observe that `authenticate_api_client` succeeds (token is valid) and `require_permission :read, :stack` passes (token has `read:stack`), then `stack` resolves stack `B` directly via `Stack.from_param!`, returning build/deploy status for stack `B` even though the token was only ever authorized for stack `A`.
