### Title
Cross-repo status forgery unblocks victim stack deploys via SHA-matched `StatusHandler#process` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` resolves target commits with a global `Commit.where(sha: params.sha)` query that is not scoped to the repository that sent the webhook, and `Commit#create_status_from_github!` writes the resulting status against whatever stack that `Commit` row already belongs to. Because the binding "commit whose blocking status changed" == "commit whose CI was actually reported by its own repository" is never enforced by repository identity, a status reported for a SHA present in an attacker's own repository can flip the blocking status of the identical SHA recorded under a victim's stack, unblocking deploys.

### Finding Description
The claimed binding is:
`commit.stack.repository == webhook.repository` for every `Commit` row whose status is mutated by a given webhook.

Tracing the code: `StatusHandler#process` does [1](#0-0) 
which looks up commits purely `where(sha: params.sha)`, with no `stack_id`/repository filter at all. Any `Commit` record in the entire Shipit install sharing that SHA — regardless of which stack/repository it belongs to — receives the status via `commit.create_status_from_github!(params)`.

`create_status_from_github!` then writes the status using the commit's own `stack_id`, not the webhook's originating repository: [2](#0-1) 

`Commit#blocked?` and `#deployable?` subsequently re-derive from these mutated statuses: [3](#0-2) 

Root cause: git SHAs are content hashes shared across forked/cloned repositories. Any repository that shares ancestry with the victim's repository (e.g., a public fork, which any unprivileged GitHub user can create) contains identical SHAs for all commits prior to the fork point. If a victim stack has an undeployed, currently-blocking commit (pending/failing CI) whose SHA also exists in the attacker's own fork, the attacker can:
1. Fork the victim's repository (shared ancestry ⇒ shared SHA for the blocking commit).
2. Configure/trigger a GitHub Status webhook from their own fork (which they legitimately own and can sign/send) for that SHA with `state: success` and a `context` matching one of the victim stack's `blocking_statuses` required contexts.
3. Because `StatusHandler#process` matches only on SHA, Shipit applies this "success" status to the `Commit` row belonging to the victim's stack.
4. `Commit#blocked?` re-evaluates: the once-blocking commit's `.blocking?` now returns false, so `stack.commits.reachable.newer_than(...).older_than(self).any?(&:blocking?)` becomes false for later commits.
5. `Commit#deployable?` then returns true for a later, legitimately queued commit that previously could not deploy.
6. `Stack#next_commit_to_deploy` can now select this commit for deployment.

No existing guard closes this gap: webhook signature verification (`verify_signature`/GitHub App webhook secret) only proves the payload came from *some* GitHub repository wired to Shipit with a valid secret — it does not prove the payload's repository matches the `stack.repository` associated with the target `Commit` row. `drop_unhandled_event`, `ExplicitParameters` schema validation on `sha`/`state`/`context`, and model validations on `Repository`/`Stack` do not perform any cross-check between the webhook's originating repository and the `Commit#stack` being mutated. The vulnerability is fully within `StatusHandler#process` and `Commit#create_status_from_github!`, i.e., this engine's own code.

### Impact Explanation
An attacker who controls (owns) any repository sharing commit ancestry with a victim's tracked repository (trivial via a public GitHub fork) can write a forged CI status against a `Commit` record belonging to a stack they do not control, flipping `blocked?`/`deployable?` for later commits in that victim stack and causing `Stack#next_commit_to_deploy` to select and deploy code that has not actually passed the victim's CI gate. This is an unauthorized-deploy-unblocking primitive — payload from one repository mutating another's commit/stack state — matching the Critical category ("a payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy"). It is repeatable against any victim stack for which the attacker can find/produce a shared-ancestry SHA that is currently in the blocking window, and requires no Shipit session, API token, or GitHub App secret beyond the attacker's own repository's ability to send GitHub status webhooks (which GitHub sends automatically for any repo with configured status checks/Shipit App installed, or which the attacker can send themselves if they can register the webhook on their own repo).

### Likelihood Explanation
Preconditions: (1) victim stack has a non-empty `blocking_statuses` configuration and an undeployed commit currently in blocking (pending/failing) state — a normal CI gating setup; (2) the attacker's own repository shares at least one commit SHA with the victim's tracked repository that falls within the "reachable, newer than last deploy, older than target" window — trivially satisfied by forking before the point of blocking commit, or by cherry-picking/rebasing to reproduce the exact SHA. No Shipit secrets, sessions, or privileged roles are required — the attacker only needs to control a GitHub repository able to emit a status webhook that Shipit's GitHub App/webhook endpoint accepts (which is the normal case for any repo the Shipit GitHub App is installed on, including attacker-owned forks if the org allows installation on forks, or any repo webhook pointed at the shared `/webhooks` endpoint with a shared app-level secret). This is a low-cost, repeatable attack limited only by the attacker's ability to find/produce matching SHAs across repositories.

### Recommendation
Scope `StatusHandler#process` (and the analogous check-run handler) to only update `Commit` rows whose `stack.repository` (owner/name) matches the repository identified in the webhook payload, e.g. `Commit.where(sha: params.sha).select { |c| c.stack.repository_matches?(payload_repository) }`, or join through `stack` in the query itself using the payload's `repository.full_name`. This restores the binding that a commit's blocking status can only be mutated by a status genuinely reported for that commit's own repository.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_cross_repo_test.rb
class StatusHandlerCrossRepoTest < ActiveSupport::TestCase
  test "a status for a foreign repository must not unblock a victim stack's later commit" do
    victim_stack = shipit_stacks(:shipit)
    victim_stack.update!(cached_deploy_spec: { blocking_statuses: ['ci/tests'] })

    shared_sha = 'a' * 40
    blocking_commit = victim_stack.commits.create!(sha: shared_sha, message: 'blocking commit')
    later_commit = victim_stack.commits.create!(sha: 'b' * 40, message: 'later commit')

    blocking_commit.statuses.create!(stack: victim_stack, state: 'pending', context: 'ci/tests')

    # LHS of binding: commit currently blocking, reported by its own (victim) repo
    assert later_commit.blocked?, "later commit should be blocked before forged status"

    # Attacker sends a webhook for a repository they own, unrelated to victim_stack,
    # but the SHA collides because of shared ancestry (e.g. a fork).
    payload = ExplicitParameters::Params.new(
      sha: shared_sha,
      state: 'success',
      context: 'ci/tests',
      # repository in the raw payload is the ATTACKER's own repo, not victim_stack's
    )

    Shipit::Webhooks::Handlers::StatusHandler.new(nil, payload).process

    later_commit.reload

    # RHS: binding broken -- blocking_commit's state flipped via a status
    # never actually reported by victim_stack's own repository
    refute later_commit.blocked?, "vulnerability: later commit became unblocked via a status for a foreign repository"
    assert later_commit.deployable?, "vulnerability: later commit became deployable via cross-repo forged status"
  end
end
```
This demonstrates that `StatusHandler#process`'s SHA-only lookup lets a status payload unrelated to `victim_stack`'s repository flip `blocked?`/`deployable?` for a legitimately queued commit, confirming the vulnerability.
