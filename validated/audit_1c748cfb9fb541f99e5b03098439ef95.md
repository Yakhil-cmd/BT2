### Title
Unlocked in-memory main-chain/state-cache mutation during AA dry-run trigger execution leads to stale, rolled-back consensus state ("use-after-rollback" cache corruption) - ([File: aa_composer.js])

### Summary
The Chrome CVE is a UAF where a network object is freed while still referenced and later used, corrupting heap state. The closest reachable analog in ocore is in `aa_composer.js`'s dry-run AA trigger path: it mutates the shared, process-wide consensus caches (`storage.assocUnstableUnits`, `assocBestChildren`, `assocStableUnits`, `assocStableUnitsByMci`) and runs main-chain stability logic for a transaction that is guaranteed to be rolled back at the SQL layer, without holding the `"write"` mutex that normally serializes all such cache mutations. Because Node interleaves async callbacks, this "temporary" mutation can race with concurrent, real unit-processing that also touches the same cache objects — leaving in-memory state that no longer matches the database (a "freed"/invalidated view of reality that is still referenced and acted upon), analogous to a use-after-free corruption.

### Finding Description
`dryRunPrimaryAATrigger` opens its own DB connection/transaction and calls `handleTrigger` with `bDryRun: true`, but never acquires the global `["write"]` mutex: [1](#0-0) 

Inside `handleTrigger`, the generated AA response unit is validated and saved via `writer.saveJoint`, but `objAAValidationState.bUnderWriteLock = true` is set unconditionally (dry-run or not), which tells `writer.saveJoint` to skip taking the write lock itself, assuming the caller already holds it: [2](#0-1) [3](#0-2) 

`writer.saveJoint` unconditionally writes the new (dry-run) unit into the live, shared caches — `storage.assocUnstableUnits[objUnit.unit]`, `storage.assocBestChildren[...]` — and unconditionally invokes `main_chain.updateMainChain(...)`, which can advance best-parent selection and stability (`markMcIndexStable`), mutating `assocStableUnits`, `assocStableUnitsByMci`, and deleting entries from `assocUnstableUnits`: [4](#0-3) [5](#0-4) [6](#0-5) 

A repo-wide search for `bDryRun` handling in `main_chain.js` returned no matches — confirming `updateMainChain`/`markMcIndexStable` have no awareness of dry-run mode and treat the ephemeral transaction as authoritative when updating these shared caches.

At the end of the dry run, `revertResponsesInCaches` is called to undo cache effects, but it only forgets the AA **response** units and fixes `is_free` on their direct parents — it does nothing to reverse any stability advancement, best-parent updates, or `assocStableUnitsByMci` changes that `main_chain.updateMainChain`/`markMcIndexStable` may have already committed to the shared in-memory caches while the dry run's SQL transaction is later rolled back: [7](#0-6) 

The dry run is triggered directly from the unit-validation success path in `network.js`, before the real `writer.saveJoint` for the triggering unit is even called, and specifically outside of the `["write"]` mutex scope used by `validation.validate` (which only locks the author addresses) and by `writer.saveJoint` (`["write"]`): [8](#0-7) [9](#0-8) 

Because this dry run is reachable by any unit poster — simply including a `payment` output addressed to an AA address is enough to make `count_primary_aa_triggers > 0` and trigger the dry run — an attacker can post ordinary units whose outputs point at any known AA address to force repeated, unsynchronized dry-run cache mutations while legitimate units are concurrently being validated and written by other peers/units, corrupting the shared consensus caches that other code (parent/stability validation, `readUnitProps` consistency assertions, double-spend `sequence`/`is_free` checks) relies on as ground truth.

### Impact Explanation
If the in-memory caches diverge from the SQL database as a result of this unsynchronized dry-run mutation (e.g., a unit is prematurely marked stable/`good` in `assocStableUnits`, or `assocBestChildren`/best-parent state is corrupted, or the rollback leaves stale entries because `revertResponsesInCaches` does not undo all side effects), the node's subsequent validity/stability determinations for real units can diverge from other nodes' determinations, or a rolled-back state could remain wrongly treated as free/stable, opening the door to accepting a conflicting (double-spend) unit as valid, or nodes disagreeing on stability/validity — matching the "node disagreement on validity or stability" / "unauthorized spending" impact classes.

### Likelihood Explanation
The trigger condition (a payment output to an AA address) is trivial and available to any unit poster; the only gate is `conf.bDryRunNewTriggers` being enabled and the node not being light and not catching up. Exploiting the race reliably (interleaving with a concurrently-processed unit that mutates the same cache keys) requires timing, which lowers ease of exploitation somewhat, but the underlying missing-synchronization/missing-rollback-cleanup is a deterministic code defect, not a timing coincidence about correctness of the logic itself.

### Recommendation
- Make `dryRunPrimaryAATrigger` (and by extension `handleTrigger`/`writer.saveJoint` when `bDryRun` is set) acquire the `["write"]` mutex for its entire duration, exactly like real unit processing.
- Make `main_chain.updateMainChain`/`markMcIndexStable` dry-run aware, or otherwise ensure no changes to `assocStableUnits`, `assocStableUnitsByMci`, `assocBestChildren`, or best-parent/level state are applied for `objValidationState.bDryRun` transactions.
- Extend `revertResponsesInCaches` (or add a comprehensive dry-run cache snapshot/restore) to fully revert *any* cache mutation performed during a dry run, not just the AA response units and their immediate parents' `is_free` flag.

### Proof of Concept
1. Enable `conf.bDryRunNewTriggers` (as intended for use in `network.js`).
2. Attacker posts a valid unit `U1` with a `payment` output to a known AA address `A`, while simultaneously another peer submits a second unrelated valid unit `U2` that is processed concurrently by the same node.
3. `network.js`'s `ifOk` callback for `U1` invokes `aa_composer.dryRunPrimaryAATrigger`, which — without the `"write"` mutex — calls `writer.saveJoint` for the AA's ephemeral response unit, mutating `storage.assocUnstableUnits`/`assocBestChildren` and invoking `main_chain.updateMainChain`.
4. Because no `["write"]` lock is held, the real write-path processing of `U2` (which does hold `["write"]`) can interleave with the dry run's async DB callbacks, reading/writing the same shared cache objects.
5. After the dry run's SQL transaction is rolled back, `revertResponsesInCaches` only removes the AA response unit and fixes its parents' `is_free`; any stability/best-parent side effects from `updateMainChain` on other units (including `U2`) remain in memory, diverging from the SQL database and from other nodes' state.
