### Title
Unhandled NULL/undefined `payload` dereference when processing a peer-supplied private payment element - (File: network.js)

### Summary
`network.js`'s `handleOnlinePrivatePayment()` dereferences `arrPrivateElements[0].payload.denomination` before verifying that `payload` exists on the attacker-controlled `arrPrivateElements[0]` object, mirroring the CVE-2018-5806 pattern of using unvalidated, attacker-controlled input fields before a null/existence check (LibRaw's `leaf_hdr_load_raw()` dereferencing a pointer derived from unchecked header data).

### Finding Description
`handleOnlinePrivatePayment(ws, arrPrivateElements, bViaHub, callbacks)` in `network.js` is the entry point that processes `private_payment` messages received directly from any peer or via a hub. The only check performed before accessing nested fields is: [1](#0-0) 
```
if (!ValidationUtils.isNonemptyArray(arrPrivateElements))
    return callbacks.ifError("private_payment content must be non-empty array");

var unit = arrPrivateElements[0].unit;
var message_index = arrPrivateElements[0].message_index;
var output_index = arrPrivateElements[0].payload.denomination ? arrPrivateElements[0].output_index : -1;
```
This confirms the array is non-empty, but does not check that `arrPrivateElements[0]` is an object nor that it has a `payload` property before dereferencing `.payload.denomination`. Since `arrPrivateElements` is taken directly from an untrusted network message (`json.private_payment` content forwarded from `handleJustsaying`/`handleRequest` in `network.js`, ultimately parsed from peer/hub JSON), an attacker can send an array such as `[{unit: "...", message_index: 0}]` (no `payload` field, or `payload: null`) and trigger `TypeError: Cannot read properties of undefined (reading 'denomination')` when Node evaluates `arrPrivateElements[0].payload.denomination`.

By contrast, the downstream validation code in `indivisible_asset.js`'s `parsePrivatePaymentChain()` and `private_payment.js`'s `validateAndSavePrivatePaymentChain()` are careful to check `!objPrivateElement.payload` before touching `.payload.x`, e.g.: [2](#0-1) [3](#0-2) 
but `network.js`'s early field extraction runs *before* these validated code paths are reached, so the crash happens first.

### Impact Explanation
An uncaught `TypeError` thrown synchronously inside a peer/hub message handler is not wrapped in a try/catch at this call site, so it propagates up the call stack of the WebSocket message-processing code. Depending on how the outer dispatcher handles exceptions, this can crash the Node.js process (unhandled exception) or, at minimum, abort processing of that peer connection. Because any peer or hub-relayed message can trigger this from a single crafted `private_payment` justsaying/request, a remote unauthenticated party can repeatedly crash full/light nodes that process private payments, resulting in a denial of service against nodes' ability to receive/process private payments and, if the process fully crashes, a broader inability to confirm new units until manually restarted.

### Likelihood Explanation
The trigger requires only sending a single JSON message of type `private_payment` with an array whose first element lacks a `payload` field — no valid unit, signature, or stability is required, and no rate-limiting/schema validation happens before the dereference. This is trivially reachable by any peer connecting to a hub or full node, making exploitation straightforward and repeatable.

### Recommendation
Add a defensive check immediately after the `isNonemptyArray` check in `network.js`:
```
if (!ValidationUtils.isNonemptyObject(arrPrivateElements[0]) || !ValidationUtils.isNonemptyObject(arrPrivateElements[0].payload))
    return callbacks.ifError("bad private payment element");
```
before accessing `unit`, `message_index`, or `payload.denomination`, consistent with the defensive patterns already used in `private_payment.js` and `indivisible_asset.js`.

### Proof of Concept
Send (as a peer or via hub) a `justsaying`/`request` of type `private_payment` with content:
```json
[
  { "unit": "AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA=", "message_index": 0 }
]
```
(i.e., omitting the `payload` field entirely, or setting `"payload": null`). This reaches `handleOnlinePrivatePayment`, passes the `isNonemptyArray` check, and then throws `TypeError: Cannot read properties of undefined (reading 'denomination')` at the `arrPrivateElements[0].payload.denomination` line, since `payload` is `undefined`.

**Note on verification limits:** I was unable to fully trace, within the available tool budget, the exact exception-handling wrapper (if any) around the WebSocket message dispatcher that calls `handleOnlinePrivatePayment`, so I cannot confirm with certainty whether the resulting `TypeError` crashes the entire Node process or is caught and only aborts that message's processing. This should be verified directly in `network.js`'s `handleJustsaying`/`handleRequest`/`onWebsocketMessage` dispatch logic before finalizing severity.
