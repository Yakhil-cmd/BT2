### Title
TSV row/column injection via unescaped filenames in `writeTSV` - ([File: pkg/cmd/repo/read-dir/read_dir.go])

### Summary
`writeTSV` writes `e.Name` directly into a tab/newline-delimited record without any escaping. Since `e.Name` comes straight from the git tree entry name returned by the GraphQL API (attacker-controlled via a repository/PR/fork file name), an attacker can embed tab or newline bytes in a file name to inject extra columns or entirely fabricated rows into the TSV output that scripts consuming `gh repo read-dir` (non-TTY mode) will parse.

### Finding Description
`fetchTree` in [1](#0-0)  populates `dirEntry.Name` directly from the GraphQL `Tree.Entries[].Name` field, which is derived from the actual git blob/tree entry name in the repository the victim queries. Git permits essentially any byte in a path component except `/` and NUL, so an attacker who controls a repository (or a fork/PR branch, since `--repo`/`--ref` can point at any accessible ref) can create a file whose name contains a literal tab (`\t`) or newline (`\n`) character.

`writeTSV` then formats each entry with `fmt.Fprintf(&sb, "%s\t%s\t%s\t%d\n", e.Type, e.Name, e.modeOctal(), e.Size)` [2](#0-1)  with no escaping or rejection of control characters in `e.Name`. A tab embedded in the name shifts/splits the fixed 4-column record that scripts expect (type, name, mode, size), and a newline embedded in the name terminates the current record early and starts what looks like an independent, attacker-crafted row (attacker also controls the following bytes, i.e. can fake a `type\tname\tmode\tsize` line with arbitrary "type" and "name" values).

Note that the codebase already exposes `NameRaw`/`PathRaw` fields [3](#0-2)  for the JSON exporter, seemingly intended to carry an escaped/raw representation for exactly this kind of unsafe-byte scenario, but `writeTSV` uses the plain `Name` field and performs no equivalent escaping for the TSV code path.

### Impact Explanation
This is an output/data injection into a machine-parsed format (TSV), not remote code execution by itself. The impact is: 1) corruption/misparsing of `gh repo read-dir` output for any downstream automation that splits on tabs/newlines expecting `type, name, mode, size` per line, and 2) fabricated extra rows that could trick automation into believing a different file (attacker-chosen name/type) exists in the directory listing. If downstream scripts feed the parsed "name"/"path" field into further shell commands, file operations, or `gh` invocations without their own validation, this could escalate to command injection or wrong-file operations in the victim's pipeline — but that escalation depends on the specific consuming script, which is outside this repo's control. Within this codebase alone, the confirmed impact is malformed/injectable structured output, not direct code execution.

### Likelihood Explanation
Highly feasible: any unprivileged attacker who can get the victim to run `gh repo read-dir <path> --repo <attacker-repo>` (or point `--ref` at an attacker-controlled fork/PR branch in a repo the victim already trusts) can create a file with a tab or newline in its name and have full control over that row's content in non-TTY output. No special privileges beyond being able to push a file with an unusual name to a git tree are required.

### Recommendation
Sanitize or escape `e.Name` (and `e.Type`/other string fields, defensively) in `writeTSV` before writing — e.g., replace/escape embedded `\t` and `\n` characters (as `NameRaw` appears intended to support), or reject/flag entries whose names contain such control characters, so each output line always corresponds to exactly one entry with a fixed number of fields.

### Proof of Concept
Go test sketch using the existing `fetchTree`/`repoDir` test scaffolding (see `read_dir_test.go`):
```go
func TestWriteTSV_NameInjection(t *testing.T) {
    dir := &repoDir{
        Entries: []dirEntry{
            {Type: "file", Name: "evil\ndir\tfaketype\t999", Mode: 0100644, Size: 1},
        },
    }
    io, _, out, _ := iostreams.Test()
    err := writeTSV(io, dir)
    require.NoError(t, err)
    lines := strings.Split(out.String(), "\n")
    // Expect 1 logical entry, but attacker-controlled newline produces 2 lines,
    // the second one being a fully attacker-fabricated fake TSV record.
    require.Len(t, lines, 2, "attacker name should not be able to inject an extra row")
}
```
Running this against the current implementation shows the injected newline splits the single entry into two output lines, the second of which is entirely attacker-controlled content masquerading as a legitimate TSV row.

func writeTSV(io *iostreams.IOStreams, dir *repoDir) error {
	var sb strings.Builder
	for _, e := range dir.Entries {
		fmt.Fprintf(&sb, "%s\t%s\t%s\t%d\n", e.Type, e.Name, e.modeOctal(), e.Size)
	}
	_, err := io.Out.Write([]byte(sb.String()))
	return err
}
