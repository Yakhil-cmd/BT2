### Title
`StatusHandler#process` applies GitHub status updates by SHA alone with no repository-identity check, allowing cross-repo replay to corrupt `commit.state` and forge `deployable_status` hooks - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` looks up commits solely by `params.sha` and calls `commit.create_status_from_github!(params)` for every matching row, never comparing `params.dig('repository', 'full_name')` against `commit.stack.repository.full_name` (or `commit.github_repo_name`). Because `verify_signature` in `WebhooksController` only checks that the webhook signature matches the GitHub App belonging to the payload's own `repository_owner`, any authenticated-but-unrelated repository can send a `status` event whose SHA happens to also exist in another stack's `commits` table, and that other stack's commit state/hooks will be mutated.

### Finding Description
The broken binding is: `params.dig('repository','full_name') == commit.stack.repository.full_name` — this equality is never evaluated anywhere in the code path.

Path traced:
- `app/controllers/shipit/webhooks_controller.rb#verify_signature` (lines 24-49) resolves `repository_owner` from the incoming payload (`params.dig('repository','owner','login')`) and validates the signature against `Shipit.github(organization: repository_owner)`. This only proves the request came from a GitHub App/org that legitimately owns *that* payload's `repository`, not that it has any relationship to the target commit's actual stack. [1](#0-0) 
- `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` dispatches to `StatusHandler.call(params)`. [2](#0-1) 
- `StatusHandler#process` does: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }`. This is a global lookup across **all** stacks/repositories in the Shipit instance keyed only by `sha`. [3](#0-2) 
- Note the base `Handler` class defines a `stacks`/`repository_name` helper that scopes lookups to `Repository.from_github_repo_name(repository_name)` [4](#0-3)  — but `StatusHandler#process` does not use this helper at all, bypassing repository scoping entirely.
- `Commit#create_status_from_github!` → `add_status` mutates `statuses`, recomputes `status`, and on a state transition (e.g. `failure` → `success`) fires `Hook.emit(:deployable_status, stack, ...)` for the commit's *actual* `stack`, whichever stack that row belongs to. [5](#0-4) 

Exploit flow: an attacker who owns/controls any GitHub repository with the Shipit GitHub App installed (satisfying `verify_signature` for their own org) pushes/creates a commit whose SHA is identical to a commit that also exists in a victim's stack — which is realistic for shared/forked/vendored code, cherry-picks, or common upstream commits tracked by multiple Shipit stacks. The attacker's repo then emits a `status` webhook (`state: success`, arbitrary `context`/`description`) for that SHA. Because Shipit does not check that the payload's `repository.full_name` equals the commit's own stack repository, every `Commit` row across every stack sharing that SHA gets updated, potentially flipping `failure` → `success` and firing `deployable_status` (and `commit_status`) hooks for stacks the attacker never authenticated against.

None of the listed guards catch this: `verify_signature` only authenticates the *sender's own* org/app, not the *target* repo/stack relationship; `drop_unhandled_event` only checks the event type is registered; the `ExplicitParameters` schema for `StatusHandler` only validates shape (`sha`, `state`, etc.), not repository identity; there is no `force_github_authentication`, `require_permission!`, or `stacks` scoping applied inside `StatusHandler#process`.

### Impact Explanation
A payload authenticated only for the attacker's own repository can flip `commit.state` and fire `Hook.emit(:deployable_status, ...)` for a completely unrelated victim stack, i.e. a payload for one repository mutating another's stack/commit state — this matches the Critical category "a payload for one repository mutating another's stack, commit, task or team." It also causes forged hook delivery (info disclosure of the existence/behavior of victim's configured hook endpoints) and can corrupt CI gating (turning a `failure` into `success`), potentially enabling downstream continuous-deployment logic (`schedule_continuous_delivery`) to treat a commit as deployable when it should not be. This is repeatable against any commit whose SHA collides across stacks under the attacker's control.

### Likelihood Explanation
The precondition is a real-world-plausible SHA collision between a commit tracked by the attacker's authenticated repo/org and a commit tracked by a victim's stack — most practically achieved via shared history (forks, vendored/cherry-picked commits, monorepo submodule commits, or shared open-source dependencies tracked as commits in multiple Shipit stacks). The attacker needs their own GitHub repo/org onboarded with the Shipit GitHub App (a normal, unprivileged action for an app that supports self-service installation), and no Shipit session, API token, or maintainer role on the victim stack. Cost is low: crafting one webhook `status` payload matching a known SHA. It is fully repeatable per shared-SHA commit.

### Recommendation
In `StatusHandler#process`, verify `params.dig('repository','full_name')` (or equivalent) equals `commit.stack.repository.full_name`/`commit.github_repo_name` before calling `commit.create_status_from_github!(params)`, and skip/reject commits whose owning stack repository doesn't match the payload's repository — mirroring the `stacks`/`repository_name` scoping helper already defined in the base `Handler` class.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb
test "status from an unrelated repository does not mutate a commit belonging to a different stack" do
  victim_stack = shipit_stacks(:shipit)
  attacker_repo_full_name = "attacker/unrelated-repo"

  commit = victim_stack.commits.create!(sha: "deadbeef" * 5, message: "shared commit")
  commit.statuses.create!(stack: victim_stack, state: "failure", context: "ci/tests")

  params = {
    "sha" => commit.sha,
    "state" => "success",
    "context" => "ci/tests",
    "repository" => { "full_name" => attacker_repo_full_name, "owner" => { "login" => "attacker" } },
  }

  assert_no_difference -> { commit.reload.state } do
    refute_hook_emit(commit, :deployable_status) do
      Shipit::Webhooks::Handlers::StatusHandler.call(params)
    end
  end

  assert_equal "failure", commit.reload.state
end
```
Both sides of the equality: `params.dig('repository','full_name')` = `"attacker/unrelated-repo"` vs `commit.stack.repository.full_name` = victim stack's actual repo — they differ, yet current code never checks this, so the existing implementation would incorrectly flip `commit.state` to `success` and emit `deployable_status`, which the assertions above would catch as a failing test against current `HEAD`.

      reload # to get the statuses into the right order (since sorted :desc)
