## Analog Found

### Title
AA bonding-curve/exchange-rate logic that reads live `balance[asset]`/`trigger.output[[...]]` with no attacker-supplied minimum-output can be sandwiched via level-controlled unit ordering - (File: aa_composer.js, main_chain.js, parent_composer.js)

### Summary
The SafEth report shows that computing a swap/stake amount from a spot price that can be shifted by an attacker inside the same "atomic" execution window, combined with a fixed protocol-side slippage tolerance instead of a caller-supplied `minOut`, lets an MEV actor front-run and back-run the victim for profit. Obyte AAs have the same structural weakness: any AA that prices a swap, deposit or divest from its own current `balance[asset]` (e.g. the shipped reference pattern in `test/samples/uniswap_like_market_maker.oscript`) computes that price only from state that is mutable by whichever unit executes immediately before it, and the ocore engine determines "immediately before/after" by a unit's `level`, which is freely chosen by whoever composes the unit.

### Finding Description
AA triggers are not processed as soon as a unit is broadcast; they are only queued once the unit's MCI stabilizes, and then executed in a fully deterministic order: [1](#0-0) 

and consumed in that same order by the composer: [2](#0-1) 

The primary sort key after `mci` is `level`. `level` is simply `max(parent levels) + 1`, and any account composing a unit chooses its own parents (and therefore its own level) via `pickParentUnitsAndLastBall`/`pickParentUnits`: [3](#0-2) [4](#0-3) 

Because parent selection is a normal, unprivileged capability of every wallet (not something that requires a malicious peer, hub, or node), an attacker who observes a pending, not-yet-stable trigger unit addressed to a price-sensitive AA can:
1. Compose a "front-run" unit built on parents that keep its level at or below the victim's unit, so it is ordered first once both land in the same stabilizing MCI.
2. Compose a "back-run" unit that takes the victim's unit (or a descendant of it) as a parent, guaranteeing a strictly higher level so it is ordered last.

Meanwhile, the AA logic itself, as documented in this very repository's reference AA samples, derives swap/issue amounts purely from its own live balance at execution time, with no caller-supplied minimum-output guard: [5](#0-4) [6](#0-5) 

The AA balance used for this pricing is exactly the mutable, per-execution state populated at trigger time: [7](#0-6) 

There is no mechanism analogous to a `minOut` parameter enforced against the trigger sender's expectations, and no TWAP — the "spot" `balance[asset]` ratio at the moment the trigger executes is used directly, just like SafEth's use of the Uniswap spot price with only a fixed `maxSlippage`.

### Impact Explanation
Any AA that follows this documented pricing pattern (a legitimate, encouraged pattern shown in `uniswap_like_market_maker.oscript`, `sell_asset_for_bytes.oscript`) is exposed to loss of value for the victim trigger sender and extraction of value by the attacker, exactly mirroring the SafEth impact: the victim receives fewer output-asset units than the fair pre-trade price implied, and the attacker profits risklessly by reversing their front-run trade after the victim's trigger executes. This is a direct fund-loss vector for AA users and can drain value from the AA's liquidity pool over repeated exploitation.

### Likelihood Explanation
Composing a unit with specific parents to control `level` relative to an observed pending unit is a standard, unprivileged wallet operation — no special network position, hub role, or protocol violation is required, only visibility of the still-unstable victim unit (readily available to any full/light node watching the DAG) and the ability to compose two ordinary units. Given that this bonding-curve pricing pattern is explicitly documented as a reference implementation in the codebase, any AA author who follows it inherits the vulnerability, making exploitation likelihood high wherever such AAs hold meaningful liquidity.

### Recommendation
- AA authors should require the trigger to supply an explicit minimum-acceptable-output (or maximum price) in `trigger.data`, and `bounce()` if the AA's live-balance-derived output would violate it, so slippage is controlled by the trigger sender rather than by the AA's internal spot ratio.
- Prefer averaged/time-weighted internal accounting (e.g., accumulate volume/price over multiple MCIs) instead of a single-unit live balance ratio for AAs that function as automated market makers, reducing the value an attacker can extract via ordering games around a single stabilizing MCI.
- Document this ordering-manipulation risk prominently next to the `uniswap_like_market_maker.oscript` sample, since it is currently presented without any slippage-protection guidance.

### Proof of Concept
1. AA `X` holds a bonding-curve pool of `base` and asset `A`, pricing swaps as `new_balance = round(balance[$asset]*balance[base]/new_balance[other])`, following exactly the pattern in `test/samples/uniswap_like_market_maker.oscript` lines 102-145.
2. Victim broadcasts unit `V` with a large payment output to `X` requesting an asset swap; `V` is still unstable/free.
3. Attacker composes unit `F` (front-run) selecting parents such that `level(F) <= level(V)` (e.g., parenting off `V`'s own parents, excluding `V`), sends a swap in the same direction as the anticipated large trade, shifting `X`'s pool ratio unfavorably for `V`.
4. Attacker composes unit `B` (back-run) parenting `V` (or a unit that includes `V`), guaranteeing `level(B) > level(V)`, reversing `F`'s trade once `V`'s unfavorable execution has moved the pool balance.
5. When the MCI containing `F`, `V`, `B` stabilizes, `handleAATriggers` processes them in `level` order — `F` first, `V` second (at a worse price than the pre-trade ratio), `B` last (extracting the price impact from `F`+`V`) — reproducing the SafEth sandwich pattern entirely through ordinary, unprivileged unit composition allowed by `pickParentUnitsAndLastBall` and the deterministic `mci, level, unit, address` trigger ordering in `main_chain.js`/`aa_composer.js`.
