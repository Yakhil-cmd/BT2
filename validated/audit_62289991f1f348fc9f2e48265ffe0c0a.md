### Title
Unauthenticated `.git/sg-reviewed-shas` entries let a repo contributor permanently suppress security review of their own commits - (File: plugins/security-guidance/hooks/diffstate.py)

### Summary
The security-guidance plugin's commit-review and push-sweep hooks decide whether to run an LLM security scan on a commit by checking a repo-local, append-only log file, `.git/sg-reviewed-shas`, that records which SHAs have "already been reviewed." [1](#0-0)  The reader, `_load_reviewed_shas`, accepts any well-formed 40-hex-character line in that file as proof a commit was reviewed, with no cryptographic binding to an actual review having occurred. [2](#0-1) 

### Finding Description
This is analogous to the reported JoePair DOS: in the original finding, the token owner front-runs the `pair` state-initializing action (`createPair()`), so the `pair` variable is permanently left in a state that satisfies "already handled" and gate-protected functions (`withdrawLiquidity`, `withdrawIncentives`) become permanently unreachable. [3](#0-2) 

Here, the analogous gate is `.git/sg-reviewed-shas`, which is treated as the durable record of "this commit was already handled" (reviewed) and is used to skip further security-review action:
- `_load_reviewed_shas` returns a bare `set()` of hex strings read straight from the file, with only a syntactic hex/length check — no signature, no correlation to an actual LLM review run. [2](#0-1) 
- `_append_reviewed_shas` writes entries with `fcntl.flock`-guarded read-modify-write, but the file itself lives under `.git/` in the working tree and is writable by anyone with write access to the local clone (an ordinary contributor — the same actor the security review is meant to check). [4](#0-3) 
- `handle_commit_review_posttooluse`'s reflog-based fallback path explicitly filters out any SHA already present in this file before running a review: `_already = _load_reviewed_shas(_root); _reflog_shas = [s for s in _fresh if s not in _already]`. [5](#0-4) 

Because the file's contents are attacker-writable (any local user/process with filesystem access to the repo, including code the agent itself might execute via Bash, or a contributor preparing a malicious commit) and are trusted without verification, an attacker can pre-populate `.git/sg-reviewed-shas` with the SHA(s) of a soon-to-be-created malicious commit (or with the outcome of a commit-amend chain) before or immediately after committing. This "front-runs" the gate the same way the JoePair attacker front-runs `createPair()` — the state that should only be set as a side effect of a genuine review is instead pre-seeded, permanently short-circuiting the check for that SHA.

### Impact Explanation
If reachable, this permanently disables the security-guidance plugin's commit-review/push-sweep security gate for attacker-chosen commits, meaning malicious or vulnerable code introduced by an untrusted/lower-trust contributor is never flagged to the user or the model, and the "reviewed" bookkeeping used by the push-sweep to skip diff ranges compounds the bypass across pushes (since the push-sweep advances its diff base past the "already reviewed" contiguous prefix). This is a security-control bypass rather than mere availability loss, arguably more severe than the original DOS analog because it silently defeats the defensive mechanism rather than just blocking withdrawals.

### Likelihood Explanation
Exploitation requires local filesystem write access to `.git/` in the clone being reviewed (e.g., a malicious script, a compromised dependency running during a build/test step invoked via Bash, or a lower-trust collaborator with repo write access). This is a real but narrower trust boundary than a fully remote/unauthenticated attacker, and I could not fully verify from the indexed code alone (a) whether the primary (non-reflog, output-based) commit-review path also consults `_load_reviewed_shas` before reviewing — only the reflog-fallback branch was confirmed to check it — or (b) all call sites in `handle_push_sweep_posttooluse` that consume this file. This limits certainty on how broadly the bypass applies versus being confined to the reflog-fallback edge case.

### Recommendation
Do not treat `.git/sg-reviewed-shas` as authoritative proof of review. Either (a) sign/HMAC each entry with a secret not accessible to arbitrary repo content/processes, (b) store the review ledger outside the repository working tree in a location not writable by code executed from within the repo (e.g., under the per-user `SECURITY_WARNINGS_STATE_DIR`, similar to the session state files), or (c) re-verify at push-sweep/commit-review time that a corresponding review record (e.g., matching findings/telemetry) actually exists rather than trusting the SHA log alone.

### Proof of Concept
Not independently executed; based on static code reading only:
1. In a local clone, run `printf '%s\t%d\t0\t0\n' "$(git rev-parse HEAD~0 | git commit-tree ...)" "$(date +%s)" >> .git/sg-reviewed-shas` — i.e., pre-write a line with the SHA of a commit you are about to create.
2. Make the malicious commit with that exact SHA (deterministic, since git commit SHAs can be computed/predicted before committing given tree/parent/author/committer/timestamp/message).
3. Trigger the commit-review PostToolUse hook via a suppressed-output path that forces `handle_commit_review_posttooluse` down the reflog-fallback branch (e.g., `git commit -q ... | tail -1` per the docstring at [6](#0-5) ).
4. Observe that `_reflog_shas` excludes the pre-seeded SHA via `_load_reviewed_shas`, so `commit_succeeded` stays reliant on the fallback finding "no fresh unreviewed commits," causing the review to be skipped (`skip_21_sub = 2`) even though no genuine LLM review ever ran on that commit's content. def _load_reviewed_shas(repo_root):
```python
    """Set of full 40-hex shas previously reviewed in this clone."""
    p = _reviewed_shas_path(repo_root)
    if not p or not os.path.exists(p):
        return set()
    out = set()
    try:
        with open(p, "r") as f:
            for line in f:
                sha = line.split("\t", 1)[0].strip()
                if len(sha) == 40 and all(c in "0123456789abcdef" for c in sha):
                    out.add(sha)
    except OSError:
        pass
    return out
```

```python
def _append_reviewed_shas(repo_root, shas, vulns_found=0):
    """Record that `shas` were reviewed. Best-effort; never raises.

    Uses fcntl.flock for the read-gc-write; appends are O_APPEND-atomic but
    GC needs the lock so concurrent CC sessions in the same clone don't race
    each other's truncation.
    """
    p = _reviewed_shas_path(repo_root)
    if not p or not shas:
        return
    import time as _time
    ts = int(_time.time())
    pv = _PV or 0
    lines = [f"{s}\t{ts}\t{pv}\t{int(vulns_found)}\n" for s in shas]
    try:
        import fcntl
        with open(p, "a+") as f:
            fcntl.flock(f.fileno(), fcntl.LOCK_EX)
            try:
                f.seek(0)
                existing = f.read().splitlines(keepends=True)
                # Dedup by sha (first column) — keep newest, then cap.
                seen = set()
                merged = []
                for ln in (existing + lines)[::-1]:
                    sha = ln.split("\t", 1)[0].strip()
                    if sha and sha not in seen:
                        seen.add(sha)
                        merged.append(ln if ln.endswith("\n") else ln + "\n")
                merged = merged[:_REVIEWED_SHAS_CAP][::-1]
                f.seek(0)
                f.truncate()
                f.writelines(merged)
            finally:
                fcntl.flock(f.fileno(), fcntl.LOCK_UN)
    except (OSError, ImportError):
        # fcntl unavailable (Windows) or write failed — degrade to plain
        # append; cap enforcement happens on the next locked write.
        try:
            with open(p, "a") as f:
                f.writelines(lines)
        except OSError:
            pass
```
