### Title
Cross-organization forgery of commit statuses via `WebhooksController` — organization-scoped signature verification is not bound to the repository the payload acts on (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
In multi-organization Shipit deployments (documented in `docs/setup.md` and exercised in `test/dummy/config/secrets_double_github_app.yml`), each GitHub organization configures its own GitHub App with its own `webhook_secret`. `WebhooksController#verify_signature` selects which secret to validate the HMAC signature against using a field taken from the very payload it is about to trust — `repository.owner.login` (or `organization.login`) — and then hands the *entire* parsed payload to event handlers that act on unrelated fields (`repository.full_name` for pushes, or nothing at all for statuses). Nothing binds the organization whose secret validated the signature to the repository/commit the handler subsequently mutates. An org admin who legitimately owns a small, low-privilege organization's webhook secret can therefore forge signed webhook deliveries that update commit statuses (and, more weakly, trigger syncs) for **any other organization's stacks** hosted on the same Shipit instance.

### Finding Description
`WebhooksController#verify_signature` resolves the app/secret purely from attacker-controlled JSON: [1](#0-0) 

`repository_owner` is derived from the same raw body that is later parsed and dispatched to handlers: [2](#0-1) 

`Shipit.github(organization:)` looks up a completely independent per-organization config/secret (multi-org mode is active whenever `secrets.github.keys.first` is not one of `TOP_LEVEL_GH_KEYS`): [3](#0-2) 

Once the signature check passes (using organization A's secret), the raw payload — including any other field the attacker put in it — is handed unmodified to handlers: [4](#0-3) 

Critically, `StatusHandler#process` never checks which repository/organization the `sha` belongs to — it matches commits **globally across the entire installation**: [5](#0-4) 

So the "authenticated organization" (whose secret produced a valid HMAC over the request body) and the "commit/repository the handler writes to" are two independent trust domains that the controller never reconciles — exactly the broken deployment-trust binding described in the report: an entity that authenticated (org A) vs. the resource actually written (stack/commit belonging to org B).

`PushHandler` has a related but weaker version of the same flaw: it authenticates against `repository.owner.login`, yet resolves the target stacks from `repository.full_name` — a second, independently attacker-controlled field in the same signed body: [6](#0-5) [7](#0-6) 

Nothing in `Shipit::Webhooks::Handlers::Handler` or the controller enforces that `repository.full_name`'s owner segment equals the `repository_owner`/`organization.login` value that selected the verifying secret.

### Impact Explanation
The `add_status` path invoked by `create_status_from_github!` drives deploy gating (`deployable?`, `blocked?`) and even automatically schedules continuous delivery when a commit becomes `success?`: [8](#0-7) [9](#0-8) 

An attacker who is a legitimate GitHub org admin for **their own**, unrelated organization onboarded on the same Shipit instance can sign a forged `status` webhook with their own org's `webhook_secret`, set the `sha` field to a real commit hash belonging to a victim organization's stack, and mark it `success`. Because `StatusHandler` performs no ownership check, this fabricates a passing CI status for a commit the attacker does not control, which can make that commit `deployable?` and can trigger `schedule_continuous_delivery`, resulting in an **unauthorized deploy** of a victim's stack. This satisfies the "Critical — an unauthorized deploy" impact criterion.

### Likelihood Explanation
Exploitation requires only that the attacker be a legitimate, low-privilege owner/admin of *any* organization configured on the same shared/multi-tenant Shipit instance (a documented, supported configuration) — no access to the victim's secrets, GitHub App, repository, or Shipit user session/API token is needed. The only guesswork required is the victim's commit SHA, which is often publicly visible (GitHub, PR links, CI logs). This is a realistic scenario for any Shipit deployment serving multiple independent GitHub organizations.

### Recommendation
Bind the verified organization to the resource being mutated:
- In `WebhooksController#verify_signature`, after verifying the signature, pass the verified `repository_owner`/organization down to handlers.
- In `Handler#stacks`/`PushHandler`, reject or filter out any target stack/repository whose owning organization does not match the organization whose secret verified the signature.
- In `StatusHandler#process` (and `CheckSuiteHandler`), scope the `Commit`/`Stack` lookup to repositories belonging to the verified organization instead of querying `Commit` globally by `sha`.

### Proof of Concept
Assume a multi-org Shipit instance with orgs `attacker-org` (attacker is admin, knows `webhook_secret_A`) and `victim-org` (hosts stack with commit `deadbeef...`, currently pending/failing CI).

1. Attacker crafts a `status` event JSON body:
```json
{
  "sha": "<victim-commit-sha>",
  "state": "success",
  "context": "ci/build",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "attacker-org/attacker-repo" }
}
```
2. Attacker computes `X-Hub-Signature: sha1=HMAC_SHA1(webhook_secret_A, raw_body)` using their own known secret for `attacker-org`.
3. POST to `/webhooks` with `X-Github-Event: status`.
4. `verify_signature` resolves `repository_owner => "attacker-org"`, fetches `Shipit.github(organization: "attacker-org")`, and the HMAC validates successfully (attacker legitimately knows this secret).
5. `WebhooksController#create` dispatches to `StatusHandler`, which runs `Commit.where(sha: params.sha)` — matching the victim's commit regardless of organization — and calls `commit.create_status_from_github!(params)`, injecting a forged `success` status onto the victim's commit, potentially making it `deployable?` and triggering continuous delivery.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
