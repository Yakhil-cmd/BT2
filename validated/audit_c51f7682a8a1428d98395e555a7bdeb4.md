### Title
Cross-organization commit-status forgery via unscoped `sha` lookup in `StatusHandler` — ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` authenticates an inbound GitHub webhook against the GitHub App/organization identified by `repository.owner.login` in the JSON body [1](#0-0) . That verified field, however, is never used to scope which record the corresponding handler acts on. `Shipit::Webhooks::Handlers::StatusHandler#process` looks up the target `Commit` purely `Commit.where(sha: params.sha)`, with no repository/stack/organization scoping at all [2](#0-1) . This breaks the binding: *organization that authenticated (via `repository.owner.login` + that org's `webhook_secret`) ≠ repository/stack whose commit status is written (any stack in the entire installation that happens to contain a commit with that `sha`)*.

### Finding Description
The webhook signature check only proves the request was signed with the `webhook_secret` configured for the organization named in `repository.owner.login` [1](#0-0) . It never verifies that the rest of the JSON body (used by the actual event handler) is consistent with that organization/repository — the raw parsed body is dispatched unchanged to every registered handler for the event: `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` [3](#0-2) .

For the `status` event, `StatusHandler` only requires `sha` and `state` (plus optional `description`, `target_url`, `context`, `created_at`) — it does not require or use `repository.full_name` at all [4](#0-3) . It resolves the target commit with `Commit.where(sha: params.sha)`, a global, unscoped query across every `Stack`/`Repository` tracked by the Shipit instance [2](#0-1) . It then calls `commit.create_status_from_github!(params)`, which writes a new `Status` row for that commit using attacker-supplied `state`/`description`/`target_url`/`context` [5](#0-4) .

Because a Shipit installation typically hosts many organizations/repositories, each configured with its own independent `webhook_secret` (see `config/secrets.development.shopify.yml` showing multiple orgs each with their own `webhook_secret`) [6](#0-5) , an actor who legitimately controls one onboarded organization (and therefore knows/derives that organization's `webhook_secret`, or can trigger a real delivery from their own GitHub org) can forge a `status` webhook whose `repository.owner.login` matches their own org (so `verify_signature` passes), but whose `sha` value names a commit that actually belongs to a **different** organization's stack — e.g., the SHA of a well-known public commit on a victim repository that Shipit has already ingested via its own push/sync flow.

This mirrors the audited bug class exactly: the verified/authenticated identity (`repository.owner.login` and its matching `webhook_secret`) is decoupled from the entity actually mutated (an arbitrary `Commit` row matched solely by `sha`), the same "checked X, acted on Y" mismatch as the USDT `safeTransferOut` report (checked for a return value that the call path could never produce; here, checked identity that the write path never re-validates).

### Impact Explanation
Commit statuses directly gate deploy safety logic: `Commit#deployable?` requires `success? && !blocked?` [7](#0-6) , and a status transition can trigger `Hook.emit(:deployable_status, ...)` and `stack.schedule_merges` and even `ContinuousDeliveryJob.perform_later(stack)` for stacks with continuous deployment enabled [8](#0-7) [9](#0-8) . An attacker who only controls one onboarded organization's webhook credentials can therefore forge a "success" status for a commit belonging to a victim stack under continuous deployment, causing that stack to auto-deploy a commit whose CI never actually passed — an unauthorized deploy triggered purely by cross-organization identity confusion in the webhook pipeline. It can equally be used to forge a "failure"/"error" status to block a legitimate deploy on a victim's stack (denial of an intended deploy), or emit falsified `commit_status`/`deployable_status` hook events to any external systems Shipit forwards them to.

### Likelihood Explanation
The prerequisite is possession of a `webhook_secret` for *any one* organization onboarded to the Shipit instance — not the victim organization's secret, and not a privileged Shipit user session or `ApiClient` token. Multi-tenant Shipit deployments (as shown by the sample secrets config listing multiple independent orgs) are the documented normal use case, so an org admin among many tenants is a realistic "unprivileged" attacker relative to other tenants' stacks. The only extra requirement is guessing/obtaining a `sha` that exists in the victim stack, which is not secret (commit SHAs are visible in GitHub history, PRs, CI logs, etc.). This is a plausible, low-effort path once the trust boundary is understood.

### Recommendation
Scope the `Commit` lookup (and any other handler's) to the repository actually authenticated by `verify_signature`, not just by `sha`. Concretely, thread the verified `repository_owner`/`full_name` through to `Handler#stacks`/`StatusHandler#process`, and require that `commit.stack.repository.full_name` (or owner) matches `payload.dig('repository', 'full_name')`/`owner.login`, and cross-check that this matches the organization whose `webhook_secret` actually verified the signature — rejecting the event otherwise. More generally, every handler should derive its target Stack/Repository the same way `verify_signature` derives the authenticating organization, and reject payloads where these disagree.

### Proof of Concept
1. Shipit is configured (per `config/secrets*.yml`) with two independent GitHub orgs, `attacker-org` and `victim-org`, each with its own App/`webhook_secret`.
2. Attacker knows/controls `attacker-org`'s `webhook_secret` (they administer that GitHub App installation).
3. Attacker identifies a commit SHA already tracked by Shipit under a `victim-org` stack (e.g., visible via the public Shipit UI, GitHub, or a previous push webhook).
4. Attacker POSTs to `/webhooks` with header `X-Github-Event: status` and body:
```json
{
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "attacker-org/whatever" },
  "sha": "<victim commit sha>",
  "state": "success",
  "context": "ci/forged",
  "created_at": "2026-09-01T00:00:00Z"
}
```
signed with `attacker-org`'s `webhook_secret` via `X-Hub-Signature`.
5. `verify_signature` resolves `repository_owner` = `"attacker-org"`, fetches `Shipit.github(organization: "attacker-org")`, and successfully verifies the HMAC [1](#0-0) .
6. `StatusHandler.call(params)` runs `Commit.where(sha: params.sha)` and finds the victim's commit regardless of `attacker-org` context, then calls `create_status_from_github!(params)`, writing a forged "success" status onto the victim's commit [2](#0-1) [5](#0-4) .
7. If the victim stack has `continuous_deployment?` enabled, `Commit#schedule_continuous_delivery` fires `ContinuousDeliveryJob.perform_later(stack)`, deploying the victim's commit based on the forged status [9](#0-8) .

      already_deployed = deployed?

      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }

        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
