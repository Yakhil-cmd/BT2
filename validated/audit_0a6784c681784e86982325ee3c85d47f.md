### Title
Accrual overflow in `scaled_to_original` permanently freezes a large high-utilization market — panic on every verb - (File: contracts/pool/src/interest.rs)

### Summary
The CVE class is a crafted input that drives parsing/arithmetic into an unhandled crash, giving a denial of service. The analog in XOXNO Lending is the RAY-scaled value ceiling in the pool's interest accrual: for a sufficiently large market run at sustained high utilization, the borrow index growth eventually makes `scaled_to_original` overflow `i128` and panic with `MATH_OVERFLOW`. Because interest accrual runs at the head of every pool verb, the first panic permanently bricks the market: no supply, borrow, withdraw, repay, liquidation, or `clean_bad_debt` can ever execute again. A dedicated test in the repo demonstrates the freeze and shows the `MAX_BORROW_INDEX_RAY` cap does not engage before the value-level overflow, contradicting the documented bound in `docs/reference/formulas.md` [1](#0-0) .

### Finding Description
Pool markets track positions as RAY-scaled shares unscaled through `scaled_to_original` against RAY indexes in `contracts/pool/src/cache/scale.rs`, with accrual executed first inside `contracts/pool/src/interest.rs`. The unscaled RAY product (`scaled_amount * index`) must fit in `i128`; for a whale-scale market (on the order of 10^27 base units on an 18-decimal asset), only ~170x of index growth remains before the product overflows. At the steep segment of the XLM-style interest curve under ~98% utilization, the borrow index crosses that range over a multi-year horizon, while the `MAX_BORROW_INDEX_RAY` ceiling is checked too late to stop the arithmetic panic [2](#0-1) . Once any accrual overflows, the panic is deterministic and state-dependent rather than input-dependent: every subsequent call that touches the market — including `withdraw` and `repay`, which accrue before settling — hits the same `MATH_OVERFLOW` and reverts [3](#0-2) .

### Impact Explanation
All tokens custodied in the affected market become permanently frozen. Suppliers cannot withdraw, borrowers cannot repay, liquidators cannot liquidate, and bad-debt cleanup and index updates all revert, since each path runs the same accrual that panics. This is a permanent freezing of user funds, not a transient fail-closed condition, and it also freezes unclaimed yield accrued in the market's revenue shares.

### Likelihood Explanation
Triggering requires an adversary (or organic growth) to build a market whose scaled debt is within ~170x of the `i128` RAY ceiling — i.e., a very large-denomination market — and then keep it at high utilization for an extended period so the borrow index compounds past the overflow point. An unprivileged address can drive this with `supply`, `borrow`, and `update_indexes` on a high-decimal, uncapped market; the blocker is capital and duration rather than permission. The failure is deterministic once the threshold is crossed, and the in-repo test confirms there is no guard that rescues the market. Medium likelihood, Medium severity.

### Recommendation
Compute accrued totals in a wider type (or checked mul/div with an explicit early clamp) inside `interest.rs` accrual and `scale.rs` `scaled_to_original`, and enforce `MAX_BORROW_INDEX_RAY` before any RAY product that can exceed `i128` — e.g., cap the index at accrual time so every later unscale stays in range. At minimum, make `withdraw`/`repay` settle against the last committed index when the new accrual would overflow, so exits remain possible, and correct the documented horizon bound in `docs/reference/formulas.md`.

### Proof of Concept
The repo's own harness reproduces it end to end: seed an 18-decimal market with ~10^27 supplied, borrow ~98%, then advance time yearly; `try_update_indexes_for` eventually returns `MATH_OVERFLOW` while `borrow_index < MAX_BORROW_INDEX_RAY`, and afterwards both `try_withdraw_raw` and `try_repay` fail with the same error [4](#0-3) .

/// `i128::MAX`, 170 times that. At the XLM curve's steep segment the index
/// grows past 170x in a few years, and the next accrual panics inside
/// `scaled_to_original`. Every verb accrues first, so the market freezes:
/// no repay, no withdraw, no liquidation. The index cap never engages.
#[test]
fn a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap() {
    let mut t = LendingTest::new()
        .with_market(big("BIG18", 18, xlm_curve()))
        .with_market(col())
        .with_max_utilization_disabled_all_markets()
        .build();
    lift_caps(&t, "BIG18", 18);
    lift_caps(&t, "COL", 7);
    let principal = BILLION * 10i128.pow(18);
    t.supply_raw(BOB, "BIG18", principal);
    let debt = principal / 100 * 98;
    t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
    t.borrow_raw(ALICE, "BIG18", debt);

    let mut years = 0u32;
    let failure = loop {
        years += 1;
        assert!(
            years <= 40,
            "no cliff within 40 years; the bound in docs/reference/formulas.md is wrong"
        );
        t.advance_time(YEAR_SECS);
        if let Err(e) = t.try_update_indexes_for(&["BIG18"]) {
            break e;
        }
    };
    let failed: Result<(), soroban_sdk::Error> = Err(failure);
    assert_contract_error(failed, errors::MATH_OVERFLOW);
    let last = book(&t, "BIG18");
    assert!(
        last.borrow_index < MAX_BORROW_INDEX_RAY,
        "the index cap did not engage before the value overflow"
    );
    // The market is frozen: exits and repayments accrue first and hit the same panic.
    assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
    assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
    std::println!(
        "ray-value cliff reached after {years} years at 98 percent utilization on the XLM curve; last index x{:.1}",
        last.borrow_index as f64 / RAY as f64
    );
}
