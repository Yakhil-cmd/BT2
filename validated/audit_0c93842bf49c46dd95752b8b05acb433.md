**Analysis:**

The premise doesn't hold up against how Move's type system actually works. In `view_function.rs`, the `ty_args` supplied by the caller are ordinary `TypeTag`s that are resolved completely independently of `view_function.module` — they are never used to look up structs "in the context of" the called function's module.

Each `TypeTag::Struct` variant carries its own fully-qualified `StructTag { address, module, name, type_args }`. When the VM resolves a struct type from a tag, module identity is derived directly from that struct tag's own `address`/`module` fields, not from the module of the function being invoked. This is visible in the lazy loader's `metered_load_type`, which builds a `ModuleId` straight from the struct tag being resolved: [1](#0-0) . Likewise, the layout builder used for annotated/BCS-decoded layouts constructs the `StructTag` (and thus module binding) from the compiled module actually being visited (`m.self_id()`), never from an unrelated caller-declared module (`third_party/move/tools/move-bytecode-utils/src/layout.rs`) [2](#0-1) .

`view_function.module` in `api/src/view_function.rs` is only used to (a) apply the view filter and (b) as the entrypoint module/function for `AptosVM::execute_view_function` [3](#0-2) . The `ty_args` are separately validated and instantiated by the VM (`construct_args`/generic instantiation in `verifier/view_function.rs` and `verifier/transaction_arg_validation.rs`), which resolves each type argument by its own embedded module id — so `0x1::foo::Bar` and `0x2::foo::Bar` (same struct name, different modules) are structurally distinguished by address, and there's no code path that conflates them or substitutes one module's struct definition into another module's namespace [4](#0-3) .

Because module binding for generic type arguments is intrinsic to the `TypeTag`/`StructTag` data itself (verified structurally by the loader against the on-chain module at that address), an attacker cannot cause the executed function to "borrow" a struct layout from a different module than the one the tag names — this is a core invariant of Move's fully-qualified naming, not something `view_function.rs` implements or could violate on its own. No admission-boundary sender/signer/fee-payer/module-context confusion results from attacker-chosen `ty_args`.
