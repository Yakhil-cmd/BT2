### Title
CEI violation in `collect_creator_fee` allows reentrant double-collection of creator fees via Token-2022 transfer-hook callback - (File: programs/cp-swap/src/instructions/collect_creator_fee.rs)

### Summary
`collect_creator_fee` performs the two outbound token transfers (the "interaction") before it zeroes `pool_state.creator_fees_token_0` / `creator_fees_token_1` (the "effect"), violating the Checks-Effects-Interactions pattern that the referenced report calls out for `FootiumAcademy.mintPlayer`. Because the vault mints can be Token-2022 mints carrying a `TransferHook` extension, the outbound `transfer_checked` CPI can itself invoke an attacker-controlled hook program before the fee counters are reset.

### Finding Description
`collect_creator_fee` reads the current fee ledger, transfers both amounts out of the vaults, and only afterwards clears the ledger: [1](#0-0) 

The vault transfers are done via `transfer_from_pool_vault_to_user`, which invokes `token_2022::transfer_checked` against whatever `token_program`/mint is supplied for that vault: [2](#0-1) 

`vault_0_mint`/`vault_1_mint` are validated only by address-equality to the vault's mint (`address = token_0_vault.mint`), with no restriction on which SPL-Token-2022 extensions the mint may carry: [3](#0-2) 

If the pool's token mint has the Token-2022 `TransferHook` extension enabled (a standard, permissionless extension a pool creator can choose when creating the mint used for the pool), `transfer_checked` will CPI into the hook program declared on that mint as part of executing the transfer. Because `pool_state` is a zero-copy account (`AccountLoader`), the in-memory/on-chain `creator_fees_token_0/1` fields are still non-zero at the moment the hook executes (the reset at lines 120–121 has not yet run). A hook program that re-invokes `collect_creator_fee` (directly, or via a second instruction later in the same transaction that is unblocked by the callback) sees the pool state with fees still credited and can trigger a second transfer of the same fee amount before the first call's zeroing takes effect, draining vault funds beyond the amount actually owed to the creator.

This is the exact bug class from the external report (state effect after external interaction), but here the impact is concrete because Solana/Token-2022 transfer hooks provide a genuine reentrant callback path into program logic, unlike a plain SPL Token transfer.

### Impact Explanation
Successful exploitation lets the pool creator (or anyone who can get creator-fee-eligible mints configured with a malicious `TransferHook` mint) extract more creator fees than are actually owed, directly draining shared pool vault funds (LP/swapper funds), i.e., "concrete theft ... of user or LP funds" via an unauthorized/duplicated privileged effect (double payout from `creator_fees_token_0/1`). This is a Medium/High-severity accounting/fund-safety issue depending on how much of the vault the fee ledger can represent and how many times the reentrant call chain can be nested/repeated in one transaction.

### Likelihood Explanation
Requires the pool to use a Token-2022 mint with the `TransferHook` extension and a fee balance to collect — a mint configuration fully controllable by whoever creates the pool (or by an attacker who creates a new pool with such a mint and accrues creator fees through swaps against their own pool). No privileged Raydium signer is needed; the attack is reachable from a single submitted transaction with attacker-chosen accounts (the hook program account, the fee mints) and standard `collect_creator_fee` call data, matching the instruction whitelist for this analysis.

### Recommendation
Apply CEI: zero `pool_state.creator_fees_token_0` and `creator_fees_token_1` (cache the amounts locally first) before performing the outbound transfers, e.g.:
```rust
let creator_fees_token_0 = pool_state.creator_fees_token_0;
let creator_fees_token_1 = pool_state.creator_fees_token_1;
...
pool_state.creator_fees_token_0 = 0;
pool_state.creator_fees_token_1 = 0;

transfer_from_pool_vault_to_user(... creator_fees_token_0 ...)?;
transfer_from_pool_vault_to_user(... creator_fees_token_1 ...)?;
```
Additionally, consider explicitly rejecting vault mints that carry the Token-2022 `TransferHook` extension for fee-bearing pools, or add an explicit reentrancy guard flag on `PoolState` that is checked/set before any outbound transfer and cleared at the end of the instruction, consistent with how `deposit`/`withdraw`/`swap_base_input`/`swap_base_output` already update `lp_supply`/fee accumulators before performing token transfers.

### Proof of Concept
1. Create a pool where `token_0_mint` (or `token_1_mint`) is a Token-2022 mint configured with the `TransferHook` extension pointing to an attacker-controlled hook program, and the attacker is the `pool_creator`.
2. Perform swaps to accrue nonzero `creator_fees_token_0`/`creator_fees_token_1` in `pool_state`.
3. Call `collect_creator_fee`. The instruction reads `creator_fees_token_0 = X`, then calls `transfer_from_pool_vault_to_user` for token_0, which CPIs into `transfer_checked`, which invokes the attacker's `TransferHook` program as part of the Token-2022 transfer logic (lines 98–107 of `collect_creator_fee.rs`).
4. Inside the hook, the attacker's program re-invokes `collect_creator_fee` (via CPI, since the hook is itself a program that can issue further CPIs) while `pool_state.creator_fees_token_0` is still `X` (the reset at line 120 has not executed yet).
5. The nested call transfers `X` again from `token_0_vault` to `creator_token_0`, and only then both calls proceed to zero the ledger — resulting in `2X` (or more, with deeper nesting) being paid out for a single `X` fee accrual, draining the vault of the difference.

```rust
pub fn collect_creator_fee(ctx: Context<CollectCreatorFee>) -> Result<()> {
    let mut pool_state = ctx.accounts.pool_state.load_mut()?;
    let creator_fees_token_0 = pool_state.creator_fees_token_0;
    let creator_fees_token_1 = pool_state.creator_fees_token_1;
    if creator_fees_token_0 == 0 && creator_fees_token_1 == 0 {
        return err!(ErrorCode::NoFeeCollect);
    }

    let signer_seeds: &[&[u8]] = &[crate::AUTH_SEED.as_bytes(), &[ctx.bumps.authority]];

    transfer_from_pool_vault_to_user(
        ctx.accounts.authority.to_account_info(),
        ctx.accounts.token_0_vault.to_account_info(),
        ctx.accounts.creator_token_0.to_account_info(),
        ctx.accounts.vault_0_mint.to_account_info(),
        ctx.accounts.token_0_program.to_account_info(),
        creator_fees_token_0,
        ctx.accounts.vault_0_mint.decimals,
        &[signer_seeds],
    )?;

    transfer_from_pool_vault_to_user(
        ctx.accounts.authority.to_account_info(),
        ctx.accounts.token_1_vault.to_account_info(),
        ctx.accounts.creator_token_1.to_account_info(),
        ctx.accounts.vault_1_mint.to_account_info(),
        ctx.accounts.token_1_program.to_account_info(),
        creator_fees_token_1,
        ctx.accounts.vault_1_mint.decimals,
        &[signer_seeds],
    )?;

    pool_state.creator_fees_token_0 = 0;
    pool_state.creator_fees_token_1 = 0;
    pool_state.recent_epoch = Clock::get()?.epoch;
```

```rust
pub fn transfer_from_pool_vault_to_user<'a>(
    authority: AccountInfo<'a>,
    from_vault: AccountInfo<'a>,
    to: AccountInfo<'a>,
    mint: AccountInfo<'a>,
    token_program: AccountInfo<'a>,
    amount: u64,
    mint_decimals: u8,
    signer_seeds: &[&[&[u8]]],
) -> Result<()> {
    if amount == 0 {
        return Ok(());
    }
    token_2022::transfer_checked(
        CpiContext::new_with_signer(
            *token_program.key,
            token_2022::TransferChecked {
                from: from_vault,
                to,
                authority,
                mint,
            },
            signer_seeds,
        ),
        amount,
        mint_decimals,
    )
}
```
