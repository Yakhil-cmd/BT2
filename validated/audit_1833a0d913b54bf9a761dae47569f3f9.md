### Title
ERC777-Compatible Token Double-Request in Bridge — Unauthorized Double-Minting of Bridged Assets via `requestERC20Transfer` + `onERC20Received` Reentrancy - (File: `contracts/service_chain/bridge/BridgeTransferERC20.sol`)

---

### Summary

`BridgeTransferERC20.requestERC20Transfer` calls `safeTransferFrom` on the token before calling `_requestERC20Transfer`. If the registered token is ERC777-compatible and calls `onERC20Received` on the bridge during its `transferFrom` execution, `_requestERC20Transfer` is invoked twice for a single actual token deposit. This emits two `RequestValueTransfer` events with distinct nonces, causing bridge operators on the counterpart chain to process two handle-transfers and mint/release 2× the deposited amount.

---

### Finding Description

`BridgeTransferERC20` exposes two deposit paths:

**2-step path** (`requestERC20Transfer`): [1](#0-0) 

```
safeTransferFrom(msg.sender, address(this), _value + _feeLimit)
_requestERC20Transfer(...)   // emits RequestValueTransfer, increments requestNonce
```

**1-step callback path** (`onERC20Received`): [2](#0-1) 

```
// called by the token contract itself after a transfer
_requestERC20Transfer(msg.sender, ...)
```

`onERC20Received` is `public` with no access control beyond the `onlyRegisteredToken` check inside `_requestERC20Transfer`, which uses `msg.sender` as the token address. [3](#0-2) 

`_requestERC20Transfer` has no `nonReentrant` guard (contrast with the KLAY path, which explicitly documents this requirement): [4](#0-3) 

The OZ ERC777 `transferFrom` calls `_callTokensReceived` after moving balances: [5](#0-4) 

A registered ERC777-compatible token whose `transferFrom` calls `bridge.onERC20Received(from, to, value, feeLimit, extraData)` on the recipient (the bridge) during execution causes the following sequence inside a single `requestERC20Transfer` call:

1. `safeTransferFrom` executes → token calls `bridge.onERC20Received(from, to, X, feeLimit, data)` → `_requestERC20Transfer` runs → emits `RequestValueTransfer(nonce=N)`, `requestNonce` becomes `N+1`.
2. `safeTransferFrom` returns.
3. `requestERC20Transfer` calls `_requestERC20Transfer` again → emits `RequestValueTransfer(nonce=N+1)`, `requestNonce` becomes `N+2`.

Two distinct `RequestValueTransfer` events are emitted for one actual token deposit of `X` tokens.

---

### Impact Explanation

Bridge operators on the counterpart chain observe both events and call `handleERC20Transfer` for each nonce. Each call passes the `closedValueTransferVotes` guard (different nonces) and the `_lowerHandleNonceCheck`: [6](#0-5) 

In `modeMintBurn` mode, `ERC20Mintable(_tokenAddress).mint(_to, _value)` is called twice, minting `2×X` tokens to the recipient while only `X` tokens were deposited. In lock/unlock mode, `safeTransfer` is called twice, draining `2×X` tokens from the bridge's liquidity pool. The attacker receives `2×X` bridged assets for `X` deposited tokens — an unauthorized mint/transfer of bridged assets.

---

### Likelihood Explanation

Requires a registered ERC777-compatible token whose `transferFrom` calls `onERC20Received` on the recipient. This is achievable if:
- A bridge owner (or compromised owner) registers a custom ERC777 token that implements this behavior, or
- A legitimate ERC777 token that notifies recipients via a custom hook (not the ERC1820 path) is listed.

Token registration is owner-controlled, but the bridge is designed to support third-party tokens, and the absence of a reentrancy guard on the ERC20 path (while the KLAY path explicitly requires one) indicates this was not considered.

---

### Recommendation

1. Add `nonReentrant` to `_requestERC20Transfer` (or to both `requestERC20Transfer` and `onERC20Received`), consistent with the KLAY path.
2. Add a check in `requestERC20Transfer` that prevents re-entry: record a flag before calling `safeTransferFrom` and revert if `_requestERC20Transfer` has already been called for this invocation.
3. Vet all registered tokens to reject ERC777-compatible tokens that call recipient hooks during `transferFrom`, analogous to the fix in the referenced report.

---

### Proof of Concept

Deploy a malicious ERC777-compatible token `MaliciousToken` registered on the bridge:

```solidity
contract MaliciousToken is ERC20 {
    address public bridge;
    function transferFrom(address from, address to, uint256 amount) public returns (bool) {
        // Standard ERC20 transfer
        _transfer(from, to, amount);
        // ERC777-style hook: call onERC20Received on the bridge
        IBridgeTransferERC20(bridge).onERC20Received(
            from, targetRecipient, amount - feeLimit, feeLimit, extraData
        );
        return true;
    }
}
```

Attack steps:
1. Owner registers `MaliciousToken` on the bridge.
2. Attacker approves bridge for `X + feeLimit` tokens.
3. Attacker calls `bridge.requestERC20Transfer(MaliciousToken, recipient, X, feeLimit, data)`.
4. Inside `safeTransferFrom`, `MaliciousToken.transferFrom` calls `bridge.onERC20Received(...)` → `RequestValueTransfer(nonce=0)` emitted, `requestNonce=1`.
5. `safeTransferFrom` returns; `requestERC20Transfer` calls `_requestERC20Transfer` → `RequestValueTransfer(nonce=1)` emitted, `requestNonce=2`.
6. Counterpart bridge operators call `handleERC20Transfer` for nonce 0 and nonce 1 → `2×X` tokens minted/released to recipient.

Corrupted state: `requestNonce` advanced by 2 for 1 deposit; counterpart chain mints `2×X` tokens against `X` deposited. [7](#0-6) [2](#0-1) [8](#0-7)
