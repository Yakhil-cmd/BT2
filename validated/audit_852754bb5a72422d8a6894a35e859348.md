### Title
Extension binary install downloads to disk from an unvalidated `release.assets[].url` returned by the repo host, mirroring the FogBugz attachment SSRF pattern - ([File: pkg/cmd/extension/http.go])

### Summary
When installing a binary extension with `gh extension install owner/repo`, `gh` fetches the GitHub Releases API response for that repo from `baseRepo.RepoHost()` (which can be `github.com`, a GHES instance, or any host implied by the repo's full name/URL a user is told to install from) and then extracts an asset URL straight out of the JSON body's `url` field. That URL is used verbatim, with no check that it belongs to the expected host, to issue a follow-up authenticated GET request whose response bytes are written directly to an executable file on disk.

### Finding Description
`fetchLatestRelease`/`fetchReleaseFromTag` call the REST API on `baseRepo.RepoHost()` and unmarshal the response into a `release` struct without any host/scheme validation of the nested asset URL: [1](#0-0) 

`installBin` then picks a matching asset and downloads it using `asset.APIURL` unmodified: [2](#0-1) 

`downloadAsset` builds an `http.Request` directly from that URL and streams the response body into a file (`0755`, i.e. executable) with the shared, authenticated `m.client`: [3](#0-2) 

The authenticated `http.Client` used here (`m.client`, built via `api.NewHTTPClient`) auto-attaches an `Authorization: token …` header to any request whose `Host` matches a configured active token host — this is decided purely by the destination host of the outgoing request, not by any allowlist tied to the repository being installed from: [4](#0-3) 

There is no equivalent of the FogBugz report's `WHITELIST`/`valid_domain?` check anywhere in this path — nothing constrains `asset.APIURL`'s host to `baseRepo.RepoHost()`, `api.<host>`, or any GitHub API domain before the request is issued. This is structurally identical to the GitLab bug class: an API response field consumed as a download URL is trusted without host validation, and the resulting request is made by the tool's own authenticated HTTP client to whatever host is embedded in that field.

### Impact Explanation
If the repository host that serves the release JSON (i.e., the GHES/tenant instance or `api.github.com` itself, or anything positioned to tamper with that specific response — compromise, cache poisoning, request smuggling, or a malicious/compromised repo integration that can control the raw REST response body rather than just release asset content) returns a crafted `url` value pointing at an internal address or attacker-controlled host, `gh` will:
1. Make an authenticated `gh` HTTP request to that URL (potential SSRF against internal infrastructure, or credential leak if the crafted host coincidentally matches a configured token host).
2. Write the response body straight to disk as an executable extension binary that the user will subsequently run with `gh <extname>`, yielding code execution.

This matches the report's core weakness class (URL from a semi-trusted upstream API response consumed by a download primitive with no destination validation) rather than a simple "you install untrusted code you chose to install" scenario, because the untrusted point of control here is the *raw API transport layer* to the repo host, not the repository content itself.

### Likelihood Explanation
Exploitation requires the same precondition category as the original report: some vulnerability or compromise on the API-response path for the target host (GHES tenant compromise, response tampering, cache poisoning, request smuggling, or a malicious API proxy for a self-hosted `--hostname`) that lets an attacker control the raw JSON `url` field independent of the actual uploaded asset. This is a non-trivial precondition and not directly attacker-triggerable purely from data an untrusted repo owner controls through normal GitHub release-asset upload flows (GitHub itself generates asset URLs for `github.com`). Likelihood is higher for GHES/enterprise or non-`github.com` hosts where response-shaping is more plausible.

### Recommendation
Before using `asset.APIURL` to build a download request in `pkg/cmd/extension/http.go`'s `downloadAsset`/`installBin`, validate that the asset URL's scheme is `https` (or `http` only for known local/dev hosts) and that its host matches `baseRepo.RepoHost()` or its `api.` subdomain / configured REST prefix — analogous to the FogBugz fix's `valid_domain?` allowlist check. Reject and error out on any asset URL whose host does not match the expected API host for that repo before dispatching the authenticated `http.Client` request.

### Proof of Concept
Not directly reproducible without control over the repo host's raw API response (the same limitation acknowledged in the original report). Conceptually:
1. Attacker controls (or compromises/poisons a response for) the REST endpoint `repos/{owner}/{repo}/releases/latest` on a GHES/tenant host that a victim is instructed to run `gh extension install owner/repo --hostname ghes.victim.example` against.
2. The crafted JSON response sets an asset's `"url"` field to `http://169.254.169.254/latest/meta-data/iam/...` or an internal service URL.
3. `gh extension install` calls `fetchLatestRelease` → `installBin` → `downloadAsset`, which issues the request via the authenticated client and writes the raw response bytes to `~/.local/share/gh/extensions/<repo>/<repo>` with executable permissions.
4. Subsequent invocation `gh <extname>` executes the SSRF-fetched content as a binary.

// downloadAsset downloads a single asset to the given file path.
func downloadAsset(httpClient *http.Client, assetURL safeurl.SafeURL, destPath string) (downloadErr error) {
	var req *http.Request
	if req, downloadErr = http.NewRequest("GET", assetURL.String(), nil); downloadErr != nil {
		return
	}

	req.Header.Set("Accept", "application/octet-stream")

	var resp *http.Response
	// TODO(api-client-rollout)
	// This has been deferred from moving to api.Client due to its custom Accept header and binary response streaming.
	if resp, downloadErr = httpClient.Do(req); downloadErr != nil {
		return
	}
	defer resp.Body.Close()

	if resp.StatusCode > 299 {
		downloadErr = api.HandleHTTPError(resp)
		return
	}

	var f *os.File
	if f, downloadErr = os.OpenFile(destPath, os.O_CREATE|os.O_WRONLY|os.O_TRUNC, 0755); downloadErr != nil {
		return
	}
	defer func() {
		if err := f.Close(); downloadErr == nil && err != nil {
			downloadErr = err
		}
	}()

	_, downloadErr = io.Copy(f, resp.Body)
	return
}

// AddAuthTokenHeader adds an authentication token header for the host specified by the request.
func AddAuthTokenHeader(rt http.RoundTripper, cfg tokenGetter) http.RoundTripper {
	return &funcTripper{roundTrip: func(req *http.Request) (*http.Response, error) {
		// If the header is already set in the request, don't overwrite it.
		if req.Header.Get(authorization) == "" {
			var redirectHostnameChange bool
			if req.Response != nil && req.Response.Request != nil {
				redirectHostnameChange = getHost(req) != getHost(req.Response.Request)
			}
			// Only set header if an initial request or redirect request to the same host as the initial request.
			// If the host has changed during a redirect do not add the authentication token header.
			if !redirectHostnameChange {
				hostname := ghauth.NormalizeHostname(getHost(req))
				if token, _ := cfg.ActiveToken(hostname); token != "" {
					req.Header.Set(authorization, fmt.Sprintf("token %s", token))
				}
			}
		}
		return rt.RoundTrip(req)
	}}
}
