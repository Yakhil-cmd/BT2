### Title
`Api::CCMenuController#stack` bypasses stack-scoped authorization, allowing any CCMenu token to read any stack's deploy status - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Api::CCMenuController` overrides the `stack` method to call `Stack.from_param!(params[:stack_id])` directly instead of using `Api::BaseController#stacks`/`#stack`, which is the only place that enforces `current_api_client.stack_id` scoping. Combined with `CCMenuUrlController#client` never passing `stack:` when creating the `ApiClient` (leaving `stack_id` nil), any minted CCMenu token can read the deploy status of any stack on the instance, not just the one it was generated for.

### Finding Description
The intended binding is: **the stack an API request may touch ∈ the stacks authorized by `current_api_client.stack_id`**. `Api::BaseController` implements this correctly: [1](#0-0) 

`stacks` restricts to `Stack.where(id: current_api_client.stack_id)` when a `stack_id` is present, and `stack` (singular) is derived from that scoped relation via `stacks.from_param!`.

`Api::CCMenuController`, however, redefines `stack` to skip this entirely: [2](#0-1) 

It calls `Stack.from_param!(params[:stack_id])` on the unscoped `Stack` relation, so `current_api_client.stack_id` is never consulted for this endpoint — the client is authenticated (via `ApiClient.authenticate(params[:token])`), but authorization to a *specific* stack is never checked. `require_permission :read, :stack` only checks that the `read:stack` permission string is present in `permissions`, not which stack it applies to.

This is compounded by `CCMenuUrlController#client`, which creates the `ApiClient` without a `stack:` association at all: [3](#0-2) 

so even if `CCMenuController#stack` respected scoping, the token would still be unscoped (`stack_id` nil ⇒ `stacks` returns `Stack.all`). The bypass in `CCMenuController#stack` makes this worse: it means *even a properly stack-scoped* `ApiClient` (one with `stack_id` set) could be used against `Api::CCMenuController#show` to read an arbitrary other stack's `cc.xml`, since that controller never routes through the `stacks` scope at all.

Attacker flow: an operator of stack A visits `GET /ccmenu/:owner/:repo/:env` (routed to `CCMenuUrlController#fetch`), obtaining a token whose `ApiClient` has no stack restriction. The token leaks (browser history / CI badge page / Referer). The attacker then requests `GET /api/1/stacks/<ownerB>/<repoB>/<envB>/ccmenu?token=<token>`. `authenticate_api_client` (overridden in `CCMenuController`) accepts the token via `ApiClient.authenticate`, and `stack` resolves stack B directly from `params[:stack_id]`, bypassing any `stack_id` check. `Api::CCMenuController#show` renders stack B's latest deploy/rollback status.

No existing guard (`require_permission`, `verify_signature`, model validations) checks stack ownership here, because the whole authorization model for this controller is built on an override that removes the scoping BaseController normally provides.

### Impact Explanation
Any holder of a CCMenu token (an operator of any single stack) can read the deploy/build status (`cc.xml`: latest deploy id, status, running state) of **any** stack on the Shipit instance, including stacks belonging to unrelated repositories/organizations they have no access to. This is an unauthenticated-for-that-resource, cross-tenant information disclosure — repeatable indefinitely and against arbitrary stacks by simply varying `stack_id` in the URL, matching the High severity category "unauthenticated read of stack state."

### Likelihood Explanation
Preconditions are minimal: the attacker needs access to only one stack (as a normal Shipit operator) to legitimately obtain a CCMenu URL/token via the UI, then can reuse that token against any other stack by editing the URL — no additional secrets, no GitHub credentials, and no privileged role required. The token is designed to be embedded in public-facing CI status tools (CCMenu clients, badges), increasing the chance of exposure via Referer headers or shared dashboards.

### Recommendation
Fix `Api::CCMenuController` to use the inherited, scoped `stack`/`stacks` method from `Api::BaseController` instead of calling `Stack.from_param!` directly, and fix `CCMenuUrlController#client` to pass `stack: stack` into `ApiClient.create_with(...)` so tokens are bound to the originating stack.

### Proof of Concept
Minitest plan (`test/controllers/api/ccmenu_controller_test.rb` style):
1. Create `stack_a = shipit_stacks(:shipit)` and a second `stack_b = create(:stack, repository: create(:repository, owner: 'other-org', name: 'other-repo'))`.
2. As a logged-in user, `get :fetch, params: { stack_id: stack_a.to_param }` on `CCMenuUrlController` to mint a token (or directly call `ApiClient.create_with(permissions: %w[read:stack]).find_or_create_by!(creator: user, name: 'CCMenu Client')` and `.authentication_token`), asserting `client.stack_id.nil?` (demonstrating the unscoped client).
3. `get :show, params: { stack_id: stack_b.to_param, token: token }` on `Api::CCMenuController`.
4. Assert response is `200` and body contains stack B's data — proving the equality `current_api_client.stack_id ∈ {stack authorized}` is violated (`current_api_client.stack_id` is `nil`/stack A, yet stack B is served) — where a correct implementation should return `403`/`404`.
