### Title
`CHECK`-style crash in address-definition evaluator via unresolved `definition template` reference - ([File: definition.js])

### Summary
The TensorFlow advisory describes an op (`AudioSummaryV2`) that assumes an untrusted input has a specific shape (`sample_rate` must have exactly one element) and, instead of returning a graceful error, hits an unguarded `CHECK` that aborts the process (DoS). `ocore`'s address-definition (oscript) evaluator has an analogous unguarded invariant: in the authentifier-evaluation path used to check spending conditions of an address (`validateAuthentifiers` in `definition.js`), the `'definition template'` opcode assumes the referenced template row count is exactly 1 and calls `throw Error("not 1 template")` when that assumption doesn't hold, instead of failing gracefully as the sibling structural-validation function does.

### Finding Description
`definition.js` contains two parallel implementations of oscript opcode evaluation for address definitions:

1. `validateDefinition()` (used once, when an address definition/asset condition is first structurally validated) — its `'definition template'` case handles an unexpected template row count gracefully: [1](#0-0) 
```
if (rows.length !== 1)
    return cb("template not found or too many");
```

2. `validateAuthentifiers()` (the *runtime* evaluator invoked every time a unit spends from / authenticates as an address that uses this definition) — its `'definition template'` case has the identical query but instead throws an uncaught `Error` on the same condition: [2](#0-1) 
```
case 'definition template':
    // ['definition template', ['unit', {param1: 'value1'}]]
    var unit = args[0];
    var params = args[1];
    conn.query(
        "SELECT payload FROM messages JOIN units USING(unit) \n\
        WHERE unit=? AND app='definition_template' AND main_chain_index<=? AND +sequence='good' AND is_stable=1",
        [unit, objValidationState.last_ball_mci],
        function(rows){
            if (rows.length !== 1)
                throw Error("not 1 template");
            var template = rows[0].payload;
            var arrTemplate = JSON.parse(template);
            var arrFilledTemplate = replaceInTemplate(arrTemplate, params);
            evaluate(arrFilledTemplate, path, cb2);
        }
    );
    break;
```

This mirrors the CVE-2022-35995 pattern: a runtime code path silently assumes a structural invariant ("exactly one matching row/element") that was checked elsewhere at a different point in time, and crashes hard (uncaught `throw` inside an async DB callback, analogous to a `CHECK`-fail abort) instead of returning a validation error when the invariant unexpectedly fails at evaluation time. The `'address'` and `'attested'` op-handlers in the same evaluator similarly `throw Error("more than 1 address definition")` on unexpected DB cardinality: [3](#0-2) 

The structural check performed once at `validateDefinition` time (`rows.length !== 1` → graceful `cb(err)`) does not guarantee the invariant holds forever at every future `main_chain_index` used for evaluation, because `main_chain_index<=?` is parameterized by the *current* unit's `last_ball_mci`, which differs from the mci that was in effect the first time the address definition was validated. This time-of-check/time-of-use style gap between the two evaluator implementations is the root cause.

### Impact Explanation
An uncaught exception thrown from inside an asynchronous `conn.query` callback during unit validation is not caught by the calling validation logic's `try/catch` (the throw happens on a later tick, outside the original stack frame), so it propagates as an unhandled exception. Depending on the Node.js process's global exception handling, this can crash the node process while it is validating a unit — a validity/stability processing crash triggered purely by a specifically crafted address definition and payment message reachable by any unprivileged unit poster who controls a definition using `'definition template'`. If different nodes evaluate this code path at slightly different `last_ball_mci` (i.e., different views of stability progression) they could crash while others do not, producing node disagreement / inability to progress on this chain of units — matching the class of impact called out for this analog family (node crash / disagreement on validity, network unable to confirm new units built on this path).

### Likelihood Explanation
Reachability requires: (a) an address whose definition includes `['definition template', [templateUnit, params]]`, and (b) that at authentifier-evaluation time the row lookup for `templateUnit`'s `definition_template` message no longer returns exactly one row for the `main_chain_index<=?` bound in use. Because the structural check was already performed successfully once (when the address definition was first chash-committed), triggering the divergent, unguarded path requires a scenario where the cached/stored definition is evaluated against a different mci context than the one used at first validation (e.g., nested/asset-condition evaluation reusing an inner definition, or unresolved-inner-definition branches in `validateDefinition` at line 279-303 which bypass re-querying), such that `rows.length` returns 0 or >1 unexpectedly. This is a narrower trigger condition than the TensorFlow bug (which is directly and trivially triggerable via one op call), so likelihood is lower and depends on specific mci/reorg timing that could not be fully confirmed with the available tools.

### Recommendation
Change the `'definition template'` case in `validateAuthentifiers()` (definition.js:802-819) to fail gracefully instead of throwing:
```js
if (rows.length !== 1)
    return cb2(false); // or treat as fatal_error, consistent with other branches
```
Audit and remove the other `throw Error(...)` statements inside async DB callbacks in the same evaluator (`'address'` at line 795, `'attested'`, `'seen'` at line 859, `'mci'`/`'timestamp'`/`'age'` default branches at lines 1046, 1060, 1068) and replace them with `cb2(false)` / `fatal_error` handling so that unexpected data states never produce an unhandled exception during unit validation.

### Proof of Concept
Conceptual (cannot be fully executed without a live network/test harness):
1. Post a unit defining `templateUnit` with a `definition_template` app message (payload = a valid definition array).
2. Create address `A` whose definition is `['definition template', [templateUnit, {param1: 'value1'}]]`. Post a unit revealing this definition as `author.definition`; it structurally validates successfully via `validateDefinition` because `rows.length === 1` holds for that mci.
3. Later, craft/trigger conditions (e.g., via a nested `'address'`/`'attested'` reference path that reuses the stored definition of `A` while evaluating at a different `last_ball_mci`, or via a competing/never-stabilized `templateUnit`) such that the `SELECT payload FROM messages JOIN units ...` query in `validateAuthentifiers` for `A`'s definition returns 0 or ≥2 rows.
4. When a node validates a unit spending from `A` under this condition, `throw Error("not 1 template")` executes inside the `conn.query` callback, producing an unhandled exception in the validation pipeline instead of the intended `ifUnitError`/`ifJointError` callback path.

Because reproducing step 3 deterministically requires precise control over mci-dependent stabilization state that could not be verified against the live validation call graph within the scope of this review, this PoC is presented as a concrete code-path description rather than a fully executed exploit.
