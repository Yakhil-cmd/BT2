### Title
Webhook signature verified against `repository.owner.login` while write target is resolved from `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to use for HMAC verification based on `repository.owner.login` (or `organization.login`) taken from the untrusted JSON body. Once the signature is accepted, every `Webhooks::Handlers::Handler` subclass resolves the actual `Repository`/`Stack` to mutate from a *different* field of the same body, `repository.full_name`. These two fields are never cross-checked, so an org that successfully authenticates the signature is not guaranteed to be the org whose stack gets written to.

### Finding Description
`verify_signature` picks the GitHub App config to verify against using the repository owner login from the payload, then verifies the HMAC signature against that org's `webhook_secret`: [1](#0-0) [2](#0-1) 

The signature check itself is a straight HMAC compare in `GitHubApp#verify_webhook_signature`: [3](#0-2) 

After the request passes `verify_signature`, the parsed body is dispatched unmodified to the registered handler for the event: [4](#0-3) 

Every handler resolves the target repository/stack from `payload.dig('repository', 'full_name')`, a field independent of `repository.owner.login` used for signature scoping: [5](#0-4) 

For example, `PushHandler` uses this `stacks` helper to trigger `sync_github` on every matching stack, and `StatusHandler` uses `Commit.where(sha:)` (also unscoped to owner) to write commit statuses that feed into deploy-safety checks: [6](#0-5) [7](#0-6) 

The presence of the `secrets_double_github_app.yml` fixture confirms the engine is designed to support multiple organizations each with independent GitHub App credentials/`webhook_secret`s in a single Shipit deployment, which is exactly the multi-tenant setup where this binding matters: `Shipit.github(organization: repository_owner)` picks the org-specific app/secret, but nothing downstream re-validates that the `full_name` acted upon actually belongs to that same `repository_owner`.

**The broken equality:** the engine implicitly assumes
`organization authenticated via HMAC(repository.owner.login) == organization that owns repository.full_name`
but this is never enforced. An attacker who legitimately administers a repository under Org A (and therefore knows/can trigger Org A's correctly-signed webhook delivery) can set `repository.owner.login: "OrgA"` (so verification passes with Org A's secret) while setting `repository.full_name: "OrgB/some-repo"` for a different tenant's repository configured in the same Shipit instance.

### Impact Explanation
This crosses the "organization authenticated versus the repository that is written" trust boundary called out in scope. Concretely reachable effects with a validly-signed-but-mismatched payload:
- `push` events cause `Stack#sync_github` to run against another organization's stack (`PushHandler#process`), which can trigger GitHub API sync activity attributed to the victim org's stack using the app's credentials.
- `status` events let the attacker forge commit statuses (via `Commit#create_status_from_github!`) for arbitrary commits by SHA, independent of which org's key signed the request, which can influence deploy-readiness/merge-status of a different repository's stack — an unauthorized-deploy precursor.
- Other handlers (pull_request family) resolve repositories the same way via `Repository.from_github_repo_name`, extending the same cross-tenant write surface to review-stack provisioning and merge-status handling.

This matches the High/Critical bucket: cross-repository writes / unauthorized deploy-chain manipulation across tenant boundaries in a single Shipit deployment.

### Likelihood Explanation
Exploitation requires the attacker to control (or have push access to configure webhooks for) at least one organization/repository that is legitimately onboarded to the same Shipit instance — a realistic scenario for any multi-tenant Shipit deployment (confirmed supported by the `double_github_app` config), and does not require any Shipit session, API token, or the target org's secret. The attacker only needs their own org's `webhook_secret` and the ability to send an arbitrary HTTP POST with a forged `repository.full_name`.

### Recommendation
Verify that `repository.owner.login` (or `organization.login`) used to select the verifying GitHub App matches the owner segment of `repository.full_name` before dispatching to handlers, or better, derive the verifying app/secret from the same `full_name` field the handlers use, so a single field governs both signature scoping and repository resolution.

### Proof of Concept
1. Deploy Shipit with two onboarded GitHub organizations, `OrgA` and `OrgB`, each with its own GitHub App `webhook_secret` (as supported per `test/dummy/config/secrets_double_github_app.yml`).
2. As an attacker who controls `OrgA/attacker-repo` and thus can trigger genuine webhook deliveries signed with `OrgA`'s secret, craft a `push` event payload:
   ```json
   {
     "ref": "refs/heads/main",
     "after": "<attacker-controlled-sha>",
     "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/victim-repo" }
   }
   ```
3. Send it with `X-Hub-Signature` computed using `OrgA`'s `webhook_secret` over this exact body.
4. `WebhooksController#verify_signature` resolves `repository_owner` to `"OrgA"`, fetches `OrgA`'s GitHub App, and the signature check passes.
5. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("OrgB/victim-repo")`, calling `sync_github` against `OrgB`'s stack, even though the request was authenticated only as `OrgA`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
