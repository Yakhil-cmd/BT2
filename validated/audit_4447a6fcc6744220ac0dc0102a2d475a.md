## Title
Webhook signature verified against attacker's own GitHub organization while the payload's `repository.full_name` writes to a victim stack - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/secret to use for HMAC verification based on `repository_owner`, which is read from the payload itself: `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` [1](#0-0) . That org string then selects a `GitHubApp` instance and its `webhook_secret` via `Shipit.github(organization: repository_owner)` [2](#0-1) . However, once the signature check passes, the actual write operation (looking up which `Stack`/`Repository` to sync, create statuses on, etc.) is driven by a *different* field of the same payload: `payload.dig('repository', 'full_name')` [3](#0-2) . In a multi-GitHub-App deployment (`Shipit.github(organization:)` supports per-organization secrets, see `test/dummy/config/secrets_double_github_app.yml`) [4](#0-3) , `repository.owner.login`/`organization.login` (used to pick the verifying secret) and `repository.full_name` (used to pick the acted-upon repository) are independent, attacker-controlled JSON fields in the same signed body — nothing forces them to refer to the same repository.

### Finding Description
The equality that must hold is:

`organization whose secret authenticated the request == organization that owns the repository being written to`

Before the attacker's request: for a legitimate GitHub webhook, `repository.owner.login` and `repository.full_name`'s owner segment are always identical because GitHub itself generates the payload.

After the attacker's request: an attacker who has installed/administers their own GitHub App/organization ("attacker-org", with a webhook secret they know) can POST an arbitrary JSON body to `/webhooks`/whatever route mounts `WebhooksController`, setting:
- `repository.owner.login` = `attacker-org` (or `organization.login` = `attacker-org`)
- `repository.full_name` = `victim-org/victim-repo`
- `X-Hub-Signature` computed with `attacker-org`'s own `webhook_secret` over this exact raw body.

`verify_signature` calls `Shipit.github(organization: "attacker-org")`, retrieves attacker-org's `GitHubApp`, and `verify_webhook_signature` succeeds because the attacker legitimately knows that secret [5](#0-4) . `verify_signature` never checks that the org used for verification matches the repository actually referenced later by handlers. Once the filter passes, `create` dispatches to handlers using `params` — the same body — and handlers resolve the target `Stack` purely by `repository.full_name`, e.g. `PushHandler#process` looks up `stacks.not_archived.where(branch:).find_each { |stack| stack.sync_github(expected_head_sha: params.after) }` where `stacks` is `Repository.from_github_repo_name(repository_name)&.stacks` and `repository_name` is `payload.dig('repository', 'full_name')` [6](#0-5) [3](#0-2) . The result: the org that "authenticated" the request (attacker-org) is not the org whose repository is acted upon (victim-org), breaking exactly the deployment-trust binding this class of report targets.

### Impact Explanation
This allows an unprivileged attacker (with no access to the victim's actual GitHub webhook secret, GitHub App, or Shipit account) to forge webhook events against a victim's stack, provided the deployment is configured with multiple GitHub Apps/organizations (the documented multi-org secrets format). Depending on which handler is reached, this can trigger unauthorized `GithubSyncJob` runs, fabricate commit `status` entries (`StatusHandler`) that gate merge/deploy decisions, or manipulate `MergeRequest`/PR-related state for a repository the attacker does not control. Forged commit statuses feeding into `StatusChecker`/CI-gating logic can be used to make `reject_unless_mergeable!` treat a PR as passing CI when it should not, potentially enabling an unauthorized merge or deploy on the victim repository. This lands in the "unauthorized deploy/merge" and "cross-repository write" impact tier defined by the rules.

### Likelihood Explanation
Exploitability requires: (1) the deployment uses the multi-organization GitHub App configuration (top-level org keys under `github` in secrets, as documented in `docs/setup.md`) [7](#0-6) , and (2) the attacker controls (or can register) at least one GitHub organization/App entry configured in that Shipit instance's secrets, which is realistic for any Shipit instance shared across multiple orgs/teams. No repository write access, API token, or session on the victim's side is needed — only knowledge of one's own configured webhook secret, which the attacker legitimately possesses for their own org.

### Recommendation
Do not let the payload dictate which secret is used to validate its own signature. Either: (a) verify signature against every configured GitHub App's secret and reject if only a mismatched org's secret succeeds while cross-checking the resulting org against `repository.full_name`'s owner segment, or (b) determine the verifying organization from `repository.full_name`'s owner component (the value actually used by handlers) rather than from `repository.owner.login`/`organization.login`, and reject if they disagree, in `WebhooksController#verify_signature` / `#repository_owner`.

### Proof of Concept
1. Configure Shipit with two GitHub App orgs, `attacker-org` (attacker knows the webhook secret) and `victim-org` (hosts the real stack), per the multi-org `secrets.yml` format.
2. Attacker crafts a `push` webhook JSON body:
   ```json
   {
     "ref": "refs/heads/main",
     "after": "<attacker-chosen sha>",
     "repository": { "full_name": "victim-org/victim-repo", "owner": { "login": "attacker-org" } }
   }
   ```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(attacker-org_webhook_secret, body)>`.
4. POST to the webhooks endpoint with `X-Github-Event: push` and the header above.
5. `verify_signature` resolves `Shipit.github(organization: "attacker-org")` and succeeds because the attacker used the correct secret for `attacker-org` [2](#0-1) .
6. `PushHandler` resolves `Repository.from_github_repo_name("victim-org/victim-repo")` and calls `stack.sync_github(expected_head_sha:)` on the victim's stack [6](#0-5) , despite the request never being signed with `victim-org`'s secret.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

### Using Multiple Github Applications

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently. The top-level keys should be the name of each Github organization, and the following sub-keys are the Github app details for that particular organization.

For example:

```yml
production:
  github:
    somegithuborg:
      app_id:
      installation_id:
      webhook_secret:
      private_key:
      oauth:
        id:
        secret:
        teams:
    someothergithuborg:
      app_id:
      installation_id:
      webhook_secret:
      private_key:
      oauth:
        id:
        secret:
        teams:
```
