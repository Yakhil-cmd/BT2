## Title
Webhook signature verification keys off `repository.owner.login` while event handlers act on `repository.full_name` / `organization.login` - unbound fields allow cross-organization webhook forgery - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects the GitHub App (and therefore the HMAC `webhook_secret`) used to authenticate an inbound webhook based on `repository.owner.login` (or `organization.login`) read from the **unverified** JSON body. Once the signature check passes, `create` dispatches the same raw payload to event handlers, which act on a *different* field of the same payload — `repository.full_name` in `Handler#repository_name` (used by `PushHandler`, `StatusHandler`, `CheckSuiteHandler` via `stacks`) or `organization.login` in `MembershipHandler`. Nothing in the engine enforces that these fields refer to the same organization, so a signature valid for organization A's secret can be replayed with a payload whose "acted upon" repository/org belongs to organization B, in installations configured with `Shipit.github` multiple organizations (`docs/setup.md` "Using Multiple Github Applications").

### Finding Description
The trust binding that should hold is:
`organization whose secret authenticated the request == organization/repository the handler subsequently writes state for`

`verify_signature` computes this binding only from `repository.owner.login`: [1](#0-0) [2](#0-1) 

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(...)
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

`verify_webhook_signature` in `lib/shipit/github_app.rb` computes `HMAC-SHA1(webhook_secret_for(repository_owner), raw_body)` and compares it to `X-Hub-Signature`: [3](#0-2) 

This proves only that the poster knows the secret configured for whichever organization name appears at `repository.owner.login` in the same body — it does not prove anything about any other field in that body.

Once `verified` is true, `create` hands the full, attacker-controlled `params` to every registered handler for the event: [4](#0-3) 

Handlers resolve the target `Stack`/`Repository` from `repository.full_name`, not from `repository.owner.login`: [5](#0-4) 

and `MembershipHandler` resolves the target `Team`/organization from `organization.login` (again a separate field from `repository.owner.login`), letting an attacker add themselves to a `Team`: [6](#0-5) 

Because `repository.owner.login` (used to pick the verifying secret) and `repository.full_name` / `organization.login` (used to select the object mutated) are two independent, attacker-supplied strings inside the same signed-body-as-a-whole, an attacker who legitimately knows/possesses a valid `webhook_secret` for *one* configured organization (e.g., because they administer that org's GitHub App installation in a multi-org `Shipit.github` deployment, per `docs/setup.md`, "Using Multiple Github Applications") can craft an arbitrary JSON body where:
- `repository.owner.login` = the org whose secret they know (so `verify_signature` passes), and
- `repository.full_name` / `organization.login` = a target belonging to a *different, victim* organization also configured on the same Shipit instance.

The signature is valid HMAC math for organization A's secret over the full raw body — Shipit never checks that A also owns the repository/org that the handler subsequently mutates in organization B's namespace.

### Impact Explanation
This breaks the deployment-trust binding "organization that authenticated == repository/org that is written," analogous to the `AuctionDemo` report's binding mismatch (approved condition vs. acted-upon condition). Concretely:
- `push` events forged this way trigger `Stack#sync_github` for arbitrary stacks belonging to the victim org (`PushHandler#process`), letting an attacker drive unauthorized syncs/deploys of repositories they have no access to.
- `status` events let an attacker fabricate CI/commit statuses (`StatusHandler#process` → `Commit#create_status_from_github!`) for any commit sha across the whole installation, which can be used to satisfy Shipit's CI gating and enable an unauthorized deploy/merge.
- `membership` events let an attacker add an arbitrary GitHub login (including their own) to any `Team` (`MembershipHandler#process` → `Team#add_member`). If that `Team` is one of `Shipit.github_teams`, `User#authorized?` becomes true for that login, which is an authentication/authorization bypass of `force_github_authentication` (`app/controllers/concerns/shipit/authentication.rb`).

This meets the "Critical/High" bar defined in scope: escalation into `Shipit.github_teams` authorization and an unauthorized deploy path, achieved purely by cross-organization payload-field confusion at the unauthenticated `/webhooks` endpoint — no session, `ApiClient` token, or GitHub App private key is required.

### Likelihood Explanation
Requires: (a) the Shipit instance is configured with more than one GitHub organization (documented, supported feature), and (b) the attacker knows or controls the `webhook_secret` of at least one of those organizations (e.g., they administer that org's App, or the secret is blank/default as shown in the shipped example configs `config/secrets.development.shopify.yml` and `docs/setup.md`, where `verify_webhook_signature` short-circuits to `true` when `webhook_secret` is blank). Given multi-org support is an advertised configuration path and the field mismatch requires no timing race (unlike the referenced 1-second overlap bug), this is a straightforward, deterministic exploit once the precondition is met — comparable or higher likelihood than the report's race-window bug.

### Recommendation
- In `WebhooksController#verify_signature`, after verifying the signature against the app selected by `repository_owner`, re-derive and cross-check every field that handlers will act on (`repository.full_name`'s owner segment, `organization.login`) against that same `repository_owner`/organization, rejecting the request (422) on mismatch.
- Alternatively, verify the signature against every configured organization's secret and only proceed if the organization that verified is the same one referenced by `repository.full_name`/`organization.login`, rather than trusting an unverified field to pick which secret to check.
- Do not treat a blank `webhook_secret` as "verification passed" (`lib/shipit/github_app.rb#verify_webhook_signature` line 77); at minimum log/alert, and consider requiring a secret to be configured before an organization's webhooks are accepted.

### Proof of Concept
Preconditions: Shipit configured with `github: { orgA: {..., webhook_secret: "secretA"}, orgB: {...} }` (multi-org config per `docs/setup.md`), attacker knows `secretA` (owns/administers orgA's App installation), and a `Stack`/`Team` exists for `orgB`.

1. Attacker builds payload:
```json
{
  "repository": { "owner": { "login": "orgA" }, "full_name": "orgB/victim-repo" },
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha-already-known-to-exist>"
}
```
2. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(secretA, raw_body)>`.
3. POST to `/webhooks` with header `X-Github-Event: push`.
4. `verify_signature` computes `repository_owner == "orgA"`, fetches `Shipit.github(organization: "orgA")`, verifies HMAC with `secretA` — passes.
5. `create` calls `Shipit::Webhooks.for_event("push")` → `PushHandler.call(params)`, which resolves `stacks` from `repository.full_name == "orgB/victim-repo"` and calls `stack.sync_github(expected_head_sha: ...)` for the victim org's stack, despite the request having been authenticated solely for orgA.

An analogous payload with `organization.login = "orgB"` and `X-Github-Event: membership`, `action: "added"`, `member.login: "attacker-login"`, signed with `secretA`, causes `MembershipHandler` to add the attacker's GitHub login to a `Team` scoped to `organization: "orgB"`, potentially satisfying `Shipit.github_teams` membership and bypassing `force_github_authentication`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
