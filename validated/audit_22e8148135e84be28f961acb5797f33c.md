### Title
CCMenu API token stack-scope bypass allows reading any stack's deploy status - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::CCMenuController` overrides the stack-resolution method used everywhere else in the API to enforce per-token stack scoping, replacing it with an unscoped lookup. This breaks the invariant that "the stack an `ApiClient` token is authorized for" must equal "the stack the request actually touches," letting a stack-scoped CCMenu token read the deploy status of any stack in the installation.

### Finding Description
Across the JSON API, `Shipit::Api::BaseController` centralizes the trust boundary between an `ApiClient`'s authorized scope and the `Stack` a request can act on:

```ruby
def stacks
  @stacks ||= current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all
end

def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
``` [1](#0-0) 

Every controller that inherits this method (stacks, deploys, tasks, hooks, etc.) is confined to the token's `stack_id` when one is set — this is the equality the system relies on: `ApiClient#stack_id ⇒ Stack resolved`.

`Api::CCMenuController`, however, redefines `stack` to bypass the scoped `stacks` helper entirely and resolve directly against the full `Stack` table:

```ruby
class CCMenuController < BaseController
  require_permission :read, :stack
  ...
  def show
    latest_deploy = stack.deploys_and_rollbacks.last || NoDeploy.new
    render('shipit/ccmenu/project', formats: [:xml], locals: { stack:, deploy: latest_deploy })
  end

  private

  def stack
    @stack ||= Stack.from_param!(params[:stack_id])
  end

  def authenticate_api_client
    @current_api_client = ApiClient.authenticate(params[:token])
    super unless @current_api_client
  end
end
``` [2](#0-1) 

`require_permission :read, :stack` only checks that the token has the `read:stack` permission string via `ApiClient#check_permissions!`, which never inspects `stack_id`:

```ruby
def check_permissions!(operation, scope)
  required_permission = "#{operation}:#{scope}"
  unless permissions.include?(required_permission)
    raise InsufficientPermission, "This operation requires the `#{required_permission}` permission"
  end
  true
end
``` [3](#0-2) 

The route confirms `stack_id` is attacker-controlled per request, independent of the token:
```ruby
scope '/stacks/*stack_id', stack_id: stack_id_format, as: :stack do
  get '/ccmenu' => 'ccmenu#show', as: :ccmenu
``` [4](#0-3) 

The application supports and expects tokens scoped to a single stack — see the `here_come_the_walrus` fixture (`stack: shipit`) and its test asserting index scoping, and the `write:hook`/`read:stack` narrow-permission pattern used elsewhere — but `CCMenuController` is the one endpoint that ignores that scope, breaking the binding `token.stack_id == stack touched`.

### Impact Explanation
This crosses the trust boundary the report's bug class describes: an entity (here, a token's authorized stack) that is validated on one path but not enforced on the actual resource acted upon. A stack-scoped `ApiClient` token — e.g. one distributed for a single stack's CCMenu integration — can be replayed against `/api/stacks/<any-other-stack>/ccmenu` to read that other stack's deploy status, timing, and last-deploy metadata, an unauthorized cross-stack information read. This matches the accepted "High" impact category: unauthenticated/unauthorized read of stack state or deploy output outside the credential's intended scope.

### Likelihood Explanation
Any holder of a valid `ApiClient` token with `read:stack` permission (including intentionally stack-restricted tokens, which are a normal and encouraged configuration per the fixtures/tests) can trigger this by simply substituting a different `stack_id` in the URL — no additional privilege, secret, or session is required beyond possessing one legitimately-issued, narrowly-scoped token.

### Recommendation
Remove the `stack` override in `Api::CCMenuController` and use the inherited, scope-respecting `stacks.from_param!(params[:stack_id])` from `BaseController` (or otherwise explicitly check `current_api_client.stack_id.nil? || current_api_client.stack_id == resolved_stack.id`) before rendering deploy status.

### Proof of Concept
1. Create/obtain an `ApiClient` scoped to `stack_id: A` with permission `read:stack` (a supported configuration, e.g. `here_come_the_walrus` fixture).
2. Authenticate to `GET /api/stacks/<owner>/<other-stack-B>/ccmenu?token=<token>` (or via Basic auth) using that token, substituting stack `B` (which the token was never authorized for) in the URL.
3. `CCMenuController#stack` resolves via `Stack.from_param!(params[:stack_id])`, ignoring `current_api_client.stack_id`, so stack B's `deploys_and_rollbacks.last` is returned — the token reads deploy state for a stack outside its authorized scope, unlike every other `/api/stacks/*` endpoint using the same token.
