### Title
Cross-tenant `Membership` mutation via unscoped `Team.find_or_create_by!(github_id:)` in `membership` webhook - ([File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`MembershipHandler#process` resolves the target `Team` solely by GitHub's global `team.id`, without checking that the organization which cryptographically verified the webhook matches the team's actual `organization`. Because membership payloads have no `repository` key, `WebhooksController#repository_owner` falls back to `params["organization"]["login"]`, so in a multi-org Shipit deployment the signature is verified against whichever organization's `login` the attacker puts in the payload — which can be the attacker's own, legitimately-configured org. This lets an operator of one tenant organization delete `Membership` rows belonging to a completely different tenant's team.

### Finding Description
The broken binding: `Membership deletion for Team T` should imply `the webhook was verified using Team T.organization's webhook_secret`. In reality the code enforces only `webhook verified using organization O's secret` where `O = params["organization"]["login"]` (or `repository.owner.login`, absent here), with no check that `O == T.organization`.

Path:
1. `WebhooksController#verify_signature` computes `repository_owner` via `params.dig('repository','owner','login') || params.dig('organization','login')` [1](#0-0)  and calls `Shipit.github(organization: repository_owner).verify_webhook_signature(...)` [2](#0-1) . For a `membership` event there is no `repository` key, so `repository_owner` is simply `params["organization"]["login"]`, i.e., whatever organization the attacker names — which succeeds as long as that org is one of Shipit's configured tenants (Shipit explicitly supports multiple GitHub apps/orgs per `docs/setup.md`) [3](#0-2) .
2. Once the signature check passes (using the attacker-org's own legitimate `webhook_secret`), `MembershipHandler#process` runs: `team = find_or_create_team!` looks up `Team.find_or_create_by!(github_id: params.team.id)` — matched purely by numeric GitHub team id, ignoring which org verified the request [4](#0-3) . If a `Team` row with that `github_id` already exists (created earlier by a legitimate `added` event from the real target organization), the block is skipped entirely and the existing (real, victim) `Team` record is returned unchanged.
3. For `action == 'removed'`, `team.members.delete(member)` deletes the real `Membership` row between that team and whatever `member.login` the attacker names [5](#0-4) .

Attacker request: attacker owns/administers `attacker-org`, which is a genuinely configured tenant in Shipit's `config/secrets.yml`. Attacker sends a `membership` webhook, signed with `attacker-org`'s real webhook secret:
```json
{"action":"removed","team":{"id":<target_team_github_id>,"name":"x","slug":"x","url":"https://x"},
 "organization":{"login":"attacker-org"},"member":{"login":"legit-operator"}}
```
`verify_signature` succeeds because it only checks the signature against `attacker-org`'s secret, which the attacker legitimately possesses for their own org. Nothing in `find_or_create_team!` or `process` cross-checks that `params.team.id` actually belongs to `attacker-org`.

Existing guards checked and found insufficient: `verify_signature`/`GithubApp#verify_webhook_signature` only proves the payload was signed by *some* configured org, not the org owning the referenced team [6](#0-5) ; `drop_unhandled_event` and the `ExplicitParameters` schema in the handler do not validate team/org linkage; there is no `require_permission!`/ownership check in `MembershipHandler`.

### Impact Explanation
A `Membership` row gates `User#authorized?`, which controls access when `Shipit.github_teams` is configured [7](#0-6) . An attacker who legitimately controls any one org onboarded into a multi-org Shipit instance can silently revoke a legitimate operator's authorization for an unrelated tenant's protected team by referencing that team's known/guessable numeric GitHub `id`. This is a cross-tenant mutation of another organization's authorization state, repeatable against any team whose `github_id` the attacker knows, and it can also be abused with `action: 'added'` to grant unauthorized team membership. This matches the Critical category ("a payload for one repository/organization mutating another's team").

### Likelihood Explanation
Requires: (a) Shipit hosting multiple GitHub organizations (a documented, supported configuration), (b) attacker legitimately controls one of those onboarded orgs (a real, low-cost precondition for a rogue or compromised tenant admin), and (c) knowledge of the target team's GitHub-side numeric `id` (discoverable via GitHub's public/team API or previous webhook traffic). No secrets of the victim org are needed. Cost per exploit is a single crafted signed HTTP POST.

### Recommendation
In `MembershipHandler#find_or_create_team!` (and any similar handler), require that the org verified by the webhook (passed down from the controller, e.g. via `repository_owner`/`params.organization.login` used for signature verification) matches the existing `Team#organization` before mutating it; reject or no-op if `team.organization != verified_organization`. More generally, the controller should pass the verified organization into handlers and every handler should assert record ownership against it rather than trusting attacker-supplied ids alone.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/membership_handler_test.rb
test "removed action cannot delete membership for a team owned by a different verified organization" do
  target_team = shipit_teams(:committers) # organization: 'shopify', github_id: 42
  operator = shipit_users(:walrus)
  Membership.find_or_create_by!(team: target_team, user: operator)

  assert Membership.exists?(team: target_team, user: operator)

  # Payload verified under a *different* org's webhook secret (attacker-org),
  # but referencing the victim team's github_id.
  payload = {
    action: 'removed',
    team: { id: target_team.github_id, name: target_team.name, slug: target_team.slug, url: target_team.api_url },
    organization: { login: 'attacker-org' },
    member: { login: operator.login }
  }.to_json

  signature = 'sha1=' + OpenSSL::HMAC.hexdigest('sha1', attacker_org_webhook_secret, payload)

  @request.headers['X-Github-Event'] = 'membership'
  @request.headers['X-Hub-Signature'] = signature
  post :create, body: payload, as: :json

  assert_response :ok
  # Binding violated: membership for 'shopify' team deleted by a request verified for 'attacker-org'
  refute Membership.exists?(team: target_team, user: operator)
end
```
This demonstrates that `Membership.exists?(team:, user: legit_operator)` flips from `true` to `false` solely due to a webhook cryptographically verified for an unrelated organization, confirming the broken binding.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
