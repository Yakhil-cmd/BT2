## Title
Precision loss to zero in AA exchange/division formulas causes silent fund loss for the trigger sender - (File: `aa_composer.js`)

### Summary
Ocore's Autonomous Agents (AAs) can implement token-swap/rounding logic in oscript formulas (e.g. `round(ratio * amount)`), the same class of "amount / price → integer truncation" arithmetic flagged in the external USSD report. Because AA payment outputs must be non-negative integers, any output whose formula evaluates to `0` for a sufficiently small trigger input is silently dropped by `aa_composer.js` before the response unit is built. If that was the only output, the AA sends **no response at all**, consumes the trigger's deposited funds into its own balance, and, critically, the state-update formula is also skipped — so nothing is even recorded to let the sender reclaim the deposit later.

### Finding Description
In `handleTrigger`'s `sendUnit()`, after evaluating the AA's message templates, outputs are filtered: [1](#0-0) 
Any output whose `amount` evaluates to `0` is removed (`output.amount > 0 || output.amount === undefined`). If this empties a payment message's outputs, the whole message is dropped, and if all messages become empty the AA falls through to `handleSuccessfulEmptyResponseUnit(null)` with `error_message = 'no messages after removing 0-outputs'`: [2](#0-1) 

This exact behavior is confirmed by the test `'only 0 output'`, where an AA computes `amount: "{trigger.output[[asset=base]] * 0}"`; the response unit ends up with **no payment message for the trigger's address at all**, and the bounce message explicitly states `"no messages after removing 0-outputs, then no state changes"`: [3](#0-2) 

Many real-world AA patterns compute payouts via division/rounding on user-supplied amounts, exactly the pattern that causes precision loss for small inputs in the referenced report. For example, the bundled market-maker sample computes an exchange amount as:
```
$current_ratio = $asset_balance / $bytes_balance;
$expected_asset_amount = round($current_ratio * trigger.output[[asset=base]]);
...
$issue_amount = round($investor_share_of_prev_balance * var['mm_asset_outstanding']);
``` [4](#0-3) 
and the "divest" branch:
```
$investor_share = $mm_asset_amount / var['mm_asset_outstanding'];
...
outputs: [{address: "{trigger.address}", amount: "{ round($investor_share * balance[$asset]) }"}]
``` [5](#0-4) 

If `$investor_share * balance[$asset]` (or the equivalent ratio in any similarly-structured AA) rounds to `0` for a small enough deposit (e.g. depositing 1 unit of an mm-asset against a very large `balance[base]`), `round()` yields `0`; `aa_composer.js` strips that output; if that payment message is the AA's only output, the whole response collapses to "no messages" and — per the confirmed test behavior — **no state changes are applied either**. The user's deposited trigger funds remain in the AA's balance with no record crediting the sender, no burn accounting, and no path to reclaim them through the AA's own logic (since the state var, e.g. `mm_asset_outstanding`, is never decremented to reflect the "phantom" divestment).

### Impact Explanation
Any unprivileged AA trigger sender who sends a sufficiently small amount into an AA whose payout formula involves division/rounding (a common, encouraged oscript pattern for shares/prices/ratios) can have their funds silently absorbed by the AA with zero compensation and zero state adjustment. This is a direct, reachable fund-loss condition triggered purely by posting a trigger unit with a small payment — no special privileges required, matching the High-severity "Precious loss" class from the referenced report (small deposits round to zero and are lost).

### Likelihood Explanation
Likelihood is High for any AA author who writes formulas like `round(a/b*x)` without explicitly bouncing on a computed `amount == 0` (a very natural omission, since `oscript` doesn't warn about it and the aa_composer's zero-output filtering is undocumented in most tutorials). An attacker/careless user simply needs to send a trigger with the right timing/size (e.g. dust amount, or right after balances make the ratio unfavorable) to hit the truncation-to-zero condition.

### Recommendation
- Have AA authors explicitly guard against zero-value payout formulas (e.g. `if ($amount == 0) bounce('amount too small')`), and document the auto-filtering behavior of zero-amount outputs prominently in the oscript reference/AA-authoring guide.
- Consider having `aa_composer.js` treat "all outputs filtered to zero, resulting in no messages/no state changes" as a bounce condition by default (returning the trigger's funds) rather than silently consuming them, unless the AA author explicitly opts into "eat funds silently" semantics.
- Provide/enforce a linting/validation check in `aa_validation.js` that warns when a payment `amount` formula is a pure division/ratio expression without a preceding zero-check.

### Proof of Concept
1. Deploy an AA with a swap/divest formula such as the sample market-maker's divest branch:
```
init: `{
    $mm_asset_amount = trigger.output[[asset=$mm_asset]];
    $investor_share = $mm_asset_amount / var['mm_asset_outstanding'];
}`,
messages: [{
    app: 'payment',
    payload: { asset: "{$asset}", outputs: [{address: "{trigger.address}", amount: "{ round($investor_share * balance[$asset]) }" }] }
}, ...]
```
2. Grow `var['mm_asset_outstanding']` large relative to `balance[$asset]` (normal usage over time).
3. Send a trigger with the smallest valid `mm_asset` amount (`$mm_asset_amount = 1`), such that `round($investor_share * balance[$asset])` evaluates to `0`.
4. Per `aa_composer.js` lines 1278/1281 and the confirmed unit test `test/aa.test.js` `'only 0 output'`, the payment output is filtered out; if it was the sole output, the response becomes empty and, per the exact bounce message text `'no messages after removing 0-outputs, then no state changes'`, the corresponding `var['mm_asset_outstanding'] -= trigger.output[[asset=$mm_asset]]` state update is also skipped.
5. Result: the sender's `mm_asset` is now held by the AA, `mm_asset_outstanding` is unchanged (inconsistent with actual outstanding shares), and the sender receives nothing back — fund loss with no recovery path.
