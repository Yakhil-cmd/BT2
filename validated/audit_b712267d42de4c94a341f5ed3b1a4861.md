### Title
Cross-organization webhook spoofing via unauthenticated `repository.owner.login` field used to select signature-verification config while `repository.full_name` (the actually-mutated object) is never bound to it - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
The bug report describes a state-machine invariant that the code assumes but never enforces (`Pending → Expired` transition relies on membership in a set that pending offers are never added to). The same class of defect — an implicit binding assumed by the code but never actually checked — exists in `Shipit::WebhooksController`. The controller determines *which organization's webhook secret to use* from a field taken straight out of the unverified request body, and only after "verifying" the signature does it dispatch handlers that act on a *different* field of the same body (`repository.full_name`). Nothing in the code ties these two fields together, so when any configured GitHub organization has no `webhook_secret` set (a state explicitly presented as valid/"optional" in `docs/setup.md` and shipped in example configs such as `test/dummy/config/secrets_double_github_app.yml` and `config/secrets.development.shopify.yml`), signature verification for that organization silently returns `true` for any body, and an attacker can direct every event handler at a completely unrelated repository/stack.

### Finding Description
`WebhooksController#verify_signature` derives the org whose secret is used purely from attacker-controlled JSON: [1](#0-0) [2](#0-1) 

`Shipit.github(organization:)` resolves per-organization config, and `GitHubApp#verify_webhook_signature` explicitly short-circuits to `true` when the resolved organization has no `webhook_secret` configured: [3](#0-2) 

Once "verified", `WebhooksController#create` dispatches to handlers using the *same raw, unauthenticated body*, and every handler resolves its target purely from `repository.full_name` — a field never checked against `repository.owner.login`, the value used moments earlier to pick the signing secret: [4](#0-3) [5](#0-4) [6](#0-5) 

The equality the code implicitly assumes but never checks is:
`organization used to authenticate the request` == `organization that owns the repository the handler mutates`

Concretely: if `Shipit.github_organizations` includes an org `X` configured without a `webhook_secret` (both the docs and the shipped multi-org example configs treat this as a normal, supported setup — see `docs/setup.md` "Webhook secret (optional)" and `test/dummy/config/secrets_double_github_app.yml` lines 7 and 46, both `webhook_secret: # nil`), then:
1. `verify_signature` resolves `Shipit.github(organization: 'X')`.
2. `verify_webhook_signature` returns `true` unconditionally for org `X` regardless of the `X-Hub-Signature` header supplied.
3. The attacker sets `repository.owner.login = "X"` (satisfying step 1/2) but `repository.full_name = "victim-org/victim-repo"` — a completely different, properly-secured organization's repository.
4. Handlers (`PushHandler`, `PullRequest::*Handler`, `StatusHandler`, `CheckSuiteHandler`) look up the target stack purely by `repository.full_name`, so they operate on the victim's stack even though the "signing" organization was `X`.

The `MembershipHandler` is the most severe instance because `Team#authorized?` (gating login into the entire application, see `app/controllers/concerns/shipit/authentication.rb`) is driven by team membership that this handler can freely create: [7](#0-6) [8](#0-7) 

### Impact Explanation
Given a Shipit deployment configured with more than one GitHub organization (an explicitly supported configuration, cf. `Shipit.github_organizations`/`github_app_config` in `lib/shipit.rb` lines 170-200) where at least one organization has no `webhook_secret`, an unauthenticated attacker can:
- Force `PushHandler` to call `stack.sync_github` on stacks belonging to a different, unrelated organization/repository.
- Force `PullRequest::OpenedHandler`/`ClosedHandler`/`LabeledHandler` to provision, archive, or unarchive review stacks belonging to a different organization's repositories.
- Use `MembershipHandler` to add an arbitrary (real) GitHub login to a `Team` matching one of `Shipit.github_teams`, which is the authorization gate for the whole application (`User#authorized?`), effectively granting themselves authenticated access and deploy/rollback/merge capability — an unauthorized escalation into `Shipit.github_teams` authorization and a path toward unauthorized deploys.

This satisfies the "High" impact bar (escalation into `Shipit.github_teams` authorization) and, via subsequent deploy triggering, can reach the "Critical" bar (unauthorized deploy).

### Likelihood Explanation
Likelihood is Medium: the attack requires a specific but documented and shipped configuration state (one org among several configured without a `webhook_secret`), which the project's own docs (`docs/setup.md`) call "optional" and which appears in the repo's own multi-org test fixtures. No repository write access, GitHub App key, `ApiClient` token, or Shipit session is required — only knowledge that such an org exists in the deployment's config, and a POST to the public `/webhooks` endpoint with a crafted `X-Github-Event` header and JSON body.

### Recommendation
- Do not select the signing organization from unverified request body fields. Instead, verify the signature against *every* configured organization/secret (or against the specific org tied to the `repository.full_name`'s actual owner as resolved server-side via `Repository`) and require a match.
- Remove or restrict the "no secret configured ⇒ verification passes" behavior in `GitHubApp#verify_webhook_signature`; require an explicit `Shipit.authentication_disabled?`-style opt-out instead of silently trusting unsigned payloads.
- After signature verification, explicitly assert that `repository.owner.login` (or `organization.login`) equals the organization associated with `repository.full_name`'s resolved `Repository`/`Stack` before invoking handlers.

### Proof of Concept
Preconditions: Shipit configured with two organizations, `NoSecretOrg` (no `webhook_secret`) and `VictimOrg/victim-repo` (has a `Stack`).

```
POST /webhooks
X-Github-Event: push
X-Hub-Signature: sha1=anything

{
  "ref": "refs/heads/master",
  "after": "deadbeefdeadbeefdeadbeefdeadbeefdeadbeef",
  "repository": {
    "full_name": "VictimOrg/victim-repo",
    "owner": { "login": "NoSecretOrg" }
  }
}
```
`repository_owner` resolves to `NoSecretOrg`, whose `webhook_secret` is unset, so `verify_webhook_signature` returns `true` for any signature. `PushHandler` then resolves the target stack from `repository.full_name = "VictimOrg/victim-repo"` and triggers `sync_github` on it, despite the request never being authenticated by anything belonging to `VictimOrg`.

Note: I could not find any additional runtime guard (e.g., a check comparing `repository.owner.login` against the resolved `Stack`'s repository owner) anywhere in `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/**`, or `lib/shipit/github_app.rb` within the indexed engine code; if such a check exists elsewhere and was not surfaced by search, that would need to be confirmed in a full checkout.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
