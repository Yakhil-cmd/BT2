### Title
Webhook signature verification binds only the payload's `repository.owner.login`, while the actual sync target is resolved from the unverified `repository.full_name` field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/secret to check the HMAC signature against using `repository_owner`, derived from `params.dig('repository', 'owner', 'login')` (or `organization.login`). Once the signature check passes, the raw payload is dispatched unmodified to event handlers. Those handlers (`Shipit::Webhooks::Handlers::Handler#repository_name` / `PushHandler`) resolve the *actual* repository/stack to act on using a **different** field of the same payload: `payload.dig('repository', 'full_name')`. Nothing ties these two fields together, so the field that authorizes the request (the owning organization) is not the field that determines what gets written.

### Finding Description
`app/controllers/shipit/webhooks_controller.rb` verifies the signature this way: [1](#0-0) [2](#0-1) 

`Shipit.github(organization: repository_owner)` loads the GitHub App configuration (and `webhook_secret`) that is specific to that organization, per the multi-org configuration format supported by Shipit: [3](#0-2) 

Once the signature is verified with that org's secret, the full parsed payload is forwarded verbatim to handlers: [4](#0-3) 

Handlers, however, do not reuse `repository.owner.login`. `Handler#repository_name` and `PushHandler#process` resolve the repository/stack solely from `repository.full_name`: [5](#0-4) [6](#0-5) 

Because the HMAC signature covers the entire raw request body, an outside party who has never seen a real webhook cannot forge one. But this design creates exactly the binding mismatch the bug-class hint describes: the **equality that should hold is `repository.owner.login used to verify == repository.full_name used to act`**, and the code never enforces it. Anyone who legitimately administers *one* of the multiple GitHub organizations configured in `config/secrets.yml` (and therefore knows that org's own `webhook_secret`, which they themselves set when installing/configuring the GitHub App for their own org) can self-sign a payload where:
- `repository.owner.login` / `organization.login` = their own org (so `verify_signature` picks their own known secret and passes), and
- `repository.full_name` = `"other-org/other-repo"` (any repository/stack already tracked by this Shipit instance under a different organization).

`verify_webhook_signature` also short-circuits to `true` when no `webhook_secret` is configured for the resolved organization at all: [7](#0-6) 

so an org with no secret configured removes the check entirely for any payload claiming to belong to it, while the actual repository acted upon (`full_name`) is still whatever the attacker wrote.

### Impact Explanation
The forged `push` event reaches `PushHandler#process`, which looks up stacks by `Repository.from_github_repo_name(repository_name)` (using the attacker-chosen `full_name`) and calls `stack.sync_github(expected_head_sha: params.after)` for a stack that belongs to an organization the attacker does not control: [6](#0-5) 

This enqueues `GithubSyncJob` against a victim stack under attacker's control of the `expected_head_sha` and `ref` parameters: [8](#0-7) 

This is a cross-organization write into the internal state (commits, cached deploy spec, retry scheduling) of a stack the caller has no legitimate relationship to, driven entirely by a payload field (`repository.full_name`) that was never covered by the authorization check on `repository.owner.login`. It breaks the binding "organization that authenticated == repository that is written," matching the report's core bug class (a signature covering one field while a different field governs the state-changing logic).

### Likelihood Explanation
This requires the attacker to control at least one of the multiple GitHub organizations configured in this Shipit deployment's `config/secrets.yml` (i.e., know that org's `webhook_secret`, or exploit an org configured with no secret). This is a realistic scenario for any Shipit deployment onboarding multiple, not-equally-trusted GitHub organizations (as explicitly supported by the multi-org config format), since each org owner independently controls their own webhook secret and can trivially craft raw JSON payloads pointing `full_name` at any other tracked repository.

### Recommendation
In `WebhooksController#verify_signature` and/or `Handler#repository_name`, require that the organization used to select/verify the signature match the owner segment of `repository.full_name` (and `organization.login` for org-scoped events) before dispatching to handlers, rejecting the webhook (422) on mismatch.

### Proof of Concept
1. Configure Shipit with two orgs, `org-attacker` and `org-victim`, each with its own `webhook_secret` (per the documented multi-org config in `config/secrets.development.example.yml`).
2. Attacker, who administers `org-attacker` and therefore knows `org-attacker`'s `webhook_secret`, crafts a `push` JSON body:
   ```json
   {
     "ref": "refs/heads/main",
     "after": "<attacker-chosen-sha>",
     "repository": { "owner": { "login": "org-attacker" }, "full_name": "org-victim/victim-repo" }
   }
   ```
3. Attacker computes `X-Hub-Signature` using `org-attacker`'s secret and POSTs to `/webhooks` with `X-Github-Event: push`.
4. `verify_signature` resolves `repository_owner` = `"org-attacker"`, loads `org-attacker`'s app/secret, and the signature validates.
5. `PushHandler#process` resolves the target repo from `repository.full_name` = `"org-victim/victim-repo"` and enqueues `GithubSyncJob` for the victim's stack, even though `org-victim` never authorized or signed anything.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
    def perform(params)
      @stack = Stack.find(params[:stack_id])
      expected_head_sha = params[:expected_head_sha]
      retry_count = params[:retry_count] || 0
      head_before_sync = spec_cache_target
      appended_commits = []

      handle_github_errors do
        new_commits, shared_parent = fetch_missing_commits { stack.github_commits }

        # Retry on Github eventual consistency: webhook indicated new commits but we found none
        if expected_head_sha && new_commits.empty? && !commit_exists?(expected_head_sha) &&
           retry_count < MAX_RETRY_ATTEMPTS
          GithubSyncJob.set(wait: RETRY_DELAY * retry_count).perform_later(params.merge(retry_count: retry_count + 1))
          return
        end

        stack.transaction do
          shared_parent&.detach_children!
          appended_commits = new_commits.map do |gh_commit|
            append_commit(gh_commit)
          end
          stack.lock_reverted_commits! if appended_commits.any?(&:revert?)
        end
      end
      sync_changed_nothing = appended_commits.empty? &&
                             spec_cache_target == head_before_sync &&
                             stack.cached_deploy_spec.present?
      return if sync_changed_nothing && !params[:force_spec_cache]

      CacheDeploySpecJob.perform_later(stack)
    end
```
