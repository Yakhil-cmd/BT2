### Title
Cross-stack read via `CCMenuController#stack` bypassing `ApiClient#stack_id` scoping - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::CCMenuController` defines its own `stack` method that loads the target stack with `Stack.from_param!(params[:stack_id])` directly, instead of the base controller's scoped `stacks.from_param!(params[:stack_id])`. Because of this, an `ApiClient` token minted with a specific `stack_id` (i.e., scoped to one stack) can be used to read the CCMenu XML status of *any* stack, not just the one it was issued for.

### Finding Description
The binding that should hold is: `current_api_client.stack_id? ? current_api_client.stack_id == stack.id : true`, i.e. if a client token is scoped to a stack, the `stack` resolved by the controller must be restricted to that same stack (this is exactly what `Api::BaseController#stacks`/`#stack` at [1](#0-0)  implements for every other API controller).

`CCMenuController` breaks this binding by redefining `stack`: [2](#0-1) 
This override calls `Stack.from_param!` on the unscoped `Stack` model, never consulting `stacks` (the scoped relation) or `current_api_client.stack_id`. This happens regardless of how authentication succeeded — via the query-string path in the controller's own `authenticate_api_client` override [3](#0-2)  or via the base class's Basic-Auth path [4](#0-3) .

The only authorization gate that runs afterward is `require_permission :read, :stack` [5](#0-4) , which calls `current_api_client.check_permissions!(:read, :stack)` [6](#0-5) . This method only checks that the string `"read:stack"` is present in the client's `permissions` array — it has no knowledge of, and does not check, which specific stack is being requested versus `current_api_client.stack_id`.

Exploit flow: an attacker who legitimately owns an `ApiClient` token scoped to `stack_a` (i.e., `ApiClient#stack_id == stack_a.id`) sends `GET /api/stacks/:stack_b_id/ccmenu.xml?token=<their-stack_a-token>`. `ApiClient.authenticate` [7](#0-6)  succeeds and returns the stack_a-scoped client object. `stack` then resolves `stack_b` unscoped, `check_permissions!` passes because the client has `read:stack` permission generically, and `show` renders `stack_b`'s CCMenu XML (build status, last build label, web URL) to the attacker.

### Impact Explanation
An attacker with a token scoped to any single stack can read the build/deploy status (`lastBuildStatus`, `lastBuildLabel`, `webUrl`, lock state, etc.) of every other stack on the Shipit instance, including private/internal projects they have no access to. This is a cross-tenant unauthorized read of stack state, repeatable against arbitrary `stack_id` values with a single legitimately-obtained token, and requires no privileged role — matching the "High: unauthorized read of stack state" impact category.

### Likelihood Explanation
Preconditions are minimal: the attacker only needs one legitimately-issued `ApiClient` token scoped to any stack they already have access to (a normal, expected credential for CCMenu integrations). No secrets, sessions, or special configuration are required beyond default engine mounting. The attack is a single unauthenticated-cost GET request per target stack ID, fully repeatable and enumerable across all stacks.

### Recommendation
Change `CCMenuController#stack` to reuse the base controller's scoped lookup, e.g. remove the local `stack` override entirely (relying on `Api::BaseController#stack`/`#stacks`), or explicitly implement it as `stacks.from_param!(params[:stack_id])` so that `current_api_client.stack_id` scoping is enforced identically to every other API controller.

### Proof of Concept
```ruby
# test/controllers/api/ccmenu_controller_test.rb
test "a token scoped to one stack cannot read another stack's ccmenu.xml" do
  stack_a = shipit_stacks(:shipit)
  stack_b = Stack.create!(repository: Repository.new(owner: "foo", name: "bar"), branch: "main")

  @client.update!(stack: stack_a, permissions: ['read:stack'])

  get :show, params: { stack_id: stack_b.to_param, token: @client.authentication_token }

  # Binding under test: current_api_client.stack_id (stack_a.id) must equal stack.id (stack_b.id)
  # for this request to be authorized. They differ, so this must NOT be 200.
  refute_equal @client.stack_id, stack_b.id
  assert_response :not_found # or :forbidden — currently fails, returns :ok
end
```
This test currently fails (returns `200 OK` with `stack_b`'s XML) because `CCMenuController#stack` never checks `current_api_client.stack_id` against the requested `stack_id`.
