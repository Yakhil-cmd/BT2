## Title
Cross-organization webhook forgery via unbound `repository.full_name` vs signature-verified `repository.owner.login` - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects the HMAC secret to validate a webhook against based on `repository.owner.login` (or `organization.login`) pulled from the same untrusted JSON body it is about to validate, but the payload's `repository.full_name` field — which is what all event handlers actually use to resolve the target `Stack`/`Repository` — is never checked for consistency with that owner field. In a multi-organization Shipit deployment (each org configured with its own `webhook_secret`, as shown in `test/dummy/config/secrets_double_github_app.yml`), an attacker who can obtain or forge a valid signature for *any one* configured organization can set `repository.owner.login` to that organization while setting `repository.full_name` to an entirely different, victim organization's repository, and the event will be processed against the victim's stack.

### Finding Description
`verify_signature` in `app/controllers/shipit/webhooks_controller.rb` does: [1](#0-0) 

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [2](#0-1) 

The org used to select the webhook secret (`repository_owner`) comes from `repository.owner.login`. But every handler (`PushHandler`, `StatusHandler` via `Commit.where(sha:)`, and all `PullRequest` handlers) resolves the target repository/stack using **`repository.full_name`** instead: [3](#0-2) 

```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
```

`Repository.from_github_repo_name` splits `owner/name` straight from `full_name` and looks up the stack: [4](#0-3) 

Nothing enforces that `repository.owner.login` (used for signature/secret selection) equals the owner segment embedded in `repository.full_name` (used for stack resolution) — they are two independent fields inside the same attacker-controlled JSON body. The signature only proves that *some* valid webhook secret configured on the Shipit instance signed the raw body, not that the secret belongs to the organization whose repository is being acted upon.

This is the structural analog of the reported bug class: a value used to authorize/attribute an operation (`vouch.lastUpdated`/accumulator source in the original report) is decoupled from the value actually acted upon (`vouch.locked`), letting the attacker present consistent-looking but logically decoupled fields to the same code path. Here, the "authenticating organization" (`repository.owner.login`) and the "repository that gets written to" (`repository.full_name`) are exactly the two independently-controlled fields the task rules call out as an explicit analog target.

### Impact Explanation
An attacker who controls, or has previously compromised/obtained, a webhook secret for *any single* organization configured on a shared/multi-tenant Shipit instance (a realistic deployment pattern explicitly supported and documented, e.g. `docs/setup.md` and `test/dummy/config/secrets_double_github_app.yml` showing multiple orgs like `OrgOne`/`OrgTwo` each with their own `webhook_secret`) can forge `push`, `status`, `check_suite`, `pull_request`, and `membership` events for *any other* organization's repositories/stacks tracked by the same Shipit instance. Concretely, by signing a payload with OrgA's secret while setting `repository.full_name` to `OrgB/victim-repo`, the attacker can:
- Trigger `GithubSyncJob`/`sync_github` on OrgB's stack (`PushHandler`), forcing it to sync against an attacker-chosen `expected_head_sha`, influencing what commit is considered deployable.
- Inject fabricated CI `Status` records (`StatusHandler`) for real commits on OrgB's stack, potentially bypassing CI gating that Shipit's deploy safety checks rely on to permit an unauthorized deploy.
- Create/close/archive review stacks for OrgB (`pull_request` handlers).

This crosses an authentication boundary (org whose secret validated the request vs. the org/repository actually mutated), which the rules classify as High-severity ("escalation into `Shipit.github_teams` authorization" adjacent territory) and, via the CI-status-forgery path enabling deploy-safety bypass, edges toward "unauthorized deploy" (Critical) depending on downstream safety checks (`required_statuses`, `blocking_statuses` in `deploy_spec.rb`) which trust the `Commit#statuses` records created via this exact `StatusHandler` path.

### Likelihood Explanation
Requires only a single valid webhook secret for *some* organization on a multi-org Shipit instance — no session, no `ApiClient` token, no repository write access to the victim org, and no GitHub App credentials for the victim org are needed. This is squarely an unprivileged-attacker path relative to the victim organization, matching the required threat model. Single-organization deployments (one `webhook_secret` total) are not exploitable this way since there is only one org to begin with — the exposure is specific to the documented multi-org configuration mode.

### Recommendation
In `WebhooksController#verify_signature`, after determining `repository_owner` and verifying the signature, cross-check that the owner segment of `params.dig('repository', 'full_name')` (and/or `organization.login` when present) matches the `repository_owner` value used to select the signing secret; reject the request (422) on mismatch. Alternatively, derive the single "authoritative" organization identifier once and use it consistently both for secret selection and for repository/stack resolution in all `Webhooks::Handlers::Handler` subclasses, rather than trusting `repository.full_name` independently.

### Proof of Concept
1. Deploy Shipit configured with two organizations, `OrgA` and `OrgB`, each with a distinct `webhook_secret` (as supported per `test/dummy/config/secrets_double_github_app.yml`).
2. Attacker has (or obtains) `OrgA`'s `webhook_secret` (e.g., they are a legitimate low-privilege collaborator with access to OrgA's GitHub App webhook config, but has no access to `OrgB`).
3. Attacker crafts a `push` payload:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "OrgA" },
    "full_name": "OrgB/victim-repo"
  }
}
```
4. Attacker computes `X-Hub-Signature` using `OrgA`'s `webhook_secret` over the raw body and POSTs to `/webhooks` with `X-Github-Event: push`.
5. `verify_signature` calls `Shipit.github(organization: "OrgA")` and successfully verifies the signature against `OrgA`'s secret — passes.
6. `Shipit::Webhooks.for_event('push')` invokes `PushHandler`, which resolves `stacks` via `Repository.from_github_repo_name("OrgB/victim-repo")`, matching `OrgB`'s real stack, and calls `stack.sync_github(expected_head_sha: <attacker-chosen sha>)` — a webhook signed by `OrgA` has driven a sync operation on `OrgB`'s stack, despite the attacker having no relationship to `OrgB`.
