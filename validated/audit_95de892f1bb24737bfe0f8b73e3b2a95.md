### Title
Global, repository-unscoped commit-status webhook handler allows cross-repository forgery of CI status, enabling unauthorized deploys - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
Shipit's webhook signature verification authenticates a `status` webhook against the GitHub App/webhook secret of the organization named in the payload's `repository.owner.login` (or `organization.login`), but the handler that actually writes the commit status (`StatusHandler`) never re-checks that the commit belongs to a repository/stack scoped to that same organization. It updates any `Commit` in the entire Shipit instance that matches the raw `sha` string. This breaks the binding "organization that authenticated == repository (commit) that is written."

### Finding Description
`WebhooksController#verify_signature` selects the GitHub App/secret to validate the HMAC against using only the repository owner extracted from the untrusted JSON body: [1](#0-0) [2](#0-1) 

Once the signature is valid for *that* organization, the raw JSON is dispatched by event type to registered handlers with no further binding of "verified organization" to "entity mutated": [3](#0-2) 

Most handlers correctly re-derive the target repository from the payload and scope their side effects to stacks that belong to that repository, e.g. the base `Handler#stacks` helper and `PushHandler`/`CheckSuiteHandler`: [4](#0-3) [5](#0-4) [6](#0-5) 

`StatusHandler`, however, is the outlier: it looks up commits purely by `sha`, with **no repository/organization scoping at all**: [7](#0-6) 

Because `Commit.where(sha: params.sha)` searches across every repository/stack tracked by the Shipit instance, and because git commit SHAs are public, non-secret identifiers (visible on GitHub, in PRs, in CI logs, etc.), any party who can get a validly-signed `status` webhook delivered — i.e., anyone who owns/administers a repository in *any* organization configured in this Shipit instance and can install/trigger a webhook there — can forge a `status` payload where:
- `repository.owner.login` = their own organization (so `verify_webhook_signature` succeeds using their own organization's webhook secret), and
- `sha` = the commit SHA of a target commit that actually belongs to a **different** organization/repository/stack tracked by the same Shipit instance.

This forges a commit status (e.g., `state: "success"`, arbitrary `context`) onto a commit in a stack that the attacker has no access to and whose real organization never authenticated this payload. The verified organization/repo (attacker's own) and the written entity (victim commit/stack) diverge — the exact class of binding violation described in the analog rules.

### Impact Explanation
Commit statuses drive Shipit's deploy-gating logic (`Commit#simple_state`, `Stack#branch_status`, `Stack#next_commit_to_deploy`, and continuous-delivery triggering) as referenced in `app/models/shipit/stack.rb` (`branch_status`, `next_commit_to_deploy`, `trigger_continuous_delivery`). By forging a "success" status for a target commit, an attacker in one tenant/org of a multi-tenant Shipit instance can make a commit in a *different* organization's stack appear CI-green:
- If continuous deployment is enabled on the victim stack, this can automatically **trigger an unauthorized deploy** of that commit.
- Otherwise, it can unblock a manual deploy of a commit that never actually passed the real CI check for that repository, or unblock deploys blocked by `ignore_ci`/status requirements.

This lands squarely in the specified Critical impact bucket: "an unauthorized deploy, rollback or merge," achieved purely through the app's own webhook authentication/dispatch logic, with no repository write access, no `ApiClient` token, and no `webhook_secret`/`api_clients_secret` of the *victim* organization required.

### Likelihood Explanation
Any Shipit deployment that serves more than one GitHub organization/repository (a common, documented multi-tenant setup — `Shipit.github(organization:)` is explicitly keyed per organization) exposes this. The only prerequisite is that the attacker administers a repository in *some* organization already configured with this Shipit instance (so they can register/trigger a real webhook and thus produce a validly-signed delivery for that org), and knows a target commit SHA in a different tracked repository — SHAs are not secret. No social engineering, no interception of secrets, and no privileged Shipit account are needed, satisfying the "unprivileged attacker" and credential/repository-boundary requirements.

### Recommendation
Scope `StatusHandler#process` to the repository indicated by the verified organization, mirroring the pattern used elsewhere (`Handler#stacks` / `Repository.from_github_repo_name`). Concretely, restrict the `Commit` lookup to commits belonging to stacks of `Repository.from_github_repo_name(payload.dig('repository', 'full_name'))`, and additionally have `WebhooksController` pass along (or the handler independently re-validate) that this derived repository's owner matches the organization used to verify the HMAC, so the two never diverge.

### Proof of Concept
1. Attacker controls repository `attacker-org/decoy`, which has a Shipit webhook configured, giving them the ability to produce a validly HMAC-signed delivery using `attacker-org`'s `webhook_secret`.
2. Attacker crafts a `status` event JSON body:
```json
{
  "sha": "<victim-org/victim-repo commit sha, e.g. from a public PR>",
  "state": "success",
  "context": "ci/required-check",
  "target_url": "https://example.com",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "attacker-org/decoy" }
}
```
3. Compute `X-Hub-Signature` using `attacker-org`'s known webhook secret over this exact raw body.
4. POST to `/webhooks` with `X-Github-Event: status`. `WebhooksController#verify_signature` resolves `Shipit.github(organization: "attacker-org")` and successfully verifies the signature. [1](#0-0) 
5. `Shipit::Webhooks.for_event('status')` dispatches to `StatusHandler`, which runs `Commit.where(sha: params.sha).each { |c| c.create_status_from_github!(params) }` — matching and updating the commit in `victim-org/victim-repo`'s stack regardless of the fact that the signature was verified against `attacker-org`. [7](#0-6) 
6. The victim stack's commit now shows a forged `success` status, potentially unblocking or auto-triggering a deploy for that stack.
