### Title
Predictable/grindable pseudo-randomness when AA formulas seed `number_from_seed()` with `mc_unit`, `trigger.unit`, or `response_unit` - ([File: formula/evaluation.js])

### Summary
The oscript formula language exposes a `number_from_seed(seed[, min, max])` primitive that derives a "random" number deterministically from a supplied seed string via `sha256(seed)`. AA authors are expected to combine this with unit/DAG values such as `mc_unit` (the current main-chain unit at trigger time) or `trigger.unit` to build lottery/gambling-style AAs. Both of these seed candidates are either already known on the DAG before the trigger is posted, or are fully controlled/grindable by the unprivileged party who composes and signs the triggering unit, making the "randomness" predictable and manipulable — the same underlying weakness as the reported `blockhash`-based randomness issue.

### Finding Description
`number_from_seed` is implemented as a pure, deterministic hash-to-number function: [1](#0-0) 

The only "unpredictable" seed values conventionally recommended in AA oscript are DAG-derived identifiers such as `mc_unit` (the main-chain unit id passed into formula evaluation as part of the trigger context) or `trigger.unit`/`response_unit`. `mc_unit` is resolved from the last stable (or, during composition, the latest) MC unit at the time the AA is triggered, as shown by how it is supplied to the trigger-handling and formula-evaluation pipeline: [2](#0-1) [3](#0-2) 

Because `mc_unit` refers to a unit that is already committed to the DAG (visible and immutable) before the trigger unit is composed, an unprivileged trigger sender can:
1. Read the current `mc_unit` (and therefore precompute `number_from_seed(mc_unit, ...)` or any `sha256`-derived value based on it) before deciding whether to send the triggering unit at all, i.e., selectively trigger the AA only when the outcome is favorable (withholding when unfavorable) — directly analogous to the "predictable blockhash, transaction can be timed/withheld" class of bug in the external report.
2. If the AA instead seeds on `trigger.unit` or `response_unit` (the id of the very unit being composed), the sender fully controls unit content (timestamp, parents, data payload, message ordering) prior to signing, and can therefore grind many candidate unit hashes off-chain, computing the resulting formula outcome for each, and only broadcast the unit whose resulting `mc_unit`/`trigger.unit`-derived number produces the desired payout — a pure grinding attack with no cost beyond local computation, since unit composition is free until broadcast.

This mirrors the reported Solidity issue: `blockhash(block.number - 1)` is a value known/controllable by the actor who decides whether/when to submit a transaction; in ocore, `mc_unit`/`trigger.unit` play the same role for AA triggers.

### Impact Explanation
Any AA that implements a lottery, raffle, weighted payout, NFT drop, or other chance-based fund distribution using `number_from_seed(mc_unit, ...)` or a hash of `trigger.unit`/`response_unit` as its sole entropy source can have its outcome predicted or steered by the triggering party. This leads to guaranteed favorable payouts for the attacker and fund loss/drain for the AA (an "AA fund loss" outcome), since the attacker only ever submits triggers (or unit variants) that yield winning outcomes, defeating the fairness guarantee the contract is meant to provide.

### Likelihood Explanation
Likelihood is high for any AA design that relies on `mc_unit` or self-referential unit identifiers combined with `number_from_seed`/`sha256` as a randomness source, since:
- Composing and inspecting a triggering unit locally (without broadcasting) costs nothing.
- `mc_unit` is public and known ahead of trigger composition.
- No privileged role is required — the attacker is just an ordinary unit poster / AA trigger sender.

### Recommendation
- Do not use any purely function of a value fully known or controllable by the trigger sender (`mc_unit`, `trigger.unit`, `response_unit`, `trigger` payload fields) as the sole entropy source for on-chain randomness in AA formulas.
- Where true unpredictability is required, use the existing `vrf_verify` primitive (already present in the formula grammar) with a VRF proof supplied by a trusted/committed oracle, or a commit-reveal scheme spanning multiple stable MC indices so the seed cannot be known or influenced at the time the triggering unit is composed.
- Document this risk clearly for AA authors, since `number_from_seed` itself is deterministic by design and the vulnerability lies in the choice of seed, not in the primitive.

### Proof of Concept
1. An AA is defined with logic such as:
   `messages: { cases: [{ if: "{ number_from_seed(mc_unit, 0, 1) == 1 }", messages: [ payout... ] }] }`
2. Attacker queries the current stable `mc_unit` off-chain (or, for a `trigger.unit`-seeded variant, composes candidate triggering units locally with different timestamps/parents/data and computes each resulting unit hash without broadcasting).
3. Attacker computes `number_from_seed(mc_unit, 0, 1)` (or the equivalent for each candidate unit hash) exactly as `formula/evaluation.js` case `'number_from_seed'` would (deterministic `sha256` + `Decimal` division), per the reproducible algorithm at: [4](#0-3) 
4. Attacker only broadcasts the trigger (or the specific candidate unit) when the precomputed result is `1` (winning), guaranteeing a win every time and draining the AA's payout funds.
