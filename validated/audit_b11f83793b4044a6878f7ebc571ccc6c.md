### Title
`SystemInstruction::AuthorizeNonceAccount` permanently locks nonce account funds when set to an unverified/incorrect authority - (File: `programs/system/src/system_instruction.rs`)

### Summary
The System program's `authorize_nonce_account` instruction allows the current nonce authority to reassign the nonce account's authority to an arbitrary `Pubkey` in a single, unverified call, exactly the anti-pattern flagged in the external report (single-call, no-verification transfer of a critical privilege). Unlike the Vote and Stake programs, which mitigate this exact risk by offering `AuthorizeChecked`/`AuthorizeWithdrawerChecked` variants that require the new authority to co-sign the transaction, the System program's nonce authorization path has no such "checked" counterpart.

### Finding Description
`SystemInstruction::AuthorizeNonceAccount(nonce_authority)` is dispatched in `system_processor.rs` directly to `authorize_nonce_account`: [1](#0-0) 

The handler itself performs no validation of the new authority beyond that the *current* authority signed: [2](#0-1) 

The instruction data (`nonce_authority: Pubkey`) is supplied entirely by the current authority with no requirement that the new pubkey sign the transaction or otherwise prove control of the corresponding private key — mirroring the `VotingEscrow.transfer_ownership(addr)` pattern in the report, where `addr` is accepted without verification.

By contrast, the Stake program (`StakeInstruction::AuthorizeChecked`, seen via `stake_instruction::authorize_checked`) and the Vote program (`VoteInstruction::AuthorizeChecked` via `vote_instruction::authorize_checked`) both provide a "checked" instruction variant that requires the new authority to be a signer on the transaction, providing exactly the extra verification step recommended by the report: [3](#0-2) [4](#0-3) 

The nonce/System program has no equivalent `AuthorizeNonceAccountChecked` instruction, so the "second signature" safeguard that exists elsewhere in Agave for identical authority-transfer operations is absent here.

### Impact Explanation
A nonce account's lamports (rent-exempt reserve, often exactly the amount needed for account existence, but can also hold larger balances) can only be withdrawn via `SystemInstruction::WithdrawNonceAccount`, which requires the *current* `nonce_authority` to sign, and the durable nonce can only be advanced/reset by the same authority. If the current authority mistakenly (typo, wrong variable, copy-paste error, or by supplying `Pubkey::default()`/an address nobody controls) sets `nonce_authority` to an unowned or incorrect pubkey via `AuthorizeNonceAccount`, there is no recovery path: no signer exists who can call `WithdrawNonceAccount` or call `AuthorizeNonceAccount` again to fix it. The account and its lamports become permanently frozen/unspendable, matching the "permanently frozen accounts" impact category.

### Likelihood Explanation
This requires only an ordinary (unprivileged) transaction sent by whoever currently controls a nonce account (used pervasively for durable-nonce transactions, e.g., offline signing, custody, and DEX/off-chain-signing flows) — no validator or operator privilege needed. Given nonce accounts are commonly manipulated via CLI/RPC tooling (`cli/src/nonce.rs` exposes `authorize-nonce-account`) where the new-authority pubkey is a free-form user-supplied argument, a single fat-fingered address is sufficient to trigger irrecoverable loss, making this a realistic, moderate-likelihood, high-consequence-per-occurrence issue.

### Recommendation
Introduce a `SystemInstruction::AuthorizeNonceAccountChecked` (or equivalent) that requires the new nonce authority to be a signer of the transaction, mirroring the `AuthorizeChecked` pattern already implemented for the Stake and Vote programs, and encourage/require CLI and RPC tooling to prefer the checked variant by default for nonce authority transfers.

### Proof of Concept
1. Create/fund a nonce account with `InitializeNonceAccount`, with `authority = A` (controlled by the user).
2. `A` submits `SystemInstruction::AuthorizeNonceAccount(B)` where `B` is a pubkey nobody holds the private key for (e.g., a mistyped address or `Pubkey::default()`), signed only by `A` as required by `authorize_nonce_account`: [2](#0-1) 
3. The instruction succeeds because only the *current* authority's signature is checked; `B`'s consent/signature is never required.
4. Any subsequent `WithdrawNonceAccount` or `AuthorizeNonceAccount` call requires a signature from `B`, which can never be produced — the account's lamports are permanently frozen.
