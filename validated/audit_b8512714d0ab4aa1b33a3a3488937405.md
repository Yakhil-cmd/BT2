### Title
`StatusHandler` writes commit statuses matched only by global `sha`, decoupled from the webhook's signature-verified organization/repository - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` authenticates an inbound webhook by selecting a GitHub App/secret keyed on the *organization derived from the payload* (`repository.owner.login` or `organization.login`), then validates the HMAC over the raw body against that org's `webhook_secret` [1](#0-0) . Once verification succeeds, `StatusHandler#process` (invoked as a handler for the `status` event) performs its write using only the global commit `sha` field from the payload - it never re-checks that the `sha` belongs to a commit whose repository/stack is owned by the same organization whose secret validated the request: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [2](#0-1) . Because Shipit stores commits with globally-unique/near-unique SHAs but is multi-tenant across organizations (`Shipit.github(organization:)`, each with its own app/secret, as documented in `docs/setup.md` and `test/dummy/config/secrets_double_github_app.yml`) [3](#0-2) [4](#0-3) , a party who can produce a validly-signed `status` webhook for *their own* configured organization can set an arbitrary `sha` value and write a `Status` (e.g. `state: 'success'`) onto any commit already tracked by Shipit, regardless of which organization/repository owns that commit.

### Finding Description
This mirrors the reported `restartDca` pattern precisely: `createDca`/`restartDca` both write DCA state, but `restartDca` omits validation checks (e.g. verifying `isGelatoWatching`/ownership) that `createDca` enforces, letting a caller mutate state belonging to someone else's task by supplying attacker-chosen IDs. Here, the "identity that authenticated" (the organization whose `webhook_secret` validated the HMAC, selected via `repository_owner = params.dig('repository','owner','login') || params.dig('organization','login')`) is never bound to the "record that gets written" (the `Commit` selected purely by `params.sha`, with no repository/stack/organization scoping) [5](#0-4) [2](#0-1) .

Contrast this with the base `Handler` class, which every *other* handler (push, pull_request, membership) uses to scope writes to the repository named in the payload via `Repository.from_github_repo_name(repository_name)` [6](#0-5) . `StatusHandler` is the outlier: it does not call `stacks`/`repository_name` at all, and instead resolves the target purely by `sha`: [7](#0-6) 

Downstream, `Status.create!` runs `after_commit :schedule_continuous_delivery` [8](#0-7) , and a `state: 'success'` status can make a commit `deployable?`, which is exactly what unblocks `Stack#next_commit_to_deploy` and continuous delivery (`ContinuousDeliveryJob#perform` → `stack.trigger_continuous_delivery`) as shown in the test suite (`test/models/commits_test.rb:233-243`, `test/models/shipit/stack_test.rb:727-738`) [9](#0-8) .

Root cause, stated as a broken equality:
`organization authenticated by verify_signature (repository_owner from payload)` ≠ `organization/repository that owns the Commit mutated by StatusHandler (matched only by global sha)`.

### Impact Explanation
An attacker who legitimately controls a `status`-event-producing integration for *any* organization configured in Shipit's multi-tenant `github:` secrets (i.e., can obtain a validly-signed webhook payload for their own org - a low, non-privileged bar, distinct from having a Shipit account, an `ApiClient` token, or write access to the *victim* repository) can forge the `sha` field to reference a commit belonging to a completely different tracked repository/stack. This creates a `Status` record with an attacker-chosen state (e.g. `success`) on that unrelated commit, which can mark the commit "deployable" and trigger an unauthorized continuous-delivery deploy on a stack the attacker has no relationship with, or otherwise poison CI-gated deploy/merge decisions across organizational boundaries. This satisfies the "unauthorized deploy" / cross-repository writes impact bar.

### Likelihood Explanation
Likelihood is moderate-to-high in the documented multi-org deployment (`docs/setup.md` "Using Multiple Github Applications"): once any one organization's webhook secret is known to (or controlled by) the attacker for their own legitimate integration, no further access to the victim organization or its repositories is required, and no Shipit login/API token/GitHub write access to the target repo is needed. The bug requires only that Shipit be configured with more than one GitHub organization sharing one commits table (the standard supported multi-tenant configuration), which is expected engine behavior, not misconfiguration.

### Recommendation
1. In `StatusHandler#process`, scope the `Commit` lookup to the repository named in the payload (as every other handler does via `Handler#stacks`/`repository_name`), e.g. `stacks.commits.where(sha: params.sha)`, instead of the unscoped `Commit.where(sha: params.sha)`.
2. Audit all `Webhooks::Handlers` subclasses to confirm each one binds writes to `Repository.from_github_repo_name(payload['repository']['full_name'])` (or equivalent), matching the organization validated by `WebhooksController#verify_signature`.
3. Add regression tests asserting that a `status` webhook signed by Org A cannot create/modify a `Status` on a commit belonging to a stack under Org B.

### Proof of Concept
1. Configure Shipit with two organizations, `OrgA` and `OrgB`, each with its own GitHub App/`webhook_secret` (per `docs/setup.md`/`secrets_double_github_app.yml`).
2. As a holder of `OrgA`'s legitimate webhook secret (e.g., because `OrgA` is the attacker's own low-trust org integrated with the same Shipit instance), craft a `status` event payload:
   ```json
   {
     "sha": "<sha of a commit belonging to a stack under OrgB>",
     "state": "success",
     "context": "ci/fake",
     "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgA/attacker-repo" }
   }
   ```
3. Sign the raw body with `OrgA`'s `webhook_secret` and send it to `POST /webhooks` with `X-Github-Event: status` and the resulting `X-Hub-Signature`.
4. `verify_signature` resolves `repository_owner` = `"OrgA"`, fetches `Shipit.github(organization: "OrgA")`, and the HMAC validates successfully [10](#0-9) .
5. `StatusHandler#process` executes `Commit.where(sha: params.sha)` and finds the `OrgB` commit purely by SHA, creating a `success` `Status` on it and potentially triggering `ContinuousDeliveryJob` for `OrgB`'s stack [2](#0-1) .

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```

```ruby
module Shipit
  module Webhooks
    module Handlers
      class StatusHandler < Handler
        params do
          requires :sha, String
          requires :state, String
          accepts :description, String
          accepts :target_url, String
          accepts :context, String
          accepts :created_at, String

          accepts :branches, Array do
            requires :name, String
          end
        end

        def process
          Commit.where(sha: params.sha).each do |commit|
            commit.create_status_from_github!(params)
          end
        end
      end
    end
```

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
