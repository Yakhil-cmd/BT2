Confirmed: `completePaymentPayload` in `aa_composer.js` builds payment inputs exclusively from `outputs` (via `readStableOutputs`/`readUnstableOutputsSentByAAs`, both querying only the `outputs` table), never from `headers_commission_outputs` or `witnessing_outputs`. [1](#0-0) 

### Title
AA-earned headers/witnessing commissions are permanently unspendable due to internal balance tracking that never accounts for them - (File: aa_composer.js, storage.js)

### Summary
An Autonomous Agent (AA) address can legitimately receive bytes from two sources: (1) ordinary payment outputs, and (2) headers commissions / witnessing (payload) commissions credited via the protocol's commission-distribution mechanism into `headers_commission_outputs` and `witnessing_outputs`. The AA's internal balance ledger (`aa_balances`, and the `balance[]` oscript primitive that reads from it) is populated and updated exclusively from the `outputs` table — never from `headers_commission_outputs`/`witnessing_outputs`. When an AA composes its response unit, its payment-input selection logic likewise reads only from `outputs`. Bytes credited to the AA via commissions therefore increase the AA address's real, protocol-recognized spendable balance but are invisible to and unreachable by the AA's own logic, becoming permanently stuck — the same class of bug as the reported "internal balance tracking that doesn't account for external balance growth" (rebasing tokens) issue.

### Finding Description
`aa_balances` is the internal ledger AAs use to know "how much do I have." It is initialized/recalculated by summing only the `outputs` table: [2](#0-1)  and is incrementally updated in `updateInitialAABalances`/`updateFinalAABalances` purely from `trigger.outputs` and payment message outputs, again never referencing commission tables: [3](#0-2) [4](#0-3) 

The oscript `balance[]`/`var[]` formula opcode used by AA authors to decide how much to send reads the same `aa_balances` table, so an AA's own code has no way to observe commission income: [5](#0-4) 

Separately, when the AA composer actually assembles the payment inputs for a response unit, it selects unspent transfer outputs only from the `outputs` table (`readStableOutputs`, `readUnstableOutputsSentByAAs`); there is no code path that pulls from `headers_commission_outputs` or `witnessing_outputs` to build `type: 'headers_commission'`/`type: 'witnessing'` inputs, unlike the wallet-side and generic `inputs.js`/`composer.js` code paths that do support building such inputs for ordinary (non-AA) addresses. [1](#0-0) 

Meanwhile, the protocol does treat these commissions as real, spendable balance of the receiving address — `readBalance`/`readSharedBalance` explicitly add `headers_commission_outputs`/`witnessing_outputs` sums to an address's balance for wallets: [6](#0-5)  and `checkBalances()` (the node's own consistency check) only reconciles `aa_balances` against the `outputs` table, meaning a real discrepancy between an AA's true byte holdings (including commissions) and its internally tracked `aa_balances` is not even flagged as an anomaly: [7](#0-6) 

An AA can become a recipient of such commissions: any unit authored by (or that names as `earned_headers_commission_recipients`) the AA address that becomes the "winning" child on the DAG earns headers commission, and if the AA address is a witness or is otherwise a beneficiary of witnessing payouts, it accrues `witnessing_outputs`. AAs can author units (their own response units) and thus be `unit_authors`, and their address can equally be named in `earned_headers_commission_recipients` by other units. This is not a purely theoretical edge case — it is a direct, protocol-level consequence of how commissions are distributed to any address, AA or not.

### Impact Explanation
This is a direct analog of the rebasing-token bug: the contract's (AA's) internal accounting of its own balance never grows with bytes it actually and legitimately possesses, and there is no mechanism in the AA composer to sweep or spend that "invisible" balance. The result is a permanent, protocol-level loss/freezing of AA funds — bytes that belong to the AA (per the ledger and per `balances.js`'s own definition of address balance) can never be spent by that AA's oscript logic, because:
1. `balance[]`/`var['balance']` never reflects it (state logic can't react to it or move it).
2. The payment-input builder in `aa_composer.js` never selects inputs of type `headers_commission`/`witnessing` for an AA-authored payment.

Because this affects the base-asset (bytes) balance of any AA address that ever earns headers or witnessing commissions, and there's no recovery path (the AA can't be manually operated the way a human wallet can, since the AA's spending is entirely defined by its oscript definition and constrained to the `aa_composer.js` input-selection code), the coins become permanently unspendable/lost from the AA's perspective — a fund-freezing condition of Medium/High severity depending on how often AAs realistically end up as commission recipients.

### Likelihood Explanation
Any address, including an AA address, can end up on the winning side of headers-commission distribution (as author of a "child" unit on the DAG, e.g. via its own response units) or as a witness/earned-recipient for witnessing payouts. AAs are extremely common (they author many response units, potentially becoming the "winner" for header commissions of their own trigger's parent units), making the condition plausible rather than purely hypothetical, though it may require specific configurations (e.g., an AA address configured as a witness, or naturally becoming a winning header-commission child) to materialize at scale.

### Recommendation
Either:
1. Extend `aa_balances` tracking and the AA's balance-recalculation SQL (`storage.js` `insertAADefinitions`, and `aa_composer.js` `updateInitialAABalances`) to also account for accrued `headers_commission_outputs`/`witnessing_outputs` amounts belonging to the AA address, and extend `completePaymentPayload`'s input-selection logic to be able to spend `headers_commission`/`witnessing` type inputs when building AA response payments (mirroring what `inputs.js`/`composer.js` already do for regular wallets), or
2. Explicitly disallow AA addresses from being counted as headers-commission/witnessing recipients (e.g., reject `earned_headers_commission_recipients` entries pointing to AA addresses, and prevent AA addresses from being placed in witness lists), so that AAs can never accrue balance through a channel their own accounting/spending logic cannot observe or reach.

### Proof of Concept
1. Deploy an AA whose oscript logic, upon trigger, reads `balance[base]` and sends out `{amount: "{balance[base]}"}` (empties itself each time) — a common "distribute everything I have" pattern using the primitives shown in `formula/evaluation.js`. [5](#0-4) 
2. Arrange for the AA's address to become the winning child unit for a headers-commission distribution round (e.g., by having the AA respond to triggers frequently, since AA response units are `unit_authors` candidates for `headers_commission_contributions`), so that `headers_commission.calcHeadersCommissions` credits bytes into `headers_commission_outputs` for the AA's address. [8](#0-7) 
3. Observe that `aa_balances.balance` (and hence `balance[base]` seen by the oscript) never increases by this amount, and that `completePaymentPayload`'s `readStableOutputs`/`readUnstableOutputsSentByAAs` never select the corresponding `headers_commission` input type when the AA next composes a response. [1](#0-0) 
4. The commission bytes remain permanently in `headers_commission_outputs` with `is_spent=0`, credited to the AA's address but with no code path in `aa_composer.js` capable of ever spending them — permanently locked, mirroring the rebasing-token "stuck rewards" scenario described in the report.
