### Title
Pool `repay` refunds the declared amount — not the funded amount — letting a permissionless caller drain pool custody on a debt-free market - (File: contracts/pool/src/ops/repay.rs)

### Summary
The kernel bug class is "two inputs that must describe one memory region are supplied separately, so they can diverge." The pool's `repay` exhibits the same shape: the refund is computed from the *declared* `action.amount`, while the pool never verifies that amount was actually transferred in. On a market with no outstanding debt the entire declared amount becomes "overpayment" and is paid out of real token custody to an arbitrary `payer`. The in-repo test `test_unfunded_repay_overpayment_refund_also_pays_out_of_custody` demonstrates exactly this drain.

### Finding Description
`repay::apply` resolves `(burned, overpayment)` from `action.amount`, credits `net_repay` to the cash book, and then calls `cache.transfer_out(payer, outcome.overpayment)` — an outbound transfer of pool custody that is not debited from `cash` and is not validated against any measured inbound transfer (`contracts/pool/src/ops/repay.rs` lines 25–67). The only synchronization assumption is the module comment "The controller transfers the repay amount into the pool before this call" — an ordering/layout assumption across two separate calls, precisely the kernel bug's "separate allocations expected to be one region" pattern.

The pool-suite test proves custody is drained: a `repay` whose declared `amount` equals `token.balance(pool)` against a market with zero debt refunds the entire custody to a freshly generated `payer` who deposited nothing (`contracts/pool/tests/flows.rs` lines 3578–3611: "the whole amount is refunded out of real custody with the book untouched"). The test's own comment notes the same gap exists in `ops::recapitalize::apply` (excess over shortfall refunded from declared amount).

Reachability: `repay` is exposed on the pool client with a plain `payer: Address` argument; the unit test invokes it directly with a generated payer and no mocked auth, indicating no `require_auth` on the caller and no controller-only check on this path (I could not fully confirm the auth gate in `contracts/pool/src/lib.rs` — if the pool gates `repay` to the controller address, this finding degrades; that is the one unverified precondition).

### Impact Explanation
Theft of user funds / contract unable to operate from lack of token funds: a single `repay` call with `amount = pool_token_balance` on any market with zero outstanding debt transfers the entire pool custody — all suppliers' underlying — to the caller. On markets with debt, `overpayment = amount - debt`, so custody minus current debt is drainable per call. Suppliers' shares remain on the book but the cash backing them is gone.

### Likelihood Explanation
If `repay` is callable by any address (as the unit test implies), the exploit needs no setup: no deposit, no account, no timing, and zero debt markets exist at market creation and whenever debt is fully repaid or written off via `clean_bad_debt`. One transaction with `amount` set to the pool's token balance suffices.

### Recommendation
Bind the refund to the actual inbound movement, not the declared amount: either require the controller (or `payer`) to pass a measured receipt and cap `overpayment` at `amount_in - net_repay` where `amount_in` is the observed pool balance delta, or pull the repay amount inside `repay` itself (e.g., `transfer_from`/authorized transfer) so the funded region and the accounted region are the same — the direct analog of the upstream fix allocating request and response in one contiguous buffer. Additionally gate `repay` to the controller if it is not already.

### Proof of Concept
```rust
// Pool with supplied liquidity, zero outstanding debt.
let token = token::Client::new(&env, &asset);
let attacker = Address::generate(&env);
let custody = token.balance(&pool); // e.g., all suppliers' USDC

// No transfer, no auth, no debt to repay:
let credited = pool_client
    .repay(&attacker, &RepayAction { position: zero, amount: custody })
    .get(0).actual_amount;

assert_eq!(credited, 0);                      // nothing booked
assert_eq!(token.balance(&attacker), custody); // entire custody drained
assert_eq!(token.balance(&pool), 0);
```
This mirrors the pinned behavior of `test_unfunded_repay_overpayment_refund_also_pays_out_of_custody` in `contracts/pool/tests/flows.rs` (lines 3589–3611), which documents that the refund "pays out of real custody with the book untouched."
