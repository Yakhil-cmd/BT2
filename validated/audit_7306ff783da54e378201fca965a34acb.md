### Title
Webhook signature is validated against the organization in `repository.owner.login`, but handlers act on the repository named in `repository.full_name` — an admin of one onboarded GitHub organization can forge events that write to another organization's stacks - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which organization's `webhook_secret` to validate the HMAC signature against using `repository.owner.login` (or `organization.login`) taken from the untrusted JSON body, while every webhook `Handler` resolves the actual `Repository`/`Stack` to mutate using a *different* field from the same body, `repository.full_name`. Nothing enforces that these two fields refer to the same organization, so a party who legitimately controls the webhook configuration for Org A (and therefore knows Org A's `webhook_secret`) can sign an arbitrary payload whose `repository.full_name` points at Org B's repository, and Shipit will accept it and mutate Org B's stacks.

### Finding Description
Shipit supports multi-tenant GitHub App configuration, one `webhook_secret` per organization: [1](#0-0) 

The controller picks the verifying secret solely from the attacker-supplied body: [2](#0-1) [3](#0-2) 

But every handler (`PushHandler`, `StatusHandler`, and all `PullRequest::*Handler`s) resolves the repository/stack to act on from a *different* field, `repository.full_name`, via the shared base class: [4](#0-3) 

For example `PushHandler` triggers `sync_github` (which reconciles commits and can drive continuous deployment) on any stack matching the branch, scoped only by `repository.full_name`: [5](#0-4) 

And the pull-request handlers `archive!`/`unarchive!`/`deprovision` review stacks resolved the same way: [6](#0-5) [7](#0-6) 

The binding that should hold is: **organization authenticated (via `repository.owner.login` → `webhook_secret`) == organization whose repository is written (via `repository.full_name`)**. Because both values are just JSON keys inside the same HMAC-signed body, and the signature check never cross-validates them against each other, an entity that controls Org A's GitHub webhook (and thus knows Org A's `webhook_secret`, which is often provisioned/rotated by the organization's own admins, not by Shipit operators) can produce a validly-signed body for Org A while setting `repository.full_name` to `OrgB/some-repo`. `verify_signature` passes (signature matches Org A's secret and raw body), and the handler then acts on Org B's stack.

### Impact Explanation
This crosses the "organization authenticated versus the repository that is written" trust boundary explicitly called out as in-scope. In a Shipit deployment onboarding multiple organizations/customers with distinct GitHub Apps, this allows a lower-trust org's webhook holder to:
- Trigger `sync_github`/push-driven continuous deployment reconciliation on another organization's stack (`PushHandler`), which can lead to unauthorized deploy/rollback pipelines being kicked off for commits the attacker names via `params.after`.
- Archive, unarchive, or deprovision another organization's review stacks (`ClosedHandler`, `LabeledHandler`, `UnlabeledHandler`, `OpenedHandler`, `ReopenedHandler`), causing cross-repository writes to infrastructure state that does not belong to the attacker's org.

This matches the specified High/Critical impact category of "cross-repository writes" / "an unauthorized deploy, rollback".

### Likelihood Explanation
Requires that the operator has configured more than one organization's `webhook_secret` in `secrets.github` (the multi-org schema `lib/shipit.rb#github_app_config`), and that the attacker is the party controlling the webhook delivery/secret for one of those organizations — a condition explicitly allowed by the rules (breaking a deployment-trust binding without needing a Shipit session/API token/full compromise). No additional Shipit credentials are needed beyond knowledge of one onboarded organization's own webhook secret, which that organization's own administrators legitimately possess.

### Recommendation
In `WebhooksController`/`Shipit::Webhooks::Handlers::Handler`, ensure the organization used to select the verifying `webhook_secret` is the same organization referenced by `repository.full_name` used for the actual write target — e.g., derive both from `repository.full_name` consistently, or explicitly assert `repository.owner.login == repository.full_name.split('/').first` before verification succeeds, rejecting the payload with 422 if they diverge.

### Proof of Concept
1. Shipit is configured with two organizations, `org-a` and `org-b`, each with its own `webhook_secret` (`lib/shipit.rb#github_app_config`).
2. Org A's webhook administrator (or anyone who legitimately knows Org A's `webhook_secret`) crafts a `push` event payload:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "org-a" },
    "full_name": "org-b/victim-repo"
  }
}
```
3. They compute `X-Hub-Signature: sha1=<HMAC-SHA1(org-a webhook_secret, body)>` and POST it to `/webhooks`.
4. `WebhooksController#verify_signature` looks up `Shipit.github(organization: "org-a")` (from `repository.owner.login`) and successfully verifies the signature against Org A's secret — see `app/controllers/shipit/webhooks_controller.rb:24-31`.
5. `PushHandler#process` resolves `stacks` via `Handler#repository_name` (`payload.dig('repository','full_name')` = `"org-b/victim-repo"`), locating and mutating Org B's stack — see `app/models/shipit/webhooks/handlers/handler.rb:32-38` and `app/models/shipit/webhooks/handlers/push_handler.rb:12-17`.
6. Org B's stack is reconciled/synced (and, depending on continuous-deployment configuration, deployed) using data the Org A party fully controls, despite Org A having no legitimate access to Org B's repository.
