### Title
Textcoin mnemonic (spending key) stored inside the same file as the private payment chain data - (File: `wallet.js`)

### Summary
When a private (hidden) asset is sent as a textcoin to an address on the same device (no `recipient_device_address`, no online device to receive over the hub), `wallet.js` writes the claim mnemonic — which *is* the private key controlling the recipient (claim) address — together with the private-payment chain (the blinded outputs/amounts that constitute the confidential payment data) into a single exported artifact. This mirrors the reported bug class exactly: the decryption/spending key is bundled with the data it protects, so a single leaked artifact grants both disclosure and immediate control of funds.

### Finding Description
`storePrivateAssetPayload` builds one combined object containing the mnemonic and the private chains, then zips and writes it to a single file: [1](#0-0) 

The `mnemonic` here is not a mere passphrase; `expandMnemonic` derives the actual private key (`xPrivKey`) and definition (`["sig", {"pubkey": ...}]`) that controls the claim address — i.e., possessing the mnemonic is equivalent to possessing full spending authority over the address: [2](#0-1) 

This combined object is produced in the `sendMultiPayment` flow, specifically the branch that handles private assets sent to a textcoin-style address without a live device recipient (`Object.keys(assocAddresses).length > 0`), where the caller supplies a file path via `opts.getPrivateAssetPayloadSavePath`: [3](#0-2) 

The private chain itself (`arrChainsOfRecipientPrivateElements`) carries the blinding factors and amounts that reveal the confidential asset transfer — the exact analog of "encrypted data" in the original report — while the mnemonic is the analog of the "encryption/decryption key." Both are written into the very same `private_textcoin` zip entry, with no separation of storage, no OS-level keychain protection, and no access-control boundary between the two.

On the import side, `handlePrivatePaymentFile` reads this same combined object back and uses `data.mnemonic` directly to derive the address and check/claim funds, confirming that whoever holds this single file has everything needed to both view and spend the private payment: [4](#0-3) 

### Impact Explanation
Any medium that can carry this exported file (shared folder, cloud-synced downloads directory, backup, USB transfer, unintended app sandbox exposure, etc.) exposes not just the confidential transaction contents, but also unconditional, immediate spending authority over the funds at the claim address — there is no additional secret, device pairing, or hub-mediated exchange required. This directly satisfies "concrete unauthorized spending" of the private asset: anyone obtaining the file can call the equivalent of `receiveTextCoin`/`handlePrivatePaymentFile` and redirect the private-asset payment to an address they control before the legitimate recipient does so, since possession of the mnemonic alone is sufficient to sign a spending unit for that address.

### Likelihood Explanation
This code path is reached by ordinary wallet functionality — sending a private asset with no online recipient device (the "same device, different wallet" / textcoin file-export flow) — and is not gated by any privileged or hub-side check. Any private-payment counterparty relying on file-based transfer of a private-asset textcoin is exposed. The only requirement is that the exported file end up somewhere an attacker can read it, which is a realistic condition for files meant to be transferred between wallets/devices (e.g., via cloud storage, messaging apps, or shared filesystem locations), making likelihood moderate-to-high for any deployment that uses this feature.

### Recommendation
Do not bundle the spending mnemonic and the private chain payload in the same artifact. Separate the key material from the payment data: transmit/store the mnemonic through a distinct, higher-trust channel (e.g., encrypted separately with a passphrase/OS keychain, or communicated out-of-band), and keep the private chain payload as the only content of the exported file. If a single-file workflow is required, encrypt the mnemonic under a key that is not co-located with the file (e.g., derived from a user-supplied passphrase or protected by platform keychain APIs) so that leaking the file alone does not confer spending capability.

### Proof of Concept
1. Sender calls `sendMultiPayment` to send a private (hidden) asset to a `textcoin:`-style address with no `recipient_device_address` (e.g., cross-wallet, same-device transfer intended for later import), supplying `opts.getPrivateAssetPayloadSavePath`.
2. `wallet.js`'s `preCommitCb` branch (`wallet.js:2409-2421`) invokes `storePrivateAssetPayload(fullPath, cordovaPathObj, mnemonic, arrChainsOfRecipientPrivateElements, cb)`.
3. `storePrivateAssetPayload` (`wallet.js:2850-2864`) writes a zip file whose sole entry `private_textcoin` is `{ mnemonic, chains }` — both the spending key and the confidential payment chain in one artifact.
4. Any third party who obtains this file (e.g., via a shared/cloud-synced save path) parses it and reads `data.mnemonic` directly (as `handlePrivatePaymentFile` itself does at `wallet.js:2918-2919`), derives the private key via `expandMnemonic`, and immediately signs a transaction to redirect the private asset to an address of their choosing — no further secret or authorization is needed.

function expandMnemonic(mnemonic) {
	var addrInfo = {};
	mnemonic = mnemonic.toLowerCase().split('-').join(' ');
	if ((mnemonic.split(' ').length % 3 !== 0) || !Mnemonic.isValid(mnemonic)) {
		throw new Error("invalid mnemonic: "+mnemonic);
	}
	mnemonic = new Mnemonic(mnemonic);
	addrInfo.xPrivKey = mnemonic.toHDPrivateKey().derive("m/44'/0'/0'/0/0");
	addrInfo.pubkey = addrInfo.xPrivKey.publicKey.toBuffer().toString("base64");
	addrInfo.definition = ["sig", {"pubkey": addrInfo.pubkey}];
	addrInfo.address = objectHash.getChash160(addrInfo.definition);
	return addrInfo;
}
