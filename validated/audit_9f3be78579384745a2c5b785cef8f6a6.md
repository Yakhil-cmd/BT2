### Title
Signed-package replay across multiple AA instances/purposes due to missing domain binding in `is_valid_signed_package` - (File: formula/evaluation.js, object_hash.js, signed_message.js)

### Summary
`is_valid_signed_package(signed_package, address)` (implemented via `signed_message.validateSignedMessage` and `objectHash.getSignedPackageHashToSign`) only proves that `address` cryptographically signed the `signed_message` payload plus generic envelope fields (`authors`, `last_ball_unit`, `version`). It never binds the signature to `this_address` (the specific AA instance consuming it), to the specific asset/AA logic, or to any AA-specific nonce beyond what the AA author manually puts inside `signed_message`. This is structurally identical to the RabbitHole `mintReceipt` bug: a signature is valid input to any consumer that accepts the same `(signer, payload-shape)` pair, so it can be replayed across multiple AA instances deployed from the same oscript template.

### Finding Description
`is_valid_signed_package` is evaluated in `formula/evaluation.js` and delegates to `signed_message.validateSignedMessage`, whose hash-to-sign is computed purely from the signed package's own fields via `objectHash.getSignedPackageHashToSign` [1](#0-0) . The oscript-level primitive checks only that the given `address` signed the package [2](#0-1) .

Crucially, nothing in the framework injects the calling AA's own address (`this_address`), asset id, or chain-scoped nonce into the data being signed or verified — that binding is entirely optional and left to the AA author to add inside `signed_message`. The repository's own reference AAs demonstrate both patterns:

- `payment_channels.oscript` explicitly guards against this by checking `trigger.data.sentByPeer.signed_message.channel != this_address` before calling `is_valid_signed_package` [3](#0-2) , i.e., the author had to manually add contract-instance binding to prevent replay.
- `order_book_exchange.oscript`, by contrast, verifies orders with `is_valid_signed_package(trigger.data.order1, $order1.address)` and de-duplicates only via a per-AA state variable keyed by `sha256(address||sell_asset||buy_asset||sell_amount||price||last_ball_unit)` [4](#0-3)  — it never includes `this_address` in the signed content or in the id. Because `var['executed_'||id]` is state local to each AA instance, the exact same signed order package accepted by one deployed instance of this exchange template remains fully valid (same signature, same hash) and unused (`executed_`-flag absent) on any other AA instance instantiated from the identical oscript with the same asset pair — the signature can be replayed to trade on the second instance without the signer's renewed consent.

This mirrors the external report's root cause precisely: the signed payload lacks a field that scopes it to one specific consuming contract (chain id / contract address in the Solidity case; `this_address` in ocore), so the same signature is accepted by every consumer that shares the verification address and payload shape.

### Impact Explanation
If an off-chain-signed order/authorization is valid input to more than one deployed AA instance (a realistic scenario for template-based exchange/marketplace/state-channel AAs, which are exactly the intended use case for `is_valid_signed_package`), an attacker who obtains a previously used signed package (packages are often transmitted in plaintext trigger data or published on-chain once used) can resubmit it to a different AA instance sharing the same template and asset configuration to execute an unintended trade/transfer. This causes AA fund movement the user never authorized for that specific instance — a concrete instance of "AA fund loss" through unauthorized use of a signed authorization.

### Likelihood Explanation
Likelihood depends on AA design: any AA author who does not manually bind `this_address` (or another AA-specific salt) into `signed_message`, as the shipped `order_book_exchange.oscript` sample does not, exposes users of every instance deployed from that template to replay by anyone who can observe a previously-submitted signed package (order-book/marketplace models routinely publish orders to multiple potential counterparties/relayers). The framework provides no default protection and no warning; the sample code itself shows the inconsistency (one template protects, the other does not), indicating this is an easy, non-obvious pitfall rather than a deliberately accepted design tradeoff.

### Recommendation
- Have `is_valid_signed_package`/`validateSignedMessage` optionally require (or at minimum strongly recommend/document) inclusion of `this_address` and, where relevant, `asset`/chain-scoped identifiers inside `signed_message` before verification succeeds for AA use, similar to EIP-712 domain separation.
- Update documentation and the shipped sample templates (`order_book_exchange.oscript`) to consistently bind signed packages to `this_address` the way `payment_channels.oscript` already does, so AA authors have a safe example to copy instead of an inconsistent one.
- Consider adding a built-in domain-separated variant of `is_valid_signed_package` that automatically mixes in `this_address` so authors cannot forget it.

### Proof of Concept
1. Deploy two AA instances from the identical `order_book_exchange.oscript` template (e.g. `AA_1` and `AA_2`), both trading the same asset pair, each funded by the same user address `U`.
2. `U` signs an order package `pkg = {signed_message: {sell_asset, buy_asset, sell_amount, price, address: U}, last_ball_unit, authors:[{address:U, definition, authentifiers}]}` intending to trade only on `AA_1`.
3. `U`'s counterparty executes the trade against `AA_1` via `is_valid_signed_package(pkg, U)`, which succeeds and consumes `var['executed_'||id]` in `AA_1`'s state only.
4. An observer resubmits the same `pkg` as `trigger.data.order1` (or `order2`) to `AA_2`. `is_valid_signed_package(pkg, U)` succeeds again (same signature, same hash, unrelated to `AA_2`'s address), and because `AA_2` has its own independent `executed_`-state, the order executes a second, unauthorized trade drawing on `U`'s balance in `AA_2`.
