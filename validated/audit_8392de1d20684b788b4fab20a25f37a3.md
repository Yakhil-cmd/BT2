### Title
Signature verification is fully bypassed when `webhook_secret` is unset, letting an unauthenticated attacker forge GitHub events and trigger unauthorized deploys - (File: lib/shipit/github_app.rb)

### Summary
`GitHubApp#verify_webhook_signature` short-circuits to `true` whenever `webhook_secret` is blank, and `webhook_secret` is explicitly documented and shipped as an optional/nil-able configuration key. This breaks the binding the report's bug class targets: *"an organization that authenticated" (the `X-Hub-Signature` HMAC check) versus "the repository that is written"* (the `Repository`/`Stack`/`Commit` records mutated by `Shipit::Webhooks::Handlers`). When the operator leaves `webhook_secret` empty — the shipped default — anyone on the network can `POST /webhooks` with a self-crafted, unsigned JSON payload and have it processed as if it came from GitHub.

### Finding Description
The webhook signature check is: [1](#0-0) 

```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
```

`webhook_secret` is optional by design and defaults to blank in every shipped config example: [2](#0-1) 

`WebhooksController#verify_signature` selects the `GitHubApp` (and thus the secret) using a field taken from the *unverified* JSON body itself (`repository_owner`), then calls `verify_webhook_signature`: [3](#0-2) 

If that organization's `webhook_secret` is blank, verification passes unconditionally — no `X-Hub-Signature` header is required, and the header value is never checked. The unauthenticated request is then dispatched straight to the registered handlers, whose data (repository name, SHA, commit `state`, `description`, `target_url`) is trusted at face value to identify and mutate records: [4](#0-3) [5](#0-4) 

`StatusHandler` writes a `Status` (`state`, `description`, `target_url`, `context`) for any `Commit` whose `sha` is guessed/known by the attacker, directly from the unauthenticated payload, with no cross-check against the real GitHub API. Because `Stack#continuous_deployment?`/commit checks (`app/models/shipit/commit_checks.rb`, `app/jobs/shipit/continuous_delivery_job.rb`) rely on these `Status`/`CommitChecks` records to decide whether a commit is deployable, an attacker who can guess or observe a public commit SHA can forge a `success` status for it and cause `ContinuousDeliveryJob` to deploy that commit — an **unauthorized deploy** — without ever presenting a webhook secret, an `ApiClient` token, or a GitHub credential.

This mirrors the bug class exactly: just as `forceDeallocatePenalty = 0` removes the intended economic gate on `forceDeallocate` (turning a "penalized but permitted" action into a fully permissionless one), an empty `webhook_secret` removes the intended cryptographic gate on `/webhooks`, turning "authenticated GitHub event" into "any HTTP POST."

### Impact Explanation
This crosses the required Critical boundary: **an unauthorized deploy**. With no `webhook_secret` configured (the documented/default state), an attacker with only network access to the Shipit instance can:
1. Discover a tracked repository/stack and a real (public) commit SHA.
2. POST an unsigned `status` event marking that SHA as `state: success` for whatever `context`s the stack's deploy spec checks.
3. Have `ContinuousDeliveryJob` treat the commit as deployable and trigger a real deploy, running the stack's deploy script with `GITHUB_TOKEN`/GitHub App credentials on the deploy host.

This is more severe than "unauthenticated read" — it is unauthenticated write access to deployment-gating state that results in code execution/deploys on the host.

### Likelihood Explanation
Likelihood is **operator-configuration dependent but plausible**: `webhook_secret` is presented in every example config (`config/secrets.development.example.yml`, `docs/setup.md`) as optional ("Webhook secret (optional): Fill it with some randomly generated string"), and the code explicitly treats "no secret" as "trust everything" rather than failing closed. Any operator who follows the documented "optional" framing and skips setting it exposes `/webhooks` (a route that, per `docs/setup.md`, must be publicly reachable at `<homepage>/webhooks` for GitHub to call it) to full spoofing. No authentication, TLS interception, or insider access is required — only knowledge of the target org/repo name and a valid commit SHA, both of which are typically public.

### Recommendation
Fail closed instead of open: `verify_webhook_signature` should reject the request (or the app should refuse to boot / should force-disable the `/webhooks` route) when `webhook_secret` is not configured, rather than treating a missing secret as "signature not required." At minimum, emit a hard startup warning/error and require an explicit, unambiguous opt-in (e.g., `webhook_secret: false` rather than merely omitting the key) before allowing unauthenticated webhook processing, mirroring the recommendation in the source report to avoid a "penalty of zero" default that silently strips the control.

### Proof of Concept
Given a Shipit deployment configured with `github.webhook_secret` left blank (as in the shipped example config), an external attacker can:

```
POST /webhooks HTTP/1.1
Host: shipit.example.com
X-Github-Event: status
Content-Type: application/json
(no X-Hub-Signature header needed)

{
  "sha": "<public commit sha tracked by the stack>",
  "state": "success",
  "context": "ci/required-check",
  "target_url": "https://attacker.example/fake",
  "repository": { "owner": { "login": "<victim-org>" }, "full_name": "<victim-org>/<victim-repo>" }
}
```

Because `Shipit.github(organization: "<victim-org>").verify_webhook_signature` returns `true` for any signature/body when `webhook_secret` is blank (`lib/shipit/github_app.rb:76-83`), `WebhooksController#create` proceeds to run `StatusHandler`, which creates a `Status` row for the matching `Commit` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`). If this satisfies the stack's deploy checks, `ContinuousDeliveryJob` (`app/jobs/shipit/continuous_delivery_job.rb:10-21`) will deploy the commit on the next cron tick.

**Uncertainty note:** I was not able to fully trace `Stack#deployable?`/`CommitChecks` logic within the tool-call budget to confirm exactly which check contexts are required for `continuous_deployment?` to trigger a deploy for every stack configuration (this may vary by `shipit.yml` `ci` settings). The core signature-bypass primitive (`lib/shipit/github_app.rb:76-83`) and its unauthenticated write path into `Status`/`Commit` records is confirmed directly from the code; whether a given stack is configured to auto-deploy off that status is configuration-dependent and would need to be validated against a specific deployment's `shipit.yml`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)

        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```
