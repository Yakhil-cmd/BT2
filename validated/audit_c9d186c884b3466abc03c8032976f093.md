### Title
Any address can register itself as a permanently-bouncing AA to force the reversal of every future AA batch payment that includes it - ([File: aa_composer.js])

### Summary
`handleTrigger()`'s `handleSecondaryTriggers()` function automatically fires a secondary AA trigger for every output address of a response unit that happens to be an AA address. If **any one** of those secondary triggers bounces, the entire chain — including the primary trigger and every other successfully-processed recipient in the same response unit — is unconditionally reverted. Because deploying a self-bouncing AA is free, permanent, and requires no privilege, this reproduces the CrabNetting "blacklisted address in a shared withdrawal batch" bug class: a single hostile participant can permanently poison any batched, multi-recipient AA payout that includes their address.

### Finding Description
When an AA response unit pays out to several addresses in one message (e.g. a rewards/refund/dividend distribution AA that iterates over a stored list of beneficiaries and sends them all a payment in the same trigger, similar in spirit to CrabNetting's `withdraws[]` array), `sendUnit()` collects all non-self output addresses into `arrOutputAddresses` and hands them to `handleSecondaryTriggers()`: [1](#0-0) 

For every output address that is itself an AA, a secondary trigger is fired via `handleTrigger()`. Bounce-fee sufficiency checks are explicitly skipped for secondary triggers ("being able to pay for bounce fees is not required for secondary triggers as they never actually send any bounce response or change state when bounced"), so an attacker's AA can always fail cheaply regardless of the amount it receives: [2](#0-1) 

Crucially, the aggregation logic treats a single secondary-trigger failure as fatal to the **entire** batch: [3](#0-2) 

`revert()` then rolls back the whole primary trigger's response — including the payments already computed for every other, non-malicious recipient in the same unit — and turns the primary response into a bounce: [4](#0-3) 

An attacker only needs to define and register a trivial AA whose template makes it always error out or "bounce" on any incoming trigger (e.g. an AA definition with no valid `messages`, or one that references an undefined state var, or has a `bounce()`-style unconditional failure), and cause its address to be added as one of the outputs in a shared/batched payout the way CrabNetting's `queueCrabForWithdrawal()` lets any user register into a shared `withdraws[]` array. Once registered, every future distribution/settlement that includes this address in the same output batch will deterministically revert in full — there is no mechanism analogous to a try/catch that would let the engine skip the failing secondary AA and still deliver funds/state changes to the other participants.

### Impact Explanation
This is a High-severity denial-of-service against any AA whose design pays multiple recipients from state in a single trigger (auctions, staking/dividend/reward AAs, crowdfunding refunds, batched settlement AAs, etc. — the same functional shape as CrabNetting's `netAtPrice()` distributing to queued withdrawers). A single malicious, permanently-registered address can:
- Cause the AA's per-batch response to always bounce, freezing the funds/state transitions intended for every other legitimate user in that batch.
- Repeat this for every future invocation of the batch operation, with no way for the AA operator to exclude/skip the malicious participant once state has been accepted, exactly mirroring the "no way in the current implementation for the protocol to address this issue" impact of the original report.

### Likelihood Explanation
Likelihood is high: deploying an AA and getting it registered as a beneficiary in a shared payout list generally only costs the minimal bounce fee/registration deposit the target AA requires (analogous to CrabNetting's "transfer a small amount of crab"), and the always-bouncing AA definition itself is trivial to construct. No special privilege, timing, or race condition is required.

### Recommendation
`handleSecondaryTriggers()` should not let a failing secondary trigger cascade into a full `revert()` of the primary response by default. Consider:
- Isolating each secondary trigger's failure so that only its own state changes/response are discarded (already partially true via the bounce mechanics), without forcing rollback of the primary trigger and sibling secondary triggers.
- Or documenting/enforcing that AA authors must not rely on secondary-trigger success for correctness of payments to co-recipients, and provide an oscript-level primitive to pay addresses without invoking them as AAs (skip secondary triggering) for exactly this class of batch-payout use case.

### Proof of Concept
1. Attacker deploys AA `M` whose `messages` template makes `evaluateAA` fail unconditionally on trigger (e.g., referencing an undefined getter or an unsatisfiable formula), guaranteeing `bounce(err)` in `handleTrigger` for any incoming payment.
2. Attacker gets `M`'s address included as one of several recipients in a state array of a target payout AA `P` (in the same way a user calls `queueCrabForWithdrawal()` to enter a shared queue) — e.g., by depositing into `P` and being added to its beneficiary list.
3. When `P`'s owner/logic triggers a batched distribution that emits one payment message with outputs to `M` and several honest addresses, `sendUnit()` executes and calls `handleSecondaryTriggers(objUnit, arrOutputAddresses)` [5](#0-4) .
4. `M`'s secondary trigger bounces, `async.eachSeries` receives `err`, and since `P`'s trigger is primary, `revert()` is called, undoing `P`'s entire response, including the payments already computed to the honest recipients [6](#0-5) .
5. Every subsequent batched distribution from `P` that still contains `M` in the output set will bounce identically, permanently denying payouts to all co-beneficiaries.
