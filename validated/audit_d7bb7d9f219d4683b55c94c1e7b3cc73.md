### Title
Webhook signature is verified against the organization named in the payload while the handlers act on a different, unchecked repository field, allowing cross-tenant webhook forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects which tenant's `webhook_secret` to validate an inbound webhook against using `repository_owner`, which is read from the payload field `repository.owner.login` (falling back to `organization.login`). Once the signature check passes, `Shipit::Webhooks::Handlers::Handler#stacks`/`#repository_name` selects the actual repository to act on using a *different* payload field, `repository.full_name`. Because the two fields are never cross-validated, and Shipit officially supports multiple independent GitHub Apps/organizations each with its own `webhook_secret` sharing one deployment, an attacker who legitimately controls one tenant organization's webhook secret can forge a payload that authenticates as their own org but targets a different org's repository/stack.

### Finding Description
The signature check is: [1](#0-0) [2](#0-1) 

`Shipit.github(organization: repository_owner)` looks up the `GitHubApp` (and its `webhook_secret`) configured for the organization named in the attacker-supplied JSON body itself (`repository.owner.login`), per the multi-org config schema: [3](#0-2) 

This is a documented, supported feature — each organization gets its own independent `webhook_secret`: [4](#0-3) [5](#0-4) 

`verify_webhook_signature` then simply HMACs the *entire raw body* with that org's secret: [6](#0-5) 

Once the check passes, `create` dispatches the parsed JSON to handlers: [7](#0-6) 

Every handler resolves the target repository/stacks from a **different, independent** field, `repository.full_name`, with no comparison back to `repository.owner.login`: [8](#0-7) 

`PushHandler` uses this to trigger a sync of arbitrary commits into a stack's deploy history, and `StatusHandler` uses it to forge commit CI statuses: [9](#0-8) [10](#0-9) 

**Root cause / broken binding:** the code implicitly assumes `repository.owner.login` (the field used to select *whose* secret authenticates the request) always matches the owner embedded in `repository.full_name` (the field used to decide *which* repository/stack is mutated). Nothing enforces this equality. An attacker fully controls the raw JSON body they send to `/webhooks`, so they can set these two fields independently: `Org_that_authenticated (repository.owner.login) ≠ Org/repo_that_is_written (repository.full_name)`.

### Impact Explanation
In a multi-tenant Shipit deployment (the documented "Using Multiple Github Applications" configuration), an org that has legitimately been given its own GitHub App/webhook secret for its own repositories can forge webhook events — signed with its own valid secret — that instead target another tenant organization's repositories tracked by the same Shipit instance. This can:
- Force `PushHandler` to enqueue `GithubSyncJob` against another org's stack with an attacker-chosen `expected_head_sha`, corrupting that stack's git-sync state [9](#0-8) .
- Force `StatusHandler` to inject fabricated commit statuses (`create_status_from_github!`) for commits in another org's repository, which can be used to make CI checks appear green and enable unauthorized merges/deploys downstream [10](#0-9) .

This is a cross-repository write / potential unauthorized-deploy vector achieved purely by an org that only has legitimate credentials for its own tenant — it never needs the victim organization's secret, GitHub App key, or a Shipit session for the victim org.

### Likelihood Explanation
Requires: (1) the Shipit instance to be configured for multiple GitHub organizations (a documented, supported setup), and (2) the attacker to control (or be) one of those tenant organizations with its own valid webhook secret — no privilege escalation, no secret guessing, no cryptographic break, just crafting a JSON body with mismatched `repository.owner.login` and `repository.full_name` fields and a correctly-computed HMAC using their own known secret.

### Recommendation
After computing `repository_owner` and verifying the signature, also derive the repository/stack owner from `repository.full_name` (or `organization.login`) and reject the request (422) if it does not match the organization whose secret validated the signature. Equivalently, `Handler#repository_name`/`#stacks` should refuse to resolve to a `Repository` whose `owner` differs from the authenticated organization for the request.

### Proof of Concept
1. Configure Shipit with two tenant orgs, `OrgA` (attacker-controlled, secret `SECRET_A`) and `OrgB` (victim, secret `SECRET_B`), both with stacks tracked by the same Shipit instance — per `docs/setup.md`'s multi-org example.
2. Attacker builds a push payload:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>",
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/victim-repo" }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC_SHA1(SECRET_A, body)` using their own known secret for `OrgA`.
4. `WebhooksController#verify_signature` resolves `repository_owner` = `"OrgA"`, fetches `Shipit.github(organization: "OrgA")`, and the signature validates successfully because the attacker legitimately knows `SECRET_A`.
5. `create` dispatches to `PushHandler`, which resolves `repository_name` = `"OrgB/victim-repo"` via `payload.dig('repository','full_name')`, finds `OrgB`'s stack, and enqueues `GithubSyncJob` with the attacker-supplied `expected_head_sha` — despite the request never being authenticated by `OrgB`'s secret.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
