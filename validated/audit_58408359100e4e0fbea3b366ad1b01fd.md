### Title
Cross-organization webhook forgery due to signature-selection field being independent of the repository-resolution field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks the HMAC verification secret using an organization name derived from attacker-controlled JSON (`repository.owner.login` / `organization.login`), but the event handlers that actually mutate state resolve the target `Repository`/`Stack` from a completely different, also attacker-controlled field (`repository.full_name`). Because the two fields are never checked for consistency, a webhook whose signature is valid for one organization's secret can be crafted to act on a different organization's repository.

### Finding Description
Shipit supports multi-tenant GitHub App configuration, where each GitHub organization can have its own `webhook_secret` (`Shipit.github_app_config(organization)` / `TOP_LEVEL_GH_KEYS` in `lib/shipit.rb`, lines 170-200). `WebhooksController#verify_signature` chooses which organization's secret to verify the incoming `X-Hub-Signature` against by reading: [1](#0-0) 

`repository_owner` is computed purely from the JSON body, before the signature has been validated: [2](#0-1) 

Once `head(422)` is not triggered (i.e., the signature matches the org whose secret was selected), `WebhooksController#create` dispatches the *entire same payload* to the registered handler: [3](#0-2) 

But the base `Handler` class resolves the affected repository/stacks using a **different** field of the payload — `repository.full_name` — with no cross-check against the organization that was actually used to verify the signature: [4](#0-3) 

`Repository.from_github_repo_name` performs a plain DB lookup by `owner/name` split from that string, again independent of which org's secret verified the request: [5](#0-4) 

This breaks the intended equality `organization whose secret verified the signature == organization that owns the repository being written to`. Concretely, an attacker who controls (or has webhook access to) *any* GitHub organization configured in the same multi-tenant Shipit instance — call it `attacker-org`, with a known/attacker-controlled `webhook_secret` — can POST a JSON body to `/webhooks` where:
- `repository.owner.login` (or `organization.login`) = `"attacker-org"` → causes `verify_signature` to fetch `attacker-org`'s app config and verify the HMAC using `attacker-org`'s own secret (which the attacker knows/controls), so `verified` is `true`.
- `repository.full_name` = `"victim-org/victim-repo"` → causes the dispatched handler to resolve and act on the victim's `Stack`.

This impacts several handlers with meaningful side effects on the victim stack:
- `StatusHandler#process` creates a CI status on any commit matching `params.sha` for whatever `Commit` records exist, regardless of stack ownership match with the verified org — this can forge a "success" status on a commit belonging to the victim's stack, potentially satisfying `required_statuses` used by `deployable?` / merge automation: [6](#0-5) 
- `PushHandler#process` triggers `stack.sync_github(expected_head_sha:)` for the victim stack found via `stacks` (which relies on `Handler#repository_name`), forcing a resync against attacker-chosen SHAs: [7](#0-6) 
- `CheckSuiteHandler#process` schedules check-run refreshes for arbitrary victim stack commits: [8](#0-7) 

### Impact Explanation
Forging a "success" `Commit` status via `StatusHandler` for a victim stack's commit can satisfy `Stack#required_statuses`/`Commit#deployable?`, which gates both manual deploy eligibility and continuous-deployment/merge-queue automation (`Stack#deployable?`, `MergeRequest#any_status_checks_missing?`/`#any_status_checks_failed?`). This can enable an unauthorized deploy or merge of a stack the attacker does not own or have write access to — this meets the "unauthorized deploy" Critical-impact criterion, since it is achieved purely by forging a webhook payload for an organization the attacker controls in a shared, multi-tenant Shipit deployment, without any Shipit session, API token, or GitHub write access to the victim repository.

### Likelihood Explanation
This requires (a) the target Shipit instance to be configured for multiple GitHub organizations (the `github_app_config`/per-org `webhook_secret` schema in `lib/shipit.rb`), and (b) the attacker to control at least one of the configured organizations (or otherwise know a valid `webhook_secret` for one). In a SaaS-like or shared-tenant Shipit deployment this is realistic — the whole point of per-org secrets is to let independent orgs register webhooks. The mismatch between the field used for secret selection and the field used for repository resolution is a straightforward oversight, not a theoretical edge case, and is easily reachable simply by crafting a JSON body without any additional access.

### Recommendation
After signature verification succeeds, re-derive (or explicitly validate) the target repository's owner against the organization that was actually used to verify the signature before dispatching to handlers — e.g., reject the webhook if `repository.full_name.split('/').first != repository_owner` (case-insensitively), or have `Handler` receive/require the verified organization and check it against `repository_name`'s owner segment before performing any lookups.

### Proof of Concept
1. Configure (or take over) a GitHub organization `attacker-org` in Shipit's multi-tenant `secrets.github` config, giving the attacker a valid `webhook_secret` for `attacker-org`.
2. Have a victim `Stack`/`Repository` `victim-org/victim-repo` already tracked by the same Shipit instance, with a real commit SHA `S` pending deploy and a required status context `ci/required`.
3. Compute a valid `X-Hub-Signature` HMAC using `attacker-org`'s `webhook_secret` over a crafted JSON body:
```json
{
  "sha": "S",
  "state": "success",
  "context": "ci/required",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
4. POST this body with header `X-Github-Event: status` and the computed `X-Hub-Signature` to `/webhooks`.
5. `verify_signature` resolves `Shipit.github(organization: "attacker-org")`, validates the signature successfully (attacker's own secret), and `StatusHandler` uses `params.sha`/`params.context` to create a `success` status on the victim's commit — satisfying `required_statuses` for a stack the attacker never had access to.

Note: I was unable to fully verify `Commit#create_status_from_github!` and downstream `deployable?`/continuous-deployment trigger code paths beyond what is cited here, so the exact automation trigger (immediate deploy vs. requiring a separate manual/CD trigger) could not be confirmed line-by-line within the available index; a Devin session with full repo access would be needed to trace `Commit#create_status_from_github!` and continuous-delivery trigger logic end-to-end.
