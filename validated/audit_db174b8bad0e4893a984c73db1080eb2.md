### Title
Webhook signature verification binds to `repository.owner.login`, but downstream handlers act on the independent `repository.full_name` field, allowing cross-repository writes - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/secret to validate the HMAC signature against using `repository_owner`, which is read from `params.dig('repository','owner','login')` (or `organization.login`). All webhook handlers, however, resolve which `Repository`/`Stack` to mutate using a *different* field of the same JSON body: `payload.dig('repository','full_name')`. These two fields are never cross-checked against each other, so the signature only proves "this body was signed by the secret belonging to organization X," not "this body's target repository belongs to organization X."

For the `push` event specifically, the handler uses that repository resolution to sync arbitrary stacks to an attacker-chosen `after` SHA: [5](#0-4) 

Because Shipit supports multiple GitHub App/organization configurations, each with its own `webhook_secret` (confirmed by `GithubApp#initialize(organization, config)` holding a per-instance `@webhook_secret` and `verify_webhook_signature`): [6](#0-5) [7](#0-6) 

an attacker who legitimately controls or registers *any* GitHub organization/App integration pointed at the shared Shipit instance holds a valid `webhook_secret` for that organization. They can then craft a raw JSON body where:
- `repository.owner.login` (and/or top-level `organization.login`) = the attacker's own organization (so `verify_signature` selects the attacker's own valid secret and the HMAC check passes), and
- `repository.full_name` = `"victim-org/victim-repo"` (an arbitrary, real target Stack's repository, which is public information on GitHub).

The equality the code is supposed to enforce — "the organization whose secret authenticated this webhook" == "the repository this webhook's actions are applied to" — is never checked. `verify_signature` authenticates the *sender's own org*, while `Handler#repository_name`/`PushHandler#process` blindly trust `repository.full_name` from the same attacker-controlled JSON body to select the `Stack` to sync.

### Impact Explanation
This lets an unprivileged external actor (who only needs their own GitHub org and its own Shipit-issued webhook secret — not any credential belonging to the victim) forge a signed `push` webhook that is verified as legitimate, yet whose payload target (`repository.full_name`) points at any other Stack configured in the instance. This forces `Stack#sync_github(expected_head_sha:)` to run against a victim stack with an attacker-chosen `after`/expected SHA. For stacks with continuous deployment/continuous delivery enabled, a forced sync to a chosen SHA can trigger an unintended/forced deploy pipeline run on a repository the attacker does not control, constituting an unauthorized deploy trigger across repository/organization trust boundaries. This matches the Critical bucket ("cross-repository writes, or an unauthorized deploy").

### Likelihood Explanation
Exploitation requires only: (1) the attacker's own GitHub organization/App to be a configured tenant of the shared Shipit instance (a normal, low-privilege setup step for any multi-tenant deployment, requiring no access to the victim's secrets, tokens, or GitHub org), and (2) knowledge of the victim's public repository `full_name`. No GitHub write access, no Shipit session, and no victim credentials are required — only the ability to send an HTTP POST with a validly-signed-for-attacker's-org payload whose `repository.full_name` differs from the signing organization.

### Recommendation
In `WebhooksController#verify_signature` (or in `Shipit::Webhooks::Handlers::Handler`), enforce that the organization/login used to select and verify the webhook secret is the same organization embedded in `repository.full_name` used to resolve the target `Repository`/`Stack`. Reject the webhook (422) if `repository.full_name.split('/').first` (or `organization.login`) does not match `repository_owner` for the same request.

### Proof of Concept
1. Attacker registers/controls GitHub org `attacker-org`, which is configured in Shipit as a tenant with webhook secret `S_attacker`.
2. Attacker crafts a `push` event JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "full_name": "victim-org/victim-repo",
    "owner": { "login": "attacker-org" }
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC(S_attacker, body)` and POSTs to `/github/webhooks`.
4. `verify_signature` calls `Shipit.github(organization: "attacker-org")` (from `repository.owner.login`), which succeeds because the signature matches `S_attacker`.
5. `PushHandler#process` resolves stacks via `Repository.from_github_repo_name("victim-org/victim-repo")` and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` on the victim's stack — a write/action on a repository outside the authenticated organization.

Note: I could not directly inspect `Shipit::Stack#sync_github` / continuous-deployment auto-trigger logic in this session (only confirmed its existence via grep matches in `app/models/shipit/stack.rb`), so the exact downstream consequence (forced deploy vs. sync-only) should be verified against that file before remediation.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
