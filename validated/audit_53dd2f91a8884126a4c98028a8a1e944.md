### Title
Reserve-ratio manipulation of AA bonding-curve/AMM balances via chained secondary-trigger calls within a single atomic primary-trigger execution - ([File: aa_composer.js])

### Summary
Autonomous Agents (AAs) that implement reserve/ratio-based pricing (e.g. bonding curves, AMMs) derive their exchange rate from the AA's own live on-chain balances (`balance[asset]`, `balance[base]`), explicitly excluding only the *current* trigger's own deposit. This mirrors the "reserve-derived livePrice" pattern in the DLMC report. In ocore, a single posted unit can drive a whole cascade of secondary AA-to-AA triggers that all execute atomically inside one database transaction (`BEGIN…COMMIT`) in `aa_composer.js`. Because the per-unit "one output per asset to an AA" restriction is enforced only for the primary trigger and not for secondary triggers, an attacker can route a chain of payments through helper AAs so that the *same* reserve-based AA is invoked multiple times within one atomic cascade, each call seeing the balance mutations left by the previous call — the same "buy, buy again with inflated reserve, then sell" sequence used in the DLMC exploit, but achieved without any flash loan, purely through ocore's secondary-trigger mechanics.

### Finding Description
`handlePrimaryAATrigger` wraps the entire chain of AA responses triggered by one unit in a single DB transaction: [1](#0-0) 
Balances used by formula evaluation (`balance[asset]`) are `objValidationState.assocBalances`, which are updated in place as each hop of the chain executes and are then visible to the *next* hop of the same cascade: [2](#0-1) 
`handleSecondaryTriggers` recursively invokes `handleTrigger` for every AA that receives an output from the just-produced response unit, with no restriction preventing the resulting chain from routing back into an AA address that already appears earlier in the same cascade: [3](#0-2) 
The only anti-replay/anti-multi-call restriction that exists applies solely to the **primary** trigger unit — it can send at most one output per asset to a given AA and no more than one primary trigger per unit — but this check is explicitly scoped to `count_primary_aa_triggers === 1`, i.e. it says nothing about secondary triggers occurring deeper in the cascade: [4](#0-3) 
A representative reserve-based AA (bundled as ocore's own documented pattern for AMM/bonding-curve AAs) computes its exchange rate purely from `balance[$asset]` / `balance[base]` minus the *current* trigger's own output, i.e. it trusts the AA's live balance as a price oracle: [5](#0-4) [6](#0-5) 
Because secondary triggers within one atomic cascade can loop back into this AA, an attacker-controlled routing AA can (1) deposit into the reserve AA, (2) forward the response to a helper AA that immediately re-triggers the same reserve AA a second time — now computing its ratio against the balance state left by step 1 — and (3) exit through a divest/exchange branch that pays out based on the manipulated ratio, exactly like DLMC's flash-swap "buy, buy again to inflate reserve, then sell against the inflated reserve" pattern, except here the atomicity is provided for free by ocore's secondary-trigger commit semantics (`aa_composer.js:91-101`, `1702-1757`) rather than by an EVM flash loan.

### Impact Explanation
Any AA implementing a reserve/ratio-derived price (bonding curves, AMMs, share-issuance schemes) is exposed to intra-cascade reserve manipulation, letting an attacker mint disproportionate shares or extract more of the reserve asset/bytes than deposited, in a single atomically-committed unit. This is a concrete AA fund-loss vector reachable by any unprivileged AA author/trigger sender who deploys or interacts with such an AA — the loss is borne by the reserve AA (and its other depositors), analogous to DLMC's ~$222k drain.

### Likelihood Explanation
Reachable purely through ordinary, unprivileged unit posting: the attacker needs only to control the trigger unit and one or more helper AA definitions, both of which are permissionless in ocore. No hub, witness, or privileged-node cooperation is required, and the entire chain executes deterministically and atomically as part of normal AA-response processing, so likelihood is high for any AA that follows the documented reserve-ratio pattern without additional reentrancy-style guards (e.g. locking/queuing repeat calls to itself within a single cascade, or basing the ratio on a value fixed at cascade start).

### Recommendation
- Introduce a per-cascade guard in `aa_composer.js`/`handleSecondaryTriggers` that detects and rejects (or serializes) re-entry into an AA address that has already produced a response earlier in the same primary-trigger cascade, unless the AA explicitly opts in.
- Extend the "one output per asset per AA" validation currently limited to primary triggers (`validation.js:1024-1037`) to also flag/limit secondary-trigger fan-in when it targets an AA address already visited in the current cascade.
- Document explicitly (beyond the current comment about fees causing "the price to move") that AA authors implementing reserve-based pricing must not trust `balance[asset]`/`balance[base]` as a manipulation-proof oracle within a single cascade, and provide a recommended pattern (e.g. snapshotting reserves at cascade start via `trigger.initial_unit`/`number_of_responses==0`) to defend against this class of bug.

### Proof of Concept
1. Deploy `ReserveAA` implementing the bundled bonding-curve pattern from `test/samples/uniswap_like_market_maker.oscript` (invest/divest/exchange branches keyed off `balance[$asset]`/`balance[base]`).
2. Deploy `HelperAA` that, upon receiving a payment from `ReserveAA`, immediately forwards funds back to `ReserveAA` with a second "invest"/"exchange" trigger payload.
3. Post a single unit from the attacker's address paying `ReserveAA` (primary trigger) an initial deposit that also nets a payout to `HelperAA`.
4. Within the same atomic cascade (`aa_composer.js:1702-1757`), `HelperAA`'s secondary trigger re-invokes `ReserveAA`, whose `balance[$asset]`/`balance[base]` now reflect the mutated state from step 3 (`aa_composer.js:543-586`), letting the attacker's second call mint/extract a disproportionate `mm_asset`/reserve amount relative to what was actually deposited.
5. A final message in the chain routes the inflated payout back to the attacker's own address, all committed in one `BEGIN…COMMIT` (`aa_composer.js:91-101`), with no on-chain check preventing the reserve AA from being invoked twice in one cascade.
