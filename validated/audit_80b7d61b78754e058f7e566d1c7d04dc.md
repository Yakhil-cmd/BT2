### Title
Cross-organization commit-status forgery leading to unauthorized continuous deployment - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects the HMAC secret to validate a `status` webhook by reading `repository.owner.login` (or `organization.login`) out of the **unverified** JSON body itself, then hands the entire parsed body to `Shipit::Webhooks::Handlers::StatusHandler`, which updates commit state using nothing but a bare `sha` lookup across the *whole* `commits` table, with no relation back to the organization/repository that was actually authenticated.

### Finding Description
`WebhooksController#verify_signature` picks which GitHub App/org config (and therefore which `webhook_secret`) to verify against using a field taken from the attacker-supplied payload: [1](#0-0) [2](#0-1) 

The signature is checked with `Shipit.github(organization: repository_owner).verify_webhook_signature(...)`, i.e. the org identity used to pick a valid HMAC key comes straight from `params.dig('repository','owner','login')`. If validation succeeds, the *entire* raw payload — not just the verified organization scope — is dispatched unmodified to every handler registered for the event: [3](#0-2) 

`StatusHandler#process` never re-derives or checks the repository/organization at all. It updates commit CI state purely by matching a raw `sha` against **every** commit row in the database, across every stack/repository the Shipit instance tracks: [4](#0-3) 

`Commit#create_status_from_github!` then folds this into the commit's aggregate `Status::Group`, which directly feeds `deployable?`: [5](#0-4) [6](#0-5) 

And `deployable?` gates automatic continuous delivery: [7](#0-6) 

**The broken binding**: the organization whose `webhook_secret` authenticated the request (`repository.owner.login`) is never checked against the repository/commit that the handler actually mutates (a global `sha` match with no stack/repository scoping). Any org onboarded to the same Shipit instance — i.e. any org for which the operator has configured a `webhook_secret` and whose GitHub App/webhook delivery the attacker can trigger (e.g. by pushing a commit status via their own repo's CI integration, or any actor with legitimate ability to fire a `status` event for *their own* org) — can forge a `status` payload whose top-level `repository.owner.login` is their own org (so the signature validates against their own known `webhook_secret`) while the `sha` field is copied from a commit belonging to a *completely different, unrelated stack* tracked by the same Shipit instance. Because `StatusHandler` performs `Commit.where(sha: params.sha)` with no repository filter, it will happily attach the forged CI status to the victim stack's commit.

### Impact Explanation
By forging a `success` status (or satisfying whatever `ci.require` statuses a victim stack demands) for a commit sha they do not own and could not otherwise produce genuine CI green states for, an attacker with only signing rights over their own unrelated organization's webhook traffic can flip `Commit#deployable?` to true on a victim stack. If that stack has `continuous_deployment` enabled, this directly triggers `ContinuousDeliveryJob`, producing an **unauthorized deploy** on the victim's stack — the concrete "unauthorized deploy" impact this scan is scoped to accept. This is a cross-organization write into another team's stack state, achieved purely by controlling one org's own webhook credentials.

### Likelihood Explanation
Exploitation requires only the ability to fire webhook events (with a known secret) for *any single organization* configured in the shared Shipit instance — a low bar in any multi-tenant/multi-org Shipit deployment, since `webhook_secret` is per-organization and unrelated to per-repository/per-stack access control. The victim `sha` is a public, guessable/observable value (from GitHub commit history), and the `StatusHandler` performs no cross-checks whatsoever between the authenticated org and the targeted commit's stack/repository, making the attack mechanically simple once webhook access to one org exists.

### Recommendation
In `WebhooksController`, resolve and pass the verified `repository_owner`/`organization` alongside the payload to handlers, and have `StatusHandler` (and similarly scoped handlers) filter `Commit` lookups by the stack's repository owner/name matching the *verified* organization, rejecting/ignoring statuses whose payload `repository.full_name` owner does not match the organization whose secret validated the signature.

### Proof of Concept
1. Shipit instance tracks two orgs, `attacker-org` (attacker has legitimate ability to send `status` webhooks for it, e.g. via their own CI system configured against their own GitHub App/webhook secret) and `victim-org/victim-repo` (an unrelated stack requiring `ci.require: [ci/tests]` for continuous deployment).
2. Attacker crafts a `status` event body:
```json
{
  "sha": "<victim-repo commit sha awaiting CI>",
  "state": "success",
  "context": "ci/tests",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "attacker-org/attacker-repo" }
}
```
3. Attacker signs this payload with `attacker-org`'s known `webhook_secret` and POSTs it to `/github/webhooks` with `X-Github-Event: status`.
4. `WebhooksController#verify_signature` resolves `repository_owner` = `"attacker-org"`, verifies successfully against `attacker-org`'s secret.
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)`, finds the victim commit (belonging to `victim-org/victim-repo`'s stack) purely by sha match, and calls `create_status_from_github!`, marking it `ci/tests: success`.
6. If the victim commit is now `deployable?` and the victim stack has `continuous_deployment` enabled, `ContinuousDeliveryJob` deploys it — an unauthorized deploy triggered entirely by an actor authenticated only for a different, unrelated organization.
