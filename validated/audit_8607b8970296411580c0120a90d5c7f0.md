### Title
`StatusHandler#process` writes GitHub statuses to any commit sharing a SHA, bypassing repository scoping - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits by bare `sha` across the entire `commits` table and calls `create_status_from_github!` on every match, without ever filtering by the repository that authenticated the webhook. Because `Handler` provides a `stacks` helper scoped to `Repository.from_github_repo_name(repository_name)` for exactly this purpose, but `StatusHandler` doesn't use it, any repository whose webhook signature validates can inject a `Status` row (and via `Commit#add_status` trigger `stack.schedule_merges`) onto a commit belonging to a completely different stack/repository that happens to share the same SHA.

### Finding Description
The broken binding: the invariant that should hold is `status.stack_id == commit.stack_id_that_authenticated_the_webhook`, i.e. a status for context `ci/test` should only ever attach to commits owned by the repository whose HMAC signature was verified for that request. Instead the actual code enforces `status ∈ Commit.where(sha: params.sha)`, with no repository/stack filter at all: [1](#0-0) 

Compare this with the `stacks` helper defined on the base `Handler` class, which every well-behaved handler is expected to use to scope its writes to the authenticated repository: [2](#0-1) 

`StatusHandler` never calls `stacks`; it queries `Commit` directly by `sha` only. The webhook controller only verifies that the signature matches for the `repository_owner` derived from the *attacker's own payload* — it never re-checks that the commits being mutated actually belong to that repository: [3](#0-2) 

`Commit#create_status_from_github!` then creates a `Status` scoped to `commit.stack_id` (the *victim's* stack, not the attacker's), and `add_status` reloads the commit's aggregate `status` and, on a state transition, calls `stack.schedule_merges`: [4](#0-3) 

`Commit` delegates `blocking_statuses` and `required_statuses` to `stack`, meaning the victim stack's `blocking_statuses`/`required_statuses` deploy-spec configuration governs whether this injected status flips `blocked?`/ship eligibility for the victim's commit: [5](#0-4) 

**Exploit flow:** An attacker who owns/controls any GitHub repository wired into this Shipit instance (an unprivileged, arbitrary organization member per the rules) can push a commit whose SHA is contrived/known to collide with a SHA already present in a victim's tracked repo (e.g., via a rebase/cherry-pick that reproduces an identical tree+parent+timestamp, or more realistically by simply reusing/predicting a SHA a victim stack is tracking), then have GitHub deliver (or directly POST, replaying a legitimately-signed status payload from their own repo) a `status` event with `context: ci/test`, `sha: <victim_sha>`, `state: success`. `WebhooksController#verify_signature` validates the signature against the attacker's own organization/app credentials — this succeeds because it is a real, attacker-controlled webhook. `StatusHandler#process` then finds `Commit.where(sha: victim_sha)`, which returns the victim's `Commit` row (with `stack_id` pointing to the victim's stack), and writes a `Status` under the victim stack's id. If the victim stack has `blocking_statuses`/`required_statuses` including `ci/test`, this either satisfies the requirement (unblocking a ship) or, with `state: failure`, blocks it — cross-tenant with no involvement of the victim's own CI.

Existing guards do not stop this: `verify_signature` only proves the payload came from *some* legitimate GitHub organization/app, not that its content only affects that organization's own resources; `ExplicitParameters` (`params do ... end`) only validates types/shape, not repository ownership; there is no `require_permission!` or stack-membership check in this handler at all.

### Impact Explanation
A payload correctly authenticated for one repository writes a `Status` record onto a `Commit` belonging to a different repository/stack, directly matching the "Critical" category: "a payload for one repository mutating another's stack, commit, task or team." Concretely, this can force `blocked?`/deploy-gating state for a victim stack that has `blocking_statuses` configured, causing an unauthorized ship (status forced to success/required context satisfied) or an unauthorized block/DoS-of-deploys (status forced to failure) on a stack the attacker does not own. This is repeatable against any stack for any SHA collision the attacker can arrange, and the blast radius spans every tenant/repository sharing the Shipit instance.

### Likelihood Explanation
The main precondition is a SHA collision or foreknowledge between attacker-controlled and victim commits — this is the practical bottleneck (SHA-1 collision is not trivial, but predictable/duplicated commits — e.g. identical cherry-picked commits, forks of the same upstream, or bots that create identical bump commits across repos — make exact SHA matches realistic in practice without cryptographic collision). No Shipit secrets, sessions, or elevated GitHub permissions are required beyond controlling one's own repository's webhook delivery, which the threat model explicitly grants to an unprivileged attacker. The victim only needs `blocking_statuses`/`required_statuses` configured in its `.shipit.yml`/deploy spec (a common configuration) for the impact (blocked?/ship gating) to be observable; even without it, the attacker still writes cross-tenant data (a `Status` row) into a repository they don't own, which alone is a state-manipulation issue.

### Recommendation
Scope `StatusHandler#process` to the authenticated repository, mirroring the `stacks` helper pattern used elsewhere: restrict the `Commit` lookup to `stacks.flat_map(&:commits)` (or `Commit.where(sha: params.sha, stack_id: stacks.select(:id))`) instead of an unscoped `Commit.where(sha: params.sha)`, so that a status can only ever be attributed to commits belonging to stacks of the repository that authenticated the webhook.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb (conceptual)
test "status webhook does not write statuses to commits of unrelated repositories" do
  victim_stack = shipit_stacks(:shipit) # repository "shopify/shipit-engine"
  victim_commit = shipit_commits(:first)
  victim_commit.update!(sha: "deadbeef" * 5)

  attacker_repo = shipit_repositories(:cyclimse) # different repo, e.g. "walrus/attacker-repo"
  attacker_stack = shipit_stacks(:cyclimse) # belongs to attacker_repo, no relation to victim_stack

  payload = {
    'sha' => victim_commit.sha,
    'state' => 'success',
    'context' => 'ci/test',
    'repository' => { 'full_name' => attacker_repo.github_repo_name } # this is what authenticated the webhook
  }

  # Binding under test (should hold, currently broken):
  #   status.stack_id == Repository.from_github_repo_name(payload['repository']['full_name']).stacks.pluck(:id)
  # i.e. any Status created from this payload must belong to attacker_stack, never victim_stack.

  assert_no_difference -> { victim_commit.statuses.count } do
    Shipit::Webhooks::Handlers::StatusHandler.call(payload)
  end
end
```
Currently this assertion fails: `victim_commit.statuses.count` increases by 1 because `StatusHandler#process` matches `Commit.where(sha: params.sha)` irrespective of `payload['repository']`, proving the cross-repository write.
