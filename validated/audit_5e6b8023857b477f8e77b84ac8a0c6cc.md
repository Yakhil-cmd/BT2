### Title
Any caller can prime the shared oracle cache with a stale-but-valid price feed that determines liquidation outcomes for unrelated borrowers - (File: `mainnet/contracts/market/v0-4-market.clar`)

### Summary
The hot-path functions `borrow`, `collateral-add`, `collateral-remove`, and `liquidate` accept a caller-supplied, optional `price-feeds` parameter that is written into globally-shared oracle state (`pyth-storage-v4` plus the market's `last-update` map) before any position math is performed. Whichever caller happens to submit a feed first "primes" this shared cache for every other participant whose subsequent transaction relies on the default (cached) price rather than submitting a fresher one, similar to how the reported Uniswap wallet issue let a remote, unconfirmed data source silently determine values a user relies on without their explicit re-validation.

### Finding Description
`write-feeds`/`write-feed` push a raw signed Pyth VAA (`buff 8192`) into `pyth-storage-v4` via `verify-and-update-price-feeds`, and `price-resolve` subsequently reads whatever is currently stored there through `call-pyth`/`resolve-pyth`, gating it only with: [1](#0-0) 
This freshness check only requires the submitted price's timestamp to be `>= prev` and within `max-staleness` of the current block time — it does not require the price to be the most recent one available. `price-resolve` then unconditionally updates the shared `last-update` map with that timestamp: [2](#0-1) 

Crucially, `price-feeds` is entirely optional and caller-controlled in every hot path: [3](#0-2) [4](#0-3) 

Because `pyth-storage-v4` and the market's `last-update`/oracle timestamp map are global, singleton state — not scoped per caller or per position — whichever transaction is first to submit a `price-feeds` update in a block "primes" the effective price basis for every other market participant's operation that runs afterward without also submitting a fresher feed (the common case, since `price-feeds` normally defaults to `none`). This is directly analogous to the reported bug class: data that is fetched/written by one interaction (the remote-signed VAA a caller chooses to submit) silently determines what gets evaluated for someone else's transaction (an unrelated borrower's health check or liquidation), without that other party's confirmation or control over which specific valid, signed price gets used.

### Impact Explanation
An attacker acting as liquidator can, ahead of calling `liquidate` on a victim's borderline-healthy position, submit any Pyth VAA that is validly signed and within `max-staleness`/confidence bounds but is *not* the newest available update (e.g., an older, less favorable-to-the-victim price still inside the staleness window). Because `oracle-timestamp-fresh` only enforces monotonicity and a staleness ceiling — not "latest" — this stale price becomes the shared basis (`last-update`, `pyth-storage-v4`) used by `price-resolve`/`get-notional-evaluation` for the victim's health computation in `liquidate`, potentially pushing an otherwise-healthy position over `ltv-liq-partial` and enabling the attacker to seize the victim's collateral plus liquidation penalty (`liq-penalty-min`/`liq-penalty-max`) that a truly current price would not have justified. This is theft of the victim's collateral at rest — a Critical impact — effected purely through manipulation of shared oracle-cache state that this contract itself writes and trusts, not through any external oracle compromise.

### Likelihood Explanation
Likelihood is constrained by the requirement that the attacker supply a legitimately Pyth-signed VAA (cannot fabricate prices), and by the confidence-ratio (`check-confidence`) and staleness bound (`max-staleness`) checks. However, because any historically valid signed update within the staleness window qualifies, and Pyth naturally publishes many updates per staleness window, an attacker has a nontrivial window of legitimate, signed price snapshots to choose from that could disadvantage a specific victim — no special privilege or DAO compromise is needed, only normal `liquidate`/`borrow` access with an attacker-chosen (but genuine) `price-feeds` argument.

### Recommendation
- Require `price-resolve` to reject any submitted or cached price whose `publish-time` is older than the most recently seen valid timestamp for that identifier by more than a very small tolerance, rather than accepting anything within a longer `max-staleness` window that is also `>= prev` — i.e., enforce "must be the newest available," not merely "not older than what we already have."
- Consider disallowing third-party `price-feeds` submissions from mutating global oracle state on behalf of protected operations (e.g., only allow the position owner, or require the freshest on-chain Pyth price already stored by `pyth-storage-v4`'s own internal timestamp guard, rather than trusting whatever VAA a liquidator chooses to submit).
- Add monitoring/alerting when a `price-feeds`-triggered update deviates significantly from the previously cached price or from off-chain reference feeds, and consider a short cooldown/grace window after any in-band price update before that price can be used to trigger liquidations against other users' positions.

### Proof of Concept
1. Pyth publishes signed price updates for BTC/STX/USDC at times T1 < T2 < T3, all within the protocol's `max-staleness` window, with T3 being materially less favorable to Borrower B's collateral valuation than T1/T2 (e.g., BTC price at T1 is higher than at T3).
2. Borrower B's position is healthy under the true, current (T3) price.
3. Attacker calls `liquidate(borrower: B, ..., price-feeds: (some (list <VAA-for-T1-or-T2>)))`. The submitted VAA is genuinely Pyth-signed, so `write-feed`/`verify-and-update-price-feeds` succeeds and stores this older price into `pyth-storage-v4`.
4. `price-resolve` for B's collateral/debt reads this now-cached, staler price via `call-pyth`/`resolve-pyth`; `oracle-timestamp-fresh` passes because `T1 >= prev` and `(stacks-block-time - T1) <= max-staleness`.
5. B's `current-ltv` computed against this attacker-chosen, valid-but-stale price crosses `ltv-liq-partial`, and `liquidate` proceeds: attacker repays debt and receives B's collateral plus liquidation penalty, even though B's position was healthy under the true current price.

(define-private (price-resolve
  (data { type: (buff 1), ident: (buff 32), callcode: (optional (buff 1)), max-staleness: uint }))
  (let ((type (get type data))
        (ident (get ident data))
        (key { type: type, ident: ident })
        (resolution (try! (resolve-price-feed type ident)))
        (price (get value resolution))
        (callcode (get callcode data))
        (final-price (try! (resolve-callcode price callcode)))
        (last-update-time (oracle-last-update key))
        (timestamp (get timestamp resolution))
        (max-staleness (get max-staleness data)))

    ;; validate price and timestamp using max-staleness from oracle data
    (asserts! (and (oracle-price-legal final-price) (oracle-timestamp-fresh timestamp last-update-time max-staleness))
              ERR-ORACLE-INVARIANT)

    ;; update timestamp if newer
    (if (> timestamp last-update-time)
        (map-set last-update key timestamp)
        false)

    (ok final-price)))
