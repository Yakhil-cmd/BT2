### Title
Cross-repository CI status forgery via unscoped `Commit.where(sha:)` lookup in `StatusHandler` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
The `StatusHandler` webhook handler resolves target commits by SHA alone, with no binding to the repository the `status` webhook event claims to originate from. Combined with the fact that webhook signature verification in `WebhooksController` selects which organization's `webhook_secret` to validate against based on an attacker-supplied JSON field (`repository.owner.login`), an actor who legitimately controls (or has leaked) the webhook secret for *any one* GitHub organization/App configured in a multi-org Shipit deployment can forge a signed `status` event whose `sha` belongs to a commit tracked under a *completely different* repository/stack, and have Shipit write a fabricated CI status for it.

### Finding Description
`WebhooksController#verify_signature` determines which `GitHub::App` (and therefore which `webhook_secret`) to use for HMAC verification purely from a field inside the untrusted JSON payload: [1](#0-0) [2](#0-1) 

This binds "which organization is authenticated" to `repository.owner.login`/`organization.login` in the body. Once the signature check passes (i.e., the request was legitimately signed with *some* configured org's secret), the raw params are handed unmodified to the registered handler: [3](#0-2) 

For the `status` event, `Shipit::Webhooks::Handlers::StatusHandler#process` never checks `repository.full_name`/`repository.owner` at all — it looks up commits by SHA across the entire `commits` table, unscoped to any stack or repository: [4](#0-3) 

Contrast this with `PushHandler`, which correctly scopes to `stacks` derived from `payload.dig('repository', 'full_name')` via the base `Handler` class: [5](#0-4) [6](#0-5) 

`StatusHandler` does not use `stacks`/`repository_name` at all, breaking the equality that the report's rule set calls out: *"an organization that authenticated versus the repository that is written."* Here, the organization/App whose secret validated the signature (Org B, which the attacker controls or knows the secret for) is decoupled from the repository/commit that actually gets mutated (Org A's tracked commit, matched purely by SHA).

### Impact Explanation
An attacker who is a legitimate administrator of, or otherwise possesses the `webhook_secret` for, any single GitHub organization/App configured in a multi-org Shipit instance can:
1. Craft a `status` webhook JSON body with `repository.owner.login` set to their own org (so `verify_signature` selects their own known secret and the HMAC check passes) and `sha`/`state`/`context` set to target a commit SHA that belongs to a different tracked repository/stack.
2. POST this to `/webhooks` with a valid `X-Hub-Signature` computed using their own org's secret.
3. `StatusHandler#process` finds `Commit.where(sha: params.sha)` (matching regardless of repository) and calls `commit.create_status_from_github!(params)`, injecting an attacker-chosen status (e.g., `state: "success"`, `context: "ci/required-check"`) onto a commit in an unrelated stack they have no authorization over.

Because Shipit stacks use commit statuses to gate `ci.require`/continuous-deployment eligibility, this can satisfy required-CI-check gating for a stack the attacker does not control, contributing to an unauthorized deploy path. This aligns with the report's Impact category of an "unauthorized deploy" via a broken repository/organization-trust binding.

Note: I was not able to fully trace, within the remaining tool budget, how `Stack`/`Commit`/`Status::Group` aggregate individual `Status` rows into deploy-readiness decisions (e.g., whether forged statuses alone are sufficient to flip `commit.success?`/`stack.deployable?` given required contexts) — this final linkage from "forged Status row exists" to "an actual deploy is triggered/permitted" should be confirmed with a concrete PoC before treating this as fully proven end-to-end; the missing repository-scoping in `StatusHandler` itself, however, is a clear defect I can support with a direct code citation.

### Likelihood Explanation
Requires the Shipit instance to be configured for multiple GitHub organizations/Apps (as documented and supported by `config/secrets.development.shopify.yml` and `lib/shipit/github_app.rb`), and requires the attacker to control a legitimate webhook secret for one of them — plausible for an org that self-services their own GitHub App registration in a shared Shipit deployment, or where any one org's `webhook_secret` has leaked. This is analogous in spirit to the original finding: a narrow, believable precondition that nonetheless breaks a documented trust boundary "core functionality" of the webhook signature scheme.

### Recommendation
In `StatusHandler#process` (and any other handler that doesn't already do so), scope the `Commit` lookup to the repository indicated by the payload (using the same `stacks`/`repository_name` binding as `PushHandler`), e.g. restrict to commits belonging to `stacks.map(&:commits)` or add an explicit repository check before calling `create_status_from_github!`. Additionally, consider deriving the webhook-secret-selection key from a source that cannot diverge from the payload fields consumed by handlers (or cross-validate that `repository.owner.login` and `repository.full_name`'s owner segment match) so that "organization authenticated" and "repository/commit written" cannot be pulled from independently-attacker-controlled JSON paths.

### Proof of Concept
1. Configure Shipit with two orgs, `attacker-org` and `victim-org`, each with distinct `webhook_secret`s (per `docs/setup.md` multi-org config).
2. Note a commit SHA `S` known to belong to a stack tracked under `victim-org/some-repo` (e.g., discoverable via the Shipit UI/API if the attacker has any read access, or a well-known public commit SHA if `victim-org`'s repo is public but Shipit access is otherwise restricted).
3. Build a JSON body:
```json
{
  "sha": "S",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "attacker-org/irrelevant-repo" }
}
```
4. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(attacker-org's webhook_secret, raw_body)>`.
5. `POST /webhooks` with header `X-Github-Event: status` and the above body/signature.
6. `WebhooksController#verify_signature` resolves `repository_owner` = `"attacker-org"`, fetches `attacker-org`'s `GitHub::App`, and the signature verifies successfully (attacker used their own real secret).
7. `StatusHandler#process` executes `Commit.where(sha: "S")` — finds and updates the commit that actually belongs to `victim-org`'s stack, calling `create_status_from_github!` and writing a forged CI status onto it, entirely outside `attacker-org`'s authorization scope.
