## Title
Webhook signature verification selects the GitHub organization from an unauthenticated payload field while handlers act on a different, attacker-chosen repository/commit — enabling cross-organization forged CI status and unauthorized deploys - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks which GitHub App's `webhook_secret` to HMAC-verify against using `repository_owner`, a value read straight out of the untrusted JSON body (`repository.owner.login`, falling back to `organization.login`). The handlers that subsequently execute against the *same* payload identify the target repository/commit independently, via `repository.full_name` (in most handlers) or, in the `StatusHandler`, via a completely unscoped `sha` lookup across all repositories. Because the field used for authentication (`repository_owner`) is never cross-checked against the field(s) used to select what gets written, an attacker who legitimately administers **any** GitHub organization configured in Shipit's multi-org `secrets.yml` can sign a payload with their own known `webhook_secret`, while making the payload's `repository`/`sha` target a completely different organization's repository/commit that they have no access to.

### Finding Description
In the multi-org configuration (documented in `docs/setup.md`, "Using Multiple Github Applications"), `Shipit.github` resolves a per-organization webhook secret from `repository_owner`: [1](#0-0) 

`WebhooksController#verify_signature` derives that organization from the raw JSON body — a field fully controlled by the request sender, not authenticated by anything at this point in the flow: [2](#0-1) 

Once the signature is accepted (because it was computed correctly against *that org's* secret — the org the attacker legitimately administers), `create` dispatches the entire attacker-controlled payload to handlers: [3](#0-2) 

Most handlers resolve their target via `payload.dig('repository', 'full_name')`, a value never compared to `repository_owner`: [4](#0-3) 

`StatusHandler`, used to record third-party CI statuses on commits, is worse still — it looks up commits **by `sha` alone, with no repository scoping whatsoever**, then writes a status onto whatever commit(s) match that sha in the entire database: [5](#0-4) 

This breaks the trust binding "the organization whose secret authenticated this request == the repository (and commits) the request is permitted to mutate." An attacker who is the legitimate GitHub App admin of `orgB` (registered in Shipit's multi-org secrets) knows `orgB`'s `webhook_secret` (they generated it when creating their own GitHub App). They can:
1. Craft a `status` event payload with `sha` = the head SHA of a commit in a **victim** stack owned by `orgA` (a repository/org they do not control), `state` = `success`, and `repository.owner.login` = `orgB`.
2. Sign the raw body with `orgB`'s `webhook_secret` and send it to `/webhooks`.
3. `verify_signature` resolves `repository_owner` = `orgB`, fetches `orgB`'s `GitHubApp`, and successfully verifies the signature (it was legitimately signed by that secret).
4. `StatusHandler#process` finds the commit by `sha` regardless of which repository/org it belongs to, and calls `commit.create_status_from_github!(params)`, forging a "success" CI status on a commit belonging to `orgA`'s stack.

Since `Commit#deployable?` is satisfied by a passing status (`#deployable? is true if commit status is 'success'` — [6](#0-5) ), and continuous delivery deploys the next deployable commit automatically once `deployable?` is true (`#trigger_continuous_delivery trigger a deploy if all conditions are met` — [7](#0-6) ), the forged status can cause Shipit to automatically ship a commit in a repository the attacker never had write or deploy access to.

The same organization/repository mismatch also lets the attacker forge `push` events for `orgA`'s repositories (spoofing `after` SHAs into `GithubSyncJob`) via `PushHandler`, since it only checks `payload.dig('repository','full_name')`, never the authenticating org: [8](#0-7) 

### Impact Explanation
This crosses the "organization that authenticated versus the repository that is written" trust boundary. The concrete outcome is an **unauthorized deploy**: an attacker with no access to `orgA`/its repositories — but with legitimate access to a *different*, unrelated org onboarded to the same Shipit instance — can forge a passing CI status on any commit sha in `orgA`'s repositories, causing Shipit's continuous delivery to automatically deploy that commit. This matches the "unauthorized deploy" Critical-tier impact.

### Likelihood Explanation
This requires only that the Shipit instance is configured with the documented multi-organization GitHub App setup (an explicitly supported, first-class configuration path in `docs/setup.md`), and that the attacker administers any one of the configured orgs (a low, "unprivileged relative to the victim org" bar). No repository write access, no Shipit session, and no leaked secrets from the victim org are required — only the attacker's own legitimately-known webhook secret.

### Recommendation
Do not use an attacker-controlled payload field to select the verification secret and then trust a different, independently-controlled payload field to select what gets mutated. Concretely:
- After verifying the signature for `repository_owner`'s app, re-validate that `payload.dig('repository','full_name')` (and, for `StatusHandler`, the repository owning the `sha`) actually belongs to that same verified organization before dispatching to handlers.
- Scope `StatusHandler#process`'s `Commit.where(sha: params.sha)` lookup to commits whose stack's repository matches the verified organization/repository, instead of matching by `sha` globally.

### Proof of Concept
1. Configure Shipit with two orgs, `orgA` (contains the victim stack/repository) and `orgB` (attacker administers this org's GitHub App and therefore knows its `webhook_secret`).
2. Attacker builds a `status` webhook JSON body:
   ```json
   {
     "sha": "<victim commit sha in orgA/repo>",
     "state": "success",
     "context": "ci/forged",
     "repository": { "owner": { "login": "orgB" }, "full_name": "orgB/irrelevant-repo" }
   }
   ```
3. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(orgB_webhook_secret, body)`.
4. `POST /webhooks` with header `X-Github-Event: status` and the above body/signature.
5. `WebhooksController#verify_signature` resolves `repository_owner` = `orgB`, loads `orgB`'s `GitHubApp`, and the signature verifies successfully.
6. `Shipit::Webhooks.for_event('status')` dispatches to `StatusHandler`, which runs `Commit.where(sha: params.sha)` — matching the victim commit in `orgA`'s repository — and calls `create_status_from_github!`, marking it `success`.
7. If `orgA`'s stack has continuous delivery enabled and this was the next undeployed commit, Shipit automatically deploys it, without the attacker ever having any access to `orgA`.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping
      head(:ok) if event == 'ping'
    end

    def event
      request.headers.fetch('X-Github-Event')
    end

    def repository_owner
      # Fallback to the organization sub-object if repository isn't included in the payload
      params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
    end

# frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
    end
  end
end
