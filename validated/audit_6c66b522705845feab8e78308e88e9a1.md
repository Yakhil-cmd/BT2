### Title
Unauthenticated cross-tenant subscription to `/events` stack/task/commit streams via unauthorized `Pubsubstub::StreamAction` mount - (File: config/routes.rb, app/controllers/concerns/shipit/authentication.rb)

### Summary
`Pubsubstub::StreamAction` is mounted directly as a Rack endpoint at `/events` in `config/routes.rb`, bypassing every Shipit controller and therefore the `force_github_authentication`/`current_user.authorized?` check that `Shipit::Authentication` installs as a `before_action` on `Shipit::ShipitController`-derived controllers. Because the channel names (`"stack.#{id}"`, `"repository.#{id}"`) are predictable, low-privilege or entirely unauthenticated requests can subscribe to any stack's live event stream by numeric id, with no authorization check at all.

### Finding Description
The intended binding is: *the set of stacks a caller is authorized to view (enforced via `current_user.authorized?` in `Shipit::Authentication#force_github_authentication`, applied to `Shipit::ShipitController` subclasses)* == *the set of channels the caller may subscribe to at `/events`*.

In practice:
- `config/routes.rb` line 9: `mount Pubsubstub::StreamAction.new, at: "/events", as: :events` mounts a plain Rack app, not a `Shipit::ShipitController` action. [1](#0-0) 
- All authorization/authentication in this engine is implemented as a controller `before_action` (`force_github_authentication`), included via `Shipit::Authentication` into `Shipit::ShipitController`: [2](#0-1) [3](#0-2) 
- Because `Pubsubstub::StreamAction` is a separately mounted Rack endpoint, it never runs through `Shipit::ShipitController`'s filter chain, so `force_github_authentication` and `current_user.authorized?` never execute for requests to `/events`. There is no other global authorization middleware registered in `lib/shipit/engine.rb` that would cover this path (only `OmniAuth::Builder` and an optional `SameSiteCookieMiddleware` are inserted, neither of which perform authorization). [4](#0-3) 
- The channel naming convention is exposed in the stack view: `subscribe events_path(channels: ["stack.#{@stack.id}"]), ...` in `app/views/shipit/stacks/show.html.erb`, confirming the predictable `stack.<id>` scheme, but knowledge of the view is not even required since ids are sequential integers.

Exploit flow: an attacker with no Shipit session, no API token, and no team membership sends `GET /events?channels[]=stack.<id>` (or `repository.<id>`) directly to the Shipit host for any guessed/enumerated numeric id and receives the live SSE/long-poll event stream for that stack's deploys/tasks/commits, regardless of whether they belong to any authorized org/team.

None of the existing guards apply: `force_github_authentication`, `User#authorized?`, and the `stacks` scoping used elsewhere are all controller-level filters on `Shipit::ShipitController` subclasses and are never invoked for the separately mounted `/events` Rack app.

### Impact Explanation
An unauthenticated (or unprivileged) attacker can read live stack/task/deploy/commit event streams for any stack in the Shipit instance by guessing/enumerating small sequential integer ids, with no dependency on GitHub team membership, session, or API token. This is a full unauthenticated read of stack state and task/deploy output across all tenants of the instance, matching the "High – unauthenticated read of stack state, task streams or deploy output" impact category. It is trivially repeatable against every stack/repository id on the instance (id enumeration), giving full blast radius across all tenants hosted by the Shipit deployment.

### Likelihood Explanation
No special configuration is required beyond the default engine mount present in every Shipit installation (`config/routes.rb`). No secrets, tokens, or team membership are needed — the attacker only needs network access to the Shipit host and to guess/enumerate small integer stack/repository ids, which are standard AR auto-increment primary keys. This makes the attack low-cost, fully repeatable, and requires no interaction with GitHub webhooks or any privileged credential.

### Recommendation
Do not mount `Pubsubstub::StreamAction` as an unauthenticated Rack app. Instead, wrap it behind a Shipit controller action (or middleware applied specifically to the `/events` path) that: (1) requires `force_github_authentication`/team authorization identical to `Shipit::ShipitController`, and (2) validates that the requested `channels[]` values correspond to a `Stack`/`Repository` the authenticated user is actually authorized to view (e.g., resolve `stack.<id>` to a `Stack` record and re-run the same authorization check used by `StacksController#show`) before allowing the subscription to be established.

### Proof of Concept
```ruby
# test/controllers/events_authorization_test.rb
require "test_helper"

module Shipit
  class EventsAuthorizationTest < ActionDispatch::IntegrationTest
    test "/events subscription is rejected for a stack the caller is not authorized to view" do
      # Arrange: an org/team-restricted stack exists, and no Shipit session is established
      stack = shipit_stacks(:shipit)
      # binding under test: authorized_stack_ids(current_user) == subscribable_channel_ids
      refute session[:user_id], "attacker holds no Shipit session"

      # Act: attacker subscribes directly to the predictable channel name
      get shipit.events_path(channels: ["stack.#{stack.id}"])

      # Assert: request must be rejected/unauthorized, mirroring StacksController#show behavior
      assert_response :unauthorized # or :forbidden / :redirect to github_authentication_path
    end

    test "an authorized controller action enforces force_github_authentication but /events does not" do
      # Demonstrates the divergence: StacksController#show requires authentication...
      get shipit.stack_path(id: shipit_stacks(:shipit).to_param)
      assert_redirected_to shipit.github_authentication_path(origin: request.original_url)

      # ...while /events, mounted as a bare Rack app, applies no equivalent before_action.
      get shipit.events_path(channels: ["stack.#{shipit_stacks(:shipit).id}"])
      assert_response :success # currently succeeds with no auth check — the vulnerability
    end
  end
end
```

      before_action :force_github_authentication
      helper_method :current_user
    end

    module ClassMethods
      def skip_authentication(*args)
        skip_before_action(:force_github_authentication, *args)
      end
    end

    private

    def force_github_authentication
      if current_user.logged_in? && current_user.requires_fresh_login?
        Rails.logger.warn("User #{current_user.id} requires a fresh login, logging out...")
        reset_session
        redirect_to(Shipit::Engine.routes.url_helpers.github_authentication_path(origin: request.original_url))
      elsif Shipit.authentication_disabled? || current_user.logged_in?
        unless current_user.authorized?
          team_handles = Shipit.github_teams.map(&:handle)
          team_list = team_handles.to_sentence(two_words_connector: ' or ', last_word_connector: ', or ')
          render(plain: "You must be a member of #{team_list} to access this application.", status: :forbidden)
        end
      else
        redirect_to(Shipit::Engine.routes.url_helpers.github_authentication_path(origin: request.original_url))
      end
    end
