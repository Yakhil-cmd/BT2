### Title
Malicious Bridge Operator Can Permanently Block Value Transfers by Repeatedly Changing Vote — (`contracts/service_chain/bridge/BridgeOperator.sol`)

---

### Summary

`BridgeOperator._voteCommon` allows any registered operator to change their vote for a given nonce at any time by calling the handle function again with different parameters. Each re-vote decrements the old `voteCounts` entry and increments a new one. A malicious operator whose vote is required to reach the threshold can exploit this to permanently prevent `voteCounts[voteKey_correct]` from ever reaching `operatorThresholds`, blocking the bridge value transfer indefinitely.

---

### Finding Description

`_voteCommon` in `BridgeOperator.sol` implements vote amendment as follows:

```solidity
// If the same voter voted again, revoke previous vote.
bytes32 oldVoteKeyOfVoter = vote.voted[msg.sender];
if (oldVoteKeyOfVoter == bytes32(0)) {
    vote.voters.push(msg.sender);
} else {
    vote.voteCounts[oldVoteKeyOfVoter]--;   // ← decrement old key
}
vote.voted[msg.sender] = _voteKey;
...
vote.voteCounts[_voteKey]++;
if (vote.voteCounts[_voteKey] >= operatorThresholds[uint8(_voteType)]) {
    return true;
}
```

The `voteKey` is `keccak256(msg.data)`, which encodes the full calldata including `_to`, `_value`, `_requestTxHash`, etc. A malicious operator can therefore call `handleKLAYTransfer` (or `handleERC20Transfer`) for the same `_requestedNonce` but with different parameters (e.g., a different `_to` address), which:

1. Decrements `voteCounts[voteKey_correct]` — the count for the legitimate transfer parameters.
2. Increments `voteCounts[voteKey_attacker]` — a count for a different, invalid set of parameters.

This is structurally identical to the M-02 pattern: a protected counter (`voteCounts[voteKey_correct]`) is reduced by the attacker just before the honest operator's deciding vote would push it to the threshold, causing the threshold check to fail.

The attack does not require frontrunning in the traditional sense. Because the malicious operator controls their own vote, they can simply re-vote with different parameters in any block after an honest operator has voted, resetting the count back below the threshold. The honest operators cannot prevent this because there is no lock on an operator's vote once cast.

The `closedValueTransferVotes[_requestNonce]` guard only prevents re-execution after the vote is already closed; it provides no protection while the vote is still open.

The code comment in `deregisterOperator` acknowledges a related vote-persistence edge case but does not address the re-voting attack vector.

---

### Impact Explanation

In any bridge configuration where the number of honest operators is strictly less than `operatorThresholds[ValueTransfer]` — i.e., the malicious operator's vote is required to reach the threshold — the malicious operator can permanently prevent `closedValueTransferVotes[nonce]` from ever being set to `true`. The corresponding `handleKLAYTransfer` or `handleERC20Transfer` call never executes, so:

- KLAY locked in the source-chain bridge contract is never released to `_to` on the destination chain.
- ERC20/ERC721 tokens are never minted or transferred to the recipient.

The bridged assets are permanently frozen. This is a direct unauthorized denial of bridged-asset settlement.

---

### Likelihood Explanation

The precondition is a single malicious operator in a configuration where `(total operators) - (malicious operators) < threshold`. Common deployments use threshold = N (all operators must agree) or threshold = N (majority), making this reachable with one compromised or malicious operator node. Service-chain operators are semi-trusted infrastructure nodes, not cryptographically enforced honest parties. No external service compromise or majority collusion is required.

---

### Recommendation

Once an operator has cast a vote for a given `(voteType, nonce)`, disallow changing that vote. Replace the amendment logic with a strict "vote once" guard:

```solidity
// In _voteCommon, replace the amendment block with:
require(vote.voted[msg.sender] == bytes32(0), "already voted");
vote.voters.push(msg.sender);
vote.voted[msg.sender] = _voteKey;
vote.voteCounts[_voteKey]++;
if (vote.voteCounts[_voteKey] >= operatorThresholds[uint8(_voteType)]) {
    return true;
}
```

If vote amendment is intentionally desired (as shown in the `vote configuration interleaved` test), it should be restricted to configuration votes only, and value-transfer votes should be immutable once cast.

---

### Proof of Concept

Setup: threshold = 2, operators = {A (malicious), B (honest)}. No third operator exists, so B alone cannot reach threshold 2.

1. User locks KLAY on the source chain; `requestNonce = N` is emitted.
2. Honest operator B calls `handleKLAYTransfer(txHash, from, user_to, value, N, blockNum, "")`.
   - `voteKey_correct = keccak256(msg.data)`, `voteCounts[voteKey_correct] = 1`. Threshold not reached.
3. Malicious operator A calls `handleKLAYTransfer(txHash, from, user_to, value, N, blockNum, "")`.
   - `voteCounts[voteKey_correct]` would become 2 → threshold reached → transfer executes.
   - **Instead**, A calls `handleKLAYTransfer(txHash, from, attacker_to, value, N, blockNum, "")` (different `_to`).
   - `voteKey_attacker = keccak256(msg.data_attacker)`, `voteCounts[voteKey_correct]` stays at 1, `voteCounts[voteKey_attacker] = 1`. Threshold not reached.
4. B re-votes with correct params: `voteCounts[voteKey_correct] = 2` → threshold reached → transfer executes.
   - **A immediately re-votes again** with attacker params: `voteCounts[voteKey_correct]` is now 1 again (B's vote only), `voteCounts[voteKey_attacker] = 1`.
5. Steps 3–4 repeat indefinitely. `closedValueTransferVotes[N]` is never set. The user's KLAY is permanently locked.

Exact corrupted storage value: `votes[ValueTransfer][N].voteCounts[voteKey_correct]` is kept at 1 (below threshold 2) by the malicious operator's repeated re-votes, preventing `closedValueTransferVotes[N]` from ever becoming `true` and blocking the `_to.call.value(_value)("")` transfer.     function _voteValueTransfer(uint64 _requestNonce)
        internal
        returns(bool)
    {
        require(!closedValueTransferVotes[_requestNonce], "closed vote");

        bytes32 voteKey = keccak256(msg.data);
        if (_voteCommon(VoteType.ValueTransfer, _requestNonce, voteKey)) {
            closedValueTransferVotes[_requestNonce] = true;
            return true;
        }

        return false;
