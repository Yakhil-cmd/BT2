### Title
Webhook signature verified against `repository.owner.login`, but the record acted on is resolved from `repository.full_name` — cross-organization webhook forgery in multi-org Shipit deployments - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/secret to verify a webhook against using `repository_owner` (`params.dig('repository','owner','login')` or `params.dig('organization','login')`), but the handler that actually mutates state resolves the target `Repository`/`Stack` using an entirely different, unchecked field: `payload.dig('repository','full_name')`. These two values are never cross-validated, breaking the binding: `organization that signed the payload == repository whose data is written`.

### Finding Description
`verify_signature` picks the `GitHubApp` (and thus the webhook secret) to check with using only the repository owner login: [1](#0-0) [2](#0-1) 

All handlers, however, resolve the affected repository/stack from `repository.full_name`, a completely separate JSON field: [3](#0-2) [4](#0-3) 

Nothing in `Shipit::Webhooks::Handlers::Handler` or its subclasses (`PushHandler`, `StatusHandler`, pull-request handlers, etc.) checks that `repository.owner.login` matches the owner portion of `repository.full_name`. `verify_webhook_signature` additionally treats an unset `webhook_secret` as automatically valid: [5](#0-4) 

Shipit explicitly supports running multiple GitHub App configs, one per organization, each with an independently optional `webhook_secret`: [6](#0-5) 

Consequently, if any one organization configured in `Shipit.secrets.github` is left without a `webhook_secret` (a state the setup docs describe as optional/acceptable), an attacker can send an unsigned POST to `/webhooks` with `repository.owner.login` (or `organization.login`) set to that unprotected org — satisfying `verify_signature` unconditionally — while setting `repository.full_name` to `<any-other-org>/<any-repo>` that the attacker wants to target. The handler layer never re-checks the owner, so it acts on the attacker-chosen repository regardless of which org "authenticated" the request.

### Impact Explanation
This breaks the equality `organization that authenticated == repository that is written`. Concretely, an attacker can forge events for any repository/stack tracked by the Shipit instance as long as one configured org lacks (or the attacker otherwise defeats) a webhook secret:
- `push` events trigger `GithubSyncJob` for the target stack (`PushHandler#process`) — polluting commit history tracking for a repository the attacker does not control.
- `status` events call `Commit#create_status_from_github!` for commits matching an arbitrary `sha` in `StatusHandler#process` — this can fabricate CI/check statuses on real commits of a targeted repository/stack, which stacks use to gate deploy safety/checklists, enabling an unauthorized deploy path against a repository the attacker has no legitimate relationship with.
- `membership`/`pull_request` handlers similarly act using attacker-supplied repository context.

This is a cross-repository write: the write target (`repository.full_name`) is never bound to the credential/authentication scope (`repository.owner.login`) that was actually verified.

### Likelihood Explanation
Requires no attacker credentials, session, or webhook secret — only that at least one configured GitHub organization in the deployment has no `webhook_secret` set, a state the engine's own docs and sample secrets files treat as normal/optional (`webhook_secret: # nil`). Any multi-tenant/multi-org Shipit deployment that onboards a low-priority or newly added org without immediately configuring its webhook secret is exposed. This is a pure logic/binding flaw in first-party code, not a third-party gem defect, and needs no privileged access.

### Recommendation
Bind webhook signature verification to the same repository record the handler will act on:
- After parsing the payload, resolve `full_name` and require that `repository.owner.login`/`organization.login` matches the owner segment of `repository.full_name` before dispatching to handlers.
- Do not allow `verify_webhook_signature` to short-circuit to `true` when `webhook_secret` is blank in multi-org configurations; require an explicit signed secret per organization, or reject events for organizations that omit one.

### Proof of Concept
1. Configure Shipit with two orgs, e.g. `orgA` (no `webhook_secret` set) and `orgB` (has `webhook_secret`, has a tracked `Repository`/`Stack` for `orgB/private-repo`).
2. Send an unsigned request to `POST /webhooks` with header `X-Github-Event: status` and body:
```json
{
  "repository": { "owner": { "login": "orgA" }, "full_name": "orgB/private-repo" },
  "sha": "<real sha of a commit in orgB/private-repo>",
  "state": "success",
  "context": "ci/required-check"
}
```
3. `verify_signature` computes `repository_owner = "orgA"`, loads `Shipit.github(organization: "orgA")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` and the request is accepted with no valid signature at all.
4. `StatusHandler#process` finds the real commit by `sha` (independent of `orgA`) via `Commit.where(sha: params.sha)` and calls `create_status_from_github!`, fabricating a passing CI status on a commit belonging to `orgB/private-repo`, an organization/repository the attacker never authenticated against.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
