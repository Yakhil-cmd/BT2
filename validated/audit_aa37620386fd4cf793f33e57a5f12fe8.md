### Title
Cross-organization commit-status forgery via unscoped `sha` lookup in `StatusHandler` - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret is used to validate an inbound webhook's HMAC signature purely from `repository.owner.login` (or `organization.login`) inside the *same* untrusted JSON body being verified. That authenticates "this payload was legitimately signed by organization X's webhook secret" — nothing more. `StatusHandler`, unlike every other webhook handler in the codebase, never re-derives or checks the repository/organization the commit belongs to: it resolves target records with a bare, database-wide `Commit.where(sha: params.sha)` lookup. This breaks the binding "organization that authenticated == repository that is written": a payload validly signed by Org A's webhook secret can carry a `sha` belonging to a commit that lives under a completely different Org B's stack, and `StatusHandler` will happily apply it.

### Finding Description
`app/controllers/shipit/webhooks_controller.rb` picks the verifying `GitHubApp`/secret using only the payload's own `repository.owner.login`/`organization.login`: [1](#0-0) [2](#0-1) 

In a multi-organization Shipit deployment (explicitly supported and documented, see `lib/shipit.rb#github_organizations` / `docs/setup.md` "Using Multiple Github Applications"), each organization that has installed the Shipit GitHub App knows *its own* `webhook_secret`. That is not a privileged Shipit credential — it is simply the webhook secret of the org the attacker legitimately administers. Because the HMAC covers only the raw JSON body content, and the org used to pick the verifying secret is read from a field (`repository.owner.login`) that the attacker fully controls when crafting the body, an attacker with a legitimate (their own) organization's webhook secret can:

1. Sign an arbitrary crafted JSON body with `X-Hub-Signature` computed via their own org's secret.
2. Set `repository.owner.login`/`organization.login` to their own org (so `verify_signature` succeeds).
3. Set every other payload field, including `sha`, to whatever they want — none of it is otherwise validated against the org used for signing.

For most handlers this is harmless because they *also* resolve the target stack from `payload.dig('repository', 'full_name')` via `Handler#stacks`: [3](#0-2) 

But `StatusHandler` does not use `stacks`/`repository_name` at all: [4](#0-3) 

`Commit.where(sha: params.sha)` is a global, cross-stack, cross-organization lookup. `Status`/`Commit` records don't have a database-level constraint proving `sha` uniqueness across the whole Shipit install, and even where SHAs happen to be unique, the point is that the handler applies the incoming status to whatever `Commit` row matches — regardless of which organization/repository that commit's `Stack` belongs to. Because attackers only need to know a *public* SHA of a commit on the target org's default/feature branch (visible via GitHub UI/API), they can pick any target commit in any org whose repositories exist on the same shared Shipit instance.

Applying the forged status calls `create_or_update_check_run_from_github!`/`create_status_from_github!` → `Commit#add_status`, which schedules merges and feeds `deployable?`: [5](#0-4) [6](#0-5) 

`add_status` calls `stack.schedule_merges` whenever the new status is `pending` or `success`, which enqueues `ProcessMergeRequestsJob`. That job merges pending merge requests once `all_status_checks_passed?`: [7](#0-6) 

So a forged `success` status on a required CI context can unblock `Commit#deployable?` and the merge queue for a target commit belonging to an org the attacker has no access to, potentially triggering an unauthorized deploy and/or merge on Org B's stack — using only Org A's own legitimately-known webhook secret.

### Impact Explanation
This is a High/Critical-tier finding per the scan rules: forging a passing CI/commit status for a foreign organization's commit can make that commit `deployable?` and unblock the merge queue (`ProcessMergeRequestsJob#merge!`), leading to an unauthorized deploy or unauthorized merge on a repository/organization the attacker does not control or have any relationship to, using only credentials (their own org's webhook secret) that are explicitly outside the excluded "privileged" categories (webhook secrets are per-org and are meant to be known by that org's own admins, not treated as a Shipit-wide privileged secret).

### Likelihood Explanation
Requires: (a) a multi-organization Shipit deployment (explicitly documented/supported feature), (b) the attacker legitimately administering at least one organization onboarded to that shared instance (a normal, unprivileged scenario — not requiring compromise of any other org, no Shipit session/API token, no GitHub token theft), and (c) knowledge of a target commit SHA in the victim org's repository, which is public. No social engineering, TLS interception, or GitHub App private key access is needed. This is a realistic, moderately-likely scenario in any environment that follows the documented multi-org setup.

### Recommendation
`StatusHandler` (and any other handler resolving records purely by content-derived identifiers like `sha`) must scope its lookup to the repository/stack indicated by `payload.dig('repository', 'full_name')` (as `Handler#stacks` already provides), rather than doing a global `Commit.where(sha:)` query. Concretely, replace `Commit.where(sha: params.sha)` with a query joined through `stacks` (e.g. `Commit.where(sha: params.sha, stack_id: stacks.select(:id))` or `stacks.flat_map(&:commits).select { |c| c.sha == params.sha }`), so a status payload can only affect commits belonging to stacks whose repository matches the organization that actually signed the payload.

### Proof of Concept
1. Deploy Shipit with two GitHub organizations configured, `OrgA` (attacker-controlled, legitimate installation) and `OrgB` (victim), per `docs/setup.md`'s "Using Multiple Github Applications" section — attacker knows `OrgA`'s `webhook_secret`.
2. Attacker finds a public commit SHA `S` on `OrgB/victim-repo`'s tracked branch (e.g. from GitHub UI) that is currently blocking deploys/merges (pending/failing CI).
3. Attacker crafts a `status` event JSON body:
   ```json
   {
     "sha": "S",
     "state": "success",
     "context": "ci/required-check",
     "repository": { "owner": { "login": "OrgA" } }
   }
   ```
4. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(OrgA_webhook_secret, body)>` and POSTs to `/webhooks` with `X-Github-Event: status`.
5. `WebhooksController#verify_signature` resolves `Shipit.github(organization: 'OrgA')` from `repository_owner` and successfully verifies the signature using `OrgA`'s secret.
6. `Shipit::Webhooks::Handlers::StatusHandler#process` executes `Commit.where(sha: 'S').each { |commit| commit.create_status_from_github!(params) }`, applying a forged `success` status onto `OrgB`'s commit, regardless of the fact the signature was verified only against `OrgA`.
7. `Commit#add_status` triggers `stack.schedule_merges`, potentially unblocking `deployable?`/merge queue for `OrgB`'s commit — an unauthorized cross-organization effect achieved with only `OrgA`'s own webhook secret.
