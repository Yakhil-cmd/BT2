### Title
Asset `transfer_condition` is skipped whenever a payment message also contains an `issue` input, allowing unauthorized transfer of a restricted asset - ([File: validation.js])

### Summary
`validatePayment()` classifies an entire asset payment message as either an "issue" or a "transfer" by looking only at `payload.inputs[0].type`, and this single classification (`bIssue`) is later used to decide which spending-condition to enforce for the *whole message*: `objAsset.issue_condition` or `objAsset.transfer_condition`, but never both. Because a single message is allowed to mix one `issue` input (at index 0) with any number of ordinary `transfer` inputs, an attacker can smuggle a `transfer` input for coins that are supposed to be gated by `transfer_condition` into a message that also contains a (self-issued) `issue` input, causing the validator to check `issue_condition` only and never evaluate `transfer_condition` at all — exactly analogous to CVE-2026-55956, where a security constraint scoped to certain HTTP methods was ignored because the enforcement point used the wrong discriminator for the actual operation being performed.

### Finding Description
`validatePayment()` determines `bIssue` once, based only on the type of the first input: [1](#0-0) 

This flag later selects the single condition that will be evaluated for the entire payment message: [2](#0-1) 

```
var arrCondition = bIssue ? objAsset.issue_condition : objAsset.transfer_condition;
if (!arrCondition) return cb();
Definition.evaluateAssetCondition(conn, payload.asset, arrCondition, objUnit, objValidationState, ...);
```

However, the per-input validation loop only forbids a *second* issue input, and only requires that the (single) issue input come first — it does not forbid mixing an issue input with subsequent transfer inputs in the same message: [3](#0-2) [4](#0-3) 

Immediately after, ordinary `"transfer"` inputs (spending previously issued coins of the same asset) are processed with no reference to `transfer_condition` in the per-input switch branch — enforcement is deferred entirely to the single message-level check quoted above: [5](#0-4) 

As a result: if an asset is defined with `issued_by_definer_only: false` (uncapped, publicly issuable) and a `transfer_condition` meant to restrict who may move already-issued coins (e.g. an address whitelist, `cosigned by`, `in data feed`/oracle gate, `attested`, etc.), a user who is *not* authorized to satisfy `transfer_condition` can still move restricted, previously-issued coins of that asset by simply adding a self-issue input (of any amount they choose, since the asset is uncapped) as input 0 of the same message, alongside the disallowed transfer input as input 1+. Because `payload.inputs[0].type === "issue"`, `bIssue` becomes `true`, `issue_condition` (if any, possibly unset/looser) is checked instead of `transfer_condition`, and the transfer of the restricted coins is admitted unconditionally.

This mirrors the reported bug class precisely: a security constraint ("transfer_condition") that is supposed to gate a specific type of operation ("transfer") is completely bypassed because the code path that decides which constraint to enforce dispatches on the wrong/insufficient signal (the type of the *first* input) rather than validating each operation (each input) against its own applicable constraint.

### Impact Explanation
This allows unauthorized spending: coins of an asset whose owner/definer configured `transfer_condition` specifically to restrict transfers (e.g., only whitelisted/attested addresses may move the asset, or transfers require a cosigner/oracle approval) can be moved by any address that is able to issue new units of the same asset (any address, when `issued_by_definer_only` is false) — completely defeating the transfer authorization mechanism. This is a concrete unauthorized-spending / asset-transfer-restriction bypass, directly reachable by any unprivileged unit poster who is an author of a payment message referencing that asset.

### Likelihood Explanation
The attack requires only that: (1) the target asset is uncapped and not `issued_by_definer_only` (a legitimate and common asset configuration used together with a `transfer_condition` for compliance/whitelisting use-cases), and (2) the attacker controls (or is an author of) a unit that spends the restricted output and is willing to add a trivial self-issue input to the same payment message. No special privileges, races, or malicious peers are needed — this is fully achievable by a single unprivileged unit author following the documented oscript/asset definition rules, making the likelihood high wherever such an asset+condition combination is deployed.

### Recommendation
Enforce `issue_condition` and `transfer_condition` per input rather than once per message: evaluate `issue_condition` against the (at most one) `issue` input specifically, and evaluate `transfer_condition` independently whenever the message contains any `transfer`-type input for that asset, regardless of whether an `issue` input is also present. Alternatively, disallow mixing `issue` and `transfer` inputs of the same restricted asset within a single message when a `transfer_condition` is defined.

### Proof of Concept
1. Definer creates asset `A` with `issued_by_definer_only: false`, no `cap`, and `transfer_condition` restricting transfers to attested/whitelisted addresses only (attacker's address does not satisfy it).
2. Attacker's address `X` already owns (or independently acquires, e.g. via a prior transfer that itself was allowed) some units of asset `A` at some `output`, which it should not be able to move per `transfer_condition`.
3. Attacker composes a single payment message for asset `A` with:
   - `inputs[0] = {type: "issue", amount: <any>, serial_number: <next>}` (self-issue, allowed since `issued_by_definer_only` is false and there's no cap),
   - `inputs[1] = {unit, message_index, output_index}` referencing the restricted output at `X` (ordinary `transfer` input, no `type` field),
   - balanced `outputs` sending the restricted-plus-issued amount to an address of the attacker's choosing.
4. In `validatePayment()`, `bIssue = (payload.inputs[0].type === "issue")` evaluates to `true` [1](#0-0) .
5. In `validatePaymentInputsAndOutputs()`, only `objAsset.issue_condition` is evaluated (which may be unset or trivially satisfiable); `objAsset.transfer_condition` is never evaluated [6](#0-5) .
6. The unit validates and gets accepted, transferring the restricted coins despite `transfer_condition` not being satisfied.
