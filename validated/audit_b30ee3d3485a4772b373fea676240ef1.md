The reported bug class — "the field acted upon differs from the field actually verified" — maps cleanly onto a real gap in this engine's webhook trust model: the organization whose secret authenticates a webhook is never bound to the repository/commit the handler actually mutates.

### Title
Webhook signature is verified against `repository.owner.login`, but `StatusHandler` mutates commits looked up globally by `sha` with no repository binding, enabling cross-organization forged CI status and unauthorized deploys - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`WebhooksController#verify_signature` picks which GitHub App/organization's `webhook_secret` to verify an inbound webhook HMAC against using `repository_owner`, derived from the JSON body itself (`params.dig('repository', 'owner', 'login')`). [1](#0-0) [2](#0-1) 

Once the signature check passes for that self-declared organization, the actual work performed by handlers is not re-checked against the same organization. `Shipit::Webhooks::Handlers::StatusHandler#process` looks up commits purely by `sha`, globally, across every stack/repository known to the Shipit instance, with no scoping to `repository.full_name` or the verifying organization at all: [3](#0-2) 

### Finding Description
This is a direct analog of the reported bonding-curve issue: a value that is checked (there, `amountTokenMin`/`amountKASMin`; here, "which organization's secret authorizes this payload") is disconnected from the value that is actually acted upon (there, the real liquidity added; here, "which commit/stack/repository gets mutated"). The equality that should hold and doesn't is:

`organization authenticated via repository.owner.login` == `repository/stack whose commit status is written`

Any Shipit deployment configured with more than one GitHub App/organization (the documented "Using Multiple Github Applications" setup) has one distinct `webhook_secret` per organization. [4](#0-3) 

An attacker who legitimately controls one onboarded organization ("Org A") knows Org A's `webhook_secret` (it is the secret they configured for their own app/installation). They can craft a `status` event whose `repository.owner.login` is `"OrgA"` (so `verify_signature` resolves and validates against Org A's known secret) but whose `sha` field names a commit that actually belongs to a completely different stack/organization ("victim-org"). Because `StatusHandler#process` performs `Commit.where(sha: params.sha)` with no repository/organization filter, it matches and mutates the victim's `Commit`, creating a forged `Status` row for it: [3](#0-2) 

Creating that `Status` triggers `Status#schedule_continuous_delivery` → `Commit#schedule_continuous_delivery`, which enqueues continuous delivery if the victim stack has continuous deployment enabled and the commit becomes `deployable?`: [5](#0-4) [6](#0-5) 

This can move the victim stack toward `trigger_continuous_delivery` → `trigger_deploy`, causing Shipit to deploy the victim's repository using Shipit's own GitHub credentials, entirely outside the victim organization's control: [7](#0-6) 

### Impact Explanation
This crosses the "an organization that authenticated versus the repository that is written" trust boundary explicitly in scope. The concrete outcome is an **unauthorized deploy**: an attacker who only controls one onboarded, low-trust organization's webhook secret can forge a passing CI/status signal for a commit belonging to an entirely different organization's stack, and push that stack toward continuous deployment — a Critical-severity impact per the stated criteria.

### Likelihood Explanation
Exploitation requires only:
1. The attacker legitimately administers one GitHub organization already onboarded to the target Shipit instance (multi-tenant deployments are explicitly documented/supported), giving them their own valid `webhook_secret`.
2. Knowledge of a target commit `sha` for the victim stack, which is generally public GitHub information (or visible via Shipit's own UI/API for that stack).
3. The victim stack has continuous deployment enabled and awaiting the specific/forged status context.

No access to the victim's secret, repository, or any Shipit session/API token is required, matching the "unprivileged attacker" and "no host misconfiguration" constraints.

### Recommendation
Bind the verified organization to the actual data acted upon:
- In `StatusHandler` (and any other handler that mutates records keyed only by loosely-derived fields), scope `Commit` lookup by the repository identified in the payload (`repository.full_name`) and cross-check that this repository belongs to the same organization/`GithubApp` that verified the webhook signature, rather than trusting `sha` alone.
- More generally, after `WebhooksController#verify_signature` resolves `repository_owner`, thread that verified organization through to `Shipit::Webhooks.for_event(event)` handlers, and have `Handler#stacks`/`Handler#repository_name`-based lookups assert that the resolved repository's owner matches the organization whose secret validated the request.

### Proof of Concept
1. Shipit is configured (per `docs/setup.md`, "Using Multiple Github Applications") with two organizations, `OrgA` (attacker-controlled, webhook secret `secretA` known to attacker) and `victim-org` (contains stack `victim-stack` with `continuous_deployment: true`).
2. Attacker obtains the `sha` of the next commit due for deploy on `victim-stack` (via public GitHub or the Shipit UI for that stack).
3. Attacker crafts payload:
```json
{
  "repository": { "owner": { "login": "OrgA" } },
  "sha": "<victim-stack commit sha>",
  "state": "success",
  "context": "ci/required-check"
}
```
4. Attacker computes `X-Hub-Signature: sha1=HMAC(secretA, payload)` and sends it to `/webhooks` with `X-Github-Event: status`.
5. `WebhooksController#verify_signature` resolves `repository_owner == "OrgA"`, fetches `Shipit.github(organization: "OrgA")`, and validates the signature successfully (attacker knows `secretA`).
6. `StatusHandler#process` executes `Commit.where(sha: params.sha)`, finds the victim's `Commit` (no organization/repo filter), and calls `create_status_from_github!`, creating a forged `success` `Status` on `victim-stack`'s commit.
7. If this satisfies the victim stack's CI requirements, `ContinuousDeliveryJob` runs and `victim-stack` is deployed — an unauthorized deploy triggered entirely by an unrelated organization's credentials.
