### Title
Webhook signature verification keys off `repository.owner.login`/`organization.login` while event handlers act on the independent `repository.full_name` field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the `GitHubApp` (and thus the HMAC secret used to validate `X-Hub-Signature`) using `repository_owner`, a value read straight from the unauthenticated JSON body. Every webhook handler, however, resolves the `Repository`/`Stack` to mutate using a *different* field of the same body: `repository.full_name`. Because these two attacker-controllable fields are never checked for consistency, and because `GitHubApp#verify_webhook_signature` trivially returns `true` whenever the selected organization has no `webhook_secret` configured (the documented default), a payload can be crafted (and, where needed, signed) using one organization's identity while acting on a completely different organization/repository's stack.

### Finding Description
The verification path is: [1](#0-0) [2](#0-1) 

`repository_owner` is taken directly from `params.dig('repository', 'owner', 'login')` (or `organization.login`) — this is attacker-supplied JSON, read *before* any cryptographic check has passed — and used solely to pick which `GitHubApp` instance's secret governs the check.

`GitHubApp#verify_webhook_signature` unconditionally accepts the request when no secret is configured for that organization: [3](#0-2) 

This is not a hypothetical misconfiguration: it is the documented/shipped default for every organization entry in the multi-org config schema (`webhook_secret: # nil`): [4](#0-3) [5](#0-4) 

Once `create` proceeds, every handler resolves the actually-affected `Repository`/`Stack` from a *separate* field, `repository.full_name`, not from `repository.owner.login`: [6](#0-5) [7](#0-6) 

The binding that should hold is: `organization used to authenticate the request == owner of the repository the handler mutates`. Instead, the engine only ever authenticates "some organization" (frequently one with no secret configured, in which case verification is a no-op) and then blindly trusts a second, independent payload field (`repository.full_name`) to decide which tracked stack across the whole Shipit instance gets updated. In a multi-organization deployment (the officially supported "Using Multiple Github Applications" configuration, `docs/setup.md:182-209`), this lets a request that is nominally "for OrgA" (and trivially passes verification because OrgA has no `webhook_secret`, or because the attacker knows/controls OrgA's secret) carry a `repository.full_name` pointing at a stack belonging to OrgB, and have it processed as if it legitimately originated from GitHub for that repository.

### Impact Explanation
Handlers driven purely by `repository.full_name`/`sha`/`state`/`ref` fields can, once past the (potentially no-op) signature check:
- Forge `status` events for arbitrary commits on any tracked stack, which is exactly the kind of trust boundary the CI-status–gated merge/deploy flow relies on.
- Forge `push` events (`PushHandler`) causing `stack.sync_github` to run for a stack the attacker never actually pushed to, potentially advancing "undeployed commits" state feeding continuous deployment.
- Archive/unarchive or create review stacks via forged `pull_request` events for repositories unrelated to the organization that "authenticated."

This crosses the required High/Critical bar because it allows a request that only weakly (or not at all) authenticates as one GitHub organization to alter deployment-relevant state (CI status, sync state, stack lifecycle) for a repository under a completely different, unrelated organization/tenant of the same Shipit instance — an unauthorized cross-repository/cross-organization state change achieved purely by manipulating unrelated fields of the JSON payload.

### Likelihood Explanation
Likelihood is highest in the officially documented multi-organization configuration, since the shipped example files (`config/secrets.development.example.yml`, `test/dummy/config/secrets_double_github_app.yml`, `docs/setup.md`) leave `webhook_secret` blank by default for each org entry, which makes `verify_webhook_signature` a no-op for that org (`return true unless webhook_secret`). Any caller who can reach the `/webhooks` endpoint and knows (or guesses) any organization login configured on the instance with a blank secret can send arbitrary bodies that target any other tracked repository via `repository.full_name`, with no signature required at all.

### Recommendation
- After signature verification, re-derive `repository_owner` from the *verified* `repository.full_name` (or explicitly enforce `repository.full_name`'s owner matches `repository.owner.login`/the organization used for verification) before dispatching to handlers.
- Do not allow `verify_webhook_signature` to return `true` when `webhook_secret` is blank; either require a secret for every configured organization or fail closed.
- Consider binding webhook processing to the specific `Repository`/organization pairing recorded when the stack/repository was created in Shipit, rather than trusting any organization field embedded in the incoming payload.

### Proof of Concept
1. Configure Shipit with two organizations, `OrgA` and `OrgB`, both tracking stacks (supported multi-org schema, `docs/setup.md:182-209`). Leave `OrgA`'s `webhook_secret` unset, as shown in the shipped example configs.
2. POST to `/webhooks` with header `X-Github-Event: status` and a body such as:
   ```json
   {
     "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/victim-repo" },
     "sha": "<victim commit sha>",
     "state": "success",
     "context": "ci/required",
     "target_url": "http://attacker",
     "created_at": "..."
   }
   ```
3. `WebhooksController#verify_signature` computes `repository_owner = "OrgA"`, loads `Shipit.github(organization: "OrgA")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` regardless of the (missing/garbage) `X-Hub-Signature` header — see `app/controllers/shipit/webhooks_controller.rb:24-30` and `lib/shipit/github_app.rb:76-83`.
4. The request passes to `StatusHandler`, which resolves the target stack via `repository.full_name` = `"OrgB/victim-repo"` (`handler.rb:36-37`) and records a forged `success` status for the specified commit, independent of `OrgA`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

# frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
