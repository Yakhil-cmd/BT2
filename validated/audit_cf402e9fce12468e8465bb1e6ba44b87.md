### Title
Assets with `spender_attested` permanently freeze holder funds once the definer revokes attestation - (File: `validation.js`, `storage.js`)

### Summary
`ocore` supports assets whose `spender_attested` flag makes every transfer conditional on the sender's address being present in an attestor-controlled whitelist (`asset_attestors`). This is functionally the same pattern as the Blueberry `onlyWhitelistedToken` check that blocked `repay`: a mutable, externally-controlled whitelist gate sits directly on the path that a coin holder must use to move their own already-owned funds. If the address that legitimately holds asset units is later dropped from the attestor list, those coins become permanently unspendable by that holder, with no fallback path in the protocol to reclaim or otherwise dispose of them.

### Finding Description
When validating any `payment` message that spends outputs of an asset with `spender_attested = true`, `validatePaymentInputsAndOutputs` requires that `owner_address` (the address currently holding the input being spent) is present in `objAsset.arrAttestedAddresses`: [1](#0-0) 

This attested-address list is derived at validation time from the live `attestations` table filtered by the asset's current `arrAttestorAddresses`, via `filterAttestedAddresses`/`loadAssetWithListOfAttestedAuthors`: [2](#0-1) 

Both the identity of the attestors (`arrAttestorAddresses`, settable through an `asset_attestors` message from the asset definer) and the attestation itself (an `attestation` message, which can be revoked simply by never re-issuing one, or by the attestor changing who they attest) are entirely under the control of parties other than the coin holder. Because the check is re-evaluated fresh at spend time (not fixed at issuance/receipt time), a coin holder who was validly attested when they received the asset can lose the ability to move it later purely due to an action taken by the attestor/definer — an action the holder does not control and cannot reverse.

The same check applies on receipt of outputs too (`arrOutputAddresses` must all be attested, `validation.js:2632-2641`), and the same `spender_attested`/attestation gate is also consulted by AA logic (`aa_composer.js:986-991`, checking `issued_by_definer_only` but going through the same asset lookup that enforces `spender_attested`), meaning an Autonomous Agent holding such an asset can equally be locked out of its own balance if it (or its counterparties) loses attestation.

Unlike a normal whitelist that only gates new issuance or new transfers going forward, here the check gates the transfer of coins the holder already legitimately owns, with no way to bypass it (there is no analogous non-attested repay/withdraw path). This mirrors exactly the structure of the reported Blueberry bug: a mandatory "unwind"/"move my own funds" operation is gated by a mutable third-party whitelist, and removal from that whitelist bricks the user's ability to ever act on funds they already possess.

### Impact Explanation
Any address (regular wallet or AA) holding units of a `spender_attested` asset can have those funds permanently frozen if the attestor/definer revokes or fails to renew the attestation, or if the definer updates the attestor list to exclude the relevant attestor. There is no recovery mechanism in the protocol — the held coins simply become unspendable forever, which is a direct, concrete instance of fund freezing/loss for the affected holder (and for AAs, permanent lock-up of AA-held balances of that asset).

### Likelihood Explanation
This requires the asset to be configured with `spender_attested = true` (an explicit, self-selected feature of the asset definer at asset-creation time), and requires the definer/attestor to subsequently change the attestor list or stop attesting an address that already holds funds. This is plausible in normal asset lifecycle management (e.g., compliance-driven de-listing of an address, KYC revocation, or attestor list changes for a "whitelisted" trading pair), i.e., an ordinary, foreseeable administrative action rather than an attack — exactly analogous to the "borrow token removed from whitelist" scenario in the report.

### Recommendation
Decouple "ability to receive/hold" from "ability to move already-owned funds" for `spender_attested` assets. For example, allow spending (transferring out or sending to the definer/burn) of previously-held outputs by an address that was attested at the time it received the coin, even if it is no longer currently in `arrAttestedAddresses` — e.g., cache/record attestation status at receipt time, or provide an unconditional "return to definer" transfer path that bypasses the live-attestation check, similar to how `auto_destroy`/definer-directed sends are already special-cased in `validation.js:2616-2628`.

### Proof of Concept
1. Definer creates an asset `A` with `spender_attested: true` and attestor `X`.
2. Attestor `X` attests address `H`.
3. `H` receives a payment output of asset `A` (valid, since `H` is attested — checked at `validation.js:2632-2641`).
4. Attestor `X` (or definer via an `asset_attestors` message) stops attesting `H` / removes `X` from the attestor list.
5. `H` now tries to spend the previously received output of asset `A`. Validation reaches `validation.js:2506-2507`, computes `arrAttestedAddresses` fresh via `storage.js:1959-1991`, finds `H` no longer attested, and rejects with `"owner address is not attested"`.
6. `H`'s funds in asset `A` are now permanently stuck; there is no alternate repay/withdraw/burn path that bypasses this check.

```javascript
// filter only those addresses that are attested (doesn't work for light clients)
function filterAttestedAddresses(conn, objAsset, last_ball_mci, arrAddresses, handleAttestedAddresses){
	conn.query(
		"SELECT DISTINCT address FROM attestations CROSS JOIN units USING(unit) \n\
		WHERE attestor_address IN(?) AND address IN(?) AND main_chain_index<=? AND is_stable=1 AND sequence='good' \n\
			AND main_chain_index>IFNULL( \n\
				(SELECT main_chain_index FROM address_definition_changes JOIN units USING(unit) \n\
				WHERE address_definition_changes.address=attestations.address AND main_chain_index<=? AND is_stable=1 AND sequence='good' ORDER BY main_chain_index DESC LIMIT 1), \n\
			0)",
		[objAsset.arrAttestorAddresses, arrAddresses, last_ball_mci, last_ball_mci],
		function(addr_rows){
			var arrAttestedAddresses = addr_rows.map(function(addr_row){ return addr_row.address; });
			handleAttestedAddresses(arrAttestedAddresses);
		}
	);
}

// note that light clients cannot check attestations
function loadAssetWithListOfAttestedAuthors(conn, asset, last_ball_mci, arrAuthorAddresses, bAcceptUnconfirmedAA, handleAsset){
	if (arguments.length === 5) {
		handleAsset = bAcceptUnconfirmedAA;
		bAcceptUnconfirmedAA = false;
	}
	readAsset(conn, asset, last_ball_mci, bAcceptUnconfirmedAA, function(err, objAsset){
		if (err)
			return handleAsset(err);
		if (!objAsset.spender_attested)
			return handleAsset(null, objAsset);
		filterAttestedAddresses(conn, objAsset, last_ball_mci, arrAuthorAddresses, function(arrAttestedAddresses){
			objAsset.arrAttestedAddresses = arrAttestedAddresses;
			handleAsset(null, objAsset);
		});
	});
```
