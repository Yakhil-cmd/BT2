### Title
Uncaught assertion (`throw Error`) crash when validating a non-private transfer of a private, fixed-denomination asset - ([File: validation.js])

### Summary
`validation.js`'s public unit-validation path (`validate()` → `validatePayment()` → `validatePaymentInputsAndOutputs()`) does not gate the "transfer" input branch for private, fixed-denomination assets behind a check that the unit is actually being validated as part of a private-payment chain. When such a "transfer" input is encountered for a private+fixed-denomination asset, the code unconditionally assumes `objValidationState.src_coin` was pre-populated by the private-chain machinery (`indivisible_asset.js`), and `throw`s a hard `Error` if it is missing, instead of returning a normal validation error through `cb()`/`callback()`. [1](#0-0) 

### Finding Description
Normal, network-wide unit validation is invoked via `validate(objJoint, callbacks, external_conn)`, which builds a fresh `objValidationState` object per unit (no `src_coin` field is ever placed on it in this path) and eventually calls `validateMessages` → `validatePayment` → `validatePaymentInputsAndOutputs`. [2](#0-1) [3](#0-2) 

Inside `validatePaymentInputsAndOutputs`, when an input has no `type` (i.e., it's a "transfer") and the referenced asset is private and uses fixed denominations, the code branches into a path that is only meant to be reached from the private-payment-chain validation flow (`indivisible_asset.js`'s `validatePrivatePayment`), where `objValidationState.src_coin` is explicitly populated before calling `validation.validatePayment`. [4](#0-3) 

However, `objAsset.is_private && objAsset.fixed_denominations` is determined purely from the asset definition stored on-chain — it is not tied to whether the *current* unit came through the private-chain code path (`indivisible_asset.js`/`private_payment.js`) or through the regular public broadcast/catchup path (`network.js handleJoint` → `validation.validate`). Any unit, whether posted by an ordinary peer over the wire or replayed during catch-up, that contains a `payment` message referencing such an asset with a plain "transfer" input, will hit this branch in the regular public validation flow, where `src_coin` was never set: [5](#0-4) 

```js
if (objAsset && objAsset.is_private && objAsset.fixed_denominations){
    if (!objValidationState.src_coin)
        throw Error("no src_coin");
    var src_coin = objValidationState.src_coin;
    if (!src_coin.src_output)
        throw Error("no src_output");
    if (!isPositiveInteger(src_coin.denomination))
        throw Error("no denomination in src coin");
    if (!isPositiveInteger(src_coin.amount))
        throw Error("no src coin amount");
    ...
}
```

Since `validatePaymentInputsAndOutputs` runs deep inside an `async.eachSeries`/`async.series` chain invoked from `validate()`, this `throw` is a **synchronous exception thrown from inside an asynchronous callback**. It is not caught by any `try/catch` in the surrounding `async` control flow (`validation.js:417-496`, `network.js handleJoint`), so it propagates up as an uncaught exception. Depending on Node's uncaught-exception handling configuration, this can crash the process (denial of service) rather than being turned into an `ifUnitError`/`ifJointError` callback as all other malformed-input cases are handled.

This is directly analogous to CVE-2018-5734: a malformed/unexpected combination of otherwise-valid-looking input data causes the validator to take a code path that assumes preconditions (an internal cache/state field) are already satisfied, and when they are not, it hits a hard assertion/crash instead of gracefully classifying the input as invalid.

### Impact Explanation
Any node (full node or hub) that receives and validates a crafted unit — either posted directly by an unprivileged peer, replayed via catch-up, or included in a hash-tree ball during sync — referencing a private, fixed-denomination asset with a bare "transfer" input (no accompanying private-chain context establishing `src_coin`) will throw an uncaught `Error` inside the validation pipeline. This can crash the node process, denying it the ability to process further units (network unable to confirm new units on that node), which matches the required "network unable to confirm new units" / node-crash impact bar for this exercise. Because asset definitions (`is_private`, `fixed_denominations`) are attacker-controlled at asset-issuance time and units are attacker-composed, no special privilege is needed beyond being able to post a unit referencing a previously-issued private/fixed-denomination asset.

### Likelihood Explanation
Likelihood is high for any attacker who can define an asset with `is_private: true` and `fixed_denominations: true` (a standard, permitted asset-definition combination) — a single ordinary unit poster can do this using the existing asset-issuance flow (`aa_validation.js`/asset definition validation permits this combination). After the asset is confirmed, the same or another unpriviledged unit poster can then construct and broadcast (or have propagated during catchup) a `payment` message with a "transfer" input for that asset, which is validated via the normal public `validate()` path without ever going through `indivisible_asset.js`'s private-chain population of `src_coin`.

### Recommendation
- Replace all `throw Error(...)` assertions in the private-fixed-denomination "transfer" branch of `validatePaymentInputsAndOutputs` (validation.js lines 2416-2424, and the related `throw Error` calls at lines 2451, 2458, 2476) with normal error propagation via `cb(...)`/`callback(...)`, so malformed/unexpected input results in `ifUnitError`/`ifJointError`, not process crash.
- Additionally, explicitly reject (via `cb("transfer of private fixed-denomination asset not allowed outside a private-payment chain")`) any attempt to validate a "transfer" input for a private, fixed-denomination asset when `objValidationState.bPrivate` is not `true`, rather than relying on `src_coin` presence as an implicit gate. This ensures the public network-validation path cannot reach the private-chain-only branch at all.
- Wrap the outer validation dispatch in `network.js`/`validation.js` with a safety net that converts unexpected synchronous throws into `ifTransientError`/`ifUnitError` callbacks, to avoid future assertion-style crashes having this same blast radius.

### Proof of Concept
1. Attacker issues an asset with `is_private: true`, `fixed_denominations: true`, and appropriate `denominations` (allowed per `validateAssetDefinition`, `validation.js:2725-2755`), gets it confirmed.
2. Attacker crafts a new unit with a `payment` message referencing that asset, containing an input object with no `type` field (a "transfer") and a fabricated `unit`/`message_index`/`output_index` (does not need to correspond to a real, previously-validated private chain on the *validating* node).
3. Attacker broadcasts this unit normally over the P2P network (`network.js` `handleJoint`) or it is otherwise queued for validation via `validation.validate`.
4. On the validating node, `validatePaymentInputsAndOutputs` reaches the `objAsset.is_private && objAsset.fixed_denominations` branch with a fresh `objValidationState` that has no `src_coin` set, hits `throw Error("no src_coin")`, and — because this executes inside an `async` callback chain with no enclosing `try/catch` — crashes the node process instead of returning a validation error.

I was not able to execute or reproduce this at runtime (no code execution environment/terminal was used for this ask-only investigation); the analysis is based on static code review of the paths cited above. If exact throw-catch/process-level exception handling behavior needs to be confirmed empirically (e.g., whether some global `uncaughtException` handler in `start.js`/`process.js` mitigates this), that verification requires running the code, which is outside the scope of this ask-only session.
