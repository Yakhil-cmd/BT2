### Title
`Api::CCMenuController` accepts a `read:stack`-scoped token to read the deploy state of an arbitrary `stack_id` because `#stack` bypasses `current_api_client.stack_id` scoping - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Api::CCMenuController#stack` calls `Stack.from_param!(params[:stack_id])` directly instead of the base controller's scoped `stacks.from_param!`, so any valid API token (including a CCMenu client token minted for one stack) can be replayed with a different `stack_id` query param to read another stack's deploy/task state. The binding the base controller relies on — that a stack lookup is scoped to `current_api_client.stack_id` when the client has one — never applies here, and worse, `CCMenuUrlController#client` never sets `stack_id` on the created `ApiClient` at all.

### Finding Description
The intended binding is: `stack accessed == current_api_client.stack_id` (when the client is stack-scoped), enforced in the base controller via [1](#0-0) 
`stacks` restricts to `Stack.where(id: current_api_client.stack_id)` when `current_api_client.stack_id?` is true, and `stack` calls `stacks.from_param!`.

`Api::CCMenuController` overrides `stack` and drops this scoping entirely: [2](#0-1) 
It authenticates via `ApiClient.authenticate(params[:token])` (query string, as the question states) and then resolves `Stack.from_param!(params[:stack_id])` against the whole `Stack` table, with `require_permission :read, :stack` only checking that `"read:stack"` is present in `permissions` (`ApiClient#check_permissions!`), never checking `stack_id`: [3](#0-2) 

Compounding this, the token minted by `CCMenuUrlController#fetch`/`#client` is created without ever setting `stack_id` on the `ApiClient` record: [4](#0-3) 
so `current_api_client.stack_id?` is false for this client even if the base scoping were used — the token is a global `read:stack` credential, not one bound to the stack whose CCMenu URL was requested.

Exploit flow: an operator fetches a CCMenu URL for stack A via `CCMenuUrlController#fetch`, producing `.../api/stacks/A/ccmenu.xml?token=T`. An attacker who obtains this URL/token (e.g., forwarded into a monitoring tool, shared link, proxy log) requests `.../api/stacks/B/ccmenu.xml?token=T` for an arbitrary stack B. `authenticate_api_client` accepts `T` (it's a valid, unexpired signed token), `require_permission!(:read, :stack)` passes because the client has `read:stack` permission generically, and `stack` resolves stack B unscoped. The response leaks stack B's latest deploy/task status, matching the test pattern already present in the suite that confirms query-string tokens are accepted: [5](#0-4) 

None of the listed guards prevent this: `require_permission!` only checks the permission string, not stack identity; there is no `subset`/stack-binding validator on `ApiClient` tying `stack_id` to the token's use; and `CCMenuController#stack` explicitly bypasses the one mechanism (`BaseController#stacks`) that would have enforced the intersection.

### Impact Explanation
An attacker who obtains any CCMenu token (or any `read:stack` API token) can enumerate/read task and deploy status (build status, last build label/time, lock state) for any stack in the Shipit instance, not just the stack the token was intended for. This is an unauthenticated-for-that-resource read of stack/task state across tenants (any repository/stack in the instance), matching the High-severity category "unauthenticated read of stack state, task streams or deploy output." It is fully repeatable — the token remains valid until revoked and works against every `stack_id` in the database.

### Likelihood Explanation
The attacker needs to obtain one valid `read:stack` token — the question's threat model explicitly allows this via a shared/forwarded CCMenu link (a normal, expected usage pattern for CCMenu/CCTray monitoring integrations, which are typically embedded in plain URLs and often logged by proxies/monitoring tools). No Shipit secrets, sessions, or privileged roles are required beyond possessing a token that a legitimate operator already generated and shared. Once obtained, exploitation is a single unauthenticated GET request with a substituted `stack_id`, so cost and feasibility are trivial and fully repeatable.

### Recommendation
In `Api::CCMenuController`, remove the private `stack` override and use the base controller's scoped `stack`/`stacks` method (`stacks.from_param!(params[:stack_id])`) so lookups are constrained by `current_api_client.stack_id` when present. Additionally, have `CCMenuUrlController#client` create/find the `ApiClient` with `stack: stack` (or `stack_id: stack.id`) set, so CCMenu tokens are inherently scoped to a single stack rather than being global `read:stack` credentials.

### Proof of Concept
```ruby
# test/controllers/api/ccmenu_controller_test.rb (additional test)
test "a token minted for stack A cannot be used to read stack B" do
  stack_b = Stack.create!(repository: Repository.new(owner: "foo", name: "bar-b"), branch: 'main')

  # Binding under test: stack accessed must equal current_api_client.stack_id
  # LHS: params[:stack_id] resolved by controller -> stack_b.id
  # RHS: @client.stack_id (nil, generic read:stack token minted for stack A context)
  assert_nil @client.stack_id

  get :show, params: { stack_id: stack_b.to_param, token: @client.authentication_token }

  assert_response :ok # currently succeeds - vulnerability
  assert_payload 'name', stack_b.to_param # leaks stack B's data using a token never scoped to stack B
end
```
This demonstrates that `@client` (a generic `read:stack` token, structurally identical to the one minted by `CCMenuUrlController#client` for a different stack) successfully authenticates and reads an arbitrary stack's CCMenu XML, confirming the LHS (`stack_b.id`) and RHS (`@client.stack_id` == `nil`, i.e., unconstrained) never match yet access is still granted — the vulnerability as claimed in the question is valid.
