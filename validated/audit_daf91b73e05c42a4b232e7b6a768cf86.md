### Title
Independent per-recipient rounding of `earned_headers_commission_share` causes unbacked supply inflation - (File: headers_commission.js)

### Summary
`calcHeadersCommissions` distributes a parent unit's `headers_commission` among multiple `earned_headers_commission_recipients` by computing each recipient's amount independently as `ROUND(headers_commission * share / 100.0)`, then simply summing whatever each recipient received into `headers_commission_outputs`. Because each recipient's share is rounded to the nearest integer independently rather than the last recipient receiving the remainder, the total amount actually credited across all recipients can exceed the original `headers_commission` collected from the payer unit. This is directly analogous to the reported precision-loss class: a per-unit rate/share calculation that individually rounds instead of preserving an exact total, creating value that either gets "lost" (per the original report) or, in this case, "created" beyond the input amount.

### Finding Description
An unprivileged unit poster can author a multi-authored unit and declare `earned_headers_commission_recipients` with shares that sum to exactly 100 (as required by `validateHeadersCommissionRecipients`) [1](#0-0) . When this unit later wins headers commission from a parent unit, `calcHeadersCommissions` computes each recipient's payout independently:

- In the RAM/JS path: `var amount = Math.round(full_amount * share / 100.0);` for each recipient, pushed individually into `headers_commission_contributions` [2](#0-1) .
- In the SQL fallback path, the same independent rounding is applied via `Math.round(full_amount * row.earned_headers_commission_share / 100.0)` [3](#0-2) , and the MySQL query path uses the equivalent `ROUND(punits.headers_commission*earned_headers_commission_share/100.0)` [4](#0-3) .

These independently rounded contributions are never reconciled against the original `headers_commission` value. They are simply summed per address and inserted into `headers_commission_outputs`:
```
INSERT INTO headers_commission_outputs (main_chain_index, address, amount)
SELECT main_chain_index, address, SUM(amount) FROM units CROSS JOIN headers_commission_contributions USING(unit)
...
GROUP BY main_chain_index, address
``` [5](#0-4) 

Because each of the (up to `MAX_AUTHORS_PER_UNIT`) recipients' shares is rounded to the nearest integer independently, the sum of the rounded amounts can differ from the true `full_amount` by up to roughly `n/2` bytes, where `n` is the number of recipients. Since rounding uses "round half away from zero," an attacker who controls all the recipient addresses can choose share percentages engineered so that most/all recipients round *up* (e.g., splitting shares as many small `x.5%`-type fractions), systematically biasing the sum above the original `headers_commission`, rather than the errors canceling out.

These `headers_commission_outputs` amounts are later spendable directly as `headers_commission` type transaction inputs, validated in `validatePaymentInputsAndOutputs` via `mc_outputs.calcEarnings`, which simply reads back the accumulated commission and allows spending it as real currency [6](#0-5) . There is no invariant anywhere in the codebase that checks `SUM(headers_commission_contributions.amount) == parent.headers_commission` for a given payer unit; the `checkBalances`-style consistency checks in `aa_composer.js` only cover AA balances, not commission distribution [7](#0-6) .

### Impact Explanation
This allows an attacker to mint bytes beyond what was actually collected as headers commission from a payer unit, i.e., a form of unbacked supply inflation of the base currency. Although the discrepancy per unit is bounded (at most a few bytes per set of recipients, limited by `MAX_AUTHORS_PER_UNIT`), it is deterministically and repeatably exploitable: an attacker can post many multi-authored units over time, each engineered to win headers commission and each configured with a skewed `earned_headers_commission_recipients` split that rounds upward, accumulating small amounts of unbacked currency across many main-chain indices. Because all nodes compute the same rounding deterministically, this does not cause node disagreement, but it does create real currency that was never paid in as a fee — a genuine (if slow) supply-inflation vector reachable purely by posting ordinary units, with no special privileges required.

### Likelihood Explanation
Likelihood is limited by two factors: (1) the attacker must be the "winner" of headers commission for a parent unit, which under `getWinnerInfo` is determined pseudo-randomly by hash comparison among sibling children rather than being fully attacker-controlled per unit [8](#0-7) , and (2) the per-unit gain is small (bounded by number of recipients). However, since anyone can post many candidate units competing for the win, and repeat the attack indefinitely over the life of the network, the attack is realistically automatable and cumulative, making the likelihood moderate rather than purely theoretical.

### Recommendation
Do not round each recipient's share independently. Compute all recipients' shares except the last using `Math.round`/`ROUND`, then assign the last recipient (in a deterministic, e.g. address-sorted order) the exact remainder: `full_amount - sum(previous recipients' rounded amounts)`. This guarantees the total distributed to `headers_commission_outputs` for a given payer unit's `headers_commission` exactly equals the original amount, eliminating any possibility of over- or under-distribution. Apply the same remainder-based approach consistently to both the MySQL query path and the JS/SQLite path in `headers_commission.js`.

### Proof of Concept
1. Author a unit `U` with multiple authors (e.g., attacker-controlled addresses A1, A2, A3) and set `earned_headers_commission_recipients` shares to values chosen so that `ROUND(headers_commission * share_i / 100)` rounds up for as many recipients as possible while the shares still sum to exactly 100 (e.g., three recipients with shares `33`, `33`, `34`, and `headers_commission` chosen such that `full_amount * 0.33` and `full_amount * 0.34` each end in `.5` or higher, causing all three roundings to round up).
2. Get unit `U` selected as the headers-commission winner for a parent unit (post several candidate sibling units to increase the chance of winning per `getWinnerInfo`'s hash-based selection) [8](#0-7) .
3. Observe that `calcHeadersCommissions` inserts `Math.round(full_amount*33/100)`, `Math.round(full_amount*33/100)`, and `Math.round(full_amount*34/100)` into `headers_commission_contributions` for A1, A2, A3 [2](#0-1) , whose sum exceeds `full_amount` (the actual `headers_commission` collected from the payer unit).
4. The excess is then aggregated unmodified into `headers_commission_outputs` via `SUM(amount) ... GROUP BY main_chain_index, address` [5](#0-4) , and becomes spendable as a normal `headers_commission` input in a subsequent payment, per `validatePaymentInputsAndOutputs`/`mc_outputs.calcEarnings` [6](#0-5) , realizing bytes that were never collected as fees.

function validateHeadersCommissionRecipients(objUnit, cb){

			if (!isPositiveInteger(recipient.earned_headers_commission_share))
				return cb("earned_headers_commission_share must be positive integer");
			if (hasFieldsExcept(recipient, ["address", "earned_headers_commission_share"]))
				return cb("unknown fields in recipient");

				return cb("invalid recipient address checksum");

				return cb("recipient list must be sorted by address");
			total_earned_headers_commission_share += recipient.earned_headers_commission_share;
			prev_address = recipient.address;
		}
		if (total_earned_headers_commission_share !== 100)
			return cb("sum of earned_headers_commission_share is not 100");
	}

function getWinnerInfo(arrChildren){
	if (arrChildren.length === 1)
		return arrChildren[0];
	if (arrChildren.length === 0)
		throw Error("no children for hc");
	arrChildren.forEach(function(child){
		child.hash = crypto.createHash("sha1").update(child.child_unit + child.next_mc_unit, "utf8").digest("hex");
	});
	arrChildren.sort(function(a, b){ return ((a.hash < b.hash) ? -1 : 1); });
	return arrChildren[0];
}
