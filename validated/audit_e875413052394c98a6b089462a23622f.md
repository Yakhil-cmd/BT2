Based on my investigation, I found a genuine analog: an authorization check that was deliberately disabled (commented out) in the device-message handling path, which is directly comparable in bug-class to the PHP report's `Permissions::skip()` disabling authorization checks before processing privileged operations.

### Title
Disabled authorization filter lets "indirect" (untrusted) paired-device correspondents send privileged wallet-state messages - (File: wallet.js)

### Summary
`handleMessageFromHub()` in `wallet.js` contains a check that used to restrict which message `subject`s an `is_indirect` correspondent (a device known to us only because it was named as another cosigner's contact, never explicitly paired with us) is allowed to send. That check is commented out, so any subject — including `new_wallet_address`, `arbiter_contract_offer/response/update`, `create_new_shared_address`, `sign`, etc. — is now processed from indirect correspondents exactly as if they were fully paired devices.

### Finding Description
`device.js` maintains `correspondent_devices.is_indirect`, set to `1` whenever a device address is auto-added via `addIndirectCorrespondents()` [1](#0-0)  — this happens for every "other cosigner" mentioned in a wallet-creation offer or shared-address definition, without any pairing secret or explicit user consent from the local user for that specific device.

In `device.js`'s `hub/message` handler, the sender's `is_indirect` flag is read from the DB and passed through to `wallet.js` as `bIndirectCorrespondent` [2](#0-1) .

In `wallet.js`, `handleMessageFromHub()` receives this flag but the intended restriction is disabled:
```
//if (bIndirectCorrespondent && ["cancel_new_wallet", "my_xpubkey", "new_wallet_address"].indexOf(subject) === -1)
//    return callbacks.ifError("you're indirect correspondent, cannot trust "+subject+" from you");
``` [3](#0-2) 

Because this gate is commented out, `bIndirectCorrespondent` is effectively ignored for the rest of `doHandle()`, and every `case` in the giant `switch(subject)` block is reachable from an indirect correspondent exactly as from a fully-paired one [4](#0-3) . This mirrors the reported bug class: a security gate (`Permissions::skip()` in the PHP report; the indirect-correspondent whitelist here) is disabled, so an operation set intended to be restricted to a trusted principal is processed for an untrusted one via a single message/request.

### Impact Explanation
An indirect correspondent is an address the local wallet has never explicitly paired with or vetted — it is added automatically from data supplied by a *different*, already-paired correspondent (e.g., the list of `other_cosigners` in a `create_new_wallet` offer, see `handleOfferToCreateNewWallet()` at `wallet_defined_by_keys.js` lines 65-111, or `arbiter_contract_offer` at `wallet.js` lines 617-655/865-940). Any correspondent can therefore introduce an arbitrary attacker-controlled device address/pubkey as your "indirect correspondent" and have it treated as trustworthy for follow-on messages. With the whitelist disabled, that attacker-controlled device can then send messages such as:
- `new_wallet_address` — silently inject derived addresses into a shared wallet's bookkeeping (`addNewAddress()` in `wallet_defined_by_keys.js` lines 415-430) if it can also guess/derive a matching address, potentially confusing wallet address tracking.
- `arbiter_contract_offer` / `arbiter_contract_response` / `arbiter_contract_update` — forge or corrupt arbiter contract state tied to shared addresses that hold funds, since some of these code paths only check `from_address` against the stored `peer_device_address`/cosigner records rather than requiring that the device be a *directly paired* correspondent.
- `create_new_shared_address` / `sign` — trigger UI confirmation flows or signing requests that a user may approve believing the request came from a legitimately paired device.

This can lead to fund-related state corruption or unauthorized contract/wallet state changes in the AA/wallet flows that ultimately drive on-chain payments, satisfying the "AA fund loss/freezing" / unauthorized spending impact category, since arbiter/prosaic contracts culminate in real payment units.

### Likelihood Explanation
Reaching this requires only: (1) being a paired correspondent of some user's wallet at some point, so as to be named as an `other_cosigners`/`peer_device` entry, thereby getting auto-registered as `is_indirect=1` in a third party's `correspondent_devices` table, and (2) sending a single crafted `hub/message` with the disabled subject. No special network position, race condition, or cryptographic break is required — the device-message signature/encryption checks in `device.js`/`network.js` are otherwise satisfied normally by any registered device keypair. This is a low-complexity, single-message trigger, matching the "unprivileged... paired device" reachability required by the task.

### Recommendation
Re-enable and generalize the indirect-correspondent restriction in `wallet.js`'s `handleMessageFromHub()`, explicitly whitelisting only the minimal subjects that are safe to accept from devices that were never directly paired (e.g., `my_xpubkey`, `wallet_fully_approved`, `cancel_new_wallet`), and reject all other subjects (`new_wallet_address`, `arbiter_contract_*`, `create_new_shared_address`, `sign`, etc.) from `bIndirectCorrespondent === true` senders, consistent with the intent already documented in the comment.

### Proof of Concept
1. Attacker Mallory pairs with victim Alice as a normal correspondent (e.g., via a chat/contact exchange) — no cosigner relationship required from Alice's perspective yet.
2. Mallory (or a colluding party) gets included as an `other_cosigners` entry in a `create_new_wallet` offer or as `peer_address`/`arbiter_address` in an `arbiter_contract_offer` sent to Alice by any correspondent Bob (Bob does not need to be malicious; Mallory just needs to be named). This causes Alice's node to call `addIndirectCorrespondents()`, inserting Mallory's device as `is_indirect=1` in `correspondent_devices` [1](#0-0) .
3. Mallory now sends Alice a `hub/message` with `subject: "arbiter_contract_update"` (or `new_wallet_address`, etc.) directly. Because the whitelist check in `wallet.js` is commented out, Alice's node processes it as if Mallory were a fully-paired, trusted correspondent [3](#0-2) , reaching the corresponding contract/wallet-state-mutating logic without the intended "indirect correspondent" barrier.
