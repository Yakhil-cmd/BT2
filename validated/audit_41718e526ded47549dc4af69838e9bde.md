### Title
Webhook signature verification key is selected by an unverified field, letting a request claiming a secret-less GitHub organization forge events (push/status) that are applied to a different, secured repository/stack - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks *which* `webhook_secret` to validate the HMAC signature against by reading `repository_owner` straight out of the still-unauthenticated JSON body, then compares the whole raw body against that org's secret [1](#0-0) [2](#0-1) . `GitHubApp#verify_webhook_signature` treats a blank/unset `webhook_secret` as an automatic pass: `return true unless webhook_secret` [3](#0-2) . Shipit's own multi-organization config format documents `webhook_secret` as optional per organization [4](#0-3) [5](#0-4) , so a real, supported deployment can legitimately have one configured organization with no secret alongside other organizations that do have one.

### Finding Description
The equality that is supposed to hold is:
`organization whose secret authenticated this request == organization/repository whose state is written by the handler`

`repository_owner` (used only to *select the verification key*) and `repository_name`/commit lookups (used by the handlers to *decide what to mutate*) are both read from the same unauthenticated JSON body, but nothing enforces that they are consistent, and nothing prevents `repository_owner` from naming an organization configured with `webhook_secret: nil`:

- `WebhooksController#verify_signature` resolves the app/secret via `Shipit.github(organization: repository_owner)` where `repository_owner = params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` — a value taken from the body before any signature has been proven valid [6](#0-5) .
- If that organization's `webhook_secret` is blank, `verify_webhook_signature` unconditionally returns `true`, i.e. *any* raw body is accepted as "verified" for that org [3](#0-2) .
- Once verification "passes", the request is dispatched to handlers keyed off `event`, which parse the rest of the same body independently of `repository_owner`:
  - `Handlers::Handler#repository_name` reads `payload.dig('repository', 'full_name')` to resolve `stacks` (via `Repository.from_github_repo_name`) [7](#0-6) .
  - `PushHandler#process` uses those `stacks` plus attacker-controlled `ref`/`after` to enqueue a sync against a real stack's git ref [8](#0-7) .
  - `StatusHandler#process` does not use `repository_name`/`stacks` scoping at all — it updates status directly from `Commit.where(sha: params.sha)`, i.e. any commit row matching an attacker-supplied `sha`, regardless of which repository the "verified" organization actually owns [9](#0-8) .

So the field that is used to pick and satisfy the trust check (`repository.owner.login`, pointing at an org with no secret) is never bound to the field(s) that determine the actual write target (`repository.full_name`, or the raw commit `sha`). This is directly analogous to the `exp()` finding: the portion of the computation that is checked/approximated (signature verification keyed on one field) diverges from the portion that is actually acted upon (state mutation keyed on other fields in the same payload), and the divergence is large exactly in the region an attacker controls (any organization without a configured secret).

### Impact Explanation
An unprivileged external actor — with no `webhook_secret`, no `ApiClient` token, and no repository write access — can:
- Forge a `push` webhook naming a secret-less organization while pointing `repository.full_name` at a different, secured stack, causing `GithubSyncJob`/deploy-eligibility state to be driven by attacker-chosen `ref`/`after` values [8](#0-7) .
- Forge a `status` webhook (again authenticated only against a secret-less organization) that writes a fabricated CI status onto any `Commit` row matching a known `sha`, since `StatusHandler` performs no repository/organization scoping [9](#0-8) . Forged "success" statuses can satisfy merge/deploy gating checks that stacks rely on, leading to an unauthorized deploy or merge — a Critical-tier impact per the engine's own trust model.

This qualifies under "unauthorized deploy, rollback, or merge" because the write path (stack sync, commit status used for gating) is reached without any valid credential for the organization/repository actually being mutated.

### Likelihood Explanation
Requires only a multi-organization Shipit deployment (a documented, supported configuration) where at least one configured organization has no `webhook_secret` set — itself a documented default/optional setting, not a misconfiguration outside the engine's design [5](#0-4) . No secret, token, or session is needed by the attacker; only the ability to POST to the public `/webhooks` endpoint with a crafted JSON body and a matching `X-Github-Event` header.

### Recommendation
Bind the key used for signature verification to the same field(s) that determine the write target, and never treat a missing `webhook_secret` as an implicit pass once any organization in the install has a secret configured. Concretely: resolve `repository_owner` only after verifying against a canonical, immutable server-side registry rather than trusting `repository.owner.login`/`organization.login` from the unauthenticated body, and re-validate inside each handler that `payload.dig('repository','full_name')`'s owner segment matches the organization whose secret produced a successful verification.

### Proof of Concept
1. Deploy Shipit in multi-org mode with `OrgSecretless` (no `webhook_secret`) and `OrgSecured` (`webhook_secret: <real secret>`), each with stacks/repositories configured — mirrors the documented setup in `docs/setup.md` "Using Multiple Github Applications" and `test/dummy/config/secrets_double_github_app.yml`.
2. POST to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "repository": {"owner": {"login": "OrgSecretless"}, "full_name": "OrgSecured/victim-repo"},
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>"
}
```
No `X-Hub-Signature` (or any arbitrary value) is required, since `WebhooksController#verify_signature` resolves `Shipit.github(organization: 'OrgSecretless')` whose `verify_webhook_signature` returns `true` unconditionally.
3. `PushHandler#process` resolves stacks from `repository.full_name` = `OrgSecured/victim-repo` and enqueues `GithubSyncJob` for that stack using the attacker-supplied `after` sha, even though the request was never authenticated against `OrgSecured`'s secret.

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",

        "status=#{status}"
      ].join(' '))

      ].join(' '))
    end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
