### Title
ERC20Transactor withdraw/deposit treats a completed-but-undecodable ERC20 return as failure without reverting the underlying token transfer, causing user funds to be stranded in the checking account - ([File: cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs])

### Summary
`ERC20Transactor::withdraw_asset_with_surplus` and `deposit_asset_with_surplus` execute a real `IERC20::transferCall` via `pallet_revive::Pallet::<T>::bare_call`, then classify the outcome purely by ABI-decoding the return data as a `bool`. A non-standard ERC20 (the exact class described in the referenced report: real USDT and similar tokens whose `transfer` returns no boolean) will execute the transfer successfully on-chain (no revert, balance actually moves), but `abi_decode_returns_validate` on the empty/incompatible return data fails, so the code returns `XcmError::FailedToTransactAsset("ERC20 contract result couldn't decode")` [1](#0-0) . The already-executed token transfer to the checking account is not rolled back by this Rust-level `Err` return, while the XCM executor treats the asset as never having entered holding.

### Finding Description
`withdraw_asset_with_surplus` performs the withdrawal by issuing a low-level `transfer(checking_address, amount)` call against the registered ERC20 contract via `pallet_revive::Pallet::<T>::bare_call` [2](#0-1) . If the call does not revert, the code assumes the return data must decode as a `bool` and only credits `AssetsInHolding` on `Ok(true)`; any decode error (e.g., because the token, like USDT, returns no data at all) is mapped to `XcmError::FailedToTransactAsset` [3](#0-2) . The `deposit_asset_with_surplus` path has the identical pattern for outbound transfers from the checking account to the beneficiary [4](#0-3) .

Crucially, `bare_call` is a genuine EVM-style call into `pallet_revive` state: for a non-compliant contract that does not revert, the transfer effect (real ERC20 balance debit/credit) has already happened in contract storage before the Rust code inspects the return bytes. Returning `Err(XcmError::FailedToTransactAsset(...))` from `withdraw_asset_with_surplus`/`deposit_asset_with_surplus` does not by itself undo that contract-storage mutation — it only tells the XCM executor "no asset entered/left holding." This is precisely the analog of the reported bug class: code that assumes an ERC20-standard boolean return value, applied here to a real, already-committed pallet-revive contract call rather than a purely reverting Solidity `IERC20` interface call. The maintainers themselves acknowledge non-compliant tokens are expected to be rejected (see the test `smart_contract_does_not_return_bool_fails` / `smart_contract_not_erc20_will_error`) [5](#0-4) , but those tests only assert that `PolkadotXcm::execute(...).is_err()`; they never assert that the checking account's real ERC20 balance is unaffected, i.e., they do not verify the transfer itself was rolled back.

I was not able to fully confirm, within the available tool budget, whether `pallet_xcm`/`xcm-executor` wraps the whole XCM program (or at least each `TransactAsset` call) in a `frame_support::storage::with_transaction` that would automatically roll back the `pallet_revive` contract-storage mutation performed inside `bare_call` when `withdraw_asset_with_surplus` subsequently returns `Err`. If such a wrapping transaction exists and covers the inner `bare_call` state changes, the underlying ERC20 transfer would be reverted along with the XCM error, and the described fund-loss impact would not materialize (the situation would degrade to a "denial of service for compliant transfers of this asset" issue instead, matching Sherlock's Medium/Low classification rather than fund loss). Given this open verification gap, I cannot assert with confidence that funds are irrecoverably stranded — this is the key uncertainty limiting the finding to a "supported analog with unresolved rollback question" rather than a proven High-severity theft/freezing bug.

### Impact Explanation
If the surrounding XCM execution is not fully transactional over the inner `pallet_revive::bare_call` state changes, then any asset registered through `ERC20Transactor` whose underlying token contract does not strictly return an ABI `bool` from `transfer` (the well-documented USDT-style non-compliance from the source report) will have real balance moved into/out of the `TransfersCheckingAccount` on every attempted XCM withdraw/deposit, while the XCM message itself fails and the counterparty side of the transfer (holding credit, or beneficiary deposit) never happens. Repeated attempts would continue draining/misplacing balances into the checking account with no compensating credit, which is a direct value-loss/fund-freezing scenario for users of that asset class.

### Likelihood Explanation
Likelihood depends entirely on (a) whether such non-boolean-return ERC20 contracts can actually be registered as fungible assets reachable through this transactor's `Matcher: MatchesFungibles` configuration in a live runtime, and (b) whether the surrounding transactional guarantees roll back the inner contract call. Both preconditions require confirmation I could not complete. The maintainers' own tests demonstrate awareness of the non-compliant-return scenario and its user-visible failure mode, which increases confidence the code path is real and reachable through ordinary permitted XCM `execute`/transfer flows (no privileged role required) [6](#0-5) .

### Recommendation
- Wrap the `bare_call` invocation and the subsequent decode/classification logic in `withdraw_asset_with_surplus` and `deposit_asset_with_surplus` in an explicit `frame_support::storage::with_transaction` so that any `Err` path (decode failure, `did_revert()`, or execution error) deterministically rolls back the contract-storage effects of the `transfer` call, matching the semantics already used elsewhere for `permit` in `substrate/frame/assets/precompiles/src/lib.rs` [7](#0-6) .
- Add a test that, after a non-compliant-return-value `transfer`, asserts the checking account's/beneficiary's actual ERC20 balance is unchanged (not just that `PolkadotXcm::execute` returns `Err`), closing the verification gap identified above.

### Proof of Concept
Not executed. I traced the code path via static review only (`erc20_transactor.rs` withdraw/deposit logic and the existing `tests.rs` non-compliant-contract tests) and did not run a local reproduction confirming whether the `pallet_revive` contract-storage mutation from the inner `transfer` call survives the outer `XcmError` return. This is the decisive open question for whether this analog is exploitable fund loss versus a benign (already-tested) failed-transfer denial-of-service; I could not resolve it within the available iterations and am flagging it explicitly rather than asserting a conclusion.
