### No vulnerability found for this question.

**Reasoning:**

The claim that `handler.call(params)` receives attacker-supplied JSON "with no relation to session[:user_id] or any authenticated GitHub identity" is incorrect for two independent reasons:

1. **Signature verification precedes dispatch.** `WebhooksController#create` only runs after the `verify_signature` before_action, which computes an HMAC-SHA1 over `request.raw_post` using the configured `webhook_secret` for the resolved `repository_owner`/`organization` and compares it via `SecureCompare.secure_compare`, returning `422` on mismatch [1](#0-0) . `verify_webhook_signature` performs this HMAC check against `GithubApp#webhook_secret` [2](#0-1) . So for a repository with a configured `webhook_secret`, the equality the binding requires — `payload as delivered == payload GitHub signed` — is enforced before any handler sees `params`. An attacker without the secret cannot forge `sender.login`, `repository.full_name`, etc.

2. **No handler uses `sender.login` as an authorization/approval signal.** Auditing all `sender` usages across the `pull_request` handlers, the only place `params.sender` is read is `ReviewStackAdapter#user`, which uses it purely to attribute *who* triggered `stack.archive!`/`unarchive!` (an audit-log field passed into the state-transition call), not to grant permission [3](#0-2) . The actual gating logic for provisioning/archiving review stacks is driven by `repository.review_stacks_enabled`, `repository.provisioning_behavior_allow_all?`/`_allow_with_label?`/`_prevent_with_label?`, and PR label membership — all sourced from `Repository` configuration and the PR's real label set (which requires write/triage access on the target repo to mutate on GitHub, not available to an unprivileged fork-only attacker) [4](#0-3) [5](#0-4) . No handler (`opened`, `closed`, `reopened`, `labeled`, `unlabeled`, `assigned`, `edited`, `label_capturing`) uses `sender.login` for merge approval or any other authorization-sensitive decision — a grep across all `.rb` handler files found `sender` used only for `login` requirement schemas and the single attribution call above [6](#0-5) .

Since (a) the signature check binds the payload's authenticity to GitHub's HMAC before any handler executes, and (b) no handler treats `sender.login` as an authorization/approval identity, the equality the question hypothesizes as broken does not diverge in this codebase. There is no `handler.rb` that "trusts `params.dig('sender','login')` as an approver identity" for auto-merge or any privileged action.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
