## Title
Webhook signature is verified against the organization named in an unauthenticated payload field, but a different unauthenticated field (`repository.full_name`) is trusted to select which repository/stack is acted upon - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App / webhook secret to verify a request against using `repository_owner`, taken from the *same* untrusted JSON body it is about to verify. All downstream event handlers, however, resolve the target `Stack`/`Repository` using a completely different field from that same body: `repository.full_name`. Nothing ties these two fields together, so a party who legitimately controls the webhook secret for *one* configured organization can forge a signed payload whose `repository.owner.login` matches their own org (so it passes signature verification) while `repository.full_name` names a repository belonging to a *different* configured organization, causing Shipit to act on that other organization's stacks.

### Finding Description
The controller picks the app/secret used for verification from an attacker-controlled JSON field before any authenticity check has occurred: [1](#0-0) [2](#0-1) 

`repository_owner` reads `params.dig('repository', 'owner', 'login')` straight out of the raw POST body. `Shipit.github(organization: repository_owner)` then loads that organization's `GitHubApp` config, and `verify_webhook_signature` is checked against it: [3](#0-2) 

Critically, if that organization has no `webhook_secret` configured, verification is skipped entirely (`return true unless webhook_secret`), and even when a secret is configured, all this proves is that the payload was signed by *someone who knows organization A's secret* — it says nothing about which repository the payload actually targets.

Every event handler, however, derives the actual target repository/stack from a second, independent field of the same JSON body — `repository.full_name` — with no cross-check against `repository.owner.login`: [4](#0-3) [5](#0-4) [6](#0-5) 

Because `repository_owner` (used for authentication) and `repository.full_name` (used for authorization/routing) are two unrelated fields inside the same forgeable body, there is no code that enforces `full_name.split('/').first == repository_owner`. A user who is entitled to configure/know organization A's GitHub App webhook secret (a normal, low-privilege action scoped to their own org) can craft and sign a payload where `repository.owner.login = "org-a"` (satisfies `verify_signature`) but `repository.full_name = "org-b/victim-repo"` (consumed by the handler), causing Shipit to process webhook events — pushes, pull-request opens/labels/closes, statuses, merges — against `org-b`'s stacks, which they have no authorization over.

This is the exact class of bug the report describes: a value used to satisfy an authentication/trust check (Stargate router address / here, `repository_owner` used to pick the verifying secret) is not the same value that is subsequently acted upon (destination token transfer target / here, `repository.full_name` used to select the acted-upon repository), breaking the intended binding between "the organization that authenticated" and "the repository that is written."

### Impact Explanation
Depending on the handler triggered, this can cause cross-repository writes on stacks belonging to an organization the attacker does not control: forged `push` events can trigger `GithubSyncJob`/`sync_github` on another org's stack (potentially feeding continuous-deployment pipelines with attacker-chosen `expected_head_sha`), forged `pull_request` events can provision/archive/unarchive review stacks, and forged `status`/`membership` events can manipulate commit statuses or team membership used for authorization decisions. This matches the "cross-repository writes" / "unauthorized deploy or rollback" impact tier.

### Likelihood Explanation
Exploitation requires the attacker to control (or know) the webhook secret of at least one organization already configured in the Shipit instance — a routine, low-privilege capability for any tenant/org onboarded onto a multi-organization Shipit deployment (`Shipit.github_organizations`, `config/secrets.*.yml` `github:` keys) — and for a targeted repository belonging to another configured organization to already exist in Shipit. This is realistic in any multi-tenant deployment where several organizations' GitHub Apps are registered against the same Shipit instance.

### Recommendation
After computing `repository_owner` for signature-selection purposes, re-validate that the same `repository.full_name`/`organization.login` in the verified payload actually belongs to that organization (e.g., assert `full_name.split('/', 2).first.casecmp?(repository_owner)`) before dispatching to handlers, or bind each configured `Repository` to a single expected organization and reject events whose `repository.owner.login` doesn't match the `Repository`'s configured organization.

### Proof of Concept
1. Shipit is configured with two organizations, `org-a` and `org-b`, each with its own `webhook_secret` (`config/secrets.*.yml` → `github.org-a.webhook_secret`, `github.org-b.webhook_secret`), per [7](#0-6) .
2. Attacker knows `org-a`'s webhook secret (e.g., they administer `org-a`'s GitHub App).
3. Attacker crafts a `push` payload:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>",
  "repository": { "owner": { "login": "org-a" }, "full_name": "org-b/victim-repo" }
}
```
4. Attacker computes `X-Hub-Signature: sha1=HMAC(org-a-webhook-secret, body)` and POSTs to `/webhooks`.
5. `verify_signature` resolves `repository_owner == "org-a"`, loads `org-a`'s `GitHubApp`, and the signature checks out — request passes with `head(:ok)` instead of `422`.
6. `PushHandler#process` resolves the target stacks via `payload.dig('repository', 'full_name') == "org-b/victim-repo"` (per [8](#0-7) ), and calls `stack.sync_github(expected_head_sha: ...)` on `org-b`'s stack — an org the attacker never authenticated against.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
