### Title
Unrestricted `inherit_from` path resolution allows path traversal / absolute-path arbitrary file read in `DeploySpec::FileSystem#build_config` - (File: app/models/shipit/deploy_spec/file_system.rb)

### Summary
`DeploySpec::FileSystem#build_config` resolves the attacker-controlled `inherit_from` key with `path.dirname.join(config_obj.delete(SHIPIT_CONFIG_INHERIT_FROM_KEY))` and never verifies the result stays inside `@app_dir`. Because `Pathname#join` returns the argument unchanged when it is absolute, and otherwise honours `..` segments, an attacker who controls a `shipit.yml`/`.shipit/*.yml` file checked out onto the deploy host can point `inherit_from` at an arbitrary absolute path or a relative path with `../` traversal, and if the target is YAML that parses to a Hash, its contents are `deep_merge`d into the effective spec that later feeds `deploy.override` / `tasks.*.steps` executed via `Command#start`.

### Finding Description
The broken binding: `inherits_from_path == path_within(@app_dir)` is expected but not enforced; in reality `inherits_from_path = path.dirname.join(config_obj.delete("inherit_from"))` can equal any filesystem path reachable by the Shipit process. [1](#0-0) 

`config_file_path`/`path` originates from a fresh checkout of a specific commit (`file(filename, root: true)` under `@app_dir`), and `config_obj` is whatever YAML the commit's `shipit.yml` contains — fully attacker-controlled if the attacker can get a commit checked out (e.g. via `EphemeralCommitChecks`, which checks out an arbitrary commit into a temp directory and instantiates `DeploySpec::FileSystem.new(directory, stack)` before running `dependencies_steps`/`review_checks`). [2](#0-1) [3](#0-2) 

`build_config` neither restricts `inherits_from_path` to descend from `@app_dir` nor rejects absolute paths, and it recurses (`build_config(path, config_obj)`), so the traversal/absolute reference is followed as long as `inherits_from_path.exist?` and the file parses. `read_config` just does `SafeYAML.load(path.read)` with no path containment check. [4](#0-3) 

Exploit flow: attacker sets `inherit_from: /etc/some_readable_yaml_file` (absolute path bypasses the `path.dirname` entirely due to `Pathname#join` semantics) or `inherit_from: ../../../../some/other/checkout/shipit.yml` (relative traversal) in a commit that gets checked out for commit checks. If the target happens to be a Hash-shaped YAML document, its keys are merged into the effective config (attacker's own keys win via `deep_merge`'s argument order), and any `deploy.override`/`tasks.*.steps`/`review.checks` values ultimately reach `Command#start`/`PTY.spawn` when the check/deploy runs.

### Impact Explanation
Confirmed as a genuine path-containment failure: `build_config` performs no validation that `inherits_from_path` remains within `@app_dir`. The severity is bounded by the requirement that the target file be reachable, existing, and parse as a YAML mapping (otherwise `deep_merge` raises `NoMethodError`, aborting the check). Within that constraint, this permits: (a) disclosure of the mere existence/YAML-hash content of arbitrary host files reachable by the Shipit process, and (b) if the target is another stack's cached `shipit.yml` (or any YAML file containing `deploy`/`tasks`/`review` keys) whose location an attacker can predict or reach via traversal, cross-tenant configuration/step blending into the attacker's own commit-check execution. This does not, by itself, prove exfiltration of `GITHUB_TOKEN`/`api_clients_secret` or forged authentication, since those are typically process environment variables, not YAML files on disk, and there is no evidence in this engine that such secrets are persisted as YAML files under paths reachable from checkout directories.

### Likelihood Explanation
Preconditions: attacker must be able to get a commit with a crafted `shipit.yml` checked out and evaluated (e.g. via a pull request that triggers `EphemeralCommitChecks`/`CommitChecks`), and a suitable YAML-Hash target file must exist at a path they can guess or traverse to. No Shipit session, API token, or maintainer privileges are required to open the PR itself. The dependency on a coincidentally-parseable target file at a known/guessable path is the main limiting factor for weaponizing this beyond information disclosure.

### Recommendation
In `build_config`, resolve `inherits_from_path` with `File.expand_path` (or `Pathname#realpath`) and assert it is a descendant of `@app_dir` (e.g. `inherits_from_path.to_s.start_with?(@app_dir.to_s + File::SEPARATOR)`) before calling `read_config`; reject/ignore `inherit_from` values that escape the checkout root, and reject absolute paths outright.

### Proof of Concept
Add to `test/models/shipit/deploy_spec/file_system_test.rb` (mirroring the existing "`#load_config` builds proper config if `inherit_from` is present" test):
1. Create an `@app_dir` fixture with a `shipit.yml` containing `inherit_from: "../../../../tmp/outside_target.yml"` (or an absolute path to a temp file created via `Tempfile`), where `outside_target.yml` lives outside `@app_dir` and contains `deploy: { override: ["echo leaked"] }`.
2. Instantiate `DeploySpec::FileSystem.new(app_dir, stack)` and call `#build_config`/`#load_config`.
3. Assert whether `spec.deploy_steps` (or the merged config) includes `"echo leaked"` — proving the traversal was followed and content outside `@app_dir` was merged, versus the expected/fixed behavior where `inherits_from_path.exist?` should be `false` because the path is rejected as outside `@app_dir`.

      SHIPIT_CONFIG_INHERIT_FROM_KEY = "inherit_from"
      def build_config(path, config_obj)
        return config_obj if config_obj.blank? || !config_obj.key?(SHIPIT_CONFIG_INHERIT_FROM_KEY)

        inherits_from_path = path.dirname.join(config_obj.delete(SHIPIT_CONFIG_INHERIT_FROM_KEY))
        if inherits_from_path.exist?
          inherits_config_obj = read_config(inherits_from_path)
          config_obj = inherits_config_obj.deep_merge(config_obj)
          path = inherits_from_path
        end

        build_config(path, config_obj)
      end
