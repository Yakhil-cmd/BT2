### Title
Delimiter injection in `arbiter_contract.getHashSrc` allows hash collisions between different contract terms - (File: `arbiter_contract.js`)

### Summary
`arbiter_contract.getHashSrc()` builds the source string that is hashed to produce a contract's identity (`getHash()`) by joining several fields — including the attacker/peer-controlled `title` and `text` — with a fixed, unescaped delimiter `exports.DELIMITER = "[|#|]"` [1](#0-0) . Because `title`/`text` are only validated to be non-empty strings, and are never checked for the presence of the delimiter sequence, a counterparty can embed the delimiter (and forged subsequent "fields") inside `title` or `text` to shift the positions of the remaining joined fields (`payer_address`, `arbiter_address`, `amount`, `asset`, etc.), producing the same SHA-256 hash for two contracts with different real terms. This is the same bug class as the Hats.sol report: unsanitized attacker-controlled strings are concatenated into a structured/delimited format without escaping, letting the attacker "break out" of the intended field boundaries and inject/alter downstream-interpreted data.

### Finding Description
`getHashSrc` computes:
```js
[contract.title, contract.text, contract.creation_date, payer_address, payer_name || '', contract.arbiter_address, payee_address, payee_name || '', contract.amount, contract.asset || 'null'].join(exports.DELIMITER)
``` [2](#0-1) 

`title` and `text` are supplied by the contract-offering peer and are only checked with `ValidationUtils.isNonemptyString` (no length/character restriction, no check that they don't contain `exports.DELIMITER`) before the hash is verified and the contract is stored:
```js
if (![body.title, body.text, body.my_pairing_code].every(ValidationUtils.isNonemptyString))
    return callbacks.ifError("wrong required fields");
...
if (body.hash !== arbiter_contract.getHash(body))
    return callbacks.ifError("wrong contract hash");
``` [3](#0-2) 

Because `join(exports.DELIMITER)` has no escaping of the delimiter inside individual fields (unlike `getSourceString`/`getJsonSourceString` in `string_utils.js`, which explicitly reject strings containing the internal join character to prevent exactly this class of ambiguity [4](#0-3) ), an attacker who controls `title` or `text` can insert the literal substring `[|#|]` plus crafted extra tokens. This shifts which substrings are interpreted as `payer_address`, `arbiter_address`, `amount`, `asset`, etc., when the same hash is later recomputed by the counterparty or by the arbstore/dispute code, or — more importantly — makes it possible to construct two different `objContract` payloads (different real amount/party/arbiter fields, hidden inside the "extra" delimiter-separated tokens absorbed into `title`/`text`) that hash to the identical value.

This same `getHash()`/`getHashSrc()` is relied upon as an integrity check in multiple places: verifying `arbiter_contract_offer` and `arbiter_contract_shared` messages, and — critically — reconstructing the expected contract hash from a decrypted dispute payload during `arbiter_dispute_request` handling:
```js
var expectedContractHash = arbiter_contract.getHash({
    title: contractContent.title,
    text: contractContent.text,
    ...
});
if (body.contract_hash !== expectedContractHash)
    return callbacks.ifError("wrong contract hash");
``` [5](#0-4) 

### Impact Explanation
The contract hash is the canonical identity of an arbiter/escrow agreement between two mutually untrusted counterparties (payer/payee) and is used to authenticate offer/shared/dispute messages without re-verifying every individual field independently. If a malicious counterparty can construct two distinct contract payloads that collide on this hash (by absorbing delimiter+forged-field content into `title`/`text`), the attacker can present a hash that was agreed/signed for one set of terms while the stored/displayed record — or the terms later used during the arbiter dispute-resolution flow, where `expectedContractHash` is recomputed from a decrypted payload and compared against the on-chain-referenced `body.contract_hash` — reflects a different amount, arbiter, or party assignment. This can misdirect fund disputes/escrow outcomes between the private-payment counterparties, i.e., cause loss/misdirection of escrowed funds or corrupt the arbiter's view of the true contract terms, which is a concrete impact in the "private payment chains / private-payment counterparty" reachable surface.

### Likelihood Explanation
The attacker only needs to be one of the two contract counterparties (or the peer offering the contract) — no special privileges, hub/node compromise, or network position are required. The `title` (VARCHAR(1000)) and `text` (TEXT) fields are attacker-controlled free text with no delimiter-escaping and are directly usable in normal wallet flows (`arbiter_contract_offer`, `arbiter_contract_shared`, dispute request) [3](#0-2) . Constructing a delimiter collision requires only string crafting (choosing `title`/`text` values containing `[|#|]` sequences); it does not require breaking SHA-256, only exploiting the ambiguity of an unescaped join.

### Recommendation
Escape/validate `title` and `text` (and all other fields fed into `getHashSrc`) so they cannot contain the delimiter sequence `exports.DELIMITER`, or switch to a canonical, length-prefixed / JSON-based hashing scheme analogous to `getSourceString`/`getJsonSourceString` in `string_utils.js`, which already reject strings containing the internal separator character specifically to prevent this ambiguity [6](#0-5) . Reject any contract offer/shared/dispute payload whose `title` or `text` contains the delimiter before computing or verifying the hash.

### Proof of Concept
1. Attacker A crafts an `arbiter_contract_offer` where `text` = `"normal text" + "[|#|]" + "<attacker-forged-alt-amount>" + "[|#|]" + "<attacker-forged-alt-asset>"` and other real fields (real `amount`, `arbiter_address`) chosen so that `getHashSrc()`'s concatenation of `[title, text, creation_date, payer_address, payer_name, arbiter_address, payee_address, payee_name, amount, asset]` is byte-identical to the concatenation for a second, legitimately-different contract B (different real `amount`/`arbiter_address`, with the difference "absorbed" into B's shorter `text`).
2. Both contracts A and B hash to the same SHA-256 value via `getHash()` [7](#0-6) .
3. `wallet.js`'s `arbiter_contract_offer`/`arbiter_contract_shared`/`arbiter_dispute_request` handlers only check `body.hash === arbiter_contract.getHash(body)` [8](#0-7) [9](#0-8) , so either payload passes validation under the same hash, letting the attacker later present or reference the contract with the terms that favor them (e.g., during dispute resolution) while the counterparty/arbiter believes the hash certifies the other set of terms.
