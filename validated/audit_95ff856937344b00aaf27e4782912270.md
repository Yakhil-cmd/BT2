### Title
CCMenu API scoped-token bypass allows reading any stack's build/deploy state - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::CCMenuController` overrides the `stack` lookup to bypass the stack-scoping enforced by `BaseController`, letting a token that is only authorised for one specific stack read the CCMenu deploy status of *any* stack in the installation.

### Finding Description
In `Shipit::Api::BaseController`, permission checks and stack lookups are supposed to work together: `stacks` restricts the visible stack set to the token's bound stack when `current_api_client.stack_id?` is true, and `stack` resolves the requested `:stack_id` param from that restricted scope: [1](#0-0) . `require_permission!` only checks whether the token carries the named `operation:scope` permission string (e.g. `read:stack`); it does not verify that the requested stack matches the token's bound stack: [2](#0-1)  and [3](#0-2) . The stack-binding equality the token is supposed to preserve is therefore: `token.stack_id == requested_stack.id` whenever `token.stack_id?` is true, enforced solely through the `stacks`/`stack` scoping helpers in `BaseController`.

`CCMenuController` breaks that binding by redefining `stack` to resolve directly from the global `Stack` table instead of from the scoped `stacks`: [4](#0-3) 

Because `show` calls this overridden `stack` (not the inherited scoped one), and `require_permission :read, :stack` only checks the generic `read:stack` permission string on the token, any token that has `read:stack` — even one created and scoped to a single stack via `CCMenuUrlController` — can be replayed against `api_stack_ccmenu_url` with a different `stack_id` to fetch another stack's deploy/rollback state: [5](#0-4) . Tokens of this kind are routinely minted with a `stack_id` binding via `CCMenuUrlController#client`, which creates an `ApiClient` scoped only by `permissions: %w[read:stack]` and `creator:` — critically, without binding it to the specific `stack` the token URL was generated for: [6](#0-5) . Even if a future fix bound the created `ApiClient` to a `stack`, the `CCMenuController#stack` override would still ignore that binding.

### Impact Explanation
An attacker who legitimately obtains a CCMenu token for one stack (any stack they can view via `CCMenuUrlController#fetch`) can use that same token to read the deploy/rollback status (id, revision, running state, ended_at) of every other stack in the Shipit installation, including private/restricted stacks they have no `read:stack` grant for. This is an unauthorized read of stack/deploy state across a repository/stack authorization boundary — matching the "unauthenticated/unauthorized read of stack state, task streams or deploy output" High-severity class, since the token's authorization for stack A is being used to touch stack B.

### Likelihood Explanation
High. Any user with read access to at least one stack can generate a CCMenu token via the existing `/ccmenu_url` endpoint, and the only additional step is substituting a different `stack_id` in the resulting CCMenu API URL — no additional privileges, signatures, or GitHub credentials are required.

### Recommendation
Remove the `stack` override in `Shipit::Api::CCMenuController` (or reintroduce scoping) so it resolves through the inherited, token-scoped `stacks` collection from `BaseController` (`stacks.from_param!(params[:stack_id])`) instead of the unscoped `Stack.from_param!`. Additionally, `CCMenuUrlController#client` should bind the created `ApiClient` to the specific `stack` for which the URL was generated, so the token cannot later be reused for unrelated stacks even outside the CCMenu controller.

### Proof of Concept
1. A legitimate user calls `GET /stacks/:stack_a_id/ccmenu_url` (`CCMenuUrlController#fetch`), which creates/reuses an `ApiClient` with `permissions: ['read:stack']` (no stack binding) and returns a CCMenu URL containing that client's `authentication_token` for `stack_a`.
2. The attacker (or the same user acting maliciously) takes that token and issues `GET /api/stacks/:stack_b_id/ccmenu.xml?token=<token>` for an arbitrary `stack_b` they are not authorized to view.
3. `CCMenuController#authenticate_api_client` authenticates the token successfully (`ApiClient.authenticate`), `require_permission :read, :stack` passes because the token carries `read:stack`, and `stack` resolves `stack_b` directly via `Stack.from_param!(params[:stack_id])` — bypassing any per-stack scoping — returning `stack_b`'s deploy/rollback status in the CCMenu XML response.
