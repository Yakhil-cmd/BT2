### Title
Webhook signature verified against attacker-controlled organization while payload actions target a different, unverified repository - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/webhook secret to verify the HMAC signature against using a value taken directly from the *unauthenticated request body* (`repository_owner`), rather than from any value covered by the signature's trust context. The actual repository/stack that the webhook event acts on is derived later, independently, from a different body field (`repository.full_name`) inside each `Handler`. Nothing cross-checks that the organization used to select the verification secret is the same organization that owns the repository being written to.

### Finding Description
`verify_signature` picks the `GitHubApp` (and thus the webhook secret used for HMAC verification) using:
```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) 
and
```ruby
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
head(422) unless verified
``` [2](#0-1) 

Both `repository.owner.login` and `organization.login` are plain JSON fields inside the raw request body — they are not covered by any cryptographic binding to the actual repository that will be processed. `Shipit.github(organization:)` resolves the corresponding webhook secret purely by string/downcase match against `Shipit.secrets.github` keys: `github_app_config` at [3](#0-2)  and `github` at [4](#0-3) . Critically, `verify_webhook_signature` treats an org with no configured secret as automatically verified: `return true unless webhook_secret` [5](#0-4) , and `webhook_secret` is explicitly documented as optional per organization in the multi-org setup: `webhook_secret:` under each org entry [6](#0-5) .

Once `verify_signature` passes, `create` dispatches to `Handler` subclasses that determine the target repository/stack using an entirely separate field:
```ruby
def repository_name
  payload.dig('repository', 'full_name')
end
``` [7](#0-6) 
used by, e.g., `PushHandler#process`, which resolves stacks from `Repository.from_github_repo_name(repository_name)` and triggers `stack.sync_github(...)` (`GithubSyncJob`) for any matching stack [8](#0-7) .

In a Shipit deployment configured for multiple GitHub organizations (the documented multi-org config format at [9](#0-8) ), an attacker only needs to know that at least one configured organization has no `webhook_secret` set (an explicitly optional field). By setting `repository.owner.login` (or `organization.login`) in the POST body to that unsecured organization's name, `verify_webhook_signature` short-circuits to `true` unconditionally — no valid `X-Hub-Signature` is required at all. The attacker then sets `repository.full_name` in the same payload to point at a stack belonging to a *different, secured* organization. The engine never checks that the organization used for signature verification equals the organization owning `repository.full_name`, so the forged event is processed as if it legitimately originated from GitHub for the victim's repository.

This is directly analogous to the reported Amp.sol bug: the code validates one thing (`transferFrom` success / a signature over "organization X") but then acts on unrelated attacker-supplied data (an arbitrary mint amount / an arbitrary `repository.full_name`) without verifying that the validated identity matches the identity acted upon.

### Impact Explanation
Depending on the event type, an attacker who abuses this mismatch can:
- Force a `push` event to enqueue `GithubSyncJob` for a victim's stack in a different, secured organization, causing Shipit to fetch and import attacker-influenced commit history via `stack.github_commits` / `FirstParentCommitsIterator` [10](#0-9) , polluting deploy history and potentially triggering continuous delivery for commits that were never actually pushed with GitHub's knowledge.
- Inject forged `status` or `check_run` payloads that get persisted as real CI status/check-run state on a victim's commits, which the `StatusChecker`/merge-queue logic (`any_status_checks_missing?`, `all_status_checks_passed?`) consults to decide whether a pull request may be merged [11](#0-10) , potentially enabling an unauthorized merge/deploy for a repository the attacker has no real write access to.

This maps to the "Critical" bucket (unauthorized deploy/merge, cross-repository writes) since the attacker crosses an organizational trust boundary purely through unauthenticated payload fields.

### Likelihood Explanation
Exploitability depends on operational configuration: it requires (a) a multi-org Shipit deployment, and (b) at least one configured organization lacking a `webhook_secret` (explicitly supported/optional per the docs). Given `webhook_secret` is marked optional in the setup guide, this is a plausible real-world configuration, but not guaranteed for every deployment — moderate likelihood, entirely configuration-dependent, and I could not verify from the indexed code whether any additional owner/organization cross-check exists elsewhere in the merge/deploy path that would mitigate this before a "Critical" outcome is realized (e.g., in `Stack.from_github_repo_name` or repository provisioning).

### Recommendation
- Bind signature verification to the same repository identity that handlers subsequently act on: derive both `repository_owner` (for secret selection) and the acted-upon repository from a single, consistent field (e.g., always use `repository.full_name`'s owner segment), and reject the request if `repository.owner.login`/`organization.login` doesn't match the owner segment of `repository.full_name`.
- Do not treat an absent `webhook_secret` as an implicit "always verified" bypass; if an org has no secret configured, either reject webhooks for it, or fail closed rather than short-circuiting to `true` in `verify_webhook_signature`.
- Add an explicit assertion in `Handler#stacks`/`repository_name` that the resolved `Repository#owner` matches the organization that was used to authenticate the webhook.

### Proof of Concept
Assume `config/secrets.yml` (or Rails credentials) configures two GitHub orgs, `victim-org` (with `webhook_secret: real-secret`) and `test-org` (no `webhook_secret` set, e.g., a sandbox/staging org left unconfigured):

```
POST /webhooks HTTP/1.1
X-Github-Event: push
Content-Type: application/json
(no valid X-Hub-Signature required)

{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "test-org" },
    "full_name": "victim-org/private-victim-repo"
  }
}
```
1. `verify_signature` computes `repository_owner` = `"test-org"` [1](#0-0) .
2. `Shipit.github(organization: "test-org")` loads `test-org`'s config, which has no `webhook_secret` [4](#0-3) .
3. `verify_webhook_signature` immediately returns `true` because `webhook_secret` is blank [5](#0-4)  — no valid signature was ever checked for `victim-org`.
4. `create` dispatches to `PushHandler`, which reads `payload.dig('repository', 'full_name')` = `"victim-org/private-victim-repo"` [7](#0-6)  and enqueues `GithubSyncJob` for that stack [8](#0-7) , entirely bypassing `victim-org`'s actual webhook secret.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

      expected_head_sha = params[:expected_head_sha]

      appended_commits = []

      handle_github_errors do

        # Retry on Github eventual consistency: webhook indicated new commits but we found none
        if expected_head_sha && new_commits.empty? && !commit_exists?(expected_head_sha) &&

            append_commit(gh_commit)
