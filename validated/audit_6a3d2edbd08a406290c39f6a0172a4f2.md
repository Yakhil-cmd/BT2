### Title
Cross-stack authorization bypass in `CCMenuController#stack` breaks the `ApiClient.stack_id` scoping binding - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::BaseController` enforces that a stack-scoped `ApiClient` (one created with a specific `stack_id`) can only ever resolve the `stack` it was scoped to, by looking it up through the `stacks` relation: [1](#0-0) 
`Api::CCMenuController` overrides this and resolves the stack unscoped, directly from the global `Stack` table: [2](#0-1) 

### Finding Description
The equality that is supposed to hold everywhere in the API layer is:

`stack a token authorizes (current_api_client.stack_id) == stack a token can act on (the `stack` resolved in the controller)`

`Shipit::ApiClient` supports being scoped to a single stack via `stack_id`, and `BaseController#stacks` is the mechanism that enforces this scope for every subsequent stack lookup: [1](#0-0) 
`Api::LocksController` and other API controllers rely on `stack` (which internally calls `stacks.from_param!`) so a token scoped to stack A cannot touch stack B — the `where(id: current_api_client.stack_id)` restriction is applied before `from_param!` raises `ActiveRecord::RecordNotFound` for any other stack.

`Api::CCMenuController`, however, defines its own private `stack` method that bypasses `stacks` entirely and queries `Stack.from_param!(params[:stack_id])` directly against the whole `Stack` table: [2](#0-1) 

`require_permission :read, :stack` only checks that the `ApiClient` possesses the `read:stack` permission string; it never checks which stack the client is scoped to: [3](#0-2) 

The realistic path to this token is `CCMenuUrlController#client`, which mints a `read:stack`-only `ApiClient` (with no `stack_id` set) for the current logged-in user: [4](#0-3) 
and any narrower `read:stack` client scoped to one stack (e.g. one created by an operator via the API/UI with `stack_id` set) that is meant to be usable only for CCMenu polling of that one stack. Because `CCMenuController#stack` never consults `current_api_client.stack_id`, that same token — regardless of how it was scoped — can be replayed against `GET /api/stacks/:any_other_stack_id/ccmenu.xml` for a stack the client was never authorized for.

Before the attacker's request: `current_api_client.stack_id` == stack A ⇒ only stack A's deploy state should be visible.
After the attacker's request: because `CCMenuController#stack` calls `Stack.from_param!` unscoped, the response reveals stack B's `latest_deploy`, deploy id, `running?`, and `ended_at` for any stack_id the attacker supplies, breaking the intended equality.

### Impact Explanation
This grants an unauthenticated-scope read of another stack's deploy/task state (last deploy id, status/running flag, timestamps) using a token that was only supposed to authorize reads for one specific stack. This matches the "High" category of unauthorized read of stack state/deploy output through an authorization scoping bypass, since it lets a client escalate the effective scope of its `read:stack` permission from "one authorized stack" to "any stack in the installation."

### Likelihood Explanation
Likelihood is high for any deployment that issues stack-scoped `read:stack` `ApiClient`s (the engine explicitly supports this via `ApiClient#stack_id` and `BaseController#stacks`) and exposes the CCMenu endpoint, since the only requirement is possession of a valid, appropriately-permissioned token and knowledge/guessing of another stack's `to_param` (owner/repo/environment), which is not secret information (stack pages are enumerable at `/repo/environment`).

### Recommendation
Remove the private `stack` override in `Api::CCMenuController` (and the analogous one in `CCMenuUrlController`, which is a non-API controller but should still resolve via the caller's authorized stacks) and instead rely on the scoped `stacks.from_param!(params[:stack_id])` from `BaseController`, exactly as `Api::LocksController` and other API controllers do, so that a stack-scoped token can never resolve a stack outside its `stack_id`.

### Proof of Concept
1. As an authorized user for Stack A, request a CCMenu URL: `GET /stacks/:owner/:repo/:env/ccmenu_url` → returns a token scoped implicitly to the CCMenu client (or, using the admin UI, create an `ApiClient` with `permissions: ['read:stack']` and `stack_id: <Stack A id>`).
2. Use that token's `authentication_token` as Basic auth (or `token` query param) against `GET /api/stacks/:owner_b/:repo_b/:env_b/ccmenu.xml` for Stack B, a stack unrelated to the token's `stack_id`.
3. Observe that `Api::CCMenuController#stack` resolves Stack B via `Stack.from_param!` (unscoped) rather than raising `ActiveRecord::RecordNotFound`, and the XML response leaks Stack B's latest deploy id/status, confirming the scope bypass.
