### Title
Vote account `InitializeAccount`/`InitializeAccountV2` can be front-run to hijack authority over a funded, uninitialized vote account - ([File: programs/vote/src/vote_state/mod.rs])

### Summary
The vote program's `initialize_account` / `initialize_account_v2` functions only require the `node_pubkey` supplied in the instruction to be a signer; they do **not** require the vote account itself (the account being initialized) to sign the initialization instruction. If the account-creation (`SystemInstruction::CreateAccount`, which does require the new account's signature) and the vote-account initialization (`VoteInstruction::InitializeAccount`) are submitted as two separate transactions instead of being bundled atomically in one message, an attacker observing the pending/landed `CreateAccount` transaction can race to submit their own `InitializeAccount` (or `InitializeAccountV2`) instruction against that same, still-uninitialized, already-funded vote account before the legitimate initializer's transaction lands. This is directly analogous to the reported `CrossCurrencyVault.initialize` issue: an externally reachable "initializer" entry point lacks any binding to the intended caller/owner and can be front-run by anyone who can produce a valid signer for one of its parameters.

### Finding Description
`initialize_account` in `programs/vote/src/vote_state/mod.rs` performs the following checks: [1](#0-0) 

- It checks the vote-state version is uninitialized (`AccountAlreadyInitialized` guards re-init).
- It calls `verify_authorized_signer(&vote_init.node_pubkey, signers)`, which only requires that `node_pubkey` (a value taken directly from instruction data, chosen by whoever submits the instruction) is present in the set of signers for *this* instruction.
- It does **not** require that the vote account's own key sign the `InitializeAccount` instruction.

The instruction-level dispatch in `programs/vote/src/vote_processor.rs` confirms this: for `VoteInstruction::InitializeAccount`, the only signer requirement enforced by the processor comes from `vote_state::initialize_account`'s call to `verify_authorized_signer`, and the accompanying test explicitly builds the instruction accounts list with the vote account marked `is_signer: false` and only `node_pubkey` marked `is_signer: true`: [2](#0-1) [3](#0-2) 

The equivalent `InitializeAccountV2` path has the same signer requirement pattern (only `node_pubkey` must sign): [4](#0-3) [5](#0-4) 

Crucially, `VoteInit`/`VoteInitV2` also carry `authorized_voter` and `authorized_withdrawer` fields, which are set unconditionally from instruction data with no check that they correspond to any particular caller:
```
VoteInstruction::InitializeAccount(vote_init) => { ... }
```
So whoever wins the race to submit a valid `InitializeAccount` instruction (with any `node_pubkey` they control as signer) against a given uninitialized, vote-program-owned account gets to set `authorized_voter` and `authorized_withdrawer` to arbitrary keys of their choosing.

In the "happy path", client tooling bundles `SystemInstruction::CreateAccount` and `VoteInstruction::InitializeAccount` into the *same* transaction/message (as seen in `local_cluster.rs`'s vote-account-creation flow and in the CLI's `create_account_with_config` usage), which makes them atomic and therefore not exploitable in that specific flow: [6](#0-5) 

However, nothing in the vote program itself enforces this bundling. The vote program has no way to know or require that `InitializeAccount` be co-signed by the same transaction that created the account, nor does it require the vote account itself to sign. Any caller/tooling that funds a vote-program-owned account and initializes it in two separate transactions (e.g., hardware-wallet flows, `--sign-only` multi-step signing, scripted deployments, or any third-party wallet/integration that doesn't strictly co-locate both instructions) exposes a window during which the account is rent-exempt-funded, owned by the vote program, and uninitialized — and any unprivileged party can submit `InitializeAccount`/`InitializeAccountV2` naming themselves as `authorized_withdrawer` before the legitimate initializer's transaction confirms.

### Impact Explanation
Once an attacker wins this race, they become the `authorized_withdrawer` of the account. The legitimate owner's `InitializeAccount` transaction subsequently fails with `AccountAlreadyInitialized` (confirmed by the existing "reinit should fail" test), permanently locking the intended owner out. The attacker, now holding `authorized_withdrawer`, can call `VoteInstruction::Withdraw` to drain the account's lamports (the funds deposited by the victim to cover the vote account's rent-exempt minimum balance, and any voting rewards subsequently accrued) to an address of their choosing. This is a concrete, unsigned fund-theft primitive reachable purely through a single crafted transaction from an unprivileged sender — matching the required "concrete unsigned fund movement" bar. It also permanently corrupts the intended vote/stake setup for the victim (their vote account becomes attacker-controlled), which can further disrupt stake delegation and reward accounting for that node.

### Likelihood Explanation
Likelihood depends entirely on how a given client/integration sequences the `CreateAccount` + `InitializeAccount` instructions. In the reference CLI/local-cluster flows in this repo, they are bundled atomically in one transaction, which closes this window. But the vote program's on-chain logic provides no protection at all if any caller (custom SDK, wallet, exchange integration, or a user manually building transactions) submits these as two separate transactions — a pattern common in flows needing separate signing steps (e.g. offline/hardware-wallet signing, or funding-then-initializing patterns). Because the on-chain program itself does not enforce atomicity or require the vote-account key to co-sign initialization, exploitability is fully within the control of an external attacker with mempool visibility and does not require any validator or leader misbehavior — likelihood is realistic wherever the two-transaction pattern is used, though it is mitigated by common tooling’s current practice of bundling instructions.

### Recommendation
Harden `initialize_account`/`initialize_account_v2` in `programs/vote/src/vote_state/mod.rs` to require the vote account itself to be a signer of the initialization instruction (in addition to `node_pubkey`), i.e. add `verify_authorized_signer(vote_account.get_key(), signers)?` (or an equivalent explicit check that the account's own key signed this specific instruction) before allowing state to be written. This removes the front-running window entirely, since only the party holding the vote account's private key (i.e., whoever created the account) could ever complete initialization — mirroring the standard Solana idiom that "new-account creation + initialization" is safe only when the new account's own signature is required somewhere in the sequence. Alternatively/additionally, document and enforce (at the CLI/SDK layer used to submit these instructions) that `CreateAccount` and `InitializeAccount` must always be included in the same atomic transaction.

### Proof of Concept
1. Victim submits Tx A: `SystemInstruction::CreateAccount` creating a new account `V` owned by the vote program, funded with the rent-exempt minimum balance, signed by victim's `payer` and `V`'s keypair (required by `CreateAccount`).
2. Victim intends to submit Tx B: `VoteInstruction::InitializeAccount(VoteInit { node_pubkey: victim_node, authorized_voter: victim, authorized_withdrawer: victim, commission: 0 })`, referencing account `V` (not required to be a signer for this instruction) and `node_pubkey = victim_node` (signer).
3. Attacker observes Tx A land (or observes it pending in the mempool) and, before Tx B confirms, submits Tx C: `VoteInstruction::InitializeAccount(VoteInit { node_pubkey: attacker_node, authorized_voter: attacker, authorized_withdrawer: attacker, commission: 0 })` against the same account `V`, signed only by `attacker_node` (an arbitrary keypair the attacker controls) — this passes `verify_authorized_signer` per [7](#0-6) .
4. Tx C lands first; `V` is now initialized with `authorized_withdrawer = attacker`.
5. Victim's Tx B now fails with `InstructionError::AccountAlreadyInitialized` (per the existing "reinit should fail" test at [8](#0-7) ), permanently blocking the victim.
6. Attacker submits `VoteInstruction::Withdraw(lamports)` signed by `attacker` (the `authorized_withdrawer`) to drain `V`'s rent-exempt balance to an attacker-controlled account, completing the fund theft.

Note: I could not fully trace the exact `Withdraw` authorization check function body (it is defined in `programs/vote/src/vote_state/mod.rs`, matched via `VoteInstruction::Withdraw(lamports)` in `vote_processor.rs`) within the available search budget, so step 6's exact code path is inferred from the `Withdraw` instruction's well-established requirement of `authorized_withdrawer` as signer rather than directly quoted; a full session with unrestricted tool access would be needed to cite that function body precisely.

pub fn initialize_account_v2<S: std::hash::BuildHasher, F>(
    vote_account: &mut BorrowedInstructionAccount,
    target_version: VoteStateTargetVersion,
    vote_init: &VoteInitV2,
    inflation_rewards_collector: NewCommissionCollector,
    block_revenue_collector: NewCommissionCollector,
    signers: &HashSet<Pubkey, S>,
    clock: &Clock,
    rent: &Rent,
    consume_pop_compute_units: F,
) -> Result<(), InstructionError>
where
    F: FnOnce() -> Result<(), InstructionError>,
{
    VoteStateHandler::check_vote_account_length(vote_account, target_version)?;
    let versioned = vote_account.get_state::<VoteStateVersions>()?;

    if !versioned.is_uninitialized() {
        return Err(InstructionError::AccountAlreadyInitialized);
    }

    // node must agree to accept this vote account
    verify_authorized_signer(&vote_init.node_pubkey, signers)?;

    // Per SIMD-0464, validate the collector accounts using the same checks as
    // `UpdateCommissionCollector` (SIMD-0232).
    let inflation_rewards_collector_key =
        inflation_rewards_collector.validate_and_resolve_key(vote_account, rent)?;
    let block_revenue_collector_key =
        block_revenue_collector.validate_and_resolve_key(vote_account, rent)?;

    // verify the BLS pubkey proof of possession
    verify_bls_proof_of_possession(
        vote_account.get_key(),
        &vote_init.authorized_voter_bls_pubkey,
        &vote_init.authorized_voter_bls_proof_of_possession,
        consume_pop_compute_units,
    )?;

    VoteStateHandler::init_vote_account_state_v2(
        vote_account,
        vote_init,
        &inflation_rewards_collector_key,
        &block_revenue_collector_key,
        clock,
        target_version,
    )
}
