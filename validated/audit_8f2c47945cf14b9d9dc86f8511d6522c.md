Confirmed: `teams` table has `github_id` as a plain non-unique-indexed column (unique index is on `["organization", "slug"]`, not on `github_id`). `Team.find_or_create_by!(github_id: params.team.id)` in `MembershipHandler#find_or_create_team!` looks up an existing row purely by `github_id`, ignoring which organization signed the webhook request that supplied it.

### Title
Membership webhook lets an attacker-controlled GitHub organization add arbitrary users to another organization's authorized Team - ([File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App (and thus the HMAC secret used to authenticate the request) using `params.dig('organization','login')` for `membership` events. `MembershipHandler#find_or_create_team!`, however, looks up the `Team` row to mutate using only `params.team.id` (the numeric GitHub team ID), which has no uniqueness or ownership binding to the organization that authenticated the webhook. This breaks the equality "organization that authenticated == organization whose Team record is written," letting an attacker who controls a legitimate-but-different GitHub organization onboarded to the same multi-tenant Shipit instance forge a `membership` webhook that adds arbitrary Shipit users to a `Team` belonging to a completely different, victim organization.

### Finding Description
`app/controllers/shipit/webhooks_controller.rb` picks which `GitHubApp`/webhook secret to verify the signature with based on `repository_owner`, which for `membership` events falls back to `params.dig('organization', 'login')`: [1](#0-0) [2](#0-1) 

This means the signature is valid as long as it was signed with *some org's* configured `webhook_secret` — specifically the org named in `params['organization']['login']` — as shown by the multi-org support in `Shipit.github(organization:)` and the sample multi-tenant config: [3](#0-2) 

`MembershipHandler` then processes the event using `params.team.id`, not `params.organization.login`, to locate the `Team` record to mutate: [4](#0-3) [5](#0-4) 

`Team.find_or_create_by!(github_id: params.team.id)` only inserts the block's `team.organization = params.organization.login` assignment on **create**. If a `Team` row with that `github_id` already exists (e.g. it was previously synced for the legitimate victim organization via `Shipit.github_teams`/`Team.find_or_create_by_handle`, which is looked up by `organization` + `slug`, not `github_id`), the existing row — and its real `organization` — is returned unchanged: [6](#0-5) 

The database schema confirms `github_id` on `teams` has **no unique index or scoping to organization** — only `["organization", "slug"]` is uniquely indexed: [7](#0-6) 

So the binding actually enforced by signature verification is "organization X authenticated this request," while the binding actually written is "team with this numeric `github_id` (which may belong to organization Y) gets a new member." An attacker who controls organization X (and therefore its GitHub App webhook secret registered in this Shipit instance) can sign a `membership` payload with `organization.login = "X"` (making `verify_signature` pass), but supply `team.id` equal to the known/leaked numeric GitHub team ID of a `Team` belonging to victim organization Y, and `member.login` equal to an attacker-controlled Shipit user login: [8](#0-7) 

`team.add_member(member)` will then add the attacker's user to that victim `Team`'s `memberships`: [9](#0-8) 

If that victim `Team` is one of `Shipit.github_teams` (i.e. listed in `oauth.teams` and used for authorization), the attacker's `User#authorized?` check will now return `true`, because it only checks membership rows, not real GitHub team membership: [10](#0-9) [11](#0-10) 

### Impact Explanation
This is an escalation into `Shipit.github_teams` authorization: an unprivileged attacker who does not have a Shipit session or real membership in an authorized GitHub team can grant themselves full access to a Shipit instance (viewing stacks, triggering deploys/tasks, merging PRs) by forging one webhook request, as long as they control any organization that is configured as a GitHub App tenant on the shared Shipit instance. This matches the High-severity category "escalation into `Shipit.github_teams` authorization."

### Likelihood Explanation
Requires the target Shipit deployment to be multi-tenant (multiple organizations configured under `github:` in `secrets.yml`, as the shipped `docs/setup.md`/`config/secrets.development.shopify.yml` examples explicitly support) and requires the attacker to know/guess the numeric GitHub `team.id` of the victim's authorized team (obtainable via GitHub's public/team API or by prior legitimate webhook traffic observed by the attacker's own org's admin). No Shipit credentials, GitHub App private key, or `webhook_secret` of the victim organization are needed — only the attacker's own org's webhook secret, which they legitimately possess as an admin of their own GitHub App.

### Recommendation
In `MembershipHandler#find_or_create_team!`, scope the lookup/creation to the authenticated organization, e.g. `Team.find_or_create_by!(github_id: params.team.id, organization: params.organization.login)`, and reject/raise if an existing `Team` with that `github_id` has a different `organization` than the one that signed the request. More generally, `WebhooksController#verify_signature` should ensure the organization used to select the webhook secret is cross-checked against every organization-scoped identifier acted upon by the handler (team, repository owner, etc.), not just used to pick a secret in isolation.

### Proof of Concept
1. Shipit is configured with two tenants, `attacker-org` and `victim-org`, each with their own GitHub App and `webhook_secret` in `secrets.yml`.
2. `victim-org/admins` team (numeric GitHub `github_id`, e.g. `4242`) is already synced into Shipit's `teams` table (via `Shipit.github_teams`/`rake teams:fetch`) and is listed in `oauth.teams`, making it authorization-relevant.
3. Attacker, who administers `attacker-org`'s GitHub App and thus knows `attacker-org`'s `webhook_secret`, POSTs to `/webhooks` with header `X-Github-Event: membership`, signed with `attacker-org`'s secret, and body:
```json
{
  "action": "added",
  "team": { "id": 4242, "name": "Admins", "slug": "admins", "url": "https://api.github.com/teams/4242" },
  "organization": { "login": "attacker-org" },
  "member": { "login": "attacker-shipit-login" }
}
```
4. `verify_signature` validates using `attacker-org`'s secret (passes). `MembershipHandler` finds the existing `Team` row with `github_id: 4242` (which belongs to `victim-org`) and adds `attacker-shipit-login` as a member.
5. The attacker's Shipit `User` now passes `authorized?` because it is a member of `victim-org/admins`, gaining full unauthorized access to the Shipit instance.
