### Title
Reserve donation to the underlying Aquarius pool inflates LP-collateral price within the sanity band, enabling over-borrow and bad debt — (File: contracts/price-aggregator/src/providers/aquarius.rs)

### Summary
The Napier bug class — "protocol prices an asset off a manipulable pool exchange rate, then trades/credits at that inflated rate" — maps onto XOXNO Lending's Aquarius LP collateral pricing. `providers/aquarius.rs::read` fetches the pool's live reserves and total shares on every price call and computes the LP share fair value in `fair_lp_price_wad` (`2·sqrt(vA·vB)/supply`) or `fair_stable_lp_price_wad` (`D·min(priceA,priceB)/supply`). An unprivileged account that lists the LP token as collateral can move those reserves (direct token transfer to the pool, or an own swap/add-liquidity) before the controller reads the price, over-borrow against the inflated collateral, and then recover the donated capital by removing liquidity — leaving bad debt. The only mitigations are the geometric-mean/stable-invariant damping and the configured `min_sanity_price_wad`/`max_sanity_price_wad` band, which is wide in deployed configs (e.g., 0.45–2.5, 1.74–2.44 WAD in `configs/ops/mainnet/*.json`), permitting tens-of-percent inflation inside the band.

### Finding Description
- `aquarius::read` calls `aquarius_pool_reserves_call` and `aquarius_total_shares_call` at resolution time (`contracts/price-aggregator/src/providers/aquarius.rs:90-113`), so any same-ledger movement of pool balances is reflected in the price.
- `fair_lp_price_wad` (`common/src/oracle/lp.rs:57-87`) scales with `sqrt(vA·vB)`. Donating token A scales the LP price by `sqrt((Ra + X)/Ra)`: a donation equal to ~1× reserve A gives ~1.41×; ~3× gives 2×. For stable pools, `solve_stable_d` grows with the sum of normalized reserves, so a one-sided donation raises `D` sub-proportionally but monotonically (`common/src/oracle/lp_stable.rs:80-110`).
- Crucially, the donation is not burned: if the attacker first holds LP shares (or deposits to mint them), the donated balance accrues to all LPs including the attacker, and is largely recoverable via `remove_liquidity` after the borrow — net cost ≈ pool fees + residual slippage.
- The inflated price feeds `Context::cached_price` → `calculate_account_risk_totals` / `calculate_ltv_collateral_wad` (`contracts/controller/src/risk/totals.rs:76-99, 157-216`), raising `ltv_collateral` and passing `require_post_pool_risk_gates` (`skills/xoxno-lending/math.md:304-316`), so `borrow` (or `swap_debt`/`multiply`) succeeds above true capacity.
- `min_pool_value_wad` does not help: it is evaluated against the *inflated* `pool_value_wad` (`aquarius.rs:118-122`).
- Caveat: this relies on Aquarius `reserves()` reflecting token balances including direct transfers (balance-based accounting) or on the attacker using real swaps/adds. If Aquarius reserves are internally stored and ignore unsolicited transfers, the manipulation requires real swaps, which move both reserve legs and cost more, but still move the price before the controller samples it. I could not verify the Aquarius reserve semantics from this repo; the on-chain `attest`/`read` calls only assert `reserves > 0`, not their provenance.

### Impact Explanation
Theft of user funds / protocol insolvency: the attacker supplies the manipulated LP token, borrows more USD value than the collateral's true value, defaults, and leaves the pool with bad debt absorbed by suppliers via supply-index write-down or `recapitalize`. Bounded by the sanity-band width rather than eliminated.

### Likelihood Explanation
Requires: an Aquarius LP token listed as collateral, sufficient capital to move reserves (capital scales quadratically with desired price move for constant-product), and a sanity band wide enough to admit the move — deployed bands allow ~1.4–5× ranges. The manipulation leg, the price read, and the borrow can be atomically ordered within one ledger via a `supply` + `borrow` sequence; repayment of the manipulated state by removing liquidity restores most capital. Medium likelihood, Medium/High severity depending on LP-collateral LTVs.

### Recommendation
- Use manipulation-resistant reserve inputs for the constant-product leg (e.g., price `2·sqrt(vA·vB)` is good, but pair it with a *minimum* of spot-vs-fair checks, or value each leg at `min(spot, oracle)`).
- Subtract unsolicited-donation exposure by reading pool reserves at a delayed/checkpointed source, or require the LP price to stay within a tighter, liquidity-scaled band (`max_sanity_price_wad` closer to expected fair value).
- Cap effective LTV of LP collateral to absorb the residual in-band deviation, per the documented band analysis in `threat-model.md`.

### Proof of Concept
1. Attacker acquires LP shares of the target Aquarius pool (deposit A+B).
2. Attacker transfers `X` units of token A directly to the pool (or executes a large buy of B), raising `reserve_a` so `fair_lp_price_wad` rises toward `max_sanity_price_wad` but stays within the band.
3. In the same transaction/ledger window, call `controller.supply` with the LP token as collateral on a position NFT, then `controller.borrow` for a stablecoin sized to the inflated `ltv_collateral`.
4. Remove liquidity from the Aquarius pool, recovering the donation (minus fees); pool reserves return to fair, LP price falls.
5. Position is underwater at true value; liquidation cannot recover full debt → bad debt for suppliers.
