### Title
Webhook signature verifies the sending GitHub organization, but the repository acted upon is taken from an unverified field, breaking the org-authenticated ↔ repository-written binding - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/org (and therefore which `webhook_secret`) to use for HMAC verification based on `params.dig('repository', 'owner', 'login')` (or the fallback `organization.login`), but the handlers that actually act on the payload resolve the target `Repository`/`Stack` from a completely different, signature-covered-but-not-cross-checked field: `repository.full_name`. Because the signature only proves "this body was signed with organization X's secret," not "this body's target repository belongs to organization X," anyone who legitimately controls a webhook secret for one onboarded organization can submit a signed payload whose `repository.full_name` names a stack belonging to a different, unrelated organization.

### Finding Description
`verify_signature` looks up the app config purely from the owner login in the payload: [1](#0-0) [2](#0-1) 

This only proves the raw body was HMAC-signed with the secret configured for whichever organization the `repository.owner.login`/`organization.login` field names — it says nothing about which repository the rest of the payload targets.

The base `Handler` (used by `PushHandler`, `StatusHandler`'s siblings, etc.) instead resolves the acted-upon repository/stacks from a separate field, `repository.full_name`, with no comparison back to the verified owner: [3](#0-2) 

Same pattern repeats in the pull-request handlers (`OpenedHandler`, `ClosedHandler`, `LabeledHandler`, `UnlabeledHandler`, `ReopenedHandler`), all of which resolve `Shipit::Repository.from_github_repo_name(params.repository.full_name)` independently of the field used for signature verification, e.g.: [4](#0-3) 

`PushHandler` then drives `GithubSyncJob` for every non-archived stack of that (attacker-chosen) repository matching the branch, with an attacker-supplied `expected_head_sha`: [5](#0-4) 

`GithubSyncJob` then uses Shipit's own GitHub credentials (`stack.github_api`) to fetch and ingest commits up to `expected_head_sha` for that target stack, mark it accessible/inaccessible, and (on the first commit) schedule a spec-cache rebuild: [6](#0-5) [7](#0-6) 

The binding that should hold is: `organization authenticated by signature == owner of repository.full_name acted upon`. Nothing in `WebhooksController` or `Handler` enforces this equality; only the raw bytes are checked against the secret keyed by `repository.owner.login`, while every handler trusts `repository.full_name` (and other payload fields) unconditionally to pick the target `Stack`/`Repository`.

### Impact Explanation
In a multi-tenant Shipit deployment (multiple organizations each configured with their own GitHub App/`webhook_secret` via `Shipit.github(organization: ...)`), an entity that legitimately possesses the webhook secret for organization A's own onboarded repositories can forge a signed payload where `repository.owner.login = "A"` (so signature verification succeeds using A's secret) but `repository.full_name = "B/other-repo"` (a stack belonging to unrelated organization B that A has no GitHub access to). This lets A:
- Force ingestion/sync of organization B's stack via `GithubSyncJob`, influencing commit history state, CI status association (`StatusHandler` matches purely on commit `sha`, globally, with no repository scoping at all) and mark stacks accessible/inaccessible.
- Archive/unarchive/deprovision B's review stacks through the PR handlers, which resolve `repository`/`stack` solely from `params.repository.full_name`.

This breaks a repository-write trust boundary across tenants without any Shipit session, ApiClient token, or GitHub write access to the target repository — matching the "cross-repository writes" Critical impact criterion.

### Likelihood Explanation
Requires the attacker to already control a legitimate webhook secret for at least one organization/app onboarded into the same Shipit instance (a realistic condition for any multi-org/shared Shipit deployment, since the secret is org-scoped, not "the whole app" scoped). No Shipit login, ApiClient token, or GitHub push access to the victim repository is needed — the endpoint is unauthenticated apart from the HMAC check, and the HMAC check never binds the verified organization to the acted-upon repository name.

### Recommendation
After `verify_signature` succeeds, additionally assert that `repository_owner` (used to select the verifying app/secret) matches the owner segment of `repository.full_name` (and any other repository identifiers used later, e.g. in `StatusHandler`/PR handlers) before dispatching to handlers; reject the webhook otherwise. Alternatively, pass the verified `repository_owner` into `Handler#stacks`/repository resolution and scope lookups to repositories owned by that verified organization only.

### Proof of Concept
1. Shipit is configured with two onboarded organizations, `org-a` (attacker-accessible, webhook secret known/derivable to the caller) and `org-b` (contains a private stack `org-b/target-repo`, unrelated to `org-a`).
2. Attacker crafts a push payload:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha-existing-on-org-b/target-repo>",
  "repository": { "owner": { "login": "org-a" }, "full_name": "org-b/target-repo" }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC(org-a-secret, body)` and POSTs to `/github/webhooks` with `X-Github-Event: push`.
4. `verify_signature` calls `Shipit.github(organization: "org-a")` and validates the HMAC successfully (per `app/controllers/shipit/webhooks_controller.rb:24-30`).
5. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("org-b/target-repo")` (per `app/models/shipit/webhooks/handlers/handler.rb:32-38`) and enqueues `GithubSyncJob` for `org-b`'s stack with the attacker-supplied `expected_head_sha`, even though the verified signature only proved knowledge of `org-a`'s secret.

    def perform(params)
      @stack = Stack.find(params[:stack_id])
      expected_head_sha = params[:expected_head_sha]
      retry_count = params[:retry_count] || 0
      head_before_sync = spec_cache_target
      appended_commits = []

      handle_github_errors do
        new_commits, shared_parent = fetch_missing_commits { stack.github_commits }

        # Retry on Github eventual consistency: webhook indicated new commits but we found none
        if expected_head_sha && new_commits.empty? && !commit_exists?(expected_head_sha) &&
           retry_count < MAX_RETRY_ATTEMPTS
          GithubSyncJob.set(wait: RETRY_DELAY * retry_count).perform_later(params.merge(retry_count: retry_count + 1))
          return
        end

        stack.transaction do
          shared_parent&.detach_children!
          appended_commits = new_commits.map do |gh_commit|
            append_commit(gh_commit)
          end
          stack.lock_reverted_commits! if appended_commits.any?(&:revert?)
        end
      end
      sync_changed_nothing = appended_commits.empty? &&
                             spec_cache_target == head_before_sync &&
                             stack.cached_deploy_spec.present?
      return if sync_changed_nothing && !params[:force_spec_cache]

      CacheDeploySpecJob.perform_later(stack)
    end
