### Title
CCMenu API endpoint bypasses ApiClient stack scoping, allowing a stack-scoped token to read the status of any stack - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::Api::CCMenuController#stack` resolves the target stack with an unscoped `Stack.from_param!(params[:stack_id])` [1](#0-0)  instead of using the scoped `stacks.from_param!` helper defined on `BaseController`, which restricts lookups to `current_api_client.stack_id` when the client is stack-scoped [2](#0-1) . This breaks the binding "the stack a token authorizes == the stack it touches": an `ApiClient` created with `stack_id` set to stack A can supply any other `stack_id` in the URL and successfully read deploy/build status for stack B.

### Finding Description
`ApiClient` records can be scoped to a single stack via `stack_id` [3](#0-2) . `BaseController#stacks` enforces this scoping for every controller that relies on it: `current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all`, and `BaseController#stack` calls `stacks.from_param!(params[:stack_id])` [2](#0-1) . This is the mechanism `StacksController`, `HooksController`, etc. rely on to keep a stack-scoped token confined to its own stack (verified by the test "an api client scoped to a stack will only see that one stack") [4](#0-3) .

`CCMenuController` overrides `stack` to bypass this scoping entirely, calling `Stack.from_param!(params[:stack_id])` directly against the full `Stack` relation [5](#0-4) . It only checks the generic `read:stack` permission via `require_permission :read, :stack` [6](#0-5) , which is a permission-name check on the `ApiClient#permissions` array [7](#0-6)  — it does not verify that the requested stack matches `current_api_client.stack_id`. `CCMenuController#show` then discloses the latest deploy/rollback status for whatever stack was resolved [8](#0-7) .

The controller also supports authenticating via a `token` query-string parameter for CI/CCMenu client compatibility [9](#0-8) , which is the normal, unprivileged way this endpoint is meant to be used (no session, no repository write access, no GitHub credentials needed) — an attacker only needs a legitimate but narrowly-scoped `ApiClient` token (e.g., one deliberately restricted to a single, low-sensitivity stack) with `read:stack` permission.

### Impact Explanation
This crosses the "stack a token authorizes vs. stack it touches" boundary and yields unauthenticated (from the perspective of the target stack) read of stack state: deploy/rollback status (`lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, lock status, etc.) for any stack in the Shipit instance, regardless of the scope the token was issued for. This matches the "High" impact bucket: "unauthenticated read of stack state, task streams or deploy output" outside the caller's authorized scope.

### Likelihood Explanation
Likelihood is high given the required conditions are ordinary and unprivileged: possession of any valid stack-scoped API token with `read:stack` permission (a very common, minimally-privileged credential type intentionally created to be narrowly scoped) plus knowledge/guessing of another stack's `to_param` (`repo_owner/repo_name/environment`), which is generally discoverable (repo names are public/known, environment names like `production`/`staging` are conventional). No repository write access, GitHub App key, or session is required — only the existing, narrowly-scoped `ApiClient` token that is explicitly permitted in this engine's threat model.

### Recommendation
Change `CCMenuController#stack` to use the scoped lookup consistent with the rest of the API, e.g. delegate to (or replicate) `BaseController#stack`/`#stacks` so the resolution is `stacks.from_param!(params[:stack_id])`, ensuring `current_api_client.stack_id` scoping is honored the same way it is for `StacksController` and `HooksController`.

### Proof of Concept
1. Create `stack_a` and `stack_b`. Create an `ApiClient` with `permissions: ['read:stack']` and `stack_id: stack_a.id` (mirrors the "here_come_the_walrus" fixture pattern already used to test scoping) [4](#0-3) .
2. Authenticate as that client (via Basic auth or `?token=`), then request:
   `GET /api/stacks/{stack_b.to_param}/ccmenu.xml?token=<stack_a_scoped_token>`
3. Because `CCMenuController#stack` calls `Stack.from_param!(params[:stack_id])` unscoped [1](#0-0)  and only checks the generic `read:stack` permission, the request succeeds and returns `stack_b`'s deploy status, even though the token is scoped to `stack_a`. Compare with the equivalent request to `StacksController#show` for `stack_b`, which would correctly 404 because `stacks.from_param!` filters by `current_api_client.stack_id`.
