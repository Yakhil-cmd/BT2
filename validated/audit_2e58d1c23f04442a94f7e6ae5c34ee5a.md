### Title
Merkle proof scheme lacks leaf/internal-node domain separation, allowing forged inclusion proofs in address definitions and AA oscript checks - ([File: merkle.js])

### Summary
`merkle.js` implements a Merkle tree where the hash function used for leaves is identical to the hash function used for internal nodes, with no prefix or domain-separation tag distinguishing them. This is the same class of root-cause defect as the "Dragonberry" advisory: a malformed/under-specified Merkle proof-verification scheme that lets an attacker construct proofs that the verifier accepts even though they do not correspond to a genuine, originally-committed element. In ocore, this proof primitive is directly reachable by unprivileged actors through the `in merkle` address-definition authentifier and the `is_valid_merkle_proof` oscript function used by AAs.

### Finding Description
`getMerkleRoot`/`getMerkleProof` build the tree as: [1](#0-0) 

Leaf hashes are `hash(element)` and internal-node hashes are `hash(left_hash + right_hash)` — both computed with the exact same `hash()` function, with no distinguishing prefix (e.g. `0x00` for leaves vs `0x01` for internal nodes, as used in properly designed Merkle schemes such as RFC 6962). Verification mirrors this: [2](#0-1) 

Because leaf and internal-node hashing are indistinguishable, an attacker who knows two sibling hashes `h1`, `h2` that combine into an internal node value `hash(h1+h2)` can submit a forged "element" equal to the literal byte string `h1+h2`. `verifyMerkleProof(element, proof)` will then compute `hash(element) == hash(h1+h2)`, which is exactly the internal node's value, and the rest of the proof path (using the corresponding higher-level siblings) will validate all the way up to the genuine, already-published root. The verifier has no way to tell that this "leaf" is actually a forged encoding of an internal node rather than a real committed element.

This proof primitive is consumed in two unprivileged-reachable paths:
- `in merkle` address-definition authentifier, which checks a caller-supplied proof against a merkle root recorded via a data feed: [3](#0-2) 
- `is_valid_merkle_proof` oscript function, callable from AA formulas using attacker/trigger-supplied `element`/`proof` data: [4](#0-3) 

In both cases the *root* comes from a trusted source (a data feed value already stable on the DAG, per `dataFeedExists`), but the *element* and *proof siblings* are fully attacker-controlled. The lack of leaf/node domain separation means an attacker does not need to break SHA-256 to forge membership of an unauthorized "element" against a legitimately-published root — they only need to know any two sibling hash values from the original tree (which are often derivable, e.g., because the tree's other leaves/roots may be disclosed, or because the oracle publishes the full element list alongside the root for verification purposes).

### Impact Explanation
If a wallet's address definition uses `in merkle` against a data-feed-published whitelist root as part of its signing conditions, or an AA's oscript logic uses `is_valid_merkle_proof` to gate execution (e.g., "did address X get whitelisted"/"is this input authorized" checks), an attacker able to construct such a colliding "element" can satisfy the check without being a genuine member of the committed set. Depending on how the definition/AA uses the result, this can lead to:
- Unauthorized signing/spending from an address whose authentifier partially relies on `in merkle`.
- AA fund loss, by causing the AA to accept an oscript condition (`is_valid_merkle_proof`) as true for a fabricated element that was never actually included by the oracle, releasing funds or performing state changes reserved for legitimately whitelisted callers.

This matches the required "concrete unauthorized spending or AA fund loss" bar, and is reachable purely from unit/trigger posting (address authentifier evaluation and AA oscript evaluation), which are unprivileged attack surfaces.

### Likelihood Explanation
Exploitation requires the attacker to know at least one pair of sibling hashes from the originally-committed tree (not to break SHA-256). This is plausible whenever:
- The oracle/whitelist owner discloses the full list of committed elements (a very common pattern, since users need the actual siblings to build their own valid proofs for legitimate elements) — in which case *any* user who receives a legitimate merkle proof already possesses the exact sibling values needed to forge this attack at the next level up the tree.
- The tree has more than one level (i.e., more than 2 elements), which is the normal case for any meaningfully sized whitelist/data-feed set.

Given that legitimate users are routinely handed sibling hashes as part of receiving their own valid inclusion proof, the barrier to constructing this forged proof is low once such usage pattern exists.

### Recommendation
Introduce domain separation between leaf and internal-node hashing in `merkle.js`, e.g.:
- `leafHash(x) = sha256(0x00 || x)`
- `nodeHash(l, r) = sha256(0x01 || l || r)`

And apply the same separation consistently in `getMerkleRoot`, `getMerkleProof`, and `verifyMerkleProof`. Additionally, since a real inclusion proof should never be confusable with an internal node, consider explicitly rejecting proofs whose depth is inconsistent with the expected tree size (bounding `proof.index`/`proof.siblings.length`) and validating that this bound is supplied out-of-band by the root-committing party where the total leaf count is known.

### Proof of Concept
1. An oracle publishes (via data feed) `root = getMerkleRoot([e0, e1, e2, e3])`, and discloses the full element list (or a legitimate user obtains a proof for `e2`, which includes sibling hashes `h(e3)` and `h(h(e0)+h(e1))` per `getMerkleProof`).
2. Attacker computes `h01 = hash(e0)` and `h23 = hash(e2)+"..."`... concretely: attacker takes the two leaf hashes of a subtree, e.g. `L = hash(e0)` and `R = hash(e1)`, and forms `forged_element = L + R` (raw concatenation, matching the exact string format used internally by `getMerkleRoot`'s `hash(arrHashes[i] + arrHashes[hash2_index])`).
3. Attacker calls `is_valid_merkle_proof(forged_element, proof)` (or supplies it as the `in merkle` authentifier value) where `proof = { index: 0 (position of the internal node one level up), siblings: [hash(h(e2)+h(e3))], root: root }`.
4. `verifyMerkleProof` computes `hash(forged_element) == hash(L+R) == internal_node_hash`, then combines with the remaining sibling to reproduce `root`, returning `true` — even though `forged_element` (`L+R`, a raw hash-concatenation string) was never one of the oracle's actual committed elements `e0..e3`.
5. Any AA or address definition relying on this check as an authorization gate is bypassed.

function hash(str){
	return crypto.createHash("sha256").update(str, "utf8").digest("base64");
}

function getMerkleRoot(arrElements){
	var arrHashes = arrElements.map(hash);
	while (arrHashes.length > 1){
		var arrOverHashes = []; // hashes over hashes
		for (var i=0; i<arrHashes.length; i+=2){
			var hash2_index = (i+1 < arrHashes.length) ? (i+1) : i; // for odd number of hashes
			arrOverHashes.push(hash(arrHashes[i] + arrHashes[hash2_index]));
		}
		arrHashes = arrOverHashes;
	}
	return arrHashes[0];
}

function verifyMerkleProof(element, proof){
	// Node-as-Leaf issue might matter in some cases
	try {
		var index = proof.index;
		var the_other_sibling = hash(element);
		for (var i = 0; i < proof.siblings.length; i++) {
			// this also works for duplicated trailing nodes
			if (index % 2 === 0)
				the_other_sibling = hash(the_other_sibling + proof.siblings[i]);
			else
				the_other_sibling = hash(proof.siblings[i] + the_other_sibling);
			index = Math.floor(index / 2);
		}
		return (the_other_sibling === proof.root);
	}
	catch (e){
		return false;
	}
}
