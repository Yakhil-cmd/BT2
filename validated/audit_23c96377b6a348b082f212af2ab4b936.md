### Title
Cross-Organization Webhook Trust Confusion: Signature Verified Against `repository.owner.login`, but Stack Mutation Keyed on Unbound `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App/organization secret to validate the HMAC signature using `repository.owner.login` (or `organization.login`), while every webhook `Handler` subclass resolves the `Stack`/`Repository` that will actually be mutated using a *different* field of the same JSON body — `repository.full_name` — via `Repository.from_github_repo_name`. These two fields are never checked for consistency, so a party who legitimately possesses the webhook secret for organization A can forge a payload whose `repository.owner.login` says "A" (to pass signature verification) but whose `repository.full_name` points at organization B's repository, causing Shipit to act on a stack that the attacker has no authorization over.

### Finding Description
The verification step binds trust to the organization name: [1](#0-0) [2](#0-1) 

`repository_owner` is read from `params.dig('repository', 'owner', 'login')` (falling back to `params.dig('organization', 'login')`), and `Shipit.github(organization: repository_owner)` returns the `GithubApp` instance configured for that organization, whose `webhook_secret` is used for the HMAC check. This proves the sender knows organization A's secret — nothing more.

Immediately after, `create` dispatches the parsed JSON body, untouched, to every registered handler for the event: [3](#0-2) 

Every handler resolves the target `Repository`/`Stack` from a *separate* payload field, `repository.full_name`, with no reference back to the verified `repository_owner`: [4](#0-3) 

For example, `PushHandler` uses this to select stacks and immediately triggers a GitHub sync against arbitrary attacker-supplied `after` (target SHA): [5](#0-4) 

The same unbound `repository.full_name` lookup pattern recurs across the pull-request handlers (`closed_handler.rb`, `edited_handler.rb`, `label_capturing_handler.rb`, `reopened_handler.rb`, `unlabeled_handler.rb`), all of which archive/unarchive review stacks or mutate pull request state for whatever repository `full_name` names, independent of which organization's secret validated the request.

**Equality that should hold but doesn't:** `organization that authenticated the request (repository.owner.login / webhook secret used)` == `repository whose Stack is mutated (repository.full_name)`. Before the attacker's request, both fields are always consistent because GitHub itself generates them together. After an attacker crafts a raw POST body directly to the `/github/webhooks` endpoint (this is a public, unauthenticated HTTP endpoint — no `ApiClient` token, session, or GitHub App private key is required, only knowledge of *some* organization's `webhook_secret`, which any admin of that organization legitimately possesses since they configured it in their own GitHub org's webhook settings), the two fields diverge: the signature is valid for org A, but the acted-upon `full_name` names org B's repository.

### Impact Explanation
An entity that is a legitimate GitHub organization admin for org A (and therefore knows only org A's `webhook_secret`) can forge webhook deliveries that pass Shipit's signature check yet mutate stacks belonging to org B, whom the attacker has no relationship with. Concretely this enables:
- Forcing `GithubSyncJob`/`stack.sync_github` on org B's stack with an attacker-chosen `after` SHA (`push_handler.rb`), influencing which commit is considered "head" for org B's deploy pipeline.
- Archiving/unarchiving org B's review stacks (`reopened_handler.rb`, `unlabeled_handler.rb`, `closed_handler.rb`), and mutating org B's pull request records (`edited_handler.rb`, `label_capturing_handler.rb`).

This is a cross-repository/cross-organization write performed without authorization from the affected organization, satisfying the "cross-repository writes" / "unauthorized deploy" impact bar.

### Likelihood Explanation
Requires only that the attacker is an admin of *any* organization already registered in Shipit's `github_apps` configuration (i.e., knows that org's own `webhook_secret`) and can send a raw HTTP POST with a crafted body to the public webhook endpoint. No Shipit session, `ApiClient` token, or the target organization's own secret is needed — only the mismatch between the verification field and the mutation field.

### Recommendation
In `Shipit::Webhooks::Handlers::Handler#stacks` (and every subclass duplicating this logic), assert that the resolved `Repository`'s owner/organization matches the `repository_owner`/organization that was cryptographically verified in `WebhooksController#verify_signature`, rejecting the payload (422) on mismatch. Alternatively, pass the verified organization down to handlers and scope `Repository.from_github_repo_name` lookups to that organization.

### Proof of Concept
1. Attacker is an admin of GitHub organization `attacker-org`, registered in Shipit with `webhook_secret = S`.
2. Attacker crafts a `push` event JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "full_name": "victim-org/victim-repo",
    "owner": { "login": "attacker-org" }
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(S, body)` using their own known secret `S`.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: "attacker-org")` (from `repository.owner.login`), successfully validates the signature against `S`.
5. `PushHandler#process` resolves stacks via `Repository.from_github_repo_name("victim-org/victim-repo")` and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` on `victim-org`'s stack — a mutation the attacker was never authorized to trigger. [6](#0-5)
