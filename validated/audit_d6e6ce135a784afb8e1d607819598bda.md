### Title
Uncaught exception from malformed address chash decoding due to insufficient length validation - ([File: chash.js])

### Summary
`isChashValid()` in `chash.js` validates only the *string length* of an attacker-supplied encoded address (32 or 48 characters) before decoding it, but does not validate that the decoded bytes actually have the exact expected bit-length before feeding them into `separateIntoCleanDataAndChecksum()`, which throws a hard, uncaught `Error` on any length mismatch. This mirrors the root cause of the reported CVE-2025-21716 (`vxlan_vnifilter_dump`): a length check performed on the outer container (netlink message / string length) is not sufficient to guarantee the inner, fixed-structure parsing routine receives data of the length it assumes, and the code proceeds to process it as if it were validated, resulting in undefined/crashing behavior.

### Finding Description
`isChashValid(encoded)` first checks only `encoded.length === 32 || encoded.length === 48`: [1](#0-0) 

The `try/catch` block covers only the decode call (`base32.decode` / `Buffer.from(encoded, 'base64')`). `Buffer.from(str, 'base64')` in Node.js is lenient: it silently skips characters that are not part of the base64 alphabet rather than throwing, so a 48-character string with malformed/invalid base64 characters can decode into a `Buffer` whose length is *not* the expected 36 bytes (288 bits).

The subsequent processing, which is **outside** the `try/catch`, assumes the decoded buffer has an exact bit length of 160 or 288: [2](#0-1) 

`buffer2bin()` converts whatever length the decode produced into a bit string: [3](#0-2) 

`separateIntoCleanDataAndChecksum()` then hard-throws if the bit-string length is not exactly 160 or 288: [4](#0-3) 

Because this `throw` happens outside any `try/catch` in `isChashValid`, it propagates as an unhandled synchronous exception to whatever calling code invoked chash/address validation (typically `isValidAddress` in `validation_utils.js`, which underlies address validation for unit authors, outputs, asset definer/attestor addresses, AA definitions, and other oscript address checks reachable directly from a posted unit, an AA trigger, or an asset definition).

### Impact Explanation
Any code path that calls address validation on attacker-controlled strings (author/output addresses in a posted unit, definer/attestor addresses in an asset definition, addresses embedded in AA definitions or trigger data, address literals evaluated by oscript) can be made to crash the validating process with a single crafted 48-character (or 32-character) string that passes the length pre-check but decodes to a buffer of the wrong bit length. Because unit/AA/asset validation is exercised synchronously on every full node and light node/wallet that processes the offending unit or trigger, this can produce a network-wide crash/hang on ingestion of a single malicious unit, i.e., nodes are unable to confirm new units — one of the explicitly accepted high-impact outcomes for this exercise.

### Likelihood Explanation
The length pre-check (`encoded.length === 32 || 48`) is trivial for an attacker to satisfy while still supplying invalid base64/base32 content, since `Buffer.from(_, 'base64')`'s lenient decoding is a well-known Node.js behavior (it does not validate the alphabet strictly). No special privileges are needed — any user able to post a unit, submit an AA trigger, or define an asset/AA with an address-shaped field can trigger the path.

### Recommendation
- In `isChashValid`, validate the *decoded* buffer's length (must equal exactly 20 bytes for the 160-bit case or 36 bytes for the 288-bit case) immediately after decoding and before calling `buffer2bin`/`separateIntoCleanDataAndChecksum`, returning `false` on mismatch instead of allowing an exception to propagate.
- Wrap the full body of `isChashValid` (not just the decode call) in `try/catch`, returning `false` on any error, consistent with how the function is documented to behave (return boolean, never throw).
- Add a regression test that feeds `isChashValid` a 48-character string containing invalid base64 characters (e.g., spaces or symbols outside the base64 alphabet) and asserts the function returns `false` rather than throwing.

### Proof of Concept
```js
const chash = require('./chash.js');

// 48 characters (passes the length check), but contains characters
// outside the base64 alphabet ('!','@', etc.), causing Buffer.from
// to silently drop them and return a buffer shorter than 36 bytes.
const malformed = '!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!'.slice(0, 48);

try {
    chash.isChashValid(malformed);
    console.log('no crash');
} catch (e) {
    console.log('UNCAUGHT EXCEPTION:', e.message); // "bad length=..." thrown, not caught
}
```
This same malformed string, when embedded as an address field in a unit's author/output, an asset definer, or an AA trigger/definition, will propagate this uncaught exception into the node's unit/AA/asset validation pipeline whenever `isValidAddress`/`isChashValid` is invoked on it.

**Note on verification limits:** Due to tool-call budget constraints, I was not able to fully trace every call site of `isValidAddress` in `validation_utils.js` in this session (only located via `grep_search`, content not read) to enumerate all reachable trigger points (e.g., exact line numbers in `validation.js`/`definition.js`/`aa_validation.js` calling `isValidAddress`). The core defect in `chash.js` (missing length re-validation after decode, and an incomplete `try/catch` scope) is confirmed directly from the source shown above; a full node session would be needed to enumerate every reachable call site with certainty.
