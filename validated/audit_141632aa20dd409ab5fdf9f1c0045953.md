**Analysis:** `PseudoGasContext::charge_struct_tag` computes its size directly from the same `StructTag` object that is subsequently used and cached — `struct_tag.address.len() + struct_tag.module.len() + struct_tag.name.len()` — where `struct_tag` is the exact value constructed by `struct_name_index_map.idx_to_struct_tag(*struct_name_idx, type_args)` just one line earlier and returned as the module-identifying value. [1](#0-0) [2](#0-1) 

Since the charge is computed from the very fields of the `StructTag` that is later cached and returned (there is no separate/independent serialization path used for "module-context comparisons"), there is no way for an attacker-controlled `StructTag` to cause the pseudo-gas size formula to diverge from the actual byte lengths used downstream — they are read from the identical struct fields. `struct_name_idx` itself comes from an already-resolved `StructNameIndex` in the `struct_name_index_map`, not from unconstrained attacker input, so an attacker cannot inject an inconsistent address/module/name combination into this function in the first place.

This code path is also purely internal type-tag metering/caching logic used during type-to-tag conversion in the Move VM runtime. It has no connection to sender/signer/fee-payer binding, sequence numbers, chain-id, expiry, authenticator parsing, or mempool/vm-validator admission checks, so it falls outside the required admission-boundary impact categories (unauthorized execution under wrong sender/signer/fee-payer, replay/expiry/domain binding failures, or authenticator/approval-set confusion).
