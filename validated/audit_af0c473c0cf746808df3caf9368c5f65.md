### Title
Webhook signature validated against `repository.owner.login` while handlers resolve the target Stack via `repository.full_name`, enabling cross-organization webhook forgery - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`Shipit::WebhooksController#verify_signature` selects the HMAC secret to validate a webhook using `params.dig('repository','owner','login')`, but `Shipit::Webhooks::Handlers::Handler#repository_name` (used by `CheckSuiteHandler` and other handlers) resolves the target `Repository`/`Stack` using `params.dig('repository','full_name')`. Because these are two independently attacker-controlled JSON fields in the same unsigned payload, an attacker who legitimately controls one GitHub organization's Shipit webhook secret can set `repository.owner.login` to their own org (so their real secret is selected and the signature verifies) while setting `repository.full_name` to `victim-org/repo` (so the handler mutates the victim's Stack/Commit rows).

### Finding Description
The broken binding: the code assumes `repository_owner` (`app/controllers/shipit/webhooks_controller.rb:61`, `params.dig('repository','owner','login')`) equals the owner embedded in `repository.full_name` (`app/models/shipit/webhooks/handlers/handler.rb:37`, `payload.dig('repository','full_name')`). These are never checked against each other.

Path:
1. `verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-30`) computes `repository_owner` from `repository.owner.login` (falling back to `organization.login`), fetches `github_app = Shipit.github(organization: repository_owner)`, and verifies `X-Hub-Signature` against `request.raw_post` using that app's `webhook_secret` (`lib/shipit/github_app.rb:76-83`).
2. If verification passes, `create` (`app/controllers/shipit/webhooks_controller.rb:10-15`) parses the same raw body and dispatches to handlers, e.g. `CheckSuiteHandler#process` (`app/models/shipit/webhooks/handlers/check_suite_handler.rb:13-17`), which calls `stacks`, defined in `Handler#stacks` (`app/models/shipit/webhooks/handlers/handler.rb:32-38`) as `Repository.from_github_repo_name(repository_name)&.stacks`, where `repository_name = payload.dig('repository','full_name')`.
3. `Repository.from_github_repo_name` (`app/models/shipit/repository.rb:53-56`) splits `full_name` on `/` and looks up by `owner`/`name` — independent of whatever `repository.owner.login` was.

Attacker request: attacker administers `org-attacker`'s GitHub App installation on the Shipit host (a legitimate, low-privilege precondition — they only know their own org's secret). They craft a JSON body for a `check_suite` event where `repository.owner.login = "org-attacker"` and `repository.full_name = "org-victim/repo"`, with a matching `check_suite.head_branch`/`head_sha` for a stack that exists under `org-victim/repo`. They compute `X-Hub-Signature` using `org-attacker`'s genuine `webhook_secret` over the raw JSON body and POST to `/webhooks`.

`verify_signature` selects `Shipit.github(organization: 'org-attacker')`, verifies successfully (since the attacker signed with the correct secret for that org), and the request proceeds to `create`, where `CheckSuiteHandler` resolves the stack for `org-victim/repo` and calls `stack.commits.where(sha: ...).each(&:schedule_refresh_check_runs!)` — a write/side-effect against the victim organization's data, authorized only by the attacker's own organization's secret.

None of the existing guards prevent this: `drop_unhandled_event` only checks the event is handled; `verify_signature` never cross-checks `repository.owner.login` against `repository.full_name`; `ExplicitParameters` schemas for handlers (e.g. `CheckSuiteHandler.params`) only validate presence/type of `check_suite.head_sha`/`head_branch`, not repository identity; there is no model-level binding between the two fields since they come from the same untrusted JSON body.

### Impact Explanation
An attacker who legitimately owns one GitHub org's Shipit App installation (and thus its own `webhook_secret`) can forge webhooks that are accepted as authentic for **any other** organization/repository hosted on the same Shipit instance, as long as they can guess or observe a valid `full_name`, branch, and commit SHA for that victim stack. For `check_suite`, this triggers `schedule_refresh_check_runs!` on arbitrary commits of the victim stack. Other handlers that also key off `repository.full_name` via `Handler#stacks`/`repository_name` (e.g. `push`, `status`) are similarly exposed to have their `GithubSyncJob`/status updates falsely attributed to a repository the attacker does not own. This is a cross-tenant authentication-bypass class issue matching the "Critical: payload for one repository mutating another's stack/commit" category, and is repeatable against any victim stack whose full name/branch/sha the attacker can discover.

### Likelihood Explanation
Preconditions are modest: the attacker must control (own) at least one GitHub organization that has its own Shipit GitHub App/webhook configuration on the target Shipit instance — a legitimate, unprivileged tenant of the same Shipit deployment, not a Shipit operator or victim-org maintainer. No Shipit session, API token, or victim secrets are needed. Constructing the forged JSON body and HMAC signature is trivial (standard HTTP POST + HMAC-SHA1 with a secret the attacker legitimately possesses). The main constraint is guessing/knowing the victim's `full_name`, branch name, and a commit SHA, which are often discoverable (public repos, PR branch names, commit SHAs from public GitHub activity).

### Recommendation
Bind signature verification to the same repository identity the handlers use. Concretely, in `verify_signature` derive `repository_owner` from `repository.full_name` (splitting on `/`) instead of, or in addition to, `repository.owner.login`, and reject the request if `repository.owner.login` (when present) does not match the owner parsed from `repository.full_name`. Alternatively, verify the signature using the secret for the owner parsed from `full_name`, and independently validate that `owner.login`/`organization.login` agree before proceeding.

### Proof of Concept
Minitest plan (in `test/controllers/webhooks_controller_test.rb`, out-of-scope directory but describing the reproducible test):
1. Configure two orgs in `Shipit.app.github` test config: `org-attacker` (with a known `webhook_secret_a`) and `org-victim` (with `webhook_secret_v`), and create `shipit_stacks` fixture for `org-victim/repo` with branch `master` and a known commit `sha`.
2. Build payload:
```ruby
body = {
  action: 'completed',
  check_suite: { head_sha: victim_commit.sha, head_branch: 'master' },
  repository: { owner: { login: 'org-attacker' }, full_name: 'org-victim/repo' }
}.to_json
signature = "sha1=" + OpenSSL::HMAC.hexdigest('sha1', 'webhook_secret_a', body)
```
3. `request.headers['X-Github-Event'] = 'check_suite'; request.headers['X-Hub-Signature'] = signature`
4. `post :create, body:, as: :json`
5. Assert both sides of the equality: `repository_owner` computed by the controller equals `"org-attacker"`, while `Repository.from_github_repo_name('org-victim/repo').owner` equals `"org-victim"` — i.e., they differ.
6. Assert `response.status == 200` (accepted) and assert `RefreshCheckRunsJob` was enqueued / `victim_commit.reload` side effects occurred, proving org-attacker's signature mutated org-victim's stack. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4)

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
