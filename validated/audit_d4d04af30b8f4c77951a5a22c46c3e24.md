### Title
World-Readable Private Textcoin Payload File Exposes Mnemonic and Private Payment Chains - (File: wallet.js)

### Summary
`storePrivateAssetPayload()` in `wallet.js` writes a zip file to disk containing the plaintext mnemonic and private payment chains for a private-asset textcoin using `fs.writeFile(fullPath, zipFile, cb)` with no explicit file mode, and no prior secure-creation step (no `O_EXCL`/`0600` flags, no `fs.chmod` call). This mirrors the Ansible `atomic_move` flaw (CVE-2020-1736 / CWE-732): a security-sensitive file is created with the platform default permissions (typically `0644` under a standard umask), making it world-readable to any local user/process on the host, rather than being restricted to the wallet owner.

### Finding Description
`storePrivateAssetPayload(fullPath, cordovaPathObj, mnemonic, chains, cb)` builds a JSON object containing `mnemonic` and `chains` (the private payment chain elements needed to redeem a private asset textcoin), zips it, and on non-Cordova platforms saves it via: [1](#0-0) 
`fs.writeFile` here uses Node's default mode (`0o666` masked by the process umask, commonly resulting in `0644`), so any other local account can read the file and recover the mnemonic — which by itself is sufficient to derive the private key (`expandMnemonic`) and privately-transferred asset chains for that textcoin, exactly analogous to `expandMnemonic()`'s derivation logic: [2](#0-1) 
There is no companion call to `fs.chmod`, `fs.open` with an explicit restrictive mode, or writing to a temp file with `0600` before an atomic rename — the same class of gap the Ansible advisory describes for `atomic_move`.

### Impact Explanation
The stored file is the complete redemption material for a private-asset textcoin (mnemonic + private chains), i.e., spendable value transferred as a private payment. If another local user or process on the same host as the wallet software can read the file (default `0644` permission), they can reconstruct the private key via `expandMnemonic()` and claim/spend the textcoin themselves before the intended recipient does, resulting in unauthorized loss of funds for the sender/recipient of a private payment — directly matching the "unauthorized spending" / "AA or private-payment counterparty fund loss" impact category.

### Likelihood Explanation
Exploitation requires local file-system access on the same machine as the wallet process (e.g., a shared or multi-tenant host, or another compromised/unprivileged process on the user's machine) — this is a real-world condition on shared systems and matches the original CVE's local, low-privilege attacker model (`AV:L/PR:L`). Any user of the wallet application who exports a private textcoin payload (a supported, user-reachable flow) is affected without requiring any additional attacker action beyond local file read.

### Recommendation
When writing `storePrivateAssetPayload`'s output file, create it with an explicit restrictive mode (e.g., `fs.writeFile(fullPath, zipFile, { mode: 0o600 }, cb)` or `fs.open(fullPath, 'w', 0o600, ...)`), and additionally call `fs.chmod(fullPath, 0o600)` after write to cover cases where the file already exists with looser permissions. Apply the same restrictive-mode pattern to any other sensitive file writes in the wallet code path (e.g., mnemonic export, key backups).

### Proof of Concept
1. On a shared/multi-user host, use the wallet's private-textcoin send feature, which internally calls `storePrivateAssetPayload(fullPath, ..., mnemonic, chains, cb)` [3](#0-2) .
2. After the call completes, inspect the resulting file's permissions on disk (`ls -l fullPath`); observe it is world-readable (e.g., `-rw-r--r--`) because `fs.writeFile` was called without a `mode` option.
3. As a second local unprivileged user/process, read the file, unzip it, and parse the JSON to extract `mnemonic`.
4. Run `expandMnemonic(mnemonic)` (or equivalent HD-derivation logic) to derive the private key and address, then broadcast a claiming transaction before the legitimate recipient, resulting in theft of the transferred funds.
