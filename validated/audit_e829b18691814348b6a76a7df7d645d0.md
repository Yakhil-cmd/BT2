### Title
Integer-precision overflow in divisible-asset denomination cap validation allows `cap` / actual-supply mismatch - (File: validation.js)

### Summary
`validateAssetDefinition()` computes `total_cap_from_denominations` by summing `denomInfo.count_coins * denomInfo.denomination` for each denomination entry supplied by the asset-defining unit's author, then compares that sum to the declared `payload.cap`. Both `count_coins` and `denomination` are only checked with `isPositiveInteger()`, which accepts any finite JS number, including values up to `Number.MAX_SAFE_INTEGER`. Because JavaScript numbers are IEEE-754 doubles, multiplying two such large integers can silently lose precision (unlike a wraparound as in the TensorFlow C++ report, but functionally analogous: an attacker-controlled multiplication of large operands produces a wrong/rounded result that a subsequent equality check treats as valid) similarly to the reported `output_size *= dim.size()` overflow used to defeat downstream size checks. [1](#0-0) 

### Finding Description
Any unprivileged unit author can post an `asset` message defining a divisible... actually the vulnerable path is specifically for **fixed/indivisible denominations** with `count_coins`. The author supplies an array of `{denomination, count_coins}` pairs. Each field is validated only with `isPositiveInteger`, and `denomination` is bounded by `constants.MAX_CAP` only under an MCI-gated condition, while `count_coins` has no upper bound at all: [2](#0-1) 

The code then accumulates:
```
total_cap_from_denominations += denomInfo.count_coins * denomInfo.denomination;
```
and later requires `payload.cap === total_cap_from_denominations`: [3](#0-2) 

Because `count_coins` and `denomination` are independently controlled 53-bit-range integers, their product can exceed `Number.MAX_SAFE_INTEGER` (2^53), at which point double-precision arithmetic rounds the result. An attacker can choose `count_coins` and `denomination` such that the *rounded* product happens to equal a chosen `payload.cap`, even though the true mathematical product (i.e., the real maximum issuable supply implied by the denomination table) differs from the declared `cap`. This is the same class of bug as the reported TensorFlow issue: an integer multiplication over attacker-supplied dimensions/factors that is not checked for safe range before being used to validate/bound a downstream quantity.

Later, actual issuance of indivisible coins in `indivisible_asset.js` uses `count_coins_to_issue * denomination` to compute `issue_amount` for each denomination row pulled from `asset_denominations`: [4](#0-3) 

If the denomination table was accepted with a `cap` that doesn't match the true product due to precision loss, the on-chain state (`asset_denominations`, `count_coins`, `cap`) becomes internally inconsistent versus what full nodes computing balances/aggregate caps expect, and this inconsistency is deterministic and would be replicated identically by every full node re-validating the same unit (both use the same double-precision arithmetic), so it would not itself cause a fork — but it does let an attacker publish an asset whose declared `cap` does not reflect the real maximum supply obtainable from the denomination table, effectively defeating the cap/count_coins consistency guarantee that other code (and asset consumers relying on `cap` as the ceiling on supply) depend on.

### Impact Explanation
If an attacker can construct `count_coins`/`denomination` pairs whose double-precision product silently differs from the true integer product while still satisfying `payload.cap === total_cap_from_denominations`, they can issue an indivisible asset whose actual issuable supply differs from its advertised `cap`. Since `cap` is relied upon elsewhere (e.g., AA logic reading `asset[$asset].cap`, or off-chain/on-chain consumers assuming `cap` bounds total supply) as a hard investment/trust guarantee, this could enable supply inflation beyond the declared cap for a specific asset, undermining any AA or contract logic that conditions fund release on total supply being bounded by `cap`.

### Likelihood Explanation
Exploitation requires the attacker to find `count_coins`/`denomination` values near or above `Number.MAX_SAFE_INTEGER` (both individually bounded only by JS "positive integer", and `denomination` bounded by `MAX_CAP` only after a specific MCI upgrade) such that the double-precision multiplication rounds to the desired `cap`. This is a non-trivial but mechanical numerical search (double rounding is deterministic and can be brute-forced/solved for), and posting an `asset` definition message is fully permissionless — reachable by any unit author, including from an AA's `asset` message. No special privilege, race condition, or peer collusion is needed.

### Recommendation
- Reject denomination/cap computations where `count_coins * denomination` or the running `total_cap_from_denominations` exceeds `Number.MAX_SAFE_INTEGER` (or exceeds `constants.MAX_CAP` unconditionally, not only after `pemCurvesFixMci`), returning a validation error instead of silently accepting the (possibly rounded) result.
- Perform the multiplication/accumulation using integer-safe arithmetic (e.g., BigInt) and validate against `MAX_CAP` before comparing to `payload.cap`.
- Apply the `denomination > MAX_CAP` check unconditionally rather than gating it behind `pemCurvesFixMci`/`hasBall` conditions, consistent with the fix pattern already used elsewhere in the same function.

### Proof of Concept
Conceptual (not executed, since only the index is available — exact double-rounding values would need to be computed with a script using `Number` semantics):
1. Choose two positive integers `count_coins` and `denomination`, each individually a "positive integer" per `isPositiveInteger`, such that their exact mathematical product `P = count_coins * denomination` exceeds `2^53` and, due to IEEE-754 rounding, JavaScript evaluates `count_coins * denomination` to a rounded value `P' ≠ P`.
2. Post an `asset` definition unit (or AA `asset` message) with `denominations: [{denomination, count_coins}]` and `cap: P'` (the rounded value the code will actually compute), causing `total_cap_from_denominations === payload.cap` to pass in `validateAssetDefinition()`. [5](#0-4) 
3. The asset is accepted with `cap = P'`, while `asset_denominations` stores the real `count_coins`/`denomination` pair; subsequent issuance via `issueNextCoin()` in `indivisible_asset.js` computes `issue_amount = count_coins_to_issue * denomination` per batch, and across the full denomination table the true total issuable amount is `P`, not `P'`, breaking the cap invariant that `total_cap_from_denominations` was meant to enforce. [4](#0-3)
