Investigation confirms the reward classification is structurally safe from double-counting. `get_rewards_and_num_partitions` reads `self.rewards` per-`Bank`, and each `Bank` instance's `rewards` vector is populated exactly once by a single code path: `RewardType::Voting` entries come only from `distribute_reward_commissions` (invoked once, at `begin_partitioned_rewards`, on the epoch-boundary bank) keyed by the commission collector address, while `RewardType::Staking` entries come only from the later partitioned-distribution banks via `build_updated_stake_reward`, keyed by the stake account address [1](#0-0) . The unit test `test_get_rewards_and_partitions` explicitly demonstrates this partitioning — the epoch-boundary bank exposes only `Voting` rewards, and each subsequent partition bank exposes only `Staking` rewards, with the total count across all partition banks exactly equal to `num_rewards` (no overlap) [2](#0-1) .

More importantly, the commission and stake-reward amounts are not duplicate copies of the same lamports but a single up-front split of one inflation reward: `calculate_stake_rewards_and_commissions` computes, per delegation, a `stake_reward` and a `reward_commission` via `redeem_delegation_rewards`, which are mutually exclusive components summed to the delegation's total point-value reward [3](#0-2) . The test `test_rewards_computation` verifies `stake_rewards.total_stake_rewards_lamports + total_reward_commissions == expected_rewards`, proving no double counting occurs even in aggregate accounting [4](#0-3) .

Even if an attacker sets a vote account's commission collector to the same pubkey as their own stake account (or any address they control), this only means the attacker's own address is credited once via the `Voting`-typed commission payment (from `distribute_reward_commissions`) and once via the `Staking`-typed stake reward (from the separate stake-account credit), each representing a distinct, non-overlapping portion of a single already-split reward amount — this is the intended commission/reward split design, not a duplication of the same lamports under two classifications. There is no mechanism by which the same lamport amount is reported/credited twice under both `RewardType::Voting` and `RewardType::Staking`.
