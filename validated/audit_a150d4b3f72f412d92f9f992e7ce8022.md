Based on the code evidence gathered, this describes a real and reproducible vulnerability in the burnchain stacking-operation identity model.

### Title
Unauthorized permanent freezing of victim STX via forged `PreStxOp`/`StackStxOp` sender identity - (File: stackslib/src/chainstate/burn/operations/stack_stx.rs)

### Summary
`PreStxOp::parse_from_tx` derives the `output` (later used as `StackStxOp.sender`) purely from the first Bitcoin transaction output's address, with no cryptographic link to the Bitcoin inputs' signing keys. Any attacker who knows a target's Stacks address and current unlocked balance can craft a `PreStxOp`/`StackStxOp` pair naming that address as `sender` using only their own Bitcoin UTXOs, causing the victim's real STX to be locked via `stack-stx` with attacker-chosen reward address and self-authorized `signer-key`.

### Finding Description
The broken equality: "the STX locked by a `StackStxOp` == STX owned by the Stacks address that cryptographically authorized this specific lock, via its own key or Bitcoin input" is violated. In reality, the `sender`/`output` field is populated solely from `outputs.get(0)....address...try_into_stacks_address()` in `PreStxOp::parse_from_tx` [1](#0-0) , with no requirement that this address relate to the transaction's own inputs/signing keys.

`StackStxOp::get_sender_txid` only requires that the spending transaction's first input reference `vout == 1` of a prior `PreStxOp` transaction [2](#0-1) . `Burnchain::classify_transaction` then looks up the `PreStxOp` purely by `pre_stx_txid` via `pre_stx_op_map.get(...)` / `burnchain_db.find_burnchain_op(...)` and passes `pre_stack_stx.output` directly as `sender` into `StackStxOp::from_tx`, with no additional identity check binding it to whoever actually spends that UTXO [3](#0-2) .

The existing test suite even demonstrates and validates this exact behavior as "expected": a single Bitcoin key is used to build both the `PreStx` and `StackStx` transactions, but the resulting `op.sender`/`op.output` is a distinct, arbitrary `StacksAddress` (`Hash160([1;20])`) with no relationship to the signing key [4](#0-3) .

Downstream, `process_stacking_ops` executes `run_contract_call` with `sender` as the `tx-sender` principal directly against `stack-stx` in the active PoX contract [5](#0-4) . In `pox-4.clar`'s `stack-stx`, the checks performed are: not already stacking, not delegating, sufficient `stx-get-balance tx-sender`, and `consume-signer-key-authorization` [6](#0-5) . None of these verify that `tx-sender` (the victim) authorized the operation — the signer-key authorization only proves that the *signer* (fully attacker-controlled key) approved a given `(pox-addr, amount, period)` tuple, not that the *stacker* (victim) consented. The only real constraint is that the victim's on-chain balance covers the amount, which is public knowledge.

Exploit flow: attacker's own Bitcoin wallet builds a `PreStxOp` with `output` = target's Stacks address; attacker spends `vout=1` of that transaction to build a `StackStxOp` with `signer_key`/`signer-sig` under the attacker's own key, `stacked_ustx` <= target's known unlocked balance; the node applies this and calls `pox_lock_v4`, permanently locking the target's real STX [7](#0-6) .

### Impact Explanation
The victim's own unlocked STX is locked into an attacker-chosen PoX reward address/signer for up to the max lock period with zero consent — this is a permanent (for the lock duration) freezing of arbitrary victims' STX, matching the Critical severity category ("permanent freezing of staked STX"). It is repeatable against any address with sufficient unlocked STX, and costs the attacker only dust-level Bitcoin fees per attempt.

### Likelihood Explanation
Preconditions are minimal: the attacker needs a Bitcoin wallet (any UTXO), knowledge of the target Stacks address (public), and the target's current unlocked balance (public/queryable). No privileged role, no compromised keys, and no interaction with the victim are required. This is fully within the stated attacker capability of "craft burnchain stacking ops from their own Bitcoin inputs." The attack is deterministic and repeatable against any qualifying address.

### Recommendation
Bind the `sender`/`output` identity of `PreStxOp`/`StackStxOp` (and the analogous `TransferStxOp`, `DelegateStxOp`, `VoteForAggregateKeyOp`) to the Bitcoin transaction's actual signing key(s) (e.g., derive the Stacks address from the input's public key rather than an arbitrary output), or require a Stacks-side signature/consent artifact proving the named `sender` authorized the stacking action before invoking `stack-stx` on its behalf.

### Proof of Concept
Rust integration test (in `stackslib/src/burnchains/tests/db.rs` style, extending the existing `test_get_stack_stx_ops`/similar test at lines 489-525):
1. Construct a single attacker-controlled Bitcoin keypair/UTXO.
2. Build a `PreStxOp` Bitcoin transaction whose first output address decodes to `victim_addr` (an arbitrary target `StacksAddress`, e.g. `Hash160([9;20])`), signed entirely by the attacker's key.
3. Spend `vout=1` of that transaction with a `StackStxOp` payload specifying `stacked_ustx = victim_balance`, `num_cycles`, and attacker's own `signer_key`/`signer-sig` authorizing an attacker-chosen `pox-addr`.
4. Feed both transactions through `Burnchain::classify_transaction` / chain processing, then run `process_stacking_ops`.
5. Assert (equality before/after):
   - Before: `get_account_stx_balance(victim_addr).amount_locked() == 0`.
   - After: `get_account_stx_balance(victim_addr).amount_locked() == victim_balance` and `stacking-state` for `victim_addr` reflects the attacker-chosen `pox-addr`/`signer-key`, despite `victim_addr`'s private key never having signed anything.

/// Lock up STX for PoX for a time.  Does NOT touch the account nonce.
pub fn pox_lock_v4(
    db: &mut ClarityDatabase,
    principal: &PrincipalData,
    lock_amount: u128,
    unlock_burn_height: u64,
) -> Result<(), LockingError> {
    assert!(unlock_burn_height > 0);
    assert!(lock_amount > 0);

    let mut snapshot = db.get_stx_balance_snapshot(principal)?;

    if snapshot.has_locked_tokens()? {
        return Err(LockingError::PoxAlreadyLocked);
    }
    if !snapshot.can_transfer(lock_amount)? {
        return Err(LockingError::PoxInsufficientBalance);
    }
    snapshot.lock_tokens_v4(lock_amount, unlock_burn_height)?;

    debug!(
        "PoX v4 lock applied";
        "pox_locked_ustx" => snapshot.balance().amount_locked(),
        "available_ustx" => snapshot.balance().amount_unlocked(),
        "unlock_burn_height" => unlock_burn_height,
        "account" => %principal,
    );

    snapshot.save()?;
    Ok(())
