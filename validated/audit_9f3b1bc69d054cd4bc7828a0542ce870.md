### Title
Unallowlisted PR-label-derived environment keys (including `BASH_ENV`) are merged into the env passed to `PTY.spawn` for shell-interpreted `shipit.yml` steps - (File: `app/models/shipit/review_stack.rb`, `lib/shipit/task_commands.rb`, `lib/shipit/command.rb`)

### Summary
`ReviewStack#env` turns every pull-request label name into an environment-variable **key** (uppercased, value hard-coded to `"true"`) with no allowlist, and that hash is merged, last and unfiltered, into the process environment `Command#unbundled_env` hands to `PTY.spawn`. A PR labeled `bash_env` therefore injects `BASH_ENV=true` into the shell that executes a `shipit.yml` step for that review stack.

### Finding Description
The broken binding is: the set of environment variable **keys** visible to a shell-interpreted `shipit.yml` step should equal `Command::BASE_ENV ∪ Shipit.env ∪ task/deploy-defined keys`, but it instead equals that set **∪ upcase(pull_request.labels)** with no allowlist, because:

- `ReviewStack#env` does `super.merge(pull_request.labels.each_with_object({}) { |n,h| h[n.upcase] = "true" })` — any label name becomes a key, unconditionally. [1](#0-0) 
- `TaskCommands#env` merges `@stack.env` (i.e. the `ReviewStack#env` above) directly into the task's command environment. [2](#0-1) 
- `Command#initialize` stores this as `@env`, and `Command#unbundled_env` merges `@env.stringify_keys` **last**, overriding `BASE_ENV`/`PATH`: [3](#0-2) 
- `Command#start` calls `PTY.spawn(unbundled_env, *interpolated_arguments, chdir: @chdir)`, and `parse_arguments` leaves a `shipit.yml` step as a single string argument, so when that string contains shell metacharacters, `Process`/`PTY.spawn` executes it via `/bin/sh -c "<step>"` with this attacker-influenced environment attached. [4](#0-3) [5](#0-4) 
- Labels reach the stack via `LabelCapturingHandler#capture_labels`, which writes `params.pull_request.labels.map(&:name)` straight from the webhook body into `pull_request.labels` for any active, non-archived review stack, with no key/format allowlist on label names. [6](#0-5) 

The only allowlist mechanism in the codebase, `EnvironmentVariables#permit`, is not applied to `ReviewStack#env`/`TaskCommands#env` at all — it is a separate opt-in facility, so it does nothing to stop this merge. [7](#0-6) 

Exploit flow: an attacker opens/owns a PR against a repository configured with `provisioning_behavior = allow_with_label`, applies a label named `bash_env` (any case) to their PR, and pushes a file literally named `true` into their branch's checkout root (or `deploy_spec.directory`). Once the review stack is provisioned and a `shipit.yml` step is shell-interpreted, `BASH_ENV=true` is present in the spawned shell's environment; a `bash`-backed `/bin/sh` will source that relative file before running the step's actual command, executing the attacker's code with the permissions of the Shipit deploy host process. Existing test coverage confirms the key-injection half of the chain directly. [8](#0-7) [9](#0-8) 

Caveat / limitation of the exploit as literally stated: the label mechanism only controls the environment **key**, not its value — `ReviewStack#env` hard-codes the value to `"true"`, so the attacker cannot set `BASH_ENV=/attacker/arbitrary/path`; the practical RCE additionally requires (a) the specific `shipit.yml` step to be executed through an actual shell (i.e., contain shell metacharacters so `Process.spawn` invokes `/bin/sh -c`), (b) `/bin/sh` on the deploy host resolving to `bash` (true on some distros/macOS, false on Debian/Ubuntu where `/bin/sh` is `dash`, which ignores `BASH_ENV`), and (c) a file literally named `true` existing in the checkout's working directory when the step runs. This makes full RCE conditional on host configuration, but the underlying binding violation — unfiltered, fork-controllable environment **keys** reaching the process env of `PTY.spawn` — is unconditionally true and independently dangerous (it can clobber/introduce keys like `IFS`, `GIT_ASKPASS`, `LD_PRELOAD`, `ENV`, etc., all forced to `"true"`).

### Impact Explanation
Under the stated preconditions, this reaches Critical — arbitrary code execution on the Shipit deploy host under the identity that runs `shipit.yml` steps for the affected repository's review stack. Repeatable per pull request/label combination against any repository configured with `allow_with_label` (or `allow_all`/`prevent_with_label`, since `ReviewStack#env` unconditionally merges labels regardless of the provisioning mode); the blast radius is scoped to the review stack's own deploy execution, but that execution runs with the deploy host's credentials (e.g., `GITHUB_TOKEN`, deploy secrets available via `TaskCommands#env`/`base_env`), so a successful chain can exfiltrate those secrets. Even without achieving full command sourcing, the unconditional key-clobbering is a real deviation from the intended trust boundary (no fork-controllable key should alter a shell-interpreted step's environment at all).

### Likelihood Explanation
Preconditions: review stacks enabled with any provisioning behavior; the attacker must be able to add a label to their own PR (a capability the rules for this audit designate as available to an "unprivileged" attacker) and control at least one file in their PR branch; a `shipit.yml` step for the repository must be shell-interpreted (common — most `shipit.yml` steps are shell command strings); and, for the full-file-sourcing RCE, the deploy host's `/bin/sh` must be bash-backed. The key-injection portion (setting arbitrary env-var names to `"true"`) requires no special host configuration and is demonstrated purely from PR labels and existing test fixtures, so it is highly feasible and fully repeatable; the terminal RCE step depends on host `/bin/sh` implementation, which is not verifiable from this repository's code alone.

### Recommendation
Apply an explicit allowlist to keys derived from pull request labels in `ReviewStack#env` (e.g., via `EnvironmentVariables#permit` with a fixed variable-definition list, or by prefixing label-derived keys with a fixed namespace such as `SHIPIT_LABEL_<NAME>` instead of writing directly into bare variable names), and reject/strip label names that collide with reserved/sensitive environment variable names (`BASH_ENV`, `ENV`, `IFS`, `LD_PRELOAD`, `GIT_ASKPASS`, `PATH`, etc.) before merging into `Command`'s environment.

### Proof of Concept
```ruby
# test/models/shipit/review_stack_test.rb (addition)
test "#env does not allow pull request labels to inject reserved shell environment keys" do
  stack = shipit_stacks(:review_stack)
  stack.pull_request.labels = ["bash_env"]

  env = stack.env

  # Binding under test: BASH_ENV should never be attacker-settable via a label.
  refute env.key?("BASH_ENV"), "PR label should not be able to inject BASH_ENV"
end

# test/unit/command_test.rb (addition)
test "label-derived env keys reach PTY.spawn's process environment unfiltered" do
  stack = shipit_stacks(:review_stack)
  stack.pull_request.labels = ["bash_env"]
  task = shipit_tasks(:shipit_restart)
  task.stack = stack

  env = Shipit::TaskCommands.new(task).env
  assert_equal "true", env["BASH_ENV"]

  command = Shipit::Command.new("echo hi; true", env:, chdir: ".")
  assert_equal "true", command.unbundled_env["BASH_ENV"]
end
```
Both assertions demonstrate the equality violation: `stack.env["BASH_ENV"]` (expected to be absent/`nil`) equals `"true"`, and `Command#unbundled_env["BASH_ENV"]` (expected to be absent/`nil`, matching `BASE_ENV`) also equals `"true"`, confirming the fork-controllable label name reaches the exact hash passed to `PTY.spawn`.

      rescue Errno::EACCES
        raise Denied, "#{Shellwords.split(interpolated_arguments.first).first}: Permission denied"
      end
      @started = true
      self
    end
