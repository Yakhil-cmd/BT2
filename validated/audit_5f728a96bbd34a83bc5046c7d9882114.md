### Title
Base-asset "dust" outputs sent to an Autonomous Agent become permanently unspendable, freezing AA funds forever - (`aa_composer.js`)

### Summary
When `aa_composer.js` composes an AA's payment response, it only considers base-asset (bytes) outputs whose individual on-chain amount is at least `FULL_TRANSFER_INPUT_SIZE` (~60 bytes) as candidate inputs to spend. Any base-asset output landing at an AA's address with an amount below this threshold is permanently excluded from every future spend attempt by that AA, for as long as the AA exists. Since AAs have no private key and can only move funds through this exact composition logic, such dust outputs can never be spent or rescued by anyone — the AA author, the trigger senders, or any admin. Any unprivileged unit poster can trigger the creation of such dust outputs at will by simply including tiny-amount outputs (as low as 1 byte) in the `payment` message addressed to any AA.

### Finding Description
`handleTrigger`'s `sendUnit`/`completePaymentPayload` logic in `aa_composer.js` builds the AA's response payment by selecting spendable UTXOs belonging to the AA address via `readStableOutputs` and `readUnstableOutputsSentByAAs`: [1](#0-0) 

The query explicitly filters out any base-asset output with `amount < FULL_TRANSFER_INPUT_SIZE`: [2](#0-1) 

`FULL_TRANSFER_INPUT_SIZE` is derived from `TRANSFER_INPUT_SIZE` (44 + 8 + 8 = 60 bytes, plus key-size overhead after the relevant upgrade MCI): [3](#0-2) 

This filter is intentional dust-attack mitigation (per the inline comment), but it has no counterpart mechanism to ever reclaim or consolidate these excluded outputs. Meanwhile, the AA's *tracked* balance in `aa_balances` is updated unconditionally for every byte received, regardless of whether the underlying output can ever be spent: [4](#0-3) 

Any unprivileged unit poster can send a payment message to an AA address containing many small-amount outputs (each below ~60 bytes, e.g. 1 byte) alongside a normal-size output that satisfies `bounce_fees`. All these outputs are summed into `trigger.outputs.base` (satisfying the bounce-fee check performed here): [5](#0-4) 

and are individually inserted into the `outputs` table and into the AA's `aa_balances.balance`. However, each dust-sized row will forever fail the `amount>=FULL_TRANSFER_INPUT_SIZE` predicate in `readStableOutputs`/`readUnstableOutputsSentByAAs`, so it can never be selected as a `transfer` input in any subsequent AA response — not now, not after any number of MCI advances, because the AA's spending logic is entirely deterministic, protocol-enforced code with no owner key and no alternate "sweep" path.

### Impact Explanation
This causes a growing, permanent divergence between an AA's nominal `aa_balances` accounting and the actual bytes it can spend on-chain. Because AAs commonly perform "send all remaining balance" operations (`{address: "{trigger.address}"}` with no `amount`, or balance-based payouts) relying on `balance[base]`/`aa_balances`, users can be under-paid on withdrawal, or a legitimate withdrawal that should succeed can bounce with "not enough funds" because the accounted balance includes unspendable dust that isn't actually available as UTXOs to compose a real payment. Since these bytes sit at the AA address, which is not controlled by any private key, they are permanently frozen — there is no owner, admin, or AA-author code path that can ever spend an output below `FULL_TRANSFER_INPUT_SIZE`. This is a direct analog of the reported "tokens stuck forever, no rescue function" bug class, reachable by any unprivileged unit poster targeting any live AA.

### Likelihood Explanation
Trivially reachable: constructing a payment message with several outputs of e.g. 1 byte each to a target AA address, combined with a normal-size output to satisfy the AA's `bounce_fees.base` requirement, is fully within reach of any wallet/unit author and requires no special privileges, cooperation, or race condition. It can be repeated indefinitely against any deployed AA to accumulate permanently frozen dust and to widen the balance/UTXO discrepancy over time.

### Recommendation
Introduce a mechanism to consolidate or "sweep" sub-threshold outputs at an AA address — for example, allow the AA composer to merge multiple dust outputs into a single input set that collectively exceeds `FULL_TRANSFER_INPUT_SIZE` (batch-consuming several small outputs in one operation instead of requiring each individual output to meet the size threshold), or reject/return dust-sized payments to AAs at validation time rather than silently accepting them into `aa_balances` while leaving the underlying UTXO permanently unspendable.
