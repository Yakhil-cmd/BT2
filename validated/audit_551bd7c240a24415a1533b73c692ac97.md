### Title
`status` webhook for repo A writes a `Status` on victim Stack B's `Commit` due to unscoped `sha` lookup - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` looks up commits by `sha` alone (`Commit.where(sha: params.sha)`), with no constraint tying the matched `Commit` rows to the repository named in the verified webhook payload. Because `WebhooksController#verify_signature` only authenticates that a payload was signed by *some* org's `webhook_secret` (chosen via `repository_owner` in the payload), and never checks that the payload's `repository.full_name` matches the repository of the `Commit`/`Stack` being mutated, any repository whose org is configured in Shipit can inject a `Status` onto a `Commit` belonging to a completely different stack/repository, as long as a commit with the same `sha` exists there.

### Finding Description
The broken binding, stated as an equality that the code should enforce but does not:
`payload['repository']['full_name']` (the repository GitHub asserts the event is about, authenticated only at the org level) **should equal** `commit.stack.repository.full_name` for every `Commit` row mutated by the handler — but the code never checks this.

Path:
1. `WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-49`) resolves `Shipit.github(organization: repository_owner)` using `repository_owner = params.dig('repository','owner','login')` and verifies the HMAC signature against that org's `webhook_secret`. This proves the request came from GitHub for *that org*, not that it belongs to any specific repository/stack.
2. `StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`):
```ruby
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
```
`Commit.sha` is queried with no `stack_id`/repository scoping at all — [1](#0-0)  matches every `Commit` row across every `Stack`/repository sharing that sha.
3. `Commit#create_status_from_github!` → `Status.replicate_from_github!` persists a `Status` row (`state`, etc.) scoped only by `stack_id` of whichever `Commit` matched — [2](#0-1) [3](#0-2) , and this in turn triggers `commit.schedule_continuous_delivery` / `enable_ci_on_stack` on the victim stack via `after_create`/`after_commit` callbacks [4](#0-3) .

Exploit flow: Attacker owns/forks repository A within an org that has a Shipit GitHub App/webhook configuration (any org onboarded to the target Shipit instance — the attacker need not be a maintainer of any stack, just able to push to some repo in that org, or own a repo whose org is registered). Victim Stack B (any repo/org known to Shipit) already contains a `Commit` row with `sha = S`, a root commit (no parents) with fully known, public tree/author/committer/timestamps/message (since Stack B's commit history is visible via the Shipit UI/API and/or the source GitHub repository). Because Git commit hashing is purely a function of the serialized commit object (tree, parents, author, committer, message) and independent of which repository stores it, the attacker reconstructs an identical commit object in repo A using `git commit-tree` with the same tree, same author/committer identity+timestamps, same message, and no parents, producing the byte-identical sha `S`. The attacker pushes this commit to repo A and causes (or GitHub causes) a genuine `status` event to fire for repo A/sha `S` (e.g., via their own CI, or by posting a Status through the GitHub API on their own repo, which they are fully entitled to do as owner of A). GitHub delivers this as a real, correctly-signed `status` webhook to Shipit's `/webhooks` endpoint for org A. `verify_signature` passes because the signature is valid for org A. `StatusHandler#process` then matches `Commit.where(sha: 'S')`, which includes both A's own tracked commit (if any) *and* Stack B's unrelated `Commit` row, and writes the attacker-controlled `state`/`description`/`target_url`/`context` onto Stack B's commit.

Existing guards checked and found insufficient:
- `verify_signature` only binds the signature to an org, not to a specific repository or stack [5](#0-4) .
- `ExplicitParameters` schema in `StatusHandler` only validates types (`sha`, `state`, etc.), no repository field is required or checked against the matched commit [6](#0-5) .
- `Commit` has no uniqueness validation or query scoping tying `sha` lookups to `stack_id`/repository in this handler.
- `drop_unhandled_event` and `check_if_ping` are irrelevant to this path.

### Impact Explanation
A `status` payload authenticated for one repository/org can mutate `Status` records (and, transitively, trigger continuous-delivery scheduling, CI-enablement, and merge-request processing) on a `Commit` belonging to an entirely different Stack/repository/tenant — this is a cross-tenant write matching the "payload for one repository mutating another's stack/commit" Critical category. Repeatable against any victim commit whose full byte content (a root commit with no parents) is knowable/public, and against any Shipit instance hosting multiple orgs/stacks. The blast radius is bounded by the requirement of an exact sha collision via content reproduction (feasible only for root commits with fully known metadata) and by needing at least one Shipit-registered org the attacker can push into or trigger status events from.

### Likelihood Explanation
Preconditions: (1) attacker controls a repository under a GitHub org configured with a `webhook_secret` in the target Shipit instance (i.e., some org the Shipit deployment already trusts — this could be their own org if Shipit is multi-tenant/open, or a shared company org where repo creation is permitted); (2) a target `Commit` in a victim Stack is a root commit (no parents) whose tree/author/committer/timestamps/message are fully known (source is often public or accessible); (3) attacker can cause GitHub to emit a genuine `status` event for their own repo/sha (trivial — they own the repo and can set commit statuses via API or CI). No Shipit secrets, sessions, or tokens are required. The main friction is the sha-reproduction step, which is only exploitable against root commits with fully disclosed metadata, not arbitrary commits with unknown parents — this narrows but does not eliminate exploitability.

### Recommendation
Scope the `Commit` lookup in `StatusHandler#process` (and analogous handlers, e.g. check_run) to the repository asserted in the verified payload, e.g. join through `Stack`/`Repository` and filter by `repository.full_name == params.dig('repository','full_name')` (or `stack.github_repo_name`) before applying the status, rejecting/no-oping matches for commits that belong to a different repository than the one authenticated by `verify_signature`.

### Proof of Concept
Minitest plan (`test/controllers/webhooks_controller_test.rb` or `test/models/webhooks/handlers/status_handler_test.rb`):
1. Create `stack_a` bound to `repository_owner/repo-a` (org `org-a`, with a `GithubHook`/`webhook_secret` fixture) and `stack_b` bound to `victim/repo-b` (org `org-b`).
2. Create `commit_a = stack_a.commits.create!(sha: 'S', ...)` and `commit_b = stack_b.commits.create!(sha: 'S', ...)` (same `sha`, different `stack_id`).
3. Stub `GithubHook`/`verify_webhook_signature` for `org-a` to return true (simulating a genuinely signed payload for repo A).
4. POST to `/webhooks` with `X-Github-Event: status`, body `{ sha: 'S', state: 'success', repository: { full_name: 'repository_owner/repo-a', owner: { login: 'org-a' } } }`.
5. Assert:
   - Before: `commit_b.statuses.count == 0`, `commit_b.state != 'success'`.
   - After: `assert_difference('commit_b.reload.statuses.count', 1)` around the POST, and `assert_equal 'success', commit_b.reload.state` — proving Stack B's commit was mutated by a payload authenticated only for Stack A's org/repo.
