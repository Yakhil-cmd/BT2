### Title
`Shipit::Webhooks::Handlers::PushHandler`/`StatusHandler` trust `repository.full_name` / commit `sha` from the JSON body without checking they belong to the org verified by `X-Hub-Signature`, letting one org's signed webhook mutate another org's `Stack`/`Commit` - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/handler.rb], [File: app/models/shipit/webhooks/handlers/push_handler.rb], [File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App/secret to validate `X-Hub-Signature` using only `repository.owner.login` (or `organization.login`), while the handlers dispatched afterward resolve the target `Stack`/`Commit` using a completely different, unchecked field: `repository.full_name` (`Handler#repository_name`) for `PushHandler`, or a bare `sha` lookup with no repository scoping at all for `StatusHandler`. Because these two values are never cross-validated, an attacker who legitimately owns a GitHub org/repo with Shipit installed (and thus knows/controls the signing of their own webhooks) can craft a raw POST to `/webhooks` that verifies under their own org's secret but names a victim's repository (`full_name`) or a victim's commit `sha`, causing the handler to write to the victim's `Stack`/`Commit`.

### Finding Description
The broken binding, stated as an equality that the code assumes but never enforces:
`repository_owner` (used in `WebhooksController#verify_signature`, `params.dig('repository','owner','login')`) `==` the organization segment of `repository.full_name` (used in `Handler#repository_name`, `payload.dig('repository','full_name')`, to resolve `Repository.from_github_repo_name`).

Trace:
- `WebhooksController#create` reads `X-Github-Event`, dispatches to `Shipit::Webhooks.for_event(event)`, and passes the *entire raw JSON body* to each handler's `.call(params)` [1](#0-0) .
- `verify_signature` picks the GitHub App config via `Shipit.github(organization: repository_owner)` and validates `X-Hub-Signature` against the *raw body* using that org's secret [2](#0-1) . `repository_owner` is derived solely from `repository.owner.login` / `organization.login` [3](#0-2) .
- Once the signature is accepted, `PushHandler#process` calls `stacks.not_archived.where(branch:).find_each { |stack| stack.sync_github(expected_head_sha: params.after) }`, where `stacks` resolves via `Handler#repository_name`, i.e. `payload.dig('repository', 'full_name')` — a *different* JSON field than the one used to pick the signing secret [4](#0-3) [5](#0-4) .
- `StatusHandler#process` is even less scoped: it does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` with **no repository check at all**, matching a commit purely by SHA anywhere in the Shipit database [6](#0-5) .

Exploit flow: Attacker owns `attacker-org/some-repo` and has legitimately installed the Shipit GitHub App there (so they know/control the HMAC secret used to sign webhooks from that repo, satisfying "emit webhooks from a repository they own"). They POST directly to `/webhooks` (bypassing GitHub) with:
- `X-Github-Event: push`
- Body: `{"repository": {"owner": {"login": "attacker-org"}, "full_name": "victim-org/victim-repo"}, "ref": "refs/heads/master", "after": "<attacker-chosen sha>"}`
- `X-Hub-Signature`: HMAC computed with `attacker-org`'s known secret over this exact raw body.

`verify_signature` passes because it only checks `repository.owner.login == "attacker-org"` against `attacker-org`'s secret — it never checks that `full_name` starts with `attacker-org/`. `PushHandler` then resolves `Repository.from_github_repo_name("victim-org/victim-repo")` and calls `stack.sync_github(expected_head_sha: "<attacker-chosen sha>")` on the **victim's** stack. Similarly, for `status` events, the attacker need not even touch `full_name`: they only need a victim commit's `sha` (public in any public repo, or shared via fork history) to write a status onto the victim's `Commit`/`Stack` via `commit.create_status_from_github!`.

None of the existing guards catch this: `drop_unhandled_event` only checks that a handler exists for the event name; `verify_signature` validates the byte-for-byte HMAC of the body but not internal cross-field consistency; `ExplicitParameters` (`params do ... end` in each handler) only validates field *types/presence*, not their *origin*; there is no `Repository`/`Stack` ownership check tying `full_name` or `sha` back to the verified `repository_owner`.

### Impact Explanation
This is a **payload for one repository mutating another's stack/commit** — the exact Critical category defined in scope. Via `PushHandler`, an attacker can force an arbitrary victim `Stack` to call `sync_github(expected_head_sha: <attacker-controlled sha>)`, influencing what commit range Shipit believes is at the head of that branch. Via `StatusHandler`, an attacker who knows/guesses a victim commit's SHA (trivial for public repos or shared fork history) can inject a fabricated CI status (`create_status_from_github!`) onto a victim's tracked `Commit`, directly affecting deploy-safety checks for the victim's `Stack`. Both are repeatable against arbitrary victim orgs/stacks with no per-repository rate limiting mentioned, and require no privilege on the victim's side.

### Likelihood Explanation
The attacker needs: (1) their own GitHub org/repo with the Shipit GitHub App/webhook installed (fully self-serve, no privilege on Shipit), (2) knowledge of the victim's `full_name` (public) or a victim commit `sha` (public for public repos), and (3) the ability to POST directly to the Shipit webhooks endpoint with a body they construct and sign themselves. No Shipit session, API token, or GitHub secret belonging to any other party is required. This is low-cost and fully repeatable against any victim repository/stack known to Shipit.

### Recommendation
Enforce that the field used to select the signing organization and the field(s) used for entity resolution refer to the same repository: validate in `WebhooksController` (or in `Handler#repository_name`) that `payload.dig('repository','full_name')` starts with `"#{repository_owner}/"` (and equivalently constrain `StatusHandler` to only update commits whose associated `Stack`'s `Repository` owner matches `repository_owner`) before invoking any handler; reject the request (e.g. `head(422)`) on mismatch.

### Proof of Concept
Minitest plan (`test/controllers/webhooks_controller_test.rb`-style, no live GitHub):
1. Create `victim_stack` backed by `Repository` with `full_name = "victim-org/victim-repo"`, and a `Commit` under it with a known `sha`.
2. Configure Shipit's GitHub App/secret for `"attacker-org"` (as would exist for any legitimate org integration) and compute a valid `X-Hub-Signature` over a crafted push body with `repository.owner.login = "attacker-org"`, `repository.full_name = "victim-org/victim-repo"`, `ref = "refs/heads/master"`, `after = "deadbeef..."`.
3. POST to `/webhooks` with `X-Github-Event: push` and the signature computed in step 2.
4. Assert both sides of the binding: `repository_owner` extracted by the controller (`"attacker-org"`) is NOT equal to the org segment of `repository.full_name` used by `PushHandler` (`"victim-org"`), yet assert `victim_stack.reload` shows `sync_github` was invoked (e.g. stub/spy on `Stack#sync_github` and assert it was called with `expected_head_sha: "deadbeef..."` for `victim_stack`), proving the write proceeded despite the mismatch.
5. Repeat analogously for `StatusHandler`: sign a `status` event under `attacker-org`'s secret containing only `{"sha": "<victim commit sha>", "state": "success"}` (no repository scoping needed), and assert the victim `Commit`'s status was updated.
