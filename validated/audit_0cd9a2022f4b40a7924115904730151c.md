This confirms the full exploit chain. `StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`) finds commits purely `Commit.where(sha: params.sha)` — with no repository/organization scoping at all — and calls `commit.create_status_from_github!(params)`, which flows into `Commit#add_status` `(app/models/shipit/commit.rb:366-386)`. That method updates `deployable?` state and, on a transition to `success`, calls `stack.schedule_merges` and fires `ProcessMergeRequestsJob`, and `Commit#deployable?` `(app/models/shipit/commit.rb:227-229)` is exactly the predicate that gates automatic deploys/merges on `ci.require` status context. Since `StatusHandler` never checks `repository.full_name` (or any organization ownership) against the commit's stack, a forged "status" webhook can mark **any** commit/sha in the entire Shipit instance (regardless of org/repo) as `success`, satisfying `ci.require` and triggering `ProcessMergeRequestsJob`/auto-merge for a stack completely unrelated to whatever organization was used to pass signature verification.

### Title
Cross-organization webhook forgery via decoupled signature-organization and target-repository fields enables spoofed CI status and unauthorized merges - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
In multi-organization Shipit deployments, `WebhooksController#verify_signature` selects which GitHub App/webhook secret to validate a request against using `repository_owner`, a value read directly out of the untrusted, attacker-supplied JSON body (`repository.owner.login` or `organization.login`). This is a *separate* field from the ones actual event handlers use to determine which `Stack`/`Commit`/`Repository` to mutate (`repository.full_name`, or in `StatusHandler`'s case, no repository field at all — just `sha`). Because these two fields are never cryptographically bound to each other and are never cross-checked, whoever can produce a valid signature "for" any one configured organization can act on data belonging to any other organization or repository configured on the same Shipit instance.

### Finding Description
`app/controllers/shipit/webhooks_controller.rb:24-49` computes:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```
`repository_owner` is taken from the raw, unauthenticated JSON body and used to pick the `GitHubApp` (and thus the webhook secret) that must sign the request, per `lib/shipit.rb:170-181` (`github_app_config(organization)` looks up `secrets.github[organization]`). This organization-keyed secret model is a documented, supported configuration (`docs/setup.md` "Using Multiple Github Applications", `test/dummy/config/secrets_double_github_app.yml`), and per-organization `webhook_secret` is explicitly documented as **optional** (`docs/setup.md:30`, `:119`) — when absent, `GitHubApp#verify_webhook_signature` (`lib/shipit/github_app.rb:76-83`) returns `true` unconditionally with no check at all:
```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
```
The binding the engine relies on is: *the organization whose secret authenticated the request* == *the organization/repository whose state is mutated*. That equality is never enforced. `Handler#repository_name` (`app/models/shipit/webhooks/handlers/handler.rb:36-38`) and every push/pull_request handler resolve the target purely from `payload.dig('repository', 'full_name')`, a JSON key wholly independent of `repository.owner.login`. Worse, `StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`) doesn't even look at the repository at all — it does `Commit.where(sha: params.sha)`, matching any commit across the entire installation by SHA alone.

Consequently, an unprivileged party can send a POST to `/webhooks` with:
- `X-Github-Event: status`
- Body `repository.owner.login` (or `organization.login`) set to the name of any organization configured on the shared Shipit instance that has no `webhook_secret` set (an explicitly supported/optional configuration), which makes `verify_webhook_signature` return `true` for free, and
- `sha`/`state: success` set to target any commit sha belonging to a *different*, properly-secured organization's stack.

This request passes `verify_signature` entirely (no secret needed at all) and is then processed by `Shipit::Webhooks.for_event('status')`, injecting a forged "success" status onto an arbitrary commit it does not control.

### Impact Explanation
`Commit#create_status_from_github!` → `#add_status` (`app/models/shipit/commit.rb:365-386`) recomputes `Commit#deployable?` (`app/models/shipit/commit.rb:227-229`), which is the gate used by `ci.require`/merge-queue logic, and on transition to `success` triggers `stack.schedule_merges` / `ProcessMergeRequestsJob` (confirmed by `test/models/commits_test.rb:763-777`, "`#add_status` schedule a MergeMergeRequests job if the commit transition to `pending` or `success`"). A forged success status therefore can satisfy required-CI checks and trigger an automatic merge/deploy for a commit/stack the attacker has no legitimate relationship to — this is an unauthorized merge/deploy, matching the Critical impact bar. The same organization/repository decoupling also lets a party who only "authenticates" as one org spoof `push` (forcing `GithubSyncJob` with an attacker-chosen `expected_head_sha`) and `pull_request` events (creating spoofed review stacks via `ReviewStackAdapter`) against completely different organizations' repositories, which is a cross-repository write.

### Likelihood Explanation
Requires no credentials, tokens, or webhook secret of any kind — only that the Shipit instance is configured (per its own documented multi-org setup) with at least one organization lacking a `webhook_secret`, which the docs mark optional and is a realistic condition for staging/internal/less-critical orgs sharing the instance with production orgs. Organization names/handles are typically public. The `verify_signature` before_action does not tie the accepted organization to the repository/commit being mutated in any handler.

### Recommendation
Bind the authenticated organization to the object being mutated: after (not instead of) verifying the signature for `repository_owner`, every handler must confirm that the resolved `Stack`/`Repository`/`Commit` actually belongs to that same, verified organization before making any state change — e.g., `StatusHandler` should scope `Commit.where(sha: params.sha)` to commits whose `stack.repository.owner` (case-insensitively) equals the verified `repository_owner`, and similarly for push/pull_request/check_suite handlers. Additionally, stop treating a missing `webhook_secret` as an implicit "always verified"; either require a webhook secret when running in multi-organization mode, or treat "no secret configured" as "cannot be used to authenticate cross-tenant requests."
