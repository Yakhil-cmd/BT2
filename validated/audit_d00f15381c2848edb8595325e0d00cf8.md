### Title
Webhook signature is verified against an organization chosen from an unbound payload field, letting the org that "signed" the request diverge from the repository the payload actually writes to - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` picks *which* GitHub App config (and therefore which `webhook_secret`) to verify the HMAC against using `repository_owner`, a value read straight out of the untrusted, attacker-supplied JSON body (`repository.owner.login` / `organization.login`). Every downstream `Webhooks::Handlers::Handler` subclass, however, resolves which `Stack`/`Repository` to act on using a *different* field of the same body: `repository.full_name`. Nothing binds these two fields together, so on a multi-org Shipit instance an attacker who legitimately controls one configured GitHub organization (and therefore knows *its* `webhook_secret`) can forge a signature that Shipit accepts, while pointing the payload's `repository.full_name` at a stack belonging to a completely different, victim organization.

### Finding Description
- Verification: `Shipit::WebhooksController#verify_signature` calls `Shipit.github(organization: repository_owner)` and then `github_app.verify_webhook_signature(signature, raw_post)`. [1](#0-0) 
- The organization used to select the verification key comes from the body itself: [2](#0-1) 
- `Shipit.github` resolves a distinct `GitHubApp` (and distinct `webhook_secret`) per organization key when the multi-org config schema is used: [3](#0-2) 
- `verify_webhook_signature` simply HMACs the raw body with whatever secret was selected: [4](#0-3) 
- Once verification passes, the base `Handler` (and every concrete handler: `PushHandler`, `StatusHandler`, `CheckSuiteHandler`, the `PullRequest::*Handler`s) resolves the target repository/stack from a *different* payload key, `repository.full_name`, with no cross-check against the org used for authentication: [5](#0-4) [6](#0-5) [7](#0-6) 

This is the exact class of bug described in the analog rules: "an organization that authenticated versus the repository that is written." The equality that should hold is:
`organization_whose_secret_signed_the_request == owner(repository_that_handlers_write_to)`
Because both `repository.owner.login` and `repository.full_name` are independent, attacker-controlled JSON fields inside the same unsigned-until-verified body, an attacker can break this equality: sign with Org A's secret (which they legitimately know because Org A's GitHub App/webhook secret was configured for their own organization on this shared, multi-tenant Shipit instance, per the documented "Using Multiple Github Applications" feature), while setting `repository.full_name` to `OrgB/victim-repo`. [8](#0-7) 

Before the attack: request forged with `repository.owner.login=OrgB` would fail verification (attacker doesn't know Org B's secret) or with `repository.owner.login=OrgA` would only ever be routed to Org A's own repositories (since GitHub itself would populate `full_name` consistently with `owner.login`). After the attack: the attacker sets `repository.owner.login=OrgA` (signs with their own known secret, passes `verify_signature`) but `repository.full_name=OrgB/victim-repo`, and the handler layer, using only `full_name`, resolves and mutates OrgB's `Stack`/`Commit`/`PullRequest` records.

### Impact Explanation
The most severe realistic outcome is via `StatusHandler`: `commit.create_status_from_github!(params)` creates a commit `Status` for any SHA the attacker names, scoped only by `Commit.where(sha:)` — not by the authenticated organization. [7](#0-6) 
Shipit's `ci.require` deployability check relies on exactly these `Status` records to decide whether a commit is safe to deploy. By forging a fake "success" status webhook for a victim commit — signed under an org/secret the attacker legitimately controls but naming the victim repository's SHA — the attacker can satisfy CI requirements and enable an unauthorized deploy of a commit that never actually passed CI, meeting the "unauthorized deploy" Critical-impact criterion. `CheckSuiteHandler` and `PushHandler` similarly act on victim stacks (`stacks` resolved solely from `repository.full_name`) using only the forged-but-verified request, causing cross-repository writes/state changes (sync jobs, check-run refresh) attributable to organizations the attacker has no legitimate relationship with. [9](#0-8) 

### Likelihood Explanation
This requires a specific precondition: Shipit must be configured with the multi-organization GitHub App schema (documented and supported), where the attacker legitimately administers at least one of the configured organizations and thus knows that organization's `webhook_secret`, while other organizations on the same Shipit instance are untrusted to each other. Under that documented configuration, the attack requires only crafting one HTTP POST to the public `/github/webhooks` endpoint with a body whose `repository.owner.login`/`organization.login` differs from `repository.full_name`'s owner — no session, no `ApiClient` token, and no GitHub App private key are needed, only knowledge of one's own configured org's webhook secret.

### Recommendation
After the handler resolves `repository.full_name` (or the organization used for any GitHub-derived model lookup), verify it belongs to the same organization whose secret was used for `verify_signature`, e.g., compare `repository_owner` (used for signature verification) against `repository.full_name`'s owner segment before dispatching to handlers, and reject the webhook if they diverge. Alternatively, derive the signing organization strictly from `repository.full_name`'s owner (a single canonical field) rather than from a separately attacker-suppliable `repository.owner.login`/`organization.login`.

### Proof of Concept
Preconditions: Shipit configured with multi-org GitHub Apps for `OrgA` (attacker-controlled, secret known) and `OrgB` (victim, hosts a tracked `Stack` with `ci.require`).

1. Attacker crafts a `status` webhook JSON body:
```json
{
  "sha": "<victim-commit-sha-pending-ci>",
  "state": "success",
  "context": "required-ci-check",
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/victim-repo" }
}
```
2. Attacker computes `X-Hub-Signature: sha1=<hmac-sha1(OrgA_webhook_secret, raw_body)>` using the secret they know for `OrgA`.
3. POST to `/github/webhooks` with header `X-Github-Event: status`.
4. `verify_signature` calls `Shipit.github(organization: "OrgA")` and validates successfully against the attacker's own known secret. [1](#0-0) 
5. `StatusHandler#process` looks up `Commit.where(sha: params.sha)` — matching the victim's commit regardless of which org "authenticated" — and creates a fabricated success `Status`, potentially unblocking a deploy gated by `ci.require` for `OrgB/victim-repo`. [7](#0-6)

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
