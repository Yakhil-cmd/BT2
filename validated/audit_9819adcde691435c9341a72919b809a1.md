### Title
Session fixation on GitHub OAuth login completion – no session ID regeneration on `callback` - ([File: app/controllers/shipit/github_authentication_controller.rb])

### Summary
`GithubAuthenticationController#callback` binds a freshly authenticated GitHub identity to the *existing* Rack session without first invalidating/rotating that session, unlike `#logout` which does call `reset_session`. This breaks the binding "GitHub identity authenticated == session the identity is bound to," letting an attacker who fixes a session ID on a victim's browser inherit the victim's authenticated Shipit session once the victim completes the OAuth flow.

### Finding Description
The OAuth callback action performs the login by writing directly into the current session hash: [1](#0-0) 

```ruby
def callback
  return_url = request.env['omniauth.origin'] || root_path
  auth = request.env['omniauth.auth']

  return render('failed', layout: false) if auth.blank?

  session[:user_id] = sign_in_github(auth)
  session[:authenticated] = true

  redirect_to(return_url)
end
```

No `reset_session` (or session ID regeneration) is called before `session[:user_id]` is set. Compare this to `#logout`, which explicitly does the safe thing: [2](#0-1) 

Downstream, `current_user` is derived purely from `session[:user_id]`, with no other binding to the browser/agent that originally negotiated the session: [3](#0-2) 

Since Rails does not automatically rotate the session ID on privilege elevation (an application must call `reset_session` or `session.regenerate_id` itself), the cookie-encoded session identifier used *before* login remains valid and now maps to the victim's identity *after* login. Classic session fixation: an attacker who can get any (even unauthenticated) session cookie planted in the victim's browser — e.g. by visiting the Shipit host once themselves and copying the `Set-Cookie` value into the victim's browser via a subdomain cookie, a shared-Wi‑Fi cookie injection, or any means that plants a cookie for the app's domain — can then wait for the victim to complete the GitHub OAuth login. After the victim's browser calls back into `callback`, the *same* session ID the attacker already knows becomes authenticated as the victim, since the identifier itself was never regenerated.

This satisfies the "before vs. after" trust binding required by the rules: before the pull request/attack sequence, `session_id → AnonymousUser`; the attacker learns/fixes `session_id`. After the victim's OAuth completion, the binding silently becomes `session_id → victim_User` without ever changing `session_id`, i.e. the identity-to-session binding is never re-established, only appended to.

### Impact Explanation
This maps directly to the accepted High-impact category "session fixation / forced OAuth completion." Successful exploitation lets an unprivileged attacker hijack another user's fully authenticated Shipit session — including whatever authorization that user has (e.g. `Shipit.github_teams` membership check in `Authentication#force_github_authentication`), letting the attacker deploy, roll back, lock/unlock stacks, or manage API clients as the victim, without ever needing the victim's GitHub credentials, an `ApiClient` token, or repository write access.

### Likelihood Explanation
Likelihood depends on the attacker's ability to plant/fix a session cookie in the victim's browser before the OAuth login. Rails session cookies are typically scoped to the app's own domain, so this generally requires a cookie-injection vector local to that domain (e.g. a subdomain XSS, a coffee-shop/captive-portal MITM without TLS pinning, or a prior unauthenticated visit whose session ID is later shared/reused). This is a real, well-known web attack class, and the root cause here — the complete absence of `reset_session`/ID regeneration in `callback`, while it is correctly present in `logout` — is a straightforward, code-level omission rather than a theoretical concern.

### Recommendation
Call `reset_session` (or `session.regenerate_id` if you need to preserve `omniauth.origin`/other pre-login session state) at the start of `callback`, before writing `session[:user_id]` and `session[:authenticated]`. Re-derive any values needed after login (e.g. `return_url`) prior to the reset, or re-establish them after regenerating the session ID.

### Proof of Concept
1. Attacker obtains/fixes a session cookie for the Shipit host in the victim's browser (e.g., via a cookie set from a shared subdomain or a network-level cookie injection prior to TLS being established), noting the resulting session ID (or simply visiting the site anonymously and forcing the victim to reuse that identical cookie).
2. Victim, using the browser session the attacker fixed, visits `/github/auth/github/` and completes the GitHub OAuth flow, hitting `GithubAuthenticationController#callback`.
3. `callback` sets `session[:user_id] = sign_in_github(auth)` on the *same, unrotated* session — no `reset_session` occurs. [4](#0-3) 
4. Attacker, still holding the identical session cookie/ID, sends requests to Shipit; `current_user` resolves to the victim via `session[:user_id]`. [5](#0-4) 
5. Attacker now acts as the victim across all Shipit UI actions gated only by `current_user.authorized?` (deploys, rollbacks, stack locks, API client management, etc.).
