### Title
Cross-tenant CommitStatus forgery via sha-only lookup in `StatusHandler#process` bypassing organization-scoped signature verification - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` only proves that the payload was signed with the `webhook_secret` of the organization named in `params.dig('repository','owner','login')` [1](#0-0) [2](#0-1) . `StatusHandler#process` then looks up commits purely by `sha` with no scoping to that organization/repository/stack, and mutates whatever it finds [3](#0-2) . This lets any organization that has its own valid `webhook_secret` in a multi-tenant Shipit install write a `CommitStatus` onto a commit that belongs to a completely different organization's stack, as long as it knows that commit's sha.

### Finding Description
The binding that should hold is: `organization verifying the HMAC signature (params.repository.owner.login, checked against Shipit.github(organization: repository_owner).verify_webhook_signature)` == `organization owning the Commit record(s) mutated by StatusHandler#process`. These are never actually compared.

- `verify_signature` computes `repository_owner` from the incoming JSON body and fetches `Shipit.github(organization: repository_owner)`, then verifies the HMAC signature against that organization's configured `webhook_secret` [1](#0-0) . This only proves "the request bytes were signed by whoever holds attacker-org's `webhook_secret`" — i.e., authenticates the sender's own tenant, not the tenant of the data referenced inside the payload.
- `StatusHandler#process` receives the same payload and does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [3](#0-2) . This query is global across the entire `commits` table — there is no join or filter on `stack_id`, `repository`, or organization matching `repository_owner`.
- `create_status_from_github!` writes a `CommitStatus` row via `statuses.replicate_from_github!(stack_id, github_status)` and triggers status-change hooks (`Hook.emit(:commit_status, ...)`, `Hook.emit(:deployable_status, ...)`, and `stack.schedule_merges`) [4](#0-3) [5](#0-4) .

Attacker flow (attacker controls/owns "attacker-org", which is one of the organizations legitimately configured in Shipit with its own `webhook_secret`, e.g. because it also runs stacks on the same Shipit instance):
1. Attacker learns a real commit `sha` that exists in `victim-org/repo`'s Shipit stack (git SHAs are content hashes, visible in any public GitHub UI/API, PR diffs, or CI logs for that repo — no Shipit credentials required).
2. Attacker crafts a `status` event JSON body with `repository.owner.login = "attacker-org"` and `sha = <victim's real sha>`, `state`, etc.
3. Attacker signs the raw body with `attacker-org`'s own `webhook_secret` (which they legitimately possess as the operator of that org's GitHub App/webhook) and POSTs it to `/webhooks` with `X-Github-Event: status`.
4. `verify_signature` resolves `Shipit.github(organization: "attacker-org")` and successfully verifies the signature — it never checks that `attacker-org` owns the commit referenced by `sha`.
5. `Webhooks.for_event('status')` dispatches to `StatusHandler`, whose `Commit.where(sha: ...)` matches the victim's commit row (any stack, any org) and writes a fabricated `CommitStatus` onto it, potentially unblocking/gating victim-org's deploy checks.

None of the existing guards prevent this: `verify_signature` authenticates only the sender's own organization, `drop_unhandled_event` and the `ExplicitParameters` schema only validate shape/presence of fields (`sha`, `state`, etc.) not ownership, and there is no `Repository`/`Stack` cross-check in `StatusHandler` or `Commit.where`.

### Impact Explanation
Any organization holding a valid `webhook_secret` for its own Shipit-integrated repos can forge CI/status state (`success`, `failure`, `pending`, arbitrary `description`/`target_url`) on any commit belonging to any other organization's stack on the same Shipit instance, provided it knows the target sha (trivially obtainable for public repos, and often knowable for private ones through PR/commit references). Because `deployable?` and `blocked?` (used to gate automatic/continuous deployment) depend on commit `status` [6](#0-5) , this can be used to spoof a passing status and cause `schedule_continuous_delivery` to fire, or to spoof a failing status to block a legitimate deploy — a cross-tenant write and deploy-gate manipulation matching the "payload for one repository mutating another's stack/commit" critical category. This is repeatable per request against any commit sha the attacker discovers, across arbitrary victim organizations, as long as those victims' commits exist in Shipit's database.

### Likelihood Explanation
Preconditions: the Shipit instance must host more than one organization/tenant, each with its own configured `webhook_secret` (a normal multi-tenant Shipit setup, as `Shipit.github(organization:)` is keyed per-org config). The attacker needs no Shipit session, API token, or team membership — only the `webhook_secret` of an org they legitimately administer (their own GitHub App/webhook config), which is within the described "unprivileged attacker who owns a repository" threat model. The only extra piece of information needed is a target sha, which is public for public repos and otherwise derivable from any exposure of the victim's commit history. Attack cost is a single crafted HTTP POST; it is fully repeatable and scriptable.

### Recommendation
In `StatusHandler#process` (and equivalent handlers, e.g. check-run status handlers), scope the `Commit` lookup to the repository/organization that was authenticated in `verify_signature`, e.g. join through `stack.repository` and filter `where(sha: params.sha, stacks: { repository_owner: repository_owner, repository_name: ... })`, or pass the verified `repository_owner`/`repository_name` down from the controller and require `commit.stack.repository.owner == repository_owner && commit.stack.repository.name == repository.name` before calling `create_status_from_github!`. Reject/skip commits that don't belong to the authenticated repository instead of applying the status unconditionally.

### Proof of Concept
Minitest plan (`test/controllers/webhooks_controller_test.rb`, no live GitHub):
1. Configure two orgs in `Shipit.github` config fixture: `victim-org` and `attacker-org`, each with a distinct `webhook_secret`.
2. Create `stack = shipit_stacks(:victim_stack)` owned by `victim-org/repo`, and `commit = stack.commits.create!(sha: "a" * 40, message: "victim commit")`.
3. Build a `status` event JSON payload: `{ "repository": { "owner": { "login": "attacker-org" } }, "sha": commit.sha, "state": "success", "context": "ci/forged" }`.
4. Sign the raw JSON with `attacker-org`'s `webhook_secret` and set `X-Hub-Signature: sha1=...`, `X-Github-Event: status`.
5. `post "/webhooks", params: raw_json, headers: {...}` and assert `response.status == 200`.
6. Assert: `commit.reload.statuses.where(context: "ci/forged").exists?` is `true` — proving a `CommitStatus` was written to `victim-org`'s commit using only `attacker-org`'s signature, i.e. the equality "signing organization == owning organization" does not hold, confirming the vulnerability.
