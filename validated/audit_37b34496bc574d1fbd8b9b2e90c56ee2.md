## Title
Spot-utilization interest accrual, cached once per timestamp, lets one caller lock in a manipulated index that all other users in the same block are forced to consume - ([File: mainnet/contracts/vault/v0-vault-usdc.clar], [File: mainnet/contracts/market/v0-4-market.clar])

## Summary
The Threat-Tia report describes a bug class where a shared, block-scoped state artifact is written by one caller's transaction and then blindly trusted by later, unrelated callers, causing harm because the writer's transient conditions get "baked in" for everyone else. In Zest v2 the analogous shared artifact is the vault liquidity/borrow index (`index`/`lindex`) and the market's `index-cache` map, which are computed from the *live, instantaneous* utilization ratio but are only allowed to change once per `stacks-block-time`. Whoever transacts first in a given timestamp determines the interest/liquidity index that every other borrower, lender, and liquidator in that same block will subsequently read, with no re-validation.

## Finding Description
Each vault computes the next borrow/liquidity index from the *current* spot utilization and a time delta since the last real update: [1](#0-0) 

Note that `time-delta` is `(- stacks-block-time (var-get last-update))`. If `time-delta` is `u0` (i.e., the vault has already accrued once at this exact `stacks-block-time`), the multiplier is forced to `INDEX-PRECISION`, meaning the index is frozen for the rest of that timestamp regardless of subsequent changes in utilization: [2](#0-1) 

`accrue()` commits whatever `next-index`/`next-liquidity-index` it computed to the vault's real state vars and updates `last-update` to `stacks-block-time`: [3](#0-2) 

`market.clar`/`v0-4-market.clar` additionally caches this once-per-timestamp result in a shared map keyed only by `{timestamp, aid}` (not by caller), so any later transaction in the same block that touches the same asset simply reads the cached value rather than recomputing: [4](#0-3) 

This cached `{index, lindex}` pair feeds directly into debt scaling for repayment and liquidation (`get-cached-indexes`, `scale-debt-for-liquidation`, `convert-to-scaled-debt`) and into zToken/collateral valuation for every account whose position includes that asset: [5](#0-4) 

**Attacker / victim / shared state:** The attacker is any unprivileged user who is first to touch a given vault's accrual path in a block. The victim is any other unprivileged user (borrower, lender, or liquidator) whose transaction in the same block/timestamp later relies on `get-cached-indexes`/the vault's `index`/`lindex` for health checks, debt repayment, or liquidation math. The shared state is the vault's `index`/`lindex` (and the market's `index-cache` mirror of it), which is written once by the attacker's transaction and consumed unconditionally by every later transaction sharing that timestamp.

**Mechanism:** Because the rate used in `next-index`/`next-liquidity-index` is read live from `(utilization)` = `(calc-utilization (get-available-assets) (total-debt))`, an attacker can transiently move utilization (e.g., temporarily supplying a large amount to depress utilization, or temporarily borrowing/withdrawing to spike it — using flash-loaned capital purely as funding, which is in-scope per the rules) immediately before triggering the vault's *first* accrual of that timestamp (via `deposit`, `borrow`, `collateral-add`, etc. through market). The resulting index reflects the manipulated instant, gets permanently written to vault storage and the market cache for that timestamp, and — because `time-delta` becomes `u0` for every subsequent call in the same timestamp — cannot be corrected by any later, honest transaction in that block, even after the attacker reverses their manipulation in the very same transaction.

## Impact Explanation
All other users borrowing, repaying, or being valued/liquidated against that asset within the remainder of the block use the manipulated index:
- A suppressed `lindex` (liquidity/supply index) permanently under-credits lenders' zToken exchange rate for that accrual period — temporary freezing/theft of unclaimed supply yield for every unrelated supplier of that vault.
- A suppressed `index` (borrow index) under-charges every borrower's scaled debt for that period, effectively socializing an interest shortfall onto the protocol/lenders.
- Because the same cached index feeds zToken collateral valuation (`get-cached-indexes` in `find-and-resolve-asset-value`/`get-notional-evaluation`) and liquidation math (`scale-debt-for-liquidation`), a manipulated index can also distort the computed health/LTV of unrelated borrowers' positions for the rest of the block, causing incorrect liquidation outcomes for victims uninvolved in the manipulation.

This lands on the in-scope High impact class: theft/temporary freezing of unclaimed yield belonging to other suppliers/borrowers, caused entirely by this contract's own accrual/caching logic (not third-party oracle data).

## Likelihood Explanation
The precondition (being first to accrue a given vault in a given `stacks-block-time`) is trivially achievable by any user who structures a single atomic transaction: temporarily move utilization via deposit/withdraw or borrow/repay of owned or flash-loaned capital, then call any market entry point that triggers `accrue-and-cache` for that asset (`collateral-add`, `borrow`, `repay`, `liquidate`, `supply-collateral-add`). No privileged role or DAO action is required, and multiple transactions routinely land in the same Stacks block/timestamp.

## Recommendation
- Short term: do not gate index recomputation solely on `time-delta == 0`; instead recompute/accrue based on genuine elapsed time versus the last *committed* rate snapshot, or accrue using a time-weighted/TWAP utilization rather than instantaneous utilization, so a single transaction cannot dictate the rate applied to an entire timestamp.
- Ensure the market's `index-cache` cannot be poisoned by an attacker-controlled first-mover transaction — e.g., validate that utilization used for the cached accrual reflects a manipulation-resistant measure, or invalidate/recompute the cache when utilization has moved significantly since it was primed.
- Long term: consider decoupling "shared cache primed once per block" optimizations from any state that is a target for atomic, single-transaction manipulation of pool-level metrics (utilization, price, etc.).

## Proof of Concept
1. Attacker takes a flash loan (or uses idle capital) and calls `deposit` on `v0-vault-usdc` with a large amount, sharply reducing `utilization()` for that vault.
2. In the same transaction, attacker calls `market.collateral-add`/`borrow` touching USDC, which invokes `accrue-and-cache` → `vault-accrue` → `accrue()`; since `time-delta` since the vault's `last-update` is non-zero (real elapsed time since a prior block), `next-index`/`next-liquidity-index` are computed using the attacker's artificially low `utilization()`, producing a suppressed index/lindex that is `var-set` into the vault and `map-set` into `index-cache` keyed by the current `stacks-block-time`.
3. Attacker withdraws/redeems their deposit within the same transaction, restoring the vault's true utilization — but `last-update` is now `stacks-block-time`, and `index`/`lindex` remain at the suppressed values.
4. Any other user's transaction later in the same block that borrows, repays, or gets liquidated on USDC calls `accrue-and-cache`, hits the cache (or recomputes with `time-delta = 0`), and is charged/valued using the attacker's manipulated index instead of the correct one, permanently shorting lenders' yield or improperly resolving a victim's collateral/debt valuation for that block.

(define-private (accrue-and-cache (aid uint))
  (let ((cache-key { timestamp: stacks-block-time, aid: aid })
        (cached? (map-get? index-cache cache-key)))

    (match cached?
      ;; cache HIT: return cached value (1 read only)
      cached-indexes (ok cached-indexes)

      ;; cache MISS: accrue and cache (vault-accrue now returns indexes)
      (let ((indexes (try! (vault-accrue aid))))
        ;; store in cache
        (map-set index-cache cache-key indexes)
        (ok indexes)))))

(define-private (scale-debt-for-liquidation
  (debt-final uint)
  (coll-actual uint)
  (curr-scaled uint)
  (asset-id uint))
  (let (;; convert debt amount to scaled units for storage
        (borrow-index (get index (unwrap-panic (get-cached-indexes asset-id))))
        (scaled-debt (mul-div-down debt-final INDEX-PRECISION borrow-index))
        ;; cap at current debt (prevent over-repayment)
        (scaled-to-remove (if (> scaled-debt curr-scaled) curr-scaled scaled-debt))
        (debt-to-repay (mul-div-up scaled-to-remove borrow-index INDEX-PRECISION))
        ;; If debt was capped, scale collateral proportionally
        (coll-final (if (< scaled-to-remove scaled-debt)
                        (mul-div-down coll-actual scaled-to-remove scaled-debt)
                        coll-actual)))
    {
      scaled-to-remove: scaled-to-remove,
      debt-to-repay: debt-to-repay,
      coll-final: coll-final
    }))
