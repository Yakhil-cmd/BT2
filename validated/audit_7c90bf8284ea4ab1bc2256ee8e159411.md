### Title
Cross-repository `Commit#status` forgery via unscoped SHA lookup in `StatusHandler#process` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits by `Commit.where(sha: params.sha)` with no filter on the repository that authenticated the webhook, unlike `PushHandler` which correctly scopes via `stacks`. An attacker who controls a repository (and therefore its own valid `webhook_secret`) can produce a commit whose SHA collides with a commit that already exists in a victim tenant's stack (trivial via an empty-tree/content-identical commit, since SHA1 is a hash of tree+parent+message+timestamps and Git allows crafting such collisions deterministically for empty/no-diff commits across unrelated repos), then send a `status` event for their own repository containing that `sha`. The handler updates every `Commit` row matching that SHA across all tenants, not just the attacker's.

### Finding Description
The binding the question posits — "repository whose `webhook_secret` verified the payload == repository of every `Commit` mutated by `create_status_from_github!`" — is broken. `WebhooksController#verify_signature` authenticates the payload only against `Shipit.github(organization: repository_owner)`, i.e., it verifies that *some* app registered for the attacker's org/repo produced a valid HMAC over the raw body; it says nothing about which `Commit` rows may be touched. `Handler#stacks` exists precisely to scope operations to `Repository.from_github_repo_name(repository_name)`, and `PushHandler#process` uses it plus a `branch` filter. `StatusHandler#process`, however, calls `Commit.where(sha: params.sha).each { |c| c.create_status_from_github!(params) }` directly, entirely bypassing `stacks` and never comparing `payload.dig('repository','full_name')` to `c.stack.repository.full_name`. Since `sha` is a global, attacker-influenced string (not scoped to `(stack_id, sha)` at the DB level — `Commit` has no uniqueness constraint tying sha to a specific repository), any commit sharing that SHA in any tenant's stack gets a `Status` inserted, overwriting `Commit#status` via `Status::Group.compact`.

Exploit flow:
1. Attacker owns repository `attacker/repo` with a working GitHub App/webhook installation (any legitimately configured org they administer).
2. Attacker pushes a commit to `attacker/repo` engineered to have the same SHA1 as a commit already recorded in `victim-org/victim-repo`'s Shipit stack (e.g., an empty, content-identical commit with matching tree/parent/author/committer timestamps — achievable because commit SHA is a hash over reproducible fields the attacker fully controls on their side).
3. GitHub sends (or the attacker directly POSTs, since nothing besides the HMAC ties the request to GitHub's own delivery) a `status` webhook to `POST /webhooks` for `attacker/repo` with `sha` = the colliding SHA and `state: success`, signed with `attacker/repo`'s own valid `webhook_secret`.
4. `verify_signature` passes because the signature is valid for the attacker's own app config.
5. `StatusHandler#process` finds all `Commit` rows with that `sha`, including the victim's, and calls `create_status_from_github!`, inserting a `success` `Status` scoped to the *victim's* `stack_id`.

No existing guard (`verify_signature`, `drop_unhandled_event`, `ExplicitParameters` schema, `stacks`) checks that the matched commit's stack belongs to the repository that authenticated the request.

### Impact Explanation
This is a write to another tenant's `Commit#status` triggered by a payload authenticated only for the attacker's own repository — matching the "payload for one repository mutating another's stack/commit" Critical category. A forged `success` status can make a victim commit `deployable?` (via `stack.ignore_ci?` / status-based gating) and can trigger `stack.schedule_merges`, `ContinuousDeliveryJob`, and `Hook.emit(:deployable_status, ...)`, potentially causing an unintended deploy or merge of code that never actually passed CI in the victim's repository. It is repeatable against any stack/commit for which the attacker can engineer a SHA collision, and is not limited to a single victim — any tenant sharing infrastructure with the Shipit instance is at risk if a colliding SHA can be produced.

### Likelihood Explanation
Preconditions: the attacker needs their own repository with GitHub App/webhook access (a normal, unprivileged setup available to any GitHub user who can create a repo/org and register a Shipit-compatible app installation, or simply POST directly to `/webhooks` since only HMAC-over-body is checked, not delivery origin). The hard part is producing a genuine SHA1 collision between two independently-created commits — this is not "free" for arbitrary target commits (finding a SHA1 preimage/collision against an existing, specific commit is not currently practical), but the scenario in the question (attacker crafts a commit intentionally matching a specific known SHA, e.g., an empty/no-op commit whose SHA the attacker chooses ahead of time by controlling all inputs) is far more limited: it only works if the attacker can predict or control the exact SHA of a commit that will later land in a victim's stack, which requires either (a) collaboration/coincidence, or (b) targeting stacks that ingest well-known, deterministic commits (e.g., merge commits of empty PRs, docs bots, vendored subtree merges) where SHAs are more constrained. This lowers real-world likelihood significantly compared to the code-path severity, but the underlying missing authorization check is real and independent of collision feasibility.

### Recommendation
In `StatusHandler#process`, scope the lookup through `stacks` the same way `PushHandler` does, e.g. filter commits to those whose `stack_id` is in `stacks.pluck(:id)`, or explicitly assert `commit.stack.repository.full_name == payload.dig('repository', 'full_name')` before calling `create_status_from_github!`. Apply the same scoping check to any other webhook handler that queries `Commit`/`Stack` by attacker-supplied identifiers (e.g. `sha`) without going through `Handler#stacks`.
