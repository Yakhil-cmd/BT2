### Title
Review-stack pull-request labels can override the `PATH` environment variable, bypassing `Shipit.shell_paths` precedence in `Command#unbundled_env` - (File: `lib/shipit/command.rb`)

### Summary
`ReviewStack#env` merges every pull request label name (upcased) into the stack's environment with a fixed value of `"true"`, with no key blacklist. Because `TaskCommands#env`/`StackCommands#env` merge `@stack.env` into the environment hash that is later passed to `Command.new(..., env:)`, and `Command#unbundled_env` applies `@env` as the *last* merge step, a pull request label literally named `path` lets an attacker who can label their own PR overwrite the `PATH` value that `Command#start` passes to `PTY.spawn`, replacing the intended `Shipit.shell_paths`-derived value with the literal string `"true"`.

### Finding Description
The claimed safe binding is:
`PTY.spawn`'s `'PATH'` (`lib/shipit/command.rb:92,104`) == `"#{Shipit.shell_paths.join(':')}:#{ENV['PATH']}"`, never derived from `pull_request.labels`.

Trace:
- `ReviewStack#env` (`app/models/shipit/review_stack.rb:84-93`) does `super.merge(pull_request.labels.each_with_object({}) { |label_name, labels| labels[label_name.upcase] = "true" })`. There is no filtering of reserved keys like `PATH`.
- `TaskCommands#env` (`lib/shipit/task_commands.rb:33-48`) and `StackCommands#env` (`lib/shipit/stack_commands.rb:13-15`) call `.merge(@stack.env)`, so any `'PATH' => 'true'` entry survives to the final hash returned by `env`.
- That hash is passed as `env:` into `Command.new` (e.g. `lib/shipit/task_commands.rb:19,25`, `lib/shipit/stack_commands.rb:20-47`), stored as `@env` (`lib/shipit/command.rb:34`).
- `Command#unbundled_env` (`lib/shipit/command.rb:103-105`) computes `BASE_ENV.merge('PATH' => "#{Shipit.shell_paths.join(':')}:#{ENV['PATH']}").merge(@env.stringify_keys)`. Because `@env` is merged *last*, if `@env['PATH']` is present it overwrites the `Shipit.shell_paths` assignment entirely.
- `Command#start` (`lib/shipit/command.rb:85-101`) then calls `PTY.spawn(unbundled_env, *interpolated_arguments, chdir: @chdir)`, so the overwritten `PATH` (`"true"`) is what governs binary resolution for that spawn.

Exploit flow: an attacker (per the stated rules, capable of labeling their own PR) adds a GitHub label named `path` (any case) to a PR that has an active, non-archived review stack. GitHub sends a signed `pull_request`/`labeled` webhook. `LabeledHandler`/`LabelCapturingHandler` (`app/models/shipit/webhooks/handlers/pull_request/label_capturing_handler.rb:98-102`) call `pull_request.update!(labels: params.pull_request.labels.map(&:name))`, persisting `"path"` into `PullRequest#labels`. On the next fetch/install/deploy/rollback for that `ReviewStack`, `PATH` in the spawned command's environment becomes `"true"` instead of the `Shipit.shell_paths` value.

Existing guards do not stop this: `verify_signature` only authenticates that the payload came from GitHub for that repository/organization (it does not restrict which label names are acceptable), `LabelCapturingHandler`'s `params` schema only requires `labels[].name` be a `String` with no format/blacklist restriction, and `ReviewStack#env` performs no key filtering before merging into the environment chain.

### Impact Explanation
The bug clobbers the `PATH` environment variable for every `Command` executed for that specific `ReviewStack` (fetch, install_dependencies, deploy/rollback steps), overriding the `Shipit.shell_paths` precedence that was explicitly added for security (CHANGELOG 0.34.0, "Give precedence to configured `shell_paths` when executing commands"). Impact is bounded to the attacker's own review stack (only that stack's `pull_request.labels` feed into `ReviewStack#env`), so it does not cross-contaminate other stacks/tenants. Whether this rises to full RCE depends on whether any command invoked for that stack resolves a bare (non-absolute) binary name via `PATH` search relative to the command's `chdir`; if so, and the attacker (who fully controls the checked-out PR branch content used as `chdir`) places a directory literally named `true` containing an executable matching that command name, the attacker's binary executes instead of the intended one. At minimum this is a demonstrable environment-variable integrity bypass that defeats the `shell_paths`-precedence guarantee for review-stack commands.

### Likelihood Explanation
Preconditions: the target repository must have review stacks enabled and an active (non-archived) review stack for the attacker's PR; the attacker must be able to add a label named `path` to their own PR (granted as an in-scope capability by the rules) and the label webhook must be correctly signed by GitHub (not forged by the attacker directly against `/webhooks`, since `verify_signature` blocks unsigned payloads). Given those preconditions — which align with the documented review-stacks feature (`docs/review_stacks.md`) — the attack is cheap and repeatable: label/unlabel toggling and re-triggering deploys/tasks reproduces the clobbered `PATH` every time.

### Recommendation
In `ReviewStack#env`, exclude reserved/sensitive keys (at minimum `PATH`, and ideally any key already defined by `Stack#env`/`Command::BASE_ENV`) from the label-derived hash before merging, e.g. reject label names that upcase to `PATH` or any other protected variable. Additionally, in `Command#unbundled_env`, compute the final `PATH` after merging `@env` (or explicitly re-assert `'PATH' => "#{Shipit.shell_paths.join(':')}:#{ENV['PATH']}"` as the last merge) so caller-supplied environment values can never override the trusted `PATH`.

### Proof of Concept
```ruby
# test/models/shipit/review_stack_path_override_test.rb
require "test_helper"

module Shipit
  class ReviewStackPathOverrideTest < ActiveSupport::TestCase
    test "a 'path' label does not override Shipit.shell_paths in TaskCommands#env" do
      stack = shipit_stacks(:review_stack)
      stack.pull_request.labels = ["path"]
      task = shipit_tasks(:shipit_restart)
      task.stack = stack

      env = Shipit::TaskCommands.new(task).env

      expected_path = "#{Shipit.shell_paths.join(':')}:#{ENV['PATH']}"
      # FAILS on current code: env['PATH'] == 'true'
      assert_equal expected_path, env['PATH']
    end

    test "Command#unbundled_env is not affected by the stack's env-derived PATH" do
      malicious_env = { 'PATH' => 'true' }
      command = Shipit::Command.new('echo hi', env: malicious_env, chdir: '.')

      expected_path = "#{Shipit.shell_paths.join(':')}:#{ENV['PATH']}"
      # FAILS on current code: unbundled_env['PATH'] == 'true'
      assert_equal expected_path, command.unbundled_env['PATH']
    end
  end
end
```

    def start(&block)
      return if @started

      @control_block = block
      @out = @pid = nil
      FileUtils.mkdir_p(@chdir)
      begin
        @out, child_in, @pid = PTY.spawn(unbundled_env, *interpolated_arguments, chdir: @chdir)
        child_in.close
      rescue Errno::ENOENT
        raise NotFound, "#{Shellwords.split(interpolated_arguments.first).first}: command not found"
      rescue Errno::EACCES
        raise Denied, "#{Shellwords.split(interpolated_arguments.first).first}: Permission denied"
      end
      @started = true
      self
    end
