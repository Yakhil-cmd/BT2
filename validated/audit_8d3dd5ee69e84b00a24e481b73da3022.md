### Title
Webhook signature verification authenticates the wrong field, allowing cross-organization event forgery - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
The `selfLiquidate` report describes a case where a value is used/acted upon before the check that should have gated it. In `WebhooksController`, the field used to *select which secret verifies the signature* (`repository_owner`) is not the same field that the downstream handlers *act on* (e.g. `repository.full_name`, `team`/`member` in membership events), and both come from the same unverified request body. This breaks the intended binding: "the organization whose secret authenticated the request" == "the organization/repository the request is allowed to mutate."

### Finding Description
`WebhooksController#verify_signature` picks the GitHub App/secret to verify against using data taken directly from the untrusted, not-yet-verified JSON body: [1](#0-0) 

`repository_owner` is derived purely from the payload itself, with a fallback to the `organization` sub-object: [2](#0-1) 

The HMAC in `verify_webhook_signature` proves only that the whole raw body was signed with *some* organization's `webhook_secret` — the specific organization is chosen using an attacker-controlled field inside that same body: [3](#0-2) 

Once signature verification passes, the entire parsed `params` (not just the field used to pick the secret) is dispatched to event handlers: [4](#0-3) 

Handlers such as the membership handler act on other fields in the same payload (`team`, `member.login`, `action`) to create/modify `Team` and `Membership` records: [5](#0-4) 

Because the field that authorizes the request (`repository.owner.login` / `organization.login`, used only to select the signing secret) is never cryptographically bound to the fields the handlers actually mutate (`repository.full_name`, `team`, `member`), an attacker who legitimately controls one organization's `webhook_secret` (e.g., they administer a GitHub org/repo that is itself integrated with this multi-tenant Shipit instance) can craft a payload that:
- Sets `repository.owner.login`/`organization.login` to *their own* organization (so `Shipit.github(organization: ...)` resolves to the secret they know, and the HMAC check passes), while
- Setting `repository.full_name`, `team`, or `member` fields to reference a *different* organization/repo/team they do not control.

This is the same class of bug as the report: a value used for authorization (fee/organization) is computed/selected from data that is not itself covered by the check that is supposed to gate the action (fee is charged from unverified pre-state; here, the org used to select the verifying secret is not the org that is actually acted on).

### Impact Explanation
If exploited, this allows an attacker who only possesses a webhook secret scoped to their own organization to forge events attributed to a different organization/repository hosted on the same Shipit instance — e.g., spoofing `membership` events to add arbitrary users to a `Team` that gates `Shipit.github_teams` authorization, which is explicitly listed as a High-impact outcome ("escalation into `Shipit.github_teams` authorization"). It could also be used to spoof `push`/`commit_status`/`deployable_status` events against a foreign stack, triggering syncs or influencing deploy-gating state for a repository the attacker does not own.

### Likelihood Explanation
This requires the deployment to be configured with more than one GitHub organization/app (multi-tenant `Shipit.github(organization:)` resolution, evidenced by the `GithubOrganizationUnknown` handling and per-organization webhook secret tests), and requires the attacker to already legitimately hold a valid webhook secret for at least one organization on the instance — a lower bar than requiring an `ApiClient` token, a Shipit session, or GitHub App private key, but not a fully anonymous attacker. I could not fully verify from the indexed code how `Shipit.github(organization:)` resolves configs across multiple organizations, nor the exact internals of the `membership` webhook handler beyond what the tests show, since handler source files were not returned by my searches.

### Recommendation
Bind the signature-selection field to the field(s) the handlers act on: verify the signature using the secret associated with the *repository actually referenced by the payload* (or reject payloads where `repository.owner.login`/`organization.login` disagree with the repository/organization used by the handler), rather than trusting an unverified field purely to select which secret to check against.

### Proof of Concept
Conceptual (not runnable without a live multi-org deployment):
1. Attacker administers `org-attacker`, integrated with the shared Shipit instance, and knows its `webhook_secret`.
2. Attacker crafts a `membership` (or `push`) webhook payload where `organization.login` / `repository.owner.login` = `org-attacker` (so `Shipit.github(organization: 'org-attacker')` resolves the known secret) but `team`/`member`/`repository.full_name` reference `org-victim`'s team or repo.
3. Attacker signs the raw body with `org-attacker`'s secret and sends it to `/webhooks`.
4. `verify_signature` passes because it only checks the body against `org-attacker`'s secret; `create` then dispatches the full `params` (referencing `org-victim`) to the handler, which creates/modifies `Membership`/`Team`/`Stack` records scoped to `org-victim`. [6](#0-5)

# frozen_string_literal: true

module Shipit
  class WebhooksController < ActionController::Base
    skip_before_action :verify_authenticity_token, raise: false
    before_action :check_if_ping, :drop_unhandled_event, :verify_signature

    respond_to :json

    def create
      params = JSON.parse(request.raw_post)
      Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }

      head(:ok)
    end

    private

    def drop_unhandled_event
      # Acknowledge, but do nothing
      head(204) unless Shipit::Webhooks.for_event(event).present?
    end

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping
      head(:ok) if event == 'ping'
    end

    def event
      request.headers.fetch('X-Github-Event')
    end

    def repository_owner
      # Fallback to the organization sub-object if repository isn't included in the payload
      params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
    end
  end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
