### Title
`min-ustx-for-sats-amount` rounds down a minimum-collateral check, letting stakers register bonds under-collateralized relative to BTC value - (File: `stackslib/src/chainstate/stacks/boot/pox-5.clar`)

### Summary
`min-ustx-for-sats-amount` computes the minimum uSTX a staker must lock relative to a given amount of BTC (`sats-amount`) using a chained integer division that always truncates toward zero [1](#0-0) . Because this "minimum required" value is a lower bound used to gate registration (as evidenced by the `RegisterForBondErrInsufficientStx` test scenario), rounding it *down* is the wrong direction: it should round up so that the protocol never accepts less STX collateral than the ratio requires.

### Finding Description
The function performs two nested floor divisions:
```
(/ (* (/ (* stx-value-ratio sats-amount) u100) min-ustx-ratio) u10000)
``` [2](#0-1) 
Each `/` in Clarity truncates toward zero for unsigned integers, so both the inner `(/ ... u100)` step and the outer `(/ ... u10000)` step lose fractional remainders. This is structurally the same rounding-direction defect as the Notional `convertFromStorage()` bug cited in the report: a value that represents a required minimum (a debt-like lower bound that must be met to protect the protocol) is computed with round-down instead of round-up, so the computed minimum is systematically less than the true mathematically exact minimum.

This minimum is used as the collateralization floor for bond registration (`register-for-bond` in `pox-5.clar`), gating whether a staker has locked enough STX relative to the sBTC/BTC value backing a signer's bond, as confirmed by the associated `RegisterForBondErrInsufficientStx` test fixture in `contrib/core-contract-tests/tests/pox-5/commands/RegisterForBondErrInsufficientStx.ts`.

### Impact Explanation
Because the minimum-required-STX check is rounded down rather than up, a staker can register/roll over a bond with a "just barely passing" STX amount that is actually a few micro-STX below the true ratio requirement. This under-collateralizes the bond relative to the BTC value it is meant to back — the same equality-breaking pattern flagged in the source report (a debt/requirement computed with the wrong rounding direction, systematically favoring the caller over the protocol). Per dust-scale, this is a small, per-call loss, but it is accumulative across every `register-for-bond` call and cycle rollover, and it weakens the STX-to-BTC collateral ratio the protocol is designed to enforce.

### Likelihood Explanation
This triggers on every call to `register-for-bond` where the computed ratio lands on a non-exact multiple of 100 and then 10000 (i.e., essentially always, since `sats-amount`, `stx-value-ratio`, and `min-ustx-ratio` are arbitrary integers). No privileged role is required — any staker calling the public registration path benefits from the shaved-down minimum. The magnitude per call is bounded by less than 1 part in 10,000 of the ratio computation, but it is realized on every registration/rollover, making it a low-severity but consistently reproducible discrepancy rather than a one-off edge case.

### Recommendation
Round the minimum-required-STX computation up (ceiling division) at both division steps, e.g.:
```clarity
(define-read-only (min-ustx-for-sats-amount
        (sats-amount uint)
        (stx-value-ratio uint)
        (min-ustx-ratio uint)
    )
    (let ((inner-num (* stx-value-ratio sats-amount)))
        (/ (+ (* (/ (+ inner-num u99) u100) min-ustx-ratio) u9999) u10000)
    )
)
```
or use a `div-ceil`-style helper consistently for any calculation that represents a minimum-required/debt-like bound, ensuring rounding always favors the protocol rather than the caller.

### Proof of Concept
Given `stx-value-ratio = 1`, `sats-amount = 199`, `min-ustx-ratio = 1`:
- Exact minimum required (real-number math): `(1 * 199 / 100) * 1 / 100 = 1.99 / 100 = 0.0199` → should round up to `1`.
- Current implementation: `(/ (* 1 199) u100)` → `1` (floor of 1.99), then `(/ (* 1 1) u10000)` → `0`.
- Result: `min-ustx-for-sats-amount` returns `0`, meaning a staker can register with **zero** STX locked and still satisfy the "minimum STX relative to BTC value" check — a full-magnitude failure of the intended collateral floor at small values, and a dust-level shortfall at larger values due to the double truncation.
