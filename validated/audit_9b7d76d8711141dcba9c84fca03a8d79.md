### Title
Webhook Signature Verification Selects Secret by Unverified `repository.owner`/`organization.login`, Allowing Cross-Repository Forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks which GitHub App/organization's `webhook_secret` to validate an inbound webhook's HMAC signature against by reading `repository.owner.login` (or `organization.login`) directly out of the untrusted JSON body, before the signature has been checked. Once verification passes, the actual event handlers resolve the repository/stack to act on using an entirely different, also-unverified field of the same body: `repository.full_name`. Nothing ties the organization whose secret validated the signature to the repository that is subsequently written to.

### Finding Description
`verify_signature` derives the signing organization from the payload itself: [1](#0-0) 

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
```

and: [2](#0-1) 

`repository_owner` is `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` — both fields live inside `request.raw_post`, the very payload the signature is supposed to protect. This is architecturally consistent with Shipit's documented multi-organization GitHub App support (`test/dummy/config/secrets_double_github_app.yml`), where each organization has its own `webhook_secret` used by `GithubApp#verify_webhook_signature`: [3](#0-2) 

The verification step only proves the request was HMAC-signed with *some* configured organization's secret — the one named by an attacker-chosen field in the same body — it does not prove that the *repository actually written to* belongs to that organization.

Downstream, all default handlers resolve the target stack/repository via a completely different field, `repository.full_name`, with no cross-check against the organization used above: [4](#0-3) 

```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
```

For example `PushHandler` triggers `stack.sync_github(expected_head_sha: params.after)` for any stack matching `repository.full_name`: [5](#0-4) 

and the pull-request handlers (`OpenedHandler`, `ClosedHandler`, `LabeledHandler`, etc.) archive/unarchive review stacks or update pull-request state for whatever repository `params.repository.full_name` names: [6](#0-5) 

**Binding broken:** organization that authenticated the request (via `repository_owner` → `Shipit.github(organization: ...)` → correct `webhook_secret`) ≠ repository that is actually written (via `repository.full_name` used by every handler). Both sides of this equality are taken from the same attacker-supplied JSON body, and the code never asserts they refer to the same tenant.

### Impact Explanation
On a Shipit instance configured for multiple organizations (each with its own GitHub App/`webhook_secret`, a supported and documented configuration), an actor who legitimately controls the webhook secret for their own organization's app installation can compute a valid HMAC signature over an arbitrary payload body. By setting `repository.owner.login`/`organization.login` to their own org (so `verify_signature` selects their own known secret and the signature check passes) while setting `repository.full_name` to a victim organization's repository, they can:
- Force `sync_github`/deploy-state resyncs on a victim stack (`push`).
- Fabricate commit statuses that could make otherwise-undeployable commits appear deployable, contributing to an unauthorized deploy.
- Archive/unarchive victim review stacks, or inject fake pull-request/label state, via the `pull_request` handlers.

This falls under the Critical impact category of "an unauthorized deploy" and cross-tenant/cross-repository writes, since state belonging to one organization's stacks is mutated using authentication material belonging to a different, unrelated organization.

### Likelihood Explanation
Exploitability requires the deployment to host more than one GitHub organization's webhook configuration behind the same Shipit instance (multi-org secrets, as shown by the `secrets_double_github_app.yml` fixture) and requires the attacker to know or control one organization's `webhook_secret` — a realistic scenario for shared/multi-tenant Shipit deployments where different teams manage separate GitHub Apps but share one Shipit instance. No GitHub App private key, `api_clients_secret`, Shipit session, or TLS interception is required — only the ability to send an HTTP POST to `/webhooks` with a self-computed HMAC using a secret the attacker legitimately possesses for their own org.

### Recommendation
After signature verification succeeds and identifies organization `O`, re-derive `repository.full_name`/`organization.login` and reject the event (or scope `Repository.from_github_repo_name` lookups) unless the resolved repository's owner is provably `O`. I.e., bind the two fields used for authentication and for state mutation together, rather than trusting them independently from the same unauthenticated body.

### Proof of Concept
1. Deploy Shipit configured with two organizations, `attacker-org` and `victim-org`, each with its own GitHub App and `webhook_secret` (as supported by Shipit's multi-org config).
2. Attacker knows `attacker-org`'s `webhook_secret` (they administer that GitHub App/org).
3. Attacker crafts a JSON body for a `push` (or `pull_request`) event:
   ```json
   {
     "ref": "refs/heads/main",
     "after": "<attacker-chosen sha>",
     "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" }
   }
   ```
4. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(attacker-org secret, body)` and POSTs to `/webhooks` with `X-Github-Event: push`.
5. `verify_signature` calls `Shipit.github(organization: "attacker-org")`, validates the signature successfully (attacker knows this secret).
6. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("victim-org/victim-repo")`, and triggers `sync_github` on the victim's stack — despite the request having been authenticated under `attacker-org`'s credentials, not `victim-org`'s.

Note: I could not fully verify from the indexed code whether `Shipit.github`'s organization-to-secret mapping is populated purely from static server-side config (`secrets.yml`) versus any self-service/API-driven mechanism that would let an untrusted org obtain a `webhook_secret` without operator involvement; this affects how "unprivileged" the attacker truly is. A Devin session with full repo/config access would be needed to confirm exactly how `github_apps`/webhook secrets are provisioned per organization in this deployment.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
