## Finding

### Title
Encrypted-transaction decryption path never checks BIBE ciphertext authenticity/AAD binding, allowing execution of a decrypted payload not committed to by the signed `sender`/signer set - (File: `consensus/src/pipeline/decryption_pipeline_builder.rs`)

### Summary
`EncryptedPayload::verify()` in `types/src/transaction/encrypted_payload.rs` binds a ciphertext to `PayloadAssociatedData { sender, signer_auth_keys }` via `Ciphertext::verify`, which checks the embedded `associated_data_bytes` and the Ed25519 signature (`vk`/`signature`) over `(bibe_ct, associated_data_bytes)`. However, this `verify()`/`Ciphertext::verify` call is never invoked anywhere in the actual consensus decryption pipeline that admits decrypted content into an executable transaction.

### Finding Description
The signature that a user actually signs for an encrypted transaction covers the `RawTransaction`, whose payload is the opaque `EncryptedPayload::Encrypted(EncryptedInner{ciphertext, payload_hash, ...})` [1](#0-0) . The cryptographic AAD binding of the ciphertext to `(sender, signer_auth_keys)` is a separate mechanism implemented in `Ciphertext::verify`, which checks that `associated_data_bytes` matches the expected `PayloadAssociatedData` and validates the embedded `vk`/`signature` [2](#0-1) , and the higher-level `EncryptedPayload::verify` wraps this for `(sender, signer_auth_keys)` [3](#0-2) .

In the consensus decryption pipeline, `do_final_decryption` calls `FPTXWeighted::decrypt(&decryption_key.key, prepared_ciphertext_or_error?)` — with no `AssociatedData`/sender/auth-key argument at all — and on success calls `encrypted_payload.try_into_decrypted(eval_proof, payload)` [4](#0-3) . `try_into_decrypted` only checks that `payload_hash == CryptoHash::hash(&plaintext)` and, optionally, that a claimed entry-function's module/function matches — it never calls `Ciphertext::verify`/`EncryptedPayload::verify` and never checks `associated_data_bytes` against the transaction's actual `sender`/`signer_auth_keys` [5](#0-4) .

The `verify(sender, signer_auth_keys)` method that performs the AAD binding check is exercised only in SDK/unit tests (`sdk/src/transaction_builder.rs::test_encrypted_payload_verification_binds_sender_and_auth_key`) [6](#0-5) , not on the node/consensus decryption admission path that determines what gets executed on-chain.

### Impact Explanation
Because `payload_hash` is committed to by the client at encryption time (`CryptoHash::hash(&decrypted_payload)`, itself derived from the executable + a random `decryption_nonce`) and is embedded in the signed `RawTransaction`'s `EncryptedInner`, a naive attacker cannot simply swap in an arbitrary plaintext — the hash check in `try_into_decrypted` blocks a mismatched executable. However, the AAD binding (`sender`, `signer_auth_keys`) that `Ciphertext::verify` is designed to enforce is dead code on the actual execution path: nothing in the decryption pipeline confirms that the ciphertext being decrypted was actually produced (encrypted) for the `sender`/signer set declared in the enclosing `RawTransaction`. If the BIBE decryption itself is not intrinsically bound to those fields (which is exactly the purpose `PayloadAssociatedData` was designed to serve, and which `Ciphertext::verify` is written specifically to check but is skipped), a ciphertext generated for one identity binding could be decrypted and admitted for execution under a different signed sender context, since only `payload_hash`/`claimed_entry_fun` gate acceptance, not sender/auth-key identity.

### Likelihood Explanation
Whether this is exploitable end-to-end depends on internal properties of `FPTXWeighted`/BIBE (i.e., whether the AAD is cryptographically mixed into decryption itself via `Id::from_verifying_key_and_ad`, or whether it's a purely post-hoc integrity check meant to be enforced by `Ciphertext::verify`). I was not able to fully trace `FPTXWeighted::decrypt`/`bibe_decrypt` internals within the remaining budget to confirm whether the BIBE identity (`hashed_id`) used for decryption independently binds `AssociatedData`, which would determine if skipping `Ciphertext::verify` is merely defense-in-depth or a real gap. This is a genuine code-path gap (dead validation function that exists specifically for this binding but is never called on the admission path) rather than a confirmed exploitable break, so I flag it with medium confidence rather than as a fully proven critical finding.

### Recommendation
Call `EncryptedPayload::verify(sender, signer_auth_keys)` (or the equivalent `Ciphertext::verify`) inside the consensus decryption pipeline (`decryption_pipeline_builder.rs`, in `do_final_decryption`/around `try_into_decrypted`) before transitioning a payload to `Decrypted`, using the `sender`/secondary/fee-payer authentication keys from the enclosing `SignedTransaction`, and reject with `DecryptionFailureReason` on mismatch — mirroring how `payload_hash` is already checked.

### Proof of Concept
Not constructed — this requires understanding whether `FPTXWeighted`/BIBE decryption is intrinsically bound to `AssociatedData` at the primitive level, which I could not fully verify in the available tool budget. Recommend a Devin session with repository access to trace `bibe_decrypt`/`Id::from_verifying_key_and_ad` usage during actual decryption (not just encryption) to confirm exploitability before treating this as a proven vulnerability.

    pub fn try_into_decrypted(
        &mut self,
        eval_proof: EvalProof,
        plaintext: DecryptedPlaintext,
    ) -> Result<(), DecryptionFailureReason> {
        let Self::Encrypted(original) = self else {
            panic!("try_into_decrypted called on non-Encrypted state");
        };

        if original.payload_hash != CryptoHash::hash(&plaintext) {
            return Err(DecryptionFailureReason::PayloadHashMismatch);
        }

        if let Some(claim) = &original.claimed_entry_fun {
            let TransactionExecutable::EntryFunction(entry_fun) = plaintext.executable() else {
                return Err(DecryptionFailureReason::ClaimedEntryFunctionMismatch);
            };
            if *entry_fun.module() != claim.module {
                return Err(DecryptionFailureReason::ClaimedEntryFunctionMismatch);
            }
            if let Some(claimed_function_id) = &claim.function
                && entry_fun.function() != claimed_function_id.as_ident_str()
            {
                return Err(DecryptionFailureReason::ClaimedEntryFunctionMismatch);
            }
        }

        *self = Self::Decrypted {
            original: original.clone(),
            eval_proof,
            decrypted: plaintext,
        };
        Ok(())
    }
