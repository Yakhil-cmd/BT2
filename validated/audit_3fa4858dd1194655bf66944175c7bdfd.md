### Title
Cross-organization webhook confusion: signature is verified against the org named in `repository.owner.login`/`organization.login`, but handlers act on the unrelated `repository.full_name` field — ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
Shipit supports hosting multiple GitHub organizations from a single instance, each with its own GitHub App and its own `webhook_secret` (`Shipit.github(organization:)`, `github_app_config`, exercised by the `secrets_double_github_app.yml` fixture). `WebhooksController#verify_signature` picks *which* organization's secret to validate the HMAC signature against using one payload field, while the event handlers act on the target repository/stack using a *different, uncorrelated* payload field. Since the whole JSON body is attacker-supplied to the public `/webhooks` endpoint and only needs to be HMAC-valid under *some* configured organization's secret (not necessarily the organization whose resources are affected), an actor who legitimately controls the GitHub App/webhook secret for Org A can forge a signed payload that pretends to reference Org B's repository and have Shipit act on Org B's stacks/data.

### Finding Description
`WebhooksController#verify_signature` selects the signing secret like this: [1](#0-0) [2](#0-1) 

`repository_owner` is derived from `params.dig('repository','owner','login')` or, if absent, `params.dig('organization','login')`. This value is used only to look up which `GitHubApp`/webhook secret (`Shipit.github(organization: repository_owner)`) to validate the raw body's HMAC against: [3](#0-2) 

Once the signature is accepted, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` hands the *entire* attacker-controlled JSON body to the handler, unchanged and un-cross-checked: [4](#0-3) 

But the handlers resolve which `Repository`/`Stack` to mutate from a *different* field — `repository.full_name` — with no comparison back to `repository.owner.login`/`organization.login` that was used for signature verification: [5](#0-4) [6](#0-5) 

Concretely, `PushHandler` (and similarly the `pull_request` handlers, which use `params.repository.full_name` to resolve `Repository.from_github_repo_name`) will locate and mutate stacks for whatever `full_name` is present in the payload, independent of which organization's secret was used to authenticate the request: [7](#0-6) 

**The broken binding, as an equality that should hold but does not:**
`organization whose webhook_secret validated the request` == `organization that owns the repository/stack the handler subsequently writes to`.

Before the attacker's request: for genuine GitHub-originated deliveries this equality always holds, because GitHub itself only ever includes a repository's true owner/full_name in an event about that repository, and only signs it with that repository's installation's secret.

After the attacker's crafted request: the attacker (who legitimately administers Org A's own GitHub App installed against the same shared Shipit instance and therefore genuinely knows Org A's `webhook_secret`) POSTs directly to `/webhooks` a body where `repository.owner.login` = "OrgA" (so `verify_signature` selects and successfully validates against OrgA's known secret) but `repository.full_name` = "OrgB/victim-repo" and arbitrary `ref`/`after` (or PR) fields. The signature check passes, and the handler subsequently resolves and mutates OrgB's `Stack` using the forged `full_name`, `ref`, and `after` values — none of which were ever bound to the secret that was actually used for verification.

This is the deployment-trust binding named directly in scope: *"an organization that authenticated versus the repository that is written."*

### Impact Explanation
Using the `push` event as the sharpest example: `PushHandler#process` calls `stack.sync_github(expected_head_sha: params.after)` for any not-archived stack on the target branch of the forged repository: [6](#0-5) 

If the targeted victim stack has `continuous_deployment` enabled, syncing a new head commit is precisely the trigger path that schedules automatic deployment (`Stack.schedule_continuous_delivery` / `ContinuousDeliveryJob`), meaning an attacker who only controls a *different*, unrelated organization's webhook secret can force Shipit to sync and subsequently auto-deploy a chosen (but still real/existing) commit SHA of a repository they have no access to. This is an **unauthorized deploy**, matching the Critical impact category ("an unauthorized deploy, rollback or merge").

The `pull_request` handlers extend the same primitive to archiving/unarchiving/provisioning review stacks (`OpenedHandler`, `ClosedHandler`, `ReopenedHandler`, `Labeled/UnlabeledHandler`) for a victim organization's repository, again keyed only off the forged `repository.full_name`, causing unauthorized stack lifecycle actions (deprovisioning, provisioning, archiving) cross-tenant.

### Likelihood Explanation
The prerequisite is that the same Shipit deployment serves more than one GitHub organization (a supported, documented configuration — see `Shipit.github_organizations`, `github_app_config`, and the `secrets_double_github_app.yml` test fixture), and that the attacker legitimately controls (as an ordinary, unprivileged-with-respect-to-Shipit GitHub org owner) the GitHub App / webhook secret for *any one* of those organizations. No Shipit session, `ApiClient` token, or GitHub App private key for the *victim* organization is required — only knowledge of one's own, already-possessed webhook secret for a co-tenant organization, and the ability to POST directly to the public `/webhooks` endpoint. This is a straightforward, always-reachable path once the multi-org feature is used, requiring no race condition or timing luck (unlike the USDC-blacklisting analog).

### Recommendation
After selecting the webhook secret by `repository_owner`, `verify_signature` (or the individual handlers) must assert that the resolved organization matches the actual owner segment of `repository.full_name` (and of any other repository-identifying fields used later, e.g. `pull_request.base.repo.full_name`) before dispatching to handlers. Reject the request if these do not match.

### Proof of Concept
Conceptual PoC (cannot be executed without the full app boot, but demonstrates the exact code path):

```ruby
# Attacker legitimately knows OrgA's webhook_secret (their own org's GitHub App on the shared Shipit instance)
secret = "orgA-known-secret"
payload = {
  "ref" => "refs/heads/main",
  "after" => "<a real, existing commit sha on victim's tracked branch>",
  "repository" => {
    "owner" => { "login" => "OrgA" },      # used ONLY to pick verification secret
    "full_name" => "OrgB/victim-repo"       # used by PushHandler to resolve the actual Stack
  }
}.to_json

signature = "sha1=" + OpenSSL::HMAC.hexdigest("sha1", secret, payload)

post "/webhooks", body: payload, headers: {
  "X-Github-Event" => "push",
  "X-Hub-Signature" => signature
}
# verify_signature succeeds (Shipit.github(organization: "OrgA").verify_webhook_signature(...) == true)
# PushHandler#process then resolves Repository.from_github_repo_name("OrgB/victim-repo")
# and calls stack.sync_github(expected_head_sha: <attacker-chosen sha>)
# -> triggers sync/continuous delivery for OrgB's stack despite the request being authenticated
#    only against OrgA's secret.
``` [8](#0-7) [5](#0-4) [9](#0-8)

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

# frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
