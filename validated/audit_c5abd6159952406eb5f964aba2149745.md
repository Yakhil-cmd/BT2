## Title
Shared `--sync-timeout` context budget causes post-sync worktree cleanup and GC to silently fail when the sync operation consumes most of the deadline - (File: `main.go`)

### Summary
The bug-class described in the GMX report is: a single resource budget (execution fee/gas) is allocated for an operation and its associated cleanup/cancellation step, but the primary operation can consume most of that budget before failing/finishing, leaving too little left for the cleanup step, which then under-performs or fails, harming the party relying on the cleanup. In `git-sync`, the same pattern exists around the `--sync-timeout` context: the same `context.Context` deadline is shared between the main `SyncRepo` operation (fetch, worktree creation, checkout, submodule update) and the subsequent `cleanup` step (stale worktree prune, reflog expire, `git gc`), so a slow-but-successful sync can exhaust the timeout budget and starve cleanup of the time it needs.

### Finding Description
In the main sync loop, one `context.Context` with a single deadline (`*flSyncTimeout`, default 120s) is created and reused for both the sync and the cleanup call: [1](#0-0) 

```go
for {
    start := time.Now()
    ctx, cancel := context.WithTimeout(context.Background(), *flSyncTimeout)
```

`git.SyncRepo(ctx, syncHooks)` performs the potentially slow operations — `fetch`, `createWorktree` (`git worktree add`), `configureWorktree` (checkout, submodule update), and `publishSymlink` — all bound by the same `ctx`: [2](#0-1) [3](#0-2) 

If `SyncRepo` succeeds (`changed` or first sync), the loop immediately reuses the *same* `ctx` — not a fresh one — to run `git.cleanup(ctx)`: [4](#0-3) 

`cleanup` runs three git subcommands against that already-partially-consumed deadline: `worktree prune`, `reflog expire --expire-unreachable=all --all`, and `gc`/`gc --auto`/`gc --aggressive`: [5](#0-4) 

Every one of these git invocations goes through `Runner.Run` → `exec.CommandContext(ctx, ...)`, which is killed as soon as `ctx`'s deadline is reached, and the error path explicitly checks for `context.DeadlineExceeded`: [6](#0-5) 

Because `fetch`, worktree creation, checkout, and submodule updates have no individual sub-timeouts — they are only bounded by the single overall `--sync-timeout` — a sync that is slow (large repo, deep history, slow network, big/many submodules) but still completes successfully within the overall deadline can consume nearly all of the allotted time. The subsequent `cleanup(ctx)` call then has only the remaining fraction of a second/second(s) left before `ctx` expires, causing `worktree prune`, `reflog expire`, and especially `gc` (which can be slow on large repos) to fail with `context deadline exceeded`.

This mirrors the GMX report's root cause exactly: the primary operation (`executeDeposit`/`SyncRepo`) and its dependent recovery/cleanup step (`cancelDeposit`/`cleanup`) draw from one shared, finite budget (gas/context deadline), and the primary operation's variable cost can leave the cleanup step starved.

### Impact Explanation
When `cleanup` fails, the loop only logs the error and continues — it does not fail the sync or retry cleanup with fresh time: [7](#0-6) 

Repeated failures of `worktree prune`/`reflog expire`/`gc` mean:
- Stale `.git/worktrees/<hash>` metadata and unreachable objects accumulate across sync cycles even after `removeStaleWorktrees` deletes the on-disk directory content, since `worktree prune` (which drops the git-internal bookkeeping) is the step most likely to be cut off.
- `git gc` never runs to completion on a busy/large repo, so the local object store and `--root` disk usage grow unbounded over the life of the sidecar.
- This can eventually exhaust the container's/volume's disk space, causing all subsequent syncs to fail — a persistent sync denial, which matches the "persistent sync denial" impact category accepted for this analysis.

The severity is moderate: it is not attacker-controlled in the classic sense (no malicious ref/commit is strictly required — any legitimately large/slow repo triggers it), but it degrades the git-sync guarantee that the tool self-maintains its `--root` directory via GC, and it does so specifically because the resource budget (`--sync-timeout`) is split unevenly between the mandatory operation and its cleanup counterpart, without accounting for how much the operation may consume.

### Likelihood Explanation
Likelihood is highest in realistic deployments with default settings: `--sync-timeout` defaults to 120s and `--git-gc` defaults to on, while repos with large history, many/large submodules, or a slow network link commonly take a large share of that window for fetch/checkout/submodule-update alone. The `test_e2e.sh` suite already demonstrates the timeout-vs-slow-operation dynamic exists (`e2e::error_slow_git_short_timeout`, `e2e::sync_slow_git_long_timeout`), confirming that the total sync-timeout can be exhausted by the primary sync steps: [8](#0-7) 

No special privileges or flags beyond normal operation are required; only a repo whose fetch/checkout/submodule cost is a large fraction of `--sync-timeout`, which is a common condition, not an edge case.

### Recommendation
Give `cleanup` its own timeout budget instead of reusing the (possibly nearly-expired) `ctx` from `SyncRepo`. For example, in the main loop, derive a fresh `context.WithTimeout(context.Background(), *flSyncTimeout)` (or a dedicated `--cleanup-timeout`) for the call to `git.cleanup(...)` at `main.go:1090`, so that worktree pruning, reflog expiry, and GC always get a guaranteed minimum window regardless of how much time the preceding fetch/checkout/submodule-update consumed. Optionally, also track/report `cleanup` failures via a metric so operators can detect chronic GC starvation before disk exhaustion occurs.

### Proof of Concept
1. Configure `--sync-timeout=5s` (or leave default `120s` but use a very large repo/submodules to simulate the same ratio) and point `--repo` at a repository whose fetch + checkout + submodule update take close to the full timeout (e.g. via the existing `SLOW_GIT_FETCH` test harness used in `test_e2e.sh::e2e::sync_slow_git_long_timeout`, but tuned so the slow fetch takes ~90% of `--sync-timeout` while still finishing in time).
2. Run `git-sync` normally; observe that `SyncRepo` succeeds (link is published, hash updated) but the immediately following `git.cleanup(ctx)` call logs `git cleanup failed` with an error wrapping `context.DeadlineExceeded` for `worktree prune`/`reflog expire`/`gc` (per the `ctx.Err() == context.DeadlineExceeded` branch in `pkg/cmd/cmd.go:85-87`).
3. Repeat several sync cycles and observe `.git/worktrees` entries and repo object count/disk usage in `--root` growing without bound because `worktree prune` and `gc` never complete, since each cycle re-creates a fresh `ctx` only for the *next* `SyncRepo`, but that new `ctx` is again eaten by the slow fetch, causing `cleanup` to be starved indefinitely.

```go
// cleanup removes old worktrees and runs git's garbage collection.  The
// specified worktree is preserved.
func (git *repoSync) cleanup(ctx context.Context) error {
	// Save errors until the end.
	var cleanupErrs multiError

	// Clean up previous worktree(s).
	if n, err := git.removeStaleWorktrees(); err != nil {
		cleanupErrs = append(cleanupErrs, err)
	} else if n == 0 {
		// We didn't clean up any worktrees, so the rest of this is moot.
		return nil
	}

	// Let git know we don't need those old commits any more.
	git.log.V(3).Info("pruning worktrees")
	if _, _, err := git.Run(ctx, git.root, "worktree", "prune", "--verbose"); err != nil {
		cleanupErrs = append(cleanupErrs, err)
	}

	// Expire old refs.
	git.log.V(3).Info("expiring unreachable refs")
	if _, _, err := git.Run(ctx, git.root, "reflog", "expire", "--expire-unreachable=all", "--all"); err != nil {
		cleanupErrs = append(cleanupErrs, err)
	}

	// Run GC if needed.
	if git.gc != gcOff {
		args := []string{"gc"}
		switch git.gc {
		case gcAuto:
			args = append(args, "--auto")
		case gcAlways:
			// no extra flags
		case gcAggressive:
			args = append(args, "--aggressive")
		}
		git.log.V(3).Info("running git garbage collection")
		if _, _, err := git.Run(ctx, git.root, args...); err != nil {
			cleanupErrs = append(cleanupErrs, err)
		}
	}
```
