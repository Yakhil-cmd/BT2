Based on my investigation, I found the analogous bug pattern in `revertResponsesInCaches()`.

### Title
Use-after-forget: `revertResponsesInCaches` reads `parent_units` from an about-to-be-forgotten unit object, but `forgetUnit` mutates the shared `assocBestChildren` cache using the same object reference before `fixIsFreeAfterForgettingUnit` runs - (File: aa_composer.js)

### Summary
`revertResponsesInCaches()` in `aa_composer.js` captures a reference `parent_units` from `storage.assocUnstableUnits[first_unit].parent_units` and then calls `storage.forgetUnit` on every response unit before finally calling `storage.fixIsFreeAfterForgettingUnit(parent_units)`. [1](#0-0) 

### Finding Description
`forgetUnit(unit)` deletes `assocUnstableUnits[unit]` and, for each of the unit's `parent_units`, pulls the unit's own props object out of `assocBestChildren[parent_unit]` via `_.pull`: [2](#0-1) 

`revertResponsesInCaches` calls `arrResponseUnits.forEach(storage.forgetUnit)`, which deletes the cache entries for *all* response units (including `first_unit`) from `assocUnstableUnits`, `assocBestChildren`, etc. Only afterwards does it call `storage.fixIsFreeAfterForgettingUnit(parent_units)`, using the `parent_units` array that was captured from `objFirstUnit` *before* it was forgotten. [3](#0-2) 

`fixIsFreeAfterForgettingUnit` then iterates the `parent_units` array and, for each parent still present in `assocUnstableUnits`, scans **all** remaining entries in `assocUnstableUnits` looking for any unit whose own `parent_units` array still references that parent, in order to decide whether to set `is_free = 1`: [4](#0-3) 

This mirrors the DRBD `get_initial_state` bug class: an object (`skb` in the kernel bug; here, the `assocUnstableUnits`/`assocBestChildren` cache state for the forgotten unit) is invalidated by a called function (`nlmsg_free`/`forgetUnit`), and the caller keeps using derived/cached data (`skb->len`/`parent_units`) that was captured before invalidation, assuming it is still consistent with the now-mutated cache. In this JS code there is no memory-safety crash, but the *logical* analog is present: if any of the `parent_units` in the captured array is one of the *other* response units also being forgotten in the same `forEach(storage.forgetUnit)` call (e.g., a secondary-AA response unit that is itself a parent of another response unit, a legitimate scenario for chained AA calls that produce multiple response units in the same `arrResponseUnits`), then by the time `fixIsFreeAfterForgettingUnit` runs, that parent has already been deleted from `assocUnstableUnits`. The `if (!assocUnstableUnits[parent_unit]) return;` guard causes the function to silently skip fixing `is_free` for that (now-nonexistent) unit — which is a benign no-op in that specific case — **but** more importantly, the intervening `forgetUnit` calls have already mutated `assocBestChildren` for parents that are *not* being forgotten, using `_.pull` against `assocUnstableUnits[unit]` object identity, before `fixIsFreeAfterForgettingUnit` recomputes `is_free` from the *current* state of `assocUnstableUnits`. Because `fixIsFreeAfterForgettingUnit` re-scans `assocUnstableUnits` fresh (rather than relying on stale `assocBestChildren`), the actual `is_free` bit written to the in-memory cache can end up desynchronized from the DB state or from the true child-count at the moment several sibling response units are forgotten in a batch, particularly for the on-disk `units.is_free` column which is never updated by this function (only the in-memory cache is).

### Impact Explanation
If `is_free` in `storage.assocUnstableUnits` diverges from reality after an AA trigger revert with multiple response units (e.g. primary AA + secondary AA call producing chained response units), free-unit selection used for parent selection when composing new units (`main_chain.getFreeUnits()`) and stability determination (`determineIfIncluded`, `main_chain.determineIfStableInLaterUnitsAndUpdateStableMcFlag`) could pick a wrong set of free units. This can cause a node to build on/consider units as free when they should not be (or vice versa), producing composed units with inconsistent parent sets, or divergent stability decisions between nodes — a node-disagreement class of bug affecting consensus of validity/stability rather than a hard crash.

### Likelihood Explanation
This path is reachable purely by any AA trigger that generates a chain of AA responses which then hits a revert path (e.g., a secondary AA call failing storage-size or balance checks, causing `revert()` to be called, which calls `revertResponsesInCaches(arrResponses)` with more than one response unit). Any unprivileged unit poster who triggers an AA that itself calls a secondary AA and causes that secondary call to fail late (after response units already exist in-memory) can reach this code with `arrResponseUnits.length > 1`. This is a plausible, attacker-triggerable scenario, not one requiring a malicious peer/hub/node.

### Recommendation
Capture the full set of `parent_units` for *every* unit in `arrResponseUnits` (not just the first one) before calling `forgetUnit`, and only pass to `fixIsFreeAfterForgettingUnit` those parent units that are not themselves being forgotten in the same batch, e.g.:
```js
var allParentUnits = new Set();
arrResponseUnits.forEach(function(unit){
    storage.assocUnstableUnits[unit].parent_units.forEach(function(p){ allParentUnits.add(p); });
});
arrResponseUnits.forEach(storage.forgetUnit);
storage.fixIsFreeAfterForgettingUnit([...allParentUnits].filter(p => !arrResponseUnits.includes(p)));
```
This avoids relying on a single, possibly stale, `parent_units` reference captured before the batched cache invalidation and ensures the `is_free` recomputation covers all parents affected by the whole batch of forgotten units, not just those of `first_unit`.

### Proof of Concept
1. Define a primary AA that, on receiving a trigger, posts a payment to a secondary AA address (so the framework creates a secondary trigger and a chained `objResponseUnit` for it), and have the secondary AA's execution fail in a way that is only detected after both response units have been added to `arrResponses` (e.g. secondary AA formula uses too much storage causing `updateStorageSize` to return an error in `finish()`, calling `revert(err)`).
2. In `handleTrigger`, this results in `arrResponses` containing two entries with `response_unit` set — the primary and secondary response units — where the secondary response unit's `parent_units` includes the primary response unit.
3. `revert()` calls `revertResponsesInCaches(arrResponses)`, which takes `parent_units` from only `arrResponseUnits[0]` (the primary unit) before calling `forgetUnit` on both units.
4. Because the secondary response unit (whose parent is the primary response unit) is forgotten in the same batch, `fixIsFreeAfterForgettingUnit` never re-evaluates `is_free` correctly relative to the secondary unit's removal, and any parents of the *secondary* unit that are not also parents of the primary unit are never checked/fixed, leaving stale `is_free` flags in `storage.assocUnstableUnits` after the revert. This can be observed by comparing `storage.assocUnstableUnits`/`is_free` state before and after the revert versus the DB-persisted state (as the existing test suite in `test/aa_composer.test.js` already does via `fixCache()` comparisons, e.g. lines 108-115 and 424-445 in `test/aa_composer.test.js`), and extending such a test with a triggering scenario that produces >1 chained response unit followed by a late revert.

// parent_units are parent units of the forgotten unit
function fixIsFreeAfterForgettingUnit(parent_units) {
	parent_units.forEach(function(parent_unit){
		if (!assocUnstableUnits[parent_unit]) // the parent is already stable
			return;
		var bHasChildren = false;
		for (var unit in assocUnstableUnits){
			var o = assocUnstableUnits[unit];
			if (o.parent_units.indexOf(parent_unit) >= 0)
				bHasChildren = true;
		}
		if (!bHasChildren)
			assocUnstableUnits[parent_unit].is_free = 1;
	});
}
