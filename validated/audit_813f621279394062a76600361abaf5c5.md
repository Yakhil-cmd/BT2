### Title
Cross-repository status forgery via SHA-only commit lookup enables unauthorized `ContinuousDeliveryJob` enqueues - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` resolves the target `Commit` for an incoming `status` webhook using only `params.sha`, with no check that the payload's `repository` matches the repository/stack that owns the commit. Since a commit SHA is a content hash and is identical across any repository containing the same commit object (forks, mirrors, copies of public history), an attacker who can generate a validly-signed webhook for their own, unrelated repository can post a fabricated `success` status for any commit whose SHA also exists in a victim `Stack`, repeatedly and independently triggering `Commit#schedule_continuous_delivery`.

### Finding Description
Broken binding: `ContinuousDeliveryJob` enqueues authorized by the victim organization's own CI reporting on the victim's actual repository == `ContinuousDeliveryJob` enqueues an attacker can cause by POSTing `status` webhooks correctly signed for their own, unrelated repository. `StatusHandler` makes these unequal.

Code path:
1. `WebhooksController#verify_signature` only authenticates that the payload was really sent by GitHub for the organization named in `repository.owner.login`/`organization.login` (`repository_owner`), via `Shipit.github(organization: repository_owner).verify_webhook_signature` (app/controllers/shipit/webhooks_controller.rb:24-38). It never checks that `repository.full_name` in the payload corresponds to the repository backing the `Commit` that will be mutated.
2. `StatusHandler` accepts `sha`, `state`, and optional fields with no repository/stack binding in its params schema (app/models/shipit/webhooks/handlers/status_handler.rb:7-18).
3. `process` does: [1](#0-0) . This is a global, unscoped query across every `Commit` row in the database that shares the given SHA — not limited to the repository the webhook claims to originate from.
4. Creating a `Status` triggers `after_create :enable_ci_on_stack` and `after_commit :schedule_continuous_delivery`, calling `commit.schedule_continuous_delivery` [2](#0-1) .
5. `Commit#schedule_continuous_delivery` enqueues `ContinuousDeliveryJob` whenever the commit is `deployable?` and the stack is `continuous_deployment?` and `deployable?` [3](#0-2) .

Attacker flow: the attacker owns/controls a repository that legitimately emits validly-signed webhooks to the Shipit host (e.g. a repo under an org/app installation Shipit already trusts). The attacker pushes/creates commits in that repository whose objects are byte-identical to ancestor commits already recorded in the victim `Stack#commits` (trivial for public history — SHAs are not secret). The attacker then causes a `status` event to fire for those SHAs (e.g., via their own CI hitting their own commit, or any mechanism generating a real, signed GitHub webhook for their repo). Each such webhook passes `verify_signature` (it's a real, correctly-signed event — just for the wrong repository) and lands in `StatusHandler#process`, which finds the victim's `Commit` row purely by SHA match and applies the forged `state`. This independently fires `schedule_continuous_delivery` for the victim stack. Repeating this for successive ancestor commits "walks" the victim stack toward HEAD, each POST producing its own `ContinuousDeliveryJob` enqueue.

No existing guard prevents this: `verify_signature` checks org-level authenticity only, not repo identity; the `ExplicitParameters` schema on `StatusHandler` has no repository constraint; there is no `Repository`/stack scoping applied to the `Commit.where(sha:)` lookup.

### Impact Explanation
An attacker who never authenticates against the victim's repository, organization, or Shipit session can cause `Status` records to be written and `ContinuousDeliveryJob` jobs to be enqueued for a victim `Stack`/`Commit` that never received any real CI signal from the victim's own repository. If `continuous_deployment?` is enabled, this is an unauthorized deploy trigger — a Critical-severity outcome ("a record written for a repository that did not authenticate it" / "unauthorized deploy... triggered"). The attack is repeatable per ancestor commit and is not bound to a single stack — any `Commit` row sharing a SHA anywhere in the Shipit instance is affected, so the blast radius spans every stack/tenant on the host, not just one victim repository.

### Likelihood Explanation
Preconditions: victim `Stack#continuous_deployment?` is true and has undeployed ancestor commits (`last_deployed_commit` behind HEAD) — a common, intentional configuration for continuous delivery. The attacker needs a repository capable of emitting a validly-signed `status` webhook to the Shipit host (satisfied by any repository under an org/app installation already integrated with Shipit) and knowledge of victim commit SHAs (public in most CI/CD and open-source workflows). No Shipit secrets, sessions, or elevated GitHub permissions are required. Cost per exploit attempt is a single HTTP POST; the attack is fully repeatable and scriptable.

### Recommendation
Scope the commit lookup in `StatusHandler#process` to the repository actually asserted in the incoming payload: resolve `stack`/`repository` from `params.repository.full_name` (or equivalent) and restrict `Commit.where(sha: params.sha, stack: stacks_for_repository)` instead of an unscoped, instance-wide `Commit.where(sha:)`. Additionally, verify that the resolved commit's `stack.repository` matches the webhook's `repository.full_name` before calling `create_status_from_github!`.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (conceptual addition)
test ":status webhook from an unrelated attacker repo can drive ContinuousDeliveryJob for a victim stack via shared SHAs" do
  victim_stack = shipit_stacks(:shipit) # continuous_deployment? == true, last_deployed_commit behind HEAD
  ancestors = [shipit_commits(:first), shipit_commits(:second), shipit_commits(:third)] # 3 undeployed ancestor commits sharing SHAs with attacker-owned commits

  request.headers['X-Github-Event'] = 'status'
  GithubHook.any_instance.stubs(:verify_signature).returns(true) # simulate a validly-signed webhook from the attacker's own, unrelated repository

  assert_enqueued_jobs 3, only: ContinuousDeliveryJob do
    ancestors.each do |commit|
      body = {
        sha: commit.sha,
        state: 'success',
        context: 'attacker/ci',
        repository: { owner: { login: 'attacker-org' }, full_name: 'attacker-org/unrelated-repo' } # NOT victim_stack's repository
      }.to_json
      post :create, body:, as: :json
    end
  end

  # Binding check: jobs enqueued by attacker-controlled cross-repo POSTs (3)
  # should equal jobs authorized by victim CI (0, since no victim CI ever ran) — they don't.
  assert_equal 3, enqueued_jobs.count { |j| j['job_class'] == 'Shipit::ContinuousDeliveryJob' }
end
