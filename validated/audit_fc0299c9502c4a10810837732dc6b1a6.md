### Title
Webhook signature verified against `repository.owner.login`-derived organization, but event handlers act on `repository.full_name` - allows cross-organization webhook forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects which GitHub App configuration (and thus which `webhook_secret`) to verify the request's HMAC signature against by reading `repository.owner.login` (or `organization.login`) out of the **unverified** JSON body. Once the signature check passes, `create` hands the very same unverified body to `Shipit::Webhooks::Handlers::Handler`, whose `stacks`/`repository_name` methods instead key off `repository.full_name` [1](#0-0) . In a multi-organization deployment (`Shipit.github_organizations` / `github_app_config`), the field used to pick the verifying secret (`owner.login`) and the field used to pick the target repository/stack acted on (`full_name`) are never bound together, so they can be set independently.

### Finding Description
`verify_signature` computes:
```ruby
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
```
with
```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [2](#0-1) 

`Shipit.github(organization:)` resolves per-organization GitHub App config, each with its own `webhook_secret`, via `github_app_config` [3](#0-2) .

After signature verification succeeds, `create` calls the registered handlers with the raw parsed JSON body unchanged:
```ruby
def create
  params = JSON.parse(request.raw_post)
  Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }
  head(:ok)
end
``` [4](#0-3) 

Handlers derive the acted-upon repository from a *different* field:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [1](#0-0)  e.g. `PushHandler#process` uses `stacks` to trigger `stack.sync_github` for every matching stack [5](#0-4) .

Because the field used to select the *verifying secret* (`repository.owner.login`) is not cryptographically or programmatically tied to the field used to select the *repository/stack being acted on* (`repository.full_name`), an attacker who legitimately controls an organization/repository installed on the same Shipit instance (and therefore knows that organization's `webhook_secret`) can forge a JSON payload where:
- `repository.owner.login` = their own organization (so `Shipit.github(organization: ...)` picks the attacker's own known secret and the HMAC they compute with it verifies successfully), and
- `repository.full_name` = a victim organization/repository's full name (so the handler executes against the victim's `Stack`/`Repository` records).

This breaks the intended binding "the organization whose secret authenticated the request == the repository being written to by the request", allowing a self-authenticated forged webhook to trigger effects (e.g. `sync_github`, deploy-triggering commit ingestion, `check_run`/`status` updates that gate merges via `StatusChecker`, membership/team changes) against a repository the attacker does not control.

### Impact Explanation
This crosses a repository-write boundary explicitly called out as in-scope ("an organization that authenticated versus the repository that is written"). A single-org deployment is unaffected (there `repository_owner` is irrelevant to signature verification since `github_default_organization` is `nil` and the top-level shared secret is used) [6](#0-5) , but any multi-org Shipit installation (configured per `TOP_LEVEL_GH_KEYS`/`github_app_config`) is exposed: an attacker with legitimate GitHub App installation on one org can push forged webhook events that get processed as if they originated from another org's repository, e.g. forcing `GithubSyncJob`/`sync_github` calls, spoofing commit statuses/check-runs consumed by `StatusChecker` (used in merge-request gating), or membership/team webhook handlers — all without ever knowing the victim organization's `webhook_secret`.

### Likelihood Explanation
Requires the target Shipit instance to run in multi-organization mode (multiple GitHub App configs under `secrets.github`) and the attacker to control (or have webhook delivery rights for) at least one of the configured organizations — a materially lower bar than compromising the victim org's `webhook_secret`, `api_clients_secret`, or GitHub App private key, and requires no Shipit session or API token.

### Recommendation
Bind the field used to select the verifying secret to the field used to select the acted-upon repository: derive `repository_owner` for signature verification from the same `repository.full_name` (e.g. `full_name.split('/').first`) that handlers use, or explicitly verify that `repository.owner.login` matches the owner segment of `repository.full_name` before dispatching to handlers.

### Proof of Concept
1. Configure Shipit with two organizations, `attacker-org` (attacker knows `webhook_secret_A`) and `victim-org` (repository `victim-org/victim-repo` tracked as a Shipit `Stack`).
2. Attacker crafts a `push` event JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker chosen sha>",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<hmac(webhook_secret_A, body)>` using their own known secret and POSTs to `/webhooks` with `X-Github-Event: push`.
4. `verify_signature` resolves `Shipit.github(organization: "attacker-org")` and successfully verifies the signature against `webhook_secret_A` [7](#0-6) .
5. `create` dispatches the same body to `PushHandler`, which resolves `repository_name` = `"victim-org/victim-repo"` and calls `stack.sync_github(expected_head_sha: ...)` on the victim's stack [5](#0-4) , despite the request never being signed with `victim-org`'s secret.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```

**File:** lib/shipit.rb (L170-200)
```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
