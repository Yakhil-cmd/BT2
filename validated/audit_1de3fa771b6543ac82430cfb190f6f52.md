### Title
Creator fee collection permanently reverts if the pool creator's token account becomes frozen/blacklisted by the token issuer - (File: `programs/cp-swap/src/instructions/collect_creator_fee_permissionless.rs`, `programs/cp-swap/src/instructions/collect_creator_fee.rs`, `programs/cp-swap/src/utils/token.rs`)

### Summary
`collect_creator_fee` and `collect_creator_fee_permissionless` unconditionally call `transfer_checked` to move accrued `creator_fees_token_0`/`creator_fees_token_1` from the pool vaults into the `pool_creator`'s token account [1](#0-0) . If the mint's issuer (freeze authority) ever freezes the creator's token account — exactly the scenario Circle used to blacklist USDC addresses, which this pool supports since `is_supported_mint` places no restriction on legacy SPL-Token mints regardless of `freeze_authority` [2](#0-1)  — every future call to either instruction reverts, and the accrued creator fees become permanently unclaimable.

### Finding Description
`transfer_from_pool_vault_to_user` performs a plain `token_2022::transfer_checked` CPI with no error handling [3](#0-2) . Both `collect_creator_fee` (creator-signed) and `collect_creator_fee_permissionless` (callable by any `payer` on behalf of the creator) invoke this function twice per call, once per vault, to pay out `pool_state.creator_fees_token_0/1` [4](#0-3) [5](#0-4) .

`is_supported_mint`, used at pool `initialize`/`initialize_with_permission` time, only inspects Token-2022 extension types (`TransferFeeConfig`, `MetadataPointer`, `TokenMetadata`, `InterestBearingConfig`, `ScaledUiAmount`) and unconditionally accepts any legacy `Token::id()` mint [2](#0-1) . It never checks the mint's `freeze_authority` field, so real-world tokens like USDC (a legacy SPL-Token mint with an active freeze authority) are fully permitted as pool assets.

Once a mint's issuer freezes the creator's associated token account (the exact "blacklist" mechanism used by Circle for USDC), `transfer_checked` into that frozen account will always fail at the SPL token program level. Because `pool_creator` is a fixed, immutable field checked via an `address` constraint [6](#0-5) , there is no way to redirect fee collection to a different destination account, and no admin/rescue instruction exists to reclaim `creator_fees_token_0/1` from the vault once accrued. As in the referenced Stream bug, the "payer" (anyone triggering `collect_creator_fee_permissionless`) cannot force settlement because the counter-party (creator) is frozen, and the funds become stuck with no fallback try/catch.

### Impact Explanation
Accrued creator fees are permanently and irrecoverably locked in `token_0_vault`/`token_1_vault`. `pool_state.creator_fees_token_0/1` never reaches zero, so this capital is permanently excluded from both the creator's payout and from LP withdrawal math (`vault_amount_without_fee` subtracts creator fees), effectively becoming dead, unrecoverable funds forever. This matches the "permanent freezing of user funds" criterion, since no rescue path exists and neither `collect_creator_fee` nor its permissionless variant can ever succeed again for that pool once the creator's account is frozen.

### Likelihood Explanation
Any pool creator using a freeze-authority-bearing legacy SPL token (e.g., pools paired against USDC or USDT) can be frozen by the token issuer at any time for regulatory/compliance reasons, entirely outside the control of this program. The likelihood is nontrivial for popular pools created against centralized stablecoins, and requires no attacker action within the program — it's a pure external condition the contract fails to defensively handle.

### Recommendation
Wrap the creator-fee transfer CPIs in a fallback path (or split them into independently retryable per-token operations) so that a frozen/blacklisted destination for one token does not block collection of the other token's fees, and/or add an admin-gated instruction allowing `creator_fees_token_0/1` to be redirected/rescued to an alternate address if the original recipient's account is permanently unable to receive funds (mirroring the try/catch remediation suggested in the referenced report).

### Proof of Concept
1. Create a pool via `initialize` where `token_0`/`token_1` is a legacy SPL token (e.g., a token mimicking USDC) with an active `freeze_authority`; `is_supported_mint` permits this since it only inspects Token-2022 extensions for Token-2022 mints and unconditionally allows `Token::id()` mints.
2. Swaps accrue `creator_fees_token_0`/`creator_fees_token_1` in `PoolState` as normal.
3. The token issuer freezes the `pool_creator`'s associated token account for that mint (simulating a blacklist event).
4. Any caller invokes `collect_creator_fee_permissionless` (or the creator itself calls `collect_creator_fee`); the `transfer_checked` CPI in `transfer_from_pool_vault_to_user` fails with a frozen-account error from the SPL token program, and the whole instruction reverts.
5. `pool_state.creator_fees_token_0/1` remains non-zero forever; there is no other instruction path to move or reclaim it, so the value is permanently locked in the vault.

pub fn collect_creator_fee_permissionless(
    ctx: Context<CollectCreatorFeePermissionless>,
) -> Result<()> {
    let mut pool_state = ctx.accounts.pool_state.load_mut()?;
    let creator_fees_token_0 = pool_state.creator_fees_token_0;
    let creator_fees_token_1 = pool_state.creator_fees_token_1;
    if creator_fees_token_0 == 0 && creator_fees_token_1 == 0 {
        return err!(ErrorCode::NoFeeCollect);
    }

    let signer_seeds: &[&[u8]] = &[crate::AUTH_SEED.as_bytes(), &[ctx.bumps.authority]];

    transfer_from_pool_vault_to_user(
        ctx.accounts.authority.to_account_info(),
        ctx.accounts.token_0_vault.to_account_info(),
        ctx.accounts.creator_token_0.to_account_info(),
        ctx.accounts.vault_0_mint.to_account_info(),
        ctx.accounts.token_0_program.to_account_info(),
        creator_fees_token_0,
        ctx.accounts.vault_0_mint.decimals,
        &[signer_seeds],
    )?;

    transfer_from_pool_vault_to_user(
        ctx.accounts.authority.to_account_info(),
        ctx.accounts.token_1_vault.to_account_info(),
        ctx.accounts.creator_token_1.to_account_info(),
        ctx.accounts.vault_1_mint.to_account_info(),
        ctx.accounts.token_1_program.to_account_info(),
        creator_fees_token_1,
        ctx.accounts.vault_1_mint.decimals,
        &[signer_seeds],
    )?;

pub fn transfer_from_pool_vault_to_user<'a>(
    authority: AccountInfo<'a>,
    from_vault: AccountInfo<'a>,
    to: AccountInfo<'a>,
    mint: AccountInfo<'a>,
    token_program: AccountInfo<'a>,
    amount: u64,
    mint_decimals: u8,
    signer_seeds: &[&[&[u8]]],
) -> Result<()> {
    if amount == 0 {
        return Ok(());
    }
    token_2022::transfer_checked(
        CpiContext::new_with_signer(
            *token_program.key,
            token_2022::TransferChecked {
                from: from_vault,
                to,
                authority,
                mint,
            },
            signer_seeds,
        ),
        amount,
        mint_decimals,
    )
}
