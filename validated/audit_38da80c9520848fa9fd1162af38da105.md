### Title
Cross-repository status forgery via unscoped `Commit.where(sha:)` lookup enables chained multi-commit unauthorized continuous-delivery deploy - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` resolves target commits solely by `sha`, with no constraint on the repository/stack that produced the webhook, and the `commits` table only enforces uniqueness on `(sha, stack_id)` — not on `sha` alone. Any party able to emit a validly-signed GitHub `status` webhook for **any** repository tracked by Shipit can therefore write a `success` status onto a same-SHA commit belonging to a **different** stack, and by repeating this for a sequence of colliding commits, can make an entire multi-commit range appear CI-approved to `Stack#trigger_continuous_delivery`, which will deploy through the forged range.

### Finding Description
The broken binding: a status written for commit `C` in stack `S` should only be authorized by a webhook that genuinely originated from `S`'s own repository/CI for that exact commit, i.e. `status.stack_id == webhook.repository.stack_id` must always hold. In practice the code only enforces `status.commit.sha == webhook.sha`, dropping the repository/stack constraint entirely: [1](#0-0) 

`Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` iterates over **every** `Commit` row across **every** stack that shares that SHA string — there is no `repository`/`full_name` check anywhere in this handler, unlike sibling handlers such as `PullRequest::OpenedHandler` which explicitly resolve `Shipit::Repository.from_github_repo_name(params.repository.full_name)` before acting: [2](#0-1) 

This is possible because the schema only guards against duplicate `(sha, stack_id)` pairs, not duplicate `sha` values globally: [3](#0-2) 

Since a git commit SHA is a pure content hash independent of which repository hosts it, an attacker who forks (or otherwise recreates byte-for-byte) a public victim repository's commit history produces commits whose SHAs are *identical* to the victim's tracked commits once ingested by `GithubSyncJob` for the attacker's own stack — no cryptographic collision is required. `create_status_from_github!` then drives `Commit#status` -> `deployable?` for both the attacker's own commit and the victim's colliding commit: [4](#0-3) [5](#0-4) 

For any commit whose forged status flips it to deployable, `schedule_continuous_delivery` fires, and `Stack#trigger_continuous_delivery` -> `next_expected_commit_to_deploy` scans `undeployed_commits` and selects the *last* deployable, non-active commit: [6](#0-5) [7](#0-6) 

If the attacker repeats the forgery for several consecutive victim commits (each individually colliding with an attacker-controlled commit of identical content), all of them become `deployable?`, and `next_expected_commit_to_deploy`/`next_commit_to_deploy` will pick the *newest* forged-success commit, so `trigger_deploy` builds a deploy whose `until_commit` spans the whole forged range — i.e. a single continuous-delivery cycle deploys a large batch of victim commits that the victim's own CI never approved.

Existing guards do not stop this: `WebhooksController#verify_signature` only checks that the payload is signed with the secret configured for the `repository.owner.login` claimed in the JSON body — it never checks that the SHA in the payload actually belongs to that repository, and the `status` handler's `params` schema requires only `sha`/`state`, with no `repository` field validated against the resolved commits at all: [8](#0-7) [9](#0-8) 

An attacker who owns/controls any repository tracked by Shipit (their own fork, sandbox, or review-stack repo) can send a legitimately-signed `status` event for that repo's own SHA, but that SHA collides with commits in an entirely different, unrelated victim stack, and the fake status is applied there too.

### Impact Explanation
Each forged webhook writes a `Status` row for a repository/stack that never authenticated it, flips `Commit#deployable?` to true for victim code, and — chained across several colliding commits — causes `Stack#trigger_continuous_delivery` to deploy an entire unvetted batch of victim commits, i.e. an unauthorized deploy executed against the victim's real deployment host/environment variables. This matches the Critical category ("a payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy"). The attack is repeatable against any pair of stacks that happen to share commit SHAs (most easily arranged by forking a public repo), and each repeated forged status widens the blast radius of a single triggered deploy.

### Likelihood Explanation
Preconditions: the attacker needs (a) a repository tracked by Shipit for which they can legitimately trigger a signed `status` webhook (granted per the threat model — "emit webhooks from a repository they own"), and (b) a target victim stack whose commit history shares SHAs with a repository the attacker controls, trivially achievable for any public repository by forking/replaying its git history. No secrets, sessions, or special roles are required beyond what the threat model already grants. Cost is low (fork + push + send N status webhooks); it is fully repeatable and scriptable against any number of colliding commits/stacks.

### Recommendation
Scope the `Commit` lookup in `StatusHandler#process` to the stack/repository indicated in the webhook payload, e.g. resolve `Shipit::Repository.from_github_repo_name(params.repository.full_name)` and constrain `Commit.joins(:stack).where(sha: params.sha, stacks: { repository_id: repository.id })`, mirroring the pattern already used in the `pull_request` handlers. Additionally require/validate a `repository.full_name` param on the `status` handler schema so unscoped lookups are structurally impossible.

### Proof of Concept
Minitest plan (model-level, no live GitHub):
1. Create two `Repository`/`Stack` pairs: `victim_stack` (repository `victim/app`) and `attacker_stack` (repository `attacker/app`).
2. Seed 3 commits with identical SHAs (`sha_1`, `sha_2`, `sha_3`) in both `victim_stack.commits` and `attacker_stack.commits` (allowed since uniqueness is only on `(sha, stack_id)`), forming a consecutive undeployed range in `victim_stack`.
3. Assert baseline: `victim_stack.commits.where(sha: sha_3).first.deployable?` is `false`, and `victim_stack.next_expected_commit_to_deploy` is `nil` or points to an older, already-deployed commit — establishing the equality `status.stack_id == webhook.repository.stack_id` currently unenforced.
4. For each of `sha_1, sha_2, sha_3`, call `Shipit::Webhooks::Handlers::StatusHandler.call({ 'sha' => sha_n, 'state' => 'success', 'context' => 'ci/attacker', 'repository' => { 'full_name' => 'attacker/app', 'owner' => { 'login' => 'attacker' } } })` (bypassing only the outer signature check, per rules, since that's granted to the attacker for their own repo).
5. Assert each corresponding commit in `victim_stack` (matched purely by SHA) now has a `Status` row with `state: 'success'` and `deployable?` is `true`, even though no status/handler ever referenced `victim/app`.
6. Assert `victim_stack.next_expected_commit_to_deploy` now equals the commit with `sha_3` (the latest forged-success commit).
7. Call `victim_stack.trigger_continuous_delivery` once and assert a single `Deploy` is created with `until_commit.sha == sha_3` and `since_commit` equal to the previously last-deployed commit — demonstrating one forged sequence caused a full multi-commit unauthorized deploy of `victim/app`.
