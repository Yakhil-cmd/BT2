### Title
Webhook Handlers Process Stacks By `repository.full_name` While Signature Verification Authenticates Only `repository.owner.login` - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/handler.rb])

### Summary
This is a check/act binding mismatch analogous to the SSVNetwork `withdraw()` bug: a validation is performed against one piece of state while the actual mutating action is later performed against a different, unchecked piece of the same attacker-controlled input. In `SSVNetwork`, the liquidation check used the pre-withdrawal balance instead of the post-withdrawal balance. In Shipit, the webhook signature check authenticates the request against the *organization* named in `repository.owner.login` (or `organization.login`), while the code that actually mutates state — selecting and syncing `Stack` records — keys off the completely independent `repository.full_name` field from the very same JSON body. Nothing binds these two fields together, so a signature that is valid for organization A can be replayed with a `repository.full_name` pointing at organization B's repository, and the B stack will be acted upon.

### Finding Description
`WebhooksController#verify_signature` selects which GitHub App / webhook secret to validate against using only the organization login: [1](#0-0) [2](#0-1) 

`repository_owner` is derived purely from the JSON body (`repository.owner.login`, falling back to `organization.login`), and `Shipit.github(organization: repository_owner)` picks the corresponding per-organization webhook secret to check the HMAC signature against.

Separately, every event handler resolves which `Stack` records to mutate using a different field of the same body — `repository.full_name` — with no cross-check against the organization that was actually authenticated: [3](#0-2) 

For example, `PushHandler#process` uses this `stacks` helper to force-sync stacks to an attacker-supplied SHA: [4](#0-3) 

The engine supports multiple GitHub App installations (one per organization) sharing a single Shipit instance, each with its own `webhook_secret`, as shown in the test fixture configuring `OrgOne` and `OrgTwo` independently: [5](#0-4) 

Because `verify_signature` binds the HMAC check to `repository.owner.login` while the handler binds the mutating action to `repository.full_name`, these two values are never required to agree. An actor who is a legitimate GitHub App/webhook owner for **their own** organization (Org A) — and therefore in possession of a validly-issued signature for Org A, exactly as intended by the design — can submit a webhook body where `repository.owner.login = "OrgA"` (so the signature check passes using Org A's secret) but `repository.full_name = "OrgB/victim-repo"` (a repository belonging to an unrelated organization hosted on the same Shipit instance). The signature check succeeds because it only ever looked at the owner field, and `Handler#stacks` then resolves and mutates stacks belonging to Org B.

**Binding broken:** `organization authenticated (repository.owner.login) == repository written (repository.full_name)` — before the attacker's forged request this equality always holds for genuine GitHub-originated webhooks (GitHub only signs events for the actual repository), but nothing in the engine enforces it, so the attacker can break the equality at will once they have a legitimately-issued signature for any organization present in the shared instance's config.

### Impact Explanation
This qualifies as a cross-repository write (Critical): the `push` handler causes `stack.sync_github(expected_head_sha:)` to run for a stack belonging to an organization the attacker does not control, forcing synchronization to an attacker-chosen SHA. Other handlers (e.g. `check_suite`, `status`, `pull_request/*`) key off the same unvalidated `repository.full_name` and can mark arbitrary commits as CI-passing/deployable, capture labels, or drive review-stack lifecycle transitions for another organization's stacks — all without ever authenticating against that organization's own webhook secret.

### Likelihood Explanation
Requires only that the shared Shipit instance host more than one GitHub organization (a documented, supported configuration — see `test/dummy/config/secrets_double_github_app.yml`) and that the attacker be a legitimate webhook sender for at least one of those organizations. No target-organization secret, session, API token, or repository write access is needed — only the ordinary, already-possessed signing capability for the attacker's own onboarded organization, exactly analogous to Alice legitimately calling `withdraw()` on her own cluster in the original report.

### Recommendation
Bind the authenticated organization to the repository actually acted upon: after selecting the GitHub App config via `repository_owner`, verify that `repository.full_name` starts with `"#{repository_owner}/"` (or otherwise assert consistency between `owner.login` and the owner segment of `full_name`) before dispatching to handlers, and reject the request otherwise.

### Proof of Concept
1. Shipit instance hosts two organizations, `OrgA` and `OrgB`, each with an independently configured GitHub App / `webhook_secret` (per the supported multi-org config).
2. Attacker is a legitimate GitHub App owner/admin for `OrgA` and can therefore produce a validly-signed webhook payload for `OrgA` events (their normal, intended capability).
3. Attacker crafts a `push` event body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "OrgA" },
    "full_name": "OrgB/victim-repo"
  }
}
```
4. Attacker signs the raw body with `OrgA`'s webhook secret and sends `POST /webhooks` with `X-Github-Event: push` and the resulting `X-Hub-Signature`.
5. `WebhooksController#verify_signature` resolves `repository_owner` = `"OrgA"`, fetches `OrgA`'s webhook config, and the signature validates successfully. [1](#0-0) 
6. `PushHandler#process` calls `Handler#stacks`, which looks up `Repository.from_github_repo_name("OrgB/victim-repo")` and syncs `OrgB`'s stacks to the attacker-chosen SHA — despite the request never being authenticated against `OrgB`'s webhook secret. [3](#0-2)
