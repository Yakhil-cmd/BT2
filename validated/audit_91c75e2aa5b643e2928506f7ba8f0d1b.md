### Title
Fee-on-transfer / partial-transfer underlying token can desynchronize vault's internal `assets` accounting from real token balance, socializing a shortfall onto all other zToken holders - (File: mainnet/contracts/vault/v0-vault-usdc.clar)

### Summary
Every Zest vault (`v0-vault-usdc.clar`, `v0-vault-usdh.clar`, `v0-vault-stx.clar`, `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`) tracks the assets it holds in a virtual state variable `assets`, incremented by the caller-supplied `amount` parameter on deposit rather than by the amount actually received from the token transfer. `receive-underlying` performs a blind, unchecked `transfer` call with no pre/post balance verification. `total-assets`/`total-assets-preview`, which price shares for every other depositor and redeemer in the vault, are derived exclusively from this `assets` variable, never from the vault's real on-chain token balance (`ubalance`). Any transfer that delivers less than the requested `amount` (fee-on-transfer, transfer hooks, blocklist-partial-transfer, etc.) inflates `assets` beyond the vault's real backing, creating a shortfall that is silently socialized across all other zToken holders.

### Finding Description
In `deposit`, the vault mints shares and updates its books using the caller-declared `amount`, not the amount actually delivered: [1](#0-0) 

The transfer that is supposed to move `amount` of the underlying token into the vault is a blind call with no balance check: [2](#0-1) 

Crucially, the value used to price shares for *every subsequent depositor/redeemer* comes only from the tracked `assets` variable plus accrued interest — never from the vault's real token balance: [3](#0-2) 

If the transfer in `receive-underlying` delivers `amount' < amount` for any reason (fee-on-transfer behavior, a token upgrade, a transfer hook that skims value, etc.), the vault still records `assets = current-assets + amount` even though it only actually received `amount'`. From that point on, `total-assets`/`total-assets-preview` overstate the vault's real backing by `amount - amount'`. Since these functions are the sole source of truth for `convert-to-shares-preview`/`convert-to-assets-preview` used by *all* other depositors and redeemers, the mispriced state primed by the depositor's single transaction is consumed by every other zToken holder afterward: shares are minted/redeemed against inflated assets the vault does not actually hold. The same unchecked-amount pattern also exists in `system-repay`/`receive-underlying capped-amount` flows and in the market's `supply-collateral-add`, which similarly forwards `amount` (not an actual-received measurement) into `vault-deposit`. [4](#0-3) 

### Impact Explanation
This is not a self-harm scenario: the attacker (or the token's inherent fee behavior) creates a shortfall in the vault's real backing while its internal accounting believes it is fully backed. Every other zToken holder's redemption is priced from this inflated shared state (`total-assets`), so honest depositors/redeemers who come after are the ones who discover — only when attempting to withdraw — that the vault cannot actually pay out the accounted value. Because `redeem` checks `(asserts! (>= current-assets inkind) ERR-INSUFFICIENT-ASSETS)` against the same inflated `assets` variable rather than the real balance, later redeemers can be blocked or receive less than entitled, i.e., temporary freezing of funds for other suppliers, and in the worst case a race to redeem before the shortfall is discovered results in latecomers permanently losing their share of the shortfall. This satisfies the temporary/permanent freezing-of-funds impact class.

### Likelihood Explanation
Likelihood depends on whether any of the six hardcoded underlying tokens (wSTX, sBTC, USDC, USDH, stSTX, stSTXbtc) ever exhibit any partial-transfer behavior (fee, hook, upgrade). Because the vaults hardcode calls to specific token contracts (e.g., `.usdc`, `.wstx`), the immediate exposure is bounded to those tokens' current behavior, but the code contains no defensive balance check regardless — so any future token upgrade, proxy change, or edge-case transfer semantics on these tokens converts directly into a shortfall with no on-chain detection or mitigation.

### Recommendation
In `receive-underlying` (and any function that credits the vault's `assets` state based on a caller-supplied amount), measure the actual balance delta: read `ubalance` before and after the `transfer` call, and use that delta — not the requested `amount` — to update `assets` and to determine `inkind` shares. Apply the same actual-received measurement in `system-repay` and in `market.clar`'s `supply-collateral-add`/`vault-deposit` chain.

### Proof of Concept
1. Suppose one of the underlying token contracts is upgraded/proxied (or already) to deliver `amount - fee` to the recipient on `transfer` (fee-on-transfer / deflationary semantics), while returning `(ok true)`.
2. User A calls `deposit(amount=1000, min-out=0, recipient=A)` on `v0-vault-usdc.clar`. `receive-underlying` calls `.usdc transfer 1000 A current-contract none`, but the vault's real USDC balance only increases by 990 (10 fee).
3. Despite this, `deposit` executes `(var-set assets (+ current-assets 1000))` — the vault's tracked assets are now 10 units higher than its real balance.
4. `total-assets`/`total-assets-preview`, used to price shares for every other user, now report a value 10 units too high.
5. User B, an existing/subsequent depositor, redeems shares priced against this inflated `total-assets`. The `ERR-INSUFFICIENT-ASSETS` check at redemption compares against the same inflated `assets` variable, so B's redemption (or a later user's redemption) can succeed nominally per accounting while the vault's real balance is insufficient to pay out the last redeemer(s) in full — the deficit of 10 units is socialized across whichever zToken holders redeem last.
