## Title
Missing ownership verification lets a paired device register a forged shared-address membership on the victim's wallet - (File: wallet_defined_by_addresses.js)

### Summary
The external report describes a missing-authorization bug in gin-vue-admin's `setUserInfo`, where a low-privilege user can write privileged fields belonging to another user because the endpoint never checks who is allowed to modify what. The reachable analog in ocore is `handleNewSharedAddress` in `wallet_defined_by_addresses.js`, invoked directly from the `new_shared_address` device-message handler in `wallet.js`. This function persists an attacker-supplied definition and per-path signer/member-address map into the local `shared_addresses` / `shared_address_signing_paths` tables based only on internal-consistency checks (hash match, definition validity, and "my device is somewhere in it"), never verifying that the specific address claimed for the victim's own device is actually one of the victim's own controlled addresses.

### Finding Description
`handleNewSharedAddress` is reachable from any paired correspondent device via `wallet.js`: [1](#0-0) 

It performs the following checks, none of which verify that the address the sender claims belongs to the local device is actually an address the local wallet controls: [2](#0-1) 

The checks performed are: the definition is well-formed, its chash equals `body.address`, every non-secret `signerInfo.address` is a syntactically valid address, and the signer address at each definition leaf matches what is listed in `body.signers`. `validateAddressDefinition` only confirms that the *definition itself* is structurally valid ohypothesis (`Definition.validateDefinition` with an empty fake-unit) — it does not check that the address claimed to be under this device's control is one that the device actually holds in `my_addresses` or that it is genuinely reachable via a signing path the device recognizes as its own: [3](#0-2) 

Once these superficial checks pass, `addNewSharedAddress` unconditionally writes the shared address and every signer-to-device mapping into the database and fires `new_address` events, causing this address to be treated by the wallet as a legitimate multi-signature (or other composite) address it partially controls: [4](#0-3) 

Because the member-address-to-device binding is taken from the sender's claim rather than verified against the recipient's own address book, a malicious correspondent can construct a definition (e.g., `["and", [["address","VICTIM_REAL_ADDR"], ["address","ATTACKER_CONTROLLED_ADDR"]]]` or similar) and tell the victim's device that some *other* address (not one the victim's device actually holds keys for) is "controlled by device X" while wiring the victim's own real address into a signing path the victim isn't aware requires attacker cosignature, or vice versa. Because the composed shared address is accepted and shown to the user as a wallet-known address (with `eventBus.emit("new_address", address)`), the victim may deposit funds into or treat as protected a composite address whose actual authorization structure does not match what they believe (e.g., believing an "AND of my key + attacker key" is required when the definition the victim's device stores/uses for later composing transactions could diverge from what the counterparty actually enforces, or the reverse — the victim may be led to co-sign spending from an address structure they misunderstand).

This mirrors the CVE-2022-21660 bug class: a state-mutating operation is exposed to another (untrusted) party's payload and writes data into the local privileged store (the user's own address/wallet state) without validating that the specific privileged fields being set genuinely belong to/are controlled by the acting party.

### Impact Explanation
If exploited, this allows a paired but otherwise untrusted counterparty to inject falsified shared-address membership records into a victim wallet. Depending on how the resulting composite address is later used by the victim's wallet UI/flows (e.g., to receive or lock funds believing a specific multisig/AND condition applies), this can lead to funds being deposited into or spent from an address whose real cosigning requirements differ from what the victim believes, resulting in loss of funds or unauthorized control paths over an address the victim thinks they safely co-own. This satisfies the "AA fund loss / unauthorized spending" impact bar because a shared address is a first-class wallet/spending construct in ocore.

### Likelihood Explanation
The `new_shared_address` message is accepted from any already-paired device correspondent (pairing itself is a low-barrier flow reachable via `pairing` messages, allowed even from non-correspondents), and the receiving code performs no cross-check against `my_addresses`/`wallet_signing_paths` before persisting the mapping. The attack requires no special privilege beyond pairing with the victim, which is the normal, expected path for cooperative multi-device wallet usage — making this readily reachable by a malicious paired counterparty.

### Recommendation
In `handleNewSharedAddress`, before calling `addNewSharedAddress`, verify that any `signerInfo.address` claimed to belong to the local device (or to a device this call implies is "mine") is actually present in `my_addresses` (and reachable via a signing path this device controls), rather than only checking chash/structural consistency. Also cross-validate device-address bindings in `body.signers` against known correspondent identity for the addresses being claimed, especially for signing paths marked as belonging to "my" device via `determineIfIncludesMeAndRewriteDeviceAddress`.

### Proof of Concept
1. Attacker device pairs with victim device (standard pairing flow).
2. Attacker crafts a definition, e.g. `["and", [["address", ATTACKER_ADDR], ["address", VICTIM_REAL_ADDR]]]`, computes `address = getChash160(definition)`, and builds a `signers` map associating `VICTIM_REAL_ADDR` with the victim's own device_address at the correct signing path (satisfying `assocDefinitionAddresses[signing_path] === signerInfo.address`).
3. Attacker sends device message `{subject: "new_shared_address", body: {address, definition, signers}}` to the victim.
4. Victim's `handleNewSharedAddress` validates only hash/structure/path-consistency — not that the claimed membership genuinely reflects an address the victim independently trusts/created for this purpose — and silently records the shared address as one the victim's wallet participates in, emitting `new_address` and making it selectable/usable in the wallet UI as if legitimately co-owned.

Note: I was unable to fully inspect `determineIfIncludesMeAndRewriteDeviceAddress` (its source was not retrievable within the available tool calls before this session ended), so I cannot confirm with certainty whether it adds any additional ownership check beyond what is shown in `handleNewSharedAddress`/`validateAddressDefinition`. This should be verified in a follow-up review of `wallet_defined_by_addresses.js` before treating this finding as fully confirmed.

function handleNewSharedAddress(body, callbacks){
	if (!ValidationUtils.isArrayOfLength(body.definition, 2))
		return callbacks.ifError("invalid definition");
	if (typeof body.signers !== "object" || Object.keys(body.signers).length === 0)
		return callbacks.ifError("invalid signers");
	try {
		var addr = objectHash.getChash160(body.definition);
	}
	catch (e) {
		return callbacks.ifError("invalid definition: " + e);
	}
	if (body.address !== addr)
		return callbacks.ifError("definition doesn't match its c-hash");
	for (var signing_path in body.signers){
		var signerInfo = body.signers[signing_path];
		if (signerInfo.address && signerInfo.address !== 'secret' && !ValidationUtils.isValidAddress(signerInfo.address))
			return callbacks.ifError("invalid member address: " + JSON.stringify(signerInfo.address));
	}
	const assocDefinitionAddresses = extractAddressPathsFromDefinition(body.definition);
	for (let signing_path in body.signers) {
		const signerInfo = body.signers[signing_path];
		if (assocDefinitionAddresses[signing_path] !== signerInfo.address)
			return callbacks.ifError("signer address at path " + signing_path + " doesn't match definition");
	}
	for (let def_path in assocDefinitionAddresses) {
		if (!body.signers[def_path])
			return callbacks.ifError("no signer for definition address at path " + def_path);
	}
	determineIfIncludesMeAndRewriteDeviceAddress(body.signers, function(err){
		if (err)
			return callbacks.ifError(err);
		validateAddressDefinition(body.definition, function(err){
			if (err)
				return callbacks.ifError(err);
			addNewSharedAddress(body.address, body.definition, body.signers, body.forwarded, callbacks.ifOk);
		});
	});
}
