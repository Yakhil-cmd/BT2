## Title
Cross-repository commit-status forgery via unscoped `Commit.where(sha:)` in `StatusHandler#process` — (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` looks up commits by bare SHA with no repository/stack scoping and writes a `Status` to every matching row. Because the `commits` table only enforces sha uniqueness per `stack_id` (not globally), the same SHA can legitimately exist in multiple `Stack`s tracking different `Repository` records (forks, mirrors, shared history). A status webhook that is validly signed for repository A therefore also mutates commit/status state for repository B's stack whenever they share a SHA, and — when a victim stack has `blocking_statuses` configured — that state feeds directly into `Commit#blocked?`/`#deployable?`, letting one repository's CI signal gate or unblock another stack's deploys.

### Finding Description
The broken invariant, stated as an equality that should hold but doesn't:
`status.stack_id == authenticated_repository.stack_id` for every `Commit` mutated by a single incoming `status` webhook.

Code path:
1. `Shipit::WebhooksController#verify_signature` authenticates the payload only against the GitHub App keyed by `repository_owner` (`params.dig('repository','owner','login')`), using `GitHubApp#verify_webhook_signature`: [1](#0-0)  This proves the event came from *some* repo covered by that org's App installation and shared webhook secret — it never validates that the SHA/context in the body actually belongs to a stack of that repository. If no `webhook_secret` is configured (documented as optional), `verify_webhook_signature` returns `true` unconditionally: [2](#0-1) 
2. `StatusHandler#process` then resolves affected commits purely by SHA, with no `repository`/`stack` filter at all: [3](#0-2) 
3. `Commit#create_status_from_github!` writes the status using each matched commit's *own* `stack_id`: [4](#0-3)  so the write is not "attacker-chosen stack" but "any stack whose commit table happens to contain that SHA."
4. The schema only guarantees sha uniqueness per stack (`index_commits_on_stack_id_and_sha` — see `db/migrate/20170524104615_index_commits_on_stack_id_and_sha.rb`), not globally, so identical SHAs across different `Stack`/`Repository` rows are an expected, supported condition (forks, mirrors, shared upstream history).
5. That status feeds `Status::Common#blocking?` (`!success? && commit.blocking_statuses.include?(context)`) [5](#0-4)  and `Commit#blocked?`, which scans reachable undeployed commits for any `blocking?` status: [6](#0-5)  This directly gates `Commit#deployable?` [7](#0-6)  and `UndeployedCommit#deploy_disallowed?`/`#deploy_state`.

Exploit flow: an attacker who can cause a legitimately signed `status` event to be emitted for some repository R covered by the Shipit-installed GitHub App (e.g. they push a commit-status via their own CI integration on a repo they control that shares the App installation, or push a branch whose head SHA is identical to a commit already tracked by a victim stack because of shared history/fork lineage) sets `context: "ci/coverage"` and `state: "failure"|"success"`. `StatusHandler` applies this to every `Commit` row sharing that SHA, including the victim stack's row, flipping `blocked?` for the victim stack (blocking a legitimate deploy, or — if the attacker forces `success` for a required/blocking context — helping clear a block) without ever authenticating against the victim's repository or stack.

None of the existing guards prevent this: `verify_signature` only checks org-level HMAC, not per-repo/stack scoping; `ExplicitParameters` in `StatusHandler.params` only validates payload shape, not ownership; there is no `repository`/`stack_id` filter anywhere in `process`.

### Impact Explanation
A payload authenticated for one repository can flip CI/blocking state (and therefore deploy eligibility) for a stack belonging to a different repository/tenant that happens to share a commit SHA — this is a cross-tenant state-mutation issue matching "a payload for one repository mutating another's stack/commit" (Critical). Repeatable on every `status` webhook received for any shared SHA; blast radius spans all stacks configured with `blocking_statuses` (or `required_statuses`) that ever ingest a commit whose SHA also appears in another tracked repository.

### Likelihood Explanation
Requires: (a) a valid signature from a GitHub App installation Shipit trusts (either because `webhook_secret` is unset — a documented "optional" config — or because the attacker can legitimately trigger a status event from a repo already covered by that installation, e.g. their own CI on a repo they control under the same org/App), and (b) a shared SHA between the attacker's repo and the victim's tracked stack (realistic for forks/mirrors/shared-history repos, which Shipit explicitly supports tracking as separate stacks). Cost to the attacker is low once these common preconditions hold; the action is fully repeatable.

### Recommendation
Scope `StatusHandler#process` (and analogous handlers) to only update commits belonging to stacks whose `Repository` matches the authenticated payload's `repository.full_name`/owner, e.g. `Commit.joins(stack: :repository).where(sha: params.sha, shipit_repositories: { full_name: params.repository... })`, instead of a bare `Commit.where(sha:)`.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb`, hypothetical — no live GitHub needed):
```ruby
test "status for repo A does not affect a same-sha commit tracked by repo B's stack" do
  sha = 'a' * 40
  stack_a = shipit_stacks(:shipit) # repo A
  stack_b = create_stack_with_repo('victim/other-repo') # repo B, blocking_statuses: ['ci/coverage']

  commit_a = stack_a.commits.create!(sha:, ...)
  commit_b = stack_b.commits.create!(sha:, ...) # same sha, different stack/repo

  before_a = commit_a.reload.blocked?
  before_b = commit_b.reload.blocked?

  Shipit::Webhooks::Handlers::StatusHandler.call(
    'sha' => sha, 'state' => 'failure', 'context' => 'ci/coverage',
    'repository' => { 'full_name' => 'org/repo-a' } # only repo A authenticated this event
  )

  assert_equal before_a, commit_a.reload.blocked? # expected: repo A's own semantics apply
  assert_equal before_b, commit_b.reload.blocked?, "repo B's stack must not be affected by repo A's status"
  # FAILS today: commit_b.blocked? flips even though repo B never authenticated the event
end
```

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
