**Rationale:** `VersionedGroupData` (and `fetch_tagged_data_no_record`) in `aptos-move/mvhashmap/src/versioned_group_data.rs` is a purely in-memory, per-block-execution multi-versioned data structure used internally by Block-STM to track speculative resource-group writes/reads during parallel execution of a single block. It has no relationship to chain-id, transaction admission, authenticators, mempool, or vm-validator logic at all.

Key points confirming this:
- `group_key`/`tag` pairs in this structure are resource-group access paths (`K`, `T` generic types bound by `Hash + Clone + Debug + Eq`), not chain-ids, and each `VersionedGroupData` instance (created via `VersionedGroupData::empty()`) is scoped to a single block's execution lifetime, not to any persistent "chain context." [1](#0-0) [2](#0-1) 
- `fetch_tagged_data_no_record` looks up data purely by `(group_key, tag)` and `txn_idx` within one such instance; it has no notion of "chain-id-scoped" data or cross-instance lookups — two separate `VersionedGroupData` instances (e.g., for two separate block executions/VM sessions) are fully independent Rust objects with their own `DashMap`/`BTreeMap` state and no shared storage, so a read from one instance can never resolve to data written in another instance. [3](#0-2) 
- Chain-id binding and validation (the actual admission-boundary invariant referenced in the question) is enforced separately in transaction prologue/vm-validator/mempool logic, entirely unrelated to this block-execution data structure. There is no code path by which unprivileged transaction/API input can cause one `VersionedGroupData` instance to read state from a different instance, so there is no "cross-context resource confusion" or "chain-id binding" to corrupt here.

The premise of the question conflates an internal Block-STM execution data structure's `group_key` with the transaction-admission chain-id binding invariant — these are unrelated concepts with no code path connecting them. This falls outside the defined admission boundary (mempool/vm-validator/authenticator/VM prologue chain-id checks) and does not meet the decision standard for a valid finding.

    group_tags: DashMap<K, HashSet<T>>,

    pub fn fetch_tagged_data_no_record(
        &self,
        group_key: &K,
        tag: &T,
        txn_idx: TxnIndex,
    ) -> Result<(Version, V), MVGroupError> {
        let key_ref = GroupKeyRef { group_key, tag };

        // We are accessing group_sizes and values non-atomically, hence the order matters.
        // It is important that initialization check happens before fetch data below. O.w.
        // we could incorrectly get a TagNotFound error (do not find data, but then find
        // size initialized in between the calls). In fact, we always write size after data,
        // and sometimes (e.g. during initialization) even hold the sizes lock during writes.
        // It is fine to observe initialized = false, but find data, in convert_tagged_data.
        let initialized = self.group_sizes.contains_key(group_key);

        let data_value = self.values.fetch_data_no_record(&key_ref, txn_idx);
        self.convert_tagged_data(data_value, initialized)
    }
