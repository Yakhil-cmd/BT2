### Title
`CCMenuUrlController#fetch` mints a global-scope `read:stack` `ApiClient` (`stack_id` never set) that `Api::BaseController#stacks` treats as unscoped access to all stacks - ([File: app/controllers/shipit/ccmenu_url_controller.rb], [File: app/controllers/shipit/api/base_controller.rb])

### Summary
`CCMenuUrlController#fetch` creates (or reuses) an `ApiClient` keyed only by `creator` and `name`, never assigning `stack`, so the resulting `ApiClient#stack_id` is always `nil`. That client's `authentication_token` is handed back to the requester in the JSON response, and because `Api::BaseController#stacks` falls back to `Stack.all` whenever `stack_id` is blank, this token — nominally minted for "read access to CCMenu status of one stack" — actually grants read access to every stack in the installation.

### Finding Description
The intended binding is: `ApiClient` issued for stack `S` == token can only read stack `S`, i.e. `current_api_client.stack_id == S.id` must hold for any client created through a single-stack-scoped flow like CCMenu. That binding is broken.

Code path:
- `app/controllers/shipit/ccmenu_url_controller.rb#client`: [1](#0-0) 
creates/fetches the client via `create_with(permissions: %w[read:stack]).find_or_create_by!(creator: current_user, name: 'CCMenu Client')`. Neither `create_with` nor `find_or_create_by!` reference `stack`, so `stack_id` is never populated — it defaults to `nil` (`belongs_to :stack, optional: true` in `app/models/shipit/api_client.rb` line 8 confirms this is a legal, unenforced state).
- The same client record (same `id`, same token) is therefore reused across every distinct stack the same user later calls `fetch` for, because the lookup key is `creator + name` only, not `creator + name + stack`.
- `Api::BaseController#stacks`: [2](#0-1) 
`current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all` — since `stack_id` is `nil`/blank, `stack_id?` is falsy, so this evaluates to `Stack.all`.
- `Api::StacksController#index` (and `#show` via `stacks.from_param!`) then operate against `Stack.all`: [3](#0-2) 
- `ApiClient.authenticate`/`message_verifier` (`app/models/shipit/api_client.rb` lines 24-31) only verifies the token signature and looks up the client by id; it performs no additional per-request stack binding check, so nothing downstream re-derives or restricts scope from the original CCMenu request.

No other guard intervenes: `require_permission!` only checks the `permissions` array (`read:stack` is present, satisfied), not `stack_id`; there is no validation on `ApiClient` requiring `stack` presence when created outside the explicit `Api::StacksController#create` (write) path.

Exploit flow: any logged-in Shipit user (any session) triggers `GET` on the CCMenu-url route for a stack they can view, receives `{ ccmenu_url: "...&token=<TOKEN>" }`, extracts `<TOKEN>`, and then uses HTTP Basic auth with that token against `GET /api/stacks` (or `/api/stacks/:id`) for any stack in the system — including stacks/repositories they have no relationship to. The response is a full listing/detail of stacks belonging to other tenants.

### Impact Explanation
An attacker with only a valid Shipit session and access to one stack's CCMenu link obtains a token that discloses `Api::StacksController#index`/`#show` data — stack `branch`, `environment`, `state`, `repository`, lock status, etc. — for every stack across every repository/tenant hosted by the same Shipit instance, not just the one they requested. This is unauthorized cross-tenant read of stack state, matching the "High" impact category (escalation to read stack state beyond the attacker's granted scope). It is repeatable indefinitely with the same token and against every stack id in the system.

### Likelihood Explanation
Preconditions are low-cost: the attacker needs an ordinary logged-in Shipit session (no `Shipit.github_teams` membership, no maintainer role) and access to trigger the CCMenu-url fetch for any single stack they can view. No secrets, no privileged role, and no interaction with GitHub webhooks/signatures is required. The flaw is purely in the engine's `ApiClient` creation logic, always reachable when the CCMenu feature is enabled.

### Recommendation
Bind the CCMenu-issued `ApiClient` to the specific stack it was requested for: include `stack: stack` in both the `create_with`/`find_or_create_by!` lookup key and creation attributes in `CCMenuUrlController#client`, and add a model-level invariant/validation ensuring `read:stack`-only clients created via this flow always have a non-nil `stack_id`. Additionally, consider hardening `Api::BaseController#stacks` so a blank `stack_id` never implicitly means "all stacks" for clients that were never explicitly granted unrestricted (`stack_id: nil` intentional) access — e.g. require an explicit `global: true` flag rather than treating `nil` as a wildcard.

### Proof of Concept
```ruby
# test/controllers/shipit/ccmenu_url_controller_test.rb (conceptual, no live GitHub)
class CcmenuUrlControllerTest < ActionController::TestCase
  test "CCMenu token is not scoped to the requested stack" do
    stack_a = shipit_stacks(:shipit)
    stack_b = create_stack(repository: create_repository(name: 'other-repo'))

    session[:user_id] = shipit_users(:walrus).id
    get :fetch, params: { stack_id: stack_a.to_param }
    token = URI.decode_www_form(URI(response.parsed_body['ccmenu_url']).query).to_h['token']

    client = Shipit::ApiClient.authenticate(token)
    assert_nil client.stack_id # binding broken: not scoped to stack_a

    # Present same token against a different stack's API
    ApiControllerTestCase.new(self).authenticated_as(client) do
      get :index, controller: Shipit::Api::StacksController
    end
    ids = response.parsed_body.map { |s| s['id'] }
    assert_includes ids, stack_b.id # attacker reads a stack never granted to this token
  end
end
```
This demonstrates the `stack_id? -> Stack.all` fallback converts a single-stack CCMenu token into a global `read:stack` grant, confirming the broken binding.
