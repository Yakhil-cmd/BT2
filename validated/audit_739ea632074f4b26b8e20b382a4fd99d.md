### Title
Webhook signature verification keyed on unsigned `repository.owner.login` allows cross-repository webhook forgery when any configured organization has no `webhook_secret` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks which GitHub App/`webhook_secret` to validate the inbound HMAC signature against using `repository_owner`, a value read straight out of the untrusted, not-yet-verified JSON body. The event handlers, however, resolve the target `Stack`/`Repository` using a different, also unverified field, `repository.full_name`. Because these two fields are never bound to each other and neither is protected by the signature check that runs before they're trusted, an attacker who knows (or targets) any configured GitHub organization in a multi-org Shipit deployment that has a blank `webhook_secret` can craft a payload that authenticates as that "weak" organization while acting on a completely different, victim repository's stack.

### Finding Description
The equality broken is: **organization that authenticated ≠ repository that is written**.

- `verify_signature` derives the authentication key purely from attacker-controlled JSON: `repository_owner` is `params.dig('repository','owner','login') || params.dig('organization','login')`. [1](#0-0) 

- It then fetches the GitHub App config for that organization name and verifies the raw body's `X-Hub-Signature` against *that org's* `webhook_secret`: [2](#0-1) 

- `GitHubApp#verify_webhook_signature` completely skips verification when the resolved organization's `webhook_secret` is not configured: `return true unless webhook_secret`. [3](#0-2) 

- Once "verified" (or trivially bypassed), `WebhooksController#create` dispatches the *entire unsigned payload* to handlers: `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`. [4](#0-3) 

- The base `Handler` (used by `PushHandler`, `PullRequest::*Handler`, etc.) resolves the target stacks using `payload.dig('repository', 'full_name')` — a field that was never checked against `repository_owner` or covered by the signature: [5](#0-4) [6](#0-5) 

- Shipit explicitly supports multiple GitHub organizations configured independently, each with its own (optionally blank) `webhook_secret`, as shown in the documented multi-org config schema, where `webhook_secret:` is commented `# nil` for each org: [7](#0-6) [8](#0-7) 

This mirrors the GroupBuy `_purchaseProof.length == 0` bug class exactly: a weaker/degenerate verification branch (`return true unless webhook_secret`) is taken based on an attacker-influenceable selector (`repository_owner`, from the unsigned body), and the field actually acted upon (`repository.full_name`, driving which `Stack`/`Repository` is looked up and operated on) is never covered by that verification, so the "proof" (signature over one org) does not correspond to the "allow list" (the actual target repository/stack).

### Impact Explanation
If any organization configured in `secrets.github` has no `webhook_secret` set (a supported and documented configuration for multi-org Shipit setups, e.g. an org onboarded without configuring a secret yet, or intentionally left blank), an unauthenticated attacker can:
1. Send a webhook POST with `X-Github-Event: push` (or `pull_request`, `check_suite`, etc.) where `repository.owner.login` (or `organization.login`) is set to that weak/no-secret organization, causing `verify_webhook_signature` to unconditionally return `true`.
2. Set `repository.full_name` in the same payload to the full name of an entirely different, victim repository/stack that Shipit tracks under a *different*, properly-secured organization.
3. Because handler dispatch keys strictly off `repository.full_name`, the forged event is treated as legitimate for the victim stack: e.g. `PushHandler` calls `stack.sync_github(expected_head_sha: params.after)` for a `stack` chosen from `Repository.from_github_repo_name(victim_full_name)`, or pull-request handlers create/close review stacks, capture labels, or trigger merges for the victim repository/stack — all without ever presenting a valid signature for that repository's organization.

This crosses a credential/authentication boundary that the engine documents as its authentication mechanism for webhooks (per-organization `webhook_secret` / GitHub App signature), letting an attacker who only knows one org's (missing) secret spoof state-changing GitHub events for another org's repositories tracked by the same Shipit instance — an unauthorized trigger of deploy-relevant workflow state (sync, review-stack provisioning, merge status, archive/unarchive) for a repository the attacker has no access to. This fits the "unauthorized deploy/rollback/merge"-adjacent High/Critical impact category, since push/pull_request/check_suite events feed directly into stacks that later trigger deploys and merges.

### Likelihood Explanation
Likelihood depends entirely on deployment configuration: it requires a multi-organization Shipit instance where at least one configured organization has a blank `webhook_secret`. This is not a hypothetical edge case — the engine's own documented multi-org config template (`config/secrets.development.shopify.yml`, `test/dummy/config/secrets_double_github_app.yml`) shows `webhook_secret: # nil` as the baseline/example value for each org, and `docs/setup.md` treats it as optional ("If you've set a webhook secret..."). Any operator who follows the documented multi-org pattern without setting a secret for every single org (e.g., while onboarding a new org, or leaving an internal/low-risk org unset) exposes every other org's stacks to this cross-organization forgery, with zero prerequisites (no session, no token, no repository access) beyond knowing/guessing the weak org's name and the victim's `repository.full_name`.

### Recommendation
- Bind the field used for handler dispatch (`repository.full_name`) to the same trust boundary as the field used for signature-key selection (`repository.owner.login`/`organization.login`); reject requests where the two are inconsistent, or resolve the target repository the same way the signing organization was resolved.
- Do not silently pass verification (`return true unless webhook_secret`) when a secret is absent for an organization; require every configured organization to have a `webhook_secret`, or reject/quarantine events for organizations without one instead of treating them as implicitly verified.
- Consider hashing/signing the full webhook payload once per Shipit instance root secret rather than per attacker-selectable organization key, removing the attacker's ability to choose which verification branch is evaluated.

### Proof of Concept
Given a Shipit instance configured with two GitHub orgs, `weakorg` (no `webhook_secret`) and `victimorg` (secured, hosting the tracked repo `victimorg/prod-app`):

```
POST /github/webhooks
X-Github-Event: push
X-Hub-Signature: sha1=anything   (never checked, since weakorg has no secret)

{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha, e.g. a malicious/old commit>",
  "repository": {
    "owner": { "login": "weakorg" },
    "full_name": "victimorg/prod-app"
  }
}
```

`verify_signature` resolves `repository_owner` = `"weakorg"`, fetches `weakorg`'s `GitHubApp`, finds `webhook_secret` blank, and returns `true` unconditionally via `GitHubApp#verify_webhook_signature`'s `return true unless webhook_secret`. The request passes verification and is dispatched to `PushHandler`, which resolves stacks via `Repository.from_github_repo_name("victimorg/prod-app")` and calls `stack.sync_github(expected_head_sha: "<attacker-chosen sha>")` for the victim's stack — a forged push event accepted for a repository/org the attacker never authenticated against.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
