### Title
`EnvironmentVariables#permit` performs name-only allowlisting, letting a `shipit.yml`-declared `PATH` deploy variable override the safe PATH used by `Command#unbundled_env` - (File: lib/shipit/environment_variables.rb)

### Summary
`EnvironmentVariables#permit` only checks that an environment variable's *name* appears in the `deploy.variables` list declared in the repository's `shipit.yml`; it applies no blocklist against security-relevant keys such as `PATH`, `LD_PRELOAD`, or `BUNDLE_GEMFILE`. Because `Command#unbundled_env` merges the task's env (`@env`) *after* the safe, hardcoded `Shipit.shell_paths` PATH, a `shipit.yml` that declares `PATH` as a permitted deploy variable lets that value completely replace the PATH used when spawning every subsequent deploy-step process.

### Finding Description
The broken binding: `EnvironmentVariables#permit(variable_definitions)` should guarantee `env_key permitted == env_key safe-to-override`, but it actually only checks `env_key ∈ variable_definitions.map(&:name)`, with no distinction between benign application variables and process-security-relevant variables like `PATH`.

Code path:
- `DeploySpec#deploy_variables` builds `VariableDefinition` objects straight from the checked-out commit's `shipit.yml` (`config('deploy', 'variables')`), with no name restriction: [1](#0-0) .
- `DeploySpec#filter_deploy_envs` delegates directly to `EnvironmentVariables#permit`: [2](#0-1) .
- `EnvironmentVariables#sanitize_env_vars` only filters by name membership, never by key identity against dangerous names: [3](#0-2) .
- `Shipit::DeploysController#deploy_params` builds the strong-params allowlist for the web form directly from `@stack.deploy_variables.map(&:name)`, so if `shipit.yml` declares `PATH`, the form (and the API's `accepts :env, Hash` schema) will accept a `PATH` key in `deploy[env]`: [4](#0-3) , [5](#0-4) .
- `TaskCommands#env` merges the task's env (including the filtered deploy env) last, before it reaches `Command`: [6](#0-5) .
- `Command#unbundled_env` merges `@env.stringify_keys` *after* the hardcoded safe `PATH`, so an attacker-controlled `PATH` key wins: [7](#0-6) .

Attacker's PR: a `shipit.yml` containing
```yaml
deploy:
  variables:
    - name: PATH
```
(optionally with `default: "/tmp/evil:$PATH"` to avoid needing any explicit env submission on deploy). When this commit is the one checked out for the deploy (e.g., a review-stack deploying the PR branch directly, or after the config is merged to the deploy branch), `deploy_variables` will include `PATH`, so `deploy_params`/API schema will accept a `PATH` value, `filter_deploy_envs`/`permit` will pass it through untouched, and `Command#unbundled_env` will use the attacker's PATH for every subsequently spawned shell command (`git`, `bundle`, deploy step scripts, etc.), enabling arbitrary code execution via a shadowed/unqualified binary in that PATH.

None of the existing guards catch this: `ExplicitParameters`/strong params only validate variable *names* against the config, not against a security blocklist; `EnvironmentVariables#permit` explicitly only checks name membership; there is no validation anywhere in `DeploySpec`, `VariableDefinition`, or `Command` rejecting names like `PATH`, `LD_PRELOAD`, or `BUNDLE_GEMFILE`.

### Impact Explanation
If exploited, the attacker achieves RCE on the deploy host: any unqualified binary invocation during the deploy (git, bundler, custom deploy-step scripts) can be hijacked via a poisoned `PATH`, executing attacker-controlled code with the privileges of the Shipit deploy worker. This is scoped to whatever stack/repository the attacker can get the malicious `shipit.yml` deployed for (e.g., their own repo's review stack, or any repo where an attacker can get a PR merged/deployed), but the blast radius extends to the whole deploy host process, not just the target repository's checkout. This matches the Critical category ("RCE on the deploy host via Command/PTY.spawn").

### Likelihood Explanation
The core defect (name-only allowlisting with no blocklist) is unconditionally present and inexpensive for an attacker to exploit at the config level — it costs nothing more than authoring a `shipit.yml`. However, actually reaching `PTY.spawn` requires that this crafted commit's `shipit.yml` becomes the one used at deploy time and that a deploy is triggered with that env. In the most permissive configuration (review stacks that deploy the PR branch directly and/or continuous-deployment auto-triggering using `DeploySpec#default_deploy_env`, which uses the variable's declared `default` with no need for any human to type a value into the deploy form), this is entirely reachable by an unprivileged PR author with no session, token, or maintainer action. In more conservative configurations requiring a maintainer to explicitly submit `PATH` in the deploy form/API, the final trigger step needs an authenticated user with deploy permission, which somewhat reduces likelihood but does not fix the underlying bug — any deploy-privileged actor (including one relying on stack defaults) can be tricked or can inadvertently poison the environment for that stack.

### Recommendation
In `EnvironmentVariables#permit` (or `DeploySpec#deploy_variables`/`VariableDefinition`), reject variable definitions whose name matches a blocklist of security-relevant environment keys (at minimum `PATH`, `LD_PRELOAD`, `LD_LIBRARY_PATH`, `BUNDLE_GEMFILE`, `RUBYOPT`, `GEM_HOME`/`GEM_PATH`), or force `Command#unbundled_env` to merge the safe `PATH` *after* `@env` so it cannot be overridden by task/deploy env values.

### Proof of Concept
```ruby
# test/unit/environment_variables_test.rb (illustrative)
test "#permit allows overriding PATH because sanitization is name-only" do
  variable = VariableDefinition.new('name' => 'PATH')
  filtered = EnvironmentVariables.with('PATH' => '/tmp/evil').permit([variable])
  assert_equal '/tmp/evil', filtered['PATH']
end

# test/unit/command_test.rb (illustrative)
test "#unbundled_env lets task env override the safe PATH" do
  command = Command.new('true', chdir: '.', env: { 'PATH' => '/tmp/evil' })
  assert command.unbundled_env['PATH'].start_with?('/tmp/evil')
  refute command.unbundled_env['PATH'].start_with?(Shipit.shell_paths.first)
end
```
Both assertions demonstrate the broken binding: `permit` treats `PATH` as an ordinary allowlisted name, and `Command#unbundled_env` lets that value replace the intended safe PATH used for `PTY.spawn`.

    def sanitize_env_vars(variable_definitions)
      allowed_variables = variable_definitions.map(&:name)

      allowed, disallowed = @env.partition { |k, _| allowed_variables.include?(k) }.map(&:to_h)

      error_message = "Variables #{disallowed.keys.to_sentence} have not been whitelisted"
      raise NotPermitted, error_message unless disallowed.empty?

      allowed
    end
