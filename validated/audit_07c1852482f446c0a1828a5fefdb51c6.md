## Analysis

The reachable analog of the reported "broken invariant" bug class is a **binding break between the stack an API token is scoped to and the stack it can actually be used to read**, in the CCMenu status-feed feature.

### Root cause

`Api::BaseController` scopes stack lookups to the authenticated client's stack when one is set: [1](#0-0) 

But `Api::CCMenuController` overrides `stack` and bypasses that scoping entirely, resolving the target stack straight from the URL parameter regardless of which stack (if any) the authenticated `ApiClient` is bound to: [2](#0-1) 

The permission check only verifies the generic `read:stack` bit is present in `ApiClient#permissions`, not that the requested stack matches the token's `stack_id`: [3](#0-2) 

Compounding this, the token minted for the CCMenu feature is not stack-scoped at all — `ApiClient#stack` is optional and `CCMenuUrlController#client` creates/reuses a single client per user with no `stack:` attribute set: [4](#0-3) [5](#0-4) 

The route embeds an arbitrary `stack_id` segment alongside the `token` query parameter, which is exactly what `CCMenuController#stack` trusts unchecked: [6](#0-5) 

### Invariant broken

For a token `T` intended for stack `S` (whether unscoped, as CCMenu issues it, or scoped via `ApiClient.stack_id == S.id` as other flows issue it), the expected equality is:

`readable_stacks(T) = {S}`

The actual behavior is:

`readable_stacks(T) = Stack.all` (any `stack_id` param accepted by `Stack.from_param!`)

because `CCMenuController#show` never intersects the requested stack with `current_api_client.stack_id`.

### Title
Cross-stack disclosure via CCMenu API token that ignores per-stack scoping - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
The CCMenu XML status endpoint (`GET /api/stacks/*stack_id/ccmenu`) authenticates via a bearer token embedded in the URL query string, but resolves the target stack directly from the request path instead of intersecting it with the stack the authenticated `ApiClient` is actually scoped to. As a result, any leaked or intercepted CCMenu URL/token — which is explicitly designed to be handed to third-party CI dashboard software and is not tied cryptographically or logically to a single stack — can be replayed against any other stack in the Shipit instance simply by swapping the `stack_id` path segment.

### Finding Description
`Api::CCMenuController` re-defines the private `stack` helper to call `Stack.from_param!(params[:stack_id])` directly [7](#0-6) , instead of using the scoped `stacks.from_param!` helper defined in `Api::BaseController`, which restricts lookups to `Stack.where(id: current_api_client.stack_id)` when the client is stack-bound [1](#0-0) . The `require_permission :read, :stack` guard only checks that `"read:stack"` is in the token's permission list [3](#0-2) ; it never compares the token's `stack_id` to the requested stack.

Separately, the token normally minted for this feature (`CCMenuUrlController#client`) is created with no `stack` at all and is memoized per-user, not per-stack [4](#0-3) , so it is unscoped by construction. Even disregarding that, `CCMenuController`'s bypass of `stacks.from_param!` means a genuinely stack-scoped `read:stack` token (e.g. one an admin manually restricts to a single stack via the `api_clients` UI) can still be replayed against every other stack through this specific endpoint.

### Impact Explanation
Anyone who obtains a CCMenu URL — designed to be pasted into external CI-status tooling, and thus prone to leaking via proxy logs, browser history, screen shares, or misconfigured dashboards — gains unauthenticated read access to build/deploy status, lock state, and latest commit metadata for every stack managed by the Shipit instance, not just the one it was generated for. This matches the High-severity class of "unauthenticated read of stack state, task streams or deploy output."

### Likelihood Explanation
The token is intentionally distributed outside the authenticated session (embedded in a query string meant for third-party polling tools), and no additional secret or session is required — an attacker only needs a single previously issued CCMenu URL for any one stack to enumerate all stacks.

### Recommendation
Have `Api::CCMenuController#stack` use the inherited, scoped `stacks.from_param!(params[:stack_id])` instead of `Stack.from_param!`, and additionally bind the `CCMenuUrlController`-issued `ApiClient` to the specific stack (`stack:` set, not left `nil`) so the invariant "token authorizes stack S" ⇒ "token can only read stack S" holds end-to-end.

### Proof of Concept
1. User with access to Stack A visits its settings page and clicks "Fetch URL", invoking `CCMenuUrlController#fetch`, which returns `https://shipit.example.com/api/stacks/org/repo-a/production/ccmenu?token=<T>` [8](#0-7) .
2. This URL/token `T` leaks (e.g. via a CI dashboard's stored config or logs).
3. Attacker requests `https://shipit.example.com/api/stacks/org/repo-b/staging/ccmenu?token=<T>` — a completely different, otherwise-inaccessible stack.
4. `authenticate_api_client` accepts `T` [9](#0-8) , `require_permission :read, :stack` passes because `T` carries `read:stack` [3](#0-2) , and `stack` resolves repo-b directly from the URL [7](#0-6) , returning repo-b's deploy status XML to the attacker.
