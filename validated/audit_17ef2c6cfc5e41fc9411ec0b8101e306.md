### Title
Webhook signature check is keyed to `repository.owner.login` while every handler acts on `repository.full_name` - cross-organization forged push/PR events - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects which GitHub App/secret to validate an inbound webhook against using `repository_owner`, derived from the attacker-controlled JSON body (`params.dig('repository','owner','login')`). Every webhook handler, however, resolves the repository/stack it actually mutates from a *different* field of that same attacker-controlled body: `payload.dig('repository','full_name')`. Because the two lookups are independent, an attacker can pick an organization for authentication whose GitHub App is configured with no `webhook_secret` (a state explicitly shown as the example/default in this repo's own config templates) and point `full_name` at a completely different, victim organization's repository, causing the engine to accept unauthenticated pushes/PR events as if GitHub had sent them for the victim repo.

### Finding Description
`WebhooksController#verify_signature` does:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
  head(422) unless verified
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) 

`GitHubApp#verify_webhook_signature` intentionally treats an app with no configured secret as always-valid:
```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
``` [2](#0-1) 

This is not a hypothetical/misconfigured edge case: every shipped configuration template in this repo (`config/secrets.development.example.yml`, `config/secrets.development.shopify.yml`, `test/dummy/config/secrets_double_github_app.yml`) ships `webhook_secret: # nil` as the documented value, and `docs/setup.md` documents the multi-organization schema without mandating a secret per organization. [3](#0-2) [4](#0-3) 

Meanwhile, every `Handler` subclass (and `Handler` base class itself) resolves the target `Repository`/`Stack` purely from `full_name`, independent of the `owner.login` used for signature selection:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [5](#0-4) 

`PushHandler` uses this to trigger a GitHub sync for the resolved stack based on attacker-supplied `ref`/`after`:
```ruby
def process
  stacks.not_archived.where(branch:).find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
end
``` [6](#0-5) 

`Stack#sync_github` enqueues `GithubSyncJob`, which fetches commits from the real GitHub API for that stack's repository and, on new commits, feeds `CacheDeploySpecJob`, which can in turn advance continuous delivery (`trigger_continuous_delivery` / `trigger_deploy`) for that stack: [7](#0-6) [8](#0-7) [9](#0-8) 

**The binding broken:** `organization authenticated (repository.owner.login used to pick GitHub App secret) != repository actually written (repository.full_name used by every handler)`. Before the attacker's request, these two are always the same organization for a legitimate GitHub-originated webhook (GitHub always signs the payload it itself generated, where `owner.login` is a prefix of `full_name`). After the attacker's crafted POST, they can be set independently: `owner.login = OrgWithNoSecret`, `full_name = "VictimOrg/victim-repo"`.

### Impact Explanation
This allows an unauthenticated, unprivileged network attacker (no Shipit session, no `ApiClient` token, no GitHub App key, no webhook secret) to make Shipit believe a push/PR/status/check_suite event occurred on an arbitrary tracked repository belonging to any organization mounted in the same Shipit instance — as long as at least one organization in the deployment's `github:` config has no `webhook_secret` set (the documented default). This can force `GithubSyncJob` to run against a victim stack, ingest attacker-claimed commit history into it, and potentially advance continuous delivery/auto-deploy for that stack (`trigger_continuous_delivery` → `trigger_deploy`), i.e., an unauthorized deploy trigger without ever possessing the victim organization's webhook secret or any Shipit credential.

### Likelihood Explanation
Any single Shipit deployment that manages more than one GitHub organization, or that ships with the documented default (`webhook_secret: nil`) for even one organization, is exploitable by any internet attacker who can reach `/webhooks`. No credentials, sessions, or GitHub access are required — only knowledge of the target Shipit host and one repository's `owner/name` that is tracked in it, both of which are typically public information (visible in the Shipit UI).

### Recommendation
Bind the signature verification to the same field used for repository/stack resolution: derive the organization used to select the webhook secret from `repository.full_name`'s owner segment (or verify that `repository.owner.login` matches the owner segment of `full_name`) before dispatching to handlers. Additionally, reject webhooks for repositories belonging to an organization configured with no `webhook_secret`, or require `webhook_secret` to be present for every configured organization, rather than treating an absent secret as an automatic pass.

### Proof of Concept
1. Deploy Shipit with two organizations configured, per `docs/setup.md`'s "Using Multiple Github Applications" section: `OrgWithNoSecret` (webhook_secret left blank, as shown in the shipped example configs) and `VictimOrg` (properly secured, running a tracked stack).
2. As an anonymous attacker, POST directly to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "OrgWithNoSecret" },
    "full_name": "VictimOrg/victim-repo"
  }
}
```
No `X-Hub-Signature` header (or an arbitrary one) is required.
3. `verify_signature` calls `Shipit.github(organization: "OrgWithNoSecret")`, whose `verify_webhook_signature` returns `true` unconditionally because `webhook_secret` is blank.
4. `PushHandler` resolves the target repository via `payload.dig('repository','full_name') == "VictimOrg/victim-repo"`, finds the real victim `Stack`, and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")`, enqueuing `GithubSyncJob` against the victim's real GitHub repo/stack — despite the attacker never having access to `VictimOrg`'s webhook secret.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

    def perform(params)
      @stack = Stack.find(params[:stack_id])
      expected_head_sha = params[:expected_head_sha]
      retry_count = params[:retry_count] || 0
      head_before_sync = spec_cache_target
      appended_commits = []

      handle_github_errors do
        new_commits, shared_parent = fetch_missing_commits { stack.github_commits }

        # Retry on Github eventual consistency: webhook indicated new commits but we found none
        if expected_head_sha && new_commits.empty? && !commit_exists?(expected_head_sha) &&
           retry_count < MAX_RETRY_ATTEMPTS
          GithubSyncJob.set(wait: RETRY_DELAY * retry_count).perform_later(params.merge(retry_count: retry_count + 1))
          return
        end

        stack.transaction do
          shared_parent&.detach_children!
          appended_commits = new_commits.map do |gh_commit|
            append_commit(gh_commit)
          end
          stack.lock_reverted_commits! if appended_commits.any?(&:revert?)
        end
      end
      sync_changed_nothing = appended_commits.empty? &&
                             spec_cache_target == head_before_sync &&
                             stack.cached_deploy_spec.present?
      return if sync_changed_nothing && !params[:force_spec_cache]

      CacheDeploySpecJob.perform_later(stack)
    end
