## Title
Webhook signature verified against `repository.owner.login`/`organization.login` while all event handlers act on `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb])

## Summary
`WebhooksController#verify_signature` derives the GitHub App / secret to check the `X-Hub-Signature` against from `repository.owner.login` (falling back to `organization.login`), while every `Handler` subclass (`PushHandler`, pull-request handlers, etc.) determines which `Stack`/`Repository` to mutate from a completely different JSON field, `repository.full_name`. These two fields are independent, attacker-controlled strings inside the same unauthenticated JSON body and are never cross-checked against each other.

## Finding Description
`verify_signature` selects the `GithubApp`/secret using:
```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) 
and verifies `request.headers['X-Hub-Signature']` against `Shipit.github(organization: repository_owner)`'s `webhook_secret`. [2](#0-1) 

Once the signature is accepted, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` is invoked with the raw parsed payload. [3](#0-2) 

Every handler resolves the target `Stack`/`Repository` via a *different* JSON field:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [4](#0-3) 

`PushHandler`, for instance, uses this `stacks` scope directly to enqueue a `GithubSyncJob` for whichever branch/stack matches:
```ruby
def process
  stacks
    .not_archived
    .where(branch:)
    .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
end
``` [5](#0-4) 

The equality the engine implicitly relies on is:
`repository.owner.login` (used to pick the HMAC secret) == `repository.full_name`'s owner (used to select which repository is synced/mutated).

Because the webhook payload is a single flat JSON body under the attacker's full control (only the raw bytes are HMAC-signed as a whole, not any cross-field consistency), nothing prevents an attacker from setting `repository.owner.login` to an organization/app they control (so they can compute a valid signature with their own `webhook_secret`) while setting `repository.full_name` to `victim-org/victim-repo`, a repository actually tracked by a *different* Shipit-configured GitHub App/organization. `verify_signature` only checks that the request is validly signed *for the attacker's own org*; it never confirms that `repository.full_name`'s owner matches `repository_owner`.

This is a structural analog of the Goldfinch report's root cause: the code checks one field (loan/App state via `termEndTime`/`balance` or, here, `owner.login`) to decide validity, while a completely different field/consequence (Late→Expired transition, or here, which repository gets acted upon) is driven by an unrelated value that isn't re-validated against the first.

## Impact Explanation
If the target Shipit instance is configured with multiple GitHub organizations/apps (the documented `Using Multiple Github Applications` setup, see `docs/setup.md` and `test/dummy/config/secrets_double_github_app.yml`), an attacker who controls (or can install) a GitHub App on **any one** of the configured organizations — including a low-value org they fully control — can forge a validly-signed webhook whose `repository.owner.login` matches their own org (so `verify_signature` passes with their own `webhook_secret`) but whose `repository.full_name` names a **different**, victim-owned repository/stack also tracked by the same Shipit instance. This lets the attacker:
- Trigger `GithubSyncJob` for the victim stack with an attacker-chosen `expected_head_sha`, or
- Drive any other webhook-triggered handler (pull_request opened/labeled/reopened/etc., which create/provision/archive `ReviewStack`s, or attach `PullRequest` records) against the victim repository/stack, using data that GitHub itself never actually sent for that repository.

This does not directly grant `GITHUB_TOKEN` exfiltration or RCE by itself, but it breaks the authentication binding between "who is allowed to speak for this webhook" and "which repository state gets mutated," enabling cross-repository state writes/triggers on stacks the attacker does not control and was never authorized to affect. This aligns with the "High" impact bucket ("escalation into authorization" / unauthorized action against a stack the caller has no rights over) since it does not require a Shipit session, API token, or GitHub write access to the victim repo — only the ability to register/own a webhook secret for *some* org configured on the instance.

## Likelihood Explanation
Requires: (1) the target Shipit deployment to use the multi-organization GitHub App configuration (explicitly supported and documented), and (2) the attacker controlling one of those configured organizations/apps (their own webhook secret) while a victim stack from a different configured org/repo exists on the same instance. Given Shipit is often run as a shared, multi-tenant deploy hub across many orgs/repos, this is a realistic configuration. No privileged Shipit session, `ApiClient` token, or GitHub write access to the victim repository is needed — only a raw HTTP POST to `/webhooks` with a validly-signed-for-the-attacker's-org payload.

## Recommendation
Bind the two fields together at verification time: derive the "owner" used both for `webhook_secret` lookup and for repository resolution from the same value, and reject the request if `repository.full_name`'s owner does not match `repository.owner.login`/`organization.login` used for signature verification. Concretely, in `Shipit::WebhooksController#verify_signature`, after determining `repository_owner`, additionally assert that `params.dig('repository', 'full_name')&.split('/')&.first == repository_owner` (case-insensitively) before dispatching to handlers, or have `Handler#repository_name` reuse/re-derive its owner from the already-verified `repository_owner` rather than trusting `repository.full_name` independently.

## Proof of Concept
1. Configure Shipit with two GitHub organizations, e.g. `AttackerOrg` (attacker installs the App and knows its `webhook_secret`) and `VictimOrg` (hosts a tracked Shipit stack for `VictimOrg/app`).
2. Craft a JSON push payload:
```json
{
  "ref": "refs/heads/main",
  "after": "deadbeef...",
  "repository": {
    "owner": { "login": "AttackerOrg" },
    "full_name": "VictimOrg/app"
  }
}
```
3. Compute `X-Hub-Signature: sha1=<hmac(AttackerOrg_webhook_secret, raw_body)>`.
4. POST to `/webhooks` with header `X-Github-Event: push`.
5. `verify_signature` looks up `Shipit.github(organization: "AttackerOrg")` and successfully verifies the signature against the attacker's own secret — request passes.
6. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("VictimOrg/app")`, finds the real victim stack, and enqueues `GithubSyncJob` with the attacker-supplied `expected_head_sha`, even though GitHub never sent this webhook for that repository.

Note: I was unable to fully verify from the available index whether any additional consistency check exists elsewhere in the request pipeline (e.g., a before_action added downstream of `verify_signature` not surfaced by search) that might cross-validate `repository.full_name` against `repository.owner.login`; the `WebhooksController` and `Handler` base class shown above contain no such check.
