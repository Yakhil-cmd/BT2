### Title
Attacker-crafted swap route injects arbitrary token transfers into the victim's authorization tree, draining wallet funds beyond the routed amount - (contracts/controller/src/strategies/swap.rs)

### Summary
The SSTI bug class — attacker-supplied instructions interpreted in a privileged context — maps directly onto the controller's swap strategies. `swap_tokens` forwards a fully caller-controlled `swap` payload (`StrategySwap`/`swap_xdr`) to the configured router inside `execute_strategy`, after granting one exact input-transfer auth. The router treats the payload as a program: it invokes whatever pool and token addresses the payload's `assets` registry names, with no venue/pool allowlist. A "pool" in the route can therefore be attacker-deployed code that calls `token.transfer(victim, attacker, X)` on any token the victim holds. During `simulateTransaction` (recording mode) that call is attached as a child of the victim's own `swap_collateral`/`multiply`/`swap_debt`/`repay_debt_with_collateral` auth entry; if the victim signs the simulated tree, the host enforces it and the theft executes inside the same transaction that delivers a perfectly fair swap.

### Finding Description
- `swap_tokens` at `contracts/controller/src/strategies/swap.rs:34-38` authorizes exactly one `token_in.transfer(controller, router, amount_in)` and then invokes `router.execute_strategy(controller, amount_in, swap)` with an unvalidated route. The controller's post-checks (`RouterOverspend`, `NoSwapOutput`) only bound the *controller's* balances — they say nothing about what route-named code does under the *caller's* authorization.
- The router dispatches hops to pool addresses taken verbatim from the payload (`dispatch_hop` → `hop.venue`/pool index into `assets`), and per the threat model "calls the pool and token addresses its payload names and keeps no allowlist of them" (`docs/explanation/threat-model.md:154-165`). Nothing in `execute_strategy` constrains which contract sits behind a `pool` index.
- Because venue calls execute below the caller's `require_auth` scope, a rogue hop pool's `token::Client::transfer(&victim, &to, &amount)` is recorded under the victim's auth entry in simulation and is accepted at enforcement time iff the victim signs that tree. The harness test `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs` proves both halves: the stolen transfer appears inside the recorded `swap_collateral` invocation (lines 194-227), and signing the poisoned tree makes the wallet drain succeed while an honest tree makes it revert (lines 229-269).

### Impact Explanation
Theft of user funds, unbounded by the routed amount or by any slippage parameter: the rogue pool can transfer *any* token in the victim's wallet (the test drains an unrelated `wallet_token` balance of 77,770 units while the swap itself is only 5,000 USDC in / fair ETH out). The victim's position even ends healthy, so `verify_router_output` and the final risk gates pass. No privileged role, upgrade, or oracle manipulation is needed — a single unprivileged address submits a `swap_collateral`/`multiply`/`repay_debt_with_collateral`/`swap_debt` transaction whose `swap` argument names a malicious pool.

### Likelihood Explanation
Routes are built off-chain (quote server `routeXdr`) and passed as opaque XDR bytes; users sign what the simulator produces. A malicious or compromised quote source, phishing UI, or attacker-generated route embeds one extra instruction pointing at a rogue pool. The auth tree the victim signs legitimately contains nested token transfers, so the extra child entry is indistinguishable to any client that does not decode the route and diff the tree — the threat model itself notes only that "a client must decode the route it signs," which is an advisory, not a contract control. The attacker's cost is deploying one small contract; no capital at risk.

### Recommendation
Bound the code a route can reach. Options in increasing strictness: (a) maintain a router- or governance-managed allowlist of venue pool addresses and reject payloads naming others; (b) have the controller verify the decoded `StrategyPayload`'s `assets` against a registry of approved venues before authorizing the input transfer; (c) at minimum, isolate the caller's auth — execute the route under a context where route-named contracts cannot attach sub-invocations to the user's entry (e.g., the controller itself being the `sender` already prevents pool code from reaching into the user's tree, since only the controller's invoker auth is granted — verify the user's `require_auth` cannot be consumed by hop code and reject any `require_auth`/`transfer` attempts on the end-user address from venue contracts).

### Proof of Concept
Reference implementation in `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs`:
1. Attacker deploys `RogueHopPool` (lines 51-72) whose `swap()` executes `token.transfer(alice, attacker, WALLET_BALANCE)` on a token the protocol never listed.
2. Attacker builds a `swap_xdr` whose `assets` registry names that contract as the hop pool, with a fair `min_out` (lines 111-125).
3. Victim calls `swap_collateral(account_id, USDC, 50_000_000_000, ETH, route)`; simulation records the rogue `transfer` as a child of her auth entry (lines 194-227).
4. Victim signs the simulated tree; the swap delivers fair output, her position is healthy, `RouterOverspend`/`NoSwapOutput` pass — and `WALLET_BALANCE` is transferred to the attacker (asserted lines 224-226, 265-268).
