### Title
Double-invocation of the `async.each` iteratee callback in `handleSavedPrivatePayments` on a malformed private-payment payload - (File: network.js)

### Summary
In `network.js`, `handleSavedPrivatePayments()` processes unhandled private payment chains that were saved to the `unhandled_private_payments` table by a private-payment counterparty. Inside the per-row `validateAndSave` closure, a `try/catch` around `objectHash.getBase64Hash(objHeadPrivateElement.payload, true)` calls `deleteHandledPrivateChain(..., cb)` in the `catch` branch but does **not** `return` afterward, so execution falls through to `privatePayment.validateAndSavePrivatePaymentChain(...)`, which itself eventually invokes the same `cb` a second time via its `ifOk`/`ifError`/`ifWaitingForChain` handlers. This is the JS analog of the Rust "double drop"/double-free bug class described in GHSA-fjr6-hm39-4cf9: the same completion handle (`cb`, the `async.each` iteratee callback) is released/finalized twice for a single logical unit of work whenever an exception path is taken. [1](#0-0) 

### Finding Description
`handleSavedPrivatePayments` iterates unhandled private-payment rows with `async.each(rows, function(row, cb){...}, finalCb)`. For each row it builds `validateAndSave`:

```
try {
    var json_payload_hash = objectHash.getBase64Hash(objHeadPrivateElement.payload, true);
}
catch (e) {
    console.log("getBase64Hash failed for private element", objHeadPrivateElement.payload, e);
    if (ws)
        sendResult(ws, {private_payment_in_unit: row.unit, result: 'error', error: e.toString()});
    deleteHandledPrivateChain(row.unit, row.message_index, row.output_index, cb);
}
var key = 'private_payment_validated-'+objHeadPrivateElement.unit+'-'+json_payload_hash+'-'+row.output_index;
privatePayment.validateAndSavePrivatePaymentChain(arrPrivateElements, {
    ifOk: function(){ ... deleteHandledPrivateChain(row.unit, row.message_index, row.output_index, cb); ... },
    ifError: function(error){ ... deleteHandledPrivateChain(row.unit, row.message_index, row.output_index, cb); ... },
    ifWaitingForChain: function(){ ... cb(); }
});
``` [2](#0-1) 

`getBase64Hash` calls `getJsonSourceString`/`getSourceString` on the attacker-controlled `payload`, which can throw for malformed/unsupported payload shapes (e.g., cyclic structures, unsupported types, or values the hashing string-builder rejects). `payload` originates from `arrPrivateElements` stored verbatim as JSON that was previously received from a private-payment counterparty and persisted to `unhandled_private_payments`. [3](#0-2) 

When `getBase64Hash` throws, the `catch` block calls `deleteHandledPrivateChain(row.unit, row.message_index, row.output_index, cb)` (which itself asynchronously calls `cb()` after a DB delete), but there is no `return`, so control continues past the `catch` and calls `privatePayment.validateAndSavePrivatePaymentChain`, which will independently reach one of `ifOk`/`ifError`/`ifWaitingForChain` and call `cb` (directly, or through another `deleteHandledPrivateChain`) a second time — with `json_payload_hash` left `undefined` because the assignment never completed. This double-invocation of the `async.each` iteratee callback for a single item is exactly the double-free/double-drop pattern: the same "resource handle" (the completion callback that finalizes iteration state and eventually calls `unlock()` on the `"saved_private"` mutex) is finalized twice.

### Impact Explanation
Calling an `async.each` iteratee callback twice for one item causes the internal completion counter to be decremented/considered-complete more often than the number of rows, which can cause the final callback (which calls `unlock()` on the `"saved_private"` mutex and emits `"new_my_transactions"`) to fire prematurely/twice while other rows in the same batch are still being processed. This can lead to:
- Premature `unlock()` of the `"saved_private"` mutex, allowing an overlapping call to `handleSavedPrivatePayments` to run concurrently and process the same or other `unhandled_private_payments` rows while the first pass is still mutating shared state, breaking the mutual-exclusion invariant the mutex was designed to provide.
- Re-entrant calls to `deleteHandledPrivateChain` on the same DB row after it may already be scheduled for deletion, and duplicate/overlapping calls into `privatePayment.validateAndSavePrivatePaymentChain`/`ifOk` handlers for other in-flight rows, since `assocNewUnits` and downstream event emission (`new_my_transactions`, `new_direct_private_chains`) could fire based on inconsistent completion state.
- General state corruption of private-payment processing (double handling of a private chain, double emission of "new" transaction events) which can confuse the wallet layer regarding which private payments were accepted, a functional integrity problem in private payment processing analogous to the double-free/double-drop corruption described in the advisory.

This does not directly grant unauthorized fund movement by itself, but it corrupts the concurrency invariant (single-flight mutex) that private-payment chain validation and persistence rely on, which is a node-disagreement/integrity-class issue for privately transferred asset chains.

### Likelihood Explanation
Reachable by any private-payment counterparty: they only need to send a private payment chain whose head payload causes `getBase64Hash`/`getJsonSourceString` to throw (e.g., a payload containing a value type that the source-string serializer cannot handle, or a manufactured object that trips an exception during hashing). The malformed chain is first persisted into `unhandled_private_payments` (as an "unhandled" chain awaiting later processing) and then reprocessed by `handleSavedPrivatePayments`, which is where the double-callback bug triggers. No special privileges are needed beyond being a paired/private-payment counterparty able to send a private chain message.

### Recommendation
Add a `return` immediately after `deleteHandledPrivateChain(...)` inside the `catch` block (and after `sendResult` if that's the intended terminal behavior) so that a hashing failure aborts `validateAndSave` before reaching `privatePayment.validateAndSavePrivatePaymentChain`, guaranteeing `cb` is invoked exactly once per row. Additionally, consider wrapping the `async.each` iteratee callback with an "already-called" guard (similar to `async`'s internal `onlyOnce`) to defensively prevent any future double-invocation from corrupting the mutex/completion state.

### Proof of Concept
1. As a paired device / private-payment counterparty, send a private payment chain whose head element's `payload` is crafted so that `getSourceString`/`getJsonSourceString` throws when hashing (e.g., includes a value type unsupported by the source-string builder).
2. The chain gets stored into `unhandled_private_payments` via the normal private-payment receipt path.
3. `handleSavedPrivatePayments` is invoked (on `unit`-specific trigger or periodic full scan), reaches `validateAndSave`, `getBase64Hash` throws, `catch` calls `deleteHandledPrivateChain(..., cb)` (schedules first `cb()` call), then control falls through and calls `privatePayment.validateAndSavePrivatePaymentChain`, which asynchronously resolves to `ifError`/`ifOk`/`ifWaitingForChain` and calls `cb` a second time.
4. Both `cb()` invocations race with `async.each`'s completion bookkeeping, causing the final callback (`unlock()` for `"saved_private"`) to be invoked out of sync with the number of pending rows, breaking the intended single-flight guarantee for concurrent `handleSavedPrivatePayments` invocations. [4](#0-3)

```javascript
function getBase64Hash(obj, bJsonBased) {
	var sourceString = bJsonBased ? getJsonSourceString(obj) : getSourceString(obj)
	return crypto.createHash("sha256").update(sourceString, "utf8").digest("base64");
}
