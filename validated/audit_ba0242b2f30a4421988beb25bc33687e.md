### Title
Cross-repository commit status forgery via unscoped `Commit.where(sha:)` lookup in `StatusHandler` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` looks up commits to attach a GitHub status to purely by `sha`, with no scoping to the repository named in the webhook payload, unlike `PushHandler` which correctly scopes through `stacks` derived from `repository.full_name`. Any actor able to trigger a validly-signed `status` webhook for a repository containing a commit whose sha is shared with a victim stack's commit (e.g. via shared git history/fork network, or a genuine sha collision) can write a `Status` row onto the victim's commit, changing its CI state as seen by `Commit#blocking?`/`Commit#blocked?`.

### Finding Description
The claimed binding is:
`commit.stack_id (of the commit a Status is attached to) == Repository.from_github_repo_name(payload.repository.full_name).stack_id`

Tracing the code shows this binding is **not enforced**:

- `app/models/shipit/webhooks/handlers/status_handler.rb`:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
This queries the global `commits` table by `sha` only. It never consults `payload.dig('repository', 'full_name')` or the `stacks` helper (`Handler#stacks`, `app/models/shipit/webhooks/handlers/handler.rb:32-38`) that `PushHandler` uses (`app/models/shipit/webhooks/handlers/push_handler.rb:13-16`, scoped via `stacks.not_archived.where(branch:)`).

- `Commit#create_status_from_github!` (`app/models/shipit/commit.rb:165-169`) then calls `statuses.replicate_from_github!(stack_id, github_status)`, using **the found commit's own `stack_id`**, not any stack derived from the payload's repository. So whichever commit row matches the sha — regardless of which repository/stack it actually belongs to — gets a new `Status` under its own stack.

- `WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-30`) only validates the HMAC signature against `Shipit.github(organization: repository_owner)`; it does not check that the `sha` in the payload actually corresponds to a commit in that repository's history. A GitHub App's webhook secret is shared across all its installations, so a webhook fired from any repository/organization where the app is installed (including one the attacker fully owns) produces a validly-signed payload.

Exploit flow:
1. Attacker owns a public repo with the Shipit GitHub App installed (or otherwise able to trigger a `status` event that GitHub signs).
2. Attacker arranges for a commit in their own repo to have the same sha as a victim stack's intermediate "blocking predecessor" commit (realistic via forked/shared git history rather than requiring a SHA-1 break) and pushes/forces a `status` event with `context` set to the victim's blocking context and `state: "success"`.
3. GitHub signs and delivers the webhook; `verify_signature` passes (org/app-level secret only).
4. `StatusHandler#process` finds the victim's `Commit` row by sha (ignoring the attacker's own repository) and calls `create_status_from_github!`, inserting a `Status(success)` under the **victim's** `stack_id`.
5. `Commit#blocking?` (delegated to `status`, `app/models/shipit/commit.rb:219`) now reports non-blocking for that predecessor.
6. `Commit#blocked?` (`app/models/shipit/commit.rb:231-237`) recomputes `stack.commits.reachable.newer_than(last_deployed_commit).older_than(self).any?(&:blocking?)` to `false` for a later, untouched commit.
7. `Commit#deployable?` (`app/models/shipit/commit.rb:227-229`) flips to `true`, unblocking a deploy the victim never actually authorized via CI.

None of the existing guards prevent this: `verify_signature` checks only the HMAC over the raw body against the org's app secret, not sha-to-repository ownership; `drop_unhandled_event`/`ExplicitParameters` only validate presence/type of `sha`, `state`, `context`, not repository binding; there is no `Repository`/`Stack` scoping check in `StatusHandler` at all.

### Impact Explanation
This allows a payload nominally about one repository (the attacker's) to mutate state (a `Status` record, and consequently blocking/deployability computation) belonging to a different repository's `Stack`/`Commit` that the attacker does not control. This directly matches the Critical category "a payload for one repository mutating another's stack, commit, task or team" and can result in an unauthorized deploy proceeding because a blocking CI failure was suppressed on an intermediate commit. It is repeatable against any victim stack whose blocking-predecessor commit sha becomes known/shared, and the effect (an extra `Status` row + recomputed `blocked?`) is deterministic per matching sha.

### Likelihood Explanation
Preconditions: the victim stack must have `ci.blocking` configured and have an intermediate commit currently in a blocking state (per the question's scoping); the attacker needs a repository where a GitHub `status` webhook they trigger will be validly signed (their own repo/org with the app installed) and a commit sha that also exists in the victim's commit table (e.g., via a shared fork ancestry, common in open-source workflows, rather than a brute-force SHA-1 collision). Given those, attacker cost is a single webhook (or a genuine GitHub status update on their own repo containing the shared commit) — no Shipit credentials, sessions, or GitHub secrets are needed beyond what any repository owner already has.

### Recommendation
Scope the commit lookup in `StatusHandler#process` to the stacks associated with the payload's repository, mirroring `PushHandler`:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
end
```
This ensures a status can only be attached to a commit that actually belongs to the repository named (and authenticated) in that same webhook payload.

### Proof of Concept
In `test/models/commits_test.rb` style (using the `soc_second`/`soc_third` cross-org fixture pattern already present):
1. Set up a victim stack chain: `soc_first` (deployed), `soc_second` (blocking, currently `pending`/`failure`), `soc_third` (later commit).
2. Assert baseline: `soc_third.blocked?` is `true` and `soc_third.deployable?` is `false`.
3. Simulate the cross-repo forged webhook by calling `Shipit::Webhooks::Handlers::StatusHandler.call` (or posting to `WebhooksControllerTest#create` with `X-Github-Event: status`) with a payload whose `repository.full_name` is an *unrelated* repository/org but whose `sha` equals `soc_second.sha`, `context` equals the victim's blocking context, and `state: "success"`.
4. Assert `soc_second.reload.blocking?` becomes `false`.
5. Assert `soc_third.reload.blocked?` becomes `false` and `soc_third.deployable?` becomes `true` — demonstrating the binding `commit.stack_id == Repository.from_github_repo_name(payload.repository.full_name).stack_id` does not hold, and downstream deployability was flipped without any authenticated action on the victim's own repository.
