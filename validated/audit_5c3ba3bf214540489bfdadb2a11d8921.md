## Analog Found

### Title
Webhook signature is verified against the payload's claimed organization, but `StatusHandler` writes a commit status looked up by SHA with no repository/organization scoping - allowing cross-repository status writes - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App/webhook secret to check the HMAC signature using the `repository.owner.login` (or `organization.login`) field extracted from the JSON payload, then hands the *entire* parsed payload off to the event handler. For the `status` event, `Shipit::Webhooks::Handlers::StatusHandler#process` looks up the target `Commit` purely by `sha`, without any check that the commit belongs to a repository owned by the organization whose secret authenticated the request. This is exactly the "organization that authenticated versus the repository that is written" binding break called out in scope: the signature binds trust to `payload['repository']['owner']['login']`, but the actual write (`commit.create_status_from_github!`) is scoped only by `payload['sha']`, a field with no cryptographic or logical tie back to the authenticating organization.

### Finding Description
`verify_signature` resolves the app via the organization named in the payload and authenticates the HMAC against that org's `webhook_secret`: [1](#0-0) [2](#0-1) 

That verified payload is then dispatched, unmodified, to any handler registered for the event: [3](#0-2) 

The base `Handler` class does scope some helper lookups by `repository.full_name` (`stacks`), but `StatusHandler` does not use that helper at all - it queries `Commit` globally by SHA: [4](#0-3) 

Compare this with the base class's `repository_name`/`stacks` helper, which *does* scope lookups to the repository named in the payload: [5](#0-4) 

`StatusHandler` never calls this scoping helper, so `Commit.where(sha: params.sha)` can match a commit belonging to **any** stack/repository in the Shipit instance, regardless of which organization's secret signed the request.

The equality that should hold but is broken:
`organization authenticated by verify_signature (payload['repository']['owner']['login']) == organization owning the repository/commit actually written by the handler (Commit#stack#repository#owner)`

Before the "attack" (legitimate use), these two are always equal because GitHub itself generates both the signature and the payload consistently. After the attacker's request, they can diverge: an attacker who administers their **own** GitHub App/organization (`OrgA`) that has been legitimately onboarded to this shared, multi-tenant Shipit instance (see `secrets_double_github_app.yml`, which supports multiple orgs each with their own `app_id`/`webhook_secret`) can compute a valid HMAC for `OrgA`'s secret over a payload whose `sha` field names a commit that actually belongs to a stack of a different onboarded repository/organization (`OrgB`). `verify_signature` passes (it only checks the org named in the payload matches the HMAC), and `StatusHandler` blindly updates the status of `OrgB`'s commit.

### Impact Explanation
This is a genuine cross-repository write: an entity authenticated only for `OrgA`'s webhook can inject arbitrary CI status values (`state`, `context`, `description`, `target_url`) onto commits belonging to unrelated repositories/stacks it has no authorization over, as long as it knows (or can force via a duplicate-content commit) the target commit's SHA - which is public, non-secret information (visible in PR pages, commit URLs, `git log`, etc.). Shipit's deploy gating is driven by aggregated commit statuses (`ci.require`, `deployable_status`, documented in the README), and `ContinuousDeliveryJob` triggers a deploy once a stack has a deployable commit: [6](#0-5) 

By forging a "success" status for a required CI context on a commit belonging to a stack with `continuous_deployment` enabled, an attacker who only controls a different, unrelated organization's webhook credentials can move that unrelated stack's commit into a deployable state and cause an unauthorized deploy - satisfying the "cross-repository writes" / "unauthorized deploy" Critical impact criteria.

### Likelihood Explanation
Requires that the Shipit instance is configured for more than one GitHub organization (a documented, supported configuration - see `test/dummy/config/secrets_double_github_app.yml`), and that the attacker controls (or is an admin of) a legitimately onboarded org/app on that shared instance. Given that, forging the request is trivial: compute HMAC-SHA1 with the known secret over an arbitrary JSON body, no other privilege is required, and the only "guessed" input is a public commit SHA.

### Recommendation
Scope every webhook handler's data lookups (not just `PushHandler`/`Handler#stacks`) to the repository named in the same payload whose organization was used for signature verification, and reject payloads where `repository.owner.login` doesn't match `repository.full_name`'s owner segment. For `StatusHandler` specifically, restrict the `Commit` lookup to commits belonging to stacks/repositories owned by the verified organization, e.g. `Commit.joins(stack: :repository).where(sha: params.sha, shipit_repositories: { owner: repository_owner })`, and apply the same organization-scoping check generically in `WebhooksController` or `Handler` before dispatching to any handler.

### Proof of Concept
1. Shipit instance is configured with two organizations, `OrgA` (attacker-controlled GitHub App, secret `S_A`) and `OrgB` (victim, secret `S_B`), as supported by `test/dummy/config/secrets_double_github_app.yml`.
2. Attacker learns the SHA of a commit belonging to a stack under `OrgB` with `continuous_deployment: true` and a `ci.require` context, e.g. by viewing the public PR/commit page.
3. Attacker crafts a `status` event payload:
```json
{
  "sha": "<OrgB commit sha>",
  "state": "success",
  "context": "<required ci context>",
  "repository": { "owner": { "login": "OrgA" } }
}
```
4. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(S_A, body)>` and POSTs to `/github/webhooks` with `X-Github-Event: status`.
5. `WebhooksController#verify_signature` resolves `Shipit.github(organization: "OrgA")` and verifies successfully (signature matches `S_A`). [1](#0-0) 
6. `StatusHandler#process` runs `Commit.where(sha: params.sha)` with no organization/repository check and writes a fabricated "success" status onto `OrgB`'s commit. [4](#0-3) 
7. If this satisfies `OrgB`'s stack's deploy-gating CI requirements, `ContinuousDeliveryJob` deploys `OrgB`'s stack, even though the request was only authenticated for `OrgA`.
