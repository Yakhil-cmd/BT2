### Title
Cross-network replay of signed packages via `is_valid_signed_package`/`validateSignedMessage` due to optional, unbound `version`/network identifier - (File: `signed_message.js`, `object_hash.js`, `formula/evaluation.js`)

### Summary
`signed_message.js`'s `validateSignedMessage()` and the underlying hash-to-sign helper `getSignedPackageHashToSign()` in `object_hash.js` do not require or bind an explicit network/chain identifier (the `alt` value that ordinary units are bound to) into every signed package. The `version` field, which is the only thing that differentiates a mainnet signature from a testnet/devnet signature, is optional in the signed-message schema, so a signed package that omits it is neither rejected nor bound to a specific network by its hash.

### Finding Description
For ordinary DAG units, ocore ties every signature to a specific network by including `alt` (and network-specific `version` strings, e.g. `'4.0'` vs `'4.0t'` vs `'4.0dev'`) inside the hashed/signed structure (`getStrippedUnit`, `object_hash.js:67-87`) and by rejecting units whose `alt` does not match the local network (`validation.js:277-278`: `if (objUnit.alt !== constants.alt) return callbacks.ifUnitError("wrong alt");`).

However, "signed messages" (used for AA-reachable `is_valid_signed_package`, prosaic-contract responses, and device/wallet signing flows) use a different, weaker schema:
- `getSignedPackageHashToSign()` (`object_hash.js:97-103`) hashes whatever fields are present in the signed package (`signed_message`, `authors`, optionally `last_ball_unit`/`version`). It never includes `alt`, and `version` is only used to pick the JSON vs legacy source-string serializer — it is not an independently-enforced network tag.
- `validateSignedMessage()` (`signed_message.js:132,136`) explicitly allows `version` to be absent: `hasFieldsExcept(objSignedMessage, ["signed_message", "authors", "last_ball_unit", "timestamp", "version"])` and `if ("version" in objSignedMessage && constants.supported_versions.indexOf(objSignedMessage.version) === -1) return handleResult(...)`. When `version` is not present at all, there is no check tying the package to `constants.supported_versions` of the validating network at all.
- Addresses are network-independent: `getChash160()` (`object_hash.js:10-13`) hashes only the definition array, with no `alt`/network component, so the exact same address/definition (and hence the exact same private key) is valid on mainnet, testnet, and devnet.

Consequently, if a `signed_message` package is produced without a `version` field (or with a `version` string shared across networks), its hash-to-sign and validation are network-agnostic: a signature collected for use on one ocore network (e.g., a testnet AA that calls `is_valid_signed_package`) can be replayed verbatim by anyone against an AA with the identical `oscript` logic deployed on mainnet (or vice versa) for the same address, since:
1. The address is the same on both networks (`getChash160` is network-independent).
2. `validateSignedMessage` performs full authentifier verification (`Definition.validateAuthentifiers`, `definition.js:734-753`) purely against `objectHash.getSignedPackageHashToSign(objSignedMessage)`, which does not encode `alt`.
3. `is_valid_signed_package` in `formula/evaluation.js:1653-1702` only additionally checks `version` format/range and that `last_ball_unit` (if present) is stable — it does not check that the package's `version`/`alt` matches the executing network's `constants.alt`.

This is directly analogous to the reported "missing chainId" cross-chain replay bug class: ocore's per-network identifier (`alt`) is the equivalent of an EVM `chainId`, and it is omitted from the object that gets signed and independently verified in `signed_message.js`/`is_valid_signed_package`, unlike ordinary units where `alt` is mandatory and checked.

### Impact Explanation
An unprivileged AA trigger sender who intercepts (or is given) a `signed_message`/`signed_package` intended for use on one network can replay it as trigger data against any AA on another ocore-compatible network (mainnet/testnet/devnet, or any future fork sharing the same `oscript` grammar) that uses `is_valid_signed_package` to authorize an action (e.g., an order in an order-book exchange AA, a payment-channel state update, or any off-chain-signed authorization). Because AA logic frequently uses `is_valid_signed_package` results to move state variables representing balances/authorizations (see `test/samples/order_book_exchange.oscript:47-49`, `test/samples/payment_channels.oscript`), a successfully replayed signature can let an attacker execute the same authorized action a second time on a different network where the same address/keys exist, causing AA fund loss/double-authorization on the second network. This satisfies "AA fund loss" impact criteria.

### Likelihood Explanation
Exploitation requires that (a) the same private key/address is used to sign packages intended for a specific network's AA, and (b) that package omits `version` (or a network-agnostic version value is reused) — this is plausible because `version` is optional per the schema and many hand-crafted or third-party-wallet-produced `signed_message` objects (not going through the canonical `signMessage()` helper, which always sets `version: constants.version`) could omit it. Given ocore explicitly supports multiple parallel networks (mainnet/testnet/devnet) sharing identical AA/oscript semantics and addresses, and users/developers commonly reuse the same seed across mainnet/testnet, the likelihood of an attacker being able to source a replayable signed package for a live AA is realistic, though it is somewhat mitigated in practice by convention (the canonical `signMessage()` helper does set `version`).

### Recommendation
Bind every signed package to the local network the same way ordinary units are bound: include `alt` (and, ideally, `version`) in `getSignedPackageHashToSign()`'s hashed payload rather than only using `version` for serializer selection, make `version`/`alt` mandatory (not optional) fields of a `signed_message`/`signed_package`, and have `validateSignedMessage()`/`is_valid_signed_package` reject any package whose `alt` does not equal `constants.alt` of the executing node, mirroring `validation.js:277-278`'s unit-level check.

### Proof of Concept
1. On network A (e.g., testnet, `constants.alt = '2'`), a user signs a package without an explicit `version` field for address `ADDR` (definition `["sig", {pubkey: PUB}]`):
   ```js
   var pkg = { signed_message: "authorize:100", authors: [{ address: ADDR, definition: ["sig",{pubkey:PUB}], authentifiers: { r: SIG } }] };
   var hash = objectHash.getSignedPackageHashToSign(pkg); // no alt/version bound in
   ```
2. An attacker captures `pkg` (e.g., from a dApp request, a public trigger unit, or off-chain channel) and submits the identical JSON as `trigger.data.signed_package` to an AA deployed with the same `oscript` on network B (e.g., mainnet, `constants.alt = '1'`), which contains `is_valid_signed_package(trigger.data.signed_package, ADDR)`.
3. `formula/evaluation.js:1653-1702` and `signed_message.js:117-303` validate the package purely by recomputing `getSignedPackageHashToSign(pkg)` and verifying the ECDSA signature against `ADDR`'s definition — since `ADDR` is identical on both networks and the hash contains no `alt`, the check returns `true` on network B even though the signature was never intended for network B, letting the attacker replay the authorized action there. function getSignedPackageHashToSign(signedPackage) {
	var unsignedPackage = _.cloneDeep(signedPackage);
	for (var i=0; i<unsignedPackage.authors.length; i++)
		delete unsignedPackage.authors[i].authentifiers;
	var sourceString = (typeof signedPackage.version === 'undefined' || signedPackage.version === constants.versionWithoutTimestamp) ? getSourceString(unsignedPackage) : getJsonSourceString(unsignedPackage);
	return crypto.createHash("sha256").update(sourceString, "utf8").digest();
}
