### Title
Cross-repository commit status forgery via unscoped `Commit.where(sha:)` lookup - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` resolves the target `Commit` records purely by bare SHA, with no scoping to the repository that authenticated the webhook, whereas the base `Handler` class already provides a `stacks`/`repository_name`-scoped lookup pattern that this handler bypasses entirely. Because GitHub SHA-1 values are content-addressed and not guaranteed unique to a single logical repository in Shipit's database (shared history from forks, common ancestors across branches/stacks, or independently identical commits), any attacker who can get GitHub to sign a genuine `status` webhook for *their own* repository can flip the status of a same-SHA commit belonging to a completely different, unrelated stack.

### Finding Description
The invariant that should hold is: `status.repository == commit.stack.repository` for every write performed by `StatusHandler#process`. In the current code that binding is never checked.

```ruby
# app/models/shipit/webhooks/handlers/status_handler.rb
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [1](#0-0) 

`Commit.where(sha: params.sha)` queries the entire `commits` table with no `stack_id`/repository filter, even though the base `Handler` class exposes exactly the scoping primitive that should have been used (`stacks`/`repository_name`, derived from `payload.dig('repository', 'full_name')`): [2](#0-1) 

`WebhooksController#verify_signature` only authenticates that the sender is a legitimate GitHub App installation for the `repository_owner`/organization named in the payload — it says nothing about which `sha` values that organization is entitled to reference: [3](#0-2) 

Exploit flow: an attacker who owns/controls any GitHub repository wired into this Shipit instance (or any org Shipit has installed the GitHub App for) can set a commit status via the normal GitHub API (`POST /repos/:owner/:repo/statuses/:sha`) on a `sha` value that also happens to identify a `Commit` row belonging to a victim's stack (e.g. shared ancestor commits between a fork and upstream, multiple stacks/branches tracking the same underlying repo history, or an independently reproduced identical commit object). GitHub signs and delivers this webhook exactly as it would any other legitimate status event for the attacker's own repository, so `verify_signature` passes. `StatusHandler#process` then finds and mutates every `Commit` in the database with that SHA — including the victim's — via `commit.create_status_from_github!(params)`, which updates `statuses`, recomputes `status`/`deployable?`/`blocked?`, and can trigger `stack.schedule_merges` or `Hook.emit(:deployable_status, ...)`: [4](#0-3) [5](#0-4) [6](#0-5) 

No existing guard prevents this: `verify_signature` checks organization identity, not SHA ownership; `ExplicitParameters` only validates payload shape, not cross-repo scoping; there is no `stacks`/repository filter applied anywhere in `StatusHandler`.

Note: the `review_stacks_enabled` / provisioning-precedence angle referenced in the prompt is a separate, unrelated code path (`PullRequest::OpenedHandler#provision?` / `LabeledHandler`), which only governs whether ephemeral review stacks get created or archived from pull-request events. It has no interaction with `StatusHandler`, and `review_stacks_enabled` does not gate or influence commit-status processing in any way — this part of the framing does not hold up in the code.

### Impact Explanation
An attacker can write a `Status` record (state, context, description, target URL) for a `Commit` belonging to a stack/repository they never authenticated for, provided a SHA collision exists across the two repositories' commit sets. This can flip `Commit#deployable?`/`#blocked?` for a victim stack, and can trigger `stack.schedule_merges` or the `deployable_status`/`commit_status` hooks, i.e. "a payload for one repository mutating another's ... commit". This matches the Critical class ("a payload for one repository mutating another's stack, commit, task or team"). The practical blast radius depends entirely on the frequency of SHA collisions between distinct repositories tracked by the same Shipit instance, which is realistic for forks, mirrored repos, or multiple stacks/branches sharing common ancestor commits, but is not an arbitrary-SHA-forgery primitive (SHA-1 preimage attacks against an unknown target commit remain infeasible).

### Likelihood Explanation
Preconditions: (1) attacker must control a GitHub repository/org that Shipit has a valid GitHub App installation/webhook secret for (so `verify_signature` passes) — this is the normal case for any onboarded repository, not a privileged capability; (2) a commit SHA must exist in both the attacker-accessible repo and a victim stack's `commits` table, which occurs naturally through forks, shared history, or multiple stacks tracking overlapping branches of the same repository. Attacker cost is a single API call to set a commit status on their own repo; the action is repeatable at will and does not require any Shipit credentials, session, or GitHub secret.

### Recommendation
Scope `StatusHandler#process` to the repository that authenticated the webhook, mirroring the base `Handler#stacks` pattern, e.g.:
```ruby
def process
  Commit.where(sha: params.sha, stack_id: stacks.select(:id)).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
where `stacks` is derived from `payload.dig('repository', 'full_name')` as already implemented in `Handler`.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb`):
1. Create `repository_a` ("attacker/repo") and `repository_b` ("victim/repo"), each with a `Stack`.
2. Create `Commit.create!(stack: stack_b, sha: "deadbeef" * 5, ...)` for the victim stack requiring `ci/kubernetes` as a required status, initially `success?` / `deployable?` true.
3. Build a `status` webhook payload with `repository.full_name = "attacker/repo"`, `sha` equal to the same SHA as the victim commit, `context: "ci/kubernetes"`, `state: "failure"`.
4. Call `Shipit::Webhooks::Handlers::StatusHandler.call(payload)`.
5. Assert the binding: before, `commit_b.reload.deployable? == true`; after processing the attacker-repo-signed payload, `commit_b.reload.deployable? == false` (or `blocked? == true`), proving the status intended only for `attacker/repo` mutated `victim/repo`'s commit — the invariant `status.repository == commit.stack.repository` is violated.
