### Title
Permissionless `DepositDelegatorRewards` can permanently lock lamports in a vote account with no active stake - ([File: programs/vote/src/vote_state/mod.rs])

### Summary
The `deposit_delegator_rewards` instruction (SIMD-0123) lets *any* unprivileged signer push lamports into *any* vote account and simultaneously bump that account's `pending_delegator_rewards` counter. Nothing checks whether the target vote account currently has, or will ever again have, delegated stake capable of consuming that reward pool. If it doesn't, `pending_delegator_rewards` can never be reduced, and the `withdraw` instruction then permanently reserves those lamports, exactly analogous to the reported vault bug where an unvalidated per-request field let attackers inflate a global "claimable" counter beyond what could ever be satisfied, freezing legitimate withdrawals.

### Finding Description
`deposit_delegator_rewards` is reachable by any signer supplying lamports; it validates only that the sender signed the transfer, not that the vote account is capable of eventually consuming the deposit: [1](#0-0) 

The amount is unconditionally accumulated via `checked_add` with no upper bound tied to the vote account's actual delegated stake: [2](#0-1) 

`pending_delegator_rewards` is only ever reduced through `calculate_block_reward`, which returns `0` whenever `total_active_stake` for the vote account's pubkey is `0` in `reward_epoch_delegated_stakes` (e.g., the vote account has no delegated stake, or every delegated stake account has fully deactivated): [3](#0-2) 

Because block-reward distribution never fires for a zero-stake vote account, any `pending_delegator_rewards` value deposited against such an account is never drained back down. Meanwhile `withdraw` enforces that the withdrawer's authority can never take the balance below `rent_exempt_minimum + pending_delegator_rewards`, and blocks full account closure entirely while `pending_delegator_rewards > 0`: [4](#0-3) 

The combination means: an unprivileged actor can call `deposit_delegator_rewards` against a vote account that currently has (or will end up with) zero effective delegated stake, permanently reserving the deposited lamports and blocking the authorized withdrawer from closing the account, mirroring the external report's pattern of an unvalidated user-supplied parameter inflating a pool counter that downstream logic can never reconcile back to zero, causing lasting disruption of core account operations (here, `withdraw`/account close instead of `sharePrice()`).

### Impact Explanation
This produces a permanently frozen balance on the affected vote account: the authorized withdrawer can never withdraw below `rent_exempt_minimum + pending_delegator_rewards`, and can never close the account while `pending_delegator_rewards > 0`, with no code path to zero it out once the vote account's delegated stake has gone to zero. This falls squarely under "permanently frozen accounts," one of the accepted impact categories.

### Likelihood Explanation
High: `deposit_delegator_rewards` requires only that the sender signs a lamport transfer to any target vote account — no relationship to that account, no minimum stake requirement, and any deposit amount (including trivially small ones) is accepted and immediately reflected in `pending_delegator_rewards`. Any vote account that is newly created, fully deactivated, or otherwise has zero currently-delegated stake in `reward_epoch_delegated_stakes` is a valid target, and this condition is easy for an attacker to identify by observing on-chain state.

### Recommendation
Before crediting a deposit to `pending_delegator_rewards`, validate that the target vote account currently has non-zero effective delegated stake capable of eventually consuming the deposit (e.g., reject deposits when the vote account's delegated stake is zero), or provide an alternate, permissioned mechanism (e.g., only the withdraw authority, or a mechanism gated by actual accrued rewards) to reduce/reclaim `pending_delegator_rewards` when a vote account's stake later drops to zero, so that `withdraw`/account closure is never permanently blocked by unconsumable pending rewards.

### Proof of Concept
1. Create/observe a vote account `V` whose delegated stake is (or has become) `0` — e.g., a freshly created vote account with no delegators, or one where all delegated stake accounts have deactivated.
2. Any unprivileged account `A` (unrelated to `V`) calls `DepositDelegatorRewards { deposit: N }` with itself as the signing source, per `deposit_delegator_rewards` in `programs/vote/src/vote_state/mod.rs`. This succeeds because the only check is that `A` signed the transfer.
3. `V.pending_delegator_rewards` becomes `N` (via `add_pending_delegator_rewards`).
4. At every subsequent epoch boundary, `calculate_block_reward` returns `0` for `V` because `total_active_stake == 0`, so `pending_delegator_rewards` is never reduced.
5. `V`'s authorized withdrawer calls `withdraw`; per the `withdraw` logic, they can never withdraw below `rent_exempt_minimum + N`, and can never fully close the account while `N > 0` — the deposited lamports (and any lamports up to that reserve) are permanently locked.

pub fn deposit_delegator_rewards<S: std::hash::BuildHasher>(
    invoke_context: &mut InvokeContext,
    vote_account_index: IndexOfAccount,
    sender_account_index: IndexOfAccount,
    deposit: u64,
    signers: &HashSet<Pubkey, S>,
) -> Result<(), InstructionError> {
    let transaction_context = &invoke_context.transaction_context;
    let instruction_context = transaction_context.get_current_instruction_context()?;

    let vote_address = *instruction_context.get_key_of_instruction_account(vote_account_index)?;
    let source_address =
        *instruction_context.get_key_of_instruction_account(sender_account_index)?;

    // Source account must sign the transfer.
    verify_authorized_signer(&source_address, signers)?;

    // SIMD-0123 states we must validate the vote account deserializes to a v4
    // *before* attempting CPI, then update the `pending_delegator_rewards`
    // field *last*.
    // We can deserialize it, and hold onto the deserialized payload in-memory.
    // This way, we can drop the account borrow but avoid re-deserializing
    // later, since we know only lamports will change.
    let mut vote_state = {
        let vote_account =
            instruction_context.try_borrow_instruction_account(vote_account_index)?;

        // Can't use `get_vote_state_handler_checked`, since it will convert
        // the underlying vote state to v4.
        // SIMD-0123 requires an *initialized v4*.
        let versioned = VoteStateVersions::deserialize(vote_account.get_data())?;
        if let VoteStateVersions::V4(vote_state_v4) = versioned {
            Ok(VoteStateHandler::new_v4(*vote_state_v4))
        } else {
            Err(InstructionError::InvalidAccountData)
        }
    }?;

    // CPI to System: Transfer from sender to vote account.
    invoke_context.native_invoke_signed(
        system_instruction::transfer(&source_address, &vote_address, deposit),
        &[],
    )?;

    // Update `pending_delegator_rewards`.
    let transaction_context = &invoke_context.transaction_context;
    let instruction_context = transaction_context.get_current_instruction_context()?;
    let mut vote_account =
        instruction_context.try_borrow_instruction_account(vote_account_index)?;

    vote_state.add_pending_delegator_rewards(deposit)?;
    vote_state.set_vote_account_state(&mut vote_account)
}
