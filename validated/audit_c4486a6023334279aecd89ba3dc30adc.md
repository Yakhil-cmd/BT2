### Title
Stale attestations remain usable via `attestation[]` formula after address control changes (key rotation) - (File: formula/evaluation.js)

### Summary
The `attestation[...]` oscript/formula function, used by AAs to check whether an address has been attested by a given attestor (e.g., KYC/identity checks), does not exclude attestations that were issued before the target address's controlling key set changed. This mirrors the Lens bug class: a stable identifier (here, an *address*, analogous to a "handle") continues to resolve to previously-issued identity data even after the underlying "owner"/authorization behind that identifier changes, letting a new (unrelated) controller inherit the old owner's attested status.

### Finding Description
`storage.js`'s `filterAttestedAddresses`, which is used in core payment validation (`validation.js` `validatePayment`) to check `spender_attested` assets, correctly guards against this scenario by requiring that the attestation's `main_chain_index` be *after* the most recent `address_definition_changes` entry for that address: [1](#0-0) 

This ensures that if address A's signing key/definition is changed (e.g., control of the address passes to someone else), any attestation issued to the *previous* controller of A stops being honored for spending purposes.

However, the `attestation[[...]]` formula function available to AAs (evaluated in `formula/evaluation.js`) performs the same kind of "is this address attested by X" lookup but has no equivalent check against `address_definition_changes`: [2](#0-1) 

It only filters by `attestor_address`, `address`, and `main_chain_index <= mci` (i.e., "was there ever an attestation before this point"), without excluding attestations that predate a later `address_definition_changes` entry for the same address. This is the same root-cause pattern as the Lens report: a check for "does an association with this identifier exist" instead of "does the *current* owner of this identifier have this association."

An AA's oscript definition frequently gates payouts, permissions, or state transitions on `attestation[[attestors=..., address=...]]` (e.g., to confirm KYC, whitelisting, or reputation of an address). Since Obyte addresses can change their controlling definition over time via `address_definition_changes` (a normal, supported feature — see `validateDefinition`'s `has definition change`/`seen definition change` and `readDefinitionChashByAddress` in `storage.js`), an address that was attested once can later be re-keyed to a completely different owner, yet the AA's `attestation[]` check will still report it as attested, because this formula function never consults `address_definition_changes`.

### Impact Explanation
An AA that uses `attestation[[...]]` as an authorization/eligibility gate for spending assets, distributing rewards, or performing privileged operations can be tricked: an attacker who gains control of (or purchases/receives) an address that was previously attested by a trusted attestor for someone else can trigger the AA to treat them as attested, because the AA-facing formula does not invalidate attestations after a definition (key) change. This can lead to unauthorized fund release from an AA to an address that is no longer legitimately associated with the attested identity — a direct AA fund loss/theft scenario, in contrast to the correctly-guarded core payment path (`filterAttestedAddresses`) which explicitly protects `spender_attested` assets from this exact issue.

### Likelihood Explanation
The pattern is only exploitable if an AA developer relies on `attestation[[...]]` for access control tied to an address's ongoing identity (a documented, expected use case for oracles/attestors and AAs), and if an address that was attested at some point later undergoes an `address_definition_change` (also a normal feature, not requiring any privileged/hub/network action — any address owner can post a change of definition unit). Both preconditions are reachable by an ordinary unprivileged unit poster/AA author using standard oscript features, without needing any malicious peer, node, or network condition.

### Recommendation
Align `attestation[[...]]` in `formula/evaluation.js` with the protection already implemented in `storage.js`'s `filterAttestedAddresses`: when querying `attestations`/`attested_fields`, add the same `main_chain_index > IFNULL((SELECT main_chain_index FROM address_definition_changes ... WHERE address=... ORDER BY main_chain_index DESC LIMIT 1), 0)` condition (for both the "recent unstable AA units" and "stable units" branches) so that attestations issued before the most recent definition change for the target address are excluded from the result.

### Proof of Concept
1. Attestor `X` attests address `A` (controlled by Alice) as `{kyc: "passed"}` via an `attestation` message.
2. An AA is deployed whose oscript gates a payout with `attestation[[attestors=X, address=trigger.address, ifnone=false]]` (or checks a specific field), releasing funds if the triggering address is attested.
3. Alice later posts a `definition_template`/`address_definition_changes` message changing the definition (signing keys) of address `A` — for example, transferring effective control of `A` to Bob (e.g., Alice sells/hands over the wallet, or in a shared/multisig arrangement the signer set is fully replaced).
4. Bob, now controlling `A` but never attested by `X`, sends a trigger unit from `A` to the AA.
5. The AA's `attestation[[attestors=X, address=trigger.address]]` check in `formula/evaluation.js` still returns `true`/the old attested value because the query in lines 967-1004 does not check `address_definition_changes`, unlike `storage.js#L1959-1974`.
6. The AA releases funds to Bob based on Alice's stale attestation, even though Bob was never vetted by attestor `X`.

function filterAttestedAddresses(conn, objAsset, last_ball_mci, arrAddresses, handleAttestedAddresses){
	conn.query(
		"SELECT DISTINCT address FROM attestations CROSS JOIN units USING(unit) \n\
		WHERE attestor_address IN(?) AND address IN(?) AND main_chain_index<=? AND is_stable=1 AND sequence='good' \n\
			AND main_chain_index>IFNULL( \n\
				(SELECT main_chain_index FROM address_definition_changes JOIN units USING(unit) \n\
				WHERE address_definition_changes.address=attestations.address AND main_chain_index<=? AND is_stable=1 AND sequence='good' ORDER BY main_chain_index DESC LIMIT 1), \n\
			0)",
		[objAsset.arrAttestorAddresses, arrAddresses, last_ball_mci, last_ball_mci],
		function(addr_rows){
			var arrAttestedAddresses = addr_rows.map(function(addr_row){ return addr_row.address; });
			handleAttestedAddresses(arrAttestedAddresses);
		}
	);
}
