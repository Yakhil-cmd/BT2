### Title
`GitHubApp#verify_webhook_signature` returns `true` for any request when an org has no `webhook_secret` configured, allowing unsigned/unauthenticated webhooks - (File: `lib/shipit/github_app.rb`)

### Summary
`Shipit::WebhooksController#verify_signature` delegates trust entirely to `GitHubApp#verify_webhook_signature`, which short-circuits with `return true unless webhook_secret` [1](#0-0) . For any org configured without a `webhook_secret` (a documented, supported configuration, e.g. the development example config), this makes the "verified" check vacuously true for any sender, with no cryptographic binding to the org at all.

### Finding Description
The binding that should hold is: `verified == true` implies `HMAC-SHA1(webhook_secret_of(repository_owner), raw_body) == X-Hub-Signature`. Instead, when `@webhook_secret = @config[:webhook_secret].presence` is `nil` for the targeted org (`lib/shipit/github_app.rb:50`), `verify_webhook_signature` returns `true` unconditionally regardless of the signature header or payload content [2](#0-1) .

The call path is: `WebhooksController#verify_signature` resolves `github_app = Shipit.github(organization: repository_owner)` from the attacker-supplied `repository.owner.login` (or `organization.login`) field in the JSON body, then calls `github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)` and only rejects with `422` if `verified` is falsy [3](#0-2) . Since `repository_owner` is attacker-controlled and used purely to select which `GitHubApp` config to check against, an attacker who knows (from public docs) that a given tenant org has no `webhook_secret` set can send a completely unsigned POST to `/webhooks` with `X-Github-Event: membership` and that org's login, and the request passes verification.

Once verified, `create` dispatches to `Shipit::Webhooks.for_event('membership')`, i.e. `MembershipHandler#process` [4](#0-3) . The handler finds/creates a `Team` by attacker-supplied `params.team.id` (`github_id`) and adds an attacker-named `member` (created via `User.find_or_create_by_login!`) to it via `team.add_member(member)` [5](#0-4) . No other guard intervenes: `drop_unhandled_event` only checks the event has a registered handler [6](#0-5) , and there is no additional authentication on `WebhooksController` beyond `verify_signature`.

### Impact Explanation
An attacker can add an arbitrary GitHub login (their own account) as a member of any `Team` (identified by a guessed/known `github_id`) for any Shipit tenant org that lacks a `webhook_secret`, without holding any secret, session, or API token. Team membership in Shipit is used for authorization gating (`Shipit.github_teams`, `User#authorized?`), so this can escalate an unprivileged attacker into a privileged Shipit team, satisfying the "escalation into `Shipit.github_teams` authorization" High-severity category (and depending on team usage, potentially enabling deploy/merge authorization abuse, pushing it toward Critical). The attack is trivially repeatable against any org tenant in the deployment that omits `webhook_secret`.

### Likelihood Explanation
The precondition is realistic and documented: Shipit explicitly supports (and its own example config ships with) `webhook_secret: nil` [7](#0-6) , and the multi-org docs repeat the same optional field per org [8](#0-7) . No GitHub secrets, sessions, or API tokens are needed — just an HTTP POST to the public `/webhooks` endpoint with a crafted JSON body, making this a zero-cost, fully repeatable attack against any such tenant.

### Recommendation
Change `verify_webhook_signature` to fail closed rather than open when `webhook_secret` is blank — i.e., reject (return `false`) instead of `return true unless webhook_secret`, and/or enforce at app boot/config-validation time that every configured GitHub org must have a non-blank `webhook_secret` before the app accepts webhook traffic for it.

### Proof of Concept
Minitest plan (`test/controllers/webhooks_controller_test.rb` style, no live GitHub):
1. Configure a `Shipit::GitHubApp` instance for org `"nosecretorg"` with `config[:webhook_secret]` set to `nil`/blank (mirroring `secrets.development.example.yml`), and stub `Shipit.github(organization: 'nosecretorg')` to return this instance in place of the test-suite default.
2. POST to `/webhooks` with `X-Github-Event: membership`, **no `X-Hub-Signature` header set**, and JSON body:
   `{ action: 'added', team: { id: 999, name: 'Attacker Team', slug: 'attacker-team', url: 'http://example.com' }, organization: { login: 'nosecretorg' }, member: { login: 'attacker' }, repository: { owner: { login: 'nosecretorg' } } }`.
3. Assert `response.status == 200` (not `422`).
4. Assert `Shipit::Team.exists?(github_id: 999)` and that the newly created/found team now has a `member` with `login: 'attacker'` via `Membership`.
5. Contrast assertion: repeat with a normal org configured with a `webhook_secret` and no signature header — assert `response.status == 422` and no `Membership` record is created, demonstrating the binding only breaks when `webhook_secret` is blank.
