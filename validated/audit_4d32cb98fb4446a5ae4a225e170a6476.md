### Title
`data_feed[[oracles="A:B:C"]]` gives full price control to the most-recently-posting oracle instead of any consensus — ([File: data_feeds.js])

### Summary
When an AA formula queries a data feed from multiple oracle addresses (a pattern explicitly supported via colon-separated `oracles` strings, e.g. `oracles="O1:O2:O3"`), the implementation does not compute any median/aggregate of the values reported by the different oracles. Instead, with the default `ifseveral='last'` option, it simply returns whichever oracle's post has the highest `main_chain_index`/`level` among the queried addresses. This means an attacker who compromises just **one** of the listed oracles can override the values from all other honest oracles at will, by posting a fresh value after them — achieving complete, unbounded control of the data-feed result an AA relies on, not merely a bounded skew as in the reported Apollo Oracle median issue.

### Finding Description
`readDataFeedValue()` iterates the `arrAddresses` list sequentially via `async.eachSeries`, calling `readDataFeedByAddress()` for each address against a **shared** `objResult` object: [1](#0-0) 

Inside `readDataFeedByAddress()`, the update condition for `ifseveral === 'last'` is purely "does this address have a higher `mci` (or `level`) than what's currently stored" — there is no cross-checking of value agreement among oracles, no averaging, no median: [2](#0-1) 

The same "last wins" logic is used for reading unstable AA-authored data feeds: [3](#0-2) 

This code path is invoked directly from oscript's `data_feed[[...]]` operator used inside AA formulas, which is exactly the mechanism AA authors use to read external price data: [4](#0-3) [5](#0-4) 

The only alternative is `ifseveral='abort'`, which aborts if two *different* oracles both have a candidate value in the queried window — but this is not the default, and even when used, it does not compute a robust median; it merely refuses to answer if a conflict happens to be detected in the same query window. The default and most commonly documented pattern (see `oracles=input[[asset=base]].address` / `oracles="A:"||this_address` patterns in `test/formula.test.js`) results in "most recent post wins," not "median of all posts" or "majority of posts."

### Impact Explanation
AA authors who list multiple oracle addresses in `data_feed[[...]]` (a pattern intended to spread trust across several data providers, e.g., for redundancy against a single compromised operator) get no actual security benefit from doing so. A single malicious or compromised oracle among the list can set the AA's read price to **any** value it chooses (not just a value bounded between honest oracles' quotes, as in the ToB Apollo report) simply by posting last. Since AAs commonly use `data_feed` results directly in payment/exchange-rate calculations (see `test/samples/futures_contract.oscript` where `$exchange_rate = data_feed[[...]]` feeds directly into payout amounts), this allows an attacker controlling one oracle in a multi-oracle list to manipulate exchange rates used by the AA and extract funds — a direct AA fund-loss vector.

### Likelihood Explanation
Exploitation only requires control of a single address that is included in the `oracles` list consulted by a target AA, and the ability to post a `data_feed` message with a favorable value after the legitimate oracles have posted (or with a later `mci`/`level`). No special privileges beyond posting units as an ordinary address are needed, and the default `ifseveral` behavior (`'last'`) is what most AA developers will end up using unless they are specifically aware of this ordering nuance and choose `'abort'` (which itself doesn't fix the underlying trust-model gap, it just refuses to answer in ambiguous cases).

### Recommendation
Document and/or change the semantics of multi-oracle `data_feed` queries so that listing several oracle addresses provides an actual security guarantee: e.g., require agreement/majority/median across the listed oracles' most recent values rather than "highest mci/level wins," or make `ifseveral='abort'`-like conflict detection the default so silent single-oracle overrides cannot happen unnoticed. At minimum, clearly document that colon-joined oracle lists do not provide consensus/robustness against a single compromised oracle, and encourage AA authors relying on price feeds to build their own median/quorum logic in the formula itself using `ifseveral='abort'` plus explicit per-oracle reads.

### Proof of Concept
1. AA formula: `$rate = data_feed[[oracles="O1:O2:O3", feed_name="GBYTE_USD", ifseveral="last"]];` where O1, O2, O3 are three independent oracle addresses intended to provide redundancy.
2. O1 and O2 (honest) post `GBYTE_USD = 50` at MCI 1000.
3. Attacker controls O3; after O1/O2 post, attacker has O3 post `GBYTE_USD = 5000` at MCI 1001 (a later main chain index / level).
4. Any subsequent AA trigger that reads this data feed via `readDataFeedByAddress` picks O3's value because it has the higher `mci`, per the `objResult.value === undefined || ifseveral === 'last' && mci > objResult.mci` condition at `data_feeds.js:318`.
5. The AA computes payouts/exchange amounts using the manipulated rate (`5000` instead of `50`), letting the attacker drain funds through favorable trades, exactly analogous to the Apollo Oracle exploit scenario but with unbounded (not just bounded) control. [2](#0-1)
