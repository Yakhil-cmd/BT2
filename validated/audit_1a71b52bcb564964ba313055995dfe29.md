### Title
Cross-tenant webhook confusion allows creating a `ReviewStack` on a victim org's repository using a signature validated against an unrelated (or unsecured) org - (`app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/secret to validate the HMAC signature against using `params.dig('repository','owner','login')`, but `OpenedHandler#repository` (and `ReviewStackAdapter`) resolve the *actual* repository/tenant to act on using the independent `params.repository.full_name` field. Because these two fields are never checked for equality, and because `GitHubApp#verify_webhook_signature` returns `true` unconditionally when an org's `webhook_secret` is blank, a request can be "authenticated" for one org while mutating another org's `ReviewStack`.

### Finding Description
The broken binding is: `signing_org (= params.repository.owner.login used in Shipit.github(organization: repository_owner))` **should equal** `acted_upon_repo_owner (= params.repository.full_name.split('/').first used by Repository.from_github_repo_name)`, but the code never enforces this.

Path:
1. `WebhooksController#verify_signature` computes `repository_owner = params.dig('repository','owner','login')` [1](#0-0) , then calls `Shipit.github(organization: repository_owner).verify_webhook_signature(signature, raw_post)` [2](#0-1) .
2. `GitHubApp#verify_webhook_signature` returns `true` unconditionally when `webhook_secret` is blank for that org's config [3](#0-2) . Multi-org example configs in the repo explicitly ship with `webhook_secret: # nil` per-org [4](#0-3) .
3. Once signature verification passes, `Shipit::Webhooks.for_event(event)` dispatches the **raw, attacker-controlled JSON** to `OpenedHandler#process` [5](#0-4) .
4. `OpenedHandler#repository` resolves the tenant to act on strictly from `params.repository.full_name`, completely independent of `repository.owner.login` used in step 1: `Shipit::Repository.from_github_repo_name(params.repository.full_name)` [6](#0-5) .
5. If that repository has `review_stacks_enabled` and `provisioning_behavior_allow_all?`, `process` calls `ReviewStackAdapter.new(params, scope: repository.review_stacks).find_or_create!` [7](#0-6) .
6. `ReviewStackAdapter#create!` builds the new `ReviewStack` directly from attacker-supplied fields: `branch: params.pull_request.head.ref`, `environment: "pr#{params.number}"`, and attaches `params.pull_request` (including `head.sha`) to the `PullRequest` record, then enqueues it for provisioning [8](#0-7) .

Attacker request: a direct `POST /webhooks` with `X-Github-Event: pull_request`, a JSON body where `repository.owner.login` = an org whose Shipit config has no `webhook_secret` set (or any org the attacker can sign for), but `repository.full_name` = `"victim-org/victim-repo"` (a real repository tracked by Shipit with `review_stacks_enabled` + `allow_all`), and `pull_request.head.sha`/`head.ref`/`labels` set to attacker-chosen values. `verify_signature` passes because it only checks the (unsecured) org named in `repository.owner.login`; the handler then provisions a `ReviewStack` for `victim-org/victim-repo` using the attacker-chosen ref/sha.

Existing guards do not close this gap: `drop_unhandled_event` only checks the event type is handled, not the payload consistency; the `ExplicitParameters` schema for `OpenedHandler` only validates presence/type of fields, not cross-field consistency between `repository.full_name` and any signer identity; there is no code path anywhere that compares the org used for signature verification against the org derived from `full_name`.

### Impact Explanation
A request "authenticated" for one namespace (an org with no configured `webhook_secret`, or any org whose secret the requester can produce) results in record creation (`ReviewStack`, `PullRequest`) scoped to a *different* organization's repository, which will subsequently be built/deployed using that victim repository's real GitHub credentials against an attacker-named ref/sha. This matches the "payload for one repository mutating another's stack" Critical category. Blast radius: any repository configured with `review_stacks_enabled` + `allow_all` (or satisfying `allow_with_label`/`prevent_with_label` provisioning rules via attacker-controlled `labels`) is exploitable, repeatably, from any request that passes `verify_signature` for some org.

### Likelihood Explanation
Requires a multi-org Shipit deployment where at least one configured org lacks a `webhook_secret` (shown as the shipped default in example/test configs), which is a plausible real-world misconfiguration, or requires the attacker to possess a valid secret for any one configured org. Given that, the attacker cost is a single crafted HTTP POST with no session, token, or GitHub involvement, and it's fully repeatable against any victim repository name known to the attacker.

### Recommendation
Enforce that the organization used to select the signing secret matches the owner of `repository.full_name` before dispatching to handlers — e.g., in `WebhooksController#verify_signature`/`create`, derive the owner from `params.repository.full_name.split('/').first` and require it to equal `repository_owner` (the `owner.login` used for the signature), rejecting the request (422) on mismatch. Additionally, treat a blank `webhook_secret` as a hard misconfiguration to reject (or at minimum log/alert) rather than silently trusting all payloads in `GitHubApp#verify_webhook_signature`.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (new test)
test "pull_request opened for org with no webhook_secret can create a ReviewStack owned by a different org" do
  # Precondition: repository "victim/repo" exists with review_stacks_enabled: true,
  # provisioning_behavior: allow_all, owner: "victim"
  victim_repo = Shipit::Repository.create!(owner: "victim", name: "repo",
                                            review_stacks_enabled: true,
                                            provisioning_behavior: :allow_all)

  # Shipit multi-org config where org "attacker-org" has no webhook_secret configured
  Shipit.stubs(:github_app_config).with("attacker-org").returns({}) # webhook_secret blank

  payload = {
    action: "opened",
    number: 999,
    pull_request: {
      id: 1, number: 999, url: "http://x", title: "x", state: "open",
      additions: 1, deletions: 0,
      head: { sha: "deadbeef", ref: "attacker-ref" },
      user: { login: "attacker" },
      assignees: [], labels: []
    },
    repository: { full_name: "victim/repo", owner: { login: "attacker-org" } },
    sender: { login: "attacker" }
  }.to_json

  request.headers['X-Github-Event'] = 'pull_request'
  request.headers['X-Hub-Signature'] = 'sha1=anything' # accepted because attacker-org has no secret

  assert_difference -> { Shipit::ReviewStack.where(repository: victim_repo).count }, 1 do
    post :create, body: payload, as: :json
  end

  assert_response :ok
  stack = victim_repo.review_stacks.last
  assert_equal "attacker-ref", stack.branch
  assert_equal "deadbeef", stack.pull_request.github_pull_request["head"]["sha"]
end
```
Both sides of the equality checked: `repository_owner` used in `verify_signature` ("attacker-org") vs. the owner of `params.repository.full_name` actually mutated ("victim") — they differ, and the request still succeeds in creating the victim's `ReviewStack`, confirming the missing binding.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
