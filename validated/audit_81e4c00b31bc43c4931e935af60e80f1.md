## Analog Found [1](#0-0) 

### Title
Zero-balance "initial deposit" branch in the shipped Uniswap-like market-maker AA template lets an attacker mint LP shares against the full pool balance while ignoring outstanding shares - (File: test/samples/uniswap_like_market_maker.oscript)

### Summary
The `stNXM` bug (M-4) stems from an `update` modifier that treats a reset/zero "last known" state (`lastBalance == 0`) as proof that no prior legitimate holdings exist, and consequently attributes the *entire* current balance to a single accounting operation (charging admin fees on migrated funds that were never actually new deposits). The ocore repository ships a reference AMM-style Autonomous Agent template, `uniswap_like_market_maker.oscript`, which contains the same root-cause pattern: it uses `asset_balance == 0` (or `bytes_balance == 0`) as a proxy for "the pool has no prior investors," and on that condition mints new LP shares (`$mm_asset`) equal to the *entire current* `balance[base]`, without checking whether `var['mm_asset_outstanding']` is actually zero.

### Finding Description
In the "invest in MM" case [1](#0-0) :

```
$asset_balance = balance[$asset] - trigger.output[[asset=$asset]];
$bytes_balance = balance[base] - trigger.output[[asset=base]];
if ($asset_balance == 0 OR $bytes_balance == 0){ // initial deposit
    $issue_amount = balance[base];
    return;
}
```

`$asset_balance` (and `$bytes_balance`) reaching exactly zero is used as the sole signal that this is a fresh, un-invested pool, mirroring the `lastBalance == 0` shortcut in stNXM's `update` modifier. But `$asset_balance` can legitimately reach zero through normal AA activity — repeated `exchange bytes to asset` / `exchange asset to bytes` swap operations [2](#0-1)  use `round()` on the constant-product formula and can, at the extremes, round `$new_asset_balance` down to `0`, fully draining the asset side of the pool while `bytes_balance` remains large and `var['mm_asset_outstanding']` is still non-zero (existing investors have not divested).

If an attacker (or anyone racing to trigger the AA at that exact moment) then sends any `base` amount above the `1e5` dust threshold plus any positive `$asset` amount, they hit the "initial deposit" branch and are issued `$issue_amount = balance[base]` — the pool's *entire* current byte balance — as newly minted `$mm_asset` shares, on top of whatever `mm_asset_outstanding` already exists from earlier depositors. This is exactly the stNXM flaw restated: a balance-vs-"last known state" check that is satisfiable to zero through normal protocol operation, and which the code interprets as "nothing was here before," causing all currently held value to be unfairly reattributed to a single triggering party at the expense of prior legitimate holders.

### Impact Explanation
An attacker who triggers the buggy "initial deposit" branch while `mm_asset_outstanding` is still non-zero mints LP shares disproportionate to their actual deposit (`$issue_amount` equals the full pool `base` balance rather than a fair proportional share). They can then immediately call the "divest MM shares" case [3](#0-2)  to redeem those inflated shares for pool assets, diluting or fully draining the claims of pre-existing LP-token holders. This is a direct, concrete fund-loss/theft vector for any unprivileged AA trigger sender who interacts with an AA deployed from this template — matching the "unauthorized spending / AA fund loss" impact bar.

### Likelihood Explanation
The zero-crossing condition is reachable purely through normal, permissionless use of the AA's own advertised swap functionality (`exchange bytes to asset` / `exchange asset to bytes`), since amounts are rounded via `round()`. No privileged role or external condition is required — any address can post payment triggers to push the asset-side balance to exactly zero and then immediately post the "invest" trigger, making this reachable by a single unprivileged AA trigger sender.

### Recommendation
Do not use a balance value (which can be legitimately driven to zero through pool activity) as the "no prior investors" signal. Instead branch on the actual outstanding-shares state variable, e.g.:

```
if (!var['mm_asset_outstanding']) { // truly the first deposit
    $issue_amount = balance[base];
    return;
}
```

and bounce (reject) attempts to invest when `asset_balance == 0` or `bytes_balance == 0` but `mm_asset_outstanding != 0`, since that indicates a degenerate/drained pool state rather than a fresh one.

### Proof of Concept
1. Deploy the AA from `uniswap_like_market_maker.oscript`; investor A deposits base+asset, receiving `mm_asset_outstanding > 0` shares.
2. Attacker repeatedly triggers "exchange bytes to asset" / "exchange asset to bytes" with amounts chosen so that a `round()` computation drives `$new_asset_balance` (and hence the pool's asset balance) to exactly `0`, while `balance[base]` remains large and `mm_asset_outstanding` is still `> 0` (investor A has not divested).
3. Attacker immediately sends an "invest" trigger with `trigger.output[[asset=base]] > 1e5` and `trigger.output[[asset=$asset]] > 0`. Because `$asset_balance == 0`, the AA executes the "initial deposit" branch and issues `$issue_amount = balance[base]` (the full pool byte balance) to the attacker as `$mm_asset`, on top of investor A's still-outstanding shares.
4. Attacker calls "divest MM shares" with the newly minted `$mm_asset`, redeeming a share of the pool disproportionate to their actual contribution, diluting/robbing investor A's claim on the pool's `base` and `$asset` balances.
