### Title
CCMenu API token can read the build status of any stack, not just the one it authorizes - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::CCMenuController` overrides the base controller's `stack` lookup and, instead of scoping to the current `ApiClient`'s authorized stack, resolves the stack directly from the class, so a token that is scoped to one stack can be used to read CCTray build-status XML for any other stack in the installation.

### Finding Description
`Shipit::Api::BaseController` defines the equality that should hold for every API endpoint: the stack a token is allowed to touch must be the stack scoped by `current_api_client.stack_id`: [1](#0-0) 

`Shipit::Api::StacksController` respects this binding by calling `stacks.from_param!(params[:id])`, i.e. resolving the requested id only within the set of stacks the client is permitted to see: [2](#0-1) 

`Shipit::Api::CCMenuController`, however, overrides both `authenticate_api_client` (to accept a `params[:token]` query-string token instead of `Authorization` header) and `stack`, and the overridden `stack` method calls `Stack.from_param!(params[:stack_id])` directly on the model class, completely bypassing the `stacks` scoping helper: [3](#0-2) 

`require_permission :read, :stack` only checks that the token carries the `read:stack` permission string via `ApiClient#check_permissions!`; it never checks that `params[:stack_id]` matches `current_api_client.stack_id`: [4](#0-3) 

As a result, the equality that should hold — *stack authorized by token* == *stack touched by the request* — is broken specifically in this controller: any token with `read:stack` permission, even one created for a single stack (e.g. via `CCMenuUrlController#client`, which mints a stack-scoped `ApiClient` with only `read:stack`), can be replayed with a different `stack_id` to read another stack's data: [5](#0-4) 

### Impact Explanation
The disclosed data includes the stack's deploy/merge status, last build time, last build label (deploy id), and whether the stack is currently building — effectively deploy-state and task-stream information for stacks the token was never authorized to see: [6](#0-5) 

This is an unauthorized cross-stack read of stack/deploy state through a token that is supposed to be scoped to a single stack, matching the "stack a token authorises vs stack it touches" binding break called out in scope.

### Likelihood Explanation
Any holder of a legitimately-issued, narrowly-scoped CCMenu/API token (e.g. one created for a single low-sensitivity stack) can trivially trigger this by changing the `stack_id` path/query parameter — no additional privilege, secret, or session is required beyond the token they already legitimately hold for a different stack.

### Recommendation
Remove the `stack` override in `Shipit::Api::CCMenuController` and use the inherited, scoped `stacks.from_param!(params[:stack_id])` (or explicitly verify `current_api_client.stack_id.nil? || current_api_client.stack_id == resolved_stack.id`) so the CCMenu endpoint enforces the same per-client stack scoping as the rest of the API.

### Proof of Concept
1. Create (or obtain) a CCMenu `ApiClient` scoped to `stack_id: A` with only `read:stack` permission (e.g. via `GET /stacks/A/ccmenu.json`, which mints such a client per `CCMenuUrlController#client`).
2. Use the returned `token` to call `GET /api/ccmenu/B/cctray.xml?token=<token>` where `B` is a different stack the client was never scoped to.
3. Observe that `Shipit::Api::CCMenuController#stack` resolves `B` via `Stack.from_param!(params[:stack_id])` unrestricted by `current_api_client.stack_id`, and the response discloses `B`'s build status, activity, and last deploy id.
