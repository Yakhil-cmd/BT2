### Title
Stack-scoped API token bypasses stack authorization in CCMenu endpoint, allowing cross-stack read of deploy/build state - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
This is an analog of the reported bug class ("data acted on is not what was actually verified/bound"). Here, the binding that breaks is: *the stack an `ApiClient` token is authorized for* ≠ *the stack the CCMenu endpoint actually serves*.

### Finding Description
`Shipit::Api::BaseController` implements stack-scoping for tokens: when an `ApiClient` is created with a `stack_id` (i.e., its token is meant to be restricted to a single stack), the generic `stacks` helper enforces this by restricting the queryable set: [1](#0-0) 

Every controller that relies on `stack` inherited from `BaseController` therefore only ever resolves a stack within the set the token is scoped to (or `Stack.all` if unscoped).

`Shipit::Api::CCMenuController`, however, overrides `stack` and resolves it directly from the global `Stack` relation, bypassing the `stacks` scoping helper entirely: [2](#0-1) 

The only authorization check performed for this controller is `require_permission :read, :stack`, which merely checks that the client's `permissions` array contains `read:stack` — it never checks that the resolved `stack` matches `current_api_client.stack_id`: [3](#0-2) [4](#0-3) 

This is exactly the same class of bug as the SoroswapFactory report: a scope/authorization value ("`stack_id`", analogous to persistent storage governance) is defined and enforced in one code path (`BaseController#stacks`/`#stack`) but a different code path (`CCMenuController#stack`) silently uses the unfiltered/raw resource, defeating the intended boundary.

Stack-scoped tokens are routinely generated and distributed for exactly this endpoint: `CCMenuUrlController#client` creates an `ApiClient` scoped to a single stack with `read:stack` permission, intended to be embedded in third-party CI dashboard tools (URLs which are inherently less protected than the main Shipit UI): [5](#0-4) 

### Impact Explanation
An attacker who obtains one such stack-scoped CCMenu token (e.g. by finding it embedded in a public/semi-public CI dashboard config, log, or leaked URL, which is the whole design intention of the token — "convenient to embed") can supply an arbitrary `stack_id` param to `Api::CCMenuController#show` and read the build/deploy status (`lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, `activity`) of **any** stack in the Shipit instance, not just the one the token was scoped and issued for. This is an unauthorized cross-stack read of deploy state, matching the High-severity category "unauthenticated read of stack state, task streams, or deploy output" (the token authenticates, but authorizes only one stack — reading others is effectively an authorization bypass across the stack boundary).

### Likelihood Explanation
Likelihood is high for exploitation once a token is obtained, because:
- No code path revalidates that `stack.id == current_api_client.stack_id` for the CCMenu-specific override.
- These tokens are specifically designed to be embedded outside the main authenticated app (in CI aggregator tools), increasing exposure risk beyond a typical `ApiClient` token.
- The exploit requires only changing a URL parameter (`stack_id`), no further authentication or privilege is needed once any valid stack-scoped token is known.

### Recommendation
Make `CCMenuController#stack` use the inherited, scope-aware `stacks` helper (i.e., `stacks.from_param!(params[:stack_id])`) instead of calling `Stack.from_param!` directly, so that stack-scoped tokens cannot resolve stacks outside their authorized `stack_id`.

### Proof of Concept
1. A user creates a CCMenu integration for `stack-A` via `GET /stack-A/ccmenu_url`, which mints an `ApiClient` with `stack_id = stack-A.id` and permission `read:stack` (`app/controllers/shipit/ccmenu_url_controller.rb:15-18`), and the returned URL/token is embedded in an external CI dashboard tool.
2. An attacker who obtains this token (e.g., from the externally-facing dashboard configuration) sends: `GET /api/stacks/stack-B/ccmenu.xml?token=<stack-A's token>`.
3. `authenticate_api_client` succeeds because the token is valid (`app/controllers/shipit/api/ccmenu_controller.rb:33-36`).
4. `require_permission :read, :stack` passes because the token has `read:stack` in its permission list, regardless of which stack (`app/models/shipit/api_client.rb:38-45`).
5. `stack` resolves `stack-B` directly via `Stack.from_param!(params[:stack_id])`, bypassing the `current_api_client.stack_id` restriction that would apply in every other API controller (`app/controllers/shipit/api/ccmenu_controller.rb:29-31` vs `app/controllers/shipit/api/base_controller.rb:74-80`).
6. The attacker receives `stack-B`'s build/deploy status XML, despite having a token only authorized for `stack-A`.

require 'uri'

module Shipit
  class CCMenuUrlController < ShipitController
    def fetch
      uri = URI(api_stack_ccmenu_url(stack_id: stack.to_param))
      uri.query = { 'token' => client.authentication_token }.to_query
      render(json: { ccmenu_url: uri.to_s })
    end

    private

    def client
      @client ||= ApiClient.create_with(permissions: %w[read:stack])
                           .find_or_create_by!(creator: current_user, name: 'CCMenu Client')
    end

    def stack
      @stack ||= Stack.from_param!(params[:stack_id])
    end
  end
end
