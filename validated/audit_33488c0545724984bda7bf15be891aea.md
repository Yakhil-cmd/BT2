### Title
Accrued RAY value overflow permanently freezes a whale market — every entrypoint panics in `scaled_to_original` before the borrow-index cap engages - (File: contracts/pool/src/interest.rs)

### Summary
The Virtuoso CVE-2024-57661 class is a denial of service triggered by attacker-shaped inputs crashing an arithmetic path. The XOXNO Lending analog is the RAY-domain value ceiling in pool accrual: interest accrual converts scaled debt/supply shares to underlying RAY values with checked `i128` math, and once a market's accrued value exceeds `i128::MAX`, the accrual itself panics with `MathOverflow`. Since every pool verb (`supply`, `borrow`, `withdraw`, `repay`, `flash_loan`, `claim_revenue`, `seize_positions`, `net_settle`, `recapitalize`) calls `interest::global_sync` first — and every controller verb (`update_indexes`, `liquidate`, `clean_bad_debt`) hits the same accrual — the entire market freezes permanently: no withdrawal, no repayment, no liquidation, no rescue.

### Finding Description
In the pool, each market mutation runs `Cache::load` → `interest::global_sync` → mutate → guards → commit, per the documented flow in `contracts/pool/README.md:159-167`. Accrual unscales share totals into RAY asset values (`scaled_to_original` in `contracts/pool/src/cache/scale.rs`), which uses checked `i128`/`I256` multiply-divide that panics `MathOverflow` when the result does not fit `i128` (`common/src/math/fp_core.rs:298-303`, `common/src/math/fp.rs:12-16`).

The docs admit the ceiling exists but claim indexes are capped: "Accrued position values and market totals must independently fit the RAY domain; valid caps and bounded indexes do not guarantee that future accrual fits. Value overflow can occur before the index ceiling and block repayment/withdrawal because those operations accrue first" (`docs/reference/formulas.md:432-437`).

The harness test `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` (`tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:320-360`) proves the cliff is reachable entirely through unprivileged calls and that it is permanent:

- `supply_raw(BOB, "BIG18", 1e9 * 1e18)` and `borrow_raw(ALICE, "BIG18", 98% of it)` are ordinary `supply`/`borrow` calls with caps lifted via normal market params.
- After enough elapsed time at high utilization, `try_update_indexes_for` fails with `MATH_OVERFLOW` while `borrow_index < MAX_BORROW_INDEX_RAY` — i.e., the value multiplication overflows before the index cap can clamp growth.
- The same panic then hits `withdraw` and `repay` (`lines 355-356`), and by symmetry every other entrypoint, because all of them accrue first.

The panic is not a one-off revert of a bad call — it is state-committed-agnostic: the accrued-value overflow is a function of the stored index and totals, so it reverts identically on every subsequent transaction touching the market, forever. `recapitalize` also accrues first, so it cannot rescue the market either.

### Impact Explanation
Permanent freezing of all supplier and collateral funds in the affected market, plus protocol insolvency mechanics being unreachable: suppliers cannot withdraw, borrowers cannot repay, liquidators cannot liquidate (the controller's liquidation path accrues through `update_indexes`/pool calls), and `clean_bad_debt`/`recapitalize` hit the same panic. This maps to the accepted impact "permanent freezing of funds."

### Likelihood Explanation
Likelihood is low but nonzero and requires no privileged role: a single unprivileged address (or two accounts) needs a market near the ~170-billion-whole-token RAY ceiling (`i128::MAX / 10^(27-d)`, `docs/reference/formulas.md:429`) at sustained ~98% utilization on a steep interest-rate curve for a few years, per the harness reproduction which reaches the cliff within 40 years at 98% utilization. On markets whose real token supply is far below the ceiling this is unreachable, which caps severity at Medium; on a very large-supply asset (e.g., an 18-decimal token) the bound is economically plausible for a whale.

### Recommendation
Inside `interest::global_sync` / `scaled_to_original`, saturate rather than panic when the RAY value would exceed `i128::MAX` — e.g., clamp the accrued index to `MAX_BORROW_INDEX_RAY` before unscaling (the cap exists but engages too late), or detect the checked-mul-div failure and pin the index at the last representable value so that `repay`, `withdraw`, and `liquidate` remain executable. Alternatively, enforce a supply cap per market comfortably below the value-overflow bound at market creation in `MarketParamsRaw::verify`, so no listing can ever reach the cliff.

### Proof of Concept
The repository already contains the reproduction: `tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:316-360`. It:

1. Builds a market `BIG18` (18 decimals) with the steep `xlm_curve()`, max utilization disabled, caps lifted via `lift_caps` (normal governance-set params, no code change).
2. `t.supply_raw(BOB, "BIG18", BILLION * 10^18)` and `t.borrow_raw(ALICE, "BIG18", 98% of principal)` — plain unprivileged `supply`/`borrow`.
3. Advances time one year per loop; `try_update_indexes_for(&["BIG18"])` eventually returns `Err` with `MATH_OVERFLOW` while `borrow_index < MAX_BORROW_INDEX_RAY`.
4. `t.try_withdraw_raw(BOB, "BIG18", 1)` and `t.try_repay(ALICE, "BIG18", 1.0)` both revert with `MATH_OVERFLOW` — the market is frozen for every verb, permanently.

Attack path by a single unprivileged address: supply a very large amount of a high-decimal token, borrow ~98% of it from a second account (or via flash-assisted leverage through `multiply`), then wait. No governance action, oracle manipulation, or privileged call is required beyond ordinary market parameters that permit a large market.
