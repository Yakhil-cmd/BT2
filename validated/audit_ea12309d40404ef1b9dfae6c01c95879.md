### Title
Cross-organization signature confusion in `verify_signature` allows one organization's webhook secret to authenticate mutations against another organization's stacks - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the HMAC secret to validate the request against using `repository.owner.login` (or `organization.login`) from the payload, while `Webhooks::Handlers::Handler#stacks` (used by `PushHandler` and others) resolves the target `Repository`/`Stack` using `repository.full_name`. In Shipit's multi-tenant github config mode (`Shipit.github_organizations`, `github_app_config`), these two fields are never checked for consistency, so a payload can be signed with organization A's legitimately-owned secret while naming organization B's repository as the target.

### Finding Description
The broken binding: the organization whose secret authenticates the request (`payload.dig('repository','owner','login')` → `Shipit.github(organization: repository_owner)` → that org's `webhook_secret`) must equal the organization owning the repository actually mutated (`payload.dig('repository','full_name')` → `Repository.from_github_repo_name` → `stack.repository.owner`). These are not the same value and nothing enforces their equality.

Code path:
- `verify_signature` computes `repository_owner = params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` and calls `Shipit.github(organization: repository_owner)`, which in multi-org mode looks up `github_app_config(organization)` and builds a `GitHubApp` scoped to that org's `webhook_secret` (`app/controllers/shipit/webhooks_controller.rb:24-49`, `lib/shipit.rb:170-200`, `lib/shipit/github_app.rb:76-83`).
- Once the signature is verified against that org's secret, `create` dispatches the parsed body to handlers (`app/controllers/shipit/webhooks_controller.rb:10-15`).
- `Handler#stacks`/`#repository_name` reads `payload.dig('repository', 'full_name')` and calls `Repository.from_github_repo_name`, which just splits the string on `/` and does a DB lookup — it has no relationship to `repository.owner.login` (`app/models/shipit/webhooks/handlers/handler.rb:32-38`, `app/models/shipit/repository.rb:53-56`).
- `PushHandler#process` then calls `stack.sync_github(expected_head_sha: params.after)` on every matching stack (`app/models/shipit/webhooks/handlers/push_handler.rb:12-17`), which enqueues `GithubSyncJob`.

Exploit: An attacker who legitimately owns GitHub organization `ORG_A` configured in Shipit's multi-tenant `secrets.github` (with their own valid `webhook_secret`) crafts a JSON payload where `repository.owner.login == "ORG_A"` but `repository.full_name == "victim-org/some-repo"`. They compute a correct `X-Hub-Signature` HMAC-SHA1 using `ORG_A`'s secret over this exact body (no GitHub secret guessing needed — it's their own). POST to `/webhooks` with `X-Github-Event: push`. `verify_signature` selects `ORG_A`'s `GitHubApp`, validates the signature successfully, and passes control to `PushHandler`, which resolves and syncs `victim-org/some-repo`'s stack based purely on `full_name`, with no re-check that `full_name`'s owner matches `repository_owner`.

No existing guard prevents this: `drop_unhandled_event` only checks the event type exists; `ExplicitParameters` schemas only validate types/presence, not cross-field consistency between `repository.owner.login` and `repository.full_name`; there is no `Repository` validation tying incoming payload owner to signature owner.

### Impact Explanation
The attacker forces `Stack#sync_github` / `GithubSyncJob` to run against a stack belonging to an organization/repository they have no relationship with, using only their own organization's valid webhook secret. This is a payload for one repository/organization mutating another's stack/task state — matching the Critical category explicitly listed ("a payload for one repository mutating another's stack, commit, task or team"). The attack is repeatable against any known `owner/repo` full_name present in the Shipit instance, and other handlers relying on the same `Handler#stacks`/`repository_name` pattern (e.g. `PullRequest` handlers) are similarly affected wherever `full_name` drives stack/repository resolution independent of the signing organization.

### Likelihood Explanation
This requires the deployment to use Shipit's multi-tenant GitHub app configuration (multiple orgs each with distinct `webhook_secret` under `secrets.github`), which is a supported, documented configuration path (`Shipit.github_organizations`, `github_app_config`, `TOP_LEVEL_GH_KEYS` check in `lib/shipit.rb:183-200`). In a single-org/global-secret deployment (`github_default_organization` returns `nil`), the same global `secrets.github` config/secret is used for all signature verification regardless of `repository_owner`, so this specific "attacker owns their own org's secret" framing doesn't apply the same way — but in that case any repository name can be signed with the one global secret, which is a related but distinct issue outside this specific question's binding. For the multi-tenant case, the attacker only needs to be an onboarded organization owner with legitimate access to their own `webhook_secret`, and can send arbitrary raw HTTP requests to `/webhooks` with no Shipit credentials — low cost and fully repeatable.

### Recommendation
In `Repository.from_github_repo_name`/`Handler#stacks` (or centrally in `WebhooksController`), verify that the owner segment of `repository.full_name` matches `repository_owner` (the organization whose secret authenticated the request) before resolving any `Stack`/`Repository`. Reject the webhook (422) if they diverge.

### Proof of Concept
Minitest plan (multi-tenant github config, `test/controllers/webhooks_controller_test.rb`):
1. Configure two orgs in `Shipit.stubs(:secrets)`/credentials fixture: `org_a` with `webhook_secret: "secret_a"`, and `victim-org` with `webhook_secret: "secret_victim"` (or leave `victim-org` unconfigured to show attacker doesn't need it).
2. Create `shipit_repository` for `victim-org/some-repo` with an associated `shipit_stack` on branch `master`.
3. Build push payload: `repository.owner.login = "org_a"`, `repository.full_name = "victim-org/some-repo"`, `ref = "refs/heads/master"`, valid `after` SHA.
4. Compute `signature = "sha1=" + OpenSSL::HMAC.hexdigest('sha1', "secret_a", body)`.
5. `request.headers['X-Github-Event'] = 'push'; request.headers['X-Hub-Signature'] = signature`.
6. `assert_enqueued_with(job: GithubSyncJob, args: [stack_id: victim_stack.id, expected_head_sha: after])` around `post :create, body:, as: :json`.
7. Assert response is `:ok` (200/204), proving `ORG_A`'s secret authenticated a mutation targeting `victim-org`'s stack — confirming the binding (`repository_owner` used for signature == organization owning the mutated repository) is broken.
