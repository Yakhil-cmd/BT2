### Title
Permanent market freeze via i128 overflow in interest accrual — once `borrowed * borrow_index` exceeds `i128::MAX`, every entrypoint panics in `global_sync` and all supplied/borrowed funds are frozen forever - (File: contracts/pool/src/interest.rs)

### Summary
The analog of CVE-2024-21219 (an attacker-triggerable, repeatable crash that denies service) is a permanent panic inside the pool's interest accrual. Every state-changing pool entrypoint (`supply`, `borrow`, `withdraw`, `repay`, `seize_positions`, `net_settle`, `claim_revenue`, `recapitalize`, `flash_loan`, `create_strategy`) runs `interest::global_sync` first, which calls `accrue_step` → `calculate_supplier_rewards` → `scaled.mul(env, index)`. The Ray multiplication panics on `i128` overflow once total debt value (`borrowed_scaled * borrow_index`) exceeds `i128::MAX`. Because the panic happens before any state is written, the overflow condition is never resolved: the market is wedged permanently, and no exit path exists — withdraw, repay, liquidation, and even `update_indexes` all hit the same panic. The borrow-index cap (`MAX_BORROW_INDEX_RAY`) does not protect against this because the value product overflows before the index reaches its cap, and the cap is applied to the index, not to `supplied`/`borrowed` magnitude.

### Finding Description
Root cause chain:

1. `interest::global_sync` runs unconditionally at the top of every market mutation (`contracts/pool/src/interest.rs:20-33`). It cannot be skipped once `needs_accrual()` is true.
2. `accrue_chunk` → `accrue_step` → `calculate_supplier_rewards` computes `borrowed.mul(env, new_borrow_index)` and `borrowed.mul(env, old_borrow_index)` (`common/src/rates/index.rs:80-81`). `Ray::mul` is a checked `i128` multiply that panics with `MathOverflow` on overflow — there is no saturation or I256 widening on this path.
3. The panic propagates through every caller. `ops::synced_market`/`load_leg` are used by `repay`, `withdraw`, `seize`, `net_settle`, `claim_revenue`, `recapitalize`, `borrow`, `supply`, `flash_loan`, `create_strategy` — all of them (`contracts/pool/src/ops/repay.rs:41`, `contracts/pool/src/ops/seize.rs:20`). Even `update_indexes` (`ops::market::accrue`) panics, so there is no administrative recovery short of an upgrade.
4. Nothing bounds the magnitude of `supplied`/`borrowed` against the future index product. `supply`/`borrow` caps validate the entry amount (`calculate_scaled_cap` saturates and `require_cap_within_asset_domain` bounds caps), but the stored totals can still reach magnitudes where `scaled * index > i128::MAX` after sustained accrual — confirmed by the dedicated harness test `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` (`tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:320-360`), which demonstrates `update_indexes`, `withdraw`, and `repay` all reverting with `MATH_OVERFLOW` while `borrow_index < MAX_BORROW_INDEX_RAY`.

The attacker needs no privilege: `supply` and `borrow` are permissionless controller verbs. Reaching the cliff requires a very large debt position (debt value in raw units approaching `i128::MAX / index`, i.e. ~10^11+ units of an 18-decimal asset at index RAY, less as the index grows) plus time at high utilization. The attacker can accelerate the freeze with their own capital by supplying and borrowing a whale-sized position on a high-APR curve; once the threshold is crossed, the panic state is self-sustaining and irreversible because the fix-up transaction (`update_indexes` or `recapitalize`) itself panics on accrual.

### Impact Explanation
Permanent freezing of funds: every supplier's deposit and every borrower's collateral-debt position in that market becomes inaccessible. Withdrawal, repayment, liquidation, and bad-debt socialization all revert in `global_sync`, so even healthy liquidations cannot run and recapitalization cannot restore solvency. The only recovery is a contract upgrade, which is a privileged governance action — the market itself is dead. This is a direct analog of the CVE's "hang or frequently repeatable crash causing complete DOS," applied to a single market's lifecycle.

### Likelihood Explanation
Medium. Exploitation requires whale-scale capital (debt value of ~10^38 raw units at index ≈ RAY, reachable only for high-supply/low-decimals-effective assets or via index growth over a long horizon) and sustained time at high utilization — the harness test needed multi-year simulated accrual at ~98% utilization before the cliff. However, no permission is needed, the attacker controls the debt size and can deliberately push a market toward the cliff, the trigger is deterministic arithmetic rather than oracle or governance failure, and the resulting freeze is permanent rather than fail-closed-for-one-call. The protocol documents `MathOverflow` as an expected error but has no mechanism to bound `borrowed * borrow_index` below `i128::MAX` or to recover the market once crossed.

### Recommendation
Guard the invariant `borrowed_scaled * borrow_index <= i128::MAX` (and the same for `supplied * supply_index`) at entry time: `supply`/`borrow`/`create_strategy` should reject mints that would leave the market within unsafe distance of the product ceiling, not just cap the per-call amount. Additionally, make accrual degradation graceful: saturate `calculate_supplier_rewards` at `i128::MAX` (or clamp the stored `borrowed`/`supplied` totals) instead of panicking, so accrual halts cleanly — indexes stop growing, but exits and liquidations remain callable and suppliers can withdraw. At minimum, `update_indexes` should be able to run with a saturating accrual so the market can be wound down rather than permanently bricked.

### Proof of Concept
The codebase's own harness test is the PoC (`tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:320-360`):

```rust
let mut t = LendingTest::new()
    .with_market(big("BIG18", 18, xlm_curve()))
    .with_market(col())
    .with_max_utilization_disabled_all_markets()
    .build();
let principal = BILLION * 10i128.pow(18);
t.supply_raw(BOB, "BIG18", principal);
t.borrow_raw(ALICE, "BIG18", principal / 100 * 98);

loop {
    t.advance_time(YEAR_SECS);
    if let Err(e) = t.try_update_indexes_for(&["BIG18"]) { break e; } // -> MATH_OVERFLOW
}
// Market is now frozen — every verb panics in global_sync:
assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
// borrow_index < MAX_BORROW_INDEX_RAY: the index cap never engaged.
```

Both attacker actions are the permissionless `supply`/`borrow` verbs. Once the accrued `borrowed * borrow_index` product crosses `i128::MAX`, the panic inside `calculate_supplier_rewards` (`common/src/rates/index.rs:80-81`) cannot be cleared by any in-protocol call, since every recovery path (`update_indexes`, `repay`, `recapitalize`, `clean_bad_debt` → `seize_positions`) runs `global_sync` first.
