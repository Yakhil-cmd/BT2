## Title
`build_updated_stake_reward` assumes stake delegation is static between reward calculation and distribution, causing an `assert_eq!` panic if a user mutates the stake account mid-distribution - (File: runtime/src/bank/partitioned_epoch_rewards/distribution.rs)

### Summary
The `RevenueHandler`/`VotingEscrow` bug is a class of vulnerability where a reward-distribution routine accumulates state across a window (multiple epochs/blocks) but assumes the user's underlying delegation/lock state was constant throughout that window. When an unprivileged user changes that state mid-window, the accumulated distribution logic becomes inconsistent with the recomputed/actual state, and the payout code fails outright rather than degrading gracefully. In Agave, `Bank::store_stake_accounts_in_partition` → `build_updated_stake_reward` reproduces this exact pattern: it assumes a stake account's `Delegation::stake` recorded during the **calculation** phase is still valid at **distribution** time (potentially many blocks later, when `adjust_delegations_for_rent` is disabled), and hard-asserts on that assumption.

### Finding Description
Partitioned epoch rewards in Agave happen in two phases separated by up to `REWARD_CALCULATION_NUM_BLOCKS` blocks and additional distribution blocks: `calculate_stake_rewards_and_commissions` computes a `PartitionedStakeReward` per stake account (capturing `inflation.stake` as the post-reward delegation) [1](#0-0) , and later `store_stake_accounts_in_partition`/`build_updated_stake_reward` applies that pre-computed reward to the **current** on-chain stake account read from `StakesCache` at distribution time [2](#0-1) .

When `adjust_delegations_for_rent` (`relax_post_exec_min_balance_check`) is *not* active, the code takes the `else` branch and hard-asserts that the stake account's on-chain delegation still equals `stake.delegation.stake + inflation.stake_reward`:

```
} else {
    let expected_delegation = stake
        .delegation
        .stake
        .saturating_add(partitioned_stake_reward.inflation.stake_reward);
    assert_eq!(
        expected_delegation, new_stake.delegation.stake,
        "stake reward delegation must be consistent with the updated stake account \
         lamport balance"
    );
}
``` [3](#0-2) 

This assumes the stake account's delegation stake did not change between the calculation slot and the distribution slot for that stake account. But an unprivileged user retains full control of their own stake account between those two events, and the standard Stake program instructions (`Split`, `Merge`, `Withdraw`-driven deactivation via rent-exempt adjustment, `Delegate`/`Deactivate`) can change `stake.delegation.stake` in that same window — this mirrors the veALCX bug where `updateLockTime` changed the user's balance-affecting state between the epochs a claim was computing over and the state actually used for computation. Distribution happens over multiple blocks after the epoch boundary (`REWARD_CALCULATION_NUM_BLOCKS` + `num_partitions` blocks) [4](#0-3) , giving a real window of ordinary user transactions during which the delegation.stake used in calculation can diverge from what's on-chain by distribution time.

I was not able to find, in the reachable code, any protocol-level restriction in the stake program that blocks users from mutating their own stake account (e.g., via `Split`/`Merge`) while `EpochRewardStatus` is `Active`; my search for such a guard (`epoch_rewards.*active`, `EpochRewardsPartitionDataInactive`, etc.) in the stake program paths returned no matches . This is a limitation of my investigation: I could not fully verify from the indexed code whether the currently-deployed stake program enforces such a restriction (this logic likely lives in the SVM `solana-stake-program` crate, whose full processor source I could not locate/confirm coverage for in this index). If such a restriction exists and fully blocks all delegation-mutating instructions while `EpochRewardStatus::Active`, this finding would not be reachable and should be treated as **unverified** rather than confirmed.

### Impact Explanation
If reachable, hitting the `assert_eq!` inside `build_updated_stake_reward` during block processing would trigger a Rust panic while executing `distribute_partitioned_epoch_rewards`, which runs on every validator processing the block deterministically at the epoch boundary. A panic in this consensus-critical path (rather than a graceful `DistributionError`) crashes/halts the validator process for every node reaching that block height, i.e., an epoch-boundary chain halt reachable by an ordinary user transaction rather than a privileged actor or a crafted snapshot.

### Likelihood Explanation
Likelihood is uncertain/low-to-unknown: the `assert_eq!` path is only taken when `adjust_delegations_for_rent` (the `relax_post_exec_min_balance_check` feature) is disabled, and I could not confirm from the available index whether the stake program actually permits `Split`/`Merge`/other delegation-mutating instructions on an account that is currently a pending partitioned-stake-reward recipient during the distribution window. Given this uncertainty, this should be treated as a hypothesis requiring validation against the current stake-program instruction handlers (outside this index's coverage) rather than a confirmed exploit.

### Recommendation
Convert the `assert_eq!` in `build_updated_stake_reward` into a recoverable `DistributionError` (as is already done for the `AccountNotFound`/`ArithmeticOverflow`/`UnableToSetState` cases) so that any unexpected mid-window mutation of the stake delegation results in a burned/skipped reward with an error log rather than a validator panic. Additionally confirm whether the stake program instruction handlers reject mutations (merge/split/delegate/deactivate) on a stake account while `EpochRewardStatus` is active; if not, add that guard so that stake accounts cannot be mutated between the calculation and distribution phases of partitioned epoch rewards.

### Proof of Concept
Not constructed — I could not verify in this index whether the stake program instruction processor rejects delegation-mutating instructions during an active `EpochRewardStatus`, which is required to determine if the `assert_eq!` in `build_updated_stake_reward` is actually reachable by an unprivileged user's ordinary transactions between the calculation and distribution blocks of partitioned epoch rewards. A concrete PoC would require exercising `Bank::new_from_parent` across the epoch boundary, submitting a `Split`/`Merge` stake instruction from the stake account owner between the calculation slot and its distribution partition slot (with `relax_post_exec_min_balance_check` disabled), and observing whether `distribute_partitioned_epoch_rewards` panics.
