### Title
Cross-organization `Team#github_id` lookup lets a webhook valid for one GitHub organization grant `Shipit.github_teams` membership in another organization - ([File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
The `MembershipHandler` for the `membership` webhook resolves the target `Team` record purely by the numeric `github_id` supplied in the JSON payload, without scoping the lookup to the organization whose credentials verified the webhook signature. This breaks the binding "the organization whose `webhook_secret` authenticated the request" == "the organization whose `Team`/authorization data is mutated," analogous to the Compound `topUp()` bug where the wrong (unscoped) selector/lookup caused the wrong entity to be acted upon.

### Finding Description
`WebhooksController#verify_signature` picks which `GitHubApp` (and thus which `webhook_secret`) to validate the incoming signature against, based on the organization embedded in the same payload the attacker controls: [1](#0-0) [2](#0-1) 

For a `membership` event, there is no top-level `repository` key, so `repository_owner` falls back to `params.dig('organization', 'login')`. This means the signature is validated against whatever GitHub App/organization matches `organization.login` — an org the attacker can genuinely control an installation of (e.g. an org where they legitimately run a GitHub App with a webhook secret they know), in a multi-org Shipit deployment (`docs/setup.md` "Using Multiple GitHub Applications", `test/dummy/config/secrets_double_github_app.yml`).

Once the signature check passes for that (attacker-controlled) organization, `MembershipHandler#process` resolves/creates the `Team` using only `github_id`, ignoring the organization that was just authenticated: [3](#0-2) 

`Team.find_or_create_by!(github_id: params.team.id)` will find an *existing* `Team` row with that `github_id` regardless of which organization it actually belongs to (the `organization:` assignment in the block only applies on creation, not when an existing record is found). GitHub team IDs are discoverable via the public API (`GET /orgs/:org/teams`), so an attacker can learn the `github_id` of an authorization team belonging to a *different* organization (e.g. the team referenced in `Shipit.github_teams`, used for access control) and reference it in a forged `membership` payload signed with their own org's webhook secret.

`team.add_member(member)` then adds an arbitrary GitHub login (which will be auto-created via `User.find_or_create_by_login!`) into that team: [4](#0-3) 

That `Team`/`Membership` state is exactly what `User#authorized?` checks to gate access to the entire Shipit UI: [5](#0-4) [6](#0-5) 

So the equality that should hold — "organization that authenticated the webhook" == "organization whose Team/membership data is mutated" — is broken: verification is scoped by `organization.login`, but the actual write (`Team.find_or_create_by!`) is scoped only by `github_id`, with no cross-check against the organization used for authentication.

### Impact Explanation
If a Shipit instance is configured for multiple GitHub organizations (a documented, supported configuration) and uses `github.oauth.teams` for access control, an attacker who is a legitimate GitHub App installer/owner for *one* configured organization can forge a signed `membership` webhook that adds an arbitrary GitHub account into an authorization team belonging to a *different* configured organization. This is an escalation into `Shipit.github_teams` authorization — granting an unauthorized identity access to the Shipit application (High impact per the rules), and in installations where a `Shipit::Team` is scoped to deploy permissions, could enable further unauthorized actions.

### Likelihood Explanation
Requires: (1) a multi-organization Shipit configuration (explicitly documented/supported), (2) the attacker being a legitimate app owner/webhook sender for at least one configured org (not privileged in the target org), and (3) knowledge of the target team's numeric `github_id`, obtainable via GitHub's public teams API if the target org's teams aren't private, or via other reconnaissance. This is a realistic but not trivial precondition set — moderate likelihood, gated on multi-org deployments.

### Recommendation
Scope the `Team` lookup/creation in `MembershipHandler#find_or_create_team!` by both `github_id` **and** `organization` (matching the authenticated `params.organization.login`), and reject/ignore the event if an existing `Team` with that `github_id` belongs to a different organization than the one that authenticated the webhook.

### Proof of Concept
1. Configure Shipit with two GitHub Apps for `OrgA` and `OrgB` (per `docs/setup.md`'s "Using Multiple GitHub Applications"), with `Shipit.github_teams` including `OrgA/authorized-team` (github_id known, e.g. `100`).
2. As the owner of `OrgB`'s GitHub App (attacker-controlled), craft a `membership` webhook payload:
```json
{
  "action": "added",
  "team": { "id": 100, "name": "authorized-team", "slug": "authorized-team", "url": "https://api.github.com/teams/100" },
  "organization": { "login": "OrgB" },
  "member": { "login": "attacker-github-login" }
}
```
3. Sign it with `OrgB`'s `webhook_secret` and POST to `/webhooks` with `X-Github-Event: membership`.
4. `verify_signature` resolves `repository_owner` = `"OrgB"`, validates successfully against `OrgB`'s secret.
5. `MembershipHandler#find_or_create_team!` calls `Team.find_or_create_by!(github_id: 100)`, finds the existing `OrgA` team, and `team.add_member(attacker)` adds `attacker-github-login` as a member.
6. `attacker-github-login` logs into Shipit via OAuth; `User#authorized?` now returns `true` because they are a member of `OrgA/authorized-team`, granting access without ever having been vetted by `OrgA`.

        def process
          team = find_or_create_team!
          member = User.find_or_create_by_login!(params.member.login)

          case params.action
          when 'added'
            team.add_member(member)
          when 'removed'
            team.members.delete(member)
          else
            raise ArgumentError, "Don't know how to perform action: `#{action.inspect}`"
          end
        end

        private

        def find_or_create_team!
          Team.find_or_create_by!(github_id: params.team.id) do |team|
            team.github_team = params.team
            team.organization = params.organization.login
          end
        end
