### Title
Missing WebAuthn `ClientDataType` (ceremony-type) binding check in `PartialAuthenticatorAssertionResponse::verify` - (File: types/src/transaction/webauthn.rs)

### Summary
`PartialAuthenticatorAssertionResponse::verify` (and `verify_arbitrary_msg`) parse `client_data_json` into a `CollectedClientData` struct but only validate the `challenge` field against the expected transaction hash. The `ty` field (which per the WebAuthn spec must be `"webauthn.get"` for an authentication/assertion ceremony) is never checked, so a structurally valid signature accompanied by a `client_data_json` claiming a different ceremony type (e.g. `"webauthn.create"`, or an arbitrary custom string) is still accepted.

### Finding Description
`verify()` does the following in [1](#0-0) :
1. Deserializes `client_data_json` into `CollectedClientData`.
2. Extracts `challenge` and checks it equals the SHA3-256 digest of the raw transaction's signing message.
3. Builds `verification_data` = `authenticator_data || SHA-256(client_data_json)` and verifies the Secp256r1 ECDSA signature over it.

At no point is `collected_client_data.ty` compared against the expected ceremony type (`ClientDataType::Get`, i.e. `"webauthn.get"`). The W3C WebAuthn spec §7.2 explicitly requires verifiers to check that `clientData.type` is the expected value to prevent cross-ceremony confusion (e.g., accepting a registration/`create` ceremony assertion as if it were a `get`/authentication assertion, or accepting a `payment.get` SPC-flavored assertion in a context that didn't intend it). Because the signature is computed over `authenticator_data || SHA-256(client_data_json)`, and `client_data_json`'s hash already commits to whatever `ty` string is present, an attacker who controls the authenticator/client (which is normal in a passkey ceremony — the "attacker" here is anyone who can produce their own client-side JSON, e.g. a malicious webpage/dApp using WebAuthn to get a user to sign something under one ceremony type while binding it into a differently-typed structure) can substitute `ty` with an unintended value without breaking signature verification, since the signature and challenge checks don't depend on `ty`.

This binds a transaction to being admitted under an authenticator ceremony-type binding that has not been validated — a partial break of the "authenticator/WebAuthn checks must bind to the intended semantics" guarantee described in the admission pivots.

Notably, the test suite in this file [2](#0-1)  demonstrates that a `client_data_json` with `"type": "payment.get"` (not `"webauthn.get"`) is accepted successfully by `verify()`, confirming that `ty` is not checked at all — any string value passes as long as the signature and challenge match.

### Impact Explanation
This is a binding/semantic-check gap rather than a full authentication bypass: the attacker still needs a valid signature from the account's real private key over `authenticator_data || SHA-256(client_data_json)`, so this does not let an unprivileged attacker forge a signature or impersonate another signer's key. It does mean the module fails to enforce the WebAuthn ceremony-type contract that the wider ecosystem (browsers, authenticators, relying-party libraries) relies on to prevent cross-ceremony replay/confusion attacks. Whether this is exploitable to admit a transaction "under an unintended ceremony context" depends on whether any attacker-influenced flow can get a real WebAuthn authenticator to sign transaction-hash challenges under a `create` (registration) ceremony and have that accepted here as if it were a `get` (assertion) ceremony — the current code does not prevent it.

### Likelihood Explanation
Moderate-to-low practical likelihood: exploiting this requires an attacker to get the legitimate signer to go through a WebAuthn ceremony whose `clientDataJSON.type` differs from `"webauthn.get"` while still embedding the intended transaction-hash challenge, which is unusual for standard passkey/browser flows (browsers set `type` automatically based on the WebAuthn API called, `navigator.credentials.get()` vs `.create()`), but it is not enforced in code, so it is a defense-in-depth omission that any custom/non-standard authenticator client could exploit deliberately, and it deviates from the WebAuthn spec's explicit verification step.

### Recommendation
Add an explicit check in `PartialAuthenticatorAssertionResponse::verify` (and `verify_arbitrary_msg`) that `collected_client_data.ty == ClientDataType::Get`, rejecting the assertion otherwise, matching WebAuthn §7.2 step "assertion.response.clientDataJSON... type ... verify that the value ... is the string webauthn.get."

### Proof of Concept
Add a unit test to `types/src/transaction/webauthn.rs`'s `mod tests` that builds a `PartialAuthenticatorAssertionResponse` whose `client_data_json` sets `"type": "webauthn.create"` (or any non-`"webauthn.get"` value) but keeps a correctly-computed `challenge` (SHA3-256 of the raw transaction signing message) and a signature validly computed over `authenticator_data || SHA-256(client_data_json)`. Call `paar.verify(&raw_txn, &any_public_key)` and observe it returns `Ok(())` instead of an error, demonstrating `ty` is not validated. The existing SPC test at [3](#0-2)  already shows a non-`"webauthn.get"` `ty` (`"payment.get"`) passing `verify()` successfully, corroborating that no ceremony-type check exists.

    pub fn verify<T: Serialize + CryptoHash>(
        &self,
        message: &T,
        public_key: &AnyPublicKey,
    ) -> Result<()> {
        let collected_client_data: CollectedClientData =
            serde_json::from_slice(self.client_data_json.as_slice())?;
        let challenge_bytes = Bytes::try_from(collected_client_data.challenge.as_str())
            .map_err(|e| anyhow!("Failed to decode challenge bytes {:?}", e))?;

        // Check if expected challenge and actual challenge match. If there's no match, throw error
        verify_expected_challenge_from_message_matches_actual(message, challenge_bytes.as_slice())?;

        // Generates binary concatenation of authenticator_data and hash(client_data_json)
        let verification_data = generate_verification_data(
            self.authenticator_data.as_slice(),
            self.client_data_json.as_slice(),
        );

        // Note: We must call verify_arbitrary_msg instead of verify here. We do NOT want to
        // use verify because it BCS serializes and prefixes the message with a hash
        // via the signing_message function invocation
        match (&public_key, &self.signature) {
            (
                AnyPublicKey::Secp256r1Ecdsa { public_key },
                AssertionSignature::Secp256r1Ecdsa { signature },
            ) => signature.verify_arbitrary_msg(&verification_data, public_key),
            _ => Err(anyhow!(
                "WebAuthn verification failure, invalid key, signature pairing"
            )),
        }
    }
