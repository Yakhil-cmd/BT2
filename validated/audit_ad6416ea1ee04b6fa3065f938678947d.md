### Title
Webhook signature verification is keyed on an attacker-controlled `repository.owner.login` while payload processing acts on unrelated fields (`repository.full_name`, or nothing at all) — ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to verify against using `repository_owner`, a field read directly from the untrusted JSON body (`params.dig('repository', 'owner', 'login')` or `params.dig('organization', 'login')`). If the organization named there has no `webhook_secret` configured, `GitHubApp#verify_webhook_signature` short-circuits to `true` and the request is accepted with **no signature check at all**. The event is then dispatched to handlers that resolve their real target using a *different* field: `Handler#repository_name` reads `payload.dig('repository', 'full_name')`, and `StatusHandler` doesn't even use the repository field — it matches purely on `sha` across the whole database. Nothing ties the "organization that authenticated" to the "repository (or commit) that is written."

### Finding Description
- `WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-49`) computes:
  ```ruby
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
  head(422) unless verified
  ```
  where `repository_owner` is `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` — both are attacker-supplied JSON values, read before any authentication occurs.
- `GitHubApp#verify_webhook_signature` (`lib/shipit/github_app.rb:76-83`) contains:
  ```ruby
  def verify_webhook_signature(signature, message)
    return true unless webhook_secret
    ...
  end
  ```
  If the organization picked via `repository_owner` has no `webhook_secret` configured (a supported, documented state — see `config/secrets.development.shopify.yml:9,18` and `docs/setup.md:119` describing it as optional), **any payload is accepted unconditionally**, regardless of the `X-Hub-Signature` header.
- After acceptance, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` dispatches to handlers that determine their *actual* target using unrelated fields:
  - `Handlers::Handler#repository_name` (`app/models/shipit/webhooks/handlers/handler.rb:36-38`) uses `payload.dig('repository', 'full_name')` to look up `Repository.from_github_repo_name(...)` and its stacks — a completely independent JSON key from the one used to pick the signing organization.
  - `Handlers::StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`) does not consult the repository at all: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` — it matches globally by commit `sha`.

Because these are all independently attacker-controlled fields in the same unauthenticated JSON body, there is no invariant enforced that the organization whose (absent) secret gated the request corresponds to the repository/commit actually mutated. An attacker who knows (or can probe) that some org configured in `Shipit.github` (e.g. an org onboarded but not yet given a `webhook_secret`, which is explicitly a supported configuration state) has no secret can send:
```
X-Github-Event: status
{
  "repository": { "owner": { "login": "org-with-no-secret" } },
  "sha": "<real sha belonging to a fully protected stack>",
  "state": "success",
  "context": "<the context required by that other stack>"
}
```
`verify_signature` passes trivially (no secret ⇒ `return true`), and `StatusHandler` writes a forged "success" CI status onto the targeted commit of a stack belonging to a completely different, secured organization, with no correlation check between the "authenticating" org and the "written" commit/repository.

### Impact Explanation
Forged CI status on `Commit` feeds `Commit#create_status_from_github!`, which is used by `deployable?`/CI gating logic and by continuous delivery scheduling (`Stack.schedule_continuous_delivery`, triggered via `after_commit :schedule_continuous_delivery` and CI-status callbacks in `app/models/shipit/commit.rb:24-25`). A forged "success" status can flip a commit into deployable state for a stack with `continuous_deployment: true`, resulting in an unauthorized automatic deploy of that commit — matching the "unauthorized deploy" impact category. Even short of that, it is an authentication-bypass for the entire webhook ingestion boundary of any organization lacking a `webhook_secret`, letting an attacker forge push/status/check_suite/membership events against stacks of *other*, properly-secured organizations that happen to be hosted by the same Shipit instance, because none of the handlers verify that the "owner" used for authentication matches the "full_name"/`sha` used for the actual write.

### Likelihood Explanation
Likelihood is conditioned on at least one organization configured in the same Shipit instance without a `webhook_secret` — an explicitly supported, undocumented-as-forbidden configuration (shown as the default/example value in `config/secrets.development.shopify.yml` and described as optional in `docs/setup.md`). Multi-tenant Shipit deployments that onboard new GitHub orgs before wiring up their webhook secret, or that intentionally leave an org's secret blank, expose every *other* org's stacks to forged webhook events, since the org-selection field and the actually-processed fields are never cross-validated anywhere in the controller or handler chain.

### Recommendation
- Enforce that the organization derived from the payload matches the organization implied by the target `repository.full_name` (or the resolved `Stack`/`Repository`) before processing any event — i.e., verify `repository_owner == full_name.split('/').first` (case-insensitively) prior to dispatch.
- Do not allow `verify_webhook_signature` to silently return `true` when `webhook_secret` is blank in any environment where other organizations are configured with secrets; either require a secret for all configured organizations or scope the "no secret" bypass to single-tenant/test deployments only.
- Have `StatusHandler` (and any other handler that doesn't already) scope its `Commit` lookup to the resolved `Repository`/`Stack` derived from the verified organization, not solely by `sha`.

### Proof of Concept
1. Configure Shipit with two orgs: `secure-org` (has stacks + a `webhook_secret`) and `unsecured-org` (no `webhook_secret` — e.g. newly onboarded).
2. Find a real commit `sha` belonging to a `secure-org` stack (commit shas are visible in the public GitHub repo / task pages).
3. POST to `/webhooks` with header `X-Github-Event: status` and body:
   ```json
   {
     "repository": { "owner": { "login": "unsecured-org" } },
     "sha": "<secure-org commit sha>",
     "state": "success",
     "context": "<required context of that stack>"
   }
   ```
   No valid `X-Hub-Signature` is required since `verify_webhook_signature` returns `true` for `unsecured-org`.
4. Observe `verify_signature` passes (`app/controllers/shipit/webhooks_controller.rb:24-49`), `StatusHandler#process` creates a forged success status on the targeted `secure-org` commit (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`), potentially unblocking continuous delivery for that commit.
