### Title
Race condition in private-payment "duplicate" check allows double-crediting of divisible private-asset outputs - ([File: private_payment.js])

### Summary
`ssh-agent`'s bug class (a resource can be released/consumed twice because the code that guards against reuse is not atomic with the action it guards) maps to a TOCTOU race in ocore's private-payment path: `validateAndSavePrivatePaymentChain()` in `private_payment.js` checks for a "duplicate" private payment with a plain `SELECT`, and only *after* that check completes does it call the asset module to `INSERT` the outputs/inputs. For divisible private assets this insert is unconditional (no `INSERT IGNORE`, no unique constraint), so two concurrent invocations for the same private-payment chain can both pass the duplicate check and both insert, duplicating the recipient's balance.

### Finding Description
`private_payment.js` exposes `validateAndSavePrivatePaymentChain(arrPrivateElements, callbacks)`, which is the sole entry point that validates and persists a chain of private-payment elements (used both for divisible and indivisible private assets): [1](#0-0) 

It takes a **new** DB connection, begins a transaction, and performs a `SELECT` to detect whether this exact output was already saved: [2](#0-1) 

Only if the row is not found (or not a match) does it hand off to the divisible/indivisible asset module to insert the rows and commit: [3](#0-2) 

Crucially, this whole "check-then-insert" sequence is **not protected by any mutex** — unlike the regular unit-validation pipeline, which always locks `mutex.lock(['handleJoint'], ...)` or per-author-address locks before validating/saving, and unlike `network.js`'s ordinary joint pipeline, which tracks in-flight units via `assocUnitsInWork[unit]` to reject a second concurrent attempt: [4](#0-3) 

No equivalent guard exists for private payments. `network.js`'s `handleOnlinePrivatePayment()` calls `privatePayment.validateAndSavePrivatePaymentChain()` directly from the `ifKnown` branch with no de-duplication tracking: [5](#0-4) 

The code even acknowledges that receiving the *same* private payment more than once is a normal, expected occurrence (not an attack): "we may receive the same unit and message index but different output indexes if recipient and cosigner are on the same device. In this case, we also receive the same (unit, message_index, output_index) twice - as cosigner and as recipient." That's precisely why `unhandled_private_payments` uses `INSERT IGNORE`: [6](#0-5) 

However, that `IGNORE` only dedupes the *queue* table; it does not protect the actual write path. If two deliveries of the same chain race through `validateAndSavePrivatePaymentChain()` (e.g., one via the direct `ifKnown` branch, one from the periodic `handleSavedPrivatePayments()` sweep, or simply two near-simultaneous "private_payment_chains" deliveries from a hub/cosigner), each opens its own connection/transaction, each executes the duplicate-detection `SELECT` **before either has committed an INSERT**, so both see "no existing row" and both proceed.

For divisible private assets, the eventual insert has no protection against duplication: [7](#0-6) 

There is no `INSERT IGNORE`/`ON DUPLICATE KEY` and no unique index enforced here (contrast with the indivisible-asset path, which explicitly uses `db.getIgnore()`): [8](#0-7) 

So two racing calls each insert a full, independent `outputs` row (and mark the same source `input` as spent redundantly) for the identical private element, effectively duplicating the recipient's (and/or the change) output amount in the local private-asset ledger.

### Impact Explanation
Private-asset balances in ocore are computed by summing unspent `outputs` rows for the address/asset. If the same private element gets inserted twice, the wallet now believes it holds two independent unspent outputs of the same amount for the same asset, when only one payment was actually made and only one input was consumed on-chain. This is a supply-inflation-class bug for private (divisible) assets: the recipient/wallet can later attempt to spend both duplicated outputs, i.e., double-spend a value that was only paid once — a direct violation of asset-conservation at a wallet/hub node, matching the "unauthorized spending"/"supply inflation" bar required by the validation rules. This is reachable purely through the private-payment counterparty flow explicitly listed as an in-scope actor, with no reliance on a malicious peer/node/hub — a duplicate/racing delivery of the very same, legitimately-signed private payment is sufficient.

### Likelihood Explanation
The race requires two invocations of `validateAndSavePrivatePaymentChain()` for the same private element to be in flight concurrently on a MySQL-backed node (which runs multiple real concurrent DB connections/transactions, e.g., a hub/witness) before either transaction commits. Because the codebase's own comments confirm that duplicate delivery of the same private payment is a normal occurrence (cosigner+recipient sharing a device, hub re-delivery/retries, or `handleSavedPrivatePayments()`'s 5-second sweep racing a freshly-arrived `ifKnown` delivery), triggering two overlapping deliveries is straightforward and does not require exploiting any other bug — a private-payment counterparty (or a device impersonating one, or simply sending the identical `private_payment_chains` payload twice back-to-back) can trigger it deliberately. The exact commit-timing window needed for the race is a factor limiting 100% reliability, which is reflected by not raising this to Critical, but the bug class and reachability are concrete.

### Recommendation
Serialize `validateAndSavePrivatePaymentChain()` per private-element identity (e.g., `mutex.lock(['private-'+unit+'-'+message_index+'-'+output_index], ...)`, similar to the existing `private_write` lock used elsewhere in `validation.js`) so that the duplicate-check `SELECT` and subsequent `INSERT` are atomic with respect to concurrent deliveries of the same private payment. Additionally, add a unique constraint / `INSERT IGNORE` (or `ON CONFLICT DO NOTHING`) on the `outputs`/`inputs` insert in `divisible_asset.js` for private-payment paths, matching the defense already used for indivisible assets in `indivisible_asset.js`.

### Proof of Concept
1. Set up a hub/node using MySQL storage (`conf.storage = 'mysql'`) so that concurrent DB transactions are truly parallel.
2. As a private-payment counterparty, construct one valid divisible-private-asset payment chain (`arrPrivateElements`) addressed to a victim/attacker-controlled wallet.
3. Deliver the exact same `arrPrivateElements` payload to the victim node twice in rapid succession through two independent channels that both resolve via `joint_storage.checkIfNewUnit`'s `ifKnown` branch — e.g., once directly via `network.handleOnlinePrivatePayment` (as would happen from `wallet.js`'s `handlePrivatePaymentChains`) and once via the periodic `handleSavedPrivatePayments()` sweep picking up a queued copy, timed to land within the same few-millisecond window (trivially reproducible by sending the "private_payment_chains" justsaying twice back to back while a previous unhandled copy from an earlier session/retry is also being swept).
4. Observe that `private_payment.js`'s duplicate `SELECT` (lines 62–76) returns no match for both concurrent calls before either commits, and both calls proceed to `divisible_asset.js`'s plain `INSERT INTO outputs` (lines 32–38), producing two `outputs` rows for the identical payment.
5. Confirm the wallet database now reports double the correct balance for that private asset and that both duplicated outputs are independently spendable.
