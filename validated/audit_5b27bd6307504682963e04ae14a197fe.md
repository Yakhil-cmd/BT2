MembershipHandler is even more telling: it derives team membership entirely from the `organization.login` field embedded in the JSON body, while `WebhooksController#verify_signature` also authenticates the request using that same `organization.login` (or `repository.owner.login`) field to pick which GitHub App secret to check the signature against. The binding that's broken is: **the organization whose webhook secret was used to authenticate the request** must equal **the organization on whose behalf the payload's contents are trusted to write** (create teams/repos, add/remove team members, sync stacks, etc.). Nothing in the engine cross-checks that the `repository`/`organization` object used by `verify_signature` is the *same* value later trusted by the handler to select the target `Repository`/`Team`/`Stack`.

### Title
Webhook signature is verified against the payload's own `organization`/`repository.owner` field, allowing any onboarded organization's webhook secret to forge writes to a different organization's stacks and teams - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` picks the GitHub App/secret used to validate the HMAC signature from the same JSON body it is trying to authenticate (`repository.owner.login`, falling back to `organization.login`), then hands the *entire* raw, self-describing payload to the event handler, which independently re-reads `repository.full_name` or `organization.login` to decide which `Stack`, `Repository`, or `Team` to mutate. Because the field that selects "whose secret must sign this" and the field that selects "what gets written" are both attacker-supplied and never checked against each other, a party who knows the webhook secret for *any* organization configured in this Shipit instance can sign a payload where the authenticating organization is their own but the target repository/organization named for writes is a different tenant's.

### Finding Description
`verify_signature` derives `repository_owner` purely from the untrusted JSON body and uses it to look up which app's secret to check the signature with: [1](#0-0) [2](#0-1) .

Once the signature check passes, `Shipit::Webhooks.for_event(event)` handlers are invoked with the same raw `params` hash [3](#0-2) . Each handler independently trusts fields from that same body to decide what to mutate: `Handler#stacks`/`#repository_name` re-reads `repository.full_name` [4](#0-3) , `PushHandler#process` uses those stacks to trigger `sync_github` [5](#0-4) , and `MembershipHandler#process` uses `params.organization.login` to create/attach a `Team` and add/remove a `member` by login, entirely independent of which organization's secret authenticated the request [6](#0-5) .

Nothing enforces that the `repository.owner.login`/`organization.login` value consumed by `verify_signature` for choosing the HMAC secret is the same value later consumed by the handler to select the `Repository`, `Stack`, or `Team` being written to. `Shipit.github(organization:)` supports multiple independently configured GitHub Apps/secrets per organization (see the multi-org test fixture referenced by `ShipitTest#".github uses indifferent access..."`), so this is a real multi-tenant configuration, not a hypothetical.

### Impact Explanation
Any user who legitimately administers one onboarded GitHub organization/App in this Shipit instance (and therefore knows that org's own webhook secret, since they configured it) can craft an HTTP POST directly to `/webhooks` with a body whose `repository.owner.login`/`organization.login` is set to their own org (so the signature validates against their known secret) but whose `repository.full_name` (for push/PR/status handlers) or nested `organization.login`/`team`/`member` (for the membership handler) names a *different* tenant's repository or team. This crosses the "organization that authenticated versus the repository that is written" boundary explicitly called out as in-scope, and enables cross-repository/cross-tenant writes: forcing a `GithubSyncJob` on someone else's stack, creating commit `Status` rows on someone else's commits, unarchiving/archiving another tenant's stacks via PR handlers, or adding/removing memberships on another tenant's `Team` records (which gates `authorized?` and therefore application-wide access control). This satisfies the Critical bucket ("cross-repository writes").

### Likelihood Explanation
Likelihood is High for any deployment where more than one GitHub organization/App is configured in `secrets.github` (a documented, supported configuration, per `docs/setup.md` and the `Shipit.github(organization:)` lookup). Any org owner who is allowed to self-service configure their own Shipit GitHub App (and thus knows their own webhook secret) is by definition an "unprivileged attacker" with respect to every *other* tenant's repositories in the same Shipit install, and can reach `/webhooks` unauthenticated (it has no `ApiClient` or session requirement) with a hand-crafted body.

### Recommendation
After signature verification succeeds for organization `X`, re-validate that every organization/repository name referenced inside the handler-relevant fields of the same payload (`repository.owner.login`, `repository.full_name`'s owner segment, `organization.login`) is equal to `X` before dispatching to any handler; reject (422) payloads where these fields disagree.

### Proof of Concept
1. Configure Shipit with two GitHub Apps, `OrgA` and `OrgB`, each with its own `webhook_secret` (as supported by `Shipit.github(organization:)`).
2. As an administrator of `OrgA` (an unprivileged party w.r.t. `OrgB`), compute `X-Hub-Signature` over a crafted JSON body using `OrgA`'s known `webhook_secret`.
3. Set the body's `repository.owner.login` (or `organization.login`) to `"OrgA"` so `verify_signature` selects `OrgA`'s secret and the HMAC check passes, per `app/controllers/shipit/webhooks_controller.rb:24-30,59-62`.
4. Set `repository.full_name` to `"OrgB/target-repo"` (for a `push` event) or nest `organization.login: "OrgB"` with an arbitrary `team`/`member` (for a `membership` event).
5. POST to `/webhooks` with header `X-Github-Event: push` (or `membership`). The signature check succeeds using `OrgA`'s secret, then `PushHandler`/`MembershipHandler` acts on `OrgB`'s `Stack`/`Team` records, per `app/models/shipit/webhooks/handlers/push_handler.rb:12-17` and `app/models/shipit/webhooks/handlers/membership_handler.rb:22-43`.
