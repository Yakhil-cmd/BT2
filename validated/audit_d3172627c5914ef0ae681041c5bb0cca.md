### Title
Missing parentheses in `OpenedHandler#provision?` let `prevent_with_label` PRs create ReviewStacks even when `review_stacks_enabled` is `false` - ([File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb])

### Summary
`provision?` intends to require `repository.review_stacks_enabled == true` as a precondition for any provisioning decision, but due to Ruby operator precedence (`&&` binds tighter than `||`), the flag only gates the `allow_all` branch. For repositories configured with `provisioning_behavior: prevent_with_label`, an attacker-controlled pull request with no provisioning label satisfies the third disjunct unconditionally, bypassing `review_stacks_enabled`.

### Finding Description
The claimed binding is: `repository.review_stacks_enabled == true` should gate every path that leads to `ReviewStackAdapter#find_or_create!` in `OpenedHandler#process` (app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb:41-46).

The actual code:
```ruby
def provision?
  repository.review_stacks_enabled &&
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
``` [1](#0-0) 

Ruby parses this as `(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?)`. The `review_stacks_enabled` term is only ANDed into the first disjunct; it has no effect on the second or third disjuncts. So for a repository with `review_stacks_enabled: false` and `provisioning_behavior: prevent_with_label`, `provisioning_behavior_prevent_with_label?` is `true`, and if the incoming PR carries no label matching `provisioning_label_name`, `!pull_request_has_provisioning_label?` is `true`, making the whole expression `true` regardless of `review_stacks_enabled`.

Exploit flow: an attacker who can open a pull request (or POST a forged-looking but validly-signed `pull_request` `opened` webhook — note: signature verification is a separate concern; here the vector is simply opening a real PR without applying the provisioning label, which is fully within an unprivileged PR author's control) against a repo with this configuration causes `respond_to_pull_request_opened?` → `provision?` to return `true`, and `process` calls `ReviewStackAdapter.new(params, scope: repository.review_stacks).find_or_create!`, which creates a new `Shipit::ReviewStack` and enqueues it via `Shipit::ReviewStackProvisioningQueue.add(stack)` [2](#0-1) , leading to provisioning (checkout/build of `shipit.yml`-driven tasks) for a repository whose operator explicitly disabled review stacks.

Existing guards do not prevent this: `respond_to_pull_request_opened?` only checks `params.action == "opened"` and `provision?` [3](#0-2) ; there is no separate `review_stacks_enabled` check like the one present in the reopened handler's `unarchive?` (same faulty precedence bug there too) or the correctly-gated `labeled_handler.rb`'s `respond_to_label_change?`, which explicitly ANDs `repository.review_stacks_enabled` as its own top-level term [4](#0-3) . The `NullRepository` fallback (used for untracked repos) hardcodes `review_stacks_enabled` to `false` and all behavior predicates to `false`, so it is not itself vulnerable — but a legitimate, tracked `Repository` record with `review_stacks_enabled: false` and `provisioning_behavior: prevent_with_label` is exposed [5](#0-4) .

### Impact Explanation
For any tracked repository configured with `review_stacks_enabled: false` and `provisioning_behavior: prevent_with_label`, an unprivileged PR author who omits the provisioning label triggers unauthorized `Shipit::ReviewStack` creation and enqueues it for provisioning, which per the codebase's execution-trust model runs `shipit.yml`-driven tasks (build/deploy commands) against that repository — this matches "unauthorized deploy" / unauthorized command execution impact. The blast radius is scoped to repositories that are (a) tracked by Shipit and (b) explicitly configured with this specific combination of settings; it does not cross tenant boundaries to repositories using other behaviors, and it does not affect the `allow_all`/`allow_with_label` cases correctly. This is repeatable per repository/PR by any user able to open a PR without the label.

### Likelihood Explanation
Requires a maintainer/operator to have configured `review_stacks_enabled: false` together with `provisioning_behavior: prevent_with_label` — a plausible but non-default configuration combination (arguably self-contradictory, since disabling review stacks while also configuring a label-based provisioning policy suggests operator intent was to disable stack creation entirely). No secrets, tokens, or special permissions are needed beyond the ability to open a PR against the target repo (or in a fork whose webhook targets Shipit), which is trivially available to any unprivileged contributor. Attacker cost is zero beyond opening a PR without adding a label — the default state.

### Recommendation
Add explicit parentheses so `review_stacks_enabled` gates the entire expression:
```ruby
def provision?
  repository.review_stacks_enabled && (
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
  )
end
```
Apply the same fix to `ReopenedHandler#unarchive?` in app/models/shipit/webhooks/handlers/pull_request/reopened_handler.rb, which has the identical precedence bug.

### Proof of Concept
minitest plan (app/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb style, outside `test/` scoping rules noted only for illustration — actual test belongs under `test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb`):
```ruby
test "does NOT create a review stack when review_stacks_enabled is false, even with prevent_with_label and no label" do
  repository = shipit_repositories(:shipit)
  configure_provisioning_behavior(
    repository:,
    provisioning_enabled: false,       # review_stacks_enabled == false
    behavior: :prevent_with_label,
    label: "pull-requests-label"
  )
  payload = payload_parsed(:pull_request_opened)
  payload["pull_request"]["labels"] = []  # no provisioning label

  assert_no_difference -> { Shipit::Stack.count } do
    OpenedHandler.new(payload).process
  end
end
```
Before the fix, this assertion fails: `Shipit::Stack.count` increases by 1 (via `ReviewStackAdapter#create!`) because `provision?` evaluates `(false && false) || (false && ...) || (true && true) == true`, even though `repository.review_stacks_enabled == false`. After applying the parenthesization fix, `provision?` correctly evaluates to `false` and no stack is created.
