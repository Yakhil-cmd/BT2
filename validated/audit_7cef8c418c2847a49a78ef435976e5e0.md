### Title
Bad-debt socialization can zero the vault's liquidity index in a single event, wiping out all suppliers - ([File: mainnet/contracts/vault/v0-vault-stx.clar])

### Summary
When a liquidator triggers bad-debt socialization on an under-collateralized borrower whose written-off debt (`debt-reduction`) is greater than or equal to the vault's current total assets, `socialize-debt` sets `new-lindex` to `u0` instead of a proportional write-down. This is analogous to the Float Capital `poolValue` bug: an unguarded arithmetic edge case in a shared per-epoch/per-event state update, triggered by one actor's action (a liquidation), causes a catastrophic, non-proportional loss to a completely different set of unprivileged parties (all liquidity suppliers of that vault, and anyone using that vault's zToken as collateral).

### Finding Description
`socialize-debt` in the vault contracts computes: [1](#0-0) 

```clarity
(define-public (socialize-debt (scaled-amount uint))
  (let (...
        (old-total-assets (total-assets))
        (debt-reduction (mul-div-down scaled-amount idx INDEX-PRECISION))
        ...
        (new-lindex (if (and (> old-total-assets u0) (> old-total-assets debt-reduction))
                       (mul-div-down current-lindex (- old-total-assets debt-reduction) old-total-assets)
                       u0)))
```

If `old-total-assets <= debt-reduction`, the intended proportional write-down `current-lindex * (old-total-assets - debt-reduction) / old-total-assets` is skipped entirely and `new-lindex` is forced to `u0`. Since the liquidity index (`lindex`) is the multiplier used everywhere the vault's share price is computed — e.g. `resolve-ztoken` in `market.clar` (`price = base_price * li / PRECISION`, as documented in `docs/oracle.md`) and `convert-to-assets-preview` (`amount = shares * ta / ts`, which itself is built from `lindex`-derived `total-assets`) — setting `lindex` to `0` instantly reduces the *redeemable value of every zToken in that vault to zero*, not just the loss actually incurred.

This function is reached from the market's liquidation flow. When a borrower has no collateral left, `v0-4-market.clar` calls `socialize-debt-asset`, which calls the vault's `socialize-debt`: [2](#0-1) 

The `scaled-debt` passed to socialization is simply the borrower's remaining unpaid scaled debt in that asset — there is no check anywhere in the liquidation path that caps this debt against the vault's `total-assets` before calling `socialize-debt`. A vault can have a small `total-assets` balance relative to one large defaulting position (e.g., a thinly-supplied vault, or a vault where other suppliers have already withdrawn while a bad debt position accrued interest), making `debt-reduction >= old-total-assets` a reachable condition without requiring any privileged action — an ordinary liquidator calling the public liquidation entrypoint is sufficient to trigger it.

### Impact Explanation
- **Victim ≠ attacker**: The party that suffers loss is every holder of that vault's zToken (suppliers) plus anyone who posted that zToken as collateral elsewhere in the protocol — not the liquidator/caller who triggers the socialization.
- **With attacker's transaction**: `lindex` collapses to `0`; `get-total-assets`/`convert-to-assets` return `0` for that vault; the zToken's oracle price resolves to `0` (`docs/oracle.md`, `resolve-ztoken`). Suppliers' redeemable balance goes from `shares * old_lindex / PRECISION` to `0`. Additionally, since the zToken price now reads `0`, any account using that zToken as collateral elsewhere becomes instantly and unfairly liquidatable/undercollateralized, even though its zToken principal was not otherwise reduced.
- **Without attacker's transaction**: In the correct/intended behavior, the write-down should be proportional to the loss (`current-lindex * (old_total_assets - debt_reduction) / old_total_assets`), and if `debt_reduction > old_total_assets`, the deficit should be capped or handled via a separate bankruptcy/insurance mechanism rather than a full-value wipe.
- This is a protocol-insolvency-class impact: complete, permanent loss of unclaimed principal/yield for all suppliers of that vault triggered by a single liquidation event, socialized unfairly across all of them at once — matching the in-scope "socialization charged to all suppliers" / "protocol insolvency" impact classes.

### Likelihood Explanation
The path requires only:
1. A borrower whose debt in one asset, after collateral exhaustion, exceeds the vault's current `total-assets` for that same asset (plausible in vaults with low TVL relative to a single large or heavily interest-accrued position, or after normal supplier withdrawals shrink `assets`).
2. A liquidator (any unprivileged account) calling the standard liquidation entrypoint, which is expected/required behavior of the protocol, not a privileged or DAO action.

No governance compromise, oracle manipulation, or flashloan abuse is needed — an ordinary liquidation of an already-bad-debt position is enough to hit the unguarded branch.

### Recommendation
In `socialize-debt` (all vault contracts, e.g. `v0-vault-stx.clar`, `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-usdc.clar`, `v0-vault-usdh.clar`, `v0-vault-ststxbtc.clar`):
- Cap `debt-reduction` at `old-total-assets` before computing the ratio, and separately track/emit any uncovered shortfall (protocol bad debt) instead of silently forcing `lindex` to `0`.
- Alternatively, floor the write-down so `new-lindex` never drops below a value proportional to the actual loss (i.e., never zero out 100% of value when the loss is, say, 90%), and add explicit bookkeeping/alerting for the case `debt-reduction >= old-total-assets` so it can be handled deliberately (e.g., pausing the vault, socializing the shortfall over time, or triggering an insurance fund) rather than an implicit, instantaneous full wipeout.

### Proof of Concept
1. Vault V has `total-assets = 1,000` (e.g., after several suppliers have withdrawn) and `lindex = 1.20` (accrued interest).
2. Borrower B has an under-collateralized position in V with remaining scaled debt whose current value (`debt-reduction`) computes to `1,500` (exceeds `old-total-assets`), e.g., due to accrued interest/price movement since origination, and B's collateral has been fully seized/liquidated in a prior step of the same liquidation call, leaving no more collateral (`no-collateral-left = true`).
3. Any liquidator calls the market's liquidation entrypoint. `v0-4-market.clar` computes `bad-debt-socialized` and invokes `socialize-debt-asset` → vault `socialize-debt(scaled-amount)` for B's remaining debt.
4. Inside `socialize-debt`, `old-total-assets (1,000) > debt-reduction (1,500)` is false, so `new-lindex` is set to `u0`.
5. `var-set lindex u0` executes. Every other supplier's zUSDC/zSTX/etc. balance in V is now worth `0` when redeemed (`convert-to-assets-preview`), and the zToken's oracle price for V resolves to `0` (`resolve-ztoken`), instantly making any position using that zToken as collateral undercollateralized/liquidatable — even though those suppliers had no relation to borrower B's default.
