## Analysis

The bug class in the report — a signed authorization message with **no deadline field or expiry check**, so it stays perpetually replayable until an unrelated nonce is consumed — has a direct analog in ocore's signed-package mechanism used by AAs (Autonomous Agents) for off-chain-signed orders/authorizations (order books, payment-channel updates, etc.).

### Title
Signed packages (`signed_message`/`is_valid_signed_package`) have no built-in deadline/expiry enforcement, allowing stale signed orders to be executed indefinitely - (File: `signed_message.js`, `formula/evaluation.js`)

### Summary
ocore lets an address sign an arbitrary payload off-chain (a "signed package") that a counterparty later attaches to an AA trigger (`trigger.data.order`, `trigger.data.sentByPeer`, etc.) and validates on-chain via the `is_valid_signed_package()` formula primitive, which calls `signed_message.validateSignedMessage()`. This is functionally the same primitive as a meta-transaction "Forwarder": the signer authorizes an action once, and any third party can later submit it to the AA to execute it, similar to a `ForwardRequest`.

`validateSignedMessage()` explicitly allows an optional `"timestamp"` field on the package (`hasFieldsExcept(objSignedMessage, ["signed_message", "authors", "last_ball_unit", "timestamp", "version"])`) [1](#0-0)  but never reads or validates that field against the current time, `last_ball_timestamp`, or any deadline — there is no expiry/deadline check anywhere in the function [2](#0-1) . The same absence exists in the `is_valid_signed_package` opcode handler in the formula evaluator, which only checks signature validity and (optionally) that `last_ball_unit` is stable — never that the package has not expired [3](#0-2) .

This gap is corroborated by ocore's own bundled reference AA sample, `order_book_exchange.oscript`, which signs orders (price, amounts, assets) and validates them with `is_valid_signed_package`, but literally contains the TODO comment `// to do check expiry` right where a deadline check should be, and never implements it [4](#0-3) . Similarly, `payment_channels.oscript` signs "amount_spent" updates and checks channel/period fields via `is_valid_signed_package`, but performs no expiry check on the signed peer message itself [5](#0-4) .

### Finding Description
A signer (e.g., a market participant placing a limit order, or a payment-channel counterparty attesting to a spent amount) signs a package containing business data plus authors/authentifiers via `signMessage()` in `signed_message.js` [6](#0-5) . Anyone holding this signed package — including a third party who is not the signer — can submit it as AA trigger data at any point in the future. The AA's `is_valid_signed_package()` check will accept it as long as the signature verifies and (when network-aware) `last_ball_unit` is stable, with no mechanism to check the age of the signature or the package's declared `timestamp` [7](#0-6) [8](#0-7) .

Because ocore does not provide this deadline enforcement as a core guarantee, every AA author must reinvent expiry logic manually in oscript, and it's easy to omit — exactly as happened in the shipped `order_book_exchange.oscript` sample.

### Impact Explanation
If an AA (order book, OTC exchange, payment channel, etc.) relies on `is_valid_signed_package` without independently implementing an expiry/deadline check in its oscript (a real and demonstrated failure mode, per the shipped sample), a stale signed order/authorization can be executed long after the signer intended it to be valid. For a price order, this can force execution at a stale price against the signer's current balance, i.e., unauthorized spending/loss of the signer's asset balance held in the AA at a price they no longer agree to. For a payment-channel "sentByPeer" attestation, a stale higher/lower spend amount could be replayed to finalize channel state unfavorably to one party.

### Likelihood Explanation
Medium: exploitation requires an AA design that uses `is_valid_signed_package`/`validateSignedMessage` without its own expiry check — but ocore's own bundled sample AA (`order_book_exchange.oscript`) does exactly this, with an explicit unresolved TODO, showing this is not a hypothetical but the natural/expected usage pattern that developers building on this primitive are likely to follow.

### Recommendation
Add first-class deadline support to the signed-package primitive rather than leaving it entirely to AA authors:
- Extend `validateSignedMessage()` in `signed_message.js` to optionally validate the existing `"timestamp"` field against `last_ball_timestamp` (or current network time) if a max-age/deadline is supplied by the caller.
- Extend the `is_valid_signed_package` formula opcode (`formula/evaluation.js`) to accept an optional expiry/deadline argument and reject expired packages during AA validation, similar to how `last_ball_unit` staleness/existence is already checked.
- At minimum, document prominently that any oscript using `is_valid_signed_package` for authorization purposes (orders, payment-channel updates, etc.) must independently embed and check an expiry/deadline field in `signed_message`, and fix the reference `order_book_exchange.oscript` sample to actually implement the expiry check instead of leaving it as a TODO, since it is used as a template by real AA authors.

### Proof of Concept
1. Alice signs an order via `signMessage()` (as in `test/formula.test.js`'s "signature verification" test) with `signed_message = {sell_asset, buy_asset, sell_amount, price}` and no built-in expiry [9](#0-8) .
2. Time passes (market conditions change materially).
3. Bob (or anyone holding the signed package) submits it as `trigger.data.order1` to the order-book AA.
4. The AA's `if` clause calls `is_valid_signed_package(trigger.data.order1, $order1.address)`, which only checks the signature and stability of `last_ball_unit`, per `signed_message.validateSignedMessage` [4](#0-3) ; because the `// to do check expiry` step was never implemented, the stale order executes at the original signed price regardless of elapsed time.
