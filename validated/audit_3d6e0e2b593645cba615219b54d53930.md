### Title
Cross-repository commit status forgery via unscoped `sha` lookup in `StatusHandler#process` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` looks up commits solely by `sha` across the entire `commits` table, with no scoping to the repository/organization whose webhook secret was used to authenticate the request. An attacker who owns repository R1 (and thus knows W1) can forge a `status` webhook naming a `sha` that happens to exist on victim repository R2's stack, and Shipit will attach the attacker-controlled CI status to R2's commit.

### Finding Description
The broken binding, stated as an equality that the code assumes but never checks: `verified_organization(payload) == organization_owning(matched_commit.stack.repository)`. In reality, `WebhooksController#verify_signature` only proves `HMAC(W_org, raw_body) == X-Hub-Signature`, where `org` is derived from `payload.dig('repository','owner','login')` [1](#0-0) [2](#0-1) . That check authenticates only "this body was signed by organization Org1's secret" — it says nothing about which commits/stacks may be mutated.

Every other handler re-derives the acting repository from the payload and scopes work to that repository's stacks, e.g. `Handler#stacks` uses `Repository.from_github_repo_name(repository_name)&.stacks` [3](#0-2) , and `PullRequest::OpenedHandler#repository` resolves `Shipit::Repository.from_github_repo_name(params.repository.full_name)` before touching any record [4](#0-3) .

`StatusHandler`, however, does not require or use the `repository` field at all in its params schema, and its `process` method queries commits globally: [5](#0-4) 

`Commit.where(sha: params.sha)` matches every `Commit` row in the database with that sha, regardless of which `stack`/`repository` it belongs to, then calls `commit.create_status_from_github!(params)` on each match [6](#0-5) . The `commits` table only enforces uniqueness of `(sha, stack_id)`, not `sha` alone [7](#0-6) , so the same sha can legitimately exist on many unrelated stacks (e.g. content-identical commits from a shared upstream, cherry-picks, or squash merges producing the same tree/commit hash across forks).

Attack: attacker creates/owns repository R1, knows W1. They discover (e.g. by observing R2's public commit history, or a shared/forked history) that R2's `Stack` has a `Commit` with the same `sha` as one in R1. They POST to `/webhooks` with header `X-Github-Event: status`, `X-Hub-Signature: sha1=HMAC(W1, body)`, and body:
```json
{"sha":"<shared_sha>","state":"success","context":"ci/required","repository":{"owner":{"login":"Org1"}}}
```
`verify_signature` succeeds because it only checks W1 against Org1 (the attacker's own org) [8](#0-7) . `Shipit::Webhooks.for_event('status')` dispatches to `StatusHandler`, which finds *all* commits with that sha — including R2's — and writes a forged `Status` (`state: success`, arbitrary `context`) onto R2's commit via `Commit#create_status_from_github!` [9](#0-8) .

### Impact Explanation
A forged status is written for a repository the attacker never authenticated for. This is a "payload for one repository mutating another's stack/commit" per the impact taxonomy. Concretely: `Status#required?`/`#blocking?` are computed from the stack's `deploy_spec` `ci.require`/`ci.blocking` contexts [10](#0-9) , and `Commit#deployable?` is `!locked? && (stack.ignore_ci? || (success? && !blocked?))` [11](#0-10) . If the attacker forges `state: success` for a required/blocking context that R2's real CI hadn't yet reported (or overrides a failing one), the victim commit can become `deployable?` prematurely. `create_status_from_github!` also fires `deployable_status`/`commit_status` hooks and enqueues `ProcessMergeRequestsJob` on relevant state transitions [12](#0-11) , which can drive automatic merges or deploys gated on CI status. This is repeatable against any repository in the installation for any sha the attacker can find/predict, so the blast radius spans all tenants sharing the Shipit instance, not just R1/R2.

### Likelihood Explanation
Preconditions: the attacker needs (a) a repository they control with a known webhook secret (trivial — they can register any repo with the Shipit GitHub App/organization they own), and (b) a `sha` value that also exists as a `Commit` in the victim's stack. Because git shas are content-derived, an attacker forking or observing a victim's public repository trivially obtains identical shas for shared commits, or can otherwise learn a target sha from public commit history/PRs. No GitHub secrets, sessions, or API tokens are required — only a normal, unprivileged POST to `/webhooks`. This is directly repeatable per request.

### Recommendation
Scope `StatusHandler` to the repository asserted in the payload, mirroring every other handler: require `repository.full_name` in the params schema, resolve `Repository.from_github_repo_name(...)`, and restrict the commit lookup to `repository.stacks.flat_map(&:commits)` (or a single joined query on `stacks: { repository_id: repository.id }`) instead of the bare `Commit.where(sha: ...)`.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb
require 'test_helper'

module Shipit
  module Webhooks
    module Handlers
      class StatusHandlerCrossRepoTest < ActiveSupport::TestCase
        test "does not attach a forged status to a commit belonging to an unrelated repository" do
          victim_stack = shipit_stacks(:shipit)
          attacker_stack = shipit_stacks(:soc) # unrelated repository/organization

          shared_sha = "deadbeefdeadbeefdeadbeefdeadbeefdeadbeef"
          victim_commit = victim_stack.commits.create!(
            sha: shared_sha, message: "victim commit",
            authored_at: Time.now, committed_at: Time.now
          )
          attacker_stack.commits.create!(
            sha: shared_sha, message: "attacker commit",
            authored_at: Time.now, committed_at: Time.now
          )

          payload = {
            "sha" => shared_sha,
            "state" => "success",
            "context" => "ci/required",
            "repository" => { "owner" => { "login" => attacker_stack.repository.owner } }
          }

          Shipit::Webhooks::Handlers::StatusHandler.call(payload)

          # EQUALITY CHECK: only the commit belonging to the repository that
          # authenticated the request should be mutated.
          assert_equal 0, victim_commit.reload.statuses.count,
            "attacker-signed webhook must not create a status on a different repository's commit"
        end
      end
    end
  end
end
```
This test currently fails against `app/models/shipit/webhooks/handlers/status_handler.rb`'s unscoped `Commit.where(sha: params.sha)`, demonstrating the cross-tenant write.
