### Title
Stale `Account.owner` lets the previous NFT holder keep spending authority after account transfer - (File: contracts/controller/src/account.rs)

### Summary
The controller records the account owner in a mutable `Account` struct field at account-creation time and never restamps it when the position NFT changes hands. `is_owner_or_delegate`/`require_owner_or_delegate` authorize `borrow`, `withdraw`, and every strategy entrypoint by comparing `caller` against this stored field rather than the live NFT owner, while `require_account_owner` (used by `renew_account`, `add_delegate`, `remove_delegate`) correctly reads the live NFT owner via `storage::account_owner`. After a `position-nft::transfer`/`transfer_from`, the old owner retains full owner-level authority over the account and can drain its collateral or borrow against it; the new owner inherits only an inconsistent state where they cannot even manage delegates.

### Finding Description
`create_account` snapshots `owner` into `Account.owner` at mint time [1](#0-0) . Every spend-side guard resolves authority against that stored field: `is_owner_or_delegate` returns `true` whenever `caller == owner` (the stored field) and only then checks delegation [2](#0-1) , and `require_owner_or_delegate` panics only when that check fails [3](#0-2) . This guard protects `borrow` [4](#0-3) , `withdraw`, `swap_debt`, `swap_collateral`, `repay_debt_with_collateral`, `multiply`, `flash_position`, and `migrate_from_blend` (the `AccountGuard::Migrate`/`Multiply` paths call the same helper) [5](#0-4) .

In contrast, `require_account_owner` consults the live NFT ownership record [6](#0-5) . The position NFT's `transfer`/`transfer_from` are stock permissionless token moves with no hook back into the controller to rewrite `Account.owner`, so the stored field diverges from the true owner on every transfer. The declared invariants even acknowledge "delegate grants from the previous owner go inactive" — but the *owner* grant never does, because it is keyed to the stale field [7](#0-6) .

### Impact Explanation
Theft of user funds and unauthorized spending power, reachable by a single unprivileged address:

1. Attacker creates account via `supply(account_id=0)`, deposits collateral (or sells/transfers an account NFT on a secondary market, a standard Enumerable NFT flow).
2. Attacker calls `position-nft::transfer`/`transfer_from` moving the NFT to a victim buyer (or any recipient).
3. The attacker — still `account.owner` in controller storage — calls `withdraw(account_id, withdrawals, to: Some(attacker))` or `borrow(account_id, borrows, to: Some(attacker))`. `require_owner_or_delegate` sees `caller == account.owner` and passes; collateral leaves to the attacker, and `borrow` can push the account to the solvency boundary, extracting value the new owner believes is theirs.

The buyer's `require_account_owner` reads the NFT owner for delegate/renew management, so the victim cannot even `remove_delegate` the attacker's previously granted delegates — while the attacker retains owner-equivalent spending authority indefinitely. This is the CWE-862 analog: a sensitive action authorized by a stale stored credential rather than the authoritative ownership source.

### Likelihood Explanation
High. `position-nft::transfer`, `transfer_from`, `approve`, and `approve_for_all` are explicitly permissionless holder actions per the declared exception list, so no privileged role is needed. Any account NFT sale, gift, or OTC transfer creates the exploitable window. The attacker needs only their own signature for `caller.require_auth` plus `caller == account.owner`, which remains true forever once set.

### Recommendation
In `is_owner_or_delegate`, resolve the owner from the live NFT record (`storage::account_owner(env, account_id)`) instead of `account.owner`, or drop `Account.owner` entirely and always consult the NFT contract. If the stored field is kept for gas reasons, the NFT contract must invoke a controller callback on every transfer to restamp it, and all delegate entries must be keyed/invalidated consistently. Add a test: transfer the NFT, then assert the old owner cannot `withdraw`/`borrow` and the new owner can.

### Proof of Concept
```rust
// contracts/controller/tests — conceptual PoC
let alice = Address::generate(&env);   // original owner / attacker
let bob   = Address::generate(&env);   // NFT buyer
let to    = Address::generate(&env);   // attacker-controlled sink

// 1. Alice supplies collateral; account minted with account.owner = alice
let account_id = controller.supply(&alice, &0, &SPOKE_ID, &collateral_vec);

// 2. Alice transfers the account NFT to Bob (permissionless holder action)
nft.transfer(&alice, &bob, &account_id);
assert_eq!(nft.owner_of(&account_id), bob);

// 3. Alice still passes require_owner_or_delegate because Account.owner == alice
//    and drains the collateral Bob just bought.
controller.withdraw(&alice, &account_id, &withdraw_all_vec, &Some(to));

// Assert: `to` holds the collateral; Bob's account is empty.
// Optionally: controller.borrow(&alice, &account_id, &borrows, &Some(to))
// succeeds up to the solvency bound, leaving Bob's account with debt.
```

Uncertainty note: the search found no code path that restamps `Account.owner` on NFT transfer and the NFT contract is stock OpenZeppelin Enumerable with no transfer callback to the controller, but I could not exhaustively read every storage module; if some hook updates the field on transfer, this finding collapses.

```rust
pub(crate) fn is_owner_or_delegate(
    env: &Env,
    account_id: u64,
    caller: &Address,
    owner: &Address,
) -> bool {
    if caller == owner {
        return true;
    }
    let active_manager =
        storage::get_position_manager(env, caller).is_some_and(|config| config.is_active);
    active_manager && storage::get_delegates(env, account_id, owner).contains(caller)
}
```
