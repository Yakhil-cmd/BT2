Webhook Signature Verified Against Attacker-Controlled Organization While Payload Fields Selecting the Target Repository/Stack Go Unchecked - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App (and therefore which `webhook_secret`) to use for HMAC verification based on `repository_owner`, a value read directly from the untrusted JSON payload (`params.dig('repository','owner','login')`), and then hands the *entire same payload* to the event handlers, which independently re-read `repository.full_name` to resolve the `Stack`/`Repository` that gets acted upon.

### Finding Description
In a multi-organization Shipit deployment, `Shipit.github(organization:)` (`lib/shipit.rb:170-181`) resolves a distinct `GitHubApp` instance per organization, each with its own `webhook_secret` (`lib/shipit/github_app.rb:44-57`). The webhook signature check is: [1](#0-0) 

`repository_owner` is derived purely from the JSON body: [2](#0-1) 

This is the *only* value covered by the signature-selection logic. The actual handler logic that determines which `Stack`/`Repository` receives the event uses a *different* field from the same untrusted body, `repository.full_name`: [3](#0-2) [4](#0-3) 

Because `Repository.from_github_repo_name` splits `owner/name` independently from `repository.owner.login`: [5](#0-4) 

nothing enforces `repository.owner.login == repository.full_name.split('/').first`. An attacker who is an admin/owner of *their own* organization ("attacker-org", with a GitHub App installed on Shipit and a known `webhook_secret`) can register/install a GitHub App for that org (per the documented multi-org setup in `docs/setup.md`), then send a forged webhook POST to `/webhooks` with:
- `repository.owner.login = "attacker-org"` (so `verify_signature` picks the attacker's own `GitHubApp`/`webhook_secret`, which the attacker knows and can therefore produce a valid `X-Hub-Signature` for), and
- `repository.full_name = "victim-org/victim-repo"` (so the handler's `stacks`/`Repository.from_github_repo_name` lookup targets a completely different, victim organization's `Stack`).

The binding broken: the organization whose credentials authenticate the request (`repository_owner`, checked against a signing secret) ≠ the repository/organization whose `Stack` is actually written to by the handler (`repository.full_name`). This is a direct structural analog of the reported bug class: a computed/verified quantity (margin computed from an unverified transient amount) diverging from the actual value that is subsequently acted upon, here a payload field used for authentication diverging from the payload field used for effecting a repository-scoped write.

### Impact Explanation
Handlers reachable this way include `PushHandler`, which calls `stack.sync_github(expected_head_sha: params.after)` for every unarchived stack of the resolved (victim) repository/branch — an unauthenticated actor from an unrelated org can trigger sync jobs and revision-fetch behaviour for a victim's stacks. `StatusHandler` similarly attaches attacker-chosen commit status/state/description to a victim commit purely by SHA match, with no repository-ownership binding check at all: [6](#0-5) 

`PullRequest::OpenedHandler`/`LabeledHandler`/etc. resolve `repository` via `params.repository.full_name` and can create/archive/unarchive Review Stacks for a victim repository. This crosses a repository trust boundary using credentials belonging to a different, attacker-controlled organization — matching "cross-repository writes" impact criteria, since state belonging to a repository the attacker's GitHub App/org has no legitimate relationship with is mutated using a signature the attacker legitimately possesses only for their own org.

### Likelihood Explanation
Requires only that the target Shipit instance is configured with multiple GitHub organizations (the documented `github: <org>: ...` multi-tenant schema in `docs/setup.md` / `lib/shipit.rb:170-200`) and that the attacker controls (or can install) a GitHub App on at least one organization Shipit trusts. No repository write access, GitHub identity impersonation of the victim, or Shipit session/API token is needed — only the ability to sign a payload with a webhook secret the attacker legitimately possesses for their *own* onboarded organization, then substitute the `repository.full_name` field. This is a plausible, realistic misconfiguration path in any multi-org Shipit deployment, which the docs explicitly support.

### Recommendation
Bind signature verification to the same repository identity that handlers act on. Concretely: derive `repository_owner` and the effective handler repository from the same normalized field (`repository.full_name`), or re-verify inside `Handler#stacks`/`Repository.from_github_repo_name` that `payload.dig('repository','owner','login')` matches the owner segment of `payload.dig('repository','full_name')` before doing any lookup, rejecting mismatches with 422.

### Proof of Concept
1. Attacker registers/owns GitHub org `attacker-org`, installs a GitHub App on it, and Shipit is configured (per `docs/setup.md` multi-org schema) with `github.attacker-org.webhook_secret = S` (attacker knows `S`).
2. Attacker crafts JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "deadbeef",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<hmac_sha1(S, body)>` and POSTs to `/webhooks` with `X-Github-Event: push`.
4. `WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-30,59-62`) computes `repository_owner = "attacker-org"`, fetches `Shipit.github(organization: "attacker-org")`, and the signature verifies successfully.
5. `Webhooks.for_event('push')` dispatches to `PushHandler`, whose `Handler#repository_name` (`app/models/shipit/webhooks/handlers/handler.rb:36-38`) reads `payload.dig('repository','full_name')` = `"victim-org/victim-repo"`, resolving and acting on the victim's `Stack` (`app/models/shipit/webhooks/handlers/push_handler.rb:12-17`) despite the signature only proving control over `attacker-org`.
