### Title
A single broken/malicious submodule reference permanently blocks all future syncs (persistent DOS) - ([File: main.go])

### Summary
`git-sync`'s reconciliation loop is directly analogous to `FundsAllocator`'s "iterate over N sub-resources, abort the whole operation if one fails" pattern. In `git-sync`, the equivalent of an "adapter" is a git submodule referenced by the tracked commit. `configureWorktree` unconditionally runs `git submodule update --init [--recursive]` for the target commit, and any failure of that single command (a broken/unreachable/malicious submodule URL, a submodule host that rejects the protocol, rate-limits, or is compromised) aborts the entire sync for that commit, with no way to skip just the offending submodule.

### Finding Description
`SyncRepo` creates a new worktree for the remote hash and calls `configureWorktree` on it before publishing the symlink: [1](#0-0) 

Inside `configureWorktree`, submodule initialization is a single, all-or-nothing git invocation: [2](#0-1) 

If that command fails (e.g., because one submodule's remote is unreachable, deliberately rejects `submodule.file.allow`, is deleted/renamed, or otherwise errors), `configureWorktree` returns an error, `SyncRepo` returns an error, and the outer sync loop treats this as a full sync failure: [3](#0-2) 

Because `git.ref` (branch/tag) still resolves to the same `remoteHash` as long as the upstream repo doesn't change, **every subsequent sync attempt will re-fetch the identical commit and fail on the identical submodule error** — there is no mechanism to bypass, skip, or force-remove the failing submodule, unlike the DynamoFinance remediation which added a bypass for a single failing adapter. This is the exact bug class described in the report: one bad sub-resource in a fan-out loop stalls the entire top-level operation indefinitely.

Two failure modes result, both matching the report's DOS pattern:
- If `--max-failures` is reached, the process calls `os.Exit(1)`: [4](#0-3) . In a Kubernetes sidecar this becomes a permanent CrashLoopBackOff for that pod, since the same commit/submodule will be re-fetched and fail identically after every restart.
- If `--max-failures` is negative (unlimited retries), the loop retries forever without ever advancing, so the mount point behind `--link` is permanently frozen at the last good commit and never sees new content again, since a repo author cannot “skip” one submodule the way `FundsAllocator`’s adapters could originally not be skipped.

### Impact Explanation
Any repository maintainer (or an attacker who can influence the tracked ref/commit, e.g., via a compromised upstream, an approved PR merge, or a malicious submodule host takeover) can permanently deny the whole `git-sync` sidecar from ever syncing again by referencing a submodule that reliably fails to clone/update. This is a persistent sync denial: the application container consuming the volume never receives further updates, and the git-sync container itself can enter permanent crash/backoff, matching the "permanently DOS entire vault" impact from the reference report, translated to git-sync's context (repo replaces vault, submodule replaces adapter).

### Likelihood Explanation
This requires only the ability to get a commit merged/tracked that references a submodule pointing at a URL/host that will predictably fail (deleted repo, protocol not allowed, auth required but not configured, rate-limited, or hostile server that hangs/errors). No malicious operator of git-sync itself, no leaked credentials, and no mocked-only environment are needed — this is reachable purely from the content of an attacker-influenced upstream commit that git-sync is configured to track, which fits the required "attacker-pushed commit/ref" threat model.

### Recommendation
Make submodule failures degradable rather than fatal to the whole sync: e.g., allow `--submodules` failures to be treated as warnings when a per-submodule bypass/allow-list is configured, or add an emergency override (akin to the DynamoFinance fix) that lets an operator explicitly exclude a specific submodule path from `git submodule update`, so a single broken submodule doesn't block publishing of the rest of the tree. At minimum, document and alarm clearly that a single failing submodule can permanently freeze `--link` at a stale commit indefinitely when `--max-failures` is unbounded.

### Proof of Concept
1. Configure `git-sync --repo=<upstream> --submodules=recursive --root=... --link=link`.
2. In the upstream repo, add a submodule entry (`.gitmodules`) pointing to a URL that will reliably fail (e.g., a deleted repo, or a host requiring auth not provided via `--username`/`--password-file`), then commit and push.
3. Observe that `configureWorktree`'s `git submodule update --init --recursive` step fails every sync cycle: [5](#0-4) .
4. Observe the outer loop: `failCount` increments every cycle at [3](#0-2) ; once `--max-failures` is hit, the process exits (`os.Exit(1)`), or if unlimited, the loop spins forever, and `--link` never advances past the last good commit — there is no flag or code path to skip just the broken submodule and continue publishing the rest of the tree.
