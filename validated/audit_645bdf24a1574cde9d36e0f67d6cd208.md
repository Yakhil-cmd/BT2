### Title
Panic-induced batch-wide liquidation DoS via `unwrap-panic` on missing asset in `process-debt-asset` - (File: mainnet/contracts/market/v0-4-market.clar)

### Summary
`liquidate-multi` intentionally uses a bare `map` over `call-liquidate` so that a single failing position (returned as an `err` response) does not revert the whole batch, per its own doc comment: "Failed liquidations return error codes but don't revert entire batch." [1](#0-0)  That guarantee only holds for ordinary `asserts!`/`try!`-generated `(err ...)` responses. It does **not** hold for Clarity runtime panics, and the liquidation path contains one: `process-debt-asset` blindly does `(unwrap-panic (find-asset debt-aid assets))` [2](#0-1)  assuming `debt-aid` is always present in the caller-supplied `assets` list derived from the borrower's *current* position mask. If that assumption is violated — e.g., because the borrower altered their position (repaid/removed that specific debt asset) between the moment a keeper assembled the batch and the moment the batched transaction executes on-chain — `find-asset` returns `none`, `unwrap-panic` throws a runtime error, and the **entire** `liquidate-multi` transaction aborts, taking down every other unrelated liquidation bundled in the same call. This mirrors the nimiq-primitives report: a value that passes upstream checks (the debt asset is a legitimately registered market asset, checked at `get-asset` [3](#0-2) ) but violates a deeper, unstated invariant (must still be part of that specific borrower's live debt set) triggers an `unwrap`-style panic instead of a graceful error, and that panic propagates outward to abort a shared batch operation rather than just the offending item.

### Finding Description
`liquidate` builds the borrower's asset list from the mask *at call time*: `(assets (get-assets mask))` [4](#0-3) , where `mask` comes from `get-liquidation-position borrower` evaluated at the top of the same call [5](#0-4) . This list only contains assets currently active in the borrower's position. `process-debt-asset` is then invoked with the liquidator-selected `debt-aid` (derived from the `debt-ft` trait argument) and unconditionally does:

```
(debt-asset-info (unwrap-panic (find-asset debt-aid assets)))
``` [2](#0-1) 

There is no `asserts!`/`unwrap!`-with-error-code guard here — only a hard panic. Because `debt-ft`/`debt-aid` is only validated against the *global* asset registry (`get-asset`) and not against the borrower's live debt set before this point, any mismatch between the batch's precomputed `debt-ft` and the borrower's on-chain debt state at execution time reaches this `unwrap-panic` and aborts the transaction.

`liquidate-multi` is built specifically to tolerate individual position failures without reverting the whole batch:
```
(define-public (liquidate-multi (positions (list 64 {...})))
  (ok (map call-liquidate positions)))
``` [6](#0-5) 

But Clarity's runtime abort semantics for `unwrap-panic` are not caught by `map`; a panic anywhere inside any mapped call unconditionally aborts and rolls back the entire enclosing transaction, including all other bundled `call-liquidate` invocations. This directly contradicts the function's documented behavior and safety assumption.

### Impact Explanation
Attacker: any borrower who is one of the entries being liquidated in a keeper's `liquidate-multi` batch. Victim: every *other* borrower and liquidator whose independent, legitimately-liquidatable positions are bundled in that same batch transaction, plus lenders relying on timely liquidation to cap bad debt.

Without the attacker's action: the keeper submits `liquidate-multi` with N positions; all N liquidations that are genuinely underwater succeed, seizing collateral and repaying debt as expected.

With the attacker's action: the attacker (one of the N borrowers) front-runs the batch — e.g., by repaying or otherwise removing the exact debt asset the keeper targeted for their position in the same block — so that by execution time their `debt-aid` is no longer in `assets`. `process-debt-asset`'s `unwrap-panic` fires, the whole `liquidate-multi` transaction aborts, and **none** of the N positions get liquidated in that block, even though most were unrelated to the attacker and remain genuinely undercollateralized. This is an ordering dependence between the attacking borrower and the other bundled borrowers/lenders in the same block, and it results in temporary freezing of the protocol's ability to seize collateral/repay debt for those unrelated positions, delaying bad-debt cleanup and increasing insolvency risk for lenders during the affected block(s).

### Likelihood Explanation
Any borrower can trivially trigger the mismatch by repaying or adjusting their own debt in the same block a keeper's batch is pending in the mempool — no special privileges or DAO/oracle compromise needed, and Stacks/Clarity mempool visibility makes front-running keeper batches straightforward. The condition only requires the keeper's precomputed `debt-ft` to no longer match the borrower's live debt set at execution time, which is a normal race, not an exotic edge case. Keepers batching multiple independent liquidations (to save fees / avoid front-running per the code's own comment about "prevent[ing] front-running attacks that prevent bad debt socialization" [7](#0-6) ) are the expected real-world usage pattern this bug undermines.

### Recommendation
Replace the panicking lookup in `process-debt-asset` with a graceful, response-typed check, e.g. `(unwrap! (find-asset debt-aid assets) ERR-ASSET-NOT-IN-POSITION)`, and ensure `call-liquidate` inside `liquidate-multi` catches/normalizes any such error into an `(err ...)` entry in the resulting list rather than letting a panic propagate. Audit all other `unwrap-panic` call sites reachable from `liquidate`/`liquidate-multi` (e.g. `scale-debt-for-liquidation` and the `rem-borrow-index` lookup [8](#0-7) [9](#0-8) ) for the same class of issue, since any of them can similarly abort an entire liquidation batch.

### Proof of Concept
1. A keeper observes borrowers B1 (attacker) and B2 (victim) are both liquidatable and submits `liquidate-multi` with two positions: one targeting B1 with `debt-ft = X`, one targeting B2 with `debt-ft = Y`.
2. Before the keeper's transaction is mined, B1 submits a `repay` (or otherwise removes) all of asset `X` debt, changing B1's mask so `X` is no longer part of B1's active debt set.
3. The keeper's `liquidate-multi` transaction executes: for B1's entry, `get-assets mask` no longer contains asset `X`; `process-debt-asset` calls `(unwrap-panic (find-asset X assets))`, which returns `none` and panics.
4. The panic aborts the entire transaction; B2's otherwise valid liquidation (and any other bundled positions) is rolled back along with B1's, despite B2 being fully unrelated to B1's action.
