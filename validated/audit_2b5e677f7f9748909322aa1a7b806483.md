### Title
Unconfined swap routes can hide arbitrary caller-authorized token transfers - (File: contracts/controller/src/strategies/swap.rs)

### Summary

The controller treats the user-supplied `StrategySwap` payload as opaque bytes and forwards it to the configured router without confining the route to trusted pool, token, or venue contracts. [1](#0-0) [2](#0-1) 

A malicious route can therefore place attacker-controlled code beneath a victim’s authorized controller call and request an unrelated `token.transfer(victim, attacker, amount)`, which an honest simulation records as a child of the victim’s authorization tree. [3](#0-2) 

### Finding Description

`swap_tokens` requires only that the route be non-empty, obtains the configured router, authorizes one exact controller-to-router input transfer, and then calls `router.execute_strategy(controller, amount_in, swap)`. [4](#0-3) 

The controller does not decode `swap`, bound its hop contracts, or require the router to confine them to an allowlist before invocation. [5](#0-4) [6](#0-5) 

The vulnerable path is reachable through `swap_collateral(caller, account_id, current, amount, new, swap)`, which authenticates the caller/account owner and forwards the supplied route after withdrawing collateral. [7](#0-6) 

The same opaque-route boundary is also used by `swap_debt` and `multiply`. [8](#0-7) [9](#0-8) 

The harness demonstrates the confinement failure directly: the router double invokes a payload-selected `hop_pool`, and that pool calls `transfer(victim, attacker, amount)` on a token unrelated to the swap. [10](#0-9) 

Simulation records that unrelated transfer as a child authorization under the victim’s `swap_collateral` invocation, and signing that poisoned tree makes the transfer execute. [11](#0-10) [12](#0-11) 

### Impact Explanation

An unprivileged attacker can steal any spendable token in a victim’s wallet, including assets that are not listed by the lending protocol and are outside the swap’s measured input/output accounting. [13](#0-12) [14](#0-13) 

The malicious route can still return a fair-looking output, so the controller’s positive-output and post-operation risk checks do not bound the unrelated wallet transfer. [15](#0-14) [16](#0-15) 

### Likelihood Explanation

Exploitation requires the victim to submit an attacker-crafted route and sign the simulated authorization tree containing the extra transfer. [17](#0-16) 

That prerequisite is realistic for opaque quote payloads supplied through a compromised quote service, malicious interface, or prompt-injected agent because the controller accepts arbitrary bytes rather than a independently validated route. [1](#0-0) [18](#0-17) 

The demonstrated transaction preserves the expected lending outcome while emptying the unrelated wallet token, making the malicious child authorization the only visible anomaly. [19](#0-18) 

### Recommendation

Constrain executable route hops to protocol-approved venue and token contracts before invoking external code, and reject payload fields that can substitute arbitrary contract addresses. [20](#0-19) 

At minimum, the router boundary should expose a decoded execution manifest for simulation and enforce that every contract invocation belongs to an allowlisted venue adapter, while clients refuse any authorization child other than the single expected input transfer. [21](#0-20) 

### Proof of Concept

1. Victim has collateral in a lending account and holds an unrelated wallet token. [22](#0-21) 
2. Attacker deploys a malicious “pool” configured with `(victim, wallet_token, attacker, amount)`. [23](#0-22) 
3. Attacker supplies `swap` bytes naming that pool while also specifying a normal token-in, token-out, and sufficient `min_out`. [24](#0-23) 
4. Victim calls `swap_collateral(caller=victim, account_id, current=USDC, amount, new=ETH, swap=malicious_bytes)`. [25](#0-24) 
5. The router invokes the payload-selected pool, which performs `token.transfer(victim, attacker, amount)` on the unrelated token. [26](#0-25) [27](#0-26) 
6. Simulation places that theft beneath the victim’s `swap_collateral` authorization; if the victim signs the returned tree, the unrelated balance moves to the attacker while the expected swap output is deposited. [28](#0-27) [12](#0-11)

That bound covers the controller's own grant only. The router calls the pool
and token addresses its payload names and keeps no allowlist of them, so a
route can put third-party code on the call stack below the caller's
authorization. A token transfer that such code makes from the caller is
recorded by an honest simulation as a child of the caller's authorization
entry, and it executes if the caller signs that tree. The loss is then the
caller's wallet, not the routed amount, and neither the payload minimum nor the
final risk gate bounds it. An honest swap strategy gives the caller no child
entry, and a direct router swap gives exactly one input transfer. A client must
decode the route it signs and refuse an authorization tree with any other
child. The direct `execute_strategy` path has the same exposure for every swap
user.

#[test]
fn simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry() {
    let s = Scene::new();
    let route = s.route_through_pool_stealing(WALLET_BALANCE);

    // `simulateTransaction` runs recording mode with non-root auth disabled.
    s.t.env.mock_all_auths();
    s.try_swap(&route)
        .expect("recording mode accepts the route");
    let recorded = s.t.env.auths();
    std::println!("recorded auth tree = {recorded:#?}");

    let stolen_transfer = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.wallet_token.clone(),
            symbol_short!("transfer"),
            (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),
        )),
        sub_invocations: std::vec![],
    };
    let poisoned_root = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.t.controller.clone(),
            Symbol::new(&s.t.env, "swap_collateral"),
            s.swap_args(&route),
        )),
        sub_invocations: std::vec![stolen_transfer],
    };
    assert_eq!(recorded, std::vec![(s.alice.clone(), poisoned_root)]);

    assert_eq!(s.wallet(&s.alice), 0);
    assert_eq!(s.wallet(&s.attacker), WALLET_BALANCE);
    assert_eq!(s.t.supply_balance_raw(ALICE, "ETH"), FAIR_OUT_ETH);
