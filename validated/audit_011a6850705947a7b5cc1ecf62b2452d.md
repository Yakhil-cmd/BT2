### Title
Membership-webhook trust binding lets an unauthenticated organization write to `Shipit.github_teams` authorization data of an unrelated organization - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks the GitHub App/secret used to authenticate a webhook delivery based on the organization login embedded in the payload itself, then hands the *same* payload to `MembershipHandler`, which writes to a globally-keyed `Team` record using only `team.id` (the GitHub team id), with no re-check that the authenticated organization matches the organization that owns that team. If any configured GitHub organization has no `webhook_secret` set (an explicitly supported, documented configuration - see `config/secrets.development.shopify.yml` and `test/dummy/config/secrets_double_github_app.yml`'s `OrgTwo`), signature verification for that organization is a no-op, letting anyone forge a `membership` event for it and mutate the membership of a `Team` belonging to a completely different, properly-secured organization used for `Shipit.github_teams` authorization.

### Finding Description
`verify_signature` resolves the app/secret to check against using an attacker-supplied field in the JSON body: [1](#0-0) [2](#0-1) 

```
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

`verify_webhook_signature` explicitly bypasses HMAC verification whenever no `webhook_secret` is configured for the resolved organization: [3](#0-2) 

```
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
```

`webhook_secret` is optional per the setup docs and multiple fixtures/configs ship with it unset (`OrgTwo`, `someothergithuborg`), so this is a documented, supported deployment state, not a misconfiguration outside the engine's scope.

Once `verify_signature` passes (trivially, for the secret-less org), the exact same `raw_post` is parsed again and dispatched to `Shipit::Webhooks::Handlers::MembershipHandler`: [4](#0-3) 

`MembershipHandler` resolves the `Team` to mutate purely by the numeric GitHub `team.id`, and the `organization.login` field is only used to *populate* a newly created team, not to scope lookups of an existing one: [5](#0-4) 

```
def process
  team = find_or_create_team!
  member = User.find_or_create_by_login!(params.member.login)
  case params.action
  when 'added'
    team.add_member(member)
  ...
def find_or_create_team!
  Team.find_or_create_by!(github_id: params.team.id) do |team|
    team.github_team = params.team
    team.organization = params.organization.login
  end
end
```

`Team#add_member` directly appends the member with no re-verification of organization ownership: [6](#0-5) 

Team membership drives application-wide authorization: `force_github_authentication` grants access whenever `current_user.authorized?` and lists `Shipit.github_teams` as the source of truth for who may use the app/deploy: [7](#0-6) 

**Trust binding broken:** the equality the signature check is supposed to enforce is `organization authenticated by verify_signature == organization whose Team membership is mutated`. Because the lookup key (`github_id`) is global and unscoped by the authenticating organization, and because the authenticating organization can be one with no secret at all, an attacker satisfies `organization authenticated (unverified secret-less org) != Team.organization (target org's authorization team)` while still passing all the engine's checks.

### Impact Explanation
An unauthenticated attacker who knows (or brute-forces/enumerates) the numeric GitHub `team.id` of a team listed in `Shipit.github_teams` for a *different, properly-secured* organization can send a forged `membership` webhook "from" any organization configured without a `webhook_secret`, and add an arbitrary GitHub login as a member of that authorization team. Since `authorized?`/`force_github_authentication` grants app-wide access based on membership of `Shipit.github_teams`, this is a direct escalation into `Shipit.github_teams` authorization - one of the explicitly accepted High-severity impacts - without any Shipit session, API token, webhook secret, or privileged account, satisfying the deployment-trust-binding class described in the report (organization authenticated vs. resource actually written).

### Likelihood Explanation
Exploitability only requires: (1) the deployment has at least one GitHub organization configured in `Shipit.github`/`config/secrets*.yml` without a `webhook_secret` (a documented, supported configuration, not a misconfiguration excluded by scope), and (2) the attacker can determine the numeric `github_id` of a target team (discoverable via the public GitHub API for any team whose org allows team listing, or via the target org's own `membership` events if reused). No repository write access, GitHub App key, or existing Shipit credential is needed - only network access to the public `/webhooks` endpoint, which is unauthenticated by design.

### Recommendation
- Scope the `Team.find_or_create_by!` lookup in `MembershipHandler#find_or_create_team!` by both `github_id` and `organization` (the organization authenticated in `verify_signature`), rejecting mismatches instead of silently reusing an existing team belonging to a different organization.
- Require `webhook_secret` to be present for every configured GitHub organization, or explicitly disallow processing of authorization-sensitive events (`membership`) for organizations without a configured secret.
- Cross-check that `params.organization.login` in the payload matches the `repository_owner`/organization resolved during `verify_signature` before mutating `Team`/`Membership` records.

### Proof of Concept
1. Deploy Shipit with two configured organizations: `SecureOrg` (has `webhook_secret` set, owns a GitHub team `T` with `github_id = 555` that is listed in `Shipit.github_teams` for authorization) and `OpenOrg` (no `webhook_secret` configured), as supported by `config/secrets.development.shopify.yml`/`test/dummy/config/secrets_double_github_app.yml`.
2. Attacker POSTs to `/webhooks` with header `X-Github-Event: membership` and body:
```json
{
  "action": "added",
  "team": { "id": 555, "name": "x", "slug": "x", "url": "https://x" },
  "organization": { "login": "OpenOrg" },
  "member": { "login": "attacker-github-login" }
}
```
No valid `X-Hub-Signature` is required because `Shipit.github(organization: "OpenOrg").verify_webhook_signature` returns `true` unconditionally (`lib/shipit/github_app.rb:77`).
3. `WebhooksController#create` dispatches to `MembershipHandler`, which does `Team.find_or_create_by!(github_id: 555)` - finding `SecureOrg`'s existing team `T` - and calls `team.add_member(User.find_or_create_by_login!("attacker-github-login"))`.
4. The attacker's GitHub account is now a member of a team in `Shipit.github_teams`, granting them authorization to use/deploy the Shipit instance despite never being an actual member of `SecureOrg`'s GitHub team.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
