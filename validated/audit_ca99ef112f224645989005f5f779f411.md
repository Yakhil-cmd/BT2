## Analysis

The external SonarQube advisory is a CWE-532 "insertion of sensitive information into a log file" bug: values meant to remain confidential (encrypted settings) ended up written to plaintext logs. The closest reachable analog in `ocore--018` is in the device-messaging layer (`device.js`), which handles peer-to-peer wallet/AA correspondence (signing requests, private payment chains, textcoin claims, shared-address invitations, etc.). This code path is triggered whenever *any* correspondent device (an unprivileged peer that the user has merely exchanged pairing info with) sends a message, or whenever the local wallet sends one — both decrypted plaintext content and the full outgoing JSON payload are unconditionally written to `console.log`, which in all standard deployments (headless wallets, hubs) is redirected to a persistent log file.

### Title
Device message plaintext (including private payment chains and signing payloads) is written to logs in cleartext - (File: device.js)

### Summary
`device.js` logs the full decrypted content of every incoming device message and the full plaintext of every outgoing device message before encryption, unconditionally via `console.log`. These messages routinely carry sensitive material: private-asset payment chains (amounts, addresses, blinding factors), `sign` requests carrying `private_payloads` and unsigned units, and other wallet-to-wallet correspondence.

### Finding Description
In `decryptPackage`, after successfully decrypting an inbound device package, the plaintext is dumped in full: [1](#0-0) 

Symmetrically, `reliablySendPreparedMessageToHub` logs the entire outbound JSON body (subject + body, which for `sign` messages includes `private_payloads` per `wallet_general.js`'s `sendOfferToSign`, and for `private_payments` includes full private chains with blinded amounts and addresses) before it is even encrypted: [2](#0-1) 

The same pattern of dumping private-payment/asset content appears elsewhere, e.g. `indivisible_asset.js` logging spend proofs and stored outputs, `wallet.js` logging the raw private chain being saved, and `wallet_general.js` sending private payloads whose content is subsequently logged on the sending side: [3](#0-2) [4](#0-3) 

None of this data is intended to be public — it's specifically kept out of the hub-visible `encrypted_package` (`device.js:700-701` marks that only the encrypted blob is "visible and verifiable by the hub"), yet it's placed in cleartext into local application logs.

### Impact Explanation
Any pairing correspondent (a completely unprivileged party from the recipient's perspective, since pairing only requires an out-of-band exchange of a pairing code) can trigger these log lines by simply sending device messages — a `sign` request, a `private_payments` push, or any other subject handled by `handleMessageFromHub`. Because Node.js processes (headless wallets, hubs) typically have stdout/stderr redirected to a persistent log file, this means:
- Confidential private-asset transaction details (amounts, addresses, blinding factors that are supposed to stay hidden from anyone but the parties to the private chain) end up readable by anyone with log access.
- Multisig/shared-address `sign` payloads, which can include the full unsigned unit and any embedded secrets needed for co-signing, are persisted in cleartext logs.
- An attacker who gains read access to log files (a much lower bar than gaining access to the wallet's live memory or database) can reconstruct private payment history or interfere with pending multi-party signing flows, undermining the confidentiality guarantees of "private" assets that the protocol explicitly tries to preserve.

### Likelihood Explanation
High likelihood of triggering: the logging happens unconditionally on every decrypted/sent device message, with no feature flag or verbosity gate, and device messages can be sent by any paired correspondent without further authorization checks at this layer.

### Recommendation
Remove or gate behind an explicit debug-only, opt-in flag all `console.log` statements in `device.js` (`decryptPackage`, `reliablySendPreparedMessageToHub`, `createEncryptedPackage`) and in `indivisible_asset.js`/`wallet.js` that print decrypted message bodies, private payment chains, spend proofs, or private payloads. If debug logging is needed, redact/hash sensitive fields (amounts, addresses, blinding, private_payloads) before logging, and ensure such logs are never enabled by default in production deployments.

### Proof of Concept
1. Pair two wallets/devices (standard, low-privilege operation).
2. From device B, send device A any message via `sendMessageToDevice` (e.g., a `private_payments` chain or a `sign` request with `private_payloads`).
3. On device A's host, inspect the console/log output: `reliablySendPreparedMessageToHub` (when A replies) and `decryptPackage` (when A receives) both print the full plaintext JSON body, including any private asset chain data or private_payloads, to stdout.
4. If stdout is captured to a log file (typical for headless wallet/hub deployments), that sensitive data now persists in cleartext on disk, accessible to anyone with log-file read access.
