### Title
`security/scan` status webhook updates commits across unrelated stacks/repositories due to unscoped SHA lookup - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` resolves the target of a `status` webhook with `Commit.where(sha: params.sha)`, a bare SHA lookup with no `stack_id` or repository filter. Since `Commit` rows are stored per-stack `belongs_to :stack` [1](#0-0)  and different stacks (including different repositories that happen to share history, e.g. forks/mirrors, or multiple stacks/environments for the same repo) can contain rows with an identical SHA, a single authenticated webhook event fans out and mutates commit status on every stack whose commit table happens to contain that SHA.

### Finding Description
The broken binding is: **the stack/repository that authenticated a `status` webhook == the stack/repository whose commit status is mutated.** `StatusHandler#process` breaks this by iterating `Commit.where(sha: params.sha)` with no scoping to the repository that produced/authenticated the event:

```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [2](#0-1) 

`Commit` is a per-stack record (`belongs_to :stack`) [1](#0-0) , and `create_status_from_github!` writes a `Status` scoped to `stack_id`, which is then consumed by `deployable?`/`blocked?`/merge scheduling for that specific stack: [3](#0-2) [4](#0-3) [5](#0-4) .

`WebhooksController#verify_signature` authenticates the payload only against the GitHub App/org config resolved from `repository_owner` in the payload — it establishes that "some repo owned by this org sent this event," not "this specific stack/repo is the only one affected": [6](#0-5) . Nothing in `StatusHandler` cross-checks the payload's `repository.full_name` against the `Commit`/`Stack` being updated, so once a `status` event is validly signed for the attacker's own repository/organization, its effect propagates to **every** `Commit` row sharing that SHA, including rows belonging to unrelated stacks the attacker never authenticated for.

Exploit flow: with `review_stacks_enabled true, allow_all` on the victim stack, any external PR auto-provisions a review stack that ingests commits (and runs `shipit.yml`). Because `security/scan` is a required status context, the victim stack's `deployable?`/merge/block behavior is driven purely by the presence of a matching `success` status row for a `Commit` with the target SHA — a row that `StatusHandler` will happily create for *any* commit that matches the SHA, regardless of which repo/stack originated the authenticated webhook. An attacker who can trigger a real, validly-signed `status` event (e.g. via their own PR/fork/Action) for a SHA that also exists as a `Commit` row on the victim's stack (common when stacks share underlying repo history, forks, or multiple environment stacks for the same repository) can flip the `security/scan` context to `success` on the victim's stack commit, unblocking deploy/merge without ever authenticating against the victim stack.

### Impact Explanation
A payload authenticated for one repository/stack mutates `Status`/deployability state on another stack it never authenticated for — this is the "payload for one repository mutating another's stack, commit ... or an unauthorized deploy, rollback or merge" Critical class. Combined with `review_stacks_enabled true, allow_all` (auto-provisioned review stacks executing `shipit.yml`), a forced `success` on a required check can trigger continuous deployment / merge scheduling (`stack.schedule_merges`, `schedule_continuous_delivery`) [7](#0-6) [8](#0-7) , leading toward command execution on the deploy host through the normal deploy/task pipeline. The blast radius spans any stack whose `Commit` table shares a SHA with the attacker-controlled event, i.e. cross-tenant within a Shipit installation.

### Likelihood Explanation
Requires: (1) a validly signed `status` webhook reaching Shipit for a repository/org the attacker legitimately controls (a PR, fork, or their own repo with the shared GitHub App installed), and (2) a SHA collision between the attacker's authenticated repository's commit history and the victim stack's commit table — realistic when stacks track the same repository across environments, or when repos are forks/mirrors sharing base commits. No Shipit secrets, sessions, or API tokens are needed; the attacker only needs the ability GitHub already grants any repo owner/collaborator: to make GitHub emit a genuinely signed `status` event.

### Recommendation
Scope the lookup in `StatusHandler#process` to the repository that authenticated the event, e.g. resolve the `Stack`(s) matching `params.dig('repository', 'full_name')` first, then restrict `Commit.where(sha: params.sha, stack_id: matching_stack_ids)` instead of a bare cross-table SHA match.

### Proof of Concept
Minitest plan (no live GitHub):
1. Create two `Stack` records (`stack_a`, `stack_b`) each requiring `security/scan` as a required status, with `stack_b` configured `review_stacks_enabled: true, allow_all: true`.
2. Create `Commit` rows with the **same** `sha` value under both `stack_a.id` and `stack_b.id` (simulating shared history / shared SHA across stacks).
3. Build a `status` webhook payload with `sha:`, `context: 'security/scan'`, `state: 'success'`, and a `repository.full_name` matching only `stack_a`'s repo.
4. Invoke `Shipit::Webhooks::Handlers::StatusHandler.new.call(payload)` (or `process`) directly.
5. Assert: `stack_b`'s commit's `deployable?`/`status.success?` changed to `true` even though the payload's `repository.full_name` never matched `stack_b`, proving cross-stack contamination — i.e. `stack_a.repo_full_name != payload_repo_full_name_for(stack_b_mutation)` yet the mutation occurred.

      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end

    def verify_signature

        "unknown_organization=#{e.message}",

      ].join(' '))
    end
