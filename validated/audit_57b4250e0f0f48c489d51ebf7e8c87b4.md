### Title
Ambiguous quoted-local-part parsing in `isValidEmail` lets a textcoin sender's mnemonic be routed to an attacker-controlled mailbox - (File: `validation_utils.js`)

### Summary
`validation_utils.isValidEmail` accepts RFC-5322-style quoted local parts (`".+"@domain`), which — like the Python `email.utils.parseaddr` behavior described in CVE-2019-11340 — allows an "address" string to contain more than one `@` in a way that is unambiguous to the validator but ambiguous to the code that later extracts the actual delivery domain from the same string using a naive `indexOf("@")`/`slice` split.

### Finding Description
`isValidEmail` matches either an unquoted local part (which explicitly excludes `@` characters) or a quoted local part `(".+")` which allows **any** character, including `@`, inside the quotes: [1](#0-0) 

This means a string such as `"user@attacker.com"@good.example.com` passes `isValidEmail` as valid (quoted local part = `"user@attacker.com"`, domain = `good.example.com`).

This validator gates the textcoin flow in `wallet.js`: when composing a payment to a non-Obyte address (e.g. `sendMultiPayment`), any output address that satisfies `isValidEmail` is treated as an email recipient — a fresh keypair/mnemonic is generated for the funds and the plaintext mnemonic is later emailed to that address via `sendTextcoinEmail`: [2](#0-1) [3](#0-2) 

However, the actual mail transport (`mail.js`, used in `direct` SMTP mode) determines the destination mail server by taking everything **after the first `@`** in the string: [4](#0-3) 

For the crafted address `"user@attacker.com"@good.example.com`, `isValidEmail` accepts it as belonging to `good.example.com`, but `mail.js`'s `indexOf("@")` finds the first `@` (inside the quotes) and resolves the MX host as `attacker.com"@good.example.com` / effectively routes/interprets the recipient differently than what the validator confirmed, and the SMTP `to` header value used by `nodemailer`/the local `sendmail` binary is likewise the full ambiguous string, not the domain a user or restriction check assumed. This is the same parsing-ambiguity root cause as GHSA-q9h8-gpw5-c95c: one component treats the string as belonging to `good.example.com`, another component's naive split derives a different endpoint from the same input.

### Impact Explanation
The textcoin mnemonic is the private key material for spendable funds — whoever receives the email containing it can claim the coins. If a wallet UI or any allow-list logic relies on `isValidEmail`/domain checks to decide that a textcoin recipient string is safe or belongs to an expected domain, an attacker who can influence or intercept the "email" destination field (e.g., a shared/multi-user composing flow, or copy-pasted recipient string) can construct a quoted-local-part string that validates against one domain while `mail.js`'s naive first-`@` split sends the actual message envelope/MX lookup based on a different substring, causing the mnemonic — and thus the funds — to be delivered to an unintended mailbox. This results in concrete unauthorized loss/redirection of funds sent via the textcoin feature.

### Likelihood Explanation
Exploitation requires the ability to supply the destination "address" string used in `sendMultiPayment`'s outputs/`to_address` — the textcoin recipient field is user/attacker-suppliable input in normal wallet usage (a sender typing/pasting a recipient "email"), so no privileged access is needed. The mismatch only manifests when `conf.smtpTransport === 'direct'` (the `sendMailDirectly` path using `indexOf("@")`), which is a supported and documented transport mode.

### Recommendation
- Reject quoted local parts (or any local part containing `@`, whitespace, or control characters) in `isValidEmail`, aligning validation with a single canonical parser.
- Replace the naive `params.to.indexOf("@")` domain extraction in `mail.js`'s `sendMailDirectly` with the same strict, single-source-of-truth email parser used for validation, ensuring the "domain" both components agree on is the last (or the RFC-correct) `@`-delimited segment, not the first.
- Add a unit test asserting `isValidEmail('"a@b"@c.com')` is rejected, and that `sendMailDirectly` and `isValidEmail` derive identical domains for any accepted string.

### Proof of Concept
1. Compose a textcoin payment via `wallet.sendMultiPayment` with an output address `"attacker@evil.tld"@good.example.com`.
2. `ValidationUtils.isValidEmail` in `validation_utils.js:99-101` returns `true` (quoted local part branch matches), so `wallet.js:2227` treats it as a valid textcoin email destination and generates a funded mnemonic for it.
3. When `conf.smtpTransport === 'direct'`, `mail.js:56` computes `hostname = params.to.slice(params.to.indexOf("@")+1)`, which yields `evil.tld"@good.example.com` (derived from the *first* `@`, inside the quoted section) instead of `good.example.com`, causing the MX lookup/delivery target to diverge from what the validator confirmed and from what the sender intended, risking mnemonic exposure to an unintended recipient.
