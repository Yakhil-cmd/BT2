### Title
Missing signer/authority checks on `InitializeBuffer` allow front-running to hijack buffer account authority - (File: `programs/bpf_loader/src/lib.rs`)

### Summary
The `bpf_loader_upgradeable` program's `InitializeBuffer` instruction sets the `authority_address` of a program buffer account from an arbitrary, attacker-suppliable account index without requiring that account (or the buffer account itself) to be a transaction signer. This is the same bug class as the CompliFi `Vault.initialize` report: an initialization routine with no access control that can be front-run by any unprivileged transaction sender to seize control of an account before its intended owner.

### Finding Description
`process_loader_upgradeable_instruction` handles `UpgradeableLoaderInstruction::InitializeBuffer` as follows: [1](#0-0) 

```
UpgradeableLoaderInstruction::InitializeBuffer => {
    instruction_context.check_number_of_instruction_accounts(2)?;
    let mut buffer = instruction_context.try_borrow_instruction_account(0)?;

    if UpgradeableLoaderState::Uninitialized != buffer.get_state()? {
        ic_logger_msg!(log_collector, "Buffer account already initialized");
        return Err(InstructionError::AccountAlreadyInitialized);
    }

    let authority_key = Some(*instruction_context.get_key_of_instruction_account(1)?);

    buffer.set_state(&UpgradeableLoaderState::Buffer {
        authority_address: authority_key,
    })?;
}
```

Unlike the `Write` handler a few lines below it, which explicitly requires the authority to be a signer (`instruction_context.is_instruction_account_signer(1)?`), `InitializeBuffer` performs **no signer check at all**, either on the buffer account (index 0) or on the proposed authority account (index 1). This is corroborated by the unit test and benchmark setup, which construct the accounts with `is_signer: false` for both the buffer and authority accounts: [2](#0-1)  and [3](#0-2) .

The only gate is that the buffer account must be in `UpgradeableLoaderState::Uninitialized` and owned by the `bpf_loader_upgradeable` program — a state reached as soon as `SystemProgram::CreateAccount` funds/assigns the account to the loader. Because `CreateAccount` and `InitializeBuffer` are two independent instructions (they are commonly, but not atomically, combined by client helpers such as `create_buffer`), any account sitting in this "created but not yet initialized" state is a race target: whoever's `InitializeBuffer` instruction lands first (by paying a higher priority fee) becomes the permanent authority, exactly mirroring the reported `Vault.initialize` front-running scenario where `_underlyingStarts` could be set by whichever party's transaction landed first.

### Impact Explanation
An attacker monitoring the mempool/leader schedule for a pending `InitializeBuffer` (or a `CreateAccount` targeting a not-yet-initialized buffer, e.g. reused/pre-funded buffer pubkeys as supported by the CLI's `buffer_pubkey: Some(...)` flow, see [4](#0-3) ) can submit a competing `InitializeBuffer` naming themselves as `authority_address`. Because `Write`, `SetAuthority`, and eventual `DeployWithMaxDataLen`/`Upgrade` all gate on `authority_address` matching a signer, the legitimate creator permanently loses write/deploy control over an account they funded (rent-exempt lamports locked), and the attacker gains exclusive control of that buffer's contents. This is an unauthorized privilege-assignment/account-hijack primitive reachable from a single unprivileged transaction.

### Likelihood Explanation
Exploitability depends on catching the narrow window between an account entering the `Uninitialized` buffer state (owned by `bpf_loader_upgradeable`, e.g. right after `CreateAccount`) and the legitimate `InitializeBuffer` instruction landing. When client tooling bundles `CreateAccount` + `InitializeBuffer` into one atomic transaction/message (the default path in `solana_loader_v3_interface::instruction::create_buffer`), the window does not exist. However, the instruction itself provides no defense-in-depth (no signer requirement), so any code path, integration, or manual instruction construction that separates account creation from initialization — including reuse of a previously created buffer account — is directly exploitable by racing with a higher compute-unit price.

### Recommendation
Require `is_instruction_account_signer` for the authority account index (and/or the buffer account) in `InitializeBuffer`, matching the existing pattern already used in the `Write` handler, so only the intended creator/owner can claim authority over a freshly created buffer account. Additionally, document that buffer/program-account initialization should always be submitted atomically with the preceding `CreateAccount` instruction in the same transaction.

### Proof of Concept
1. Party A creates a fresh keypair `buffer` and submits `SystemProgram::CreateAccount(buffer, owner=bpf_loader_upgradeable, space=size_of_buffer(N))` as its own transaction (not atomically bundled with `InitializeBuffer`), intending to follow up with `InitializeBuffer` naming itself as authority.
2. Attacker observes this transaction in the mempool/gossip and, before Party A's `InitializeBuffer` transaction lands, submits its own transaction invoking `bpf_loader_upgradeable::InitializeBuffer` on `buffer` with instruction account 1 set to the attacker's own pubkey (no signature required, per [1](#0-0) ), using a higher compute-unit price for faster inclusion.
3. Attacker's transaction lands first; `buffer.get_state()` was `Uninitialized`, so it succeeds and sets `authority_address = Some(attacker)`.
4. Party A's subsequent `InitializeBuffer` attempt now fails with `AccountAlreadyInitialized`; Party A has permanently lost the ability to `Write` to or deploy from `buffer`, while the attacker now holds exclusive authority over the account Party A funded.
