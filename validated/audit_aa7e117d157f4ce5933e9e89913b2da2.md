### Title
Inconsistent `earned_headers_commission_recipients` resolution between TPS-fee validation and TPS-fee-balance accounting can allow a unit to be accepted while paying an insufficient TPS fee - (File: `validation.js`, `storage.js`)

### Summary
`ocore` has two independent code paths that resolve which addresses are responsible for paying/covering a unit's TPS fee from `earned_headers_commission_recipients`: the consensus check in `validateTpsFee()` [1](#0-0)  and the balance/accounting helper `getPaidTpsFee()` used elsewhere (e.g. by AA/formula code and headers-commission bookkeeping) [2](#0-1) . The validation path explicitly branches on a hard-fork MCI (`constants.tpsFeeRecipientsFixMci`) to decide whether to treat `earned_headers_commission_recipients` as a raw array or as a normalized association map via `ehcr2assoc()`, while the balance-computation path always uses the normalized `assocEarnedHeadersCommissionRecipients` regardless of MCI. This is structurally the same class of bug as the AVM/`claim()` vs `claim_many()` discrepancy: one code path applies a "fix"/special-case resolution of the true fee-payer, the other path (used for a related, security-relevant computation) does not, creating disagreement about who actually bears/paid the fee.

### Finding Description
In `validation.js`, `validateTpsFee()` determines who is responsible for a unit's TPS fee like so:
```
const recipients = storage.getTpsFeeRecipients(objValidationState.last_ball_mci < constants.tpsFeeRecipientsFixMci ? objUnit.earned_headers_commission_recipients : storage.ehcr2assoc(objUnit.earned_headers_commission_recipients), author_addresses);
``` [3](#0-2) 

This conditionally passes either the raw `earned_headers_commission_recipients` array (pre-fix behavior) or the normalized assoc-map (post-fix behavior) into `storage.getTpsFeeRecipients()`, which expects an address→share map [4](#0-3) .

Elsewhere, `storage.getPaidTpsFee()` — used to compute the tps fee that a *specific unit* has already effectively paid (relevant for chained/AA-triggered units and other bookkeeping) — always builds recipients from `objUnitProps.assocEarnedHeadersCommissionRecipients`, i.e. the normalized map, with no analogous MCI branch:
```
const recipients = getTpsFeeRecipients(objUnitProps.assocEarnedHeadersCommissionRecipients, objUnitProps.author_addresses);
``` [2](#0-1) 

`objUnitProps.assocEarnedHeadersCommissionRecipients` itself is derived the same way in both `writer.js` (`objNewUnitProps.assocEarnedHeadersCommissionRecipients`) [5](#0-4)  and in `storage.js`'s on-demand reconstruction [6](#0-5) , and is not conditioned on `tpsFeeRecipientsFixMci`.

Because `validateTpsFee` treats units before `tpsFeeRecipientsFixMci` differently (feeding the raw array, not the assoc map) than `getPaidTpsFee` (which always uses the assoc map), the two functions can disagree about which address(es) are charged for/credited with a unit's TPS fee near/around the fork point, exactly mirroring the `claim()`/`claim_many()` pattern where one code path applies the "real payer/owner" resolution and a sibling path relevant to the same funds does not.

### Impact Explanation
If the set of "recipients" (fee payers) used by `getPaidTpsFee()` diverges from the set enforced by `validateTpsFee()`, a unit author could construct `earned_headers_commission_recipients` such that:
- `validateTpsFee()` (the consensus-critical check performed by every node during unit validation) computes a smaller or different tps_fees_balance debit path than intended, potentially allowing a unit with insufficient real tps_fee coverage to pass validation for one address while the accounting used elsewhere (`getPaidTpsFee`, consumed by AA logic/other units relying on it, e.g. determining a chained AA trigger's already-paid tps fee) computes a different amount.
- This can lead to nodes/AAs disagreeing about the effectively "paid" tps fee for a unit, which is a network-DoS/anti-spam-mechanism weakening rather than a benign display bug — it can let spam/flood units bypass or under-pay the TPS fee anti-spam gate at the pre/post-fix MCI boundary, and any AA logic depending on `getPaidTpsFee` results could be fed inconsistent numbers relative to what was actually validated on-chain.

### Likelihood Explanation
This requires an attacker to specifically craft `earned_headers_commission_recipients` around the `tpsFeeRecipientsFixMci` boundary and rely on the differing treatment (array vs. assoc-map) between the two functions; since `tpsFeeRecipientsFixMci` is a one-time historical hard-fork point, exploitability going forward is limited to units validated with `last_ball_mci` below that boundary (i.e., only relevant for historical/legacy re-validation or catch-up scenarios, not new units after the fork). This significantly reduces practical, ongoing exploitability, but the code inconsistency itself is real and reachable by any unprivileged unit poster who can set multiple authors with `earned_headers_commission_recipients` in a unit that would be validated against an old `last_ball_mci`.

### Recommendation
Refactor to a single shared helper that resolves the TPS-fee recipients for a unit, applying the `tpsFeeRecipientsFixMci` logic (or the `ehcr2assoc` normalization) consistently, and use that single helper in both `validateTpsFee()` (`validation.js`) and `getPaidTpsFee()` (`storage.js`), the same way the C4 report recommends factoring `_getRewardRecipient()` and calling it from both `claim()` and `claim_many()`.

### Proof of Concept
Not independently reproduced end-to-end in this review (would require constructing units at/near `constants.tpsFeeRecipientsFixMci` with multi-author `earned_headers_commission_recipients` and diffing `validateTpsFee`'s accepted tps_fee against `getPaidTpsFee`'s computed value for the same unit). Root-cause mapping is based on direct code comparison: [1](#0-0)  vs [2](#0-1) , both consuming `storage.getTpsFeeRecipients()` [4](#0-3)  with inconsistent input normalization.

function getTpsFeeRecipients(assocEarnedHeadersCommissionRecipients, author_addresses) {
	let recipients = assocEarnedHeadersCommissionRecipients || { [author_addresses[0]]: 100 };
	if (assocEarnedHeadersCommissionRecipients) {
		let bHasExternalRecipients = false;
		for (let address in recipients) {
			if (!author_addresses.includes(address))
				bHasExternalRecipients = true;
		}
		if (bHasExternalRecipients) // override, non-authors won't pay for our tps fee
			recipients = { [author_addresses[0]]: 100 };
	}
	return recipients;
}
