### Title
Webhook signature verification is scoped to the payload's `repository.owner.login` while event handlers act on the payload's `repository.full_name` — an organization configured without a `webhook_secret` lets an attacker forge events against *any* other repository/stack - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` picks which GitHub App configuration (and therefore which `webhook_secret`) to validate the request against using only `params.dig('repository', 'owner', 'login')` (falling back to `organization.login`). Every downstream `Shipit::Webhooks::Handlers::Handler` subclass, however, resolves the repository/stack to act on using a completely different, attacker-controlled field of the same unsigned JSON body: `payload.dig('repository', 'full_name')`. Because `GithubApp#verify_webhook_signature` treats a blank `webhook_secret` as "always verified", any organization onboarded onto the Shipit instance without a configured `webhook_secret` becomes a skeleton key: an attacker can send a request claiming to originate from that lightly-configured organization (satisfying signature verification trivially) while setting `repository.full_name` to any other, strictly-secured repository that Shipit tracks, and have the corresponding handler act on it.

### Finding Description
The verification step binds trust to one field: [1](#0-0) [2](#0-1) 

The actual signature check trusts an org with no secret unconditionally: [3](#0-2) 

But every default handler acts on a different field of the same body, `repository.full_name`, to look up the target `Stack`: [4](#0-3) [5](#0-4) 

Because `WebhooksController#create` parses the raw JSON body once and passes the same untrusted hash to every registered handler regardless of which org's secret satisfied `verify_signature`, the field used to select the cryptographic key (`repository.owner.login`) is never checked for consistency against the field used to select the object being mutated (`repository.full_name`): [6](#0-5) 

This breaks the intended equality:
`organization whose webhook_secret authenticated the request == organization that owns the repository/stack being written`

In a multi-org configuration (explicitly documented and supported, see `config/secrets.development.shopify.yml`), if any one configured organization has `webhook_secret` left blank/nil, that organization's name becomes usable to bypass signature verification for a payload that actually targets a stack belonging to a different, properly-secured organization. [7](#0-6) 

### Impact Explanation
An unprivileged network attacker (no `ApiClient` token, no GitHub App credentials, no repository write access) who only needs to know:
1. the name of any organization onboarded to the Shipit instance that has no `webhook_secret` set (organization names are not secret — they can often be inferred from Shipit's public login/OAuth flow or from an existing installed-orgs listing), and
2. the `full_name` of a target repository already tracked by Shipit (also not secret),

can forge webhook events (`push`, `status`, `check_suite`, `pull_request`, etc.) that are processed as if they came from GitHub for a completely unrelated, properly-secured repository/organization. Concretely, forging a `push` event lets the attacker cause `PushHandler` to call `stack.sync_github(expected_head_sha:)` with an attacker-chosen SHA for a target stack the attacker does not control, and forging `status`/`check_suite` events can flip commit CI/deployability state used to gate deploys. This is a cross-organization/cross-repository write achieved purely by exploiting the mismatch between the field used for authentication and the field used for authorization of the mutation — meeting the "cross-repository writes" / "unauthorized deploy" bar in scope.

### Likelihood Explanation
The precondition (one configured org lacking a `webhook_secret`) is realistic: the shipped example configs literally show `webhook_secret: # nil` as a valid/blank value, and nothing in `GithubApp#initialize` or `WebhooksController` enforces that all configured organizations must have a secret, nor that the org used for verification match the org that owns the acted-upon repository. Any operator running multiple GitHub orgs through one Shipit instance, where even a single low-priority/test org is left without a webhook secret, exposes every other repository tracked by that Shipit instance to forged events.

### Recommendation
- In `WebhooksController#verify_signature`, derive the verifying organization from the same field the handlers use to select the target repository (`repository.full_name`'s owner segment), not a value that can diverge from it.
- Reject webhook signature verification for any organization whose `webhook_secret` is blank, or require an explicit config flag ("no signature enforced") only for single-organization/dev deployments, never merged silently with production-mode multi-org configs.
- Assert, before dispatching to handlers, that the organization that satisfied `verify_signature` matches the organization portion of `payload.dig('repository', 'full_name')`.

### Proof of Concept
1. Configure Shipit with two organizations, e.g. `attacker-org` (no `webhook_secret` set) and `victim-org` (strict `webhook_secret`), both onboarded per `config/secrets.development.shopify.yml`'s documented multi-org format.
2. `victim-org/critical-repo` has an existing tracked `Stack` in Shipit.
3. Attacker sends:
```
POST /webhooks
X-Github-Event: push
X-Hub-Signature: sha1=anything-or-omitted
Body:
{
  "repository": {"owner": {"login": "attacker-org"}, "full_name": "victim-org/critical-repo"},
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>"
}
```
4. `verify_signature` calls `Shipit.github(organization: "attacker-org").verify_webhook_signature(...)`, which returns `true` unconditionally because `attacker-org`'s `webhook_secret` is blank.
5. `PushHandler.call(params)` runs, resolves `stacks` via `Repository.from_github_repo_name("victim-org/critical-repo")`, and invokes `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` on `victim-org`'s stack — despite the request never being authenticated by `victim-org`'s webhook secret.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
