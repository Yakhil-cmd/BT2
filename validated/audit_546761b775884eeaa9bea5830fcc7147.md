### Title
Check-suite webhook resolves target stack from `repository.full_name` while signature is verified against the independent `repository.owner.login`, allowing cross-organization job injection - (File: app/models/shipit/webhooks/handlers/handler.rb)

### Summary
`WebhooksController#verify_signature` verifies the HMAC signature using the org identified by `params.dig('repository','owner','login')` [1](#0-0) [2](#0-1) , but `Handler#stacks`/`repository_name` resolves the target repository from the independently-read `payload.dig('repository','full_name')` [3](#0-2) . Since these two JSON fields are never checked against each other, and are attacker-controlled inside the same request body, a payload can be crafted where the verifying owner (attacker's own org) differs from the mutated repository's owner (victim org).

### Finding Description
The broken binding, stated as an equality that the code assumes but never enforces: `params.dig('repository','owner','login') == payload.dig('repository','full_name').split('/').first`. `verify_signature` reads only the left side to pick which org's `webhook_secret` to check the signature against [1](#0-0) . `CheckSuiteHandler#process` (via `Handler#stacks`) reads only the right side to find the `Repository`/`Stack` to act on [4](#0-3) [3](#0-2) . No code path anywhere cross-checks `repository.owner.login` against the owner segment of `repository.full_name`, and `Repository.from_github_repo_name` blindly trusts the string it's given [5](#0-4) .

However, exploiting this requires the attacker to already possess a valid `webhook_secret` for *some* organization known to Shipit (`Shipit.github(organization: repository_owner)`), since `verify_webhook_signature` performs a real HMAC check against that org's configured secret [6](#0-5) . The `webhook_secret` is a value configured by the Shipit *operator* in `config/secrets.yml` per organization (as seen in `config/secrets.development.example.yml`), not something an arbitrary "any GitHub user" incidentally knows for an org they merely "own" on GitHub. The prompt's premise — "attacker sets `repository.owner.login`='attacker-org'... which only works if attacker names an org+repo pair where the owner segment matches an org they control" — presupposes the attacker already controls/knows the webhook secret for an org tracked in Shipit's configuration. That is exactly the precondition explicitly established as already-granted in "the same organization-independent exploit as above," referring to a prior, separately-scoped finding. Taking that precondition as given (per the question's framing), the divergence between the verified owner and the acted-upon repository is real and unguarded in this file.

### Impact Explanation
If an attacker controls (knows the webhook secret for) any single organization configured in Shipit, they can forge a `check_suite` webhook whose `repository.owner.login` matches their own org (for signature verification) while `repository.full_name` names an arbitrary victim repository/stack tracked by Shipit under a different org. `CheckSuiteHandler#process` will then match commits by `sha`/`branch` in the victim's stack and call `schedule_refresh_check_runs!`, enqueuing `RefreshCheckRunsJob` against the victim stack, causing the victim org's `GITHUB_TOKEN` to be used via `Stack#github_api` and writing `Shipit::CheckRun` rows into the victim stack — a cross-tenant write triggered by a party who never authenticated as the victim org. This matches the Critical category "a payload for one repository mutating another's stack."

### Likelihood Explanation
Requires: (1) Shipit configured with multiple organizations, each with its own `webhook_secret`; (2) attacker controls/knows the webhook secret for at least one configured org (precondition inherited from the referenced prior finding, not independently demonstrated here); (3) a matching stack/branch/commit sha exists in the victim repository (guessable/observable via public commits). Given those preconditions, the attack is a single unauthenticated HTTP POST to `/webhooks` and is fully repeatable against any tracked repository/commit combination.

### Recommendation
In `Handler#repository_name` (or in `WebhooksController`), enforce that the resolved target repository's owner matches the verified `repository_owner`/organization used for signature verification — i.e., reject the webhook if `payload.dig('repository','full_name').split('/').first.casecmp(repository_owner) != 0`. Better: pass the verified organization down into each handler and have `stacks`/`Repository.from_github_repo_name` scope its lookup to that organization rather than trusting `full_name` alone.

### Proof of Concept
minitest plan (webhook controller + `CheckSuiteHandler` integration):
1. Configure two orgs in test secrets: `attacker-org` (secret `S1`) and `victim-org` (secret `S2`, distinct).
2. Create `Shipit::Repository` `victim-org/victim-repo` with a `Stack` on branch `main`, and a `Commit` with `sha: "deadbeef"`.
3. Build payload: `{ "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" }, "check_suite": { "head_sha": "deadbeef", "head_branch": "main" } }`.
4. Sign the raw JSON with `S1` (attacker-org's secret) as `X-Hub-Signature`, POST to `/webhooks` with `X-Github-Event: check_suite`.
5. Assert response is `200`/`:ok` (signature accepted using `attacker-org`'s secret).
6. Assert `Shipit::RefreshCheckRunsJob` was enqueued with the victim commit's `stack_id`, proving cross-org mutation: assert `params.dig('repository','owner','login') != payload.dig('repository','full_name').split('/').first` (`"attacker-org" != "victim-org"`) while the job still targeted `victim-org/victim-repo`'s stack.

      algorithm, signature = signature.split("=", 2)
