### Title
Worktree sanity check accepts a partially-checked-out revision as valid before publish - (File: main.go)

### Summary
`git-sync`'s `sanityCheckWorktree` function, used to decide whether an existing worktree can be reused and republished without repeating the checkout, explicitly does not verify that all files were actually written to disk. The same gap the Particle report describes — a completion/coverage check that is known to be insufficient but shipped anyway — exists here: the function checks only that `HEAD` matches the expected hash and that `git fsck --connectivity-only` passes, not that the working tree content is complete.

### Finding Description
`sanityCheckWorktree` carries an explicit comment acknowledging the gap: [1](#0-0) 

```go

This function is called from `SyncRepo` exactly in the path where the previously-published worktree is *reused* rather than freshly checked out again: [2](#0-1) 

If `HEAD` happens to match the target hash (which it will as soon as `git reset --hard`/checkout has updated the ref pointer, even if the working-tree file writes did not all complete — e.g., the process was killed by an OOM-killer or `SIGKILL` partway through `configureWorktree`'s `reset --hard`), the connectivity-only `fsck` will still pass because it only walks the object graph, not the working tree contents. On the next `SyncRepo` iteration where the remote hash hasn't changed, this reused, partially-checked-out worktree is treated as fully valid and continues to be served through the already-published `--link` symlink — the "contract" that consumers rely on for atomic, complete data: [3](#0-2) 

### Impact Explanation
This matches the "publishing wrong or partial content" impact category. A consumer container reading through `--link` can be served an incomplete checkout (missing or truncated files) while git-sync reports steady-state as healthy (`good_sync_count` increments, readiness probe stays green), because the only verification performed (`rev-parse HEAD` + `fsck --connectivity-only`) is, by the maintainers' own comment, insufficient to catch this class of failure.

### Likelihood Explanation
The condition requires the git-sync process (or the underlying `git` child process) to be interrupted mid-checkout — e.g., due to resource exhaustion triggered by a large/adversarial upstream repository (huge blobs, deep history, or submodule bombs an attacker who controls the synced repo can push), a container OOM-kill, or a crash — combined with a restart or next poll cycle where the remote hash is unchanged so the "reuse" branch is taken instead of a fresh checkout. This is a realistic, if not everyday, occurrence in Kubernetes sidecar deployments where OOM-kills and preemption are common, and an attacker who controls the content of the synced repository can increase the likelihood by inflating repo size/complexity to increase the checkout window during which a kill/crash can land the worktree in a half-checked-out state.

### Recommendation
Strengthen `sanityCheckWorktree` (or add a dedicated check) to verify checkout completeness, e.g., by comparing `git status --porcelain` for unexpected missing/untracked deletions, or running `git diff --quiet HEAD --` / `git checkout-index` verification, rather than relying solely on `rev-parse HEAD` and connectivity-only `fsck`. At minimum, the known limitation documented in the comment should be closed rather than left as an acknowledged gap, mirroring the Particle team's eventual recommendation to add the missing coverage check rather than skip it.

### Proof of Concept
1. Start `git-sync` against a repo, let it publish worktree `W` at hash `H` via `--link`.
2. Simulate a crash mid checkout for a subsequent sync to the same hash `H` (e.g., `docker pause`/`kill -9` the process while `configureWorktree`'s `git reset --hard H --` is writing files, similar to the existing `e2e::worktree_unexpected_removal`/`e2e::sync_recover_wrong_worktree_hash` test harness patterns in `test_e2e.sh`), leaving some files from `H` not yet written to `W`.
3. Restart `git-sync` with `--period` polling the same ref/hash `H` (no remote change). `SyncRepo` takes the `currentHash == remoteHash` branch and calls `sanityCheckWorktree(ctx, W)`.
4. Because `HEAD` already points at `H` (updated early in the reset) and `fsck --connectivity-only` only validates object-graph reachability, the check returns `true` despite missing working-tree files, and the incomplete `W` continues to be served through `--link`, an outcome the code comment explicitly says can happen.

// sanityCheckWorktree tries to make sure that the dir is a valid git
// repository.  Note that this does not guarantee that the worktree has all the
// files checked out - git could have died halfway through and the repo will
// still pass this check.
func (git *repoSync) sanityCheckWorktree(ctx context.Context, worktree worktree) bool {
	git.log.V(3).Info("sanity-checking worktree", "repo", git.root, "worktree", worktree)

	// If it is empty, we are done.
	if empty, err := dirIsEmpty(worktree.Path()); err != nil {
		git.log.Error(err, "can't list worktree directory", "path", worktree.Path())
		return false
	} else if empty {
		git.log.V(0).Info("worktree is empty", "path", worktree.Path())
		return false
	}

	// Make sure it is synced to the right commmit.
	stdout, _, err := git.Run(ctx, worktree.Path(), "rev-parse", "HEAD")
	if err != nil {
		git.log.Error(err, "can't get worktree HEAD", "path", worktree.Path())
		return false
	}
	if stdout != worktree.Hash() {
		git.log.V(0).Info("worktree HEAD does not match worktree", "path", worktree.Path(), "head", stdout)
		return false
	}

	// Consistency-check the worktree.  Don't use --verbose because it can be
	// REALLY verbose.
	if _, _, err := git.Run(ctx, worktree.Path(), "fsck", "--no-progress", "--connectivity-only"); err != nil {
		git.log.Error(err, "worktree fsck failed", "path", worktree.Path())
		return false
	}

	return true
}
```
