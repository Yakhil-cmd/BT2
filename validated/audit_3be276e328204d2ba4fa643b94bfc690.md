### Title
Webhook signature verified against an attacker-chosen organization while handlers act on a different, unverified `repository.full_name` / `sha` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks the GitHub App/webhook secret to validate the HMAC signature against using `repository.owner.login` (falling back to `organization.login`) taken straight from the unauthenticated JSON body [1](#0-0) [2](#0-1) . Once that check passes, every webhook handler resolves the target `Stack`/`Commit` using a *different* field of the same body - `repository.full_name` in the base `Handler` class [3](#0-2) , or a raw `sha` for `StatusHandler` [4](#0-3) , or `ref`/`after` for `PushHandler` [5](#0-4) . Nothing enforces that the organization used to select/verify the signing secret actually owns the repository/stack the handler subsequently mutates. This is the same class of bug as `CLGauge.deposit()`: a value that is checked (the pool/organization the signature is "bound" to) is never confirmed to be the same value that is actually acted upon (the pool/repository whose state gets written).

### Finding Description
Shipit explicitly supports hosting multiple GitHub organizations from one instance, each with its own `webhook_secret` [6](#0-5) . `Shipit.github(organization:)` resolves the app/secret purely from the organization string supplied by the caller [7](#0-6) .

In `WebhooksController`:
```
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [8](#0-7) 

`repository_owner` is read from the raw, attacker-supplied request body before any signature has been checked - it is not itself protected by anything except the HMAC over the *whole* body, which is verified using the secret for whatever organization the attacker names in that same field. Because the attacker fully controls the raw body (they are simply crafting an HTTP request to `/webhooks`), they can independently set:
- `repository.owner.login` = an organization whose `webhook_secret` they know (e.g. an org they administer that happens to also be configured in this shared/multi-tenant Shipit instance), used purely to pick the secret for HMAC verification, and
- `repository.full_name` (used by every handler via `Handler#repository_name`, e.g. `PushHandler`, `StatusHandler` via `Commit.where(sha:)` is not scoped to org/repo at all) or `sha` referring to a totally different repository/stack/commit that they do not control.

`verify_webhook_signature` only checks that the HMAC matches *some* secret they picked for signing; it never re-derives or checks that the organization it verified against is the same organization whose data is later mutated [9](#0-8) . `Handler#stacks` then trusts `repository.full_name` unconditionally: `Repository.from_github_repo_name(repository_name)&.stacks` [3](#0-2) , and `StatusHandler#process` looks up `Commit.where(sha: params.sha)` globally, with no org/repo scoping at all [4](#0-3) .

This is directly analogous to the CLGauge bug: the "signature" (deposit) is checked against one binding (the organization/pool an attacker names), but the write (staking liquidity / mutating commit/stack state) is performed against a completely different, unverified binding (the actual repository/stack/commit).

### Impact Explanation
An attacker who knows the `webhook_secret` for *any one* GitHub organization configured on a shared Shipit instance (a low-privilege position - they can be the GitHub App admin of their own small org, entirely outside Shipit's authentication boundary) can forge signed webhook deliveries that:
- Spoof `status` events for arbitrary commit SHAs belonging to stacks of *other* organizations, marking otherwise-unreviewed commits "success", which can satisfy `required_statuses`/CI gating and enable continuous-deployment or manual deploys of unvetted code (`Stack.schedule_continuous_delivery` deploys stacks flagged `continuous_deployment: true`) [10](#0-9) .
- Spoof `push` events for repositories/stacks belonging to other organizations, triggering `GithubSyncJob` with an attacker-chosen `expected_head_sha`.

This crosses the "authentication versus write target" boundary called out by the rules (an organization that authenticated versus the repository that is written), and can culminate in an unauthorized deploy/CI-status bypass, matching the High severity bar.

### Likelihood Explanation
Requires the attacker to control/know a `webhook_secret` for at least one organization onboarded to the same Shipit instance (a scenario the docs explicitly support - "Using Multiple GitHub Applications") and craft a raw HTTP POST; no Shipit session, `ApiClient` token, or repository write access on GitHub is needed. This is plausible in any multi-tenant Shipit deployment (e.g., a platform team running Shipit for many customer orgs).

### Recommendation
Do not select the verification secret from unauthenticated body content that differs from the value handlers actually consume. Either:
1. Verify the signature against every configured organization's secret and, once verified, record which organization actually validated it, then require handlers to check that `repository.full_name`'s owner / `organization.login` matches that verified organization; or
2. Bind the webhook URL itself to a specific organization (e.g. `/webhooks/:organization`) so the secret used for verification is a controller-level constant unrelated to any body field, and re-validate that `repository.owner.login`/`full_name` matches the URL-bound organization before dispatching to handlers.

### Proof of Concept
1. Shipit is configured with two organizations, `OrgA` and `OrgB`, each with its own `webhook_secret` (per the documented multi-org config) [11](#0-10) ; `OrgB` has a Stack tracking `OrgB/victim-repo` with `continuous_deployment: true`.
2. Attacker administers `OrgA`'s GitHub App installation (their own, low-privilege org) and thus knows `OrgA`'s `webhook_secret`.
3. Attacker crafts a `status` webhook JSON body:
```json
{
  "sha": "<existing-unreviewed-commit-sha-in-OrgB/victim-repo>",
  "state": "success",
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/victim-repo" }
}
```
4. Attacker computes `X-Hub-Signature` using `OrgA`'s known `webhook_secret` over this exact raw body and POSTs it to `/webhooks` with `X-Github-Event: status`.
5. `verify_signature` calls `Shipit.github(organization: "OrgA")`, verifies the HMAC successfully with the attacker's own secret, and passes [1](#0-0) .
6. `StatusHandler#process` runs unscoped and marks the named commit's status "success" in `OrgB/victim-repo`'s stack, even though the attacker never had `OrgB`'s secret [4](#0-3) .
7. If continuous deployment is enabled, the falsely-green commit is auto-deployed, or a legitimate user is misled into deploying it.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

### Using Multiple Github Applications

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently. The top-level keys should be the name of each Github organization, and the following sub-keys are the Github app details for that particular organization.
