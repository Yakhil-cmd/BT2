### Title
Webhook signature verified against an attacker-selected organization while a different organization's repository/stack is written - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects *which* GitHub App configuration (and therefore which HMAC `webhook_secret`) to check the signature against by reading `repository.owner.login`/`organization.login` out of the very same untrusted JSON body it is trying to authenticate. In a multi-organization Shipit deployment (`Shipit.github_organizations`/`github_app_config`), each configured organization has its own `webhook_secret`. Nothing binds the organization used to select the secret to the repository that the event handlers subsequently act on (`repository.full_name`), so a request that is validly signed for organization A can carry a payload whose `repository.full_name` targets a stack that belongs to organization B.

### Finding Description
`verify_signature` computes `repository_owner` from the request body and calls `Shipit.github(organization: repository_owner)` to fetch the app config/secret used for HMAC verification: [1](#0-0) 

`Shipit.github_app_config` performs a case-insensitive per-organization secret lookup, confirming that in multi-org mode every organization has an independently held `webhook_secret`: [2](#0-1) 

After signature verification passes, event handlers (e.g. `PushHandler`, `StatusHandler`) resolve the *target* stack/repository from a completely different, unchecked field of the same payload — `repository.full_name` — via `Handler#stacks`/`Handler#repository_name`: [3](#0-2) [4](#0-3) 

Because `verify_signature` only checks "was this payload HMAC-signed by *some* organization's registered secret", and the handlers trust the (separately supplied) `repository.owner.login`/`full_name` field for routing to the actual `Stack`/`Repository` without cross-checking it against the organization whose secret validated the signature, an attacker who legitimately controls one configured organization (e.g., they administer their own org's installation and thus know/can obtain that org's `webhook_secret`) can forge a POST to `/webhooks` that: (1) sets `repository.owner.login`/`organization.login` = their own org (so `verify_signature` succeeds using their own known secret), and (2) sets `repository.full_name` = a *different* organization's tracked repository/stack. The signature check never verifies that the owner used to pick the secret matches the owner embedded in `full_name`.

This is the direct analog of the Firedancer report's bug class: a field (`sig`/`sz`/`chunk` in the frag) is used to route/act on data without being covered by the same trust boundary that gated the read. Here, the field used to select the verifying secret (`repository.owner.login`) is disjoint from the field used to select the write target (`repository.full_name`) — i.e., "an organization that authenticated versus the repository that is written."

### Impact Explanation
If exploitable, this allows an attacker who controls webhook delivery for Organization A (a legitimately configured, lower-trust org in a shared Shipit instance) to inject forged `push`/`status`/`pull_request`/`membership` events that are accepted as authentic and processed against Organization B's stacks — e.g., triggering `stack.sync_github(expected_head_sha:)` on push events, mutating commit statuses, or creating/archiving review stacks for a repository they do not control. This crosses a repository-authorization boundary and can influence what gets deployed for another organization's stack, matching the "unauthorized deploy/rollback or cross-repository writes" High/Critical impact bucket.

### Likelihood Explanation
Exploitability is conditioned on: (a) the deployment using the multi-organization GitHub App configuration schema (`secrets.github` keyed by org, each with a distinct `webhook_secret`), and (b) the attacker being an authorized administrator/owner of at least one of the configured organizations (so they know that organization's `webhook_secret`, or can trigger genuine deliveries and observe the signature is only per-org, not per-repository). This is a narrower, "insider-across-orgs" primitive rather than a fully unauthenticated one, since a single-org (legacy) Shipit config is not affected (`github_default_organization` returns `nil` and the whole install shares one secret, so there's no cross-org boundary to break). Likelihood is Medium: it requires the specific multi-tenant configuration and possession of one org's real secret, but no GitHub write access, `ApiClient` token, or session is needed.

### Recommendation
After `verify_signature` succeeds, have the webhook handlers verify that the organization login used to select the verifying secret is the same as the owner encoded in `repository.full_name` / `organization.login` used for routing, and reject the event (422) on mismatch. Alternatively, pass the already-verified `repository_owner` into `Shipit::Webhooks.for_event(event)` handlers so lookups (`Repository.from_github_repo_name`) are constrained to repositories belonging to that verified owner, rather than trusting the `full_name` string independently.

### Proof of Concept
1. Configure Shipit with multi-org GitHub Apps, e.g. `secrets.github = { orgA: { webhook_secret: "secretA", ... }, orgB: { webhook_secret: "secretB", ... } }`, with `orgB/some-repo` tracked as a Shipit stack.
2. As an attacker who administers `orgA` (and therefore knows `secretA`), craft a JSON body:
```json
{
  "repository": { "owner": { "login": "orgA" }, "full_name": "orgB/some-repo" },
  "ref": "refs/heads/main",
  "after": "<attacker chosen sha>"
}
```
3. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(secretA, body)>` and POST it to `/webhooks` with `X-Github-Event: push`.
4. `verify_signature` resolves `repository_owner = "orgA"`, fetches `secretA`, and the HMAC check passes.
5. `PushHandler#process` resolves the target using `repository.full_name = "orgB/some-repo"`, locating and acting on `orgB`'s stack — an event forged with `orgA`'s credentials mutating `orgB`'s stack state.

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping
      head(:ok) if event == 'ping'
    end

    def event
      request.headers.fetch('X-Github-Event')
    end

    def repository_owner
      # Fallback to the organization sub-object if repository isn't included in the payload
      params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
```

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
