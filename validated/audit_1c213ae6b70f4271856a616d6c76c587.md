### Title
Unbounded Recursion in `cleanNullsDeep` Causes Stack Overflow / Node Crash When Processing Device Messages - (File: object_hash.js)

### Summary
`object_hash.js` exposes `getDeviceMessageHashToSign()`, which is used to hash/verify signed device messages exchanged between paired wallet devices before they are accepted and processed [1](#0-0) . To compute this hash, it first calls `cleanNullsDeep()` on the received, attacker-controlled `objDeviceMessage`. This helper recurses into every nested object/array with no depth limit, no node-count limit and no protection against cycles or pathological nesting [2](#0-1) . The comment directly above the call acknowledges the danger but the mitigation (stripping `null`s) does nothing to bound recursion depth: *"device messages have free format and we can't guarantee absence of malicious fields"* [3](#0-2) .

### Finding Description
This is structurally the same bug class as CVE-2019-10094 (Apache Tika): an untrusted, attacker-supplied nested structure is walked with a recursive function that has no depth ceiling, so sufficiently deep nesting exhausts the JS call stack (`RangeError: Maximum call stack size exceeded`).

Elsewhere in the codebase, ocore developers are clearly aware of this exact risk class and defend against it in the places that matter for consensus:
- `aa_validation.js` bounds recursive definition validation with `MAX_DEPTH` and periodically yields the stack via `setImmediate` [4](#0-3) .
- `formula/validation.js` and `formula/evaluation.js` explicitly cap AST-evaluation recursion depth ("avoid extra long call stacks to prevent Maximum call stack size exceeded" / `depth > 100`) [5](#0-4) [6](#0-5) .
- `string_utils.js` provides `isTooDeeplyNestedOrHasTooManyNodes`/`isTooBigObj` guards that are applied to formula-produced JSON (`json_parse`) before further processing [7](#0-6) [8](#0-7) .

`cleanNullsDeep`, by contrast, has none of these protections, even though it operates on data that is explicitly documented as attacker-controlled ("free format", "can't guarantee absence of malicious fields") [3](#0-2) . A paired correspondent device can send a `device_message` object containing a deeply nested chain of objects/arrays (e.g. `{a:{a:{a:...}}}`, thousands of levels deep) as part of any message type that is hashed this way. When the recipient device processes the message and calls `getDeviceMessageHashToSign`, `cleanNullsDeep` recurses once per nesting level with no interruption, eventually overflowing the stack.

### Impact Explanation
A stack overflow thrown inside synchronous processing of an incoming device/wallet message is not guaranteed to be safely caught the way ordinary validation errors are (many callers assume `getDeviceMessageHashToSign`/hash functions are pure and non-throwing, and don't wrap them defensively the way JSON.parse or formula evaluation is wrapped elsewhere). This can crash the recipient wallet/hub process handling correspondent device traffic, denying that wallet the ability to process further private payments, chat messages, shared-address negotiation, or AA-related device notifications until restarted — a resource-exhaustion/availability impact consistent with CWE-770, reachable by any paired correspondent device (a normal, low-privilege capability in ocore's wallet-pairing model).

### Likelihood Explanation
Likelihood is high for any node/wallet that accepts correspondent pairing: pairing is a low-friction, self-service feature, and any paired correspondent (attester, merchant, bot, or malicious "friend") can send a message. Constructing a deeply nested JSON payload is trivial and requires no computational resources or special permissions.

### Recommendation
Add explicit depth/node-count limits to `cleanNullsDeep` (mirroring the existing `isTooDeeplyNestedOrHasTooManyNodes`/`MAX_DEPTH` patterns already used elsewhere in the codebase), and reject/abort processing of any device message whose payload exceeds the limit before hashing/signature verification. Additionally, wrap `getDeviceMessageHashToSign` callers so an unexpected `RangeError` cannot escape and crash the process.

### Proof of Concept
1. Attacker pairs their device with the victim's wallet (a normal, permissionless correspondent-pairing flow).
2. Attacker sends a `device_message` (any type routed through `getDeviceMessageHashToSign`, e.g. as part of a `chat`, `private_payments`, or `shared_address` notification) whose JSON body contains an extremely deeply nested object, e.g.:
   ```js
   let payload = 1;
   for (let i = 0; i < 50000; i++) payload = { a: payload };
   ```
3. When the victim device receives and processes this message, `getDeviceMessageHashToSign` invokes `cleanNullsDeep(objNakedDeviceMessage)` [3](#0-2) , which recurses 50,000 levels deep with no depth check [2](#0-1) , triggering `RangeError: Maximum call stack size exceeded` and disrupting/crashing message processing.

Note: I was not able to fully trace every call path from `network.js`'s device-message handler down to `getDeviceMessageHashToSign` within the available search iterations (the index confirms three references in `network.js` and five in `device.js`, but I could not read their full bodies before running out of tool calls). I recommend a Devin session with full file access to confirm the exact entry point(s) and whether any surrounding try/catch already mitigates the crash, before treating this as fully verified.

```javascript
function isTooDeeplyNestedOrHasTooManyNodes(obj, depthLimit = 100, nodesLimit = 10000) {
	let nodeCount = 0;

	function check(variable, depth){
		if (depth > depthLimit || nodeCount > nodesLimit)
			return true;
		if (variable === null || typeof variable !== "object")
			return false;
		if (Array.isArray(variable)) {
			nodeCount += variable.length;
			for (let v of variable)
				if (check(v, depth + 1))
					return true;
		}
		else {
			nodeCount += Object.keys(variable).length;
			for (let key in variable)
				if (check(variable[key], depth + 1))
					return true;
		}
		return false;
	}

	return check(obj, 1);
}
```
