### Title
Missing validation on attacker-controlled `creator` account in `initialize_with_permission` permanently freezes pool creator fees - ([File: programs/cp-swap/src/instructions/initialize_with_permission.rs])

### Summary
`initialize_with_permission` accepts `creator` as an `UncheckedAccount` that is **not required to sign** the transaction and is never validated against `Pubkey::default()` (or any other off-curve/unspendable address) before being persisted into `PoolState.pool_creator`. This mirrors the root cause of the referenced Timelock report: a privileged/authoritative address field is accepted from constructor/initialize input without a zero-address (or validity) check, and that address subsequently becomes the sole authority gating a class of fund-moving functionality.

### Finding Description
In `initialize_with_permission.rs`, the `creator` account is declared as: [1](#0-0) 
i.e. `UncheckedAccount<'info>` with no signer requirement and no address constraint. The payer, who can be any unprivileged caller, supplies this account.

The value is then written directly into the pool state without any validation: [2](#0-1) 
which calls `PoolState::initialize`, storing `pool_creator = creator.key()`: [3](#0-2) 

This `pool_creator` field later becomes the sole authority for creator-fee withdrawal in both the signed and "permissionless" collection paths, where the fee-receiving ATA's authority is set to this address: [4](#0-3) [5](#0-4) 

If `creator` is supplied as `Pubkey::default()` (the all-zero System Program address, which is off the ed25519 curve and has no corresponding private key), the pool is still created successfully — there is no on-chain check rejecting this value anywhere in `initialize_with_permission`, `create_pool`, or `PoolState::initialize`. Creator fees will continue to accrue in `pool_state.creator_fees_token_0`/`creator_fees_token_1` on every swap, and `collect_creator_fee_permissionless` will happily create an ATA with `associated_token::authority = creator` (i.e., authority = the zero pubkey) and transfer the accrued fees into it — but that ATA can never be spent from again, because no keypair exists that can sign as authority for `Pubkey::default()`.

### Impact Explanation
This permanently and irrecoverably freezes the creator-fee share of trading fees for any pool initialized this way. Since `creator_fee_on` in `initialize_with_permission` can direct a nonzero share of every swap's fee to the creator (`CreatorFeeOn::BothToken`/single-token variants), and swaps are open to any user, real value continuously accumulates in a frozen, permanently inaccessible account. This is a concrete, permanent freezing of protocol fee funds reachable from a single transaction with attacker-chosen accounts — matching the severity bar (permanent freezing of funds).

### Likelihood Explanation
`initialize_with_permission` is reachable by any unprivileged caller who is permitted to create a permissioned pool (subject to whatever permission-PDA gating exists for the config), and the `creator` field is fully attacker-controlled with zero validation. No signature or address constraint is enforced on `creator`, so setting it to the zero address (or any other unspendable/off-curve pubkey) requires no special privilege beyond being allowed to call the instruction at all. This can happen either through attacker intent or simple misconfiguration by a well-meaning integrator, making it a realistic and low-effort trigger.

### Recommendation
Add an explicit check in `initialize_with_permission` (and, for defense-in-depth, in `initialize` as well) rejecting `creator.key() == Pubkey::default()`, and ideally validate the key is on the ed25519 curve (or simply require `creator` to be a `Signer` as is already done in the standard `initialize` instruction) before persisting it into `PoolState.pool_creator`.

### Proof of Concept
1. Call `initialize_with_permission` as any payer, supplying `creator` = `Pubkey::default()` (system program's all-zero address) as the `creator` account — no signature is required for this account.
2. The instruction succeeds; `pool_state.pool_creator` is set to `Pubkey::default()` via `PoolState::initialize` (`programs/cp-swap/src/states/pool.rs:134-152`).
3. Perform swaps against the pool; a nonzero `creator_fee_rate` portion of fees accrues into `pool_state.creator_fees_token_0`/`creator_fees_token_1`.
4. Anyone calls `collect_creator_fee_permissionless`, which creates an ATA with `associated_token::authority = creator` (the zero pubkey) and transfers the accrued creator fees into it (`programs/cp-swap/src/instructions/collect_creator_fee_permissionless.rs:17-79`).
5. Because no private key exists for the zero pubkey, the tokens in that ATA can never be moved again — the creator-fee funds are permanently frozen.
