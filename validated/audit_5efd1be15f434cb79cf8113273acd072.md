### Title
Webhook signature is verified against an organization derived independently from the repository the payload actually writes to, allowing cross-repository forged events - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which organization's HMAC secret to check the request against using `repository_owner`, a value read from the raw, attacker-supplied JSON body. Separately, `Shipit::Webhooks::Handlers::Handler#repository_name` (and therefore which `Repository`/`Stack` the event is applied to) is read from a *different* field of the same JSON body (`repository.full_name`). Because these two fields are never cross-checked against each other, an attacker who legitimately controls one organization's webhook secret can craft a payload whose signature validates against their own organization while the `repository.full_name` field points at a completely different repository/stack hosted on the same Shipit instance.

`repository_name` comes from `payload.dig('repository', 'full_name')`, not from `repository.owner.login` (the field used for signature-organization selection). Nothing in the request pipeline enforces that the owner segment of `repository.full_name` matches `repository.owner.login`/`organization.login` used to pick the HMAC secret. This breaks the intended binding: *the organization whose secret authenticated the request* should equal *the repository/organization whose stack is written to*. An attacker who administers (or has compromised) a legitimate organization/app installation on the same Shipit instance can forge a signature that is valid for their own org, while setting `repository.full_name` to `"other-org/other-repo"` to target a stack they don't control.

### Impact Explanation
Depending on the event type, this allows an attacker who only holds one organization's webhook secret to inject verified-looking GitHub events against a completely unrelated repository's stack, e.g.:
- The `status` handler creates a `Status` record for an arbitrary `sha`/`state`/`context` on the target stack's commit, which feeds directly into `Commit#deployable?` used to gate deploys — forging a `success` status can make an otherwise-blocked commit deployable, contributing to an unauthorized deploy of a repository the attacker does not own.
- The `push` handler enqueues a `GithubSyncJob` against the victim stack.
- Other handlers (`check_suite`, `membership`, etc.) similarly act on the victim's `Repository`/`Stack` records.

This matches the "unauthorized deploy" cross-repository impact class, since it lets an attacker cross the organizational trust boundary Shipit is meant to enforce per-organization webhook secrets for.

### Likelihood Explanation
Requires the attacker to already hold a valid webhook secret for *some* organization configured on the Shipit instance (a real but weaker credential than full repository write access), and requires that Shipit instance to host stacks/repositories for multiple organizations that don't fully trust each other — a common multi-tenant Shipit deployment. No repository write access, GitHub App private key, or Shipit session/API token is needed, only knowledge of one org's `webhook_secret`.

### Recommendation
Cross-validate that the organization/owner used to select and verify the HMAC secret is the same owner embedded in `repository.full_name` (and `organization.login`) before dispatching to handlers; reject the request if they diverge. Alternatively, derive `repository_owner` and `repository_name` from the exact same JSON path so there is only one source of truth for which tenant a payload belongs to.

### Proof of Concept
1. Attacker legitimately administers `org-a` on the shared Shipit instance and knows `org-a`'s `webhook_secret`.
2. Attacker crafts a `status` (or `push`) webhook payload:
```json
{
  "repository": { "owner": { "login": "org-a" }, "full_name": "org-b/victim-repo" },
  "sha": "<victim commit sha>",
  "state": "success",
  "context": "ci/travis"
}
```
3. Attacker computes `X-Hub-Signature` using `org-a`'s known `webhook_secret` over the exact raw body.
4. `WebhooksController#verify_signature` resolves `repository_owner` to `"org-a"` (from `repository.owner.login`), fetches `org-a`'s `github_app`, and successfully verifies the signature.
5. `Shipit::Webhooks.for_event('status').each { |handler| handler.call(params) }` runs; the handler computes `repository_name` from `repository.full_name` = `"org-b/victim-repo"`, looks up `org-b`'s stack, and creates a forged `success` status on `org-b`'s commit — despite the request only ever being authenticated as belonging to `org-a`.

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
