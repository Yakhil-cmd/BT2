### Title
Race condition in private-asset doublespend "ununiquing" allows concurrent double-spend of a stable output - (File: validation.js)

### Summary
`isAnyOfKeysLocked` confirms the outer per-unit validation lock in `validation.js` (`mutex.lock(arrAuthorAddresses, …)`) only serializes units that share an *author* address [1](#0-0) . The doublespend-resolution write for private, fixed-denomination assets, however, is protected by a completely different, narrower lock key (`"private_write"`), taken deep inside `checkInputDoubleSpend`/`checkForDoublespends`, after the conflicting record has already been read (checked) outside that lock [2](#0-1) . This is structurally the same bug class as CVE-2022-1247: a shared, security-relevant piece of state (`inputs.is_unique`) is checked under one synchronization domain and mutated under a different, narrower one, opening a window where two units racing through validation can both be told "your doublespend was accepted" for the same `(asset, denomination, serial_number/src_output)` even though only one write should ever win.

### Finding Description
`checkForDoublespends` (`validation.js:1661-1705`) reads existing conflicting `inputs` rows for the unit currently being validated, and for every conflict decides whether it should be treated as an accepted double-spend of an older, not-yet-final unit [3](#0-2) . For public payments/assets the resolution is deferred: it is pushed into `objValidationState.arrAdditionalQueries`, to be executed later inside the same author-address-locked transaction in `writer.js` — this path is safe because it never leaves the outer `arrAuthorAddresses` lock.

For **private, fixed-denomination assets**, the code takes a shortcut and executes the "ununique" write immediately, using a *different* mutex key, `"private_write"`, instead of the `arrAuthorAddresses` lock that the whole `validate()` call is already holding:

```js
mutex.lock(["private_write"], function(unlock){
    console.log("--- will ununique the conflicts of unit "+objUnit.unit);
    conn.query(sql, doubleSpendVars, function(){
        objValidationState.arrDoubleSpendInputs.push({message_index, input_index});
        unlock();
        cb3();
    });
});
``` [4](#0-3) 

Because `isAnyOfKeysLocked` only detects overlap between two `arrKeys` arrays [5](#0-4) , and `"private_write"` is never a member of `arrAuthorAddresses`, this inner lock provides **no mutual exclusion with the outer per-author validation lock**. Two units that spend the *same private, fixed-denomination coin* but are validated on different DB connections (which happens for private payments delivered out-of-band via device messages/hub and validated through `validateAndSavePrivatePaymentChain` → `initPrivatePaymentValidationState`, rather than through the normal network `handleJoint` "handleJoint" gate) can concurrently:
1. Both run the `SELECT …` in `checkForDoublespends` and both see the *same* prior conflicting record with `is_unique=1` (nobody has ununiqued it yet).
2. Both independently reach `acceptDoublespends`, briefly serialize only around the actual `UPDATE inputs SET is_unique=NULL …` via the unrelated `"private_write"` key, and both push themselves into `arrDoubleSpendInputs`.
3. Each validation's own transaction subsequently proceeds to `ifOk`, and `writer.saveJoint` inserts its own `inputs` row with `is_unique = null` (since `arrDoubleSpendInputs` marks it) for a private/fixed-denomination coin, using `INSERT ... IGNORE` (`db.getIgnore()`) rather than a hard uniqueness violation [6](#0-5) , because private-asset validation intentionally treats non-final conflicts as coexisting non-unique claims until stability resolves them via `graph.determineIfIncludedOrEqual`.

The root problem mirrors CVE-2022-1247 exactly: a reference/uniqueness state (`is_unique`, analogous to `rose_neigh->use`) is checked in one code path and mutated in another path that is synchronized by an unrelated lock, letting a second "connect" (second spend of the same coin) slip through the same narrow window the first spend is still using to decide the coin is free.

### Impact Explanation
If two private-payment chains spending the *same* fixed-denomination coin race through validation concurrently (e.g., a malicious payer sends the same private coin to two different counterparties/cosigners at once — an unprivileged private-payment counterparty action, no special privilege required), both validations can independently conclude "double-spend accepted, my copy stays valid" and get persisted. This can result in a private asset being spent twice, i.e. a concrete double-spend of a stable/serial private output, which is a form of unauthorized/duplicated spending and asset-supply inflation for private indivisible assets.

### Likelihood Explanation
Reachability requires only that an attacker control a private, fixed-denomination asset coin and send conflicting private payments to two different recipients/cosigners at (nearly) the same time — well within the capability of an ordinary wallet user / private-payment counterparty, no node/peer/hub compromise needed. The window is small (a DB round-trip between the `SELECT` in `checkForDoublespends` and the `UPDATE` under `"private_write"`), but private-asset validation for multi-hop chains involves several sequential async DB calls per chain element, widening the race window compared to a single query. Because full confirmation would require independently reproducing device-to-device message timing, likelihood is assessed as medium, but the mechanism itself is concretely reachable and the mutex-key mismatch is unambiguous in the code.

### Recommendation
Serialize the doublespend acceptance path for private/fixed-denomination assets using the *same* lock domain as the rest of unit validation (e.g., include the owning address, or a per-asset-serial-number key, in the lock actually protecting the read-modify-write of `is_unique`), or move the read (`SELECT` in `checkForDoublespends`) inside the `"private_write"` critical section so the check-then-act is atomic with respect to all concurrent validators of the same coin, not just those sharing an author address with a completely different lock.

### Proof of Concept
Not independently executable within this review's scope — reproducing the race requires orchestrating two concurrent `validateAndSavePrivatePaymentChain` calls (e.g., via two device-message deliveries) referencing the same fixed-denomination `src_coin`/serial number, timed so both reach `checkInputDoubleSpend`'s `SELECT` before either's `"private_write"`-locked `UPDATE` completes. This would need to be validated with a live multi-connection DB test harness, which is outside the scope of this static analysis. The lock-key mismatch (`arrAuthorAddresses` vs `"private_write"`) itself is directly verifiable in [7](#0-6)  versus [8](#0-7) , and in `mutex.js`'s intersection-only lock check [5](#0-4) .

function checkForDoublespends(conn, type, sql, arrSqlArgs, objUnit, objValidationState, onAcceptedDoublespends, cb){
	conn.query(
		sql, 
		arrSqlArgs,
		function(rows){
			if (rows.length === 0)
				return cb();
			var arrAuthorAddresses = objUnit.authors.map(function(author) { return author.address; } );
			async.eachSeries(
				rows,
				function(objConflictingRecord, cb2){
					if (arrAuthorAddresses.indexOf(objConflictingRecord.address) === -1)
						throw Error("conflicting "+type+" spent from another address?");
					if (conf.bLight) // we can't use graph in light wallet, the private payment can be resent and revalidated when stable
						return cb2(objUnit.unit+": conflicting "+type);
					graph.determineIfIncludedOrEqual(conn, objConflictingRecord.unit, objUnit.parent_units, function(bIncluded){
						if (bIncluded){
							var error = objUnit.unit+": conflicting "+type+" in inner unit "+objConflictingRecord.unit;

							// too young (serial or nonserial)
							if (objConflictingRecord.main_chain_index > objValidationState.last_ball_mci || objConflictingRecord.main_chain_index === null)
								return cb2(error);

							// in good sequence (final state); final-bad is excluded by the query and treated as non-existent
							if (objConflictingRecord.sequence === 'good')
								return cb2(error);

							throw Error("unreachable code, conflicting "+type+" in unit "+objConflictingRecord.unit);
						}
						else{ // arrAddressesWithForkedPath is not set when validating private payments
							if (objValidationState.arrAddressesWithForkedPath && objValidationState.arrAddressesWithForkedPath.indexOf(objConflictingRecord.address) === -1)
								throw Error("double spending "+type+" without double spending address?");
							cb2();
						}
					});
				},
				function(err){
					if (err)
						return cb(err);
					onAcceptedDoublespends(cb);
				}
			);
		}
	);
}
