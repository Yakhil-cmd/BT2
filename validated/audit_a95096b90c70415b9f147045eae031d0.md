### Title
Regex-based sanitization of forged contract/dispute tags in device "text" messages can be bypassed with embedded newlines - ([File: wallet.js])

### Summary
`wallet.js`'s handling of the `"text"` device-message subject strips out marker tags such as `(prosaic-contract:...)`, `(arbiter-contract-offer:...)`, `(arbiter-contract-event:...)` and `(arbiter-dispute:...)` before the text is emitted to the wallet UI for display. The stripping regexes use `.+?` without the `s` (dotAll) flag, so they cannot match content that contains a newline character. A paired correspondent (an unprivileged peer that any wallet user can pair with) can send a forged `"text"` message embedding one of these tags with an injected `\n` inside the parenthesized payload; the sanitizer will fail to remove it, and the forged tag reaches the UI layer unmodified, exactly as the legitimate, hash-validated tags produced internally by `prosaic_contract_offer`/`arbiter_contract_offer`/`arbiter_dispute` handlers.

### Finding Description
When ocore receives a `"prosaic_contract_offer"` (or `"arbiter_contract_offer"`, `"arbiter_dispute"`) device message, it fully validates the contract fields (`title`, `text`, `creation_date`, hash match via `prosaic_contract.getHash`/`arbiter_contract.getHash`, address ownership, etc.) before it constructs a special chat marker and re-emits it as a `"text"` event: [1](#0-0) 

That marker (`(prosaic-contract:<base64>)`, `(arbiter-contract-offer:...)`, `(arbiter-dispute:...)`) is meant to be an internal signal consumed by the wallet UI (comment: "the wallet should have an event handler that displays the text to the user") to render special, actionable elements (e.g., "View/Accept contract") tied to the already-validated record stored via `prosaic_contract.store` / `arbiter_contract.store`.

However, an ordinary `"text"` chat message from any correspondent — the plain-text pathway that requires none of the above validation — is only defended against forging these same tags by a regex-strip step: [2](#0-1) 

The regexes `/\(prosaic-contract:.+?\)/g`, `/\(arbiter-contract-offer:.+?\)/g`, `/\(arbiter-contract-event:.+?\)/g`, and `/\(arbiter-dispute:.+?\)/g` use `.` which, in JavaScript without the `s` flag, never matches `\n`. Any correspondent can therefore send a `"text"` message whose body is:
```
(prosaic-contract:AAAA\nBBBB)
```
The pattern will not match (because `.+?` cannot cross the embedded newline), so the forged tag is **not stripped** and is passed unmodified to `eventBus.emit("text", from_address, body, message_counter)`, reaching the exact same UI surface that legitimate, hash-validated contract-offer tags reach — but this time completely unvalidated content, since the `"text"` subject bypasses the contract/hash/date/address checks performed on the `prosaic_contract_offer` / `arbiter_contract_offer` / `arbiter_dispute` subjects.

This is structurally identical to CVE-2022-29166: a message-boundary/format detector implemented with a regex that assumes single-line content is defeated by embedding a newline, letting attacker content be misclassified as a trusted, structured directive rather than being neutralized as plain text.

### Impact Explanation
Any wallet/UI built on ocore that listens for the `"text"` event and parses out `(prosaic-contract:...)`/`(arbiter-contract-offer:...)`/`(arbiter-dispute:...)` markers to surface "Accept contract"/"View dispute" actions to the user can be fed forged, attacker-controlled base64 payloads that were never checked against `getHash()`, `my_addresses` ownership, `creation_date` format, or `ttl`. A user who trusts the resulting UI prompt (because it visually/structurally matches a genuine contract or dispute notification) can be led into signing or paying against attacker-chosen terms (fake title/text/amount/addresses), resulting in loss of funds or acceptance of a malicious multisig/shared-address arrangement — i.e., unauthorized spending induced through a spoofed, unvalidated trust signal, analogous to the reply-injection command spoofing in the referenced CVE.

### Likelihood Explanation
Any device the user has paired with (a normal, low-privilege correspondent relationship established via pairing codes that are often shared somewhat broadly, e.g. bot pairing links) can send arbitrary `"text"` messages, which are only lightly gated (`ValidationUtils.isNonemptyString(body)`). Crafting a payload with an embedded `\n` inside the parentheses is trivial and requires no special access, making this a straightforward attack for any correspondent to attempt.

### Recommendation
Add the `s` (dotAll) flag to all four sanitizing regexes in `wallet.js` (or otherwise use a pattern that matches across newlines, e.g. `[\s\S]+?`), so that any embedded newline cannot be used to smuggle these reserved tags past the sanitizer:
```js
body = body
    .replace(/\(prosaic-contract:[\s\S]+?\)/g, '')
    .replace(/\(arbiter-contract-offer:[\s\S]+?\)/g, '')
    .replace(/\(arbiter-contract-event:[\s\S]+?\)/g, '')
    .replace(/\(arbiter-dispute:[\s\S]+?\)/g, '');
```
Additionally, downstream UI code that renders these tags should independently re-validate the referenced contract/dispute by hash against locally stored, previously-validated records rather than trusting the tag's embedded payload directly.

### Proof of Concept
1. Attacker pairs with victim's wallet as a normal correspondent (standard pairing flow).
2. Attacker sends a device message with `subject: "text"` and body:
   `"Hey, check this out (prosaic-contract:` + Buffer.from(JSON.stringify(fakeContractJson)).toString('base64').replace(/./, (m)=>m+'\n') + `)"`
   i.e., a payload containing a literal `\n` inside the parentheses (can simply insert `\n` anywhere between `(prosaic-contract:` and the closing `)`).
3. On the victim's node, `wallet.js`'s `"text"` handler at lines 105-109 applies the four `.replace(...)` calls; because of the embedded newline, `/\(prosaic-contract:.+?\)/g` does not match, so the tag is not removed.
4. `eventBus.emit("text", from_address, body, message_counter)` fires with the forged tag intact, identical in shape to a legitimately validated `(prosaic-contract:...)` marker, and reaches whatever UI event handler renders/acts on it — without ever having passed through the hash/address/date checks used in the genuine `prosaic_contract_offer` handler (`wallet.js` lines 455-480).
