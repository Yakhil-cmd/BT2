## Analysis Summary

I traced the external report's core invariant — *"approval/validation that should re-run every time can be silently skipped depending on an unchecked condition, letting the actually-executed action diverge from what was approved"* — to Aptos's multisig transaction admission path, `validate_multisig_transaction` in `multisig_account.move`, which is invoked by the VM as part of the transaction prologue.

I generated and discarded three weaker candidates first: (1) `TransactionAuthenticator::FeePayer` dual-message verification — sound, both zero-address and real-address messages are checked; (2) WebAuthn challenge binding in `PartialAuthenticatorAssertionResponse::verify` — sound, challenge bytes are checked against the actual message; (3) sequence-number/replay checks in `transaction_validation.move::prologue_common` — sound. The strongest candidate is the multisig payload-approval binding described below.

### Title
Multisig transaction execution can bypass payload-approval binding when `abort_if_multisig_payload_mismatch_enabled` is not active - (File: aptos-move/framework/aptos-framework/sources/multisig_account.move)

### Summary
`validate_multisig_transaction` is the VM-invoked admission check that is supposed to guarantee that the payload actually executed for a multisig transaction is the same payload the required quorum of owners approved. When a transaction was created via the "store full payload" path (`payload_hash` is `None`), the code only compares the caller-supplied payload against the stored, approved payload if the feature flag `abort_if_multisig_payload_mismatch_enabled` is turned on. If it is not enabled (or the caller passes an empty payload), no comparison happens at all, so the caller's own payload bytes — not the approved one — determine what gets executed.

### Finding Description
`validate_multisig_transaction` in [1](#0-0)  performs quorum/timelock checks against the stored `MultisigTransaction`, and then attempts to bind the actually-executed `payload` (an argument supplied by the executing owner's transaction) to what was approved:

```
if (transaction.payload_hash.is_some()) {
    let payload_hash = transaction.payload_hash.borrow();
    assert!(sha3_256(payload) == *payload_hash, error::invalid_argument(EPAYLOAD_DOES_NOT_MATCH_HASH));
};

if (features::abort_if_multisig_payload_mismatch_enabled()
    && transaction.payload.is_some()
    && !payload.is_empty()
) {
    let stored_payload = transaction.payload.borrow();
    assert!(payload == *stored_payload, error::invalid_argument(EPAYLOAD_DOES_NOT_MATCH));
}
``` [2](#0-1) 

There are two distinct storage modes for a pending multisig transaction: (a) only a `payload_hash` is stored (created via a "with hash" flow), or (b) the full `payload` is stored on-chain (the normal `create_transaction` flow). In mode (b), `transaction.payload_hash` is `None`, so the *first* assertion is a no-op. The *second* assertion — the only one capable of catching a mismatched full payload — is gated behind the `abort_if_multisig_payload_mismatch_enabled` feature flag, and additionally short-circuits whenever the caller-supplied `payload` argument is empty (`!payload.is_empty()`).

This means that whenever the feature flag is not active on a given network/deployment (the very existence of a feature-gate name like "abort_if_multisig_payload_mismatch_enabled" indicates this check is a *newly introduced, gradually-rolled-out* fix, not something guaranteed to be on everywhere), the function that quorum of owners voted to approve (the on-chain stored `payload`) is never compared against the payload bytes the final executing owner actually supplies to the VM for execution. Only sequence number, owner membership, and approval-count are checked — none of these bind the approved *content* of the call to the executed content when payload_hash is absent and the flag is off.

### Impact Explanation
This breaks the core authorization guarantee of a k-of-n multisig account: that funds/permissions can only move via an action that a quorum of owners explicitly approved. If the payload-match enforcement is not active, a single owner who is otherwise entitled to be *the executor* (which requires no extra approval beyond the already-established quorum) could execute the multisig transaction using a payload of their choosing rather than the one that was actually voted on and stored, since nothing at the admission boundary re-validates that binding in this code path. This is a state-transition-under-the-wrong-approval-set class issue — impact is High/Critical for any multisig account that relies on `create_transaction` (full-payload) semantics before this flag is fully enabled.

### Likelihood Explanation
The trigger requires no privileged access beyond being one of the existing multisig owners with execution rights already granted by network design (any owner can be the final executor once quorum is met) — this is an "unprivileged" bypass in the sense that the check that should further restrict *what* they can execute is absent. Likelihood is gated on the deployment-specific state of the `abort_if_multisig_payload_mismatch_enabled` feature flag, which I could not fully confirm as enabled/disabled by default in this snapshot (tool budget exhausted before completing that check). This uncertainty should be resolved before treating this as confirmed-exploitable in production: if the flag defaults to "enabled" and has been active since the feature was introduced, this issue exists only during any interim/rollback window; if it defaults to disabled, it is live today.

### Recommendation
Remove the feature gate and the `!payload.is_empty()` bypass on the payload-match assertion; always assert `payload == *stored_payload` whenever `transaction.payload.is_some()`, exactly mirroring the unconditional `payload_hash` check already performed. Alternatively, require that submitted payload can never be empty when the stored transaction carries a full payload, and if it is empty, substitute the stored payload for execution (i.e., the "omitted" convenience path should only be legal when it results in exactly the stored payload being executed, never a caller-chosen one).

### Proof of Concept
1. Owner A calls `create_transaction(owner_a, multisig_account, payload_A)`, storing `payload_A` fully on-chain (`payload_hash == None`, `payload == Some(payload_A)`).
2. Owners B, C vote to approve, reaching quorum for `payload_A`.
3. Owner A (or any owner with execute rights) submits the actual execution transaction with `MultisigTransactionPayload { multisig_address, transaction_payload: Some(payload_B) }` where `payload_B != payload_A` (e.g., transferring funds to a different recipient).
4. In `validate_multisig_transaction`, `transaction.payload_hash.is_some()` is false (mode b), so no hash check runs; if `features::abort_if_multisig_payload_mismatch_enabled()` is false, the second assertion block is skipped entirely.
5. The VM proceeds to execute `payload_B`, which was never voted on by owners B and C, using the quorum approval that was only ever granted for `payload_A`.

**Note on confidence:** I was unable to verify, within the remaining tool budget, whether `abort_if_multisig_payload_mismatch_enabled` defaults to enabled in this codebase snapshot (it appeared only in `aptos-move/framework/move-stdlib/sources/configs/features.move` and `aptos-release-builder`, which I did not get to open). This should be checked directly before treating exploitability as certain in current production configuration; the code-level admission gap itself is confirmed from the `multisig_account.move` source shown above.

    fun validate_multisig_transaction(
        owner: &signer, multisig_account: address, payload: vector<u8>) {
        assert_multisig_account_exists(multisig_account);
        assert_is_owner(owner, multisig_account);
        let sequence_number = last_resolved_sequence_number(multisig_account) + 1;
        assert_transaction_exists(multisig_account, sequence_number);

        if (features::multisig_v2_enhancement_feature_enabled()) {
            assert!(
                can_execute(address_of(owner), multisig_account, sequence_number),
                error::invalid_argument(ENOT_ENOUGH_APPROVALS),
            );
        }
        else {
            assert!(
                can_be_executed(multisig_account, sequence_number),
                error::invalid_argument(ENOT_ENOUGH_APPROVALS),
            );
        };

        // Count approvals, including the executing owner's implicit vote.
        let (num_approvals, _) = num_approvals_and_rejections(multisig_account, sequence_number);
        if (!has_voted_for_approval(multisig_account, sequence_number, address_of(owner))) {
            num_approvals += 1;
        };
        assert!(num_approvals >= num_signatures_required(multisig_account), error::invalid_argument(ENOT_ENOUGH_APPROVALS));

        // Timelock check — separate from quorum so the error is unambiguous.
        assert!(
            can_execute_with_timelock(multisig_account, sequence_number, num_approvals),
            error::invalid_state(ETIMELOCK_NOT_EXPIRED),
        );

        // If the transaction payload is not stored on chain, verify that the provided payload matches the hashes stored
        // on chain.
        let multisig_account_resource = borrow_global<MultisigAccount>(multisig_account);
        let transaction = multisig_account_resource.transactions.borrow(sequence_number);
        if (transaction.payload_hash.is_some()) {
            let payload_hash = transaction.payload_hash.borrow();
            assert!(
                sha3_256(payload) == *payload_hash,
                error::invalid_argument(EPAYLOAD_DOES_NOT_MATCH_HASH),
            );
        };

        // If the transaction payload is stored on chain and there is a provided payload,
        // verify that the provided payload matches the stored payload.
        if (features::abort_if_multisig_payload_mismatch_enabled()
            && transaction.payload.is_some()
            && !payload.is_empty()
        ) {
            let stored_payload = transaction.payload.borrow();
            assert!(
                payload == *stored_payload,
                error::invalid_argument(EPAYLOAD_DOES_NOT_MATCH),
            );
        }
    }
