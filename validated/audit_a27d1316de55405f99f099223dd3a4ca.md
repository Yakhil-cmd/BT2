This confirms the vulnerability chain. The multi-org GitHub App configuration (`Shipit.github_app_config`, documented in `docs/setup.md:182-209` and tested in `test/dummy/config/secrets_double_github_app.yml`) is a first-class, documented feature of the engine — not a misconfiguration. Each organization gets its own webhook secret, and `WebhooksController#verify_signature` selects **which** organization's secret to check against using an attacker-controlled field from the unauthenticated request body itself.### Title
Cross-organization webhook signature bypass allows forged CI status and stack-sync events on any repository - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App's webhook secret to authenticate a payload against using an attacker-controlled field taken from the *unauthenticated* request body itself (`repository.owner.login`, falling back to `organization.login`), while the code that actually acts on the payload resolves the target repository/stack from a *different* field in that same body (`repository.full_name` / `Commit.where(sha:)`). In the documented multi-organization configuration (`docs/setup.md`, `secrets_double_github_app.yml`), each org has its own independent `webhook_secret`, and any org configured without one accepts unsigned/unverified requests unconditionally. An attacker who controls (or is granted) one org in a multi-org Shipit install — especially one with no secret configured — can forge a webhook payload claiming `repository.owner.login` = their own org (to pass/bypass verification) while `repository.full_name` names a completely different, victim organization's repository, and the handler will act on the victim's stacks/commits without ever validating a real signature from that victim organization.

### Finding Description
`app/controllers/shipit/webhooks_controller.rb:24-30` selects the app config to verify against:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
```
`repository_owner` (lines 59-61) is read straight out of the untrusted, unverified JSON body:
```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```
`Shipit.github(organization:)` (`lib/shipit.rb:170-181, 196-200`) looks up a per-organization config block; `GitHubApp#verify_webhook_signature` (`lib/shipit/github_app.rb:76-83`) short-circuits entirely when that org has no `webhook_secret`:
```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
```
This "optional secret" behavior is explicitly documented and tested (`config/secrets.development.example.yml`, `secrets_double_github_app.yml`, `docs/setup.md:182-209`) as a supported multi-org setup where each org independently opts in/out of HMAC verification.

Once `verify_signature` passes, `WebhooksController#create` dispatches the raw JSON to handlers (`webhooks_controller.rb:10-15`), which resolve the actual target using unrelated fields of the same untrusted body:
- `Handler#repository_name` / `#stacks` uses `payload.dig('repository', 'full_name')` (`app/models/shipit/webhooks/handlers/handler.rb:32-38`), looked up via `Repository.from_github_repo_name` (`app/models/shipit/repository.rb:53-56`), which splits on `owner/name` independent of `repository.owner.login`.
- `StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`) matches purely on commit `sha`, with no repository/owner check at all — `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }`.
- `PushHandler#process` resolves stacks by branch within the (attacker-supplied) `repository.full_name`-derived scope and calls `stack.sync_github(expected_head_sha:)`.

Because `repository.owner.login` (used to pick the secret) and `repository.full_name` (used to pick the target) are two independent JSON fields with no cross-field validation, and because at least one configured org may have no secret at all, an attacker can construct a single JSON body where:
- `organization`/`repository.owner.login` = an org they control or one known to have no webhook secret configured (satisfies/bypasses `verify_signature`), and
- `repository.full_name` = `victim-org/victim-repo`, or a bare commit `sha` belonging to any stack in the install (drives the handler's actual side effects).

This breaks the intended binding: `organization authenticated == repository written`. The signature step authenticates (or waives authentication for) one organization, but the code that mutates state trusts a completely different, unauthenticated field for determining what to mutate.

### Impact Explanation
With `StatusHandler`, an attacker can inject an arbitrary CI status (`state: success`) for any known commit `sha` across the entire Shipit installation, without any signature matching that commit's real owning organization — this is exactly the kind of "unauthenticated write of stack/commit state" that can feed into `required_statuses`/merge-queue gating (`app/models/shipit/deploy_spec.rb:194-196`) used to authorize merges, i.e., contributing to an unauthorized merge. With `PushHandler`, arbitrary stacks can be forced to re-sync against an attacker-chosen `expected_head_sha`. This satisfies the High-impact bucket ("unauthenticated read/write of stack state") and can escalate toward the Critical bucket ("unauthorized merge") when combined with merge-queue automation that trusts commit statuses.

### Likelihood Explanation
Exploitation requires the deployment to use the documented multi-organization GitHub App configuration and for at least one configured organization to have no `webhook_secret` set (a state the engine's own example configs, `config/secrets.development.example.yml` and `secrets_double_github_app.yml`, treat as normal/supported, with the comment `webhook_secret: # nil`). No repository write access, API token, or session is needed — only knowledge/observation that some organization in a multi-org Shipit deployment lacks a webhook secret, or control of one org's own valid secret to pass verification while spoofing a different `repository.full_name`/`sha`. This is a design-level flaw in how the signature-selection field and the action-target field are decoupled, not merely a one-off misconfiguration bug.

### Recommendation
After verifying the webhook signature against `repository_owner`'s app config, re-validate that every field the handler subsequently uses to select a target (`repository.full_name`, `organization.login`, commit `sha` ownership) belongs to that *same, already-verified* organization before dispatching to handlers. Alternatively, bind signature verification to the resolved target repository's owning organization (looked up from `Repository.from_github_repo_name`) rather than to a raw, unauthenticated payload field, and require a webhook secret for every configured organization (rejecting configs that omit it) instead of silently trusting unsigned requests.

### Proof of Concept
1. Configure Shipit with two organizations, `AttackerOrg` (webhook_secret unset) and `VictimOrg` (real secret, real stacks/commits), as in `secrets_double_github_app.yml`.
2. POST to `/webhooks` with header `X-Github-Event: status` and body:
```json
{
  "sha": "<victim-commit-sha>",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "AttackerOrg" }, "full_name": "VictimOrg/victim-repo" }
}
```
No `X-Hub-Signature` header is required (or any arbitrary value works) because `verify_signature` resolves `Shipit.github(organization: "AttackerOrg")`, whose `webhook_secret` is nil, so `verify_webhook_signature` returns `true` unconditionally (`lib/shipit/github_app.rb:76-77`).
3. `StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`) matches on `sha` alone and creates a `success` status on the victim's commit, with no check that the verified organization (`AttackerOrg`) has any relationship to that commit's real repository (`VictimOrg`).
