### Title
Stale `bOpListCanChange` snapshot lets the main-chain stability point advance using an outdated OP-list check after a lock wait - ([File: main_chain.js])

### Summary
`determineIfStableInLaterUnitsAndUpdateStableMcFlag()` in `main_chain.js` snapshots whether the OP (order-provider) list can still change (`hasUnstableOpVoteCount()`) *before* it queues for the `"handleJoint"` mutex, then reuses that stale boolean after the lock is finally granted to decide whether each advancing MCI must be re-validated against the best parent's OP list. [1](#0-0) 

### Finding Description
The function first computes stability for `earlier_unit` without holding any lock, then re-acquires the `"handleJoint"` lock to actually advance the stability point: [2](#0-1) 

The check `const bOpListCanChange = hasUnstableOpVoteCount();` is evaluated immediately, but `mutex.lock(["handleJoint"], ...)` may have to wait for an arbitrary amount of time (other units are being validated/written, catchup, etc.) before this callback actually executes: [3](#0-2) [4](#0-3) 

`hasUnstableOpVoteCount()` derives its answer entirely from the current contents of `storage.assocUnstableMessages`: [5](#0-4) 

This cache is mutated concurrently by unrelated unit processing — every new unit carrying a `system_vote`/`system_vote_count` message is pushed into `assocUnstableMessages` as soon as it is written (`writer.js`), and entries are removed only when the unit's MCI stabilizes: [6](#0-5) 

Once the lock is finally granted, the code re-checks freshness of `last_stable_mci` and `objEarlierUnitProps.is_stable`/`main_chain_index` (a "did stability advance already" guard, correctly re-derived from fresh reads) but it never re-evaluates whether the OP-list-change condition is still accurate for the just-acquired window: [7](#0-6) 

The per-MCI loop only re-validates stability against the best parent's live OP list when `bOpListCanChange` is true: [8](#0-7) 

Because `bOpListCanChange` was captured before waiting for the lock, two divergent, order-dependent outcomes are possible depending purely on scheduling/timing of the local node's write queue:
- `bOpListCanChange` was `false` at snapshot time (no unstable `op_list` vote existed), but by the time the lock is granted a new unit carrying a `system_vote_count`/`op_list` message has been written and stabilization-in-progress code now (incorrectly) skips the mandatory best-parent-OP-list re-check for the mcis being advanced in this pass, blindly calling `stabilizeMci(mci)` for MCIs whose witness/OP-list validity was never actually confirmed under the currently-live (changing) OP list.
- Conversely, `bOpListCanChange` was `true`, but the vote that made it true itself finishes stabilizing (and is deleted from `assocUnstableMessages`) while waiting for the lock; the extra re-check then runs unnecessarily but harmlessly (this direction is not exploitable).

The dangerous direction is the first one: a unit poster can shape the timing of when an OP-list vote unit is broadcast/written relative to another unit's earlier-unit-stability computation, so that the snapshot is taken in the small window where the vote is not yet counted as "unstable", then have the vote land before the `"handleJoint"` lock is actually granted (lock contention on a busy node is easy to induce, e.g. by flooding units to serialize through `mutex.lock(["handleJoint"], ...)`). This is exactly analogous to the CVE's root cause: a "still valid" check is captured before releasing/waiting on a lock, and is trusted again after the lock is regranted without re-verifying it against the interim state change, so the code proceeds down a path (skip the mandatory best-parent-OP-list recheck) that assumes an invariant that no longer holds.

### Impact Explanation
If the OP list is skipped from re-validation at exactly the mci where it should have been re-verified, different nodes can reach a different stability decision for the same MCI depending on their own local lock-contention timing (since the snapshot moment is purely local scheduling, not a value derived from the DAG itself). This is a **node disagreement on validity/stability** class issue: honest nodes could stabilize different MCIs, or stabilize the same MCI using an OP list that a majority of the network would consider stale/incorrect, undermining consensus on which units/order-provider list is authoritative, potentially freezing further confirmations if nodes diverge on the main chain.

### Likelihood Explanation
Reaching this code path requires only posting units — no privileged network position, no malicious peer or hub — a normal unit poster can create a chain of units whose earlier unit becomes "stable in later units" while another unit is concurrently mutating `assocUnstableMessages` via a `system_vote_count`/`op_list` message. Triggering the specific race requires precise timing of when the `"handleJoint"` lock queue is contended (achievable by flooding units to serialize handling), so likelihood is non-trivial but plausible on a live network with realistic throughput. This is a genuine TOCTOU flaw in production consensus code, not a hypothetical.

### Recommendation
Recompute `hasUnstableOpVoteCount()` *after* the `"handleJoint"` lock has actually been granted (inside the callback, alongside the `last_stable_mci` freshness re-check), rather than snapshotting it before requesting the lock. This mirrors the fix pattern in the referenced CVE: re-validate the condition that justified skipping/choosing a code path at the exact point of use, not at the point where the check was originally made.

### Proof of Concept
1. Node A is processing many incoming units, causing its `"handleJoint"` mutex queue to build up (i.e., there is contention such that a `mutex.lock(["handleJoint"], ...)` call will wait non-trivially before executing).
2. A unit `E` (earlier_unit) is found to be stable-in-later-units by `determineIfStableInLaterUnits`. At the moment `hasUnstableOpVoteCount()` is evaluated, no unit carrying `system_vote_count`/`op_list` is present in `storage.assocUnstableMessages`, so `bOpListCanChange = false`.
3. Before Node A's queued `mutex.lock(["handleJoint"], ...)` callback actually runs, an attacker posts a new unit `V` containing a `system_vote_count` message with `payload === 'op_list'`. `writer.js` pushes this message into `storage.assocUnstableMessages[V]` as soon as `V` is written.
4. Node A's earlier queued callback for `E` finally executes with the lock held; it reuses the stale `bOpListCanChange = false` and advances the stability point for MCIs in range `[last_stable_mci+1, new_last_stable_mci]` via `stabilizeMci(mci)` without performing the best-parent-OP-list re-validation that the presence of `V`'s vote should have triggered.
5. Another node, whose local lock queue happened not to be contended at that moment, evaluates `hasUnstableOpVoteCount()` with `V` already counted, takes `bOpListCanChange = true`, and performs the extra re-check, potentially reaching a different stability conclusion for the same MCI range. function hasUnstableOpVoteCount() {
	for (let unit in storage.assocUnstableMessages) {
		for (let message of storage.assocUnstableMessages[unit]) {
			if (message.app === 'system_vote_count' && message.payload === 'op_list')
				return true;
		}
	}
	return false;
}
