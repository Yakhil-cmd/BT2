### Title
AA logic that relies on the `timestamp` oscript keyword can be manipulated by an unprivileged trigger sender who deliberately references a stale `last_ball` - ([File: formula/evaluation.js], [File: validation.js])

### Summary
The oscript `timestamp` keyword used inside Autonomous Agent (AA) formulas does not reflect the real-world clock or the timestamp of the trigger unit itself. It is populated from `objValidationState.last_ball_timestamp`, i.e. the timestamp of whichever already-stable MC ball the trigger's author chose to cite as `last_ball` when composing the unit.

### Finding Description
Inside formula evaluation, the `timestamp` operator simply returns the cached `last_ball_timestamp` from the validation state: [1](#0-0) 

That value is set from `objMcUnit.timestamp` (the last stable MC unit) when an AA trigger is processed: [2](#0-1) 

And, for a real (non-simulated) trigger, `last_ball_timestamp` comes straight from the `last_ball_unit` the author referenced in their own unit, validated here: [3](#0-2) 

Crucially, the constraint on which `last_ball` a poster may reference is only a monotonicity check relative to the chosen parents, not a freshness/recency check: [4](#0-3) 

The only clock-related check performed on the unit is on the unit's *own* `timestamp` field (must not be more than `max_seconds_into_the_future_to_accept`, default 5s, ahead of the validator's clock): [5](#0-4) 

There is no lower bound requiring `last_ball` (and therefore `last_ball_timestamp`) to be "recent." An unprivileged unit poster composing a raw unit (not via the standard wallet composer, which always auto-selects the freshest stable ball, see `objUnit.timestamp = Math.round(Date.now() / 1000);` and the following `pickParentUnitsAndLastBall` call) is free to pick older, already-stable parent units/`last_ball`, as long as it does not retreat below what those parents already used: [6](#0-5) 

Because deterministic AA execution (`objValidationState.last_ball_timestamp`) trusts whatever `last_ball` the trigger author supplies (bounded only from below by ancestry, never forced to be "now"), the AA-visible `timestamp` can lag arbitrarily far behind real time. This is analogous to the reported "block.timestamp manipulation" class: the value an AA treats as "current time" is attacker-influenced rather than derived from an untamperable, monotonically-advancing clock tied to the trigger's actual submission time.

### Impact Explanation
Many AA scripts use `timestamp` for time-gated business logic — expiry checks, deadline cut-offs, lock/unlock windows, or option/auction settlement conditions (as seen in the codebase's own sample contract using `timestamp > 1556668800` style guards): [7](#0-6) 

An attacker crafting a trigger unit that cites an intentionally old, already-stable `last_ball` can make such an AA "believe" less time has passed than actually has. For AA conditions gated on "must act before deadline X" (i.e., proceed only if `timestamp <= X`), this lets the attacker continue interacting with the contract (e.g., trigger favorable payouts, extend a supposedly-expired offer, or re-enter a window that should be closed) after the real-world deadline has passed — leading to AA fund loss/misallocation or freezing of funds that legitimate participants expected to be settled by then.

### Likelihood Explanation
Exploitation only requires composing a unit whose `last_ball_unit` (and consistent parents) reference an old but still valid, stable ball rather than the current MC tip — something achievable by anyone constructing a raw unit outside the default wallet composer flow, without any special privilege, hub cooperation, or race condition. The relevant validation code performs no freshness requirement on `last_ball`, only a non-retreating check against parents.

### Recommendation
- For AA-visible `timestamp`, prefer binding it more tightly to real elapsed time, e.g. reject triggers whose `last_ball_timestamp` is older than some bounded staleness threshold relative to the unit's own (clock-checked) `timestamp`, or use `mci` progression (which does have stronger deterministic guarantees) instead of `timestamp` for security-critical AA time logic.
- Document clearly for AA authors that `timestamp` reflects the referenced `last_ball`'s timestamp (attacker-selectable within DAG constraints) rather than the trigger's true submission time, and recommend using `mci`-based deadlines or requiring a minimum number of confirmations before honoring time-sensitive branches.

### Proof of Concept
1. An AA is deployed with logic such as: `if (timestamp <= DEADLINE) { ...favorable branch... } else { bounce('expired'); }` (pattern present in `test/samples/option_contract.oscript`).
2. After `DEADLINE` has passed in real time, an attacker composes a raw trigger unit referencing `parent_units`/`last_ball_unit` from a stable ball whose timestamp is still `<= DEADLINE` (permitted because `validateParents` only forbids the `last_ball_mci` from retreating below the parents' own `last_ball_mci`, not from being "old"): [4](#0-3) 
3. The unit's own `timestamp` field passes the only real clock check (within 5s of now): [8](#0-7) 
4. When the AA executes, `objValidationState.last_ball_timestamp` is taken from the attacker-chosen stale `last_ball`, so `timestamp` in the oscript evaluates to a value `<= DEADLINE`, and the "favorable" branch executes even though real-world time is past `DEADLINE`.
