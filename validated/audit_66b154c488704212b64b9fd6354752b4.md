## Finding: Webhook signature verification can be bypassed via organization-config confusion across a multi-org Shipit deployment

### Title
Webhook authentication bypass via attacker-chosen `repository.owner.login` selecting an unsecured GitHub App config — ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App configuration (and therefore which `webhook_secret`) is used to validate the inbound webhook's HMAC signature based on a field taken directly from the *unauthenticated* JSON body (`repository.owner.login`, falling back to `organization.login`). If a Shipit deployment configures multiple GitHub organizations (a documented, supported setup) and any one of them has no `webhook_secret` configured, an attacker can forge a payload whose `owner`/`organization` field names that unsecured org while other payload fields (used later by the actual event handlers) reference a different, properly-secured org's tracked repository — causing signature verification to be skipped entirely for a payload that is then dispatched unmodified to the handlers.

### Finding Description
`verify_signature` computes `repository_owner` purely from request body content, before any cryptographic check: [1](#0-0) 

That value is used to look up which `GithubApp`/secret to verify against: [2](#0-1) 

`verify_webhook_signature` in the resolved app config short-circuits to `true` whenever that particular org's `webhook_secret` is blank — i.e., signature checking is entirely skipped for organizations configured without a secret: [3](#0-2) 

Multi-organization configuration, where each org gets its own independent `webhook_secret` entry (and it can be left blank), is a documented and tested configuration shape: [4](#0-3) [5](#0-4) 

Because `params` (the full attacker-supplied JSON body) is passed unchanged to every registered handler after `verify_signature` passes... [6](#0-5) 

...an attacker can submit a payload whose `repository.owner.login`/`organization.login` names the org that lacks a `webhook_secret` (bypassing verification), while any other field consumed by the handler logic (e.g., `repository.full_name`, `sha`, `state`, `after`) can be set independently within the same JSON body. This is the same class of bug as the Redstone oracle report: the code assumes a single value (the Redstone report's shared timestamp; here, the webhook's org) is authoritative for validation and is trustworthy for downstream logic, when in fact the untrusted input can supply inconsistent values for the field used to *authenticate* versus the fields used to *act*.

I was not able to fully trace, within the remaining investigation budget, the exact handler code that resolves a `Stack`/`Commit` purely from `repository.full_name` independent of `owner.login` (e.g. the push/status handlers under `app/models/shipit/webhooks/handlers/`), so the precise scope of which fields the handlers trust versus cross-check against `repository_owner` is not fully confirmed from the code read so far. This should be verified before treating the full cross-repository-write impact as proven; the signature-bypass mechanism itself, however, is directly supported by the cited code.

### Impact Explanation
If confirmed against the handler code, this allows an unauthenticated attacker to inject forged `push`, `status`, or `check_suite` events for any repository tracked by Shipit — as long as the deployment has at least one configured GitHub organization with no `webhook_secret`. Forged `status` events can mark commits as deployable/mergeable, and forged `push` events can trigger sync jobs, potentially leading to unauthorized deploys or merges — squarely within the "unauthorized deploy, rollback or merge" Critical-impact category defined in scope.

### Likelihood Explanation
Requires: (1) a multi-organization Shipit deployment (documented/supported feature), and (2) at least one configured organization without a `webhook_secret`. Leaving `webhook_secret` blank is explicitly supported by `verify_webhook_signature`'s `return true unless webhook_secret` fallback rather than being rejected, so it's a plausible real-world misconfiguration, not a contrived edge case. No credentials or prior access are required — the attacker only needs to know or guess the `login` of the unsecured configured organization, information that is generally public.

### Recommendation
- Do not derive the org used for signature verification solely from unauthenticated request content when the outcome of that lookup can itself waive verification.
- Reject (422) any webhook when the resolved GitHub App has no `webhook_secret` configured, rather than treating a missing secret as "signature verified."
- Cross-validate that the org resolved for signature verification matches the org actually referenced by the repository/organization data the handlers act upon before dispatching to handlers.

### Proof of Concept (conceptual — pending handler confirmation)
1. Deployment configures two orgs: `OrgTwo` (no `webhook_secret`) and `OrgOne` (has a `webhook_secret`, and owns a repo tracked as a Shipit `Stack`).
2. Attacker POSTs to `/webhooks` with `X-Github-Event: push`, an arbitrary/garbage `X-Hub-Signature`, and a JSON body where `repository.owner.login = "OrgTwo"` but `repository.full_name = "OrgOne/tracked-repo"` (and other push fields crafted to match the tracked stack/branch).
3. `verify_signature` resolves `Shipit.github(organization: "OrgTwo")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` unconditionally regardless of the actual (invalid) signature. [7](#0-6) 
4. The full attacker-controlled `params` (naming `OrgOne/tracked-repo`) is dispatched to registered `push` handlers as if it were a legitimately signed webhook from GitHub. [8](#0-7)

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently.
