### Title
Webhook authentication is bound to `repository.owner.login`, but event processing is bound to a different, unauthenticated field (`repository.full_name`) — ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController` selects which GitHub App/organization config (and therefore which `webhook_secret`) to verify a webhook's HMAC signature against based on `repository.owner.login`, but the handlers that actually act on the payload (create commits, statuses, sync stacks, create teams/memberships) key off a completely different field — `repository.full_name` (or `organization.login`/`team` for membership events). Because Shipit supports multiple GitHub organizations, each with an independently optional `webhook_secret` (`webhook_secret: # nil` is a documented, valid configuration), an attacker can pick an org that has no secret configured to make signature verification vacuously pass, while pointing the payload's `repository.full_name` at a victim organization's stack.

### Finding Description
`WebhooksController#verify_signature` resolves the app config purely from the attacker-controlled JSON body: [1](#0-0) [2](#0-1) 

`GitHubApp#verify_webhook_signature` treats an unset `webhook_secret` as "always verified": [3](#0-2) 

The equality that should hold is:
`organization authenticated (repository.owner.login → webhook_secret used) == organization actually written to (repository.full_name's owner)`

Downstream handlers, however, derive the target repository/stack from a separate JSON field that is never covered by the authentication decision: [4](#0-3) [5](#0-4) 

Because the entire raw body is attacker-supplied and both fields live in the same untrusted JSON, nothing forces `repository.owner.login` (used to pick the signing secret) to match `repository.full_name`'s owner (used to pick the Stack/Repository that gets mutated). If any one configured organization in `Shipit.github` has `webhook_secret` unset — an explicitly supported configuration shown in the shipped example config — an attacker can set `repository.owner.login` to that org to make `verify_webhook_signature` return `true` unconditionally, while setting `repository.full_name` to any victim org/repo tracked by Shipit.

### Impact Explanation
This breaks the authentication boundary that protects unauthenticated webhook ingestion entirely — no Shipit session, ApiClient token, or GitHub credentials are required, satisfying the "unprivileged attacker" requirement. With signature verification bypassed for the target repository, an attacker can:
- Forge `status`/`check_suite` events reporting fabricated "success" CI states on arbitrary commits of a victim stack, which — combined with `continuous_deployment: true` — can trigger an **unauthorized deploy** of a commit that never actually passed CI (Critical, matches the accepted "unauthorized deploy" impact category).
- Forge `push` events to make `GithubSyncJob` fetch/append attacker-chosen state for a victim stack.
- Forge `membership` events to auto-create arbitrary `Team`/`User`/`Membership` records, potentially colliding with a team referenced in `Shipit.github_teams`, escalating into the `authorized?` check used for access control (High, matches "escalation into `Shipit.github_teams` authorization").

### Likelihood Explanation
Requires only that the deployment operator configure at least two GitHub organizations in `Shipit.github`, with at least one of them (which need not be the victim org) left without a `webhook_secret` — a state the shipped example config (`config/secrets.development.example.yml`) explicitly documents as valid (`webhook_secret: # nil`). This is a realistic, supported deployment pattern (e.g., staging/internal org with signature checking disabled while production orgs have secrets), not a misconfiguration outside documented behavior.

### Recommendation
Bind the authentication decision to the same entity that is mutated: after computing the payload's target repository (`repository.full_name` or `organization.login`), verify that its owner matches the `repository_owner` used to select the `webhook_secret`/app config, and reject the request if they diverge. Additionally, do not allow `verify_webhook_signature` to silently return `true` when `webhook_secret` is blank for a specific org unless that behavior is a deliberate, isolated opt-out that cannot be triggered by attacker-supplied fields naming an unrelated organization's repository.

### Proof of Concept
1. Operator configures `Shipit.github` with two orgs: `victim-org` (has `webhook_secret` set) and `low-trust-org` (no `webhook_secret`, e.g., a staging/internal org).
2. Attacker sends `POST /github/webhooks` with header `X-Github-Event: status` and body:
```json
{
  "sha": "<victim-commit-sha>",
  "state": "success",
  "context": "ci/required-check",
  "repository": {
    "full_name": "victim-org/victim-repo",
    "owner": { "login": "low-trust-org" }
  }
}
```
No `X-Hub-Signature` matching `low-trust-org`'s (nonexistent) secret is required — `verify_webhook_signature` returns `true` because `webhook_secret` is blank for `low-trust-org`.
3. `WebhooksController` proceeds to `Shipit::Webhooks.for_event('status')`, whose handler resolves the target stack via `repository.full_name` = `victim-org/victim-repo`, creating a forged "success" `Status` on the victim's commit — as shown in `app/models/shipit/webhooks/handlers/handler.rb` line 37 (`payload.dig('repository', 'full_name')`).
4. If `victim-org/victim-repo`'s stack has `continuous_deployment: true` and this forged status satisfies `required_statuses`, an automatic deploy is triggered on an unreviewed commit.

Note: I was unable to fully inspect `Shipit.github`'s multi-org resolution implementation in `lib/shipit.rb` (the `read_file` calls to confirm its exact registry/lookup logic did not complete), so the precise mechanics of how `organization:` maps to a `GitHubApp` instance should be double-checked in that file before treating this as fully confirmed, though the controller/handler code cited above is sufficient to establish the binding mismatch.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
