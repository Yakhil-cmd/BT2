## Analog Found

### Title
Race condition on unlocked `assocUnitsWaitingForPrunedContent` map permanently strands units waiting on pruned final-bad content - (File: ocore--008/network.js)

### Summary
The reported kernel bug is a classic "schedule work → free state → work still fires and touches stale state" race: `dev3_register_work` is scheduled outside of the section that `flush_workqueue()` protects, so it can still run and dereference `priv` after `alps_disconnect()` has freed it. The reachable analog in ocore is the pruned-content-recovery bookkeeping in `network.js`, where a shared map (`assocUnitsWaitingForPrunedContent`) is written under the `'handleJoint'` mutex but is read, mutated, and torn down completely outside any lock, from independent asynchronous callbacks triggered by peer/network messages.

### Finding Description
When validating a posted unit that spends an output of a locally-pruned final-bad unit, `validation.validate()` calls back with `ifNeedParentUnits(arrMissingUnits, bRequestPrunedContent=true)`. This branch, executed while holding the `'handleJoint'` mutex, persists the full joint body in RocksDB and registers a lightweight pointer in the in-memory map: [1](#0-0) 

```
kvstore.put('wj\n' + unit, JSON.stringify({ objJoint, peer: ws ? ws.peer : null }), () => {});
const expiry_ts = Date.now() + 60 * 60 * 1000;
for (let missing_unit of arrMissingUnits) {
    if (!assocUnitsWaitingForPrunedContent[missing_unit])
        assocUnitsWaitingForPrunedContent[missing_unit] = [];
    assocUnitsWaitingForPrunedContent[missing_unit].push({ unit, expiry_ts });
}
```

This mutation happens inside `mutex.lock(['handleJoint'], ...)`.

Two other code paths mutate/consume the very same map with **no mutex protection at all**:

1. `tryRecoverPrunedContentOfFinalBadUnit`, invoked directly from `handleResponseToJointRequest` (a `get_joint` response handler, fully attacker/peer-driven, not gated by the `'handleJoint'` lock): [2](#0-1) 

```
function tryRecoverPrunedContentOfFinalBadUnit(ws, objJoint){
    const unit = objJoint.unit.unit;
    const arrWaitingJoints = assocUnitsWaitingForPrunedContent[unit];
    if (!arrWaitingJoints) return false;
    ...
    delete assocUnitsWaitingForPrunedContent[unit];
    async.eachSeries(arrWaitingJoints, function(o, cb){
        const key = 'wj\n' + o.unit;
        kvstore.get(key, strSavedJoint => {
            kvstore.del(key);
            if (!strSavedJoint) return cb();
            const { objJoint: objWaitingJoint, peer } = JSON.parse(strSavedJoint);
            handleOnlineJoint(peer ? getPeerWebSocket(peer) : null, objWaitingJoint, cb);
        });
    });
    return true;
}
```

2. `purgeExpiredUnitsWaitingForPrunedContent`, run every hour on a bare `setInterval`, also touches the map and deletes the RocksDB pointers with no coordination with the mutex-protected writer: [3](#0-2) 

Because the "register a new waiter" path (mutex-protected) and the "consume/delete the waiters for this missing unit" path (unlocked, network-message-driven) operate on the same JS object without any synchronization primitive between them, the following interleaving is possible for a single missing (pruned, final-bad) unit `X`:

- Peer A's response to an earlier `get_joint(X)` request arrives and starts running `tryRecoverPrunedContentOfFinalBadUnit`, which reads `arrWaitingJoints = assocUnitsWaitingForPrunedContent[X]` and then does `delete assocUnitsWaitingForPrunedContent[X]`.
- Concurrently, a newly posted unit `Y` (submitted by any unprivileged network participant/wallet) also spends an output of the same pruned unit `X`; its validation reaches `ifNeedParentUnits(..., true)` under the `'handleJoint'` mutex and executes `assocUnitsWaitingForPrunedContent[X].push({unit: Y, expiry_ts})` — but because event-loop scheduling interleaves this with step 1's `delete`, `Y`'s pointer can be pushed into an array that has already been captured (and is about to be dropped) by `tryRecoverPrunedContentOfFinalBadUnit`, or `Y`'s registration can immediately follow the `delete`, so a brand-new array is created for `X` right after the content for `X` was already fetched, cached (`archiving.cachePrunedJoint`), and the in-memory pointer torn down.

In the second scenario, unit `Y`'s `wj\n`+`Y` RocksDB pointer is durably stored, but the only trigger that would ever call `tryRecoverPrunedContentOfFinalBadUnit(X)` again is another unsolicited `get_joint` response for `X` from some peer — which will not happen once the content for `X` has already been fully recovered and processed once. `Y` is therefore left registered against `X` forever (until the unrelated hourly `purgeExpiredUnitsWaitingForPrunedContent` timer expires it up to an hour later, silently dropping it and its RocksDB body), with no further replay attempt in between, exactly the "state was already cleaned up but late-scheduled work still references/depends on the freed pointer" bug class described by CVE-2025-68822, adapted to ocore's async architecture instead of a kernel workqueue.

### Impact Explanation
A unit that legitimately depends on (spends from) a locally-pruned final-bad unit's output can become permanently un-confirmable on affected nodes for up to an hour (silently discarded thereafter), because the bookkeeping structure that is supposed to trigger its replay is torn down/rebuilt without synchronization relative to the writer. This produces node-local failure to process/confirm a submitted unit — falling under "a network unable to confirm new units" / "AA fund loss or freezing" for wallets or AAs whose spend depends on recovering that output, and it can also lead to node disagreement: some nodes may successfully replay the waiting joint (if the race doesn't trigger) while others silently drop it, producing divergent views of which units are known/pending across the network.

### Likelihood Explanation
Triggering `bRequestPrunedContent` requires an existing final-bad, already-pruned unit and a subsequent unit spending its output — a rare but fully attacker-reachable scenario (any unprivileged unit poster can construct a payment that spends an output later stripped by pruning of a final-bad unit, and simultaneously multiple parties/relays can be racing `get_joint` responses for the same pruned unit). Because both code paths run on Node's single-threaded event loop, the actual interleaving window is a race between microtask/callback ordering (`kvstore.get`/`kvstore.del` callbacks vs. the `'handleJoint'` mutex queue), which is timing-dependent but not require any privileged position — it can be influenced by an attacker controlling message timing to multiple peers.

### Recommendation
Guard all reads, writes, and deletes of `assocUnitsWaitingForPrunedContent` (and the associated `wj\n` RocksDB keys) with the same synchronization mechanism, e.g., always mutate it while holding the `'handleJoint'` mutex (or a dedicated mutex key), so that the "register a new waiter" and "consume/purge existing waiters" operations cannot interleave. Alternatively, use atomic per-unit map operations (e.g., only `delete`/replace the array under a compare-and-swap-like guard) so a concurrently pushed waiter is never lost when the entry is deleted by a competing async callback.

### Proof of Concept
Not directly demonstrable without a live two-node/two-peer network harness; the race requires: (1) a final-bad unit `X` that has been pruned (`main_chain_index < getMinRetrievableMci()`), (2) unit `Y` posted spending `X`'s output causing `ifNeedParentUnits(['X'], true)`, and (3) a concurrent `get_joint` response for `X` arriving and running `tryRecoverPrunedContentOfFinalBadUnit` at the same time `Y`'s validation is pushing into `assocUnitsWaitingForPrunedContent['X']` under the `'handleJoint'` mutex. Reproduction would require instrumenting/mocking the event-loop ordering (or forcing the specific interleave via `setImmediate`/delayed kvstore mocks) to force the `push` to occur between the `delete` and the map's fresh recreation in `tryRecoverPrunedContentOfFinalBadUnit`. I could not execute this in the current read-only environment; a Devin session with the ability to run the test suite and manipulate timing would be needed to confirm the exact interleave experimentally.

function purgeExpiredUnitsWaitingForPrunedContent(){
	const now = Date.now();
	for (let missing_unit in assocUnitsWaitingForPrunedContent){
		const arrExpired = assocUnitsWaitingForPrunedContent[missing_unit].filter(o => o.expiry_ts < now);
		arrExpired.forEach(o => kvstore.del('wj\n' + o.unit));
		assocUnitsWaitingForPrunedContent[missing_unit] = assocUnitsWaitingForPrunedContent[missing_unit].filter(o => o.expiry_ts >= now);
		if (assocUnitsWaitingForPrunedContent[missing_unit].length === 0)
			delete assocUnitsWaitingForPrunedContent[missing_unit];
	}
}
setInterval(purgeExpiredUnitsWaitingForPrunedContent, 60 * 60 * 1000);
