### Title
Unbounded accumulation of dust outputs on an AA address can prevent the AA from ever completing a payment response - (File: aa_composer.js)

### Summary
In `Carousel.sol`, an unbounded `rolloverQueue` array that is fully read into memory on every `mintRollovers` call eventually makes the function revert once enough unprivileged users have queued entries, permanently freezing the mechanism. The analogous pattern in `ocore` is the coin-selection logic AA responses use to fund their own outgoing payments: `completePaymentPayload`/`readStableOutputs`/`iterateUnspentOutputs` inside `handleTrigger`'s `sendUnit` in `aa_composer.js`, which selects unspent outputs belonging to the AA address with an unbounded, un-LIMITed SQL query and then iterates the full result set in memory to build the `inputs` array of the response payment.

### Finding Description
When an AA needs to send a payment (including a "send-all" response or a response requiring more than one output to cover the target amount), `completePaymentPayload` calls `readStableOutputs`, which queries every unspent, non-AA-response output belonging to the AA address for the given asset with **no `LIMIT` clause**: [1](#0-0) 

The result set is consumed entirely in memory by `iterateUnspentOutputs`, which pushes one `input` entry into `payload.inputs` per row until the target amount is reached: [2](#0-1) 

For the base asset, there is a dust-filter (`amount>=FULL_TRANSFER_INPUT_SIZE`) explicitly described in the code as protection "to prevent dust attack: spamming the AA with very small outputs so that the AA spends all its money for fees when it tries to respond": [3](#0-2) 

However, `readUnstableOutputsSentByAAs`, used for outputs sent to the AA by other AAs (unstable, not yet included in a stable MC ball), applies the same size filter only for the base asset, and any unprivileged party can trigger other AAs (or send outputs directly) that leave many tiny outputs on the target AA's balance sheet: [4](#0-3) 

Because every unspent output the AA owns is eligible to be selected as an input, and any address (an unprivileged unit poster / AA trigger sender) can send unlimited tiny payments to an AA address over time (each transfer just needs to cover its own commission, not the recipient AA's future spending costs), the AA's set of spendable outputs for a given asset can grow without bound. Each output selected as an input consumes space in the response unit's `payload.inputs` array; the number of inputs a single payment message may contain is bounded by protocol-level limits (`constants.MAX_MESSAGES_PER_UNIT`, `MAX_INPUTS_PER_PAYMENT_MESSAGE` referenced in `inputs.js`/`indivisible_asset.js`). If the number of tiny outputs needed to reach the AA's own required payout ever exceeds what a single unit can encode, or the accumulated size/oversize fee calculations before hitting the amount target consume most of the transferred value, the AA's outgoing payment can never be composed successfully — the AA is permanently unable to fulfill legitimate payouts in that asset, analogous to `mintRollovers` reverting once `rolloverQueue` is too large.

### Impact Explanation
An attacker can flood an AA address (any AA that must later send a payment/response, e.g. a bounce, a send-all, or a payout in a custom asset that lacks the dust-size guard) with many small outputs of a custom asset (the byte dust guard doesn't defend other assets, and issued/attested tokens routed through AAs are common). Once the number of such outputs required to satisfy a subsequent AA response exceeds the per-message/per-unit input limits, that AA permanently fails to respond correctly for that asset — funds held by the AA in that asset become effectively frozen (AA fund loss/freezing), and legitimate users interacting with the AA can no longer receive their expected payouts. This matches the "AA fund loss or freezing" acceptance criterion.

### Likelihood Explanation
Likelihood is moderate: creating many small outputs to a known AA address is cheap for an attacker (bounded only by their own transaction fees), and many AAs (e.g., token-distribution, DEX, or bridge AAs) route custom-asset balances that lack the FULL_TRANSFER_INPUT_SIZE dust filter used for base-asset outputs. The condition requires accumulation over time and a subsequent AA logic path that needs to spend enough of the dusted asset balance to trigger the input-count limit, so it is not an immediate one-shot revert but a griefing/DoS vector that degrades and eventually can permanently break specific AA payout paths.

### Recommendation
- Apply the existing dust-size filtering strategy (used for base-asset outputs in `readStableOutputs`/`readUnstableOutputsSentByAAs`) uniformly to non-base assets, or make the minimum acceptable incoming output amount asset-aware (e.g. proportional to typical input overhead in that asset).
- Add an explicit cap on the number of unspent outputs considered/consumed per response (`LIMIT` in the SQL query plus a hard cap check before adding inputs), analogous to the `constants.MAX_MESSAGES_PER_UNIT - 1` guard already used in `indivisible_asset.js`'s `pickNextCoin`, and bounce cleanly with a clear error instead of silently failing to compose a valid unit.
- Consider a periodic/administrative "sweep" mechanism (or AA-authorable consolidation) to merge dust outputs before they threaten the input-count limit, or reject incoming outputs below a protocol-enforced minimum viable amount regardless of asset.

### Proof of Concept
1. Deploy/trigger an AA that receives and eventually must return balances in a custom asset that does not benefit from the `FULL_TRANSFER_INPUT_SIZE` dust guard (i.e., `asset` is set, not base).
2. Repeatedly trigger payments of the smallest possible amount (e.g., 1 unit of denomination) of that asset to the AA address from many different unprivileged unit-posting accounts, accumulating hundreds/thousands of tiny unspent outputs owned by the AA for that asset.
3. Trigger a subsequent AA response (e.g., a send-all payout or a payout requiring the AA to spend a large amount in that asset) that must call `completePaymentPayload` → `readStableOutputs`/`readUnstableOutputsSentByAAs` → `iterateUnspentOutputs`.
4. Observe that `iterateUnspentOutputs` must traverse and include a large number of tiny inputs to reach `target_amount`, eventually exceeding the maximum permissible inputs for a single payment message/unit, causing the AA's payment composition to fail to produce a valid unit and the AA to bounce or become unable to complete the payout — freezing funds held by the AA in that asset.
