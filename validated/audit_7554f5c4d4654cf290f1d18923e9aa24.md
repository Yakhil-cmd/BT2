## Title
Uncaught exception crashes full nodes on a crafted private-asset double-spend conflict - (File: `validation.js`)

## Summary
`validatePaymentInputsAndOutputs()` in `validation.js` deliberately `throw`s an uncaught `Error` instead of returning a normal validation error whenever a **private-asset** input's double-spend check comes back with a conflict that the code doesn't already whitelist as an "accepted double-spend". Because `network.js` intentionally re-throws inside its global `uncaughtException` handler to "crash the process to avoid ending up in an inconsistent state", any peer (an asset issuer or the counterparty of a private payment) can craft a private-asset payment/chain that reaches this branch and crash every full (non-light) node that validates it — a direct analog of the CVE's "improper input validation... denial of service" class.

## Finding Description
`checkForDoublespends()` resolves a conflicting spend record either as:
- an accepted double-spend (calls `onAcceptedDoublespends`), or
- a rejected conflict, passed back as `err` to its `cb` callback. [1](#0-0) 

In `validatePaymentInputsAndOutputs()`, the `onDone` callback that receives this `err` for a divisible input is:

```js
function onDone(err){
    if (err && objAsset && objAsset.is_private && !conf.bLight)
        throw Error("spend proof didn't help: "+err);
    cb2(err);
}
``` [2](#0-1) 

For a public asset, `err` is simply propagated to `cb2(err)`, which becomes an ordinary "unit is invalid" verdict. But for a **private** asset on any node that is not `conf.bLight` (i.e. every full/hub node), the exact same "spend proof didn't help" condition instead throws. This throw happens inside a deeply nested `async`/DB-callback chain, so it cannot be caught by any surrounding `try/catch` in the validation call stack — it propagates to Node's `process.on('uncaughtException', ...)` handler in `network.js`, which logs it and then explicitly re-throws to crash the process:

```js
process.on('uncaughtException', (err) => {
    ...
    throw err; // crash the process to avoid ending up in an inconsistent state
});
``` [3](#0-2) 

This code path is reachable from ordinary user-level actions:
- Validating a divisible/indivisible private payment chain (`indivisible_asset.js` `validatePrivatePayment`, and `validation.js` `validatePayment`/`validatePaymentInputsAndOutputs`) which is exactly the path exercised when a private-payment counterparty forwards a chain that references a conflicting/older spend of the same private output. [4](#0-3) [5](#0-4) 

The condition that trips the `throw` (rather than the "accepted doublespend" branch) is reached when `checkForDoublespends` finds that the conflicting spend-proof's owning unit is included in the new unit's ancestry (`bIncluded===true`) and is either:
- not yet stable / too young (`main_chain_index > last_ball_mci` or `null`), or
- already finally accepted with `sequence === 'good'` [6](#0-5) 

Both of these are attacker-controllable: a malicious asset issuer/private-payment sender can build two private payment chains from the same private asset input where the second one's `parent_units` legitimately include the first (already-confirmed) spend, satisfying `bIncluded` while `sequence === 'good'`. Feeding the second chain to a peer/node for validation drives the code straight into the `throw Error("spend proof didn't help: ...")` branch.

## Impact Explanation
Because the throw happens for **any full node** (`!conf.bLight`) that validates the crafted private payment, and `network.js`'s handler purposely re-throws to kill the process, a single crafted private-payment message can crash any full node/hub that processes it (directly, or by relaying/validating it on behalf of a wallet). Since private payments are typically forwarded peer-to-peer and revalidated by each recipient's node, this can be used to selectively or broadly crash full nodes that handle a given asset's private payments, i.e. a network unable to confirm new units for the affected population of nodes — matching the CVE's DoS impact class.

## Likelihood Explanation
Likelihood is high for anyone acting as an issuer or counterparty of a private asset: the double-spend detection logic itself is standard and frequently exercised code (`checkInputDoubleSpend`/`checkForDoublespends`), and the special-cased `throw` for private assets is trivially reachable by constructing a second private-asset transfer whose ancestry already contains an accepted spend of the same output — a scenario that requires no privileged access, only the ability to compose and send a private payment chain, which is a normal wallet operation.

## Recommendation
Remove the `throw Error("spend proof didn't help: "+err)` branch and instead propagate `err` through the normal validation-failure callback (`cb2(err)`), exactly as is already done for non-private assets. If the condition is believed to indicate a genuine internal invariant violation (as opposed to attacker input), first prove it can never occur under adversarial input; otherwise treat it as ordinary invalid-unit feedback so a single crafted payload cannot crash node processes.

## Proof of Concept
1. Attacker issues (or receives) a private, transferable asset and creates an initial spend of an indivisible/divisible private output `O` (unit `A`, sequence `good`, already stable).
2. Attacker crafts a second private payment chain (unit `B`) that spends the same output `O` again, with `B`'s `parent_units` set to include `A` in its DAG ancestry (so `graph.determineIfIncludedOrEqual` returns `bIncluded = true`), and either while `A` is not yet stable or after `A` is finally `good`.
3. Attacker sends the private payment chain for `B` to a full-node wallet/hub for validation (e.g., via `handleSavedPrivatePayments`/`validateAndSavePrivatePaymentChain`, which calls into `validation.validatePayment` → `validatePaymentInputsAndOutputs`).
4. `checkForDoublespends` detects the conflict, returns the error to `onDone`, which executes `throw Error("spend proof didn't help: "+err)` because `objAsset.is_private && !conf.bLight`.
5. The throw escapes to `process.on('uncaughtException')` in `network.js`, which re-throws and crashes the node process.

function checkForDoublespends(conn, type, sql, arrSqlArgs, objUnit, objValidationState, onAcceptedDoublespends, cb){
	conn.query(
		sql, 
		arrSqlArgs,
		function(rows){
			if (rows.length === 0)
				return cb();
			var arrAuthorAddresses = objUnit.authors.map(function(author) { return author.address; } );
			async.eachSeries(
				rows,
				function(objConflictingRecord, cb2){
					if (arrAuthorAddresses.indexOf(objConflictingRecord.address) === -1)
						throw Error("conflicting "+type+" spent from another address?");
					if (conf.bLight) // we can't use graph in light wallet, the private payment can be resent and revalidated when stable
						return cb2(objUnit.unit+": conflicting "+type);
					graph.determineIfIncludedOrEqual(conn, objConflictingRecord.unit, objUnit.parent_units, function(bIncluded){
						if (bIncluded){
							var error = objUnit.unit+": conflicting "+type+" in inner unit "+objConflictingRecord.unit;

							// too young (serial or nonserial)
							if (objConflictingRecord.main_chain_index > objValidationState.last_ball_mci || objConflictingRecord.main_chain_index === null)
								return cb2(error);

							// in good sequence (final state); final-bad is excluded by the query and treated as non-existent
							if (objConflictingRecord.sequence === 'good')
								return cb2(error);

							throw Error("unreachable code, conflicting "+type+" in unit "+objConflictingRecord.unit);
						}
						else{ // arrAddressesWithForkedPath is not set when validating private payments
							if (objValidationState.arrAddressesWithForkedPath && objValidationState.arrAddressesWithForkedPath.indexOf(objConflictingRecord.address) === -1)
								throw Error("double spending "+type+" without double spending address?");
							cb2();
						}
					});
				},
				function(err){
					if (err)
						return cb(err);
					onAcceptedDoublespends(cb);
				}
			);
		}
	);
}
