### Title
`pallet-asset-rewards` permanently strands reward-asset funds accrued during zero-stake periods due to `reward_per_token()` early-return - ([File: substrate/frame/asset-rewards/src/lib.rs])

### Summary
`pallet-asset-rewards` implements the Synthetix-style `StakingRewards.sol` JIT reward algorithm noted in its own doc comments. Its `reward_per_token()` function contains the exact same zero-total-staked short-circuit as the reported EVM bug: when `total_tokens_staked == 0`, it returns `reward_per_token_stored` without accounting for elapsed blocks. Combined with `update_pool_rewards()` always advancing `last_update_block` to the current block whenever it *is* invoked, any block range during which the pool had zero stakers produces reward budget (`reward_rate_per_block * blocks_elapsed`) that is never credited to `reward_per_token_stored` and can never be claimed by any staker, past or future. The corresponding reward-asset balance remains locked in the pool's dedicated account and is only recoverable by the admin via `cleanup_pool`, which requires the pool to have zero stakers - impossible to reach while the pool remains in active use.

### Finding Description
The pallet mirrors the vulnerable pattern verbatim: [1](#0-0) 

```rust
pub(super) fn reward_per_token(
    pool_info: &PoolInfoFor<T>,
) -> Result<T::Balance, DispatchError> {
    if pool_info.total_tokens_staked.is_zero() {
        return Ok(pool_info.reward_per_token_stored);
    }
    let rewardable_blocks_elapsed: u32 = ...
    Ok(pool_info.reward_per_token_stored.ensure_add(
        pool_info.reward_rate_per_block
            .ensure_mul(rewardable_blocks_elapsed.into())?
            .ensure_mul(PRECISION_SCALING_FACTOR.into())?
            .ensure_div(pool_info.total_tokens_staked)?,
    )?)
}
```

`update_pool_rewards()` is called from `update_pool_and_staker_rewards()`, which runs on every `stake`, `unstake`, and `harvest_rewards` call: [2](#0-1) 

```rust
pub fn update_pool_rewards(
    pool_info: &PoolInfoFor<T>,
    reward_per_token: T::Balance,
) -> Result<PoolInfoFor<T>, DispatchError> {
    let mut new_pool_info = pool_info.clone();
    new_pool_info.last_update_block = T::BlockNumberProvider::current_block_number();
    new_pool_info.reward_per_token_stored = reward_per_token;
    Ok(new_pool_info)
}
```

Concrete attacker-free sequence, using the fully permissioned/permissionless `stake`/`unstake` extrinsics (`stake`/`unstake` are `ensure_signed` calls open to any account holding the staked asset; `create_pool` requires a configured origin but that is orthogonal - the bug triggers under normal pool usage with no privileged action required):

1. Last staker in a pool calls `unstake` to withdraw all tokens, driving `total_tokens_staked` to `0`. This call invokes `update_pool_and_staker_rewards`, which calls `reward_per_token()` while `total_tokens_staked` is still nonzero (pre-mutation), then `update_pool_rewards` sets `last_update_block = N` (the unstake block) and stores the correctly-computed `reward_per_token_stored`.
2. `reward_rate_per_block` keeps accruing conceptually while no one is staked, for `M` blocks (pool remains unclaimed/idle, `expiry_block` not yet reached).
3. A staker calls `stake` at block `N+M`. `update_pool_and_staker_rewards` is invoked, calling `reward_per_token(pool_info)` where `pool_info.total_tokens_staked == 0` (the staker's new deposit hasn't been applied to `total_tokens_staked` yet at this point in the call). The zero-check short-circuits and returns the stale `reward_per_token_stored` unchanged, ignoring the elapsed `M` blocks. `update_pool_rewards` then blindly overwrites `last_update_block` to `N+M`.
4. As a result, the `M` blocks' worth of `reward_rate_per_block * M` reward-asset tokens are never reflected in `reward_per_token_stored` and are permanently unreachable by any staker - the accounting window for those blocks is silently skipped forever, yet the equivalent balance was expected to have been provisioned into the pool's reward account by the pool operator per the pallet's own documentation ("Care should be taken by the pool operator to keep pool accounts adequately funded with the reward asset"). [3](#0-2) 

The only way to recover the stranded reward-asset balance is `cleanup_pool`, which requires the pool to have **no stakers** (`PoolStakers::<T>::iter_key_prefix(pool_id).next()` must be `None`) and admin origin: [4](#0-3) 

This is unreachable while any staker remains in the pool, meaning the funds accrued during the zero-stake gap are locked indefinitely for the lifetime of the pool if even a single staker persists afterward.

### Impact Explanation
This is a direct, permanent loss of reward-asset funds allocated to the pool's dedicated account, exactly matching the referenced report's impact category. The magnitude scales with `reward_rate_per_block * (blocks pool had zero stakers)`, and can recur every time a pool becomes fully unstaked and later restaked before expiry - a state reachable by ordinary, unprivileged users through `stake`/`unstake`, with no governance or malicious actor required. Because `cleanup_pool` needs zero stakers, recovery is blocked as soon as the reward accrual gap is "papered over" by a new stake.

### Likelihood Explanation
Likelihood is moderate-to-high: any pool with intermittent participation (a very plausible operational pattern for LP/staking incentive pools) will hit this condition without any special conditions, timing tricks, or privileged actions - it only requires ordinary unstake/re-stake activity that is entirely within normal user behavior.

### Recommendation
When `total_tokens_staked == 0`, still advance an internal tracking of "unrewarded" blocks (or refuse to bump `last_update_block` past the point at which staking resumed), and/or implement a mechanism (analogous to the referenced recommendation) allowing the admin to reclaim or reallocate the un-accrued reward budget for zero-participation windows without needing to wait for `PoolStakers` to become fully empty. At minimum, `update_pool_rewards` should not silently discard the elapsed zero-stake window when it later computes `reward_per_token`.

### Proof of Concept
No local FRAME integration test was executed as part of this analysis due to tool constraints (read-only code search); the above trace is derived directly from reading `substrate/frame/asset-rewards/src/lib.rs` (`reward_per_token`, `update_pool_rewards`, `update_pool_and_staker_rewards`, `stake`/`unstake`/`harvest_rewards` call handlers) and the pallet's own existing test suite in `substrate/frame/asset-rewards/src/tests.rs`, which demonstrates the reward-per-block/elapsed-block accounting model (e.g., `extends_reward_accumulation`, `integration`) but does not include a test covering a stake→full-unstake→idle-period→re-stake sequence, so this specific zero-participation loss scenario appears unverified by the existing harness. A reproduction should add a `#[test]` in `substrate/frame/asset-rewards/src/tests.rs` that: creates a pool, stakes, fully unstakes (driving `total_tokens_staked` to 0), advances the block number by `M` blocks, re-stakes, and asserts that `assert_hypothetically_earned` for the new/returning staker excludes the `reward_rate_per_block * M` budget that should logically have accrued, confirming the funds are unaccounted for and unclaimable while `PoolStakers` remains non-empty (blocking `cleanup_pool`). I was not able to execute this reproduction in this environment; it should be run and its concrete pass/fail result attached before this finding is submitted to a bounty program, along with confirmation of which live Parity-run chain (if any) has `pallet-asset-rewards` deployed and in-scope for a bounty.

		pub(super) fn reward_per_token(
			pool_info: &PoolInfoFor<T>,
		) -> Result<T::Balance, DispatchError> {
			if pool_info.total_tokens_staked.is_zero() {
				return Ok(pool_info.reward_per_token_stored);

				pool_info

					.ensure_mul(rewardable_blocks_elapsed.into())?
					.ensure_mul(PRECISION_SCALING_FACTOR.into())?
					.ensure_div(pool_info.total_tokens_staked)?,
