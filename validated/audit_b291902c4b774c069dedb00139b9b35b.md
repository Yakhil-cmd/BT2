### Title
Cross-Stack Read via CCMenu API Endpoint Bypasses Per-Stack ApiClient Scoping - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::CCMenuController` resolves the target `Stack` directly from the request parameter instead of through the `ApiClient`-scoped collection used by every other API controller, breaking the binding `current_api_client.stack_id == accessed_stack.id`. A stack-scoped `ApiClient` token can therefore be used to read CI/deploy status for any other stack in the installation.

### Finding Description
`Shipit::ApiClient` supports scoping a token to a single stack via its `stack_id` column, and `Shipit::ApiClient#check_permissions!` only validates that the permission string (e.g. `read:stack`) is present in the token's permission list — it performs no per-object check: [1](#0-0) 

The actual stack-level authorization boundary is enforced centrally in `Shipit::Api::BaseController`, where `stacks` is filtered by the client's `stack_id` before `stack` looks up the record from `params[:stack_id]`: [2](#0-1) 

Every other API controller (`StacksController`, `TasksController`, `DeploysController`, `LocksController`, `MergeRequestsController`, `HooksController`) relies on this inherited `stack`/`stacks` method, so a client scoped to stack A cannot act on stack B — this is explicitly tested in `test/controllers/api/stacks_controller_test.rb` ("an api client scoped to a stack will only see that one stack").

`Shipit::Api::CCMenuController`, however, overrides `stack` to bypass the scoped collection entirely: [3](#0-2) 

`require_permission :read, :stack` only calls `check_permissions!(:read, :stack)`, which — as shown above — never inspects `current_api_client.stack_id`. Because `stack` resolves `Stack.from_param!(params[:stack_id])` unconditionally, any valid token carrying the `read:stack` permission (regardless of which stack it was scoped to at creation) can fetch `show` for **any** stack slug, since the route accepts an arbitrary `stack_id` (`owner/repo/environment`): [4](#0-3) 

This mirrors the reported bug class: a credential is validated for one authorization context (the stack it was issued/scoped for) but is then used to act on a different context (an arbitrary stack) because the code path that should enforce the binding was bypassed — analogous to a signed message whose verified content doesn't cover the context it's replayed into.

### Impact Explanation
An attacker holding any valid API token with `read:stack` permission — even one an operator deliberately scoped to a single, low-sensitivity stack (e.g., to embed a CCTray/CI status widget for one project) — can read build/deploy status (`name`, `activity`, `lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, `webUrl`, lock state) for every other stack managed by the Shipit instance, including stacks the token was never authorized to see. This is an unauthorized cross-stack read of stack state, matching the High-severity category ("unauthenticated read of stack state ... deploy output") since access to that specific stack was never authenticated for the token being used.

### Likelihood Explanation
Exploitation only requires possession of any working API token with `read:stack` permission (these are routinely distributed for the CCMenu/CCTray integration and can also be obtained via `CCMenuUrlController`) and knowledge/guessing of another stack's slug (`owner/repo/environment`), which is often discoverable (public repo names, predictable environment naming, or the Shipit UI itself). No special privileges beyond an ordinary limited-scope API token are needed.

### Recommendation
Make `Shipit::Api::CCMenuController#stack` resolve through the scoped `stacks` collection (i.e., reuse `BaseController#stack`/`#stacks` instead of overriding it), so that `current_api_client.stack_id`, when set, is enforced identically to every other API endpoint. Alternatively, enforce the stack-scope check explicitly inside `ApiClient#check_permissions!`/`require_permission` so the binding cannot be silently bypassed by controller-level overrides in the future.

### Proof of Concept
1. As an operator, create a stack-scoped API client restricted to Stack A: `ApiClient.create!(creator: user, name: 'A-only', stack: stack_a, permissions: ['read:stack'])`, and obtain `client.authentication_token`.
2. As the attacker holding only this token, issue:
   `GET /api/stacks/<owner>/<stack_b_repo>/<environment>/ccmenu?token=<A-only-token>`
3. The response renders `shipit/ccmenu/project` XML with Stack B's `name`, `activity`, `lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, and `webUrl`, even though the token was never granted access to Stack B — confirmed by comparing against `BaseController#stack`, which would raise/scope out Stack B for the same token on any other API controller.
