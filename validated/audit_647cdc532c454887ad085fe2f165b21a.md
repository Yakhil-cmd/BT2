### Title
Uncontrolled Recursion in `hasReferences()` Definition Walker Leads to Stack Overflow / Process Crash - ([File: definition.js])

### Summary
`definition.js` contains a synchronous, unbounded recursive AST walker, `hasReferences(arrDefinition)`, that recurses into `'or'`, `'and'`, `'r of set'`, and `'weighted and'` branches of an address/AA/asset spending-condition definition with **no depth counter, no complexity increment, and no recursion-depth limit**, unlike every other definition walker in the same file.

### Finding Description
`definition.js` implements several tree-walking validators over address/asset spending-condition definitions (`['and', [...]]`, `['or', [...]]`, `['r of set', {...}]`, etc.). All of the "real" validators enforce hard limits on recursion:

- `validateDefinition()`'s inner `evaluate()` increments `complexity`/`count_ops` on every call and aborts once `constants.MAX_COMPLEXITY` / `constants.MAX_OPS` is exceeded: [1](#0-0) 

- `validateAuthentifiers()`'s inner `evaluate()` is likewise gated by the complexity check enforced beforehand and is `async`-based (interruptible call stack via `async.eachSeries`).

However, `hasReferences(arrDefinition)`, defined later in the same file, walks the **same** `'and'`/`'or'`/`'r of set'`/`'weighted and'` structure completely synchronously and with **no bound whatsoever**: [2](#0-1) 

Each `'and'`/`'or'` node recurses into every child with a plain `for` loop and a direct (non-async, non-interrupted) call to `evaluate(args[i])`, and `'not'` recurses directly into its single argument: [3](#0-2) 

Because this function is called directly on `arrDefinition` (an attacker-controlled address/AA/asset spending-condition definition embedded in a unit's `author.definition`, an `asset` message's `issue_condition`/`transfer_condition`, or an AA's nested `definition` message), a sufficiently deep chain of nested `["and", [ ["and", [...]] ]]` (or `"or"`) can drive the native JS call stack to exhaustion before any complexity-based limit that the other, properly-guarded validators enforce is ever reached — mirroring exactly the CWE-674 pattern in the reported Scriban advisory: a recursive-descent tree walk with no default depth limit, leading to an uncatchable stack overflow and full process crash.

### Impact Explanation
Any peer able to post a unit that carries an address definition, an asset's `issue_condition`/`transfer_condition`, or an AA definition containing a deeply-nested `'and'`/`'or'`/`'r of set'`/`'weighted and'` structure can crash the node process that calls `hasReferences()` on it. A `RangeError: Maximum call stack size exceeded` (Node.js's equivalent of `StackOverflowException`) is not reliably recoverable at the point of a deeply-recursive synchronous call chain and can abort request processing or, depending on where it is invoked (e.g. from `writer.js` while committing/writing a unit, or `aa_addresses.js` while registering an AA address), take down the whole node process. If this occurs on witness/hub nodes processing new units, it directly impairs the network's ability to confirm new units (a network-availability impact matching the "network unable to confirm new units" category), not merely a single client's crash.

### Likelihood Explanation
The vulnerability is reachable by an unprivileged unit poster: nested `'and'`/`'or'` spending-condition definitions are attacker-controlled data that any wallet can construct and broadcast as part of a normal unit (address definition change, asset definition, or AA definition). The depth achievable is bounded only by the unit/message size limits, which are large enough (tens of KB) to encode thousands of nesting levels — well beyond what synchronous V8 recursion tolerates. I was not able to fully confirm, within the available tool budget, the exact call sites and ordering of `hasReferences()` in `writer.js` and `aa_addresses.js` (i.e., whether it is always invoked only after `validateDefinition()`'s complexity cap has already bounded the depth, which would reduce/eliminate exploitability). This should be verified against the actual call sites before treating this as conclusively exploitable in all code paths.

### Recommendation
Add the same depth/complexity guard to `hasReferences()` that `validateDefinition()` and `validateAuthentifiers()` already use (a depth counter checked against `constants.MAX_COMPLEXITY`/`MAX_OPS` or a fixed max recursion depth, returning an error/false rather than recursing further), and/or convert it to an iterative/worklist algorithm to remove native stack growth entirely. As a defense-in-depth measure, ensure `hasReferences()` is only ever invoked on definitions that have already passed `validateDefinition()`'s complexity check, and add an explicit depth ceiling regardless.

### Proof of Concept
Construct an address/AA definition whose spending condition is a deeply right-nested `'and'`:
```js
let def = ['sig', { pubkey: 'AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA=' }];
for (let i = 0; i < 50000; i++)
    def = ['and', [def, ['sig', { pubkey: 'AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA=' }]]];
// def now ~50000 levels deep
require('./definition.js'); // internal, illustrative only
hasReferences(def); // -> uncatchable RangeError: Maximum call stack size exceeded, crashes the process
``` [4](#0-3)
