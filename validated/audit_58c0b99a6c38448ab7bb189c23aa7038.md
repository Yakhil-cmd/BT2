### Title
Webhook signature is validated against an attacker‑chosen organization while the write target is taken from an unrelated payload field, enabling cross‑repository event forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
The GitHub webhook signature check in `WebhooksController#verify_signature` looks up which organization's `webhook_secret` to validate against by reading an **unverified** field from the same JSON body it is about to verify (`repository.owner.login` / `organization.login`), while the handlers that actually mutate state (`PushHandler`, and any handler relying on `Handler#stacks`) resolve the target `Repository`/`Stack` from a **different** field of the same body (`repository.full_name`). Because these two fields are never cross‑checked, a payload can be legitimately signed with the webhook secret of organization A while pointing its write target at a repository belonging to organization B.

### Finding Description
`WebhooksController#verify_signature` derives the signing organization from the raw request body before the signature has been checked: [1](#0-0) [2](#0-1) 

It then fetches `Shipit.github(organization: repository_owner)` and validates the entire raw body's HMAC against **that organization's** `webhook_secret` via `GitHubApp#verify_webhook_signature`: [3](#0-2) 

Since the HMAC covers the whole raw body, anyone who knows a *single* organization's `webhook_secret` (e.g. an admin of any GitHub org already onboarded into this Shipit instance) can compute a valid signature for **any JSON content**, including a `repository.owner.login`/`organization.login` that matches their own org (so the correct secret is selected) but a `repository.full_name` that names a completely different repository.

Downstream, every handler resolves the actual write target purely from `repository.full_name`, with no relationship enforced to the organization that authenticated the request: [4](#0-3) 

`PushHandler`, for example, uses this to locate stacks and immediately triggers a GitHub sync using an attacker-supplied `after` SHA: [5](#0-4) 

This breaks the intended binding: `organization authenticated by signature == organization owning the repository being written`. The signature only proves "signed by the holder of organization A's secret," not "this event concerns a repository under organization A." An attacker who legitimately controls (or has been granted webhook configuration for) one onboarded organization/repository can forge events that resolve to stacks under a completely different, unrelated repository/organization.

### Impact Explanation
This is a cross-repository write: an attacker who is a legitimate, unprivileged (relative to the victim) admin of one onboarded organization can forge `push`, `status`, `check_suite`, etc. events for a victim's stack, causing `Stack#sync_github` (and any continuous-deployment logic gated on synced HEAD) to run with attacker-chosen commit data on a repository the attacker does not own. This matches the "cross-repository writes" Critical impact class, because the deployment-trust binding between "who authenticated" and "what gets written" is not enforced anywhere in the request path.

### Likelihood Explanation
Requires the attacker to control (or know the webhook secret of) at least one organization already configured in the Shipit instance's GitHub App config — a realistic scenario in any multi-tenant Shipit deployment where multiple organizations are onboarded, since organization admins configure/see their own `webhook_secret` and can freely POST to the shared `/github/webhooks` endpoint. No access to the victim organization's credentials, tokens, or GitHub App keys is needed.

### Recommendation
When resolving the target repository/stack for a webhook event, verify that `repository.owner.login` (or `organization.login`) — the same field used to select the `webhook_secret` for signature verification — matches the organization owning `repository.full_name` before any handler acts on the payload. Reject events where these fields diverge, and log the mismatch (`app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/handler.rb`).

### Proof of Concept
1. Attacker is an admin of organization `attacker-org`, which has been legitimately onboarded to the Shipit instance and has repositories with a configured `webhook_secret` known to the attacker.
2. Attacker crafts a `push` webhook JSON body:
   ```json
   {
     "ref": "refs/heads/master",
     "after": "<attacker-chosen sha>",
     "repository": {
       "full_name": "victim-org/victim-repo",
       "owner": { "login": "attacker-org" }
     }
   }
   ```
3. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(attacker-org webhook_secret, body)` and POSTs to `/github/webhooks` with `X-Github-Event: push`.
4. `verify_signature` reads `repository_owner` = `"attacker-org"`, fetches `attacker-org`'s `webhook_secret`, and the signature validates successfully (`app/controllers/shipit/webhooks_controller.rb:24-30,59-62`; `lib/shipit/github_app.rb:76-83`).
5. `PushHandler#process` resolves stacks via `repository.full_name` = `"victim-org/victim-repo"` (`app/models/shipit/webhooks/handlers/handler.rb:36-38`) and calls `stack.sync_github(expected_head_sha: "<attacker-chosen sha>")` on the victim's stack (`app/models/shipit/webhooks/handlers/push_handler.rb:12-17`), even though the request was never signed by `victim-org`'s secret.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
