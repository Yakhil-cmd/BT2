### Title
Front-runnable, permissionless `initialize()` in vault contracts allows DOS of the DAO's atomic launch/finalization proposal - (File: `mainnet/contracts/vault/v0-vault-sbtc.clar`)

### Summary
Each vault contract (`v0-vault-sbtc.clar`, `v0-vault-stx.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`, `v0-vault-usdc.clar`, `v0-vault-usdh.clar`) exposes a `public` `initialize` function guarded only by an `initialized` flag check, with no `check-dao-auth` restriction, mirroring the reported `UniswapV3Pool.initialize()` issue where a step meant to run only as part of a controlled finalization flow can be triggered early by anyone.

### Finding Description
`initialize()` is defined as: [1](#0-0) 

It only checks `(asserts! (not (var-get initialized)) ERR-ALREADY-INITIALIZED)` before flipping `initialized` to `true` and depositing `MINIMUM-LIQUIDITY` to `NULL-ADDRESS`, unlike every other state-mutating admin function in the same contract which is protected with `(try! (check-dao-auth))`, e.g. `set-cap-supply` and `set-authorized-contract`. [2](#0-1) [3](#0-2) 

The DAO's intended launch sequence bundles calling `initialize` on every vault and then authorizing the `market` contract inside one atomic proposal: [4](#0-3) 

Because every `try!` call in an atomic `execute` aborts the whole transaction on failure, any unprivileged principal can call `initialize()` on a vault directly - supplying only the trivial `MINIMUM-LIQUIDITY` (`u1000`) of the underlying token as deposit collateral - before the DAO's proposal is mined. This sets `initialized` to `true` for that vault ahead of time. When the DAO proposal subsequently executes `(try! (contract-call? .vault-sbtc initialize))`, it fails with `ERR-ALREADY-INITIALIZED`, and the entire `proposal-init-vaults` transaction reverts - including the `set-authorized-contract` calls for the `market` contract on *every* vault in that batch, not just the one the attacker touched.

### Impact Explanation
This is a shared-state race between an unprivileged attacker and the DAO's launch/finalization script: the `initialized` boolean is the shared state, primed by the attacker and consumed by the DAO's atomic multi-vault setup. Without the attacker's transaction, the DAO proposal succeeds and `market` becomes authorized in all vaults, enabling normal deposit/borrow/repay/redeem flows for all users. With the attacker's front-run transaction, the proposal reverts, `market` is never authorized, and all users are blocked from using the lending market through the intended flow until the DAO redeploys and re-executes a corrected proposal. This is a temporary freeze of protocol funds/functionality at launch, directly analogous to the reported "DoSing the launch finalization process" bug class.

### Likelihood Explanation
The attack requires only a small amount of the underlying token (`MINIMUM-LIQUIDITY = u1000`, e.g., 1000 base units of sBTC/STX/USDC/etc.) and knowledge of the vault contract's deployed address, which is public prior to the DAO proposal being submitted/mined. No special privileges or DAO compromise are needed - any address can call `initialize()` once the contract is deployed and before the DAO proposal transaction confirms.

### Recommendation
Restrict `initialize()` to be callable only by the DAO/executor (e.g., add `(try! (check-dao-auth))` before the `initialized` check), or perform the initialization atomically as part of contract deployment rather than as a separate permissionless public call.

### Proof of Concept
1. Vault contracts (`vault-sbtc`, `vault-stx`, etc.) are deployed to mainnet but not yet initialized.
2. Attacker acquires `u1000` of the vault's underlying token (e.g., sBTC) and calls `vault-sbtc.initialize()` directly, before the DAO's `proposal-init-vaults` transaction is broadcast/mined.
3. `vault-sbtc`'s `initialized` var is set to `true`; attacker's deposit succeeds and mints minimum-liquidity shares to `NULL-ADDRESS`.
4. The DAO submits `proposal-init-vaults.execute`, which calls `(try! (contract-call? .vault-sbtc initialize))` per [5](#0-4) ; this call now returns `ERR-ALREADY-INITIALIZED` per [6](#0-5) , causing the whole proposal transaction to revert.
5. None of the vaults in the batch get `market` authorized (`set-authorized-contract`), freezing the market's ability to operate on any of these vaults until a corrective DAO proposal is prepared and executed.
