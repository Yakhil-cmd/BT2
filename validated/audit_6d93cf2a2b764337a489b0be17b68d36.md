### Title
Stale delegate grant silently re-arms when the position NFT returns to the original owner, restoring borrow/withdraw authority without a new grant - (File: contracts/controller/src/storage/account.rs)

### Summary
A `DelegateGrant` is stamped with `granted_by` and is only masked — never deleted — when the position NFT moves to a new owner. If the token later returns to the original grantor, the old delegate list becomes live again with no fresh authorization, no event, and no warning. A dormant delegate (including an unprivileged externally registered "position manager" address) can then borrow and withdraw the account's collateral to a recipient of its choosing, draining the returning owner. This mirrors CVE-2023-4053's class: hidden/obscured authority state that a user cannot see and does not expect, producing a confusion-driven loss.

### Finding Description
`get_delegates` filters stored grants by `grant.granted_by == *owner`, so a grant survives transfer untouched and simply stops matching while someone else holds the NFT [1](#0-0) . `set_delegates` rewrites the grant only when the *current* owner calls `add_delegate`/`remove_delegate`; an intermediate owner who never touches delegates leaves the previous owner's grant intact [2](#0-1) . When `try_account_owner` once again resolves the NFT holder to the original `granted_by` address, the stale grant matches again and `is_owner_or_delegate` accepts the old delegates [3](#0-2) . The project documentation itself confirms the resurrection: "The stale grant stays in storage and re-arms if the token returns to `granted_by`" [4](#0-3) .

Delegates are not benign viewers: per the threat model, "Delegates can borrow/withdraw to their chosen recipient within account gates" and the gates "do not constrain them to acting in the owner's economic interest" [5](#0-4) . The only extra requirement is that the delegate address be an active global position manager, which is a governance-registered but unprivileged role.

### Impact Explanation
Theft of user funds. A re-armed delegate can call `borrow` / `withdraw` on the account and direct proceeds to its own recipient, extracting collateral up to the account's LTV/health-factor limits. The victim never re-authorized the delegate: the grant they made months ago silently reactivates purely because an NFT round-tripped back to their address. Because NFT transfer is a normal wallet/marketplace operation, the trigger is invisible — the account's *effective* authority set differs from what any UI would show the returning owner.

### Likelihood Explanation
Reachable by a single unprivileged address (the stale delegate) once two conditions hold: (1) the owner previously granted a delegate that was never removed via `remove_delegate` before transfer, and (2) the NFT returns to that owner. Path: Alice grants delegate M → Alice transfers/sells the position NFT to Bob → Bob transfers it back to Alice (gift, failed sale, OTC return, or Bob is a confederate) → M's grant re-matches `granted_by == Alice` and M drains via `borrow`/`withdraw`. No signature from Alice is required for re-arming. This is narrower than a full always-on exploit since it needs the NFT to come back, but it is an unprivileged, repeatable path with no user-visible signal — matching a Medium-severity analog.

### Recommendation
Invalidate delegate grants on ownership change rather than by `granted_by` string equality. Concretely: stamp grants with a transfer epoch or NFT "owner generation" (e.g., store the owner plus a monotonically increasing per-token transfer counter read from the NFT contract, or have the NFT/controller clear `ControllerKey::Delegates(account_id)` on transfer detection). Alternatively, delete the `Delegates` entry whenever `try_account_owner` resolves a different address than `granted_by` on any state-changing call, so a stale grant can never re-arm.

### Proof of Concept
1. Alice owns account `A` (NFT token id = `A`) holding USDC collateral. Alice calls `add_delegate(A, M)` where `M` is an active position manager; storage now holds `DelegateGrant { granted_by: Alice, delegates: [M] }` at `ControllerKey::Delegates(A)`.
2. Alice calls `position-nft::transfer(Alice, Bob, A)`. `get_delegates(A, Bob)` returns empty (grant masked, not deleted).
3. Bob never calls `add_delegate`/`remove_delegate`, so the grant stays. Bob calls `position-nft::transfer(Bob, Alice, A)` (or Alice re-acquires it via `transfer_from` through any marketplace flow).
4. `get_delegates(A, Alice)` now returns `[M]` again — no new authorization occurred and no event marks the re-arm.
5. M calls `controller::borrow` (or `withdraw`) with `caller = M`, `account_id = A`, `to = M`. `is_owner_or_delegate(A, M, Alice)` passes because the stale grant matches, and M extracts Alice's collateral.

The existing test `transfer_revokes_prior_owner_and_delegates` only asserts the grant is inactive while Bob holds the token; it does not cover the round-trip return path where the grant reactivates [6](#0-5) .

fn set_delegates(env: &Env, account_id: u64, owner: &Address, delegates: &Vec<Address>) {
    let key = ControllerKey::Delegates(account_id);
    if delegates.is_empty() {
        env.storage().persistent().remove(&key);
    } else {
        set_user(
            env,
            &key,
            &DelegateGrant {
                granted_by: owner.clone(),
                delegates: delegates.clone(),
            },
        );
    }
}

fn transfer_revokes_prior_owner_and_delegates() {
    let env = Env::default();
    env.mock_all_auths();
    let admin = Address::generate(&env);
    let contract_id = env.register(Controller, (admin,));
    let nft = setup_position_nft(&env, &contract_id);

    let alice = Address::generate(&env);
    let bob = Address::generate(&env);
    let manager = Address::generate(&env);
    let account_id = seed_account(&env, &contract_id, &nft, &alice);

    env.as_contract(&contract_id, || {
        crate::storage::set_position_manager(
            &env,
            &manager,
            &common::types::PositionManagerConfig { is_active: true },
        );
        assert!(crate::storage::add_delegate(
            &env, account_id, &alice, &manager
        ));
        // Pre-transfer: owner and delegate both authorized.
        assert!(is_owner_or_delegate(&env, account_id, &alice, &alice));
        assert!(is_owner_or_delegate(&env, account_id, &manager, &alice));
    });

    position_nft::PositionNftClient::new(&env, &nft).transfer(
        &alice,
        &bob,
        &u32::try_from(account_id).unwrap(),
    );

    env.as_contract(&contract_id, || {
        let owner = crate::storage::account_owner(&env, account_id);
        assert_eq!(owner, bob);
        // Old owner and the grant they made are both dead.
        assert!(!is_owner_or_delegate(&env, account_id, &alice, &owner));
        assert!(!is_owner_or_delegate(&env, account_id, &manager, &owner));
        // New owner works, and a fresh grant by the new owner works.
        assert!(is_owner_or_delegate(&env, account_id, &bob, &owner));
        assert!(crate::storage::add_delegate(
            &env, account_id, &bob, &manager
        ));
        assert!(is_owner_or_delegate(&env, account_id, &manager, &owner));
    });
