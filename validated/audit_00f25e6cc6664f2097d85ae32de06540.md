This confirms the vulnerability path. Critically, `StatusHandler` (app/models/shipit/webhooks/handlers/status_handler.rb:20-24) matches by `sha` **globally across all stacks** (`Commit.where(sha: params.sha)`), with no repository-scoping at all — unlike `PushHandler`/`Handler#stacks` which at least scope by `repository_name`. Combined with `WebhooksController#verify_signature` authenticating only the *organization* (via `repository_owner`) rather than the specific *repository* being written to, this is the strongest reachable analog.

<title>Reentrancy analog: webhook signature authenticates an organization while `StatusHandler`/`Handler` write to an unrelated repository — unauthorized deploy</title>

### Title
Webhook signature verifies attacker's own organization while `StatusHandler`/`PushHandler` act on any repository named in the payload, enabling forged CI status and unauthorized deploys - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/status_handler.rb`, `app/models/shipit/webhooks/handlers/handler.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/`webhook_secret` to validate the request against using `repository_owner`, i.e. `params.dig('repository','owner','login')` or the fallback `params.dig('organization','login')` [1](#0-0) [2](#0-1) . In a multi-organization Shipit deployment, each organization has its own independent `webhook_secret`, `app_id`, and `private_key` [3](#0-2) [4](#0-3) . However, once the signature check passes for *that* organization, the actual handler that processes the event uses separate, independently-controlled payload fields to decide what to write: `StatusHandler#process` looks up commits purely `Commit.where(sha: params.sha)` — with no repository or stack scoping at all [5](#0-4) , and the base `Handler#repository_name`/`#stacks` used by other handlers reads `payload.dig('repository','full_name')` [6](#0-5) . Since these are all just independent keys inside the same JSON body, an attacker who legitimately controls a GitHub App/org configured on this Shipit instance can sign a payload with the `repository.owner.login`/`organization.login` set to their own org (so `verify_webhook_signature` succeeds against their own `webhook_secret`), while other content of that same payload (`sha`, or `repository.full_name` for other handlers) targets a completely different, victim organization's repository/stack.

### Finding Description
The trust binding that should hold is: **organization that authenticated == repository that is written**. Instead:
- Authentication binds to `repository_owner` only (`app/controllers/shipit/webhooks_controller.rb:59-62`), which selects the `GitHubApp` (and thus the `webhook_secret`) via `Shipit.github(organization: repository_owner)` [7](#0-6) .
- The actual mutation target is decided independently: `StatusHandler` trusts `params.sha` alone with no repository check [5](#0-4) , meaning any commit SHA that happens to exist in *any* stack across the whole Shipit instance (including stacks belonging to organizations other than the one whose key signed the request) will receive a forged `Status`.
- `Status.create!` triggers `schedule_continuous_delivery` → `Commit#schedule_continuous_delivery`, which — if the target stack has `continuous_deployment?` enabled and is `deployable?` — enqueues `ContinuousDeliveryJob`, which can trigger a real deploy [8](#0-7) [9](#0-8) . Tests confirm this exact chain: creating a `success` status directly enqueues `ContinuousDeliveryJob` and creates a new `Deploy` [10](#0-9) .

Since GitHub SHA-1 commit hashes are public/predictable (an attacker with any read access to the victim's public/forked repo, or who can compute/guess the SHA of the commit already sitting at the tip of the victim's tracked branch, knows it), the attacker does not need any credential belonging to the victim organization — only their own organization's legitimately-configured (and possibly much lower-trust) webhook secret.

### Impact Explanation
This crosses the "unauthorized deploy" bar explicitly listed as Critical impact. An attacker who administers/controls a GitHub App for *their own*, unrelated organization onboarded to a shared multi-tenant Shipit instance can forge a `status` webhook (`state: success`, matching `context`) for a commit SHA belonging to a victim's stack with `continuous_deployment` enabled, causing Shipit to autonomously trigger a deploy of that commit to the victim's production environment — a cross-repository, cross-organization write/deploy despite a "validly signed" request.

### Likelihood Explanation
Requires the Shipit instance to be configured for multiple GitHub organizations (an explicitly documented, supported configuration - `docs/setup.md` "Using Multiple Github Applications") and requires the attacker to control at least one such organization's GitHub App integration (their own), plus knowledge of a target commit SHA (trivially obtainable for any repo the attacker can read, including forks/public repos, or matching a branch tip via commit polling). No access to the victim org's credentials, tokens, or Shipit session is required.

### Recommendation
Bind the verified signing organization to the object being mutated:
1. In `WebhooksController`, pass the verified `repository_owner`/organization down to handlers, and have `Handler#stacks`/`StatusHandler#process` filter by `Repository` scoped to that verified organization, not merely by SHA or by an independently-supplied `repository.full_name`.
2. In `StatusHandler`, scope `Commit.where(sha: params.sha)` by the repository derived from the authenticated organization (e.g., `stacks.joins(:commits).where(commits: { sha: params.sha })`) instead of a global, unscoped `Commit` lookup.
3. Reject payloads where `repository.owner.login`/`organization.login` (used for authentication) does not match the repository that the handler is about to mutate.

### Proof of Concept
1. Configure Shipit with two orgs, `AttackerOrg` and `VictimOrg`, each with distinct `webhook_secret`s (supported multi-org config, see `test/dummy/config/secrets_double_github_app.yml`).
2. Attacker administers `AttackerOrg`'s GitHub App/webhook secret (legitimate low-privilege access to their own org's integration).
3. Attacker learns the current commit SHA at the tip of `VictimOrg/repo`'s deploy branch (public info via GitHub API/UI).
4. Attacker POSTs to `/webhooks` with `X-Github-Event: status`, a body `{"sha": "<victim_sha>", "state": "success", "context": "ci/travis", "repository": {"owner": {"login": "AttackerOrg"}, "full_name": "AttackerOrg/whatever"}}`, signed with `AttackerOrg`'s `webhook_secret`.
5. `verify_signature` resolves `repository_owner` = `AttackerOrg`, verifies successfully against `AttackerOrg`'s secret.
6. `StatusHandler#process` runs `Commit.where(sha: params.sha)`, finds the `VictimOrg` commit (SHA match is org-agnostic), and creates a `Status`, which — if `VictimOrg`'s stack has continuous deployment enabled — enqueues `ContinuousDeliveryJob` and produces an unauthorized `Deploy`.
