Based on my research, the strongest analog to the Sherlock report's bug class (a per-item validation revert that permanently blocks batch processing of a shared queue, wiping accounted state with no recovery path) is the delayed-receipt processing path in nearcore's runtime, combined with the resharding-shard-remapping hazard that the `receipt_filter_fn()` / `receiver_shard_id()` logic is exposed to.

### Title
Delayed-receipt re-validation failure converts a recoverable per-receipt error into a fatal `StorageInconsistentState`, permanently stalling chunk application - ([File: runtime/runtime/src/lib.rs])

### Summary
In `process_delayed_receipts`, every receipt popped from the persistent delayed-receipt queue is re-validated with `validate_receipt(..., ValidateReceiptMode::ExistingReceipt)`. If this re-validation fails, the error is wrapped into `StorageError::StorageInconsistentState` and propagated as a hard `RuntimeError`, aborting the entire `apply()` call for the chunk [1](#0-0) . Because `apply()` only writes changes to the trie/database if it returns `Ok`, an error here means the delayed receipt is **not removed** from the queue and no forward progress is made — but it also means the same receipt will be re-fetched and re-validated on every subsequent attempt to apply that chunk, since nothing about the on-disk state changed. If the failure condition is deterministic (not transient), this repeats forever, permanently stalling the shard/chain, mirroring the guardian's inability to “restart the protocol manually” once `deltaAllocations` accounting is stuck in the Sherlock report.

### Finding Description
The delayed receipt queue (`DelayedReceiptQueueWrapper`) is a generic, protocol-level per-shard queue used to hold any receipt (action, data, or `GlobalContractDistribution`) that could not be processed immediately due to gas/compute/proof-size limits [2](#0-1) . When receipts are popped back out for processing, `receipt_filter_fn()` computes `receiver_shard_id()` against the *current* epoch's shard layout to decide whether the receipt still belongs to this shard, unwrapping the result [3](#0-2) . A receipt can sit in the delayed queue across multiple resharding events; if the shard-layout remapping cannot resolve the receipt's originally recorded target shard (e.g., because the shard was split more than once), this lookup can fail.

This exact scenario was identified and is now regression-tested for `GlobalContractDistribution` receipts in `test_stale_global_contract_distribution_after_double_resharding`, which explicitly documents: "If the vulnerability exists, processing the stale GlobalContractDistribution receipt will panic in `receipt_filter_fn()` when `receiver_shard_id()` fails to remap the old target_shard after two resharding generations" [4](#0-3) . The test currently passes (asserting the chain does *not* stall), which indicates a fix exists for that specific receipt-kind/shard-layout combination, but the underlying architectural pattern — a queue whose contents are validated against layout/config state that can drift out of sync between enqueue time and dequeue time, with a hard failure on mismatch — is generic to `process_delayed_receipts` and `process_incoming_receipts`, both of which convert any `validate_receipt` failure into a fatal, chunk-application-aborting error rather than a receipt-local, recoverable failure [5](#0-4) .

The comment in the code itself flags the fragility: "Validating the delayed receipt. If it fails, it's likely the state is inconsistent" [1](#0-0)  — i.e., the authors already treat any re-validation failure of a previously-accepted, in-state receipt as an unrecoverable, panic-worthy condition rather than something to skip/quarantine, structurally identical to `setDeltaAllocationsInt()`'s `require(!blacklisted)` revert blocking `rebalance()` in the Sherlock report.

### Impact Explanation
If any code path (new receipt kind, new protocol feature, edge case in resharding, or a different validation rule tightened/loosened across a protocol upgrade) causes a previously-valid, already-enqueued receipt to fail `ExistingReceipt` validation on dequeue, the shard's chunk application becomes permanently unable to progress: the offending receipt can never be popped and discarded, the chunk apply always errors out, and the chain stalls at that shard/height with no operator-level recovery mechanism analogous to the guardian being unable to restart `rebalance()`. This matches the "chain stall" / "node panic" acceptance criteria.

### Likelihood Explanation
This is a latent architectural pattern rather than a directly exploitable bug in the current codebase, since the one known concrete trigger (double-resharding + stale `GlobalContractDistribution` receipt) already has a fix and a regression test guarding it. Reaching this from a submitted transaction requires finding another receipt/validation-rule/layout-drift combination not covered by the existing fix — I was not able to confirm such a combination exists within my available searches. The `debug_assert!` and `unwrap()` patterns nearby the delayed-receipt handling (e.g., `receipt_filter_fn`'s use of `.unwrap()` on `receiver_shard_id()`) suggest the class of hazard is still present as a coding pattern in adjacent, non-`GlobalContractDistribution` code paths, but I could not fully verify this within the given tool budget — the `receiver_shard_id()` implementation itself (in `core/primitives/src/receipt.rs`) was not returned in full by my searches, so I cannot state with certainty whether other receipt kinds are equally exposed today.

### Recommendation
Treat `validate_receipt` failures for receipts already accepted into state (delayed queue) as a receipt-local, recoverable condition (e.g., dropping/quarantining the malformed receipt with a metric/log, or moving it to a side channel for manual inspection) rather than aborting the entire chunk application with a fatal `StorageInconsistentState`/panic. Audit all consumers of `receiver_shard_id()`/`receipt_filter_fn()` for other receipt kinds that can be enqueued before a resharding event and dequeued after multiple subsequent reshardings, ensuring the shard remapping logic cannot fail non-recoverably for any receipt kind, not just `GlobalContractDistribution`.

### Proof of Concept
I could not construct a concrete, currently-reachable transaction-level PoC given the available tooling and time — the one confirmed concrete trigger (`test_stale_global_contract_distribution_after_double_resharding`) is already fixed and covered by a passing regression test [4](#0-3) . Further investigation would need to enumerate all `Receipt` variants reachable through `process_delayed_receipts`/`process_incoming_receipts` and check whether any of them can hit the same "validated then dequeued after layout drift" hazard without the mitigation applied to `GlobalContractDistribution`.

/// A wrapper around `DelayedReceiptQueue` to accumulate changes in gas and
/// bytes.
///
/// This struct exists for two reasons. One, to encapsulate the accounting of
/// gas and bytes in functions that can be called in all necessary places. Two,
/// to accumulate changes and only apply them to `CongestionInfo` in the end,
/// which avoids problems with multiple mutable borrows with the closure
/// approach we currently have in receipt processing code.
///
/// We use positive added and removed values to avoid integer conversions with
/// the associated additional overflow conditions.
pub(crate) struct DelayedReceiptQueueWrapper<'a> {
    // The delayed receipt queue.
    queue: DelayedReceiptQueue,

    // Epoch_info_provider, shard_id, and epoch_id are used to determine
    // if a receipt belongs to the current shard or not after a resharding event.
    epoch_info_provider: &'a dyn EpochInfoProvider,
    shard_id: ShardId,
    epoch_id: EpochId,

    // Accumulated changes in gas and bytes for congestion info calculations.
    new_delayed_gas: Gas,
    new_delayed_bytes: u64,
    removed_delayed_gas: Gas,
    removed_delayed_bytes: u64,
}

impl<'a> DelayedReceiptQueueWrapper<'a> {
    pub fn new(
        queue: DelayedReceiptQueue,
        epoch_info_provider: &'a dyn EpochInfoProvider,
        shard_id: ShardId,
        epoch_id: EpochId,
    ) -> Self {
        Self {
            queue,
            epoch_info_provider,
            shard_id,
            epoch_id,
            new_delayed_gas: Gas::ZERO,
            new_delayed_bytes: 0,
            removed_delayed_gas: Gas::ZERO,
            removed_delayed_bytes: 0,
        }
    }

    pub(crate) fn push(
        &mut self,
        trie_update: &mut TrieUpdate,
        receipt: &Receipt,
        apply_state: &ApplyState,
    ) -> Result<(), RuntimeError> {
        let config = &apply_state.config;

        let gas = compute_receipt_congestion_gas(&receipt, &config)?;
        let size = compute_receipt_size(&receipt)? as u64;

        // TODO It would be great to have this method take owned Receipt and
        // get rid of the Cow from the Receipt and StateStoredReceipt.
        let receipt = match config.use_state_stored_receipt {
            true => {
                let metadata =
                    StateStoredReceiptMetadata { congestion_gas: gas, congestion_size: size };
                let receipt = StateStoredReceipt::new_borrowed(receipt, metadata);
                ReceiptOrStateStoredReceipt::StateStoredReceipt(receipt)
            }
            false => ReceiptOrStateStoredReceipt::Receipt(Cow::Borrowed(receipt)),
        };

        self.new_delayed_gas = self.new_delayed_gas.checked_add(gas).ok_or(IntegerOverflowError)?;
        self.new_delayed_bytes =
            self.new_delayed_bytes.checked_add(size).ok_or(IntegerOverflowError)?;
        self.queue.push_back(trie_update, &receipt)?;
        Ok(())
    }

    // With ReshardingV3, it's possible for a chunk to have delayed receipts that technically
    // belong to the sibling shard before a resharding event.
    // Here, we filter all the receipts that don't belong to the current shard_id.
    //
    // The function follows the guidelines of standard iterator filter function
    // We return true if we should retain the receipt and false if we should filter it.
    fn receipt_filter_fn(&self, receipt: &ReceiptOrStateStoredReceipt) -> bool {
        let shard_layout = self.epoch_info_provider.shard_layout(&self.epoch_id).unwrap();
        let receipt_shard_id = receipt.get_receipt().receiver_shard_id(&shard_layout).unwrap();
        receipt_shard_id == self.shard_id
    }

    pub(crate) fn pop(
        &mut self,
        trie_update: &mut TrieUpdate,
        config: &RuntimeConfig,
    ) -> Result<Option<ReceiptOrStateStoredReceipt<'_>>, RuntimeError> {
        // While processing receipts, we need to keep track of the gas and bytes
        // even for receipts that may be filtered out due to a resharding event
        loop {
            // Check proof size limit before each receipt is popped.
            if trie_update.trie.check_proof_size_limit_exceed() {
                break;
            }
            let Some(receipt) = self.queue.pop_front(trie_update)? else {
                break;
            };
            let delayed_gas = receipt_congestion_gas(&receipt, &config)?;
            let delayed_bytes = receipt_size(&receipt)? as u64;
            self.removed_delayed_gas =
                self.removed_delayed_gas.checked_add(delayed_gas).ok_or(IntegerOverflowError)?;
            self.removed_delayed_bytes = self
                .removed_delayed_bytes
                .checked_add(delayed_bytes)
                .ok_or(IntegerOverflowError)?;

            // Track gas and bytes for receipt above and return only receipt that belong to the shard.
            if self.receipt_filter_fn(&receipt) {
                return Ok(Some(receipt));
            }
        }
        Ok(None)
    }

fn test_stale_global_contract_distribution_after_double_resharding() {
    init_test_logger();

    // The fix only works with V3 shard layouts (dynamic resharding).
    // With static resharding, the shard layout doesn't maintain a full split history.
    if !ProtocolFeature::DynamicResharding.enabled(PROTOCOL_VERSION) {
        return;
    }

    let epoch_length: BlockHeightDelta = 10;
    let base_boundary_accounts = create_account_ids(["user2", "user3"]).to_vec();
    let base_shard_layout = ShardLayout::multi_shard_custom(base_boundary_accounts, 3);
    let deploy_user: AccountId = create_account_id("user0");
    let users = create_account_ids(["user0", "user1", "user2", "user3", "user4", "user5"]).to_vec();
    let validators_spec = create_validators_spec(1, 0);
    let clients = validators_spec_clients(&validators_spec);
    let chunk_producer = clients[0].clone();
    let gas_limit = Gas::from_teragas(300);
    let base_pv = PROTOCOL_VERSION - 1;

    // Configure dynamic resharding to force-split two shards sequentially.
    // The first split targets the shard containing deploy_user (user0), so the
    // GlobalContractDistribution receipt becomes stale after two layout transitions.
    let first_split_shard = base_shard_layout.account_id_to_shard_id(&deploy_user);
    let second_split_shard = base_shard_layout.account_id_to_shard_id(&create_account_id("user4"));
    assert_ne!(first_split_shard, second_split_shard);

    let dynamic_config = DynamicReshardingConfig {
        memory_usage_threshold: u64::MAX,
        min_child_memory_usage: u64::MAX,
        max_number_of_shards: 100,
        min_epochs_between_resharding: 1.try_into().unwrap(),
        force_split_shards: vec![first_split_shard, second_split_shard],
        block_split_shards: vec![],
    };

    let genesis = TestLoopBuilder::new_genesis_builder()
        .protocol_version(base_pv)
        .validators_spec(validators_spec)
        .shard_layout(base_shard_layout.clone())
        .epoch_length(epoch_length)
        .gas_limit(gas_limit)
        .add_user_accounts_simple(&users, Balance::from_near(1_000_000))
        .build();
    let base_epoch_config = TestEpochConfigBuilder::from_genesis(&genesis).build();

    let mut dynamic_epoch_config = base_epoch_config.clone();
    dynamic_epoch_config.shard_layout_config =
        ShardLayoutConfig::Dynamic { dynamic_resharding_config: dynamic_config };

    let epoch_config_store = EpochConfigStore::test(BTreeMap::from([
        (base_pv, Arc::new(base_epoch_config)),
        (base_pv + 1, Arc::new(dynamic_epoch_config)),
    ]));

    let mut env = TestLoopBuilder::new()
        .genesis(genesis)
        .clients(clients)
        .epoch_config_store(epoch_config_store)
        .gc_num_epochs_to_keep(5)
        .build();

    // Step 1: Deploy the test contract on user0's account so we can call burn_gas_raw.
    {
        let node = env.node_for_account(&chunk_producer);
        let tx = node.tx_deploy_test_contract(&deploy_user);
        node.submit_tx(tx);
    }
    env.runner_for_account(&chunk_producer).run_for_number_of_blocks(2);

    // Step 2: Deploy a global contract from user0. This creates a
    // GlobalContractDistribution receipt with target_shard = user0's shard (S_A),
    // which is the shard that will be split in the first resharding.
    {
        let node = env.node_for_account(&chunk_producer);
        let code = ContractCode::new(near_test_contracts::rs_contract().to_vec(), None);
        let tx = node.tx_deploy_global_contract(
            &deploy_user,
            code.code().to_vec(),
            GlobalContractDeployMode::CodeHash,
        );
        node.submit_tx(tx);
    }

    // Step 3: Saturate compute on user0's shard every block so that the
    // GlobalContractDistribution receipt (arriving as incoming) gets pushed to
    // the delayed queue and stays there through both resharding events.
    //
    // Each burn_gas_raw call burns slightly more than half the gas limit, so
    // two local receipts exhaust the chunk's compute budget. We submit 3 per
    // block to ensure at least 2 are processed as local receipts.
    let gas_to_burn = gas_limit.checked_div(2).unwrap().checked_add(Gas::from_gas(1)).unwrap();
    let initial_num_shards = base_shard_layout.num_shards();
    let target_num_shards = initial_num_shards + 2; // after two splits

    let start_height = {
        let node = env.node_for_account(&chunk_producer);
        node.client().chain.chain_store().head().unwrap().height
    };

    // Keep saturating until both resharding events complete. Dynamic resharding has a
    // 2-epoch proposal-to-activation pipeline, so we need enough epochs for both splits.
    let max_saturation_height = start_height + epoch_length * 12;
    let mut both_splits_done = false;
    for target_height in (start_height + 1)..=max_saturation_height {
        // Submit 3 heavy transactions to saturate this block's compute budget.
        {
            let node = env.node_for_account(&chunk_producer);
            for _ in 0..3 {
                let tx = node.tx_call(
                    &deploy_user,
                    &deploy_user,
                    "burn_gas_raw",
                    gas_to_burn.as_gas().to_le_bytes().to_vec(),
                    Balance::ZERO,
                    gas_limit,
                );
                node.submit_tx(tx);
            }
        }
        env.runner_for_account(&chunk_producer).run_until_head_height(target_height);

        // Check if both resharding events have completed.
        let node = env.node_for_account(&chunk_producer);
        let epoch_id = node.client().chain.chain_store().head().unwrap().epoch_id;
        let current_layout = node.client().epoch_manager.get_shard_layout(&epoch_id).unwrap();
        if current_layout.num_shards() >= target_num_shards {
            both_splits_done = true;
            break;
        }
    }
    assert!(both_splits_done, "both shard splits did not complete within the allotted blocks");

    // Step 4: Stop saturating. Let the delayed queue drain.
    // If the vulnerability exists, processing the stale GlobalContractDistribution
    // receipt will panic in receipt_filter_fn() when receiver_shard_id() fails
    // to remap the old target_shard after two resharding generations.
    let current_height = {
        let node = env.node_for_account(&chunk_producer);
        node.client().chain.chain_store().head().unwrap().height
    };
    let drain_end = current_height + epoch_length * 2;
    env.runner_for_account(&chunk_producer).run_until_head_height(drain_end);

    let head_height = {
        let node = env.node_for_account(&chunk_producer);
        node.client().chain.chain_store().head().unwrap().height
    };
    assert!(
        head_height >= drain_end,
        "chain stalled at height {}; expected >= {} (likely panicked processing stale receipt)",
        head_height,
        drain_end
    );
