### Title
Cross-stack information disclosure via CCMenu API token scope bypass - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
An `ApiClient` token scoped to a single stack (`api_client.stack_id`) can be used to read the CCMenu status of **any** stack in the Shipit instance, not just the stack it was authorized for. This breaks the binding "a stack a token authorises versus a stack it touches", the exact analog class the report's bug (a checked/expected value never actually enforced against the value acted upon) maps to in this engine.

### Finding Description
`Shipit::Api::BaseController` scopes stack access to the token's authorized stack: [1](#0-0) 

```
def stacks
  @stacks ||= current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all
end

def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```

Every other API controller inherits this `stack` method, so a token created with a `stack_id` (e.g. via the `here_come_the_walrus`-style scoped client seen in `test/controllers/api/stacks_controller_test.rb`) can only resolve `stack` to the one row it's bound to; `Stack.from_param!` on an unauthorized stack id raises `ActiveRecord::RecordNotFound` because the scoped `stacks` relation excludes it.

`Shipit::Api::CCMenuController`, however, overrides `stack` and bypasses this scoping entirely: [2](#0-1) 

```
private

def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end

def authenticate_api_client
  @current_api_client = ApiClient.authenticate(params[:token])
  super unless @current_api_client
end
```

It only enforces `require_permission :read, :stack` (a permission bit, not a stack-membership check): [3](#0-2) 

Because `stack` is looked up directly against `Stack` (unscoped), the equality the system is supposed to enforce — `token.authorized_stack == stack_being_read` — is never checked here. Any valid token carrying the `read:stack` permission, even one explicitly created and scoped to Stack A, can be used to fetch CCMenu build/status data for Stack B, C, etc., by simply changing `params[:stack_id]` in the request.

### Impact Explanation
This is an authenticated but unauthorized cross-stack read of stack state (build status, last build label/time, lock state), matching the "High – unauthenticated/unauthorized read of stack state" impact category. An attacker holding any narrowly-scoped, low-privilege API token (e.g. one issued to a CI-status widget for a single non-sensitive stack) can enumerate and read the deploy/build status of every other stack in the Shipit instance, including private or sensitive stacks the token was never meant to see.

### Likelihood Explanation
Likelihood is high for any deployment that issues stack-scoped `ApiClient` tokens (a documented, encouraged practice, e.g. `stack_id` scoping shown in `test/controllers/api/stacks_controller_test.rb` "#index returns a list of stacks filtered by repo and api client"). Exploitation requires only possession of any such token (which the attacker is expected to legitimately hold for their own stack) and changing a URL parameter — no privilege escalation, secret material, or special access is needed beyond what an "unprivileged" scoped API client already has.

### Recommendation
Remove the `stack` override in `CCMenuController` and rely on the inherited, scoped `stacks`/`stack` implementation from `BaseController` (`stacks.from_param!(params[:stack_id])`), so that a stack-scoped token can only resolve to its authorized stack. Audit other controllers for similar overrides of `stack`/`stacks` that bypass `current_api_client.stack_id` scoping.

### Proof of Concept
1. Create two stacks, `stack-a` (private/sensitive) and `stack-b`.
2. Issue an `ApiClient` token scoped to `stack-b` only (`stack_id = stack-b.id`, permissions include `read:stack`).
3. As the holder of that token, call:
   `GET /stacks/stack-a-owner/stack-a-name/stack-a-env/ccmenu.xml?token=<stack-b-token>`
   (per `Shipit::Api::CCMenuController#show`, using `stack_id: params[:stack_id]`).
4. Observe the CCMenu XML for `stack-a` is returned successfully, even though the token is only authorized (via `current_api_client.stack_id`) for `stack-b` — confirming the scoping check enforced elsewhere (`BaseController#stack`) is skipped in `CCMenuController`.
