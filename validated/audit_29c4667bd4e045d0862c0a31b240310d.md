### Title
Boolean operator-precedence bug in `OpenedHandler#provision?` bypasses `review_stacks_enabled: false` when `provisioning_behavior` is `prevent_with_label` - ([File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb])

### Summary
`OpenedHandler#provision?` is written as a single boolean expression where Ruby's operator precedence (`&&` binds tighter than `||`) causes only the first disjunct to be gated by `repository.review_stacks_enabled`. The third disjunct, which handles `prevent_with_label`, evaluates independently of `review_stacks_enabled`, so a PR opened without the block-label triggers stack provisioning even when the repository owner has explicitly disabled review stacks.

### Finding Description
The broken binding: the intended invariant is `repository.review_stacks_enabled == true` for **any** `Shipit::ReviewStack` to be created via `OpenedHandler`, but the actual code guarantees only `(repository.review_stacks_enabled && provisioning_behavior_allow_all?) == true` as a precondition for the *first* disjunct.

Actual code, [1](#0-0) , parses as:

```ruby
(repository.review_stacks_enabled && repository.provisioning_behavior_allow_all?) ||
(repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
(repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
```

`review_stacks_enabled` is only referenced in the first parenthesized clause. When `provisioning_behavior == :prevent_with_label` and the incoming PR's `pull_request.labels` do not include `repository.provisioning_label_name`, the third clause is `true` regardless of `review_stacks_enabled`, so `provision?` returns `true`.

Path: `respond_to_pull_request_opened?` calls `provision?` [2](#0-1) ; if true, `process` invokes `ReviewStackAdapter#find_or_create!`, which creates a real `Shipit::ReviewStack` record and enqueues it for provisioning via `Shipit::ReviewStackProvisioningQueue.add(stack)` [3](#0-2) .

Attacker's exact action: open a legitimate pull request (via fork, as any contributor with fork/PR rights) against a repository configured with `review_stacks_enabled: false` and `provisioning_behavior: prevent_with_label`, deliberately not applying the configured block-label to the PR. GitHub delivers a normal, correctly-signed `pull_request` `opened` webhook to Shipit (no signature forgery or secret needed — this is a legitimate GitHub-originated event), and `OpenedHandler` processes it, creating an unauthorized `Shipit::ReviewStack`.

Existing guards do not prevent this: `verify_signature`/webhook signature verification only authenticates that the payload came from GitHub for that repo — it does not enforce the `review_stacks_enabled` business rule. The `ExplicitParameters` schema validates payload shape only. No model validation on `Repository` or `Stack` re-checks `review_stacks_enabled` before stack creation in `ReviewStackAdapter#create!`.

The existing test suite confirms the gap: it covers `review_stacks_enabled: false` only with `behavior: :allow_all` [4](#0-3) , and separately covers `prevent_with_label` only with `review_stacks_enabled` left at its default (enabled) [5](#0-4) . No test exercises `review_stacks_enabled: false` combined with `prevent_with_label`.

### Impact Explanation
An unprivileged PR author can force creation of a `Shipit::ReviewStack` — including a real infrastructure provisioning job queued via `Shipit::ReviewStackProvisioningQueue.add(stack)` — for a repository whose owner explicitly disabled review-stack auto-provisioning. This is a cross-tenant authorization bypass: the repository owner's configuration (`review_stacks_enabled: false`) is a security/cost control that is silently overridden by an untrusted PR contributor's choice not to add a label. It is repeatable against any repository configured this way, on every PR opened without the label, matching the Critical category ("a payload for one repository mutating another's stack" / "an unauthorized deploy" analog — here, an unauthorized stack/resource provisioning against explicit owner intent).

### Likelihood Explanation
Preconditions: the target repository must be tracked by Shipit and configured with `review_stacks_enabled: false` and `provisioning_behavior: prevent_with_label`. Given those settings (plausible, since `prevent_with_label` combined with disabling review stacks entirely is a reasonable admin intent — "disable auto-provisioning except require explicit opt-out label," or simply a misconfigured toggle), the attacker cost is trivial: open a PR without the label, which requires no elevated privileges — only the ability to open a PR against the repo (e.g., via fork on a public repo accepting external contributions). Fully repeatable per PR.

### Recommendation
Add explicit parentheses/short-circuit so `review_stacks_enabled` gates the entire expression, e.g.:

```ruby
def provision?
  return false unless repository.review_stacks_enabled

  repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
```

### Proof of Concept
In `test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb`:

```ruby
test "does not create stacks for repos with review_stacks_enabled false, prevent_with_label, and no label" do
  repository = shipit_repositories(:shipit)
  configure_provisioning_behavior(
    repository:,
    provisioning_enabled: false,
    behavior: :prevent_with_label,
    label: "pull-requests-label"
  )
  payload = payload_parsed(:pull_request_opened)
  payload["pull_request"]["labels"] = []

  assert_no_difference -> { Shipit::ReviewStack.count } do
    OpenedHandler.new(payload).process
  end
end
```

Binding to assert: `repository.review_stacks_enabled == false` must imply `Shipit::ReviewStack.count` unchanged after `OpenedHandler#process`, for every value of `provisioning_behavior` — including `prevent_with_label`. Under current code this assertion fails because `provision?` returns `true`.
