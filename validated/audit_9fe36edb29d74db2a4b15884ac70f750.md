### Title
Cross-organization forged commit status bypasses CI gating and enables an unauthorized deploy - (File: app/controllers/shipit/webhooks_controller.rb, app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
The reported bug is a class of vulnerability where a check is bound to the wrong identity/address: the factory validates `stakingToken` address deterministically without binding it to the legitimate caller's context, letting an attacker who can predict/observe that value break the invariant. In `shipit-engine`, the same class of flaw exists in how webhook authenticity is bound to the action performed: signature verification is keyed on `repository.owner.login` (the org whose GitHub App/`webhook_secret` is used), while `StatusHandler` performs its write using only `sha`, with **no scoping to the repository/organization that was actually verified**.

### Finding Description
`WebhooksController#verify_signature` selects which GitHub App config (and thus which `webhook_secret`) to use for HMAC verification based on `repository_owner`, taken directly from the untrusted JSON payload: [1](#0-0) [2](#0-1) 

Once the signature is verified against *that org's* secret, the payload is dispatched to handlers with no re-validation tying the payload's claimed repository to the repository the handler actually mutates: [3](#0-2) 

`StatusHandler#process` looks up commits **purely by `sha`**, globally across all stacks, and writes a new `Status` record from the attacker-supplied fields (`state`, `description`, `target_url`, `context`, `created_at`) with no repository check at all: [4](#0-3) 

That status directly feeds `Commit#deployable?`, which is the safety gate used before ships/deploys and continuous delivery: [5](#0-4) [6](#0-5) 

The engine explicitly supports installing multiple independent GitHub Apps for multiple organizations, each with its own `webhook_secret`, as documented: [7](#0-6) 

**Binding broken (equality that should hold but doesn't):**
`organization authenticated (repository.owner.login used to pick webhook_secret)` == `repository/commit actually written to (sha lookup with no owner scoping)`.

Before the attack: an org "attacker-org" has its own legitimately configured Shipit GitHub App/`webhook_secret` (a normal, unprivileged tenant in a multi-org Shipit install). A victim stack in "victim-org" has an undeployed commit with a known SHA (SHAs are public on GitHub) that is pending/failing CI.

After the attack: the attacker sends a `status` webhook where `X-Github-Event: status`, `repository.owner.login = "attacker-org"` (so the HMAC is computed and verified with attacker-org's own known `webhook_secret`), but `sha` is set to the victim commit's SHA and `state: "success"`. `verify_signature` passes because it only checks the signature against attacker-org's secret; `StatusHandler` then blindly matches by `sha` and creates a "success" `Status` for the victim's commit, regardless of which organization actually owns that commit.

### Impact Explanation
This crosses the "cross-repository writes" / "unauthorized deploy" impact bar explicitly listed as Critical: an attacker who legitimately controls only their own org's Shipit GitHub App can forge CI status for a commit belonging to a different organization's stack, and if that stack has `continuous_deployment: true` or a human triggers a deploy relying on the status, `deployable?` will report true, enabling an **unauthorized deploy** of a commit that never actually passed CI in the victim's repository. This is a real credential/trust-binding violation: the identity that was cryptographically authenticated (attacker-org) is not the identity whose data is mutated (victim commit/stack).

### Likelihood Explanation
Requires the host application to configure multiple GitHub Apps for multiple orgs (a documented, supported configuration), and requires the attacker to control at least one such org (e.g., is a legitimate tenant of a shared Shipit instance) and to know a target commit SHA (public information on GitHub). No `ApiClient` token, no session, and no privileged Shipit account is required — only the ability to receive/replay a signed request from a GitHub App the attacker legitimately controls. This is a realistic scenario for any multi-tenant Shipit deployment.

### Recommendation
Bind the verified organization to the repository being mutated: after verifying the signature for `repository_owner`, re-derive/validate that `payload.dig('repository','full_name')`'s owner matches the same `repository_owner`, and scope `StatusHandler` (and any handler using bare `sha`/global lookups) to only commits belonging to stacks under that verified repository/organization, instead of a global `Commit.where(sha: ...)` lookup.

### Proof of Concept
1. Configure Shipit with two GitHub Apps: `attacker-org` and `victim-org` (per `docs/setup.md` multi-org setup).
2. Attacker knows their own `attacker-org` webhook_secret (they administer that GitHub App) and knows the SHA of an undeployed, CI-pending commit in a `victim-org` stack (visible via GitHub UI/API).
3. Attacker POSTs to `/webhooks` with `X-Github-Event: status`, body: `{"repository":{"owner":{"login":"attacker-org"}}, "sha": "<victim-sha>", "state":"success", ...}`, and `X-Hub-Signature` computed with `attacker-org`'s secret.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: "attacker-org")` and verifies successfully.
5. `StatusHandler#process` runs `Commit.where(sha: "<victim-sha>")` (matches across all stacks) and creates a "success" status on the victim's commit via `commit.create_status_from_github!(params)`.
6. `Commit#deployable?` now returns true for the victim commit, allowing an unauthorized deploy/continuous-delivery trigger.

### Using Multiple Github Applications

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently. The top-level keys should be the name of each Github organization, and the following sub-keys are the Github app details for that particular organization.

For example:

```yml
production:
  github:
    somegithuborg:
      app_id:
      installation_id:
      webhook_secret:
      private_key:
      oauth:
        id:
        secret:
        teams:
    someothergithuborg:
      app_id:
      installation_id:
      webhook_secret:
      private_key:
      oauth:
        id:
        secret:
