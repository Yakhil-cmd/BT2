### Title
Webhook signature verification is scoped to the payload-supplied `repository.owner`/`organization` while the `status` handler writes to a globally-unscoped `Commit.where(sha:)` query — org that authenticated ≠ repository (or record) that is written (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App / `webhook_secret` to validate the HMAC signature against using an attacker-supplied JSON field (`repository.owner.login`, falling back to `organization.login`), and if that organization has no `webhook_secret` configured the check is bypassed entirely (`return true unless webhook_secret`). The `status` event handler, however, never re-derives or re-checks that same organization/repository scope when writing data: it matches and mutates `Commit` records purely by SHA, globally across every stack/repo tracked by the Shipit instance. This breaks the same "authenticated organization vs. written record" binding described in the referenced report (rounding direction favored the wrong side of an equality), except here the mismatch is not a rounding error but a complete absence of scope-binding between the field used to authenticate and the field used to write.

### Finding Description
`repository_owner` is computed purely from the untrusted request body and used to pick which app's secret validates the signature: [1](#0-0) [2](#0-1) 

If the organization named in that field happens to have no `webhook_secret` configured, `verify_webhook_signature` short-circuits and returns `true` unconditionally, regardless of the actual `X-Hub-Signature` header value: [3](#0-2) 

This is a documented, optional setting (`webhook_secret` "if you've set" one), so a multi-tenant Shipit deployment can legitimately have some organizations configured with a secret and others without one.

Once past `verify_signature`, the dispatched `StatusHandler` never re-checks any repository/organization scope. It looks up `Commit` rows purely by `sha` (a fully attacker-controlled field) with no join/filter on stack, repository, or organization at all: [4](#0-3) 

Contrast this with the base `Handler` class, which does scope by `repository.full_name` for other handlers (e.g. `PushHandler`), showing that `StatusHandler` is an outlier that omits repository binding entirely: [5](#0-4) [6](#0-5) 

Writing a status triggers CI-state changes and continuous-delivery scheduling regardless of which org's secret (if any) was used to authenticate the request: [7](#0-6) [8](#0-7) [9](#0-8) 

**Equality that should hold but is broken:** `organization used to select/verify webhook_secret == organization/repository whose Commit records are mutated`. In practice: `verify_signature` binds trust to `params.dig('repository','owner','login')`, while `StatusHandler#process` binds writes to `Commit.where(sha: params.sha)` — a completely different, unscoped predicate.

### Impact Explanation
An external, unprivileged attacker who knows (or can guess/enumerate) that at least one organization configured on the Shipit instance has no `webhook_secret` set can send a `status` event whose `repository.owner.login` names that unsecured organization (satisfying/bypassing signature verification with zero knowledge of any secret), while setting `sha` to the SHA of a commit tracked under a *different*, secured organization's stack. Because `StatusHandler` performs no repository check, the forged `state: "success"` status gets attached to that other stack's commit. This can:
- Falsely mark a commit as CI-successful (`deployable_status` hook, `schedule_merges`, `schedule_continuous_delivery`), potentially causing an **unauthorized deploy** if continuous deployment is enabled and the stack's deployability gate depends on that CI context reaching `success`.
- Corrupt commit status history/audit trail for stacks the attacker has no access to.

This matches the "High" impact bucket in the rules: escalation into unauthorized deploy triggered by a forged, unauthenticated cross-repository status write.

### Likelihood Explanation
Requires: (1) a multi-org Shipit deployment, (2) at least one configured organization without a `webhook_secret` (an explicitly optional, documented setting — plausible in real deployments, especially staging/legacy orgs), and (3) the target stack's deployability actually depending on the specific status `context` the attacker fabricates. This is analogous to the original report's characterization: the exploit is not guaranteed on every deployment but is concretely reachable given realistic, permitted configuration states, and requires no privileged credentials, API tokens, or GitHub App secrets — only knowledge of an unsecured org's name and a target commit SHA (both discoverable, e.g. via the public Shipit UI or GitHub).

### Recommendation
- In `StatusHandler` (and any other handler that mutates `Commit`/`Status` records), scope the lookup by the repository named in the *same signed payload* used for signature verification (i.e., join through `Repository`/`Stack` using `repository.full_name`, consistent with `Handler#stacks`), rather than a bare, cross-tenant `Commit.where(sha:)`.
- Do not allow `verify_webhook_signature` to return `true` when `webhook_secret` is blank for multi-org configurations; require every configured organization to have a non-blank secret, or refuse to process events for organizations without one.
- Ensure the value used to select the verifying secret and the value used to scope the resulting write always refer to the same organization/repository object.

### Proof of Concept
1. Configure two GitHub orgs in `secrets.yml`: `secured-org` (has `webhook_secret` set) and `unsecured-org` (no `webhook_secret`), both with stacks tracked in the same Shipit instance.
2. Attacker (no credentials) sends:
```
POST /webhooks
X-Github-Event: status
X-Hub-Signature: sha1=anything-or-omitted

{
  "sha": "<sha of a commit belonging to a stack under secured-org>",
  "state": "success",
  "context": "ci/travis",
  "repository": { "owner": { "login": "unsecured-org" }, "full_name": "unsecured-org/whatever" }
}
```
3. `verify_signature` calls `Shipit.github(organization: "unsecured-org")`; since that app has no `webhook_secret`, `verify_webhook_signature` returns `true` unconditionally [3](#0-2) .
4. `StatusHandler#process` runs `Commit.where(sha: params.sha)`, finds the `secured-org` commit (no org/repo filter), and calls `create_status_from_github!`, creating a `success` status on it [10](#0-9) .
5. If `secured-org`'s stack has continuous deployment enabled and was waiting on that CI context, this triggers deploy scheduling for a commit the attacker never had permission to affect.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
