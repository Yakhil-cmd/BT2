### Title
Global oracle-timestamp cache allows a front-runner to force `ERR-ORACLE-INVARIANT` reverts on a victim's borrow/repay/liquidate transaction - (File: `mainnet/contracts/market/v0-4-market.clar`)

### Summary
`market.clar`'s price resolution enforces a monotonic timestamp constraint against a single global map keyed only by `{type, ident}` (the oracle feed identifier), not by caller or position. Because any unprivileged caller can push a fresh signed Pyth price update via the optional `price-feeds` parameter on public entrypoints (`liquidate`, `collateral-add`, borrow/repay, etc.), an attacker can front-run a pending victim transaction with a newer Pyth VAA for the same feed, advancing the shared `last-update` cache past the timestamp embedded in the victim's own (already-signed, slightly older) VAA. The victim's transaction then fails `oracle-timestamp-fresh` and reverts with `ERR-ORACLE-INVARIANT`, exactly mirroring the Beanstalk report's pattern of a state written by one caller and consumed adversarially against another, causing denial-of-service on a time-sensitive protective action.

### Finding Description
`price-resolve` validates freshness against a shared, asset-scoped (not caller-scoped) map: [1](#0-0) 

```
(define-private (oracle-timestamp-fresh (ts uint) (prev uint) (max-staleness uint))
  (let ((delta ...))
    (and
      (<= delta max-staleness)
      (>= ts prev))))

(define-private (price-resolve ...)
  (let (...
        (last-update-time (oracle-last-update key))
        ...)
    (asserts! (and (oracle-price-legal final-price) (oracle-timestamp-fresh timestamp last-update-time max-staleness))
              ERR-ORACLE-INVARIANT)
    (if (> timestamp last-update-time)
        (map-set last-update key timestamp)
        false)
    (ok final-price)))
```

`key` is `{ type: type, ident: ident }` — i.e. it is shared across every account and every position that references that price feed identifier, updated by `map-set last-update` on any caller's transaction. `write-feeds`/`write-feed` allow any unprivileged caller to submit a `(list 3 (buff 8192))` of raw Pyth update payloads together with any market call, updating both the shared on-chain Pyth storage and (via subsequent `price-resolve`) this `last-update` cache: [2](#0-1) 

This is used by every state-changing entrypoint that accepts `(price-feeds (optional (list 3 (buff 8192))))`, e.g. `liquidate`: [3](#0-2) 

Attacker (any address) and victim (any borrower/liquidator) share this state through the single global `last-update[{type,ident}]` entry for a given asset's oracle feed. An attacker who observes a victim's pending transaction in the mempool (which embeds a Pyth VAA with timestamp `T_v`) can fetch a newer, still-valid Pyth VAA for the same feed (Pyth republishes prices roughly every second) with timestamp `T_a > T_v`, and submit it first (any harmless market call with `price-feeds` set). This advances `last-update` to `T_a`. When the victim's transaction then executes with `T_v < T_a`, `oracle-timestamp-fresh` returns `false` and the whole transaction reverts with `ERR-ORACLE-INVARIANT` — independent of any economic cost to the attacker, similar to the low-cost sandwich in the source report.

### Impact Explanation
Victim outcome without attacker: the victim's `collateral-add`/`repay`/`liquidate` transaction with a valid, non-stale Pyth VAA succeeds normally (e.g. a borrower tops up collateral to escape liquidation, or a liquidator liquidates an unhealthy position).

Victim outcome with attacker: the identical, individually valid transaction reverts purely because the shared `last-update` timestamp was advanced by an unrelated party's transaction executed first in the same block. A well-timed attacker can repeat this each time the victim resubmits (each time fetching a marginally newer VAA), effectively denying the victim's protective action (`collateral-add`/`repay`) for as long as they choose, while an attacking liquidator races to seize the now-eligible position, or a targeted borrower is prevented from repaying/liquidating in time. This is a temporary freezing of the victim's ability to act on their own funds/position, and in the liquidation-race case can translate into the attacker capturing a liquidation opportunity (bonus/collateral) that would not otherwise have existed — a "High" impact (temporary freezing of funds / unclaimed value) analogous to the Flood-mechanism DoS in the source report.

### Likelihood Explanation
The precondition is only that: (1) the market has more than one Pyth price update available for the same feed within the caller's expected window (trivially true given Pyth's ~sub-second publish cadence), and (2) the attacker can observe the victim's pending transaction to extract its target feed/asset and race it with a fresher VAA. Both are cheap and require no special privilege — comparable to the near-zero-cost sandwich noted in the original report. The attack does not need a flashloan or any governance/DAO compromise, and is purely a function of `market.clar`'s global, non-partitioned `last-update` cache.

### Recommendation
Scope the freshness/monotonicity check to the caller's own transaction rather than a global cross-user cache — e.g., only require `ts` to be within the staleness window of `stacks-block-time`, and drop (or make caller/position-scoped) the `(>= ts prev)` comparison against a globally shared `last-update` map so that one user's Pyth submission cannot invalidate another user's independently valid, freshly-signed price update in the same or a later block.

### Proof of Concept
1. Victim signs and broadcasts `collateral-add` (or `repay`/`liquidate`) with `price-feeds` containing a Pyth VAA for asset `X` with `publish-time = T_v`, which is fresh relative to `max-staleness` and to the currently stored `last-update[X]`.
2. Attacker observes this transaction in the mempool, fetches (from the public Pyth Hermes API) a newer valid VAA for the same feed `X` with `publish-time = T_a > T_v`.
3. Attacker submits any market call (e.g. a harmless `collateral-add` of a negligible/self-owned amount, or simply `write-feeds` indirectly via any entrypoint) carrying that VAA, with a higher fee/earlier position so it executes first in the block; `price-resolve` succeeds and `map-set last-update {type,ident} T_a` runs.
4. Victim's original transaction now executes; `price-resolve` computes `oracle-timestamp-fresh(T_v, T_a, max-staleness)` → `(>= T_v T_a)` is `false` → `asserts!` fails → entire transaction reverts with `ERR-ORACLE-INVARIANT`, regardless of the fact that `T_v` was itself perfectly fresh and valid in isolation.
5. Attacker repeats this at negligible cost each time the victim resubmits, indefinitely delaying the victim's collateral top-up/repay while the position remains liquidatable, or blocking a competing liquidator's `liquidate` call so the attacker's own (later) liquidation lands instead.

Note: I was unable to execute this against a live/test environment from this tool set; the analysis is based on static reading of `price-resolve`, `oracle-timestamp-fresh`, and `write-feeds` in `mainnet/contracts/market/v0-4-market.clar`. Confirming exact staleness-window sizes and Pyth publish cadence in production would require running the local test suite (`local-testing/`) or a Devin session with full repository/tooling access.
