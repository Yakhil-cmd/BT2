### Title
Webhook Signature Verification Does Not Bind the Authenticated Organization to the Repository Whose Data Is Written - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret to use for HMAC verification from an **unverified** field of the incoming JSON body (`repository.owner.login` or `organization.login`), then hands the same unverified body to event handlers that identify *which repository/commit to mutate* using a **different, unrelated field** of that same body (`repository.full_name`, or for status events, no repository check at all). Because the two lookups are independent, a payload signed with organization A's webhook secret can still cause writes against organization B's stacks/commits.

### Finding Description
`WebhooksController#verify_signature` picks the signing key like this: [1](#0-0) [2](#0-1) 

`repository_owner` is read straight out of the untrusted, unverified request body (`params.dig('repository', 'owner', 'login')` / `organization.login`) *before* the signature is checked, and it is only used to pick the `Shipit.github(organization:)` instance whose `webhook_secret` is used to validate `X-Hub-Signature`: [3](#0-2) 

Once verification succeeds, the raw params are dispatched to handlers unchanged: [4](#0-3) 

Handlers, however, resolve the target repository/stack from a **different field of the same body**, `repository.full_name`, with no cross-check against the organization that was actually used to verify the signature: [5](#0-4) 

`PushHandler` uses this to enqueue a resync of any stack under the named repo: [6](#0-5) 

`StatusHandler` is worse: it does not even use `repository_name`/`stacks` — it matches by commit SHA **globally, across every repository in the Shipit instance** and writes a status record: [7](#0-6) 

Multi-organization Shipit installations configure a distinct `webhook_secret` per GitHub organization, exactly to keep one organization's app from being able to speak for another's: [8](#0-7) 

**Binding that should hold:** `organization authenticated via X-Hub-Signature == organization owning the repository/commit being written`.

**Before an attack:** a legitimate GitHub webhook for org A is signed with org A's `webhook_secret`, `repository.owner.login == "A"`, and `repository.full_name` is also an "A/..." repo — the two fields agree.

**After the attacker's crafted request:** the attacker only needs a valid `webhook_secret` for *any one* organization configured on the Shipit instance (e.g. their own org A, which they administer and therefore legitimately know the secret for, per the setup docs). They send:
- `X-Hub-Signature` computed with org A's `webhook_secret`
- `repository.owner.login = "A"` (or `organization.login = "A"`) — satisfies `verify_signature`
- `repository.full_name = "B/some-repo"` (org B's repo, tracked by a different stack) for push events, or simply any `sha` belonging to a commit under org B for status events

`verify_signature` passes because it only checks org A's secret. `PushHandler`/`StatusHandler` then act on org B's stacks/commits because they never re-validate that `repository.full_name`'s owner equals the organization that produced a valid signature.

### Impact Explanation
This breaks the "organization authenticated vs. repository written" trust binding called out in scope, resulting in **cross-repository/cross-organization writes**: an attacker who controls a GitHub App installation/webhook secret for one tenant organization on a multi-org Shipit instance can inject fabricated commit statuses (`StatusHandler`) or trigger sync/deploy-adjacent jobs (`PushHandler`) against a completely different organization's stacks and commits, without ever authenticating to that organization. Forged commit statuses can flip a commit from "pending/failure" to "success" for a foreign repository's stack, which is exactly the kind of gate Shipit uses to allow deploys — an unauthorized write with deploy-authorization consequences.

### Likelihood Explanation
Exploitability requires only a valid webhook secret for *one* organization on the Shipit instance — which is knowledge the attacker legitimately possesses for their own org — plus the ability to guess/observe another tracked repository's `full_name` or an in-flight commit `sha` (both are non-secret, often public, GitHub metadata). No GitHub App private key, `api_clients_secret`, or Shipit session is needed, only a single organization's webhook secret, which is a lower-privilege credential than the ones excluded by scope.

### Recommendation
After `verify_signature` succeeds, re-derive the organization/repository the event is allowed to affect strictly from the same field that was cryptographically verified (`repository_owner`), and reject or scope the handler's target lookup (`Handler#repository_name`, `PushHandler`, and especially `StatusHandler`'s unscoped `Commit.where(sha:)`) to repositories owned by that verified organization only.

### Proof of Concept
1. Configure/observe that the attacker controls org `A`'s Shipit GitHub App installation and therefore knows `webhook_secret_A`.
2. Note a commit `sha` (or `repository.full_name`) belonging to a stack under org `B`, also tracked by the same Shipit instance.
3. Craft a `push`/`status` webhook JSON body with `repository.owner.login = "A"` but `repository.full_name = "B/target-repo"` (push) or an org-`B` commit `sha` (status).
4. Sign the raw body with `webhook_secret_A` and send it as `X-Hub-Signature` to `POST /webhooks`.
5. `verify_signature` resolves `Shipit.github(organization: "A")` and successfully verifies the signature against `webhook_secret_A`.
6. `PushHandler`/`StatusHandler` process the body, resolving the actual target via `repository.full_name` or a global commit-`sha` lookup — mutating org `B`'s stack/commit state despite the request never having been authenticated for org `B`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

### Using Multiple Github Applications

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently. The top-level keys should be the name of each Github organization, and the following sub-keys are the Github app details for that particular organization.

      private_key:
      oauth:
        id:

    someothergithuborg:
