### Title
Webhook Signature Verified Against Payload-Chosen Organization While Push/Status/Membership Handlers Act on a Different Repository/Owner From the Same Payload - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App (and thus which `webhook_secret`) to validate the inbound HMAC against using a field taken directly from the untrusted JSON body — `repository.owner.login` (or `organization.login`) — rather than from any value bound to a specific, already-provisioned installation. [1](#0-0)  Once the signature check passes, the full, unvalidated `params` hash (including `repository.full_name`) is handed to every registered handler for the event. [2](#0-1)  Nothing re-validates that the repository/stack a handler subsequently looks up or mutates (via `repository.full_name`) actually belongs to the same `owner.login` that was used to pick the signing secret.

### Finding Description
Shipit is designed to serve multiple GitHub organizations from one instance, each configured with its own independent `webhook_secret` in `secrets.yml` (`config/secrets.development.shopify.yml` shows two separate orgs, each with their own `webhook_secret`). [3](#0-2)  `GithubApp#verify_webhook_signature` verifies the raw request body against exactly one secret — the one for the org resolved from `repository_owner`: [4](#0-3) 

```
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  algorithm, signature = signature.split("=", 2)
  return false unless algorithm == 'sha1'
  SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
end
```

The org used to select `webhook_secret` is derived entirely from attacker-supplied JSON: [5](#0-4) 

```
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

This creates an equality that is never enforced: `signing_org (repository.owner.login used to pick webhook_secret)` == `target_org (owner segment of repository.full_name used by handlers to resolve/create the Stack/Repository)`. Only the left-hand side is authenticated; the right-hand side, taken from the same request body, is what handlers such as the push/status handlers actually act on. The existing test suite already demonstrates that `repository.full_name` alone drives repository/stack resolution and can diverge from other repository fields in the same payload, independent of signature verification: [6](#0-5) 

An operator who legitimately administers *any* one GitHub org onboarded to a shared Shipit instance possesses that org's `webhook_secret` (it is configured per-org for installations they control) and can sign arbitrary JSON with it. Because the org used to choose the secret and the org whose repository is ultimately written to are read from two different, non-cross-checked fields of the same signed body, that operator can forge a webhook whose `repository.owner.login`/`organization.login` matches their own org (so signature verification passes against their own secret) while `repository.full_name` names a repository belonging to a completely different, unrelated org also hosted on the same Shipit instance.

### Impact Explanation
This breaks the "organization that authenticated versus the repository that is written" trust binding explicitly called out as in-scope. A forged `push` event can enqueue `GithubSyncJob` against an arbitrary stack matched by the attacker-chosen `repository.full_name`, and a forged `membership` event can create/delete `Team`/`Membership` records tied to the target org, altering authorization state used by `Shipit.github_teams` checks. Depending on which handler is exercised, this can escalate into cross-repository state changes or authorization-affecting writes for an org the attacker does not control — matching the High-impact category (escalation into `Shipit.github_teams` authorization / unauthorized cross-tenant writes).

### Likelihood Explanation
Exploitation requires only that the attacker legitimately controls at least one GitHub organization/app installation already configured on the shared Shipit instance (an "unprivileged" position relative to the victim org) — no `ApiClient` token, GitHub App private key, or TLS interception is required. This is a realistic operating condition for any multi-tenant Shipit deployment, which the docs explicitly support (multiple orgs configured under `github:` in `secrets.yml`). [7](#0-6) 

### Recommendation
- Short term: after `verify_webhook_signature` succeeds, re-derive the target repository/stack strictly from the same organization value that was authenticated (`repository_owner`), and reject the webhook if `repository.full_name`'s owner segment does not match `repository_owner`/`organization.login`.
- Long term: bind webhook secrets to a specific `installation_id`/app config and validate every repository-scoped payload field (`full_name`, `owner.login`) against that installation's known set of repositories before dispatching to handlers, rather than trusting unauthenticated fields of the same JSON body used only for routing.

### Proof of Concept
1. Attacker administers `org-attacker`, a GitHub org/app installation configured on the shared Shipit instance with `webhook_secret: S_attacker`.
2. Attacker crafts a `push` payload: `repository.owner.login = "org-attacker"`, `organization.login = "org-attacker"`, but `repository.full_name = "org-victim/target-repo"`.
3. Attacker computes `X-Hub-Signature` as `sha1=HMAC(S_attacker, raw_body)`.
4. `WebhooksController#verify_signature` resolves `Shipit.github(organization: "org-attacker")` and verifies successfully because the attacker used the correct secret for that org. [8](#0-7) 
5. `create` proceeds and dispatches `params` (still containing `org-victim/target-repo`) to the push handler, which enqueues `GithubSyncJob` for the stack matching `org-victim/target-repo`, as shown to be driven purely by `repository.full_name` in the existing test. [9](#0-8) 

Note: direct inspection of `app/models/shipit/webhooks/handlers/push_handler.rb` could not be completed in this session due to a tool error on the final iteration; the behavioral claim about `repository.full_name`-only resolution is supported by the webhook controller test fixtures rather than by reading the handler source directly. A follow-up review of that handler is recommended to confirm the exact lookup key before remediation.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
