### Title
Missing upper-bound validation on `system_vote` numeric parameters (`threshold_size`, `tps_interval`) allows a majority-stake voting bloc to push network-critical fee parameters to unsafe extremes - ([File: validation.js])

### Summary
`ocore` implements an on-chain, stake-weighted governance mechanism (`system_vote` / `system_vote_count` messages) that lets addresses vote to change protocol parameters: `op_list`, `threshold_size`, `base_tps_fee`, `tps_interval`, and `tps_fee_multiplier` [1](#0-0) . This is structurally analogous to Nouns DAO's `NounsDAOV3Admin.forkPeriod`/`forkThresholdBPS` governance knobs: a majority of voting weight (bytes balance) can change consensus-relevant parameters, and some of these parameters are validated with only a one-sided bound, not a symmetric min/max range.

### Finding Description
In `validateInlinePayload`'s `system_vote` case, each numeric subject is range-checked inconsistently [2](#0-1) :
- `threshold_size`: only a **minimum** of 1000 is enforced (`payload.value < 1000`); there is **no maximum**.
- `tps_interval`: only a **minimum** of 0.1 is enforced (`payload.value < 0.1`); there is **no maximum**.
- `base_tps_fee`: only a **maximum** of 1e8 is enforced; no explicit minimum other than `> 0`.
- `tps_fee_multiplier` is the only subject with both a minimum and a maximum (1 to 1000).

These values are collected as one-address-one-vote-weighted-by-balance entries in `numerical_votes`, tallied by `countVotes()` in `main_chain.js` using a stake-weighted median, and then written into `storage.systemVars[subject]`, taking effect network-wide from the counted MCI onward [3](#0-2) . Any address whose stake-weighted vote wins the median can permanently shift the parameter, exactly as a majority-stake actor can shift `forkPeriod`/`forkThresholdBPS` in the Nouns DAO report. Because `threshold_size` and `tps_interval` have only one-sided bounds, a majority voting bloc can drive them to extreme values (e.g., an enormous `tps_interval`, or an extreme `threshold_size`) that inattentive minority stakeholders did not anticipate and cannot immediately counteract, since changing the value back requires organizing a new majority vote, and the parameter takes effect automatically once counted.

### Impact Explanation
`tps_interval` and `threshold_size` feed the network's TPS-fee-based anti-spam/anti-congestion mechanism (`base_tps_fee`/`tps_interval`/`tps_fee_multiplier` are always voted on and consumed together as a set, per `initial_votes.js` and `network.js`'s `get_system_vars`/`get_system_var_votes` handlers) [4](#0-3) [5](#0-4) . Pushing `tps_interval` to an extreme value (with no ceiling enforced) can distort the TPS-fee averaging window used to price and throttle transaction throughput, degrading the network's ability to fairly price and confirm units, or effectively disabling the intended fee-based congestion control - a "network unable to confirm new units under fair conditions" class of impact, mirroring how an unbounded `forkPeriod` locks minority Nouns holders out of protecting their funds. Because I could not fully trace every downstream consumer of `tps_interval` in the fee-calculation modules within the available search budget, the precise numerical failure mode (overflow vs. starvation vs. fee bypass) is not fully confirmed and should be verified directly in the fee-calculation code before treating this as certain; the concrete finding is the validation asymmetry itself, which is directly analogous to the reported bug class.

### Likelihood Explanation
Requires a coalition holding a stake-weighted majority of `TOTAL_WHITEBYTES` participating in the vote (per `SYSTEM_VOTE_MIN_SHARE` expanding-window logic in `countVotes`) [6](#0-5) , so — like the original Nouns finding — likelihood is low, but the same "malicious majority governance capture" precondition as the source report applies directly to this governance surface, and the missing bound is a straightforward oversight comparable to the missing `MIN_FORK_PERIOD`.

### Recommendation
Apply symmetric min/max bounds to all `system_vote` numeric subjects, not just `tps_fee_multiplier`: add an explicit maximum for `threshold_size` and `tps_interval` (and an explicit minimum for `base_tps_fee` beyond `>0`) in the `system_vote` validation switch in `validation.js`, consistent with how `tps_fee_multiplier` is bounded. Consider also rate-limiting how much a single vote-count cycle can move these parameters, analogous to the recommendation to prevent decreasing `forkPeriod` during an active escrow window in the source report.

### Proof of Concept
1. A coalition controlling a stake-weighted majority of address balances (subject to `SYSTEM_VOTE_MIN_SHARE` participation) posts `system_vote` units with `subject: "tps_interval"` and an extreme `value` (e.g. a very large number), which passes validation because only `value < 0.1` is rejected — no upper bound exists [7](#0-6) .
2. Once the MCI containing enough votes stabilizes, `countVotes()` computes the stake-weighted median and writes the new `tps_interval` into `system_vars`/`storage.systemVars`, effective from that MCI onward, with no possibility for minority holders to opt out [3](#0-2) .
3. The extreme `tps_interval` value now governs the anti-spam TPS-fee calculation network-wide, degrading the network's transaction-fee/congestion protections for all users who did not participate in or notice the vote — an effect structurally identical to the malicious-majority `forkPeriod` capture described in the source report, differing only in which governance parameter is abused.
