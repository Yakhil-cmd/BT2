### Title
Forged `check_suite` webhook via no-secret organization bypasses signature verification and lets attacker choose the target repository - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/handler.rb`, `app/models/shipit/webhooks/handlers/check_suite_handler.rb`)

### Summary
`WebhooksController#verify_signature` selects the GitHub App config to verify against using only `repository.owner.login`, and `GitHubApp#verify_webhook_signature` returns `true` unconditionally when that org's `webhook_secret` is blank. The handler layer (`Handler#stacks`), however, selects the target stacks using `repository.full_name`, a completely separate, attacker-controlled field. Because these two fields are never checked for consistency, an attacker can set `repository.owner.login` to an org configured in Shipit with no `webhook_secret` (so the check passes) while setting `repository.full_name` to any other org/repo, allowing `CheckSuiteHandler` to mutate commits/stacks belonging to a victim repository.

### Finding Description
The broken binding: the question's invariant requires `organization_that_verified_signature == organization_that_owns_the_mutated_repository/stack/commit`. In code this is `params.dig('repository','owner','login')` (used in `repository_owner`) `== payload.dig('repository','full_name').split('/').first` (used in `Handler#repository_name`/`stacks`). These are never enforced to be equal.

- `Shipit::WebhooksController#verify_signature` computes `repository_owner` as `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` and fetches `Shipit.github(organization: repository_owner)`: [1](#0-0) [2](#0-1) 
- `GitHubApp#verify_webhook_signature` returns `true` immediately when `webhook_secret` is blank, with no HMAC check at all: [3](#0-2) 
- Once accepted, `WebhooksController#create` parses the raw JSON body and dispatches it, unmodified, to `Shipit::Webhooks::Handlers::CheckSuiteHandler`: [4](#0-3) 
- `Handler#stacks` resolves the target repository by `payload.dig('repository', 'full_name')` — a field entirely independent from `repository.owner.login` used above: [5](#0-4) 
- `CheckSuiteHandler#process` then filters those stacks by attacker-controlled `head_branch` and reschedules check-run refresh for commits matching attacker-controlled `head_sha`: [6](#0-5) 

Exploit flow: the attacker crafts a JSON body where `repository.owner.login = "no-secret-org"` (an org configured in Shipit but with `webhook_secret` empty/absent) and `repository.full_name = "victim-org/victim-repo"` (a real, secured, unrelated repository with existing stacks/commits). They POST it to `/webhooks` with `X-Github-Event: check_suite` and any/no `X-Hub-Signature`. `verify_signature` looks up `Shipit.github(organization: "no-secret-org")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` without ever checking the signature. The request proceeds to `CheckSuiteHandler`, which resolves stacks via `repository.full_name = "victim-org/victim-repo"` and mutates that victim's commits (`schedule_refresh_check_runs!`) — a repository the attacker never authenticated against and holds no secret for.

None of the existing guards catch this: `verify_signature` never compares `repository.owner.login` to `repository.full_name`'s owner segment; `drop_unhandled_event` only checks the event type is registered; the `ExplicitParameters` schema for `CheckSuiteHandler` only requires `head_sha`/`head_branch` types, not repository identity; there is no `force_github_authentication`, `User#authorized?`, or `require_permission!` check anywhere in this unauthenticated webhook path (which is by design, since GitHub webhooks are meant to be verified by signature alone — the whole security model rests on the signature check that is bypassed here).

### Impact Explanation
Any org configured in Shipit without a `webhook_secret` becomes a skeleton key: signing with "no signature required" for that org unlocks handler execution against **any** repository, because the repository used for the HMAC-org lookup (`repository.owner.login`) and the repository used to select mutated records (`repository.full_name`) are decoupled fields in the same attacker-controlled JSON body. This is a cross-tenant state-mutation bug: an unprivileged internet user can trigger `schedule_refresh_check_runs!` on commits of any stack/repository configured in the target Shipit instance, without ever holding that repository's `webhook_secret`. While `CheckSuiteHandler` itself only reschedules check-run refresh jobs (a relatively low-impact action per se), the same divergence (`repository.owner.login` vs `repository.full_name`) applies to every other `Shipit::Webhooks::Handlers` class that reads `payload['repository']['full_name']` via `Handler#stacks`, so the blast radius extends to any handler performing state changes keyed off `full_name` (e.g. status/check-run updates, PR handlers) — matching the "payload for one repository mutating another's stack/commit" Critical category, contingent on at least one Shipit-configured org lacking a `webhook_secret`.

### Likelihood Explanation
Preconditions: the target Shipit instance must have at least one GitHub organization configured (in `Shipit.github_configs`/similar) without a `webhook_secret` — a realistic misconfiguration, since `@webhook_secret = @config[:webhook_secret].presence` silently tolerates blank/missing secrets rather than raising. No Shipit credentials, sessions, or tokens are needed; the attacker only needs to know (or guess/enumerate) the login of such an org and the `full_name` of a victim repository already known to be configured in Shipit (visible in the Shipit UI/URLs, which is typically public within an org). The request is a single unauthenticated `POST /webhooks` with attacker-fully-controlled JSON, trivially repeatable and scriptable against arbitrary stacks/commits.

### Recommendation
In `Shipit::WebhooksController#verify_signature`, require that the organization derived from `repository.full_name` (the one actually used by handlers to select stacks) matches the organization used for signature verification, and reject (422) on mismatch. Additionally, treat a blank `webhook_secret` as a configuration error that fails closed (reject the webhook) rather than as an implicit bypass, and have `Handler#repository_name` cross-validate against the verified organization rather than trusting `repository.full_name` unconditionally.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (new test)
test "check_suite webhook from an org with no webhook_secret can mutate a different org's stack" do
  # Arrange: victim org+repo with a real secret, attacker org with a blank secret
  Shipit.stubs(:github).with(organization: 'no-secret-org').returns(
    Shipit::GitHubApp.new('no-secret-org', { webhook_secret: nil })
  )
  victim_stack = shipit_stacks(:shipit) # owned by e.g. "victim-org/victim-repo"
  victim_commit = victim_stack.commits.last
  victim_stack.update!(branch: 'main')
  victim_commit.update!(sha: 'deadbeef')

  body = {
    repository: { owner: { login: 'no-secret-org' }, full_name: victim_stack.repository.full_name },
    check_suite: { head_sha: 'deadbeef', head_branch: 'main' }
  }.to_json

  # Left side of invariant: org that "verifies" = "no-secret-org"
  # Right side of invariant: org that owns mutated record = victim_stack.repository.owner
  assert_not_equal 'no-secret-org', victim_stack.repository.owner

  post :create, body: body, headers: { 'X-Github-Event' => 'check_suite', 'X-Hub-Signature' => 'sha1=bogus' }

  assert_response :ok
  # Assert the victim's commit was mutated despite attacker never holding victim's webhook_secret
  assert_enqueued_with(job: RefreshCheckRunsJob) # or assert changed state on victim_commit
end
```
This demonstrates that `repository_owner` (used to select the verifying `webhook_secret`) and `repository.full_name` (used to select the mutated stack/commit) can diverge, and that a blank secret on an unrelated org lets the forged payload mutate a victim repository's records.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
