### Title
Cross-repository commit-status forgery via unscoped `Commit.where(sha:)` lookup - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up target commits with a global `Commit.where(sha: params.sha)` query that has no repository/organization filter, unlike sibling handlers such as `PushHandler` which scope through the `stacks` helper (which filters by `payload.dig('repository','full_name')`). Because webhook signature verification (`WebhooksController#verify_signature`) only proves the payload was signed by the org named in the payload itself, an attacker who owns any GitHub org/repo can send a validly-signed `status` webhook naming a `sha` belonging to a victim stack in a completely different repository, and `StatusHandler` will happily write a forged status onto that victim commit.

### Finding Description
The binding that should hold is: `repository named in the verified payload (payload.dig('repository','full_name'))` == `repository owning the Commit row identified by params.sha`. This binding is never checked.

Code path:
- `WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-49`) resolves `Shipit.github(organization: repository_owner)` where `repository_owner` comes from `params.dig('repository','owner','login')` in the **attacker's own payload**, and verifies the signature against that org's webhook secret. This only proves "the org in this payload signed this payload" — it proves nothing about which `sha`s that org is authorized to attest to.
- `Shipit::Webhooks.for_event('status')` dispatches to `StatusHandler.call(params)` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`).
- `StatusHandler#process` runs `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` — a global lookup across **all stacks/repositories** in the Shipit instance, with no reference to `payload.dig('repository', ...)` at all.
- Contrast with `PushHandler#process` (`app/models/shipit/webhooks/handlers/push_handler.rb:12-17`), which correctly scopes via `stacks` (defined in `Handler#stacks`, `app/models/shipit/webhooks/handlers/handler.rb:32-34`), itself derived from `Repository.from_github_repo_name(repository_name)`.
- `Commit#create_status_from_github!` (`app/models/shipit/commit.rb:165-169`) creates a `Status` row and triggers `add_status`, which emits `Hook.emit(:commit_status, ...)`/`:deployable_status` and calls `stack.schedule_merges`, directly affecting `deployable?` (`app/models/shipit/commit.rb:227-229`) and merge-gating for the victim stack.

Attacker exploit: attacker creates/owns GitHub org "attacker-org" with a repo registered as a Shipit `Repository`/`Stack` (or any repo triggering a valid webhook secret lookup), obtains a legitimate signed webhook by pushing to their own repo, then crafts/sends a `status` event to `POST /webhooks` with `X-Hub-Signature` computed using their own (self-controlled) webhook secret, `repository.owner.login` = their own org (so `verify_signature` passes), but `sha` set to a 40-hex value equal to a real commit sha in victim stack B. No knowledge of victim's secret, org membership, or session is required — only that the attacker knows/guesses a victim's real commit sha (commit shas are often publicly visible via PRs, CI logs, badges, etc.).

Existing guards checked and found insufficient:
- `verify_signature` / `GitHubApp#verify_webhook_signature` — verifies payload integrity per-org, but the org is attacker-controlled and never cross-checked against the resolved `Commit`'s stack/repository.
- `drop_unhandled_event` — only checks the event type is handled; `status` is a handled event.
- `ExplicitParameters` schema in `StatusHandler` — validates types/presence of `sha`, `state`, etc., but has no repository-binding field or check.
- No `Repository` format validator or `stacks` scoping is invoked anywhere in `StatusHandler`.

### Impact Explanation
An attacker fully controlling an unrelated GitHub org/repo (webhook-secret owner of their own account) can write arbitrary commit statuses (`state`, `description`, `target_url`, `context`) onto any victim commit in any other stack managed by the same Shipit instance, provided they know that commit's sha. This directly manipulates `Commit#deployable?` and `blocked?`/merge-gating logic, and can force `stack.schedule_merges` to run, potentially triggering an unauthorized merge/deploy decision on a victim's stack — satisfying the "payload for one repository mutating another's stack/commit" Critical impact category. It is fully repeatable against any known sha in any hosted stack.

### Likelihood Explanation
Preconditions: attacker needs a Shipit-registered repository they control (to have a real webhook secret to sign with) or any org for which `Shipit.github(organization: ...)` resolves successfully, and knowledge of a target victim commit's 40-character sha (often discoverable via public GitHub activity, PR pages, CI badges, or Shipit's own public UI if stacks are visible). No Shipit credentials, GitHub App keys, or team membership are required. Cost is a single crafted, correctly-signed HTTP POST to `/webhooks`. This is highly feasible and trivially repeatable.

### Recommendation
Scope the `Commit` lookup in `StatusHandler#process` to only commits belonging to stacks under the repository named in the verified payload, mirroring `PushHandler`'s use of `stacks`, e.g. `stacks.flat_map(&:commits).select { |c| c.sha == params.sha }` or `Commit.where(sha: params.sha, stack_id: stacks.select(:id))`, ensuring `repository_name` (from `payload.dig('repository','full_name')`) is bound to the commit's owning stack/repository before applying the status.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb`):
```ruby
test "status event from unrelated repository forges status on victim commit" do
  victim_stack = shipit_stacks(:shipit) # repo A
  victim_commit = victim_stack.commits.create!(sha: '1' * 40, message: 'victim commit')

  # payload signed/verified as belonging to attacker's own repo/org B, but naming victim's sha
  attacker_payload = {
    'sha' => victim_commit.sha,
    'state' => 'success',
    'context' => 'attacker-forged',
    'repository' => { 'full_name' => 'attacker/unrelated-repo', 'owner' => { 'login' => 'attacker-org' } }
  }

  assert_difference -> { victim_commit.statuses.count }, 1 do
    Shipit::Webhooks::Handlers::StatusHandler.call(attacker_payload)
  end

  assert_equal 'success', victim_commit.reload.status.state
end
```
Assertion of the broken binding: `attacker_payload.dig('repository','full_name') == 'attacker/unrelated-repo'` while `victim_commit.stack.repository.full_name == 'shopify/shipit-engine'` (or equivalent victim repo) — these are unequal, yet the status is still written to `victim_commit`, proving the binding is not enforced.
