### Title
`StatusHandler#process` writes commit statuses by bare SHA with no repository scoping, letting one repo's `status` webhook flip `blocked?`/`deployable?` on any other stack sharing the SHA - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` resolves target records with `Commit.where(sha: params.sha)` and calls `commit.create_status_from_github!(params)` on every match, with no check that `params.dig('repository','full_name')` (or `.name`) equals `commit.stack.github_repo_name` [1](#0-0) . Because `Commit` rows for different `Stack`s (different repositories) can legitimately share the same `sha` (forks, shared history, imported/mirrored repos), a validly-signed `status` event for repo A is applied to every stack that happens to have a commit with that SHA, including victim stacks for repo B.

### Finding Description
The broken binding, stated as an equality that the code must (but does not) enforce:

`commit.stack.github_repo_name == params.dig('repository', 'full_name')`

`StatusHandler#process` never checks this. It only checks `sha` equality:

```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [1](#0-0) 

`create_status_from_github!` then persists the status and recomputes derived state:

```ruby
def create_status_from_github!(github_status)
  add_status do
    statuses.replicate_from_github!(stack_id, github_status)
  end
end
``` [2](#0-1) 

`Status::Common#blocking?` and `Commit#blocked?`/`#deployable?` are driven purely by the stored status rows for that commit, gated on the victim stack's own `blocking_statuses` configuration:

```ruby
def blocking?
  !success? && commit.blocking_statuses.include?(context)
end
``` [3](#0-2) 

```ruby
def deployable?
  !locked? && (stack.ignore_ci? || (success? && !blocked?))
end

def blocked?
  return false if stack.blocking_statuses.empty?
  stack.commits.reachable.newer_than(stack.last_deployed_commit).older_than(self).any?(&:blocking?)
end
``` [4](#0-3) 

`add_status` also triggers `stack.schedule_merges` and `Hook.emit(:deployable_status, ...)` when the simple state changes [5](#0-4) , so a forced `failure`/`success` flip can gate or unblock continuous delivery/merges for the victim stack.

**Why existing guards don't catch this:** `WebhooksController#verify_signature` validates the HMAC signature against the GitHub App configured for `repository_owner` (`params.dig('repository','owner','login')`) [6](#0-5) . This proves the payload was genuinely signed by GitHub for *some* repository under that owner/installation — it does not prove, and `StatusHandler` never checks, that the `repository` in the payload is the same repository that owns the target `Commit`/`Stack`. GitHub Apps are commonly installed org-wide ("all repositories"), so any repository under that installation (including one the low-privileged attacker legitimately owns or has push/status access to) can produce a validly-signed webhook whose `sha` is chosen by the attacker (e.g., a SHA shared via fork ancestry, a shared submodule commit, or an imported/mirrored history) with the victim's stack. No `ExplicitParameters` schema field, `Repository` validator, or `subset`/`url` validator restricts `params.sha` to commits actually belonging to the authenticating repository — the schema only validates types (`requires :sha, String`, etc.) [7](#0-6) .

**Exploit flow:** Attacker controls a repository within any GitHub organization/installation for which Shipit has a configured GitHub App secret (or their own account, if it shares SHA history with the victim repo via fork). They send/produce a GitHub `status` event with `sha` equal to a commit SHA that also exists in the victim stack's `commits` table, `context: 'ci/integration'` (matching the victim stack's `blocking_statuses`), and `state: 'failure'`. `POST /webhooks` verifies the signature against the attacker's own (legitimate) repository owner, passes `drop_unhandled_event`, and dispatches to `StatusHandler`, which finds and updates the victim's `Commit` row purely by `sha`, flipping `blocking?` → `blocked?` → `deployable?` for the victim stack, without ever touching or authenticating against the victim's repository.

### Impact Explanation
An attacker who controls (or has push/status-emitting rights to) any repository sharing SHA history/coverage with a target stack can force a `Commit` belonging to a stack they do not own to become blocked (denial of deploy) or, by sending a subsequent `success` status for a status context the victim doesn't otherwise require, potentially clear a block and permit a deploy that shouldn't have been permitted. This is a cross-repository state write: "a payload for one repository mutating another's stack, commit, task" — matching the Critical impact category. Repeatable per request; any stack configuring `blocking_statuses` with a context also used elsewhere is exposed, so the blast radius grows with the number of stacks sharing status contexts and SHA-space with an attacker-reachable repo.

### Likelihood Explanation
Preconditions: (1) attacker must be able to produce a validly-signed webhook for *some* repository (their own repo, or one they have push/status access to, under an org whose GitHub App installation Shipit trusts) — this is the normal, unprivileged capability of any GitHub user who owns a repo; (2) the victim stack must have `blocking_statuses` configured for a `context` the attacker can trigger; (3) the target `sha` must exist in the victim stack's `commits` table, which is realistic for forks/mirrors/shared-history repos or any Shipit deployment tracking multiple stacks on the same underlying repository/branches. Attacker cost is a single unauthenticated-to-Shipit HTTP-equivalent GitHub status event; no Shipit credentials, session, or `github_teams` membership required. This is fully repeatable and does not require live GitHub access to reproduce in tests.

### Recommendation
In `StatusHandler#process` (and any sibling handlers, e.g. check-run handlers, with the same pattern), scope the `Commit` lookup by both `sha` and the owning stack's repository, e.g.:
```ruby
Commit.joins(:stack).where(sha: params.sha, shipit_stacks: { repository_id: repository_for(params) }).each { ... }
```
or otherwise verify `commit.stack.github_repo_name == params.dig('repository', 'full_name')` before calling `create_status_from_github!`, discarding non-matching commits.

### Proof of Concept
Minitest plan (no live GitHub):
1. Create two `Stack`s/`Repository` records: `victim_repo` (`owner/victim`) and `attacker_repo` (`owner/attacker`), both under the same organization (or simulate via directly invoking the handler, bypassing controller signature check since that's out of scope for the model-level assertion).
2. Create a `Commit` with `sha: SHARED_SHA` on `victim_repo`'s stack; configure victim stack's `deploy_spec`/`blocking_statuses` to include `ci/integration`.
3. Assert baseline: `commit.blocked?` is `false` and `commit.deployable?` is (whatever baseline, e.g. `true` given prior successful CI).
4. Build `params` for `StatusHandler` with `sha: SHARED_SHA`, `context: 'ci/integration'`, `state: 'failure'`, and a `repository` payload pointing to `attacker_repo` (not `victim_repo`).
5. Call `Shipit::Webhooks::Handlers::StatusHandler.new(params).process` (or `.call`).
6. Assert the equality that should have held before/after: `commit.stack.github_repo_name == params.dig('repository', 'full_name')` is `false`, yet `commit.reload.blocked?` changed from `false` to `true` (or `commit.deployable?` flipped from `true` to `false`) — demonstrating the victim stack's state was mutated by a payload that authenticated only for `attacker_repo`.
