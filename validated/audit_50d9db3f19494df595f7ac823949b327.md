### Title
`OpenedHandler#provision?` operator-precedence bug provisions review stacks on repositories with `review_stacks_enabled == false` - (File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb)

### Summary
`PullRequest::OpenedHandler#provision?` uses `&&`/`||` in a way where Ruby's operator precedence causes `repository.review_stacks_enabled` to gate only the `provisioning_behavior_allow_all?` branch, not the `provisioning_behavior_allow_with_label?` or `provisioning_behavior_prevent_with_label?` branches. As a result, an attacker who opens a pull request against a repository with `review_stacks_enabled: false` and `provisioning_behavior: prevent_with_label` (no label applied) can still trigger `provision?` to return `true`, causing a `ReviewStack` to be created and queued for provisioning off their fork's branch.

### Finding Description
The broken binding, stated as an equality that the code implicitly assumes but does not enforce: the intended invariant is `repository.review_stacks_enabled == true` for *every* provisioning decision, but the actual code only applies that check to the first disjunct.

```ruby
def provision?
  repository.review_stacks_enabled &&
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
``` [1](#0-0) 

In Ruby, `&&` binds tighter than `||`, so this parses as:
`(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?)`.

For the attacker's PR: `review_stacks_enabled = false`, `provisioning_behavior = prevent_with_label`, no label applied.
- Term 1: `false && false` = `false`
- Term 2: `allow_with_label?` is `false` (behavior isn't allow_with_label) = `false`
- Term 3: `prevent_with_label? (true) && !has_label? (true)` = `true`

Overall: `false || false || true` = `true`. `review_stacks_enabled` is never evaluated against term 3, so it does not gate the `prevent_with_label` path at all.

Call path: `respond_to_pull_request_opened?` (`params.action == "opened" && provision?`) returns true [2](#0-1)  → `process` calls `ReviewStackAdapter.new(params, scope: repository.review_stacks).find_or_create!` [3](#0-2)  → `create!` builds `stack_attributes` with `branch: params.pull_request.head.ref` (attacker-controlled) and calls `scope.create!` then `Shipit::ReviewStackProvisioningQueue.add(stack)` [4](#0-3) . Nothing in `Repository#review_stacks` association or `ReviewStack` model re-checks `review_stacks_enabled` before creation [5](#0-4) . `ReviewStackProvisioningQueue.work` later calls `stack.provisioner.provision?` and `stack.provision`, which transitions the state machine and calls `provisioner.up`, ultimately checking out the attacker's branch and running `shipit.yml` steps through `TaskCommands#perform` → `Command.new(command_line, ...)` [6](#0-5) , feeding into `PTY.spawn` execution.

No existing guard intercepts this: `respond_to_pull_request_opened?` only checks `params.action == "opened"`, and `provision?` is the sole authorization gate — which is exactly the buggy method. `review_stacks_enabled` is a plain boolean column with no other enforcement point between the webhook handler and stack creation/provisioning.

### Impact Explanation
An unprivileged GitHub user who can open a pull request against any repository configured with `provisioning_behavior: prevent_with_label` and a `provisioning_label_name` that they simply don't apply, causes a `ReviewStack` to be created and queued for provisioning even though that repository explicitly has `review_stacks_enabled: false` (i.e., never opted into review stacks). Provisioning checks out the attacker's branch and executes `shipit.yml`-defined steps as shell commands via `Command`/`PTY.spawn`, which is attacker-controlled code execution on the deploy host. This is repeatable against any repository in this misconfiguration state and matches the Critical "RCE on the deploy host via `Command`/`PTY.spawn`" category.

### Likelihood Explanation
Preconditions are narrow but plausible: a repository must have `review_stacks_enabled: false` while also having `provisioning_behavior` set to `prevent_with_label` (rather than left at a truly disabled/no-op state), which suggests an admin transitioning away from review stacks or misconfiguring settings without disabling the behavior field. No secrets, tokens, or privileged roles are required — only the ability to open a PR against the target repository (public repos, or any repo where the attacker has fork/PR rights) — the webhook delivery itself is normal GitHub behavior once the app is installed on the repo. This is low-cost and repeatable for any repository fitting the precondition.

### Recommendation
Fix operator precedence by parenthesizing the `review_stacks_enabled` check to gate the entire expression:
```ruby
def provision?
  repository.review_stacks_enabled &&
    (repository.provisioning_behavior_allow_all? ||
     (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
     (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?))
end
```
Apply the same fix to the structurally identical `ReopenedHandler#unarchive?` [7](#0-6) , which has the same precedence bug.

Mock `Shipit::ReviewStackProvisioningQueue.add` and `TaskCommands#perform`/`Command#start` to capture that a `Command` is constructed with a `chdir` pointing at the checked-out attacker branch, demonstrating the execution-trust violation (repository never enabled review stacks yet a command executes against attacker-supplied branch content).
