### Title
Webhook signature check can be bypassed by spoofing `repository.owner.login`/`organization.login` to select an unconfigured/secret-less GitHub App, letting an attacker forge events (including team membership) for a **different**, secured organization/repository - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` picks *which* GitHub App configuration (and therefore which `webhook_secret`) is used to validate the inbound webhook HMAC purely from attacker-controlled JSON fields in the request body, while the event handlers that actually act on the payload resolve the target repository/stack independently from a different field of the same untrusted body. These two lookups are never cross-checked, breaking the binding "organization that authenticated versus the repository that is written."

### Finding Description
`WebhooksController` verifies the signature like this: [1](#0-0) [2](#0-1) 

`repository_owner` is read straight out of the unauthenticated request body (`params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`) before any signature has been verified, and is used to select a `GitHubApp` instance via `Shipit.github(organization: repository_owner)`.

`GitHubApp#verify_webhook_signature` then does: [3](#0-2) 

Critically, `return true unless webhook_secret` — if the selected organization's app config has **no `webhook_secret` configured** (which the setup docs explicitly show as optional/`nil`, e.g. `webhook_secret: # nil`), signature verification is skipped entirely, independent of the actual `X-Hub-Signature` header. [4](#0-3) [5](#0-4) 

Once the request passes `verify_signature`, the raw payload is dispatched to handlers untouched: [6](#0-5) 

Handlers determine which `Repository`/`Stack` to act on from a **different** field of the same attacker-controlled body — `repository.full_name` — with no relationship enforced to the `repository.owner.login`/`organization.login` value that was used to pick the (possibly secret-less) app: [7](#0-6) 

So an attacker can set `repository.owner.login` to any organization name that happens to have no `webhook_secret` configured in Shipit's multi-app config, while setting `repository.full_name` to a completely different, securely-configured organization's tracked repository. The signature check will pass unconditionally for the first (secret-less) org, but the event will be processed against the second org's stack.

### Impact Explanation
This directly breaks a deployment-trust binding: the "GitHub organization that authenticated" the request (via its app config, used only to choose the HMAC secret) is decoupled from "the repository that is actually written to" by the handler. Depending on event type, this enables:
- Forged `push`/`status`/`check_suite` events against a fully secured org's stacks, triggering `GithubSyncJob`/status writes, which can be leveraged to mark commits healthy and drive continuous/auto-deployment on stacks the attacker was never authorized to touch — an unauthorized deploy.
- Forged `membership` events writing `Team`/`Membership` records via `MembershipHandler`, escalating into `Shipit.github_teams` authorization, since Shipit derives GitHub-team-based authorization from these very membership records.

Both outcomes map to explicitly in-scope Critical/High impacts (unauthorized deploy; escalation into `Shipit.github_teams` authorization).

### Likelihood Explanation
Exploitability requires only that at least one organization configured in Shipit's (documented, supported) multi-GitHub-App setup lacks a `webhook_secret` — an explicitly supported/optional configuration state per the setup docs and example secrets file, not a hypothetical misconfiguration outside the engine's own code. No GitHub session, API token, or repository write access is needed; the attacker only needs network access to the public `/webhooks` endpoint.

### Recommendation
- Require `webhook_secret` to be present for every configured GitHub App/organization, or fail closed (reject) instead of `return true unless webhook_secret`.
- After signature verification, re-derive the acting organization strictly from the verified app's own configuration/installation identity rather than trusting `repository.owner.login`/`organization.login` from the body, and assert it matches the org prefix of `repository.full_name` before dispatching to handlers.

### Proof of Concept
1. Configure Shipit with the documented multi-org GitHub App setup (`docs/setup.md`, "Using Multiple Github Applications"), where org `looseorg` is configured with `webhook_secret: nil` and org `secureorg` owns a tracked Stack with a real secret.
2. POST to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "repository": {"owner": {"login": "looseorg"}, "full_name": "secureorg/target-repo"},
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>"
}
```
No valid `X-Hub-Signature` is required.
3. `verify_signature` selects `Shipit.github(organization: "looseorg")`, whose `webhook_secret` is nil, so `verify_webhook_signature` returns `true` unconditionally.
4. `PushHandler` resolves `stacks` from `full_name = "secureorg/target-repo"` and enqueues `sync_github(expected_head_sha: "<attacker-chosen-sha>")` on `secureorg`'s stack, despite the attacker never possessing `secureorg`'s webhook secret.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
