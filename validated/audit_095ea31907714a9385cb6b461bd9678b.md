### Title
Use-after-free-style corruption of shared unit caches via unauthenticated AA dry-run trigger racing real unit validation - (File: aa_composer.js)

### Summary
`dryRunPrimaryAATrigger` in `aa_composer.js` executes a real AA-trigger simulation against the node's live, process-global in-memory unit caches (`storage.assocUnstableUnits`, `assocBestChildren`, `assocStableUnits`, `assocCachedUnits`, `assocUnstableMessages`) and then "frees" the objects it created there via `revertResponsesInCaches()` → `storage.forgetUnit()`, all **without ever taking the write mutex** that protects those same caches during real unit validation/writing. Any unprivileged peer can trigger this path remotely (`light/dry_run_aa`), and it is also triggered automatically for every ordinary posted unit that pays an AA address when `conf.bDryRunNewTriggers` is enabled. This creates a Chrome-CVE-2024-4671-style "use of an object after its backing memory/cache slot was released by a concurrent operation" condition: real validation logic elsewhere in the process (`validateParents`, `validateWitnesses`, `fixIsFreeAfterForgettingUnit`, etc.) reads and mutates the same global associative caches concurrently, so a dry run's cache inserts/deletes can interleave with, and corrupt, the state a concurrent real-unit validation is relying on.

### Finding Description
`dryRunPrimaryAATrigger` (`aa_composer.js:272-306`) is called with `bDryRun: true` and internally calls `handleTrigger()`, which builds full response units and inserts them into the *same* global caches used for real, permanent units (see `revertResponsesInCaches`, which manipulates `storage.assocUnstableUnits`, `storage.forgetUnit`, `storage.fixIsFreeAfterForgettingUnit`): [1](#0-0) [2](#0-1) 

`storage.forgetUnit()` directly mutates the shared global associative maps that are also read/written by ordinary unit validation and by `main_chain`/graph logic (`assocKnownUnits`, `assocCachedUnits`, `assocCachedUnitAuthors`, `assocCachedUnitWitnesses`, `assocUnstableUnits`, `assocStableUnits`, `assocUnstableMessages`, `assocBestChildren`): [3](#0-2) [4](#0-3) 

Unlike real unit validation, which serializes access with `mutex.lock(arrAuthorAddresses, ...)` around all cache reads/writes for a unit (`validation.js:357`) and unlike `shrinkCache()`, which explicitly takes the global `"write"` mutex before mutating these same maps (`storage.js:2261`), `dryRunPrimaryAATrigger`/`handleTrigger` in dry-run mode take **no such lock** around their cache mutations: [5](#0-4) [6](#0-5) 

This function is reachable by any unauthenticated peer via the light-vendor request `light/dry_run_aa`, which only requires a syntactically valid address and passes attacker-controlled `params.trigger` straight into `dryRunPrimaryAATrigger`: [7](#0-6) 

It is also invoked automatically, without any special privilege, whenever `conf.bDryRunNewTriggers` is enabled and *any* ordinary unit posted by *any* unprivileged unit poster pays to a known AA address — i.e. it is on the hot path of ordinary unit acceptance (`network.js:1271-1281`), running concurrently with the very `writer.saveJoint`/cache-mutation logic it races against: [8](#0-7) 

Because `dryRunPrimaryAATrigger` inserts, then deletes ("frees"), entries keyed by freshly-generated response-unit hashes/addresses in the exact same global objects that real validation code paths (`validateParents`, `validateWitnesses`, `fixIsFreeAfterForgettingUnit`, `readUnitProps`, etc.) iterate and dereference without re-checking existence at every step, an interleaved dry run can:
- delete an `assocUnstableUnits[unit]` entry that a concurrently-running real validation has already captured a reference to (e.g. `objParentUnitProps` in `validateParents`, `validation.js:692`) and is about to dereference again later in the same async chain, or
- mutate `assocBestChildren[parent_unit]` (via `_.pull`) while a concurrent chain-selection/graph routine is iterating the same array, or
- leave a `assocUnstableUnits[parent_unit].is_free` flag stale/incorrect for a real unit if `fixIsFreeAfterForgettingUnit` runs interleaved with real stabilization logic that also mutates `is_free`.

This is the direct structural analog of the Chromium UAF: an object (in this case, a cache slot representing an in-flight unit) is released ("freed") by one code path while another concurrent code path retains and continues to operate on a stale reference to it, because no synchronization primitive protects the shared object's lifetime across the async boundary.

### Impact Explanation
Corruption of `assocUnstableUnits` / `assocBestChildren` / `is_free` flags is used throughout main-chain determination, witnessed-level calculation, and parent-unit validation to decide whether a unit is serial/good, stable, or a double-spend. If a concurrent dry run's insert/forget cycle corrupts these structures for a genuinely-being-validated unit (e.g., pulling the wrong entry from `assocBestChildren`, or deleting `assocUnstableUnits[unit]` out from under an in-flight `validateParents`/`determineWitnessedLevelAndBestParent` call), the affected node can reach an incorrect validity/stability/double-spend determination that diverges from other nodes that did not experience the race — i.e., node disagreement on validity/stability, and in the worst case acceptance of a conflicting/double-spending unit as "good" locally. Because `dryRunPrimaryAATrigger` is reachable by any unprivileged unit poster (via ordinary AA-paying units when `bDryRunNewTriggers` is on) or any light-vendor peer (`light/dry_run_aa`), this satisfies the "unprivileged unit poster / AA trigger sender" reachability bar and the required Medium/High/Critical impact (node disagreement on validity/stability).

### Likelihood Explanation
Exploitation requires winning a race between two async I/O-bound chains of callbacks (a dry run and a concurrent real-unit validation) inside the same Node.js event loop — this is plausible because both paths do multiple DB round trips (`conn.query`) and the event loop will freely interleave their callbacks. An attacker can amplify the race window by sending many `light/dry_run_aa` requests (unauthenticated) concurrently with posting units that touch the same AA/graph region, increasing the probability of hitting the vulnerable interleaving. However, this is a timing-dependent race, not a deterministic single-request exploit, and I was not able to fully trace every downstream validation function that reads `assocBestChildren`/`assocUnstableUnits` to confirm a fully deterministic exploit chain to a concrete double-spend within the scope of this analysis — this should be verified with concurrency/stress testing.

### Recommendation
- Have `dryRunPrimaryAATrigger` / `handleTrigger(bDryRun=true)` operate on a fully isolated, cloned view of the caches it needs (unstable units, best children, unstable messages), never touching the live `storage.assoc*` singletons that are shared with real validation, or
- Wrap the entire dry-run cache-mutation sequence (`handleTrigger` insertion of temporary response units through `revertResponsesInCaches`) in the same `"write"` mutex used by `shrinkCache()`, serializing it against real validation/writing, and
- Audit `storage.forgetUnit`/`fixIsFreeAfterForgettingUnit` callers to ensure no caller retains stale references to forgotten cache entries across an await/callback boundary.

### Proof of Concept
1. Deploy an AA at address `A` with a normal message set that produces a response unit.
2. Concurrently:
   - Repeatedly send `light/dry_run_aa` requests (or, on a full node with `conf.bDryRunNewTriggers=true`, repeatedly post ordinary units paying `A`) to trigger `dryRunPrimaryAATrigger` in a tight loop.
   - Simultaneously post/validate real units whose parents are being iterated by `validateParents`/`determineWitnessedLevelAndBestParent`, touching the same parent-unit entries in `assocUnstableUnits`/`assocBestChildren` that the dry run's `handleTrigger`/`revertResponsesInCaches` insert-then-forget cycle also touches.
3. Observe (via added instrumentation/logging around `assocBestChildren`/`assocUnstableUnits` mutations, or via divergent validation outcomes across repeated runs) that the interleaving of insert/forget from the dry run corrupts state consumed by the concurrent real validation, producing an incorrect serial/stability/double-spend determination.

Note: I was unable to execute this PoC in this environment (no filesystem/terminal access) and could not fully confirm a deterministic, single-shot exploit path to double-spend; the above demonstrates the missing-synchronization root cause and a plausible triggering sequence, and should be validated with actual concurrent execution/stress testing.

function fixIsFreeAfterForgettingUnit(parent_units) {
	parent_units.forEach(function(parent_unit){
		if (!assocUnstableUnits[parent_unit]) // the parent is already stable
			return;
		var bHasChildren = false;
		for (var unit in assocUnstableUnits){
			var o = assocUnstableUnits[unit];
			if (o.parent_units.indexOf(parent_unit) >= 0)
				bHasChildren = true;
		}
		if (!bHasChildren)
			assocUnstableUnits[parent_unit].is_free = 1;
	});
}
