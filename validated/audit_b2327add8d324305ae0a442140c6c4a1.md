### Title
Cross-organization/cross-repository CI status forgery via unscoped `Commit.where(sha:)` lookup in `StatusHandler` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`WebhooksController#verify_signature` authenticates an incoming GitHub webhook against the `GitHubApp` for a single organization derived from the payload's `repository.owner.login` [1](#0-0) [2](#0-1) . Every other handler that acts on payload data scopes its writes to the repository named in `payload.dig('repository', 'full_name')` via the shared `stacks`/`repository_name` helpers [3](#0-2) . `StatusHandler`, however, breaks this binding: it looks up commits by SHA across the **entire** `Commit` table with no repository or organization scoping at all [4](#0-3) , then writes a GitHub-supplied status directly onto whatever stack that commit belongs to [5](#0-4) [6](#0-5) .

### Finding Description
The binding that should hold is: *the organization whose `webhook_secret` authenticated the request* == *the repository/stack whose data is written*. `verify_signature` picks the `GitHubApp` (and thus the HMAC secret) using `repository_owner`, itself read straight out of the same unverified JSON body being signed [7](#0-6) . Once the signature check passes, `StatusHandler#process` never re-derives or checks the repository at all — it queries `Commit.where(sha: params.sha)` globally, across every stack and every repository configured on the instance, and calls `create_status_from_github!` on each match [4](#0-3) .

Contrast this with the base `Handler` class, which every other handler (`push`, `pull_request/*`, `check_suite`, `label_capturing`, etc.) uses to constrain itself to `Repository.from_github_repo_name(repository_name)&.stacks` [3](#0-2) . `StatusHandler` inherits from `Handler` but ignores `stacks`/`repository_name` entirely, so the org/repo binding that `verify_signature` is meant to enforce is never re-checked at the point the actual database write happens.

`create_status_from_github!` calls `statuses.replicate_from_github!(stack_id, github_status)` using the matched `Commit`'s own `stack_id` [5](#0-4) , i.e. whichever stack that SHA happens to belong to — not the stack implied by the authenticating organization. `Status.replicate_from_github!` persists the attacker-chosen `state`/`description`/`context` verbatim [8](#0-7) , and creation of a `Status` record triggers `enable_ci_on_stack` and `schedule_continuous_delivery` [9](#0-8) .

### Impact Explanation
Because `Commit#deployable?` is `success? && !blocked?` [10](#0-9) , and `#state`/`#success?` are simply delegated to the most recent `Status` [11](#0-10) , an attacker who administers any single organization/GitHub App configured on a shared, multi-organization Shipit instance (a supported configuration, per the "Using Multiple Github Applications" setup) can:
1. Sign an arbitrary webhook body with the `webhook_secret` of the org they legitimately administer, satisfying `verify_signature`.
2. Set `repository.owner.login` to their own org (so the secret lookup matches) while setting the top-level `status` payload's `sha` to the SHA of a commit that exists in a **different** organization's/repository's stack tracked by the same Shipit instance.
3. Because `StatusHandler` never checks which repository that SHA actually belongs to, the forged `state: "success"` status is written onto the victim stack's commit, flipping `deployable?` to true and triggering `schedule_continuous_delivery` — enabling an unauthorized deploy of that commit, or bypassing required/blocking CI checks that gate deploys for a repository/organization the attacker has no legitimate access to [12](#0-11) .

This is a direct analog of the report's bug class: a non-unique, attacker-influenced value (`sha`, decoupled from any authenticated org/repo binding) is trusted to select which protected resource is acted upon, exactly as the original report's `symbol` string was trusted to select which price/authorization path applied. Here the consequence is a genuine unauthorized-deploy / cross-repository-write, satisfying the Critical impact bar.

### Likelihood Explanation
Exploitability requires only that the attacker legitimately possesses a `webhook_secret` for *some* organization/GitHub App configured on the shared Shipit instance — not the victim's. This is realistic in the documented multi-tenant deployment model where each organization independently configures and owns its own GitHub App credentials in `config/secrets.yml`, and is precisely the kind of "unprivileged relative to the victim" attacker the rules target. The only additional requirement is knowledge of a target commit SHA in the victim repository, which is trivial for public repositories and is the normal case for CI status events (SHAs are routinely visible via GitHub UI/API to anyone with any read access, and are content-addressed so can be independently reconstructed). No repository write access, stolen credentials, or privileged Shipit account is needed.

### Recommendation
In `StatusHandler#process`, scope the `Commit` lookup to the authenticated repository, mirroring every other handler's use of `stacks`/`repository_name`, e.g. `stacks.flat_map(&:commits).select { |c| c.sha == params.sha }` or a joined query restricted to `stacks` derived from `Repository.from_github_repo_name(repository_name)`. This restores the binding between the organization that authenticated the webhook and the repository whose commit/status data is mutated.

### Proof of Concept
1. Configure Shipit with two organizations, `org-attacker` and `org-victim`, each with its own GitHub App / `webhook_secret` (per `docs/setup.md`'s multi-org setup). Attacker administers `org-attacker` and legitimately knows its `webhook_secret`.
2. Attacker identifies a commit SHA `S` that exists in a `Stack` under `org-victim/some-repo` (trivial if the repo is public, or already known to the attacker for any other reason).
3. Attacker crafts a `status` event payload:
```json
{
  "sha": "S",
  "state": "success",
  "context": "ci/attacker-forced",
  "repository": { "owner": { "login": "org-attacker" }, "full_name": "org-attacker/anything" }
}
```
4. Attacker computes `X-Hub-Signature` using `org-attacker`'s `webhook_secret` over this exact body and POSTs it to `/github/webhooks`.
5. `WebhooksController#verify_signature` resolves `repository_owner` = `"org-attacker"`, fetches that org's `GitHubApp`, and the signature check succeeds [1](#0-0) .
6. `StatusHandler#process` runs `Commit.where(sha: "S")`, matching the victim's commit regardless of organization, and calls `create_status_from_github!`, writing a `success` status onto the `org-victim` stack's commit [4](#0-3) .
7. The victim commit's `deployable?` becomes true and continuous delivery is scheduled for a repository the attacker never had access to [9](#0-8) [10](#0-9) .
