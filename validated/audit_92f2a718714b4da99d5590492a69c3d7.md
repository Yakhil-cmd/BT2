### Title
Griefing attack on AA market-maker/AMM templates via balance-based exact-match checks - (File: `test/samples/uniswap_like_market_maker.oscript`, `formula/evaluation.js`)

### Summary
The `TempusController.exitTempusAMM` bug class — an attacker front-running an exact-equality/assert check by donating dust so a legitimate transaction is rejected — has a direct analog in Obyte AAs that use the `balance[asset]` primitive for exact ratio/ownership calculations. The shipped reference "Uniswap-like market maker" AA template computes pool ratios from `balance[asset]` and `balance[base]`, which include *all* confirmed funds sent to the AA address by anyone, not just the current trigger's payer. An attacker can send a dust payment of the pool asset (or bytes) directly to the AA address to shift these balances just before a legitimate investor's deposit trigger is processed, causing the AA's exact-ratio check to fail and `bounce()`.

### Finding Description
`balance[asset]` in oscript is evaluated by `readBalance` in `formula/evaluation.js`, which returns the AA's persisted balance for that asset from `objValidationState.assocBalances` / the `aa_balances` table — the sum of all outputs ever sent to that address, regardless of sender. [1](#0-0) 

This state is populated for every stable unit paid to the AA address (`updateFinalAABalances`), and any user (unprivileged unit poster) can pay bytes or any asset to an AA address as a plain payment — this is not restricted to trigger senders. [2](#0-1) 

The reference market-maker AA relies on the raw `balance[$asset]`/`balance[base]` (minus the current trigger's own contribution) to derive the current pool ratio, and then enforces an *exact* match against the amount the investor sent: [3](#0-2) 

Because `$asset_balance` and `$bytes_balance` are derived from the AA's total balance (which anyone can alter by sending a stray payment directly to the AA address), an attacker can pre-empt a legitimate investor's carefully-computed "invest in MM" trigger by sending a tiny amount of the pool asset or bytes to the AA address first. This changes `$current_ratio` between the time the investor computed their expected deposit amount off-chain and the time their trigger unit is actually processed, causing:

```
if ($expected_asset_amount != trigger.output[[asset=$asset]])
    bounce('wrong ratio of amounts, expected ' || $expected_asset_amount || ' of asset');
```

to fail and bounce the investor's unit — exactly mirroring the `assert(tempusAMM.balanceOf(address(this)) == 0)` griefing pattern, where an attacker manipulates the "final expected exact state" that a benign transaction depends on.

### Impact Explanation
Every time a legitimate investor tries to deposit into the market-maker AA, an attacker (who only needs to observe the mempool/DAG for pending "invest" triggers) can front-run with a single dust payment to the AA's address, guaranteeing the deposit trigger bounces. The investor loses the AA's `bounce_fees` (paid unconditionally on bounce) each time, and the "invest in MM" feature of the AA becomes effectively unusable — a repeatable, low-cost denial-of-service against fund deposits, and direct fund loss (bounce fees) for the victim.

### Likelihood Explanation
High. Sending a payment to a known AA address is a normal, always-available action for any unit poster; no special privileges or race-condition luck beyond ordinary unit-inclusion timing are needed, and the attack can be repeated indefinitely at negligible cost (a few bytes).

### Recommendation
AA templates that need deterministic, trigger-scoped balances (e.g., AMM/market-maker ratio checks) should not use unconstrained `balance[asset]` reads for correctness-critical exact-match logic. Instead, they should track pool reserves via explicit state variables (`var['pool_asset_reserve']`, `var['pool_bytes_reserve']`) that are updated only by the AA's own trades/deposits, so unrelated donations cannot influence the computed ratio. Where `balance[...]` must be used, avoid hard `!=` bounce conditions on attacker-influenceable derived values; use tolerant thresholds or track "confirmed-by-this-AA" reserves separately from the address's raw ledger balance.

### Proof of Concept
1. Investor computes `$expected_asset_amount` off-chain based on current pool ratio and posts an "invest in MM" trigger sending exactly that amount of pool asset plus bytes.
2. Attacker observes the unstable/pending investor unit and posts a plain payment of a small amount of the pool asset (or bytes) directly to the AA address, timed to become stable/counted before the investor's trigger is processed.
3. When the investor's trigger is handled, `$asset_balance = balance[$asset] - trigger.output[[asset=$asset]]` and `$bytes_balance = balance[base] - trigger.output[[asset=base]]` now reflect the attacker's donation, shifting `$current_ratio` and thus `$expected_asset_amount`.
4. `$expected_asset_amount != trigger.output[[asset=$asset]]` evaluates true, and the AA calls `bounce('wrong ratio of amounts...')`, forfeiting the investor's bounce fee and failing the deposit. [3](#0-2) [1](#0-0)
