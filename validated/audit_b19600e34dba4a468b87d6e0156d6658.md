### Title
Unbounded/underestimated weight for `remote_proxy` trie-proof verification allows a cheap PoV/weight amplification DoS - (File: pallets/remote-proxy/src/lib.rs)

### Summary
`Pallet::remote_proxy` / `do_remote_proxy` charges a fixed, benchmarked weight (`WeightInfoOf::<T, I>::remote_proxy()`) for verifying an attacker-supplied `RemoteProxyProof::RelayChain { proof: Vec<Vec<u8>>, block }`, but the benchmark only exercises a minimal, realistic proof produced by `T::RemoteProxy::create_remote_proxy_proof`, never scaling the charged weight with `proof.len()`/total node bytes. A signed, unprivileged caller can submit a structurally valid but much larger `StorageProof` (still bounded only by the chain's generic extrinsic-length/PoV limits) whose `sp_trie::StorageProof::into_memory_db` + `sp_trie::read_trie_value` processing cost is far above the ~18µs fixed weight charged for it.

### Finding Description
`remote_proxy` (call_index 0) is dispatchable by any `ensure_signed` origin and forwards to `Pallet::do_remote_proxy`: [1](#0-0) 

Its weight annotation charges a fixed `WeightInfoOf::<T, I>::remote_proxy()` plus the inner call's own weight, but nothing derived from `proof.len()` or the byte size of the trie nodes inside `proof`: [2](#0-1) 

Inside `do_remote_proxy`, the attacker-controlled `proof: Vec<Vec<u8>>` is turned into a `MemoryDB` and then walked with `sp_trie::read_trie_value`: [3](#0-2) 

There is no field-level bound (`BoundedVec`, `MaxEncodedLen`, or explicit length check) on `proof` or on the size/number of its inner `Vec<u8>` nodes in the pallet's storage/call definition: [4](#0-3) 

The benchmark that produces the shipped weight constants only ever supplies the trivial proof from `create_remote_proxy_proof`, i.e. it is **not parameterized on proof size** (no `x`/`b`-component linear in `proof.len()`): [5](#0-4) 

The generated weight for Asset Hub Kusama reflects this: a flat ~18.26µs / 1846-byte PoV estimate regardless of how large the caller's actual `proof` argument is: [6](#0-5) 

Because `BlockToRoot` retains up to `MaxStorageRootsToKeep` historical relay-chain storage roots, any signed account can pick any retained `block`/`storage_root` pair and craft an oversized but well-formed `StorageProof` (long/duplicated trie nodes, deep paths, or garbage-but-decodable nodes) against that root; `into_memory_db` and the underlying node hashing/decoding cost scales with total proof bytes even though the final lookup fails or succeeds trivially. Since the extrinsic weight is fixed independent of `proof` size, the statically charged weight does not bound the actual CPU/verification time spent, breaking the "charged weight bounds actual weight" invariant. `Error::InvalidProof`/`DidNotFindMatchingProxyDefinition` failures still occur only *after* the expensive `into_memory_db`/`read_trie_value` work is done, so failure does not save the cost — and DispatchResult errors from a correctly-weighted-but-underpriced call don't refund based on actual heavier work, they just don't correct the mis-estimation.

### Impact Explanation
An attacker can repeatedly submit `remote_proxy` calls with maximal well-formed-but-bloated `StorageProof`s (as large as the runtime's normal extrinsic length / parachain PoV limit allows) while only paying for and being charged the fixed, tiny benchmarked weight. Because block builders and the weight-metering system assume charged weight approximates execution time, a block filled with such extrinsics can push actual wasm-execution/import time well past the intended budget, causing slower block production/import and worse-case validation-function (PVF) timeouts on parachains that include this pallet — a weight/PoV accounting bug rather than fund theft.

### Likelihood Explanation
Feasibility is moderate: the attacker needs only (a) a signed account able to pay normal transaction fees, and (b) knowledge of one storage root currently retained in `BlockToRoot` (a public, non-secret value derived from relay-chain state) plus the ability to construct a valid-shaped (not necessarily matching) `StorageProof` blob of the maximum permitted extrinsic size. No proxy relationship or privileged origin is required — the call is reachable directly by any signed user via `remote_proxy`. This is repeatable every block since `BlockToRoot` is refreshed each relay-parent and the attack requires no state accumulation.

### Recommendation
Add a proof-size-aware weight component to `remote_proxy`/`remote_proxy_with_registered_proof` (e.g. `Weight::from_parts(per_byte_cost, 0).saturating_mul(proof_total_len)` added on top of `WeightInfoOf::<T,I>::remote_proxy()`), enforce an explicit maximum on `proof.len()`/total encoded byte size (reject with a new error before calling `into_memory_db`), and update the benchmarks in `pallets/remote-proxy/src/benchmarking.rs` to include a size-parameterized worst-case proof so `WeightInfo::remote_proxy()` reflects true node-count/byte-size scaling.

### Proof of Concept
Rust benchmark/fuzz-style integration test in `pallets/remote-proxy/src/tests.rs`:
```rust
#[test]
fn oversized_proof_cost_exceeds_charged_weight() {
    let mut ext = new_test_ext();
    // 1. Set up a real BlockToRoot entry with a known storage_root (as in remote_proxy_works).
    // 2. Craft a StorageProof whose Vec<Vec<u8>> nodes are large (e.g. N x 32KB decodable-but-irrelevant
    //    trie node blobs) up to the maximum allowed extrinsic length, all anchored to the retained root.
    // 3. Measure wall-clock time (std::time::Instant) around Pallet::do_remote_proxy(...) call.
    // 4. Compare against WeightInfoOf::<Test, ()>::remote_proxy() converted to a time bound
    //    (via Weight::ref_time() and a known picoseconds-per-unit ratio).
    // Assert: measured_time_ns > charged_weight_time_bound_ns * some_safety_factor,
    // demonstrating the static weight does not bound actual execution time.
}
```
Expected assertion: actual measured execution time (and/or proof_size PoV consumed) for a maximal-size `proof` grows with `proof.len()`/total node bytes while `WeightInfoOf::<T,I>::remote_proxy()` stays constant, showing the mismatch grows unbounded with attacker-chosen input size up to the extrinsic length ceiling.
