### Title
Webhook signature verification is bound to an attacker-chosen `repository.owner.login`/`organization.login` while every event handler acts on the independent `repository.full_name` field, letting a forged event for one configured GitHub organization mutate stacks belonging to a different organization - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects which `GitHubApp` (and therefore which `webhook_secret`) to use for HMAC verification based on `repository_owner`, a value read straight out of the unauthenticated JSON body (`params.dig('repository','owner','login')` or the `organization.login` fallback). Every `Shipit::Webhooks::Handlers::Handler` subclass, however, resolves the repository/stack to act on using a *different* field from the same body: `payload.dig('repository','full_name')`. Nothing ties these two fields together, so the "organization that authenticated" and the "repository that is written" are never asserted to be the same tenant. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
Shipit supports a multi-organization GitHub App configuration where each organization has its own `webhook_secret` (and can have none at all - `webhook_secret: # nil` is a documented valid value): [4](#0-3) [5](#0-4) 

`GitHubApp#verify_webhook_signature` returns `true` unconditionally when the selected organization has no `webhook_secret` configured:
```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
``` [5](#0-4) 

The organization used to pick the `GitHubApp`/secret is derived from the JSON body's `repository.owner.login` (or `organization.login`), not from any TLS/App-level identity:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(...)
  ...
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [6](#0-5) 

Once `verify_signature` passes (either because the correct secret was computed by an attacker who can produce a valid signature for *any* configured org, or because that org has no secret at all), the controller hands the *entire raw JSON body* to every registered handler for the event type:
```ruby
def create
  params = JSON.parse(request.raw_post)
  Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }
  head(:ok)
end
``` [7](#0-6) 

Every handler then independently determines which `Repository`/`Stack` to mutate using `repository.full_name`, a field that is never checked against `repository_owner` (the field that was actually used for signature selection):
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [3](#0-2) 

This is used, unmodified, by `PushHandler` (queues `sync_github`), `PullRequest::ClosedHandler` (archives review stacks), and other handlers, all of which resolve the target `Repository` from `full_name` alone: [8](#0-7) [9](#0-8) 

Because the webhook JSON body is fully attacker-controlled apart from the HMAC covering the whole payload, an attacker who can produce a valid signature/secret for **any one** organization configured in Shipit (including one deliberately left with `webhook_secret: nil` for convenience, or one whose secret has leaked/rotated separately) can set `repository.owner.login` to that organization while setting `repository.full_name` to an entirely different, unrelated, and better-protected organization/repository that is also tracked by the same Shipit instance. The signature check "authenticates" organization A, but the handler code "writes" to organization B's stack - exactly the class of bug described in the report: a value that participates in downstream logic (`full_name`) is never covered by the check that gates the whole operation (`repository_owner`-selected signature).

### Impact Explanation
This breaks the binding: `organization authenticated by HMAC == organization owning the repository being written`. Concretely, an unprivileged external attacker who only needs to know/guess one organization's (mis)configured or weak webhook secret can:
- Force `GithubSyncJob` to run against an arbitrary tracked stack of a different, unrelated organization via a forged `push` event (`PushHandler`), influencing which commit is treated as HEAD for that stack's sync/merge-queue/CI logic.
- Archive review stacks or drive pull-request lifecycle handlers (`opened`, `closed`, `labeled`, etc.) for a repository that has nothing to do with the organization whose secret was actually used to authenticate the request.

This constitutes a cross-repository write across organizational trust boundaries not authorized by GitHub for the forging party, which matches the Critical criterion "cross-repository writes / an unauthorized deploy, rollback or merge" in the engine's own webhook-processing code (not requiring a GitHub App private key, `ApiClient` token, or repository write access - only knowledge/derivation of one configured org's webhook secret, or exploitation of an org intentionally left with no secret, which the app itself supports as valid configuration).

### Likelihood Explanation
Likelihood depends on operational configuration: exploitability requires either (a) at least one organization in the multi-org Shipit config having `webhook_secret` unset (a state explicitly documented and supported by the app), or (b) the attacker obtaining/guessing a valid secret for any single configured organization. Given multi-tenant Shipit deployments commonly onboard many orgs over time, and the example config explicitly shows `webhook_secret: # nil` as an acceptable value, this is a realistic misconfiguration rather than a purely theoretical one, and the code contains no additional server-side check to prevent it even when all orgs are properly secured for the *legitimate* case, since GitHub itself always keeps `owner.login` and `full_name`'s prefix consistent - the divergence can only be introduced by a forged/replayed request, which is exactly what the missing binding fails to reject.

### Recommendation
After successfully verifying the webhook signature for `repository_owner`, add an explicit invariant check that `repository.full_name`'s owner segment equals the `repository_owner` (or `organization.login`) that was used to select the signing secret, and reject (422) the request if they diverge, before dispatching to any handler in `Shipit::WebhooksController#create`. Additionally, treat organizations configured with an empty `webhook_secret` as unable to authenticate cross-organization-sensitive events, or require a non-empty `webhook_secret` for every organization at boot time in multi-org mode.

### Proof of Concept
Given a Shipit instance configured with two organizations:
```yaml
github:
  low-security-org:
    app_id: ...
    installation_id: ...
    webhook_secret:            # left blank/nil
  victim-org:
    app_id: ...
    installation_id: ...
    webhook_secret: "s3cr3t"
```
An attacker (no credentials, no GitHub App key) sends:
```
POST /github_authentication/webhooks
X-Github-Event: push
X-Hub-Signature: sha1=anything   # ignored, secret is nil for this org

{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "low-security-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
`repository_owner` resolves to `low-security-org`, whose `webhook_secret` is nil, so `verify_webhook_signature` returns `true` unconditionally [5](#0-4) . The request then reaches `PushHandler`, which resolves the target stack via `repository.full_name` = `victim-org/victim-repo` [10](#0-9)  and enqueues `GithubSyncJob` for that stack with the attacker-chosen `expected_head_sha`, even though `victim-org`'s own webhook secret was never presented or checked.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
