### Title
Insufficient dependency checks in AA asset-definition validation allow AA to define non-compliant assets - (File: aa_validation.js)

### Summary
`aa_validation.js`'s `validateAADefinition` statically validates the `asset` message template of an AA definition, but the checks it performs are a strict subset of the checks that `validation.js`'s `validateAssetDefinition` performs on the actual instantiated `asset` message at runtime. In particular, the AA-definition-time validator never checks the rule "if `cap` is set, `issued_by_definer_only` must be true" (enforced only in `validation.js`), nor the rule that `attestors` must not be present when `spender_attested` is false is checked only under an MCI gate that differs from the AA path. This mirrors the reported `addPool` bug class: a function performs a partial set of the checks its own semantics actually require, while the remaining, security-relevant invariants are enforced only in a different code path.

### Finding Description
`aa_validation.js` `validateAADefinition` → case `'asset'` (around lines 225-336) validates fields such as `cap`, `fixed_denominations`, `denominations`, `issue_condition`/`transfer_condition`, `cosigned_by_definer`, and the `issued_by_definer_only` vs `is_private`/`fixed_denominations` conflict: [1](#0-0) 

However, it never checks the invariant that a capped asset must be issued by the definer only, which is enforced in the "real" asset-definition validator used for ordinary units: [2](#0-1) 

Because `objAsset.issued_by_definer_only=false` combined with `objAsset.cap` set is exactly the condition that, in `validatePaymentInputsAndOutputs`, allows the double-spend uniqueness key for an `issue` input to omit the issuer's address from the SQL uniqueness constraint (`if (objAsset && !objAsset.issued_by_definer_only){ doubleSpendWhere += " AND address=?"; ...}` — only added when `issued_by_definer_only` is true): [3](#0-2) 
combined with the cap-equality requirement: [4](#0-3) 
this invariant ("capped ⇒ definer-only issuance") is what prevents every address from independently issuing a full `cap` amount of the asset (since serial_number=1 is only unique per definer address when `issued_by_definer_only` is enforced). `aa_validation.js`'s definition-time linter for AA-generated asset templates does not check this dependency, so an AA author can craft an `asset` message template (`cap` set, `issued_by_definer_only` left `false` or set to a formula evaluating to `false`) that passes AA-definition validation successfully.

### Impact Explanation
If the AA-emitted `asset` message ultimately still passes through the general-purpose `validateAssetDefinition` (`validation.js`, line ~2725) when the AA response unit is composed and validated as an ordinary unit, then the missing check in `aa_validation.js` is purely a static/definition-time linting gap: it only causes AAs whose definitions violate this invariant to bounce at trigger time (denial of AA execution / wasted trigger funds), not an actual asset-cap bypass, because the authoritative enforcement point (`validation.js:2802`) still runs for every unit regardless of its author (bAA or not).

I was not able to fully verify within the remaining budget whether every AA-generated `asset` message is unconditionally re-validated through `validateAssetDefinition` before being written to the ledger, or whether any AA-specific fast path in `aa_composer.js`/`writer.js` skips that re-validation for AA response messages. If such a fast path exists, the impact escalates to supply inflation (every holder/attacker address could independently mint the full `cap` amount of the asset, since the per-address double-spend uniqueness constraint that normally prevents multiple issuances of the capped serial_number=1 output is only added when `issued_by_definer_only` is true).

### Likelihood Explanation
Low-to-Medium if the runtime re-validation path (`validation.js:2725`) always re-checks AA-emitted asset messages (most likely case), because the only consequence is an AA definition that always bounces when its asset-issuing case is triggered — a functional/availability nuisance for the AA author, not a fund-safety violation for other users. It would be High if AA response messages bypass the general `validateAssetDefinition` check (unverified).

### Recommendation
Add the missing dependent checks to `aa_validation.js`'s `'asset'` case so that AA-definition-time validation matches exactly the invariants enforced by `validation.js`'s `validateAssetDefinition`, specifically:
- Reject definitions where `payload.cap` is set (or is a formula) while `payload.issued_by_definer_only` is not provably `true`.
- Reject `attestors` present when `spender_attested` is not `true`, using the same MCI gating as `validation.js`.

Independently, audit whether AA-emitted `asset` messages are unconditionally passed through `validateAssetDefinition` (the authoritative runtime check) with no fast path that trusts the AA-definition-time validation — this is the critical fact that determines whether the missing check is only a linting gap or an actual fund-safety bug.

### Proof of Concept
1. Author an AA with a case that emits an `asset` message such as:
```
{
  app: 'asset',
  payload: {
    cap: 1000000,
    is_private: false,
    is_transferrable: true,
    auto_destroy: false,
    fixed_denominations: false,
    issued_by_definer_only: false,   // should be rejected together with cap, but aa_validation.js does not check this combination
    cosigned_by_definer: false,
    spender_attested: false
  }
}
```
2. Submit this AA definition; `validateAADefinition` in `aa_validation.js` accepts it because it never checks "`cap` set ⇒ `issued_by_definer_only` must be true" (contrast with `validation.js` lines 2802-2803).
3. Trigger the AA so it emits the `asset` message as a real unit message. If this message bypasses re-validation by `validateAssetDefinition` on the resulting unit, any address could subsequently issue up to `cap` units of the asset (each with `serial_number=1`), because the per-issuer double-spend uniqueness constraint is only added when `issued_by_definer_only` is true (`validation.js` lines 2370-2373), leading to supply inflation of the asset. If re-validation does occur, the AA's asset-issuing case will simply bounce every time it's triggered, an availability defect for the AA's users rather than a fund-safety break — this distinction could not be fully confirmed with the tools available in this session.
