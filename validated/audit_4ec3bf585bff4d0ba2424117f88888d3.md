### Title
Griefing/DoS of any AA that pays out to an externally-influenced address via forced secondary-trigger bounce - (File: aa_composer.js)

### Summary
Any Autonomous Agent (AA) whose payment logic can be steered by a trigger author (or by any party who can get their address baked into an AA's output list) into sending funds to an attacker-controlled AA address is exposed to a deterministic denial-of-service: the attacker's AA is auto-invoked as a "secondary trigger" and can unconditionally bounce, which propagates a full revert of the entire trigger chain, including the state changes and response of the AA the victim actually wanted to interact with. This mirrors the ERC777-hook DoS pattern in the report: an externally chosen, attacker-controlled callee is synchronously invoked mid-transaction and can revert the whole operation.

### Finding Description
When a primary AA trigger is processed, `handleTrigger()` builds and posts the AA's response unit, then calls `handleSecondaryTriggers()` [1](#0-0)  which looks up whether any of the AA's own payment output addresses are themselves AA addresses. If so, each such address is *automatically* re-triggered synchronously as a secondary AA, without any explicit opt-in from either the paying AA or the ultimate trigger author: [2](#0-1) 

Critically, if that secondary AA's own execution results in a bounce (`bounce_message` non-empty), the error is propagated back through `async.eachSeries`, and for a *primary* (non-secondary) trigger this forces a full `revert()` of the entire chain built so far: [3](#0-2) 

`revert()` rolls back all state variable changes, clears the write batch, and issues `ROLLBACK TO SAVEPOINT initial_balances`, discarding every response accumulated in the whole trigger chain (not just the secondary AA that bounced), before finally bouncing the *primary* trigger itself: [4](#0-3) 

The secondary AA's bounce decision is entirely under the control of whoever deploys that AA — it can trivially always fail (e.g., define an AA with no `messages`, or a formula that always errors), since `bounce()` has no constraint requiring it to ever succeed: [5](#0-4) 

This is structurally identical to the ERC777 report's core issue: a permissionless, externally-influenced target ("recipient" chosen by the calling context, analogous to the ERC1820 registered hook implementer) is synchronously invoked as part of someone else's higher-level operation, and that target unilaterally decides to revert, DoS-ing the entire operation for the legitimate caller.

### Impact Explanation
Any AA design pattern that forwards part of the payment to an address supplied by, or otherwise influenced by, an untrusted party (e.g., a "pay-to" / referral / affiliate / router / relayer address field commonly used in exchange, escrow, or vault-style AAs on top of `ocore`) is vulnerable: an attacker deploys a trivial "always-bounce" AA and causes it to be adopted as that address. From then on, every legitimate trigger that would send funds through that address to reach the real target AA is unconditionally reverted by `revert()`/`bounce()`, effectively freezing/DoS-ing that AA's functionality for all users routing through the compromised address, without the attacker needing any special privilege — they only need to be able to deploy an AA and get one address baked into another AA's output set. This falls under AA fund loss/freezing and denial of confirmable operation for the affected AA, satisfying the required impact bar.

### Likelihood Explanation
The precondition — an AA sending outputs to an address that is influenced by an external, potentially untrusted party — is a common and encouraged AA design pattern (referral/router/pay-to-address style AAs), and the secondary-trigger auto-invocation plus chain-wide revert-on-bounce is unconditional core behavior with no allowlisting, gas/complexity-based limiting per secondary bounce, or opt-out. No special access is required beyond deploying an ordinary AA, making this readily reachable by any unprivileged unit poster/AA author.

### Recommendation
Do not allow a bounce from a secondary (auto-triggered) AA to unconditionally revert the entire primary trigger chain when the secondary AA's address was not an intrinsic, trusted part of the calling AA's own definition (e.g., distinguish "secondary AAs invoked because the calling AA's own logic hardcodes them" vs. "secondary AAs whose address came from externally influenced trigger data"). At minimum, consider making a bounced secondary trigger a local/contained failure (e.g., have the calling AA explicitly handle failure via a getter/dry-run-style call before committing funds) rather than an implicit full-chain revert, and document/emphasize to AA authors that sending money to an externally-controllable address exposes them to this griefing vector so they should validate/sandbox such recipients (e.g., via `remote_func_call` "read-only" style validation) before committing payments in the same trigger.

### Proof of Concept
1. Attacker deploys `EvilAA`, an AA with no `messages` (or a message set that always fails filtering / errors), so any trigger sent to it always bounces, per the `bounce('no messages')` path at `aa_composer.js:1869-1870`.
2. Attacker gets `EvilAA`'s address accepted as a "pay-to"/referral/router address by some victim AA `VictimAA` that supports a caller-influenced destination for part of its payout (a widespread pattern for exchange/vault-style AAs).
3. A legitimate user posts a normal trigger to `VictimAA` with the payout destination set (directly or indirectly) to `EvilAA`'s address.
4. `handleTrigger()` composes `VictimAA`'s response unit with a payment output to `EvilAA`; `handleSecondaryTriggers()` (`aa_composer.js:1702`) detects that the output address is an AA and auto-invokes `EvilAA` as a secondary trigger.
5. `EvilAA` bounces; `async.eachSeries`'s final callback receives the error and, because this is the primary trigger, calls `revert({...})` (`aa_composer.js:1749`), which rolls back all state changes and forces the whole trigger, including `VictimAA`'s intended successful response, to bounce.
6. The legitimate user's transaction is reverted (losing only the bounce fee) despite `VictimAA`'s own logic being entirely correct, and this repeats for every future trigger that routes a payout to `EvilAA`, permanently denying that code path.
