### Title
Webhook signature verification binds to attacker-controlled organization field, decoupled from the repository actually written - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
Shipit supports multi-tenant GitHub App configuration, where multiple GitHub organizations, each with their own `webhook_secret`, can be registered in a single Shipit instance (as demonstrated by `test/dummy/config/secrets_double_github_app.yml`). The webhook signature check selects which organization's secret to verify against using a field taken directly from the untrusted JSON payload (`repository.owner.login`), while the code that actually acts on the webhook (looking up the `Repository`/`Stack` to sync, archive, update statuses, etc.) uses a different payload field (`repository.full_name`) with no cross-check that it belongs to the same organization that was used for signature verification. An administrator of one onboarded organization (who legitimately knows their own org's `webhook_secret`) can therefore forge a correctly-signed webhook whose `repository.full_name` references a repository/stack belonging to a *different* onboarded organization, causing Shipit to process writes against a repository the attacker does not control.

### Finding Description
`WebhooksController#verify_signature` computes the organization used to select the GitHub App / webhook secret entirely from the request body: [1](#0-0) [2](#0-1) 

`repository_owner` is `params.dig('repository', 'owner', 'login')` (or `organization.login`), both attacker-supplied JSON fields. `Shipit.github(organization: repository_owner)` looks up the per-organization secret keyed by this exact string: [3](#0-2) 

Meanwhile, every webhook handler resolves the actual repository/stack to act on using a *different* field from the same untrusted payload, `repository.full_name`, with no verification that its owner matches `repository_owner`: [4](#0-3) [5](#0-4) 

For example, the push handler triggers a GitHub sync solely based on the resolved `Repository`/`Stack`, regardless of which organization's secret was used to authenticate the request: [6](#0-5) 

The invariant that should hold is: **organization whose secret validated the HMAC signature == organization owning the repository that is subsequently written to**. Because both sides are independently derived from attacker-controlled JSON fields (`repository.owner.login` vs `repository.full_name`), an attacker who administers Org A's GitHub App integration in this Shipit instance (and thus legitimately knows Org A's `webhook_secret`) can set `repository.owner.login = "OrgA"` (to pass signature verification with a secret they know) while setting `repository.full_name = "OrgB/some-repo"` (to target a Stack that actually belongs to Org B). The HMAC only covers the raw body bytes and says nothing about consistency between these two JSON fields, so a validly-signed request from Org A can drive writes against Org B's repositories.

### Impact Explanation
This breaks the tenant isolation binding "an organization that authenticated versus the repository that is written," matching the High-severity category (cross-repository writes / unauthorized deploy actions triggered through webhook processing). Concretely, an attacker with legitimate (non-privileged, tenant-scoped) control of one onboarded GitHub organization's App/webhook secret can:
- Trigger `stack.sync_github` for another organization's stack via the `push` handler, forcing Shipit to fetch/record commits it did not actually receive from GitHub for that repo.
- Create/update commit statuses (`status` handler) or open/close/archive review stacks (`pull_request` handlers) for repositories owned by a different, unrelated organization onboarded to the same Shipit instance.
This is possible without any GitHub access to the victim organization's repository, purely by picking a `full_name` value that matches an existing `Repository` record.

### Likelihood Explanation
Likelihood is Medium-High in any multi-tenant Shipit deployment (explicitly supported per `secrets_double_github_app.yml` / `Shipit.github_organizations`). The attack requires only knowledge of one legitimately-configured org's `webhook_secret` (which an admin of that org would normally have, e.g. from initial GitHub App setup) and knowledge of the target repository's `owner/name` (often public information), no other repo write access needed.

### Recommendation
- After signature verification, re-derive the organization the webhook actually targets from the same field used for signature selection (`repository.owner.login`/`organization.login`) and require it to match the organization of the `Repository` resolved via `repository.full_name` before invoking any handler.
- Alternatively, bind webhook secrets per-repository/per-stack (as GitHub delivers them) rather than per-organization keyed off a payload field, removing the indirection entirely.
- Add regression tests asserting that a validly-signed webhook whose `repository.full_name` belongs to a different organization than `repository.owner.login`/`organization.login` is rejected.

### Proof of Concept
1. Shipit instance configured with two organizations, `OrgA` and `OrgB` (as in `test/dummy/config/secrets_double_github_app.yml`), each with distinct `webhook_secret`s, and each having a tracked `Repository`/`Stack` (e.g. `OrgB/victim-repo`).
2. Attacker is an admin of `OrgA` and knows `OrgA`'s `webhook_secret` (e.g. because they configured its GitHub App integration themselves).
3. Attacker crafts a `push` event JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "OrgA" },
    "full_name": "OrgB/victim-repo"
  }
}
```
4. Attacker computes `X-Hub-Signature: sha1=<hmac>` using `OrgA`'s known `webhook_secret` over the raw body and POSTs it to `/webhooks`.
5. `verify_signature` calls `Shipit.github(organization: "OrgA")`, verifies successfully against `OrgA`'s secret.
6. `PushHandler#process` resolves the target via `Repository.from_github_repo_name("OrgB/victim-repo")` and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` on `OrgB`'s stack — a write against `OrgB`'s data triggered using only `OrgA`'s credentials.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
# frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
    end
  end
end
```
