### Title
Malicious commit content (broken submodule reference) causes permanent, unrecoverable sync denial with no skip/rollback mechanism - (File: main.go)

### Summary
The M-04 report describes a "poison" state: a single trusted-but-later-malicious input (an `emissionToken` that reverts) gets baked into a loop that is re-executed for every user forever, permanently blocking progress with no admin recourse short of a contract change. The closest reachable analog in `git-sync` is in `configureWorktree`/`SyncRepo`: once an attacker who can push to the synced repository lands a commit whose submodule configuration is broken (bad URL, unreachable host, conflicting shallow config, etc.), `git submodule update --init` fails on every single sync loop iteration forever, because `SyncRepo` recomputes `changed` from the (unpublished) remote hash each time and always re-attempts the exact same failing operation, with no mechanism to skip, quarantine, or roll the target ref forward/backward.

### Finding Description
`SyncRepo` computes `remoteHash` from `FETCH_HEAD^{}` and compares it to `currentHash` (the hash represented by the currently published symlink) to decide whether an update is needed [1](#0-0) . If `changed` is true, it creates a worktree for `remoteHash` and calls `configureWorktree`, which performs the working-tree reset and then runs `git submodule update --init [--recursive] [--depth N]` [2](#0-1) . If that command fails, `configureWorktree` returns an error, `SyncRepo` returns before calling `publishSymlink`, and the symlink is never advanced [3](#0-2) .

Because the symlink was never updated, `currentHash` on the *next* loop iteration is still the old (previously published) hash, while `remoteHash` is still the same broken commit (assuming the attacker does not push further commits). `changed` is therefore true again, and `main()`'s outer loop simply logs the error and retries after `--period`, indefinitely [4](#0-3) . There is no mechanism in `configureWorktree`, `cleanup`, or the main loop to detect "this exact hash has repeatedly failed" and skip it, quarantine it, or fall back to the last-known-good state in a way that stops the retry storm — the only comment addressing repeated-failure hygiene is about avoiding a stale worktree directory collision, not about breaking the retry loop [5](#0-4) .

This is directly analogous to the reported bug class: a single piece of untrusted/attacker-influenced input (here, `.gitmodules`/submodule config committed to the tracked repository, which an attacker with push access — e.g. to a branch/PR that is auto-synced — fully controls) permanently poisons an otherwise-shared execution path (the sync loop), causing indefinite denial of forward progress until a human intervenes (e.g., by changing `--submodules=off`, forcing a revert commit upstream, or manually fixing `--root`).

### Impact Explanation
The impact is **persistent sync denial**: legitimate updates to the tracked repository can never be published as long as the poisoned commit is at the tip of the tracked ref, because every sync attempt re-derives the same `remoteHash` and re-runs the same failing submodule step. Consumers of `--link` are stuck on a stale checkout indefinitely (fail-static, not fail-open, so no wrong-content is served, but availability of updates is denied). This matches the report's "Reject ... no-impact analogs" bar because it is a genuine availability failure with no automatic remediation, not merely a single failed attempt — every subsequent poll wastes a fetch + worktree/checkout attempt in a busy retry loop until `--max-failures` (if set) causes the whole process to exit.

### Likelihood Explanation
Likelihood is moderate-to-high in any deployment where `git-sync` tracks a branch/ref that receives commits from less-trusted contributors (e.g., a GitOps repo where PR merges are auto-synced, or any setup where `--submodules` is left at its default `recursive` value and the tracked repo consumes third-party submodule URLs). No special privileges beyond normal push/merge access to the tracked ref are required — this is reachable purely through "untrusted repo content," consistent with the allowed analog surface (submodules, git argv construction). It does require that the broken submodule config actually causes `git submodule update --init` to fail (e.g. unreachable/renamed submodule remote, disallowed protocol, or conflicting shallow/depth settings) rather than merely warn.

### Recommendation
- Track consecutive failures per target hash; if the same `remoteHash` fails repeatedly (e.g., N times or for a configurable duration), stop retrying that exact hash and surface a persistent, actionable error (already partially supported via `--error-file`) rather than looping forever with no forward-progress signal beyond logs.
- Consider allowing `--submodules=off` behavior to be auto-triggered or clearly surfaced as the escape hatch, and document that a single broken submodule reference blocks all future syncs regardless of unrelated top-level changes.
- Optionally, support advancing past a known-bad hash once a newer commit is fetched (this already happens naturally when upstream moves forward, but there is no way to “unstick” without a further upstream commit or an operator flag change), and emit a distinct metric/log class for "stuck on hash X for N consecutive attempts" to make this condition observable.

### Proof of Concept
1. Configure `git-sync` with `--repo=<tracked-repo>` and default `--submodules=recursive`.
2. As a contributor with push access to the tracked ref, add a `.gitmodules` entry / submodule commit pointing to an unreachable or disallowed URL (e.g., a host that will refuse the connection, or a protocol not permitted by the git-sync's `protocol.*.allow` config) and push it as the new HEAD.
3. Observe: `git-sync`'s `SyncRepo` fetches the new `remoteHash`, calls `createWorktree`/`configureWorktree`, and the `git submodule update --init` step in `configureWorktree` fails [6](#0-5) ; `SyncRepo` returns an error before `publishSymlink` is reached.
4. Observe further: on every subsequent `--period` tick, the same failure repeats indefinitely (confirmed by the loop/error-handling logic in `main()` at [7](#0-6) ), and the published `--link` never advances even if a benign top-level file also changed in that same or later commits (because `changed` remains gated on reaching the fixed broken commit first, and forward progress requires either a further upstream fix commit or an operator changing flags).
