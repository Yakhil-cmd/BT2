### Title
Sustained high-utilization accrual overflows `i128` in `scaled_to_original`, permanently freezing all funds in the market - (File: contracts/pool/src/interest.rs)

### Summary
The LibTIFF CVE is an unchecked-bounds write that corrupts memory on a crafted input — the analog class here is unchecked arithmetic on an attacker-influenced quantity producing a persistent failure. In the XOXNO Lending pool, `global_sync` accrues interest by multiplying the market's scaled `borrowed` balance by the new borrow index via `Ray::mul` / `scaled_to_original`, which panics with `GenericError::MathOverflow` when the product exceeds `i128::MAX`. An unprivileged borrower who keeps a large market at ~98% utilization drives the borrow index past `i128::MAX / borrowed` — roughly 170x on a billion-token 18-decimal market — *before* the `MAX_BORROW_INDEX_RAY` cap engages, at which point every subsequent accrual traps. Because `global_sync` runs at the head of every entrypoint, the market is permanently bricked: no `withdraw`, `repay`, `borrow`, `liquidate`, or `update_indexes` can execute, freezing all supplier principal forever.

### Finding Description
`global_sync` in `contracts/pool/src/interest.rs` (lines 20–33) calls `accrue_chunk`, which invokes the shared `accrue_step`. Inside `accrue_step`, `calculate_supplier_rewards` (common/src/rates/index.rs:80–81) computes `borrowed.mul(old_borrow_index)` and `borrowed.mul(new_borrow_index)`; `Ray::mul` is `scaled_to_original` (common/src/rates/scaling.rs:14–16), a `mul_div_half_up` that panics with `MathOverflow` when `scaled * index` does not fit `i128`. `update_borrow_index` (common/src/rates/index.rs:13–19) clamps the *index* at `MAX_BORROW_INDEX_RAY` (1e36 raw), but nothing bounds the *value product* `borrowed * index`. A scaled borrow book of `B` ray overflows once `index > i128::MAX / B`; for `B = 1e36` (a billion 18-decimal tokens) the cliff is ≈170x, far below the 1e9x index cap, and the XLM-style steep curve reaches it in a small number of years at 98% utilization. The production harness test `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` (tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:315–361) demonstrates exactly this: `update_indexes` reverts with `MATH_OVERFLOW`, `last.borrow_index < MAX_BORROW_INDEX_RAY`, and `withdraw`/`repay` both revert with the same panic because every verb accrues first. `calculate_scaled_cap` (scaling.rs:26–33) deliberately saturates to avoid exactly this trap, so the accrual panic is an inconsistency rather than an accepted bound.

### Impact Explanation
Permanent freezing of funds: once `borrowed * borrow_index` crosses `i128::MAX`, no transaction touching the market can ever succeed, since accrual precedes position resolution in every verb. All suppliers' principal and accrued yield in that market are locked forever; borrowers cannot repay and liquidators cannot liquidate, so the bad debt can never be cleaned either — the contract is unable to operate on that market.

### Likelihood Explanation
Reachable by a single unprivileged address using only `supply`, `borrow`, and `update_indexes`, provided a listed market's caps admit a book large enough that `borrowed_ray * borrow_index` can exceed `i128::MAX` before the index cap (i.e., scaled borrows above roughly `i128::MAX / MAX_BORROW_INDEX_RAY` ≈ 1.7e2 ray… realistically ~1e36 ray, e.g. a billion 18-decimal tokens at ~98% utilization). The capital cost is high but it is own-funds griefing, not privileged access; once pushed over the cliff the freeze is irreversible because there is no path to lower the scaled book without a successful accrual. Severity: High — permanent freeze, deterministic once reached.

### Recommendation
Make the accrual path overflow-safe instead of panicking: use the saturating/I256-aware variants (`mul_div_floor_saturating`, as `update_supply_index` already does at index.rs:41, or `protocol_fee_shares`' headroom clamp at index.rs:94–99) when computing `old_total_debt`/`new_total_debt` in `calculate_supplier_rewards`, and cap `accrued_interest` at the representable headroom rather than trapping. Alternatively, enforce at borrow time a per-market ceiling on `borrowed` scaled ray (e.g., `i128::MAX / MAX_BORROW_INDEX_RAY` divided by a safety factor) so the product can never overflow before the index cap engages.

### Proof of Concept
```rust
// Reproduced by tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:321
let mut t = LendingTest::new()
    .with_market(big("BIG18", 18, xlm_curve()))
    .with_market(col())
    .with_max_utilization_disabled_all_markets()
    .build();
lift_caps(&t, "BIG18", 18);
lift_caps(&t, "COL", 7);
let principal = BILLION * 10i128.pow(18);
t.supply_raw(BOB, "BIG18", principal);
t.borrow_raw(ALICE, "BIG18", principal / 100 * 98); // ~98% util, unprivileged
loop {
    t.advance_time(YEAR_SECS);
    if t.try_update_indexes_for(&["BIG18"]).is_err() { break; } // MATH_OVERFLOW
}
// Now the market is permanently frozen:
assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0),   errors::MATH_OVERFLOW);
```
The panic originates in `scaled_to_original` / `calculate_supplier_rewards` when `borrowed * new_borrow_index` exceeds `i128::MAX`, before `update_borrow_index`'s `MAX_BORROW_INDEX_RAY` clamp can engage.
