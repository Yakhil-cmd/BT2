### Title
Stack-scoped ApiClient tokens can read CI/deploy status of any stack via CCMenuController - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::Api::CCMenuController` overrides the shared `stack` lookup helper to bypass the stack-scoping enforced everywhere else in the API, letting a token that is only authorized for one stack read CCMenu build/deploy status for **any** stack in the installation.

### Finding Description
Every other API controller resolves the target stack through `Shipit::Api::BaseController#stack`, which is scoped to the stacks the authenticated `ApiClient` is allowed to see: [1](#0-0) 

```
def stacks
  @stacks ||= current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all
end

def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```

`stacks` restricts the queryable set to `current_api_client.stack_id` when the client was created scoped to a single stack (as is the case for the CCMenu-specific client generated by `CCMenuUrlController`, see below). `require_permission :read, :stack` only checks the permission list (`ApiClient#check_permissions!`), it does **not** check that the resolved stack matches `current_api_client.stack_id`: [2](#0-1) 

So the *only* place that binds "the stack a token authorizes" to "the stack a request touches" is the `stacks.from_param!` scoping inside `#stack`.

`CCMenuController` re-defines `stack` to call `Stack.from_param!` directly, skipping the `stacks` scope entirely: [3](#0-2) 

```
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end

def authenticate_api_client
  @current_api_client = ApiClient.authenticate(params[:token])
  super unless @current_api_client
end
```

`Stack.from_param!` performs a global, unscoped lookup by owner/name/environment: [4](#0-3) 

The equality that should hold — `current_api_client.stack_id == resolved_stack.id` (when the client is stack-scoped) — is never checked in this controller. The CCMenu-dedicated tokens are minted exactly for this narrow purpose (stack-scoped, `read:stack` only) by `CCMenuUrlController`: [5](#0-4) 

```
def client
  @client ||= ApiClient.create_with(permissions: %w[read:stack])
                       .find_or_create_by!(creator: current_user, name: 'CCMenu Client')
end
```

Because these clients validate `belongs_to :stack, optional: true` and are typically bound to one stack, the intended invariant is "this token can only see CCMenu data for the stack it was minted for." `CCMenuController#stack` breaks that invariant: any holder of a valid (even minimally-scoped) `read:stack` token can substitute an arbitrary `stack_id` param and read another stack's build/deploy status.

### Impact Explanation
This is an unauthenticated-scope read of stack state: a token deliberately restricted to one stack (e.g., leaked via a CCMenu URL shared with a CI dashboard tool, which is explicitly designed to be embedded in third-party CCTray clients) can be replayed against `/api/stacks/:stack_id/ccmenu.xml` for any other stack to disclose its name, last build status/label, last build time, activity, and web URL — information about deploy pipelines that the token holder was never granted `read:stack` access to for that repository/environment. This matches the "unauthorized read of stack state" high-impact category since it crosses the credential-to-repository binding without any additional authentication.

### Likelihood Explanation
High. Exploitation only requires possession of any valid `ApiClient` token with `read:stack` permission (including intentionally narrow, single-stack CCMenu tokens meant to be shared externally) and knowledge/guessing of another stack's `owner/repo/environment` identifier, which is often predictable or discoverable from the org's repository list. No privileged access or additional secrets are needed beyond the already-issued token.

### Recommendation
Make `CCMenuController#stack` use the scoped `stacks` helper (i.e., `stacks.from_param!(params[:stack_id])`) exactly like `BaseController#stack`, instead of calling `Stack.from_param!` unscoped. This restores the invariant that a stack-scoped `ApiClient` can only resolve to the stack it was authorized for.

### Proof of Concept
1. As a legitimate user, generate a CCMenu URL for Stack A via `CCMenuUrlController#fetch` (`GET /stacks/:stack_id/ccmenu_url`), obtaining a token whose `ApiClient` record has `stack_id = A.id` and `permissions = ["read:stack"]`.
2. Using that same token, call `GET /api/stacks/<owner>/<repo-B>/<environment>/ccmenu.xml?token=<token>` for a different Stack B that the client was never scoped to.
3. Because `CCMenuController#stack` calls `Stack.from_param!` directly (bypassing `stacks`/`current_api_client.stack_id` filtering), the request succeeds and returns Stack B's CCMenu XML (build status, last build label/time, web URL), even though the token's `stack_id` only authorizes Stack A.
