### Title
Membership webhook signature verification keys off a spoofable `repository.owner.login` field instead of the `organization.login` actually written to `Team#organization` - (File: app/controllers/shipit/webhooks_controller.rb, app/models/shipit/webhooks/handlers/membership_handler.rb)

### Summary
`WebhooksController#verify_signature` selects the `GitHubApp`/`webhook_secret` used to check `X-Hub-Signature` using `repository_owner`, which reads `params.dig('repository','owner','login')` first and only falls back to `params.dig('organization','login')` if the `repository` key is absent. Because the raw JSON body is entirely attacker-controlled (the attacker only needs a valid HMAC computed with a secret they legitimately possess for their own onboarded organization), they can inject an arbitrary `repository.owner.login` (their own org, X) to select their own secret for signature verification, while leaving a different, victim `organization.login` (Y) in the body — the field `MembershipHandler#find_or_create_team!` actually writes into `Team#organization`.

### Finding Description
The claimed broken binding is: `repository_owner` (used by `verify_signature` to pick the verifying `webhook_secret`) == `params.organization.login` (used by `find_or_create_team!` to set `Team#organization`).

Code path:
- `WebhooksController#verify_signature` [1](#0-0)  resolves the signing org via `repository_owner` [2](#0-1) , which is computed straight off the raw, attacker-controlled JSON body, before any `ExplicitParameters` schema validation runs (schema parsing only happens later, inside `Handler#initialize` when `MembershipHandler.call(params)` is invoked) [3](#0-2) .
- `MembershipHandler`'s schema only `requires` an `action`, a `team` object, an `organization.login`, and a `member.login` [4](#0-3) ; it does not forbid or validate an extraneous top-level `repository` key, so the attacker is free to add one purely to steer `repository_owner` in the controller.
- `find_or_create_team!` unconditionally writes `params.organization.login` — not `repository_owner` — onto the new/updated `Team` record [5](#0-4) .

Exploit: the attacker, who legitimately owns organization X (onboarded in `Shipit.github_apps` with a real `webhook_secret`), POSTs to `/webhooks` with header `X-Github-Event: membership` and a JSON body such as:
```json
{
  "action": "added",
  "team": {"id": 999999, "name": "n", "slug": "n", "url": "u"},
  "organization": {"login": "victim-org"},
  "member": {"login": "attacker-login"},
  "repository": {"owner": {"login": "attacker-org"}}
}
```
signed with `X` (`attacker-org`)'s real `webhook_secret`. `verify_signature` computes `repository_owner = "attacker-org"` (repository key present), fetches `attacker-org`'s `GitHubApp`, and the HMAC checks out because it was actually signed with that secret — verification passes. `MembershipHandler#find_or_create_team!` then creates a `Team` with `organization: "victim-org"` and adds the attacker as a member via `team.add_member(member)`, using an org name never authenticated by any secret belonging to `victim-org`.

None of the existing guards catch this: `drop_unhandled_event` only checks the event is registered; `verify_signature` itself is the mechanism being subverted since it derives its key-selection field from the same untrusted body used later by the handler, but from a different, independently-forgeable subfield (`repository.owner.login` vs `organization.login`); the `ExplicitParameters` schema for `membership` never constrains or cross-checks the `repository` key against `organization.login`.

### Impact Explanation
This lets any attacker who owns/controls a single legitimately-onboarded GitHub organization in `Shipit.github_apps` forge `Team` records (and team membership) attributed to any other organization configured in Shipit, without ever possessing that victim organization's `webhook_secret`. If `Team#organization`/slug pairs are consulted anywhere for authorization (`Shipit.github_teams` role mapping / `User#authorized?`), this becomes a cross-tenant authorization/escalation vector: an attacker can insert themselves into a `Team` object that appears to belong to the victim org and be added as a member, potentially gaining elevated permissions tied to that org's teams. This is a genuine cross-organization write not authenticated by the org whose value is written, matching the "payload for one repository/organization mutating another's team" Critical/High impact category.

### Likelihood Explanation
Preconditions: the attacker must own/control at least one organization that is configured as a `GithubApp` in `Shipit.github_apps` with a valid `webhook_secret` (i.e., is legitimately onboarded to send webhooks to this Shipit instance) — a normal, low-cost precondition satisfied by any org admin who set up Shipit for their own repos. The attacker does not need any Shipit session, API token, or the victim org's secret. Given that, the attack is a single crafted HTTP POST with a correct HMAC over an attacker-authored JSON body; it is fully repeatable and can target arbitrary victim organization names, limited only by whatever `github_id` values collide with existing `Team` rows (attacker can pick an unused id to force creation, or reuse to overwrite `team.github_team`/organization on an existing record within `find_or_create_by!`'s block — note the block only runs on creation, but the divergence still applies to any newly created org/team pairing).

### Recommendation
`verify_signature` must not resolve the signing key from `repository.owner.login` when the event has no canonical `repository` object for the event type; more importantly, the field used to select the `webhook_secret` must be the same field used by every handler for state mutation. Concretely: (1) make `repository_owner` for org-level events (`membership`, `team`, etc.) always read `organization.login` and never accept a `repository` key for these event types; (2) update handlers to re-derive `Team#organization` (or any similarly-persisted attacker-supplied identity) from the same value that was used to authenticate the request, not from an independent field in the same untrusted payload; (3) have the `ExplicitParameters` schemas reject unexpected top-level keys (e.g., disallow `repository` on `membership`/`team` events) to eliminate the injection vector entirely.

### Proof of Concept
```ruby
test "membership webhook cannot bind organization from a different org than the one whose secret signed it" do
  Shipit.github_apps["attacker-org"] = GitHubApp.new("attacker-org", webhook_secret: "attacker-secret")
  Shipit.github_apps["victim-org"]   = GitHubApp.new("victim-org",   webhook_secret: "victim-secret")

  body = {
    action: "added",
    team: { id: 424242, name: "n", slug: "n", url: "u" },
    organization: { login: "victim-org" },
    member: { login: "attacker-login" },
    repository: { owner: { login: "attacker-org" } }
  }.to_json

  signature = "sha1=" + OpenSSL::HMAC.hexdigest("sha1", "attacker-secret", body)

  post "/webhooks", params: body, headers: {
    "X-Github-Event" => "membership",
    "X-Hub-Signature" => signature,
    "Content-Type" => "application/json"
  }

  assert_response :ok
  team = Team.find_by(github_id: 424242)
  # binding under test: repository_owner ("attacker-org") should equal Team#organization
  # if the fix is correct; currently it diverges to "victim-org"
  refute_equal "victim-org", team.organization
end
```
Under current code, this test fails: `team.organization` is `"victim-org"` while the signature was verified using `attacker-org`'s secret, confirming the divergence.
