### Title
Removal of an address from a `spender_attested` asset's attestor list permanently freezes any AA holding that asset — ([File: validation.js])

### Summary
`ocore` supports assets with `spender_attested: true`, where every input owner (spender) and output recipient must currently be on the asset's attestor-approved list, checked dynamically at validation time rather than at the time the funds were received. The attestor list is a mutable configuration (`asset_attestors` message) that the asset's attestors/definer can change at any time, independent of the current holders' balances. If an Autonomous Agent (AA) is a holder of such an asset and its address is later removed from (or simply omitted from a re-published) attestor list, the AA becomes permanently unable to spend that balance in any trigger, since AA logic offers no way to react preemptively (an AA cannot watch for and act on the specific unit that would revoke its own attestation before it's stable). This directly mirrors the external report's root cause: a downstream protocol parameter change (LTV=0 on Aave) breaking a smart-contract holder's (Morpho's) ability to withdraw/transfer/liquidate a wrapped asset it holds, because the restriction is re-evaluated dynamically against the *current* configuration rather than the configuration at time of receipt.

### Finding Description
When a `payment` message spends or issues a `spender_attested` asset, validation loads the *current* list of attested addresses at `objValidationState.last_ball_mci` and requires the spender/issuer/output addresses to be in that list: [1](#0-0) 
This dynamic check is repeated for every transfer input: [2](#0-1) 
and for every output address: [3](#0-2) 

The attestor list backing this check is computed fresh via `filterAttestedAddresses`, which queries the `attestations` table joined against the asset's currently configured attestor addresses (`objAsset.arrAttestorAddresses`), not against a snapshot from when the balance was received: [4](#0-3) 

The attestor list itself is a first-class, freely updatable message type — `asset_attestors` — validated only for basic shape, with no restriction tied to current holders' balances or any grace period: [5](#0-4) 

Critically, AAs are explicitly permitted to hold and be required to comply with `spender_attested` asset constraints when sending payments in a trigger response: the AA composer loads the asset info including `arrAttestedAddresses` for the *current* mci right before building the response unit and enforces the same conditions transitively through the shared `validatePaymentInputsAndOutputs`/`validatePayment` code paths: [6](#0-5) 

Because AAs have no way to unilaterally react to an upcoming attestor-list change (they only execute deterministically in response to triggers, and cannot "front-run" or preemptively withdraw before a particular `asset_attestors` unit becomes stable, since AA logic has no branch conditioned on "my address is about to be de-attested"), once such a unit stabilizes and the AA's address is no longer attested, any balance of that asset held by the AA becomes permanently unspendable by that AA. This is structurally identical to the reported Aave/Morpho issue: a downstream protocol configuration change (attestor list / LTV) is checked dynamically against current state, and the affected holder (AA / Morpho) has no built-in mechanism to react and preserve its own or its users' ability to move funds, resulting in permanently frozen AA funds.

### Impact Explanation
Funds sent to or accumulated by an AA in a `spender_attested` asset can become permanently locked/frozen if the asset's attestor(s) later republish a shorter attestor list omitting the AA's address (or simply let the AA's attestation lapse/get revoked via a new `attestations` record from a different attestor, combined with the list logic). This is an AA fund freezing scenario reachable purely by an ordinary asset-issuer/attestor action (posting `asset_attestors`) combined with a pre-existing AA trigger/deposit — no privileged network role is required beyond being the asset's definer/attestor, which is normal, permitted asset governance. Users interacting with that AA (e.g., via a DeFi-like AA that custodies this asset on their behalf) lose access to their funds with no recourse, matching the "AA fund loss or freezing" acceptance criterion.

### Likelihood Explanation
Any asset can be created with `spender_attested: true` and an attestor list by any user (including an AA definer creating an asset via an AA, as seen in `test/samples/create_an_asset.oscript`). Any AA that is designed to hold/route such assets (e.g., custodial, DeFi, or escrow AAs) is exposed. The attestor(s) can update the list unilaterally, at any time, and validation always uses the current list — there's no timelock, grace period, or check that would exempt existing holders. Given ordinary asset governance practices (e.g., compliance-driven attestor rotation) this is a realistic occurrence, not a contrived edge case.

### Recommendation
- When an AA's balance includes a `spender_attested` asset, consider warning AA authors (in documentation/oscript static analysis) that funds may become permanently stuck if the AA's address is de-attested, and encourage defensive designs (e.g., promptly forwarding such assets rather than holding them long-term).
- Consider adding an AA-specific safeguard, such as evaluating attestor-list changes against a grace period (e.g., requiring some number of MCIs before a removal takes effect) so that a currently-attested holder has a window to move funds out before losing spend rights.
- Document this dynamic-recheck behavior clearly for asset/attestor designers and AA authors, analogous to what Spearbit recommended for Morpho: describe the side effects and provide a recommended remediation procedure (e.g., AA should sweep/forward `spender_attested` balances immediately rather than accumulate them).

### Proof of Concept
1. Attestor `X` creates asset `A` with `spender_attested: true` and initial `attestors: [X]`.
2. `X` attests AA address `G` via an `attestation` message referencing asset `A`'s attestor `X`.
3. A trigger sends units of asset `A` to AA `G`; AA `G` accumulates a balance in asset `A` (e.g., holds it in state rather than immediately forwarding).
4. Attestor `X` posts a new `asset_attestors` message for asset `A` that lists a different attestor set/address, effectively removing `G` from future attestation eligibility (or simply attests a different address going forward without ever renewing `G`'s attestation, letting time invalidate reliance on it via `filterAttestedAddresses`'s dynamic query).
5. Any subsequent trigger causing AA `G` to attempt sending/spending its balance of asset `A` fails validation at [2](#0-1)  / [3](#0-2)  because `G` is no longer in the dynamically recomputed `arrAttestedAddresses`, and the AA has no way to have preemptively moved the funds since it cannot foresee or synchronously react to the attestor-list change unit before it becomes stable.
6. Asset `A` balance held by AA `G` is now permanently frozen; no AA logic path exists to release it once the attestation requirement fails.

function filterAttestedAddresses(conn, objAsset, last_ball_mci, arrAddresses, handleAttestedAddresses){
	conn.query(
		"SELECT DISTINCT address FROM attestations CROSS JOIN units USING(unit) \n\
		WHERE attestor_address IN(?) AND address IN(?) AND main_chain_index<=? AND is_stable=1 AND sequence='good' \n\
			AND main_chain_index>IFNULL( \n\
				(SELECT main_chain_index FROM address_definition_changes JOIN units USING(unit) \n\
				WHERE address_definition_changes.address=attestations.address AND main_chain_index<=? AND is_stable=1 AND sequence='good' ORDER BY main_chain_index DESC LIMIT 1), \n\
			0)",
		[objAsset.arrAttestorAddresses, arrAddresses, last_ball_mci, last_ball_mci],
		function(addr_rows){
			var arrAttestedAddresses = addr_rows.map(function(addr_row){ return addr_row.address; });
			handleAttestedAddresses(arrAttestedAddresses);
		}
	);
}
