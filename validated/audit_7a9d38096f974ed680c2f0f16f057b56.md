### Title
Malicious Proposer Equivocation Poisons Candidate `seenPreprepare`, Inflating CFS and Wrongly Excluding Candidate from KAIA Reward Distribution — (`kaiax/vrank/impl/handler.go`)

### Summary
A single malicious proposer can sign two valid `VRankPreprepare` messages for the same `(blockNum, round)` view with different block hashes. By delivering the wrong-hash message to a candidate first, the candidate's `seenPreprepare` map is poisoned. The subsequent legitimate preprepare is silently dropped as a "conflicting view." The candidate then broadcasts a `VRankCandidate` with the wrong block hash, which is counted as a failure by honest committee members in `EvaluateCandidates`, inflating the candidate's CFS score and wrongly excluding it from KAIA reward distribution at epoch transition.

### Finding Description

`HandleVRankPreprepare` verifies that the sender is the legitimate proposer, then calls `markSeenPreprepare` to record the first `(viewKey → blockHash)` pair seen. Any subsequent message for the same view with a different hash is classified as a "conflicting view" and dropped:

```go
} else if conflictingView {
    logger.Warn("Conflicting VRankPreprepare ignored", ...)
    return nil
}
``` [10](#0-9) 

The signature verification in `recoverVRankPreprepareSender` covers `(chainID, blockNum, round, blockHash)`. A malicious proposer can legitimately sign two different `(blockNum, round, H_wrong)` and `(blockNum, round, H_correct)` payloads with their own key — both signatures are valid. The code has no mechanism to detect or reject equivocation (two valid signatures from the same proposer for the same view with different hashes). [11](#0-10) 

When the wrong-hash message arrives first, `markSeenPreprepare` stores `H_wrong`. The candidate then broadcasts `VRankCandidate{BlockHash: H_wrong}`. When the correct message arrives, it is dropped. The candidate never broadcasts a `VRankCandidate` with the correct hash. [3](#0-2) 

In `EvaluateCandidates`, the committee member's `expectedBlockHash` is the correct hash (from the Istanbul PREPREPARE). The candidate's stored message has `H_wrong`, so the check `msgWithTime.Msg.BlockHash != expectedBlockHash` is true, and the candidate is added to `cfReport`: [7](#0-6) 

The byzantine filter removes the top-`F` reporter totals per candidate, where `F = floor(ProposerCount/3)`. However, the reporter of the false failure is the honest proposer of block N+1 (who accurately observed the wrong-hash response). The filter is designed to discard malicious reporters, not honest ones, so it provides no protection here. [8](#0-7) 

At epoch transition, `isPassVrankTest` checks `cfs < CfsThreshold`. An inflated CFS causes the candidate to fail this test, blocking promotion to `ValActive` and excluding it from KAIA reward distribution. [9](#0-8) 

### Impact Explanation
A single malicious proposer can repeatedly target specific candidates every time they are scheduled as proposer, accumulating CFS failures across an epoch. At epoch-end, the victim candidate fails the VRank test and is denied KAIA staking rewards — a direct, unauthorized manipulation of reward distribution affecting KAIA system-managed funds.

### Likelihood Explanation
Every validator is scheduled as proposer in rotation. A single Byzantine validator (no collusion required) can execute this attack every time they are the proposer. The attack requires only crafting a P2P message with a different block hash and ensuring it is delivered before the legitimate one — trivially achievable since the attacker controls their own node's send order.

### Recommendation
1. **Detect equivocation, don't silently drop:** When `conflictingView` is true, the candidate has received two valid signatures from the same proposer for the same view with different hashes. This is cryptographic proof of equivocation. The candidate should respond to the **first** valid preprepare it received (already done) but should not be penalized for the proposer's equivocation.
2. **Respond to the first valid preprepare regardless of subsequent conflicts:** The current code already broadcasts `VRankCandidate` on the first valid preprepare (before the conflicting one arrives). The issue is that the first message carries `H_wrong`. A fix is to only accept a `VRankPreprepare` whose block hash matches the block hash the candidate observed from the Istanbul PREPREPARE (i.e., cross-check against the candidate's own view of the canonical block).
3. **Alternatively, record equivocation evidence:** Log and expose equivocation proofs (two signatures from the same proposer for the same view with different hashes) so that governance or slashing mechanisms can penalize the equivocating proposer.

func (v *VRankModule) markSeenPreprepare(vk vrank.ViewKey, blockHash common.Hash) (bool, bool) {
	v.seenPreprepareMu.Lock()
	defer v.seenPreprepareMu.Unlock()

	if seenHash, ok := v.seenPreprepare[vk]; ok {
		if seenHash == blockHash {
			return true, false
		}
		return false, true
	}
	v.seenPreprepare[vk] = blockHash
	return false, false

func (v *VRankModule) vrankPreprepareSigHash(blockNum uint64, round uint8, blockHash common.Hash) common.Hash {
	chainID := v.ChainConfig.ChainID.Uint64()

	// Canonical encoding:
	// domain separator || chain_id(uint64 BE) || block_number(uint64 BE) || round(uint8) || block_hash(32 bytes)
	payload := make([]byte, 0, len(vrankPreprepareSigDomain)+8+8+1+len(blockHash))
	payload = append(payload, []byte(vrankPreprepareSigDomain)...)
	payload = binary.BigEndian.AppendUint64(payload, chainID)
	payload = binary.BigEndian.AppendUint64(payload, blockNum)
	payload = append(payload, round)
	payload = append(payload, blockHash[:]...)
	return crypto.Keccak256Hash(payload)
}

func (v *VRankModule) recoverVRankPreprepareSender(msg *vrank.VRankPreprepare) (common.Address, error) {
	sigHash := v.vrankPreprepareSigHash(msg.Block.NumberU64(), uint8(msg.View.Round.Uint64()), msg.Block.Hash())
	pubkey, err := crypto.SigToPub(sigHash.Bytes(), msg.Sig)
	if err != nil {
		logger.Debug("SigToPub failed for VRankPreprepare", "err", err, "blockNum", msg.Block.NumberU64())
		return common.Address{}, fmt.Errorf("%w: %v", vrank.ErrInvalidProposerSig, err)
	}
	return crypto.PubkeyToAddress(*pubkey), nil
}

func generateCFSFromCPMatrix(cpMatrix vrank.CPMatrix) map[common.Address]uint64 {
	F := cpMatrix.ProposerCount() / 3
	return byzantineFilter(cpMatrix, F)
}

// byzantineFilter computes CFS scores from pre-aggregated per-candidate failure data.
//
// cpMatrix[candidate][reporter] is the number of times reporter included candidate
// in cfReport over the epoch. F is the number of highest reporter totals to discard
// per candidate, defending against up to F byzantine reporters that may inflate scores.
func byzantineFilter(cpMatrix vrank.CPMatrix, F int) map[common.Address]uint64 {
	cfs := make(map[common.Address]uint64)
	for cand, reporterToScore := range cpMatrix {
		scores := slices.Collect(maps.Values(reporterToScore))
		slices.Sort(scores)
		if F >= len(scores) {
			// since `scores` contain non-zero scores only, F >= len(scores) can happen, in which case all scores are discarded.
			scores = nil
		} else {
			scores = scores[:len(scores)-F]
		}
		var sum uint64
		for _, t := range scores {
			sum += t
		}
		cfs[cand] = sum
	}
	return cfs
}
