### Title
Webhook signature verification org-selection is decoupled from the org whose repository is actually acted upon, allowing unauthenticated forged events on protected orgs - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks the GitHub App (and thus the `webhook_secret` used to validate `X-Hub-Signature`) using `repository.owner.login` (or `organization.login`) taken straight from the unauthenticated JSON body. Every webhook `Handler` (`PushHandler`, `StatusHandler`, etc.), however, resolves the actual `Stack`/`Repository` to mutate using a *different* field of the same body: `repository.full_name`. Because these two fields are never cross-checked, an attacker can pick an organization that has no `webhook_secret` configured (which bypasses HMAC verification entirely) while pointing `repository.full_name` at a completely different, "protected" organization's repository.

### Finding Description
`verify_signature` selects the verifying app via the attacker-supplied `repository_owner`: [1](#0-0) [2](#0-1) 

`GitHubApp#verify_webhook_signature` unconditionally trusts the request if that particular org has no secret configured: [3](#0-2) 

Once verification passes (trivially, for a secret-less org), the controller dispatches the raw, attacker-controlled `params` to the event handlers: [4](#0-3) 

Every handler resolves its target `Stack` via a *separate* JSON field, `repository.full_name`, with zero relation to the `repository.owner.login`/`organization.login` value used for signature-org-selection: [5](#0-4) 

`PushHandler` and `StatusHandler` act directly on whatever stack/commit that `full_name`/`sha` resolves to: [6](#0-5) [7](#0-6) 

Multi-org configuration is a documented, supported feature where each org independently defines its own `webhook_secret`: [8](#0-7) 

Every shipped example config leaves `webhook_secret` unset for at least one org, including the double-org fixture used by this engine's own tests: [9](#0-8) 

The equality that should hold — *the organization whose secret validated the signature == the organization owning the repository the handler mutates* — is broken because the two are read from independent, both-attacker-controlled JSON fields (`repository.owner.login` vs `repository.full_name`), with no cross-validation anywhere in the request pipeline.

### Impact Explanation
An attacker with no credentials at all can:
1. POST to the webhooks endpoint with `repository.owner.login` (or `organization.login`) set to any org that has `webhook_secret: nil` in the multi-org config (the documented default in every shipped config example).
2. Set `repository.full_name` to `"<protected-org>/<victim-repo>"`, and craft `ref`/`after` (for `push`) or `sha`/`state`/`context` (for `status`).
3. `verify_webhook_signature` returns `true` unconditionally (no secret to check against), so the request is accepted without any valid HMAC.
4. The dispatched handler resolves the *victim* org's `Stack` via `full_name` and either forces a `GithubSyncJob` (syncing/attaching arbitrary commit history) or forges a commit `status` (`StatusHandler#process`) that can flip CI/merge-gating state used by Shipit's merge queue and deploy decision logic — for a stack belonging to an organization whose webhook secret the attacker never possessed.

This maps to the required impact category "unauthorized deploy/merge": forged `status` events can satisfy required-status checks that gate Shipit's automated merge/deploy pipeline for a protected repository, without the attacker ever authenticating with that repository's webhook secret.

### Likelihood Explanation
Likelihood is high in any Shipit deployment using the (documented, first-class) multi-org `github:` config schema where at least one configured org omits `webhook_secret` — which is the value shown in every example/config file shipped with this engine. No credentials, no GitHub App key, no session, and no prior repository access are required; only knowledge of the org name lacking a secret and the target `full_name`, both of which are visible/discoverable (org names and repo full names are public GitHub identifiers).

### Recommendation
Cross-validate that the organization used to select/verify the webhook secret is identical to the organization actually referenced by `repository.full_name` (and `organization.login` when used as fallback) before dispatching to handlers, rejecting the request if they differ. Additionally, consider refusing webhook delivery entirely for any configured org lacking a `webhook_secret` in multi-org mode, since a secret-less org effectively disables authentication for every organization sharing the same webhook endpoint.

### Proof of Concept
1. Configure Shipit in multi-org mode with `OrgA` (`webhook_secret: nil`) and `OrgB` (`webhook_secret: <real secret>`), each with a tracked stack, per `test/dummy/config/secrets_double_github_app.yml`.
2. Send `POST /github/hooks` with header `X-Github-Event: status`, no valid `X-Hub-Signature`, and body:
```json
{
  "organization": {"login": "OrgA"},
  "repository": {"owner": {"login": "OrgA"}, "full_name": "OrgB/protected-repo"},
  "sha": "<sha-of-pending-commit-in-OrgB-stack>",
  "state": "success",
  "context": "required-check"
}
```
3. `verify_signature` resolves `Shipit.github(organization: "OrgA")`, whose `verify_webhook_signature` returns `true` immediately because `OrgA` has no `webhook_secret`.
4. `StatusHandler` looks up `Commit.where(sha: params.sha)` — resolved independently of `OrgA` — and marks the `OrgB` commit's status as `success`, without ever supplying `OrgB`'s webhook secret.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
