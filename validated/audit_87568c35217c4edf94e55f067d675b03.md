### Title
Webhook Signature Bound to `repository.owner.login` While Handlers Act on Unverified `repository.full_name`/`sha` Fields, Enabling Cross-Organization Writes - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects the HMAC secret to check using the organization derived from the payload (`repository.owner.login`, falling back to `organization.login`), then verifies the raw body against that org's `webhook_secret`. However, the handlers that subsequently act on the *same, already-signed* payload do not use that verified organization; they resolve their write target from other unrelated fields (`repository.full_name` in `Handler#repository_name`, or a bare `sha` lookup in `StatusHandler`). Any tenant that legitimately owns a Shipit-configured GitHub organization (and therefore knows its own `webhook_secret`) can craft a signed payload whose "authenticated" organization is their own, but whose acted-upon repository/commit belongs to a completely different organization also hosted on the same Shipit instance.

### Finding Description
`verify_signature` derives the organization for secret lookup like this: [1](#0-0) [2](#0-1) 

The signature is verified with `Shipit.github(organization: repository_owner).verify_webhook_signature`, which HMACs the *entire raw body* against that organization's configured `webhook_secret` (multi-tenant configuration is intentional — see `config/secrets.development.shopify.yml`, which lists multiple orgs each with its own `webhook_secret`). The check only proves "this body was signed by whoever holds `repository_owner`'s secret" — it says nothing about which *other* repository/commit the body claims to reference.

Once verification passes, `WebhooksController#create` dispatches to handlers using the raw parsed body, unrelated to `repository_owner`: [3](#0-2) 

`Handler#stacks`/`#repository_name` resolve the target repository from `repository.full_name`, a *different* JSON field than the one used for signature-org selection: [4](#0-3) 

`PushHandler#process` then acts on stacks resolved from that untrusted field: [5](#0-4) 

`StatusHandler#process` is worse still — it never consults `repository` at all, matching purely on a global `sha`, so any commit sharing that SHA across *any* stack/organization in the installation is affected: [6](#0-5) 

This is a direct structural analog to the `addRewards()` bug: the field that is checked/verified (`periodFinish`/timestamp gate, here `repository.owner.login`) is decoupled from the field that actually drives the state-changing effect (`rewardRate`/`periodFinish` write, here `repository.full_name` / `sha`). The binding "organization authenticated == repository written" is broken.

### Impact Explanation
A GitHub organization owner who has (legitimately) had their own org onboarded into a shared, multi-org Shipit deployment can forge a webhook payload signed with their own valid `webhook_secret`, but whose `repository.full_name` (push) or `sha` (status) references a stack/commit belonging to a different, unrelated organization/repository hosted on the same Shipit instance. This drives `Stack#sync_github` and `Commit#create_status_from_github!` for victim repositories the attacker has no GitHub access to — a cross-repository write triggered without any credential belonging to the victim organization. Depending on downstream effects of `sync_github` (commit ingestion, merge-queue/CI status changes, deploy readiness signals), this can influence deploy/merge decisions for repositories outside the attacker's authorization scope.

### Likelihood Explanation
Requires only that the attacker control one legitimately configured organization in a multi-org Shipit deployment (a supported, documented configuration per `config/secrets.development.shopify.yml`), and does not require any victim-side secret, `ApiClient` token, or session — it is a same-instance, cross-tenant boundary crossing using a POST directly to the public `/github/webhooks` endpoint.

### Recommendation
Bind the value used to select/verify the signature to the exact same value used to resolve the write target. Concretely, `Handler#repository_name` (and any handler resolving repository/commit from the payload) should re-derive/re-validate against the same `repository.owner.login` (or the verified `organization`) that `WebhooksController#verify_signature` used, rejecting payloads where `repository.full_name`'s owner segment does not match the organization whose secret validated the signature. `StatusHandler` should additionally scope its `Commit` lookup by the repository/organization derived from the verified payload rather than a global `sha` match.

### Proof of Concept
1. Shipit is configured (as in `config/secrets.development.shopify.yml`) with two orgs, `attacker-org` (attacker-controlled, `webhook_secret: S_attacker`) and `victim-org` (hosting a stack tracked by Shipit).
2. Attacker crafts a raw JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "deadbeefdeadbeefdeadbeefdeadbeefdeadbeef",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(S_attacker, body)>` using their own valid secret, and sets `X-Github-Event: push`.
4. `POST /github/webhooks` with this body/signature. `verify_signature` looks up `repository_owner` = `"attacker-org"`, fetches `Shipit.github(organization: "attacker-org")`, and the HMAC check passes (attacker's own valid secret).
5. `PushHandler.call(params)` runs, resolving `stacks` via `Repository.from_github_repo_name("victim-org/victim-repo")` — a repository the attacker does not own — and invokes `stack.sync_github(expected_head_sha: "deadbeef...")` against it, despite the signature only having proven attacker's ownership of `attacker-org`.
