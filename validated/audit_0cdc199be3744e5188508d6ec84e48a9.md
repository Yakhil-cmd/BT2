### Title
Webhook signature verified against the payload's `repository.owner.login`, but Shipit actions are dispatched by the independent `repository.full_name` field, letting a holder of one org's webhook secret spoof events for another org's stacks - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App / webhook secret to validate the HMAC signature against using `repository_owner`, which is read from `params.dig('repository', 'owner', 'login')` (or `organization.login`) [1](#0-0) [2](#0-1) . Once the signature is accepted, every event handler (`PushHandler`, `StatusHandler`, `CheckSuiteHandler`, the `PullRequest::*Handler`s) resolves the target `Repository`/`Stack` using an entirely different, independently-controlled field: `payload.dig('repository', 'full_name')` [3](#0-2) [4](#0-3) . The HMAC signature only proves the JSON body as a whole came from *an* organization whose webhook secret matches; it never binds `repository.owner.login` (used to pick the secret) to `repository.full_name` (used to pick the acted-upon stack).

### Finding Description
The binding that should hold is: `organization whose secret validated the signature == organization that owns the repository/stack being acted upon`. Concretely, `repository_owner` (secret-selection key) and `repository_name`/`full_name` (action-target key) must refer to the same GitHub organization for every event.

Before an attacker's request: a legitimate webhook for organization A carries `repository.owner.login = "OrgA"` and `repository.full_name = "OrgA/some-repo"`, both consistent, and is signed with `Shipit.github(organization: "OrgA")`'s `webhook_secret` [5](#0-4) .

After the attacker's crafted request: anyone who legitimately controls a GitHub App installation on some organization "OrgA" that is configured in Shipit's `github:` secrets (e.g. they are an admin of their own org that also uses this Shipit instance) knows/can compute OrgA's `webhook_secret` and can sign an arbitrary JSON body with it. They construct a payload where:
- `repository.owner.login` (or `organization.login`) = `"OrgA"` — so `verify_signature` looks up and validates against OrgA's secret and succeeds [1](#0-0) .
- `repository.full_name` = `"OrgB/victim-repo"` — a repository belonging to a *different* organization ("OrgB") that has stacks configured in this same Shipit instance.

Since the handler layer never re-derives or cross-checks the organization from the same field used for signature selection, `PushHandler.process` will locate `OrgB/victim-repo`'s stacks via `Repository.from_github_repo_name(repository_name)` and invoke `stack.sync_github(expected_head_sha: params.after)` for an org the attacker does not control [6](#0-5) . The same class of mismatch applies to `StatusHandler` (forging commit CI statuses on OrgB's commits) and `CheckSuiteHandler`/`PullRequest` handlers, all of which key off `params.repository.full_name` alone [7](#0-6) .

### Impact Explanation
This crosses a repository/organization trust boundary: possession of a *valid signature for organization A* is treated by the controller as authorization to identify "the org," but the handlers let the *payload* redirect the actual write target to organization B's stacks. Faking `push`/`status` events lets an attacker trigger `GithubSyncJob`/`sync_github` and inject fabricated commit statuses that continuous-delivery logic relies on to gate automatic deploys, which can cascade into an unauthorized deploy on a stack the attacker does not own. This aligns with the "Critical: unauthorized deploy/rollback" and "High: unauthenticated writes to stack state" impact classes in scope.

### Likelihood Explanation
Requires the attacker to be a legitimate holder of a webhook secret for at least one GitHub App/organization configured in the same shared Shipit instance (multi-tenant deployments configure several orgs under `github:` in `config/secrets.yml`, see `config/secrets.development.shopify.yml`) [8](#0-7) . No GITHUB_TOKEN, session, or ApiClient token is needed — only a raw POST to `/webhooks` with a body signed by any one configured org's secret. Likelihood is Medium-to-High in any multi-org Shipit deployment, and the analog is unrelated to DoS/rate-limiting/host-compromise scenarios excluded by scope.

### Recommendation
In `WebhooksController#verify_signature` / the `Handler` base class, require that `repository.owner.login` (the organization used to select and validate the webhook secret) equals the organization portion of `repository.full_name` before dispatching to any handler, rejecting the request (422) otherwise. Alternatively, bind repository resolution to the verified organization rather than trusting an unverified `full_name` string taken from the same untrusted payload.

### Proof of Concept
1. Attacker is an admin of "OrgA," which has a GitHub App installed and configured in this Shipit instance's `config/secrets.yml` (`github.OrgA.webhook_secret = S`).
2. Attacker computes `sha1=HMAC(S, body)` for a crafted JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "OrgA" },
    "full_name": "OrgB/victim-repo"
  }
}
```
3. POST to `/webhooks` with header `X-Github-Event: push` and `X-Hub-Signature: sha1=<computed>`.
4. `verify_signature` calls `Shipit.github(organization: "OrgA")` and validates the signature successfully [1](#0-0) .
5. `PushHandler#process` resolves `Repository.from_github_repo_name("OrgB/victim-repo")` and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` [6](#0-5)  — a forged sync/deploy trigger on an organization the attacker does not control, despite never possessing OrgB's webhook secret.

*Note: I was unable to fully inspect `status_handler.rb` and `check_suite_handler.rb` contents in this session (only located them via glob/grep), so I cannot cite their exact `process` bodies; based on the shared `Handler#repository_name`/`stacks` pattern used across all handlers, the same mismatch is expected to apply to them as well.*

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
