### Title
Per-organization webhook signature routing lets a caller with any single org's (or no) `webhook_secret` forge state-changing GitHub events for a different, unrelated repository - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` picks *which* `GitHubApp` (and therefore which `webhook_secret`) to verify a request against using an attacker-supplied field of the very same unauthenticated payload (`repository.owner.login` / `organization.login`), while the handlers that actually mutate state (`PushHandler`, PR handlers, etc.) key off a *different* field, `repository.full_name`. The organization whose credential authenticates the request is not bound to the repository that ends up being written.

### Finding Description
`Shipit::WebhooksController#verify_signature` resolves the signing app like this: [1](#0-0) 
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
```
`repository_owner` is derived from the request body itself: [2](#0-1) 

`Shipit.github(organization:)` looks up per-organization config from `secrets.github`, and `GitHubApp#verify_webhook_signature` **trivially returns `true` when no `webhook_secret` is configured for that resolved organization**: [3](#0-2) 
```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
```
`webhook_secret` is documented as optional per organization: [4](#0-3) 

Meanwhile, the code path that actually acts on the payload (queuing syncs, archiving/unarchiving review stacks, updating pull requests, etc.) resolves the target repository/stack from a **different** field of the same payload, `repository.full_name`: [5](#0-4) 
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
```
and `PushHandler` uses `stacks` to trigger `stack.sync_github(expected_head_sha: params.after)`: [6](#0-5) 

This creates an equality that is never enforced: `repository.owner.login` (used to pick the verifying `GitHubApp`/secret) ≠ `repository.full_name`'s owner (used to select the `Repository`/`Stack` that is actually mutated). In a multi-organization deployment (`docs/setup.md` "Using Multiple Github Applications", `config/secrets.development.shopify.yml`), if *any one* configured organization has no `webhook_secret` set (an explicitly supported/optional configuration), an unprivileged caller can:

1. Send a POST to `/webhooks` with `X-Github-Event: push`, no valid `X-Hub-Signature` (or any arbitrary one).
2. Set `repository.owner.login` (or `organization.login`) to the name of the org that has no `webhook_secret` configured — this makes `verify_signature` select that org's `GitHubApp`, whose `verify_webhook_signature` unconditionally returns `true`.
3. Set `repository.full_name` to `"OtherOrg/target-repo"` — a completely different, secret-protected organization's repository that has real Shipit stacks.
4. `PushHandler` resolves `Repository.from_github_repo_name("OtherOrg/target-repo")` and calls `stack.sync_github(expected_head_sha: <attacker-chosen sha>)` on every non-archived stack/branch match — with no signature check ever validated against `OtherOrg`'s actual secret.

### Impact Explanation
This allows an unauthenticated network caller to trigger unauthorized synchronization/deploy-adjacent state transitions (`sync_github`, review-stack `archive!`/`unarchive!`, pull-request/commit-status mutation) against a repository/organization whose webhook integrity was never actually checked, purely by picking a *different*, unsecured organization slot to satisfy the signature gate. This matches the listed High/Critical impact of "unauthorized deploy, rollback" — since `sync_github` with an attacker-chosen `expected_head_sha` and forced un-archival of review stacks directly drives the deploy pipeline without any verified GitHub authenticity.

### Likelihood Explanation
Requires: (a) a multi-org Shipit deployment (a documented, supported configuration) where at least one configured organization omits `webhook_secret` (explicitly "optional" per docs), and (b) knowledge of a public target repository's `full_name`. No GitHub App private key, no `ApiClient` token, no Shipit session, and no knowledge of any other organization's `webhook_secret` is required — only the name of the org without a secret, which is operator configuration, not a cryptographic secret. This is plausible in real deployments that mix low-trust demo/sandbox orgs (secret left blank for convenience) with production orgs behind the same Shipit instance.

### Recommendation
Bind the two fields together and fail closed:
- Verify the signature using the `GitHubApp` selected for the *same* organization that owns `repository.full_name` (not a caller-chosen alternate field), and reject if they disagree.
- Do not allow `verify_webhook_signature` to silently return `true` when `webhook_secret` is blank; instead, require `webhook_secret` to be present for every configured organization, or explicitly reject requests targeting repositories under organizations other than the one whose secret validated the payload.

### Proof of Concept
Given a `secrets.yml` with two organizations, one without a `webhook_secret`:
```yaml
production:
  github:
    OpenOrg:
      app_id: ...
      installation_id: ...
      webhook_secret:      # blank/optional
    SecureOrg:
      app_id: ...
      installation_id: ...
      webhook_secret: real-secret
```
Request:
```
POST /webhooks
X-Github-Event: push
X-Hub-Signature: sha1=deadbeef   # arbitrary, unverifiable

{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "OpenOrg" },
    "full_name": "SecureOrg/production-repo"
  }
}
```
- `verify_signature` computes `repository_owner == "OpenOrg"`, resolves `Shipit.github(organization: "OpenOrg")`, whose `webhook_secret` is blank ⇒ `verify_webhook_signature` returns `true` for any signature.
- Request proceeds to `PushHandler`, which resolves `Repository.from_github_repo_name("SecureOrg/production-repo")` and calls `sync_github(expected_head_sha: "<attacker-chosen sha>")` on its stacks — despite `SecureOrg`'s real `webhook_secret` never being checked.

Note: I was unable to fully verify in the available index whether `Repository.from_github_repo_name` or `stack.sync_github` apply any additional authorization check limiting cross-organization repository resolution; based on the code reviewed (`app/models/shipit/webhooks/handlers/handler.rb`, `app/models/shipit/webhooks/handlers/push_handler.rb`), no such secondary organization-binding check exists.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
