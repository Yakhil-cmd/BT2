### Title
Webhook signature verification keys off attacker-controlled `repository.owner.login` while handlers act on `repository.full_name`, letting a request "authenticated" for one GitHub org drive state changes for a different org's repository - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
In multi-organization deployments (explicitly documented and supported — see `docs/setup.md` "Using Multiple Github Applications" and `config/secrets.development.shopify.yml`), `WebhooksController#verify_signature` selects which `GitHubApp`/`webhook_secret` to verify the HMAC signature against based on `repository_owner`, a value read directly from the untrusted JSON body. Every event `Handler` in `app/models/shipit/webhooks/handlers/**`, however, resolves the actual `Repository`/`Stack` to mutate using a completely different, also attacker-controlled field: `repository.full_name`. These two identifiers are never cross-validated, so the "organization whose secret authenticated the payload" is not bound to "the repository that is actually written."

### Finding Description
`verify_signature` picks the verifying app config purely from the payload: [1](#0-0) [2](#0-1) 

`repository_owner` is taken from `params.dig('repository', 'owner', 'login')` — fully attacker-controlled JSON, not from any verified GitHub source. `Shipit.github(organization: ...)` then looks up that organization's app config and returns a `GitHubApp` used only for HMAC verification: [3](#0-2) 

Signature verification itself trivially passes if that specific organization has no `webhook_secret` configured — which the setup docs describe as optional per-organization: [4](#0-3) [5](#0-4) 

Meanwhile, once the request passes `verify_signature`, `WebhooksController#create` dispatches to handlers using the raw parsed body, not anything tied to the org used for verification: [6](#0-5) 

Every handler resolves the target `Repository`/`Stack` from a *different* field, `repository.full_name`, which is never checked against `repository.owner.login`: [7](#0-6) [8](#0-7) 

This means the binding the system relies on — "the org that authenticated the webhook signature" == "the org that owns the repository being mutated" — is never enforced. An attacker can craft a payload where `repository.owner.login` is set to an organization configured in this Shipit instance with no `webhook_secret` (or one whose secret is otherwise easy to satisfy), while `repository.full_name` points at a repository belonging to a different, security-sensitive organization that Shipit actually tracks (has a `Stack`/`Repository` record for). The signature check only validates against the "cheap" org's config (or is skipped entirely if that org has `webhook_secret: nil`), yet the event still gets dispatched and acted on for the real target repository.

### Impact Explanation
This breaks the "GitHub organization that authenticated the webhook vs. repository actually written" binding called out as an in-scope analog target. Depending on which handler is triggered for the spoofed `full_name`, an attacker can:
- Force `PushHandler`/`GithubSyncJob` to sync arbitrary refs/SHAs into an unrelated stack.
- Force `PullRequest::ClosedHandler` to archive a `review_stack` for a repository they don't control.
- Inject fabricated commit `Status`/`CheckSuite` events for arbitrary commits via `StatusHandler`/`CheckSuiteHandler`, which can influence `deployable_status`/merge gating used elsewhere in the engine.

Any of these constitute unauthorized state mutation of a stack/repository the attacker was never authorized to touch, satisfying the "unauthorized deploy/rollback/merge"-adjacent High-severity bar when the affected handler feeds into deploy or merge gating logic.

### Likelihood Explanation
The precondition is that the Shipit instance is configured for multiple GitHub organizations (a documented, supported configuration) and that at least one configured organization has no `webhook_secret` set — explicitly presented as optional in `docs/setup.md`. Given that precondition, the attack requires only sending an unauthenticated HTTP POST to `/webhooks` with a crafted JSON body containing mismatched `owner.login` / `full_name` values; no GitHub credentials, no Shipit session, and no legitimate webhook secret are needed. This is a plausible, realistic multi-tenant misconfiguration rather than a theoretical one, since the docs steer administrators toward per-org optional secrets.

### Recommendation
- Bind signature verification to the repository actually acted upon: derive the verifying organization from `repository.full_name`'s owner segment (or from the resolved `Repository`/`Stack`'s configured GitHub org), not from `repository.owner.login`/`organization.login` alone, and require they match.
- Do not allow `verify_webhook_signature` to trivially return `true` when a per-org secret is absent; require every configured organization to have a `webhook_secret`, or reject events for any org lacking one.
- Add a check that `repository.owner.login` (or `organization.login`) is consistent with the owner segment of `repository.full_name` before dispatching to handlers.

### Proof of Concept
1. Configure Shipit with two GitHub organizations in `secrets.yml`: `secure-org` (has `webhook_secret` set, hosts a tracked `Stack` for `secure-org/target-repo`) and `open-org` (no `webhook_secret`, per docs this is optional).
2. Attacker sends `POST /webhooks` with header `X-Github-Event: push` and body:
```json
{
  "repository": { "owner": { "login": "open-org" }, "full_name": "secure-org/target-repo" },
  "after": "<attacker chosen sha>",
  "ref": "refs/heads/master"
}
```
3. `verify_signature` calls `Shipit.github(organization: "open-org")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` regardless of the (even absent) `X-Hub-Signature` header.
4. `WebhooksController#create` dispatches the push handler, which resolves the target via `repository.full_name = "secure-org/target-repo"`, enqueuing `GithubSyncJob` against `secure-org`'s real, secured stack — despite the request never being authenticated by `secure-org`'s secret.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
