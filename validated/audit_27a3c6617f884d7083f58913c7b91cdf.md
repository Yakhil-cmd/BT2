### Title
CCMenu API endpoint bypasses ApiClient stack scoping, allowing a stack-scoped token to read any stack's deploy status - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::BaseController` enforces that a stack-scoped `ApiClient` (one with `stack_id` set) can only see the stack it was issued for, via the `stacks` helper. `Shipit::Api::CCMenuController` overrides `#stack` to bypass this scoping entirely, breaking the binding "stack a token authorises == stack a token touches."

### Finding Description
`ApiClient` records can optionally be scoped to a single stack: `belongs_to :stack, optional: true` [1](#0-0) . Every other API controller resolves the target stack through `BaseController#stack`, which filters through `#stacks`, restricting results to `current_api_client.stack_id` when the client is scoped: [2](#0-1) 

`CCMenuController`, however, defines its own `#stack` that ignores this scoping and resolves directly from the global `Stack` table using the attacker-controlled `params[:stack_id]`: [3](#0-2) 

`require_permission :read, :stack` only checks that the `ApiClient` has the `read:stack` permission bit; it never checks that the requested stack matches `current_api_client.stack_id` [4](#0-3) . So the equality that should hold — `current_api_client.stack_id == params[:stack_id]` (when the client is scoped) — is never enforced in this controller, unlike in every sibling controller that goes through `BaseController#stack`.

### Impact Explanation
Any holder of a legitimately-issued, narrowly-scoped `ApiClient` token (e.g. one created for a single team's CCMenu/CI status badge, scoped to Stack A) can pass an arbitrary `stack_id` to `GET /api/ccmenu/:stack_id` and read the deploy/rollback status, lock state, and last build info of any other stack in the Shipit instance (Stack B, C, …) that they were never authorized to see. This is an authorization-scope escalation: a credential meant to authorize access to one stack ends up touching all stacks, matching the "unauthenticated/unauthorized read of stack state" High-impact category.

### Likelihood Explanation
The only prerequisite is possession of a valid, but stack-scoped, `ApiClient` token with `read:stack` permission — a routine credential handed out for CI dashboards/CCMenu integrations. The bypass itself requires no special conditions: simply supplying a different `stack_id` in the URL, since `CCMenuController#stack` performs no ownership check.

### Recommendation
Remove the custom `#stack` override in `CCMenuController`, or make it consistent with `BaseController#stacks`, e.g.:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
so that a stack-scoped `ApiClient` can only ever resolve to its own `stack_id`.

### Proof of Concept
1. Create an `ApiClient` scoped to Stack A (`stack_id: A.id`) with permission `read:stack`.
2. Authenticate as that client and issue `GET /api/ccmenu/:stack_id?token=<token>` with `stack_id` set to Stack B's param instead of A's, as done in the existing test harness pattern: [5](#0-4) 
3. Because `#stack` calls `Stack.from_param!(params[:stack_id])` unscoped, the response returns Stack B's `lastBuildStatus`, `lastBuildLabel`, lock state, etc., even though the token was only ever supposed to authorize Stack A.
