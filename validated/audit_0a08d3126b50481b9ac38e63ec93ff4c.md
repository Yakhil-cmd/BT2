Found the analog. In `WebhooksController#verify_signature`, the HMAC signature computed by `github_app.verify_webhook_signature` is verified against the **whole raw request body**, but the `github_app` instance itself — and thus which `webhook_secret` is used to verify it — is selected using `repository_owner`, a value read **from the unverified JSON body** (`params.dig('repository', 'owner', 'login')` or `params.dig('organization', 'login')`), before the signature has been checked.

### Title
Webhook signature verified against attacker-chosen organization's secret, allowing cross-repository event forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController` picks which GitHub App/organization's `webhook_secret` to use for HMAC verification based on a field inside the *unverified* payload (`repository.owner.login` / `organization.login`), then verifies the signature using that attacker-selected secret before trusting the rest of the payload for `repository.full_name` used to look up the target `Stack`/`Repository`.

### Finding Description
`before_action :check_if_ping, :drop_unhandled_event, :verify_signature` runs `verify_signature` before parsing/trusting the body for anything else, but `verify_signature` itself derives the signing key from the body: [1](#0-0) [2](#0-1) 

`repository_owner` is read directly from `params` (the raw JSON body, not signed by anything at this point) and is used to select which configured GitHub organization's `webhook_secret` is used for verification via `Shipit.github(organization: repository_owner)`. If an attacker controls a webhook secret for **any** one organization configured in the multi-tenant `Shipit.github(organization:)` registry (e.g., they operate their own low-trust GitHub App/org onboarded to the same Shipit instance, a common multi-org deployment pattern per `config/secrets.*.yml` showing multiple orgs each with their own `webhook_secret`), they can sign a payload with *their own* organization's secret while setting `repository.owner.login`/`organization.login` to their own org (satisfying `verify_signature`), but crafting `repository.full_name` inside the same payload to reference a stack/repository belonging to a **different, unrelated organization** that they don't otherwise have write access to.

Because `verify_signature` only checks the signature validity, and the field used to select the verification key (`repository_owner`) is not cryptographically bound to the field later used to resolve the target entity (`repository.full_name`, consumed downstream in `Handlers::Handler#repository_name` / `Repository.from_github_repo_name`), the two fields can diverge: [3](#0-2) 

This breaks the intended binding: `organization that authenticated (signed) the webhook == organization whose repository/stack is acted upon`. Handlers such as `PushHandler`, `StatusHandler`, `CheckSuiteHandler`, and the pull-request handlers (`OpenedHandler`, `ClosedHandler`, etc.) all resolve their target `Repository`/`Stack` purely from `repository.full_name`/`organization.login` inside the payload: [4](#0-3) [5](#0-4) 

### Impact Explanation
An attacker who legitimately controls one tenant/organization's webhook secret on a multi-org Shipit deployment (a realistic, documented setup — see `config/secrets.development.shopify.yml` showing multiple independent orgs each with their own `webhook_secret`) can forge webhook events attributed to a **different** organization's repository/stack that they are not authorized to write to. Depending on the handler this enables: injecting fake `push` events to trigger `GithubSyncJob`, forging `status`/`check_suite` results to flip a commit's CI status to `success` (`Handlers::StatusHandler`/`CheckSuiteHandler`) and thereby make an otherwise-blocked commit `deployable?`, or manipulating pull-request/review-stack lifecycle (archiving/creating review stacks) for repositories outside the attacker's own org. Forged CI status combined with continuous deployment (`continuous_deployment: true` on a stack) can lead to an unauthorized deploy of attacker-influenced state — this is a cross-repository/cross-organization write achieved purely by exploiting a credential-binding gap, not by needing the target org's own webhook secret.

### Likelihood Explanation
Requires the attacker to control at least one organization's webhook secret in a multi-tenant Shipit instance (a supported and documented configuration), and knowledge/guessing of another target org's repository naming — no access to the target org's actual secret, GitHub account, or Shipit session is required. This is a moderate-likelihood, configuration-dependent issue: it only manifests on deployments serving multiple organizations with independently held webhook secrets, which `Shipit.github(organization:)` and the secrets templates explicitly support.

### Recommendation
Bind the field used to select the verification key to the field used to resolve the acted-upon entity. Concretely, after verifying the signature with the organization derived from `repository_owner`, re-validate that `repository.full_name`'s owner segment matches `repository_owner` (or resolve the target `Repository`/`Stack` using `repository_owner` directly rather than re-parsing `repository.full_name` independently in each handler), rejecting the webhook if they diverge.

### Proof of Concept
1. Deploy Shipit configured with two organizations, `attacker-org` (attacker holds `webhook_secret`) and `victim-org` (unrelated), per the multi-org `github:` config shown in `config/secrets.development.shopify.yml`.
2. Craft a JSON payload: `{"repository": {"owner": {"login": "attacker-org"}, "full_name": "victim-org/victim-repo"}, "sha": "<commit>", "state": "success", ...}`.
3. Compute `X-Hub-Signature: sha1=<hmac(attacker-org's webhook_secret, payload)>`.
4. POST to `/webhooks` with `X-Github-Event: status`. `verify_signature` calls `Shipit.github(organization: 'attacker-org')` (derived from `repository.owner.login`) and succeeds, since the attacker's own secret was used to sign it.
5. `Handlers::StatusHandler` (via `Handler#repository_name` → `payload.dig('repository', 'full_name')`) resolves and updates the commit status for `victim-org/victim-repo`, a repository the attacker does not control.

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```
