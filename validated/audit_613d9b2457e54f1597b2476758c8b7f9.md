### Title
Accrual value overflow permanently freezes an oversized high-utilization market - ([File: common/src/rates/simulate.rs](common/src/rates/simulate.rs))

### Summary
A market can reach a state where `scaled_amount * index` no longer fits in `i128`, causing every subsequent accrual to panic. Because all principal pool mutations synchronize interest before checking liquidity or applying the user action, the affected market permanently rejects repayment, withdrawal, liquidation, bad-debt cleanup, and further index updates. The repository contains a reproduction demonstrating this condition below the borrow-index cap. [1](#0-0) [2](#0-1) 

### Finding Description
Each accrual step first unscales total borrowed and supplied shares using `scaled_to_original`, which performs `shares * index / RAY`. [3](#0-2)  Although intermediate multiplication can be widened to `I256`, the final quotient must still fit into `i128`; otherwise `mul_div_half_up` panics with `MathOverflow`. [4](#0-3) [5](#0-4) 

The borrow-index ceiling is applied only after these total-value computations, so it does not prevent the absolute debt or supply value from crossing the representable `i128` domain. [6](#0-5)  `global_sync` runs this step for every elapsed chunk and stores the resulting indexes and revenue shares. [7](#0-6) [8](#0-7) 

Once the current `borrowed * borrow_index / RAY` or `supplied * supply_index / RAY` exceeds `i128::MAX`, the next synchronization fails before any index cap, rate cap, reserve check, or user-operation guard can execute. [9](#0-8)  The pool loads and synchronizes the market before each operation through `synced_market`, so the failure propagates to withdrawals and repayments rather than being confined to the public index updater. [10](#0-9) 

### Impact Explanation
The accepted impact is permanent freezing of funds: suppliers cannot withdraw, borrowers cannot repay, liquidators cannot liquidate, and index synchronization cannot advance the market. [11](#0-10) [12](#0-11) 

The in-repository proof explicitly reaches `MATH_OVERFLOW` before `MAX_BORROW_INDEX_RAY`, then verifies that both a withdrawal and a repayment fail with the same error. [13](#0-12)  This is therefore not merely a bounds issue in an off-chain simulation; it is a persistent contract-state DoS affecting all users of the market.

### Likelihood Explanation
Likelihood is moderate rather than high because the attacker must establish an unusually large market and sustain high utilization long enough for index growth to cross the value ceiling. The reproduction uses one billion whole tokens at 18 decimals, 98% utilization, and repeated yearly index updates on a high-rate curve. [14](#0-13) 

A single sufficiently funded unprivileged account can construct the precondition through `Controller::supply` with the target asset and separate collateral legs, followed by `Controller::borrow` for approximately 98% of the target market, and then permissionless `update_indexes` calls as ledger time advances. [15](#0-14) [16](#0-15)  No privileged parameter change, leaked key, oracle manipulation, or contract upgrade is required.

### Recommendation
Make accrual resilient to unrepresentable absolute totals before evaluating utilization or interest. In particular, `accrue_step` should avoid materializing `borrowed * index` and `supplied * index` as unbounded `i128` values, or explicitly clamp and settle the market when the index reaches a safe value-derived ceiling. [17](#0-16) 

At minimum, update the borrow index through a saturating or widened representation and perform utilization/reward calculations on the capped result so `MAX_BORROW_INDEX_RAY` is always reached before value decoding can panic. [6](#0-5)  Add invariant coverage asserting that an admitted market can always execute at least `repay`, `withdraw`, `liquidate`, and `update_indexes` after arbitrary valid accrual, rather than only documenting that value overflow may precede the index cap. [18](#0-17) 

### Proof of Concept
The existing integration test is a contract-level reproduction:

1. Create an 18-decimal `BIG18` market and a collateral market.
2. Supply `1_000_000_000 * 10^18` base units of `BIG18`.
3. Supply sufficient collateral and borrow `98%` of the `BIG18` pool.
4. Advance ledger time and call `update_indexes` repeatedly.
5. `update_indexes` eventually panics with `MATH_OVERFLOW` while `borrow_index < MAX_BORROW_INDEX_RAY`.
6. Subsequent `withdraw` and `repay` calls panic with `MATH_OVERFLOW` because both synchronize the same market first.

The exact implementation is in `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap`. [19](#0-18)

/// The cliff. A billion whole tokens is `1e36` raw ray; the value ceiling is
/// `i128::MAX`, 170 times that. At the XLM curve's steep segment the index
/// grows past 170x in a few years, and the next accrual panics inside
/// `scaled_to_original`. Every verb accrues first, so the market freezes:
/// no repay, no withdraw, no liquidation. The index cap never engages.
#[test]
fn a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap() {
    let mut t = LendingTest::new()
        .with_market(big("BIG18", 18, xlm_curve()))
        .with_market(col())
        .with_max_utilization_disabled_all_markets()
        .build();
    lift_caps(&t, "BIG18", 18);
    lift_caps(&t, "COL", 7);
    let principal = BILLION * 10i128.pow(18);
    t.supply_raw(BOB, "BIG18", principal);
    let debt = principal / 100 * 98;
    t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
    t.borrow_raw(ALICE, "BIG18", debt);

    let mut years = 0u32;
    let failure = loop {
        years += 1;
        assert!(
            years <= 40,
            "no cliff within 40 years; the bound in docs/reference/formulas.md is wrong"
        );
        t.advance_time(YEAR_SECS);
        if let Err(e) = t.try_update_indexes_for(&["BIG18"]) {
            break e;
        }
    };
    let failed: Result<(), soroban_sdk::Error> = Err(failure);
    assert_contract_error(failed, errors::MATH_OVERFLOW);
    let last = book(&t, "BIG18");
    assert!(
        last.borrow_index < MAX_BORROW_INDEX_RAY,
        "the index cap did not engage before the value overflow"
    );
    // The market is frozen: exits and repayments accrue first and hit the same panic.
    assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
    assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);

/// Computes `x * y / d` rounded half up. Requires `x >= 0`, `y >= 0`, and `d > 0`; a
/// `debug_assert` checks this in debug builds. Panics with `GenericError::DivisionByZero` if
/// `d == 0`, and with `GenericError::MathOverflow` if any other precondition is violated or if
/// the result does not fit in `i128`.
pub fn mul_div_half_up(env: &Env, x: i128, y: i128, d: i128) -> i128 {
    // The zero check runs first so debug and release builds agree on a zero

        x >= 0 && y >= 0 && d > 0,
        "mul_div_half_up: non-negative x, y and positive d"
    );
    try_mul_div_half_up(env, x, y, d)
        .unwrap_or_else(|| panic_with_error!(env, GenericError::MathOverflow))
}

pub(crate) fn global_sync(env: &Env, cache: &mut Cache) {
    if !cache.needs_accrual() {
        return;
    }

    let mut remaining = cache.elapsed_ms();
    while let Some(nonzero) = NonZeroU64::new(remaining) {
        let chunk = nonzero.get().min(MAX_COMPOUND_DELTA_MS);
        accrue_chunk(env, cache, chunk);
        remaining = remaining.saturating_sub(chunk);
    }

    cache.mark_accrued();
}

        cache.supplied(),
        cache.borrow_index(),
        cache.supply_index(),
        delta_ms,
    );

    cache.set_borrow_index(step.borrow_index);
    cache.set_supply_index(step.supply_index);

The token-to-RAY maximum is also the admitted cap maximum. Accrued position
values and market totals must independently fit the RAY domain; valid caps and
bounded indexes do not guarantee that future accrual fits. Value overflow can
occur before the index ceiling and block repayment/withdrawal because those
operations accrue first. At the borrow-index ceiling, further accrual produces
