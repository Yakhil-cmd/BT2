### Title
Crash-loop on stale `aa_triggers` queue entry when `handlePrimaryAATrigger()` finds no cached stable unit - ([File: aa_composer.js])

### Summary
`aa_triggers` is a persisted SQL queue table: rows are inserted transactionally when an MCI stabilizes [1](#0-0) , and are re-processed both after every stabilization and unconditionally on every node startup via `aa_composer.handleAATriggers()` [2](#0-1) . This is structurally identical to erigon's `PersistentBlockCollector`: a durable, restart-surviving queue that is replayed from disk on every boot.

### Finding Description
`handlePrimaryAATrigger()` processes a queued trigger inside an open DB transaction (`BEGIN` at the top). It first deletes the queue row, then unconditionally dereferences the in-RAM cache `storage.assocStableUnits[unit]` and throws a hard, uncaught `Error` if the unit isn't found there — before the transaction is committed: [3](#0-2) 

Because the `throw` happens inside nested async DB callbacks, it becomes an uncaught exception. `network.js` deliberately re-throws on `uncaughtException` to force a full process crash ("crash the process to avoid ending up in an inconsistent state"): [4](#0-3) 

Since the throw happens before `COMMIT`, the `DELETE FROM aa_triggers` is rolled back with the aborted connection, so the row survives in the database. On restart, `startRelay()` calls `aa_composer.handleAATriggers()` again "in case anything's left from the previous run" [2](#0-1) , which re-reads the same `aa_triggers` row and hits the identical `throw Error("handlePrimaryAATrigger: unit ... not found in cache")` again — an unconditional, permanent crash-loop, exactly the failure mode the erigon `BlockCollector` fix addresses (persisted queue + panic on inconsistency = process can never come back up on its own).

The relevant cache (`storage.assocStableUnits`) is populated only in RAM at startup (`initStableUnits`) and mutated during `markMcIndexStable`/`resetMemory`; `forgetUnit()` even asserts it must never delete a still-"stable" entry [5](#0-4) . Any code path (memory reset after a write error, a race between `resetMemory()` triggered by `writer.js`'s error-handling and `handleAATriggers()` being invoked concurrently, or the unit being pruned/forgotten from cache before its `aa_triggers` row is drained) that leaves a queued `aa_triggers` row pointing at a unit no longer present in `assocStableUnits` reproduces this permanently.

Notably, `writer.saveJoint()` calls `storage.resetMemory(conn)` on any write error [6](#0-5)  (typo aside, see citation below) which clears and re-populates `assocStableUnits` from disk while `aa_triggers` rows for units that are only present as recently-inserted-but-not-yet-committed remain in the table, creating a window where the association between the persisted queue and the RAM cache can diverge. [7](#0-6) 

### Impact Explanation
This is a permanent denial-of-service of the whole node (full/hub) process: once a stale `aa_triggers` row exists whose target unit is missing from `storage.assocStableUnits`, every process restart re-triggers the identical crash immediately during `startRelay()`'s mandatory `handleAATriggers()` call, before the node can accept traffic or resync. The node can never self-heal because the offending queue row is never cleared (the transaction that would delete it never commits). This matches the "node unable to confirm new units" / crash-loop class explicitly called out as an acceptable analog impact.

### Likelihood Explanation
Reaching this code path only requires posting an ordinary unit that triggers an AA (any unprivileged sender can send funds to an AA address, which is the normal way AAs are invoked) combined with a state where the node's in-memory `assocStableUnits` cache and the durable `aa_triggers` table go out of sync (e.g., via the `resetMemory()` path after any transient write error concurrent with trigger processing). The exact reliable reproduction sequence needing a guaranteed inconsistency between the RAM cache and DB queue could not be fully confirmed from static analysis alone — the concurrency window between `resetMemory()`, `markMcIndexStable()`, and `handleAATriggers()` calls would need dynamic/runtime verification to pin down a deterministic trigger sequence.

### Recommendation
- In `handlePrimaryAATrigger()`, do not `throw` on a missing `assocStableUnits[unit]` entry inside an open, uncommitted transaction. Instead, roll back gracefully, log a warning, and either re-derive the missing unit props from the DB (already available via `conn`) or safely delete/skip the stale `aa_triggers` row so it does not get reprocessed forever.
- Ensure the `DELETE FROM aa_triggers` and any cache-consistency check happen atomically with respect to `COMMIT`, so a crash never leaves an un-processable row behind indefinitely.
- Audit all call sites that mutate/reset `storage.assocStableUnits` (`resetMemory`, `resetStableUnits`) for races with in-flight `handleAATriggers()` invocations.

### Proof of Concept
Exact conditions producing the RAM/DB divergence require further dynamic testing; conceptually:
1. An unprivileged unit poster sends funds to an AA address, causing an `aa_triggers` row to be inserted when the triggering unit's MCI stabilizes [8](#0-7) .
2. Before `handlePrimaryAATrigger()` for that row completes and commits, a concurrent write error elsewhere in the node triggers `storage.resetMemory(conn)` [7](#0-6) , which clears and repopulates `assocStableUnits` from the DB.
3. If the repopulation excludes the still-queued unit for any reason (e.g., it was rolled back from `units` too, or a timing edge case in `initStableUnits`), the next invocation of `handlePrimaryAATrigger()` for that queue row hits `if (!objUnitProps) throw Error(...)` [9](#0-8) , crashing the process before the `DELETE FROM aa_triggers` commits.
4. On restart, `startRelay()`'s `await aa_composer.handleAATriggers();` [2](#0-1)  immediately reprocesses the same row and crashes again — a permanent crash-loop.
