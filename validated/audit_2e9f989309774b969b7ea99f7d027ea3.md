### Title
Permanent market freeze via i128 overflow in RAY-scaled accrual — unrecoverable `MathOverflow` panic blocks all market operations - (File: common/src/rates/index.rs via contracts/pool/src/interest.rs)

### Summary
`accrue_step` (used by `global_sync`, which every pool market verb calls first) computes the accrued borrow value as a RAY-fixed-point product of `borrowed` shares and `borrow_index`. When `borrowed * borrow_index` exceeds `i128::MAX`, the multiplication panics with `GenericError::MathOverflow`. Because the panic happens inside `global_sync` before any state mutation — and before `last_timestamp` advances — every subsequent call to the market hits the same panic. The market is permanently frozen: suppliers cannot withdraw, borrowers cannot repay, and liquidators cannot liquidate. This is the on-chain analog of CVE-2025-43343's "unexpected process crash": an unchecked arithmetic growth path that terminates execution and, unlike a transient crash, permanently bricks a stateful contract holding user funds.

### Finding Description
- `Cache::load` → `interest::global_sync` runs at the top of every market mutation (`supply`, `withdraw`, `borrow`, `repay`, `seize`, `flash_loan`, `run_batch`). `contracts/pool/src/interest.rs:20-33` chunks elapsed time into ≤1-year windows and calls `accrue_chunk`, which calls `common::rates::accrue_step` with the live `borrowed`/`borrow_index`.
- Inside `accrue_step`, `scaled_to_original(borrowed, borrow_index)` computes `borrowed * borrow_index / RAY` in RAY fixed point. The underlying `mul_div` helpers panic with `MathOverflow` when `borrowed * borrow_index` overflows `i128` — `borrowed` alone can approach `i128::MAX / RAY` only via extreme supply, but the product `borrowed_raw * borrow_index_raw` overflows far earlier since `borrow_index` grows multiplicatively with utilization.
- The borrow-index cap (`MAX_BORROW_INDEX_RAY`) does not save the market: the harness test `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` in `tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:316-360` demonstrates empirically that the RAY-value ceiling is reached before the index cap engages, after which `try_update_indexes_for`, `try_withdraw_raw`, and `try_repay` all return `MATH_OVERFLOW`. The comment states plainly: "the market freezes: no repay, no withdraw, no liquidation."
- The panic path requires no privileged role: an unprivileged address supplies to a market (`controller::supply` → `pool` ops), another unprivileged address (or the same attacker with collateral in a second market) borrows to high utilization (`controller::borrow`), and time does the rest. Each unprivileged caller's `update_indexes` call then deterministically panics.

### Impact Explanation
Permanent freezing of user funds and protocol insolvency. Once the overflow threshold is crossed, the affected `(hub, token)` book is bricked forever: supplier principal and accrued yield are unwithdrawable, outstanding debt is unrepayable and unliquidatable, and `recapitalize`/`clean_bad_debt` paths that also run `global_sync` are dead too. Since Soroban contract storage cannot be rolled back by an unprivileged party, this is a permanent loss condition, not a temporary DoS.

### Likelihood Explanation
Reaching the cliff requires a very large supplied/borrowed value relative to the asset's decimals (the harness fixture uses ~10²⁷ raw units of an 18-decimal asset at ~98% utilization sustained for years, i.e., index growth of ~170×). For realistic TVL this is a tail risk rather than an imminent one — but it is driven entirely by unprivileged `supply`/`borrow` calls plus elapsed time, requires no governance misconfiguration beyond permissive caps, and there is no recovery path once crossed, because the fix would require skipping or saturating accrual, which the current code does not do. Rated Medium: high-severity impact gated by an extreme-but-possible market state.

### Recommendation
Make accrual saturate rather than panic at the RAY-value ceiling: in `accrue_step`, detect when `borrowed * borrow_index` would overflow `i128` (use `mul_div_floor_saturating`, already present in `common/src/math/fp_core.rs` and used by `update_supply_index`) and clamp the growth — e.g., stop growing `borrow_index` once the scaled value is near the ceiling, or cap `borrowed * borrow_index` at `i128::MAX` so subsequent calls remain no-ops instead of panicking. Alternatively, enforce a hard supply cap `max_cap_for_decimals`-style bound scaled so that `borrowed * MAX_BORROW_INDEX_RAY` can never overflow `i128`, ensuring the index cap is always reached before the value ceiling.

### Proof of Concept
Encoded in the repo's own harness test `tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:321-360`:

1. Unprivileged `BOB` calls `supply` with `principal = BILLION * 10^18` on an 18-decimal market (`lift_caps` removes supply caps; note this fixture itself acknowledges caps must be lifted, so severity depends on configured caps).
2. Unprivileged `ALICE` supplies collateral in a second market and calls `borrow` for 98% of `principal` — sustained max utilization.
3. Time advances in 1-year steps. After index growth ≈170×, `try_update_indexes_for(["BIG18"])` returns `MATH_OVERFLOW`.
4. From that point: `try_withdraw_raw(BOB, "BIG18", 1)` → `MATH_OVERFLOW`; `try_repay(ALICE, "BIG18", 1.0)` → `MATH_OVERFLOW`. The test asserts `last.borrow_index < MAX_BORROW_INDEX_RAY`, proving the value ceiling — not the designed index cap — is what bricked the market, with no unprivileged path to recover the locked funds.

Uncertainty: whether production supply caps keep `borrowed` small enough that the index cap always engages first is a deployment-parameter question; the code provides no invariant enforcing it, so the freeze remains reachable whenever caps are set high relative to `i128` headroom.
