### Title
Position NFT minted/transferred to a contract that cannot move it permanently freezes the whole lending position - (File: contracts/position-nft/src/contract.rs)

### Summary
`PositionNft` inherits the OpenZeppelin `stellar-tokens` non-fungible base and mints via `Enumerable::sequential_mint`, which performs a bare ownership write with no verification that the recipient can ever move the token. The controller's `create_account_with` mints the NFT directly to the `owner`/`caller` address with no check that it is an account that can later authorize `transfer`. If the recipient is a contract that has no entrypoint which calls `transfer`/`transfer_from` (or performs invoker auth for them), the position NFT — which *is* the lending position, since the controller resolves ownership exclusively via `owner_of` — is stuck forever, permanently freezing all supplied collateral and any claimable yield held by that account.

### Finding Description
Every controller account is exactly one token in the `PositionNft` collection, and the controller stores no owner address; it calls `owner_of(account_id)` on the NFT contract for every owner check [1](#0-0) . When a user calls `Controller::supply` with `account_id = 0` (the create sentinel), `create_account_with` calls `nft_mint_call(env, &nft, owner)` and the returned token id becomes the account id [2](#0-1) .

`PositionNft::mint` executes `Enumerable::sequential_mint(e, &to)`, the OZ non-safe mint path: it writes `Owner(token_id)` and `Balance(to)` but never checks whether `to` is capable of later authorizing a transfer [3](#0-2) . Likewise, the inherited `transfer`/`transfer_from` entrypoints move the token to any `to` address with no receiver check [4](#0-3) .

On Soroban, moving the NFT out of a contract address requires that contract to authorize the `transfer` call (either by being the direct invoker of a wrapper entrypoint, or via its own auth logic). A contract that holds the token but exposes no such path can never satisfy `from.require_auth()` inside the OZ `transfer` implementation, so the token — and therefore the entire account, its collateral, and its accrued supply yield — is frozen permanently. There is no admin recovery: `burn` is controller-only and only invoked when an account is emptied, and `transfer` requires the holder's auth [5](#0-4) . The protocol even documents that "nothing in the controller changes on transfer: the next controller call resolves the new holder," confirming that whoever/whatever holds the token fully controls the position [6](#0-5) .

### Impact Explanation
Permanent freezing of user funds. All supplied collateral credited to the stuck account can never be withdrawn (every mutating controller entrypoint resolves the caller through `nft_try_owner_of_call`/`require_auth` on the NFT owner), and unclaimed supply yield/revenue accruing to the account's shares is likewise unclaimable. Borrowed debt on such an account is also frozen (repay/liquidate can still operate on it, but the owner can never manage it). This matches the "permanent freezing of funds / freezing of unclaimed yield" acceptance criteria and mirrors the source report's Medium severity.

### Likelihood Explanation
Low-to-medium. It requires a user to interact through a contract (multisig/smart-wallet/router contract, or a contract explicitly transferring the NFT to a contract address) that lacks an NFT-management entrypoint. This is a self-inflicted scenario rather than something an attacker can force on a victim — but it is precisely the scenario the accepted Medium source report covers, and contract wallets are a normal Stellar usage pattern. No privileged action is needed: any unprivileged caller reaches `mint` via `supply(account_id = 0)` and reaches `transfer` directly on the NFT contract.

### Recommendation
There is no `onERC721Received`-style receiver callback in the Soroban NFT standard, so `_safeMint` cannot be adopted verbatim. Practical mitigations:
- In `PositionNft::mint` and in the `transfer`/`transfer_from` overrides, document or enforce the risk (e.g., a two-step "claim" flow where the recipient must authorize before the token binds, or a rescue path).
- Alternatively, give the controller a limited recovery entrypoint (e.g., governance-timelocked `rescue_position_nft`) so a position provably held by an incapable contract can be migrated, rather than frozen forever.

### Proof of Concept
1. Deploy `PositionNft` with `controller` set; deploy a minimal contract `DumbWallet` that can invoke `Controller::supply` with its own address as `caller` (granting invoker auth) but exposes no entrypoint that calls `PositionNft::transfer`/`transfer_from`.
2. `DumbWallet` calls `Controller::supply(caller = DumbWallet, account_id = 0, spoke_id = 1, assets = [(hub, usdc, amount)])`. `create_account_with` mints token id `N` to `DumbWallet` via `nft_mint_call` [7](#0-6) .
3. `owner_of(N) == DumbWallet`; `PositionNft::transfer(from = DumbWallet, ...)` can never succeed because no contract path exists to authorize `from.require_auth()` — there is no signature mechanism by which an external party can authorize for a contract address.
4. `Controller::withdraw(caller = DumbWallet, account_id = N, ...)` fails: the owner check resolves `owner_of(N) = DumbWallet` and requires that address's auth, which cannot be produced. The USDC collateral is permanently locked in the pool under account `N`.

    pub fn mint(e: &Env, to: Address) -> u32 {
        controller(e).require_auth();
        renew_instance(e);
        let token_id = Enumerable::sequential_mint(e, &to);
        // sequential_mint writes Owner/Balance at the network minimum TTL; lift
        // them to the user window so a new position does not archive early.
        extend_user_persistent_ttl(e, &to, token_id);
        token_id
    }
