## Analysis

The reported CVE (`python-jwt`/`jwcrypto`) is a canonicalization-confusion bug: two different serializations of the "same" signed data are treated as equivalent by the verifier, so an attacker can substitute forged claims that verify correctly against a signature computed over different bytes.

`ocore` has a structurally identical flaw in its custom canonical serializer used for **all address/definition/unit/message hashing and signing**.

### Root cause [1](#0-0) 

`getSourceString()` builds a flat token stream by recursively walking an object/array and pushing type-tagged tokens (`"s"`,`"n"`,`"b"`,`"["`,`"]"`) for strings/numbers/booleans/arrays. Object values, however, get **no wrapping delimiter at all** — for an object, the function simply pushes each sorted `key` token followed directly by the token stream of its value:

```js
keys.forEach(function(key){
    arrComponents.push(key);
    extractComponents(variable[key]);
});
```

Because objects have no start/end marker (unlike arrays, which are wrapped in `'['`/`']'`), the flattened token stream of a nested object is indistinguishable from the flattened stream of a sibling key at the parent level. Concretely:

```
A = { a: { b: "c", d: "e" } }
B = { a: { b: "c" }, d: "e" }
```

Both serialize to the identical token stream `[a, b, s, c, d, s, e]` → identical string `"a\x00b\x00s\x00c\x00d\x00s\x00e"`, hence identical SHA-256 hash and identical signature-message bytes — even though `A` and `B` are semantically different objects.

### Where this is exploitable

`getSourceString` (not the newer `getJsonSourceString`) is the function used to compute:

- Address chash: [2](#0-1) 
- Unit hash-to-sign (pre-JSON-format units): [3](#0-2) 
- Signed-message hash-to-sign (pre-JSON-format): [4](#0-3) 

The address chash is checked for equality — not for full re-validation of definition semantics — the moment a definition is *first revealed* for an address: [5](#0-4) 

The identical pattern (chash equality only) recurs in:
- `signed_message.js` author/definition binding: [6](#0-5)  and [7](#0-6) 
- Shared-address creation: [8](#0-7) 
- Nested `["address", ...]` definitions during authentication: [9](#0-8) 

Several definition ops accept exactly the kind of multi-key object args needed to build a colliding pair, e.g. `weighted and` / `r of set` whose args are `{required, set}` objects whose `set` elements are themselves `{value, weight}` objects — [10](#0-9) . This is precisely the "object nested inside object, redistributable across levels" shape that produces token-stream collisions.

### Title
Address/definition and signed-message hash collision via missing object-boundary delimiter in `getSourceString` enables authentication bypass (chash forgery) - (File: `string_utils.js`)

### Summary
`getSourceString()` (used by `object_hash.getChash160`/`getHexHash`/`getUnitHashToSign`/`getSignedPackageHashToSign` for non-JSON-versioned data) canonicalizes objects by concatenating `key, value-tokens` pairs with **no wrapper marking the start/end of the object**, unlike arrays which are bracket-delimited. Because bare object keys and the bare intermediate tokens produced by nested objects look identical, two structurally different objects can produce the exact same token stream and therefore the exact same SHA-256 hash / chash / hash-to-sign — the same class of bug as CVE-2022-39227 (mixing representations so the verifier hashes different logical content than what is actually used).

### Finding Description
For any two objects `A = {k: {k1:v1, k2:v2}}` and `B = {k: {k1:v1}, k2:v2}`, `getSourceString(A) === getSourceString(B)` because object serialization never emits a boundary token — see [11](#0-10) . Since `getChash160` (address derivation) and `getUnitHashToSign`/`getSignedPackageHashToSign` (message/unit signing) route through this function for definitions and messages not using the JSON-string format, an attacker can construct two definitions with the *same op name* but a *different, redistributed args shape* (e.g. a `weighted and`/`r of set` definition whose nested `{value, weight}` sub-object keys are moved to be siblings of `required`/`set`) that hash to the identical `chash160`, i.e., to the identical Obyte address, while representing completely different (and differently satisfiable) spending conditions.

### Impact Explanation
An address's authorization rule is *whatever definition first hashes to that chash* (`validateDefinition`'s `ifDefinitionNotFound` branch just checks `getChash160(arrDefinition) === definition_chash`, then accepts it permanently as the address's rule). If an attacker can craft a weak/attacker-controlled colliding definition (e.g., satisfiable by the attacker's own key) that hashes to the same chash as the definition the legitimate owner intends to use, and gets it recorded first (as author of any unit spending from that address, in a signed_message, or in a shared-address announcement), the attacker's weak definition becomes "the" definition for that address. Funds later sent to that address (believing it is protected by the strong/multisig definition) can then be spent by the attacker under their colliding weak definition — unauthorized spending / authentication bypass, CWE-290, matching the severity of the reported analog.

### Likelihood Explanation
Reachable by any unprivileged actor who can post a unit or `signed_message`/shared-address message with a `definition` field — no special privileges are required. The attacker only needs to find one concrete colliding pair of well-formed definitions (constrained by the op grammar in `definition.js`), which is a search/engineering problem, not a cryptographic one, since the collision is deterministic and not probabilistic (it's a structural equivalence, not a hash-brute-force).

### Recommendation
Fix `getSourceString` (and any other place relying on delimiter-less object serialization) to add an explicit, unambiguous boundary marker around object serialization (e.g., wrap object token streams the same way arrays are wrapped with `'['`/`']'`, or prefix every key with a type tag distinct from value type tags), and add regression tests asserting that no two structurally different JS objects can produce equal `getSourceString`/`getChash160` output. Since this affects address/definition chash and legacy unit/message signing, any fix must be versioned/mci-gated exactly like other consensus-affecting hash changes (`getJsonSourceString`, `aa2UpgradeMci`, `pemCurvesFixMci`, etc.) to avoid a ledger split.

### Proof of Concept
```js
const stringUtils = require('./string_utils.js');

const A = { a: { b: "c", d: "e" } };
const B = { a: { b: "c" }, d: "e" };

console.log(stringUtils.getSourceString(A));
console.log(stringUtils.getSourceString(B));
// both print: a\x00b\x00s\x00c\x00d\x00s\x00e
console.log(stringUtils.getSourceString(A) === stringUtils.getSourceString(B)); // true

const objectHash = require('./object_hash.js');
console.log(objectHash.getChash160(A) === objectHash.getChash160(B)); // true -> same address for two different structures
```
This demonstrates the underlying collision primitive; applying the same key-redistribution technique inside an in-grammar op (e.g. `weighted and`'s `{required, set:[{value, weight}, ...]}` schema, validated in [12](#0-11) ) yields two different, independently-valid address definitions — one strong/multisig, one attacker-satisfiable — that hash to the same `chash160`/address.

function getSourceString(obj) {
	var arrComponents = [];
	function extractComponents(variable){
		if (variable === null)
			throw Error("null value in "+JSON.stringify(obj));
		switch (typeof variable){
			case "string":
				if (variable.includes(STRING_JOIN_CHAR))
					throw Error("00 byte in string value in " + JSON.stringify(obj));
				arrComponents.push("s", variable);
				break;
			case "number":
				if (!isFinite(variable))
					throw Error("invalid number: " + variable);
				arrComponents.push("n", variable.toString());
				break;
			case "boolean":
				arrComponents.push("b", variable.toString());
				break;
			case "object":
				if (Array.isArray(variable)){
					if (variable.length === 0)
						throw Error("empty array in "+JSON.stringify(obj));
					arrComponents.push('[');
					for (var i=0; i<variable.length; i++)
						extractComponents(variable[i]);
					arrComponents.push(']');
				}
				else{
					var keys = Object.keys(variable).sort();
					if (keys.length === 0)
						throw Error("empty object in "+JSON.stringify(obj));
					keys.forEach(function(key){
						if (typeof variable[key] === "undefined")
							throw Error("undefined at "+key+" of "+JSON.stringify(obj));
						if (key.includes(STRING_JOIN_CHAR))
							throw Error("00 byte in object key in " + JSON.stringify(obj));
						arrComponents.push(key);
						extractComponents(variable[key]);
					});
				}
				break;
			default:
				throw Error("getSourceString: unknown type="+(typeof variable)+" of "+variable+", object: "+JSON.stringify(obj));
		}
	}

	extractComponents(obj);
	return arrComponents.join(STRING_JOIN_CHAR);
}
