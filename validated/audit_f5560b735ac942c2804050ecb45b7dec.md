### Title
Webhook signature verification is scoped by `repository.owner.login`, but event handlers act on the independently-controlled `repository.full_name` field, allowing cross-organization forgery of GitHub events — ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which organization's webhook secret to use for HMAC verification based on `repository.owner.login` (or `organization.login`), but every event `Handler` resolves the target `Stack`/`Repository` from the separate, unverified `repository.full_name` field. In a multi-organization Shipit deployment, a party holding the webhook secret for organization A can craft a payload whose `repository.owner.login` is `"A"` (so the signature check passes) while `repository.full_name` points at a repository belonging to organization B, causing Shipit to act on organization B's stack.

### Finding Description
`Shipit.github(organization:)` supports a per-organization configuration schema (`lib/shipit.rb:170-200`), where each org key under `secrets.github` has its own `webhook_secret`. `WebhooksController` uses this to select the correct signing secret: [1](#0-0) [2](#0-1) 

`repository_owner` — the value used to pick the HMAC secret — is read from `params.dig('repository', 'owner', 'login')` (falling back to `params.dig('organization', 'login')`). The HMAC itself is computed with `HMAC(secret_for(repository_owner), raw_body)` in `verify_webhook_signature`: [3](#0-2) 

Crucially, the signature only proves that *some* field inside the payload (`repository.owner.login`) matches an organization whose secret was used — it does not bind that organization to the *other* repository identifier used by the business logic. Every `Handler` subclass locates the affected `Stack`/`Repository` via `repository.full_name`, a sibling field inside the same `repository` object but never cross-checked against `repository.owner.login`: [4](#0-3) 

For example, `PushHandler` triggers a GitHub sync for any stack whose repository matches `repository.full_name`: [5](#0-4) 

The same pattern (`Repository.from_github_repo_name(params.repository.full_name)`) is used throughout the pull-request handlers, e.g.: [6](#0-5) 

Because `repository.owner.login` and `repository.full_name` are independent, attacker-controlled JSON fields inside the same request body, a party that legitimately possesses the webhook secret for organization A (e.g., an org admin of A who can view/rotate A's GitHub webhook secret configured to point at this Shipit instance) can forge a valid signature for a payload while setting `repository.full_name` to `"B/some-repo"` — a repository belonging to an unrelated organization B also configured on the same Shipit instance. The signature check in `verify_signature` will succeed (it only validates against A's secret because `repository_owner` resolves to A), yet the handler dispatched by `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` will operate on B's stack.

This breaks the intended binding: *the organization that authenticated the request* (A) must equal *the repository the engine writes to* (should be under A, but is actually B).

### Impact Explanation
This allows an attacker who administers one onboarded GitHub organization to forge webhook events (push, status, check_suite, pull_request, etc.) that are processed as if legitimately sent by GitHub for a different organization's repository/stack. Concretely, using the `status` event handler, an attacker can inject arbitrary/fake commit CI statuses onto a victim organization's commits (`Shipit::Webhooks::Handlers::StatusHandler`, resolved the same way via `repository.full_name`). Because Shipit's continuous-delivery gating relies on stored commit statuses (`ci.require`/`ci.blocking` in `shipit.yml`), forging passing statuses on a victim's commits can satisfy deploy safety checks and cause an **unauthorized deploy** of attacker-influenced state on a repository/stack the attacker does not control — a cross-repository write into another organization's deployment pipeline. This matches the Critical-impact category ("cross-repository writes... or an unauthorized deploy").

### Likelihood Explanation
Requires the Shipit instance to be configured for multiple GitHub organizations (a documented, supported configuration via `secrets.github` per-org keys) and requires the attacker to possess a valid webhook secret for at least one onboarded organization — typically available to any admin/maintainer of that organization's GitHub webhook settings, not a Shipit account or API token. No Shipit session, `ApiClient` token, or GitHub App private key is needed; only knowledge of one org's already-configured webhook secret, which is inherent to operating that org's GitHub webhook.

### Recommendation
In `WebhooksController#verify_signature` and in `Handler#repository_name`, ensure the organization/owner used to select the verification secret is cryptographically tied to the same repository/owner value used to resolve the target `Stack`. Concretely, derive the target repository strictly from the same `repository.owner.login` used for signature verification (or re-derive `repository_owner` from `repository.full_name`'s owner segment), and reject any payload where `repository.owner.login` does not match the owner segment of `repository.full_name`.

### Proof of Concept
1. Configure Shipit with two organizations, `org-a` and `org-b`, each with distinct `webhook_secret` values (multi-org `secrets.github` schema per `lib/shipit.rb`).
2. As an admin of `org-a`'s GitHub organization, obtain `org-a`'s webhook secret (legitimately visible to org admins configuring the webhook pointed at this Shipit instance).
3. Craft a `status` (or `push`) webhook payload body:
```json
{
  "sha": "<victim commit sha in org-b/repo>",
  "state": "success",
  "context": "ci/required-check",
  "repository": {
    "owner": { "login": "org-a" },
    "full_name": "org-b/repo"
  }
}
```
4. Sign the raw body with `org-a`'s webhook secret and send it as `X-Hub-Signature`.
5. `WebhooksController#verify_signature` resolves `repository_owner` = `"org-a"`, fetches `org-a`'s secret, and the HMAC check passes.
6. `Shipit::Webhooks::Handlers::StatusHandler` (or `PushHandler`) resolves the target repository/stack via `repository.full_name` = `"org-b/repo"`, and applies the forged status/sync to `org-b`'s stack — despite the request never being signed by `org-b`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
