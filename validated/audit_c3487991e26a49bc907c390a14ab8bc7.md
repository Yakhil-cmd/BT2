### Title
Webhook signature verification silently bypassed when a multi-org `webhook_secret` is unset, allowing forged `membership` events to grant `Shipit.github_teams` authorization - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the `GitHubApp` used to check the `X-Hub-Signature` header based on `repository_owner`, an **unverified** field pulled straight out of the still-unauthenticated JSON body. That `GitHubApp#verify_webhook_signature` implementation treats a blank/unset `webhook_secret` as "always verified" (`return true unless webhook_secret`). Since `authorized?` for a `User` is gated on team membership synced from GitHub `membership` webhooks, an attacker who can reach the `/webhooks` endpoint for an org whose per-org config omits `webhook_secret` can forge a `membership` event that adds an arbitrary `User` to a `Team` listed in `Shipit.github_teams`, escalating that user into an authorized session.

### Finding Description
The controller picks the app/secret to verify against using data from the payload itself, before any signature has been checked: [1](#0-0) 

`repository_owner` is derived from `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` — both attacker-controlled fields in the unauthenticated request body: [2](#0-1) 

`verify_webhook_signature` in the resolved `GitHubApp` returns `true` unconditionally when that organization's config has no `webhook_secret` configured: [3](#0-2) 

In a multi-org deployment (`config/secrets.yml` with per-org `github:` sub-keys, as documented), it's easy for one organization's entry to be left without a `webhook_secret` (the example templates even show `webhook_secret: # nil`): [4](#0-3) [5](#0-4) 

For any organization matching that unset-secret entry, `verify_signature` becomes a no-op regardless of the actual `X-Hub-Signature` value or its absence, and the handler pipeline runs unauthenticated attacker input: [6](#0-5) 

`MembershipHandler#process` uses that payload to create/find a `Team` and add an arbitrary `User` (also created on the fly from attacker-supplied `login`) to it: [7](#0-6) 

Authorization to use the whole application is gated purely on team membership: [8](#0-7) [9](#0-8) 

This breaks the trust binding described in the rules: the organization that is (nominally) authenticated by `verify_signature` (based on an unverified field) is not equal to the guarantee actually enforced, because for orgs without a secret configured, verification is unconditionally true — i.e. "authentication" happens for an org that never possessed a shared secret in the first place.

### Impact Explanation
This is a High severity finding: it allows escalation into `Shipit.github_teams` authorization without any GitHub credential, webhook secret, or session — matching the explicit High-impact criteria in the rules. Once a `Team` matching `Shipit.github_teams` has an attacker-supplied `User` added as a member via the forged `membership` webhook, and that GitHub identity subsequently completes OAuth login (attacker's own GitHub account, using their own real login matching the `member.login` they forged), `User#authorized?` returns true, granting access to stacks, deploys, rollbacks, and API client management otherwise restricted to team members.

### Likelihood Explanation
Likelihood depends entirely on operational configuration: this only fires for organizations in a multi-org `github:` config that have no `webhook_secret` set. Single-org deployments with a secret configured are unaffected because `verify_webhook_signature` performs the HMAC comparison normally. However, the documented multi-org config templates and test fixtures both show `webhook_secret: # nil` as an accepted/example value, making misconfiguration plausible in real deployments that manage several organizations.

### Recommendation
Do not treat a blank `webhook_secret` as "verification passed." Either require `webhook_secret` to be present for every configured organization (raise a startup/configuration error if missing) or fail closed (`return false unless webhook_secret`) in `GitHubApp#verify_webhook_signature`. Additionally, avoid using unverified payload fields (`repository_owner`) to select the verification key when possible, or re-validate that the verified organization matches the organization ultimately acted upon by the handler.

### Proof of Concept
1. Deploy Shipit with a multi-org `github:` config (as in `docs/setup.md`) where `OrgVictim` has `webhook_secret:` left blank/nil, and `Shipit.github_teams` includes a team belonging to `OrgVictim`.
2. POST to `/webhooks` with header `X-Github-Event: membership` and no (or a garbage) `X-Hub-Signature`, with body:
```json
{
  "action": "added",
  "team": {"id": 999, "name": "target-team", "slug": "target-team", "url": "https://api.github.com/teams/999"},
  "organization": {"login": "OrgVictim"},
  "member": {"login": "attacker-github-login"}
}
```
3. `verify_signature` resolves `Shipit.github(organization: "OrgVictim")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` unconditionally, per [10](#0-9) .
4. `MembershipHandler#process` runs, creating/finding `Team#999` and adding `User` with login `attacker-github-login` as a member, per [11](#0-10) .
5. The attacker completes GitHub OAuth login with that same GitHub login; `User#authorized?` now returns `true` because the user's `teams` includes a team in `Shipit.github_teams`, per [8](#0-7) , granting unauthorized access to the application.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

        def process
          team = find_or_create_team!
          member = User.find_or_create_by_login!(params.member.login)

          case params.action
          when 'added'
            team.add_member(member)
          when 'removed'
            team.members.delete(member)
          else
            raise ArgumentError, "Don't know how to perform action: `#{action.inspect}`"
          end
        end

        private

        def find_or_create_team!
          Team.find_or_create_by!(github_id: params.team.id) do |team|
            team.github_team = params.team
            team.organization = params.organization.login
          end
        end

      if current_user.logged_in? && current_user.requires_fresh_login?

        reset_session
        redirect_to(Shipit::Engine.routes.url_helpers.github_authentication_path(origin: request.original_url))

          team_list = team_handles.to_sentence(two_words_connector: ' or ', last_word_connector: ', or ')
          render(plain: "You must be a member of #{team_list} to access this application.", status: :forbidden)
        end
      else
        redirect_to(Shipit::Engine.routes.url_helpers.github_authentication_path(origin: request.original_url))
      end
    end
