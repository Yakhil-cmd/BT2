### Title
Webhook signature verification authenticates a different field than the one used to select the written repository, allowing cross-repository, cross-organization webhook forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks the GitHub App/secret to verify against based on `repository.owner.login` (or `organization.login`) taken from the untrusted, not-yet-verified request body, while `Shipit::Webhooks::Handlers::Handler#repository_name` (used by every handler to decide which `Stack`/`Repository` actually gets written to) reads a *different* field of the same body: `repository.full_name`. These two attacker-controlled fields are never bound to each other by the signature check.

### Finding Description
`verify_signature` selects the app config to check the HMAC against using: [1](#0-0) [2](#0-1) 

and `Shipit::GithubApp#verify_webhook_signature` intentionally *skips* verification entirely when the resolved organization has no `webhook_secret` configured: [3](#0-2) 

Meanwhile, every webhook handler determines which `Repository`/`Stack` the event is applied to using a *separate* field of the same JSON body — `repository.full_name` — via the shared base class: [4](#0-3) 

`repository.owner.login` (used for authentication/secret selection) and `repository.full_name` (used to select the actual `Stack` that gets mutated) are both attacker-supplied and are never cross-checked against each other. An attacker who knows of, or controls, any organization configured on the Shipit instance with no `webhook_secret` (or whose secret they otherwise know) can submit a forged webhook where `repository.owner.login` = that low-security/known-secret organization, but `repository.full_name` = `victim-org/victim-repo`. `verify_signature` will authenticate the request against the attacker-controlled org (passing trivially because `verify_webhook_signature` returns `true` when `webhook_secret` is blank, or because the attacker knows that org's secret), while the handler dispatch (`PushHandler`, `StatusHandler`, `CheckSuiteHandler`) resolves and mutates the victim repository's stacks because it reads `repository.full_name` instead.

### Impact Explanation
This breaks the trust binding "organization that authenticated == repository that is written." Concretely:
- `StatusHandler`/commit-status ingestion creates forged `Status` rows for the victim commit via `Commit#create_status_from_github!`/`#add_status`, which drives `deployable_status` hooks and `stack.schedule_merges if new_status.pending? || new_status.success?`: [5](#0-4) 
- A forged "success" CI status on an unreviewed/failing commit can make it appear deployable and enter the merge queue, leading to an unauthorized merge/deploy of that commit — without ever presenting a valid signature for the victim organization.
- `PushHandler` similarly triggers `stack.sync_github` for the victim's stacks based on the forged `full_name`/`branch`, at the attacker's chosen SHA: [6](#0-5) 

This matches the High-impact criteria: "escalation into `Shipit.github_teams` authorization" analog and unauthenticated write of stack/task state leading toward an unauthorized deploy/merge, achieved purely by exploiting the mismatch between the authenticating field and the field driving repository selection.

### Likelihood Explanation
Exploitability requires the attacker to know an organization on the same Shipit deployment for which `webhook_secret` is unset (a documented, intentionally permissive fallback in `GithubApp#verify_webhook_signature`) or whose secret they already know (e.g., their own onboarded test org on a multi-tenant Shipit instance). Given Shipit is commonly deployed to serve multiple GitHub organizations/repos from one instance, and per-org `webhook_secret` configuration is optional, this is a realistic misconfiguration/multi-tenant scenario rather than a purely theoretical one. No GitHub App private key, `GITHUB_TOKEN`, or valid webhook secret for the *victim* organization is required.

### Recommendation
Bind authentication and repository resolution to the same field: verify the signature using the organization/owner derived from `repository.full_name` (the same field `Handler#repository_name` uses), not from a separately-read `repository.owner.login`/`organization.login`. Additionally, reconsider the `return true unless webhook_secret` fallback in `GithubApp#verify_webhook_signature`, or at minimum ensure it cannot be reached by supplying a different, unrelated `full_name` in the payload than the one that determined the (missing) secret.

### Proof of Concept
1. Attacker controls or knows of organization `attacker-org` configured on the target Shipit instance with no `webhook_secret` (or a known secret).
2. Attacker crafts a `status` (or `push`/`check_suite`) webhook body:
```json
{
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  },
  "sha": "<victim-commit-sha>",
  "state": "success",
  "context": "ci/required-check"
}
```
3. `WebhooksController#verify_signature` resolves `Shipit.github(organization: "attacker-org")` and calls `verify_webhook_signature`, which returns `true` unconditionally (no secret configured) — the request passes.
4. `create` dispatches to `StatusHandler`, whose base `Handler#repository_name` reads `payload.dig('repository','full_name')` → `"victim-org/victim-repo"`, resolving the real victim `Stack`s and writing a forged successful CI status for the victim's commit, potentially unblocking merge-queue progression/deploy eligibility — all without ever satisfying the victim organization's `webhook_secret`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
