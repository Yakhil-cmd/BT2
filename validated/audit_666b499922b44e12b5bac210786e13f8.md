### Title
Inflated `gasLimit` in ApproveTx/SwapTx causes proposer to lend far more KAIA than actual gas cost, with full loss on swap revert — (`kaiax/gasless/impl/getter.go`)

---

### Summary

`lendAmount` is computed from `tx.Fee() = gasLimit × gasPrice` (the worst-case fee ceiling), not from actual gas consumed. A sender can set `gasLimit = 30_000_000` on both ApproveTx and SwapTx, forcing the proposer to lend 60 KAIA. If the SwapTx reverts (e.g., slippage causes `minAmountOut` to be unachievable at execution time), the proposer receives no repayment and loses the full lent amount.

---

### Finding Description

`lendAmount` is defined in `kaiax/gasless/impl/getter.go`:

```go
func lendAmount(approveTxOrNil, swapTx *types.Transaction) *big.Int {
    r := new(big.Int)
    if approveTxOrNil != nil {
        r.Add(r, approveTxOrNil.Fee())   // R2 = approveTx.gasLimit * gasPrice
    }
    r.Add(r, swapTx.Fee())               // R3 = swapTx.gasLimit * gasPrice
    return r
}
``` [1](#0-0) 

`Fee()` for a legacy transaction equals `gasLimit × gasPrice` — the maximum possible fee, not the actual gas consumed. There is no cap on `gasLimit` anywhere in the gasless module.

`repayAmount` is:

```go
func repayAmount(approveTxOrNil, swapTx *types.Transaction) *big.Int {
    r1 := new(big.Int).Mul(swapTx.GasPrice(), new(big.Int).SetUint64(params.TxGas))
    return new(big.Int).Add(r1, lendAmount(approveTxOrNil, swapTx))
}
``` [2](#0-1) 

The SP4 check in `VerifyExecutable` enforces `swapArgs.AmountRepay == repayAmount(...)` exactly: [3](#0-2) 

And `checkBalanceForSwap` enforces `minAmountOut >= amountRepay`: [4](#0-3) 

The `ShouldCheckSwapAmount` guard checks `amountIn >= getAmountIn(minAmountOut)` **at txpool admission time** against the current on-chain exchange rate: [5](#0-4) 

This snapshot check does **not** hold at block execution time if the exchange rate moves.

The LendTx is generated by the proposer's node key and sends `lendAmount` KAIA to the sender before ApproveTx and SwapTx execute: [6](#0-5) 

---

### Impact Explanation

With `gasLimit = 30_000_000` and `gasPrice = 1 gwei`:

| Component | Value |
|---|---|
| `lendAmount` (R2+R3) | `30M×1gwei + 30M×1gwei = 60 KAIA` |
| `amountRepay` (R1+R2+R3) | `21000×1gwei + 60 KAIA ≈ 60.000021 KAIA` |
| `minAmountOut` (must be ≥ amountRepay) | `≥ 60.000021 KAIA` |

Execution sequence:
1. **LendTx executes**: proposer transfers 60 KAIA to sender. ✓
2. **ApproveTx executes**: ERC-20 approval succeeds. ✓
3. **SwapTx reverts**: exchange rate moved (slippage), actual output < `minAmountOut`. The `swapForGas` call reverts; `amountRepay` is never transferred back to the proposer.

Proposer net position:
- **Sent**: 60 KAIA (LendTx value)
- **Received**: gas fees from ApproveTx + SwapTx at actual gas used (e.g., ~50K gas each = 0.0001 KAIA total)
- **Net loss**: ~59.9999 KAIA

Sender net position:
- **Received**: 60 KAIA (LendTx)
- **Paid**: ~0.0001 KAIA (actual gas fees)
- **Net gain**: ~59.9999 KAIA

This constitutes an unauthorized transfer of KAIA from the proposer to the attacker.

---

### Likelihood Explanation

The attacker controls `gasLimit` freely — no cap is enforced in the gasless module. Causing the swap to revert requires only that `minAmountOut` be set near the current exchange rate; any natural price movement between txpool admission and block execution suffices. An active attacker can also front-run the bundle with a large opposing swap to guarantee the revert. The proposer has no on-chain protection and the code does not mandate bundle simulation before inclusion.

---

### Recommendation

1. **Cap `gasLimit`** for ApproveTx and SwapTx in `VerifyExecutable` / `checkBalanceForSwap` to a reasonable maximum (e.g., the block gas limit divided by a safety factor, or a protocol-defined constant).
2. **Base `lendAmount` on a conservative gas estimate** rather than `gasLimit × gasPrice`, or add a separate `maxLendAmount` parameter validated against a protocol cap.
3. **Enforce bundle simulation** in the worker before including a gasless bundle, and skip the bundle if the SwapTx would revert.

---

### Proof of Concept

1. Craft `ApproveTx`: `to=allowedToken`, `data=approve(router, MaxUint256)`, `gasLimit=30_000_000`, `gasPrice=1 gwei`.
2. Craft `SwapTx`: `to=swapRouter`, `data=swapForGas(token, amountIn, minAmountOut=60.000021 KAIA, amountRepay=60.000021 KAIA, deadline)`, `gasLimit=30_000_000`, `gasPrice=1 gwei`. Set `amountIn` to satisfy `getAmountIn(minAmountOut)` at current rate.
3. Submit both to the txpool. SP4 and `minAmountOut >= amountRepay` checks pass.
4. Before the proposer's block is sealed, submit a large swap on the same pool to move the price so the output falls below `minAmountOut`.
5. The proposer's node builds the bundle: LendTx (60 KAIA → sender), ApproveTx (succeeds), SwapTx (reverts due to slippage).
6. Assert: proposer KAIA balance decreased by ~60 KAIA; sender KAIA balance increased by ~60 KAIA; no repayment occurred.
