### Title
Webhook authenticator/repository-writer binding mismatch allows cross-organization forgery of commit statuses, pushes, and check-suite events - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/webhook secret to validate a webhook's HMAC signature against based on `repository.owner.login` (falling back to `organization.login`), but every event `Handler` subsequently resolves the target `Stack`/`Repository` using an entirely different, unconstrained field: `repository.full_name` (`Handler#repository_name`). Nothing enforces that `repository.owner.login` and the owner portion of `repository.full_name` refer to the same organization. An operator of one organization/app installation configured in this multi-tenant Shipit instance can therefore sign a payload with their own legitimate webhook secret while pointing `repository.full_name` at a `Stack` belonging to a completely different organization, causing the handler to mutate state (commit statuses, pushes, check suites, membership) for a repository it never authenticated for.

### Finding Description
The signature check is: [1](#0-0) 

`repository_owner` is derived purely from attacker-controlled JSON: [2](#0-1) 

`Shipit.github(organization: repository_owner)` resolves a per-organization `GitHubApp` instance (and its own `webhook_secret`) from `secrets.github`, supporting genuinely separate secrets per organization in multi-org deployments: [3](#0-2) 

Once the signature is accepted, `WebhooksController#create` dispatches the *entire raw payload* to every registered handler for the event, with no re-validation that the payload's owner matches the org whose secret verified it: [4](#0-3) 

Every handler then determines which `Repository`/`Stack` to act on using a **different payload field** — `repository.full_name` — with no cross-check against `repository.owner.login`: [5](#0-4) 

This is the same bug class as the Plaza Finance issue: one field (`amount`/here, `repository.owner.login`) is the one validated/capped, while a different field (`amount` actually transferred/here, `repository.full_name`) is the one actually acted upon — the two are assumed to agree but nothing enforces it. In Shipit's threat model this breaks the binding: *"an organization that authenticated versus the repository that is written."*

### Impact Explanation
An attacker who controls (or has been granted) one organization's GitHub App installation configured in this Shipit instance's `secrets.github` (and therefore genuinely knows/controls that org's `webhook_secret`, e.g. via GitHub's App settings for their own org) can craft an arbitrary JSON body, sign it with their own org's secret, and set `repository.owner.login` to their own org (to pass `verify_signature`) while setting `repository.full_name` to `victim-org/victim-repo`. This forged, correctly-signed request will be processed by:
- `StatusHandler` — write a fabricated commit `Status` (e.g. mark a malicious commit's CI as `success`) for a commit in another organization's tracked repository, which can satisfy `release_status?` deploy-safety gating and enable an otherwise-blocked deploy of that commit.
- `PushHandler` — enqueue a `GithubSyncJob` for another organization's `Stack`.
- `CheckSuiteHandler` — force a `RefreshCheckRunsJob` for another organization's stack.
- `MembershipHandler`/`PullRequest` handlers — mutate `Team`/`Membership`/PR-derived state cross-tenant.

Faking a passing commit status to bypass deploy safety checks constitutes an unauthorized deploy path, which is a Critical-tier impact per the engagement rules; at minimum this is cross-tenant state corruption/writes across repository boundaries (High/Critical depending on handler exercised).

### Likelihood Explanation
This requires an attacker to control at least one organization's webhook secret configured in the same multi-tenant Shipit deployment (`secrets.github` with multiple org keys, per `Shipit.github_organizations`/`TOP_LEVEL_GH_KEYS`) — a realistic scenario for shared/self-service Shipit instances hosting multiple organizations, and it needs no privileged Shipit account, `ApiClient` token, or repository write access to the victim repo, satisfying the "unprivileged attacker" constraint since the attacker is unprivileged with respect to the *victim* organization.

### Recommendation
In `WebhooksController`/`Handler`, after signature verification, enforce that the organization used to select/verify the webhook secret is the same organization that owns the repository referenced by `repository.full_name` (and `organization.login` for org-scoped events) before any handler mutates state — reject the request if they diverge.

### Proof of Concept
Conceptual request (assuming attacker administers `attacker-org`'s GitHub App install configured in this Shipit's `secrets.github`):
```
POST /webhooks
X-Github-Event: status
X-Hub-Signature: sha1=<hmac using attacker-org's known webhook_secret over the raw body below>

{
  "sha": "<victim commit sha>",
  "state": "success",
  "context": "ci/tests",
  "repository": { "full_name": "victim-org/victim-repo", "owner": { "login": "attacker-org" } }
}
```
`verify_signature` resolves `Shipit.github(organization: "attacker-org")`, validates the HMAC successfully (attacker knows this secret), then `StatusHandler` writes a `Status` against `victim-org/victim-repo`'s commit `sha`, based solely on `repository.full_name`, unrelated to the org used for verification.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
