The unique index confirms the design intent: `add_index :commits, [:sha, :stack_id], unique: true` [1](#0-0)  — the same `sha` is expected to legitimately exist across *multiple different* `stack_id`s (otherwise a unique index on `sha` alone would suffice). This confirms multi-tenant collision on `sha` is a normal, anticipated condition in this schema, not an edge case.

### Title
`StatusHandler#process` applies GitHub `status` webhooks to commits by `sha` alone, with no binding to the reporting repository, letting a webhook from one repo trigger `stack.schedule_merges` for another repo's stack - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`Webhooks::Handlers::StatusHandler#process` resolves target commits with `Commit.where(sha: params.sha)` and never restricts the query to the repository named in the webhook payload. Since `Commit` records are indexed on `(sha, stack_id)` — not `sha` alone — the same `sha` can and does legitimately exist attached to multiple different stacks (e.g. forks, mirrored repos, or repos created from identical templates), so a validly signed `status` webhook from repository A can flip the CI state of a commit belonging to stack B, triggering `Commit#add_status` → `stack.schedule_merges` on B.

### Finding Description
The claimed binding should be: `commit.stack.repository.full_name == payload.dig('repository', 'full_name')` for every `Commit` whose status is mutated by a given webhook delivery. Tracing the code shows this equality is never checked.

- `WebhooksController#create` dispatches strictly by event type: `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` [2](#0-1) . `verify_signature` authenticates that the payload was signed by the GitHub App belonging to `repository_owner` (i.e. `payload.dig('repository','owner','login')`) [3](#0-2) . This only proves the sender is a legitimate GitHub webhook from *that organization*; it says nothing about which commit `sha` the event is entitled to affect.
- The base `Handler` class provides a `stacks` helper explicitly scoped to the reporting repository: `Repository.from_github_repo_name(repository_name)&.stacks || Stack.none` [4](#0-3) , and other handlers (e.g. `PullRequest::OpenedHandler`, `ReopenedHandler`, `UnlabeledHandler`) correctly resolve their `repository`/`stack` through this helper before acting [5](#0-4) .
- `StatusHandler`, however, ignores `stacks`/`repository_name` entirely: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [6](#0-5) . Every `Commit` row across the entire Shipit instance sharing that `sha` gets the status applied, regardless of which stack/repository the webhook actually came from.
- `create_status_from_github!` → `add_status` computes `previous_status`/`new_status` and, on a simple-state transition, calls `stack.schedule_merges if new_status.pending? || new_status.success?` [7](#0-6) , which in turn enqueues `ProcessMergeRequestsJob` to merge any queued `MergeRequest`s [8](#0-7) .
- The `(sha, stack_id)` unique index rather than a `sha`-only unique index confirms that identical `sha` values across distinct stacks is a designed, expected occurrence [1](#0-0) , e.g. forked repositories, mirrored repos, or repos created from a shared template share identical commit objects (and therefore identical SHA-1s) by construction of Git itself.

Exploit flow: an attacker who owns (or can push to a fork of, or create a new repo within an organization whose GitHub App is installed org-wide and thus produces validly-signed webhooks) a repository that shares a commit `sha` with the victim's queued merge commit sets a commit status via GitHub's ordinary Statuses API (`POST /repos/{attacker}/{repo}/statuses/{sha}` with `state: success`) on their own repository — an action requiring only push access to their own repo, no privilege on the victim's repo. GitHub delivers a correctly-signed `status` webhook to Shipit for the attacker's organization. `verify_signature` passes because the signature is checked only against the attacker's own org's app credentials, not against the specific commit's owning stack. `StatusHandler#process` then matches the `sha` against `Commit` rows globally and applies the forged `success` status to the victim's commit, driving `stack.schedule_merges` and an unauthorized merge of the queued PR.

Existing guards do not stop this: `verify_signature`/`GithubApp#verify_webhook_signature` authenticate sender-organization identity, not sha-to-repository ownership; `drop_unhandled_event` only checks the event type is registered; the `ExplicitParameters` schema on `StatusHandler` validates shape (`sha`, `state`, etc.) but performs no repository binding [9](#0-8) ; and no model validation on `Status`/`Commit` enforces repository origin of the sha.

### Impact Explanation
A webhook that authenticates only as "some org's repo" can mutate CI status for, and trigger a merge in, an entirely unrelated stack/repository/tenant, satisfying the "payload for one repository mutating another's stack, commit ... or an unauthorized deploy, rollback or merge" Critical category. The blast radius spans every stack hosted by the same Shipit instance whenever any two tracked repositories (forks, templates, mirrors) share commit history/SHAs, and is repeatable per attacker-controlled `sha` collision.

### Likelihood Explanation
Requires: (1) the attacker's own repository to be recognized by Shipit's webhook signature check (i.e. under an org/app installation Shipit already trusts — commonly true for org-wide GitHub App installs where any org member can create/fork repos), (2) the victim stack's `merge_queue_enabled`/auto-merge configuration with a `MergeRequest` awaiting exactly a pending→success transition, and (3) a `sha` collision between the attacker's repo and the victim's queued commit, most plausibly via forking the victim repository (which reproduces identical commit objects/SHAs by Git's design) or via commits shared from a common template. All of these are attacker-cost-cheap and repeatable — no Shipit session, API token, or secret is required, only ordinary GitHub push/API access to a repo the attacker controls.

### Recommendation
Scope `StatusHandler#process` to the reporting repository using the existing `stacks` helper (as other handlers do), e.g. resolve target commits via `stacks.flat_map { |stack| stack.commits.where(sha: params.sha) }` instead of the unscoped `Commit.where(sha: params.sha)`, so that a `status` event can only mutate commits belonging to stacks whose `Repository` matches `payload.dig('repository', 'full_name')`.

### Proof of Concept
Minitest plan (model/controller level, no live GitHub):
1. Create two `Repository`/`Stack` fixtures, `repo_a` (attacker) and `repo_b` (victim), and two `Commit` rows with the identical `sha` value but different `stack_id` (legal per the `(sha, stack_id)` unique index).
2. On `repo_b`'s commit, seed a `MergeRequest` in `pending` state whose `merge_commit` is that colliding-sha commit, and set `repo_b`'s stack to `merge_queue_enabled: true`.
3. POST to `WebhooksController#create` with `X-Github-Event: status`, a payload whose `repository.full_name == repo_a.full_name` and `sha` equal to the colliding value, `state: 'success'`, stubbing `verify_signature` to true (simulating a validly-signed webhook from `repo_a`).
4. Assert both sides of the binding: before the request, `repo_b_commit.stack.repository.full_name != payload['repository']['full_name']` (i.e. the equality is false). After the request, assert `repo_b_commit.reload.status.success?` is true and `assert_enqueued_with(job: ProcessMergeRequestsJob, args: [repo_b.stack])`, proving the mutation and merge scheduling occurred for `repo_b` despite the webhook only authenticating `repo_a`.

    def perform(stack)
      merge_requests = stack.merge_requests.to_be_merged.to_a
      merge_requests.each do |merge_request|

          return false
        end
      end
    end
