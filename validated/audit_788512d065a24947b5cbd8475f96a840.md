### Title
Bridge `lowerHandleNonce` Permanently Stuck When `_requestedBlockNumber = 0` Due to Wrong Handled-State Proxy Check — (`contracts/service_chain/bridge/BridgeTransfer.sol`)

---

### Summary

`_updateHandleNonce` in `BridgeTransfer.sol` uses `handleNoncesToBlockNums[i] > 0` as a proxy to determine whether nonce `i` has been handled. However, the actual "handled" state is tracked by `closedValueTransferVotes[i]`. When an operator calls `handleKLAYTransfer` / `handleERC20Transfer` / `handleERC721Transfer` with `_requestedBlockNumber = 0`, the nonce is fully executed (assets transferred, vote closed), but `handleNoncesToBlockNums[nonce]` is set to `0` — indistinguishable from "never handled." The loop in `_updateHandleNonce` then permanently stalls at that nonce, freezing `lowerHandleNonce` and `recoveryBlockNumber` forever.

---

### Finding Description

In `BridgeTransfer.sol`, after a threshold of operators vote to execute a bridge request, the handle functions (`handleKLAYTransfer`, `handleERC20Transfer`, `handleERC721Transfer`) execute the following sequence:

```solidity
handleNoncesToBlockNums[_requestedNonce] = _requestedBlockNumber;
_updateHandleNonce(_requestedNonce);
// ... asset transfer ...
```

`_updateHandleNonce` advances `lowerHandleNonce` by scanning forward:

```solidity
for (i = lowerHandleNonce; i <= limit && handleNoncesToBlockNums[i] > 0; i++) {
    recoveryBlockNumber = handleNoncesToBlockNums[i];
    delete handleNoncesToBlockNums[i];
    delete closedValueTransferVotes[i];
}
lowerHandleNonce = i;
```

The loop condition `handleNoncesToBlockNums[i] > 0` is the wrong invariant. The correct invariant for "nonce `i` has been handled" is `closedValueTransferVotes[i] == true`, which is set in `_voteValueTransfer` before `_updateHandleNonce` is called. When `_requestedBlockNumber = 0`, `handleNoncesToBlockNums[nonce]` is written as `0` — the same as the Solidity default for an unset mapping entry — so the loop immediately exits at that nonce and `lowerHandleNonce` is set to `nonce` and never advances further.

There is no validation that `_requestedBlockNumber > 0` anywhere in the call path. The contract's own initialization sets `recoveryBlockNumber = 1`, implying block 0 is not a valid source block, but this is never enforced.

Once stuck, the state cannot be self-healed: `closedValueTransferVotes[nonce] = true` causes any re-attempt to handle the same nonce to revert with `"closed vote"`, so there is no way to write a non-zero `handleNoncesToBlockNums[nonce]` after the fact.

---

### Impact Explanation

1. **`lowerHandleNonce` permanently frozen** at the stuck nonce. All subsequent `_updateHandleNonce` calls start the loop at the stuck nonce, immediately fail `handleNoncesToBlockNums[stuck] > 0`, and exit without advancing.

2. **`recoveryBlockNumber` permanently frozen** at its last value before the stuck nonce. The off-chain recovery daemon (`node/sc/vt_recovery.go`) reads `LowerHandleNonce` and `RecoveryBlockNumber` to determine which requests need re-submission. With both frozen, the daemon perpetually re-scans from the old block and re-submits already-handled nonces (which are rejected by `closedValueTransferVotes` but waste gas and operator resources).

3. **Permanent storage leak**: `handleNoncesToBlockNums[i]` and `closedValueTransferVotes[i]` for all `i > stuck_nonce` are never deleted, growing unboundedly.

4. **Bridge recovery mechanism broken**: Any future bridge request that operators miss cannot be recovered via the normal recovery path, because the recovery hint is permanently anchored to the pre-stuck block. New unhandled requests may be silently skipped by the recovery system.

The stuck state is **irrecoverable** without deploying a new bridge contract.

---

### Likelihood Explanation

The trigger is an operator calling any handle function with `_requestedBlockNumber = 0`. Operators are registered by the bridge owner and are semi-trusted. The scenario arises from:

- A buggy operator implementation that passes a zero block number (e.g., off-by-one in block number lookup, or a default-initialized struct field).
- A malicious operator intentionally freezing the bridge's recovery state.

No privileged escalation beyond the existing operator role is required. The contract imposes no lower bound on `_requestedBlockNumber`.

---

### Recommendation

Replace the wrong proxy check with the authoritative handled-state flag:

```diff
- for (i = lowerHandleNonce; i <= limit && handleNoncesToBlockNums[i] > 0; i++) {
+ for (i = lowerHandleNonce; i <= limit && closedValueTransferVotes[i]; i++) {
      recoveryBlockNumber = handleNoncesToBlockNums[i];
      delete handleNoncesToBlockNums[i];
      delete closedValueTransferVotes[i];
  }
```

Additionally, add an input validation guard in all handle functions:

```solidity
require(_requestedBlockNumber > 0, "invalid block number");
```

---

### Proof of Concept

1. Deploy `BridgeTransferKLAY` (or the full `Bridge` contract) with a single operator (threshold = 1).
2. Fund the bridge with KLAY.
3. Handle nonces 0, 1, 2 with valid non-zero block numbers → `lowerHandleNonce` advances to 3.
4. Handle nonce 3 with `_requestedBlockNumber = 0`:
   - KLAY is transferred to `_to` ✓
   - `closedValueTransferVotes[3] = true` ✓
   - `handleNoncesToBlockNums[3] = 0` ← wrong
   - `lowerHandleNonce` is set to 3 and never advances again.
5. Handle nonces 4, 5, 6 with valid non-zero block numbers:
   - Each call: loop starts at `i = 3`, `handleNoncesToBlockNums[3] = 0` → loop exits immediately.
   - `lowerHandleNonce` remains 3 forever.
6. Verify: `bridge.lowerHandleNonce()` returns 3 regardless of how many subsequent nonces are handled.
7. Verify: `bridge.recoveryBlockNumber()` is frozen at the block number of nonce 2.
8. Attempt to re-handle nonce 3 with `_requestedBlockNumber = 1` → reverts with `"closed vote"` → stuck state is irrecoverable.

    function _voteValueTransfer(uint64 _requestNonce)
        internal
        returns(bool)
    {
        require(!closedValueTransferVotes[_requestNonce], "closed vote");

        bytes32 voteKey = keccak256(msg.data);
        if (_voteCommon(VoteType.ValueTransfer, _requestNonce, voteKey)) {
            closedValueTransferVotes[_requestNonce] = true;

        return false;
