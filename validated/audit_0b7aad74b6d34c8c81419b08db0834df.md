### Title
Unmeasured `recapitalize` refund pays attacker-declared `amount` out of pool custody without any deposit - (File: contracts/pool/src/ops/recapitalize.rs)

### Summary
The pool's `recapitalize` leg treats the caller-declared `amount` as if it had already been paid in, credits only `min(amount, backing_shortfall)` to the cash book, and refunds `amount - applied` directly to `payer` via `Cache::transfer_out`. Because the inbound leg is never measured against a balance delta inside this call, an attacker who invokes the pool entrypoint with no deposit receives a "refund" of funds that were never transferred in — an input that escapes the scope of what the payer actually supplied, analogous to a relative path escaping a base directory. The same pattern exists in `ops::repay::accounting`, where the overpayment refund is derived from the declared `action.amount` rather than a measured receipt.

### Finding Description
In `contracts/pool/src/ops/recapitalize.rs`, `accounting` computes `applied = amount.min(guards::backing_shortfall(&cache))` and `refund = amount - applied` purely from the declared `amount`; `apply` then calls `outcome.cache.transfer_out(&payer, outcome.refund)`. Neither leg debits `cash` nor passes `require_reserves`, and the pool does not verify that `amount` tokens actually arrived — the doc comment only states "The controller transfers `amount` into the pool before this call", i.e., settlement correctness is assumed, not enforced at the pool layer. The controller wrapper `markets::recapitalize` in `contracts/controller/src/markets.rs` does measure the receipt (`transfer_amount_measured` → `received`), but the pool itself trusts whatever `amount` it is handed and pays the refund out of real custody. The in-repo test `test_unfunded_recapitalize_leaves_the_cash_book_overstating_custody` demonstrates that `client().recapitalize(&hub(asset), &payer, &custody)` with zero tokens transferred in drains the pool's entire token balance to `payer`, and `test_unfunded_repay_overpayment_refund_also_pays_out_of_custody` shows the identical unfunded-refund path via `repay` on a market with no debt (`resolve_repay` yields `overpayment == amount`, `net_repay == 0`, whole declared amount refunded).

### Impact Explanation
Theft of user funds. Any unprivileged address can call the pool's `recapitalize` (or `repay` on a debt-free market) with an arbitrary `payer` and an `amount` up to the pool's live token balance, deposit nothing, and receive the full amount as a "refund" of tokens that were never paid in. Custody is drained while the cash book still claims the funds exist, so subsequent legitimate withdraws revert inside the SAC transfer — the protocol is left insolvent with an overstated book, compounding the loss into permanent freezing of remaining suppliers' funds.

### Likelihood Explanation
The exploit requires no privileges, no oracle manipulation, and no market preconditions beyond a live token balance in the pool — even a solvent market with `backing_shortfall == 0` yields `applied == 0` and a full refund. A single transaction with attacker-chosen `hub_asset`, `payer`, and `amount = token.balance(pool)` suffices, as the pool's own tests demonstrate. The only precondition is direct reachability of the pool entrypoint; the refund path is unguarded by auth, reserves checks, or balance-delta measurement.

### Recommendation
Inside `contracts/pool/src/ops/recapitalize.rs` (and `ops/repay.rs`), derive the applied/refund split from a measured custody delta — snapshot `token.balance(pool)` before crediting and cap `applied + refund` at the actual delta, or require the caller to be the controller and have the controller pass only the measured `received`. Alternatively, gate the entrypoint with `require_auth`/invoker check against the stored controller address so untrusted declared amounts can never reach `transfer_out`.

### Proof of Concept
```rust
// Attacker controls `payer`; pool holds `custody` of `asset` from suppliers.
// No tokens are transferred in.
pool_client.recapitalize(&HubAssetKey { hub_id, asset }, &payer, &custody);
// applied = min(custody, backing_shortfall) = 0 on a solvent market
// refund  = custody - 0 = custody
// Cache::transfer_out(payer, custody) pays the full balance to attacker.
assert_eq!(token.balance(&pool), 0);
assert_eq!(token.balance(&payer), custody);
```
This mirrors `test_unfunded_recapitalize_leaves_the_cash_book_overstating_custody` in `contracts/pool/tests/flows.rs` and the parallel `repay`-based drain in `test_unfunded_repay_overpayment_refund_also_pays_out_of_custody`. Note: this assessment is based on the pool-side code and tests, which invoke `recapitalize`/`repay` directly with attacker-chosen arguments; I did not fully verify an invoker-auth check on the pool entrypoints in `contracts/pool/src/lib.rs` — if one exists restricting calls to the controller, reachability collapses, but the unmeasured-refund defect in the refund math stands regardless.
