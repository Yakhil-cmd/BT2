Confirmed the multi-org design: `docs/setup.md` and `test/dummy/config/secrets_double_github_app.yml` show that a single Shipit install can be configured with multiple independent GitHub Apps (`OrgOne`, `OrgTwo`), each with its own `webhook_secret` [1](#0-0) . The signature check and payload processing use two different, attacker-controllable fields from the same untrusted body.

### Title
Webhook signature is validated against the org named in the payload while handlers act on the (unrelated) repository named in the same payload, enabling cross-organization writes - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks which GitHub App/secret to validate the HMAC signature against using `repository_owner`, a value read straight out of the untrusted, attacker-suppliable JSON body (`params.dig('repository','owner','login')` or `params.dig('organization','login')) [2](#0-1) [3](#0-2) . Once the signature is accepted, the actual event handlers (e.g. `PushHandler`) resolve the target `Stack`/`Repository` using a *different* field from that same body: `payload.dig('repository', 'full_name')`, defined in the shared `Handler` base class [4](#0-3) . Nothing ties the org whose secret validated the signature to the repository the handler subsequently mutates.

### Finding Description
Shipit explicitly supports hosting multiple independent GitHub Apps/organizations from one instance, each with its own `webhook_secret`, as documented in `docs/setup.md` ("Using Multiple Github Applications") and exercised in `test/dummy/config/secrets_double_github_app.yml` (`OrgOne`, `OrgTwo`) [1](#0-0) [5](#0-4) . `Shipit.github(organization:)` resolves the app/secret purely by organization name, with no linkage back to any specific repository [6](#0-5) .

In `WebhooksController`:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [7](#0-6) 

`verify_webhook_signature` is a straightforward HMAC-SHA1 check of the raw body against that org's configured secret [8](#0-7) . Crucially, the HMAC only proves the request was signed with *some* org's secret—it says nothing about which repository the payload's other fields describe. The `create` action then dispatches the full, attacker-supplied body to handlers unmodified:
```ruby
def create
  params = JSON.parse(request.raw_post)
  Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }
  head(:ok)
end
``` [9](#0-8) 

`PushHandler` (and the other handlers) resolve which `Stack`s to act on from `repository.full_name`, independent of `repository.owner.login` used for the signature check:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [4](#0-3) 
```ruby
def process
  stacks.not_archived.where(branch:).find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
end
``` [10](#0-9) 

An administrator of any one org configured on the Shipit instance (call it `OrgA`) legitimately knows `OrgA`'s own `webhook_secret` (they configured their own GitHub App). They can POST an arbitrary crafted JSON body directly to `/webhooks` with:
- `repository.owner.login` (or `organization.login`) = `"OrgA"` → so `verify_signature` selects `OrgA`'s `GitHubApp` and the HMAC computed with `OrgA`'s secret validates,
- `repository.full_name` = `"OrgB/victim-repo"` (a repo/stack belonging to a completely different, unrelated organization hosted on the same Shipit instance),
- `ref` / `after` set to any branch/SHA they choose.

`verify_signature` passes because the signature genuinely matches `OrgA`'s secret over the exact bytes sent; it never checks that `repository.full_name`'s owner matches `repository_owner`. `PushHandler` then resolves `OrgB/victim-repo`'s `Stack` and calls `stack.sync_github(expected_head_sha: <attacker-chosen sha>)`, enqueuing `GithubSyncJob` for `OrgB`'s stack [11](#0-10) . That job fetches commits from `OrgB`'s repo (using `OrgB`'s own GitHub credentials, since `stack.github_api` is derived from `repository.owner`, not from the webhook's signing org) up to the attacker-chosen SHA, appends them, and — if `OrgB`'s stack has `continuous_deployment` enabled — automatically schedules `ContinuousDeliveryJob`/`trigger_continuous_delivery`, triggering an unauthorized deploy [12](#0-11) [13](#0-12) .

This is exactly the same class of bug as the report: two fields inside one authenticated payload are supposed to refer to the same entity, but only one of them is bound to the authentication check (org-secret selection) while the other (repository full name) drives the actual state-changing action, so an attacker who legitimately controls one binding can substitute a different value for the other.

### Impact Explanation
An operator of any one org hosted on a shared Shipit instance can force GitHub sync and, if continuous deployment is enabled, an unauthorized deploy trigger for a completely unrelated organization's stack, without ever needing that other organization's webhook secret, API credentials, or Shipit session. This is a cross-repository/cross-organization write and can lead to an unauthorized deploy, matching the "Critical" impact bucket ("cross-repository writes, or an unauthorized deploy, rollback or merge").

### Likelihood Explanation
Requires only that the Shipit instance is configured to serve more than one GitHub organization (a documented, supported configuration) and that the attacker administers one of those organizations' GitHub Apps — no privileged Shipit account, GitHub App private key, or victim secrets are needed. The `/webhooks` endpoint is publicly reachable by design (it must accept unauthenticated deliveries from GitHub).

### Recommendation
Bind the org used for signature verification to the actual repository being acted on: after verifying the signature with the org resolved from the payload, re-derive/validate that `repository.full_name`'s owner matches (or is otherwise authorized under) that same org before dispatching to handlers, or resolve the signing org from the installation/app credentials rather than from attacker-controlled payload fields, and reject payloads where `repository.owner.login` does not match the resolved signing organization.

### Proof of Concept
1. Configure Shipit with two orgs, e.g. `OrgA` and `OrgB`, each with distinct `webhook_secret`s (per `docs/setup.md`'s multi-app schema) and each with a stack, `OrgA/repoA` and `OrgB/repoB` (with `OrgB/repoB` set to `continuous_deployment: true`).
2. As the administrator of `OrgA`'s GitHub App, know `OrgA`'s `webhook_secret`.
3. Build a JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha-that-exists-on-OrgB/repoB>",
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/repoB" }
}
```
4. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(OrgA_webhook_secret, body)>`.
5. `POST /webhooks` with header `X-Github-Event: push` and the above body/signature.
6. `verify_signature` resolves `Shipit.github(organization: "OrgA")` and validates successfully (signature matches `OrgA`'s secret over the exact body). `PushHandler` then resolves stacks via `repository.full_name` = `"OrgB/repoB"`, calling `stack.sync_github(expected_head_sha: ...)` — enqueuing a `GithubSyncJob` (and potentially a continuous-delivery deploy) for `OrgB`'s stack, despite the request never being signed by `OrgB`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

    def perform(params)
      @stack = Stack.find(params[:stack_id])
      expected_head_sha = params[:expected_head_sha]
      retry_count = params[:retry_count] || 0
      head_before_sync = spec_cache_target
      appended_commits = []

      handle_github_errors do
        new_commits, shared_parent = fetch_missing_commits { stack.github_commits }

        # Retry on Github eventual consistency: webhook indicated new commits but we found none
        if expected_head_sha && new_commits.empty? && !commit_exists?(expected_head_sha) &&
           retry_count < MAX_RETRY_ATTEMPTS
          GithubSyncJob.set(wait: RETRY_DELAY * retry_count).perform_later(params.merge(retry_count: retry_count + 1))
          return
        end

        stack.transaction do
          shared_parent&.detach_children!
          appended_commits = new_commits.map do |gh_commit|
            append_commit(gh_commit)
          end
          stack.lock_reverted_commits! if appended_commits.any?(&:revert?)
        end
      end
      sync_changed_nothing = appended_commits.empty? &&
                             spec_cache_target == head_before_sync &&
                             stack.cached_deploy_spec.present?
      return if sync_changed_nothing && !params[:force_spec_cache]

      CacheDeploySpecJob.perform_later(stack)
    end
