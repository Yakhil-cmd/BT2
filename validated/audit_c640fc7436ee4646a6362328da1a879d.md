### Title
Unbounded growth of `handledChainsCache` allows memory-exhaustion via private payment chain messages - ([File: wallet.js])

### Summary
`wallet.js` maintains a process-wide, unbounded in-memory cache (`handledChainsCache`) keyed by the hash of the received `chains` payload of a `private_payment` device message. Any paired device / private-payment counterparty can send arbitrarily many distinct (even trivially varied) chain payloads to a wallet, and each distinct payload creates a new permanent entry that is only evicted after a full hour, and only if it is older than an hour when the hourly sweep runs.

### Finding Description
`handlePrivatePaymentChains` computes `cache_key = objectHash.getBase64Hash(arrChains)` from the attacker-supplied `body.chains` and unconditionally stores it in the module-level object `handledChainsCache`, with no size cap and no per-sender rate limit: [1](#0-0) [2](#0-1) 

The only validation performed before the entry is cached is a shallow structural check (`isNonemptyArray`, `isNonemptyObject`, presence of `unit`/`payload.asset`/`inputs`/`outputs`) — it does not verify that the chain is cryptographically valid, that the referenced units exist, or that the sender is authorized to send on behalf of the claimed asset/address: [3](#0-2) 

Because the cache key is derived from the full serialized content of `chains` (hashed with `getBase64Hash`), an attacker can trivially generate a large number of distinct keys by varying any inconsequential field (e.g., a nonce, or a bogus but structurally valid unit id string) in the payload, each producing a new permanent object in `handledChainsCache` until the next hourly sweep. The sweep itself only removes entries whose *insertion timestamp* is more than an hour old, so an attacker sending payloads continuously can keep the cache growing indefinitely between sweeps, and each sweep still leaves an hour's worth of accumulated garbage resident in memory.

This mirrors the CWE-770 pattern in the referenced ckb advisory: an attacker-controlled key space is used to grow an in-process `HashMap`/object without any size bound or per-peer accounting, eventually threatening to exhaust available memory on the receiving node/wallet process.

### Impact Explanation
A paired device or private-payment counterparty (an entity explicitly reachable per the analog rules) can cause unbounded memory growth on the victim's wallet process purely by sending a stream of `private_payment` messages with distinct, cheaply-generated `chains` payloads. This can degrade or crash the wallet process (denial of service against a single node/wallet), and because `handlePrivatePaymentChains` runs on every device message handling path before deeper validation, the attack surface is reachable by any correspondent who is already paired (a normal, low-privilege trust relationship, not an operator or hub role).

### Likelihood Explanation
Likelihood is high for a paired correspondent: no cryptographic proof, unit existence check, or fee payment is required before an entry is cached — only a structurally well-formed chain array. Generating new cache keys is cheap (varying a field and rehashing), and the growth is not throttled by rate limiting, size caps, or per-sender quotas.

### Recommendation
- Bound `handledChainsCache` with a maximum size (e.g., LRU eviction) instead of relying solely on a time-based sweep.
- Rate-limit or account for `private_payment` messages per sending device/correspondent before caching.
- Only cache the key after (or as part of) validating that the chain minimally references real, retrievable units, rather than caching based purely on shallow structural checks.

### Proof of Concept
1. Pair a device with the target wallet (a normal, expected trust relationship for private payments).
2. Repeatedly send `private_payment` messages via `handleMessageFromHub` → `handlePrivatePaymentChains` with `body.chains` payloads that pass the structural check in [3](#0-2)  but differ in a single field (e.g. dummy `unit` string), so each request computes a distinct `cache_key`.
3. Observe `handledChainsCache` (declared at [4](#0-3) ) grow without bound between hourly sweeps, consuming increasing process memory.

---

Note: I was unable to fully trace whether additional downstream consumers (`checkIfAllValidated`, `forwardPrivateChainsToOtherMembersOfSharedAddresses`) impose any implicit rate limiting or additional cost amplification beyond the cache growth itself, since those code paths were not fully inspected before the iteration budget was exhausted. This does not affect the core finding (the cache itself is unbounded and keyed by attacker-controlled data), but a full review of downstream cost per cached entry would strengthen the impact analysis.

function handlePrivatePaymentChains(ws, body, from_address, callbacks){
	var arrChains = body.chains;
	if (!ValidationUtils.isNonemptyArray(arrChains))
		return callbacks.ifError("no chains found");
	if (!arrChains.every(c =>
		isNonemptyArray(c) &&
		c.every(e =>
			isNonemptyObject(e) &&
			isNonemptyString(e.unit) &&
			isNonemptyObject(e.payload) &&
			isNonemptyString(e.payload.asset) &&
			isNonemptyArray(e.payload.inputs) &&
			isNonemptyArray(e.payload.outputs) &&
			e.payload.inputs.every(isNonemptyObject) &&
			e.payload.outputs.every(isNonemptyObject)
		)
	))
		return callbacks.ifError("malformed private chain");
	try {
		var cache_key = objectHash.getBase64Hash(arrChains);
	}
	catch (e) {
		return callbacks.ifError("chains hash failed: " + e.toString());		
	}
	if (handledChainsCache[cache_key]) {
		eventBus.emit('all_private_payments_handled', from_address);
		eventBus.emit('all_private_payments_handled-' + arrChains[0][0].unit);
		return callbacks.ifOk();
	}
