### Title
`StatusHandler#process` mutates commit statuses via a global `sha` lookup with zero repository resolution or ownership check - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Finding Description
The claimed binding is: `StatusHandler#process`'s write to `commit.statuses` must be preconditioned on `Repository.from_github_repo_name(payload['repository']['full_name'])` resolving to the repository that owns the target `Commit`'s `Stack`. Tracing the code shows this equality never exists.

`StatusHandler#process` does: [1](#0-0) 
It queries `Commit.where(sha: params.sha)` — a global, unscoped lookup across every `Stack`/`Repository` in the database — and calls `commit.create_status_from_github!(params)` on every match. It never calls `stacks` or `repository_name`, both of which exist on the base class specifically to scope handler mutations to the repository named in the webhook payload: [2](#0-1) 
Sibling handlers such as the label handlers correctly call `.stacks`/`repository.review_stacks` to constrain mutation to the reporting repository, but `StatusHandler` performs no such resolution.

The one existing guard, `WebhooksController#verify_signature`, only checks that the payload's HMAC signature matches the secret for `Shipit.github(organization: repository_owner)`: [3](#0-2) 
This proves the request was genuinely emitted by GitHub for *some* repository the sender controls — it does **not** prove that the `sha` in the payload belongs to a commit under that same repository's stacks. Git commit SHAs are content-addressed and identical across forks/mirrors that share history. An attacker who owns (or has push/status access to) any repository sharing commit history with a victim repository tracked by Shipit — e.g., a public fork — can push/replicate a commit that already exists in the victim's history (same SHA) and then emit a real, validly signed `status` webhook event for their own repository referencing that shared SHA (e.g., via the GitHub Statuses API on their own repo). Because `StatusHandler` never checks that `params.repository`/`repository_name` corresponds to the commit's actual stack, `Commit.where(sha: params.sha)` will match the victim's `Commit` row regardless of which repository actually sent the webhook, and `create_status_from_github!` mutates it.

### Impact Explanation
This allows one repository's legitimate (self-signed, real GitHub) webhook traffic to mutate `Commit#statuses` belonging to a completely different repository's `Stack`, satisfying the Critical category "a payload for one repository mutating another's stack, commit, task or team." Commit statuses drive Shipit's mergeability/deployability checks (`Commit#create_status_from_github!` feeds into status aggregation used elsewhere for gating merges/deploys), so a forged status can be used to poison or spoof another tenant's commit state. This is repeatable against any commit whose SHA is shared across repositories tracked by different Shipit stacks (trivially achievable via forks of the same upstream), and the blast radius spans all stacks/repositories configured on the same Shipit instance.

### Likelihood Explanation
Preconditions: the attacker needs webhook delivery for a `status` event from a repository they control (fork or any repo with the Shipit GitHub App/webhook attached), and a commit SHA that also exists as a `Commit` row belonging to a different stack — trivially satisfied for any commit shared via git history (forks, mirrors, cherry-picked/merged commits). No Shipit secrets, sessions, or API tokens are required; only ordinary GitHub repository capabilities (push, or Statuses API write on their own repo) are needed. This is low-cost and repeatable per targeted SHA.

### Recommendation
In `StatusHandler#process`, scope the `Commit` lookup to commits whose stack belongs to the reporting repository, mirroring the base `Handler#stacks` pattern used by other handlers, e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` (or join `Commit` through `Stack`/`Repository` filtered by `repository_name`), instead of the unscoped `Commit.where(sha: params.sha)`.

### Proof of Concept
Minitest plan (`test/models/webhooks/handlers/status_handler_test.rb`):
1. Create two `Stack`/`Repository` fixtures, `victim_repo` and `attacker_repo`.
2. Create a `Commit` under `victim_repo`'s stack with a known `sha`.
3. Build a `status` webhook payload where `payload['repository']['full_name']` is `attacker_repo`'s full name, but `sha` matches the victim commit's sha.
4. `Shipit::Repository.expects(:from_github_repo_name).never` (or `.stubs(:from_github_repo_name).raises("should not be called")`).
5. Call `Shipit::Webhooks::Handlers::StatusHandler.new(payload).process`.
6. Assert `victim_commit.statuses.count` increased and no exception was raised — proving the mutation succeeded with zero repository resolution, confirming the binding `Repository.from_github_repo_name(...) == commit.stack.repository` is never checked.
