## Title
Transaction Pool Admission Has No Priority-Based Eviction, Allowing Size-Limited Pool to Be Filled with Low-Value Transactions to Block Better Ones - (File: `chain/pool/src/lib.rs`)

## Summary
`TransactionPool::insert_transaction` enforces an optional hard `total_transaction_size_limit` and rejects any new transaction with `InsertTransactionResult::NoSpaceLeft` once that limit is reached, with no mechanism to evict lower-priority/lower-value transactions already resident in the pool to make room for a "better" incoming transaction.

## Finding Description
The pool tracks a running `total_transaction_size` and compares it against an optional `total_transaction_size_limit` on every insert: [1](#0-0) 

If the new transaction would push the total size over the limit, it is unconditionally rejected via `InsertTransactionResult::NoSpaceLeft`, regardless of how much more useful/valuable that transaction is than the ones already occupying the pool. Transactions are only removed from the pool when they are included in a block or explicitly evicted for other reasons (e.g. reorg cleanup) — there is no "worst transaction eviction" or "quality comparison" logic analogous to what would be needed to admit a better transaction when the pool is full.

The caller in the RPC handler surfaces this directly and only retries forwarding, it never attempts to bump a lower-priority transaction out of the local pool: [2](#0-1) 

This mirrors the reported bug class: a bounded/capacity-limited admission structure that rejects new, potentially higher-value entries once full, with no eviction of the weakest existing entries. In the `API3Market.sol` report, the queue was explicitly compared by `endTimestamp` quality; here, the pool has no notion of transaction "quality" at admission time — size is the only criterion — so any account with enough balance to pay for a stream of valid transactions can occupy the size-limited pool with minimal-value transactions (e.g., 1-yoctoNEAR transfers) and cause `NoSpaceLeft` for other users' transactions, including transactions that any protocol-level fairness policy would prefer to include first (e.g., high value/urgent transfers).

## Impact Explanation
Because pool inclusion order is randomized by `key_seed`/`PoolKey` rather than prioritized by fee or value, and because there is no eviction of low-quality entries when the pool is at capacity, an attacker who continuously submits minimal-cost valid transactions can keep the per-shard pool at its size limit. This causes legitimate transactions from other accounts to be rejected at the RPC layer (`InsertTransactionResult::NoSpaceLeft`) until the attacker's own transactions are included and removed. This is a temporary but real chunk-producer-local denial-of-service/griefing vector against transaction admission for a shard, degrading availability of the tx pool for all other unprivileged accounts targeting that shard.

## Likelihood Explanation
Exploitability depends on whether `pool_size_limit`/`total_transaction_size_limit` is configured to a value low enough to be filled by an attacker with modest funds; the search confirms it is `Option<u64>` and configurable (present in `nearcore/src/config.rs`, `client_config.rs`), but I could not fully verify from the index what the default production value is or whether it is tight enough in practice to make the attack cheap on mainnet. This uncertainty affects the severity/likelihood assessment and should be validated further (e.g. by checking `core/chain-configs/src/client_config.rs` default and any per-node/shard scaling) — the index did not return the exact default constant during this session.

## Recommendation
- Consider replacing the pure size-based reject-when-full policy with an eviction policy that compares the incoming transaction's priority (e.g., effective gas price, deposit, or another protocol-defined "quality" metric) against the lowest-priority transaction currently in the pool, evicting the latter if the incoming transaction is strictly better — analogous to recommendation 2 in the referenced report, with a minimum-value floor to prevent the eviction mechanism itself from being gamed.
- Alternatively, increase per-account/per-key limits within the pool (similar to the vendor's stated mitigation of relaxing a hard cap) so that a single or few accounts cannot exhaust the size-limited slot economy, and/or apply a per-account quota within the shared pool independent of the global size limit.

## Proof of Concept
Not independently reproduced in this session (no execution environment available); the vulnerability is inferred from static analysis of `chain/pool/src/lib.rs::insert_transaction` (rejects on overflow of `total_transaction_size_limit`, no eviction logic) and `chain/client/src/rpc_handler.rs` (`InsertTransactionResult::NoSpaceLeft` handling), both of which show a capacity-limited, non-priority-evicting admission queue reachable directly from any account able to submit transactions.

    pub fn insert_transaction(
        &mut self,
        validated_tx: ValidatedTransaction,
    ) -> InsertTransactionResult {
        let tx_hash = validated_tx.get_hash();
        if self.unique_transactions.contains(&tx_hash) {
            return InsertTransactionResult::Duplicate;
        }
        // We never expect the total size to go over `u64` during real operation as that would
        // be more than 10^9 GiB of RAM consumed for transaction pool, so panicking here is intended
        // to catch a logic error in estimation of transaction size.
        let new_total_transaction_size = self
            .total_transaction_size
            .checked_add(validated_tx.wire_size())
            .expect("Total transaction size is too large");
        if let Some(limit) = self.total_transaction_size_limit {
            if new_total_transaction_size > limit {
                return InsertTransactionResult::NoSpaceLeft;
            }
        }

        // At this point transaction is accepted to the pool.

        // This is guaranteed to succeed because of the check above that the
        // hashset does not contain this hash.  This can be improved once the
        // entries API is stabilized
        // (https://github.com/rust-lang/rust/issues/60896).
        assert_eq!(self.unique_transactions.insert(tx_hash), true);
        self.total_transaction_size = new_total_transaction_size;
        let signer_id = validated_tx.signer_id();
        let signer_public_key = validated_tx.public_key();
        self.transactions
            .entry(self.key(signer_id, signer_public_key, validated_tx.nonce().nonce_index()))
            .or_insert_with(Vec::new)
            .push(validated_tx);

        self.transaction_pool_count_metric.inc();
        self.transaction_pool_size_metric.set(self.total_transaction_size as i64);
        InsertTransactionResult::Success
    }
