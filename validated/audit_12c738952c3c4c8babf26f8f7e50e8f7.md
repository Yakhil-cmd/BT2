Confirmed root cause: `Shipit::WebhooksController#verify_signature` selects **which** GitHub App's `webhook_secret` to validate the HMAC against using `repository_owner`, derived from `params.dig('repository', 'owner', 'login')` (falling back to `params.dig('organization', 'login')`) — attacker-controlled fields inside the *unverified* raw JSON body. The HMAC signature is computed over the *entire* raw payload, but it only proves the payload was signed by *some* configured organization's secret; it does not bind the signature to the specific `repository.full_name` that the downstream event handlers act on (e.g. `Shipit::Webhooks::Handlers::PushHandler` / `Handler#repository_name`, which reads `payload.dig('repository', 'full_name')` to resolve the target `Stack`).

### Title
Webhook signature validated against attacker-chosen organization while event handlers act on an unbound repository field — cross-repository writes - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
In multi-organization Shipit installations (`Shipit.github_organizations` > 1, each with its own `webhook_secret`), the webhook signature check picks the verification secret from `repository.owner.login`/`organization.login` in the untrusted payload body, then hands the *same* fully attacker-controlled payload to handlers that key off `repository.full_name` to find the `Stack`/`Repository` to act on.

### Finding Description
`WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-49`) does:
```ruby
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
```
`repository_owner` (`webhooks_controller.rb:59-62`) is read straight from the JSON body the attacker POSTs. `Shipit.github(organization:)` (`lib/shipit.rb:170-181`) looks up a *per-organization* `webhook_secret` from `secrets.github[org]`.

Because the attacker fully controls the raw POST body, an attacker who is a legitimate member/admin of **any one** organization configured on the shared Shipit instance (and therefore knows/can generate that org's `webhook_secret` via GitHub's own webhook delivery for their own repo) can craft a synthetic payload where:
- `repository.owner.login` = their own organization (so `verify_signature` picks *their* secret and the HMAC they compute validates), and
- `repository.full_name` = a **different** organization/repository's `owner/name` that the target stack handlers use to resolve the `Stack` (e.g. `PushHandler` → `Handler#repository_name` at `app/models/shipit/webhooks/handlers/handler.rb:36-38`, or any `pull_request/*` handler using `params.repository.full_name`).

There is no code path enforcing `repository.owner.login == repository.full_name.split('/').first`. This breaks the intended binding: `organization that authenticated == repository that is written`.

### Impact Explanation
A successfully forged, validly-"signed" webhook can trigger `stack.sync_github` and other repository-scoped webhook side effects (e.g. archiving/unarchiving review stacks via `provisioning_behavior`, updating `PullRequest` records, syncing commits) for a **stack belonging to a different organization/repository** than the one whose secret was actually used to sign the request. This is a cross-repository write from an attacker who is not authorized on the victim repository at all — satisfying the Critical "cross-repository writes" bar, since it originates from a completely unauthenticated public endpoint (`/webhooks`) requiring only knowledge of one org's own webhook secret (which that org's own admins legitimately possess, not the target org's).

### Likelihood Explanation
Requires the Shipit instance to be configured with multiple GitHub organizations (`config/secrets.yml` `github:` keyed by org, as documented in `docs/setup.md:182-209`), and requires the attacker to control (or be an admin of) at least one such organization installed on the shared Shipit instance — a realistic scenario for centrally-hosted, multi-tenant Shipit deployments. No GitHub App private key, session, or `ApiClient` token is needed; only a raw HTTP POST to the public `/webhooks` endpoint.

### Recommendation
Bind the signature verification to the same repository/organization identity that handlers subsequently act on: either (a) verify the signature using a secret keyed off the same field used for stack lookup (`repository.full_name`'s owner segment) rather than falling back to a separately-controllable `organization.login`, or (b) after choosing the app/secret from `repository_owner`, additionally assert that `repository.full_name`'s owner segment matches `repository_owner` before dispatching to handlers, rejecting mismatches with `422`.

### Proof of Concept
1. Attacker is an admin of GitHub org `attacker-org`, which is one of several orgs configured in this shared Shipit instance's `secrets.github`, and thus attacker knows `attacker-org`'s `webhook_secret` (obtainable by installing/inspecting their own GitHub App webhook config or via a real delivery from their own org).
2. Attacker crafts a JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(attacker-org's webhook_secret, body)>` and sets `X-Github-Event: push`.
4. POST to `/webhooks`. `verify_signature` resolves `Shipit.github(organization: "attacker-org")` and the HMAC validates successfully.
5. `Shipit::Webhooks.for_event('push')` dispatches to `PushHandler`, which resolves `stacks` via `Repository.from_github_repo_name("victim-org/victim-repo")` (`app/models/shipit/webhooks/handlers/handler.rb:32-38`) and calls `stack.sync_github(expected_head_sha: ...)` on the victim's stack — a write triggered on a repository the attacker does not control, using a signature that was only ever validated against the attacker's own organization's secret. module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
    end

If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently.
