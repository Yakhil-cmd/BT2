## Title
Unhandled TypeError in dry-run AA trigger detection crashes the node - (File: `network.js`)

### Summary
In `handleJoint`'s `ifOk` callback, when `conf.bDryRunNewTriggers` is enabled, the code collects payment output addresses from an incoming unit by directly dereferencing `msg.payload.outputs` without checking that `payload` exists: [1](#0-0) 

This mirrors the CVE-2021-2020 bug class: a low-privileged, unauthenticated party can submit ordinary, protocol-valid input (a unit) that triggers a crafted code path in the node's optimizer-like preprocessing logic, producing a crash instead of a normal query/validation result.

### Finding Description
`payment` messages in ocore are not required to carry a `payload` field. Private-asset payments are validated with `payload_location`/`spend_proofs` semantics, where the actual output data is withheld from the public unit and only a spend proof is included; the `payload` key can legitimately be absent from a public payment message of app `payment`. This is enforced throughout `validate()`/`validateMessages()` in `validation.js`, which explicitly branches on `payload_location` (public / private / none) rather than assuming `payload` is always present.

Meanwhile, `network.js` builds `outputAddresses` purely to find whether the unit is a trigger for some `aa_addresses` row, and does so with:
```js
const outputAddresses = objJoint.unit.messages
    .filter(msg => msg.app === 'payment')
    .reduce((acc, msg) => acc.concat(msg.payload.outputs.map(output => output.address)), []);
``` [2](#0-1) 

Any unit that contains **at least one** `payment` message app whose `payload` is missing (e.g. a private-asset payment message, or `payload_location: 'none'`/`'uri'` variants) alongside any other message causes `msg.payload.outputs` to throw `TypeError: Cannot read properties of undefined (reading 'outputs')`. This throw happens synchronously inside the `.reduce()` callback, inside the `async` `ifOk` handler of `handleJoint`: [3](#0-2) 

Because this is a synchronous throw inside an `async function` that is not wrapped by a `try/catch` here, and this call stack does not go through `validation.js`'s controlled error paths, the exception bubbles up as an unhandled promise rejection / uncaught exception. The top-level handler intentionally treats any uncaught exception as fatal:
```js
process.on('uncaughtException', (err) => {
    ...
    throw err; // crash the process to avoid ending up in an inconsistent state
});
``` [4](#0-3) 

This deliberately crashes the whole ocore node process.

### Impact Explanation
Any unprivileged unit poster (a light client posting via `handlePostedJoint`, or any full node peer forwarding a joint) can craft a syntactically valid unit that:
1. Sends a public payment to an address that is registered as an AA address (`aa_addresses`), making `objValidationState.count_primary_aa_triggers` truthy, and
2. Includes a second `payment` message that omits `payload` (e.g., a private-asset transfer message, valid per `validation.js`'s private-payment handling).

Once this unit passes normal validation and reaches `ifOk`, the dry-run pre-check throws an uncaught `TypeError`, which crashes the receiving node via the `uncaughtException` handler. This satisfies "a network unable to confirm new units" / node-crash DoS, matching the accepted impact classes (this is a crash of the local node process reachable by any unit sender, not a malicious-peer/network-only bug — the crash is caused by unit *content*, not connection-level abuse).

### Likelihood Explanation
- Reaching this code requires only that `conf.bDryRunNewTriggers` is enabled (a normal, documented full-node feature flag) and `!conf.bLight` (i.e., affects full/hub nodes) and that the unit is not yet stable (`!objJoint.ball`).
- Constructing a unit with a public AA-trigger payment plus a private-asset payment message is a standard, protocol-legal shape — no exotic or malformed data is required, only a combination the developers apparently did not anticipate when writing this dry-run shortcut.
- No special privileges, keys, or trusted relationship are needed; a single crafted unit posted or broadcast by any user reaches this code path in any node running with `bDryRunNewTriggers` enabled.

### Recommendation
Guard the reduce against missing `payload`:
```js
const outputAddresses = objJoint.unit.messages
    .filter(msg => msg.app === 'payment' && msg.payload && Array.isArray(msg.payload.outputs))
    .reduce((acc, msg) => acc.concat(msg.payload.outputs.map(output => output.address)), []);
```
Additionally, wrap the whole `bDryRunNewTriggers` block in a `try/catch` so any dry-run failure is logged and skipped rather than allowed to crash the node, consistent with the comment's intent ("if it would crash, let it crash now, not when we execute the trigger for real") which should apply to the *AA execution itself*, not to this address-extraction bookkeeping.

### Proof of Concept
1. Register/use an existing AA address `X` (any AA on the network).
2. Craft and post a unit with two `payment` messages:
   - Message 1: public `payment` app, `asset` omitted (base), with an output to `X` and sufficient amount to trigger the AA (satisfies `count_primary_aa_triggers`).
   - Message 2: a private-asset `payment` app message conforming to the private-payment format accepted by `validation.js` (i.e., `payload` absent, referencing an existing private asset the attacker controls or has legitimately received, satisfying `payload_location`/spend-proof checks).
3. Post this unit to a full hub/node running with `conf.bDryRunNewTriggers = true`.
4. Once the unit passes `validation.validate()` and `ifOk` runs, `objJoint.unit.messages.filter(...).reduce(...)` executes `msg.payload.outputs` on the private-payment message where `payload` is `undefined`, throwing a `TypeError`.
5. The exception is not caught locally, becomes an uncaught exception, and the process crashes via the handler in `network.js:4530-4543`.

**Note:** I was unable to fully confirm within the available tool budget (a) the exact default value of `conf.bDryRunNewTriggers` in the shipped `conf.js` (the grep for it in `conf.js` returned no matches, so it may only be set in deployment-specific config or default to `undefined`/falsy), and (b) the precise structural constraints ocore's `validation.js` enforces on private payment messages that determine whether `payload` can be entirely absent from a `payment` message while `app === 'payment'` still holds true within the same unit as a public AA-triggering payment. These are important to fully validate exploitability, and I recommend a Devin session with full repository/test access to confirm the default config value and construct/execute a concrete unit against `test/` fixtures to prove the crash reproducibly.
