### Title
Fee-on-transfer-style silent under-transfer in `pallet-psm::mint`/`redeem` due to unchecked `Fungibles::transfer` return value - (File: `substrate/frame/psm/src/lib.rs`)

### Summary
`pallet-psm`'s `mint` and `redeem` extrinsics move funds via `T::Fungibles::transfer(...)` and then credit/debit the counter-asset based on the *requested* amount rather than the amount the call actually returns. The generic default implementation of `fungibles::Mutate::transfer` (`substrate/frame/support/src/traits/tokens/fungibles/regular.rs:373-393`) decreases the source balance with `Precision::BestEffort` but discards the returned "actual decreased" value and unconditionally reports `Ok(amount)` (the requested amount) to the caller — the FRAME analogue of an ERC20 fee-on-transfer token silently moving less than requested while the caller's accounting assumes the full amount landed.

### Finding Description
In the Sherlock report, `SemiFungibleVault.deposit()` mints shares equal to the *requested* `assets` value without verifying that `asset.safeTransferFrom` actually moved that much (fee-on-transfer tokens transfer less). The same "assume requested == actual" pattern exists in this codebase.

`fungibles::Mutate::transfer`'s default body: [1](#0-0) 

calls `decrease_balance(..., BestEffort, ...)` — meaning the source may legitimately be debited *less* than `amount` (e.g. dust/ED interactions, `Preservation::Preserve`/`Protect` edge cases, or provider-count/hold interactions) — yet the return value of `decrease_balance` is thrown away with `?`, `increase_balance(dest, amount, BestEffort)` still deposits the full requested `amount` into `dest`, and the function returns `Ok(amount)` regardless of what was actually moved out of `source`.

The codebase's own authors are aware this class of bug is real and dangerous: `substrate/frame/asset-conversion/ops/src/lib.rs` explicitly guards against it — [2](#0-1) 
— by checking `balance1 == T::Assets::transfer(...)?` and erroring with `Error::<T>::PartialTransfer` if not. Likewise, `prdoc/pr_12366.prdoc` documents a real, shipped fix for exactly this bug class in `pallet-assets::transfer_ownership`, where a partial `repatriate_reserved` remainder was previously silently discarded: [3](#0-2) 

`pallet-psm`, however, does **not** apply this same defensive check. In `mint`, the external-asset transfer's return value is discarded via `?`, and `internal_to_user`/`fee` are minted based on `internal_equivalent` computed from `effective_external` (the *requested* transfer amount), not the actual amount received by the PSM reserve account: [4](#0-3) 

Symmetrically, in `redeem`, the external-asset payout to the user is also unchecked: [5](#0-4) 

`Config::Fungibles` is a generic bound (`FungiblesMutate<Self::AccountId, AssetId = Self::AssetId>`): [6](#0-5) 
so any runtime that wires a `Fungibles` backend which does not override the default `transfer` (or whose override can legitimately return less than requested, analogous to a fee-on-transfer token) inherits this exact accounting bug: the PSM would mint internal stablecoin backed by less external collateral than recorded in `PsmDebt`, silently under-collateralizing the peg and letting later redeemers drain the reserve, exactly mirroring the Sherlock report's `sendTokens`/`ClaimTVL` mismatch.

### Impact Explanation
If the transfer under-delivers relative to the requested `effective_external`, `PsmDebt` is incremented by the full `internal_equivalent` while the reserve only received a lesser amount, permanently under-collateralizing the internal asset for that (internal, external) pair. Later redeemers who call `redeem` will find `InsufficientReserve`/`Unexpected` (a defensive halt) or, in the more severe case, later redeemers earlier in the queue succeed while later ones cannot — a direct funds-loss/DoS on that PSM instance, analogous to the "last withdrawer cannot withdraw" and "steal funds from later withdrawers" impacts in the original report.

### Likelihood Explanation
This requires the `Fungibles` implementation configured for a specific runtime's PSM instance to actually produce actual-transferred < requested under normal parameters (not a privileged/malicious actor) — I was not able to fully verify within the tool-call budget whether the concrete `pallet-assets` `impl_fungibles.rs` overrides `transfer` with an equivalent guard, or falls back to this vulnerable default. This is the primary uncertainty in this analog: without confirming a concrete, reachable code path where `pallet-assets` (or another shipped `Fungibles` backend actually used by `T::Fungibles` in a production runtime) returns less than requested under attacker-reachable, permission-less conditions, this remains a code-pattern/defense-in-depth gap rather than a confirmed exploitable Critical/High. Given the project's own precedent (`pallet-assets: transfer_ownership` fix, `asset-conversion/ops` explicit checks) treating unchecked partial transfers as a real, fixable bug class, I assess this as a genuine Medium-severity finding, matching the severity of the original report, pending confirmation of a concrete backend exhibiting partial-transfer behavior in a live runtime.

### Recommendation
In `pallet-psm::mint` and `pallet-psm::redeem`, capture the `Result<Balance, DispatchError>` returned by every `T::Fungibles::transfer(...)` call and assert it equals the amount that was intended to move (mirroring the pattern already used in `substrate/frame/asset-conversion/ops/src/lib.rs`), erroring out (and rolling back) on any shortfall rather than proceeding to mint/burn/credit based on the requested amount. Additionally, consider hardening the shared default `fungibles::Mutate::transfer` implementation to propagate and check the actual `decrease_balance` result instead of discarding it, since multiple pallets rely on this default and could be silently exposed to the same class of bug.

### Proof of Concept
No executable PoC was produced. Confirming exploitability would require identifying a concrete `Fungibles`/`fungible` backend wired into a production runtime's `pallet-psm::Config::Fungibles` that legitimately returns `actual < amount` under non-privileged, attacker-reachable conditions (e.g. relying on the default `transfer` trait body shown above without an overriding, exactness-enforcing implementation), then constructing a signed `pallet_psm::mint` extrinsic with such an asset and asserting `PsmDebt` exceeds the PSM reserve account's true external-asset balance afterward. This step (verifying `pallet-assets`' own `fungibles::Mutate::transfer` override behavior in `substrate/frame/assets/src/impl_fungibles.rs`) was not completed due to tool-call budget exhaustion, so deployment/PoC-execution status is: **not run / not verified**.

	fn transfer(
		asset: Self::AssetId,
		source: &AccountId,
		dest: &AccountId,
		amount: Self::Balance,
		preservation: Preservation,
	) -> Result<Self::Balance, DispatchError> {
		let _extra = Self::can_withdraw(asset.clone(), source, amount)
			.into_result(preservation != Expendable)?;
		Self::can_deposit(asset.clone(), dest, amount, Extant).into_result()?;
		if source == dest {
			return Ok(amount);
		}

		Self::decrease_balance(asset.clone(), source, amount, BestEffort, preservation, Polite)?;
		// This should never fail as we checked `can_deposit` earlier. But we do a best-effort
		// anyway.
		let _ = Self::increase_balance(asset.clone(), dest, amount, BestEffort);
		Self::done_transfer(asset, source, dest, amount);
		Ok(amount)
	}
