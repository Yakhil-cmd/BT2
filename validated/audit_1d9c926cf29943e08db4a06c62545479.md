### Title
Deflationary ERC20 Token Accounting Discrepancy Drains Source Bridge Reserves — (`contracts/service_chain/bridge/BridgeTransferERC20.sol`)

### Summary

`BridgeTransferERC20.requestERC20Transfer` and `onERC20Received` record the caller-supplied `_value` in the `RequestValueTransfer` event without verifying the actual token amount received by the bridge. When a registered deflationary ERC20 token (one that deducts a fee on every transfer) is used, the bridge receives fewer tokens than `_value`, but the counterpart bridge releases the full `_value` to the recipient. In lock/unlock mode this creates a permanent per-transfer shortfall in the source bridge's reserves, eventually making it insolvent and preventing legitimate users from withdrawing their bridged assets.

---

### Finding Description

In `requestERC20Transfer`:

```solidity
// BridgeTransferERC20.sol line 133-134
IERC20(_tokenAddress).safeTransferFrom(msg.sender, address(this), _value.add(_feeLimit));
_requestERC20Transfer(_tokenAddress, msg.sender, _to, _value, _feeLimit, _extraData);
``` [1](#0-0) 

The bridge pulls `_value + _feeLimit` from the user, but for a deflationary token with transfer-fee rate `r`, it actually receives `(_value + _feeLimit) × (1 − r)`. No balance-before/after check is performed.

Inside `_requestERC20Transfer`, the bridge then pays the bridge fee and refunds excess `_feeLimit` to the user — both of which are additional deflationary transfers that further reduce the bridge's actual balance:

```solidity
// BridgeTransferERC20.sol line 91
uint256 fee = _payERC20FeeAndRefundChange(_from, _tokenAddress, _feeLimit);
``` [2](#0-1) 

After all transfers, the bridge holds approximately `_value × (1 − r) − _feeLimit × r` tokens, but the event emits the full `_value`:

```solidity
// BridgeTransferERC20.sol lines 97-106
emit RequestValueTransfer(
    TokenType.ERC20, _from, _to, _tokenAddress,
    _value,          // ← nominal amount, not actual received
    requestNonce, fee, _extraData
);
``` [3](#0-2) 

The counterpart bridge's operators relay this event and call `handleERC20Transfer` with the same `_value`, releasing the full amount to the recipient:

```solidity
// BridgeTransferERC20.sol line 71
IERC20(_tokenAddress).safeTransfer(_to, _value);
``` [4](#0-3) 

`BridgeTokens.sol` enforces only that a token is registered and unlocked — there is no guard against deflationary or rebasing token behavior:

```solidity
// BridgeTokens.sol lines 32-35
modifier onlyRegisteredToken(address _token) {
    require(registeredTokens[_token] != address(0), "not allowed token");
    _;
}
``` [5](#0-4) 

The same flaw exists in the 1-step path `onERC20Received`, where the token contract itself reports `_value` but the bridge has already received less:

```solidity
// BridgeTransferERC20.sol line 120
_requestERC20Transfer(msg.sender, _from, _to, _value, _feeLimit, _extraData);
``` [6](#0-5) 

---

### Impact Explanation

**Lock/unlock mode (`modeMintBurn = false`):**

Per transfer, the source bridge accumulates a shortfall of `(_value + _feeLimit) × r` tokens (where `r` is the deflationary rate). After `N` transfers the bridge is short `N × (_value + _feeLimit) × r` tokens. When users attempt to bridge back, `handleERC20Transfer` on the source bridge calls `safeTransfer(_to, _value)` but the bridge no longer holds enough tokens — the call reverts and users cannot recover their bridged assets. This is an unauthorized drain of bridged ERC20 reserves held by the source bridge.

**Mint/burn mode (`modeMintBurn = true`):**

`ERC20Burnable(_tokenAddress).burn(_value)` is called after the deflationary `safeTransferFrom`, so the bridge tries to burn more than it received. This causes a revert, making the bridge completely unusable for that token — a denial-of-service on the bridge for that asset.

---

### Likelihood Explanation

- Any user can call `requestERC20Transfer` once a deflationary token is registered by the bridge owner. The bridge owner registration is a one-time setup step; exploitation requires no further privileged action.
- The `onERC20Received` path is callable by anyone who holds the deflationary token and triggers a transfer to the bridge, requiring no approval step.
- The shortfall is deterministic and accumulates with every transfer, making insolvency inevitable rather than probabilistic.

---

### Recommendation

Record the bridge's actual token balance before and after the `safeTransferFrom` and use the difference as the canonical transfer amount:

```solidity
function requestERC20Transfer(
    address _tokenAddress, address _to,
    uint256 _value, uint256 _feeLimit, bytes memory _extraData
) public {
    uint256 before = IERC20(_tokenAddress).balanceOf(address(this));
    IERC20(_tokenAddress).safeTransferFrom(msg.sender, address(this), _value.add(_feeLimit));
    uint256 actualReceived = IERC20(_tokenAddress).balanceOf(address(this)).sub(before);
    // derive actual _value and _feeLimit from actualReceived, then proceed
    _requestERC20Transfer(_tokenAddress, msg.sender, _to, actualValue, actualFeeLimit, _extraData);
}
```

Alternatively, maintain a token whitelist that excludes deflationary and rebasing tokens.

### Proof of Concept

**Setup:** Deploy a deflationary ERC20 token that deducts 1% on every transfer. Register it on both the source and destination bridges in lock/unlock mode (`modeMintBurn = false`). Set bridge fee to 0 and `feeReceiver` to `address(0)` for simplicity.

**Steps:**

1. Alice holds 1 000 deflationary tokens. She approves the source bridge for 1 000 and calls:
   ```
   sourceBridge.requestERC20Transfer(token, bob, 1000, 0, "0x")
   ```
2. `safeTransferFrom(alice, sourceBridge, 1000)` executes. Due to the 1% deflationary fee, the source bridge receives **990** tokens.
3. `_requestERC20Transfer` emits `RequestValueTransfer` with `_value = 1000`.
4. Bridge operators observe the event and call `destBridge.handleERC20Transfer(..., 1000, ...)`.
5. The destination bridge transfers **1 000** counterpart tokens to Bob. Bob is fully satisfied.
6. Bob bridges back: destination bridge locks 1 000 counterpart tokens, emits event with `_value = 1000`.
7. Bridge operators call `sourceBridge.handleERC20Transfer(..., 1000, ...)`.
8. Source bridge calls `safeTransfer(bob, 1000)` but only holds **990** tokens → **revert**. Bob cannot withdraw.

**Shortfall per round-trip:** 10 tokens (1% of 1 000). After 100 such round-trips the source bridge is completely drained and all pending withdrawals fail.
