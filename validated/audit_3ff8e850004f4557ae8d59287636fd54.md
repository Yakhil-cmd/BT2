### Title
Cross-stack authorization bypass in `Shipit::Api::CCMenuController` due to unscoped `stack` lookup and instance-blind `check_permissions!` - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`ApiClient#check_permissions!` only checks whether the bare string `"#{operation}:#{scope}"` (e.g. `"read:stack"`) is present in the client's `permissions` array; it never compares against `stack.id` or `current_api_client.stack_id`. In most API controllers this is masked because `BaseController#stack` resolves the target stack through the `stacks` helper, which is scoped to `current_api_client.stack_id` when present. `CCMenuController` overrides `stack` to bypass that scoping entirely, so the missing instance-binding in `check_permissions!` becomes directly exploitable.

### Finding Description
The broken binding, stated as an equality: the code needs `current_api_client.stack_id == target_stack.id` (or "no stack_id restriction") AND `permissions.include?("read:stack")`, but it only ever checks `permissions.include?("read:stack")` [1](#0-0) .

- `require_permission :read, :stack` on `CCMenuController` triggers `require_permission!(:read, :stack)` before every action [2](#0-1) , which calls `current_api_client.check_permissions!(operation, scope)` [3](#0-2) .
- `check_permissions!` builds `required_permission = "#{operation}:#{scope}"` and checks `permissions.include?(required_permission)` — no reference anywhere to `stack.id` or `self.stack_id` [1](#0-0) .
- In `BaseController`, this gap is normally covered because the target stack is resolved via `stacks.from_param!(params[:stack_id])`, and `stacks` is defined as `current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all` [4](#0-3) . So an `ApiClient` scoped to stack A cannot even resolve stack B's record — a `RecordNotFound` results before any state is read.
- `CCMenuController` overrides this `stack` method with its own private method: `@stack ||= Stack.from_param!(params[:stack_id])`, calling `Stack.from_param!` directly on the unscoped model class instead of on the `stacks` relation [5](#0-4) . It also overrides `authenticate_api_client` to authenticate via `params[:token]` instead of Basic Auth, but this does not restore the stack-scoping [6](#0-5) .
- As a result, once `check_permissions!(:read, :stack)` passes (true for *any* `ApiClient` row holding the bare `'read:stack'` permission, regardless of its `stack_id`), `CCMenuController#show` fetches `stack.deploys_and_rollbacks.last` for whatever `stack_id`/slug the attacker supplies in the URL, unconstrained by the client's own `stack_id` [7](#0-6) .

Attacker exploit flow: obtain (or be given) any `ApiClient` token scoped to stack A with `permissions: ['read:stack']` (e.g., the `here_come_the_walrus` fixture pattern, an `ApiClient` legitimately minted for one stack) [8](#0-7) . Send `GET /stacks/:owner/:repo/:env/cc_menu.xml?token=<token>` where `:owner/:repo/:env` identify stack B, not stack A. `authenticate_api_client` succeeds since the token is valid, `check_permissions!(:read, :stack)` passes since the permission string matches, and `stack` resolves stack B unscoped — leaking stack B's deploy/rollback status via the rendered XML.

### Impact Explanation
This grants unauthenticated cross-tenant read of deploy/task state: any holder of a `read:stack`-scoped `ApiClient` token minted for one repository/stack can read the CC Menu status (latest deploy/rollback outcome, timing, running state) of any other stack in the Shipit instance, not just their own. This matches "unauthenticated read of stack state" for a repository that did not grant that client access — High severity, repeatable against arbitrary stacks with a single HTTP GET per target, no per-request cost beyond guessing/knowing the target's owner/repo/environment slug.

### Likelihood Explanation
Precondition: attacker must already control (or reuse) one legitimate `ApiClient` credential scoped to `read:stack` for any stack — this is the normal credential handed out to CI/monitoring tools for CCTray/CCMenu integration, a low-privilege, commonly distributed token. No GitHub secrets, session, or admin role needed. The attack is a single unauthenticated GET request with a known/guessable `stack_id` route param, fully repeatable.

### Recommendation
Bind the permission check to the specific stack instance rather than just the permission string, and fix the missing scoping in `CCMenuController`:
- In `ApiClient#check_permissions!`, when `stack_id` is present, also verify `stack_id == target.id` (accept the target stack/resource as a parameter) for stack-scoped operations.
- In `CCMenuController#stack`, resolve through the scoped `stacks` helper (i.e., `stacks.from_param!(params[:stack_id])`) instead of `Stack.from_param!`, consistent with `BaseController`, so a stack-scoped client cannot resolve stacks outside its `stack_id`.

### Proof of Concept
```ruby
# test/controllers/api/ccmenu_controller_test.rb (new test)
test "an ApiClient scoped to stack A cannot read stack B's cc_menu via check_permissions! alone" do
  stack_a = shipit_stacks(:shipit)
  stack_b = shipit_stacks(:cocaine_lint) # any other fixture stack
  client = shipit_api_clients(:here_come_the_walrus) # stack_id == stack_a.id, permissions: ['read:stack']

  # Equality claimed broken: client.stack_id (stack_a.id) != stack_b.id, yet check passes
  assert_equal stack_a.id, client.stack_id
  refute_equal client.stack_id, stack_b.id
  assert client.check_permissions!(:read, :stack) # passes with no reference to stack_b.id at all

  get :show, params: { stack_id: stack_b.to_param, token: client.authentication_token }
  assert_response :ok # demonstrates cross-stack leak; should be :not_found or :forbidden
end
```
