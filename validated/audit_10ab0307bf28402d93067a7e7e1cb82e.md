### Title
Webhook signature is verified against the organization derived from `repository.owner.login`, but events are routed and applied using the unrelated `repository.full_name` field, allowing a valid webhook secret for one GitHub organization to forge cross-organization/cross-repository webhook events - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
In multi-tenant Shipit deployments, each GitHub organization can be configured with its own distinct `webhook_secret` [1](#0-0) . `WebhooksController#verify_signature` selects *which* organization's secret to check the HMAC against by reading `params.dig('repository', 'owner', 'login')` from the **same untrusted, attacker-supplied JSON body** it is trying to authenticate [2](#0-1) [3](#0-2) . Once the signature check passes, every event handler routes and applies the event using a completely different field of the same body: `payload.dig('repository', 'full_name')` [4](#0-3) . No code checks that the organization whose secret authenticated the request actually owns the repository named in `full_name`.

### Finding Description
The binding that should hold is: `organization authenticated == owner of repository written`. Instead, the two fields are read independently from the same request body and never reconciled:

1. `verify_signature` picks the GitHub App/secret with `Shipit.github(organization: repository_owner)`, where `repository_owner` comes straight from the payload (`repository.owner.login`, falling back to `organization.login`) [2](#0-1) .
2. `verify_webhook_signature` merely proves the whole raw body was HMAC-signed with *that* organization's `webhook_secret`; it does not constrain the *content* of the body beyond matching the digest, so any payload the attacker (who possesses that organization's own webhook secret, which was legitimately issued to them for their own repos) chooses to craft will pass, provided `repository.owner.login`/`organization.login` in that payload matches the org they authenticate as [5](#0-4) .
3. Every handler (`PushHandler`, `StatusHandler`, `CheckSuiteHandler`, `PullRequest::*Handler`) then resolves the target `Repository`/`Stack` using `payload.dig('repository', 'full_name')` via `Handler#repository_name`/`#stacks` [4](#0-3)  or the equivalent `Shipit::Repository.from_github_repo_name(params.repository.full_name)` used by the pull-request handlers [6](#0-5) .
4. `PushHandler#process` uses that mismatched routing to enqueue `stack.sync_github(expected_head_sha: params.after)` for stacks matching the attacker-controlled `full_name`/branch, with `params.after` also fully attacker-controlled [7](#0-6) .

Before the attacker's request: `repository_owner (used to pick secret) == full_name's owner (used to pick repository)` holds for every legitimate GitHub-delivered webhook, because GitHub always emits both fields consistently for the real repository being pushed to. After the attacker's crafted request: the attacker sets `repository.owner.login = "OrgA"` (an org whose `webhook_secret` they legitimately hold, e.g. because they administer their own GitHub App entry in this shared, multi-tenant Shipit instance) while setting `repository.full_name = "OrgB/victim-repo"` (a repository/stack they do not own). The HMAC is computed over the whole raw body using OrgA's secret and validates, but the acted-upon resource is OrgB's stack — breaking the `organization authenticated == repository written` binding described in scope.

### Impact Explanation
This allows cross-tenant, cross-repository writes without any authorization on the target repository: an attacker who only controls one organization's webhook secret in a multi-tenant Shipit install can trigger `GithubSyncJob` (via `PushHandler`) against a stack belonging to a completely different, unrelated organization/repository, influencing `expected_head_sha` and forcing a resync of that victim stack. Depending on downstream consumers of `sync_github`/`GithubSyncJob`, this can affect which commit is treated as the branch head for deploy purposes on a repository/organization the attacker has no legitimate relationship with. It is exactly the "cross-repository writes" class of impact the rules classify as Critical, since it bypasses the intended per-organization trust boundary of the webhook endpoint entirely.

### Likelihood Explanation
The `/webhooks` endpoint is unauthenticated by design (it only relies on HMAC signature verification, `skip_before_action :verify_authenticity_token` [8](#0-7) ) and reachable by any external actor, so no session, API token, or repository write access is required — only knowledge of one organization's own configured `webhook_secret`, which that organization's legitimate GitHub App owner already possesses. In single-org Shipit installs this is not exploitable (there's only one secret and it is expected to authorize all events for the single configured org), but the codebase explicitly supports and ships a multi-organization configuration (`secrets_double_github_app.yml`) where each org gets an independent secret [9](#0-8) , making this a realistic configuration for shared/hosted Shipit deployments.

### Recommendation
After successfully verifying the signature for `repository_owner`, re-derive/validate the repository used for routing strictly from that same authenticated organization (e.g., assert that `payload.dig('repository', 'full_name')` starts with `"#{repository_owner}/"`, or resolve the target `Repository` only within stacks scoped to the authenticated organization) before dispatching to any `Webhooks::Handlers`. Reject the request if the two do not match.

### Proof of Concept
1. Deploy Shipit with the multi-org GitHub App configuration (as in `test/dummy/config/secrets_double_github_app.yml`), configuring `OrgA` (attacker-controlled) and `OrgB` (victim, hosting stack `OrgB/victim-repo`).
2. As the legitimate owner/admin of `OrgA`'s GitHub App, the attacker knows `OrgA`'s `webhook_secret`.
3. Craft a JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>",
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/victim-repo" }
}
```
4. Compute `X-Hub-Signature: sha1=<hmac-sha1(OrgA_webhook_secret, body)>` and POST to the Shipit `webhooks` route with `X-Github-Event: push`.
5. `verify_signature` resolves `repository_owner` = `"OrgA"`, fetches `OrgA`'s app/secret, and the signature validates [2](#0-1) .
6. `PushHandler` resolves `stacks` via `Repository.from_github_repo_name("OrgB/victim-repo")` [4](#0-3)  and enqueues `GithubSyncJob` with `expected_head_sha` set to the attacker-chosen SHA for `OrgB`'s stack [10](#0-9) , despite the attacker having no relationship whatsoever to `OrgB` or `victim-repo`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
