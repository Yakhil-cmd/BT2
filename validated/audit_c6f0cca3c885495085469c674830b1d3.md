## Analysis Result

Confirmed analog: `pallet-nomination-pools`'s `bond_extra`/`bond_extra_other` extrinsics have no minimum-bond check and can issue **zero points** for a non-zero, real transfer of funds due to integer-division rounding in `balance_to_point`, mirroring the reported `InsuranceFund.depositFor` zero-shares issue.

### Title
Small `bond_extra` deposits into a large nomination pool can transfer real funds while minting zero points, permanently freezing the deposit - (File: `substrate/frame/nomination-pools/src/lib.rs`)

### Summary
`Pallet::balance_to_point` computes `points = current_points * new_funds / current_balance` using integer division [1](#0-0) . `Call::join` enforces `MinJoinBond` before calling this [2](#0-1) , but `Call::bond_extra` / `Call::bond_extra_other` never enforce any minimum amount for `BondExtra::FreeBalance(amount)` before calling `try_bond_funds` → `issue` → `balance_to_point` [3](#0-2) [4](#0-3) . In a pool whose bonded balance is large relative to points (e.g. after growth or where `current_points` < `current_balance`), a member can call `bond_extra(BondExtra::FreeBalance(amount))` with a small `amount` such that `amount * current_points / current_balance == 0`, yielding `points_issued = 0`, while the funds themselves are still moved via `pledge_bond`.

### Finding Description
`do_bond_extra` unconditionally calls `try_bond_funds`, which issues points *before* transferring/delegating funds, and never checks that `points_issued > 0` [5](#0-4) . If `points_issued` is `0`, `member.points` is unchanged (`checked_add` of 0), but the underlying stake mechanism still moves real value:
- Under `TransferStake` strategy, `T::Currency::transfer(&who.0, &pool_account.0, amount, Preservation::Preserve)` unconditionally moves `amount` from the member's account to the pool account and calls `Staking::bond_extra` [6](#0-5) .
- Under `DelegateStake` strategy, `Delegation::delegate` similarly locks the amount against the member without any points minted [7](#0-6) .

Since a pool member's withdrawable/unbondable balance is entirely determined by `member.points` (via `point_to_balance`), any balance contributed with zero resulting points can never be redeemed by that member through the pool's normal `unbond`/`withdraw_unbonded` flow — it is effectively donated to the rest of the pool (its value is absorbed into `current_balance` used by everyone else's point-to-balance ratio).

This directly matches the reported bug class: an integer-division share/point calculation that can silently mint zero shares for a real, non-zero deposit, with no revert-on-zero-shares guard, unlike `join`, which does guard via `MinJoinBond`, and unlike `pallet-asset-conversion::do_add_liquidity`, which explicitly reverts via `Error::<T>::InsufficientLiquidityMinted` when minted LP tokens are too small [8](#0-7) .

### Impact Explanation
A pool member who calls `bond_extra` with a small enough amount relative to the pool's balance-to-points ratio loses effective ownership of that amount: it is bonded into the pool (staked) but not represented by any of the caller's points, meaning they cannot unbond/withdraw it back through the pool. Impact is a fund-freezing/loss bug affecting the depositor, bounded by the size of a single "dust" `bond_extra` call, and does not by itself allow theft from other members — it is directly analogous to a Medium-severity finding in the referenced report class.

### Likelihood Explanation
Reachability requires no special privilege — any signed account that is already a pool member (via `Call::join`, itself subject only to `MinJoinBond`, which is not required to be non-trivial, and defaults can be `0`) can call `bond_extra(BondExtra::FreeBalance(amount))` freely, any number of times, with attacker-chosen `amount`. It requires that `current_points < current_balance` (i.e., pool value grown relative to points, e.g. after rewards/slashing history or bond_extra by other large depositors) so that a chosen small `amount` rounds to `0` points. This is a realistic, naturally occurring pool state as the pool accrues rewards, so likelihood is non-trivial but depends on specific pool state (ratio conditions), and the affected amount per call is limited to whatever rounds to zero, which is bounded by `current_balance / current_points`.

### Recommendation
In `try_bond_funds` (or `do_bond_extra` prior to calling it), assert that `points_issued` (or `amount` for `BondExtra::FreeBalance`) is non-zero and return an error (e.g. a new `Error::<T>::InsufficientBondExtra` / reusing `Error::<T>::MinimumBondNotMet`) when it isn't, mirroring the `join` extrinsic's `MinJoinBond` check and `pallet-asset-conversion`'s `InsufficientLiquidityMinted` guard.

### Proof of Concept
I was unable to run an actual FRAME/mock-runtime reproduction in this environment (no execution access here); this is a code-path/reachability analysis based on the cited source only. A concrete reproduction would need to:
1. Build a pool where `current_points` (bonded_pool.points) is meaningfully smaller than `current_balance` (active stake), e.g. via reward accrual moved into active stake through `bond_extra(BondExtra::Rewards)` by other members, or by manipulating mock balances as done in `substrate/frame/nomination-pools/src/tests.rs::join_errors_correctly`, which already demonstrates deliberately setting `set_pool_balance` to control the points:balance ratio for testing purposes [9](#0-8) .
2. Have a pool member call `Pools::bond_extra(RuntimeOrigin::signed(member), BondExtra::FreeBalance(amount))` with `amount` chosen so `amount * bonded_pool.points / bonded_pool.balance == 0`.
3. Assert `PoolMembers::<Runtime>::get(member).unwrap().points` is unchanged (0 issued) while the member's free balance decreased by `amount` (transferred into the pool), demonstrating the loss.

```rust
	fn do_bond_extra(
		signer: T::AccountId,
		member_account: T::AccountId,
		extra: BondExtra<BalanceOf<T>>,
	) -> DispatchResult {
		// ensure account is not restricted from joining the pool.
		ensure!(!T::Filter::contains(&member_account), Error::<T>::Restricted);

		if signer != member_account {
			ensure!(
				ClaimPermissions::<T>::get(&member_account).can_bond_extra(),
				Error::<T>::DoesNotHavePermission
			);
			ensure!(extra == BondExtra::Rewards, Error::<T>::BondExtraRestricted);
		}

		let (mut member, mut bonded_pool, mut reward_pool) =
			Self::get_member_with_pools(&member_account)?;

		// payout related stuff: we must claim the payouts, and updated recorded payout data
		// before updating the bonded pool points, similar to that of `join` transaction.
		reward_pool.update_records(
			bonded_pool.id,
			bonded_pool.points,
			bonded_pool.commission.current(),
		)?;
		let claimed = Self::do_reward_payout(
			&member_account,
			&mut member,
			&mut bonded_pool,
			&mut reward_pool,
		)?;

		let (points_issued, bonded) = match extra {
			BondExtra::FreeBalance(amount) => {
				(bonded_pool.try_bond_funds(&member_account, amount, BondType::Extra)?, amount)
			},
			BondExtra::Rewards => {
				(bonded_pool.try_bond_funds(&member_account, claimed, BondType::Extra)?, claimed)
			},
		};

		bonded_pool.ok_to_be_open()?;
		member.points =
			member.points.checked_add(&points_issued).ok_or(Error::<T>::OverflowRisk)?;
```
