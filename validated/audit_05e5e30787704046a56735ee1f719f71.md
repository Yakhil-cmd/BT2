### Title
Webhook Signature Verification Uses `repository.owner.login` While Handlers Act On `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
In a multi-organization Shipit deployment, the field used to select which GitHub App/`webhook_secret` verifies a webhook's HMAC signature (`repository.owner.login`) is never checked for equality against the field handlers use to locate the `Stack`/`Repository` that is actually mutated (`repository.full_name`). An operator who legitimately administers one configured GitHub organization (and therefore knows that organization's `webhook_secret`) can forge a signed payload whose `owner.login` matches their own org (so the signature check passes) but whose `full_name` points at a *different* organization's repository configured on the same Shipit instance, causing Shipit to sync/deploy that unrelated stack.

### Finding Description
`WebhooksController#verify_signature` picks the GitHub App/secret to validate against based on the organization name extracted straight from the untrusted JSON body: [1](#0-0) [2](#0-1) 

`repository_owner` reads `params.dig('repository', 'owner', 'login')`, and `Shipit.github(organization: repository_owner)` resolves the per-organization config (secret/app) as configured in `secrets.yml`: [3](#0-2) 

Once the signature is confirmed against *that* organization's secret, the raw params are handed unmodified to every registered handler: [4](#0-3) 

But the handlers never re-check `owner.login`; they resolve the target repository/stack purely from `repository.full_name`: [5](#0-4) 

`PushHandler`, for example, uses that repository-derived `stacks` scope directly to trigger a sync with an attacker-chosen `expected_head_sha`: [6](#0-5) 

The equality the design implicitly relies on is:
`organization authenticated (repository.owner.login, used to pick webhook_secret)` == `organization/repository actually written (repository.full_name, used by Handler#repository_name / Repository.from_github_repo_name)`

Nothing in `verify_signature` or `Handler#repository_name` enforces this equality. In the documented multi-org configuration (`docs/setup.md`, "Using Multiple Github Applications"), each organization admin supplies their own `app_id`/`private_key`/`webhook_secret` to the Shipit operator; the org admin necessarily knows their own `webhook_secret` since they generated it in their own GitHub App settings. That secret is sufficient to sign an arbitrary JSON body whose `repository.full_name` names a stack belonging to a *different* organization hosted on the same Shipit instance.

### Impact Explanation
This breaks the repository/organization trust boundary between tenants on a shared Shipit instance: an org admin/user with only legitimate access to their own organization's webhook secret can force a sync (`GithubSyncJob`) — and depending on which event/handler is invoked, other repository-scoped side effects (status creation, check-suite refresh, PR-driven review-stack actions) — against a stack owned by an organization they have no GitHub permissions on. This can be leveraged to trigger unauthorized deploys/rollback triggers or state changes on another tenant's stack, i.e., cross-repository writes not gated by that repository's own GitHub authorization.

### Likelihood Explanation
Requires the attacker to already be a legitimate administrator of at least one GitHub organization configured on the target multi-tenant Shipit instance (so they know their own `webhook_secret`), and requires the instance to be configured for more than one organization per `docs/setup.md`'s multi-org schema. This is a real, documented, supported configuration, and no additional privilege on the victim organization is required — only knowledge of one's own already-authorized webhook secret plus the ability to craft/POST an HTTP request with a valid `X-Hub-Signature`.

### Recommendation
After identifying the GitHub App via `repository.owner.login` and verifying the signature, re-derive the organization from `repository.full_name` (or `organization.login`) and require it to match the organization whose secret validated the signature before dispatching to handlers. Alternatively, bind webhook secrets per-repository rather than per-organization-name lookup, or have `Handler#repository_name`/`stacks` cross-check the verified organization against the repository owner before resolving `Stack`s.

### Proof of Concept
1. Shipit is configured with two organizations, `org-a` and `org-b`, each with its own GitHub App and `webhook_secret` (per `docs/setup.md`, "Using Multiple Github Applications").
2. Attacker administers `org-b`'s GitHub App and therefore knows `org-b`'s `webhook_secret`.
3. Attacker crafts a JSON payload:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker chosen sha>",
  "repository": {
    "owner": { "login": "org-b" },
    "full_name": "org-a/victim-repo"
  }
}
```
4. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(org-b webhook_secret, body)>` and POSTs to `/webhooks` with `X-Github-Event: push`.
5. `WebhooksController#verify_signature` resolves `repository_owner == "org-b"`, fetches `org-b`'s `GitHubApp`, and the signature validates successfully because it was computed with the correct (`org-b`) secret.
6. `Shipit::Webhooks.for_event('push')` dispatches to `PushHandler`, whose `repository_name` reads `repository.full_name == "org-a/victim-repo"`; it resolves `org-a`'s stacks via `Repository.from_github_repo_name` and enqueues `GithubSyncJob` with the attacker-supplied `expected_head_sha`, even though the attacker has no GitHub relationship to `org-a` at all.

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
