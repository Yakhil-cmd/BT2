### Title
Missing cosigner authorization check lets any paired device trigger arbitrary local-address signing requests - (File: wallet.js)

### Summary
`handleMessageFromHub()` in `wallet.js` processes the `"sign"` subject sent by any paired (correspondent) device without verifying that the sender is actually an authorized cosigner of the target address. The check that would enforce this is present in the code but explicitly commented out.

### Finding Description
This is a direct structural analog of CVE-2016-10746: libvirt's `virDomainGetTime` accepted calls over a read-only connection even though the API was supposed to require a privileged (RW) connection — the authorization gate existed conceptually but was not actually enforced on the request path. In `ocore--012`, the `"sign"` message handler has the same shape of bug: the code path for `ifRemote` (address hosted on another device) does check that `other_device_addresses.includes(from_address)` before honoring the request [1](#0-0) , but the `ifLocal` branch (the address is hosted locally, i.e. the operation directly touches this node's own signing/private key material) has the equivalent authorization check present only as a comment: [2](#0-1) 

The commented-out query would have verified `SELECT 1 FROM extended_pubkeys WHERE wallet=? AND device_address=?` to confirm `from_address` is actually a registered cosigner device of the wallet that owns `body.address`, mirroring how `ifRemote` verifies membership via `other_device_addresses`. Because this check is disabled, `callbacks.ifOk()` is invoked and a `"signing_request"` event is emitted for **any** correspondent device that sends a well-formed `"sign"` message referencing one of the node's local addresses (`address` found among `objUnit.authors`), even if that device was never granted signing rights over that address [3](#0-2) . The only guard against a fully arbitrary address is `findAddress()`, which merely determines whether the address is `ifLocal`/`ifRemote`/`ifMerkle`/`ifUnknownAddress` based on `my_addresses`/`wallet_signing_paths`/`shared_address_signing_paths`, not on the identity of the sender [4](#0-3) .

Compare this to the properly-guarded `arbiter_contract_update` handler in the same file, which explicitly checks `wallet_signing_paths`/`my_addresses` membership for `from_address` before acting on privileged fields [5](#0-4) , demonstrating that this class of check is the established security pattern elsewhere in `wallet.js` but is missing here.

### Impact Explanation
Because `"sign"` requests are unauthenticated with respect to cosigner membership on the local branch, a paired device that is not actually a cosigner of a multisig/shared address can:
- Flood the node with fabricated unsigned units referencing that address, forcing `network.handleOnlineJoint()` validation and repeated `"signing_request"` event emission to any listening UI/automation layer [6](#0-5) .
- For `signed_message` requests, directly trigger the `"signing_request"` event with attacker-controlled `objUnit`/messages without any wallet-side authorization gate at all [7](#0-6) , since that branch bypasses even the `validated-` unit check used in the payment path.

If the consuming application (headless/automated wallet, bot, or exchange-style hot wallet) treats any `"signing_request"` originating from a device known to the wallet (paired correspondent) as sufficiently trusted to auto-approve — which is a realistic deployment pattern for automated multisig cosigners — this missing check allows an unauthorized paired device to obtain signatures over a shared/multisig address it is not entitled to sign for, leading to unauthorized spending from that shared address. Even absent full auto-approval, it enables spoofed signing prompts and denial-of-confirmation-service against legitimate cosigner wallets.

### Likelihood Explanation
Reaching this code requires only pairing with the target device (a normal, low-privilege wallet operation exposed to any device that obtains a pairing code) and then sending a `"sign"` message through the hub — no special network position, hub compromise, or key leak is required. The `hasFieldsExcept`/hash/format checks on the message are satisfied trivially since they validate structure, not sender authority [8](#0-7) . The missing check is unconditional (not behind a feature flag), and the comment explaining why it was disabled ("would make multilateral signing impossible") confirms it is a deliberate but overly broad removal of the authorization check rather than dead code.

### Recommendation
Restore an authorization check in the `ifLocal` branch of the `"sign"` handler that verifies `from_address` is a legitimate cosigner for `body.address`/`body.signing_path` before emitting `"signing_request"` or invoking `network.handleOnlineJoint()`. Since multilateral signing legitimately requires accepting signing requests from non-cosigner counterparties (e.g., contract counterparties), the fix should distinguish between:
1. True multisig paths, where `from_address` must be validated against `wallet_signing_paths`/`extended_pubkeys` for the same wallet, and
2. Multilateral/dumb-contract signing, where the counterparty is expected to be untrusted but the UI-level confirmation must clearly disclose the untrusted origin so a human (or automated policy) can reject it, rather than relying on the wallet layer to have already validated cosigner status.

At minimum, emit enough information in the `"signing_request"` event for downstream consumers to distinguish "verified cosigner request" from "unverified request," so headless/automated signers do not blindly trust it.

### Proof of Concept
1. Attacker device A pairs with victim device V (normal pairing flow, no elevated trust required).
2. V is a cosigner on a shared multisig address `S` together with device C, but A is not a cosigner of `S`.
3. A crafts an `unsigned_unit` object whose `authors` array includes an entry for `S` (with placeholder authentifiers) and valid, well-formed payment messages passing `hasValidPayloadHashes`.
4. A sends this as a `"sign"` message to V: `{subject: "sign", body: {address: S, signing_path: "r.0", unsigned_unit: ...}}`.
5. V's `handleMessageFromHub` reaches the `"sign"` case; `findAddress(S, "r.0", ...)` returns `ifLocal` (since S's signing path resolves to V's own key material); the disabled cosigner check means `callbacks.ifOk()` is called and `"signing_request"` fires immediately without any check that A is entitled to request this [2](#0-1)  — regardless of A's actual relationship to `S`.
6. If V's application layer approves signing requests from any known/paired device (e.g., an automated cosigning bot), V will produce a valid signature share for a transaction A was never authorized to initiate, enabling unauthorized spending from `S`.
