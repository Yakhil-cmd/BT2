### Title
Webhook signature is verified against the payload's claimed organization while handlers act on unrelated `repository.full_name`/global `sha` fields, allowing cross-repository status/commit forgery — ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks which GitHub App/organization secret to validate the HMAC signature against using a field taken from the *unauthenticated* request body (`repository.owner.login` or `organization.login`), while the webhook handlers that subsequently mutate state key off *other* fields in that same body (`repository.full_name` for `Repository.from_github_repo_name`, or a bare `sha` lookup across all stacks for `StatusHandler`). Because these two lookups are not bound to each other, a signature that is valid for "organization A" (whose secret the attacker legitimately knows) can be replayed with body content that targets a completely different, unrelated repository/commit tracked by the same Shipit instance.

### Finding Description
The signature check is: [1](#0-0) [2](#0-1) 
`repository_owner` is derived purely from the JSON body: [3](#0-2) 

`Shipit.github(organization: repository_owner)` selects the `GitHubApp` config (and its `webhook_secret`) for that org, and `verify_webhook_signature` HMACs the *entire raw body* with that secret: [4](#0-3) 

This part is sound on its own — the whole payload is signed. The problem is that the handlers that run afterwards do not re-derive the target resource from the same `repository_owner`/organization that was just verified; they use independent fields of the same (attacker-authored) JSON body:

- Generic handler base class resolves the target `Repository`/`Stack` via `repository.full_name`, not `repository.owner.login`: [5](#0-4) 

- `StatusHandler` is worse: it doesn't scope by repository/organization at all, it matches **any** commit in the entire database whose `sha` equals the attacker-supplied value: [6](#0-5) 

Because the signature is computed over the whole request body, an attacker cannot forge an arbitrary payload for a secret they don't know. But an attacker who legitimately controls (or is a member of) *any* GitHub organization/app that Shipit is configured to trust (Shipit explicitly supports configuring multiple orgs, each with its own `webhook_secret`, per `docs/setup.md` and `config/secrets.development.example.yml`) knows that organization's secret. Nothing in `verify_signature` or the handlers ties the `sha`/`repository.full_name` fields to that same organization — they only have to be internally consistent JSON, which the attacker fully controls since they compute the HMAC themselves.

This breaks the equality the engine is supposed to enforce: `organization authenticated by webhook_secret == repository/commit actually mutated by the handler`. Concretely:
- `repository_owner` (used to pick and validate against a known-to-attacker secret) can be attacker's own trusted org.
- `repository.full_name` (used by most handlers) or the raw `sha` (used by `StatusHandler`) can reference a totally different, victim-owned stack/commit tracked by the same Shipit instance.

### Impact Explanation
Using a `status` event, the attacker can inject arbitrary GitHub commit statuses (e.g., mark `ci/required` as `success`) on a commit belonging to any stack in the Shipit instance, not just their own org's repository, via `Commit#create_status_from_github!`. `Commit#deployable?` depends directly on that status: [7](#0-6) 
and `ci.require`/`required_statuses` gates deploys via `DeploySpec`: [8](#0-7) 

Forging a passing status thus lets an unrelated attacker satisfy CI gating and enable an unauthorized deploy of a victim stack/repository they have no access to — this is a cross-repository write / unauthorized-deploy-enabling primitive, matching the Critical impact bar (cross-repository writes, unauthorized deploy). `push`/`check_suite`/`pull_request` handlers extend the same class of impact to sync jobs, check-run refreshes, and review-stack archive/unarchive/merge-queue state for arbitrary tracked repositories, using only the `repository.full_name` field disconnected from the verified `repository_owner`.

### Likelihood Explanation
Likelihood is not "admin error" as in the original report — it requires only that the attacker be a legitimate member/admin of *any* GitHub organization/app that the Shipit deployment trusts (a normal, expected condition in a multi-org Shipit install, which the project explicitly documents as a supported configuration). No Shipit session, `ApiClient` token, or `webhook_secret` compromise of the *victim* org is needed — only knowledge of the secret for the attacker's own, unrelated org.

### Recommendation
Bind the organization that was cryptographically verified to the resource the handler is allowed to touch: after `verify_signature` succeeds for `repository_owner`, pass that verified owner down to the handlers and require that `repository.full_name`'s owner segment (and, for `StatusHandler`, the owning stack/repository of the matched commit) equals `repository_owner`/the verified organization before any mutation. Reject the webhook otherwise.

### Proof of Concept
1. Shipit is configured (per `docs/setup.md`) with two GitHub orgs, `attacker-org` (secret known to the attacker, who is its GitHub App admin) and `victim-org` (an unrelated org whose repos/commits are tracked by the same Shipit instance).
2. Attacker learns/observes a commit `sha` belonging to a stack under `victim-org` (e.g. from the public Shipit UI, public repo, or PR).
3. Attacker builds a `status` webhook JSON body: `{"repository": {"owner": {"login": "attacker-org"}, "full_name": "attacker-org/whatever"}, "sha": "<victim commit sha>", "state": "success", "context": "ci/required"}`.
4. Attacker computes `X-Hub-Signature: sha1=HMAC(attacker-org's webhook_secret, raw_body)` and POSTs to `/webhooks` with `X-Github-Event: status`.
5. `verify_signature` resolves `repository_owner` = `attacker-org`, fetches `attacker-org`'s secret, and the HMAC matches → request passes (see `app/controllers/shipit/webhooks_controller.rb:24-38`, `lib/shipit/github_app.rb:76-83`).
6. `StatusHandler#process` runs `Commit.where(sha: params.sha)` — matching the victim's commit regardless of organization — and calls `create_status_from_github!`, setting a forged `success` status on it (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`).
7. If `victim-org`'s stack requires that context via `ci.require`, `Commit#deployable?` now returns true, permitting an unauthorized deploy of `victim-org`'s stack.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
