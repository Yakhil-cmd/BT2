### Title
`OpenedHandler#provision?` and `ReopenedHandler#unarchive?` operator precedence bug bypasses `review_stacks_enabled` for `allow_with_label`/`prevent_with_label` behaviors - ([File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb])

### Summary
`provision?` (and the identical `unarchive?` in `reopened_handler.rb`) is written as `a && b || c || d` in Ruby, where `&&` binds tighter than `||`. This means `repository.review_stacks_enabled` is only ANDed with `provisioning_behavior_allow_all?`; it is **not** applied to the `allow_with_label` or `prevent_with_label` branches at all, letting an attacker provision (or unarchive) a review stack even when `review_stacks_enabled` is `false`.

### Finding Description
The intended binding is `review_stacks_enabled == true` required for ANY branch of `provision?`. The actual code:
```ruby
def provision?
  repository.review_stacks_enabled &&
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
``` [1](#0-0) 

parses per Ruby operator precedence as:
```
(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?)
```
The last two disjuncts have no `review_stacks_enabled` term. The identical bug exists in `unarchive?`. [2](#0-1) 

Exploit for the exact scenario posed in the question: repository has `review_stacks_enabled = false`, `provisioning_behavior = prevent_with_label`. The attacker opens a PR **without** the provisioning label (the opposite of what the question hypothesized, but the more dangerous variant): `pull_request_has_provisioning_label?` is `false`, so `!pull_request_has_provisioning_label?` is `true`, and `prevent_with_label? && true` is `true` → `provision?` returns `true` despite `review_stacks_enabled` being `false`. This calls `ReviewStackAdapter#find_or_create!`, which creates a `ReviewStack` record and enqueues it via `Shipit::ReviewStackProvisioningQueue.add(stack)` [3](#0-2) , i.e., provisioning proceeds (branch/stack creation, queued for infra provisioning) for a repository whose owner explicitly disabled review stacks. Likewise with `allow_with_label` and the label applied, or on `reopened` events via `unarchive?`, an archived stack can be unarchived (`stack.unarchive!`) with `review_stacks_enabled` false [4](#0-3) .

Regarding the specific case the question asked to verify (`prevent_with_label`, PR labeled, `review_stacks_enabled` false): here `!pull_request_has_provisioning_label?` is `false`, so this specific disjunct is `false`, and since `review_stacks_enabled` is `false` the `allow_all` disjunct is also `false`; the other disjunct depends on `allow_with_label?` which is `false` here (mutually exclusive enum) — so `provision?` correctly evaluates to `false` in that exact sub-case. However, the broader truth table shows the binding `review_stacks_enabled == true required for ANY branch` is violated for `prevent_with_label` + unlabeled and for `allow_with_label` + labeled, both with `review_stacks_enabled = false`.

This is not blocked by webhook signature verification, `drop_unhandled_event`, or `ExplicitParameters` schema validation — those only validate authenticity/shape of the payload, not the business logic in `provision?`/`unarchive?`.

### Impact Explanation
An attacker who can open/label/reopen a pull request against a repository registered in Shipit (with `review_stacks_enabled` disabled but a stale/misconfigured `provisioning_behavior`) can cause Shipit to create a `ReviewStack` record and enqueue it for provisioning, and can unarchive previously archived review stacks — actions the repository owner explicitly disabled by setting `review_stacks_enabled = false`. This is a record written / infrastructure action performed for a repository that did not authorize it via its intended feature flag, matching "an unauthorized deploy" / stack-mutation class of impact. It is repeatable against any repository with this configuration combination (`review_stacks_enabled: false` + `provisioning_behavior: allow_with_label` or `prevent_with_label`).

### Likelihood Explanation
Requires a repository already onboarded to Shipit with `review_stacks_enabled = false` while `provisioning_behavior` remains `allow_with_label` or `prevent_with_label` (plausible operational/config drift, e.g., temporarily disabling review stacks without resetting `provisioning_behavior` back to a neutral state). No Shipit secrets are needed beyond what a normal GitHub webhook from that repo already provides (webhook signature is a repo-owner-controlled secret already trusted for that repo, not attacker-controlled). Attacker cost is a single PR open/label/reopen action they can perform on their own PR.

### Recommendation
Add parentheses to correctly scope `review_stacks_enabled` across all disjuncts, e.g.:
```ruby
def provision?
  repository.review_stacks_enabled && (
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
  )
end
```
Apply the identical fix to `unarchive?` in `reopened_handler.rb`.

### Proof of Concept
Table-driven minitest (outside `test/` per rules, but described for the fix's verification) enumerating `{review_stacks_enabled: [true, false]} x {provisioning_behavior: allow_all/allow_with_label/prevent_with_label} x {labeled: true/false}`, asserting `provision?`/`unarchive?` is `false` whenever `review_stacks_enabled` is `false`. Concretely:
- `review_stacks_enabled: false`, `provisioning_behavior: prevent_with_label`, `labeled: false` → current code returns `true` (VIOLATION; expected `false`).
- `review_stacks_enabled: false`, `provisioning_behavior: allow_with_label`, `labeled: true` → current code returns `true` (VIOLATION; expected `false`).
- All other `review_stacks_enabled: false` combinations correctly return `false`.
