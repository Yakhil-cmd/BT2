This confirms the vulnerability path. The webhook signature verification and the repository/stack resolution use two different fields from the same attacker-controlled JSON payload, with no cross-check that they match.

## Analysis

`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to verify the HMAC against using `repository_owner`, which reads `params.dig('repository', 'owner', 'login')` (falling back to `params.dig('organization', 'login')`) [1](#0-0) . The signature is verified via `Shipit.github(organization: repository_owner).verify_webhook_signature(...)` against the raw request body [2](#0-1) .

However, once the signature check passes, every `Handler` resolves the target `Repository`/`Stack` using a **different** field from the very same JSON body: `payload.dig('repository', 'full_name')` [3](#0-2) . This pattern is repeated across `PushHandler`, `StatusHandler`, and all `PullRequest::*Handler` classes, e.g. `Shipit::Repository.from_github_repo_name(params.repository.full_name)` [4](#0-3) .

Nothing enforces that `repository.owner.login` (used to pick the HMAC secret) equals the owner segment inside `repository.full_name` (used to pick the affected `Repository`/`Stack`). Both are independently attacker-supplied JSON fields inside the same signed body — the HMAC only proves the bytes came from whoever holds *some* org's `webhook_secret`, not that the org matches the object being mutated.

**Binding broken:** `organization authenticated (repository.owner.login) ≠ repository written (repository.full_name)`.

### Exploit path
An attacker who controls a GitHub organization/app installation registered in Shipit (`config/secrets*.yml` `github:` block, e.g. their own `someothergithuborg` with its own `webhook_secret`) can:
1. Craft a payload where `repository.owner.login` = `"someothergithuborg"` (their own org, so `verify_webhook_signature` succeeds using their own legitimately-known secret) [2](#0-1) .
2. Set `repository.full_name` = `"somegithuborg/victim-repo"` — a repository/stack belonging to a different, victim organization also configured in the same Shipit instance.
3. Sign the whole payload with their own valid `webhook_secret` and POST it to `/github/webhooks`.
4. Handlers like `PushHandler` will call `stack.sync_github(expected_head_sha: ...)` [5](#0-4)  or `StatusHandler`/`PullRequest` handlers will mutate commit statuses, archive/unarchive review stacks, or add/remove team memberships on the **victim's** stack, using data the attacker fully controls, despite never having proven control of the victim org.

This matches the bug class from the external report: a value ("more native tokens than needed") is accepted and acted upon (crediting the bridge fee) without being bound to what was actually verified/needed — here, the "verified organization" is accepted and acted upon as if it verified the "written repository," when the code never checks that the two match.

### Impact
This does not directly grant `Critical` outcomes like RCE or `GITHUB_TOKEN` exfiltration by itself, since handlers here don't execute deploys/tasks (that requires further explicit user/API-client action) — the concrete, immediately reachable effects are unauthenticated writes to `commit_status`/`Membership`/`Team`/review-stack archival state for arbitrary repositories cross-tenant, and forcing `GithubSyncJob`/`RefreshCheckRunsJob` against an arbitrary stack. This is a cross-repository write primitive (data integrity across tenants, using another org's signature "credentials" to affect a different org's resources), but it requires the attacker to already control a second organization/app registered in the same Shipit deployment (multi-tenant setup) — a precondition that meaningfully limits severity/likelihood versus the reported High/Critical bar.

### Recommendation
`WebhooksController#verify_signature` (or each `Handler`) should validate that the organization used to resolve the webhook secret is the same organization owning the resource being mutated — e.g., derive/compare `repository.full_name`'s owner segment against `repository_owner` and reject on mismatch, or better, resolve the target `Repository` and re-derive the expected signing organization from it rather than trusting an independent payload field for the security decision.     def verify_signature

      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post

      head(422) unless verified

      Rails.logger.info([
