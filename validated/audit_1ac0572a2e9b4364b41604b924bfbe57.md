### Title
`CheckSuiteHandler`/`Webhooks::Handlers::Handler#stacks` trusts `repository.full_name` independent of the org that authenticated the webhook signature - ([File: app/models/shipit/webhooks/handlers/handler.rb])

### Summary
`WebhooksController#verify_signature` selects the signing org and its `webhook_secret` using `params.dig('repository','owner','login')`, but the shared `Handler#stacks` method (used by `CheckSuiteHandler`) resolves the target stack using a *different* field of the same attacker-supplied JSON body: `payload.dig('repository','full_name')`. Nothing cross-checks that the repository named by `full_name` belongs to the org that verified the signature, so a webhook that is "authenticated" for org A can still target and mutate a stack belonging to org B.

### Finding Description
Binding claimed: `verified_org (owner.login used to select webhook_secret) == owner_of(repository.full_name used to resolve the target stack)`.

Trace:
- `WebhooksController#verify_signature` picks the `GitHubApp` (and therefore the `webhook_secret` used in HMAC verification) via `repository_owner`, which reads `params.dig('repository', 'owner', 'login')`: [1](#0-0) [2](#0-1) 
- `GitHubApp#verify_webhook_signature` computes HMAC over the raw body using that org's `webhook_secret`, but if that org's `webhook_secret` is blank/unset it unconditionally returns `true`, bypassing verification entirely: [3](#0-2) 
- Once verification passes, `WebhooksController#create` dispatches to `Shipit::Webhooks.for_event(event)`, which for `check_suite` calls `Handlers::CheckSuiteHandler`: [4](#0-3) [5](#0-4) 
- `CheckSuiteHandler#process` resolves target stacks via the base `Handler#stacks` method, which reads `payload.dig('repository', 'full_name')` - a field entirely independent from `owner.login` used above: [6](#0-5) [7](#0-6) 
- The two fields (`repository.owner.login` and `repository.full_name`) live in the same attacker-controlled JSON body and are never checked against each other anywhere in the request path.

Exploit flow: An attacker crafts (or triggers, from a repo/org they control where the configured `webhook_secret` for that org is blank, or where they otherwise possess a validly-signed payload for some org A) a `check_suite` POST to `/webhooks` with `X-Github-Event: check_suite`, `repository.owner.login` set to org A (the org whose secret check passes/blank), and `repository.full_name` set to the victim's repository (e.g., `"victim-org/victim-repo"`), plus a matching `head_branch`/`head_sha` for a real victim commit. `verify_signature` passes because it only checks org A's secret/blankness. `CheckSuiteHandler` then resolves `Repository.from_github_repo_name("victim-org/victim-repo")` and calls `schedule_refresh_check_runs!` on the victim's commits, enqueuing `RefreshCheckRunsJob` for the victim stack - a job the attacker fully controls the triggering of, for a repository they never authenticated for.

None of the existing guards prevent this: `drop_unhandled_event` only checks the event name is registered; `verify_signature` authenticates the *org named in `owner.login`*, not the repository named in `full_name`; the `ExplicitParameters` schema on `CheckSuiteHandler` only validates presence/type of `head_sha`/`head_branch`, not repository identity; there is no `require_permission!`/`stacks` scoping tying the verified org to the resolved `Repository`.

### Impact Explanation
A request "authenticated" for one organization's webhook secret (or an org with no secret configured) can enqueue `RefreshCheckRunsJob` and mutate check-run/commit state for a completely different, victim organization's stack. Since check-run state can feed into deploy-gating logic (`Stack::schedule_refresh_check_runs!`), this is a cross-tenant write triggered by an unauthenticated-for-that-repository payload - matching the Critical category "a payload for one repository mutating another's stack, commit, task or team." It's repeatable against any stack whose `full_name` the attacker knows, as long as they can get any signature check to pass (e.g., an org with a blank `webhook_secret`).

### Likelihood Explanation
Likelihood depends entirely on Shipit's GitHub App configuration: if every configured org has a properly-set, secret `webhook_secret`, the attacker cannot produce a valid HMAC for any org and thus cannot reach `CheckSuiteHandler` at all, since `verify_webhook_signature` would reject the forged signature. However, if any org onboarded to the Shipit instance has a blank/unset `webhook_secret` (explicitly supported and defaulting to bypass, per `lib/shipit/github_app.rb:76-77`), or if the attacker legitimately controls a repo/org with a known secret, the exploit is trivial and repeatable with a single crafted HTTP POST, no privileges, no session, and no knowledge of the victim's secrets.

### Recommendation
In `Handler#stacks` (or in `CheckSuiteHandler`/`WebhooksController`), verify that the organization owning `payload.dig('repository', 'full_name')` matches the organization that was used to authenticate the webhook signature (`repository_owner`/`owner.login`) before resolving/mutating any stack. Reject the request (e.g., `head(422)`) if they diverge.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb
test ":check_suite payload naming a different repository's full_name refreshes the victim's stack" do
  victim_stack = shipit_stacks(:shipit) # stack for "Shopify/shipit-engine"
  # Simulate org A ("attacker-org") passing signature verification because its
  # configured webhook_secret is blank (verify_webhook_signature returns true).
  Shipit.stubs(:github).with(organization: 'attacker-org').returns(
    Shipit::GitHubApp.new('attacker-org', { webhook_secret: nil })
  )

  request.headers['X-Github-Event'] = 'check_suite'
  body = JSON.parse(payload(:check_suite_master))
  body['repository']['owner']['login'] = 'attacker-org' # signature check uses this
  body['repository']['full_name'] = 'Shopify/shipit-engine' # stack lookup uses this (victim)

  assert_enqueued_with(job: RefreshCheckRunsJob, args: [stack_id: victim_stack.id]) do
    post :create, body: body.to_json, as: :json
    assert_response :ok
  end
end
```
This demonstrates that `verified_org ("attacker-org")` != `owner_of(repository.full_name) ("Shopify")`, yet `RefreshCheckRunsJob` is still enqueued for the victim stack, confirming the broken binding.

      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
