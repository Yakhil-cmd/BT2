### Title
Merkle proof verification lacks leaf/internal-node domain separation, enabling second-preimage forgery of "in merkle" and `is_valid_merkle_proof` proofs - (File: merkle.js)

### Summary
`merkle.js` implements a Merkle tree where leaf hashes and internal-node hashes are computed with the exact same hash function and no domain-separation tag (no `0x00`/`0x01` prefix, no length prefix, no distinct salt). This is the same root cause flagged in the referenced report: pre-hashed leaf data can be reinterpreted as a concatenated pair of internal nodes, letting an attacker forge a "valid" proof for data that was never part of the original tree. This primitive is exposed to unprivileged actors both through address-definition authentifiers (`in merkle`) and, most critically, through the AA formula function `is_valid_merkle_proof`, where both the "element" and the "proof" are attacker-controlled trigger data.

### Finding Description
`getMerkleRoot`/`getMerkleProof` hash leaves with a plain `hash(element)` and hash internal nodes with `hash(hash_left + hash_right)`, using the identical `hash()` function for both: [1](#0-0) 

`verifyMerkleProof` walks the same recomputation upward from the supplied `element` and explicitly acknowledges the risk in a code comment ("Node-as-Leaf issue might matter in some cases") without any mitigation: [2](#0-1) 

Because there is no domain separation, an attacker who knows (or can derive/observe) two adjacent hash strings `h_a`, `h_b` at some internal level of a real tree can set a crafted "element" equal to `h_a + h_b`. `hash(h_a + h_b)` collides with the real internal-node hash at that position, so supplying the genuine sibling path from that internal node up to the root makes `verifyMerkleProof` return `true` for a value that was never one of the tree's actual leaves.

This primitive is reachable by unprivileged parties in two places:
1. Address-definition authentifier `in merkle`, used during `validateAuthentifiers`, where the proof (`assocAuthentifiers[path]`) is fully attacker-supplied in the signed unit: [3](#0-2) 
Here `element` itself is fixed at definition time (validated by a strict regex at `definition.js:470-475`), which limits (but does not eliminate) exploitability for this specific call site.

2. The AA-formula built-in `is_valid_merkle_proof`, where **both** the `element` and the `proof` object are evaluated directly from oscript expressions and can be sourced entirely from `trigger.data`, i.e. fully controlled by the unprivileged AA-trigger sender: [4](#0-3) 

Any AA that implements a Merkle-based whitelist/allowlist/airdrop check (`is_valid_merkle_proof(trigger.data.leaf, trigger.data.proof)` compared against a known root) is exposed: the attacker does not need knowledge of any genuine leaf value, only knowledge of two sibling hash strings inside the real tree (which are often public, e.g. published alongside legitimate claims or reconstructible from the full data set an oracle publishes).

### Impact Explanation
An attacker who can forge inclusion of an unauthorized/never-issued "leaf" value in a Merkle tree can defeat any AA-side authorization logic built on `is_valid_merkle_proof` (e.g., claim-based airdrops, allowlisted spender/asset checks, off-chain-computed reward tables). Depending on how the AA formula subsequently uses the "verified" element (e.g., as a recipient address or claim amount embedded in the leaf string), this can lead to unauthorized AA fund disbursement/loss — a concrete, direct financial impact consistent with High severity, matching the underlying bug class of the referenced report.

### Likelihood Explanation
Exploitability depends on the specific AA's oscript design (whether it trusts arbitrary attacker-chosen `element` strings that happen to equal internal-hash concatenations, and how it decodes accepted leaves), so the finding is a library-level vulnerability whose real-world blast radius is contingent on downstream AA logic rather than a universally and immediately exploitable bug in the base protocol. The `in merkle` address-definition path is less practically exploitable because `element` is fixed and regex-constrained at definition time. The AA-formula path (`is_valid_merkle_proof`) is the higher-likelihood vector because both the element and proof are unrestricted attacker inputs from `trigger.data`.

### Recommendation
Add domain separation to `merkle.js`'s hashing so that leaf hashes and internal-node hashes cannot collide, e.g.:
- Prefix leaf hashing: `hash("\x00" + element)`.
- Prefix internal-node hashing: `hash("\x01" + left + right)`.

This must be a breaking/versioned change to `getMerkleRoot`, `getMerkleProof`, and `verifyMerkleProof` in [5](#0-4)  and would require an MCI-gated protocol upgrade (similar to other `constants.*UpgradeMci` gates already used elsewhere in the codebase) to avoid breaking already-computed proofs/roots relied upon by `is_valid_merkle_proof` [4](#0-3)  and `in merkle` [3](#0-2) .

### Proof of Concept
1. Build a real tree over leaves `L0..Ln` via `merkle.getMerkleRoot`; note that at some internal level two hash strings `h_a` (left) and `h_b` (right) combine into a parent node `P = hash(h_a + h_b)`.
2. An attacker constructs `forged_element = h_a + h_b` and a `proof` object whose `siblings`/`index` are exactly the real path from `P` up to `root` (unchanged from the real tree).
3. Call `merkle.verifyMerkleProof(forged_element, proof)`:
   - `the_other_sibling = hash(forged_element) = hash(h_a + h_b) = P`, matching the genuine internal node hash.
   - The remaining loop iterations use the real sibling path and correctly reconstruct `root`.
   - Function returns `true`, incorrectly certifying that `forged_element` (never a real leaf) is included in the tree.
4. In an AA whose formula includes `is_valid_merkle_proof(trigger.data.leaf, trigger.data.proof) && ...` gating a payout, the trigger sender supplies `trigger.data.leaf = forged_element` and `trigger.data.proof = {index, siblings, root}` to pass the check without ever knowing a genuine leaf, as reachable through the code paths cited above [4](#0-3) [2](#0-1) .

function hash(str){
	return crypto.createHash("sha256").update(str, "utf8").digest("base64");
}

function getMerkleRoot(arrElements){
	var arrHashes = arrElements.map(hash);
	while (arrHashes.length > 1){
		var arrOverHashes = []; // hashes over hashes
		for (var i=0; i<arrHashes.length; i+=2){
			var hash2_index = (i+1 < arrHashes.length) ? (i+1) : i; // for odd number of hashes
			arrOverHashes.push(hash(arrHashes[i] + arrHashes[hash2_index]));
		}
		arrHashes = arrOverHashes;
	}
	return arrHashes[0];
}

function getMerkleProof(arrElements, element_index){
	if (element_index < 0 || element_index >= arrElements.length)
		throw Error("invalid index");
	var arrHashes = arrElements.map(hash);
	var index = element_index;
	var arrSiblings = [];
	while (arrHashes.length > 1){
		var arrOverHashes = []; // hashes over hashes
		var overIndex = null;
		for (var i=0; i<arrHashes.length; i+=2){
			var hash2_index = (i+1 < arrHashes.length) ? (i+1) : i; // for odd number of hashes
			if (i === index){
				arrSiblings.push(arrHashes[hash2_index]);
				overIndex = i/2;
			}
			else if (hash2_index === index){
				arrSiblings.push(arrHashes[i]);
				overIndex = i/2;
			}
			arrOverHashes.push(hash(arrHashes[i] + arrHashes[hash2_index]));
		}
		arrHashes = arrOverHashes;
		if (overIndex === null)
			throw Error("overIndex not defined");
		index = overIndex;
	}
	// add merkle root
	//arrSiblings.push(arrHashes[0]);
	return {
		root: arrHashes[0],
		siblings: arrSiblings,
		index: element_index
	};
}

// returns a string element_index-siblings_joined_by_dash-root
function serializeMerkleProof(proof){
	var serialized_proof = proof.index;
	if (proof.siblings.length > 0)
		serialized_proof += "-"+proof.siblings.join("-");
	serialized_proof += "-"+proof.root;
	return serialized_proof;
}

function deserializeMerkleProof(serialized_proof){
	var arr = serialized_proof.split("-");
	var proof = {};
	proof.root = arr.pop();
	proof.index = arr.shift();
	proof.siblings = arr;
	return proof;
}

function verifyMerkleProof(element, proof){
	// Node-as-Leaf issue might matter in some cases
	try {
		var index = proof.index;
		var the_other_sibling = hash(element);
		for (var i = 0; i < proof.siblings.length; i++) {
			// this also works for duplicated trailing nodes
			if (index % 2 === 0)
				the_other_sibling = hash(the_other_sibling + proof.siblings[i]);
			else
				the_other_sibling = hash(proof.siblings[i] + the_other_sibling);
			index = Math.floor(index / 2);
		}
		return (the_other_sibling === proof.root);
	}
	catch (e){
		return false;
	}
}
