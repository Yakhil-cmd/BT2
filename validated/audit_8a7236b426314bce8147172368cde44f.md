### Title
Missing `nonReentrant` Guard on `handleERC20Transfer` and `handleERC721Transfer` Allows Re-entrancy into Public Bridge Functions — (`contracts/service_chain/bridge/BridgeTransferERC20.sol`, `contracts/service_chain/bridge/BridgeTransferERC721.sol`)

---

### Summary

`handleKLAYTransfer` in `BridgeTransferKLAY.sol` is protected with `nonReentrant`, but the functionally equivalent `handleERC20Transfer` and `handleERC721Transfer` are not. Both functions make external calls to token contracts after updating bridge state. If the token is ERC777-compliant (or any token with transfer hooks), the recipient `_to` can receive a callback during the external call and re-enter public bridge entry points (`requestERC20Transfer`, `onERC20Received`, `requestERC721Transfer`, `onERC721Received`), causing `requestNonce` to be incremented and a spurious `RequestValueTransfer` event to be emitted mid-handle. The bridge relayer on the counterpart chain treats that event as a legitimate cross-chain transfer request, potentially locking additional bridged assets.

---

### Finding Description

`handleKLAYTransfer` explicitly inherits `ReentrancyGuard` and applies `nonReentrant`: [1](#0-0) [2](#0-1) 

The KLAY handle function performs its external call (`_to.call.value(_value)("")`) **after** all state updates and the event, and is guarded by `nonReentrant`. [3](#0-2) 

`handleERC20Transfer` has no `nonReentrant` modifier. After updating `closedValueTransferVotes`, `handleNoncesToBlockNums`, and `lowerHandleNonce`, it makes an external call to the token contract: [4](#0-3) [5](#0-4) 

`handleERC721Transfer` has the same omission. After state updates it calls `transferFrom` on the ERC721 contract, which triggers `onERC721Received` on `_to` if `_to` is a contract: [6](#0-5) [7](#0-6) 

The public entry points that can be re-entered are: [8](#0-7) [9](#0-8) [10](#0-9) 

These functions are **not** `onlyOperators` and increment `requestNonce` and emit `RequestValueTransfer` / `RequestValueTransferEncoded`.

Additionally, `_updateHandleNonce` — called before the external interaction — deletes `closedValueTransferVotes[i]` for nonces in the sliding window: [11](#0-10) 

After `_updateHandleNonce` runs, `closedValueTransferVotes[N]` for the just-handled nonce is deleted. `lowerHandleNonce` is advanced past N, so a re-entrant call with the same nonce is blocked by `_lowerHandleNonceCheck`. However, a re-entrant call into a **public** function (not `onlyOperators`) is not blocked.

---

### Impact Explanation

During `handleERC20Transfer` or `handleERC721Transfer`, if the token contract is ERC777-compliant or implements transfer hooks, the recipient `_to` receives a callback (`tokensReceived` / `onERC721Received`). A malicious `_to` contract can re-enter `requestERC20Transfer` or `onERC20Received`:

1. `requestNonce` is incremented mid-handle, emitting a `RequestValueTransfer` event with an unexpected nonce.
2. The bridge relayer on the counterpart chain observes this event and submits a `handleERC20Transfer` / `handleKLAYTransfer` transaction on the other side, minting or transferring tokens to the attacker-specified `_to` address.
3. The tokens used in the re-entrant `requestERC20Transfer` call are locked in the bridge contract, and the attacker receives the corresponding bridged assets on the counterpart chain.

The corrupted value is `requestNonce` (incremented out of order) and the bridged asset balance (unauthorized cross-chain transfer initiated without a legitimate user request).

---

### Likelihood Explanation

- Requires the registered token to be ERC777-compliant or to implement transfer hooks — a realistic scenario since ERC777 is backward-compatible with ERC20 and bridge operators may register such tokens.
- `_to` is an operator-supplied parameter in `handleERC20Transfer`/`handleERC721Transfer`, but the re-entrant path through `requestERC20Transfer` is triggered by the token contract calling `_to`, not by the operator directly.
- The asymmetry with `handleKLAYTransfer` (which has `nonReentrant`) suggests this was an oversight rather than an intentional design decision.
- Likelihood: **Low-Medium** — requires a specific token type, but the attack surface is real and the guard is demonstrably missing relative to the KLAY path.

---

### Recommendation

Add `nonReentrant` to `handleERC20Transfer` and `handleERC721Transfer`, mirroring the protection already applied to `handleKLAYTransfer`. Both contracts must inherit `ReentrancyGuard`:

```solidity
// BridgeTransferERC20.sol
contract BridgeTransferERC20 is BridgeTokens, IERC20BridgeReceiver, BridgeTransfer, ReentrancyGuard {
    function handleERC20Transfer(...) public onlyOperators nonReentrant { ... }
}

// BridgeTransferERC721.sol
contract BridgeTransferERC721 is BridgeTokens, IERC721BridgeReceiver, BridgeTransfer, ReentrancyGuard {
    function handleERC721Transfer(...) public onlyOperators nonReentrant { ... }
}
```

---

### Proof of Concept

1. Deploy an ERC777-compliant token registered on the bridge.
2. Deploy a malicious recipient contract `MaliciousRecipient` that implements `tokensReceived`. In `tokensReceived`, call `bridge.requestERC20Transfer(token, attacker, amount, 0, "")` (having pre-approved the bridge).
3. Operator calls `bridge.handleERC20Transfer(..., MaliciousRecipient, amount, nonce, ...)`.
4. The bridge updates state and emits `HandleValueTransfer`, then calls `token.mint(MaliciousRecipient, amount)` (mintBurn mode) or `token.safeTransfer(MaliciousRecipient, amount)`.
5. The ERC777 token fires `tokensReceived` on `MaliciousRecipient`.
6. `MaliciousRecipient.tokensReceived` calls `bridge.requestERC20Transfer(...)`, which increments `requestNonce` and emits `RequestValueTransfer` with nonce R.
7. The bridge relayer on the counterpart chain processes nonce R and mints/transfers tokens to the attacker's address on the other chain.
8. The attacker has received tokens on both chains for a single legitimate handle operation. [12](#0-11) [13](#0-12) [14](#0-13)
