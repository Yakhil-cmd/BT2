### Title
Cross-repository Status forgery via unscoped `Commit.where(sha:)` lookup in `StatusHandler#process` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` resolves the target commit(s) for an incoming GitHub `status` webhook purely by `sha`, with no filter on the payload's `repository`/`repository_owner`. Every other handler (e.g. `PushHandler`) scopes its work through the `stacks` helper, which restricts the query to stacks matching the webhook's own repository, but `StatusHandler` does not, so a status event carrying a sha that happens to also exist in a *different* tracked stack (e.g. a fork or mirror sharing pre-fork history) will mutate that unrelated stack's commit/status state.

### Finding Description
The claimed binding should be: `commit.stack.repository == payload.repository` for any `Status` row created from a webhook. Tracing the code shows this binding is never enforced for the `status` event:

- `WebhooksController#create` only verifies the HMAC signature against the GitHub App secret associated with `repository_owner` (the *organization*, not the specific repo) before dispatching to handlers: [1](#0-0) [2](#0-1) 
- `StatusHandler#process` then does: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` — it never restricts by which repository the commit's stack belongs to: [3](#0-2) 
- By contrast, `PushHandler#process` scopes its query with `stacks.not_archived.where(branch:)`, where `stacks` is presumably derived from the webhook's repository, showing the codebase's own convention of repository-scoping handlers is violated here: [4](#0-3) 
- `Commit#create_status_from_github!` unconditionally records the forged state via `Status.replicate_from_github!`: [5](#0-4) [6](#0-5) 
- The forged `error`/`failure` status makes that commit `blocking?` (delegated to `Status#blocking?`/state), and `Commit#blocked?` scans `stack.commits.reachable.newer_than(stack.last_deployed_commit).older_than(self).any?(&:blocking?)`, so any later commit in the same (victim) stack becomes `blocked?` and therefore non-`deployable?`: [7](#0-6) 

Root cause: the "binding" is enforced by the *outer* signature check (organization-level secret) but not re-checked at the *handler* level against the specific repository named in the payload. Since the signature only proves the request came from a legitimately-signed webhook for the trusted organization/app installation—not that the sha named in it belongs to the specific stack it will be applied to—any status event whose `sha` collides with a commit sha already recorded on a different stack (most plausibly a fork/mirror sharing pre-fork commit history under the same GitHub organization/app installation) will corrupt that other stack's blocking chain. `drop_unhandled_event`, `ExplicitParameters` (`StatusHandler`'s `params do ... end` block), and `verify_signature` all pass in this scenario because they operate on event-type and organization-secret validity, not on per-repository ownership of the sha.

### Impact Explanation
An attacker with push/webhook-triggering rights on some repository within the same trusted GitHub organization/app installation as the victim stack can write forged `Shipit::Status` rows against commits belonging to a *different* stack/repository, as long as they can produce (or already share, via fork ancestry) a matching commit `sha`. This is an unauthorized cross-repository write to another tenant's `Commit`/`Status` data and directly corrupts the victim's CI-derived blocking chain used by `deployable?`/`blocked?`, matching the Critical category "a payload for one repository mutating another's stack, commit ... ". The blast radius is bounded to stacks sharing the same GitHub organization/app secret as the attacker's own repository — it is not a global cross-tenant primitive across unrelated organizations, since `verify_signature` still requires the org-level secret to validate.

### Likelihood Explanation
Preconditions: the attacker's repository (or one they can trigger status events for) must belong to the same GitHub organization/app installation as the victim stack (so the signature check passes with a secret the attacker doesn't need to know — GitHub signs it for them), and a commit sha must exist identically in both the attacker's repo and the victim's tracked stack. The practical, non-theoretical route to a shared sha is a fork/mirror relationship sharing pre-fork commit history within the same org, not a brute-force SHA1 collision (which is not a trivial/unprivileged capability). Given that requirement, the exploit is fully repeatable — every future status event with that sha reapplies. This is a real but moderately-constrained precondition (same-org repository access), not a fully unauthenticated arbitrary-repository attack.

### Recommendation
In `app/models/shipit/webhooks/handlers/status_handler.rb`, scope the `Commit` lookup to stacks whose repository matches the webhook's `repository`/`repository_owner` (mirroring the `stacks` scoping already used by `PushHandler`), e.g. filter `Commit.joins(:stack).merge(Stack.where(repository: <resolved repo from payload>))` before applying `create_status_from_github!`, instead of matching on `sha` alone across the entire installation.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb`, hypothetical — not present in current `test/` per repo state found):
```ruby
test "status webhook for repo A does not mutate a commit sharing the same sha in repo B's stack" do
  victim_stack = shipit_stacks(:some_other_repo_stack)
  victim_older_commit = victim_stack.commits.create!(sha: "deadbeef" * 5, ...)
  victim_newer_commit = victim_stack.commits.create!(sha: "...", ...)
  victim_stack.update!(cached_deploy_spec: DeploySpec.new('ci' => { 'blocking' => ['ci/travis'] }))

  attacker_payload = {
    'sha' => victim_older_commit.sha,
    'state' => 'error',
    'context' => 'ci/travis',
    'repository' => { 'full_name' => 'attacker/unrelated-repo', 'owner' => { 'login' => 'trusted-org' } }
  }

  # binding under test: victim_newer_commit.stack.repository == attacker_payload['repository']['full_name']
  refute_equal victim_stack.repository.full_name, attacker_payload['repository']['full_name']

  Shipit::Webhooks::Handlers::StatusHandler.call(attacker_payload)

  refute_predicate victim_newer_commit.reload, :blocked?, "victim commit must not be blocked by a status forged via a different repository's webhook"
end
```
Expected current (buggy) behavior: `StatusHandler#process` matches `Commit.where(sha: attacker_payload['sha'])` irrespective of `attacker_payload['repository']`, creates the `error` status on `victim_older_commit`, and `victim_newer_commit.blocked?` becomes `true` — violating the asserted binding.
