### Title
Governance changes executed inside `flash_position` are bypassed by stale cached spoke configuration - ([File: contracts/controller/src/context.rs](contracts/controller/src/context.rs))

### Summary
`flash_position` validates collateral listings before invoking an untrusted receiver, but keeps those listings cached for the rest of the invocation. The receiver can execute an already-ready governance operation that edits or halts the same spoke asset; the post-callback deposit and risk checks continue using the pre-operation configuration, allowing a new debt position to be opened under superseded collateral parameters.

### Finding Description
`process_flash_position` creates one invocation-local `Context`, validates the requested collateral assets, and calls `require_can_supply`, which populates `Context::spoke_assets` from storage. [1](#0-0)  `cached_spoke_asset` returns the stored `Map` entry whenever it exists and only reads storage on a cache miss. [2](#0-1) 

The same context remains alive while the controller forwards the minted debt and invokes the caller-selected Wasm receiver. [3](#0-2)  During that callback, the receiver can call governance `execute` for an already-ready operation; governance execution itself is externally reachable and does not require the executor to be privileged once the operation is ready. [4](#0-3) 

If that operation is `EditAssetInSpoke`, `upsert_spoke_asset` writes the replacement `SpokeAssetConfig` to persistent storage. [5](#0-4)  However, after the callback returns, `process_deposit` and `merge_supply_leg` call `require_spoke_asset`, which receives the old cached config rather than the replacement. [6](#0-5) [7](#0-6) 

The resulting `AccountPosition` is stamped with the obsolete LTV, liquidation threshold, liquidation bonus, and fees through `refresh_supply_risk_params`. [8](#0-7)  The post-callback deposit and final solvency checks therefore evaluate a world that no longer exists after the governance operation committed.

### Impact Explanation
An attacker can open a leveraged account at the instant governance tightens or disables a collateral market, while retaining the former, more permissive collateral terms. For example, a ready `EditAssetInSpoke` operation can reduce the asset's LTV and liquidation threshold or remove collateral permission; the attacker nevertheless creates the supply position with the old parameters and leaves debt denominated in another asset outstanding. [9](#0-8) 

This can leave the protocol with debt that should not have been permitted under the current listing. If the tightened listing reflects impaired collateral liquidity, reduced confidence, or a lower safe threshold, the resulting position can become bad debt and socialize losses into the pool's supply index. Persisted position risk parameters are subsequently used for health-factor and liquidation calculations rather than automatically rereading the live listing. [10](#0-9) 

### Likelihood Explanation
The attacker does not need governance permission to create the operation: they only need a pre-approved operation to reach `Ready`. They can monitor governance, start `flash_position` when a tightening operation becomes executable, and have their receiver execute it during the callback. The receiver is explicitly attacker-selected and only needs to return the required collateral assets. [11](#0-10) 

The exploit depends on the existence and timing of a suitable ready governance operation, so it is opportunistic rather than continuously available. When the opportunity exists, the stale-cache behavior is deterministic because no cache invalidation occurs between the callback and the deposit/finalization steps. [2](#0-1) 

### Recommendation
Invalidate and reload spoke-level security/configuration state after the receiver callback and before depositing collateral or running final risk checks. Do not use `reset_spoke_context` blindly after debt has been minted, because that would discard pending spoke-usage deltas; instead, clear only `spoke_config` and `spoke_assets`, or record the relevant listing configuration/flags epoch before the callback and require it to remain unchanged afterward. The post-callback deposit should read `SpokeAssetConfig` directly from storage so a governance update cannot coexist with pre-update risk parameters in one transaction.

### Proof of Concept
1. Governance has a ready `EditAssetInSpoke` operation for collateral asset `C` that lowers `ltv`/`threshold` or sets `can_collateral = false`.
2. The attacker calls `Controller::flash_position`, requesting debt asset `D`, collateral `C`, and an attacker-controlled Wasm receiver.
3. Before the callback, `validate_collaterals` calls `require_can_supply`; `cached_spoke_asset` loads the old permissive config into `Context::spoke_assets`.
4. The pool mints `D` to the controller and the controller forwards it to the receiver inside `with_flash_guard`.
5. In `execute_flash_position`, the receiver calls `Governance::execute` for the ready `EditAssetInSpoke` operation. The controller writes the tightened config to storage.
6. The receiver sends the required amount of `C` back to the controller.
7. `process_flash_position` calls `process_deposit`; its entry gate consults `Context::spoke_assets` and observes the old permissive config, not the newly stored config.
8. `merge_supply_leg` creates or updates the attacker's supply position and stamps the obsolete LTV, threshold, bonus, and fees into the position.
9. Finalization evaluates the leveraged account using the same stale snapshot, so the transaction succeeds even though a new position would fail under the committed governance parameters.
10. The attacker retains the borrowed `D` proceeds while the account keeps debt backed by collateral accepted under superseded terms.

## 10. Existing positions keep their stamped terms

Each supply position stores its own LTV, LT, base bonus and liquidation fee.
It copies them from the spoke listing when it is created
(`get_or_create_supply_position`). After that, the controller uses the
stored values, not the live listing:

- HF uses the stored LT (`calculate_account_risk_totals`).
- The borrow limit uses the lower of the stored LTV and the stored LT.
- The base bonus `b0` is the USD-weighted stored bonus. The maximum bonus `M`
  comes from the stored LT. The fee is the stored fee
  (`get_account_bonus_params`).
