## Confirmed analog: CCMenu API stack-scope bypass

### Title
CCMenu API endpoint bypasses `ApiClient` stack scoping, allowing a token authorized for one stack to read the deploy/task status of any stack - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
This is a structural analog of the reported bug class: a permission/authentication check is validated against one binding (the API client's authorized scope) while the actual resource acted upon is resolved through an unbound path, letting a narrowly-scoped credential act outside its intended boundary.

### Finding Description
`Shipit::Api::BaseController` enforces per-client stack scoping through its `stacks`/`stack` helpers: an `ApiClient` that has a `stack_id` set is restricted to that single stack via `stacks` — `current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all` — and `stack` resolves `params[:stack_id]` only from within that scoped relation. [1](#0-0) 

`Shipit::Api::CCMenuController`, however, overrides `stack` to resolve the resource directly from the global `Stack` model, bypassing the scoped `stacks` relation entirely: [2](#0-1) 

The controller still declares `require_permission :read, :stack`, which only checks that the authenticated `ApiClient` has the `read:stack` permission string — it does not verify that the specific `stack_id` in the URL matches the client's authorized `stack_id`. [3](#0-2) [4](#0-3) 

The binding that is broken (equality that should hold but does not): `ApiClient#stack_id` (the stack the token authorizes) ≠ `stack` resolved in `CCMenuController#show` (the stack whose deploy state is actually returned). Every other stack-scoped API controller (`stacks_controller.rb`, `deploys_controller.rb`, `tasks_controller.rb`, etc.) inherits `BaseController#stack`, which correctly enforces this equality; `CCMenuController` alone re-implements `stack` and drops the check.

### Impact Explanation
An `ApiClient` created and scoped to a single, low-sensitivity stack (e.g. `here_come_the_walrus` fixture with `stack: shipit`, `permissions: [read:stack]`) can supply its own valid token together with an arbitrary `stack_id` in the CCMenu URL (`/api/stacks/:stack_id/ccmenu?token=...`) and receive the latest deploy/rollback status (id, timestamps, running state) of a completely different, unauthorized stack. This is an unauthenticated-for-that-stack read of stack/task state, matching the "High" impact category defined in scope ("unauthenticated read of stack state, task streams or deploy output").

### Likelihood Explanation
Any holder of a legitimately-issued, narrowly-scoped `ApiClient` token (e.g. a CI system meant to only see one stack's CCMenu badge) can trivially trigger this by changing the `stack_id` segment of the URL — no additional credentials, brute force, or privilege escalation is required beyond having any valid `read:stack` token for any stack. Given CCMenu tokens are typically embedded in build-status widgets/URLs that may be shared or exposed in dashboards, this is a straightforward and easily discoverable escalation.

### Recommendation
Remove the local `stack` override in `CCMenuController` and instead use the inherited `stack` method from `BaseController` (which raises via `stacks.from_param!`), or explicitly validate that `current_api_client.stack_id.nil? || current_api_client.stack_id == Stack.from_param!(params[:stack_id]).id` before rendering. This restores the equality between the stack an `ApiClient` is authorized for and the stack whose data is exposed.

### Proof of Concept
1. Create (or obtain) an `ApiClient` scoped to `stack_id: <stack A>` with `permissions: ['read:stack']` (e.g., fixture `here_come_the_walrus`).
2. Authenticate as this client and issue: `GET /api/stacks/<owner>/<repo-B>/<env-B>/ccmenu?token=<clientA_token>` where `repo-B/env-B` is a *different* stack the client is not scoped to.
3. `authenticate_api_client` succeeds because the token is valid; `require_permission :read, :stack` passes because the client has `read:stack`; `stack` resolves stack B directly via `Stack.from_param!`, bypassing the `stacks` scoping check that every other controller uses.
4. The response renders stack B's latest deploy/rollback status (`shipit/ccmenu/project` view), which the client was never authorized to see. [5](#0-4)
