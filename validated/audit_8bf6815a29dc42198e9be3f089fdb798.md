### Title
Cross-repository Status contamination via unscoped SHA lookup - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` resolves target commits by SHA alone (`Commit.where(sha: params.sha)`), without ever checking `params.repository.full_name` against the resolved commit's `stack.repository.full_name`. Every other webhook handler (`PushHandler`, `CheckSuiteHandler`, PR handlers) scopes its lookups through `stacks`, which is derived from `Repository.from_github_repo_name(repository_name)`; `StatusHandler` does not use `stacks` at all, so a valid signed webhook from any repository can write a `Status` onto a `Commit` belonging to a completely different repository's `Stack` as long as the SHA happens to match.

### Finding Description
Binding claimed and broken: `params.repository.full_name == commit.stack.repository.full_name` for every `Status` created by a `status` webhook.

Code path:
- `WebhooksController#create` parses the payload and dispatches to `Shipit::Webhooks.for_event('status')`, i.e. `Handlers::StatusHandler`. [1](#0-0) 
- `WebhooksController#verify_signature` only checks the payload's HMAC against `Shipit.github(organization: repository_owner)`'s `webhook_secret`, where `repository_owner` is `params.dig('repository','owner','login')` from the *same untrusted payload*. If Shipit is configured with a `github` entry for `mirror-org` (the documented multi-org config, exactly the "mirror repo owned by a different org" scenario the question describes), a webhook signed with `mirror-org`'s own `webhook_secret` passes this check trivially — the attacker owns that org/repo and can legitimately compute a valid signature for it. [2](#0-1) 
- `StatusHandler#process` then does:
```ruby
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
```
This is a bare `sha` lookup across the entire `commits` table, with no filter derived from `params.repository.full_name`. [3](#0-2) 
- Contrast with `PushHandler` and `CheckSuiteHandler`, which both scope through `Handler#stacks`, itself built from `Repository.from_github_repo_name(repository_name)` — i.e., they *do* bind the payload's repository to the stack/repository being mutated. [4](#0-3) [5](#0-4) [6](#0-5) 
- `Commit#create_status_from_github!` performs no repository check either; it just writes the status against `stack_id` (`self.stack_id`), whatever stack that commit happens to belong to. [7](#0-6) 

Exploit flow: attacker owns `mirror-org/mirror`, a repo Shipit is configured to authenticate (a legitimate multi-org mirror setup, per `docs/setup.md`'s documented multi-org `github:` config). The canonical stack tracks `org/canonical` with a `Commit` at some `sha`. Because `mirror-org/mirror` mirrors the same upstream history, a commit with the identical `sha` naturally exists in both repos (this is exactly the "mono-to-poly-repo mirror" scenario named in the question — no forgery of the SHA is even required, but even if it were, nothing stops an attacker from also fabricating a `status` payload with an arbitrary `sha` string that happens to match a real commit in a target repo they don't own, since GitHub's `status` payload's `sha`/`repository` fields aren't cross-checked here). The attacker fires `POST /webhooks` with `X-Github-Event: status`, `repository.full_name = 'mirror-org/mirror'`, `sha` equal to the canonical commit's sha, and a valid `X-Hub-Signature` computed with `mirror-org`'s own webhook secret (which the attacker, as owner of that org/app installation, legitimately possesses). `verify_signature` passes (correct org, correct secret, own repo). `StatusHandler#process` then finds `Commit.where(sha: ...)` across **all stacks in the Shipit instance**, including the canonical stack's commit, and calls `create_status_from_github!` on it — writing a `Status` row (state, description, context, target_url — including arbitrary CI context/state values fully controlled by the attacker) onto the canonical stack's commit, with no verification that `mirror-org/mirror` has anything to do with `org/canonical`.

None of the listed guards prevent this: `verify_signature` only proves the payload's *own claimed* org/repo signed the payload correctly — it says nothing about which `Stack`/`Commit` the payload is permitted to mutate. `drop_unhandled_event` doesn't apply (status has a handler). `ExplicitParameters` schema only validates types/presence of fields, not cross-repository binding. No `force_github_authentication`, `User#authorized?`, `require_permission!`, or `stacks` scope call exists in `StatusHandler`.

### Impact Explanation
An attacker who owns/controls any repository whose org is configured in Shipit (a normal, low-privilege setup for teams that mirror an org's repos, e.g., CI mirrors, forks-as-mirrors, or multi-org deployments) can inject arbitrary `Status` rows (state: `success`/`failure`/`error`/`pending`, arbitrary `context`, `description`, `target_url`) onto commits belonging to a **different repository's Stack** that they do not own or have any permission on, as long as they can produce a colliding SHA (trivial in mirrored/forked histories, or via any repo they fully control publishing a commit with an attacker-chosen SHA is not needed — matching a known upstream SHA is sufficient). This directly enables triggering `stack.enable_ci!`, `schedule_continuous_delivery`, and ultimately marking a commit `success`/`deployable` on the canonical stack (`Status#enable_ci_on_stack`, `Status#schedule_continuous_delivery`, `Commit#add_status`/`schedule_continuous_delivery`), which can trigger an unauthorized continuous deployment of that commit — this matches the Critical category "payload for one repository mutating another's stack/commit... or an unauthorized deploy". It is fully repeatable against any stack/commit sha the attacker can guess or observe (mirrors make guessing trivial), and the blast radius spans every Stack configured in the Shipit instance, not just the attacker's own repository. [8](#0-7) [9](#0-8) 

### Likelihood Explanation
Preconditions: Shipit must be configured to accept webhooks from more than one GitHub org/repo (the documented multi-org `github:` config in `config/secrets.development.example.yml`/`docs/setup.md`), which is common precisely in the mono-to-poly-repo mirror scenario the question describes. The attacker needs no Shipit credentials, no session, no API token — only ownership of a repository/org that Shipit already trusts for webhook signing, which they can normally provision themselves (e.g., adding the Shipit GitHub App to their own mirror repo, or being a legitimate member of an org Shipit already trusts). Given that, the attack is a single unauthenticated `POST /webhooks` request with a correctly-signed payload for the attacker's own repo — no rate limiting or additional secrets required, fully repeatable.

### Recommendation
In `StatusHandler#process`, replace the unscoped `Commit.where(sha: params.sha)` with a lookup scoped via `stacks` (as `PushHandler`/`CheckSuiteHandler` do), e.g. `stacks.flat_map(&:commits).select { |c| c.sha == params.sha }` or `Commit.where(sha: params.sha, stack_id: stacks.select(:id))`, so that only commits belonging to stacks whose `Repository` matches `params.repository.full_name` can receive the status. Add an explicit assertion/test that `params.repository.full_name == commit.stack.repository.full_name` before calling `create_status_from_github!`.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb
require 'test_helper'

module Shipit
  module Webhooks
    module Handlers
      class StatusHandlerTest < ActiveSupport::TestCase
        test "status webhook for a mirror repository must not update a commit belonging to a different repository's stack" do
          canonical_repo = Repository.create!(owner: 'org', name: 'canonical')
          canonical_stack = Stack.create!(repository: canonical_repo, environment: 'production')
          shared_sha = 'a' * 40
          canonical_commit = canonical_stack.commits.create!(sha: shared_sha, message: 'shared upstream commit')

          # Attacker's own mirror repo/org, unrelated to canonical_repo
          payload = {
            'sha' => shared_sha,
            'state' => 'success',
            'context' => 'attacker-ci',
            'repository' => { 'full_name' => 'mirror-org/mirror' }
          }

          assert_no_difference -> { canonical_commit.statuses.count } do
            StatusHandler.new(payload).process
          end

          # Binding check: params.repository.full_name != commit.stack.repository.full_name,
          # yet a status was (incorrectly) written without this fix in place.
          assert_not_equal payload['repository']['full_name'], canonical_commit.stack.repository.full_name
        end
      end
    end
  end
end
```
Running this against current `StatusHandler#process` fails (`assert_no_difference` fails because a `Status` row is created), proving that `Commit.where(sha: params.sha)` matches the canonical commit regardless of the payload's `repository.full_name`.
