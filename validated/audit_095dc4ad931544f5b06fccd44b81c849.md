### Title
Unauthenticated `onERC20Received` Allows Any Registered Token to Drain Bridge ERC20 Reserves via Spoofed `_from` and Inflated `_feeLimit` — (`contracts/service_chain/bridge/BridgeTransferERC20.sol`)

---

### Summary

`BridgeTransferERC20.onERC20Received` is declared `public` with no caller-authentication guard. The `onlyRegisteredToken` check is deferred to the internal `_requestERC20Transfer`. Any contract whose address is registered as a bridge token can call `onERC20Received` directly — without having transferred any tokens to the bridge — and supply an arbitrary `_from` address and an inflated `_feeLimit`. The fee-refund path in `_payERC20FeeAndRefundChange` then transfers the bridge's own token reserves to the attacker-controlled `_from` address.

---

### Finding Description

`onERC20Received` is the 1-step deposit entry point. Its intended caller is a registered `ERC20ServiceChain` token that first transfers `_amount + _feeLimit` to the bridge and then calls back:

```solidity
// ERC20ServiceChain.requestValueTransfer
require(transfer(bridge, _amount.add(_feeLimit)), ...);
IERC20BridgeReceiver(bridge).onERC20Received(msg.sender, _to, _amount, _feeLimit, _extraData);
``` [1](#0-0) 

The bridge's implementation of `onERC20Received` is:

```solidity
function onERC20Received(
    address _from,
    address _to,
    uint256 _value,
    uint256 _feeLimit,
    bytes memory _extraData
)
    public          // ← no access control here
{
    _requestERC20Transfer(msg.sender, _from, _to, _value, _feeLimit, _extraData);
}
``` [2](#0-1) 

The `onlyRegisteredToken` guard lives only on the internal function:

```solidity
function _requestERC20Transfer(
    address _tokenAddress,
    address _from, ...
)
    internal
    onlyRegisteredToken(_tokenAddress)   // ← guard is here, not on onERC20Received
    onlyUnlockedToken(_tokenAddress)
``` [3](#0-2) 

Inside `_requestERC20Transfer`, the fee-refund path is:

```solidity
uint256 fee = _payERC20FeeAndRefundChange(_from, _tokenAddress, _feeLimit);
``` [4](#0-3) 

And in `BridgeFee._payERC20FeeAndRefundChange`, when `feeOfERC20[token] == 0` (the default) and `_feeLimit > 0`:

```solidity
if (_feeLimit > 0) {
    IERC20(_token).safeTransfer(from, _feeLimit);   // ← transfers bridge's own reserves to `from`
}
``` [5](#0-4) 

`from` is the caller-supplied `_from` argument — it is never verified to be the address that actually deposited tokens.

---

### Impact Explanation

**Concrete attack (registered token contract as attacker):**

1. Attacker controls a contract at address `T` that is registered as a bridge token.
2. Attacker calls `bridge.onERC20Received(attacker_addr, any_to, 1, bridge_T_balance, "")` directly from `T` — without transferring any tokens to the bridge.
3. `onlyRegisteredToken(T)` passes because `T` is registered.
4. `_payERC20FeeAndRefundChange(attacker_addr, T, bridge_T_balance)` executes.
5. Since `feeOfERC20[T] == 0`, the bridge calls `IERC20(T).safeTransfer(attacker_addr, bridge_T_balance)` — transferring the bridge's entire `T` reserve to the attacker.
6. A `RequestValueTransfer` event is emitted with `_value = 1` and `_from = attacker_addr`.
7. Bridge operators on the counterpart chain observe the event and call `handleERC20Transfer`, releasing 1 token to `any_to` on the counterpart chain.

**Result:** The bridge's full ERC20 reserve for token `T` is stolen. A spurious cross-chain transfer request is also created, consuming counterpart-chain liquidity. [6](#0-5) 

---

### Likelihood Explanation

The trigger requires that `msg.sender` be a registered token address. Token registration requires `onlyOwner` access. However:

- Once a token is registered, **any code deployed at that address** can call `onERC20Received` with arbitrary parameters.
- A registered token contract that has been upgraded, self-destructed and redeployed, or that contains a re-entrancy hook in its `transfer` path can exploit this without any additional privilege.
- The `_from` and `_feeLimit` parameters are entirely attacker-controlled with no on-chain verification that tokens were actually deposited.

---

### Recommendation

1. **Add caller authentication directly on `onERC20Received`:**

```solidity
function onERC20Received(
    address _from,
    address _to,
    uint256 _value,
    uint256 _feeLimit,
    bytes memory _extraData
)
    public
    onlyRegisteredToken(msg.sender)   // ← add this
    onlyUnlockedToken(msg.sender)     // ← add this
{
    _requestERC20Transfer(msg.sender, _from, _to, _value, _feeLimit, _extraData);
}
```

2. **Verify that the bridge actually received the tokens** before processing the transfer request. Track the bridge's token balance before and after the call and require the difference to equal `_value + _feeLimit`.

3. **Do not use caller-supplied `_from` for fee refunds.** Refund excess fee to `msg.sender` (the token contract), which is the entity that actually transferred the tokens, not the unverified `_from` argument.

---

### Proof of Concept

```
Preconditions:
- Bridge deployed with token T registered (feeOfERC20[T] = 0)
- Bridge holds 1,000,000 T tokens as reserves (non-mintBurn mode)
- Attacker controls the contract at address T

Attack:
1. Attacker (from address T) calls:
   bridge.onERC20Received(
       attacker_wallet,   // _from  ← spoofed, attacker's wallet
       attacker_wallet,   // _to
       1,                 // _value ← minimum to pass require(_value > 0)
       1_000_000,         // _feeLimit ← entire bridge reserve
       ""
   )

2. Execution path:
   onERC20Received → _requestERC20Transfer(T, attacker_wallet, ..., 1, 1_000_000)
   → onlyRegisteredToken(T) ✓
   → _payERC20FeeAndRefundChange(attacker_wallet, T, 1_000_000)
   → feeOfERC20[T] == 0, _feeLimit > 0
   → IERC20(T).safeTransfer(attacker_wallet, 1_000_000)  ← bridge pays attacker

3. Result:
   - Bridge loses 1,000,000 T tokens
   - RequestValueTransfer event emitted; operators release 1 T on counterpart chain
   - Net loss: 1,000,000 T tokens from bridge reserves
``` [2](#0-1) [6](#0-5)

    function _payERC20FeeAndRefundChange(address from, address _token, uint256 _feeLimit) internal returns(uint256) {
        uint256 fee = feeOfERC20[_token];

        if (feeReceiver != address(0) && fee > 0) {
            require(_feeLimit >= fee, "insufficient feeLimit");

            IERC20(_token).safeTransfer(feeReceiver, fee);

            uint256 feeRefund = _feeLimit.sub(fee);
            if (feeRefund > 0) {
                IERC20(_token).safeTransfer(from, feeRefund);
            }

            return fee;
        }

        if (_feeLimit > 0) {
            IERC20(_token).safeTransfer(from, _feeLimit);
        }
        return 0;
    }
```
