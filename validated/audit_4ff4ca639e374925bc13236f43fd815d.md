### Title
Cross-repository status forgery via unscoped `Commit.where(sha:)` lookup - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` looks up commits by SHA across the *entire* `commits` table with no repository scoping, then calls `commit.create_status_from_github!(params)` on every match. Because a valid webhook signature only proves the sender controls *some* repository (their own), an attacker can send a `status` webhook from their own repo with any SHA that happens to collide with a commit in an unrelated stack, and forge that stack's CI status.

### Finding Description
The binding that must hold is: `commit.stack.repository.full_name == payload.dig('repository', 'full_name')` (the repository that authenticated the webhook). In `StatusHandler#process`:

```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [1](#0-0) 

this queries `Commit` globally by `sha` alone, with no filter on `commit.stack.repository`. Compare with `CheckSuiteHandler#process`, which correctly scopes via the base class's `stacks` helper (`Repository.from_github_repo_name(repository_name)&.stacks`) before touching commits:

```ruby
stacks.where(branch: params.check_suite.head_branch).each do |stack|
  stack.commits.where(sha: params.check_suite.head_sha).each(&:schedule_refresh_check_runs!)
end
``` [2](#0-1) 

The base `Handler` class exposes exactly this scoping mechanism (`stacks`/`repository_name`) but `StatusHandler` never calls it: [3](#0-2) 

`WebhooksController#verify_signature` only verifies that the HMAC signature matches the `webhook_secret` for the organization named in the payload's `repository.owner.login` — i.e., it proves the request legitimately originates from *some* GitHub App installation the sender controls, not that the sender is authorized to write to the specific commit/stack being touched: [4](#0-3) 

So an attacker who owns any repository with a Shipit-installed GitHub App can send a `status` event naming their own repository, but with `sha` set to a SHA borrowed/guessed from an unrelated victim repository's public commit history. If `Commit.where(sha: params.sha)` matches a row belonging to a different stack, `create_status_from_github!` mutates that victim commit's status — with no check that the sending repository owns that commit.

### Impact Explanation
Each successful SHA match lets the attacker write an arbitrary CI status (`success`, `failure`, `pending`, `error`, with attacker-controlled `description`/`target_url`/`context`) onto a commit belonging to a stack/repository they do not control, via `Commit#create_status_from_github!` [5](#0-4) . Since Shipit typically gates deploys on required statuses, forging a `success` status can unblock a deploy/merge for a repository the attacker never authenticated against — this is a payload for one repository mutating another's commit/stack, matching the Critical impact category ("a payload for one repository mutating another's stack, commit, task or team"). The attack is blind (no feedback on which SHA matched) but is repeatable at scale across the whole Shipit install, not limited to one victim.

### Likelihood Explanation
Preconditions are minimal: the attacker needs only their own repository with a Shipit GitHub App installation/`webhook_secret` (any tenant can self-register per `docs/setup.md`), which satisfies `verify_webhook_signature`. No Shipit session, API token, or team membership is required. The only real cost is guessing/enumerating SHAs that exist in the target's `commits` table (feasible since Git SHAs of trivial/empty/lockfile-only commits repeat across many public repos, and GitHub activity leaks SHAs). Exploitability is therefore realistic, if probabilistic per attempt, and trivially repeatable.

### Recommendation
Scope the commit lookup to the repository that authenticated the webhook, mirroring `CheckSuiteHandler`:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
end
```
using the existing `stacks`/`repository_name` helpers from `Handler`, so a `status` webhook can only affect commits belonging to the repository named in its own payload.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb`-style, using existing test factories, no live GitHub):
1. Create two unrelated stacks/repositories, `repo_a` and `repo_b`, each with a commit sharing the same `sha` value (`"deadbeef" * 5`).
2. Build a webhook payload whose `repository.full_name` is `repo_a`'s name but `sha` matches both commits (simulate signature already verified, i.e., call `StatusHandler.call(payload)` directly, bypassing controller-level signature check since that's not in question here).
3. Assert, before: `repo_a_commit.statuses.count == 0` and `repo_b_commit.statuses.count == 0`.
4. After calling `StatusHandler.call(payload)` with `state: 'success'`, assert `repo_a_commit.statuses.reload.count == 1` (expected) **and** `repo_b_commit.statuses.reload.count == 1` (unexpected cross-tenant write), proving `repo_b`'s commit status was mutated by a webhook that only authenticated `repo_a`.
5. Assert the equality `commit.stack.repository.full_name == payload.dig('repository', 'full_name')` is `false` for the `repo_b` commit yet a status row was still created, demonstrating the broken binding.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e

        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
