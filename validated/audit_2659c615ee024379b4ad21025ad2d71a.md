### Title
Webhook Signature Verified Against `repository.owner.login`/`organization.login` While Event Handlers Act On The Unrelated `repository.full_name` Field, Allowing Cross-Organization Payload Spoofing - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects the HMAC secret to validate an inbound GitHub webhook using the organization derived from `repository.owner.login` (or `organization.login`), but the event handlers that subsequently mutate state key off the completely independent `repository.full_name` field of the very same JSON body. Because these two fields are never cross-checked, a party who legitimately knows the webhook secret for *any* organization configured in a multi-tenant Shipit instance can forge a signed payload whose `owner.login` matches their own org (so it passes signature verification) while `repository.full_name` points at a stack belonging to a different organization, causing Shipit to process spoofed events (pushes, commit statuses, check-suite results, membership changes) for a repository they do not control.

### Finding Description
Signature verification: [1](#0-0) 

```
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(...)
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

`Shipit.github(organization:)` resolves a per-organization `GitHubApp` instance, each configured with its own independent `webhook_secret` in the multi-org secrets schema: [2](#0-1) 

The signature is verified using only the secret belonging to whatever organization is named in `repository.owner.login`/`organization.login`. That HMAC only proves the payload was signed with *that* organization's secret — it says nothing about the rest of the payload's content being trustworthy for other purposes.

However, once the request passes `verify_signature`, `create` dispatches to handlers that resolve which `Stack`/`Repository` to act on using a *different* field entirely: [3](#0-2) 

```
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
```

Nothing enforces that `repository.full_name` belongs to the same organization as `repository.owner.login`/`organization.login`. This breaks the intended binding: *"the organization whose secret authenticated the request"* must equal *"the repository the handlers act on."* An attacker who administers (or otherwise knows the webhook secret of) any single organization configured on the Shipit instance can compute a valid `X-Hub-Signature` over an arbitrary JSON body using their own org's secret, set `repository.owner.login`/`organization.login` to their own org (satisfying `verify_signature`), and set `repository.full_name` to `victim-org/victim-repo` (satisfying the handler's repository resolution). The webhook is accepted and processed against the victim stack.

### Impact Explanation
Depending on which event type is spoofed, this enables cross-organization writes to a stack the attacker does not own:
- `push` events queue `GithubSyncJob` for the targeted stack's commits [4](#0-3) .
- `status`/`check_suite` events can inject arbitrary CI/check results against a victim's commits, which feed directly into Shipit's deployability, merge-queue, and continuous-delivery logic (statuses gating commit deployability are described in `README.md`'s CI/merge configuration). Forging a passing status/check-suite for a targeted commit can move it into a "deployable"/"mergeable" state it should not have reached.
- `membership` events can create/modify `Team`/`Membership` records tied to the resolved organization's authorization model.

Because continuous delivery can automatically deploy commits once they are deemed deployable, and the merge queue can automatically merge PRs once required checks are green, spoofing status/check-suite success for a victim stack can lead to an unauthorized deploy or merge on infrastructure the attacker does not control — matching the Critical impact bar (cross-repository writes / unauthorized deploy or merge).

### Likelihood Explanation
This requires the Shipit instance to be configured with the multi-organization `github` secrets schema (distinct `webhook_secret` per org) and requires the attacker to legitimately possess (or be an administrator able to view) the webhook secret for at least one configured organization — a realistic scenario for any multi-tenant deployment of Shipit where multiple, mutually-distrusting GitHub organizations share one instance. No repository write access, Shipit session, or `ApiClient` token is required; only knowledge of one organization's webhook secret is needed to attack every other organization's stacks on the same instance.

### Recommendation
After computing `repository_owner` for signature selection, also validate that `repository.full_name`'s owner segment matches `repository_owner` (or `organization.login`) before dispatching to handlers, rejecting the webhook otherwise. Alternatively, resolve the target `Repository`/`Stack` using the same organization-scoped field used for signature verification rather than trusting `repository.full_name` independently.

### Proof of Concept
1. Configure Shipit in multi-org mode with two organizations, `attacker-org` (secret known to the attacker, e.g. an org admin) and `victim-org` (unrelated, target stack `victim-org/app`).
2. Attacker builds a JSON body:
```json
{
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/app" },
  "sha": "<victim commit>",
  "state": "success",
  ...
}
```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(attacker-org's webhook_secret, body)>`.
4. `POST /github/webhooks` with `X-Github-Event: status` and this body/signature.
5. `verify_signature` resolves `repository_owner => "attacker-org"`, uses `attacker-org`'s secret, and the HMAC checks out — the request passes verification.
6. The `status` handler resolves the target stack via `repository.full_name => "victim-org/app"`, applying the forged `success` status to a commit in `victim-org`'s stack, which the attacker does not own or control.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
