### Title
AAs can receive and permanently lock private assets they can never pay back out - (File: aa_composer.js)

### Summary
This is the same bug class as the reported `OngoingBounty.receiveNft()` issue: a contract-like entity (`OngoingBounty`) can accept a deposit type (NFTs) that it has no mechanism to ever pay back out, permanently locking value. In `ocore`, Autonomous Agents (AAs) have the exact same defect for private assets: an AA's trigger accounting (`getTrigger`) and balance bookkeeping (`updateInitialAABalances`) unconditionally credit *any* asset paid to the AA address, including private (`is_private`) assets, but the AA response composer (`sendUnit`) explicitly refuses to ever include a payment message for a private asset, unconditionally bouncing any attempt to do so.

### Finding Description
When a unit pays an AA address, `getTrigger()` builds `trigger.outputs[asset]` for every payment message targeting that address, with no filtering by asset privacy: [1](#0-0) 

`updateInitialAABalances()` then unconditionally credits `aa_balances` for the address with every asset present in `trigger.outputs`, again without any exclusion for private assets: [2](#0-1) 

However, when the AA's own oscript logic later tries to construct a response `payment` message spending any asset out of its balance, `sendUnit()` explicitly detects a private asset and unconditionally fails that message, which bounces the whole response: [3](#0-2) 

The comment on line 1329 ("it'll fail validation anyway due to lack of spend_proofs") documents that this is a deliberate protocol limitation, not a bug in the oscript author's code — private-asset payments require `spend_proofs` that only a real wallet holding the private encrypted chain can produce, and AAs (deterministic on-chain automatons) have no such private chain data. There is no other route in `aa_composer.js` for an AA to release a private-asset balance: `sendDummyUnit` (dry-run path) applies the same balance/asset bookkeeping and would hit the identical restriction in a real run, and `checkAAOutputs`/`aa_addresses.js` bounce-fee logic operates purely on public output amounts, offering no alternate withdrawal path.

Any unit poster (anyone, unprivileged) can send a private-asset payment to an AA address exactly like sending base bytes or a public asset — this is reachable purely by constructing a normal AA-trigger unit that outputs to the AA. Nothing in `validateAATrigger()` rejects private-asset outputs to AA addresses: [4](#0-3) 

### Impact Explanation
Any private asset value paid into an AA address is permanently and irrevocably locked: the AA's own balance bookkeeping records it as belonging to the AA, but the AA has no code path capable of ever spending it back out, since every private-asset outgoing message construction is hard-bounced. Unlike the original NFT case (which at least has an expiry timestamp implied by "locked in a timelock"), there is no protocol-level unlock mechanism at all for an AA's private-asset holdings — the funds are lost forever, constituting a permanent freezing of user/AA funds.

### Likelihood Explanation
Likelihood is high in the sense that any user can trigger this simply by mistakenly (or as a consequence of a poorly-audited AA definition that expects to reflow arbitrary received assets, e.g. generic "bounce/forward received coins" patterns seen in `bouncer_infinite_cycle.oscript` and `a_bank_without_percent.oscript`) sending a private asset to an AA address. AA authors are not warned anywhere in validation (`validateAA`) that private assets sent to their AA can never be forwarded, so an AA design that assumes it can reflect/forward "any asset received" (a common oscript idiom, as seen in the reflection/bouncer samples) will silently and permanently trap private-asset deposits.

### Recommendation
- Either reject private-asset payments to AA addresses at the protocol/validation level (in `validateAATrigger` / `validatePayment`), so such units cannot even be posted to an AA address, giving the sender an on-chain-enforced early failure instead of silent fund loss; or
- Add an explicit, well-documented mechanism (e.g., special-case handling in `aa_composer.js`) that at minimum prevents `getTrigger`/`updateInitialAABalances` from crediting an AA with private-asset value it can never spend, and instead causes the AA response to bounce the *entire trigger* (refusing the private-asset trigger up front) rather than accepting/crediting the balance and only failing later when the oscript tries to forward it out.

### Proof of Concept
1. Deploy an AA whose oscript unconditionally reflects any asset it receives back to the sender (pattern from `test/samples/bouncer_infinite_cycle.oscript` / `test/samples/a_bank_without_percent.oscript`).
2. A user issues a private, divisible asset (`is_private: true`) and sends a private payment output to the AA's address as part of a normal AA-trigger unit.
3. `getTrigger()` records `trigger.outputs[asset] = amount` for the private asset (aa_composer.js:375-397), and `updateInitialAABalances()` credits `aa_balances` for that asset (aa_composer.js:474-541).
4. The AA's `messages` template includes a `payment` message trying to forward the asset back; in `sendUnit()`'s per-message loop, `storage.loadAssetWithListOfAttestedAuthors` returns `objAsset.is_private === true`, and the code immediately does `return cb("sending private asset from AA")` (aa_composer.js:1329-1330), which propagates to `bounce(err)`.
5. The AA response bounces (or, if other messages exist, forwards only the public parts), but the private-asset balance credited to the AA's `aa_balances` row remains and can never be included in any future outgoing payment message, since every future attempt hits the same explicit rejection — the asset is permanently stuck.

function getTrigger(objUnit, receiving_address) {
	var trigger = { address: objUnit.authors[0].address, unit: objUnit.unit, outputs: {} };
	if ("max_aa_responses" in objUnit)
		trigger.max_aa_responses = objUnit.max_aa_responses;
	objUnit.messages.forEach(function (message) {
		if (message.app === 'data' && !trigger.data) // use the first data message, ignore the subsequent ones
			trigger.data = message.payload;
		else if (message.app === 'payment' && message.payload) {
			var payload = message.payload;
			var asset = payload.asset || 'base';
			payload.outputs.forEach(function (output) {
				if (output.address === receiving_address) {
					if (!trigger.outputs[asset])
						trigger.outputs[asset] = 0;
					trigger.outputs[asset] += output.amount; // in case there are several outputs
				}
			});
		}
	});
	if (Object.keys(trigger.outputs).length === 0)
		throw Error("no outputs to " + receiving_address);
	return trigger;
}
