Based on my investigation, the strongest SQL‑injection‑class analog I found in this repo is in the system‑vote counting logic executed automatically when a main‑chain index (MCI) becomes stable, specifically the numeric system‑vote branch that builds an `INSERT` statement by directly string‑interpolating a value taken from a unit's message payload instead of parameterizing it.

### Title
Unescaped interpolation of AA/unit `system_vote` value into `numerical_votes` INSERT query - ([File: main_chain.js])

### Summary
`saveSystemVote()`, invoked from `markMcIndexStable()` while processing stabilized units, builds SQL insert statements for the `numerical_votes` table by directly concatenating the vote `value` into the SQL string instead of using a parameterized `?` placeholder, mirroring the CVE-2022-42425 root cause (unsanitized user‑supplied string spliced into a SQL statement).

### Finding Description
When a unit becomes stable and carries a `system_vote` message with `subject` in `threshold_size`, `base_tps_fee`, `tps_interval`, or `tps_fee_multiplier`, `saveSystemVote()` builds the insert values like this: [1](#0-0) 
```
case "threshold_size":
case "base_tps_fee":
case "tps_interval":
case "tps_fee_multiplier":
    await conn.query("DELETE FROM numerical_votes WHERE subject=? AND address IN (?)", [subject, author_addresses]);
    for (let address of author_addresses)
        sqlValues.push(`(${db.escape(unit)}, ${db.escape(address)}, ${db.escape(subject)}, ${value}, ${timestamp})`);
    await conn.query("INSERT INTO numerical_votes (unit, address, subject, value, timestamp) VALUES " + sqlValues.join(', '));
    break;
```
Note that `unit`, `address`, and `subject` are passed through `db.escape()`, but `value` — which originates from the unit's own `system_vote` message payload authored by the unit's author (an ordinary, unprivileged address) — is spliced into the SQL string verbatim, with no `db.escape()` call and no parameter binding.

By contrast, the `op_list` branch just above it correctly escapes every element: [2](#0-1) 
```
case "op_list":
    const arrOPs = value;
    await conn.query("DELETE FROM op_votes WHERE address IN (?)", [author_addresses]);
    for (let address of author_addresses)
        sqlValues = sqlValues.concat(arrOPs.map(op_address => `(${db.escape(unit)}, ${db.escape(address)}, ${db.escape(op_address)}, ${timestamp})`));
    await conn.query("INSERT INTO op_votes (unit, address, op_address, timestamp) VALUES " + sqlValues.join(', '));
```

Whether this is remotely exploitable hinges entirely on how strictly `validation.js` type‑checks the `value` field for these numeric subjects before the unit is accepted/stabilized. I located references to `threshold_size`, `base_tps_fee`, `tps_interval`, and `tps_fee_multiplier` in `validation.js` (15 matches) but ran out of tool budget before I could confirm the exact type check applied to `value` there — i.e., whether it strictly enforces `typeof value === 'number'` (which would make raw interpolation safe because a JS number cannot carry SQL metacharacters) or whether it merely checks numeric-looking strings/ranges (which could leave a path for a crafted string to survive validation and reach the unescaped interpolation).

### Impact Explanation
If `validation.js` permits `value` to remain a string (e.g., only checking that it parses as a finite number without enforcing `typeof value === 'number'`), a malicious unit author could smuggle SQL metacharacters (e.g. via scientific/hex-like numeric strings that also validate but contain injected SQL) into the `INSERT INTO numerical_votes ...` statement built at `main_chain.js:1644-1645`, corrupting the votes table used later by `countVotes()` to determine consensus system parameters (TPS fee, threshold size, etc.). Since this path runs during MC stabilization — a step every full node performs identically — a successful injection could cause nodes to diverge on stored `numerical_votes` rows, resulting in disagreement on system-level parameters used for fee calculation/consensus, which maps to "node disagreement on validity/stability" impact category.

### Likelihood Explanation
Likelihood is **conditional and currently unconfirmed**: it requires that `validation.js`'s check for `threshold_size`/`base_tps_fee`/`tps_interval`/`tps_fee_multiplier` values does not strictly enforce a native JS `number` type prior to unit acceptance. If it does enforce `typeof value === 'number'` (as is typical hardening for these vote-count subjects in ocore), the interpolation, while stylistically inconsistent with the rest of the codebase (the `op_list` branch fully escapes, this branch does not), would not be exploitable because a JS `number` serializes to a plain digit string with no injectable characters. I was not able to confirm this validation rule within the available tool budget.

### Recommendation
Regardless of current validation strictness, harden `saveSystemVote()` in `main_chain.js` to use parameterized queries for `value` (and all fields) instead of string interpolation, consistent with the rest of the codebase's pattern of using `?` placeholders or `db.escape()` uniformly. This removes any possibility that a future relaxation of `validation.js`'s type checks (or edge cases like `NaN`, `Infinity`, or non-finite number serialization quirks) could reopen an injection path. Additionally, confirm in `validation.js` that `value` for these subjects is checked with a strict `typeof value === 'number'` guard (not just a numeric-string regex).

### Proof of Concept
Not constructable with certainty given the current unresolved state of `validation.js`'s type enforcement for `system_vote` numeric subjects. A concrete PoC would require confirming: (1) the exact validation applied to `payload.value` for `system_vote` messages with `subject` in the numeric set, and (2) whether any legal, validation‑passing value can carry characters that break out of the numeric-literal SQL context at `main_chain.js:1645`. Because I could not verify point (1) within available tool calls, I cannot supply a working exploit unit/trigger sequence — this should be treated as a **flagged code-hygiene / potential-injection risk requiring confirmation via `validation.js` inspection**, not a fully proven exploit.
