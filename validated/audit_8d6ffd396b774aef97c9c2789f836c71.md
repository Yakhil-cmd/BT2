### Title
CCMenuController bypasses ApiClient stack scoping, letting a stack-scoped token read the CI status of any stack - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Api::CCMenuController` overrides `BaseController#stack` with a version that resolves the target stack via the unscoped class method `Stack.from_param!`, instead of the scoped `stacks.from_param!` used everywhere else. This breaks the trust binding "a stack a token authorizes vs. a stack it touches": an `ApiClient` token that is restricted to a single stack (`stack_id` set) can still read the deploy/CI status of any other stack in the installation.

### Finding Description
`BaseController` scopes stack lookups to the API client's authorized stack when the client has a `stack_id`: [1](#0-0) 

This is the mechanism that enforces the equality "stack the token authorizes == stack the request touches" for every other stack-scoped API controller (deploys, tasks, rollbacks, hooks, etc.), which all call `stack` and get filtered through `stacks`.

`CCMenuController`, however, redefines `stack` to bypass this scoping entirely, resolving directly against the global `Stack` model: [2](#0-1) 

`Stack.from_param!` performs an unscoped lookup across all stacks by `repo_owner/repo_name/environment`: [3](#0-2) 

The only authorization check that runs is `require_permission :read, :stack`, which merely asserts that the client's `permissions` array contains `"read:stack"` — it never checks `stack_id`: [4](#0-3) 

So the equality that should hold — `current_api_client.stack_id == requested stack.id` (when `stack_id` is set) — is silently dropped for this one controller. Any client with `read:stack` permission (whether globally scoped or restricted to one specific stack) can pass an arbitrary `stack_id` in the URL and receive that other stack's `show` view.

### Impact Explanation
This is an authenticated-but-unauthorized cross-stack read: a token that was deliberately minted and scoped to a single, low-sensitivity stack (e.g., a CI status badge integration) can be replayed against the `stack_id` path segment to enumerate build status, last deploy id, and status (Success/Failure/lastBuildLabel) of every other stack managed by the installation, including stacks the client was never granted access to. This matches the "unauthenticated/unauthorized read of stack state" High-impact category defined in the rules — the token authorizes reads for stack A, but the code lets it touch stack B, C, … N.

### Likelihood Explanation
High. Exploitation requires only possession of any valid API token with `read:stack` permission — no signing secret, no privileged account, and no GitHub credentials are needed. `CCMenuController#authenticate_api_client` even accepts the token via a plain query-string `?token=` parameter (rather than Basic Auth), and its `require_permission :read, :stack` check runs against the raw client permissions, not against the client's `stack_id`, so the bypass is trivially reachable by anyone who already legitimately holds a scoped, low-privilege token (e.g., a CCMenu URL generated for one stack, cf. `CCMenuUrlController`, which mints a `read:stack`-only client tied to one stack and exposes its token in a URL).

### Recommendation
Make `CCMenuController#stack` reuse the scoped `stacks` collection (i.e., `stacks.from_param!(params[:stack_id])`) instead of calling `Stack.from_param!` directly, so the `current_api_client.stack_id` restriction from `BaseController#stacks` is enforced consistently across all API controllers.

### Proof of Concept
1. Create/obtain an `ApiClient` scoped to Stack A with permission `read:stack` only (e.g., via `CCMenuUrlController#fetch`, which creates such a client and returns its authentication token embedded in a CCMenu URL for Stack A): [5](#0-4) 
2. Using that token, issue: `GET /api/stacks/<stack-owner>/<stack-name>/<environment>/ccmenu?token=<stack-A-token>` but substitute Stack B's `owner/name/environment` in place of Stack A's.
3. `authenticate_api_client` accepts the token (it is valid), `require_permission :read, :stack` passes (the client has `read:stack`), and `stack` resolves Stack B via the unscoped `Stack.from_param!`, returning Stack B's CI/deploy status XML — even though the token was only ever meant to authorize reads of Stack A.
