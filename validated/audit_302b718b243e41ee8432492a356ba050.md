**Analysis:**

The `reject_transaction` early-return for `DiscardedVMStatus::SEQUENCE_NUMBER_TOO_NEW` is intentional, documented mempool behavior, not an admission-bypass bug. [1](#0-0) 

Key reasons this doesn't qualify as a valid finding under the review criteria:

1. **No admission bypass occurs.** `SEQUENCE_NUMBER_TOO_NEW` means the VM validator already checked signature, chain-id, expiry, and sequence-number ordering for this transaction and determined it is simply *ahead* of the account's current sequence number — i.e., it is a legitimately signed, well-formed future transaction from the correct sender that cannot execute yet because earlier sequence numbers haven't landed. It is not "rebound" to any different sender, signer set, or domain; no verification is skipped for it going forward — it must still pass full VM validation (including chain-id/expiry/signature) again before it can ever be included in a block via `get_batch`, which only selects transactions when `account_sequence_number == Some(&txn_seq)` or the immediate predecessor was already sent to consensus. [2](#0-1) 

2. **Retention is bounded, not permanent.** Regardless of `DiscardedVMStatus`, parked/pending transactions are still subject to independent garbage collection based on `system_transaction_timeout` (`gc_by_system_ttl`) and client-specified expiration (`gc_by_expiration_time`), which run periodically and evict stale entries irrespective of why they were never removed via `reject_transaction`. [3](#0-2) 

3. **No breach of sender/signer/replay/chain-id/expiry binding.** The scenario describes a transaction sitting in the "parking lot" waiting for its turn — this is the designed sequencing mechanism for out-of-order submission, not a corruption of admission state. It does not let an unprivileged attacker rebind, replay, or revive a transaction under a different sender/signer/domain, nor does it cause vm-validator, mempool, and VM checks to diverge on what is executable — they still agree that this transaction is inadmissible until its sequence number becomes current.

4. **Framing mismatch.** The cited file `randomness_config.move` has no relationship to mempool sequence-number handling or `reject_transaction`; there is no code path connecting randomness configuration to this mempool logic. [4](#0-3) 

This is expected mempool design (analogous to a "future nonce" holding area) rather than an admission-boundary vulnerability, and it does not meet the decision standard requiring a broken sender/signer/replay/domain guarantee from unprivileged input.
