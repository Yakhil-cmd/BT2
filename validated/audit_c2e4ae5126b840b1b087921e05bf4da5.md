### Title
Cross-organization forged commit status via unscoped `StatusHandler` lookup - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
The webhook signature check in `WebhooksController#verify_signature` authenticates a webhook against the GitHub organization derived from the payload's `repository.owner.login` field, but `StatusHandler#process` writes commit status data by matching `Commit.where(sha: params.sha)` with no repository/organization scoping at all. The binding "organization that authenticated" != "repository/commit that is written" is broken.

### Finding Description
`WebhooksController#verify_signature` looks up the webhook secret via `Shipit.github(organization: repository_owner)`, where `repository_owner` is read directly from the untrusted, not-yet-verified JSON body: `params.dig('repository', 'owner', 'login')` [1](#0-0) [2](#0-1) . The signature is a valid HMAC over the entire raw body computed with that organization's configured `webhook_secret` [3](#0-2) .

Once verified, `StatusHandler#process` locates target commits purely by SHA, with no check that the commit belongs to a stack/repository owned by the authenticated organization: [4](#0-3) 

Compare this to `PushHandler` and `CheckSuiteHandler`, which at least resolve target stacks through `Repository.from_github_repo_name(repository_name)` [5](#0-4)  — itself derived from the same attacker-supplied `repository.full_name` field, independent of `repository.owner.login` used for signing. `StatusHandler` doesn't even do that much: it never consults `repository` at all.

In a multi-tenant Shipit deployment (multiple GitHub organizations each configured with their own `webhook_secret` via `Shipit.github(organization:)`), an attacker who legitimately controls one onboarded organization's webhook secret (e.g., because they administer that org's GitHub App/webhook config, which is not a privileged action relative to *other* tenants' repositories) can craft an arbitrary JSON body — setting `repository.owner.login` to their own org (so the HMAC validates against their own secret) while setting `sha` to a commit SHA belonging to a completely different organization's stack. Because `StatusHandler` never checks that the "authenticated" organization is the actual owner of the commit being updated, the forged status is written directly onto a victim commit via `Commit#create_status_from_github!`.

### Impact Explanation
A forged commit status (e.g., a fake `success` state for a required CI context) written onto a victim organization's commit can satisfy `StatusChecker`/merge-queue/deploy gating logic (`required_statuses`, `merge_request_required_statuses`, etc.) for a repository the attacker has no legitimate write access to, enabling an unauthorized deploy or merge on a cross-tenant stack — a Critical-tier outcome ("cross-repository writes" / "unauthorized deploy, rollback or merge").

### Likelihood Explanation
Exploitation requires the attacker to be an onboarded tenant/organization admin in a multi-org Shipit instance (able to know or set their own org's `webhook_secret`) and to guess or discover a victim commit SHA (SHAs are often publicly visible via GitHub, PRs, CI logs, etc.). No GitHub App private key, `api_clients_secret`, or Shipit session/API token is required — only the ability to send a correctly-signed webhook for one's own organization, which is normal onboarding capability, not a privileged escalation.

### Recommendation
`StatusHandler` (and any handler acting on payload-derived identifiers) must cross-check that the target `Commit`'s `Stack`/`Repository` actually belongs to the organization that produced a valid signature, e.g., by joining through `stacks.commits.where(sha: params.sha)` scoped to `Repository.from_github_repo_name(payload.dig('repository','full_name'))`, and additionally verifying that the payload's `repository.full_name` owner segment matches the authenticated `repository.owner.login` used to select the webhook secret, rejecting the payload otherwise.

### Proof of Concept
1. Attacker administers `attacker-org/some-repo` in the same multi-tenant Shipit instance and knows/controls that org's configured `webhook_secret`.
2. Attacker crafts a `status` event JSON body:
```json
{
  "sha": "<victim_commit_sha>",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "attacker-org/some-repo" }
}
```
3. Attacker computes `sha1=HMAC(attacker_org_webhook_secret, raw_body)` and sends the POST with header `X-Github-Event: status` and `X-Hub-Signature: sha1=<hmac>`.
4. `WebhooksController#verify_signature` resolves `Shipit.github(organization: "attacker-org")` and verifies successfully against the attacker's own secret [1](#0-0) .
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)`, matches the victim's commit (in a different organization's stack), and calls `create_status_from_github!(params)`, injecting a forged "success" status onto it [4](#0-3) .
6. If that context is required for merge/deploy gating on the victim's stack, the forged status can unblock an unauthorized merge/deploy there.

Note: confirming this end-to-end requires validating `Commit#create_status_from_github!` and the exact `StatusChecker` gating logic, plus whether the deployed Shipit instance actually runs in multi-organization mode with per-org `webhook_secret`s (single-org deployments would not expose this cross-tenant boundary). I was unable to fully inspect `Commit#create_status_from_github!` before the iteration limit; a Devin session with full file access could verify this remaining detail.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
