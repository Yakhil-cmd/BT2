## Title
CCMenu API endpoint ignores per-stack token scoping, allowing a stack-restricted `ApiClient` to read any stack's build status - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::CCMenuController` overrides the base `stack` resolver to look up the stack directly with `Stack.from_param!(params[:stack_id])` instead of using the stack-scoped lookup (`stacks.from_param!`) that every other API controller inherits from `Shipit::Api::BaseController`. This decouples the stack the `ApiClient` token is authorized for from the stack the request actually touches, letting a token scoped to one stack read CCMenu status for any stack in the installation.

### Finding Description
`Shipit::Api::BaseController` enforces per-token stack scoping through two cooperating methods: [1](#0-0) 

`stacks` restricts the queryable set to `current_api_client.stack_id` when the `ApiClient` is scoped to a specific stack (`belongs_to :stack, optional: true` on the model), and `stack` resolves `params[:stack_id]` only within that restricted set. Every other API controller (e.g. `Shipit::Api::StacksController#stack`, `Shipit::Api::TasksController`) relies on this scoped `stack` helper.

`Shipit::Api::CCMenuController`, however, redefines `stack` to bypass the scoping entirely: [2](#0-1) 

The action only checks the coarse permission list via `require_permission :read, :stack`: [3](#0-2) 

`ApiClient#check_permissions!` verifies only that `"read:stack"` is present in the client's `permissions` array — it never consults `stack_id`: [4](#0-3) 

The binding that should hold is: **stack authorized by token (`current_api_client.stack_id`) == stack touched by request (`params[:stack_id]` resolved via `stack`)**. Before the CCMenu endpoint existed as written, this equality was maintained by `BaseController#stack`. In `CCMenuController`, the equality is broken: the resolved stack is any stack matching `params[:stack_id]`, regardless of `current_api_client.stack_id`.

This controller additionally supports a bespoke authentication path (`authenticate_api_client` overridden to accept `params[:token]` directly, used for the public CCMenu XML feed), but that does not change the scoping issue — even ApiClients authenticated the normal Basic-Auth way and legitimately restricted to one stack are affected because the override applies to `show` regardless of how authentication happened.

### Impact Explanation
Any `ApiClient` created with a `stack_id` restriction and `read:stack` permission — the model explicitly supports (and the fixture `here_come_the_walrus` demonstrates) this restricted-token pattern for delegating scoped access to a single repository/stack — can be replayed against `GET /api/stacks/:stack_id/ccmenu` with an arbitrary `stack_id` to read another stack's build status, label, last build time, and activity (`app/views/shipit/ccmenu/project` renders `name`, `activity`, `lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, `webUrl`). This is an unauthorized read of stack state outside the boundary the token issuer intended, which is explicitly one of the accepted High-impact classes (escalation into stack read authorization / unauthenticated-scope read of stack state) for this engine.

### Likelihood Explanation
Likelihood is high for any deployment that issues per-stack scoped `ApiClient` tokens (a supported, documented model feature — `belongs_to :stack, optional: true`), since exploitation requires nothing more than possessing one valid, narrowly-scoped token and changing the `stack_id` path parameter in an otherwise ordinary API call; no additional privilege, secret, or session is needed beyond the token itself.

### Recommendation
Remove the `stack` override in `Shipit::Api::CCMenuController` (or reimplement it using the inherited `stacks.from_param!`) so the CCMenu endpoint respects `current_api_client.stack_id` scoping identical to every other API controller:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```

### Proof of Concept
1. Create (or have an administrator create) an `ApiClient` with `stack_id` set to stack A and `permissions: ['read:stack']` — mirrors fixture `here_come_the_walrus` in `test/fixtures/shipit/api_clients.yml`.
2. Using that client's `authentication_token`, issue `GET /api/stacks/<stack-B-id>/ccmenu` (Basic Auth or `?token=` per `authenticate_api_client` override), where stack B is a different stack the token was never granted access to.
3. Observe the response returns HTTP 200 with stack B's CCMenu XML (`name`, `lastBuildStatus`, etc.), even though `current_api_client.stack_id` is stack A — demonstrating the scoping bypass, in contrast to the same token being correctly rejected/limited by `stack_id` scoping if used against, e.g., `GET /api/stacks/<stack-B-id>` (`Shipit::Api::StacksController#show`), which uses the properly scoped `stack` helper.
