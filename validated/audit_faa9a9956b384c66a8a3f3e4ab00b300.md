### Title
Webhook signature verification selects the organization's secret from an unverified payload field, letting one org's webhook secret forge events for a *different* org's tracked repositories - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` picks which GitHub App/organization secret to validate a webhook's HMAC signature against by reading `repository.owner.login` (or `organization.login`) directly out of the same, not-yet-verified JSON body. Once the HMAC passes for *that* chosen organization, the entire body — including unrelated fields such as `repository.full_name`, `sha`, `state`, `ref` — is handed unmodified to the event handlers, which use those other fields to decide which `Stack`/`Commit` to mutate. Nothing ties the organization whose secret validated the signature to the repository the handlers actually act on.

### Finding Description [1](#0-0)  chooses the `GithubApp` used for signature verification with: [2](#0-1) 

`repository_owner` is derived purely from the JSON body the attacker controls, before the signature has been checked. `verify_webhook_signature` then does a plain HMAC-SHA1 comparison of the *entire* raw body against that organization's `webhook_secret`: [3](#0-2) 

Crucially, the code never checks that the `repository_owner` used to *select the secret* is consistent with any other repository identifier used *by the handler that ultimately runs* (e.g. `repository.full_name`, used for stack lookups). `Shipit.github(organization:)` is explicitly multi-tenant — each configured organization has its own independent `webhook_secret`: [4](#0-3) 

The handlers that run after verification act on payload fields taken at face value with no re-validation against GitHub's API — e.g. `StatusHandler`-driven commit status creation directly copies `target_url`, `state`, `description`, `context` from the payload: [5](#0-4) 
and `PushHandler` uses `params.ref`/`params.after` to find matching stacks by branch and kick off a sync/deploy pipeline: [6](#0-5) 

**Binding broken (equality that should hold but doesn't):**
`organization whose webhook_secret authenticated the request == organization/repository the handler subsequently writes to`

**Before the attack (legitimate flow):** GitHub signs the *entire* payload with the secret for the organization that actually owns `repository.full_name`; `repository.owner.login` and `repository.full_name`'s owner are always consistent because GitHub itself produced both fields.

**After the attack:** An attacker who only knows Organization A's `webhook_secret` (e.g., because they are able to configure/view OrgA's GitHub App webhook settings — an action entirely external to Shipit's own authorization model) crafts an arbitrary JSON body where `repository.owner.login` (or `organization.login`) = `"OrgA"`, but `repository.full_name` = `"OrgB/victim-repo"` (any other repository/stack tracked by the same shared Shipit instance). They sign the raw body with OrgA's secret. `repository_owner` resolves to OrgA, `Shipit.github(organization: "OrgA")` returns OrgA's `GithubApp`, and the HMAC check succeeds because it is being checked against the correct (OrgA) secret for the body the attacker actually sent. The handlers then process `repository.full_name = "OrgB/victim-repo"`, writing state for a repository the attacker has no legitimate relationship with.

### Impact Explanation
This crosses the "cross-repository writes / unauthorized deploy" impact bar: an actor who legitimately controls only one tenant organization's webhook secret can forge `push`, `status`/`commit_status`, `check_suite`, `membership`, or `pull_request` events for a **different** organization's repositories tracked in the same Shipit instance. Concretely:
- Forged `push` events queue `GithubSyncJob` for the victim stack (`Stack#sync_github`), which can trigger continuous delivery / unwanted deploy scheduling for a stack the attacker doesn't control.
- Forged `status`/`commit_status` events directly create `Status` records with attacker-chosen `state`, `context`, `target_url`, potentially unblocking or blocking deploy gating checks (`ci.require` logic) for the victim stack.
- Forged `membership`/`pull_request` events can create/alter `Team`/`Membership`/merge-queue state tied to the victim org.

This is a cross-tenant trust-boundary break specific to multi-organization Shipit deployments (a configuration the engine explicitly supports via `Shipit.github(organization:)`), matching the "organization that authenticated versus the repository that is written" binding called out in scope.

### Likelihood Explanation
Requires: (1) the Shipit instance to be configured for more than one GitHub organization (multiple `GithubApp` configs, each with its own `webhook_secret`), and (2) the attacker to be able to obtain/know one configured organization's `webhook_secret` (e.g., as that organization's own GitHub App administrator) — this does not require any Shipit-side credential (no `ApiClient` token, no Shipit session, no GitHub App private key of the victim org). Given that shared Shipit instances serving multiple organizations are a documented and supported use case, this is a realistic configuration, though it depends on the deployer actually configuring multiple orgs.

### Recommendation
When resolving `repository_owner` for signature verification, require that the same field used to select the secret is also the field used by every handler for repository resolution, and additionally re-verify (post-signature) that `repository.full_name`'s owner segment matches `repository.owner.login`/`organization.login` before dispatching to handlers. Reject the webhook if these are inconsistent.

### Proof of Concept
1. Configure Shipit with two organizations, `OrgA` and `OrgB`, each with its own `webhook_secret` (`SECRET_A`, `SECRET_B`), both tracked as stacks in the same instance.
2. As an administrator of OrgA (who legitimately knows `SECRET_A` from OrgA's own GitHub App settings), craft a `push` payload:
```json
{
  "ref": "refs/heads/master",
  "after": "<any-existing-sha-in-OrgB/victim-repo>",
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/victim-repo" }
}
```
3. Compute `sha1=<hmac>` using `SECRET_A` over the raw JSON body.
4. `POST /webhooks` with header `X-Github-Event: push` and `X-Hub-Signature: sha1=<hmac>`.
5. `repository_owner` resolves to `"OrgA"` [2](#0-1) , `verify_webhook_signature` succeeds using `SECRET_A` [3](#0-2) , and `PushHandler` processes the forged event for `OrgB/victim-repo`, enqueuing `GithubSyncJob` for stacks whose repository is `OrgB/victim-repo` [6](#0-5) .

Note: I was not able to fully inspect `Shipit::Webhooks::Handlers::StatusHandler` and the generic `Handler` base class within the tool-call budget (file reads for those specific files did not return content), so the exact repository-lookup mechanism used by non-push handlers (e.g., whether they resolve by `repository.id` vs `full_name`, and whether any additional owner-consistency check exists there) could not be verified line-by-line; the push/status behavior above is inferred from `test/controllers/webhooks_controller_test.rb` and `PushHandler`. A Devin session with full repository access should verify `app/models/shipit/webhooks/handlers/status_handler.rb` and `handler.rb` directly to confirm identical behavior across all `EVENTS`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
