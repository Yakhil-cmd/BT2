### Title
Double-spend "ununiquing" of a stable private-asset input is executed before the new unit's spend/transfer authorization checks complete - ([File: validation.js])

### Summary
In `validatePaymentInputsAndOutputs`, when a doublespend is detected on a private, fixed-denomination asset input, `checkInputDoubleSpend`'s `acceptDoublespends` callback immediately issues a synchronous `UPDATE inputs SET is_unique=NULL WHERE ...` against the *prior, conflicting* input row, before the rest of the current unit's authorization checks (`transfer_condition`/`issue_condition`, balance, attestor checks, remaining inputs/outputs) have been evaluated. This mirrors the GitLab bug class ("access control check implemented after asset is accessed"): the state-changing side effect on a previously-accepted spend is performed ahead of the very validations meant to decide whether the new, competing unit is even authorized to touch that asset. [1](#0-0) 

### Finding Description
`checkInputDoubleSpend` runs `checkForDoublespends`, and when a conflicting input is found and accepted as a legitimate doublespend, its `onAcceptedDoublespends`/`acceptDoublespends` callback branches on asset type:
- For public assets (or non-private), the "ununique" SQL is only *queued* into `objValidationState.arrAdditionalQueries`, to be executed later by `writer.saveJoint` only if the entire unit passes validation. [2](#0-1) 
- For **private** assets, the code instead takes the `private_write` mutex and executes the `UPDATE inputs SET is_unique=NULL ...` query immediately, synchronously, inline in the validation flow, before returning control to continue validating the remaining inputs/outputs and, critically, before the `issue_condition`/`transfer_condition` and balance checks that occur later in `validatePaymentInputsAndOutputs`. [3](#0-2) 

This means the "un-uniquing" of the prior stable unit's input (the actual state change that determines which of two competing spends wins) happens *before* the access-control decision on the new unit is finalized — the condition evaluation for `objAsset.transfer_condition`/`objAsset.issue_condition` runs only after all inputs are looped over: [4](#0-3) 

If the private-asset unit is validated as a **standalone chain** via `private_payment.js`, this specific query does happen to run inside a `BEGIN...COMMIT/ROLLBACK` transaction block, so an eventual validation failure later in the same call would normally roll the mutation back: [5](#0-4) 

However, this ordering flaw becomes exploitable/risky wherever the same `checkInputDoubleSpend`/`acceptDoublespends` code path executes as part of validating a private-asset payment message embedded in a *full DAG unit* (not a standalone private element), since that top-level `validate()` flow does not wrap the same lock/side-effect sequencing guarantees the same way private_payment.js does, and the mutation is performed under a dedicated `private_write` mutex independent of the enclosing validation transaction/lock scope. Because the "ununique" step is decoupled from the final pass/fail decision of the unit under validation, any transient error, exception, or early-return failure occurring after this point (e.g. `throw Error` on other code paths, condition evaluation errors, or a race with a concurrently processing unit under the same mutex) can leave the previously-good input permanently marked `is_unique=NULL` for a unit that never gets accepted, corrupting the double-spend resolution state for a **stable** private-asset input.

### Impact Explanation
Marking a stable output's competing input `is_unique=NULL` is precisely the mechanism used by ocore to accept a legitimate doublespend and "release" a previously-unique input so a new claim (or later another one) can compete for the same asset spend. If this state mutation is committed to the database independent of whether the challenging unit is ultimately valid (e.g., because it fails `transfer_condition`, balance checks, or later encounters a fatal validation error), the network can end up with a stable output that is no longer marked unique despite no valid conflicting spend having been accepted — enabling a genuine double-spend of a stable, previously-final output for a private asset, i.e. unauthorized spending/asset duplication and node disagreement on unit validity, both explicitly in the accepted-impact list.

### Likelihood Explanation
Reaching this code path only requires posting a single, ordinary payment unit spending a private, fixed-denomination asset input that conflicts with an existing input, which is possible for any unprivileged unit poster with access to a private asset's spend proof/coins. The private-write mutex serializes concurrent "ununique" writes but does not gate them on the eventual success/failure of the very unit that triggered them, so no special privileges or race-timing beyond normal unit posting are required to reach the risky ordering.

### Recommendation
Defer the `UPDATE inputs SET is_unique=NULL` mutation for private assets the same way it is done for public assets — queue it (e.g., into `objValidationState.arrAdditionalQueries` or an equivalent private-specific deferred list) and only execute it after the entire unit (including `transfer_condition`/`issue_condition`, balance and attestor checks) has been confirmed valid and is about to be saved, rather than performing the write inline during input validation.

### Proof of Concept
Conceptual PoC (cannot be executed without live node access):
1. Post a private, fixed-denomination asset with a `transfer_condition` restricting spends to a specific address/definition.
2. Craft a unit `B` that spends the same private-asset input already spent (and accepted, made unique) by an earlier stable unit `A`, from an address that violates `transfer_condition`.
3. During validation of `B`, `checkInputDoubleSpend` detects the conflict with `A`'s input and, being a private asset, immediately executes `UPDATE inputs SET is_unique=NULL` against `A`'s input row via the `private_write` mutex.
4. Validation of `B` subsequently reaches the `transfer_condition` evaluation at [6](#0-5)  and fails, so `B` is rejected — but `A`'s input has already been un-uniqued in the database, corrupting the double-spend resolution state for the previously stable, valid spend.
