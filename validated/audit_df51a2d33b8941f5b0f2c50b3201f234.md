### Title
Webhook signature verification binds to the wrong field, letting any onboarded GitHub organization forge events for another organization's repository - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which HMAC secret to check a webhook against using `repository_owner`, which is read from the attacker-fully-controlled JSON body (`repository.owner.login` / `organization.login`), and then verifies the entire raw body against that organization's `webhook_secret`. Because the HMAC signer, the signed payload, and the field used to pick the secret are all chosen by whoever crafts the request, any principal who knows (or is issued) a valid `webhook_secret` for *one* organization configured in this Shipit instance can compute a valid signature for a payload whose `repository.full_name` (the field every downstream handler actually acts on) points at a *different* organization/repository.

### Finding Description
`verify_signature` does:
```ruby
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
``` [1](#0-0) 
with
```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [2](#0-1) 

`GitHubApp#verify_webhook_signature` just HMAC-verifies the raw body against the secret for that organization:
```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  algorithm, signature = signature.split("=", 2)
  return false unless algorithm == 'sha1'
  SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
end
``` [3](#0-2) 

Meanwhile, every event handler resolves the *repository actually acted upon* from a different JSON field, `repository.full_name`:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [4](#0-3) 

and PR handlers resolve it the same way (`params.repository.full_name`): [5](#0-4) 

Since a request forger controls the entire raw HTTP body, they can construct a JSON payload where `repository.owner.login` (used only to pick the verification secret) is set to an organization whose `webhook_secret` they know, while `repository.full_name` (used by every handler to select the target `Repository`/`Stack`) is set to `"victim-org/victim-repo"`. They then sign the whole body with the known secret and send it. `verify_signature` looks up `Shipit.github(organization: "attacker-org")`, HMAC-verifies successfully (it's their own secret over their own crafted bytes), and the request passes. The webhook handlers then act on `victim-org/victim-repo` because they trust `repository.full_name`, a field that was never cross-checked against the organization whose secret validated the signature.

This breaks the binding: *the organization whose credential authenticated the request* ≠ *the repository the handler subsequently writes to*. The signature only proves "this body was produced by someone who knows attacker-org's secret" — it says nothing about which repository the body claims to describe, since that claim is inside the very body the attacker wrote.

### Impact Explanation
An attacker with legitimate but unprivileged access to *any* one organization onboarded into this (evidently multi-tenant) Shipit instance — e.g., they administer their own GitHub org that has a Shipit GitHub App/webhook configured, or they have obtained that org's `webhook_secret` — can forge `pull_request` events for a victim organization's repository:
- `PullRequest::OpenedHandler#process` calls `ReviewStackAdapter#find_or_create!`, which on `create!` builds a new `ReviewStack` with `branch: params.pull_request.head.ref` and stores `github_pull_request: params.pull_request`, then queues it for provisioning: [6](#0-5) 
This causes the victim's Shipit stack to check out and provision/deploy an attacker-chosen ref against the victim's real deploy infrastructure — an unauthorized deploy of a repository the attacker has no write access to, and no `ApiClient`/session/GitHub-permission on.
- The `push` handler (`PushHandler#process` via `Handler#stacks`) similarly can trigger `GithubSyncJob` against the victim's stacks using an attacker-forged `expected_head_sha`. [7](#0-6) 

This qualifies as Critical: an unauthorized deploy triggered by an attacker who never held credentials scoped to the victim repository/organization.

### Likelihood Explanation
Requires the Shipit deployment to be multi-tenant (serving multiple GitHub organizations with distinct `webhook_secret`s configured via `Shipit.github(organization:)`), which is explicitly supported by the code (`Shipit::GithubOrganizationUnknown` handling, per-organization config lookup). Any org admin/webhook-secret holder for one tenant can exploit this against any other tenant without further privileges — no session, no `ApiClient` token, no GitHub write access to the victim repo is needed. Likelihood is high in any deployment with more than one onboarded organization.

### Recommendation
After signature verification succeeds, cross-check that `repository.owner.login` (or `organization.login`) used to select the secret actually matches the owner portion of `repository.full_name` (and any other repository identifiers used by handlers) before dispatching to `Shipit::Webhooks.for_event`. Reject the webhook if they diverge. More robustly, resolve the target `Repository`/`Stack` first from `full_name`, derive its expected owning organization from Shipit's own stored configuration, and verify the signature using that organization's secret rather than trusting the org name embedded in the payload.

### Proof of Concept
1. Shipit instance has two onboarded GitHub orgs: `attacker-org` (attacker is an admin, knows `webhook_secret_A`) and `victim-org` (a stack `victim-org/victim-repo` exists with review-stacks provisioning enabled).
2. Attacker crafts a `pull_request` "opened" JSON payload with:
   - `repository.owner.login = "attacker-org"`
   - `repository.full_name = "victim-org/victim-repo"`
   - `pull_request.head.ref = "attacker-controlled-branch"`
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(webhook_secret_A, raw_body)>` and POSTs to `/webhooks` with `X-Github-Event: pull_request`.
4. `verify_signature` calls `Shipit.github(organization: "attacker-org")`, verifies successfully against the attacker's own known secret.
5. `PullRequest::OpenedHandler` resolves `repository` via `Repository.from_github_repo_name("victim-org/victim-repo")` and creates/provisions a `ReviewStack` for the victim repository using the attacker-supplied ref, causing deploy commands to run against the victim's infrastructure.
