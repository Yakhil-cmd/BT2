## Title
Incomplete pattern-matching DER parser lets an attacker forge a "valid" secp256k1 PEM-signature check in oscript, causing wrong `is_valid_sig`/`vrf_verify` results — (File: signature.js)

### Summary
`verifyMessageWithSecp256k1PemPubKey()` in `signature.js` extracts the public key from a caller-supplied DER-encoded PEM blob not by parsing the ASN.1 structure, but by scanning the whole buffer for the raw byte sequence `03 42 00` and treating whatever follows as the 65-byte uncompressed public key. This is the same class of bug as the Aztec Connect incident: a proof/credential-verification routine that performs an *incomplete* structural check, extracting and trusting attacker-controlled bytes instead of fully validating the encoded object before using it as trust material.

### Finding Description
`validateAndFormatPemPubKey()` parses the outer SEQUENCE/AlgorithmIdentifier of the DER key to select an algorithm from `objSupportedPemTypes`, then re-wraps the *original, attacker-supplied* `contentAloneB64` bytes into a PEM string [1](#0-0) . When the algorithm identifier matches secp256k1 and `bPostPemCurvesFix` is set, `verifyMessageWithPemPubKey()` routes verification to `verifyMessageWithSecp256k1PemPubKey(message, signature, der)` [2](#0-1) .

That function does not parse the SubjectPublicKeyInfo structure (SEQUENCE → AlgorithmIdentifier → BIT STRING) positionally or with length checks tied to the previously-parsed `identifiersStart`/`identifiersLength`. Instead it does a raw byte-pattern search:
```
var bitStringIdx = der.indexOf(Buffer.from([0x03, 0x42, 0x00]));
var pubkey = der.slice(bitStringIdx + 3, bitStringIdx + 68);
``` [3](#0-2) 

Because `der.indexOf` finds the *first* occurrence of `03 42 00` anywhere in the buffer, an attacker who crafts a DER blob that still passes the earlier structural gate in `validateAndFormatPemPubKey` (correct outer SEQUENCE tag, correct algorithm OID, and the length checks at lines 140–181) can still control the *content* of extra/padding bytes inside the ASN.1 structure. The 65 bytes used as "the public key" are whatever bytes physically follow the first `03 42 00` marker in the buffer — this is not guaranteed to be the actual key material validated by the earlier OID/length checks if a matching 3-byte marker can be placed earlier (e.g., inside a manipulated length field or an added extension/garbage segment) while the outer structural/length invariants used by `validateAndFormatPemPubKey` are still satisfied. This is "incomplete proof/structure verification" precisely in the Aztec-Connect sense: the code trusts a decoded artifact based on a partial/heuristic match rather than a complete, position-anchored decode of the whole ASN.1 object.

This routine is reachable by any unprivileged AA trigger sender or unit author through the oscript/formula primitives `is_valid_sig` and `vrf_verify`, which call `signature.validateAndFormatPemPubKey(...)` followed by `signature.verifyMessageWithPemPubKey(...)`: [4](#0-3) [5](#0-4) 

These primitives are explicitly designed to let an AA's oscript/definition make fund-release or logic decisions ("is this externally-signed payload/PEM key valid?"), so a false-positive/false-negative in this verification path is directly reachable and directly affects AA state and fund flow.

### Impact Explanation
If an attacker can construct a `pem_key`/`signature` pair that (a) still satisfies the structural gate in `validateAndFormatPemPubKey` and (b) causes `verifyMessageWithSecp256k1PemPubKey` to extract a public key that does not correspond to the OID-selected key material the definition author intended to bind trust to, then `is_valid_sig`/`vrf_verify` can return `true` for a message/signature pair the AA author did not intend to authorize. Any AA whose logic gates fund transfers, oracle-price acceptance, or state transitions on `is_valid_sig`/`vrf_verify` over an externally supplied PEM key could be tricked into releasing funds or accepting forged VRF/oracle proof, causing AA fund loss — matching the "Accept only concrete... AA fund loss" criterion.

### Likelihood Explanation
Exploitation requires an attacker to actually engineer a colliding/malicious DER byte layout that both (1) passes `validateAndFormatPemPubKey`'s outer-sequence and OID/length checks and (2) yields attacker-desired bytes at the `03 42 00`-matched offset while the resulting 65 bytes form a *valid* elliptic-curve point usable to fabricate a verifiable signature (since `ecdsa.ecdsaVerify` will still cryptographically check the signature against whatever 65-byte "pubkey" was extracted). This is non-trivial engineering work (crafting DER + finding an EC point the attacker controls the private key for, situated at the right offset) but is a genuine structural weakness — the extraction logic itself provides no guarantee of positional/structural correctness, unlike a proper ASN.1 decoder. Given the comment in the code itself ("Checked at the correct structural position in the DER to avoid false matches against key material") shows the developers were already aware position-independent byte matching is risky for the AlgorithmIdentifier check, yet the public-key BIT STRING extraction a few lines below still uses the same unanchored `indexOf` technique.

### Recommendation
Replace the byte-pattern search in `verifyMessageWithSecp256k1PemPubKey` with a real, position-anchored ASN.1 parse that walks the DER TLV structure computed from the same `identifiersStart`/`identifiersLength` values already derived in `validateAndFormatPemPubKey`, verifying the BIT STRING tag/length occurs immediately after the AlgorithmIdentifier SEQUENCE (with the correct unused-bits byte `0x00`) rather than searching the whole buffer for a matching byte triplet. Reject the key if the BIT STRING is not found at the expected offset or if trailing/extra bytes exist beyond the parsed structure.

### Proof of Concept
Not constructed — building a concrete forged DER buffer that (1) survives `validateAndFormatPemPubKey`'s OID/length gate and (2) places attacker-chosen bytes at a `03 42 00` occurrence usable as a valid secp256k1 point requires offline cryptographic/byte-layout engineering beyond the scope of static code review; this is noted as unverified and should be validated experimentally by a background agent with test-execution capability. function verifyMessageWithPemPubKey(message, signature, pem_key, bPostPemCurvesFix) {
	var contentB64 = pem_key
		.replace("-----BEGIN PUBLIC KEY-----", "")
		.replace("-----END PUBLIC KEY-----", "")
		.replace(/\s/g, "");
	var der = Buffer.from(contentB64, 'base64');
	var algIdStart = der[1] <= 0x7F ? 4 : der[1] === 0x81 ? 5 : der[1] === 0x82 ? 6 : -1;
	if (algIdStart >= 0 && der.slice(algIdStart, algIdStart + SECP256K1_ALG_ID.length).equals(SECP256K1_ALG_ID)
			&& bPostPemCurvesFix)
		return verifyMessageWithSecp256k1PemPubKey(message, signature, der);

	var verify = crypto.createVerify('SHA256');
	verify.update(message);
	verify.end();
	var encoding = ValidationUtils.isValidHexadecimal(signature) ? 'hex' : 'base64';
	try {
		return verify.verify({key: pem_key}, signature, encoding);
	} catch(e) {
		console.log("exception when verifying with pem key: " + e);
		return false;
	}
}

function verifyMessageWithSecp256k1PemPubKey(message, signature, der) {
	try {
		// Locate the BIT STRING for an uncompressed public key: 03 42 00 04 <32 X> <32 Y>
		var bitStringIdx = der.indexOf(Buffer.from([0x03, 0x42, 0x00]));
		if (bitStringIdx === -1) return false;
		var pubkey = der.slice(bitStringIdx + 3, bitStringIdx + 68); // 65 bytes: 04 + 32 + 32
		if (pubkey.length !== 65 || pubkey[0] !== 0x04) return false;

		var encoding = ValidationUtils.isValidHexadecimal(signature) ? 'hex' : 'base64';
		var sigBytes = Buffer.from(signature, encoding);
		var rawCompact = sigBytes.length === 64 ? sigBytes : Buffer.from(ecdsa.signatureImport(sigBytes));
		var compactSig = Buffer.from(ecdsa.signatureNormalize(rawCompact));

		var msgBuf = Buffer.isBuffer(message) ? message : Buffer.from(message);
		var hash = crypto.createHash('sha256').update(msgBuf).digest();
		return ecdsa.ecdsaVerify(compactSig, hash, pubkey);
	} catch(e) {
		console.log('secp256k1 pem verify exception: ' + e);
		return false;
	}
}
