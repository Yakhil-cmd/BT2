## Title
`PERL5OPT` (or any env var name) injected via uppercased pull-request label reaches spawned process env, enabling command injection into perl-based deploy steps - (File: `app/models/shipit/review_stack.rb`)

## Summary
`ReviewStack#env` merges the pull request's label names — uppercased, with no allowlist — directly into the stack's environment hash. That hash flows unfiltered through `TaskCommands#env` (merged after `deploy_spec.machine_env`, meaning label-derived keys can even override machine-defined vars) and finally into `Command#unbundled_env`, which is passed straight to `PTY.spawn`. An attacker who can open/label a PR on their own fork (owned by them, not privileged) fully controls the label names captured by `LabelCapturingHandler`, giving them attacker-controlled keys such as `PERL5OPT` in the environment of every command Shipit executes for that review stack, including `machine.environment` steps and any perl-invoking step in the deploy spec.

## Finding Description
The broken binding: `Stack#env` is expected to return only fixed, Shipit-controlled keys (`ENVIRONMENT`, `LAST_DEPLOYED_SHA`, `GITHUB_REPO_OWNER`, `GITHUB_REPO_NAME`, `DEPLOY_URL`, `BRANCH` — [1](#0-0) ), but `ReviewStack#env` overrides this invariant by merging attacker-controlled label names into that same hash with no key allowlist: [2](#0-1) 

Labels originate straight from the webhook payload and are persisted verbatim (just `.map(&:name)`, no filtering) by `LabelCapturingHandler#capture_labels`: [3](#0-2) 

This env hash is then merged into `TaskCommands#env` — notably **after** `deploy_spec.machine_env`, so a label-derived key overrides any machine-defined environment value of the same name: [4](#0-3) 

`Command#unbundled_env` merges `@env` (stringified) directly on top of the base/allowed env with no filtering of dangerous variable names, and this is what's handed to `PTY.spawn`: [5](#0-4) [6](#0-5) 

Existing guards do not stop this: `EnvironmentVariables#permit` (deploy_variables allowlist) is only applied via `DeploySpec#filter_deploy_envs`/`filter_rollback_envs` to `@task.env`-style deploy variables — it is never applied to `@stack.env` or `deploy_spec.machine_env` inside `TaskCommands#env`. The webhook `params` schema in `LabelCapturingHandler` validates types (`String`) but not content — any string, including `PERL5OPT`, `LD_PRELOAD`, `RUBYOPT`, `BUNDLE_GEMFILE`, etc., passes validation. `provisioning_behavior=prevent_with_label` only gates whether the review stack is *provisioned*; it does not gate what environment variables end up in the deploy commands for a stack that is already provisioned/active.

Exploit flow: An attacker opens a PR from their own fork against a repo configured with review stacks, adds a label named e.g. `perl5opt` (case-insensitive on GitHub UI, and `capture_labels` stores it verbatim; `ReviewStack#env` upcases it to `PERL5OPT`), and sets label value effectively to `"true"` (the hardcoded value — see below on limitation). The `LabeledHandler`/`LabelCapturingHandler` processes the `labeled` webhook event, persists the label onto `pull_request.labels`, and the next deploy/rollback/task run for that review stack calls `TaskCommands#env`, which calls `@stack.env` → `ReviewStack#env`, injecting `PERL5OPT=true` into the process environment used for every step, including any perl invocation performed by `machine.environment` or deploy-step scripts.

Caveat/limitation: the value assigned to any injected variable is hardcoded to the string `"true"` (`labels[label_name.upcase] = "true"`), not attacker-arbitrary. `PERL5OPT=true` is not itself a valid perl option string and would just cause perl to error on `-Mtrue`-style parsing rather than executing arbitrary code (since the value isn't `-Mattacker_module` etc.). This significantly limits the direct RCE claim as stated in the question — the attacker controls the *variable name* but not an arbitrary *value* through this specific vector, unless a subsequent step happens to read that boolean-flag-style variable in an unsafe way (e.g., an actual `if ENV['PERL5OPT']` gate in the deploy spec). Achieving `-M`/`-d` perl RCE specifically requires the attacker to control the *value* string passed to `PERL5OPT`, which this code path does not provide.

## Impact Explanation
If a deploy spec step actually inherits `PERL5OPT` (or any other sensitive env-parsed variable name, e.g. `RUBYOPT`, `NODE_OPTIONS`, `LD_PRELOAD`, `BUNDLE_GEMFILE`) and that step invokes an interpreter honoring it, an attacker-controlled boolean/string `"true"` value could still cause unexpected behavior (e.g., breaking a step, or, if the interpreter treats any nonempty value oddly, unintended option parsing) on the shared Shipit deploy host, for a stack the attacker's fork-PR maps into (via `ReviewStackAdapter`), scoped to their own review-stack/branch. This does not directly demonstrate full RCE because the value is fixed to `"true"`, not an attacker-chosen payload — the exploit for full RCE as described (arbitrary `-M`/`-d` args) is not achievable through this code path alone. The realistic, demonstrable impact is: unauthorized environment-variable name injection reaching `PTY.spawn`, capable of overriding `machine.environment`-declared variables (since it's merged after `deploy_spec.machine_env`) for the attacker's own review stack — a configuration-integrity issue rather than confirmed Critical RCE.

## Likelihood Explanation
Preconditions: the target repo must have review stacks enabled (`provisioning_behavior` gating provisioning only, not required for this env leak once a stack exists) and a shipit.yml with steps that source such an environment variable at runtime. Attacker cost is trivial — open a fork PR and add a label; no privileged role, token, or secret needed. It is fully repeatable per PR/label on any repo the attacker can fork and open PRs against, but is confined to the attacker's own review stack (their own PR's environment), not other tenants' stacks, since `ReviewStackAdapter` scopes to `repository.review_stacks` and finds/creates the stack tied to that specific PR.

## Recommendation
Apply an explicit allowlist (mirroring `EnvironmentVariables#permit` used for `deploy_variables`/`rollback_variables`) to the label-derived hash in `ReviewStack#env` before merging, rejecting or dropping names matching sensitive/interpreter-consumed environment variables (`PERL5OPT`, `RUBYOPT`, `LD_PRELOAD`, `NODE_OPTIONS`, `PATH`, `BUNDLE_*`, etc.), and change merge order in `TaskCommands#env` so `deploy_spec.machine_env` is applied last (or otherwise cannot be overridden by stack/label-derived env), so operator-declared machine environment cannot be shadowed by PR-controlled data.

## Proof of Concept
```ruby
# test/models/shipit/review_stack_test.rb (illustrative)
test "labels cannot inject sensitive env var names into TaskCommands#env" do
  stack = shipit_review_stacks(:review_stack)  # or create ReviewStack fixture
  pull_request = stack.pull_request
  pull_request.update!(labels: ["perl5opt"])

  env = stack.env
  assert_equal "true", env["PERL5OPT"], "label name is uppercased and injected verbatim into env"

  # Demonstrate it reaches Command#unbundled_env / PTY.spawn inputs
  command = Shipit::Command.new("true", env: env, chdir: Dir.tmpdir)
  assert_equal "true", command.unbundled_env["PERL5OPT"]

  # But value is NOT attacker-controlled beyond the literal string "true":
  refute_match(/^-M|-d/, env["PERL5OPT"], "value is fixed, not an attacker-chosen perl option string")
end
```
This confirms the binding break (`Stack#env` invariant of fixed-keys-only is violated by `ReviewStack#env`) and that the injected key reaches `Command#unbundled_env`, but also confirms the value is not attacker-arbitrary, so the specific "`-M`/`-d` RCE via `PERL5OPT` value" claim in the question is **not substantiated** — only unauthorized key injection (with fixed value `"true"`) is demonstrable.
