### Title
Unprivileged PR label name (e.g. `GIT_PROXY_COMMAND`) injects an arbitrary env key into `TaskCommands#env`/`Command#unbundled_env` with no allowlist, enabling RCE via `PTY.spawn` - (File: app/models/shipit/review_stack.rb, lib/shipit/task_commands.rb, lib/shipit/command.rb)

### Summary
`ReviewStack#env` takes every pull-request label name, uppercases it, and merges it as an environment-variable **key** with value `"true"`, with no allowlist of permitted names. [1](#0-0)  `LabelCapturingHandler#capture_labels` persists label names verbatim from the webhook payload onto `pull_request.labels`. [2](#0-1)  `TaskCommands#env` merges `@stack.env` into the environment used for every task, including `install_dependencies` (bundle/ruby dependency step), and `Command#unbundled_env`/`#start` merges that hash on top of `BASE_ENV` with no key restriction before calling `PTY.spawn`. [3](#0-2) [4](#0-3) 

### Finding Description
The broken binding, stated as an equality: the set of keys reaching `PTY.spawn` (`Command#unbundled_env` keys) should equal `BASE_ENV.keys ∪ {'PATH'} ∪ deploy_spec.machine_env.keys ∪ declared VariableDefinition names`. In fact it equals that set **∪ `pull_request.labels.map(&:upcase)`**, because `ReviewStack#env` does `pull_request.labels.each_with_object({}) { |label_name, labels| labels[label_name.upcase] = "true" }` with no filtering against a known/declared variable list. [1](#0-0) 

Path: an unprivileged (per the question's own attacker model) user labels their fork PR with a label literally named `git_proxy_command` (case-insensitive, since it's uppercased). GitHub emits a `pull_request` `labeled` webhook. `LabelCapturingHandler#process` validates only the shape of the payload via `ExplicitParameters` (`params.pull_request.labels` array of `{name: String}`), not the content of `name`. [5](#0-4)  It writes the label list unchanged onto the `PullRequest` record via `capture_labels`. [2](#0-1)  Existing tests confirm this exact flow is intentional and functioning: `test/models/shipit/review_stack_test.rb` and `test/lib/shipit/task_commands_test.rb` both assert that setting `stack.pull_request.labels = ["wip", "bug"]` causes `env["WIP"]` and `env["BUG"]` to equal `"true"` in `ReviewStack#env` and `TaskCommands#env` respectively. [6](#0-5) [7](#0-6)  There is no allowlist check anywhere in `ReviewStack#env`, `TaskCommands#env`, `Commands#git`, or `Command#unbundled_env`; every key survives merge-through to `PTY.spawn(unbundled_env, *interpolated_arguments, chdir: @chdir)`. [8](#0-7)  `install_dependencies` builds `Command.new(command_line, env:, chdir: steps_directory)` using this same `env` for the `bundle install` step whenever the target repo has a `Gemfile`. [9](#0-8)  Once `GIT_PROXY_COMMAND` (or `GIT_SSH_COMMAND`, etc.) is present in the child process environment, git — invoked by Shipit itself for `clone`/`checkout` (`Commands#git`) as well as by any `bundle install` that fetches a git-sourced gem — will execute the attacker-named command whenever it opens a transport connection, giving code execution on the deploy host under the Shipit worker's privileges.

None of the listed guards intercept this: `verify_signature`/`GitHubApp#verify_webhook_signature` only authenticates that the webhook truly came from GitHub for the sender's own repo — it does not validate or restrict the *content* of the `label.name` field, which GitHub happily transmits verbatim. `drop_unhandled_event` and the `ExplicitParameters` schema check types/presence, not value allowlists. `EnvironmentVariables#permit` was searched for and not found to be used anywhere in this env-merging path (it exists in `lib/shipit/environment_variables.rb` but is unrelated to filtering `ReviewStack#env` keys — no reference to it was found gating label-derived keys). No `VariableDefinition`/declared-name allowlist filters `ReviewStack#env`'s label-derived hash before merge.

### Impact Explanation
An attacker who can label a pull request on a repository that Shipit tracks as a review-stack-enabled repo can inject an arbitrary environment variable name (`GIT_PROXY_COMMAND`, `GIT_SSH_COMMAND`, `BUNDLE_GEMFILE`, `RUBYOPT`, etc., subject to label-name character constraints on GitHub) into every task/deploy/dependency-install command run against that PR's stack, up to and including code execution on the Shipit deploy host when git or bundler consults that variable. This is scoped to review stacks for the repository the attacker can label; it is repeatable on every subsequent task run for that PR/stack. This matches the Critical "RCE on the deploy host via `Command`/`PTY.spawn`" category.

### Likelihood Explanation
Preconditions: the target repository must have review-stack provisioning enabled in Shipit, and the attacker must be able to attach a label to their PR — per this question's attacker model this is treated as an unprivileged capability, though in real GitHub deployments adding labels typically requires triage/write access to the base repository (fork PR authors alone cannot label PRs by default). Assuming the question's attacker model, cost is trivial (open a PR, add one label) and fully repeatable; every task command for that review stack inherits the injected variable for as long as the label remains and the PR pipeline runs `install_dependencies`, `deploy`, or any other step through `TaskCommands`.

### Recommendation
Restrict `ReviewStack#env`'s label-derived hash to a strict allowlist of permitted variable-name patterns (e.g., require a fixed prefix like `LABEL_` or maintain an explicit allowlist of names declared safe), and additionally block any label-derived key that collides with a known dangerous/loader environment variable (`GIT_*`, `RUBYOPT`, `BUNDLE_*`, `LD_PRELOAD`, `PATH`, etc.) before merging into `Command`'s environment. Alternatively, namespace all label flags under a single prefixed key/hash structure so they can never collide with real environment variable names consumed by subprocesses.

### Proof of Concept
```ruby
# test/models/shipit/review_stack_test.rb (add)
test "#env does not allow labels to set dangerous loader/proxy env vars" do
  stack = shipit_stacks(:review_stack)
  stack.pull_request.labels = ["git_proxy_command", "wip"]

  refute stack.env.key?("GIT_PROXY_COMMAND"),
    "PR label should not be able to inject GIT_PROXY_COMMAND into the task environment"
end

# test/lib/shipit/task_commands_test.rb (add)
test "#env does not leak attacker-controlled GIT_PROXY_COMMAND into install_dependencies command env" do
  stack = shipit_stacks(:review_stack)
  stack.pull_request.labels = ["git_proxy_command"]
  task = shipit_tasks(:shipit_restart)
  task.stack = stack

  env = Shipit::TaskCommands.new(task).env
  refute env.key?("GIT_PROXY_COMMAND")

  command = Shipit::Command.new("echo test", env: env, chdir: ".")
  refute command.unbundled_env.key?("GIT_PROXY_COMMAND"),
    "Command#unbundled_env must not inherit label-injected GIT_PROXY_COMMAND before PTY.spawn"
end
```
Both assertions currently fail against the shown code (`env["GIT_PROXY_COMMAND"]` equals `"true"`), demonstrating the unfiltered merge from `ReviewStack#env` through `TaskCommands#env` into `Command#unbundled_env`.

    def start(&block)
      return if @started

      @control_block = block
      @out = @pid = nil
      FileUtils.mkdir_p(@chdir)
      begin
        @out, child_in, @pid = PTY.spawn(unbundled_env, *interpolated_arguments, chdir: @chdir)
        child_in.close
      rescue Errno::ENOENT
        raise NotFound, "#{Shellwords.split(interpolated_arguments.first).first}: command not found"
      rescue Errno::EACCES
        raise Denied, "#{Shellwords.split(interpolated_arguments.first).first}: Permission denied"
      end
      @started = true
      self
    end

    def unbundled_env
      BASE_ENV.merge('PATH' => "#{Shipit.shell_paths.join(':')}:#{ENV['PATH']}").merge(@env.stringify_keys)
    end
