### Title
Reachable assertion-crash on stable "temp-bad" input causes full node DoS - ([File: validation.js])

### Summary
`validatePaymentInputsAndOutputs()` in `validation.js` contains a hard `throw Error()` that is meant to be an unreachable invariant check, but the reachability of the `temp-bad` sequence state for a *stable* output is not fully proven safe against attacker-controlled double-spend sequencing, similar in class to the Samba dirsync crash (CVE-2019-14847), where a specially crafted, otherwise-authenticated request drives the server into an unhandled code path that terminates the process.

### Finding Description
When validating a `transfer` payment input, the code looks up the source output and, if that output's containing unit is stable in the current unit's view (`bStableInParents`), asserts that its `sequence` can never be `'temp-bad'`: [1](#0-0) 

`temp-bad` is the transient state assigned to a non-first branch of a double-spend before the double-spend outcome is finalized at stabilization; `main_chain.js` is responsible for resolving `temp-bad` sequences to either `good` or `final-bad` once the relevant units become stable. The check at line 2457-2458 assumes that by the time an output's unit is stable, `main_chain.js` has already always converted any lingering `temp-bad` sequence, so it treats survival of `temp-bad` past stabilization as impossible and crashes the process with `throw Error(...)` instead of returning a normal validation error via `cb(...)`.

This is exactly the same bug class as the Samba dirsync CVE: an attacker-reachable code path that is expected to never fire under correct sequencing logic, but if the double-spend/stabilization bookkeeping in `main_chain.js` (or its interaction with catch-up, hash-tree rebuilds, or private/AA-triggered spends) fails to update a temp-bad row before the owning unit is marked stable, *any* node that later validates a unit spending that output will hit `throw Error("spending a stable temp-bad output ...")`. Unlike the neighboring `final-bad` branch three lines below, which correctly reports the condition through the normal `cb(...)` error channel, this branch escalates to a hard `throw`.

Because `validation.validate()` is invoked from `network.js`'s `handleJoint()` for units received from ordinary peers, an uncaught exception here propagates to the global `process.on('uncaughtException', ...)` handler in `network.js`, which explicitly re-throws to crash the process: [2](#0-1) 

### Impact Explanation
If an attacker can construct (or cause, e.g. via crafted double-spend sequencing, private-payment chain replay, or AA-triggered spend interacting with `main_chain.js` stabilization) a stable output whose `sequence` remains `'temp-bad'`, then simply broadcasting (or having any node process) a further unit spending that output causes every full node that validates it to crash via the uncaught exception handler. Because this is triggered during ordinary unit validation reachable from any unprivileged unit poster, and the crash is deterministic and reproducible on every node that processes the offending unit, this can propagate network-wide and render the network unable to confirm new units — nodes need to be manually restarted, and if the poisoning condition persists in the database, they crash again immediately upon re-validating the same unit/dependents.

### Likelihood Explanation
This is a Medium-likelihood finding: it requires an as-yet-unverified sequencing defect in `main_chain.js`'s temp-bad-to-final resolution logic (which I could not fully trace to prove exploitability end-to-end within the current investigation), so I cannot demonstrate a concrete input sequence that leaves a `temp-bad` output stable. However, the code explicitly encodes this as "should never happen" via a crash rather than a graceful error, which is a clear defense-in-depth gap: even if triggered only through an edge case (e.g., interaction with catchup, hash-tree processing, or private-chain revalidation racing with stabilization), the consequence is a hard process crash rather than a rejected unit.

### Recommendation
Replace the `throw Error("spending a stable temp-bad output " + input.unit)` at validation.js:2458 with a normal validation error returned via `cb(...)`, exactly as done for the `final-bad` sequence case immediately below it. This ensures that even if the invariant is violated due to an unforeseen edge case in stabilization logic, the offending unit is simply rejected as invalid rather than crashing the validating node. Additionally, audit `main_chain.js`'s temp-bad resolution paths to confirm no code path can leave a `temp-bad` sequence on an output whose unit has become stable.

### Proof of Concept
Not reproducible from static analysis alone: exploitation depends on identifying a concrete sequence of unit submissions (e.g., overlapping double-spends combined with catch-up/hash-tree unit propagation) that leaves a stable output's `sequence` at `'temp-bad'` in `main_chain.js`'s bookkeeping. I could not confirm such a sequence exists within the scope of this review; a Devin session with full repository/test access and DB-level tracing of `main_chain.js` stabilization would be needed to construct and verify a concrete PoC.
