### Title
Cross-organization Team hijack via `github_id` collision in `MembershipHandler#find_or_create_team!` - ([File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`MembershipHandler#find_or_create_team!` looks up an existing `Team` solely by `github_id`, and `WebhooksController#verify_signature` selects the HMAC-verifying `webhook_secret` solely by `params.organization.login`/`repository_owner`, so once a `Team` row exists for ORG_A the signature check on a webhook claiming to be from ORG_B never revalidates that the `team.id` in the payload actually belongs to ORG_B. An attacker who legitimately controls ORG_B (and thus its own webhook secret) can send a genuinely-signed `membership` event whose `team.id` equals ORG_A's stored `github_id`, causing `Team.find_or_create_by!` to return ORG_A's row and `team.add_member(member)` to insert a `Membership` binding an arbitrary attacker-controlled GitHub login into ORG_A's privileged team.

### Finding Description
The broken binding: the value used to verify the webhook's authenticity, `params.organization.login` (via `repository_owner` in `app/controllers/shipit/webhooks_controller.rb:59-62` and `Shipit.github(organization: repository_owner)` in `verify_signature`, lines 24-30), is never checked to equal the `organization` column already persisted on the `Team` row selected by `github_id` in `find_or_create_team!`:

```ruby
def find_or_create_team!
  Team.find_or_create_by!(github_id: params.team.id) do |team|
    team.github_team = params.team
    team.organization = params.organization.login
  end
end
``` [1](#0-0) 

`find_or_create_by!` only sets `team.organization` in the creation block, which is skipped entirely when a row with that `github_id` already exists — the existing record's `organization` (ORG_A's) is returned unchanged and unchecked. `process` then unconditionally calls `team.add_member(member)` on whatever `Team` was returned:

```ruby
def process
  team = find_or_create_team!
  member = User.find_or_create_by_login!(params.member.login)
  case params.action
  when 'added'
    team.add_member(member)
``` [2](#0-1) 

Meanwhile the signature verification path resolves the verifying app purely from the envelope's organization field:

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(...)
  ...
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [3](#0-2) 

For `membership` events there is no `repository` key, so `repository_owner` resolves to `params.organization.login` — i.e., ORG_B's own login, verified with ORG_B's own genuine `webhook_secret`. This proves only that ORG_B sent the envelope, not that `team.id` inside belongs to ORG_B. Nothing downstream re-derives or re-checks `team.organization` against the verified `repository_owner`/`organization.login` before mutating the team.

Exploit flow: attacker (owner of ORG_B, with a Shipit GitHub App configured for ORG_B) sends a real `membership` webhook to `POST /webhooks` with `organization.login: "attacker-org"`, `team.id` equal to ORG_A's stored `github_id` (team IDs are public/discoverable via GitHub API), `member.login` of their choosing, `action: "added"`. It is correctly signed with ORG_B's secret, passes `verify_signature`, and `find_or_create_team!` returns ORG_A's `Team` record because it matches on `github_id` alone, adding the attacker-chosen member to ORG_A's team.

None of the existing guards (`drop_unhandled_event`, `verify_signature`, the `ExplicitParameters` schema) check organization ownership of the matched `Team` row; the schema only validates presence/types of `team.id`, `organization.login`, `member.login`, not their consistency with stored data.

### Impact Explanation
A cross-tenant write: ORG_B's genuinely-signed webhook creates a `Membership` row linking an attacker-controlled GitHub user to ORG_A's `Team`, which feeds `User#authorized?`/`Shipit.github_teams` checks used for stack/deploy permissions in the host app. This is a privileged-team-membership escalation reachable by any organization owner without needing ORG_A's secrets, matching the "escalation into `Shipit.github_teams` authorization" / cross-tenant mutation category. It is repeatable against any `Team` whose `github_id` an attacker can guess or enumerate (GitHub team IDs are sequential/discoverable), and works for any ORG_A configured in Shipit.

### Likelihood Explanation
Requires: Shipit configured multi-tenant with GitHub Apps for both a privileged org (ORG_A) and an attacker-controlled org (ORG_B); ORG_A must already have at least one `Team` row (created from a prior legitimate webhook or admin action) so the `github_id` collision path (existing-record branch) is hit. Attacker cost is low — they only need to own/administer any GitHub organization enrolled in Shipit and know/guess a target team's numeric `github_id`. No Shipit secrets, sessions, or maintainer status needed, satisfying the attacker model.

### Recommendation
In `find_or_create_team!`, after fetching/creating the `Team`, verify `team.organization == params.organization.login` (i.e., bind the stored `organization` to the value used for signature verification) and reject/raise (or scope the lookup by both `github_id` and `organization`) if they diverge, e.g. `Team.find_or_create_by!(github_id: params.team.id, organization: params.organization.login)` combined with reconciling any pre-existing mismatched row explicitly rather than silently reusing it.

### Proof of Concept
minitest (`test/models/webhooks/handlers/membership_handler_test.rb` style, no live GitHub):
1. Create `shipit_teams(:shopify_developers)` fixture/record with `github_id: 100, organization: 'shopify'`.
2. Stub `Shipit.github(organization: 'attacker-org')` so `verify_webhook_signature` returns `true` (simulating ORG_B's genuine secret).
3. POST to `/webhooks` with header `X-Github-Event: membership`, body: `{"action":"added","team":{"id":100,"name":"x","slug":"x","url":"x"},"organization":{"login":"attacker-org"},"member":{"login":"attacker"}}`.
4. Assert response is `200`/`204` (not `422`), confirming the equality `repository_owner == "attacker-org"` was verified against ORG_B's secret only.
5. Assert `Shipit::Team.find_by(github_id: 100).organization == "shopify"` (unchanged — still bound to ORG_A) while `Shipit::Membership.exists?(team: shipit_teams(:shopify_developers), user: Shipit::User.find_by(login: 'attacker'))` is `true`, proving ORG_B's signed webhook mutated ORG_A's team membership despite `team.organization` ("shopify") ≠ `params.organization.login` ("attacker-org").

        "status=#{status}"
      ].join(' '))
    end
