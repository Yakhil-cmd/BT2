### Title
Credential Disclosure to Attacker-Controlled Hosts via Unrestricted Submodule URLs - (File: main.go)

### Summary
`git-sync` trusts arbitrary submodule URLs found in the *content* of the synced repository (the `.gitmodules` file, which any committer/attacker who can push to the tracked ref controls) and blindly executes `git submodule update --init --recursive` against them, using whatever credentials git-sync has configured for the main `--repo`. This is the same bug class as the reported finding: a downstream operation (fetching/authenticating) is driven by an address/URL that comes from untrusted, attacker-influenced content, with no allow-list or validation against the set of "known-good" endpoints the operator actually intended to trust.

### Finding Description
`repoSync.configureWorktree` unconditionally runs submodule updates once a worktree is checked out: [1](#0-0) 

The `submodulesArgs` passed to `git.Run` are `submodule update --init [--recursive] [--depth N]` — there is no restriction on which URLs those submodules may point to. The submodule URLs are read from `.gitmodules`, which lives in the tracked repository content and can be changed by anyone who can push a commit that git-sync will sync (a compromised upstream contributor, a malicious PR that gets merged, etc.). No code path in `main.go` sets `protocol.allow`, `GIT_ALLOW_PROTOCOL`, or otherwise constrains which hosts/protocols submodules are permitted to use before invoking `git submodule update`.

Meanwhile, git-sync's credential machinery pre-loads credentials into the git credential store keyed by URL, intended for the main repo (and, per the docs, explicitly extended to also cover submodules): [2](#0-1) [3](#0-2) 

Because `git credential` matching is normally scoped by protocol+host (not full path, unless `useHttpPath` is set), any submodule URL whose host matches a host for which git-sync has stored credentials (e.g., an internal Git server, or a broad credential entry) will cause git to present those credentials when fetching that submodule — even though the specific submodule path was chosen entirely by the attacker via the tracked repo's `.gitmodules` file. This is analogous to the audited bug: the "source" (here, the submodule fetch target) is attacker-controlled data that is never validated against a known-good allow-list (analogous to the missing `VaultFactory.deployedVaults` check), yet the privileged action (credential presentation / outbound fetch) is performed against it anyway.

### Impact Explanation
An attacker who can influence the content of the synced ref (e.g., a merged malicious PR, a compromised co-maintainer, or a supply-chain commit) can add or modify a submodule entry to point at an attacker-controlled endpoint sharing a host that git-sync has stored credentials for (or any host, for pure SSRF/outbound-request purposes). This can result in:
- Disclosure of git-sync's configured HTTP(S) Basic Auth credentials, askpass-supplied tokens, or GitHub App installation tokens to an attacker-controlled path if it shares a matching host/protocol scope.
- Outbound requests (SSRF) from the git-sync sidecar to arbitrary internal or external hosts chosen by the untrusted repo content.
- Publishing of unexpected/attacker-chosen content into the published symlink tree (since submodule content becomes part of what's exposed at `--link`), i.e., "publishing wrong or partial content."

### Likelihood Explanation
Requires `--submodules` to not be `off` (the default is `recursive`, per `flSubmodules` default) and requires the attacker to have some ability to introduce/modify `.gitmodules` in the tracked ref — a realistic scenario for any git-sync deployment tracking a repo with multiple contributors, bot-driven merges, or dependency-style submodule references. No git-sync misconfiguration beyond default settings is needed; this is reachable via a normal attacker-pushed commit that changes `.gitmodules`.

### Recommendation
- Add a flag to restrict submodule URLs to an explicit allow-list of hosts/protocols (or default to disabling cross-host submodule fetches), analogous to validating `_source` against `deployedVaults` in the original report.
- Scope stored credentials as tightly as possible (enable `useHttpPath` / bind credentials to specific paths, not just host) so that submodule URLs on the same host cannot silently reuse credentials meant for the primary repo.
- Consider setting `protocol.allow`/`GIT_ALLOW_PROTOCOL` explicitly rather than relying on git's own defaults, and document/enforce this in git-sync's submodule handling.

### Proof of Concept
1. Deploy git-sync with `--repo=https://git.example.com/org/main-repo` and a stored credential (`--username`/`--password-file` or `--credential`) scoped to `https://git.example.com`.
2. As an attacker with push/merge access to `main-repo` (or via a malicious contribution that gets merged), add to `.gitmodules`:
   ```
   [submodule "evil"]
       path = evil
       url = https://git.example.com/attacker/evil-repo
   ```
3. On next sync, `configureWorktree` (main.go:1733-1747) runs `git submodule update --init --recursive`, and git presents the stored `git.example.com` credentials while fetching `attacker/evil-repo`, which the attacker controls and can log/inspect the authentication attempt, or use the credentials for further reconnaissance/impersonation on that host.

Note: I could not fully verify from the indexed code alone whether the underlying `git` binary invoked here is configured anywhere (outside of `main.go`) with stricter credential-path scoping or protocol allow-lists; this would need confirmation via a live/full-repo review (e.g., a Devin session) since the index may not include all configuration files.

```go
// StoreCredentials stores a username and password for later use.
func (git *repoSync) StoreCredentials(ctx context.Context, url, username, password string) error {
	git.log.V(1).Info("storing git credential", "url", redactURL(url))
	git.log.V(9).Info("md5 of credential", "url", url, "username", md5sum(username), "password", md5sum(password))

	creds := fmt.Sprintf("url=%v\nusername=%v\npassword=%v\n", url, username, password)
	_, _, err := git.RunWithStdin(ctx, "", creds, "credential", "approve")
	if err != nil {
		return fmt.Errorf("can't configure git credentials: %w", err)
	}

	return nil
}
```
