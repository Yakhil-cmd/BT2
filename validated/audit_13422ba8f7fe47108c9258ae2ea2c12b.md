### Title
Cross-organization commit-status forgery via payload-controlled webhook signature routing — ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the `GitHubApp`/`webhook_secret` used to validate an inbound webhook's HMAC based on `repository_owner`, a value read directly from the unverified JSON body, not from any authenticated source tied to the request. [1](#0-0)  Once the signature check passes, `Shipit::Webhooks::Handlers::StatusHandler#process` applies the status update to *every* `Commit` in the entire installation matching `params.sha`, with no check that the commit's stack/repository belongs to the organization that was used to validate the signature. [2](#0-1) 

### Finding Description
This mirrors the report's bug class: a verification check is bound to one identity/field, while the privileged action is actually performed against a different, uncontrolled field from the same untrusted payload — the "policyCenter" check verified `msg.sender` but the pool/token/amount fields it authorized were fully attacker-controlled.

Here the equality that should hold is:
`organization whose secret validated the signature == organization owning the repository/commit that is mutated`

Before the attacker's request: for a webhook genuinely from GitHub, `repository.owner.login` in the payload and the repository actually referenced always belong to the same GitHub organization, so this equality holds implicitly.

`Shipit.github(organization: repository_owner)` picks the `GitHubApp` (and thus `webhook_secret`) purely from `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`, both attacker-writable JSON fields inside the same body whose HMAC is being checked. [3](#0-2)  `Shipit.github` resolves this organization key against the multi-org `github:` config block documented for multi-tenant installs. [4](#0-3) [5](#0-4) 

For the `status` event, the handler that then runs never re-derives or re-checks the repository/organization: it looks up commits globally by `sha` across the whole Shipit instance and writes a GitHub-supplied status onto them. [6](#0-5)  Unlike other handlers (`PushHandler`, `PullRequest::*Handler`, `CheckSuiteHandler`) which scope their `stacks` lookup by `repository_name` derived from `payload.dig('repository', 'full_name')`, [7](#0-6)  `StatusHandler` has no such scoping.

After the attacker's request: an attacker who administers **any one** GitHub organization/App configured on a multi-tenant Shipit instance (and therefore legitimately knows that org's own `webhook_secret`, which they set themselves when creating their own GitHub App) can craft and self-sign a `status` webhook whose `repository.owner.login` is set to their own org (so `verify_webhook_signature` succeeds using their own known secret), while `sha` is set to a real commit SHA belonging to a stack owned by a completely different tenant organization on the same Shipit instance. `StatusHandler` will then apply a forged `state` (e.g. `"success"`) to that victim commit, because the lookup `Commit.where(sha: params.sha)` is not scoped to any repository or organization at all.

### Impact Explanation
This is an authentication-bypass-class issue: the org that authenticated the request is not the org whose data is written, letting a low-privileged actor (any org owner able to create a GitHub App with a webhook secret they control) forge status for arbitrary commits in unrelated, victim-owned stacks tracked by the same shared Shipit instance. Since commit/CI status is one of the signals Shipit surfaces for a commit's deployability, this lets an attacker mark an untested or malicious commit as passing status checks it never actually passed in a repository they do not own — a cross-tenant integrity violation that can facilitate an unauthorized deploy decision on unrelated stacks, matching the "High" bucket (escalation of authorization boundary / unauthenticated write of stack state across tenants).

### Likelihood Explanation
Exploitability is limited to multi-organization Shipit deployments (the `github:` per-org config schema), and requires the attacker to control a GitHub App/webhook secret for at least one of the organizations onboarded to that shared instance — a scenario the docs explicitly support ("Using Multiple Github Applications"). [5](#0-4)  No repository write access, Shipit session, or `ApiClient` token is required — only knowledge of a webhook secret the attacker legitimately possesses for their own onboarded org, plus the target commit SHA (visible via GitHub itself). This is a realistic misuse for shared/multi-tenant Shipit installs.

### Recommendation
In `WebhooksController#verify_signature`/`repository_owner`, and in every handler, derive the organization/repository used for both signature verification and state mutation from the same trusted binding, and enforce that they match. Specifically:
- Scope `StatusHandler#process` (and any other handler that queries records without a repository filter) to `stacks`/`Repository.from_github_repo_name(repository_name)` the same way `PushHandler` and the `PullRequest` handlers already do, rather than a bare global `Commit.where(sha: ...)`.
- After selecting the `GitHubApp` for verification via `repository_owner`, re-validate that the resolved repository's owner literally equals `repository_owner` before allowing any handler to run, closing the gap between the identity used to authenticate and the entity being mutated.

### Proof of Concept
1. Operate a multi-tenant Shipit instance configured with two GitHub orgs, `AttackerOrg` and `VictimOrg`, per the documented multi-app `github:` schema.
2. As the owner of `AttackerOrg`, create (or already possess) a GitHub App with a known `webhook_secret` for `AttackerOrg`.
3. Identify a commit SHA `S` belonging to a stack tracked under `VictimOrg` (visible via GitHub's public/private API for that repo, or Shipit's UI if the attacker has any read access).
4. Craft a `status` event JSON body:
   ```json
   {
     "sha": "S",
     "state": "success",
     "context": "ci/forged",
     "repository": { "owner": { "login": "AttackerOrg" }, "full_name": "AttackerOrg/some-repo" }
   }
   ```
5. Compute `X-Hub-Signature: sha1=HMAC_SHA1(AttackerOrg_webhook_secret, body)` and POST it to `/webhooks` with `X-Github-Event: status`.
6. `verify_signature` resolves `Shipit.github(organization: "AttackerOrg")` and validates successfully using the attacker's own known secret. [8](#0-7) 
7. `StatusHandler#process` runs `Commit.where(sha: "S").each { |commit| commit.create_status_from_github!(params) }`, applying the forged `"success"` status to the `VictimOrg` commit despite the request never being authenticated as `VictimOrg`. [2](#0-1)

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping
      head(:ok) if event == 'ping'
    end

    def event
      request.headers.fetch('X-Github-Event')
    end

    def repository_owner
      # Fallback to the organization sub-object if repository isn't included in the payload
      params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
    end

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
