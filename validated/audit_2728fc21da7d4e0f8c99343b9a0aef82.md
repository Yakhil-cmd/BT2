### Title
Bridged Assets Permanently Locked/Burned When Destination `_to` Rejects Transfer in `handleKLAYTransfer` / `handleERC20Transfer` — (`contracts/service_chain/bridge/BridgeTransferKLAY.sol`, `contracts/service_chain/bridge/BridgeTransferERC20.sol`)

---

### Summary

The Kaia service-chain bridge contracts `BridgeTransferKLAY` and `BridgeTransferERC20` perform the actual asset delivery to `_to` **after** all nonce/vote state has been committed within the same transaction. If the delivery call fails (e.g., `_to` is a contract that rejects KLAY, or a token with a blacklist rejects the mint/transfer), the entire transaction reverts. While this prevents nonce consumption in that single call, it creates a permanent deadlock: the source-chain assets (KLAY locked in the bridge, or ERC20 burned in mint/burn mode) can never be recovered because the protocol has no on-chain mechanism to redirect the transfer or refund the original sender, and the VT recovery system will retry indefinitely with the same failing parameters.

---

### Finding Description

**`BridgeTransferKLAY.sol` — `handleKLAYTransfer`:**

```
_lowerHandleNonceCheck(...)          // 1. nonce guard
_voteValueTransfer(...)              // 2. closes vote, sets closedValueTransferVotes[nonce]=true
_setHandledRequestTxHash(...)        // 3. marks tx hash handled
handleNoncesToBlockNums[nonce] = ... // 4. records block number
_updateHandleNonce(...)              // 5. advances lowerHandleNonce

emit HandleValueTransfer(...)        // 6. event

(bool ok,) = _to.call.value(_value)(""); // 7. KLAY delivery
require(ok, "handleKLAYTransfer: transfer failed"); // 8. REVERTS entire tx if ok==false
```

If step 7 returns `ok = false` (e.g., `_to` is a contract with no payable fallback, or one that explicitly reverts), step 8 reverts the entire transaction, rolling back steps 2–5. The nonce is not consumed in that call, but the source-chain KLAY is already locked inside the source bridge contract with no refund path. [1](#0-0) 

**`BridgeTransferERC20.sol` — `handleERC20Transfer` (mint/burn mode):**

```solidity
if (modeMintBurn) {
    require(ERC20Mintable(_tokenAddress).mint(_to, _value), "handleERC20Transfer: mint failed");
} else {
    IERC20(_tokenAddress).safeTransfer(_to, _value);
}
```

In mint/burn mode, the source-chain tokens are **burned** in `_requestERC20Transfer` before the `RequestValueTransfer` event is emitted. On the destination side, if `mint(_to, _value)` returns `false` (e.g., `_to` is blacklisted in a USDC-style token contract), `require(false, ...)` reverts the entire `handleERC20Transfer` transaction. The burned tokens are permanently destroyed with no recovery path. [2](#0-1) [3](#0-2) 

**Why recovery is impossible:**

The VT recovery system (`vt_recovery.go`) detects unhandled nonces and resubmits the original `handleXxxTransfer` call with the **same parameters** (same `_to`). Since `_to` permanently rejects the transfer, every retry fails. There is no on-chain function to redirect the transfer to a different address or refund the original sender on the source chain. [4](#0-3) [5](#0-4) 

The `_voteValueTransfer` vote key is `keccak256(msg.data)`, which includes `_to`. Operators cannot change `_to` without creating a new, separate vote for the same nonce — this is not a standard protocol operation and is not supported by the automated bridge relay. [6](#0-5) 

---

### Impact Explanation

- **ERC20 mint/burn mode**: Tokens are burned on the source chain before the `RequestValueTransfer` event. If `mint(_to, _value)` permanently fails on the destination, the burned tokens are irrecoverable — total supply is reduced with no corresponding credit.
- **KLAY / ERC20 lock/unlock mode**: Assets are locked in the source bridge. If `handleKLAYTransfer` or `handleERC20Transfer` permanently fails, the locked assets can never be released or refunded.
- In both cases, the `lowerHandleNonce` never advances past the stuck nonce, which also blocks the VT recovery window from progressing for all subsequent nonces.

**Impact: High** — permanent loss or permanent lock of bridged KAIA/ERC20 assets.

---

### Likelihood Explanation

- Any user who bridges to a contract address that has no payable fallback (KLAY case) triggers this immediately.
- For ERC20 with blacklists (e.g., USDC, USDT bridged via the service chain), an address that is blacklisted after the `RequestValueTransfer` event is emitted but before `handleERC20Transfer` is executed triggers this.
- The service chain bridge is a production component used for cross-chain value transfer; both scenarios are realistic.

**Likelihood: Medium**

---

### Recommendation

1. **`handleKLAYTransfer`**: Replace `require(ok, ...)` with a graceful failure path. If `ok == false`, store `(nonce → value, _from, _to)` in a recovery mapping instead of reverting. Add an owner/operator function to redirect or refund stuck transfers.

2. **`handleERC20Transfer`**: Solidity 0.5.6 does not support `try/catch`. Use a low-level `call` to invoke `mint`/`transfer` and check the return value without reverting. On failure, store the amount in a recovery mapping.

3. **Source-side guard**: Before burning/locking on the source chain, verify that `_to` is not a known-rejecting address (e.g., check it is not a contract with no payable fallback for KLAY transfers).

4. **VT recovery**: Extend the recovery system to detect permanently failing nonces and surface them for manual operator intervention with an alternative `_to`.

---

### Proof of Concept

**KLAY scenario:**

1. Alice deploys a contract `Rejector` on the destination chain with no payable fallback.
2. Alice calls `requestKLAYTransfer(Rejector, 1000e18, "")` on the source bridge, sending 1000 KLAY. The source bridge holds 1000 KLAY.
3. Bridge operators call `handleKLAYTransfer(..., Rejector, 1000e18, nonce=N, ...)` on the destination bridge.
4. Steps 2–5 of `handleKLAYTransfer` execute (nonce state committed).
5. `Rejector.call.value(1000e18)("")` returns `ok = false`.
6. `require(ok, ...)` reverts the entire transaction — all state changes rolled back.
7. VT recovery retries step 3 indefinitely; every attempt reverts at step 5.
8. Alice's 1000 KLAY is permanently locked in the source bridge.

**ERC20 mint/burn scenario:**

1. Alice calls `requestERC20Transfer(token, Bob, 1000e6, ...)` on the source bridge (mint/burn mode). `token.burn(1000e6)` executes — tokens destroyed.
2. Before operators relay the transfer, Bob is blacklisted in the `token` contract on the destination chain.
3. Operators call `handleERC20Transfer(..., Bob, token, 1000e6, nonce=N, ...)`.
4. `ERC20Mintable(token).mint(Bob, 1000e6)` returns `false` (blacklisted).
5. `require(false, "handleERC20Transfer: mint failed")` reverts the entire transaction.
6. VT recovery retries indefinitely; every attempt reverts.
7. 1000e6 tokens are permanently burned with no credit issued anywhere. [7](#0-6) [8](#0-7)

	}

// handleRequestValueTransferEvent handles the given request value transfer event.
func (bi *BridgeInfo) handleRequestValueTransferEvent(ev IRequestValueTransferEvent) error {
	var (
		tokenType                         = ev.GetTokenType()
		tokenAddr, from, to, contractAddr = ev.GetTokenAddress(), ev.GetFrom(), ev.GetTo(), ev.GetRaw().Address
		txHash                            = ev.GetRaw().TxHash
		valueOrTokenId                    = ev.GetValueOrTokenId()
		requestNonce, blkNumber           = ev.GetRequestNonce(), ev.GetRaw().BlockNumber
		extraData                         = ev.GetExtraData()
	)

	ctpartTokenAddr := bi.GetCounterPartToken(tokenAddr)
	// TODO-Kaia-Servicechain Add counterpart token address in requestValueTransferEvent
	if tokenType != KAIA && ctpartTokenAddr == (common.Address{}) {
		logger.Warn("Unregistered counter part token address.", "addr", ctpartTokenAddr.Hex())
		ctTokenAddr, err := bi.counterpartBridge.RegisteredTokens(nil, tokenAddr)
		if err != nil {
			return err
		}
		if ctTokenAddr == (common.Address{}) {
			return errors.New("can't get counterpart token from bridge")
		}
		if err := bi.RegisterToken(tokenAddr, ctTokenAddr); err != nil {
			return err
		}
		ctpartTokenAddr = ctTokenAddr
		logger.Info("Register counter part token address.", "addr", ctpartTokenAddr.Hex(), "cpAddr", ctTokenAddr.Hex())
	}

	bridgeAcc := bi.account

	bridgeAcc.Lock()
	defer bridgeAcc.UnLock()

	auth := bridgeAcc.GenerateTransactOpts()

	var handleTx *types.Transaction
	var err error

	switch tokenType {
	case KAIA:
		handleTx, err = bi.bridge.HandleKLAYTransfer(auth, txHash, from, to, valueOrTokenId, requestNonce, blkNumber, extraData)
		if err != nil {
			return err
		}
		handleValueTransferLog(bi.onChildChain, handleVTmethods[KAIA], handleTx.Hash().String(), requestNonce, from, to, valueOrTokenId)
	case ERC20:
		handleTx, err = bi.bridge.HandleERC20Transfer(auth, txHash, from, to, ctpartTokenAddr, valueOrTokenId, requestNonce, blkNumber, extraData)
		if err != nil {
			return err
		}
		handleValueTransferLog(bi.onChildChain, handleVTmethods[ERC20], handleTx.Hash().String(), requestNonce, from, to, valueOrTokenId)
	case ERC721:
		uri := GetURI(ev)
		handleTx, err = bi.bridge.HandleERC721Transfer(auth, txHash, from, to, ctpartTokenAddr, valueOrTokenId, requestNonce, blkNumber, uri, extraData)
		if err != nil {
			return err
		}
		handleValueTransferLog(bi.onChildChain, handleVTmethods[ERC721], handleTx.Hash().String(), requestNonce, from, to, valueOrTokenId)
	default:
		logger.Error("Got Unknown Token Type ReceivedEvent", "bridge", contractAddr, "nonce", requestNonce, "from", from)
		return nil
	}

	bridgeAcc.IncNonce()

	bi.bridgeDB.WriteHandleTxHashFromRequestTxHash(txHash, handleTx.Hash())
	return nil
}

    function _voteValueTransfer(uint64 _requestNonce)
        internal
        returns(bool)
    {
        require(!closedValueTransferVotes[_requestNonce], "closed vote");

        bytes32 voteKey = keccak256(msg.data);
        if (_voteCommon(VoteType.ValueTransfer, _requestNonce, voteKey)) {
            closedValueTransferVotes[_requestNonce] = true;
            return true;
        }

        return false;
    }
