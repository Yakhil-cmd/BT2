### Title
Second-preimage / node-as-leaf ambiguity in `merkle.js` allows forged Merkle inclusion proofs, bypassing `in merkle` address-definition and `is_valid_merkle_proof` AA conditions - (File: merkle.js)

### Summary
`merkle.js` builds leaf hashes and internal-node hashes with the exact same function and no domain separation: a leaf is `hash(element)` and an internal node is `hash(childHash_left + childHash_right)` [1](#0-0) [2](#0-1) . Because both are plain SHA-256 over a string with no leaf/node tag, anyone who knows two sibling hashes at any level of the tree can set a forged "element" equal to the raw concatenation of those two hashes and produce a proof that verifies successfully against the true, honestly-computed root, even though that string was never part of the original data set. This is the classic CVE-2012-2459-class "same tree, different leaf" attack, and it is directly reachable through the `in merkle` address-definition operator and the `is_valid_merkle_proof` oscript function.

### Finding Description
`getMerkleRoot`/`getMerkleProof` hash leaves as `hash(element)` and internal nodes as `hash(arrHashes[i] + arrHashes[hash2_index])` [3](#0-2) . `verifyMerkleProof` reconstructs the root the same way, starting from `hash(element)` and repeatedly concatenating with siblings [4](#0-3) ; the code even contains the author's own comment flagging this: `// Node-as-Leaf issue might matter in some cases`.

Because leaves and internal nodes are hashed identically, if an attacker knows two sibling hash strings `h1` and `h2` at any internal node of a legitimately-published tree (revealed to anyone who requests a normal proof, since siblings are public data), they can:
1. Set `forged_element = h1 + h2` (the raw 88-character base64 concatenation).
2. Build a proof whose `siblings` array is exactly the remaining path from that internal node up to the root, with the appropriate `index`.
3. Call `verifyMerkleProof(forged_element, forged_proof)`, which computes `hash(forged_element) = hash(h1+h2)`, i.e., exactly the real internal-node hash, and continues up the authentic path — verification succeeds against the true root, without ever needing cooperation from the tree's original publisher.

This directly maps to the report's bug class: a proof mechanism admits nodes that were never legitimate "leaves" of the tree but are still accepted by the verifier as if they were, because the hashing scheme is not injective/domain-separated between node types (the report's own remediation — "ensure commitments and message encodings are injective," "use unique prefixes" — is precisely what's missing here).

Two concrete consumers of this primitive in ocore are attacker-reachable without any privilege:
- `in merkle` address-definition operator, used to gate authentication of an address on membership in an oracle-published Merkle root: it deserializes an attacker-supplied proof and directly calls `merkle.verifyMerkleProof(element, proof)` before checking the recovered root against the data feed [5](#0-4) . Any string satisfying the definition-time regex `/^[\w ~,.\/\\;:!@#$%^&*\(\)=+\[\]\{\}<>\?|-]{1,100}$/` is accepted as a valid `element` [6](#0-5) ; that regex explicitly whitelists `+`, `/`, `=`, `\w` — i.e., the full base64 alphabet — so an 88-character concatenation of two base64 SHA-256 hashes passes trivially.
- `is_valid_merkle_proof(element, proof)` in AA oscript, reachable directly from any AA trigger sender's `trigger.data`, with no format restriction on `element` at all beyond being a non-empty string [7](#0-6) .

### Impact Explanation
Any address, definition-template, or AA that relies on `in merkle`/`is_valid_merkle_proof` to gate authentication or fund release based on membership in a Merkle-committed set (e.g., a whitelist/allowlist condition combined with other authentifiers to authorize spending from a shared address, or an AA that checks a claimant/commitment against a stored root) can be bypassed: an attacker can produce a syntactically valid `(element, proof)` pair that verifies against the legitimate, honestly-computed root without that element ever having been part of the original committed data set. Where such a condition contributes to spending authorization (`in merkle` inside an `and`/`or` address definition) or to state transitions inside an AA (fund release, whitelist gating, double-claim prevention keyed on the "element" value), this can lead to unauthorized signing/spending or bypass of intended set-membership restrictions — matching the "unauthorized spending" / "AA fund loss" impact classes.

### Likelihood Explanation
The attacker only needs to observe the sibling-hash values of a real, previously-published Merkle proof — public information any party can obtain, since revealing siblings is the entire point of a Merkle proof. No cryptographic primitive is broken (this is a structural/domain-separation flaw, not a hash break) and both entry points (`in merkle` in `definition.js`, `is_valid_merkle_proof` in `formula/evaluation.js`) are reachable by ordinary unprivileged unit posters / AA trigger senders. The main constraint on real-world exploitability is that the forged "element" is not freely chosen content but a fixed 88-character base64-hash-concatenation string, limiting scenarios to those where a definition or AA only checks set membership of an opaque token/commitment rather than requiring the recovered content to encode meaningful spend parameters (address/amount) that the attacker also controls.

### Recommendation
- Add domain separation in `merkle.js`: hash leaves as `hash(0x00 + element)` and internal nodes as `hash(0x01 + left + right)` (or an equivalent unique-prefix scheme), and reject any leaf whose byte length/structure could pass for the internal-node encoding.
- Alternatively/additionally, in `verifyMerkleProof`, add an explicit invariant that rejects claimed leaves whose value matches the exact concatenation pattern of two hash-length strings, or reduce the accepted proof-length/element format to make second-preimage collisions with internal nodes cryptographically distinguishable.
- Audit and tighten the `in merkle` element regex in `definition.js` to reject values shaped like raw hash concatenations, and document/require that any `is_valid_merkle_proof` consumer treat the recovered element as untrusted until it round-trips through domain-appropriate parsing/validation.

### Proof of Concept
1. Oracle publishes (as a `data_feed` message) a Merkle root `R` over a legitimate list of elements `[e0, e1, ..., en]` using `merkle.getMerkleRoot` [3](#0-2) .
2. Attacker requests (or otherwise obtains) a normal proof for any element `ei`, e.g. via `merkle.getMerkleProof(arrElements, i)` [2](#0-1) , which reveals the sibling hash chain, including two adjacent leaf hashes `h1 = hash(ea)`, `h2 = hash(eb)` combined into an internal node at some level.
3. Attacker sets `forged_element = h1 + h2` and constructs `forged_proof = { root: R, index: <parent index>, siblings: <remaining siblings from that internal node up to R> }`.
4. Attacker calls `merkle.verifyMerkleProof(forged_element, forged_proof)` — this returns `true` because `hash(forged_element) === hash(h1+h2)`, exactly the true internal node hash, and the rest of the path to `R` is authentic [4](#0-3) .
5. Attacker submits `forged_element`/serialized `forged_proof` as the authentifier for an `in merkle` condition in an address definition [5](#0-4)  (the 88-char base64 string passes the format regex at [6](#0-5) ), or as `trigger.data.element`/`trigger.data.proof` to an AA calling `is_valid_merkle_proof` [7](#0-6) . Both accept the forged pair as proof of "membership" in the set committed to root `R`, despite `forged_element` never being one of `[e0...en]`.

	var arrHashes = arrElements.map(hash);

		var arrOverHashes = []; // hashes over hashes

		arrHashes = arrOverHashes;

}

function getMerkleProof(arrElements, element_index){
	if (element_index < 0 || element_index >= arrElements.length)
		throw Error("invalid index");
	var arrHashes = arrElements.map(hash);
	var index = element_index;
	var arrSiblings = [];
	while (arrHashes.length > 1){
		var arrOverHashes = []; // hashes over hashes
		var overIndex = null;
		for (var i=0; i<arrHashes.length; i+=2){
			var hash2_index = (i+1 < arrHashes.length) ? (i+1) : i; // for odd number of hashes
			if (i === index){
				arrSiblings.push(arrHashes[hash2_index]);
				overIndex = i/2;
			}
			else if (hash2_index === index){
				arrSiblings.push(arrHashes[i]);
				overIndex = i/2;
			}
			arrOverHashes.push(hash(arrHashes[i] + arrHashes[hash2_index]));
		}
		arrHashes = arrOverHashes;
		if (overIndex === null)
			throw Error("overIndex not defined");
		index = overIndex;
	}
	// add merkle root
	//arrSiblings.push(arrHashes[0]);
	return {
		root: arrHashes[0],
		siblings: arrSiblings,
		index: element_index
	};
}

function verifyMerkleProof(element, proof){
	// Node-as-Leaf issue might matter in some cases
	try {
		var index = proof.index;
		var the_other_sibling = hash(element);
		for (var i = 0; i < proof.siblings.length; i++) {
			// this also works for duplicated trailing nodes
			if (index % 2 === 0)
				the_other_sibling = hash(the_other_sibling + proof.siblings[i]);
			else
				the_other_sibling = hash(proof.siblings[i] + the_other_sibling);
			index = Math.floor(index / 2);
		}
		return (the_other_sibling === proof.root);
	}
	catch (e){
		return false;
	}
}
