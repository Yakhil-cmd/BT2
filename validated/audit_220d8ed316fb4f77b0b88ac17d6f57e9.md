## Title
Stale OP Votes for Disqualified Addresses Remain Counted, and the Elected op_list Is Never Re-Validated for Eligibility - (File: `main_chain.js`, `validation.js`)

### Summary
The reported bug class — votes cast for an entity that later becomes disqualified remain locked in and cannot be excluded or reallocated — has a direct analog in ocore's `op_list` system-vote mechanism. Eligibility of a candidate OP (not an AA, known/good/stable, no references in its address definition) is checked only once, at the moment the `system_vote` unit naming it is validated. That same eligibility is never re-checked either when votes are tallied at `countVotes()` (`main_chain.js`) or when the resulting `op_list` is actually enforced as the network witness list in `validateWitnesses()` (`validation.js`). Because vote tallying windows can span multiple years, an address's eligibility can change between the moment it is voted for and the moment the vote is counted, with no mechanism to exclude the stale vote or reassign it, mirroring the underlying "votes for cancelled protocols are lost" bug class.

### Finding Description
`system_vote` for subject `op_list` is only checked for candidate eligibility at message-validation time: [1](#0-0) 

That check calls `checkNotAAs`, `checkWitnessesKnownAndGood`, and `checkNoReferencesInWitnessAddressDefinitions` — but only against the address's state at `objValidationState.last_ball_mci` at the time the vote unit is posted: [2](#0-1) [3](#0-2) 

Votes are stored per-voter in `op_votes` and are looked up much later by `countVotes()`, which purposefully widens the counting window (1 year, then 2, then 3, ...) until enough voting balance is found: [4](#0-3) 

When actually tallying, `countVotes()` simply sums balances per `op_address` and takes the top `COUNT_WITNESSES` addresses — it performs none of the eligibility checks (`checkNotAAs`, `checkWitnessesKnownAndGood`, `checkNoReferencesInWitnessAddressDefinitions`) that were applied at vote-casting time: [5](#0-4) 

Finally, once an `op_list` is selected and stored, it is used directly as the enforced witness set for new units once `last_ball_mci >= constants.v4UpgradeMci`. At that point, `validateWitnesses()` only checks that the witnessed level does not retreat — it does **not** re-verify that the OPs in `storage.getOpList(...)` are still non-AA, known/good/stable, or free of address-definition references: [6](#0-5) 

This is in sharp contrast to the pre-v4 path a few lines below, which explicitly calls `checkWitnessesKnownAndGood` and `checkNoReferencesInWitnessAddressDefinitions` before accepting an inline witness list: [7](#0-6) 

So an address that was eligible when a voter cast their `system_vote` can, by the time votes are tallied (potentially years later per the widening window), have become an AA, lost its "known and good" status, or acquired a reference in its address definition — yet the stale vote for it is still counted, and if it wins, it is installed into `op_list` and used as a witness with no further eligibility check.

### Impact Explanation
If enough historical/stale votes accumulate for an address that has since become ineligible (e.g., it was later turned into an AA via a matching AA definition, since AAs can never author units), that address can be elected into `op_list` unchecked. A witness slot occupied by an address that structurally cannot author units (an AA) or that fails the "known and good" / "no references" checks reduces the pool of functioning OPs. If enough elected OPs end up in this disqualified state, the network's ability to reach `MAJORITY_OF_WITNESSES` for witnessed-level advancement and main-chain stabilization degrades, directly threatening the network's ability to confirm/stabilize new units — one of the accepted high-impact outcomes. There is also no user-facing or protocol-level mechanism to reallocate or invalidate a stale vote once the underlying candidate becomes disqualified, exactly mirroring the reported bug class.

### Likelihood Explanation
Triggering this requires an address to be voted for as an OP while eligible, and then transition to an ineligible state (e.g., becoming an AA, or having its definition mutated to include references) before the accumulated vote balance is tallied. Because the tally window is deliberately extended (1, 2, 3+ years) whenever voter turnout is low, and votes are never re-validated once cast, this is a realistic, deterministic occurrence rather than a purely theoretical one — any legitimate wallet holder that later chooses to become an AA (a normal, supported operation) while still holding old OP votes would trigger this gap. Likelihood is Medium: it requires accumulation of significant voting balance and time to elapse, but no adversarial cooperation from other network participants is needed.

### Recommendation
- Re-verify OP eligibility (`checkNotAAs`, `checkWitnessesKnownAndGood`, `checkNoReferencesInWitnessAddressDefinitions`) inside `countVotes()` in `main_chain.js` before finalizing the elected `op_list`, excluding stale/ineligible votes from the tally rather than silently keeping them.
- Alternatively (or additionally), re-check the same eligibility conditions in `validateWitnesses()` in `validation.js` for the `last_ball_mci >= constants.v4UpgradeMci` branch before accepting `storage.getOpList(...)` as valid witnesses for a unit, matching the pre-v4 code path's behavior.
- Consider invalidating/expiring a user's `system_vote` for `op_list` automatically once the voted-for address becomes disqualified, so voting power is not silently wasted and can be reallocated by prompting the voter to re-vote.

### Proof of Concept
1. Address `X` is a normal (non-AA) address. Voter `V` posts a `system_vote` unit naming `op_list` that includes `X`; validation succeeds because at that `last_ball_mci`, `X` passes `checkNotAAs`, `checkWitnessesKnownAndGood`, and `checkNoReferencesInWitnessAddressDefinitions` (`validation.js:1874-1882`).
2. Time passes without enough voter turnout in the most recent year, so `countVotes()` widens the counting window to 2+ years (`main_chain.js:1807-1821`), still including `V`'s vote for `X`.
3. Independently, the owner of `X` posts an AA definition matching `X`'s chash, converting `X` into an AA (a supported, ordinary operation).
4. At the next `system_vote_count`, `countVotes()` tallies `op_votes` purely by balance (`main_chain.js:1850-1876`) with no eligibility re-check, and `X` — now an AA — is selected into `op_list`.
5. `storage.systemVars.op_list` is updated with `X` included; subsequent units validate their witnesses via `validateWitnesses()`, which for `last_ball_mci >= v4UpgradeMci` only checks witnessed-level non-retreat (`validation.js:925-926`) and never re-verifies `X`'s AA/eligibility status, so `X` remains an accepted OP despite being structurally unable to author witnessing units, degrading the effective witness quorum.

function checkWitnessesKnownAndGood(conn, objValidationState, arrWitnesses, cb) {
	if (objValidationState.bGenesis)
		return cb();
	profiler.start();
	// check that all witnesses are already known and their units are good and stable
	conn.query(
		// address=definition_chash is true in the first appearence of the address
		// (not just in first appearence: it can return to its initial definition_chash sometime later)
		"SELECT COUNT(DISTINCT address) AS count_stable_good_witnesses \n\
		FROM unit_authors " + db.forceIndex(conf.storage === 'sqlite' ? 'byDefinitionChash' : 'unitAuthorsIndexByAddressDefinitionChash') + " \n\
		CROSS JOIN units USING(unit) \n\
		WHERE address=definition_chash AND +sequence='good' AND is_stable=1 AND main_chain_index<=? AND definition_chash IN(?)",
		[objValidationState.last_ball_mci, arrWitnesses],
		function(rows){
			profiler.stop('validation-witnesses-stable');
			if (rows[0].count_stable_good_witnesses !== constants.COUNT_WITNESSES)
				return cb("some witnesses are not stable, not serial, or don't come before last ball");
			cb();
		}
	);
}
