### Title
Webhook signature verification selects the validating GitHub App secret from an unverified payload field, allowing cross-organization webhook forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
This is a structural analog of the "zero-value fee" class of bug: a value that is *acted upon* (here, which HMAC secret is used to authenticate a request) is derived from data that has not yet been — and never fully is — covered by the very check meant to protect it. In `Beedle`, the fee amount computed and *then* transferred could be zero, silently skipping the intended value-transfer safety check. In `shipit-engine`, the organization used to *select* the webhook-verification secret is read straight out of the still-unverified JSON body, so the field that determines "which secret proves authenticity" is itself unauthenticated at the moment it's used.

### Finding Description
`WebhooksController#verify_signature` picks which GitHub App (and thus which `webhook_secret`) will be used to validate the incoming signature by reading `repository_owner`, which comes directly from the raw, not-yet-verified JSON payload: [1](#0-0) [2](#0-1) 

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

`Shipit.github(organization:)` looks up per-organization configuration (including the org-specific `webhook_secret`) from this same untrusted field: [3](#0-2) 

`verify_webhook_signature` then simply HMAC-verifies the raw body against the secret belonging to whichever org was named: [4](#0-3) 

The equality this design silently assumes is:
`organization used to select webhook_secret == organization that legitimately owns the repository named later in the same payload (e.g. repository.full_name used by handlers such as GithubSyncJob to resolve the target Stack)`.

Because `repository_owner` is taken from the payload *before* any signature check occurs, and because it is only used to pick the secret (not cross-checked against the `repository.full_name` value the downstream handlers act on), the binding between "who signed this" and "what repository/stack this event claims to be about" is never enforced by the controller.

### Impact Explanation
In a multi-organization deployment (`docs/setup.md` documents this as a supported configuration with one `webhook_secret` per organization), an attacker who possesses (or knows) the `webhook_secret` for *any one* configured organization — e.g., a low-trust org they administer themselves — can craft a webhook body where `organization.login`/`repository.owner.login` names that org (so verification succeeds using that org's key) while other payload fields the event handlers actually key off (`repository.full_name`, branch, sha, etc.) reference a different, more privileged Stack/repository under a different organization also registered with Shipit. If the corresponding event handler resolves the target `Stack`/`Repository` purely from `repository.full_name` without asserting it belongs to the same organization whose secret verified the request, the attacker can inject spoofed GitHub events (push, status, check_suite, membership, pull_request, etc.) for a repository they do not control, potentially triggering unauthorized syncs, status changes, or deploy/merge-eligibility side effects — an authentication-bypass class impact scoped to the affected Stack.

### Likelihood Explanation
Requires: (1) a multi-organization Shipit deployment, and (2) the attacker to possess a valid `webhook_secret` for at least one configured organization (e.g., their own, since Shipit lets organizations self-manage their GitHub App and secret). No `ApiClient` token, `github_access_token`, or write access to the target repository is required — only knowledge of one org's webhook secret, which by design many organizations legitimately hold. This is a moderate-likelihood scenario limited to multi-org setups.

### Recommendation
After `verify_webhook_signature` succeeds, re-derive the repository/stack strictly from the same `repository_owner`/organization that was verified, and reject (422) any payload where `repository.owner.login`/`organization.login` used for downstream resolution differs from the value used to select the signing secret. Do not trust `repository.full_name` independent of the authenticated organization.

### Proof of Concept
1. Configure Shipit with two organizations, `OrgA` (target, privileged) and `OrgB` (attacker-controlled, e.g., attacker is an admin of `OrgB`'s GitHub App), each with distinct `webhook_secret`s, per `docs/setup.md`'s multi-app format.
2. Attacker crafts a webhook body:
   ```json
   {
     "organization": { "login": "OrgB" },
     "repository": { "full_name": "OrgA/target-repo", "owner": { "login": "OrgB" } },
     "after": "<attacker-chosen-sha>"
   }
   ```
3. Attacker signs the raw body with `OrgB`'s known `webhook_secret` and sets `X-Hub-Signature` accordingly, `X-Github-Event: push`.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: "OrgB")`, verifies successfully against `OrgB`'s secret.
5. The `push` handler proceeds to process the event using `repository.full_name = "OrgA/target-repo"`, i.e., the attacker has produced a signature-valid event for a repository outside the organization whose secret they used — without ever needing `OrgA`'s webhook secret.

Note: full confirmation of the downstream handler's lookup keys (e.g., `app/models/shipit/webhooks/handlers/push_handler.rb`) could not be completed within the available tool budget; the root-cause binding break in `verify_signature`/`Shipit.github` is confirmed directly from source, but exact exploitability depends on whether any handler independently cross-checks organization ownership of `repository.full_name`, which was not verified in this pass.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
