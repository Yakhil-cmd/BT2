### Title
Webhook signature verification binds trust to `repository.owner.login`, not to the `repository.full_name` actually acted upon, allowing cross-organization stack writes when any configured org has no `webhook_secret` - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/secret to verify a webhook against using `repository.owner.login` (or `organization.login`) from the untrusted payload, while the downstream event handlers (e.g. `PushHandler`) resolve the target `Stack`/`Repository` from a different field, `repository.full_name`. If any organization configured in `Shipit.github` has `webhook_secret` unset — a state explicitly shown as the default/example value (`# nil`) throughout the docs and templates — `verify_webhook_signature` unconditionally returns `true`, so an attacker can forge a payload whose `owner.login` matches that unsecured org while `full_name` points at a completely different, securely-configured organization's tracked repository, causing Shipit to act on it as if it were a verified event.

### Finding Description
`verify_signature` derives the authenticating organization purely from the payload, not from anything independently trustworthy: [1](#0-0) [2](#0-1) 

The signature check itself is delegated to `GithubApp#verify_webhook_signature`, which explicitly no-ops when the resolved org has no `webhook_secret` configured: [3](#0-2) 

`webhook_secret: # nil` is the value shown for every example/template configuration shipped with the engine, including multi-org setups where per-org secrets can independently be left blank: [4](#0-3) [5](#0-4) [6](#0-5) 

Meanwhile, the event handlers that actually mutate state (create commits, sync branches, trigger jobs, etc.) resolve the target repository/stack from a separate payload field, `repository.full_name`, independent of `repository.owner.login`: [7](#0-6) [8](#0-7) 

This is confirmed by the engine's own test, which independently manipulates `repository.full_name` to control which repository record is targeted, showing that repository resolution for handling is decoupled from the org used in `verify_signature`: [9](#0-8) 

**The equality that should hold but doesn't:**
`organization authenticated by verify_signature (repository.owner.login / organization.login)` == `organization owning the repository actually written by the handler (repository.full_name)`.

Because the whole raw POST body is what's HMAC-signed (when a secret exists) via `X-Hub-Signature`, this binding normally holds for any *single*, properly-secreted org — you can't change `full_name` without invalidating the signature for that org's secret. But the check that "unless webhook_secret" is `true` breaks this entirely for any org that has no secret configured: no HMAC is computed or compared at all, so an attacker can submit an arbitrary payload where `repository.owner.login` (or `organization.login`) is set to the org with no secret, while `repository.full_name` is set to any other Shipit-tracked repository (owned by a different, properly-configured org).

### Impact Explanation
This crosses the "organization that authenticated versus the repository that is written" trust binding described in the rules. Concretely, an unauthenticated, unprivileged attacker who knows (or guesses) that a Shipit deployment has at least one configured GitHub org without a `webhook_secret` (a common oversight since it's the documented/templated default) can:
- Forge `push` events (`GithubSyncJob`) targeting any tracked repository under a different, secured organization, injecting arbitrary fabricated "GitHub commits" data via the sync path.
- Forge `check_suite`, `status`, `pull_request`, `membership`, etc. events for arbitrary tracked stacks/repositories, creating teams/users on the fly (as shown by the `:membership` tests) or affecting merge/review-stack state for repos they have no legitimate access to.

This is a cross-repository/cross-organization write achieved without any credential, satisfying the Critical impact bar ("cross-repository writes").

### Likelihood Explanation
Likelihood is moderate-to-high in realistic deployments: the vulnerability doesn't require compromising any secret — it requires only that one configured GitHub organization (out of potentially several in a multi-org setup) has `webhook_secret` unset, which is exactly the state shown by every shipped example/template. The webhook endpoint (`/webhooks`) is unauthenticated by design and reachable by anyone, so the only barrier is the attacker's knowledge of which org lacks a secret — discoverable by trial (submitting to the endpoint with different `owner.login`/`organization.login` values and observing the response code: `head(422)` for verified-but-failed, `200/204` for accepted).

### Recommendation
- Do not allow `verify_webhook_signature` to silently pass when `webhook_secret` is blank; require a secret and reject the event (`422`) instead of returning `true`.
- Bind the org used for signature verification to the actual `full_name` (owner+name) that will be acted upon, not two independently attacker-controlled fields (`owner.login` vs `full_name`), so a mismatch between them is impossible.
- Consider requiring `webhook_secret` to be present for every organization at boot/config-validation time, especially in multi-org configurations, to eliminate silent unauthenticated orgs.

### Proof of Concept
Given a multi-org configuration where `orgA` has no `webhook_secret` and `orgB` (with a tracked repository `orgB/victim-repo`) has one configured properly:

```
POST /webhooks
X-Github-Event: push
X-Hub-Signature: sha1=anything-or-omitted

{
  "ref": "refs/heads/main",
  "after": "deadbeef...",
  "repository": {
    "owner": { "login": "orgA" },
    "full_name": "orgB/victim-repo"
  }
}
```

- `verify_signature` computes `repository_owner = "orgA"`, loads `Shipit.github(organization: "orgA")`, whose `webhook_secret` is `nil`; `verify_webhook_signature` returns `true` unconditionally per [10](#0-9) , regardless of the (even absent/garbage) `X-Hub-Signature` value.
- `PushHandler#process` then resolves stacks via `stacks` (backed by `Repository.from_github_repo_name`/`full_name` lookup, see [8](#0-7) ) using `orgB/victim-repo`, enqueuing `GithubSyncJob` against `orgB`'s stack — despite the request never having been authenticated as coming from `orgB`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
```
