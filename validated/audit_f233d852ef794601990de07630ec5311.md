### Title
Webhook signature verification binds only to `repository.owner.login`, not to the repository/commit actually mutated by handlers, allowing cross-organization status/sync forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App secret to use for HMAC verification based on `repository_owner`, a value read out of the same JSON body it is verifying [1](#0-0) , computed as `params.dig('repository','owner','login') || params.dig('organization','login')` [2](#0-1) . Once the signature check passes, the event handlers act on other fields of that same body (`repository.full_name`, `sha`) without re-validating that they belong to the organization whose secret authenticated the request. This breaks the trust binding "organization that authenticated == repository that is written."

### Finding Description
Shipit supports multiple GitHub Apps/organizations configured side by side, each with its own `webhook_secret`, as shown by `TOP_LEVEL_GH_KEYS` and the multi-org fixture `secrets_double_github_app.yml` [3](#0-2) . `Shipit.github(organization: repository_owner)` looks up the app/secret purely from the `repository_owner` string taken out of the request body [1](#0-0) .

Because the signature is only validated as "this body was HMAC-signed with Org X's secret," and `repository_owner` (Org X) is itself attacker-supplied content inside that same body, nothing forces the *rest* of the payload (the repository actually mutated, or the commit sha actually updated) to belong to Org X. The base `Handler` class derives the target repository from `repository.full_name` [4](#0-3) , a field completely independent of `repository.owner.login` used for signing.

`StatusHandler` is the most severe case: it doesn't even scope by repository — it matches by SHA alone, globally, across every stack/commit in the Shipit install: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [5](#0-4) . `PushHandler` similarly resolves stacks via `repository.full_name` and forces a sync to an attacker-chosen `after` sha [6](#0-5) .

Thus, anyone who legitimately administers one organization's GitHub App on a multi-tenant Shipit instance (and therefore knows that org's `webhook_secret`) can sign a webhook body where `repository.owner.login`/`organization.login` names their own org (so `verify_signature` passes using their own secret) while `repository.full_name`/`sha` reference a commit/repository belonging to an entirely different tenant tracked by the same instance.

### Impact Explanation
A forged `status` event lets the attacker set an arbitrary CI status (e.g., `success`) on any commit sha they can guess/know in another organization's stack, with no repository-ownership check at all in `StatusHandler`. `Commit#deployable?` depends on `success?` [7](#0-6) , and `schedule_continuous_delivery` triggers `ContinuousDeliveryJob` once a commit becomes deployable [8](#0-7) . This can cause an unauthorized deploy of a stack the attacker has no legitimate access to — matching the Critical "unauthorized deploy" impact category. A forged `push` event similarly forces `GithubSyncJob`/`sync_github` against another tenant's stack, an unscoped cross-repository write.

### Likelihood Explanation
This requires the attacker to hold a valid `webhook_secret` for *some* organization configured on the Shipit instance — realistic in the documented multi-org deployment model where each tenant organization independently owns/rotates its own GitHub App and its own webhook secret, but all tenants are tracked by the same Shipit instance and are supposed to be isolated from each other. No GitHub-side repository write access, Shipit session, or `ApiClient` token is needed — only knowledge of one tenant's own webhook secret plus the target commit sha/repo full_name, both of which are frequently public/predictable (public repos, public CI logs, etc.).

### Recommendation
After selecting the GitHub App/secret via `repository_owner`, re-verify that every repository/commit referenced elsewhere in the payload (`repository.full_name`, and for `StatusHandler`, the stack owning the matched commit) actually belongs to that same `repository_owner`/organization before processing. In particular, `StatusHandler` should scope `Commit` lookups through the stack's repository owner and reject statuses whose repository does not match the organization that authenticated the webhook.

### Proof of Concept
1. Shipit is configured with two orgs, `OrgA` (attacker-administered GitHub App, attacker knows `webhook_secret_A`) and `OrgB` (victim tenant tracked by the same Shipit instance), as in `secrets_double_github_app.yml`.
2. Attacker crafts a `status` webhook body:
```json
{
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgA/whatever" },
  "sha": "<known sha of a pending commit in OrgB/victim-repo>",
  "state": "success"
}
```
3. Attacker signs the raw body with `webhook_secret_A` and sets `X-Hub-Signature` and `X-Github-Event: status`.
4. `verify_signature` calls `Shipit.github(organization: 'OrgA')` (from `repository.owner.login`) and the signature check passes [1](#0-0) .
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)`, finds the victim's commit in `OrgB/victim-repo` (no org/repo check), and creates a forged `success` status on it [5](#0-4) .
6. If `OrgB`'s stack is `continuous_deployment?`, the forged success status can trigger an unauthorized deploy via `schedule_continuous_delivery` [8](#0-7) .
