## Analysis

The CVE-2023-54164 bug class is: a validity check (`sk->sk_state`) is read and relied upon without holding the lock that serializes state transitions, so a concurrent path can free/mutate the checked object between the check and its use, leading to unsynchronized/duplicate handling of the same logical resource.

The closest reachable analog in `ocore--014` is in the **private-payment validation/save pipeline**, which — unlike public unit validation — is not serialized by any mutex across concurrent invocations for the same source output.

### Title
Missing serialization allows double-spend of private-asset outputs via concurrently processed private payment chains - (File: private_payment.js)

### Summary
Public-unit validation always takes `mutex.lock(arrAuthorAddresses)` (`validation.js`, `validate()`) before checking/writing input uniqueness, which serializes conflicting spends of the same source output. Private-asset chain validation, however, calls `privatePayment.validateAndSavePrivatePaymentChain` directly with **no mutex at all**: it opens its own DB connection, `BEGIN`s a private transaction, performs a duplicate/spend check by `SELECT`, and only then inserts the `inputs`/`outputs` rows and `COMMIT`s.

### Finding Description
`private_payment.js` `validateAndSavePrivatePaymentChain` (`private_payment.js:23-119`) takes a fresh connection and its own transaction with no external lock: [1](#0-0) 
The duplicate check queries `outputs` for a pre-existing row and, if absent, delegates to `indivisibleAsset`/`divisibleAsset`'s `validateAndSavePrivatePaymentChain`, which validates the spend proof / double-spend status (`indivisible_asset.js` `validatePrivatePayment` → `validation.validatePayment` → `checkInputDoubleSpend`) and then inserts input rows: [2](#0-1) 

Crucially, callers can and do run multiple such validations **concurrently**. `network.js` `handleSavedPrivatePayments` explicitly processes queued private chains "in parallel": [3](#0-2) 
and `handleOnlinePrivatePayment`'s `ifKnown` branch calls `validateAndSavePrivatePaymentChain` directly, with the `assocUnitsInWork` guard that protects public units explicitly commented out: [4](#0-3) 

Because each invocation opens its own DB connection/transaction, the double-spend check in `validatePaymentInputsAndOutputs`/`checkForDoublespends` (`validation.js:2258-2305`) only sees rows already committed by other transactions — it cannot see another private chain's in-flight, uncommitted insert of a conflicting input for the same `(src_unit, src_message_index, src_output_index)`: [5](#0-4) 
The only mutex present, `mutex.lock(["private_write"])`, is scoped narrowly to the "ununique the conflicting older record" branch (`acceptDoublespends`), not to the entire check-then-insert sequence for the first accepted spend: [6](#0-5) 

This is structurally the same defect as CVE-2023-54164: a decision ("is this output already spent / is this the accepted branch of a conflict?") is made by reading shared state without holding the lock that would make the check-then-act sequence atomic with respect to other concurrent handlers touching the same state, allowing two racing paths to both proceed as if they were first.

### Impact Explanation
A private-payment counterparty (e.g., a device sending two conflicting private chains for the same hidden/private output — trivially reachable since private payments are peer-to-peer and not subject to global witness-ordering until stable) can submit two private chains spending the same source output through two different code paths that run concurrently (`handleSavedPrivatePayments`'s parallel `async.each`, or overlapping `handleOnlinePrivatePayment` calls from different devices/hub messages). Each validation runs on its own connection/transaction and cannot observe the other's uncommitted insert, so both can pass the double-spend check and both commit `is_unique=1` inputs referencing the same source output — a double-spend of a private asset, i.e., unauthorized duplication of value that should not confirm twice.

### Likelihood Explanation
Requires only that an attacker control (or induce, e.g. via a compromised/duplicated wallet device or resent private payment messages) two private chains spending the same private output and get them processed concurrently — no privileged, hub, or network-level position is needed beyond being an ordinary private-payment counterparty. `handleSavedPrivatePayments`'s parallel processing of queued chains and independent `handleOnlinePrivatePayment` invocations make simultaneous evaluation plausible under normal wallet activity (e.g. resubmission/retry, or being sent as both direct peer and cosigner).

### Recommendation
Serialize private-payment chain validation-and-save per conflicting source output (or globally, like public units use `mutex.lock(arrAuthorAddresses)`) before the duplicate/double-spend check runs, e.g. wrap `private_payment.js`'s `validateAndSave` (and the `indivisible_asset.js`/`divisible_asset.js` `validateAndSavePrivatePaymentChain` save paths) in a `mutex.lock(["private_write"])` (or a per-`src_output` key) that spans from the initial duplicate check through the final `INSERT`/`COMMIT`, not just the "accept doublespend" branch.

### Proof of Concept
1. Create a private (indivisible or divisible) asset output `O` owned by device A.
2. Craft two private payment chains `C1` and `C2`, each spending `O` to different destinations, with valid spend proofs (only A can produce these, but a compromised/duplicated device or a resent message could yield two chains).
3. Submit `C1` via `handleOnlinePrivatePayment` to peer 1 and `C2` via `handleOnlinePrivatePayment` to peer 2 (or queue both as `unhandled_private_payments` so `handleSavedPrivatePayments`'s parallel `async.each` picks them up together).
4. Both validations run on separate DB connections/transactions; each `checkForDoublespends` query in `validation.js` only sees already-committed rows, so both see `O` as unspent and both commit `is_unique=1` inputs.
5. Result: two conflicting private inputs spending the same output are both marked unique/serial, i.e., a successful double-spend of the private asset.
