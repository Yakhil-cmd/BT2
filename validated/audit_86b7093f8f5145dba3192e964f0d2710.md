### Title
Cross-repository SHA collision lets an unprivileged webhook mutate an already-deployed commit's status history silently - ([File: app/models/shipit/commit.rb], [File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` resolves target commits with `Commit.where(sha: params.sha)`, which is scoped only by `sha` and not by the repository that authenticated the webhook via `verify_signature`. If an attacker's own repository (e.g. a fork sharing history with the victim) produces a webhook `status` event for a sha that also exists in a victim stack, `Commit#add_status` will unconditionally run `statuses.replicate_from_github!` for the victim's commit while the `unless already_deployed` guard silently swallows the `Hook.emit(:commit_status, ...)` notification if that commit is already deployed.

### Finding Description
The binding claimed to hold is: **a `Status` row is created only for commits belonging to the repository that authenticated the request** (i.e. `commit.stack.repository == repository_owner_from_signed_payload`). This does not hold.

- `WebhooksController#verify_signature` authenticates that the payload signature matches the GitHub App secret for `repository_owner` (`params.dig('repository','owner','login')`) [1](#0-0) . This only proves the payload really came from that organization/repo — it says nothing about which `Commit`/`Stack` rows in the Shipit database the `sha` inside the payload should touch.
- `StatusHandler#process` then does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [2](#0-1) . This query is global across all stacks/repositories tracked by the Shipit instance; it is not scoped to a stack whose repository matches `repository_owner`.
- `create_status_from_github!` calls `add_status { statuses.replicate_from_github!(stack_id, github_status) }` [3](#0-2) .
- `add_status` computes `already_deployed = deployed?` up front, then **unconditionally executes `yield`** (the `replicate_from_github!` write) regardless of `already_deployed`, and only uses the flag to suppress the subsequent `Hook.emit(:commit_status, ...)` and `Hook.emit(:deployable_status, ...)` calls [4](#0-3) .

Exploit flow: an attacker forks/mirrors the victim's GitHub repository into their own GitHub account or organization (an unprivileged action they fully control), which by construction shares commit SHAs with the victim history — including a SHA that the victim stack has already deployed (`deployed?` true, i.e. `stack.last_deployed_commit.id >= id`). The attacker installs/configures the (self-service) GitHub App on their own repo/org so they can produce a validly-signed webhook for events on their own repo, and sends a `status` event referencing that shared SHA with an arbitrary `state`/`context`/`description`. `verify_signature` passes because the signature matches the attacker's own org's secret. `StatusHandler` then matches the SHA against the victim's `Commit` row (because `Commit.where(sha:)` isn't scoped to the sender's repo) and calls `add_status` on it, writing a new forged `Status` row into `commit.statuses` for the victim stack, while the `already_deployed` guard suppresses `Hook.emit(:commit_status, ...)`, so no operator-visible notification/audit hook fires.

None of the existing guards prevent this: `verify_signature` authenticates the sender's organization, not the target commit's ownership; `drop_unhandled_event` only filters unsupported event types; there is no `ExplicitParameters` or model validation constraining `Commit.where(sha:)` to the authenticated repository.

### Impact Explanation
A payload authenticated for repository B mutates commit/status state that belongs to a different stack/repository A, matching the Critical category "a payload for one repository mutating another's stack, commit, task or team." The forged `Status` row corrupts the audit trail of an already-shipped commit and can influence subsequent status/state computations (`Status::Group.compact`) for that commit in the victim stack, without any `Hook.emit(:commit_status, ...)` being fired to alert operators or external integrations, because the emission is specifically suppressed for already-deployed commits. This is repeatable against any victim stack whose repository shares commit history (fork/mirror) with a repository the attacker controls, and works for every shared SHA, not a single request.

### Likelihood Explanation
Preconditions: the attacker must control a GitHub repository/org that (a) shares at least one commit SHA with a victim's Shipit-tracked stack (trivially achievable via forking/mirroring, since git SHAs are content-addressed and identical across forks), and (b) has the Shipit-integrated GitHub App configured for signing (feasible if Shipit's GitHub App is self-serve/installable by any GitHub user/org, which is the normal GitHub Apps model). No Shipit session, API token, or operator privilege is required — only the ability to emit a validly signed webhook from a repository the attacker owns, which is explicitly within the stated attacker capability. This is repeatable at will and does not depend on any Shipit misconfiguration beyond normal multi-tenant SaaS operation.

### Recommendation
Scope commit lookups in `StatusHandler#process` (and analogous handlers) to only stacks belonging to the authenticated repository (e.g. `Commit.joins(:stack).merge(Stack.where(repository: matching_repo)).where(sha: params.sha)`) instead of a global `sha`-only match. Additionally, `Commit#add_status` should not execute the mutating `yield` for commits it considers out of scope; at minimum, the write and the hook-suppression logic should not diverge — either both are skipped or both proceed, and repository ownership should be verified before any write occurs.

### Proof of Concept
```ruby
# test/models/commit_add_status_cross_repo_test.rb
require 'test_helper'

module Shipit
  class CommitAddStatusCrossRepoTest < ActiveSupport::TestCase
    test 'a cross-repository status payload mutates an already-deployed commit silently' do
      stack_a = shipit_stacks(:shipit) # victim stack
      commit = stack_a.commits.create!(sha: 'deadbeef' * 5, message: 'deployed commit')
      stack_a.update!(last_deployed_commit: commit) # commit.deployed? == true

      hook_emitted = false
      Hook.stub(:emit, ->(*args) { hook_emitted = true if args.first == :commit_status }) do
        github_status = stub(
          id: 1, state: 'success', target_url: nil, description: nil,
          context: 'ci/attacker-repo', created_at: Time.now.to_s
        )

        assert_equal 0, commit.statuses.count
        commit.create_status_from_github!(github_status) # simulates StatusHandler#process match

        assert_equal 1, commit.statuses.count, 'Status row was written for the victim commit'
        refute hook_emitted, 'Hook.emit(:commit_status, ...) was NOT invoked despite the write'
      end
    end
  end
end
```
This demonstrates the equality failure: `commit.statuses.count` increases for stack A's already-deployed commit while `Hook.emit(:commit_status, ...)` is never invoked, confirming the write happens for a commit not scoped to any specific authenticated repository, and silently so.

    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
