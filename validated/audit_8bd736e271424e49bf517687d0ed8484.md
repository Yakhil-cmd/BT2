### Title
Webhook signature verification is bound to the payload's `repository.owner.login`, not to the `repository.full_name` the handlers act on - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
In a multi-organization Shipit deployment (each org configured with its own `webhook_secret` under `secrets.github`), `WebhooksController#verify_signature` selects which organization's HMAC secret to check the signature against using a field read out of the *unverified* JSON body, while the handlers that actually mutate state look up the target `Repository`/`Stack` using a *different* field of that same unverified body. Nothing ties these two fields together, so an attacker who legitimately holds a valid webhook secret for one configured organization can forge a signed payload whose `repository.owner.login` matches their own org (so the signature check passes) while `repository.full_name` points at a repository belonging to a completely different organization configured on the same Shipit instance.

### Finding Description
`WebhooksController#verify_signature` picks the GitHub App/organization config to validate the signature with like this: [1](#0-0) 

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) 

`repository_owner` is read directly from the attacker-controlled JSON body (`request.raw_post`, parsed later in `create`), not from anything cryptographically bound at this point. `Shipit.github(organization:)` then looks up that organization's own `webhook_secret` from `secrets.github` and uses only that secret to HMAC-verify the raw request body: [2](#0-1) 

The event handler, however, resolves the repository/stack to act on using a *different* field of the same payload, `repository.full_name`, with no cross-check against the value used to select the signing secret: [3](#0-2) 

```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
```

`Repository.from_github_repo_name` splits this string on `/` and looks the repo up purely by `owner`/`name` columns, with no relation at all to which organization's secret validated the request: [4](#0-3) 

So the equality the system implicitly relies on is:
`organization whose webhook_secret authenticated the request == owner of the repository the handler writes to`

In a genuine GitHub delivery this holds because GitHub itself populates both `repository.owner.login` and `repository.full_name` from the same underlying repository object. But the whole JSON body is attacker-supplied to the `/webhooks` endpoint (this endpoint has no per-organization routing/URL segment; the raw body can encode any values), so an attacker holding a valid `webhook_secret` for Org A on this Shipit instance can set `repository.owner.login = "org-a"` (making `verify_signature` select and validate against Org A's secret, which the attacker knows and can correctly HMAC-sign) while setting `repository.full_name = "org-b/victim-repo"`. `PushHandler`, `PullRequest::*Handler`, etc. all resolve the target purely from `repository.full_name`/`params.repository.full_name`, e.g.: [5](#0-4) [6](#0-5) 

This lets the attacker inject fully-signed, "verified" webhook events (push, pull_request opened/closed/labeled/reopened, status, check_suite, membership, etc.) that target a stack belonging to an organization they have no relationship with, purely because the signature check and the object-resolution logic trust two different, independently-forgeable fields of the same untrusted payload.

### Impact Explanation
Successful forgery lets an attacker drive Shipit actions against another organization's stacks despite never having been granted access to that organization:
- A forged `push` event triggers `GithubSyncJob`/`stack.sync_github` against the victim's stack, letting an attacker force resynchronization/rewrite of commit state used for deploy eligibility.
- Forged `pull_request` `opened`/`closed`/`reopened`/`labeled` events can archive/unarchive review stacks or otherwise manipulate the merge/provisioning lifecycle of another organization's repository.
- Forged `status`/`check_suite` events can inject fabricated CI status onto the victim's commits, which downstream feeds directly into Shipit's merge-queue and deploy-eligibility checks — a path toward an unauthorized deploy or merge on a repository the attacker does not control.

This crosses the "cross-repository writes / unauthorized deploy or merge" bar defined for Critical-severity findings, because it lets a party authenticated only for organization A write state belonging to organization B.

### Likelihood Explanation
This only manifests on Shipit instances configured for multiple GitHub organizations (the `github: <org>: {webhook_secret: ...}` schema in `secrets.github`, as documented in `docs/setup.md`), which is a supported, documented configuration. Within that configuration, the only prerequisite is possession of a valid `webhook_secret` for *any one* of the configured organizations (which any org admin who set up their own GitHub App on the shared Shipit instance would legitimately have) — no access to other organizations, no Shipit session, and no `ApiClient` token is required. This is a realistic multi-tenant deployment scenario and fits squarely in the unprivileged-attacker class the rules call out ("an organization that authenticated versus the repository that is written").

### Recommendation
Bind signature verification to the same field the handlers use to resolve the target repository, and reject payloads whose `repository.owner.login` does not match the owner encoded in `repository.full_name`. Concretely, in `WebhooksController#verify_signature`, derive `repository_owner` from `repository.full_name` (splitting on `/`) rather than the separate `repository.owner.login`/`organization.login` fields, or explicitly validate that `repository.owner.login == repository.full_name.split('/').first` before dispatching to handlers. Handlers should also refuse to process an event if the resolved `Repository`'s `owner` doesn't match the organization whose secret validated the signature.

### Proof of Concept
1. Deploy Shipit configured for two organizations, `org-a` and `org-b`, each with its own `github.webhook_secret` under `secrets.github` (per `docs/setup.md`'s multi-org schema).
2. As an attacker who legitimately administers a GitHub App for `org-a` (and thus knows `org-a`'s `webhook_secret`), craft a `push` event body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "org-a" },
    "full_name": "org-b/victim-repo"
  }
}
```
3. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(org-a webhook_secret, raw_body)>` and set `X-Github-Event: push`.
4. POST to `/webhooks`. `verify_signature` calls `Shipit.github(organization: "org-a")` (from `repository.owner.login`) and validates successfully using `org-a`'s secret, per `app/controllers/shipit/webhooks_controller.rb:24-30`.
5. `PushHandler#process` calls `stacks`, which resolves via `Handler#repository_name` → `payload.dig('repository', 'full_name')` → `"org-b/victim-repo"`, and enqueues `GithubSyncJob`/`stack.sync_github` against `org-b`'s stack — despite the request only being authenticated for `org-a`, per `app/models/shipit/webhooks/handlers/handler.rb:30-38` and `app/models/shipit/webhooks/handlers/push_handler.rb:6-17`.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
