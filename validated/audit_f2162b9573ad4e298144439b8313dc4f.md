### Title
Cross-repository status forgery via unscoped `Commit.where(sha:)` lookup in `StatusHandler` - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` authenticates a webhook payload against the GitHub organization/App that owns the `repository` field declared *in that same payload*, then dispatches to per-event handlers. Every handler except `StatusHandler` scopes its writes through `Handler#stacks`, which resolves `Stack`s strictly via `Repository.from_github_repo_name(payload.dig('repository','full_name'))`. `StatusHandler`, however, ignores that repository scoping entirely and matches by commit SHA alone across the whole `commits` table, breaking the binding between "the organization/repository that authenticated the webhook" and "the repository whose commit is written to."

### Finding Description
`app/controllers/shipit/webhooks_controller.rb` verifies webhook signatures using the organization derived from the payload's own `repository.owner.login` (or `organization.login`) field: [1](#0-0) [2](#0-1) 

This only proves that the sender knows the webhook secret for *that* organization/repository — it says nothing about any other repository configured on the same Shipit instance.

`Handler#stacks` — used by `PushHandler` and `CheckSuiteHandler` — correctly re-derives the target repository from the payload's `repository.full_name` and scopes all writes to `Stack`s belonging to that repository: [3](#0-2) [4](#0-3) [5](#0-4) 

`StatusHandler`, in contrast, never calls `stacks` / never checks `repository_name` at all — it looks up commits globally by SHA only: [6](#0-5) 

`Commit.create_status_from_github!` then calls `add_status`, which emits `commit_status`/`deployable_status` hooks and, crucially, schedules continuous delivery/merges when the new status is `pending` or `success`: [7](#0-6) [8](#0-7) 

Because git commit objects (and therefore SHAs) are identical across forks of the same repository, any organization/repository that is legitimately onboarded to the Shipit instance (and therefore possesses a valid `webhook_secret` for its *own* repository) can send a signed `status` webhook whose `sha` matches a commit that also exists in a completely different, unrelated `Stack`/repository tracked by the same Shipit instance. The signature check only validates that the sender owns the repository named in the payload — it does not validate that the `sha` in the payload actually belongs to that repository. `StatusHandler` will happily attach the forged status to every `Commit` row sharing that SHA, including ones belonging to other organizations' stacks.

### Impact Explanation
This breaks the trust binding "organization that authenticated the webhook" ⇔ "repository whose commit is written." An attacker who controls one legitimately-configured repository/organization on the Shipit instance can forge CI status (`success`) for a commit belonging to a different repository/stack they have no authorization over. Since a `success` status can flip a commit to `deployable?` and, if `continuous_deployment` is enabled on the victim stack, triggers `ProcessMergeRequestsJob`/continuous delivery, this results in cross-repository writes and can enable an unauthorized deploy of a commit the attacker never had CI/authorization rights over. This matches the "cross-repository writes / unauthorized deploy" High/Critical impact category.

### Likelihood Explanation
Requires the attacker to control at least one repository/organization already onboarded to the target Shipit instance (a low bar in multi-tenant/GitHub-org-wide deployments) and to know a SHA shared with the victim's tracked commit — trivially obtainable by forking the victim's public repository, since fork commits retain identical SHAs to their upstream. No privileged Shipit account, `ApiClient` token, or GitHub App private key is required — only a standard `status` webhook signed with the attacker's own valid `webhook_secret`.

### Recommendation
Scope `StatusHandler#process` through the same repository-derived `stacks`/`Repository.from_github_repo_name(repository_name)` mechanism used by `PushHandler` and `CheckSuiteHandler`, e.g. restrict the `Commit.where(sha: params.sha)` lookup to `stacks.flat_map(&:commits)` (or an equivalent `stack_id IN (stacks)` scoped query) instead of querying the global `Commit` table unscoped.

### Proof of Concept
1. Attacker owns/administers `attacker-org/victim-repo-fork`, a fork of `victim-org/victim-repo`, and this fork/org is legitimately configured as a Shipit stack (attacker has a valid `webhook_secret` for `attacker-org`).
2. `victim-org/victim-repo` has an existing tracked `Commit` with SHA `abc123...` that is currently `pending`/undeployed and gates `continuous_deployment`.
3. Since the fork shares git history, the same commit `abc123...` also exists (and is trivially discoverable) in `attacker-org/victim-repo-fork`.
4. Attacker crafts a `status` event payload: `{"sha": "abc123...", "state": "success", "context": "ci/attacker", "repository": {"owner": {"login": "attacker-org"}, "full_name": "attacker-org/victim-repo-fork"}}` and signs it with their own valid `webhook_secret` for `attacker-org`.
5. `WebhooksController#verify_signature` succeeds (correct secret for `attacker-org`). `StatusHandler#process` runs `Commit.where(sha: "abc123...")`, which matches the victim's `Commit` row too, and calls `create_status_from_github!` on it, forging a `success` status and potentially triggering continuous delivery on `victim-org`'s stack.
