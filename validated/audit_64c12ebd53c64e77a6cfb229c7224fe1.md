## Analysis

The core of CVE-2023-0944 is a **missing ownership/authorization check** that lets an authenticated-but-unrelated party modify a resource that should be scoped to a specific owner. The closest analog in ocore is in the device-to-device "sign" message handler in `wallet.js`, where an authorization check that would verify the requesting device is actually a legitimate cosigner of the address has been **deliberately removed (commented out)**. [1](#0-0) 

When a `"sign"` message arrives from any paired correspondent device, `findAddress` resolves `body.address` and, if the address's private key lives on the local device (`ifLocal`), the code used to check that the sender is actually registered as a cosigner of the wallet owning that address: [2](#0-1) 
That check is now commented out with the note "the commented check would make multilateral signing impossible", so **any** paired device — not just a legitimate cosigner of that particular address/wallet — can trigger a signing request for **any** local address: [3](#0-2) 

Only the `ifRemote` branch (signing on another device) retains an explicit ownership check (`other_device_addresses.includes(from_address)`), while the `ifLocal` branch (signing with the local device's own key) has none: [4](#0-3) 

### Title
Missing cosigner-authorization check lets any paired device request signatures on wallet addresses it does not own - (File: wallet.js)

### Summary
The `"sign"` message handler in `handleMessageFromHub` (`wallet.js`, `case "sign"`) removed the check that verifies the requesting device is a registered cosigner of the target address's wallet before emitting a `signing_request` event. As a result, any device paired as a correspondent (e.g., a contact from a text-coin exchange, a prosaic/arbiter contract counterpart, or any other paired peer) can send a `"sign"` message naming **any** local wallet address and signing path, and the wallet will happily construct an unsigned unit and raise a UI signing-confirmation dialog for it — despite the sender never having been authorized as a cosigner for that address.

### Finding Description
`handleMessageFromHub` dispatches the `"sign"` subject to `findAddress(body.address, body.signing_path, ...)`. [5](#0-4) 
`findAddress` classifies the target address/path as local (`ifLocal`), remote (`ifRemote`), merkle, secret, or unknown, based purely on where the resolved signing path's device_address lives — it performs no check on whether `from_address` (the actual sender of the "sign" request) has any legitimate relationship to that address. [6](#0-5) 
In the `ifLocal` callback, the intended safeguard — verifying that `from_address` is one of the wallet's registered device cosigners via `extended_pubkeys` — is explicitly commented out: [1](#0-0) 
Without this check, the handler accepts the request from **any** correspondent device address and proceeds to validate the supplied unsigned unit, then emits `signing_request` which the wallet UI/headless-wallet consumer is expected to act on (typically by prompting the user or auto-signing in a headless setup). [7](#0-6) 
This is structurally the same bug class as CVE-2023-0944: a message that is supposed to be restricted to a specific set of authorized parties (in bhima's case, the record owner; here, the wallet's registered cosigners for a given address) is instead accepted from any authenticated-but-unrelated party, because the authorization check was removed while retaining validation of the message's *shape* (address format, signing path format, payload hashes, etc.) but not the sender's *right* to act on that address.

### Impact Explanation
Because `ifLocal` is reached for ordinary single-sig wallet addresses as well as for the "leaf" of shared/multisig address definitions that resolve to the local device's own key, any paired correspondent (a "friend" contact, a merchant from a text-coin trade, a prosaic/arbiter contract counterpart, etc.) can send crafted `"sign"` requests naming the victim's own payment addresses and an attacker-chosen unsigned unit/outputs. If the recipient approves the resulting signing-confirmation dialog (or the flow runs in a headless/auto-approving wallet configuration), this results in the local device signing and broadcasting a transaction that spends from that address — i.e., unauthorized fund movement initiated by a device that was never authorized as a cosigner of that address. Even in interactive setups, the missing check removes a defense-in-depth layer and blurs the trust boundary between "cosigner-initiated multisig requests" and "arbitrary request from any paired peer," increasing the likelihood of successful social-engineering-driven unauthorized spends.

### Likelihood Explanation
Pairing with a new correspondent device is a normal, low-friction wallet operation (accepting a pairing code/QR from any counterparty, e.g. during a trade or contract negotiation), so an attacker can trivially become a "paired device" without needing to compromise anything. From there, sending a `"sign"` message with a locally-known address is straightforward, and the handler performs no ownership check before surfacing the request to the user for confirmation — the primary limiting factor is UI confirmation, not code-level authorization.

### Recommendation
Reinstate (and fix, since the address is now used instead of an undefined `row`) the cosigner-ownership check in the `ifLocal` branch of `case "sign"`: before emitting `signing_request`, verify that `from_address` is a registered device (via `extended_pubkeys`/`wallet_signing_paths`) for the wallet that owns `body.address`, and reject with `callbacks.ifError("sender is not cosigner of this address")` otherwise. If multilateral/contract signing genuinely requires accepting requests from non-cosigner correspondents (e.g., prosaic/arbiter contract flows), that case should be explicitly whitelisted (e.g., only allow it when the address is tied to a known `wallet_arbiter_contracts`/`prosaic_contracts` shared address with `from_address` matching the contract's registered peer), rather than removing the check for all `"sign"` requests.

### Proof of Concept
1. Attacker device pairs with victim's wallet as an ordinary correspondent (e.g., via QR/pairing link shared for an unrelated purpose such as a trade or chat).
2. Victim's wallet has address `A` (a normal single-sig address in `my_addresses`) with balance.
3. Attacker crafts and sends a device message:
   ```
   subject: "sign"
   body: {
     address: "A",
     signing_path: "r",
     unsigned_unit: { authors: [{address: "A", authentifiers: {r: ""}}], messages: [ ...payment outputs sending funds to attacker-controlled address... ] }
   }
   ```
4. Victim's `handleMessageFromHub` → `case "sign"` resolves `A` via `findAddress` → `ifLocal` (since `A` belongs to victim's own device), and — because the cosigner check is commented out — proceeds straight to constructing/validating the unit and firing `signing_request`, without ever verifying that the attacker's device has any relationship to wallet `A`.
5. If the victim's client/UI approves the resulting prompt (or runs an automated/headless signer), the unit is signed and broadcast, moving funds from `A` to the attacker-chosen output — despite the attacker never being an authorized cosigner of `A`.
