### Title
Null Pointer Dereference DoS in `getPrivateProfileFromJsonBase64()` via Malformed Private-Profile Payload - (File: private_profile.js)

### Summary
`private_profile.js`'s `getPrivateProfileFromJsonBase64()` decodes and `JSON.parse()`s a base64 string supplied by a private-payment/attestation counterparty (typically embedded as a `(profile:BASE64)` link shared over the paired-device chat/DH channel), then immediately dereferences properties on the parsed result without first checking that it is a non-null object. Because `JSON.parse` happily returns `null`, a number, or a string for valid JSON such as `"null"`, `"5"`, or `"\"x\""`, a hostile private-payment counterparty or paired device can supply a crafted base64 blob that parses to `null`, causing an uncaught `TypeError: Cannot read properties of null` when the code accesses `objPrivateProfile.unit`. This mirrors the reported llama.cpp bug class: a value obtained from untrusted, attacker-controlled input is dereferenced before any null/type check, crashing the consuming process.

### Finding Description [1](#0-0) 

```
function getPrivateProfileFromJsonBase64(privateProfileJsonBase64){
	var privateProfileJson = Buffer.from(privateProfileJsonBase64, 'base64').toString('utf8');
	try{
		var objPrivateProfile = JSON.parse(privateProfileJson);
	}
	catch(e){
		return null;
	}
	if (!ValidationUtils.isStringOfLength(objPrivateProfile.unit, constants.HASH_LENGTH) || ...)
```

The `try/catch` only guards against `JSON.parse` throwing (malformed JSON syntax). It does not guard against `JSON.parse` *succeeding* with a non-object result. Standard JSON allows top-level primitives (`null`, numbers, booleans, quoted strings) as valid documents. If the attacker supplies base64 that decodes to the literal text `null`, `JSON.parse` returns the JavaScript value `null`; the very next line then evaluates `objPrivateProfile.unit`, which throws a `TypeError` because property access on `null` is illegal in JavaScript. This throw happens synchronously and outside of any further `try/catch` in this function, so it propagates to the caller. If the caller (an ocore-consuming wallet/UI, e.g. when a peer shares a private-profile attestation link during a private-payment or pairing/chat interaction) does not itself wrap the call in `try/catch`, the exception is unhandled and crashes the Node.js process — a full denial of service for that wallet/device instance, exactly analogous to the null model-context dereference in `bench_1model()` that crashed the Android process in the reported CVE.

### Impact Explanation
This function is a public, exported API (`exports.getPrivateProfileFromJsonBase64`) intended to be invoked whenever a wallet receives an attestation/private-profile reference from a correspondent — a scenario reachable by any paired device or private-payment counterparty without requiring privileged access, matching the "private payment chains" / "paired device" reachable surface explicitly in scope. A malicious counterparty can send a chat message or attestation-linked payload whose base64 content decodes to a bare JSON primitive (e.g. `null`), causing an unhandled `TypeError` and terminating the victim's wallet process — denial of service, consistent with the Medium severity of the original CVE (process crash via null dereference from attacker-supplied, unvalidated input).

### Likelihood Explanation
High: no cryptographic material, signature, or on-chain unit is required — only a syntactically valid JSON primitive base64-encoded and delivered through the existing paired-device/private-payment sharing mechanism (e.g., embedded as `(profile:...)` in a text message, which `wallet.js`'s `handleMessageFromHub` "text" case explicitly passes through without profile-specific validation, or via any UI flow that decodes a profile link received from a peer). Constructing the payload requires no special conditions beyond delivering a string to this parsing function.

### Recommendation
After `JSON.parse`, explicitly validate that the result is a non-null object before accessing any of its properties, e.g.:
```js
if (typeof objPrivateProfile !== 'object' || objPrivateProfile === null)
    return null;
```
placed immediately after the `try/catch` block and before the `ValidationUtils.isStringOfLength(objPrivateProfile.unit, ...)` check in [2](#0-1) .

### Proof of Concept
1. Attacker crafts `privateProfileJsonBase64 = Buffer.from("null", "utf8").toString("base64")` (i.e., `"bnVsbA=="`).
2. Attacker delivers this string to a victim wallet as a private-profile reference (e.g., via a paired-device chat message or attestation link flow that calls `getPrivateProfileFromJsonBase64`).
3. Inside `getPrivateProfileFromJsonBase64`, `JSON.parse("null")` succeeds and returns `null`.
4. The subsequent line `objPrivateProfile.unit` throws `TypeError: Cannot read properties of null (reading 'unit')`.
5. If the caller does not wrap the invocation in `try/catch`, the exception is unhandled and crashes the wallet's Node.js process, producing a denial of service.
