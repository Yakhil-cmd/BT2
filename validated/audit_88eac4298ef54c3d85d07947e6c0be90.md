### Title
Attacker-controlled `timestamp` value via arbitrary `last_ball_unit` selection lets an unprivileged trigger sender forge a stale lock-start time - (File: formula/evaluation.js)

### Summary
An AA trigger sender chooses `last_ball` / `last_ball_unit` when composing their own unit. The oscript `timestamp` keyword resolves to `objValidationState.last_ball_timestamp`, which is simply the timestamp of whatever stable unit the sender declared as `last_ball_unit`, not a network-enforced "current time". Validation only requires this value to be non-decreasing relative to the sender's own prior units and to be an ancestor already included by the chosen parents — it does not require it to be fresh. This mirrors the TrustPad incident, where an incorrect `LockStartTime` (derived from an untrusted/attacker-influenced timestamp source) let the lock period be miscalculated.

### Finding Description
`timestamp` in oscript is evaluated as: [1](#0-0) 

`objValidationState.last_ball_timestamp` is populated from the `last_ball_unit` referenced by the *triggering* unit, both in normal validation and in the AA trigger-handling path: [2](#0-1) [3](#0-2) 

The only constraints imposed on the chosen `last_ball_unit`/`last_ball_mci` are (a) it must be on the main chain and already included by the unit's own parents, and (b) it must not retreat below the max `last_ball_mci` already committed to by those parents: [4](#0-3) [5](#0-4) [6](#0-5) 

There is no rule anywhere in this path binding `last_ball_timestamp` to real wall-clock time or to the unit's own `objUnit.timestamp`; the only wall-clock freshness check applies to `objUnit.timestamp` itself (must not be too far in the future), and to strict non-decrease from the *unit's own* parent chain: [7](#0-6) [8](#0-7) 

Because the constraint is "must not retreat from what my own parents already committed to" rather than "must equal the most recent stable point," a sender who deliberately selects an older-but-still-valid last ball (e.g. by choosing older/less-advanced parent units, or via the "deep parent" fallback path in `parent_composer.js` which explicitly allows falling back to older main-chain ancestors) can make `objValidationState.last_ball_timestamp` (and thus the oscript `timestamp` value) point to a moment far in the past relative to true current time, while `objUnit.timestamp` itself stays fresh: [9](#0-8) 

An AA staking/vesting contract that naively records `var['lock_start'] = timestamp;` when a stake payment is triggered will therefore store an artificially old lock-start value supplied by the depositor. On a later withdrawal trigger (using a fresh, current last ball), the AA computes `timestamp - var['lock_start']` and concludes the lock period has elapsed, releasing funds early — exactly analogous to TrustPad's "incorrect LockStartTime" bug that let the lock time be manipulated.

### Impact Explanation
Any Autonomous Agent that uses the bare `timestamp` oscript keyword as a trust anchor for time-based logic (lock/vesting start, cooldowns, auction end conditions, rate-limiting) can have that value forged backward by the very party whose trigger the AA is trusting. In a staking/locking AA this allows unauthorized early withdrawal of locked funds, i.e. AA fund loss/drain — the same class of loss described in the TrustPad report ($155k). This is a Medium-severity, generically reachable design pitfall of the `timestamp` primitive rather than an outright consensus break, since it does not enable double-spending or MC-stability disagreement between nodes (all nodes evaluate the same deterministic `last_ball_unit`); the damage is confined to AAs that rely on `timestamp` for security-critical time comparisons without additional safeguards.

### Likelihood Explanation
Reachable by any unprivileged unit poster / AA trigger sender who composes their own unit (not requiring a compromised node, peer, or hub). The attacker only needs the ability to select `parent_units`/`last_ball_unit` when constructing a raw unit, which any wallet/composer already exposes as unit-building parameters, and the `parent_composer.js` deep-parent fallback logic already tolerates unit graphs where a sender's declared last ball is not the most recently advanced one. Practical exploitability depends on how far back a valid last ball can be pushed given real DAG/witness advancement, which requires deeper live-network characterization the index does not fully cover — the mechanism is confirmed at the validation-logic level, but the exact achievable skew (seconds vs. hours vs. days) could not be independently bounded from the code alone.

### Recommendation
- AAs must never use `timestamp` alone as a lock/vesting start reference without additionally validating that the trigger unit's `last_ball_mci`/`timestamp` is recent (e.g. bound the allowed staleness, or record `mci` alongside `timestamp` and require monotonic MCI progression consistent with expected block cadence).
- Consider having ocore expose (or documentation strongly warn) that `timestamp` reflects the sender-chosen `last_ball`, not a network-verified "now," and recommend AA authors compare against `previous_aa_responses`/stored MCI deltas rather than raw timestamp deltas for security-critical intervals.
- Alternatively, tighten `validateParents`/`pickParentUnitsAndLastBall` so the allowable staleness between a unit's declared `last_ball_mci` and the true tip MCI available via its parents is bounded, closing the ability to arbitrarily backdate `last_ball_timestamp`.

### Proof of Concept
1. Deploy a staking AA that, on a deposit trigger, executes `var['lock_start'] = timestamp;` and on a withdrawal trigger checks `require(timestamp - var['lock_start'] >= LOCK_PERIOD)` before releasing funds (mirroring TrustPad's lock design).
2. Attacker composes the deposit-triggering unit manually, choosing `parent_units`/`last_ball_unit` that reference an older stable main-chain ball far in the past (permitted so long as it is an ancestor already included by the chosen parents and does not retreat below the attacker's own prior `last_ball_mci`, per `validation.js:668-674,737-741`), while `objUnit.timestamp` itself remains close to real time to pass the future-timestamp check (`validation.js:280-287`).
3. The AA's `init`/`state` formula evaluates `timestamp` as `objValidationState.last_ball_timestamp` (`formula/evaluation.js:1050-1052`) using this old value and stores it as `lock_start`.
4. Attacker immediately sends the withdrawal trigger using a normal, current last ball. `timestamp - lock_start` now exceeds `LOCK_PERIOD` even though no real time has elapsed, and the AA releases the locked funds early.
