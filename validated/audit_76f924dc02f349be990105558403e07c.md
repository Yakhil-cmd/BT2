### Title
Webhook signature verified against the wrong organization's secret because the "which secret to use" lookup key is read from the unverified request body - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects **which** organization's GitHub App/webhook secret to verify the HMAC signature against by reading `repository.owner.login` (or `organization.login`) straight out of the still-unauthenticated JSON body, before the signature has been checked. Because Shipit supports multiple organizations, each with its own `GithubApp`/`webhook_secret` [1](#0-0) , an attacker who legitimately controls one configured organization (and therefore knows *that* organization's real webhook secret) can forge a webhook payload that names their own organization in `repository.owner.login` (so the correct/known secret is selected and the HMAC passes) while putting a *different* organization's/repository's `full_name`, `ref`, `after` (SHA), etc. in the rest of the payload body. The signature is valid for the org that was named, but the payload's operative fields — which actually drive stack lookup and mutation — belong to a repository the attacker does not control.

### Finding Description
`verify_signature` does:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [2](#0-1) 

`repository_owner` is derived entirely from the raw, unverified JSON body — it is exactly the field the signature is supposed to protect. `Shipit.github(organization:)` picks a distinct `GithubApp` instance (with its own `webhook_secret`) per organization, confirmed by the test asserting the lookup uses `organization: 'shopify'` matching the payload's `repository.owner.login` [3](#0-2) , and `verify_webhook_signature` simply HMAC-compares against that org's secret using `SecureCompare` [4](#0-3) .

Once `head(422) unless verified` passes, `create` re-parses the same raw body and dispatches it to `Shipit::Webhooks.for_event(event)` handlers [5](#0-4) . Those handlers (e.g. the push handler that enqueues `GithubSyncJob` with `stack_id` and `expected_head_sha`) resolve the target `Stack`/`Repository` using the payload's `repository.full_name`, not using the organization value that was used for signature selection [6](#0-5) .

**The binding that is broken:** "organization that authenticated the HMAC" ⇔ "repository the handler subsequently writes to." The controller trusts that these are the same because in a legitimate GitHub-delivered webhook they always are (GitHub signs the exact payload it sends for a specific repo/org). But an attacker fully controls the raw body they send to Shipit's endpoint; nothing forces `repository.owner.login` (used to pick the secret) to correspond to `repository.full_name` (used by the handler to pick the stack). An attacker who owns Organization A (and thus legitimately knows Org A's webhook secret because they configured/received it for their own installation) can:
1. Set `repository.owner.login` = `"orgA"` so `Shipit.github(organization: "orgA")` is selected.
2. Compute a valid `X-Hub-Signature` using Org A's own secret over the full crafted body.
3. Set `repository.full_name`, `ref`, `after` (or other event-specific fields) to point at a *different*, victim stack (e.g. `orgB/target-repo`) tracked by the same Shipit instance.

The webhook signature check passes (it's genuinely valid for Org A), but the event is processed as if it legitimately originated from `orgB/target-repo`.

### Impact Explanation
Depending on which event type/handler is targeted, this allows an unprivileged-but-multi-tenant attacker (one who legitimately owns/administers any org configured on the shared Shipit instance) to:
- Trigger `GithubSyncJob` for a victim stack with an attacker-chosen `expected_head_sha`, influencing which commit is considered head/deployable and potentially feeding into continuous deployment, resulting in an unauthorized deploy of attacker-influenced state.
- Forge `status`/`check_suite` events to mark arbitrary commits on a victim stack as passing CI, bypassing `required_statuses` gating and enabling unauthorized merges/deploys of unreviewed code.
- Forge `pull_request`/`membership` events processed by handlers that mutate victim-repo review stacks, teams, or memberships cross-repository.

This satisfies the "Critical" bar: cross-tenant/cross-repository writes and unauthorized deploy triggering, achieved purely by an unprivileged party who only legitimately controls one org on a shared multi-tenant Shipit deployment.

### Likelihood Explanation
Requires the Shipit instance to be configured to serve multiple GitHub organizations (a documented, supported configuration since `Shipit.github(organization:)` and `GithubOrganizationUnknown` explicitly exist to support per-organization apps/secrets). Any org already onboarded onto that shared instance can mount the attack against any other org's stacks with no additional privilege — no Shipit session, no API token, and no access to the victim org's actual webhook secret is needed. This is a realistic and low-effort attack for that threat model.

### Recommendation
Do not use attacker-supplied payload fields to select the verification secret before the signature is validated. Instead:
- Bind the webhook delivery to the intended organization out-of-band (e.g. verify against the secret associated with the receiving endpoint/path, or verify against *every* configured organization's secret and require the payload's `repository.owner.login`/`full_name` to belong to that same, already-verified organization before dispatching), or
- After signature verification succeeds for organization `O`, additionally assert that every repository referenced in the payload (`repository.full_name`, `organization.login`, etc.) actually belongs to organization `O` before allowing handlers to act on it.

### Proof of Concept
1. Configure Shipit with two organizations, `orgA` and `orgB`, each with its own `webhook_secret` in `secrets.yml`.
2. As the administrator of `orgA` (attacker), craft a `push` webhook body:
```json
{
  "repository": { "owner": { "login": "orgA" }, "full_name": "orgB/victim-repo" },
  "ref": "refs/heads/master",
  "after": "deadbeefdeadbeefdeadbeefdeadbeefdeadbeef"
}
```
3. Compute `X-Hub-Signature: sha1=<hmac-sha1(orgA_webhook_secret, body)>` (known to the attacker, since it's their own org's secret).
4. POST this to `/github/webhooks` with header `X-Github-Event: push`.
5. `repository_owner` resolves to `"orgA"`, `Shipit.github(organization: "orgA")` is selected, and `verify_webhook_signature` succeeds because the signature is genuinely valid for `orgA`'s secret.
6. `create` dispatches the parsed body to the push handler, which looks up the stack for `orgB/victim-repo` and enqueues `GithubSyncJob` with the attacker-supplied SHA, even though the attacker has no legitimate relationship to `orgB`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
