### Title
CCMenu API token generated for one stack authorizes `read:stack` access to every stack in the deployment - ([File: app/controllers/shipit/ccmenu_url_controller.rb])

### Summary
`CCMenuUrlController#fetch` is presented to the user as a per-stack "CCMenu status" URL, but the `ApiClient` it mints is never scoped to that stack, so the resulting long‑lived token authorizes `read:stack` on **all** stacks, not just the one the URL was generated for. This breaks the "a stack a token authorises versus a stack it touches" binding: the UI/URL implies the token = stack X, while `ApiClient#stack_id` = nil = every stack.

### Finding Description
`CCMenuUrlController#fetch` builds a per-stack CCMenu URL and appends a freshly minted/looked-up `ApiClient` token as a query parameter: [1](#0-0) 

The client is created with:
```ruby
ApiClient.create_with(permissions: %w[read:stack])
         .find_or_create_by!(creator: current_user, name: 'CCMenu Client')
```
Note that `stack:` is **never** passed to `create_with`/`find_or_create_by!`. `ApiClient#stack` is an optional `belongs_to`, so the created (or found) record has `stack_id == nil`.

`Api::BaseController` decides the visible stack set purely from that field: [2](#0-1) 
```ruby
def stacks
  @stacks ||= current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all
end
```
Because `stack_id?` is false, `stacks` resolves to `Stack.all` for this token. Every controller that only requires `read:stack` permission (no additional check) is therefore reachable for **any** stack once you hold this one token:
- `Api::StacksController#index` / `#show` — list/read every stack's config [3](#0-2) 
- `Api::OutputsController#show` — read task output/console logs of any task on any stack [4](#0-3) 
- `Api::TasksController#index` / `#show` — list/read tasks (deploy metadata) of any stack [5](#0-4) 
- `Api::CCMenuController#show`, `Api::CommitsController`, `Api::MergeRequestsController` — same pattern, all gated only by `require_permission :read, :stack`.

Also note `find_or_create_by!(creator:, name:)` is keyed only on `creator` + fixed name `'CCMenu Client'`, confirmed by the test asserting a single client is created/reused per user regardless of which stack the URL was requested for: [6](#0-5) . So the very first CCMenu URL a user generates (for stack A) yields a token that, when later reused in a CCMenu URL for stack B, is the *same* unscoped token — it was never bound to A or B in the first place.

The "equality" broken: `token.stack_id (nil ⇒ Stack.all)` ≠ `stack_id embedded in the generated ccmenu_url path`. The generation flow visibly ties the token to `stack.to_param` in the URL path, but the actual authorization object carries no such binding.

### Impact Explanation
CCMenu URLs are designed to be embedded in unauthenticated third-party CI dashboard tools (CCMenu/CCTray clients), which is the entire purpose of this endpoint — the token is meant to leak outside of Shipit's session-based access control by design, scoped (supposedly) to one stack's build status. Because the underlying `ApiClient` is unscoped, exposing that URL/token (e.g., pasted into a public CI dashboard, or a stack visible to a low-privileged internal team member) grants the holder unauthenticated `read:stack` access to **every** stack managed by that Shipit instance: full list of stacks, all task/deploy records, and full task console output (which frequently contains SHAs, commit metadata, links, and command output). This matches the "High — unauthenticated read of stack state, task streams or deploy output" impact bucket, achieved purely by leaking a token that a legitimate, low-trust workflow (public CI status badge) intentionally exposes outside the normal session boundary.

### Likelihood Explanation
Any authenticated Shipit user (any team member, regardless of which specific stacks they're supposed to see) can trigger `CCMenuUrlController#fetch` for a stack they have UI access to, generating (or retrieving) the token, no special permission required beyond normal login. The feature is explicitly meant to be shared with external, unauthenticated CCMenu/CI tools, so exposure of the token outside the application boundary is the intended/expected usage pattern, not an edge case. No attacker code execution or GitHub credentials are required — this is a straightforward authorization-scoping bug reachable by design usage of a documented feature.

### Recommendation
Bind the `ApiClient` created by `CCMenuUrlController#fetch` to the specific stack, e.g.:
```ruby
def client
  @client ||= ApiClient.create_with(permissions: %w[read:stack])
                       .find_or_create_by!(creator: current_user, stack:, name: 'CCMenu Client')
end
```
and ensure `find_or_create_by!` is keyed on `(creator, stack)` so that a distinct, stack-scoped client/token is created per stack instead of one global unscoped client reused for every stack a user requests a URL for. Additionally consider validating on `ApiClient` creation that clients minted for external/public exposure always require a non-nil `stack_id`.

### Proof of Concept
1. As any logged-in Shipit user with UI access to at least one stack (e.g. `stack-A`), call:
   `GET /stacks/stack-A/ccmenu_url` → response contains `ccmenu_url` with `?token=<TOKEN>`.
2. Inspect the `ApiClient` created: `ApiClient.last.stack_id # => nil`, `ApiClient.last.permissions # => ["read:stack"]`.
3. Use `<TOKEN>` against the JSON API for a completely different, unrelated stack `stack-B` that the user was never intended to access via this token:
   - `GET /api/stacks?token=<TOKEN>` → returns **all** stacks, not just `stack-A`.
   - `GET /api/stacks/stack-B/tasks/<task_id>/output?token=<TOKEN>` → returns full console output of `stack-B`'s deploy/task, even though the CCMenu URL was only ever generated in the context of `stack-A`.
4. This confirms the token minted for `stack-A`'s public CCMenu badge authorizes read access to `stack-B` (and every other stack), violating the intended per-stack scoping of the exposed token.

  class CCMenuUrlController < ShipitController
    def fetch
      uri = URI(api_stack_ccmenu_url(stack_id: stack.to_param))
      uri.query = { 'token' => client.authentication_token }.to_query
      render(json: { ccmenu_url: uri.to_s })
    end
