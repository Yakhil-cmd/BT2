### Title
Unconditional rejection of duplicate (even identical) address definitions permanently DOS's legitimate first-use transactions - (File: `validation.js`)

### Summary
`validateAuthor()`'s `validateDefinition()` path rejects **any** unit whose author explicitly discloses an address definition that has already been disclosed for that address — even when the definition is byte-for-byte identical and correctly signed. The code that would have allowed a matching redisclosure has been commented out, leaving an unconditional `callback("duplicate definition...")`. This is analogous to the reported bug class: a state-changing, "first writer wins" check with no re-entrancy/idempotency handling can be triggered by any party who discloses the (deterministic, hash-derived) address definition first, permanently blocking a subsequent, otherwise fully valid unit from another legitimate holder of the same address (e.g., a co-signer of a shared/multisig address).

### Finding Description
In `validation.js`, `validateAuthor()` calls `validateDefinition()` whenever an author explicitly attaches a `definition` array to a unit (the normal path for the first-ever use of an address, or the first disclosure after a keychange): [1](#0-0) 

If the definition was already disclosed for that address (`ifFound` branch of `storage.readDefinitionByAddress`), control passes to `handleDuplicateAddressDefinition()`: [2](#0-1) 

The intended guard (`if (!bNonserial || ...)`) that would allow a matching redisclosure to pass is commented out, so the function **always** returns an error, regardless of whether the newly-supplied definition is identical to (and validly signed for) the one already on record. The developers' own comment "`todo: investigate if this can split the nodes`" flags this as an unresolved consensus-risk area.

Because an address's identity is `chash160(definition)`, anyone who legitimately shares knowledge of a definition (e.g., a co-signer of a shared/multisig address created via `wallet_defined_by_addresses.js`, where multiple devices independently possess and can act on the same `arrDefinition`) can be the one who first discloses that definition on-chain by spending from the address with any satisfying authentifier set (e.g., a valid signature branch of an `or` definition, or a data-feed/formula-satisfied branch). Once that first disclosure stabilizes, **every other party's first-time explicit disclosure of the very same address's definition is permanently and unconditionally rejected** as "duplicate definition of address", even though:
- the definition content is identical,
- the authentifiers are valid, and
- there is no actual double-spend of any output.

This differs from `checkForDoublespends()`, which correctly resolves genuine input conflicts; here, the rejection triggers purely because the *definition payload* is attached twice, independent of which outputs are being spent.

### Impact Explanation
For a shared/multisig address where more than one signer/device holds the full definition (a routine configuration produced by `wallet_defined_by_addresses.js`/`handleNewSharedAddress`), a co-signer's concurrently-submitted first transaction from that address can be deterministically blocked once any other party's disclosure of the same definition stabilizes first — not because of a real conflict, but purely due to this unconditional check. This is a self-inflicted but validator-code-level DOS on a legitimate spend/first-use of a multi-party-controlled address, and the code's own comment acknowledges the risk of causing "node[s] split" (i.e., possible disagreement about which units are valid) if this logic is ever tightened/loosened inconsistently across node versions.

### Likelihood Explanation
Multi-signer/shared addresses are a standard, documented feature (see `wallet_defined_by_addresses.js`), and it is entirely plausible in normal operation for two co-signers to independently initiate transactions from the same freshly-created shared address around the same time, both including the definition on first use. No malicious intent beyond "acting first" is required by the party whose disclosure stabilizes first — the second, fully legitimate holder's transaction is unconditionally rejected.

### Recommendation
Restore (and complete) the intended idempotency check: when `ifFound` returns an existing definition, compare it against the newly supplied `arrAddressDefinition` via `chash160`; if they match, accept the unit (treat the resupplied definition as redundant/no-op) instead of unconditionally erroring. Only reject when the definitions genuinely differ (a real conflicting/duplicate-definition attempt).

### Proof of Concept
1. Two devices, A and B, jointly control shared address `S` via `wallet_defined_by_addresses.js`, both holding the identical `arrDefinition` for `S` (e.g., `['or', [['sig', pubkeyA], ['sig', pubkeyB]]]`).
2. Device B broadcasts a unit spending from `S` for the first time, attaching `definition: arrDefinition`, signed by B's key. This unit stabilizes; `readDefinitionByAddress(S)` now resolves via `ifFound`.
3. Device A, unaware/concurrently, broadcasts its own first transaction from `S`, also attaching the identical `arrDefinition`, correctly signed by A's key, spending a different (non-conflicting) output.
4. In `validateAuthor()` → `validateDefinition()` → `ifFound` → `handleDuplicateAddressDefinition()`, A's unit is rejected with `"duplicate definition of address S, bNonserial=false"`, per: [3](#0-2) 
even though A's signature and definition are fully valid and no output is double-spent.

	function validateDefinition(){
		if (!("definition" in objAuthor))
			return callback();
		// the rest assumes that the definition is explicitly defined
		var arrAddressDefinition = objAuthor.definition;
		storage.readDefinitionByAddress(conn, objAuthor.address, objValidationState.last_ball_mci, {
			ifDefinitionNotFound: function(definition_chash){ // first use of the definition_chash (in particular, of the address, when definition_chash=address)
				try {
					if (objectHash.getChash160(arrAddressDefinition) !== definition_chash)
						return callback("wrong definition: " + objectHash.getChash160(arrAddressDefinition) + "!==" + definition_chash);
				}
				catch (e) {
					return callback("definition hash failed: " + e.toString());
				}
				callback();
			},
			ifFound: function(arrAddressDefinition2){ // arrAddressDefinition2 can be different
				handleDuplicateAddressDefinition(arrAddressDefinition2);
			}
		});
	}
