### Title
Approved operator can create a secondary approval that survives operator revocation - (File: contracts/position-nft/src/contract.rs)

### Summary
`PositionNft` exports OpenZeppelin’s stock NFT approval methods unchanged, so an address granted `approve_for_all` authority can call `approve` and grant a separate per-token approval to a third party. [1](#0-0) [2](#0-1)  The secondary approval uses independent `Approval(token_id)` storage and therefore is not revoked when the owner revokes the operator’s `ApprovalForAll(owner, operator)` grant. [3](#0-2) 

### Finding Description
`approve` authorizes an `approver` that is either the token owner or an owner-approved operator, while `transfer_from` authorizes a spender that is the owner, the token-approved address, or an operator. [4](#0-3)  Because these approval modes are stored separately, an operator can create a token-specific approval for an accomplice before the owner revokes the operator grant; that token approval remains usable until its own `live_until_ledger`. [3](#0-2) 

The NFT token id is the lending account id, and transferring it transfers control of the account’s collateral and debt. [5](#0-4)  After the accomplice takes the NFT, controller owner checks resolve the accomplice as the account owner and permit owner-authorized actions such as withdrawal. [6](#0-5) 

### Impact Explanation
An operator trusted only temporarily can leave behind a durable secondary approval that lets a third party transfer the lending position after the operator is revoked, resulting in theft of the account’s withdrawable collateral and control of the associated debt position. [7](#0-6) 

### Likelihood Explanation
Exploitation requires the position owner to grant operator authority to an address that later acts maliciously, so it is not executable by an arbitrary unrelated address. Once that trust exists, the malicious operator needs only one ordinary `approve` call before revocation and an accomplice `transfer_from` call afterward. [2](#0-1) 

### Recommendation
Override `approve` so only the current NFT owner can create or replace a per-token approval, rather than accepting an operator as `approver`. [1](#0-0)  Alternatively, explicitly revoke or bound every operator-created `Approval(token_id)` whenever `approve_for_all` is revoked or expires, and add regression coverage for the revocation-followed-by-secondary-transfer sequence. [3](#0-2) 

### Proof of Concept
1. The position owner calls `approve_for_all(owner, operator, live_until_ledger = L1)`, making `operator` an operator for all of the owner’s position NFTs. [2](#0-1) 
2. Before `L1`, `operator` calls `approve(approver = operator, approved = accomplice, token_id = account_id, live_until_ledger = L2)`, which passes because `operator` is an owner-approved operator. [2](#0-1) 
3. The owner calls `approve_for_all(owner, operator, 0)`, revoking the operator grant; this does not remove the independent `Approval(account_id)` entry naming `accomplice`. [3](#0-2) 
4. `accomplice` calls `transfer_from(spender = accomplice, from = owner, to = accomplice, token_id = account_id)`, which succeeds through the live per-token approval even though `operator` is revoked. [4](#0-3) 
5. `accomplice` is now the NFT owner, so `withdraw(caller = accomplice, account_id = account_id, ...)` satisfies the controller’s owner-or-delegate check and can withdraw the account’s collateral subject to the normal risk rules. [6](#0-5)
