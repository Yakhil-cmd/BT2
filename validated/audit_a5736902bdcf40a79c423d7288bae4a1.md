### Title
`StatusHandler#process` mutates `Commit` rows globally by `sha` without scoping to the webhook's repository, unlike `Handler#stacks` - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`Handler#stacks` exists specifically to scope webhook processing to the `Repository` named in `payload.dig('repository','full_name')`, but `StatusHandler#process` never calls it. Instead it runs `Commit.where(sha: params.sha)` across the entire database, so any commit sha collision between an attacker-controlled repository and an unrelated tenant's repository lets a validly-signed webhook from the attacker's own repo mutate CI status on the victim's `Commit` row.

### Finding Description
The binding that should hold is:
`self.stacks.commits.where(sha: params.sha) == { Commit rows mutated by StatusHandler#process }`

Tracing the code:
- `Handler#stacks` is defined as `Repository.from_github_repo_name(repository_name)&.stacks || Stack.none`, scoping any lookup to the repository named in the payload [1](#0-0) .
- `StatusHandler#process` ignores this scoping entirely and does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [2](#0-1) .
- `Commit#sha` has no uniqueness constraint scoped to (or otherwise) globally; it is simply a git sha column, and `Commit#create_status_from_github!` writes a new `Status` (via `add_status`) which changes `commit.status`, triggers `Hook.emit(:commit_status, ...)`, and can trigger `stack.schedule_merges` [3](#0-2) [4](#0-3) .

So the equality holds for every other handler that uses `stacks`, but is broken specifically for `StatusHandler`: the query has no `stack_id`/repository filter at all.

`verify_signature` in `WebhooksController` only checks that the payload was signed by the GitHub App/webhook secret configured for `repository_owner` (`payload.dig('repository','owner','login')`) [5](#0-4) . This authenticates *that the event genuinely originated from GitHub for that repository*, but says nothing about which `Commit` rows the handler is allowed to touch. It does not, and cannot, prevent the same `sha` value from legitimately existing in another tenant's `Commit` table (e.g. via a fork sharing git history with an upstream repo, where identical commits carry identical shas). Once the attacker's own repository is a Shipit-tracked `Stack` and receives a real, correctly-signed `status` webhook for a commit whose sha is shared with another tenant's commit (a completely ordinary occurrence for forks/shared history, not a SHA1 break), `Commit.where(sha: params.sha)` returns commits belonging to unrelated stacks/repositories and mutates them.

Exploit flow:
1. Attacker forks or otherwise legitimately owns a repository that shares commit history (and therefore identical commit shas) with another repository tracked as a different tenant's `Stack` in the same Shipit instance.
2. Attacker's repository is registered/onboarded as a `Stack` (attacker legitimately owns and controls this repository).
3. Attacker triggers (or crafts, since they own the repo and can push status via their own CI/App) a `status` event for a shared-history commit sha; GitHub signs and delivers this webhook correctly for the attacker's own repository/organization.
4. `WebhooksController#create` passes it to `StatusHandler.call`, whose `#process` runs `Commit.where(sha: params.sha)` — matching not only the attacker's own `Commit` but also the victim tenant's `Commit` row with the same sha.
5. Both commits get `create_status_from_github!` applied, potentially flipping the victim's commit to `success`, which can unblock deploys, trigger `stack.schedule_merges`, or otherwise change the victim stack's CI-driven deploy eligibility — entirely without the victim's authorization.

### Impact Explanation
Any repository owner able to get a validly-signed `status` webhook processed by Shipit for their own repository can overwrite the CI status of a `Commit` belonging to an entirely different, unrelated `Stack`/tenant, provided a sha collision (e.g. via shared fork history) exists. This is a cross-tenant write: a payload authenticated for repository A mutates state (CI status, potentially triggering `schedule_merges`/continuous deployment eligibility) for repository B's commit, matching the "Critical: a payload for one repository mutating another's stack, commit, task or team" category.

### Likelihood Explanation
Preconditions: attacker owns/controls a repository registered as a Stack in the target Shipit instance, and that repository shares at least one commit sha with the victim's repository (trivially true for any fork of a public repository, or for any repository whose history overlaps with the victim's, e.g. shared vendored commits, cherry-picks, or common upstream ancestry). No secrets, sessions, or privileged roles are required — the attacker only needs a legitimately owned repository whose real GitHub-signed webhooks Shipit accepts. This is realistically achievable at low cost for any public-repo fork scenario and is repeatable against any commit sha the attacker can discover (e.g. via the public dashboard) that also exists in their own repo's history.

### Recommendation
Scope `StatusHandler#process` to the webhook's own repository, analogous to other handlers, e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` or more directly `Commit.where(sha: params.sha, stack_id: stacks.select(:id))`, ensuring only commits belonging to `Repository.from_github_repo_name(repository_name)`'s stacks are updated.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb`):
1. Create two `Repository`/`Stack` fixtures, `repo_a` (attacker-owned, e.g. `full_name: "attacker/app"`) and `repo_b` (victim, `full_name: "victim/app"`), each with a `Commit` sharing the identical `sha` value (`"deadbeef" * 5`).
2. Build a `status` webhook payload with `repository.full_name = "attacker/app"` and `sha` equal to the shared value, `state: "success"`.
3. Call `Shipit::Webhooks::Handlers::StatusHandler.call(payload)` directly (bypassing signature verification, as in-scope for this handler's own logic).
4. Assert: `repo_a`'s commit `.reload.status.state == "success"` (expected, same repo).
5. Assert (the vulnerability): `repo_b`'s (victim) commit `.reload.status.state == "success"` as well — demonstrating the victim commit, in a completely different `Stack`, was mutated despite the payload only naming `repo_a`.
6. Contrast assertion showing the binding is broken: `Shipit::Webhooks::Handlers::Handler.new(payload).send(:stacks)` returns only `repo_a`'s stack (excluding `repo_b`), while the actual set of mutated `Commit` ids includes both `repo_a` and `repo_b`'s commits — proving `stacks`-scoped commits ≠ commits actually mutated by `process`.

    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
