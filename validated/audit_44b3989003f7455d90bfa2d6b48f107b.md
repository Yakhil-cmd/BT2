### Title
Webhook signature verification org is not bound to the acted-upon repository, allowing cross-organization event forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
### Finding Description
Shipit supports multi-organization deployments where each GitHub organization has its own `webhook_secret` [1](#0-0) , resolved via `Shipit.github(organization:)` which looks up `github_app_config(organization)` keyed by the organization name [2](#0-1) .

`WebhooksController#verify_signature` selects which organization's secret to validate the HMAC signature against using `repository_owner`, which is read straight from the attacker-controlled JSON payload (`repository.owner.login`, or falling back to `organization.login`): [3](#0-2) 

Once the signature is accepted, the raw `params` (the same JSON payload) are dispatched unchanged to event handlers. Those handlers determine which `Repository`/`Stack` to act on using a **different** field of the same payload — `repository.full_name` — with no cross-check against the `repository_owner` value that was actually used to select the verifying secret: [4](#0-3) [5](#0-4) 

`Repository.from_github_repo_name` simply splits `owner/name` and does a direct lookup with no additional binding back to which webhook secret authenticated the request: [6](#0-5) .

This is the same class of bug as the reported voting-power issue: a value used to make the trust/authorization decision (`repository_owner`, which selects the HMAC secret) is not the same value that is subsequently acted upon (`repository.full_name`, which selects the repository/stack to mutate). The equality the code implicitly assumes — `organization that authenticated == organization owning the repository written` — is never enforced.

**Attack surface:** In a multi-org configuration, the operator of Org A's own GitHub App knows Org A's `webhook_secret` (they configured it when registering their App with Shipit). An attacker who legitimately controls Org A (an unprivileged actor with respect to Org B, no Shipit session or GitHub App private key needed) can:
1. Craft a webhook payload with `repository.owner.login = "orgA"` (satisfies `repository_owner`, so `Shipit.github(organization: "orgA")`'s `webhook_secret` is used) and correctly HMAC-sign it with that known secret.
2. Set `repository.full_name = "orgB/private-repo"` inside the same JSON body.
3. POST it to `/webhooks`. `verify_signature` succeeds because it only checks the org derived from `repository.owner.login`/`organization.login`, using a secret the attacker legitimately possesses.
4. The dispatched handler (e.g. `PushHandler`) looks up the stack via `repository.full_name`, resolving to Org B's repository/stack, and triggers `stack.sync_github` — enqueuing a `GithubSyncJob` that will fetch commits and act on Org B's stack using Shipit's own GitHub App credentials for Org B.

### Impact Explanation
This breaks the binding "organization that authenticated" == "repository that is written," letting a legitimate Org A webhook holder forge events (`push`, `status`, `check_suite`, `pull_request`, `membership`, etc.) targeting an unrelated Org B's stacks/repositories they have no access to. Depending on the handler, this can cause spurious commit ingestion, false CI/deployability status, membership/team mutation, or triggering of `sync_github` against another organization's repository — a cross-repository/cross-organization write performed with Shipit's own credentials on behalf of an org the attacker does not control. This matches the "cross-repository writes" Critical-impact class in scope.

### Likelihood Explanation
Requires only that the deployment use the documented multi-organization `github:` configuration (explicitly supported and documented, e.g. `config/secrets.development.shopify.yml`, `docs/setup.md`) and that the attacker be a legitimate operator/owner of at least one configured organization (able to know its own `webhook_secret`, which they set up themselves). No Shipit session, `ApiClient` token, or GitHub App private key is required — only knowledge of a secret the attacker legitimately possesses for their own org.

### Recommendation
After verifying the signature, re-derive the repository/stack strictly from the same organization value used to select the verifying secret (`repository_owner`), and reject or ignore events where `repository.full_name`'s owner segment does not match `repository_owner`. Alternatively, look up the `Repository`/`Stack` scoped to the verified organization instead of trusting `full_name` independently in `Handler#stacks`.

### Proof of Concept
1. Configure Shipit with two organizations, `orgA` and `orgB`, each with distinct `webhook_secret`s (as in `config/secrets.development.shopify.yml`).
2. As the legitimate admin of `orgA` (knows `orgA`'s `webhook_secret`), craft a push payload:
```json
{
  "ref": "refs/heads/main",
  "after": "deadbeef",
  "repository": {
    "owner": { "login": "orgA" },
    "full_name": "orgB/private-repo"
  }
}
```
3. Compute `X-Hub-Signature: sha1=<hmac-sha1(orgA_webhook_secret, body)>`.
4. POST to `/webhooks` with header `X-Github-Event: push`.
5. `verify_signature` resolves `repository_owner` = `"orgA"`, verifies successfully against `orgA`'s secret [7](#0-6) .
6. `PushHandler#stacks` resolves the target via `payload.dig('repository', 'full_name')` = `"orgB/private-repo"` [8](#0-7) , and `sync_github` is enqueued against Org B's stack — despite the request never being authenticated by Org B's secret.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping
      head(:ok) if event == 'ping'
    end

    def event
      request.headers.fetch('X-Github-Event')
    end

    def repository_owner
      # Fallback to the organization sub-object if repository isn't included in the payload
      params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
    end

# frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
    end
  end
end
