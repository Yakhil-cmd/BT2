### Title
ERC20 XCM Transactor trusts attacker-controlled contract return value instead of verifying actual balance delta - ([File: cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs])

### Summary
`ERC20Transactor::withdraw_asset_with_surplus` and `ERC20Transactor::deposit_asset_with_surplus` in `assets-common` (wired into Asset Hub Westend per `prdoc/stable2506/pr_7762.prdoc`) credit or debit XCM's `AssetsInHolding` register purely based on the boolean return value decoded from a `bare_call` to an arbitrary, attacker-deployable smart contract's `IERC20::transfer` function. Neither function checks the actual ERC20 balance of the checking account (or origin) before/after the call. This is the same root-cause pattern as the Allo.sol report: an amount is credited to internal accounting because an externally-controlled contract call "reported success," not because a balance was verifiably moved.

### Finding Description
`Matcher::matches_fungibles` resolves any XCM asset of the form `{parents:0, interior: X1(AccountKey20{key, network})}` to `key` as an arbitrary `H160` contract address [1](#0-0) . The `key` is fully attacker-controlled: any user can deploy a `pallet-revive` contract implementing (or merely mimicking) the `IERC20` interface and reference it in an XCM program via that address, exactly as documented in `prdoc/stable2506/pr_7762.prdoc` ("asset ids ... will be matched by this transactor and the corresponding `transfer` function will be called in the smart contract whose address is `key`").

In `withdraw_asset_with_surplus`, the transactor calls `transfer(checking_address, amount)` as the origin, and if the call does not revert, decodes the boolean return value; on `true` it unconditionally mints `AssetsInHolding` credit of `amount` via `Erc20Credit`: [2](#0-1) 

Similarly, `deposit_asset_with_surplus` calls `transfer(beneficiary, amount)` from the `TransfersCheckingAccount`, and treats a `true` return as proof the deposit succeeded: [3](#0-2) 

At no point does either function read `balanceOf(checking_account)` (or `balanceOf(beneficiary)`) before and after the call to confirm that `amount` actually moved, unlike the pattern used elsewhere in the same codebase for asset-conversion pool transfers, which explicitly check the actual transferred amount against the requested amount (`ensure!(balance1 == T::Assets::transfer(...))`) [4](#0-3) . A contract whose `transfer()` function is written to always `return true` without moving any real ERC20 balance (an EVM analog of the report's malicious `receive()` that silently redirects funds) will cause the XCM executor to believe `amount` was legitimately withdrawn into (or deposited out of) the holding register, when in fact the checking account's real token balance never changed.

### Impact Explanation
This breaks the fundamental invariant that `AssetsInHolding` — the XCM executor's internal ledger of assets currently "in flight" during program execution — accurately reflects value actually backed by a real balance movement, exactly as `poolAmount` was falsely incremented in the original report without the strategy holding real funds. Because the holding register is subsequently usable within the same XCM program (e.g., for `DepositAsset`, `BuyExecution`, or reserve-transfer instructions), phantom credit created this way can be redirected to other beneficiaries or asserted as a legitimate asset elsewhere in the executor without a corresponding real debit ever having occurred in the checking account. This is a violation of the "amount actually transferred must equal amount accounted" invariant, the same missing check identified in the report's recommendation (compare balances before/after instead of trusting the callee).

### Likelihood Explanation
The entry point requires no privileged role: any signed account can (a) deploy an arbitrary contract via `pallet-revive`, and (b) submit an XCM program (via `pallet_xcm::execute` or a local transact/reserve instruction routed through the configured `XcmExecutor`) referencing that contract's address as an `AccountKey20` asset id. Both preconditions are ordinary, permissionless user actions on Asset Hub Westend once this transactor is enabled in its `xcm_config.rs`.

### Recommendation
Mirror the fix recommended in the original report and already used elsewhere in this codebase (`asset-conversion/ops`): before crediting/debiting `AssetsInHolding`, read `IERC20::balanceOf` for the relevant account before and after the `bare_call`, and only credit/report success for the amount by which the balance actually changed, rejecting (or truncating to) any mismatch rather than trusting the decoded boolean return value alone.

### Proof of Concept
I was not able to complete a full, executed reproduction within the available investigation budget. What is confirmed by static inspection:
- `ERC20Transactor` is real production code, present in `assets-common` and wired into `asset-hub-westend-runtime` per `prdoc/stable2506/pr_7762.prdoc`.
- The matcher and transfer call sites shown above contain no balance-delta verification, only trust in the decoded ERC20 return value, confirmed by reading the full transactor implementation.
- I could not, in the remaining time, confirm (a) the exact `xcm_config.rs` wiring point where `ERC20Transactor` is inserted into the `AssetTransactors` tuple on Asset Hub Westend, (b) whether reserve-transfer/teleport filters (`IsReserve`/`IsTeleporter`) would allow this asset class to move cross-chain (which would be needed to escalate this into cross-chain unbacked issuance rather than an in-message accounting inconsistency), or (c) whether a downstream consumer of `AssetsInHolding` (e.g. fee payment, reserve deposit) can be reached with the phantom credit before the program ends. These require a running integration-test harness (`emulated-integration-tests-common` style setup with `pallet-revive` contract deployment) to demonstrate end-to-end, which I could not execute in this session.

Given this gap, I am reporting the confirmed missing-invariant defect (unverified trust in an attacker-controlled contract's reported success) as the demonstrable analog, but flag that the full cross-chain/loss-of-funds escalation chain is **not verified** and would need a live Devin session with build/test execution to confirm reachability and quantify concrete loss (severity should be reassessed once that reachability is confirmed — treat as a plausible High rather than a fully proven Critical).
