### Title
Missing frame-blocking on `MergeStatusController#show` enables clickjacking of the merge-queue "Add to merge queue" action - (File: app/controllers/shipit/merge_status_controller.rb)

### Summary
`#show` explicitly sets `X-Frame-Options: ALLOWALL` [1](#0-0)  and the action is exempted from authentication for GET requests [2](#0-1) , which lets any page frame the merge-status widget for a logged-in operator. However, the actual enqueue action is a `PUT` guarded by Rails' `protect_from_forgery with: :exception` inherited from `ShipitController` [3](#0-2) , and clickjacking (unlike CSRF) causes the victim to click on the genuine, framed page rather than forge a cross-origin request — so CSRF protection does not block it, since the request/CSRF token originates from the real, framed Shipit page itself.

### Finding Description
Binding claimed broken: `merge_request enqueued by #enqueue == merge_request the operator consciously chose to enqueue`.

Trace:
- `GET /merge_status?stack_id=<victim_stack>&referrer=<victim_pr_url>` resolves `stack` via `Stack.from_param!` and `merge_request` via the `referrer` param parsed by `ReferrerParser` [4](#0-3) .
- The response sets `X-Frame-Options: ALLOWALL` before rendering [1](#0-0) , and the action skips authentication for `show`/`check` [2](#0-1) . If the user isn't logged in, it renders `logged_out`; if they are, it renders the widget with an "Add to merge queue" button pointing at `enqueue_merge_request_path` (`PUT /merge_status/*stack_id/pull/:number`).
- An attacker embeds this URL in an `<iframe>` sized/positioned under a decoy UI element on an attacker page, luring a logged-in operator to click through to the real button rendered in the frame (classic clickjacking). Because the frame contains the genuine Shipit page served with the operator's real session cookie and the real embedded CSRF token, the resulting `PUT` request is a legitimate, correctly-CSRF-tokened request from the browser's perspective — `protect_from_forgery` does not detect or prevent this, because that protection only guards against forged cross-origin requests, not visually-hijacked genuine same-origin clicks.
- `#enqueue` then calls `MergeRequest.request_merge!(stack, params[:number], current_user)` [5](#0-4)  using the `number` baked into the route by whatever PR/URL the attacker chose for the iframe, using the operator's authenticated `current_user` identity.

Existing guards checked: `protect_from_forgery` is present [3](#0-2)  but does not stop clickjacking as explained above. No `X-Frame-Options: DENY/SAMEORIGIN` or `Content-Security-Policy: frame-ancestors` restriction exists anywhere for this controller — the header is explicitly set to permit framing from any origin. There is no additional confirmation step (e.g., re-auth, distinct token) between viewing the widget and submitting the `PUT`.

### Impact Explanation
A successful clickjack causes `MergeRequest.request_merge!` to enqueue an attacker-chosen pull request into a real merge queue using a legitimate operator's authenticated session — i.e., an unauthorized merge-queue enqueue action performed by/through a victim's identity for a PR the victim never intended to select. This is scoped to the merge-queue-enqueue action on stacks the operator already has access to (it does not escalate privileges beyond what the operator's session can already do), but it does let the attacker force that operator's session into queuing an attacker-controlled PR, matching the "unauthorized... merge" impact category. It is repeatable against any stack/PR combination the attacker can construct a valid GitHub PR URL for, and reusable per victim visit to the malicious page.

### Likelihood Explanation
Preconditions: the operator must be logged into Shipit, must visit an attacker-controlled page while authenticated (session cookie present), and must be tricked into clicking through an overlay positioned over the iframe’s "Add to merge queue" button at pixel-precise coordinates — a nontrivial but standard clickjacking UI/UX challenge (target coordinates depend on rendered layout, button state (`queue_enabled?`), and browser). No secrets are required. Feasibility is real (no framing controls whatsoever are applied by this action), but the attack is a UI-based social/interaction attack requiring precise victim behavior, not a purely mechanical HTTP replay — so exploitation requires successful clickjacking execution against a specific, authenticated operator, not one arbitrary click.

### Recommendation
Set `X-Frame-Options` to `SAMEORIGIN` (or remove the `ALLOWALL` override entirely so the application's default frame policy applies) and/or add a `Content-Security-Policy: frame-ancestors 'self'` header for `MergeStatusController#show`, if third-party framing (e.g., a browser extension shown in `contrib/browser-extension`) is not required. If framing must be supported for a legitimate embedding use case, restrict `frame-ancestors` to a known allowlist rather than `ALLOWALL`, and require an explicit user-driven confirmation (e.g., a same-page click plus a fresh, single-use action token) before executing `MergeRequest.request_merge!` for the queue-add action, so a hijacked click alone cannot trigger the state-changing PUT.

### Proof of Concept
Minitest plan (controller/integration test, no live GitHub, under `test/` — for reference only, since `test/**` files are out of scope for this audit but describe the mechanics):
1. Integration test: `get :show, params: { stack_id: stack.to_param, referrer: "https://github.com/#{repo.owner}/#{repo.name}/pull/1" }` while `current_user` is authenticated; assert `response.headers['X-Frame-Options'] == 'ALLOWALL'` (not `DENY`/`SAMEORIGIN`).
2. Controller test: `put :enqueue, params: { stack_id: stack.to_param, number: attacker_chosen_number }` as the authenticated operator; assert `MergeRequest.request_merge!` is invoked with `attacker_chosen_number` regardless of whether that number matches any PR the operator viewed/intended, demonstrating the enqueue action has no binding to operator intent beyond the raw route parameter.     def show
```ruby
      response.headers['X-Frame-Options'] = 'ALLOWALL'
      response.headers['Vary'] = 'X-Requested-With'

      if stack
        return render('logged_out') unless current_user.logged_in?

        if stale?(last_modified: [stack.updated_at, merge_request.updated_at].max, template: false)
          render(stack_status, layout: !request.xhr?)
        end
      else
        render(html: '')
      end
    rescue ArgumentError
      render(html: '')
    end

    def enqueue
      MergeRequest.request_merge!(stack, params[:number], current_user)
      render(stack_status, layout: !request.xhr?)
    end
```
