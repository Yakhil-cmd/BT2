### Title
Webhook signature verification is bound to `repository.owner.login` while all handlers act on the unverified `repository.full_name`, allowing cross-organization payload forgery - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/handler.rb`, `lib/shipit.rb`)

### Summary
In multi-organization Shipit deployments, `WebhooksController#verify_signature` selects which GitHub App secret to use for HMAC verification based on an **unverified** field of the incoming JSON body (`repository.owner.login`, falling back to `organization.login`), then verifies the signature over the *entire* raw body with that secret. Every webhook handler, however, resolves the target `Repository`/`Stack` using a *different* field of that same unverified body: `repository.full_name`. Because the field used to pick the verification key and the field used to pick the acted-upon repository are independent and both attacker-supplied, an attacker who legitimately controls the webhook secret for **any one** organization configured in Shipit can forge a request whose signature validates against their own org's secret while `repository.full_name` points at a completely different, victim organization's repository.

### Finding Description
`WebhooksController#verify_signature` does:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) 

`Shipit.github(organization:)` looks up a distinct `webhook_secret` per organization when Shipit is configured with `Using Multiple Github Applications`, as documented and tested: [2](#0-1) [3](#0-2) 

Once the signature check passes (using OrgA's secret because `repository.owner.login == "OrgA"`), the actual event handlers never re-check that binding. Instead they resolve the target repository purely from `repository.full_name`:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [4](#0-3) 

The `Repository.from_github_repo_name` lookup only matches on this field, independent of the org used to authenticate: [5](#0-4) 

The binding that should hold is: `organization used to authenticate the payload == organization that owns the repository the handler subsequently mutates`. Nothing enforces `repository.owner.login == repository.full_name.split('/').first`, so an attacker can set them to different values in the same JSON body.

### Impact Explanation
An attacker who administers their own GitHub App installed on `OrgA` (a legitimate, low-privilege organization also configured in the same Shipit instance) knows `OrgA`'s `webhook_secret` because they created it. They can POST directly to Shipit's `/webhooks` endpoint (no GitHub involvement needed) with:
- `repository.owner.login = "OrgA"` (so the signature check uses OrgA's secret, which they control and can compute correctly)
- `repository.full_name = "OrgB/victim-repo"` (a repository belonging to a completely different, victim organization they have no access to)

Handlers such as `PushHandler` will then call `stack.sync_github(expected_head_sha: ...)` on the victim's stack with an attacker-chosen `after` SHA, and PR-event handlers (`OpenedHandler`, `ClosedHandler`, `ReopenedHandler`, `LabelCapturingHandler`, etc.) can archive/unarchive/create review stacks or otherwise mutate state for `OrgB`'s repositories/stacks — all triggered by forged data whose signature never actually vouched for `OrgB`. This is a cross-repository, cross-organization write achieved without ever possessing the victim organization's credentials, which is exactly the kind of trust-binding break the deployment platform relies on the webhook signature to prevent.

### Likelihood Explanation
This requires the Shipit instance to be configured for multiple GitHub organizations (an explicitly documented and supported configuration, see `docs/setup.md` "Using Multiple Github Applications"), and requires the attacker to control at least one of those configured organizations' own GitHub App/webhook secret — which they legitimately possess for their own org. No access to the victim org's secret, private key, or any Shipit account is needed. Given multi-tenant Shipit deployments servicing several orgs, this is a realistic configuration and a realistic attacker (any org admin sharing the Shipit instance).

### Recommendation
After signature verification succeeds, `WebhooksController`/`Handler` should validate that the organization derived from `repository.full_name` (and `organization.login` where present) matches the `repository_owner` value that was used to select the verifying `webhook_secret`, rejecting the request (422) on mismatch. Alternatively, verify the signature independently per-organization for every configured org and require the resolved repository's owner to match the org whose secret validated.

### Proof of Concept
1. Configure Shipit with two organizations, `OrgA` and `OrgB`, each with a distinct `webhook_secret` (as documented in `docs/setup.md`), and add a `Repository`/`Stack` for `OrgB/victim-repo`.
2. As an attacker who owns the GitHub App/webhook secret for `OrgA` only, craft a `push` payload:
```json
{
  "ref": "refs/heads/main",
  "after": "deadbeef...attacker_chosen_sha",
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/victim-repo" }
}
```
3. Compute `X-Hub-Signature: sha1=HMAC_SHA1(OrgA_webhook_secret, raw_body)`.
4. POST to `/webhooks` with header `X-Github-Event: push`.
5. `verify_signature` reads `repository_owner == "OrgA"`, fetches `Shipit.github(organization: "OrgA")`, and the signature validates successfully.
6. `PushHandler#process` resolves `repository_name == "OrgB/victim-repo"` via `Handler#repository_name`, finds the victim's `Stack`, and enqueues `stack.sync_github(expected_head_sha: "deadbeef...")` — a forged sync/deploy trigger against a repository the attacker never authenticated for.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
