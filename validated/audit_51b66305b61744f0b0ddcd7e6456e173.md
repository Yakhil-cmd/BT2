### Title
Webhook signature verification selects the GitHub App/secret from an unauthenticated field while handlers act on a different, unverified field — cross-organization webhook forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks *which* GitHub App config (and therefore which `webhook_secret`) to validate the HMAC signature against based on `repository_owner`, a value read straight out of the still-unauthenticated JSON body. Once the HMAC check passes, every registered `Shipit::Webhooks` handler is invoked with the full, attacker-supplied `params` hash, and those handlers resolve the *target* repository from a **different** field of the same body (`repository.full_name`). In a multi-organization Shipit deployment, an attacker who legitimately controls a webhook secret for one onboarded organization can use that secret to sign a payload whose `repository.owner.login` matches "their" org (so the correct secret is selected and the HMAC passes) while `repository.full_name` names a repository belonging to a completely different organization. The engine binds the wrong pair of values: the organization whose secret authenticated the request vs. the repository the handlers actually write.

### Finding Description
The signature-verification flow is: [1](#0-0) 

`repository_owner` is derived purely from the JSON body before any cryptographic check occurs: [2](#0-1) 

`Shipit.github(organization: repository_owner)` looks up the `GithubApp`/`webhook_secret` configured for that named organization (Shipit explicitly supports one config per GitHub org, as shown by the multi-org fixture): [3](#0-2) 

The HMAC is computed with that chosen secret over the *entire* raw body: [4](#0-3) 

Once verification succeeds, the raw parsed body is dispatched unchanged to all handlers: [5](#0-4) 

Handlers determine the target `Stack`/`Repository` using a **separate** key of that same JSON body — `repository.full_name` — not `repository.owner.login`: [6](#0-5) 

Because HMAC signing is over the raw bytes and not over a canonicalized/consistent identity, nothing prevents `repository.owner.login` and `repository.full_name` from disagreeing. An attacker who is an admin of Organization B (and therefore legitimately possesses Org B's `webhook_secret`, because they configured B's own GitHub webhook to point at the shared Shipit instance) can craft a payload with `repository.owner.login = "OrgB"` (so `Shipit.github(organization: "OrgB")` returns Org B's app/secret) and `repository.full_name = "OrgA/target-repo"`, then HMAC-sign that exact payload with Org B's secret. `verify_webhook_signature` succeeds — the signature is mathematically valid for the secret it was checked against — but the acted-upon repository (`OrgA/target-repo`) was never covered by any authentication tied to Org A.

This is the same class of defect as the reported bug: a downstream consumer (`Handler#repository_name`) trusts a payload field (`full_name`) that was never bound by the check that gated access (`verify_signature`'s use of `owner.login` to pick the secret). Just as the vesting-contract report found that `redeem` derived rewards from `msg.sender` instead of the value the protocol actually verified via `getAllocation`, here the controller "authenticates" one field (organization login) but the business logic acts on an unrelated field (full repo name) from the same unauthenticated body.

### Impact Explanation
Any handler registered for GitHub events becomes forgeable across organization boundaries in a multi-org Shipit deployment, as long as the attacker controls a legitimate webhook secret for *any one* onboarded organization on that instance. This includes:
- `push` events, which enqueue `GithubSyncJob` and can move a stack's tracked ref/state for a repository the attacker doesn't own,
- `status`/`check_suite` events, which write commit statuses used to gate deploy eligibility for another org's repository,
- `pull_request`/`membership` events, which create/mutate `Team`/`User`/`MergeRequest` records tied to another org's repo.

Forged status/check events feeding into deploy-gating logic can lead to an unauthorized deploy being triggered for a repository the attacker does not control — this matches the "unauthorized deploy" High/Critical impact category.

### Likelihood Explanation
Exploitability is conditioned on the host running a multi-organization Shipit deployment (an explicitly supported, documented configuration per `secrets_double_github_app.yml`/`secrets.development.example.yml`), and on the attacker holding legitimate admin rights over the webhook configuration of at least one of the onboarded organizations — a realistic scenario where a shared Shipit instance serves several orgs with independent GitHub admins. No token, session, or Shipit account is required; only knowledge of a webhook secret the attacker is entitled to configure for their own org.

### Recommendation
Bind the organization used to select the verification secret to the same identity used by handlers to resolve the target repository. Concretely, derive `repository_owner` and the repository/`full_name` consistently from a single canonical source, and after selecting the app/secret, assert that `repository.full_name`'s owner segment matches the `repository_owner` used for verification (reject the webhook with 422 otherwise) before invoking any handler.

### Proof of Concept
1. Configure Shipit with two organizations, `OrgA` and `OrgB`, each with its own `webhook_secret` (as supported by `Shipit.github(organization:)`).
2. As an attacker who administers `OrgB` (and thus knows/controls `OrgB`'s `webhook_secret` because they can configure GitHub webhooks for their own org), build a `push` payload:
   ```json
   {
     "repository": {
       "owner": { "login": "OrgB" },
       "full_name": "OrgA/target-repo"
     },
     "after": "<attacker chosen sha>"
   }
   ```
3. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(OrgB_webhook_secret, raw_body)>`.
4. POST to `/github/webhooks` (per `Shipit::WebhooksController#create`) with `X-Github-Event: push`.
5. `verify_signature` calls `Shipit.github(organization: "OrgB")` and the HMAC check passes (it is legitimately signed with `OrgB`'s secret over this exact body).
6. `Shipit::Webhooks.for_event('push')` handlers run using `payload.dig('repository','full_name') == "OrgA/target-repo"`, causing `GithubSyncJob` to act on `OrgA/target-repo` — a repository never authenticated by the request's signature.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
