### Title
Unhandled `throw Error()` in the AA formula interpreter causes an uncaught exception on malformed/edge-case expressions - (File: `formula/evaluation.js`)

### Summary
`formula/evaluation.js`'s `evaluate()` function — the actual runtime interpreter for oscript/AA formulas — uses raw `throw Error(...)` as its fallback error path for "should never happen" conditions (unrecognized ops, unexpected value types after evaluation), instead of the safe `setFatalError()`/`cb()` error-propagation pattern used everywhere else in the same function. [1](#0-0) [2](#0-1) [3](#0-2) 

This mirrors the libpcap BPF-interpreter bug class: a well-formed grammar-level filter/opcode reaches an "impossible" branch of the interpreter and the process `abort()`s instead of gracefully rejecting the input.

### Finding Description
`formula/validation.js` is the static verifier for oscript formulas (analogous to a BPF verifier): its own `evaluate()` switch statement is designed to reject invalid/unknown constructs *safely*, returning an error string through `cb(...)` rather than throwing. [4](#0-3) 

`formula/evaluation.js`'s `evaluate()` is the actual interpreter (analogous to the BPF interpreter) that runs the same AST when an AA trigger is executed, an AA response formula is composed, or a state/getter formula is evaluated. Unlike the validator, several of its internal branches use `throw Error(...)` directly for conditions that are supposed to be guaranteed unreachable by prior validation — for example the `default` case of the whole op-dispatch `switch` (`unrecognized op`), and type-narrowing branches inside `substring`/`has_only` handling that throw if a previously-evaluated value doesn't match an expected JS type. [5](#0-4) [6](#0-5) 

Because `evaluate()` is deeply recursive and asynchronous (calls itself through `async.eachSeries`/`async.forEachOfSeries` callbacks and `setImmediate` for stack-depth mitigation), a `throw` executed from inside one of these nested callbacks is **not** synchronously catchable by the caller (`exports.evaluate`, `aa_composer.js handleTrigger`, etc.). It escapes as an unhandled exception in an async callback context, which in Node.js becomes an uncaught exception rather than a value returned through the normal `ifUnitError`/`ifTransientError` validation callback machinery used elsewhere in `validation.js`. [7](#0-6) 

This is architecturally the same class of bug as CVE-2026-31911: a "verifier"-checked input still causes the "interpreter" to hit a hard-coded fatal condition, because the two code paths (verifier vs. interpreter switch statements) are maintained as two independently-written, hand-synchronized copies of the same grammar dispatch, exactly as libpcap's BPF verifier and interpreter can drift out of sync on which opcodes are considered valid.

### Impact Explanation
If a code path exists where `formula/validation.js` accepts a formula/value combination that `formula/evaluation.js` does not have a corresponding safe branch for (or where a value computed during evaluation legitimately produces a JS type the type-narrowing branches don't anticipate), any AA whose definition includes that formula will crash the evaluating node's process when a trigger unit reaches that AA. Since AA execution happens on every full node that processes the DAG, a trigger unit posted by any user (unprivileged unit poster / AA trigger sender) that reaches this branch would crash all full nodes simultaneously when they attempt to determine AA responses/stability for that unit, producing either a persistent crash loop for nodes trying to reprocess the same MC point, or divergent behavior between nodes that crash vs. nodes that don't reach the code (e.g. due to differing cached parser results), which can manifest as node disagreement on AA response validity/stability, satisfying the "node unable to confirm new units" impact bar.

### Likelihood Explanation
Exploitability strictly depends on finding a concrete op/value combination that passes `formula/validation.js`'s switch but lands on a `throw` in `formula/evaluation.js`'s switch. I was not able to fully enumerate and diff every `case` in both 250+ branch switch statements within the available search budget, so I cannot certify a specific triggering formula exists. The finding is a genuine structural weakness (safe-verifier vs. throwing-interpreter asymmetry) but concrete reachability of a specific throwing branch from attacker-controlled formula/trigger data needs deeper manual/differential analysis of `formula/validation.js` vs `formula/evaluation.js` case-by-case.

### Recommendation
Replace all internal `throw Error(...)` fallback paths inside `formula/evaluation.js`'s `evaluate()` (and any nested op-specific switches such as `has_only`/`substring`) with `setFatalError(...)`-based safe error propagation, matching the pattern already used for all other error conditions in that function, so that any parser/validator drift degrades to a rejected/failed AA execution rather than an uncaught process exception. Additionally, add a differential test that walks every `case` label present in `formula/validation.js` and asserts an equivalent `case` exists in `formula/evaluation.js` (and vice versa) to prevent future drift between the two switch statements.

### Proof of Concept
Not able to construct a concrete triggering formula within the current investigation; would require an exhaustive case-by-case diff of `formula/validation.js` (~1500+ lines) against `formula/evaluation.js` (~2800+ lines) to find a validator-accepted / interpreter-throwing mismatch, which is recommended as a follow-up deep-dive (e.g. in a full Devin session with repo access) rather than something confirmable through the indexed search alone.
