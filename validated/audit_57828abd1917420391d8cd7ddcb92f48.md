### Title
Unbounded `ENV` fallback in `EnvironmentVariables#interpolate` leaks host process secrets into task output - ([File: lib/shipit/command.rb])

### Summary
`Command#interpolate_environment_variables` delegates to `EnvironmentVariables#interpolate`, which resolves any `$WORD` token found in a `shipit.yml` step by first checking the task's merged `env` hash and, if absent, falling back to `ENV[variable]` — the Shipit host process's own OS environment — with no whitelist check. Since step strings originate from the deploy spec (`deploy_spec.deploy_steps`/`rollback_steps`/`dependencies_steps`, i.e. `shipit.yml` in the target repository), a pull request author can inject a token name that is never defined in `stack.env`, `deploy_spec.machine_env`, or `task.env` and have it resolved from the Shipit process's environment instead, echoing it into task output.

### Finding Description
The broken binding: the set of names resolvable through `EnvironmentVariables#interpolate`'s `@env.fetch(variable) { ENV[variable] }` should equal the set of names explicitly permitted for that context (as enforced by `EnvironmentVariables#permit`'s `variable_definitions` whitelist, used for `deploy_variables`/`rollback_variables` in `app/models/shipit/deploy_spec.rb#filter_deploy_envs`/`filter_rollback_envs`), but `interpolate` never calls or checks against `permit`: [1](#0-0) 

`Command#interpolate_environment_variables` invokes `EnvironmentVariables.with(env).interpolate(argument)` for every argument of every step, and `interpolated_arguments` is called right before `PTY.spawn`: [2](#0-1) [3](#0-2) 

Steps themselves come from `TaskCommands#perform`, which builds `Command.new(command_line, env:, chdir:)` from `@task.definition.steps`, ultimately sourced from the deploy spec parsed out of `shipit.yml` in the PR's working tree: [4](#0-3) 

Attack: an unprivileged contributor opens a PR that edits `shipit.yml` to add a step such as `echo $GITHUB_TOKEN` (or any other name present in Shipit's own OS `ENV`, e.g. `AWS_SECRET_ACCESS_KEY`), a name intentionally never added to `stack.env`, `machine_env`, or `task.env`. When any task on that stack is run, `interpolate` fails the `@env.fetch` lookup and falls back to `ENV[variable]`, substituting the literal secret value into the command's argv before shell-escaping and spawning, so it appears verbatim in the task's captured output stream that the PR author can view.

Existing guards do not stop this: `EnvironmentVariables#permit` (the whitelist mechanism) is applied only to `deploy_variables`/`rollback_variables` supplied via HTTP parameters (`filter_deploy_envs`/`filter_rollback_envs` in `app/models/shipit/deploy_spec.rb`), not to step interpolation. `interpolate` has no such enforcement at all.

### Impact Explanation
If the Shipit host process holds sensitive tokens in its OS environment (e.g., `GITHUB_TOKEN`, cloud credentials), any contributor able to modify `shipit.yml` for a stack and trigger a task can exfiltrate that secret into the visible task log. This is repeatable per stack/task run and is not limited to a single repository if the same host process env is shared across multiple stacks — i.e., a secret intended to be scoped to Shipit's internal operation becomes readable by any PR author with step-editing capability on any stack served by the same Shipit instance. This matches the "exfiltration of deploy-time secrets" Critical category.

### Likelihood Explanation
Requires: (1) attacker can modify `shipit.yml` for the target stack (i.e., can open/merge or otherwise get a step definition executed — typical for `dependencies`/`deploy`/`rollback`/custom task steps), (2) the targeted secret name exists in Shipit's own process `ENV` (feasible for `GITHUB_TOKEN`, `BUNDLE_*`, or other credentials commonly exported to the app process), and (3) the attacker can trigger the corresponding task. No Shipit session, API token, or GitHub secret is needed — only the ability to influence the executed step text and cause it to run, which is inherent to how Shipit executes deploy/task steps defined in-repo. This is a low-cost, straightforward text edit in a config file.

### Recommendation
Restrict `EnvironmentVariables#interpolate` to only resolve variables present in the already-merged, explicitly-trusted `env` hash (`stack.env`, `deploy_spec.machine_env`, `task.env`) and drop the `ENV[variable]` fallback entirely, or route it through the same whitelist mechanism as `permit`. At minimum, never fall back to the full process `ENV`; unresolved variables should either raise or be left as an empty string.

### Proof of Concept
```ruby
# test/unit/environment_variables_test.rb (additional test)
test 'interpolate must not leak host process ENV for undeclared variables' do
  ENV['GITHUB_TOKEN'] = 'super-secret-token'
  begin
    result = EnvironmentVariables.with({}).interpolate('echo $GITHUB_TOKEN')
    # Binding under test: EnvironmentVariables#interpolate resolvable-name-set
    # should equal EnvironmentVariables#permit's variable_definitions name-set (here: empty).
    # Before: falls back to ENV, so result contains the secret.
    refute_includes result, 'super-secret-token'
  ensure
    ENV.delete('GITHUB_TOKEN')
  end
end
```
This test currently fails against the existing implementation, demonstrating that `interpolate` admits `ENV` values outside any declared whitelist, unlike `permit`, which would raise `EnvironmentVariables::NotPermitted` for the same undeclared name.

    def interpolate(argument)
      return argument unless @env

      argument.gsub(/(\$\w+)/) do |variable|
        variable.sub!('$', '')
        Shellwords.escape(@env.fetch(variable) { ENV[variable] })
      end
    end
