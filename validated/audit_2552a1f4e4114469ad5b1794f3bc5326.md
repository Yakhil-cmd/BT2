### Title
Webhook signature is verified against the payload's `repository.owner.login` but event handlers dispatch on `repository.full_name`, allowing cross-organization stack sync/deploy triggers - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects the GitHub App/webhook secret to validate the HMAC signature using `repository_owner`, a field parsed independently from the JSON body [1](#0-0) . But the actual event handlers (e.g. `PushHandler`) resolve which `Stack`/`Repository` to act on using a *different* field of the same payload, `repository.full_name` [2](#0-1) [3](#0-2) . Nothing binds these two fields together, so the organization whose secret authenticated the request is not guaranteed to be the organization that owns the repository actually written to.

### Finding Description
Shipit explicitly supports multi-tenant configuration where multiple independent GitHub organizations, each with its own `webhook_secret`, are configured and dispatched through the same `/webhooks` endpoint (`Shipit.github(organization: ...)`), as documented in `docs/setup.md` [4](#0-3) .

The signature-verification code picks the verifying secret from the payload's `repository.owner.login` (or `organization.login`): [5](#0-4) 

Once verification succeeds, the raw JSON `params` are handed unchanged to `Shipit::Webhooks.for_event(event)` handlers: [6](#0-5) 

Every handler, however, looks up the target repository/stack from a *different* JSON key — `repository.full_name` — rather than `repository.owner.login`: [2](#0-1) 

For example `PushHandler#process` calls `stack.sync_github(expected_head_sha: params.after)` for every stack whose repository matches `repository.full_name`: [3](#0-2) 

Because HMAC-SHA1 signs raw bytes without any semantic binding between `owner.login` and `full_name`, an org that legitimately controls its own webhook secret (i.e., an org onboarded to this Shipit instance, who therefore knows/owns the secret Shipit computed the signature with) can craft an arbitrary payload where:
- `repository.owner.login` = their own org (so `Shipit.github(organization: repository_owner)` picks their own configured secret, and the HMAC check passes), while
- `repository.full_name` = `"victim-org/victim-repo"` (an entirely different, unrelated stack/repository managed by the same Shipit instance).

`stacks` in `Handler` is resolved purely from `full_name`: [7](#0-6) 

This lets the request pass signature verification under org A's identity while acting on org B's `Stack`, invoking `GithubSyncJob`, which uses **Shipit's own GitHub App credentials for the target stack's org** to fetch commits and append them to the victim stack, potentially detaching/rewriting reachable commit history and re-caching the deploy spec: [8](#0-7) 

If the victim stack has `continuous_deployment` enabled, appending attacker-chosen "new commits" (subject to what GitHub's API returns for that repo, but the *timing/trigger* is fully attacker controlled) can force an unauthorized sync/deploy cycle. Other handlers (`Handlers::PullRequest::*`, `CheckSuiteHandler`) exhibit the same pattern — they authenticate via `repository.owner.login`/`organization.login` and act on `repository.full_name`, which is never cross-checked against the authenticated organization.

### Impact Explanation
This breaks the trust binding: **organization that authenticated (via webhook secret) ≠ repository that is written to**. An attacker who legitimately administers one onboarded GitHub organization's webhook (an "unprivileged" party from Shipit's perspective — no Shipit session, ApiClient token, or GitHub App private key required) can force sync/deploy-trigger side effects on stacks belonging to a completely unrelated organization also hosted by the same Shipit instance. This matches the report's root cause exactly: a validity check (`verify_signature`/allocation cap check) that does not account for the full state (accumulated allocation / actual repository acted upon) before permitting the downstream effect. The impact reaches "unauthorized deploy" territory for continuous-deployment-enabled stacks (Critical) and, at minimum, unauthorized cross-organization mutation of commit/stack state (High).

### Likelihood Explanation
Requires the deployment to be configured for multiple GitHub organizations (a documented, supported configuration) and requires the attacker to control the webhook secret of at least one onboarded organization — which is a normal, expected capability of any org administrator who set up that org's GitHub App/webhook pointing at the shared Shipit instance. No compromise of Shipit credentials, sessions, or the victim org's secrets is needed.

### Recommendation
Bind the field used for signature-key selection to the field used for repository/stack resolution. Concretely, in `Shipit::Webhooks::Handlers::Handler#repository_name` (and all direct-access `repository.full_name` usages), verify that the owning organization of `repository.full_name` (i.e., the first path segment) equals the organization used in `WebhooksController#verify_signature` (`repository_owner`), and reject (422) the request otherwise. Alternatively, pass the already-resolved/authenticated organization from the controller into the handler context and have handlers scope `Repository`/`Stack` lookups to that organization instead of trusting `full_name` from the payload independently.

### Proof of Concept
1. Configure Shipit (per `docs/setup.md`) with two organizations, `attacker-org` and `victim-org`, each with its own `webhook_secret`, both with stacks tracked by this Shipit instance.
2. As the (legitimate) owner/admin of `attacker-org`'s GitHub App/webhook configuration, craft a POST to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. Compute `X-Hub-Signature` as `sha1=HMAC-SHA1(attacker-org_webhook_secret, raw_body)` — a secret the attacker legitimately possesses.
4. `verify_signature` calls `Shipit.github(organization: "attacker-org")` and validates successfully [9](#0-8) .
5. `PushHandler` resolves stacks via `repository.full_name` = `"victim-org/victim-repo"` [2](#0-1)  and calls `stack.sync_github(expected_head_sha: ...)` on the victim's stack — triggering `GithubSyncJob` using Shipit's `victim-org` GitHub App credentials, entirely outside the attacker's authorization scope [10](#0-9) .

Note: I was not able to fully trace every downstream handler's exact deploy-trigger side effects (e.g., whether `continuous_deployment` auto-triggers a deploy synchronously from `sync_github` versus requiring a separate cron/condition) within the available index; a Devin session with full repository access is recommended to confirm the exact automatic-deploy trigger chain from `Stack#sync_github` through to `Deploy` creation for continuous-deployment-enabled stacks.

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```

```ruby
    def perform(params)
      @stack = Stack.find(params[:stack_id])
      expected_head_sha = params[:expected_head_sha]
      retry_count = params[:retry_count] || 0
      head_before_sync = spec_cache_target
      appended_commits = []

      handle_github_errors do
        new_commits, shared_parent = fetch_missing_commits { stack.github_commits }

        # Retry on Github eventual consistency: webhook indicated new commits but we found none
        if expected_head_sha && new_commits.empty? && !commit_exists?(expected_head_sha) &&
           retry_count < MAX_RETRY_ATTEMPTS
          GithubSyncJob.set(wait: RETRY_DELAY * retry_count).perform_later(params.merge(retry_count: retry_count + 1))
          return
        end

        stack.transaction do
          shared_parent&.detach_children!
          appended_commits = new_commits.map do |gh_commit|
            append_commit(gh_commit)
          end
          stack.lock_reverted_commits! if appended_commits.any?(&:revert?)
        end
      end
      sync_changed_nothing = appended_commits.empty? &&
                             spec_cache_target == head_before_sync &&
                             stack.cached_deploy_spec.present?
      return if sync_changed_nothing && !params[:force_spec_cache]

      CacheDeploySpecJob.perform_later(stack)
    end
```
