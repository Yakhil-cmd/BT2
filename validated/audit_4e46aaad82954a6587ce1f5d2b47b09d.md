### Title
Webhook signature verification keyed on attacker-controlled `repository.owner.login`/`organization.login` while handlers act on the unrelated `repository.full_name` field, allowing cross-organization webhook forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/webhook secret to validate the HMAC signature against by reading `repository_owner`, a field taken directly from the untrusted, attacker-supplied JSON body. All downstream webhook handlers, however, resolve the target `Stack`/`Repository`/`Commit` using a *different* field of that same untrusted body: `repository.full_name`. Nothing binds these two fields together, so a payload can pass signature verification "as organization A" while acting on a stack that belongs to organization B.

### Finding Description
`verify_signature` looks up the GitHub App config to use for HMAC verification using a value pulled straight out of the incoming (unauthenticated) request body: [1](#0-0) [2](#0-1) 

`repository_owner` is `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` — both attacker-controlled. The signature check only proves the request was signed with *some* org's configured `webhook_secret`; it never proves that the org whose secret matched is the org that actually owns the repository the payload claims to describe.

Once signature verification passes, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` dispatches the full (still attacker-controlled) JSON to handlers: [3](#0-2) 

Every handler resolves its target `Stack`/`Repository` from `payload.dig('repository', 'full_name')` — a field distinct from the one used for signature verification: [4](#0-3) 

For example, `PushHandler` uses this `stacks` helper to find and mutate real stacks via `stack.sync_github`: [5](#0-4) 

And the `status`/commit-status webhook flow creates a `Status` on a commit resolved independently of the org used for signing, as shown by the controller's own test suite: [6](#0-5) 

This is exactly the bug class described in the report: a value is verified/authenticated (there, an in-memory `from` balance key; here, `repository_owner`) but a *different* key/field (there, the `to` balance; here, `repository.full_name`) is the one actually written/acted upon, with no cross-check tying the two together.

Shipit explicitly supports hosting multiple GitHub organizations, each with its own independently-configured `webhook_secret`: [7](#0-6) 

Any organization/GitHub App owner who is a legitimate (even low-privilege, unrelated) tenant of the same Shipit instance knows their own App's `webhook_secret` (they set it when creating the App) and can freely POST directly to the public `/webhooks` endpoint (no Shipit session, no GitHub delivery required — Shipit doesn't validate source IP or a GitHub delivery ID). By setting `repository.owner.login`/`organization.login` to their own org (so `verify_signature` selects and validates against their own known secret) while setting `repository.full_name` to a victim stack's `owner/repo`, they craft a validly-signed webhook that manipulates a stack they do not own.

### Impact Explanation
This breaks the equality "organization that authenticated == repository that is written." Concretely, an attacker who controls one org onboarded to a shared Shipit instance can:
- Force `PushHandler`/`GithubSyncJob` to run against a victim stack, and
- Inject fabricated commit `Status`/check results (per the `status` webhook flow) attributed to a victim's real commits.

Since Shipit's CI gating (`ci.require`) and merge-queue gating rely on commit statuses/checks recorded through this same webhook path, forging these for a victim repository can be used to mark required checks as passing on commits the attacker does not control, which can lead to an unauthorized deploy or merge being permitted by Shipit's automation — matching the "unauthorized deploy, rollback, or merge" Critical impact category. I could not fully trace `StatusHandler`'s exact commit-status write logic within the remaining investigation budget, so this specific escalation path (status forgery → bypassed CI gate → unauthorized deploy/merge) is inferred from the test coverage and CI-gating documentation rather than a line-by-line trace of `status_handler.rb`; this should be independently confirmed before triage.

### Likelihood Explanation
Exploitation only requires being any legitimate (even unrelated) multi-tenant GitHub organization/App admin on the shared Shipit instance — no access to the victim org, no Shipit session, and no privileged Shipit account are required, satisfying the "unprivileged attacker" constraint. The request is a simple, directly-craftable HTTP POST to the public `/webhooks` endpoint.

### Recommendation
In `WebhooksController#verify_signature`, after selecting the GitHub App/secret via `repository_owner` and verifying the signature, additionally verify that `repository_owner` matches the owner segment of `params.dig('repository', 'full_name')` (and reject/short-circuit otherwise). Equivalently, have handlers resolve the target stack using the same organization identity that was cryptographically verified, rather than trusting `repository.full_name` independently.

### Proof of Concept
1. Attacker owns/administers GitHub organization `attacker-org`, which has its own GitHub App installed on the shared Shipit instance with a webhook secret `S` (chosen by the attacker at App-creation time, per `docs/setup.md`'s multi-org config).
2. Attacker crafts a JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(S, body)>` using their own known secret `S`.
4. Attacker POSTs this to `/webhooks` with header `X-Github-Event: push`.
5. `WebhooksController#verify_signature` resolves `repository_owner` → `"attacker-org"`, fetches `Shipit.github(organization: "attacker-org")`, and the signature validates successfully against `S`.
6. `PushHandler` is invoked and resolves `stacks` via `payload.dig('repository', 'full_name')` → `"victim-org/victim-repo"`, matching real victim stacks and calling `stack.sync_github(expected_head_sha: ...)` on a stack the attacker does not own.

          requires :after
