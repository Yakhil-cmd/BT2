### Title
`update_pool_rewards` stores unclamped `current_block_number` as `last_update_block`, causing a permanent arithmetic underflow that blocks `unstake`/`harvest_rewards`/`stake` after pool expiry - ([File: substrate/frame/asset-rewards/src/lib.rs])

### Summary
`pallet-asset-rewards` implements a Synthetix-style `reward_per_token` / `periodFinish`-analog mechanism (`expiry_block` capping accrual, similar in spirit to Tokemak's `periodInBlockFinish`). Unlike the Tokemak report's root cause (an admin lowering `durationInBlock`), here the SDK code already blocks rate/expiry decreases [1](#0-0) [2](#0-1) . However, the same class of bug (an unclamped counter compared against a fixed cap, producing a checked-subtraction underflow) is reachable through the ordinary `stake`/`unstake`/`harvest_rewards` extrinsics once a pool naturally expires, with no privileged action required.

### Finding Description
`reward_per_token` clamps the "now" used for reward accrual to `expiry_block` via `last_block_reward_applicable`, then computes elapsed blocks as `last_block_reward_applicable(expiry_block).ensure_sub(pool_info.last_update_block)` [3](#0-2) [4](#0-3) .

However, `update_pool_rewards`—called by `stake`, `unstake`, and `harvest_rewards` via `update_pool_and_staker_rewards` before every operation—unconditionally stores the *real*, unclamped `current_block_number()` into `last_update_block`, not the capped value used for the reward math: [5](#0-4) 

Consequence: the **first** extrinsic call that happens after `expiry_block` has passed succeeds (it computes `elapsed = expiry_block - last_update_block` correctly, since the stored `last_update_block` was still `<= expiry_block` from before expiry) but then overwrites `last_update_block` with `now`, which is now strictly greater than `expiry_block`. On the **second** such call (by the same or any other staker doing `stake`/`unstake`/`harvest_rewards`), `reward_per_token` computes `last_block_reward_applicable(expiry_block) = expiry_block` (since `now` only grows) and then `expiry_block.ensure_sub(last_update_block)` where `last_update_block > expiry_block`, which triggers an arithmetic underflow and returns `Err(ArithmeticError::Underflow)`, propagated as the call's `DispatchError` [6](#0-5) .

This is a direct analog to the report's root cause: a fixed boundary (`periodInBlockFinish`/`expiry_block`) is compared against a monotonically-increasing counter (`block.number`/`last_update_block`) with no guarantee that the counter stays bounded by the boundary, and `ensure_sub`/raw subtraction underflows, reverting the caller. The Tokemak report's issue was triggered by an admin decreasing `durationInBlock`; here it's triggered organically by the passage of time past `expiry_block` combined with `update_pool_rewards`'s failure to clamp the stored block. No privileged role or governance action is required — any staker calling `stake`, `unstake`, or `harvest_rewards` after expiry (permitted for non-staker callers too once `now > expiry_block`, per the `ensure!(now > pool_info.expiry_block || caller == staker, BadOrigin)` checks in `unstake`/`harvest_rewards`) triggers the second, failing call [7](#0-6) [8](#0-7) .

### Impact Explanation
Once triggered, every subsequent `stake`, `unstake`, and `harvest_rewards` call on that pool permanently fails with an underflow error, because `last_update_block` can never be reset back below `expiry_block` (the pool's `expiry_block` can only be *increased* by the admin, and increasing it far enough to exceed the already-inflated `last_update_block` is the only recovery path, which requires trusting/relying on the admin to act, and is not guaranteed). This would freeze already-staked tokens (frozen via `AssetsFreezer`) and lock unharvested rewards indefinitely for that pool — an irreversible or governance-dependent freezing of user funds, matching the "DOS/no new rewards" impact class from the source report, but here the frozen funds are staker funds/rewards, which is a more severe consequence than the disallowed reward queuing in the original report.

### Likelihood Explanation
High likelihood in practice: this triggers deterministically for **any** pool once it passes `expiry_block` and receives two ordinary interactions afterward (e.g., two different stakers harvesting rewards, or a staker withdrawing in two calls) with no attacker privilege, stolen keys, or governance action needed. Pools with a finite `expiry_block` (the common case; `DispatchTime::At` or `After`) will hit this window inevitably unless the admin actively (and repeatedly) extends the expiry to outpace real time, which is not enforced by the protocol.

### Recommendation
In `update_pool_rewards`, store the *reward-applicable* (clamped) block number, not the raw current block number:
```rust
new_pool_info.last_update_block = Self::last_block_reward_applicable(pool_info.expiry_block);
```
This keeps `last_update_block <= expiry_block` invariant, matching what `reward_per_token` assumes, and prevents the underflow for all future calls after expiry.

### Proof of Concept
I could not execute a live Rust/FRAME test in this environment (read-only ask-mode, no build/test execution available), so this cannot be reported as a confirmed, run PoC. Based on static code tracing, a reproduction would be:
1. `create_pool` with `expiry = DispatchTime::At(E)`.
2. `stake` some tokens for staker A before `E` (sets `last_update_block <= E`).
3. Advance block number past `E` (e.g., to `E + k`).
4. Call `harvest_rewards`/`unstake` once — succeeds, but sets `last_update_block = E + k` (unclamped).
5. Advance a further block and call `harvest_rewards`/`unstake`/`stake` again — expect `Err(ArithmeticError::Underflow)` from `ensure_sub` in `reward_per_token`, because `expiry_block (E) < last_update_block (E+k)`.

This matches the existing test file's patterns (`extends_reward_accumulation`, `success_signed_admin`, etc.) in `substrate/frame/asset-rewards/src/tests.rs` [9](#0-8) , but none of the existing tests perform two consecutive mutating calls (`stake`/`unstake`/`harvest_rewards`) strictly after `expiry_block`, so this specific double-call-after-expiry underflow path does not appear to be covered by current tests — this should be verified with an actual test run in a full development environment before being treated as fully confirmed.
