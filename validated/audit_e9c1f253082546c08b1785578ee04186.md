### Title
Webhook signature is authenticated against `repository.owner.login`, but the target `Stack` is resolved from the unrelated `repository.full_name` field, allowing cross-organization writes - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects the GitHub App/webhook secret to validate an inbound webhook using `repository_owner`, which is read straight out of the (still-unverified-at-that-point) JSON body: `params.dig('repository', 'owner', 'login')`, falling back to `params.dig('organization', 'login')`. Once the HMAC check passes with that org's secret, the entire raw body — including the completely independent `repository.full_name` field — is handed to `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`. Every handler (`Handler#stacks`) resolves the target `Stack` via `Repository.from_github_repo_name(repository_name)` where `repository_name = payload.dig('repository', 'full_name')`, never checking that this value belongs to the organization that was actually authenticated. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
Shipit supports hosting multiple GitHub organizations with distinct GitHub Apps/webhook secrets, each configured under `secrets.github.<org>` [4](#0-3) . The equality the design implicitly relies on is:

`organization authenticated by HMAC (repository.owner.login) == organization that owns the repository actually written to (repository.full_name)`

This equality is never enforced anywhere in the request pipeline. `verify_signature` only proves that *some* field of the JSON body (`repository.owner.login`/`organization.login`) names an org whose secret was used to sign the raw body [5](#0-4) . It does not prove anything about `repository.full_name`, which is a sibling field in the same attacker-controlled JSON document and can be set to any value independent of `repository.owner.login`.

Any party that legitimately controls a GitHub App/webhook installed on **any one** organization configured in Shipit (e.g. their own low-privilege org "attacker-org") knows that org's `webhook_secret` and can compute a valid `X-Hub-Signature` over an arbitrary JSON payload. They can craft a body such as:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>",
  "repository": {
    "full_name": "victim-org/victim-repo",
    "owner": { "login": "attacker-org" }
  }
}
```
`repository_owner` resolves to `attacker-org`, so `Shipit.github(organization: 'attacker-org')` is used and the signature check succeeds using the attacker's own secret [6](#0-5) . The payload is then dispatched unmodified to handlers, which look up the target stacks purely by `repository.full_name`, i.e. `victim-org/victim-repo`, with no cross-check against `attacker-org` [3](#0-2) [7](#0-6) .

This is directly analogous to the Rolla report's bug class: a trust boundary (here, "which org authenticated this request") is established over one field, while the write operation acts on a sibling field that was never bound to that authentication.

### Impact Explanation
This crosses the "cross-repository writes" boundary explicitly called out as Critical impact:
- `PushHandler` enqueues `stack.sync_github(expected_head_sha:)` for any non-archived stack on `victim-org/victim-repo`'s branch, letting the attacker force a specific (attacker-chosen) `expected_head_sha` sync against a stack they do not control [7](#0-6) .
- `StatusHandler` and `CheckSuiteHandler` allow forging CI status/check-run state for a victim's commits/stacks, which downstream deploy-safety checks (e.g. "deployable" gating before a ship) rely on [8](#0-7) [9](#0-8) . Forged green statuses/check-runs can unlock an unauthorized deploy on a stack belonging to an organization the attacker never authenticated as.

### Likelihood Explanation
Exploitability requires the attacker to control at least one org/webhook secret configured in the same Shipit instance (a multi-tenant deployment scenario the engine explicitly supports via `github.<org>.webhook_secret`). This is a realistic scenario for any Shipit instance shared across multiple orgs/teams, where one org's operators are lower-trust than another's — no GitHub write access, `ApiClient` token, or session is required, only knowledge of one legitimate webhook secret they were issued.

### Recommendation
In `WebhooksController#verify_signature`/`repository_owner`, and in `Handler#stacks`/`repository_name`, enforce that the organization used to select the webhook secret is the same organization implied by `repository.full_name` (i.e., require `repository.full_name.split('/').first == repository.owner.login` before dispatching, and reject/422 on mismatch). Alternatively, resolve the target `Stack`/`Repository` first, look up the owning organization from the stored repository record, and use that organization's secret for verification, rather than trusting an unverified field in the same payload.

### Proof of Concept
1. Attacker legitimately installs/owns a GitHub App on `attacker-org`, configured in `secrets.github.attacker-org.webhook_secret`.
2. Attacker crafts a `push` event JSON body with `repository.full_name = "victim-org/victim-repo"` and `repository.owner.login = "attacker-org"`, and `after` set to an arbitrary sha.
3. Attacker computes `X-Hub-Signature: sha1=<hmac(attacker-org secret, raw_body)>` and POSTs to `/webhooks`.
4. `verify_signature` resolves `repository_owner` to `"attacker-org"`, fetches that org's `GitHubApp`, and the HMAC check passes [1](#0-0) .
5. `PushHandler` resolves stacks via `Repository.from_github_repo_name("victim-org/victim-repo")` and calls `stack.sync_github(expected_head_sha: <attacker sha>)` on a stack the attacker never authenticated for [3](#0-2) [7](#0-6) .

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
