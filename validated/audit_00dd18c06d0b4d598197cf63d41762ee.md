## Title
AA evaluation of `data_feed[[...]]` can consume price/oracle values from not-yet-stable, provisional (`sequence === 'good'`) units, allowing non-deterministic/manipulable results before oracle data is final - (File: `data_feeds.js`, `formula/evaluation.js`)

### Summary
The Perennial report shows the Vault trusting an oracle's `latestPrice` (an unconfirmed/instantaneous value) instead of a settled one for irreversible collateral moves. Ocore has a structurally identical pattern: when an Autonomous Agent (AA) evaluates a `data_feed[[...]]` formula, the engine is allowed to source the feed value not only from finalized (stable) data feeds, but also from data-feed messages belonging to units that have **not yet stabilized** on the main chain, i.e., are still provisional.

### Finding Description
`formula/evaluation.js` computes `bAA` and forwards it directly as the `unstable_opts` argument to `dataFeeds.readDataFeedValue`: [1](#0-0) 

Inside `readDataFeedValue`, when `unstable_opts` is truthy, the function scans `storage.assocUnstableMessages` — units that are **not yet part of the stable DAG** — and accepts any data-feed message whose containing unit currently has `sequence === 'good'`: [2](#0-1) 

`sequence === 'good'` is only a provisional classification. The stabilization logic explicitly acknowledges that a unit's final sequence can still resolve to `'final-bad'` once the DAG is finalized, at which point any of its unstable messages (including `data_feed`) are simply discarded and never committed: [3](#0-2) [4](#0-3) 

Because an AA's `data_feed[[...]]` call can read this transient, not-yet-final state, and because different full nodes execute the AA trigger asynchronously (as soon as *their own* view of the DAG makes the trigger's MCI stable), two honest nodes can observe **different sets of currently-unstable-but-"good"** data-feed candidates for the same `feed_name` at the moment they run the AA formula — depending on which additional (still-unstable) units from the oracle they happen to have received by then. The `readDataFeedValue` candidate-selection/sort logic even acknowledges the ambiguity of multiple "good" pre-final candidates: [5](#0-4) 

This mirrors the reported bug class exactly: a critical financial decision inside a contract (AA) is made using a value that has not achieved the protocol's actual finality guarantee, and that value can still change (or vanish entirely, if the source unit turns `final-bad`) before it is truly settled.

### Impact Explanation
An AA that uses `data_feed[[...]]` to compute payout amounts, asset-issuance ratios, or exchange rates (a pattern explicitly used in ocore's own sample AAs, e.g. `GBYTE_USD_MA` exchange-rate contracts) can execute an irreversible `payment`/`asset` message based on a value that:
1. Was never actually finalized (the source unit later becomes `final-bad`), meaning the AA's committed state was derived from data that officially never existed on the ledger, or
2. Different full nodes could, in principle, observe a different transient value at the moment of AA execution for the same feed/trigger, risking disagreement on the resulting AA state/balance across nodes.

Either outcome can translate into fund loss/freezing for AA participants (payouts computed from a repudiated price) or a node-consensus divergence about the correctness of the resulting response unit — both are impacts explicitly in scope.

### Likelihood Explanation
Exploitation only requires an unprivileged party to control (or collude with) the "oracle" address referenced by the target AA and to time-post a data-feed update immediately before/alongside a trigger to that AA, relying on the window between "unstable but sequence=good" and true stabilization. No special network position, hub/peer privilege, or protocol-level access is required — only normal unit posting.

### Recommendation
Restrict `data_feed[[...]]` (and `in_data_feed`) evaluation inside AA formulas to only stable, fully-finalized data feeds (i.e., drop the `unstable_opts`/`bAA` fast-path in `readDataFeedValue` for price-bearing lookups, or require `min_mci` combined with strict stability checks) so that AA execution is always deterministic and based on values that cannot later be discarded as `final-bad`.

### Proof of Concept
1. AA `X` is defined with `oracles = ORACLE_ADDR` and a formula such as `data_feed[[oracles=ORACLE_ADDR, feed_name='rate']]` used to compute a payout/exchange amount, as illustrated in ocore's own sample: [6](#0-5) .
2. `ORACLE_ADDR` (attacker-controlled) posts a `data_feed` unit with a favorable `rate`, but the unit has not yet stabilized (`sequence` still provisional `'good'`).
3. Attacker immediately posts a trigger to AA `X`. Because AA formula evaluation calls `dataFeeds.readDataFeedValue(..., bAA, ...)` with `unstable_opts=bAA=true`, the still-unstable rate is picked up (`data_feeds.js:211-224`) and used to compute an irreversible payment.
4. If the DAG later resolves the oracle's unit as `final-bad` (e.g. due to a conflicting parallel unit), `main_chain.js` deletes/ignores that data feed entirely (`main_chain.js:1554-1563`) — yet AA `X` has already executed and paid out based on a rate that never became part of the finalized ledger, and other nodes evaluating the trigger at a different instant may have seen a different candidate value.
