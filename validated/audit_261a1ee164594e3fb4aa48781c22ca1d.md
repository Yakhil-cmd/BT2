## Finding

### Title
Webhook signature verification selects the signing organization from an unverified field, letting one org's webhook secret authorize forged events for any other org's repositories - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` picks which GitHub App/organization secret to use for HMAC verification from a field taken out of the *unverified* raw JSON body, while the downstream event handlers select which repository/stacks to mutate from a *different* field of that same unverified body. Nothing ties these two fields together, so a caller who legitimately knows one organization's webhook secret (e.g. an admin of an org configured on a shared, multi-tenant Shipit instance) can forge a correctly-signed payload whose "acted-upon" repository belongs to a different organization/stack entirely.

### Finding Description
`verify_signature` derives the signing organization straight from the attacker-controlled body, before the signature has been checked: [1](#0-0) [2](#0-1) 

`Shipit.github(organization: repository_owner)` looks up the `GitHubApp`/`webhook_secret` for that organization, and `verify_webhook_signature` just checks the HMAC of the raw body against that specific secret: [3](#0-2) 

Shipit explicitly supports hosting multiple GitHub organizations behind one instance, each with its **own independent** `webhook_secret`: [4](#0-3) [5](#0-4) 

Once the signature check passes, every event handler is dispatched with the same parsed body and resolves its target `stacks`/repository from a *separate* JSON key — `repository.full_name` — which is never cross-checked against `repository_owner`: [6](#0-5) 

For example the `status` handler applies an arbitrary commit status to any commit matching a `sha`, using only the top-level `sha`/`state` fields, with no organization/repository binding at all: [7](#0-6) 

and the `push` handler similarly resolves stacks purely by branch name within `stacks`, which itself is scoped only by `Repository.from_github_repo_name(payload.dig('repository','full_name'))`: [8](#0-7) 

**The broken binding:** `repository_owner` (used to pick the *signing/authenticating* organization) should equal the owner of `repository.full_name` (the *repository actually written to*), but this equality is never enforced. An attacker who knows Organization A's `webhook_secret` (as its GitHub App admin — a privilege external to Shipit itself, not a Shipit session/token/credential) can HMAC-sign a raw body directly against `/github_webhooks` (bypassing GitHub) with:
- `repository.owner.login = "OrgA"` (satisfies `verify_signature`, since it picks OrgA's real secret)
- `repository.full_name = "OrgB/victim-repo"` (used by every `Handler` to select the target stacks)

Because the signature only certifies "this body's bytes were HMAC'd with OrgA's secret," not "this body only describes OrgA's repositories," the forged event is accepted and dispatched against OrgB's stacks.

### Impact Explanation
This is a genuine cross-repository/cross-organization confused-deputy write, matching the report's "field acted on but never covered by the verified signature" bug class:
- `status` events let the attacker inject arbitrary CI status for any commit sha across any stack in the shared instance, which drives Shipit's continuous-deployment/merge-queue gating (`Commit#create_status_from_github!` → `add_status` → `stack.schedule_merges`), enabling unauthorized deploy/merge triggering for repositories the attacker does not own.
- `push` events force `GithubSyncJob` re-syncs on arbitrary victim stacks.
- `pull_request opened/closed/labeled` events can archive, unarchive, or provision review stacks belonging to other organizations.

This satisfies the "Critical: cross-repository writes / unauthorized deploy" bar since it lets a party with only one organization's webhook secret manipulate stacks belonging to a different organization hosted on the same Shipit deployment.

### Likelihood Explanation
Requires: (1) a Shipit deployment configured for multiple GitHub organizations (an explicitly documented, supported configuration), and (2) the attacker controlling/knowing the webhook secret of at least one of those organizations (e.g., as that org's own GitHub App administrator) — no Shipit session, ApiClient token, or GITHUB_TOKEN is needed. Given multi-tenant setups are a first-class documented use case, this is realistically reachable.

### Recommendation
In `WebhooksController#verify_signature` / `Handler`, require that the organization used to select the verifying secret matches the owner of `repository.full_name` used by the handlers (e.g., derive both from the same normalized value and reject if they mismatch, or scope handler repository lookups by the same `repository_owner` value that was cryptographically bound to the signature).

### Proof of Concept
1. Configure Shipit with two organizations, `OrgA` and `OrgB`, each with distinct `webhook_secret`s (per `docs/setup.md`'s multi-org schema).
2. As an attacker who knows `OrgA`'s webhook secret (e.g., its GitHub App admin), craft a `status` event JSON body:
```json
{
  "sha": "<victim commit sha belonging to an OrgB stack>",
  "state": "success",
  "repository": { "full_name": "OrgB/victim-repo", "owner": { "login": "OrgA" } }
}
```
3. Compute `X-Hub-Signature: sha1=<hmac-sha1(OrgA_webhook_secret, body)>` locally.
4. POST this body directly to `/github_webhooks` with header `X-Github-Event: status`.
5. `verify_signature` calls `Shipit.github(organization: "OrgA")` (from `repository.owner.login`) and successfully verifies the signature using OrgA's secret.
6. `Shipit::Webhooks::Handlers::StatusHandler` processes the event and calls `Commit.where(sha: params.sha)`, applying the forged status to the victim commit belonging to `OrgB`'s stack — even though the signature never certified anything about `OrgB`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
    end
  end
end
