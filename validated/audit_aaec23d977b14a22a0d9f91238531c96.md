### Title
Unauthenticated `sender` spoofing in `TransferStxOp` allows theft of arbitrary Stacks address's STX via self-crafted `PreStxOp`/`TransferStxOp` pair - (File: stackslib/src/chainstate/burn/operations/transfer_stx.rs)

### Summary
`TransferStxOp::parse_from_tx` assigns the `sender` field directly from the caller-supplied `pre_stx.output` value, and `classify_transaction` in `stackslib/src/burnchains/burnchain.rs` passes that value straight from the previously-parsed `PreStxOp` with no check that it corresponds to any Bitcoin key that actually authorized the spend. Since a `PreStxOp` is a transaction fully controlled and signed by whoever broadcasts it, the broadcaster can set `output` to any arbitrary `StacksAddress` (a victim's address) and later spend the `PreStxOp`'s second output themselves to mint a `TransferStxOp` that debits the victim.

### Finding Description
The equality that should hold is: *the Stacks address debited by `TransferStxOp` (`sender`) must equal an address whose private key authorized the Bitcoin spend that produced the op* — i.e., `sender == owner_of(pre_stx_output_utxo)`. Instead, the code establishes: `sender == pre_stx.output`, a field written into the `PreStxOp` wire data by whoever constructs that transaction, with no cryptographic binding to the UTXO's actual controlling key.

Concretely:
- `classify_transaction` resolves the `TransferStxOp`'s `sender` purely from the antecedent `PreStxOp`: `let sender = &pre_stx.output; TransferStxOp::from_tx(block_header, burn_tx, sender)` [1](#0-0) .
- `TransferStxOp::parse_from_tx` simply clones this parameter into `sender` on the resulting op, and derives `recipient` from the first output of the *current* Bitcoin transaction (fully attacker-chosen) [2](#0-1) .
- The only follow-up structural checks are `get_sender_txid`, which merely enforces that the `TransferStxOp` transaction's first input spends vout `1` of the referenced `PreStxOp` txid [3](#0-2) , and `TransferStxOp::check()`, which only validates `transfered_ustx != 0` and `sender != recipient` [4](#0-3) . Neither check verifies that the entity spending the `PreStxOp`'s second output (i.e., the entity who actually pays Bitcoin fees and controls the input key) is the same entity whose Stacks address was written into `pre_stx.output`.

Because a `PreStxOp` is broadcast entirely by the attacker (their own Bitcoin inputs, their own chosen `output` field, their own second output which they later spend), the attacker fully controls both halves of the link: they set `output` to a victim's `StacksAddress` and they alone hold the key to spend the second UTXO to build the `TransferStxOp`. There is no signature, script, or address-derivation check anywhere in this path that ties `pre_stx.output` to the Bitcoin key spending the second output. Downstream, `process_transfer_ops` in `stackslib/src/chainstate/stacks/db/blocks.rs` takes the op's `sender`/`recipient` at face value and calls `tx.run_stx_transfer(&sender, &recipient, transfered_ustx, ...)`, moving real STX balance from the victim's account without any Stacks-transaction signature from the victim.

### Impact Explanation
An attacker can drain the unlocked STX balance of any Stacks address for the cost of two low-value Bitcoin transactions (the `PreStxOp` and the spend of its second output), with `recipient` set to an address they control. This is repeatable against any victim address with a positive unlocked STX balance, for as long as the attacker can fund the two Bitcoin transactions (their own UTXOs, no victim cooperation or signature required). This matches the Critical severity bucket: theft of STX belonging to a party who never authorized the transfer.

### Likelihood Explanation
No privileged role, no chain-of-custody assumptions, and no cooperation from the victim are required — the attacker only needs their own funded Bitcoin UTXOs and knowledge of the victim's `StacksAddress` (public knowledge for any account with an on-chain balance). The attack is a straightforward two-transaction Bitcoin sequence and requires no special mempool timing or miner cooperation, making it highly feasible if the guards described above do not exist elsewhere in the pipeline.

### Recommendation
Bind `PreStxOp.output` (or a newly added field) cryptographically to the actual signer/spender of the `PreStxOp`'s inputs — e.g., require it to equal the address derived from the `PreStxOp` transaction's own input signer (`tx.get_signer()`), and additionally require that the `TransferStxOp`/`StackStxOp` transaction's own input signer matches that same address before honoring `sender`. This closes the gap between "who chose the sender label" and "who actually controls the spend."

### Proof of Concept
Rust integration test outline (chainstate/coordinator harness, similar to existing tests in `stackslib/src/chainstate/coordinator/tests.rs`):
1. Fund a victim Stacks address `V` with STX via a normal genesis/faucet allocation; record `balance_before(V)`.
2. As the attacker, using attacker-owned Bitcoin keys/UTXOs, broadcast a `PreStxOp` whose `output` field is set to `V` (not any address derived from the attacker's own signing key), with a second Bitcoin output funded by the attacker.
3. As the attacker, spend that second output to broadcast a `TransferStxOp` with `recipient = attacker_address` and `transfered_ustx = balance_before(V)`.
4. Run these through `classify_transaction`/`process_transfer_ops` on a booted chainstate.
5. Assert: `sender` on the resulting `TransferStxOp` equals `V`, and `balance_after(V) == balance_before(V) - transfered_ustx` and `balance_after(attacker) == balance_before(attacker) + transfered_ustx`, despite `V` never signing any Stacks transaction and never holding the private key spent to authorize the second Bitcoin output.

Note: I was unable to locate the source file defining `PreStxOp`/`PreStxOp::from_tx` (it did not resolve under the expected path in this index) to double-check whether `output` is derived from the `PreStxOp`'s own input-signer address rather than an arbitrary output address; if such a binding exists there, it would need to be checked against the `TransferStxOp`/`StackStxOp` spender as well, since none of the code inspected in `transfer_stx.rs` or `burnchain.rs` performs that cross-check.

    pub fn get_sender_txid(tx: &BurnchainTransaction) -> Result<&Txid, op_error> {
        match tx.get_input_tx_ref(0) {
            Some((ref txid, vout)) => {
                if *vout != 1 {
                    warn!(
                        "Invalid tx: TransferStxOp must spend the second output of the PreStacksOp"
                    );
                    Err(op_error::InvalidInput)
                } else {
                    Ok(txid)
                }
            }
            None => {
                warn!("Invalid tx: TransferStxOp must have at least one input");
                Err(op_error::InvalidInput)
            }
        }
    }

impl TransferStxOp {
    pub fn check(&self) -> Result<(), op_error> {
        if self.transfered_ustx == 0 {
            warn!("Invalid TransferStxOp, must have positive ustx");
            return Err(op_error::TransferStxMustBePositive);
        }
        if self.sender == self.recipient {
            warn!("Invalid TransferStxOp, sender is recipient");
            return Err(op_error::TransferStxSelfSend);
        }
        Ok(())
    }
}
