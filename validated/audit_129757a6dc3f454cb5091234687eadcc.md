### Title
`provision?` operator precedence bypasses `review_stacks_enabled` for label-based provisioning - (File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb)

### Summary
`provision?` intends `review_stacks_enabled` to gate all provisioning behaviors, but due to Ruby `&&`/`||` precedence, `review_stacks_enabled` only binds to the `allow_all?` clause. An attacker opening a PR on a repository with `review_stacks_enabled: false` and `provisioning_behavior: 'allow_with_label'` can attach a label matching `provisioning_label_name` and still trigger `ReviewStack` creation. The same bug is present in `reopened_handler.rb`'s `unarchive?`.

### Finding Description
The broken binding: the code intends `review_stacks_enabled == true` to be a precondition for **every** provisioning path, but the actual evaluated expression only requires `review_stacks_enabled == true` for the `allow_all?` path.

`provision?` is written as:
```ruby
repository.review_stacks_enabled &&
  repository.provisioning_behavior_allow_all? ||
  (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
  (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
``` [1](#0-0) 

Because `&&` binds tighter than `||` in Ruby, this parses as `(A && B) || (C && D) || (E && F)`, where `A = review_stacks_enabled`. `review_stacks_enabled` is only ANDed with `provisioning_behavior_allow_all?` (`B`); it has no effect on the `allow_with_label?`/`prevent_with_label?` branches. `pull_request_has_provisioning_label?` reads `pull_request_label_names`, sourced from `params.pull_request.labels`, which is attacker-controlled data from the PR payload/GitHub labels the attacker attaches to their own PR [2](#0-1) . `provisioning_label_name` is a repository setting exposed in `settings.html.erb`, so it's discoverable by anyone with read access to the repo's Shipit config [3](#0-2) .

For comparison, `LabeledHandler#respond_to_label_change?` correctly ANDs `review_stacks_enabled` across the whole expression as a separate top-level condition, showing the intended (and correct) gating pattern:
```ruby
params.action == "labeled" &&
  pull_request_state == "open" &&
  repository.review_stacks_enabled &&
  (archive? || unarchive?)
``` [4](#0-3) 

No other guard rescues this: `ReviewStackAdapter#find_or_create!`/`create!` does not re-check `review_stacks_enabled` before creating the stack and enqueuing provisioning [5](#0-4) . `Repository.review_stacks_enabled` is a plain boolean column with no validation tying it to `provisioning_behavior`, and `NullRepository` (used when the repo isn't registered) returns `false` for all these predicates so it can't be exploited for unregistered repos, but a legitimate repository configured with `review_stacks_enabled: false` and `provisioning_behavior: 'allow_with_label'` is exploitable [6](#0-5) .

Exploit flow: attacker forks/owns a repo registered in Shipit with `review_stacks_enabled: false, provisioning_behavior: allow_with_label`, reads `provisioning_label_name` from the repo's Shipit settings page, opens a PR and adds that exact label, GitHub emits a `pull_request opened` webhook (signed by GitHub, so signature validation passes normally since this is a real, legitimate webhook — no forgery required), `OpenedHandler#process` calls `provision?` which evaluates true despite `review_stacks_enabled` being false, and `ReviewStackAdapter#find_or_create!` creates a `ReviewStack` and enqueues it for provisioning.

The same flawed precedence pattern exists in `ReopenedHandler#unarchive?` [7](#0-6) .

### Impact Explanation
This causes unauthorized `ReviewStack` record creation and enqueues it into `Shipit::ReviewStackProvisioningQueue`, which drives downstream provisioning task execution for a repository whose maintainer explicitly disabled review stacks (`review_stacks_enabled: false`). This is a record/action created for a repository against the operator's explicit configuration intent, triggering task execution the maintainer did not authorize. It is repeatable for any PR the attacker opens on any repository configured this way, and scoped to repositories with this specific misconfiguration (`review_stacks_enabled: false` + `allow_with_label`/`prevent_with_label`), not a fully unauthenticated cross-tenant bypass.

### Likelihood Explanation
Requires a specific repository configuration: `review_stacks_enabled: false` combined with `provisioning_behavior` set to `allow_with_label` or `prevent_with_label`. Attacker cost is low — opening a PR and applying a label they can read the name of from the repo's own settings page, both actions available to any contributor able to open PRs with label permissions on their own fork/PR. No secrets, tokens, or privileged roles are needed. Feasibility is high once the configuration precondition holds; it's fully repeatable per PR.

### Recommendation
Add explicit parentheses so `review_stacks_enabled` gates the entire expression:
```ruby
def provision?
  repository.review_stacks_enabled &&
    (repository.provisioning_behavior_allow_all? ||
     (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
     (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?))
end
```
Apply the identical fix to `ReopenedHandler#unarchive?`.

### Proof of Concept
In `test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb` style:
1. Create a `Shipit::Repository` with `review_stacks_enabled: false`, `provisioning_behavior: 'allow_with_label'`, `provisioning_label_name: 'deploy-preview'`.
2. Build PR payload params with `action: 'opened'`, `pull_request.labels: [{name: 'deploy-preview'}]`.
3. Before fix: assert `repository.review_stacks_enabled == false` (left side of binding) yet `OpenedHandler.new(params).process` results in `repository.review_stacks.count == 1` (right side/actual effect) — demonstrating the binding "provisioning requires review_stacks_enabled" is broken.
4. After applying the parenthesization fix: assert `repository.review_stacks.count == 0` for the same payload.

          def archive!(*args, &block)
            if stack.blank?
              Rails.logger.info(
                "Processing #{action} event for #{repo_name} PR #{pr_number} but no Stack exists. Ignoring."
              )
              return true
            end
            return if stack.archived?

            stack.remove_from_provisioning_queue
            stack.deprovision
            stack.archive!(user, *args, &block)
          end

          def unarchive!(*args, &block)
            if stack.blank?
              Rails.logger.info(
                "Processing #{action} event for #{repo_name} PR #{pr_number} but no ReviewStack exists. Creating."
              )
              return create!
            end
            return unless stack.archived?

            stack.transaction do
              Shipit::ReviewStackProvisioningQueue.add(stack)
              stack.unarchive!(*args, &block)
            end
          end

          def user
            @user ||= Shipit::User.find_or_create_by_login!(params.sender["login"])
          end

          private

          attr_reader :params, :scope

          def action
            params.action
          end

          def repo_name
            params.repository["full_name"]
          end

          def pr_number
            params.number
          end

          end
