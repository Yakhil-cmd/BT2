# Multisig `validate_multisig_transaction` does not enforce that the approved on-chain payload is the payload actually executed (feature-gated / bypassable equality check) — (File: `aptos-move/framework/aptos-framework/sources/multisig_account.move`)

### Summary
The `0x1::multisig_account` module supports two flows for multisig execution: `create_transaction` (stores the **full payload** on-chain) and `create_transaction_with_hash` (stores only a **hash**). At execution time, `validate_multisig_transaction` is invoked as the VM prologue for `MultisigTransaction` and is the sole gate that checks that (a) enough owners approved and (b) the payload being executed matches what was approved. The hash-based path always enforces a match. The full-payload path, however, only enforces the match when a feature flag is enabled *and* the caller-supplied payload bytes are non-empty.

### Finding Description
`validate_multisig_transaction` in `aptos-move/framework/aptos-framework/sources/multisig_account.move` performs the quorum check unconditionally, but the on-chain payload consistency check for the "full payload stored" case is gated: [1](#0-0) 

Concretely:
- If `transaction.payload_hash` is set (hash-only flow), the equality check `sha3_256(payload) == *payload_hash` is unconditional — this is safe.
- If `transaction.payload` is set (the full-payload flow, from `create_transaction`), the equality check `payload == *stored_payload` **only fires when `features::abort_if_multisig_payload_mismatch_enabled()` is true and the caller-supplied `payload` argument is non-empty**.

This means:
1. When the feature is disabled, an executing owner can call the `MultisigTransaction` execution entry point with a `payload` argument that differs from the payload the other owners actually voted on and approved (`transaction.payload`), and `validate_multisig_transaction` will not reject it — only quorum/timelock is checked, not payload identity.
2. Even when the feature is enabled, supplying an **empty** `payload` bypasses the equality check entirely (`!payload.is_empty()` guard), regardless of feature state.

The admission invariant that breaks is the same class as the report's `stablecoin` binding bug: two related state components (the recorded/approved payload vs. the payload that is actually admitted for execution) are expected to always match, but the code path that is supposed to enforce that binding is conditionally skippable, so the executing party (who only needs to already be a quorum-satisfying owner, not a privileged admin) can decouple "what was approved" from "what gets executed."

### Impact Explanation
If the executing owner can present arbitrary payload bytes for the actual `MultisigTransactionPayload` used by the VM (rather than being forced to match `transaction.payload`), any owner (not necessarily privileged/admin) who already satisfies quorum for *some* transaction slot can potentially get a **different, unapproved entry function invoked as the multisig account** — a form of "unauthorized transaction execution or state transition under the wrong ... module context" at the admission boundary, since `validate_multisig_transaction` is explicitly documented as being invoked by the VM prologue during both mempool validation and execution to gate what is executable.

### Likelihood Explanation
I was not able to fully confirm, within the scope of this investigation, (a) the default/enabled state of `abort_if_multisig_payload_mismatch_enabled` in this snapshot, or (b) definitively trace the exact VM-side code path that selects between the transaction's supplied `MultisigTransactionPayload` bytes and the on-chain `transaction.payload` for the actual execution call when a full payload is stored on-chain (`aptos-move/aptos-vm/src/aptos_vm.rs` references `validate_multisig_transaction` and multisig payload handling, but I did not get to read the exact dispatch logic before running out of iterations). If the VM always re-derives execution from `transaction.payload` when it is present (using the caller-supplied bytes only for the hash-based case), this finding would not be exploitable. This uncertainty is the key gap preventing a fully-proven, standalone conclusion.

### Recommendation
Make the full-payload equality check in `validate_multisig_transaction` unconditional (not gated by `abort_if_multisig_payload_mismatch_enabled`), and require it whenever `transaction.payload.is_some()`, regardless of whether the caller's `payload` argument is empty — if empty is meant to signal "use the on-chain payload," this must be explicit at the type level (e.g., `Option<vector<u8>>`) rather than inferred from an empty vector, and the VM should be verified to only ever execute `transaction.payload` (never attacker-supplied bytes) whenever it is present on-chain.

### Proof of Concept
Not independently verified end-to-end due to the unresolved VM-side payload-selection question above; a concrete PoC would require:
1. Deploy `multisig_account` with 2-of-3 owners, feature `abort_if_multisig_payload_mismatch_enabled` disabled.
2. Owner A calls `create_transaction` with payload `P1` (e.g., transfer to Owner A).
3. Owners A and B approve.
4. Executing owner submits the `MultisigTransaction` with payload `P2` (e.g., transfer all funds to Owner A) instead of `P1`.
5. Confirm whether `validate_multisig_transaction` accepts this (expected, per code read) and whether the VM subsequently executes `P2` instead of `P1`.

Given the unresolved trace in step 5, I am reporting this with the above caveat rather than as a fully-proven independent vulnerability.
