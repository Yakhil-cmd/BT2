### Title
Atomic dual-token transfer in `withdraw` permanently freezes LP funds when a freezable/pausable Token-2022 vault or destination account is frozen - ([File: programs/cp-swap/src/instructions/withdraw.rs])

### Summary
`withdraw` burns the user's LP tokens and then performs two sequential, non-optional token transfers — token_0 followed by token_1 — inside a single atomic instruction. Because Token-2022 mints can carry a freeze authority / default-account-state extension, either vault or the user's destination account for one of the two tokens can be frozen (independently of the other token). Since both transfers must succeed for the instruction to complete, a freeze on just one side is enough to permanently block withdrawal of both assets, mirroring the reported bug class where a single blacklistable/pausable asset among several breaks an all-or-nothing payout.

### Finding Description
`withdraw` first burns `lp_token_amount` of the user's LP tokens via `token_burn`, then unconditionally calls `transfer_from_pool_vault_to_user` for token_0 and again for token_1: [1](#0-0) 

Both transfers use `token_2022::transfer_checked`, which for Token-2022 mints enforces the mint/account extensions, including frozen state: [2](#0-1) 

The `Withdraw` accounts struct accepts arbitrary `token_0_vault`/`token_1_vault` and user-supplied `token_0_account`/`token_1_account`, only constraining that they match the pool's mint/vault addresses — there is no requirement that these accounts remain unfrozen: [3](#0-2) 

If either token_0's or token_1's mint has a freeze authority (or `DefaultAccountState = Frozen`) and the pool vault or the LP's destination ATA for that single token becomes frozen, the second `transfer_from_pool_vault_to_user` call reverts, rolling back the entire instruction — including the LP-token burn that already succeeded in the same transaction. The LP is left holding LP tokens that represent a claim on funds it can never withdraw as long as the freeze persists, and if the vault itself (not just one user account) is frozen, **all** LPs in the pool are permanently blocked from withdrawing both tokens, not just the frozen one.

The identical atomic dual-transfer pattern also exists in `collect_creator_fee`, `collect_creator_fee_permissionless`, and `collect_fund_fee`, so a freeze on one token's fee-recipient account or vault can likewise permanently block fee collection for both tokens: [4](#0-3) [5](#0-4) 

### Impact Explanation
Any pool paired with a Token-2022 mint that has a freeze authority or default-frozen-account extension is exposed. Freezing (deliberately by a malicious/rug mint issuer, or by a compliance-driven stablecoin issuer) the pool's token vault or a user's destination account for just one of the two pool assets makes `withdraw` permanently revert for that account, locking the user's entire LP position (both token_0 and token_1 shares) even though the other token is fully transferable. This is a permanent freezing of user/LP funds, satisfying the High-severity bar for locked funds.

### Likelihood Explanation
Token-2022 pools are explicitly supported by this program (mint/token-program interfaces accept both `Token` and `Token2022`), so pairing with a freezable/pausable Token-2022 mint is a normal, unprivileged configuration choice at pool creation — no privileged action or non-default build is required to reach this path. Any mint authority that later chooses to freeze a vault or user ATA (a standard, sanctioned Token-2022 capability) triggers the DoS deterministically.

### Recommendation
Avoid coupling unrelated token transfers into a single all-or-nothing instruction for asset recovery paths. Consider allowing partial withdrawal/collection (e.g., letting the caller specify which of token_0/token_1 to attempt, or catching a failed transfer for one leg without reverting the other and the LP burn), or documenting/enforcing that pools cannot be created with freeze-authority-enabled Token-2022 mints.

### Proof of Concept
1. Create a CP-swap pool where token_1 is a Token-2022 mint with a freeze authority (or `DefaultAccountState::Frozen`), token_0 is a standard SPL token.
2. LP deposits liquidity, receiving LP tokens (`token_1` destination ATA is unfrozen at this point).
3. Token_1's freeze authority freezes the LP's token_1 associated token account (or the pool's token_1 vault).
4. LP calls `withdraw` with any `lp_token_amount`. `token_burn` succeeds, `transfer_from_pool_vault_to_user` for token_0 succeeds, but the token_1 `transfer_checked` in [6](#0-5) 
fails because the frozen account rejects the CPI, reverting the whole instruction including the LP burn.
5. The LP can never withdraw any amount of token_0 or token_1 for their LP position as long as the freeze persists, permanently locking their share of both pool assets.

```rust
pub fn transfer_from_pool_vault_to_user<'a>(
    authority: AccountInfo<'a>,
    from_vault: AccountInfo<'a>,
    to: AccountInfo<'a>,
    mint: AccountInfo<'a>,
    token_program: AccountInfo<'a>,
    amount: u64,
    mint_decimals: u8,
    signer_seeds: &[&[&[u8]]],
) -> Result<()> {
    if amount == 0 {
        return Ok(());
    }
    token_2022::transfer_checked(
        CpiContext::new_with_signer(
            *token_program.key,
            token_2022::TransferChecked {
                from: from_vault,
                to,
                authority,
                mint,
            },
            signer_seeds,
        ),
        amount,
        mint_decimals,
    )
}
```
