## Local Admission Analog Found: Reject vote silently overridden as an implicit approval in `validate_multisig_transaction`

### Title
Multisig owner's explicit rejection vote is overridden into an implicit approval during the VM prologue admission of a multisig transaction execution - (File: `aptos-move/framework/aptos-framework/sources/multisig_account.move`)

### Summary
`validate_multisig_transaction` is documented as being invoked by the VM as part of transaction prologue — i.e., it runs during mempool admission and as the first execution step of a transaction targeting a `MultisigAccount`. When counting approvals to decide whether the required quorum (`num_signatures_required`) is met, the code only checks `has_voted_for_approval(owner)`, which returns `false` both when the owner never voted **and** when the owner explicitly voted to reject. In either case, the code silently treats the executing owner as an implicit "approve" vote for quorum-counting purposes, without ever checking whether that owner had in fact recorded an explicit rejection.

### Finding Description
`validate_multisig_transaction` computes the approvals as follows: [1](#0-0) 

The implicit-approval flag is derived from `has_voted_for_approval`, defined as: [2](#0-1) 

This helper returns `true` only if the owner voted **and** their recorded vote is `true` (approve). It returns `false` in two very different situations: (1) the owner never voted at all, and (2) the owner explicitly voted `false` (reject) via `reject_transaction`/`vote_transanction`: [3](#0-2) 

Because `validate_multisig_transaction` (and the identical pattern in `transaction_execution_cleanup_common`, used by both the success and failure post-execution cleanup paths) only tests "has this owner explicitly approved", not "has this owner voted at all", an owner who explicitly rejected a transaction can still trigger execution of that very transaction by submitting the execute-multisig transaction themselves. Their prior reject vote does not block the implicit-approval fallback, so their execution call is silently counted as a "yes" toward `num_signatures_required`: [4](#0-3) 

The counterpart flow for *rejecting* a transaction (`execute_rejected_transaction`) correctly checks `has_voted_for_rejection` before applying an implicit vote, showing the intended symmetric design was to only apply the implicit vote when the owner has not already voted in the relevant direction — but the approval path fails to also guard against a *conflicting* explicit vote: [5](#0-4) 

The same `has_voted_for_approval`-based (rather than "hasn't voted at all"-based) logic is duplicated in the view functions `can_be_executed`/`can_execute`, so off-chain simulators and the wallet UI will also report the transaction as executable under this scenario: [6](#0-5) 

### Impact Explanation
This breaks the multisig approval-set admission invariant: `validate_multisig_transaction` runs at the transaction-prologue admission boundary and is meant to gate whether a `MultisigTransaction` payload should be allowed to execute based on the recorded approval set. An owner who has explicitly signaled rejection (an on-chain, auditable act) should not be able to unilaterally flip their own vote into an approval simply by being the one who submits the execute call — this silently manufactures an approval that never happened, letting the transaction reach quorum and execute/commit even though the genuine, deliberate approval set doesn't actually support it. In a k-of-n multisig where this owner is needed to make up the quorum, they can nullify their own declared rejection without going through `vote_transanction(..., approved=true)`, and the on-chain vote record remains `false` (reject) even as the transaction executes — creating a discrepancy between the recorded approval set and what was actually allowed to execute.

### Likelihood Explanation
Any owner of a multisig account can trigger this by: (1) calling `reject_transaction` on a pending transaction, then (2) submitting the transaction-execution call themselves once enough other implicit/explicit approvals exist to reach quorum together with their own flipped vote. No privileged access or off-chain conditions are required; the flow only depends on ordinary multisig-owner permissions already granted to that address.

### Recommendation
Change the implicit-approval condition in `validate_multisig_transaction`, `can_execute`, `can_be_executed`, and `transaction_execution_cleanup_common` from "has NOT voted for approval" to "has NOT voted at all" (i.e., check that the owner has no entry in `transaction.votes`) before granting an implicit approval. This preserves the intended UX convenience (an owner who never voted can execute and have that count as an approval) without allowing an owner who explicitly rejected to have that rejection silently converted into an approval.

### Proof of Concept
1. Create a 2-of-N multisig account (`num_signatures_required = 2`) with owners A, B, C.
2. Owner A calls `create_transaction` — A is auto-recorded as an approval (`votes[A] = true`), 1 approval so far.
3. Owner B calls `reject_transaction` — `votes[B] = false` is recorded on-chain (an explicit, auditable rejection).
4. Owner B then submits a transaction whose payload targets execution of this pending multisig transaction (the VM invokes `validate_multisig_transaction` with `owner = B` during prologue/admission).
5. Inside `validate_multisig_transaction`: `has_voted_for_approval(multisig_account, seq, B)` returns `false` (because `votes[B] == false`, not because B never voted). The code therefore adds an implicit `+1` approval for B, yielding `num_approvals = 2` (A's real approval + B's manufactured implicit approval), meeting `num_signatures_required = 2`.
6. The transaction is admitted and executes, even though the only genuine approvals came from A (creator) while B's on-chain vote is still recorded as a rejection — quorum was reached using an approval that was never actually cast.
