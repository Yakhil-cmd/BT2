### Title
Cross-org webhook forgery via `owner.login`/`full_name` mismatch lets attacker mutate a victim repository's ReviewStack - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/pull_request/review_stack_adapter.rb])

### Summary
`WebhooksController#verify_signature` authenticates an inbound webhook using the GitHub App config keyed by `params.dig('repository','owner','login')` [1](#0-0) [2](#0-1) , while every `pull_request` handler and `ReviewStackAdapter` resolve the target `Repository`/`Stack` using the independent `params.repository.full_name` field [3](#0-2) [4](#0-3) . Because these two fields are never checked for consistency, and `GitHubApp#verify_webhook_signature` returns `true` unconditionally when the resolved org has no `webhook_secret` configured [5](#0-4) , an attacker who crafts a payload with `repository.owner.login` set to any Shipit-configured org that has no webhook secret can set `repository.full_name` to an arbitrary victim repo and have `ReviewStackAdapter` create/archive/unarchive that victim's real review Stack.

### Finding Description
The broken binding: `org whose GitHubApp config verified this payload signature` (`params.repository.owner.login`) MUST equal `org owning the Repository/Stack that gets mutated` (`owner` parsed from `params.repository.full_name`). These are two separately-attacker-controlled JSON fields in the raw POST body, and nothing in the request pipeline enforces they match.

- `WebhooksController#verify_signature` picks the `GitHubApp` instance via `repository_owner`, which reads `params.dig('repository', 'owner', 'login')` (falling back to `organization.login`) [1](#0-0) [2](#0-1) .
- `Shipit.github(organization:)` looks up per-org config; in a multi-org deployment (`config/secrets.yml` supporting `github: { org1: {...}, org2: {...} }`, as documented) an org can legitimately have no `webhook_secret` set, since the docs mark it "optional" [6](#0-5) .
- `GitHubApp#verify_webhook_signature` short-circuits to `true` when `webhook_secret` is blank, regardless of the `X-Hub-Signature` header's actual value [5](#0-4) .
- Once signature verification passes, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` dispatches the raw, attacker-supplied JSON to the `pull_request` handler [7](#0-6) .
- Every `pull_request` handler (e.g. `OpenedHandler`, `ClosedHandler`, `LabeledHandler`, `ReopenedHandler`) resolves `repository` purely from `params.repository.full_name` via `Shipit::Repository.from_github_repo_name`, with no reference back to the org used for signature verification [3](#0-2) .
- `ReviewStackAdapter` is instantiated with `scope: repository.review_stacks` (scoped to that resolved repository) and finds/creates/archives/unarchives the `Stack` keyed only by `environment` (`"pr#{params.number}"`) and attacker-controlled `params.pull_request.head.ref` [4](#0-3) [8](#0-7) .

Attacker request: `POST /webhooks` with `X-Github-Event: pull_request`, any `X-Hub-Signature` value, and a JSON body where `repository.owner.login` = a Shipit-configured, secret-less org (attacker discovers/controls this org, e.g. their own org if the Shipit operator configured multiple orgs and left one without a secret), and `repository.full_name` = `"victim-org/victim-repo"` with `number` set to a real open PR number on the victim repo and `pull_request.head.ref` set arbitrarily. `drop_unhandled_event` and `ExplicitParameters` schemas do not check cross-field consistency, and `force_github_authentication`/`User#authorized?` are irrelevant since this is the unauthenticated webhook endpoint, not the session-based UI.

### Impact Explanation
The attacker causes `ReviewStackAdapter` to create, archive, or unarchive a Stack row belonging to a repository the attacker never authenticated for — a payload accepted for org A mutates a Stack owned by org B. This is a direct cross-tenant write of state (`Shipit::Stack`/`Shipit::ReviewStack` records), triggers `Shipit::ReviewStackProvisioningQueue.add`/`GithubSyncJob` enqueues, and can archive (tear down) or unarchive (re-provision) a victim's real review environment — matching the "payload for one repository mutating another's stack" Critical category. It is repeatable against any repository whose `full_name` and an open PR number the attacker can guess or observe (PR numbers are small sequential integers, often public).

### Likelihood Explanation
The attack requires a Shipit deployment configured with the multi-org GitHub App schema and at least one org lacking a `webhook_secret` (explicitly documented as optional) [6](#0-5) . Given that precondition, the attacker's cost is a single unauthenticated HTTP POST with a hand-crafted JSON body — no GitHub session, API token, or secret needed. This is fully repeatable and scriptable against arbitrary victim repos.

### Recommendation
Enforce that the org used to select the webhook-verifying `GitHubApp` matches the org embedded in `repository.full_name` before dispatching to handlers, e.g., derive `repository_owner` strictly from `full_name.split('/').first` and reject if it disagrees with `repository.owner.login`/`organization.login`. Additionally, require every configured org (or at least warn/refuse) to set a non-blank `webhook_secret`, since a blank secret currently makes `verify_webhook_signature` accept unsigned traffic unconditionally [9](#0-8) .

### Proof of Concept
Add to `test/controllers/webhooks_controller_test.rb` (or a new adapter-focused controller test):
1. Configure two orgs in test secrets: `no-secret-org` (no `webhook_secret`) and `victim-org` (with a `webhook_secret`), mirroring `test/dummy/config/secrets_double_github_app.yml`.
2. Create a `victim-org/victim-repo` `Repository` fixture with `review_stacks_enabled: true` and an existing open PR number, and assert no `pr1` Stack exists yet.
3. `POST :create` with `X-Github-Event: pull_request`, an arbitrary/garbage `X-Hub-Signature`, and body:
   ```json
   { "action": "opened", "number": 1,
     "pull_request": {"id":1,"number":1,"url":"...","title":"x","state":"open","additions":0,"deletions":0,
       "head": {"sha":"abc","ref":"attacker-branch"}, "user": {"login":"attacker"},
       "assignees": [], "labels": []},
     "repository": {"owner": {"login": "no-secret-org"}, "full_name": "victim-org/victim-repo"},
     "sender": {"login": "attacker"} }
   ```
4. Assert `response.status == 200` (signature accepted because `no-secret-org` has no secret) and `assert_difference -> { victim_repo.review_stacks.count }, 1` — proving a Stack was created under `victim-org` despite the payload only being "verified" for `no-secret-org`, demonstrating the broken binding `verified_org("no-secret-org") != mutated_stack_owner("victim-org")`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
