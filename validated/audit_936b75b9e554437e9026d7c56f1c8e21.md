### Title
Webhook signature verification uses `repository.owner.login` while stack lookup uses `repository.full_name`, allowing a secret-less org to forge state changes on any other org's stack - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects the GitHub App/secret to check the HMAC against based on `params.dig('repository','owner','login')`, but the actual push-handling logic (`Shipit::Webhooks::Handlers::Handler#stacks` / `PushHandler#process`) resolves the target `Stack` using the unrelated field `payload.dig('repository','full_name')`. If any org configured in `Shipit.github(organization:)` has no `webhook_secret` (a "secret-less org"), `GitHubApp#verify_webhook_signature` returns `true` unconditionally regardless of payload content, so an attacker can set `repository.owner.login` to that secret-less org while setting `repository.full_name` to an arbitrary victim repository, forging an authenticated-looking webhook for a stack they don't control.

### Finding Description
The claimed binding is: `organization used to verify the HMAC (repository.owner.login)` == `organization/repository whose Stack record is mutated (repository.full_name)`.

Trace:
- `WebhooksController#verify_signature` (app/controllers/shipit/webhooks_controller.rb:24-49) computes `github_app = Shipit.github(organization: repository_owner)` where `repository_owner` (line 59-62) reads `params.dig('repository','owner','login')`.
- `GitHubApp#verify_webhook_signature` (lib/shipit/github_app.rb:76-83) returns `true` immediately `unless webhook_secret` — i.e., for any org configured without a `webhook_secret`, **all** payloads pass verification regardless of the `X-Hub-Signature` header or body content. [1](#0-0) 
- After verification passes, `WebhooksController#create` dispatches `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` using the raw parsed JSON body — the *same* body the attacker fully controls. [2](#0-1) 
- `Handler#stacks` / `#repository_name` (app/models/shipit/webhooks/handlers/handler.rb:32-38) resolves stacks via `Repository.from_github_repo_name(payload.dig('repository','full_name'))` — a completely independent field from the one used in `verify_signature`. [3](#0-2) 
- `PushHandler#process` (app/models/shipit/webhooks/handlers/push_handler.rb:12-17) calls `stack.sync_github(expected_head_sha: params.after)` for every matching, non-archived stack on the parsed branch, which enqueues `GithubSyncJob`, which in turn calls `stack.lock_reverted_commits!` at line 40 if any newly fetched (real, from GitHub API) commit is a revert. [4](#0-3) 

Exploit: attacker owns/controls an org (or any org lacking a configured `webhook_secret` — this is a realistic operational misconfiguration, not attacker-controlled infra) that Shipit is configured to work with. Attacker POSTs to `/webhooks` with header `X-Github-Event: push` and body:
```json
{"ref":"refs/heads/master","after":"<any sha, irrelevant>",
 "repository":{"full_name":"victim-org/victim-repo","owner":{"login":"secretless-org"}}}
```
`repository_owner` resolves to `"secretless-org"`, `verify_webhook_signature` short-circuits to `true` because that org has no secret, and the handler then looks up and syncs `victim-org/victim-repo`'s real stack — with attacker only needing to guess/know a valid `expected_head_sha` timing coincidence for `GithubSyncJob` to fetch real GitHub commits (including a genuine, freshly-landed revert) and call `stack.lock_reverted_commits!`, attributing the trigger to the forged, unauthenticated request.

Why existing guards fail: `drop_unhandled_event` only filters unrecognized event types, not payload authenticity; `verify_signature` authenticates the *wrong* organization field relative to what is actually acted upon; `ExplicitParameters` (`PushHandler.params`) only validates presence/shape of `ref`/`after`, not repository identity; there is no cross-check that `repository.owner.login` is a prefix/component of `repository.full_name`.

### Impact Explanation
An unauthenticated, cross-org attacker can force a `GithubSyncJob` run (and thus `stack.lock_reverted_commits!`, `stack.mark_as_accessible!/inaccessible!`, commit creation via `append_commit`, `CacheDeploySpecJob` enqueue) against any victim stack whose repository full name they know (public GitHub org/repo names), as long as at least one org in the Shipit deployment's GitHub config lacks a `webhook_secret`. This is a "payload for one repository mutating another's stack" — matching the Critical impact category. The blast radius spans every stack/tenant hosted by the same Shipit instance, and every webhook event type dispatched through the same controller (push, status, membership, pull_request, check_suite) is equally exposed to this owner/full_name mismatch, not just push.

### Likelihood Explanation
Requires an operational precondition: at least one configured GitHub organization in `Shipit.github` credentials without a `webhook_secret`. This is plausible in multi-org Shipit deployments where some orgs are configured for read-only or lower-trust integration and secrets were never set — the code path exists specifically to make `webhook_secret` optional (`return true unless webhook_secret`), so this is a designed, not merely hypothetical, code branch. Given that precondition, the attack costs a single unauthenticated HTTP POST with a hand-crafted JSON body, is fully repeatable, and requires no GitHub App private key, no `webhook_secret`, and no session or API token.

### Recommendation
Bind the field used for signature verification to the same field used for state mutation: derive the org used both in `verify_signature` and in the handler's repository lookup from a single, consistent source (e.g., always use `repository.full_name`'s owner segment, and validate `repository.owner.login` matches the owner prefix of `repository.full_name` before dispatching). Additionally, consider removing/hardening the "no secret configured = trust anything" fallback in `GitHubApp#verify_webhook_signature`, or require every configured org to have a `webhook_secret` set at boot (raise if missing) rather than silently trusting unsigned webhooks for that org.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (new test)
test "forged secret-less-org push webhook can sync an unrelated victim stack" do
  victim_stack = shipit_stacks(:shipit) # repository full_name e.g. "shopify/shipit-engine"

  # Configure an org with no webhook_secret ("secret-less" org)
  Shipit.stubs(:github).with(organization: 'secretless-org').returns(
    Shipit::GitHubApp.new('secretless-org', { webhook_secret: nil })
  )

  request.headers['X-Github-Event'] = 'push'
  forged_payload = {
    ref: 'refs/heads/master',
    after: 'deadbeef',
    repository: {
      full_name: victim_stack.repository.full_name, # victim, not attacker's org
      owner: { login: 'secretless-org' }             # used only for verify_signature
    }
  }.to_json

  # No X-Hub-Signature header set / arbitrary value - should be rejected but isn't
  assert_enqueued_with(job: Shipit::GithubSyncJob, args: [stack_id: victim_stack.id, expected_head_sha: 'deadbeef']) do
    post :create, body: forged_payload, as: :json
  end
  assert_response :ok
end
```
This asserts that `repository_owner` (`'secretless-org'`) ≠ the org actually owning the mutated stack (`victim_stack.repository.full_name`'s owner), yet the job is enqueued and the response is `200 OK`, proving the authentication-organization/mutation-organization binding is broken.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)

    end
