### Title
Webhook signature verified against `repository.owner.login`/`organization.login` while stack mutation is keyed off unrelated `repository.full_name` - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects the `GitHubApp` (and thus the `webhook_secret`) used to validate the HMAC based on `params.dig('repository','owner','login') || params.dig('organization','login')`, while `PushHandler` (via `Handler#stacks`/`#repository_name`) resolves the target `Repository`/`Stack` from a completely different field, `payload.dig('repository','full_name')`. Because the attacker controls the raw JSON body they POST, these two fields need not agree, letting a webhook signed with org A's secret operate on a stack that belongs to org B.

### Finding Description
The binding that should hold is: `organization_that_verified_signature == organization_that_owns_the_mutated_repository`, i.e. `repository_owner` (used in `Shipit.github(organization: repository_owner)`) must equal the owner portion of `repository.full_name` (used by `Repository.from_github_repo_name`). This binding is never enforced.

Code path:
1. `verify_signature` computes `repository_owner` purely from the unsigned, attacker-supplied JSON body: [1](#0-0) 
It then fetches `Shipit.github(organization: repository_owner)` and calls `verify_webhook_signature(header, request.raw_post)`: [2](#0-1) 
2. `create` re-parses the same raw body and dispatches it unchanged to the handler: [3](#0-2) 
3. `Handler#stacks` resolves the target repository from a different field of the very same payload, `repository.full_name`, with no cross-check against `repository_owner`: [4](#0-3) 
4. `Repository.from_github_repo_name` splits `full_name` on `/` and does a plain `find_by(owner:, name:)` lookup, independent of which org's secret verified the request: [5](#0-4) 
5. `PushHandler#process` then calls `stack.sync_github(expected_head_sha: params.after)` on whatever stacks that lookup returns: [6](#0-5) 

Given the premise that the attacker knows org A's `webhook_secret` (stated precondition — they administer org A's webhook configuration pointing at the Shipit host), they can send:
```
POST /webhooks
X-Github-Event: push
X-Hub-Signature: sha1=<HMAC(org-A-secret, raw_body)>
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "org-a" },
    "full_name": "org-b/private-repo"
  }
}
```
`repository_owner` resolves to `"org-a"`, so verification succeeds against org A's secret. `PushHandler` then independently resolves `"org-b/private-repo"` from `full_name` and calls `sync_github` on org B's real stack. Nothing in `verify_signature`, `drop_unhandled_event`, `ExplicitParameters` (`PushHandler` only `requires :ref, :after`), or `Repository.from_github_repo_name` cross-checks that the two fields describe the same organization.

### Impact Explanation
An attacker who controls a webhook secret for any org configured in Shipit can force `Stack#sync_github` to run against any other org's stack registered in the same Shipit instance, using an attacker-chosen `after` SHA in the push payload. This is a cross-tenant write triggered by a payload that authenticated as a different repository/organization than the one mutated — matching the Critical category "a payload for one repository mutating another's stack" and potentially triggering downstream deploy behavior driven by the forced sync. It is repeatable against any repository name the attacker can guess/enumerate, and the blast radius spans all tenants/organizations hosted on the same Shipit instance.

### Likelihood Explanation
Preconditions: the attacker must control (know) the `webhook_secret` for at least one organization configured in Shipit (`org A`), which per the question's stated setup is achievable by an org that has its own webhook configuration pointing at the shared Shipit host — a realistic multi-tenant deployment. No Shipit session, API token, or GitHub App private key is required. The attacker needs only to know a target repository's `owner/name` (often discoverable, e.g. via the Shipit UI's stack listing or guessed org/repo names) and craft a single HTTP POST. Cost is low and the attack is fully repeatable.

### Recommendation
Enforce the binding explicitly: after re-parsing the body in `create` (or inside `verify_signature`), derive the organization used to select the `GitHubApp`/secret and the organization implied by `repository.full_name`, and reject the request (`head(422)`) unless they match. Alternatively, verify the signature using the org derived from `full_name`'s owner segment consistently in both `verify_signature` and the handlers, so there is a single source of truth for "which org authenticated this payload." Also fix `head(422) unless verified` to actually halt the filter chain (`return head(422) unless verified`), since currently execution continues to `create` regardless.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (conceptual addition)
test "push webhook signed by org A cannot mutate org B's stack" do
  org_a_secret = 'org-a-secret'
  Shipit.stubs(:github).with(organization: 'org-a').returns(
    stub(verify_webhook_signature: true) # signed correctly with org-a secret
  )

  victim_repo = shipit_repositories(:org_b_private_repo) # owner: 'org-b', name: 'private-repo'
  victim_stack = shipit_stacks(:org_b_private_repo_master)

  body = {
    ref: 'refs/heads/master',
    after: 'attacker0000000000000000000000000000000',
    repository: {
      owner: { login: 'org-a' },
      full_name: 'org-b/private-repo'
    }
  }.to_json

  signature = 'sha1=' + OpenSSL::HMAC.hexdigest('sha1', org_a_secret, body)

  Stack.any_instance.expects(:sync_github)
    .with(expected_head_sha: 'attacker0000000000000000000000000000000')

  post shipit.webhooks_path,
    params: body,
    headers: {
      'X-Github-Event' => 'push',
      'X-Hub-Signature' => signature,
      'Content-Type' => 'application/json'
    }

  assert_response :ok
  # Assert: org that verified signature ("org-a") != org whose stack was mutated ("org-b")
end
```
This demonstrates that the organization whose secret validated the request (`org-a`) diverges from the organization whose `Stack#sync_github` is invoked (`org-b`), violating the required binding.
