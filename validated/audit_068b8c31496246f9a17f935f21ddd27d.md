### Title
Type-3 ERC20 tokens (no boolean return on success) cause `ERC20Transactor::deposit_asset_with_surplus` to trap real, already-transferred tokens, enabling duplicate payout via the permissionless `claim_assets` extrinsic - (File: cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs)

### Summary
`ERC20Transactor` (used by Asset Hub's XCM `AssetTransactors`) speaks to arbitrary on-chain contracts via the raw Solidity `IERC20::transferCall` ABI, exactly the pattern flagged by the external report: it assumes every ERC20 always returns a `bool` on success. For "type 3" tokens (e.g. USDT-style contracts that `throw` on failure but return **no** data on success), `abi_decode_returns_validate` fails to decode the empty/short return payload even though the underlying `transfer()` already succeeded and moved real tokens. The code then treats this as a failed deposit/withdraw and returns the un-consumed `Erc20Credit` back into the XCM holding register, which is trapped by `pallet_xcm::DropAssets`. Because trapped assets can later be reclaimed with the fully permissionless `pallet_xcm::claim_assets` extrinsic (any signed account, no privilege required) and reclaiming re-mints the imbalance through the same `AssetTransactor`, this can result in the checking account being debited twice for a single logical credit - i.e. a duplicate real ERC20 payout funded out of the shared `ERC20TransfersCheckingAccount` pool that backs *all* users' balances of that token.

### Finding Description
`ERC20Matcher` matches **any** local `AccountKey20` location as a fungible asset id: [1](#0-0) 
This makes the asset id an arbitrary H160 contract address - no governance registration is required for a location like `(0, [AccountKey20 { key: <any deployed contract> }])` to be routed through `ERC20Transactor`.

`deposit_asset_with_surplus` performs a real `bare_call` to the target contract's `transfer(to, value)` and then requires the return data to decode as a `bool`: [2](#0-1) 
If the transfer did not revert (i.e. it succeeded and moved real tokens out of the checking account) but returns no/insufficient data - the exact "type 3" ERC20 behaviour the external report describes (USDT-style: throws on failure, no return value on success) - `abi_decode_returns_validate` fails, and the function returns `Err((what, XcmError::FailedToTransactAsset("ERC20 contract result couldn't decode")))`, handing the un-consumed `Erc20Credit` imbalance for `amount` back to the XCM executor even though the physical tokens already left the checking account.

The XCM executor's error handling for `DepositAsset` trap-drops this returned `what` via `pallet_xcm::DropAssets::drop_assets`, which explicitly "forgets" the imbalance so it isn't dropped, with the comment stating the mirrored claim operation will *recover* it by minting a fresh imbalance: [3](#0-2) 
This trapped credit is keyed by `hash(origin, assets)` and can be reclaimed by anyone whose XCM-execution origin matches the trap origin, using the fully permissionless extrinsic: [4](#0-3) 
`claim_assets` -> `ClaimAssets::claim_assets` re-mints the imbalance through `AssetTransactor::mint_asset`, explicitly described as "duplicating the imbalance": [5](#0-4) 
`mint_asset` for a `TransactAsset` implementation is conventionally routed to `deposit_asset` (there is no override in `ERC20Transactor`, which only implements `withdraw_asset_with_surplus`/`deposit_asset_with_surplus` plus the no-op check-in/out methods) - meaning claiming the trap triggers a **second real** `transfer()` call to the beneficiary, drawing again from the same checking-account balance that backs every other holder of that ERC20 asset.

Every single deposit of a genuine "type 3" token (return-nothing-on-success, e.g. a real USDT-style contract) through this transactor will hit the decode failure path on the *first* attempt, no attacker sophistication required beyond being the recipient of an XCM deposit of such a token and then calling the public `claim_assets` extrinsic for themselves.

`ERC20Transactor` is wired into Asset Hub Westend's production `AssetTransactors` tuple: [6](#0-5) 

### Impact Explanation
If a "type 3" ERC20 (no boolean return on success, e.g. a faithfully-ported USDT contract) is ever bridged/registered as an XCM fungible via this transactor, every deposit into a user's account traps a duplicate credit that the recipient can immediately claim through the permissionless `claim_assets` extrinsic, causing a second real ERC20 transfer out of the shared `ERC20TransfersCheckingAccount`. Because that account pools the balances backing *all* holders of the same ERC20 contract, this results in unbacked/duplicate payouts and can drain funds belonging to other legitimate users of the same token from the checking account - a direct token-theft/insolvency vector, not merely a denial of service.

### Likelihood Explanation
Reachability requires no privileged role: any signed account can (a) trigger a deposit of the offending ERC20 (via ordinary XCM reserve transfer/execute) and (b) call the public `pallet_xcm::claim_assets` extrinsic for their own trapped assets. The only precondition is that a "type 3"-style ERC20 contract is used as an asset through `ERC20Transactor` - the `ERC20Matcher` accepts arbitrary contract addresses without governance gating, so this is within reach of an ordinary user who deploys/uses such a contract (e.g. any pallet-revive/EVM-bytecode contract that mimics real-world USDT's non-standard return behaviour). This is not a hypothetical config-only issue: it is a deterministic consequence of the `abi_decode_returns_validate` check on line 276 combined with the standard XCM trap/claim mechanism.

### Recommendation
- Do not treat "successful call with undecodable/empty return data" as a failure once `did_revert()` is `false`; distinguish between a genuine `false`-return failure and a token that (like USDT) returns no data at all - e.g. only fail decode if the data length is nonzero and doesn't match the expected ABI shape; treat 0-length data on a non-reverted call as success (mirroring OpenZeppelin's `SafeERC20`, which only requires that the call not revert and, if data is returned, that it decode to `true`).
- Ensure the transactor's contract call and the accounting decision are atomic: either wrap the `bare_call` + decode-and-decide logic in a single transactional storage layer so that a decode failure cannot leave a real, already-executed transfer unaccounted for, or make the trap/claim mechanism aware that `Erc20Credit` for this transactor must never be re-minted without re-verifying on-chain balances.
- More generally, adopt `SafeERC20`-equivalent semantics (accept "no return data" as success on non-revert) throughout `erc20_transactor.rs`'s `withdraw_asset_with_surplus` and `deposit_asset_with_surplus`.

### Proof of Concept
Not executed against a live network or public test harness; this is a source-level trace through `erc20_transactor.rs`, `xcm-executor`'s `ClaimAsset`/error-trap path, and `pallet_xcm`'s `DropAssets`/`ClaimAssets`/`claim_assets` extrinsic, all cited above. I could not, within the available tool budget, directly read the `TransactAsset` trait's default `mint_asset` body in `polkadot/xcm/xcm-executor/src/traits/transact_asset.rs` to 100% confirm it forwards to `deposit_asset`/`deposit_asset_with_surplus` for `ERC20Transactor` (which has no override for `mint_asset`/`burn_asset`); the `pallet_xcm::ClaimAssets` comment ("mirrored asset claiming operation will recover the imbalances by minting back into holding, effectively duplicating the imbalance") strongly corroborates this but should be independently verified with a minimal FRAME/XCM integration test (deploy a mock "type-3" ERC20 precompile/contract returning empty data on success, drive a `WithdrawAsset`→failed `DepositAsset`→`AssetsTrapped`→`claim_assets` sequence, and assert the checking account is debited twice for one logical credit) before filing to a live bounty program.

impl<T: Config> DropAssets for Pallet<T> {
	fn drop_assets(origin: &Location, holding: AssetsInHolding, _context: &XcmContext) -> Weight {
		if holding.is_empty() {
			return Weight::zero();
		}
		let assets: Vec<Asset> = holding.assets_iter().collect();
		// SAFETY: "forget" about any fungible imbalances so that they are not dropped/resolved
		// here. The mirrored asset claiming operation will "recover" the imbalances by minting
		// back into holding, effectively duplicating the imbalance and only then dropping the
		// duplicate. As a result, total issuance doesn't change.
		holding.fungible.into_iter().for_each(|(_, mut accounting)| {
			accounting.forget_imbalance();
		});
		let versioned = VersionedAssets::from(Assets::from(assets));
		let hash = BlakeTwo256::hash_of(&(&origin, &versioned));
		AssetTraps::<T>::mutate(hash, |n| *n += 1);
		Self::deposit_event(Event::AssetsTrapped {
			hash,
			origin: origin.clone(),
			assets: versioned,
		});
		// TODO #3735: Put the real weight in there.
		Weight::zero()
	}

impl<T: Config> ClaimAssets for Pallet<T> {
	fn claim_assets(
		origin: &Location,
		ticket: &Location,
		assets: &Assets,
		context: &XcmContext,
	) -> Option<AssetsInHolding> {
		let mut versioned = VersionedAssets::from(assets.clone());
		match ticket.unpack() {
			(0, [GeneralIndex(i)]) => {
				versioned = match versioned.into_version(*i as u32) {
					Ok(v) => v,
					Err(()) => return None,
				}
			},
			(0, []) => (),
			_ => return None,
		};
		let hash = BlakeTwo256::hash_of(&(origin.clone(), versioned.clone()));
		match AssetTraps::<T>::get(hash) {
			0 => return None,
			1 => AssetTraps::<T>::remove(hash),
			n => AssetTraps::<T>::insert(hash, n - 1),
		}
		let mut claimed = AssetsInHolding::new();
		for asset in assets.inner() {
			match <T::XcmExecutor as XcmAssetTransfers>::AssetTransactor::mint_asset(asset, context)
			{
				Ok(minted) => {
					// SAFETY: Any fungible imbalances are now effectively duplicated because they
					// were not resolved when the asset was trapped (so total issuance tracks
					// trapped assets too), and now a duplicate asset was just minted.
					// To balance the system and keep total issuance constant, we drop and resolve
					// one of the duplicates. As a result, total issuance doesn't change.
					//
					// Note: This may emit Burned/Minted events even though the net issuance change
					// is zero. The mint creates a +X imbalance, and dropping the clone resolves -X,
					// resulting in no net change but potentially two events. This is an acceptable
					// tradeoff for the asset trap/claim mechanism.
					minted.fungible.iter().for_each(|(_, imbalance)| {
						let to_resolve = imbalance.unsafe_clone();
						core::mem::drop(to_resolve);
					});
					claimed.subsume_assets(minted)
				},
				Err(error) => tracing::debug!(
					target: "xcm::pallet_xcm::claim_assets",
					?asset, ?error, "Asset claimed from trap but unable to mint."
				),
			}
		}
