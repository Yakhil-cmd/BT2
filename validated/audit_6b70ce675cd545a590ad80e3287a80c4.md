### Title
CCMenu API endpoint bypasses ApiClient stack scoping, allowing a stack-restricted token to read another stack's build/deploy status - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Shipit::Api::BaseController` enforces that a stack-scoped `ApiClient` (one created with a `stack_id`) can only see the single stack it was authorized for, by routing all stack lookups through the `stacks` helper. `Shipit::Api::CCMenuController` overrides `#stack` to bypass that scoping and resolve the stack directly from the global `Stack` collection using only the request parameter, so any client holding a token with the generic `read:stack` permission can query CCMenu status for a stack it was never authorized to see.

### Finding Description
`BaseController#stacks` restricts the queryable stack set to the one the `ApiClient` is scoped to: [1](#0-0) 

Every other resource controller (e.g. `StacksController#stack`, `HooksController#stack_id`) resolves the target stack through this scoped `stacks` relation: [2](#0-1) 

`CCMenuController`, however, defines its own `#stack` method that ignores the scoping entirely and looks the stack up directly from the unscoped `Stack` model, keyed only on the caller-supplied `params[:stack_id]`: [3](#0-2) 

The only authorization check performed is the coarse-grained permission string `read:stack`: [4](#0-3) 

which does not verify the requested stack matches `current_api_client.stack_id`, unlike the `stacks` helper used everywhere else. This breaks the binding: `current_api_client.stack_id == stack it is permitted to touch` vs. `params[:stack_id] == stack the controller actually reads`. This is directly analogous to the reported bug class: a value (`stack_id`) that should always be derived/checked against an authoritative constraint (the client's granted scope) is instead accepted verbatim from an untrusted input, causing an accounting/authorization mismatch.

### Impact Explanation
A token that was deliberately minted and scoped to a single stack (e.g. via `CCMenuUrlController#client`, which creates a `read:stack`-only client tied to one stack) can be replayed against `Api::CCMenuController#show` with a different `stack_id` parameter to read that other stack's build/deploy status (`lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, `webUrl`, activity). This is a cross-stack disclosure of deploy/build state that the token issuer never intended to grant, matching the "unauthenticated/unauthorized read of stack state or deploy output" impact class.

### Likelihood Explanation
Exploitation only requires possession of any valid API token with the generic `read:stack` permission (including narrowly-scoped CCMenu tokens that are routinely embedded in third-party CI dashboard tools), and knowledge or guessing of another stack's `to_param` (owner/repo/environment/branch), which is often predictable or discoverable. No privileged access, signature forgery, or session is required beyond having any one legitimate scoped token.

### Recommendation
Change `Shipit::Api::CCMenuController#stack` to resolve the stack through the scoped `stacks` helper (`stacks.from_param!(params[:stack_id])`) exactly as the other API controllers do, so a stack-scoped `ApiClient` cannot read state for stacks outside its granted `stack_id`.

### Proof of Concept
1. Create a stack-scoped API client for Stack A via `CCMenuUrlController#fetch` (or any `ApiClient` with `stack_id` set to Stack A and `permissions: ['read:stack']`).
2. Using that client's `authentication_token`, send `GET /api/stacks/:stack_id/ccmenu.xml` with `stack_id` set to Stack B (a different stack the client was never authorized for).
3. Observe that `CCMenuController#stack` resolves Stack B via `Stack.from_param!(params[:stack_id])` (bypassing the `stacks` scoping), the `read:stack` permission check passes, and Stack B's build/deploy status is returned to a caller who only held a token scoped to Stack A.
