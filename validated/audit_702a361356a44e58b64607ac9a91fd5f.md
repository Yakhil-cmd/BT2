### Title
Cross-repository status writes via bare-SHA lookup in `StatusHandler#process` amplified by `blocking_statuses` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` resolves target commits with `Commit.where(sha: params.sha)`, which matches every `Commit` record across every stack/repository sharing that SHA, with no check that the SHA belongs to the repository that authenticated the webhook. When a victim stack configures `blocking_statuses` requiring a context such as `review/approved`, any status payload matching that SHA and context — regardless of source repository — can set or clear `Commit#blocked?` and thereby gate or unblock deploys on the victim stack.

### Finding Description
The broken binding: the intended invariant is `commit.stack.github_repo_name == verified_repository_owner/repository` for every commit mutated by a status webhook, i.e. a status should only affect commits belonging to the repository whose signature was verified. The actual code enforces only `Shipit.github(organization: repository_owner).verify_webhook_signature(...)` in `Shipit::WebhooksController#verify_signature` (app/controllers/shipit/webhooks_controller.rb:24-30), which is a per-organization signature check, not a per-commit/per-repo scoping check.

`StatusHandler#process` then does:
```ruby
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
``` [1](#0-0) 

This query is global across the `commits` table — it is not scoped by `stack_id`, `stack.repository`, or the organization that signed the request. Any `Commit` row in any stack whose `sha` column matches the attacker-supplied `params.sha` will receive the status via `create_status_from_github!` → `add_status` → `statuses.replicate_from_github!`. [2](#0-1) 

`Commit#blocked?` and `deployable?` depend purely on the presence of a "blocking" status among commits in the stack's undeployed range, with no repository check: [3](#0-2) 

Root cause: the webhook signature check authenticates *which organization* sent the payload but the handler never re-validates that the SHA being updated actually belongs to a stack/repository under that organization. Since git commit SHAs are content-addressed, an attacker can produce a commit with an identical SHA to one already known to a victim stack (e.g., by pushing the exact same tree/parents/commit metadata to their own repository, or by simply reusing a SHA that appears in multiple stacks' `commits` tables, e.g. a shared base commit, cherry-pick, or a commit from a public repo mirrored into both an attacker-controlled and a victim stack). The attacker can then trigger (or directly emit, if they control any repository whose organization is configured in `Shipit.github_teams`/App installation) a `status` event with `context: "review/approved"` for that SHA. If they hold no valid signature at all, `verify_signature` in the controller will reject the request outright, since it validates the raw payload signature against the app secret for the organization named in the payload body — for an attacker with no GitHub App installation or team access this blocks unauthenticated forgery. However, if the attacker legitimately owns *any* repository under an organization that itself has a Shipit GitHub App installation (i.e., they are simply an unprivileged contributor/owner of a separate, unrelated repo in an org that also hosts unrelated stacks), GitHub itself will sign and deliver their own repo's real status events, and `StatusHandler` will apply that status to **any** `Commit` row sharing the SHA, including ones belonging to a different stack/repository than the one that produced the event.

This violates the stated invariant: "A status for `review/approved` only affects the repository that authenticated it, irrespective of `blocking_statuses` configured." The existing guards (`verify_signature`, `drop_unhandled_event`, `ExplicitParameters` schema) validate organization-level signature and payload shape only — none of them check `commit.stack.repository` against the payload's `repository.full_name`.

### Impact Explanation
An attacker who controls (or can trigger real webhook events from) a repository whose signing organization is configured in Shipit can, per request, write a `Status` row onto **any** `Commit` record sharing the same SHA in a different stack/repository. On a victim stack configured to require `review/approved` via `blocking_statuses`, this can set or clear `Commit#blocked?`, directly gating `deployable?` and `schedule_continuous_delivery`, i.e. force or suppress a deploy without any interaction with the victim repository. This is a payload from one repository mutating another repository's commit/stack state, matching the Critical severity category ("a payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy, rollback or merge"). The blast radius extends to any stack that happens to share a commit SHA with the attacker's controlled repository (common for monorepo forks, shared base branches, or cherry-picked commits), and the attack is fully repeatable per matching SHA.

### Likelihood Explanation
Preconditions: attacker needs a way to produce a webhook payload that passes `verify_signature`, and a Commit row with a matching `sha` must exist in the victim's stack. `verify_signature` checks only the organization-level signature, not the specific repository, so any org member able to trigger a real GitHub status event (e.g., a collaborator on any repo under that org, or a public-repo contributor whose PR CI reports a `review/approved`-context status) can produce a valid signed request. SHA collision across stacks is realistic in shared-history scenarios (shared base commits, forks, monorepo submodules) without requiring cryptographic SHA collision. Attacker cost is low (an ordinary push/PR/API call to their own accessible repository); the finding is repeatable against any stack that shares a SHA with an attacker-accessible repository.

### Recommendation
Scope `StatusHandler#process` (and the analogous check-run handler) to only update commits belonging to the repository that authenticated the webhook. Concretely, join/filter with the stack's repository derived from `payload['repository']['full_name']` (or `repository_owner`/`repository_name` from the verified payload), e.g.:
```ruby
Commit.joins(:stack).where(sha: params.sha, shipit_stacks: { repository_id: repository.id }).each do |commit|
  ...
end
```
and pass the verified repository identity from the controller into the handler so the lookup can be scoped instead of a bare, engine-wide `sha` match.

### Proof of Concept
minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb`, not included in this audit's OUT-OF-SCOPE test dir but describing the required assertions):
1. Create `attacker_stack` bound to `repository_a` (`org/attacker-repo`) and `victim_stack` bound to `repository_b` (`org/victim-repo`), with `victim_stack.blocking_statuses = ['review/approved']`.
2. Create `Commit` rows in both stacks with the identical `sha = "deadbeef" * 5` (simulate SHA collision/shared history).
3. Before: assert `victim_stack.commits.last.blocked?` reflects only statuses attached to that commit under `victim_stack`; establish equality `victim_commit.blocking? == false` and `victim_commit.blocked? == false`.
4. Invoke `Shipit::Webhooks::Handlers::StatusHandler.new.call(sha: shared_sha, state: 'success', context: 'review/approved')` — simulating a payload that only ever named `repository_a` in its outer JSON (the handler itself never checks `repository`).
5. After: assert `Commit.where(sha: shared_sha)` returns **two** rows (one per stack) and that `victim_stack.commits.find_by(sha: shared_sha).blocking?` and `blocked?` changed state, proving cross-repository mutation — i.e., the equality `victim_commit.status_before == victim_commit.status_after` no longer holds despite the payload only being attributable to `repository_a`.
