### Title
Webhook signature verification authenticates a different organization than the repository whose state is mutated - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/handler.rb], [File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` selects the HMAC secret to validate a webhook request against using `repository_owner`, which is read straight out of the unauthenticated JSON body (`params.dig('repository', 'owner', 'login')` or `organization.login`). Once the signature check passes, every `Handler` subclass instead resolves the target repository/stacks and commits using a *different* field from the same untrusted body: `Handler#repository_name` (`payload.dig('repository', 'full_name')`) for `PushHandler`, and, worse, no repository scoping at all for `StatusHandler`, which does `Commit.where(sha: params.sha)` across the entire database. The field that is "authenticated" (the org whose secret matched) is never checked for equality against the field that is actually acted upon (the target repo/commit).

### Finding Description
`verify_signature` picks the org whose `webhook_secret` to check against based on attacker-suppliable JSON, before the signature has been validated: [1](#0-0) [2](#0-1) 

If the HMAC computed with that org's secret matches `X-Hub-Signature`, the whole raw payload is accepted and dispatched to handlers: [3](#0-2) 

Every handler's target-selection logic reads a *separate* field of the same payload, with no cross-check that it matches the organization that actually authenticated the request: [4](#0-3) 

`PushHandler` uses `repository_name` (`repository.full_name`) to select stacks to `sync_github`: [5](#0-4) 

`StatusHandler` is worse: it does not scope by repository/stack at all, it matches on `sha` globally across the whole `commits` table: [6](#0-5) [7](#0-6) 

This is the same bug class as the audit finding H-5: one field (`initialCollateralDeltaAmount`, here `repository.owner.login`) is treated as validated/trusted for a check, while a *different, unchecked* field (the USD-denominated total, here `repository.full_name` / `sha`) is what the subsequent logic actually operates on — breaking the equality `organization-that-authenticated == repository-that-is-written`.

Concretely: in a multi-tenant Shipit deployment (`Shipit.github(organization: ...)` supports per-organization GitHub Apps/webhook secrets), an attacker who knows/controls the `webhook_secret` for *any one* configured organization (e.g. because they administer that org's GitHub App/webhook settings) can POST directly to `/webhooks` with:
- `repository.owner.login` (or `organization.login`) = the org whose secret they know, so `verify_signature` looks up and validates against that org's secret, and
- `repository.full_name` (for push events) or `sha` (for status events) = a value belonging to a completely unrelated organization/stack/commit hosted on the same Shipit instance.

Because the handlers never re-check that the authenticated org matches the org implied by `full_name`/`sha`, the request is processed against the unrelated target.

### Impact Explanation
The clearest instance is `StatusHandler`: `Commit.where(sha: params.sha)` has zero repository scoping, so a request that passes signature verification for *organization A* can inject a spoofed commit status (`create_status_from_github!`) onto commits belonging to *organization B*, as long as the SHA collides/matches (SHAs are per-repo but the table is global; an attacker can target any known SHA in the shared Shipit instance). Commit status directly feeds `Commit#deployable?`, which gates automatic/continuous deployment (`schedule_continuous_delivery` → `ContinuousDeliveryJob`) and CI-required checks for deploys: [8](#0-7) [9](#0-8) 

Forging a "success" status can therefore unlock continuous deployment / clear CI-required gates for a stack the attacker has no legitimate access to, which is an unauthorized-deploy-class impact.

### Likelihood Explanation
Exploitability depends on the attacker legitimately knowing the `webhook_secret` for at least one organization configured on the Shipit instance (typically because they are an admin of that org's own GitHub App/webhook settings) while having no authorization over the *other* org/repo they target — this matches the "cross-tenant" scenario expected for a multi-organization Shipit deployment and does not require a Shipit session, API token, or the target repo's own secret.

### Recommendation
- In `WebhooksController#verify_signature`, after the signature check succeeds, re-derive the same "owner"/organization identity that each `Handler` will use to select records, and reject the request if they don't match exactly (i.e. bind the field used for HMAC selection to the field used for record resolution).
- In `Handler#repository_name`, and specifically in `StatusHandler#process`, always scope lookups through `Repository`/`Stack` derived from the verified organization, and filter `Commit` lookups by `stack_id`/`github_repo_name` rather than a bare global `sha` match.

### Proof of Concept
Not independently executable without live multi-org Shipit config (needing two configured GitHub Apps/orgs with distinct webhook secrets and at least one commit belonging to a "victim" stack), but the code path is:
1. Configure Shipit with two orgs, `org-a` (attacker-known secret `S_A`) and `org-b` (victim, stack `victim/repo`, has a commit with `sha=abc123`).
2. POST to `/webhooks` with header `X-Github-Event: status`, `X-Hub-Signature: sha1=<HMAC(S_A, body)>`, and body:
```json
{
  "repository": { "owner": { "login": "org-a" }, "full_name": "org-a/irrelevant" },
  "sha": "abc123",
  "state": "success"
}
```
3. `verify_signature` computes `Shipit.github(organization: "org-a")` and validates against `S_A` → passes.
4. `StatusHandler#process` runs `Commit.where(sha: "abc123")`, which finds the victim's commit regardless of `org-a`/`org-b` mismatch, and writes a forged "success" status to it via `create_status_from_github!`.
