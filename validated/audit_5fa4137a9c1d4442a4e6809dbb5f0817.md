### Title
`Controller::withdraw`/`borrow` allow paying out to arbitrary contract addresses, permanently stranding tokens — (File: contracts/controller/src/positions/supply.rs)

### Summary
`Controller::withdraw` (and `borrow`) accept an optional `to: Option<Address>` recipient and forward it to `settle_withdraw`, which makes the pool transfer underlying tokens to that address. The only recipient guard, `require_external_recipient` in `contracts/controller/src/positions/mod.rs:36-43`, rejects the pool and the controller itself but places no restriction on other contract addresses. This is the same bug class as the missing `onlyEOA` check in `L2ECOBridge.withdraw()`: funds can be paid out to a contract that has no code capable of moving them, permanently freezing them.

### Finding Description
`process_withdraw` resolves `recipient = to.unwrap_or(caller)` and calls `require_external_recipient`, which only asserts the recipient is neither the controller nor the pool (`contracts/controller/src/positions/supply.rs:152-154`, `contracts/controller/src/positions/mod.rs:36-43`). The pool leg then calls `transfer_out(receiver, net_transfer)` (`contracts/pool/src/ops/withdraw.rs:48`), a plain SAC/token transfer. On Soroban, a token balance held by a contract `Address` can only be moved by that contract's own code; a recipient contract with no token-management entrypoint (or no admin able to act) holds the tokens forever. The protocol's own documentation acknowledges the stranding risk — it rejects pool/controller recipients precisely because "the controller holds funds no balance-delta measurement can ever claim" — but the identical failure mode for *any other* contract recipient is left open. An unprivileged user reaches this via `ControllerClient::withdraw(caller, account_id, withdrawals, Some(contract_addr))`, and `borrow` shares the same `to` path.

### Impact Explanation
Permanent freezing/loss of user funds: once the pool transfers underlying to a contract that cannot transfer out (e.g., a script-runner, a deployed instance with no token API, or an address mistakenly pasted), the tokens are unrecoverable — same "possible token loss accidentally" impact as the L2ECOBridge issue. No privileged role, upgrade, or leaked key is required; a single unprivileged caller submits one transaction.

### Likelihood Explanation
Medium: `to` is a user-supplied free-form `Address` and nothing in the type system or validation distinguishes contracts from accounts. Mistaken input (integrator passing a vault/strategy/router address instead of an EOA, or UI defaulting `to` to a contract) triggers it in one call, and there is no recovery path since the transfer already settled.

### Recommendation
Extend the recipient validation so payout entrypoints (`withdraw`, `borrow`, and any other `transfer_out` path taking a `to`/recipient) reject contract recipients unless the recipient is a known-capable contract. Concretely, in `require_external_recipient` (`contracts/controller/src/positions/mod.rs:36`), also require `recipient.executable()` to be `None`/an account executable, or gate contract recipients behind an explicit opt-in flag so accidental contract payouts revert before shares are burned.
