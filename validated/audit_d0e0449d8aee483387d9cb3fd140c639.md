Based on my investigation, the price-staleness bug class from the report does not map cleanly onto ocore's data-feed reading code as a "stale value" issue (AA authors control config), but a closely related and more concrete flaw exists in the same code path: `data_feed[[...]]`'s handling of **unstable** oracle data can crash node processing (an unhandled exception) or return a non-deterministic result across full nodes, both of which map to the accepted "network unable to confirm new units" outcome.

### Title
Uncaught exception / non-deterministic candidate selection in `data_feed[[...]]` unstable-data-feed lookup can halt AA processing across full nodes - (File: `data_feeds.js`)

### Summary
When an AA formula uses `data_feed[[...]]`, evaluation.js passes `bAA` (a boolean) as the `unstable_opts` argument to `dataFeeds.readDataFeedValue()`, which makes the lookup also scan `storage.assocUnstableMessages` for **not-yet-stable** `data_feed` messages authored by other AAs, in addition to the confirmed key-value store. If two or more matching unstable candidates cannot be strictly ordered, the code throws an uncaught `Error` from inside an `Array.prototype.sort()` comparator instead of failing gracefully.

### Finding Description
`evaluate()` in `formula/evaluation.js` calls: [1](#0-0) 
which forwards `bAA` as `unstable_opts` into `readDataFeedValue()`.

Inside `readDataFeedValue()` in `data_feeds.js`, when `unstable_opts` is truthy, the function iterates over every currently unstable unit in `storage.assocUnstableMessages`, filters by author address and mci range, and collects all matching candidate `data_feed` values: [2](#0-1) 

If more than one candidate is found and `ifseveral` is the default `'last'` (not `'abort'`), the code sorts candidates by `latest_included_mc_index` then `level`, and if it still cannot distinguish them it throws synchronously from within the sort comparator: [3](#0-2) 

Notably, this unstable-candidate path has **no `sequence === 'good'` filter**, unlike the analogous existence check `dataFeedExists()`, which explicitly skips units whose `sequence !== 'good'`: [4](#0-3) 

This means `data_feed[[...]]` can (a) pick up a value from a unit that is later marked `final-bad` and therefore never gets persisted to the authoritative stable data-feed store at stabilization (data feeds of `final-bad` units are explicitly dropped and never written): [5](#0-4) 
and (b) throw an uncaught exception when two unstable AA-authored `data_feed` messages for the same oracle address happen to sit at the same `latest_included_mc_index` and DAG `level` — a condition any address that is an AA (including an attacker-controlled one) can trivially create by emitting two `data_feed` messages from parallel/sibling unstable units (e.g., via two triggers processed as siblings, or two secondary-trigger branches) before either becomes stable.

### Impact Explanation
An uncaught `Error` thrown synchronously inside the formula-evaluation call chain used during AA trigger processing/stabilization is not a validation failure that can be cleanly bounced — it is a JS exception that propagates up through `evaluate()`/`handleTrigger()`/the stabilization routines in `main_chain.js`. Any full node that is executing the exact same deterministic AA trigger (which every full node must do to agree on state) hits the same crash path, since the input to the crash (an ambiguous sort of unstable data-feed candidates for a given oracle address at a given mci) is a property of the unit content the AA author (attacker) controls. This can stop stabilization on that trigger for every node that reaches it, i.e., the network becomes unable to confirm/progress past that unit — a network-halting DoS, not merely a single-node crash.

Independently of the crash path, the missing `sequence==='good'` filter (present in the sibling function `dataFeedExists` but absent in `readDataFeedValue`) allows an AA to base a state-changing decision on a data-feed value from a unit that will ultimately be excluded from the authoritative persisted feed once stability is finalized, which can make AA outcomes depend on transient, not-yet-final data.

### Likelihood Explanation
Reaching this requires only: (1) an AA that uses `data_feed[[...]]` referencing another AA address as oracle (a supported, documented feature, and used in this codebase's own tests, e.g. `test/ojson.test.js`), and (2) an attacker who controls (or triggers) an AA address that posts conflicting `data_feed` messages from two units that remain unstable simultaneously at the same mci/level — achievable by posting two trigger units in parallel that each cause the oracle AA to emit a `data_feed` response. No special privileges, hub/peer trust, or timing races beyond normal DAG posting are required, and it is reachable purely by an unprivileged AA-trigger sender.

### Recommendation
- Add a `sequence === 'good'` filter to the unstable-candidate loop in `readDataFeedValue()`, matching `dataFeedExists()`, so that only units that are actually eligible to become part of the authoritative history are considered.
- Replace the `throw Error("can't sort candidates ...")` inside the `.sort()` comparator with a deterministic, total-order tie-breaker (e.g., fall back to comparing `unit` hash lexicographically) so that ambiguous cases resolve deterministically instead of throwing, for both `bIncludeAllUnstable` and AA-restricted lookups.
- Consider requiring `ifseveral='abort'` semantics (a clean, catchable formula error) rather than an uncaught exception whenever multiple unstable candidates cannot be strictly ordered.

### Proof of Concept
1. Deploy Oracle AA `O` whose logic, on receiving a trigger, emits a `data_feed` message `{price: X}` where `X` is derived from `trigger.data` (attacker-controlled input), so the attacker can produce two different values from `O` on demand.
2. Deploy Consumer AA `C` containing `data_feed[[oracles='O', feed_name='price']]` (default `ifseveral='last'`) in its formula, used in a payout decision.
3. Attacker sends two separate trigger units to `O` that get included as siblings in the DAG (same level, same `latest_included_mc_index` before either stabilizes), causing `O` to emit two different, currently-unstable `data_feed` messages for `feed_name='price'`.
4. Before either of `O`'s response units stabilizes, attacker sends a trigger to `C`. When `C`'s trigger unit stabilizes and its formula is evaluated, `readDataFeedValue()` collects both `O` candidates; if they cannot be strictly ordered by `latest_included_mc_index`/`level`, the `.sort()` comparator throws an uncaught `Error`, crashing/breaking stabilization for every full node processing `C`'s trigger at that mci.
