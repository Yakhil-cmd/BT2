### Title
Unfiltered PR-label injection into task/rollback subprocess environment via `ReviewStack#env` bypasses `EnvironmentVariables.permit` whitelist - (File: `app/models/shipit/review_stack.rb`, `lib/shipit/task_commands.rb`, `lib/shipit/rollback_commands.rb`)

### Summary
`ReviewStack#env` unconditionally converts every PR label into an environment variable (`LABEL_NAME.upcase => "true"`) with no whitelist, and `TaskCommands#env`/`RollbackCommands#env` merge that hash directly into the `Command` environment that reaches `PTY.spawn`. Unlike the task-level env (which passes through `filter_rollback_envs`/`filter_deploy_envs`), the stack-level, label-derived env is never sanitized, so an unprivileged PR author can inject arbitrary variables — including `GIT_SSH_COMMAND` — into every command run for that stack, including rollback steps.

### Finding Description
The claimed binding: `Command#env['GIT_SSH_COMMAND']` spawned by `PTY.spawn` should equal the operator-configured ssh command (i.e., be absent, so real `ssh` is used). This binding is broken.

Path:
1. `LabelCapturingHandler#capture_labels` persists the raw label list from the webhook payload onto `stack.pull_request.labels` with no filtering: [1](#0-0) 
2. `ReviewStack#env` turns every label into an upcased env var, value `"true"`, unconditionally (no `EnvironmentVariables.permit`/whitelist call at all): [2](#0-1) 
3. `TaskCommands#env` (used directly by `Deploy`, and inherited by `RollbackCommands` via `DeployCommands`) merges `@stack.env` straight into the command environment, before merging `deploy_spec.machine_env` and `@task.env`: [3](#0-2) 
4. `RollbackCommands#env` only adds `'ROLLBACK' => '1'` on top of that inherited chain — it does not filter anything: [4](#0-3) 
5. `Command#start`/`#unbundled_env` merges `@env` (stringified) directly over `BASE_ENV`/`PATH` and spawns the child process with it via `PTY.spawn`: [5](#0-4) 

Root cause / why the whitelist doesn't help: `DeploySpec#filter_rollback_envs`/`filter_deploy_envs` (backed by `EnvironmentVariables#permit`) are only invoked on the **explicit, user-supplied** task env — e.g. in `Shipit::Api::RollbacksController#create`, `rollback_env = stack.filter_rollback_envs(params.env)` is computed and stored on the `Rollback` record (`@task.env`) — [6](#0-5) . That filtered value is merged last in `TaskCommands#env` (`.merge(@task.env)`), but the earlier `.merge(@stack.env)` call — which contains the label-derived vars — is never passed through `permit`. Existing tests confirm this is a known, intended feature for labels-as-env, with no name restriction: [7](#0-6) [8](#0-7) .

Attacker exploit flow: on a repository they own/control with review stacks enabled (`deploy_spec.supports_rollback?` true), the attacker opens a PR (creating/provisioning a `ReviewStack`), then labels the PR `GIT_SSH_COMMAND` (case-insensitive; `capture_labels` stores it verbatim, `ReviewStack#env` upcases it). This is entirely within the described unprivileged attacker capability ("label their own PR ... emit webhooks from a repository they own"). When an operator (or `continuous_deployment`) later triggers a rollback, `RollbackCommands#perform` builds `Command.new(rollback_step, env:, chdir:)` whose `env['GIT_SSH_COMMAND']` is `"true"` — a value fully attacker-controlled, not the operator-configured ssh binary. Any git invocation inside the rollback step (capistrano `deploy:rollback`, submodule updates, `checkout`/`clone` in `TaskCommands#clone`/`#checkout`, `StackCommands#fetch`/`#fetch_commit`) that goes over ssh will silently no-op (git replaces its ssh call with the literal command `true`, exit 0, no data transferred).

### Impact Explanation
An unprivileged PR author can force arbitrary environment variables (not limited to `GIT_SSH_COMMAND`) into every `Command` executed for their `ReviewStack`, including rollback and deploy steps, entirely bypassing the `EnvironmentVariables.permit` whitelist mechanism that exists specifically to prevent this. For `GIT_SSH_COMMAND`, this can cause ssh-backed git fetch/checkout/submodule operations inside a rollback to silently succeed without transferring data, letting a stale or attacker-favored commit remain "deployed" while the system believes the rollback completed — an unauthorized/incorrect deploy state. This is scoped per-repository/per-review-stack (the review stack the attacker's PR provisioned), so blast radius is limited to that stack's task execution environment, but repeatable on every labeled PR the attacker controls. This matches the Critical category ("unauthorized deploy, rollback ... state").

### Likelihood Explanation
Preconditions: review stacks enabled on the repository, an active (non-archived) `ReviewStack` for the attacker's PR, and `deploy_spec.supports_rollback?` true. No Shipit session, API token, or GitHub team membership is required — only the ability to label a PR on a repository the attacker controls, which is exactly the assumed attacker capability. The attacker cost is a single label add; the exploit is deterministic and repeatable on demand.

### Recommendation
Apply `EnvironmentVariables.permit`/an explicit whitelist to `@stack.env` (in particular the label-derived variables added by `ReviewStack#env`) before merging it into `TaskCommands#env`/`RollbackCommands#env`, or restrict label-to-env conversion to a configured allow-list of variable names, and reject/strip label names that collide with security-sensitive variable names (e.g. `GIT_SSH_COMMAND`, `PATH`, `LD_PRELOAD`, `BUNDLE_*`).

### Proof of Concept
```ruby
# test/lib/shipit/rollback_commands_test.rb (new test)
test "#perform does not let PR labels inject GIT_SSH_COMMAND into rollback env" do
  stack = shipit_stacks(:review_stack)
  stack.pull_request.labels = ["GIT_SSH_COMMAND"]
  rollback = stack.rollbacks.build(since_commit: stack.commits.first, until_commit: stack.commits.last)
  commands = Shipit::RollbackCommands.new(rollback)
  commands.stubs(:deploy_spec).returns(stub(
    rollback_steps!: ['git fetch origin'],
    machine_env: {},
    directory: nil
  ))

  command = commands.perform.first

  # Binding under test: subprocess GIT_SSH_COMMAND should equal the operator-configured
  # ssh command (absent/nil), NOT the attacker's label-derived value.
  assert_nil command.env['GIT_SSH_COMMAND'],
    "expected no GIT_SSH_COMMAND override, got #{command.env['GIT_SSH_COMMAND'].inspect} " \
    "injected via PR label"
end
```
Running this against the current code fails: `command.env['GIT_SSH_COMMAND']` equals `"true"` (from the label), demonstrating the injected binding.

    def start(&block)
      return if @started

      @control_block = block
      @out = @pid = nil
      FileUtils.mkdir_p(@chdir)
      begin
        @out, child_in, @pid = PTY.spawn(unbundled_env, *interpolated_arguments, chdir: @chdir)
        child_in.close
      rescue Errno::ENOENT
        raise NotFound, "#{Shellwords.split(interpolated_arguments.first).first}: command not found"
      rescue Errno::EACCES
        raise Denied, "#{Shellwords.split(interpolated_arguments.first).first}: Permission denied"
      end
      @started = true
      self
    end

    def unbundled_env
      BASE_ENV.merge('PATH' => "#{Shipit.shell_paths.join(':')}:#{ENV['PATH']}").merge(@env.stringify_keys)
    end
