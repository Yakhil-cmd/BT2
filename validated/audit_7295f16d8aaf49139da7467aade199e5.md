### Title
Remote proxy delay bypass via stale storage root retained in `BlockToRoot` - (File: pallets/remote-proxy/src/lib.rs)

### Summary
`Pallet::do_remote_proxy` resolves the storage root to verify a remote proxy proof purely by attacker-supplied `block` number looked up in `BlockToRoot`, which retains up to `MaxStorageRootsToKeep` historical roots regardless of whether the proxy's remote state has since changed. Because the `delay` field used for the `Unannounced` check is read directly from whatever historical `ProxyDefinition` the proof anchors to, an attacker can present an old proof from before a delay was configured to immediately execute a call that should require a timelock.

### Finding Description
In `do_remote_proxy` [1](#0-0) , the `block` field inside the caller-supplied `RemoteProxyProof::RelayChain` is used to binary-search `BlockToRoot` for a matching storage root, with no requirement that this be the *latest* or *current* root — any of the up-to-`MaxStorageRootsToKeep` roots stored via `on_validation_data` is accepted [2](#0-1) .

The trie proof is then verified against that historical root and decoded into a `ProxyDefinition` list, from which the matching definition for `who`/`force_proxy_type` is selected [3](#0-2) . The `delay` value used for the enforcement check comes directly from this historically-anchored definition:

```rust
ensure!(def.delay.is_zero(), Error::<T, I>::Unannounced);
Self::do_proxy(def, real, call);
``` [4](#0-3) 

If the remote proxy relationship was originally created with `delay = 0` and was later updated on the remote chain to `delay > 0`, an attacker who captured (or can reconstruct via a full/archive node) the proof and root from the earlier block can still submit that old `block` number as long as its root remains in `BlockToRoot` (bounded by `MaxStorageRootsToKeep`). The pallet has no mechanism to invalidate a `ProxyDefinition`'s field values based on "freshness" beyond the coarse root-retention window — it only checks that *some* retained root anchors the proof, not that the proof reflects the *current* delay configuration. This lets the attacker's `remote_proxy` call pass the `Unannounced` check and immediately execute `Self::do_proxy`, bypassing the delay/timelock that `pallet_proxy`'s local announcement mechanism is meant to enforce.

Notably, the pallet's own doc comments acknowledge a related staleness caveat for proxy *removal* ("the caller will be able to provide an old proof at which the proxy was still available") [5](#0-4) , but this same staleness property extends to any mutable field of the `ProxyDefinition`, including `delay`, which is a distinct and more severe security consequence than simple proxy revocation lag: it can nullify the delay-based defense entirely for the retention window, not merely delay its removal.

### Impact Explanation
An attacker with a proxy relationship that once had `delay = 0` can execute arbitrary calls authorized by that proxy definition (subject to `proxy_type` filters) immediately, without the timelock/announcement step that `delay > 0` is supposed to enforce, for as long as the pre-delay-update root remains within `MaxStorageRootsToKeep`. This defeats the intended timelock security control (e.g., allowing an operator to react to and cancel malicious proxy actions before they execute) and can enable unauthorized immediate execution of privileged-on-behalf-of-`real` calls such as asset transfers, undermining the "no bypass of proxy proof/timelock checks" invariant.

### Likelihood Explanation
Feasibility depends on: (1) the remote proxy definition existing with `delay = 0` at some point and later being updated to `delay > 0` (a normal governance/self-service action on the remote chain), and (2) the older block's storage root still residing in `BlockToRoot`, bounded by `T::MaxStorageRootsToKeep`. Both conditions are realistic operational scenarios (e.g., a user tightens their own proxy security by adding a delay after initially setting delay=0), and the attack requires only a signed extrinsic (`remote_proxy`) with a proof/root that was valid at an earlier point — no privileged access or malicious relayer/node collusion needed, since users can retain proofs/roots they observed live on-chain.

### Recommendation
Enforce that anchored proofs reflect a recent-enough remote state relative to when the delay was last modified — for example, by additionally checking that the anchored `block` is no earlier than a stored "delay change" watermark for that specific proxy relationship, or by requiring the proof's block to be the *latest* available root rather than any historically retained one when validating delay-sensitive fields.

### Proof of Concept
Rust unit test outline (in `pallets/remote-proxy/src/tests.rs` style):
1. Create a remote proxy relationship for `who -> real` with `delay = 0`; call the mock's `block_to_storage_root` hook (or drive `on_validation_data`) to populate `BlockToRoot` with `(block_1, root_1)` reflecting this state; capture the corresponding trie proof for `block_1`.
2. Advance blocks and update the remote proxy relationship's `delay` to a non-zero value; drive further `on_validation_data` calls so `BlockToRoot` now also contains `(block_2, root_2)` for the updated state, while `(block_1, root_1)` remains present (within `MaxStorageRootsToKeep`).
3. Call `Pallet::remote_proxy(origin_who, real, None, call, RemoteProxyProof::RelayChain { proof: proof_from_block_1, block: block_1 })`.
4. Assert the call **succeeds and executes `call` immediately** (no `Unannounced` error), despite the proxy currently requiring `delay > 0` on the remote chain — demonstrating the timelock bypass via a stale but still-retained root/proof.

		fn on_validation_data(validation_data: &PersistedValidationData) {
			let Some((block, hash)) = T::RemoteProxy::block_to_storage_root(validation_data) else {
				return;
			};

			// Update the block to root mappings.
			BlockToRoot::<T, I>::mutate(|roots| {
				let delete_up_to =
					block.clone().saturating_sub(T::MaxStorageRootsToKeep::get().into());

				while roots.first().is_some_and(|f| f.0 <= delete_up_to) {
					roots.remove(0);
				}

				// We always remove all the old items before, thus there should always be space in
				// the vector.
				let _res = roots.try_push((block, hash));
				debug_assert!(_res.is_ok());
			});
		}
