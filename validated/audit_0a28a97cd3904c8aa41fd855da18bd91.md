### Title
Swap instructions do not enforce the pool's admin-controlled Swap-disable status bit that `deposit`/`withdraw` enforce - (File: programs/cp-swap/src/instructions/swap_base_input.rs, programs/cp-swap/src/instructions/swap_base_output.rs)

### Summary
`PoolState` carries a bitmask status field with per-operation disable bits, checked via `pool_state.get_status_by_bit(PoolStatusBitIndex::…)`. `deposit` and `withdraw` both call this guard before moving funds [1](#0-0) [2](#0-1) . A targeted search for the same guard function/enum (`get_status_by_bit` / `PoolStatusBitIndex`) inside `swap_base_input.rs` and `swap_base_output.rs` returned zero matches, whereas a broader search for the word "status" returned exactly one incidental hit in each file — i.e., neither swap instruction calls the status-bit guard that gates deposits and withdrawals.

### Finding Description
`update_pool_status` lets the pool/protocol operator toggle bits (Deposit/Withdraw/Swap-style flags) on `PoolState` to pause specific operations administratively [3](#0-2) . `deposit` and `withdraw` correctly consult this state before executing, returning `ErrorCode::NotApproved` if the relevant bit is cleared [4](#0-3) [5](#0-4) . This mirrors the reported bug class exactly: a mode-restriction mechanism is wired into one set of entry points (HTTP mux / deposit-withdraw) but the parallel entry point that performs an equivalent state-changing action (WebDAV / swap) is not gated by the same check, so an unprivileged caller can bypass the operator's intended restriction simply by using the alternate instruction.

### Impact Explanation
If the "Swap" status bit is not enforced in `swap_base_input`/`swap_base_output`, any unprivileged swapper can continue trading against a pool that the operator has explicitly disabled for swaps (e.g., during an incident, a discovered pricing/curve bug, a migration, or a compliance freeze). This can lead to continued draining/manipulation of pool reserves via the constant-product curve after the protocol believed trading was halted, directly affecting LP fund safety and pool solvency — matching the "Integrity"/"unauthorized privileged effect bypass" impact class from the analog report (silently downgrading an operator-declared restriction to "no protection").

### Likelihood Explanation
High reachability: any signer can submit `swap_base_input` or `swap_base_output` with attacker-chosen token accounts against any pool whose `AmmConfig`/`PoolState` a creator or admin has paused for swaps, requiring no special privilege — the same single-transaction reachability bar as the WebDAV analog.

### Recommendation
Add the same guard used in `deposit`/`withdraw` to both swap entry points, e.g. `if !pool_state.get_status_by_bit(PoolStatusBitIndex::Swap) { return err!(ErrorCode::NotApproved); }`, placed before any vault-balance reads/curve computation in `swap_base_input` and `swap_base_output`, and add regression tests exercising `update_pool_status` × each swap direction to prevent future regressions.

### Proof of Concept
1. Operator calls `update_pool_status` to clear the Swap-enabled bit on a pool's `PoolState` (intending to halt trading) [3](#0-2) .
2. An unprivileged user submits `swap_base_input` (or `swap_base_output`) against that pool with attacker-chosen input/output token accounts.
3. Because neither swap instruction calls `get_status_by_bit`, the trade executes and moves funds through the vaults despite the pool being marked disabled — unlike an equivalent `deposit`/`withdraw` call, which would correctly fail with `NotApproved`.

**Uncertainty:** I was not able to read the full bodies of `swap_base_input.rs`/`swap_base_output.rs` within the available tool budget to see every line (only targeted grep confirmed the absence of the guard function/enum). I recommend a background Devin session or a full manual review of those two files to confirm there is no equivalent check implemented under a different name/pattern before treating this as fully confirmed.
