### Title
Stack-scoped API token can read CCMenu status of any stack, bypassing its `stack_id` binding - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::ApiClient` records can be scoped to a single stack via `stack_id`, and this scoping is meant to be enforced by `Api::BaseController#stack`, which restricts lookups to `stacks` (filtered by `current_api_client.stack_id`). `Api::CCMenuController` overrides `#stack` to look up `Stack.from_param!(params[:stack_id])` directly against the entire `Stack` table, ignoring the scoping filter entirely. Any valid API token with `read:stack` permission — even one deliberately scoped to a single stack — can therefore fetch the CCMenu status (build/deploy state, last build label, web URL) of any other stack in the installation.

### Finding Description
`ApiClient#check_permissions!` only validates the operation/scope string (e.g. `read:stack`) against the client's `permissions` array; it never checks the client's `stack_id`: [1](#0-0) 

Stack-level scoping is enforced separately, in `Api::BaseController`, via the `stacks`/`stack` helper methods: [2](#0-1) 

`Api::CCMenuController` bypasses this by redefining `stack` to query `Stack.from_param!(params[:stack_id])` unscoped, and also swaps in a token-based authentication method that doesn't otherwise change this behavior: [3](#0-2) 

The route accepts an arbitrary `stack_id` path segment independent of the authenticating token: [4](#0-3) 

The binding broken: `stack a token authorises` (`current_api_client.stack_id`, enforced elsewhere via `stacks.from_param!`) `≠` `stack a token touches` (`Stack.from_param!(params[:stack_id])`, unscoped) for this specific controller.

### Impact Explanation
This qualifies as **High** severity per the rubric: "unauthenticated read of stack state" analog — more precisely, an authenticated-but-narrowly-scoped token achieves an unauthorized read of stack state (deploy/build status, lock status, web URL) outside its authorized stack. A token intentionally minted for one repository/stack (e.g. via `CCMenuUrlController#client`, which creates a `read:stack` client scoped to a specific stack for embedding in third-party CI dashboards) can be used to enumerate/read the deploy status of every other stack hosted on the same Shipit instance.

### Likelihood Explanation
Likelihood is high given intended use: stack-scoped CCMenu tokens are explicitly generated and exposed to end users/embedded dashboards by `CCMenuUrlController`: [5](#0-4) 

Anyone who legitimately possesses such a token (e.g. copied from a CI dashboard config, or leaked via a public build status page) can trivially swap the `stack_id` in the URL to query any other stack, with no further credentials needed.

### Recommendation
In `Api::CCMenuController`, use the inherited scoped `stack` lookup (via `stacks.from_param!(params[:stack_id])`) instead of the unscoped `Stack.from_param!`, so the `current_api_client.stack_id` restriction is honored consistently with the rest of the API surface.

### Proof of Concept
1. Create (or obtain) an `ApiClient` scoped to `stack_id: A` with `permissions: ['read:stack']` (as done by `CCMenuUrlController#client` for stack A).
2. Using that client's `authentication_token`, request `GET /api/stacks/<owner>/<repo-B>/<env-B>/ccmenu?token=<token>` where stack B is a *different* stack than the one the token was scoped to.
3. Observe `200 OK` with stack B's build/deploy status returned, even though the token was never authorized for stack B — demonstrated by the absence of any stack-scoping assertion in `test/controllers/api/ccmenu_controller_test.rb`, contrasted with the explicit scoping test present for `Api::StacksController`: [6](#0-5)
