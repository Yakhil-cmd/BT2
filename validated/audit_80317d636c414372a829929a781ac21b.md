## Analog Found: ERC20 Asset Transactor assumes transferred amount == received amount for fee-on-transfer / non-standard ERC20 tokens

The Sherlock report's core defect — "assumes transferred amount equals received amount, which is not the case for fee-on-transfer tokens, destroying accounting" — has a direct analog in the `ERC20Transactor` XCM `TransactAsset` implementation, which bridges arbitrary Solidity ERC20 contracts (via `pallet-revive`) into the XCM asset-holding accounting model on Asset Hub.

### Title
XCM `ERC20Transactor` credits/debits the nominal `amount` instead of the actually-transferred balance, breaking holding-register accounting for fee-on-transfer ERC20 tokens - (File: `cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs`)

### Summary
`ERC20Transactor::withdraw_asset_with_surplus` and `deposit_asset_with_surplus` move value between a user and a shared `TransfersCheckingAccount` by calling the target ERC20 contract's Solidity `transfer()` function, and treat the call as fully successful — crediting/debiting the XCM `AssetsInHolding` register with the exact nominal `amount` — as soon as the contract returns `true`. Neither function checks the checking account's actual token balance before/after the call, so any ERC20 that does not move a full 1:1 amount on `transfer()` (fee-on-transfer, deflationary/rebasing tokens, or any non-standard implementation) desynchronizes the XCM holding register from the real balance held by the shared checking account.

### Finding Description
`ERC20Transactor` is wired into Asset Hub Westend's `AssetTransactors` tuple: [1](#0-0) 

It is matched via `ERC20Matcher`, which accepts **any** local `AccountKey20` location as an asset id — i.e., any Solidity contract address a user names in their XCM program is treated as a valid ERC20 "asset": [2](#0-1) 

On `WithdrawAsset`, `withdraw_asset_with_surplus` calls `IERC20::transfer(checking_address, amount)` on the user-specified contract and, if the call succeeds and doesn't revert, unconditionally mints `Erc20Credit(amount)` into `AssetsInHolding` — the *requested* `amount`, not any measured balance delta of the checking account: [3](#0-2) 

Symmetrically, on `DepositAsset`, `deposit_asset_with_surplus` calls `IERC20::transfer(beneficiary, amount)` **from** the checking account using the nominal `amount` taken out of holding, again only checking the boolean return value: [4](#0-3) 

`TransfersCheckingAccount` is a single fixed, shared account for *all* ERC20 XCM operations on the chain (`ERC20TransfersCheckingAccount` derived from a fixed `PalletId`): [5](#0-4) 

This is reachable by any signed, unprivileged account through `pallet_xcm::execute`, `transfer_assets`, or any of the reserve-transfer extrinsics, since the ERC20 asset is user-selectable in the `Assets`/`WithdrawAsset`/`DepositAsset` XCM instructions — no governance, no privileged role, and no malicious relayer/collator/validator is required.

**Root cause mapped to the report's invariant:** just like `AccountManager` assumed `transfer()` moves exactly `amount` to `LToken`, `ERC20Transactor` assumes the ERC20 contract's `transfer()` return value of `true` implies the checking account's real balance changed by exactly `amount`. For fee-on-transfer, deflationary, or otherwise non-standard ERC20 contracts, this is false: the checking account actually receives/sends `amount - fee`, while the runtime's `AssetsInHolding` ledger (and hence all downstream XCM logic — `DepositAsset`, `RefundSurplus`, reserve transfers, `pallet-xcm` events) continues to track the un-discounted nominal `amount`.

### Impact Explanation
Because `TransfersCheckingAccount` is a single account shared by every user and every ERC20 registered through this transactor, the accounting desync is not confined to the depositing user:
- Each fee-on-transfer withdraw leaves the checking account's *real* balance short of what the holding register implies was received.
- A subsequent `DepositAsset` for the full nominal amount will attempt to move more real tokens out of the checking account than are actually backed, which either (a) reverts (denial of service / stuck XCM, funds trapped via `AssetTrap`), or (b) succeeds by drawing down real balance that was actually contributed by *other* users of the same ERC20, letting an attacker who structures withdraw+deposit sequences ahead of other users extract more real value from the shared pool than they net-deposited.
- This directly mirrors the original report's impact: "destroys the accounting ... and is bad for the token holders" — here, holders of the shared checking-account pool for that ERC20.

This is a genuine Medium-severity accounting-integrity bug (per the original report's own accepted severity), not a theft-of-arbitrary-funds bug, since it is bounded by the specific ERC20 contract's token economy and the shared checking account's balance for that contract.

### Likelihood Explanation
Fee-on-transfer/deflationary ERC20 contracts are a common, legitimate token design (not attacker-privileged or exotic) that can be freely deployed via `pallet-revive` and then simply *referenced* as an XCM asset id by any signed user — no special permission, no governance action, no malicious external actor is needed. Any user choosing to move such a token through `pallet_xcm::execute`/`transfer_assets` triggers the mismatched accounting deterministically on every operation.

### Recommendation
`ERC20Transactor` should measure the checking account's (or beneficiary's) actual `balanceOf` before and after the `transfer()` call and credit/debit `AssetsInHolding` with the *measured delta*, not the requested `amount` — exactly the fix Sherlock recommended for `AccountManager`. Alternatively, explicitly document/enforce (e.g., via an allow-list or a supply-invariant check) that only strictly-conforming, non-fee ERC20 tokens may be registered through this transactor.

### Proof of Concept
- Program: Parity Bug Bounty (Asset Hub Westend runtime, `assets-common` crate, live in-repo via `pallet_revive`-enabled Asset Hub runtimes).
- Failed guard: no balance-delta verification in `withdraw_asset_with_surplus` (erc20_transactor.rs:159-203) or `deposit_asset_with_surplus` (erc20_transactor.rs:251-298); only the boolean `transfer()` return value is checked.
- Suggested minimal repro (to be executed as a FRAME/pallet-revive + `pallet-xcm` integration test, analogous to the existing `smart_contract_does_not_return_bool_fails` test at `cumulus/parachains/runtimes/assets/asset-hub-westend/tests/tests.rs:2026-2082`):
  1. Deploy a Solidity contract implementing `IERC20` where `transfer(to, value)` moves only `value * 99 / 100` to `to` but returns `true` for the full nominal `value` (a standard fee-on-transfer pattern), register it as `ERC20Matcher` asset (its `AccountKey20` address).
  2. Fund the sender's ERC20 balance, then call `PolkadotXcm::execute` with an XCM program: `WithdrawAsset((erc20_location, amount))`, `DepositAsset(All, beneficiary)`.
  3. Observe: `withdraw_asset_with_surplus` credits `AssetsInHolding` with the full `amount` (erc20_transactor.rs:197-203) even though the checking account's real `balanceOf` only increased by `amount * 0.99`.
  4. `deposit_asset_with_surplus` then attempts `transfer(beneficiary, amount)` from the checking account for the full nominal `amount` (erc20_transactor.rs:253), which must revert with insufficient balance once the checking account's cumulative real shortfall exceeds its buffer — demonstrating the assert `checking_account_real_balance == sum(nominal_amounts_ever_withdrawn)` is false, and that legitimate deposits for other holders of the same asset can be blocked/reverted (`XcmError::FailedToTransactAsset("ERC20 contract transfer failed")`, erc20_transactor.rs:281-287) or asset-trapped by the executor.
- Deployment/PoC execution status: analysis performed via static code reading only; no test was executed against a live network or local harness in this session — the reproduction above is a concrete, minimal integration-test design based on existing test scaffolding (`smart_contract_does_not_return_bool_fails`) in the repository, not a claimed run.

pub struct IsLocalAccountKey20;
impl Contains<Location> for IsLocalAccountKey20 {
	fn contains(location: &Location) -> bool {
		matches!(location.unpack(), (0, [AccountKey20 { .. }]))
	}
}

/// Fallible converter from a location to a `H160` that matches any location ending with
/// an `AccountKey20` junction.
pub struct AccountKey20ToH160;
impl MaybeEquivalence<Location, H160> for AccountKey20ToH160 {
	fn convert(location: &Location) -> Option<H160> {
		match location.unpack() {
			(0, [AccountKey20 { key, .. }]) => Some((*key).into()),
			_ => None,
		}
	}

	fn convert_back(key: &H160) -> Option<Location> {
		Some(Location::new(0, [AccountKey20 { key: (*key).into(), network: None }]))
	}
