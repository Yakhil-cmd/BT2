### Title
Api::StacksController#create ignores current_api_client.stack_id scope, allowing a stack-scoped write:stack token to create stacks against arbitrary repositories - (File: app/controllers/shipit/api/stacks_controller.rb)

### Summary
`Api::StacksController#create` builds a brand-new `Stack` and attaches an attacker-controlled `Repository` (`find_or_create_by(owner: repo_owner, name: repo_name)`) without ever consulting the `stacks`/`stack` scoping helpers that enforce `current_api_client.stack_id`. Any token with the `write:stack` permission - even one issued and scoped to a single, unrelated stack - can therefore create a new stack for any repository name/owner the attacker supplies.

### Finding Description
The intended binding is: *an ApiClient scoped to stack A (`current_api_client.stack_id == A.id`) must only be able to write within stack A's repository, i.e. `current_api_client.authorized_repository == stack.repository`.* This never holds for `#create`.

`Api::BaseController` implements scope enforcement in two places only:
- `stacks` — `current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all` [1](#0-0) 
- `stack` — `stacks.from_param!(params[:stack_id])` [2](#0-1) 

`require_permission!` only checks the static permission string via `ApiClient#check_permissions!`, which is nothing more than `permissions.include?("#{operation}:#{scope}")` — it never looks at `stack_id` or any repository: [3](#0-2) 

`StacksController#create` does not call `stacks` or `stack` at all — it constructs the `Stack` directly and resolves the repository purely from request params:
```ruby
def create
  stack = Stack.new(create_params)
  stack.repository = repository
  stack.save
  render_resource(stack)
end
...
def repository
  @repository ||= Repository.find_or_create_by(owner: repo_owner, name: repo_name)
end
``` [4](#0-3) [5](#0-4) 

The route is `POST /api/stacks` with no `stack_id` path segment at all (unlike `update`/`destroy`, which are nested under `/stacks/*id`): [6](#0-5) , so there is no `stack_id` to scope against even if the controller wanted to check it.

That `ApiClient` records can genuinely be scoped to a single stack (`belongs_to :stack, optional: true`, and `stack_id` scoping is exercised by `"an api client scoped to a stack will only see that one stack"`) is confirmed by the model and existing test suite: [7](#0-6) [8](#0-7) .

Exploit flow: attacker holds a legitimate `write:stack`-permissioned token belonging to `ApiClient` with `stack_id = A` (issued, e.g., for CI on their own stack A). They send `POST /api/stacks` with `repo_owner`/`repo_name` naming a completely different repository X (including one they have no GitHub relationship to). `check_permissions!(:write, :stack)` passes because the permission string matches, regardless of `stack_id`. `repository` looks up/creates repository X unconditionally, and `stack.save` persists a brand-new `Stack` bound to X. No guard - `require_permission`, `ExplicitParameters` schema, or model validation (`Stack`/`Repository` validators only check format, not ownership) - checks that repo X falls within the token's authorized scope.

### Impact Explanation
A token holder authorized only for one stack/repository can unilaterally create a new `Stack` (and implicitly a `Repository` record) for any other repository name, including private orgs the attacker has no relationship to. This is a cross-tenant write: a credential scoped to repository A mutates state for repository X. Once created, the stack can be targeted by subsequent API calls (deploys, tasks, locks) if the attacker also holds broader permissions, and at minimum it litters/squats on repository namespaces and can disrupt legitimate later stack creation by the real owner (duplicate-repository uniqueness conflicts). This matches the Critical category: "a payload for one repository mutating another's stack ... or an unauthorized deploy."

### Likelihood Explanation
Preconditions are modest: attacker needs any valid `ApiClient` token with `write:stack` permission, however narrowly that client was intended to be scoped (`stack_id` set to an unrelated stack). Such tokens are commonly issued for CI integrations tied to a single stack via the web UI/API-client management flow. No GitHub relationship to the target repository, no Shipit session, and no additional secrets are required — a single unauthenticated-w.r.t.-target-repo HTTP POST suffices, and it is fully repeatable against arbitrary `repo_owner`/`repo_name` values.

### Recommendation
In `Api::StacksController#create`, when `current_api_client.stack_id?` is true, reject the request (or force `repository` to equal `current_api_client.stack.repository`) instead of trusting attacker-supplied `repo_owner`/`repo_name`. More generally, `check_permissions!`/`require_permission!` should be extended to take the target repository/stack into account for stack-scoped clients, not just the bare `operation:scope` string.

### Proof of Concept
```ruby
test "#create with a stack-scoped write:stack token creates a stack for an unrelated repository" do
  scoped_client = shipit_api_clients(:here_come_the_walrus) # stack_id points to an unrelated stack
  scoped_client.update!(permissions: ['write:stack'])
  authenticate!(:here_come_the_walrus)

  assert_difference -> { Stack.count } do
    post :create, params: {
      repo_owner: 'attacker-named-org',
      repo_name: 'private-repo-not-owned-by-token',
      environment: 'production',
      branch: 'main'
    }
  end

  assert_response :ok
  new_stack = Stack.last
  # Binding under test: current_api_client.stack_id-scoped repository == new_stack.repository
  # This assertion FAILS today, proving the scope is not enforced:
  refute_equal scoped_client.stack.repository, new_stack.repository
  assert_equal 'attacker-named-org', new_stack.repository.owner
  assert_equal 'private-repo-not-owned-by-token', new_stack.repository.name
end
```
