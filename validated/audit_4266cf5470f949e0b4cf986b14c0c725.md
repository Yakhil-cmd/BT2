### Title
Git-sync approves the top-level repo credentials host-wide, leaking them to attacker-controlled submodule URLs on the same host - (File: `main.go`)

### Summary
git-sync stores the operator-supplied username/password or GitHub App installation token by calling `git credential approve` with the *repo URL* only (host+scheme), not scoped to a specific path. Since git's default credential matching (`credential.useHttpPath=false`) is host-scoped, any subsequent git network operation to the same host — including a fetch of an attacker-controlled submodule declared in a synced repo's `.gitmodules` — will cause git to automatically supply the stored credential to that attacker-controlled endpoint. This is the git-sync analog of the Trail of Bits "insufficient protection of sensitive keys" finding: the secret (an owner-equivalent git credential/token) is not scoped/protected tightly enough, and an attacker who can push content (a `.gitmodules` file) reachable by git-sync can cause that secret to be disclosed to infrastructure they control.

### Finding Description
`StoreCredentials` approves credentials for `git.repo` as a whole: [1](#0-0) 

Both the static username/password path and the dynamic GitHub App token path call this same function using only the top-level `--repo` URL: [2](#0-1) [3](#0-2) 

git-sync does support recursive submodule fetching, and the README itself acknowledges that submodules can point at different hosts/credentials, which is why it added a separate `--credential` flag specifically "for specific URLs, for example when using submodules": [4](#0-3) 

That flag is opt-in. When an operator uses the simpler and far more common `--username`/`$GITSYNC_PASSWORD` (or GitHub App) auth without also configuring `--credential` per submodule URL, the credential is registered by git only at host granularity (git's `credential.helper` protocol defaults to matching by `protocol://host`, not full path, unless `credential.useHttpPath` is explicitly set — which git-sync never sets). A commit pushed to the synced repo that adds/updates a `.gitmodules` entry pointing to a different path or repository on the *same host* (e.g., a different project on the same GitHub Enterprise/GitLab instance, or even a public fork under a different org on github.com when using GITSYNC_PASSWORD/App token credentials) will cause git, during the automatic submodule fetch that git-sync performs as part of `SyncRepo`, to present the stored credential to that attacker-chosen path.

### Impact Explanation
This results in credential/token disclosure to an attacker-controlled or attacker-observable endpoint (the submodule's git server can log the Basic-Auth header/token used to fetch it). Depending on the scope of the leaked token (a PAT, GitHub App installation token, or username/password), this can grant read/write access to private repositories, enabling supply-chain tampering of content git-sync later publishes to `--root`/`--link`, or further compromise of the underlying git hosting account — directly matching the "compromise of keys enabling theft/control" impact from the original ToB report, adapted to git-sync's credential/token disclosure surface.

### Likelihood Explanation
This is reachable purely from repository content: any actor with push/PR-merge access sufficient to modify `.gitmodules` in the synced repo (or its already-included submodules) can trigger it — no additional flags or operator misconfiguration beyond the common `--username`/`$GITSYNC_PASSWORD` or GitHub App auth setup are required, since `--credential` per-submodule scoping is optional and not the default guidance emphasized for basic username/password use. Because git-sync's `AUTHENTICATION` docs describe username/password and GitHub App auth as the primary "natural" mechanisms and treat `--credential` as an addendum only "when using submodules," many deployments plausibly only configure the single top-level credential.

### Recommendation
- When configuring git credentials for the primary `--repo`, always set `credential.useHttpPath=true` (or equivalent path-restriction) so the stored credential is not replayed to other paths/projects on the same host.
- Require/auto-enable per-submodule `--credential` scoping (or refuse to approve host-wide credentials) whenever submodules are enabled, so a credential for the top-level repo can never satisfy a fetch for a different repository path discovered via `.gitmodules`.
- Document and, ideally, enforce in code that `StoreCredentials` should be called with the narrowest possible URL (including path) rather than the bare `git.repo` host, consistent with the "avoid over-broad access" recommendation in the original audit.

### Proof of Concept
1. Operator runs git-sync against `https://git.example.com/org/main-repo` using `--username=bot --password-file=/creds/token` (no `--credential` overrides), with submodule recursion enabled.
2. An attacker with push access to `main-repo` (or a merged PR) adds a `.gitmodules` entry: `url = https://git.example.com/attacker/evil-repo`.
3. On the next sync, git-sync's `SyncRepo` fetch path clones/updates submodules, and git — matching by host only (`credential.useHttpPath` unset) — sends the `bot`/token Basic-Auth credential to `https://git.example.com/attacker/evil-repo`.
4. The attacker, who controls `evil-repo`'s hosting/logging (e.g., a repo they own on the same multi-tenant git server), captures the `bot` credential from the inbound request, obtaining a live token usable against the org's git server.

```go
// StoreCredentials stores a username and password for later use.
func (git *repoSync) StoreCredentials(ctx context.Context, url, username, password string) error {
	git.log.V(1).Info("storing git credential", "url", redactURL(url))
	git.log.V(9).Info("md5 of credential", "url", url, "username", md5sum(username), "password", md5sum(password))

	creds := fmt.Sprintf("url=%v\nusername=%v\npassword=%v\n", url, username, password)
	_, _, err := git.RunWithStdin(ctx, "", creds, "credential", "approve")
	if err != nil {
		return fmt.Errorf("can't configure git credentials: %w", err)
	}

	return nil
}
```
