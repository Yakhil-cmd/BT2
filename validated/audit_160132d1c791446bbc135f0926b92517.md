### Title
Webhook signature verification silently no-ops when an organization has no `webhook_secret`, allowing forged `membership` events to escalate into `Shipit.github_teams` authorization - ([File: lib/shipit/github_app.rb])

### Summary
`GitHubApp#verify_webhook_signature` returns `true` (i.e. "verified") whenever the configured GitHub App/organization has no `webhook_secret` set, without checking the supplied `X-Hub-Signature` header at all. `Shipit::WebhooksController#verify_signature` selects which app/secret to validate against using an **unauthenticated payload field** (`repository.owner.login` / `organization.login`), and then dispatches the same unauthenticated JSON body to event handlers such as `MembershipHandler`, which directly mutates `Team`/`Membership` records used by `User#authorized?` to gate access via `Shipit.github_teams`. This mirrors the reported bug class: a value that should gate/limit a privileged action (the verified signature) is not actually enforced, and the downstream code proceeds to act on the full, unchecked attacker payload instead of a value actually covered by the check.

### Finding Description
`WebhooksController#verify_signature` resolves the GitHub App using the organization named inside the untrusted JSON body: [1](#0-0) [2](#0-1) [3](#0-2) 

The actual signature check is: [4](#0-3) 

Because `verify_webhook_signature` returns `true` unconditionally when `webhook_secret` is blank for the resolved organization, any organization configured in `Shipit.github` without a `webhook_secret` accepts **any** payload with **any** (or no) `X-Hub-Signature` header — the "verification" step performs no cryptographic check at all for that org. The controller then dispatches the raw, unverified JSON body straight to registered handlers: [5](#0-4) 

The `membership` event is routed to `MembershipHandler`, which creates/updates `Team` records and adds/removes `Membership` rows purely from payload content, with no additional authorization check: [6](#0-5) 

Those `Membership`/`Team` records directly back `User#authorized?`, which is the authorization gate enforced by `Shipit::Authentication#force_github_authentication` for every engine controller: [7](#0-6) [8](#0-7) 

**The equality/binding broken:** the organization whose signature is (nominally) checked ≠ the organization whose team membership is actually written, because the "check" is a no-op for orgs without a secret. Put differently: `verify_webhook_signature` is supposed to bind "payload accepted" to "signed by the real GitHub App secret", but for any misconfigured/secret-less organization entry, "payload accepted" is unconditionally true regardless of what (if anything) signs the request — the signature-verification binding never actually applies, yet the full payload is still trusted for privileged mutations (team membership, which gates `Shipit.github_teams` authorization).

### Impact Explanation
An unprivileged network attacker who can reach the `/webhooks` endpoint of a Shipit deployment can forge a `membership` `action: added` event naming any configured organization that lacks a `webhook_secret`, adding an arbitrary GitHub login to any team tracked by Shipit (including a team listed in `Shipit.github_teams`). Since `User#authorized?` is solely driven by team membership (`teams.where(id: Shipit.github_teams.map(&:id)).exists?`), this is a direct escalation into `Shipit.github_teams` authorization — allowing an unauthorized identity to pass the application-wide access gate and reach all Shipit UI/actions as an "authorized" user, including deploys/rollbacks once that GitHub identity also has a valid GitHub OAuth session. This matches the High-impact category "escalation into `Shipit.github_teams` authorization."

### Likelihood Explanation
Likelihood depends entirely on host configuration: it is only exploitable for organizations configured in `Shipit.github` without a `webhook_secret`. Where every configured organization has a `webhook_secret` set, the analog does not apply. This is a real code-level footgun (silent verification bypass rather than a hard failure) rather than a certainty for every deployment — the code should fail closed (reject) instead of returning `true` when no secret is configured, or Shipit should require `webhook_secret` to be present as a hard precondition for enabling webhook-driven team membership changes.

### Recommendation
Change `GitHubApp#verify_webhook_signature` to fail closed: if `webhook_secret` is not configured, treat the webhook as unverifiable and reject it (return `false`), rather than treating "no secret configured" as automatically "verified." Alternatively, require a non-blank `webhook_secret` at configuration/boot time for any organization/app that is expected to receive `membership` (or any privileged) webhooks, and refuse to process `membership` events for organizations without a configured secret.

### Proof of Concept
1. Configure Shipit with an organization/app entry (e.g. via the multi-org `Shipit.github` config) that omits `webhook_secret`.
2. Send an HTTP POST to `/webhooks` with header `X-Github-Event: membership` and no (or arbitrary) `X-Hub-Signature`, with body:
```json
{
  "action": "added",
  "team": { "id": 48, "name": "Admins", "slug": "admins", "url": "https://example.com" },
  "organization": { "login": "<org-without-secret>" },
  "member": { "login": "attacker-controlled-login" }
}
```
3. `WebhooksController#verify_signature` resolves the app for `<org-without-secret>`, calls `verify_webhook_signature`, which returns `true` immediately because `webhook_secret` is blank — no signature is actually checked.
4. `MembershipHandler#process` runs, adding `attacker-controlled-login`'s corresponding `User` to the `admins` `Team`.
5. If `admins` is listed in `Shipit.github_teams`, any session subsequently authenticated as `attacker-controlled-login` (via normal GitHub OAuth login) now passes `User#authorized?` and gains full access to the Shipit engine, matching the "escalation into `Shipit.github_teams` authorization" High-impact criterion.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
