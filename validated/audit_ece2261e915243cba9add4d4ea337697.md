### Title
ERC20 asset transactor credits the full requested amount to XCM holding without verifying the checking account actually received it, causing fee-on-transfer/deflationary ERC20 tokens to permanently break XCM asset accounting - ([File: cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs])

### Summary
`ERC20Transactor::withdraw_asset_with_surplus` moves ERC20 tokens from a user into a shared `TransfersCheckingAccount` via a Solidity `IERC20::transfer` call, then unconditionally credits the *requested* `amount` into the XCM `AssetsInHolding` register — it never measures what the checking account actually received. Any ERC20 contract that charges a fee/burn on transfer (a common, legal ERC20 pattern) will make the checking account's real balance diverge from what the runtime believes it holds, exactly mirroring the reported Sherlock finding where `Vault` assumed `_amount` sent equals `_amount` received. [1](#0-0) 

### Finding Description
`withdraw_asset_with_surplus` executes an ERC20 `transfer(checking_address, amount)` call from the user's account to `TransfersCheckingAccount`: [2](#0-1) 

On success (return value `true`), it builds the XCM holding credit using the *originally requested* `amount`, not the delta actually observed in the checking account's ERC20 balance: [3](#0-2) 

If the ERC20 contract implements a fee-on-transfer/deflationary mechanism (charges or burns a percentage on every `transfer`, while still returning `true`), the checking account will receive `amount - fee`, but the XCM executor's holding register — and hence any downstream XCM instructions (`DepositAsset`, `InitiateReserveWithdraw`, cross-chain reserve/bridge transfers, etc.) — will treat the full `amount` as available and backed by the checking account.

Symmetrically, `deposit_asset_with_surplus` later transfers this same over-stated `amount` **out** of the checking account to a beneficiary: [4](#0-3) 

Because the checking account's real ERC20 balance is short by the accumulated fees from all prior fee-on-transfer deposits, this call will eventually fail (revert / return `false`) once the shortfall exceeds the checking account's actual balance — this is the exact analog of the reported bug: `amountStored` (here, the XCM holding credit) is increased by the nominal `_amount` transmitted, while the actual balance received is less, so a later withdrawal for the correct recorded amount fails and locks funds, in this case another (unrelated) user's XCM transfer using the same shared checking account.

This code is reachable by any ordinary, unprivileged account: `pallet_revive` contract deployment is permissionless, and the existing test `withdraw_and_deposit_erc20s` demonstrates that arbitrary user-deployed ERC20 contracts (identified by `AccountKey20` locations) can be used directly in `pallet_xcm::execute` `withdraw_asset`/`deposit_asset` instructions without any registration/allow-list step visible at the transactor level: [5](#0-4) 

I was unable to fully verify, within the available context, whether a higher-level asset registry or `Matcher` configuration in `xcm_config.rs` restricts which ERC20 contract addresses are eligible for `ERC20Transactor` (grep only located references to `ERC20Transactor`/`ERC20TransferGasLimit` wiring in that file; I did not have the iteration budget to read the full `Matcher` implementation). If such an allow-list exists and is governance-gated, the practical severity would be lower (an attacker would need their fee-on-transfer token registered), but the transactor itself contains no defensive balance check regardless of whether the asset is allow-listed, so any registered ERC20 that later becomes fee-on-transfer (e.g., via an upgradeable proxy contract, if such registered tokens are ever proxies) would still trigger this.

### Impact Explanation
The `TransfersCheckingAccount` is a shared custodial account backing all ERC20 assets moved through XCM on this chain. A single fee-on-transfer ERC20 deposit corrupts the invariant "XCM holding credit == checking account's real spendable balance" for that asset. This can:
- Cause legitimate, unrelated XCM messages depositing/withdrawing the same ERC20 asset to fail once the shortfall accumulates, trapping assets (`AssetTrap`) or reverting cross-chain transfers after fees/weight have already been spent.
- Deterministically lock out the "last" user attempting to withdraw the recorded balance, precisely as in the referenced report, since the checking account can no longer cover the total nominally credited across all XCM operations for that asset.

This is a Medium-severity fund-availability/accounting-integrity issue (not outright unbacked issuance, since the shortfall reduces total available holdings rather than creating new value), consistent with the severity of the original report.

### Likelihood Explanation
Likelihood is Medium: deploying an ERC20 contract with fee-on-transfer semantics is trivial and permissionless via `pallet_revive`; using it through `pallet_xcm::execute`/reserve-transfer style calls with `withdraw_asset`/`deposit_asset` requires no privileged role. The main open question, which I could not fully verify given remaining context, is whether an asset allow-list gates which ERC20 contracts are actually routed through `ERC20Transactor` in the deployed `asset-hub-westend` runtime configuration — if it is ungated (as the reachable test suggests), likelihood is high; if governance-controlled, an attacker would need their token approved first, lowering likelihood but not eliminating the risk for any token that changes behavior post-registration.

### Recommendation
In both `withdraw_asset_with_surplus` and `deposit_asset_with_surplus`, measure the checking account's (or beneficiary's) ERC20 balance before and after the `transferCall`, and use the actual observed delta — not the requested `amount` — when constructing/consuming the `AssetsInHolding` credit. This mirrors the report's recommended fix for `Transfer.sol`: record `balance_before`/`balance_after` and derive the real transferred amount rather than trusting the nominal transfer amount.

### Proof of Concept
No live execution was run (per constraints); the following is the concrete reachable path substantiated by existing code/tests:
1. Deploy a permissionless ERC20 contract via `pallet_revive` whose `transfer` implementation charges e.g. 1% fee/burn on every call while still returning `true`.
2. As an ordinary signed account, call `pallet_xcm::execute` with an XCM program: `withdraw_asset` for this ERC20 (routed to `ERC20Transactor::withdraw_asset_with_surplus`, [6](#0-5) ), exactly as exercised by `withdraw_and_deposit_erc20s` [7](#0-6) , followed by `deposit_asset` to a beneficiary.
3. Observe: XCM holding is credited with the full nominal `amount` (line 197-201) even though the checking account received `amount - fee`.
4. Repeat/scale: after enough fee-on-transfer deposits, a subsequent legitimate `deposit_asset_with_surplus` transferCall out of the checking account (line 253-266) for a previously recorded amount fails because the checking account's real ERC20 balance is insufficient, trapping that beneficiary's assets.

I did not execute this against a running node/test harness; the analysis is based on static code reachability and the existing `withdraw_and_deposit_erc20s` integration test proving the withdraw/deposit path is reachable by an ordinary signed account with an arbitrary (non-preregistered-looking) ERC20 contract address. Full confirmation of any allow-list gating in `xcm_config.rs`'s `Matcher` configuration was not completed due to context/iteration limits and should be verified before treating this as unconditionally exploitable.

	fn withdraw_asset_with_surplus(
		what: &Asset,
		who: &Location,
		_context: Option<&XcmContext>,
	) -> Result<(AssetsInHolding, Weight), XcmError> {
		tracing::trace!(
			target: "xcm::transactor::erc20::withdraw",
			?what, ?who,
		);
		let (asset_id, amount) = Matcher::matches_fungibles(what)?;
		let who = AccountIdConverter::convert_location(who)
			.ok_or(MatchError::AccountIdConversionFailed)?;
		// We need to map the 32 byte checking account to a 20 byte account.
		let checking_account_eth = T::AddressMapper::to_address(&TransfersCheckingAccount::get());
		let checking_address = Address::from(Into::<[u8; 20]>::into(checking_account_eth));
		let weight_limit = WeightLimit::get();
		// To withdraw, we actually transfer to the checking account.
		// We do this using the solidity ERC20 interface.
		let data =
			IERC20::transferCall { to: checking_address, value: EU256::from(amount) }.abi_encode();
		let ContractResult { result, weight_consumed, storage_deposit, .. } =
			pallet_revive::Pallet::<T>::bare_call(
				OriginFor::<T>::signed(who.clone()),
				asset_id,
				U256::zero(),
				TransactionLimits::WeightAndDeposit {
					weight_limit,
					deposit_limit: StorageDepositLimit::get(),
				},
				data,
				&ExecConfig::new_substrate_tx(),
			);
		// We need to return this surplus for the executor to allow refunding it.
		let surplus = weight_limit.saturating_sub(weight_consumed);
		tracing::trace!(target: "xcm::transactor::erc20::withdraw", ?weight_consumed, ?surplus, ?storage_deposit);
		if let Ok(return_value) = result {
			tracing::trace!(target: "xcm::transactor::erc20::withdraw", ?return_value, "Return value by withdraw_asset");
			if return_value.did_revert() {
				tracing::debug!(target: "xcm::transactor::erc20::withdraw", "ERC20 contract reverted");
				Err(XcmError::FailedToTransactAsset("ERC20 contract reverted"))
			} else {
				let is_success = IERC20::transferCall::abi_decode_returns_validate(&return_value.data).map_err(|error| {
					tracing::debug!(target: "xcm::transactor::erc20::withdraw", ?error, "ERC20 contract result couldn't decode");
					XcmError::FailedToTransactAsset("ERC20 contract result couldn't decode")
				})?;
				if is_success {
					tracing::trace!(target: "xcm::transactor::erc20::withdraw", "ERC20 contract was successful");
					Ok((
						AssetsInHolding::new_from_fungible_credit(
							what.id.clone(),
							Box::new(Erc20Credit(amount)),
						),
						surplus,
					))
				} else {
					tracing::debug!(target: "xcm::transactor::erc20::withdraw", "contract transfer failed");
					Err(XcmError::FailedToTransactAsset("ERC20 contract transfer failed"))
				}
			}
		} else {
			tracing::debug!(target: "xcm::transactor::erc20::withdraw", ?result, "Error");
			// This error could've been duplicate smart contract, out of gas, etc.
			// If the issue is gas, there's nothing the user can change in the XCM
			// that will make this work since there's a hardcoded gas limit.
			Err(XcmError::FailedToTransactAsset("ERC20 contract execution errored"))
		}
	}

#[test]
fn withdraw_and_deposit_erc20s() {
	let sender: AccountId = ALICE.into();
	let beneficiary: AccountId = BOB.into();
	let revive_account = pallet_revive::Pallet::<Runtime>::account_id();
	let checking_account =
		asset_hub_westend_runtime::xcm_config::ERC20TransfersCheckingAccount::get();
	let initial_wnd_amount = 100_000_000_000_000_000u128;
	sp_tracing::init_for_tests();

	ExtBuilder::<Runtime>::default().build().execute_with(|| {
		// Bring the revive account to life.
		assert_ok!(Balances::mint_into(&revive_account, initial_wnd_amount));
		// Fund all accounts involved.
		assert_ok!(Balances::mint_into(&sender, initial_wnd_amount));
		assert_ok!(Balances::mint_into(&beneficiary, initial_wnd_amount));
		assert_ok!(Balances::mint_into(&checking_account, initial_wnd_amount));

		let code = compile_module_with_type("MyToken", FixtureType::Resolc)
			.expect("compile ERC20")
			.0;

		let initial_amount_u256 = U256::from(1_000_000_000_000u128);
		let constructor_data = sol_data::Uint::<256>::abi_encode(&initial_amount_u256);
		let Contract { addr: erc20_address, .. } = bare_instantiate(&sender, code)
			.transaction_limits(TransactionLimits::WeightAndDeposit {
				weight_limit: Weight::from_parts(500_000_000_000, 10 * 1024 * 1024),
				deposit_limit: Balance::MAX,
			})
			.data(constructor_data)
			.build_and_unwrap_contract();

		let sender_balance_before = <Balances as fungible::Inspect<_>>::balance(&sender);

		let erc20_transfer_amount = 100u128;
		let wnd_amount_for_fees = 10_000_000_000_000u128;
		// Actual XCM to execute locally.
		let message = Xcm::<RuntimeCall>::builder()
			.withdraw_asset((Parent, wnd_amount_for_fees))
			.pay_fees((Parent, wnd_amount_for_fees))
			.withdraw_asset((
				AccountKey20 { key: erc20_address.into(), network: None },
				erc20_transfer_amount,
			))
			.deposit_asset(AllCounted(1), beneficiary.clone())
			.refund_surplus()
			.deposit_asset(AllCounted(1), sender.clone())
			.build();
		assert_ok!(PolkadotXcm::execute(
			RuntimeOrigin::signed(sender.clone()),
			Box::new(VersionedXcm::V5(message)),
			Weight::from_parts(600_000_000_000, 15 * 1024 * 1024),
		));

		// Revive is not taking any fees.
		let sender_balance_after = <Balances as fungible::Inspect<_>>::balance(&sender);
		// Balance after is larger than the difference between balance before and transferred
		// amount because of the refund.
		assert!(sender_balance_after > sender_balance_before - wnd_amount_for_fees);

		// Beneficiary receives the ERC20.
		let beneficiary_amount =
			<Revive as fungibles::Inspect<_>>::balance(erc20_address, &beneficiary);
		assert_eq!(beneficiary_amount, erc20_transfer_amount);
	});
