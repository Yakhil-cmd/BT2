### Title
Unchecked exception in `handleSavedPrivatePayments` causes double invocation of the private-chain completion callback, leading to double `unlock()`/duplicate processing of an attacker-controlled private payment - ([File: network.js])

### Summary
`network.js`'s `handleSavedPrivatePayments()` computes `objectHash.getBase64Hash(objHeadPrivateElement.payload, true)` inside a `try/catch`. When this throws, the `catch` block calls `deleteHandledPrivateChain(...)` (which itself invokes `cb()`asynchronously) but does **not** `return`. Execution falls through to the code after the `try/catch`, which unconditionally calls `privatePayment.validateAndSavePrivatePaymentChain(...)` a second time on the same private-payment element, whose `ifOk`/`ifError`/`ifWaitingForChain` handlers each call `cb()` again. This mirrors the root cause of CVE‑2020‑6072: a decode/parse routine's exceptional/error path is not checked before the caller proceeds to reuse the same object, so the "cleanup" callback fires twice on a single attacker-supplied message.

### Finding Description [1](#0-0) 
The relevant code:
```js
var validateAndSave = function(){
    var objHeadPrivateElement = arrPrivateElements[0];
    try {
        var json_payload_hash = objectHash.getBase64Hash(objHeadPrivateElement.payload, true);
    }
    catch (e) {
        console.log("getBase64Hash failed for private element", objHeadPrivateElement.payload, e);
        if (ws)
            sendResult(ws, {private_payment_in_unit: row.unit, result: 'error', error: e.toString()});
        deleteHandledPrivateChain(row.unit, row.message_index, row.output_index, cb);
    }
    var key = 'private_payment_validated-'+objHeadPrivateElement.unit+'-'+json_payload_hash+'-'+row.output_index;
    privatePayment.validateAndSavePrivatePaymentChain(arrPrivateElements, { ... });
};
```
There is no `return` statement after `deleteHandledPrivateChain(...)` inside the `catch` block. `deleteHandledPrivateChain` (network.js:2523) itself asynchronously calls `cb()` after a `DELETE` query completes. Meanwhile, execution continues synchronously past the `catch` and immediately invokes `privatePayment.validateAndSavePrivatePaymentChain(arrPrivateElements, {...})`, whose three outcome handlers (`ifOk`, `ifError`, `ifWaitingForChain`) each also eventually call the same `cb` (the `async.each` iteratee callback for that row). This produces two independent completion paths for one iteration of `async.each`, i.e., the per-item callback of `async.each` can be invoked twice for a single malicious/malformed private payment.

This is reachable by an unprivileged private-payment counterparty: private chains reach `handleSavedPrivatePayments` via `unhandled_private_payments` rows populated when a peer/hub sends a "private_payment" chain (through `handleOnlinePrivatePayment`/`wallet.js`'s `handlePrivatePaymentChains`, both accepting attacker/counterparty-controlled JSON). A crafted `payload` object that makes `objectHash.getBase64Hash` throw (e.g., an unsupported/invalid type, or a structure `getSourceString`/JSON serialization chokes on) will trigger this dual-callback bug without requiring any special privileges — only sending (or forwarding) a private-payment chain to the victim's node/wallet.

### Impact Explanation
`async.each`'s iteratee callback being invoked more than once for the same item causes it to double-count completed tasks internally; this can cause the outer completion function (which calls `unlock()` on the `"saved_private"` mutex and, on some code paths, `unlock()` for the `"private_write"` mutex or other resources acquired elsewhere) to run prematurely or be invoked twice, corrupting the mutex/lock bookkeeping used to serialize private-payment processing and unit saving. Because private-payment validation/saving elsewhere in the codebase (e.g., `divisible_asset.js`, `indivisible_asset.js`) relies on the same `mutex` module to serialize "handleJoint"/"private_write" operations before writes are committed, releasing/acquiring locks out of sequence can allow a second, concurrently-arriving private payment referencing the same spend proof/output to be processed against inconsistent lock state, opening a window for a double-spend of a private/stable output or for a payment chain to be treated as accepted/duplicated when it should not be. At minimum this is a reliably triggerable logic-corruption bug in the private-payment processing pipeline reachable by any private-payment counterparty, and in the worst case enables node disagreement or double-processing of a spend.

### Likelihood Explanation
Likelihood is Medium-High for reaching the buggy code path: any wallet/hub-connected user that can send a private payment chain (a completely standard action for private-asset or textcoin transfers) controls the `payload` object of the head private element. Achieving a JSON payload that causes `objectHash.getBase64Hash` to throw requires crafting the payload with a type/structure not supported by the hashing/serialization routine (e.g., functions, unsupported nested types, or excessively deep/duplicate-key objects, depending on what `getSourceString`/`JSON.stringify` rejects) — a bug-class hint directly taken from CVE-2020-6072 (unchecked decode-function return leads to double free). While proving the exact downstream double-spend impact requires runtime confirmation of the mutex sequencing, the missing `return` after the `catch` block is a clear-cut logic defect guaranteed to run both code paths whenever the exception is thrown.

### Recommendation
Add a `return` after the error branch in the `catch` block of `validateAndSave` in `network.js` (around line 2476) so that execution never falls through to `privatePayment.validateAndSavePrivatePaymentChain` when hashing the payload has already failed and `cb` has already been scheduled for invocation. Additionally, audit all similar `try { var x = ...; } catch (e) { ...; cb(...); }` patterns in the codebase (missing an explicit `return`) for the same double-callback hazard, and consider using strict-mode linting (`no-fallthrough`/consistent-return rules) to catch this class of bug automatically.

### Proof of Concept
1. As a peer/hub, or through the wallet's `handlePrivatePaymentChains`/`handleOnlinePrivatePayment` flow, submit a private-payment chain whose head element's `payload` is a JSON object that `objectHash.getBase64Hash(payload, true)` cannot hash (e.g., a payload containing a value type not handled by `getSourceString`, such as `NaN`, `Infinity`, or a `Function`-shaped object after JSON round-trip abuse, or one with duplicate/looping structure that the hashing code's helper functions in `object_hash.js`/`string_utils.js` reject with a thrown error).
2. The chain is stored in `unhandled_private_payments` (via the normal private-payment receipt path) and is later processed by `handleSavedPrivatePayments()`.
3. In `validateAndSave`, `objectHash.getBase64Hash` throws; the `catch` block runs `deleteHandledPrivateChain(..., cb)` (schedules a `cb()` call once the `DELETE` completes) but does not return.
4. Control falls through to `privatePayment.validateAndSavePrivatePaymentChain(arrPrivateElements, {...})`, which independently calls `cb()` a second time via one of `ifOk`/`ifError`/`ifWaitingForChain`.
5. The `async.each` completion function for `handleSavedPrivatePayments` therefore executes twice (or its bookkeeping is corrupted), unlocking the `"saved_private"` mutex out of the expected sequence and creating a race window during which other private-payment/asset-saving operations relying on the same lock discipline can interleave incorrectly.
