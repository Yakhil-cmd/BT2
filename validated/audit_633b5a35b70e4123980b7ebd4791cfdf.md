### Title
Webhook signature verification authenticates the wrong organization while handlers act on an attacker-controlled repository field, breaking the organization-authenticated vs. repository-written binding - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks which GitHub App/organization's `webhook_secret` to validate a delivery against using one attacker-supplied JSON field (`repository.owner.login`, falling back to `organization.login`), while the handlers that actually mutate application state (sync commits, update statuses, trigger check-suite refresh) resolve the target `Repository`/`Stack` from a second, independently attacker-supplied field (`repository.full_name`). Because the HMAC covers only the raw bytes and not any semantic binding between these two fields, an attacker who controls (and thus knows the `webhook_secret` for) one organization's GitHub App installation can forge a validly-signed payload whose `repository.owner.login` matches their own org (so it passes verification) but whose `repository.full_name` names a completely different, victim organization's repository/stack.

### Finding Description
`verify_signature` in [1](#0-0)  derives `repository_owner` from the payload and uses it to select `Shipit.github(organization: repository_owner)`, then verifies the raw request body against that organization's `webhook_secret` via `verify_webhook_signature` [2](#0-1) . The organization selector is computed as:

```
params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
``` [3](#0-2) 

Once signature verification passes, `create` dispatches the *entire* raw payload to the registered handler for the event [4](#0-3) . Handlers resolve the target repository independently, via `payload.dig('repository', 'full_name')`:

```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [5](#0-4) 

`PushHandler#process`, for example, then finds every matching, non-archived `Stack` and calls `sync_github` on it [6](#0-5) .

Because the app supports multiple GitHub organizations each with their own installation and `webhook_secret` (as shown in the multi-tenant fixture [7](#0-6) ), a member of one onboarded organization (`OrgTwo`) who legitimately knows/controls that org's `webhook_secret` (e.g., by having admin access to configure the GitHub App webhook for their own org, which is not a privileged Shipit action) can:

1. Compute a valid HMAC over an arbitrary JSON body using their own org's `webhook_secret`.
2. Set `repository.owner.login` (or `organization.login`) to their own org so `verify_signature` selects and validates against the secret they know.
3. Independently set `repository.full_name` to `victim-org/victim-repo` — a repository/stack belonging to a different, unrelated organization tracked by the same Shipit instance.

The signature check only proves "this bytes blob was signed by *some* known org's secret" — it never proves that the `repository.full_name` field used by the handler belongs to that same org. This is exactly analogous to the reported bug class: one field (`voucherIndexes`/staker binding) is authenticated/updated, while a different field (the actual `lastVoucher.staker` pointer) is used for the state mutation and is never checked against the authenticated one. Here, the "authenticated organization" and "the repository actually written to" are never bound together.

### Impact Explanation
This lets an attacker who administers any single organization onboarded to a shared Shipit instance forge webhook events (`push`, `status`, `check_suite`, etc.) targeting a stack owned by a different organization on the same instance. Via `PushHandler`, this triggers `Stack#sync_github`, causing Shipit to sync/re-fetch commits for the victim's stack based on attacker-chosen `after` SHAs; via `StatusHandler`/`CheckSuiteHandler`, it can inject fabricated CI status/check-run information for the victim's commits. Since Shipit deploy gating (`ignore_ci`, deployable status, merge queue "ready to ship" checks) commonly relies on these commit statuses/check-runs, this can be used to make an unreviewed or malicious commit appear CI-green in the victim's stack, materially contributing to an unauthorized deploy path — meeting the "unauthorized deploy" Critical impact bar via a cross-organization write that should never have been reachable from the attacker's authentication context.

### Likelihood Explanation
This requires only that (a) the Shipit instance is configured with more than one GitHub organization (a documented, supported configuration — see `test/dummy/config/secrets_double_github_app.yml`), and (b) the attacker has legitimate control of their own org's app/webhook configuration (not a privileged Shipit account, no GitHub App private key, no `ApiClient` token, no session). No interaction with the victim org is required, and the request is a single unauthenticated HTTP POST to `/webhooks`. This is a realistic, low-effort exploitation path for any multi-tenant Shipit deployment.

### Recommendation
Bind the organization used for signature verification to the organization implied by the field the handlers actually act on. Concretely, in `verify_signature`, derive `repository_owner` strictly from `repository.full_name`'s owner segment (the same field `Handler#repository_name` uses), or, after verification, re-derive the organization from `repository.full_name` and re-check it matches the one used to select the `webhook_secret` before dispatching to handlers. Alternatively, look up the `Repository`/`Stack` first and confirm the resolved repository's configured GitHub organization matches the organization whose secret validated the signature, rejecting the request (422) on mismatch.

### Proof of Concept
1. Configure/assume a Shipit instance with two organizations, `attacker-org` and `victim-org`, each with its own GitHub App and `webhook_secret` (per `test/dummy/config/secrets_double_github_app.yml` pattern).
2. As an administrator of `attacker-org` (a legitimate, unprivileged Shipit end-user w.r.t. `victim-org`), craft a `push` payload:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" }
}
```
3. Compute `X-Hub-Signature: sha1=<hmac-sha1(attacker-org's webhook_secret, raw_body)>`.
4. POST to `/webhooks` with `X-Github-Event: push`.
5. `verify_signature` selects `Shipit.github(organization: "attacker-org")` and successfully verifies the signature [8](#0-7) .
6. `PushHandler` resolves `Repository.from_github_repo_name("victim-org/victim-repo")` [5](#0-4)  and calls `sync_github` on every matching, non-archived stack belonging to `victim-org` [6](#0-5) , despite the request never having been authenticated against `victim-org`'s webhook secret.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",

    end

**File:** lib/shipit/github_app.rb (L76-83)
```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
