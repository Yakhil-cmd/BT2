### Title
Cross-tenant repository spoofing in webhook signature verification allows a no-secret org's request to mutate a victim repository's review stack - (File: app/controllers/shipit/webhooks_controller.rb, app/models/shipit/webhooks/handlers/pull_request/*)

### Summary
`Shipit::WebhooksController#verify_signature` selects the `GitHubApp` (and thus the `webhook_secret`) using `params.dig('repository','owner','login')`, while the `pull_request` handlers (`OpenedHandler`, `EditedHandler`, `ClosedHandler`, etc.) resolve the target `Shipit::Repository` using the independent field `params.repository.full_name`. Because these two JSON fields are not required to be consistent, an attacker can pick a `repository.owner.login` belonging to an organization configured in Shipit with a blank `webhook_secret` (which short-circuits `verify_webhook_signature` to `true` unconditionally) while setting `repository.full_name` to an unrelated victim repository, causing the handler to create/mutate that victim's review stack. Note: the specific `action: "ready_for_review"` value cited in the question does not match any action guard in the current handler set (`OpenedHandler` requires `action == "opened"`, `EditedHandler` requires `"edited"`, and the other PR handlers similarly key off their own specific action strings), so a payload literally using `ready_for_review` is a no-op across all registered handlers — but the identical bypass is fully exploitable using `action: "opened"`, `"edited"`, `"labeled"`, etc.

### Finding Description
The broken binding is: **the org whose `webhook_secret` verified the request MUST equal the org owning `repository.full_name` used by the handler.**

Code path:
- `Shipit::WebhooksController#verify_signature` [1](#0-0)  looks up the app config via `repository_owner` [2](#0-1) , which reads `params.dig('repository','owner','login')`.
- `GitHubApp#verify_webhook_signature` returns `true` unconditionally when the resolved org's `webhook_secret` is blank [3](#0-2) .
- `Shipit::Webhooks.for_event('pull_request')` fans the parsed body out to every PR handler regardless of `action` [4](#0-3)  and [5](#0-4) .
- Each handler independently resolves its target `Shipit::Repository` from `params.repository.full_name`, e.g. `OpenedHandler#repository` [6](#0-5)  and `EditedHandler#repository`/`#pull_request` [7](#0-6) .
- `repository.owner.login` and `repository.full_name` are both attacker-supplied JSON leaves inside the same forged body with no cross-validation enforcing that `full_name`'s owner segment matches `owner.login`.

Exploit flow: attacker POSTs `/webhooks` with header `X-Github-Event: pull_request`, body `{"action":"opened","repository":{"owner":{"login":"<no-secret-org>"},"full_name":"victim-org/victim-repo"},"pull_request":{...},"sender":{"login":"attacker"}}`. `verify_signature` resolves `Shipit.github(organization: "<no-secret-org>")`, whose config has no `webhook_secret`, so `verify_webhook_signature` returns `true` without checking `X-Hub-Signature` at all. `OpenedHandler#process` then looks up `Shipit::Repository.from_github_repo_name("victim-org/victim-repo")` and, if review stacks are enabled/allowed for that repo's provisioning policy, creates a `ReviewStack` for a PR the attacker fabricated, backed by data the attacker fully controls (branch name, PR number, etc.). Existing guards (`drop_unhandled_event`, `ExplicitParameters` schema validation, action-specific checks) do not prevent this because they never compare `owner.login` to `full_name`'s owner segment.

The question specifically names `action: "ready_for_review"`; none of the registered `pull_request` handlers check for that literal action string, so this exact action value produces no side effect. The vulnerable binding/mechanism is real and reachable, but only via actions the handlers actually key on (`opened`, `edited`, `labeled`, `unlabeled`, `closed`, `reopened`, `assigned`).

### Impact Explanation
An unauthenticated internet requester can create or mutate `Shipit::ReviewStack`/`Shipit::PullRequest` records belonging to an arbitrary victim repository configured in Shipit, as long as any organization in the Shipit config has a blank `webhook_secret` — this satisfies "a payload for one repository mutating another's stack" (Critical). This is repeatable against any victim repo/organization pair as long as one no-secret org exists in the deployment's config.

### Likelihood Explanation
Requires: (1) at least one GitHub organization configured in Shipit's `github` config without a `webhook_secret` (a documented/plausible misconfiguration, not something the attacker controls), and (2) a victim repository already known to Shipit with review stacks enabled for the relevant provisioning policy. Given those preconditions, attacker cost is a single unauthenticated HTTP POST with a JSON body they fully control; no valid HMAC, session, or token is needed.

### Recommendation
In `Shipit::WebhooksController#verify_signature`, after resolving the org/app, additionally verify that `repository.full_name`'s owner segment matches the organization used for signature verification (or verify against every configured org that could plausibly match, rejecting on mismatch). Do not allow `verify_webhook_signature` to silently return `true` for blank secrets in production configs, or require the org key that authenticates to equal the repository owner referenced anywhere in the payload used for downstream lookups.

### Proof of Concept
minitest plan (`test/controllers/webhooks_controller_test.rb`):
1. Configure two orgs in `Shipit.github_apps`/config fixture: `"no-secret-org"` with no `webhook_secret`, and `"victim-org"` with a real secret, mirroring existing fixtures for `verify_webhook_signature`.
2. Create `victim_repo = Shipit::Repository.create!(github_repo_name: "victim-org/victim-repo", review_stacks_enabled: true, provisioning_behavior: "allow_all")`.
3. POST to `/webhooks` with header `X-Github-Event: pull_request`, no/garbage `X-Hub-Signature`, and body: `{"action":"opened","number":1,"pull_request":{...valid schema...,"head":{"ref":"feature"}},"repository":{"owner":{"login":"no-secret-org"},"full_name":"victim-org/victim-repo"},"sender":{"login":"attacker"}}`.
4. Assert response is `200 OK` (bypassing signature check).
5. Assert `Shipit::ReviewStack.exists?(environment: "pr1")` under `victim_repo` — i.e., a stack was created for `victim-org/victim-repo` without any valid signature from `victim-org`'s secret, proving `owner.login` (used to authenticate) ≠ `full_name`'s owner (used to mutate).

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
