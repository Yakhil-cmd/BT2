Found the bug. The `last-update` oracle timestamp map in `mainnet/contracts/market/v0-4-market.clar` is a **shared global cache keyed only by `{type, ident}`** — not per-caller, not per-position. Any unprivileged caller supplying `price-feeds` on any public entry point (`borrow`, `repay`, `deposit`, `liquidate`, etc.) can push this shared state forward, and every other user's subsequent transaction that touches the same asset in the same or later block consumes whatever was last written — this is exactly the "shared cache primed by one caller and consumed by another" bug class from the report (Sawyer object mutated by one HTTP response and consumed unsafely by unrelated GitLab import code).

### Title
Attacker-controlled price-feed monotonic timestamp write lets one user freeze/DoS oracle price resolution for all other users - (File: mainnet/contracts/market/v0-4-market.clar)

### Summary
`price-resolve` in `v0-4-market.clar` lets **any caller**, on **any public market action**, submit an off-chain Pyth/DIA feed via the `price-feeds` argument that is verified and then written into a **global, asset-keyed** `last-update` map shared by every user of the market, gating all future price reads for that asset via `oracle-timestamp-fresh`.

### Finding Description
`price-resolve` computes `last-update-time` from the shared `last-update` map keyed only by `{ type, ident }` [1](#0-0) , and enforces freshness with `oracle-timestamp-fresh`, which requires the newly supplied timestamp to be `>= prev` (the last stored timestamp) and within `max-staleness` of `stacks-block-time` [2](#0-1) . Any caller who legitimately possesses a valid, signed Pyth/DIA feed can call any public entrypoint (`borrow`, `repay`, `deposit`, `liquidate`, etc.) that accepts `price-feeds`, causing `map-set last-update key timestamp` to advance the global `prev` value for that asset [3](#0-2) .

Because the map is not scoped to the caller or their position, this write is consumed by every other unrelated user's subsequent transaction touching the same asset: if the attacker's feed timestamp is the newest currently obtainable one, `prev` is now pinned at that value for *everyone*, and no one (including honest liquidators or borrowers) can supply an older-but-still-fresh feed even if the third-party oracle later republishes with a marginally lower timestamp due to normal publisher jitter, since `oracle-timestamp-fresh` rejects any `ts < prev`. This is precisely the "shared cache primed by one caller and consumed by another" pattern described in the mining-lineage report, where Sawyer’s type confusion let one caller's malformed input poison state read unsafely by a different, unrelated code path.

### Impact Explanation
A malicious or careless caller can, for the cost of one ordinary transaction, ratchet the shared `last-update` value for a widely-used collateral/debt asset to the newest available feed. Any other account attempting to `borrow`, `repay`, `deposit`, or (critically) be `liquidate`d in the same or a following block, whose relayed price feed has a timestamp below the ratcheted `prev` (e.g., due to oracle publisher timing, relayer latency, or partial feed availability), will have `price-resolve` revert with `ERR-ORACLE-INVARIANT`, blocking price resolution for that asset entirely until a newer feed becomes available. This can be weaponized to stall liquidations against an unhealthy position the attacker controls (temporary freezing of the ability to act on collateral/debt for that asset) by racing to submit the newest feed just ahead of a liquidator, denying the liquidator a valid input within the freshness window. This lands on **temporary freezing of funds** (unclaimed liquidation eligibility / user operations) for other, unrelated market participants using the same asset.

### Likelihood Explanation
Likelihood is moderate: the attacker needs no special privileges — any address can call the public market functions with a `price-feeds` argument and does not need to hold any position for that transaction, since the price-resolution helper functions are invoked directly during normal user flows (e.g., `borrow`) [4](#0-3) . Exploitation only requires access to a marginally-fresher signed feed than a target liquidator/borrower will present, which is realistic given natural oracle publish jitter and relayer race conditions.

### Recommendation
Do not treat `last-update` as a monotonic gate shared across all callers for correctness of *other* users' actions. Either (a) only use the stored `last-update` to prevent stale-price replay for the *same* transaction's own risk checks rather than rejecting any independently-valid, sufficiently-fresh feed regardless of a globally-ratcheted `prev`, or (b) relax the freshness check to accept any timestamp within `max-staleness` of `stacks-block-time` without requiring `ts >= prev`, since `max-staleness` combined with `stacks-block-time` already bounds staleness without needing artificial monotonicity that can be weaponized by an unrelated caller.

### Proof of Concept
1. Attacker observes a healthy liquidation opportunity is about to be taken against Account B for asset `sBTC`.
2. Attacker calls any public function (e.g., `repay`) on their own irrelevant position, passing a `price-feeds` buffer containing the newest available signed Pyth feed for `sBTC` with timestamp `T_max`.
3. `price-resolve` accepts it (fresh, valid) and executes `map-set last-update {type, ident} T_max` [3](#0-2) .
4. The liquidator's transaction, built moments earlier with a feed timestamp `T < T_max` (still within `max-staleness` of `stacks-block-time`), now fails `oracle-timestamp-fresh` because `T < prev (T_max)`, reverting with `ERR-ORACLE-INVARIANT`.
5. Liquidation of Account B is blocked for that block/window despite a valid, fresh price being available, at no cost or risk to the attacker.

```text
(define-private (oracle-timestamp-fresh (ts uint) (prev uint) (max-staleness uint))
  (let ((delta (if (> ts stacks-block-time)
                   u0
                   (- stacks-block-time ts))))
    (and
      (<= delta max-staleness)
      (>= ts prev))))
```

```text
(define-private (price-resolve
  (data { type: (buff 1), ident: (buff 32), callcode: (optional (buff 1)), max-staleness: uint }))
  (let ((type (get type data))
        (ident (get ident data))
        (key { type: type, ident: ident })
        (resolution (try! (resolve-price-feed type ident)))
        (price (get value resolution))
        (callcode (get callcode data))
        (final-price (try! (resolve-callcode price callcode)))
        (last-update-time (oracle-last-update key))
        (timestamp (get timestamp resolution))
        (max-staleness (get max-staleness data)))

    ;; validate price and timestamp using max-staleness from oracle data
    (asserts! (and (oracle-price-legal final-price) (oracle-timestamp-fresh timestamp last-update-time max-staleness))
              ERR-ORACLE-INVARIANT)

    ;; update timestamp if newer
    (if (> timestamp last-update-time)
        (map-set last-update key timestamp)
        false)

    (ok final-price)))
```
