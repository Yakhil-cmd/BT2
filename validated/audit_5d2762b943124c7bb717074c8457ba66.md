### Title
Webhook signature is verified against an attacker-chosen organization while the payload's `sha`/`repository.full_name` fields (never bound to that organization) select the actual target — allowing cross-repository status/commit-state forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects which GitHub App/organization secret to use for HMAC verification based on `repository.owner.login`, an attacker-controlled JSON field, but the handlers that subsequently act on the payload (e.g. `StatusHandler`, `PushHandler`) use a *different* field (`sha`, `repository.full_name`) to decide which commit/stack to mutate, with no check that it belongs to the organization that authenticated the request.

### Finding Description
`WebhooksController#verify_signature` reads the organization to authenticate against directly out of the unauthenticated JSON body: [1](#0-0) [2](#0-1) 

`Shipit.github(organization: repository_owner)` returns the `GithubApp` configured for that organization, and `verify_webhook_signature` HMACs the raw body using **that organization's** `webhook_secret`: [3](#0-2) 

Because the attacker fully controls the raw JSON body they send, they can pick `repository.owner.login` to be an organization whose `webhook_secret` they know (their own org's Shipit-installed webhook, which GitHub reveals to whoever configures it, or any org with no configured secret at all, since `verify_webhook_signature` returns `true` unconditionally when `webhook_secret` is blank). Nothing enforces that the rest of the payload (the commit `sha`, or `repository.full_name`) actually belongs to that authenticating organization.

Downstream, `StatusHandler#process` looks up commits globally by `sha` with no scoping to a repository or organization at all: [4](#0-3) 

and `PushHandler`/the base `Handler#stacks` resolve the target purely from `repository.full_name`: [5](#0-4) [6](#0-5) 

This breaks the intended binding: `organization authenticated by signature == organization whose stacks/commits are mutated`. An attacker who can satisfy the signature check for *any one* configured organization (their own, or an unconfigured/secret-less one) can forge a `status` event carrying a commit `sha` belonging to a completely unrelated victim stack/repository and inject an arbitrary commit status (e.g. `state: "success"`) for it via `Commit#create_status_from_github!`.

### Impact Explanation
Commit statuses drive Shipit's deployability checks (required CI checks that gate whether a commit can be shipped/auto-deployed). Forging a success status for an arbitrary commit belonging to a stack the attacker has no legitimate relationship with can satisfy deploy-gating checks and contribute to an unauthorized deploy of that commit — meeting the Critical bar of "an unauthorized deploy". At minimum it is an authentication-boundary violation: the entity that cryptographically authenticated (one organization) is not the entity whose state is mutated (an unrelated repository's commit).

### Likelihood Explanation
Exploitation only requires: (1) knowledge of a webhook secret for any organization onboarded to the target Shipit instance (obtainable by the attacker if they administer any such GitHub org/App, or trivially if that org has no `webhook_secret` configured, which `verify_webhook_signature` explicitly allows), and (2) crafting a raw HTTP POST directly to the public `/webhooks` endpoint — no GitHub UI interaction is required since the controller only checks the `X-Hub-Signature` header against the raw body, not the origin. This is a moderate-likelihood, unprivileged-attacker path once one organization boundary is available to the attacker.

### Recommendation
Bind the authenticated organization to the object being mutated: after verifying the signature against `repository_owner`, re-derive the target repository/commit and assert that `repository.full_name`'s owner matches `repository_owner`, and scope `StatusHandler`'s `Commit.where(sha:)` lookup to commits belonging to stacks under the verified organization (join through `Repository`/`Stack` and filter by owner) instead of a global, unscoped lookup. Also disallow silently returning `true` from `verify_webhook_signature` when no secret is configured (require an explicit "no signature required" opt-in per organization instead of a global bypass).

### Proof of Concept
1. Attacker controls (or knows the webhook secret of, or it's simply unconfigured for) organization `attacker-org`, which is registered in Shipit's `github` config.
2. Attacker crafts a JSON body:
```json
{
  "sha": "<sha of a commit belonging to victim-org/victim-repo tracked by Shipit>",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "attacker-org/some-repo" }
}
```
3. Attacker signs the raw body with `attacker-org`'s known/blank webhook secret and sets `X-Github-Event: status`, `X-Hub-Signature: sha1=<computed>`.
4. `verify_signature` looks up `Shipit.github(organization: "attacker-org")` and the signature check passes.
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)` — matching the victim commit — and calls `commit.create_status_from_github!(params)`, injecting a forged "success" status onto a commit in `victim-org/victim-repo`, a repository the attacker never authenticated against.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
