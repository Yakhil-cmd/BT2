Confirmed root cause: `WebhooksController#verify_signature` selects the GitHub App / webhook secret to check the signature against based on `repository_owner`, which is read straight from the *unverified* JSON body (`params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`), and this same body is then handed unmodified to `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`. Handlers such as `PushHandler`/`StatusHandler`/`CheckSuiteHandler` (via `Handlers::Handler#repository_name`, `app/models/shipit/webhooks/handlers/handler.rb:36-38`) resolve which `Repository`/`Stack` to mutate purely from `payload.dig('repository', 'full_name')` — a *different* field of the same unverified body, with no equality check against `repository_owner`.

### Title
Webhook organization used for signature verification is not bound to the repository the payload mutates - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
In a multi-org Shipit deployment (`config/secrets.yml` with multiple `github:` orgs, each with its own `webhook_secret`), `WebhooksController#verify_signature` picks the HMAC secret to check based on `repository_owner`, a value read from the unauthenticated JSON body, while the actual repository/stack mutated by the handler is read from a different, independently-controlled field (`repository.full_name`) of that same body.

### Finding Description
`WebhooksController#verify_signature` computes:
```ruby
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
``` [1](#0-0) 
where
```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [2](#0-1) 

This only proves that the raw request body was signed by *the App installed for organization `repository_owner`*. It does not prove anything about which repository the payload describes beyond that top-level owner login. GitHub Apps are typically installed per-organization but a compromised/rogue repository within that org (or a malicious actor who can trigger deliveries carrying an arbitrary `repository.full_name`, e.g. through crafted webhook relays, App proxies, or a org admin misusing per-org webhook config) can produce a validly-signed payload for org A while setting `repository.full_name` to a completely different repository string.

Every handler resolves the target purely from `repository.full_name`:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [3](#0-2) 

`PushHandler#process` then calls `stack.sync_github(expected_head_sha: params.after)` for every matching stack [4](#0-3) , and `StatusHandler#process` writes a `Status` on any `Commit` matching `params.sha` regardless of repository [5](#0-4) , with no assertion that `repository.full_name`'s owner equals `repository_owner`.

The binding that should hold is:
`organization authenticated by verify_webhook_signature(repository_owner) == owner(repository.full_name acted on by handler)`
but nothing in the controller or `Handler` base class enforces this equality — the two fields are read independently from the same untrusted JSON body.

### Impact Explanation
If a Shipit instance is configured with multiple GitHub orgs (as `test/dummy/config/secrets_double_github_app.yml` and the README's multi-org config sample demonstrate this is a supported configuration) [6](#0-5) , and an attacker controls/compromises a webhook secret or delivery path for any one configured organization, they can forge a `push`/`status`/`check_suite` payload whose signature validates against that org's secret while `repository.full_name` names a stack belonging to a *different, unrelated organization*. This lets the attacker:
- Trigger `GithubSyncJob`/`sync_github` on foreign stacks, forcing Shipit to re-sync/re-fetch commits/refs from GitHub for repositories it should have no authority over.
- Inject fabricated commit `Status` records (arbitrary `state`, `context`, `target_url`, `description`) onto commits of a stack outside the authenticating organization, which is exactly the CI-status gate Shipit relies on to permit or block a deploy — a cross-repository write of trust-relevant state driven by only one organization's credentials.

This breaks the "organization authenticated vs. repository written" binding required by scope, and the practical effect (forged status feeding the deploy-gating logic, forced resync of unrelated stacks) is a cross-repository, unauthorized state write achievable purely by an unprivileged holder of one org's webhook credentials.

### Likelihood Explanation
Requires a Shipit deployment configured with more than one GitHub organization (an explicitly documented and tested configuration in this engine) and requires the attacker to be able to produce a validly-signed delivery for at least one of the configured orgs (e.g. by compromising or intercepting that org's App webhook credentials, or through any GitHub-side relay/proxy misconfiguration that lets one org's signed payload reference another org's repository name). Given the multi-org support is a first-class, documented feature, and the check never validates owner-consistency, likelihood is moderate wherever multi-org secrets are used.

### Recommendation
In `WebhooksController#verify_signature`/`create`, after establishing which organization's key validated the signature, re-derive `repository_owner` from the same trusted source used for verification and assert that every field the handlers subsequently act on (`repository.full_name`, `organization.login`) is scoped to that same organization before dispatching to handlers. Concretely, pass the verified `repository_owner` into `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` and have `Handlers::Handler#repository_name`/`#stacks` reject (or scope their queries by) any payload whose `repository.full_name` owner does not match the organization that produced a valid signature.

### Proof of Concept
1. Configure Shipit with two organizations, `OrgA` and `OrgB`, each with its own `webhook_secret` (supported per `config/secrets.development.shopify.yml`/`test/dummy/config/secrets_double_github_app.yml`).
2. Obtain/compromise `OrgA`'s webhook secret (or otherwise cause a signed delivery to originate under `OrgA`).
3. Craft a `push` (or `status`) webhook body where `repository.owner.login == "OrgA"` (so `repository_owner` resolves to `OrgA` and the signature check passes with `OrgA`'s secret) but `repository.full_name == "OrgB/some-other-repo"`.
4. Sign the raw body with `OrgA`'s `webhook_secret` and POST to `/webhooks` with `X-Github-Event: push`.
5. `verify_signature` passes (checked against `OrgA`), then `PushHandler` resolves `stacks` via `Repository.from_github_repo_name("OrgB/some-other-repo")` and calls `sync_github` / writes commit `Status` for `OrgB`'s stack — a write to a repository never authenticated by the presented signature.
