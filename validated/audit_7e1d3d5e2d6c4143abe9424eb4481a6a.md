### Title
Webhook signature is verified against the organization owning `repository.owner.login`, but state changes are applied to the repository named in `repository.full_name` - allowing cross-organization forged CI status and unauthorized deploys - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/handler.rb])

### Summary
`WebhooksController#verify_signature` selects which `GitHubApp`/webhook secret to validate a request against using `params.dig('repository', 'owner', 'login')`, i.e. the *owner* embedded in the payload. [1](#0-0) [2](#0-1)  But every event handler resolves the actual `Repository`/`Stack` that gets mutated from a *different* field of the same JSON body, `repository.full_name`, with no re-check that it matches the organization whose secret validated the request. [3](#0-2)  Combined with the documented, optional nature of `webhook_secret` (`return true unless webhook_secret`), this breaks the intended binding "organization that authenticated == repository that is written." [4](#0-3) [5](#0-4) 

### Finding Description
`verify_signature` does:
```
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
```
where `repository_owner` reads `repository.owner.login` (falling back to `organization.login`) straight from the untrusted, attacker-suppliable JSON body. [6](#0-5)  `GitHubApp#verify_webhook_signature` unconditionally returns `true` when no `webhook_secret` is configured for that organization: `return true unless webhook_secret`. [4](#0-3)  A `webhook_secret` is explicitly documented as *optional* per organization in `config/secrets.yml`. [5](#0-4) [7](#0-6) 

Once `verify_signature` passes (trivially, for any org lacking a secret, with zero credentials), `Webhooks.for_event(event)` handlers process the raw body. [8](#0-7)  Every handler resolves the target stacks via `Handler#repository_name`, which reads `payload.dig('repository', 'full_name')` - a completely independent field from the `repository.owner.login` used moments earlier to pick the (secret-less) org:
```
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [3](#0-2) 

Nothing enforces `repository.full_name.split('/').first == repository.owner.login`. An attacker only needs one organization in the Shipit deployment's `config/secrets.yml` to be configured without a `webhook_secret` (an explicitly supported, "optional" configuration) to satisfy `repository_owner` for that org, while pointing `repository.full_name` at a stack belonging to an entirely different, fully-secured organization.

### Impact Explanation
This lets an unauthenticated, unprivileged attacker (no Shipit session, no `ApiClient` token, no GitHub App key, no webhook secret) forge arbitrary webhook events against **any** repository/stack tracked by the Shipit instance, not just the secret-less organization's own repositories. Concretely:
- `StatusHandler#process` writes an attacker-controlled `CommitStatus` (`state`, `context`, `description`, `target_url`) onto any existing `Commit` matched purely by `sha`, regardless of which org's stack it belongs to. [9](#0-8)  Since Shipit stacks gate deploy eligibility and continuous delivery scheduling on commit statuses, an attacker can flip a target commit to "success" and trigger continuous-delivery-driven deploys/rollbacks on a stack they have no authorization over - an unauthorized deploy crossing the organization boundary that the webhook signature was supposed to enforce.
- `CheckSuiteHandler#process` and `PushHandler#process` similarly act on `stacks` resolved via the same unchecked `repository.full_name`, letting the attacker enqueue `RefreshCheckRunsJob`/`GithubSyncJob` for arbitrary stacks. [10](#0-9) [11](#0-10) 

This satisfies the "unauthorized deploy" / cross-repository-write impact bar.

### Likelihood Explanation
Requires only that at least one organization configured in the Shipit deployment omits `webhook_secret` - a state the project's own setup documentation calls "optional," so it is realistic in real deployments (small teams, staging environments, or orgs added without following the security hardening step). [5](#0-4)  No credentials, sessions, or GitHub write access are needed - just an HTTP POST to `/webhooks` with a crafted JSON body and a matching `X-Github-Event` header.

### Recommendation
- After resolving `stacks`/`Repository.from_github_repo_name(repository_name)` in `Handler`, verify that the resolved repository's `owner` matches the organization (`repository_owner`) whose secret validated the request, or thread the authenticated organization through to each handler and assert equality before acting.
- Alternatively/additionally, make `webhook_secret` mandatory (fail closed) instead of allowing `verify_webhook_signature` to return `true` when unset.

### Proof of Concept
1. Deploy Shipit configured with two organizations in `config/secrets.yml`: `orgA` (no `webhook_secret` set) and `orgB` (has a `webhook_secret`, hosts a stack with `continuous_deployment: true`).
2. Attacker (no account, no token) sends:
   ```
   POST /webhooks
   X-Github-Event: status
   Content-Type: application/json

   {
     "repository": { "owner": { "login": "orgA" }, "full_name": "orgB/target-repo" },
     "sha": "<known head sha of orgB's stack>",
     "state": "success",
     "context": "ci/forced",
     "description": "forced"
   }
   ```
3. `WebhooksController#verify_signature` calls `Shipit.github(organization: "orgA")`, whose `verify_webhook_signature` returns `true` unconditionally because `orgA` has no `webhook_secret`. [4](#0-3) 
4. `StatusHandler#process` locates the commit by `sha` (belonging to `orgB`'s stack) and records the forged "success" status. [9](#0-8) 
5. If `orgB`'s stack has continuous delivery enabled, the forged passing status can trigger an automatic, unauthorized deploy - despite the attacker never having interacted with `orgB` or its webhook secret at all.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e

        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
