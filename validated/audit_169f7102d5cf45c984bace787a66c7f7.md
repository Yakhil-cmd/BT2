### Title
Cross-repository status pollution via unscoped `Commit.where(sha:)` lookup - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits by bare `sha` across the entire `commits` table with no repository/stack scoping, unlike every other webhook handler in the same directory which resolves the target stack via `Repository.from_github_repo_name(payload.dig('repository','full_name'))`. Because git commit SHAs are content-addressed and identical across forks/shared history, an attacker who owns any repository connected to Shipit can send a validly-signed `status` webhook for their own repo whose `sha` happens to also identify a commit tracked by an unrelated victim stack, writing a `Status` row onto that victim commit and driving `stack.schedule_merges` when `merge_queue_enabled` is true.

### Finding Description
The broken binding is: **a `Status` record for context `ci/test` must only be attributable to the repository that the GitHub webhook signature authenticated**, i.e. `status.commit.stack.repository == payload.repository`. The code violates this.

- `WebhooksController#verify_signature` only checks the HMAC signature against `Shipit.github(organization: repository_owner)`; it authenticates that the payload came from *some* trusted GitHub organization, not that the `sha` inside the payload belongs to that organization's repository. [1](#0-0) 
- `StatusHandler#process` then does:
```ruby
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
```
with no reference to `payload['repository']['full_name']` at all. [2](#0-1) 
- Compare with every other handler (`Handler#stacks`, `PullRequest::OpenedHandler#repository`, `AssignedHandler#pull_request`, etc.), which explicitly resolve `Repository.from_github_repo_name(repository_name)` before touching any record. [3](#0-2) [4](#0-3) 
- `Commit#sha` is **not** globally unique — it's scoped per `stack_id` (`Commit belongs_to :stack`, and helper scopes like `children` explicitly filter `where(stack_id:)`), so it is entirely normal for two different stacks tracking related/forked repositories to have `Commit` rows sharing the same `sha`. [5](#0-4) [6](#0-5) 
- Writing the status triggers `create_status_from_github! -> add_status`, which on a state transition to `success`/`pending` calls `stack.schedule_merges`, feeding the merge queue with an attacker-forged green status on the victim's commit. [7](#0-6) [8](#0-7) 

**Exploit flow**: Attacker owns (or forks) a repository connected to Shipit with its own registered GitHub App/webhook secret for their organization. Because forked repositories share commit ancestry, some commit SHAs in the attacker's repo are identical to SHAs already tracked in the victim's stack (`Commit` rows created via normal `push`/GithubSync). The attacker triggers (or directly POSTs, since no live GitHub signature is required beyond their own organization's secret, which they legitimately hold for their own repo) a `status` webhook with `context: "ci/test"`, `state: "success"`, and `sha` set to that shared commit SHA. `StatusHandler` matches and mutates every `Commit` row across every stack sharing that SHA, including the victim's, regardless of `merge_queue_enabled`. If the victim stack requires `ci/test` and has `merge_queue_enabled: true`, this fabricated green status can allow `ProcessMergeRequestsJob`/`stack.schedule_merges` to proceed with a merge/deploy the victim never actually greenlit via their own CI.

Existing guards (`verify_signature`, `drop_unhandled_event`, `ExplicitParameters` schema) only validate payload shape and organization-level HMAC — none of them constrain which `Commit`/`Stack` records the `sha` can touch, so they do not stop this divergence.

### Impact Explanation
An attacker who controls only their own repository/organization webhook secret can write `Status` rows into an arbitrary victim stack's commit, as long as a shared SHA exists (a routine occurrence for forks, cherry-picks, or shared monorepo history). Combined with `merge_queue_enabled`, this can flip a required check to green and drive `stack.schedule_merges`, i.e. an unauthorized merge/deploy of code the victim's own CI never verified for that context. This is a payload for one repository mutating another's commit/stack state, matching the Critical category ("a payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy, rollback or merge").

### Likelihood Explanation
Preconditions: attacker needs a repository already connected to Shipit (or one whose organization is already onboarded, since `verify_signature` resolves `Shipit.github(organization: repository_owner)`) so they can produce a validly-signed `status` webhook, and a SHA collision with a targeted victim stack's tracked commit — trivially achievable via forking a shared public repository (fork commits are byte-identical, hence SHA-identical, to their upstream ancestors) or via any repo with shared git history. No GitHub secrets, Shipit session, or maintainer role of the victim stack are required. The attack is repeatable against any stack sharing history with any repo the attacker can post webhooks for.

### Recommendation
Scope `StatusHandler#process` (and `Commit` status/check-run replication generally) by repository, mirroring the pattern used in `Handler#stacks` / other handlers: resolve the target `Repository`/`Stack` from `payload.dig('repository','full_name')` first, then restrict the `Commit` lookup to `stack.commits.where(sha: params.sha)` (or join through `stacks: { repositories: { id: repository.id } }`) instead of a bare `Commit.where(sha: params.sha)` across all stacks.

### Proof of Concept
minitest outline (`test/models/shipit/webhooks/handlers/status_handler_test.rb`, hypothetical):
```ruby
test "status for one repository does not mutate a commit belonging to another stack sharing the same sha" do
  victim_stack = shipit_stacks(:shipit)
  victim_stack.update!(merge_queue_enabled: true)
  shared_sha = "a" * 40

  victim_commit = victim_stack.commits.create!(sha: shared_sha, message: "shared ancestor")

  attacker_stack = shipit_stacks(:cyclimse) # different repository
  attacker_commit = attacker_stack.commits.create!(sha: shared_sha, message: "shared ancestor")

  payload = {
    'sha' => shared_sha,
    'state' => 'success',
    'context' => 'ci/test',
    'repository' => { 'full_name' => attacker_stack.repository.github_repo_name }
  }

  # Binding under test:
  # status.commit.stack.repository == payload['repository'] must hold for every created Status
  Shipit::Webhooks::Handlers::StatusHandler.call(payload)

  victim_commit.reload
  assert_empty victim_commit.statuses, "status webhook for attacker's repository must not create a Status on the victim stack's commit"
end
```
This test currently fails against the existing `StatusHandler#process` implementation, confirming the invariant is broken.

    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
