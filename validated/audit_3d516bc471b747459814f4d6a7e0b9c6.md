### Title
Cross-repository status forgery via unscoped `Commit.where(sha:)` lookup in `StatusHandler` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits by bare SHA across the entire `commits` table with no repository scoping, unlike other handlers (e.g. `PushHandler`) which restrict their effect to `stacks` derived from `Repository.from_github_repo_name(repository_name)`. Because `verify_signature` only proves the payload came from *some* organization the attacker controls (their own GitHub account/org with the Shipit GitHub App installed), an attacker can send a validly-signed `status` webhook from their own repository for a SHA that also exists as a commit on a victim's stack, and `StatusHandler` will write that status to the victim's commit regardless of which repository authenticated the webhook.

### Finding Description
The broken binding: the code should guarantee `commit.stack.repository.full_name == payload['repository']['full_name']` for every commit whose status is mutated by a webhook, but `StatusHandler` never establishes this equality.

Code path:
- `Shipit::WebhooksController#create` (app/controllers/shipit/webhooks_controller.rb:10-15) parses the raw JSON and dispatches to `Shipit::Webhooks.for_event(event)` handlers after `verify_signature`.
- `verify_signature` (app/controllers/shipit/webhooks_controller.rb:24-49) validates the HMAC signature using `Shipit.github(organization: repository_owner)`, where `repository_owner` is read straight from the attacker-supplied `payload['repository']['owner']['login']`. This only proves the request was signed for *the organization named in the attacker's own payload* — it says nothing about which commit/stack the status content (`sha`, `context`) is allowed to touch.
- `StatusHandler#process` (app/models/shipit/webhooks/handlers/status_handler.rb:20-24):
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
This queries `Commit` by SHA only, with no `Repository`/`stack` filter, in contrast to `PushHandler#process` (app/models/shipit/webhooks/handlers/push_handler.rb:12-17) which scopes via `stacks.not_archived.where(branch:)`, and the base `Handler#stacks` helper (app/models/shipit/webhooks/handlers/handler.rb:32-34) which derives stacks strictly from `Repository.from_github_repo_name(repository_name)`.
- `Commit#create_status_from_github!` → `add_status` (app/models/shipit/commit.rb:165-169, 366-386) creates the `Status` record, recomputes `status`, and — critically — calls `stack.schedule_merges` when the new status is `pending?` or `success?`, and emits `deployable_status` hooks that feed continuous delivery (`schedule_continuous_delivery`, app/models/shipit/commit.rb:281-287) which checks `deployable?` (`stack.ignore_ci? || (success? && !blocked?)`).

Exploit flow: An attacker owns a repository (with the Shipit GitHub App installed on their own org/account, satisfying `verify_signature`). They craft/obtain a commit whose SHA is identical to one that also exists as a `Commit` row for a victim's production stack (e.g., a commit cherry-picked, rebased without changes, or otherwise shared/duplicated across repositories, which preserves the Git SHA). They send `POST /webhooks` with `X-Github-Event: status`, a validly-signed body for their own repo, `sha` equal to the victim's commit SHA, `context: "ci/jenkins"`, `state: "success"`. `StatusHandler` finds the victim's `Commit` row purely by SHA match and writes a successful status to it, flipping its CI state and triggering `stack.schedule_merges`/continuous delivery on the victim's production stack — with no check that the request came from the victim's repository.

Existing guards fail here because: `verify_signature` authenticates *organization identity*, not *content scope*; `drop_unhandled_event`/`check_if_ping` are irrelevant; `ExplicitParameters` only validates types, not repo ownership; there is no `Repository`/`stack` scoping anywhere in `StatusHandler`.

### Impact Explanation
A payload signed for one repository can mutate the CI status of a commit belonging to a completely different stack/repository, which is explicitly listed as a Critical-severity impact ("a payload for one repository mutating another's stack, commit, task or team"). Since `add_status` triggers `stack.schedule_merges` and continuous-delivery evaluation, and the affected stack is production, this can cause an unauthorized deploy/merge/block on production — also Critical ("unauthorized deploy, rollback or merge"). The attack is repeatable against any stack whose commit table contains a SHA the attacker can also produce/control in their own repo (shared history via forks, cherry-picks, or rebase-preserving-SHA scenarios), and is not limited to a single victim.

### Likelihood Explanation
Preconditions: attacker must own/control a repository with the Shipit GitHub App installed (to pass `verify_signature`) and must know or engineer a SHA collision with a commit tracked by a victim stack — realistic when repositories share history (forks, mirrors, cherry-picked commits, or a monorepo shared across multiple Shipit stacks), since Git SHAs are identical when tree/parents/message/authorship are identical. No Shipit session, API token, or maintainer privilege is required. Cost is a single crafted webhook POST; fully repeatable.

### Recommendation
Scope `StatusHandler#process` by the repository that authenticated the webhook, mirroring `PushHandler`/`Handler#stacks`: resolve the commit(s) through the stacks tied to `Repository.from_github_repo_name(repository_name)` (or equivalently join `Commit` to `Stack`/`Repository` and filter by `stack.repository == repository_from_payload`) before applying the status, rejecting/ignoring commits belonging to other repositories.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb (conceptual)
test "status for a commit shared across repositories only affects the authenticating repository's stack" do
  attacker_stack = shipit_stacks(:shipit)          # attacker-controlled repo/stack
  victim_stack   = shipit_stacks(:production)      # victim stack, environment: 'production'
  shared_sha     = 'deadbeef' * 5

  victim_commit   = victim_stack.commits.create!(sha: shared_sha, message: "shared commit")
  attacker_commit = attacker_stack.commits.create!(sha: shared_sha, message: "shared commit")

  # BEFORE: binding under test
  # victim_commit.status.state == 'unknown' (no ci/jenkins status yet)
  assert_equal 'unknown', victim_commit.reload.status.simple_state

  payload = { sha: shared_sha, state: 'success', context: 'ci/jenkins' }
  Shipit::Webhooks::Handlers::StatusHandler.call(
    ExplicitParameters::Parameters.new(payload) # simulating attacker-signed payload for attacker's own repo
  )

  # AFTER: assert the equality is violated -- victim's commit was mutated
  # even though the webhook was only ever authenticated for the attacker's repository
  assert_equal 'success', victim_commit.reload.status.simple_state
  refute_equal attacker_commit.stack.repository.full_name, victim_commit.stack.repository.full_name
end
```
This demonstrates `StatusHandler` writes to `victim_commit` (belonging to `victim_stack`/production) despite the webhook signature only authenticating `attacker_stack`'s repository, confirming the missing repository-scoping equality.
