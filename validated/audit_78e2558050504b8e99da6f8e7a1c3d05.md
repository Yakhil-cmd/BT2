### Title
Cross-repository `Commit` status write via unscoped `Commit.where(sha:)` in `StatusHandler#process` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` resolves the target `Commit` purely by `sha`, without any check that the commit's `stack.repository.full_name` matches `payload.dig('repository', 'full_name')` that was signature-verified in `WebhooksController#verify_signature`. Any organization/repository whose GitHub App webhook secret is configured in this Shipit instance can push a valid, correctly-signed `status` event referencing a SHA that happens to exist in a completely unrelated repository/stack, and that unrelated commit's status/state will be silently updated.

### Finding Description
Binding claimed: `Repository` resolvable from `payload.dig('repository','full_name')` should equal the `Repository` owning each `Commit` returned by `Commit.where(sha: params.sha)`. Tracing the code shows this binding is never enforced.

- `WebhooksController#create` parses the JSON body and dispatches to handlers registered for the event, e.g. `Handlers::StatusHandler`: [1](#0-0) 
- `verify_signature` only checks that the payload is signed with the webhook secret belonging to the organization named in `payload.dig('repository','owner','login')` (`repository_owner`) — it authenticates *which org sent the request*, not which commit/stack the payload is authorized to mutate: [2](#0-1) 
- `Handler#initialize` only parses parameters via `ExplicitParameters`; it stores `payload` but the base class never cross-checks `repository_name` against the record(s) a subclass will mutate — that check (`stacks`) exists as a helper but is opt-in per handler: [3](#0-2) 
- `StatusHandler#process` uses the opt-in helper nowhere; it queries `Commit` globally by `sha` alone: [4](#0-3) 
- Contrast with `CheckSuiteHandler#process`, which does scope through `stacks.where(branch: ...)` (derived from `repository_name`) before touching commits — showing the engine's own convention for correctly scoping mutations, which `StatusHandler` fails to follow: [5](#0-4) 
- `commit.create_status_from_github!` creates a `Status` row and, via `add_status`, calls `Hook.emit(:commit_status, ...)`, potentially `Hook.emit(:deployable_status, ...)`, and `stack.schedule_merges`, all against the resolved commit's actual stack/repository — not the attacker's: [6](#0-5) [7](#0-6) 

Exploit flow: the attacker (an unprivileged party who owns/administers a repository/org that has its own valid Shipit webhook configuration, e.g. their own fork or their own private org registered with this Shipit instance) sends a `status` webhook, correctly signed with *their own* org's webhook secret, whose `repository.full_name` is their own repo but whose `sha` is copied from a public commit in a target victim repository/stack tracked by the same Shipit instance. `verify_signature` passes because the signature is valid for the attacker's own organization. `StatusHandler#process` then finds the `Commit` row for that `sha` regardless of which repository it belongs to and mutates it. Existing guards (`verify_signature`, `drop_unhandled_event`, `ExplicitParameters` schema) only validate signature/shape, never the sha-to-repository binding, so they do not prevent this divergence.

Note: `sha` collisions across unrelated repositories require the attacker to guess/know a commit sha tracked in the victim stack (e.g., by observing a public GitHub commit or PR that Shipit has already ingested via `push`), which is realistic since commit SHAs are public and this Shipit instance's tracked stacks/branches are often visible in the UI.

### Impact Explanation
A cross-tenant/cross-repository write occurs: an attacker controlling one onboarded repository/org can write `Status` records (and cascade `Hook.emit(:commit_status/:deployable_status)`, `stack.schedule_merges`) against a `Commit` belonging to an entirely different repository's `Stack`, without ever authenticating against that repository. This matches "a payload for one repository mutating another's stack, commit, task or team" — Critical. It is repeatable against any known/discoverable SHA across all stacks hosted on the same Shipit instance, and can influence continuous-deployment/merge-queue decisions (`schedule_merges`, `deployable_status`) for a victim repository the attacker has no relationship with.

### Likelihood Explanation
Preconditions: the attacker needs at least one repository/organization already configured with this Shipit instance's GitHub App (so `verify_webhook_signature` succeeds for their own org), and knowledge of a target commit SHA tracked by a victim `Stack` on the same instance (SHAs are public on GitHub and often visible via the Shipit UI). No GitHub App private key, `webhook_secret` of the victim, session, or API token is required — only the attacker's own already-issued webhook secret for their own repo. This is straightforward to reproduce and repeat against any stack sharing the instance.

### Recommendation
In `StatusHandler#process` (and any other handler doing global lookups by external identifiers), scope the `Commit` lookup to stacks/repositories resolvable from the authenticated `payload.dig('repository','full_name')`, mirroring the pattern already used in `CheckSuiteHandler#process` (`stacks.where(...)`), e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` or `Commit.joins(:stack).merge(Stack.where(repository: Repository.from_github_repo_name(repository_name)))`.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (new test)
test ":status from one repository silently mutates a commit belonging to an unrelated stack" do
  victim_commit = shipit_commits(:first) # belongs to shipit_stacks(:shipit), repo e.g. "shopify/shipit-engine"
  attacker_repo_payload = { repository: { owner: { login: 'attacker-org' } } }

  before_state = victim_commit.state
  refute_equal 'success', before_state

  body = {
    'sha' => victim_commit.sha,
    'state' => 'success',
    'context' => 'ci/attacker'
  }.merge(attacker_repo_payload).to_json

  request.headers['X-Github-Event'] = 'status'
  GithubHook.any_instance.stubs(:verify_signature).returns(true) # simulate attacker's own valid signature for attacker-org

  assert_nothing_raised do
    post :create, body: body, as: :json
  end
  assert_response :ok

  victim_commit.reload
  assert_equal 'success', victim_commit.state
  refute_equal 'attacker-org', victim_commit.stack.repository.full_name.split('/').first
end
```
Both sides of the binding are asserted: `payload['repository']['owner']['login']` == `'attacker-org'` while `victim_commit.stack.repository.full_name` remains unrelated, yet the write to `victim_commit`'s `Status` succeeds with `head(:ok)` and no exception, confirming a silent unauthorized cross-repository write.

    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
