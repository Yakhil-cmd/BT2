### Title
Webhook signature is verified against `repository.owner.login`, but repository-scoped handlers act on the unchecked `repository.full_name` field, allowing cross-organization writes - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects which GitHub App/organization secret to use for HMAC verification based on `params.dig('repository', 'owner', 'login')`, but every webhook handler (`PushHandler`, `PullRequest::*Handler`, etc.) resolves the repository/stack to act on using the separate `repository.full_name` field via `Handler#repository_name` / `Repository.from_github_repo_name`. The signature only proves the request was authorized by whichever organization's secret matches `repository.owner.login`; it does not bind that authorization to the `full_name` field that actually determines which tracked repository gets written to.

### Finding Description
`verify_signature` computes the verifying organization purely from the payload: [1](#0-0) [2](#0-1) 

```
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(...)
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

Meanwhile, every handler that actually performs a write scopes its action using a *different* field of the same payload, `repository.full_name`: [3](#0-2) 

```
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
```

and, e.g., `PushHandler#process`: [4](#0-3) 

There is no code path that checks `repository.owner.login == repository.full_name.split('/').first` (or equivalent) before dispatching the handler. Because the webhooks endpoint is a shared, multi-tenant entry point (any organization with a GitHub App/webhook secret configured via `Shipit.github(organization: ...)` can deliver a validly-signed request), a request that is correctly signed for organization A can carry `repository.full_name` pointing at a repository/stack that belongs to organization B. The `create` action performs no additional binding check before invoking handlers: [5](#0-4) 

This is the same class of bug as the reported issue: a security-critical guard (the HMAC signature) validates one part of the "message" (which the report frames as re-entrant state, here it's the authenticating organization), while a different, unguarded part of the same message (`repository.full_name`, analogous to the untouched `lastPriceTimestamp`/state) is what downstream logic actually trusts and acts on.

### Impact Explanation
This breaks the binding "an organization that authenticated versus the repository that is written." Any organization onboarded to a Shipit instance (i.e., any tenant that can obtain a validly-signed webhook delivery for its own repos) can forge a webhook body whose `repository.full_name` names a stack/repository belonging to a different, unrelated organization tracked on the same Shipit deployment. Depending on handler, this can:
- Trigger `GithubSyncJob`/`stack.sync_github` on a victim stack via `PushHandler`, forcing resyncs of another org's stack.
- Drive PR lifecycle handlers (`opened_handler.rb`, `closed_handler.rb`, `labeled_handler.rb`, etc.) to mutate merge-queue / review-stack state, pull_request records, and provisioning/unprovisioning of review stacks for a repository the attacker does not own.
This is an unauthorized cross-repository/cross-organization write and satisfies the Critical-tier "cross-repository writes" impact bucket.

### Likelihood Explanation
Requires only that the Shipit instance is multi-tenant (serves more than one GitHub organization/app installation) - a documented, supported configuration (`Shipit.github(organization:)` is keyed by organization). Any org admin capable of receiving one legitimate webhook delivery (or replaying/crafting a POST with a self-controlled repo's signature) can supply arbitrary payload content for the fields handlers actually trust, since GitHub's HMAC only guarantees payload integrity relative to the org whose secret produced it - not that `repository.owner.login` and `repository.full_name` are cross-checked by Shipit itself.

### Recommendation
In `WebhooksController#verify_signature`, after selecting `repository_owner` to pick the verifying app/secret, also assert that `repository.full_name`'s owner segment matches `repository_owner` (or, more robustly, have handlers derive the target repository strictly from the same owner value that was used for signature verification) before dispatching to `Shipit::Webhooks.for_event(event)`. Reject the request (422) if the two disagree.

### Proof of Concept
1. Shipit instance is configured with two GitHub App/organization credentials: `org-attacker` and `org-victim` (both have stacks tracked on the same Shipit deployment).
2. Attacker controls a repo under `org-attacker` and can obtain (or compute, given their own webhook secret) a valid `X-Hub-Signature` for an arbitrary JSON body, by having GitHub deliver (or by directly POSTing, since the secret used is `org-attacker`'s own) a `push` event payload where:
   - `repository.owner.login = "org-attacker"` (so `verify_signature` selects and validates against `org-attacker`'s secret, and passes)
   - `repository.full_name = "org-victim/victim-repo"` (the field actually used by `PushHandler#stacks` / `Repository.from_github_repo_name`)
3. POST this payload with header `X-Github-Event: push` and a signature valid for `org-attacker` to `/webhooks`.
4. `verify_signature` succeeds (signature matches `org-attacker`'s secret). `PushHandler#process` then resolves stacks via `repository_name` = `"org-victim/victim-repo"` and invokes `stack.sync_github(expected_head_sha: params.after)` on the victim's stack - a write the attacker has no legitimate authorization to trigger.

*Note:* I was unable to fully trace `Shipit.github`/`GithubApp#verify_webhook_signature` (`lib/shipit/github_app.rb`) implementation details or `Stack#sync_github` internals within the available index to confirm every downstream write path's exact severity per handler; a full audit of each handler under `app/models/shipit/webhooks/handlers/**` (push, pull_request/*, check_suite, status) is recommended to enumerate the complete set of exploitable writes.
