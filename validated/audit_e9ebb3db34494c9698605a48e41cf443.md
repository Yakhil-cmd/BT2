### Title
RAY value overflow before the index cap permanently freezes a market - (File: `common/src/rates/simulate.rs`)

### Summary
**Severity: Medium.** An attacker who can create sufficiently large supply and debt positions can make `borrowed * borrow_index` exceed `i128::MAX`. Once ledger time advances, `update_indexes` attempts to unscale the debt before applying the borrow-index cap, panics with `MathOverflow`, and leaves the market permanently unable to accrue, repay, withdraw, or liquidate. [1](#0-0) [2](#0-1) 

### Finding Description
The permissionless `Controller::update_indexes(caller, assets)` entry point forwards each `HubAssetKey` to the pool. [3](#0-2)  In the pool, every listed market is loaded and passed through `interest::global_sync` before state is committed. [4](#0-3) 

`accrue_step` first reconstructs the market’s asset-denominated debt and supply with `scaled_to_original(borrowed, borrow_index)` and `scaled_to_original(supplied, supply_index)`; utilization, rate selection, and the new index are computed only afterward. [5](#0-4)  `scaled_to_original` is a checked `Ray::mul`, which calls `mul_div_half_up`. [6](#0-5) [7](#0-6)  When the exact `scaled * index / RAY` result does not fit `i128`, the widened conversion returns `None` and the caller panics with `GenericError::MathOverflow`. [8](#0-7) 

The existing `MAX_BORROW_INDEX_RAY` cap does not prevent this state: it is applied to the newly calculated index only after the already-stored scaled debt has been multiplied by the old index. [9](#0-8) [1](#0-0) 

### Impact Explanation
This is permanent market freezing, not merely a rejected input. The panic occurs before `mark_accrued`, so `last_timestamp` does not advance and every later transaction retries the same overflowing conversion. [10](#0-9)  Because the failed `global_sync` also precedes the market commit, there is no partial accrual or safer capped state left behind. [11](#0-10) 

The stuck accrual is on the settlement path for user exits and debt repayment: withdrawal loads an accrued market leg before resolving and burning supply, while repayment does the same before resolving and burning debt. [12](#0-11) [13](#0-12)  The repository’s regression test demonstrates this exact end state: `update_indexes`, `withdraw`, and `repay` all return `MathOverflow`, while the stored borrow index remains below `MAX_BORROW_INDEX_RAY`. [14](#0-13) 

Consequently, suppliers cannot recover principal, borrowers cannot cure positions, liquidators cannot clear unhealthy debt, and protocol revenue in the affected market remains unreachable without a privileged contract upgrade.

### Likelihood Explanation
Triggering the condition requires a large market, sustained borrowing, and enough ledger time for index growth to make a scaled total unrepresentable; it is therefore not an immediate dust griefing vector. The required shape is nevertheless reachable through ordinary user calls: `supply` can create an account for a caller, `borrow` can draw the supplied asset to that caller, and `update_indexes` is permissionless. [15](#0-14) [16](#0-15)  A single address can own separate supplier and borrower position accounts.

Feasibility depends on configured caps, token supply, available collateral, and the market’s rate curve. The checked-in proof uses a high-decimal market and 98% utilization to reach the overflow before the protocol’s index ceiling. [17](#0-16) [18](#0-17) 

### Recommendation
Do not represent accrual-critical market values in `i128` before establishing that the result fits the accounting domain. At minimum:

- Use non-panicking or widened arithmetic for the utilization inputs in `accrue_step`, with an explicit saturation policy for utilization.
- Enforce an invariant such as `borrowed * borrow_index <= i128::MAX` and `supplied * supply_index <= i128::MAX` before index growth can cross the value ceiling.
- Keep a bounded emergency repayment or bad-debt path available after the cliff, or clamp accrual in a way that leaves debt and supply convertible.
- Add the existing long-horizon scenario as a regression test against any revised accrual implementation.

### Proof of Concept
A single caller can create the position shape through two owned accounts:

```rust
let debt_asset = HubAssetKey { hub_id, asset: debt_token };
let collateral_asset = HubAssetKey { hub_id, asset: collateral_token };

// Account A supplies liquidity to the debt market.
let supplier_id = controller.supply(
    attacker,
    0,
    spoke_id,
    vec![(debt_asset.clone(), debt_liquidity)],
);

// Account B supplies separate collateral.
let borrower_id = controller.supply(
    attacker,
    0,
    spoke_id,
    vec![(collateral_asset, collateral_amount)],
);

// Account B borrows nearly all debt-market liquidity.
controller.borrow(
    attacker,
    borrower_id,
    vec![(debt_asset.clone(), borrow_amount)],
    Some(attacker),
);

// After enough ledger advancement that debt_asset.borrowed *
// debt_asset.borrow_index / RAY exceeds i128::MAX:
controller.update_indexes(attacker, vec![debt_asset.clone()]);
```

The final call panics with `MathOverflow` inside `scaled_to_original`; subsequent `repay`, `withdraw`, `liquidate`, and later `update_indexes` attempts repeat the same accrual and fail. [19](#0-18) [20](#0-19)

/// Computes `x * y / d` rounded half up. Returns `None` if `x < 0`, `y < 0`, `d <= 0`, or the
/// result does not fit in `i128`.
pub fn try_mul_div_half_up(env: &Env, x: i128, y: i128, d: i128) -> Option<i128> {
    if x < 0 || y < 0 || d <= 0 {
        return None;
    }
    let half = d / 2;

    // Fast path: the biased product fits `i128`, so the whole computation is
    // native. `x * y + half` is non-negative here, so `/` is the floor the
    // widened path would produce.
    if let Some(biased) = x
        .checked_mul(y)
        .and_then(|product| product.checked_add(half))
    {
        return Some(biased / d);
    }

    let (x256, y256, d256) = to_i256_operands(env, x, y, d);
    x256.mul(&y256)
        .add(&I256::from_i128(env, half))
        .div(&d256)
        .to_i128()
}

pub(crate) fn global_sync(env: &Env, cache: &mut Cache) {
    if !cache.needs_accrual() {
        return;
    }

    let mut remaining = cache.elapsed_ms();
    while let Some(nonzero) = NonZeroU64::new(remaining) {
        let chunk = nonzero.get().min(MAX_COMPOUND_DELTA_MS);
        accrue_chunk(env, cache, chunk);
        remaining = remaining.saturating_sub(chunk);
    }

    cache.mark_accrued();
}
