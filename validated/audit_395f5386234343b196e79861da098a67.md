### Title
`OpenedHandler#provision?` operator precedence bypasses `review_stacks_enabled` gate for label-based provisioning - (File: `app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb`)

### Summary
`OpenedHandler#provision?` combines `review_stacks_enabled` with `provisioning_behavior_allow_all?` using `&&`/`||` without parentheses grouping the `review_stacks_enabled` check across all branches. Because Ruby's `&&` binds tighter than `||`, the `review_stacks_enabled` check only guards the `allow_all` branch, not the `allow_with_label` or `prevent_with_label` branches, so a repository with review stacks disabled but `provisioning_behavior: :allow_with_label` will still provision a review stack for any PR carrying the configured label.

### Finding Description
The claimed binding is: `repository.review_stacks_enabled == true` must hold before any `ReviewStack` is created from that repository's pull requests.

The code is:
```ruby
def provision?
  repository.review_stacks_enabled &&
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
``` [1](#0-0) 

Due to standard Ruby precedence (`&&` before `||`), this parses as:
`(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?)`

`review_stacks_enabled` is scoped only to the first disjunct. If `review_stacks_enabled == false` and `provisioning_behavior == "allow_with_label"`, the first disjunct is `false`, but the second disjunct `(allow_with_label? && has_label?)` evaluates independently of `review_stacks_enabled` and can be `true`, making `provision?` return `true`.

`respond_to_pull_request_opened?` gates `process`, which calls `ReviewStackAdapter#find_or_create!`, which calls `create!`, building a `ReviewStack` with `branch: params.pull_request.head.ref` (attacker-controlled branch name) and `environment: "pr#{params.number}"`. [2](#0-1) [3](#0-2) 

The attacker's exact action: open a PR on a repository configured with `review_stacks_enabled: false, provisioning_behavior: "allow_with_label"`, and add the exact `provisioning_label_name` label to that PR (a normal GitHub action any contributor can do on their own PR). GitHub then emits a legitimate, signature-valid `pull_request` `opened` (or subsequently `labeled`) webhook to `/webhooks`.

Existing guards do not prevent this: signature verification in `WebhooksController` only authenticates that the payload genuinely came from GitHub for that org/repo — it says nothing about whether the *business logic* correctly enforces `review_stacks_enabled`. `Repository#review_stacks_enabled` and `provisioning_behavior` are legitimate admin-configured columns; nothing in `Repository`, `ExplicitParameters` schema, or `ReviewStackAdapter` re-checks `review_stacks_enabled` before `create!`. The bug is purely in the boolean logic of `provision?`.

### Impact Explanation
For any repository whose administrator (intending to disable review stacks entirely) sets `review_stacks_enabled: false` but leaves/sets `provisioning_behavior: allow_with_label` (or `prevent_with_label`, which is even more permissive by default), an unprivileged PR author who can label their own PR (or, in the `prevent_with_label` case, simply avoid adding a label) can force creation of a `ReviewStack` record with attacker-influenced `branch`/`environment`, feeding the `ReviewStackProvisioningQueue` and downstream provisioning/deploy machinery for a repository that was explicitly configured to have review stacks disabled. This is an unauthorized-record-write / unauthorized-provisioning path scoped to a single repository's own PRs (not cross-tenant), matching "unauthorized deploy/rollback" adjacent impact via unintended `ReviewStack` provisioning.

### Likelihood Explanation
Requires a repository configured with `review_stacks_enabled: false` and `provisioning_behavior: allow_with_label` (or `prevent_with_label`) — a plausible/realistic misconfiguration since these two settings are logically independent fields and an admin could reasonably believe `review_stacks_enabled: false` fully disables the feature regardless of `provisioning_behavior`. No secrets, tokens, or elevated permissions are needed beyond the ability to open a PR and add a label on one's own PR/fork, both of which are default GitHub permissions for any contributor. Fully repeatable per PR/branch.

### Recommendation
Add explicit parentheses so `review_stacks_enabled` gates every branch:
```ruby
def provision?
  repository.review_stacks_enabled && (
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
  )
end
```
Apply the same fix to the analogous `provision?`/logic in `labeled_handler.rb`, `unlabeled_handler.rb`, and `reopened_handler.rb`, which share the identical pattern. [4](#0-3) 

### Proof of Concept
In `test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb`, add a test with a repository fixture/stub having `review_stacks_enabled: false, provisioning_behavior: "allow_with_label", provisioning_label_name: "deploy-preview"`, and `params.pull_request.labels` containing `{ "name" => "deploy-preview" }`. Assert both sides of the binding before calling `process`: `repository.review_stacks_enabled` is `false` and `Shipit::Stack.count`/`Shipit::ReviewStack.count` is the baseline `N`. After invoking `OpenedHandler.new(...).process` (or posting the webhook fixture through the controller), assert `Shipit::ReviewStack.count == N + 1` even though `repository.review_stacks_enabled == false`, demonstrating the divergence from the intended binding.
