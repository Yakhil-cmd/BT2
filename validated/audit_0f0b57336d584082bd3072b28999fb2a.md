### Title
Webhook signature is verified against the organization derived from `repository.owner.login`/`organization.login`, but handlers act on the independently-attacker-supplied `repository.full_name` — allowing one tenant's GitHub App secret to forge push/check_suite events against another tenant's repository - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` picks which `GitHubApp` (and therefore which `webhook_secret`) to validate the HMAC against using `repository_owner`, computed as `params.dig('repository','owner','login') || params.dig('organization','login')` [1](#0-0) [2](#0-1) . Shipit supports multiple independently-configured GitHub Apps/organizations, each with its own `webhook_secret`, as shown in the multi-org secrets template [3](#0-2) . Once the signature check passes, event handlers such as `PushHandler` and `CheckSuiteHandler` resolve the target repository/stacks from a *different*, independently attacker-controlled field of the same JSON body: `payload.dig('repository', 'full_name')` [4](#0-3) . Nothing enforces that `repository.owner.login` (used to select the verifying secret) matches the owner encoded in `repository.full_name` (used to select the acted-upon `Repository`/`Stack`).

### Finding Description
The binding that should hold is:
`organization whose secret authenticated the signature == owner of the repository the handler acts on`

In `verify_signature`, the org used to select the verifying `GitHubApp`/secret comes from the top-level `repository.owner.login` (or `organization.login`) field [1](#0-0) . The HMAC covers the raw POST body, so the signature does prove "whoever holds the secret for that organization crafted this exact byte string" — but it does not prove that the byte string's *other* fields, in particular `repository.full_name`, are truthful with respect to that organization. `Handler#stacks` uses `repository_name = payload.dig('repository', 'full_name')` to resolve `Repository.from_github_repo_name(repository_name)` and the `Stack`s to operate on [4](#0-3)  — a value that is never cross-checked against `repository.owner.login`.

Because a legitimate tenant administrator of Organization A (a genuine, unprivileged-relative-to-other-tenants customer of a shared multi-org Shipit deployment) necessarily knows Organization A's own `webhook_secret` (it is a value they configured when creating their own GitHub App, per `docs/setup.md`) [5](#0-4) , they can independently compute a valid `X-Hub-Signature` for an arbitrary crafted JSON payload and POST it directly to `/webhooks` — bypassing GitHub delivery entirely. By setting `repository.owner.login` (or top-level `organization.login`) to their own org "A" (so `verify_signature` selects and validates against A's own secret, which passes) while setting `repository.full_name` to `"B/victim-repo"` (a different tenant's repository), they defeat the intended isolation between tenants.

`PushHandler` then resolves stacks via `Repository.from_github_repo_name("B/victim-repo")` and, for matching branches, calls `stack.sync_github(expected_head_sha: params.after)` [6](#0-5) , enqueuing `GithubSyncJob` for a stack that belongs to organization B, entirely under the control of an actor whose only credential is organization A's webhook secret [7](#0-6) . `CheckSuiteHandler` and `StatusHandler` are similarly reachable and act on `stacks`/`Commit.where(sha:)` derived from body fields not covered by the org-secret binding [8](#0-7) [9](#0-8) .

### Impact Explanation
This crosses the "organization authenticated vs. repository written" boundary called out as in-scope. A tenant with only their own (legitimate) webhook secret can inject forged `push`/`check_suite`/`status` events that are processed against another tenant's `Stack`/`Repository`/`Commit` records — a cross-repository/cross-tenant write not authorized by the requesting tenant's credentials. In a single-organization deployment this is inert (the owner field and full_name always agree), but the engine explicitly documents and supports the multi-org configuration where this boundary matters [3](#0-2) .

The concrete reachable actions are constrained by what the sync/check/status jobs actually do (fetch upstream commits via `stack.github_api`, mark stacks accessible/inaccessible, create commit statuses, or schedule check-run refresh) rather than an unrestricted arbitrary write; I could not fully verify within the available context whether any of these paths can be chained into a deploy/rollback trigger (e.g., via a continuous-delivery schedule reacting to newly synced commits), which would elevate this from a data-integrity/cross-tenant-DoS issue to the "unauthorized deploy" impact tier required by scope.

### Likelihood Explanation
Moderate-to-low: it requires the attacker to already be a legitimate operator of at least one organization/GitHub App configured on the same multi-tenant Shipit instance (i.e., to know that organization's own `webhook_secret`), plus knowledge of a target org/repo's `full_name`. This is a real but non-trivial precondition — it is not exploitable by a fully unauthenticated internet attacker with no relationship to the deployment, but it is exploitable without any privileged Shipit account, `ApiClient` token, or GitHub write access to the victim repository, matching the required unprivileged-attacker analog.

### Recommendation
In `WebhooksController#verify_signature`, after verifying the HMAC, cross-validate that every repository/organization identifier referenced later in the payload (in particular `repository.full_name`'s owner segment) is consistent with the `repository_owner` used to select the verifying secret, and reject the request otherwise. Equivalently, resolve the target `Repository`/`Stack` using the same organization identifier that authenticated the request, not a separately-trusted field of the same unauthenticated-until-verified JSON body.

### Proof of Concept
1. Deploy Shipit configured with two organizations, `orga` and `orgb`, each with distinct `webhook_secret`s (per `config/secrets.development.shopify.yml` format).
2. As an administrator of `orga` (knows `orga`'s `webhook_secret`), craft a JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<victim-sha>",
  "repository": { "owner": { "login": "orga" }, "full_name": "orgb/victim-repo" }
}
```
3. Compute `X-Hub-Signature: sha1=<hmac-sha1(orga_webhook_secret, body)>` and `X-Github-Event: push`, then POST directly to `/webhooks`.
4. `verify_signature` resolves `repository_owner` = `"orga"`, looks up `orga`'s `GitHubApp`, and the signature verifies successfully [1](#0-0) .
5. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("orgb/victim-repo")` [4](#0-3)  and enqueues `stack.sync_github(expected_head_sha: ...)` for `orgb`'s stack [6](#0-5)  — an action on `orgb`'s data triggered solely with `orga`'s webhook secret.

    def perform(params)
      @stack = Stack.find(params[:stack_id])
      expected_head_sha = params[:expected_head_sha]
      retry_count = params[:retry_count] || 0
      head_before_sync = spec_cache_target
      appended_commits = []

      handle_github_errors do
        new_commits, shared_parent = fetch_missing_commits { stack.github_commits }

        # Retry on Github eventual consistency: webhook indicated new commits but we found none
        if expected_head_sha && new_commits.empty? && !commit_exists?(expected_head_sha) &&
           retry_count < MAX_RETRY_ATTEMPTS
          GithubSyncJob.set(wait: RETRY_DELAY * retry_count).perform_later(params.merge(retry_count: retry_count + 1))
          return
        end

        stack.transaction do
          shared_parent&.detach_children!
          appended_commits = new_commits.map do |gh_commit|
            append_commit(gh_commit)
          end
          stack.lock_reverted_commits! if appended_commits.any?(&:revert?)
        end
      end
      sync_changed_nothing = appended_commits.empty? &&
                             spec_cache_target == head_before_sync &&
                             stack.cached_deploy_spec.present?
      return if sync_changed_nothing && !params[:force_spec_cache]

      CacheDeploySpecJob.perform_later(stack)
    end

          stacks.where(branch: params.check_suite.head_branch).each do |stack|

          end
