### Title
Webhook signature is verified against the org selected by an attacker-controlled `repository.owner.login` field, while handlers act on the separately attacker-controlled `repository.full_name` field, enabling cross-organization/cross-repository webhook forgery — (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` picks *which* GitHub App/organization secret to validate the HMAC signature against using a field read directly out of the unverified raw JSON body (`repository.owner.login`), before the signature has been checked. Every downstream `Webhooks::Handlers::Handler` then resolves the target `Stack`/`Repository` using a *different* field from that same unverified body (`repository.full_name`). Because these two fields are never cross-checked for consistency, an attacker who legitimately knows the webhook secret for one configured organization can forge a payload whose `repository.owner.login` names that (their own) organization — so the HMAC verifies — while `repository.full_name` names a repository belonging to a completely different organization, causing the handler to act on that unrelated repository/stack.

### Finding Description
`Shipit.github(organization: repository_owner)` is used to fetch the `GitHubApp` (and its `webhook_secret`) that will verify the incoming signature: [1](#0-0) [2](#0-1) 

`repository_owner` is computed as `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` — this is parsed straight from `request.raw_post` before any signature check has run, i.e. it is fully attacker-controlled. `Shipit.github(organization:)` then looks up that organization's own per-org config (and thus its own `webhook_secret`) via `github_app_config`: [3](#0-2) 

Once `verify_webhook_signature` succeeds (using HMAC-SHA1 keyed with *that org's* secret), `create` hands the *entire, unmodified* payload to every registered handler for the event: [4](#0-3) 

Handlers, however, resolve the actual target `Stack`/`Repository` from a *different* payload key — `repository.full_name` — not from `repository.owner.login`: [5](#0-4) 

Nothing in the request pipeline enforces that `repository.owner.login` and the owner portion of `repository.full_name` refer to the same organization. The equality that should hold — *"the organization whose secret authenticated the request" == "the organization owning the repository the handler writes to"* — is broken: the first is taken from `repository.owner.login`, the second from `repository.full_name`, and both are read from the same unverified body before the HMAC check runs.

In a multi-tenant Shipit deployment (multiple GitHub orgs configured under `secrets.github`, selected via `github_default_organization`/`github_organizations`), any party who legitimately knows **one** org's `webhook_secret` (e.g., an admin of Org A's own GitHub App/webhook, who is a normal, unprivileged Shipit user with respect to Org B) can:
1. Build a JSON payload with `repository.owner.login = "OrgA"` (or `organization.login`) but `repository.full_name = "OrgB/victim-repo"`.
2. Sign it with Org A's `webhook_secret` and send it as `X-Hub-Signature`.
3. `verify_signature` loads Org A's `GitHubApp`, verifies successfully.
4. The relevant handler (`PushHandler`, `StatusHandler`, `CheckSuiteHandler`, `MembershipHandler`, pull_request handlers, etc.) resolves stacks via `Repository.from_github_repo_name(payload.dig('repository','full_name'))` → finds Org B's repository/stacks and acts on them, even though the request was never actually vouched for by Org B.

This is a direct instance of the audited bug class: a value that is *authenticated* (the organization) diverges from the value that is *acted upon* (the repository being written to), because the signature covers the raw bytes but the trust decision ("whose secret do we check with") and the effect ("which repo do we mutate") are derived from two independently-attacker-controlled JSON keys instead of one canonical, verified identifier.

### Impact Explanation
This crosses the organization/tenant boundary that Shipit's per-org webhook secrets are meant to enforce, producing unauthorized cross-repository writes triggered against a target org's stacks (e.g., forged `push` events enqueueing `GithubSyncJob` against Org B's stack, forged `status`/`check_suite` events fabricating commit statuses/check runs that gate deploy readiness for Org B's stacks, or forged `pull_request`/`membership` events mutating Org B's data) — all without ever possessing Org B's webhook secret or any Shipit credential for Org B. Per the impact taxonomy, cross-repository writes triggered without the victim organization's authentication is a Critical-class impact.

### Likelihood Explanation
Exploitability requires only that the attacker legitimately controls one organization's webhook secret in a multi-org Shipit deployment — a realistic scenario for any Shipit instance onboarding more than one GitHub organization, since each org administrator configures/knows their own `webhook_secret`. No Shipit session, `ApiClient` token, or GitHub App private key for the *target* org is required; only knowledge of secrets the attacker was already given for their *own* org. The `webhooks_controller` endpoint is public and unauthenticated by design (it exists to receive GitHub callbacks), so nothing else gates the request.

### Recommendation
Do not let the payload itself choose which secret verifies the payload. Bind signature verification to a single canonical, already-known-good identifier and re-derive the acting organization from the same verified field the handlers use (`repository.full_name`), rather than from `repository.owner.login`/`organization.login`. Concretely:
- Resolve the target `Repository`/`Stack` from `repository.full_name` first, derive its organization from that already-provisioned mapping, and verify the signature using that organization's secret — never use an unverified payload field to pick the verification key when a different unverified payload field is later used to select the mutated resource.
- Alternatively, after verifying with the org selected by `repository_owner`, explicitly assert `repository.full_name`'s owner matches `repository_owner` before dispatching to handlers, rejecting mismatches with 422.

### Proof of Concept
1. Configure Shipit with two organizations, `OrgA` and `OrgB`, each with a distinct `webhook_secret` under `secrets.github`.
2. As someone who knows `OrgA`'s `webhook_secret` (e.g., the GitHub App/webhook administrator for `OrgA`), craft:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker chosen sha in OrgB/victim-repo>",
  "repository": {
    "owner": { "login": "OrgA" },
    "full_name": "OrgB/victim-repo"
  }
}
```
3. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(OrgA_webhook_secret, body)>` and POST it to `/webhooks` with `X-Github-Event: push`.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: "OrgA")`, verifies the HMAC successfully against `OrgA`'s secret. [6](#0-5) 
5. `PushHandler` (subclass of `Handler`) resolves `stacks` via `Repository.from_github_repo_name("OrgB/victim-repo")` and enqueues sync/other actions for `OrgB`'s stacks — despite the request never being authenticated by `OrgB`. [5](#0-4)

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
