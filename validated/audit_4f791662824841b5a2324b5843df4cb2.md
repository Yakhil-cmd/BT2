### Title
`StatusHandler#process` matches commits by bare `sha` with no repository/stack scoping, letting a status webhook for one repository mutate commit state on any stack sharing that SHA - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` looks up commits with `Commit.where(sha: params.sha)` and calls `create_status_from_github!` on every match, with no filter on the repository that authenticated the webhook. Because webhook signature verification is scoped to a GitHub *organization* (not a specific repository or stack), and `sha` values are not guaranteed globally unique across `Shipit::Stack`/`Shipit::Repository` records, a status for one repo's commit can flip CI state for a commit belonging to a different stack that happens to share the same SHA.

### Finding Description
The broken binding is: **the status webhook `sha`/`context`/`state` should only affect `Commit` rows belonging to the stack/repository that authenticated via `verify_webhook_signature`, i.e. `commit.stack.repository == repository_owner`. Instead it affects `Commit.where(sha: params.sha)` unconditionally**: [1](#0-0) 

Trace:
1. `WebhooksController#create` parses the raw JSON and dispatches to `Shipit::Webhooks.for_event('status')` → `[StatusHandler]`, after `verify_signature`, which only checks the HMAC against the webhook secret configured for `repository_owner` (the org named in the payload) — [2](#0-1) . This proves *who* sent the request but does not scope which `Commit`/`Stack` rows may be touched by the payload's `sha`.
2. `StatusHandler#process` does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` — [1](#0-0) . `Commit` has no repository-scoped uniqueness constraint on `sha` visible in the model (`belongs_to :stack`, no `validates :sha, uniqueness: { scope: :stack_id }` or similar) — [3](#0-2) .
3. `Commit#create_status_from_github!` → `add_status` creates a `Status`, recomputes `status`, and if the "simple state" transitions it fires `Hook.emit(:deployable_status, ...)` and `stack.schedule_merges` on `pending`/`success`, and separately `Commit#schedule_continuous_delivery` can trigger `ContinuousDeliveryJob` if `deployable? && stack.continuous_deployment? && stack.deployable?` — [4](#0-3) [5](#0-4) .

The attacker's exact request: a `status` event payload (`X-Github-Event: status`) with `sha` set to a value that is *also* present as a `Commit.sha` on a victim stack, `context: 'ci/kubernetes'` (or whatever `required_statuses` the victim stack expects), `state: 'success'`, and `repository.full_name`/`repository.owner.login` set to a repo the attacker controls (so the HMAC signature validates against that org's configured webhook secret). Because `StatusHandler` never checks `params.repository` against `commit.stack.repository`, the created `Status` row is attached to *every* commit across *every* stack sharing that SHA, not just commits belonging to the authenticated repository.

Existing guards do not stop this:
- `verify_signature` only proves the payload came from a legitimate sender for *some* org's webhook secret — it says nothing about which `sha`s that sender is allowed to reference — [6](#0-5) .
- `params` schema (`ExplicitParameters`) only validates types (`sha: String`, `state: String`, `context: String`), not ownership — [7](#0-6) .
- No model validation ties `Commit#sha` uniqueness to a stack/repository, and `StatusHandler` performs a bare `.where(sha:)` lookup with no `joins(:stack).where(stacks: { repository_id: ... })`.

Note on the "review_stacks_enabled precedence bug" referenced in the question: that is a separate, real defect in `PullRequest::OpenedHandler#provision?` / `ReopenedHandler#unarchive?`, where `repository.review_stacks_enabled` is only ANDed into the `allow_all` branch of the boolean expression (`a && b || c || d`), so the `allow_with_label`/`prevent_with_label` branches provision review stacks even when `review_stacks_enabled` is `false` — [8](#0-7) . This is a distinct code path (PR opened/reopened, not `status`) and I could not establish a concrete mechanism by which it causally combines with `StatusHandler` to "force a ship or block" on a `review_stacks_enabled: false` stack in a single reproducible flow — the two bugs affect different handlers and different preconditions. I can only confirm the `StatusHandler` cross-repository write independently.

### Impact Explanation
An attacker who owns any GitHub repository (or any repository whose org webhook secret they can trigger legitimate signed webhooks from) can create a commit whose SHA collides with, or is deliberately reused for, a commit tracked by an unrelated victim stack (SHAs are 40-hex chars, so natural collision is not feasible, but an attacker can arrange for a shared/forked/mirrored history commit to exist identically in both a repo they control and the victim's tracked repo — e.g., cherry-picking or force-pushing identical content across forks tracked as different Shipit stacks). If successful, a forged `status` webhook for `context: ci/kubernetes`/`state: success` can create a `Status` row on the victim's `Commit`, flipping `Commit#state`, potentially satisfying `deployable?` and triggering `ContinuousDeliveryJob` (unauthorized deploy) or affecting `blocked?`/merge queue processing (`stack.schedule_merges`) on a repository/stack the attacker never authenticated for. This matches "a payload for one repository mutating another's stack, commit ... or an unauthorized deploy" (Critical category), contingent on the victim stack having `continuous_deployment: true` and matching required contexts.

### Likelihood Explanation
Exploitability is gated primarily by SHA collision/reuse across independently-tracked stacks — this is a real but narrower precondition than the question implies (it requires identical commit content tracked by two different Shipit stacks, e.g. shared submodules, forks, or mirrored repos with identical commit hashes), not an unrestricted cross-repo write for arbitrary content. Given that precondition, the rest of the chain (`StatusHandler`'s lack of repository scoping) is unconditional and trivially repeatable once a shared SHA exists.

### Recommendation
Scope `StatusHandler#process` to only update commits belonging to the repository that authenticated the webhook, e.g. `Commit.joins(:stack).merge(Stack.where(repository: repository)).where(sha: params.sha)`, deriving `repository` from `params.repository.full_name` the same way other handlers do (see `PullRequest::OpenedHandler#repository`). Additionally fix the `provision?`/`unarchive?` boolean precedence so `review_stacks_enabled` gates all three provisioning-behavior branches, not just `allow_all`.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb (conceptual)
test "status for a SHA is scoped to the repository that authenticated the webhook" do
  victim_stack = shipit_stacks(:shipit) # repository X, review_stacks_enabled: false, required ci/kubernetes
  attacker_stack = create_stack_for_different_repository # repository Y

  shared_sha = "a" * 40
  victim_commit = victim_stack.commits.create!(sha: shared_sha, ...)
  attacker_commit = attacker_stack.commits.create!(sha: shared_sha, ...)

  payload = OpenStruct.new(sha: shared_sha, state: "success", context: "ci/kubernetes")

  # equality that should hold: only attacker_commit's stack is mutated
  assert_no_difference -> { victim_commit.reload.statuses.count } do
    Shipit::Webhooks::Handlers::StatusHandler.new(
      { "sha" => shared_sha, "state" => "success", "context" => "ci/kubernetes",
        "repository" => { "full_name" => attacker_stack.repository.full_name } }
    ).process
  end
  assert_difference -> { attacker_commit.reload.statuses.count }, 1 do
    # (rerun or assert prior run only touched attacker_commit)
  end
end
```
Currently, with the unscoped `Commit.where(sha: params.sha)` implementation, the first `assert_no_difference` would fail — `victim_commit.statuses.count` increases even though the webhook only authenticated for `attacker_stack`'s repository, proving the cross-tenant write. I was not able to construct a combined PoC that also exercises the `review_stacks_enabled` precedence bug as part of this same flow, since it lives in an entirely separate handler (`PullRequest::OpenedHandler`) with no code-level interaction with `StatusHandler`.

    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
