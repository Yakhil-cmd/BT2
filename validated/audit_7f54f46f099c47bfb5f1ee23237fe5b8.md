Based on my investigation, I found a directly analogous bug class in ocore's system-vote mechanism for TPS-fee-related parameters (`base_tps_fee`, `tps_interval`, `tps_fee_multiplier`), which mirrors the Sherlock finding almost exactly: an externally-influenceable numeric parameter that is missing an upper/lower bound check on part of the code's history, and whose value feeds directly into a fee/threshold formula (`exp(tps / tps_interval)`), where an extreme value causes the computed fee to blow up to `Infinity`/`NaN`, breaking the very validation function meant to gate acceptance of new units.

### Title
Unbounded historical range for `tps_interval`/`base_tps_fee`/`tps_fee_multiplier` system votes allows the TPS-fee formula to blow up before `pemCurvesFixMci`, breaking `validateTpsFee()` for all new units - ([File: validation.js])

### Summary
`validation.js`'s `validateInlinePayload` handler for `"system_vote"` only enforces bounds on `base_tps_fee`, `tps_interval`, and `tps_fee_multiplier` when `objValidationState.last_ball_mci >= constants.pemCurvesFixMci` (or the light-client equivalent condition). Below that upgrade point, the only check is `typeof payload.value === 'number' && isFinite(payload.value) && payload.value > 0` [1](#0-0) . This is structurally identical to the audited `setThresholds()` bug: a numeric governance parameter with no meaningful bound is later consumed in a formula (`MAX_BPS - slippageThresholdGmxBps` in the original vs. `exp(tps / tps_interval)` here) that can overflow/degenerate and make a core function unusable.

### Finding Description
`tps_interval`, `base_tps_fee`, and `tps_fee_multiplier` are consensus system variables that any address can propose via a `system_vote` unit message, and that get counted into effect via `system_vote_count` based on balance-weighted median voting [2](#0-1) . These raw votes are stored with only the "positive number" sanity check applied at the time the vote unit itself was validated (see above), and the additional guardrails (`tps_interval >= 0.1`, `base_tps_fee <= 1e8`, `tps_fee_multiplier` between 1 and 1000) were only introduced from `pemCurvesFixMci` onward [3](#0-2) .

Once accepted as the new system var, these values are consumed unguarded in the TPS-fee formulas that gate every ordinary (non-AA) unit's admission to the DAG:
- `getFinalTpsFee()`: `Math.round(base_tps_fee * (exp(tps / tps_interval) - 1))` [4](#0-3) 
- `getLocalTpsFee()`: `Math.round(tps_fee_multiplier * base_tps_fee * (exp(tps / tps_interval) - 1))` [5](#0-4) 
- `getCurrentTpsFee()` / `getCurrentTpsFeeToPay()` [6](#0-5) 

These are invoked from `validateTpsFee()`, which every unit (from every unprivileged unit poster) must pass to be accepted: `min_tps_fee = await storage.getLocalTpsFee(...)` and the subsequent comparison against `objUnit.tps_fee` [7](#0-6) . If `tps_interval` is voted arbitrarily close to `0` (allowed pre-fix, since the only constraint was `>0`), `exp(tps/tps_interval)` explodes to `Infinity` for any nonzero `tps`, making `min_tps_fee` become `Infinity`/`NaN`. Every ordinary unit thereafter fails the tps-fee check in `validateTpsFee()` (`tps_fees_balance + objUnit.tps_fee * share < min_tps_fee * share` becomes true for any finite `tps_fee`), so no unit can ever satisfy the fee requirement — exactly the "function reverts/becomes uncallable due to unbounded parameter" pattern in the original finding, but here the "function" is the network-wide unit-validation gate.

### Impact Explanation
If such a vote is accepted and counted before the current mainnet/testnet MCI reaches `pemCurvesFixMci`, `tps_interval`/`base_tps_fee`/`tps_fee_multiplier` could be pushed to a degenerate value by a coordinated balance-weighted vote, causing `validateTpsFee()` to reject essentially all new ordinary units network-wide — a "network unable to confirm new units" scenario, one of the explicitly accepted impact categories. This is a protocol-level DoS, not merely a client convenience issue.

### Likelihood Explanation
Exploitation requires accumulating enough voting balance (weighted, balance-based, `SYSTEM_VOTE_MIN_SHARE` participation threshold) to become the median for the vote, so it is not trivial for a single low-balance attacker, but it is fully permissionless — any address holding/controlling sufficient balance can submit the `system_vote` unit; no special (operator) privilege beyond normal wallet ability is required, which meets the "unprivileged unit poster" reachability bar. According to `constants.js`, `pemCurvesFixMci` is already in the past for both networks (`bTestnet ? 3975000 : 12185000`, both far below current chain heights), so the guarded path is currently active going forward; the vulnerable window exists only retroactively for MCIs prior to that constant, which limits current exploitability. I flag this uncertainty explicitly: whether this is *currently* exploitable on live chains depends on whether the code path evaluated is always gated by "current" mci (which it is, based on `last_ball_mci >= pemCurvesFixMci`), so on live networks today the bug is not reachable — it only illustrates the exact bug class from the report and was already patched via the `pemCurvesFixMci` upgrade.

### Recommendation
Since the fix has already been applied for `mci >= pemCurvesFixMci`, no further code change is strictly required for current chain operation. For completeness/defense-in-depth, consider applying the same bound checks unconditionally to `system_vote` regardless of `last_ball_mci`, so that no legacy/devnet/light-client code path can ever accept an out-of-range vote value, matching the recommended pattern of validating bounds at the point of input rather than relying on a hard fork cutoff.

### Proof of Concept
1. Before `pemCurvesFixMci`, submit a `system_vote` unit with `subject: "tps_interval"`, `value: 1e-9` (passes `isFinite && > 0`, the only check active at that mci).
2. Accumulate/organize balance-weighted votes to make this the counted median value at the next `system_vote_count`.
3. Once `storage.systemVars.tps_interval` becomes `1e-9`, any subsequent ordinary unit triggers `getLocalTpsFee`/`getFinalTpsFee` computing `exp(tps / 1e-9)` → `Infinity`, making `min_tps_fee` infinite in `validateTpsFee()`.
4. All newly submitted ordinary units are rejected by `validateTpsFee()`'s balance/fee comparison, halting confirmation of new units network-wide until an emergency governance fix restores a sane `tps_interval`.

async function getLocalTpsFee(conn, objUnitProps, count_units = 1) {
	const objLastBallUnitProps = await readUnitProps(conn, objUnitProps.last_ball_unit);
	const last_ball_mci = objLastBallUnitProps.main_chain_index;
	const base_tps_fee = getSystemVar('base_tps_fee', last_ball_mci); // unit's mci is not known yet
	const tps_interval = getSystemVar('tps_interval', last_ball_mci);
	const tps_fee_multiplier = getSystemVar('tps_fee_multiplier', last_ball_mci);
	const tps = await getLocalTps(conn, objUnitProps, count_units);
	console.log(`local tps at ${objUnitProps.unit} ${tps}`);
	const tps_fee_per_unit = Math.round(tps_fee_multiplier * base_tps_fee * (exp(tps / tps_interval) - 1));
	return count_units * tps_fee_per_unit;
}

function getCurrentTpsFee(shift = 0, count_units = 1) {
	const tps = getCurrentTps(shift, count_units);
	console.log(`current tps with shift ${shift} ${tps}`);
	const base_tps_fee = getSystemVar('base_tps_fee', last_stable_mci);

function getCurrentTpsFeeToPay(shift = 0, count_units = 1) {
	const tps_fee_multiplier = getSystemVar('tps_fee_multiplier', last_stable_mci);
