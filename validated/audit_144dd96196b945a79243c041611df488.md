### Title
Cross-repository commit-status forgery via unscoped `sha` lookup in `StatusHandler` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` looks up commits by `sha` alone, with no repository/stack scoping, even though the webhook's HMAC signature is verified only against the GitHub *organization* named in the payload's `repository.owner.login`. This breaks the binding "organization authenticated == repository that is written": a signature that only proves "this request came from org A" is treated as authorization to write a commit status onto *any* commit in the entire Shipit instance whose SHA happens to match, including commits belonging to different repositories/stacks (potentially in different orgs).

### Finding Description
`WebhooksController#verify_signature` selects the GitHub App/webhook secret to check the `X-Hub-Signature` against using only `repository_owner` (`repository.owner.login` or `organization.login`) from the untrusted payload: [1](#0-0) [2](#0-1) 

This only proves the request was signed with the secret configured for that organization — it says nothing about which specific repository, stack, or commit the payload is allowed to affect. That finer-grained binding is supposed to be enforced by each event handler, and most handlers do it correctly by scoping through `Repository.from_github_repo_name(repository_name)`: [3](#0-2) 
(e.g. `PushHandler` restricts to `stacks.not_archived.where(branch:)`, `CheckSuiteHandler` restricts to `stacks.where(branch: ...)`).

`StatusHandler`, however, never calls `stacks`/`repository_name` at all — it queries `Commit` globally by SHA and writes a status onto every matching row, in every stack, regardless of which repository/org actually owns that commit: [4](#0-3) 

So the equality that should hold — `organization that signed the webhook == repository whose commit is mutated` — is violated: the signature check binds to an org, but the write binds only to a SHA value taken verbatim from the same untrusted payload, with no cross-check against `repository_name`/`repository_owner` or the commit's `stack`.

### Impact Explanation
Commit statuses gate deploys through `Commit#deployable?` and `stack.required_statuses` / `blocking_statuses`: [5](#0-4) 
`create_status_from_github!`/`add_status` also triggers `commit_status`/`deployable_status` hooks and `stack.schedule_merges`, feeding directly into `ContinuousDeliveryJob` via `schedule_continuous_delivery`: [6](#0-5) [7](#0-6) 

An attacker who merely has "repo:status" write access to any GitHub repository belonging to an organization Shipit already trusts (i.e., not a Shipit user/session, not an `ApiClient` token — just ordinary GitHub commit-status permissions on some repo in that org) can send a real, validly-signed `status` webhook for their own repository but with a `sha` value chosen to collide with a commit that exists in a *different* stack/repository tracked by the same Shipit instance. Because `StatusHandler` never checks repository identity, Shipit will record a forged `success` status against that unrelated commit, which can:
- flip `Commit#deployable?` to true for a commit that never actually passed CI in its real repo, enabling an unauthorized deploy through `continuous_deployment`, or
- flip a previously green commit to `failure`/`error`, blocking legitimate deploys.

This satisfies the "unauthorized deploy" impact class defined in scope.

### Likelihood Explanation
Likelihood is moderate-to-low but concrete: it requires (a) the attacker to have commit-status write access to at least one repository in an organization already onboarded to this Shipit instance (a much lower bar than Shipit admin/session access), and (b) knowledge or brute-forcing of a target commit SHA in another stack (SHAs are 40-hex but are routinely public information — visible in PRs, commit lists, CI logs, etc., so they are not a secret in practice). No Shipit session, `ApiClient` token, or GitHub App private key is required — only the ordinary "status" write scope on a GitHub repo whose org webhook is already configured, which is exactly the unprivileged-attacker boundary this analog targets.

### Recommendation
In `StatusHandler#process`, scope the lookup through the handler's own `repository_name`/`stacks` helper (as `PushHandler` and `CheckSuiteHandler` already do) instead of matching on `sha` alone, e.g. restrict to `stacks.flat_map(&:commits).where(sha: params.sha)` or equivalently `Commit.where(sha: params.sha, stack_id: stacks.select(:id))`, so a commit status can only be applied to commits belonging to the repository named (and whose org signed) the webhook payload.

### Proof of Concept
1. Shipit is configured for orgs `org-a` and `org-b`, each with `webhook_secret` set per `config/secrets.*.yml`.
2. Attacker has "status" write access to `org-a/some-repo` (a repo they legitimately control or collaborate on) which has its GitHub webhook correctly pointed at this Shipit instance.
3. Attacker discovers/observes a commit SHA `deadbeef...` that belongs to a stack tracked for `org-b/other-repo` (SHAs are public in PRs/commit history).
4. Attacker uses the GitHub Statuses API (`POST /repos/org-a/some-repo/statuses/deadbeef...`) to create a `success` status with that SHA. GitHub delivers a `status` webhook to Shipit, correctly signed with `org-a`'s `webhook_secret`.
5. `WebhooksController#verify_signature` passes (signature matches `org-a`'s secret) — see `app/controllers/shipit/webhooks_controller.rb:24-30`.
6. `StatusHandler#process` runs `Commit.where(sha: params.sha)` with no repository filter — see `app/models/shipit/webhooks/handlers/status_handler.rb:20-24` — and finds/updates the commit belonging to `org-b/other-repo`'s stack, calling `create_status_from_github!` on it.
7. If that commit in `org-b`'s stack was otherwise the current deployable head and `continuous_deployment` is enabled, this forged `success` status can trigger `schedule_continuous_delivery` → `ContinuousDeliveryJob`, causing an unauthorized deploy of `org-b`'s stack, or conversely poison its status to block legitimate deploys.
