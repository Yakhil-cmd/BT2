### Title
Incomplete cache invalidation on AA-response revert leaves stale `is_free`/DAG cache state - ([File: aa_composer.js])

### Summary
CVE-2024-24266 is a use-after-free caused by `dasher_configure_pid` mutating/tearing down internal state (a pid/context) that other in-flight code still depends on, without fully resyncing dependent state. The reachable analog in `ocore` is in the AA-composer's revert path, where `revertResponsesInCaches()` tears down the in-memory unit cache (`storage.assocUnstableUnits`, `assocBestChildren`) for a chain of AA-response units but only recomputes the `is_free` flag for the parents of the **first** response unit, not for the parents of every unit removed from the cache.

### Finding Description
When a primary AA trigger cascades into secondary AA calls and one of them fails, `revert()` calls `revertResponsesInCaches(arrResponses)`: [1](#0-0) 

This function only reads `parent_units` from the **first** unit in `arrResponseUnits` and passes that single set to `storage.fixIsFreeAfterForgettingUnit()`, even though `storage.forgetUnit` is invoked for every unit in the chain: [2](#0-1) 

Each AA response unit in a cascading chain can have parents other than the immediately preceding response unit (see `pickParents`, which sometimes selects `[row.unit, objMcUnit.unit].sort()` — two distinct parents), and each subsequent response unit's parent chain diverges from the first unit's parents: [3](#0-2) 

Because `fixIsFreeAfterForgettingUnit` is only ever invoked with the first unit's `parent_units`, the parents of the second, third, etc. response units (once their own children are deleted from `assocUnstableUnits`) never get their in-memory `is_free` flag recomputed. This leaves the node's live, mutable DAG cache (`storage.assocUnstableUnits`, consumed directly by `main_chain.getFreeUnits()` and by `parent_composer.pickParentUnitsAndLastBall`) in an incorrect state relative to the real DB after a legitimately rolled-back AA-response chain — an in-memory-cache/DB desync analogous to referencing state that should have been "freed"/reset but wasn't. [4](#0-3) [5](#0-4) 

`getFreeUnits()` is the exact function used to decide the free/tip set feeding main-chain stability determination (`main_chain.js` `advanceMcStability`) and used by `network.js`'s catchup stability-advance logic. A stale/incorrect `is_free` set on cached unstable units can make this node compute a different set of free tips than a node that queries the DB directly, which is precisely the kind of node-state divergence class (main chain / stability disagreement) that the bug-class hint (silent corruption of internal object graph state from incomplete configuration/cleanup) maps to in oscript/AA-triggered code that any address can invoke by sending a payment to an AA that triggers cascading secondary calls and then deliberately fails (bounces) deep in the chain.

### Impact Explanation
If `assocUnstableUnits[parent].is_free` is left `0` when it should be `1` (or vice versa), this node's view of "free units" (candidate main-chain tips and parent-selection candidates) diverges from the DB-truth and from other honest nodes that recompute it correctly from SQL. This can:
- Cause this node to pick different/incorrect parents when composing its own units (potential consensus/parent-selection anomalies), and
- Cause `main_chain.advanceMcStability`/`determineIfStableInLaterUnits`, which iterate `getFreeUnits()`, to reach different main-chain-stability conclusions than the rest of the network — i.e., disagreement on unit stability, matching the "node disagreement on validity or stability" acceptance criterion.

Because AA triggers, cascades and bounces are entirely attacker-controllable (any unprivileged user can post a payment to a chain of AAs designed to bounce deep in a multi-hop secondary-trigger chain), this is reachable without any special privilege.

### Likelihood Explanation
Reaching the vulnerable path only requires: (1) deploying/using a chain of ≥2 AAs where a secondary trigger has at least one AA response unit with parents other than the immediate predecessor unit (a fairly common shape once an AA response also references the original MC unit as a parent, per `pickParents`), and (2) causing the chain to fail deep enough that `revert()` is invoked. Both are achievable by an ordinary AA-trigger/asset-issuer without elevated access, and the `revert` path is exercised routinely whenever a secondary AA bounces (a normal, frequently-tested code path, per `aa_composer.test.js`). However, whether the divergence actually manifests as an externally observable stability disagreement depends on the specific DAG shape at the time (whether that stale parent is later re-checked/re-derived through a DB round-trip before it matters) — I could not fully verify from the available code index whether other code paths independently re-verify/self-heal `is_free` before it is consumed by consensus-critical logic (e.g., via `readUnitProps`'s consistency check against DB, seen in `storage.js:1497-1554`) in every call path, so the practical exploitability (versus being caught/thrown by the extensive internal consistency assertions like `throwError("different props...")` scattered through `main_chain.js`) is uncertain and would need runtime verification.

### Recommendation
In `revertResponsesInCaches` (aa_composer.js:1900-1916), collect and pass the `parent_units` of **every** unit in `arrResponseUnits` (not just the first) to `storage.fixIsFreeAfterForgettingUnit`, e.g. compute the union of `storage.assocUnstableUnits[unit].parent_units` for each unit before calling `storage.forgetUnit`, mirroring the pattern used correctly in `storage.archiveJointAndDescendants` and `joint_storage.purgeUncoveredNonserialJoints`, which call `fixIsFreeAfterForgettingUnit` per-unit immediately after each `forgetUnit`.

### Proof of Concept
Conceptual reproduction (cannot be fully executed without a live node, but derivable from `test/aa_composer.test.js` patterns):
1. Deploy AA `A` (primary) whose response payment triggers secondary AA `B`.
2. Deploy AA `B`'s response such that its resulting response unit has two parents (the `A`-response unit and the MC unit, per `pickParents`'s `[row.unit, objMcUnit.unit].sort()` branch), and AA `B` further triggers AA `C` which is made to bounce (e.g., insufficient bounce fee or explicit `bounce()`).
3. Post a trigger unit to `A` causing the `A→B→C` cascade; `C` bounces, causing `revert()` in `aa_composer.js` to run and call `revertResponsesInCaches([A-response, B-response])`.
4. `objFirstUnit.parent_units` used for `fixIsFreeAfterForgettingUnit` is only `A-response`'s parents; `B-response`'s second parent (`objMcUnit.unit`) is forgotten as a child but never has its `is_free` recomputed after `B-response` is deleted from `assocUnstableUnits`.
5. Compare `storage.assocUnstableUnits[objMcUnit.unit].is_free` against a fresh `SELECT is_free FROM units WHERE unit=?` — expect a mismatch (0 in cache vs 1 in DB, or vice versa), which is exactly the kind of divergence the existing test-suite in-memory/DB consistency assertions (`throwError("different props...")` in `main_chain.js`) are designed to catch, indicating this is a genuine, previously-unguarded cache-consistency gap in the revert path specifically.

// parent_units are parent units of the forgotten unit
function fixIsFreeAfterForgettingUnit(parent_units) {
	parent_units.forEach(function(parent_unit){
		if (!assocUnstableUnits[parent_unit]) // the parent is already stable
			return;
		var bHasChildren = false;
		for (var unit in assocUnstableUnits){
			var o = assocUnstableUnits[unit];
			if (o.parent_units.indexOf(parent_unit) >= 0)
				bHasChildren = true;
		}
		if (!bHasChildren)
			assocUnstableUnits[parent_unit].is_free = 1;
	});
}
