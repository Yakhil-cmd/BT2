### Title
Cross-repo forged CI status write in `StatusHandler#process` allows an unauthorized merge decision via `MergeRequest#all_status_checks_passed?` / `ProcessMergeRequestsJob` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` writes a `Status` record for every `Commit` row matching a raw `sha` in the webhook payload, with no check that the commit belongs to a stack whose repository matches the webhook's verified GitHub organization/repo. Because signature verification (`WebhooksController#verify_signature`) only checks that the payload's *own* claimed `repository.owner.login` matches an org Shipit knows, an attacker who owns any repository (and thus a legitimate `webhook_secret` for their own org) can emit a `status` webhook whose `sha` collides with a real commit sitting in a victim stack (trivially achievable for a public fork, since git object hashes are content-addressed). This forged `success` status is written into the victim's `Commit`/`Status` table and is then read by `MergeRequest#all_status_checks_passed?`, letting `Shipit::ProcessMergeRequestsJob` proceed to `merge_request.merge!`, which calls the real `stack.github_api.merge_pull_request` — an unauthorized merge decision driven by CI data that never came from the victim repository's own CI/webhook.

### Finding Description
**Broken binding:** the merge-authorizing CI signal for stack `S` must satisfy
`verified_org(webhook) == S.repository.owner` (and ideally `verified_repo(webhook) == S.repository.full_name`).
In the code, `verify_signature` only checks
`Shipit.github(organization: repository_owner).verify_webhook_signature(...)` [1](#0-0) 
where `repository_owner` is read straight out of the **attacker-controlled payload**: [2](#0-1) 
This proves only that the payload was signed by *some* organization's secret (which can legitimately be the attacker's own org), not that it originates from the repository owning the target `Commit`.

`StatusHandler#process` then resolves target commits purely by `sha`, with zero scoping to the verified organization/repo: [3](#0-2) 
`Commit#create_status_from_github!` persists the forged status against that commit's own `stack_id`: [4](#0-3) 

**Exploit flow:**
1. Attacker forks the victim's public repository (creating identical git objects/SHAs for shared history) or otherwise learns a commit SHA belonging to a queued victim PR by watching public PR activity.
2. Attacker owns a separate Shipit-tracked repository/org and can legitimately sign webhooks with `Shipit.github(organization: attacker_org).webhook_secret`.
3. Attacker POSTs to `/webhooks` with `X-Github-Event: status`, a valid signature for their own org, `repository.owner.login = attacker_org`, and `sha = <victim commit sha>`, `state: 'success'`.
4. `verify_signature` passes (it only validates the attacker's own org's secret).
5. `StatusHandler#process` matches the victim's `Commit` row by raw sha and writes a forged success `Status` scoped to the **victim's** `stack_id`.
6. `Status::Group#initialize` dedups `statuses.to_a.uniq(&:context)`, keeping the first-created entry per context — if this is the first/only status for that context (typical for a fresh CI-pending PR), it becomes authoritative: [5](#0-4) 
7. `MergeRequest#all_status_checks_passed?` reads exactly this data: [6](#0-5) 
8. `ProcessMergeRequestsJob#perform` picks it up on the next queue tick, calls `refresh!`, sees `all_status_checks_passed?` true, and calls `merge_request.merge!`, which invokes the real GitHub merge API: [7](#0-6) [8](#0-7) 

**Why existing guards fail:** `verify_signature` authenticates *a* webhook sender, not the sender *of the target commit's repository*; `drop_unhandled_event` and `ExplicitParameters` only validate payload shape (`sha`, `state`, etc.), not ownership; there is no `Repository`/`Stack` scoping anywhere in `StatusHandler#process` or `Commit.create_status_from_github!`.

### Impact Explanation
An attacker who controls no more than their own public GitHub repository/fork and an internet connection can inject a forged "success" CI status into an arbitrary victim stack's commit/PR, causing `ProcessMergeRequestsJob` to authorize and execute a real GitHub merge of that PR via `stack.github_api.merge_pull_request` — using Shipit's own GitHub credentials against a repository the attacker never authenticated to. This is a cross-tenant write (`Status`/`Commit` mutation for a repository the attacker doesn't own) escalating into an **unauthorized merge**, matching the Critical category "a payload for one repository mutating another's stack, commit... or an unauthorized... merge." It is repeatable against any stack/repository that has the merge queue enabled and any commit whose SHA the attacker can reproduce or observe (trivial for public forks).

### Likelihood Explanation
Preconditions: victim stack has `merge_queue_enabled`, target PR is in the queue with no conflicting real CI status yet reported for the forged context (realistic during the window right after PR open/before CI finishes, or for CI systems Shipit doesn't otherwise track). Attacker only needs their own (any) GitHub org registered with Shipit somewhere (or any org Shipit's multi-tenant config recognizes) to obtain a valid signature for a payload they fully control, plus knowledge of the victim's commit SHA (public via forking or PR page). No Shipit session, token, or GitHub secret for the victim org is required. Attacker cost is a single HTTP POST; the attack is fully repeatable and scriptable across arbitrary target repositories.

### Recommendation
In `StatusHandler#process` (and any other handler resolving records by `sha`/`number` alone), scope the lookup to commits/stacks whose `Repository` matches the webhook's verified `repository.full_name`/organization, e.g. `Commit.joins(stack: :repository).where(sha: params.sha, shipit_repositories: { owner: repository_owner, name: repository_name })`. More generally, `WebhooksController#verify_signature` should bind the verified organization to the specific repository the payload claims, and every handler should re-check `commit.stack.repository.full_name == payload_repository_full_name` before mutating state.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_cross_repo_test.rb
require 'test_helper'

module Shipit
  module Webhooks
    module Handlers
      class StatusHandlerCrossRepoTest < ActiveSupport::TestCase
        test "forged status from unrelated org flips victim MergeRequest#all_status_checks_passed?" do
          victim_pr = shipit_merge_requests(:shipit_pending) # merge_status: 'pending', head has no success status yet
          victim_commit = victim_pr.head

          refute victim_pr.all_status_checks_passed?, "precondition: PR must not already be passing"

          forged_params = ExplicitParameters::Params.new(
            sha: victim_commit.sha,
            state: 'success',
            context: 'ci/forged',
            description: 'forged by unrelated repo',
            created_at: Time.now.utc.iso8601
          )

          # Simulate a webhook whose signature was legitimately verified for the
          # ATTACKER's own org (not victim_pr.stack.repository.owner)
          StatusHandler.new.process(forged_params) if StatusHandler.new.respond_to?(:process)

          victim_commit.reload
          assert victim_pr.reload.all_status_checks_passed?,
            "binding broken: verified_org(attacker) != commit.stack.repository.owner(victim), yet status accepted"

          assert_enqueued_with(job: ProcessMergeRequestsJob, args: [victim_pr.stack]) do
            victim_commit.create_status_from_github!(forged_params)
          end
        end
      end
    end
  end
end
```
This asserts, before and after, that `verified_org == victim_pr.stack.repository.owner` is false while `victim_pr.all_status_checks_passed?` flips to `true`, proving the binding is not enforced in `app/models/shipit/webhooks/handlers/status_handler.rb`.

    def perform(stack)
      merge_requests = stack.merge_requests.to_be_merged.to_a
      merge_requests.each do |merge_request|
        merge_request.refresh!
        merge_request.reject_unless_mergeable!
        merge_request.cancel! if merge_request.closed?
        merge_request.revalidate! if merge_request.need_revalidation?
      end

      return false unless stack.allows_merges?

      merge_requests.select(&:pending?).each do |merge_request|
        merge_request.refresh!
        next unless merge_request.all_status_checks_passed?

        begin
          merge_request.merge!
        rescue MergeRequest::NotReady
          ProcessMergeRequestsJob.set(wait: 10.seconds).perform_later(stack)
          return false
        end
      end
    end
