### Title
Cross-organization team-membership escalation via unscoped `Team.find_or_create_by!(github_id:)` lookup - (File: app/models/shipit/webhooks/handlers/membership_handler.rb)

### Summary
`MembershipHandler#find_or_create_team!` looks up an existing `Team` solely by the GitHub-assigned numeric `github_id`, without verifying that the team's stored `organization` matches the organization whose webhook secret was used to authenticate the request. An attacker who legitimately controls a GitHub organization (and therefore knows its own webhook secret) can forge a `membership` event that names the numeric `id` of a *different* organization's already-existing, `Shipit.github_teams`-authorized team, causing `team.add_member` to insert an arbitrary login into that authorized team.

### Finding Description
The binding the code implicitly needs to hold is:
`team.organization (record being mutated) == params.organization.login (organization whose secret validated the signature)`.

`WebhooksController#verify_signature` selects the `GitHubApp` (and therefore the HMAC secret to check) using `repository_owner`, which for a `membership` event falls back to `params.dig('organization', 'login')`: [1](#0-0) [2](#0-1) 

This only proves the payload was legitimately signed *by the organization named in `params['organization']['login']`* — nothing more. `MembershipHandler#process` then does: [3](#0-2) 

`Team.find_or_create_by!(github_id: params.team.id)` performs the lookup by `github_id` alone. The `organization:` assignment inside the block only executes when a **new** record is being built; if a `Team` row with that `github_id` already exists (e.g., the row created ahead of time via `Shipit.github_teams`/`Team.find_or_create_by_handle`, which is populated from the operator's `oauth.teams` config using the real GitHub API): [4](#0-3) [5](#0-4) 

...then the existing row (with its real `organization`, e.g. `"shopify"`) is returned unchanged, and `team.add_member(member)` mutates that team's membership regardless of which organization actually authenticated the request: [6](#0-5) 

Exploit flow: attacker administers `attacker-org`, which is a legitimately configured GitHub App/org in Shipit (so its `webhook_secret` is known to the attacker as the org owner). Attacker learns (via GitHub's team/API discovery, not a Shipit secret) the numeric `id` of a target `Team` already present in Shipit's DB and listed in `Shipit.github_teams` (e.g. `shopify/developers`). Attacker POSTs a `membership` webhook to `/webhooks` with:
```json
{"action":"added","organization":{"login":"attacker-org"},
 "team":{"id":<real id of shopify/developers>,"name":"x","slug":"x","url":"x"},
 "member":{"login":"victim"}}
```
signed with `attacker-org`'s own secret. `verify_signature` passes (correctly, for `attacker-org`). `find_or_create_team!` finds the pre-existing `shopify/developers` `Team` row by `github_id` and `team.add_member(User.find_or_create_by_login!('victim'))` adds `victim` to it — a team belonging to `shopify`, authorized despite the request only being authenticated as `attacker-org`.

None of the listed guards catch this: `verify_signature` only checks the HMAC against the organization named in the payload (which is honestly `attacker-org`), not against the organization that owns the target `Team` row being mutated; `ExplicitParameters` only enforces types/presence, not cross-field consistency between `params.organization.login` and the team ultimately resolved; `User#authorized?` trusts `teams.where(id: Shipit.github_teams.map(&:id)).exists?` and has no way to know the membership was inserted by a different org's signature.

### Impact Explanation
An attacker can add an arbitrary GitHub login as a member of any `Team` row already present in Shipit's database that has a known/guessable GitHub numeric team `id` — including teams enumerated in `Shipit.github_teams`. Since `User#authorized?` grants full application access purely based on team membership rows, this results in unauthorized escalation into `Shipit.github_teams` authorization for an attacker-chosen login, matching the High severity category ("escalation into `Shipit.github_teams` authorization"). It is repeatable against any pre-existing `Team` row regardless of which organization actually owns it, as long as the attacker's own organization is a configured Shipit tenant.

### Likelihood Explanation
Preconditions: (1) the attacker's own GitHub organization must already be a configured tenant in Shipit (i.e., have a registered `GitHubApp`/webhook secret known to Shipit), so its webhooks are accepted at all; (2) the attacker must know or discover the numeric GitHub `id` of the target team (not a Shipit secret — obtainable through GitHub's own APIs/UI depending on team visibility, or via ID enumeration since GitHub team IDs are sequential integers); (3) the target `Team` row must already exist in Shipit's DB (true for any team ever referenced by `Shipit.github_teams` config, or by any prior legitimate membership webhook). No Shipit secret, session, or API token is required — only knowledge/control of the attacker's own already-connected org. This is feasible for any multi-tenant Shipit deployment serving more than one GitHub organization.

### Recommendation
In `MembershipHandler#find_or_create_team!`, scope the lookup/creation by both `github_id` **and** `organization`, and explicitly reject (or drop) the event if a `Team` is found with the given `github_id` but a mismatched `organization` compared to `params.organization.login`. E.g.:
```ruby
team = Team.find_by(github_id: params.team.id)
raise SecurityError, "organization mismatch" if team && team.organization != params.organization.login.downcase
team ||= Team.create!(github_id: params.team.id, organization: params.organization.login, ...)
```

### Proof of Concept
```ruby
test ":membership webhook cannot add members to a team owned by a different organization" do
  target_team = shipit_teams(:shopify_developers) # organization: 'shopify', github_id: <real id>
  @request.headers['X-Github-Event'] = 'membership'

  # signature stubbed true for attacker's own org, as in existing setup
  GithubHook.any_instance.stubs(:verify_signature).returns(true)

  payload = {
    action: 'added',
    organization: { login: 'attacker-org' },
    team: { id: target_team.github_id, name: target_team.name, slug: target_team.slug, url: target_team.api_url },
    member: { login: 'victim' }
  }.to_json

  assert_difference -> { target_team.reload.members.count }, 1 do
    post :create, body: payload, as: :json
    assert_response :ok
  end

  assert_equal 'shopify', target_team.reload.organization # team ownership unchanged
  assert target_team.members.exists?(login: 'victim')     # but victim was still added
end
```
This demonstrates the equality `team.organization ('shopify') == params.organization.login ('attacker-org')` is false both before and after the request, yet the membership write still succeeds.

          team = find_or_create_team!
          member = User.find_or_create_by_login!(params.member.login)

          case params.action
          when 'added'
            team.add_member(member)
          when 'removed'

          end
        end
