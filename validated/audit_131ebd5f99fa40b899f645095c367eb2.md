### Title
i128 overflow in accrued-debt computation permanently freezes a market before `MAX_BORROW_INDEX_RAY` cap engages — (File: common/src/rates/index.rs)

### Summary
CVE-2023-4072 is an out-of-bounds read/write triggered by attacker-crafted input; the closest analog in XOXNO Lending is an out-of-range `i128` fixed-point computation. Every mutating entrypoint on the pool calls `synced_market` → `interest::global_sync` → `accrue_step`, which internally computes `borrowed.mul(new_borrow_index)` inside `calculate_supplier_rewards` (`common/src/rates/index.rs:80-81`). `Ray::mul` panics on overflow (`common/src/math/fp.rs`, `mul_div_half_up`), so once `scaled_borrowed × borrow_index > i128::MAX`, accrual panics. Because every verb accrues first (`contracts/pool/src/ops/mod.rs:30-34`), all exits — `withdraw`, `repay`, `liquidate`, `borrow`, `update_indexes` — revert permanently. The borrow-index cap in `update_borrow_index` (`common/src/rates/index.rs:13-18`) never engages because the panic occurs in the *value* computation, which overflows while the index is still far below `MAX_BORROW_INDEX_RAY` — this is proven by the harness test `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` (`tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:316-361`), which asserts `last.borrow_index < MAX_BORROW_INDEX_RAY` and that `try_withdraw_raw`, `try_repay`, and `try_update_indexes_for` all fail with `MATH_OVERFLOW`, with the comment "the bound in docs/reference/formulas.md is wrong".

### Finding Description
`update_borrow_index` caps the index itself, but nothing caps `scaled_borrowed`. `scaled_borrowed` is `amount × 10^(27−decimals) / index` at mint time — roughly the RAY value of principal. For an 18-decimal asset, a 10^27-base-unit debt produces ~10^36 ray scaled shares; multiplying by a borrow index of ~170× overflows `i128::MAX ≈ 1.7×10^38`. On steep rate curves at sustained high utilization that index is reachable in a few years (per the test's own comment); smaller debts need proportionally larger indexes but the same cliff exists for every market size. Once crossed, the panic is unrecoverable: `global_sync` runs before any state mutation, so no path can shrink `borrowed` or reset the index.

### Impact Explanation
Permanent freezing of all user funds in the affected (hub, token) book: suppliers cannot withdraw, borrowers cannot repay, liquidators cannot liquidate, and governance-driven `recapitalize`/`clean_bad_debt` also accrue first and revert. The market is bricked.

### Likelihood Explanation
An unprivileged user can reach the state via `controller` `supply`/`borrow` (or a single whale supplier plus a highly-collateralized borrower at ~98% utilization). It requires very large liquidity or a long high-utilization period, so it is a tail-risk rather than a cheap one-transaction attack — but once the state is reached the freeze is irreversible and no admin action can recover it. Medium likelihood.

### Recommendation
Make the accrual arithmetic saturate instead of panicking: in `calculate_supplier_rewards`, compute `borrowed.mul(index)` via a saturating `mul_div` (as `update_supply_index` already does with `mul_div_floor_saturating` at `index.rs:41`), and/or clamp scaled `borrowed` growth at mint time so `scaled × MAX_BORROW_INDEX_RAY` stays in range. Additionally enforce a supply/borrow cap in RAY terms derived from `i128::MAX / MAX_BORROW_INDEX_RAY` so the cliff is unreachable by construction.
