### Title
Membership webhooks accepted unconditionally for orgs configured without `webhook_secret`, allowing forged team-membership writes into `Shipit.github_teams` authorization teams - ([File: lib/shipit/github_app.rb])

### Summary
`GitHubApp#verify_webhook_signature` returns `true` unconditionally when the org's config has no `webhook_secret` [1](#0-0) , so `WebhooksController#verify_signature` accepts *any* payload for that org regardless of headers [2](#0-1) . `MembershipHandler` then trusts attacker-supplied `params.team.id` to locate/create a `Team` and unconditionally adds/removes the attacker-chosen `member.login` from it [3](#0-2) . Because `Team.find_or_create_by_handle` (used to build `Shipit.github_teams`) records the real GitHub team id fetched from the API [4](#0-3) , a forged `membership` event whose `team.id` matches that real id lets an attacker add themselves as a member of an authorization-granting team, which `User#authorized?` reads directly [5](#0-4) .

### Finding Description
The broken binding: "a `membership` webhook is trusted only if it is HMAC-signed with the org's `webhook_secret`" is violated whenever that org has no `webhook_secret` configured. `verify_webhook_signature(signature, message)` is:

```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  algorithm, signature = signature.split("=", 2)
  return false unless algorithm == 'sha1'
  SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
end
``` [6](#0-5) 

Note that when `webhook_secret` is blank, the method returns `true` *before* the `signature.split('=', 2)` line is ever reached — so the "malformed signature split" behavior described in the question is not actually the mechanism of the bypass in this scenario; the bypass is the unconditional `return true unless webhook_secret` short-circuit itself, independent of what `X-Hub-Signature` contains (even a header with no `=`, or no header at all, is accepted).

`WebhooksController#verify_signature` picks the `GitHubApp` instance for the org derived from the payload itself (`repository_owner`, falling back to `params.dig('organization', 'login')`, which for `membership` events is exactly `organization.login`) [2](#0-1) [7](#0-6) . If that org's config has no `webhook_secret` (a state explicitly documented as "optional" in `docs/setup.md`), verification passes for any forged request naming that org.

`MembershipHandler#process` then does:
```ruby
team = find_or_create_team!          # Team.find_or_create_by!(github_id: params.team.id)
member = User.find_or_create_by_login!(params.member.login)
team.add_member(member) # action == 'added'
``` [3](#0-2) 

`params.team.id` is fully attacker-controlled JSON in the request body; there is no check that it corresponds to a team the attacker actually belongs to, nor any tie-back to a specific repository/stack. If an operator has set up `Shipit.github_teams` (`github.oauth.teams`) to gate access, those `Team` rows carry the real GitHub `github_id` fetched from the API [4](#0-3) [8](#0-7) . An attacker who knows (or discovers, e.g. via GitHub's public team API for a public org, or brute force of small integer ids) that `github_id` can forge:

```
POST /webhooks
X-Github-Event: membership
X-Hub-Signature: <anything, even malformed>
{
  "action": "added",
  "team": { "id": <real authorized team's github_id>, "name": "...", "slug": "...", "url": "..." },
  "organization": { "login": "<org with no webhook_secret>" },
  "member": { "login": "<attacker's github login>" }
}
```

This causes `Team.find_or_create_by!(github_id: ...)` to find the *existing, authorization-granting* `Team` row and add the attacker as a member. Once added, `User#authorized?` — `Shipit.github_teams.empty? || teams.where(id: Shipit.github_teams.map(&:id)).exists?` — evaluates true for the attacker's `User` record [5](#0-4) , which `force_github_authentication` uses to gate the entire application [9](#0-8) .

None of the documented guards stop this: `verify_signature` is the only signature check and it is bypassed by design for no-secret orgs; `drop_unhandled_event` does not apply since `membership` is a handled event; `ExplicitParameters` only validates shape/types of `params.team.id`, `params.member.login`, etc., not their trustworthiness; there is no cross-check that the forged `team.id`/`organization.login` correspond to a repository/stack that authenticated the request.

### Impact Explanation
An attacker who can send an unauthenticated HTTP POST to `/webhooks` can, for any org configured without `webhook_secret`, forge a `membership` `added` event that adds an arbitrary GitHub login (their own account) into any `Team` row identified by a guessed/known `github_id` — including a `Team` referenced in `Shipit.github_teams`, which is the exact set used for global authorization to the Shipit UI/API (`User#authorized?`, `force_github_authentication`). This is an authentication/authorization bypass matching the "escalation into `Shipit.github_teams` authorization" / forged-webhook-accepted-as-trusted category. It is repeatable (idempotent `find_or_create_by!` + `add_member`) and not scoped to a single repository or stack — it globally affects Shipit's access control for the whole installation, since `Shipit.github_teams`/`User#authorized?` are host-wide, not per-repository.

### Likelihood Explanation
Preconditions: (1) at least one org in the multi-org `github` config has no `webhook_secret` set — a state explicitly presented as optional/acceptable in `docs/setup.md` and the example secrets files (`webhook_secret: # nil`); (2) `Shipit.github_teams` (i.e., `github.oauth.teams`) is configured for access restriction, and the attacker can learn or guess the numeric `github_id` of one of those teams (discoverable via GitHub's team API for teams the attacker can view, or via public org data). No Shipit session, API token, or GitHub App secret is required — only crafting a raw HTTP POST to `/webhooks` with an arbitrary/malformed `X-Hub-Signature`. This is low-cost and fully repeatable.

### Recommendation
Do not let "no `webhook_secret` configured" silently mean "trust everything." At minimum: require `webhook_secret` for any org whose `Team`s participate in `Shipit.github_teams` authorization, or reject/require operator opt-in for unsigned webhooks; alternatively, make `MembershipHandler` never mutate `Team`s that are part of `Shipit.github_teams` via unsigned/no-secret-verified webhooks, and validate `team.id`/`organization.login` against the actual GitHub API before trusting membership changes rather than trusting the payload verbatim.

### Proof of Concept
Minitest plan (no live GitHub, using existing fixtures):
1. Configure a fake `GitHubApp` for organization `"nosecret-org"` with `webhook_secret` absent (nil), reusing `Shipit.github(organization:)` stubbing patterns used elsewhere in tests.
2. Seed a `Team` fixture representing an authorization team with a known `github_id` (e.g., `shipit_teams(:shopify_developers)` with `github_id: 999`), and stub `Shipit.github_teams` to return `[shipit_teams(:shopify_developers)]`.
3. Assert the binding before the request: `refute shipit_users(:new_attacker).authorized?` (attacker not a member) and `refute shipit_teams(:shopify_developers).members.include?(shipit_users(:new_attacker))`.
4. POST to `/webhooks` with header `X-Github-Event: membership`, `X-Hub-Signature: 'malformedwithoutequals'`, and JSON body:
   `{"action":"added","team":{"id":999,"name":"Developers","slug":"developers","url":"https://api.github.com/teams/999"},"organization":{"login":"nosecret-org"},"member":{"login":"new_attacker"}}`.
5. Assert response is `200`, not `422`.
6. Assert the binding after: `Shipit::User.find_by(login: 'new_attacker').authorized?` is now `true`, and `shipit_teams(:shopify_developers).members.reload.map(&:login)` includes `'new_attacker'` — proving a forged, unsigned webhook mutated authorization-granting team membership for an org with no configured secret.

    class << self
      def find_or_create_by_handle(handle)
        organization, slug = handle.split('/').map(&:downcase)
        find_by(organization:, slug:) || fetch_and_create_from_github(organization, slug)
      end

      def fetch_and_create_from_github(organization, slug)
        return unless github_team = find_team_on_github(organization, slug)

        create!(github_team:, organization:)
      end

      def find_team_on_github(organization, slug)
        gh_api = Shipit.github(organization:).api
        teams = Shipit::OctokitIterator.new(github_api: gh_api) { gh_api.org_teams(organization, per_page: 100) }
        teams.find { |t| t.slug == slug }
      rescue Octokit::NotFound
      end
