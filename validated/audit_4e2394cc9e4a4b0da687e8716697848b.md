### Title
Staking Reward Allocation Silently Drops CN Portion When `RewardAddr == CLPoolAddr` Due to Map Overwrite — (`File: kaiax/reward/impl/getter.go`)

### Summary

In `assignStakingRewards` and `assignStakingRewardsFlex`, the Prague-hardfork CL-split path uses direct map assignment (`alloc[addr] = value`) for both the CN reward address and the CL pool address. If those two addresses are equal — or if one CN's `CLPoolAddr` equals another CN's `RewardAddr` — the second write silently overwrites the first, permanently destroying the earlier allocation. The `remaining` counter is still decremented by the full `reward`, so the lost `cnAmount` is never recovered by the proposer or any other recipient: it simply vanishes from the per-block KAIA distribution.

### Finding Description

Both functions contain the identical pattern (Prague path):

```go
// assignStakingRewards  (lines 521-525)
// assignStakingRewardsFlex (lines 474-477)
if isPrague && cn.CLStakingInfo != nil {
    cnAmount, clAmount := cn.Split(reward)
    alloc[cn.RewardAddr] = cnAmount                    // direct assignment
    alloc[cn.CLStakingInfo.CLPoolAddr] = clAmount      // direct assignment — overwrites if equal
}
remaining.Sub(remaining, reward)                       // always decremented by full reward
``` [1](#0-0) 

The `Split` helper correctly divides `reward` into `cnAmount + clAmount = reward`. [2](#0-1) 

However, the two results are written back with `=` (overwrite), not `+=` (accumulate). The contrast with the correct pattern used in `specWithProposerAndFunds` / `specWithProposerAndFundsFlex` is instructive — those functions call `newSpec.IncRecipient(addr, amount)`, which accumulates into the map:

```go
// specWithProposerAndFunds (correct — uses IncRecipient)
newSpec.IncRecipient(cn.RewardAddr, cnAmount)
newSpec.IncRecipient(cn.CLStakingInfo.CLPoolAddr, clAmount)
``` [3](#0-2) 

`IncRecipient` is defined as:

```go
func (spec *RewardSpec) IncRecipient(addr common.Address, amount *big.Int) {
    _, ok := spec.Rewards[addr]
    if !ok { spec.Rewards[addr] = big.NewInt(0) }
    spec.Rewards[addr].Add(spec.Rewards[addr], amount)
}
``` [4](#0-3) 

The `alloc` map returned by `assignStakingRewards` / `assignStakingRewardsFlex` is then iterated and applied to the `RewardSpec` via `spec.IncRecipient`:

```go
for addr, amount := range stakersAlloc {
    spec.IncRecipient(addr, amount)
}
``` [5](#0-4) 

But the damage is already done inside `assignStakingRewards`: the `alloc` map entry for the colliding address holds only `clAmount`, not `cnAmount + clAmount`. The `cnAmount` is never placed anywhere.

The `remaining` is decremented by the full `reward` regardless:

```go
remaining.Sub(remaining, reward)
``` [6](#0-5) 

So `kip82Remainder` (which flows to the proposer) is also unaffected — the `cnAmount` is simply gone.

**Two triggerable collision scenarios:**

**Scenario A — same-CN collision** (`cn.RewardAddr == cn.CLStakingInfo.CLPoolAddr`):
A validator registers the same address as both their AddressBook reward address and their CLRegistry pool address. Step 1 sets `alloc[addr] = cnAmount`; step 2 immediately overwrites it with `alloc[addr] = clAmount`. The validator loses `cnAmount` every block.

**Scenario B — cross-CN collision** (`CN_i.CLPoolAddr == CN_j.RewardAddr`):
If CN_i is processed before CN_j, step 2 of CN_i sets `alloc[R_j] = clAmount_i`. Then step 1 of CN_j sets `alloc[R_j] = cnAmount_j`, overwriting `clAmount_i`. CN_i's CL pool loses `clAmount_i` per block. If CN_j is processed first, CN_j's CN reward is overwritten by CN_i's CL allocation.

The `consolidateNodes()` function guarantees unique `RewardAddr` per consolidated node, but places no constraint on `CLPoolAddr` values relative to other nodes' `RewardAddr` values:

```go
if r, ok := nToR[clsi.CLNodeId]; ok {
    cmap[r].CLStakingInfo = clsi   // CLPoolAddr taken verbatim from CLRegistry
}
``` [7](#0-6) 

### Impact Explanation

Per block, `cnAmount` (proportional to the CN's staking weight) of KAIA staking reward is permanently destroyed — not redirected to the proposer, not burned to a known address, simply absent from `state.AddBalance` calls in `FinalizeState`:

```go
for addr, amount := range spec.Rewards {
    state.AddBalance(addr, amount)
}
``` [8](#0-7) 

For a large validator the per-block loss is material. In the cross-CN scenario, a third party can cause another validator's CL pool to receive zero staking rewards indefinitely.

### Likelihood Explanation

Scenario A requires a validator to misconfigure their own addresses (self-harm, low likelihood). Scenario B requires `CN_i.CLPoolAddr == CN_j.RewardAddr`; since the CLRegistry accepts arbitrary pool addresses and the AddressBook reward addresses are public, a malicious or careless actor could register a CL pool at an existing validator's reward address. No privileged access is required beyond normal validator registration. The Prague hardfork (which activates `CLStakingInfos`) is the activation gate.

### Recommendation

Replace the two direct-assignment blocks in `assignStakingRewards` and `assignStakingRewardsFlex` with accumulating writes, mirroring the pattern already used in `specWithProposerAndFunds`:

```go
// Before (buggy):
alloc[cn.RewardAddr] = cnAmount
alloc[cn.CLStakingInfo.CLPoolAddr] = clAmount

// After (correct):
if _, ok := alloc[cn.RewardAddr]; !ok {
    alloc[cn.RewardAddr] = new(big.Int)
}
alloc[cn.RewardAddr].Add(alloc[cn.RewardAddr], cnAmount)

if _, ok := alloc[cn.CLStakingInfo.CLPoolAddr]; !ok {
    alloc[cn.CLStakingInfo.CLPoolAddr] = new(big.Int)
}
alloc[cn.CLStakingInfo.CLPoolAddr].Add(alloc[cn.CLStakingInfo.CLPoolAddr], clAmount)
```

Alternatively, extract a small `incAlloc(alloc map, addr, amount)` helper (analogous to `IncRecipient`) and use it consistently. Additionally, add a validation step in `consolidateNodes` or `parseCallResult` / `parsePermissionlessCallResult` that rejects or warns when any `CLPoolAddr` collides with any `RewardAddr` in the same `StakingInfo`.

### Proof of Concept

Given a `StakingInfo` with two validators after the Prague hardfork:

```
NodeIds          = [N1, N2]
RewardAddrs      = [R1, R2]
StakingAmounts   = [10_000_000, 8_000_000]   (both above minStake)
CLStakingInfos   = [{CLNodeId: N1, CLPoolAddr: R2, CLStakingAmount: 2_000_000}]
```

`ConsolidatedNodes()` produces:
- CN1: `RewardAddr=R1`, `StakingAmount=10M`, `CLStakingInfo={CLPoolAddr=R2, CLStakingAmount=2M}`
- CN2: `RewardAddr=R2`, `StakingAmount=8M`, `CLStakingInfo=nil`

In `assignStakingRewards` (Prague path), processing CN1 first:
1. `cn.Split(reward1)` → `cnAmount1 = reward1 * 10/(10+2)`, `clAmount1 = reward1 * 2/12`
2. `alloc[R1] = cnAmount1` ✓
3. `alloc[R2] = clAmount1` ← sets R2's entry

Processing CN2:
4. `alloc[R2] = cnAmount2` ← **overwrites** `clAmount1`; `clAmount1` is permanently lost

Final `alloc`: `{R1: cnAmount1, R2: cnAmount2}`. Address R2 receives only `cnAmount2` instead of `clAmount1 + cnAmount2`. The `clAmount1` portion of staking reward is never credited to any balance. [9](#0-8) [10](#0-9)

```go
func (c consolidatedNode) Split(amount *big.Int) (*big.Int, *big.Int) {
	if c.CLStakingInfo == nil {
		return amount, big.NewInt(0)
	}

	var (
		cnAmountBig = big.NewInt(int64(c.StakingAmount))
		clAmountBig = big.NewInt(int64(c.CLStakingInfo.CLStakingAmount))
		totalAmount = new(big.Int).Add(cnAmountBig, clAmountBig)
	)

	clAmount := new(big.Int).Mul(clAmountBig, amount)
	clAmount = clAmount.Div(clAmount, totalAmount)

	// The remaining amount is for the CN.
	cnAmount := big.NewInt(0).Sub(amount, clAmount)

	return cnAmount, clAmount
}
```
