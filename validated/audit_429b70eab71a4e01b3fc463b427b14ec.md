### Title
Blacklisted ERC-20 Recipient Permanently Freezes Bridge Handle-Nonce and Causes Irreversible Loss of Bridged Assets — (`contracts/service_chain/bridge/BridgeTransferERC20.sol`)

---

### Summary

`handleERC20Transfer` in the Kaia service-chain bridge performs all nonce-accounting state writes **before** the actual token push to `_to`. Because Solidity reverts the entire transaction on failure, a single blacklisted recipient address causes every operator attempt to revert, leaving `lowerHandleNonce` permanently stuck and the user's source-chain tokens irreversibly lost with no on-chain recovery path.

---

### Finding Description

`handleERC20Transfer` executes in this order:

```
_lowerHandleNonceCheck(_requestedNonce)          // 1. gate
_voteValueTransfer(_requestedNonce)              // 2. vote
_setHandledRequestTxHash(_requestTxHash)         // 3. mark tx hash
handleNoncesToBlockNums[N] = _requestedBlockNum  // 4. record block
_updateHandleNonce(N)                            // 5. advance lowerHandleNonce
emit HandleValueTransfer(...)                    // 6. event
IERC20(_tokenAddress).safeTransfer(_to, _value) // 7. push tokens  ← revert point
``` [1](#0-0) 

If step 7 reverts — which happens when `_to` is blacklisted by the token contract (USDC, USDT, etc.) — the EVM unwinds **all** of steps 3–6. Specifically:

- `handleNoncesToBlockNums[N]` is **not** written.
- `_updateHandleNonce` is **not** executed, so `lowerHandleNonce` stays at `N`.
- `recoveryBlockNumber` is **not** advanced. [2](#0-1) 

`_updateHandleNonce` advances `lowerHandleNonce` only while `handleNoncesToBlockNums[i] > 0` for consecutive `i` starting from `lowerHandleNonce`. Because nonce `N` is never written, the loop halts at `N` on every future call, permanently freezing `lowerHandleNonce = N` and `recoveryBlockNumber`. [3](#0-2) 

On the source chain, the user's tokens were already transferred to the bridge (or burned in `modeMintBurn`) inside `_requestERC20Transfer` before the `RequestValueTransfer` event was emitted. There is no refund path. [4](#0-3) 

There is no owner-callable function to skip a nonce, redirect `_to`, or otherwise unblock the stuck nonce. The bridge contract exposes only `setRunningStatus`, `setFeeReceiver`, and operator/token management — none of which can advance `lowerHandleNonce` past a permanently failing nonce. [5](#0-4) 

---

### Impact Explanation

| Asset / State | Corrupted Value |
|---|---|
| Bridged ERC-20 tokens | Permanently locked/burned on source chain; never minted/transferred on destination chain |
| `lowerHandleNonce` | Frozen at `N`; never advances past the stuck nonce |
| `recoveryBlockNumber` | Frozen at the last successfully handled block; bridge recovery replays from stale point indefinitely |
| `closedValueTransferVotes[N+k]` | Accumulates without cleanup (storage leak) |

The user suffers a **complete, unrecoverable loss** of their bridged assets. The bridge's `recoveryBlockNumber` being frozen means the off-chain bridge relay (`node/sc/bridge_manager.go`) will perpetually re-scan from an old block, potentially causing duplicate vote submissions for already-handled nonces. [6](#0-5) 

---

### Likelihood Explanation

- Any ERC-20 token with a blacklist (USDC, USDT, BUSD, etc.) registered on the bridge is sufficient.
- The attacker surface is **unprivileged**: any user can call `requestERC20Transfer` specifying any `_to` address.
- The blacklisting event can occur at any time between the source-chain request and the destination-chain handle — a window that can span multiple blocks.
- The token issuer (a third party) blacklisting an address is a realistic, documented real-world event.
- No majority-validator collusion or compromised keys are required.

---

### Recommendation

Move the token transfer **before** the nonce-accounting state writes, or — preferably — adopt a pull-based pattern:

1. **Pull pattern (preferred)**: Instead of pushing tokens to `_to` inside `handleERC20Transfer`, record the claimable amount in a mapping (`pendingWithdrawals[_to] += _value`) and let `_to` call a separate `withdraw()` function. This decouples nonce advancement from token delivery.

2. **Try/catch (Solidity ≥ 0.6)**: Wrap the `safeTransfer`/`mint` call in a `try/catch`. On failure, record the amount in a `pendingWithdrawals` mapping so the user can claim later, while still advancing `lowerHandleNonce`.

3. **Nonce-skip escape hatch**: Add an owner-only function that can mark a nonce as handled (writing `handleNoncesToBlockNums[N]` and calling `_updateHandleNonce`) without performing the token transfer, allowing manual recovery.

---

### Proof of Concept

1. Alice calls `requestERC20Transfer(usdcAddr, aliceDest, 1000e6, feeLimit, "")` on the source bridge. USDC is transferred to the bridge; `RequestValueTransfer(ERC20, alice, aliceDest, usdc, 1000e6, nonce=5, ...)` is emitted. `requestNonce` becomes 6.

2. USDC issuer blacklists `aliceDest`.

3. Bridge operators call `handleERC20Transfer(txHash, alice, aliceDest, usdcAddr, 1000e6, 5, blockNum, "")` on the destination bridge. Voting passes. Steps 3–6 execute. Step 7 (`IERC20(usdcAddr).safeTransfer(aliceDest, 1000e6)`) reverts because `aliceDest` is blacklisted. The entire transaction reverts.

4. `handleNoncesToBlockNums[5]` remains 0. `lowerHandleNonce` stays at 5. `recoveryBlockNumber` is unchanged.

5. Every subsequent operator retry for nonce 5 reverts identically. Nonces 6, 7, … can be handled out of order and stored in `handleNoncesToBlockNums`, but `lowerHandleNonce` never advances past 5 because `handleNoncesToBlockNums[5] == 0` breaks the loop in `_updateHandleNonce`. [3](#0-2) 

6. Alice's 1000 USDC on the source chain is permanently lost. `recoveryBlockNumber` is frozen. The bridge relay keeps re-scanning from the stale block.
