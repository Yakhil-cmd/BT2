Based on my investigation, I found a concrete analog that maps directly onto the reported bug class: a field consumed to select the verification key is read from the *unverified* payload before that payload's signature is checked, breaking the binding between "the organization that authenticated" and "the repository that gets written."

### Title
Webhook signature verified against a secret selected from the unverified payload, decoupling authenticated organization from written repository - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to use for HMAC verification by reading `repository.owner.login` (or `organization.login`) directly out of the untrusted, unparsed request body — before the signature over that same body has been validated.

### Finding Description
The controller's `verify_signature` before_action does: [1](#0-0) 
picking `github_app` via `Shipit.github(organization: repository_owner)`, where `repository_owner` is computed from the JSON body: [2](#0-1) 

This means the *choice of secret* used to verify `X-Hub-Signature` is itself derived from attacker-controlled, not-yet-verified data. Shipit supports multiple GitHub Apps/organizations, each with its own `webhook_secret`, configured under `secrets.github.<org>.webhook_secret`, as shown in the multi-org secrets fixture: [3](#0-2) 

The actual HMAC comparison itself is a legitimate constant-time compare: [4](#0-3) 

So if an attacker controls (or has legitimately obtained, e.g. by installing their own GitHub App/webhook on an organization also configured on this same multi-tenant Shipit instance) the `webhook_secret` for *any one* configured organization "OrgB", they can sign an arbitrary payload with OrgB's secret while setting `repository.owner.login` to `"OrgB"` for verification purposes, but the actual handlers (`push_handler.rb`, `pull_request/*`, etc.) act on `repository.full_name`/`repository.owner.login` values inside that same body to look up and mutate `Stack`/`Commit`/`PullRequest` records — there is no code path that cross-checks that the `repository` object used by the handler is the one whose owner's secret was used to authenticate the request. Because JSON allows independent nested owner fields for `repository` vs `organization`, and because the same top-level payload is passed unmodified to `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`: [5](#0-4) 
this is architecturally the same class of bug as the reported finding: a value used to select/derive the trust anchor (secret key / proposal id) is read from data that has not yet been authenticated by that same anchor, allowing content and authenticator to be mismatched.

### Impact Explanation
If exploitable, this allows a party who has been granted their own organization/app on a shared multi-tenant Shipit deployment to forge webhook events (push, pull_request, status, check_suite, membership) that Shipit will treat as authentic for a *different* organization's repositories/stacks, because the verification step only checks "is this signed by *some* configured org's secret that the payload claims to be," not "is this signed by the secret belonging to the org that owns the repository being acted upon." This could lead to spoofed commit ingestion, spoofed CI statuses used to gate deploys, or spoofed team/membership changes — touching the "unauthorized deploy" and cross-repository-write impact tiers.

### Likelihood Explanation
This requires the target Shipit instance to be configured with more than one GitHub organization (the multi-org `secrets.github` layout), and requires the attacker to control a `webhook_secret` for at least one of those configured organizations (e.g., by being a legitimate but lower-trust tenant). This is a real, supported configuration (documented in `secrets.development.shopify.yml` and `secrets_double_github_app.yml`), so it is plausible in shared/multi-tenant Shipit deployments, though it does not apply to the common single-organization deployment.

### Recommendation
After verifying the signature, re-derive `repository_owner`/organization strictly from the verified body and confirm it matches the organization whose secret was actually used (i.e., don't let the payload pick its own verifier). Alternatively, verify the signature against every configured secret and only accept the request if the resolved organization used for verification also matches the resolved organization of the concrete `repository`/`stack` the handler will act on, rejecting mismatches explicitly.

### Proof of Concept
1. Configure Shipit with two organizations, `OrgA` (victim, high-trust) and `OrgB` (attacker-controlled or attacker-owned installation), per `test/dummy/config/secrets_double_github_app.yml`.
2. Attacker obtains `OrgB`'s `webhook_secret` (they legitimately created/administer the OrgB GitHub App).
3. Attacker crafts a `push` payload with `repository.owner.login = "OrgB"` (so `Shipit.github(organization: "OrgB")` is used for verification) but with `repository.full_name` set to an `OrgA`-owned repo/stack that also exists on the instance, and signs the body with OrgB's `webhook_secret`.
4. `WebhooksController#verify_signature` resolves `repository_owner` from the body ("OrgB"), verifies successfully against OrgB's secret, and the request proceeds; `PushHandler`/`GithubSyncJob` then act on the `OrgA` stack keyed by `repository.full_name`, without ever re-checking that the verifying organization matches the repository's real owner.

Note: I was unable to fully trace whether every downstream handler (`push_handler.rb`, `check_suite_handler.rb`, etc.) strictly resolves the `Stack` by `Repository` records scoped to the verified organization versus purely by `repository.full_name`/`owner/name` — I did not get to inspect `push_handler.rb` contents in this session due to a tool error on the final iteration. This should be confirmed by reading `app/models/shipit/webhooks/handlers/push_handler.rb` and `app/models/shipit/webhooks/handlers/handler.rb` to verify whether `Stack`/`Repository` lookups are unconditionally scoped by owner, which would determine whether this is fully exploitable end-to-end or only partially (e.g., limited to spoofing membership/team events, or push events on repos not yet backed by an existing `Stack`).

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
