### Title
`StatusHandler#process` writes cross-tenant `Status` rows because it looks up commits by SHA globally instead of scoping to the webhook-verified repository - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` finds target commits with `Commit.where(sha: params.sha)` across the entire `commits` table, with no scoping to the repository whose `webhook_secret` was verified for this request. Since `Commit#sha` is not globally unique (any fork of an upstream repo can share ancestor commits), a webhook signed for org A's repository can create/update `Status` rows on org B's `Commit` records whenever the SHAs collide, and those status changes drive `Commit#state`/CI-gating logic on org B's stack.

### Finding Description
Binding claimed safe: `webhook_secret_A` authenticates `payload_A` ⇒ mutation scoped to `repository_A`. In the actual code this becomes: `webhook_secret_A` authenticates `payload_A` ⇒ mutation applied to `Commit.where(sha: payload_A['sha'])`, which is **not** filtered by `repository_A`/`stack_A` at all.

Trace:
- `WebhooksController#verify_signature` resolves `Shipit.github(organization: repository_owner)` from `payload.dig('repository','owner','login')` and verifies `X-Hub-Signature` against that org's `webhook_secret`. This only proves the payload was signed by org A's GitHub App/secret; it says nothing about which `Commit` rows may be touched. [1](#0-0) 
- `WebhooksController#create` dispatches the raw JSON straight to handlers: `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`. [2](#0-1) 
- The base `Handler` class does define a repository-scoped helper, `stacks`, built from `Repository.from_github_repo_name(repository_name)` (i.e., `payload.dig('repository','full_name')`), which other handlers use to constrain writes to the correct repository. [3](#0-2) 
- `StatusHandler#process` does **not** use `stacks`/`repository_name` at all. It only validates `sha`/`state`/etc. via the `ExplicitParameters` schema (which enforces types, not tenant ownership) and then does a bare, unscoped lookup: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }`. [4](#0-3) 
- `Commit` belongs to a `Stack` (one `Stack` per repository/branch/environment), and `sha` has no global uniqueness constraint across stacks; nothing in `Commit` prevents two different stacks (for two different repositories/orgs) from having rows with the identical `sha` for a shared ancestor commit. [5](#0-4) 

Exploit flow: Org A configures a Shipit stack for `orgA/fork`, org B configures a stack for `orgB/fork`, both forked from the same upstream and both containing an unmodified ancestor commit `SHA_X`. Org A's attacker-controlled CI/App (which the attacker fully controls because it's their own fork/CI, no Shipit secrets needed beyond the ability to trigger their own repo's `status` webhook, e.g. via their own CI or a self-hosted GitHub App configured on their fork) sends a legitimately-signed `status` event for `orgA/fork` with `sha = SHA_X`, `state = success`. `verify_signature` passes because the signature matches org A's real `webhook_secret`. `StatusHandler#process` then matches **every** `Commit` row with `sha = SHA_X`, including org B's `Commit` for `orgB/fork`, and calls `create_status_from_github!` on it, writing a `Status` and changing `Commit#state` for org B's stack. None of the listed guards (`verify_signature`, `drop_unhandled_event`, `ExplicitParameters` schema, model validations) check that the matched `Commit` actually belongs to the repository that was cryptographically verified for this specific payload.

### Impact Explanation
This is a payload for one repository mutating another repository's `Commit`/`Status` state — matching the Critical category "a payload for one repository mutating another's stack, commit, task or team." An attacker who controls only their own fork's webhook delivery can flip CI status (`success`/`failure`/`error`/`pending`) for a commit in a completely unrelated organization's stack whenever a SHA collision exists (guaranteed for any unmodified file/commit shared between an upstream and its forks). Downstream effects of `Commit#create_status_from_github!` include CI-gating decisions, `ProcessMergeRequestsJob` enqueuing on transition to `success`/`pending` (per `test/models/commits_test.rb`), and deployability signals — i.e., the attacker can potentially push a shared ancestor commit into a "green"/deployable state for org B without ever authenticating against org B. This is repeatable against any pair of stacks (regardless of org) that happen to share a commit SHA — common for OSS forks, and also possible for any two Shipit-tracked repos that historically shared a merge base.

### Likelihood Explanation
Preconditions: (1) two Shipit stacks configured for different repositories that share at least one commit SHA (near-guaranteed for forks of the same upstream with unmodified files/commits), (2) attacker controls webhook delivery for their own repository (any GitHub App/CI configured on a repo they own can emit a `status` event, or they can `POST /webhooks` directly with a correctly-signed payload for their own org, which they can produce because they own the app/secret for their own org). No Shipit session, API token, or org B's secret is required. Cost is a single HTTP POST with a valid signature for org A only. Fully repeatable and scriptable against any target stack once a matching SHA is known (trivial to arrange by forking and never modifying the target file).

### Recommendation
Scope `StatusHandler#process` to the repository verified by the webhook, mirroring the base `Handler#stacks` helper used elsewhere: replace `Commit.where(sha: params.sha)` with a query restricted to `stacks.joins(:commits).where(commits: { sha: params.sha })` (i.e., `Commit.where(sha: params.sha, stack: stacks)`), so that a `status` payload can only mutate commits belonging to the repository whose signature was verified.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb
require 'test_helper'

module Shipit
  module Webhooks
    module Handlers
      class StatusHandlerCrossTenantTest < ActiveSupport::TestCase
        test "status webhook for org A does not mutate org B's commit with the same sha" do
          shared_sha = 'deadbeefcafedeadbeefcafedeadbeefcafe123'

          repo_a = Repository.create!(owner: 'orgA', name: 'fork')
          stack_a = Stack.create!(repository: repo_a, environment: 'production', branch: 'master')
          commit_a = stack_a.commits.create!(sha: shared_sha, message: 'shared ancestor')

          repo_b = Repository.create!(owner: 'orgB', name: 'fork')
          stack_b = Stack.create!(repository: repo_b, environment: 'production', branch: 'master')
          commit_b = stack_b.commits.create!(sha: shared_sha, message: 'shared ancestor')

          # Binding under test, stated before tracing:
          # webhook_secret(orgA) authenticates payload ==> mutation should be confined to repo_a's commits.
          assert_equal 'unknown', commit_b.reload.state

          payload = {
            'sha' => shared_sha,
            'state' => 'success',
            'context' => 'ci/attacker',
            'repository' => { 'full_name' => 'orgA/fork', 'owner' => { 'login' => 'orgA' } }
          }

          # StatusHandler.call is invoked only after WebhooksController#verify_signature
          # has already succeeded using orgA's webhook_secret -- it never references repo_b.
          StatusHandler.call(payload)

          assert_equal 'success', commit_a.reload.state, "expected org A's own commit to be updated"
          assert_equal 'unknown', commit_b.reload.state,
            "org B's commit must NOT change from a payload verified only against org A's secret"
        end
      end
    end
  end
end
```
With current code, the last assertion fails: `commit_b.reload.state` becomes `'success'`, proving the cross-tenant mutation via `StatusHandler#process`'s unscoped `Commit.where(sha: params.sha)` lookup. [6](#0-5)
