### Title
Wildcard Pairing Secret Allows Unauthenticated Device Pairing - (File: device.js)

### Summary
`device.js`'s `handlePairingMessage()` validates an incoming pairing request against the local `pairing_secrets` table using `pairing_secret IN(?,'*')`. Any row whose `pairing_secret` column is literally the wildcard string `'*'` will match **every** incoming pairing attempt, regardless of the actual secret value the sender supplies. This is structurally the same bug class as CVE-2026-46376 (FreePBX UCP): a hard-coded/catch-all credential that, once present/enabled and not disabled by the operator, allows any unauthenticated remote party to pass an authentication check meant to gate a privileged relationship (becoming a trusted "paired device"/correspondent).

### Finding Description
`handlePairingMessage(json, device_pubkey, callbacks)` [1](#0-0)  is invoked whenever the local node receives a device message with subject `"pairing"` from an address that is not yet a known correspondent — `"pairing"` is explicitly in the list of subjects allowed from non-correspondents (`arrSubjectsAllowedFromNoncorrespondents`), so this is reachable by any device/peer that knows the target's permanent device pubkey and hub, both of which are routinely shared publicly (e.g. via `byteball:`/`obyte:` pairing URIs, `arbiter_contract.js`'s `my_pairing_code`, support-bot links, etc.) [2](#0-1) .

The core validation query is:
```
SELECT is_permanent FROM pairing_secrets WHERE pairing_secret IN(?,'*') AND expiry_date>... ORDER BY (pairing_secret=?) DESC LIMIT 1
``` [3](#0-2) 

If the answer set is non-empty, the sender is unconditionally accepted, inserted/confirmed as a correspondent device, and treated as paired: `INSERT ... INTO correspondent_devices ... is_confirmed=1` and the `paired` event is emitted [4](#0-3) . Crucially, the `IN(?, '*')` clause means the check does not require the caller-supplied `pairing_secret` to equal the stored value at all — it only requires that *some* row in the local `pairing_secrets` table equal `'*'` (a hard-coded wildcard sentinel) and be unexpired. Once such a row exists, the actual per-session secret generated by `startWaitingForPairing()` or `getOrGeneratePermanentPairingInfo()` (normally a `crypto.randomBytes(9)` value) becomes irrelevant: **any** pairing_secret string sent by **any** remote device pubkey will satisfy the `IN(?, '*')` predicate and complete pairing.

This mirrors the FreePBX bug class exactly: a legitimate, code-supported "convenience" mechanism (hard-coded/template credential in FreePBX; wildcard `'*'` pairing secret here) that is meant to be a controlled/temporary configuration but, if left active by whoever configured it (analogous to "not immediately changed by the Administrator"), grants unauthenticated access — here, full "paired device" trust status — to any anonymous caller who merely knows the target's public pairing endpoint (pubkey@hub), which is often intentionally published (arbiter contracts, exchange deposit bots, chat pairing links).

### Impact Explanation
Being accepted as a paired/correspondent device is a significant trust escalation in ocore's wallet/device model: correspondent devices are the entities with which shared multisig wallets are negotiated (`extended_pubkeys`, `wallet_signing_paths`, `shared_addresses`), arbiter contracts are exchanged, and private/AA-related messages are routed. An attacker who successfully triggers the wildcard-match path becomes a `is_confirmed=1` correspondent without ever knowing the intended secret, enabling them to initiate wallet-sharing flows, private payment/contract negotiations, or social-engineering follow-on attacks (device chat is displayed as any other paired contact) against the victim node. Depending on downstream flows (e.g., accepting a shared address invite, a private asset transfer, or an arbiter contract as "cosigner"), this could lead to fund-loss scenarios consistent with the required impact classes (e.g., unauthorized participation in private payment chains or shared wallet definitions), which is why this is rated High rather than merely informational.

### Likelihood Explanation
Exploitability depends entirely on whether a `'*'` row is ever inserted into `pairing_secrets` in real deployments. No code path within `device.js`, `arbiter_contract.js`, or the SQL schema files in this repository is shown inserting `pairing_secret='*'` — `startWaitingForPairing()` and `getOrGeneratePermanentPairingInfo()` both insert `crypto.randomBytes(9)`-derived secrets, never the literal `'*'` [5](#0-4) . This means the wildcard branch of the `IN(?, '*')` clause is dead code under normal, in-repo usage and only becomes exploitable if an operator, a customization, or an external tool populates the table with `'*'` (e.g., to intentionally allow open/unauthenticated pairing for bot-like services). I could not find, within the indexed portion of this codebase, any legitimate feature that sets this value, so I cannot confirm this wildcard is actually exercised in production; it may be inert defensive/legacy SQL. This uncertainty should be resolved by checking downstream products (wallet GUIs, hub operator tooling, chatbots) that build on ocore, which are outside this repository's index.

### Recommendation
Remove or gate the `'*'` wildcard branch in the `pairing_secrets` lookup unless it is a deliberately documented, opt-in "open pairing" mode; if it must be supported, require an explicit, separate, rate-limited, and clearly-logged configuration flag (not a magic string in the same secrets table used for real secrets), and never allow it to silently short-circuit secret comparison to `true` for arbitrary caller-supplied values. Regardless, add unit tests asserting that pairing fails when no matching non-wildcard secret exists, and audit any downstream products for whether they ever write `'*'` into `pairing_secrets`.

### Proof of Concept
1. Assume (or configure) a node such that its local `pairing_secrets` table contains a row `pairing_secret='*', expiry_date` in the future (e.g., via a hub/bot operator setting intended to allow open pairing).
2. As an unrelated, previously-unpaired attacker device, obtain the victim's device pubkey and hub host (commonly shared via a `byteball:`/`obyte:` pairing URI or an arbiter-contract `my_pairing_code`).
3. Send a `device_hub`-valid "pairing" justsaying/message to the victim with an arbitrary, guessed `pairing_secret` value (e.g. `"anything"`), per `sendPairingMessage()`'s message shape [6](#0-5) .
4. On the victim node, `handlePairingMessage()` runs the query `pairing_secret IN(?,'*')` with `?` = `"anything"`; because a `'*'` row exists and is unexpired, the row set is non-empty and the attacker is inserted as a confirmed correspondent device [7](#0-6) , despite never knowing the actual intended secret.

// {pairing_secret: "random string", device_name: "Bob's MacBook Pro", reverse_pairing_secret: "random string"}
function handlePairingMessage(json, device_pubkey, callbacks){
	var body = json.body;
	var from_address = objectHash.getDeviceAddress(device_pubkey);
	if (!ValidationUtils.isNonemptyString(body.pairing_secret))
		return callbacks.ifError("correspondent not known and no pairing secret");
	if (!ValidationUtils.isNonemptyString(json.device_hub)) // home hub of the sender
		return callbacks.ifError("no device_hub when pairing");
	if (json.device_hub.length > 200)
		return callbacks.ifError("device_hub too long");
	if (!network.isValidWsUrl(conf.WS_PROTOCOL + json.device_hub))
		return callbacks.ifError("invalid device_hub URL");
	if (!ValidationUtils.isNonemptyString(body.device_name))
		return callbacks.ifError("no device_name when pairing");
	if (body.device_name.length > 100)
		return callbacks.ifError("device_name too long");
	if ("reverse_pairing_secret" in body && !ValidationUtils.isNonemptyString(body.reverse_pairing_secret))
		return callbacks.ifError("bad reverse pairing secret");
	eventBus.emit("pairing_attempt", from_address, body.pairing_secret);
	db.query(
		"SELECT is_permanent FROM pairing_secrets WHERE pairing_secret IN(?,'*') AND expiry_date>"+db.getNow()+" ORDER BY (pairing_secret=?) DESC LIMIT 1", 
		[body.pairing_secret, body.pairing_secret], 
		function(pairing_rows){
			if (pairing_rows.length === 0)
				return callbacks.ifError("pairing secret not found or expired");
			// add new correspondent and delete pending pairing
			var safe_device_name = body.device_name.replace(/<[^>]*>?/g, '');
			db.query(
				"INSERT "+db.getIgnore()+" INTO correspondent_devices (device_address, pubkey, hub, name, is_confirmed) VALUES (?,?,?,?,1)", 
				[from_address, device_pubkey, json.device_hub, safe_device_name],
				function(){
					db.query( // don't update name if already confirmed
						"UPDATE correspondent_devices SET is_confirmed=1, name=? WHERE device_address=? AND is_confirmed=0", 
						[safe_device_name, from_address],
						function(){
							db.query("UPDATE correspondent_devices SET is_blackhole=0 WHERE device_address=?", [from_address], function(){
								eventBus.emit("paired", from_address, body.pairing_secret);
								if (pairing_rows[0].is_permanent === 0){ // multiple peers can pair through permanent secret
									db.query("DELETE FROM pairing_secrets WHERE pairing_secret=?", [body.pairing_secret], function(){});
									eventBus.emit('paired_by_secret-'+body.pairing_secret, from_address);
								}
								if (body.reverse_pairing_secret)
									sendPairingMessage(json.device_hub, device_pubkey, body.reverse_pairing_secret, null);
								callbacks.ifOk();
							});
