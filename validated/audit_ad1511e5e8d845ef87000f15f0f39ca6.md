### Title
Cross-repository commit-status forgery via unscoped `Commit.where(sha:)` lookup in `StatusHandler` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`WebhooksController#verify_signature` authenticates a webhook only against the GitHub organization named in the payload (`repository.owner.login` / `organization.login`), but `StatusHandler`, unlike its sibling handlers, never re-checks that the commit being updated actually belongs to that repository/organization. It updates **any** `Commit` record in the entire Shipit installation whose `sha` matches the attacker-supplied value, regardless of which repository or stack owns it.

### Finding Description
`WebhooksController#verify_signature` picks the GitHub App/organization config to validate the HMAC signature against, based on data taken from the untrusted payload itself: [1](#0-0) [2](#0-1) 

This only proves the request was legitimately signed by GitHub *for that organization*. It says nothing about which specific repository/commit the payload content refers to — that binding is supposed to be enforced by each event handler.

The base `Handler` class does provide a repository-scoping helper (`stacks`, derived from `payload.dig('repository', 'full_name')`), and it is correctly used by sibling handlers such as `PushHandler` (`stacks.not_archived.where(branch:)...`) and `CheckSuiteHandler` (`stacks.where(branch: ...)`): [3](#0-2) [4](#0-3) [5](#0-4) 

`StatusHandler`, however, is inconsistent with this pattern: it doesn't require or use `repository` at all, and looks up commits globally, unscoped to any repository: [6](#0-5) 

`Commit.where(sha: params.sha)` matches *every* commit row in the database sharing that SHA, across every `Stack`/`Repository`/GitHub organization configured on this single Shipit instance (Shipit explicitly supports multi-organization configuration, see `config/secrets.development.example.yml`). Since a git commit's SHA-1 is a deterministic hash of its tree/parent/author/committer/message/timestamps, an attacker who can see a target commit's metadata (e.g. via Shipit's own UI/API for a stack they can view) can recreate an identical commit object in a repository they fully control (in the same or a different org configured on the same Shipit instance) and obtain the exact same SHA. They then legitimately trigger a real, correctly-signed `status` webhook from GitHub for their own repository/org (e.g. by having their own CI post a commit status), which Shipit will accept because the signature check only validates the sending organization, not the target commit's ownership.

`StatusHandler#process` then calls `Commit#create_status_from_github!`, which updates the *victim* commit's status and can enable CI/mark it deployable and trigger continuous delivery, even though the victim commit's own CI never ran: [7](#0-6) [8](#0-7) [9](#0-8) [10](#0-9) 

This mirrors the report's bug class exactly: the verified binding is "organization authenticated" (webhook signature scope), but the value actually acted upon — the `sha` used to select and mutate `Commit` rows — is never checked against that same organization/repository, breaking the equality `organization_authenticated == repository_written`.

### Impact Explanation
An attacker who legitimately controls (or has commit/CI-status posting rights on) any single GitHub repository tracked by this Shipit instance can forge a passing CI status for a commit belonging to a *different*, unrelated stack/repository (potentially in a different organization on a shared multi-org install), as long as they can reproduce that commit's exact SHA. Because `Commit#deployable?` depends on status state and `add_status` schedules continuous delivery / merges, this can result in an **unauthorized deploy** of a commit that never actually passed CI on its own repository — directly matching the "High: ... unauthorized deploy" impact criterion.

### Likelihood Explanation
Exploitation requires the attacker to reproduce an identical git commit object (same SHA) in a repository they control. This is feasible in practice for commits with simple/short content, replayed commits between repos, or where the attacker already knows/controls the exact tree/parent/author/committer/timestamp fields (e.g. via a fork, mirror, or a previously-observed commit). It does not require a Shipit session, API token, or the webhook secret — only push/CI access to some repository already integrated with the shared Shipit instance, which is a materially weaker requirement than compromising the target repository itself.

### Recommendation
`StatusHandler#process` (and the base `Handler` in general) should scope commit lookups by `stacks` / repository, exactly like `PushHandler` and `CheckSuiteHandler` do, e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` or equivalently join through `Repository.from_github_repo_name(payload.dig('repository','full_name'))`, so a status webhook can only affect commits belonging to the repository named (and cryptographically authenticated) in that same payload.

### Proof of Concept
1. Shipit is configured with two organizations/repos it tracks (or two stacks under the same org), e.g. `victim-org/victim-repo` (Stack V) and `attacker-org/attacker-repo` (Stack A), each with the App installed and its own `webhook_secret`.
2. Attacker observes (via Shipit UI/API, which is public read for visible stacks, or via GitHub) the exact tree/parent/author/committer/message/timestamps of a pending commit `C` in `victim-repo`.
3. Attacker reconstructs an identical commit object with `git commit-tree` (or replays the same git objects) inside `attacker-repo`, yielding the same 40-character SHA as `C`.
4. Attacker's own CI (or a manual API call to `POST /repos/attacker-org/attacker-repo/statuses/:sha`) posts a `success` status for that SHA. GitHub sends a legitimately-signed `status` webhook to Shipit for `attacker-org`.
5. `WebhooksController#verify_signature` validates the signature against `attacker-org`'s webhook secret and passes.
6. `StatusHandler#process` runs `Commit.where(sha: params.sha)`, which matches commit `C` in `victim-repo`'s Stack V (in addition to any commit in `attacker-repo`), and calls `create_status_from_github!`, marking `C` as `success` in the victim stack — potentially making it `deployable?` and triggering continuous delivery/deploy.

      new_status
