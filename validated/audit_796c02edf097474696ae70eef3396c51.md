### Title
Webhook signature verification is scoped to `repository.owner.login` while every event handler acts on `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the HMAC secret (and therefore which GitHub organization is treated as "authenticated") using `repository.owner.login` from the JSON body, but `Shipit::Webhooks::Handlers::Handler#repository_name` (and every handler built on it, e.g. `PushHandler`) resolves the repository/stack to actually act on using the unrelated `repository.full_name` field from the same body. Nothing ties these two fields together, so a signature that is valid for organization A can be replayed with a body whose `full_name` points at organization B's repository.

### Finding Description
The controller picks the webhook secret like this: [1](#0-0) [2](#0-1) 

`repository_owner` is `params.dig('repository', 'owner', 'login')` (falling back to `organization.login`). This value is used only to look up which per-organization `Shipit.github(organization:)` config (and thus which `webhook_secret`) to verify the HMAC-SHA1 signature against, as implemented in: [3](#0-2) 

Once the signature check passes, `create` dispatches the *entire raw payload* to the handlers for the event: [4](#0-3) 

But every handler resolves the target repository/stack from a **different** field, `repository.full_name`, never `repository.owner.login`: [5](#0-4) 

For example `PushHandler`, which triggers `stack.sync_github`, only reads `ref`/`after` plus the inherited `stacks`/`repository_name` helper - it never checks `repository.owner.login`: [6](#0-5) 

The same pattern repeats for the pull-request family of handlers (`OpenedHandler`, `ClosedHandler`, `LabeledHandler`, `ReopenedHandler`, `AssignedHandler`), which all resolve `Shipit::Repository.from_github_repo_name(params.repository.full_name)` and then archive/unarchive/provision review stacks, e.g.: [7](#0-6) 

This engine explicitly supports hosting multiple, mutually untrusted GitHub organizations from a single Shipit instance, each with its own `webhook_secret`, as documented and fixture-tested: [8](#0-7) [9](#0-8) 

The equality the code assumes but never enforces is:
`organization whose webhook_secret authenticated the request (repository.owner.login) == organization whose repository/stack is mutated (repository.full_name's owner)`

An attacker who controls (or is a legitimate admin/owner of) one onboarded organization "OrgA" knows OrgA's `webhook_secret` (they configured the GitHub App installation per `docs/setup.md`). They can POST directly to the webhooks endpoint (GitHub's IP is never checked, only the HMAC) with a forged body: `repository.owner.login = "OrgA"` (so the correct, known secret is selected and the signature check passes) but `repository.full_name = "OrgB/some-repo"` (so the handler acts on OrgB's stack). This lets OrgA's holder of a legitimate webhook secret trigger events (`push`, `pull_request`, `status`, `check_suite`) against any other organization tracked by the same Shipit instance without ever knowing OrgB's secret.

### Impact Explanation
This breaks the "organization that authenticated versus the repository that is written" binding explicitly. Concretely:
- `push` events forged this way call `stack.sync_github(expected_head_sha:)` on OrgB's stack, which enqueues a `GithubSyncJob` and can drive Shipit's continuous-deployment pipeline for a repository/organization the attacker never authenticated for - an unauthorized deploy/sync trigger.
- `pull_request` events can archive/unarchive/provision review stacks belonging to OrgB.

This satisfies the "unauthorized deploy" high/critical-impact criteria via a credential-boundary bypass (the wrong organization's secret authorizing actions on another organization's repository).

### Likelihood Explanation
Requires only that the target Shipit deployment hosts more than one GitHub organization (a documented, supported configuration) and that the attacker is a legitimate admin of one of those organizations (able to know/derive their own org's `webhook_secret`, which they configured themselves per the setup docs) — no privileged access to the victim organization or to Shipit itself is needed. This is a realistic scenario for shared/multi-tenant Shipit instances.

### Recommendation
Bind the two identities together: derive the organization used for signature verification from the same field the handlers use to resolve the target repository (`repository.full_name`'s owner segment, or `organization.login` for org-scoped events), and reject the request if `repository.owner.login` does not match the owner segment of `repository.full_name`. Alternatively, have handlers re-verify that the resolved `Repository`/`Stack`'s organization matches the organization whose secret validated the signature before performing any mutation.

### Proof of Concept
1. Shipit is configured (per `docs/setup.md`, "Using Multiple Github Applications") with two organizations, `OrgA` and `OrgB`, each with its own GitHub App and `webhook_secret`.
2. Attacker is an admin of `OrgA` and knows `OrgA`'s `webhook_secret` (they set it up).
3. Attacker crafts a push payload body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha, e.g. an old/malicious commit already on OrgB's branch>",
  "repository": {
    "owner": { "login": "OrgA" },
    "full_name": "OrgB/victim-repo"
  }
}
```
4. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(OrgA_webhook_secret, body)>` and POSTs directly to the Shipit webhooks endpoint with `X-Github-Event: push`.
5. `WebhooksController#verify_signature` calls `Shipit.github(organization: "OrgA")` (from `repository.owner.login`), verifies the signature successfully against `OrgA`'s secret.
6. `create` dispatches to `PushHandler`, which resolves `stacks` via `repository.full_name = "OrgB/victim-repo"`, matching the `OrgB` stack, and calls `stack.sync_github(expected_head_sha: params.after)` — triggering a sync/deploy action on `OrgB`'s stack despite the request being authenticated only by `OrgA`'s credentials.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
    end
  end
end
```
