### Title
Duplicate CLStakingInfo Overwrite in `consolidateNodes()` Causes Incorrect Prague-Era Reward Distribution — (`File: kaiax/staking/staking_info.go`)

---

### Summary

In `kaiax/staking/staking_info.go`, the `consolidateNodes()` function silently overwrites a validator's `CLStakingInfo` when multiple NodeIds sharing the same `RewardAddr` are each independently registered in the CLRegistry. The overwrite discards the first pool's staking amount from reward calculations, causing the affected CLPool to receive zero KAIA staking rewards and corrupting the reward-split ratio for every block after the Prague hardfork.

---

### Finding Description

Kaia's AddressBook explicitly supports a single GC validator registering multiple NodeIds that share one `RewardAddr`. These are consolidated into a single `consolidatedNode` during block processing. Since Prague, each NodeId may also be independently registered in the CLRegistry (consensus liquidity), producing one `CLStakingInfo` per NodeId.

In `consolidateNodes()`, the loop over `si.CLStakingInfos` resolves each `CLNodeId` to its `RewardAddr` via `nToR`, then writes:

```go
// One CLStakingInfo per validator is guaranteed by CLRegistry.
cmap[r].CLStakingInfo = clsi   // line 157
``` [1](#0-0) 

The comment's guarantee is scoped to "one CLStakingInfo per NodeId" — which CLRegistry does enforce. However, it does **not** guarantee "one CLStakingInfo per RewardAddr." When two NodeIds (N1, N3) share RewardAddr R1 and both are registered in CLRegistry, the loop processes N1's entry first (`cmap[R1].CLStakingInfo = clsi_N1`), then immediately overwrites it with N3's entry (`cmap[R1].CLStakingInfo = clsi_N3`). N1's `CLPoolAddr` and `CLStakingAmount` are permanently discarded.

The test suite already documents this exact behavior:

```go
// CL1 will be ignored when being consolidated since it has duplicate CL (not feasible in real)
{CLNodeId: n3, CLPoolAddr: clPool2, CLStakingAmount: clStakingAmount2},
```

Expected result: `&CLStakingInfo{n3, clPool2, clStakingAmount2}` — N1's entry is gone. [2](#0-1) 

The comment "not feasible in real" is a developer assumption, not an enforced invariant. The CLRegistry is a separate system contract that maps NodeId → CLPool without any knowledge of AddressBook's RewardAddr groupings. Nothing prevents a validator operator from registering both N1 and N3 in CLRegistry.

---

### Impact Explanation

The corrupted `consolidatedNode.CLStakingInfo` flows directly into `assignStakingRewards()`:

```go
if isPrague && cn.CLStakingInfo != nil {
    cnAmount, clAmount := cn.Split(reward)
    alloc[cn.RewardAddr] = cnAmount
    alloc[cn.CLStakingInfo.CLPoolAddr] = clAmount   // only N3's pool
}
``` [3](#0-2) 

`Split()` computes the CL fraction as `CLStakingAmount(N3) / (CNStaking(N1+N3) + CLStaking(N3))`: [4](#0-3) 

Three concrete errors per block:

1. **N1's CLPool receives zero KAIA rewards** — its `CLPoolAddr` never appears in `alloc`.
2. **Total staking amount is understated** — `CLStaking(N1)` is excluded from `cnTotalStakingAmount`, so the consolidated validator's weight in the proportional reward calculation is too low, reducing its total reward share.
3. **Wrong split ratio** — the denominator omits `CLStaking(N1)`, so N3's CLPool receives a larger fraction than it is entitled to, and the RewardAddr receives the remainder that should have gone to N1's CLPool.

This constitutes incorrect reward distribution affecting KAIA on every block after Prague hardfork for any validator in this configuration.

---

### Likelihood Explanation

The trigger requires:
- A validator with ≥2 NodeIds registered in AddressBook under the same `RewardAddr` (explicitly supported and documented as a normal multi-staking-contract pattern).
- Each of those NodeIds independently registered in the CLRegistry.

Neither step requires privileged access beyond the validator operator's own keys. The AddressBook multi-NodeId pattern is described in the staking README and tested. The CLRegistry registration is a normal validator action. No majority-validator collusion is required. The scenario is labeled "not feasible in real" only by developer assumption, not by any on-chain enforcement.

---

### Recommendation

Replace the single-slot overwrite with a guard that detects the collision and applies a deterministic resolution. The simplest safe fix is to skip subsequent CLStakingInfos that resolve to an already-assigned `RewardAddr`, and emit a warning:

```go
if r, ok := nToR[clsi.CLNodeId]; ok {
    if cmap[r].CLStakingInfo != nil {
        logger.Warn("duplicate CLStakingInfo for RewardAddr, skipping",
            "rewardAddr", r, "existing", cmap[r].CLStakingInfo.CLNodeId, "duplicate", clsi.CLNodeId)
        continue
    }
    cmap[r].CLStakingInfo = clsi
}
```

A more complete fix would sum the `CLStakingAmount` values and track all `CLPoolAddr`s, mirroring how `StakingAmount` is summed across multiple NodeIds. This requires extending `consolidatedNode` to hold `[]CLStakingInfo` and updating `Split()` and `assignStakingRewards()` accordingly.

---

### Proof of Concept

The existing test case in `kaiax/staking/staking_info_test.go` already demonstrates the overwrite:

```
AddressBook:
  NodeIds      = [N1, N2, N3, N4]
  RewardAddrs  = [R1, R2, R1, R2]   ← N1 and N3 share R1

CLRegistry:
  N1 → clPool1, clStakingAmount1
  N3 → clPool2, clStakingAmount2    ← second entry for R1

consolidateNodes() result:
  CN_R1 = {[N1,N3], R1, A1+A3, CLStakingInfo{N3, clPool2, clStakingAmount2}}
                                    ← clPool1 / clStakingAmount1 silently dropped

assignStakingRewards():
  alloc[R1]      = reward * (A1+A3) / (A1+A3 + clStakingAmount2)
  alloc[clPool2] = reward * clStakingAmount2 / (A1+A3 + clStakingAmount2)
  alloc[clPool1] = 0   ← N1's CLPool receives nothing
``` [2](#0-1) [5](#0-4) [6](#0-5)

func (c consolidatedNode) Split(amount *big.Int) (*big.Int, *big.Int) {
	if c.CLStakingInfo == nil {
		return amount, big.NewInt(0)
	}

	var (
		cnAmountBig = big.NewInt(int64(c.StakingAmount))
		clAmountBig = big.NewInt(int64(c.CLStakingInfo.CLStakingAmount))
		totalAmount = new(big.Int).Add(cnAmountBig, clAmountBig)
	)

	clAmount := new(big.Int).Mul(clAmountBig, amount)
	clAmount = clAmount.Div(clAmount, totalAmount)

	// The remaining amount is for the CN.
	cnAmount := big.NewInt(0).Sub(amount, clAmount)

	return cnAmount, clAmount
}
