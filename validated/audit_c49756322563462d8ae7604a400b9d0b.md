### Title
Webhook signature is verified against the wrong organization's secret, allowing forged commit-status / push events for repositories belonging to any other configured organization - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
In a multi-organization Shipit deployment (`config/secrets.yml` keyed by organization, see `docs/setup.md:182-209`), `WebhooksController#verify_signature` selects which organization's `webhook_secret` to validate the HMAC signature against by reading `repository.owner.login` (or `organization.login`) out of the *unverified* JSON body, then calls `Shipit.github(organization: repository_owner)` to fetch that org's `GitHubApp` and check the signature. [1](#0-0)  Once the signature check passes, the entire raw payload — including a completely independent `repository.full_name` field — is handed unchanged to the event handlers (`Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`). [2](#0-1)  Handlers such as `PushHandler` and the base `Handler#repository_name`/`#stacks` resolve the target repository/stack from `payload.dig('repository', 'full_name')`, and `StatusHandler` resolves the target commit purely from `params.sha` with no repository/organization check at all. [3](#0-2) [4](#0-3) [5](#0-4) 

### Finding Description
The signature check verifies "this payload was signed by *some org's* GitHub App secret, where the org name is taken from a field inside that same unverified payload." It never verifies that the organization whose secret validated the signature is the *same* organization that owns the repository/commit the handlers subsequently act on. This breaks the intended binding:

`organization authenticated by verify_signature == organization/repository acted on by the handlers`

Concretely:
1. Shipit is configured with multiple GitHub Apps, one per organization, each with its own `webhook_secret` (`docs/setup.md:182-209`, `lib/shipit.rb:196-200` `github_app_config`).
2. An attacker who administers (or otherwise knows the `webhook_secret` of) one of those configured organizations — call it `OrgB` — can craft an arbitrary JSON body where `repository.owner.login` (or `organization.login`) is set to `"OrgB"` so `verify_signature` validates it against `OrgB`'s secret via `Shipit.github(organization: repository_owner).verify_webhook_signature`. [6](#0-5) [7](#0-6) 
3. In the same body, the attacker sets `repository.full_name` to `"OrgA/victim-repo"` (a repository belonging to an entirely different, unrelated organization also tracked by the same Shipit instance) and `sha` to an arbitrary commit hash, `state: "success"`.
4. Because the signature passed, the request proceeds to `create`, which dispatches to `StatusHandler`, which does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` — no organization/repository ownership check is performed at all before writing the status. [8](#0-7) 
5. The same applies to `PushHandler`, which resolves `stacks` from `Repository.from_github_repo_name(repository_name)` — again purely from the unverified `repository.full_name` field, independent of which org's secret validated the signature — and triggers `stack.sync_github(expected_head_sha: params.after)`. [9](#0-8) 

The result: an entity with legitimate access to one tenant organization's webhook secret can forge CI/commit-status and push events for any *other* organization's repositories tracked by the same Shipit instance, since the code that decides "is this signature valid" and the code that decides "which repository do I act on" trust two different, uncorrelated fields of the same untrusted JSON body.

### Impact Explanation
Forged commit statuses are not cosmetic — `Commit#create_status_from_github!` feeds the commit's CI/status state, which downstream `merge_status`/`deployable_status` logic (`app/models/shipit/status/group.rb`, `app/models/shipit/merge_request.rb`) uses to decide whether a commit/PR is safe to merge or deploy. An attacker forging a `"success"` status for a commit in a repository they don't otherwise have write access to can unlock/trigger automated merges or deploys gated on that status, and forged `push` events can force out-of-band `GithubSyncJob`s against another org's stacks. This satisfies the "unauthorized deploy/merge" and "cross-repository writes" impact bar, achieved purely by an actor who is trusted for one tenant organization (or in the single-app case, one arbitrary field of an unsigned-looking JSON key) forging state for a completely different repository — without needing an `ApiClient` token, session, or GitHub write access on the victim repo.

### Likelihood Explanation
This requires a multi-organization Shipit deployment (explicitly documented and supported in `docs/setup.md`) where the attacker legitimately controls (or has obtained the webhook secret of) at least one of the configured organizations — a realistic scenario for a Shipit instance shared across multiple business units, agencies, or partner orgs with differing trust levels. No repository write access, `ApiClient` token, or Shipit session is required to exploit; only knowledge of one tenant's webhook secret and the ability to POST to `/webhooks`.

### Recommendation
After verifying the HMAC signature, re-derive the trusted organization/repository binding server-side rather than trusting attacker-controlled JSON fields for routing: verify that the organization used to select the `webhook_secret` matches the owner organization of `repository.full_name` (or `organization.login`) actually referenced later by the handler, e.g. reject the payload if `repository.full_name.split('/').first != repository_owner` (case-insensitively), or better, look up the `Stack`/`Repository` and confirm its configured organization equals the one that authenticated the signature before dispatching to any handler.

### Proof of Concept
```
POST /webhooks
X-Github-Event: status
X-Hub-Signature: sha1=<HMAC-SHA1 of body, computed with OrgB's webhook_secret>

{
  "sha": "<victim commit sha in OrgA/victim-repo, tracked by the same Shipit instance>",
  "state": "success",
  "repository": { "owner": { "login": "OrgB" }, "full_name": "OrgA/victim-repo" }
}
```
`repository_owner` resolves to `"OrgB"` for signature verification (`app/controllers/shipit/webhooks_controller.rb:59-62`), which the attacker's own known `webhook_secret` satisfies. `verify_signature` passes, `StatusHandler#process` then looks up commits purely by `sha` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`) and writes a forged "success" status for the `OrgA/victim-repo` commit, with no check that `OrgA` was the organization that authenticated the request.

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
