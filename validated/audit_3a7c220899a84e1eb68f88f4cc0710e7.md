## Title
`transfer_to_post_migration_treasury` allows any signed user to migrate an arbitrary asset class, not just the intended migrated asset - (pallets/ah-ops/src/lib.rs)

### Summary
`transfer_to_post_migration_treasury` accepts a caller-supplied `asset_id: Box<AssetId>` with no validation against an intended/allow-listed asset set, and moves the *entire* balance of that arbitrary asset from `TreasuryPreMigrationAccount` to `TreasuryPostMigrationAccount`. Any signed account can invoke it with any `AssetId` (e.g. `Location`) for which the pre-migration treasury account happens to hold a nonzero balance.

### Finding Description
The extrinsic only checks `ensure_signed(origin)` (any user, no permission check) and `T::MigrationCompletion::get()`: [1](#0-0) 

There is no restriction that `asset_id` must equal a specific native asset or be a member of an allow-list (unlike `translate_para_sovereign_child_to_sibling_derived`, which iterates over `T::RelevantAssets::get()` — a bounded, governance-configured list). Here the caller fully controls `asset_id`, and the function:
1. Reads `balance = Fungibles::balance(*asset_id, &pre_migration_account)`.
2. Requires only `balance > 0`.
3. Transfers the *entire* balance of that asset to `post_migration_account`.

If `TreasuryPreMigrationAccount` ever holds any nonzero balance of an asset class unrelated to the intended migration (e.g., dust sent accidentally, an airdrop, a foreign asset received via XCM teleport/reserve-transfer to that account, or any other protocol interaction that credits that account), any unprivileged signed user can call this extrinsic with that `AssetId` and force the transfer, permanently commingling that asset's accounting into `TreasuryPostMigrationAccount`. This is callable repeatedly for every asset class the account happens to hold, since the call is not indexed/tracked per-asset and has no "already migrated" guard beyond the balance simply becoming zero after the first call.

### Impact Explanation
Impact is scoped to cross-asset accounting contamination between the two treasury accounts, as specified: an attacker can force migration of assets never intended to be part of this single-asset migration path, altering `TreasuryPostMigrationAccount`'s asset composition and requiring manual reconciliation/governance intervention. It does not let the attacker steal funds for themselves (funds move treasury-to-treasury), but it does break the invariant that migration transfer must be scoped to the intended asset(s) only.

### Likelihood Explanation
Feasibility depends entirely on whether `TreasuryPreMigrationAccount` can realistically hold a nonzero balance of an asset not intended for migration. Since this is a chain-controlled sovereign/treasury account, in principle any user can send it dust of any registered foreign asset or teleport/reserve-transfer an arbitrary asset into it via existing XCM configuration, at essentially zero cost, and then call this permissionless extrinsic. This makes the precondition (account holding an unrelated nonzero asset balance) attacker-achievable, and the call itself is a single unauthenticated extrinsic — fully repeatable for each asset class.

### Recommendation
Restrict `asset_id` to only the intended migration asset(s), analogous to `T::RelevantAssets` used elsewhere in the pallet — e.g., add a `type MigrationTreasuryAssetId: Get<...>` (or an allow-list `Get<Vec<AssetId>>`) and `ensure!(*asset_id == T::MigrationTreasuryAssetId::get(), Error::<T>::InvalidAsset)` (or membership check) before performing the balance query/transfer, rather than accepting an arbitrary caller-supplied asset id.

### Proof of Concept
Rust unit test in `pallets/ah-ops/src/tests.rs`:
```rust
#[test]
fn transfer_to_post_migration_treasury_migrates_unrelated_asset() {
    new_test_ext().execute_with(|| {
        // Arrange: migration completed
        // (mock MigrationCompletion::get() = true)
        let pre = TreasuryPreMigrationAccount::get();
        let post = TreasuryPostMigrationAccount::get();

        // Fund pre-migration account with an *unrelated* asset (not the intended migration asset)
        let unrelated_asset_id = 9999u32; // or arbitrary Location in AH runtime
        Fungibles::mint_into(unrelated_asset_id, &pre, 1_000).unwrap();

        // Act: arbitrary signed (non-privileged) account calls with the unrelated asset id
        assert_ok!(AhOps::transfer_to_post_migration_treasury(
            RuntimeOrigin::signed(ALICE), // attacker-controlled, unrelated to migration
            Box::new(unrelated_asset_id),
        ));

        // Assert: unrelated asset balance was moved despite not being the intended migrated asset
        assert_eq!(Fungibles::balance(unrelated_asset_id, &pre), 0);
        assert_eq!(Fungibles::balance(unrelated_asset_id, &post), 1_000);
    });
}
```
This demonstrates the call succeeds for any asset id with nonzero balance and moves funds regardless of whether it's the intended migrated asset, confirming the missing asset-scoping check.

### Citations

**File:** pallets/ah-ops/src/lib.rs (L355-379)
```rust
		pub fn transfer_to_post_migration_treasury(
			origin: OriginFor<T>,
			asset_id: Box<<T::Fungibles as FungiblesInspect<T::AccountId>>::AssetId>,
		) -> DispatchResultWithPostInfo {
			ensure_signed(origin)?;

			ensure!(T::MigrationCompletion::get(), Error::<T>::MigrationNotCompleted);

			let pre_migration_account = T::TreasuryPreMigrationAccount::get();
			let post_migration_account = T::TreasuryPostMigrationAccount::get();

			let balance =
				<T as Config>::Fungibles::balance(*asset_id.clone(), &pre_migration_account);
			ensure!(balance > 0, Error::<T>::ZeroBalance);

			<T as Config>::Fungibles::transfer(
				*asset_id,
				&pre_migration_account,
				&post_migration_account,
				balance,
				Preservation::Expendable,
			)?;

			Ok(Pays::No.into())
		}
```
