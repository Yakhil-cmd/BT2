### Title
Unhandled TypeError on missing `payload` in `arrPrivateElements[0]` crashes the node - ([File: network.js])

### Summary
`handleOnlinePrivatePayment()` in `network.js` dereferences `arrPrivateElements[0].payload.denomination` before validating that `payload` exists, mirroring the igmpproxy CVE pattern where an attacker-controlled field is used to format/branch without a prior null-check, causing a crash.

### Finding Description
`handleOnlinePrivatePayment(ws, arrPrivateElements, bViaHub, callbacks)` only validates that `arrPrivateElements` is a non-empty array before accessing nested fields: [1](#0-0) 

```
function handleOnlinePrivatePayment(ws, arrPrivateElements, bViaHub, callbacks){
	if (!ValidationUtils.isNonemptyArray(arrPrivateElements))
		return callbacks.ifError("private_payment content must be non-empty array");
	
	var unit = arrPrivateElements[0].unit;
	var message_index = arrPrivateElements[0].message_index;
	var output_index = arrPrivateElements[0].payload.denomination ? arrPrivateElements[0].output_index : -1;
```

There is no check that `arrPrivateElements[0].payload` is present or is an object before `.denomination` is read on it. If `payload` is `undefined` (e.g., the sender omits it or sets it to `null`), this line throws `TypeError: Cannot read properties of undefined (reading 'denomination')`. This is analogous to the CVE-2025-50681 root cause: a crafted/omitted field bypasses validation and reaches a dereference (`inet_fmtsrc()` on a null pointer in igmpproxy vs. property access on `undefined` here), producing an unhandled crash instead of a graceful validation error.

Unlike other private-payment entry points such as `wallet.js`'s `handlePrivatePaymentChains`, which explicitly requires `isNonemptyObject(e.payload)` for every chain element before calling into the network layer [2](#0-1) , `handleOnlinePrivatePayment` in `network.js` is a lower-level function reachable more directly from device/peer message handling and does not perform this same guard itself. Any code path that calls `handleOnlinePrivatePayment` with a private element lacking a `payload` field (or with `payload: null`) will trigger the uncaught exception before `payload` is otherwise validated further down (`checkIfNewUnit` / `privatePayment.validateAndSavePrivatePaymentChain`).

Because this exception is thrown synchronously and not wrapped in a `try/catch`, it becomes an uncaught exception. The registered global handler explicitly re-throws to crash the process: [3](#0-2) 

```
process.on('uncaughtException', (err) => {
	console.log('Uncaught exception:', err);
	console.error('Uncaught exception:', err);
	...
	throw err; // crash the process to avoid ending up in an inconsistent state
});
```

### Impact Explanation
A private-payment counterparty or paired device that can reach `handleOnlinePrivatePayment` with a malformed `private_payment` element (missing/null `payload`) can crash the receiving node process — a denial-of-service condition consistent with the "network unable to confirm new units" impact category, since the crashed process stops validating/relaying units until restarted.

### Likelihood Explanation
Exploitation only requires sending one message with a private-payment array whose head element omits the `payload` field; no cryptographic material, signatures, or prior state is required to reach this line, only the initial non-empty-array check needs to pass.

### Recommendation
Add an explicit `isNonemptyObject(arrPrivateElements[0].payload)` (or equivalent) check immediately after the array-length check in `handleOnlinePrivatePayment`, returning `callbacks.ifError(...)` on failure, mirroring the guard already present in `wallet.js`'s `handlePrivatePaymentChains`.

### Proof of Concept
1. Establish a device/peer connection capable of invoking `handleOnlinePrivatePayment` (e.g., via the private-payment message flow) without going through `wallet.js`'s `handlePrivatePaymentChains` pre-validation, or via any caller that forwards attacker-supplied `arrPrivateElements` directly.
2. Send `arrPrivateElements = [{ unit: "<valid-looking base64 unit id>", message_index: 0 }]` — i.e., omit the `payload` field entirely.
3. Execution reaches `arrPrivateElements[0].payload.denomination`, throwing `TypeError: Cannot read properties of undefined (reading 'denomination')`.
4. The exception is uncaught, hits `process.on('uncaughtException', ...)`, which re-throws and crashes the node process.

**Uncertainty note:** I was unable to fully trace every call site that invokes `handleOnlinePrivatePayment` (there are 3 references in `network.js` and 5 in `wallet.js`) to confirm with certainty that at least one path bypasses the `isNonemptyObject(payload)` guard present in `handlePrivatePaymentChains`. Due to index size limits, not all call sites and their exact wrapping logic could be inspected line-by-line; a full-repository review (e.g., via a Devin session) is recommended to confirm all reachable paths into this function before treating this as fully confirmed exploitable in every configuration.
