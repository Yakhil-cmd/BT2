### Title
Webhook signature verification keys off an attacker-controlled organization field that is decoupled from the repository actually acted upon - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
The bug class in the report (`_movePop` acting on the wrong element because the operation's target and the value actually removed diverge) has a structural analog in `Shipit::WebhooksController`: the value used to *select which secret authenticates the request* is not the same value used to *select which repository/stack the request acts on*, even though both are read from the same untrusted JSON body.

### Finding Description
`WebhooksController#verify_signature` picks the `GitHubApp`/secret to verify the HMAC using `repository_owner`, computed from the raw JSON payload itself: [1](#0-0) [2](#0-1) 

`GitHubApp#verify_webhook_signature` short-circuits to `true` whenever no `webhook_secret` is configured for the resolved organization: [3](#0-2) 

Shipit explicitly supports multi-organization configuration where `webhook_secret` is optional and can be `nil` per org: [4](#0-3) 

Separately, once the request passes `verify_signature`, the actual JSON `params` (the full untouched payload) is handed to the event handler, which independently resolves the target repository via a *different* field: `payload.dig('repository', 'full_name')`: [5](#0-4) 

Because `repository_owner` (used to pick the authenticating secret) and `repository.full_name` (used to pick the repository/stack that is written to) are two independent, attacker-supplied fields of the same JSON body, they need not refer to the same organization. If a Shipit deployment has multiple GitHub orgs configured and *any one* of them has `webhook_secret` left blank (a documented, supported configuration), an attacker can craft a payload where `repository.owner.login` (or `organization.login`) names that unsecured org — causing `verify_webhook_signature` to return `true` unconditionally — while `repository.full_name` names a completely different, secured organization's real repository. `Handler#repository_name`/`#stacks` then resolves and mutates state for that unrelated, secured repository.

This breaks the equality that should hold: `organization whose secret authenticated the request == organization that owns the repository being acted upon`. Concretely for `StatusHandler`, this lets an unauthenticated party inject a forged commit status (`Commit#create_status_from_github!`) for any commit belonging to any stack in the installation, using only the identity of a loosely-configured (or secret-less) sibling org: [6](#0-5) 

### Impact Explanation
Forged/unauthenticated statuses can flip a commit's CI state to green for stacks that rely on `deployable?`/CI checks before allowing deploys, and `PushHandler`/`GithubSyncJob` can be triggered to sync arbitrary SHAs into a targeted stack's commit history — both without possessing the correct webhook secret for the org that actually owns the target repository. Combined with continuous deployment settings, a forged "success" status can be a prerequisite step toward an unauthorized deploy. This matches the "unauthorized deploy" / "escalation" impact tier, but requires a specific precondition (a Shipit instance configured with multiple GitHub orgs where at least one has no `webhook_secret`) which I could not confirm is common or default — single-org installs where the org's secret is set are not affected, since `repository_owner` and the org whose secret is checked are effectively the only org in scope, matching the eventual `repository.full_name` owner in the normal case.

### Likelihood Explanation
Exploitability depends entirely on deployment configuration: it requires (a) multiple GitHub orgs configured in `Shipit.github`, and (b) at least one of them configured with no `webhook_secret`. This is a documented/supported configuration (`webhook_secret: # nil`), so it is plausible in real deployments that mix a "public"/low-trust org with a "private"/high-value org, but it is not guaranteed to exist in any given install. I was not able to find any additional check in the codebase (e.g., verifying `repository.owner.login == repository.full_name`'s owner, or requiring a secret to be present for all configured orgs) that would close this gap.

### Recommendation
- Require a non-blank `webhook_secret` for every configured GitHub org (fail closed instead of `return true unless webhook_secret`) in `GitHubApp#verify_webhook_signature`, at least when multiple orgs are configured.
- Additionally, cross-check that the organization used to select the verifying secret (`repository_owner` in `WebhooksController`) matches the owner embedded in `repository.full_name` used by `Handler#repository_name`, rejecting the webhook (422) on mismatch.

### Proof of Concept
1. Configure two GitHub orgs in `secrets.yml`: `OrgPublic` (no `webhook_secret`) and `OrgPrivate` (with `webhook_secret` set), each with a Shipit stack.
2. POST to `/github_webhooks` (or engine-mounted webhook path) with header `X-Github-Event: status` and body:
```json
{
  "sha": "<sha-of-a-commit-in-OrgPrivate-repo>",
  "state": "success",
  "context": "ci/forged",
  "repository": { "owner": { "login": "OrgPublic" }, "full_name": "OrgPrivate/target-repo" }
}
```
No valid `X-Hub-Signature` is required because `Shipit.github(organization: "OrgPublic")` has no `webhook_secret`, so `verify_webhook_signature` returns `true` unconditionally per `lib/shipit/github_app.rb` lines 76-77.
3. `WebhooksController#create` dispatches the full `params` (unchanged) to `Shipit::Webhooks.for_event('status')`, i.e. `StatusHandler`, which resolves `Commit.where(sha: params.sha)` — a commit that actually belongs to `OrgPrivate/target-repo` — and calls `commit.create_status_from_github!(params)`, injecting a forged CI status for `OrgPrivate`'s repository despite never presenting `OrgPrivate`'s webhook secret.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
