### Title
Webhook signature verification authenticates the payload's `repository.owner.login` while every event handler dispatches writes based on the independent `repository.full_name` field, letting one org's signed webhook write to another org's stack - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret to validate the HMAC signature against using `repository_owner`, a value read straight out of the untrusted JSON payload (`repository.owner.login`, falling back to `organization.login`). Once the signature is accepted, `Shipit::Webhooks::Handlers::Handler#repository_name` (used by every handler: push, status, check_suite, membership, pull_request) resolves the target `Repository`/`Stack` using a *different* payload field, `repository.full_name`. These two fields are never cross-checked against each other, so the "organization that authenticated" and the "repository that is written" are two independently attacker-controlled strings inside the same signed body.

### Finding Description
`verify_signature` is a `before_action` on `Shipit::WebhooksController`: [1](#0-0) [2](#0-1) 

`Shipit.github(organization: repository_owner)` fetches the `GitHubApp` (and its `webhook_secret`) for whatever organization name is present in `repository.owner.login`/`organization.login`, and then verifies the raw body's HMAC against that org's secret: [3](#0-2) 

If the signature validates, the entire raw JSON body is handed unmodified to the registered handler: [4](#0-3) 

Every handler (`PushHandler`, `StatusHandler`, `CheckSuiteHandler`, and the `pull_request` handlers) resolves its target `Stack`s through `Handler#stacks`, which uses a *separate* JSON field, `repository.full_name`: [5](#0-4) [6](#0-5) [7](#0-6) 

`repository.owner.login` (checked by the signature-selection logic) and `repository.full_name` (used to pick the repository/stack to mutate) are two distinct JSON keys in the same payload with no assertion that `full_name` starts with `owner.login`. This is the direct structural analog of the M01 report: two representations of "which repository/org this event belongs to" that are supposed to move together, but nothing in the code enforces that they stay in sync — exactly like `Governed.contracts` and `Directory.contracts` in the referenced report.

Shipit explicitly supports multiple configured GitHub orgs, each with its own `webhook_secret` (see `config/secrets.development.shopify.yml`, `Shipit#github_app_config`), which is the normal multi-tenant deployment this engine documents: [8](#0-7) 

An attacker who legitimately controls one configured organization ("attacker-org", with its own valid `webhook_secret`) can therefore sign a webhook payload with their own secret while setting `repository.full_name` to `"victim-org/victim-repo"` (or `organization.login` to their own org while `repository.owner.login` for the signature path). Because the signature check only cares that *some* configured org's secret matches the body, and the handler never checks that `full_name`'s owner segment equals the org that was actually verified, the request is accepted as authentic and is dispatched against the victim stack.

### Impact Explanation
Depending on the event type this crosses the "unauthorized deploy/rollback" boundary explicitly called out as Critical impact:
- `push` → `PushHandler#process` calls `stack.sync_github(expected_head_sha: ...)` on the victim's stack, forcing a `GithubSyncJob`/`CacheDeploySpecJob` re-sync against attacker-chosen head SHA expectations, which can trigger unwanted continuous-delivery deploys on a stack the attacker's org never owns write access to (cross-repository writes).
- `status` → `StatusHandler#process` writes fabricated CI status onto commits of the victim's stack (`Commit#create_status_from_github!`), which can flip a commit from non-deployable to deployable, enabling an unauthorized deploy to proceed.
- `check_suite` → schedules `schedule_refresh_check_runs!` against the victim's commits, similarly manipulable to unblock deploys gated on required checks.

This satisfies "cross-repository writes" / "an unauthorized deploy" under the Critical impact bar.

### Likelihood Explanation
Exploitation requires only that the attacker control one legitimately configured GitHub organization in the multi-org Shipit deployment (a normal, documented configuration, not a privileged Shipit account, ApiClient token, or session) and knows/derives the victim's `owner/repo` name (public information). No GitHub write access to the victim repo, no Shipit user session, and no webhook secret of the victim are needed — the only credential used is the attacker's own valid webhook secret, which correctly signs a payload whose `repository.full_name` field is otherwise unconstrained.

### Recommendation
Bind repository resolution to the same identity that was cryptographically verified: derive the target repository/organization from `repository_owner` (the field actually checked in `verify_signature`) rather than from the independently-controlled `repository.full_name`, or explicitly assert `repository.full_name.split('/').first.casecmp?(repository_owner)` before dispatching to handlers. More robustly, have `verify_signature` record the verified organization and pass it alongside the payload to `Handler.call`, and have `Handler#stacks` reject any repository whose owner does not match the verified organization.

### Proof of Concept
1. Shipit is configured with two GitHub orgs in `secrets.yml`: `attacker-org` (attacker's own legitimate installation, `webhook_secret: S_A`) and `victim-org` (unrelated tenant, `webhook_secret: S_V`, unknown to attacker), per the multi-org schema in `config/secrets.development.shopify.yml`.
2. Attacker crafts a `push` event JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "deadbeef...",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC(S_A, body)` using their own valid secret and POSTs to `/webhooks` with `X-Github-Event: push`.
4. `WebhooksController#verify_signature` computes `repository_owner == "attacker-org"`, fetches `Shipit.github(organization: "attacker-org")`, and the HMAC validates successfully (`verify_webhook_signature` returns true) since the attacker signed with their own real secret.
5. `Shipit::Webhooks.for_event("push")` dispatches to `PushHandler.call(params)`; `Handler#repository_name` reads `payload.dig('repository','full_name')` → `"victim-org/victim-repo"`, resolves the victim `Stack`, and calls `stack.sync_github(expected_head_sha: "deadbeef...")` — a write against a stack the attacker's org has no legitimate claim over.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
