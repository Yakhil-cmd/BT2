### Title
Unbounded native recursion during AA formula evaluation may crash nodes and cause validity disagreement - (File: formula/evaluation.js)

### Summary
The oscript/AA formula interpreter recursively walks the parsed formula's abstract syntax tree using the native (V8) call stack, exactly the pattern described in the external report. `formula/validation.js` was hardened with an explicit recursion-depth guard, but the actual runtime evaluator, `formula/evaluation.js`, has no equivalent depth check, so a formula whose AST nesting escapes (or predates) the validator's guard can still drive the interpreter's `evaluate()` into unbounded native recursion at trigger-execution time.

### Finding Description
`formula/evaluation.js`'s `evaluate()` function recursively calls itself once per nested formula node (arithmetic operators, `if`, arrays, function calls, etc.). The only stack-size mitigation present is a counter that inserts a `setImmediate` every 100 *sibling* evaluations to avoid extending the call stack across successive statements: [1](#0-0) 

Crucially, this counter resets on entry into nested scopes and does **not** track or cap recursion *depth* — only the number of calls made so far in the current execution, so a deeply nested expression (e.g. `((((((...1...))))))`) still recurses once per nesting level with no ceiling.

By contrast, the sibling module `formula/validation.js`, which statically checks a formula's AST before it is allowed to be stored (e.g., in an AA definition), does track true recursion depth and rejects formulas whose AST exceeds 100 levels: [2](#0-1) 

However, that depth check is gated behind a network-upgrade flag (`constants.pemCurvesFixMci`) and a fallback stable-DAG check: [3](#0-2) 

Any AA definition whose formulas were validated (and thus deployed) *before* `pemCurvesFixMci` activated is never re-validated against the new depth limit, and the tests exercising deep nesting (arrays, dictionaries, `max(...)`, `if`) rely entirely on this validator-side guard to reject deep formulas before they ever reach the evaluator: [4](#0-3) 

Because the evaluator (`formula/evaluation.js`) itself carries no independent depth limit, it depends entirely on the validator having rejected the formula beforehand. This is the same architectural weakness flagged in the external report: the interpreter's call/recursion mechanism is implemented directly on the native stack rather than through a depth-checked or heap-based structure, so any code path that reaches `evaluate()` with a deeply nested AST that the validator failed to reject (grandfathered pre-upgrade AAs, or any future divergence between the two independently-implemented depth-tracking mechanisms in `validation.js` and `evaluation.js`) can overflow the native stack.

A very similar pattern is repeated in `definition.js`'s `validateAuthentifiers`/`evaluate()` used to authenticate address definitions on every posted unit, where recursion (e.g. via chained `not`/`address` references) is only implicitly bounded by the `complexity`/`count_ops` counters rather than an explicit depth check: [5](#0-4) [6](#0-5) 

### Impact Explanation
An attacker-controlled deeply nested formula that reaches `evaluate()` in `formula/evaluation.js` without having been rejected by the validator's depth check can throw `RangeError: Maximum call stack size exceeded`, crashing the Node.js process handling that unit/trigger. If different full nodes have different V8 stack-size configurations (`--stack-size`, platform defaults) or run different code versions where the two depth-tracking implementations diverge, some nodes may successfully evaluate the AA response while others crash or throw, producing disagreement on unit/AA-response validity — a consensus-relevant outcome.

### Likelihood Explanation
The likelihood is currently low-to-moderate: on a live network past `pemCurvesFixMci`, new AA/formula deployments are filtered by `formula/validation.js`'s depth check, and the reachable path requires either (a) an AA/formula deployed and grandfathered before the upgrade activated, or (b) a future edit to one of the two independently maintained recursive walkers (`validation.js` vs `evaluation.js`) that reintroduces a depth mismatch, since there is no shared, single source of truth for the depth limit between validation and execution.

### Recommendation
Add an explicit, unconditional recursion-depth guard directly inside `formula/evaluation.js`'s `evaluate()` (not only in `formula/validation.js`), mirroring the `depth > 100` check already used in `validation.js`, so the interpreter cannot recurse past a safe bound regardless of when/how the formula was originally validated. Consider converting the interpreter to an explicit heap-allocated work-stack instead of native recursion, consistent with the external report's long-term recommendation. Apply the same reasoning to `definition.js`'s `evaluate()`/`validateAuthentifiers` recursive walkers, adding an explicit depth counter independent of the `complexity`/`count_ops` limits.

### Proof of Concept
Conceptual reproduction (cannot be executed against production nodes from this analysis):
1. Construct (or identify a pre-`pemCurvesFixMci` deployed) AA formula/state-variable expression with thousands of levels of nesting, e.g. `'('.repeat(N) + '1' + ')'.repeat(N)` equivalent AST, exceeding the native V8 stack limit.
2. Have this AA respond to a trigger, causing `formula/evaluation.js`'s `evaluate()` to be invoked on the stored (already-validated, grandfathered) AST.
3. Observe the node process throw `RangeError: Maximum call stack size exceeded` during trigger processing, as no depth guard exists in `evaluate()` itself: [7](#0-6) .
