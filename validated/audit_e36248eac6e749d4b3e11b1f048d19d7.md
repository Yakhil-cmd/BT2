### Title
Stale `dry_run_aa` / getter previews combined with unprotected bonding-curve AAs let a trigger sender receive a worse price/amount than expected due to intervening triggers - (File: `aa_composer.js`, `network.js`, `test/samples/uniswap_like_market_maker.oscript`)

### Summary
Wallets and light clients preview an AA's response to a not-yet-submitted trigger via `light/dry_run_aa` (`network.js`, calling `aa_composer.dryRunPrimaryAATrigger`) or via `light/execute_getter` (a read-only "getter" formula defined in the AA). Both compute a result against the *current* last-stable state and are used off-chain to decide the parameters (amounts) of a trigger unit that is only broadcast afterward. If the AA's formulas do not independently re-validate that the live state at actual processing time still matches what the client previewed, the trigger sender ends up executing against different, possibly attacker-manipulated state - conceptually identical to `MuteBond`'s `maxPurchaseAmount()`-then-`deposit()` race.

### Finding Description
`dryRunPrimaryAATrigger` (`aa_composer.js:272-306`) simulates a trigger unit against the current last-stable MC unit and rolls back, returning the exact response (including computed payment `outputs`) without committing anything: [1](#0-0) 

This is exposed to any peer over the network via `light/dry_run_aa` (`network.js:3939-3963`): [2](#0-1) 

Similarly, `light/execute_getter` (`network.js:4008-4031`) lets a client invoke a custom AA "getter" (a view-style formula, e.g. `$f` in `test/aa_composer.test.js:1073-1081`) to compute values such as a swap-out amount, an exchange rate, or a maximum available amount, all read live from current `balance[...]`/`var[...]` state: [3](#0-2) [4](#0-3) 

A typical bonding-curve/AMM-style AA - such as the repository's own `uniswap_like_market_maker.oscript` - computes swap output amounts purely from live balances at trigger-processing time, with **no user-supplied minimum-output / expected-price parameter** to guard against the state having moved between the client's preview and the trigger's actual processing: [5](#0-4) [6](#0-5) 

Note that the "invest in MM" (two-sided liquidity provisioning) case in the same file *does* defend itself with a strict equality bounce check, proving that the AA author intentionally protects only that one path, while the swap paths remain unprotected: [7](#0-6) 

The root cause mirrors `MuteBond.deposit()`: a value (`maxPurchaseAmount()` there, `dry_run_aa`/getter results here) is computed from state as of query time, then used to size a transaction submitted later, with no on-chain check that the state is still what the client observed. Because ocore processes AA triggers in DAG/stability order (not a fixed block), any other trigger unit that reaches an earlier position in that order can change `balance[...]`/`var[...]` before the victim's trigger is processed, exactly as an "innocent user or attacker" starting a new epoch changes `maxPurchaseAmount()` in the original report.

### Impact Explanation
A trigger sender who composes a payment/trigger based on a `light/dry_run_aa` or `light/execute_getter` preview can have their unit processed against materially different state:
- They may receive fewer output tokens/bytes than previewed (worse price), directly mirroring Impact B of the original report ("less payout for the buyer").
- In bonding-curve or auction/ICO-style AAs without an expectation check (unlike the equality-guarded liquidity path shown above), the AA silently executes with the live, unfavorable value instead of bouncing, so the sender's funds are irrevocably consumed as an AA response and cannot be recovered - a genuine AA fund loss for the trigger sender, analogous to the buyer overpaying/underreceiving in `MuteBond`.
- This affects any deployed AA following the shipped market-maker/bonding-curve template pattern that lacks its own slippage protection, which is a class of contracts explicitly provided as a reference by the ocore project.

### Likelihood Explanation
Any unprivileged AA trigger sender can trigger the pattern unintentionally simply by using the standard preview APIs (`light/dry_run_aa`, `light/execute_getter`) that wallets are expected to call before broadcasting a real trigger; no privileged access is required. An adversary wishing to exploit it deliberately only needs to observe the victim's pending trigger unit (visible pre-stabilization on the DAG) and get their own competing trigger processed first, similar to standard front-running - achievable by any ordinary network participant, not requiring a malicious peer/hub/node.

### Recommendation
- For AA templates intended to be used as living contracts (e.g. `uniswap_like_market_maker.oscript` and similar reference oscripts), require the trigger sender to supply an explicit expectation/tolerance parameter (e.g. `trigger.data.min_amount` or `trigger.data.max_price`) and `bounce()` if the live computed result violates it, the same way the "invest in MM" case already does for the two-sided deposit path.
- Document clearly (e.g., in AA-authoring guidance) that `light/dry_run_aa` and getter results are only a preview of state at query time and are not binding; AA authors must add on-chain guards if a stale preview could cause fund loss.
- Consider adding a wallet-side warning when broadcasting a trigger whose composed amount was derived from a `dry_run_aa`/getter call, since intervening triggers can invalidate it before actual processing.

### Proof of Concept
1. A user issues `light/execute_getter` (or `light/dry_run_aa`) against a deployed `uniswap_like_market_maker.oscript`-style AA to preview how much of `$asset` they would receive for `N` bytes via the "exchange bytes to asset" case.
2. The user composes and broadcasts a trigger unit sending `N` bytes to the AA, expecting the previewed `$amount` of `$asset`.
3. Before the user's trigger stabilizes, another trigger changes `balance[$asset]` and `balance[base]` (e.g., a large swap or divestment).
4. When the user's trigger is finally processed, `$amount = $asset_balance - $new_asset_balance` (`test/samples/uniswap_like_market_maker.oscript:105-121`) is recomputed against the new, worse ratio; the AA does not bounce because there is no user-supplied minimum-output check, and the user irrevocably receives less than what was shown by the earlier preview.
