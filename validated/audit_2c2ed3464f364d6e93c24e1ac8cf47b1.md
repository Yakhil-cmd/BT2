### Title
Bridge Value Transfer Permanently Locked When Recipient Is Blacklisted or Non-Payable — (`contracts/service_chain/bridge/BridgeTransferERC20.sol`, `contracts/service_chain/bridge/BridgeTransferKLAY.sol`)

---

### Summary

The Kaia service-chain bridge's `handleERC20Transfer` and `handleKLAYTransfer` functions push assets directly to the `_to` address with no fallback path. If the push fails — because the ERC20 token (e.g., USDC) has blacklisted `_to`, or because `_to` is a contract that reverts on receiving KLAY — the entire `handle*` transaction reverts. The nonce is never consumed, `lowerHandleNonce` never advances past that slot, and the user's assets on the source chain are permanently locked with no on-chain recovery mechanism.

---

### Finding Description

**`handleERC20Transfer` (lock mode)**

```solidity
// BridgeTransferERC20.sol lines 44–72
_lowerHandleNonceCheck(_requestedNonce);
if (!_voteValueTransfer(_requestedNonce)) { return; }

_setHandledRequestTxHash(_requestTxHash);
handleNoncesToBlockNums[_requestedNonce] = _requestedBlockNumber;
_updateHandleNonce(_requestedNonce);          // ← nonce state written

emit HandleValueTransfer(...);

if (modeMintBurn) {
    require(ERC20Mintable(_tokenAddress).mint(_to, _value), ...);
} else {
    IERC20(_tokenAddress).safeTransfer(_to, _value);  // ← can revert
}
``` [1](#0-0) 

All state mutations (nonce update, tx-hash mark) are written before the `safeTransfer`. If `safeTransfer` reverts (e.g., USDC blacklist), the EVM rolls back every state change. The nonce slot is left unconsumed and `handleNoncesToBlockNums[N]` remains `0`.

**`handleKLAYTransfer`**

```solidity
// BridgeTransferKLAY.sol lines 75–99
_lowerHandleNonceCheck(_requestedNonce);
...
handleNoncesToBlockNums[_requestedNonce] = _requestedBlockNumber;
_updateHandleNonce(_requestedNonce);

emit HandleValueTransfer(...);

(bool ok, ) = _to.call.value(_value)("");
require(ok, "handleKLAYTransfer: transfer failed");  // ← reverts if _to rejects KLAY
``` [2](#0-1) 

Same pattern: if `_to` is a contract without a payable fallback, the `call` returns `ok = false`, the `require` reverts, and the nonce is never consumed.

**`_updateHandleNonce` advancement is blocked**

```solidity
// BridgeTransfer.sol lines 149–155
for (i = lowerHandleNonce; i <= limit && handleNoncesToBlockNums[i] > 0; i++) {
    recoveryBlockNumber = handleNoncesToBlockNums[i];
    ...
}
lowerHandleNonce = i;
``` [3](#0-2) 

Because `handleNoncesToBlockNums[N]` is always `0` for the stuck nonce (every attempt reverts), the loop exits immediately at `i = N` and `lowerHandleNonce` is permanently frozen at `N`. `recoveryBlockNumber` is also frozen, causing the off-chain recovery daemon to re-scan from an old block indefinitely. [4](#0-3) 

There is no owner-callable function to skip a nonce, override `_to`, or drain stuck funds from the bridge.

---

### Impact Explanation

**Bridged assets permanently locked.** In lock mode, the user's ERC20 tokens are held in the source bridge; the destination bridge holds the counterpart tokens but can never deliver them. In mint/burn mode, the source-chain tokens are already burned; the destination mint never succeeds. For KLAY, the source bridge holds the user's KLAY and the destination bridge cannot release its KLAY to `_to`. In all cases the user suffers a total, unrecoverable loss of bridged assets.

**`lowerHandleNonce` frozen.** The off-chain recovery system reads `lowerHandleNonce` (via `UpdateInfo` → `LowerHandleNonce`) to determine the scan start point. [5](#0-4) 

With `lowerHandleNonce` frozen, `recoveryBlockNumber` is also frozen, causing the recovery daemon to re-scan the same old range on every cycle, wasting resources and potentially masking other missed events.

---

### Likelihood Explanation

USDC (and USDT, EUROC, and other regulated stablecoins) maintain on-chain blacklists. An address can be blacklisted after a bridge request is submitted but before operators call `handleERC20Transfer`. This is not a theoretical edge case: Circle has blacklisted thousands of addresses in response to regulatory orders and sanctions. Any user who bridges a blacklistable token to an address that subsequently gets blacklisted — or who bridges KLAY to a contract address that does not accept native transfers — triggers this condition without any malicious intent required.

---

### Recommendation

Adopt a pull-payment (escrow) pattern identical to the Teller fix:

1. On a failed push, store `(nonce → (recipient, amount, token))` in a claimable escrow mapping instead of reverting.
2. Advance `lowerHandleNonce` normally so the bridge pipeline is not blocked.
3. Expose a `claim(nonce)` function that lets the original recipient (or a governance-designated address) withdraw the stuck funds later.

Alternatively, wrap the push in a `try/catch` (Solidity ≥ 0.6) or a low-level call that does not propagate the revert, and emit a `TransferFailed` event so the off-chain system can alert operators.

---

### Proof of Concept

1. Deploy a `Rejector` contract on the destination chain with no payable fallback (or a USDC-blacklisted EOA).
2. On the source chain call `requestKLAYTransfer(rejectorAddress, 1 ether, "")` (or `requestERC20Transfer` with a USDC-like token whose `transfer` reverts for `rejectorAddress`).
3. Operators observe the `RequestValueTransfer` event and call `handleKLAYTransfer(..., rejectorAddress, 1 ether, N, ...)`.
4. The transaction reverts with `"handleKLAYTransfer: transfer failed"`.
5. Repeat step 3 — it always reverts.
6. Query `lowerHandleNonce()`: it remains at `N` forever.
7. Query the source bridge balance: the user's 1 KLAY is permanently locked.
8. No owner function exists to recover the funds or advance the nonce. [6](#0-5) [7](#0-6) [8](#0-7)
