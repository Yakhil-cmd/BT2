### Title
AA response silently drops zero-amount payment outputs while sibling `state`/bookkeeping messages still execute, causing user fund loss without a bounce - (File: aa_composer.js)

### Summary
`aa_composer.js`'s `sendUnit()` post-processing filters out any payment output whose computed `amount` evaluates to `0`, and then removes the entire message if it ends up with no outputs, per-message rather than per-case. If an AA case pairs a `payment` message with sibling `state`/`data` messages that update internal accounting (e.g. decrementing a user's tracked balance) assuming the payment is actually sent, a triggering condition that produces a `0` payout (e.g. rounding, fee subtraction, stale/zero balance) causes the payout to vanish silently while the balance-decrementing bookkeeping still runs — the AA "succeeds" and the user's tracked balance is debited with nothing paid out. This mirrors the reported `PartyGovernanceNFT#rageQuit()` bug, where a zero-value branch bypasses the intended value/amount check, silently causing loss without reverting.

### Finding Description
In `aa_composer.js`, for every `payment` message the composer validates outputs and then strips zero-amount entries: [1](#0-0) 
followed by removing any `payment` message whose `outputs` array became empty: [2](#0-1) 
This filtering/removal is applied per-message. It does not roll back or revert the *sibling* non-payment messages that belong to the same matched `case`/`messages` block (e.g. `app: 'state'` messages that unconditionally subtract the withdrawal amount from a variable-tracked balance, as in the AA scripts under `test/samples/a_bank_without_percent.oscript` and `test/samples/order_book_exchange.oscript`, which pair a `payment` message with a `state` message decrementing `var[$key]` by the same `trigger.data.amount`): [3](#0-2) 
An AA author reasonably assumes that if a payment message is emitted with a positive intended amount, either it is paid or the whole response bounces — there is no engine-level guarantee that a message dropped for having `amount == 0` will also invalidate or roll back sibling bookkeeping messages in the same case. If the computed amount rounds to (or is later reduced to) zero for any reason not re-checked by the AA's own `if` guard (e.g. a race/balance change between guard evaluation and payload composition, or a formula path where a nonzero-looking value truncates to `0` due to integer division inside the formula before reaching the payment message), the withdrawal debit is applied to the user's internal balance while the actual byte/asset transfer silently disappears rather than causing the whole unit response to fail.

This is analogous to the Party bug: there, `amount > 0` gating the `minWithdrawAmounts` check meant a zero balance silently bypassed the revert that should have protected the user, burning their shares for nothing. Here, the engine's own zero-output filtering silently removes the payout while leaving the parallel state-mutation message intact, so the "check" (that a payout occurred) is effectively skipped whenever the amount is zero, and the transaction does not bounce.

### Impact Explanation
Any AA whose withdrawal/payout logic couples a `payment` message with a separate bookkeeping message (a very common oscript pattern, as shown in the bundled sample AAs) is exposed to silent fund loss/freezing for the triggering user whenever the composed payment amount ends up at `0` but a sibling accounting message still executes and reduces the user's recorded balance. This is a genuine AA-fund-loss class issue reachable directly by an ordinary trigger sender simply by calling the AA under conditions that make the computed payout zero, without any privileged access.

### Likelihood Explanation
Likelihood depends on the specific AA's formula design (whether its `if` guard perfectly matches the amount actually placed into the `outputs` array by the time `sendUnit()` composes and filters the payload), but the engine provides no protection or bounce guarantee against this mismatch — it is a structural gap in `aa_composer.js`'s message/output filtering rather than something individual AA authors can defend against without knowledge of this exact composer behavior.

### Recommendation
When a `payment` message is dropped because all of its outputs filtered to zero, the AA response should be treated as invalid/bounced if that message's case also emits other messages, or at minimum the whole case that produced a message with a `0` amount output should bounce rather than silently continue with the remaining messages. Alternatively, `aa_composer.js` should require the AA author's formula to guarantee non-zero amounts by validating at formula-evaluation time (before case messages are finalized) that any payment `amount` field greater than zero as computed in the `if`-condition remains greater than zero in the final composed payload, bouncing otherwise instead of silently filtering the output.

### Proof of Concept
1. Deploy an AA using the withdraw pattern from `test/samples/a_bank_without_percent.oscript`, i.e. a case with a `payment` message paying `trigger.data.amount` and a sibling `state` message decrementing `var[$key]` by `trigger.data.amount`. [4](#0-3) 
2. Construct a trigger/formula path where the `if` guard passes with a nonzero-looking `trigger.data.amount`, but the value used to populate the `payment` message's `outputs[].amount` at composition time is computed as (or rounds to) `0` — e.g. because the amount is derived via a secondary formula/rounding step after the guard check rather than being `trigger.data.amount` directly.
3. Observe that `aa_composer.js` filters the zero-amount output and removes the `payment` message entirely: [5](#0-4) 
4. The remaining `state` message still executes and decrements `var[$key]` by the full intended amount, so the user's internal balance is reduced while they receive nothing, and the AA response unit does not bounce.
