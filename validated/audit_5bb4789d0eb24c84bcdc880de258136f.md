### Title
Unauthenticated `creator` field in `initialize_with_permission` lets a permissioned payer redirect all future creator fees to an attacker-chosen address - (File: `programs/cp-swap/src/instructions/initialize_with_permission.rs`)

### Summary
The `InitializeWithPermission` accounts struct gates *pool creation* behind a `permission` PDA that is derived from and tied only to `payer`, but the separate `creator` field that becomes the permanent fee-recipient of record (`pool_state.pool_creator`) is an `UncheckedAccount` with no signature requirement and no relationship check to `payer` or the `permission` PDA.

### Finding Description
`InitializeWithPermission` declares two independent identities:
- `payer`: `Signer<'info>`, whose key is used to derive the `permission` PDA `[PERMISSION_SEED, payer.key()]` [1](#0-0) , which must have been created in advance by an admin via `create_permission_pda` [2](#0-1) .
- `creator`: declared merely as `/// CHECK: creator of pool` `UncheckedAccount<'info>` with no `Signer`, no `address =`, and no `constraint =` tying it to `payer` or to the `permission` account [3](#0-2) .

In `initialize_with_permission`, the value of `creator` is written straight into permanent on-chain pool state via `pool_state.initialize(..., ctx.accounts.creator.key(), ...)` [4](#0-3) , populating `pool_state.pool_creator`.

That field is later trusted as the sole authorization check in both fee-collection paths:
- `CollectCreatorFee` requires the `creator` signer's address to equal `pool_state.load()?.pool_creator` [5](#0-4) .
- `CollectCreatorFeePermissionless` sends fees to whatever address is recorded as `pool_state.load()?.pool_creator`, with no additional check [6](#0-5) .

Because the "permission" verification only authenticates `payer` (who is legitimately allowed to create a pool), it does nothing to constrain who is recorded as `creator`. Any transaction submitted by a permissioned `payer` can pass an arbitrary `creator` pubkey (attacker-controlled), permanently fixing that arbitrary address as the recipient of all `creator_fees_token_0`/`creator_fees_token_1` accrued by the pool over its lifetime, siphoned via `collect_creator_fee_permissionless` which anyone can call to route funds to the recorded (attacker) address.

This mirrors the CWE-284 (Improper Access Control) pattern in the advisory: the authentication/permission check exists but is bound to the wrong identity, so a legitimate action (pool creation by an approved payer) is silently able to grant a privileged, persistent capability (creator-fee ownership) to an unverified third party.

### Impact Explanation
Since `creator_fees_token_0`/`creator_fees_token_1` accumulate from every swap for the life of the pool [7](#0-6) , an attacker who controls (or colludes with) a permissioned payer can set `creator` to any address they choose, permanently diverting the intended pool creator's fee stream to that address. This is a concrete theft of protocol/LP-adjacent fee revenue and an unauthorized privileged effect (assignment of `pool_creator` rights) — meeting the Medium/High bar for concrete fund diversion.

### Likelihood Explanation
Exploitation requires the ability to submit an `initialize_with_permission` transaction as a `payer` who already holds a valid `permission` PDA. Because permission is admin-granted, this narrows the attacker set to entities the protocol already trusts to create pools, but nothing in the account constraints prevents such a payer (whether malicious or compromised) from naming an unrelated `creator`; there is no on-chain enforcement that `creator == payer` or that `creator` co-signs.

### Recommendation
Add an explicit binding between `payer`/`permission` and `creator` in `InitializeWithPermission`, e.g. require `creator` to be a `Signer` and either equal `payer`, or add a `constraint = permission.authority == creator.key()` check against the `Permission` account so that only the entity the admin actually granted permission to can be recorded as `pool_creator`.

### Proof of Concept
1. Admin runs `create_permission_pda` granting permission to `payer_pubkey` [8](#0-7) .
2. `payer_pubkey` signs and submits `initialize_with_permission` with `creator = attacker_pubkey` (any arbitrary, non-signing pubkey) alongside valid mints/vaults/amm_config.
3. The instruction succeeds; `pool_state.pool_creator` is set to `attacker_pubkey` [4](#0-3) .
4. As the pool accrues `creator_fees_token_0/1` through normal swaps, `attacker_pubkey` (or anyone calling `collect_creator_fee_permissionless` on their behalf) can withdraw all accumulated creator fees to `attacker_pubkey`'s associated token accounts [9](#0-8) , with no way for the intended/legitimate creator to reclaim ownership of that role.
