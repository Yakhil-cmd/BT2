### Title
Missing Cosigner-Membership Check Allows Any Paired Device to Trigger Local Signing Requests for Shared/Multisig Addresses - (File: wallet.js)

### Summary
In `wallet.js`, the `"sign"` case of `handleMessageFromHub` handles a `sign` request received from any correspondent device and, when the target address resolves to a local key (`findAddress` → `ifLocal`), immediately triggers a signing confirmation flow without verifying that the requesting device (`from_address`) is actually a legitimate cosigner of that address's wallet. The check that would enforce this is explicitly commented out.

### Finding Description
`handleMessageFromHub` dispatches the `"sign"` subject to request another device to co-sign a unit for a shared/multisig address [1](#0-0) . After validating message shape, it calls `findAddress(body.address, body.signing_path, ...)`, and in the `ifLocal` branch — reached when the target address's signing key lives on *this* device — it unconditionally proceeds to trigger a "confirm and sign" flow (`eventBus.emit("signing_request", ...)`) for any `from_address` [2](#0-1) .

The code contains an explicit comment acknowledging the missing authorization check:
```
// the commented check would make multilateral signing impossible
//db.query("SELECT 1 FROM extended_pubkeys WHERE wallet=? AND device_address=?", [row.wallet, from_address], function(sender_rows){
//    if (sender_rows.length !== 1)
//        return callbacks.ifError("sender is not cosigner of this address");
``` [3](#0-2) 

Note the contrast with the `ifRemote` branch of the same handler, which *does* enforce that the sender is a listed cosigner (`if (!other_device_addresses.includes(from_address)) return callbacks.ifError(...)`) [4](#0-3) . The `ifLocal` branch has no equivalent check — this is the same class of bug as TastyIgniter's `index_onUpdateStatus()`, which performed a privileged state-changing action without verifying the caller's authorization to do so for that specific resource.

Any device that is merely paired with the victim (a correspondent, which for `"pairing"`, is trivially obtainable and even device addresses that are non-correspondents are allowed for whitelisted subjects such as `"pairing"`) can send a forged `sign` request naming: 
- an arbitrary shared/multisig address for which the victim holds one of several signing keys,
- an arbitrary unsigned unit (payment outputs, asset issuance, AA trigger, etc.),
- and any valid `signing_path` for that address (found by brute-forcing/observing the address's known paths),

and the victim's wallet will process it as if it originated from a legitimate cosigner: it validates the unit via `network.handleOnlineJoint`, and, upon successful validation, fires the `"signing_request"` UI event (or directly proxies through `network.handleOnlineJoint` and later cosigns) with attacker-controlled `unsigned_unit` content and `objAddress` metadata, using `from_address` as the (unverified) claimed requester identity that gets embedded in the confirmation dialog and eventually in the multisig signing / consensus tracking logic [5](#0-4) .

### Impact Explanation
This breaks the access-control invariant for multisig/shared address signing: only members of the shared address's wallet (as tracked in `extended_pubkeys`/`wallet_signing_paths`) should be able to solicit a cosignature from the local device for a given unit. Because the check is disabled, an attacker who is merely paired as any correspondent device (including one whitelisted before being an approved cosigner, e.g. during the `"pairing"`/`"my_xpubkey"` flow) can:
- Spam/spoof signing requests for shared addresses the victim participates in, tricking the victim (via the UI confirmation dialog fed with attacker-supplied `unsigned_unit`/output data) into approving a transaction that spends jointly-controlled funds to attacker-chosen outputs — leading to unauthorized spending of the shared/multisig funds if the user isn't careful reading dialog details, since the request's legitimacy (cosigner membership) is never validated by the wallet backend itself.
- Cause repeated `network.handleOnlineJoint` invocations and `eventBus` emissions with attacker-crafted unit content targeting the victim's shared addresses, undermining the wallet's assumption that only actual cosigners can initiate this flow.

This matches the CWE-285 pattern in the report: a state-changing/security-sensitive action (soliciting a cosignature that can lead to fund movement) is performed without verifying the requester's authorization for the specific resource (the shared address's cosigner set).

### Likelihood Explanation
Likelihood is Medium-High: exploitation only requires the attacker to be a paired device of the victim (correspondent relationship, which is trivial to establish via normal pairing, and even indirect/non-approved correspondents are allowed for some whitelisted subjects) and to know/guess a shared address and signing path the victim participates in (both learnable from prior chat/shared-address exchange messages, e.g. `create_new_shared_address`/`new_shared_address` flows that are exchanged in plaintext between devices). No cryptographic secrets need to be broken; the missing check is a straightforward logic omission, not a hardened control.

### Recommendation
Restore (in a way compatible with multilateral signing) the authorization check that verifies `from_address` is actually one of the recognized signers/cosigners for `body.address` (via `extended_pubkeys`/`wallet_signing_paths` for wallet-based addresses, or `shared_address_signing_paths`/`peer_addresses` for shared/peer addresses) before proceeding to raise a `signing_request` in the `ifLocal` branch. If multilateral signing intentionally allows non-cosigner counterparties to request signatures (e.g., for contract flows), scope the exemption narrowly (e.g., only for peer/contract addresses) rather than removing the check for all local signing paths, and ensure the emitted confirmation UI clearly and unambiguously identifies the unverified requester so users cannot be tricked into approving fund transfers based on forged sender identity.

### Proof of Concept
1. Attacker device pairs with victim device (or is already an indirect correspondent, e.g. via a shared-address negotiation) so that `handleMessageFromHub` accepts messages from `from_address` = attacker device address.
2. Attacker learns (via prior exchanged shared-address setup messages, or by observation) a shared/multisig `address` and a valid `signing_path` on which the victim's device is one of several key-holding cosigners, but the attacker is not actually a cosigner (or is a cosigner for a different, unrelated shared address controlled separately).
3. Attacker sends a device message with `subject: "sign"`, `body: {address: <shared_address>, signing_path: <path>, unsigned_unit: <attacker-crafted unit spending shared funds to attacker address>}`.
4. Victim's `handleMessageFromHub` reaches the `"sign"` case, calls `findAddress`, which resolves to `ifLocal` (since victim holds the local key at that path), and — because the cosigner-membership check is commented out — immediately validates the unit and fires `signing_request`, prompting the victim to sign a transaction whose legitimacy as "from a cosigner" was never verified by the backend [6](#0-5) .
