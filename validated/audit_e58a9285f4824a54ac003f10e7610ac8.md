### Title
CCMenu API endpoint bypasses ApiClient stack scoping via `Stack.from_param!` instead of `stacks.from_param!` - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Api::CCMenuController#stack` overrides `Api::BaseController#stack` and calls `Stack.from_param!(params[:stack_id])` directly on the unscoped `Stack` model, rather than the scoped `stacks.from_param!(params[:stack_id])` inherited from `BaseController`. This means an `ApiClient` token bound to a single stack (via `stack_id`) with only the `read:stack` permission can be used to fetch CCMenu XML for any stack on the Shipit instance, not just the one it is scoped to.

### Finding Description
The broken binding: `current_api_client.stack_id == A` must equal the id of the stack actually rendered by `show`, but the code allows rendering for any `B`.

- `BaseController#stacks` correctly scopes lookups: `current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all` [1](#0-0) , and `BaseController#stack` uses that scope: `@stack ||= stacks.from_param!(params[:stack_id])` [2](#0-1) .
- `CCMenuController` overrides `stack` to bypass this scope entirely: `@stack ||= Stack.from_param!(params[:stack_id])` [3](#0-2) .
- The only permission check performed is `require_permission :read, :stack` [4](#0-3) , which calls `current_api_client.check_permissions!(operation, scope)` — this checks only that the string `"read:stack"` is present in the token's `permissions` array; it never compares `stack_id` to the requested stack [5](#0-4) .
- `ApiClient.authenticate` just verifies the signed token and loads the `ApiClient` record by id; it performs no stack binding check either [6](#0-5) .

Exploit flow: given `ApiClient` with `stack_id = A.id`, `permissions = ['read:stack']`, and its valid token, an attacker (or any party with such a legitimately-scoped token) sends `GET /api/stacks/B/ccmenu.xml?token=<token>`. `CCMenuController#authenticate_api_client` authenticates the client via the token [7](#0-6) , the `read:stack` permission check passes (it's stack-agnostic), and `stack` resolves `params[:stack_id]` = B against the entire `Stack` table, returning stack B's record regardless of the token's `stack_id`. The `show` action then renders `shipit/ccmenu/project.xml.builder` with stack B's deploy/task data [8](#0-7) .

None of the listed guards catch this: `require_permission!`/`check_permissions!` only validates the operation:scope string, not stack ownership; there is no `stacks` scope usage in this controller at all since it defines its own `stack` method that shadows the inherited scoped one.

### Impact Explanation
Any holder of a valid `read:stack` `ApiClient` token scoped to one stack can read CCMenu status/build data (last deploy, activity, lock status, running task info) for **any** other stack in the installation, purely by changing the `stack_id` route parameter. This is a cross-tenant/cross-stack information disclosure of deploy/task state — matching the "unauthenticated read of stack state" High-severity category in spirit, but here it's actually an authorization-scope-bypass read of stack state by an out-of-scope authenticated token. It's fully repeatable against arbitrary stack ids on the same Shipit instance.

### Likelihood Explanation
Requires only a valid `ApiClient` token with `read:stack` permission scoped to any single stack (a common, low-privilege configuration for CI dashboards etc.) — no other secret or elevated permission required. Attacker cost is a single HTTP GET, trivially repeatable and enumerable across stack ids/slugs.

### Recommendation
Remove the `stack` override in `Api::CCMenuController` and rely on `BaseController#stack` (i.e., `stacks.from_param!(params[:stack_id])`), so the lookup is scoped by `current_api_client.stack_id` exactly like every other API controller in the codebase.

### Proof of Concept
In `test/controllers/api/ccmenu_controller_test.rb` (or a new integration test), following the existing `ApiControllerTestCase` pattern used in this file:
1. Create `stack_a` and `stack_b` (e.g. two distinct `Stack` fixtures/records).
2. Create an `ApiClient` with `stack_id: stack_a.id`, `permissions: ['read:stack']`, and obtain `client.authentication_token`.
3. `get :show, params: { stack_id: stack_b.to_param, token: client.authentication_token }`.
4. Assert `response.status == 200` and that the rendered XML's `name`/project data corresponds to `stack_b` (e.g. `assert_payload('name', stack_b.to_param)`), proving the token scoped to `stack_a` (`current_api_client.stack_id == stack_a.id`) was used to read `stack_b`'s data (`stack_b.id != stack_a.id`), i.e. the binding `current_api_client.stack_id == rendered_stack.id` is violated.
