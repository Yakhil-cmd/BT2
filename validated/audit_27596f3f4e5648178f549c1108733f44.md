### Title
Permanent liquidation/refund denial for AA-managed assets whose transfer condition blocks a specific recipient (`spender_attested` / `transfer_condition`) - (File: `aa_composer.js`, `validation.js`)

### Summary
An Autonomous Agent (AA) that pays out funds in a custom asset with a `transfer_condition` or `spender_attested` restriction (Obyte's analog of a token "blacklist"/whitelist) can become permanently unable to complete any operation that must send that asset to a specific address once that address fails the asset's condition. Because AA response construction is all-or-nothing (any failing output causes the whole trigger to `bounce`), this reproduces the same failure pattern described in the external report: the state-changing operation (e.g. "unregister/liquidate a position") and the "push" of resulting funds are coupled in one atomic step with no fallback ("pull") path, so a single unspendable output permanently blocks the entire operation for that address.

### Finding Description
In `aa_composer.js`, when an AA finishes evaluating its oscript and builds outgoing payment messages, `sendUnit()` validates and completes each output address [1](#0-0) , then finally builds and validates the response unit through `validateAndSaveUnit()`: [2](#0-1) 

If `validation.validate()` returns `ifUnitError`, the composer immediately calls `bounce(err)` [3](#0-2) . This is the **only** recovery path — there is no way to send a *smaller* or *zero* amount, or to let the recipient later "claim" the funds; the AA must push the exact computed output to the address in the same unit, or the whole trigger fails.

The `bounce()` function then discards all state changes accumulated by the AA for this trigger (they were never persisted, since `saveStateVars()`/`addResponse()` only run on success) and only refunds the trigger's own incoming payment, not the asset the AA was trying to pay out: [4](#0-3) 

The trigger for the failing output can be a payment in a custom asset whose transferability is gated by `spender_attested` (an attestor allow-list) or an arbitrary `transfer_condition` oscript expression, which is exactly the analog of a centralized token's transfer-blocking/blacklist logic: [5](#0-4) 

These conditions are declared and validated when the asset is defined (`aa_validation.js`/`validation.js`) and can reference attestor lists or arbitrary boolean logic evaluated per spend: [6](#0-5) 

Because an asset's attestor list can be updated post-issuance via an `asset_attestors` message, or the `transfer_condition` can encode any denylist-like rule, a specific trader/user address can lose the ability to receive that asset at any time after a position was opened. If an AA (e.g. a lending/perpetuals/vault protocol built on top of ocore) must push residual collateral to that address as part of unwinding/liquidating a position, `validateAndSaveUnit` will fail every single time this operation is attempted (by anyone posting the trigger), and `bounce()` will unwind the whole operation, leaving the position/state exactly as before.

### Impact Explanation
Any protocol AA that combines "close/liquidate position" state logic with a mandatory payout of a conditioned/attested asset to the counterparty address is affected. Once that address is excluded from the asset's condition (attestor removed, or condition logic denies it), the entire liquidation/closing trigger deterministically bounces, forever:
- The position can never be liquidated/closed through the normal path (no partial success, no "claim later" fallback exists in the composer).
- Collateral/backing for that position remains locked inside the AA, and the position can keep accruing further losses to the protocol/other users, matching the reported impact of undercollateralized/unliquidatable positions causing losses to the protocol.
- This is a general architecture-level footgun for exactly the class of assets ocore explicitly supports (`spender_attested`, `transfer_condition`), i.e. it is reachable by any AA author using standard, documented asset features, and triggerable by any unprivileged user who can influence which address becomes non-compliant (e.g. an attestor removing an address, or a condition depending on public on-chain state).

### Likelihood Explanation
Likelihood is low-to-moderate: it requires (a) an AA-based financial protocol that pays a `spender_attested`/`transfer_condition`-gated asset back to counterparty addresses as part of a liquidation/close flow, and (b) that a specific counterparty's address becomes non-compliant with the asset condition after entering the position (attestor revocation or condition change). Both are realistic designs given ocore's stated purpose for such assets (compliance-gated stablecoins, KYC/attestation-gated tokens), which is precisely why `spender_attested` and `transfer_condition` exist.

### Recommendation
- Avoid making a single atomic unit responsible for both the irreversible state transition (e.g., marking a position liquidated) and the mandatory push-payment to a possibly-restricted asset recipient.
- Allow AAs to first perform the state transition and credit an internal, pull-based balance for the trader (a `pull` claim variable), with a separate, later message/trigger that the trader (or anyone) can call to withdraw once/if the transfer condition is satisfied again, mirroring the "pull over push" recommendation from the original report.
- Where residual payouts must be pushed in a conditioned asset, consider redirecting the payout to a fallback/insurance address when the primary recipient's output fails validation, rather than allowing the whole trigger (including position state changes) to bounce.

### Proof of Concept
1. Definer issues asset `A` with `spender_attested: true` and an attestor list including trader `T`.
2. AA `L` (e.g. a leveraged-trading/lending AA) opens a position for `T`, collateralized in asset `A`, tracked in AA state vars.
3. Definer (or an authorized attestor) removes `T` from `A`'s attestor list via an `asset_attestors` update message (`validateAttestorListUpdate` in `validation.js`, lines 2829-2848).
4. Any user posts a liquidation trigger to `L` for `T`'s position. `L`'s oscript computes the state change (mark position closed/liquidated) and a payment message sending remaining collateral in asset `A` back to `T`.
5. In `sendUnit()`, `completePaymentPayload`/`validateAndSaveUnit` evaluates `validatePaymentInputsAndOutputs`, and because `T` is no longer in `objAsset.arrAttestedAddresses`, it fails with `"some output addresses are not attested"` (`validation.js`, lines 2634-2641).
6. `validateAndSaveUnit`'s `ifUnitError` triggers `bounce(err)` (`aa_composer.js`, lines 1405-1410); the whole response — including the liquidation state change — is discarded, and only the trigger's own incoming payment (if any, in bytes) is refunded.
7. Every subsequent liquidation attempt for `T`'s position bounces identically as long as `T` remains unattested/blocked by `A`'s condition, permanently preventing liquidation while the position (and any bad debt) persists on `L`.
