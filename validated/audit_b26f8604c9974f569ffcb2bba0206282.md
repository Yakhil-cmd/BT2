### Title
Cross-organization webhook forgery via decoupled signature-verification identity and payload-acted-upon identity - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/status_handler.rb`, `app/models/shipit/webhooks/handlers/handler.rb`)

### Summary
`WebhooksController#verify_signature` selects the GitHub App / `webhook_secret` used to validate the HMAC signature based on `repository_owner`, a field read straight out of the *unverified* JSON body (`params.dig('repository', 'owner', 'login')` or `organization.login`). Once the signature check passes, every webhook handler acts on a completely different field of that same, attacker-influenced body — `repository.full_name` (used by `Handler#stacks`/`#repository_name`) or, in the case of `StatusHandler`, no repository field at all, just a global `Commit.where(sha: params.sha)` lookup. Because Shipit supports multiple independently configured GitHub organizations (each with its own `webhook_secret`, per `docs/setup.md` "Using Multiple Github Applications"), anyone who legitimately controls one configured organization's GitHub App can compute a valid HMAC for an arbitrary payload using their own known secret, set `repository.owner.login`/`organization.login` to their own org (so it authenticates), but set `repository.full_name` / commit `sha` to point at a stack or commit belonging to a *different, victim* organization/repository tracked by the same Shipit instance.

### Finding Description
- `app/controllers/shipit/webhooks_controller.rb` lines 24-30 pick the signing secret via `repository_owner`: [1](#0-0) 
  `repository_owner` itself comes from the raw, unauthenticated body: [2](#0-1) 
- `verify_webhook_signature` only checks that the whole raw body is signed by *some* configured org's secret — it has no way to know that the org whose secret matched is actually the owner of the repository referenced deeper in the payload: [3](#0-2) 
- Handlers then key off a **different** field of the same body to decide what to mutate. `Handler#stacks`/`#repository_name` uses `payload.dig('repository', 'full_name')`: [4](#0-3) 
- `PushHandler#process` uses that repository-derived `stacks` scope to force-sync arbitrary commits into tracked stacks: [5](#0-4) 
- `StatusHandler#process` is even less scoped — it doesn't consult `repository` at all, just matches globally by SHA across the entire Shipit installation: [6](#0-5) 

The binding that should hold is: `organization that authenticated the request == organization owning the resource the handler mutates`. It does not — the verified identity is `repository_owner` (org A, whoever's secret matched), while the mutated identity is `repository.full_name` / commit `sha` (any org/commit chosen by the payload author). Anyone administering one legitimately configured GitHub App/org in a multi-org Shipit deployment can therefore forge signed webhooks that mutate state belonging to any other org/repo/stack tracked by the same instance.

### Impact Explanation
This breaks a repository/organization trust boundary between tenants of the same Shipit instance: an entity that only controls one configured GitHub organization (and therefore only its own `webhook_secret`) can forge validly-signed `push`, `status`, `check_suite`, `membership`, and `pull_request` events naming a victim organization's repository or an arbitrary commit `sha`. Concretely:
- `push` events can force `GithubSyncJob` to run against a victim's tracked `Stack` with an attacker-chosen `expected_head_sha`.
- `status` events can set/forge CI status (`state`, `context`, `target_url`, `description`) on **any** commit tracked anywhere in the instance, regardless of which org actually owns it, potentially unblocking a merge/deploy that is gated on CI status.
- `membership` events let the forger add/remove arbitrary GitHub users from `Shipit.github_teams`-backed `Team`/`Membership` records tied to a different org, since `MembershipHandler` also trusts the unauthenticated `organization.login`/`team` fields once the "matching" secret is found.

This crosses into unauthorized deploy/merge-gating manipulation and unauthorized cross-repository writes, matching the High/Critical impact classes defined for this engine (escalation into `Shipit.github_teams` authorization, and unauthorized deploy/merge via forged CI status).

### Likelihood Explanation
Requires only that the Shipit installation be configured for multiple GitHub organizations (an explicitly documented, supported configuration in `docs/setup.md`), and that the attacker legitimately administers one of them (their own GitHub App and its `webhook_secret`) — no Shipit session, `ApiClient` token, or access to the victim org's credentials is needed. This satisfies the "unprivileged attacker" bar defined in scope, since the attacker never needs privileged access to the victim's resources, only to their own, separately configured org.

### Recommendation
Bind the identity used for signature verification to the identity acted upon:
- After signature verification succeeds for org A, re-derive `repository.full_name`'s owner and require it to equal the verified `repository_owner`/`organization.login`; reject (422) on mismatch.
- In `StatusHandler`, scope `Commit.where(sha: params.sha)` additionally by the commit's `stack.repository.owner` matching the verified `repository_owner`, instead of matching globally by SHA.
- In `MembershipHandler`, verify `params.organization.login` matches the org whose secret validated the signature before creating/mutating `Team`/`Membership` records.

### Proof of Concept
1. Shipit is configured with two GitHub orgs, `attacker-org` (attacker's own GitHub App, secret known to the attacker) and `victim-org` (a separate tracked org/repo), per the documented multi-org `secrets.yml` format.
2. Attacker crafts a JSON body:
   ```json
   {
     "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" },
     "ref": "refs/heads/master",
     "after": "<attacker-chosen sha>"
   }
   ```
3. Attacker computes `sha1=HMAC(attacker_webhook_secret, body)` and POSTs to `/webhooks` with `X-Github-Event: push` and the computed `X-Hub-Signature`.
4. `verify_signature` resolves `repository_owner` to `attacker-org`, fetches `attacker-org`'s `webhook_secret`, and the signature validates because the attacker signed with their own known secret.
5. `PushHandler#process` resolves stacks via `repository.full_name = "victim-org/victim-repo"` and calls `stack.sync_github(expected_head_sha: "<attacker-chosen sha>")` on the victim's stack — mutating state the attacker was never authorized to touch.

**Uncertainty note:** I could not fully trace `Commit#create_status_from_github!` and downstream merge/deploy-gating logic within the remaining tool budget to confirm the exact conditions under which a forged `status` event unlocks a deploy/merge (e.g., required-status-check enforcement in `MergeRequest`/`Stack`). The forgery of the webhook signature binding itself, however, is confirmed directly from `webhooks_controller.rb`, `github_app.rb`, `handler.rb`, `push_handler.rb`, and `status_handler.rb`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
