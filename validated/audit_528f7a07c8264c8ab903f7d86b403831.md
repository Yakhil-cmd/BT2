### Title
Webhook Signature Verified Against `repository.owner.login` While All Handlers Act On The Unverified `repository.full_name` — Cross-Organization / Cross-Repository Writes - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the HMAC secret used to authenticate an inbound GitHub webhook using `repository.owner.login` (or `organization.login`), but every webhook handler that actually mutates data (push syncs, commit statuses, pull-request/review-stack state, merges) resolves its target `Stack`/`Repository` using the completely separate `repository.full_name` field from the same JSON body. Because these two payload fields are never cross-checked against each other, a party who legitimately knows the webhook secret for *one* organization configured in Shipit can forge a signature with that secret while pointing `repository.full_name` at a *different* organization's repository, causing Shipit to accept and process the payload as if it came from the victim repository's GitHub App.

### Finding Description
The signature check is: [1](#0-0) [2](#0-1) 

`verify_signature` calls `Shipit.github(organization: repository_owner)` and verifies the raw body's HMAC against **that organization's** `webhook_secret`, per `verify_webhook_signature`: [3](#0-2) 

`Shipit.github(organization:)` looks up per-organization credentials, and the codebase explicitly supports multiple simultaneously-configured GitHub organizations/apps, each with its own independent `webhook_secret`, as shown in the fixture configuration: [4](#0-3) 

Once the signature check passes (based on `repository.owner.login`), the request is dispatched to handlers via `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`: [5](#0-4) 

Every handler resolves its target repository/stack using a *different* field, `repository.full_name`, not `repository.owner.login`: [6](#0-5) 

For example, `PushHandler` finds and syncs any not-archived stack whose `Repository.from_github_repo_name(repository.full_name)` matches, entirely independent of which organization's secret validated the request: [7](#0-6) 

The same pattern (`Repository.from_github_repo_name(params.repository.full_name)`) is used across all pull-request/review-stack handlers: [8](#0-7) , [9](#0-8) , and the `status` handler builds a `Commit#statuses` record directly from unverified payload fields (`sha`, `state`, `target_url`, `description`, `context`, `created_at`) as evidenced by its test: [10](#0-9) 

**The broken binding, stated as an equality that the code assumes but never enforces:**
`organization_that_authenticated (repository.owner.login) == organization_of_repository_that_is_written (repository.full_name's owner)`

Before an attacker's request: for legitimate webhooks delivered by GitHub, these two fields always describe the same repository, so the equality holds incidentally (not because the code checks it).

After an attacker's crafted request: an attacker who operates (or has been granted webhook credentials for) **any one** organization/repository registered in a multi-tenant Shipit deployment can submit a raw HTTP POST directly to `/github/webhooks` (this endpoint requires no session, no `ApiClient` token, only knowledge of a valid `X-Hub-Signature` computed from a webhook secret they legitimately possess for their own org) with:
- `repository.owner.login = "AttackerOrg"` (or `organization.login`), so `verify_signature` selects and validates against AttackerOrg's known secret — passes.
- `repository.full_name = "VictimOrg/victim-repo"` — a stack tracked under a different, unrelated organization.

Because no handler ever compares `repository.owner.login` to the owner segment of `repository.full_name`, the payload is processed against the victim's `Stack`/`Repository`/`Commit` records.

### Impact Explanation
This breaks the cross-repository isolation that Shipit's multi-organization webhook design is supposed to provide. Depending on event type, this enables:
- Forged commit statuses on a victim repository's commits (`status` event), which can flip `deployable?`/CI-gating checks used to allow deploys.
- Forged `push` events causing `GithubSyncJob`s to run against a victim stack with an attacker-chosen `expected_head_sha`.
- Manipulation of pull-request/review-stack lifecycle state (archive/unarchive, label captures) for a victim's review stacks.

These are cross-repository writes performed by a party who has no privilege on the victim repository/organization — matching the "cross-repository writes" / "unauthorized deploy" impact bar.

### Likelihood Explanation
Requires the attacker to control (or have configured) a legitimate webhook secret for *some* organization onboarded to the same Shipit instance — a low bar for large multi-tenant Shipit deployments where many independent teams/orgs each register their own GitHub App/webhook secret, and none of them are meant to trust each other. No GitHub org membership, Shipit session, or `ApiClient` token for the *victim* org is required — only the ability to send a raw HTTP POST with a body they fully control and a valid signature computed from a secret that is entirely under the attacker's own knowledge/control.

### Recommendation
After selecting the authenticating organization via `repository.owner.login`/`organization.login`, every handler (or a single point in `WebhooksController`) must verify that the resolved target `Repository`'s owner matches the organization that produced a valid signature, e.g. reject the webhook if `Repository.from_github_repo_name(payload.dig('repository','full_name'))&.owner != repository_owner`, before dispatching to any handler.

### Proof of Concept
1. Shipit is configured (as in `test/dummy/config/secrets_double_github_app.yml`) with two organizations, `OrgOne` (secret `S1`) and `OrgTwo` (secret `S2`), each with stacks tracked in Shipit.
2. An attacker who administers `OrgTwo` (and therefore knows `S2`, since they configured GitHub's webhook delivery for their own repos) crafts a JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "deadbeefdeadbeefdeadbeefdeadbeefdeadbeef",
  "repository": {
    "owner": { "login": "OrgTwo" },
    "full_name": "OrgOne/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<hmac-sha1(S2, body)>` and POSTs to `/github/webhooks` with `X-Github-Event: push`.
4. `verify_signature` resolves `repository_owner` to `OrgTwo`, fetches `S2`, and the signature validates successfully.
5. `PushHandler#stacks` resolves `Repository.from_github_repo_name("OrgOne/victim-repo")`, finds the matching stack owned by `OrgOne`, and enqueues `GithubSyncJob` for it — despite the request only being authenticated as belonging to `OrgTwo`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
