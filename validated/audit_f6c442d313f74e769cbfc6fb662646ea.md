`SeizeMode::Credit` persists a stale pre-liquidation snapshot when the receiver is the liquidated account, resurrecting seized collateral - (File: contracts/controller/src/positions/liquidation/mod.rs)

### Summary
In `process_liquidation`, the `SeizeMode::Credit` receiver account is loaded once, **before** any repayment or seizure is applied (`resolve_seize_receiver`, mod.rs:53-55). The liquidated `account` is then mutated and persisted; afterwards the receiver's `receiving_account` snapshot — captured pre-seizure — is written back via `record_share_credit_updates` and `finalize_position_flow(..., PositionSides::Supply)` (mod.rs:123-133). If the receiver resolves to the same `account_id` being liquidated, that stale `supply_positions` map overwrites the post-seizure map, restoring collateral that was already burned/seized.

### Finding Description
The flow order in `process_liquidation` is:

1. `storage::get_account(env, account_id)` loads the victim's positions (mod.rs:46).
2. `resolve_seize_receiver` loads `receiving_account` — a **second, independent in-memory snapshot** of the receiver's supply positions (mod.rs:53-55).
3. `apply_liquidation_seizures` / `apply_liquidation_share_credit` burn seized shares out of `account` and credit shares into `receiving_account` (mod.rs:82-92).
4. `finalize_position_flow(env, account_id, &account, PositionSides::Both, ...)` persists the victim's post-seizure maps (mod.rs:114-121).
5. `record_share_credit_updates` + `finalize_position_flow(env, *receiver_id, receiving_account, PositionSides::Supply, ...)` then writes `receiving_account.supply_positions` to the **same storage key** `SupplyPositions(account_id)` (mod.rs:123-133).

When `receiver_id == account_id`, step 5 overwrites the post-seizure supply map with the pre-seizure map plus the credited seized shares. The shares that were burned in step 3 reappear. This is the direct analog of the kernel bug: a reference (`receiving_account`) is held across a mutation that "reaps" state (share burn), then the stale copy is dereferenced and committed.

I could not confirm within the available iterations whether `resolve_seize_receiver` rejects `receiver_id == account_id`; the shown code in mod.rs contains no such check, and `require_credit_position_limit` only bounds new-asset positions, not identity. If no guard exists, `liquidate(liquidator, account_id, payments, SeizeMode::Credit(account_id))` is reachable by any address since liquidation is permissionless.

### Impact Explanation
Resurrected supply shares are backed by nothing — the underlying collateral was already transferred or credited as fee/seized value. The victim account (whose NFT the liquidator need not own to trigger) ends up with unbacked supply shares it can withdraw, draining real pool cash. That is theft of supplier funds / protocol insolvency.

### Likelihood Explanation
Requires only a permissionless `liquidate` call on any account holding collateral and debt, with `SeizeMode::Credit(<same account_id>)` — a single unprivileged transaction. Preconditions: receiver resolution must accept the liquidated account's own id, and the account must survive (non-empty positions) so the later `check_bad_debt_after_liquidation` cleanup at mod.rs:135 does not delete the overwritten map.

### Recommendation
- In `resolve_seize_receiver`, reject `receiver_id == account_id` for `SeizeMode::Credit`, or
- Reload the receiver's supply positions from storage immediately before `apply_liquidation_share_credit`/`finalize_position_flow` instead of reusing the snapshot taken at step 2, so the write always merges into current state.

### Proof of Concept
1. Victim account `V` holds supply `S` (USDC) and debt `D` (ETH), liquidatable.
2. Liquidator calls `liquidate(liquidator, V, debt_payments=[(ETH, x)], SeizeMode::Credit(V))`.
3. `receiving_account` snapshot = `S` at load; `account` snapshot = `S`.
4. Seizure burns `s` shares from `account` → persisted as `S − s`; `s` (minus fee) credited into `receiving_account` → its map is `S + s_credit`.
5. Receiver finalize writes `SupplyPositions(V) = S + s_credit`, overwriting `S − s`. Net effect: victim keeps nearly all collateral plus the credited shares; the debt repayment was collected but collateral was never actually removed.
