Based on my investigation, I found a real analog to CVE-2017-1000135 in `pallet-people`'s account-linked authentication paths, but I was unable to fully verify the precise block-level timing gap because I ran out of iterations. I present the finding with that caveat.

### Title
Suspended person can still authenticate as `PersonalIdentity`/`PersonalAlias` origin via account link until `remove_suspended_keys` runs - (File: `substrate/frame/people/src/extension.rs`)

### Summary
`pallet-people` lets an account "log in" as a `PersonalIdentity` or `PersonalAlias` origin via a lightweight signed extrinsic (nonce-based) once the account has been linked with `set_alias_account`/`set_personal_id_account`. When a person is suspended (`suspend_personhood`), their ring record is marked `RingPosition::Suspended` immediately, but the `AccountToPersonalId`/`AccountToAlias` lookup maps used by the transaction extension are only cleared later, in `remove_suspended_keys`, a separate call invoked after `end_people_set_mutation_session`/`migrate_keys`. The extension's `validate()` never checks the person's suspension state — analogous to Mahara's stale institution-suspension session bug.

### Finding Description
In `AsPerson::validate` (`substrate/frame/people/src/extension.rs:173-190`), the `AsPersonalIdentityWithAccount` branch only checks: [1](#0-0) 
```
let id = AccountToPersonalId::<T>::get(&who).ok_or(InvalidTransaction::BadSigner)?;
let local_origin = Origin::PersonalIdentity(id);
```
There is no lookup of `People::<T>::get(id).position` to reject suspended persons — contrast this with `migrate_included_key`, which explicitly checks for `Error::<T>::Suspended` (see `substrate/frame/people/src/tests.rs:1296-1323`) [2](#0-1) .

The `suspending_person_removes_associated_data` test shows the ordering of state transitions: [3](#0-2) 
1. `suspend_personhood(&[person_id])` marks the record `Suspended` and queues it for ring removal.
2. `end_people_set_mutation_session()` / `migrate_keys()` process the ring mutation.
3. Only `remove_suspended_keys(RI_ZERO)` actually purges `AccountToPersonalId` for that person — after which the account-based `AsPerson` extension correctly returns `InvalidTransaction::BadSigner`.

Between steps 1 and 3, `AccountToPersonalId` (or `AccountToAlias`, which additionally only checks `ring.revision` matches, unrelated to suspension) still resolves to the suspended person, so the linked account origin conversion in `validate()` succeeds and the extrinsic dispatches with `Origin::PersonalIdentity(id)`/`Origin::PersonalAlias(...)` despite the underlying person being suspended.

### Impact Explanation
Other pallets/consumers of `PeopleOrigin::PersonalIdentity`/`PersonalAlias` (e.g. proof-of-unique-personhood gated dispatchables, sybil-resistant governance/airdrop logic) rely on the invariant that only currently-valid (non-suspended) persons can act under that origin. A person suspended for misbehavior (e.g., detected duplicate/sybil) retains the ability to act with that origin for an unknown/attacker-uncontrolled window until the asynchronous `remove_suspended_keys` housekeeping call executes, undermining the uniqueness/suspension guarantee the whole pallet is built to provide.

### Likelihood Explanation
Likelihood depends entirely on how quickly `remove_suspended_keys` runs after suspension in the deployed runtime — I could not determine from available code whether this is called in the same block as `suspend_personhood`/`migrate_keys` or deferred over multiple blocks via the `WeightMeter`-based migration seen in `migrate_keys(&mut meter)`. If deferred (which the API shape — taking a `WeightMeter` and being callable per-ring — strongly suggests it's designed to be), the exposure window is real and requires no attacker privilege: the suspended individual simply needs their previously-linked account key, which they already legitimately possess.

### Recommendation
In `AsPerson::validate` (`substrate/frame/people/src/extension.rs`), for both `AsPersonalIdentityWithAccount` and `AsPersonalAliasWithAccount` branches, explicitly check that the resolved person's `RingPosition` is not `Suspended` (mirroring the check already done in `migrate_included_key`) before converting the origin, rather than relying solely on the lazy removal of `AccountToPersonalId`/`AccountToAlias` performed by `remove_suspended_keys`.

### Proof of Concept
I was not able to execute a reproduction within this investigation (no terminal/test-execution tool available in this session); this is a static-analysis finding based on `substrate/frame/people/src/extension.rs` and `substrate/frame/people/src/tests.rs`. A concrete reproduction would extend `suspending_person_removes_associated_data` to attempt the `AsPerson` account-based dispatch (as in `suspending_person_removes_associated_data`'s `exec_tx` call) **between** `PeoplePallet::suspend_personhood(...)` and `PeoplePallet::remove_suspended_keys(...)` (i.e., skip the removal step) and assert that it currently succeeds rather than failing with `InvalidTransaction::BadSigner`. I did not run this reproduction, so I cannot confirm actual pass/fail results — this should be verified with a background Devin session that has Rust/cargo test execution access before relying on this as confirmed exploitable.
