### Title
Uncaught exception in AA trigger processing crashes the whole node process (`network.js` global `uncaughtException` handler) - ([File: network.js])

### Summary
The Open vSwitch CVE describes a crash/DoS: a specially crafted, malformed metadata field (Geneve TLV options) reaches a code path that is not exercised by the normal, well-tested packet pipeline (the netlink hardware-offload path) and causes an invalid memory access that the process cannot recover from. The structural analog in `ocore--012` is a code path that is likewise less rigorously validated than the main "must not throw" unit-validation pipeline — AA trigger execution (`aa_composer.js`) — where a `throw Error(...)` (as opposed to returning an error through the callback chain) can escape all the way to Node's `process.on('uncaughtException')` handler in `network.js`, which deliberately re-throws to crash the whole process.

### Finding Description
Normal unit validation in `validation.js` is written so that essentially all error conditions are reported through callbacks (`callbacks.ifUnitError`, `ifJointError`, etc.) rather than by throwing, precisely because a thrown exception is fatal to the process [1](#0-0) . That handler explicitly says: *"crash the process to avoid ending up in an inconsistent state"* — i.e., any uncaught exception anywhere in the unit-processing call graph brings the whole node down.

However, `aa_composer.js`, which executes AA (Autonomous Agent) triggers on data supplied entirely by unprivileged unit posters (via `trigger.data`, `trigger.outputs`, formula parameters, etc.), contains numerous `throw Error(...)` statements executed synchronously in the handler chain instead of being routed through `bounce()`/`onDone(err)`, e.g. in `getTrigger()`: [2](#0-1) 
and multiple invariant checks inside `handleTrigger` (e.g. `template.base_aa` handling, `arrDefinition[0] !== 'autonomous agent'`, `assocBalances`/`bAir` mismatch checks) at [3](#0-2) ,
plus similar `throw Error` invariant checks deep inside `formula/evaluation.js`'s `evaluate()` (e.g. line 94-98, 1395) that are reached while evaluating attacker-supplied formulas/state during AA execution [4](#0-3) [5](#0-4) .

Crucially, the codebase itself acknowledges this class of risk: when receiving a new unit whose output triggers an AA, the code proactively performs a synchronous *dry run* specifically to surface such crashes early, with the comment "if it would crash, let it crash now, not when we execute the trigger for real": [6](#0-5) 
which calls `aa_composer.getTrigger()` and `aa_composer.dryRunPrimaryAATrigger()` [7](#0-6) .
This defensive dry-run only covers `conf.bDryRunNewTriggers` and only for *new, non-ball* units seen live; it does not cover every code path (e.g. `light/dry_run_aa` request handling still calls `dryRunPrimaryAATrigger` directly and any thrown error there is likewise uncaught) [8](#0-7) , nor does it protect the real execution during main-chain stabilization/catch-up, where triggers are executed for real via `writer.saveJoint`/`main_chain` processing without a preceding dry run.

Formula *validation* (`formula/validation.js`) is meant to reject any AST that would trigger these invariant violations at evaluation time, but as the AA formula language is large (dictionaries, arrays, `var`/`balance` selectors, `local_var_assignment`, remote AA calls, `reduce`/`map`/`filter`, parameterized/base AAs, etc.), a gap between what the validator accepts and what the evaluator can safely handle is a realistic and recurring bug class in this codebase (the numerous "message ... invalid" / edge-case tests around state var/local var assignment, e.g. `test/aa_composer.test.js:1827-1881`, `test/formula.test.js:4396-4435`, show the validator/evaluator boundary is delicate and has previously required patching).

### Impact Explanation
If any attacker (an ordinary user posting a unit with an output to an AA address, or a light client sending a `light/dry_run_aa`/`light/get_aa_state_vars` request) can construct a trigger/formula input that reaches one of these `throw Error(...)` invariant checks instead of being caught earlier by formula validation, the thrown exception propagates out of the async callback chain uncaught, is caught only by the global `process.on('uncaughtException')` handler in `network.js`, and that handler re-throws to **crash the entire ocore process**. Since AA execution occurs as part of consensus-relevant unit processing (stabilizing the main chain, computing AA responses that are also part of consensus-critical hash state), a reliably reproducible crash trigger can be broadcast to every full node running the same code, taking the whole network offline simultaneously (a network unable to confirm new units) until node operators manually restart — directly matching the "network unable to confirm new units" acceptance criterion, and structurally analogous to the OVS bug where a single crafted packet made `ovs-vswitchd` fail to recover.

### Likelihood Explanation
Likelihood is Medium: reaching one of the `throw Error` invariant checks requires crafting an AA trigger and/or state/formula combination that satisfies static `formula/validation.js` checks but nonetheless violates an assumption made only in `formula/evaluation.js`/`aa_composer.js`. The extensive number of specific edge-case regression tests around state var/local var mutation and object handling in `test/aa_composer.test.js` and `test/formula.test.js` indicate this boundary has been a recurring source of edge cases historically, making it plausible that further edge cases exist that are not yet covered by validation. The `conf.bDryRunNewTriggers` "let it crash now" pre-check reduces — but does not eliminate — the exposure for live gossip, and does not cover `light/dry_run_aa`/`light/get_aa_state_vars` RPCs or trigger execution during catch-up.

### Recommendation
- Audit `aa_composer.js` and `formula/evaluation.js` for every `throw Error(...)` reachable from processing attacker-controlled trigger/formula/state data, and convert them into `bounce()`/`setFatalError()`/`onDone(err)` calls so malformed input causes an AA bounce rather than a process crash.
- Wrap AA trigger evaluation (`handleTrigger`, `dryRunPrimaryAATrigger`, and the formula `evaluate()` entry point) in a try/catch boundary that converts any unexpected exception into a bounced/failed response instead of letting it propagate to `process.on('uncaughtException')`.
- Extend `conf.bDryRunNewTriggers`-style protective dry-running to cover all AA-trigger execution paths (including catch-up/secondary triggers and the `light/dry_run_aa` RPC), or better, remove the fatal-crash dependency entirely by hardening the evaluator against all validator-accepted ASTs.
- Add fuzz/property-based tests that generate ASTs which pass `formula/validation.js` and feed them into `formula/evaluation.js` to find further validator/evaluator mismatches.

### Proof of Concept
A concrete triggering AST/formula for a currently-unguarded `throw Error` was not confirmed within available tooling (this requires dynamic fuzzing/execution of the formula grammar against the evaluator, which is outside the scope of static code search). The report identifies the exact vulnerable pattern and file/line locations (`aa_composer.js:393-397`, `aa_composer.js:419-425`, `formula/evaluation.js:93-98`, `formula/evaluation.js:1394-1395`, and the crash-propagation sink at `network.js:4530-4543`) for a Devin agent or security engineer to construct a concrete crafted AA definition + trigger unit that passes `aa_validation.js`/`formula/validation.js` but throws during `formula/evaluation.js` execution.
