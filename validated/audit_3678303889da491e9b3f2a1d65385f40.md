### Title
`Team.find_or_create_by!(github_id: params.team.id)` ignores organization on lookup, letting membership webhooks from a different verified GitHub organization mutate a Team created by another organization - (File: app/models/shipit/webhooks/handlers/membership_handler.rb)

### Summary
`MembershipHandler#find_or_create_team!` looks up a `Team` solely by `github_id`, so once a team row with a given `github_id` exists (created via org_a's webhook), any subsequent `membership` webhook from a *different but independently verified* organization (org_b) that happens to carry the same `team.id` will find and return org_a's row instead of creating/using a distinct one. `add_member`/`members.delete` is then executed against org_a's `Team` using org_b's member, with no equality check between `team.organization` and `params.organization.login`. This is deterministic and reproducible with strictly sequential (non-concurrent) requests, so it is not a race condition — it is a structural missing-binding bug.

### Finding Description
The broken binding: the code should enforce `team.organization == params.organization.login` for any `Team` row returned to a membership handler operating on behalf of `params.organization`, but it only enforces `team.github_id == params.team.id`.

Code path:
- `Shipit::WebhooksController#create` dispatches the parsed payload to `Shipit::Webhooks.for_event(event)` handlers after `verify_signature`, which validates the payload against the secret configured for `repository_owner` (i.e., `params.dig('organization','login')` for membership events) via `Shipit.github(organization: repository_owner).verify_webhook_signature` [1](#0-0) . This signature check is *per-organization* — it only proves the payload actually came from `params.organization.login`'s GitHub App/webhook secret. It says nothing about which `Team.github_id` values that organization is allowed to reference.
- `MembershipHandler#process` calls `find_or_create_team!`, then `User.find_or_create_by_login!`, then either `team.add_member(member)` or `team.members.delete(member)` [2](#0-1) .
- `find_or_create_team!` is: `Team.find_or_create_by!(github_id: params.team.id) { |team| team.github_team = params.team; team.organization = params.organization.login }` [3](#0-2) . The block (which sets `organization`) only executes on the *create* path of `find_or_create_by!`. When a row with that `github_id` already exists, Rails returns the existing record untouched — no organization comparison, no re-validation, no error.
- `Team#add_member` simply does `members.append(member) unless members.include?(member)` [4](#0-3) , with no organization/team ownership check either.

Exploit flow (sequential, no race required):
1. org_a's GitHub organization sends a real, correctly-signed `membership` `added` webhook: `{action: "added", team: {id: 42, name: ..., slug: ..., url: ...}, organization: {login: "org-a"}, member: {login: "alice"}}`. `verify_signature` passes because it's genuinely signed by org_a's secret. `find_or_create_team!` creates `Team(github_id: 42, organization: "org-a")`; `alice` is added.
2. org_b — a completely separate, independently verified GitHub organization that also has a Shipit webhook configured — has (or an attacker who controls a team's numeric ID within org_b's org can arrange to have) a team whose `id` happens to equal `42`. It sends its own genuinely-signed `membership` `added` webhook: `{action: "added", team: {id: 42, ...}, organization: {login: "org-b"}, member: {login: "bob"}}`. `verify_signature` passes (correctly signed by org_b's own secret — this is legitimate traffic from org_b, not forgery).
3. `find_or_create_team!` runs `Team.find_or_create_by!(github_id: 42)`, finds org_a's existing row, returns it unchanged (organization remains `"org-a"`).
4. `team.add_member(bob)` appends `bob` to org_a's `Team` row. Now `alice` (org_a) and `bob` (org_b) are both members of a `Team` whose `organization` column still says `"org-a"`.

If that `Team` is used anywhere for authorization scoping (e.g. `Shipit.github_teams`, permission checks tied to `Team#handle`/`organization`), `bob` — a member of org_b — gains membership in a team record attributed to org_a, without org_a's org ever granting it, purely because GitHub team IDs are not globally unique across organizations and Shipit's lookup key (`github_id` alone) collides across tenants.

Existing guards do not prevent this: `verify_signature` only proves *who signed the payload*, not that the `team.id` inside the payload is scoped to that signer; `ExplicitParameters` schema only validates types/presence, not cross-field consistency; there is no `validates_uniqueness_of` or composite-key check on `Team` tying `github_id` to `organization`.

### Impact Explanation
This is a cross-tenant record-mutation bug: a `Team` record created and "owned" by one verified GitHub organization can be silently modified (members added/removed) by webhook traffic from a second, unrelated but also verified organization, with no forgery and no timing dependency. If `Team` membership feeds into `Shipit.github_teams`-based authorization or any deploy/task permission gating, this is an escalation path into another organization's team membership records — matching the High/Critical categories described (escalation into `Shipit.github_teams` authorization; a payload for one entity mutating another's record). The blast radius is bounded by GitHub's own team-ID numbering (an attacker able to influence which numeric `team.id` their own org's team receives, e.g. by controlling team creation order, could target a collision), but even without deliberate targeting the bug is a structural cross-tenant integrity violation reproducible deterministically once two orgs' `github_id`s collide.

### Likelihood Explanation
Preconditions: Shipit must have two or more GitHub organizations configured/verified for webhooks (`Shipit.github_teams`/multi-org setups are an intended, documented configuration in this engine), and GitHub team IDs are per-installation sequential integers that are not namespaced per organization — collisions across independent organizations are plausible, especially for low-numbered teams (e.g., first team created in each org) or if an attacker who administers their own org can create/delete teams to land on a specific ID. No secrets, sessions, or privileged roles are required — only that the attacker's own organization is one of the verified organizations, which is an intended/legitimate integration, not a compromise.

### Recommendation
Change `find_or_create_team!` to key the lookup on the composite `(github_id, organization)` rather than `github_id` alone, e.g. `Team.find_or_create_by!(github_id: params.team.id, organization: params.organization.login) { |team| team.github_team = params.team }`, and add a uniqueness validation/index on `[:github_id, :organization]` on `Shipit::Team` so a `github_id` can never be silently reused across organizations. If an existing row is found with matching `github_id` but a different `organization`, the handler should raise/reject rather than proceeding.

### Proof of Concept
Minitest plan (sequential, no concurrency) under `test/models/shipit/webhooks/handlers/membership_handler_test.rb` (or wherever handler tests live):
1. Build payload A: `action: 'added', team: {id: 42, name: 'Eng', slug: 'eng', url: '...'}, organization: {login: 'org-a'}, member: {login: 'alice'}`. Call `Shipit::Webhooks::Handlers::MembershipHandler.new(payload_a).process` (or via the dispatch path with signature verification stubbed to succeed for `org-a`).
2. Assert: `Shipit::Team.find_by(github_id: 42).organization == 'org-a'` and `Shipit::Team.find_by(github_id: 42).members.map(&:login) == ['alice']`.
3. Build payload B with the *same* `team.id: 42`, but `organization: {login: 'org-b'}, member: {login: 'bob'}`, `action: 'added'`. Call the handler again (again simulating a genuinely-signed request from `org-b`).
4. Assert the vulnerability: `Shipit::Team.where(github_id: 42).count == 1` (no second Team row was created for org-b) AND that single `Team`'s `members.map(&:login).sort == ['alice', 'bob']` AND `team.organization == 'org-a'` (unchanged) — proving org-b's webhook mutated org-a's Team, with no exception raised and no organization equality enforced anywhere in the path.
