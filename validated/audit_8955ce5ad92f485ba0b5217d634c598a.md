I found a solid analog. The core issue in the Sherlock report is that a state-mutating "membership registration" action is performed by an unauthorized party without going through the intended consent/authorization step. In `ocore`, the exact same pattern exists in the shared-address (multisig) subsystem.

### Title
Unauthorized registration of a shared (multisig) address bypasses the create/approve consent flow - (File: `wallet_defined_by_addresses.js`)

### Summary
The `new_shared_address` device-message handler calls `handleNewSharedAddress()` directly and persists the shared address (and associates the local user's own address as one of its members) without ever verifying that the local user actually went through the `create_new_shared_address` → `approve_new_shared_address` consent flow. Any paired correspondent device can therefore force a victim's wallet to silently "enter" an attacker-chosen multisig arrangement, exactly like the `Market.borrow()` bug let anyone force a victim to "enter the market" by skipping the amount/allowance-gated authorization step.

### Finding Description
The legitimate flow for creating a shared address is: `create_new_shared_address` (which explicitly triggers a confirmation dialog for the user, see the comment "this event should trigger a confirmation dialog, user needs to approve creation of the shared address") [1](#0-0)  → `approve_new_shared_address` from each cosigner → only then is `new_shared_address` broadcast to finalize it.

However, the `new_shared_address` message is handled unconditionally as soon as it's received from any known correspondent device, with no check that a corresponding `pending_shared_addresses` entry (i.e., prior local approval) exists: [2](#0-1) 

This routes straight into `handleNewSharedAddress()`, which only checks internal structural consistency of the attacker-supplied payload (definition hash matches, signer addresses match paths in the definition, every definition-leaf has a signer) — not that the *user* consented to this specific address: [3](#0-2) 

`determineIfIncludesMeAndRewriteDeviceAddress()` merely checks whether one of the addresses named in the attacker-supplied `signers` map is already one of *my* addresses (`my_addresses`/`shared_addresses`) — it does not require prior opt-in, it just discovers "am I mentioned": [4](#0-3) 

If that check passes, `addNewSharedAddress()` is called and immediately writes the new `shared_addresses` / `shared_address_signing_paths` rows and fires `new_address` events — no user confirmation, no linkage back to a `pending_shared_addresses` record the user actually approved: [5](#0-4) 

This mirrors the `Market.borrow()` bug precisely: a security-relevant state transition (there: "enter the market" via `checkBorrow()`; here: "register/enter a shared multisig address") is reachable through a path that omits the actual consent/allowance check (there: `assets != 0` gate on `spendAllowance`; here: the create/approve handshake tied to `pending_shared_addresses`), because the final state-mutating function trusts structural validity of attacker-supplied data instead of verifying that the affected party actually authorized this specific membership.

### Impact Explanation
An attacker (any paired correspondent device) can craft an arbitrary address definition — e.g. `["or", [["address", attacker_address], ["address", victim_address]]]` — and send it as a `new_shared_address` message directly. The victim's wallet will accept it as a legitimate shared address it is a member of, without ever asking for confirmation. Because `extractAddressPathsFromDefinition` only requires that leaf addresses in the definition have a matching signer entry, the attacker fully controls the combinator (`or`, `and`, `r of set`, `weighted and`), so they can construct a definition that *looks* like a joint/multisig address to the victim's UI while in fact requiring only the attacker's own signature to spend. If the victim (trusting the UI that shows this as "their" shared address, since it's now stored in `shared_addresses`/`shared_address_signing_paths`) is misled into treating it as a safe deposit target or into believing joint control exists, funds sent there can be swept unilaterally by the attacker — analogous to the "unauthorized market entry enabling unexpected liquidation/seizure" impact in the original report, here manifesting as unauthorized state (spurious multisig membership) that can lead to loss of funds sent to that address.

### Likelihood Explanation
Any existing paired correspondent (a normal, unprivileged pairing relationship used throughout the wallet chat/contract features) can trigger this by simply sending a `new_shared_address` justsaying message — no special privilege, no unit, no on-chain cost. This matches the "unprivileged paired device" reachability bar in scope.

### Recommendation
`handleNewSharedAddress()` (invoked from the `new_shared_address` case in `wallet.js`) should verify that a matching `pending_shared_addresses`/`pending_shared_address_signing_paths` record exists that was created and approved locally (via the `create_new_shared_address`/`approve_new_shared_address` flow) before persisting the shared address and associating the local user's address with it, instead of accepting any well-formed, self-consistent `{address, definition, signers}` payload from a correspondent at face value.

### Proof of Concept
1. Attacker pairs with victim's device as a normal correspondent (or forwards through an existing indirect correspondent link).
2. Attacker computes `arrDefinition = ["or", [["address", attacker_address], ["address", victim_address]]]` and `address = chash160(arrDefinition)`.
3. Attacker sends a device message `{subject: "new_shared_address", body: {address, definition: arrDefinition, signers: {"r.0": {address: attacker_address, device_address: attacker_device_address}, "r.1": {address: victim_address, device_address: victim_device_address}}}}`.
4. `wallet.js` routes this straight to `walletDefinedByAddresses.handleNewSharedAddress()` (`wallet.js:236-245`), which passes all structural checks and calls `addNewSharedAddress()`, silently registering the address as a shared address including the victim — without any `pending_shared_addresses` record or user confirmation ever having existed.

// Checks if any of my payment addresses is mentioned.
// It is possible that my device address is not mentioned in the definition if I'm a member of multisig address, one of my cosigners is mentioned instead
function determineIfIncludesMeAndRewriteDeviceAddress(assocSignersByPath, handleResult){
	var assocMemberAddresses = {};
	var bHasMyDeviceAddress = false;
	for (var signing_path in assocSignersByPath){
		var signerInfo = assocSignersByPath[signing_path];
		if (signerInfo.device_address === device.getMyDeviceAddress())
			bHasMyDeviceAddress = true;
		if (signerInfo.address)
			assocMemberAddresses[signerInfo.address] = true;
	}
	var arrMemberAddresses = Object.keys(assocMemberAddresses);
	if (arrMemberAddresses.length === 0)
		return handleResult("no member addresses?");
	db.query(
		"SELECT address, 'my' AS type FROM my_addresses WHERE address IN(?) \n\
		UNION \n\
		SELECT shared_address AS address, 'shared' AS type FROM shared_addresses WHERE shared_address IN(?)", 
		[arrMemberAddresses, arrMemberAddresses],
		function(rows){
		//	handleResult(rows.length === arrMyMemberAddresses.length ? null : "Some of my member addresses not found");
			if (rows.length === 0)
				return handleResult("I am not a member of this shared address");
			var arrMyMemberAddresses = rows.filter(function(row){ return (row.type === 'my'); }).map(function(row){ return row.address; });
			// rewrite device address for my addresses
			if (!bHasMyDeviceAddress){
				for (var signing_path in assocSignersByPath){
					var signerInfo = assocSignersByPath[signing_path];
					if (signerInfo.address && arrMyMemberAddresses.indexOf(signerInfo.address) >= 0)
						signerInfo.device_address = device.getMyDeviceAddress();
				}
			}
			handleResult();
		}
	);
}

// {address: "BASE32", definition: [...], signers: {...}}
function handleNewSharedAddress(body, callbacks){
	if (!ValidationUtils.isArrayOfLength(body.definition, 2))
		return callbacks.ifError("invalid definition");
	if (typeof body.signers !== "object" || Object.keys(body.signers).length === 0)
		return callbacks.ifError("invalid signers");
	try {
		var addr = objectHash.getChash160(body.definition);
	}
	catch (e) {
		return callbacks.ifError("invalid definition: " + e);
	}
	if (body.address !== addr)
		return callbacks.ifError("definition doesn't match its c-hash");
	for (var signing_path in body.signers){
		var signerInfo = body.signers[signing_path];
		if (signerInfo.address && signerInfo.address !== 'secret' && !ValidationUtils.isValidAddress(signerInfo.address))
			return callbacks.ifError("invalid member address: " + JSON.stringify(signerInfo.address));
	}
	const assocDefinitionAddresses = extractAddressPathsFromDefinition(body.definition);
	for (let signing_path in body.signers) {
		const signerInfo = body.signers[signing_path];
		if (assocDefinitionAddresses[signing_path] !== signerInfo.address)
			return callbacks.ifError("signer address at path " + signing_path + " doesn't match definition");
	}
	for (let def_path in assocDefinitionAddresses) {
		if (!body.signers[def_path])
			return callbacks.ifError("no signer for definition address at path " + def_path);
	}
	determineIfIncludesMeAndRewriteDeviceAddress(body.signers, function(err){
		if (err)
			return callbacks.ifError(err);
		validateAddressDefinition(body.definition, function(err){
			if (err)
				return callbacks.ifError(err);
			addNewSharedAddress(body.address, body.definition, body.signers, body.forwarded, callbacks.ifOk);
		});
	});
}
