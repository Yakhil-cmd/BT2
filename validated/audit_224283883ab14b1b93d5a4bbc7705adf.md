### Title
Fork PR's `shipit.yml` `machine.environment` injects arbitrary env vars (e.g. `LD_LIBRARY_PATH`) into spawned deploy processes - (File: `lib/shipit/task_commands.rb`, `app/models/shipit/deploy_spec.rb`, `lib/shipit/command.rb`)

### Summary
For a repository configured with `review_stacks_enabled` + `provisioning_behavior: allow_with_label`, an unprivileged fork PR author can self-label their own PR to get a `ReviewStack` provisioned and deployed against their fork's branch. Because `TaskCommands#env` merges `DeploySpec::FileSystem#machine_env` — sourced from the fork's own `shipit.yml` `machine.environment` key — into the process environment with **no key allowlist/denylist**, and `Command#unbundled_env`/`PTY.spawn` pass that hash straight to the child process, the attacker can set `LD_LIBRARY_PATH` (or `LD_PRELOAD`, etc.) for every command Shipit executes against their own review stack.

### Finding Description
The broken binding: the set of environment keys reaching `PTY.spawn` should equal `Shipit`/operator-controlled keys only; instead it equals `Shipit`-controlled keys ∪ **fork-controlled `machine.environment` keys** ∪ **fork PR label names** (as keys, via `ReviewStack#env`).

Path:
1. Attacker opens a fork PR and adds the repository's `provisioning_label_name` label. `OpenedHandler#provision?` (and `LabeledHandler#archive?`/`unarchive?`) treats this as sufficient to provision a `ReviewStack` when `provisioning_behavior_allow_with_label?` is set — no maintainer approval is required. [1](#0-0) 
2. The stack's working directory is checked out from the PR head (fork branch/commit). `TaskCommands#deploy_spec` builds `DeploySpec::FileSystem.new(@task.working_directory, @stack)`, which reads the repository's own `shipit.yml`. [2](#0-1) 
3. `DeploySpec#machine_env` returns `config('machine', 'environment')` verbatim — the fork author fully controls this hash's keys and values, including `LD_LIBRARY_PATH`. [3](#0-2) 
4. `TaskCommands#env` merges `deploy_spec.machine_env` into the process env with no sanitization or key filtering. [4](#0-3) 
5. `Command#unbundled_env` merges `@env` (stringified) on top of `BASE_ENV`/`PATH`, again with no denylist of dangerous keys. [5](#0-4) 
6. `Command#start` calls `PTY.spawn(unbundled_env, *interpolated_arguments, chdir: @chdir)`, so every spawned binary (git, deploy scripts, custom task commands) inherits the attacker-supplied `LD_LIBRARY_PATH`. [6](#0-5) 

Additionally, `ReviewStack#env` independently merges the PR's label *names* directly as environment variable keys (uppercased) with value `"true"` — meaning an attacker can also create/collide arbitrary env var keys purely by naming a label, with less value control. [7](#0-6) 

Existing guards do not prevent this: `EnvironmentVariables#permit` exists and is used to whitelist keys for `deploy.variables`/`rollback.variables` and task-triggered `env` params (`Task#filter_envs` used in `Stack#trigger_task`, `Stack#filter_deploy_envs` used in `build_deploy`), but it is never applied to `deploy_spec.machine_env` merged in `TaskCommands#env`. [8](#0-7) [9](#0-8) 

### Impact Explanation
Any command Shipit executes for the deploy/task on that review stack (git operations, dependency install, custom deploy/rollback scripts) inherits `LD_LIBRARY_PATH` pointed at attacker-controlled paths inside the checked-out fork tree, letting the attacker redirect dynamic linking of any dynamically-linked binary invoked in that process tree to a malicious shared library, achieving code execution on the Shipit deploy host under the Shipit worker's privileges — Critical, RCE on the deploy host via `Command`/`PTY.spawn`. This is scoped to repositories that opted into `review_stacks_enabled` + `allow_with_label`, but is fully repeatable per PR/label add and requires no maintainer action once that configuration exists.

### Likelihood Explanation
Preconditions: the target repository must have `review_stacks_enabled = true` and `provisioning_behavior = allow_with_label` (or `allow_all`, which needs no label at all) — a configuration explicitly supported and documented as an "opt-in" workflow for external contributor review stacks. Given that configuration, the only attacker cost is opening a PR from a fork, adding a `shipit.yml` with `machine.environment.LD_LIBRARY_PATH`, and applying the provisioning label to their own PR — all actions available to any unprivileged GitHub user per the threat model. No secrets, sessions, or maintainer approval are needed.

### Recommendation
Do not merge `deploy_spec.machine_env` (or any fork-derived config) into the spawned-process environment unfiltered. Apply an explicit denylist/allowlist in `Command#unbundled_env` (or in `TaskCommands#env`/`DeploySpec#machine_env`) rejecting dynamic-linker and interpreter-hijacking variables (`LD_LIBRARY_PATH`, `LD_PRELOAD`, `DYLD_*`, `PYTHONPATH`, etc.), and additionally require that `machine.environment` for review stacks come only from the base branch's `shipit.yml` (or be restricted to a maintainer-approved allowlist) rather than the fork's own file. Also stop using raw PR label names as environment variable keys in `ReviewStack#env`; use a fixed prefix/namespace and validate names against an allowlist.

### Proof of Concept
Minitest plan (`test/unit/task_commands_test.rb` or similar):
1. Build a `ReviewStack` fixture with `provisioning_behavior: allow_with_label`, provisioned/labeled per `LabeledHandler`/`OpenedHandler` flow.
2. Stub `DeploySpec::FileSystem#machine_env` (representing the fork's `shipit.yml`) to return `{ 'LD_LIBRARY_PATH' => '/tmp/evil' }`.
3. Assert `TaskCommands.new(task).env['LD_LIBRARY_PATH'] == '/tmp/evil'`.
4. Construct `Command.new('true', env: task_commands.env, chdir: '.')` and assert `command.unbundled_env['LD_LIBRARY_PATH'] == '/tmp/evil'`.
5. Equality check before/after: expected binding `Command#unbundled_env.keys ⊆ Shipit-controlled keys` is violated — `'LD_LIBRARY_PATH'` (fork-controlled) is present, proving the invariant "no fork-controllable key reaches the environment hash of a spawned deploy process" is broken.
