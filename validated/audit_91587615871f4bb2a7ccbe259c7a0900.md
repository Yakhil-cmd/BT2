Looking at the `BridgeOperator.sol` voting mechanism, I found a direct analog to the external report's front-running vulnerability.

The critical code is in `_voteValueTransfer`:

```solidity
function _voteValueTransfer(uint64 _requestNonce) internal returns(bool) {
    require(!closedValueTransferVotes[_requestNonce], "closed vote");
    bytes32 voteKey = keccak256(msg.data);
    if (_voteCommon(VoteType.ValueTransfer, _requestNonce, voteKey)) {
        closedValueTransferVotes[_requestNonce] = true;
        return true;
    }
    return false;
}
```

`closedValueTransferVotes` is keyed only by `_requestNonce`. Once any operator reaches the threshold for **any** set of parameters at that nonce, the nonce is permanently closed. The default threshold is 1 (set in the constructor). A malicious operator can call `handleKLAYTransfer` with the correct nonce but a different `_to` address, closing the vote and stealing the funds before the legitimate operator acts.

### Title
Malicious Bridge Operator Can Front-Run `handleKLAYTransfer` to Redirect Bridged Assets — (`contracts/service_chain/bridge/BridgeOperator.sol`)

### Summary
The Kaia service-chain bridge's operator voting mechanism permanently closes a value-transfer vote (`closedValueTransferVotes[nonce] = true`) after the operator threshold is reached, keyed only by request nonce. With the default threshold of 1, a single malicious operator can call `handleKLAYTransfer` (or `handleERC20Transfer` / `handleERC721Transfer`) with a different `_to` address before the legitimate operator, permanently closing the vote for that nonce and redirecting bridged KAIA/ERC20/ERC721 assets to themselves.

### Finding Description

In `BridgeOperator.sol`, `_voteValueTransfer` computes `voteKey = keccak256(msg.data)`, which commits to all calldata parameters. However, the nonce-closure flag `closedValueTransferVotes` is keyed only by `_requestNonce`:

```solidity
// BridgeOperator.sol lines 103-116
function _voteValueTransfer(uint64 _requestNonce) internal returns(bool) {
    require(!closedValueTransferVotes[_requestNonce], "closed vote");
    bytes32 voteKey = keccak256(msg.data);
    if (_voteCommon(VoteType.ValueTransfer, _requestNonce, voteKey)) {
        closedValueTransferVotes[_requestNonce] = true;  // keyed by nonce only
        return true;
    }
    return false;
}
```

The constructor sets `operatorThresholds[ValueTransfer] = 1` by default:

```solidity
// BridgeOperator.sol lines 54-61
constructor() internal {
    for (uint8 i = 0; i < uint8(VoteType.Max); i++) {
        operatorThresholds[uint8(i)] = 1;
    }
    operators[msg.sender] = true;
    operatorList.push(msg.sender);
}
```

With threshold = 1, the first operator to call `handleKLAYTransfer` for a given nonce wins, regardless of the `_to`, `_value`, or other parameters. The `voteKey` differentiation only matters when threshold > 1.

**Attack path:**

1. User Alice calls `requestKLAYTransfer(bob_address, 100_KLAY)` on the source chain, emitting `RequestValueTransfer(KLAY, alice, bob, address(0), 100, nonce=5, fee, extraData)`.
2. Malicious operator Eve observes the event and immediately calls `handleKLAYTransfer(txHash, alice, eve_address, 100, 5, blockNum, extraData)` on the destination chain.
3. `_voteValueTransfer(5)` executes: `closedValueTransferVotes[5]` is false → `voteKey = keccak256(malicious_calldata)` → `voteCounts[voteKey]++` = 1 ≥ threshold 1 → `closedValueTransferVotes[5] = true` → returns `true`.
4. `(bool ok,) = eve_address.call.value(100)("")` executes — 100 KLAY sent to Eve.
5. Legitimate operator Bob calls `handleKLAYTransfer(txHash, alice, bob_address, 100, 5, blockNum, extraData)`.
6. `_voteValueTransfer(5)` hits `require(!closedValueTransferVotes[5], "closed vote")` → **reverts**.

Alice's 100 KLAY is permanently lost to Eve. The same attack applies to `handleERC20Transfer` and `handleERC721Transfer`.

### Impact Explanation

Bridged KAIA, ERC20, and ERC721 assets can be permanently redirected to an attacker-controlled address. The user's funds are unrecoverable because the nonce is permanently closed. The bridge contract holds no record of the intended recipient, so there is no on-chain recourse. This is an unauthorized transfer of bridged assets directly matching the allowed impact gate.

### Likelihood Explanation

The default operator threshold is 1. Any registered operator can execute this attack unilaterally with a single transaction. The incentive scales linearly with the value of bridged assets. Operators are registered by the owner (`onlyOwner`), making them semi-trusted — analogous to the DAO-approved operators in the external report. The cost of the attack is a single gas payment for the malicious `handleKLAYTransfer` call.

### Recommendation

1. **Require threshold > 1 when multiple operators are registered.** The `registerOperator` function should enforce `operatorThresholds[ValueTransfer] > 1` or automatically raise the threshold.
2. **Store expected transfer parameters on-chain.** When `RequestValueTransfer` is emitted on the source chain, the bridge relayer should commit the expected `(from, to, value, tokenAddress)` tuple on-chain, and `handleKLAYTransfer` should verify the parameters match before executing.
3. **Adopt a guardian/committee model** (analogous to Lido's fix): require a quorum of operators to sign the same parameters off-chain before any on-chain execution, and verify the aggregate signature in `handleKLAYTransfer`.
