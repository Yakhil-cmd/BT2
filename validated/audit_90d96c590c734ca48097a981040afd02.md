### Title
Missing deposit refund on intermediate cross-contract call failure locks caller funds in `WalletContract` - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The `WalletContract`'s `rlp_execute` flow tracks an external caller's attached deposit via `CallerDeposit` so it can be refunded if the underlying cross-contract call the wallet initiates on the caller's behalf fails. This refund logic is correctly implemented in `rlp_execute_callback`, but it is missing in the two intermediate callbacks — `address_check_callback` and `nep_141_storage_balance_callback` — that are invoked before `rlp_execute_callback` for certain transaction kinds (address-registrar lookups for EOA transfers, and NEP-141 `storage_balance_of` checks for ERC-20 transfers). If the intermediate promise result is `Failed` or returns unparseable data, these callbacks return an error response directly without ever forwarding or refunding `caller_deposit`, permanently trapping the caller's attached NEAR in the contract.

### Finding Description
`CallerDeposit::new` records the predecessor's attached deposit whenever the predecessor is not the contract itself, i.e. whenever an external relayer calls `rlp_execute` on behalf of a user and attaches a deposit: [1](#0-0) 

For two specific transaction kinds, `inner_rlp_execute` schedules an intermediate cross-contract call before reaching the final action, threading `caller_deposit` through to the intermediate callback rather than directly to `rlp_execute_callback`: [2](#0-1) 

In `rlp_execute_callback`, the final callback, a promise failure is handled correctly — the caller's deposit is refunded via a `Transfer` action before returning the failure response: [3](#0-2) 

However, `address_check_callback`, which runs after the address-registrar `lookup` call for `EOABaseTokenTransfer` with `address_check: Some(_)`, drops `caller_deposit` on both the `PromiseResult::Failed` branch and the JSON-deserialization-error branch without issuing any refund: [4](#0-3) 

Similarly, `nep_141_storage_balance_callback`, which runs after the `storage_balance_of` call for `ERC20Transfer`, drops `caller_deposit` on the same two failure branches without a refund: [5](#0-4) 

In both cases, `caller_deposit` is only used to refund the caller by being forwarded to `rlp_execute_callback` on the success path (via `.then(ext.rlp_execute_callback(caller_deposit))`); on the early-return failure paths it is simply discarded, so the previously attached NEAR is never sent back and remains stranded in the `WalletContract` account's balance.

### Impact Explanation
Any relayer/external caller that attaches a deposit while invoking `rlp_execute` (e.g., to cover a fee or a `FunctionCall` deposit for an ERC-20/EOA-emulated transfer) risks permanent loss of that deposit whenever:
- the address-registrar `lookup` call fails or returns malformed data (for base-token transfers where `address_check` is required), or
- the token contract's `storage_balance_of` call fails or returns malformed data (for ERC-20 transfers to an unregistered receiver).

Because the deposit was already attached to the `rlp_execute` function call (and thus already added to the `WalletContract` account's own balance), and no code path recovers or forwards it on these failures, the funds become permanently locked in the contract with no user-facing mechanism to reclaim them. This is a direct, unprivileged loss of funds for the caller, matching the reported bug class (return/result of an inner cross-contract call not being handled, leaving value stuck in the contract).

### Likelihood Explanation
This is reachable by any account without special privileges: simply calling `rlp_execute` with a `target`/transaction that routes through `EOABaseTokenTransfer{address_check: Some(_)}` or `ERC20Transfer` while attaching a deposit is sufficient to expose the funds to this bug. Triggering the failure only requires the address-registrar contract or the destination token contract to fail or misbehave on the intermediate call (e.g. contract paused, insufficient gas, unexpected response format, or the account not existing), which is plausible in normal operation, not just adversarial conditions.

### Recommendation
In both `address_check_callback` and `nep_141_storage_balance_callback`, refund `caller_deposit` (mirroring the logic in `rlp_execute_callback`) on every early-return failure branch (`PromiseResult::Failed` and the JSON parse error branch) before returning the `ExecuteResponse`, instead of silently discarding it.

### Proof of Concept
1. An external relayer account calls `rlp_execute` with a `target` account and an RLP-encoded transaction that decodes to `TransactionKind::EthEmulation(EthEmulationKind::EOABaseTokenTransfer { address_check: Some(address), .. })`, attaching a non-zero deposit. [6](#0-5) 
2. `inner_rlp_execute` schedules `address_registrar.lookup(address).then(ext.address_check_callback(target, action, caller_deposit))`, passing along the tracked `CallerDeposit`.
3. The address registrar contract's `lookup` call fails (e.g., account doesn't exist, is out of gas, or panics), so `env::promise_result(0)` returns `PromiseResult::Failed` inside `address_check_callback`. [7](#0-6) 
4. `address_check_callback` returns `ExecuteResponse{success:false, ...}` immediately; `caller_deposit` is dropped, and no `Transfer` refund action is ever created — the caller's originally-attached deposit remains part of the `WalletContract` account's NEAR balance permanently.
5. Compare against the equivalent flow through `rlp_execute_callback` (used for the default/non-intermediate path), where the same `PromiseResult::Failed` scenario correctly issues a refund `Transfer` to the caller. [3](#0-2)
