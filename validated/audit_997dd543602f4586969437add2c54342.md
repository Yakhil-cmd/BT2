### Title
`data_feed[[...]]` oscript function exposes only the raw feed value/unit with no way to check the posting mci/timestamp, preventing any staleness check by AA authors - ([File: formula/evaluation.js], [File: formula/validation.js], [File: data_feeds.js])

### Summary
The oscript `data_feed[[...]]` function (used inside Autonomous Agent formulas to read oracle-posted values) only ever returns the raw `value` or the posting `unit`, never the `mci` (or timestamp) at which the value was posted. As with the reported Chainlink `latestRoundData()` issue — where the returned tuple is used without checking `updatedAt`/`answeredInRound` for staleness — an ocore AA has no built-in mechanism, and no exposed metadata, to detect that the oracle value it consumes is stale.

### Finding Description
The `data_feed` opcode is parsed with a restricted parameter set (`oracles`, `feed_name`, `min_mci`, `feed_value`, `ifseveral`, `ifnone`, `what`, `type`), and `what` can only be `'value'` or `'unit'`: [1](#0-0) 

At evaluation time, `getDataFeed()` resolves the query via `dataFeeds.readDataFeedValue`, and the callback only returns `objResult.unit` or `objResult.value` — the resolved `objResult.mci` (the main-chain index at which the matched oracle post was made) is computed internally but is never surfaced to the formula: [2](#0-1) 

`readDataFeedValue`/`readDataFeedByAddress` in `data_feeds.js` do track `mci` internally for sorting/selection purposes, but this value is discarded once a match is chosen — it's only used to decide "most recent within `[min_mci,max_mci]`", not exposed to the caller for a freshness check: [3](#0-2) 

Unlike Chainlink's `latestRoundData()`, which at least returns `updatedAt`/`answeredInRound` so a caller *can* implement its own staleness guard (even though the audited protocol failed to do so), ocore's `data_feed[[...]]` gives the AA author no equivalent field at all. The only staleness control available is the caller-supplied `min_mci` parameter, which defaults to `0`: [4](#0-3) 

A `min_mci=0` (or any low fixed value) accepts *any* historical post from the oracle address(es), including one made long ago and never refreshed since — the AA cannot dynamically require "value must not be older than N mci/seconds relative to the current trigger," because it cannot read back the value's actual mci or timestamp to compute that check itself, even if the author is aware of the risk and tries to defend against it.

### Impact Explanation
Any AA design that depends on an oracle-posted price/value (e.g. stablecoin issuance, prediction markets, DEX/AMM logic, insurance payouts) to gate fund movement is structurally unable to enforce a robust staleness check inside the oscript formula itself, because the language does not expose the posting mci/timestamp of the matched data feed entry. This mirrors the audited root cause directly: consumption of an oracle read without the metadata needed to detect staleness, which can be leveraged by an ordinary trigger sender to have the AA execute economic logic (trades, payouts, minting/burning) against an out-of-date value, producing unauthorized fund transfers/loss inside the AA.

### Likelihood Explanation
Any unprivileged user can send an AA trigger unit at any time; if the target AA uses `data_feed[[...]]` (as documented/intended usage pattern for oracle-driven AAs) and the referenced oracle has stopped posting fresh updates (temporarily or permanently) while the underlying real-world value has moved, the trigger sender can time their trigger to exploit the frozen value. Because the language provides no primitive to detect this condition, no reasonable AA-side mitigation exists other than the coarse, caller-fixed `min_mci` threshold, which cannot adapt to "how old is too old" relative to the trigger's own mci at execution time.

### Recommendation
Extend the `data_feed[[...]]` opcode's `what` parameter to support returning the feed entry's `mci` (and/or `timestamp`), analogous to Chainlink's `updatedAt`, so AA formulas can implement `mci - data_feed[[..., what='mci']] <= MAX_AGE` style staleness checks. Update `getDataFeed()` in `formula/evaluation.js` and `validateDataFeed()`/`validateDataFeedExists()` in `formula/validation.js` to accept and validate this new `what` value, and thread `objResult.mci` (already computed in `data_feeds.js`) through to the formula result.

### Proof of Concept
1. Oracle O posts `data_feed[[price]] = 100` at mci `M0`, then stops posting for a long period.
2. AA `X` is defined to accept payments and calculate payout using `data_feed[[oracles=O, feed_name='price']]` (default `min_mci=0`), with no way to verify the value's age since the language exposes no mci/timestamp field for the query.
3. Real-world price moves substantially away from `100`, but the AA still resolves the same stale value because it has no data available to reject it.
4. An unprivileged user sends a trigger unit to AA `X` at the currently favorable (to them) stale price, extracting funds at a rate the AA would never have permitted under an up-to-date price, causing fund loss to the AA/other participants.
