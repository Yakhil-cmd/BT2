### Title
Cross-organization webhook forgery via unverified `repository_owner` used to select the signature-verification secret - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController` picks which GitHub App configuration (and thus which `webhook_secret`) to verify a webhook's HMAC signature against by reading the organization name straight out of the **unverified** JSON body, before the signature has been checked. In a multi-organization Shipit deployment, this decouples "the organization whose secret authenticated the request" from "the repository/stack the payload actually causes Shipit to mutate," exactly the class of binding violation described in the bribe report (a value that's blindly trusted to select the semantics of an already-signed payload).

### Finding Description
The webhook signature is verified like this: [1](#0-0) 

`repository_owner` is derived purely from the raw JSON body supplied by the caller, not from anything cryptographically bound to a specific GitHub App installation: [2](#0-1) 

`Shipit.github(organization: repository_owner)` looks up a `GitHubApp` instance whose `webhook_secret` is configured per-organization, as shown by the multi-org secrets format: [3](#0-2) 

Verification itself is a straightforward HMAC compare against that org-specific secret: [4](#0-3) 

The problem: the field used to *pick the secret* (`repository.owner.login` / `organization.login`) and the field(s) used *downstream by webhook handlers* to identify which `Repository`/`Stack` to act on (e.g. `repository.full_name`, used by `Repository.from_github_repo_name`) both live inside the same attacker-suppliable JSON body, and nothing forces them to refer to the same GitHub organization: [5](#0-4) 

Because the whole raw body is HMAC-signed, the signature is *self-consistent* with whatever secret is chosen — but the choice of secret is attacker-influenced. Anyone who legitimately owns one configured GitHub App (and therefore knows the `webhook_secret` they set when creating it, per the setup docs) can compute a valid signature for a payload of their choosing: [6](#0-5) 

By setting `repository.owner.login` (used only for secret selection) to their own organization while setting `repository.full_name` / other repo-identifying fields (used by the actual event handlers, e.g. push, status, check_suite, membership) to a *different* organization/repository configured in the same Shipit instance, the attacker gets a request that passes signature verification with their own known secret, yet whose payload content drives handlers to write to a repository/stack they have no legitimate relationship with.

### Impact Explanation
This breaks the binding "organization that authenticated == repository that is written," letting an attacker who administers one tenant's GitHub App forge events (pushes, commit statuses, check suites, membership changes, pull_request events) attributed to a different organization's stacks. Depending on which handler is reached, this can trigger unauthorized commit-status/CI-state changes that gate deploys, spurious team/user creation, or corrupted merge-request state for a repository the attacker does not control — i.e., cross-repository writes, matching the Critical impact bar in scope.

### Likelihood Explanation
Requires only that the Shipit instance is configured with more than one GitHub organization (a documented, supported configuration — see `config/secrets.development.shopify.yml`) and that the attacker is a legitimate owner/admin of one of those configured organizations (they set that org's `webhook_secret` themselves during GitHub App creation). No GitHub App private key, `ApiClient` token, or session is required — only knowledge of one's own org's webhook secret and the ability to POST to the public `/webhooks` endpoint.

### Recommendation
Do not let attacker-controlled payload fields decide which secret validates the payload. Options: bind webhook delivery to org/installation via a server-side, non-spoofable identifier (e.g., GitHub's `X-GitHub-Hook-Installation-Target-ID` header or the App's installation ID resolved server-side), verify the signature against *all* configured secrets and only accept if exactly one matches, or, after verification, require that the resolved organization used for signature selection matches the organization referenced by the repository/stack the handler is about to mutate, rejecting the event otherwise.

### Proof of Concept
1. Configure Shipit (as in `config/secrets.development.shopify.yml`) with two orgs: `orgA` (attacker-controlled, attacker knows `webhook_secret_A`) and `orgB` (victim, has a real Stack in Shipit).
2. Attacker builds a JSON payload for, e.g., the `push` or `status` event where `repository.owner.login == "orgA"` but `repository.full_name == "orgB/victim-repo"` (and any other repo-identifying fields the target handler uses also point at `orgB`).
3. Attacker computes `X-Hub-Signature: sha1=HMAC(webhook_secret_A, raw_body)`.
4. POST to `/webhooks` with `X-Github-Event` set appropriately.
5. `WebhooksController#verify_signature` calls `Shipit.github(organization: "orgA")`, which verifies successfully using `webhook_secret_A`, since it never validates that `orgA` genuinely owns the repository referenced elsewhere in the body.
6. The event handler for that event type proceeds to process the payload against `orgB/victim-repo`'s Stack, causing unauthorized state changes on a repository/organization the attacker does not control.

Note: I was unable to inspect the full body of `push_handler.rb`, `status_handler.rb`, `membership_handler.rb`, and `handlers/handler.rb` within the iteration budget to confirm the exact field(s) each handler uses to resolve the target `Stack`/`Repository` (only match counts for "repository lookup" patterns were retrieved). The root-cause mismatch in `WebhooksController#verify_signature`/`#repository_owner` is confirmed directly from source, but the precise downstream field each individual handler trusts should be re-verified against those handler files before treating this as fully proven for every event type.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
