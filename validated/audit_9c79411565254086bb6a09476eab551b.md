### Title
`StatusHandler#process` mutates `Commit` rows across repositories via unscoped `Commit.where(sha:)`, unlike `CheckSuiteHandler` which scopes through `stacks` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`CheckSuiteHandler#process` filters through `stacks.where(branch: ...)` (derived from `payload['repository']['full_name']` via `Handler#stacks`) before ever touching a `Commit`, enforcing that only commits belonging to the authenticated repository's stacks are mutated. `StatusHandler#process` instead runs `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` with no call to `stacks` at all, so any commit anywhere in the database sharing that SHA gets a new `Status` written, regardless of which repository the signed webhook belongs to.

### Finding Description
The broken binding: for any mutating `Handler#process`, the equality that must hold is `mutated_commit.stack.repository.full_name == payload['repository']['full_name']` (i.e., every `Commit`/`Stack` touched must come from `Handler#stacks`, which is `Repository.from_github_repo_name(repository_name)&.stacks`, `repository_name` being `payload.dig('repository', 'full_name')`) — see [1](#0-0) .

`CheckSuiteHandler#process` respects this: it does `stacks.where(branch: params.check_suite.head_branch).each { |stack| stack.commits.where(sha: ...) }`, so a commit only gets its check runs refreshed if it belongs to a stack of the exact repository that signed the webhook [2](#0-1) .

`StatusHandler#process` does not call `stacks` (or any repository-derived scope) at all: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [3](#0-2) . `Commit#sha` is indexed together with `stack_id` (`add_index ... [:stack_id, :sha]`, per `db/migrate/20170524104615_index_commits_on_stack_id_and_sha.rb`), not globally unique — there is no DB constraint preventing two different stacks/repositories from having commits with the identical SHA (e.g., empty-repo initial commits, cherry-picked/rebased-with-identical-tree commits, or a fork pushing the exact same commit into two separately tracked repositories).

Attack path: `WebhooksController#create` only validates the HMAC signature against the organization derived from `repository.owner.login` in the payload and does not check that the `repository.full_name` in the payload corresponds to a repository whose `Stack` actually contains the commit being mutated [4](#0-3) . An attacker who owns/administers *any* GitHub repository configured with a webhook to this Shipit instance (a low-privilege repo owner, per the threat model) can send a `status` event whose `sha` field matches a commit belonging to a *different*, unrelated `Stack`/repository tracked by the same Shipit instance. Because `StatusHandler` never checks that the commit's `stack`'s repository matches `payload['repository']['full_name']`, the attacker's webhook writes a forged `Status` (arbitrary `state`, `description`, `target_url`, `context`) onto that unrelated repository's commit. Since `Commit#create_status_from_github!` → `add_status` recomputes `Status::Group`, this can flip a target commit from pending/failure to `success`, and since `Commit#schedule_continuous_delivery` (triggered on the `after_commit` callbacks, or indirectly through `Status::Group` state changes feeding `deployable?`/`stack.schedule_merges`) can enable continuous deployment/merge scheduling for a foreign stack — i.e., a payload for one repository mutating another's commit/stack state, matching the Critical-impact "cross-tenant mutation" category defined in the rules.

None of the existing guards prevent this: `verify_signature` only checks the HMAC secret for the *organization named in the attacker's own payload* (which the attacker legitimately owns/administers and can set correctly), not that the mutated `Commit` belongs to that organization/repository [5](#0-4) ; `ExplicitParameters` schema only validates types/presence, not repository scoping [6](#0-5) ; `Handler#stacks` exists precisely to close this gap but `StatusHandler` never invokes it.

### Impact Explanation
A `Status` record (state/description/target_url/context) is written to a `Commit` belonging to a `Stack`/repository that the attacker does not control and that never authenticated the request, purely because the attacker's own repository happens to produce a webhook containing a matching SHA. This can flip commit status aggregation (`Status::Group`) for the victim stack, potentially triggering `stack.schedule_merges` or continuous-delivery scheduling for commits the attacker doesn't own — an unauthorized state change/deploy trigger on another tenant's stack. This is repeatable against any repository/stack pair that shares (or can be made to share, e.g. via an empty initial commit or an identical file tree commit) a SHA, and is not limited to a single victim — it generalizes across all stacks tracked by the instance. This matches the Critical category "a payload for one repository mutating another's stack, commit, task or team."

### Likelihood Explanation
Preconditions: the attacker needs a GitHub repository (which they own or administer) configured to send webhooks to the shared Shipit instance — a common multi-tenant Shipit deployment scenario where many unrelated repositories/teams point at one Shipit host. The attacker must produce/find a commit SHA that also exists in a victim stack's `Commit` table; this is trivially achievable for degenerate cases (e.g., an empty repository's initial commit, or any commit whose SHA collides due to identical tree/parent/message/timestamp — realistic for auto-generated bootstrap commits, template-generated repos, or squash-merges producing identical diffs) — no cryptographic SHA-1 collision is required, only a "SHA reuse across repos" scenario, which is common for freshly-scaffolded repos or forks. No Shipit secrets are needed since the attacker's own webhook secret/signature is valid for their own repository. The attack is cheap (single HTTP POST) and fully repeatable.

### Recommendation
Scope `StatusHandler#process` through `stacks` exactly like `CheckSuiteHandler`, e.g. iterate `stacks.flat_map(&:commits).where(sha: params.sha)` (or `Commit.where(sha: params.sha, stack: stacks)`) instead of the global `Commit.where(sha: params.sha)`, so only commits belonging to stacks of the repository named in the verified payload can have a status written.

### Proof of Concept
Add to `test/models/shipit/webhooks/handlers_test.rb` (or a new file) a minitest that:
1. Creates two `Stack`s/`Repository`s, `repo_a` and `repo_b`, each with a `Commit` sharing the identical `sha` value `"deadbeef" * 5`.
2. Builds a `check_suite` payload whose `repository.full_name` is `repo_a`'s but whose `check_suite.head_sha` equals the shared SHA and `head_branch` matches `repo_b`'s stack's branch (cross-repo, same-SHA setup) — asserts `CheckSuiteHandler.new(payload).process` does **not** enqueue `RefreshCheckRunsJob` for `repo_b`'s commit, because `stacks` (scoped to `repo_a`) never contains `repo_b`'s stack.
3. Builds an equivalent `status` payload with `repository.full_name` set to `repo_a` and `sha` equal to the shared SHA, then asserts `StatusHandler.new(payload).process` **does** create a `Status` on `repo_b`'s commit (`assert_difference('repo_b_commit.statuses.count', 1)`), proving the asymmetry: `StatusHandler` never references `stacks`, so the binding `mutated_commit.stack.repository.full_name == payload['repository']['full_name']` fails to hold, while it correctly holds for `CheckSuiteHandler`. module Shipit
  module Webhooks
    module Handlers
      class Handler
        class << self
          attr_reader :param_parser

          def params(&block)
            @param_parser = ExplicitParameters::Parameters.define(&block)
          end
        end

        def self.call(params)
          new(params).process
        end

        attr_reader :params, :payload

        def initialize(payload)
          @payload = payload
          @params = self.class.param_parser.parse!(payload)
        end

        def process
          raise NotImplementedError
        end

        private

        def stacks
          @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
        end

        def repository_name
          payload.dig('repository', 'full_name')
        end
      end
    end
  end
end

          stacks.where(branch: params.check_suite.head_branch).each do |stack|
