### Title
Cross-tenant webhook forgery: signature verified against `repository.owner.login`'s secret while handlers act on unrelated `repository.full_name` - (`app/controllers/shipit/webhooks_controller.rb`)

### Summary
In multi-organization deployments (per the nested `secrets.github` schema, e.g. `test/dummy/config/secrets_double_github_app.yml`), `WebhooksController#verify_signature` selects which org's `webhook_secret` to validate the HMAC against using `repository_owner`, a value read from `params.dig('repository','owner','login')` or `params.dig('organization','login')`. Handlers, however, resolve the target `Repository`/stacks using a completely different JSON field, `payload.dig('repository','full_name')`, with no assertion that this field's owner segment matches `repository_owner`. Because both fields are attacker-controlled in the raw POST body, a legitimate webhook sender for one org can forge a payload that authenticates as their own org while targeting another org's repository.

### Finding Description
The broken binding, stated as an equality that should hold but is never enforced:
`repository_owner` (used in `verify_signature` to pick the HMAC secret) `==` owner segment of `repository.full_name` (used in `Handler#stacks`/`repository_name` and in every pull_request handler's `repository` method to select the DB `Repository`).

Code path:
- `verify_signature` in [1](#0-0)  computes `github_app = Shipit.github(organization: repository_owner)` and verifies `request.raw_post` against that org's `webhook_secret`.
- `repository_owner` is derived from `params.dig('repository','owner','login') || params.dig('organization','login')` [2](#0-1) .
- `Shipit.github(organization:)` in multi-org mode looks up a per-organization config/secret (`github_app_config(organization)`), distinct per tenant, as evidenced by the two-org fixture [3](#0-2) .
- `create` re-parses the same raw body and dispatches to handlers: `params = JSON.parse(request.raw_post); Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` [4](#0-3) .
- `Handler#stacks`/`repository_name` resolve the target using `payload.dig('repository','full_name')`, a field independent of `repository.owner.login` [5](#0-4) .
- Every pull_request sub-handler independently repeats this pattern: `Shipit::Repository.from_github_repo_name(params.repository.full_name)` [6](#0-5) [7](#0-6) .
- `Repository.from_github_repo_name` does a plain owner/name lookup with no ownership cross-check against the verifying org [8](#0-7) .

Attack: an unprivileged party who is a legitimate customer/admin of "OrgAttacker" (and therefore knows/controls OrgAttacker's configured `webhook_secret`, since they configured that webhook on their own GitHub org) sends `POST /webhooks` with `X-Github-Event: push`, HMAC-SHA1 signed with `OrgAttacker`'s secret, and a body where `repository.owner.login = "OrgAttacker"` (so `verify_signature` picks and passes OrgAttacker's secret) but `repository.full_name = "OrgVictim/some-repo"`. `verify_signature` succeeds; `PushHandler#process` then calls `stacks.not_archived.where(branch:).find_each { |stack| stack.sync_github(...) }` against `OrgVictim`'s stacks [9](#0-8) . The same divergence applies to `CheckSuiteHandler` (`schedule_refresh_check_runs!` on victim's commits) [10](#0-9)  and every pull_request handler that can archive/unarchive review stacks or update PR records belonging to `OrgVictim`.

Existing guards fail to prevent this: `verify_signature` only checks the signature is valid for *some* org derivable from the payload; it does not check that org against `repository.full_name`. `drop_unhandled_event` and `check_if_ping` are unrelated. `ExplicitParameters` schemas only validate field presence/type, not cross-field consistency with the authenticated org. `Repository.from_github_repo_name`/model validations only constrain `owner`/`name` character format, not tenant boundary.

### Impact Explanation
A legitimate but unprivileged tenant of one organization can trigger `GithubSyncJob` (via push), `RefreshCheckRunsJob` (via check_suite), or archive/unarchive review stacks and mutate `PullRequest` records (via pull_request events) for a *different* organization's repositories/stacks that they do not own or administer, matching the Critical category "a payload for one repository mutating another's stack, commit, task or team." This is repeatable for any target repository whose `owner/name` is known and configured in Shipit, and the blast radius spans every tenant hosted on a single multi-org Shipit instance.

### Likelihood Explanation
This requires a Shipit deployment using the multi-organization `secrets.github` schema (nested per-org configs with distinct `webhook_secret`s), which the engine explicitly supports and ships a fixture for (`test/dummy/config/secrets_double_github_app.yml`). The attacker only needs to be a legitimate, unprivileged webhook-sender for *any one* configured org (i.e., control of that org's own webhook secret, which org admins normally have access to when wiring up the webhook) — no access to the victim org's secret is required. In the common single-org legacy config (`github_default_organization.nil?`), `Shipit.github` ignores the passed organization and always uses the single global secret, so this specific divergence has no effect there (only multi-org deployments are exposed).

### Recommendation
In `WebhooksController#verify_signature` (or in `Handler#initialize`), after verifying the signature, assert that the org used to select the webhook secret equals the owner segment of `payload.dig('repository','full_name')` (or `organization.login` for org-only events), rejecting the request with 422 otherwise. Centralize this check in `Handler` so all handlers enforce it uniformly rather than trusting `repository.full_name` unchecked.

### Proof of Concept
Minitest plan (multi-org config, e.g. loading `secrets_double_github_app.yml` fixtures):
```ruby
test "push payload signed for OrgAttacker but targeting OrgVictim repo is rejected" do
  # Arrange: OrgAttacker configured with known webhook_secret "attacker-secret"
  # OrgVictim configured separately; has stack for "orgvictim/target-repo"
  body = {
    ref: 'refs/heads/master',
    after: 'deadbeef',
    repository: { owner: { login: 'orgattacker' }, full_name: 'orgvictim/target-repo' }
  }.to_json
  signature = "sha1=" + OpenSSL::HMAC.hexdigest('sha1', 'attacker-secret', body)

  request.headers['X-Github-Event'] = 'push'
  request.headers['X-Hub-Signature'] = signature

  # Equality under test:
  # repository_owner ("orgattacker") == owner segment of repository.full_name ("orgvictim") ? => false
  assert_no_enqueued_jobs do
    post :create, body:, as: :json
  end
  # Currently FAILS: GithubSyncJob is enqueued for orgvictim/target-repo despite
  # signature being verified only against orgattacker's secret.
end
```
Repeat the pattern for `check_suite` (assert no `RefreshCheckRunsJob` enqueued for victim stack) and `pull_request:opened`/`labeled` (assert no `ReviewStack` created/archived for victim repository) using the same owner/full_name mismatch, confirming the divergence is systemic across `Shipit::Webhooks::HANDLERS`.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
