### Title
Cross-organization webhook signature confusion allows forging CI status to trigger an unauthorized deploy - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the HMAC secret to validate an inbound webhook using `repository.owner.login` (or `organization.login`) taken from the JSON body, but the handler that then acts on the same body (`Handlers::StatusHandler`) looks up the target `Commit` purely by `sha`, with no scoping to the repository/organization whose secret validated the signature. In a multi-organization Shipit deployment (`Shipit.github(organization:)`, documented under "Using Multiple Github Applications"), this breaks the binding: *the organization whose secret authenticated the request* ≠ *the repository/commit that the handler actually writes to*.

### Finding Description
`WebhooksController#verify_signature` resolves the signing secret like this: [1](#0-0) 

`repository_owner` is read directly from the attacker-controlled JSON body: [2](#0-1) 

Because the whole raw body is attacker-controlled, and only the *owner login* field is used to pick which org's `webhook_secret` must sign it, any party that legitimately knows one configured organization's `webhook_secret` (e.g. an org admin who created their own tenant's GitHub App per `docs/setup.md`, "Using Multiple Github Applications") can compute a valid `X-Hub-Signature` for a completely different, forged payload — as long as `repository.owner.login`/`organization.login` in that payload still names their own org.

The event dispatch then acts on the same raw body without re-checking that the acted-upon repository/commit belongs to the organization that authenticated it: [3](#0-2) 

The `status` handler is the clearest sink — it looks up commits **globally by `sha`, with no repository/stack scoping at all**: [4](#0-3) 

`Commit.create_status_from_github!` then writes the attacker-supplied `state`/`description`/`target_url`/`context` directly as a `Status` on that commit: [5](#0-4) 

This status feeds directly into deploy gating logic — `deployable?` uses `success?` (derived from the injected status) and `ci.require`/blocking-status checks: [6](#0-5) 

and into continuous delivery scheduling: [7](#0-6) 

**Equality that should hold but doesn't:**
`organization_whose_secret_verified_signature == organization_owning_the_repository/commit_being_mutated`

Before the attack: the signature-verifying org and the repository being mutated are the same GitHub org, because in normal operation GitHub itself generates and signs the payload for events on repos belonging to the org whose app fired the webhook.

After the attack: an attacker directly POSTs a synthetic body to the public `/webhooks` endpoint. They set `repository.owner.login` (or `organization.login`) to an org whose `webhook_secret` they know (their own tenant in a multi-org Shipit install), correctly sign the raw body with that known secret, but populate the actual state-changing fields (`sha`, `state`, `context`, `target_url`, `description`) to target a `Commit` belonging to an entirely different stack/repository/org tracked by the same Shipit instance. `StatusHandler` performs the lookup with `Commit.where(sha: params.sha)`, which is unscoped by org/repo, so the forged status is applied.

### Impact Explanation
This breaks the "GitHub identity/organization authenticated versus the repository actually written" trust binding called out in scope. By forging a `success` status with a matching required CI `context` on a victim commit, an attacker who only controls one (possibly low-privilege, self-registered) organization's webhook secret in a multi-tenant Shipit instance can make `Commit#deployable?` return true for a victim stack's commit, satisfy `ci.require` checks, and trigger `ContinuousDeliveryJob`/manual deploy eligibility — i.e., an **unauthorized deploy** on infrastructure/repositories the attacker has no legitimate write access to. This matches the "Critical" impact bucket (unauthorized deploy) defined in scope.

### Likelihood Explanation
Requires: (1) the Shipit deployment to use the multi-organization GitHub App configuration (explicitly documented and supported), and (2) the attacker to know the `webhook_secret` of at least one configured organization (plausible if they are the admin who set up their own tenant's GitHub App, as per the setup docs) and (3) the ability to reach the public `/webhooks` endpoint directly (no authentication is required beyond the HMAC check). No repository write access, GitHub App private key, or `ApiClient` token is needed — the only credential needed is a secret the attacker was handed for their own, unrelated organization. Likelihood is medium: it only applies to multi-tenant configurations, but is trivially exploitable once that precondition holds.

### Recommendation
Scope every webhook handler's data lookups to the repository identified by `repository.owner.login`/`organization.login` — the exact field used to select the signing secret — not merely to `full_name`/`sha` in isolation. Concretely:
- In `Shipit::Webhooks::Handlers::Handler`, validate that `payload.dig('repository','owner','login')` (or `organization.login`) matches the repository/stack actually resolved via `repository_name`, and reject otherwise.
- In `StatusHandler`, scope `Commit.where(sha: ...)` to commits whose `stack.repository` belongs to the verified organization, instead of a global, cross-tenant lookup by sha alone.
- More generally, treat the webhook secret as scoped per-organization *and* enforce that every field a handler mutates is nested under the same repository/organization object whose owner login was used for signature verification, rejecting cross-org payload construction.

### Proof of Concept
Conceptual PoC (multi-org Shipit configuration with orgs `attacker-org` and `victim-org`, both tracked by the same Shipit instance, `attacker-org`'s `webhook_secret` known to the attacker):

```
POST /webhooks HTTP/1.1
X-Github-Event: status
X-Hub-Signature: sha1=<HMAC-SHA1(attacker_org_webhook_secret, raw_body)>

{
  "sha": "<victim commit sha belonging to victim-org's stack>",
  "state": "success",
  "context": "ci/required-context",
  "description": "forged",
  "target_url": "https://example.com",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "attacker-org/some-repo" }
}
```

- `verify_signature` resolves `Shipit.github(organization: "attacker-org")` and validates successfully because the attacker knows `attacker-org`'s secret and signed the exact raw body themselves.
- `Shipit::Webhooks::Handlers::StatusHandler.call(params)` runs `Commit.where(sha: params.sha)`, finds the victim commit belonging to a completely different org's stack, and calls `create_status_from_github!`, injecting a fabricated "success" status that can satisfy `deployable?`/`ci.require` and unblock deploys for that victim stack — without the attacker ever having legitimate access to `victim-org`.

module Shipit
  module Webhooks
    module Handlers
      class StatusHandler < Handler
        params do
          requires :sha, String
          requires :state, String
          accepts :description, String
          accepts :target_url, String
          accepts :context, String
          accepts :created_at, String

          accepts :branches, Array do
            requires :name, String
          end
        end

        def process
          Commit.where(sha: params.sha).each do |commit|
            commit.create_status_from_github!(params)
          end
        end
      end
