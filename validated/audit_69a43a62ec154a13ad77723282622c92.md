### Title
Unbounded accumulation of unresolved private-payment chains in `unhandled_private_payments` - (File: network.js)

### Summary
A private-payment counterparty (or a hub relaying on their behalf) can repeatedly send `private_payment`/`private_payments` chains whose head/parent units are not yet known or stable. Each such chain is persisted verbatim into the `unhandled_private_payments` table via `savePrivatePayment()` in `handleOnlinePrivatePayment`, with no limit on the number of queued chains, their aggregate size, or how long they can remain unresolved, mirroring the libevent WS fragmented-frame accumulation bug class (data kept accumulating in a buffer/queue that is never bounded and never forced to complete).

### Finding Description
`handleOnlinePrivatePayment` in `network.js` accepts an array of private elements (`arrPrivateElements`) from any peer/hub and, whenever the referenced unit chain isn't fully known/stable yet (`ifNew`, `ifKnownUnverified`, or a light client with `arrPrivateElements.length > 1`), calls `savePrivatePayment`: [1](#0-0) 
which does an unconditional `INSERT ... INTO unhandled_private_payments (unit, message_index, output_index, json, peer) VALUES (?,?,?,?,?)` with the full serialized JSON of the chain: [2](#0-1) 

There is no cap on:
- the number of rows an attacker-controlled counterparty can insert into `unhandled_private_payments`,
- the total size of the `json` column contents accumulated over time,
- how long a chain can sit unresolved if the sender never provides (or never intends to provide) the missing/unstable parent units.

The only gating mechanism (`db.getIgnore()`, i.e. `INSERT IGNORE`) deduplicates exact `(unit, message_index, output_index)` triples, but an attacker can trivially generate new distinct `(unit, message_index, output_index)` combinations (e.g., by crafting many different fake "head" units referencing different, never-completing chains, or by using distinct `output_index`/`message_index` values) to keep inserting new rows indefinitely. This is directly analogous to the CVE-2026-63495 pattern: content is appended to a growing buffer (`evws->incomplete_frames` there, the `unhandled_private_payments` table/`json` blobs here) keyed on a per-message identifier, with no overall size or count ceiling, and completion depends entirely on a cooperating remote party that need never cooperate.

Both `handlePrivatePaymentChains` (wallet-to-wallet device messages, reachable from any paired device/private-payment counterparty) and the peer/hub `private_payment` justsaying path funnel into this same unbounded sink: [3](#0-2) [4](#0-3) 

Retry/resolution logic (`requestUnfinishedPastUnitsOfPrivateChains`, `handleSavedPrivatePayments`) periodically re-scans the entire `unhandled_private_payments` table: [5](#0-4) 
so a growing table also increases CPU/DB/memory pressure on every periodic scan, compounding the effect over time.

### Impact Explanation
An unprivileged private-payment counterparty (anyone who can send a wallet a "private_payments" device message, or a peer/hub relaying `private_payment` justsayings) can cause unbounded growth of the `unhandled_private_payments` table and its in-memory processing (`JSON.parse(row.json)` on every scan, for every row, every scan cycle). Over time this exhausts disk/DB storage and drives up memory/CPU usage on the receiving node, degrading or halting normal operation (a denial-of-service against a specific wallet/hub node). This does not directly cause double-spend or fund loss, but matches the "network unable to confirm new units" / node resource-exhaustion class of impact from the report, scoped to nodes that receive private payments.

### Likelihood Explanation
High: sending private-payment chains is a normal, permissionless capability of any paired device or private-payment counterparty — no special privileges, signatures beyond normal message signing, or node cooperation are required. Since dedup keys off `(unit, message_index, output_index)`, an attacker can cheaply manufacture unlimited distinct combinations (fabricated head units/indexes) to bypass the `INSERT IGNORE` protection and keep growing the table indefinitely, with no rate limit or storage cap enforced in this code path.

### Recommendation
Add bounds to the unresolved private-payment intake path in `network.js`:
- Enforce a maximum number of pending rows per sender/peer and/or per receiving wallet address in `unhandled_private_payments` (e.g., reject or evict when exceeding a threshold).
- Enforce a maximum total serialized size for the stored `json` blob and reject oversized/implausible chains before insertion (similar to `isTooDeeplyNestedOrHasTooManyNodes` checks used elsewhere for device messages).
- Add an expiration/purge policy for old unresolved entries independent of successful resolution (there is a 1-day purge only for a narrow "missing units" branch in `requestUnfinishedPastUnitsOfPrivateChains`; extend equivalent aging/eviction to all unresolved rows, not just that branch).
- Rate-limit repeated `private_payment(s)` submissions from the same peer/device.

### Proof of Concept
1. As any paired device (private-payment counterparty), repeatedly send `private_payments` device messages to a victim wallet, each containing a synthetic `arrPrivateElements` chain whose head unit is a distinct, never-broadcast/never-completable fake unit hash, with distinct `message_index`/`output_index` values to defeat the `INSERT IGNORE` dedup key.
2. Each submission flows through `handlePrivatePaymentChains` → `network.handleOnlinePrivatePayment` → `savePrivatePayment`, which unconditionally inserts a new row into `unhandled_private_payments` because the referenced unit is unknown (`ifNew`) and thus never resolves.
3. Repeat at high volume; observe `unhandled_private_payments` table size and process memory/CPU (from repeated full-table scans in `handleSavedPrivatePayments`/`requestUnfinishedPastUnitsOfPrivateChains`) grow without bound until disk or memory exhaustion on the victim node.
