### Title
API-scoped `ApiClient` tokens can read CCMenu status for any stack, bypassing the token's `stack_id` scope - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::ApiClient` supports scoping a token to a single stack (`stack_id`), and `Api::BaseController#stack` correctly enforces this by resolving stacks through the scoped `stacks` collection (`stacks.from_param!`). `Api::CCMenuController`, however, overrides `#stack` to call `Stack.from_param!(params[:stack_id])` directly on the unscoped `Stack` model, never going through the `stacks` scoping helper. This mirrors the report's bug class: a data/authorization structure ("what stacks this token authorizes") is defined for N cases, but the code path that actually acts (reads CCMenu status) only checks a subset — in this instance zero — of that scope, exactly like the Bronze-tier loop never touching bits 24-31.

### Finding Description
`Shipit::ApiClient#stack_id` and `permissions` define what a token may access. `Api::BaseController` enforces this binding for every other API resource: [1](#0-0) 
`stacks` returns `Stack.where(id: current_api_client.stack_id)` when the client is scoped, else `Stack.all`, and `stack` resolves via that scoped relation.

`Api::CCMenuController` requires the `read:stack` permission (the same permission check applies), but its `stack` method bypasses the scoped `stacks` helper entirely and resolves against the full `Stack` table: [2](#0-1) 

The binding that should hold is: *the set of stacks a token authorizes == the set of stacks the CCMenu endpoint touches*. Before the break: for the generic `Api::StacksController`/`BaseController` resources this equality holds because `stack`/`stacks` are always derived from `current_api_client.stack_id`. After the break: for `CCMenuController#show`, `stack` is derived from `Stack.from_param!(params[:stack_id])` with no reference to `current_api_client` at all, so any authenticated token — even one explicitly scoped to a single stack via `stack_id` — can query the CCMenu XML for every other stack in the installation by simply changing the `stack_id` route/query parameter.

### Impact Explanation
This is an authorization-scope escalation: a token that was deliberately restricted to one stack (e.g., issued by `CCMenuUrlController#client`, which creates `read:stack`-scoped tokens bound to a specific stack) can be used to read task/deploy status (`lastBuildStatus`, `lastBuildLabel`, `activity`, etc.) for any stack in the Shipit instance, not just the one it was authorized for. This matches the "unauthenticated/unauthorized read of stack state" High-impact category, since it lets an attacker who obtains one legitimately-scoped, low-privilege CCMenu token enumerate and read state for stacks they were never granted access to.

### Likelihood Explanation
Likelihood is high given a valid token: `CCMenuUrlController#fetch` (in `app/controllers/shipit/ccmenu_url_controller.rb`) automatically mints an `ApiClient` scoped with `permissions: %w[read:stack]` and bound to the current stack, and exposes its `authentication_token` embedded in a CCMenu URL to any user who can view a stack page. Any holder of one such URL/token can trivially swap the `stack_id` in the request path to target other stacks, since `CCMenuController#stack` never consults `current_api_client.stack_id`.

### Recommendation
Change `Api::CCMenuController#stack` to resolve through the scoped collection, consistent with the rest of the API:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
removing the local override so it inherits `Api::BaseController#stack`/`#stacks`, ensuring the token's `stack_id` scope is always enforced.

### Proof of Concept
1. On a stack `A`, visit the CCMenu URL feature to obtain a scoped token: `GET /A/ccmenu_url` → returns `ccmenu_url` containing `token=<T>` where `T` is an `ApiClient` with `permissions: ["read:stack"]` and `stack_id` set to `A`'s id.
2. Using that same token `T`, request CCMenu status for a different stack `B`:
   `GET /api/stacks/B/ccmenu.xml?token=<T>`
3. Because `Api::CCMenuController#stack` calls `Stack.from_param!(params[:stack_id])` instead of the scoped `stacks.from_param!`, the request succeeds and returns stack `B`'s deploy status/activity, even though token `T` was only authorized for stack `A`.
