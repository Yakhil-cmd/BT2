### Title
Webhook signature is verified against the organization derived from `repository.owner.login`, but every event handler resolves and mutates the target repository/stack using the unverified `repository.full_name` field from the same payload - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which organization's `webhook_secret` to check the HMAC against using `repository_owner`, taken from `params.dig('repository', 'owner', 'login')` (or `organization.login`) [1](#0-0) . Once the signature check passes, `WebhooksController#create` hands the *entire raw payload* to the registered handlers [2](#0-1) , and every handler resolves the repository/stack to act on using a different field, `payload.dig('repository', 'full_name')` [3](#0-2) , via `Repository.from_github_repo_name` [4](#0-3) . Nothing ties `repository.owner.login` (the field the signature check trusts) to `repository.full_name` (the field the handlers trust). This is structurally the same class of bug as the report: two different fields of the same attacker-influenced input are used for two different purposes (identity binding vs. state-mutating action), and no invariant enforces they refer to the same entity.

### Finding Description
Shipit supports hosting multiple GitHub organizations from a single instance, each with its own GitHub App and its own `webhook_secret`, as documented in `docs/setup.md` and implemented by `Shipit.github(organization:)` / `Shipit.github_app_config` [5](#0-4) .

For every inbound webhook, `verify_signature` does:
```ruby
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
```
where `repository_owner` reads `repository.owner.login` (or `organization.login`) straight out of the untrusted JSON body [6](#0-5) . This only proves the request was HMAC-signed with the webhook secret belonging to *that org*.

The `create` action then dispatches the same raw payload to handlers such as `PushHandler`, `StatusHandler`, `PullRequest::OpenedHandler`, etc. Every one of them determines the actual `Repository`/`Stack` to mutate via `repository.full_name`:
```ruby
def repository_name
  payload.dig('repository', 'full_name')
end
``` [7](#0-6) , and `Repository.from_github_repo_name` parses `owner/name` from that string to find the DB record and trigger sync/status/pull-request state changes [4](#0-3) . A legitimate GitHub-generated webhook always has `repository.owner.login` match the owner segment of `repository.full_name`, so this discrepancy never surfaces normally. But the signature only certifies "this byte stream was HMAC-signed with organization X's secret" — it says nothing about internal consistency of the JSON fields inside that byte stream.

Since any operator/administrator who legitimately owns a GitHub App installation for their own organization knows that organization's `webhook_secret` (it's a secret they configure themselves in `config/secrets.yml` for their own org), they can sign an arbitrary payload with their own org's secret while setting `repository.owner.login` to their own org (satisfying `verify_signature`) but `repository.full_name` to `"other-org/other-repo"` (satisfying the handler's repository lookup). This crosses the binding: *organization that authenticated* (`repository.owner.login`, checked against org A's secret) vs. *repository actually written* (`repository.full_name`, used unchecked by every handler).

### Impact Explanation
Exploiting this lets a user who administers one onboarded GitHub organization (org A) on a shared Shipit instance forge webhook events that are processed as if they came from a different organization's repository (org B), without ever needing org B's webhook secret. Depending on event type this enables:
- `push`: force `GithubSyncJob` to run against org B's stack with an attacker-chosen `expected_head_sha`, driving unauthorized deploy/build activity on a repository the attacker does not control [8](#0-7) .
- `pull_request` events: spoof provisioning/archival/label state transitions and pull request metadata updates on org B's review stacks [9](#0-8) .
- `status`/`check_suite`: inject fabricated commit statuses/check-run refresh triggers for org B's commits.

This is a cross-organization/cross-repository write performed by an attacker who only controls one tenant's credentials on the shared instance — matching the Critical "cross-repository writes / unauthorized deploy" impact bucket. Actual severity depends on the deployment model: this only matters on multi-organization Shipit installs where mutually untrusted organizations are hosted on the same instance (as `docs/setup.md`'s "Using Multiple Github Applications" section explicitly supports).

### Likelihood Explanation
Requires: (1) the Shipit instance to be configured for multiple GitHub organizations (a documented, supported configuration), and (2) the attacker to control one onboarded organization's webhook secret — which, in a multi-tenant hosting scenario, is exactly the credential a "legitimate but less-trusted tenant" is expected to have. No GitHub App private key, session, or `ApiClient` token is needed; only the ability to send an arbitrary signed HTTP POST to the shared `/webhooks` endpoint. The mismatch between `repository.owner.login` and `repository.full_name` is never validated anywhere in `WebhooksController` or `Handler`.

### Recommendation
In `WebhooksController#verify_signature` (or in `Shipit::Webhooks::Handlers::Handler`), assert that `params.dig('repository', 'owner', 'login')` and the owner segment of `params.dig('repository', 'full_name')` refer to the same organization before processing, e.g.:
```ruby
def consistent_repository_owner?
  owner_login = params.dig('repository', 'owner', 'login')
  full_name_owner = params.dig('repository', 'full_name')&.split('/')&.first
  owner_login.blank? || full_name_owner.blank? || owner_login.casecmp?(full_name_owner)
end
```
and `head(422)` if this fails, before dispatching to handlers.

### Proof of Concept
1. Configure Shipit with two organizations, `OrgA` and `OrgB`, each with its own GitHub App and `webhook_secret` (per `docs/setup.md`'s multi-org example), and onboard a repository from each (e.g. `OrgA/repo-a`, `OrgB/repo-b`), each tracked by a Shipit `Stack`.
2. As the administrator/attacker for `OrgA`, who knows `OrgA`'s `webhook_secret`, craft a `push` event JSON body:
   ```json
   {
     "ref": "refs/heads/main",
     "after": "<attacker-chosen sha>",
     "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/repo-b" }
   }
   ```
3. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(OrgA_webhook_secret, raw_body)>` and POST it to the Shipit `/webhooks` endpoint (mounted per `config/routes.rb`) with header `X-Github-Event: push`.
4. `verify_signature` resolves `repository_owner` = `"OrgA"`, loads `OrgA`'s `GitHubApp`, and the signature verifies successfully [10](#0-9) .
5. `PushHandler#process` resolves `Repository.from_github_repo_name("OrgB/repo-b")` and enqueues `GithubSyncJob` against `OrgB`'s stack with the attacker-supplied `expected_head_sha`, even though the attacker never possessed `OrgB`'s webhook secret [8](#0-7) , [4](#0-3) .

      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
