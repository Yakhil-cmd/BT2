### Title
Webhook signature verification keyed on `repository.owner.login` while event routing trusts the unrelated `repository.full_name` field, allowing cross-organization webhook forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` is used to validate the HMAC signature based on `params.dig('repository', 'owner', 'login')` (falling back to `params.dig('organization', 'login')`). Every downstream handler, however, resolves the target `Stack`/`Repository` using a completely different field, `payload.dig('repository', 'full_name')`. Because the signature only proves that *some* configured organization's secret was used, and not that the organization matches the repository being acted upon, an attacker who legitimately owns one Shipit-tracked GitHub organization (and therefore knows its own `webhook_secret`) can forge a payload whose `repository.owner.login` matches their own org (to pass verification) while `repository.full_name` names a completely different, victim-owned stack tracked by the same Shipit instance.

### Finding Description
The binding that should hold is: `organization that authenticated == repository that is acted upon`. Instead:

- Verification side: [1](#0-0)  looks up `github_app = Shipit.github(organization: repository_owner)` and calls `github_app.verify_webhook_signature(signature, raw_post)`, where `repository_owner` is defined as [2](#0-1) , i.e. `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`. This value comes straight from the JSON body and only determines *which* configured secret is used for the HMAC comparison; it does not otherwise constrain the rest of the payload.
- Signature computation itself is a plain HMAC-SHA1 over the raw request body using that selected secret (`OpenSSL::HMAC.hexdigest` in `verify_webhook_signature`) — see [3](#0-2) . Since Shipit supports "bring your own GitHub App per organization" multi-tenant configuration (documented in `docs/setup.md` "Using Multiple Github Applications"), an org's own administrator legitimately knows that org's `webhook_secret` because they created the GitHub App themselves.
- Action side: every webhook `Handler` subclass resolves the target stack independently of `repository_owner`, using only `repository.full_name`: [4](#0-3) . `PushHandler#process`, for example, uses this to load stacks and immediately triggers `stack.sync_github(expected_head_sha: params.after)` for any stack matching the branch: [5](#0-4) .

Because `repository.owner.login` (used to pick the verification key) and `repository.full_name` (used to pick the acted-upon repository/stack) are two independent, attacker-supplied fields inside the same self-signed JSON body, nothing forces them to refer to the same repository. An attacker who controls Org A (and thus knows Org A's `webhook_secret`) can:
1. Build a raw JSON body with `repository.owner.login = "orgA"` and `repository.full_name = "orgB/victim-repo"` (or any other repository already tracked in the Shipit instance).
2. Compute a valid `X-Hub-Signature` using Org A's secret over that exact body.
3. POST it to `/webhooks` with `X-Github-Event: push` (or `status`, `check_suite`, etc.).

`verify_signature` succeeds because it only checks that the signature matches Org A's secret — it never checks that Org A actually owns `orgB/victim-repo`. The handler then processes the forged event against `orgB`'s stack using entirely attacker-chosen fields (`ref`, `after`/SHA for push; state/context for status; etc.), even though the attacker has no GitHub access to `orgB` at all.

### Impact Explanation
This breaks the deployment-trust binding "organization authenticated == repository written," letting an unprivileged (per-org) attacker forge GitHub events against any other Shipit-tracked stack:
- Forged `push` events can trigger `GithubSyncJob`/`stack.sync_github` with an attacker-chosen `expected_head_sha`, causing Shipit to sync a victim stack against a commit the attacker names, without any real push happening in the victim's actual repository.
- Forged `status`/`check_suite` events can inject fabricated commit statuses or check-run results for a victim's commits, which Shipit's merge/deploy safety logic (e.g., "wait for CI green before merge/deploy") relies on — effectively spoofing CI outcomes that gate unauthorized ships/merges.
This aligns with the High-severity bucket: escalation of trust across repositories via a webhook whose authentication is not properly scoped, unauthenticated manipulation of stack/task state, and a plausible path to an unauthorized deploy/merge if a merge-queue or deploy-gate condition can be satisfied by a forged status.

### Likelihood Explanation
The precondition is only that the attacker legitimately administers at least one GitHub organization that is configured in the same multi-tenant Shipit instance (a documented, supported configuration — `docs/setup.md`, "Using Multiple Github Applications"). Such an attacker is otherwise unprivileged with respect to any other org's stacks. No GitHub write access to the victim repository, no Shipit session, and no knowledge of the victim's `webhook_secret` are required — only knowledge of their own org's secret, which they legitimately possess by having created their own GitHub App. This makes the attack realistically reachable in any multi-org deployment of shipit-engine.

### Recommendation
Bind the verification key to the same repository identity that handlers act upon:
- Resolve the target `Repository`/`Stack` from `repository.full_name` first, derive its owning organization from that persisted record (not from the attacker-supplied `repository.owner.login`/`organization.login`), and use that organization's `webhook_secret` to verify the signature.
- Alternatively, after verifying the signature with the org selected from `repository_owner`, explicitly assert that `repository_owner` matches the owner segment of `repository.full_name` before dispatching to handlers, rejecting (422) on mismatch.

### Proof of Concept
1. Configure two organizations in `secrets.yml`, `orgA` (attacker-controlled, secret known to attacker) and `orgB` (victim, tracked in Shipit with an existing `Stack`).
2. Attacker crafts a JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "orgA" },
    "full_name": "orgB/victim-repo"
  }
}
```
3. Compute `X-Hub-Signature: sha1=<hmac-sha1(orgA_webhook_secret, body)>`.
4. `POST /webhooks` with header `X-Github-Event: push` and the crafted body/signature.
5. `WebhooksController#verify_signature` looks up `Shipit.github(organization: "orgA")` (from `repository.owner.login`), verifies successfully against Org A's secret (`app/controllers/shipit/webhooks_controller.rb:24-38`, `lib/shipit/github_app.rb:76-83`).
6. `PushHandler#process` resolves stacks via `repository.full_name = "orgB/victim-repo"` (`app/models/shipit/webhooks/handlers/handler.rb:32-38`) and calls `stack.sync_github(expected_head_sha: params.after)` (`app/models/shipit/webhooks/handlers/push_handler.rb:12-17`) for Org B's stack — despite the request being authenticated only against Org A's secret.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
