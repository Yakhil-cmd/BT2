### Title
Accrual `scaled_to_original` overflow permanently freezes a high-utilization market before the borrow-index cap can engage - ([File: common/src/rates/simulate.rs](common/src/rates/simulate.rs))

### Summary
The MySQL CVE is a crash/hang DoS in a core computation. The analog is a permanent market freeze: interest accrual computes `scaled_to_original(borrowed, borrow_index)` via a panicking `Ray::mul` before the `MAX_BORROW_INDEX_RAY` cap in `update_borrow_index` can clamp growth. On a large market sustained at high utilization, the RAY-scaled borrowed value crosses `i128::MAX` while the index is still below its cap, and every subsequent operation on that market — `update_indexes`, `withdraw`, `repay`, `borrow`, `liquidate` — panics with `MathOverflow`, because every verb accrues first.

### Finding Description
`accrue_step` computes utilization from unscaled originals at the very top of the step: [1](#0-0) . `scaled_to_original` is `scaled.mul(env, index)`, which panics with `GenericError::MathOverflow` when `scaled * index / RAY` exceeds `i128` [2](#0-1) . The index cap is applied only later inside `update_borrow_index`, after the vulnerable multiply — so the value ceiling is hit before the index ceiling [3](#0-2) . The same unscaling runs on every verb through `Cache::calculate_utilization` and the pool's `interest::global_sync` [4](#0-3) . An existing characterization test confirms the freeze: after the cliff, `try_update_indexes_for`, `try_withdraw_raw`, and `try_repay` all fail with `MATH_OVERFLOW` while `borrow_index < MAX_BORROW_INDEX_RAY` [5](#0-4) .

### Impact Explanation
Permanent freezing of funds: once `scaled_to_original` overflows, no supplier can withdraw and no borrower can repay or be liquidated on that market — all supplied tokens and accrued yield are locked forever, and bad debt cannot be resolved. This is a protocol-wide loss confined to the affected market book, matching the accepted "permanent freezing of funds" impact class.

### Likelihood Explanation
No privileged action is required: an unprivileged address creates the condition by supplying a very large balance and holding high utilization (the test uses ~1B×10^18 units at 98% utilization on the XLM curve). The trigger is purely time-driven accrual via the permissionless `update_indexes` — anyone can keep accruing until the cliff. Reachability is gated by economic scale (a whale-scale deposit on a steep rate curve), so it is a Medium-severity, slow-burn DoS rather than an instantly reachable freeze.

### Recommendation
Use saturating/unscaled-aware math at the accrual entry: compute utilization from `mul_div_floor_saturating` (or clamp `scaled_to_original` at `i128::MAX`) inside `accrue_step`/`calculate_utilization`, and/or check `borrow_index >= MAX_BORROW_INDEX_RAY` before unscaling so the cap short-circuits accrual instead of panicking. Reorder so the index cap is evaluated before any value multiplication that can exceed `i128`.

### Proof of Concept
See `tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:321-361`: supply `principal = 1e9 * 10^18` of an 18-decimal market on the XLM curve, borrow 98% of it, advance time ~years while calling `update_indexes`; accrual eventually panics with `MATH_OVERFLOW` at `borrow_index < MAX_BORROW_INDEX_RAY`, and subsequent `withdraw`/`repay` calls revert identically — the market is bricked.

pub fn update_borrow_index(env: &Env, old_index: Ray, interest_factor: Ray) -> Ray {
    let new_index = old_index.mul(env, interest_factor);
    if new_index.raw() > MAX_BORROW_INDEX_RAY {
        return Ray::from(MAX_BORROW_INDEX_RAY);
    }
    new_index
}
