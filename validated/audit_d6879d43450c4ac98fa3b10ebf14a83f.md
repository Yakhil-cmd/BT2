## Title
CCMenu API token authorizes `read:stack` globally but is not bound to the specific `stack_id` it was issued for, allowing cross-stack status disclosure - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::CCMenuController` authenticates a request using a per-stack CCMenu token (an `ApiClient` scoped to one stack via `stack_id`) but resolves the target stack directly from the `stack_id` URL parameter instead of the `BaseController#stack`/`#stacks` helpers that enforce `current_api_client.stack_id` scoping. This breaks the binding "stack a token authorises == stack it touches," letting a holder of any legitimate CCMenu token read the build/deploy status of any other stack in the Shipit instance.

### Finding Description
The normal API scoping mechanism lives in `Shipit::Api::BaseController`: [1](#0-0) 

`stacks` restricts the queryable set to `current_api_client.stack_id` when the client is scoped to one stack, and `stack` uses that scoped relation to resolve `params[:stack_id]`. This is exactly the enforcement of the equality: `token.stack_id == stack.id` (or "any stack" for unscoped clients).

`CCMenuController`, however, overrides `stack` to bypass this scoping entirely: [2](#0-1) 

It only calls `require_permission :read, :stack`, which invokes `current_api_client.check_permissions!(operation, scope)`: [3](#0-2) 

`check_permissions!` only checks that the string `"read:stack"` is present in the client's `permissions` array — it never compares `current_api_client.stack_id` to the requested `params[:stack_id]`. Because `CCMenuController#stack` does `Stack.from_param!(params[:stack_id])` directly (mirroring `CCMenuUrlController#stack`, which resolves the stack the token was minted for): [4](#0-3) 

there is no code path that verifies the authenticated CCMenu client's `stack_id` equals the `stack_id` being requested.

**Binding broken:** `token.stack_id (authorized stack) == params[:stack_id] (stack touched)` — this equality is enforced in the generic `BaseController#stack`/`#stacks` path but is absent in `CCMenuController`, which defines its own unscoped `stack` method.

### Impact Explanation
CCMenu tokens are intentionally low-privilege, single-purpose `read:stack` credentials generated per stack (e.g., embedded in CI dashboard tools, CCMenu XML feed clients, status badges) and are handed to less-trusted contexts than the main Shipit session, per `CCMenuUrlController#client`: [5](#0-4) 

Anyone who legitimately possesses one such token (which is transmitted in a plain URL query string, `?token=...`, and thus more exposure-prone than session cookies) can swap the `stack_id` path segment and read deploy/rollback status (`latest_deploy`, `deploys_and_rollbacks`) for every other stack hosted by the Shipit instance — including stacks belonging to different repositories/teams they were never authorized to see. This matches the in-scope High-impact category "unauthenticated read of stack state... " via escalation beyond the token's authorized stack scope.

### Likelihood Explanation
Likelihood is high for anyone already holding a valid (even minimally-scoped) CCMenu token: the attack requires zero additional privilege escalation, no signature forgery, and no interaction with GitHub credentials — only changing a URL parameter (`stack_id`) on an otherwise-valid authenticated request. CCMenu tokens are designed to be embedded in low-trust environments (CI dashboards, badges), making leakage/possession by an unprivileged party plausible.

### Recommendation
Make `CCMenuController#stack` (and any other controller that defines its own `stack`/`stacks` bypassing `BaseController`) resolve the stack through the scoped `stacks` relation, e.g.:

```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```

so that a client scoped to `stack_id: N` cannot resolve any stack other than `N`, consistent with the enforcement already present in `Shipit::Api::BaseController`.

### Proof of Concept
1. A user requests a CCMenu URL for `stack_id: A` via `CCMenuUrlController#fetch`, receiving `https://shipit.example.com/api/stacks/A/ccmenu.xml?token=<token-A>` where `<token-A>` authenticates an `ApiClient` with `stack_id = A`, `permissions = ["read:stack"]`.
2. This URL/token is embedded in a public or semi-public consumer (CI badge, dashboard).
3. An unprivileged party who obtains `<token-A>` sends: `GET /api/stacks/B/ccmenu.xml?token=<token-A>` for an arbitrary other stack `B`.
4. `authenticate_api_client` succeeds (token A is valid), `require_permission :read, :stack` succeeds (`token A` has `read:stack`), and `stack` resolves to `Stack.from_param!("B")` — unrelated to the token's `stack_id`.
5. The response renders stack `B`'s latest deploy/rollback status, disclosing information the token was never authorized to access.
