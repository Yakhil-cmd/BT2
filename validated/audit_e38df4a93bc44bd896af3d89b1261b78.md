## Finding: TOCTOU Race in Divisible Private-Asset Spend-Tracking Allows Double-Spend of a Private Output

### Title
Race Condition in Divisible Private Payment Validation Permits Double-Spending of the Same Private Output — (File: `divisible_asset.js`)

### Summary
`validateAndSaveDivisiblePrivatePayment` in `divisible_asset.js` follows the same unsafe **CHECK → CREATE → mark-consumed** pattern described in the Homarr CVE: the "is this input already spent" check is performed in one step (`validateDivisiblePrivatePayment`), and the consumption of the spent output (`UPDATE outputs SET is_spent=1 ...`) happens later, unconditionally, with **no `AND is_spent=0` guard** tying the update to the state that was checked. [1](#0-0) 

Because two private payment chains referencing the same source output can be validated concurrently (each chain gets its own connection/transaction, and multiple chains are explicitly processed "in parallel"), both validations can read `is_spent=0` before either commits its `UPDATE`, allowing both spends to be accepted.

### Finding Description
`validateAndSaveDivisiblePrivatePayment(conn, objPrivateElement, callbacks)` inserts the new outputs/inputs for a private divisible-asset chain and marks the *source* output consumed: [2](#0-1) 

The `UPDATE outputs SET is_spent=1 WHERE unit=? AND message_index=? AND output_index=?` on line 67–70 has no `is_spent=0` condition, meaning it always succeeds regardless of the row's current state — it does not use the row itself as the synchronization primitive. Compare this to the indivisible-asset equivalent, `validateAndSavePrivatePaymentChain` in `indivisible_asset.js`, which correctly guards the same operation with `AND is_spent=0`: [3](#0-2) 

The actual "is this output already spent" check for the divisible case happens earlier, in a separate call (`validateDivisiblePrivatePayment`), decoupled in time from the later `UPDATE`. Each private-payment chain is validated and saved inside its own `BEGIN ... COMMIT` transaction taken from the connection pool in `private_payment.js`: [4](#0-3) 

There is no lock (no `mutex.lock` keyed by the source `unit/message_index/output_index`) serializing concurrent validations of chains that spend the same private output. Multiple chains are explicitly handled concurrently: `handleSavedPrivatePayments` in `network.js` iterates unhandled private payments with `async.each` and the comment states this is intentional — "handle different chains in parallel": [5](#0-4) 

Additionally, `handlePrivatePaymentChains` in `wallet.js` validates each incoming chain from a `private_payments` device message via `network.handleOnlinePrivatePayment`, and a malicious counterparty (device contact) can deliver two conflicting private chains (spending the same source output to two different destinations) through separate messages/paths that race each other: [6](#0-5) [7](#0-6) 

### Impact Explanation
A malicious private-payment counterparty (payer) can construct two divisible private payment chains that both spend the same source private output — one sent to the actual recipient and one crafted to spend the identical output elsewhere (e.g., back to the attacker, or to a colluding second recipient) — and deliver both concurrently. Because the spent-check and the spent-mark are not atomic and not covered by a serializing lock, both chains can pass validation on the victim's node before either `is_spent=1` update commits, resulting in the same private funds being accepted as valid twice. This is a genuine double-spend of asset value at the wallet level (the recipient believes they received/hold funds that were also spent elsewhere), which can result in unauthorized loss of funds for whichever party relied on the second, conflicting spend, and in general leads to disagreement between honest nodes/wallets about which spend of the output is valid.

### Likelihood Explanation
Triggering this requires only being the sender (a private-payment counterparty) of a divisible private asset and controlling the timing of two chain deliveries to the victim — no privileged network position, hub compromise, or peer manipulation is needed. The relevant code paths (`handleOnlinePrivatePayment`, `handleSavedPrivatePayments`, `handlePrivatePaymentChains`) are all reachable via ordinary device/chat messages exchanged between correspondents. The explicit design decision to process multiple private chains "in parallel" (per code comment) increases the practical window for the race.

### Recommendation
- Make the "spend" atomic and self-checking: change the `UPDATE outputs SET is_spent=1 WHERE unit=? AND message_index=? AND output_index=?` in `divisible_asset.js` (line 67–70) to include `AND is_spent=0`, and check the affected row count; if zero rows were affected, fail the chain as a double-spend, mirroring the pattern already used in `indivisible_asset.js` (line 287).
- Serialize concurrent validation of private chains that reference the same source output (e.g., `mutex.lock(['priv-'+src_unit+'-'+src_message_index+'-'+src_output_index], ...)`) before performing the check-then-update sequence, similar to the `private_write` mutex already used elsewhere in `validation.js` for double-spend acceptance bookkeeping.

### Proof of Concept
1. Attacker (payer) creates a divisible private asset chain with source output `O` and builds two conflicting spend chains: Chain A (`O` → victim wallet W1) and Chain B (`O` → attacker-controlled wallet W2).
2. Attacker sends Chain A and Chain B nearly simultaneously to the same victim (or to two different wallets that each hold a copy of the private history) via `private_payments` device messages, such that both trigger `handleOnlinePrivatePayment` → `private_payment.js`'s `validateAndSavePrivatePaymentChain` on separate DB connections.
3. Both validations independently query the "is this already spent" state via `validateDivisiblePrivatePayment` before either has committed its transaction, so both observe `O` as unspent.
4. Both proceed to `INSERT` their outputs/inputs and execute the unguarded `UPDATE outputs SET is_spent=1 ...` (`divisible_asset.js` line 67–70); since the update is unconditional, both commits succeed.
5. Result: output `O` is recorded as spent twice, into two different destination chains, causing wallets to disagree about valid ownership of the double-spent funds.
