### Title
Cross-organization webhook confusion allows CI-status/push spoofing for a repository whose organization was never authenticated - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` picks the GitHub App (and therefore the `webhook_secret`) used to validate an inbound webhook from an attacker-controlled JSON field, while the handlers that actually mutate data (`PushHandler`, `StatusHandler`, etc.) resolve the target `Stack`/`Repository`/`Commit` from a *different* attacker-controlled field in the same unverified body. Nothing ties these two fields together, so the organization whose secret authenticated the request is not guaranteed to be the organization whose repository gets written.

### Finding Description
`verify_signature` selects the verifying `GitHubApp` using: [1](#0-0) 
where `repository_owner` is read straight out of the unauthenticated raw POST body: [2](#0-1) 

`Shipit.github(organization:)` looks up per-organization config (`Shipit::TOP_LEVEL_GH_KEYS`, multi-org support documented in `docs/setup.md` under "Using Multiple Github Applications") and each organization can have its own, independently-set `webhook_secret`, which is explicitly allowed to be left blank (`webhook_secret: # nil` in `config/secrets.development.example.yml` and `config/secrets.development.shopify.yml`). `GitHubApp#verify_webhook_signature` short-circuits to `true` whenever that organization's `webhook_secret` is unset: [3](#0-2) 

Meanwhile, every webhook `Handler` resolves the `Stack`/`Repository` it will act on from a **separate** field of the same body: [4](#0-3) 

and handlers such as `PushHandler` use this repository-scoped lookup to sync commits/trigger jobs directly: [5](#0-4) 

The `status` webhook handler writes a `Status` record on an existing `Commit` directly from unverified payload fields (`state`, `target_url`, `description`, `context`), as shown by the controller test asserting a `Commit#statuses` row is created verbatim from the payload: [6](#0-5) 

The equality that should hold is: **organization authenticated by `verify_signature` (`repository.owner.login`) == organization/repository actually mutated by the handler (`repository.full_name`)**. No code enforces this. Because `repository.owner.login` alone decides which secret (if any) validates the request, and a webhook-secret-less organization validates unconditionally, an attacker only needs one Shipit-tracked organization configured without a `webhook_secret` to author a payload whose `repository.owner.login` names that unsecured organization (satisfying `verify_signature` with no secret at all) while `repository.full_name`/`repository.owner.login` used deeper in the payload names an entirely different, secret-protected organization/repository that Shipit also tracks. The handler then acts on that unrelated repository's `Stack`/`Commit` records.

### Impact Explanation
This lets an unauthenticated attacker write CI `Status` rows (used by `ci.require` deployability checks, see `README.md` "ci.require") or trigger `sync_github`/commit ingestion for a `Stack` belonging to an organization whose webhook secret the attacker never possessed and never needs to guess. Forged "success" statuses can satisfy `ci.require` gating and continuous-deployment eligibility on a targeted stack, leading toward an unauthorized deploy — matching the report's underlying bug class of a value (here, the authenticating organization) being trusted for an action (mutating a different repository's records) it was never actually verified for, exactly mirroring the collateral/`redemptionCooldownPeriod` binding break in the reference report (a state transition trusted for an entity it doesn't actually correspond to).

### Likelihood Explanation
Likelihood is Low/conditional: it requires the deployment to run in the documented multi-organization webhook mode (`docs/setup.md`) with at least one configured organization left without a `webhook_secret` (an explicitly supported configuration shown in the shipped example secrets files) while other organizations are still tracked by the same Shipit instance. This is a plausible real-world misconfiguration precisely because the engine's own example configs show `webhook_secret: # nil` as valid.

### Recommendation
- Cross-validate that `repository.owner.login` (used to select the verifying `GitHubApp`) matches the owner embedded in `repository.full_name` before dispatching to any handler.
- Do not allow silent, unconditional pass-through in `verify_webhook_signature` when `webhook_secret` is blank for a multi-org configuration; either require a secret whenever more than one organization is configured, or scope handler repository resolution strictly to the same organization used for verification.
- Reject webhooks whose `repository.owner.login` does not correspond to the `Repository` ultimately resolved by `Handler#repository_name`.

### Proof of Concept
1. Configure Shipit with two organizations per `docs/setup.md`'s multi-app format: `OrgWeak` (no `webhook_secret` set) and `OrgTarget` (secret set, tracking a real `Stack`).
2. POST to `/webhooks` with header `X-Github-Event: status` and body:
   ```json
   {
     "sha": "<commit sha belonging to OrgTarget/repo>",
     "state": "success",
     "context": "ci/required-check",
     "repository": { "full_name": "OrgTarget/repo", "owner": { "login": "OrgWeak" } }
   }
   ```
3. `verify_signature` resolves `repository_owner` = `"OrgWeak"`, whose `webhook_secret` is unset, so `verify_webhook_signature` returns `true` regardless of any `X-Hub-Signature` value (none required).
4. The `status` handler resolves the target `Commit`/`Stack` via `repository.full_name` = `"OrgTarget/repo"`, and writes a fabricated successful `Status`, potentially satisfying `ci.require` for `OrgTarget`'s stack without ever touching `OrgTarget`'s webhook secret.

Note: I could not view the full body of `app/models/shipit/webhooks/handlers/status_handler.rb` before running out of tool calls (a file-read attempt failed due to a missing parameter), so the exact status-handler implementation is inferred from `app/models/shipit/webhooks/handlers/handler.rb`'s shared `repository_name`/`stacks` resolution and the controller test's observed behavior rather than from reading that file directly. This should be verified directly against `status_handler.rb` before treating the PoC as final.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
# frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
    end
  end
end
```
