### Title
Confirmation-dialog suppression via amount-heuristic lets a cosigner disguise an unrelated payment as an innocuous contract signature - ([File: wallet.js])

### Summary
`ocore`'s multi-device signing flow (`getSigner().sign()` in `wallet.js`) decides which human-facing confirmation event to fire — `confirm_contract_deposit`, `confirm_contract_claim`, `confirm_contract_sign`, or the generic `confirm_on_other_devices` — by *heuristically re-interpreting* the exact unit that is about to be cryptographically signed. This heuristic classification, not the actual signed argv, is what the paired-device UI shows the user before they approve. The classification and the object actually hashed/signed (`buf_to_sign = objectHash.getUnitHashToSign(objUnsignedUnit)`) can diverge, mirroring the OpenClaw bug class: the approval surface displays a benign, narrow interpretation ("this is just a contract deposit/claim/sign") while the thing that gets authorized is the full, unconstrained `objUnsignedUnit`.

### Finding Description
In `wallet.js`, `getSigner()` builds a `sign` function used whenever this device is asked to co-sign a unit for a shared/multisig address (`ifRemote` branch, reachable directly from any paired device that can send a `"sign"` message per the `case "sign":` handler at `wallet.js:251`): [1](#0-0) 

Before requesting a signature (and before the user is asked to approve), the code tries to classify the transaction so it can decide what confirmation dialog/text to surface: [2](#0-1) 

The classification logic:
1. Looks for a `payment` message with an output whose `amount` equals `prosaic_contract.CHARGE_AMOUNT` or `arbiter_contract.CHARGE_AMOUNT` (both are small, **fixed, publicly known constants**), and if the destination address is a known `shared_address` in the `prosaic_contracts`/`wallet_arbiter_contracts` table, it emits `confirm_contract_deposit` (or suppresses it if `peer_device_address === device_address`).
2. Otherwise, if any output pays a known contract-shared/peer address for the recorded `asset`/`my_address`, it emits `confirm_contract_claim` or `confirm_contract_sign`.
3. Only if none of these heuristics match does it fall back to the generic `confirm_on_other_devices` event.

Critically, `objUnsignedUnit` — the actual object that is fed into `objectHash.getUnitHashToSign()` and cryptographically authorized by the resulting signature — is **not constrained** by this classification. The heuristics only look at the *first* qualifying output amount; they do not verify that the unit's *entire* content (all messages, all outputs, fee-paying addresses, etc.) is limited to the recognized contract deposit/claim/sign pattern. A unit can legitimately contain multiple payment messages/outputs, definitions, AA triggers, data messages, etc., alongside one output that happens to match `CHARGE_AMOUNT` for a known shared address.

Because `bRequestedConfirmation` is a single boolean gate (set once per call to `sign`, `wallet.js:1977,2058,2085,2094`) and the `async.series` steps `return cb(true)` as soon as one heuristic fires, only the *first* matching, weaker-worded event (`confirm_contract_deposit`/`confirm_contract_claim`/`confirm_contract_sign`) is ever emitted for the whole unit — the stronger, unconditional `confirm_on_other_devices` prompt is suppressed. This is exactly the reported bug class: the thing shown for approval (a narrow, benign-sounding "contract deposit/claim/sign" dialog) is decided by extracting/matching a fragment of the payload, while the thing actually executed and authorized by the signature is the complete, unconstrained unit.

A malicious cosigner device (reachable as "a paired device" per the allowed threat surface) that already shares a `prosaic_contracts`/`wallet_arbiter_contracts` record with the victim (e.g., from a prior legitimate contract) can send a crafted `"sign"` request whose `unsigned_unit` contains:
- one output of exactly `CHARGE_AMOUNT` to the recognized shared/contract address (to trip the "claim"/"sign"/"deposit" heuristic and stop further checks), and
- additional messages/outputs that actually move much larger amounts, add unrelated payments, or otherwise are not benign contract activity.

The victim's wallet UI is driven by the emitted event (`confirm_contract_sign`/`confirm_contract_claim`), which presents a soft, contract-specific prompt rather than a full-detail confirmation, while the signature that is actually produced (`buf_to_sign`) authorizes the *entire* unsigned unit, not merely the recognized contract fragment.

### Impact Explanation
If the operator approves based on the misleading contract-specific prompt, the resulting signature legitimizes and helps complete a multisig unit whose real content (extra outputs/messages) was not what was displayed. For shared/multisig addresses this can lead to unauthorized spending of funds held at the shared address (the co-signer approves signing something believed to be a narrow contract deposit/claim, but the signature is valid for the full transaction, including unrelated/larger outputs), i.e., concrete unauthorized spending — matching the required "concrete unauthorized spending" bar for this class of report.

### Likelihood Explanation
Reaching this path only requires being a paired device that is already a co-signer/counterparty in a `prosaic_contract`/`arbiter_contract` relationship with the victim (a normal outcome of any prior contract interaction), and sending a `"sign"` message with a unit that includes one CHARGE_AMOUNT-valued output alongside other, unrelated content. `CHARGE_AMOUNT` is a fixed protocol constant, so crafting a matching output is trivial. The heuristic is purely amount/address-based and does not cryptographically bind the "reason for confirmation" to the exact set of outputs approved, so exploitation likelihood is moderate to high wherever this specific confirmation-suppression behavior is relied upon by the operator to gauge risk.

### Recommendation
- Bind the confirmation dialog to the exact unit content, not to a matched fragment: verify that *all* messages/outputs in `objUnsignedUnit` are consistent with the recognized contract deposit/claim/sign pattern (e.g., exactly one payment message, exactly the expected output(s)) before suppressing the generic `confirm_on_other_devices` prompt.
- Never let a partial match (single matching output) short-circuit evaluation of the rest of the unit; iterate over *all* outputs/messages and require the unit be fully explained by the recognized use case before downgrading the warning.
- Surface the full unit content (all outputs/messages, not just the "reason") in every confirmation event so the operator's approval is always tied to what will actually be signed.

### Proof of Concept
1. Attacker device D (already a `peer_device_address` on a `prosaic_contracts`/`wallet_arbiter_contracts` row shared with victim device V, from a legitimate earlier contract) crafts an `unsigned_unit` containing:
   - message 0: `payment` with outputs `[{address: shared_address, amount: CHARGE_AMOUNT}, {address: attacker_drain_address, amount: <large>}]`
2. D sends `{"subject":"sign", "body":{address: shared_address, signing_path:"r.0", unsigned_unit}}` to V.
3. On V, `wallet.js` `case "sign"` validates the message and calls `findAddress` → `getSigner().sign()`.
4. The `async.series` step 2 in `sign()` finds the `CHARGE_AMOUNT` output addressed to the known shared address and emits `confirm_contract_sign` (or `confirm_contract_claim`), suppressing the generic `confirm_on_other_devices` dialog: [3](#0-2) 
5. If the UI built on top of `ocore` renders a narrow "sign contract" prompt for this event without listing the full outputs, the operator approves believing only the contract-related deposit is being authorized.
6. `buf_to_sign = objectHash.getUnitHashToSign(objUnsignedUnit)` is signed over the *whole* unit including the drain output, and the resulting signature is returned to D, which can now finalize and broadcast a unit that pays the attacker the large amount from the shared address — unauthorized spending achieved via a misleading approval prompt.
