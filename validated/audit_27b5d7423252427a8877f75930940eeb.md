### Title
Unchecked ERC721 `transferFrom` Return in Bridge Unlock Path Allows Silent Asset Loss or Unauthorized Cross-Chain Minting — (`contracts/service_chain/bridge/BridgeTransferERC721.sol`)

---

### Summary

`BridgeTransferERC721` calls `IERC721(_tokenAddress).transferFrom(...)` in two places without verifying success. The ERC20 sibling contract correctly uses OpenZeppelin's `SafeERC20` wrapper for all token movements, but the ERC721 path has no equivalent protection. A registered non-standard ERC721 token whose `transferFrom` silently succeeds without moving the token (e.g., via a fallback function) can cause: (a) permanent loss of a user's bridged NFT in `handleERC721Transfer`, or (b) unauthorized cross-chain minting in `requestERC721Transfer`.

---

### Finding Description

**Location 1 — `handleERC721Transfer`, line 69:**

```solidity
IERC721(_tokenAddress).transferFrom(address(this), _to, _tokenId);
```

This call is made **after** all state mutations have already been committed:
- `_setHandledRequestTxHash(_requestTxHash)` — nonce marked as handled
- `handleNoncesToBlockNums[_requestedNonce] = _requestedBlockNumber` — block recorded
- `_updateHandleNonce(_requestedNonce)` — lower/upper nonce advanced
- `emit HandleValueTransfer(...)` — event emitted

If `transferFrom` silently does nothing (non-reverting non-standard ERC721), the nonce is permanently consumed and the recipient never receives the NFT. There is no retry path. [1](#0-0) 

**Location 2 — `requestERC721Transfer`, line 129:**

```solidity
IERC721(_tokenAddress).transferFrom(msg.sender, address(this), _tokenId);
_requestERC721Transfer(_tokenAddress, msg.sender, _to, _tokenId, _extraData);
```

If `transferFrom` silently succeeds without moving the token, `_requestERC721Transfer` proceeds to emit `RequestValueTransferEncoded` and increment `requestNonce`. The counterpart bridge's operator will then call `handleERC721Transfer` on the other chain, minting or releasing an NFT to the recipient — without the bridge ever having custody of the source token. [2](#0-1) 

**Contrast with ERC20 path (protected):**

`BridgeTransferERC20` imports and uses `SafeERC20` for every token movement:

```solidity
using SafeERC20 for IERC20;
...
IERC20(_tokenAddress).safeTransfer(_to, _value);       // handleERC20Transfer
IERC20(_tokenAddress).safeTransferFrom(...);            // requestERC20Transfer
IERC20(_token).safeTransfer(feeReceiver, fee);          // BridgeFee
``` [3](#0-2) [4](#0-3) 

The ERC721 path imports no safe wrapper and performs no success check.

---

### Impact Explanation

**`handleERC721Transfer` path:** The bridge nonce for the cross-chain request is permanently consumed (`closedValueTransferVotes[nonce] = true`, `lowerHandleNonce` advanced) before the transfer executes. A silent failure means the user's NFT is locked on the source chain forever and never delivered on the destination chain. This is an unauthorized permanent loss of a bridged asset. [5](#0-4) 

**`requestERC721Transfer` path:** A silent `transferFrom` failure causes the bridge to emit a `RequestValueTransferEncoded` event and increment `requestNonce` without holding the NFT. The counterpart bridge's operators will process this event and mint or release an NFT to the recipient on the other chain. This is unauthorized minting of a bridged asset. [2](#0-1) 

---

### Likelihood Explanation

The token address must be registered by the bridge owner (`onlyRegisteredToken` modifier in `_requestERC721Transfer`). However:

1. Once a non-standard ERC721 is registered (even inadvertently), **any unprivileged user** can call `requestERC721Transfer` to trigger the unauthorized minting path.
2. For `handleERC721Transfer`, the `_tokenAddress` parameter is passed by an operator and there is **no `onlyRegisteredToken` check** on that function — an operator can pass any token address. [6](#0-5) [7](#0-6) 

Non-standard ERC721 tokens with fallback functions that silently absorb unknown calls are a known class of deployed contracts. The ERC721 standard does not mandate revert-on-failure in the same way ERC20 does, and the `IERC721` interface declares `transferFrom` as returning nothing, making silent failures possible with non-conforming implementations. [8](#0-7) 

---

### Recommendation

Replace the bare `transferFrom` calls with `safeTransferFrom` (which reverts if the recipient is a contract that does not implement `onERC721Received`) or add explicit success verification. At minimum, mirror the ERC20 pattern by using a safe wrapper:

```solidity
// handleERC721Transfer — use safeTransferFrom instead of transferFrom
IERC721(_tokenAddress).safeTransferFrom(address(this), _to, _tokenId);

// requestERC721Transfer — use safeTransferFrom instead of transferFrom
IERC721(_tokenAddress).safeTransferFrom(msg.sender, address(this), _tokenId);
```

Alternatively, wrap the call in a low-level call and require success, analogous to how `SafeERC20.callOptionalReturn` works. [9](#0-8) 

---

### Proof of Concept

1. Deploy a malicious ERC721 contract `MaliciousNFT` whose `transferFrom` emits no event, moves no token, and does not revert (e.g., has an empty body or a fallback that accepts the call).
2. Bridge owner calls `registerToken(maliciousNFT, counterpartNFT)` on the source bridge.
3. Attacker calls `requestERC721Transfer(maliciousNFT, victim, tokenId, "")`.
4. `MaliciousNFT.transferFrom(attacker, bridge, tokenId)` silently succeeds — bridge does not hold the token.
5. `_requestERC721Transfer` passes the `onlyRegisteredToken` check, emits `RequestValueTransferEncoded`, increments `requestNonce`.
6. Counterpart bridge operators observe the event and call `handleERC721Transfer` on the destination chain.
7. Destination bridge mints or releases `counterpartNFT` to `victim` — an NFT is created on the destination chain without any NFT being locked on the source chain. [2](#0-1) [10](#0-9)
