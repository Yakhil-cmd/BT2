### Title
CCMenu API token scoped to a single stack in intent is honored engine-wide because the client record it authenticates is never bound to `stack_id` - (File: app/controllers/shipit/ccmenu_url_controller.rb)

### Summary
`CCMenuUrlController#client` (`app/controllers/shipit/ccmenu_url_controller.rb:15-18`) mints (or reuses) an `ApiClient` with `permissions: %w[read:stack]` but never sets `stack:` on it, then embeds that client's `authentication_token` in a URL intended to expose build status for **one** stack. Because `Api::CCMenuController#show` (`app/controllers/shipit/api/ccmenu_controller.rb:22-36`) authenticates via `ApiClient.authenticate(params[:token])` and resolves the target stack independently from `params[:stack_id]` (`stack` method, lines 29-31), the unscoped token is honored for **any** `stack_id` supplied in the URL, not just the one it was generated for.

### Finding Description [1](#0-0)  creates the `ApiClient` with `find_or_create_by!(creator: current_user, name: 'CCMenu Client')` and `permissions: %w[read:stack]`, but the `stack:` association is left `nil`. `ApiClient#check_permissions!` ( [2](#0-1) ) only verifies the requested `operation:scope` string is present in `permissions`; it performs no stack-identity comparison. Ordinarily `Api::BaseController#stacks` ( [3](#0-2) ) restricts a scoped client (`current_api_client.stack_id?`) to `Stack.where(id: current_api_client.stack_id)`, but `Api::CCMenuController` never uses `stacks`; it defines its own `stack` method ( [4](#0-3) ) that resolves `Stack.from_param!(params[:stack_id])` for whatever id is passed, with no cross-check against the token's owning stack (which is `nil` here anyway).

Since the `ApiClient` is `find_or_create_by!(creator:, name:)`-keyed only on the user and a fixed name, the same client/token is reused across every stack that user ever generates a CCMenu URL for. This produces a token that is intentionally shared/embedded in external CI dashboards (the CCMenu/CCTray XML feed use case), semantically scoped to "read status of stack X," but which in fact authorizes unauthenticated (no session, no team membership check) read access to `deploys_and_rollbacks` and status data for **every** stack in the Shipit instance.

Binding broken (equality that should hold but doesn't):
`stack the token is issued for` == `stack the token can read` — the left side is unset (`stack_id: nil`) while the right side is attacker/requester-controlled via `params[:stack_id]` at request time.

### Impact Explanation
Anyone who obtains one CCMenu token (e.g., from a build dashboard, screen share, leaked URL, or an external CI aggregator that stores/displays the URL) gains unauthenticated read access to deploy/task state for every stack managed by that Shipit instance, not just the one the token was displayed for. This matches the in-scope High-severity class "unauthenticated read of stack state, task streams or deploy output" via a token that should have been stack-scoped but was not.

### Likelihood Explanation
No privileged access, GitHub App key, or session is required to exploit once a token is obtained — only the existing token string and knowledge/guessing of another stack's `to_param` (owner/name/environment), which is generally discoverable (Shipit stack pages are named predictably and often visible in the Shipit UI to any team member). The vulnerable code path is exercised on every legitimate use of the CCMenu feature, since the unscoped token is created unconditionally.

### Recommendation
Set `stack:` on the `ApiClient` when creating/finding the CCMenu client in `CCMenuUrlController#client`, keyed per-stack (e.g., include the stack in the `find_or_create_by!` lookup rather than only `creator`/`name`), and have `Api::CCMenuController#stack` use the scoped `stacks` helper from `BaseController` (or explicitly verify `current_api_client.stack_id == stack.id`) instead of resolving `params[:stack_id]` unconditionally.

### Proof of Concept
1. As an authenticated Shipit user, open Stack A's settings page and trigger the CCMenu URL generation (`CCMenuUrlController#fetch`), obtaining `https://shipit.example.com/api/<owner>/<repo>/<env-A>/ccmenu.xml?token=T`.
2. Note that `T` authenticates an `ApiClient` with `permissions: ['read:stack']` and `stack_id: nil`.
3. Replay the same token against a different stack the requester should not be scoped to: `GET /api/<owner>/<repo>/<env-B>/ccmenu.xml?token=T`.
4. `Api::CCMenuController#authenticate_api_client` succeeds (`ApiClient.authenticate` only verifies the signed id), `require_permission :read, :stack` passes (permission array contains `read:stack`), and `stack` resolves Stack B directly from `params[:stack_id]` — the response discloses Stack B's deploy/build status even though the token was only ever intended for Stack A.
