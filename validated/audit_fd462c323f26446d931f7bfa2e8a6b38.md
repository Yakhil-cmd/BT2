### Title
Webhook signature is verified against a secret keyed by an attacker-controlled `repository.owner.login` field, while all event handlers act on the independent, unverified `repository.full_name` field - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
In multi-organization Shipit deployments (`secrets.github` keyed by organization), `WebhooksController#verify_signature` selects which organization's `webhook_secret` to HMAC-verify the payload against by reading `repository.owner.login` (or `organization.login`) straight out of the **unauthenticated** JSON body, before the signature has been checked. Every downstream event handler (`Handler#stacks` / `Handler#repository_name`, used by `PushHandler`, `StatusHandler`, `CheckSuiteHandler`, pull-request handlers, etc.) instead resolves the target `Repository`/`Stack` using `repository.full_name`, a second, independent field of that same unauthenticated body. Nothing ties the `owner.login` field used to pick the verification secret to the `full_name` field used to pick the target repository.

### Finding Description
`WebhooksController#verify_signature` computes:

```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end

def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
  head(422) unless verified
  ...
end
``` [1](#0-0) 

`Shipit.github(organization:)` looks up a per-organization config (and thus per-organization `webhook_secret`) via `github_app_config`: [2](#0-1) 

Once the signature check passes, `create` re-parses the same raw body and dispatches it to handlers keyed only by the `X-Github-Event` header: [3](#0-2) 

Every handler resolves its target repository/stack via `Handler#repository_name`, which reads a **different** JSON field — `repository.full_name` — not `repository.owner.login`:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [4](#0-3) 

`Repository.from_github_repo_name` splits this `owner/name` string and looks up the matching `Repository` row directly, independent of which org's secret validated the request: [5](#0-4) 

This is the exact analog called out in the report: the field used to authenticate the request (`repository.owner.login`, used to pick the verification key) is not the field the system actually acts on (`repository.full_name`, used to pick the repository/stack to write). Just as `ValidateVoteExtensions` trusted `extCommit.Round`/vote power without binding it to the actual validator set it claimed to represent, `verify_signature` trusts an attacker-supplied "owner" label to select a secret, then lets a completely separate attacker-supplied field drive the write path.

In a single-org deployment this is not exploitable because there is only one secret to consult (`github_default_organization` is `nil` and `Shipit.github` always returns the same app) — see `github_default_organization`/`github` in `lib/shipit.rb`. But in a multi-org configuration (as documented in `docs/setup.md`/`config/secrets.development.shopify.yml`, `github: { orgA: {...webhook_secret...}, orgB: {...webhook_secret...} }`), an attacker who is a legitimate administrator of `orgA` (and therefore knows `orgA`'s own `webhook_secret`, which they set when installing the shared Shipit GitHub App) can forge a payload where `repository.owner.login = "orgA"` but `repository.full_name = "orgB/victim-repo"`. `verify_signature` validates the HMAC using `orgA`'s secret and succeeds, but the handler that actually executes (`PushHandler`, `StatusHandler`, etc.) operates on `orgB/victim-repo`.

### Impact Explanation
Concretely this lets an attacker who legitimately controls one tenant organization in a multi-org Shipit deployment forge webhook events against a different organization's stacks:
- `StatusHandler` creates a commit status (`commit.create_status_from_github!`) for any commit whose SHA is guessed/known in the victim repository, using attacker-controlled `state`/`description`/`context`/`target_url`, which can flip `deployable_status`/CI gating used to authorize deploys — an unauthorized-deploy-adjacent primitive.
- `PushHandler`/`CheckSuiteHandler`/pull-request handlers can trigger syncs and state changes scoped to the victim's stack.

This breaks the trust binding "organization that authenticated == repository that is written," matching the Critical/High bar in scope (unauthorized deploy / cross-repository writes via commit status forgery), though the depth of exploitation depends on the deployment actually running multiple GitHub organizations under one Shipit instance and on predictable/known commit SHAs for the status-forgery path.

### Likelihood Explanation
Requires: (1) a Shipit deployment configured with more than one GitHub organization (each with distinct `webhook_secret`), and (2) the attacker being a legitimate webhook-secret holder for at least one of those organizations (e.g., an org admin who configured the shared App on their own org). This is a real, documented supported configuration (`docs/setup.md`, `secrets.development.shopify.yml` show multi-org `github:` maps), but it is not the default single-org case, so likelihood is moderate rather than universal.

### Recommendation
Bind the field used for signature-secret selection to the field used for repository resolution: verify the signature using the secret for the organization derived from `repository.full_name`'s owner segment (or reject payloads where `repository.owner.login` does not match the owner segment of `repository.full_name`) before any handler dispatch, and/or verify the signature against every configured organization's secret only after confirming ownership of the target repository through a trusted, out-of-band association (e.g., stored per-`Repository` organization mapping) rather than trusting an unauthenticated JSON field to select the verification key.

### Proof of Concept
1. Deploy Shipit with two organizations configured: `github: { "orgA": {webhook_secret: "secretA", ...}, "orgB": {webhook_secret: "secretB", ...} }`, where the attacker legitimately administers `orgA` and knows `secretA`.
2. Attacker crafts a JSON push payload:
```json
{
  "ref": "refs/heads/main",
  "after": "<victim head sha>",
  "repository": { "owner": { "login": "orgA" }, "full_name": "orgB/victim-repo" }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(secretA, body)>` and sends it with `X-Github-Event: push` to `/webhooks`.
4. `verify_signature` resolves `repository_owner` = `"orgA"`, fetches `orgA`'s `webhook_secret`, and the HMAC check passes (`app/controllers/shipit/webhooks_controller.rb:24-30`).
5. `create` dispatches to `PushHandler`, which resolves the target via `payload.dig('repository', 'full_name')` = `"orgB/victim-repo"` (`app/models/shipit/webhooks/handlers/handler.rb:32-38`), causing `orgB`'s stack to be synced/acted upon using a signature the attacker forged only with `orgA`'s secret.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
