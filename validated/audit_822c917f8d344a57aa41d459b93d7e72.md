### Title
Signature verification keyed on `repository.owner.login` while handler routes writes by `repository.full_name` allows cross-tenant `PullRequest` forgery via a no-secret organization - (File: `app/controllers/shipit/webhooks_controller.rb`, `lib/shipit/github_app.rb`, `app/models/shipit/webhooks/handlers/pull_request/assigned_handler.rb`)

### Summary
`Shipit::WebhooksController#verify_signature` selects the `GitHubApp` (and therefore the HMAC secret) using `params.dig('repository','owner','login')`, but `AssignedHandler#repository` (and every other `pull_request` handler using `Repository.from_github_repo_name`) resolves the target repository using the independent `repository.full_name` field of the same attacker-controlled JSON body. Since these two fields are never cross-checked for consistency, and `GitHubApp#verify_webhook_signature` returns `true` unconditionally when the selected organization's config has no `webhook_secret`, an attacker can pick a "no-secret" organization for `owner.login` to bypass all HMAC verification while pointing `full_name` at any real victim repository to mutate its `PullRequest` record.

### Finding Description
The broken binding: the code implicitly assumes `params.repository.owner.login == params.repository.full_name.split('/').first`, i.e. that the field used to select the verifying secret is the same tenant as the field used to resolve the affected record. This is never enforced.

- `WebhooksController#verify_signature` computes `repository_owner` from `params.dig('repository','owner','login')` and calls `Shipit.github(organization: repository_owner)` [3](#0-2) .
- `GitHubApp#verify_webhook_signature` returns `true` immediately if that organization's `webhook_secret` is blank [4](#0-3) , which is a documented/supported configuration state for multi-org Shipit deployments (`config/secrets.development.shopify.yml`, `docs/setup.md` "Using Multiple Github Applications").
- `AssignedHandler#repository` resolves the target repository via `Shipit::Repository.from_github_repo_name(params.repository.full_name)`, which simply splits `full_name` on `/` and looks up `owner`/`name` in the DB — with zero reference to `repository.owner.login` [5](#0-4) [1](#0-0) .
- `AssignedHandler#process` then looks up the persisted `Shipit::PullRequest` scoped to that resolved repository and calls `pull_request.update(github_pull_request: params.pull_request)` [6](#0-5) .

Exploit flow: attacker sends `POST /webhooks` with header `X-Github-Event: pull_request` and a JSON body where `repository.owner.login = "no-secret-org"` (a configured org with `webhook_secret: nil`) but `repository.full_name = "victim-org/victim-repo"` (the real target), `action = "assigned"`, and a `pull_request` payload matching an existing `Shipit::PullRequest#number` on the victim stack. `verify_signature` looks up `Shipit.github(organization: "no-secret-org")`, whose `webhook_secret` is blank, so `verify_webhook_signature` short-circuits to `true` regardless of the (even absent) `X-Hub-Signature` header. The request proceeds to `AssignedHandler`, which resolves `victim-org/victim-repo` from `full_name` and overwrites that repo's `PullRequest#github_pull_request` — data that other logic (e.g. `blocked?`/status-derived gating) may read to decide whether a stack is blocked for deploys.

Existing guards fail because: `drop_unhandled_event` only checks the event type is registered, not the payload's internal consistency; `ExplicitParameters` (`params do ... end`) only validates the shape/types of fields, not cross-field tenant binding; and there is no code anywhere that asserts `repository.owner.login` matches the owner embedded in `repository.full_name`.

### Impact Explanation
An attacker who owns no repository related to the victim, and controls only a GitHub org that happens to be configured in Shipit without a `webhook_secret`, can write to `Shipit::PullRequest` records belonging to an arbitrary victim repository/stack that IS otherwise properly secret-protected. This is a payload for one repository (the no-secret org) mutating another repository's (the victim's) persisted record — matching the "Critical: a payload for one repository mutating another's stack, commit, task or team" category. The blast radius extends to any handler using `Repository.from_github_repo_name(params.repository.full_name)` for routing (e.g. `OpenedHandler`, `ClosedHandler`, `LabeledHandler`, `UnlabeledHandler`, `ReopenedHandler`, `EditedHandler`), not just `AssignedHandler`. It is repeatable against any stack/repo whose owner/name is known or guessable, without rate limiting on `/webhooks`.

### Likelihood Explanation
This requires: (1) at least one Shipit-configured GitHub organization exists with a blank `webhook_secret` — an explicitly documented, supported configuration in `docs/setup.md`/`config/secrets.development.shopify.yml`; and (2) a victim stack/repository whose `full_name` is known (repo names are typically public/discoverable). The attacker needs no Shipit credentials, no GitHub App keys, and no access to the victim repo — only knowledge of a no-secret org name and the victim's `owner/name` string, both learnable from public Shipit UI or GitHub. This is trivially repeatable via a single unauthenticated HTTP POST per forged event.

### Recommendation
Bind repository resolution and signature verification to the same value: derive the verifying organization from the same field used for the eventual repository/stack lookup (or vice versa), and reject any webhook where `repository.owner.login` does not match the owner segment of `repository.full_name`. Additionally, treat a blank `webhook_secret` as a configuration error rather than an implicit bypass — require operators to set a `webhook_secret` for every configured organization, and fail closed (`head(422)`) instead of returning `true` from `verify_webhook_signature` when it is absent.

### Proof of Concept
Minitest plan (`test/controllers/shipit/webhooks_controller_test.rb`-style, no live GitHub):
1. Configure `Shipit.secrets.github` with two orgs: `"no-secret-org"` (no `webhook_secret`) and `"victim-org"` (with a `webhook_secret`), mirroring `test/dummy/config/secrets_double_github_app.yml`.
2. Create `victim_repo = Shipit::Repository.create!(owner: "victim-org", name: "victim-repo")`, a `Shipit::Stack` on it with `blocking_statuses` configured, and a `Shipit::PullRequest` with a known `number` and initial `github_pull_request`.
3. POST to `/webhooks` with header `X-Github-Event: pull_request`, no valid `X-Hub-Signature` (or a garbage one), and body: `{"action":"assigned","number":<pr.number>,"pull_request":{...,"assignees":[{"login":"attacker"}]},"repository":{"owner":{"login":"no-secret-org"},"full_name":"victim-org/victim-repo"},"sender":{"login":"attacker"}}`.
4. Assert response is `200 OK` (not `422`), proving the forged, unsigned request for the victim repo was accepted purely because `owner.login` pointed at the no-secret org.
5. Reload `pull_request` and assert `pull_request.github_pull_request["assignees"]` now equals the attacker-forged assignees array — i.e. `pull_request.reload.github_pull_request.dig("assignees").first["login"] == "attacker"` — demonstrating a write to `victim-org/victim-repo`'s persisted `PullRequest` performed without ever presenting `victim-org`'s `webhook_secret`.
6. Contrast: repeat step 3 with `repository.owner.login` set to `"victim-org"` (i.e., no divergence) and no valid signature; assert `422` is returned and the `PullRequest` is unchanged — establishing that the divergence between `owner.login` and `full_name` is exactly what breaks the invariant.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
