Found it: the webhook signature verification is keyed off `repository_owner`, which is derived from the `repository.owner.login` field, but the actual repository the webhook acts on is derived from `repository.full_name` — a **different, unauthenticated field of the same unverified payload**. Because signature verification happens against the whole raw body with a secret selected by parsing an unverified field, and multi-tenant Shipit deployments configure a **separate `webhook_secret` per GitHub organization**, an attacker who knows (or controls) any one organization's `webhook_secret` in a multi-org Shipit install can forge a payload whose `repository.owner.login` matches the org they know the secret for, while `repository.full_name` (used by `Handler#repository_name`/`Repository.from_github_repo_name`) points at a **different organization's/repository's stack**. The HMAC only proves "this body was signed with organization X's secret" — it does not bind that signature to the specific repository object the handlers subsequently act upon. ### Title
Webhook signature is bound to `repository.owner.login`, not to `repository.full_name` used for the actual write - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects a per-organization `GitHubApp`/`webhook_secret` using `repository_owner`, parsed from the unverified JSON body (`params.dig('repository','owner','login')`). Once the HMAC check passes, the same raw, attacker-controlled payload is dispatched unchanged to `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`. Handlers (e.g. `PushHandler`, `StatusHandler`) determine which `Stack`/`Repository` to mutate using `payload.dig('repository', 'full_name')` — a field that is never itself checked against the organization whose secret validated the signature.

### Finding Description
This mirrors the bad-debt bug's structural flaw: a value used to authorize an action (fully-repaid debt / verified signature) does not equal the value the action actually operates on (the NFT's real market value / the specific repository being mutated). Here, the equality that should hold is:

`organization_whose_secret_verified_signature == organization_owning_the_repository_the_handler_writes_to`

but the code only checks:
`verify_webhook_signature(signature, raw_body)` using `Shipit.github(organization: repository_owner)`

where `repository_owner` and `repository.full_name` are two independently-controlled fields of the *same unverified JSON body*. In a single-organization Shipit instance this is harmless (there is only one secret, so any successfully-signed payload is trusted regardless of which field is read). But in a multi-organization deployment — which the engine explicitly supports via `secrets.github` being a hash keyed by organization login, see `Shipit.github_app_config` and `config/secrets.development.shopify.yml` — each organization gets its **own independent `webhook_secret`**. A user/attacker with legitimate GitHub App admin access to Organization A (and thus knowledge of Organization A's `webhook_secret`, e.g. via their own GitHub App settings page) can craft a POST where `repository.owner.login = "OrgA"` (so `verify_signature` picks OrgA's secret and passes) while `repository.full_name = "OrgB/some-repo"` and `after`/`ref` point at an arbitrary SHA/branch. `PushHandler#process` will then call `stack.sync_github(expected_head_sha: ...)` against OrgB's stacks, and other handlers (`StatusHandler`, `CheckSuiteHandler`, `MembershipHandler`) similarly act on data keyed off `repository.full_name` or `organization.login` without re-validating that these fields match the organization that produced a valid signature. ### Impact Explanation
This lets a party who legitimately controls one configured GitHub organization's webhook secret trigger status/push/check-suite/membership side effects against stacks/repositories belonging to a *different* organization configured in the same Shipit instance — e.g. forcing `sync_github` on another org's stack, injecting forged commit statuses via `StatusHandler`, or creating/removing `Team`/`Membership` records cross-organization. This crosses an authentication boundary (Organization A's credentials being usable to affect Organization B's data) which the rules classify under cross-organization/cross-repository writes.

### Likelihood Explanation
Requires (a) a Shipit deployment configured with multiple GitHub organizations (a documented, supported configuration — see `secrets.development.shopify.yml`), and (b) the attacker possessing legitimate control of at least one configured organization's GitHub App / webhook secret (a realistic "unprivileged relative to the other org" attacker, not requiring any Shipit session or token). Given these preconditions, forging the JSON body and its HMAC is trivial since the secret is known to the attacker for their own org.

### Recommendation
After `verify_signature` succeeds for organization `repository_owner`, re-derive the target `Repository`/`Stack` via `Repository.from_github_repo_name(payload.dig('repository','full_name'))` and assert that repository's owner matches `repository_owner` (the same field used to select the signing secret) before dispatching to handlers. Alternatively, bind handlers to operate only on repositories whose recorded owner org equals the authenticated organization.

### Proof of Concept
1. Configure Shipit with two orgs, `orga` and `orgb`, each with a distinct `webhook_secret` (as in `config/secrets.development.shopify.yml`).
2. As someone with access to OrgA's GitHub App settings (or its `webhook_secret`), craft a `push` event body:
   ```json
   {
     "ref": "refs/heads/main",
     "after": "<attacker-chosen-sha>",
     "repository": { "owner": { "login": "orga" }, "full_name": "orgb/target-repo" }
   }
   ```
3. Compute `X-Hub-Signature: sha1=<hmac using orga's webhook_secret>` over this exact raw body.
4. POST to `/shipit/webhooks`. `verify_signature` resolves `Shipit.github(organization: "orga")` and successfully validates the signature.
5. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("orgb/target-repo")` and calls `sync_github(expected_head_sha: "<attacker-chosen-sha>")` on OrgB's stack, despite the signature only proving trust from OrgA.

      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([

    end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
