The binding at risk: **the organization whose webhook secret authenticates the request** (`repository_owner` = `params.dig('repository', 'owner', 'login')` in `WebhooksController#verify_signature`) must equal **the repository whose Stack gets written/synced** (`repository.full_name` used in `Handler#repository_name` / `Handler#stacks`). ### Title
Webhook signature verification is bound to the wrong organization, allowing cross-repository event injection - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects the GitHub App whose `webhook_secret` is used for HMAC verification based on `repository_owner`, a value read directly from the unverified JSON body (`params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`). [1](#0-0) [2](#0-1)  The actual repository the event is applied to is taken from a *different* field of the same body, `repository.full_name`, in `Shipit::Webhooks::Handlers::Handler#repository_name` used by every handler (e.g. `PushHandler`) to resolve `Stack`s to mutate. [3](#0-2)  Because Shipit supports multiple GitHub Apps/organizations, each with its own `webhook_secret` selected by `Shipit.github(organization:)` [4](#0-3) , the field that picks the verification secret (`repository.owner.login`) is never bound to the field that determines which stack is written (`repository.full_name`).

### Finding Description
This breaks the equality that should hold: `organization_that_authenticated_the_signature == organization_that_owns_the_repository_being_written`.

In a multi-org deployment (documented in `docs/setup.md` "Using Multiple Github Applications" and exercised by `test/dummy/config/secrets_double_github_app.yml`) [5](#0-4) , an attacker who has installed their own legitimate GitHub App on an org they control (`attacker-org`) knows `attacker-org`'s `webhook_secret`. They can craft an arbitrary JSON payload where:
- `repository.owner.login` = `attacker-org` (or `organization.login` = `attacker-org`) — used only to select which secret verifies the HMAC.
- `repository.full_name` = `victim-org/victim-repo` — used by the handler to look up `Repository.from_github_repo_name` and the `Stack`s to act on.

`verify_signature` computes `Shipit.github(organization: repository_owner)` with `repository_owner` = `attacker-org`, fetches `attacker-org`'s `webhook_secret`, and successfully verifies the HMAC that the attacker legitimately computed with their own known secret. [1](#0-0)  The request then reaches `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` [6](#0-5) , and e.g. `PushHandler#process` resolves stacks via `repository_name` = `payload.dig('repository', 'full_name')` = `victim-org/victim-repo`, then calls `stack.sync_github(expected_head_sha: params.after)` on the victim's stacks. [7](#0-6) 

This is directly analogous to the H-13 root cause: the code checks one value (`userCrossChainCollaterals.length` / here, the signing-secret-selecting `repository_owner`) but the state mutation is driven by a different, unsynchronized value (post-removal length / here, `repository.full_name`), because the two are read from the same mutable structure at different points without an equality check binding them together.

### Impact Explanation
An attacker with a legitimate (self-owned) GitHub App installation, but no privileges on the victim org, can inject an authenticated-looking webhook that forces `GithubSyncJob`/`stack.sync_github` and related handler side effects (PR merge status changes, membership/team changes via `MembershipHandler`, commit statuses via `StatusHandler`) against a victim's stack, all attributed as if it came from the victim's own GitHub organization. This is an unauthorized cross-repository write into another tenant's Shipit state and can trigger sync/merge-adjacent side effects, matching the "cross-repository writes" / "unauthorized deploy" class of Critical impact.

### Likelihood Explanation
Requires only: (1) a multi-organization Shipit deployment (documented and supported first-class configuration), and (2) the attacker's own GitHub App installed on an org they control — no access to the victim's secrets, tokens, or repository is needed. The attacker fully controls both the payload and the valid signature for their own org's secret, so this is trivially and repeatedly exploitable via direct HTTP POST to `/webhooks`.

### Recommendation
Bind signature verification to the same repository identity the handlers act on: after verifying the HMAC with the secret for `repository_owner`, additionally assert that the verified organization matches the owner segment of `repository.full_name` (and of `organization.login` if present) before dispatching to handlers. Reject the request if these values diverge.

### Proof of Concept
1. Deploy Shipit with two configured GitHub orgs, `attacker-org` and `victim-org`, each with its own `webhook_secret` (per `docs/setup.md`'s multi-app config).
2. Attacker installs a GitHub App on `attacker-org` and obtains/knows `attacker-org`'s `webhook_secret`.
3. Attacker crafts a `push` payload: `{"ref": "refs/heads/master", "after": "<attacker-controlled sha>", "repository": {"full_name": "victim-org/victim-repo", "owner": {"login": "attacker-org"}}}`.
4. Attacker computes `X-Hub-Signature` using `attacker-org`'s known `webhook_secret` over the raw body and POSTs to `/webhooks` with header `X-Github-Event: push`.
5. `verify_signature` resolves `Shipit.github(organization: "attacker-org")`, verifies successfully, request proceeds.
6. `PushHandler#process` resolves `victim-org/victim-repo`'s stacks and calls `sync_github`, mutating victim state despite the request never being authenticated by `victim-org`'s secret.
